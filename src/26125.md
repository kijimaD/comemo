## 元コミット内容

`net/http` パッケージにおいて、`Request.Method` が空文字列の場合と "GET" の場合とで、その扱いをより一貫性のあるものにする。この変更はRuss Coxからのパッチに基づいている。特定のバグが特定されたわけではないが、新しいコードはより読みやすくなっている。

## 変更の背景

Goの `net/http` パッケージでは、HTTPクライアントがリクエストを送信する際に、`http.Request` の `Method` フィールドが空文字列の場合、デフォルトで "GET" メソッドとして扱われるという慣習があります。これは、特に `http.NewRequest("", url, nil)` のようにメソッドを省略してGETリクエストを作成する際の利便性のために存在します。

しかし、この暗黙的なデフォルトの挙動がコードの様々な箇所で明示的に考慮されていない場合、以下のような問題が生じる可能性があります。

1.  **可読性の低下**: `req.Method == "" || req.Method == "GET"` のような条件式が散在し、メソッドが空文字列の場合に「GET」として扱われるという意図がコードを追わないと理解しにくい。
2.  **一貫性の欠如**: `Request.Method` が空文字列の場合の処理が、コードベース全体で統一されていない可能性がある。ある場所では `""` を「GET」として扱い、別の場所ではそうでない、といった状況はバグの温床となり得ます。
3.  **保守性の問題**: 将来的にデフォルトの挙動を変更する必要が生じた場合、複数の箇所を修正する必要があり、変更が困難になる。

このコミットは、これらの問題を解決し、`Request.Method` が空文字列の場合には常に明示的に「GET」として扱うためのヘルパー関数 `valueOrDefault` を導入し、それを使ってコードをリファクタリングすることで、上記の問題を解消しようとしています。コミットメッセージにある「No bug identified, but I didn't search exhaustively. The new code is easier to read.」という記述は、機能的なバグ修正というよりも、コード品質と可読性の向上を主眼としたリファクタリングであることを示唆しています。`Fixes #13621` は、このリファクタリングの必要性を示した内部的な課題トラッカーの番号であると考えられます。

## 前提知識の解説

*   **HTTPメソッド**: HTTPプロトコルにおいて、クライアントがサーバーにどのような操作を要求するかを示すものです。主要なメソッドにはGET（リソースの取得）、POST（データの送信）、PUT（リソースの更新）、DELETE（リソースの削除）、HEAD（ヘッダーのみの取得）、OPTIONS（通信オプションの取得）、TRACE（パスのトレース）などがあります。
*   **Go `net/http` パッケージ**: Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
    *   `http.Request`: HTTPリクエストを表す構造体で、`Method` フィールド（文字列型）にHTTPメソッドが格納されます。
    *   `http.Client`: HTTPリクエストを送信するためのクライアントです。`Do` メソッドを使ってリクエストを実行します。
    *   `http.NewRequest`: 新しい `http.Request` を作成する関数です。この関数でメソッドを空文字列にすると、内部的にGETリクエストとして扱われます。
*   **リダイレクト**: HTTPリクエストに対する応答として、サーバーがクライアントに別のURLへリクエストを再送信するよう指示する仕組みです。GETやHEADリクエストは通常、安全にリダイレクトに従うことができますが、POSTやPUTなどのメソッドは、リダイレクト時にメソッドがGETに変更されるなどの挙動の違いがあります。

## 技術的詳細

このコミットの核心は、`Request.Method` が空文字列の場合に「GET」をデフォルト値として適用する `valueOrDefault` という内部ヘルパー関数の導入と、その適用です。

`valueOrDefault` 関数は、以下のようなシンプルなロジックを持つと推測されます（コミットの差分から直接的な定義は読み取れませんが、その使用方法から推測できます）。

```go
// valueOrDefault は s が空文字列の場合に def を返し、そうでない場合は s を返す。
func valueOrDefault(s, def string) string {
    if s == "" {
        return def
    }
    return s
}
```

この関数を使用することで、コード内の `req.Method == "" || req.Method == "GET"` のような冗長なチェックを `valueOrDefault(req.Method, "GET") == "GET"` のように簡潔に記述できるようになります。これにより、メソッドが空文字列の場合には「GET」として扱うという意図がより明確になります。

具体的には、以下の3つのファイルで変更が加えられています。

1.  `src/net/http/client.go`: `Client.Do` メソッド内で、リダイレクトの挙動を決定する際に `req.Method` を評価する箇所で `valueOrDefault` が使用されています。これにより、空文字列のメソッドが常に「GET」として扱われ、適切なリダイレクトロジック（GET/HEADリクエストのリダイレクト、POST/PUTリクエストのリダイレクト）が適用されるようになります。
2.  `src/net/http/request.go`: `Request.isReplayable` メソッド内で、リクエストが再試行可能かどうかを判断するロジックにおいて `valueOrDefault` が使用されています。再試行可能なリクエストは通常、副作用のないGET、HEAD、OPTIONS、TRACEメソッドに限定されます。ここでも、空文字列のメソッドが「GET」として扱われることで、再試行可能性の判断が一貫して行われます。また、`switch` 文を使用することで、複数のメソッドチェックがより簡潔に記述されています。
3.  `src/net/http/transfer.go`: `newTransferWriter` 関数内で、リクエストのメソッドを転送ライターに設定する際に `valueOrDefault` が使用されています。これにより、転送処理においてもメソッドのデフォルト値が適切に設定されることが保証されます。

これらの変更により、`net/http` パッケージ全体で `Request.Method` の空文字列に対する挙動が統一され、コードの意図が明確になり、将来的な変更や拡張が容易になります。

## コアとなるコードの解説

### `src/net/http/client.go` の変更

`Client.Do` メソッドは、HTTPリクエストを実行する主要なエントリポイントです。このメソッド内で、リクエストのメソッドに基づいてリダイレクトの挙動を決定するロジックがあります。

変更前:
```go
if req.Method == "" || req.Method == "GET" || req.Method == "HEAD" {
    return c.doFollowingRedirects(req, shouldRedirectGet)
}
if req.Method == "POST" || req.Method == "PUT" {
    return c.doFollowingRedirects(req, shouldRedirectPost)
}
```
ここでは、`req.Method` が空文字列の場合も「GET」として扱われ、`shouldRedirectGet` ロジックが適用されていました。

変更後:
```go
method := valueOrDefault(req.Method, "GET")
if method == "" || method == "GET" || method == "HEAD" {
    return c.doFollowingRedirects(req, shouldRedirectGet)
}
if method == "POST" || method == "PUT" {
    return c.doFollowingRedirects(req, shouldRedirectPost)
}
```
まず `valueOrDefault(req.Method, "GET")` を呼び出して、`req.Method` が空文字列であれば `method` に "GET" を設定し、そうでなければ `req.Method` の値をそのまま使用します。その後の条件分岐では、この `method` 変数を使用することで、空文字列のケースを明示的に「GET」として扱いつつ、コードの意図をより明確にしています。`method == ""` のチェックは、`valueOrDefault` の結果が空文字列になることはないため、厳密には不要ですが、既存のパターンを維持しつつ、`valueOrDefault` の導入による変更を最小限に抑えるための過渡的な記述である可能性があります。

### `src/net/http/request.go` の変更

`Request.isReplayable` メソッドは、特定のリクエスト（特にボディを持たないGET、HEAD、OPTIONS、TRACEリクエスト）が、ネットワークエラー時などに安全に再試行可能であるかを判断します。

変更前:
```go
return r.Body == nil &&
    (r.Method == "GET" ||
    r.Method == "HEAD" ||
    r.Method == "OPTIONS" ||
    r.Method == "TRACE")
```
ここでも `r.Method` が直接評価されており、空文字列のケースは考慮されていませんでした。もし `r.Method` が空文字列の場合、この条件は `false` となり、再試行不可能と判断されてしまいます。

変更後:
```go
if r.Body == nil {
    switch valueOrDefault(r.Method, "GET") {
    case "GET", "HEAD", "OPTIONS", "TRACE":
        return true
    }
}
return false
```
まず `r.Body == nil` の条件を確認し、ボディがない場合にのみメソッドの評価に進みます。`switch valueOrDefault(r.Method, "GET")` を使用することで、`r.Method` が空文字列の場合には「GET」として評価され、再試行可能なメソッドのリストに含まれるかどうかが判断されます。これにより、空文字列のメソッドを持つリクエストも適切に再試行可能と判断されるようになり、一貫性が向上します。`switch` 文の導入により、複数の `||` で連結された条件式よりも可読性が向上しています。

### `src/net/http/transfer.go` の変更

`newTransferWriter` 関数は、HTTPリクエストのボディをネットワークに書き込むための内部的なヘルパー関数です。

変更前:
```go
t.Method = rr.Method
```
リクエストのメソッドをそのまま `transferWriter` の `Method` フィールドにコピーしていました。

変更後:
```go
t.Method = valueOrDefault(rr.Method, "GET")
```
`valueOrDefault(rr.Method, "GET")` を使用することで、`rr.Method` が空文字列の場合には「GET」が `transferWriter` の `Method` フィールドに設定されるようになります。これにより、転送処理の内部でもメソッドのデフォルト値が確実に適用され、後続の処理でメソッドが空文字列であることによる予期せぬ挙動を防ぎます。

これらの変更は、`net/http` パッケージの内部ロジックにおいて、`Request.Method` の空文字列と「GET」の間の曖昧さを解消し、より堅牢で理解しやすいコードベースを構築する上で重要な役割を果たしています。

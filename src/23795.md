## 変更の背景

このコミットは、Goコンパイラが従来のAST (Abstract Syntax Tree) ベースのコード生成から、SSA (Static Single Assignment) 形式の中間表現を用いた新しいバックエンドへの移行を進める中で行われました。SSA形式は、コンパイラがより高度な最適化を適用するための強力な基盤を提供します。

Go言語では、変数が関数のスコープを超えて参照される可能性がある場合（エスケープ解析によって判断される）、その変数はスタックではなくヒープに割り当てられます。ヒープ割り当てはガベージコレクションの対象となり、スタック割り当てに比べてコストが高くなりますが、変数の寿命が関数の実行期間を超える場合に必要不可欠です。

このコミットの主な目的は、SSAバックエンドがヒープに割り当てられる自動変数（Goコンパイラ内部では `PHEAP` フラグを持つ `PAUTO` 変数として扱われる）を正しく処理できるようにすることでした。具体的には、これらの変数に対してランタイムのメモリ割り当て関数（`new` に相当）を呼び出し、その結果として得られるアドレスをSSA形式で利用するメカニズムを確立します。これにより、SSAベースの最適化がヒープ割り当てされた変数にも適用できるようになり、コンパイラ全体の効率と性能が向上します。

また、SSAバックエンドへの移行作業中に見落とされていた `CALLstatic` オペレーションのAuxiliary情報処理の不備や、`OCONVNOP` という型変換ノードのSSA変換漏れといった既存のバグも同時に修正されています。これらは、SSA形式への完全な移行と安定稼働のために必要な修正でした。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。Go 1.7以降、コンパイラのバックエンドはSSA形式の中間表現を使用するようになりました。SSA形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化（例: 共通部分式除去、定数伝播、デッドコード除去など）が大幅に容易かつ効率的になります。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラが行う静的解析の一種で、プログラム中の変数がその宣言されたスコープ（通常は関数）を超えて「エスケープ」するかどうかを判断します。
*   **エスケープしない変数**: 関数の実行が終了すると同時に寿命が尽きる変数。これらは通常、高速なスタックメモリに割り当てられます。
*   **エスケープする変数**: 関数の実行が終了した後も参照され続ける可能性がある変数（例: ポインタが関数から返される、グローバル変数に格納される、チャネルを通じて他のゴルーチンに渡されるなど）。これらは、ガベージコレクションの対象となるヒープメモリに割り当てられます。
エスケープ解析は、メモリ割り当ての効率を最大化し、ガベージコレクションの負荷を軽減するために非常に重要です。

### スタックとヒープ

*   **スタック (Stack)**: 関数呼び出しやローカル変数の格納に使われるメモリ領域です。LIFO (Last-In, First-Out) 構造で、非常に高速な割り当てと解放が可能です。変数の寿命が関数の実行期間に限定される場合に利用されます。
*   **ヒープ (Heap)**: プログラム実行中に動的にメモリを割り当てるために使われる領域です。スタックに比べて割り当てと解放のオーバーヘッドが大きいですが、変数の寿命が不定である場合や、関数のスコープを超えてデータを共有する場合に利用されます。Goでは、ヒープに割り当てられたメモリはガベージコレクタによって管理されます。

### `PAUTO` と `PHEAP`

Goコンパイラの内部では、変数はその特性に応じて様々なフラグを持ちます。
*   `PAUTO`: 自動変数（ローカル変数）を示します。
*   `PHEAP`: `PAUTO` 変数の中でも、エスケープ解析の結果ヒープに割り当てられるべきと判断された変数に付与されるフラグです。

このコミットでは、`PAUTO | PHEAP` という形で、ヒープに割り当てられる自動変数を識別し、SSA形式で適切に処理するためのロジックが追加されています。

### `OCONVNOP`

`OCONVNOP` は、GoコンパイラのASTノードの一種で、「変換なし」を意味する型変換オペレーションです。これは、例えば `interface{}` 型から具体的な型への型アサーションなど、実行時には実質的なコード生成を伴わないが、型システム上は変換として扱われるようなケースで使われます。SSAバックエンドへの移行では、このようなASTノードもSSAオペレーションに正しく変換される必要がありました。

### `CALLstatic`

`CALLstatic` は、SSA形式における静的関数呼び出しを表すオペレーションです。コンパイラは、プログラム中の関数呼び出しをSSA形式の `CALLstatic` オペレーションに変換し、その後の最適化やコード生成に利用します。

### Aux (Auxiliary Information)

SSA形式のオペレーション（`Value`）には、そのオペレーションに関する追加情報（Auxiliary Information）を格納するためのフィールドがあります。
*   `AuxInt`: 整数値を格納するためのフィールド。
*   `Aux`: 任意のインターフェース型を格納するためのフィールド。
このコミットでは、`CALLstatic` オペレーションが `AuxInt` ではなく `Aux` を使用するように変更されており、より柔軟な補助情報の格納が可能になっています。

## 技術的詳細

このコミットは主に `src/cmd/compile/internal/gc/ssa.go`、`src/cmd/compile/internal/ssa/gen/AMD64.rules`、および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の3つのファイルに影響を与えています。

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルは、Goコンパイラのフロントエンド（AST）からSSA中間表現への変換ロジックを担っています。

1.  **`ODCL` (変数宣言) の処理**:
    *   `ODCL` ノードが `PHEAP` フラグを持つ変数（ヒープにエスケープする自動変数）を宣言している場合、特別な処理が追加されました。
    *   ランタイムのメモリ割り当て関数 `callnew` を呼び出し、その変数の型に応じたメモリをヒープに確保します。
    *   `prealloc` マップに、変数と割り当てられたメモリのアドレスを関連付けて保存します。
    *   最終的に、変数の `Heapaddr` フィールド（ヒープ上のアドレスを指す）に、`callnew` で得られたアドレスを代入するSSA命令を生成します。これにより、SSAバックエンドはヒープ上の変数にアクセスできるようになります。
    *   ランタイム自体が `PHEAP` 変数を使用しようとすると `log.Fatalf` でエラーを出すガードも追加されています。これは、ランタイムコードは通常、ヒープ割り当てを避けるべきであるという原則に基づいています。

2.  **`OAS` (代入) の処理のリファクタリング**:
    *   以前は `OAS` ノードの処理が `stmt` 関数内に直接記述されていましたが、`assign` という新しいヘルパー関数に抽出されました。
    *   `assign` 関数は、代入の右辺をSSA値に変換し、左辺がSSA対応変数 (`ONAME` かつ `canSSA`) であればその変数のSSA値を更新します。
    *   SSA対応でない変数への代入は、メモリへのストア操作として扱われ、`ssa.OpStore` オペレーションが生成されます。
    *   このリファクタリングにより、コードの可読性と保守性が向上し、今後のSSA変換ロジックの拡張が容易になります。

3.  **`addr` 関数における `PAUTO | PHEAP` のアドレス解決**:
    *   `addr` 関数は、ASTノードのアドレスをSSA値として取得する役割を担います。
    *   `PAUTO | PHEAP` フラグを持つ変数に対して、その `Name.Heapaddr` フィールド（ヒープ上のアドレスを指すSSA値）を返すロジックが追加されました。これにより、ヒープに割り当てられた変数のアドレスをSSA形式で正しく参照できるようになります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルは、AMD64アーキテクチャ向けのSSA最適化ルールを定義しています。

1.  **`StaticCall` ルールの修正**:
    *   `StaticCall` オペレーションのパターンマッチングにおいて、`[target]` (AuxInt) ではなく `{target}` (Aux) を使用するように変更されました。
    *   変更前: `(StaticCall [target] mem) -> (CALLstatic [target] mem)`
    *   変更後: `(StaticCall {target} mem) -> (CALLstatic {target} mem)`
    *   これは、`CALLstatic` オペレーションが、呼び出しターゲットに関する情報を `AuxInt` (整数) ではなく `Aux` (任意のインターフェース型) に格納するように変更されたことに対応しています。これにより、より複雑なターゲット情報をSSA形式で扱えるようになります。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

このファイルは、SSA形式の値をAMD64アーキテクチャ固有のオペレーションに書き換える（リライトする）ロジックを含んでいます。

1.  **`OpStaticCall` のリライトロジックの修正**:
    *   `OpStaticCall` のリライト処理において、`v.AuxInt` を使用していた箇所が `v.Aux` を使用するように変更されました。
    *   具体的には、`target := v.AuxInt` が `target := v.Aux` に変更され、`v.AuxInt = target` が `v.Aux = target` に変更されています。
    *   これは、`AMD64.rules` の変更と同様に、`CALLstatic` オペレーションが補助情報を `Aux` フィールドに格納するようになったことに対応する修正です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

*   **`ODCL` ノードの処理**:
    *   `if n.Left.Class&PHEAP == 0 { return }`：宣言される変数 `n.Left` がヒープにエスケープしない場合は、この新しいロジックをスキップします。
    *   `if compiling_runtime != 0 { log.Fatalf(...) }`：Goランタイム自体をコンパイルしている場合、ヒープにエスケープする変数は許可されません。これは、ランタイムのメモリ管理が非常に低レベルで行われるため、通常のヒープ割り当てを避けるべきであるという設計原則に基づいています。
    *   `palloc := prealloc[n.Left]` と `if palloc == nil { palloc = callnew(n.Left.Type); prealloc[n.Left] = palloc }`：`prealloc` マップは、既にヒープ割り当てが計画されている変数とその割り当て結果をキャッシュするために使用されます。もし初めてこの変数に出会った場合、`callnew(n.Left.Type)` を呼び出して、その変数の型に応じたメモリをヒープに割り当てます。`callnew` はGoの `new` キーワードに相当するランタイム関数を生成します。
    *   `s.assign(OAS, n.Left.Name.Heapaddr, palloc)`：ここで、新しく割り当てられたヒープアドレス (`palloc`) を、変数のヒープアドレスを指すフィールド (`n.Left.Name.Heapaddr`) に代入するSSA命令を生成します。これにより、SSAバックエンドは、この変数がヒープ上に存在し、そのアドレスが `palloc` であることを認識し、以降のアクセスでこのアドレスを使用するようになります。

*   **`OAS` ノードの処理と `assign` 関数の導入**:
    *   変更前は `OAS` (代入) のロジックが `stmt` 関数内に直接記述されており、冗長で複雑でした。
    *   変更後は `s.assign(n.Op, n.Left, n.Right)` というシンプルな呼び出しに置き換えられ、実際の代入処理は新しく導入された `assign` ヘルパー関数に委譲されています。
    *   `assign` 関数は、代入の右辺をSSA値に変換し、左辺がSSA対応の変数であればその変数のSSA値を更新します。SSA対応でない変数（例: 構造体のフィールドなど）への代入は、メモリへのストア操作 (`ssa.OpStore`) として扱われます。このリファクタリングにより、コードの整理と再利用性が向上しています。

*   **`addr` 関数における `PAUTO | PHEAP` のアドレス解決**:
    *   `case PAUTO | PHEAP: return s.expr(n.Name.Heapaddr)`：`addr` 関数は、特定のASTノードのアドレスをSSA値として取得する際に、`PAUTO | PHEAP` フラグを持つ変数に対しては、その変数の `Name.Heapaddr` フィールドが保持するSSA値（ヒープ上のアドレス）を直接返すように変更されました。これにより、ヒープに割り当てられた変数のアドレスをSSA形式で正しく取得できるようになります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更点

*   **`StaticCall` の `AuxInt` から `Aux` への移行**:

    *   この変更により、`CALLstatic` オペレーションは、単なる整数値だけでなく、より複雑な構造体やポインタなどの情報を補助情報として保持できるようになり、コンパイラの柔軟性が向上します。
    *   コミットメッセージにある「The rule for CALLstatic was missed during the Aux refactor」とは、SSAバックエンドのAuxiliary情報のリファクタリング中に、`CALLstatic` のルールがこの変更に追従していなかったことを指しており、このコミットでその修正が行われたことを示しています。
*   **`OCONVNOP` の変換漏れ修正**:
    *   コミットメッセージには「OCONVNOP wasn't converted」とありますが、提供されたdiffには `OCONVNOP` に直接関連するコード変更は含まれていません。これは、`OCONVNOP` の変換漏れが、このコミットに含まれる他の変更（例えば、`assign` 関数の導入や、SSA変換ロジックの全体的な改善）によって間接的に修正されたか、あるいはdiffには現れないが関連する他のファイルでの修正があった可能性を示唆しています。一般的に、`OCONVNOP` のようなノードは、SSA形式では特定のオペレーションに変換されるか、あるいは最適化によって除去されるべきものです。

## 変更の背景

このコミットは、Goコンパイラが従来のAST (Abstract Syntax Tree) ベースのコード生成から、SSA (Static Single Assignment) 形式の中間表現を用いた新しいバックエンドへの移行を進める中で行われました。SSA形式は、コンパイラがより高度な最適化を適用するための強力な基盤を提供します。

Go言語では、変数が関数のスコープを超えて参照される可能性がある場合（エスケープ解析によって判断される）、その変数はスタックではなくヒープに割り当てられます。ヒープ割り当てはガベージコレクションの対象となり、スタック割り当てに比べてコストが高くなりますが、変数の寿命が関数の実行期間を超える場合に必要不可欠です。

このコミットの主な目的は、SSAバックエンドがヒープに割り当てられる自動変数（Goコンパイラ内部では `PHEAP` フラグを持つ `PAUTO` 変数として扱われる）を正しく処理できるようにすることでした。具体的には、これらの変数に対してランタイムのメモリ割り当て関数（`new` に相当）を呼び出し、その結果として得られるアドレスをSSA形式で利用するメカニズムを確立します。これにより、SSAベースの最適化がヒープ割り当てされた変数にも適用できるようになり、コンパイラ全体の効率と性能が向上します。

また、SSAバックエンドへの移行作業中に見落とされていた `CALLstatic` オペレーションのAuxiliary情報処理の不備や、`OCONVNOP` という型変換ノードのSSA変換漏れといった既存のバグも同時に修正されています。これらは、SSA形式への完全な移行と安定稼働のために必要な修正でした。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。Go 1.7以降、コンパイラのバックエンドはSSA形式の中間表現を使用するようになりました。SSA形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化（例: 共通部分式除去、定数伝播、デッドコード除去など）が大幅に容易かつ効率的になります。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラが行う静的解析の一種で、プログラム中の変数がその宣言されたスコープ（通常は関数）を超えて「エスケープ」するかどうかを判断します。
*   **エスケープしない変数**: 関数の実行が終了すると同時に寿命が尽きる変数。これらは通常、高速なスタックメモリに割り当てられます。
*   **エスケープする変数**: 関数の実行が終了した後も参照され続ける可能性がある変数（例: ポインタが関数から返される、グローバル変数に格納される、チャネルを通じて他のゴルーチンに渡されるなど）。これらは、ガベージコレクションの対象となるヒープメモリに割り当てられます。
エスケープ解析は、メモリ割り当ての効率を最大化し、ガベージコレクションの負荷を軽減するために非常に重要です。

### スタックとヒープ

*   **スタック (Stack)**: 関数呼び出しやローカル変数の格納に使われるメモリ領域です。LIFO (Last-In, First-Out) 構造で、非常に高速な割り当てと解放が可能です。変数の寿命が関数の実行期間に限定される場合に利用されます。
*   **ヒープ (Heap)**: プログラム実行中に動的にメモリを割り当てるために使われる領域です。スタックに比べて割り当てと解放のオーバーヘッドが大きいですが、変数の寿命が不定である場合や、関数のスコープを超えてデータを共有する場合に利用されます。Goでは、ヒープに割り当てられたメモリはガベージコレクタによって管理されます。

### `PAUTO` と `PHEAP`

Goコンパイラの内部では、変数はその特性に応じて様々なフラグを持ちます。
*   `PAUTO`: 自動変数（ローカル変数）を示します。
*   `PHEAP`: `PAUTO` 変数の中でも、エスケープ解析の結果ヒープに割り当てられるべきと判断された変数に付与されるフラグです。

このコミットでは、`PAUTO | PHEAP` という形で、ヒープに割り当てられる自動変数を識別し、SSA形式で適切に処理するためのロジックが追加されています。

### `OCONVNOP`

`OCONVNOP` は、GoコンパイラのASTノードの一種で、「変換なし」を意味する型変換オペレーションです。これは、例えば `interface{}` 型から具体的な型への型アサーションなど、実行時には実質的なコード生成を伴わないが、型システム上は変換として扱われるようなケースで使われます。SSAバックエンドへの移行では、このようなASTノードもSSAオペレーションに正しく変換される必要がありました。

### `CALLstatic`

`CALLstatic` は、SSA形式における静的関数呼び出しを表すオペレーションです。コンパイラは、プログラム中の関数呼び出しをSSA形式の `CALLstatic` オペレーションに変換し、その後の最適化やコード生成に利用します。

### Aux (Auxiliary Information)

SSA形式のオペレーション（`Value`）には、そのオペレーションに関する追加情報（Auxiliary Information）を格納するためのフィールドがあります。
*   `AuxInt`: 整数値を格納するためのフィールド。
*   `Aux`: 任意のインターフェース型を格納するためのフィールド。
このコミットでは、`CALLstatic` オペレーションが `AuxInt` ではなく `Aux` を使用するように変更されており、より柔軟な補助情報の格納が可能になっています。

## 技術的詳細

このコミットは主に `src/cmd/compile/internal/gc/ssa.go`、`src/cmd/compile/internal/ssa/gen/AMD64.rules`、および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の3つのファイルに影響を与えています。

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルは、Goコンパイラのフロントエンド（AST）からSSA中間表現への変換ロジックを担っています。

1.  **`ODCL` (変数宣言) の処理**:
    *   `ODCL` ノードが `PHEAP` フラグを持つ変数（ヒープにエスケープする自動変数）を宣言している場合、特別な処理が追加されました。
    *   ランタイムのメモリ割り当て関数 `callnew` を呼び出し、その変数の型に応じたメモリをヒープに確保します。
    *   `prealloc` マップに、変数と割り当てられたメモリのアドレスを関連付けて保存します。
    *   最終的に、変数の `Heapaddr` フィールド（ヒープ上のアドレスを指す）に、`callnew` で得られたアドレスを代入するSSA命令を生成します。これにより、SSAバックエンドはヒープ上の変数にアクセスできるようになります。
    *   ランタイム自体が `PHEAP` 変数を使用しようとすると `log.Fatalf` でエラーを出すガードも追加されています。これは、ランタイムコードは通常、ヒープ割り当てを避けるべきであるという原則に基づいています。

2.  **`OAS` (代入) の処理のリファクタリング**:
    *   以前は `OAS` ノードの処理が `stmt` 関数内に直接記述されていましたが、`assign` という新しいヘルパー関数に抽出されました。
    *   `assign` 関数は、代入の右辺をSSA値に変換し、左辺がSSA対応変数 (`ONAME` かつ `canSSA`) であればその変数のSSA値を更新します。
    *   SSA対応でない変数への代入は、メモリへのストア操作として扱われ、`ssa.OpStore` オペレーションが生成されます。
    *   このリファクタリングにより、コードの可読性と保守性が向上し、今後のSSA変換ロジックの拡張が容易になります。

3.  **`addr` 関数における `PAUTO | PHEAP` のアドレス解決**:
    *   `addr` 関数は、ASTノードのアドレスをSSA値として取得する役割を担います。
    *   `PAUTO | PHEAP` フラグを持つ変数に対して、その `Name.Heapaddr` フィールド（ヒープ上のアドレスを指すSSA値）を返すロジックが追加されました。これにより、ヒープに割り当てられた変数のアドレスをSSA形式で正しく参照できるようになります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルは、AMD64アーキテクチャ向けのSSA最適化ルールを定義しています。

1.  **`StaticCall` ルールの修正**:
    *   `StaticCall` オペレーションのパターンマッチングにおいて、`[target]` (AuxInt) ではなく `{target}` (Aux) を使用するように変更されました。
    *   変更前: `(StaticCall [target] mem) -> (CALLstatic [target] mem)`
    *   変更後: `(StaticCall {target} mem) -> (CALLstatic {target} mem)`
    *   これは、`CALLstatic` オペレーションが、呼び出しターゲットに関する情報を `AuxInt` (整数) ではなく `Aux` (任意のインターフェース型) に格納するように変更されたことに対応しています。これにより、より複雑なターゲット情報をSSA形式で扱えるようになります。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

このファイルは、SSA形式の値をAMD64アーキテクチャ固有のオペレーションに書き換える（リライトする）ロジックを含んでいます。

1.  **`OpStaticCall` のリライトロジックの修正**:
    *   `OpStaticCall` のリライト処理において、`v.AuxInt` を使用していた箇所が `v.Aux` を使用するように変更されました。
    *   具体的には、`target := v.AuxInt` が `target := v.Aux` に変更され、`v.AuxInt = target` が `v.Aux = target` に変更されています。
    *   これは、`AMD64.rules` の変更と同様に、`CALLstatic` オペレーションが補助情報を `Aux` フィールドに格納するようになったことに対応する修正です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

*   **`ODCL` ノードの処理**:
    *   `if n.Left.Class&PHEAP == 0 { return }`：宣言される変数 `n.Left` がヒープにエスケープしない場合は、この新しいロジックをスキップします。
    *   `if compiling_runtime != 0 { log.Fatalf(...) }`：Goランタイム自体をコンパイルしている場合、ヒープにエスケープする変数は許可されません。これは、ランタイムのメモリ管理が非常に低レベルで行われるため、通常のヒープ割り当てを避けるべきであるという設計原則に基づいています。
    *   `palloc := prealloc[n.Left]` と `if palloc == nil { palloc = callnew(n.Left.Type); prealloc[n.Left] = palloc }`：`prealloc` マップは、既にヒープ割り当てが計画されている変数とその割り当て結果をキャッシュするために使用されます。もし初めてこの変数に出会った場合、`callnew(n.Left.Type)` を呼び出して、その変数の型に応じたメモリをヒープに割り当てます。`callnew` はGoの `new` キーワードに相当するランタイム関数を生成します。
    *   `s.assign(OAS, n.Left.Name.Heapaddr, palloc)`：ここで、新しく割り当てられたヒープアドレス (`palloc`) を、変数のヒープアドレスを指すフィールド (`n.Left.Name.Heapaddr`) に代入するSSA命令を生成します。これにより、SSAバックエンドは、この変数がヒープ上に存在し、そのアドレスが `palloc` であることを認識し、以降のアクセスでこのアドレスを使用するようになります。

*   **`OAS` ノードの処理と `assign` 関数の導入**:
    *   変更前は `OAS` (代入) のロジックが `stmt` 関数内に直接記述されており、冗長で複雑でした。
    *   変更後は `s.assign(n.Op, n.Left, n.Right)` というシンプルな呼び出しに置き換えられ、実際の代入処理は新しく導入された `assign` ヘルパー関数に委譲されています。
    *   `assign` 関数は、代入の右辺をSSA値に変換し、左辺がSSA対応の変数であればその変数のSSA値を更新します。SSA対応でない変数（例: 構造体のフィールドなど）への代入は、メモリへのストア操作 (`ssa.OpStore`) として扱われます。このリファクタリングにより、コードの整理と再利用性が向上しています。

*   **`addr` 関数における `PAUTO | PHEAP` のアドレス解決**:
    *   `case PAUTO | PHEAP: return s.expr(n.Name.Heapaddr)`：`addr` 関数は、特定のASTノードのアドレスをSSA値として取得する際に、`PAUTO | PHEAP` フラグを持つ変数に対しては、その変数の `Name.Heapaddr` フィールドが保持するSSA値（ヒープ上のアドレス）を直接返すように変更されました。これにより、ヒープに割り当てられた変数のアドレスをSSA形式で正しく取得できるようになります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更点

*   **`StaticCall` の `AuxInt` から `Aux` への移行**:
    *   これらの変更は、`StaticCall` オペレーションが、呼び出しターゲットに関する補助情報を `AuxInt` (整数) ではなく、より汎用的な `Aux` (インターフェース型) フィールドに格納するように変更されたことに対応しています。
    *   `AMD64.rules` では、パターンマッチングの構文が `[target]` から `{target}` に変更され、`rewriteAMD64.go` では、`v.AuxInt` へのアクセスが `v.Aux` へのアクセスに置き換えられています。
    *   この変更により、`CALLstatic` オペレーションは、単なる整数値だけでなく、より複雑な構造体やポインタなどの情報を補助情報として保持できるようになり、コンパイラの柔軟性が向上します。
    *   コミットメッセージにある「The rule for CALLstatic was missed during the Aux refactor」とは、SSAバックエンドのAuxiliary情報のリファクタリング中に、`CALLstatic` のルールがこの変更に追従していなかったことを指しており、このコミットでその修正が行われたことを示しています。
*   **`OCONVNOP` の変換漏れ修正**:
    *   コミットメッセージには「OCONVNOP wasn't converted」とありますが、提供されたdiffには `OCONVNOP` に直接関連するコード変更は含まれていません。これは、`OCONVNOP` の変換漏れが、このコミットに含まれる他の変更（例えば、`assign` 関数の導入や、SSA変換ロジックの全体的な改善）によって間接的に修正されたか、あるいはdiffには現れないが関連する他のファイルでの修正があった可能性を示唆しています。一般的に、`OCONVNOP` のようなノードは、SSA形式では特定のオペレーションに変換されるか、あるいは最適化によって除去されるべきものです。

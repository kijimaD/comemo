# [インデックス 21773] ファイルの概要

このコミットは、Go言語のツールチェインにおけるリンカ（`liblink`）およびコンパイラ（`cmd/gc`）が使用する命令コード（A-numbers）の定義を標準化し、アーキテクチャ非依存の処理パスで共通の命令をより容易に利用できるようにすることを目的としています。具体的には、`ANOP`, `ATEXT`, `AGLOBL`, `ACALL`, `AJMP`, `ARET`といった汎用的な命令に対して固定のA-numberを割り当て、各アーキテクチャ固有の定義からこれらを分離しました。これにより、Goコンパイラとリンカのコードベースの保守性と移植性が向上します。

## 変更の背景

Go言語のコンパイラとリンカは、様々なCPUアーキテクチャをサポートしています。これまでの実装では、`ACALL`（関数呼び出し）、`AJMP`（ジャンプ）、`ARET`（リターン）といった基本的な命令であっても、各アーキテクチャ（例: ARM, x86, PowerPC）のリンカ定義ファイル（`*.out.h`）内で個別に定義されていました。

このアプローチは、以下のような問題を引き起こしていました。

1.  **冗長性**: 共通のセマンティクスを持つ命令が、アーキテクチャごとに重複して定義されるため、コードの冗長性が高まっていました。
2.  **保守性の低下**: 共通命令の動作を変更する場合、複数のファイルにわたる修正が必要となり、エラーの発生リスクが高まりました。
3.  **アーキテクチャ非依存処理の複雑化**: コンパイラのバックエンドやリンカの最適化パスなど、アーキテクチャに依存しない処理を記述する際に、各アーキテクチャ固有の命令コードを考慮する必要があり、コードが複雑になっていました。

このコミットは、これらの問題を解決するために、Goツールチェイン内で使用される共通の命令コード（A-numbers）を中央集権的に定義し、アーキテクチャ非依存の処理パスがこれらの命令を統一的に参照できるようにすることを目的としています。これにより、コードの重複を排除し、保守性を向上させ、将来的な機能拡張や最適化を容易にすることが可能になります。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイルプロセス、特に`liblink`とA-numbersの概念について理解しておく必要があります。

### Go言語のコンパイルプロセス

Go言語のコンパイルプロセスは、おおよそ以下のステップで構成されます。

1.  **フロントエンド（`cmd/compile`）**: Goのソースコードを解析し、抽象構文木（AST）を生成します。その後、ASTを中間表現（IR）に変換し、型チェックや最適化を行います。
2.  **バックエンド（`cmd/compile`の一部）**: 中間表現を、Go独自の仮想命令セットである「A-numbers」に変換します。このA-numbersは、特定のCPUアーキテクチャに依存しない抽象的な命令コードです。
3.  **アセンブラ（`cmd/asm`）**: A-numbersを含むアセンブリコードを、オブジェクトファイル（`.o`）に変換します。この段階で、A-numbersはまだ具体的な機械語には変換されません。
4.  **リンカ（`cmd/link`、内部で`liblink`を使用）**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能バイナリを生成します。この過程で、`liblink`はA-numbersをターゲットCPUアーキテクチャの実際の機械語命令に変換します。

### A-numbers (Architecture-Independent Opcodes)

A-numbersは、Go言語のコンパイラとアセンブラが内部的に使用する、アーキテクチャ非依存の命令コードです。これらは、`AADD`（加算）、`AMOV`（移動）、`ACALL`（関数呼び出し）といった汎用的な操作を表します。A-numbersは、特定のCPUのレジスタや命令セットに直接対応するものではなく、Goコンパイラが異なるアーキテクチャ向けにコードを生成する際の中間抽象化レイヤーとして機能します。

例えば、`AADD`というA-numberは、x86アーキテクチャでは`ADD`命令に、ARMアーキテクチャでは`ADD`命令（またはそれに相当する命令）に変換されます。この抽象化により、Goコンパイラのバックエンドは、ターゲットアーキテクチャの詳細を意識することなく、共通のA-numbersを生成できます。

### `liblink` (Go Linker)

`liblink`は、Go言語のリンカである`cmd/link`の内部で使用されるライブラリです。その主な役割は、コンパイルされたオブジェクトファイル（A-numbersを含む）を読み込み、シンボル解決、再配置、そしてA-numbersからターゲットアーキテクチャの機械語への最終的な変換を行い、実行可能バイナリを生成することです。

このコミットは、`liblink`がA-numbersを処理する方法、特に共通の命令コードの定義方法に焦点を当てています。

## 技術的詳細

このコミットの技術的な核心は、Goツールチェインにおける命令コードの定義方法を、アーキテクチャ固有の分散型アプローチから、より中央集権的でアーキテクチャ非依存なアプローチへと移行した点にあります。

1.  **`include/link.h`における共通A-numbersの定義**:
    *   これまで各アーキテクチャのリンカヘッダファイル（例: `src/cmd/5l/5.out.h`）に散在していた`ACALL`, `ATEXT`, `AGLOBL`, `AJMP`, `ANOP`, `ARET`などの共通命令が、`include/link.h`という共通ヘッダファイル内の`enum`として一元的に定義されました。
    *   この`enum`には、`AXXX`（無効な命令）、`ADATA`（データセクション）、`AFUNCDATA`（関数データ）、`APCDATA`（PCデータ）、`ACHECKNIL`（nilチェック）、`AVARDEF`（変数定義）、`AVARKILL`（変数破棄）、`ADUFFCOPY`（Duff's Deviceによるコピー）、`ADUFFZERO`（Duff's Deviceによるゼロ初期化）といった、Goランタイムやコンパイラが内部的に使用する重要な命令も含まれています。
    *   `A_ARCHSPECIFIC`という新しい列挙値が導入され、これ以降のA-numbersはアーキテクチャ固有の命令コードとして扱われることが明示されました。これにより、共通命令とアーキテクチャ固有命令の範囲が明確に区別されます。

2.  **アーキテクチャ固有ヘッダファイルからの削除**:
    *   `src/cmd/5l/5.out.h` (ARM), `src/cmd/6l/6.out.h` (AMD64), `src/cmd/8l/8.out.h` (386), `src/cmd/9l/9.out.h` (PPC64) など、各アーキテクチャのリンカヘッダファイルから、`include/link.h`で定義された共通A-numbersの重複定義が削除されました。
    *   これにより、各アーキテクチャのヘッダファイルは、そのアーキテクチャ固有の命令コードのみを定義するようになり、コードの重複が大幅に削減されました。

3.  **コンパイラ（`cmd/gc`）およびリンカ（`liblink`）の更新**:
    *   Goコンパイラのソースコード（例: `src/cmd/gc/pgen.c`, `src/cmd/gc/plive.c`, `src/cmd/gc/popt.c`）では、これまで`arch.ACALL`のように`Arch`構造体を介して参照していた共通命令が、直接`ACALL`のように参照するように変更されました。これは、共通A-numbersがグローバルに利用可能になったためです。
    *   `liblink`内の各アーキテクチャ固有のコード生成部分（例: `src/liblink/obj5.c`, `src/liblink/obj6.c`など）からも、`LinkArch`構造体内の`ACALL`, `ADATA`などのフィールドが削除されました。これにより、これらのフィールドを介した間接的な参照が不要になりました。
    *   ARM (`5g`) および PPC64 (`9g`) アーキテクチャでは、`ABL`が`ACALL`の、`AB`/`ABR`が`AJMP`の、`ARETURN`が`ARET`のエイリアスとして扱われるようになりました。これは、これらのアーキテクチャで歴史的に使用されてきた命令名と、新しい標準化されたA-numbersとの互換性を保つための措置です。`src/cmd/5l/5.out.h`や`src/cmd/9l/9.out.h`の末尾にエイリアスの定義が追加されています。

4.  **`cmd/dist/buildgc.go`の変更**:
    *   `buildgc.go`は、Goのビルドシステムの一部であり、コンパイラやリンカで使用される名前リストを生成する役割を担っています。このコミットでは、`mkanames`関数が`include/link.h`の内容も読み込むように変更されました。これにより、生成される名前リストに新しい共通A-numbersが適切に含まれるようになります。また、エイリアスや`A_ARCHSPECIFIC`のような特殊なA-numbersを適切に処理するためのロジックが追加されました。

これらの変更により、Goツールチェインは、よりクリーンでモジュール化された命令コード定義を持つことになり、将来的なアーキテクチャサポートの追加や、コンパイラ・リンカの最適化がより容易になります。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、その変更の概要は以下の通りです。

*   **`include/link.h`**:
    *   `Prog.as`オペコードとして、`ACALL`, `ACHECKNIL`, `ADATA`, `ADUFFCOPY`, `ADUFFZERO`, `AEND`, `AFUNCDATA`, `AGLOBL`, `AJMP`, `ANOP`, `APCDATA`, `ARET`, `ATEXT`, `ATYPE`, `AUNDEF`, `AUSEFIELD`, `AVARDEF`, `AVARKILL`といった共通のアーキテクチャ非依存オペコードが`enum`として追加されました。
    *   `A_ARCHSPECIFIC`が、アーキテクチャ固有のオペコードの開始点として定義されました。
    *   `LinkArch`構造体から、`ACALL`, `ADATA`, `AEND`などの共通オペコードのフィールドが削除されました。

*   **`src/cmd/5g/galign.c`, `src/cmd/6g/galign.c`, `src/cmd/8g/galign.c`, `src/cmd/9g/galign.c`**:
    *   各アーキテクチャの`galign.c`ファイルから、`arch`構造体への共通オペコード（例: `arch.ACALL`, `arch.ADATA`）の割り当てが削除されました。これは、これらのオペコードがグローバルに定義されたため、`arch`構造体を介した参照が不要になったためです。

*   **`src/cmd/5g/opt.h`, `src/cmd/9g/opt.h`**:
    *   ARM (`5g`) および PPC64 (`9g`) の`opt.h`ファイルから、`AJMP`, `ACALL`, `ARET`のエイリアス定義が削除されました。これらのエイリアスは、リンカのヘッダファイル（`*.out.h`）に移動されました。

*   **`src/cmd/5l/5.out.h`, `src/cmd/6l/6.out.h`, `src/cmd/8l/8.out.h`, `src/cmd/9l/9.out.h`**:
    *   各アーキテクチャのリンカヘッダファイルから、`include/link.h`で定義された共通オペコードの重複定義が削除されました。
    *   ARM (`5l`) および PPC64 (`9l`) のヘッダファイルには、`AB = AJMP`, `ABL = ACALL`, `ARETURN = ARET`といったエイリアスが追加されました。これにより、既存のコードが新しい共通オペコード定義にスムーズに移行できるようになります。

*   **`src/cmd/gc/go.h`**:
    *   `Arch`構造体から、`ACALL`, `ACHECKNIL`, `ADATA`などの共通オペコードのフィールドが削除されました。

*   **`src/cmd/gc/pgen.c`, `src/cmd/gc/plive.c`, `src/cmd/gc/popt.c`**:
    *   Goコンパイラのこれらのファイルでは、`arch.AFUNCDATA`, `arch.AVARDEF`, `arch.AVARKILL`, `arch.ATEXT`, `arch.ATYPE`, `arch.ARET`, `arch.ACHECKNIL`, `arch.APCDATA`, `arch.AJMP`といった`arch`構造体を介した共通オペコードの参照が、直接`AFUNCDATA`, `AVARDEF`などのグローバルな定義に置き換えられました。

*   **`src/cmd/dist/buildgc.go`**:
    *   `mkanames`関数が、`include/link.h`の内容も読み込むように変更されました。これにより、共通オペコードの名前が適切に処理されるようになります。また、エイリアスや`A_ARCHSPECIFIC`の処理ロジックが追加されました。

*   **`src/liblink/obj5.c`, `src/liblink/obj6.c`, `src/liblink/obj8.c`, `src/liblink/obj9.c`**:
    *   各アーキテクチャの`liblink`オブジェクトファイルから、`LinkArch`構造体内の`ACALL`, `ADATA`などの共通オペコードのフィールドが削除されました。また、`isdata`や`iscall`といったヘルパー関数も、共通オペコードがグローバルになったため削除されました。

## コアとなるコードの解説

このコミットの最も重要なコード変更は、`include/link.h`における共通A-numbersの定義と、それに伴う既存コードからの`arch`構造体を介した参照の削除です。

**`include/link.h`の変更（追加部分の抜粋）:**

```c
// Prog.as opcodes.
// These are the portable opcodes, common to all architectures.
// Each architecture defines many more arch-specific opcodes,
// with values starting at A_ARCHSPECIFIC.
enum {
	AXXX = 0,

	ACALL,
	ACHECKNIL,
	ADATA,
	ADUFFCOPY,
	ADUFFZERO,
	AEND,
	AFUNCDATA,
	AGLOBL,
	AJMP,
	ANOP,
	APCDATA,
	ARET,
	ATEXT,
	ATYPE,
	AUNDEF,
	AUSEFIELD,
	AVARDEF,
	AVARKILL,
	
	A_ARCHSPECIFIC, // first architecture-specific opcode value
};
```

この`enum`の導入により、`ACALL`や`ATEXT`といった命令は、Goツールチェイン全体で一意の固定された数値を持つことになります。`A_ARCHSPECIFIC`は、この共通命令の範囲の終わりを示し、これ以降の数値は各アーキテクチャ固有の命令に割り当てられます。

**`src/cmd/gc/pgen.c`の変更例（`arch.AFUNCDATA`から`AFUNCDATA`への変更）:**

変更前:
```c
	arch.gins(arch.AFUNCDATA, &nod, pnod);
```

変更後:
```c
	arch.gins(AFUNCDATA, &nod, pnod);
```

この変更は、コンパイラが命令を生成する際に、もはや`arch`構造体を介して`AFUNCDATA`の具体的な数値を取得する必要がないことを示しています。`AFUNCDATA`は`include/link.h`でグローバルに定義された定数であるため、直接参照できるようになりました。同様の変更が、`src/cmd/gc`内の他のファイル（`plive.c`, `popt.c`）や、`liblink`内のアーキテクチャ固有のコード生成部分でも行われています。

**`src/liblink/obj6.c`の変更例（`LinkArch`構造体からのフィールド削除）:**

変更前（`LinkArch`構造体の一部）:
```c
LinkArch linkamd64 = {
	// ...
	.ACALL = ACALL,
	.ADATA = ADATA,
	.AEND = AEND,
	.AFUNCDATA = AFUNCDATA,
	.AGLOBL = AGLOBL,
	.AJMP = AJMP,
	.ANOP = ANOP,
	.APCDATA = APCDATA,
	.ARET = ARET,
	.ATEXT = ATEXT,
	.ATYPE = ATYPE,
	.AUSEFIELD = AUSEFIELD,
};
```

変更後（該当フィールドが削除されている）:
```c
LinkArch linkamd64 = {
	// ...
	// 共通オペコードのフィールドは削除された
};
```

この変更は、`LinkArch`構造体が各アーキテクチャ固有のリンカの動作を定義するためのものであり、共通のA-numbersを保持する必要がなくなったことを意味します。これにより、`LinkArch`構造体の定義がより簡潔になり、アーキテクチャ固有の機能に集中できるようになりました。

これらの変更は、Goツールチェインの内部構造をより整理し、共通の概念を中央集権的に管理することで、将来的な開発と保守を容易にするための重要なステップです。

# [インデックス 23038] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における`gcDrainN`関数の動作を変更するものです。具体的には、GCが実行する作業量の計測単位を、これまでの「スキャンするオブジェクトの数」から「スキャン作業量（ポインタのトレース量）」へと変更しています。これにより、GCの作業量がより正確に、かつ時間的なコストに即した形で制御できるようになります。

## コミット

```
runtime: make gcDrainN in terms of scan work

Currently, the "n" in gcDrainN is in terms of objects to scan. This is
used by gchelpwork to perform a limited amount of work on allocation,
but is a pretty arbitrary way to bound this amount of work since the
number of objects has little relation to how long they take to scan.

Modify gcDrainN to perform a fixed amount off scan work instead. For
now, gchelpwork still performs a fairly arbitrary amount of scan work,
but at least this is much more closely related to howlong the work
will take. Shortly, we'll use this to precisely control the scan work
performed by mutator assists during allocation to achieve the heap
size goal.

Reviewed-on: https://go-review.googlesource.com/8835
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作するコンカレントなマーク＆スイープ方式を採用しています。GCの効率性とアプリケーションのパフォーマンスを両立させるためには、GCが実行する作業量を適切に制御することが重要です。

このコミット以前の`gcDrainN`関数は、GCが処理する作業量を「スキャンするオブジェクトの数」で定義していました。この方法は、特に`gchelpwork`（ミューテータアシストの一部として、アロケーション時にGC作業を補助的に行うメカニズム）において使用されていました。しかし、オブジェクトの数と、そのオブジェクトをスキャンするのにかかる時間（つまり実際の作業量）との間には直接的な相関関係がありませんでした。例えば、小さなオブジェクトを100個スキャンするのと、大きなオブジェクトを100個スキャンするのとでは、後者の方がはるかに多くのCPU時間やメモリ帯域を消費します。このため、「オブジェクト数」を基準とした作業量の制御は、GCのパフォーマンス予測を困難にし、GCの遅延やヒープサイズの変動に繋がる可能性がありました。

このコミットの目的は、`gcDrainN`が実行する作業量を、より実際の計算コストに近い「スキャン作業量」（ポインタのトレース量）で定義し直すことです。これにより、GCが実行する作業量をより正確に、かつ予測可能な形で制御できるようになります。特に、将来的にミューテータアシストがヒープサイズ目標を達成するために実行するスキャン作業量を厳密に制御するための基盤を築くことが意図されています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な概念と、関連する内部メカニズムについて理解しておく必要があります。

*   **Goのガベージコレクション (GC)**:
    GoのGCは、並行（Concurrent）、三色（Tri-color）、マーク＆スイープ（Mark-and-Sweep）方式を採用しています。
    *   **並行性**: GCの大部分は、ユーザープログラム（ミューテータ）と並行して実行されます。これにより、GCによるアプリケーションの一時停止（Stop-the-World: STW）時間を最小限に抑えることを目指しています。
    *   **三色マーキング**: GCはオブジェクトを以下の3つの色で分類し、到達可能性を判断します。
        *   **白 (White)**: まだGCによって訪問されていないオブジェクト。最終的に到達不可能と判断されれば回収対象となります。
        *   **灰 (Gray)**: 訪問済みだが、そのオブジェクトが参照する他のオブジェクト（子）がまだスキャンされていないオブジェクト。
        *   **黒 (Black)**: 訪問済みで、そのオブジェクトが参照する全ての子オブジェクトもスキャン済みのオブジェクト。黒いオブジェクトは到達可能であり、回収されません。
    *   **マークフェーズ**: GCのルート（グローバル変数、スタックなど）から到達可能なオブジェクトを特定し、マークします。このフェーズでオブジェクトは白から灰、そして黒へと変化していきます。
    *   **スイープフェーズ**: マークされなかった（白いままの）オブジェクトのメモリを解放し、再利用可能にします。このフェーズも並行して実行されます。

*   **スキャン作業 (Scan Work)**:
    GCのマークフェーズにおいて、灰色のオブジェクトが参照するポインタを辿り、その子オブジェクトを灰色にマークし、親オブジェクトを黒色に変化させる一連の処理を指します。この「ポインタを辿る」作業が「スキャン作業」であり、GCが消費するCPU時間やメモリ帯域の主要な要因となります。

*   **ミューテータアシスト (Mutator Assists)**:
    GoのGCは並行性を重視していますが、アプリケーションが非常に高速にメモリを確保し続けると、バックグラウンドのGCが追いつかなくなり、ヒープサイズが際限なく増加する可能性があります。これを防ぐため、Goランタイムは「ミューテータアシスト」というメカニズムを導入しています。
    ミューテータアシストとは、メモリを確保しようとするユーザーゴルーチン（ミューテータ）が、GCが遅れていると判断された場合に、そのアロケーション要求を満たす前に、GCのスキャン作業の一部を自ら実行することを強制される仕組みです。これにより、アプリケーション自身がGCの進行に貢献し、ヒープサイズの制御とGCの追いつきを助けます。プロファイリングツールで`runtime.gcAssistAlloc`として表示されることがあります。

*   **`gcWork`構造体**:
    GC作業の状態を管理するための内部構造体です。`scanWork`フィールドを持ち、これはGCが実行したスキャン作業量（ポインタのトレース量）を累積するために使用されます。

*   **`gcDrainN`関数**:
    Goランタイム内部の関数で、GCのスキャン作業を実行します。この関数は、GCワーカーゴルーチンやミューテータアシストによって呼び出され、灰色のオブジェクトを処理し、その子をマークする役割を担います。

*   **`gchelpwork`関数**:
    ミューテータアシストの一部として、アロケーション時にGC作業を補助的に行う関数です。この関数内で`gcDrainN`が呼び出され、一定量のGC作業が実行されます。

## 技術的詳細

このコミットの核心は、`gcDrainN`関数のインターフェースと内部ロジックの変更にあります。

変更前は、`gcDrainN`は`n`という整数値を受け取っていました。この`n`は「スキャンするオブジェクトの数」を意味していました。`gchelpwork`関数では、`workbuf{}.obj`の長さ（つまり、ワークバッファが保持できるオブジェクトの最大数）を`n`として`gcDrainN`に渡していました。これは、GCがアロケーション時に「ワークバッファ1つ分のオブジェクトをスキャンする」という形で作業量を制限していました。

変更後は、`gcDrainN`は`scanWork`という`int64`型の値を受け取るようになりました。この`scanWork`は「ポインタのトレース量」を意味します。`gchelpwork`関数では、`helpScanWork`という定数（現在のコミットでは`500`）を`scanWork`として`gcDrainN`に渡すようになりました。これにより、アロケーション時に「500個のポインタをトレースする」という形でGC作業量を制限するようになります。

`gcDrainN`の内部では、`gcw.scanWork`というフィールドが導入され、実行されたスキャン作業量が累積されるようになりました。ループは、`gcw.scanWork`が`targetScanWork`（初期の`gcw.scanWork`に引数で渡された`scanWork`を加算した値）に達するまで継続されます。これにより、`gcDrainN`は指定された`scanWork`量に「およそ」相当する作業を実行するようになります。コミットメッセージにあるように、これはベストエフォートであり、ワークバッファの取得に失敗した場合は指定量より少なくなる可能性や、オブジェクト単位でスキャンが行われるため指定量より多くなる可能性も示唆されています。

この変更により、GCの作業量がオブジェクトのサイズに依存せず、より実際の計算コスト（ポインタの数）に比例する形で制御できるようになります。これは、GCのパフォーマンスをより予測可能にし、特にミューテータアシストがヒープサイズ目標を達成するために必要なGC作業量を正確に調整するための重要なステップとなります。

## コアとなるコードの解説

1.  **`gchelpwork`関数の変更**:
    *   変更前: `const n = len(workbuf{}.obj)` で、ワークバッファのオブジェクト容量を`n`として定義し、`gcDrainN(&gcw, n)`を呼び出していました。これは「オブジェクト数」を基準とした作業量でした。
    *   変更後: `const helpScanWork = 500 // pointers to trace` で、`helpScanWork`という定数（500）を定義し、`gcDrainN(&gcw, helpScanWork)`を呼び出しています。これにより、`gcDrainN`に渡される作業量の単位が「ポインタのトレース量」に変わりました。コメントで「pointers to trace」と明記されており、意図が明確になっています。

2.  **`gcDrainN`関数のシグネチャ変更**:
    *   変更前: `func gcDrainN(gcw *gcWork, n int)` で、`n`は`int`型でした。
    *   変更後: `func gcDrainN(gcw *gcWork, scanWork int64)` で、引数名が`scanWork`に変わり、型が`int64`になりました。これは、より大きな作業量を表現するため、また「スキャン作業量」という概念を明確にするためです。

3.  **`gcDrainN`関数の内部ロジック変更**:
    *   変更前: `for i := 0; i < n; i++ { ... }` というループで、`n`回（オブジェクト数分）処理を繰り返していました。
    *   変更後: `targetScanWork := gcw.scanWork + scanWork` で目標スキャン作業量を計算し、`for gcw.scanWork < targetScanWork { ... }` というループに変更されました。このループは、`gcw`（`gcWork`構造体）に累積される`scanWork`が目標値に達するまで処理を続けます。これにより、`gcDrainN`は「指定されたスキャン作業量」を達成するまで実行されるようになりました。`gcw.scanWork`は、`gcDrainN`がポインタをトレースするたびに増加するカウンターであり、実際の作業量を反映します。

これらの変更により、GoのGCは、アロケーション時のミューテータアシストを含むGC作業の量を、より正確で予測可能な「スキャン作業量」に基づいて制御できるようになりました。これは、GCのレイテンシを削減し、ヒープサイズの変動を抑える上で重要な改善です。

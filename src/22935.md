# [インデックス 22935] ファイルの概要

このコミットは、Go言語の標準ライブラリ `compress/flate` パッケージにおける、不正なハフマン符号化シーケンスの処理に関するバグ修正です。具体的には、ハフマンデコーダが不正なビットシーケンスを検出した場合に、それを0-lengthコードとして誤って解釈するのではなく、エラーとして適切に拒否するように変更されました。これにより、悪意のある、または破損した入力データによってデコンプレッサがハングアップする可能性が排除されます。

## 変更の背景

このコミットは、Go言語の `compress/flate` パッケージにおける、特定の不正な入力データに対する脆弱性を修正するために行われました。具体的には、Go issue #10426で報告された問題に対応しています。この問題は、「over-subscribed HCLenTree」（ハフマン符号長ツリーが過剰に定義されている状態）と呼ばれる、不正に構築されたハフマンツリーがデコンプレッサに与えられた場合に、デコンプレッサがハングアップする可能性があるというものでした。

従来の `compress/flate` の実装では、ハフマンデコード中に不正なビットシーケンスが検出された場合、それを有効な0-lengthコードとして誤って解釈してしまう可能性がありました。これは、デコンプレッサが無限ループに陥ったり、予期せぬ動作を引き起こしたりする原因となり、サービス拒否（DoS）攻撃に利用される可能性も秘めていました。このコミットは、このようなセキュリティ上のリスクと安定性の問題を解消することを目的としています。

## 前提知識の解説

### DEFLATE圧縮形式

DEFLATEは、可逆データ圧縮アルゴリズムであり、LZ77アルゴリズムとハフマン符号化の組み合わせによって機能します。多くの一般的な圧縮形式（ZIP、gzip、PNGなど）の基盤となっています。

### ハフマン符号化 (Huffman Coding)

ハフマン符号化は、データ圧縮に用いられる可変長符号化の一種です。データ内の文字の出現頻度に基づいて、頻繁に出現する文字には短いビット列を、稀にしか出現しない文字には長いビット列を割り当てます。これにより、平均ビット長を短縮し、データを効率的に圧縮します。

ハフマン符号化では、ハフマンツリーと呼ばれる二分木を構築し、そのツリーを辿ることでビット列を文字にデコードします。各文字はツリーの葉ノードに対応し、根ノードから葉ノードまでのパスがその文字のハフマンコードとなります。

### `compress/flate` パッケージ

Go言語の標準ライブラリ `compress/flate` は、DEFLATE圧縮形式の実装を提供します。このパッケージは、データの圧縮と解凍（デフレートとインフレート）を行うための機能を提供し、`compress/gzip` や `compress/zlib` などの他の圧縮パッケージの基盤としても利用されています。

### 不正なハフマン符号化シーケンス

ハフマン符号化では、各コードは一意であり、どのコードも他のコードのプレフィックス（接頭辞）にならないというプレフィックスフリーの特性を持っています。これにより、ビットストリームを曖昧さなくデコードできます。しかし、不正に生成された、または破損したデータストリームでは、このプレフィックスフリーの特性が破られたり、ハフマンツリーに存在しないビットシーケンスが出現したりすることがあります。このようなシーケンスは「不正なハフマン符号化シーケンス」と呼ばれ、デコーダはこれを適切に処理する必要があります。

## 技術的詳細

このコミットの核心は、`compress/flate` パッケージ内のハフマンデコーダが、不正なビットシーケンスを検出した際の挙動を変更することにあります。

従来の `inflate.go` の `huffSym` 関数では、ハフマンツリーを探索してシンボルをデコードする際に、`n`（現在のビットシーケンスの長さ）が `f.nb`（バッファ内の利用可能なビット数）よりも大きい場合、つまり、現在のビットシーケンスがバッファ内のビット数を超えている場合に、そのシーケンスを0-lengthコードとして扱ってしまう可能性がありました。これは、ハフマンツリーの構造によっては、有効なコードとして解釈されるべきではないビットパターンが、誤って「長さ0のコード」として処理され、結果としてデコーダが無限ループに陥る原因となっていました。

この修正では、`n` が `huffmanChunkBits` を超える場合の処理（ハフマンツリーの次のチャンクへの移動）の後に、`n <= f.nb` のチェックを移動させました。これにより、`n` が0である（つまり、有効なコードが見つからなかった）場合に、`CorruptInputError` を発生させてデコードを中断するロジックが、より早期に、かつ正確に適用されるようになります。

具体的には、`huffSym` 関数内でハフマンツリーを探索し、`chunk` からシンボルとコード長 `n` を取得した後、`n` が `huffmanChunkBits` を超える場合の追加のツリー探索ロジックが実行されます。この追加ロジックの後に、`n` が0であるかどうかのチェックが行われるようになりました。これにより、不正なビットシーケンスが0-lengthコードとして誤って解釈されることを防ぎ、代わりに `CorruptInputError` を返すことで、デコード処理を安全に終了させます。

## コアとなるコードの解説

### `src/compress/flate/inflate.go` の変更点

`inflate.go` の `huffSym` 関数は、ハフマン符号化されたビットストリームから次のシンボルをデコードする役割を担っています。この関数内の変更は非常に小さいですが、その影響は大きいです。

変更前は、以下のコードブロックがありました。

```go
		if n > huffmanChunkBits {
			chunk = h.links[chunk>>huffmanValueShift][(f.b>>huffmanChunkBits)&h.linkMask]
			n = uint(chunk & huffmanCountMask)
		}
		if n <= f.nb { // この条件が外側にあった
			if n == 0 {
				f.err = CorruptInputError(f.roffset)
				return 0, f.err
			}
		}
```

変更後は、`if n <= f.nb` の条件ブロックが、`if n > huffmanChunkBits` のブロックの**内側**に移動しました。

```go
		if n > huffmanChunkBits {
			chunk = h.links[chunk>>huffmanValueShift][(f.b>>huffmanChunkBits)&h.linkMask]
			n = uint(chunk & huffmanCountMask)
		}
		// この条件が内側に移動した
		if n <= f.nb { 
			if n == 0 {
				f.err = CorruptInputError(f.roffset)
				return 0, f.err
			}
			f.b >>= n
			f.nb -= n
			return int(chunk >> huffmanValueShift), nil
		}
```

この変更により、`n` が `huffmanChunkBits` を超える場合の追加のハフマンツリー探索（`h.links` を使用する部分）が完了した**後**に、`n` が0であるかどうかのチェックが実行されるようになりました。これにより、不正なビットシーケンスがハフマンツリーの探索中に0-lengthコードとして誤って解釈されることを防ぎ、代わりに `CorruptInputError` を返すことで、デコード処理を安全に終了させることができます。

### `src/compress/flate/flate_test.go` の変更点

`flate_test.go` に `TestInvalidEncoding` という新しいテストケースが追加されました。このテストは、不正なハフマン符号化シーケンスが与えられた場合に、デコーダが適切にエラーを返すことを検証します。

1.  `huffmanDecoder` を初期化し、`init([]int{1})` を呼び出しています。これは、長さ1のコードのみを認識する非常に単純なハフマンツリーをシミュレートしています。
2.  `decompressor` を初期化し、`f.r = bytes.NewReader([]byte{0xff})` で不正なバイトシーケンス `0xff` を入力として与えています。`0xff` は、この単純なハフマンツリーでは有効なコードとしてデコードできないビットパターンです。
3.  `f.huffSym(&h)` を呼び出してデコードを試みます。
4.  `err == nil` でエラーが返されなかった場合に `t.Fatal` を呼び出すことで、デコーダが不正なビットシーケンスを拒否し、エラーを返すことを期待しています。

このテストケースは、このコミットによって修正された問題が実際に解決されたことを確認するための重要な検証手段となります。

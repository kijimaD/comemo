# [インデックス 20738] ファイルの概要

このコミットは、Goランタイムにおける `runtime.SetFinalizer` 関数の挙動を修正し、ドキュメントを更新するものです。特に、グローバルに割り当てられたオブジェクト（リンカによって割り当てられる可能性のあるオブジェクト）に対して `SetFinalizer` が適用された際の、以前の「緩すぎる」挙動を是正し、クラッシュを回避しつつも、より正確なチェックを行うように改善しています。これにより、グローバルな割り当てに対するファイナライザが実行されない可能性があることを明確にし、そのチェックを厳密化しています。

## 変更の背景

Go 1.3のリリース直前、`runtime.SetFinalizer` 関数にグローバルに割り当てられたオブジェクト（`var Foo = &Object{}` のような、リンカによって割り当てられる可能性のあるオブジェクト）を渡すとクラッシュする問題（Issue #7656）が発生していました。このクラッシュを回避するため、一時的な措置として `SetFinalizer` のチェックが緩和されました。具体的には、`findObject` 関数がオブジェクトの基底アドレスを見つけられなかった場合（`base == nil` の場合）に、無条件でファイナライザの設定をスキップするという変更が行われました。

しかし、この緩和策は「緩すぎた」と判断されました。つまり、グローバルな割り当てだけでなく、本来ファイナライザが設定されるべき他の有効なケースまで誤って無視してしまう可能性があったのです。このコミットの目的は、この「緩すぎる」挙動を是正し、グローバルな割り当てに対してはファイナライザが実行されない可能性があることを明確にドキュメント化しつつ、それ以外の正当なヒープ割り当てオブジェクトに対してはファイナライザが正しく設定されるように、チェックを厳密化することでした。

## 前提知識の解説

### Goのガベージコレクション (GC) とファイナライザ

Goは自動メモリ管理（ガベージコレクション）を採用しています。プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったものをGCが自動的に解放します。

`runtime.SetFinalizer(obj, finalizer)` 関数は、特定のオブジェクト `obj` がガベージコレクタによって到達不可能と判断され、メモリが解放される直前に、指定された `finalizer` 関数を実行するように設定します。ファイナライザは、ファイルハンドルやネットワーク接続などの外部リソースをクリーンアップする際に役立ちますが、以下の重要な制約があります。

*   **実行の保証なし**: ファイナライザは、プログラムが正常終了する前に必ず実行されるとは限りません。特に、プログラムがクラッシュしたり、`os.Exit` などで終了したりした場合には実行されない可能性があります。
*   **実行タイミングの不確実性**: ファイナライザがいつ実行されるかはGCのタイミングに依存するため、予測できません。
*   **単一のゴルーチン**: すべてのファイナライザは単一のゴルーチンで順次実行されます。ファイナライザ内で時間のかかる処理を行うと、他のファイナライザの実行やGCの進行をブロックする可能性があります。

### Goのメモリ割り当てとセグメント

Goプログラムのメモリは、大きく分けて以下の領域に分類されます。

*   **ヒープ (Heap)**: `new()` や `make()` などで動的に割り当てられるメモリ領域。GCの管理対象となります。
*   **スタック (Stack)**: 関数のローカル変数などが割り当てられるメモリ領域。関数呼び出しのたびに確保・解放されます。
*   **データセグメント (Data Segment)**:
    *   `.text` (コードセグメント): 実行可能な機械語コードが格納されます。
    *   `.rodata` (読み取り専用データ): 定数や文字列リテラルなど、変更されないデータが格納されます。
    *   `.data` (初期化済みデータ): 初期値を持つグローバル変数や静的変数が格納されます。
    *   `.bss` (初期化なしデータ): 初期値を持たないグローバル変数や静的変数が格納されます（通常はゼロ初期化されます）。
    *   `.noptrdata` / `.noptrbss`: ポインタを含まないデータ（`noptr` は "no pointer" の略）。GCがスキャンする必要がないため、GCの効率化に寄与します。

グローバル変数（パッケージレベル変数）は、通常、プログラムの起動時にリンカによってデータセグメント（`.data` や `.bss`、`.noptrdata`、`.noptrbss`）に割り当てられます。これらのメモリはヒープとは異なり、GCの直接的な管理対象ではありません。`SetFinalizer` はヒープに割り当てられたオブジェクトに対して機能することを前提としているため、リンカによって割り当てられたオブジェクトにファイナライザを設定しようとすると問題が発生する可能性があります。

### `unsafe.Pointer` とメモリレイアウト

`unsafe.Pointer` は、Goの型システムを迂回して任意のメモリを指すことができる特殊なポインタ型です。このコミットでは、`unsafe.Pointer` を用いてメモリアドレスを `uintptr` に変換し、特定のメモリセグメントの範囲内にあるかどうかをチェックしています。

`noptrdata` と `enoptrbss` は、Goランタイム内部で定義されるシンボルで、それぞれ `.noptrdata` セグメントの開始アドレスと `.noptrbss` セグメントの終了アドレスを示します。これらのシンボルはリンカによって提供され、Goプログラムの静的メモリレイアウトを把握するために使用されます。

*   `var noptrdata struct{}`: `.noptrdata` セグメントの開始点を示すためのダミー変数。
*   `var enoptrbss struct{}`: `.noptrbss` セグメントの終了点を示すためのダミー変数。

これらの変数を使って、`uintptr(unsafe.Pointer(&noptrdata))` と `uintptr(unsafe.Pointer(&enoptrbss))` の範囲内にポインタがあるかどうかをチェックすることで、そのポインタがリンカによって割り当てられた（ヒープではない）メモリを指しているかどうかを判断します。

## 技術的詳細

このコミットの主要な技術的変更点は、`runtime.SetFinalizer` 関数内のオブジェクトの有効性チェックを改善したことです。

以前のGo 1.3リリース前の緩和策では、`findObject` 関数がオブジェクトの基底アドレスを見つけられなかった場合（`base == nil`）、無条件にファイナライザの設定をスキップしていました。これは、グローバルな割り当てがヒープ上にないため `findObject` が見つけられないことに起因するクラッシュを回避するためのものでした。

しかし、このコミットでは、`base == nil` のケースをさらに細分化し、以下の条件でファイナライザの設定をスキップまたはエラーとします。

1.  **ゼロサイズオブジェクトの扱い**: `e.data == unsafe.Pointer(&zerobase)` の場合、つまりゼロサイズのオブジェクト（`struct{}` など）に対しては、ファイナライザを設定しても意味がないため、引き続きスキップします。`zerobase` はランタイムが内部的に使用するゼロサイズのオブジェクトの共通アドレスです。
2.  **リンカ割り当てオブジェクトの識別**: `uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss))` の条件を追加しました。これは、`e.data` が `.noptrdata` から `.noptrbss` までの範囲、すなわちリンカによって割り当てられた静的メモリ領域内にあるかどうかをチェックします。この範囲内のオブジェクトに対しては、ファイナライザが実行されない可能性があるため、ファイナライザの設定をスキップします。
3.  **その他の無効なポインタ**: 上記のいずれの条件にも当てはまらず、かつ `base == nil` の場合は、`gothrow("runtime.SetFinalizer: pointer not in allocated block")` を呼び出してランタイムパニックを発生させます。これは、`e.data` がヒープ上の有効なオブジェクトを指していないにもかかわらず、リンカ割り当てでもゼロサイズでもない、不正なポインタであると判断されるためです。

この変更により、`SetFinalizer` はグローバルな割り当てによるクラッシュを回避しつつ、ヒープ上の有効なオブジェクトに対してのみファイナライザを設定するように、より賢明な判断を下せるようになりました。

また、`src/runtime/mfinal_test.go` のテストコードも更新されています。`TestFinalizerType` 内で `new(int)` の代わりに `new(T).v` を使用するように変更されています。これは、`new(int)` のような小さなオブジェクトが `tinyalloc` という最適化されたアロケータによって割り当てられる可能性があり、その場合、GCのタイミングやメモリ解放の挙動が予測しにくくなるためです。`struct` を介してポインタを含むオブジェクトを割り当てることで、より確実にヒープに割り当てられ、ファイナライザのテストが安定して実行されるようにしています。

```go
// linker-provided
var noptrdata struct{}
var enoptrbss struct{}

// ...

func SetFinalizer(obj interface{}, finalizer interface{}) {
	// ...
	_, base, _ := findObject(e.data)

	if base == nil {
		// 0-length objects are okay.
		if e.data == unsafe.Pointer(&zerobase) {
			return
		}

		// Global initializers might be linker-allocated.
		//	var Foo = &Object{}
		//	func main() {
		//		runtime.SetFinalizer(Foo, nil)
		//	}
		// The segments are, in order: text, rodata, noptrdata, data, bss, noptrbss.
		if uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss)) {
			return
		}
		gothrow("runtime.SetFinalizer: pointer not in allocated block")
	}

	// ...
}
```

*   **`noptrdata` と `enoptrbss`**: これらの変数は、Goのランタイムがリンカによって割り当てられたメモリセグメントの境界を特定するために使用されます。`unsafe.Pointer` を介してこれらの変数のアドレスを取得し、`uintptr` にキャストすることで、メモリ上の数値的な位置を比較できます。
*   **`if base == nil` ブロックの修正**:
    *   `base == nil` は、`e.data` がヒープ上の有効なオブジェクトを指していないことを意味します。
    *   `e.data == unsafe.Pointer(&zerobase)`: これはゼロサイズのオブジェクト（例: `struct{}`）を指している場合のチェックです。ゼロサイズのオブジェクトはGCの対象外であり、ファイナライザを設定しても意味がないため、ここで `return` します。
    *   `uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss))`: この行が今回のコミットの核心です。`e.data` が `noptrdata` セグメントの開始から `enoptrbss` セグメントの終了までの範囲内にあるかどうかをチェックします。この範囲は、リンカによって割り当てられた静的データ領域（ポインタを含まないデータ）に対応します。もし `e.data` がこの範囲内にある場合、それはヒープ割り当てではないため、ファイナライザを設定しても実行されない可能性があり、ここで `return` します。これが、グローバルな割り当てに対するファイナライザの挙動を修正する部分です。
    *   `gothrow("runtime.SetFinalizer: pointer not in allocated block")`: 上記のどの条件にも当てはまらない `base == nil` のケースは、`e.data` がヒープ上の有効なオブジェクトでも、ゼロサイズオブジェクトでも、リンカ割り当てオブジェクトでもない、不正なポインタであることを意味します。この場合、ランタイムパニックを発生させて、プログラマに問題があることを知らせます。

### `src/runtime/mfinal_test.go` の変更点

```go
func TestFinalizerType(t *testing.T) {
	// ...
	for i, tt := range finalizerTests {
		done := make(chan bool, 1)
		go func() {
			// allocate struct with pointer to avoid hitting tinyalloc.
			// Otherwise we can't be sure when the allocation will
			// be freed.
			type T struct {
				v int
				p unsafe.Pointer
			}
			v := &new(T).v
			*v = 97531
			runtime.SetFinalizer(tt.convert(v), tt.finalizer)
			v = nil
			runtime.GC()
			runtime.GC()
		}()
		// ...
	}

```

*   **`type T struct { v int; p unsafe.Pointer }` と `v := &new(T).v`**: 以前は `v := new(int)` のように直接 `int` のポインタを割り当てていました。しかし、`int` のような小さなオブジェクトは、Goランタイムの `tinyalloc` という最適化されたアロケータによって割り当てられることがあります。`tinyalloc` は、小さなオブジェクトをまとめて割り当てることで、メモリ割り当てのオーバーヘッドを削減しますが、そのメモリがいつGCによって解放されるか（ひいてはファイナライザがいつ実行されるか）が予測しにくくなる場合があります。
*   新しいコードでは、`int` と `unsafe.Pointer` を含む構造体 `T` を定義し、その `v` フィールドのアドレス `&new(T).v` を取得しています。構造体 `T` は `unsafe.Pointer` フィールドを持つため、`tinyalloc` の対象外となり、通常のヒープ割り当てが行われます。これにより、GCがオブジェクトをより確実に認識し、ファイナライザが期待通りに実行されることを保証し、テストの信頼性を高めています。

*   **実行の保証なし**: ファイナライザは、プログラムが正常終了する前に必ず実行されるとは限りません。特に、プログラムがクラッシュしたり、`os.Exit` などで終了したりした場合には実行されない可能性があります。
*   **実行タイミングの不確実性**: ファイナライザがいつ実行されるかはGCのタイミングに依存するため、予測できません。
*   **単一のゴルーチン**: すべてのファイナライザは単一のゴルーチンで順次実行されます。ファイナライザ内で時間のかかる処理を行うと、他のファイナライザの実行やGCの進行をブロックする可能性があります。

### Goのメモリ割り当てとセグメント

Goプログラムのメモリは、大きく分けて以下の領域に分類されます。

*   **ヒープ (Heap)**: `new()` や `make()` などで動的に割り当てられるメモリ領域。GCの管理対象となります。
*   **スタック (Stack)**: 関数のローカル変数などが割り当てられるメモリ領域。関数呼び出しのたびに確保・解放されます。
*   **データセグメント (Data Segment)**:
    *   `.text` (コードセグメント): 実行可能な機械語コードが格納されます。
    *   `.rodata` (読み取り専用データ): 定数や文字列リテラルなど、変更されないデータが格納されます。
    *   `.data` (初期化済みデータ): 初期値を持つグローバル変数や静的変数が格納されます。
    *   `.bss` (初期化なしデータ): 初期値を持たないグローバル変数や静的変数が格納されます（通常はゼロ初期化されます）。
    *   `.noptrdata` / `.noptrbss`: ポインタを含まないデータ（`noptr` は "no pointer" の略）。GCがスキャンする必要がないため、GCの効率化に寄与します。

グローバル変数（パッケージレベル変数）は、通常、プログラムの起動時にリンカによってデータセグメント（`.data` や `.bss`、`.noptrdata`、`.noptrbss`）に割り当てられます。これらのメモリはヒープとは異なり、GCの直接的な管理対象ではありません。`SetFinalizer` はヒープに割り当てられたオブジェクトに対して機能することを前提としているため、リンカによって割り当てられたオブジェクトにファイナライザを設定しようとすると問題が発生する可能性があります。

### `unsafe.Pointer` とメモリレイアウト

`unsafe.Pointer` は、Goの型システムを迂回して任意のメモリを指すことができる特殊なポインタ型です。このコミットでは、`unsafe.Pointer` を用いてメモリアドレスを `uintptr` に変換し、特定のメモリセグメントの範囲内にあるかどうかをチェックしています。

`noptrdata` と `enoptrbss` は、Goランタイム内部で定義されるシンボルで、それぞれ `.noptrdata` セグメントの開始アドレスと `.noptrbss` セグメントの終了アドレスを示します。これらのシンボルはリンカによって提供され、Goプログラムの静的メモリレイアウトを把握するために使用されます。

*   `var noptrdata struct{}`: `.noptrdata` セグメントの開始点を示すためのダミー変数。
*   `var enoptrbss struct{}`: `.noptrbss` セグメントの終了点を示すためのダミー変数。

これらの変数を使って、`uintptr(unsafe.Pointer(&noptrdata))` と `uintptr(unsafe.Pointer(&enoptrbss))` の範囲内にポインタがあるかどうかをチェックすることで、そのポインタがリンカによって割り当てられた（ヒープではない）メモリを指しているかどうかを判断します。

## 技術的詳細

このコミットの主要な技術的変更点は、`runtime.SetFinalizer` 関数内のオブジェクトの有効性チェックを改善したことです。

以前のGo 1.3リリース前の緩和策では、`findObject` 関数がオブジェクトの基底アドレスを見つけられなかった場合（`base == nil`）、無条件にファイナライザの設定をスキップしていました。これは、グローバルな割り当てがヒープ上にないため `findObject` が見つけられないことに起因するクラッシュを回避するためのものでした。

しかし、このコミットでは、`base == nil` のケースをさらに細分化し、以下の条件でファイナライザの設定をスキップまたはエラーとします。

1.  **ゼロサイズオブジェクトの扱い**: `e.data == unsafe.Pointer(&zerobase)` の場合、つまりゼロサイズのオブジェクト（`struct{}` など）に対しては、ファイナライザを設定しても意味がないため、引き続きスキップします。`zerobase` はランタイムが内部的に使用するゼロサイズのオブジェクトの共通アドレスです。
2.  **リンカ割り当てオブジェクトの識別**: `uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss))` の条件を追加しました。これは、`e.data` が `.noptrdata` から `.noptrbss` までの範囲、すなわちリンカによって割り当てられた静的メモリ領域内にあるかどうかをチェックします。この範囲内のオブジェクトに対しては、ファイナライザが実行されない可能性があるため、ファイナライザの設定をスキップします。
3.  **その他の無効なポインタ**: 上記のいずれの条件にも当てはまらず、かつ `base == nil` の場合は、`gothrow("runtime.SetFinalizer: pointer not in allocated block")` を呼び出してランタイムパニックを発生させます。これは、`e.data` がヒープ上の有効なオブジェクトを指していないにもかかわらず、リンカ割り当てでもゼロサイズでもない、不正なポインタであると判断されるためです。

この変更により、`SetFinalizer` はグローバルな割り当てによるクラッシュを回避しつつ、ヒープ上の有効なオブジェクトに対してのみファイナライザを設定するように、より賢明な判断を下せるようになりました。

また、`src/runtime/mfinal_test.go` のテストコードも更新されています。`TestFinalizerType` 内で `new(int)` の代わりに `new(T).v` を使用するように変更されています。これは、`new(int)` のような小さなオブジェクトが `tinyalloc` という最適化されたアロケータによって割り当てられる可能性があり、その場合、GCのタイミングやメモリ解放の挙動が予測しにくくなるためです。`struct` を介してポインタを含むオブジェクトを割り当てることで、より確実にヒープに割り当てられ、ファイナライザのテストが安定して実行されるようにしています。

## コアとなるコードの変更箇所

### `src/runtime/malloc.go`

*   `noptrdata` と `enoptrbss` というリンカ提供のダミー変数が追加されました。
*   `SetFinalizer` 関数内の `if base == nil` ブロックが大幅に修正されました。
    *   ゼロサイズオブジェクト (`e.data == unsafe.Pointer(&zerobase)`) のチェックが明示的に行われます。
    *   リンカ割り当てオブジェクト (`noptrdata` と `enoptrbss` の範囲内) のチェックが追加されました。
    *   上記以外の `base == nil` のケースでは `gothrow` が呼び出されるようになりました。

### `src/runtime/mfinal_test.go`

*   `TestFinalizerType` 関数内のテストケースで、`v := new(int)` の代わりに、ポインタを含む構造体 `T` を介して `v := &new(T).v` のようにオブジェクトを割り当てるように変更されました。これにより、`tinyalloc` を回避し、ファイナライザのテストの信頼性を向上させています。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更点

```go
// linker-provided
var noptrdata struct{}
var enoptrbss struct{}

// ...

func SetFinalizer(obj interface{}, finalizer interface{}) {
	// ...
	_, base, _ := findObject(e.data)

	if base == nil {
		// 0-length objects are okay.
		if e.data == unsafe.Pointer(&zerobase) {
			return
		}

		// Global initializers might be linker-allocated.
		//	var Foo = &Object{}
		//	func main() {
		//		runtime.SetFinalizer(Foo, nil)
		//	}
		// The segments are, in order: text, rodata, noptrdata, data, bss, noptrbss.
		if uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss)) {
			return
		}
		gothrow("runtime.SetFinalizer: pointer not in allocated block")
	}

	// ...
}
```

*   **`noptrdata` と `enoptrbss`**: これらの変数は、Goのランタイムがリンカによって割り当てられたメモリセグメントの境界を特定するために使用されます。`unsafe.Pointer` を介してこれらの変数のアドレスを取得し、`uintptr` にキャストすることで、メモリ上の数値的な位置を比較できます。
*   **`if base == nil` ブロックの修正**:
    *   `base == nil` は、`e.data` がヒープ上の有効なオブジェクトを指していないことを意味します。
    *   `e.data == unsafe.Pointer(&zerobase)`: これはゼロサイズのオブジェクト（例: `struct{}`）を指している場合のチェックです。ゼロサイズのオブジェクトはGCの対象外であり、ファイナライザを設定しても意味がないため、ここで `return` します。
    *   `uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss))`: この行が今回のコミットの核心です。`e.data` が `noptrdata` セグメントの開始から `enoptrbss` セグメントの終了までの範囲内にあるかどうかをチェックします。この範囲は、リンカによって割り当てられた静的データ領域（ポインタを含まないデータ）に対応します。もし `e.data` がこの範囲内にある場合、それはヒープ割り当てではないため、ファイナライザを設定しても実行されない可能性があり、ここで `return` します。これが、グローバルな割り当てに対するファイナライザの挙動を修正する部分です。
    *   `gothrow("runtime.SetFinalizer: pointer not in allocated block")`: 上記のどの条件にも当てはまらない `base == nil` のケースは、`e.data` がヒープ上の有効なオブジェクトでも、ゼロサイズオブジェクトでも、リンカ割り当てオブジェクトでもない、不正なポインタであることを意味します。この場合、ランタイムパニックを発生させて、プログラマに問題があることを知らせます。

### `src/runtime/mfinal_test.go` の変更点

```go
func TestFinalizerType(t *testing.T) {
	// ...
	for i, tt := range finalizerTests {
		done := make(chan bool, 1)
		go func() {
			// allocate struct with pointer to avoid hitting tinyalloc.
			// Otherwise we can't be sure when the allocation will
			// be freed.
			type T struct {
				v int
				p unsafe.Pointer
			}
			v := &new(T).v
			*v = 97531
			runtime.SetFinalizer(tt.convert(v), tt.finalizer)
			v = nil
			runtime.GC()
			runtime.GC()
		}()
		// ...
	}
}
```

*   **`type T struct { v int; p unsafe.Pointer }` と `v := &new(T).v`**: 以前は `v := new(int)` のように直接 `int` のポインタを割り当てていました。しかし、`int` のような小さなオブジェクトは、Goランタイムの `tinyalloc` という最適化されたアロケータによって割り当てられることがあります。`tinyalloc` は、小さなオブジェクトをまとめて割り当てることで、メモリ割り当てのオーバーヘッドを削減しますが、そのメモリがいつGCによって解放されるか（ひいてはファイナライザがいつ実行されるか）が予測しにくくなる場合があります。
*   新しいコードでは、`int` と `unsafe.Pointer` を含む構造体 `T` を定義し、その `v` フィールドのアドレス `&new(T).v` を取得しています。構造体 `T` は `unsafe.Pointer` フィールドを持つため、`tinyalloc` の対象外となり、通常のヒープ割り当てが行われます。これにより、GCがオブジェクトをより確実に認識し、ファイナライザが期待通りに実行されることを保証し、テストの信頼性を高めています。

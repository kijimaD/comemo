## 変更の背景

このコミットの背景には、GoランタイムのWindows固有のコードの可読性と保守性の向上が挙げられます。以前のコードでは、Windowsのシステムコールを動的にロードするロジックが`osinit()`関数内に直接記述されており、コードが複雑になっていました。特に、一部のシステムコールは全てのWindowsバージョンで利用可能ではないため、実行時にその存在を確認し、動的にロードする必要がありました。

このコミットは、これらの「オプションの」システムコールをロードする処理を専用の関数`loadOptionalSyscalls()`に分離し、`osinit()`関数を簡素化することを目的としています。これにより、コードの役割が明確になり、将来的な変更やデバッグが容易になります。また、コメントを追加することで、各システムコールの利用可能性（常に利用可能か、オプションか）に関する情報が明確に示されています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのコンポーネントです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、コンパイル時にランタイムとリンクされ、ランタイムがOSとの橋渡し役となります。

### システムコール (Syscalls)

システムコールは、ユーザー空間で実行されているプログラムが、オペレーティングシステムカーネルが提供するサービスを要求するためのメカニズムです。ファイルI/O、ネットワーク通信、メモリ管理、プロセス管理など、OSの機能にアクセスするために使用されます。Windowsでは、これらの機能は通常、DLL（Dynamic Link Library）として提供され、API関数として公開されています。

### Windows API

Windows APIは、Microsoft Windowsオペレーティングシステムが提供する一連の関数、データ構造、およびプロトコルです。Goランタイムは、Windows上で動作するために、これらのAPIを直接呼び出す必要があります。

### `LoadLibraryA` と `GetProcAddress`

これらはWindows API関数であり、DLLから関数を動的にロードするために使用されます。
- `LoadLibraryA`: 指定されたDLLをプロセスのアドレス空間にロードし、そのモジュールハンドルを返します。
- `GetProcAddress`: ロードされたDLLから、指定された関数名に対応する関数のアドレスを取得します。これにより、プログラムはコンパイル時には存在しない関数を、実行時にロードして呼び出すことができます。これは、特定のWindowsバージョンでのみ利用可能なAPIや、プラグインのような動的な拡張機能を扱う際に特に有用です。

### ベクタ化例外ハンドラ (Vectored Exception Handler)

Windowsの例外処理メカニズムの一つです。通常の構造化例外処理（SEH）とは異なり、ベクタ化例外ハンドラは、例外が発生する前に登録され、例外が発生した際に最初に呼び出されるハンドラです。`AddVectoredExceptionHandler`は例外発生時に呼び出されるハンドラを登録し、`AddVectoredContinueHandler`は例外処理後に実行を継続するハンドラを登録します。これらは、Goランタイムがクラッシュやその他の予期せぬイベントを捕捉し、適切に処理するために使用されます。

### I/O完了ポート (I/O Completion Port - IOCP)

Windowsにおける高性能な非同期I/Oメカニズムです。複数の非同期I/O操作の結果を効率的に処理するために使用されます。`GetQueuedCompletionStatusEx`は、IOCPから複数の完了したI/O操作の結果を一度に取得するための関数で、特に多数の同時I/O操作を扱うサーバーアプリケーションなどでパフォーマンスを向上させます。

## 技術的詳細

このコミットの主要な変更点は、Windows固有のシステムコールをロードする方法の改善です。

Goランタイムは、Windows上で動作するために、多くのWindows API関数を呼び出す必要があります。これらのAPI関数の中には、全てのWindowsバージョンで利用可能なもの（例: `CreateEventA`, `CloseHandle`など）と、特定のWindowsバージョン（例: Windows Vista以降）で導入されたため、古いシステムでは利用できないもの（例: `AddVectoredContinueHandler`, `GetQueuedCompletionStatusEx`など）があります。

以前のコードでは、`osinit()`関数内で、これらのオプションのシステムコールを動的にロードする処理が直接行われていました。具体的には、`kernel32.dll`を`LoadLibraryA`でロードし、その後`GetProcAddress`を使って各関数のアドレスを取得していました。この際、関数名を表すバイトスライス（例: `addVectoredContinueHandlerName`）が定義され、それらが`unsafe.Pointer`を介して`GetProcAddress`に渡されていました。

このコミットでは、以下の点が変更されました。

1.  **`loadOptionalSyscalls()`関数の導入**: オプションのシステムコールをロードするロジックが、新しく導入された`loadOptionalSyscalls()`関数にカプセル化されました。これにより、`osinit()`関数が簡素化され、その主な役割が明確になりました。
2.  **文字列から`uintptr`への変換の共通化**: `strtoptr`というヘルパー関数が導入され、文字列を`uintptr`（ポインタとして扱われる整数型）に変換する処理が共通化されました。これは、`LoadLibraryA`や`GetProcAddress`に文字列を渡す際に、Goの文字列をCスタイルのヌル終端文字列に変換するために使用されます。
3.  **`stdFunction`型の利用**: `_AddVectoredContinueHandler`と`_GetQueuedCompletionStatusEx`が、`stdFunction`型として宣言され、`loadOptionalSyscalls()`内で初期化されるようになりました。これにより、これらの変数がオプションのシステムコールを表すことがより明確になります。
4.  **コメントの追加**: `var`ブロックにコメントが追加され、どのシステムコールが「全てのWindows PCで利用可能」であり、どのシステムコールが「一部のWindows PCでのみ利用可能」であるかが明示されました。これにより、コードの意図がより明確になりました。
5.  **エラーハンドリングの改善**: `_AddVectoredContinueHandler`が`nil`であるか、または32ビットシステムである場合に、代替の例外ハンドリングメカニズム（`SetUnhandledExceptionFilter`）を使用するロジックが維持されています。これは、`AddVectoredContinueHandler`が利用できない環境でもGoランタイムが適切に動作することを保証するためです。

この変更により、GoランタイムのWindows固有のコードはよりモジュール化され、理解しやすくなりました。

## コアとなるコードの解説

### 変更前

変更前のコードでは、`osinit()`関数内で、`kernel32.dll`をロードし、その中から`AddVectoredContinueHandler`と`GetQueuedCompletionStatusEx`のアドレスを直接取得していました。これらの関数名はバイトスライスとして定義され、`unsafe.Pointer`を介して`GetProcAddress`に渡されていました。このロジックは`osinit()`内に散在しており、特に`AddVectoredContinueHandler`のロードと利用可能性チェックが複雑でした。

### 変更後

1.  **`var`ブロックの整理とコメント追加**:
    -   常に利用可能なシステムコールと、オプションのシステムコールが明確に区別され、それぞれに説明的なコメントが追加されました。
    -   `_AddVectoredContinueHandler`と`_GetQueuedCompletionStatusEx`は、オプションのシステムコールとして、`var`ブロックの新しいセクションに移動されました。

2.  **`loadOptionalSyscalls()`関数の新規追加**:
    -   この関数は、`kernel32.dll`をロードし、その中から`AddVectoredContinueHandler`と`GetQueuedCompletionStatusEx`のアドレスを取得する処理をカプセル化します。
    -   `strtoptr`というローカル関数が定義され、Goの文字列をCスタイルのヌル終端文字列に変換する処理を簡素化しています。これは、`LoadLibraryA`や`GetProcAddress`に文字列を渡す際に必要です。
    -   `findfunc`というローカル関数も定義され、`GetProcAddress`を呼び出して`stdFunction`型を返す処理を共通化しています。
    -   `kernel32.dll`のロードが成功した場合（`l != 0`）、`_AddVectoredContinueHandler`と`_GetQueuedCompletionStatusEx`にそれぞれ対応する関数のアドレスが設定されます。

3.  **`osinit()`関数の簡素化**:
    -   `osinit()`関数から、`kernel32.dll`のロードとオプションのシステムコールの取得に関する冗長なコードが削除されました。
    -   代わりに、新しく作成された`loadOptionalSyscalls()`関数が呼び出されるようになりました。
    -   `AddVectoredContinueHandler`の利用可能性チェックも簡素化され、`_AddVectoredContinueHandler == nil`（関数がロードされなかった場合）または32ビットシステムの場合に、代替の例外ハンドラ（`SetUnhandledExceptionFilter`）を使用するロジックがより明確になりました。
    -   `_AddVectoredContinueHandler`が利用可能な場合は、直接その変数を使用して`stdcall2`が呼び出されるようになりました。

これらの変更により、コードの構造が改善され、各部分の役割がより明確になりました。特に、オプションのシステムコールの動的ロードに関するロジックが`loadOptionalSyscalls()`に集約されたことで、`osinit()`の複雑さが軽減され、全体的な可読性と保守性が向上しています。

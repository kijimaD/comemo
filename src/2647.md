## コミット

このコミットは、Goコンパイラ（`gc`）の型チェックおよびエラー報告メカニズムにおける2つの独立した改善を目的としています。

1.  **`go.y` からの `ANY` 型チェックの削除**: `go.y` ファイル（Go言語の文法定義を扱うYacc/Bisonのソースファイル）から、`ANY` 型に関する冗長なチェックコードが削除されました。これは、`ANY` 型のチェックが既に別の場所で適切に行われているため、重複を避けるための変更です。
2.  **`badtype` 関数における型エラー報告の改善**: `subr.c` ファイル内の `badtype` 関数（型エラーを報告する役割を持つ）から、ポインタ型を「削除」（つまり、ポインタの指す先の型に変換）するロジックが削除されました。この変更は、特に異なる名前を持つが同じ基底型を指す2つのポインタ型が関与するエラーの場合に、元の型情報を保持することでエラーメッセージの明確性を向上させることを目的としています。以前のロジックは、このような状況で混乱を招く可能性がありました。

## 変更の背景

このコミットは、Go言語の初期開発段階におけるコンパイラの洗練の一環として行われました。

1.  **`ANY` 型チェックの冗長性解消**: Go言語の型システムは厳密であり、`ANY`（現在の `interface{}` に相当する概念）のような汎用的な型は特別な扱いを受けます。初期のコンパイラ実装では、`ANY` 型に関するチェックが複数の場所で行われていた可能性があり、このコミットは冗長なチェックを特定し、コードベースを簡素化することを目的としています。これにより、コンパイラの保守性が向上し、将来的な変更が容易になります。
2.  **型エラーメッセージの精度向上**: コンパイラが型エラーを検出した際、開発者にとって最も重要なのは、何が問題で、どの型が関与しているのかを正確に理解することです。`badtype` 関数におけるポインタ型の自動的なデリファレンス（ポインタの指す先の型への変換）は、単純なケースでは問題ないかもしれませんが、`type MyInt *int` と `type YourInt *int` のように、異なる名前を持つが同じ基底型 (`*int`) を指すポインタ型が関与する複雑なシナリオでは、エラーメッセージが混乱を招く可能性がありました。元のポインタ型をそのまま表示することで、開発者はコードの意図とエラーの原因をより正確に把握できるようになります。これは、コンパイラが提供するフィードバックの質を高める上で重要な改善です。

## 前提知識の解説

*   **Goコンパイラ (`gc`)**: Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担います。`src/cmd/gc` ディレクトリにそのソースコードが格納されています。
*   **Yacc/Bison (`.y` ファイル)**: Yacc (Yet Another Compiler Compiler) や Bison は、文法定義からパーサー（構文解析器）を自動生成するためのツールです。`go.y` ファイルは、Go言語の文法規則を定義しており、Goコンパイラの字句解析器と構文解析器の基盤となっています。

*   **ポインタ型**: Goにおけるポインタは、変数のメモリアドレスを保持する型です。`*T` の形式で表され、`T` 型の変数へのポインタであることを示します。ポインタをデリファレンス（間接参照）すると、そのポインタが指すメモリ位置にある値にアクセスできます。
*   **型システム**: プログラミング言語において、値や変数の種類（型）を定義し、それらの型がどのように相互作用するかを規定する規則の集合です。Goの型システムは静的型付けであり、コンパイル時に厳密な型チェックが行われます。
*   **`badtype` 関数**: Goコンパイラの内部関数で、型チェック中に互換性のない型が検出された場合にエラーメッセージを生成し、報告する役割を担います。

## 技術的詳細

### `go.y` における `ANY` 型チェックの削除

Goコンパイラの構文解析フェーズでは、`go.y` に定義された文法規則に基づいてソースコードが解析されます。このコミットで削除されたコードブロックは以下の通りです。

```diff
--- a/src/cmd/gc/go.y
+++ b/src/cmd/gc/go.y
@@ -1104,10 +1104,6 @@ othertype:
 			$$ = T;
 			break;
 		}
-		if($1->op == OTYPE)
-		if($1->type->etype == TANY)
-		if(strcmp(package, "PACKAGE") != 0)
-			yyerror("the any type is restricted");
 		$$ = oldtype($1->sym);
 	}
```

このコードは、`othertype` ルール内で、`$1` が `OTYPE`（型を表すオペレーション）であり、その型が `TANY`（`ANY` 型）であり、かつ現在のパッケージが `"PACKAGE"` ではない場合に、「the any type is restricted」というエラーを発生させていました。

この削除は、`ANY` 型に関する制限（例えば、特定のコンテキストでのみ使用可能である、あるいは特定のパッケージでのみ定義可能であるといった制限）が、コンパイラの別のフェーズや別の場所で既に適切に処理されていることを示唆しています。構文解析器の段階でこのチェックを行うことは冗長であり、コンパイラのロジックを不必要に複雑にしていたため、削除されました。これにより、コンパイラのコードベースがよりクリーンで効率的になります。

### `subr.c` における `badtype` 関数の変更

`subr.c` ファイルは、Goコンパイラの様々なユーティリティ関数やサブルーチンを含んでいます。`badtype` 関数は、型エラーが発生した際に呼び出され、適切なエラーメッセージを生成します。このコミットで削除された `badtype` 関数内のコードブロックは以下の通りです。

```diff
--- a/src/cmd/gc/subr.c
+++ b/src/cmd/gc/subr.c
@@ -2120,21 +2120,6 @@ void
 badtype(int o, Type *tl, Type *tr)
 {
 
-loop:
-	switch(o) {
-	case OCALL:
-		if(tl == T || tr == T)
-			break;
-		if(isptr[tl->etype] && isptr[tr->etype]) {
-			tl = tl->type;
-			tr = tr->type;
-			goto loop;
-		}
-		if(tl->etype != TFUNC || tr->etype != TFUNC)
-			break;
-//		if(eqtype(t1, t2))\n
-	}
-
 	yyerror("illegal types for operand: %O", o);
 	if(tl != T)
 		print("\t%T\n", tl);
```

削除された `loop` ブロックは、`OCALL`（関数呼び出し）オペレーションに関連する型エラーを処理する際に、`tl` と `tr` の両方がポインタ型である場合に、それらをデリファレンスして（`tl = tl->type; tr = tr->type;`）再度 `loop` の先頭に戻る（`goto loop;`）というロジックを含んでいました。これは、ポインタの指す先の型に基づいてエラーを報告しようとする試みでした。

しかし、コミットメッセージにあるように、この挙動は「異なる名前を持つが同じ基底型を指す2つの名前付きポインタ型が関与する」場合に混乱を招く可能性がありました。例えば、`type P1 *int` と `type P2 *int` という2つの型があり、これらが型エラーに関与する場合、以前のロジックでは両方とも `*int` をデリファレンスして `int` として扱ってしまうため、`P1` と `P2` という元の型情報が失われ、エラーメッセージが不明瞭になる可能性がありました。

この変更により、`badtype` 関数はポインタ型を自動的にデリファレンスすることなく、エラーが発生した時点での元の型 (`tl` と `tr`) をそのまま `yyerror` や `print` 関数に渡すようになります。これにより、エラーメッセージにはより正確で、開発者にとって理解しやすい型情報が含まれるようになります。これは、コンパイラの診断能力を向上させる重要な改善です。

## コアとなるコードの解説

### `src/cmd/gc/go.y` の変更

`go.y` から削除されたコードは、`othertype` という文法規則の一部でした。この規則は、Go言語の型定義を解析する際に使用されます。削除された `if` 文の連鎖は、以下の条件がすべて真である場合にエラーを発生させていました。

1.  `$1->op == OTYPE`: 構文解析中の要素が型を表すオペレーションである。
2.  `$1->type->etype == TANY`: その型が `ANY` 型である。
3.  `strcmp(package, "PACKAGE") != 0`: 現在のパッケージ名が `"PACKAGE"` ではない。

このチェックは、`ANY` 型の使用に特定のパッケージ制限を課すためのものでしたが、このコミットの時点で、この制限がコンパイラの他の部分でより適切に、あるいはより広範に処理されるようになったため、構文解析器レベルでのこの特定のチェックは冗長と判断され削除されました。これにより、パーサーのロジックが簡素化され、コンパイラの全体的な効率が向上します。

### `src/cmd/gc/subr.c` の変更

`subr.c` の `badtype` 関数から削除された `loop` ブロックは、型エラー報告のロジックを複雑にしていました。特に `OCALL`（関数呼び出し）の場合に、`tl`（左側の型）と `tr`（右側の型）が両方ともポインタ型であると判断されると、`tl = tl->type; tr = tr->type;` によってポインタをデリファレンスし、`goto loop;` で処理を繰り返していました。

この再帰的なデリファレンスは、ポインタの連鎖を辿って最終的な基底型に到達し、その基底型に基づいてエラーを報告しようとする意図があったと考えられます。しかし、Go言語では `type MyPointer *int` のように、基底型が同じでも異なる名前を持つポインタ型を定義できます。このような場合、デリファレンスによって元の名前付きポインタ型 (`MyPointer`) の情報が失われ、エラーメッセージが「`int` と `int` は互換性がありません」のような、あまり役に立たないものになってしまう可能性がありました。

このコミットにより、`badtype` 関数はポインタのデリファレンスを行わなくなり、エラーが発生した時点での `tl` と `tr` の元の型情報をそのまま使用してエラーメッセージを生成します。これにより、例えば「`MyPointer` と `YourPointer` は互換性がありません」といった、より具体的で診断に役立つエラーメッセージが提供されるようになります。これは、コンパイラのユーザーエクスペリエンスを向上させる重要な変更です。

削除された `loop` ブロックは、`OCALL`（関数呼び出し）オペレーションに関連する型エラーを処理する際に、`tl`（左側の型）と `tr`（右側の型）が両方ともポインタ型であると判断されると、`tl = tl->type; tr = tr->type;` によってポインタをデリファレンスし、`goto loop;` で処理を繰り返していました。

この再帰的なデリファレンスは、ポインタの連鎖を辿って最終的な基底型に到達し、その基底型に基づいてエラーを報告しようとする意図があったと考えられます。しかし、Go言語では `type MyPointer *int` のように、基底型が同じでも異なる名前を持つポインタ型を定義できます。このような場合、デリファレンスによって元の名前付きポインタ型 (`MyPointer`) の情報が失われ、エラーメッセージが「`int` と `int` は互換性がありません」のような、あまり役に立たないものになってしまう可能性がありました。

このコミットにより、`badtype` 関数はポインタのデリファレンスを行わなくなり、エラーが発生した時点での `tl` と `tr` の元の型情報をそのまま使用してエラーメッセージを生成します。これにより、例えば「`MyPointer` と `YourPointer` は互換性がありません」といった、より具体的で診断に役立つエラーメッセージが提供されるようになります。これは、コンパイラのユーザーエクスペリエンスを向上させる重要な変更です。

## コアとなるコードの解説

### `src/cmd/gc/go.y` の変更

`go.y` から削除されたコードは、`othertype` という文法規則の一部でした。この規則は、Go言語の型定義を解析する際に使用されます。削除された `if` 文の連鎖は、以下の条件がすべて真である場合にエラーを発生させていました。

1.  `$1->op == OTYPE`: 構文解析中の要素が型を表すオペレーションである。
2.  `$1->type->etype == TANY`: その型が `ANY` 型である。
3.  `strcmp(package, "PACKAGE") != 0`: 現在のパッケージ名が `"PACKAGE"` ではない。

このチェックは、`ANY` 型の使用に特定のパッケージ制限を課すためのものでしたが、このコミットの時点で、この制限がコンパイラの他の部分でより適切に、あるいはより広範に処理されるようになったため、構文解析器レベルでのこの特定のチェックは冗長と判断され削除されました。これにより、パーサーのロジックが簡素化され、コンパイラの全体的な効率が向上します。

# [インデックス 25564] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージ内の `prf.go` ファイルにおける、TLS (Transport Layer Security) の鍵導出プロセスに関するバグ修正です。具体的には、マスターシークレットおよびキーマテリアルの生成に使用される擬似乱数関数 (PRF) のシード構築において、`clientRandom` と `serverRandom` の結合方法に誤りがあった点を修正しています。

## コミット

`crypto/tls`: `len(clientRandom)` が `serverRandom` のソースとして使用されていた問題の修正。

`keysFromMasterSecret()` 関数内で、`serverRandom` を `seed[:len(clientRandom)]` にコピーしないように変更。また、`keysFromMasterSecret()` および `masterFromPreMasterSecret()` 関数において、配列ではなくスライスを使用するように変更し、長さの指定が不要になるようにした。これはファイル内の他の箇所での実装方法に合わせるものである。

Fixes #13181

## 変更の背景

この変更は、Go言語の `crypto/tls` パッケージにおけるTLSハンドシェイクの鍵導出プロセスに存在する潜在的なバグを修正するために行われました。具体的には、`keysFromMasterSecret` 関数内で、`serverRandom` の一部が誤った長さでコピーされる可能性がありました。これは、`seed` バッファの初期化とデータのコピー方法に起因します。

TLSプロトコルでは、セッションごとに一意の暗号鍵を導出するために、クライアントとサーバーがそれぞれ生成するランダムな値（`clientRandom` と `serverRandom`）が重要な役割を果たします。これらのランダム値は、プリマスターシークレットと共に擬似乱数関数（PRF）の入力として使用され、マスターシークレットや最終的な暗号鍵（キーマテリアル）が生成されます。

元のコードでは、`seed` バッファを固定長配列として宣言し、その後に `clientRandom` と `serverRandom` を `copy` 関数で書き込んでいました。この際、`keysFromMasterSecret` 関数において、`serverRandom` をコピーする際に `len(clientRandom)` をオフセットとして使用していたため、`serverRandom` の長さが `clientRandom` の長さと異なる場合に、`serverRandom` の一部が切り捨てられたり、意図しないデータが残ったりする可能性がありました。この問題は、鍵導出のセキュリティに影響を与える可能性があり、TLSセッションの安全性を損なう恐れがありました。

このバグは Issue #13181 として報告され、その修正としてこのコミットが作成されました。修正の目的は、`seed` の構築をより堅牢にし、`clientRandom` と `serverRandom` の実際の長さに依存しない、安全な方法で結合することです。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を提供するための暗号プロトコルです。ウェブブラウザとサーバー間のHTTPS通信などで広く利用されています。TLSハンドシェイクは、クライアントとサーバーが互いに認証し、セッション鍵を確立するプロセスです。

### TLSハンドシェイクにおけるランダム値 (`clientRandom`, `serverRandom`)

TLSハンドシェイクの初期段階で、クライアントとサーバーはそれぞれ32バイトのランダムなバイト列を生成し、交換します。これらが `clientRandom` と `serverRandom` です。これらのランダム値は、リプレイ攻撃を防ぎ、セッションごとに一意の鍵を生成するために不可欠です。これらは、プリマスターシークレットと共に、マスターシークレットおよび最終的な暗号鍵を導出するための入力として使用されます。

### プリマスターシークレット (Pre-Master Secret)

クライアントとサーバー間で共有される秘密情報です。通常、Diffie-Hellman鍵交換やRSA暗号化などの鍵交換アルゴリズムによって生成されます。このプリマスターシークレットは、直接暗号鍵として使用されるのではなく、マスターシークレットを導出するための基盤となります。

### マスターシークレット (Master Secret)

プリマスターシークレット、`clientRandom`、`serverRandom` を入力として、擬似乱数関数 (PRF) を用いて生成される48バイトの秘密情報です。このマスターシークレットが、最終的な暗号鍵（キーマテリアル）を導出するための主要な秘密情報となります。

### キーマテリアル (Key Material)

マスターシークレット、`clientRandom`、`serverRandom` を入力として、再度PRFを用いて生成されるバイト列です。このキーマテリアルから、以下の鍵が導出されます。

*   **クライアントMAC秘密鍵 (client_write_MAC_secret)**: クライアントからサーバーへのメッセージ認証コード (MAC) の生成に使用。
*   **サーバーMAC秘密鍵 (server_write_MAC_secret)**: サーバーからクライアントへのメッセージ認証コード (MAC) の生成に使用。
*   **クライアント暗号鍵 (client_write_key)**: クライアントからサーバーへのデータ暗号化に使用。
*   **サーバー暗号鍵 (server_write_key)**: サーバーからクライアントへのデータ暗号化に使用。
*   **クライアントIV (client_write_IV)**: クライアントからサーバーへの初期化ベクトル (IV) として使用。
*   **サーバーIV (server_write_IV)**: サーバーからクライアントへの初期化ベクトル (IV) として使用。

これらの鍵は、TLSレコードプロトコルにおけるデータの暗号化と認証に使用され、通信の機密性、完全性、および真正性を保証します。

### 擬似乱数関数 (PRF: Pseudo-Random Function)

TLSプロトコルにおいて、より長いランダムなバイト列を生成するために使用される関数です。RFC 5246 (TLS 1.2) では、PRFはHMAC-SHA256をベースとして定義されています。PRFは、秘密鍵、ラベル（文字列）、およびシード（ランダム値の結合）を入力として受け取り、指定された長さの擬似乱数バイト列を出力します。

### Go言語における配列とスライス

*   **配列 (Array)**: 固定長で、宣言時にサイズが決定されます。サイズは型の一部です。例: `var a [32]byte`
*   **スライス (Slice)**: 可変長で、配列のセグメントを指し示します。スライスは、基になる配列へのポインタ、長さ、容量の3つの要素で構成されます。動的なデータ構造を扱う際に非常に便利です。`append` 関数を使って要素を追加できます。例: `s := make([]byte, 0, capacity)`

## 技術的詳細

このコミットの技術的詳細な問題点は、`src/crypto/tls/prf.go` 内の `masterFromPreMasterSecret` 関数と `keysFromMasterSecret` 関数における `seed` の構築方法にありました。

### 変更前の問題点

1.  **固定長配列の使用**:
    ```go
    // masterFromPreMasterSecret 関数内
    var seed [tlsRandomLength * 2]byte // tlsRandomLength は 32 バイトなので、64 バイトの配列
    copy(seed[0:len(clientRandom)], clientRandom)
    copy(seed[len(clientRandom):], serverRandom)

    // keysFromMasterSecret 関数内
    var seed [tlsRandomLength * 2]byte // 同様に 64 バイトの配列
    copy(seed[0:len(clientRandom)], serverRandom) // ここが問題
    copy(seed[len(serverRandom):], clientRandom)
    ```
    `tlsRandomLength` は `clientRandom` と `serverRandom` の標準的な長さである32バイトを指します。したがって、`seed` は64バイトの固定長配列として宣言されていました。

2.  **`keysFromMasterSecret` における `serverRandom` のコピーの誤り**:
    `keysFromMasterSecret` 関数では、`seed` の前半に `serverRandom` を、後半に `clientRandom` を配置します。
    ```go
    copy(seed[0:len(clientRandom)], serverRandom) // 問題の箇所
    ```
    ここで、`serverRandom` を `seed` の `0` から `len(clientRandom)` までの範囲にコピーしています。もし `len(serverRandom)` が `len(clientRandom)` よりも長い場合、`serverRandom` の一部が切り捨てられてしまいます。逆に `len(serverRandom)` が `len(clientRandom)` よりも短い場合、`seed` の `len(serverRandom)` から `len(clientRandom)` までの範囲には、以前の `seed` の初期値（ゼロバイト）が残ってしまい、意図しないデータがPRFの入力として使用されることになります。
    TLSプロトコルでは `clientRandom` と `serverRandom` は通常32バイトですが、プロトコル拡張や実装によっては異なる長さになる可能性も考慮する必要があります。この固定長配列と `len(clientRandom)` をオフセットとして使用するアプローチは、柔軟性に欠け、潜在的なバグの原因となっていました。

3.  **`seed[0:]` の使用**:
    `prfForVersion` 関数に `seed` を渡す際に `seed[0:]` と記述されていましたが、これは配列全体をスライスとして渡すことを意味します。しかし、上記の問題により、`seed` の内容自体が正しく構築されていない可能性がありました。

### 変更後の修正点

1.  **スライスの動的な生成**:
    ```go
    // masterFromPreMasterSecret 関数内
    seed := make([]byte, 0, len(clientRandom)+len(serverRandom))
    seed = append(seed, clientRandom...)
    seed = append(seed, serverRandom...)

    // keysFromMasterSecret 関数内
    seed := make([]byte, 0, len(serverRandom)+len(clientRandom))
    seed = append(seed, serverRandom...)
    seed = append(seed, clientRandom...)
    ```
    `seed` を固定長配列ではなく、`make` 関数で容量を事前に確保したスライスとして動的に生成するように変更しました。容量は `clientRandom` と `serverRandom` の合計長に設定されます。

2.  **`append` 関数による安全な結合**:
    `copy` 関数を `append` 関数に置き換えました。`append` はスライスの長さを動的に調整し、要素を安全に追加します。これにより、`clientRandom` と `serverRandom` の実際の長さに応じて `seed` が正確に構築されることが保証されます。`len(clientRandom)` や `len(serverRandom)` の値に依存したオフセット計算の誤りの可能性がなくなります。

3.  **`seed` の直接渡し**:
    `prfForVersion` 関数に `seed` を渡す際に `seed[0:]` ではなく `seed` を直接渡すように変更しました。これは、`seed` が既にスライスであるため、冗長なスライス操作が不要になったためです。

この修正により、TLSの鍵導出プロセスにおける `seed` の構築がより堅牢になり、`clientRandom` と `serverRandom` の長さの変動に対して安全になりました。これは、TLSセッションのセキュリティを確保する上で非常に重要な改善です。

## コアとなるコードの解説

### `masterFromPreMasterSecret` 関数

この関数は、プリマスターシークレット、`clientRandom`、`serverRandom` を使用してマスターシークレットを生成します。

**変更前**:
1.  `var seed [tlsRandomLength * 2]byte` で64バイトの固定長配列 `seed` を宣言。
2.  `copy(seed[0:len(clientRandom)], clientRandom)` で `clientRandom` を `seed` の先頭にコピー。
3.  `copy(seed[len(clientRandom):], serverRandom)` で `serverRandom` を `clientRandom` の直後にコピー。
    *   ここで `len(clientRandom)` をオフセットとして使用しているため、`clientRandom` と `serverRandom` の長さが異なる場合に問題が生じる可能性がありました。

**変更後**:
1.  `seed := make([]byte, 0, len(clientRandom)+len(serverRandom))` で、`clientRandom` と `serverRandom` の合計長を容量とする動的なスライス `seed` を作成。初期の長さは0。
2.  `seed = append(seed, clientRandom...)` で `clientRandom` の全バイトを `seed` に追加。
3.  `seed = append(seed, serverRandom...)` で `serverRandom` の全バイトを `seed` に追加。
    *   `append` を使用することで、`clientRandom` と `serverRandom` の実際の長さに応じて `seed` が正確に構築され、切り捨てや余分なデータが混入するリスクがなくなりました。
4.  `prfForVersion(... seed)`: PRF関数に、正しく結合された `seed` スライスを直接渡します。

### `keysFromMasterSecret` 関数

この関数は、マスターシークレット、`clientRandom`、`serverRandom` を使用してキーマテリアル（MAC鍵、暗号鍵、IV）を生成します。

**変更前**:
1.  `var seed [tlsRandomLength * 2]byte` で64バイトの固定長配列 `seed` を宣言。
2.  `copy(seed[0:len(clientRandom)], serverRandom)` で `serverRandom` を `seed` の先頭にコピー。
    *   **この行が特に問題でした。`serverRandom` をコピーする際に `len(clientRandom)` をコピー先の長さとして指定しているため、`serverRandom` の長さが `clientRandom` の長さと異なる場合に、`serverRandom` のデータが不完全になるか、バッファオーバーフロー/アンダーフローのような状況を引き起こす可能性がありました。**
3.  `copy(seed[len(serverRandom):], clientRandom)` で `clientRandom` を `serverRandom` の直後にコピー。
    *   ここでも `len(serverRandom)` をオフセットとして使用しており、上記と同様の問題を抱えていました。

**変更後**:
1.  `seed := make([]byte, 0, len(serverRandom)+len(clientRandom))` で、`serverRandom` と `clientRandom` の合計長を容量とする動的なスライス `seed` を作成。
2.  `seed = append(seed, serverRandom...)` で `serverRandom` の全バイトを `seed` に追加。
3.  `seed = append(seed, clientRandom...)` で `clientRandom` の全バイトを `seed` に追加。
    *   `masterFromPreMasterSecret` と同様に `append` を使用することで、`serverRandom` と `clientRandom` の実際の長さに応じて `seed` が正確に構築されることが保証されます。
4.  `prfForVersion(... seed)`: PRF関数に、正しく結合された `seed` スライスを直接渡します。

この修正により、TLSの鍵導出におけるランダム値の結合がプロトコル仕様に厳密に準拠し、セキュリティ上の潜在的な脆弱性が解消されました。

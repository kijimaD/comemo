# [インデックス 21510] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）における無限再帰のバグを修正するものです。具体的には、再帰的な型が複数回自身を参照している場合に、型の幅（`width`）を計算する`dowidth`関数が無限ループに陥る問題を解決します。これにより、不正な再帰型定義がコンパイラによって正しく検出され、無限再帰が回避されるようになります。

## 変更の背景

このコミットは、Goコンパイラ（`cmd/gc`）が特定の不正な再帰型定義を処理する際に発生する無限再帰の問題を修正するために導入されました。具体的には、構造体などの複合型が自身を複数回参照するような再帰的な定義を持つ場合、コンパイラが型のメモリ上のサイズ（幅）を計算する`dowidth`関数が無限ループに陥り、コンパイルが完了しないというバグが存在しました。

この問題は、Go言語の型システムが再帰型をサポートしている一方で、その処理ロジックに不備があったために発生しました。コンパイラは型の幅を決定するために、その型が参照するすべてのフィールドの幅を再帰的に計算する必要があります。しかし、不正な再帰型の場合、この再帰的な計算が終了条件を満たさずに無限に繰り返されてしまうことがありました。

このバグは、GoのIssue #9432として報告されており、このコミットはその問題を解決することを目的としています。

## 前提知識の解説

### Goコンパイラ (`cmd/gc`)

`cmd/gc`は、Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担っています。コンパイラは、字句解析、構文解析、型チェック、最適化、コード生成など、複数のフェーズを経て処理を行います。このコミットが関連するのは、主に型チェックと型のメモリレイアウト決定のフェーズです。

### 再帰型 (Recursive Types)

再帰型とは、型定義の中に自身と同じ型、または自身を参照する別の型が含まれる型のことです。Go言語では、ポインタ型や構造体を通じて再帰型を定義することが可能です。例えば、リンクリストのノードやツリー構造のノードなどが典型的な再帰型の例です。

```go
type Node struct {
    Value int
    Next  *Node // Node型が自身へのポインタを含む
}
```

### 型の幅 (Type Width)

Goコンパイラは、各型がメモリ上で占めるバイト数を計算します。これを「型の幅」と呼びます。型の幅は、構造体のフィールドのオフセット計算や、アライメントの決定、メモリ割り当てなど、コンパイル時の様々な最適化やコード生成において非常に重要な情報です。複合型（構造体など）の幅は、そのフィールドの幅とアライメント要件に基づいて計算されます。

### `dowidth`関数

`src/cmd/gc/align.c`ファイルに存在する`dowidth`関数は、Goコンパイラのバックエンドの一部であり、与えられた型のメモリ上の幅を計算する役割を担っています。この関数は、型の構造を再帰的に辿り、その構成要素の幅を合計することで全体の幅を決定します。再帰型の場合、この関数は再帰的に自身を呼び出すことになります。

### 無限再帰 (Infinite Recursion)

プログラミングにおいて、関数が自身を呼び出し続けるが、終了条件が満たされないために呼び出しが永遠に続く状態を指します。これにより、スタックオーバーフローやプログラムのハングが発生します。コンパイラのような複雑なシステムでは、型定義の解析など、再帰的な処理が多用されるため、無限再帰のバグが発生する可能性があります。

## 技術的詳細

このコミットが修正する問題は、`dowidth`関数が再帰型を処理する際のロジックの欠陥に起因します。通常、`dowidth`は型の幅を計算する際に、既に計算中の型や、既に計算が完了した型については再計算を避けるためのメカニズムを持っています。しかし、不正な再帰型、特に自身を複数回参照するようなケースでは、このメカニズムが適切に機能せず、`dowidth`が同じ「壊れた（`broke`）再帰型」に対して繰り返し呼び出され、無限ループに陥っていました。

無限ループが発生するシナリオは以下の通りです。

1.  `dowidth`関数が、不正な再帰型（例: `type foo struct { bar foo; blah foo }`）の幅を計算しようとします。
2.  この型は不正であるため、コンパイラは最終的にエラーを報告しますが、その前に型の幅を決定しようとします。
3.  `dowidth`は、この型が「壊れている」（`t->broke`が真）とマークされているにもかかわらず、まだ幅が決定されていない（`t->width == 0`）場合に、再度その型の幅を計算しようとします。
4.  この再計算の試みが、再び同じ無限ループのパスに入り込み、結果としてコンパイラがハングアップします。

このコミットの修正は、`dowidth`関数の冒頭にガード条件を追加することで、この無限再帰を回避します。追加された条件は、型が既に「壊れている」とマークされており（`t->broke`が真）、かつその幅がまだ0である（`t->width == 0`）場合に、即座に`dowidth`関数からリターンするというものです。

これにより、不正な再帰型が複数回参照されたとしても、`dowidth`が無限に再帰することなく、適切なエラー処理パスに進むことができるようになります。この修正は、コンパイラの堅牢性を高め、特定の不正なコードパターンに対する耐性を向上させます。

## コアとなるコードの変更箇所

`src/cmd/gc/align.c` の `dowidth` 関数に以下の変更が加えられました。

```diff

+++ b/src/cmd/gc/align.c
@@ -137,6 +137,11 @@ dowidth(Type *t)\n 	\treturn;\n 	}\n \n+\t// break infinite recursion if the broken recursive type\n+\t// is referenced again\n+\tif(t->broke && t->width == 0)\n+\t\treturn;\n+\n \t// defer checkwidth calls until after we're done\n \tdefercalc++;
```

## コアとなるコードの解説

### `src/cmd/gc/align.c` の変更

追加されたコードは以下の通りです。

```c
	// break infinite recursion if the broken recursive type
	// is referenced again
	if(t->broke && t->width == 0)
		return;
```

*   `t->broke`: これは、現在処理している型 `t` が、何らかの理由で「壊れている」または「不正である」とコンパイラによってマークされていることを示します。再帰型の場合、循環参照が検出された際にこのフラグが設定されることがあります。
*   `t->width == 0`: これは、型の幅がまだ計算されていないことを示します。`dowidth`関数が正常に完了すれば、`t->width`には非ゼロの値が設定されます。

この条件 `t->broke && t->width == 0` が真である場合、つまり、型が不正であるとマークされており、かつその幅がまだ決定されていない（そしておそらく決定できない）状況で、`dowidth`関数は即座にリターンします。これにより、既に不正と判断された型に対して、`dowidth`が再度無限に再帰的に呼び出されることを防ぎます。これは、無限ループの脱出条件として機能し、コンパイラがハングアップするのを防ぎます。

### `test/fixedbugs/issue9432.go` の追加

このテストファイルは、修正が正しく機能することを確認するために作成されました。

```go
type foo struct { // GCCGO_ERROR "invalid recursive type"
	bar  foo
	blah foo
} // ERROR "invalid recursive type foo"
```

このGoコードは、`foo`という構造体が自身を`bar`と`blah`という2つのフィールドで参照する、不正な再帰型を定義しています。このような定義はGo言語の型システムでは許可されず、コンパイル時にエラーとなるべきです。

*   `// errorcheck`: このコメントは、Goのテストフレームワークに対して、このファイルがコンパイルエラーを期待するテストであることを示します。
*   `// GCCGO_ERROR "invalid recursive type"` と `// ERROR "invalid recursive type foo"`: これらのコメントは、コンパイラが期待するエラーメッセージのパターンを示しています。`GCCGO_ERROR`はGCCベースのGoコンパイラ（`gccgo`）向け、`ERROR`は標準のGoコンパイラ（`gc`）向けです。

このテストケースは、修正前のコンパイラでは無限ループに陥っていましたが、このコミットの修正が適用されたコンパイラでは、無限ループに陥ることなく、期待される「invalid recursive type」エラーを正しく出力して終了するようになります。

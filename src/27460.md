## 元コミット内容

`cmd/compile: optimize remaining convT2I calls`

このコミットは、Goコンパイラが`convT2I`（型からインターフェースへの変換）呼び出しを最適化するものです。特に、ポインタ型ではない値の`convT2I`において、`itab`シンボルがコンパイラによって直接生成されるようになったため、インターフェースの型とキャッシュポインタを渡す代わりに、`itab`のアドレスを直接`convT2I`関数に渡すように変更されています。これにより、ランタイムでの`itab`ルックアップのオーバーヘッドが削減され、パフォーマンスが向上します。

関連するIssueとして、`#14874`と`#6853`が挙げられています。

ベンチマーク結果では、`Compiler`の実行時間が約6.64%短縮されるなど、全体的なパフォーマンス改善が見られます。一方で、`CmdGoSize`の`data-bytes`が約20.76%増加している点も示されています。

## 変更の背景

Go言語のインターフェースは、その柔軟性から非常に強力な機能ですが、その実装にはランタイムのオーバーヘッドが伴います。特に、具体的な型（concrete type）からインターフェース型への変換（`convT2I`）は、ランタイムが`itab`（インターフェーステーブル）を検索または構築する必要があるため、コストがかかる処理の一つです。

以前のGoのバージョンでは、`itab`はランタイムで動的に構築されることが多く、そのために型情報とキャッシュポインタを`convT2I`に渡していました。しかし、コンパイラが`itab`シンボルを直接生成できるようになると、この動的なルックアップの一部をコンパイル時に解決できる可能性が生まれます。

このコミットの背景には、Goのコンパイラとランタイムの連携を強化し、インターフェース変換の効率をさらに高めるという目的があります。特に、ポインタ型ではない値のインターフェース変換は、値のコピーが発生する可能性があり、その`itab`ルックアップの最適化は全体的なパフォーマンス改善に寄与します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部実装に関する知識が必要です。

1.  **Goのインターフェースの内部表現 (`iface`と`eface`)**:
    *   Goのインターフェースは、内部的には2つのポインタで構成されます。
    *   **`eface` (empty interface)**: `interface{}`型。`_type`ポインタと`data`ポインタの2つで構成されます。`_type`は格納されている具体的な値の型情報へのポインタ、`data`は具体的な値へのポインタです。
    *   **`iface` (non-empty interface)**: `io.Reader`のようなメソッドを持つインターフェース型。`itab`ポインタと`data`ポインタの2つで構成されます。`itab`はインターフェーステーブルへのポインタ、`data`は具体的な値へのポインタです。
2.  **`itab` (Interface Table)**:
    *   `itab`は、特定の具体的な型が特定のインターフェース型を実装していることを記述するランタイムデータ構造です。
    *   `itab`には、具体的な型情報、インターフェース型情報、そしてその具体的な型がインターフェースのメソッドを実装する際のメソッドポインタの配列が含まれます。
    *   インターフェースメソッドが呼び出される際、ランタイムは`itab`から適切なメソッドポインタを見つけて呼び出します。
    *   `itab`は一度構築されるとキャッシュされ、同じ型とインターフェースの組み合わせに対して再利用されます。
3.  **`convT2I` (Type-to-Interface Conversion)**:
    *   具体的な型`T`の値をインターフェース型`I`に変換する際にGoランタイムが呼び出す内部関数です。
    *   この関数は、`T`が`I`を実装しているかを確認し、`itab`を検索または構築し、最終的に`iface`構造体を構築します。
4.  **Goコンパイラの`gc`パッケージ**:
    *   Goの標準コンパイラ（`gc`）のバックエンド部分。型チェック、AST変換、コード生成などを行います。
    *   `walk.go`は、AST（抽象構文木）を走査し、高レベルなGoの構文を低レベルな中間表現に変換する処理（"walking"）を行うファイルです。この過程で、インターフェース変換のような特定の操作がランタイム関数呼び出しに置き換えられます。
5.  **`Pkglookup`**: コンパイラ内部でシンボルを検索または作成するための関数。
6.  **`typename`**: 型の名前を取得するコンパイラ内部関数。
7.  **`Nod`**: ASTノードを作成するコンパイラ内部関数。
8.  **`typecheck`**: ASTノードの型チェックを行うコンパイラ内部関数。
9.  **`walkexpr`**: 式のASTを走査し、変換するコンパイラ内部関数。
10. **`atomicloadtype`, `atomicstorep`**: Goランタイムが提供するアトミック操作。並行処理環境でデータの一貫性を保つために使用されます。特に`itab`キャッシュのような共有リソースへのアクセスで重要です。

## 技術的詳細

このコミットの核心は、`convT2I`関数のシグネチャ変更と、それに伴うコンパイラ（`src/cmd/compile/internal/gc/walk.go`）およびランタイム（`src/runtime/iface.go`）の挙動の変更にあります。

**変更前**:
`convT2I`は、具体的な型`t`、インターフェース型`inter`、そして`itab`をキャッシュするためのポインタ`cache`を受け取っていました。ランタイムの`convT2I`関数内で、`cache`ポインタを使って`itab`をアトミックにロードし、もし`itab`が`nil`であれば`getitab`を呼び出して`itab`を検索・構築し、その結果を`cache`にアトミックにストアしていました。

```go
// 変更前のconvT2Iシグネチャ (runtime/iface.go)
func convT2I(t *_type, inter *interfacetype, cache **itab, elem unsafe.Pointer, x unsafe.Pointer) (i iface) {
    // ...
    tab := (*itab)(atomic.Loadp(unsafe.Pointer(cache)))
    if tab == nil {
        tab = getitab(inter, t, false)
        atomicstorep(unsafe.Pointer(cache), unsafe.Pointer(tab))
    }
    // ...
}
```

コンパイラ側（`walk.go`）では、`convT2I`を呼び出す際に、`itab`キャッシュのためのシンボルを生成し、そのアドレスを`cache`引数として渡していました。

**変更後**:
このコミットでは、コンパイラが`itab`シンボルを直接生成し、そのアドレスを`convT2I`に直接渡せるようになりました。これにより、ランタイムの`convT2I`関数内で`itab`キャッシュのロード/ストアロジックが不要になります。

1.  **`convT2I`シグネチャの変更**:
    `src/cmd/compile/internal/gc/builtin/runtime.go`と`src/cmd/compile/internal/gc/builtin.go`で、`convT2I`のシグネチャが変更されました。
    変更前: `func convT2I(typ *byte, typ2 *byte, cache **byte, elem *any, buf *any) (ret any)`
    変更後: `func convT2I(tab *byte, elem *any, buf *any) (ret any)`
    `typ`（具体的な型）、`typ2`（インターフェース型）、`cache`（キャッシュポインタ）の3つの引数がなくなり、代わりに`tab`（`itab`のアドレス）が直接渡されるようになりました。

2.  **ランタイムの`convT2I`の実装変更**:
    `src/runtime/iface.go`の`convT2I`関数から、`atomic.Loadp`と`atomicstorep`を使った`itab`キャッシュのロジックが削除されました。代わりに、`itab`のアドレスが直接引数`tab`として渡されるため、関数内で`t := tab._type`として具体的な型情報を取得するだけになりました。

3.  **コンパイラ（`walk.go`）の変更**:
    `src/cmd/compile/internal/gc/walk.go`では、`OCONVIFACE`（型からインターフェースへの変換）ノードを処理するロジックが大幅に簡素化されました。
    *   以前は、`itab`キャッシュのためのシンボル（`sym`）を`itabpkg`からルックアップし、そのアドレスを`typ2Itab`関数に渡して`itab`を取得する複雑なロジックがありました。
    *   変更後は、`isnilinter(n.Type)`（空インターフェースへの変換）でない場合、`itabname(n.Left.Type, n.Type)`を呼び出して、コンパイル時に`itab`のアドレスを直接取得し、それを`convT2I`に渡すようになりました。`itabname`関数は、具体的な型とインターフェース型に基づいて`itab`シンボルを生成またはルックアップします。

4.  **`typ2Itab`関数の削除**:
    `src/runtime/iface.go`から`typ2Itab`関数が削除されました。この関数は、ランタイムで`itab`を検索・構築し、キャッシュにストアする役割を担っていましたが、コンパイラが`itab`アドレスを直接渡すようになったため不要になりました。

5.  **`itab2pkg`の削除**:
    `src/cmd/compile/internal/gc/go.go`と`src/cmd/compile/internal/gc/main.go`で、`itab2pkg`という擬似パッケージが削除されました。これは、以前の`itab`キャッシュメカニズムに関連していたと考えられます。`itabpkg`が`itab`エントリの擬似パッケージとして残されています。

この最適化により、`convT2I`の呼び出しがより直接的になり、ランタイムでの条件分岐やアトミック操作のオーバーヘッドが削減されます。特に、コンパイル時に`itab`が確定できるケースにおいて、より効率的なコードが生成されるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、Goコンパイラが`convT2I`（型からインターフェースへの変換）を処理する方法を根本的に簡素化し、効率化することです。

1.  **`convT2I`関数の役割の変化**:
    以前の`convT2I`は、具体的な型、インターフェース型、そして`itab`をキャッシュするためのポインタを受け取り、ランタイム内で`itab`の検索とキャッシュの更新を行っていました。これは、`itab`がまだ存在しない場合に動的に生成する必要があるためです。
    変更後は、`convT2I`は既に解決された`itab`のアドレスを直接受け取るようになりました。これにより、ランタイム関数内で`itab`の検索やアトミックなキャッシュ更新ロジックが不要になり、関数呼び出しのオーバーヘッドが削減されます。

2.  **コンパイラの役割の強化**:
    この変更は、コンパイラが`itab`の解決においてより大きな役割を担うようになったことを意味します。`src/cmd/compile/internal/gc/walk.go`の`OCONVIFACE`処理では、具体的な型とインターフェース型が与えられたときに、`itabname`関数を使用して対応する`itab`シンボルをコンパイル時に特定できるようになりました。
    `itabname`は、`Pkglookup`を使って`itabpkg`（`itab`エントリの擬似パッケージ）から`itab`シンボルを検索または作成します。これにより、コンパイラは`convT2I`を呼び出す際に、必要な`itab`のアドレスを直接引数として渡すことができるようになります。

3.  **`itab`キャッシュの最適化**:
    以前は、`convT2I`が呼び出されるたびに、`atomic.Loadp`と`atomicstorep`を使って`itab`キャッシュをチェックし、必要に応じて更新していました。これらのアトミック操作は、並行アクセスから保護するために必要ですが、それ自体が一定のコストを伴います。
    コンパイラが`itab`のアドレスを直接渡せるようになったことで、ランタイムの`convT2I`からこれらのアトミック操作が削除され、実行時の効率が向上します。これは、コンパイル時に`itab`が静的に決定できるケースにおいて特に有効です。

4.  **`typ2Itab`関数の廃止**:
    `typ2Itab`関数は、ランタイムで`itab`を検索・構築し、キャッシュにストアする役割を担っていました。コンパイラが`itab`のアドレスを直接渡すようになったため、この関数は不要となり、削除されました。これにより、ランタイムのコードベースが簡素化されます。

この最適化は、Goのインターフェース変換のパフォーマンスを向上させるための重要なステップであり、コンパイラとランタイムの間の責任分担をより効率的な形に再調整したものです。

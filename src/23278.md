## 変更の背景

この変更の背景には、Go言語の`fmt`パッケージが、書式設定文字列（format string）内の数値（例えば、フィールド幅や精度を指定する際に使われる数値）を解析する際に、非常に大きな数値が与えられた場合に適切にオーバーフローを検出できていなかったという問題があります。コミットメッセージにある「The old one was inferior.（以前のものは劣っていた）」という記述は、既存のオーバーフロー検出ロジックが不十分であったことを示唆しています。

具体的には、Goの`fmt`パッケージは、`Printf`系の関数などで使用されるフォーマット動詞（例: `%d`, `%s`, `%v`など）に付随する数値（例: `%10d`の`10`）を解析する際に、内部的に数値を読み取る処理を行います。この処理において、入力された数値がGoの`int`型で表現できる範囲を超えていた場合、予期せぬ動作やクラッシュを引き起こす可能性がありました。特に、負の数へのオーバーフローに依存するような検出方法は、符号なし整数型や、特定のアーキテクチャにおける整数の挙動に依存するため、移植性や信頼性に欠ける場合があります。

このコミットは、このような潜在的な問題を解決し、`fmt`パッケージがより堅牢に、そして予測可能に動作するようにするための改善です。`Fixes #10695`という記述がありますが、現在のGoの公開イシュートラッカーではこの番号のイシューは見つかりませんでした。これは、イシューが非常に古く、アーカイブされたか、内部的なイシュー番号であった可能性が考えられます。しかし、変更内容から、大きな数値入力に対する堅牢性向上が目的であることは明らかです。

## 前提知識の解説

### Go言語の`fmt`パッケージ

`fmt`パッケージは、Go言語における基本的な入出力フォーマット機能を提供します。C言語の`printf`や`scanf`に似た機能を持っており、様々なデータ型を整形して文字列に出力したり、文字列からデータを読み取ったりすることができます。

- **フォーマット動詞 (Format Verbs)**: `%d`（整数）、`%s`（文字列）、`%v`（任意の型）、`%T`（型の名前）など、出力するデータの型や形式を指定する記号です。
- **フィールド幅 (Field Width)**: フォーマット動詞の前に指定される数値で、出力される値が占める最小の文字数を指定します（例: `%10d`は、整数を少なくとも10文字幅で出力します）。
- **精度 (Precision)**: 浮動小数点数や文字列に対して、小数点以下の桁数や最大文字数などを指定します（例: `%.2f`は、浮動小数点数を小数点以下2桁で出力します）。

### 整数オーバーフロー

コンピュータにおける整数型には、表現できる数値の範囲に限りがあります。この範囲を超える数値を扱おうとすると、「オーバーフロー」が発生します。

- **符号付き整数 (Signed Integer)**: 正と負の数を表現できる整数型です。例えば、32ビットの符号付き整数（`int32`）は、約-20億から+20億までの範囲を表現できます。この範囲を超えて大きな数値を代入しようとすると、通常は最大値から最小値に「ラップアラウンド」し、負の数になることがあります（例: `MAX_INT + 1`が`MIN_INT`になる）。
- **符号なし整数 (Unsigned Integer)**: 負の数を表現せず、0以上の数のみを表現できる整数型です。例えば、32ビットの符号なし整数（`uint32`）は、0から約40億までの範囲を表現できます。

オーバーフローの検出は、プログラムの堅牢性を保つ上で非常に重要です。特に、ユーザーからの入力や外部データに基づいて数値を解析する場合、悪意のある入力や予期せぬ大きな数値によってプログラムがクラッシュしたり、誤った結果を生成したりするのを防ぐ必要があります。

### `parsenum`関数

このコミットで変更された`parsenum`関数は、`fmt`パッケージの内部で、フォーマット文字列から数値（フィールド幅や精度など）を解析するために使用されるユーティリティ関数です。文字列中の数字列を読み取り、それを整数値に変換する役割を担っています。この関数は、数値の読み取り中にオーバーフローが発生しないように、適切なチェックを行う必要があります。

## 技術的詳細

このコミットの核心は、`src/fmt/print.go`内の`parsenum`関数における数値オーバーフロー検出ロジックの改善です。

### 変更前のオーバーフロー検出

変更前のコードでは、数値の読み取りと同時にオーバーフローをチェックしていました。

```go
		num = num*10 + int(s[newi]-'0')
		if num < 0 {
			return 0, false, end // Overflow; crazy long number most likely.
		}
```

このロジックは、`num`が`int`型の最大値を超えてオーバーフローし、結果として負の値になった場合にのみオーバーフローを検出します。しかし、この方法はいくつかの問題点があります。

1.  **符号付き整数のラップアラウンドに依存**: このチェックは、符号付き整数がオーバーフローした際に負の値にラップアラウンドするという特定の挙動に依存しています。これはGoの仕様で保証されている挙動ではありますが、より明示的なチェックが望ましいです。
2.  **検出の遅延**: オーバーフローが発生した「後」に検出するため、`num`がすでに不正な値になっている可能性があります。
3.  **`int`型のサイズ**: `int`型はシステムによって32ビットまたは64ビットのいずれかになります。32ビットシステムで非常に大きな数値が入力された場合、このチェックでは不十分な可能性があります。特に、フォーマットの幅や精度は通常、そこまで大きな値は必要ありません。

### 変更後のオーバーフロー検出

変更後のコードでは、数値の読み取りを行う「前」に、次の桁を読み込んだ場合にオーバーフローするかどうかを事前にチェックするようになりました。

```go
		const maxInt32 = 1<<31 - 1 // 31 bits is plenty for a width.
		max := maxInt32/10 - 1
		if num > max {
			return 0, false, end // Overflow; crazy long number most likely.
		}
		num = num*10 + int(s[newi]-'0')
```

この新しいロジックのポイントは以下の通りです。

1.  **`maxInt32`の導入**: `const maxInt32 = 1<<31 - 1`は、32ビット符号付き整数の最大値を定義しています。コメントにある「31 bits is plenty for a width.（幅には31ビットで十分）」という記述から、`fmt`パッケージの幅や精度指定には、32ビット整数で十分であるという設計上の考慮が読み取れます。これにより、たとえ実行環境の`int`型が64ビットであっても、意図的に32ビットの範囲でオーバーフローを検出するようになります。これは、非常に大きな幅や精度が指定された場合に、それが無効な入力であると判断するためのものです。
2.  **事前チェック**: `max := maxInt32/10 - 1`は、現在の`num`に次の桁（0-9）を加えて10倍しても`maxInt32`を超えないための安全な上限値を計算しています。
3.  **`if num > max`**: この条件式は、現在の`num`が、次の桁を読み込んだ場合に`maxInt32`を超えてしまう可能性があるかどうかをチェックします。もし超える可能性がある場合、その時点でオーバーフローと判断し、解析を中断してエラーを返します。これにより、`num`が不正な値になる前にオーバーフローを検出できます。
4.  **堅牢性と移植性**: この事前チェック方式は、特定のアーキテクチャにおける整数のラップアラウンド挙動に依存せず、より明示的で堅牢なオーバーフロー検出を提供します。

## コアとなるコードの解説

### `src/fmt/fmt_test.go`の変更点

追加されたテストケースは以下の通りです。

```go
{"%184467440737095516170v", 0, "%!(NOVERB)%!(EXTRA int=0)"},
```

この行は、`fmtTests`というテスト構造体スライスに新しい要素を追加しています。
-   最初の文字列`"%184467440737095516170v"`は、テスト対象のフォーマット文字列です。ここで注目すべきは、`%`と`v`の間に非常に大きな数値`184467440737095516170`が挿入されている点です。これは、`v`動詞のフィールド幅として解釈されることを意図しています。この数値は`uint64`の最大値（約1.84 x 10^19）よりも大きく、Goの`int`型（通常64ビットシステムでは`int64`、32ビットシステムでは`int32`）では表現できない値です。
-   `0`は、フォーマットされる引数です。このテストでは、引数の値自体は重要ではなく、フォーマット文字列の解析が正しく行われるかどうかが焦点です。
-   最後の文字列`"%!(NOVERB)%!(EXTRA int=0)"`は、期待される出力結果です。これは、`fmt`パッケージがこの非常に大きな数値を有効な幅として解析できず、エラーとして処理したことを示しています。具体的には、`%!(NOVERB)`は有効なフォーマット動詞が見つからなかったことを、`%!(EXTRA int=0)`は余分な引数があったことを示唆していますが、この文脈では、幅の解析が失敗した結果としてこのようなエラーメッセージが生成されることを確認しています。

このテストケースの追加により、`parsenum`関数がこのような極端な入力に対して適切にオーバーフローを検出し、エラーを返すことを保証します。

### `src/fmt/print.go`の`parsenum`関数の変更点

`parsenum`関数は、文字列`s`の`start`から`end`までの範囲から数値を解析します。

**変更前のロジック:**

```go
		num = num*10 + int(s[newi]-'0')
		if num < 0 {
			return 0, false, end // Overflow; crazy long number most likely.
		}
```

このコードは、現在の`num`に新しい桁を加えて10倍した後に、その結果が負になった場合にオーバーフローと判断していました。これは、符号付き整数が最大値を超えてラップアラウンドし、負の値になるという挙動を利用したものです。しかし、これは間接的な検出方法であり、`num`がすでにオーバーフローした状態になってから検出されるため、潜在的な問題がありました。

**変更後のロジック:**

```go
		const maxInt32 = 1<<31 - 1 // 31 bits is plenty for a width.
		max := maxInt32/10 - 1
		if num > max {
			return 0, false, end // Overflow; crazy long number most likely.
		}
		num = num*10 + int(s[newi]-'0')
```

1.  `const maxInt32 = 1<<31 - 1`:
    これは、32ビット符号付き整数の最大値を定義しています。`1`を31ビット左シフトし、そこから1を引くことで、`0111...111`（31個の1）というビットパターン、すなわち`int32`の最大値（2,147,483,647）を生成します。この定数は、`fmt`パッケージの幅や精度が32ビット整数で十分であるという設計上の制約を明示しています。これにより、たとえ`int`型が64ビットであっても、この関数が解析する数値は32ビットの範囲に収まるべきであるという意図が明確になります。

2.  `max := maxInt32/10 - 1`:
    この行は、次に読み込む桁（`s[newi]-'0'`）を`num`に加算し、さらに10倍しても`maxInt32`を超えないための、現在の`num`の最大許容値を計算しています。
    -   `maxInt32/10`: `maxInt32`を10で割った値です。これは、`num`がこの値を超えると、次の桁を加えて10倍したときに`maxInt32`を超える可能性があることを示します。
    -   `- 1`: さらに1を引くことで、次の桁が`9`であった場合でもオーバーフローしないように、安全マージンを設けています。例えば、`maxInt32`が2147483647の場合、`maxInt32/10`は214748364です。`max`は214748363となります。もし`num`が214748364で次の桁が`0`であれば`num*10+0`は2147483640となり、`maxInt32`を超えます。この`max`の計算により、`num`が`max`を超えた時点で、次の桁を読み込むと確実にオーバーフローすることが保証されます。

3.  `if num > max`:
    この条件式は、現在の`num`が、次に読み込む桁を考慮しても`maxInt32`の範囲内に収まるかどうかを事前にチェックします。もし`num`が`max`を超えている場合、次の桁を読み込むと確実にオーバーフローするため、その時点で`return 0, false, end`を実行し、オーバーフローエラーとして処理を終了します。

この新しいロジックは、オーバーフローが発生する「前」にそれを予測し、処理を中断することで、より安全で堅牢な数値解析を実現しています。これにより、不正な入力によって`fmt`パッケージが予期せぬ動作をするリスクが低減されます。

# [インデックス 20420] ファイルの概要

このコミットは、GoランタイムにおけるWindowsシステムコール（Syscall）のスタックコピーに関する問題を修正するものです。特に、`Syscall`関数とその内部で呼び出されるすべての関数が`nosplit`（スタック分割を行わない）である必要があるという制約に対応しています。これは、`Syscall`が呼び出された後では、その引数のどれがポインタであるかをランタイムが判断できないため、スタックの安全な分割が困難になるためです。

## 変更の背景

Goランタイムは、ゴルーチンスタックの動的なサイズ変更（スタック分割）をサポートしています。これにより、必要に応じてスタックを拡張できます。しかし、システムコール（特にWindows API呼び出し）を行う際には、このスタック分割のメカニズムが問題を引き起こす可能性があります。

Windowsシステムコールは、Goランタイムの管理外のネイティブコードを実行します。Goのガベージコレクタは、スタック上のポインタをスキャンして到達可能なオブジェクトを特定しますが、システムコールが実行されている間は、スタック上のどの値がGoのポインタであるかを正確に識別することが困難になります。もしシステムコール中にスタック分割が発生し、スタックが移動したり拡張されたりすると、ガベージコレクタが誤ったポインタをスキャンしたり、無効なメモリにアクセスしたりするリスクが生じます。これは、メモリ破損やクラッシュにつながる可能性があります。

この問題を回避するため、`Syscall`関数とその関連する低レベル関数は、スタック分割を禁止する`nosplit`属性を持つ必要があります。これにより、システムコール実行中にスタックが変更されることがなくなり、ガベージコレクタの安全性が保証されます。このコミットは、この`nosplit`の制約をWindowsシステムコール関連のコードに適用することで、これらの潜在的な問題を修正することを目的としています。

## 前提知識の解説

### 1. Goのスタック管理とスタック分割 (Stack Splitting)

Goのゴルーチンは、比較的小さな初期スタックサイズで開始し、必要に応じて自動的にスタックを拡張します。これを「スタック分割」と呼びます。関数が呼び出される際、Goランタイムは通常、スタックに十分な空きがあるかを確認します。もし足りなければ、より大きなスタックを割り当て、現在のスタックの内容を新しいスタックにコピーし、実行を継続します。このプロセスは透過的に行われ、開発者は通常、スタックサイズを意識する必要がありません。

### 2. `//go:nosplit` ディレクティブ

`//go:nosplit`は、Goコンパイラに対する特殊なディレクティブで、その関数に対してスタックオーバーフローチェックを省略するよう指示します。つまり、このディレクティブが付与された関数は、スタックが足りなくなった場合でも自動的にスタックを拡張しようとしません。これは、以下のような特定の低レベルのランタイム関数で使用されます。

*   **スタックの安全なスキャンが困難な場合**: システムコールやCgo呼び出しのように、Goランタイムがスタック上のすべての値をGoのポインタとして認識できない状況では、スタック分割によるスタックの移動がメモリ安全性の問題を引き起こす可能性があります。
*   **プリエンプションの抑制**: `nosplit`関数は、スタック分割を伴うプリエンプションポイントを生成しないため、クリティカルなセクションでの実行を保証するのに役立ちます。
*   **パフォーマンス**: スタックチェックのオーバーヘッドを排除することで、わずかなパフォーマンス向上が期待できますが、これは主にランタイムの内部で重要です。

`nosplit`関数は、呼び出し元が十分なスタック空間を保証できる場合にのみ安全に使用できます。誤用すると、スタックオーバーフローによるクラッシュを引き起こす可能性があります。

### 3. Cgoとシステムコール (Syscall)

GoプログラムがC言語のライブラリやオペレーティングシステムのネイティブAPI（システムコール）を呼び出す場合、GoランタイムはCgoメカニズムを介してこれらの呼び出しを仲介します。この際、GoのスタックとCのスタック（またはOSスレッドのスタック）の間でコンテキストの切り替えが発生します。

Windowsシステムコールの場合、GoランタイムはWindows APIの呼び出し規約（例: `stdcall`）に従って引数を準備し、ネイティブコードに制御を渡します。この過程で、Goのガベージコレクタがスタックをスキャンするタイミングと、ネイティブコードがスタックを使用するタイミングが重なる可能性があり、スタックの整合性を維持することが重要になります。

### 4. `cgocall` と `cgocall_errno`

`cgocall`は、GoからCへの呼び出しを処理するGoランタイムの内部関数です。`cgocall_errno`は、エラーコードを返すCgo呼び出しを処理する際に使用されます。これらの関数は、GoのゴルーチンスタックからOSスレッドのスタックへの移行を管理し、Cコードの実行を可能にします。

## 技術的詳細

このコミットの核心は、Windowsシステムコールに関連するGoランタイムのCコード（`.c`ファイル）およびGoコード（`.go`ファイル）に`nosplit`属性を明示的に適用することです。

Goランタイムは、`Syscall`関数が呼び出された後、その引数がポインタであるかどうかを追跡できません。これは、Windows APIがGoの型システムとは異なる方法でメモリを扱うためです。もし`Syscall`の実行中にスタック分割が発生し、スタックが移動すると、ガベージコレクタが誤ったメモリ位置をスキャンしたり、無効なポインタを検出したりする可能性があります。これにより、プログラムのクラッシュや未定義の動作につながります。

この問題を解決するため、コミットでは以下の変更が行われています。

1.  **`cgocall` および `cgocall_errno` への `//go:nosplit` の追加**:
    `src/pkg/runtime/cgocall.go` 内の `cgocall` および `cgocall_errno` 関数に `//go:nosplit` ディレクティブが追加されました。これにより、GoからCへの呼び出しを行うこれらの基盤関数がスタック分割を行わないことが保証されます。これは、システムコールがCgoメカニズムを介して行われるため、非常に重要です。

2.  **`src/pkg/runtime/os_windows.c` 内のランタイム関数への `#pragma textflag NOSPLIT` の追加**:
    Windows固有のランタイムC関数（例: `runtime·exit`, `runtime·write`, `runtime·semawakeup`, `runtime·semacreate`, `runtime·systime`, `runtime·nanotime`, `time·now`）に `#pragma textflag NOSPLIT` が追加されました。これは、Cコードにおける`nosplit`の同等物であり、これらの関数がスタック分割を行わないことをコンパイラに指示します。これらの関数は、システムコールを直接的または間接的に呼び出す可能性があり、スタックの安全性を確保するために`nosplit`である必要があります。

3.  **`src/pkg/runtime/syscall_windows.c` の新規作成と `syscall_windows.goc` の削除**:
    以前は `src/pkg/runtime/syscall_windows.goc` というファイルで定義されていたWindowsシステムコール関連のCgo関数（`syscall·loadlibrary`, `syscall·getprocaddress`, `syscall·Syscall`など）が、`src/pkg/runtime/syscall_windows.c` という新しいファイルに移動されました。
    この新しいファイル内のすべての関数にも `#pragma textflag NOSPLIT` が付与されています。
    `.goc`ファイルは、GoのツールチェーンによってCコードに変換される特殊なファイルでしたが、この変更により、純粋なCファイルとして直接コンパイルされるようになりました。これにより、`nosplit`属性の適用がより直接的かつ明確になります。

これらの変更により、Windowsシステムコールが実行される間、Goランタイムはスタックの変更を試みなくなり、ガベージコレクタが安全に動作できるようになります。

### `src/pkg/runtime/cgocall.go` の変更

```go
 // Call from Go to C.
+//go:nosplit
 func cgocall(fn, arg unsafe.Pointer) {
 	cgocall_errno(fn, arg)
 }
 
+//go:nosplit
 func cgocall_errno(fn, arg unsafe.Pointer) int32 {
 	if !iscgo && GOOS != "solaris" && GOOS != "windows" {
 		gothrow("cgocall unavailable")
```
`cgocall`と`cgocall_errno`は、GoランタイムがCコードを呼び出すためのエントリポイントです。これらの関数に`//go:nosplit`ディレクティブを追加することで、Cコードへの移行中にGoのスタックが拡張されることを防ぎます。これにより、CコードがGoのスタックを直接操作する際に、スタックの移動による問題が発生するリスクがなくなります。

### `src/pkg/runtime/os_windows.c` の変更

```c
 #pragma textflag NOSPLIT
 void
 runtime·exit(int32 code)
 {
 	runtime·stdcall1(runtime·ExitProcess, code);
 }
```
`#pragma textflag NOSPLIT`は、Cコンパイラに対して、続く関数がスタック分割を行わないように指示するディレクティブです。`os_windows.c`内の多くのランタイム関数は、Windows APIを直接呼び出すか、システムコールに関連する低レベルの操作を行います。これらの関数が`nosplit`であることは、システムコール実行中のスタックの安定性を保証するために不可欠です。

特に注目すべきは、`runtime·systime`関数内のエラーハンドリングの変更です。
```c
 // Old code:
 // runtime·throw("interrupt/system time is changing too fast");
 
 // New code:
 fn = badsystime;
 runtime·onM(&fn);
```
以前は`runtime·throw`を直接呼び出していましたが、これはスタックを消費する可能性があり、`nosplit`のコンテキストでは問題となる可能性があります。新しいコードでは、`badsystime`という`NOSPLIT`関数を定義し、`runtime·onM`を介してその関数を呼び出すように変更されています。`runtime·onM`は、現在のM（OSスレッド）上で指定された関数を実行するためのランタイム内部関数であり、`nosplit`の制約を維持しながらエラーを安全に処理するためのメカニズムを提供します。

### `src/pkg/runtime/syscall_windows.c` の新規作成

このファイルは、WindowsシステムコールをラップするGoランタイムのC関数群を定義しています。
例えば、`syscall·Syscall`関数は以下のように定義されています。

```c
 #pragma textflag NOSPLIT
 SyscallErr
 syscall·Syscall(uintptr fn, uintptr nargs, uintptr a1, uintptr a2, uintptr a3)
 {
 	LibCall c;
 
 	USED(a2);
 	USED(a3);
 	c.fn = (void*)fn;
 	c.n = nargs;
 	c.args = &a1;
 	runtime·cgocall_errno(runtime·asmstdcall, &c);
 	return (SyscallErr){c.r1, c.r2, c.err};
 }
```
これらの関数は、Goの`syscall`パッケージから呼び出される実際のシステムコールラッパーです。すべての`syscall·SyscallN`関数に`#pragma textflag NOSPLIT`が付与されていることで、これらの関数がWindows APIを呼び出す際にスタック分割が発生しないことが保証されます。これにより、GoランタイムがWindows APIに渡す引数のポインタの安全性が確保され、ガベージコレクタがスタックを安全にスキャンできるようになります。

### `src/pkg/runtime/syscall_windows.goc` の削除

このファイルの削除は、Goのビルドシステムにおける変更を示唆しています。以前は`.goc`ファイルが使用されていましたが、より直接的なCコード（`.c`ファイル）に移行することで、コンパイルプロセスが簡素化され、`nosplit`属性の適用がより明確になったと考えられます。

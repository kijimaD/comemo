## 変更の背景

Go言語のガベージコレクタ（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要なコンポーネントです。GCの動作中、特に並行GCにおいては、プログラムがオブジェクトへのポインタを書き換える際に、GCがオブジェクトグラフを正確に追跡できるように「ライトバリア（Write Barrier）」と呼ばれる処理を挿入する必要があります。ライトバリアは、ポインタの書き込み操作をインターセプトし、GCが必要とする情報を記録する役割を担います。

しかし、Goランタイムの非常に低レベルな部分、特にGC自体が動作するコードや、特定の最適化されたコードでは、ライトバリアの挿入が問題を引き起こす可能性があります。例えば、GCの内部ロジックでライトバリアが発火すると、デッドロックや無限ループ、あるいはGCの正確性を損なうような予期せぬ副作用が生じる可能性があります。このような状況を避けるため、Goコンパイラには特定の関数に`Nowritebarrier`という属性を付与する機能があります。この属性が付与された関数は、コンパイラによってライトバリアが挿入されないように特別に扱われます。

このコミット以前は、`Nowritebarrier`属性を持つ関数内であっても、特定のコードパスでライトバリアが誤って挿入される可能性がありました。これは、コンパイラのライトバリア挿入ロジックと`Nowritebarrier`チェックの間に同期のずれがあったためです。このずれは、コンパイラがコードを生成する際のバグや、予期せぬ動作につながる可能性がありました。このコミットは、この潜在的な問題を修正し、`Nowritebarrier`属性の意図が常に尊重されるようにすることで、Goランタイムの堅牢性を高めることを目的としています。

## 前提知識の解説

### ガベージコレクタ (GC) とライトバリア

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しています。これは、GCがプログラムの実行と並行して動作し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指すものです。

並行GCでは、GCがオブジェクトグラフを走査している最中に、アプリケーションがポインタを書き換える可能性があります。この書き換えによって、GCがまだマークしていないオブジェクトが参照されなくなり、誤って解放されてしまう（「ポインタの消失」問題）か、あるいはGCが既にマークしたオブジェクトが参照されなくなり、GCが完了した後にそのオブジェクトが到達可能であるにもかかわらず解放されてしまう（「ポインタの再出現」問題）可能性があります。

この問題を解決するために導入されるのが「ライトバリア」です。ライトバリアは、ヒープ上のポインタが変更されるたびに実行される小さなコードスニペットです。GoのGCでは、Dijkstraの三色マーキングアルゴリズムの変種が使用されており、ライトバリアは通常、ポインタの書き込み時に「古い参照先のオブジェクトを灰色にマークする」または「新しい参照先のオブジェクトを灰色にマークする」といった操作を行います。これにより、GCはポインタの変更を追跡し、オブジェクトグラフの一貫性を保つことができます。

### `Nowritebarrier`属性

Goランタイムのコードベースには、`//go:nowritebarrier`というディレクティブを使って、特定の関数に`Nowritebarrier`属性を付与する慣習があります。この属性は、コンパイラに対して、その関数内ではライトバリアを挿入しないように指示します。

`Nowritebarrier`が使用される主な理由は以下の通りです。

1.  **GCの内部処理**: ガベージコレクタ自体がメモリを操作する際に、ライトバリアが挿入されると、GCのロジックが複雑になったり、デッドロックを引き起こしたりする可能性があります。GCの内部コードは、ライトバリアなしで安全に動作するように設計されています。
2.  **パフォーマンスクリティカルなコード**: 非常にパフォーマンスが要求される低レベルなコードでは、ライトバリアのオーバーヘッドを避けるために`Nowritebarrier`が使用されることがあります。
3.  **アトミック操作**: 特定のアトミックなポインタ操作では、ライトバリアが介入するとアトミック性が損なわれる可能性があるため、`Nowritebarrier`が適用されます。

`Nowritebarrier`属性は、コンパイラがコードを生成する際に考慮すべき重要な制約であり、その遵守はGoランタイムの正確性と安定性に直結します。

## 技術的詳細

このコミットは、Goコンパイラのバックエンド部分、特にコード生成（`cgen.go`）と中間表現のウォーク（`walk.go`）の段階で、`Nowritebarrier`属性のチェックを強化しています。

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現（IR）に変換し、様々な最適化を適用してから最終的な機械語コードを生成します。ライトバリアの挿入は、この中間表現の処理段階で行われます。

`cgen.go`ファイルは、主にコード生成に関連する処理を担当しています。`cgen_wbptr`と`cgen_wbfat`は、それぞれポインタのライトバリアと「fat pointer」（インターフェース値やスライスヘッダなど、ポインタと追加のデータを含む構造体）のライトバリアを生成する関数です。これらの関数は、ポインタの書き込み操作が検出された際に呼び出され、対応するライトバリアコードを挿入します。

`walk.go`ファイルは、中間表現のASTを走査（ウォーク）し、様々な変換や最適化を適用する役割を担っています。`applywritebarrier`関数は、このウォーク中に呼び出され、特定のノード（ASTの要素）に対してライトバリアを適用するかどうかを決定します。

このコミットでは、これらのライトバリアを挿入する可能性のある関数（`cgen_wbptr`, `cgen_wbfat`, `applywritebarrier`）の冒頭に、以下のチェックが追加されました。

```go
if Curfn != nil && Curfn.Func.Nowritebarrier {
    Yyerror("write barrier prohibited")
}
```

ここで:
*   `Curfn`は、現在コンパイル中の関数を表すグローバル変数です。
*   `Curfn.Func.Nowritebarrier`は、現在の関数が`Nowritebarrier`属性を持っているかどうかを示すブール値です。
*   `Yyerror("write barrier prohibited")`は、コンパイル時にエラーを報告する関数です。このエラーが発生すると、コンパイルは失敗します。

このチェックが追加されたことにより、コンパイラは`Nowritebarrier`属性を持つ関数内でライトバリアを挿入しようとした場合、即座にエラーを検出し、コンパイルを中止するようになります。これにより、ランタイムの低レベルなコードが意図せずライトバリアの影響を受けることを確実に防ぎ、Goランタイムの安定性と予測可能性が向上します。

## コアとなるコードの解説

追加されたコードは、Goコンパイラの内部で、現在処理中の関数（`Curfn`）が`Nowritebarrier`属性を持っているかどうかをチェックしています。

*   `Curfn != nil`: 現在コンパイル中の関数が存在するかどうかを確認します。これは、トップレベルのコードや初期化コードなど、特定のコンテキストでは`Curfn`が`nil`である可能性があるためです。
*   `Curfn.Func.Nowritebarrier`: `Curfn`が指す関数の定義（`Func`フィールド）に`Nowritebarrier`フラグが設定されているかどうかを確認します。このフラグは、ソースコード内の`//go:nowritebarrier`ディレクティブによって設定されます。

もし、現在コンパイル中の関数が`Nowritebarrier`属性を持ち、かつライトバリアを挿入しようとするコードパスに到達した場合、`Yyerror("write barrier prohibited")`が呼び出されます。`Yyerror`はコンパイラのエラー報告メカニズムの一部であり、指定されたメッセージと共にコンパイルエラーを発生させます。これにより、開発者は`Nowritebarrier`属性の誤用や、コンパイラのライトバリア挿入ロジックのバグを早期に発見できるようになります。

この変更は、コンパイラが`Nowritebarrier`属性のセマンティクスをより厳密に強制することを保証し、Goランタイムの低レベルなコードがライトバリアによって予期せぬ影響を受けることを防ぐための重要な安全策です。

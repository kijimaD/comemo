## 変更の背景

Go言語の `math/big` パッケージは、任意精度の整数 (`Int`) や有理数 (`Rat`) を扱うための機能を提供します。これらの型は、標準の `int` や `float64` では表現できない非常に大きな数値を扱う際に不可欠です。しかし、これらの大きな数値をJSONやテキスト形式で外部にエンコードする際、内部表現から人間が読める文字列形式への変換が必要になります。

以前の実装では、`Int` 型や `Rat` 型を `json.Marshaler` や `encoding.TextMarshaler` インターフェースを通じてエンコードする際に、まず `String()` メソッドを呼び出して `string` 型の表現を取得し、その後その `string` を `[]byte` 型に変換していました。この `string` 型への中間変換は、特に桁数の多い大きな数値の場合、不要なメモリ割り当てとCPUサイクルを消費し、パフォーマンスのボトルネックとなることが知られていました。

このコミットは、この非効率性を解消し、`Int` および `Rat` 型のエンコーディング性能を向上させることを目的としています。具体的には、中間的な `string` 型への変換を避け、数値を直接バイト列として表現する内部関数 `itoa` を利用することで、より効率的なエンコーディングパスを実現しています。

## 前提知識の解説

### `math/big` パッケージ

`math/big` パッケージは、Go言語で任意精度の数値を扱うための機能を提供します。これは、標準の組み込み型（`int`, `float64` など）が持つ精度や範囲の限界を超える計算が必要な場合に利用されます。
*   **`big.Int`**: 任意精度の整数を表現します。非常に大きな整数値（例: 暗号通貨の計算、科学技術計算）を扱う際に使用されます。
*   **`big.Rat`**: 任意精度の有理数（分数）を表現します。正確な分数計算が必要な場合（例: 金融計算）に利用されます。

### `json.Marshaler` と `encoding.TextMarshaler` インターフェース

Go言語では、構造体やカスタム型をJSONやテキスト形式にエンコード（マーシャリング）する際に、標準の `encoding/json` や `encoding` パッケージが提供する機能を利用します。これらのパッケージは、特定のインターフェースを実装することで、カスタムのマーシャリングロジックを提供することを可能にします。

*   **`json.Marshaler` インターフェース**:
    ```go
    type Marshaler interface {
        MarshalJSON() ([]byte, error)
    }
    ```
    このインターフェースを実装する型は、`MarshalJSON` メソッドを提供することで、JSONエンコーダがその型の値をどのようにJSONバイト列に変換するかを制御できます。

*   **`encoding.TextMarshaler` インターフェース**:
    ```go
    type TextMarshaler interface {
        MarshalText() (text []byte, err error)
    }
    ```
    このインターフェースを実装する型は、`MarshalText` メソッドを提供することで、テキストエンコーダがその型の値をどのようにテキストバイト列に変換するかを制御できます。

これらのインターフェースを実装することで、開発者は型の内部表現と外部表現の間の変換を細かくカスタマイズできます。

### Goにおける文字列変換のコスト

Go言語において、`string` 型は不変なバイト列として扱われます。`[]byte` と `string` の間で変換を行う場合、多くの場合、新しいメモリ割り当てとデータのコピーが発生します。特に、大きなデータ構造や頻繁な変換が必要なシナリオでは、このオーバーヘッドがパフォーマンスに大きな影響を与える可能性があります。

`math/big` パッケージの数値は、その性質上、非常に多くの桁数を持つことがあります。このような大きな数値を `String()` メソッドで `string` に変換し、さらにそれを `[]byte` に変換するという二段階のプロセスは、以下の点で非効率です。
1.  **中間 `string` の生成**: `String()` メソッドは、数値を10進数文字列に変換するために計算を行い、その結果を新しい `string` オブジェクトとしてメモリに割り当てます。
2.  **`[]byte` へのコピー**: その後、`[]byte(s)` のように `string` を `[]byte` にキャストする際、`string` の内容が新しい `[]byte` スライスにコピーされます。

この二重のメモリ割り当てとコピーは、特にパフォーマンスが要求される場面で顕著なオーバーヘッドとなります。

## 技術的詳細

このコミットの核心は、`math/big.Int` および `math/big.Rat` 型の `MarshalJSON` と `MarshalText` メソッドから、中間的な `string` 型への変換を排除することです。

変更前は、これらのメソッドは以下のようなロジックでした。

```go
// MarshalJSON (変更前)
func (z *Int) MarshalJSON() ([]byte, error) {
    return []byte(z.String()), nil // z.String()でstringを生成し、それを[]byteに変換
}

// MarshalText (変更前)
func (z *Int) MarshalText() (text []byte, err error) {
    return []byte(z.String()), nil // z.String()でstringを生成し、それを[]byteに変換
}
```

変更後、これらのメソッドは `x.abs.itoa(x.neg, 10)` という内部関数を直接呼び出すようになりました。

```go
// MarshalJSON (変更後)
func (x *Int) MarshalJSON() ([]byte, error) {
    if x == nil {
        return []byte("<nil>"), nil // nilレシーバのハンドリングを追加
    }
    return x.abs.itoa(x.neg, 10), nil // 直接バイト列を生成
}

// MarshalText (変更後)
func (x *Int) MarshalText() (text []byte, err error) {
    if x == nil {
        return []byte("<nil>"), nil // nilレシーバのハンドリングを追加
    }
    return x.abs.itoa(x.neg, 10), nil // 直接バイト列を生成
}
```

ここで重要なのは `itoa` 関数です。`itoa` は "integer to ASCII" の略で、`big.Int` の内部表現（`abs` は絶対値、`neg` は符号を示す）から直接10進数表現のバイト列 (`[]byte`) を生成する効率的な内部ヘルパー関数です。この関数を直接利用することで、`String()` メソッドが生成する中間的な `string` オブジェクトの割り当てと、その後の `[]byte` へのコピーが不要になります。これにより、メモリ使用量が削減され、エンコーディング処理の速度が向上します。

また、このコミットでは、`MarshalJSON` および `MarshalText` メソッドが `nil` レシーバで呼び出された場合のハンドリングも追加されています。これは、`*big.Int` や `*big.Rat` が `nil` の場合に `"<nil>"` というバイト列を返すようにすることで、より堅牢な動作を保証します。

`math/big/ratmarsh.go` の `MarshalText` メソッドについても同様の変更が適用されていますが、こちらは `RatString()` メソッドを呼び出した後に `[]byte` に変換するロジックが残っており、コメントで将来的な改善の余地が示唆されています。これは `Rat` 型の `itoa` に相当する直接的なバイト列生成関数がまだ存在しないためと考えられます。

## コアとなるコードの解説

### `src/math/big/intmarsh.go` の変更点

*   **`(*Int).MarshalJSON()`**:
    *   変更前: `return []byte(z.String()), nil`
    *   変更後:
        ```go
        if x == nil {
            return []byte("<nil>"), nil
        }
        return x.abs.itoa(x.neg, 10), nil
        ```
    *   `z.String()` を呼び出して `string` を生成し、それを `[]byte` に変換する代わりに、`x.abs.itoa(x.neg, 10)` を直接呼び出すことで、`big.Int` の内部表現から直接10進数バイト列を生成するように変更されました。これにより、中間的な `string` オブジェクトの生成とコピーが回避され、パフォーマンスが向上します。
    *   レシーバ `x` が `nil` の場合のチェックが追加され、`"<nil>"` というバイト列を返すようになりました。これにより、`nil` の `*big.Int` をJSONにマーシャリングしようとした際の挙動が明確になります。

*   **`(*Int).MarshalText()`**:
    *   `MarshalJSON` と同様に、`[]byte(z.String())` から `x.abs.itoa(x.neg, 10)` への変更と、`nil` レシーバのハンドリングが追加されました。これにより、`encoding.TextMarshaler` インターフェースを通じたテキストエンコーディングも効率化されます。

*   **`(*Int).UnmarshalJSON()` および `(*Int).UnmarshalText()`**:
    *   これらのメソッドには、`// TODO(gri): get rid of the []byte/string conversion` というコメントが追加されました。これは、アンマーシャリング時にも `string(text)` という変換が残っており、将来的にこの部分も最適化される可能性があることを示唆しています。

### `src/math/big/ratmarsh.go` の変更点

*   **`(*Rat).MarshalText()`**:
    *   `// TODO(gri): get rid of the []byte/string conversion` というコメントが追加されました。`Rat` 型の `MarshalText` は依然として `[]byte(r.RatString())` を使用しており、`Int` 型のように直接バイト列を生成する `itoa` に相当する最適化はまだ適用されていません。これは、`Rat` 型の文字列表現が分子と分母の組み合わせであるため、`Int` 型よりも複雑なロジックが必要となるためと考えられます。

*   **`(*Rat).UnmarshalText()`**:
    *   `UnmarshalJSON` と同様に、`// TODO(gri): get rid of the []byte/string conversion` というコメントが追加されました。

このコミットは、`math/big.Int` のエンコーディングパスにおける重要なパフォーマンス改善であり、特に大きな整数を扱うアプリケーションにおいて、JSONやテキスト形式でのデータ交換の効率を高める効果があります。

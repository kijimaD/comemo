## 変更の背景

このコミットは、Goプログラムを共有ライブラリとしてリンクする際に発生する `moduledata` のサイズ設定に関する問題を修正することを目的としています。

Goのランタイムは、実行時にプログラムのメタデータ（型情報、関数情報、グローバル変数など）を管理するために `moduledata` という構造体を使用します。通常、コンパイラは `moduledata` のサイズを事前に計算し、リンカはその情報を使用します。しかし、`-linkshared` オプションを使用して共有ライブラリとしてリンクする場合、ランタイムを含まないオブジェクトをリンクすることがあります。この場合、`moduledata` はリンカによってゼロから構築されるため、コンパイラが提供する事前のサイズ情報が存在しませんでした。

この状況下では、`moduledata` のサイズが正しく設定されず、結果としてランタイムが `moduledata` を適切に初期化できない、あるいは誤ったメモリ領域を参照してしまう可能性がありました。これは、特に動的リンクされたGoプログラムの安定性や正確性に影響を与えるバグにつながる可能性があります。

このコミットは、`-linkshared` のシナリオにおいて、`moduledata` の実際の型情報からそのサイズを動的に取得することで、この問題を解決しようとしています。

## 前提知識の解説

### Goのリンカ (`cmd/internal/ld`)

`cmd/internal/ld` は、Goコンパイラツールチェーンの一部であり、Goのソースコードから実行可能バイナリやライブラリを生成する際のリンク処理を担当します。リンカの主な役割は以下の通りです。

*   **オブジェクトファイルの結合**: コンパイラによって生成された複数のオブジェクトファイル（`.o` ファイル）を結合します。
*   **シンボル解決**: 各オブジェクトファイルで定義されたシンボル（関数、変数など）を解決し、それらが参照するアドレスを決定します。
*   **メモリレイアウトの決定**: 最終的なバイナリのメモリレイアウトを決定し、セクション（コード、データなど）を配置します。
*   **ランタイムとの連携**: Goランタイムが必要とするメタデータ（`moduledata` など）をバイナリに埋め込みます。

### `moduledata` 構造体

`moduledata` はGoランタイム内部で使用される重要なデータ構造です。これは、Goのバイナリが実行時に自身の構造や含まれる型、関数、グローバル変数などのメタデータにアクセスするために使用されます。具体的には、以下のような情報を含んでいます。

*   **型情報**: プログラム内で定義されているすべての型の情報。
*   **関数情報**: 各関数の開始アドレス、終了アドレス、スタックフレームサイズなど。
*   **グローバル変数**: グローバル変数のアドレスとサイズ。
*   **GC関連情報**: ガベージコレクションに必要な情報。
*   **モジュール間のリンク情報**: 複数のGoモジュールがリンクされている場合の関連情報。

Goのランタイムは、この `moduledata` を参照して、リフレクション、スタックトレースの生成、ガベージコレクション、デバッグなどの様々な内部処理を行います。

### `moduledatasize`

`moduledatasize` は、`moduledata` 構造体のメモリ上での実際のサイズを指します。リンカは、このサイズ情報に基づいて `moduledata` のためのメモリを確保し、適切に初期化する必要があります。

### 共有ライブラリと `-linkshared`

Goは通常、静的リンクされたバイナリを生成します。これは、すべての依存関係（Goランタイムを含む）が単一の実行可能ファイルにバンドルされることを意味します。しかし、`-linkshared` オプションを使用すると、Goプログラムを共有ライブラリ（例: Linuxの`.so`、macOSの`.dylib`、Windowsの`.dll`）としてビルドしたり、既存の共有ライブラリにリンクしたりすることができます。

共有ライブラリを使用する主な利点は以下の通りです。

*   **バイナリサイズの削減**: 複数のプログラムが同じ共有ライブラリを使用する場合、各プログラムがランタイムのコピーを持つ必要がなくなるため、個々のバイナリサイズが小さくなります。
*   **メモリ使用量の削減**: 複数のプロセスが同じ共有ライブラリを使用する場合、メモリ上でライブラリのコードが共有されるため、システム全体のメモリ使用量が削減されます。
*   **更新の容易さ**: 共有ライブラリを更新するだけで、それに依存するすべてのプログラムが更新されたライブラリを使用するようになります。

`-linkshared` オプションは、Goプログラムが動的にリンクされるシナリオで重要になります。このモードでは、Goランタイム自体が別の共有ライブラリとして提供されることがあり、アプリケーションのバイナリにはランタイムのコードが含まれない場合があります。このことが、`moduledata` のサイズ計算に影響を与えていました。

## 技術的詳細

このコミットの核心は、`moduledata` のサイズを決定する方法の変更にあります。

変更前は、`moduledata` シンボルの `Size` フィールドを一時的に `moduledatasize` という変数に保存し、`moduledata.Size` を0にリセットした後、最後に保存しておいた `moduledatasize` を再度設定していました。これは、コンパイラが事前に計算した `moduledata` のサイズを信頼していることを示唆しています。

しかし、`-linkshared` オプションが使用され、リンカがランタイムを含まないオブジェクトをリンクする場合、`moduledata` はコンパイラによって事前にサイズが計算されていません。このシナリオでは、`moduledata.Size` は初期状態で正しい値を持っていません。

この問題を解決するため、コミットでは以下の変更が行われました。

1.  **`moduledatasize` 変数の削除**: 一時的にサイズを保存していた `moduledatasize` 変数が削除されました。これは、コンパイラが提供するサイズに依存しないアプローチへの移行を示しています。
2.  **`moduledata` サイズの動的な取得**:
    *   `moduledatatype := Linkrlookup(Ctxt, "type.runtime.moduledata", 0)`: `Linkrlookup` 関数を使用して、`"type.runtime.moduledata"` というシンボルをルックアップしています。このシンボルは、Goランタイムが定義する `moduledata` 構造体自体の型情報への参照です。
    *   `moduledata.Size = decodetype_size(moduledatatype)`: `decodetype_size` 関数は、与えられた型情報（ここでは `moduledata` の型情報）から、その型の実際のメモリ上のサイズを計算して返します。これにより、コンパイラが事前にサイズを提供しない場合でも、リンカが `moduledata` の正しいサイズを動的に決定できるようになります。
3.  **`Symgrow` の引数変更**: `Symgrow(Ctxt, moduledata, moduledata.Size)` となり、動的に取得した `moduledata.Size` を使用してシンボルを成長させるようになりました。

この変更により、`-linkshared` を使用してビルドされたGoプログラムでも、`moduledata` が常に正しいサイズで初期化されることが保証されます。これは、Goの動的リンク機能の堅牢性を向上させる上で重要な修正です。

## コアとなるコードの解説

変更されたコードブロックは、`symtab` 関数内で `runtime.firstmoduledata` シンボルを初期化する部分です。

**変更前:**

```go
	moduledata := Linklookup(Ctxt, "runtime.firstmoduledata", 0)
	moduledata.Type = obj.SNOPTRDATA
	moduledatasize := moduledata.Size // moduledataの現在のサイズを一時変数に保存
	moduledata.Size = 0 // シンボルサイズをリセット
	// ... (moduledataの他のフィールドの初期化)
	moduledata.Size = moduledatasize // 保存しておいたサイズを再設定
	Symgrow(Ctxt, moduledata, moduledatasize) // そのサイズでシンボルを成長させる
```
このコードは、`moduledata` シンボルが既に正しい `Size` を持っていることを前提としていました。しかし、`-linkshared` の場合、この前提が崩れることが問題でした。

**変更後:**

```go
	moduledata := Linklookup(Ctxt, "runtime.firstmoduledata", 0)
	moduledata.Type = obj.SNOPTRDATA
	// moduledatasize := moduledata.Size // この行が削除された
	moduledata.Size = 0 // シンボルサイズをリセット
	// ... (moduledataの他のフィールドの初期化)
	// The rest of moduledata is zero initialized.
	// When linking an object that does not contain the runtime we are
	// creating the moduledata from scratch and it does not have a
	// compiler-provided size, so read it from the type data.
	moduledatatype := Linkrlookup(Ctxt, "type.runtime.moduledata", 0) // moduledataの型情報をルックアップ
	moduledata.Size = decodetype_size(moduledatatype) // 型情報から実際のサイズを計算
	Symgrow(Ctxt, moduledata, moduledata.Size) // 計算されたサイズでシンボルを成長させる
```

この変更により、`moduledata` のサイズは、コンパイラが提供する値に依存するのではなく、`"type.runtime.moduledata"` という型シンボルから動的に計算されるようになりました。`decodetype_size` 関数は、Goの型システムが持つ情報に基づいて、その型のインスタンスがメモリ上で占める正確なバイト数を返します。これにより、`-linkshared` のような特殊なリンクシナリオでも、`moduledata` が常に正しいサイズで確保され、ランタイムが期待通りに動作することが保証されます。

# [インデックス 27521] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）最適化フェーズにおいて、複数のバイトロードをより大きなロード（例：複数の1バイトロードを1つの4バイトロード）に結合する際の挙動を改善するものです。特に、結合されたロード命令が発行される前に、個々のバイトロードに対するすべての境界チェックが確実に実行されるように、その配置場所を調整します。これにより、最適化によって予期せぬセグメンテーション違反が発生する可能性を防ぎ、Goのメモリ安全性を維持します。

## コミット

```
cmd/compile: place combined loads at the location of the last byte load

a load which combines several others. We do this by issuing the
```

## 変更の背景

Go言語はメモリ安全性を重視しており、スライスや配列へのアクセス時には必ず境界チェック（bounds check）が行われます。Goコンパイラは、パフォーマンス向上のために様々な最適化を行います。その一つに、複数の連続した小さなメモリーロード（例えば、バイト単位のロード）を、より大きな単一のロード命令（例えば、ワード単位やダブルワード単位のロード）に結合する「ロード結合」最適化があります。

しかし、このロード結合最適化には潜在的な問題がありました。個々のバイトロードにはそれぞれ境界チェックが関連付けられていますが、コンパイラがこれらのバイトロードを結合する際に、結合された大きなロード命令を、個々のバイトロードの境界チェックがすべて完了するよりも前の、不適切な位置に配置してしまう可能性があったのです。

このような状況が発生すると、本来であれば境界外アクセスとしてランタイムパニック（`runtime error: index out of range`）が発生すべき場所で、最適化された結合ロードが不正なメモリアクセスを引き起こし、セグメンテーション違反（segmentation fault）などの予期せぬクラッシュにつながる可能性がありました。これはGoのメモリ安全性保証に反する挙動です。

このコミットは、この問題を解決するために、結合ロードを配置する場所をより厳密に制御することを目的としています。具体的には、Issue #15002で報告されたこの種のバグを修正します。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを中間表現であるSSA（Static Single Assignment）フォームに変換して最適化を行います。SSAフォームでは、各変数が一度だけ代入されるという特性があり、これによりデータフロー分析が非常に容易になります。コンパイラはSSAグラフ上で様々な最適化パスを実行し、最終的に機械語コードを生成します。ロード結合や境界チェック除去も、このSSA最適化パスの一部として行われます。

### ロードの結合 (Load Combining)

ロード結合は、メモリから連続したデータを読み込む複数の命令を、より効率的な単一の命令にまとめる最適化手法です。例えば、`byte[0]`, `byte[1]`, `byte[2]`, `byte[3]`を個別に読み込んでシフト・OR演算で32ビット整数を構築するようなコードは、`uint32`を一度に読み込む命令に置き換えられる可能性があります。これにより、メモリアクセスの回数を減らし、CPUのパイプライン効率を向上させることができます。

### 境界チェック (Bounds Checks)

Go言語では、スライスや配列へのアクセスがその範囲内にあることを保証するために、実行時に境界チェックが行われます。例えば、`s[i]`というアクセスがあった場合、`0 <= i < len(s)`が満たされているかどうかが確認されます。このチェックはGoの安全性を保つ上で不可欠ですが、オーバーヘッドを伴うため、コンパイラは可能な限りこれを最適化しようとします。

### 境界チェックの除去 (Bounds Check Elimination - BCE)

Goコンパイラは、静的解析によってインデックスが常に有効な範囲内にあることを証明できる場合、冗長な境界チェックを削除する最適化（BCE）を行います。例えば、ループの条件がインデックスの有効性を保証している場合などです。BCEはプログラムの実行速度を向上させますが、誤った除去はメモリ破壊につながるため、非常に慎重に行われます。

### ドミネーターツリー (Dominator Tree)

ドミネーターツリーは、プログラムの制御フローグラフ（CFG）から構築されるデータ構造です。ある基本ブロックAが基本ブロックBのドミネーターであるとは、AからBへのすべてのパスがAを通過する場合を指します。ドミネーターツリーは、コードの最適化、特に命令の再配置や到達可能性の分析において重要な役割を果たします。このコミットで導入される`mergePoint`関数は、このドミネーター関係を利用して、結合ロードの安全な配置場所を決定します。

### `encoding/binary.LittleEndian`

`encoding/binary`パッケージは、Goのプリミティブ型とバイトシーケンスの間で変換を行うための機能を提供します。特に`LittleEndian`は、リトルエンディアン形式でバイト列を数値に変換する際に使用されます。この変換は、通常、個々のバイトを読み込み、適切なビット数だけシフトし、それらをOR演算で結合するというパターンで行われます。このパターンは、まさにこのコミットが最適化しようとしている「複数のバイトロードを結合する」典型的なケースであり、`AMD64.rules`のコメントにもその旨が記載されています。

## 技術的詳細

### 問題の再確認

従来のGoコンパイラのSSA最適化では、複数の`MOVBload`（1バイトロード）命令を`MOVWload`（2バイトロード）、`MOVLload`（4バイトロード）、`MOVQload`（8バイトロード）といったより大きなロード命令に結合するルールが存在しました。これらのルールは、結合されたロード命令を最初のバイトロード命令が存在するブロック（`@x.Block`）に配置していました。

しかし、この配置戦略では、結合されるすべてのバイトロードに対する境界チェックが、結合ロード命令が発行される前に完了していることが保証されませんでした。特に、複数のバイトロードが異なる基本ブロックに分散している場合や、条件分岐によって一部のバイトロードが実行されない可能性がある場合、結合ロードが実行される時点で、まだチェックされていない境界外アクセスが発生する可能性がありました。これにより、本来パニックで停止すべきプログラムが、セグメンテーション違反でクラッシュするという問題が発生していました。

### `mergePoint`関数の導入による解決

このコミットは、`mergePoint`という新しい関数を導入することでこの問題を解決します。`mergePoint`関数は、結合されるすべてのバイトロード命令のブロックを支配し、かつ、それらのブロックによって支配される最も「遅い」共通のブロック（ドミネーターツリーの葉に近いブロック）を見つけ出すことを目的としています。

`mergePoint`が返すブロックは、結合されるすべてのバイトロード命令が実行されることが保証される（または、それらの境界チェックが完了していることが保証される）最も適切な場所となります。これにより、結合ロード命令が発行される時点では、すべての必要な境界チェックが既に通過していることが保証され、メモリ安全性が維持されます。

### `mergePoint`関数の実装ロジック (`src/cmd/compile/internal/ssa/rewrite.go`)

`mergePoint`関数は、現在の基本ブロック`b`と、結合対象となる複数の`Value`（バイトロード命令）のリスト`a`を受け取ります。

1.  **後方探索**: まず、`b`から制御フローグラフを逆方向に辿ります。この探索は最大100ブロックの距離に制限されています（`d = 100`）。
2.  **最初の発見**: 探索中に、`a`に含まれるいずれかの`Value`のブロックに到達した場合、そのブロックを`r`として記録します。これが、結合ロードの候補となるブロックです。
3.  **すべての支配関係の確認**: `r`が見つかった後も、さらに逆方向に探索を続けます。この際、`a`に含まれるすべての`Value`のブロックが、`r`を支配している（つまり、`r`に到達するすべてのパスがそれらのブロックを通過する）ことを確認します。
4.  **条件分岐の回避**: 探索中に、現在のブロックが複数の先行ブロックを持つ場合（つまり、条件分岐の合流点である場合）、`mergePoint`は`nil`を返します。これは、このような状況では、すべてのバイトロードが実行されることを保証するのが困難であるため、安全のために最適化を適用しないという判断です。
5.  **結果**: `a`に含まれるすべての`Value`のブロックが`r`を支配していることが確認できれば、`r`を返します。そうでなければ、`nil`を返します。

このロジックにより、`mergePoint`は、結合ロードを配置するのに最も安全で、かつドミネーターツリーの葉に近い（つまり、可能な限り遅い）ブロックを特定します。

### `AMD64.rules`の変更

`src/cmd/compile/internal/ssa/gen/AMD64.rules`ファイルでは、ロード結合に関するルールが変更されました。

*   **`@x.Block`から`@mergePoint(...)`への変更**: 結合ロード命令の配置場所を、従来の最初のバイトロードのブロック（`@x.Block`）から、`mergePoint`関数が返すブロック（`@mergePoint(b, x0, x1, ...)`）に変更しました。
*   **`&& mergePoint(...) != nil`条件の追加**: `mergePoint`関数が有効なブロックを返した場合にのみ、ロード結合最適化が適用されるように条件が追加されました。`mergePoint`が`nil`を返した場合（例えば、安全な配置場所が見つからない場合や、探索距離の制限を超えた場合）、この最適化は適用されず、個々のバイトロード命令がそのまま残ります。

これらの変更により、ロード結合最適化は、より厳密な安全性のチェックの下で実行されるようになります。

### `issue15002.go`テストの役割

`test/fixedbugs/issue15002.go`は、このコミットが修正する問題を再現し、その修正が正しく機能することを検証するための新しいテストケースです。

このテストは、`syscall.Mmap`と`syscall.Mprotect`を使用して、特殊なメモリ領域を設定します。
1.  `syscall.Mmap`で2ページ分のメモリを確保します。
2.  `syscall.Mprotect`で2ページ目のメモリをアクセス不可（`PROT_NONE`）に設定します。
3.  1ページ目の最後のバイトにポインタを合わせるようにスライス`x`を作成します。このスライス`x`は長さが1バイトです。

この状態で、`x[0]`はアクセス可能ですが、`x[1]`は境界外アクセスとなり、さらにその先はアクセス不可のメモリページに突入します。

テスト関数（`test16`, `test32`, `test64`など）は、`uint16(x[0]) | uint16(x[1])<<8`のように、複数のバイトを読み込んで結合する操作を行います。

*   **修正前**: 最適化された結合ロードが不適切な位置に配置されると、`x[1]`の境界チェックが実行される前に、`x[0]`と`x[1]`を結合した2バイトロードが発行され、アクセス不可のメモリページにアクセスしようとしてセグメンテーション違反が発生する可能性がありました。
*   **修正後**: `mergePoint`の導入により、結合ロードは`x[1]`の境界チェックが完了した後に配置されるようになります。したがって、`x[1]`へのアクセスが境界外であると判断され、`runtime error: index out of range`というパニックが正しく発生することが期待されます。

このテストは、セグメンテーション違反ではなく、期待されるパニックが発生することを確認することで、このコミットの修正が正しく機能していることを検証します。

## コアとなるコードの解説

### `AMD64.rules`の変更

上記の`AMD64.rules`の変更は、GoコンパイラのSSAバックエンドにおける最適化ルールを定義しています。`ORW`、`ORL`、`ORQ`はそれぞれ、2バイト、4バイト、8バイトのロード結合に対応するルールです。

変更前は、これらのルールは`@x.Block`という記述を使用していました。これは、結合されるバイトロードのうち、最初にマッチした`MOVBload`命令（`x`としてキャプチャされる）が存在する基本ブロックに、結合されたロード命令を配置することを意味していました。

変更後は、`@mergePoint(b,x0,x1,...)`という記述に変わり、さらに`&& mergePoint(b,x0,x1,...) != nil`という条件が追加されています。
*   `x0`, `x1`, ... は、結合される個々の`MOVBload`命令を表すSSA `Value`です。
*   `mergePoint(b,x0,x1,...)`は、新しく追加された`mergePoint`関数を呼び出し、結合ロードを配置すべき安全な基本ブロックを決定します。
*   `&& mergePoint(...) != nil`という条件は、`mergePoint`関数が有効なブロックを返した場合にのみ、この最適化ルールが適用されることを保証します。これにより、安全な配置場所が見つからない場合には、ロード結合は行われず、個々のバイトロードが維持されます。

この変更により、結合ロード命令は、個々のバイトロードの境界チェックがすべて完了していることが保証される、より適切な位置に配置されるようになります。

### `mergePoint`関数の解説

`mergePoint`関数は、`src/cmd/compile/internal/ssa/rewrite.go`に追加されました。この関数の目的は、複数のSSA `Value`（この場合はバイトロード命令）がすべて実行されることが保証される、最も適切な基本ブロックを見つけることです。

1.  **`b *Block`**: 現在の基本ブロック。これは、ロード結合が行われる可能性のあるコンテキストのブロックです。
2.  **`a ...*Value`**: 結合対象となる複数のSSA `Value`（バイトロード命令）の可変長引数リスト。

関数のロジックは以下の通りです。

*   **後方探索の開始**: `b`から開始し、`b.Preds`（先行ブロック）を辿って制御フローグラフを逆方向に探索します。
*   **`d := 100`**: 探索の深さを100ブロックに制限しています。これは、無限ループを防ぎ、非効率な探索を避けるためのヒューリスティックな制限です。
*   **`found`ラベル**: 探索中に、`a`に含まれるいずれかの`Value`のブロックと現在のブロック`b`が一致した場合、`found`ラベルにジャンプします。この時点で、`b`は結合ロードの候補となるブロック`r`として設定されます。
*   **単一の先行ブロック**: `len(b.Preds) > 1`の場合、つまり現在のブロックが複数の先行ブロックを持つ場合（条件分岐の合流点）、`nil`を返します。これは、このような状況では、すべてのバイトロードが実行されることを保証するのが困難であるため、安全のために最適化を適用しないという判断です。
*   **すべての支配関係の確認**: `found`ラベルに到達した後、`r`を候補ブロックとして、さらに逆方向に探索を続けます。このループでは、`na`カウンターを使用して、`a`に含まれるすべての`Value`のブロックが、現在の`b`（`r`の先行ブロック）と一致するかどうかを確認します。
    *   `na == len(a)`となった場合、これは`a`に含まれるすべての`Value`のブロックが`r`を支配していることを意味します。この場合、`r`が安全な配置場所として返されます。
*   **`nil`を返す条件**: 探索距離の制限を超えた場合、または複数の先行ブロックを持つ合流点に遭遇した場合は、`nil`を返します。

この`mergePoint`関数は、ドミネーターツリーの概念を応用し、結合されるすべてのバイトロードが実行されることが保証される、最も「遅い」共通の基本ブロックを特定することで、ロード結合最適化の安全性を大幅に向上させています。

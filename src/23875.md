# [インデックス 23875] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるエラーメッセージの改善に関するものです。具体的には、メソッド式（`Type.Method`）がレシーバなしで呼び出された場合、または引数が不足している場合に、より分かりやすいエラーメッセージを提供するように変更されています。

## 元コミット内容

Goコンパイラにおいて、メソッドがレシーバなしで、または引数不足で呼び出された際に、より適切なエラーメッセージを提供する。特に、`Type.Method(receiver, args...)`という構文でメソッドが呼び出された際に、レシーバや十分な引数が提供されていない場合、従来の「`not enough arguments in call to Type.Method`」というメッセージではなく、「`not enough arguments in call to method expression Type.Method`」という、より分かりやすいエラーメッセージを出力するように修正する。これにより、ユーザーは問題の原因を特定しやすくなる。

この変更はIssue #8385を修正するものである。

## 変更の背景

Go言語では、メソッドは型に関連付けられた関数であり、通常はレシーバ（メソッドが呼び出されるインスタンス）を介して呼び出されます。しかし、Goには「メソッド式（Method Expression）」という機能があり、`Type.Method`という形式でメソッドを関数値として取得し、後からレシーバと引数を渡して呼び出すことができます。

例えば、`T`という型に`M`というメソッドがある場合、通常の呼び出しは`t.M(args)`ですが、メソッド式として`T.M`を取得し、`T.M(t, args)`のように呼び出すことも可能です。

このコミット以前は、メソッド式を誤ってレシーバなしで呼び出したり、引数が不足していたりした場合、コンパイラは一般的な「`not enough arguments in call to ...`」というエラーメッセージを出力していました。このメッセージは、通常の関数呼び出しの引数不足と区別がつきにくく、特にメソッド式に慣れていない開発者にとっては、なぜレシーバが引数として必要とされるのか理解しにくいという問題がありました。

Issue #8385は、このエラーメッセージの分かりにくさを指摘し、メソッド式の場合にはその旨を明示するような、より詳細なエラーメッセージを求めるものでした。この変更は、コンパイラが生成するエラーメッセージの質を向上させ、開発者のデバッグ体験を改善することを目的としています。

## 前提知識の解説

### Go言語のメソッドとレシーバ

Go言語において、メソッドは特定の型に関連付けられた関数です。メソッドは、そのメソッドが操作する値（またはポインタ）である「レシーバ」を伴って定義されます。

```go
type MyType struct {
    value int
}

// MyTypeのメソッド
func (m MyType) GetValue() int {
    return m.value
}

// ポインタレシーバを持つMyTypeのメソッド
func (m *MyType) SetValue(newValue int) {
    m.value = newValue
}
```

メソッドを呼び出す際は、通常、レシーバのインスタンスを通じて行います。

```go
var t MyType
t.SetValue(10) // tがレシーバ
val := t.GetValue() // tがレシーバ
```

### メソッド式 (Method Expression)

Go言語には、メソッドを関数値として扱う「メソッド式」という機能があります。これは、`Type.Method`という形式で記述され、そのメソッドが期待するレシーバを最初の引数として受け取る関数を返します。

例えば、上記の`MyType`の`GetValue`メソッドの場合、メソッド式は`MyType.GetValue`となります。このメソッド式の型は`func(MyType) int`です。呼び出す際は、以下のようにレシーバを明示的に最初の引数として渡します。

```go
var t MyType
t.value = 5

// メソッド式を取得
f := MyType.GetValue
// メソッド式を呼び出す際に、レシーバtを最初の引数として渡す
val := f(t) // valは5
```

ポインタレシーバを持つメソッドの場合も同様です。`(*MyType).SetValue`というメソッド式は`func(*MyType, int)`という型を持ちます。

```go
var t MyType
ptr := &t
setter := (*MyType).SetValue
setter(ptr, 20) // t.valueは20になる
```

この機能は、メソッドを汎用的な関数として扱いたい場合や、高階関数にメソッドを渡したい場合などに有用です。

### Goコンパイラの型チェック (`gc/typecheck.go`)

Goコンパイラの`src/cmd/compile/internal/gc/typecheck.go`ファイルは、Goプログラムの型チェックを担当する部分です。このファイルには、式の型を決定し、型の一貫性を検証し、Go言語の型規則に違反するコードに対してエラーを報告するロジックが含まれています。

`Yyerror`関数は、コンパイラがエラーメッセージを出力するために使用する関数です。型チェック中に問題が検出されると、この関数が呼び出され、適切なエラーメッセージがユーザーに表示されます。

このコミットの変更は、`typecheck.go`内の`Yyerror`呼び出しのロジックを修正し、特定の条件下でより具体的なエラーメッセージを生成するようにしています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの型チェックフェーズにおいて、メソッド式が誤って呼び出されたケースを正確に識別し、それに応じたエラーメッセージを生成することにあります。

変更は`src/cmd/compile/internal/gc/typecheck.go`ファイルの`notenough`ラベルが付いたエラー処理ブロックに集中しています。このブロックは、関数やメソッドの呼び出しにおいて引数が不足している場合に到達します。

元のコードでは、引数不足のエラーは一律に「`not enough arguments in call to %v`」というメッセージで報告されていました。ここで`%v`には呼び出された式（`call`変数）が挿入されます。

新しいコードでは、`call`変数が特定の条件を満たすかどうかをチェックするロジックが追加されています。
具体的には、以下の条件をチェックします。

1.  `call.Op == ONAME`: `call`ノードの操作が`ONAME`（名前付きエンティティ、例えば変数や関数名）であること。
2.  `call.Left != nil`: `call`ノードの左の子ノードが存在すること。
3.  `call.Left.Op == OTYPE`: `call`ノードの左の子ノードの操作が`OTYPE`（型）であること。

これらの条件がすべて真である場合、それは`Type.Method`のようなメソッド式が呼び出されている状況を示唆しています。Goコンパイラは、メソッド式を内部的に`ONAME`ノードとして表現し、その`Left`フィールドにレシーバの型（`OTYPE`ノード）を保持するように変換します。

この条件が満たされた場合、コンパイラは「`not enough arguments in call to method expression %v`」という、より具体的なエラーメッセージを出力します。それ以外の場合は、従来の汎用的なエラーメッセージが使用されます。

この変更により、コンパイラは単なる引数不足ではなく、「メソッド式」の呼び出しにおける引数不足であることを明示的にユーザーに伝えることができるようになります。これは、メソッド式がレシーバを最初の引数として期待するというGo言語の特定のセマンティクスを反映したものであり、エラーの解釈を大幅に容易にします。

また、この変更を検証するための新しいテストファイル`test/fixedbugs/issue8385.go`が追加されています。

```go
// errorcheck

// Copyright 2014 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Issue 8385: provide a more descriptive error when a method expression
// is called without a receiver.

package main

type Fooer interface {
	Foo(i, j int)
}

func f(x int) {
}

type I interface {
	M(int)
}
type T struct{}

func (t T) M(x int) {
}

func g() func(int)

func main() {
	Fooer.Foo(5, 6) // ERROR "not enough arguments in call to method expression Fooer.Foo"

	var i I
	var t *T

	g()()    // ERROR "not enough arguments in call to g()"
	f()      // ERROR "not enough arguments in call to f"
	i.M()    // ERROR "not enough arguments in call to i.M"
	I.M()    // ERROR "not enough arguments in call to method expression I.M"
	t.M()    // ERROR "not enough arguments in call to t.M"
	T.M()    // ERROR "not enough arguments in call to method expression T.M"
	(*T).M() // ERROR "not enough arguments in call to method expression (*T).M"
}
```

## コアとなるコードの解説

`typecheck.go`の変更点では、`call`変数がメソッド式を表す`ONAME`ノードであり、その左の子ノードが型を表す`OTYPE`ノードである場合に、特別なエラーメッセージを出力するように条件分岐が追加されています。

-   `call.Op == ONAME`: これは、`call`が識別子（名前）を表す抽象構文木（AST）ノードであることを意味します。メソッド式`T.M`は、コンパイラの内部表現では`ONAME`として扱われます。
-   `call.Left != nil`: `ONAME`ノードが左の子ノードを持つことを確認します。メソッド式の場合、この左の子ノードはレシーバの型を表します。
-   `call.Left.Op == OTYPE`: 左の子ノードが型を表す`OTYPE`ノードであることを確認します。これにより、`T.M`のような形式のメソッド式であることが特定されます。

これらの条件がすべて満たされると、`Yyerror("not enough arguments in call to method expression %v", call)`が呼び出され、より詳細なエラーメッセージが生成されます。

追加された`test/fixedbugs/issue8385.go`テストファイルは、この変更が正しく機能することを確認します。
このテストファイルには、意図的に引数不足のメソッド式呼び出しが多数含まれており、それぞれに期待されるエラーメッセージが`// ERROR "..."`コメントとして記述されています。

-   `Fooer.Foo(5, 6)`: インターフェース型`Fooer`のメソッド`Foo`をメソッド式として呼び出していますが、レシーバが不足しています。期待されるエラーは「`not enough arguments in call to method expression Fooer.Foo`」です。
-   `I.M()`: インターフェース型`I`のメソッド`M`をメソッド式として呼び出していますが、レシーバと引数が不足しています。期待されるエラーは「`not enough arguments in call to method expression I.M`」です。
-   `T.M()`: 構造体型`T`のメソッド`M`をメソッド式として呼び出していますが、レシーバと引数が不足しています。期待されるエラーは「`not enough arguments in call to method expression T.M`」です。
-   `(*T).M()`: ポインタ型`*T`のメソッド`M`をメソッド式として呼び出していますが、レシーバと引数が不足しています。期待されるエラーは「`not enough arguments in call to method expression (*T).M`」です。

これらのテストケースは、新しいエラーメッセージがメソッド式に対して正しく適用されることを保証します。一方で、`g()()`, `f()`, `i.M()`, `t.M()`のような通常の関数呼び出しやインスタンスメソッド呼び出しの引数不足に対しては、従来の汎用的なエラーメッセージが引き続き出力されることも確認しています。

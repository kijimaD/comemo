## 元コミット内容

```
runtime: Remove write barriers during STW.

The GC assumes that there will be no asynchronous write barriers when
the world is stopped. This keeps the synchronization between write
barriers and the GC simple. However, currently, there are a few places
in runtime code where this assumption does not hold.
The GC stops the world by collecting all Ps, which stops all user Go
code, but small parts of the runtime can run without a P. For example,
the code that releases a P must still deschedule its G onto a runnable
queue before stopping. Similarly, when a G returns from a long-running
syscall, it must run code to reacquire a P.
Currently, this code can contain write barriers. This can lead to the
GC collecting reachable objects if something like the following
sequence of events happens:
1. GC stops the world by collecting all Ps.
2. G #1 returns from a syscall (for example), tries to install a
pointer to object X, and calls greyobject on X.
3. greyobject on G #1 marks X, but does not yet add it to a write
buffer. At this point, X is effectively black, not grey, even though
it may point to white objects.
4. GC reaches X through some other path and calls greyobject on X, but
greyobject does nothing because X is already marked.
5. GC completes.
6. greyobject on G #1 adds X to a work buffer, but it's too late.
7. Objects that were reachable only through X are incorrectly collected.
To fix this, we check the invariant that no asynchronous write
barriers happen when the world is stopped by checking that write
barriers always have a P, and modify all currently known sources of
these writes to disable the write barrier. In all modified cases this
is safe because the object in question will always be reachable via
some other path.

Some of the trace code was turned off, in particular the
code that traces returning from a syscall. The GC assumes
that as far as the heap is concerned the thread is stopped
when it is in a syscall. Upon returning the trace code
must not do any heap writes for the same reasons discussed
above.
```

## 変更の背景

Goのガベージコレクタ（GC）は、Stop-the-World（STW）フェーズ中に非同期のライトバリアが発生しないことを前提として動作します。この前提は、GCとライトバリア間の同期を単純に保つために重要です。しかし、Goランタイムの特定のコードパスでは、この前提が破られるケースが存在しました。

具体的には、GCがSTWを開始し、すべてのP（プロセッサ）を停止してユーザーのGoコードの実行を止めますが、ランタイムの小さな部分（例えば、Pを解放するコードや、長時間実行されるシステムコールからG（ゴルーチン）が戻ってPを再取得するコード）はPなしで実行されることがあります。これらのコードパスがポインタの書き込みを伴う場合、ライトバリアがトリガーされる可能性がありました。

このような状況下でライトバリアが非同期に発生すると、GCが到達可能なオブジェクトを誤って回収してしまうという深刻なバグにつながります。コミットメッセージでは、以下のシナリオが例として挙げられています。

1.  GCがすべてのPを停止してSTWを開始します。
2.  システムコールから戻ったG #1がオブジェクトXへのポインタをインストールしようとし、`greyobject`を呼び出します。
3.  G #1上の`greyobject`はXをマークしますが、まだライトバッファに追加しません。この時点では、Xは実質的にブラック（マーク済み）ですが、まだホワイト（未マーク）のオブジェクトを指している可能性があります。
4.  GCが別のパスを通じてXに到達し、`greyobject`を呼び出しますが、Xは既にマークされているため何も行いません。
5.  GCが完了します。
6.  G #1上の`greyobject`がXをワークバッファに追加しますが、既に手遅れです。
7.  Xを通じてのみ到達可能だったオブジェクトが誤って回収されてしまいます。

この問題は、GCの正確性を損ない、プログラムのクラッシュやデータ破損を引き起こす可能性があるため、修正が必要でした。

## 前提知識の解説

このコミットの理解には、Goランタイムの以下の主要な概念の理解が不可欠です。

### 1. Goのガベージコレクション (GC)

GoのGCは、主に**三色マーキング（Tri-color Marking）**アルゴリズムと**ライトバリア（Write Barrier）**、そして**Stop-the-World (STW)**フェーズを組み合わせて動作します。

*   **三色マーキング**: オブジェクトを以下の3つの色に分類して到達可能性を判断します。
    *   **白 (White)**: GCによってまだ訪問されていないオブジェクト。回収候補。
    *   **灰 (Gray)**: 到達可能と判断されたが、その子（参照しているオブジェクト）がまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: 到達可能と判断され、そのすべての子もスキャン済みのオブジェクト。
    GCはルートオブジェクト（グローバル変数、スタック上の参照など）を灰色にマークすることから始め、灰色オブジェクトの子を灰色にマークし、親を黒にすることで、オブジェクトグラフを走査します。最終的に白のまま残ったオブジェクトは到達不可能と判断され、回収されます。

*   **ライトバリア**: GCがアプリケーションと並行して動作するために不可欠なメカニズムです。アプリケーションがポインタを書き換える（例: 構造体のフィールドにオブジェクトを代入する）際にトリガーされます。GoではYuasaスタイルの挿入ライトバリアを使用しており、新しい参照先がまだ白（未マーク）の場合、ライトバリアはそれを即座に灰色にマークします。これにより、GCが並行マーキング中に新しく到達可能になったオブジェクトを誤って回収してしまうことを防ぎ、「黒オブジェクトが白オブジェクトを指さない」という三色マーキングの不変条件を維持します。

*   **Stop-the-World (STW)**: GoのGCはほとんどが並行処理されますが、それでも短いSTWポーズが必要です。STW中、すべてのゴルーチン（ユーザーアプリケーションコード）は一時停止され、GCは整合性の取れた状態で重要な操作を実行します。STWは主にGCサイクルの開始時（初期マーキング）と終了時（マーク終了）に発生し、ルートオブジェクトのスキャンやライトバリアの有効化/無効化などを行います。これにより、GCがメモリを分析している間にアプリケーションがメモリを変更することによるデータ競合を防ぎます。

### 2. GPMスケジューラモデル

Goランタイムのスケジューラは、**G (Goroutine)**、**P (Processor)**、**M (Machine)**という3つのエンティティで構成されます。

*   **G (Goroutine)**: Goランタイムによって管理される軽量なユーザー空間スレッドです。OSスレッド上に多重化されます。
*   **P (Processor)**: ゴルーチンを実行するための論理プロセッサです。各Pは実行準備ができたゴルーチンのローカルキューを持ちます。Pの数は通常`GOMAXPROCS`によって設定されます。
*   **M (Machine)**: オペレーティングシステムのスレッドです。MはPによって割り当てられたゴルーチンを実行します。

スケジューラは、ゴルーチンの作成、スケジューリング、ブロック、プリエンプションなどを処理し、利用可能なPとMにゴルーチンを効率的に分散させる役割を担います。

### 3. STW中のランタイムコードの実行

STWフェーズ中、ユーザーのGoコードは停止しますが、Goランタイム自体の一部のコードは引き続き実行されることがあります。これは、Pの解放、システムコールからの復帰、スケジューラの内部処理など、ランタイムの整合性を維持するために必要な操作です。これらの操作は、Pが割り当てられていないM上で実行されることがあり、通常のライトバリアのメカニズムが期待通りに機能しない可能性があります。

## 技術的詳細

このコミットの技術的詳細は、STW中の非同期ライトバリアが引き起こすGCの不整合と、それを防ぐためのGoランタイムの変更に焦点を当てています。

### 問題の核心

GCがSTWフェーズに入ると、すべてのPが停止され、ユーザーゴルーチンは実行されなくなります。このとき、GCはヒープの状態が静的であり、オブジェクトグラフが変更されないことを前提とします。しかし、前述の通り、ランタイムの特定のコードパス（特にPを持たないM上で実行されるコード）は、STW中であってもポインタの書き込みを行う可能性がありました。

このような書き込みが発生すると、ライトバリアがトリガーされますが、STW中であるためGCの内部状態と同期が取れていません。コミットメッセージの例で示されたように、ライトバリアがオブジェクトをマークしても、その変更がGCのワークバッファに適切に反映される前にGCが完了してしまうと、そのオブジェクトを通じてのみ到達可能だった他のオブジェクトが誤って回収されてしまいます。これは、GCが「黒オブジェクトが白オブジェクトを指さない」という不変条件を破ることを意味し、メモリ安全性の問題を引き起こします。

### 解決策

このコミットは、以下の2つの主要なアプローチでこの問題を解決します。

1.  **Pの有無によるライトバリアのチェック**:
    `src/runtime/mbarrier.go`の`writebarrierptr_nostore1`関数に、`mp.p == nil`（MにPが割り当てられていない状態）かつGCが有効な場合に、ヒープオブジェクトへのポインタ書き込みが発生したら`throw`（パニック）するチェックを追加しました。これにより、STW中にPなしでライトバリアがトリガーされるという不変条件の違反を検出します。

    ```go
    //go:nosplit
    func writebarrierptr_nostore1(dst *uintptr, src uintptr) {
    	mp := acquirem()
    	if mp.inwb {
    		releasem(mp)
    		return
    	}
    	systemstack(func() {
    		if mp.p == nil && memstats.enablegc && !mp.inwb && inheap(src) {
    			throw("writebarrierptr_nostore1 called with mp.p == nil")
    		}
    		mp.inwb = true
    		gcmarkwb_m(dst, src)
    	})
    	mp.inwb = false
    	releasem(mp)
    }
    ```
    このチェックは、問題のあるコードパスを特定し、修正を強制するためのものです。

2.  **クリティカルセクションでのライトバリアの無効化**:
    STW中にPなしで実行されることがあり、かつポインタ書き込みを伴うランタイムのクリティカルなコードパスにおいて、明示的にライトバリアを無効化するメカニズムを導入しました。これは、`go:nowritebarrier`ディレクティブと、新しい`set*NoWriteBarrier`ヘルパー関数群によって実現されます。

    *   **`go:nowritebarrier`ディレクティブ**:
        関数の定義の前に`//go:nowritebarrier`と記述することで、その関数内のポインタ書き込みに対してコンパイラがライトバリアを生成しないように指示します。これは、その関数がSTW中など、ライトバリアが不要または有害な状況で実行されることを保証する場合にのみ使用されます。

    *   **`set*NoWriteBarrier`ヘルパー関数**:
        `src/runtime/runtime2.go`に以下の関数が追加されました。
        *   `setGNoWriteBarrier(gdst **g, gval *g)`
        *   `setMNoWriteBarrier(mdst **m, mval *m)`
        *   `setPNoWriteBarrier(pdst **p, pval *p)`
        *   `setMcacheNoWriteBarrier(mcachedst **mcache, mcacheval *mcache)`
        これらの関数は、`*(*uintptr)(unsafe.Pointer(dst)) = uintptr(unsafe.Pointer(val))`という形式で、`unsafe.Pointer`と`uintptr`を介してポインタの値を直接書き込みます。これにより、コンパイラがライトバリアを挿入するのを回避します。これらの関数は、書き込まれるオブジェクトがGCによって常に到達可能であることが保証される場合にのみ安全に使用できます。コミットメッセージでは、「オブジェクトが常に別のパスを通じて到達可能であるため、これは安全である」と説明されています。

### 影響を受けるコードパス

コミットメッセージとコード変更から、以下のランタイムコードパスが特に影響を受け、修正されました。

*   **`netpoll.go`**: ネットワークポーリング関連のコードで、ゴルーチンを準備する`netpollready`関数が`go:nowritebarrier`でマークされ、`setGNoWriteBarrier`を使用してゴルーチンポインタの書き込みが行われるようになりました。これは、STW中に実行される可能性があり、ゴルーチンが`allg`リストを通じて常に到達可能であるため安全です。
*   **`proc1.go`**: スケジューラ関連の多くの関数（`newm`, `startm`, `startlockedm`, `acquirep`, `mput`, `mget`, `globrunqput`, `pidleput`, `pidleget`など）が`go:nowritebarrier`でマークされ、`setPNoWriteBarrier`, `setMNoWriteBarrier`, `setGNoWriteBarrier`を使用してポインタ書き込みが行われるようになりました。これらの関数はSTW中に実行されることがあり、P、M、Gオブジェクトがそれぞれ`allp`, `allm`, `allg`リストを通じて常に到達可能であるため、ライトバリアを無効にしても安全です。
*   **`runtime2.go`**: `m`構造体の`mstartfn`フィールドの型が`unsafe.Pointer`から`uintptr`に変更されました。これは、`mstartfn`がヒープに割り当てられない関数ポインタを保持するため、ライトバリアが不要であることを示しています。
*   **トレースコードの無効化**: システムコールからの復帰をトレースする一部のコードが一時的に無効化されました。これは、このコードがヒープ書き込みを行い、STW中のライトバリアの問題を引き起こす可能性があったためです。将来的に、このトレースコードがライトバリアなしで安全に実行できるように再設計される必要があります。

この修正により、GoのGCはSTWフェーズ中も正確に動作し、到達可能なオブジェクトが誤って回収されることがなくなりました。

## コアとなるコードの解説

### `src/runtime/mbarrier.go` の変更

`writebarrierptr_nostore1`関数に、STW中にPが割り当てられていないM上でヒープオブジェクトへのポインタ書き込みが発生した場合にパニックを発生させるチェックが追加されました。

```go
//go:nosplit
func writebarrierptr_nostore1(dst *uintptr, src uintptr) {
	mp := acquirem()
	if mp.inwb {
		releasem(mp)
		return
	}
	systemstack(func() {
		// ここが追加されたチェック
		if mp.p == nil && memstats.enablegc && !mp.inwb && inheap(src) {
			throw("writebarrierptr_nostore1 called with mp.p == nil")
		}
		mp.inwb = true
		gcmarkwb_m(dst, src)
	})
	mp.inwb = false
	releasem(mp)
}
```
この`throw`は、開発者がSTW中にライトバリアが発生する可能性のあるコードパスを特定し、`go:nowritebarrier`ディレクティブや`set*NoWriteBarrier`関数を使って修正することを促すためのものです。

### `src/runtime/runtime2.go` の変更

`set*NoWriteBarrier`ヘルパー関数群が追加されました。これらの関数は、`unsafe.Pointer`と`uintptr`を介してポインタの値を直接書き込むことで、コンパイラによるライトバリアの挿入を回避します。

```go
// ps, ms, gs, and mcache are structures that must be manipulated at a level
// lower than that of the normal Go language. For example the routine that
// stops the world removes the p from the m structure informing the GC that
// this P is stopped and then it moves the g to the global runnable queue.
// If write barriers were allowed to happen at this point not only does
// the GC think the thread is stopped but the underlying structures
// like a p or m are not in a state that is not coherent enough to
// support the write barrier actions.
// This is particularly painful since a partially executed write barrier
// may mark the object but be delinquent in informing the GC that the
// object needs to be scanned.

// setGNoWriteBarriers does *gdst = gval without a write barrier.
func setGNoWriteBarrier(gdst **g, gval *g) {
	*(*uintptr)(unsafe.Pointer(gdst)) = uintptr(unsafe.Pointer(gval))
}

// setMNoWriteBarriers does *mdst = mval without a write barrier.
func setMNoWriteBarrier(mdst **m, mval *m) {
	*(*uintptr)(unsafe.Pointer(mdst)) = uintptr(unsafe.Pointer(mval))
}

// setPNoWriteBarriers does *pdst = pval without a write barrier.
func setPNoWriteBarrier(pdst **p, pval *p) {
	*(*uintptr)(unsafe.Pointer(pdst)) = uintptr(unsafe.Pointer(pval))
}

// setMcacheNoWriteBarriers does *mcachedst = mcacheval without a write barrier.
func setMcacheNoWriteBarrier(mcachedst **mcache, mcacheval *mcache) {
	*(*uintptr)(unsafe.Pointer(mcachedst)) = uintptr(unsafe.Pointer(mcacheval))
}
```
これらの関数は、GCの整合性を損なうことなく、STW中のランタイム内部構造の変更を安全に行うための低レベルなプリミティブを提供します。

### `src/runtime/netpoll.go` および `src/runtime/proc1.go` の変更

これらのファイルでは、STW中に実行される可能性のある関数に`//go:nowritebarrier`ディレクティブが追加され、ポインタの書き込みに`set*NoWriteBarrier`関数が使用されるようになりました。

**例: `src/runtime/netpoll.go` の `netpollready` 関数**

```go
// May run during STW, so write barriers are not allowed.
// Eliminating WB calls using setGNoWriteBarrier are safe since the gs are
// reachable through allg.
//go:nowritebarrier
func netpollready(gpp **g, pd *pollDesc, mode int32) {
	var rg, wg *g
	if mode == 'r' || mode == 'r'+'w' {
		setGNoWriteBarrier(&rg, netpollunblock(pd, 'r', true)) // 変更箇所
	}
	if mode == 'w' || mode == 'r'+'w' {
		setGNoWriteBarrier(&wg, netpollunblock(pd, 'w', true)) // 変更箇所
	}
	if rg != nil {
		setGNoWriteBarrier(&rg.schedlink, *gpp) // 変更箇所
		setGNoWriteBarrier(gpp, rg)             // 変更箇所
	}
	if wg != nil {
		setGNoWriteBarrier(&wg.schedlink, *gpp) // 変更箇所
		setGNoWriteBarrier(gpp, wg)             // 変更箇所
	}
}
```
`netpollready`関数はSTW中に実行される可能性があり、ここで操作される`g`（ゴルーチン）オブジェクトは`allg`リストを通じて常に到達可能であるため、ライトバリアを無効にしても安全です。

**例: `src/runtime/proc1.go` の `newm` 関数**

```go
// Create a new m.  It will start off with a call to fn, or else the scheduler.
// fn needs to be static and not a heap allocated closure.
// May run during STW, so write barriers are not allowed.
//go:nowritebarrier
func newm(fn func(), _p_ *p) {
	mp := allocm(_p_)
	// procresize made _p_ reachable through allp, which doesn't change during GC, so WB can be eliminated
	setPNoWriteBarrier(&mp.nextp, _p_) // 変更箇所
	// Store &fn as a uintptr since it is not heap allocated so the WB can be eliminated
	mp.mstartfn = *(*uintptr)(unsafe.Pointer(&fn)) // 変更箇所 (型も変更)

	if iscgo {
		var ts cgothreadstart
		if _cgo_thread_start == nil {
			throw("_cgo_thread_start missing")
		}
		// mp is reachable via allm and mp.g0 never changes, so WB can be eliminated.
		setGNoWriteBarrier(&ts.g, mp.g0) // 変更箇所
		ts.tls = (*uint64)(unsafe.Pointer(&mp.tls[0]))
		ts.fn = unsafe.Pointer(funcPC(mstart))
		asmcgocall(_cgo_thread_start, unsafe.Pointer(&ts))
	}
	// ...
}
```
`newm`関数もSTW中に実行される可能性があり、`_p_`は`allp`を通じて、`mp`は`allm`を通じて到達可能であるため、`setPNoWriteBarrier`や`setGNoWriteBarrier`の使用は安全です。また、`mstartfn`がヒープに割り当てられない関数ポインタであるため、`uintptr`として直接格納することでライトバリアを回避しています。

これらの変更により、GoランタイムはSTW中のライトバリアの不整合問題を解決し、GCの正確性と安定性を向上させています。

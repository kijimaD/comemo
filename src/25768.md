# [インデックス 25768] ファイルの概要

このコミットは、Go言語の`cgo`ツールにおける動的シンボルテーブルへのエクスポートメカニズムの修正に関するものです。具体的には、`//go:cgo_export_dynamic`ディレクティブが、Goの内部ラッパー関数ではなく、実際にCから呼び出し可能な関数を動的シンボルテーブルに登録するように変更されました。これにより、`cgo`が生成するコードの正確性と堅牢性が向上します。

    cmd/cgo: put the real C function in the dynamic symbol table
    
    In the past, cgo generated Go code and C code.  The C code was linked
    into a shared library.  The Go code was built into an executable that
    dynamically linked against that shared library.  C wrappers were
    exported from the shared library, and the Go code called them.
    
    It was all a long time ago, but in order to permit C code to call back
    into Go, somebody implemented #pragma dynexport (https://golang.org/cl/661043)
    to export a Go symbol into the dynamic symbol table.  Then that same
    person added code to cgo to recognize //export comments
    (https://golang.org/cl/853042).  The //export comments were implemented
    by generating C code, to be compiled by GCC, that would refer to C code,
    to be compiled by 6c, that would call the Go code.  The GCC code would
    go into a shared library.  The code compiled by 6c would be in the Go
    executable.  The GCC code needed to refer to the 6c code, so the 6c
    function was marked with #pragma dynexport.  The important point here is
    that #pragma dynexport was used to expose an internal detail of the
    implementation of an exported function, because at the time it was
    necessary.
    
    Moving forward to today, cgo no longer generates a shared library and 6c
    no longer exists.  It's still true that we have a function compiled by
    GCC that refers to a wrapper function now written in Go.  In the normal
    case today we are doing an external link, and we use a
    //go:cgo_export_static function to make the Go wrapper function visible
    to the C code under a known name.
    
    The #pragma dynexport statement has become a //go:cgo_export_dynamic
    comment on the Go code.  That comment only takes effect when doing
    internal linking.  The comment tells the linker to put the symbol in the
    dynamic symbol table.  That still makes sense for the now unusual case
    of using internal linking with a shared library.
    
    However, all the changes to this code have carefully preserved the
    property that the //go:cgo_export_dynamic comment refers to an internal
    detail of the implementation of an exported function.  That was
    necessary a long time ago, but no longer makes sense.
    
    This CL changes the code to put the actual C-callable function into the
    dynamic symbol table.  I considered dropping the comment entirely, but
    it turns out that there is even a test for this, so I preserved it.

## 元コミット内容

このコミットは、`cmd/cgo`ツールが生成するコードにおいて、Go関数をCから呼び出す際に使用される動的シンボルテーブルへのエクスポート方法を修正するものです。以前は、`//go:cgo_export_dynamic`ディレクティブがGoの内部的なラッパー関数（実装の詳細）を動的シンボルテーブルに登録していましたが、この変更により、実際にCから呼び出し可能な「本物の」関数が登録されるようになります。これは、`cgo`の進化に伴い、過去の設計上の制約が解消されたため、より直接的で正しいエクスポート方法に改められたものです。

## 変更の背景

Go言語の`cgo`は、GoコードとCコードを相互に呼び出すためのメカニズムを提供します。その歴史の中で、Go関数をCから呼び出すためのエクスポート方法は何度か進化してきました。

初期の`cgo`では、GoコードとCコードが生成され、Cコードは共有ライブラリにリンクされ、Goコードはそれを動的にリンクする実行可能ファイルとしてビルドされていました。Cのラッパー関数が共有ライブラリからエクスポートされ、Goコードはそれらを呼び出していました。

CコードからGoコードを呼び出す（コールバック）ことを可能にするために、`#pragma dynexport`というディレクティブが導入されました（`https://golang.org/cl/661043`）。これはGoシンボルを動的シンボルテーブルにエクスポートするものでした。その後、`cgo`は`//export`コメントを認識するようになりました（`https://golang.org/cl/853042`）。`//export`コメントは、GCCでコンパイルされるCコードを生成することで実装され、そのCコードは6c（当時のGoコンパイラ）でコンパイルされるCコードを参照し、最終的にGoコードを呼び出すという複雑な構造でした。このとき、GCCコードが6cコードを参照する必要があったため、6c関数は`#pragma dynexport`でマークされていました。ここで重要なのは、`#pragma dynexport`が、エクスポートされた関数の実装の内部的な詳細を公開するために使用されていたという点です。これは当時の制約上、必要不可欠なものでした。

しかし、時代が進み、`cgo`はもはや共有ライブラリを生成せず、6cコンパイラも存在しません。現在でも、GCCでコンパイルされた関数が、Goで書かれたラッパー関数を参照するという構造は残っています。通常の場合、外部リンキング（external linking）を使用しており、`//go:cgo_export_static`ディレクティブを使ってGoラッパー関数をCコードから既知の名前で可視化しています。

`#pragma dynexport`は、Goコード上の`//go:cgo_export_dynamic`コメントに置き換えられました。このコメントは内部リンキング（internal linking）の場合にのみ有効で、リンカにシンボルを動的シンボルテーブルに配置するよう指示します。これは、共有ライブラリとの内部リンキングという、現在では珍しいケースにおいて依然として意味を持ちます。

これまでのコード変更は、`//go:cgo_export_dynamic`コメントがエクスポートされた関数の実装の内部的な詳細を参照するという特性を慎重に維持してきました。これは過去には必要でしたが、もはや意味をなさなくなっていました。このコミットは、この状況を是正し、実際にCから呼び出し可能な関数を動的シンボルテーブルに配置するように変更します。

## 前提知識の解説

*   **cgo**: Go言語の機能の一つで、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGo言語の関数を呼び出したりするためのインターフェースを提供します。これにより、既存のCライブラリをGoから利用したり、Goの高性能な並行処理機能をCプログラムに組み込んだりすることが可能になります。
*   **動的リンキング (Dynamic Linking)**: プログラムの実行時にライブラリをロードし、リンクする方式です。これにより、複数のプログラムが同じライブラリのコピーを共有でき、ディスクスペースの節約やメモリ効率の向上が図れます。また、ライブラリの更新が容易になります。
*   **静的リンキング (Static Linking)**: プログラムのコンパイル時に必要なライブラリコードをすべて実行可能ファイルに組み込む方式です。これにより、実行可能ファイルは自己完結型となり、外部ライブラリの有無に依存しなくなりますが、ファイルサイズは大きくなります。
*   **動的シンボルテーブル (Dynamic Symbol Table)**: 実行時に動的にリンクされるライブラリや実行可能ファイルが持つシンボル（関数名や変数名など）の情報を格納するテーブルです。リンカやローダーは、このテーブルを参照してシンボル解決を行います。
*   **`//export`コメント**: Goコード内でCから呼び出したいGo関数をマークするために使用されます。`cgo`ツールは、このコメントを解析し、CからGo関数を呼び出すための適切なラッパーコードを生成します。
*   **`//go:cgo_export_dynamic`ディレクティブ**: Goコンパイラ/リンカに対する指示で、指定されたシンボルを動的シンボルテーブルにエクスポートするよう指示します。これは主に、Goプログラムが共有ライブラリとしてビルドされ、他のプログラムからGo関数が動的に呼び出される場合に利用されます。
*   **`//go:cgo_export_static`ディレクティブ**: Goコンパイラ/リンカに対する指示で、指定されたシンボルを静的リンキング時にCコードから可視にするよう指示します。これは、Goプログラムが静的にリンクされる実行可能ファイルとしてビルドされ、CコードがGo関数を呼び出す場合に利用されます。
*   **内部リンキング (Internal Linking)**: Goツールチェーンが、Goのランタイムや標準ライブラリをGoのリンカでリンクする方式。
*   **外部リンキング (External Linking)**: Goツールチェーンが、Goのランタイムや標準ライブラリの一部をCのリンカ（例: `gcc`）でリンクする方式。`cgo`を使用する場合や、特定のプラットフォームで共有ライブラリを生成する場合によく用いられます。

## 技術的詳細

このコミットの核心は、`cgo`がGo関数をCにエクスポートする際の動的シンボルテーブルへの登録方法の「正確性」を改善することにあります。

歴史的に、`cgo`はGo関数をCから呼び出せるようにするために、いくつかのレイヤーのラッパー関数を生成してきました。`//export`でマークされたGo関数は、直接Cから呼び出されるわけではなく、`cgo`が生成するCのラッパー関数を介して呼び出されます。さらに、このCのラッパー関数も、Goの内部的なラッパー関数を呼び出す形になっていました。

問題は、`//go:cgo_export_dynamic`ディレクティブが、この「Goの内部的なラッパー関数」を動的シンボルテーブルに登録していた点です。これは、エクスポートされた関数の「実装の詳細」を外部に公開していることになり、抽象化の原則に反し、将来的な実装変更に対して脆弱でした。コミットメッセージにあるように、これは過去の`cgo`の設計（特に6cコンパイラが存在し、`#pragma dynexport`が使われていた時代）の制約によるものでした。

現在の`cgo`のアーキテクチャでは、Goの内部的なラッパー関数ではなく、Cから直接呼び出し可能な「本物の」C-callable関数（`cgo`が生成するCのラッパー関数）を動的シンボルテーブルに登録することが可能です。この「本物の」C-callable関数は、`exp.ExpName`という名前で参照されます。

この変更により、`//go:cgo_export_dynamic`が指すシンボルが、Goの内部実装の詳細ではなく、Cの呼び出し規約に準拠した安定したインターフェースとなるため、より堅牢で理解しやすいエクスポートメカニズムが実現されます。特に、内部リンキングと共有ライブラリを組み合わせるような、現在では珍しいケースにおいても、正しいシンボルがエクスポートされることが保証されます。

この修正は、`cgo`の進化とクリーンアップの一環であり、過去の技術的負債を解消し、より現代的なGoのリンキングモデルに適合させるものです。

## コアとなるコードの解説

最も重要な変更は`src/cmd/cgo/out.go`ファイルにあります。

```go
-		fmt.Fprintf(fgo2, "//go:cgo_export_dynamic %s\\n", exp.Func.Name.Name)
+		fmt.Fprintf(fgo2, "//go:cgo_export_dynamic %s\\n", exp.ExpName)
```

この変更は、`cgo`がGo関数をCにエクスポートする際に生成する`//go:cgo_export_dynamic`ディレクティブの引数を変更しています。

*   **変更前**: `exp.Func.Name.Name`
    *   これは、`//export`でマークされたGo関数の元の名前、またはGoの内部的なラッパー関数の名前を指していました。コミットメッセージが説明するように、これはエクスポートされた関数の「実装の詳細」を動的シンボルテーブルに公開していました。
*   **変更後**: `exp.ExpName`
    *   `exp.ExpName`は、`cgo`が生成するCから呼び出し可能な「本物の」ラッパー関数の名前を指します。この関数は、Cの呼び出し規約に準拠しており、Goの内部的な詳細を隠蔽します。これにより、動的シンボルテーブルに登録されるシンボルが、C側から期待される安定したインターフェースとなります。

この修正により、`cgo`の生成コードがより抽象化され、Goの内部実装の変更に影響されにくくなります。また、`misc/cgo/test/issue4029.go`と`misc/cgo/test/issue4029.c`のテストケースは、この変更が正しく機能し、CからGo関数へのコールバックが期待通りに動作することを検証するために追加・修正されました。特に、`callbacks`変数のインクリメントと最終的な値の検証は、Go関数がCから複数回正しく呼び出されたことを確認するものです。

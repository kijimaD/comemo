cmd/compile: recognize more memory runs in generated algs

The old implementation assumed that all memory runs
were terminated by non-memory fields.
This isn't necessarily so.
They might be terminated by padding or blank fields.

For example, given

type T struct {
        a int64
        b byte
        c, d, e int64
}

the old implementation did a memory comparison on a+b, on c, and on d+e.

Instead, check for memory runs at the beginning of every round.
This now generates a memory comparison on a+b and on c+d+e.

Also, delete some now-dead code.

## 変更の背景

Goコンパイラは、構造体などの複合型に対して、ハッシュ計算や等値比較を行うためのコードを自動生成します。この生成されるコードの効率は、メモリ上の連続したデータブロック（「メモリラン」）をどれだけ大きく認識できるかに依存します。大きなメモリランを一度に処理できると、個々のフィールドごとに処理するよりも高速になります。

以前の実装では、メモリランが非メモリフィールド（例えば、ポインタやインターフェースなど、単純なバイト列として扱えないフィールド）によってのみ中断されると仮定していました。しかし、実際には構造体のパディング（アライメントのために挿入される未使用バイト）や、Goの言語仕様で特別な意味を持つ「ブランクフィールド」（`_` で宣言されるフィールド）によってもメモリランが中断される可能性がありました。

この誤った仮定により、コンパイラは本来であれば連続したメモリブロックとして扱える部分を、複数の小さなブロックに分割して処理していました。これは、生成されるハッシュ関数や等値比較関数のパフォーマンス低下につながっていました。

このコミットの目的は、このメモリランの認識ロジックを修正し、パディングやブランクフィールドによって中断された場合でも、その後に続くメモリフィールドが連続していれば、それらを新たなメモリランとして認識できるようにすることです。これにより、より大きなメモリランを効率的に処理できるようになり、生成されるコードのパフォーマンスが向上します。

## 前提知識の解説

### Goコンパイラのコード生成

Goコンパイラは、ユーザーが定義した型（特に構造体）に対して、特定の操作（ハッシュ計算、等値比較、ゼロ値設定など）を行うための低レベルな関数を自動的に生成します。これらは「アルゴリズム」（`alg`）と呼ばれ、`runtime` パッケージ内で使用されます。`genhash` と `geneq` は、それぞれハッシュアルゴリズムと等値比較アルゴリズムを生成するコンパイラ内部の関数です。

### 構造体のアライメントとパディング

Goを含む多くのプログラミング言語では、メモリ効率とCPUのアクセス効率のために、データ型が特定のメモリアドレスに配置されるように「アライメント」されます。例えば、`int64` は8バイト境界に、`byte` は1バイト境界に配置されるのが一般的です。

構造体内のフィールドは、その型のアライメント要件を満たすように配置されます。この際、フィールド間に未使用のバイトが挿入されることがあり、これを「パディング」と呼びます。パディングは、構造体のサイズを大きくする可能性がありますが、CPUが効率的にデータにアクセスするために必要です。

例:
```go
type S struct {
    a byte  // 1バイト
    _ [7]byte // パディング (7バイト) - 8バイト境界に合わせるため
    b int64 // 8バイト
}
```
この例では、`a` の後に `b` が続く場合、`b` が8バイト境界に配置されるように `a` の後に7バイトのパディングが挿入されます。

### ブランクフィールド (`_`)

Goでは、フィールド名を `_` とすることで、そのフィールドを「ブランクフィールド」として宣言できます。ブランクフィールドは、メモリを占有しますが、その値にアクセスすることはできません。これは、構造体のアライメントを調整したり、特定のインターフェースを満たすためにフィールドが必要だがその値は使わない、といった場合に利用されます。

### メモリラン (Memory Runs)

Goコンパイラにおける「メモリラン」とは、構造体内で連続してメモリ上に配置され、かつ単純なバイト列として扱えるフィールドのブロックを指します。例えば、`int64` や `byte` のようなプリミティブ型はメモリランの一部となり得ます。ポインタやインターフェースのような型は、その値がメモリ上の別のアドレスを指すため、通常はメモリランを中断します。

コンパイラは、このメモリランを検出することで、`memhash` (メモリブロックのハッシュ計算) や `memequal` (メモリブロックの等値比較) といった最適化されたランタイム関数を呼び出すことができます。これらの関数は、CPUのSIMD命令などを利用して高速に動作するため、個々のフィールドをループで処理するよりもはるかに効率的です。

### `memrun` 関数

`memrun` はGoコンパイラ内部の関数で、与えられた型 `t` とそのフィールド `t1` から開始して、連続するメモリランの最初のフィールド、そのサイズ、そしてメモリランの次のフィールドを返します。この関数が、メモリランの検出ロジックの核心を担っています。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/compile/internal/gc/subr.go` 内の `genhash` 関数と `geneq` 関数における構造体フィールドのイテレーションロジックです。

以前の実装では、`memrun` 関数がメモリランを検出した後、そのメモリランの終端が非メモリフィールドであると仮定していました。しかし、パディングやブランクフィールドもメモリランを中断する要因となり得ます。

新しいアプローチでは、ループの各イテレーションの開始時に `memrun` を呼び出すことで、常に現在のフィールドから可能な限り最大のメモリランを検出するように変更されました。これにより、パディングやブランクフィールドがメモリランを中断しても、その直後のメモリフィールドが新たなメモリランの開始点として正しく認識されるようになります。

具体的には、以下の変更が行われました。

1.  **ループ構造の変更**:
    *   `for t1 := t.Type; ; t1 = t1.Down { ... }` というループが、`t1 := t.Type; for { ... }` に変更されました。これにより、`t1` の更新がループの内部でより柔軟に制御できるようになります。
2.  **ブランクフィールドの処理**:
    *   `isblanksym(t1.Sym)` でブランクフィールドが検出された場合、以前は単に `continue` していましたが、新しいコードでは `t1 = t1.Down` を追加して、次のフィールドに進むように明示的に指示しています。これにより、ブランクフィールドをスキップしつつ、その後のフィールドで新たなメモリランを探索できるようになります。
3.  **メモリラン中断後の処理**:
    *   `algtype1(t1.Type, nil) == AMEM` の条件が追加されました。これは、現在のフィールドがメモリフィールドであるにもかかわらず、`memrun` によってメモリランが中断された場合（つまり、パディングやブランクフィールドが原因で中断された場合）に該当します。この場合、以前は個別のハッシュ/等値比較処理を行っていましたが、新しいコードでは `continue` することで、次のループイテレーションで `memrun` が再度呼び出され、現在のフィールドから始まる新たなメモリランを検出するようにします。これにより、`c, d, e int64` の例で `c+d+e` が一つのメモリランとして扱われるようになります。
4.  **デッドコードの削除**:
    *   上記の変更により、`AMEM` タイプに対する個別のハッシュ/等値比較処理を行うためのコードブロックが不要になったため、削除されました。これはコードの簡素化と保守性の向上に貢献します。

この変更により、コンパイラは構造体のメモリレイアウトをより正確に分析し、より大きな連続したメモリブロックに対して `memhash` や `memequal` のような最適化されたランタイム関数を適用できるようになります。結果として、Goプログラムの実行時パフォーマンス、特にハッシュマップのキー操作や構造体の比較操作において改善が期待されます。

最後に、`t1 = t1.Down` がループの最後に移動しました。これにより、`memrun` が `t1` を更新した後、または `continue` で次のイテレーションに進む前に、`t1` が適切に次のフィールドを指すように保証されます。

## 変更の背景

Goコンパイラは、構造体などの複合型に対して、ハッシュ計算や等値比較を行うためのコードを自動生成します。この生成されるコードの効率は、メモリ上の連続したデータブロック（「メモリラン」）をどれだけ大きく認識できるかに依存します。大きなメモリランを一度に処理できると、個々のフィールドごとに処理するよりも高速になります。

以前の実装では、メモリランが非メモリフィールド（例えば、ポインタやインターフェースなど、単純なバイト列として扱えないフィールド）によってのみ中断されると仮定していました。しかし、実際には構造体のパディング（アライメントのために挿入される未使用バイト）や、Goの言語仕様で特別な意味を持つ「ブランクフィールド」（`_` で宣言されるフィールド）によってもメモリランが中断される可能性がありました。

この誤った仮定により、コンパイラは本来であれば連続したメモリブロックとして扱える部分を、複数の小さなブロックに分割して処理していました。これは、生成されるハッシュ関数や等値比較関数のパフォーマンス低下につながっていました。

このコミットの目的は、このメモリランの認識ロジックを修正し、パディングやブランクフィールドによって中断された場合でも、その後に続くメモリフィールドが連続していれば、それらを新たなメモリランとして認識できるようにすることです。これにより、より大きなメモリランを効率的に処理できるようになり、生成されるコードのパフォーマンスが向上します。

## 前提知識の解説

### Goコンパイラのコード生成

Goコンパイラは、ユーザーが定義した型（特に構造体）に対して、特定の操作（ハッシュ計算、等値比較、ゼロ値設定など）を行うための低レベルな関数を自動的に生成します。これらは「アルゴリズム」（`alg`）と呼ばれ、`runtime` パッケージ内で使用されます。`genhash` と `geneq` は、それぞれハッシュアルゴリズムと等値比較アルゴリズムを生成するコンパイラ内部の関数です。

### 構造体のアライメントとパディング

Goを含む多くのプログラミング言語では、メモリ効率とCPUのアクセス効率のために、データ型が特定のメモリアドレスに配置されるように「アライメント」されます。例えば、`int64` は8バイト境界に、`byte` は1バイト境界に配置されるのが一般的です。

構造体内のフィールドは、その型のアライメント要件を満たすように配置されます。この際、フィールド間に未使用のバイトが挿入されることがあり、これを「パディング」と呼びます。パディングは、構造体のサイズを大きくする可能性がありますが、CPUが効率的にデータにアクセスするために必要です。

例:
```go
type S struct {
    a byte  // 1バイト
    _ [7]byte // パディング (7バイト) - 8バイト境界に合わせるため
    b int64 // 8バイト
}
```
この例では、`a` の後に `b` が続く場合、`b` が8バイト境界に配置されるように `a` の後に7バイトのパディングが挿入されます。

### ブランクフィールド (`_`)

Goでは、フィールド名を `_` とすることで、そのフィールドを「ブランクフィールド」として宣言できます。ブランクフィールドは、メモリを占有しますが、その値にアクセスすることはできません。これは、構造体のアライメントを調整したり、特定のインターフェースを満たすためにフィールドが必要だがその値は使わない、といった場合に利用されます。

### メモリラン (Memory Runs)

Goコンパイラにおける「メモリラン」とは、構造体内で連続してメモリ上に配置され、かつ単純なバイト列として扱えるフィールドのブロックを指します。例えば、`int64` や `byte` のようなプリミティブ型はメモリランの一部となり得ます。ポインタやインターフェースのような型は、その値がメモリ上の別のアドレスを指すため、通常はメモリランを中断します。

コンパイラは、このメモリランを検出することで、`memhash` (メモリブロックのハッシュ計算) や `memequal` (メモリブロックの等値比較) といった最適化されたランタイム関数を呼び出すことができます。これらの関数は、CPUのSIMD命令などを利用して高速に動作するため、個々のフィールドをループで処理するよりもはるかに効率的です。

### `memrun` 関数

`memrun` はGoコンパイラ内部の関数で、与えられた型 `t` とそのフィールド `t1` から開始して、連続するメモリランの最初のフィールド、そのサイズ、そしてメモリランの次のフィールドを返します。この関数が、メモリランの検出ロジックの核心を担っています。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/compile/internal/gc/subr.go` 内の `genhash` 関数と `geneq` 関数における構造体フィールドのイテレーションロジックです。

以前の実装では、`memrun` 関数がメモリランを検出した後、そのメモリランの終端が非メモリフィールドであると仮定していました。しかし、パディングやブランクフィールドもメモリランを中断する要因となり得ます。

新しいアプローチでは、ループの各イテレーションの開始時に `memrun` を呼び出すことで、常に現在のフィールドから可能な限り最大のメモリランを検出するように変更されました。これにより、パディングやブランクフィールドがメモリランを中断しても、その直後のメモリフィールドが新たなメモリランの開始点として正しく認識されるようになります。

具体的には、以下の変更が行われました。

1.  **ループ構造の変更**:
    *   `for t1 := t.Type; ; t1 = t1.Down { ... }` というループが、`t1 := t.Type; for { ... }` に変更されました。これにより、`t1` の更新がループの内部でより柔軟に制御できるようになります。
2.  **ブランクフィールドの処理**:
    *   `isblanksym(t1.Sym)` でブランクフィールドが検出された場合、以前は単に `continue` していましたが、新しいコードでは `t1 = t1.Down` を追加して、次のフィールドに進むように明示的に指示しています。これにより、ブランクフィールドをスキップしつつ、その後のフィールドで新たなメモリランを探索できるようになります。
3.  **メモリラン中断後の処理**:
    *   `algtype1(t1.Type, nil) == AMEM` の条件が追加されました。これは、現在のフィールドがメモリフィールドであるにもかかわらず、`memrun` によってメモリランが中断された場合（つまり、パディングやブランクフィールドが原因で中断された場合）に該当します。この場合、以前は個別のハッシュ/等値比較処理を行っていましたが、新しいコードでは `continue` することで、次のループイテレーションで `memrun` が再度呼び出され、現在のフィールドから始まる新たなメモリランを検出するようにします。これにより、`c, d, e int64` の例で `c+d+e` が一つのメモリランとして扱われるようになります。
4.  **デッドコードの削除**:
    *   上記の変更により、`AMEM` タイプに対する個別のハッシュ/等値比較処理を行うためのコードブロックが不要になったため、削除されました。これはコードの簡素化と保守性の向上に貢献します。

この変更により、コンパイラは構造体のメモリレイアウトをより正確に分析し、より大きな連続したメモリブロックに対して `memhash` や `memequal` のような最適化されたランタイム関数を適用できるようになります。結果として、Goプログラムの実行時パフォーマンス、特にハッシュマップのキー操作や構造体の比較操作において改善が期待されます。

# [インデックス 20472] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9オペレーティングシステム上での`rfork`システムコールに関する競合状態を解決するためのものです。具体的には、スケジューラゴルーチン（g0）のスタック空間をプロセスごとのコピーオンライトスタックセグメントに割り当て、`rfork`をスケジューラスタック上でのみ呼び出すことで、親プロセスと子プロセスの間の競合を解消しています。

## 元コミット内容

```
runtime: call rfork on scheduler stack on Plan 9

A race exists between the parent and child processes after a fork.
The child needs to access the new M pointer passed as an argument
but the parent may have already returned and clobbered it.

Previously, we avoided this by saving the necessary data into
registers before the rfork system call but this isn't guaranteed
to work because Plan 9 makes no promises about the register state
after a system call. Only the 386 kernel seems to save them.
For amd64 and arm, this method won't work.

We eliminate the race by allocating stack space for the scheduler
goroutines (g0) in the per-process copy-on-write stack segment and
by only calling rfork on the scheduler stack.
```

## 変更の背景

この変更は、GoランタイムがPlan 9オペレーティングシステム上でプロセスをフォークする際に発生する特定の競合状態を解決するために導入されました。

Goランタイムは、新しいOSスレッド（M: Machine）を作成する際に、Plan 9の`rfork`システムコールを使用します。`rfork`は、Unix系の`fork`に似ていますが、より細粒度なリソース共有の制御が可能です。GoのMは、OSスレッドに相当し、その上でGoのゴルーチン（G: Goroutine）が実行されます。

問題は、`rfork`呼び出し後に親プロセスと子プロセスの間で発生する競合状態にありました。具体的には、子プロセスが新しいMポインタ（`rfork`の引数として渡される）にアクセスする必要があるにもかかわらず、親プロセスがすでにリターンし、そのポインタが上書きされてしまう可能性がありました。

以前のアプローチでは、`rfork`システムコールを呼び出す前に必要なデータをレジスタに保存することでこの問題を回避しようとしていました。しかし、Plan 9カーネルはシステムコール後にレジスタの状態を保証しないため、この方法は信頼性が低いことが判明しました。特に、386アーキテクチャのカーネルではレジスタが保存されるようでしたが、amd64やARMアーキテクチャではこの方法は機能しませんでした。このため、より堅牢な解決策が必要とされました。

## 前提知識の解説

### Plan 9オペレーティングシステム

Plan 9 from Bell Labsは、Unixの設計思想をさらに推し進めた分散オペレーティングシステムです。その特徴的な設計原則の一つに、「すべてがファイルである」というものがあります。プロセス間通信、デバイスアクセス、ネットワーク通信など、あらゆるリソースがファイルシステムを通じて抽象化されます。

*   **`rfork`システムコール**: Plan 9におけるプロセス作成の主要なシステムコールです。Unixの`fork`とは異なり、`RFPROC` (新しいプロセス空間)、`RFMEM` (新しいメモリ空間)、`RFNOWAIT` (親が子を待たない) など、様々なフラグを組み合わせて、親プロセスと子プロセスの間で共有するリソースを細かく制御できます。このコミットでは、新しいOSスレッドを作成するために`rfork`が使用されています。

### GoランタイムのM, G, Pモデル

Goのランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）という3つの主要な抽象化を使用して並行処理を管理します。

*   **G (Goroutine)**: Goにおける軽量な並行実行単位です。数KB程度のスタックを持ち、Goランタイムによってスケジューリングされます。
*   **P (Processor)**: OSスレッド（M）がGoのコードを実行するために必要なコンテキストを提供します。Pは、実行可能なGのキューを保持し、MがGを実行する際にPをアタッチします。
*   **M (Machine)**: OSスレッドに相当します。MはPを一つ持ち、そのPに紐付けられたGを実行します。Mはシステムコールを実行したり、Cgoコードを実行したりする際に、Pを解放してブロックすることがあります。

### スタックとレジスタ

*   **スタック**: プログラムの実行中に、関数呼び出しの引数、ローカル変数、リターンアドレスなどを一時的に保存するために使用されるメモリ領域です。
*   **レジスタ**: CPU内部にある高速な記憶領域で、現在実行中の命令に必要なデータを保持します。システムコールが呼び出されると、カーネルモードに切り替わり、レジスタの状態が変更される可能性があります。

### コピーオンライト (Copy-on-Write, COW)

コピーオンライトは、リソースを共有する際に、実際に書き込みが発生するまでコピーを作成しない最適化手法です。メモリ管理においてよく使用され、複数のプロセスが同じメモリページを読み取り専用で共有し、いずれかのプロセスがそのページに書き込もうとしたときに初めてそのページのプライベートなコピーが作成されます。これにより、メモリ使用量を削減し、プロセス作成のオーバーヘッドを減らすことができます。

## 技術的詳細

このコミットの技術的解決策は、以下の2つの主要な変更に基づいています。

1.  **スケジューラゴルーチン（g0）のスタック空間の割り当て変更**:
    *   以前は、`runtime.allocm`関数内で、cgoやSolaris、Windowsの場合を除き、`mp->g0 = runtime.malg(8192)`によって8KBのスタックが割り当てられていました。
    *   このコミットでは、Plan 9の場合も`mp->g0 = runtime.malg(-1)`（スタックサイズをOSに任せる）に変更され、`runtime.proc.c`の`runtime·allocm`関数で`Plan9`が`Windows`や`Solaris`と同様に扱われるようになりました。これは、g0のスタックがOSスタック上にレイアウトされることを意味します。
    *   さらに重要なのは、`sys_plan9_386.s`と`sys_plan9_amd64.s`のアセンブリコードで、`runtime·tstart_plan9`関数が導入されたことです。この関数は、新しいMのスケジューラスタックをOSスタック上にレイアウトします。具体的には、現在のスタックポインタ（SP）をg0のスタックの`stack_hi`として設定し、そこから64KBを引いた値を`stack_lo`として設定します。これにより、g0のスタックがプロセスごとのコピーオンライトスタックセグメント内に確保されるようになります。

2.  **`rfork`の呼び出しをスケジューラスタック上でのみ行う**:
    *   以前の`runtime·rfork`関数は、`stk`, `mm`, `gg`, `fn`といった引数を受け取っていました。これらの引数は、新しい子プロセスが使用するスタック、Mポインタ、Gポインタ、そして実行開始関数を直接指定していました。
    *   このコミットでは、`runtime·rfork`のシグネチャが変更され、`flags`のみを受け取るようになりました。これにより、`rfork`システムコール自体は、新しいプロセスを作成するだけで、スタックやM/Gポインタの初期化は行いません。
    *   代わりに、`runtime·tstart_plan9`という新しい関数が導入されました。この関数は、`rfork`によって作成された子プロセス側で実行され、新しいMのg0スタックを初期化し、`runtime·mstart`を呼び出してGoランタイムのスケジューリングを開始します。
    *   この変更により、`rfork`呼び出し時に親プロセスと子プロセスの間でMポインタの競合が発生する可能性がなくなります。なぜなら、Mポインタの初期化は子プロセスが自身のスタック上で安全に行うためです。

これらの変更により、Plan 9カーネルがシステムコール後にレジスタの状態を保証しないという問題が回避され、より堅牢なプロセス作成メカニズムが実現されました。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/os_plan9.c`: `runtime·newosproc`関数が変更され、`rfork`の呼び出し方が簡素化され、`runtime·tstart_plan9`が子プロセス側で呼び出されるようになりました。
*   `src/runtime/os_plan9.go`: `rfork`関数のシグネチャが変更され、`tstart_plan9`関数が追加されました。
*   `src/runtime/os_plan9.h`: `rfork`関数のプロトタイプが変更され、`tstart_plan9`関数のプロトタイプが追加されました。
*   `src/runtime/proc.c`: `runtime·allocm`関数で、Plan 9の場合もg0スタックがOSスタック上にレイアウトされるように変更されました。
*   `src/runtime/runtime.h`: `Plan9`という定数が追加され、Plan 9固有のコンパイルフラグが定義されました。
*   `src/runtime/sys_plan9_386.s`: 386アーキテクチャ向けのアセンブリコードで、`runtime·rfork`の変更と`runtime·tstart_plan9`の実装が含まれます。特に、g0スタックの初期化ロジックが追加されています。
*   `src/runtime/sys_plan9_amd64.s`: AMD64アーキテクチャ向けのアセンブリコードで、386版と同様の変更が加えられています。

## コアとなるコードの解説

### `src/runtime/os_plan9.c` の変更

```c
// 変更前
void
runtime·newosproc(M *mp, void *stk)
{
	mp->tls[0] = mp->id;	// so 386 asm can find it
	if(0){
		runtime·printf("newosproc stk=%p m=%p g=%p rfork=%p id=%d/%d ostk=%p\n",
			stk, mp, mp->g0, runtime·rfork, mp->id, (int32)mp->tls[0], &mp);
	}

	if(runtime·rfork(RFPROC|RFMEM|RFNOWAIT, stk, mp, mp->g0, runtime·mstart) < 0)
		runtime·throw("newosproc: rfork failed");
}

// 変更後
void
runtime·newosproc(M *mp, void *stk)
{
	int32 pid;

	if(0)
		runtime·printf("newosproc mp=%p ostk=%p\n", mp, &mp);

	USED(stk); // stkは使われなくなったが、引数として残っているためUSEDマクロで警告を抑制
	if((pid = runtime·rfork(RFPROC|RFMEM|RFNOWAIT)) < 0) // rforkの引数がflagsのみに
		runtime·throw("newosproc: rfork failed\n");
	if(pid == 0) // 子プロセスの場合
		runtime·tstart_plan9(mp); // 新しい関数を呼び出す
}
```
`runtime·newosproc`は、新しいOSスレッド（M）を作成するGoランタイムの内部関数です。変更前は`rfork`に直接スタック、M、G、開始関数を渡していましたが、変更後は`rfork`は単に新しいプロセスを作成するだけになり、子プロセス側（`pid == 0`）で`runtime·tstart_plan9(mp)`を呼び出すことで、Mの初期化とGoランタイムの開始を遅延させています。これにより、親プロセスがMポインタを上書きする競合がなくなります。

### `src/runtime/os_plan9.go` および `src/runtime/os_plan9.h` の変更

`rfork`のシグネチャが変更され、`tstart_plan9`が追加されています。

```go
// 変更前 (os_plan9.go)
func rfork(flags int32, stk, mm, gg, fn unsafe.Pointer) int32

// 変更後 (os_plan9.go)
func rfork(flags int32) int32
func tstart_plan9(newm *m)
```

これは、C言語のヘッダファイル`os_plan9.h`でも同様に反映されています。

### `src/runtime/proc.c` の変更

```c
// 変更前
	// In case of cgo or Solaris, pthread_create will make us a stack.
	// Windows will layout sched stack on OS stack.
	if(runtime·iscgo || Solaris || Windows)
		mp->g0 = runtime·malg(-1);
	else
		mp->g0 = runtime·malg(8192);

// 変更後
	// In case of cgo or Solaris, pthread_create will make us a stack.
	// Windows and Plan 9 will layout sched stack on OS stack.
	if(runtime·iscgo || Solaris || Windows || Plan9) // Plan9が追加
		mp->g0 = runtime·malg(-1);
	else
		mp->g0 = runtime·malg(8192);
```
`runtime·allocm`関数は新しいMを割り当てます。ここで、`mp->g0`（スケジューラゴルーチンg0）のスタックサイズが決定されます。変更後、Plan 9の場合もスタックサイズをOSに任せる（`runtime·malg(-1)`）ようになり、OSスタック上にg0のスタックがレイアウトされることを示唆しています。

### `src/runtime/sys_plan9_386.s` および `src/runtime/sys_plan9_amd64.s` の変更

これらのアセンブリファイルは、`rfork`システムコールの呼び出しと、新しい`runtime·tstart_plan9`関数の実装を含んでいます。

**`runtime·rfork`の変更 (例: 386)**

```assembly
// 変更前
TEXT runtime·rfork(SB),NOSPLIT,$0
	MOVL	$19, AX // rfork
	MOVL	stack+8(SP), CX
	MOVL	mm+12(SP), BX	// m
	MOVL	gg+16(SP), DX	// g
	MOVL	fn+20(SP), SI	// fn
	INT     $64
    // ... 後続の処理 ...

// 変更後
TEXT runtime·rfork(SB),NOSPLIT,$0
	MOVL	$19, AX
	INT	$64
	MOVL	AX, ret+4(FP) // 戻り値のみを処理
	RET
```
`rfork`システムコール自体は、引数としてスタック、M、G、関数ポインタを受け取らなくなり、単に`rfork`システムコール（番号19）を呼び出すだけになりました。

**`runtime·tstart_plan9`の追加 (例: 386)**

```assembly
TEXT runtime·tstart_plan9(SB),NOSPLIT,$0
	MOVL	newm+0(FP), CX // newm (新しいMポインタ) を取得
	MOVL	m_g0(CX), DX   // newm->g0 を取得

	// Layout new m scheduler stack on os stack.
	MOVL	SP, AX // 現在のスタックポインタをAXに
	MOVL	AX, (g_stack+stack_hi)(DX) // g0のスタックのhiを設定
	SUBL	$(64*1024), AX		// スタックサイズ (64KB) を引く
	MOVL	AX, (g_stack+stack_lo)(DX) // g0のスタックのloを設定
	MOVL	AX, g_stackguard0(DX)
	MOVL	AX, g_stackguard1(DX)

	// Initialize procid from TOS struct.
	MOVL	_tos(SB), AX
	MOVL	48(AX), AX
	MOVL	AX, m_procid(CX)	// save pid as m->procid

	// Finally, initialize g.
	get_tls(BX)
	MOVL	DX, g(BX) // TLSにg0を設定

	CALL	runtime·stackcheck(SB)
	CALL	runtime·mstart(SB) // Goランタイムのスケジューリングを開始
```
この新しい関数は、`rfork`によって作成された子プロセス側で実行されます。ここで、新しいMのg0スタックがOSスタック上にレイアウトされ、`stack_hi`と`stack_lo`が設定されます。これにより、g0のスタックがコピーオンライトセグメント内に適切に配置され、`runtime·mstart`が呼び出されてGoランタイムのスケジューリングが開始されます。

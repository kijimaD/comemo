# [インデックス 25654] ファイルの概要

このコミットは、Goランタイムにおけるスレッドローカルストレージ（TLS）の管理方法に関する改善です。具体的には、Goランタイムが起動時に作成する最初のOSスレッドである `m0` のTLS領域について、これまで独立して存在していた `tls0` というグローバル変数を使用するのをやめ、`m0` 構造体自身が持つ `m.tls` フィールドを利用するように変更しています。これにより、TLSストレージの割り当てと管理が一元化され、コードの簡素化と整合性の向上が図られています。

## 変更の背景

Goランタイムは、プログラムの実行を管理するために独自のスケジューラを持っています。このスケジューラは、Goroutine (G)、論理プロセッサ (P)、OSスレッド (M) という3つの主要な抽象化を使用します。各OSスレッド (M) は、自身の実行コンテキストやGoroutineのスタックポインタなどの重要な情報を保持するために、スレッドローカルストレージ (TLS) を利用します。

Goランタイムが起動する際、最初に `m0` と呼ばれる特別なOSスレッドが作成されます。この `m0` は、他の `M` と同様に、`m` 構造体内に `tls` フィールドを持っていました。しかし、これまでの実装では、`m0` のTLSとして、`m` 構造体内の `tls` フィールドではなく、`tls0` というグローバルな配列が別途用意され、それが使用されていました。

コミットメッセージにある「We're allocating TLS storage for m0 anyway, so might as well use it.」（どうせ `m0` のためにTLSストレージを割り当てているのだから、それを使えばいい）という言葉が示すように、`m0` のために二重にTLS領域が確保されている状態であり、これは冗長でした。このコミットは、この冗長性を排除し、`m0` も他の `M` と同様に `m` 構造体内の `tls` フィールドを使用するように変更することで、コードの整合性を高め、理解を容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と低レベルなシステムプログラミングの知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理する部分で、ガベージコレクション、Goroutineスケジューリング、メモリ管理、システムコールインターフェースなどを担当します。Goプログラムは、OSによって直接実行されるのではなく、Goランタイム上で動作します。

2.  **Goroutine (G)**:
    Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のGoroutineを同時に実行できます。GoroutineはGoランタイムによってスケジューリングされます。

3.  **Logical Processor (P)**:
    Goroutineを実行するためのコンテキスト（実行キュー、スケジューラの状態など）を表します。Goランタイムは、利用可能なOSスレッド (M) の数に応じてPの数を調整し、GをPに割り当てて実行します。

4.  **Machine (M) / OSスレッド**:
    OSによって管理される実際の実行スレッドです。Goランタイムは、Pに割り当てられたGを実行するためにMをOSスレッドにマッピングします。Mは、Gの実行に必要なスタックやレジスタの状態を保持します。

5.  **TLS (Thread Local Storage)**:
    スレッドローカルストレージは、各OSスレッド（M）が自身固有のデータを格納するためのメモリ領域です。これにより、グローバル変数を使用せずにスレッド間で独立した状態を維持できます。Goランタイムでは、現在のGoroutineのポインタ (`g`) やMのポインタ (`m`) などの重要な情報がTLSに格納され、アセンブリコードから高速にアクセスされます。

6.  **`m0`**:
    Goプログラムが起動する際に、Goランタイムによって最初に作成される特別なOSスレッド（M）です。この `m0` は、ランタイムの初期化処理や、他のMの起動などを担当します。

7.  **`tls0`**:
    このコミット以前に存在した、`m0` のTLSとして使用されていたグローバルな `uintptr` 配列です。`m0` のTLS領域を指すために使われていました。

8.  **`m.tls`**:
    `m` 構造体（GoランタイムにおけるOSスレッドの表現）内に定義されているTLS領域です。他のすべての `M` はこの `m.tls` を使用して自身のスレッドローカルデータを管理します。

9.  **アセンブリコード (`.s`ファイル)**:
    Goランタイムの低レベルな部分、特にOSとのインターフェースやパフォーマンスが重要な部分（例: スケジューラのコンテキストスイッチ、TLSのセットアップ）は、Goのアセンブリ言語で記述されています。これは、特定のCPUアーキテクチャ（例: x86, AMD64, ARM）に依存する処理を直接制御するためです。

10. **`SB` (Static Base)**:
    Goアセンブリにおける特別な擬似レジスタで、静的（グローバル）なデータセグメントのベースアドレスを表します。`runtime·tls0(SB)` のように記述することで、グローバル変数 `tls0` のアドレスを参照します。

11. **`LEAQ` / `LEAL` (Load Effective Address)**:
    アセンブリ命令で、オペランドのアドレスを計算し、その結果をレジスタに格納します。`LEAQ` は64ビット、`LEAL` は32ビットのアドレスを扱います。データそのものではなく、そのアドレスが必要な場合に使用されます。

12. **`MOVL` / `MOVQ` (Move Long/Quad)**:
    アセンブリ命令で、データをレジスタまたはメモリ間で移動させます。`MOVL` は32ビット（Long Word）、`MOVQ` は64ビット（Quad Word）のデータを扱います。

## 技術的詳細

このコミットの核心は、`m0` のTLS管理を `runtime·tls0(SB)` から `runtime·m0+m_tls(SB)` へと移行することです。

以前のGoランタイムでは、`m0` のTLSは `runtime/runtime.go` で定義されたグローバル変数 `tls0` を使用していました。しかし、`m` 構造体自体にも `tls` フィールドが存在するため、`m0` のTLSを管理する方法が二重になっていました。この二重管理は、コードの複雑性を増し、将来的なメンテナンスの負担となる可能性がありました。

この変更により、`m0` も他の `M` と同様に、自身の `m` 構造体内の `tls` フィールドを使用するようになります。これにより、TLSの初期化、アクセス、および管理ロジックが `m` 構造体を中心に一元化され、ランタイムコード全体の整合性が向上します。

具体的な変更は、主にアセンブリコード (`.s` ファイル) と `runtime/runtime.go`、`runtime/os1_windows.go` に見られます。アセンブリコードでは、`tls0` のアドレスを参照していた箇所が `m0` 構造体内の `m_tls` フィールドのアドレスを参照するように変更されています。例えば、`LEAQ runtime·tls0(SB)` は `LEAQ runtime·m0+m_tls(SB)` に置き換えられています。これは、TLS領域の物理的な場所が、グローバルな `tls0` から `m0` インスタンスのメモリ領域内の `tls` フィールドへと変更されたことを意味します。

`runtime/os1_windows.go` では、`profilem` 関数内で `m0` の場合に `tls0` を特別に参照していたロジックが削除されています。これは、`m0` も通常の `m` と同じ `mp.tls` を使うようになったため、特別な処理が不要になったことを示しています。

`runtime/runtime.go` からは、`tls0` グローバル変数の宣言自体が削除されています。これは、`tls0` がもはや不要になったことを明確に示しています。

この変更は、Goランタイムの内部構造のクリーンアップであり、直接的なパフォーマンスへの影響は小さいと考えられますが、コードの可読性と保守性を向上させる重要な改善です。

## コアとなるコードの解説

### アセンブリコードの変更 (`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `rt0_linux_ppc64le.s`)

これらのファイルでは、TLS領域のアドレスをロードする命令が変更されています。

-   **変更前**: `LEAQ runtime·tls0(SB)` または `MOVL runtime·tls0(SB), AX`
    これは、グローバル変数 `tls0` のアドレス（またはその内容）をレジスタにロードしていました。`SB` は静的ベースレジスタを意味し、`runtime·tls0(SB)` は `runtime` パッケージ内の `tls0` というグローバルシンボルを参照しています。

-   **変更後**: `LEAQ runtime·m0+m_tls(SB)` または `MOVL runtime·m0+m_tls(SB), AX`
    これは、`runtime` パッケージ内の `m0` というグローバル変数（`m` 構造体のインスタンス）のアドレスに、`m_tls` フィールドのオフセットを加えたアドレス（またはその内容）をレジスタにロードしています。つまり、`m0` 構造体内の `tls` フィールドを直接参照するように変更されています。

この変更により、`m0` のTLS領域が、独立したグローバル変数 `tls0` ではなく、`m0` 構造体の一部として扱われるようになります。

### `src/runtime/os1_windows.go` の変更

`profilem` 関数内の条件分岐が削除されています。

-   **変更前**:
    ```go
    tls := &mp.tls[0]
    if mp == &m0 {
        tls = &tls0[0]
    }
    ```
    このコードは、現在の `m` (`mp`) が `m0` である場合に、`mp.tls` ではなく `tls0` を使用するように特別に処理していました。

-   **変更後**:
    ```go
    tls := &mp.tls[0]
    ```
    `m0` も他の `m` と同様に `mp.tls` を使用するようになったため、この特別な条件分岐は不要になり、削除されました。これにより、コードが簡素化され、`m0` のTLSアクセスが他の `m` と一貫するようになりました。

### `src/runtime/runtime.go` の変更

`tls0` グローバル変数の宣言が削除されています。

-   **変更前**:
    ```go
    var tls0 [8]uintptr // available storage for m0's TLS; not necessarily used; opaque to GC
    ```
    この行は、`m0` のTLSとして使用される `tls0` という `uintptr` の配列を宣言していました。

-   **変更後**:
    この宣言が完全に削除されました。これは、`tls0` がもはやGoランタイムのどこからも参照されなくなり、不要になったことを意味します。

これらの変更は、Goランタイムの内部的なクリーンアップと整合性の向上を目的としており、`m0` のTLS管理をより論理的で一貫性のあるものにしています。

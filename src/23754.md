## 変更の背景

このコミットは、Goコンパイラが従来のAST（Abstract Syntax Tree）ベースの最適化から、より高度なSSA（Static Single Assignment）形式に基づく最適化へと移行する「dev.ssa」ブランチの一部として行われました。SSA形式は、変数の定義と使用を明確に分離することで、より強力なデータフロー解析と最適化を可能にします。

関数呼び出しは、プログラムの実行フローにおいて非常に重要な要素であり、特にGo言語ではクロージャ（関数リテラル）が頻繁に使用されます。SSAバックエンドがこれらの呼び出しを正確に表現し、最適化できるようにするためには、専用のSSAオペコードが必要でした。

従来のコンパイラでは、関数呼び出しはASTノードとして表現されていましたが、SSA形式では、呼び出し自体もSSA値として扱われ、その副作用（メモリの変更など）もSSAの枠組みの中で管理される必要があります。このコミットは、このギャップを埋め、SSAバックエンドが関数呼び出し、特に動的なクロージャ呼び出しを適切に処理できるようにするための基盤を構築しました。

また、どの変数がSSA形式に変換可能であるかを正確に判定するロジックも重要です。SSAは、変数が一度だけ代入されることを前提とするため、アドレスが取られている変数（ポインタとして扱われる可能性がある変数）やヒープに割り当てられる変数、外部変数などはSSA形式に直接変換できません。このコミットでは、`ssa.go`内のSSA変換可能な変数判定ロジックが再編成され、より明確かつ正確な判定が行われるようになりました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。

例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

SSA形式では、変数の各代入が新しい「バージョン」の変数を生成します。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

これにより、`x`のどの定義が`x + 2`や`x * 3`で使用されているかが明確になります。

### 2. Goコンパイラの構造 (`gc` と `ssa` パッケージ)

Goコンパイラ（`gc`）は、複数のステージで構成されています。
*   **フロントエンド**: ソースコードの字句解析、構文解析、AST構築、型チェックなどを行います。
*   **ミドルエンド**: AST上で一部の最適化（インライン化など）を行います。
*   **バックエンド**: ASTを中間表現に変換し、最適化を行い、最終的に機械語を生成します。

このコミットが関連する`cmd/compile/internal/gc`パッケージは、Goコンパイラの主要部分であり、`cmd/compile/internal/ssa`パッケージは、SSA形式への変換とSSAベースの最適化を担当する新しいバックエンドです。

### 3. 関数呼び出しの種類 (静的呼び出しとクロージャ呼び出し)

Go言語における関数呼び出しは、大きく分けて2種類あります。
*   **静的呼び出し (Static Call)**: コンパイル時に呼び出す関数が確定している場合です。例えば、`fmt.Println("hello")`のように、パッケージ内の特定の関数を直接呼び出す場合です。この場合、呼び出し先のアドレスはコンパイル時に決定できます。
*   **クロージャ呼び出し (Closure Call)**: 実行時に呼び出す関数が決定される場合です。Goのクロージャは、周囲の環境（レキシカルスコープ）の変数をキャプチャする関数リテラルです。クロージャは、関数ポインタとキャプチャされた環境（コンテキスト）を保持する構造体として実装されることが多く、呼び出し時にはこの構造体から実際の関数アドレスと環境を取り出して実行します。

### 4. ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタが正確に動作するために、ポインタの書き込み操作を監視するメカニズムです。Goのコンカレントガベージコレクタでは、ヒープ上のオブジェクトへのポインタが変更される際に、ガベージコレクタにその変更を通知する必要があります。これにより、ガベージコレクタはオブジェクトグラフの整合性を保ちながら、並行してマークフェーズを実行できます。`OASWB`（Assign Write Barrier）は、ライトバリアを伴う代入操作を表すASTオペコードです。

### 5. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要な最適化フェーズの一つです。プログラム中の変数をCPUのレジスタに割り当てることで、メモリへのアクセスを減らし、実行速度を向上させます。SSA形式は、変数のライフタイムが明確になるため、レジスタ割り当てを効率的に行うのに役立ちます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の点に集約されます。

### 1. 関数呼び出しのSSAオペコード導入

*   **`genericOps.go` と `opGen.go`**:
    *   `ClosureCall` と `StaticCall` という新しい汎用SSAオペコードが導入されました。
    *   `ClosureCall`: クロージャを介した関数呼び出しを表します。引数としてコードポインタ、コンテキストポインタ、メモリを受け取り、メモリを返します。
    *   `StaticCall`: 静的な関数呼び出しを表します。引数として呼び出す関数のシンボルとメモリを受け取り、メモリを返します。
    *   以前の`Call`オペコードは`ClosureCall`に名称変更され、より具体的な意味を持つようになりました。
*   **`AMD64Ops.go`**:
    *   AMD64アーキテクチャ固有のオペコードとして `OpAMD64CALLstatic` と `OpAMD64CALLclosure` が追加されました。これらは、汎用的な`StaticCall`および`ClosureCall`オペコードがAMD64の機械語命令に変換される際に使用されます。
    *   `CALLclosure`オペコードには、レジスタクローバー情報（呼び出しによって破壊される可能性のあるレジスタ）が設定される予定であることがコメントで示唆されています（`//TODO: set register clobber to everything?`）。

### 2. `ssa.go` における関数呼び出しのSSA変換ロジック

`ssa.go`の`expr`メソッド内の`OCALLFUNC`ケースが大幅に修正されました。
*   **静的呼び出しとクロージャ呼び出しの区別**: `n.Left.Op == ONAME && n.Left.Class == PFUNC`という条件で、呼び出しが静的な関数（`static`）であるか、クロージャを介した動的な呼び出しであるかを判定します。
*   **クロージャの評価**: `static`でない場合（クロージャ呼び出しの場合）、`n.Left`（クロージャを表す式）を評価して、クロージャのSSA値を取得します。
*   **`OpStaticCall` と `OpClosureCall` の生成**:
    *   静的呼び出しの場合、`s.newValue1(ssa.OpStaticCall, ssa.TypeMem, n.Left.Sym, s.mem())` を使用して `OpStaticCall` オペコードを生成します。`n.Left.Sym`は呼び出す関数のシンボルです。
    *   クロージャ呼び出しの場合、まずクロージャのSSA値から関数エントリポイント（コードポインタ）をロードし（`s.newValue2(ssa.OpLoad, s.config.Uintptr, nil, closure, s.mem())`）、その後 `s.newValue3(ssa.OpClosureCall, ssa.TypeMem, nil, entry, closure, s.mem())` を使用して `OpClosureCall` オペコードを生成します。
*   **ブロックの種類の変更**: 関数呼び出しを含むブロックの`Kind`が`ssa.BlockCall`に設定され、`Control`フィールドに生成された`call`オペコードが割り当てられます。これは、SSAバックエンドが呼び出しブロックを特別に扱い、呼び出し後のメモリ状態などを適切に管理するために重要です。

### 3. SSA変換可能な変数判定ロジックの再編成 (`canSSA`関数)

`ssa.go`に`canSSA`という新しいヘルパー関数が導入されました。この関数は、与えられた`ONAME`ノード（変数）がSSA形式に変換可能かどうかを判定します。
*   **判定条件**:
    *   `n.Addrtaken`: 変数のアドレスが取られている場合（ポインタとして扱われる可能性がある場合）、SSA化できません。
    *   `n.Class&PHEAP != 0`: 変数がヒープに割り当てられている場合、SSA化できません。
    *   `n.Class == PEXTERN`: 外部変数（グローバル変数など）はSSA化できません。
    *   `n.Class == PPARAMOUT`: 戻り値パラメータはSSA化できません。
*   この`canSSA`関数は、`OAS`（代入）および`ONAME`（変数参照）の処理において、変数をSSA化するか、それともメモリへのストア/ロードとして扱うかを決定するために使用されます。これにより、SSA変換ロジックがより明確になり、保守性が向上しました。

### 4. AMD64リライトルール (`AMD64.rules` と `rewriteAMD64.go`)

*   **`AMD64.rules`**: 汎用的な`StaticCall`および`ClosureCall`オペコードを、AMD64アーキテクチャ固有の`CALLstatic`および`CALLclosure`オペコードに変換するためのリライトルールが追加されました。
    *   `(StaticCall [target] mem) -> (CALLstatic [target] mem)`
    *   `(ClosureCall entry closure mem) -> (CALLclosure entry closure mem)`
*   **`rewriteAMD64.go`**: 上記のリライトルールに対応するGoコードが生成され、SSA値のオペコードをAMD64固有の呼び出しオペコードに変換するロジックが実装されました。

### 5. ライトバリアの考慮

`ssa.go`の`OAS`（代入）処理において、`OASWB`（ライトバリア付き代入）が追加されました。これは、ガベージコレクタのライトバリアをSSAバックエンドで適切に処理するための準備です。コミットメッセージの`TODO: do write barrier`というコメントから、この時点ではまだ完全な実装ではないものの、将来的な対応を見越した変更であることがわかります。

`src/cmd/compile/internal/ssa/TODO`ファイルが更新され、ライトバリアのサポートや、関数呼び出しがすべてのレジスタをクローバー（破壊）することの考慮など、今後の課題が追記されました。

### `ssa.go` の `stmt` メソッドにおける代入処理の変更

```go
	case OAS, OASWB:
		// ... (値の評価) ...
		if n.Left.Op == ONAME && canSSA(n.Left) {
			// Update variable assignment.
			s.vars[n.Left.Sym.Name] = val
			return
		}
		// not ssa-able.  Treat as a store.
		addr := s.addr(n.Left)
		s.vars[".mem"] = s.newValue3(ssa.OpStore, ssa.TypeMem, nil, addr, val, s.mem())
```
この部分では、代入文（`OAS`または`OASWB`）がSSA形式に変換される際のロジックが示されています。
*   まず、代入される値（`val`）が評価されます。
*   次に、代入先の変数（`n.Left`）が`ONAME`（通常の変数）であり、かつ新しく導入された`canSSA`関数によってSSA化可能であると判定された場合、その変数はSSA形式で管理されます。具体的には、`s.vars`マップ（SSA変換中の変数の現在のSSA値を保持）が更新され、変数の名前と新しいSSA値が関連付けられます。
*   `canSSA`が`false`を返した場合、その変数はSSA化できないと判断されます。この場合、代入はメモリへのストア操作として扱われます。`s.addr(n.Left)`で変数のメモリアドレスが取得され、`ssa.OpStore`オペコードを使用してメモリへの書き込みが表現されます。`s.vars[".mem"]`は、メモリの状態を表す特別なSSA値で、メモリへの変更を追跡するために使用されます。

### `ssa.go` の `expr` メソッドにおける `ONAME` 処理の変更

```go

変数を参照する`ONAME`ノードの処理です。
*   `n.Class == PFUNC`の場合、それは関数名自体を参照していることを意味します。この場合、その関数のクロージャ（実体）のアドレスを指す`OpGlobal`オペコードが生成されます。これは、関数がSSA形式で値として扱われるための準備です。
*   `canSSA(n)`が`true`の場合、その変数はSSA化可能であるため、`s.variable`メソッドを通じてその変数の現在のSSA値が取得されます。
*   `canSSA(n)`が`false`の場合、変数はSSA化できないため、その変数のメモリアドレスを`s.addr(n)`で取得し、`ssa.OpLoad`オペコードを使用してメモリから値をロードする操作として表現されます。

### `ssa.go` の `expr` メソッドにおける `OCALLFUNC` 処理の変更

```go
	case OCALLFUNC:
		static := n.Left.Op == ONAME && n.Left.Class == PFUNC

		// evaluate closure
		var closure *ssa.Value
		if !static {
			closure = s.expr(n.Left)
		}

		// run all argument assignments
		s.stmtList(n.List)

		bNext := s.f.NewBlock(ssa.BlockPlain)
		var call *ssa.Value
		if static {
			call = s.newValue1(ssa.OpStaticCall, ssa.TypeMem, n.Left.Sym, s.mem())
		} else {
			entry := s.newValue2(ssa.OpLoad, s.config.Uintptr, nil, closure, s.mem())
			call = s.newValue3(ssa.OpClosureCall, ssa.TypeMem, nil, entry, closure, s.mem())
		}
		b := s.endBlock()
		b.Kind = ssa.BlockCall
		b.Control = call
		s.startBlock(bNext)
		s.vars[".mem"] = call
```
関数呼び出し（`OCALLFUNC`）をSSA形式に変換する最も重要な部分です。
*   `static`変数は、呼び出しが静的な関数呼び出しであるか（`n.Left`が`PFUNC`クラスの`ONAME`であるか）を判定します。
*   `!static`の場合、つまりクロージャ呼び出しの場合、`n.Left`（クロージャを表す式）を`s.expr(n.Left)`で評価し、クロージャのSSA値を取得します。
*   引数の代入（`n.List`）は、`s.stmtList(n.List)`で処理されます。これは、呼び出し前に引数がスタックなどに配置されることを意味します。
*   新しいSSAブロック`bNext`が作成されます。
*   `static`の判定結果に基づいて、`OpStaticCall`または`OpClosureCall`オペコードが生成されます。
    *   `OpStaticCall`は、呼び出す関数のシンボル（`n.Left.Sym`）を補助情報として持ちます。
    *   `OpClosureCall`は、クロージャのSSA値からロードされたエントリポイント（コードポインタ）と、クロージャ自体のSSA値を引数として持ちます。
*   現在のSSAブロック`b`は`s.endBlock()`で閉じられ、その`Kind`が`ssa.BlockCall`に設定されます。これは、このブロックが関数呼び出しを含む特別なブロックであることを示します。`b.Control`には生成された`call`オペコードが設定され、この呼び出しがブロックの制御フローを決定することを示します。
*   `s.startBlock(bNext)`で新しいブロックが開始され、呼び出し後の処理が続行されます。
*   `s.vars[".mem"] = call`は、関数呼び出しがメモリの状態を変更する可能性があるため、呼び出しの結果として新しいメモリの状態が生成されることを示します。

### `ssa.go` の `canSSA` 関数

```go
func canSSA(n *Node) bool {
	if n.Op != ONAME {
		log.Fatalf("canSSA passed a non-ONAME %s %v", Oconv(int(n.Op), 0), n)
	}
	if n.Addrtaken {
		return false
	}
	if n.Class&PHEAP != 0 {
		return false
	}
	if n.Class == PEXTERN {
		return false
	}
	if n.Class == PPARAMOUT {
		return false
	}
	return true
	// TODO: try to make more variables SSAable.
}
```
この関数は、GoコンパイラのASTノード`n`がSSA形式に変換可能かどうかを判定します。
*   `n.Op != ONAME`: `canSSA`は変数（`ONAME`）に対してのみ意味があるため、それ以外のオペコードの場合はエラーとなります。
*   `n.Addrtaken`: 変数のアドレスが取られている場合（`&var`のような操作が行われている場合）、その変数はメモリ上で直接操作される可能性があり、SSAの「一度だけ代入」という原則に反するため、SSA化できません。
*   `n.Class&PHEAP != 0`: 変数がヒープに割り当てられている場合、複数のゴルーチンからアクセスされる可能性があり、SSAのローカルな性質と合わないため、SSA化できません。
*   `n.Class == PEXTERN`: 外部変数（グローバル変数など）は、プログラム全体からアクセスされ、SSAのスコープ外で変更される可能性があるため、SSA化できません。
*   `n.Class == PPARAMOUT`: 戻り値パラメータは、関数呼び出しのセマンティクス上、特別な扱いが必要であり、直接SSA化するのには適さない場合があります。

これらの条件をすべて満たさない場合、変数はSSA化可能であると判断されます。

## 変更の背景

このコミットは、Goコンパイラが従来のAST（Abstract Syntax Tree）ベースの最適化から、より高度なSSA（Static Single Assignment）形式に基づく最適化へと移行する「dev.ssa」ブランチの一部として行われました。SSA形式は、変数の定義と使用を明確に分離することで、より強力なデータフロー解析と最適化を可能にします。

関数呼び出しは、プログラムの実行フローにおいて非常に重要な要素であり、特にGo言語ではクロージャ（関数リテラル）が頻繁に使用されます。SSAバックエンドがこれらの呼び出しを正確に表現し、最適化できるようにするためには、専用のSSAオペコードが必要でした。

従来のコンパイラでは、関数呼び出しはASTノードとして表現されていましたが、SSA形式では、呼び出し自体もSSA値として扱われ、その副作用（メモリの変更など）もSSAの枠組みの中で管理される必要があります。このコミットは、このギャップを埋め、SSAバックエンドが関数呼び出し、特に動的なクロージャ呼び出しを適切に処理できるようにするための基盤を構築しました。

また、どの変数がSSA形式に変換可能であるかを正確に判定するロジックも重要です。SSAは、変数が一度だけ代入されることを前提とするため、アドレスが取られている変数（ポインタとして扱われる可能性がある変数）やヒープに割り当てられる変数、外部変数などはSSA形式に直接変換できません。このコミットでは、`ssa.go`内のSSA変換可能な変数判定ロジックが再編成され、より明確かつ正確な判定が行われるようになりました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。

例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

SSA形式では、変数の各代入が新しい「バージョン」の変数を生成します。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

これにより、`x`のどの定義が`x + 2`や`x * 3`で使用されているかが明確になります。

### 2. Goコンパイラの構造 (`gc` と `ssa` パッケージ)

Goコンパイラ（`gc`）は、複数のステージで構成されています。
*   **フロントエンド**: ソースコードの字句解析、構文解析、AST構築、型チェックなどを行います。
*   **ミドルエンド**: AST上で一部の最適化（インライン化など）を行います。
*   **バックエンド**: ASTを中間表現に変換し、最適化を行い、最終的に機械語を生成します。

このコミットが関連する`cmd/compile/internal/gc`パッケージは、Goコンパイラの主要部分であり、`cmd/compile/internal/ssa`パッケージは、SSA形式への変換とSSAベースの最適化を担当する新しいバックエンドです。

### 3. 関数呼び出しの種類 (静的呼び出しとクロージャ呼び出し)

Go言語における関数呼び出しは、大きく分けて2種類あります。
*   **静的呼び出し (Static Call)**: コンパイル時に呼び出す関数が確定している場合です。例えば、`fmt.Println("hello")`のように、パッケージ内の特定の関数を直接呼び出す場合です。この場合、呼び出し先のアドレスはコンパイル時に決定できます。
*   **クロージャ呼び出し (Closure Call)**: 実行時に呼び出す関数が決定される場合です。Goのクロージャは、周囲の環境（レキシカルスコープ）の変数をキャプチャする関数リテラルです。クロージャは、関数ポインタとキャプチャされた環境（コンテキスト）を保持する構造体として実装されることが多く、呼び出し時にはこの構造体から実際の関数アドレスと環境を取り出して実行します。

### 4. ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタが正確に動作するために、ポインタの書き込み操作を監視するメカニズムです。Goのコンカレントガベージコレクタでは、ヒープ上のオブジェクトへのポインタが変更される際に、ガベージコレクタにその変更を通知する必要があります。これにより、ガベージコレクタはオブジェクトグラフの整合性を保ちながら、並行してマークフェーズを実行できます。`OASWB`（Assign Write Barrier）は、ライトバリアを伴う代入操作を表すASTオペコードです。

### 5. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要な最適化フェーズの一つです。プログラム中の変数をCPUのレジスタに割り当てることで、メモリへのアクセスを減らし、実行速度を向上させます。SSA形式は、変数のライフタイムが明確になるため、レジスタ割り当てを効率的に行うのに役立ちます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の点に集約されます。

### 1. 関数呼び出しのSSAオペコード導入

*   **`genericOps.go` と `opGen.go`**:
    *   `ClosureCall` と `StaticCall` という新しい汎用SSAオペコードが導入されました。
    *   `ClosureCall`: クロージャを介した関数呼び出しを表します。引数としてコードポインタ、コンテキストポインタ、メモリを受け取り、メモリを返します。
    *   `StaticCall`: 静的な関数呼び出しを表します。引数として呼び出す関数のシンボルとメモリを受け取り、メモリを返します。
    *   以前の`Call`オペコードは`ClosureCall`に名称変更され、より具体的な意味を持つようになりました。
*   **`AMD64Ops.go`**:
    *   AMD64アーキテクチャ固有のオペコードとして `OpAMD64CALLstatic` と `OpAMD64CALLclosure` が追加されました。これらは、汎用的な`StaticCall`および`ClosureCall`オペコードがAMD64の機械語命令に変換される際に使用されます。
    *   `CALLclosure`オペコードには、レジスタクローバー情報（呼び出しによって破壊される可能性のあるレジスタ）が設定される予定であることがコメントで示唆されています（`//TODO: set register clobber to everything?`）。

### 2. `ssa.go` における関数呼び出しのSSA変換ロジック

`ssa.go`の`expr`メソッド内の`OCALLFUNC`ケースが大幅に修正されました。
*   **静的呼び出しとクロージャ呼び出しの区別**: `n.Left.Op == ONAME && n.Left.Class == PFUNC`という条件で、呼び出しが静的な関数（`static`）であるか、クロージャを介した動的な呼び出しであるかを判定します。
*   **クロージャの評価**: `static`でない場合（クロージャ呼び出しの場合）、`n.Left`（クロージャを表す式）を評価して、クロージャのSSA値を取得します。
*   **`OpStaticCall` と `OpClosureCall` の生成**:
    *   静的呼び出しの場合、`s.newValue1(ssa.OpStaticCall, ssa.TypeMem, n.Left.Sym, s.mem())` を使用して `OpStaticCall` オペコードを生成します。`n.Left.Sym`は呼び出す関数のシンボルです。
    *   クロージャ呼び出しの場合、まずクロージャのSSA値から関数エントリポイント（コードポインタ）をロードし（`s.newValue2(ssa.OpLoad, s.config.Uintptr, nil, closure, s.mem())`）、その後 `s.newValue3(ssa.OpClosureCall, ssa.TypeMem, nil, entry, closure, s.mem())` を使用して `OpClosureCall` オペコードを生成します。
*   **ブロックの種類の変更**: 関数呼び出しを含むブロックの`Kind`が`ssa.BlockCall`に設定され、`Control`フィールドに生成された`call`オペコードが割り当てられます。これは、SSAバックエンドが呼び出しブロックを特別に扱い、呼び出し後のメモリ状態などを適切に管理するために重要です。

### 3. SSA変換可能な変数判定ロジックの再編成 (`canSSA`関数)

`ssa.go`に`canSSA`という新しいヘルパー関数が導入されました。この関数は、与えられた`ONAME`ノード（変数）がSSA形式に変換可能かどうかを判定します。
*   **判定条件**:
    *   `n.Addrtaken`: 変数のアドレスが取られている場合（ポインタとして扱われる可能性がある場合）、SSA化できません。
    *   `n.Class&PHEAP != 0`: 変数がヒープに割り当てられている場合、SSA化できません。
    *   `n.Class == PEXTERN`: 外部変数（グローバル変数など）はSSA化できません。
    *   `n.Class == PPARAMOUT`: 戻り値パラメータはSSA化できません。
*   この`canSSA`関数は、`OAS`（代入）および`ONAME`（変数参照）の処理において、変数をSSA化するか、それともメモリへのストア/ロードとして扱うかを決定するために使用されます。これにより、SSA変換ロジックがより明確になり、保守性が向上しました。

### 4. AMD64リライトルール (`AMD64.rules` と `rewriteAMD64.go`)

*   **`AMD64.rules`**: 汎用的な`StaticCall`および`ClosureCall`オペコードを、AMD64アーキテクチャ固有の`CALLstatic`および`CALLclosure`オペコードに変換するためのリライトルールが追加されました。
    *   `(StaticCall [target] mem) -> (CALLstatic [target] mem)`
    *   `(ClosureCall entry closure mem) -> (CALLclosure entry closure mem)`
*   **`rewriteAMD64.go`**: 上記のリライトルールに対応するGoコードが生成され、SSA値のオペコードをAMD64固有の呼び出しオペコードに変換するロジックが実装されました。

### 5. ライトバリアの考慮

`ssa.go`の`OAS`（代入）処理において、`OASWB`（ライトバリア付き代入）が追加されました。これは、ガベージコレクタのライトバリアをSSAバックエンドで適切に処理するための準備です。コミットメッセージの`TODO: do write barrier`というコメントから、この時点ではまだ完全な実装ではないものの、将来的な対応を見越した変更であることがわかります。

関数呼び出し（`OCALLFUNC`）をSSA形式に変換する最も重要な部分です。
*   `static`変数は、呼び出しが静的な関数呼び出しであるか（`n.Left`が`PFUNC`クラスの`ONAME`であるか）を判定します。
*   `!static`の場合、つまりクロージャ呼び出しの場合、`n.Left`（クロージャを表す式）を`s.expr(n.Left)`で評価し、クロージャのSSA値を取得します。
*   引数の代入（`n.List`）は、`s.stmtList(n.List)`で処理されます。これは、呼び出し前に引数がスタックなどに配置されることを意味します。
*   新しいSSAブロック`bNext`が作成されます。
*   `static`の判定結果に基づいて、`OpStaticCall`または`OpClosureCall`オペコードが生成されます。
    *   `OpStaticCall`は、呼び出す関数のシンボル（`n.Left.Sym`）を補助情報として持ちます。
    *   `OpClosureCall`は、クロージャのSSA値からロードされたエントリポイント（コードポインタ）と、クロージャ自体のSSA値を引数として持ちます。
*   現在のSSAブロック`b`は`s.endBlock()`で閉じられ、その`Kind`が`ssa.BlockCall`に設定されます。これは、このブロックが関数呼び出しを含む特別なブロックであることを示します。`b.Control`には生成された`call`オペコードが設定され、この呼び出しがブロックの制御フローを決定することを示します。
*   `s.startBlock(bNext)`で新しいブロックが開始され、呼び出し後の処理が続行されます。
*   `s.vars[".mem"] = call`は、関数呼び出しがメモリの状態を変更する可能性があるため、呼び出しの結果として新しいメモリの状態が生成されることを示します。

### `ssa.go` の `canSSA` 関数

```go
func canSSA(n *Node) bool {
	if n.Op != ONAME {
		log.Fatalf("canSSA passed a non-ONAME %s %v", Oconv(int(n.Op), 0), n)
	}
	if n.Addrtaken {
		return false
	}
	if n.Class&PHEAP != 0 {
		return false
	}
	if n.Class == PEXTERN {
		return false
	}
	if n.Class == PPARAMOUT {
		return false
	}
	return true
	// TODO: try to make more variables SSAable.
}
```
この関数は、GoコンパイラのASTノード`n`がSSA形式に変換可能かどうかを判定します。
*   `n.Op != ONAME`: `canSSA`は変数（`ONAME`）に対してのみ意味があるため、それ以外のオペコードの場合はエラーとなります。
*   `n.Addrtaken`: 変数のアドレスが取られている場合（`&var`のような操作が行われている場合）、その変数はメモリ上で直接操作される可能性があり、SSAの「一度だけ代入」という原則に反するため、SSA化できません。
*   `n.Class&PHEAP != 0`: 変数がヒープに割り当てられている場合、複数のゴルーチンからアクセスされる可能性があり、SSAのローカルな性質と合わないため、SSA化できません。
*   `n.Class == PEXTERN`: 外部変数（グローバル変数など）は、プログラム全体からアクセスされ、SSAのスコープ外で変更される可能性があるため、SSA化できません。
*   `n.Class == PPARAMOUT`: 戻り値パラメータは、関数呼び出しのセマンティクス上、特別な扱いが必要であり、直接SSA化するのには適さない場合があります。

これらの条件をすべて満たさない場合、変数はSSA化可能であると判断されます。

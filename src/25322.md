## 変更の背景

このコミットは、Go言語の標準ライブラリである `crypto/cipher` パッケージ内のCTRモード暗号化ストリームの実装において発見されたバグを修正するために行われました。具体的には、`ctr.go` 内の `refill` メソッドにおいて、暗号ブロックのサイズが非常に大きい場合に、内部バッファの再充填ロジックが正しく機能せず、無限ループに陥る可能性がありました。

CTRモードは、ブロック暗号をストリーム暗号のように扱うためのモードであり、カウンタをインクリメントしながらブロック暗号を適用し、その出力を平文とXORすることで暗号化・復号化を行います。この処理の効率性を高めるため、Goの実装では内部バッファ `x.out` を使用して、一度に複数のブロックを生成し、それを `XORKeyStream` メソッドで消費する形をとっています。

問題は、`refill` メソッドが `x.out` バッファを再充填する際の条件判定にありました。特に、`remain > x.outUsed` という条件が、特定の状況下（特にブロックサイズが大きい場合）でバッファが適切に再充填されず、結果として `XORKeyStream` が常に空のバッファを処理しようとして無限ループを引き起こす可能性がありました。

このバグは、GoのIssue #12975として報告され、このコミットによって修正されました。修正の目的は、`refill` メソッドのロジックを改善し、あらゆるブロックサイズにおいてCTRストリームが正しく、かつ効率的に動作するようにすることです。

## 前提知識の解説

### 1. ブロック暗号とストリーム暗号

*   **ブロック暗号 (Block Cipher)**: データを固定長のブロック（例: 128ビット）に分割し、ブロックごとに暗号化・復号化を行う暗号方式です。AES (Advanced Encryption Standard) などが代表的です。
*   **ストリーム暗号 (Stream Cipher)**: データをビットまたはバイト単位で暗号化・復号化を行う暗号方式です。鍵ストリームと呼ばれる擬似乱数を生成し、それを平文とXORすることで暗号化します。

### 2. CTR (Counter) モード

CTRモードは、ブロック暗号をストリーム暗号のように扱うための運用モード（Mode of Operation）の一つです。その主な特徴は以下の通りです。

*   **カウンタの利用**: 各ブロックの暗号化に際し、ユニークな「カウンタ」値を入力としてブロック暗号を適用します。このカウンタは、初期ベクトル (IV: Initialization Vector) と連番を組み合わせたものなど、予測可能かつユニークな値が使われます。
*   **鍵ストリームの生成**: ブロック暗号の出力が鍵ストリームとして機能します。
*   **XOR処理**: 生成された鍵ストリームと平文（または暗号文）をXORすることで、暗号化（または復号化）を行います。
*   **並列処理**: 各ブロックの暗号化が独立しているため、並列処理が可能です。これはパフォーマンス面で大きな利点となります。
*   **エラー伝播**: ストリーム暗号と同様に、暗号文の一部のビットエラーが平文の対応するビットにのみ影響し、他の部分には伝播しません。
*   **初期ベクトル (IV)**: 各暗号化セッションでユニークなIVを使用することが極めて重要です。同じ鍵とIVで異なる平文を暗号化すると、セキュリティ上の脆弱性が発生します。

### 3. `crypto/cipher` パッケージ

Go言語の `crypto/cipher` パッケージは、ブロック暗号やストリーム暗号の運用モード（CTR, CBC, GCMなど）を実装するためのインターフェースと共通ロジックを提供します。具体的なブロック暗号アルゴリズム（AESなど）は `crypto/aes` などのサブパッケージで提供され、`crypto/cipher` はそれらのアルゴリズムをどのように使うかを定義します。

*   `cipher.Block` インターフェース: ブロック暗号が実装すべきインターフェースで、`BlockSize()`、`Encrypt(dst, src []byte)`、`Decrypt(dst, src []byte)` メソッドを持ちます。
*   `cipher.Stream` インターフェース: ストリーム暗号が実装すべきインターフェースで、`XORKeyStream(dst, src []byte)` メソッドを持ちます。これは、`src` の内容を鍵ストリームとXORして `dst` に書き込むものです。
*   `cipher.NewCTR(block Block, iv []byte) Stream`: 指定されたブロック暗号と初期ベクトルを使用して、新しいCTRモードのストリームを生成する関数です。

### 4. バッファリングと効率

暗号化処理では、特に大量のデータを扱う場合、ブロックごとに暗号化関数を呼び出すのはオーバーヘッドが大きくなることがあります。そのため、内部的にバッファ（このケースでは `x.out`）を設け、一度に複数のブロックを生成して鍵ストリームとして利用することで、効率を向上させることが一般的です。`refill` メソッドは、このバッファが枯渇しそうになったときに、次の鍵ストリームデータを事前に生成する役割を担います。

## 技術的詳細

このコミットの技術的詳細な変更点は、`src/crypto/cipher/ctr.go` 内の `ctr` 構造体の `refill` メソッドにおけるバッファ再充填ロジックの修正と、それに関連するテストの追加です。

### `refill` メソッドの役割

`ctr` 構造体は、CTRモードのストリーム暗号を管理するための内部状態を保持します。
*   `b`: 基となる `cipher.Block` インターフェース（例: AESブロック暗号）。
*   `ctr`: 現在のカウンタ値（バイトスライス）。
*   `out`: 生成された鍵ストリームを一時的に保持するバッファ。
*   `outUsed`: `out` バッファのうち、既に `XORKeyStream` で消費されたバイト数。

`refill` メソッドは、`out` バッファの鍵ストリームが不足しそうになったときに呼び出され、新しい鍵ストリームデータを生成して `out` バッファに充填します。この処理は以下のステップで行われます。

1.  **消費済みデータの移動**: `x.out` バッファの先頭に、まだ消費されていない残りの鍵ストリームデータを移動させます。`copy(x.out, x.out[x.outUsed:])`
2.  **バッファのリサイズ**: `x.out` をその容量いっぱいに拡張します。`x.out = x.out[:cap(x.out)]`
3.  **新しい鍵ストリームの生成**: `for` ループ内で、`x.b.Encrypt(x.out[remain:], x.ctr)` を呼び出し、現在のカウンタ `x.ctr` をブロック暗号で暗号化し、その結果を `x.out` バッファの `remain` 位置から書き込みます。その後、カウンタ `x.ctr` をインクリメントし、`remain` をブロックサイズ分進めます。このループは、`x.out` バッファが十分に満たされるまで繰り返されます。

### 修正前の問題点

修正前の `refill` メソッドには以下の条件分岐がありました。

```go
	remain := len(x.out) - x.outUsed
	if remain > x.outUsed {
		return
	}
```

この `if remain > x.outUsed` という条件は、`x.out` バッファの残りのデータ量 (`remain`) が、既に消費されたデータ量 (`x.outUsed`) よりも大きい場合に `refill` を早期に終了させていました。

問題は、ブロックサイズが非常に大きい場合（例えば、`x.out` バッファの容量に近い、あるいはそれ以上の場合）に発生しました。
`x.outUsed` が小さい値（例えば0）で、`remain` が大きい値（例えば `len(x.out)`）である場合、`remain > x.outUsed` の条件が真となり、`refill` メソッドが何もせずにリターンしてしまうことがありました。
これにより、`x.out` バッファが適切に再充填されず、`XORKeyStream` メソッドが次に鍵ストリームを要求した際に、常に空に近いバッファを受け取ることになります。結果として、`XORKeyStream` は必要な鍵ストリームを得られず、無限ループに陥る可能性がありました。

### 修正内容

修正は、この問題のある `if` 文を削除することによって行われました。

```diff
--- a/src/crypto/cipher/ctr.go
+++ b/src/crypto/cipher/ctr.go
@@ -41,13 +41,10 @@ func NewCTR(block Block, iv []byte) Stream {
 
 func (x *ctr) refill() {
 	remain := len(x.out) - x.outUsed
-	if remain > x.outUsed {
-		return
-	}
 	copy(x.out, x.out[x.outUsed:])
 	x.out = x.out[:cap(x.out)]
 	bs := x.b.BlockSize()
-	for remain < len(x.out)-bs {
+	for remain <= len(x.out)-bs {
 		x.b.Encrypt(x.out[remain:], x.ctr)
 		remain += bs
 		inc(x.ctr)
```

この変更により、`refill` メソッドは常にバッファの再充填ロジックを実行するようになります。`remain` の値に関わらず、`copy` と `x.out = x.out[:cap(x.out)]` が実行され、その後 `for` ループでバッファが適切に満たされるまで鍵ストリームが生成されます。

また、`for` ループの条件も `remain < len(x.out)-bs` から `remain <= len(x.out)-bs` に変更されています。これは、バッファの最後のブロックを生成する際に、`remain` が `len(x.out)-bs` と等しい場合にもループが実行されるようにするためです。これにより、バッファが完全に満たされることが保証され、エッジケースでのバッファ不足を防ぎます。

### テストの追加

`src/crypto/cipher/ctr_test.go` には、新しいテスト `TestCTR` が追加されました。このテストは、様々なブロックサイズ（64バイトから1024バイトまで2倍ずつ）に対してCTRモードが正しく動作するかを検証します。

*   `noopBlock`: テスト用に、ブロックサイズを指定できるが、実際にはデータを暗号化せずにそのままコピーするだけのダミーの `cipher.Block` 実装です。これにより、CTRモードのロジック自体をテストし、基盤となるブロック暗号の実装に依存しないようにします。
*   `inc(b []byte)`: バイトスライスをカウンタとしてインクリメントするヘルパー関数です。
*   `xor(a, b []byte)`: 2つのバイトスライスをXORするヘルパー関数です。
*   `TestCTR` のロジック:
    1.  `size` を64から1024まで変化させながらループします。
    2.  `noopBlock(size)` を使用して `cipher.NewCTR` を作成します。
    3.  `src`（入力平文）と `want`（期待される暗号文）を準備します。`want` は、`src` を手動でカウンタとXORして計算されます。
    4.  `ctr.XORKeyStream(dst, src)` を呼び出して暗号化を実行します。
    5.  `bytes.Equal(dst, want)` で結果が期待通りか検証します。

このテストは、特に大きなブロックサイズでの `refill` ロジックの正確性を検証するのに役立ちます。

## コアとなるコードの解説

### `src/crypto/cipher/ctr.go` の変更点

`refill` メソッドの変更は、CTRモードの鍵ストリーム生成バッファの管理をより堅牢にするものです。

1.  **`if remain > x.outUsed { return }` の削除**:
    この条件は、バッファの残りの部分が既に消費された部分よりも大きい場合に、`refill` 処理をスキップしていました。しかし、これはブロックサイズが大きい場合や、バッファがほとんど空の状態で `refill` が呼び出された場合に、バッファが適切に再充填されない原因となっていました。この条件を削除することで、`refill` が呼び出された際には常にバッファの再充填ロジックが実行されるようになり、バッファが不適切な状態になることを防ぎます。

2.  **`for remain < len(x.out)-bs` から `for remain <= len(x.out)-bs` への変更**:
    この変更は、`for` ループがバッファの最後のブロックを生成する条件を調整するものです。
    *   `len(x.out)` は `x.out` バッファの現在の長さ（容量いっぱいまで拡張された後）。
    *   `bs` はブロックサイズ。
    *   `len(x.out) - bs` は、バッファの最後にブロックを書き込むことができる開始インデックスの最大値を示します。
    修正前は `remain` がこの値より小さい場合にのみループが実行されていました。つまり、`remain` がちょうど `len(x.out) - bs` と等しい場合、ループは実行されず、最後のブロックが生成されない可能性がありました。
    修正後は `remain <= len(x.out)-bs` となったため、`remain` が `len(x.out) - bs` と等しい場合でもループが実行され、バッファの最後のブロックが確実に生成されるようになります。これにより、バッファが完全に満たされ、`XORKeyStream` が常に十分な鍵ストリームデータを利用できるようになります。

これらの変更により、`refill` メソッドは、どのようなブロックサイズやバッファの状態であっても、`x.out` バッファを適切に、かつ完全に鍵ストリームで満たすことができるようになり、無限ループのバグが解消されました。

### `src/crypto/cipher/ctr_test.go` の追加点

追加された `ctr_test.go` は、CTRモードの実装の堅牢性を高めるための重要なテストです。

1.  **`noopBlock` 型**:
    これはテスト専用の `cipher.Block` インターフェースの実装です。`BlockSize()` メソッドはコンストラクタで与えられた `int` 値を返し、`Encrypt()` と `Decrypt()` メソッドは単に `src` を `dst` にコピーするだけです。
    このダミー実装の目的は、実際のブロック暗号アルゴリズム（例: AES）の動作に依存せず、`crypto/cipher` パッケージのCTRモードロジック自体（特にバッファリングとカウンタのインクリメント）が正しく機能するかを独立してテストすることです。これにより、テストの焦点をCTRモードの実装に限定し、デバッグを容易にします。

2.  **`inc(b []byte)` 関数**:
    これは、バイトスライスを数値としてインクリメントするヘルパー関数です。CTRモードでは、カウンタ値がブロックごとにインクリメントされるため、この関数はカウンタの動作をシミュレートするために使用されます。最下位バイトから順にインクリメントし、オーバーフローが発生した場合は上位バイトに繰り上げます。

3.  **`xor(a, b []byte)` 関数**:
    これは、2つのバイトスライスをビット単位でXORするヘルパー関数です。CTRモードの暗号化・復号化の核心であるXOR操作をシミュレートするために使用されます。

4.  **`TestCTR` 関数**:
    このテストは、`size` 変数を64、128、256、512、1024バイトと変化させながらループを実行します。これは、様々なブロックサイズ（特に大きなブロックサイズ）でのCTRモードの動作を検証するためです。
    *   各 `size` に対して、`noopBlock` を使用して `cipher.NewCTR` を初期化します。
    *   `src`（平文）をすべて `0xff` で初期化します。
    *   `want`（期待される暗号文）は、`src` を手動でカウンタとXORすることで計算されます。`inc` 関数と `xor` 関数がここで使用されます。
    *   `ctr.XORKeyStream(dst, src)` を呼び出して、実際のCTRストリームによる暗号化を実行します。
    *   最後に `bytes.Equal(dst, want)` を使用して、生成された暗号文 `dst` が期待される `want` と一致するかを検証します。

このテストの追加により、`refill` メソッドの修正が、特に大きなブロックサイズにおいてCTRモードの正しい動作を保証していることが確認できるようになりました。

## 元コミット内容

Goランタイムの`mallocgc`関数におけるtinyアロケータのロジックが修正されました。以前の`golang.org/cl/2814`での変更により、新しいtinyブロックが割り当てられた際に、そのブロックが適切に保存されず、結果として再利用されないというバグが発生していました。このコミットは、このバグを修正し、tinyブロックが正しく保存・再利用されるようにします。

## 変更の背景

Goランタイムは、様々なサイズのオブジェクトに対して効率的なメモリ割り当てを行うために、複数のアロケータ戦略を採用しています。その一つが「tiny allocator」です。これは、非常に小さなオブジェクト（例えば、数バイトから数十バイト程度）の割り当てを最適化するためのものです。

小さなオブジェクトが頻繁に割り当てられる場合、それぞれに対して独立したメモリブロックを確保し、ガベージコレクションの対象とすることはオーバーヘッドが大きくなります。そこで、tiny allocatorは、より大きなメモリブロック（tinyブロック）を確保し、その中から小さなオブジェクトを順次割り当てていくことで、このオーバーヘッドを削減します。これにより、メモリのフラグメンテーションを減らし、ガベージコレクションの効率を向上させることができます。

このコミットの背景にある問題は、以前の変更（`golang.org/cl/2814`）によって、このtiny allocatorのロジックに微妙なバグが混入したことです。具体的には、`mallocgc`が新しいtinyブロックを割り当てる際に、古いtinyブロックよりも多くの空きスペースがある場合に新しいブロックを保存するはずのロジックが正しく機能していませんでした。このため、新しいtinyブロックが一度も保存されず、結果として再利用されることがなく、メモリ効率が低下していました。この修正は、この重要な最適化が意図通りに機能するようにするためのものです。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリ管理システムを持っています。これは、OSから大きなメモリ領域を確保し、それを細かく分割してユーザープログラムに提供します。主なコンポーネントは以下の通りです。

*   **mheap (ヒープ)**: Goプログラムが動的に確保するメモリ領域全体を管理します。
*   **mspan (スパン)**: ヒープを構成する連続したページ（通常8KB）のまとまりです。各スパンは特定のサイズのオブジェクトを格納するために使用されます。
*   **mcache (Pごとのキャッシュ)**: 各論理プロセッサ（P）は、頻繁に割り当てられる小さなオブジェクトのために、mspanのキャッシュを持っています。これにより、ロックなしで高速なメモリ割り当てが可能になります。
*   **mallocgc**: Goのメモリ割り当て関数です。オブジェクトのサイズに応じて、適切なmspanからメモリを割り当てるか、tiny allocatorを使用するかを決定します。
*   **ガベージコレクション (GC)**: 不要になったメモリを自動的に解放する仕組みです。GoのGCは並行・世代別・三色マーク＆スイープ方式を採用しています。

### Tiny Allocator

Goのメモリ管理において、特に重要な最適化の一つがtiny allocatorです。これは、サイズが非常に小さいオブジェクト（例えば、16バイト未満）の割り当てを効率化するために導入されています。

通常のメモリ割り当てでは、オブジェクトのサイズに合ったmspanを探し、そこからメモリを切り出します。しかし、非常に小さなオブジェクトの場合、このプロセス自体がオーバーヘッドとなることがあります。また、小さなオブジェクトが多数存在すると、mspanの管理が複雑になり、メモリのフラグメンテーションを引き起こす可能性もあります。

tiny allocatorは、これらの問題を解決するために、各Pのmcache内に「tinyブロック」と呼ばれる小さなバッファを保持します。`mallocgc`が小さなオブジェクトの割り当て要求を受け取ると、まずこのtinyブロックに十分な空きがあるかを確認します。空きがあれば、そこからメモリを切り出してオブジェクトに割り当てます。tinyブロックが満杯になった場合や、割り当てようとしているオブジェクトがtinyブロックに収まらない場合は、新しいtinyブロックを割り当てます。

このメカニズムの鍵は、新しいtinyブロックを割り当てた際に、古いtinyブロックと比較してどちらがより多くの空きスペースを持っているかを判断し、より効率的な方を`c.tiny`（現在のtinyブロック）として保存することです。これにより、将来の小さなオブジェクト割り当てでそのブロックを再利用できるようになります。

### `c.tiny`と`c.tinyoffset`

`c`は`mcache`構造体（またはそれに相当する、現在のPのメモリキャッシュを表すコンテキスト）を指します。
*   `c.tiny`: 現在使用中のtinyブロックの先頭アドレスを指すポインタです。
*   `c.tinyoffset`: `c.tiny`ブロック内で次に割り当て可能なアドレスのオフセットを示します。つまり、`c.tiny + c.tinyoffset`が次の割り当て開始位置となります。

これらの変数を適切に管理することで、tinyブロック内での連続的な小さなオブジェクトの割り当てと、ブロックの効率的な再利用が可能になります。

## 技術的詳細

このコミットは、`src/runtime/malloc.go`内の`mallocgc`関数におけるtiny allocatorのロジックを修正します。問題は、新しいtinyブロックが割り当てられた際に、既存の`c.tiny`ブロックと比較して、どちらを保持すべきかを判断する条件式にありました。

元のコードでは、新しいオブジェクトのサイズ`size`が現在の`c.tinyoffset`（現在のtinyブロックの空きスペースの開始位置）よりも小さい場合にのみ、新しいブロック`x`を`c.tiny`として保存していました。

```go
// 修正前
if size < c.tinyoffset {
    c.tiny = x
    c.tinyoffset = size
}
```

この条件式は、「新しいオブジェクトが現在のtinyブロックに収まらないため、新しいtinyブロック`x`を割り当てた」という状況で評価されます。この時、`c.tinyoffset`は現在のtinyブロックの残りの空きスペースの量を示しています。`size < c.tinyoffset`という条件は、「新しいオブジェクトのサイズが、現在のtinyブロックの残りの空きスペースよりも小さい」という意味になります。

しかし、このロジックには問題がありました。`mallocgc`が新しいtinyブロック`x`を割り当てるのは、現在の`c.tiny`ブロックに割り当てようとしているオブジェクトが収まらない場合です。この時、`c.tiny`は既に使い切られているか、残りのスペースが小さすぎる状態です。したがって、`c.tinyoffset`は非常に小さい値か、あるいは`size`よりも小さい値になっているはずです。

この条件式では、`c.tiny`が`nil`（つまり、まだtinyブロックが一度も割り当てられていないか、完全に使い切られてリセットされた状態）の場合に、新しいブロック`x`を`c.tiny`として保存することができませんでした。`c.tiny`が`nil`の場合、`c.tinyoffset`は通常0ですが、`size < 0`は常に偽となるため、新しいブロックが保存されませんでした。

結果として、`c.tiny`が一度`nil`になると、新しいtinyブロックが割り当てられても`c.tiny`に設定されることがなく、tinyブロックの再利用が全く行われない状態になっていました。これは、`golang.org/cl/2814`で導入されたバグであり、tiny allocatorの効率を著しく低下させていました。

修正後のコードは、この条件に`c.tiny == nil`というチェックを追加します。

```go
// 修正後
if size < c.tinyoffset || c.tiny == nil {
    c.tiny = x
    c.tinyoffset = size
}
```

この変更により、以下のいずれかの条件が満たされた場合に、新しいブロック`x`が`c.tiny`として保存されるようになります。
1.  `size < c.tinyoffset`: 新しいオブジェクトのサイズが、現在のtinyブロックの残りの空きスペースよりも小さい場合（これは、新しいブロック`x`がより多くの空きスペースを持つことを意味します）。
2.  `c.tiny == nil`: 現在のtinyブロックがまだ設定されていないか、完全に使い切られてリセットされた状態の場合。

特に2番目の条件が追加されたことで、`c.tiny`が`nil`の場合でも、新しく割り当てられたブロック`x`が正しく`c.tiny`として設定され、その後の小さなオブジェクト割り当てで再利用されるようになります。これにより、tiny allocatorが意図通りに機能し、メモリ割り当ての効率が回復します。

また、このコミットには`src/runtime/malloc_test.go`に新しいテストケース`TestTinyAlloc`が追加されています。このテストは、複数の小さなオブジェクト（`new(byte)`）を割り当て、それらが同じ8バイトチャンク内に割り当てられていることを確認することで、tiny allocatorが正しく機能しているかを検証します。もしすべてのオブジェクトが異なる8バイトチャンクに割り当てられていた場合、それはtiny allocatorが機能していないことを意味し、テストは失敗します。このテストの追加は、修正が正しく適用され、将来的に同様の回帰バグが発生しないようにするための重要な措置です。

### `src/runtime/malloc.go`の変更

`mallocgc`関数内の、新しいtinyブロック`x`を現在のtinyブロック`c.tiny`として保存するかどうかを決定する条件式が変更されました。

*   **変更前**: `if size < c.tinyoffset`
    *   この条件は、「割り当てようとしているオブジェクトのサイズ`size`が、現在のtinyブロックの残りの空きスペースの開始位置`c.tinyoffset`よりも小さい場合」に真となります。これは、新しいブロック`x`が現在の`c.tiny`よりも多くの空きスペースを持つ場合に`c.tiny`を更新するという意図でしたが、`c.tiny`が`nil`の場合に正しく機能しませんでした。
*   **変更後**: `if size < c.tinyoffset || c.tiny == nil`
    *   `c.tiny == nil`という条件が追加されました。これにより、`c.tiny`がまだ初期化されていないか、完全に使い切られてリセットされた状態である場合でも、新しく割り当てられたブロック`x`が確実に`c.tiny`として設定されるようになります。
    *   この修正により、tiny allocatorは常に有効なtinyブロックを保持し、小さなオブジェクトの割り当て要求に対してそれを再利用できるようになります。

### `src/runtime/malloc_test.go`の変更

`TestTinyAlloc`という新しいテスト関数が追加されました。

1.  `const N = 16`: 16個の小さなオブジェクトを割り当てることを想定しています。
2.  `var v [N]unsafe.Pointer`: 割り当てられたオブジェクトへのポインタを格納する配列です。
3.  `for i := range v { v[i] = unsafe.Pointer(new(byte)) }`: 16個の1バイトオブジェクトを割り当てます。`new(byte)`は非常に小さなオブジェクトであり、tiny allocatorの対象となります。
4.  `chunks := make(map[uintptr]bool, N)`: 割り当てられたオブジェクトが属する8バイトチャンクのベースアドレスを記録するためのマップです。Goのtiny allocatorは通常、8バイトアラインメントでメモリを割り当てます。
5.  `for _, p := range v { chunks[uintptr(p)&^7] = true }`: 各オブジェクトのポインタ`p`から、そのオブジェクトが属する8バイトチャンクの先頭アドレスを計算し、マップに記録します。`&^7`は、アドレスの下位3ビットをクリアすることで、8バイトアラインメントされたベースアドレスを取得するビット演算です。
6.  `if len(chunks) == N { t.Fatal("no bytes allocated within the same 8-byte chunk") }`: もし`chunks`マップの要素数が`N`（16）と等しい場合、それは16個のオブジェクトすべてが異なる8バイトチャンクに割り当てられたことを意味します。これは、tiny allocatorが機能しておらず、オブジェクトが個別に割り当てられている状態を示します。この場合、テストは失敗します。

このテストは、tiny allocatorが正しく機能していれば、複数の小さなオブジェクトが同じtinyブロック（8バイトチャンク）内に割り当てられることを期待しています。これにより、メモリの効率的な利用と、tiny allocatorのバグが修正されたことを検証します。

このメカニズムの鍵は、新しいtinyブロックを割り当てた際に、古いtinyブロックと比較してどちらがより多くの空きスペースを持っているかを判断し、より効率的な方を`c.tiny`（現在のtinyブロック）として保存することです。これにより、将来の小さなオブジェクト割り当てでそのブロックを再利用できるようになります。

### `c.tiny`と`c.tinyoffset`

`c`は`mcache`構造体（またはそれに相当する、現在のPのメモリキャッシュを表すコンテキスト）を指します。
*   `c.tiny`: 現在使用中のtinyブロックの先頭アドレスを指すポインタです。
*   `c.tinyoffset`: `c.tiny`ブロック内で次に割り当て可能なアドレスのオフセットを示します。つまり、`c.tiny + c.tinyoffset`が次の割り当て開始位置となります。

これらの変数を適切に管理することで、tinyブロック内での連続的な小さなオブジェクトの割り当てと、ブロックの効率的な再利用が可能になります。

## 技術的詳細

このコミットは、`src/runtime/malloc.go`内の`mallocgc`関数におけるtiny allocatorのロジックを修正します。問題は、新しいtinyブロックが割り当てられた際に、既存の`c.tiny`ブロックと比較して、どちらを保持すべきかを判断する条件式にありました。

元のコードでは、新しいオブジェクトのサイズ`size`が現在の`c.tinyoffset`（現在のtinyブロックの空きスペースの開始位置）よりも小さい場合にのみ、新しいブロック`x`を`c.tiny`として保存していました。

```go
// 修正前
if size < c.tinyoffset {
    c.tiny = x
    c.tinyoffset = size
}
```

この条件式は、「新しいオブジェクトが現在のtinyブロックに収まらないため、新しいtinyブロック`x`を割り当てた」という状況で評価されます。この時、`c.tinyoffset`は現在のtinyブロックの残りの空きスペースの量を示しています。`size < c.tinyoffset`という条件は、「新しいオブジェクトのサイズが、現在のtinyブロックの残りの空きスペースよりも小さい」という意味になります。

しかし、このロジックには問題がありました。`mallocgc`が新しいtinyブロック`x`を割り当てるのは、現在の`c.tiny`ブロックに割り当てようとしているオブジェクトが収まらない場合です。この時、`c.tiny`は既に使い切られているか、残りのスペースが小さすぎる状態です。したがって、`c.tinyoffset`は非常に小さい値か、あるいは`size`よりも小さい値になっているはずです。

この条件式では、`c.tiny`が`nil`（つまり、まだtinyブロックが一度も割り当てられていないか、完全に使い切られてリセットされた状態）の場合に、新しいブロック`x`を`c.tiny`として保存することができませんでした。`c.tiny`が`nil`の場合、`c.tinyoffset`は通常0ですが、`size < 0`は常に偽となるため、新しいブロックが保存されませんでした。

結果として、`c.tiny`が一度`nil`になると、新しいtinyブロックが割り当てられても`c.tiny`に設定されることがなく、tinyブロックの再利用が全く行われない状態になっていました。これは、`golang.org/cl/2814`で導入されたバグであり、tiny allocatorの効率を著しく低下させていました。

修正後のコードは、この条件に`c.tiny == nil`というチェックを追加します。

```go
// 修正後
if size < c.tinyoffset || c.tiny == nil {
    c.tiny = x
    c.tinyoffset = size
}
```

この変更により、以下のいずれかの条件が満たされた場合に、新しいブロック`x`が`c.tiny`として保存されるようになります。
1.  `size < c.tinyoffset`: 新しいオブジェクトのサイズが、現在のtinyブロックの残りの空きスペースよりも小さい場合（これは、新しいブロック`x`がより多くの空きスペースを持つことを意味します）。
2.  `c.tiny == nil`: 現在のtinyブロックがまだ設定されていないか、完全に使い切られてリセットされた状態の場合。

特に2番目の条件が追加されたことで、`c.tiny`が`nil`の場合でも、新しく割り当てられたブロック`x`が正しく`c.tiny`として設定され、その後の小さなオブジェクト割り当てで再利用されるようになります。これにより、tiny allocatorが意図通りに機能し、メモリ割り当ての効率が回復します。

また、このコミットには`src/runtime/malloc_test.go`に新しいテストケース`TestTinyAlloc`が追加されています。このテストは、複数の小さなオブジェクト（`new(byte)`）を割り当て、それらが同じ8バイトチャンク内に割り当てられていることを確認することで、tiny allocatorが正しく機能しているかを検証します。もしすべてのオブジェクトが異なる8バイトチャンクに割り当てられていた場合、それはtiny allocatorが機能していないことを意味し、テストは失敗します。このテストの追加は、修正が正しく適用され、将来的に同様の回帰バグが発生しないようにするための重要な措置です。

## コアとなるコードの解説

### `src/runtime/malloc.go`の変更

`mallocgc`関数内の、新しいtinyブロック`x`を現在のtinyブロック`c.tiny`として保存するかどうかを決定する条件式が変更されました。

*   **変更前**: `if size < c.tinyoffset`
    *   この条件は、「割り当てようとしているオブジェクトのサイズ`size`が、現在のtinyブロックの残りの空きスペースの開始位置`c.tinyoffset`よりも小さい場合」に真となります。これは、新しいブロック`x`が現在の`c.tiny`よりも多くの空きスペースを持つ場合に`c.tiny`を更新するという意図でしたが、`c.tiny`が`nil`の場合に正しく機能しませんでした。
*   **変更後**: `if size < c.tinyoffset || c.tiny == nil`
    *   `c.tiny == nil`という条件が追加されました。これにより、`c.tiny`がまだ初期化されていないか、完全に使い切られてリセットされた状態である場合でも、新しく割り当てられたブロック`x`が確実に`c.tiny`として設定されるようになります。
    *   この修正により、tiny allocatorは常に有効なtinyブロックを保持し、小さなオブジェクトの割り当て要求に対してそれを再利用できるようになります。

### `src/runtime/malloc_test.go`の変更

`TestTinyAlloc`という新しいテスト関数が追加されました。

1.  `const N = 16`: 16個の小さなオブジェクトを割り当てることを想定しています。
2.  `var v [N]unsafe.Pointer`: 割り当てられたオブジェクトへのポインタを格納する配列です。
3.  `for i := range v { v[i] = unsafe.Pointer(new(byte)) }`: 16個の1バイトオブジェクトを割り当てます。`new(byte)`は非常に小さなオブジェクトであり、tiny allocatorの対象となります。
4.  `chunks := make(map[uintptr]bool, N)`: 割り当てられたオブジェクトが属する8バイトチャンクのベースアドレスを記録するためのマップです。Goのtiny allocatorは通常、8バイトアラインメントでメモリを割り当てます。
5.  `for _, p := range v { chunks[uintptr(p)&^7] = true }`: 各オブジェクトのポインタ`p`から、そのオブジェクトが属する8バイトチャンクの先頭アドレスを計算し、マップに記録します。`&^7`は、アドレスの下位3ビットをクリアすることで、8バイトアラインメントされたベースアドレスを取得するビット演算です。
6.  `if len(chunks) == N { t.Fatal("no bytes allocated within the same 8-byte chunk") }`: もし`chunks`マップの要素数が`N`（16）と等しい場合、それは16個のオブジェクトすべてが異なる8バイトチャンクに割り当てられたことを意味します。これは、tiny allocatorが機能しておらず、オブジェクトが個別に割り当てられている状態を示します。この場合、テストは失敗します。

このテストは、tiny allocatorが正しく機能していれば、複数の小さなオブジェクトが同じtinyブロック（8バイトチャンク）内に割り当てられることを期待しています。これにより、メモリの効率的な利用と、tiny allocatorのバグが修正されたことを検証します。

# [インデックス 28018] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDNSリゾルバの挙動を改善するものです。具体的には、DNSサーバから「lame referral（不適切な委任）」応答を受け取った際に、システム標準の`libresolv`ライブラリと同様にその応答を無視し、次のDNSサーバへの問い合わせを続行するように変更します。これにより、特定のDNS設定下での名前解決の遅延や失敗が解消されます。

## 変更の背景

この変更の背景には、Goの`net`パッケージが提供するDNSリゾルバが、特定の「lame referral」応答を不適切に処理し、名前解決に問題を引き起こしていたという課題があります。

「lame referral」とは、DNSサーバが、本来そのドメインの権威を持つべきではないにもかかわらず、そのドメインに対する問い合わせに対して委任（referral）応答を返す状況を指します。これは通常、DNS設定の誤りや古い情報が原因で発生します。

従来のGoの純粋なGoリゾルバ（`netgo`）は、このようなlame referral応答を受け取った際に、それを有効な応答の一部として解釈してしまうことがありました。その結果、名前解決が遅延したり、誤った情報に基づいて解決を試みたり、最終的に名前解決に失敗したりする可能性がありました。

一方、多くのUnix系システムで利用される標準のCライブラリである`libresolv`は、lame referral応答を検出した場合、それを無視して次のDNSサーバに問い合わせを試みるという堅牢な挙動を示します。このコミットは、Goの純粋なGoリゾルバの挙動を`libresolv`のそれに合わせることで、DNS解決の信頼性と互換性を向上させることを目的としています。これにより、`Fixes #15434`で報告されたような問題が解決されます。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### DNS (Domain Name System)
DNSは、インターネット上のコンピュータやサービスを識別するためのドメイン名（例: `www.example.com`）を、それに対応するIPアドレス（例: `192.0.2.1`）に変換（名前解決）する分散型データベースシステムです。

### DNS解決プロセス
クライアントがドメイン名を解決する際、通常は設定されたDNSリゾルバ（ネームサーバ）に問い合わせを行います。リゾルバは、その情報を持っている場合は直接応答し、持っていない場合は他のDNSサーバに問い合わせを転送したり、クライアントに別のDNSサーバへの問い合わせを指示（委任/referral）したりします。このプロセスは、最終的に権威DNSサーバ（そのドメインの情報を正式に管理しているサーバ）に到達するまで繰り返されます。

### 委任 (Delegation) と Lame Delegation/Referral
*   **委任 (Delegation):** あるドメインの管理が、その親ドメインのDNSサーバから子ドメインのDNSサーバに移譲されることです。例えば、`.com`ドメインのサーバは`example.com`の管理を`example.com`のネームサーバに委任します。
*   **Lame Delegation/Referral:** DNSサーバが、あるドメインの権威を持つべきではないにもかかわらず、そのドメインに対する問い合わせに対して委任応答を返す状況です。これは、親ゾーンの委任情報が誤っているか、委任されたネームサーバが応答しない、またはそのドメインの権威を持っていない場合に発生します。クライアントがこのような「lame」なサーバに問い合わせると、名前解決が遅延したり失敗したりする原因となります。

### Goの`net`パッケージとDNSリゾルバ
Goの`net`パッケージは、ネットワーク通信機能を提供し、その中にDNS名前解決の機能も含まれています。Goには主に2種類のDNSリゾルバがあります。
1.  **純粋なGoリゾルバ (`netgo`):** Go言語で完全に実装されたリゾルバです。`CGO_ENABLED=0`の場合や、クロスコンパイル時に使用されます。システムライブラリに依存しないため、移植性が高いですが、システム固有のDNS設定（例: `/etc/resolv.conf`の複雑なオプション）を完全にサポートしない場合があります。
2.  **Cgoリゾルバ:** `CGO_ENABLED=1`の場合に、システムのCライブラリ（主に`libresolv`）を介してDNS解決を行います。このリゾルバは、OSが提供するDNS解決メカニズムを直接利用するため、システム固有のDNS設定や機能（例: `/etc/nsswitch.conf`）に完全に準拠します。

このコミットは、純粋なGoリゾルバが`libresolv`の堅牢な挙動を模倣するように変更することで、両者の間の挙動の不一致を解消しようとしています。

### DNSメッセージの構造（RCODE, Authoritative, Recursion Available, Answer, Extraセクション）
DNS応答メッセージには、以下のような重要なフィールドが含まれます。
*   **RCODE (Response Code):** 応答のステータスコードを示します（例: `dnsRcodeSuccess`は成功、`dnsRcodeNameError`はドメイン名が存在しない）。
*   **Authoritative (AAフラグ):** 応答を返したサーバが、問い合わせられたドメインに対して権威を持っているかどうかを示します。
*   **Recursion Available (RAフラグ):** 応答を返したサーバが再帰的な問い合わせをサポートしているかどうかを示します。
*   **Answerセクション:** 問い合わせに対する直接の回答（例: ドメイン名に対応するIPアドレス）が含まれます。
*   **Extraセクション (Additional Records):** 回答に関連する追加情報（例: ネームサーバのIPアドレス）が含まれます。

このコミットでは、これらのフィールドの特定の組み合わせをチェックしてlame referral応答を識別します。

## 技術的詳細

このコミットの技術的な核心は、Goの純粋なGoリゾルバがDNS応答を処理するロジックに、lame referral応答を検出して無視する条件を追加した点にあります。

具体的には、`src/net/dnsclient_unix.go`内の`tryOneName`関数において、DNSサーバからの応答メッセージ（`msg`）が以下の条件をすべて満たす場合に、その応答を「lame referral」と判断し、次のDNSサーバへの問い合わせを続行するように変更されました。

1.  `msg.rcode == dnsRcodeSuccess`: 応答コードが成功を示している。
2.  `!msg.authoritative`: 応答を返したサーバが、問い合わせられたドメインに対して権威を持っていない。
3.  `!msg.recursion_available`: 応答を返したサーバが再帰的な問い合わせをサポートしていない。
4.  `len(msg.answer) == 0`: Answerセクションにレコードが含まれていない。
5.  `len(msg.extra) == 0`: Extraセクションにレコードが含まれていない。

これらの条件は、`libresolv`がlame referralを識別するために使用するヒューリスティックを模倣したものです。このような応答は、通常、権威のないサーバが誤って委任応答を返しているか、あるいは単に有用な情報を提供できない状況を示します。Goリゾルバは、このような応答を無視することで、不適切な情報に基づいて名前解決を試みることを避け、より信頼性の高いDNSサーバに問い合わせを続けることができます。

また、この変更に伴い、`src/net/dnsclient_unix_test.go`には、lame referral応答をシミュレートし、Goリゾルバがそれを正しく無視して次のサーバにフォールバックすることを確認する新しいテストケース`TestIgnoreLameReferrals`が追加されています。これにより、変更の意図した挙動が保証されます。

## コアとなるコードの解説

### `src/net/dnsclient_unix.go`の変更

追加された以下のコードブロックが、lame referral応答を無視する主要なロジックです。

```go
			// libresolv continues to the next server when it receives
			// an invalid referral response. See golang.org/issue/15434.
			if msg.rcode == dnsRcodeSuccess && !msg.authoritative && !msg.recursion_available && len(msg.answer) == 0 && len(msg.extra) == 0 {
				lastErr = &DNSError{Err: "lame referral", Name: name, Server: server}
				continue
			}
```

*   **`if msg.rcode == dnsRcodeSuccess && !msg.authoritative && !msg.recursion_available && len(msg.answer) == 0 && len(msg.extra) == 0`**:
    *   この条件式は、受信したDNS応答メッセージ`msg`がlame referralの典型的な特徴を持っているかをチェックします。
    *   `msg.rcode == dnsRcodeSuccess`: 応答コードが「成功」であるにもかかわらず、以下の条件が続く点が重要です。これは、サーバがエラーを返しているわけではないが、有用な情報も提供していないことを示唆します。
    *   `!msg.authoritative`: 応答を返したサーバが、問い合わせられたドメインに対して権威を持っていないことを示します。
    *   `!msg.recursion_available`: 応答を返したサーバが再帰的な問い合わせをサポートしていないことを示します。これは、通常、権威サーバの挙動です。
    *   `len(msg.answer) == 0`: Answerセクションに解決結果（IPアドレスなど）が含まれていないことを示します。
    *   `len(msg.extra) == 0`: Extraセクションにも追加情報が含まれていないことを示します。
    *   これらの条件がすべて真である場合、その応答は「lame referral」と判断されます。
*   **`lastErr = &DNSError{Err: "lame referral", Name: name, Server: server}`**:
    *   lame referralが検出された場合、`lastErr`変数に`"lame referral"`というエラー情報が設定されます。これは、デバッグやエラー報告のために役立ちます。
*   **`continue`**:
    *   この`continue`ステートメントが最も重要です。lame referral応答が検出された場合、現在のDNSサーバからの応答は無視され、`tryOneName`関数はループの次のイテレーションに進みます。これにより、設定されている次のDNSサーバへの問い合わせが試行され、名前解決のプロセスが続行されます。

### `src/net/dnsclient_unix_test.go`の変更

テストファイルでは、主に以下の変更が行われています。

1.  **`const TestAddr uint32 = 0xc0000201` の追加**:
    *   RFC 5737でドキュメント用に予約されているIPアドレスブロック`192.0.2.0/24`からテスト用アドレスが定義されました。これにより、テストのIPアドレスが実際のネットワークと衝突する可能性が低減されます。
2.  **`fakeDNSConn`から`fakeDNSDialer`への変更と構造体の再定義**:
    *   DNSのダイヤル処理をより正確にシミュレートするために、`fakeDNSConn`が`fakeDNSDialer`にリファクタリングされました。`fakeDNSDialer`は`dialDNS`メソッドを持ち、`fakeDNSConn`を返すようになりました。
    *   `fakeDNSConn`も変更され、`rh`（reply handler）関数が`s string, q *dnsMsg`という引数を受け取るようになり、どのサーバからの問い合わせかを識別できるようになりました。これにより、テスト内で異なるDNSサーバからの応答をシミュレートする柔軟性が向上しました。
3.  **`TestIgnoreLameReferrals`テストケースの追加**:
    *   この新しいテストケースは、lame referral応答をシミュレートし、Goリゾルバがそれを正しく無視して次のDNSサーバにフォールバックすることを確認します。
    *   `conf.writeAndUpdate([]string{"nameserver 192.0.2.1", "nameserver 192.0.2.2"})`で、2つのネームサーバが設定されます。
    *   `fakeDNSDialer`の`rh`関数は、`192.0.2.1:53`からの問い合わせに対してはlame referral応答（`response: true`, `authoritative: false`, `recursion_available: false`, `answer: []`, `extra: []`）を返し、`192.0.2.2:53`からの問い合わせに対しては有効なAレコード応答を返すように設定されています。
    *   テストは`www.golang.org`の名前解決を試み、最終的に`192.0.2.1`というIPアドレスが返されることを期待します。これは、最初のサーバ（`192.0.2.1`）からのlame referral応答が無視され、2番目のサーバ（`192.0.2.2`）からの有効な応答が使用されたことを意味します。

これらの変更により、GoのDNSリゾルバは、lame referralのような不適切なDNS応答に対してより堅牢になり、`libresolv`と同様の信頼性の高い名前解決挙動を提供するようになりました。

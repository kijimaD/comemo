# [インデックス 27000] ファイルの概要

`src/runtime/mgc.go` は、Go言語のランタイムにおけるガベージコレクション (GC) の主要なロジックが実装されているファイルです。GoのGCは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省くことで、生産性と安全性を向上させます。このファイルには、GCの開始、マークフェーズ、スイープフェーズ、および関連する補助機能や状態管理が含まれています。

## コミット

```
runtime: fix checkmark scanning of finalizers

Currently work.finalizersDone is reset only at the beginning of
gcStart. As a result, it will be set when checkmark runs, so checkmark
will skip scanning finalizers. Hence, if there are any bugs that cause
the regular scan of finalizers to miss pointers, checkmark will also
miss them and fail to detect the missed pointer.

Fix this by resetting finalizersDone in gcResetMarkState. This way it
gets reset before any full mark, which is exactly what we want.
```

## 元コミット内容

このコミットは、Goランタイムのガベージコレクタにおけるファイナライザのスキャンに関するバグを修正するものです。具体的には、`work.finalizersDone`という内部フラグのリセットタイミングが不適切であったため、GCの整合性チェック機構である「チェックマーク」がファイナライザのスキャンをスキップしてしまう問題に対処しています。これにより、通常のファイナライザスキャンでポインタの見落としバグが発生した場合でも、チェックマークがそれを検出できないという潜在的なリスクがありました。修正は、`work.finalizersDone`のリセットを`gcStart`から`gcResetMarkState`に移動することで行われ、これによりフルマークの前に確実にフラグがリセットされるようになります。

## 変更の背景

Goのガベージコレクタは、メモリの安全性を確保し、メモリリークを防ぐための重要なコンポーネントです。その中でも、ファイナライザは、GoのGCが直接管理しない外部リソース（C言語で確保されたメモリ、ファイルディスクリプタ、ネットワーク接続など）を解放するために使用されるメカニズムです。`runtime.SetFinalizer`関数を使ってオブジェクトにファイナライザを設定すると、そのオブジェクトがGCによって到達不可能と判断された後に、指定された関数が実行されます。

このコミット以前は、`work.finalizersDone`という内部フラグが`gcStart`関数の開始時にのみリセットされていました。このフラグは、ファイナライザの処理が完了したかどうかを示すもので、GCの「チェックマーク」フェーズにおいて重要な役割を果たします。チェックマークは、GCが正しく動作しているか、特にすべての到達可能なオブジェクトをマークし、ポインタを見落としていないかを検証するための整合性チェック機構です。

問題は、`work.finalizersDone`が`gcStart`でリセットされると、GCサイクル中にこのフラグが`true`に設定されたままになる可能性があったことです。その結果、チェックマークが実行される際に`work.finalizersDone`が`true`であると、チェックマークはファイナライザのスキャンをスキップしてしまいます。これは、もし通常のファイナライザスキャンにポインタの見落としなどのバグがあった場合、チェックマークがそのバグを検出できず、GCの整合性が損なわれるリスクがあることを意味します。GCのバグは非常に深刻であり、メモリ破損やクラッシュにつながる可能性があるため、このような潜在的な問題は早急に修正する必要がありました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、並行（Concurrent）かつ低遅延（Low-latency）な三色マーク＆スイープアルゴリズムを採用しています。これは、プログラムの実行と並行してGC処理の大部分を実行することで、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。

*   **三色マーク＆スイープ**: オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みかつ参照先も訪問済み）」の3色に分類し、到達可能なオブジェクトをマークし、到達不可能なオブジェクトをスイープ（解放）します。
*   **STWフェーズ**: GCの開始時（マークセットアップ）と終了時（マークターミネーション）には、ごく短いSTWフェーズが存在し、この間はすべてのGoルーチンが一時停止します。

### ファイナライザ (Finalizers)

Goのファイナライザは、`runtime.SetFinalizer(obj, finalizerFunc)` を用いて設定されます。

*   **目的**: GoのGCが直接管理しない外部リソース（C言語のライブラリで確保したメモリ、ファイルハンドル、ネットワークソケットなど）を、Goのオブジェクトが不要になったときに解放するために使用されます。
*   **動作原理**: `SetFinalizer`でファイナライザが設定されたオブジェクトがGCによって到達不可能と判断されると、そのオブジェクトは「ファイナライザキュー」に入れられます。その後、専用のGoルーチンがこのキューからファイナライザを取り出し、実行します。
*   **注意点**:
    *   **実行タイミングの非保証**: ファイナライザはGCサイクルの一部として実行されるため、いつ実行されるかは保証されません。プログラム終了前に実行されない可能性もあります。
    *   **GCサイクルへの影響**: ファイナライザが実行されるまで、そのオブジェクトのメモリは解放されません。また、ファイナライザ内でオブジェクトへの新しい参照が作成されると、そのオブジェクトは再び到達可能と見なされ、次のGCサイクルまでメモリが解放されない可能性があります。
    *   **`runtime.AddCleanup`**: Go 1.24以降では、`runtime.AddCleanup`が導入され、`SetFinalizer`のいくつかの制限（実行タイミングの不確実性、複数のクリーンアップ関数の設定不可など）を改善する代替手段として提供されています。

### `gcStart`

`gcStart`関数は、Goランタイム内でガベージコレクションサイクルを開始するための内部関数です。GCの状態を遷移させ、マークフェーズの準備を行います。

### `gcResetMarkState`

`gcResetMarkState`関数は、新しいGCマークフェーズの準備として、GCの内部状態をリセットする内部関数です。これには、各Goルーチンのスタックを再スキャンするためのフラグのリセットや、GCアシスト（GoルーチンがGCを手伝うメカニズム）のカウンタのリセットなどが含まれます。この関数は、GCの並行フェーズ中に呼び出されることもあります。

### `work.finalizersDone`

`work.finalizersDone`は、GoランタイムのGC内部で使用されるブール型のフラグです。このフラグは、現在のGCサイクルにおいてファイナライザの処理が完了したかどうかを示します。GCがファイナライザを持つオブジェクトを処理し終えると、このフラグが`true`に設定されると考えられます。

### チェックマーク (Checkmark)

チェックマークは、GoのGCにおけるデバッグおよび整合性検証のメカニズムです。GCが正しく動作し、到達可能なオブジェクトをすべてマークしていることを確認するために、GCのマークフェーズの後に実行されることがあります。これは、GCアルゴリズム自体のバグや、ポインタの誤った扱いによるメモリ破損を防ぐための重要な安全策です。チェックマークは、GCがポインタを見落としていないかを再確認することで、GCの信頼性を高めます。

## 技術的詳細

このコミットが修正しようとしている問題は、`work.finalizersDone`フラグのリセットタイミングが、GCの整合性チェック機構である「チェックマーク」の動作に悪影響を与えていた点にあります。

1.  **不適切なリセットタイミング**: 以前のコードでは、`work.finalizersDone`は`gcStart`関数の冒頭でのみ`false`にリセットされていました。`gcStart`はGCサイクルを開始する関数ですが、GCサイクルは複数のフェーズから構成され、その間に`work.finalizersDone`が`true`に設定される可能性があります。
2.  **チェックマークのスキップ**: GoのGCには、デバッグや検証のために「チェックマーク」と呼ばれるフェーズが存在します。これは、GCが正しく動作しているか、特に到達可能なすべてのオブジェクトをマークし、ポインタを見落としていないかを検証するためのものです。このチェックマークのロジックは、`work.finalizersDone`フラグを参照し、このフラグが`true`である場合、ファイナライザのスキャンをスキップするように設計されていました。これは、ファイナライザの処理が既に完了していると仮定していたためです。
3.  **潜在的なバグの見落とし**: 上記の2つの要因が組み合わさると、以下のような問題が発生します。
    *   GCサイクル中に`work.finalizersDone`が`true`に設定されたままになる。
    *   その状態でチェックマークが実行されると、ファイナライザのスキャンがスキップされる。
    *   もし、通常のファイナライザスキャンロジックにポインタの見落としなどのバグがあったとしても、チェックマークはそのバグを検出できません。なぜなら、チェックマーク自体がファイナライザ領域を検証しないためです。
    *   これにより、GCの整合性に関する深刻なバグが未検出のまま残り、メモリ破損や予期せぬクラッシュにつながる可能性がありました。

4.  **修正の論理**: この問題を解決するため、`work.finalizersDone`のリセットタイミングが`gcResetMarkState`関数に移動されました。
    *   `gcResetMarkState`は、GCのマークフェーズが開始される前に、GCの内部状態をリセットするために呼び出される関数です。
    *   この関数で`work.finalizersDone`を`false`にリセットすることで、GCの「フルマーク」（完全なマークフェーズ）が開始される前に、ファイナライザの処理が未完了の状態に確実に設定されます。
    *   これにより、チェックマークが実行される際には`work.finalizersDone`が常に`false`となり、ファイナライザのスキャンをスキップすることなく、その領域のポインタの整合性も検証できるようになります。結果として、GCの信頼性とデバッグ能力が向上します。

この変更は、GoランタイムのGCの堅牢性を高め、潜在的なメモリ関連のバグを早期に検出できるようにするための重要な修正です。

## コアとなるコードの解説

このコミットの核心は、`work.finalizersDone`というフラグのリセットタイミングの変更です。

*   **`gcStart`からの削除**:
    `gcStart`はGCサイクルを開始する関数ですが、この関数が呼び出された後、マークフェーズが実際に開始されるまでに、`work.finalizersDone`が`true`に設定される可能性がありました。これは、GCの並行処理の性質上、GCの開始とマークフェーズの準備が完全に同期しているわけではないためです。`gcStart`でリセットしても、その後の処理で再び`true`になる可能性があり、チェックマークが実行される時点での状態が保証されませんでした。

*   **`gcResetMarkState`への移動**:
    `gcResetMarkState`は、GCのマークフェーズが実際に開始される直前に、GCの内部状態を「クリーン」な状態にリセットするために設計された関数です。この関数は、新しいマークフェーズの準備として、すべての関連するフラグやカウンタを初期化します。
    `work.finalizersDone = false`を`gcResetMarkState`に移動することで、以下の重要な保証が得られます。
    1.  **フルマーク前の確実なリセット**: `gcResetMarkState`は、GCの「フルマーク」（オブジェクトの到達可能性を完全に判断するマークフェーズ）が開始される前に必ず呼び出されます。したがって、この時点で`work.finalizersDone`を`false`に設定することで、マークフェーズ全体を通じて、ファイナライザの処理が未完了であるという正しい状態が維持されます。
    2.  **チェックマークの完全な動作**: チェックマークが実行される際には、`work.finalizersDone`が確実に`false`であるため、ファイナライザのスキャンをスキップすることなく、その領域のポインタの整合性も検証できるようになります。これにより、ファイナライザに関連するポインタの見落としバグもチェックマークによって検出可能となり、GCのデバッグと信頼性が大幅に向上します。

この変更は、GoのGCの内部的な状態管理の正確性を高め、特にデバッグや整合性チェックのメカニズムが意図通りに機能することを保証するための、非常に重要かつ巧妙な修正と言えます。

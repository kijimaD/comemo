## 変更の背景

この変更が行われた2009年当時、Go言語はまだ開発の初期段階にあり、ビルドシステムは現在よりも多くのシェルスクリプトに依存していました。`quietgcc.bash` は、Goのコンパイラやその他のツールがCコードをコンパイルするためにGCCを呼び出す際に、そのコマンドライン引数を調整し、特定の警告を抑制する役割を担っていました。

問題は、このスクリプトがGCCを呼び出す際に、常に `-m64` フラグを付加していたことにありました。`-m64` フラグは、GCCに対して64ビットアーキテクチャ用のコードを生成するように指示するものです。しかし、32ビットのオペレーティングシステムやハードウェア上でGoをビルドしようとすると、この `-m64` フラグが問題を引き起こしました。32ビットシステムでは64ビットコードを生成できないため、GCCはエラーを発生させ、ビルドが失敗していました。

このコミットは、`quietgcc.bash` が実行されているマシンのアーキテクチャを検出し、それが64ビットマシンである場合にのみ `-m64` フラグを追加するように修正することで、この問題を解決しました。これにより、Goのビルドプロセスが32ビット環境でも正しく動作するようになりました。

## 前提知識の解説

*   **Go言語のビルドシステム**: Go言語は、その初期からセルフホスト型コンパイラを目指していましたが、初期のバージョンではC言語で書かれた部分（特にランタイムや一部のツール）をコンパイルするためにGCCのような既存のCコンパイラに依存していました。`quietgcc.bash` のようなスクリプトは、このCコンパイルプロセスを管理し、Goのビルド要件に合わせて調整するために使用されていました。
*   **GCC (GNU Compiler Collection)**: C、C++、Goなど、多くのプログラミング言語をサポートするフリーのコンパイラシステムです。Goの初期のビルドでは、Cコード部分のコンパイルにGCCが利用されていました。
*   **`-m64` フラグ**: GCCのコンパイルオプションの一つで、コンパイラに64ビットアーキテクチャ（x86-64、AMD64など）向けのコードを生成するように指示します。これに対し、32ビットアーキテクチャ向けのコードを生成する場合は `-m32` フラグを使用します。
*   **32ビットと64ビットアーキテクチャ**:
    *   **32ビットシステム**: CPUが32ビット幅のレジスタとメモリアドレスを使用します。これにより、最大で2^32バイト（約4GB）のメモリしか直接アドレス指定できません。
    *   **64ビットシステム**: CPUが64ビット幅のレジスタとメモリアドレスを使用します。これにより、理論上はるかに大きなメモリ空間（2^64バイト）をアドレス指定でき、より大きなデータセットや高性能なアプリケーションに適しています。
    *   コンパイラが生成するコードは、ターゲットとするアーキテクチャに適合している必要があります。32ビットシステムで64ビットコードをコンパイルしようとすると、通常はエラーになります。
*   **`uname` コマンド**: Unix系オペレーティングシステムでシステム情報を表示するコマンドです。
    *   `uname -a`: すべてのシステム情報を表示します。
    *   `uname -m`: マシン（ハードウェア）のアーキテクチャを表示します（例: `x86_64`, `i686`）。
    *   `uname -p`: プロセッサのタイプを表示します（例: `x86_64`, `i686`）。
*   **シェルスクリプト (Bash)**: Unix系システムでコマンドを実行するためのスクリプト言語です。このコミットでは、Bashスクリプトの条件分岐 (`case` 文) と変数操作が使われています。

## 技術的詳細

変更前の `quietgcc.bash` スクリプトは、GCCを呼び出す際に、常に以下の行で `-m64` フラグを渡していました。

```bash
$gcc -m64 -Wall -Wno-sign-compare ...
```

これは、スクリプトが実行されている環境が64ビットであるかどうかに関わらず、GCCに64ビットコードの生成を強制していました。その結果、32ビットシステム上でこのスクリプトが実行されると、GCCは「64ビットコードを生成できない」という旨のエラーを返し、Goのビルドプロセスが中断していました。

このコミットでは、この問題を解決するために、スクリプトの実行環境が64ビットアーキテクチャであるかどうかを動的に判定するロジックが追加されました。具体的には、`uname -m -p` コマンドの出力を使用して、システムが `x86_64` または `amd64` のいずれかであるかをチェックします。

```bash
# If this is a 64-bit machine, compile 64-bit versions of
# the host tools, to match the native ptrace.
case "`uname -m -p`" in
*x86_64* | *amd64*)
    gcc="$gcc -m64"
esac
```

この `case` 文により、システムが64ビットアーキテクチャであると判断された場合にのみ、`$gcc` 変数に `-m64` フラグが追加されます。その後、GCCの呼び出し部分では、この `$gcc` 変数が使用されるため、32ビットシステムでは `-m64` フラグが渡されなくなり、64ビットシステムでは引き続き渡されるようになります。

```bash
-$gcc -m64 -Wall -Wno-sign-compare \\\
+$gcc -Wall -Wno-sign-compare -Wno-missing-braces \\\
```

これにより、`quietgcc.bash` は異なるアーキテクチャのシステムに対してより柔軟に対応できるようになり、Goのビルドのポータビリティが向上しました。

## コアとなるコードの解説

1.  **新しい条件分岐の追加**:
    ```bash
    +# If this is a 64-bit machine, compile 64-bit versions of
    +# the host tools, to match the native ptrace.
    +case "`uname -m -p`" in
    +*x86_64* | *amd64*)
    +    gcc="$gcc -m64"
    +esac
    ```
    このブロックが新たに追加されました。
    *   `uname -m -p`: 現在のシステムのマシンハードウェア名 (`-m`) とプロセッサタイプ (`-p`) を出力します。例えば、64ビットLinuxシステムでは `x86_64 x86_64` のような出力が期待されます。
    *   `case ... in ... esac`: シェルスクリプトの条件分岐構文です。`uname -m -p` の出力が `*x86_64*` または `*amd64*` のパターンにマッチする場合（つまり、システムが64ビットアーキテクチャである場合）、次の行が実行されます。
    *   `gcc="$gcc -m64"`: `$gcc` 変数に、既存の値に加えて `-m64` フラグを追加します。これにより、`$gcc` は `gcc -m64` のような文字列になります。32ビットシステムの場合、このブロックはスキップされるため、`$gcc` は元の値（通常は単に `gcc` コマンドへのパス）のままです。

2.  **GCC呼び出し部分の変更**:
    ```diff
    -$gcc -m64 -Wall -Wno-sign-compare -Wno-missing-braces \\\
    +$gcc -Wall -Wno-sign-compare -Wno-missing-braces \\\
    ```
    この部分が変更されました。
    *   変更前は、`$gcc` 変数に加えて、明示的に `-m64` フラグがハードコードされていました。
    *   変更後は、ハードコードされていた `-m64` フラグが削除されました。これにより、GCCに渡される `-m64` フラグは、上記の新しい条件分岐で `$gcc` 変数に追加されたもののみになります。結果として、32ビットシステムでは `-m64` が渡されなくなり、64ビットシステムでは引き続き渡されるようになります。

この変更により、`quietgcc.bash` は実行環境のアーキテクチャに動的に適応し、32ビットシステムでのビルドエラーを防ぐことができるようになりました。

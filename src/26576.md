## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、Phi関数のリライト処理を改善するコミットです。

主な変更点は以下の通りです。

- Phi関数は可変長の引数を持つことができますが、`rulegen`ツールは各オペレーションが固定数の引数を持つと仮定していました。この仮定を修正します。
- 以下の例のようなケースを処理するために、Phi関数のリライトが必要でした。

```go
func f1_ssa(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x|v
}
```

この関数では、`v`の値が`if`と`else`のどちらのパスを通っても`-1`になります。SSA形式では、このような分岐の合流点でPhi関数が導入されますが、両方の入力が同じ定数である場合、Phi関数自体をその定数に簡略化できるはずです。このコミットは、このような最適化を可能にするための変更を含んでいます。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式を使用しています。SSA形式では、変数は一度だけ代入され、複数の制御フローパスが合流する点では「Phi関数」が導入されます。Phi関数は、どのパスから来たかに応じて適切な値を選択する役割を果たします。

このコミット以前のGoコンパイラのSSAバックエンドでは、`rulegen`というツールがSSAオペレーションのリライトルールを生成していました。しかし、この`rulegen`は、すべてのSSAオペレーションが固定数の引数を持つという誤った仮定に基づいていました。

問題となったのは`Phi`オペレーションです。`Phi`オペレーションは、合流する制御フローパスの数に応じて可変数の引数を取ります。例えば、2つのパスが合流する場合は2つの引数を、3つのパスが合流する場合は3つの引数を取ります。`rulegen`のこの仮定のため、Phi関数に対するリライトルールを適切に生成・適用することができませんでした。

コミットメッセージに示されている例：

```go
func f1_ssa(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x|v
}
```

このコードでは、`v`は`if`ブロックでも`else`ブロックでも`-1`に設定されます。SSA形式に変換されると、`if`と`else`のブロックの後に`v`の値を決定するためにPhi関数が導入されます。このPhi関数は、両方の入力が同じ定数`-1`であるため、それ自体を`-1`という定数に簡略化できるはずです。このような定数伝播の最適化は、コンパイラの性能にとって重要です。しかし、`rulegen`の制限により、この最適化が妨げられていました。

このコミットは、`rulegen`がPhi関数の可変長引数を正しく認識し、Phi関数に対するリライトルールを生成・適用できるようにすることで、このような最適化を可能にすることを目的としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式の主な特徴は以下の通りです。

- **単一代入**: 各変数はプログラム内で一度だけ代入されます。もし同じ変数名が複数回代入される場合、SSA形式では異なるバージョン（例: `x1`, `x2`, `x3`）として扱われます。
- **Phi関数 (Φ関数)**: 複数の制御フローパスが合流する点（例: `if-else`文の終わり、ループの終わり）で、同じ変数に対する異なるバージョンの値を結合するために導入されます。Phi関数は、どの制御フローパスから実行が来たかに応じて、適切なバージョンの値を選択します。例えば、`x3 = Φ(x1, x2)`というPhi関数は、「もしパス1から来たなら`x1`を、パス2から来たなら`x2`を`x3`とする」という意味を持ちます。Phi関数は、実際の実行時には存在しない概念であり、コンパイル時に解決されます。

SSA形式の利点は、データフロー解析と最適化を大幅に簡素化できる点にあります。変数の定義と使用の関係が明確になるため、定数伝播、共通部分式除去、デッドコード除去などの最適化が容易になります。

### 2. GoコンパイラのSSAバックエンド

Goコンパイラは、Go 1.7からSSAバックエンドを導入しました。これにより、生成されるコードの品質が向上し、コンパイル時間も短縮されました。GoコンパイラのSSAバックエンドは、ソースコードを抽象構文木（AST）から中間表現（IR）に変換し、そのIRをSSA形式に変換します。その後、SSA形式に対して様々な最適化パスを適用し、最終的に機械語コードを生成します。

### 3. `rulegen`ツール

`rulegen`は、GoコンパイラのSSAバックエンドで使用されるコード生成ツールです。これは、SSAオペレーションに対するリライトルール（最適化ルール）を記述した`.rules`ファイル（例: `generic.rules`）を読み込み、それらのルールをGoのソースコード（例: `rewritegeneric.go`）に変換します。この生成されたコードは、SSA形式の値を走査し、パターンマッチングによって最適化ルールを適用します。

リライトルールは通常、`パターン -> 結果` の形式で記述されます。例えば、`(Add8 (Const8 [c]) (Const8 [d])) -> (Const8 [c+d])` のようなルールは、「2つの8ビット定数の加算は、その結果の定数に置き換えられる」という最適化を表します。

### 4. オペレーションの可変長引数

多くのSSAオペレーションは固定数の引数を持ちます（例: `Add`は2つの引数、`Neg`は1つの引数）。しかし、`Phi`オペレーションのように、そのセマンティクス上、可変数の引数を必要とするオペレーションも存在します。`rulegen`がこのような可変長引数を正しく扱えない場合、Phi関数に対する最適化ルールを記述しても、それがコンパイラに組み込まれるコードに正しく変換されないという問題が発生します。

## 技術的詳細

このコミットの技術的詳細は、主にGoコンパイラのSSAバックエンドにおける`Phi`オペレーションの扱いと、`rulegen`ツールの機能拡張に焦点を当てています。

### 1. `Phi`オペレーションの特性と`rulegen`の課題

前述の通り、`Phi`オペレーションは、複数の制御フローパスが合流する際に、それぞれのパスから来る値を選択するために使用されます。そのため、`Phi`オペレーションの引数の数は、合流するパスの数に依存し、可変となります。

しかし、`rulegen`ツールは、SSAオペレーションの引数の数が固定であるという前提で設計されていました。これは、リライトルールのパターンマッチングコードを生成する際に、オペレーションの引数にアクセスするコード（例: `v.Args[0]`, `v.Args[1]`) を固定的に生成するためです。`Phi`オペレーションに対してこの仮定が適用されると、`rulegen`はPhi関数の引数の数を正確に検証できず、結果としてPhi関数に対するリライトルールが正しく機能しないか、あるいはコンパイルエラーを引き起こす可能性がありました。

### 2. `opData`構造体への`variableLength`フィールドの追加

この問題を解決するため、`src/cmd/compile/internal/ssa/gen/main.go`の`opData`構造体に`variableLength bool`フィールドが追加されました。

```go
type opData struct {
	typ               string // default result type
	aux               string
	rematerializeable bool
	variableLength    bool // if true the operation has a variable number of arguments
}
```

このフィールドは、特定のSSAオペレーションが可変長引数を持つかどうかを示すフラグです。

### 3. `Phi`オペレーションの`variableLength`属性の設定

`src/cmd/compile/internal/ssa/gen/genericOps.go`では、`Phi`オペレーションの定義が更新され、`variableLength: true`が設定されました。

```go
// Data movement
-{name: "Phi"},  // select an argument based on which predecessor block we came from
+{name: "Phi", variableLength: true}, // select an argument based on which predecessor block we came from
{name: "Copy"}, // output = arg0
```

これにより、`rulegen`は`Phi`オペレーションが可変長引数を持つことを認識できるようになります。

### 4. `rulegen`における可変長引数の処理

`src/cmd/compile/internal/ssa/gen/rulegen.go`の`genMatch0`関数が修正され、`variableLength`フラグをチェックするロジックが追加されました。

```go
	variableLength := false
	for _, op := range genericOps {
		if op.name == s[0] {
			variableLength = op.variableLength
			break
		}
	}
	for _, op := range arch.ops {
		if op.name == s[0] {
			variableLength = op.variableLength
			break
		}
	}
	if variableLength {
		fmt.Fprintf(w, "if len(%s.Args) != %d {\\nbreak\\n}\\n", v, argnum)
	}
```

この変更により、`rulegen`は、可変長引数を持つオペレーション（`Phi`など）のリライトルールを生成する際に、そのオペレーションの引数の数がルールで指定された数と一致するかどうかを動的にチェックするコードを生成するようになります。これにより、`rulegen`が固定数の引数を仮定していた問題が解決されます。

### 5. `generic.rules`へのPhi簡略化ルールの追加

`src/cmd/compile/internal/ssa/gen/generic.rules`には、Phi関数の簡略化ルールが追加されました。

```
// basic phi simplifications
(Phi (Const8 [c]) (Const8 [d])) && int8(c) == int8(d) -> (Const8 [c])
(Phi (Const16 [c]) (Const16 [d])) && int16(c) == int16(d) -> (Const16 [c])
(Phi (Const32 [c]) (Const32 [d])) && int32(c) == int32(d) -> (Const32 [c])
(Phi (Const64 [c]) (Const64 [c])) -> (Const64 [c])
```

これらのルールは、Phi関数のすべての入力が同じ定数である場合に、Phi関数自体をその定数に置き換えることを目的としています。例えば、`(Phi (Const8 [c]) (Const8 [d])) && int8(c) == int8(d) -> (Const8 [c])` は、「もし8ビットのPhi関数の両方の入力が同じ定数`c`と`d`であり、かつ`c`と`d`が同じ値であるならば、そのPhi関数を定数`c`に置き換える」という意味です。これにより、コンパイラは冗長なPhi関数を削除し、より効率的なコードを生成できるようになります。

### 6. `rewritegeneric.go`への`OpPhi`リライト関数の追加

`src/cmd/compile/internal/ssa/rewritegeneric.go`には、`rewriteValuegeneric_OpPhi`関数が追加され、`OpPhi`オペレーションに対するリライトロジックが実装されました。

```go
func rewriteValuegeneric_OpPhi(v *Value, config *Config) bool {
	b := v.Block
	_ = b
	// match: (Phi (Const8 [c]) (Const8 [d]))
	// cond: int8(c) == int8(d)
	// result: (Const8 [c])
	for {
		if v.Args[0].Op != OpConst8 {
			break
		}
		c := v.Args[0].AuxInt
		if v.Args[1].Op != OpConst8 {
			break
		}
		d := v.Args[1].AuxInt
		if len(v.Args) != 2 { // This check is crucial for variableLength ops
			break
		}
		if !(int8(c) == int8(d)) {
			break
		}
		v.reset(OpConst8)
		v.AuxInt = c
		return true
	}
	// ... similar rules for Const16, Const32, Const64
	return false
}
```

この関数は、`generic.rules`で定義されたPhi簡略化ルールに対応するGoコードです。`rulegen`によって生成されるコードの一部であり、SSA値の走査中に`OpPhi`に遭遇した場合に、定義されたパターンにマッチするかどうかをチェックし、マッチすればリライトを実行します。特に注目すべきは、`len(v.Args) != 2`のような引数の数をチェックする条件が追加されている点です。これは、`rulegen`が可変長引数を考慮して生成したコードであり、Phi関数の引数の数がルールに合致するかを検証するために重要です。

### 7. テストケースの追加

`src/cmd/compile/internal/gc/testdata/arith_ssa.go`には、`orPhi_ssa`関数と`testOrPhi`関数が追加されました。

```go
//go:noinline
func orPhi_ssa(a bool, x int) int {
	v := 0
	if a {
		v = -1
	} else {
		v = -1
	}
	return x | v
}

func testOrPhi() {
	if want, got := -1, orPhi_ssa(true, 4); got != want {
		println("orPhi_ssa(true, 4)=", got, " want ", want)
	}
	if want, got := -1, orPhi_ssa(false, 0); got != want {
		println("orPhi_ssa(false, 0)=", got, " want ", want)
	}
}
```

この`orPhi_ssa`関数は、コミットメッセージで例示されたシナリオを具体化したものです。`v`の値が常に`-1`になるため、SSA形式に変換された際にPhi関数が導入され、そのPhi関数が`-1`という定数に簡略化されることを期待しています。このテストケースは、今回の変更によってPhi関数のリライトが正しく機能することを確認するために追加されました。

これらの変更により、GoコンパイラはPhi関数をより効果的に最適化できるようになり、結果として生成されるコードの効率が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/gen/main.go`

これらのファイルへの変更は、`Phi`オペレーションが可変長引数を持つという事実をコンパイラのメタデータに明示的に記録するためのものです。`opData`構造体に`variableLength`フィールドを追加し、`Phi`オペレーションの定義でこれを`true`に設定することで、`rulegen`ツールがこの特性を認識できるようになります。これは、`rulegen`がリライトルールを生成する際の前提条件を修正する、基盤となる変更です。

### `src/cmd/compile/internal/ssa/gen/rulegen.go`

`genMatch0`関数内の変更は、`rulegen`がリライトルールをGoコードに変換する際の挙動を修正します。以前は、すべてのオペレーションが固定数の引数を持つと仮定していましたが、この変更により、`variableLength`フラグが`true`のオペレーションに対しては、生成されるコードに`len(v.Args) != argnum`のようなチェックが追加されます。これにより、リライトルールが適用される際に、Phi関数の実際の引数の数がルールで期待される数と一致するかどうかが実行時に検証されるようになり、より堅牢なリライト処理が可能になります。

### `src/cmd/compile/internal/ssa/gen/generic.rules`

追加されたPhi簡略化ルールは、定数伝播最適化の具体的な実装です。例えば、`(Phi (Const8 [c]) (Const8 [d])) && int8(c) == int8(d) -> (Const8 [c])`というルールは、8ビットのPhi関数が、両方の入力として同じ定数`c`と`d`（ただし`c == d`）を受け取る場合に、そのPhi関数を単一の定数`c`に置き換えることを指示します。これは、コンパイラが冗長な計算やデータ移動を排除し、より効率的な機械語コードを生成するための重要なステップです。同様のルールが16ビット、32ビット、64ビットの整数型に対しても追加されています。

### `src/cmd/compile/internal/ssa/rewritegeneric.go`

このファイルに追加された`rewriteValuegeneric_OpPhi`関数は、`generic.rules`で定義されたPhi簡略化ルールを実際に適用するGoコードです。`rulegen`によって生成されるコードの一部として、SSAグラフを走査する際に`OpPhi`オペレーションに遭遇するとこの関数が呼び出されます。関数内では、Phi関数の引数が定数であるか、そしてそれらの定数が同じ値であるかといった条件がチェックされます。条件が満たされた場合、Phiオペレーションは対応する単一の定数オペレーションに`v.reset()`によって置き換えられ、最適化が実行されます。この関数は、`rulegen`が生成するパターンマッチングとリライトのロジックの具体的な例を示しています。

### `src/cmd/compile/internal/gc/testdata/arith_ssa.go`

追加されたテストケースは、今回の変更が意図通りに機能することを確認するためのものです。`orPhi_ssa`関数は、`if-else`分岐のどちらのパスを通っても同じ定数`-1`が変数`v`に代入されるというシナリオを再現しています。このコードがSSA形式に変換されると、`v`の値を結合するためにPhi関数が導入されますが、今回の変更によってこのPhi関数が`-1`という定数に簡略化されるはずです。`testOrPhi`関数は、この最適化が正しく行われた結果、期待される値が返されることをアサートします。これにより、コンパイラの変更が正しく動作し、コードの最適化に貢献していることが検証されます。

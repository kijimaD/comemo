## 元コミット内容

runtime: fix heapBitsSweepSpan comment

Currently the heapBitsSweepSpan comment claims that heapBitsSweepSpan
sets the heap bitmap for the first two words to dead. In fact, it sets
the first *four* words to scalar/dead. This is important because first
two words don't actually have a dead bit, so for objects larger than
two words it *must* set a dead bit in third word to reset the object
to a "noscan" state. For example, we use this in heapBits.hasPointers
to detect that an object larger than two words is noscan.

## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理、特にガベージコレクション（GC）の動作に関する既存のコメントが、実際のコードの振る舞いと一致していなかったという問題があります。`src/runtime/mbitmap.go`ファイル内の`heapBitsSweepSpan`関数のコメントは、GCのスイープフェーズ中に解放されたオブジェクトのヒープビットマップがどのように更新されるかを説明していました。しかし、このコメントは、オブジェクトの最初の2ワードのみが`typeDead`としてマークされると誤って記述していました。

実際には、`heapBitsSweepSpan`は最初の4ワードを`scalar/dead`としてマークしていました。この不一致は、Goランタイムの内部動作を理解しようとする開発者にとって混乱を招く可能性がありました。特に、GoのGCはヒープビットマップを利用して、オブジェクトがポインタを含むかどうか（スキャンする必要があるか）を判断するため、この情報は非常に重要です。オブジェクトが「noscan」状態（ポインタを含まないためGCスキャンが不要）であると正しく識別されるためには、特定のビットが設定されている必要があります。コミットメッセージが指摘するように、2ワードを超えるオブジェクトの場合、3番目のワードに「dead bit」を設定することが「noscan」状態にリセットするために不可欠でした。

このコメントの修正は、ドキュメントがコードの実際の動作を正確に反映するようにし、Goランタイムのメモリ管理の複雑な側面に関する理解を深めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの前提知識が必要です。

1.  **Goランタイムのメモリ管理とガベージコレクション (GC)**:
    Goは、並行（concurrent）かつ三色（tri-color）マーク＆スイープ方式のガベージコレクタを採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ (Mark Phase)**: プログラムのルート（グローバル変数やゴルーチンのスタックなど）から到達可能なすべてのオブジェクトを「ライブ（生存）」としてマークします。オブジェクトは通常、白（未訪問、回収候補）、灰色（到達可能だが子をスキャンしていない）、黒（完全にスキャン済み）の三色に分類されます。
    *   **スイープフェーズ (Sweep Phase)**: マークフェーズで「ライブ」とマークされなかったオブジェクト（つまり「白」のままのオブジェクト）のメモリを回収し、ヒープに再利用可能な領域として返します。Goのスイープフェーズは、ほとんどが並行して動作し、アプリケーションの実行を妨げません。これは、メモリを小さなスパン（後述）単位で、必要に応じて、またはバックグラウンドで処理することで実現されます。

2.  **ヒープビットマップ (Heap Bitmap)**:
    Goランタイムは、ヒープ上のオブジェクトに関するメタデータを追跡するためにヒープビットマップを使用します。このビットマップは、メモリのどの部分がポインタを含み、どの部分がスカラーデータ（ポインタではないデータ）を含むかをGCが識別するために不可欠です。これにより、GCはオブジェクトグラフを正確に辿り、到達可能なオブジェクトをマークできます。
    *   歴史的に、ヒープビットマップはヒープ内の各ポインタサイズのワードに対して1ビットを使用していましたが、最近では各ポインタサイズのワードに対して2ビットを使用し、`heapArena`メタデータに格納されています。
    *   Go 1.22では、GCのCPU効率を向上させ、メモリオーバーヘッドを削減するためにアロケーションヘッダが導入されました。ポインタを含むオブジェクトの場合、8バイトのアロケーションヘッダがそのオブジェクトの型情報へのポインタを持ち、GCの局所性を向上させます。

3.  **`heapBits` と `heapBitsSweepSpan`**:
    *   `heapBits`は、ヒープビットマップの情報を表現する構造体です。
    *   `heapBitsSweepSpan`は、スイープフェーズに関連する内部ランタイム関数です。Goのメモリ管理における「スパン（span）」は、連続したメモリページの領域を指します。この関数は、特定のメモリ「スパン」のスイープを調整し、対応するヒープビットマップエントリを読み取り、更新します。具体的には、スパン内の解放されたオブジェクトに対して、そのヒープビットマップエントリを更新し、次のGCサイクルに備えてマークビットをクリアします。

4.  **`typeDead` / `scalar/dead` / `noscan`**:
    これらは、GCがメモリを分類する方法に関連する用語です。
    *   **`scalar` (スカラー)**: ポインタを含まないデータ（整数、ブール値、ポインタ型を含まない構造体など）を指します。スカラーオブジェクトの場合、GCはポインタをスキャンする必要がないため、マーキングプロセスが簡素化されます。
    *   **`dead` (デッド)**: プログラムのルートから到達できなくなったオブジェクトを指します。到達不能になったオブジェクトは「デッド」と見なされ、ガベージコレクタによる回収の対象となります。
    *   **`typeDead` / `scalar/dead`**: 解放されたメモリが、もはやアクティブなオブジェクトではなく、ポインタを含まないことをGCに伝えるために使用される状態です。これにより、そのメモリ領域は「noscan」状態として扱われます。
    *   **`noscan`**: GCがポインタをスキャンする必要がないと認識している状態です。これはGCの最適化であり、スキャン不要なメモリ領域をスキップすることでGCの効率を向上させます。

## 技術的詳細

このコミットの技術的な核心は、`heapBitsSweepSpan`関数が解放されたオブジェクトのヒープビットマップをどのように更新するかに関する正確な記述です。

元のコメントでは、`heapBitsSweepSpan`が「最初の2ワード」の型ビットを`typeDead`に設定すると述べていました。しかし、実際の動作では「最初の4ワード」を`scalar/dead`に設定していました。この違いは、Goのヒープビットマップの内部構造と、オブジェクトの「noscan」状態の検出方法に深く関連しています。

コミットメッセージが説明するように、最初の2ワードには「dead bit」が実際に存在しません。これは、Goのヒープビットマップがオブジェクトのポインタ情報をエンコードする方法に起因します。オブジェクトが2ワードよりも大きい場合、そのオブジェクトを「noscan」状態にリセットするためには、*3番目のワード*に「dead bit」を設定することが不可欠です。これは、`heapBits.hasPointers`のような他のGCコンポーネションが、オブジェクトがポインタを含まない（したがってスキャン不要である）と判断するためにこのビットを利用しているためです。

したがって、`heapBitsSweepSpan`が最初の4ワードを`scalar/dead`としてマークするという事実は、単なるコメントの誤り以上の意味を持ちます。これは、Goランタイムが解放されたメモリを効率的かつ正確に「noscan」として分類し、GCが不要なスキャンを避けるための重要なメカニズムを反映しています。この修正により、Goランタイムのメモリ管理の内部ロジックがより明確になり、将来のデバッグや最適化の際に誤解が生じるリスクが低減されます。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、純粋にコメントの更新です。しかし、このコメントの更新は、Goランタイムのガベージコレクションにおける`heapBitsSweepSpan`関数の実際の動作を正確に反映させるために非常に重要です。

変更前は、コメントは「解放されたオブジェクトの最初の2ワード（または単一ワードオブジェクトの場合は1ワード）の型ビットを`typeDead`に設定する」と記述していました。これは、GCがオブジェクトを解放する際に、そのメモリ領域がもはやポインタを含まないことを示すために、ヒープビットマップを更新する方法を説明しようとしたものです。

変更後は、「解放されたオブジェクトの最初の4ワード（より小さいオブジェクトの場合はそれ以下）の型ビットを`scalar/dead`に設定する」と記述されています。この修正は、以下の点を明確にしています。

1.  **ワード数の変更**: 実際に`heapBitsSweepSpan`が操作するワードの数が2から4に増えました。これは、Goのヒープビットマップの内部表現や、オブジェクトの「noscan」状態を確実に設定するために必要な最小限のビット数に関する実装の詳細を反映しています。特に、コミットメッセージが指摘するように、最初の2ワードには「dead bit」が存在しないため、2ワードを超えるオブジェクトを「noscan」状態にリセットするには、3番目のワードに「dead bit」を設定する必要があるという事実を考慮しています。
2.  **用語の変更**: `typeDead`から`scalar/dead`への変更は、より正確な用語の使用を示唆しています。`scalar`はポインタを含まないデータを指し、`dead`は到達不能なオブジェクトを指すため、`scalar/dead`は「ポインタを含まず、かつ到達不能なオブジェクト」という状態をより明確に表現しています。これにより、GCがこのメモリ領域をスキャンする必要がない（noscan）という意図がより明確になります。

このコメントの修正は、コードの動作自体を変更するものではありませんが、Goランタイムのメモリ管理の複雑なロジックを理解する上で、ドキュメントの正確性を保証し、開発者が誤解する可能性を排除するために不可欠です。

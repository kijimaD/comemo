# [インデックス 20868] ファイルの概要

このコミットは、Go言語の標準ライブラリ `compress/gzip` パッケージにおいて、GZIPリーダーが最初のストリームの終端で停止できるようにする機能を追加します。これにより、複数のGZIPストリームが連結されたファイル（マルチストリームGZIPファイル）を扱う際に、個々のストリームを区別して処理する必要がある特定のファイル形式の解析が可能になります。

## 元コミット内容

`compress/gzip` パッケージにおいて、GZIPリーダーが最初のストリームの終端で停止できるようにする変更です。これは、データがどのストリームにあるかに特別な意味を持たせる一部のファイル形式を解析するために必要とされます。この変更は、`compress/bzip2` にも同様に適用される予定です。Issue #6486 を修正します。

## 変更の背景

GZIP形式は、複数のGZIP圧縮データストリームを連結することを許容しています。標準的なGZIPリーダーは、これらの連結されたストリームを透過的に処理し、あたかも単一の大きなデータストリームであるかのように振る舞います。しかし、一部のファイル形式やプロトコルでは、GZIPストリームの連結を利用して、各ストリームに特定の意味やメタデータを持たせることがあります。例えば、最初のストリームがヘッダー情報を含み、2番目以降のストリームが実際のデータを含む、といったケースです。

このような場合、標準的なGZIPリーダーの振る舞いでは、最初のストリームの終端で処理を停止し、そのストリームの内容だけを読み取ることができませんでした。このコミットは、この要件に対応するために、リーダーが最初のGZIPストリームの終端で明示的に停止する機能を提供します。これにより、アプリケーションは個々のGZIPストリームを独立した論理単位として扱い、それぞれのストリームに割り当てられた特別な意味を解釈できるようになります。

コミットメッセージにある `Fixes #6486` については、現在の環境では詳細な情報を取得できませんでしたが、この変更が特定のバグや機能不足を解消するものであることを示唆しています。

## 前提知識の解説

### GZIPファイル形式

GZIP (GNU Zip) は、データ圧縮のためのファイル形式であり、RFC 1952 で定義されています。GZIPファイルは通常、単一の圧縮データストリームを含みますが、仕様上は複数のGZIP圧縮データストリームを連結することが可能です。

*   **GZIPヘッダー**: 各GZIPストリームは、マジックナンバー、圧縮方式、フラグ、タイムスタンプ、OSタイプなどの情報を含むヘッダーで始まります。
*   **圧縮データ**: ヘッダーの後に、DEFLATEアルゴリズムによって圧縮されたデータが続きます。
*   **GZIPトレーラー**: データの終端には、CRC32チェックサムと元の（非圧縮）データのサイズを含むトレーラーがあります。

### マルチストリームGZIPファイル

複数のGZIP圧縮データストリームが単一のファイル内で連結されている場合、それを「マルチストリームGZIPファイル」と呼びます。例えば、`file1.gz` と `file2.gz` がある場合、`cat file1.gz file2.gz > combined.gz` のように連結された `combined.gz` はマルチストリームGZIPファイルとなります。

多くのGZIP解凍ツールやライブラリは、このマルチストリームの連結を透過的に処理します。つまり、最初のストリームの終端に達すると、自動的に次のストリームのヘッダーを探し、その解凍を続行します。これにより、ユーザーは連結されたファイルを単一の論理的なデータとして扱うことができます。

### `io.Reader` と `io.EOF`

Go言語の `io.Reader` インターフェースは、データの読み取り操作を抽象化します。`Read` メソッドは、データを読み取り、読み取ったバイト数とエラーを返します。データがこれ以上ない場合、`io.EOF` エラーを返します。通常、`io.EOF` は入力の終端に達したことを示しますが、このコミットの文脈では、GZIPストリームの論理的な終端を指すことになります。

## 技術的詳細

このコミットは、`src/compress/gzip/gunzip.go` にある `Reader` 型に `multistream` という新しいフィールドを追加し、その振る舞いを制御するための `Multistream` メソッドを導入します。

### `Reader` 構造体への `multistream` フィールドの追加

`Reader` 構造体は、GZIPデータを読み取るための状態を保持します。ここに `multistream bool` フィールドが追加されました。
```go
type Reader struct {
	flg          byte
	buf          [512]byte
	err          error
	multistream  bool // 新しく追加されたフィールド
}
```
このフィールドは、リーダーがマルチストリームGZIPファイルを透過的に処理するかどうかを制御します。デフォルトでは `true` に設定され、従来のマルチストリーム対応の振る舞いを維持します。

### `NewReader` および `Reset` での `multistream` の初期化

`NewReader` 関数と `Reset` メソッドは、`Reader` の新しいインスタンスを作成またはリセットする際に、`multistream` フィールドをデフォルトで `true` に設定します。これは、既存のコードとの互換性を保つためです。
```go
func NewReader(r io.Reader) (*Reader, error) {
	z := new(Reader)
	z.r = makeReader(r)
	z.multistream = true // ここでtrueに初期化
	z.digest = crc32.NewIEEE()
	if err := z.readHeader(true); err != nil {
		return nil, err
	}
	return z, nil
}

func (z *Reader) Reset(r io.Reader) error {
	// ...
	z.size = 0
	z.err = nil
	z.multistream = true // ここでもtrueに初期化
	return z.readHeader(true)
}
```

### `Multistream` メソッドの追加

新しい `Multistream(ok bool)` メソッドは、`Reader` の `multistream` フラグを設定するために提供されます。
```go
func (z *Reader) Multistream(ok bool) {
	z.multistream = ok
}
```
このメソッドを `Multistream(false)` と呼び出すことで、リーダーは単一のGZIPストリームの終端で `io.EOF` を返すように設定されます。

### `Read` メソッドの変更

`Read` メソッドは、GZIPデータを実際に解凍して読み取る主要なメソッドです。このメソッドに、`multistream` フラグをチェックするロジックが追加されました。
```go
func (z *Reader) Read(p []byte) (n int, err error) {
	// ... 既存の読み取りロジック ...

	// File is ok; is there another?
	if !z.multistream { // ここでmultistreamフラグをチェック
		return 0, io.EOF // falseの場合、現在のストリームの終端でio.EOFを返す
	}

	if err = z.readHeader(false); err != nil {
		z.err = err
		return
	}
	// ...
}
```
`multistream` が `false` に設定されている場合、現在のGZIPストリームのデータがすべて読み取られた後、`Read` メソッドは `io.EOF` を返して処理を終了します。これにより、呼び出し元は次のGZIPストリームが始まる前に、現在のストリームの終端を検出できます。

## コアとなるコードの解説

### `src/compress/gzip/gunzip.go` の変更点

1.  **`Reader` 構造体への `multistream` フィールド追加**:
    `Reader` 構造体に `multistream bool` フィールドが追加されました。これは、GZIPリーダーが複数の連結されたGZIPストリームを透過的に処理するかどうかを制御するためのフラグです。デフォルトの動作（マルチストリーム対応）を維持するために、`NewReader` および `Reset` メソッドで `true` に初期化されます。

2.  **`Multistream` メソッドの追加**:
    `func (z *Reader) Multistream(ok bool)` メソッドが追加されました。このメソッドは、`multistream` フラグの値を設定するために使用されます。`Multistream(false)` を呼び出すことで、リーダーは現在のGZIPストリームの終端で `io.EOF` を返すように設定され、次のストリームを自動的に読み進めることはなくなります。

3.  **`Read` メソッドのロジック変更**:
    `Read` メソッド内に、`multistream` フラグをチェックする条件が追加されました。
    ```go
    if !z.multistream {
        return 0, io.EOF
    }
    ```
    この変更により、`multistream` が `false` の場合、現在のGZIPストリームのデータがすべて読み取られた後（内部的に `readHeader` が次のヘッダーを読み込もうとする前）、`Read` は直ちに `0` バイトと `io.EOF` を返します。これにより、呼び出し元は単一のGZIPストリームの論理的な終端を正確に検出できるようになります。

### `src/compress/gzip/gunzip_test.go` の変更点

1.  **`TestMultistreamFalse` テスト関数の追加**:
    この新しいテスト関数は、`Multistream(false)` が正しく機能することを確認します。
    *   まず、連結されたGZIPデータ（`hello world\n` が2回繰り返されるデータ）をテストデータとして使用します。
    *   最初のストリームを読み取る前に `r.Multistream(false)` を呼び出し、リーダーが最初のストリームの終端で停止することを確認します。`ioutil.ReadAll(&r)` は最初の `hello world\n` のみを読み取り、その後 `io.EOF` が返されることを期待します。
    *   次に、`r.Reset(br)` を呼び出してリーダーをリセットし、再度 `r.Multistream(false)` を設定して、2番目のストリームを読み取ります。これも同様に `hello world\n` を読み取り、その後 `io.EOF` が返されることを期待します。
    *   最後に、もう一度 `r.Reset(br)` を呼び出した際に、これ以上ストリームがないため `io.EOF` が返されることを確認します。

このテストは、`Multistream(false)` が設定された場合に、GZIPリーダーが個々のストリームの境界を尊重し、それぞれのストリームの終端で `io.EOF` を返すという新しい振る舞いを検証しています。

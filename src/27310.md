# [インデックス 27310] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）内の到達不能なハッシュ衝突チェックを削除するものです。具体的には、`readsym`関数内に存在していた、`gclocals·`プレフィックスを持つシンボルに対するハッシュ衝突チェックのコードブロックが、論理的に決して真にならない条件に基づいていたため、削除されました。

## 元コミット内容

Goリンカの`readsym`関数内に、`gclocals·`プレフィックスを持つシンボルに対するハッシュ衝突をチェックするコードブロックが存在していました。しかし、このチェックの条件式 `dup != nil && len(dup.P) > 0 && strings.HasPrefix(s.Name, "gclocals·")` は、`dup != nil` が真である場合、`s.Name` が常に `".dup"` となるため、`strings.HasPrefix(s.Name, "gclocals·")` の部分が偽となり、結果としてこのブロック全体が実行されることはありませんでした。この論理的な欠陥はGo 1.4の時点から存在していたと指摘されています。

## 変更の背景

この変更の背景には、Goリンカのコードベースの健全性を維持し、到達不能なコードを削除するという目的があります。到達不能なコードは、デッドコードとして存在し続けることで、コードの可読性を低下させ、将来的なメンテナンスの際に混乱を招く可能性があります。また、誤ってそのコードが実行されるような変更が加えられた場合に、予期せぬバグを引き起こすリスクも排除できます。

この特定のケースでは、`readsym`関数内のハッシュ衝突チェックが、その条件式のために決して実行されないことが判明しました。`dup != nil` の場合、`s.Name` は常に `".dup"` となるというリンカの内部的な挙動が原因です。したがって、`gclocals·`で始まるシンボル名を持つ`s.Name`と同時に`dup != nil`が成立することはありえないため、このチェックは無意味でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部動作とリンカの概念について理解しておく必要があります。

*   **Goリンカ (`cmd/link`)**: Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。シンボルの解決、アドレスの割り当て、セクションの結合など、最終的な実行ファイルを構築する上で重要な役割を担います。
*   **シンボル (Symbol)**: プログラム内の関数、グローバル変数、静的変数など、名前を持つエンティティを識別するための情報です。リンカはこれらのシンボルを解決し、参照が正しいメモリ位置を指すようにします。
*   **`readsym` 関数**: リンカの処理過程で、オブジェクトファイルからシンボル情報を読み取る役割を担う関数です。この関数は、各シンボルの名前、型、サイズ、値などの情報を解析し、リンカの内部シンボルテーブルに格納します。
*   **`gclocals·` シンボル**: Goランタイムとガベージコレクタによって使用される特殊なシンボルです。これは、特定の関数のスタックフレームにおけるローカル変数のレイアウトに関するメタデータを含んでいます。特に、どのローカル変数がポインタであるかを示し、ガベージコレクタが正確にライブポインタを識別し、誤って回収されるのを防ぐために不可欠な情報です。このシンボル名は、通常 `gclocals·<関数名>` の形式を取ります。
*   **ハッシュ衝突 (Hash Collision)**: リンカはシンボルを効率的に検索するためにハッシュテーブルを使用することがよくあります。ハッシュ衝突とは、異なる2つのシンボルが同じハッシュ値を生成してしまう状況を指します。通常、ハッシュテーブルは衝突を解決するメカニズム（チェイニングやオープンアドレス法など）を持っていますが、予期せぬ衝突はリンカの誤動作やエラーを引き起こす可能性があります。
*   **`dup` と `s.Name` の関係**: Goリンカの内部では、シンボルを処理する際に、既存のシンボルとの重複（`dup`）を検出することがあります。このコミットの文脈では、`dup != nil` の場合、つまり重複するシンボルが見つかった場合、リンカは内部的にそのシンボル名を `".dup"` のような特殊な名前に変更して処理する挙動があったと推測されます。

## 技術的詳細

このコミットの核心は、Goリンカの`src/cmd/link/internal/ld/objfile.go`ファイル内の`readsym`関数における特定の条件式の誤りです。

問題のコードブロックは、`gclocals·`で始まるシンボル名を持つシンボルが重複した場合に、その内容（`s.P`と`dup.P`）が一致するかどうかをチェックし、一致しない場合はハッシュ衝突として致命的なエラーを報告するものでした。これは、`gclocals·`シンボルがガベージコレクションの正確性に直結する重要な情報であるため、その整合性を保証するための安全策として導入されたと考えられます。

しかし、コミットメッセージが指摘するように、このチェックの条件式は以下の通りでした。

```go
if len(s.P) > 0 && dup != nil && len(dup.P) > 0 && strings.HasPrefix(s.Name, "gclocals·") {
    // ... ハッシュ衝突チェック ...
}
```

ここで問題となるのは、`dup != nil` が真である場合、つまり`s`が既存のシンボル`dup`の重複として扱われる場合、リンカの内部ロジックによって`s.Name`が`".dup"`のような内部的な名前に変更されてしまうという挙動です。このため、`strings.HasPrefix(s.Name, "gclocals·")`という条件は、`dup != nil`が真である限り、常に偽となります。

結果として、この`if`ブロック内のハッシュ衝突チェックは、論理的に決して実行されることがない「到達不能なコード」となっていました。このコミットは、この到達不能なコードを特定し、削除することで、コードベースの無駄をなくし、保守性を向上させることを目的としています。

## コアとなるコードの解説

削除されたコードブロックは、`readsym`関数内でシンボル`s`を処理する際に、それが既存のシンボル`dup`と重複しているかどうかをチェックし、さらに`gclocals·`で始まる名前を持つ場合に、その内容が一致するかを確認するものでした。

*   `len(s.P) > 0 && dup != nil && len(dup.P) > 0`: これは、現在のシンボル`s`と重複シンボル`dup`の両方が実体（`P`フィールド）を持ち、かつ`dup`が存在する場合の条件です。
*   `strings.HasPrefix(s.Name, "gclocals·")`: これは、シンボル`s`の名前が`gclocals·`で始まるかどうかをチェックする条件です。`gclocals·`シンボルは、Goのガベージコレクションにおいて重要な役割を果たすため、その整合性は非常に重要です。
*   `if !bytes.Equal(s.P, dup.P)`: もし上記の条件が全て真であった場合、この内部の`if`文で`s`と`dup`の実際のデータ（`P`フィールド）がバイト単位で一致するかを比較していました。
*   `log.Fatalf("dupok hash collision for %s in %s and %s", s.Name, s.File, pn)`: もしデータが一致しなかった場合、これはハッシュ衝突と見なされ、リンカは致命的なエラーを発生させていました。

しかし、前述の通り、`dup != nil`が真である場合、`s.Name`は`".dup"`のような内部名に変わるため、`strings.HasPrefix(s.Name, "gclocals·")`は常に偽となり、このブロック全体が実行されることはありませんでした。したがって、このコードは機能的に無意味であり、削除されてもリンカの動作に影響はありません。

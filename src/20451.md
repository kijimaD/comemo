# [インデックス 20451] ファイルの概要

このコミットは、Goランタイムのスタック管理に関する重要な変更を`src/runtime/stack.c`ファイルに対して行っています。具体的には、`StackCopyAlways`という内部フラグの値を変更することで、特定の環境下で発生していたスタック関連の致命的なエラーを回避することを目的としています。

## コミット

このコミットは、Goランタイムにおけるスタックコピーの挙動を制御する`StackCopyAlways`フラグを無効化するものです。これは、Windows/amd64環境でのビルド失敗と、`syscall.Syscall`呼び出し中に発生する「split stack not allowed」という致命的なエラーに対応するための修正です。このエラーは、Goのスタック成長メカニズムがCGOを介したシステムコールと適切に連携できない場合に発生していました。

## 変更の背景

このコミットは、Goのビルドシステムで報告されたWindows/amd64環境での特定の失敗に対応するために行われました。提供されたビルドログのリンク（`http://build.golang.org/log/1ded5e3ef4bd1226f976e3180772f87e6c918255`）が示すように、`misc/cgo/testso`というテスト中にランタイムパニックが発生していました。

パニックの具体的なエラーメッセージは以下の通りです。
*   `runtime: copystack: locals size info only for syscall.Syscall`
*   `fatal error: split stack not allowed`

このエラーは、Goランタイムがスタックをコピーしようとした際に、`syscall.Syscall`のコンテキストで問題が発生したことを示唆しています。特に「split stack not allowed」というメッセージは、Goの動的なスタック成長メカニズム（必要に応じてスタックを拡張するために新しい、より大きなスタックに内容をコピーする）が、CGOを介したシステムコール中に実行できない、または実行すべきではない状況で試みられたことを意味します。

`StackCopyAlways`というフラグが`1`に設定されていたことは、ランタイムが常にスタックコピーが可能であると「期待」していたことを示します。しかし、この期待がWindows/amd64環境での特定のシステムコール（`syscall.Syscall`）中に裏切られ、致命的なエラーにつながったため、このフラグを無効化する必要が生じました。

## 前提知識の解説

### Goのスタック管理

Goは、他の多くの言語とは異なり、固定サイズのスタックではなく、動的にサイズが変更されるスタックを使用します。各Goルーチンは比較的小さなスタックで開始し、関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的に現在のスタックの内容を、より大きな新しいスタック領域にコピーします。このプロセスは「スタック成長」または「スタックコピー」と呼ばれ、プログラマがスタックサイズを事前に心配する必要がないように設計されています。

### Split Stack (分割スタック)

「Split Stack」は、Goのスタック成長メカニズムの根幹をなす概念です。Goの関数は、そのプロローグ（関数の冒頭部分）で、現在のスタックフレームが残りの処理に十分なスペースを持っているかを確認します。もし十分なスペースがなければ、`runtime.morestack`という特別な関数が呼び出され、スタックの成長（新しいスタックの割り当てと内容のコピー）が行われます。この仕組みにより、Goルーチンは必要に応じてスタックを動的に拡張できます。

しかし、「fatal error: split stack not allowed」というエラーは、このスタック成長メカニズムが特定の状況下で許可されていないことを示します。これは通常、以下のような場合に発生します。
*   **低レベルのランタイムコード:** ランタイムの非常にクリティカルな部分では、スタック成長による中断が許されない場合があります。
*   **CGO呼び出し:** GoコードがCコード（またはOSのAPI）を呼び出すCGO（C Go）を介した呼び出しでは、GoのスタックとCのスタックの間でコンテキストが切り替わります。この切り替え中にGoのスタックが動的に成長しようとすると、予期せぬ問題や競合状態を引き起こす可能性があります。

### CGO

CGOは、GoプログラムがC言語の関数を呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリを利用したり、OSの低レベルAPIにアクセスしたりすることが可能になります。CGO呼び出しは、GoのランタイムとCのランタイム（またはOSのランタイム）の間でスタックやレジスタの状態を適切に管理する必要があるため、複雑な処理を伴います。

### `syscall.Syscall`

`syscall.Syscall`は、Goの`syscall`パッケージに含まれる低レベルの関数で、オペレーティングシステムのシステムコールを直接実行するために使用されます。Windows環境では、これはWindows API関数を呼び出すことを意味します。これらの呼び出しは通常、CGOのメカニズムを内部的に利用しており、Goのランタイムが直接OSのカーネルやユーザーモードライブラリと対話する橋渡しをします。

### `StackCopyAlways`フラグ

`StackCopyAlways`は、Goランタイムの内部で定義されていたコンパイル時または実行時のフラグです。このフラグが`1`に設定されている場合、Goランタイムは「常にスタックコピーが可能である」という前提で動作します。これは、スタックコピーが非常に効率的であり、ほとんどの状況で安全に実行できるという最適化の仮定を意味していました。しかし、このコミットが示すように、特定の条件下（特にCGOを介したシステムコール中）では、この仮定が破綻し、ランタイムパニックを引き起こすことが判明しました。

## 技術的詳細

この問題の核心は、Goランタイムが`StackCopyAlways = 1`という設定の下で、`syscall.Syscall`呼び出し中にスタック成長を試みたことにあります。Windows/amd64環境において、`syscall.Syscall`はOSのネイティブAPIを呼び出すためにCGOメカニズムを利用します。このCGO呼び出しの最中、Goルーチンのスタックが不足し、ランタイムが`runtime.morestack`を介してスタック成長（スタックコピー）を試みました。

しかし、CGO呼び出しの特定のフェーズ、特にOSのAPIが実行されている間や、GoとCのスタックコンテキストが切り替わっている最中には、Goのスタックを動的にコピーして移動させることが安全ではない、あるいは技術的に不可能な場合があります。このような状況でスタックコピーが強制されると、「fatal error: split stack not allowed」というパニックが発生し、プログラムがクラッシュします。スタックトレースは、`runtime.throw` -> `runtime.newstack` -> `runtime.morestack`というパスを示しており、スタック成長の試みがパニックの原因であることを明確に裏付けています。

このコミットでは、`StackCopyAlways`フラグを`0`に設定することで、この「常にスタックコピーが可能である」という仮定を無効にします。これにより、ランタイムはスタックコピーが常に安全であるとは限らないことを認識し、`syscall.Syscall`のようなクリティカルなCGOコンテキストでは、スタック成長の挙動をより慎重に、あるいは異なる方法で処理するようになります。例えば、システムコール前に十分なスタックを確保したり、スタック成長を一時的に抑制したりするなどの対策が講じられる可能性があります。この変更は、特定の環境下でのランタイムの安定性を向上させるための重要な修正です。

## コアとなるコードの解説

変更は`src/runtime/stack.c`ファイル内の`enum`定義にあります。

*   **変更前:** `StackCopyAlways = 1, // expect to be able to copy stacks 100% of the time`
*   **変更後:** `StackCopyAlways = 0, // expect to be able to copy stacks 100% of the time`

この変更は、`StackCopyAlways`という定数の値を`1`から`0`に切り替えるものです。
*   `StackCopyAlways = 1`は、Goランタイムがスタックコピー操作を常に成功させることができると「期待」していることを意味していました。これは、スタックコピーが非常に信頼性が高く、どのような状況でも問題なく実行できるという前提に基づいた最適化やアサーションとして機能していた可能性があります。
*   `StackCopyAlways = 0`に設定することで、この「常にコピー可能である」という期待を無効にします。これにより、ランタイムはスタックコピーが常に可能であるとは限らないという現実を考慮に入れ、特にCGO呼び出しのようなデリケートなコンテキストでは、スタック成長の処理をより堅牢かつ安全な方法で行うようになります。具体的には、スタックコピーが不可能な状況を検出し、パニックを回避するための代替メカニズム（例えば、事前に十分なスタックを確保する、スタック成長を一時的にブロックする、など）がトリガーされるようになります。

このシンプルな変更は、Goランタイムのスタック管理戦略における重要な調整であり、特定のOS/アーキテクチャの組み合わせにおける安定性の問題を解決するために不可欠でした。

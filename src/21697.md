# [インデックス 21697] ファイルの概要

このコミットは、Go言語のアセンブラツール `cmd/asm` における整数演算のオーバーフローチェックを導入するものです。具体的には、乗算 (`*`) と左シフト (`<<`) 操作において、結果が表現可能な範囲を超える場合にエラーを検出する機能が追加されました。これにより、アセンブラが生成するコードの堅牢性と移植性が向上します。

変更された主要なファイルは以下の2つです。

-   `src/cmd/asm/internal/asm/overflow.go`: 整数オーバーフローを検出するためのヘルパー関数が追加されました。特に、左シフトのオーバーフローをチェックする `shiftOverflows` 関数とその符号付きバージョンが新しく定義されています。
-   `src/cmd/asm/internal/asm/parse.go`: `cmd/asm` のパーサー部分で、乗算と左シフトの式を評価する際に、`overflow.go` で定義されたオーバーフローチェック関数を呼び出すように変更されました。

## 変更の背景

この変更の背景には、Go言語のアセンブラ `cmd/asm` が直面していた、整数演算における移植性の問題があります。

アセンブラは、特定のCPUアーキテクチャ向けの機械語を生成するためのツールです。しかし、アセンブラの定義自体には、内部で扱う整数の具体的なビット幅（例：32ビット、64ビット）が明示的に含まれていませんでした。この曖昧さが問題を引き起こしていました。

具体的には、乗算や左シフトといったビット操作を伴う演算において、結果がそのアーキテクチャのレジスタやメモリが表現できる範囲を超えてしまう「オーバーフロー」が発生する可能性がありました。もしオーバーフローが発生し、上位ビットが切り捨てられたり、予期せぬ値になったりした場合、そのアセンブリコードは異なるアーキテクチャや異なるコンパイル環境では正しく動作しない可能性があります。これは「移植性の問題」として顕在化します。

例えば、あるアーキテクチャでは64ビット整数として扱われる値が、別のアーキテクチャでは32ビット整数として扱われる場合、同じアセンブリコードでも結果が異なる可能性があります。このような状況は、デバッグを困難にし、Goプログラム全体の信頼性を損なう原因となります。

このコミットは、このような移植性の問題を未然に防ぐことを目的としています。アセンブラの段階でオーバーフローを検出し、開発者に警告することで、より堅牢で移植性の高いアセンブリコードの作成を促します。コミットメッセージにある「If you need to use shift to create a mask, use & to restrict the bit count before shifting. That will make it portable, too.」という記述は、開発者に対する具体的な回避策の提案であり、オーバーフローを意識したコーディングの重要性を示唆しています。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下の前提知識が必要です。

### 1. 整数オーバーフロー (Integer Overflow)

整数オーバーフローとは、数値計算の結果が、その数値を格納するために割り当てられたデータ型（ビット幅）で表現できる最大値を超えてしまう現象です。例えば、8ビット符号なし整数（0〜255）で200 + 100を計算すると、結果は300ですが、8ビットでは255までしか表現できないため、オーバーフローが発生し、結果が44（300を256で割った余り）になることがあります。

オーバーフローの挙動はプログラミング言語やCPUアーキテクチャによって異なりますが、一般的には以下のいずれかの結果になります。

-   **ラップアラウンド (Wrap-around)**: 最大値を超えると最小値に戻り、最小値を下回ると最大値に戻る（例：符号なし整数）。
-   **飽和 (Saturation)**: 最大値を超えると最大値に、最小値を下回ると最小値に固定される。
-   **未定義動作 (Undefined Behavior)**: 予測不能な結果となり、プログラムのクラッシュやセキュリティ脆弱性につながる可能性がある（C/C++の符号付き整数など）。

Go言語では、整数オーバーフローは通常ラップアラウンド挙動を示しますが、アセンブラレベルではより低レベルな挙動が問題となります。

### 2. 左シフト演算子 (`<<`)

左シフト演算子 (`<<`) は、数値のビットを左に指定された回数だけ移動させるビット演算子です。左にシフトされたビットは失われ、右側には0が埋められます。

例: `5 << 2` (5はバイナリで `00000101`)
1.  `00000101` (5)
2.  `00001010` (10, 1回左シフト)
3.  `00010100` (20, 2回左シフト)

左シフトは、数値を2のべき乗で乗算するのと同じ効果があります（例: `x << n` は `x * (2^n)`）。しかし、シフトの結果がデータ型のビット幅を超えると、上位ビットが失われ、オーバーフローが発生します。

例: 8ビット符号なし整数で `100 << 2`
1.  `01100100` (100)
2.  `11001000` (200, 1回左シフト)
3.  `10010000` (144, 2回左シフト - 最上位ビットが失われたため、値が減少)

### 3. Go言語の `cmd/asm` ツール

`cmd/asm` は、Go言語のツールチェインに含まれるアセンブラです。Goプログラム内でインラインアセンブリを使用する場合や、Goランタイム自体のアセンブリコード（例：スケジューラ、メモリ管理の一部）をコンパイルする際に使用されます。

`cmd/asm` は、Goのアセンブリ言語（Plan 9アセンブリの派生）を機械語に変換します。このアセンブリ言語は、一般的なx86-64アセンブリとは異なる独自の構文を持っています。

### 4. 移植性 (Portability)

移植性とは、ソフトウェアが異なる環境（異なるCPUアーキテクチャ、オペレーティングシステム、コンパイラなど）で、変更なしに、または最小限の変更で動作する能力を指します。

アセンブリ言語は通常、特定のアーキテクチャに強く依存するため、移植性が低いとされます。しかし、Go言語の設計哲学では、可能な限り多くのプラットフォームで動作することが重視されており、`cmd/asm` を通じて書かれるアセンブリコードも、異なるアーキテクチャ間で問題なく動作することが望ましいとされています。整数オーバーフローのような問題は、アーキテクチャ間のビット幅の違いによって移植性を損なう典型的な例です。

## 技術的詳細

このコミットは、`cmd/asm` がアセンブリコードをパースする際に、定数式の乗算と左シフトでオーバーフローが発生するかどうかをチェックするメカニズムを導入しています。

### オーバーフロー検出ロジック

`src/cmd/asm/internal/asm/overflow.go` に追加された主要な関数は以下の通りです。

1.  **`func mulOverflows(a, b uint64) bool`**:
    この関数は、2つの符号なし64ビット整数 `a` と `b` の乗算 `a * b` がオーバーフローするかどうかをチェックします。
    ロジックは非常にシンプルで、`c = a * b` を計算した後、`c / b` が元の `a` と等しいかどうかを比較します。
    -   もしオーバーフローが発生していなければ、`a * b / b` は `a` に戻るはずです。
    -   しかし、オーバーフローが発生して `c` が切り詰められた値になっている場合、`c / b` は元の `a` とは異なる値になります。
    この方法は、`b` がゼロでない場合に有効です。`b` がゼロの場合は、`parse.go` 側でゼロ除算として別途処理されます。

2.  **`func shiftOverflows(a, b uint64) bool`**:
    この関数は、符号なし64ビット整数 `a` を `b` ビットだけ左シフト (`a << b`) したときにオーバーフローするかどうかをチェックします。
    ロジックは `mulOverflows` と同様に、シフト操作の逆演算を利用します。
    -   `c = a << b` を計算します。
    -   次に、`c` を `b` ビットだけ右シフト (`c >> b`) します。
    -   もしオーバーフローが発生していなければ、`((a << b) >> b)` は元の `a` に戻るはずです。
    -   しかし、左シフトによって上位ビットが失われた（オーバーフローした）場合、右シフトで元の位置に戻しても、失われたビットは復元されないため、結果は元の `a` とは異なる値になります。

3.  **`func signedShiftOverflows(a, b int64) bool`**:
    この関数は、符号付き64ビット整数 `a` を `b` ビットだけ左シフト (`a << b`) したときにオーバーフローするかどうかをチェックします。
    符号付き整数のシフトは、符号ビットの扱いや右シフトの挙動が符号なし整数と異なるため、より複雑なロジックが必要です。
    -   **`a >= 0` の場合**: 符号なしの場合と同様に `c := a << b; return c>>b != a` でチェックします。正の数の左シフトは、符号なしの場合と同じオーバーフロー挙動を示します。
    -   **`a < 0` の場合**: 負の数の右シフトは、Go言語では算術右シフト（符号ビットを保持しながらシフト）になります。オーバーフローチェックのために逆演算を行う際に、この挙動が問題となる可能性があります。
        この実装では、負の数 `a` を `^a` (ビット反転) することで、正の数に変換し、上位ビットがゼロになるようにします。その後、この変換された値に対して左シフトと逆シフトを行い、オーバーフローをチェックします。このアプローチにより、符号付き整数の複雑な挙動を回避しつつ、オーバーフローを検出しています。

### パーサーへの統合

`src/cmd/asm/internal/asm/parse.go` の `Parser.term()` メソッドは、アセンブリコード内の式（定数式など）を解析する役割を担っています。このメソッド内で、乗算と左シフトの処理にオーバーフローチェックが組み込まれました。

-   **乗算 (`*`)**:
    ```go
    case '*':
        p.next()
        x := p.factor()
        if mulOverflows(value, x) {
            p.errorf("%d * %d overflows", value, x)
        }
        value *= x
    ```
    `p.factor()` で右オペランド `x` を取得した後、`mulOverflows(value, x)` を呼び出します。もしオーバーフローが検出された場合、`p.errorf()` を使ってエラーメッセージを生成し、アセンブル時にエラーとして報告します。その後、実際に乗算を実行します。

-   **左シフト (`lex.LSH`)**:
    ```go
    case lex.LSH:
        p.next()
        shift := p.factor()
        if int64(shift) < 0 { // シフト量が負の場合のチェック
            p.errorf("negative left shift %d", shift)
        }
        if shiftOverflows(value, shift) {
            p.errorf("%d << %d overflows", value, shift)
        }
        return value << shift
    ```
    まず、シフト量 `shift` が負でないことを確認します。負のシフトは不正な操作です。
    次に、`shiftOverflows(value, shift)` を呼び出し、オーバーフローをチェックします。オーバーフローが検出された場合、乗算と同様にエラーを報告します。その後、実際に左シフトを実行し、結果を返します。

この統合により、`cmd/asm` はアセンブリコードのコンパイル時に、定数式の乗算と左シフトにおける潜在的なオーバーフロー問題を早期に発見し、開発者に通知できるようになりました。これにより、実行時エラーや移植性の問題を防ぐことができます。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/overflow.go` の変更点

このファイルには、整数オーバーフローを検出するための新しいヘルパー関数が追加されました。

-   **`func shiftOverflows(a, b uint64) bool`**:
    符号なし64ビット整数 `a` を `b` ビット左シフトした際のオーバーフローを検出します。
    `c := a << b` でシフトを実行し、その結果 `c` を `b` ビット右シフトして元の `a` と比較します (`c>>b != a`)。
    もし左シフトで上位ビットが失われていれば、右シフトで元の位置に戻しても失われたビットは復元されないため、`c>>b` は元の `a` と異なる値になります。これにより、オーバーフローを正確に検出できます。

-   **`func signedShiftOverflows(a, b int64) bool`**:
    符号付き64ビット整数 `a` を `b` ビット左シフトした際のオーバーフローを検出します。
    符号付き整数の場合、負の数の右シフトは算術右シフト（符号ビットを保持）になるため、単純な逆演算ではうまくいかないことがあります。
    この関数は、`a >= 0` の場合は符号なしの場合と同じロジックを適用します。
    `a < 0` の場合、`a = ^a` (ビット反転) を行い、負の数を正の数に変換し、上位ビットがゼロになるようにします。これにより、符号なしシフトと同様のオーバーフローチェックを適用できるようにしています。

-   **コメントアウトされたテストコード**:
    `overflow.go` の冒頭には、`shiftOverflows` 関数のテストに使用されたと思われるコメントアウトされたコードブロックが含まれています。これは、`a` と `b` の様々な組み合わせ（0から255まで）に対して、手動で実装されたオーバーフローチェックロジック (`overflow := func(a, b int) bool`) と、新しく追加された `shiftOverflows` 関数の結果を比較し、不一致があれば報告するというものです。これは、新しいオーバーフロー検出ロジックが正しく機能することを確認するためのデバッグ/テスト手法を示しています。

### `src/cmd/asm/internal/asm/parse.go` の変更点

このファイルは `cmd/asm` のパーサーの一部であり、アセンブリコード内の式を解析します。`term()` メソッドは、乗算やシフトなどの演算子を含む式を処理します。

-   **乗算 (`*`) のオーバーフローチェック**:
    以前は `value *= p.factor() // OVERFLOW?` とコメントがあるだけで、実際のオーバーフローチェックは行われていませんでした。
    変更後、`x := p.factor()` で乗算の右オペランドを取得した後、`mulOverflows(value, x)` を呼び出してオーバーフローをチェックするようになりました。
    もし `mulOverflows` が `true` を返した場合（オーバーフローが検出された場合）、`p.errorf("%d * %d overflows", value, x)` を呼び出し、具体的な数値とともにオーバーフローエラーを報告します。これにより、アセンブル時に開発者に問題が通知されます。

-   **左シフト (`lex.LSH`) のオーバーフローチェック**:
    以前は `value <<= uint(shift) // OVERFLOW?` とコメントがあるだけで、オーバーフローチェックは行われていませんでした。
    変更後、まず `int64(shift) < 0` でシフト量が負でないことを確認します。負のシフトは不正な操作であり、エラーとして報告されます。
    次に、`shiftOverflows(value, shift)` を呼び出してオーバーフローをチェックします。
    もし `shiftOverflows` が `true` を返した場合、`p.errorf("%d << %d overflows", value, shift)` を呼び出し、具体的な数値とともにオーバーフローエラーを報告します。
    これらのチェックの後、実際に `value << shift` を実行し、結果を返します。

これらの変更により、`cmd/asm` はアセンブリコードのコンパイル時に、定数式の乗算と左シフトにおける潜在的なオーバーフロー問題を早期に発見し、開発者に通知できるようになりました。これにより、実行時エラーや移植性の問題を防ぐことができます。

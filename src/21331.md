# [インデックス 21331] ファイルの概要

## コミット

このコミットは、Go言語のランタイムにおけるハッシュマップ（`map`）の実装に関する重要な変更です。具体的には、マップのバケット構造体内でオーバーフローポインタの位置を移動させることで、ゼロサイズ値（zero-sized values）に関連する潜在的なメモリリークやガベージコレクタ（GC）の誤認識の問題を解決しています。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/fbc56cf05015899aba236d5a68096a770de3ad0a](https://github.com/golang/go/commit/fbc56cf05015899aba236d5a68096a770de3ad0a)

## 元コミット内容

```
runtime: hashmap: move overflow pointer to end of bucket

Pointers to zero-sized values may end up pointing to the next
object in memory, and possibly off the end of a span.  This
can cause memory leaks and/or confuse the garbage collector.

By putting the overflow pointer at the end of the bucket, we
make sure that pointers to any zero-sized keys or values don't
accidentally point to the next object in memory.

fixes #9384

Change-Id: I5d434df176984cb0210b4d0195dd106d6eb28f73
Reviewed-on: https://go-review.googlesource.com/1869
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

Goのマップは、内部的にハッシュテーブルとして実装されており、キーと値のペアを「バケット」と呼ばれる固定サイズのメモリブロックに格納します。各バケットには、複数のキーと値のペアを格納できるスロットがあり、さらに、バケットが満杯になった場合に次のバケットを指す「オーバーフローポインタ」を持っています。

このコミットが行われる前は、オーバーフローポインタがバケットの先頭近くに配置されていました。この配置が、特定の状況下で問題を引き起こす可能性がありました。特に、マップのキーや値が「ゼロサイズ型」（例: `struct{}`, `[0]int`）である場合に問題が発生しました。

ゼロサイズ型は、それ自体がメモリを消費しないため、そのポインタは理論的にはどのメモリ位置を指しても問題ありません。しかし、Goのランタイムやガベージコレクタは、ポインタが指すメモリ領域の型情報に基づいて動作します。ゼロサイズ値へのポインタが、意図せずバケット内の次のフィールド、特にオーバーフローポインタを指してしまうと、以下の問題が発生する可能性がありました。

1.  **メモリリーク**: GCが、ゼロサイズ値のポインタが指すオーバーフローバケットを「到達可能」と誤認識し、実際には不要なオーバーフローバケットが解放されないまま残ってしまう。
2.  **GCの誤認識**: GCが、ゼロサイズ値のポインタを介して、本来ポインタではないデータ（例えば、オーバーフローポインタのビットパターン）をポインタとして解釈し、誤ったメモリ領域をスキャンしようとする。これにより、クラッシュや不正な動作につながる可能性がありました。

この問題を解決するため、オーバーフローポインタをバケットの末尾に移動させるという変更が提案されました。これにより、ゼロサイズ値のポインタがバケット内の他の有効なデータ構造を指す可能性が低くなり、GCの正確な動作が保証されます。

## 前提知識の解説

### Goのマップ (hashmap) の内部構造

Goのマップは、ハッシュテーブルの一種であり、キーと値のペアを効率的に格納・検索するために設計されています。その内部構造は以下の要素で構成されます。

*   **`hmap` 構造体**: マップ全体のメタデータを管理する構造体です。バケットの数、要素数、ハッシュシードなどが含まれます。
*   **バケット (`bmap`)**: キーと値のペアを実際に格納する固定サイズのメモリブロックです。各バケットは通常、`bucketCnt`（Go 1.xでは8）個のキーと値のスロットを持ちます。
*   **`tophash`**: 各スロットに対応するハッシュ値の上位バイトを格納する配列です。これにより、キーの比較を高速化し、衝突を減らします。
*   **キーと値の格納**: バケット内では、`tophash` の後にすべてのキーが連続して配置され、その後にすべての値が連続して配置されます。これは、パディングを最小限に抑え、メモリ効率を高めるための設計です。
*   **オーバーフローバケット**: バケットが満杯になった場合、新しいキーと値のペアは「オーバーフローバケット」と呼ばれる別のバケットに格納されます。元のバケットはオーバーフローポインタを介してこのオーバーフローバケットを指します。これにより、ハッシュ衝突が発生してもマップの容量を動的に拡張できます。

### ゼロサイズ型 (zero-sized types)

Goにおけるゼロサイズ型とは、メモリを一切消費しない型のことです。代表的なものに、空の構造体 `struct{}` や、要素数0の配列 `[0]int` などがあります。これらの型は、主にセマフォやプレースホルダー、型パラメータの制約など、値そのものよりもその存在や型情報が重要な場合に利用されます。

ゼロサイズ型の変数を宣言しても、メモリは割り当てられません。しかし、その変数へのポインタは存在し、Goの仕様では、ゼロサイズ型へのポインタは、その型のインスタンスがメモリ上に存在しないため、任意の有効なアドレスを指すことができます。この「任意の有効なアドレス」が、今回の問題の根源となりました。

### Goのガベージコレクタ (GC) の基本的な動作

Goのガベージコレクタは、マーク＆スイープ方式をベースとした並行（concurrent）かつ低遅延（low-latency）のコレクタです。GCの主な役割は、プログラムがもはや到達できない（参照されていない）メモリ領域を特定し、それを解放して再利用可能にすることです。

GCは、プログラムのルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。マークされたオブジェクトは「生きている」と判断され、マークされなかったオブジェクトは「死んでいる」と判断され、スイープフェーズで解放されます。

ポインタはGCがオブジェクトの到達可能性を判断するための重要な情報源です。GCはポインタをたどってメモリグラフを構築し、到達可能なオブジェクトを特定します。もしポインタが誤った情報を指していたり、本来ポインタではないものをポインタとして解釈してしまうと、GCの正確性が損なわれ、メモリリークやクラッシュにつながる可能性があります。

### ポインタの挙動とアライメント

Goにおけるポインタは、メモリ上の特定のアドレスを指す変数です。Goの型システムは、ポインタが指すデータの型を厳密に管理し、型安全性を保証します。しかし、`unsafe.Pointer` を使用すると、任意の型へのポインタを表現したり、ポインタと `uintptr`（符号なし整数型）の間で変換を行ったりすることが可能になります。これは、低レベルのメモリ操作や、Goの型システムでは表現できない特殊なケースで利用されますが、誤用するとメモリ安全性の問題を引き起こす可能性があります。

アライメントとは、メモリ上のデータが特定のバイト境界に配置されることを指します。CPUは、アライメントされたデータにアクセスする方が高速であるため、コンパイラは通常、構造体のフィールドなどを適切にアライメントするように配置します。

### `reflect` パッケージと型情報 (`rtype`)

`reflect` パッケージは、Goの実行時に型情報を検査・操作するための機能を提供します。Goの内部では、すべての型は `_type`（または `rtype`）構造体によって表現されます。この構造体には、型のサイズ、アライメント、メソッド、そしてGCがポインタを識別するために使用する「GCビットマップ」などの情報が含まれています。

マップのバケット構造体のようなランタイム内部の型も、この `rtype` 構造体によって定義され、GCはこれを利用してバケット内のどの部分がポインタであるかを判断します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイルされたプログラムのデバッグ情報を格納するための標準的な形式です。これには、変数名、型情報、ソースコードの行番号と実行可能コードのアドレスのマッピングなどが含まれます。Goのコンパイラとリンカは、デバッグ情報を生成する際にDWARF形式を使用します。

このコミットでは、マップのバケット構造体のレイアウトが変更されたため、デバッガが正しくメモリを解釈できるように、DWARF情報も更新する必要がありました。

## 技術的詳細

このコミットの核心は、Goのマップバケット構造体 `bmap` におけるオーバーフローポインタ (`overflow *bmap`) の位置を、バケットの先頭近くから**バケットの末尾**に移動したことです。

### `bmap` 構造体の変更

変更前:
```go
type bmap struct {
	tophash  [bucketCnt]uint8
	overflow *bmap // オーバーフローポインタが先頭近くにあった
	// Followed by bucketCnt keys and then bucketCnt values.
}
```

変更後:
```go
type bmap struct {
	tophash  [bucketCnt]uint8
	// Followed by bucketCnt keys and then bucketCnt values.
	// NOTE: packing all the keys together and then all the values together makes the
	// code a bit more complicated than alternating key/value/key/value/... but it allows
	// us to eliminate padding which would be needed for, e.g., map[int64]int8.
	// Followed by an overflow pointer. // オーバーフローポインタが末尾に移動
}
```
`bmap` 構造体自体からは `overflow *bmap` フィールドが削除され、代わりにバケットのメモリレイアウトの最後にオーバーフローポインタが配置されるというコメントが追加されました。これは、Goのコンパイラが構造体のフィールドをどのように配置するかを制御する `src/cmd/gc/reflect.c` で定義されます。

### `overflow` および `setoverflow` ヘルパー関数の導入

オーバーフローポインタが構造体の固定フィールドではなくなったため、そのポインタへのアクセスはオフセット計算によって行われるようになりました。これを抽象化するために、`bmap` 型に以下のヘルパーメソッドが追加されました。

```go
func (b *bmap) overflow(t *maptype) *bmap {
	return *(**bmap)(add(unsafe.Pointer(b), uintptr(t.bucketsize) - ptrSize))
}
func (b *bmap) setoverflow(t *maptype, ovf *bmap) {
	*(**bmap)(add(unsafe.Pointer(b), uintptr(t.bucketsize) - ptrSize)) = ovf
}
```
これらの関数は、`unsafe.Pointer` と `uintptr` を使用して、バケットの先頭アドレス `b` から `t.bucketsize - ptrSize` のオフセットにあるメモリ位置にアクセスします。`t.bucketsize` はバケット全体のサイズであり、`ptrSize` はポインタのサイズ（通常は4バイトまたは8バイト）です。これにより、バケットの末尾からポインタのサイズ分だけ手前の位置、つまりバケットの最後にオーバーフローポインタが配置されることになります。

### `src/cmd/gc/reflect.c` でのバケット構造体のレイアウト定義の変更

このファイルは、Goのコンパイラがランタイム型情報（`rtype`）を生成する際に使用されます。`mapbucket` 関数は、マップのバケットのメモリレイアウトを定義します。

変更前は、`overflowfield` が `keysfield` の前に定義され、そのオフセットが計算されていました。
変更後は、`overflowfield` の定義が `valuesfield` の後に移動し、そのオフセットが `valuesfield` の直後、つまりバケットの末尾近くになるように計算されるようになりました。

```c
// 変更前: overflowfield が keysfield の前に定義されていた
// overflowfield = typ(TFIELD);
// overflowfield->type = ptrto(bucket);
// overflowfield->width = offset; // "width" is offset in structure
// offset += widthptr;

// 変更後: overflowfield が valuesfield の後に定義された
// valuesfield->down = overflowfield;
// overflowfield->down = T;
// overflowfield = typ(TFIELD);
// overflowfield->type = ptrto(bucket);
// overflowfield->width = offset; // "width" is offset in structure
// offset += widthptr;
```
また、フィールドのリンクリストの順序も変更され、`keysfield` -> `valuesfield` -> `overflowfield` の順に連結されるようになりました。

### `src/cmd/ld/dwarf.c` でのDWARF情報生成の変更

このファイルは、Goのリンカがデバッグ情報（DWARF）を生成する際に使用されます。マップのバケット構造体のレイアウトが変更されたため、デバッガが正しくバケットのフィールドを解釈できるように、DWARF情報も更新する必要がありました。

具体的には、`synthesizemaptypes` 関数内で、`overflow` フィールドのオフセット計算が変更され、`keys` と `values` フィールドの後に来るように調整されました。また、パディングに関するDWARF情報も追加されました。

### `src/reflect/type.go` でのGCビットマップ生成ロジックの変更

このファイルは、Goの `reflect` パッケージが型情報を扱う際に使用され、特にGCがポインタを識別するためのビットマップを生成するロジックが含まれています。

`bucketOf` 関数は、マップのバケットのGCビットマップを生成します。変更前は、`tophash` の後に `overflow` ポインタのビットマップが追加されていましたが、変更後は、キーと値のビットマップの後に `overflow` ポインタのビットマップが追加されるようになりました。これにより、GCがバケット内のポインタを正しく識別できるようになります。

### `src/runtime/hashmap.go` および `src/runtime/hashmap_fast.go` でのオーバーフローバケットへのアクセス方法の変更

これらのファイルには、マップの基本的な操作（アクセス、挿入、削除、イテレーション、リサイズなど）を実装するランタイムコードが含まれています。

変更前は、`b.overflow` のように直接 `bmap` 構造体のフィールドとしてオーバーフローポインタにアクセスしていましたが、変更後は、新しく導入されたヘルパー関数 `b.overflow(t)` および `b.setoverflow(t, newb)` を使用してアクセスするように変更されました。これにより、オーバーフローポインタの物理的な位置が抽象化され、コードの保守性が向上しました。

## コアとなるコードの解説

### `bmap` 構造体定義の変更

`src/runtime/hashmap.go` における `bmap` 構造体の変更は、オーバーフローポインタが構造体の明示的なフィールドではなくなったことを示しています。これは、Goのコンパイラがこの構造体のメモリレイアウトを決定する際に、オーバーフローポインタをバケットの最後に配置するように指示されることを意味します。この変更により、`bmap` の定義はよりクリーンになり、オーバーフローポインタの物理的な位置がランタイムの内部実装に委ねられる形になりました。

### `overflow` および `setoverflow` ヘルパー関数

これらの関数は、オーバーフローポインタへのアクセスをカプセル化するために導入されました。
*   `b.overflow(t *maptype) *bmap`: このメソッドは、現在のバケット `b` のオーバーフローポインタが指す次のバケットを返します。`unsafe.Pointer(b)` でバケットの先頭アドレスを取得し、`uintptr(t.bucketsize) - ptrSize` のオフセットを加算することで、バケットの末尾からポインタのサイズ分だけ手前の位置（つまりオーバーフローポインタが格納されている場所）を計算します。そのアドレスを `**bmap` 型にキャストし、デリファレンスすることで、オーバーフローバケットのポインタを取得します。
*   `b.setoverflow(t *maptype, ovf *bmap)`: このメソッドは、現在のバケット `b` のオーバーフローポインタを `ovf` に設定します。同様にオフセット計算を行い、そのメモリ位置に `ovf` ポインタを書き込みます。

これらのヘルパー関数を使用することで、マップの操作を行う他のランタイムコードは、オーバーフローポインタの物理的な位置を意識することなく、論理的なアクセスを行うことができます。

### `src/cmd/gc/reflect.c` の `mapbucket` 関数における `overflowfield` の配置変更

`mapbucket` 関数は、Goのマップバケットの型情報をコンパイラに提供します。この関数内の変更は、バケットのメモリレイアウトがどのように定義されるかを直接制御します。

*   **フィールド定義の移動**: 以前は `overflowfield` が `keysfield` の前に定義されていましたが、変更後は `valuesfield` の後に移動しました。これにより、`overflowfield` のオフセットが、キーと値のフィールドの後に計算されるようになります。
*   **フィールドのリンクリストの順序変更**: `bucket->type` が `keysfield` を指し、`keysfield->down` が `valuesfield` を指し、`valuesfield->down` が `overflowfield` を指すように変更されました。これは、バケット内のフィールドの論理的な順序を反映しており、GCがバケットをスキャンする際の順序にも影響を与えます。

これらの変更により、コンパイラはマップバケットのメモリレイアウトを、オーバーフローポインタがバケットの末尾に位置するように正しく生成するようになります。

# [インデックス 26385] ファイルの概要

このコミットは、Goの`net/http`パッケージにおけるHTTP/2のバンドル版を更新し、特にHTTP/2接続の確立プロセスにおける効率性と堅牢性を向上させるものです。主な変更点は、HTTP/2プロトコルがまだ不明な状態で複数のHTTPリクエストが同時に開始された場合に発生する、不要なTCP接続の確立とその後の処理の最適化、およびGo 1.6で導入された`TLSNextProto`の挙動に対応するためのTLSハンドシェイクの保証です。

## 変更の背景

このコミットには主に二つの背景があります。

1.  **HTTP/2接続確立時の非効率性**:
    HTTP/2は単一のTCP接続上で複数のリクエストを多重化することで効率を高めます。しかし、クライアントがサーバーがHTTP/1.1とHTTP/2のどちらをサポートしているかを知らない状態で、同時に複数のHTTPリクエストを開始することがあります。この場合、クライアントはそれぞれのリクエストに対して新しいTCP接続を確立しようとします。もしサーバーがHTTP/2をサポートしていることが判明した場合、これらの接続のうち一つだけがHTTP/2通信に利用され、残りの接続は冗長となります。以前の実装では、これらの冗長なTLS接続もHTTP/2にアップグレードしようとしていましたが、これは無駄なリソース消費と遅延を引き起こしていました。このコミットは、この非効率性を解消し、不要な接続を早期に閉じることでリソースを節約し、パフォーマンスを向上させることを目的としています。

2.  **Go 1.6におけるTLSNextProtoの導入**:
    Go 1.6では、`net/http`パッケージに`TLSNextProto`フィールドが導入され、TLSハンドシェイク時にアプリケーション層プロトコルネゴシエーション（ALPN）の結果に基づいてカスタムハンドラを登録できるようになりました。`TLSNextProto`は、TLS接続の状態（`ConnectionState.NegotiatedProtocol`）を参照して、どのプロトコルがネゴシエートされたかを判断します。しかし、`DialTLS`フックを使用する際に、TLSハンドシェイクが必ずしも完了しているとは限りませんでした。`ConnectionState.NegotiatedProtocol`を正確に参照するためには、TLSハンドシェイクが完了していることが必須であるため、このコミットでは`DialTLS`フックの後にTLSハンドシェイクが確実に行われるように変更が加えられました。これにより、`TLSNextProto`が意図通りに機能することが保証されます。

## 前提知識の解説

*   **HTTP/2**: HTTP/1.1の後継プロトコルで、単一のTCP接続上での多重化、ヘッダ圧縮、サーバープッシュなどの機能により、Webパフォーマンスを向上させます。ALPN (Application-Layer Protocol Negotiation) を使用して、TLSハンドシェイク中にクライアントとサーバー間でHTTP/2の使用をネゴシエートします。
*   **TLS (Transport Layer Security)**: インターネット上での通信を暗号化し、認証を行うためのプロトコルです。HTTPSの基盤となります。
*   **ALPN (Application-Layer Protocol Negotiation)**: TLSの拡張機能の一つで、TLSハンドシェイク中にクライアントとサーバーがどのアプリケーション層プロトコル（例: HTTP/1.1, HTTP/2）を使用するかをネゴシエートできるようにします。
*   **`net/http`パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
*   **`x/net/http2`**: Goの`net/http`パッケージが内部的にHTTP/2サポートのために利用する外部パッケージです。Goの標準ライブラリにバンドルされています。
*   **`http.Transport`**: `net/http`パッケージにおいて、HTTPリクエストの送信、接続の管理、プロキシ設定などを担当する構造体です。
*   **`TLSNextProto`**: `http.Transport`および`http.Server`のフィールドで、ALPNによってネゴシエートされたプロトコルに基づいてカスタムハンドラを登録するために使用されます。Go 1.6で導入されました。
*   **`tls.ConnectionState`**: TLS接続の現在の状態に関する情報（ネゴシエートされたプロトコル、暗号スイートなど）を含む構造体です。
*   **`DialTLS`フック**: `http.Transport`のフィールドで、TLS接続を確立するためのカスタム関数を指定できます。

## 技術的詳細

このコミットは、主に`net/http`パッケージ内のHTTP/2クライアント接続プールとTLS接続処理に焦点を当てています。

1.  **重複接続の最適化**:
    *   以前は、HTTP/2がサポートされているか不明な状態で複数のリクエストが同時に発生した場合、それぞれが新しいTLS接続を確立し、その後両方がHTTP/2にアップグレードされていました。
    *   この変更では、`http2clientConnPool`に`addConnIfNeeded`という新しいメソッドが導入されました。このメソッドは、特定のキー（ホスト:ポート）に対する接続がまだ存在しない場合にのみ新しいHTTP/2クライアント接続を作成します。
    *   `addConnIfNeeded`は、`http1 Transport`が新しい接続を作成する際に使用されます。`http1 Transport`は、プロトコルが不明なためTCPダイヤルを重複排除しないため、複数のTLS接続を持つ状況に陥る可能性があります。
    *   `addConnIfNeeded`は、既存のHTTP/2接続がリクエストを受け入れ可能であれば、新しい接続を作成せずに`false`を返します。これにより、重複する接続の作成を防ぎます。
    *   もし新しい接続が不要と判断された場合、新しく確立されたTLS接続（`*tls.Conn`）は、HTTP/2のプレフェースやSETTINGSフレームの交換が行われる前に閉じられます。これにより、無駄なHTTP/2アップグレード処理が回避されます。
    *   `addConnIfNeeded`は、同じキーに対する同時呼び出しを`http2addConnCall`構造体と`sync.Once`のようなメカニズム（`addConnCalls`マップとチャネル）で調整し、重複する接続の追加処理を防ぎます。

2.  **TLSハンドシェイクの保証**:
    *   `src/net/http/transport.go`の`dialConn`メソッド内で、`DialTLS`フックが使用された後に、TLS接続（`*tls.Conn`）に対して明示的に`Handshake()`が呼び出されるようになりました。
    *   これは、Go 1.6で`TLSNextProto`が`tls.ConnectionState.NegotiatedProtocol`を参照するようになったためです。`NegotiatedProtocol`は、TLSハンドシェイクが完了した後にのみ有効な値を持つため、この変更により`TLSNextProto`が常に正しいプロトコル情報を取得できるようになります。
    *   もしハンドシェイク中にエラーが発生した場合、確立された接続は閉じられ、エラーが返されます。

3.  **`x/net/http2`の更新**:
    *   このコミットは、`x/net/http2`パッケージを特定のGitリビジョン`a8e212f3d`に更新します。これにより、`net/http`パッケージが利用するHTTP/2実装が最新の状態になり、上記の変更をサポートするための基盤が提供されます。

## コアとなるコードの解説

### `src/net/http/h2_bundle.go` の変更点

*   **`http2clientConnPool`構造体の拡張**:
    `addConnCalls map[string]*http2addConnCall`フィールドが追加されました。これは、特定の`key`（ホスト:ポート）に対する`addConnIfNeeded`の同時呼び出しを調整するためのマップです。これにより、複数のゴルーチンが同時に同じ宛先への接続を追加しようとした場合に、実際に接続が追加されるのは一度だけとなり、重複する接続の作成を防ぎます。

*   **`addConnIfNeeded`メソッドの追加**:
    この新しいメソッドは、HTTP/1.1の`Transport`がTLS接続を確立した後に、その接続をHTTP/2クライアント接続プールに追加する必要があるかどうかを判断するために使用されます。
    1.  まず、`p.mu.Lock()`でミューテックスをロックし、接続プールへのアクセスを保護します。
    2.  既存の接続をチェックし、もし`key`に対応する利用可能なHTTP/2接続が既に存在すれば、新しい接続は不要と判断し`false`を返します。
    3.  `addConnCalls`マップをチェックし、同じ`key`に対する`addConnIfNeeded`の呼び出しが既に進行中であれば、その呼び出しの結果を待ちます。
    4.  もし進行中の呼び出しがなければ、新しい`http2addConnCall`を作成し、`addConnCalls`マップに登録し、新しいゴルーチンで`call.run`を実行します。
    5.  `call.run`は、`t.NewClientConn(tc)`を呼び出して新しいHTTP/2クライアント接続を作成し、成功すればそれをプールに追加します。エラーが発生した場合は`call.err`に格納します。
    6.  `addConnIfNeeded`は`<-call.done`で`call.run`の完了を待ち、結果を返します。
    7.  このメカニズムにより、複数のリクエストが同時に新しい接続を必要とした場合でも、実際に新しいHTTP/2接続が確立されるのは一つだけであり、残りのTLS接続は`upgradeFn`内で`c.Close()`によって閉じられます。

*   **`upgradeFn`の変更**:
    `http2configureTransport`内の`upgradeFn`は、TLS接続が確立された後にHTTP/2へのアップグレードを処理する関数です。この関数内で、以前は無条件に`t2.NewClientConn(c)`を呼び出し、`connPool.addConn`でプールに追加していましたが、変更後は`connPool.addConnIfNeeded`を呼び出すようになりました。
    *   `addConnIfNeeded`が`used`を`false`と返した場合（つまり、既に利用可能なHTTP/2接続があったため、このTLS接続は不要と判断された場合）、`go c.Close()`によって不要なTLS接続が非同期で閉じられます。これにより、無駄なHTTP/2アップグレード処理が回避され、リソースが節約されます。

### `src/net/http/transport.go` の変更点

*   **`dialConn`メソッド内のTLSハンドシェイクの追加**:
    `dialConn`メソッドは、新しいネットワーク接続を確立する役割を担います。このメソッド内で、`DialTLS`フックが使用されてTLS接続（`*tls.Conn`）が返された後、以下のコードが追加されました。
    ```go
    if tc, ok := pconn.conn.(*tls.Conn); ok {
        // Handshake here, in case DialTLS didn't. TLSNextProto below
        // depends on it for knowing the connection state.
        if err := tc.Handshake(); err != nil {
            go pconn.conn.Close()
            return nil, err
        }
        cs := tc.ConnectionState()
        pconn.tlsState = &cs
    }
    ```
    この変更により、`DialTLS`フックがカスタムのTLS接続を返した場合でも、`tc.Handshake()`が明示的に呼び出され、TLSハンドシェイクが完了することが保証されます。これにより、その後の`TLSNextProto`が`tc.ConnectionState()`から`NegotiatedProtocol`を安全に参照できるようになります。ハンドシェイクに失敗した場合は、接続を閉じ、エラーを返します。

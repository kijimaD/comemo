# [インデックス 21883] ファイルの概要

このコミットは、Go言語のビルドシステムの中核を担う `src/cmd/go/build.go` ファイルに変更を加えています。具体的には、新しいGoベースのアセンブラが、既存のCベースのアセンブラと同一のバイナリ出力を生成することを検証するためのテストロジックが追加されています。この変更は、Goランタイムの重要な部分であるアセンブリコードの正確性と互換性を保証するために導入されました。

このコミットは、新しいアセンブラのための `verifyAsm` テストを追加します。このテストは `amd64` および `386` アーキテクチャでのみ有効です。

## 変更の背景

Go言語のツールチェインは、その初期からC言語で実装されたアセンブラ（通称「Cアセンブラ」）を使用していました。しかし、Go言語自体の成熟とツールチェインの自己ホスト化（GoでGoをコンパイルする能力）の推進に伴い、アセンブラもGo言語で再実装されることになりました。この「新しいアセンブラ」（Goアセンブラ）への移行は、ツールチェイン全体の整合性を高め、開発の効率化を図る上で重要なステップでした。

このコミットが行われた時期は、まさにその移行期にあたります。新しいGoアセンブラが開発される中で、それが既存のCアセンブラと完全に互換性のあるバイナリコードを生成することが極めて重要でした。もし互換性がなければ、既存のGoプログラムや標準ライブラリのアセンブリコードが正しく動作しなくなる可能性があります。

`verifyAsm` テストは、この互換性を保証するためのものです。新しいアセンブラと古いアセンブラの両方で同じアセンブリソースファイルを処理し、生成されたオブジェクトファイルがビット単位で完全に一致するかどうかを検証します。これにより、新しいアセンブラが導入されても、Goプログラムの動作に予期せぬ変更がないことを確認できます。特に、`amd64` と `386` はGoがサポートする主要なアーキテクチャであり、これらのプラットフォームでの正確な動作は不可欠です。

## 前提知識の解説

### Go言語のビルドプロセスとツールチェイン

Go言語のプログラムは、`go build` コマンドによってコンパイルされます。このプロセスは、ソースコードの解析、中間表現への変換、最適化、そして最終的な機械語コードの生成という複数の段階を含みます。Goのツールチェインは、これらの各段階を担当する複数のツール（`go tool compile`、`go tool asm`、`go tool link`など）で構成されています。

### アセンブラとアセンブリ言語

アセンブリ言語は、CPUが直接実行できる機械語命令を人間が読み書きしやすいように記号化した低水準プログラミング言語です。アセンブラは、アセンブリ言語で書かれたソースコードを機械語コード（オブジェクトファイル）に変換するプログラムです。Go言語では、パフォーマンスが非常に重要な部分（例：ガベージコレクション、スケジューラ、特定の標準ライブラリ関数）でアセンブリコードが使用されます。

### Goのアセンブラ（Cアセンブラ vs Goアセンブラ）

*   **Cアセンブラ**: Goの初期バージョンで使用されていたアセンブラで、C言語で実装されていました。これはPlan 9オペレーティングシステムのアセンブラに由来し、Go特有の擬似命令（例：`MOVQ`、`CALL`など）をサポートしていました。
*   **Goアセンブラ**: Go言語で再実装された新しいアセンブラです。ツールチェイン全体の自己ホスト化の一環として開発されました。このコミットは、GoアセンブラがCアセンブラと同等の出力を生成することを検証するものです。

### `go tool compile` と `go tool asm`

*   `go tool compile`: Goソースコードをオブジェクトファイルにコンパイルするツールです。
*   `go tool asm`: アセンブリソースコード（`.s`ファイル）をオブジェクトファイルにアセンブルするツールです。このコミットの文脈では、`go tool asm` が内部的にCアセンブラまたはGoアセンブラのどちらかを使用することになります。

### `amd64` と `386`

これらはCPUアーキテクチャの名称です。
*   `amd64` (または `x86-64`): 64ビットのIntel/AMDプロセッサアーキテクチャ。現代のほとんどのデスクトップ、サーバー、ラップトップで使用されています。
*   `386` (または `x86`): 32ビットのIntel/AMDプロセッサアーキテクチャ。古いシステムや一部の組み込みシステムで使用されます。

Go言語はこれらのアーキテクチャを主要なターゲットとしてサポートしており、アセンブリコードもこれらのアーキテクチャに特化して記述されます。

### `verifyAsm` フラグ

このコミットで導入された `verifyAsm` は、Goビルドプロセス内部で使用されるフラグです。このフラグが有効な場合、アセンブラが生成するオブジェクトファイルが、新旧のアセンブラ間で一致するかどうかを検証する追加のステップが実行されます。これは開発およびテスト段階でのみ使用されるべきであり、通常のエンドユーザービルドでは無効になっています。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/go/build.go` ファイル内の `gcToolchain` 型の `asm` メソッドに集中しています。このメソッドは、Goのビルドプロセスにおいてアセンブリソースファイルをアセンブルする役割を担っています。

### `gcToolchain.asm` メソッドの変更

元のコードでは、`verifyAsm` が `true` の場合、Cアセンブラ（`tool("new" + archChar + "a")`、ここで `archChar` はアーキテクチャを示す文字、例: `6` for `amd64`）を使用してアセンブルし、その出力と通常の `go tool asm` の出力を比較していました。

変更後のコードでは、`asmVerify` という新しいヘルパー関数が導入され、検証ロジックがカプセル化されました。
`gcToolchain.asm` 内では、`verifyAsm` が `true` の場合、以下の処理が行われます。

1.  `goarch` (ターゲットアーキテクチャ) が `"386"` または `"amd64"` であることを確認します。これは、新しいアセンブラがこれらのアーキテクチャでのみサポートされているためです。
2.  `asmVerify` 関数を2回呼び出します。
    *   1回目は、新しいGoアセンブラ（`"new"+archChar+"a"`）の出力を検証します。
    *   2回目は、既存のCアセンブラ（`"asm"`）の出力を検証します。
    この二重検証により、両方のアセンブラが期待通りの出力を生成していることを確認します。

### `asmVerify` ヘルパー関数の導入

`asmVerify` 関数は、アセンブラの出力検証ロジックを抽象化するために導入されました。この関数は以下の引数を取ります。

*   `b *builder`: ビルドプロセスを管理するビルダーオブジェクト。
*   `p *Package`: 現在処理中のGoパッケージ。
*   `asm string`: 使用するアセンブラのツール名（例: `"new6a"` または `"asm"`）。
*   `ofile string`: 生成されるオブジェクトファイルのパス。
*   `args []interface{}`: アセンブラに渡す引数。

`asmVerify` 関数の内部では、以下のステップが実行されます。

1.  `newArgs` を作成し、元の `args` をコピーします。
2.  `newArgs` のアセンブラツール名を、引数で指定された `asm` に変更します。
3.  `newArgs` の出力ファイル名を、元の `ofile` に `.new` サフィックスを付けたもの（例: `x.6.new`）に変更します。
4.  `b.run` を使用して、指定されたアセンブラ（`asm`）を実行し、一時的なオブジェクトファイルを生成します。
5.  元のオブジェクトファイル (`ofile`) と、新しく生成された一時オブジェクトファイル (`ofile + ".new"`) の内容をそれぞれ読み込みます。
6.  `bytes.Equal` を使用して、これら2つのファイルのバイナリ内容が完全に一致するかどうかを比較します。
7.  もし一致しない場合、エラーを返します。このエラーメッセージには、どの2つのアセンブラが異なる出力を生成したか、およびそれらの実行コマンドが含まれます。

### `bytes.Equal` によるビット単位の比較

`bytes.Equal` は、2つのバイトスライスが同じ長さで、かつすべての要素が同じである場合に `true` を返します。この関数を使用することで、アセンブラが生成したオブジェクトファイルが、ビット単位で完全に同一であることを厳密に検証しています。これは、アセンブラの出力がわずかでも異なると、プログラムの動作に予期せぬ影響を与える可能性があるため、非常に重要なチェックです。

### 依存関係 `https://go-review.googlesource.com/4502`

コミットメッセージに記載されている `Depends on https://go-review.googlesource.com/4502` は、このコミットが別の変更セットに依存していることを示しています。通常、このような依存関係は、新しいアセンブラ自体の導入や、そのアセンブラが生成するコードに影響を与える変更など、この検証テストが機能するために必要な前提となる変更を指します。

## コアとなるコードの解説

### `gcToolchain.asm` の変更点

*   **変更前**: `verifyAsm` が `true` の場合、直接 `new` プレフィックス付きのアセンブラ（Goアセンブラ）を実行し、その出力と既存の出力とを比較していました。この比較ロジックは `asm` メソッド内に直接記述されていました。
*   **変更後**:
    *   `asmVerify` という新しい関数が導入され、検証ロジックがこの関数に移動しました。これにより、コードの可読性と再利用性が向上しています。
    *   `verifyAsm` が `true` の場合、まず `new` プレフィックス付きのアセンブラ（Goアセンブラ）に対して `asmVerify` を呼び出します。
    *   次に、`goarch` が `"386"` または `"amd64"` の場合に限り、通常の `"asm"` ツール（Cアセンブラ）に対しても `asmVerify` を呼び出します。これは、新しいアセンブラがこれらのアーキテクチャでのみ関連性があるためです。
    *   この二段階の検証により、GoアセンブラとCアセンブラの両方が、それぞれ期待される出力を生成していることを確認します。

### `asmVerify` 関数の詳細

`asmVerify` 関数は、アセンブラの出力検証の共通ロジックを encapsulating しています。

1.  **引数の準備**:
    *   `newArgs := make([]interface{}, len(args))` と `copy(newArgs, args)` で、アセンブラ実行のための引数スライスをコピーします。
    *   `newArgs[1] = tool(asm)`: 実行するアセンブラツール（例: `new6a` または `asm`）を設定します。`tool` 関数は、Goツールチェイン内の特定のツールへのパスを解決します。
    *   `newArgs[3] = ofile + ".new"`: 生成される一時的なオブジェクトファイルのパスを設定します。これにより、元のオブジェクトファイルを上書きすることなく、比較用のファイルを作成できます。

2.  **アセンブラの実行**:
    *   `b.run(p.Dir, p.ImportPath, nil, newArgs...)` を使用して、指定されたアセンブラを実行します。`b.run` は、指定されたディレクトリでコマンドを実行し、エラーがあれば返します。

3.  **ファイルの読み込み**:
    *   `ioutil.ReadFile(ofile)` と `ioutil.ReadFile(ofile + ".new")` で、元のオブジェクトファイルと一時的に生成されたオブジェクトファイルの内容をバイトスライスとして読み込みます。

4.  **バイナリ比較**:
    *   `!bytes.Equal(data1, data2)`: 読み込んだ2つのバイトスライスがビット単位で一致しない場合、エラーを生成します。
    *   エラーメッセージは、どの2つのアセンブラ（例: `6a` と `new6a`）が異なる出力を生成したか、およびそれぞれの実行コマンドを示し、デバッグに役立つ情報を提供します。

この `asmVerify` 関数の導入により、アセンブラの検証ロジックが明確に分離され、将来的な拡張やメンテナンスが容易になっています。また、`bytes.Equal` を用いた厳密なバイナリ比較は、GoアセンブラがCアセンブラと完全に互換性のあるコードを生成するという重要な要件を満たすための堅牢なメカニズムを提供しています。

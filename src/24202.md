# [インデックス 24202] ファイルの概要

このコミットは、Goの標準ライブラリである`encoding/json`パッケージにおける、`TextUnmarshaler`インターフェースを実装する型への非文字列JSON値のアンマーシャリングに関するバグ修正です。具体的には、JSONデコーダが「out of phase」状態に陥るのを防ぐための変更が加えられています。

## コミット

`encoding/json`パッケージにおいて、`TextUnmarshaler`を実装する型に非文字列のJSON値をアンマーシャリングしようとした際に発生する「out of phase」エラーを修正します。

## 変更の背景

このコミットは、Goの`encoding/json`パッケージが、`encoding.TextUnmarshaler`インターフェースを実装するGoの型に対して、JSONの非文字列値（例えば数値、ブーリアン、nullなど）をデコードしようとした際に発生する特定のバグを修正するために導入されました。

`TextUnmarshaler`インターフェースは、JSONの文字列値をGoのカスタム型に変換するために設計されています。しかし、JSONデータが文字列ではなく、例えば`123`のような数値であった場合、`json.Unmarshal`は内部的に`UnmarshalText`メソッドを呼び出そうとします。このとき、`UnmarshalText`は文字列以外の入力を処理できないため、エラーを返します。

問題は、このエラーが発生した後のデコーダの内部状態管理にありました。以前の実装では、`UnmarshalText`がエラーを返した後も、デコーダはJSONストリーム内の問題のある非文字列トークンを適切にスキップせず、その結果、デコーダの内部ポインタが実際のJSON構造と「out of phase」（同期がずれた状態）になっていました。この「out of phase」状態は、後続のJSONデータの解析を誤らせ、予期せぬデコードエラーや、場合によってはパニックを引き起こす可能性がありました。

このコミットは、このような状況でデコーダが正しくエラーを処理し、JSONストリームの残りの部分を適切にスキップして、デコーダの状態を整合性の取れたものに保つことを目的としています。

## 前提知識の解説

このコミットの理解には、以下のGoの概念と`encoding/json`パッケージの動作に関する知識が役立ちます。

*   **`encoding/json`パッケージ**: Goの標準ライブラリの一部で、Goのデータ構造とJSONデータの間で変換（マーシャリングとアンマーシャリング）を行う機能を提供します。
*   **`json.Unmarshal`関数**: JSON形式のバイトスライスをGoの指定されたデータ構造にデコードする主要な関数です。この関数は、リフレクションを使用してGoの型のフィールドを検査し、対応するJSON値を割り当てます。
*   **`encoding.TextUnmarshaler`インターフェース**:
    ```go
    type TextUnmarshaler interface {
        UnmarshalText(text []byte) error
    }
    ```
    このインターフェースは、Goのカスタム型がJSONの文字列値をどのようにデコードするかを定義するために使用されます。`json.Unmarshal`は、デコード対象のGoのフィールドがこのインターフェースを実装している場合、JSONの文字列値をその`UnmarshalText`メソッドにバイトスライスとして渡し、カスタムデコードロジックを実行させます。例えば、`time.Time`型は`TextUnmarshaler`を実装しており、特定のフォーマットのタイムスタンプ文字列を`time.Time`オブジェクトに変換します。
*   **JSONのデータ型とGoの型マッピング**: JSONには、文字列、数値、ブーリアン、null、オブジェクト、配列といった基本的なデータ型があります。`json.Unmarshal`はこれらのJSON型をGoの適切な型（例：JSON文字列はGoの`string`、JSON数値はGoの`int`や`float64`など）にマッピングしようとします。`TextUnmarshaler`は、JSONの文字列型に特化したカスタムマッピングを提供します。
*   **デコーダの内部状態**: `encoding/json`パッケージの内部には、JSONストリームを効率的に解析するための複雑な状態管理ロジックがあります。これには、現在の読み取り位置（オフセット）、次に期待されるJSONトークンの種類、エラー状態などが含まれます。この状態が、実際に読み取られたJSONトークンと一致しない場合、デコーダは「out of phase」状態に陥り、後続の解析が失敗する可能性があります。
*   **`UnmarshalTypeError`**: `json.Unmarshal`が、期待されるGoの型と互換性のないJSON値に遭遇した場合に返すエラー型です。例えば、Goの`int`型にJSONの文字列をアンマーシャリングしようとした場合などに発生します。

## 技術的詳細

この修正は、`src/encoding/json/decode.go`内の`literalStore`メソッドに焦点を当てています。このメソッドは、JSONのプリミティブ値（文字列、数値、ブーリアン、null）をGoの対応する値に格納する役割を担っています。

問題のシナリオは以下の通りです。
1.  `json.Unmarshal`が、`encoding.TextUnmarshaler`を実装するGoの型（`v`）にJSON値をデコードしようとします。
2.  JSONストリームから読み取られた値（`item`）が、実際には文字列ではない（例: `123`という数値）。
3.  `literalStore`メソッド内で、`TextUnmarshaler`の処理パスに入ります。
4.  `v.Interface().(TextUnmarshaler).UnmarshalText(item)`が呼び出されます。ここで`item`は非文字列のバイトスライスです。
5.  `UnmarshalText`の実装は、非文字列の入力を処理できないため、エラーを返します。例えば、`net.IP`型は`TextUnmarshaler`を実装していますが、`UnmarshalText`はIPアドレス形式の文字列を期待します。`123`のような数値が渡されると、パースエラーを返します。
6.  以前の実装では、この`UnmarshalText`からのエラーが`d.saveError`で記録された後、`literalStore`メソッドは`return`せずに処理を続行していました。
7.  `UnmarshalText`がエラーを返したにもかかわらず、デコーダはJSONストリーム内の問題のあった非文字列トークンを適切に消費（スキップ）していませんでした。その結果、デコーダの内部状態（`d.off`などのオフセット）が、実際のJSONストリームの読み取り位置と一致しなくなり、「out of phase」状態に陥りました。
8.  この「out of phase」状態が、後続のJSONトークンの誤った解釈や、さらなるエラー（例えば、予期せぬEOFや構文エラー）を引き起こしていました。

修正は、`UnmarshalText`がエラーを返した場合に、`literalStore`メソッドから即座に`return`することで、この問題を解決します。これにより、デコーダはエラーを記録した後、それ以上誤った状態での処理を続行せず、呼び出し元に制御を戻します。これにより、デコーダの内部状態が不整合になることを防ぎ、後続のデコード処理が正しく行われるか、または適切なエラーで終了するようになります。

## コアとなるコードの解説

### `src/encoding/json/decode.go`の変更

`literalStore`関数内の変更は非常にシンプルですが、効果的です。

```go
			} else {
				d.saveError(&UnmarshalTypeError{"string", v.Type(), int64(d.off)})
			}
			return // この行が追加された
		}
		s, ok := unquoteBytes(item)
		if !ok {
```

この`return`文が追加される前は、`TextUnmarshaler`の`UnmarshalText`メソッドがエラーを返した場合（つまり、非文字列のJSON値が渡された場合）、`d.saveError`でエラーが記録された後も、`literalStore`関数は後続の処理を続行していました。具体的には、`s, ok := unquoteBytes(item)`という行が実行されようとします。しかし、`item`は既に`UnmarshalText`で処理され（そして失敗し）、デコーダの内部状態は非文字列トークンを消費していないため、この`unquoteBytes`の呼び出しは誤ったコンテキストで行われることになります。

追加された`return`文は、`UnmarshalText`がエラーを返した場合に、`literalStore`関数がそれ以上の処理をせずに即座に終了することを保証します。これにより、デコーダの内部状態が不整合になることを防ぎ、JSONストリームの「out of phase」エラーを回避します。エラーは`d.saveError`によって適切に記録され、`json.Unmarshal`の呼び出し元に返されます。

### `src/encoding/json/decode_test.go`の変更

`TestInvalidUnmarshalText`という新しいテスト関数が追加されました。このテストは、`TextUnmarshaler`を実装する型（この場合は`*net.IP`）に対して、JSONの非文字列値（`123`）をアンマーシャリングしようとしたときに、期待されるエラーが返されることを検証します。

```go
var invalidUnmarshalTextTests = []struct {
	v    interface{}
	want string
}{
	// ... 既存のテストケース ...
	{new(net.IP), "json: cannot unmarshal string into Go value of type *net.IP"},
}

func TestInvalidUnmarshalText(t *testing.T) {
	buf := []byte(`123`) // JSONの非文字列値（数値）
	for _, tt := range invalidUnmarshalTextTests {
		err := Unmarshal(buf, tt.v)
		if err == nil {
			t.Errorf("Unmarshal expecting error, got nil")
			continue
		}
		if got := err.Error(); got != tt.want {
			t.Errorf("Unmarshal = %q; want %q", got, tt.want)
		}
	}
}
```

このテストの重要な点は、`new(net.IP)`という`TextUnmarshaler`を実装する型に対して、JSONの数値`123`をアンマーシャリングしようとすることです。`net.IP`の`UnmarshalText`メソッドはIPアドレス形式の文字列を期待するため、`123`が渡されるとエラーを返します。このテストは、そのエラーが正しく捕捉され、デコーダが「out of phase」状態に陥らずに、期待されるエラーメッセージ（`json: cannot unmarshal string into Go value of type *net.IP`）を返すことを確認します。

このテストの追加により、以前のバグが修正されたことを検証し、将来的に同様の回帰が発生しないように保護されます。

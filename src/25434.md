# [インデックス 25434] ファイルの概要

このコミットは、Goリンカが動的リンクを行う際に、モジュール内で定義された関数への参照が常にその関数オブジェクト自体を指すようにする変更を導入しています。これは、Procedure Linkage Table (PLT) を介した間接的な参照を回避し、ELFリンカの `-Bsymbolic-functions` オプションが抱えるプラットフォーム依存のバグを回避するための、Goリンカ独自のシンボル解決戦略の実装です。具体的には、グローバルな関数シンボルに対して追加のローカルシンボルを生成し、そのグローバルシンボルに対する全てのリロケーションをこのローカルシンボルにリダイレクトすることで実現しています。

## コミット

```
cmd/link: always resolve functions locally when linking dynamically

When dynamically linking, we want references to functions defined
in this module to always be to the function object, not to the
PLT. We force this by writing an additional local symbol for
every global function symbol and making all relocations against
the global symbol refer to this local symbol instead. This is
approximately equivalent to the ELF linker -Bsymbolic-functions
option, but that is buggy on several platforms.

Reviewed-on: https://go-review.googlesource.com/16436
Reviewed-by: Ian Lance Taylor <iant@golang.org>
```

## 元コミット内容

動的リンクを行う際、現在のモジュール内で定義された関数への参照は、PLT（Procedure Linkage Table）ではなく、常にその関数オブジェクト自体を指すようにしたい。
これを実現するために、全てのグローバル関数シンボルに対して追加のローカルシンボルを書き込み、グローバルシンボルに対する全てのリロケーションをこのローカルシンボルを参照するように変更する。
これはELFリンカの `-Bsymbolic-functions` オプションとほぼ同等だが、そのオプションはいくつかのプラットフォームでバグがあるため、この独自の実装を採用する。

## 変更の背景

Goプログラムは通常、静的リンクを志向していますが、`cgo` を使用する場合や、特定のビルドモード（例: `BuildmodeShared`）では動的リンクが行われます。動的リンクされたプログラムでは、外部ライブラリの関数を呼び出す際に、その関数のアドレスを解決するためにPLT (Procedure Linkage Table) と GOT (Global Offset Table) という仕組みが利用されます。

しかし、モジュール（共有ライブラリや実行ファイル）内で定義された関数を、そのモジュール自身が呼び出す場合でも、デフォルトの動的リンクの挙動ではPLTを介して解決されることがあります。これは、シンボル解決のオーバーヘッドを発生させるだけでなく、シンボルプリエンプション（symbol preemption、またはinterposition）という問題を引き起こす可能性があります。シンボルプリエンプションとは、同じ名前のシンボルが複数の共有ライブラリや実行ファイルに存在する場合に、どの定義が実際に使用されるかが実行時に決定される挙動です。これにより、モジュールが自身の内部関数を呼び出しているつもりが、誤って外部の異なる定義を呼び出してしまう、といった予期せぬ動作やバグにつながる可能性があります。

ELFリンカには、このような問題を緩和するために `-Bsymbolic-functions` というオプションが存在します。このオプションは、共有ライブラリ内で定義された関数シンボルを非プリエンプティブ（non-preemptible）にし、その共有ライブラリ内部からの関数呼び出しが常に自身の定義にバインドされるようにします。しかし、コミットメッセージにある通り、この `-Bsymbolic-functions` オプションは「いくつかのプラットフォームでバグがある」という問題がありました。

このコミットは、外部リンカのバグのあるオプションに依存するのではなく、Goリンカ自身が同様のセマンティクスを安全かつ確実に実現するための内部的なメカニズムを導入することを目的としています。これにより、Goの動的リンクの堅牢性と予測可能性が向上します。

## 前提知識の解説

### 1. ELF (Executable and Linkable Format)
LinuxなどのUnix系システムで実行ファイル、共有ライブラリ、オブジェクトファイルなどのバイナリ形式として広く使われている標準フォーマットです。プログラムのコード、データ、シンボル情報、リロケーション情報などが構造化されて格納されています。

### 2. 動的リンク (Dynamic Linking)
プログラムの実行時に、必要なライブラリ（共有ライブラリ、Shared Object: SO）をメモリにロードし、それらのライブラリ内の関数やデータにリンクする手法です。
*   **利点**: 実行ファイルのサイズ削減、メモリ使用量の効率化（複数のプログラムで同じライブラリを共有）、ライブラリの更新が容易。
*   **欠点**: 実行時のリンク処理によるオーバーヘッド、ライブラリの依存関係管理の複雑さ（DLL Hellなど）。

### 3. シンボル (Symbol)
プログラム内の関数やグローバル変数などの名前付きエンティティです。リンカはこれらのシンボルを使って、コード内の参照を実際のメモリ上のアドレスに解決します。
*   **グローバルシンボル (Global Symbol)**: 外部から参照可能、または外部の定義を参照するシンボル。
*   **ローカルシンボル (Local Symbol)**: 定義されたオブジェクトファイルやモジュール内でのみ参照可能なシンボル。

### 4. リロケーション (Relocation)
コンパイル時にアドレスが確定できないシンボル参照（例: 外部ライブラリの関数呼び出し）について、リンカが実行ファイルや共有ライブラリを生成する際に、正しいメモリアドレスを埋め込む処理です。動的リンクの場合、一部のリロケーションはプログラムのロード時に動的リンカによって行われます。

### 5. PLT (Procedure Linkage Table) と GOT (Global Offset Table)
動的リンクにおける外部関数呼び出しを解決するための主要なメカニズムです。
*   **PLT**: 実行ファイル内の読み取り専用セクションで、外部関数呼び出しのための小さなコードスタブ（トラポリン）を含みます。プログラムが外部関数を初めて呼び出す際、PLTエントリにジャンプします。
*   **GOT**: 実行ファイル内の書き込み可能セクションで、外部関数やグローバル変数の実際のアドレスが格納されます。PLTエントリはGOTエントリを介して実際の関数アドレスにジャンプします。
*   **遅延バインディング (Lazy Binding)**: 外部関数のアドレスは、その関数が初めて呼び出されるまで解決されません。初回呼び出し時にPLTとGOTが連携して動的リンカを呼び出し、実際の関数アドレスを解決してGOTに書き込みます。2回目以降の呼び出しでは、GOTに格納されたアドレスに直接ジャンプするため、高速になります。

### 6. シンボルプリエンプション (Symbol Preemption / Interposition)
動的リンクされたプログラムにおいて、同じ名前のグローバルシンボルが複数の共有ライブラリや実行ファイルに存在する場合、実行時にどの定義が使われるかが決定される挙動です。通常、先にロードされたライブラリのシンボルが優先されるか、メイン実行ファイルのシンボルが優先されるかなど、システムやリンカのオプションによって挙動が変わります。これにより、モジュールが自身の内部関数を呼び出しているつもりが、外部の異なる定義を呼び出してしまう「横取り」が発生する可能性があります。

### 7. `-Bsymbolic-functions` リンカオプション
GNUリンカ (`ld`) のオプションの一つで、共有ライブラリをビルドする際に使用されます。このオプションを付けると、その共有ライブラリ内で定義されたグローバルな関数シンボルが非プリエンプティブになります。つまり、その共有ライブラリ内部からの関数呼び出しは、常に自身の定義にバインドされ、外部の同じ名前の関数によって「横取り」されることがなくなります。これにより、パフォーマンスの向上（PLTを介さない直接呼び出しが可能になるため）と、ライブラリの内部的な一貫性の保証が期待できます。ただし、コミットメッセージにあるように、このオプションはプラットフォームによってはバグがあったり、`LD_PRELOAD`のようなデバッグ・フック機構との相性が悪い場合もあります。

## 技術的詳細

このコミットの核心は、Goリンカが動的リンク時に、モジュール内部の関数呼び出しをPLTを介さずに直接解決するための独自の戦略を実装した点にあります。これは、外部リンカの `-Bsymbolic-functions` オプションが抱える問題を回避しつつ、同様の効果を得るためのものです。

具体的なアプローチは以下の通りです。

1.  **`LSym` 構造体の拡張**:
    Goリンカがシンボル情報を管理するために使用する `LSym` 構造体に、`LocalElfsym int32` という新しいフィールドが追加されました。このフィールドは、グローバル関数シンボルに対して特別に生成される「ローカルなELFシンボル」のインデックスを格納するために使用されます。

2.  **`ElfsymForReloc()` メソッドの導入**:
    `LSym` 構造体に `ElfsymForReloc()` という新しいメソッドが追加されました。このメソッドは、リロケーション処理において、どのELFシンボルを参照すべきかを決定します。
    *   もし `s.LocalElfsym` がゼロでない（つまり、このシンボルに対してローカルなELFシンボルが生成されている）場合、`s.LocalElfsym` の値を返します。
    *   そうでなければ、通常の `s.Elfsym` の値を返します。
    これにより、リロケーションは、もし存在すればローカルシンボルを優先的に参照するようになります。

3.  **`putelfsym` 関数でのローカルシンボル生成ロジックの追加**:
    `src/cmd/link/internal/ld/symtab.go` 内の `putelfsym` 関数は、ELFシンボルテーブルにエントリを追加する役割を担っています。この関数に、動的リンク時 (`DynlinkingGo()`) に特定の条件を満たすグローバル関数シンボル (`bind == STB_GLOBAL && elfbind == STB_LOCAL && x.Type == obj.STEXT`) に対して、追加のローカルシンボルを生成するロジックが追加されました。
    *   このローカルシンボルは、元のグローバルシンボル名に "local." というプレフィックスを付けた名前で (`"local."+s`)、`STB_LOCAL` バインディングタイプでELFシンボルテーブルに書き込まれます。
    *   新しく生成されたローカルシンボルのインデックスは、元のグローバルシンボルの `LSym` 構造体の `LocalElfsym` フィールドに格納されます。
    *   `numelfsym` はELFシンボルテーブル内のシンボル数を追跡するカウンタであり、新しいシンボルが追加されるたびにインクリメントされます。

4.  **リロケーション処理の変更**:
    `src/cmd/link/internal/amd64/asm.go`、`src/cmd/link/internal/arm/asm.go`、`src/cmd/link/internal/arm64/asm.go`、`src/cmd/link/internal/x86/asm.go`、`src/cmd/link/internal/ld/elf.go` の各アーキテクチャ固有のリロケーション処理コードにおいて、シンボルのELFインデックスを参照する箇所が `r.Xsym.Elfsym` から `r.Xsym.ElfsymForReloc()` に変更されました。これにより、リロケーションは、グローバル関数シンボルに対して生成されたローカルシンボルを優先的に参照するようになります。

この一連の変更により、Goリンカは、動的リンクされたGoモジュール内で定義された関数への内部参照が、PLTを介さずに直接その関数オブジェクトに解決されることを保証します。これは、外部リンカの `-Bsymbolic-functions` オプションが提供する機能と同等ですが、Goリンカが内部で制御するため、プラットフォーム間の互換性やバグの問題を回避できます。

## コアとなるコードの変更箇所

### `src/cmd/link/internal/ld/link.go`
`LSym` 構造体に `LocalElfsym` フィールドが追加され、`ElfsymForReloc()` メソッドが定義されました。

```go
type LSym struct {
	// ... 既存のフィールド ...
	Got         int32
	Align       int32
	Elfsym      int32
	LocalElfsym int32 // 追加: ローカルELFシンボルのインデックス
	Args        int32
	Locals      int32
	Value       int64
	// ... 既存のフィールド ...
}

func (s *LSym) ElfsymForReloc() int32 {
	// このシンボルに対してローカルバージョンが作成されている場合、全てのリロケーションでそれを使用する
	if s.LocalElfsym != 0 {
		return s.LocalElfsym
	} else {
		return s.Elfsym
	}
}
```

### `src/cmd/link/internal/ld/symtab.go`
`putelfsym` 関数内で、動的リンク時にグローバル関数シンボルに対して追加のローカルシンボルを生成するロジックが追加されました。

```go
func putelfsym(x *LSym, s string, t int, addr int64, size int64, ver int, go_ *LSym) {
	// ... 既存のコード ...

	// 変更前:
	// if bind != elfbind {
	// 	return
	// }

	// 変更後:
	if DynlinkingGo() && bind == STB_GLOBAL && elfbind == STB_LOCAL && x.Type == obj.STEXT {
		// 動的リンク時、このモジュール内で定義された関数への参照が常にPLTではなく
		// 関数オブジェクト自体を指すようにしたい。
		// これを強制するために、全てのグローバル関数シンボルに対して追加のローカルシンボルを書き込み、
		// グローバルシンボルに対する全てのリロケーションをこのローカルシンボルを参照するようにする
		// (LSym).ElfsymForReloc を参照)。これはELFリンカの -Bsymbolic-functions オプションと
		// ほぼ同等だが、そのオプションはいくつかのプラットフォームでバグがある。
		putelfsyment(putelfstr("local."+s), addr, size, STB_LOCAL<<4|type_&0xf, elfshnum, other)
		x.LocalElfsym = int32(numelfsym)
		numelfsym++
	} else if bind != elfbind { // 変更前のロジックがこのelse ifに移動
		return
	}

	putelfsyment(putelfstr(s), addr, size, bind<<4|type_&0xf, elfshnum, other)
	x.Elfsym = int32(numelfsym)
	numelfsym++
}
```

## コアとなるコードの解説

このコミットの主要な変更は、Goリンカが動的リンク時に、モジュール内部の関数呼び出しをPLTを介さずに直接解決するためのカスタムメカニズムを導入したことです。

1.  **`LSym.LocalElfsym` の追加**:
    `LSym` はGoリンカが扱うシンボルを表す構造体です。`LocalElfsym` フィールドが追加されたことで、各シンボルは通常のELFシンボルインデックス (`Elfsym`) に加えて、そのシンボルがグローバル関数であり、かつローカルな解決を意図している場合に生成される「ローカル版ELFシンボル」のインデックスを保持できるようになりました。これにより、シンボルごとに異なる解決パスを指示する柔軟性が生まれます。

2.  **`LSym.ElfsymForReloc()` メソッド**:
    このメソッドは、リロケーション処理がシンボルを参照する際に、どのELFシンボルインデックスを使用すべきかを決定するゲートウェイとなります。もし `LocalElfsym` が設定されていれば、それはこのシンボルが内部的にローカル解決されるべきグローバル関数であることを意味するため、`LocalElfsym` の値を返します。そうでなければ、通常の `Elfsym` を返します。この抽象化により、リロケーション処理のコードは、シンボルがどのように解決されるべきかという詳細を知る必要がなくなります。

3.  **`putelfsym` におけるローカルシンボル生成**:
    `putelfsym` 関数は、GoリンカがELFシンボルテーブルにシンボルエントリを書き込む際に呼び出されます。このコミットで追加されたロジックは、以下の条件が全て満たされた場合に発動します。
    *   `DynlinkingGo()`: 現在Goコードが動的リンクされている。
    *   `bind == STB_GLOBAL`: シンボルがグローバルバインディングを持つ。
    *   `elfbind == STB_LOCAL`: リンカがこのシンボルを現在のモジュール内でローカルとして扱うことを意図している。
    *   `x.Type == obj.STEXT`: シンボルが関数（テキストセクション）である。
    これらの条件が揃った場合、Goリンカは元のグローバル関数シンボルとは別に、`"local."` プレフィックスを持つ新しいローカルシンボルをELFシンボルテーブルに生成します。そして、この新しいローカルシンボルのインデックスを元のグローバルシンボルの `LSym.LocalElfsym` フィールドに格納します。これにより、このグローバル関数への内部参照は、`ElfsymForReloc()` を介してこの新しく生成されたローカルシンボルにリダイレクトされるようになります。

4.  **リロケーション処理の統一的な変更**:
    `amd64`, `arm`, `arm64`, `x86` といった各アーキテクチャ固有のアセンブラコードや、共通のELFリロケーション処理 (`elf.go`) において、シンボルのELFインデックスを取得する箇所が `r.Xsym.Elfsym` から `r.Xsym.ElfsymForReloc()` に変更されました。この変更は、上記で説明した `ElfsymForReloc()` メソッドの導入と連携し、リロケーションが適切にローカルシンボルを参照するようにします。

5.  **`-Bsymbolic-functions` の削除**:
    `lib.go` から外部リンカの `-Wl,-Bsymbolic-functions` オプションが削除されたことは、Goリンカがこの問題を外部ツールに依存するのではなく、自身の内部メカニズムで解決するという明確な方針転換を示しています。これにより、外部リンカのバグやプラットフォーム依存性から解放され、Goの動的リンクの挙動がより予測可能で堅牢になります。

これらの変更により、Goリンカは、動的リンクされたGoモジュールが自身の内部関数を呼び出す際に、PLTを介した間接的な呼び出しやシンボルプリエンプションのリスクを回避し、常に直接的かつ効率的に自身の定義にバインドされることを保証します。

## 元コミット内容

動的リンクを行う際、現在のモジュール内で定義された関数への参照は、PLT（Procedure Linkage Table）ではなく、常にその関数オブジェクト自体を指すようにしたい。
これを実現するために、全てのグローバル関数シンボルに対して追加のローカルシンボルを書き込み、グローバルシンボルに対する全てのリロケーションをこのローカルシンボルを参照するように変更する。
これはELFリンカの `-Bsymbolic-functions` オプションとほぼ同等だが、そのオプションはいくつかのプラットフォームでバグがあるため、この独自の実装を採用する。

## 変更の背景

Goプログラムは通常、静的リンクを志向していますが、`cgo` を使用する場合や、特定のビルドモード（例: `BuildmodeShared`）では動的リンクが行われます。動的リンクされたプログラムでは、外部ライブラリの関数を呼び出す際に、その関数のアドレスを解決するためにPLT (Procedure Linkage Table) と GOT (Global Offset Table) という仕組みが利用されます。

しかし、モジュール（共有ライブラリや実行ファイル）内で定義された関数を、そのモジュール自身が呼び出す場合でも、デフォルトの動的リンクの挙動ではPLTを介して解決されることがあります。これは、シンボル解決のオーバーヘッドを発生させるだけでなく、シンボルプリエンプション（symbol preemption、またはinterposition）という問題を引き起こす可能性があります。シンボルプリエンプションとは、同じ名前のシンボルが複数の共有ライブラリや実行ファイルに存在する場合に、どの定義が実際に使用されるかが実行時に決定される挙動です。これにより、モジュールが自身の内部関数を呼び出しているつもりが、誤って外部の異なる定義を呼び出してしまう、といった予期せぬ動作やバグにつながる可能性があります。

ELFリンカには、このような問題を緩和するために `-Bsymbolic-functions` というオプションが存在します。このオプションは、共有ライブラリ内で定義された関数シンボルを非プリエンプティブ（non-preemptible）にし、その共有ライブラリ内部からの関数呼び出しが常に自身の定義にバインドされるようにします。しかし、コミットメッセージにある通り、この `-Bsymbolic-functions` オプションは「いくつかのプラットフォームでバグがある」という問題がありました。

このコミットは、外部リンカのバグのあるオプションに依存するのではなく、Goリンカ自身が同様のセマンティクスを安全かつ確実に実現するための内部的なメカニズムを導入することを目的としています。これにより、Goの動的リンクの堅牢性と予測可能性が向上します。

## 前提知識の解説

### 1. ELF (Executable and Linkable Format)
LinuxなどのUnix系システムで実行ファイル、共有ライブラリ、オブジェクトファイルなどのバイナリ形式として広く使われている標準フォーマットです。プログラムのコード、データ、シンボル情報、リロケーション情報などが構造化されて格納されています。

### 2. 動的リンク (Dynamic Linking)
プログラムの実行時に、必要なライブラリ（共有ライブラリ、Shared Object: SO）をメモリにロードし、それらのライブラリ内の関数やデータにリンクする手法です。
*   **利点**: 実行ファイルのサイズ削減、メモリ使用量の効率化（複数のプログラムで同じライブラリを共有）、ライブラリの更新が容易。
*   **欠点**: 実行時のリンク処理によるオーバーヘッド、ライブラリの依存関係管理の複雑さ（DLL Hellなど）。

### 3. シンボル (Symbol)
プログラム内の関数やグローバル変数などの名前付きエンティティです。リンカはこれらのシンボルを使って、コード内の参照を実際のメモリ上のアドレスに解決します。
*   **グローバルシンボル (Global Symbol)**: 外部から参照可能、または外部の定義を参照するシンボル。
*   **ローカルシンボル (Local Symbol)**: 定義されたオブジェクトファイルやモジュール内でのみ参照可能なシンボル。

### 4. リロケーション (Relocation)
コンパイル時にアドレスが確定できないシンボル参照（例: 外部ライブラリの関数呼び出し）について、リンカが実行ファイルや共有ライブラリを生成する際に、正しいメモリアドレスを埋め込む処理です。動的リンクの場合、一部のリロケーションはプログラムのロード時に動的リンカによって行われます。

### 5. PLT (Procedure Linkage Table) と GOT (Global Offset Table)
動的リンクにおける外部関数呼び出しを解決するための主要なメカニズムです。
*   **PLT**: 実行ファイル内の読み取り専用セクションで、外部関数呼び出しのための小さなコードスタブ（トラポリン）を含みます。プログラムが外部関数を初めて呼び出す際、PLTエントリにジャンプします。
*   **GOT**: 実行ファイル内の書き込み可能セクションで、外部関数やグローバル変数の実際のアドレスが格納されます。PLTエントリはGOTエントリを介して実際の関数アドレスにジャンプします。
*   **遅延バインディング (Lazy Binding)**: 外部関数のアドレスは、その関数が初めて呼び出されるまで解決されません。初回呼び出し時にPLTとGOTが連携して動的リンカを呼び出し、実際の関数アドレスを解決してGOTに書き込みます。2回目以降の呼び出しでは、GOTに格納されたアドレスに直接ジャンプするため、高速になります。

### 6. シンボルプリエンプション (Symbol Preemption / Interposition)
動的リンクされたプログラムにおいて、同じ名前のグローバルシンボルが複数の共有ライブラリや実行ファイルに存在する場合、実行時にどの定義が使われるかが決定される挙動です。通常、先にロードされたライブラリのシンボルが優先されるか、メイン実行ファイルのシンボルが優先されるかなど、システムやリンカのオプションによって挙動が変わります。これにより、モジュールが自身の内部関数を呼び出しているつもりが、外部の異なる定義を呼び出してしまう「横取り」が発生する可能性があります。

### 7. `-Bsymbolic-functions` リンカオプション
GNUリンカ (`ld`) のオプションの一つで、共有ライブラリをビルドする際に使用されます。このオプションを付けると、その共有ライブラリ内で定義されたグローバルな関数シンボルが非プリエンプティブになります。つまり、その共有ライブラリ内部からの関数呼び出しは、常に自身の定義にバインドされ、外部の同じ名前の関数によって「横取り」されることがなくなります。これにより、パフォーマンスの向上（PLTを介さない直接呼び出しが可能になるため）と、ライブラリの内部的な一貫性の保証が期待できます。ただし、コミットメッセージにあるように、このオプションはプラットフォームによってはバグがあったり、`LD_PRELOAD`のようなデバッグ・フック機構との相性が悪い場合もあります。

## 技術的詳細

このコミットの核心は、Goリンカが動的リンク時に、モジュール内部の関数呼び出しをPLTを介さずに直接解決するための独自の戦略を実装した点にあります。これは、外部リンカの `-Bsymbolic-functions` オプションが抱える問題を回避しつつ、同様の効果を得るためのものです。

具体的なアプローチは以下の通りです。

1.  **`LSym` 構造体の拡張**:
    Goリンカがシンボル情報を管理するために使用する `LSym` 構造体に、`LocalElfsym int32` という新しいフィールドが追加されました。このフィールドは、グローバル関数シンボルに対して特別に生成される「ローカルなELFシンボル」のインデックスを格納するために使用されます。

2.  **`ElfsymForReloc()` メソッドの導入**:
    `LSym` 構造体に `ElfsymForReloc()` という新しいメソッドが追加されました。このメソッドは、リロケーション処理において、どのELFシンボルを参照すべきかを決定します。
    *   もし `s.LocalElfsym` がゼロでない（つまり、このシンボルに対してローカルなELFシンボルが生成されている）場合、`s.LocalElfsym` の値を返します。
    *   そうでなければ、通常の `s.Elfsym` の値を返します。
    これにより、リロケーションは、もし存在すればローカルシンボルを優先的に参照するようになります。

3.  **`putelfsym` 関数でのローカルシンボル生成ロジックの追加**:
    `src/cmd/link/internal/ld/symtab.go` 内の `putelfsym` 関数は、ELFシンボルテーブルにエントリを追加する役割を担っています。この関数に、動的リンク時 (`DynlinkingGo()`) に特定の条件を満たすグローバル関数シンボル (`bind == STB_GLOBAL && elfbind == STB_LOCAL && x.Type == obj.STEXT`) に対して、追加のローカルシンボルを生成するロジックが追加されました。
    *   このローカルシンボルは、元のグローバルシンボル名に "local." というプレフィックスを付けた名前で (`"local."+s`)、`STB_LOCAL` バインディングタイプでELFシンボルテーブルに書き込まれます。
    *   新しく生成されたローカルシンボルのインデックスは、元のグローバルシンボルの `LSym` 構造体の `LocalElfsym` フィールドに格納されます。
    *   `numelfsym` はELFシンボルテーブル内のシンボル数を追跡するカウンタであり、新しいシンボルが追加されるたびにインクリメントされます。

4.  **リロケーション処理の変更**:
    `src/cmd/link/internal/amd64/asm.go`、`src/cmd/link/internal/arm/asm.go`、`src/cmd/link/internal/arm64/asm.go`、`src/cmd/link/internal/x86/asm.go`、`src/cmd/link/internal/ld/elf.go` の各アーキテクチャ固有のリロケーション処理コードにおいて、シンボルのELFインデックスを参照する箇所が `r.Xsym.Elfsym` から `r.Xsym.ElfsymForReloc()` に変更されました。これにより、リロケーションは、グローバル関数シンボルに対して生成されたローカルシンボルを優先的に参照するようになります。

この一連の変更により、Goリンカは、動的リンクされたGoモジュール内で定義された関数への内部参照が、PLTを介さずに直接その関数オブジェクトに解決されることを保証します。これは、外部リンカの `-Bsymbolic-functions` オプションが提供する機能と同等ですが、Goリンカが内部で制御するため、プラットフォーム間の互換性やバグの問題を回避できます。

	// ... 既存のフィールド ...
	Got         int32
	Align       int32

	// このシンボルに対してローカルバージョンが作成されている場合、全てのリロケーションでそれを使用する
	if s.LocalElfsym != 0 {
		return s.LocalElfsym
	} else {
		return s.Elfsym
	}

## コアとなるコードの解説

このコミットの主要な変更は、Goリンカが動的リンク時に、モジュール内部の関数呼び出しをPLTを介さずに直接解決するためのカスタムメカニズムを導入したことです。

1.  **`LSym.LocalElfsym` の追加**:
    `LSym` はGoリンカが扱うシンボルを表す構造体です。`LocalElfsym` フィールドが追加されたことで、各シンボルは通常のELFシンボルインデックス (`Elfsym`) に加えて、そのシンボルがグローバル関数であり、かつローカルな解決を意図している場合に生成される「ローカル版ELFシンボル」のインデックスを保持できるようになりました。これにより、シンボルごとに異なる解決パスを指示する柔軟性が生まれます。

2.  **`LSym.ElfsymForReloc()` メソッド**:
    このメソッドは、リロケーション処理がシンボルを参照する際に、どのELFシンボルインデックスを使用すべきかを決定するゲートウェイとなります。もし `LocalElfsym` が設定されていれば、それはこのシンボルが内部的にローカル解決されるべきグローバル関数であることを意味するため、`LocalElfsym` の値を返します。そうでなければ、通常の `Elfsym` を返します。この抽象化により、リロケーション処理のコードは、シンボルがどのように解決されるべきかという詳細を知る必要がなくなります。

3.  **`putelfsym` におけるローカルシンボル生成**:
    `putelfsym` 関数は、GoリンカがELFシンボルテーブルにシンボルエントリを書き込む際に呼び出されます。このコミットで追加されたロジックは、以下の条件が全て満たされた場合に発動します。
    *   `DynlinkingGo()`: 現在Goコードが動的リンクされている。
    *   `bind == STB_GLOBAL`: シンボルがグローバルバインディングを持つ。
    *   `elfbind == STB_LOCAL`: リンカがこのシンボルを現在のモジュール内でローカルとして扱うことを意図している。
    *   `x.Type == obj.STEXT`: シンボルが関数（テキストセクション）である。
    これらの条件が揃った場合、Goリンカは元のグローバル関数シンボルとは別に、`"local."` プレフィックスを持つ新しいローカルシンボルをELFシンボルテーブルに生成します。そして、この新しいローカルシンボルのインデックスを元のグローバルシンボルの `LSym.LocalElfsym` フィールドに格納します。これにより、このグローバル関数への内部参照は、`ElfsymForReloc()` を介してこの新しく生成されたローカルシンボルにリダイレクトされるようになります。

4.  **リロケーション処理の統一的な変更**:
    `amd64`, `arm`, `arm64`, `x86` といった各アーキテクチャ固有のアセンブラコードや、共通のELFリロケーション処理 (`elf.go`) において、シンボルのELFインデックスを取得する箇所が `r.Xsym.Elfsym` から `r.Xsym.ElfsymForReloc()` に変更されました。この変更は、上記で説明した `ElfsymForReloc()` メソッドの導入と連携し、リロケーションが適切にローカルシンボルを参照するようにします。

5.  **`-Bsymbolic-functions` の削除**:
    `lib.go` から外部リンカの `-Wl,-Bsymbolic-functions` オプションが削除されたことは、Goリンカがこの問題を外部ツールに依存するのではなく、自身の内部メカニズムで解決するという明確な方針転換を示しています。これにより、外部リンカのバグやプラットフォーム依存性から解放され、Goの動的リンクの挙動がより予測可能で堅牢になります。

これらの変更により、Goリンカは、動的リンクされたGoモジュールが自身の内部関数を呼び出す際に、PLTを介した間接的な呼び出しやシンボルプリエンプションのリスクを回避し、常に直接的かつ効率的に自身の定義にバインドされることを保証します。

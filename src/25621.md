## 変更の背景
このコミットは、Goランタイムの `heapsampling.go` テストが特定のアーキテクチャで時折失敗するという、不安定な挙動（flaky test）を修正するために導入されました。この問題はGo issue #13098として報告されていました。

`heapsampling.go` テストは、Goプログラムのヒーププロファイリング機能が正しく動作し、メモリ割り当ての統計情報が正確に収集されることを検証することを目的としています。しかし、テストが実行される環境やGCのタイミングによっては、`main.alloc` 関数で割り当てられたメモリのヒーププロファイルサンプルがゼロとして報告されることがありました。

この問題の根本原因は、Goランタイムがヒーププロファイルにおけるバイト数とオブジェクト数のカウントを、ガベージコレクション（GC）が実行されるタイミングでのみ更新するという内部的な挙動にありました。具体的には、テスト内の `allocInterleaved` 関数でメモリ割り当てが行われ、その途中でGCが発生したとします。その後、`main.alloc` 関数が呼び出されてさらにメモリ割り当てが行われたにもかかわらず、プロファイル収集前に次のGCが実行されない場合、`checkAllocations` 関数は `main.alloc` 内のコード行に対応するプロファイルバケット（メモリ割り当ての発生源を示すエントリ）を検出できます。しかし、これらのバケットに関連付けられるべき実際のバイト数やオブジェクト数のカウントは、GCによる更新が行われていないため、ゼロのままとなっていました。バケット自体はメモリ割り当て時に「eagerly (積極的に)」作成されますが、その統計情報はGCによって集計されるという非同期性によって、テストが期待する正確な値が得られず、結果としてテストが失敗していたのです。

このコミットは、プロファイルデータを収集する直前に明示的にGCを強制実行することで、このタイミングの問題を解消し、テストの安定性を確保することを目的としています。

## 前提知識の解説

### Goのヒーププロファイリング
Go言語は、プログラムの実行時パフォーマンスを分析するための強力なプロファイリングツール群を提供しており、その一つがヒーププロファイリングです。ヒーププロファイリングは、プログラムがヒープメモリをどのように割り当て、使用しているかを詳細に把握するために用いられます。

*   **`runtime/pprof` パッケージ**: Goの標準ライブラリに含まれるプロファイリングパッケージです。CPU、メモリ（ヒープ）、ゴルーチンなどのプロファイル情報を収集するためのAPIを提供します。
*   **`runtime.MemProfileRecord`**: ヒーププロファイルのスナップショットを構成する個々のレコードを表す構造体です。各 `MemProfileRecord` は、特定の呼び出しスタック（メモリ割り当てが行われたコードの場所）におけるメモリ割り当ての統計情報（割り当てられたオブジェクトの総数、解放されたオブジェクトの総数、割り当てられたバイトの総数、解放されたバイトの総数など）を含みます。
*   **ヒープサンプリング**: Goのヒーププロファイラは、すべてのメモリ割り当てを記録するのではなく、デフォルトで一定の割合（例えば、512KBごとに1回）でサンプリングを行います。これにより、プロファイリングによる実行時オーバーヘッドを最小限に抑えつつ、アプリケーションの代表的なメモリ割り当てパターンを効率的に把握できます。
*   **プロファイルバケット**: ヒーププロファイリングにおいて、「バケット」とは、特定のコードパス（呼び出しスタック）で発生したメモリ割り当ての統計情報を集約する論理的なグループを指します。コミットメッセージで言及されている「buckets for the lines in main.alloc」は、`main.alloc` 関数内の特定の行でメモリ割り当てが行われた場合に生成される、その割り当て元を識別するためのプロファイルエントリを意味します。

### Goのガベージコレクション (GC)
Goランタイムは、自動メモリ管理のためにトレース型ガベージコレクタ（GC）を採用しています。GCの主な役割は、プログラムがもはや到達不能になったメモリ領域を自動的に識別し、解放することで、メモリリークを防ぎ、開発者が手動でメモリを管理する負担を軽減することです。

*   **GCのトリガー**: GoのGCは、主に以下の条件でトリガーされます。
    *   **ヒープ使用量の閾値**: 前回のGC完了後のヒープ使用量が、設定された閾値（`GOGC` 環境変数で制御される）を超えた場合。
    *   **明示的な呼び出し**: `runtime.GC()` 関数がプログラムコードから明示的に呼び出された場合。
    *   **メモリ割り当ての失敗**: メモリ割り当て要求が失敗した場合（非常に稀）。
*   **プロファイル情報の更新とGCの関連性**: このコミットの核心的な問題は、ヒーププロファイルにおける「バイト数」と「オブジェクト数」の統計情報が、Goランタイムの内部でGCの実行時に集計され、更新されるという点にあります。つまり、GCが実行されない限り、最新のメモリ割り当て状況がプロファイルデータに完全に反映されない可能性があるのです。これは、メモリ割り当て自体は即座に発生し、プロファイルバケットも作成されますが、その割り当ての「量」に関する統計的な集計はGCサイクルの一部として行われるためです。

## 技術的詳細
`heapsampling.go` テストは、`main` 関数内で `allocInterleaved` と `main.alloc` という二つの関数を呼び出して意図的にメモリを割り当てます。その後、`getMemProfileRecords()` を呼び出して現在のヒーププロファイルのスナップショットを取得し、`checkAllocations` 関数でそのプロファイルデータが期待される値と一致するかを検証します。

問題が発生したのは、`allocInterleaved` の実行中にGCが一度発生し、その後 `main.alloc` が呼び出されてメモリ割り当てが行われたにもかかわらず、`getMemProfileRecords()` が呼び出される前に次のGCが実行されないという特定のタイミングでした。

このシナリオでは、`main.alloc` 内で発生したメモリ割り当てに対して、プロファイラは対応するプロファイルバケットを「積極的に (eagerly)」作成します。これは、どのコードパスでメモリが割り当てられたかという情報は、割り当てが発生した時点で記録されるためです。しかし、これらのバケットに記録されるべき「割り当てられたバイト数」や「割り当てられたオブジェクト数」といった統計情報は、Goランタイムの設計上、次のGCサイクルが完了するまで集計・更新されません。

その結果、`checkAllocations` 関数がプロファイルデータを検証する際、`main.alloc` に対応するバケットは存在しますが、その中のバイト数やオブジェクト数のカウントはゼロのままとなっていました。テストはこれらのカウントがゼロではないことを期待しているため、この不一致によりテストが失敗し、不安定な挙動を示していました。

この問題を解決するために、`getMemProfileRecords()` 関数内でプロファイルデータを取得する直前に `runtime.GC()` を明示的に呼び出す変更が加えられました。`runtime.GC()` を呼び出すことで、Goランタイムは強制的にガベージコレクションを実行します。このGCの実行プロセス中に、それまでに発生したすべてのメモリ割り当てに関する保留中のヒーププロファイル統計情報が確実に集計され、更新されます。これにより、`runtime.MemProfile()` が呼び出されてプロファイルデータが取得される際には、常に最新かつ正確なバイト数とオブジェクト数が反映されるようになり、GCのタイミングに起因するテストの不安定性が完全に解消されました。

## コアとなるコードの解説

このコミットによる変更は、主に `test/heapsampling.go` ファイル内の2箇所に集中しています。

1.  **`main` 関数からの `return` 文の削除**:
    ```go
    -	return // TODO: fix this flaky test; golang.org/issue/13098
    ```
    変更前は、`main` 関数の冒頭に `return` 文がコメントアウトされた状態で存在していました。これは、このテストが以前から不安定な挙動を示しており（Go issue #13098で追跡されていた問題）、一時的にテストの実行をスキップするために挿入されていたものです。今回のコミットで根本原因が解決されたため、この `return` 文が削除され、`heapsampling.go` テストが再び有効化されました。これにより、Goのヒーププロファイリング機能の健全性が継続的に検証されるようになります。

2.  **`getMemProfileRecords` 関数への `runtime.GC()` の追加**:
    ```go
    func getMemProfileRecords() []runtime.MemProfileRecord {
    +	// Force the runtime to update the object and byte counts.
    +	runtime.GC()
    
     	// Find out how many records there are (MemProfile(nil, true)),
     	// allocate that many records, and get the data.
     	// There's a race—more records might be added between
    ```
    `getMemProfileRecords` 関数は、Goランタイムからヒーププロファイルのスナップショットを取得する役割を担っています。この関数の冒頭に、`runtime.GC()` の呼び出しが追加されました。この変更の意図は、プロファイルデータを実際に収集する直前に、Goランタイムにガベージコレクションを強制的に実行させることです。

    前述の通り、Goランタイムはヒーププロファイルにおけるメモリ割り当てのバイト数とオブジェクト数の統計情報をGCの実行時に更新します。したがって、`runtime.GC()` を明示的に呼び出すことで、それまでに発生したすべてのメモリ割り当てに関する統計情報が確実に集計され、最新の状態に更新されます。これにより、その直後に呼び出される `runtime.MemProfile()` が返すプロファイルデータには、常に正確で最新のバイト数とオブジェクト数が含まれることが保証されます。結果として、GCのタイミングに左右されることなく、`heapsampling.go` テストは常に一貫した、信頼性の高い結果を返すようになり、不安定な挙動が解消されました。

## 元コミット内容
`cmd/gc: blank methods are not permitted in interface types`

このコミットは、Goコンパイラ（`cmd/gc`）において、インターフェース型でブランク識別子（`_`）を使用したメソッド定義を許可しないようにする変更です。これはIssue #6606を修正します。

## 変更の背景

Go言語では、ブランク識別子 `_` は、変数や戻り値が使用されないことを明示的に示すために使用されます。これにより、コンパイラが未使用の変数に関するエラーを発生させるのを防ぎ、コードの意図を明確にすることができます。しかし、このコミット以前のGoコンパイラでは、インターフェースのメソッド定義において、メソッド名としてブランク識別子 `_` を使用することが可能でした。

例えば、以下のようなインターフェース定義が許容されていました。

```go
type MyInterface interface {
    _() // ブランク識別子をメソッド名として使用
}
```

このような定義は、Go言語の設計思想、特にインターフェースの目的と矛盾していました。インターフェースは、型が満たすべきメソッドのセットを定義し、そのメソッドを通じて振る舞いを抽象化するためのものです。メソッドには意味のある名前が付けられ、その名前を通じて呼び出されることが期待されます。ブランク識別子をメソッド名として使用することは、そのメソッドが「名前を持たない」ことを意味し、実質的にそのメソッドを呼び出すことができません。これはインターフェースの目的を損ない、混乱を招く可能性がありました。

Issue #6606は、この問題点を指摘し、インターフェースのメソッド名にブランク識別子を使用することを禁止するよう提案しました。このコミットは、その提案を受けて、コンパイラレベルでこの不正なパターンを検出・禁止するように実装されました。これにより、Go言語のインターフェースの健全性が保たれ、より明確で意図通りのコードが書かれるようになります。

## 前提知識の解説

### Go言語のインターフェース

Go言語のインターフェースは、メソッドのシグネチャの集まりを定義する型です。インターフェースは、そのインターフェースで定義されたすべてのメソッドを実装する任意の具象型によって「満たされる」ことができます。Goのインターフェースは暗黙的に満たされる（implicit interface satisfaction）ため、型が特定のインターフェースを満たすことを明示的に宣言する必要はありません。

例:
```go
type Greeter interface {
    Greet() string
}

type Person struct {
    Name string
}

func (p Person) Greet() string {
    return "Hello, " + p.Name
}

// Person 型は Greeter インターフェースを満たす
```

### Go言語のメソッド

Go言語のメソッドは、特定の型に関連付けられた関数です。メソッドはレシーバ引数（receiver argument）を持ち、これによりそのメソッドがどの型の値に対して呼び出されるかを指定します。

例:
```go
type MyInt int

func (m MyInt) Add(val int) MyInt {
    return m + MyInt(val)
}
```

### Go言語のブランク識別子 (`_`)

ブランク識別子 `_` は、Go言語において、値が使用されないことを明示的に示すために使用される特別な識別子です。これは、コンパイラが未使用の変数やインポートに関するエラーを発生させるのを防ぐために役立ちます。

使用例:
*   **未使用の変数**: `_ = someValue`
*   **複数の戻り値を持つ関数のうち、一部の戻り値が不要な場合**: `result, _ := someFunction()`
*   **インポートされたパッケージが直接使用されないが、その副作用（例: `init`関数）が必要な場合**: `import _ "net/http/pprof"`

ブランク識別子は、名前を持つべきではない、あるいは名前が重要ではない文脈で使用されます。しかし、メソッド名のように、通常は明確な識別子が必要な場所でブランク識別子を使用することは、Goの設計思想に反します。

## 技術的詳細

このコミットは、Goコンパイラのフロントエンド部分、特に型チェックと宣言処理を担当する`cmd/gc`パッケージに修正を加えています。

Goコンパイラは、ソースコードを解析し、抽象構文木（AST）を構築します。その後、ASTに対して型チェックやセマンティック解析を行い、最終的に実行可能なバイナリを生成します。インターフェースのメソッド定義は、この型チェックの段階で処理されます。

変更の中心は、`src/cmd/gc/dcl.c`ファイル内の`ifacedcl`関数です。この関数は、インターフェース型の宣言を処理する役割を担っています。インターフェースの各メソッドが宣言される際に、この関数が呼び出され、メソッドのプロパティ（名前、引数、戻り値など）が検証されます。

このコミットでは、`ifacedcl`関数内に新しいチェックが追加されました。このチェックは、現在処理しているメソッドの名前がブランク識別子であるかどうかを`isblank`関数（Goコンパイラ内部のヘルパー関数）を使って判定します。もしメソッド名がブランク識別子であると判定された場合、コンパイラは`yyerror`関数を呼び出してエラーメッセージ「`methods must have a unique non-blank name`」（メソッドは一意の非ブランク名を持つ必要があります）を出力し、コンパイルを失敗させます。

この変更により、コンパイル時にインターフェースのメソッド名がブランク識別子でないことが保証されるようになり、Go言語のインターフェースのセマンティクスがより厳密に適用されるようになりました。

## コアとなるコードの解説

### `src/cmd/gc/dcl.c` の変更

`ifacedcl`関数は、Goコンパイラがインターフェース型を処理する際の中心的な部分です。この関数は、インターフェース内の各メソッド宣言を反復処理し、その妥当性を検証します。

追加されたコードは以下の通りです。

```c
	if(isblank(n->left))
		yyerror("methods must have a unique non-blank name");
```

*   `n`は現在のメソッド宣言を表すASTノードです。
*   `n->left`はメソッドの名前を表すノードです。
*   `isblank(n->left)`: この関数は、`n->left`がブランク識別子（`_`）を表すかどうかをチェックします。`isblank`はGoコンパイラ内部のユーティリティ関数で、識別子がブランク識別子であるかを効率的に判定します。
*   `yyerror("methods must have a unique non-blank name")`: もし`isblank`が真（メソッド名がブランク識別子である）を返した場合、`yyerror`関数が呼び出されます。`yyerror`はコンパイラのエラー報告メカニズムの一部であり、指定されたエラーメッセージをユーザーに表示し、コンパイルプロセスをエラー状態にします。

このシンプルな追加により、コンパイラはインターフェースのメソッド名がブランク識別子である場合に、明確なエラーメッセージとともにコンパイルを停止するようになります。これにより、Go言語のインターフェースの設計原則が強制され、開発者が意図しない、または無意味なインターフェース定義を作成するのを防ぎます。

### テストファイルの変更

*   **`test/interface/explicit.go`**: このファイルは、コンパイラが期待通りにエラーを報告するかどうかを検証するためのものです。`B1`と`B2`インターフェースの定義に`_()`メソッドが含まれており、その行に`// ERROR "..."`というコメントが追加されています。これはGoのテストフレームワークにおける慣習で、その行で指定されたエラーメッセージがコンパイラによって出力されることを期待するという意味です。この変更により、新しいコンパイラの挙動が正しくテストされるようになりました。

*   **`test/interface/fail.go`**: このファイルからのコード削除は、以前のコンパイラではコンパイルが通ってしまい、実行時にパニックを引き起こす可能性があった`p2`関数と関連する`B`インターフェースのテストケースが、新しいコンパイラではコンパイル時にエラーとなるため、もはや不要になったことを示しています。これは、コンパイラがより早期に問題を検出するようになったことの証拠であり、Go言語の堅牢性が向上したことを意味します。

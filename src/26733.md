## 変更の背景

Go言語のバイナリサイズは、特に組み込みシステムやコンテナ環境において重要な考慮事項です。このコミットは、Goコンパイラ（`cmd/go`）によって生成されるバイナリのサイズを削減することを目的としています。

Goのランタイムは、リフレクションやインターフェースの処理のために、プログラム内のすべての型に関する詳細なメタデータ（型名を含む）を保持しています。これらの型情報は`_type`（ランタイム内部）や`rtype`（`reflect`パッケージ公開）といった構造体に格納されます。以前の実装では、型名は`*string`、つまり文字列データへのポインタとしてこれらの構造体内に保持されていました。

`*string`を使用すると、`rtype`構造体自体にはポインタ（通常8バイト）のみが格納され、実際の文字列データはヒープまたは別のデータセクションに配置されます。しかし、このアプローチは、特に多数の型が存在する場合に、ポインタの間接参照によるオーバーヘッドや、文字列データ自体の重複、あるいは効率の悪いメモリ配置を引き起こす可能性がありました。

このコミットは、型名を`string`ヘッダとして`rtype`構造体に直接埋め込むことで、このオーバーヘッドを削減しようとします。`string`型はGoではデータポインタと長さのペアで構成される構造体であり、これを直接埋め込むことで、間接参照を排除し、全体的なメモリフットプリントとバイナリサイズを最適化します。コミットメッセージにある「Reduces binary size of cmd/go by 1%」という記述は、この変更が実際に測定可能な効果をもたらしたことを示しています。

## 前提知識の解説

### Goの型システムとリフレクション

Go言語は静的型付け言語ですが、`reflect`パッケージを通じて実行時に型情報を検査・操作するリフレクション機能を提供します。この機能は、`encoding/json`のような汎用的なライブラリや、インターフェースの動的なディスパッチにおいて不可欠です。

### `_type`と`rtype`構造体

Goのランタイムは、プログラム内のすべての型に関するメタデータを`_type`という内部構造体で管理しています。`reflect`パッケージが提供する`reflect.Type`インターフェースは、この`_type`構造体へのポインタをラップした`rtype`構造体を通じて実装されています。これらの構造体には、型のサイズ、アライメント、メソッド情報、そして型名などの情報が含まれています。

### Goにおける文字列の内部表現

Goの`string`型は、実際にはデータポインタと文字列の長さ（バイト数）の2つのフィールドを持つ構造体です。例えば64ビットシステムでは、データポインタが8バイト、長さが8バイトで、合計16バイトを占めます。これは値型であり、文字列データそのものではなく、文字列データが格納されているメモリ領域への参照と、その長さを保持します。

### ポインタと間接参照

`*string`は`string`型へのポインタです。つまり、`*string`型の変数は、`string`構造体（データポインタと長さ）が格納されているメモリのアドレスを保持します。この場合、型名を取得するためには、`rtype`構造体から`*string`ポインタを読み出し、さらにそのポインタが指すメモリ位置から`string`構造体を読み出すという二段階の間接参照が必要になります。

### バイナリサイズ最適化の考慮事項

コンパイラやリンカは、プログラムの実行に必要なすべてのコードとデータを最終的なバイナリファイルに含めます。型情報のようなメタデータもその一部です。データ構造の設計は、メモリ使用量だけでなく、バイナリサイズにも直接影響します。特に、ポインタの数が多いと、それらを解決するための情報や、ポインタが指すデータが分散して配置されることで、キャッシュ効率の低下や、全体的なデータ量の増加につながることがあります。

## 技術的詳細

このコミットの核心は、`rtype`および`_type`構造体内の型名フィールドを`*string`から`string`に変更することです。

**変更前:**
```go
type rtype struct {
    // ...
    string        *string  // string form; unnecessary but undeniably useful
    // ...
}

type _type struct {
    // ...
    _string *string
    // ...
}
```

**変更後:**
```go
type rtype struct {
    // ...
    string        string   // string form; unnecessary but undeniably useful
    // ...
}

type _type struct {
    // ...
    _string string
    // ...
}
```

この変更がもたらす技術的な影響は以下の通りです。

1.  **間接参照の排除**: 以前は`rtype`構造体内に`string`構造体へのポインタが格納されていました。型名にアクセスするには、まず`rtype`からポインタを読み出し、次にそのポインタが指すアドレスから`string`構造体（データポインタと長さ）を読み出す必要がありました。変更後は、`rtype`構造体内に`string`構造体自体が直接埋め込まれるため、型名へのアクセスに必要な間接参照が1段階減ります。

2.  **メモリレイアウトとサイズ**:
    *   64ビットシステムを例にとると、`*string`は8バイトのポインタです。`string`はデータポインタ（8バイト）と長さ（8バイト）で構成されるため、合計16バイトです。
    *   一見すると、`*string`から`string`への変更は、`rtype`構造体自体のサイズを8バイト増加させるように見えます。しかし、Goの構造体はアライメントの制約があり、フィールドの並び順や型によってパディングが発生することがあります。この変更により、構造体全体のパディングが最適化され、結果的に全体のメモリフットプリントが削減される可能性があります。
    *   最も重要なのは、`*string`の場合、`string`構造体自体は別のメモリ領域に存在し、その領域もバイナリサイズに貢献します。多数の型が存在する場合、これらの`string`構造体の集合体が大きなデータ量となり得ます。`string`を直接埋め込むことで、これらの`string`構造体が`rtype`構造体の一部としてより密接に配置され、全体として効率的なデータ配置が実現される可能性があります。特に、型名が短い場合、この埋め込みは非常に効率的です。

3.  **バイナリサイズ削減のメカニズム**:
    *   `*string`の場合、コンパイラは各型名文字列に対して`string`構造体を生成し、それをデータセクションに配置し、`rtype`構造体からはその`string`構造体へのポインタを指していました。
    *   `string`を直接埋め込むことで、`rtype`構造体自体が型名文字列のデータポインタと長さを直接保持するようになります。これにより、個別の`string`構造体をデータセクションに配置する必要がなくなり、その分のデータと、それらを指すポインタのオーバーヘッドが削減されます。
    *   特に`cmd/go`のような、多くのGoの型情報を扱うツールでは、この最適化が多数の`rtype`インスタンスに適用されるため、全体として顕著なバイナリサイズ削減効果（1%）が得られたと考えられます。

4.  **コンパイラとリンカの変更**:
    *   `src/cmd/compile/internal/gc/reflect.go`の`dcommontype`関数は、型情報をバイナリに書き出す役割を担っています。この関数が、型名文字列を`*string`としてではなく、`string`ヘッダとして直接埋め込むように変更されました。具体的には、`dgostringptr`（Go文字列へのポインタを書き出す）の代わりに、`stringsym`で文字列シンボルを取得し、`dsymptr`でそのシンボルへのポインタを書き込み、さらに`duintxx`で文字列の長さを書き込むことで、`string`ヘッダの構造を直接構築しています。
    *   `src/cmd/link/internal/ld/decodesym.go`の`commonsize`関数は、`runtime._type`構造体の共通部分のサイズを返します。この関数が返すサイズが`7*Thearch.Ptrsize + 8`から`8*Thearch.Ptrsize + 8`に増加しています。これは、`string`ヘッダがポインタ2つ分（データポインタと長さ）に相当するため、`rtype`の共通部分のサイズがポインタ1つ分増加したことを示しています。

5.  **`reflect`および`runtime`パッケージの変更**:
    *   `rtype`および`_type`構造体の定義変更に伴い、これらの構造体の`string`フィールドにアクセスするすべての箇所で、`*t.string`や`*t._string`といったポインタのデリファレンスが不要になり、`t.string`や`t._string`と直接アクセスするように変更されています。これは、`reflect/type.go`内の型生成関数（`ptrTo`, `ChanOf`, `MapOf`, `FuncOf`, `SliceOf`, `ArrayOf`など）や、`runtime`パッケージ内のエラーメッセージ生成、デバッグ出力、型比較ロジックなど、広範囲にわたります。

Goのランタイムは、リフレクションやインターフェースの処理のために、プログラム内のすべての型に関する詳細なメタデータ（型名を含む）を保持しています。これらの型情報は`_type`（ランタイム内部）や`rtype`（`reflect`パッケージ公開）といった構造体に格納されます。以前の実装では、型名は`*string`、つまり文字列データへのポインタとしてこれらの構造体内に保持されていました。

`*string`を使用すると、`rtype`構造体自体にはポインタ（通常8バイト）のみが格納され、実際の文字列データはヒープまたは別のデータセクションに配置されます。しかし、このアプローチは、特に多数の型が存在する場合に、ポインタの間接参照によるオーバーヘッドや、文字列データ自体の重複、あるいは効率の悪いメモリ配置を引き起こす可能性がありました。

このコミットは、型名を`string`ヘッダとして`rtype`構造体に直接埋め込むことで、このオーバーヘッドを削減しようとします。`string`型はGoではデータポインタと長さのペアで構成される構造体であり、これを直接埋め込むことで、間接参照を排除し、全体的なメモリフットプリントとバイナリサイズを最適化します。コミットメッセージにある「Reduces binary size of cmd/go by 1%」という記述は、この変更が実際に測定可能な効果をもたらしたことを示しています。

また、コミットメッセージには「For #6853」と記載されていますが、このIssueは一般的なWeb検索では見つかりませんでした。これは、内部のトラッキングシステムや非常に古いIssueである可能性が高いですが、文脈からバイナリサイズ削減や型情報の効率化に関する議論であったと推測されます。

## 前提知識の解説

### Goの型システムとリフレクション

Go言語は静的型付け言語ですが、`reflect`パッケージを通じて実行時に型情報を検査・操作するリフレクション機能を提供します。この機能は、`encoding/json`のような汎用的なライブラリや、インターフェースの動的なディスパッチにおいて不可欠です。

### `_type`と`rtype`構造体

Goのランタイムは、プログラム内のすべての型に関するメタデータを`_type`という内部構造体で管理しています。`reflect`パッケージが提供する`reflect.Type`インターフェースは、この`_type`構造体へのポインタをラップした`rtype`構造体を通じて実装されています。これらの構造体には、型のサイズ、アライメント、メソッド情報、そして型名などの情報が含まれています。

### Goにおける文字列の内部表現

Goの`string`型は、実際にはデータポインタと文字列の長さ（バイト数）の2つのフィールドを持つ構造体です。例えば64ビットシステムでは、データポインタが8バイト、長さが8バイトで、合計16バイトを占めます。これは値型であり、文字列データそのものではなく、文字列データが格納されているメモリ領域への参照と、その長さを保持します。

### ポインタと間接参照

`*string`は`string`型へのポインタです。つまり、`*string`型の変数は、`string`構造体（データポインタと長さ）が格納されているメモリのアドレスを保持します。この場合、型名を取得するためには、`rtype`構造体から`*string`ポインタを読み出し、さらにそのポインタが指すメモリ位置から`string`構造体を読み出すという二段階の間接参照が必要になります。

### バイナリサイズ最適化の考慮事項

コンパイラやリンカは、プログラムの実行に必要なすべてのコードとデータを最終的なバイナリファイルに含めます。型情報のようなメタデータもその一部です。データ構造の設計は、メモリ使用量だけでなく、バイナリサイズにも直接影響します。特に、ポインタの数が多いと、それらを解決するための情報や、ポインタが指すデータが分散して配置されることで、キャッシュ効率の低下や、全体的なデータ量の増加につながることがあります。

## 技術的詳細

このコミットの核心は、`rtype`および`_type`構造体内の型名フィールドを`*string`から`string`に変更することです。

**変更前:**
```go
type rtype struct {
    // ...
    string        *string  // string form; unnecessary but undeniably useful
    // ...
}

type _type struct {
    // ...
    _string *string
    // ...
}
```

**変更後:**
```go
type rtype struct {
    // ...
    string        string   // string form; unnecessary but undeniably useful
    // ...
}

type _type struct {
    // ...
    _string string
    // ...
}
```

この変更がもたらす技術的な影響は以下の通りです。

1.  **間接参照の排除**: 以前は`rtype`構造体内に`string`構造体へのポインタが格納されていました。型名にアクセスするには、まず`rtype`からポインタを読み出し、次にそのポインタが指すアドレスから`string`構造体（データポインタと長さ）を読み出す必要がありました。変更後は、`rtype`構造体内に`string`構造体自体が直接埋め込まれるため、型名へのアクセスに必要な間接参照が1段階減ります。

2.  **メモリレイアウトとサイズ**:
    *   64ビットシステムを例にとると、`*string`は8バイトのポインタです。`string`はデータポインタ（8バイト）と長さ（8バイト）で構成されるため、合計16バイトです。
    *   一見すると、`*string`から`string`への変更は、`rtype`構造体自体のサイズを8バイト増加させるように見えます。しかし、Goの構造体はアライメントの制約があり、フィールドの並び順や型によってパディングが発生することがあります。この変更により、構造体全体のパディングが最適化され、結果的に全体のメモリフットプリントが削減される可能性があります。
    *   最も重要なのは、`*string`の場合、`string`構造体自体は別のメモリ領域に存在し、その領域もバイナリサイズに貢献します。多数の型が存在する場合、これらの`string`構造体の集合体が大きなデータ量となり得ます。`string`を直接埋め込むことで、これらの`string`構造体が`rtype`構造体の一部としてより密接に配置され、全体として効率的なデータ配置が実現される可能性があります。特に、型名が短い場合、この埋め込みは非常に効率的です。

3.  **バイナリサイズ削減のメカニズム**:
    *   `*string`の場合、コンパイラは各型名文字列に対して`string`構造体を生成し、それをデータセクションに配置し、`rtype`構造体からはその`string`構造体へのポインタを指していました。
    *   `string`を直接埋め込むことで、`rtype`構造体自体が型名文字列のデータポインタと長さを直接保持するようになります。これにより、個別の`string`構造体をデータセクションに配置する必要がなくなり、その分のデータと、それらを指すポインタのオーバーヘッドが削減されます。
    *   特に`cmd/go`のような、多くのGoの型情報を扱うツールでは、この最適化が多数の`rtype`インスタンスに適用されるため、全体として顕著なバイナリサイズ削減効果（1%）が得られたと考えられます。

4.  **コンパイラとリンカの変更**:
    *   `src/cmd/compile/internal/gc/reflect.go`の`dcommontype`関数は、型情報をバイナリに書き出す役割を担っています。この関数が、型名文字列を`*string`としてではなく、`string`ヘッダとして直接埋め込むように変更されました。具体的には、`dgostringptr`（Go文字列へのポインタを書き出す）の代わりに、`stringsym`で文字列シンボルを取得し、`dsymptr`でそのシンボルへのポインタを書き込み、さらに`duintxx`で文字列の長さを書き込むことで、`string`ヘッダの構造を直接構築しています。
    *   `src/cmd/link/internal/ld/decodesym.go`の`commonsize`関数は、`runtime._type`構造体の共通部分のサイズを返します。この関数が返すサイズが`7*Thearch.Ptrsize + 8`から`8*Thearch.Ptrsize + 8`に増加しています。これは、`string`ヘッダがポインタ2つ分（データポインタと長さ）に相当するため、`rtype`の共通部分のサイズがポインタ1つ分増加したことを示しています。

5.  **`reflect`および`runtime`パッケージの変更**:
    *   `rtype`および`_type`構造体の定義変更に伴い、これらの構造体の`string`フィールドにアクセスするすべての箇所で、`*t.string`や`*t._string`といったポインタのデリファレンスが不要になり、`t.string`や`t._string`と直接アクセスするように変更されています。これは、`reflect/type.go`内の型生成関数（`ptrTo`, `ChanOf`, `MapOf`, `FuncOf`, `SliceOf`, `ArrayOf`など）や、`runtime`パッケージ内のエラーメッセージ生成、デバッグ出力、型比較ロジックなど、広範囲にわたります。

## コアとなるコードの変更箇所

このコミットは、Goのコンパイラ、リンカ、`reflect`パッケージ、および`runtime`パッケージの複数のファイルにわたる変更を含んでいます。

1.  **`src/cmd/compile/internal/gc/reflect.go`**:
    *   `dcommontype`関数内で、型名文字列を`rtype`構造体に埋め込むロジックが変更されました。
    *   以前は`dgostringptr(s, ot, p)`で文字列へのポインタを書き込んでいましたが、変更後は`stringsym(p)`で文字列シンボルを取得し、`dsymptr(s, ot, symdata, 0)`でシンボルへのポインタを書き込み、`duintxx(s, ot, uint64(len(p)), Widthint)`で文字列の長さを書き込むことで、`string`ヘッダを直接埋め込むように変更されています。

2.  **`src/cmd/link/internal/ld/decodesym.go`**:
    *   `commonsize`関数の戻り値が変更されました。`rtype`の共通部分のサイズが、`7*Thearch.Ptrsize + 8`から`8*Thearch.Ptrsize + 8`に増えています。これは、`string`ヘッダがポインタ2つ分のサイズを持つため、`rtype`構造体のサイズが増加したことを反映しています。

3.  **`src/reflect/type.go`**:
    *   `rtype`構造体の`string`フィールドの型が`*string`から`string`に変更されました。
    *   これに伴い、`String()`メソッド、`ptrTo()`、`typesByString()`、`ChanOf()`、`MapOf()`、`FuncOf()`、`bucketOf()`、`SliceOf()`、`ArrayOf()`、`funcLayout()`など、`rtype.string`にアクセスするすべての箇所で、`*t.string`から`t.string`への変更が行われています。

4.  **`src/runtime/type.go`**:
    *   `_type`構造体の`_string`フィールドの型が`*string`から`string`に変更されました。

5.  **`src/runtime/alg.go`, `src/runtime/error.go`, `src/runtime/heapdump.go`, `src/runtime/iface.go`, `src/runtime/mbitmap.go`, `src/runtime/mfinal.go`, `src/runtime/mprof.go`**:
    *   これらのファイル内で`_type._string`フィールドにアクセスしている箇所が、`*t._string`から`t._string`へと変更されています。これは、型定義の変更に合わせた単純なアクセス方法の修正です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go` の変更

```diff
--- a/src/cmd/compile/internal/gc/reflect.go
+++ b/src/cmd/compile/internal/gc/reflect.go
@@ -764,12 +764,14 @@ func dcommontype(s *Sym, ot int, t *Type) int {
 	} else {
 		ot = dsymptr(s, ot, algsym, 0)
 	}\n-\tot = dsymptr(s, ot, gcsym, 0)\n+\tot = dsymptr(s, ot, gcsym, 0) // gcdata\n \n 	p := Tconv(t, obj.FmtLeft|obj.FmtUnsigned)\n \n-\t//print(\"dcommontype: %s\\n\", p);\n-\tot = dgostringptr(s, ot, p) // string\n+\t_, symdata := stringsym(p) // string\n+\tot = dsymptr(s, ot, symdata, 0)\n+\tot = duintxx(s, ot, uint64(len(p)), Widthint)\n+\t//fmt.Printf(\"dcommontype: %s\\n\", p)\n \n 	// skip pointer to extraType,\n 	// which follows the rest of this type structure.
```
この差分は、コンパイラが型情報をバイナリに書き出す際の`dcommontype`関数の挙動を変更しています。
- 以前は`dgostringptr(s, ot, p)`を呼び出して、型名文字列`p`へのポインタを`rtype`構造体内に書き込んでいました。
- 変更後は、まず`stringsym(p)`で型名文字列`p`に対応するシンボルデータ（`symdata`）を取得します。
- 次に、`dsymptr(s, ot, symdata, 0)`で、この`symdata`へのポインタを`rtype`構造体内に書き込みます。これはGoの`string`型のデータポインタ部分に相当します。
- 最後に、`duintxx(s, ot, uint64(len(p)), Widthint)`で、文字列`p`の長さ（`len(p)`）を`rtype`構造体内に書き込みます。これはGoの`string`型の長さ部分に相当します。
この2つのステップにより、`string`ヘッダ（データポインタと長さ）が`rtype`構造体内に直接埋め込まれることになります。

### `src/reflect/type.go` の `String()` メソッドの変更

```diff
--- a/src/reflect/type.go
+++ b/src/reflect/type.go
@@ -460,7 +460,7 @@ func (t *uncommonType) Name() string {
 	return *t.name
 }
 
-func (t *rtype) String() string { return *t.string }
+func (t *rtype) String() string { return t.string }

```

これらの変更は、Goの型システムが内部で型名をどのように管理し、バイナリに埋め込むかという低レベルな部分に影響を与え、結果としてバイナリサイズの最適化に貢献しています。

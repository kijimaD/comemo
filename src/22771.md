## 変更の背景

Go言語は、様々なプラットフォームとアーキテクチャをサポートすることを目指しています。Cgoは、GoプログラムがC言語のコードを呼び出すための重要なメカニズムであり、オペレーティングシステムとの低レベルな相互作用や、既存のCライブラリの利用に不可欠です。

このコミットは、`misc/cgo/test/issue9400`という特定のテストケースに対して、ARM64アーキテクチャ向けの具体的な実装を追加するものです。`issue9400`という番号は、Goの公開Issueトラッカーには直接見当たらないものの、これは内部的な追跡番号であるか、あるいはより大きな問題（例えば、GoのIssue #9410がSWIGとCgoのビルド問題に関連していたように）の一部として、特定のシナリオにおけるCgoの挙動を検証するためのテストである可能性が高いです。

特に、`RewindAndSetgid`という関数名が示唆するように、このテストは`setgid`のような権限変更を伴うシステムコールや、シグナルハンドリングなど、スタックの状態が非常に重要になる低レベルな操作におけるCgoの堅牢性を検証していると考えられます。ARM64のような新しいアーキテクチャでは、既存のテストケースがそのまま適用できない場合や、アーキテクチャ固有の挙動を考慮した実装が必要になることがあります。このコミットは、ARM64環境でのCgoの正確性と信頼性を保証するための一環として追加されました。

## 前提知識の解説

### Go言語とCgo

*   **Go言語**: Googleによって開発された静的型付けのコンパイル型言語です。並行処理のサポート（ゴルーチンとチャネル）、ガベージコレクション、高速なコンパイル、シンプルな構文が特徴です。
*   **Cgo**: Go言語の標準パッケージの一つで、GoプログラムからC言語の関数を呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムを提供します。これにより、既存のCライブラリをGoプロジェクトで再利用したり、OSの低レベルな機能にアクセスしたりすることが可能になります。Cgoを使用すると、Goのビルドプロセス中にCコードがコンパイルされ、Goの実行可能ファイルにリンクされます。

### ARM64アーキテクチャ

*   **ARM64 (AArch64)**: ARMアーキテクチャの64ビット版で、スマートフォン、タブレット、サーバー、組み込みシステムなど、幅広いデバイスで利用されています。Apple SiliconやRaspberry Pi 4などもARM64ベースです。
*   **レジスタ**: ARM64プロセッサは、汎用レジスタ（X0-X30）、スタックポインタ（SP）、プログラムカウンタ（PC）、リンクレジスタ（LR/X30）などを持っています。Goのアセンブリでは、これらのレジスタは`R0`、`R1`、`RSP`、`R30`などの表記で参照されます。
    *   `RSP`: スタックポインタ。現在のスタックの最上位アドレスを指します。
    *   `R30`: リンクレジスタ (LR)。関数呼び出し時に戻りアドレスを保存するために使用されます。
    *   `R0-R7`: 関数呼び出し規約において、引数や戻り値を渡すために使用されるレジスタ。
*   **命令セット**: ARM64はRISC（Reduced Instruction Set Computer）アーキテクチャであり、比較的単純な命令セットを持ちます。

### アセンブリ言語 (Goアセンブリ)

*   **アセンブリ言語**: プロセッサが直接実行できる機械語命令を、人間が読める形式で記述した低レベルプログラミング言語です。Go言語では、特定のパフォーマンス要件やOSとの低レベルな相互作用のために、Goアセンブリ（Plan 9アセンブラの派生）を使用することがあります。
*   **Goアセンブリの構文**: 一般的なアセンブリ言語とは異なる独自の構文を持ちます。例えば、レジスタの前に`R`を付けたり、シンボルに`SB`（Static Base）を付けたりします。

### システムコールと`setgid`

*   **システムコール**: オペレーティングシステムが提供するサービス（ファイルI/O、メモリ管理、プロセス管理など）をプログラムから利用するためのインターフェースです。
*   **`setgid`**: プロセスの実効グループID (effective group ID) を設定するためのシステムコールです。これにより、プログラムが特定のグループの権限でファイルやリソースにアクセスできるようになります。セキュリティ上非常に重要な操作であり、権限昇格やサンドボックス化の際に利用されます。`setgid`のような操作は、プロセスのセキュリティコンテキストを変更するため、細心の注意を払って実装される必要があります。

### アトミック操作

*   **アトミック操作**: 複数のCPUコアやスレッドから同時にアクセスされる共有データに対して、不可分（atomic）に行われる操作です。つまり、その操作が完全に完了するか、全く行われないかのどちらかであり、途中で他の操作に割り込まれることがありません。これにより、競合状態（race condition）を防ぎ、データの整合性を保つことができます。
*   **`LDAXRW` (Load-Acquire Exclusive Register Word)** と **`STLXRW` (Store-Release Exclusive Register Word)**: ARM64アーキテクチャにおけるアトミック操作のための命令です。
    *   `LDAXRW`: 指定されたメモリ位置から値を排他的にロードします。これにより、そのメモリ位置に対する排他ロックが取得されます。
    *   `STLXRW`: 指定されたメモリ位置に値を排他的にストアします。ストアが成功した場合（排他ロックがまだ有効な場合）、レジスタに0が設定され、排他ロックが解除されます。失敗した場合は非ゼロが設定されます。
    *   これらの命令は、ロード・リンク/ストア・コンディション (LL/SC) のペアとして機能し、ロックフリーなデータ構造や同期プリミティブの実装に利用されます。

## 技術的詳細

このコミットで追加された`asm_arm64.s`ファイルは、GoのランタイムやCgoが内部的に使用するアセンブリ関数を定義しています。ファイル名が示すように、これはARM64アーキテクチャ専用のコードです。

### `asm_arm64.s` ファイルの構造

Goのアセンブリファイルは、通常、`TEXT`ディレクティブで関数を定義します。このファイルには`·RewindAndSetgid`という関数が定義されています。

```asm
#include "textflag.h"

TEXT ·RewindAndSetgid(SB),NOSPLIT,$-8-0
    // Save link register
    MOVD    R30, R9

    // Rewind stack pointer so anything that happens on the stack
    // will clobber the test pattern created by the caller
    ADD $(1024 * 8), RSP

    // Ask signaller to setgid
    MOVD    $·Baton(SB), R0
    MOVD    $1, R1
storeloop:
    LDAXRW  (R0), R2
    STLXRW  R1, (R0), R3
    CBNZ    R3, storeloop

    // Wait for setgid completion
    MOVW    $0, R1
    MOVW    $0, R2
loop:
    LDAXRW  (R0), R3
    CMPW    R1, R3
    BNE loop
    STLXRW  R2, (R0), R3
    CBNZ    R3, loop

    // Restore stack
    SUB $(1024 * 8), RSP

    MOVD    R9, R30
    RET
```

### 関数定義 `TEXT ·RewindAndSetgid(SB),NOSPLIT,$-8-0`

*   `TEXT`: Goアセンブリで関数を定義するためのディレクティブ。
*   `·RewindAndSetgid`: 関数名。Goのシンボルは通常、パッケージパスと関数名の間にドット（`.`）ではなく、中点（`·`）を使用します。これはGoのリンカが内部的に使用する表記です。
*   `(SB)`: シンボルが静的ベース（Static Base）からのオフセットであることを示します。これはグローバルシンボルや外部シンボルを参照する際に使用されます。
*   `NOSPLIT`: この関数がスタック分割（stack splitting）を行わないことを示します。Goのランタイムは、ゴルーチンのスタックが不足した場合に自動的にスタックを拡張しますが、`NOSPLIT`はこれを無効にします。これは、シグナルハンドラや低レベルなランタイム関数など、スタックの状態が厳密に管理される必要がある場合に用いられます。
*   `$-8-0`: スタックフレームのサイズと引数のサイズを示します。
    *   `-8`: スタックフレームのサイズが8バイトであることを示します。これは、関数が自身のローカル変数やレジスタの保存のために使用するスタック領域です。負の値は、スタックポインタが減少し、スタックが下方に成長することを示します。
    *   `0`: 引数のサイズが0バイトであることを示します。この関数はGoの引数を直接受け取らないことを意味します。

### 命令の詳細

1.  **`MOVD R30, R9`**:
    *   `MOVD`: 64ビットの値を移動する命令（Move Doubleword）。
    *   `R30` (Link Register, LR): 関数呼び出し元への戻りアドレスが格納されているレジスタ。
    *   `R9`: 一時的に戻りアドレスを保存するための汎用レジスタ。関数内で`R30`が変更される可能性があるため、元の戻りアドレスを退避させています。

2.  **`ADD $(1024 * 8), RSP`**:
    *   `ADD`: 加算命令。
    *   `$(1024 * 8)`: 即値。1024 * 8 = 8192バイト。
    *   `RSP`: スタックポインタ。
    *   この命令は、スタックポインタを8192バイト分「巻き戻し」ます。スタックは通常、アドレスが減少する方向に成長するため、スタックポインタに正の値を加算すると、スタックの「上」方向（より高いアドレス）に移動します。コメントにあるように、これは呼び出し元によって作成されたテストパターンを上書きするため、または特定のメモリ領域をクリアするために行われます。これにより、テストの再現性やクリーンな状態を保証します。

3.  **`MOVD $·Baton(SB), R0`**:
    *   `$·Baton(SB)`: `·Baton`というシンボルのアドレスをロードします。`·Baton`は、`setgid`の完了をシグナルするための共有メモリ上の「バトン」として機能する変数であると推測されます。
    *   `R0`: `·Baton`のアドレスを格納します。これは後続のアトミック操作の対象アドレスとなります。

4.  **`MOVD $1, R1`**:
    *   `$1`: 即値1。
    *   `R1`: `·Baton`に書き込む値（`setgid`を要求するシグナル）を格納します。

5.  **`storeloop:` (アトミックな`setgid`要求)**
    *   `LDAXRW (R0), R2`: `R0`が指すメモリ位置（`·Baton`）から32ビットワードを排他的にロードし、`R2`に格納します。これにより、このメモリ位置に対する排他ロックが取得されます。
    *   `STLXRW R1, (R0), R3`: `R1`の値（1）を`R0`が指すメモリ位置（`·Baton`）に排他的にストアします。ストアが成功した場合（排他ロックが有効な場合）、`R3`に0が設定されます。失敗した場合（他のプロセッサが排他ロックを破棄した場合）、非ゼロが設定されます。
    *   `CBNZ R3, storeloop`: `R3`がゼロでない場合（ストアが失敗した場合）、`storeloop`に分岐します。これは、ストアが成功するまでループを繰り返すことで、アトミックな書き込みを保証します。

6.  **`MOVW $0, R1` と `MOVW $0, R2`**:
    *   `MOVW`: 32ビットの値を移動する命令（Move Word）。
    *   `R1`に0、`R2`に0を格納します。これらは後続のループで使用される比較値とストア値です。

7.  **`loop:` (アトミックな`setgid`完了待機)**
    *   `LDAXRW (R0), R3`: `R0`が指すメモリ位置（`·Baton`）から32ビットワードを排他的にロードし、`R3`に格納します。
    *   `CMPW R1, R3`: `R1`の値（0）と`R3`の値（`·Baton`の現在の値）を32ビットで比較します。
    *   `BNE loop`: 比較結果が等しくない場合（`·Baton`がまだ0でない場合）、`loop`に分岐します。これは、`·Baton`が0になるまで（つまり、`setgid`が完了したことを示すまで）ループを繰り返します。
    *   `STLXRW R2, (R0), R3`: `R2`の値（0）を`R0`が指すメモリ位置（`·Baton`）に排他的にストアします。これは、`setgid`完了のシグナルを受け取った後、バトンをリセットする（または別の状態に遷移させる）ための操作です。
    *   `CBNZ R3, loop`: `R3`がゼロでない場合（ストアが失敗した場合）、`loop`に分岐します。これもアトミックな書き込みを保証するためのリトライループです。

8.  **`SUB $(1024 * 8), RSP`**:
    *   `SUB`: 減算命令。
    *   スタックポインタを8192バイト分「復元」します。これにより、関数エントリ時のスタックポインタの状態に戻ります。

9.  **`MOVD R9, R30`**:
    *   退避しておいた戻りアドレス（`R9`に保存されていた値）を`R30`（リンクレジスタ）に戻します。

10. **`RET`**:
    *   関数から戻る命令。`R30`に保存されているアドレスにジャンプし、呼び出し元に戻ります。

## コアとなるコードの解説

追加された`asm_arm64.s`ファイルは、`RewindAndSetgid`という単一の関数を実装しています。この関数の目的は、Cgoのテストシナリオにおいて、スタックの状態を操作し、`setgid`のような権限変更操作の完了をアトミックに同期することです。

1.  **戻りアドレスの保存**: 関数が開始されると、まずリンクレジスタ`R30`（呼び出し元への戻りアドレスが格納されている）の値を`R9`に保存します。これは、関数内で`R30`が使用される可能性があるため、安全に元の戻りアドレスを保持するためです。

2.  **スタックポインタの巻き戻し**: `ADD $(1024 * 8), RSP`命令により、スタックポインタ`RSP`を8192バイト分「巻き戻し」ます。これは、スタック上の特定の領域をクリアしたり、テストのために既知の状態にリセットしたりする目的で行われます。例えば、呼び出し元がスタックに書き込んだテストパターンを意図的に上書きすることで、テストの独立性と再現性を高めます。

3.  **`setgid`要求のシグナル送信**:
    *   `·Baton(SB)`というグローバル変数（または共有メモリ上の位置）のアドレスを`R0`にロードします。この`·Baton`は、`setgid`操作の進行状況を伝えるための共有フラグとして機能します。
    *   `R1`に値`1`をロードします。
    *   `storeloop`というループ内で、`LDAXRW`と`STLXRW`というアトミックなロード・ストア命令のペアを使用して、`·Baton`に値`1`を書き込もうとします。これは、他のスレッドやプロセスに対して「`setgid`操作を開始してほしい」という要求をアトミックに通知するものです。`STLXRW`が失敗した場合（他の競合があった場合）、`CBNZ R3, storeloop`によってループが繰り返され、成功するまでリトライされます。

4.  **`setgid`完了の待機**:
    *   `R1`と`R2`に値`0`をロードします。
    *   `loop`というループ内で、再び`LDAXRW`命令で`·Baton`の値をロードし、`R3`に格納します。
    *   `CMPW R1, R3`で`·Baton`の値が`0`になったかどうかをチェックします。`setgid`操作を実行する別のエンティティが、完了後に`·Baton`を`0`にリセットすると想定されます。
    *   `BNE loop`により、`·Baton`が`0`になるまでループを繰り返します。
    *   `setgid`が完了し`·Baton`が`0`になった後、`STLXRW R2, (R0), R3`で再度`·Baton`に`0`を書き込もうとします。これは、バトンをクリアする、または次のサイクルに備えるための最終的なアトミック操作です。ここでも`CBNZ R3, loop`でリトライが保証されます。

5.  **スタックポインタの復元**: `SUB $(1024 * 8), RSP`命令により、スタックポインタを元の位置に戻します。これにより、関数が呼び出し元に戻る際に、スタックがクリーンな状態になります。

6.  **戻りアドレスの復元と関数終了**: `R9`に保存しておいた戻りアドレスを`R30`に戻し、`RET`命令で関数から戻ります。

この関数は、GoのランタイムがCgoを介して低レベルなシステム操作を行う際に、スタックの整合性を保ちつつ、複数のコンテキスト間での同期をアトミックに行うための重要なテストメカニズムの一部であると考えられます。

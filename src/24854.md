# [インデックス 24854] ファイルの概要

このコミットは、Goの`net/http`パッケージにおける`io.Copy`の特定の呼び出しを最適化するものです。具体的には、`io.ReaderFrom`や`io.WriterTo`といった最適化トリックを利用できないケースにおいて、再利用可能なバッファを持つ`io.CopyBuffer`を使用するように変更することで、メモリ割り当てとパフォーマンスを改善しています。この最適化は、`http.CloseNotifier`インターフェースを使用するハンドラ（特に`httputil.ReverseProxy`）や、`sendfile`による最適化が利用できない場合のフォールバックパスに影響します。

net/http: optimize some io.Copy calls by reusing buffers

Optimize two calls of io.Copy which cannot make use of neither
io.ReaderFrom nor io.WriterTo optimization tricks by replacing them with
io.CopyBuffer with reusable buffers.

First is fallback call to io.Copy when server misses the optimized case
of using sendfile to copy from a regular file to net.TCPConn; second is
use of io.Copy on piped reader/writer when handler implementation uses
http.CloseNotifier interface. One of the notable users of

## 変更の背景

この変更の背景には、Goの`net/http`パッケージにおける特定のデータコピー操作のパフォーマンス改善があります。特に、`io.Copy`関数が内部的にバッファを割り当てる際に発生するメモリ割り当てのオーバーヘッドを削減することが目的です。

コミットメッセージに記載されているように、`io.Copy`は通常、`io.ReaderFrom`や`io.WriterTo`インターフェースを実装している場合に最適化されたパスを使用します。これらのインターフェースは、データソースとデータシンクが直接データを転送できるような、より効率的なメカニズムを提供します（例: `sendfile`システムコールなど）。しかし、これらの最適化が利用できない特定のシナリオでは、`io.Copy`は内部で一時的なバッファを割り当ててデータの読み書きを行います。このバッファの割り当てが頻繁に発生すると、ガベージコレクションの負荷が増大し、パフォーマンスが低下する可能性があります。

このコミットは、以下の2つの具体的なケースでこの問題に対処しています。

1.  **`sendfile`最適化のフォールバック**: `net/http`サーバーが、通常のファイルから`net.TCPConn`へのコピーに`sendfile`のような最適化されたパスを使用できない場合、`io.Copy`がフォールバックとして使用されます。このフォールバックパスでのバッファ再利用は、効率を向上させます。
2.  **`http.CloseNotifier`インターフェースの使用**: ハンドラが`http.CloseNotifier`インターフェースを使用する場合、パイプされたリーダー/ライター間で`io.Copy`が使用されます。`httputil.ReverseProxy`はこのインターフェースの顕著な利用者の一つであり、リバースプロキシのような高負荷なアプリケーションでは、このコピー操作が頻繁に発生するため、最適化の恩恵が大きいです。

ベンチマーク結果が示すように、この変更により`BenchmarkCloseNotifier`において、実行時間のわずかな改善（-2.00%）に加えて、メモリ割り当て回数（-2.00%）と割り当てバイト数（-91.32%）が大幅に削減されています。これは、ガベージコレクションの頻度を減らし、全体的なシステムのスループットとレイテンシを改善する上で非常に重要です。

この変更は、GoのIssue #12455を修正するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念とインターフェースに関する知識が必要です。

1.  **`io.Copy`**:
    `io.Copy(dst io.Writer, src io.Reader)`は、`src`から`dst`へデータをコピーするGoの標準ライブラリ関数です。内部的には、`src`が`io.ReaderFrom`を実装している場合、または`dst`が`io.WriterTo`を実装している場合、それらの最適化されたメソッドを優先的に使用します。どちらも実装されていない場合、`io.Copy`は内部で一時的なバイトスライス（バッファ）を割り当てて、`src.Read()`と`dst.Write()`を繰り返し呼び出すことでデータを転送します。この一時バッファの割り当てと解放が、頻繁な呼び出しの際にガベージコレクションのオーバーヘッドを引き起こす可能性があります。

2.  **`io.CopyBuffer`**:
    `io.CopyBuffer(dst io.Writer, src io.Reader, buf []byte)`は、`io.Copy`と同様にデータをコピーしますが、コピーに使用するバッファを呼び出し元が明示的に提供できる点が異なります。これにより、`io.Copy`が内部でバッファを割り当てるのを防ぎ、バッファを再利用することでメモリ割り当てを削減できます。

3.  **`sync.Pool`**:
    `sync.Pool`は、一時的なオブジェクトを再利用するためのGoの標準ライブラリの機能です。頻繁に生成・破棄されるが、その都度新しいインスタンスを割り当てる必要がないオブジェクト（例: バイトスライス、特定の構造体）に対して使用すると効果的です。`sync.Pool`は、`Get()`メソッドでプールからオブジェクトを取得し、`Put()`メソッドでオブジェクトをプールに戻します。これにより、ガベージコレクションの負荷を軽減し、アプリケーションのパフォーマンスを向上させることができます。`sync.Pool`はスレッドセーフであり、複数のゴルーチンから安全にアクセスできます。

4.  **`http.CloseNotifier`インターフェース**:
    `net/http`パッケージの`http.CloseNotifier`インターフェースは、HTTPリクエストのクライアント接続が閉じられたときに通知を受け取るためのメカニズムを提供します。これは、サーバーがクライアントの切断を検出し、それに応じてリソースを解放したり、進行中の処理を中止したりするのに役立ちます。このインターフェースは、`http.ResponseWriter`が実装していることがあり、`CloseNotify()`メソッドはクライアントが接続を閉じたときにクローズされるチャネルを返します。

5.  **`httputil.ReverseProxy`**:
    `httputil.ReverseProxy`は、Goの標準ライブラリで提供されるリバースプロキシの実装です。これは、受信したHTTPリクエストを別のサーバーに転送し、そのサーバーからの応答をクライアントに返す役割を担います。リバースプロキシは、ロードバランシング、SSLオフロード、キャッシュなどの目的で広く使用されます。`ReverseProxy`は、クライアントとバックエンドサーバー間のデータ転送に`io.Copy`を多用し、`http.CloseNotifier`を利用してクライアントの切断を処理することがあります。

6.  **`sendfile`システムコール**:
    `sendfile`は、一部のUnix系OSで利用可能なシステムコールで、カーネル空間内でファイルディスクリプタからソケットディスクリプタへデータを直接コピーする機能を提供します。これにより、ユーザー空間へのデータコピーが不要になり、CPUオーバーヘッドとメモリ帯域幅の使用量を削減し、非常に効率的なデータ転送が可能になります。`net/http`サーバーは、静的ファイルの提供などでこの最適化を利用しようとします。

## 技術的詳細

このコミットの技術的詳細の中心は、`io.Copy`から`io.CopyBuffer`への置き換えと、それに伴う`sync.Pool`を使用したバッファの再利用戦略です。

変更は主に`src/net/http/server.go`ファイルで行われています。

1.  **`copyBufPool`の導入**:
    `sync.Pool`型の`copyBufPool`が新しく定義されています。このプールは、`io.CopyBuffer`で使用するバイトスライス（バッファ）を管理するために使用されます。
    ```go
    var copyBufPool = sync.Pool{
        New: func() interface{} {
            b := make([]byte, 32*1024) // 32KBのバッファを生成
            return &b
        },
    }
    ```
    `New`フィールドに指定された関数は、プールが新しいオブジェクトを生成する必要があるときに呼び出されます。ここでは、32KBのバイトスライスが作成され、そのポインタが返されます。32KBというサイズは、一般的なネットワークI/O操作において良好なパフォーマンスを発揮することが経験的に知られているサイズです。

2.  **`conn.closeNotify()`内の変更**:
    `conn.closeNotify()`メソッドは、クライアントが接続を閉じたときに通知を受け取るための内部的なメカニズムに関連しています。この中で、パイプされたリーダー/ライター間でデータをコピーする際に`io.Copy`が使用されていました。
    変更前:
    ```go
    _, err := io.Copy(pw, readSource)
    ```
    変更後:
    ```go
    bufp := copyBufPool.Get().(*[]byte) // プールからバッファを取得
    defer copyBufPool.Put(bufp)         // 関数終了時にバッファをプールに戻す
    _, err := io.CopyBuffer(pw, readSource, *bufp) // 取得したバッファを使用
    ```
    ここで、`copyBufPool.Get()`を呼び出して`*[]byte`型のバッファポインタを取得し、`defer`ステートメントを使って関数が終了する際に`copyBufPool.Put(bufp)`でバッファをプールに戻しています。これにより、このコピー操作が頻繁に実行されても、新しいバッファが毎回割り当てられるのではなく、既存のバッファが再利用されるようになります。

3.  **`response.ReadFrom()`内の変更**:
    `response.ReadFrom()`メソッドは、`http.ResponseWriter`が`io.ReaderFrom`インターフェースを実装している場合に、効率的なデータ転送を提供するために使用されます。このメソッド内には、`sendfile`のような最適化が利用できない場合のフォールバックパスがあります。
    変更前:
    ```go
    return io.Copy(writerOnly{w}, src)
    ```
    変更後:
    ```go
    bufp := copyBufPool.Get().(*[]byte) // プールからバッファを取得
    defer copyBufPool.Put(bufp)         // 関数終了時にバッファをプールに戻す
    return io.CopyBuffer(writerOnly{w}, src, *bufp) // 取得したバッファを使用
    ```
    ここでも同様に、`sync.Pool`からバッファを取得し、`io.CopyBuffer`に渡して使用し、処理後にプールに戻すことで、メモリ割り当てを削減しています。

4.  **ベンチマークの追加**:
    `src/net/http/serve_test.go`には、`BenchmarkCloseNotifier`という新しいベンチマークが追加されています。このベンチマークは、`http.CloseNotifier`を使用するシナリオをシミュレートし、このコミットによるパフォーマンス改善を測定するために使用されます。ベンチマークは`b.ReportAllocs()`を呼び出すことで、メモリ割り当てに関する詳細な統計情報も報告するように設定されています。これにより、変更がメモリ使用量に与える影響を定量的に評価できます。

これらの変更により、特に高負荷な環境や、`io.ReaderFrom`/`io.WriterTo`最適化が利用できない状況下での`net/http`サーバーの効率が向上します。メモリ割り当ての削減は、ガベージコレクションのポーズタイムを短縮し、全体的なレイテンシとスループットの改善に貢献します。

## コアとなるコードの解説

このコミットのコアとなるコードの変更は、`src/net/http/server.go`における`io.Copy`から`io.CopyBuffer`への置き換えと、それに伴う`sync.Pool`の導入です。

1.  **`copyBufPool`の定義**:
    `var copyBufPool = sync.Pool{...}`
    このコードは、`sync.Pool`型のグローバル変数`copyBufPool`を定義しています。`New`フィールドに指定された匿名関数は、プールが空のときに新しいオブジェクト（この場合は`[]byte`型の32KBバッファへのポインタ）を生成するために使用されます。このプールは、複数のゴルーチン間でバッファを安全に再利用することを可能にし、頻繁なバッファの割り当てとガベージコレクションのオーバーヘッドを削減します。

2.  **`conn.closeNotify()`内の変更**:
    `bufp := copyBufPool.Get().(*[]byte)`
    `defer copyBufPool.Put(bufp)`
    `_, err := io.CopyBuffer(pw, readSource, *bufp)`
    `conn.closeNotify()`内のゴルーチンでは、以前は`io.Copy`を使用していましたが、この変更により`copyBufPool.Get()`で`sync.Pool`からバイトスライスバッファを取得し、それを`io.CopyBuffer`の第三引数として渡しています。`defer copyBufPool.Put(bufp)`は、このゴルーチンが終了する際に、取得したバッファをプールに返却することを保証します。これにより、このコピー操作が繰り返されても、新しいバッファがヒープに割り当てられることなく、既存のバッファが再利用されます。

3.  **`response.ReadFrom()`内の変更**:
    `bufp := copyBufPool.Get().(*[]byte)`
    `defer copyBufPool.Put(bufp)`
    `return io.CopyBuffer(writerOnly{w}, src, *bufp)`
    `response.ReadFrom()`メソッドのフォールバックパスでも同様の変更が行われています。`sendfile`のような最適化が利用できない場合に、`io.Copy`の代わりに`io.CopyBuffer`が使用され、`copyBufPool`から取得したバッファが渡されます。ここでも`defer`を使ってバッファの返却を保証しています。

これらの変更は、Goの`net/http`サーバーが、特に`http.CloseNotifier`を使用するシナリオや、`sendfile`最適化が利用できないフォールバックパスにおいて、より効率的に動作するように設計されています。バッファの再利用は、メモリ割り当てを劇的に削減し、結果としてガベージコレクションの頻度と時間を減らし、アプリケーションの全体的なパフォーマンスと応答性を向上させます。

`src/net/http/serve_test.go`に追加された`BenchmarkCloseNotifier`は、これらの最適化が実際に効果を発揮していることを検証するためのものです。`b.ReportAllocs()`を呼び出すことで、ベンチマークは操作ごとのメモリ割り当て回数とバイト数を報告し、このコミットが目指すメモリ効率の改善を明確に示しています。

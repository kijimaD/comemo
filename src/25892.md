# [インデックス 25892] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/tar` パッケージ内の `Reader.Next` メソッドのロジックを、再帰ベースからループベースへと変更するものです。これにより、特に複数のヘッダーを持つtarアーカイブの処理における正確性と可読性が向上しました。

## コミット

`archive/tar` パッケージの `Reader.Next` メソッドが、再帰的なロジックからループベースのロジックに書き換えられました。この変更は、複数のメタヘッダー（PAX拡張ヘッダーやGNU拡張ヘッダーなど）が連続して出現するtarアーカイブの解析において、ヘッダーの適用順序の正確性を保証し、コードの理解を容易にすることを目的としています。

## 変更の背景

この変更の主な背景には、`archive/tar` パッケージがtarアーカイブを解析する際の、既存の再帰的ロジックが抱えていた問題点があります。

1.  **可読性と理解の困難さ**: 再帰的な処理は、特に複数のメタヘッダーが連続して出現し、それぞれが後続のエントリに影響を与えるような複雑なシナリオにおいて、コードの追跡と理解を困難にします。tarフォーマットの仕様では、メタヘッダーは「次のエントリに影響を与える」と記述されることが多く、再帰はこれを「逆順に適用する」傾向があるため、直感に反する動作となりがちでした。

2.  **ヘッダー適用順序の誤り**: 以前の再帰的な実装では、複数のヘッダーが連続する場合に、それらの変更が誤った順序で適用される可能性がありました。これは、特にPAX拡張ヘッダーやGNU拡張ヘッダーのような、ファイル名やリンク名、その他の属性を拡張するメタデータを持つ場合に顕著でした。結果として、Goの `archive/tar` の動作が、GNU tarやBSD tarといった広く使われている他のtarユーティリティの動作と異なるという問題が発生していました。これは、tarアーカイブの互換性において重要な問題です。

これらの問題を解決し、より堅牢で標準に準拠したtarアーカイブの解析を実現するために、`Reader.Next` メソッドのロジックを再帰からループベースへと移行する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### Tar (Tape Archive) フォーマット

Tarは、複数のファイルを一つのアーカイブファイルにまとめるためのフォーマットです。元々は磁気テープへのバックアップのために開発されましたが、現在ではファイル配布やアーカイブ作成に広く利用されています。Tarアーカイブは、一連の「メンバー」または「エントリ」で構成され、各エントリはヘッダーブロックとそれに続くデータブロック（ファイルの内容）からなります。

### Tarのヘッダーと拡張

オリジナルのtarフォーマットには、ファイル名やリンク名の長さ、ファイルサイズなどに制限がありました。これらの制限を克服するために、様々な拡張が導入されました。

1.  **Ustar (POSIX.1-1988)**: POSIX標準によって定義された拡張で、ファイル名にプレフィックスフィールドを導入することで、ファイル名の長さを256文字まで拡張しました。

2.  **PAX (Portable Archive eXchange) 拡張ヘッダー**: POSIX.1-2001で定義されたPAXフォーマットは、`ustar` フォーマットをさらに拡張します。これは、特別な「拡張ヘッダーレコード」を導入することで実現されます。これらのヘッダーは、`tar` アーカイブ内の特殊なファイルとして扱われ、`typeflag` が `'x'` (ファイルごとの拡張ヘッダー) または `'g'` (グローバル拡張ヘッダー) で識別されます。PAX拡張ヘッダーは、以下の機能を提供します。
    *   **無制限の長さのファイル名とリンク名**: `path` および `linkpath` キーワードを使用して、任意の長さの名前を格納できます。
    *   **より大きなファイルサイズ**: 従来の8 GiBを超えるファイルをアーカイブできます。
    *   **高精度なタイムスタンプ**: ナノ秒単位のタイムスタンプを格納できます。
    *   **UTF-8エンコーディング**: パス名、リンク名、ユーザー名、グループ名にUTF-8をサポートします。
    PAXは `ustar` リーダーとの後方互換性があり、古い `tar` プログラムは拡張ヘッダーレコードを無視するか、通常のファイルとして扱います。

3.  **GNU Tar 拡張**: GNU `tar` は、PAXとは異なる独自の一連の拡張を持っています。
    *   **ロングネームとロングリンク**: GNU `tar` は、特別なファイルタイプ `'L'` (ロングファイル名) と `'K'` (ロングリンク名) を使用します。これらは、後続のファイルエントリの完全なロング名またはリンク名を含むヘッダーブロックです。
    *   **スパースファイル**: GNU `tar` は、スパースファイル（大部分がゼロで構成され、ディスクスペースを節約するために最適化されたファイル）の効率的なアーカイブをサポートします。

### `io.Reader` インターフェース

Go言語の `io.Reader` インターフェースは、データを読み込むための基本的な抽象化を提供します。`archive/tar` パッケージは、このインターフェースを実装してtarアーカイブからデータを読み込みます。

## 技術的詳細

このコミットの技術的な核心は、`Reader.Next()` メソッドの制御フローを、再帰呼び出しから明示的な `for` ループへと変更した点にあります。

以前の再帰的な実装では、`Reader.Next()` が特殊なヘッダー（PAX拡張ヘッダーやGNUロングネーム/ロングリンクヘッダー）を読み込んだ場合、そのヘッダーを処理した後、自身を再帰的に呼び出して次のエントリを読み込もうとしていました。このアプローチは、ヘッダーが「次のエントリに影響を与える」というtarフォーマットのセマンティクスと、再帰が「逆順に適用する」という性質との間に不整合を生じさせ、特に複数のメタヘッダーが連続する場合に、ヘッダーの属性が正しく結合されない、あるいは誤った順序で適用される原因となっていました。

新しいループベースの実装では、`Reader.Next()` は `for` ループ内でヘッダーを繰り返し読み込みます。
1.  まず、`tr.skipUnread()` を呼び出して、前のエントリの未読データをスキップし、アライメントパディングを処理します。
2.  次に、`tr.readHeader()` を呼び出して次のヘッダーを読み込みます。
3.  読み込んだヘッダーの `Typeflag` に応じて、`switch` ステートメントで処理を分岐します。
    *   **`TypeXHeader` (PAX拡張ヘッダー)**: `parsePAX(tr)` を呼び出してPAXヘッダーを解析し、`extHdrs` マップに格納します。このヘッダーは現在のエントリではなく、**次のエントリ**に適用されるメタデータであるため、`continue loop` を実行してループの先頭に戻り、次のヘッダーの読み込みを試みます。
    *   **`TypeGNULongName` または `TypeGNULongLink` (GNUロングネーム/ロングリンクヘッダー)**: `ioutil.ReadAll(tr)` を使用して、ヘッダーのペイロード（実際のロングネームまたはロングリンク名）を読み込みます。これを `extHdrs` マップに変換して格納し、同様に `continue loop` を実行して次のヘッダーを読み込みます。
    *   **`default` (通常のファイルヘッダー)**: ここで初めて、`mergePAX(hdr, extHdrs)` を呼び出して、これまでに収集されたPAX/GNU拡張ヘッダーの情報を現在の `hdr` に適用します。その後、スパースファイルのチェックを行い、`break loop` を実行してループを終了し、通常のファイルヘッダーを返します。

このループベースのアプローチにより、メタヘッダーは「次のエントリ」が実際に読み込まれるまで適用されず、複数のメタヘッダーが連続しても、それらが正しい順序で累積され、最終的なファイルヘッダーに正確に適用されることが保証されます。これにより、GNU tarやBSD tarとの互換性が向上し、コードの動作がより予測可能で理解しやすくなりました。

## コアとなるコードの変更箇所

主な変更は `src/archive/tar/reader.go` の `Reader.Next()` メソッドに集中しています。

-   **`src/archive/tar/reader.go`**:
    -   `Reader.Next()` メソッドの全体的な構造が、再帰的な呼び出しから `for` ループ (`loop:` ラベル付き) に変更されました。
    -   `TypeXHeader`, `TypeGNULongName`, `TypeGNULongLink` の処理が `switch` ステートメント内に移動し、これらの特殊なヘッダーが読み込まれた際には `continue loop` を使用して次のヘッダーの読み込みを継続するようになりました。
    -   通常のファイルヘッダー (`default` ケース) が検出された場合にのみ、これまでに収集された拡張ヘッダー情報 (`extHdrs`) が現在のヘッダー (`hdr`) に `mergePAX` を介して適用され、ループが `break loop` で終了します。
    -   `checkForGNUSparsePAXHeaders` の呼び出しも、通常のファイルヘッダーが処理される `default` ケース内に移動しました。

-   **`src/archive/tar/reader_test.go`**:
    -   `untarTests` 変数に、`gnu-multi-hdrs.tar` と `pax-multi-hdrs.tar` を使用した新しいテストケースが追加されました。これらのテストは、複数のヘッダーが連続するシナリオで、Goの `archive/tar` がGNU tarやBSD tarと同じ動作をすることを確認するために設計されています。

-   **`src/archive/tar/testdata/gnu-multi-hdrs.tar` および `src/archive/tar/testdata/pax-multi-hdrs.tar`**:
    -   新しいバイナリテストデータファイルが追加されました。これらは、複数のGNU拡張ヘッダーおよびPAX拡張ヘッダーを含むtarアーカイブであり、新しいロジックの正確性を検証するために使用されます。

## コアとなるコードの解説

変更された `Reader.Next()` メソッドのコアとなる部分は以下の通りです。

```go
func (tr *Reader) Next() (*Header, error) {
	if tr.err != nil {
		return nil, tr.err
	}

	var hdr *Header
	var extHdrs map[string]string

loop:
	for {
		tr.err = tr.skipUnread() // 前のエントリの未読データをスキップ
		if tr.err != nil {
			return nil, tr.err
		}

		hdr = tr.readHeader() // 次のヘッダーを読み込む
		if tr.err != nil {
			return nil, tr.err
		}

		// PAX/GNUの特殊ヘッダーとファイルをチェック
		switch hdr.Typeflag {
		case TypeXHeader: // PAX拡張ヘッダー
			extHdrs, tr.err = parsePAX(tr) // PAXヘッダーを解析
			if tr.err != nil {
				return nil, tr.err
			}
			continue loop // これは次のヘッダーに影響するメタヘッダーなので、ループを続行

		case TypeGNULongName, TypeGNULongLink: // GNUロングネーム/ロングリンクヘッダー
			var realname []byte
			realname, tr.err = ioutil.ReadAll(tr) // ロングネーム/リンク名を読み込む
			if tr.err != nil {
				return nil, tr.err
			}

			// GNU拡張をPAXヘッダーに変換
			if extHdrs == nil {
				extHdrs = make(map[string]string)
			}
			var p parser
			switch hdr.Typeflag {
			case TypeGNULongName:
				extHdrs[paxPath] = p.parseString(realname)
			case TypeGNULongLink:
				extHdrs[paxLinkpath] = p.parseString(realname)
			}
			if p.err != nil {
				tr.err = p.err
				return nil, tr.err
			}
			continue loop // これは次のヘッダーに影響するメタヘッダーなので、ループを続行

		default: // 通常のファイルヘッダー
			mergePAX(hdr, extHdrs) // 収集したPAX/GNU拡張ヘッダー情報を現在のヘッダーに適用

			// PAXフォーマットのスパースファイルをチェック
			sp, err := tr.checkForGNUSparsePAXHeaders(hdr, extHdrs)
			if err != nil {
				tr.err = err
				return nil, err
			}
			if sp != nil {
				// 現在のファイルがPAXフォーマットのGNUスパースファイルの場合
				// 現在のファイルリーダーをスパースファイルリーダーに設定
				tr.curr, tr.err = newSparseFileReader(tr.curr, sp, hdr.Size)
				if tr.err != nil {
					return nil, tr.err
				}
			}
			break loop // これはファイルなので、ループを終了
		}
	}
	return hdr, nil // 最終的なヘッダーを返す
}
```

このコードは、`for` ループと `switch` ステートメントを巧みに利用して、tarアーカイブ内のヘッダーを順次処理します。

-   `loop:` ラベルは、`continue loop` ステートメントがループの先頭に戻るためのターゲットを提供します。
-   `tr.skipUnread()` は、前のエントリのデータが完全に読み込まれていない場合や、アライメントのためのパディングが存在する場合に、それらをスキップして次のヘッダーの開始位置に移動します。
-   `tr.readHeader()` は、物理的に次のヘッダーブロックを読み込みます。
-   `switch hdr.Typeflag` は、読み込んだヘッダーの種類に基づいて処理を分岐します。
    -   `TypeXHeader` (PAX拡張ヘッダー) や `TypeGNULongName`, `TypeGNULongLink` (GNU拡張ヘッダー) の場合、これらはメタデータであり、それ自体がファイルエントリではないため、関連する情報を `extHdrs` マップに格納した後、`continue loop` を実行して次のヘッダーの読み込みに進みます。これにより、メタデータが「次の」実際のファイルエントリに適用されるまで保持されます。
    -   `default` ケースは、通常のファイルエントリのヘッダーが検出されたことを意味します。この時点で、これまでに収集されたすべての拡張ヘッダー情報 (`extHdrs`) が `mergePAX` 関数を通じて現在の `hdr` に結合されます。これにより、ロングネームやその他の拡張属性が正しく適用されます。
    -   その後、`checkForGNUSparsePAXHeaders` を呼び出してスパースファイルの情報をチェックし、必要に応じて `newSparseFileReader` を使用してスパースファイルリーダーを設定します。
    -   最後に `break loop` を実行してループを終了し、完全に構築された `Header` オブジェクトを返します。

このループベースの設計により、ヘッダーの処理順序が明確になり、複数のメタヘッダーが連続しても、それらが正しく累積され、最終的なファイルエントリに適用されることが保証されます。

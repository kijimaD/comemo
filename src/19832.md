## 元コミット内容

`cmd/ld: better diagnostics on unaligned symbols`

このコミットの目的は、アライメントされていないシンボルに関する診断メッセージを改善することです。ビルドが失敗する原因を特定し、その後のロールバックや修正の判断に役立てることを意図しています。

## 変更の背景

Go言語のビルドシステム、特にリンカ (`cmd/ld`) は、生成されるバイナリのメモリレイアウトにおいて、特定のデータ構造が特定のバイト境界に配置される（アライメントされる）ことを要求します。これは、プロセッサがメモリからデータを効率的に読み書きするために重要であり、多くの場合、パフォーマンスの向上や、特定のハードウェアアーキテクチャでのクラッシュの回避に寄与します。

コミットメッセージにある「Want to see why builders are failing.」という記述から、当時、Goのビルドシステム（おそらくCI/CD環境のビルダ）が、アライメントされていないシンボルが原因で失敗している問題に直面していたことが伺えます。しかし、既存の診断メッセージは単に「unaligned symbol」としか表示されず、どのシンボルが、どのサイズで、どの位置でアライメント違反を起こしているのかという詳細情報が不足していました。この情報不足が、問題の根本原因を特定し、修正する作業を困難にしていたと考えられます。

このコミットは、問題の根本的な修正ではなく、まず問題の診断能力を向上させることを目的としています。詳細な診断メッセージが出力されることで、開発者はアライメント違反が発生している具体的なシンボルを特定し、その後の修正作業を効率的に進めることができるようになります。

## 前提知識の解説

### 1. メモリアライメント (Memory Alignment)

メモリアライメントとは、コンピュータのメモリ上でデータが特定のバイト境界に配置されることを指します。例えば、4バイトの整数は4の倍数のアドレスに配置される、といったルールです。多くのCPUアーキテクチャでは、アライメントされたデータへのアクセスは高速ですが、アライメントされていないデータへのアクセスは低速になったり、場合によってはハードウェア例外（クラッシュ）を引き起こしたりすることがあります。Go言語のランタイムやリンカは、このアライメントを適切に管理することで、パフォーマンスと移植性を確保しています。

### 2. Goリンカ (`cmd/ld`)

`cmd/ld` はGo言語のリンカです。Goのコンパイラ (`cmd/compile`) が生成したオブジェクトファイル（`.o`ファイル）や、Goの標準ライブラリ、その他の依存関係を結合して、実行可能なバイナリファイルを生成する役割を担っています。この過程で、各種シンボル（変数、関数、型情報など）がメモリ上に配置され、その際にアライメントの制約が考慮されます。

### 3. シンボル (Symbol)

プログラミングにおけるシンボルは、プログラム内の特定のエンティティ（変数、関数、型など）を識別するための名前です。リンカはこれらのシンボルを解決し、最終的な実行可能ファイル内でそれらがメモリ上のどこに配置されるかを決定します。

### 4. `PtrSize`

`PtrSize` は、ポインタのサイズ（バイト単位）を表す定数です。これは、ターゲットアーキテクチャ（例: 32ビットシステムでは4バイト、64ビットシステムでは8バイト）に依存します。Goのランタイムでは、メモリの割り当てやアライメントの計算において、この`PtrSize`が基準としてよく用いられます。

### 5. `diag` 関数

`diag` 関数は、Goのツールチェイン内で診断メッセージ（エラーや警告）を出力するために使用される内部関数です。このコミットでは、この`diag`関数の呼び出しに、より多くの引数を渡すことで、出力されるメッセージを詳細化しています。

### 6. `proggenaddsym` 関数

`src/cmd/ld/data.c` 内の `proggenaddsym` 関数は、リンカがシンボルをプログラムのデータセクションに追加する際の処理を担当しています。この関数内で、シンボルのサイズや現在のメモリ位置 (`g->pos`) が `PtrSize` の倍数であるかどうかがチェックされ、アライメント違反が検出されると `diag` 関数が呼び出されます。

### 7. GC関連のシンボル (`gotype`, `gcprog`, `gcmask`)

Goのガベージコレクション (GC) は、メモリ管理において重要な役割を果たします。GCは、どのメモリ領域がポインタを含んでいるかを正確に知る必要があります。
- `gotype`: Goの型情報を表すシンボルです。GCは型情報に基づいて、オブジェクト内のどの部分がポインタであるかを判断します。
- `gcprog`: ガベージコレクタがオブジェクトをスキャンする際に使用するプログラム（命令列）です。
- `gcmask`: ガベージコレクタがオブジェクト内のポインタを識別するために使用するビットマスクです。
これらのGC関連のシンボルも、メモリ上で適切にアライメントされる必要があります。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/ld/data.c` ファイル内の `proggenaddsym` 関数における `diag` 関数の呼び出し方を変更した点にあります。

変更前は、アライメント違反が検出された際に、以下のような一般的なメッセージが出力されていました。

```c
diag("proggenaddsym: unaligned symbol");
```

これに対し、変更後は、アライメント違反が発生したシンボルの具体的な情報がメッセージに含まれるようになりました。

```c
diag("proggenaddsym: unaligned conservative symbol %s: size=%lld pos=%lld",
     s->name, s->size, g->pos);
```

この変更により、`diag` 関数に以下の情報が追加で渡されるようになりました。

*   `s->name`: アライメント違反を起こしたシンボルの名前。これにより、どのシンボルが問題の原因であるかを直接特定できます。
*   `s->size`: シンボルのサイズ。シンボルのサイズが`PtrSize`の倍数でない場合にアライメント違反が発生する可能性があるため、この情報は重要です。
*   `g->pos`: シンボルがメモリに配置されようとしている現在の位置（オフセット）。この位置が`PtrSize`の倍数でない場合にアライメント違反が発生する可能性があるため、この情報も重要です。

`proggenaddsym` 関数内では、シンボルの種類（`conservative scan`、`noscan`、`gcprog`、`gcmask`）に応じて、アライメントチェックが行われています。このコミットでは、これらすべてのケースにおいて、より詳細な診断メッセージが出力されるように修正が加えられています。これにより、リンカがアライメント違反を検出した際に、開発者はエラーメッセージから直接、問題のシンボル名、そのサイズ、そしてメモリ上の位置を把握できるようになり、デバッグの労力を大幅に削減できます。

## コアとなるコードの解説

`proggenaddsym` 関数は、Goリンカがシンボルを処理し、最終的なバイナリのデータセクションに配置する際の中心的なロジックを含んでいます。この関数は、シンボルの種類や特性に基づいて異なる処理パスを持ちます。

変更された4つの箇所は、それぞれ異なる種類のシンボル（またはスキャンモード）におけるアライメントチェックの条件分岐内にあります。

1.  **`conservative scan` の場合**:
    ```c
    // conservative scan
    if((s->size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned conservative symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `conservative scan` は、ガベージコレクタがポインタであるかどうかを厳密に判断できない場合に、ヒューリスティックに基づいてポインタである可能性のある値をスキャンするモードに関連しています。ここでは、シンボルのサイズまたは配置位置が `PtrSize` の倍数でない場合に診断メッセージが出力されます。

2.  **`noscan` の場合**:
    ```c
    // Emit large symbols as array.
    if((s->size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned noscan symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `noscan` は、ガベージコレクタがスキャンする必要のないデータ（例えば、ポインタを含まない純粋なデータ構造）を指します。ここでも、サイズまたは位置のアライメント違反がチェックされます。

3.  **`gcprog` の場合**:
    ```c
    gcprog = decodetype_gcprog(s->gotype);
    size = decodetype_size(s->gotype);
    if((size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned gcprog symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `gcprog` は、特定の型に関連付けられたガベージコレクションプログラムです。このプログラム自体もメモリに配置されるため、そのサイズと位置が `PtrSize` にアライメントされているかどうかが確認されます。

4.  **`gcmask` の場合**:
    ```c
    mask = decodetype_gcmask(s->gotype);
    size = decodetype_size(s->gotype);
    if((size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned gcmask symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `gcmask` は、ガベージコレクタがオブジェクト内のポインタを識別するために使用するビットマスクです。これもまた、メモリに配置される際にアライメントが重要となります。

これらの変更は、既存のアライメントチェックロジック自体を変更するものではなく、チェックが失敗した場合の**診断メッセージを強化する**ものです。これにより、Goのビルドプロセスでアライメント関連の問題が発生した際に、開発者がより迅速かつ正確に原因を特定できるようになります。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/ld/data.c` ファイル内の `proggenaddsym` 関数における `diag` 関数の呼び出し方を変更した点にあります。

変更前は、アライメント違反が検出された際に、以下のような一般的なメッセージが出力されていました。

```c
diag("proggenaddsym: unaligned symbol");
```

これに対し、変更後は、アライメント違反が発生したシンボルの具体的な情報がメッセージに含まれるようになりました。

```c
diag("proggenaddsym: unaligned conservative symbol %s: size=%lld pos=%lld",
     s->name, s->size, g->pos);
```

この変更により、`diag` 関数に以下の情報が追加で渡されるようになりました。

*   `s->name`: アライメント違反を起こしたシンボルの名前。これにより、どのシンボルが問題の原因であるかを直接特定できます。
*   `s->size`: シンボルのサイズ。シンボルのサイズが`PtrSize`の倍数でない場合にアライメント違反が発生する可能性があるため、この情報は重要です。
*   `g->pos`: シンボルがメモリに配置されようとしている現在の位置（オフセット）。この位置が`PtrSize`の倍数でない場合にアライメント違反が発生する可能性があるため、この情報も重要です。

`proggenaddsym` 関数内では、シンボルの種類（`conservative scan`、`noscan`、`gcprog`、`gcmask`）に応じて、アライメントチェックが行われています。このコミットでは、これらすべてのケースにおいて、より詳細な診断メッセージが出力されるように修正が加えられています。これにより、リンカがアライメント違反を検出した際に、開発者はエラーメッセージから直接、問題のシンボル名、そのサイズ、そしてメモリ上の位置を把握できるようになり、デバッグの労力を大幅に削減できます。

## コアとなるコードの解説

`proggenaddsym` 関数は、Goリンカがシンボルを処理し、最終的なバイナリのデータセクションに配置する際の中心的なロジックを含んでいます。この関数は、シンボルの種類や特性に基づいて異なる処理パスを持ちます。

変更された4つの箇所は、それぞれ異なる種類のシンボル（またはスキャンモード）におけるアライメントチェックの条件分岐内にあります。

1.  **`conservative scan` の場合**:
    ```c
    // conservative scan
    if((s->size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned conservative symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `conservative scan` は、ガベージコレクタがポインタであるかどうかを厳密に判断できない場合に、ヒューリスティックに基づいてポインタである可能性のある値をスキャンするモードに関連しています。ここでは、シンボルのサイズまたは配置位置が `PtrSize` の倍数でない場合に診断メッセージが出力されます。

2.  **`noscan` の場合**:
    ```c
    // Emit large symbols as array.
    if((s->size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned noscan symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `noscan` は、ガベージコレクタがスキャンする必要のないデータ（例えば、ポインタを含まない純粋なデータ構造）を指します。ここでも、サイズまたは位置のアライメント違反がチェックされます。

3.  **`gcprog` の場合**:
    ```c
    gcprog = decodetype_gcprog(s->gotype);
    size = decodetype_size(s->gotype);
    if((size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned gcprog symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `gcprog` は、特定の型に関連付けられたガベージコレクションプログラムです。このプログラム自体もメモリに配置されるため、そのサイズと位置が `PtrSize` にアライメントされているかどうかが確認されます。

4.  **`gcmask` の場合**:
    ```c
    mask = decodetype_gcmask(s->gotype);
    size = decodetype_size(s->gotype);
    if((size%PtrSize) || (g->pos%PtrSize))
        diag("proggenaddsym: unaligned gcmask symbol %s: size=%lld pos=%lld",
             s->name, s->size, g->pos);
    ```
    `gcmask` は、ガベージコレクタがオブジェクト内のポインタを識別するために使用するビットマスクです。これもまた、メモリに配置される際にアライメントが重要となります。

これらの変更は、既存のアライメントチェックロジック自体を変更するものではなく、チェックが失敗した場合の**診断メッセージを強化する**ものです。これにより、Goのビルドプロセスでアライメント関連の問題が発生した際に、開発者がより迅速かつ正確に原因を特定できるようになります。

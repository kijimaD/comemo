このコミットは、Goランタイムの`IndexByte`関数（バイトスライス内で特定のバイトを検索する関数）のパフォーマンス改善を目的としています。特に、x86-64アーキテクチャのアセンブリコードにおいて、`REP`プレフィックス付き命令の使用を避けることで、短いバイト列の検索性能を大幅に向上させています。`REP`プレフィックス付き命令は、その起動コストの高さから、短いデータに対する処理では非効率的であることが知られており、このコミットではその問題を解決するためにSSE命令などを活用した新しい検索ロジックが導入されています。

## 変更の背景

この変更の背景には、Goの`IndexByte`関数が内部的に使用していたx86-64アセンブリ命令`REPN; SCASB`のパフォーマンス特性があります。`REPN; SCASB`は、メモリブロックを効率的にスキャンするための命令ですが、その実行には一定の「起動コスト（startup cost）」が伴います。これは、命令のセットアップや内部パイプラインの初期化に時間がかかることを意味します。

短いバイト列（例えば10バイト程度）に対して`IndexByte`が呼び出される場合、この起動コストが実際のデータ処理にかかる時間よりも支配的になり、全体の実行時間を不必要に長くしていました。コミットメッセージに示されているベンチマーク結果（`BenchmarkIndexByte10-8`で22.4 ns/opから5.34 ns/opへ、-76.16%の改善）は、この問題が特に短い入力で顕著であったことを明確に示しています。

開発者は、この非効率性を認識し、`REP`プレフィックス付き命令の使用を「疫病のように避ける（Avoid them like the plague）」という強い表現で、その回避の重要性を強調しています。この改善は、Goプログラムが頻繁に実行する可能性のある短い文字列操作の性能を底上げし、全体的なアプリケーションの応答性向上に貢献します。

## 前提知識の解説

### `IndexByte`関数の役割

`IndexByte`関数は、Go言語の`bytes`パッケージや`strings`パッケージで提供される基本的なユーティリティ関数の一つです。その主な役割は、与えられたバイトスライス（または文字列）の中から、特定のバイト（文字）が最初に現れるインデックスを検索することです。もしバイトが見つからない場合は-1を返します。この関数は、文字列処理やバイナリデータ解析において非常に頻繁に使用されるため、その性能はGoプログラム全体のパフォーマンスに大きな影響を与えます。

### x86-64アセンブリにおける`REP`プレフィックス命令と性能特性

x86-64アーキテクチャには、メモリ操作を効率化するための「文字列命令（string instructions）」と呼ばれる特殊な命令群があります。これらは通常、`REP`（Repeat）プレフィックスと組み合わせて使用されます。

*   **`REP`プレフィックス**: `REP`プレフィックスは、続く文字列命令を`CX`レジスタで指定された回数だけ繰り返すようにCPUに指示します。例えば、`REPN; SCASB`は、`AL`レジスタの内容と`DI`レジスタが指すメモリ位置のバイトを比較し、一致しないか`CX`がゼロになるまで繰り返します。
*   **`SCASB`**: `SCASB`（Scan String Byte）は、`AL`レジスタに格納されたバイトと、`ES:DI`（または`DI`）が指すメモリ位置のバイトを比較し、`DI`をインクリメント（またはデクリメント）する命令です。
*   **`REPN; SCASB`**: これは「Not Equalが続く限り`SCASB`を繰り返す」という意味で、特定のバイトが見つかるまでメモリをスキャンするのに使われます。

**性能特性と「起動コスト」**:
`REP`プレフィックス付き命令は、大量のデータを処理する場合には非常に効率的です。これは、CPUが命令フェッチやデコードのオーバーヘッドを一度で済ませ、内部的に最適化されたループで高速にデータを処理できるためです。しかし、この命令には「起動コスト」という欠点があります。これは、命令の実行を開始するための内部的なセットアップ（マイクロコードのロード、パイプラインの初期化など）に一定の時間がかかることを指します。

短いデータ（例えば16バイト未満）に対して`REPN; SCASB`を使用すると、この起動コストがデータ処理自体の時間よりも大きくなり、結果として通常のループ処理やSIMD（Single Instruction, Multiple Data）命令（SSE/AVX2など）を使った方が速くなることがあります。このコミットは、まさにこの「起動コスト」の問題を解決しようとしています。

### SSE/AVX2命令セットの概要とバイト検索における利点

**SIMD (Single Instruction, Multiple Data)**:
SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行できるプロセッサの機能です。これにより、データ並列処理が可能となり、特にメディア処理、科学計算、そして文字列操作のような大量のデータに対する反復的な処理で高い性能を発揮します。

**SSE (Streaming SIMD Extensions)**:
SSEはIntelが開発したSIMD命令セットで、128ビットのXMMレジスタを使用します。これにより、16個のバイト、8個のワード、4個のダブルワード、2個のクアッドワード、または2個の倍精度浮動小数点数を同時に処理できます。`IndexByte`の文脈では、16個のバイトを一度に比較できる`PCMPEQB`（Packed Compare Equal Bytes）のような命令が非常に有用です。

**AVX2 (Advanced Vector Extensions 2)**:
AVX2はSSEの拡張であり、256ビットのYMMレジスタを使用します。これにより、SSEの2倍のデータ（例えば32個のバイト）を一度に処理できます。AVX2は、より大規模なデータ並列処理を可能にし、対応するCPUではさらに高い性能を提供します。

**バイト検索における利点**:
SSEやAVX2命令を使用すると、一度に多くのバイトを検索対象のバイトと比較できます。例えば、`PCMPEQB`命令は、128ビットレジスタ内の16バイトすべてを、検索対象のバイトで埋められた別の128ビットレジスタと比較し、一致するバイトに対応するビットをセットした結果を生成します。この結果を`PMOVMSKB`命令で整数レジスタに抽出し、`BSFL`（Bit Scan Forward）命令で最初のセットビットを見つけることで、一致するバイトのインデックスを高速に特定できます。これにより、`REP`プレフィックス付き命令の起動コストを回避しつつ、効率的な並列検索を実現できます。

### Goランタイムにおけるアセンブリコードの役割

Go言語は、その高性能な実行環境を実現するために、一部のクリティカルな部分でアセンブリ言語を使用しています。特に、スケジューラ、メモリ管理、そして今回のような低レベルのプリミティブ操作（バイトスライス操作など）では、C言語やGo言語では実現が難しいレベルの最適化を行うためにアセンブリコードが書かれます。これにより、GoプログラムはOSやハードウェアの機能を最大限に活用し、高い実行効率を達成しています。`src/runtime/asm_amd64.s`は、x86-64アーキテクチャ向けのGoランタイムのアセンブリコードが記述されているファイルです。

## 技術的詳細

このコミットの技術的詳細の中心は、`IndexByte`関数のx86-64アセンブリ実装（`runtime·indexbytebody`）から`REP`プレフィックス付き命令を排除し、代わりにSIMD命令（SSE/AVX2）をより積極的に活用する点にあります。

### 変更前の実装（推測）

変更前の実装では、おそらく以下のロジックが使用されていました。

1.  **短いバイト列の処理**: 非常に短いバイト列（例えば16バイト未満）の場合、`REPN; SCASB`を使って直接スキャンしていました。
2.  **アライメント調整**: 16バイト以上のバイト列の場合、まずデータポインタを16バイト境界にアライメントするために、先頭の数バイトを`REPN; SCASB`でスキャンしていました。
3.  **SSE/AVX2による高速スキャン**: アライメントされた後、SSE（またはAVX2）命令を使って16バイト（または32バイト）単位で高速にスキャンしていました。
4.  **残りのバイトの処理**: 最後に、SSE/AVX2で処理しきれなかった末尾の数バイトを、再度`REPN; SCASB`でスキャンしていました。

このアプローチの問題は、短いバイト列の処理や、アライメント調整、末尾処理といった部分で`REPN; SCASB`が使われるたびに、その起動コストが発生し、特に短い入力でオーバーヘッドが大きくなることでした。

### 変更後の実装

変更後の実装では、`REPN; SCASB`の使用を完全に排除し、すべてのケースでSIMD命令（SSE/AVX2）またはよりシンプルなループ構造に切り替えています。

1.  **検索対象バイトの準備**:
    *   `MOVD AX, X0`
    *   `PUNPCKLBW X0, X0`
    *   `PSHUFL $0, X0, X0`
    これらの命令により、検索対象のバイト（`AL`レジスタに格納されている）が、128ビットのXMMレジスタ`X0`のすべてのバイトに複製されます。これにより、`X0`は検索対象バイトで埋め尽くされたベクトルとなり、`PCMPEQB`命令で他のバイト列と比較する準備が整います。

2.  **短いバイト列の処理 (`small`ラベル)**:
    *   変更前は`REPN; SCASB`が使われていましたが、変更後はSIMD命令とビット操作を組み合わせた新しいロジックが導入されています。
    *   `TESTQ BX, BX` / `JEQ failure`: 長さが0の場合は即座に失敗を返します。
    *   `MOVOU (SI), X1`: 検索対象のバイト列の先頭から最大16バイトをXMMレジスタ`X1`にロードします。
    *   `PCMPEQB X0, X1`: `X0`（検索対象バイト）と`X1`（データ）をバイト単位で比較し、一致するバイトに対応するビットをセットした結果を`X1`に格納します。
    *   `PMOVMSKB X1, DX`: `X1`の各バイトの最上位ビットを抽出し、16ビットのマスクとして`DX`レジスタに格納します。
    *   `BSFL DX, DX`: `DX`レジスタの最下位ビットから最初のセットビットのインデックスを検索し、そのインデックスを`DX`に格納します。これは、一致するバイトが`X1`のどの位置にあるかを示します。
    *   `JZ failure`: セットビットが見つからなければ、一致するバイトがないため失敗を返します。
    *   `CMPL DX, BX` / `JAE failure`: 見つかったインデックスがバイト列の長さ`BX`以上であれば、それは有効な一致ではないため失敗を返します。
    *   `MOVQ DX, (R8)` / `RET`: 有効な一致が見つかれば、そのインデックスを結果として返します。
    *   **ページ境界の考慮**: `endofpage`ラベルへのジャンプロジックが追加されており、短いバイト列がメモリページ境界をまたぐ場合に、安全にデータをロードするための特別な処理が導入されています。これは、`MOVOU`命令がページ境界をまたぐとパフォーマンスが低下したり、アライメントされていないアクセスでクラッシュする可能性があるため、その対策と考えられます。

3.  **長いバイト列の処理 (`sse`ラベル)**:
    *   変更前はアライメント調整のために`REPN; SCASB`が使われていましたが、変更後は`LEAQ -16(SI)(BX*1), AX`で最後の16バイトの開始アドレスを計算し、`sseloop`と`sseloopentry`を使って、データポインタ`DI`が`AX`に到達するまで16バイト単位でループ処理を行います。
    *   `MOVOU (DI), X1`: 16バイトのチャンクを`X1`にロード。
    *   `PCMPEQB X0, X1`: 比較。
    *   `PMOVMSKB X1, DX`: マスク抽出。
    *   `BSFL DX, DX`: 最初のセットビット検索。
    *   `JNZ ssesuccess`: 見つかれば`ssesuccess`へジャンプ。
    *   `ADDQ $16, DI`: 次の16バイトチャンクへ進む。
    *   ループ終了後、残りの末尾の16バイト（オーバーラップする可能性あり）を再度処理することで、すべてのバイトが確実にスキャンされるようにしています。これにより、`REP`プレフィックスを使わずに、アライメントの有無にかかわらず効率的に処理できるようになっています。

4.  **AVX2の活用 (`avx2`ラベル)**:
    *   AVX2が利用可能なシステムでは、`VPBROADCASTB`と`VPCMPEQB`を使って32バイト単位で処理することで、さらに高速化を図っています。基本的なロジックはSSEの場合と同様ですが、レジスタ幅が256ビットに拡張されています。

## コアとなるコードの解説

### `src/runtime/asm_amd64.s` の `runtime·indexbytebody` 関数

この関数は、Goの`IndexByte`関数の実体であり、特定のバイトをバイトスライス内で検索するアセンブリコードです。変更の核心は、`REP`プレフィックス付き命令の排除と、SIMD命令（SSE/AVX2）のより洗練された利用にあります。

#### 検索対象バイトの準備

```assembly
	MOVD AX, X0
	PUNPCKLBW X0, X0
	PUNPCKLBW X0, X0
	PSHUFL $0, X0, X0
```
これは、検索対象のバイト（`AL`レジスタに格納されている）を128ビットのXMMレジスタ`X0`のすべてのバイトに複製する標準的なSIMDテクニックです。
1.  `MOVD AX, X0`: `AX`レジスタの下位32ビット（`AL`を含む）を`X0`レジスタの下位32ビットに移動します。
2.  `PUNPCKLBW X0, X0`: `X0`の下位8バイトを、そのバイトを複製して16バイトに拡張します。これにより、`X0`の下位16バイトが検索対象バイトで埋められます。
3.  `PSHUFL $0, X0, X0`: `X0`レジスタのバイトをシャッフルして、すべてのバイトが検索対象バイトのコピーになるようにします。これで`X0`は`[c, c, c, c, c, c, c, c, c, c, c, c, c, c, c, c]`のような形になります。

#### 短いバイト列の処理 (`small`ラベル)

```assembly
small:
	TESTQ	BX, BX
	JEQ	failure

	// Check if we'll load across a page boundary.
	LEAQ	16(SI), AX
	TESTW	$0xff0, AX
	JEQ	endofpage

	MOVOU	(SI), X1 // Load data
	PCMPEQB	X0, X1	// Compare target byte with each byte in data.
	PMOVMSKB X1, DX	// Move result bits to integer register.
	BSFL	DX, DX	// Find first set bit.
	JZ	failure	// No set bit, failure.
	CMPL	DX, BX
	JAE	failure	// Match is past end of data.
	MOVQ	DX, (R8)
	RET

endofpage:
	MOVOU	-16(SI)(BX*1), X1	// Load data into the high end of X1.
	PCMPEQB	X0, X1	// Compare target byte with each byte in data.
	PMOVMSKB X1, DX	// Move result bits to integer register.
	MOVL	BX, CX
	SHLL	CX, DX
	SHRL	$16, DX	// Shift desired bits down to bottom of register.
	BSFL	DX, DX	// Find first set bit.
	JZ	failure	// No set bit, failure.
	MOVQ	DX, (R8)
	RET
```
このセクションは、バイト列の長さが16バイト未満の場合（`CMPQ BX, $16; JLT small`）に実行されます。
*   `TESTQ BX, BX; JEQ failure`: 長さが0の場合は、検索対象が見つからないため`-1`を返して終了します。
*   **ページ境界チェック**: `LEAQ 16(SI), AX; TESTW $0xff0, AX; JEQ endofpage` は、`SI`（データの開始アドレス）から16バイト先がメモリページ境界をまたぐかどうかをチェックしています。これは、`MOVOU`命令がアライメントされていないアクセスでも動作しますが、ページ境界をまたぐとパフォーマンスが低下したり、特定の状況で問題を引き起こす可能性があるため、その対策です。
*   **通常ケース (`small`のメインパス)**:
    *   `MOVOU (SI), X1`: データの先頭から最大16バイトを`X1`にロードします。`MOVOU`はアライメントされていないロード命令です。
    *   `PCMPEQB X0, X1`: `X0`（検索対象バイト）と`X1`（ロードしたデータ）の各バイトを比較し、一致するバイトに対応するビットを`X1`の対応するバイトの最上位ビットにセットします。
    *   `PMOVMSKB X1, DX`: `X1`の各バイトの最上位ビットを抽出し、16ビットの整数マスクとして`DX`レジスタに格納します。例えば、`X1`の0番目のバイトが一致していれば`DX`の0ビット目が1になります。
    *   `BSFL DX, DX`: `DX`レジスタの最下位ビットから最初のセットビットのインデックスを検索し、そのインデックスを`DX`に格納します。これは、一致するバイトが`X1`のどの位置（0-15）にあるかを示します。
    *   `JZ failure`: `DX`が0（セットビットがない）であれば、一致するバイトが見つからなかったため失敗です。
    *   `CMPL DX, BX; JAE failure`: 見つかったインデックス`DX`が、実際のバイト列の長さ`BX`以上であれば、それは有効な一致ではないため失敗です。これは、`MOVOU`が最大16バイトをロードするため、実際のデータ長より多くのバイトを読み込む可能性があるためです。
    *   `MOVQ DX, (R8); RET`: 有効な一致が見つかれば、そのインデックスを結果として返します。
*   **ページ境界をまたぐケース (`endofpage`ラベル)**:
    *   `MOVOU -16(SI)(BX*1), X1`: この命令は、バイト列の末尾から16バイトを`X1`にロードします。`BX*1`はバイト列の長さを示し、`-16(SI)(BX*1)`は`SI + BX - 16`のアドレス、つまりバイト列の末尾から16バイト手前のアドレスを指します。これにより、ページ境界をまたぐ可能性のある短いバイト列でも、安全に末尾のデータを含む16バイトをロードできます。
    *   `PCMPEQB X0, X1`、`PMOVMSKB X1, DX`、`BSFL DX, DX` は上記と同様です。
    *   `MOVL BX, CX; SHLL CX, DX; SHRL $16, DX`: この部分は、`PMOVMSKB`で得られたマスクを調整し、実際のバイト列の範囲内でのみ有効なビットを考慮するための複雑なビットシフト操作です。具体的には、`BX`（長さ）を使ってマスクをシフトし、不要なビットをクリアすることで、有効な一致のみを抽出します。
    *   `JZ failure`: 調整後のマスクにセットビットがなければ失敗です。
    *   `MOVQ DX, (R8); RET`: 有効な一致が見つかれば、そのインデックスを結果として返します。

#### 長いバイト列の処理 (`sse`ラベル)

```assembly
sse:
	LEAQ	-16(SI)(BX*1), AX	// AX = address of last 16 bytes
	JMP	sseloopentry
	
sseloop:
	// Move the next 16-byte chunk of the data into X1.
	MOVOU	(DI), X1
	// Compare bytes in X0 to X1.
	PCMPEQB	X0, X1
	// Take the top bit of each byte in X1 and put the result in DX.
	PMOVMSKB X1, DX
	// Find first set bit, if any.
	BSFL	DX, DX
	JNZ	ssesuccess
	// Advance to next block.
	ADDQ	$16, DI
sseloopentry:
	CMPQ	DI, AX
	JB	sseloop

	// Search the last 16-byte chunk.  This chunk may overlap with the
	// chunks we've already searched, but that's ok.
	MOVQ	AX, DI
	MOVOU	(AX), X1
	PCMPEQB	X0, X1
	PMOVMSKB X1, DX
	BSFL	DX, DX
	JNZ	ssesuccess
```
このセクションは、バイト列の長さが16バイト以上の場合に実行されます。
*   `LEAQ -16(SI)(BX*1), AX`: `AX`レジスタに、バイト列の末尾から16バイト手前のアドレスを計算して格納します。これは、ループがこのアドレスに到達するまで16バイト単位で処理し、その後、末尾の16バイトを別途処理するための境界です。
*   `sseloopentry`と`sseloop`: これは、`DI`（現在のデータポインタ）が`AX`に到達するまで16バイト単位でデータを処理するループです。
    *   `MOVOU (DI), X1`: 現在の16バイトチャンクをロード。
    *   `PCMPEQB X0, X1`、`PMOVMSKB X1, DX`、`BSFL DX, DX`: 検索対象バイトとの比較、マスク抽出、最初のセットビット検索を行います。
    *   `JNZ ssesuccess`: 一致するバイトが見つかれば、`ssesuccess`へジャンプして結果を返します。
    *   `ADDQ $16, DI`: `DI`を16バイト進めて次のチャンクへ。
*   ループ終了後、`MOVQ AX, DI; MOVOU (AX), X1; ...` の部分で、バイト列の末尾の16バイトを処理します。この末尾の16バイトは、前のループで処理されたチャンクとオーバーラップする可能性がありますが、これによりすべてのバイトが確実にスキャンされます。

#### 成功時の処理 (`ssesuccess`ラベル)

```assembly
ssesuccess:
	SUBQ SI, DI	// Compute offset of chunk within data.
	ADDQ DX, DI	// Add offset of byte within chunk.
	MOVQ DI, (R8)
	RET
```
一致するバイトが見つかった場合に実行されます。
*   `SUBQ SI, DI`: `DI`（一致が見つかったチャンクの開始アドレス）から`SI`（元のバイト列の開始アドレス）を引くことで、チャンクが元のバイト列のどこから始まるかのオフセットを計算します。
*   `ADDQ DX, DI`: `DX`（チャンク内での一致バイトのインデックス）を上記のオフセットに加えることで、元のバイト列全体における一致バイトの最終的なインデックスを計算します。
*   `MOVQ DI, (R8); RET`: 計算されたインデックスを結果として返します。

### `src/bytes/bytes_test.go` の変更

`TestIndexByteSmall`は、アセンブリコードの変更が、特に短いバイト列やメモリページ境界をまたぐようなエッジケースで正しく機能することを保証するための重要なテストです。このテストは、様々なオフセットで短いスライスを生成し、検索対象のバイトが見つかる場合と見つからない場合の両方で`IndexByte`の動作を検証しています。

`BenchmarkIndexByte10`の追加は、コミットメッセージに示された性能改善を直接測定するためのものです。このベンチマークが大幅な改善を示したことは、アセンブリコードの変更が成功したことを裏付けています。

# [インデックス 25642] ファイルの概要

このコミットは、Goランタイムにおける386アーキテクチャ（darwin/386, freebsd/386, linux/386など）での新しいOSスレッド（M）の起動処理に関する最適化と簡素化を目的としています。具体的には、スレッドローカルストレージ（TLS）の設定に必要なMのID (`m.id`) を、以前は `m.tls[0]` という中間的な場所にコピーしてからアセンブリコードで参照していたのを、アセンブリコードから `m.id` を直接参照するように変更することで、不要なデータコピーを排除し、コードの明確性を向上させています。

## 元コミット内容

```
runtime: update newosproc asm to access m.id directly

darwin/386, freebsd/386, and linux/386 use a setldt system call to
setup each M's thread-local storage area, and they need access to the
M's id for this.  The current code copies m.id into m.tls[0] (and this
logic has been cargo culted to OSes like NetBSD and OpenBSD, which
don't even need m.id to configure TLS), and then the 386 assembly
loads m.tls[0]... but since the assembly code already has a pointer to
the M, it might as well just load m.id directly.
```

## 変更の背景

Goランタイムは、GoルーチンをOSスレッド上で実行するために、M（Machine）と呼ばれるOSスレッドを抽象化した構造体を使用します。特定の386アーキテクチャ（darwin/386, freebsd/386, linux/386）では、新しいOSスレッドを起動する際に、そのスレッド固有のデータ領域であるスレッドローカルストレージ（TLS）を設定するために `setldt` システムコールが使用されます。この `setldt` システムコールは、TLS領域を識別するためにMのID (`m.id`) を必要とします。

これまでの実装では、Goのコード（`newosproc` 関数内）で `m.id` の値を `m` 構造体内の `m.tls[0]` というフィールドに一旦コピーしていました。その後、OSスレッドの起動処理を行うアセンブリコードが、この `m.tls[0]` から `m.id` を読み出して `setldt` システムコールに渡していました。

しかし、コミットメッセージが指摘するように、この `m.tls[0]` へのコピーは冗長でした。なぜなら、アセンブリコードは既に `m` 構造体へのポインタを持っており、そこから `m.id` を直接読み出すことが可能だったからです。さらに、NetBSDやOpenBSDのような一部のOSでは、TLSの設定に `m.id` がそもそも不要であるにもかかわらず、この「`m.id` を `m.tls[0]` にコピーする」というロジックが「カーゴカルト的」に（つまり、理由を深く理解せずに慣習的に）踏襲されていました。

このコミットは、この冗長なコピー処理を排除し、アセンブリコードが `m.id` を直接参照するように変更することで、コードの簡素化と効率化を図っています。

## 前提知識の解説

### GoランタイムとM (Machine)

Goプログラムは、Goルーチンと呼ばれる軽量な並行処理単位で動作します。これらのGoルーチンは、GoランタイムによってOSスレッド上でスケジューリングされます。Goランタイムは、このスケジューリングのために以下の3つの主要な要素を使用します。

-   **G (Goroutine)**: Goルーチンそのもの。スタック、命令ポインタ、その他のスケジューリング情報を持つ。
-   **M (Machine)**: OSスレッドを表す。Goルーチンを実行するための実際のOSスレッド。各Mは1つのOSスレッドに対応し、Goルーチンを実行したり、システムコールを実行したりする。
-   **P (Processor)**: 論理プロセッサ。MとGの間の仲介役。Goルーチンを実行するMに割り当てられる。

このコミットでは、特にM（OSスレッド）の起動と、それに伴うスレッド固有のデータ設定が焦点となっています。

### TLS (Thread-Local Storage)

TLS（Thread-Local Storage）は、マルチスレッドプログラミングにおいて、各スレッドが自分専用のデータを保持するための仕組みです。通常、グローバル変数や静的変数はすべてのスレッドで共有されますが、TLSを使用すると、同じ変数名であっても各スレッドが独立した値を持ち、他のスレッドからその値にアクセスされることはありません。Goランタイムでは、M（OSスレッド）ごとに固有の情報を保持するためにTLSが利用されます。

### `m.id` と `m.tls`

-   **`m.id`**: `m` 構造体（OSスレッドを表す）のフィールドの一つで、そのOSスレッドを一意に識別するためのIDです。
-   **`m.tls`**: `m` 構造体内のフィールドで、スレッドローカルストレージとして利用される領域です。通常は `uintptr` の配列として定義され、各要素にスレッド固有のデータが格納されます。

### `setldt` システムコール

`setldt` は、386アーキテクチャ（32ビットx86プロセッサ）で利用されるシステムコールの一つです。LDT（Local Descriptor Table）は、特定のタスク（スレッド）に固有のメモリセグメント記述子を格納するテーブルです。`setldt` システムコールは、このLDTのエントリを設定するために使用され、特にTLS領域をOSに登録する際に利用されます。これにより、各スレッドが自分自身のTLS領域に効率的にアクセスできるようになります。

### 386アーキテクチャとアセンブリコード

386アーキテクチャは、Intel 80386プロセッサに代表される32ビットのx86プロセッサアーキテクチャです。Goランタイムは、OSスレッドの起動やコンテキストスイッチなど、OSと密接に連携する低レベルな処理の一部をアセンブリ言語で実装しています。これは、C言語などの高水準言語では実現が難しい、あるいは効率が悪い操作（レジスタの直接操作、特定のCPU命令の使用など）を行うためです。このコミットでは、`setldt` システムコールを呼び出すアセンブリコードが変更の対象となっています。

## 技術的詳細

このコミットの核心は、Goランタイムが新しいOSスレッドを起動する際の `m.id` の取り扱い方法の変更にあります。

### 変更前

1.  Goのコード（`src/runtime/os1_*.go` ファイル内の `newosproc` 関数）で、新しいM（OSスレッド）が作成されると、そのMのID (`mp.id`) が `mp.tls[0]` にコピーされていました。
    ```go
    mp.tls[0] = uintptr(mp.id) // so 386 asm can find it
    ```
    このコメントが示すように、これは386アセンブリコードが `m.id` を見つけられるようにするための措置でした。
2.  その後、OSスレッドの起動処理を担うアセンブリコード（`src/runtime/sys_*_386.s` ファイル内）が実行されます。このアセンブリコードは、`m` 構造体へのポインタ（レジスタ `DX` などに格納されている）を受け取ります。
3.  アセンブリコードは、`m` 構造体内の `m.tls` フィールドのアドレスを計算し、その先頭（`m.tls[0]`）から `m.id` の値を読み出していました。
    ```assembly
    LEAL    m_tls(DX), BP
    MOVL    0(BP), DI  // m.tls[0] から m.id を読み出す
    ```
4.  読み出された `m.id` の値は、`setldt` システムコールに渡され、TLS領域の設定に使用されていました。

### 変更後

1.  Goのコード（`src/runtime/os1_*.go` ファイル内の `newosproc` 関数）から、`mp.tls[0] = uintptr(mp.id)` という行が削除されました。これにより、`m.id` を `m.tls[0]` にコピーする冗長な処理がなくなりました。
2.  アセンブリコード（`src/runtime/sys_*_386.s` ファイル内）は、`m` 構造体へのポインタ（`DX` レジスタ）を直接利用して、`m.id` フィールドから値を読み出すように変更されました。
    ```assembly
    MOVL    m_id(DX), DI // m.id を直接読み出す
    ```
    ここで `m_id(DX)` は、`DX` レジスタが指す `m` 構造体のアドレスから `m.id` フィールドのオフセットを加算したアドレスを指します。
3.  読み出された `m.id` の値は、引き続き `setldt` システムコールに渡され、TLS領域の設定に使用されます。

### 変更のメリット

-   **コードの簡素化**: `m.id` を `m.tls[0]` にコピーする不要なステップが削除され、Goコードとアセンブリコードの両方がより直接的になりました。
-   **効率の向上**: 不要なメモリ書き込み（`mp.tls[0] = uintptr(mp.id)`) がなくなり、わずかながらパフォーマンスが向上します。
-   **明確性の向上**: `m.id` が必要なOSでのみ `m.id` が利用され、不要なOSではそのコピー処理がなくなることで、コードの意図がより明確になりました。特に、NetBSDやOpenBSDのように `m.id` がTLS設定に不要なOSでもこのコピー処理が行われていた問題が解消されます。

### `//go:nowritebarrier` について

変更前のコードと変更後のコードの両方に `//go:nowritebarrier` というコメントが見られます。これはGoコンパイラに対する指示で、この関数内ではライトバリア（Write Barrier）を生成しないことを意味します。ライトバリアは、Goのガベージコレクション（GC）がオブジェクトの参照関係を正確に追跡するために、ポインタの書き込み時に実行される特別なコードです。`newosproc` のような低レベルなランタイム関数では、GCが完全に初期化されていない段階で実行されたり、GCの内部状態を直接操作したりすることがあるため、ライトバリアが予期せぬ副作用を引き起こす可能性があります。そのため、このような関数ではライトバリアを無効にすることがあります。このコミットの変更自体はライトバリアとは直接関係ありませんが、関連するコードのコンテキストとして重要です。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2種類の変更が行われています。

1.  **`newosproc` 関数からの `m.id` の `m.tls[0]` へのコピー処理の削除**:
    `src/runtime/os1_darwin.go`, `src/runtime/os1_dragonfly.go`, `src/runtime/os1_freebsd.go`, `src/runtime/os1_linux.go`, `src/runtime/os1_netbsd.go`, `src/runtime/os1_openbsd.go` の各ファイルで、`newosproc` 関数内の以下の行が削除されています。

    ```diff
    --- a/src/runtime/os1_darwin.go
    +++ b/src/runtime/os1_darwin.go
    @@ -78,9 +78,8 @@ func goenvs() {
     // May run with m.p==nil, so write barriers are not allowed.
     //go:nowritebarrier
     func newosproc(mp *m, stk unsafe.Pointer) {
    -	mp.tls[0] = uintptr(mp.id) // so 386 asm can find it
     	if false {
    -		print("newosproc stk=", stk, " m=", mp, " g=", mp.g0, " id=", mp.id, "/", int(mp.tls[0]), " ostk=", &mp, "\n")
    +		print("newosproc stk=", stk, " m=", mp, " g=", mp.g0, " id=", mp.id, " ostk=", &mp, "\n")
     	}
    ```
    また、デバッグ用の `print` 文からも `mp.tls[0]` の出力が削除されています。

2.  **386アセンブリコードでの `m.id` の直接参照**:
    `src/runtime/sys_darwin_386.s`, `src/runtime/sys_freebsd_386.s`, `src/runtime/sys_linux_386.s` の各ファイルで、アセンブリコードが `m.id` を読み出す部分が変更されています。

    ```diff
    --- a/src/runtime/sys_darwin_386.s
    +++ b/src/runtime/sys_darwin_386.s
    @@ -361,10 +361,8 @@ TEXT runtime·bsdthread_create(SB),NOSPLIT,$32
     //	SP = stack - C_32_STK_ALIGN
     TEXT runtime·bsdthread_start(SB),NOSPLIT,$0
      	// set up ldt 7+id to point at m->tls.
    -	// m->tls is at m+40.  newosproc left
    -	// the m->id in tls[0].
      	LEAL	m_tls(DX), BP
    -	MOVL	0(BP), DI
    +	MOVL	m_id(DX), DI
      	ADDL	$7, DI	// m0 is LDT#7. count up.
      	// setldt(tls#, &tls, sizeof tls)
      	PUSHAL	// save registers
    ```

## コアとなるコードの解説

### `newosproc` 関数 (Goコード)

`newosproc` 関数は、Goランタイムが新しいOSスレッドを起動する際に呼び出されるGoの関数です。この関数は、新しいM構造体 (`mp`) とスタックポインタ (`stk`) を引数として受け取ります。変更前は、この関数内で `mp.tls[0] = uintptr(mp.id)` という行があり、`mp.id` の値を `mp.tls` 配列の最初の要素に格納していました。これは、後続のアセンブリコードが `m.id` を利用できるようにするための準備でした。このコミットにより、この行が削除され、Goコード側での冗長なデータコピーがなくなりました。

### アセンブリコード (`sys_*_386.s` ファイル)

`runtime·bsdthread_start` (darwin), `runtime·thr_start` (freebsd), `runtime·clone` (linux) などのアセンブリ関数は、新しいOSスレッドが実際に起動された後に実行されるエントリポイントです。これらの関数は、`setldt` システムコールを呼び出して、新しいスレッドのTLS領域を設定する責任を負っています。

変更前のアセンブリコードでは、`m` 構造体へのポインタが `DX` レジスタに格納されていると仮定し、以下のような手順で `m.id` を取得していました。

1.  `LEAL m_tls(DX), BP`: `DX` が指す `m` 構造体のアドレスに `m_tls` フィールドのオフセットを加算し、その結果（`m.tls` のアドレス）を `BP` レジスタにロードします。
2.  `MOVL 0(BP), DI`: `BP` が指すアドレス（`m.tls` の先頭、つまり `m.tls[0]`）から4バイト（`MOVL` は32ビット移動）の値を `DI` レジスタに移動します。この値が `m.id` でした。

変更後、アセンブリコードは `m.id` を直接参照するように変わりました。

1.  `MOVL m_id(DX), DI`: `DX` が指す `m` 構造体のアドレスに `m_id` フィールドのオフセットを加算し、その結果のアドレスから `m.id` の値を直接 `DI` レジスタにロードします。

この変更により、アセンブリコードは `m.tls[0]` を介さずに、`m` 構造体から直接 `m.id` を取得できるようになり、より効率的で直接的なアクセスが実現されました。`ADDL $7, DI` の部分は、`m.id` の値に7を加算してLDTのエントリ番号を計算していることを示しています。これは、Goランタイムが特定のLDTエントリをTLSのために予約しているためです。

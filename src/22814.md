# [インデックス 22814] ファイルの概要

このコミットは、Goランタイムのガベージコレクション(GC)トレース出力において、初期ヒープサイズとして報告される値の精度を向上させるための変更です。具体的には、GCがトリガーされた時点の`next_gc`値（GCが次に実行されるべきヒープサイズ）を報告するように修正し、実際のGC開始時とGCトレース出力の間の乖離を減らすことを目的としています。

## 元コミット内容

```
runtime: report next_gc for initial heap size in gctrace

Currently, the initial heap size reported in the gctrace line is the
heap_live right before sweep termination. However, we triggered GC
when heap_live reached next_gc, and there may have been significant
allocation between that point and the beginning of sweep
termination. Ideally these would be essentially the same, but
currently there's scheduler delay when readying the GC goroutine as
well as delay from background sweep finalization.

We should fix this delay, but in the mean time, to give the user a
better idea of how much the heap grew during the whole of garbage
collection, report the trigger rather than what the heap size happened
to be after the garbage collector finished rolling out of bed. This
will also be more useful for heap growth plots.

Change-Id: I08476b9fbcfb2de90592405e9c9f434dfb9eb1f8
Reviewed-on: https://go-review.googlesource.com/8512
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goのガベージコレクタは、ヒープサイズが特定の閾値（`next_gc`）に達するとGCサイクルを開始します。しかし、これまでの`gctrace`の出力では、GCサイクルの初期ヒープサイズとして、スイープ終了直前の`heap_live`（現在生きているオブジェクトが占めるヒープサイズ）が報告されていました。

この報告方法には問題がありました。GCがトリガーされてから実際にスイープ終了に至るまでの間に、ミューテータ（ユーザープログラム）がさらにメモリを割り当てる可能性があります。また、GCゴルーチンの準備におけるスケジューラの遅延や、バックグラウンドでのスイープ完了処理の遅延も存在しました。これにより、GCがトリガーされた時点のヒープサイズと、`gctrace`で報告される初期ヒープサイズとの間に乖離が生じていました。

この乖離は、ユーザーがGCによるヒープの成長を正確に把握することを困難にしていました。特に、ヒープ成長のプロットを作成する際に、GCが実際に開始された時点のヒープサイズではなく、GCサイクル終了間際のヒープサイズが報告されるため、データが実態と合わないという問題がありました。このコミットは、この遅延自体を修正するのではなく、一時的な対策として、より実態に近いGCトリガー時のヒープサイズ（`next_gc`）を報告することで、ユーザーにGC中のヒープ成長についてより良い洞察を提供することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクションに関する概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが動的に確保したメモリのうち、もはや到達不可能になった（使われなくなった）領域を自動的に解放する仕組みです。GoのGCは、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。
*   **`gctrace`**: Goプログラムの実行時に`GODEBUG=gctrace=1`環境変数を設定することで出力される、GCの動作に関する詳細なログです。このログは、GCの実行タイミング、ヒープサイズの変化、GCに要した時間などの情報を提供し、メモリ使用量のプロファイリングやGCパフォーマンスのデバッグに役立ちます。
    `gctrace`の出力は通常、以下のような形式です。
    ```
    gc # @#s #%: #+ #+ # ms clock, #+ #/#/# ms cpu, #->#-># MB, # MB goal, # P
    ```
    この中で、`#->#-># MB`の部分がヒープサイズの変化を示しており、最初の`# MB`がGC開始時のヒープサイズ、次の`# MB`がマークフェーズ終了時のヒープサイズ、最後の`# MB`がGC終了時のヒープサイズを表します。このコミットは、この最初の`# MB`の報告値を変更します。
*   **`heap_live`**: Goランタイムが管理するヒープ上で、現在「生きている」（プログラムから到達可能な）オブジェクトが占めるメモリの総量です。これはGCが完了した時点での実際のメモリ使用量に近い値を示します。
*   **`next_gc`**: 次のGCサイクルがトリガーされるべきヒープサイズの閾値です。GoのGCは、`heap_live`がこの`next_gc`に達すると、GCサイクルを開始します。この値は、前回のGCサイクルで生き残ったオブジェクトの量に基づいて動的に調整されます。
*   **スイープ (Sweep)**: GoのGCのフェーズの一つで、マークフェーズで到達不可能と判断されたオブジェクトが占めるメモリ領域を解放し、再利用可能な状態にする処理です。
*   **スイープ終了 (Sweep Termination)**: スイープフェーズが完了し、GCサイクルが実質的に終了する時点です。
*   **ミューテータ (Mutator)**: ガベージコレクタの文脈で、ユーザープログラム（アプリケーションコード）を指します。ミューテータはメモリを割り当て、オブジェクトグラフを変更します。
*   **スケジューラ (Scheduler)**: Goランタイムのスケジューラは、ゴルーチンをOSスレッドにマッピングし、実行を管理します。GCゴルーチンが実行可能になっても、スケジューラの遅延によりすぐに実行されない場合があります。
*   **バックグラウンドスイープ完了 (Background Sweep Finalization)**: スイープ処理の一部がバックグラウンドで非同期的に行われることがあります。これにより、GCがトリガーされてから完全に終了するまでに時間がかかることがあります。

## 技術的詳細

このコミットの技術的な核心は、`gctrace`が出力するGC開始時のヒープサイズを、`memstats.heap_live`（スイープ終了直前の実際のヒープ使用量）から`memstats.next_gc`（GCがトリガーされた目標ヒープサイズ）に変更することです。

従来の挙動では、GCがトリガーされた時点（`heap_live`が`next_gc`に達した時点）と、`gctrace`で報告される初期ヒープサイズ（スイープ終了直前の`heap_live`）との間に時間差がありました。この時間差の間に、ミューテータがさらにメモリを割り当てたり、GCゴルーチンのスケジューリング遅延やバックグラウンドスイープの完了遅延が発生したりすることで、報告される初期ヒープサイズが実際のGCトリガー時よりも大きくなる可能性がありました。

この変更により、`gctrace`の出力は、GCが「なぜ」開始されたのか、つまりヒープがどの程度のサイズに達したときにGCがトリガーされたのかをより正確に反映するようになります。これは、特にヒープの成長パターンを分析する際に非常に重要です。例えば、アプリケーションがメモリを大量に割り当てて`next_gc`に達し、GCがトリガーされたにもかかわらず、GCが実際に開始されるまでの間にさらにメモリを消費した場合、従来の`gctrace`ではその追加の消費量を含んだ値が初期ヒープサイズとして報告されていました。しかし、この変更後は、GCがトリガーされた時点の`next_gc`が報告されるため、ユーザーはGCのトリガー条件と実際のヒープ成長の関連性をより明確に理解できるようになります。

コミットメッセージにもあるように、この変更は根本的な遅延問題を解決するものではありませんが、ユーザーがGCの動作をより正確に理解するための暫定的な改善策として導入されました。ヒープ成長のプロットを作成する際には、GCがトリガーされた時点のヒープサイズがプロットの開始点としてより適切であるため、この変更はデータ分析の観点からも有用です。

## コアとなるコードの解説

変更の中心は、`gc`関数内で`gctrace`の出力のために初期ヒープサイズを格納する変数`heap0`に値を代入する部分です。

変更前は、`heap0 = memstats.heap_live`と直接代入されていました。これは、GCサイクルがスイープ終了に近づいた時点での`heap_live`の値を`heap0`に設定することを意味します。

変更後は、条件分岐が導入されています。
```go
		if mode == gcBackgroundMode {
			// We started GC when heap_live == next_gc,
			// but the mutator may have allocated between
			// then and now. Report heap when GC started.
			heap0 = memstats.next_gc
		} else {
			heap0 = memstats.heap_live
		}
```

*   `if mode == gcBackgroundMode`: この条件は、現在のGCサイクルがバックグラウンドGCモードで実行されているかどうかをチェックします。GoのGCは、主にバックグラウンドで並行して実行されます。このモードの場合、GCは`heap_live`が`next_gc`に達したときにトリガーされます。
    *   このブロック内では、`heap0 = memstats.next_gc`と設定されています。これは、GCがトリガーされた時点の目標ヒープサイズ（`next_gc`）を初期ヒープサイズとして報告することを意味します。コミットメッセージのコメントにもあるように、「`heap_live`が`next_gc`に達したときにGCを開始したが、その間にミューテータが割り当てを行った可能性がある。GCが開始された時点のヒープを報告する」という意図が明確に示されています。
*   `else`: `gcBackgroundMode`ではない場合（例えば、GCが明示的に同期的に呼び出された場合など）は、引き続き`heap0 = memstats.heap_live`が使用されます。これは、バックグラウンドGCのような遅延の問題が少ない、あるいは異なるコンテキストでのGC実行を想定しているためと考えられます。

この変更により、`gctrace`の出力におけるGC開始時のヒープサイズは、ほとんどの一般的なGCサイクル（バックグラウンドGC）において、GCがトリガーされた時点の`next_gc`値が反映されるようになり、より実態に即した情報が提供されるようになりました。

# [インデックス 25655] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/tar` パッケージにおいて、生成されるTARアーカイブの出力が決定論的（deterministic）になるように修正するものです。具体的には、PAX拡張ヘッダーにプロセスID (PID) を含めるのをやめ、代わりに定数 `0` を使用するように変更し、さらにPAXヘッダーのキーを書き出す前にソートすることで、同じ入力からは常に同じTARアーカイブが生成されることを保証します。

## 変更の背景

この変更の主な背景は、TARアーカイブの「決定論的出力（deterministic output）」を保証することにあります。決定論的出力とは、同じ入力データと設定が与えられた場合、常に全く同じバイナリ出力を生成するという特性を指します。これはソフトウェア開発、特にビルドシステムやパッケージ管理において非常に重要な概念です。

Go言語の `archive/tar` パッケージは、TARアーカイブの読み書きを扱うための標準ライブラリです。このパッケージが生成するTARアーカイブが非決定論的であると、以下のような問題が発生します。

1.  **再現性の欠如**: 同じソースコードからビルドしても、生成されるバイナリ（この場合はTARアーカイブ）が毎回異なる可能性があります。これは、ビルドの再現性を保証する上で大きな障害となります。
2.  **キャッシュの非効率性**: ビルドシステムやCI/CDパイプラインでは、変更がない場合に以前のビルド結果をキャッシュして再利用することがよくあります。出力が非決定論的だと、内容が実質的に同じであってもバイナリが異なるため、キャッシュがヒットせず、毎回再ビルドが必要になり、ビルド時間が長くなります。
3.  **セキュリティ監査の困難さ**: ソフトウェアのサプライチェーンセキュリティにおいて、配布されるバイナリが特定のソースコードから正確にビルドされたものであることを検証する「再現可能なビルド（reproducible builds）」の重要性が高まっています。非決定論的な出力は、この検証を不可能にします。
4.  **バージョン管理のノイズ**: TARアーカイブ自体をバージョン管理システムに含める場合、内容が同じでも非決定論的な要素によってファイルが変更されたと認識され、不要な差分が発生します。

このコミットは、具体的に以下の2つの非決定論的要素を排除することを目的としています。

*   **PAXヘッダー内のプロセスID (PID)**: 以前の実装では、PAXヘッダーのファイル名の一部に現在のプロセスのPIDを含めていました。PIDはプログラムが実行されるたびに異なる値を取るため、これにより生成されるTARアーカイブは実行ごとに異なるものとなっていました。
*   **PAXヘッダーキーの順序**: Go言語の `map` は、要素のイテレーション順序が保証されません。そのため、PAXヘッダーに複数の拡張属性が含まれる場合、それらがアーカイブに書き込まれる順序が実行ごとに異なる可能性があり、これも非決定論的な出力の原因となっていました。

これらの問題は、GoのIssue #12358で報告され、このコミットによって解決されました。

## 前提知識の解説

### TARアーカイブ

TAR (Tape Archive) は、複数のファイルを一つのアーカイブファイルにまとめるためのファイル形式です。元々は磁気テープにデータを保存するために設計されましたが、現在ではファイルシステム上のファイルをまとめる目的で広く利用されています。

TARアーカイブは、基本的に一連の「ヘッダーブロック」と「データブロック」で構成されます。各ファイルやディレクトリは、そのメタデータ（ファイル名、パーミッション、所有者、タイムスタンプ、サイズなど）を記述するヘッダーブロックと、実際のファイル内容を格納するデータブロックからなります。

### PAXヘッダー (POSIX.1-2001拡張ヘッダー)

従来のTAR形式には、ファイル名の長さ制限（100文字）や、ユーザー/グループIDの数値制限、拡張属性（extended attributes）のサポート不足など、いくつかの制約がありました。これらの制約を克服するために、POSIX.1-2001標準で「PAX拡張ヘッダー（PAX Extended Headers）」が導入されました。

PAXヘッダーは、通常のTARヘッダーの後に続く特別なヘッダーブロックとして機能します。これには、キーと値のペアの形式で、従来のTARヘッダーでは表現できなかった追加のメタデータ（例: 長いファイル名、高精度なタイムスタンプ、ファイルサイズ、拡張属性など）が格納されます。PAXヘッダー自体もTARアーカイブ内のファイルとして扱われ、通常は `PaxHeaders.<PID>/<original_filename>` のような名前で識別されます。

このコミットの変更点の一つは、この `PaxHeaders.<PID>` の部分の `<PID>` を `0` に固定することです。

### 決定論的ビルド (Deterministic Builds)

決定論的ビルド（または再現可能なビルド、Reproducible Builds）とは、特定のソースコード、ビルド環境、およびビルド手順が与えられた場合、常にビット単位で同一のバイナリ出力を生成できるビルドプロセスのことです。

これは、ソフトウェアの信頼性、セキュリティ、および保守性を向上させる上で非常に重要です。

*   **信頼性**: 開発者やユーザーは、ビルドプロセスが安定しており、予期せぬ変更がないことを信頼できます。
*   **セキュリティ**: 悪意のある改ざんやバックドアがビルドプロセスに挿入されていないことを検証できます。配布されたバイナリが、公開されているソースコードから実際にビルドされたものであることを第三者が確認できるようになります。
*   **デバッグ**: 特定のビルドの問題を再現しやすくなります。
*   **キャッシュ**: ビルド成果物が同一であれば、ビルドシステムは以前の成果物を再利用でき、ビルド時間を大幅に短縮できます。

決定論的ビルドを実現するためには、ビルドプロセスにおけるあらゆる非決定論的要素（例: タイムスタンプ、ファイル順序、プロセスID、環境変数、ランダムな値の生成など）を排除する必要があります。このコミットは、TARアーカイブ生成における非決定論的要素を排除することで、Go言語のビルドシステムや関連ツールがより決定論的になるよう貢献しています。

## 技術的詳細

Go言語の `archive/tar` パッケージは、TARアーカイブの作成と抽出のための機能を提供します。このコミットで変更されたのは、主に `Writer` 型の `writePAXHeader` メソッドです。

### 変更前の非決定論的要素

1.  **PAXヘッダーのファイル名におけるPIDの使用**:
    `writePAXHeader` 関数は、PAXヘッダーを書き込む際に、そのヘッダーファイルの名前を `PaxHeaders.<PID>/<original_filename>` の形式で生成していました。ここで `<PID>` は `os.Getpid()` 関数によって取得される現在のプロセスのIDです。プロセスIDは、プログラムが実行されるたびにオペレーティングシステムによって割り当てられる一意の数値であり、通常は実行ごとに異なります。このため、同じ入力ファイルからTARアーカイブを複数回作成しても、PAXヘッダーのファイル名が異なるため、結果として生成されるTARアーカイブのバイナリは毎回異なっていました。

2.  **PAXヘッダーキーの書き込み順序**:
    PAXヘッダーは、キーと値のペアの集合（Goでは `map[string]string` で表現される `paxHeaders`）として扱われます。Goの `map` は、要素をイテレートする際の順序が保証されません。つまり、同じマップに対して `for k, v := range paxHeaders` のようにループを回しても、キーが取得される順序は実行ごとに異なる可能性があります。PAXヘッダーのキーと値のペアがアーカイブに書き込まれる順序が異なると、これもまた生成されるTARアーカイブのバイナリが非決定論的になる原因となっていました。

### 変更による決定論的出力の実現

このコミットは、上記の2つの非決定論的要素を直接的に排除します。

1.  **PIDの固定値 `0` への置き換え**:
    `os.Getpid()` の呼び出しを削除し、PAXヘッダーのファイル名を生成する際に `PaxHeaders.0` という固定の文字列を使用するように変更しました。これにより、プロセスIDに依存しない一貫したファイル名が保証され、この点での非決定性が解消されます。コミットメッセージにもあるように、仕様ではPIDを含めることが求められる場合もありますが、決定論的出力の要件が優先されました。

2.  **PAXヘッダーキーのソート**:
    PAXヘッダーのキーをアーカイブに書き込む前に、`sort.Strings` を使用してアルファベット順にソートするように変更しました。これにより、`paxHeaders` マップからキーと値のペアが取り出され、アーカイブに書き込まれる順序が常に一定になります。結果として、PAXヘッダーの内容のバイナリ表現が常に同じになり、この点での非決定性も解消されます。

これらの変更により、`archive/tar` パッケージは、同じ入力に対して常にビット単位で同一のTARアーカイブを生成するようになります。

## コアとなるコードの解説

### `src/archive/tar/writer.go` の変更点

1.  **インポートの変更**:
    *   `"os"` パッケージのインポートが削除されました。これは、`os.Getpid()` の使用がなくなったためです。
    *   `"sort"` パッケージが新しくインポートされました。これは、PAXヘッダーのキーをソートするために必要です。

2.  **PAXヘッダーファイル名の変更**:
    変更前:
    ```go
    pid := os.Getpid()
    fullName := path.Join(dir,
        fmt.Sprintf("PaxHeaders.%d", pid), file)
    ```
    変更後:
    ```go
    // The spec asks that we namespace our pseudo files
    // with the current pid.  However, this results in differing outputs
    // for identical inputs.  As such, the constant 0 is now used instead.
    // golang.org/issue/12358
    dir, file := path.Split(hdr.Name)
    fullName := path.Join(dir, "PaxHeaders.0", file)
    ```
    この変更により、PAXヘッダーのファイル名にプロセスID (`pid`) を含める代わりに、常に `"PaxHeaders.0"` という固定の文字列が使用されるようになりました。これにより、TARアーカイブの生成が実行環境のPIDに依存しなくなり、決定論的な出力が保証されます。コメントで `golang.org/issue/12358` が参照されており、この変更の背景にある問題が明確に示されています。

3.  **PAXヘッダーキーのソート**:
    変更前:
    ```go
    for k, v := range paxHeaders {
        fmt.Fprint(&buf, paxHeader(k+"="+v))
    }
    ```
    変更後:
    ```go
    // Keys are sorted before writing to body to allow deterministic output.
    var keys []string
    for k := range paxHeaders {
        keys = append(keys, k)
    }
    sort.Strings(keys)

    for _, k := range keys {
        fmt.Fprint(&buf, paxHeader(k+"="+paxHeaders[k]))
    }
    ```
    この変更では、まず `paxHeaders` マップのすべてのキーを `keys` スライスに抽出し、`sort.Strings(keys)` を使ってアルファベット順にソートしています。その後、ソートされた `keys` スライスを使って `paxHeaders` から値を取り出し、PAXヘッダーのボディに書き込んでいます。これにより、PAXヘッダー内のキーと値のペアが常に同じ順序で書き込まれることが保証され、Goのマップの非決定論的なイテレーション順序による問題が解消されます。

### `src/archive/tar/writer_test.go` の変更点

1.  **インポートの追加**:
    *   `"sort"` パッケージがテストファイルにもインポートされました。これは、新しいテストケースでソートされた順序を検証するために使用されます。

2.  **既存テストの修正**:
    `TestPax`, `TestPaxSymlink`, `TestPaxNonAscii` の各テストにおいて、PAXヘッダーの存在をチェックする部分が `bytes.Contains(buf.Bytes(), []byte("PaxHeaders."))` から `bytes.Contains(buf.Bytes(), []byte("PaxHeaders.0"))` に変更されました。これは、PAXヘッダーのファイル名が `PaxHeaders.0` に固定されたことに対応する修正です。

3.  **新しいテストケース `TestPaxHeadersSorted` の追加**:
    この新しいテスト関数は、PAXヘッダーのキーがソートされて書き込まれることを検証します。
    *   `hdr.Xattrs` に複数の拡張属性（"foo", "bar", "baz", "qux"）を意図的に異なる順序で設定したマップを作成します。
    *   `NewWriter` を使ってTARアーカイブを書き込みます。
    *   生成されたアーカイブのバイト列から、各拡張属性のキーと値のペア（例: "bar=bar"）が出現するインデックスを取得します。
    *   `sort.IntsAreSorted(indices)` を使用して、これらのインデックスが昇順にソートされているか（つまり、PAXヘッダーがアルファベット順に書き込まれているか）を検証します。もしソートされていなければ、テストは失敗します。

これらのテストの追加と修正により、コミットで導入された決定論的出力の変更が正しく機能していることが保証されます。

# [インデックス 26474] ファイルの概要

`src/runtime/trace.go` は、Goランタイムの実行トレーサーに関連するコードが含まれています。Goのトレーサーは、プログラムの実行中に発生する様々なイベント（ガーベージコレクション、goroutineのスケジューリング、システムコールなど）を記録し、その後のプロファイリングやデバッグに利用するためのものです。このファイルは、これらのイベントを記録するための低レベルなメカニズムを提供します。

## コミット

```
runtime: acquire stack lock in traceEvent

traceEvent records system call events after a G has already entered
_Gsyscall, which means the garbage collector could be installing stack
barriers in the G's stack during the traceEvent. If traceEvent
attempts to capture the user stack during this, it may observe a
inconsistent stack barriers and panic. Fix this by acquiring the stack
lock around the stack walk in traceEvent.

Fixes #14101.
```

## 変更の背景

このコミットは、Goランタイムのトレーサーがシステムコールイベントを記録する際に発生する可能性のあるパニック（panic）を修正するために導入されました。

問題の核心は、`traceEvent` 関数が、goroutine (G) が既に `_Gsyscall` 状態（システムコールを実行中）に入った後にシステムコールイベントを記録しようとすることにありました。この `_Gsyscall` 状態の間に、Goのガーベージコレクタ（GC）が、当該goroutineのスタックに「スタックバリア」をインストールしている可能性がありました。

もし `traceEvent` がこのタイミングでユーザーのスタックをキャプチャしようとすると、GCによるスタックバリアの変更と競合し、スタックバリアが不整合な状態にあることを観測してしまう可能性がありました。この不整合な状態が原因で、ランタイムがパニックを引き起こすことがありました。

このコミットは、このような競合状態を解消し、ランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

*   **Goランタイムトレーサー**: Goには、プログラムの実行状況を詳細に記録する組み込みのトレーサーがあります。これは、GCイベント、goroutineの作成・終了・スケジューリング、システムコールなどのイベントを記録し、`go tool trace` コマンドで可視化することで、パフォーマンス分析やデバッグに役立てられます。`traceEvent` 関数は、このトレーサーがイベントを記録する際の内部的なエントリポイントの一つです。
*   **Goroutine (G)**: Goの並行処理の基本単位であり、軽量なスレッドのようなものです。各goroutineは独自のスタックを持っています。
*   **スタックバリア (Stack Barriers)**: Goのガベージコレクタ（GC）は、並行GCアルゴリズムを採用しており、プログラムの実行と並行してGC処理を行います。この際、GCがスタックをスキャンしてポインタを特定し、マークする過程で、goroutineのスタックが成長したり縮小したり、あるいは移動したりすることがあります。スタックバリアは、GCがスタックを安全に操作できるように、スタック上のポインタの整合性を保護するためのメカニズムです。具体的には、GCがスタックをスキャンしている間に、goroutineがスタックを書き換えることを防ぐために一時的に挿入される保護機構と考えることができます。
*   **システムコール (`_Gsyscall` 状態)**: goroutineがオペレーティングシステム（OS）のシステムコール（例: ファイルI/O、ネットワーク通信）を実行している間は、Goランタイムのスケジューラから一時的に離れ、OSカーネル内で実行されます。この状態をGoランタイムでは `_Gsyscall` と呼びます。システムコール中は、goroutineのスタックはOSによって管理される部分があり、Goランタイムが直接制御できない期間が生じます。
*   **スタックウォーク (Stack Walk)**: プログラムの実行中に、現在の関数呼び出しの連鎖（コールスタック）を遡って、どの関数がどの関数を呼び出したかを特定する処理です。デバッグやプロファイリング、そしてこのコミットで問題となっているスタックトレースのキャプチャなどで利用されます。`gcallers` 関数は、特定のgoroutineのスタックウォークを実行します。
*   **スタックロック (Stack Lock)**: スタックの整合性を保護するための排他制御メカニズムです。特に、GCがスタックバリアを操作しているようなクリティカルな期間に、他のランタイム処理（例えばスタックウォーク）がスタックにアクセスするのを一時的にブロックするために使用されます。これにより、複数の処理が同時にスタックの構造や内容を変更しようとすることによる競合状態や不整合を防ぎます。

## 技術的詳細

このコミットが解決しようとしている問題は、Goランタイムにおける並行処理とメモリ管理の複雑な相互作用に起因します。

1.  **競合状態の発生**:
    *   `traceEvent` 関数は、システムコールイベントを記録する際に、そのイベントを発生させたgoroutine (`gp`) のコールスタックをキャプチャしようとします。
    *   この `traceEvent` の呼び出しは、`gp` が既に `_Gsyscall` 状態に入った後に行われます。
    *   `_Gsyscall` 状態では、GCが `gp` のスタックに対してスタックバリアをインストールする可能性があります。スタックバリアのインストールは、GCがスタックをスキャンする準備として行われる重要なステップです。
    *   もし `traceEvent` が `gcallers` を呼び出してスタックウォークを実行する際に、GCが同時にスタックバリアを操作していると、`gcallers` はスタックバリアの不整合な状態を観測してしまう可能性があります。例えば、バリアが部分的にインストールされた状態や、一時的に無効化された状態などです。
    *   このような不整合なスタックバリアの状態は、スタックウォークのロジックを混乱させ、最終的にランタイムのパニックを引き起こす原因となります。

2.  **解決策**:
    *   この問題に対処するため、コミットでは `traceEvent` 関数内で `gcallers` を呼び出す際に、`gcTryLockStackBarriers` と `gcUnlockStackBarriers` という関数を使用してスタックロックを取得・解放するように変更されました。
    *   `gcTryLockStackBarriers(gp)` は、指定されたgoroutine `gp` のスタックバリアに対するロックを試みます。このロックが成功すると、GCは `gp` のスタックバリアに対する操作を一時的に停止します。これにより、`traceEvent` がスタックウォークを実行している間、GCがスタックバリアを変更することによる競合が防止されます。
    *   ロックが取得された状態で `gcallers(gp, skip, buf.stk[:])` が呼び出され、安全にスタックトレースがキャプチャされます。
    *   スタックトレースのキャプチャが完了した後、`gcUnlockStackBarriers(gp)` が呼び出され、スタックバリアのロックが解放されます。これにより、GCは `gp` のスタックバリアに対する操作を再開できます。
    *   この排他制御により、`traceEvent` がスタックウォークを行う際に、常に整合性の取れたスタックバリアの状態を観測できるようになり、パニックが回避されます。

この変更は、Goランタイムのトレーシング機能とGCの間の繊細な同期要件を浮き彫りにし、並行処理環境におけるデータ構造の整合性維持の重要性を示しています。

## コアとなるコードの解説

変更されたコードブロックは、`traceEvent` 関数が特定のgoroutine (`gp`) のスタックトレースをキャプチャしようとする部分です。

*   **変更前**:
    ```go
    nstk = gcallers(gp, skip, buf.stk[:])
    ```
    以前は、`gcallers` 関数が直接呼び出され、`gp` のスタックトレースが取得されていました。この直接呼び出しが、GCによるスタックバリアの操作と競合する可能性がありました。

*   **変更後**:
    ```go
    // This may happen when tracing a system call,
    // so we must lock the stack.
    if gcTryLockStackBarriers(gp) {
        nstk = gcallers(gp, skip, buf.stk[:])
        gcUnlockStackBarriers(gp)
    }
    ```
    1.  `// This may happen when tracing a system call, // so we must lock the stack.`
        このコメントは、システムコールをトレースしている際にこのコードパスが実行される可能性があり、そのためにスタックをロックする必要があることを明確に示しています。
    2.  `if gcTryLockStackBarriers(gp)`:
        `gcTryLockStackBarriers` 関数は、`gp` のスタックバリアに対するロックを試みます。この関数は、ロックの取得に成功した場合に `true` を返します。これにより、GCが `gp` のスタックバリアを操作するのを一時的に停止させることができます。
    3.  `nstk = gcallers(gp, skip, buf.stk[:])`:
        ロックが正常に取得された場合のみ、`gcallers` 関数が呼び出され、`gp` のスタックトレースが安全にキャプチャされます。この間、GCはスタックバリアを変更しないことが保証されます。
    4.  `gcUnlockStackBarriers(gp)`:
        スタックトレースのキャプチャが完了した後、`gcUnlockStackBarriers` 関数が呼び出され、`gp` のスタックバリアに対するロックが解放されます。これにより、GCはスタックバリアの操作を再開できるようになります。

この変更により、`traceEvent` がシステムコール中のgoroutineのスタックを安全にウォークできるようになり、GCとの競合によるパニックが防止されます。これは、Goランタイムの堅牢性を高めるための重要な修正です。

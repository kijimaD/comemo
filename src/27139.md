# [インデックス 27139] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける`prove`パスの機能を拡張し、より一般的なブール条件の推論を可能にするものです。具体的には、値間の関係性を追跡するための内部データ構造が大幅に改善され、境界チェックだけでなく、より複雑なブール論理式に対しても最適化が適用できるようになりました。これにより、生成されるコードの効率が向上し、特に冗長な条件分岐や境界チェックの削除に貢献します。

## 変更の背景

GoコンパイラのSSAバックエンドには、`prove`と呼ばれる最適化パスが存在します。このパスの主な目的は、プログラムの実行フローに基づいて、ある条件が常に真または常に偽であることを推論し、冗長な条件分岐やチェックを削除することです。以前の`prove`パスは、主に配列の境界チェック（`IsInBounds`や`IsSliceInBounds`）のような数値の範囲に関する推論に特化していました。

しかし、プログラムには数値の範囲チェック以外にも多くのブール条件が存在します。例えば、`if a && b`のような論理演算や、`if x == y`のような比較演算などです。これらのブール条件が、プログラムの特定の実行パスにおいて常に真または偽であることが判明した場合、その条件分岐自体を削除したり、条件式を簡略化したりすることで、より効率的なコードを生成できます。

このコミットの背景には、`prove`パスの適用範囲を数値の範囲チェックだけでなく、より広範なブール条件に一般化することで、コンパイラの最適化能力を向上させるという目的があります。特に、複雑なブール式や、複数の条件が連鎖するようなケースにおいて、より多くの最適化機会を見つけることが期待されます。

また、コンパイラの最適化は、コードサイズや実行速度に直接影響します。この変更によって、特に`pkg/tools/linux_amd64`のようなツール群でコードサイズが削減されたことは、最適化が成功した証拠と言えます。

## 前提知識の解説

### GoコンパイラとSSA

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要な最適化ステージの一つがSSA (Static Single Assignment) フォームです。SSAフォームでは、各変数が一度だけ代入されるようにプログラムが変換されます。これにより、データフロー解析や最適化が容易になります。

SSAバックエンドでは、プログラムは「値 (Value)」と「ブロック (Block)」のグラフとして表現されます。
*   **Value**: 演算の結果や定数など、プログラム中のあらゆる値を表します。
*   **Block**: 連続した命令のシーケンスであり、条件分岐やループの開始・終了点などで区切られます。

### `prove`パス

`prove`パスは、SSAフォームのグラフ上でデータフロー解析を行い、特定のブロックに到達した時点で、ある条件が常に真または常に偽であるかを推論する最適化パスです。例えば、`if i < len(a)`という条件分岐があった後、その`if`ブロックの内部では`i < len(a)`が常に真であることが保証されます。`prove`パスはこのような情報を利用して、後続の冗長な境界チェックを削除します。

### ドミナータツリー (Dominator Tree)

`prove`パスは、ドミナータツリーというグラフ構造を利用して解析を行います。ドミナータツリーは、プログラムの制御フローグラフにおいて、あるブロックに到達する全てのパスが必ず通過するブロック（ドミネータ）の関係を表します。このツリー構造を利用することで、あるブロックで確立された条件が、そのドミネートされる子孫ブロックでも有効であるかを効率的に判断できます。

### 書き換えルール (Rewrite Rules)

Goコンパイラには、SSAフォームの値をより効率的な形に変換するための「書き換えルール」が多数定義されています。これらは`generic.rules`のようなファイルに記述されており、特定のパターンにマッチするSSA値を別のSSA値に置き換えることで最適化を行います。例えば、`x + 0`を`x`に置き換えるような単純なものから、より複雑な代数的な簡約まで多岐にわたります。

### `IsInBounds`と`IsSliceInBounds`

これらはGoコンパイラのSSA内部で使われる操作で、配列やスライスのインデックスが有効な範囲内にあるかをチェックするものです。Go言語は実行時パニックを防ぐために、これらの境界チェックを自動的に挿入しますが、`prove`パスのような最適化によって冗長なチェックは削除されます。

## 技術的詳細

このコミットの核となる技術的変更は、`prove`パスが値間の関係性を追跡する方法の根本的な見直しです。

1.  **`factsTable`の導入**:
    *   以前は`mask`という`map[control]rangeMask`型のデータ構造で値間の関係性を追跡していましたが、これを`factsTable`という新しい構造体に置き換えました。
    *   `factsTable`は、`map[pair]relation`型の`facts`フィールドを持ち、`pair`（2つの値とそれらのドメイン）と`relation`（値間の可能な関係性、例: `lt` (less than), `eq` (equal), `gt` (greater than)）をマッピングします。
    *   この`factsTable`は、DFS (Depth First Search) を用いたドミナータツリーの走査中に、条件分岐を降りる際に現在の状態を`checkpoint`し、分岐から戻る際に`restore`するメカニズムを備えています。これにより、特定の実行パスでのみ有効な条件情報を正確に管理できます。

2.  **`domain`と`relation`の一般化**:
    *   以前の`typeMask`（`signed`, `unsigned`, `pointer`）は`domain`に、`rangeMask`（`lt`, `eq`, `gt`）は`relation`にそれぞれ名称変更されました。
    *   特に重要なのは、`domain`に`boolean`が追加されたことです。これにより、`prove`パスは数値の比較だけでなく、ブール値そのものの真偽に関する推論も行えるようになりました。
    *   `relation`は、2つの値`v`と`w`の間に存在する可能性のある関係性の集合を表します。例えば、`v < w`という条件が真であるパスでは、`relation`は`lt`のみに制限されます。

3.  **`simplifyBlock`の強化**:
    *   `simplifyBlock`関数は、現在のブロックの条件分岐（`BlockIf`）が、`factsTable`に格納されている情報に基づいて常に真または常に偽であるかを判断します。
    *   もし条件が常に真または偽であることが証明された場合、その条件分岐は削除され、常に通るべきパスに直接ジャンプするように変更されます。
    *   ブール値の推論が強化されたことで、`if a || (b && c)`のような複雑なブール式も、特定のコンテキストで簡略化される可能性が高まります。

4.  **書き換えルールの追加**:
    *   `src/cmd/compile/internal/ssa/gen/generic.rules`と`src/cmd/compile/internal/ssa/rewritegeneric.go`に、`IsInBounds`や`IsSliceInBounds`に関する新しい書き換えルールが追加されました。
    *   例えば、`IsInBounds x x`は常に偽（インデックスが配列の長さと同じ場合、それは範囲外）であるため、`ConstBool [0]`（false）に書き換えられます。
    *   `IsSliceInBounds x x`は常に真（`a[x:x]`は常に有効な空スライス）であるため、`ConstBool [1]`（true）に書き換えられます。
    *   `IsSliceInBounds (Const32 [0]) _`や`IsSliceInBounds (Const64 [0]) _`も常に真（スライスの開始インデックスが0の場合、常に有効）であるため、`ConstBool [1]`に書き換えられます。
    *   これらのルールは、`prove`パスが実行される前に、より単純なケースで最適化を適用することを可能にします。

5.  **`isNonNegative`ヘルパー関数の追加**:
    *   `simplifyBlock`内で、値が非負であることが既知であるかを判断するための`isNonNegative`関数が追加されました。これは、`IsInBounds`や`IsSliceInBounds`の最適化において、インデックスが負でないことを利用する際に役立ちます。

これらの変更により、`prove`パスはより多くの種類の条件を推論できるようになり、コンパイラが生成するコードの品質が全体的に向上しました。

### `src/cmd/compile/internal/ssa/prove.go`における`factsTable`

```go
type relation uint
const (
	lt relation = 1 << iota
	eq
	gt
)

type domain uint
const (
	signed domain = 1 << iota
	unsigned
	pointer
	boolean // 新しく追加されたドメイン
)

type pair struct {
	v, w *Value // a pair of values, ordered by ID.
	d domain
}

type fact struct {
	p pair
	r relation
}

type factsTable struct {
	facts map[pair]relation // current known set of relation
	stack []fact            // previous sets of relations
}

// newFactsTableは新しいfactsTableを初期化します。
func newFactsTable() *factsTable {
	ft := &factsTable{}
	ft.facts = make(map[pair]relation)
	ft.stack = make([]fact, 4)
	return ft
}

// getはvとw間の既知の可能な関係性を返します。
func (ft *factsTable) get(v, w *Value, d domain) relation {
	// ... (vとwのIDに基づいて順序を正規化し、factsマップから関係性を取得するロジック)
}

// updateはvとw間の関係性をrに制限して更新します。
func (ft *factsTable) update(v, w *Value, d domain, r relation) {
	// ... (vとwのIDに基づいて順序を正規化し、古い関係性をスタックに保存してから新しい関係性を設定するロジック)
}

// checkpointは既知の関係性の現在の状態を保存します。
// 分岐を降りる際に呼び出されます。
func (ft *factsTable) checkpoint() {
	ft.stack = append(ft.stack, checkpointFact)
}

// restoreは以前のチェックポイントの直前の状態に関係性を復元します。
// 分岐から戻る際に呼び出されます。
func (ft *factsTable) restore() {
	for {
		old := ft.stack[len(ft.stack)-1]
		ft.stack = ft.stack[:len(ft.stack)-1]
		if old == checkpointFact {
			break
		}
		if old.r == lt|eq|gt { // 全ての関係性が可能だった場合、エントリを削除
			delete(ft.facts, old.p)
		} else { // 特定の関係性が設定されていた場合、それを復元
			ft.facts[old.p] = old.r
		}
	}
}
```
この`factsTable`は、`prove`パスがドミナータツリーをDFSで走査する際に、各ブロックで確立された条件（ファクト）を効率的に管理するための中心的なデータ構造です。`checkpoint`と`restore`メカニズムにより、条件分岐の各パスで独立したファクトの集合を追跡し、パスが終了したときに元の状態に戻すことができます。これにより、特定のパスでのみ有効な推論を正確に行うことが可能になります。`boolean`ドメインの追加は、この`factsTable`が数値の範囲だけでなく、一般的なブール条件も扱えるようになったことを示しています。

### `src/cmd/compile/internal/ssa/prove.go`における`simplifyBlock`

```go
// simplifyBlockはft内の制限に基づいてブロックを簡略化します。
// 常に取られるべき分岐を返します。
func simplifyBlock(ft *factsTable, b *Block) branch {
	if b.Kind != BlockIf {
		return unknown
	}

	// まず、条件自体が冗長であるかをチェックします。
	// 例えば、if true { ... } のようなケース。
	m := ft.get(nil, b.Control, boolean) // b.Controlがブール値として常に真/偽かをチェック
	if m == lt|gt { // 常に真 (lt|gtはbooleanドメインではtrueを意味する)
		if b.Func.pass.debug > 0 {
			b.Func.Config.Warnl(int(b.Line), "Proved boolean %s", b.Control.Op)
		}
		return positive // positive branch (true)が常に取られる
	}
	if m == eq { // 常に偽 (eqはbooleanドメインではfalseを意味する)
		if b.Func.pass.debug > 0 {
			b.Func.Config.Warnl(int(b.Line), "Disproved boolean %s", b.Control.Op)
		}
		return negative // negative branch (false)が常に取られる
	}

	// 次に、比較演算子をチェックします。
	c := b.Control
	tr, has := domainRelationTable[c.Op] // 比較演算子に対応するドメインと関係性を取得
	if !has {
		return unknown
	}

	a0, a1 := c.Args[0], c.Args[1]
	for d := domain(1); d <= tr.d; d <<= 1 { // 関連する全てのドメインをイテレート
		if d&tr.d == 0 {
			continue
		}

		// tr.rはpositive branchが取られる場合に有効な関係性を表します。
		// mは以前の関係性から可能なケースを表します。
		// もしmがtr.rに含まれるなら、positive branchが常に取られます。
		m := ft.get(a0, a1, d)
		if m != 0 && tr.r&m == m {
			if b.Func.pass.debug > 0 {
				b.Func.Config.Warnl(int(b.Line), "Proved %s", c.Op)
			}
			return positive
		}
		// もしmがtr.rの補集合に含まれるなら、negative branchが常に取られます。
		if m != 0 && ((lt|eq|gt)^tr.r)&m == m {
			if b.Func.pass.debug > 0 {
				b.Func.Config.Warnl(int(b.Line), "Disproved %s", c.Op)
			}
			return negative
		}
	}

	// ... (IsInBounds/IsSliceInBoundsに関するHACKロジック)

	return unknown
}
```
`simplifyBlock`関数は、`factsTable`から得られる情報に基づいて、現在の`BlockIf`が常に特定の分岐を取るかどうかを判断します。特に、`ft.get(nil, b.Control, boolean)`という呼び出しは、`b.Control`（条件式自体）がブール値として常に真または偽であるかを直接推論しようとします。これは、`if true { ... }`や`if false { ... }`のような自明なケースを削除するために非常に強力です。さらに、`domainRelationTable`と`ft.get(a0, a1, d)`を組み合わせて、`a0 < a1`のような比較演算子についても、`factsTable`に格納された`a0`と`a1`の関係性から、その条件が常に真または偽であるかを推論します。

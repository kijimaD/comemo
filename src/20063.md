# [インデックス 20063] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるメモリ管理の最適化に関するものです。具体的には、フリーリスト（解放されたオブジェクトのリスト）にあるオブジェクトを、GC中に「割り当て済み」としてマークし続けるように変更することで、GCの効率を向上させています。これは、以前のGC書き換え後に失われた最適化を復元するものです。

## 元コミット内容

このコミットは、Goランタイムのガベージコレクタ（GC）の動作を変更し、フリーリスト（解放されたがまだ再利用されていないメモリブロックのリスト）にあるオブジェクトを、GCサイクル中も「割り当て済み」としてマークし続けるようにします。これにより、`malloc`（メモリ割り当て）と`free`（メモリ解放）の際にGCビットを変更する必要がなくなります。その代わり、GC中にフリーリスト内のオブジェクトをマークする必要がありますが、GC時のフリーリストは通常小さいため、全体としてパフォーマンスの向上が期待されます。

ベンチマーク結果は以下の通りです。
- `BenchmarkMalloc8`: 21.9 ns/op -> 20.4 ns/op (-6.85%改善)
- `BenchmarkMalloc16`: 31.1 ns/op -> 29.6 ns/op (-4.82%改善)

この変更は、以前のGC書き換えによって失われた`https://golang.org/cl/41040043`の最適化を復元するものです。

## 変更の背景

Goのガベージコレクタは、メモリの割り当てと解放を効率的に管理するために、様々な最適化を行っています。このコミットの背景には、以下の点が挙げられます。

1.  **GCの書き換え**: Goのランタイムは、GCの性能を向上させるために大規模な書き換えが行われました。この書き換えの過程で、以前のGC実装で存在した一部の最適化が失われた可能性があります。
2.  **フリーリストの管理**: メモリが解放されると、すぐにOSに返されるのではなく、将来の割り当てのために「フリーリスト」と呼ばれるリストに保持されることがあります。これにより、メモリ割り当てのオーバーヘッドを削減できます。
3.  **GCとフリーリストの相互作用**: GCが実行される際、GCは到達可能なオブジェクトをマークし、マークされていないオブジェクトを解放します。フリーリストにあるオブジェクトは、論理的には解放されていますが、物理的にはまだランタイムによって保持されています。GCがこれらのオブジェクトをどのように扱うかは、GCの効率に影響を与えます。
4.  **パフォーマンスのボトルネック**: `malloc`や`free`のような基本的なメモリ操作の性能は、Goアプリケーション全体の性能に大きな影響を与えます。これらの操作におけるオーバーヘッドを削減することは、常に重要な目標です。

このコミットは、GC書き換え後に失われた、フリーリスト上のオブジェクトのGCマークに関する最適化を復元することで、`malloc`の性能を改善し、全体的なランタイムの効率を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの基本的な概念を理解しておく必要があります。

### 1. Goのメモリ管理の基本

Goランタイムは、独自のメモリマネージャを持っています。これは、OSから大きなメモリブロック（アリーナ）を確保し、それを小さなチャンクに分割してアプリケーションに提供します。

*   **アリーナ (Arena)**: GoランタイムがOSから取得する大きなメモリ領域。
*   **スパン (MSpan)**: アリーナをさらに小さな固定サイズのページ（通常8KB）の連続したブロックに分割したもの。各スパンは、特定のサイズのオブジェクトを格納するために使用されます。
*   **オブジェクト (Object)**: Goプログラムで割り当てられるデータ構造。

### 2. ガベージコレクション (GC)

Goはトレース型ガベージコレクタを使用しています。これは、プログラムがアクセス可能な（到達可能な）オブジェクトを特定し、それ以外の（到達不可能な）オブジェクトを「ガベージ」として回収する仕組みです。

*   **マーク＆スイープ (Mark and Sweep)**: GoのGCの基本的なアルゴリズム。
    *   **マークフェーズ (Mark Phase)**: GCルート（グローバル変数、スタック上の変数など）から開始し、到達可能なすべてのオブジェクトをマークします。
    *   **スイープフェーズ (Sweep Phase)**: マークされていないオブジェクト（ガベージ）を特定し、それらが占めていたメモリを解放し、フリーリストに戻します。

### 3. GCビットマップ (GC Bitmap)

Goランタイムは、メモリ上の各ワードがポインタであるか、またはポインタを含まないかを示すためにGCビットマップを使用します。これにより、GCはオブジェクトの内部を効率的にスキャンし、ポインタをたどって到達可能なオブジェクトをマークできます。

*   **`bitBoundary`**: オブジェクトの開始位置を示すビット。
*   **`bitMarked`**: オブジェクトがGCによってマークされたことを示すビット。
*   **`bitAllocated` (変更前)**: オブジェクトが割り当て済みであることを示すビット。このコミットで`bitAllocated`の概念が`bitBoundary`と`bitMarked`に統合されるような変更が見られます。
*   **`bitMiddle` (変更前)**: オブジェクトの中間部分を示すビット。このコミットで削除されます。
*   **`gcBits`**: GCビットマップにおける各ワードあたりのビット数。

### 4. フリーリスト (Free List)

メモリが解放されると、そのメモリはすぐにOSに返されるのではなく、Goランタイムの内部的なフリーリストに追加されます。これにより、同じサイズのオブジェクトが再度割り当てられる際に、OSへのシステムコールを回避し、高速にメモリを提供できます。

*   **`MLink`**: フリーリスト内のオブジェクトをリンクするための構造体。

### 5. `gomallocgc`

Goランタイムにおけるメモリ割り当ての主要な関数の一つ。新しいオブジェクトを割り当て、GCビットマップを更新します。

### 6. `MSpan_Sweep`

GCのスイープフェーズで、特定の`MSpan`（メモリブロック）を走査し、マークされていないオブジェクトをフリーリストに戻す処理を行います。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ管理におけるGCビットマップの扱いと、フリーリスト上のオブジェクトのライフサイクルに関する変更です。

### 変更のポイント

1.  **GCビットマップの簡素化**:
    *   変更前は、`bitMiddle`, `bitBoundary`, `bitAllocated`, `bitMarked`という4種類のビットが定義されていました。
    *   変更後は、`bitMiddle`と`bitAllocated`が削除され、`bitBoundary`と`bitMarked`の2種類に簡素化されています。
    *   これにより、メモリ割り当て時のGCビットの操作が簡素化され、`malloc`のオーバーヘッドが削減されます。

2.  **フリーリスト上のオブジェクトの扱い**:
    *   以前は、オブジェクトがフリーリストに置かれると、そのGCビットは「解放済み」の状態にリセットされる可能性がありました。
    *   このコミットでは、フリーリストにあるオブジェクトも「割り当て済み」（または`bitMarked`が設定された状態）としてマークし続けるように変更されます。
    *   これにより、`malloc`時にGCビットを変更する必要がなくなります。オブジェクトがフリーリストから再利用される際、そのGCビットは既に適切な状態にあるため、追加の操作が不要になります。

3.  **GC時のフリーリストのマーク**:
    *   フリーリスト上のオブジェクトを「割り当て済み」としてマークし続けるという新しいアプローチの「デメリット」として、GC中にこれらのオブジェクトを明示的にマークする必要が生じます。
    *   しかし、コミットメッセージにあるように、GC時のフリーリストは通常小さいため、この追加のマーク処理によるオーバーヘッドは、`malloc`時のビット操作削減によるメリットを上回ると考えられます。

4.  **`heapdump.c`の変更**:
    *   `dumpobjs`関数（ヒープダンプ時にオブジェクトを走査する関数）において、フリーリスト上のオブジェクトを識別するための新しいロジックが追加されています。
    *   `free`という一時的なビットベクトルが導入され、フリーリスト上のオブジェクトを一時的にマークし、ヒープダンプ時にそれらをスキップするようにしています。これは、ヒープダンプの正確性を保ちつつ、新しいGCビットマップのセマンティクスに対応するための変更です。

5.  **`malloc.go`の変更**:
    *   `gomallocgc`関数において、GCビットマップの操作ロジックが大幅に変更されています。
    *   `bitAllocated`の概念が削除され、オブジェクトの境界を示す`bitBoundary`と、GCマークを示す`bitMarked`が主要なビットとして扱われます。
    *   特に、`flags&flagNoScan != 0`の場合（スキャン不要なオブジェクトの場合）や、ポインタを含むオブジェクトの場合のビット設定ロジックが簡素化されています。
    *   ポインタマスクのコピーロジックも、新しいビットマップのセマンティクスに合わせて調整されています。

6.  **`mgc0.c`の変更**:
    *   `scanblock`関数（GCがメモリブロックをスキャンする関数）において、GCビットのチェックロジックが変更されています。
    *   `bitMiddle`のチェックが`bitBoundary`のチェックに置き換えられ、オブジェクトの境界をより正確に識別するようになっています。
    *   `MSpan_Sweep`関数（スイープフェーズでスパンを処理する関数）において、フリーリスト上のオブジェクトを`bitMarked`としてマークする新しいループが追加されています。これは、このコミットの主要な変更点の一つであり、GC中にフリーリスト上のオブジェクトが誤って回収されないようにするためのものです。
    *   また、`bitAllocated`のチェックが`bitMarked`のチェックに置き換えられ、オブジェクトがマークされていない場合にのみ回収対象とするロジックに変更されています。

7.  **`mgc0.h`の変更**:
    *   GCビットの定義が更新され、`bitMiddle`と`bitAllocated`が削除され、`bitBoundary`と`bitMarked`のみが残されています。
    *   `bitMask`の定義もこれに合わせて変更されています。

### パフォーマンスへの影響

この変更は、`malloc`操作の性能向上を目的としています。ベンチマーク結果が示すように、`BenchmarkMalloc8`と`BenchmarkMalloc16`でそれぞれ約6.85%と4.82%の改善が見られます。これは、メモリ割り当て時にGCビットを頻繁に変更する必要がなくなったことによるものです。GC時のフリーリストのマークという追加のオーバーヘッドはありますが、そのコストは`malloc`の改善によって相殺され、全体としてネットゲイン（純利益）が得られるという設計思想に基づいています。

3.  **`src/pkg/runtime/mgc0.c`**:
    *   `scanblock`関数内のGCビットチェックロジックが変更され、`bitMiddle`の代わりに`bitBoundary`を使用するようになりました。

4.  **`src/pkg/runtime/mgc0.h`**:
    *   GCビットの定義が更新され、`bitMiddle`と`bitAllocated`が削除されました。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.go` の変更点

```go
// 変更前
// const (
// 	bitsDead           = 0
// 	bitsPointer        = 2
// 
// 	bitMiddle    = 0
// 	bitBoundary  = 1
// 	bitAllocated = 2
// 	bitMarked    = 3
// 	bitMask      = bitMiddle | bitBoundary | bitAllocated | bitMarked
// )

// 変更後
const (
	bitsDead           = 0
	bitsPointer        = 2

	bitBoundary = 1
	bitMarked   = 2
	bitMask     = bitBoundary | bitMarked
)
```
この変更は、GCビットマップのセマンティクスを根本的に変えています。`bitMiddle`と`bitAllocated`が削除され、`bitBoundary`と`bitMarked`のみが残りました。これは、オブジェクトが割り当てられた際に`bitAllocated`を設定するのではなく、`bitBoundary`とポインタ情報のみでオブジェクトの開始とスキャン情報を表現し、フリーリスト上のオブジェクトも`bitMarked`として扱うという新しいアプローチを反映しています。

`gomallocgc`関数内のGCビット設定ロジックもこれに合わせて変更されています。特に、`flags&flagNoScan != 0`の場合（スキャン不要なオブジェクト）や、単一ワードのポインタオブジェクトの場合のビット設定が簡素化されています。

### `src/pkg/runtime/mgc0.c` の `runtime·MSpan_Sweep` 関数内の変更点

```c
// 変更前: フリーリストのオブジェクトをマークするロジックはここにはない

// 変更後:
	// Mark any free objects in this span so we don't collect them.
	for(link = s->freelist; link != nil; link = link->next) {
		off = (uintptr*)link - (uintptr*)arena_start;
		bitp = (uintptr*)arena_start - off/wordsPerBitmapWord - 1;
		shift = (off % wordsPerBitmapWord) * gcBits;
		*bitp |= bitMarked<<shift;
	}
```
このコードブロックは、このコミットの最も重要な変更点の一つです。`MSpan_Sweep`関数はGCのスイープフェーズで呼び出され、メモリを回収する役割を担います。この変更により、スイープが開始される前に、現在のスパンのフリーリストに存在するすべてのオブジェクトが`bitMarked`としてマークされます。

**なぜこれが必要なのか？**
新しいアプローチでは、フリーリスト上のオブジェクトも「割り当て済み」として扱われます。GCはマークされていないオブジェクトを回収するため、もしフリーリスト上のオブジェクトがマークされていなければ、それらは誤って回収されてしまう可能性があります。このループは、フリーリスト上のオブジェクトがGCによって「生きている」と見なされ、回収されないようにするために、明示的に`bitMarked`を設定しています。これにより、`malloc`時にGCビットを変更する手間を省くことができます。

### `src/pkg/runtime/mgc0.c` の `scanblock` 関数内の変更点

```c
// 変更前:
// 			if(i != 0 && (bits&bitMask) != bitMiddle)
// 				break; // reached beginning of the next object

// 変更後:
			if(i != 0 && (bits&bitBoundary) != 0)
				break; // reached beginning of the next object
```
この変更は、オブジェクトの境界を識別するためのロジックを更新しています。以前は`bitMiddle`ビットを使用してオブジェクトの中間部分を識別していましたが、新しいGCビットマップでは`bitMiddle`が削除されたため、代わりに`bitBoundary`ビットを使用してオブジェクトの開始位置を検出するようになりました。これにより、`scanblock`関数がメモリブロックを正確に走査し、オブジェクトの境界を正しく認識できるようになります。

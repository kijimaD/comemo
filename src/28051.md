# [インデックス 28051] ファイルの概要

このコミットは、Goコンパイラがパッケージのエクスポートデータを生成する際のフォーマットを、従来のテキスト形式からよりコンパクトなバイナリ形式へデフォルトで切り替えるものです。これにより、エクスポートデータのサイズが大幅に削減され、コンパイル時の読み書き速度が向上します。

## 変更の背景

このコミットの主な背景は、Goコンパイラのパフォーマンスと効率の向上です。Goコンパイラは、パッケージ間で型情報や関数シグネチャなどのメタデータを共有するために「エクスポートデータ」を生成します。従来のGoコンパイラ（gc）では、このエクスポートデータは人間が読めるテキスト形式で保存されていました。

テキスト形式のエクスポートデータはデバッグや理解には役立つものの、いくつかの欠点がありました。
1.  **サイズが大きい:** テキスト形式は冗長になりがちで、特に大規模なプロジェクトではコンパイル済みパッケージのサイズを不必要に増大させていました。
2.  **パースに時間がかかる:** コンパイラがこのテキストデータを読み込み、内部のデータ構造に変換するプロセスは、CPU時間とメモリを消費し、コンパイル速度のボトルネックとなる可能性がありました。

これらの問題を解決するため、よりコンパクトで効率的なバイナリ形式のエクスポートデータへの移行が計画されました。このコミットは、そのバイナリ形式をデフォルトで有効にすることで、コンパイル時間の短縮と生成されるバイナリの効率化を目指しています。コミットメッセージには、標準ライブラリのパッケージで平均してエクスポートデータサイズが約65%削減され、書き込み時間が62%以上、読み込み時間が37%以上削減されたと明記されており、その効果の大きさが伺えます。

## 前提知識の解説

このコミットを深く理解するためには、以下の概念を把握しておく必要があります。

*   **Goコンパイラ (gc):** Go言語の公式コンパイラであり、ソースコードを機械語に変換する役割を担います。Goのビルドプロセスの中核です。
*   **パッケージ (Package):** Go言語におけるコードの再利用と構造化の単位です。各パッケージは、他のパッケージから利用可能なエクスポートされた（大文字で始まる）識別子を持ちます。
*   **エクスポートデータ (Export Data):** Goコンパイラが、あるパッケージのコンパイル時に、そのパッケージが外部に公開している型、関数、変数などの情報を記述したメタデータです。このデータは、そのパッケージをインポートする他のパッケージが、型チェックやコード生成を行う際に必要となります。コンパイル済みパッケージファイル（通常は `.a` 拡張子を持つアーカイブファイル）内に埋め込まれています。
*   **テキスト形式のエクスポートデータ:** 従来のGoコンパイラで用いられていたエクスポートデータの形式です。人間が読める形式で、`$$` で始まるセクションに記述されていました。Goの構文に似た形式で型情報などが表現されていましたが、冗長性がありました。
*   **バイナリ形式のエクスポートデータ:** このコミットで導入された新しいエクスポートデータの形式です。機械が効率的に読み書きできるように最適化された形式で、人間が直接読むことは困難です。`$$B` で始まるセクションに記述されます。
*   **`go tool compile`:** Goコンパイラを直接呼び出すコマンドです。通常は `go build` や `go install` コマンドの内部で利用されます。
*   **`go build`:** Goのソースファイルをコンパイルし、実行可能ファイルやパッケージアーカイブを生成するコマンドです。
*   **`gcflags`:** `go build` や `go test` などのコマンドに渡すことができるフラグで、Goコンパイラ (`gc`) に追加のオプションを渡すために使用されます。例えば、`-gcflags="-newexport=0"` のように使われます。
*   **`builtin.go`:** Goの標準ライブラリの一部であり、Go言語の組み込み型（`int`, `string` など）や組み込み関数（`len`, `cap`, `panic` など）の定義が含まれています。これらの定義は、コンパイラが言語の基本的な要素を認識するために重要です。このファイルは通常 `go generate` によって自動生成されます。
*   **`cgo`:** GoプログラムからC言語のコードを呼び出すためのメカニズムです。cgoを使用するパッケージは、コンパイルプロセスが複雑になり、一時ディレクトリの使用などにより、ビルド間でファイルパスの差分が生じることがあります。
*   **アセンブリコード (`-S` フラグ):** `go build -gcflags="-S"` コマンドを使用すると、コンパイルされたGoコードが生成するアセンブリコードを表示できます。これは、コンパイラの最適化やコード生成の挙動を詳細に分析する際に役立ちます。このコミットでは、新しいエクスポート形式が生成されるアセンブリコードに意図しない変更を与えないことを検証するために使用されました。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのエクスポートデータフォーマットを、従来のテキストベースからバイナリベースへと移行し、それをデフォルトで有効にすることです。

1.  **フォーマットの変更:**
    *   **旧フォーマット (テキスト):** パッケージのメタデータは、人間が読める形式の文字列として保存されていました。これは、`builtin.go` の `runtimeimport` や `unsafeimport` 定数に見られるように、Goの構文に似た形式で記述されていました。ファイル内で `$$` で始まるセクションに格納されます。
    *   **新フォーマット (バイナリ):** 新しいフォーマットは、コンパイラが効率的に読み書きできるように設計されたコンパクトなバイナリ表現です。これにより、データの冗長性が排除され、パースのオーバーヘッドが大幅に削減されます。ファイル内で `$$B` で始まるセクションに格納されます。`builtin.go` の変更を見ると、`runtimeimport` や `unsafeimport` の文字列が、一見して意味不明なバイト列に置き換えられていることがわかります。これは、これらの組み込みパッケージのエクスポートデータがバイナリ形式で直接埋め込まれるようになったことを示しています。

2.  **パフォーマンスへの影響:**
    *   **データサイズ削減:** 標準ライブラリのパッケージにおいて、エクスポートデータのサイズが平均で約65%削減されました。これは、コンパイル済みパッケージファイル（`.a`）のサイズを小さくし、ディスクI/Oを削減する効果があります。
    *   **書き込み速度向上:** エクスポートデータの書き込み時間が少なくとも62%削減されました。これは、コンパイルフェーズにおけるコンパイラの処理速度向上に直結します。
    *   **読み込み速度向上:** インポートデータの読み込み時間が少なくとも37%削減されました。これは、他のパッケージをインポートする際のコンパイラの処理速度向上に寄与し、全体的なビルド時間の短縮につながります。

3.  **互換性と透過性:**
    *   Goコンパイラは、新旧両方のエクスポートフォーマットを透過的に処理できるように設計されています。これにより、新しいコンパイラでコンパイルされたパッケージと古いコンパイラでコンパイルされたパッケージが混在する環境でも、問題なく動作します。これは、エコシステム全体の移行をスムーズにする上で非常に重要です。

4.  **検証と安定性:**
    *   変更がGoの生成するコードに悪影響を与えないことを確認するため、`cmp.bash` という新しいスクリプトが追加されました。このスクリプトは、新旧のエクスポート形式でビルドした標準ライブラリの各パッケージのアセンブリコード (`go build -gcflags="-S"`) を比較します。
    *   比較の結果、ほとんどのパッケージでアセンブリコードが同一であることが確認されました。
    *   一部のファイル (`src/crypto/x509`, `src/net`, `src/os/user`, `src/runtime/cgo`) ではファイル:行の差分が見られましたが、これらはcgoの使用による一時ディレクトリの違いに起因するものであり、無害であると判断されました。
    *   `src/go/internal/gccgoimporter` と `src/go/internal/gcimporter` の2つのファイルでもファイル:行の差分が見られましたが、これらは新しいエクスポート形式とは関係なく以前から存在していた問題 (`issue #15453` を参照) であり、この変更によって導入されたものではないとされています。
    *   これらの検証により、新しいエクスポート形式への切り替えが、実用上、以前と同じパッケージファイルを生成することが保証されました。

5.  **デバッグとフォールバック:**
    *   問題が発生した場合に備え、新しいエクスポート形式を無効にして古いテキスト形式に戻すためのオプションが提供されています。
        *   `go tool compile -newexport=0 <files>` (単一のコンパイラ呼び出し)
        *   `go build -gcflags="-newexport=0" <pkg>` (単一パッケージのビルド)
        *   `(export GO_GCFLAGS="-newexport=0"; sh make.bash)` (make/all.bash を使用したビルド)
    *   エクスポートデータの形式を視覚的に確認する方法も提供されています。パッケージファイル (`.a`) をエディタで開いた際、ヘッダの後に `$$` があればテキスト形式、`$$B` があればバイナリ形式です。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/cmd/compile/internal/gc/bexport.go`**:
    *   `forceNewExport` という定数が削除されています。これは、新しいエクスポート形式を強制的に有効にするためのデバッグ用フラグであり、デフォルト化に伴い不要となりました。
*   **`src/cmd/compile/internal/gc/builtin.go`**:
    *   `runtimeimport` および `unsafeimport` 定数の値が大幅に変更されています。従来の人間が読めるテキスト形式の文字列から、バイナリ形式のバイト列に置き換えられています。これが、エクスポートデータのコンパクト化の最も直接的な証拠です。
*   **`src/cmd/compile/internal/gc/export.go`**:
    *   `dumpexport` 関数内のロジックが変更され、エクスポート形式を選択する条件から `forceNewExport` が削除され、`newexport` フラグのみでバイナリ形式が選択されるようになっています。
*   **`src/cmd/compile/internal/gc/main.go`**:
    *   `newexport` コマンドラインフラグのデフォルト値が `false` から `true` に変更されています。これにより、新しいバイナリ形式がデフォルトで有効になります。
    *   関連する `TODO` コメントのイシュー番号が `13241` から `15323` に更新されています。
*   **`src/cmp.bash`**:
    *   新しいファイルとして追加されています。これは、新旧のエクスポート形式でビルドしたパッケージのアセンブリコードを比較し、差分を検出するためのシェルスクリプトです。

## コアとなるコードの解説

*   **`builtin.go` の変更:**
    *   このファイルはGoの組み込み型や関数をコンパイラに認識させるための重要な定義を含んでいます。以前は、これらの定義がGoのソースコードのようなテキスト形式で `runtimeimport` や `unsafeimport` という文字列定数としてハードコードされていました。これは、コンパイラがこれらの組み込み要素を「インポート」する際に、通常のパッケージと同様にパースする必要があることを意味します。
    *   今回の変更では、これらの文字列が、`c\x00\x03v0\x01\rruntime\x00\t\x11newobject ...` のようなバイナリ形式のバイト列に置き換えられました。これは、コンパイラがこれらの組み込み定義をより効率的に、直接内部データ構造にマッピングできるようになったことを示しています。テキストパースのオーバーヘッドがなくなるため、コンパイラの起動時や組み込みパッケージの処理が高速化されます。
*   **`export.go` と `main.go` の変更:**
    *   `export.go` の `dumpexport` 関数は、実際にエクスポートデータをファイルに書き出す部分を制御します。ここでの変更は、`newexport` フラグが `true` であれば、無条件に新しいバイナリ形式 (`$$B`) を使用するようにロジックを簡素化しています。
    *   `main.go` の `newexport` フラグのデフォルト値が `true` になったことで、ユーザーが明示的に `-newexport=0` を指定しない限り、すべてのコンパイルで新しいバイナリ形式が使用されるようになります。これは、この新しい形式が十分に安定しており、パフォーマンス上の利点からデフォルトとして採用する準備ができたことを示しています。
*   **`cmp.bash` の追加:**
    *   このスクリプトは、コンパイラの変更が生成される機械語コードに予期せぬ影響を与えないことを保証するための「安全網」として機能します。コンパイラの内部実装が変更されても、最終的に生成されるアセンブリコードが同じであれば、プログラムの挙動は変わらないはずです。このスクリプトは、コンパイラの変更が機能的なリグレッションを引き起こしていないことを自動的に検証する重要なテストツールです。

これらの変更は、Goコンパイラの内部動作を最適化し、ビルドパフォーマンスを向上させるための重要なステップであり、Go言語の進化における継続的なパフォーマンス改善への取り組みを反映しています。

# [インデックス 26986] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9オペレーティングシステム、特にARMアーキテクチャ上でのシグナル（Plan 9では「ノート」と呼ばれる）ハンドリングのサポートを改善するものです。主に、ARMプロセッサのリンクレジスタ (LR) の特殊な扱いと、Plan 9のトラップメッセージの構文の差異に対応するための変更が含まれています。

- `src/runtime/defs_plan9_386.go`: Plan 9/386アーキテクチャ向けのシグナルコンテキスト定義ファイル。ARMとのインターフェース統一のため、LR関連のダミーメソッドが追加されました。
- `src/runtime/defs_plan9_amd64.go`: Plan 9/AMD64アーキテクチャ向けのシグナルコンテキスト定義ファイル。Plan 9/386と同様に、LR関連のダミーメソッドが追加されました。
- `src/runtime/os3_plan9.go`: Plan 9向けのOS固有のランタイム処理、特にシグナルハンドラ (`sighandler`) の実装が含まれるファイル。ARMのLRを考慮したパニック処理ロジックが追加されました。
- `src/runtime/os_plan9.go`: Plan 9向けのOS固有のランタイム処理、特に`sigpanic`関数が含まれるファイル。トラップメッセージからのアドレス解析ロジックが改善されました。
- `src/runtime/signal_plan9.go`: Plan 9向けのシグナル定義と関連するテーブルが含まれるファイル。トラップメッセージ文字列が更新されました。

## 変更の背景

この変更の主な背景には、GoランタイムがPlan 9オペレーティングシステム上でARMアーキテクチャをサポートする際に直面した二つの課題があります。

1.  **ARMアーキテクチャのリンクレジスタ (LR) の存在**: ARMプロセッサは、関数呼び出し時に戻りアドレスを格納するためにリンクレジスタ (LR) を使用します。これは、x86やAMD64のような他のアーキテクチャが通常スタックに戻りアドレスをプッシュするのとは異なる動作です。シグナルやトラップが発生した際、正確な実行コンテキスト（特に戻りアドレス）を保存・復元するためには、このLRを適切に扱う必要があります。Goランタイムのパニック処理 (`sigpanic`) において、LRの存在はスタックトレースの正確性に影響を与える可能性がありました。
2.  **Plan 9のトラップメッセージ構文の差異**: Plan 9システムでは、トラップ（他のOSにおけるシグナルに相当）が発生した際に、その詳細を記述した「ノート」と呼ばれる文字列メッセージが生成されます。しかし、このメッセージの構文がアーキテクチャ間で一貫しておらず、特にメモリアクセス違反のアドレスを示す部分のプレフィックスが `"addr="` の場合と `"va="` の場合があるという「歴史的な偶然」による差異が存在しました。これにより、Goランタイムがトラップメッセージから正確な情報を抽出できない可能性がありました。

これらの差異に対応し、Plan 9/ARM上でのGoプログラムの安定性とデバッグ可能性を向上させるために、ランタイムのシグナルハンドリングメカニズムの修正が必要となりました。

## 前提知識の解説

このコミットの理解を深めるために、いくつかの前提知識を解説します。

*   **Plan 9**: Bell Labsが開発した分散オペレーティングシステムです。UNIXの思想を受け継ぎつつ、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルシステムとして抽象化し、それらを操作することでシステム全体を管理するという独特の設計思想を持っています。シグナルの代わりに「ノート (notes)」と呼ばれる文字列ベースの通知機構を使用します。
*   **ARMアーキテクチャとリンクレジスタ (LR)**: ARM (Advanced RISC Machine) は、モバイルデバイスなどで広く使用されているRISCベースのプロセッサアーキテクチャです。ARMプロセッサには、関数呼び出し時に呼び出し元に戻るためのアドレスを格納する専用のレジスタである「リンクレジスタ (LR)」が存在します。関数が別の関数を呼び出す際、現在のプログラムカウンタ (PC) の値（つまり戻りアドレス）がLRに保存されます。これは、x86/x64アーキテクチャが通常、戻りアドレスをスタックにプッシュするのとは対照的な動作です。シグナルハンドリングにおいて、割り込み発生時の正確な実行コンテキストの保存と復元には、このLRの適切な扱いが不可欠です。
*   **Goランタイムのシグナルハンドリング**: Go言語のプログラムは、OSからのシグナル（Plan 9ではノート）をGoランタイムが捕捉し、処理します。これにより、プログラムの異常終了（例えば、ゼロ除算や無効なメモリアクセスによるパニック）が発生した場合に、Go独自のスタックトレースを生成したり、`recover`機構を通じてパニックから回復したりすることが可能になります。ランタイムは、OSのシグナルハンドラをフックし、Goのスケジューラやガベージコレクタと連携して動作します。
*   **`sigctxt`構造体**: Goランタイムのシグナルハンドリングにおいて、`sigctxt`はシグナル発生時のCPUレジスタの状態（プログラムカウンタ、スタックポインタ、その他の汎用レジスタなど）を抽象化して表現する構造体です。シグナルハンドラはこの`sigctxt`を通じて、割り込み発生時のCPUの状態を検査したり、必要に応じて変更したりすることができます。これにより、シグナル処理後にプログラムの実行を特定の場所から再開させるといった制御が可能になります。アーキテクチャごとに異なるレジスタセットを共通のインターフェースで操作できるようにするための重要な抽象化レイヤーです。
*   **`funcPC`関数**: Goランタイム内部で、特定のGo関数のエントリポイントのアドレス（プログラムカウンタ値）を取得するために使用されるヘルパー関数です。シグナルハンドラがパニック処理のために`sigpanic`関数へジャンプする際などに、その関数のアドレスを動的に取得するために利用されます。
*   **`_NCONT`定数**: Plan 9のシグナルハンドリングにおいて、シグナルハンドラが処理を終えた後、OSに対して通常のプログラム実行を継続するように指示するための戻り値です。

## 技術的詳細

このコミットは、Plan 9/ARM環境におけるGoランタイムの堅牢性を高めるために、以下の技術的な変更を導入しています。

1.  **リンクレジスタ (LR) の抽象化と管理**:
    *   `src/runtime/defs_plan9_386.go` と `src/runtime/defs_plan9_amd64.go` に、`sigctxt`構造体に対する新しいメソッド `lr()`, `setlr(x uintptr)`, `savelr(x uintptr)` が追加されました。これらのメソッドは、ARMアーキテクチャでLRを扱うためのインターフェースを定義します。
    *   x86およびAMD64アーキテクチャではLRが存在しないため、これらのメソッドはダミーの実装（`lr()`は常に`0`を返し、`setlr`と`savelr`は何もしない）となっています。これにより、異なるアーキテクチャ間で`sigctxt`のインターフェースを統一しつつ、ARM固有のLR処理を可能にしています。

2.  **ARM向け`sigpanictramp`の導入**:
    *   `src/runtime/defs_plan9_386.go` と `src/runtime/defs_plan9_amd64.go` に `func sigpanictramp() {}` というダミー関数が追加されました。これは、ARMアーキテクチャにおいて`sigpanic`関数を直接呼び出すのではなく、このトランポリン関数を介して呼び出すためのプレースホルダーです。
    *   ARMでは、`sigpanic`が呼び出される前にLRの値をスタックに保存する必要があります。`sigpanictramp`は、このLRの保存処理を実行してから実際の`sigpanic`を呼び出す役割を担います。これにより、リーフ関数（他の関数を呼び出さない関数）でパニックが発生した場合でも、LRが正しく保存され、正確なスタックトレースが得られるようになります。

3.  **`src/runtime/os3_plan9.go`における`sighandler`の変更**:
    *   `sighandler`関数内で、`usesLR`というブール変数が導入され、現在のアーキテクチャがLRを使用するかどうかを判定します。これにより、ARM固有のLR処理が条件付きで有効になります。
    *   パニック処理の際に、`usesLR`が真の場合、`c.savelr(c.lr())` を呼び出して現在のLRの値をスタックに保存するロジックが追加されました。これは、`sigpanic`が呼び出される前にLRを保護するための重要なステップです。
    *   プログラムカウンタ (PC) が`0`でない場合（つまり、有効な呼び出し元がある場合）のスタック操作も変更されました。`usesLR`が真の場合、`c.setlr(pc)`によってLRにPCを設定し、それ以外の場合は従来のスタックに`pc`をプッシュする動作が維持されます。
    *   `c.setpc`の呼び出し先も変更され、`usesLR`が真の場合は`funcPC(sigpanictramp)`（トランポリン関数）を、それ以外の場合は`funcPC(sigpanic)`を指すようになりました。
    *   `tracebacktrap`関数への引数に`c.lr()`が追加され、スタックトレース生成時にLRの値も考慮されるようになりました。これにより、ARM環境でのスタックトレースの正確性が向上します。

4.  **`src/runtime/os_plan9.go`におけるノートメッセージ解析の改善**:
    *   `sigpanic`関数内で、Plan 9のトラップメッセージからメモリアクセス違反のアドレスを解析するロジックが強化されました。以前は`"addr="`プレフィックスのみを検索していましたが、この変更により`"va="`プレフィックスも認識するようになりました。
    *   これは、Plan 9のトラップメッセージの構文がアーキテクチャによって異なるという「歴史的な偶然」に対応するためのもので、より広範なトラップメッセージ形式から正確なアドレス情報を抽出できるようになります。

5.  **`src/runtime/signal_plan9.go`におけるトラップメッセージ文字列の更新**:
    *   `sigtable`内のトラップメッセージ文字列が、`"sys: trap: fault read addr"`から`"sys: trap: fault read"`へ、`"sys: trap: fault write addr"`から`"sys: trap: fault write"`へと変更されました。
    *   この変更は、`os_plan9.go`での解析ロジックの変更と整合性を取るため、または実際のPlan 9システムでのトラップメッセージ形式に合わせたものと考えられます。これにより、GoランタイムがOSからのトラップメッセージをより正確に識別し、適切なパニック処理を行うことが可能になります。

これらの変更は、GoランタイムがPlan 9/ARM環境でより安定して動作し、デバッグ時に有用な情報（正確なスタックトレースなど）を提供できるようにするために不可欠です。

## コアとなるコードの解説

### `sigctxt`へのLR関連メソッドの追加 (`defs_plan9_386.go`, `defs_plan9_amd64.go`)

`sigctxt`構造体は、シグナルハンドラがCPUレジスタの状態を操作するための抽象化を提供します。ARMアーキテクチャではリンクレジスタ (LR) が重要な役割を果たすため、`lr()`, `setlr()`, `savelr()`というメソッドが追加されました。これにより、`sigctxt`を通じてLRの値を読み書きしたり、スタックに保存したりする操作が可能になります。x86/AMD64ではLRが存在しないため、これらのメソッドはダミー実装（何もしない、または0を返す）とすることで、インターフェースの統一性を保っています。

### `sigpanictramp`の導入 (`defs_plan9_386.go`, `defs_plan9_amd64.go`)

`sigpanictramp`は、ARMアーキテクチャで`sigpanic`関数を呼び出す際に使用されるトランポリン関数です。ARMでは、関数呼び出し時に戻りアドレスがLRに格納されるため、パニック発生時に`sigpanic`へジャンプする前に、現在のLRの値をスタックに明示的に保存する必要があります。`sigpanictramp`はこの保存処理を実行してから`sigpanic`を呼び出すことで、リーフ関数（他の関数を呼び出さない関数）でパニックが発生した場合でも、正確なスタックトレースが生成されるようにします。

### `sighandler`におけるLRの扱い (`os3_plan9.go`)

`sighandler`関数は、Plan 9からのノート（シグナル）を処理するGoランタイムの主要なハンドラです。この関数には、`usesLR`というフラグが導入され、現在のアーキテクチャがLRを使用するかどうかに応じて処理を分岐させます。

*   **LRの保存**: `usesLR`が真の場合、パニック処理の開始時に`c.savelr(c.lr())`を呼び出し、現在のLRの値をスタックに保存します。これは、`sigpanic`が呼び出される前にLRを保護し、スタックトレースの正確性を保証するために重要です。
*   **PCとLRの設定**: パニック発生時に`sigpanic`（または`sigpanictramp`）へジャンプする際、`pc != 0`（有効な呼び出し元がある）であれば、`usesLR`に応じてPCの扱いが変わります。`usesLR`が真の場合、`c.setlr(pc)`でLRにPCを設定し、それ以外の場合は従来のスタックにPCをプッシュします。
*   **ジャンプ先の選択**: `c.setpc`の呼び出し先も`usesLR`に応じて分岐し、ARMでは`sigpanictramp`へ、それ以外では`sigpanic`へジャンプするように設定されます。
*   **スタックトレースへのLRの追加**: `tracebacktrap`関数への引数に`c.lr()`が追加されました。これにより、スタックトレースを生成する際にLRの値も考慮されるようになり、ARM環境でのデバッグ情報がより充実します。

これらの変更により、ARMアーキテクチャの特性を考慮した、より正確で堅牢なパニック処理が実現されます。

### `sigpanic`におけるノートメッセージ解析の改善 (`os_plan9.go`)

`sigpanic`関数は、メモリアクセス違反などのトラップが発生した際に、Plan 9から受け取ったノートメッセージを解析し、問題のアドレスを特定します。以前はアドレスを示すプレフィックスとして`"addr="`のみを想定していましたが、Plan 9のトラップメッセージの構文がアーキテクチャによって異なる場合があるため、この変更では`"va="`というプレフィックスも認識するように拡張されました。これにより、より多様なPlan 9環境からのトラップメッセージに対応できるようになり、アドレス解析の信頼性が向上します。

### トラップメッセージ文字列の更新 (`signal_plan9.go`)

`sigtable`は、Goランタイムが認識するPlan 9のノートメッセージとその対応するGoシグナルをマッピングするテーブルです。このコミットでは、メモリアクセス違反に関連するトラップメッセージ文字列が`"sys: trap: fault read addr"`から`"sys: trap: trap: fault read"`へ、`"sys: trap: fault write addr"`から`"sys: trap: fault write"`へと変更されました。これは、`os_plan9.go`での解析ロジックの変更と整合性を取るため、または実際のPlan 9システムで生成されるメッセージ形式に合わせたものと考えられます。これにより、GoランタイムがOSからのトラップをより正確に識別し、適切なパニック処理をトリガーできるようになります。

## 変更の背景

Go言語は、その設計思想としてコードの明確性と予測可能性を重視しています。これには、識別子（変数、関数、型など）の名前解決とスコープのルールも含まれます。このコミットが修正しているのは、Goコンパイラが、より内側のスコープで宣言された変数が、より外側のスコープで宣言された「型」の名前を意図せずシャドーイング（隠蔽）してしまう状況を正しく検出できなかったバグです。

この問題は、`bug144.go` で修正された定数のシャドーイング問題と類似しています。定数と同様に、型名が変数によってシャドーイングされると、その型が内側のスコープからアクセスできなくなり、コードの意図が不明瞭になったり、予期せぬ動作を引き起こしたりする可能性があります。Go言語の設計原則に反し、開発者が混乱する原因となるため、コンパイラがこのような状況をエラーとして報告することが望ましいと判断されました。

## 前提知識の解説

### Go言語のスコープ

Go言語は**レキシカルスコープ**を採用しており、識別子の可視性はソースコード上での宣言位置によって決定されます。Goにはいくつかのスコープレベルがあります。

*   **ユニバースブロックスコープ**: `int`, `string`, `true`, `false`, `len` などの組み込み識別子が属する最も広範なスコープです。
*   **パッケージブロックスコープ**: パッケージレベル（関数外）で宣言された識別子は、そのパッケージ内のすべてのファイルから可視です。大文字で始まる識別子はエクスポートされ、他のパッケージからもアクセス可能です。
*   **ファイルブロックスコープ**: インポートされたパッケージの識別子はこのスコープに属します。
*   **関数ブロックスコープ**: 関数内で宣言された変数やパラメータは、その関数内でのみ可視です。
*   **ブロックスコープ**: `if`文、`for`ループ、`switch`文、または明示的な `{}` ブロック内で宣言された識別子は、そのブロック内でのみ可視です。

内側のスコープは外側のスコープの識別子にアクセスできますが、外側のスコープは内側のスコープの識別子にアクセスできません。

### 変数シャドーイング

変数シャドーイングとは、内側のスコープで宣言された識別子（変数など）が、外側のスコープで同じ名前を持つ別の識別子を「隠蔽」する現象を指します。内側のスコープ内でその名前を参照すると、内側の識別子が優先され、外側の識別子は一時的にアクセスできなくなります。

Go言語では、`:=` (短い変数宣言) 演算子を使用する際に意図しないシャドーイングが発生しやすいです。例えば、外側のスコープに存在する変数と同じ名前で `:=` を使って内側のスコープで変数を宣言すると、Goは新しい変数を宣言し、外側の変数をシャドーイングします。これは、特にエラーハンドリングなどで `err := someFunc()` のように使われる場合に、混乱を招くことがあります。

シャドーイング自体が常にバグであるとは限りませんが、コードの可読性を損ない、デバッグを困難にする可能性があるため、注意が必要です。

### Goの型システム

Goは**静的型付け言語**であり、変数の型はコンパイル時に決定され、実行時に変更されることはありません。Goには、`int`, `string`, `bool` などの基本型と、配列、スライス、構造体、マップ、ポインタ、関数、チャネル、インターフェースなどの複合型があります。

このコミットの文脈では、`type T int` のように宣言される「型名」が、`T := 0` のように宣言される「変数名」によってシャドーイングされる問題が焦点となります。

### `go test` と `golden.out`

Goプロジェクトでは、`go test` コマンドを使用してテストを実行します。`test/bugs` ディレクトリには、Goコンパイラやランタイムの特定のバグを再現するためのテストケースが格納されています。これらのテストは、コンパイラが特定のコードに対して期待されるエラーメッセージや出力を生成するかどうかを検証するために使用されます。

`test/golden.out` ファイルは、これらのバグテストが生成すべき標準出力（コンパイラのエラーメッセージなど）の「ゴールデン」または「期待される」バージョンを記録するファイルです。テスト実行時に生成された出力が `golden.out` の内容と一致しない場合、テストは失敗します。これにより、コンパイラの挙動が意図せず変更されていないか、または特定のバグが修正されたことを確認できます。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラの名前解決ロジックの改善にあります。以前のコンパイラは、内側のスコープで変数を宣言する際に、その名前が外側のスコープで既に型として定義されている場合でも、それを許容していました。これは、Goの厳格なスコープルールと明確性の原則に反する挙動でした。

修正の核心は、コンパイラが識別子の宣言を処理する際に、現在のスコープだけでなく、その外側のスコープも参照し、同じ名前の型が存在しないかをチェックするようになった点です。もし同じ名前の型が外側のスコープに存在し、内側のスコープで変数を宣言しようとしている場合、コンパイラはこれを名前の衝突とみなし、コンパイルエラーを発生させるように変更されました。

これにより、`type t int` のような型宣言が存在する状況で、`func main() { t := 0 }` のように同じ名前 `t` で変数を宣言しようとすると、コンパイラは「`t` は型であり、変数ではない」という旨のエラーを報告するようになります。この変更によって、Goコードの予測可能性と堅牢性が向上し、開発者が意図しない名前の衝突や型の隠蔽に遭遇するリスクが低減されます。

この修正は、`test/bugs/bug145.go` という新しいテストケースの追加と、そのテストケースが期待するエラーメッセージを `test/golden.out` に追記することで検証されています。

```go
// $G $D/$F.go || echo BUG should compile

// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

	t := 0 // main関数内で 't' という名前の変数を宣言しようとする
}

*/
```

このファイルは、バグを再現するための最小限のコードです。
1.  `package main` の直下で `type t int` と宣言し、`t` という名前のカスタム型（ここでは `int` のエイリアス）を定義しています。この `t` はパッケージスコープで可視です。
2.  `main` 関数内で `t := 0` と記述し、`t` という名前の新しい変数を宣言し、`0` で初期化しようとしています。
このコードは、修正前のコンパイラではコンパイルが通ってしまうか、意図しない挙動を示していました。しかし、Goのスコープルールと明確性の原則からすると、内側のスコープで変数を宣言する際に、外側のスコープの型名をシャドーイングすべきではありません。

ファイルの先頭にある `// $G $D/$F.go || echo BUG should compile` は、このテストケースがコンパイルエラーを発生させることを期待していることを示しています。また、コメントブロック `/* bug145.go:8: t is type, not var */` は、このテストが期待する正確なエラーメッセージと行番号を示しています。

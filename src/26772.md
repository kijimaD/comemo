## 変更の背景

この変更の背景には、Goランタイムのガベージコレクション（GC）における`markroot`関数の呼び出し方法の進化があります。以前は`markroot`関数が`parfor`という並列処理の深い部分から呼び出されており、そのコンテキストでは`gcWork`オブジェクトを呼び出し元から渡すことが困難でした。そのため、`markroot`関数内で一時的に`gcWork`をスタック上に作成し、ルートオブジェクトをマークした直後に破棄するという非効率な処理が行われていました。

しかし、ランタイムの変更により、`markroot`が直接呼び出されるようになり、呼び出し元で`gcWork`にアクセスできる状況になりました。この新しい呼び出しパターンを利用して、`gcWork`を引数として`markroot`に渡すことで、オブジェクトの生成と破棄のオーバーヘッドを削減し、同じP（プロセッサ）からの`markroot`呼び出し間で`gcWork`を共有できるようになりました。これにより、GCのマーキングフェーズの効率が向上し、全体的なパフォーマンス改善に寄与します。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクションは、主に三色マーク＆スイープアルゴリズムをベースにしています。これは、プログラムの実行と並行して動作する並行GCであり、STW（Stop The World）時間を最小限に抑えることを目指しています。GCサイクルは主に以下のフェーズで構成されます。

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（グローバル変数、スタック上の変数など、GCの起点となるオブジェクト）から到達可能なオブジェクトを「生きている（live）」とマークします。
    *   このフェーズは、プログラムの実行と並行して行われます。
    *   `gcWork`は、このマークフェーズで「マークすべきオブジェクト」のキューとして機能します。

2.  **マーク終了フェーズ (Mark Termination Phase)**:
    *   マークフェーズの終了を調整し、すべてのゴルーチンがマーク作業を完了したことを確認します。短いSTWが発生します。

3.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクト（「死んでいる（dead）」オブジェクト）がメモリから解放されます。このフェーズも並行して行われます。

### `gcWork`とは

`gcWork`は、Goランタイムのガベージコレクションにおいて、マークフェーズ中に到達可能なオブジェクトを追跡し、マーク作業を効率的に行うためのデータ構造です。具体的には、マークすべきオブジェクトのポインタを一時的に保持するキューのような役割を果たします。

*   GCワーカーゴルーチンは、`gcWork`からオブジェクトを取り出し、そのオブジェクトが参照する他のオブジェクトをスキャンし、まだマークされていないオブジェクトがあれば`gcWork`に追加します。
*   このプロセスを繰り返すことで、GCルートから到達可能なすべてのオブジェクトがマークされます。
*   `gcWork`は通常、各P（プロセッサ）にローカルに割り当てられ、並行してGC作業を進めるために使用されます。

### `markroot`関数

`markroot`関数は、GCルートをマークする役割を担います。GCルートには、グローバル変数、スタック、ファイナライザキュー、スパン（メモリブロック）などが含まれます。この関数は、これらの様々な種類のルートを走査し、そこから到達可能なオブジェクトを`gcWork`に追加してマーク作業を開始します。

### `parfor`とは

`parfor`は、Goランタイム内部で並列処理を行うためのメカニズムの一つです。特定のタスクを複数のゴルーチンに分割して並行して実行するために使用されます。このコミットの文脈では、以前の`markroot`の呼び出しが`parfor`の深い層から行われていたため、`gcWork`を引数として渡すことが困難だったという状況を説明するために言及されています。

## 技術的詳細

このコミットの技術的な詳細な変更点は、`markroot`関数が`gcWork`オブジェクトをどのように取得し、使用するかという点に集約されます。

**変更前:**
`markroot`関数は、以下のように定義されていました。
```go
func markroot(i uint32) {
    var gcw gcWork
    // ... gcw を使用してマーク作業 ...
    gcw.dispose()
}
```
この実装では、`markroot`が呼び出されるたびに、スタック上に新しい`gcWork`インスタンスが作成され、その直後に`dispose`メソッドが呼び出されてリソースが解放されていました。これは、`markroot`が`parfor`のような並列処理の深いコンテキストから呼び出されていたため、呼び出し元が`gcWork`を管理して渡すことが難しかった時代の名残です。しかし、ルートを一つマークするたびに`gcWork`の生成と破棄を繰り返すことは、オーバーヘッドとなり、GCの効率を低下させていました。

**変更後:**
このコミットにより、`markroot`関数は以下のように変更されました。
```go
func markroot(gcw *gcWork, i uint32) {
    // ... 渡された gcw を直接使用してマーク作業 ...
}
```
`markroot`関数は、`gcWork`へのポインタを引数として受け取るようになりました。これにより、呼び出し元（この場合は`gcDrain`関数）が`gcWork`オブジェクトを管理し、それを複数の`markroot`呼び出し間で共有することが可能になります。

具体的には、`gcDrain`関数内で`gcWork`が一度だけ初期化され、そのポインタが`markroot`に渡されるようになります。これにより、`markroot`が呼び出されるたびに`gcWork`を生成・破棄する必要がなくなり、以下の利点が得られます。

1.  **オーバーヘッドの削減**: `gcWork`オブジェクトの生成と破棄に伴うCPUサイクルとメモリ割り当てのオーバーヘッドがなくなります。
2.  **リソースの再利用**: 同じP（プロセッサ）上で実行される`markroot`呼び出し間で`gcWork`を再利用できるため、キャッシュ効率が向上し、GC作業がよりスムーズになります。
3.  **コードの簡素化**: `markroot`関数内での`gcWork`の初期化と破棄のロジックが不要になり、コードがよりシンプルになります。

この変更は、GoランタイムのGCが進化し、`markroot`の呼び出しコンテキストがより直接的になったことによる最適化であり、GCの全体的なパフォーマンス向上に貢献します。

`markroot`関数は、`gcWork`へのポインタを引数として受け取るようになりました。これにより、呼び出し元（この場合は`gcDrain`関数）が`gcWork`オブジェクトを管理し、それを複数の`markroot`呼び出し間で共有することが可能になります。

具体的には、`gcDrain`関数内で`gcWork`が一度だけ初期化され、そのポインタが`markroot`に渡されるようになります。これにより、`markroot`が呼び出されるたびに`gcWork`を生成・破棄する必要がなくなり、以下の利点が得られます。

1.  **オーバーヘッドの削減**: `gcWork`オブジェクトの生成と破棄に伴うCPUサイクルとメモリ割り当てのオーバーヘッドがなくなります。
2.  **リソースの再利用**: 同じP（プロセッサ）上で実行される`markroot`呼び出し間で`gcWork`を再利用できるため、キャッシュ効率が向上し、GC作業がよりスムーズになります。
3.  **コードの簡素化**: `markroot`関数内での`gcWork`の初期化と破棄のロジックが不要になり、コードがよりシンプルになります。

この変更は、GoランタイムのGCが進化し、`markroot`の呼び出しコンテキストがより直接的になったことによる最適化であり、GCの全体的なパフォーマンス向上に貢献します。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、`src/runtime/mgcmark.go` 内の `markroot` 関数のシグネチャと実装、およびその呼び出し箇所に集中しています。

1.  **`markroot` 関数のシグネチャ変更**:
    *   変更前: `func markroot(i uint32)`
    *   変更後: `func markroot(gcw *gcWork, i uint32)`
    `markroot`関数は、GCルートのインデックス`i`に加えて、`gcWork`構造体へのポインタ`gcw`を引数として受け取るようになりました。これにより、`markroot`関数内で`gcWork`を新たに作成する必要がなくなり、呼び出し元から提供された`gcWork`を直接利用できるようになります。

2.  **`markroot` 関数内の `gcWork` の初期化と破棄の削除**:
    *   変更前は、`markroot`関数の冒頭で`var gcw gcWork`としてローカルな`gcWork`がスタック上に作成され、関数の最後で`gcw.dispose()`が呼び出されていました。
    *   変更後、これらの行は削除されました。これにより、`markroot`が呼び出されるたびに`gcWork`オブジェクトの生成と破棄が行われるオーバーヘッドがなくなります。

3.  **`markroot` 関数内での `gcw` の使用方法の変更**:
    *   `markroot`関数内で`gcw`を使用していた箇所（例: `markrootBlock`, `scanblock`, `markrootSpans`の呼び出し）では、以前はローカル変数`gcw`のアドレス`&gcw`を渡していましたが、変更後は引数として受け取ったポインタ`gcw`を直接渡すようになりました。

4.  **`gcDrain` 関数からの `markroot` の呼び出し変更**:
    *   `gcDrain`関数は、GCワーカーがマーク作業を行う主要な関数です。この関数内で`markroot`が呼び出される箇所も変更されました。
    *   変更前は`markroot(job)`のように`gcWork`を渡さずに呼び出されていました。
    *   変更後、`markroot(gcw, job)`のように、`gcDrain`関数が管理する`gcWork`のポインタ`gcw`を`markroot`に渡すようになりました。これにより、`gcDrain`が`gcWork`のライフサイクルを管理し、複数の`markroot`呼び出し間で共有することが可能になります。

これらの変更により、`gcWork`オブジェクトの生成と破棄の頻度が大幅に減少し、GCのマークフェーズにおけるパフォーマンスが向上します。特に、`markroot`が頻繁に呼び出される環境では、この最適化が顕著な効果を発揮します。

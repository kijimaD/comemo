## 元コミット内容

Goランタイムのガベージコレクション(GC)トレースの出力に、ヒープの目標サイズ（heap goal）を含めるように変更します。この情報はエンドユーザーにとって直接役立つかどうかは不明ですが、Go開発者がGCペーサーの挙動を理解する上で非常に有用です。現状では、他のヒープ統計からこの目標値を導出することは可能ですが、目標値の計算方法が変更される予定であり、その変更後は導出が困難になるため、この変更が導入されました。

## 変更の背景

Goのガベージコレクタは、プログラムの実行と並行して動作する並行GCを採用しています。GCの効率とアプリケーションのパフォーマンスのバランスを取るために、「GCペーサー（GC Pacer）」と呼ばれるメカニズムが導入されています。GCペーサーは、ヒープの使用状況に基づいて次のGCサイクルを開始するタイミングや、GCが消費すべきCPUリソースの量を動的に調整します。

このコミットが導入された背景には、GCペーサーの内部的な動作をより正確に監視し、デバッグする必要性がありました。特に、GCペーサーが「次に到達すべきヒープサイズ」として設定する`heapGoal`の値は、GCの挙動を理解する上で非常に重要です。コミットメッセージにあるように、当時`heapGoal`の計算方法が変更される計画があり、その変更後には既存のGCトレース出力から`heapGoal`を推測することが難しくなるため、明示的に出力に含めることが決定されました。これにより、開発者はGCペーサーがどのようにヒープの成長を制御しようとしているかを直接確認できるようになります。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、メモリ管理を自動化するシステムです。Go 1.5以降、GoのGCは「並行（concurrent）」かつ「非世代別（non-generational）」のマーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGCが動作し、プログラムの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。

GCの主なフェーズは以下の通りです。
1.  **マークフェーズ (Mark Phase)**:
    *   **マーク準備 (Mark Setup / STW)**: GCが開始される前に、非常に短いSTWが発生し、GCに必要な初期設定が行われます。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、到達可能なオブジェクトがマークされます。
    *   **マーク終了 (Mark Termination / STW)**: 並行マークフェーズの終了時に、再び短いSTWが発生し、マークフェーズの最終処理が行われます。
2.  **スイープフェーズ (Sweep Phase)**:
    *   **並行スイープ (Concurrent Sweep)**: マークされなかった（到達不可能な）オブジェクトが解放され、メモリが再利用可能になります。このフェーズもアプリケーションの実行と並行して行われます。

### GCペーサー (GC Pacer)

GCペーサーは、Goランタイムの重要なコンポーネントであり、GCの実行を制御し、アプリケーションのスループットとレイテンシのバランスを取る役割を担っています。その主な目的は、ヒープの成長を監視し、次のGCサイクルをいつ開始すべきか、そしてGCがどれくらいのCPUリソースを消費すべきかを決定することです。

ペーサーは、前回のGCサイクルで解放されたメモリ量と、現在のヒープの成長率に基づいて、次のGCサイクルが開始されるべきヒープの目標サイズ（`heapGoal`）を計算します。これにより、GCがメモリを使い果たす前に効率的に動作し、かつアプリケーションの実行を不必要に妨げないように調整されます。

### `gctrace`

`gctrace`は、GoランタイムのGC活動に関する詳細な情報を標準エラー出力（stderr）に表示するためのデバッグフラグです。`GODEBUG=gctrace=1`環境変数を設定してGoプログラムを実行すると、GCサイクルごとに以下のような情報が出力されます。

```
gc # @#s #%: #+...+# ms clock, #+...+# ms cpu, #->#-># MB, # MB goal, # P
```

各項目の意味は以下の通りです（このコミット以前の一般的な形式）：
*   `gc #`: GCサイクルの番号。
*   `@#s`: プログラム開始からの経過時間。
*   `#%`: GCが消費したCPU時間の割合。
*   `#+...+# ms clock`: GCの各フェーズ（STW、並行マーク、マーク終了など）にかかった実時間（ウォールクロック時間）。
*   `#+...+# ms cpu`: GCの各フェーズで消費されたCPU時間。
*   `#->#-># MB`: GC開始前のヒープサイズ -> マーク終了後のライブオブジェクトサイズ -> GC終了後のヒープサイズ。
*   `# P`: GCに参加したプロセッサ（P）の数。

このコミットは、この出力行に「`# MB goal`」という項目を追加し、GCペーサーが設定したヒープの目標サイズを明示的に表示するようにします。

### `heapGoal`

`heapGoal`は、GoランタイムのGCペーサーが計算する、次のGCサイクルが開始されるべきヒープの目標サイズです。この値は、GCがメモリを使い果たす前に効率的に動作し、かつアプリケーションの実行を不必要に妨げないように調整するために使用されます。`heapGoal`は、GCの効率とアプリケーションのパフォーマンスのバランスを取る上で中心的な役割を果たします。

## 技術的詳細

このコミットの技術的な変更は、Goランタイムのガベージコレクタのコア部分である`src/runtime/mgc.go`ファイルに集中しています。

変更の核心は、GCトレース出力に`heapGoal`の値を直接含めることです。これまでは、`gctrace`の出力にはGC開始時、マーク終了時、GC終了時のヒープサイズは含まれていましたが、GCペーサーが目標とするヒープサイズは明示的に表示されていませんでした。開発者は他のヒープ統計からこの値を推測する必要がありましたが、GCペーサーのアルゴリズム変更により、その推測が困難になることが予想されていました。

具体的な変更点は以下の通りです。

1.  **`heapGoal`変数の追加**: `func gc(mode int)`関数のローカル変数として`heapGoal uint64`が追加されました。これは、GCトレース出力のためにヒープ目標値を一時的に保持するためのものです。
2.  **`heapGoal`への値の代入**:
    *   `gcBackgroundMode`（並行GCモード）の場合、`gcController.heapGoal`の値が`heapGoal`変数に代入されます。`gcController`はGCペーサーのロジックをカプセル化しており、`heapGoal`はその内部で計算された目標値です。
    *   それ以外のモード（例えば、強制GCなど）で`debug.gctrace > 0`の場合、GC開始時のヒープサイズである`heap0`が`heapGoal`に代入されます。これは、これらのモードではGCペーサーが設定する明確な`heapGoal`という概念が適用されないため、GC開始時のヒープサイズを便宜的に目標値として表示することで、トレース出力の形式を統一するためと考えられます。
3.  **`gctrace`出力の変更**: `print`関数呼び出しによって生成されるGCトレースの出力フォーマットが変更され、`heapGoal`の値がメガバイト単位で追加されました。具体的には、既存のヒープサイズ表示（`heap0->heap1->heap2 MB`）の後に、「`heapGoal MB goal`」という形式で目標ヒープサイズが表示されるようになります。

これらの変更により、GoランタイムのGCペーサーの挙動をより直接的かつ正確に監視できるようになり、GCのパフォーマンスチューニングやデバッグ作業が容易になります。

## コアとなるコードの解説

### 1. `var heap0, heap1, heap2, heapGoal uint64` の追加

`src/runtime/mgc.go` の `gc` 関数内で、GCトレースに関連する統計情報を保持するための変数群に `heapGoal uint64` が追加されました。
*   `heap0`: GC開始時のヒープサイズ。
*   `heap1`: マークフェーズ終了後のライブオブジェクトの合計サイズ。
*   `heap2`: GCサイクル終了後のヒープサイズ。
*   `heapGoal`: 今回のコミットで追加された変数で、GCペーサーが設定した次のGCサイクルが開始されるべきヒープの目標サイズを保持します。

### 2. `heapGoal = gcController.heapGoal` の代入

`if mode == gcBackgroundMode` ブロック内で、`gcController.startCycle()` の呼び出し後に `heapGoal = gcController.heapGoal` が追加されました。
*   `gcBackgroundMode` は、Goの並行GCがバックグラウンドで実行されている通常のモードを指します。
*   `gcController` は、GCペーサーのロジックを管理する構造体です。
*   `gcController.heapGoal` は、GCペーサーが計算した、次のGCサイクルが開始されるべきヒープの目標サイズです。この行は、この計算された目標値をローカル変数 `heapGoal` に格納しています。

### 3. `heapGoal = heap0` の代入

`if debug.gctrace > 0` ブロック内で、`heapGoal = heap0` が追加されました。このブロックは、GCがバックグラウンドモードではない場合（例えば、`runtime.GC()`による強制GCなど）にGCトレースが有効な場合に実行されます。
*   この場合、GCペーサーによる動的な`heapGoal`の概念は直接適用されないため、GC開始時のヒープサイズ（`heap0`）を便宜的に`heapGoal`として設定し、トレース出力の形式を統一しています。これにより、どのようなGCモードであっても`heapGoal`の項目がトレースに出力されるようになります。

### 4. `gctrace` 出力フォーマットの変更

`print` 関数呼び出しによって生成されるGCトレースの出力文字列に、`heapGoal` の値が追加されました。
変更前:
```go
			heap0>>20, "->", heap1>>20, "->", heap2>>20, " MB, ",
```
変更後:
```go
			heap0>>20, "->", heap1>>20, "->", heap2>>20, " MB, ",
			heapGoal>>20, " MB goal, ",
```
*   `>>20` は、バイト単位のサイズをメガバイト単位に変換するためのビットシフト演算です（1MB = 2^20 バイト）。
*   この変更により、GCトレースの出力行に「`[heapGoal] MB goal`」という形式で、GCペーサーが設定したヒープの目標サイズが明示的に表示されるようになります。

これらの変更は、GoランタイムのGCの内部動作をより透過的にし、開発者がGCのパフォーマンス特性を理解し、デバッグする上で非常に貴重な情報を提供します。

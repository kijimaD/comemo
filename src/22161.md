## 元コミット内容

```
runtime: simplify CPU profiling code

This makes Go's CPU profiling code somewhat more idiomatic; e.g.,
using := instead of forward declaring variables, using "int" for
element counts instead of "uintptr", and slices instead of C-style
pointer+length. This makes the code easier to read and eliminates a
lot of type conversion clutter.

Additionally, in sigprof we can collect just maxCPUProfStack stack
frames, as cpuprof won't use more than that anyway.
```

## 変更の背景

このコミットの主な目的は、GoランタイムのCPUプロファイリングコードの可読性と保守性を向上させることです。具体的には、以下の点が挙げられます。

1.  **Goらしい記述への移行**: 従来のコードには、C言語のようなポインタと長さの組み合わせや、変数の事前宣言など、Go言語のイディオムにそぐわない記述が見られました。これをGoらしい`:=`による変数宣言、スライス、そして適切な型（`uintptr`ではなく`int`）の使用に置き換えることで、コードの自然さを高めています。
2.  **型変換の煩雑さの解消**: `uintptr`と`int`の間での頻繁な型変換は、コードを読みにくくし、エラーの原因となる可能性がありました。要素数にはより適切な`int`型を使用することで、この煩雑さを排除しています。
3.  **スタックフレーム収集の最適化**: `sigprof`（シグナルプロファイリング）において、`maxCPUProfStack`で定義された最大数を超えるスタックフレームを収集しても、`cpuprof`がそれ以上を使用しないため、無駄な処理が発生していました。このコミットでは、必要な数のスタックフレームのみを収集するように制限することで、効率を改善しています。

これらの変更により、CPUプロファイリングコードはより理解しやすくなり、将来的なメンテナンスや機能追加が容易になることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびランタイムに関する知識が必要です。

*   **CPUプロファイリング**: プログラムがCPU時間をどこで消費しているかを特定するための手法です。Goでは、`pprof`ツールを通じてCPUプロファイルを取得できます。これは、一定の間隔で実行中のゴルーチンのスタックトレースをサンプリングすることで実現されます。
*   **`uintptr`と`int`**:
    *   `uintptr`: ポインタを保持するのに十分な大きさの符号なし整数型です。主に`unsafe`パッケージと組み合わせて、メモリ操作やシステムコールなどで使用されます。しかし、これはあくまで「ポインタを保持できる整数」であり、一般的な数値計算には適していません。
    *   `int`: 符号付き整数型で、要素数やカウントなど、一般的な数値表現に適しています。
    *   Goのイディオムでは、要素数や長さには`int`を使用することが推奨されます。`uintptr`は、メモリアドレスを扱うなど、特定の低レベルな状況でのみ使用されるべきです。
*   **スライス (Slices)**: Go言語の組み込み型で、配列の一部を参照する動的なビューです。C言語のポインタと長さの組み合わせ（例: `(pointer, length)`）に代わる、より安全でGoらしいデータ構造です。スライスは、基になる配列への参照、長さ、容量を持ちます。
*   **`:=` 演算子**: Go言語の短縮変数宣言演算子です。変数の宣言と初期化を同時に行い、型推論を利用できます。これにより、コードが簡潔になります。
*   **`sigprof`**: シグナルプロファイリングの略で、GoランタイムがCPUプロファイリングのために使用するメカニズムの一部です。通常、`SIGPROF`シグナル（Unix系システム）が定期的にプロセスに送信され、そのシグナルハンドラ内で現在の実行スタックが収集されます。
*   **`gentraceback`**: Goランタイム内部の関数で、現在のゴルーチンのスタックトレースを収集するために使用されます。これは、デバッグ、プロファイリング、パニック時のスタックダンプなど、様々な場面で利用されます。
*   **`callers` / `gcallers`**: `runtime`パッケージ内の関数で、現在のゴルーチンまたは指定されたゴルーチンの呼び出しスタック（コールスタック）を取得するために使用されます。これらの関数は、`gentraceback`を内部的に呼び出します。

## 技術的詳細

このコミットは、GoランタイムのCPUプロファイリングサブシステムにおける複数の技術的な改善を含んでいます。

1.  **型の統一と簡素化**:
    *   `cpuprofEntry`構造体の`depth`フィールドが`uintptr`から`int`に変更されました。`depth`はスタックフレームの深さ、つまり要素数を表すため、`int`がより適切です。
    *   `cpuProfile`構造体の`nlog`フィールドも同様に`uintptr`から`int`に変更されました。これもログエントリの数を表すためです。
    *   これにより、`len(pc)`（スライスの長さは`int`を返す）との比較や代入において、不要な型変換（例: `uintptr(len(pc))`）が削減され、コードがより自然で読みやすくなりました。

2.  **スライスの活用**:
    *   `cpuproftick`関数が削除され、そのロジックが`cpuProfile.add`メソッドに統合されました。
    *   `cpuProfile.add`メソッドの引数が、従来のCスタイルに近いポインタと長さの組み合わせ（`pc *uintptr, n int32`）から、Goのスライス（`pc []uintptr`）に変更されました。これにより、スタックトレースの処理がより安全でGoらしい方法で行われるようになりました。
    *   `callers`および`gcallers`関数のシグネチャも変更され、`*uintptr, m int`の代わりに`[]uintptr`を直接受け取るようになりました。これにより、呼び出し元でスライスを渡すだけでよくなり、ポインタと長さの管理が不要になります。

3.  **スタックフレーム収集の最適化**:
    *   `sigprof`関数内で`gentraceback`を呼び出す際に、収集するスタックフレームの数を`maxCPUProfStack`に制限するロジックが追加されました。具体的には、`stk`スライスを`stk[:n]`のようにスライス式で渡すことで、`gentraceback`が`maxCPUProfStack`を超えるフレームを収集しないようにしています。
    *   これにより、プロファイリング時に必要以上のスタック情報を収集するオーバーヘッドが削減され、パフォーマンスがわずかに向上する可能性があります。

4.  **`:=` 演算子の積極的な使用**:
    *   コード全体で、変数の宣言と初期化に`var`キーワードと代入を分けて行う代わりに、`:=`演算子が積極的に使用されています。これにより、コードの行数が減り、簡潔さが増しています。例えば、`sigprof`関数内の`traceback`変数の宣言が`var traceback bool`から`traceback := true`に変更されています。

これらの変更は、Goランタイムの低レベルな部分におけるコード品質の向上に貢献し、将来的な開発の基盤を強化するものです。

## コアとなるコードの解説

以下に、特に重要な変更箇所のコードと解説を示します。

### `src/runtime/cpuprof.go` における `depth` および `nlog` の型変更

```go
// 変更前:
type cpuprofEntry struct {
	count uintptr
	depth uintptr // uintptr
	stack [maxCPUProfStack]uintptr
}

type cpuProfile struct {
	// ...
	nlog    uintptr // uintptr
	// ...
}

// 変更後:
type cpuprofEntry struct {
	count uintptr
	depth int // int
	stack [maxCPUProfStack]uintptr
}

type cpuProfile struct {
	// ...
	nlog    int // int
	// ...
}
```
**解説**: `depth`はスタックの深さ（フレーム数）、`nlog`はログエントリの数を表します。これらは本質的に「数」であり、メモリのアドレスを指す`uintptr`よりも、一般的な整数を表す`int`型が適切です。この変更により、`len(pc)`（スライスの長さは`int`を返す）との比較や代入時に発生していた不要な`uintptr()`への型変換が不要になり、コードがより自然で読みやすくなりました。

### `src/runtime/cpuprof.go` における `cpuProfile.add` メソッドの変更

```go
// 変更前 (cpuproftick 関数):
// func cpuproftick(pc *uintptr, n int32) {
// 	if n > maxCPUProfStack {
// 		n = maxCPUProfStack
// 	}
// 	s := (*[maxCPUProfStack]uintptr)(unsafe.Pointer(pc))[:n]
// 	cpuprof.add(s)
// }

// 変更後 (cpuProfile.add メソッド):
func (p *cpuProfile) add(pc []uintptr) {
	if len(pc) > maxCPUProfStack {
		pc = pc[:maxCPUProfStack] // スライスを制限
	}
	// ... 既存のロジック ...
	// e.depth = uintptr(len(pc)) // 変更前
	e.depth = len(pc) // 変更後
	// ...
}
```
**解説**: 従来の`cpuproftick`関数は、C言語のようなポインタと長さの組み合わせでスタックトレースを受け取っていました。この変更により、`cpuProfile.add`メソッドが直接Goのスライス`[]uintptr`を受け取るようになりました。また、`maxCPUProfStack`を超えるスタックフレームが渡された場合でも、`pc = pc[:maxCPUProfStack]`というスライス式を使って、Goのイディオムに沿って安全かつ簡潔にスライスを必要な長さに制限しています。これにより、コードの安全性と可読性が向上しています。

### `src/runtime/proc1.go` における `sigprof` 関数の変更

```go
// 変更前:
// func sigprof(pc *uint8, sp *uint8, lr *uint8, gp *g, mp *m) {
// 	var n int32
// 	var traceback bool
// 	var stk [100]uintptr
// 	// ...
// 	n = int32(gentraceback(uintptr(unsafe.Pointer(pc)), uintptr(unsafe.Pointer(sp)), uintptr(unsafe.Pointer(lr)), gp, 0, &stk[0], len(stk), nil, nil, _TraceTrap))
// 	// ...
// 	cpuproftick(&stk[0], n)
// }

// 変更後:
func sigprof(pc, sp, lr uintptr, gp *g, mp *m) {
	// ...
	traceback := true // := 演算子を使用
	// ...
	var stk [maxCPUProfStack]uintptr // スタック配列のサイズを maxCPUProfStack に変更
	n := gentraceback(pc, sp, lr, gp, 0, &stk[0], len(stk), nil, nil, _TraceTrap) // n の型が int になり、int32() へのキャストが不要に
	// ...
	cpuprof.add(stk[:n]) // cpuprof.add にスライスを渡す
}
```
**解説**:
*   `sigprof`関数の引数`pc`, `sp`, `lr`が`*uint8`から`uintptr`に直接変更されました。これにより、関数呼び出し側での`unsafe.Pointer`を介した煩雑な型変換が不要になり、コードが簡潔になりました。
*   `traceback`変数の宣言に`:=`演算子が使用され、Goらしい記述になっています。
*   `stk`配列のサイズが`maxCPUProfStack`に固定され、`gentraceback`の呼び出しで`len(stk)`が使用されることで、収集されるスタックフレーム数が`maxCPUProfStack`に制限されるようになりました。
*   `cpuproftick`の呼び出しが`cpuprof.add(stk[:n])`に変更され、`cpuprof.add`がスライスを直接受け取るようになったため、よりGoらしい方法でスタックトレースが処理されるようになりました。

### `src/runtime/extern.go` および `src/runtime/traceback.go` における `callers` / `gcallers` の変更

```go
// 変更前 (extern.go):
// func Callers(skip int, pc []uintptr) int {
// 	// ...
// 	return callers(skip, &pc[0], len(pc))
// }

// 変更後 (extern.go):
func Callers(skip int, pc []uintptr) int {
	// ...
	return callers(skip, pc) // スライスを直接渡す
}

// 変更前 (traceback.go):
// func callers(skip int, pcbuf *uintptr, m int) int {
// 	// ...
// 	n = gentraceback(pc, sp, 0, getg(), skip, pcbuf, m, nil, nil, 0)
// }

// 変更後 (traceback.go):
func callers(skip int, pcbuf []uintptr) int { // pcbuf がスライスに
	// ...
	n = gentraceback(pc, sp, 0, getg(), skip, &pcbuf[0], len(pcbuf), nil, nil, 0) // gentraceback にはポインタと長さを渡す
}
```
**解説**: `callers`および`gcallers`関数は、外部から呼び出される際にスライス`[]uintptr`を直接受け取るように変更されました。これにより、呼び出し元はポインタと長さのペアを管理する必要がなくなり、Goのスライスの利便性を享受できます。ただし、`callers`関数内部から`gentraceback`を呼び出す際には、`gentraceback`がまだポインタと長さを期待するため、`&pcbuf[0]`と`len(pcbuf)`を渡す形が維持されています。これは、`gentraceback`がより低レベルな操作を行うためと考えられます。

これらの変更は、GoランタイムのCPUプロファイリングコードをより現代的で、Goのイディオムに沿ったものにし、可読性と保守性を大幅に向上させています。

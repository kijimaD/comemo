# [インデックス 20925] ファイルの概要

このコミットは、Go言語の`go get`コマンドに`-f`（force/fork）フラグを追加するものです。これにより、`go get -u`（アップデート）実行時に、インポートパスが示すリモートリポジトリと実際にチェックアウトされたリポジトリのパスが一致するかどうかの検証をスキップできるようになります。これは、特に元のリポジトリのローカルフォークを使用している場合に有用です。

## 元コミット内容

このコミットは、`go get`コマンドに`-f`フラグを追加します。以前の`go get -u`コマンドは、リモートリポジトリのパスがインポートパスによって予測されるものと一致するかどうかを検証するようになりました。これは、例えば`rsc.io/pdf`のようなリダイレクトが変更された場合に重要です。しかし、一部のユーザーは非標準のリモートリポジトリを使用する正当な理由があるため、その場合にこの検証を強制的にスキップするための`-f`フラグが導入されました。`-f`は「force（強制）」または「fork（フォーク）」を意味します。この変更は、Goの内部課題トラッカーのIssue #8850を修正します。

## 変更の背景

Goのパッケージ管理ツールである`go get`は、指定されたインポートパスに基づいてリモートリポジトリからソースコードを取得し、ビルド・インストールを行います。Goのインポートパスは、通常、そのパッケージのソースコードがどこから取得されるべきかを暗黙的に示しています（例: `github.com/user/repo`）。

このコミットが導入される以前、または導入と同時期に、`go get -u`（アップデート）コマンドの動作が変更され、インポートパスから予測されるリモートリポジトリのURLと、実際にローカルにチェックアウトされているリポジトリのURLが一致するかどうかの検証が追加されました。この検証は、以下のようなシナリオで重要となります。

1.  **リダイレクトの変更への対応**: `rsc.io/pdf`のようなカスタムドメインを使用している場合、そのドメインが指す実際のGit/Mercurial/SVNリポジトリのURLは時間とともに変更される可能性があります。`go get -u`がこの変更を検知し、古いリポジトリからアップデートしようとするのを防ぐために、検証が必要でした。
2.  **セキュリティの向上**: 悪意のあるユーザーが、正規のインポートパスを装って異なるリポジトリに誘導し、不正なコードをダウンロードさせるような攻撃を防ぐためにも、この検証は有効です。

しかし、この厳格な検証は、特定の開発ワークフローにおいて問題を引き起こす可能性がありました。特に、以下のようなケースです。

*   **ローカルフォークの使用**: 開発者が公式リポジトリをフォークし、そのフォークに対して変更を加え、ローカルでテストしている場合。このフォークは、元のインポートパスとは異なるリモートURLを持つことがあります。
*   **プライベートリポジトリやミラーの使用**: 企業内での開発など、プライベートなGitサーバーやミラーリポジトリを使用している場合、それらのURLは公開されているインポートパスとは異なる場合があります。

このような「非標準のリモートリポジトリ」を使用している場合、`go get -u`が常に検証エラーを発生させ、アップデートを妨げてしまうことになります。この問題を解決し、開発者に柔軟性を提供するために、この検証を意図的にスキップする手段として`-f`フラグが導入されました。これにより、ユーザーは自身の判断で非標準のリポジトリからのアップデートを強制できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびバージョン管理システムに関する基本的な知識が必要です。

1.  **`go get`コマンド**:
    *   Go言語の公式ツールチェーンの一部であり、リモートリポジトリからGoパッケージのソースコードをダウンロードし、依存関係を解決し、必要に応じてビルド・インストールを行うコマンドです。
    *   `go get <import-path>`: 指定されたインポートパスのパッケージをダウンロード・インストールします。
    *   `go get -u`: 既にダウンロードされているパッケージとその依存関係を最新バージョンにアップデートします。
    *   **インポートパス**: Goのパッケージは、`github.com/user/repo/package`のようなパスで識別されます。このパスは、通常、そのパッケージのソースコードがどこにあるか（どのバージョン管理システムのリポジトリのどのパスにあるか）を示しています。`go get`は、このインポートパスを解析して、適切なリポジトリを特定し、クローンまたはフェッチを行います。

2.  **バージョン管理システム (VCS)**:
    *   Git, Mercurial (hg), Subversion (svn) など、ソースコードの変更履歴を管理するためのシステムです。`go get`はこれらのVCSと連携して動作します。
    *   `go get`は、インポートパスからVCSの種類（Git, hgなど）とリモートリポジトリのURLを推測し、それを使ってソースコードをダウンロードします。

3.  **リモートリポジトリのURLとローカルリポジトリの関連**:
    *   VCSでは、ローカルにクローンされたリポジトリは、通常、その元となったリモートリポジトリのURL（`origin`などとして設定される）を記憶しています。
    *   `go get -u`が検証を行うのは、このローカルリポジトリが記憶しているリモートURLが、現在のインポートパスから予測されるURLと一致するかどうかです。

4.  **フォーク (Fork)**:
    *   Gitなどの分散型VCSにおいて、既存のリポジトリのコピーを自分のアカウント下に作成することです。これにより、元のリポジトリに影響を与えることなく、自由にコードを変更・実験できます。
    *   フォークされたリポジトリは、元のリポジトリとは異なるURLを持つため、`go get -u`の検証に引っかかる可能性があります。

## 技術的詳細

このコミットの技術的な変更点は、主に`go get`コマンドのフラグ解析と、パッケージのダウンロードロジックにおけるリモートリポジトリの検証部分にあります。

1.  **`-f`フラグの追加**:
    *   `cmd/go/get.go`ファイルにおいて、`cmdGet.Flag.Bool("f", false, "")`として新しいブール型フラグ`getF`が追加されました。これにより、コマンドラインで`-f`オプションが指定されたかどうかをプログラム内で判定できるようになります。
    *   `UsageLine`にも`-f`が追加され、ユーザーがヘルプメッセージでこのフラグの存在を確認できるようになりました。
    *   `-f`フラグは`-u`フラグが設定されている場合にのみ有効です。もし`-u`なしで`-f`が指定された場合、`fatalf("go get: cannot use -f flag without -u")`というエラーメッセージを出力して終了するロジックが追加されています。これは、`-f`が「アップデート時の検証スキップ」という特定の目的のために設計されているためです。

2.  **リモートリポジトリ検証の条件付きスキップ**:
    *   `downloadPackage`関数内で、リモートリポジトリの検証ロジックが変更されました。
    *   変更前は、`*getU && vcs.remoteRepo != nil`という条件で検証が実行されていました。これは、「`-u`フラグが指定されており、かつリモートリポジトリが存在する場合」に検証を行うことを意味します。
    *   変更後は、この条件が`*getU && vcs.remoteRepo != nil && !*getF`となりました。これにより、「`-u`フラグが指定されており、かつリモートリポジトリが存在し、**かつ`-f`フラグが指定されていない場合**」にのみ検証が実行されるようになります。
    *   つまり、`-f`フラグが指定されていれば、`go get -u`はリモートリポジトリのパスがインポートパスと一致するかどうかのチェックをスキップするようになります。

3.  **テストの追加**:
    *   `src/cmd/go/test.bash`に新しいテストケースが追加されました。このテストは、`go get -d -f -u`コマンドが、意図的に間違ったリモートリポジトリURLを持つパッケージに対しても成功することを確認します。
    *   具体的には、`GOPATH=$d ./testgo get -d -f -u $url`を実行し、エラーが出ないことを確認します。もしエラーが出た場合、それが「validating server certificate」や「not found」といった正当なエラーではないことを確認し、それ以外の場合はテストを失敗させます。これにより、`-f`フラグが期待通りに検証をスキップし、非標準のリポジトリからの取得を許可することを確認しています。

### `src/cmd/go/test.bash`

```bash
# ... (既存のテストコード)

if GOPATH=$d ./testgo get -d -f -u $url 2>$d/err; then
	echo "go get -d -u $url succeeded with wrong remote repo"
	cat $d/err
	ok=false
elif ! egrep -i 'validating server certificate|not found' $d/err >/dev/null; then
	echo "go get -d -f -u $url failed for wrong reason"
	cat $d/err
	ok=false
fi
# ... (テストのクリーンアップ)
```

このシェルスクリプトのテストは、`-f`フラグが期待通りに機能することを確認します。
1.  `GOPATH=$d ./testgo get -d -f -u $url 2>$d/err`: テスト用のGOPATHを設定し、`-d`（ダウンロードのみ）、`-f`（強制）、`-u`（アップデート）フラグを付けて`go get`を実行します。`$url`は、通常のリモートリポジトリとは異なるURLを持つように設定されたテスト用のパッケージを指します。
2.  `if ...; then echo "go get -d -u $url succeeded with wrong remote repo" ...`: この`if`ブロックは、`go get`コマンドが成功した場合（つまり、`-f`フラグによって検証がスキップされ、非標準のリポジトリからでもダウンロードが成功した場合）に実行されます。これは期待される動作です。
3.  `elif ! egrep -i 'validating server certificate|not found' $d/err >/dev/null; then ...`: もし`go get`が失敗した場合、そのエラーメッセージが「validating server certificate」や「not found」といった、ネットワークの問題やリポジトリの存在しないことによる正当なエラーではないことを確認します。もしそれ以外の理由で失敗した場合（例えば、`-f`フラグが機能せず、リモートリポジトリの不一致で失敗した場合）、テストは「failed for wrong reason」として失敗します。

このテストにより、`-f`フラグがリモートリポジトリの検証を正しく無効化し、非標準のリポジトリからのパッケージ取得を許可することが保証されます。

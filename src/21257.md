## 元コミット内容

`net/http` パッケージの `Response.Body` に関するドキュメントを更新し、キープアライブ接続との相互作用について記述を追加しました。これはIssue #5645を修正するものです。

## 変更の背景

Goの `net/http` クライアントは、HTTP/1.0およびHTTP/1.1プロトコルにおいて、TCP接続の再利用（キープアライブ）をサポートしています。しかし、この接続再利用が正しく機能するためには、クライアントがレスポンスボディを適切に処理する必要があります。具体的には、`http.Response` の `Body` フィールド（`io.ReadCloser` インターフェースを実装）を完全に読み込み、その後 `Close()` メソッドを呼び出すことが不可欠です。

過去には、開発者が `Response.Body` を完全に読み込まなかったり、`Close()` を呼び出さなかったりした場合に、キープアライブ接続が再利用されず、新しいTCP接続が確立されてしまうという問題が頻繁に発生していました。これは、リソースリーク（ファイルディスクリプタの枯渇など）やパフォーマンスの低下（TCPハンドシェイクのオーバーヘッド）につながる可能性がありました。

Issue #5645は、この挙動に関する混乱や誤解を解消するために提起されました。このコミットは、コードの動作を変更するのではなく、既存の動作に関するドキュメントを改善することで、開発者が `net/http` クライアントをより効果的に使用できるようにすることを目的としています。ドキュメントを明確にすることで、キープアライブ接続の恩恵を最大限に活用し、アプリケーションの効率と堅牢性を向上させることができます。

## 前提知識の解説

### HTTP キープアライブ (Persistent Connections)

HTTPキープアライブ（または持続的接続）は、単一のTCP接続上で複数のHTTPリクエストとレスポンスを交換することを可能にするメカニズムです。HTTP/1.0では `Connection: keep-alive` ヘッダによってオプトインされ、HTTP/1.1ではデフォルトで有効になっています。

**利点:**
*   **レイテンシの削減:** 各リクエストごとに新しいTCP接続を確立するための3ウェイハンドシェイクが不要になるため、特に多数の小さなリクエストを送信する場合に顕著なレイテンシ削減が期待できます。
*   **ネットワークリソースの効率化:** TCP接続の確立と終了にかかるオーバーヘッド（CPU、メモリ、ポートなど）が削減されます。
*   **輻輳制御の改善:** TCPの輻輳ウィンドウが維持されるため、データ転送がよりスムーズになります。

**動作原理:**
クライアントがサーバーにリクエストを送信し、サーバーがレスポンスを返した後も、TCP接続はすぐに閉じられず、一定時間開いたままになります。この間に同じクライアントから同じサーバーへの次のリクエストがあれば、既存の接続が再利用されます。

### Goの `net/http` パッケージと `Response.Body`

Goの標準ライブラリ `net/http` は、HTTPクライアントとサーバーの両方を提供します。クライアント側でHTTPリクエストを送信すると、`http.Response` 構造体が返されます。この構造体には、レスポンスボディを表す `Body` フィールドが含まれています。

`Body` フィールドは `io.ReadCloser` インターフェース型です。これは、`Read(p []byte) (n int, err error)` メソッドと `Close() error` メソッドを持つことを意味します。

*   **`Read()`:** レスポンスボディのデータを読み込むために使用されます。
*   **`Close()`:** レスポンスボディに関連付けられたリソースを解放するために使用されます。これは、基になるTCP接続を再利用可能にするために非常に重要です。

**重要な注意点:**
`Response.Body` はストリームとして扱われます。つまり、データを一度にすべてメモリに読み込むのではなく、必要に応じて少しずつ読み込むことができます。しかし、キープアライブ接続を再利用するためには、このストリームを完全に読み込むか、少なくとも `Close()` を呼び出して、基になる接続が次のリクエストのために解放されることを保証する必要があります。もしボディが完全に読み込まれずに `Close()` が呼び出された場合、`net/http` の `Transport` は残りのデータを破棄し、接続を再利用可能な状態にします。しかし、`Close()` が呼び出されないと、接続は解放されず、再利用されません。

## 技術的詳細

このコミットは、`http.Response` 構造体の `Body` フィールドのコメントに、キープアライブ接続の再利用に関する具体的な条件を追加しています。変更前は、単に「呼び出し元がBodyを閉じる責任がある」とだけ記載されていました。しかし、この記述だけでは、なぜ `Body` を閉じることが重要なのか、特にキープアライブ接続の文脈でどのような影響があるのかが不明確でした。

追加されたドキュメントは、以下の重要な点を明確にしています。

1.  **接続再利用の条件:** デフォルトのHTTPクライアントの `Transport` は、HTTP/1.0またはHTTP/1.1のTCP接続（キープアライブ）を再利用しようとしません。
2.  **再利用を可能にする条件:** 接続が再利用されるのは、`Body` が**完全に読み込まれ** (`Read` to completion)、**閉じられた** (`Close`) 場合のみです。

このドキュメントの追加は、`net/http` パッケージの内部実装が、レスポンスボディの読み込み状況に基づいて接続の再利用を決定しているという事実を反映しています。`Transport` は、レスポンスボディのストリームが完全に消費されたか、または `Close()` が呼び出されたことを検出すると、その接続を接続プールに戻し、後続のリクエストで再利用できるようにします。もしボディが完全に読み込まれずに `Close()` が呼び出されなかった場合、`Transport` はその接続がまだ使用中であると判断し、プールに戻しません。結果として、新しい接続が確立されることになります。

この挙動は、特に大きなレスポンスボディを持つリクエストや、エラーが発生してボディの読み込みが途中で中断されるようなシナリオで重要になります。開発者は、どのような場合でも `defer resp.Body.Close()` を使用して `Body` を閉じる習慣を身につけるべきです。さらに、キープアライブの恩恵を最大限に受けるためには、`io.Copy(ioutil.Discard, resp.Body)` のようにしてボディを完全に読み捨てるか、必要なデータをすべて読み込む必要があります。

## コアとなるコードの変更箇所

変更は `src/net/http/response.go` ファイルの `Response` 構造体内の `Body` フィールドのコメントにあります。


## コアとなるコードの解説

変更された行は、`Response` 構造体の `Body` フィールドのドキュメントに、以下の3行を追加しています。

```go
// close Body. The default HTTP client's Transport does not
// attempt to reuse HTTP/1.0 or HTTP/1.1 TCP connections
// ("keep-alive") unless the Body is read to completion and is
// closed.
```

この追加により、`Body` を閉じることの重要性が、単なるリソース解放だけでなく、HTTPキープアライブ接続の再利用という具体的なパフォーマンス上の利点と結びつけられました。

*   `The default HTTP client's Transport does not attempt to reuse HTTP/1.0 or HTTP/1.1 TCP connections ("keep-alive")`: これは、Goの `net/http` クライアントが、デフォルトではキープアライブ接続を再利用しないという前提条件を述べています。
*   `unless the Body is read to completion and is closed.`: この部分が最も重要で、キープアライブ接続が再利用されるための具体的な条件を明示しています。つまり、`Response.Body` を完全に読み込み（`Read` メソッドでEOFまで読み進める）、その後 `Close()` メソッドを呼び出す必要があるということです。

このドキュメントの追加は、Goの `net/http` パッケージを使用する開発者にとって、接続管理とパフォーマンス最適化に関する重要なガイドラインとなります。これにより、開発者は意図せず新しいTCP接続を確立し続けることによるオーバーヘッドを回避し、アプリケーションの効率を向上させることができます。

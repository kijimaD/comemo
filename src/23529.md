# [インデックス 23529] ファイルの概要

このコミットは、Go言語のツールチェインにおいて長らく使用されてきた「アーキテクチャレター（architecture letter）」という概念を廃止し、ファイル命名規則や公開APIを簡素化・統一することを目的としています。具体的には、アーキテクチャに依存するツール名（例: `6g`、`8l`）やオブジェクトファイル名（例: `source.6`）を廃止し、それぞれ`go tool compile`、`go tool link`、`source.o`といった汎用的な名前に統一します。また、`go env`コマンドの出力から`GOCHAR`環境変数を削除し、`go/build.ArchChar`関数が常にエラーを返すように変更することで、この概念がGoユーザーから完全に隠蔽されます。

## 変更の背景
このコミットは、Goツールチェインにおける「アーキテクチャレター（architecture letter）」という概念を廃止することを目的としています。Goの初期のバージョンでは、各CPUアーキテクチャ（例: `amd64`, `386`, `arm`）は、それぞれ一文字の識別子（例: `6`, `8`, `5`）で表されていました。これは、コンパイラやリンカのツール名（例: `6g`、`8l`）や、生成されるオブジェクトファイルの名前（例: `source.6`）に利用されていました。

しかし、このアーキテクチャレターは、Goのツールチェインが進化し、より多くのアーキテクチャをサポートするにつれて、その有用性が薄れ、むしろ混乱を招く要因となっていました。特に、新しいアーキテクチャが追加されるたびに新しいレターを割り当てる必要があり、その規則性も一貫していませんでした。このコミットは、ユーザーから見える範囲でこのレターの概念を完全に排除し、ツールチェインの命名規則とファイル出力形式を簡素化・統一することを目指しています。これにより、Goのビルドシステムがより直感的で、将来の拡張にも対応しやすくなります。この変更は、Go 1.5で導入されたセルフホスト型コンパイラ（Go自身でGoコンパイラをコンパイルする）の実現に向けた重要なステップの一つでもあります。

## 前提知識の解説

### Goのツールチェインとビルドプロセス
Go言語のプログラムは、`go build`コマンドによってコンパイル・リンクされます。この裏側では、`go tool`コマンドを通じて、アセンブラ（`asm`）、コンパイラ（`compile`）、リンカ（`link`）などの低レベルツールが呼び出されています。これらのツールは、Goソースコードを機械語に変換し、実行可能なバイナリを生成する役割を担っています。

### アーキテクチャレターの歴史
Goの初期のバージョン（Go 1.4以前）では、各CPUアーキテクチャは以下のような一文字の「アーキテクチャレター」で識別されていました。
*   `386` (x86 32-bit) -> `8`
*   `amd64` (x86 64-bit) -> `6`
*   `arm` (ARM 32-bit) -> `5`
*   `arm64` (ARM 64-bit) -> `7` (Go 1.5で導入)
*   `ppc64`, `ppc64le` (PowerPC 64-bit) -> `9` (Go 1.5で導入)

このレターは、以下の用途で使われていました。
1.  **ツール名**: コンパイラは`6g`（amd64用）、`8g`（386用）、リンカは`6l`、`8l`といった形で、アーキテクチャレターが接頭辞として付与されていました。
2.  **オブジェクトファイル名**: Goソースファイル（例: `main.go`）をコンパイルすると、中間オブジェクトファイルとして`main.6`や`main.8`といった名前のファイルが生成されていました。
3.  **`go env`出力**: `GOCHAR`という環境変数として、現在のターゲットアーキテクチャのレターが出力されていました。
4.  **`go/build.ArchChar`関数**: `go/build`パッケージ内の`ArchChar`関数は、`GOARCH`文字列（例: "amd64"）を受け取り、対応するアーキテクチャレター（例: "6"）を返す役割を担っていました。

### 廃止の理由
このアーキテクチャレターのシステムは、Goがサポートするアーキテクチャが増えるにつれて、いくつかの問題を引き起こしました。
*   **命名の一貫性の欠如**: 新しいアーキテクチャが追加されるたびに、新しいレターを割り当てる必要がありましたが、その割り当て規則は必ずしも直感的ではありませんでした。例えば、`arm64`が`7`、`ppc64`が`9`といった具合で、数字とアーキテクチャの間に明確な関連性はありませんでした。
*   **ユーザーの混乱**: ユーザーは、`6g`や`8l`といったツール名が何を意味するのかを理解するために、このレターの対応関係を覚える必要がありました。これは、特にGoを学び始めたばかりのユーザーにとって障壁となっていました。
*   **内部実装の複雑さ**: ツールチェインの内部でも、このレターに基づいてパスを構築したり、条件分岐を行ったりする必要があり、コードの可読性や保守性を低下させていました。例えば、ビルドスクリプトでは、ターゲットアーキテクチャに応じて適切なツール名を選択するロジックが必要でした。

このコミットは、これらの問題を解決し、Goツールチェインをよりシンプルでモダンなものにするための重要な一歩です。

## 技術的詳細

このコミットの主要な技術的変更は、Goツールチェイン全体から「アーキテクチャレター」の概念を排除し、より汎用的な命名規則とAPIに移行することです。

1.  **ツール名の統一**:
    *   以前は`6g`（amd64コンパイラ）、`8g`（386コンパイラ）のようにアーキテクチャレターを含むツール名が使われていましたが、Go 1.5からは`go tool compile`、`go tool asm`、`go tool link`のように、アーキテクチャに依存しない統一されたコマンド名が使用されるようになりました。
    *   これにより、`src/cmd/dist/build.go`内のビルドスクリプトから、`gochars`変数や`gohostchar`、`gochar`といったアーキテクチャレター関連の変数が削除されています。`src/cmd/compile/internal/gc/mkbuiltin.go`でも、`gochar+"g"`のようなツール呼び出しが`"compile"`に置き換えられています。

2.  **オブジェクトファイル名の標準化**:
    *   中間オブジェクトファイルは、以前は`source.6`や`source.8`のようにアーキテクチャレターを含む拡張子を持っていましたが、この変更により、すべてのアーキテクチャで`.o`という標準的な拡張子（例: `source.o`）が使用されるようになりました。
    *   これは、`src/cmd/asm/internal/flags/flags.go`、`src/cmd/compile/internal/gc/lex.go`、`src/cmd/compile/internal/gc/obj.go`、`src/cmd/go/build.go`、`src/go/internal/gcimporter/gcimporter.go`など、多くのファイルでファイルパスの構築ロジックが変更されている箇所から確認できます。特に、`fmt.Sprintf("%s.%c", input, theChar)`のような形式が`fmt.Sprintf("%s.o", input)`に置き換えられています。

3.  **`go env`からの`GOCHAR`の削除**:
    *   `go env`コマンドの出力から、`GOCHAR`環境変数が削除されました。これは、`src/cmd/go/env.go`の変更によって実現されています。この変数は、アーキテクチャレターの概念が廃止されたため、もはや意味を持たなくなりました。

4.  **`go/build.ArchChar`の廃止**:
    *   `src/go/build/build.go`内の`ArchChar`関数は、以前は`GOARCH`文字列から対応するアーキテクチャレターを返していましたが、このコミット以降は常にエラーを返すようになりました。関数のドキュメントも更新され、この関数がもはや使用されないことが明記されています。これは、このAPIが公開されていたため、互換性を保ちつつ廃止を明確にするための措置です。

5.  **テストコードの更新**:
    *   `doc/go1.5.txt`には、Go 1.5の変更点として、新しいツール名とデフォルトの出力ファイル名（`file.o`と`a.out`）が記載されています。
    *   `test/bench/shootout/timing.sh`や`test/fixedbugs/*.go`、`test/run.go`などのテストスクリプトやテストケースも、新しい命名規則とツール呼び出しに合わせて更新されています。例えば、`$O.$EXE`のような変数参照が`a.$EXE`や`a.out`に、`hello.6`のようなファイル名が`hello.o`に置き換えられています。

これらの変更は、Goツールチェインの内部構造を簡素化し、ユーザーエクスペリエンスを向上させることを目的としています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなる変更は、主に以下のファイルに見られます。

1.  **`src/go/build/build.go`**:
    *   `ArchChar`関数の実装が大幅に変更され、特定のアーキテクチャレターを返す代わりに、常にエラーを返すようになりました。
    *   変更前:
        ```go
        func ArchChar(goarch string) (string, error) {
            switch goarch {
            case "386":
                return "8", nil
            case "amd64", "amd64p32":
                return "6", nil
            // ... (他のアーキテクチャ)
            }
            return "", errors.New("unsupported GOARCH " + goarch)
        }
        ```
    *   変更後:
        ```go
        func ArchChar(goarch string) (string, error) {
            return "", errors.New("architecture letter no longer used")
        }
        ```
    *   この変更は、アーキテクチャレターが公開APIから完全に削除されたことを示しています。

2.  **`src/cmd/go/env.go`**:
    *   `mkEnv`関数内で`GOCHAR`環境変数を`go env`の出力に追加するロジックが削除されました。
    *   変更前:
        ```go
        if archCharErr == nil {
            env = append(env, envVar{"GOCHAR", archChar()})
        }
        ```
    *   変更後:
        ```go
        // 関連する行が削除
        ```
    *   これにより、ユーザーは`go env`を通じて`GOCHAR`を取得できなくなります。

3.  **`src/cmd/asm/internal/flags/flags.go`**:
    *   `Parse`関数のシグネチャが変更され、`theChar`引数が削除されました。
    *   出力ファイル名の生成ロジックが`fmt.Sprintf("%s.%c", input, theChar)`から`fmt.Sprintf("%s.o", input)`に変更されました。
    *   変更前:
        ```go
        func Parse(theChar int) {
            // ...
            *OutputFile = fmt.Sprintf("%s.%c", input, theChar)
        }
        ```
    *   変更後:
        ```go
        func Parse() {
            // ...
            *OutputFile = fmt.Sprintf("%s.o", input)
        }
        ```
    *   これは、アセンブラが生成するオブジェクトファイルの命名規則が統一されたことを示します。

4.  **`src/cmd/compile/internal/gc/lex.go`**:
    *   パッケージファイルの検索ロジックにおいて、アーキテクチャレターを含むファイル名（例: `name.6`）の代わりに、`.o`拡張子を持つファイル名（例: `name.o`）を優先的に探すように変更されました。
    *   `fmt.Sprintf("%s.%c", name, Thearch.Thechar)`のような記述が`fmt.Sprintf("%s.o", name)`に置き換えられています。

5.  **`src/cmd/dist/build.go`**:
    *   `gochars`、`gohostchar`、`gochar`といったアーキテクチャレターに関連する変数の定義と使用が削除されました。
    *   ビルドプロセスにおけるファイル名の生成やツール呼び出しのロジックが、アーキテクチャレターに依存しない形に修正されました。

これらの変更は、Goツールチェインのビルドシステムと公開APIからアーキテクチャレターの概念を体系的に排除していることを示しています。

## コアとなるコードの解説

このコミットの核心は、Goツールチェインの内部および外部インターフェースから、長らく使われてきた「アーキテクチャレター」という概念を完全に排除することにあります。

### `src/go/build/build.go` の `ArchChar` 関数
この関数は、Goのビルドシステムが特定のアーキテクチャ（例: `amd64`）に対応する一文字の識別子（例: `6`）を取得するために提供されていました。しかし、このコミットにより、この関数はもはや有効なアーキテクチャレターを返さず、代わりに`errors.New("architecture letter no longer used")`というエラーを返すようになりました。これは、この概念がGoの公開APIから正式に廃止されたことを意味します。この変更は、`go/build`パッケージを利用する外部ツールやライブラリに対して、アーキテクチャレターに依存しないように促す明確なシグナルとなります。

### `src/cmd/go/env.go` からの `GOCHAR` 削除
`go env`コマンドは、Goの環境設定に関する情報を提供するもので、以前は`GOCHAR`という変数を通じて現在のターゲットアーキテクチャのレターを出力していました。この変数の削除は、アーキテクチャレターが環境設定の一部としてユーザーに公開されるべきではないという判断に基づいています。これにより、ユーザーはアーキテクチャレターの存在を意識する必要がなくなり、Goの環境設定がよりシンプルになります。

### `src/cmd/asm/internal/flags/flags.go` および `src/cmd/compile/internal/gc/lex.go` におけるファイル命名規則の変更
Goのアセンブラ（`asm`）やコンパイラ（`compile`）は、ソースコードを中間オブジェクトファイルに変換します。以前は、これらのオブジェクトファイルは`source.6`や`source.8`のように、アーキテクチャレターを拡張子として含んでいました。このコミットでは、この命名規則が`source.o`という統一された形式に変更されました。
*   `src/cmd/asm/internal/flags/flags.go`では、`Parse`関数が`theChar`引数を受け取らなくなり、出力ファイル名が常に`.o`拡張子を持つように変更されました。
*   `src/cmd/compile/internal/gc/lex.go`では、パッケージのインポート時に検索するファイル名が、アーキテクチャレターを含む形式から`.o`拡張子を持つ形式へと変更されました。
この変更により、ビルドシステム全体でオブジェクトファイルの取り扱いが一貫し、特定のアーキテクチャに依存しないパス解決が可能になります。

### `src/cmd/dist/build.go` におけるビルドロジックの簡素化
`src/cmd/dist/build.go`はGoツールチェインのビルドプロセスを管理する重要なスクリプトです。このファイルから`gochars`、`gohostchar`、`gochar`といったアーキテクチャレターに関連する変数が削除されたことは、ビルドシステムがこれらのレターに依存しなくなったことを明確に示しています。これにより、ビルドスクリプトの複雑性が軽減され、新しいアーキテクチャの追加や既存アーキテクチャの変更が容易になります。

これらの変更は、Goツールチェインの内部実装をクリーンアップし、ユーザーがGoをより簡単に、そして直感的に利用できるようにするための基盤を強化するものです。Go 1.5で導入されたセルフホスト型コンパイラへの移行と密接に関連しており、ツールチェインのモジュール化と将来の拡張性を高める上で不可欠なステップでした。

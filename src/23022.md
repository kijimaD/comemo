## 元コミット内容

このコミットの目的は、Goのコンパイラおよびリンカの内部コードベース (`cmd/internal`) における `fmt.Sprintf` の使用を整理し、より効率的な文字列変換手法に置き換えることです。コミットメッセージの "C->Go printf cleanup" は、Goの内部ツールがC言語のコードベースから移植された際に残った `printf` スタイルの文字列フォーマットの慣習を、よりGoらしい、かつパフォーマンスに優れた方法に改善するという意図を示しています。具体的には、不要な一時バッファの削除や、数値から文字列への変換に特化した `strconv.Itoa` や `fmt.Sprint` の利用への切り替えが含まれます。

## 変更の背景

Goの `fmt.Sprintf` 関数は非常に柔軟で便利ですが、その柔軟性ゆえに、シンプルな数値変換など、より特化した関数で済む場合でも使用されることがあります。`fmt.Sprintf` は内部的にフォーマット文字列の解析や、可変引数の処理、そして結果文字列のためのメモリ割り当てを行うため、オーバーヘッドが発生します。特に、コンパイラやリンカのようなパフォーマンスが重視されるツールでは、このような小さなオーバーヘッドが積み重なると無視できない影響を与える可能性があります。

このコミットの背景には、以下の点が考えられます。

1.  **パフォーマンスの最適化**: `fmt.Sprintf` の代わりに `strconv.Itoa` や `fmt.Sprint` を使用することで、数値から文字列への変換がより高速に行われます。`strconv.Itoa` は整数を文字列に変換する専用の関数であり、`fmt.Sprint` は引数をスペースで区切って文字列に変換するシンプルな関数です。これらは `fmt.Sprintf` のような汎用的なフォーマット処理を必要としないため、より効率的です。
2.  **メモリ割り当ての削減**: `fmt.Sprintf` は結果の文字列を格納するために新しいメモリを割り当てることがよくあります。特に、以前のコードでは `lexname_buf` や `typekind_buf`、`headstr_buf` のようなグローバルな文字列バッファを再利用していましたが、これはスレッドセーフティの問題や、意図しないデータ競合を引き起こす可能性がありました。このコミットでは、これらのバッファを削除し、関数内で直接結果を返すように変更しています。これにより、不要な状態の共有が排除され、コードの健全性が向上します。
3.  **コードの簡潔化とGoイディオムへの準拠**: `fmt.Sprintf` をより適切な関数に置き換えることで、コードがより意図を明確に表現し、Goの慣用的なスタイルに近づきます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念とパッケージに関する知識が必要です。

1.  **`fmt` パッケージ**:
    *   `fmt.Sprintf(format string, a ...interface{}) string`: フォーマット文字列と引数を受け取り、フォーマットされた文字列を返します。C言語の `sprintf` に似ており、様々な型の値を文字列に変換し、整形するのに非常に強力です。しかし、その汎用性ゆえに、シンプルな変換ではオーバーヘッドが生じることがあります。
    *   `fmt.Sprint(a ...interface{}) string`: 引数をデフォルトのフォーマットでスペース区切りで連結した文字列を返します。`Sprintf` よりもシンプルで、主にデバッグ出力や簡単な文字列結合に使用されます。

2.  **`strconv` パッケージ**:
    *   `strconv.Itoa(i int) string`: 整数 `i` を基数10の文字列表現に変換します。`fmt.Sprintf("%d", i)` と同じ結果を返しますが、整数から文字列への変換に特化しているため、通常は `fmt.Sprintf` よりも高速です。

3.  **`cmd/internal` パッケージ**:
    Go言語のソースコードには、`cmd/internal` というディレクトリ構造がよく見られます。これは、Goツールチェイン（コンパイラ、リンカ、アセンブラなど）の内部で使用されるパッケージを格納するための慣習です。これらのパッケージは、Goの標準ライブラリの一部ではなく、Goツールチェインのビルドプロセスでのみ使用されることを意図しています。そのため、これらのパッケージは安定したAPIを提供する必要がなく、パフォーマンスや内部構造の変更が頻繁に行われる可能性があります。このコミットも、このような内部パッケージの最適化の一環です。

4.  **文字列バッファの再利用とスレッドセーフティ**:
    Goの初期のコードベースでは、C言語の慣習を引き継ぎ、文字列を生成する際にグローバルなバッファを再利用するパターンが見られました。これは、メモリ割り当てのオーバーヘッドを避けるための最適化として行われることがありますが、Goの並行処理モデルにおいては問題を引き起こす可能性があります。複数のGoroutineが同時に同じグローバルバッファに書き込もうとすると、データ競合が発生し、予期せぬ結果やクラッシュにつながる可能性があります。このコミットでグローバルバッファが削除されたのは、このような潜在的な問題を回避し、コードの堅牢性を高めるためと考えられます。

## 技術的詳細

このコミットでは、主に以下のパターンで `fmt.Sprintf` の使用が変更されています。

1.  **グローバルバッファの削除と `fmt.Sprintf` の直接利用**:
    `src/cmd/internal/gc/lex.go` の `lexname` 関数と `src/cmd/internal/gc/typecheck.go` の `typekind` 関数では、以前は `lexname_buf` および `typekind_buf` というグローバルな文字列バッファを宣言し、`fmt.Sprintf` の結果をそこに格納してから返していました。この変更により、これらのグローバルバッファが削除され、`fmt.Sprintf` の結果が直接返されるようになりました。これにより、不要な状態の共有が排除され、関数の純粋性が高まります。

    *   `lex.go`:
        ```diff
        -var lexname_buf string
        func lexname(lex int) string {
            // ...
        -	lexname_buf = fmt.Sprintf("LEX-%d", lex)
        -	return lexname_buf
        +	return fmt.Sprintf("LEX-%d", lex)
        }
        ```

    *   `typecheck.go`:
        ```diff
        -var typekind_buf string
        func typekind(t *Type) string {
            // ...
        -	typekind_buf = fmt.Sprintf("etype=%d", et)
        -	return typekind_buf
        +	return fmt.Sprintf("etype=%d", et)
        }
        ```

2.  **`fmt.Sprintf` から `strconv.Itoa` への置き換え**:
    `src/cmd/internal/ld/sym.go` の `Headstr` 関数では、整数を文字列に変換するために `fmt.Sprintf("%d", v)` を使用していました。このコミットでは、これを `strconv.Itoa(v)` に置き換えています。`strconv.Itoa` は整数から文字列への変換に特化しており、`fmt.Sprintf` よりも効率的です。また、ここでも `headstr_buf` というグローバルバッファが削除されています。

    *   `sym.go`:
        ```diff
        -var headstr_buf string
        func Headstr(v int) string {
            // ...
        -	headstr_buf = fmt.Sprintf("%d", v)
        -	return headstr_buf
        +	return strconv.Itoa(v)
        }
        ```

3.  **`fmt.Sprintf("%v", ...)` から `fmt.Sprint(...)` への置き換え**:
    `src/cmd/internal/obj/flag.go` の `int32Value` 型の `String` メソッドと、`src/cmd/internal/obj/util.go` の `Dconv` および `Mconv` 関数では、`fmt.Sprintf("%v", ...)` を使用していましたが、これを `fmt.Sprint(...)` に置き換えています。`%v` はGoの値をデフォルトのフォーマットで出力する汎用的な動詞ですが、単に値を文字列に変換するだけであれば `fmt.Sprint` の方がシンプルで、オーバーヘッドが少ない可能性があります。

    *   `flag.go`:
        ```diff
        -func (i *int32Value) String() string { return fmt.Sprintf("%v", *i) }
        +func (i *int32Value) String() string { return fmt.Sprint(*i) }
        ```

    *   `util.go` (`Dconv` 関数内):
        ```diff
        -		str = fmt.Sprintf("%v", Rconv(int(a.Reg)))
        +		str = Rconv(int(a.Reg)) // Rconv returns string directly, no need for fmt.Sprintf
        // ...
        -			str = fmt.Sprintf("%d", p.Pcond.Pc)
        +			str = fmt.Sprint(p.Pcond.Pc)
        // ...
        -			str = fmt.Sprintf("%d", a.Val.(*Prog).Pc)
        +			str = fmt.Sprint(a.Val.(*Prog).Pc)
        // ...
        -			str = fmt.Sprintf("%d", a.Offset)
        +			str = fmt.Sprint(a.Offset)
        ```
        `Dconv` 関数では、`Rconv(int(a.Reg))` の結果が既に文字列であるため、`fmt.Sprintf("%v", ...)` が完全に不要になり、直接 `Rconv` の結果を代入するように変更されています。これは、冗長な変換処理の削除であり、最も直接的な最適化です。

これらの変更は、Goの内部ツールチェインのコード品質とパフォーマンスを継続的に改善する取り組みの一環です。特に、コンパイラやリンカのような低レベルのツールでは、細かな最適化が全体のビルド時間に影響を与えるため、このようなクリーンアップは重要です。

## コアとなるコードの解説

上記の変更箇所は、Goの内部ツールチェインにおける文字列変換の効率化とコードの健全性向上という共通のテーマを持っています。

1.  **グローバルバッファの削除 (`lex.go`, `typecheck.go`, `sym.go`)**:
    `lexname_buf`, `typekind_buf`, `headstr_buf` といったグローバルな文字列バッファは、以前は `fmt.Sprintf` の結果を一時的に保持するために使用されていました。しかし、Goの関数は通常、結果を直接返すことで、呼び出し元がその値をどのように使用するかを決定できるように設計されています。グローバルバッファの利用は、並行処理環境下でのデータ競合のリスクを高めるだけでなく、コードの可読性や保守性も低下させます。この変更により、これらのバッファが削除され、`fmt.Sprintf` や `strconv.Itoa` の結果が直接 `return` されるようになりました。これにより、関数はより純粋になり、副作用がなくなります。

2.  **`fmt.Sprintf("%d", ...)` から `strconv.Itoa(...)` への置き換え (`sym.go`)**:
    `Headstr` 関数では、整数 `v` を文字列に変換するために `fmt.Sprintf("%d", v)` を使用していました。これは機能的には正しいですが、`strconv.Itoa` は整数から文字列への変換に特化しているため、より高速で効率的です。`strconv.Itoa` は、`fmt.Sprintf` のような汎用的なフォーマット解析のオーバーヘッドを持たないため、パフォーマンスが向上します。

3.  **`fmt.Sprintf("%v", ...)` から `fmt.Sprint(...)` または直接代入への置き換え (`flag.go`, `util.go`)**:
    *   `int32Value.String()` メソッドでは、`fmt.Sprintf("%v", *i)` を `fmt.Sprint(*i)` に変更しています。`%v` はGoの値をデフォルトのフォーマットで出力する汎用的な動詞ですが、`fmt.Sprint` も同様に値を文字列に変換します。`fmt.Sprint` は `Sprintf` よりもシンプルな実装であり、このケースでは同等の結果をより効率的に得られる可能性があります。
    *   `Dconv` 関数と `Mconv` 関数では、特に注目すべき変更として、`fmt.Sprintf("%v", Rconv(int(a.Reg)))` が `str = Rconv(int(a.Reg))` に変更されています。これは、`Rconv` 関数が既に文字列を返しているため、`fmt.Sprintf` を介して再度文字列に変換する必要がないという、冗長な処理の削除です。このような変更は、コードの実行パスから不必要な処理を取り除くことで、パフォーマンスを直接的に向上させます。
    *   また、`Dconv` および `Mconv` 関数内の他の箇所でも、数値の `Pc` や `Offset` を文字列に変換する際に `fmt.Sprintf("%d", ...)` から `fmt.Sprint(...)` へと変更されています。これも同様に、よりシンプルで効率的な文字列変換手法への移行です。

これらの変更は、Goの内部ツールチェインのコードが、よりGoらしいイディオムに準拠し、パフォーマンスと堅牢性を向上させるための継続的な努力を示しています。特に、コンパイラやリンカのような基盤ツールでは、このような細かな最適化が全体の開発エコシステムに大きな影響を与える可能性があります。

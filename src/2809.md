## 元コミット内容

無名関数引数でのセグメンテーション違反を修正します。`continue` 文が条件チェックではなく、`post` ステートメントにジャンプするように変更します。

## 変更の背景

このコミットは、Go言語のコンパイラまたはインタプリタの初期開発段階における2つの重要なバグ修正を目的としています。

1.  **無名関数引数でのセグメンテーション違反 (segfault on unnamed function arguments)**:
    Go言語では、関数の引数や戻り値に名前を付けない（無名にする）ことができます。例えば `func(int, string)` のような関数シグネチャです。コンパイラがこのような無名引数を処理する際に、正しくスコープに定義できず、メモリ破壊（セグメンテーション違反）を引き起こす可能性があったと考えられます。これは、コンパイラが引数名を期待する箇所で `nil` 値を適切に扱えなかったことに起因する可能性があります。

2.  **`continue` 文のジャンプ先誤り (`continue` jump to the post statement instead of the condition check)**:
    `for` ループにおける `continue` 文の動作は、現在のイテレーションをスキップし、次のイテレーションに進むことです。C言語系の言語では、通常 `for` ループの `continue` は「更新式（post statement）」を実行した後に「条件式」を評価します。このコミット以前のGoコンパイラでは、`continue` が直接条件式にジャンプしてしまい、`post` ステートメント（例: `i++`）が実行されないという誤った動作をしていた可能性があります。これは、ループの無限化や意図しない動作を引き起こす重大なバグです。

これらの問題は、言語の基本的な制御フローと関数定義の正確な動作に影響を与えるため、安定したコンパイラを構築する上で早期に修正する必要がありました。

## 前提知識の解説

### 1. 抽象構文木 (Abstract Syntax Tree, AST)
コンパイラやインタプリタは、ソースコードを直接解釈するのではなく、まずソースコードを解析してプログラムの構造を木構造で表現した「抽象構文木（AST）」を生成します。このASTは、プログラムの論理的な構造を表現しており、コンパイラの各フェーズ（意味解析、最適化、コード生成など）で利用されます。Go言語の `ast` パッケージは、このASTを表現するための型を提供します。`ast.ForStmt` は `for` ループ文のASTノードを表し、`ast.FuncDecl` は関数宣言のASTノードを表します。

### 2. `for` ループの構造と `continue` 文
Go言語の `for` ループは、C言語の `for` ループに似た形式を持ちます。
`for init; condition; post { body }`
- `init`: ループの開始前に一度だけ実行される初期化ステートメント。
- `condition`: 各イテレーションの開始前に評価される条件式。`true` の間ループが続行されます。
- `post`: 各イテレーションの本体 (`body`) の実行後に実行される更新ステートメント。
- `body`: ループの本体。

`continue` 文は、`body` 内で実行されると、現在のイテレーションの残りの部分をスキップし、`post` ステートメント（もしあれば）を実行し、その後 `condition` を再評価して次のイテレーションに進みます。

### 3. コンパイラのコード生成とジャンプ命令
コンパイラはASTを元に、最終的に機械語や中間コードを生成します。この過程で、制御フロー（条件分岐、ループ、関数呼び出しなど）はジャンプ命令（`goto` のようなもの）によって実現されます。
- `PC (Program Counter)`: プログラムカウンタ。次に実行される命令のアドレスを指すレジスタ。
- `bodyPC`: ループ本体の開始アドレス。
- `checkPC`: ループの条件チェック部分の開始アドレス。
- `postPC`: ループの更新ステートメント（`post`）部分の開始アドレス。
- `endPC`: ループの終了アドレス。
`continue` 文が正しく動作するためには、`body` 内で `continue` が実行された際に、`postPC` にジャンプし、その後 `checkPC` にジャンプするという一連の動作がコード生成時に適切に設定されている必要があります。

### 4. スコープと変数定義
プログラミング言語において、スコープは変数がアクセス可能な範囲を定義します。関数引数もその関数のローカルスコープ内で定義され、利用可能になります。コンパイラは、各変数がどのスコープに属し、どのような型を持つかを管理する必要があります。無名引数の場合でも、それらはメモリ上に存在し、型を持つため、コンパイラはそれらを一時変数（temp）としてスコープに定義する必要があります。

## 技術的詳細

このコミットは、Go言語のコンパイラ（またはインタプリタのバックエンド）における `stmtCompiler` および `compiler` 構造体のメソッドに焦点を当てています。

### 1. `for` ループにおける `continue` の修正

`stmtCompiler.DoForStmt` メソッドは `for` ループ文をコンパイルする役割を担っています。
変更前は、`continuePC` (continue文がジャンプすべきアドレス) が `&checkPC` (条件チェックのアドレス) に設定されていました。これは、`continue` が実行されると直接条件チェックに飛び、`post` ステートメントがスキップされることを意味します。

変更後は、`continuePC` が `&postPC` (更新ステートメントのアドレス) に設定されています。これにより、`continue` が実行されるとまず `post` ステートメントが実行され、その後 `post` ステートメントの最後に自動的に `checkPC` へジャンプするようなコードが生成されるようになります。これは、C言語系の `for` ループにおける `continue` の標準的な動作と一致させ、ループの更新ロジックが常に実行されることを保証します。

この修正は、`for` ループのセマンティクスを正しく実装するために不可欠です。`post` ステートメントがスキップされると、例えば `for i := 0; i < N; i++ { ... continue ... }` のようなループで `i++` が実行されず、無限ループに陥る可能性がありました。

### 2. 無名関数引数のセグメンテーション違反の修正

`compiler.compileFunc` メソッドは関数宣言をコンパイルする役割を担っています。
Go言語では、関数引数や戻り値に名前を付けないことができます。例えば `func(a int, b string)` の代わりに `func(int, string)` と書けます。
変更前は、`decl.InNames[i].Value` を直接参照して引数をスコープに定義しようとしていました。しかし、無名引数の場合、`decl.InNames[i]` は `nil` になる可能性があります。`nil` のポインタに対して `.Value` を呼び出すと、セグメンテーション違反が発生します。

変更後は、`decl.InNames[i] != nil` のチェックが追加されました。
- 引数に名前がある場合 (`decl.InNames[i] != nil`) は、これまで通り `bodyScope.DefineVar(decl.InNames[i].Value, t)` を呼び出し、その名前と型で変数をスコープに定義します。
- 引数に名前がない場合 (`decl.InNames[i] == nil`) は、`bodyScope.DefineTemp(t)` を呼び出して、その型の「一時変数」としてスコープに定義します。これにより、無名引数もコンパイラによって適切に管理され、セグメンテーション違反が回避されます。

同様の修正が戻り値の定義 (`decl.OutNames`) にも適用されています。これにより、無名引数や無名戻り値が原因で発生していたセグメンテーション違反が解消されます。`TODO(austin) Not technically a temp` というコメントは、厳密には一時変数ではないが、名前がないため一時変数として扱うという当時の設計判断を示唆しています。

## コアとなるコードの解説

### `func (a *stmtCompiler) DoForStmt(s *ast.ForStmt)` 内の変更

1.  **`postPC` 変数の追加**:
    ```diff
    -	var bodyPC, checkPC, endPC uint;
    +	var bodyPC, postPC, checkPC, endPC uint;
    ```
    `for` ループの `post` ステートメント（更新式）へのジャンプ先アドレスを保持するための `postPC` 変数が追加されました。これにより、`continue` 文が `post` ステートメントに正しくジャンプするための準備が整います。

2.  **`continuePC` のジャンプ先修正**:
    ```diff
    -	body.continuePC = &checkPC;
    +	body.continuePC = &postPC;
    ```
    `body` (ループ本体) のコンパイルスコープにおける `continuePC` が、`checkPC` (条件チェック) から `postPC` (更新ステートメント) のアドレスを指すように変更されました。これにより、`continue` 文が実行された際に、まず `post` ステートメントが実行されるようになります。

3.  **`postPC` の設定**:
    ```diff
    +	postPC = a.nextPC();
    ```
    `post` ステートメントのコンパイルが始まる直前に、現在のプログラムカウンタ (`a.nextPC()`) の値が `postPC` に格納されます。これは、`post` ステートメントのコードが実際に配置されるアドレスを記録するものです。

これらの変更により、`for` ループ内の `continue` 文は、ループ本体の残りをスキップし、`post` ステートメントを実行してから条件チェックに戻るという、Go言語の仕様に合致した正しい動作をするようになります。

## 変更の背景

この変更の背景には、Go 1.5における `crypto/tls` パッケージの機能拡張があります。以前のバージョンでは、TLSサーバーを設定する際に `Config` 構造体の `Certificates` フィールドに少なくとも1つの証明書チェーンを明示的に指定することが必須でした。しかし、サーバーネームインディケーション (SNI) のような動的な証明書選択が必要なシナリオでは、事前にすべての証明書を `Certificates` フィールドにロードしておくのは非効率的であるか、あるいは不可能でした。

Go 1.5では、この問題を解決するために `Config.GetCertificate` という新しいフィールド（関数）が導入されました。このフィールドは、クライアントから提示されたTLS Helloメッセージに基づいて、実行時に適切な証明書を動的に取得するためのコールバック関数を指定できるようにするものです。この機能が導入されたことで、`Certificates` フィールドが空であっても、`GetCertificate` が設定されていればサーバーが正しく動作するようになりました。

このコミットは、この新しい動作を開発者に明確に伝えるため、既存のドキュメントコメントを更新することを目的としています。これにより、開発者はGo 1.5以降の `crypto/tls` の柔軟な証明書ハンドリング機能を正しく理解し、利用できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **TLS (Transport Layer Security)**: インターネット上でデータを安全にやり取りするための暗号化プロトコルです。ウェブサイトのHTTPS通信などで広く利用されています。
*   **TLS証明書**: サーバーの身元を証明し、クライアントとの間で暗号化された通信を確立するために使用されます。通常、公開鍵と秘密鍵のペア、および認証局 (CA) によって署名された証明書ファイルで構成されます。
*   **`crypto/tls` パッケージ**: Go言語の標準ライブラリで、TLSクライアントおよびサーバーの実装を提供します。
*   **`tls.Config` 構造体**: TLS接続の設定を保持する構造体です。この構造体には、証明書、鍵、プロトコルバージョン、暗号スイートなど、TLSハンドシェイクの挙動を制御するための多くのフィールドが含まれています。
*   **`Config.Certificates []Certificate`**: このフィールドは、サーバーがクライアントに提示する1つ以上の証明書チェーンを格納します。通常、サーバーの秘密鍵と対応する公開鍵証明書が含まれます。以前は、サーバー設定においてこのフィールドに少なくとも1つの証明書が含まれていることが必須でした。
*   **`Config.GetCertificate func(*ClientHelloInfo) (*Certificate, error)`**: Go 1.5で導入されたフィールドです。これは関数ポインタであり、クライアントからの `ClientHello` メッセージ（SNI情報などを含む）を受け取り、それに基づいて適切な `tls.Certificate` を動的に返す役割を担います。この関数が設定されている場合、`Certificates` フィールドが空であってもサーバーは動作可能です。これは、特にSNIをサポートするサーバーや、多数のドメインに対して異なる証明書を提供するサーバーにとって非常に有用です。
*   **SNI (Server Name Indication)**: TLSプロトコルの拡張機能で、クライアントがTLSハンドシェイクの初期段階で接続しようとしているホスト名（ドメイン名）をサーバーに伝えることができます。これにより、単一のIPアドレスで複数のドスト名に対応するサーバーが、クライアントが要求するドメイン名に応じた適切な証明書を提示できるようになります。

## 技術的詳細

このコミットは、`crypto/tls` パッケージの `Config` 構造体とその関連関数におけるコメントを修正することで、Go 1.5で導入された `GetCertificate` フィールドの重要性と代替性について開発者に通知しています。

具体的には、以下の点が技術的な詳細として挙げられます。

1.  **`Certificates` フィールドの必須条件の緩和**:
    *   Go 1.5より前は、TLSサーバーを構成する際、`Config.Certificates` スライスに少なくとも1つの `tls.Certificate` を設定することが必須でした。これは、サーバーがクライアントに提示するデフォルトの証明書を持つ必要があるためです。
    *   Go 1.5以降では、`Config.GetCertificate` フィールドに有効な関数が設定されている場合、`Config.Certificates` は空であってもよくなりました。これは、証明書が静的に設定されるのではなく、リクエストに応じて動的に取得されるためです。

2.  **`GetCertificate` の役割**:
    *   `GetCertificate` は、クライアントがTLSハンドシェイクを開始する際に送信する `ClientHelloInfo` を引数として受け取ります。この `ClientHelloInfo` には、クライアントが接続しようとしているサーバー名（SNI情報）が含まれることがあります。
    *   サーバー開発者は、この `ClientHelloInfo` を利用して、例えばSNIで指定されたホスト名に対応する証明書をデータベースやファイルシステムから検索し、それを返却するロジックを `GetCertificate` 関数内に実装できます。
    *   これにより、単一のTLSサーバーが複数のドメインに対して異なる証明書を提供することが可能になり、証明書の管理がより柔軟になります。

3.  **コメント更新の重要性**:
    *   このコミットで行われたコメントの更新は、APIの動作変更をドキュメントに反映させるという点で非常に重要です。開発者が古いドキュメントに基づいてコードを書くと、Go 1.5以降の新しい機能を見落としたり、不必要な `Certificates` 設定を行ったりする可能性があります。
    *   更新されたコメントは、「サーバー設定には少なくとも1つの証明書を含めるか、`GetCertificate` を設定する必要がある」という明確な指示を提供し、開発者が正しい方法でTLSサーバーを構成できるように導きます。

4.  **エラーハンドリングの変更**:
    *   `tls.Listen` 関数内では、`config == nil || (len(config.Certificates) == 0 && config.GetCertificate == nil)` という条件でエラーチェックが行われています。これは、`Config` が `nil` でないこと、そして `Certificates` が空で `GetCertificate` も `nil` でないこと（つまり、どちらか一方が設定されていること）を保証しています。このチェックは、サーバーが証明書なしで起動されるのを防ぐためのものです。

この変更は、Goの `crypto/tls` パッケージがより柔軟で、現代のTLSサーバーの要件（特にSNIのサポート）に適合するように進化していることを示しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`crypto/tls` パッケージ内の主要な関数と `Config` 構造体の `Certificates` フィールドに関するコメントの修正です。これらのコメントは、Go 1.5で導入された `Config.GetCertificate` フィールドの存在と、それが `Config.Certificates` の代替となり得ることを明確にしています。

1.  **`src/crypto/tls/common.go` の `Certificates` フィールドのコメント**:
    *   変更前: `// Server configurations must include at least one certificate.`
    *   変更後: `// Server configurations must include at least one certificate // or else set GetCertificate.`
    *   この変更は、`Config` 構造体内の `Certificates` フィールドのドキュメントを更新し、サーバー設定において証明書を静的に提供する代わりに、`GetCertificate` 関数を動的に設定することも許容されることを明示しています。これにより、開発者はSNIなどの高度なシナリオで `GetCertificate` を利用する際のガイドラインを得られます。

2.  **`src/crypto/tls/tls.go` 内の `Server`, `NewListener`, `Listen` 関数のコメント**:
    *   これらの関数は、TLSサーバー接続やリスナーを作成するためのエントリポイントです。
    *   変更前は、いずれの関数も `config` 引数について「非nilであり、少なくとも1つの証明書を持たなければならない」と記述していました。
    *   変更後は、この記述が「非nilであり、少なくとも1つの証明書を含むか、`GetCertificate` を設定しなければならない」と修正されています。
    *   この修正は、`GetCertificate` が `Certificates` と同等に、サーバーが有効な証明書を持つための手段として認識されるべきであることを強調しています。これにより、これらの関数を利用する開発者は、証明書の設定方法に複数の選択肢があることを理解し、自身のユースケースに最適な方法を選択できるようになります。

これらのコメントの更新は、APIの振る舞いの変更を正確に反映し、開発者がGo 1.5以降の `crypto/tls` パッケージをより効果的に利用するための重要なドキュメント改善です。特に、動的な証明書選択が必要なアプリケーションを構築する際に、この情報は不可欠となります。

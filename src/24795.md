## 変更の背景

Go言語のランタイムは、様々なアーキテクチャで効率的に動作するように設計されています。`cmpstring`（内部的な文字列比較）や `bytes.Compare`（バイトスライスの比較）のような基本的な操作は、プログラムの実行性能に大きな影響を与える可能性があります。特に、大量の文字列やバイトスライスを扱うアプリケーションでは、これらの関数の効率がボトルネックとなることがあります。

PowerPC 64ビット (ppc64) アーキテクチャは、サーバーや高性能コンピューティングの分野で利用されることがあり、そのプラットフォーム上でのGoプログラムの性能最適化は重要です。Goランタイムでは、特定のアーキテクチャ向けにC言語やGo言語で書かれたコードを、より高速なアセンブリ言語で再実装することで性能向上を図ることがよく行われます。

このコミットの背景には、ppc64アーキテクチャ上での文字列およびバイトスライス比較の性能を向上させるという目的があります。アセンブリ言語を使用することで、CPUのレジスタを直接操作し、特定の命令セットを活用して、コンパイラが生成する汎用的なコードよりも効率的な比較ロジックを実装することが可能になります。これにより、ppc64環境でGoアプリケーションがより高速に動作することが期待されます。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、プリミティブな操作（文字列比較など）といった低レベルな機能を提供します。Goプログラムは、コンパイル時にランタイムとリンクされ、ランタイムの機能を利用して動作します。

### アセンブリ言語 (Assembly Language)

アセンブリ言語は、特定のCPUアーキテクチャの機械語命令と1対1に対応する低レベルなプログラミング言語です。Goランタイムでは、性能がクリティカルな部分（例: コンテキストスイッチ、メモリコピー、特定の算術演算、今回のような比較操作）で、GoやC言語では実現が難しいレベルの最適化を行うためにアセンブリ言語が使用されます。Goのアセンブリは、Plan 9アセンブラの構文をベースにしています。

### PowerPC 64ビット (ppc64) アーキテクチャ

PowerPCはIBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。ppc64はその64ビット版で、主にサーバー、組み込みシステム、スーパーコンピュータなどで使用されます。Goは、このアーキテクチャもサポートしており、クロスコンパイルやネイティブビルドが可能です。ppc64には、特定のデータ処理を高速化するための命令セットが含まれています。

### `runtime.cmpstring`

`runtime.cmpstring` はGoランタイム内部で使用される文字列比較関数です。Go言語の文字列は不変なバイトスライスとして表現されるため、この関数は2つの文字列のバイト列を比較し、辞書順でどちらが大きいか、または等しいかを判断します。

### `bytes.Compare`

`bytes.Compare` はGo標準ライブラリの `bytes` パッケージで提供される関数で、2つのバイトスライスを辞書順で比較します。戻り値は、`a < b` なら -1、`a == b` なら 0、`a > b` なら 1 です。これはユーザーが直接利用するAPIであり、その性能はGoプログラム全体の効率に影響します。

### `NOSPLIT`

Goのアセンブリ関数における `NOSPLIT` ディレクティブは、その関数がスタックを分割しないことをコンパイラに指示します。これは、非常に短い関数や、スタックの分割がオーバーヘッドとなるようなクリティカルな関数で使用されます。

### `TEXT` ディレクティブ

Goのアセンブリ言語では、`TEXT` ディレクティブを使用して関数を定義します。`TEXT symbol(SB), flags, args-framesize` の形式で記述され、`symbol` は関数の名前、`(SB)` はシンボルが静的セグメントのベースアドレスからのオフセットであることを示します。`flags` は `NOSPLIT` などの属性、`args` は引数のサイズ、`framesize` はスタックフレームのサイズを示します。

## 技術的詳細

このコミットは、`src/runtime/asm_ppc64x.s` ファイルにppc64アーキテクチャ向けのアセンブリコードを追加することで、`runtime.cmpstring` と `bytes.Compare` の実装を最適化しています。

具体的には、以下の3つのアセンブリ関数が追加されています。

1.  **`runtime·cmpstring(SB)`**: Goランタイム内部の文字列比較関数 `runtime.cmpstring` のアセンブリ実装へのエントリポイントです。引数として2つの文字列のベースアドレスと長さをフレームポインタ (FP) 経由で受け取り、共通の比較ロジックである `runtime·cmpbody<>(SB)` へジャンプします。
2.  **`bytes·Compare(SB)`**: `bytes` パッケージの `Compare` 関数のアセンブリ実装へのエントリポイントです。こちらも2つのバイトスライスのベースアドレスと長さをFP経由で受け取り、`runtime·cmpbody<>(SB)` へジャンプします。
3.  **`runtime·cmpbody<>(SB)`**: 実際のバイト列比較ロジックを実装した共通のアセンブリ関数です。この関数は、`runtime·cmpstring` と `bytes·Compare` の両方から呼び出されます。

`runtime·cmpbody<>(SB)` のロジックは以下の通りです。

*   **レジスタの役割**:
    *   `R3`: 1つ目のバイトスライス (s1) の長さ
    *   `R4`: 2つ目のバイトスライス (s2) の長さ
    *   `R5`: s1 の開始アドレス
    *   `R6`: s2 の開始アドレス
    *   `R7`: 戻り値 (-1, 0, 1) を書き込むメモリ位置 (フレームポインタからのオフセット)

*   **初期比較**: まず、`R5` と `R6` (s1とs2の開始アドレス) が等しいかどうかを比較します。もし等しければ、同じバイト列を指している可能性があるので、`samebytes` ラベルにジャンプして長さのみを比較します。
*   **ポインタ調整**: `SUB $1, R5` と `SUB $1, R6` でポインタをデクリメントしています。これは、PowerPCのロード/ストア命令でインデックス付きアドレッシング（例: `MOVBZU 1(R5)` は `R5+1` のアドレスからバイトをロード）を使用する際に、ループ内でポインタをインクリメントする代わりに、ベースポインタをデクリメントしておくことで、ループ内の命令を簡略化するためと考えられます。
*   **最小長の決定**: `R3` (s1の長さ) と `R4` (s2の長さ) を比較し、短い方の長さを `R8` に格納します (`R8` は `min(R3, R4)`)。これは、比較するバイト数を決定するためです。
*   **ループによるバイト比較**: `loop` ラベルで開始されるループでは、`R5` (s1の現在バイトポインタ) が `R8` (比較する最後のバイトのポインタ) に達するまで、1バイトずつ比較を行います。
    *   `MOVBZU 1(R5), R9`: `R5+1` のアドレスから1バイトを符号なしで `R9` にロードします。
    *   `MOVBZU 1(R6), R10`: `R6+1` のアドレスから1バイトを符号なしで `R10` にロードします。
    *   `CMP R9, R10`: ロードした2つのバイトを比較します。
    *   `BEQ loop`: バイトが等しければ、次のバイトの比較に進みます。
    *   バイトが異なれば、ループを終了し、どちらのバイトが大きいかに基づいて戻り値を設定します。
*   **戻り値の設定**:
    *   バイトが異なった場合: `R9` と `R10` の比較結果に基づき、`R4` に 1 または -1 を設定し、`R7` が指す戻り値のメモリ位置に書き込みます。
    *   すべての比較バイトが等しかった場合 (`samebytes`): `R3` (s1の長さ) と `R4` (s2の長さ) を比較します。
        *   長さが等しければ、`R0` (常に0) を戻り値として書き込みます。
        *   長さが異なれば、長い方が大きいと判断し、`R8` に 1 または -1 を設定して戻り値として書き込みます。

このアセンブリ実装は、Go言語やC言語で書かれた同等のコードよりも、レジスタの効率的な利用、分岐予測の最適化、そしてPowerPCの特定の命令セット（例: `MOVBZU`）を直接活用することで、より高速な比較を実現します。

また、`src/runtime/noasm.go` ファイルの変更は、ppc64アーキテクチャ向けにアセンブリ実装が提供されたため、Go言語で書かれた汎用的な（アセンブリ実装がない場合の）比較関数が不要になったことを示しています。具体的には、`+build ppc64 ppc64le` タグが `+build ignore` に変更され、ppc64環境ではこのファイルがコンパイル対象から外れるようになっています。

## コアとなるコードの変更箇所

*   `src/runtime/asm_ppc64x.s`:
    *   `TEXT runtime·cmpstring(SB)` 関数の追加
    *   `TEXT bytes·Compare(SB)` 関数の追加

## コアとなるコードの解説

### `src/runtime/asm_ppc64x.s` の追加コード

```assembly
TEXT runtime·cmpstring(SB),NOSPLIT,$-4-40
	MOVD	s1_base+0(FP), R5
	MOVD	s1_len+8(FP), R3
	MOVD	s2_base+16(FP), R6
	MOVD	s2_len+24(FP), R4
	MOVD	$ret+32(FP), R7
	BR	runtime·cmpbody<>(SB)

TEXT bytes·Compare(SB),NOSPLIT,$-4-56
	MOVD	s1+0(FP), R5
	MOVD	s1+8(FP), R3
	MOVD	s2+24(FP), R6
	MOVD	s2+32(FP), R4
	MOVD	$ret+48(FP), R7
	BR	runtime·cmpbody<>(SB)

// On entry:
// R3 is the length of s1
// R4 is the length of s2
// R5 points to the start of s1
// R6 points to the start of s2
// R7 points to return value (-1/0/1 will be written here)
//
// On exit:
// R5, R6, R8, R9 and R10 are clobbered
TEXT runtime·cmpbody<>(SB),NOSPLIT,$-4-0
	CMP	R5, R6
	BEQ	samebytes // same starting pointers; compare lengths
	SUB	$1, R5
	SUB	$1, R6
	MOVD	R4, R8
	CMP	R3, R4
	BGE	2(PC)
	MOVD	R3, R8	// R8 is min(R3, R4)
	ADD	R5, R8	// R5 is current byte in s1, R8 is last byte in s1 to compare
loop:
	CMP	R5, R8
	BEQ	samebytes // all compared bytes were the same; compare lengths
	MOVBZU	1(R5), R9
	MOVBZU	1(R6), R10
	CMP	R9, R10
	BEQ	loop
	// bytes differed
	MOVD	$1, R4
	BGT	2(PC)
	NEG	R4
	MOVD	R4, (R7)
	RET
samebytes:
	MOVD	$1, R8
	CMP	R3, R4
	BNE	3(PC)
	MOVD	R0, (R7)
	RET
	BGT	2(PC)
	NEG	R8
	MOVD	R8, (R7)
	RET
```

*   `runtime·cmpstring` と `bytes·Compare` は、それぞれGoの関数呼び出し規約に従ってスタックフレームから引数（文字列/バイトスライスのベースアドレスと長さ）をレジスタにロードし、`runtime·cmpbody<>` に処理を委譲しています。`$ret+XX(FP)` は戻り値が書き込まれるスタック上の位置を示します。
*   `runtime·cmpbody<>` は、2つのバイト列を効率的に比較するためのメインロジックです。
    *   `CMP R5, R6`: まずポインタ自体が同じかどうかをチェックし、同じであれば長さ比較のみで済む `samebytes` へ分岐します。これは、同じ文字列やスライスが渡された場合の高速パスです。
    *   `SUB $1, R5` と `SUB $1, R6`: ポインタを1デクリメントしているのは、PowerPCの `MOVBZU 1(R5)` のような命令が `R5+1` のアドレスからロードするため、ループ内でポインタをインクリメントする手間を省くための最適化です。
    *   `MOVD R4, R8` と `CMP R3, R4; BGE 2(PC); MOVD R3, R8`: 2つの長さ (`R3`, `R4`) のうち小さい方を `R8` に格納し、比較するバイト数を決定します。
    *   `ADD R5, R8`: `R8` には比較する最後のバイトのポインタが計算されます。
    *   `loop:` ラベル内の処理は、`R5` が `R8` に達するまで、`MOVBZU` 命令で1バイトずつロードし、`CMP` 命令で比較します。バイトが異なればループを抜け、どちらが大きいかに応じて戻り値を設定します。
    *   `samebytes:` ラベルは、ポインタが同じか、または比較したすべてのバイトが同じだった場合に到達します。ここでは、残りの長さ (`R3`, `R4`) を比較して最終的な戻り値を決定します。

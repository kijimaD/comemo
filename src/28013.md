## 元コミット内容

Goランタイムにおいて、ARMv5アーキテクチャでの大きなオフセットを持つ浮動小数点数ストア命令の処理を修正します。この修正は、ベースポインタをr11レジスタに加算する命令シーケンスが正しく解釈されるようにすることで、ビルドエラーを修正し、Issue #15440で報告された問題を解決します。

## 変更の背景

このコミットは、GoコンパイラがARMv5アーキテクチャ向けに生成するコードが、特定の条件下で正しく動作しないという問題に対処しています。具体的には、配列の要素など、ベースアドレスから大きなオフセットを持つメモリ位置に浮動小数点数をストア（書き込み）する際に問題が発生していました。

ARMv5のような古いARMアーキテクチャでは、メモリロード/ストア命令のオフセット値には制限があります。大きなオフセットが必要な場合、コンパイラは複数の命令を組み合わせて目的のアドレスを計算します。このコミットで問題となっているのは、その計算過程でベースポインタ（この場合はスタックポインタ `sp`）を一時レジスタ（`r11`）に加算する命令が、Goランタイムのソフトウェア浮動小数点エミュレータによって正しく解釈されていなかった点です。

Goランタイムには、ハードウェアが浮動小数点演算をサポートしていない、または特定の浮動小数点命令をサポートしていない場合に備えて、ソフトウェアによる浮動小数点エミュレーション機能が含まれています。このエミュレータが、アドレス計算の一部である `add` 命令を、浮動小数点ストア命令の文脈で適切に処理できていなかったため、ストアが失敗し、結果としてプログラムが誤動作したり、ビルドが失敗したりしていました。

Issue #15440は、この問題が具体的に報告された場所であり、このコミットはその問題を解決するために作成されました。

## 前提知識の解説

1.  **ARMv5アーキテクチャ**:
    *   ARMv5は、ARMアーキテクチャの古いバージョンの一つで、組み込みシステムや古いモバイルデバイスで広く使用されていました。
    *   特徴として、命令セットが比較的シンプルで、メモリロード/ストア命令のオフセット値に制限があることが挙げられます。
    *   浮動小数点演算ユニット（FPU）がオプションであり、FPUがないシステムではソフトウェアによるエミュレーションが必要になります。
2.  **Goランタイムのソフトウェア浮動小数点エミュレーション**:
    *   Go言語は、様々なアーキテクチャで動作するように設計されています。ARMv5のようなFPUを持たない、または特定の浮動小数点命令をサポートしない環境では、Goランタイムがソフトウェアで浮動小数点演算をエミュレートします。
    *   このエミュレーションは、ハードウェア命令をフックし、対応するソフトウェアルーチンを実行することで実現されます。
    *   `src/runtime/softfloat_arm.go` は、このソフトウェア浮動小数点エミュレータの一部です。
3.  **ARMアセンブリとレジスタ**:
    *   **`sp` (Stack Pointer)**: スタックの現在のトップを指すレジスタ。関数呼び出し時のローカル変数や引数の保存に使用されます。
    *   **`r11`**: 汎用レジスタの一つ。このコミットでは、大きなオフセットアドレス計算のための一時レジスタとして使用されています。
    *   **`add` 命令**: レジスタの内容を別のレジスタの内容または即値に加算する命令。
    *   **`ldr` (Load Register)**: メモリからレジスタに値をロードする命令。
    *   **`str` (Store Register)**: レジスタからメモリに値をストアする命令。
    *   **`vldr` (Vector Load Register)**: 浮動小数点レジスタに値をロードする命令（VFP/NEON拡張）。
    *   **`vstr` (Vector Store Register)**: 浮動小数点レジスタから値をストアする命令（VFP/NEON拡張）。
    *   **オフセットアドレッシング**: ベースレジスタの値にオフセット（定数または別のレジスタの値）を加算してメモリアドレスを計算する方式。ARMでは、ロード/ストア命令で直接指定できるオフセットの範囲に制限があります。
4.  **Goコンパイラのコード生成**:
    *   Goコンパイラは、Goソースコードをターゲットアーキテクチャの機械語に変換します。
    *   大きな配列の要素へのアクセスなど、ベースアドレスから遠いメモリ位置へのアクセスが必要な場合、コンパイラは複数のアセンブリ命令を組み合わせて目的のアドレスを計算するコードシーケンスを生成します。

## 技術的詳細

この問題は、GoコンパイラがARMv5向けに生成するアセンブリコードと、Goランタイムのソフトウェア浮動小数点エミュレータの連携にありました。

Goコンパイラは、`a[128] = 128.0` のような大きなオフセットを持つ浮動小数点ストア操作に対して、以下のようなアセンブリ命令シーケンスを生成することがあります（`vlop_arm_test.go` のコメントより抜粋）：

```armasm
ldr     r0, [sp, #8]    ; sp+8からr0に値をロード
bl      6f690 <_sfloat> ; ソフトウェア浮動小数点エミュレータの呼び出し
ldr     fp, [pc, #32]   ; (address of 128.0)
vldr    d0, [fp]        ; 浮動小数点値128.0をd0レジスタにロード
ldr     fp, [pc, #28]   ; (1024)
add     fp, fp, r0      ; fpレジスタにfpとr0を加算（アドレス計算）
vstr    d0, [fp]        ; d0レジスタの浮動小数点値をfpが指すアドレスにストア
```

ここで問題となるのは `add fp, fp, r0` 命令です。この命令は、`fp` レジスタ（ここでは一時的にアドレス計算に使用されている）に `r0` の内容を加算して、最終的なストアアドレスを計算しています。

Goランタイムの `src/runtime/softfloat_arm.go` にある `execute` 関数は、ARM命令をデコードし、ソフトウェアでエミュレートする必要がある命令を処理します。以前のコードでは、`i == 0xe08bb00d` という特定の命令（`add sp to r11` に相当）のみを特別扱いしていました。これは、スタックポインタ `sp` を `r11` に加算するケースを想定したものでした。

しかし、コンパイラが生成するコードでは、`add` 命令が `sp` 以外のレジスタ（例: `fp`）と別のレジスタ（例: `r0`）の間で行われる場合もありました。この `add fp, fp, r0` のような命令は、`0xe08bb00d` とは異なる命令コードを持ちます。

修正前のコードは、`0xe08bb00d` という特定の命令コードにのみ反応し、`regs[11] += regs[13]` (つまり `r11 += sp`) を実行していました。しかし、汎用的なアドレス計算のための `add` 命令（`add r, r, r` 形式）は、`0xe08bb000` のビットマスクと一致するが、下位4ビットが異なる命令コードを持つ可能性があります。

このコミットでは、`if i == 0xe08bb00d` を `if i&0xfffffff0 == 0xe08bb000` に変更することで、より汎用的な `add` 命令のパターンを捕捉するようにしました。これにより、`add r, r, r` 形式の命令で、`r11` レジスタがベースレジスタとして使用され、別のレジスタ `r` の内容が加算されるケース（`regs[11] += regs[r]`）を正しくエミュレータが解釈できるようになります。

具体的には、`i&0xfffffff0 == 0xe08bb000` は、命令の上位28ビットが `0xe08bb000` と一致するかどうかをチェックします。これにより、`add r11, r11, R_x` の形式の命令（`R_x` は任意のレジスタ）を捕捉できます。そして、`r := i & 0xf` で加算されるレジスタ `R_x` のインデックスを抽出し、`regs[11] += regs[r]` でその加算をエミュレートします。

この修正により、ソフトウェア浮動小数点エミュレータが、コンパイラが生成する大きなオフセットアドレス計算のための `add` 命令を正しく処理できるようになり、浮動小数点ストアが期待通りに動作するようになりました。

## コアとなるコードの解説

### `src/runtime/softfloat_arm.go` の変更

*   **変更前**:
    ```go
    if i == 0xe08bb00d {
        // add sp to r11.
        // might be part of a large stack offset address
        regs[11] += regs[13]
    ```
    このコードは、特定の命令コード `0xe08bb00d` のみをチェックしていました。この命令コードは、`r11` に `sp` (レジスタ13) を加算する命令に対応していました。これは、スタック上の大きなオフセットへのアクセスを処理するためのものでしたが、汎用的なアドレス計算には対応していませんでした。

*   **変更後**:
    ```go
    if i&0xfffffff0 == 0xe08bb000 {
        r := i & 0xf
        // add r to r11.
        // might be part of a large offset address calculation
        // (or might not, but again no harm done).
        regs[11] += regs[r]
    ```
    この変更により、命令 `i` の上位28ビットが `0xe08bb000` と一致するかどうかをチェックするようになりました。これは、ARMの `ADD` 命令で、デスティネーションレジスタが `r11`、第一オペランドが `r11`、第二オペランドが任意のレジスタ `r` である形式（`ADD R11, R11, R_r`）を捕捉するためのビットマスクです。
    `r := i & 0xf` は、命令の下位4ビットから第二オペランドのレジスタ番号 `r` を抽出します。
    `regs[11] += regs[r]` は、抽出したレジスタ `r` の内容を `r11` に加算することで、この `ADD` 命令をソフトウェアでエミュレートします。
    この汎用的なパターンマッチングにより、コンパイラが生成する様々な形式の大きなオフセットアドレス計算に対応できるようになり、浮動小数点ストアが正しく行われるようになりました。

### `src/runtime/vlop_arm_test.go` の追加

*   **`armFloatWrite` 関数**:
    *   `//go:noinline` ディレクティブは、コンパイラがこの関数をインライン化しないように指示します。これにより、特定の呼び出し規約とアセンブリコード生成が保証され、テストの意図が損なわれないようにします。
    *   `a[128] = 128.0` という行が、大きなオフセットを持つ配列要素への浮動小数点ストア操作を引き起こします。コメントには、この操作がARMv5でどのように誤コンパイルされていたか、そしてその結果として生成されるアセンブリコードのシーケンスが詳細に記述されています。特に `add fp, fp, r0` の部分が、ソフトウェア浮動小数点エミュレータによって正しく処理されなかったことが指摘されています。
*   **`TestArmFloatBigOffsetWrite` 関数**:
    *   `armFloatWrite` を呼び出し、その結果として配列 `a` の `a[128]` が正しく `128.0` に設定されているかを検証します。他の要素が変更されていないことも確認します。
*   **`armFloatRead` 関数**:
    *   `a[128]` の値を読み取る関数です。これも `//go:noinline` が指定されています。
*   **`TestArmFloatBigOffsetRead` 関数**:
    *   `armFloatRead` を呼び出し、`a[128]` から読み取られた値が期待通り `128.0` であるかを検証します。

これらのテストケースは、修正が正しく機能し、大きなオフセットを持つ浮動小数点ストアおよびロード操作がARMv5アーキテクチャで期待通りに動作することを確認するために追加されました。

# [インデックス 22275] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）の内部におけるハッシュテーブルの実装を、C言語で書かれたカスタム実装からGo言語の組み込み`map`型に置き換えるものです。これにより、コンパイラのシンボル管理がよりGoらしい慣用的な方法に改善されます。

変更されたファイルは以下の通りです。

*   `src/cmd/internal/gc/export.go`: エクスポートデータの処理に関連する変更。
*   `src/cmd/internal/gc/fmt.go`: フォーマット処理に関連する変更。
*   `src/cmd/internal/gc/go.go`: コンパイラの主要なデータ構造定義に関連する変更。`Pkg`構造体に`Syms`マップが追加され、グローバルなハッシュテーブルが削除されています。
*   `src/cmd/internal/gc/go.y`: Yacc/Bisonで生成されたパーサーの定義ファイル。インポート処理に関連する変更。
*   `src/cmd/internal/gc/init.go`: `init`関数の処理に関連する変更。
*   `src/cmd/internal/gc/lex.go`: 字句解析器に関連する変更。シンボルルックアップの変更。
*   `src/cmd/internal/gc/reflect.go`: リフレクション情報の生成に関連する変更。
*   `src/cmd/internal/gc/subr.go`: サブルーチンやユーティリティ関数に関連する変更。シンボルルックアップのコアロジックが大幅に変更されています。
*   `src/cmd/internal/gc/typecheck.go`: 型チェックに関連する変更。構造体リテラルの重複フィールドチェックにマップが使用されています。
*   `src/cmd/internal/gc/y.go`: Yacc/Bisonで生成されたパーサーの定義ファイル。インポート処理に関連する変更。

## 変更の背景

このコミットの主な背景は、Goコンパイラ（`cmd/internal/gc`）の内部実装を、よりGo言語のイディオムに沿った形に近代化することにあります。

元々、Goコンパイラの一部はC言語で書かれており、その名残としてカスタムのハッシュテーブル実装が使用されていました。このハッシュテーブルは、シンボル（変数名、関数名など）を管理するためのシンボルテーブルとして機能し、`(シンボル名, パッケージ)`のペアをキーとしていました。

しかし、Go言語には強力で最適化された組み込みの`map`型が存在します。カスタムのC言語ハッシュテーブルをGoの`map`に置き換えることで、以下のようなメリットが期待されます。

1.  **コードの簡素化と保守性の向上**: カスタムのハッシュテーブル実装は、ハッシュ関数の定義、衝突解決、メモリ管理など、多くの低レベルな詳細を開発者が手動で管理する必要がありました。Goの`map`を使用することで、これらの複雑さが抽象化され、コードがより簡潔になり、バグの発生リスクが低減し、保守が容易になります。
2.  **Goランタイムとの統合**: Goの`map`はGoランタイムと密接に統合されており、ガベージコレクションや並行処理の恩恵を最大限に受けることができます。カスタム実装では、これらの最適化を独自に実装する必要がありました。
3.  **パフォーマンスの改善**: コミットメッセージにある「non-allocating []byte key lookups」は重要なポイントです。Goの`map`は、`string`だけでなく`[]byte`もキーとして使用できます。`[]byte`をキーとして使用する場合、文字列への変換（メモリ割り当てを伴う可能性がある）を避けることで、ルックアップ時のオーバーヘッドを削減し、パフォーマンスを向上させることができます。コンパイラは頻繁にシンボル名をルックアップするため、この最適化は全体的なコンパイル速度に寄与します。
4.  **Go言語の慣用的な利用**: Go言語で書かれたプロジェクトでは、組み込みのデータ構造を最大限に活用することが推奨されます。カスタムのC言語スタイルをGoの`map`に置き換えることは、プロジェクト全体のコードベースの一貫性を高め、新しい開発者がコードを理解しやすくすることにも繋がります。

ただし、この変更には副作用もありました。元のC言語ハッシュテーブルは、要素が追加された順序ではなく、ハッシュ値に基づいた「ハッシュテーブル順序」でエクスポートデータや`init`関数の呼び出しを出力していました。Goの`map`は要素の順序を保証しないため、この変更により、エクスポートデータや`init`呼び出しの出力順序が「テーブルに追加された順序」に変わります。これは、生成されるオブジェクトファイルのバイナリ互換性に影響を与える可能性がありますが、コンパイラの機能的な正しさには影響しないと判断されたものと考えられます。

## 前提知識の解説

### Goコンパイラ (`cmd/internal/gc`)

Go言語の公式コンパイラは、主にGo言語自体で書かれています。`cmd/internal/gc`は、そのフロントエンド部分を指します。これは、Goのソースコードを解析し、抽象構文木（AST）を構築し、型チェック、最適化、中間コード生成などを行う役割を担っています。最終的には、バックエンドがこの中間コードをターゲットアーキテクチャの機械語に変換します。

### ハッシュテーブル

ハッシュテーブル（またはハッシュマップ、連想配列）は、キーと値のペアを格納するデータ構造です。キーをハッシュ関数に通してハッシュ値（インデックス）を計算し、そのインデックスを使って内部配列の対応する位置に値を格納します。これにより、平均的にはO(1)の高速な検索、挿入、削除が可能になります。衝突（異なるキーが同じハッシュ値を生成すること）が発生した場合は、チェイニング（リンクリストで連結）やオープンアドレス法などの方法で解決されます。

### Goの `map`

Go言語の`map`は、組み込みのハッシュテーブル実装です。`map[KeyType]ValueType`という構文で宣言され、キーと値のペアを格納します。Goの`map`は、以下のような特徴を持ちます。

*   **組み込み型**: 言語に組み込まれているため、効率的で最適化されています。
*   **型安全性**: キーと値の型がコンパイル時に決定され、型安全性が保証されます。
*   **動的なサイズ変更**: 要素の追加や削除に応じて、内部的に自動的にサイズが調整されます。
*   **順序の非保証**: `map`をイテレートする際の要素の順序は保証されません。これは、ハッシュテーブルの内部実装に依存するためです。

### シンボルテーブル

コンパイラにおけるシンボルテーブルは、プログラム内で使用されるすべての識別子（シンボル）に関する情報を格納するデータ構造です。これには、変数名、関数名、型名、パッケージ名などが含まれます。シンボルテーブルは、コンパイルの様々な段階で利用されます。

*   **字句解析**: 識別子を認識し、シンボルテーブルに登録します。
*   **構文解析**: 識別子の使用箇所を解決し、シンボルテーブルのエントリと関連付けます。
*   **意味解析（型チェック）**: 識別子の型やスコープをチェックし、正当性を検証します。
*   **コード生成**: シンボルテーブルの情報（メモリ位置など）に基づいて、実行可能なコードを生成します。

シンボルテーブルは、コンパイラがプログラムの構造と意味を理解するために不可欠な要素です。

### `Sym` と `Pkg` 構造体

Goコンパイラにおいて、`Sym`と`Pkg`はシンボルテーブル管理の中核をなす構造体です。

*   **`Sym` (Symbol)**: 個々のシンボル（識別子）を表します。シンボル名、それが属するパッケージ、型情報、定義されている場所（ノード）、その他のフラグなど、シンボルに関する詳細な情報が格納されます。
*   **`Pkg` (Package)**: Goのパッケージを表します。パッケージ名、インポートパス、そのパッケージに属するシンボル群など、パッケージに関する情報が格納されます。

このコミット以前は、グローバルなハッシュテーブルが`Sym`オブジェクトを管理していましたが、このコミットにより、各`Pkg`構造体内にそのパッケージに属する`Sym`オブジェクトを管理するための`map[string]*Sym`が導入されました。

### エクスポートデータと `init` 呼び出しの順序

Goコンパイラは、コンパイルされたパッケージの情報を他のパッケージが利用できるように「エクスポートデータ」として出力します。また、Goプログラムにはパッケージの初期化時に自動的に実行される`init`関数があります。

このコミット以前は、これらのエクスポートデータや`init`関数の呼び出しは、内部のC言語ハッシュテーブルの「ハッシュテーブル順序」で出力されていました。これは、ハッシュ関数の結果に依存する順序であり、必ずしもソースコード上の定義順やアルファベット順ではありませんでした。

Goの`map`は要素の順序を保証しないため、`map`に置き換えることで、これらの出力順序が「テーブルに追加された順序」に変わります。これは、コンパイラがシンボルを処理する内部的な順序に依存することになります。通常、これは機能的な問題を引き起こしませんが、生成されるバイナリのバイト列が以前とは異なることを意味します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に`src/cmd/internal/gc/go.go`、`src/cmd/internal/gc/subr.go`、`src/cmd/internal/gc/init.go`、`src/cmd/internal/gc/typecheck.go`に集中しています。

1.  **`src/cmd/internal/gc/go.go`**:
    *   `Pkg`構造体に`Syms map[string]*Sym`フィールドが追加されました。
    *   グローバル変数`hash`と`phash`が削除されました。

2.  **`src/cmd/internal/gc/subr.go`**:
    *   `stringhash`関数が削除され、`Lookup`および`LookupBytes`関数が`Pkg`のメソッドとして再定義されました。
    *   `Pkglookup`関数が`pkg.Lookup(name)`を呼び出すように変更されました。
    *   `mkpkg`関数が`pkgMap`と`pkgs`スライスを使用してパッケージを管理するように変更されました。
    *   `importdot`関数内のシンボル走査ロジックが、グローバルハッシュテーブルの走査から`opkg.Syms`マップの走査に変更されました。

3.  **`src/cmd/internal/gc/init.go`**:
    *   `init`関数シンボルを走査するループが、グローバルハッシュテーブルの走査から`initSyms`スライスの走査に変更されました。

4.  **`src/cmd/internal/gc/typecheck.go`**:
    *   `fielddup`関数で、重複フィールドチェックのためのハッシュテーブルが`map[string]bool`に置き換えられました。

## コアとなるコードの解説

### `Pkg`構造体の変更 (`src/cmd/internal/gc/go.go`)

```go
type Pkg struct {
	Path     string
	Pathsym  *Sym
	Prefix   string
	// Link     *Pkg // 削除
	Imported uint8
	Exported int8
	Direct   int8
	Safe     bool
	Syms     map[string]*Sym // 追加
}
```

この変更は、シンボル管理のパラダイムシフトを象徴しています。以前は、すべてのシンボルが単一のグローバルなハッシュテーブルにフラットに格納されていました。しかし、Goのプログラムはパッケージによって構造化されており、シンボルは特定のパッケージに属します。`Pkg`構造体に`Syms map[string]*Sym`を追加することで、各パッケージが自身のシンボルを直接管理できるようになり、シンボルルックアップの際にパッケージのコンテキストを自然に利用できるようになりました。これにより、シンボルテーブルの構造がより論理的で、Goのパッケージシステムと整合性が取れるようになりました。

### シンボルルックアップロジックの変更 (`src/cmd/internal/gc/subr.go`)

```go
// 以前のグローバルハッシュテーブルと関連関数は削除

var initSyms []*Sym // init関数シンボルを格納するスライス

var nopkg = new(Pkg) // nil Pkgの場合のデフォルト

func (pkg *Pkg) Lookup(name string) *Sym {
	if pkg == nil {
		pkg = nopkg // nilチェック
	}
	if s := pkg.Syms[name]; s != nil {
		return s // マップから既存のシンボルを返す
	}

	// シンボルが見つからない場合、新しく作成してマップに追加
	s := &Sym{
		Name:    name,
		Pkg:     pkg,
		Lexical: LNAME,
	}
	if s.Name == "init" {
		initSyms = append(initSyms, s) // init関数シンボルを追跡
	}
	if pkg.Syms == nil {
		pkg.Syms = make(map[string]*Sym) // マップがnilなら初期化
	}
	pkg.Syms[name] = s
	return s
}

func (pkg *Pkg) LookupBytes(name []byte) *Sym {
	if pkg == nil {
		pkg = nopkg
	}
	if s := pkg.Syms[string(name)]; s != nil {
		return s
	}
	str := internString(name) // []byteをstringにインターン（重複を避ける）
	return pkg.Lookup(str)
}

func Pkglookup(name string, pkg *Pkg) *Sym {
	return pkg.Lookup(name) // PkglookupはPkg.Lookupのラッパーに
}
```

このセクションは、シンボルルックアップのメカニズムが根本的に変更されたことを示しています。

*   **グローバルハッシュテーブルの廃止**: 以前は、`hash`というグローバル配列を線形探索またはリンクリストを辿ってシンボルを検索していました。この複雑なC言語スタイルのロジックが完全に削除されました。
*   **`Pkg.Lookup`メソッドの導入**: シンボルルックアップの責任が`Pkg`構造体に移譲されました。これにより、シンボルがどのパッケージに属するかという情報がルックアップのコンテキストとして常に利用されるようになりました。`map[string]*Sym`を使用することで、Goランタイムが提供する最適化されたハッシュルックアップを利用できます。
*   **`LookupBytes`による最適化**: コンパイラは、ソースコードから読み取ったシンボル名を`[]byte`として扱うことがよくあります。`LookupBytes`メソッドは、この`[]byte`を直接キーとして`map`に渡すことで、`[]byte`から`string`への変換に伴うメモリ割り当てを避けることができます。`internString`関数は、同じ文字列が複数回出現する場合に、それらを単一の`string`オブジェクトにマッピングすることで、メモリ使用量をさらに最適化します。
*   **`initSyms`スライス**: `init`関数はGoプログラムの初期化において特別な役割を果たすため、それらのシンボルを効率的に収集・管理するために専用のスライス`initSyms`が導入されました。これにより、`init`関数の処理が高速化されます。

### パッケージルックアップロジックの変更 (`src/cmd/internal/gc/subr.go`)

```go
var pkgMap = make(map[string]*Pkg) // パスからPkgへのマップ
var pkgs []*Pkg // すべてのPkgを順序付けて保持するスライス

func mkpkg(path string) *Pkg {
	if p := pkgMap[path]; p != nil {
		return p // 既存のPkgを返す
	}

	// 新しいPkgを作成し、マップとスライスに追加
	p := new(Pkg)
	p.Path = path
	p.Prefix = pathtoprefix(path)
	// p.Link = phash[h] // 削除
	// phash[h] = p     // 削除
	pkgMap[path] = p
	pkgs = append(pkgs, p)
	return p
}
```

この変更は、パッケージ自体の管理方法を改善しています。

*   **`pkgMap`の導入**: パッケージのパスをキーとする`map[string]*Pkg`を導入することで、特定のパスに対応する`Pkg`オブジェクトをO(1)で高速に検索できるようになりました。以前の`phash`配列を線形探索するよりも効率的です。
*   **`pkgs`スライスの導入**: `pkgs`スライスは、コンパイラが処理したすべての`Pkg`オブジェクトを、それらが作成された順序で保持します。これは、エクスポートデータや`init`呼び出しの順序が「テーブルに追加された順序」に変わるというコミットメッセージの記述と直接関連しています。このスライスをイテレートすることで、特定の順序でパッケージを処理する必要がある場合に利用されます。

これらの変更は、Goコンパイラの内部構造をよりGo言語のイディオムに適合させ、パフォーマンスと保守性を向上させるための重要なステップです。

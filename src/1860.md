# [インデックス 1860] ファイルの概要

このコミットは、Go言語のx86アーキテクチャ向けツールチェイン（アセンブラ `8a`、コンパイラ `8c`、リンカ `8l`）における重要な変更を導入しています。主な目的は、新しいオブジェクトファイルフォーマットへの対応、`extern register` 機能の追加、そしてセグメント化されたスタックチェックの実装です。これにより、Goプログラムの実行時におけるスタック管理が改善され、より堅牢な実行環境が提供されます。

## 変更の背景

このコミットは、Go言語の初期開発段階におけるランタイムの基盤を強化するために行われました。主な背景は以下の通りです。

1.  **新しいオブジェクトファイルフォーマットへの移行**: Goコンパイラとアセンブラが生成するオブジェクトファイルの内部構造が変更され、リンカがそれを正しく解釈・リンクできるようにするための更新が必要でした。これにより、将来的な機能拡張や最適化の余地が生まれます。
2.  **`extern register`の導入**: 特定のグローバル変数やスレッドローカルなデータへのアクセスを効率化するため、x86アーキテクチャのFSセグメントレジスタを介したアドレス指定を可能にする `extern register` という概念が導入されました。これは、特にGoのランタイムがゴルーチン（goroutine）のコンテキスト情報（`g` ポインタ）やマシン（`m` ポインタ）の情報を効率的に管理するために重要です。
3.  **セグメント化されたスタックチェックの実装**: Goの初期のランタイムは、スタックを必要に応じて動的に拡張する「セグメント化されたスタック」を採用していました。この方式では、関数呼び出し時にスタックオーバーフローが発生しないかを確認するチェックが必要です。このコミットは、リンカがこのスタックチェックコードを自動的に生成するように変更し、ランタイムの安全性と効率性を向上させました。これにより、スタックの枯渇によるクラッシュを防ぎ、必要に応じてスタックを拡張するメカニズムが機能するようになります。

これらの変更は、Goプログラムのコンパイル、リンク、および実行時の安定性とパフォーマンスを向上させるための基盤を築くものでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念が前提となります。

1.  **Goツールチェイン (8a, 8c, 8l)**:
    *   `8a`: x86アーキテクチャ向けのアセンブラ。アセンブリ言語のソースコードをオブジェクトファイルに変換します。
    *   `8c`: x86アーキテクチャ向けのGoコンパイラ。Goのソースコードをアセンブリ言語またはオブジェクトファイルに変換します。
    *   `8l`: x86アーキテクチャ向けのGoリンカ。複数のオブジェクトファイルを結合し、実行可能ファイルを生成します。
    これらはPlan 9のツールチェインに由来しており、Goの初期開発において採用されました。

2.  **オブジェクトファイルフォーマット**: コンパイラやアセンブラが生成する中間ファイルで、機械語コード、データ、シンボル情報などが含まれます。リンカはこのファイルを読み込み、最終的な実行可能ファイルを生成します。フォーマットの変更は、これらのツール間の互換性に影響を与えます。

3.  **x86セグメントレジスタ (FS)**: x86アーキテクチャには、コードセグメント (CS)、データセグメント (DS)、スタックセグメント (SS) などのセグメントレジスタがあります。FSレジスタは、通常、スレッドローカルストレージ (TLS) や、Goランタイムにおけるゴルーチン構造体 (`g`) やマシン構造体 (`m`) へのポインタを指すために使用されます。FSセグメントを介したアクセスは、特定のメモリ領域への高速かつ相対的なアドレッシングを可能にします。

4.  **セグメント化されたスタック (Segmented Stacks)**: Goの初期バージョンで採用されていたスタック管理方式です。関数呼び出し時にスタックが足りなくなると、新しいより大きなスタックセグメントを割り当て、古いセグメントとリンクすることでスタックを動的に拡張します。これにより、固定サイズのスタックで発生するスタックオーバーフローを回避しつつ、必要以上に大きなスタックを最初から確保する無駄を省きます。しかし、スタックの拡張・縮小にはオーバーヘッドが伴い、後にGo 1.3で連続スタック (Contiguous Stacks) に置き換えられました。

5.  **スタックチェック (Stack Checks)**: セグメント化されたスタックでは、関数が呼び出されるたびに、現在のスタックセグメントに残りの容量があるかを確認する必要があります。容量が不足している場合、ランタイムの `morestack` 関数が呼び出され、新しいスタックセグメントが割り当てられます。このチェックは、通常、関数のプロローグ（開始部分）に挿入されるコードによって行われます。

6.  **`sys·morestack`**: Goランタイムの内部関数で、スタックが不足した際に呼び出され、新しいスタックセグメントを割り当てたり、スタックを切り替えたりする処理を担当します。

## 技術的詳細

このコミットは、Goツールチェインの複数のコンポーネントにわたる広範な変更を含んでいます。

### 新しいオブジェクトフォーマットへの対応

*   **`offset2` フィールドの追加**: `src/cmd/8a/a.h` の `Gen` 構造体と `src/cmd/8c/gc.h` の `Adr` 構造体に `int32 offset2` フィールドが追加されました。これは、新しいアドレス指定モードやデータ表現に対応するためのものです。
*   **`D_CONST2` 型の導入**: `src/cmd/8l/8.out.h` に `D_CONST2` という新しいアドレスタイプが定義されました。これは、2つのオフセット値を持つ定数を表現するために使用されます。アセンブラ (`8a`) とリンカ (`8l`) は、この新しい型を処理できるようになりました。
*   **オブジェクトファイルヘッダの変更**: `src/cmd/8l/obj.c` の `ldobj` 関数が変更され、オブジェクトファイルの先頭に特定の文字列 (`thestring`) と `!\n` というマーカーを読み込むようになりました。これは、オブジェクトファイルのバージョン管理や整合性チェックに利用されます。

### `extern register` サポート

*   **`OEXREG` オペレーションの追加**: `src/cmd/cc/cc.h` に `OEXREG` という新しいオペレーションが追加され、`src/cmd/cc/com.c` と `src/cmd/cc/sub.c` で処理されます。これは、Cコンパイラが `extern register` キーワードを認識し、それに対応するアセンブリコードを生成するためのものです。
*   **FSセグメント相対アドレッシング**: `src/cmd/8c/txt.c` の `naddr` 関数は、`OEXREG` タイプのアドレスを `D_INDIR + D_FS` タイプに変換します。これは、x86のFSセグメントレジスタをベースとした間接アドレッシングを意味します。`exreg` 関数は、FSセグメント内のオフセットを管理し、`g` や `m` ポインタのようなランタイムの重要なデータ構造へのアクセスを効率化します。

### セグメント化されたスタックチェックの生成

*   **`NOSPLIT` フラグの導入**: `src/cmd/8l/8.out.h` に `NOSPLIT` という新しいフラグが追加されました。これは、特定の関数（例えば `sys·morestack` 自体）がスタックチェックを生成しないようにリンカに指示するために使用されます。
*   **`dostkoff` 関数の大幅な変更**: `src/cmd/8l/pass.c` の `dostkoff` 関数は、リンカがスタックチェックコードを挿入する主要な場所です。
    *   `sys·morestack` シンボルを検索し、そのアドレスを取得します。
    *   各関数のプロローグに、以下の命令シーケンスを挿入します（`NOSPLIT` フラグが設定されていない場合）。
        1.  `AMOVL D_INDIR+D_FS, D_CX`: FSセグメントのオフセット0からゴルーチン構造体 (`g`) へのポインタを `CX` レジスタにロードします。
        2.  **スタックオーバーフローチェック**:
            *   小さいスタックの場合 (`autoffset <= 75`): `ACMPL D_SP, D_INDIR+D_CX`: スタックポインタ (`SP`) と `g->stackguard` (FSセグメントのオフセット0から4バイト目にあるスタックガード値) を比較します。
            *   大きいスタックの場合 (`autoffset > 75`): `ALEAL -(autoffset-75)(SP), AX; ACMPL D_AX, D_INDIR+D_CX`: 必要なスタックサイズを考慮して、`SP` から計算したアドレスと `g->stackguard` を比較します。
        3.  `AJHI`: 比較結果に基づいて、スタックが十分な場合は `morestack` 呼び出しをスキップします。
        4.  `AMOVL D_INDIR+D_FS+4, D_DX`: FSセグメントのオフセット4からマシン構造体 (`m`) へのポインタを `DX` レジスタにロードします。
        5.  `AMOVL D_CONST, D_INDIR+D_DX+4`: `autoffset` (自動変数領域のサイズ) を `m->autostack` (DX+4) に保存します。
        6.  `AMOVL D_CONST, D_INDIR+D_DX+8`: `textarg` (関数の引数サイズ) を `m->textarg` (DX+8) に保存します。
        7.  `ACALL sys·morestack`: スタックが不足している場合、`sys·morestack` 関数を呼び出します。
    *   デバッグフラグ (`-K`) が有効な場合、スタックアンダーフローチェックも追加されます。

### その他の変更

*   **`CMPXCHG` 命令のサポート**: `src/cmd/8a/lex.c` と `src/cmd/8l/optab.c` で `CMPXCHGB`, `CMPXCHGL`, `CMPXCHGW` 命令（比較交換命令）が追加されました。これは、アトミック操作をサポートするために重要です。
*   **`Biobuf` への移行**: `src/cmd/8l/obj.c` のファイルI/O処理が、従来の `read`/`open`/`close` から `Biobuf` (バッファリングされたI/O) を使用するように変更されました。これにより、I/O効率が向上します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに集中しています。

1.  **`src/cmd/8l/pass.c`**: `dostkoff` 関数が大幅に修正され、セグメント化されたスタックチェックのロジックが実装されました。これは、Goの関数呼び出し規約とスタック管理の根幹に関わる部分です。
2.  **`src/cmd/8l/obj.c`**: `ldobj` 関数が新しいオブジェクトファイルフォーマットを読み込むように変更され、`zaddr` 関数も `Biobuf` を使用するように書き換えられました。これは、リンカがコンパイラ/アセンブラからの出力を正しく処理するための基盤です。
3.  **`src/cmd/8c/sgen.c`**: `codgen` 関数が `ATEXT` 疑似命令の処理を変更し、関数の引数サイズを `D_CONST2` タイプでオブジェクトファイルに書き込むようになりました。また、`OEXREG` の処理も追加されています。

## コアとなるコードの解説

### `src/cmd/8l/pass.c` の `dostkoff` 関数

この関数は、Goのリンカ (`8l`) において、各関数のスタックフレームオフセットを計算し、必要に応じてスタックチェックコードを挿入する役割を担います。

変更点の中で最も重要なのは、`pmorestack` シンボル（`sys·morestack` 関数へのポインタ）の検索と、それに続くスタックチェックコードの挿入ロジックです。

```c
// src/cmd/8l/pass.c
// ...
	pmorestack = P;
	symmorestack = lookup("sys·morestack", 0);

	if(symmorestack->type == STEXT)
	for(p = firstp; p != P; p = p->link) {
		if(p->as == ATEXT) {
			if(p->from.sym == symmorestack) {
				pmorestack = p;
				p->from.scale |= NOSPLIT; // sys·morestack itself should not have stack checks
				break;
			}
		}
	}
	if(pmorestack == P)
		diag("sys·morestack not defined");
// ...
// Inside the loop for each ATEXT (function)
// ...
			q = P;
			q1 = P;
			if(pmorestack != P)
			if(!(p->from.scale & NOSPLIT)) { // If NOSPLIT is not set, insert stack checks
				p = appendp(p);	// load g into CX
				p->as = AMOVL;
				p->from.type = D_INDIR+D_FS;
				p->from.offset = 0; // g is at FS:0
				p->to.type = D_CX;

				// ... (stack underflow check for debug builds) ...

				if(autoffset < 4096) {  // do we need to call morestack
					if(autoffset <= 75) { // small stack
						p = appendp(p);
						p->as = ACMPL;
						p->from.type = D_SP;
						p->to.type = D_INDIR+D_CX; // Compare SP with g->stackguard
					} else { // large stack
						p = appendp(p);
						p->as = ALEAL;
						p->from.type = D_INDIR+D_SP;
						p->from.offset = -(autoffset-75); // Calculate required stack bottom
						p->to.type = D_AX;

						p = appendp(p);
						p->as = ACMPL;
						p->from.type = D_AX;
						p->to.type = D_INDIR+D_CX; // Compare calculated stack bottom with g->stackguard
					}

					// common
					p = appendp(p);
					p->as = AJHI; // Jump if SP (or calculated value) is higher than stackguard
					p->to.type = D_BRANCH;
					p->to.offset = 4; // Jump over the morestack call
					q = p;
				}

				p = appendp(p);	// load m into DX
				p->as = AMOVL;
				p->from.type = D_INDIR+D_FS;
				p->from.offset = 4; // m is at FS:4
				p->to.type = D_DX;

				p = appendp(p);	// save autoffset in 4(DX)
				p->as = AMOVL;
				p->to.type = D_INDIR+D_DX;
				p->to.offset = 4; // m->autostack
				p->from.type = D_CONST;
				if(autoffset+160 > 4096)
					p->from.offset = (autoffset+160) & ~7LL;

				p = appendp(p);	// save textarg in 8(DX)
				p->as = AMOVL;
				p->to.type = D_INDIR+D_DX;
				p->to.offset = 8; // m->textarg
				p->from.type = D_CONST;
				p->from.offset = curtext->to.offset2; // Function argument size

				p = appendp(p);
				p->as = ACALL;
				p->to.type = D_BRANCH;
				p->pcond = pmorestack; // Call sys·morestack
				p->to.sym = symmorestack;

			}
			if(q != P)
				q->pcond = p->link; // Link the AJHI to the instruction after the morestack call
// ...
```

このコードは、Goの関数が呼び出されるたびに、スタックの残りの容量をチェックし、必要であれば `sys·morestack` を呼び出してスタックを拡張するメカニズムを実装しています。`D_FS` を使用して `g` と `m` ポインタにアクセスしている点が、`extern register` の概念と密接に関連しています。

### `src/cmd/8c/txt.c` の `naddr` および `exreg` 関数

これらの関数は、Cコンパイラ (`8c`) が `extern register` 変数をどのように処理するかを示しています。

```c
// src/cmd/8c/txt.c
// ...
case OEXREG: // Handle OEXREG operation
	a->type = D_INDIR + D_FS; // Set address type to FS-relative indirect
	a->offset = n->reg - 1; // Calculate offset within FS segment
	break;
// ...

int32
exreg(Type *t)
{
	int32 o;

	if(typechlp[t->etype]){ // If type is char, short, long, pointer
		if(exregoffset >= 32) // Limit the number of extern registers
			return 0;
		o = exregoffset;
		exregoffset += 4; // Allocate 4 bytes for the register
		return o+1;	// +1 to avoid 0 == failure; naddr case OEXREG will -1.
	}

	USED(t);
	return 0;
}
```

`exreg` 関数は、`extern register` として宣言された変数にFSセグメント内のオフセットを割り当てます。`naddr` 関数は、そのオフセットを使用して `D_INDIR+D_FS` というアドレスタイプを生成し、リンカがFSセグメント相対のアドレッシングを行うように指示します。これにより、Goランタイムの重要なデータ（`g` や `m`）がFSセグメントに配置され、効率的にアクセスできるようになります。

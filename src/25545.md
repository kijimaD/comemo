# [インデックス 25545] ファイルの概要

このコミットは、Go言語の`crypto/tls`パッケージにおいて、TLS (Transport Layer Security) のServer Name Indication (SNI) 拡張でIPアドレスリテラルを送信しないように修正するものです。これは、RFC 6066の仕様に準拠するための重要な変更です。

## 変更の背景

この変更の背景には、TLSプロトコルの拡張であるServer Name Indication (SNI) の仕様と、Go言語の`crypto/tls`パッケージの実装における不整合がありました。

RFC 6066のセクション3では、SNI拡張の`HostName`フィールドに「リテラルなIPv4およびIPv6アドレスは許可されない」と明確に規定されています。SNIは、単一のIPアドレスで複数のドメインをホストするサーバーが、クライアントがどのドメインに接続しようとしているかを識別し、適切なTLS証明書を提示できるようにするために設計されたものです。このメカニズムはドメイン名に基づいており、IPアドレスリテラルは想定されていません。

しかし、Goの`crypto/tls`パッケージでは、`Config.ServerName`フィールドにIPアドレスリテラルが設定された場合（例えば、IPアドレスを直接指定して`Dial`を呼び出した場合など）、そのIPアドレスリテラルがそのままSNI値として送信されてしまう問題がありました。これはRFCの規定に反するため、一部のTLSサーバーやプロキシで問題を引き起こす可能性がありました。

このコミットは、この仕様違反を修正し、GoのTLSクライアントがRFC 6066に準拠するようにするために導入されました。具体的には、`Config.ServerName`がIPアドレスリテラルであると認識された場合、SNI値として送信しないように変更されています。これにより、TLSハンドシェイクの互換性と堅牢性が向上します。

## 前提知識の解説

### TLS (Transport Layer Security) とハンドシェイク

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。クライアントとサーバー間で安全な接続を確立するプロセスは「TLSハンドシェイク」と呼ばれます。このハンドシェイク中に、両者はプロトコルバージョン、暗号スイート、証明書などを交換し、共有の秘密鍵を確立します。

### Server Name Indication (SNI)

SNIは、TLSプロトコルの拡張機能の一つで、クライアントがTLSハンドシェイクの初期段階（ClientHelloメッセージ）で接続しようとしているサーバーのホスト名（ドメイン名）を伝えることを可能にします。これにより、単一のIPアドレスで複数のウェブサイト（それぞれ異なるドメイン名とTLS証明書を持つ）をホストしているサーバーが、クライアントがどのサイトにアクセスしようとしているかを判断し、適切な証明書を提示できるようになります。SNIがなければ、サーバーはどの証明書を提示すべきか判断できず、デフォルトの証明書を返すか、接続を拒否するしかありませんでした。

### RFC 6066

RFC 6066は、TLSプロトコルの拡張機能について定義しているIETFの文書です。この文書のセクション3でSNI拡張が規定されており、その中で`HostName`フィールドにはIPアドレスリテラルを含めるべきではないと明記されています。

### `net.ParseIP`関数

Go言語の`net`パッケージに含まれる`net.ParseIP`関数は、文字列として与えられたIPアドレスを解析し、`net.IP`型のオブジェクトに変換します。
*   入力文字列が有効なIPv4またはIPv6アドレスのテキスト表現である場合、対応する`net.IP`オブジェクトを返します。
*   入力文字列が有効なIPアドレスでない場合、`nil`を返します。

この関数は、文字列がIPアドレスであるかどうかを効率的に判定するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、TLSクライアントハンドシェイクのロジックに、`Config.ServerName`がIPアドレスリテラルであるかどうかをチェックする処理を追加し、もしそうであればSNIとして送信しないようにすることです。

具体的には、`src/crypto/tls/handshake_client.go`内の`clientHandshake`関数が変更されています。この関数は、TLSクライアントがサーバーとのハンドシェイクを開始する際にClientHelloメッセージを構築する役割を担っています。

変更前は、`c.config.ServerName`の値が直接`clientHelloMsg`構造体の`serverName`フィールドに割り当てられていました。変更後は、`c.config.ServerName`の値を`net.ParseIP`関数で評価し、それが有効なIPアドレスリテラルであると判断された場合、`serverName`フィールドには空文字列が設定されるようになります。これにより、IPアドレスリテラルがSNI拡張として送信されることを防ぎます。

また、`src/crypto/tls/common.go`の`Config`構造体の`ServerName`フィールドのコメントも更新され、IPアドレスがSNI値として含まれないことが明記されています。

さらに、この変更の正しさを検証するために、`src/crypto/tls/handshake_client_test.go`に新しいテストケース`TestNoIPAddressesInSNI`が追加されています。このテストは、IPv4およびIPv6のリテラルIPアドレスを`ServerName`として設定した場合に、ClientHelloメッセージのペイロード内にそれらのIPアドレスリテラルが含まれていないことを確認します。

func TestNoIPAddressesInSNI(t *testing.T) {
	for _, ipLiteral := range []string{"1.2.3.4", "::1"} {
		c, s := net.Pipe()

		go func() {
			client := Client(c, &Config{ServerName: ipLiteral})
			client.Handshake()
		}()

		var header [5]byte
		if _, err := io.ReadFull(s, header[:]); err != nil {
			t.Fatal(err)
		}
		recordLen := int(header[3])<<8 | int(header[4])

		record := make([]byte, recordLen)
		if _, err := io.ReadFull(s, record[:]); err != nil {
			t.Fatal(err)
		}
		s.Close()

		if bytes.Index(record, []byte(ipLiteral)) != -1 {
			t.Errorf("IP literal %q found in ClientHello: %x", ipLiteral, record)
		}
	}
}

## コアとなるコードの解説

### `src/crypto/tls/handshake_client.go`の変更

このファイルでは、`clientHandshake`関数内でSNI値を設定するロジックが変更されました。

1.  `sni := c.config.ServerName`
    *   まず、`tls.Config`に設定されている`ServerName`の値を`sni`変数にコピーします。
2.  `if net.ParseIP(sni) != nil { sni = "" }`
    *   ここで`net.ParseIP(sni)`が呼び出されます。もし`sni`が有効なIPアドレスリテラルであれば、`net.ParseIP`は`nil`ではない`net.IP`オブジェクトを返します。
    *   この条件が真（つまり`sni`がIPアドレスリテラルである）の場合、`sni`変数は空文字列`""`に上書きされます。
3.  `serverName: sni,`
    *   `clientHelloMsg`構造体の`serverName`フィールドに、この修正された`sni`の値が設定されます。
    *   これにより、`Config.ServerName`がIPアドレスリテラルであっても、実際のSNI拡張にはそのIPアドレスリテラルは含まれず、代わりにSNI拡張自体が送信されないか、空のホスト名が送信されることになります（RFC 6066の要件に準拠）。

### `src/crypto/tls/common.go`の変更

`Config`構造体の`ServerName`フィールドのコメントが更新され、この変更の意図が明確に示されています。
「クライアントのハンドシェイクに含まれるが、それがIPアドレスである場合は含まれない」という記述が追加され、開発者がこのフィールドの挙動を正しく理解できるようになりました。

### `src/crypto/tls/handshake_client_test.go`の追加テスト

`TestNoIPAddressesInSNI`テスト関数は、この修正が正しく機能することを保証します。
*   `"1.2.3.4"` (IPv4) と`"::1"` (IPv6) のIPアドレスリテラルをテストケースとして使用します。
*   各IPアドレスリテラルに対して、`tls.Config`の`ServerName`にそのIPアドレスを設定したクライアントを作成し、ハンドシェイクを実行します。
*   ハンドシェイク中にクライアントから送信されるClientHelloメッセージの生データを読み取ります。
*   `bytes.Index`を使用して、ClientHelloメッセージのペイロード内にIPアドレスリテラルが含まれていないことを確認します。もし含まれていればテストは失敗し、この修正が正しく適用されていないことを示します。

これらの変更により、Goの`crypto/tls`パッケージはSNIのRFC仕様に厳密に準拠し、IPアドレスリテラルが誤ってSNI値として送信されることによる潜在的な互換性問題を回避できるようになりました。

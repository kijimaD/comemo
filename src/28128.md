# [インデックス 28128] ファイルの概要

このコミットは、Go言語の`crypto/cipher`および`crypto/aes`パッケージに、IBM System z (s390x) アーキテクチャ向けのAES-CTRモードの最適化された実装を追加するものです。特に、`ctrAble`という新しいインターフェースを導入し、ブロック暗号がCTRモードの処理を効率的に行えるようにすることで、s390x環境でのAES-CTRのパフォーマンスを大幅に向上させています。

## コミット

```
crypto/cipher, crypto/aes: add s390x implementation of AES-CTR

This commit adds the new 'ctrAble' interface to the crypto/cipher
package. The role of ctrAble is the same as gcmAble but for CTR
instead of GCM. It allows block ciphers to provide optimized CTR
implementations.

The primary benefit of adding CTR support to the s390x AES
implementation is that it allows us to encrypt the counter values
in bulk, giving the cipher message instruction a larger chunk of
data to work on per invocation.

The xorBytes assembly is necessary because xorBytes becomes a
bottleneck when CTR is done in this way. Hopefully it will be
possible to remove this once s390x has migrated to the ssa
backend.

AESCTR1K  160MB/s ± 6%  867MB/s ± 0%  +442.42%  (p=0.000 n=9+10)
```

## 変更の背景

Go言語の`crypto`パッケージは、様々な暗号アルゴリズムとモードを提供していますが、特定のCPUアーキテクチャにおいては、汎用的な実装よりもアセンブリ言語による最適化が大幅なパフォーマンス向上をもたらすことがあります。このコミットの背景には、IBM System z (s390x) アーキテクチャにおけるAES-CTRモードの性能改善の必要性がありました。

従来のGoの`crypto/cipher`パッケージにおけるCTRモードの実装は、ブロック暗号の`Block`インターフェースを汎用的に利用する形でした。これは多くのアーキテクチャで動作しますが、s390xのような特定のハードウェア命令を持つアーキテクチャでは、その特性を活かしきれていませんでした。特に、CTRモードではカウンタ値を暗号化し、その結果と平文/暗号文をXORする処理が繰り返されます。このカウンタ値の暗号化をブロックごとに個別に行うのではなく、まとめて（バルクで）処理できれば、CPUのパイプライン効率が向上し、スループットが大幅に改善される可能性があります。

また、CTRモードの処理において、暗号化されたカウンタ値とデータとのXOR演算がボトルネックとなることが判明しました。特に、バルク処理を行う場合、このXOR演算の効率が全体の性能に大きく影響します。そのため、s390x向けにこの`xorBytes`関数をアセンブリ言語で実装し、高速化を図る必要がありました。

この変更は、s390xプラットフォーム上でのGoアプリケーションが、より高速な暗号処理を利用できるようにすることを目的としています。

## 前提知識の解説

### 1. AES (Advanced Encryption Standard)
AESは、現代において最も広く利用されている共通鍵暗号方式の一つです。ブロック暗号であり、固定長のデータブロック（128ビット）を鍵を使って暗号化・復号します。鍵長は128ビット、192ビット、256ビットがあります。

### 2. CTR (Counter Mode)
CTRモードは、ブロック暗号をストリーム暗号のように扱うための動作モードです。以下の特徴があります。
*   **カウンタの利用**: 各データブロックに対して、ユニークなカウンタ値を生成し、それをブロック暗号で暗号化します。
*   **XOR演算**: 暗号化されたカウンタ値と平文（または暗号文）をXORすることで、最終的な暗号文（または平文）を得ます。
*   **並列処理**: 各ブロックの暗号化が独立しているため、並列処理が容易であり、高速な処理が可能です。
*   **エラー伝播**: 1ビットのエラーが、対応する暗号文ブロックの1ビットにのみ影響し、他のブロックには伝播しません。

### 3. s390xアーキテクチャ
s390xは、IBMのメインフレームコンピュータ（System z）で使用される64ビットの命令セットアーキテクチャです。このアーキテクチャは、高い信頼性、可用性、保守性（RAS）と、大量のトランザクション処理、I/O処理に特化しています。特定の暗号処理を高速化するためのハードウェア命令（例: Message-Security-Assist Extension）を持つことが多く、これらを活用することでソフトウェア実装よりも大幅な性能向上が期待できます。

### 4. Go言語の`crypto/cipher`パッケージ
Goの標準ライブラリである`crypto/cipher`パッケージは、ブロック暗号やストリーム暗号のインターフェースと、それらを利用した様々な動作モード（CBC, CTR, GCMなど）の実装を提供します。
*   **`cipher.Block`インターフェース**: ブロック暗号の基本的な操作（ブロックサイズ、暗号化、復号）を定義します。
*   **`cipher.Stream`インターフェース**: ストリーム暗号の基本的な操作（XORKeyStream）を定義します。
*   **`cipher.NewCTR`関数**: `cipher.Block`インターフェースを実装するブロック暗号と初期ベクトル（IV）を受け取り、`cipher.Stream`インターフェースを返す汎用的なCTRモードのコンストラクタです。

### 5. `gcmAble`インターフェース
Goの`crypto/cipher`パッケージには、既に`gcmAble`というインターフェースが存在します。これは、ブロック暗号がGCM (Galois/Counter Mode) の最適化された実装を提供できる場合に実装するインターフェースです。`NewGCM`関数は、この`gcmAble`インターフェースをチェックし、もし実装されていればその最適化されたGCM実装を利用します。今回の`ctrAble`は、この`gcmAble`と同様の役割をCTRモードに対して提供するものです。

### 6. アセンブリ言語による最適化
Go言語は通常、Goコンパイラによって機械語にコンパイルされますが、特定のパフォーマンスが要求される箇所や、ハードウェア固有の命令を利用したい場合には、アセンブリ言語で関数を記述することができます。Goのツールチェーンは、Goのアセンブリ言語（Plan 9アセンブリに似た構文）をサポートしており、これによってCPUのレジスタを直接操作したり、特定のSIMD命令などを利用して処理を高速化することが可能です。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、以下の主要な要素が挙げられます。

### 1. `ctrAble`インターフェースの導入
`crypto/cipher`パッケージに新しい`ctrAble`インターフェースが追加されました。このインターフェースは、`NewCTR(iv []byte) Stream`というメソッドを定義します。これは、`cipher.Block`を実装する型が、CTRモードのストリーム暗号を生成する際に、独自の最適化された実装を提供できるようにするためのフックとなります。
`cipher.NewCTR`関数は、引数として渡された`cipher.Block`がこの`ctrAble`インターフェースを実装しているかどうかをチェックし、もし実装していれば、その`NewCTR`メソッドを呼び出して最適化された`Stream`を返します。これにより、汎用的なCTR実装と、特定のアーキテクチャ（この場合はs390x）に特化した高性能なCTR実装を透過的に切り替えることが可能になります。

### 2. s390x向けAES-CTRの最適化戦略
s390xアーキテクチャでは、AESのハードウェア命令を利用してカウンタ値の暗号化を効率的に行えます。このコミットでは、カウンタ値を一つずつ暗号化するのではなく、`streamBufferSize`（32 * `BlockSize` = 512バイト）という比較的大きなバッファに複数のカウンタ値をまとめて生成し、それを一括でAES暗号化する戦略を採用しています。
*   `aesctr`構造体: s390x向けのCTRストリームを管理する構造体で、`block`（AESブロック暗号インスタンス）、`ctr`（現在のカウンタ値）、`buffer`（暗号化されたカウンタ値をキャッシュするバッファ）、`storage`（バッファの実際のメモリ領域）を持ちます。
*   `refill()`メソッド: `aesctr`の`buffer`が空になった際に呼び出され、`streamBufferSize`分のカウンタ値を生成し、それを`cryptBlocks`関数（s390xのアセンブリ実装を利用するAES暗号化関数）で一括暗号化して`buffer`に格納します。カウンタ値はビッグエンディアンでインクリメントされます。
*   `XORKeyStream()`メソッド: 実際の暗号化/復号処理を行うメソッドで、`src`データと`buffer`内の暗号化されたカウンタ値を`xorBytes`関数でXORします。`buffer`が不足すれば`refill()`を呼び出して補充します。

この「バルク暗号化」により、CPUのキャッシュ効率が向上し、AES命令の呼び出し回数を減らすことで、大幅な性能向上が実現されています。

### 3. `xorBytes`のアセンブリ実装
CTRモードの処理において、暗号化されたカウンタ値と入力データ（平文または暗号文）とのXOR演算は非常に頻繁に行われます。特に、バルク処理を行う場合、このXOR演算が全体のボトルネックとなることが判明しました。
このため、`src/crypto/aes/asm_s390x.s`に`xorBytes`関数がs390xアセンブリ言語で実装されました。このアセンブリ実装は、Goコンパイラが生成する汎用的なコードよりも、s390xのレジスタや命令セットを直接利用することで、より効率的なバイト列のXOR演算を実現します。具体的には、64ビットレジスタを最大限に活用し、ループアンローリングや効率的なメモリアクセスパターンを用いることで、XOR処理の高速化を図っています。コミットメッセージにもあるように、将来的にGoコンパイラのSSAバックエンドがs390xを完全にサポートすれば、このアセンブリ実装は不要になる可能性も示唆されていますが、現状ではパフォーマンス向上のために不可欠な要素でした。

### 4. パフォーマンス向上
コミットメッセージに記載されているベンチマーク結果が、この最適化の成功を明確に示しています。
`AESCTR1K`ベンチマークにおいて、旧実装の160MB/sから新実装の867MB/sへと、**442.42%**もの速度向上を達成しています。これは、s390xアーキテクチャの特性を活かした最適化が非常に効果的であったことを裏付けています。

### `src/crypto/aes/asm_s390x.s` - `xorBytes` アセンブリ関数

```assembly
// func xorBytes(dst, a, b []byte) int
TEXT ·xorBytes(SB),NOSPLIT,$0-80
	MOVD	dst_base+0(FP), R1  // dstのスライスデータポインタをR1にロード
	MOVD	a_base+24(FP), R2   // aのスライスデータポインタをR2にロード
	MOVD	b_base+48(FP), R3   // bのスライスデータポインタをR3にロード
	MOVD	a_len+32(FP), R4    // aの長さをR4にロード
	MOVD	b_len+56(FP), R5    // bの長さをR5にロード
	CMPBLE	R4, R5, skip        // aの長さとbの長さを比較し、aがb以下ならskipへ
	MOVD	R5, R4              // aの長さがbより大きい場合、R4（処理バイト数）をbの長さに設定
skip:
	MOVD	R4, ret+72(FP)      // 戻り値（処理バイト数）をR4に設定
	MOVD	$0, R5              // オフセットR5を0に初期化
	CMPBLT	R4, $8, tail        // 処理バイト数が8未満ならtailへ（8バイト未満の残りを処理）
loop:
	MOVD	0(R2)(R5*1), R7     // a[R5]から8バイトをR7にロード
	MOVD	0(R3)(R5*1), R8     // b[R5]から8バイトをR8にロード
	XOR	R7, R8              // R7とR8をXORし、結果をR8に格納
	MOVD	R8, 0(R1)(R5*1)     // R8の内容をdst[R5]にストア
	LAY	8(R5), R5           // オフセットR5を8バイト進める
	SUB	$8, R4              // 残り処理バイト数R4を8減らす
	CMPBGE	R4, $8, loop        // 残り処理バイト数が8以上ならloopへ
tail:
	CMPBEQ	R4, $0, done        // 残り処理バイト数が0ならdoneへ
	MOVB	0(R2)(R5*1), R7     // a[R5]から1バイトをR7にロード
	MOVB	0(R3)(R5*1), R8     // b[R5]から1バイトをR8にロード
	XOR	R7, R8              // R7とR8をXORし、結果をR8に格納
	MOVB	R8, 0(R1)(R5*1)     // R8の内容をdst[R5]にストア
	LAY	1(R5), R5           // オフセットR5を1バイト進める
	SUB	$1, R4              // 残り処理バイト数R4を1減らす
	BR	tail                // tailへジャンプ（残りの1バイト未満を処理）
done:
	RET                         // 関数から戻る
```
このアセンブリコードは、`dst`、`a`、`b`という3つのバイトスライスを受け取り、`a`と`b`の短い方の長さだけバイトをXORし、その結果を`dst`に書き込みます。処理されたバイト数を返します。
主要なループでは、一度に8バイト（64ビット）ずつデータをロードし、XOR演算を行い、ストアすることで、効率的な処理を実現しています。残りの8バイト未満のデータは`tail`セクションで1バイトずつ処理されます。s390xの`MOVD`（Move Doubleword）や`XOR`命令を直接利用することで、Goコンパイラが生成するコードよりも高速なバイト操作を可能にしています。

### `src/crypto/aes/ctr_s390x.go` - s390x向けAES-CTR実装

```go
package aes

import (
	"crypto/cipher"
	"unsafe"
)

// Assert that aesCipherAsm implements the ctrAble interface.
var _ ctrAble = (*aesCipherAsm)(nil)

// xorBytes xors the contents of a and b and places the resulting values into
// dst. If a and b are not the same length then the number of bytes processed
// will be equal to the length of shorter of the two. Returns the number
// of bytes processed.
//go:noescape
func xorBytes(dst, a, b []byte) int

// streamBufferSize is the number of bytes of encrypted counter values to cache.
const streamBufferSize = 32 * BlockSize // 32 * 16バイト = 512バイト

type aesctr struct {
	block   *aesCipherAsm          // underlying AES block cipher (s390x specific)
	ctr     [2]uint64              // current counter value (high and low 64-bit parts, big endian)
	buffer  []byte                 // buffer for encrypted counter values
	storage [streamBufferSize]byte // backing array for the buffer slice
}

// NewCTR returns a Stream which encrypts/decrypts using the AES block
// cipher in counter mode. The length of iv must be the same as BlockSize.
func (c *aesCipherAsm) NewCTR(iv []byte) cipher.Stream {
	if len(iv) != BlockSize {
		panic("cipher.NewCTR: IV length must equal block size")
	}
	var ac aesctr
	ac.block = c
	// Initialize counter from IV. IV is 16 bytes, split into two 64-bit uints.
	ac.ctr[0] = *(*uint64)(unsafe.Pointer((&iv[0]))) // high bits
	ac.ctr[1] = *(*uint64)(unsafe.Pointer((&iv[8]))) // low bits
	ac.buffer = ac.storage[:0] // Initialize buffer as empty
	return &ac
}

func (c *aesctr) refill() {
	// Fill up the buffer with an incrementing count.
	c.buffer = c.storage[:streamBufferSize] // Reset buffer to full capacity
	c0, c1 := c.ctr[0], c.ctr[1]            // Get current counter value
	for i := 0; i < streamBufferSize; i += BlockSize {
		b0 := (*uint64)(unsafe.Pointer(&c.buffer[i]))         // Pointer to high 64-bit part in buffer
		b1 := (*uint64)(unsafe.Pointer(&c.buffer[i+BlockSize/2])) // Pointer to low 64-bit part in buffer
		*b0, *b1 = c0, c1                                     // Store current counter value into buffer
		// Increment in big endian: c0 is high, c1 is low.
		c1++
		if c1 == 0 { // Check for carry
			c0++
		}
	}
	c.ctr[0], c.ctr[1] = c0, c1 // Update internal counter state
	// Encrypt the buffer using AES in ECB mode.
	// cryptBlocks is an s390x specific assembly function for bulk AES encryption.
	cryptBlocks(c.block.function, &c.block.key[0], &c.buffer[0], &c.buffer[0], streamBufferSize)
}

func (c *aesctr) XORKeyStream(dst, src []byte) {
	for len(src) > 0 {
		if len(c.buffer) == 0 { // If buffer is empty, refill it
			c.refill()
		}
		// XOR src with the encrypted counter values from buffer
		n := xorBytes(dst, src, c.buffer)
		c.buffer = c.buffer[n:] // Advance buffer
		src = src[n:]           // Advance src
		dst = dst[n:]           // Advance dst
	}
}
```
このファイルは、s390xアーキテクチャに特化したAES-CTRの実装を提供します。
*   `aesCipherAsm`型が`ctrAble`インターフェースを実装していることを表明しています。
*   `xorBytes`関数は、前述のアセンブリ実装へのGoからの呼び出しを宣言しています。`//go:noescape`は、この関数がGoのスタックフレームを必要としないことをコンパイラに伝えます。
*   `aesctr`構造体は、CTRモードのストリームの状態を保持します。特に、`buffer`と`storage`は、暗号化されたカウンタ値をキャッシュするためのものです。
*   `NewCTR`メソッドは、`aesCipherAsm`のメソッドとして定義され、`ctrAble`インターフェースの要件を満たします。IVからカウンタを初期化し、`aesctr`インスタンスを返します。
*   `refill`メソッドは、`streamBufferSize`分のカウンタ値を生成し、それを`cryptBlocks`（s390xのアセンブリで実装されたAESブロック暗号化関数）で一括暗号化して`buffer`に格納します。カウンタはビッグエンディアンでインクリメントされます。
*   `XORKeyStream`メソッドは、入力データ`src`と`buffer`内の暗号化されたカウンタ値を`xorBytes`アセンブリ関数でXORし、結果を`dst`に書き込みます。`buffer`が尽きると`refill`を呼び出して補充します。

### `src/crypto/aes/modes.go` - `ctrAble`インターフェースの定義

```go
type ctrAble interface {

}
```
このインターフェースは、`crypto/aes`パッケージ内で定義され、`cipher.Block`を実装する型が、CTRモードのストリーム暗号を生成する際に、独自の最適化された実装を提供できることを示します。`NewCTR`メソッドは、初期ベクトル（IV）を受け取り、`cipher.Stream`インターフェースを返すことを期待されます。

### `src/crypto/cipher/ctr.go` - `NewCTR`関数の変更

```go
func NewCTR(block Block, iv []byte) Stream {
	if ctr, ok := block.(ctrAble); ok {
		return ctr.NewCTR(iv)
	}
	if len(iv) != block.BlockSize() {
		panic("cipher.NewCTR: IV length must equal block size")
	}
	// ... 既存の汎用CTR実装 ...
}
```
汎用的な`cipher.NewCTR`関数が変更され、最初に引数`block`が`ctrAble`インターフェースを実装しているかどうかを型アサーションでチェックします。もし`ctrAble`を実装していれば、その`block`の`NewCTR`メソッド（つまり、最適化された実装）を呼び出して返します。これにより、s390xのような特定のアーキテクチャ向けに最適化された実装が存在する場合、そちらが優先的に利用されるようになります。`ctrAble`を実装していない場合は、既存の汎用的なCTR実装がフォールバックとして使用されます。

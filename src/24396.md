# [インデックス 24396] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるミューテータアシストの有効化タイミングを早めることで、ヒープサイズの制御を改善することを目的としています。具体的には、GCの「スキャンフェーズ」中にミューテータアシストを有効にすることで、高速にメモリを割り当てるミューテータがヒープ目標を過度に超えるのを防ぎます。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。GCサイクル中、ミューテータ（アプリケーションの実行スレッド）はメモリの割り当てを継続します。このコミット以前は、GCコーディネータがGCアシストを有効にするのは、コンカレントスキャンフェーズが完了し、バックグラウンドマークワーカーが有効になるのと同時でした。

このタイミングの問題点は、高速にメモリを割り当てるミューテータが存在する場合に顕著になります。コンカレントスキャンフェーズの間、ミューテータはGCアシストによる「バックプレッシャー」なしに自由にメモリを割り当て続けることができました。これにより、ヒープサイズがGC開始のトリガー（heap trigger）を超え、さらにはGCが目標とするヒープサイズ（heap goal）を大幅に超過してしまう可能性がありました。結果として、ヒープサイズを目標値以下に保つためのフィードバックシステムが適切に機能しないという問題が発生していました。

この挙動は、特に`TestTraceStress`のような非常に高速にメモリを割り当てるテストケースで、ヒープサイズが目標値を一時的に大きく上回る原因となっていました。

## 前提知識の解説

このコミットの理解には、GoのコンカレントGCの仕組み、特に以下の概念が不可欠です。

### Goのガベージコレクション (GC)

GoのGCは、主に「コンカレントマーク＆スイープ」アルゴリズムに基づいています。これは、アプリケーションの実行（ミューテータの動作）と並行してGCの大部分の作業を進めることで、アプリケーションの一時停止時間（Stop-The-World, STW）を最小限に抑える設計です。

GCサイクルはいくつかのフェーズに分かれます。
1.  **Marking (マークフェーズ)**: ライブオブジェクト（到達可能なオブジェクト）を識別し、マークします。このフェーズは大部分がコンカレントに実行されます。
2.  **Mark Termination (マーク終了フェーズ)**: 短いSTWを伴い、マークフェーズの最終処理を行います。
3.  **Sweeping (スイープフェーズ)**: マークされなかったオブジェクト（デッドオブジェクト）が占めていたメモリを解放し、再利用可能にします。これもコンカレントに実行されます。

### Write Barrier (ライトバリア)

コンカレントGCにおいて、ミューテータがオブジェクトのポインタを変更する際に、GCがオブジェクトグラフの変更を正しく追跡できるようにするためのメカニズムです。GoのGCでは、マークフェーズ中にライトバリアが有効になります。これにより、ミューテータがポインタを更新しても、GCがライブオブジェクトを見落とすことがなくなります。具体的には、"white to black"（白いオブジェクトから黒いオブジェクトへのポインタ変更）の不変条件を維持します。

### GC Assists (GCアシスト)

GCアシストは、ミューテータがメモリを割り当てる際に、GCの作業を「手伝う」仕組みです。ミューテータが新しいオブジェクトを割り当てようとしたとき、もしGCが遅れていてヒープサイズが急増している場合、ミューテータは自身の割り当ての一部をGC作業に費やします。これにより、GCの進行を加速させ、ヒープサイズが目標値を超過するのを防ぐ「バックプレッシャー」として機能します。GCアシストは、特にメモリ割り当てが非常に速いアプリケーションにおいて、GCの効率とヒープサイズの安定性を保つ上で重要です。

### Heap Trigger (ヒープトリガー) と Heap Goal (ヒープ目標)

*   **Heap Trigger**: 次のGCサイクルを開始するトリガーとなるヒープサイズです。現在のヒープサイズがこの値を超えると、GCが開始されます。
*   **Heap Goal**: GCが完了した後に目指すヒープサイズです。GoのGCは、この目標値にヒープサイズを収めるように動作します。

### GC Coordinator (GCコーディネータ) と Background Mark Workers (バックグラウンドマークワーカー)

*   **GC Coordinator**: GCの各フェーズの開始と終了を調整し、全体的なGCの進行を管理する役割を担います。
*   **Background Mark Workers**: GCのマークフェーズにおいて、ライブオブジェクトをマークする作業をバックグラウンドで実行するゴルーチンです。これにより、マーク作業の大部分がアプリケーションの実行と並行して行われます。

## 技術的詳細

このコミットの核心は、GCアシストの有効化タイミングを、GCの「コンカレントスキャンフェーズ」の開始直後に移動することです。

以前のGo GCでは、GCアシストとバックグラウンドマークワーカーは、コンカレントスキャンフェーズが完了した後に同時に有効化されていました。この遅延により、スキャンフェーズ中にミューテータが大量のメモリを割り当てた場合、GCアシストによる抑制が効かず、ヒープサイズが制御不能になるリスクがありました。

この変更では、`gcBlackenEnabled`というアトミック変数（`atomicstore(&gcBlackenEnabled, 1)`）のセットを、`gcBgMarkPrepare()`の呼び出し後、かつ`startTheWorldWithSema()`（ミューテータの実行再開）の直前に移動しています。

このタイミングでのGCアシストの有効化は安全です。なぜなら、この時点では既にライトバリアが有効になっており、すべてのP（プロセッサ、Goスケジューラの論理CPU）によってグローバルに認識されているためです。ライトバリアが有効であれば、「白から黒へのポインタ変更」という不変条件が維持されるため、GCアシストがマーク作業を補助しても、GCの正確性が損なわれることはありません。

これにより、ミューテータがコンカレントスキャンフェーズ中にメモリを割り当てようとすると、すぐにGCアシストが発動し、GC作業を補助するようになります。結果として、高速にメモリを割り当てるミューテータに対しても早期にバックプレッシャーがかかり、ヒープサイズがGC目標を過度に超えるのを防ぐことができます。

コミットメッセージでは、`TestTraceStress`のような非常に高速なアロケータであっても、ヒープトリガーに達してからGCコーディネータがSTWを開始するまでのごく短い期間に、わずかながらヒープ目標を超える可能性があることに言及しています（最大で約20MB）。しかし、これは稀なケースであり、全体的なヒープ制御の改善が優先されると判断されています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、`src/runtime/mgc.go`と`src/runtime/mgcmark.go`の2つのファイルに集中しています。

### `src/runtime/mgc.go`

*   **変更前**:
    ```go
    		// Concurrent mark.
    		gcBgMarkPrepare() // Must happen before assist enable.
    		// At this point all Ps have enabled the mark phase
    		// write barrier, thus maintaining the no white to
    		// black invariant. Mutator assists and mark workers
    		// can now be enabled to safely blacken grey objects.
    		atomicstore(&gcBlackenEnabled, 1)
    		if debug.gctrace > 0 {
    			tMark = nanotime()
    		}

    		// Wait for background mark completion.
    		work.bgMark1.clear()
    		work.bgMark1.wait()
    ```
    GCアシストの有効化 (`atomicstore(&gcBlackenEnabled, 1)`) は、`gcBgMarkPrepare()`の呼び出し後、つまりコンカレントスキャンフェーズが完了し、コンカレントマークフェーズが始まる直前に行われていました。

*   **変更後**:
    ```go
    			setGCPhase(_GCscan)

    			gcBgMarkPrepare() // Must happen before assist enable.

    			// At this point all Ps have enabled the write
    			// barrier, thus maintaining the no white to
    			// black invariant. Enable mutator assists to
    			// put back-pressure on fast allocating
    			// mutators.
    			atomicstore(&gcBlackenEnabled, 1)

    			// Concurrent scan.
    			startTheWorldWithSema()
    			now = nanotime()
    ```
    `gcBgMarkPrepare()`の呼び出しと`atomicstore(&gcBlackenEnabled, 1)`によるGCアシストの有効化が、`setGCPhase(_GCscan)`（スキャンフェーズの開始）の直後、かつ`startTheWorldWithSema()`（ミューテータの実行再開）の直前に移動されました。これにより、ミューテータがスキャンフェーズ中にメモリを割り当て始める前にGCアシストが有効になります。

    さらに、以前の`atomicstore(&gcBlackenEnabled, 1)`があった場所は削除され、バックグラウンドマークワーカーの開始時間設定 (`gcController.bgMarkStartTime = nanotime()`) が追加されています。

### `src/runtime/mgcmark.go`

*   このファイルでは、`gcscan_m()`関数内の`work.nwait = 0`、`work.ndone = 0`、`work.nproc = 1`の初期化が削除されています。これは、GCアシストの有効化タイミングとは直接関係なく、おそらくGCの内部的な状態管理の整理によるものです。

## コアとなるコードの解説

変更の核心は、`src/runtime/mgc.go`における`gcBgMarkPrepare()`と`atomicstore(&gcBlackenEnabled, 1)`の移動です。

1.  **`setGCPhase(_GCscan)`**: これはGCがスキャンフェーズに入ったことを示す状態遷移です。
2.  **`gcBgMarkPrepare()`**: この関数は、バックグラウンドマークワーカーの準備を行うものです。GCアシストを有効にする前に実行される必要があります。
3.  **`atomicstore(&gcBlackenEnabled, 1)`**: この行がGCアシストを有効にする重要な部分です。`gcBlackenEnabled`は、ミューテータがGCアシストを行うべきかどうかを制御するフラグです。このフラグが`1`に設定されると、ミューテータはメモリ割り当て時にGC作業を補助するようになります。
    このコミットにより、この行が`setGCPhase(_GCscan)`の直後に移動されたことで、スキャンフェーズの開始と同時にGCアシストが有効になります。
4.  **`startTheWorldWithSema()`**: これは、GCが一時停止していたミューテータの実行を再開させる関数です。GCアシストがこの関数の前に有効化されることで、ミューテータがメモリ割り当てを再開した瞬間からGCアシストが機能するようになります。

この変更により、GCサイクルがスキャンフェーズに入り、ミューテータが再び実行され始めると、すぐにGCアシストが作動し、高速なメモリ割り当てに対するバックプレッシャーが提供されます。これにより、ヒープサイズがGC目標を過度に超えるリスクが大幅に軽減され、GCのフィードバックシステムがより効果的に機能するようになります。

`src/runtime/mgcmark.go`の変更は、主に`gcscan_m()`関数内の`work`構造体のフィールド初期化の削除です。これは、GCアシストの有効化とは直接的な機能変更ではなく、GCの内部的な状態管理の最適化またはリファクタリングの一部と考えられます。

## 技術的詳細

このコミットの核心は、GCアシストの有効化タイミングを、GCの「コンカレントスキャンフェーズ」の開始直後に移動することです。

以前のGo GCでは、GCアシストとバックグラウンドマークワーカーは、コンカレントスキャンフェーズが完了した後に同時に有効化されていました。この遅延により、スキャンフェーズ中にミューテータが大量のメモリを割り当てた場合、GCアシストによる抑制が効かず、ヒープサイズが制御不能になるリスクがありました。

この変更では、`gcBlackenEnabled`というアトミック変数（`atomicstore(&gcBlackenEnabled, 1)`）のセットを、`gcBgMarkPrepare()`の呼び出し後、かつ`startTheWorldWithSema()`（ミューテータの実行再開）の直前に移動しています。

このタイミングでのGCアシストの有効化は安全です。なぜなら、この時点では既にライトバリアが有効になっており、すべてのP（プロセッサ、Goスケジューラの論理CPU）によってグローバルに認識されているためです。ライトバリアが有効であれば、「白から黒へのポインタ変更」という不変条件が維持されるため、GCアシストがマーク作業を補助しても、GCの正確性が損なわれることはありません。

これにより、ミューテータがコンカレントスキャンフェーズ中にメモリを割り当てようとすると、すぐにGCアシストが発動し、GC作業を補助するようになります。結果として、高速にメモリを割り当てるミューテータに対しても早期にバックプレッシャーがかかり、ヒープサイズがGC目標を過度に超えるのを防ぐことができます。

コミットメッセージでは、`TestTraceStress`のような非常に高速なアロケータであっても、ヒープトリガーに達してからGCコーディネータがSTWを開始するまでのごく短い期間に、わずかながらヒープ目標を超える可能性があることに言及しています（最大で約20MB）。しかし、これは稀なケースであり、全体的なヒープ制御の改善が優先されると判断されています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、`src/runtime/mgc.go`と`src/runtime/mgcmark.go`の2つのファイルに集中しています。

### `src/runtime/mgc.go`

*   **変更前**:
    ```go
    		// Concurrent mark.
    		gcBgMarkPrepare() // Must happen before assist enable.
    		// At this point all Ps have enabled the mark phase
    		// write barrier, thus maintaining the no white to
    		// black invariant. Mutator assists and mark workers
    		// can now be enabled to safely blacken grey objects.
    		atomicstore(&gcBlackenEnabled, 1)
    		if debug.gctrace > 0 {
    			tMark = nanotime()
    		}

    		// Wait for background mark completion.
    		work.bgMark1.clear()
    		work.bgMark1.wait()
    ```
    GCアシストの有効化 (`atomicstore(&gcBlackenEnabled, 1)`) は、`gcBgMarkPrepare()`の呼び出し後、つまりコンカレントスキャンフェーズが完了し、コンカレントマークフェーズが始まる直前に行われていました。

*   **変更後**:
    ```go
    			setGCPhase(_GCscan)

    			gcBgMarkPrepare() // Must happen before assist enable.

    			// At this point all Ps have enabled the write
    			// barrier, thus maintaining the no white to
    			// black invariant. Enable mutator assists to
    			// put back-pressure on fast allocating
    			// mutators.
    			atomicstore(&gcBlackenEnabled, 1)

    			// Concurrent scan.
    			startTheWorldWithSema()
    			now = nanotime()
    ```
    `gcBgMarkPrepare()`の呼び出しと`atomicstore(&gcBlackenEnabled, 1)`によるGCアシストの有効化が、`setGCPhase(_GCscan)`（スキャンフェーズの開始）の直後、かつ`startTheWorldWithSema()`（ミューテータの実行再開）の直前に移動されました。これにより、ミューテータがスキャンフェーズ中にメモリを割り当て始める前にGCアシストが有効になります。

    さらに、以前の`atomicstore(&gcBlackenEnabled, 1)`があった場所は削除され、バックグラウンドマークワーカーの開始時間設定 (`gcController.bgMarkStartTime = nanotime()`) が追加されています。

### `src/runtime/mgcmark.go`

*   このファイルでは、`gcscan_m()`関数内の`work.nwait = 0`、`work.ndone = 0`、`work.nproc = 1`の初期化が削除されています。これは、GCアシストの有効化タイミングとは直接関係なく、おそらくGCの内部的な状態管理の整理によるものです。

## コアとなるコードの解説

変更の核心は、`src/runtime/mgc.go`における`gcBgMarkPrepare()`と`atomicstore(&gcBlackenEnabled, 1)`の移動です。

1.  **`setGCPhase(_GCscan)`**: これはGCがスキャンフェーズに入ったことを示す状態遷移です。
2.  **`gcBgMarkPrepare()`**: この関数は、バックグラウンドマークワーカーの準備を行うものです。GCアシストを有効にする前に実行される必要があります。
3.  **`atomicstore(&gcBlackenEnabled, 1)`**: この行がGCアシストを有効にする重要な部分です。`gcBlackenEnabled`は、ミューテータがGCアシストを行うべきかどうかを制御するフラグです。このフラグが`1`に設定されると、ミューテータはメモリ割り当て時にGC作業を補助するようになります。
    このコミットにより、この行が`setGCPhase(_GCscan)`の直後に移動されたことで、スキャンフェーズの開始と同時にGCアシストが有効になります。
4.  **`startTheWorldWithSema()`**: これは、GCが一時停止していたミューテータの実行を再開させる関数です。GCアシストがこの関数の前に有効化されることで、ミューテータがメモリ割り当てを再開した瞬間からGCアシストが機能するようになります。

この変更により、GCサイクルがスキャンフェーズに入り、ミューテータが再び実行され始めると、すぐにGCアシストが作動し、高速なメモリ割り当てに対するバックプレッシャーが提供されます。これにより、ヒープサイズがGC目標を過度に超えるリスクが大幅に軽減され、GCのフィードバックシステムがより効果的に機能するようになります。

`src/runtime/mgcmark.go`の変更は、主に`gcscan_m()`関数内の`work`構造体のフィールド初期化の削除です。これは、GCアシストの有効化とは直接的な機能変更ではなく、GCの内部的な状態管理の最適化またはリファクタリングの一部と考えられます。

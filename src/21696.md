# [インデックス 21696] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズム、特にヒープ管理とGCアシストの挙動に関する変更を導入しています。`src/runtime/mgc.go` はGoランタイムのガベージコレクタの主要なロジックが実装されているファイルであり、メモリの割り当て、解放、マーク、スイープといったGCの核心部分を担っています。

## 変更の背景

このコミットには大きく分けて二つの変更が含まれており、それぞれ異なる背景を持っています。

1.  **最小ヒープサイズの設定 (4MB)**:
    Goのガベージコレクタは、ヒープの使用量に基づいて次回のGC実行タイミングを決定します。`memstats.next_gc` という値がその閾値となります。これまでの実装では、ヒープサイズが非常に小さい場合、例えばライブオブジェクトがほとんどないアプリケーションでは、GCが頻繁に実行される可能性がありました。`gcpercent`（デフォルト100%）の設定により、ライブヒープサイズの100%が割り当てられるたびにGCがトリガーされます。もしライブヒープが数KBしかない場合、GCは非常に短い間隔で繰り返し実行され、GC自体のオーバーヘッドがアプリケーションの実行時間に大きな影響を与える可能性がありました。これは、GCの準備や実行にかかる固定コストが、回収されるメモリ量に対して相対的に高くなるためです。
    この問題を緩和するため、ヒープサイズが非常に小さい場合でも、GCが頻繁に発生しすぎないように、最小ヒープサイズを4MBに設定することで、GCの実行頻度を適切に制御し、全体的なパフォーマンスを向上させることを目的としています。これにより、特に起動時やアイドル状態のアプリケーションにおいて、GCのオーバーヘッドが削減されます。

2.  **ミューテーターによるGCアシストの挙動変更**:
    GoのGCは並行（concurrent）に動作しますが、GCの特定のフェーズでは、アプリケーションの通常の処理（ミューテーター）がGCを「アシスト」することがあります。これは、GCが追いつかない場合に、ミューテーターがポインタのマーク作業などを手伝うことで、GCの進行を加速させるメカニズムです。
    以前の実装では、ミューテーターがGCアシストを行う際に、特定のワークバッファ（`workbuf`）を処理し終えると、たとえ要求されたポインタ数を処理しきっていなくても、アシストを終了してしまう可能性がありました。この挙動では、GCが必要とする作業が効率的に完了しない場合があり、GCの完了が遅れたり、GC停止時間（STW）が長くなる原因となる可能性がありました。
    この変更は、ミューテーターがGCアシストを行う際に、要求された数のポインタを処理し終えるまで、必要に応じて追加のワークバッファを要求し、作業を継続するように修正することで、GCアシストの効率と確実性を向上させることを目的としています。これにより、GCの進行がよりスムーズになり、全体的なGCのパフォーマンスが改善されます。

## 前提知識の解説

このコミットの変更内容を理解するためには、Goのガベージコレクション（GC）とメモリ管理に関する以下の基本的な概念を理解しておく必要があります。

*   **Goのガベージコレクション (GC)**:
    GoのGCは、主に「三色マーキング（Tri-color marking）」アルゴリズムに基づいています。これは、オブジェクトを白（未訪問）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類し、到達可能なオブジェクトをマークするプロセスです。GoのGCは並行（concurrent）GCであり、ほとんどのGC作業はアプリケーションの実行と並行して行われます。これにより、アプリケーションの停止時間（Stop-The-World: STW）を最小限に抑えています。しかし、GCの特定のフェーズ（例えば、マークフェーズの開始や終了）では、短いSTWが発生します。

*   **ヒープとメモリ管理**:
    Goプログラムが動的に確保するメモリは「ヒープ」と呼ばれる領域に配置されます。Goランタイムは、このヒープを効率的に管理し、オブジェクトの割り当てと解放を行います。GCは、ヒープ上の不要になったオブジェクト（どこからも参照されていないオブジェクト）を特定し、そのメモリを再利用可能にします。

*   **`memstats.next_gc`**:
    `runtime.MemStats` 構造体の一部であり、次回のGCがトリガーされるヒープサイズ（バイト単位）の閾値を示します。Goランタイムは、現在のヒープ使用量がこの `next_gc` の値を超えると、GCサイクルを開始します。

*   **`gcpercent`**:
    環境変数 `GOGC` または `runtime/debug.SetGCPercent` で設定される値で、GCの実行頻度を制御します。デフォルト値は100です。これは、「前回のGC完了時のライブヒープサイズに対して、追加でどれだけのメモリが割り当てられたら次回のGCを開始するか」をパーセンテージで示します。例えば、`gcpercent=100` で前回のライブヒープが10MBだった場合、さらに10MBが割り当てられてヒープが合計20MBになった時点で次回のGCがトリガーされます。

*   **ミューテーター (Mutator) とGCアシスト**:
    「ミューテーター」とは、Goプログラムの通常の実行スレッド、つまりヒープ上のオブジェクトグラフを変更（mutate）するスレッドを指します。Goの並行GCでは、ミューテーターはGCと並行して動作しますが、GCがメモリの割り当て速度に追いつかない場合など、特定の状況下ではGCを「アシスト」するよう求められます。GCアシストは、ミューテーターが自身の割り当て処理の一部として、GCのマーク作業などを手伝うことで、GCの進行を助けるメカニズムです。これにより、GCが完了するまでの時間を短縮し、STWの発生を避けるか、その長さを短縮します。

*   **ワークバッファ (Workbuf)**:
    GoのGCでは、マークフェーズ中に到達可能なオブジェクトを探索し、ポインタをキューに入れるために「ワークバッファ」と呼ばれる一時的なバッファを使用します。GCワーカーやGCアシストを行うミューテーターは、これらのワークバッファからポインタを取り出して処理し、新しいポインタをワークバッファに追加します。`drainobjects` 関数は、これらのワークバッファからオブジェクトを処理する役割を担います。

*   **アトミック操作 (`xadd64`, `atomicstore64`)**:
    Goランタイムの内部では、複数のゴルーチンやスレッドが共有データにアクセスするため、競合状態を避けるためにアトミック操作が頻繁に用いられます。
    *   `xadd64`: 64ビット整数に対してアトミックな加算操作を行います。これは、指定された値に別の値を加算し、その結果をメモリに書き込む一連の操作を不可分に行うことを保証します。
    *   `atomicstore64`: 64ビット整数に対してアトミックな書き込み操作を行います。これは、指定された値をメモリ位置に書き込む操作を不可分に行うことを保証します。これらの操作は、GC統計のような共有カウンタを更新する際に、データの整合性を保つために重要です。

## 技術的詳細

このコミットは、`src/runtime/mgc.go` 内の複数の箇所に影響を与えています。

1.  **`heapminimum` 変数の導入**:
    新たに `heapminimum` というグローバル変数が導入されました。この変数は `uint64(4 << 20)`、つまり4MBに初期化されます。これは、Goランタイムが管理するヒープの最小サイズを定義します。

    ```go
    // heapminimum is the minimum number of bytes in the heap.
    // This cleans up the corner case of where we have a very small live set but a lot
    // of allocations and collecting every GOGC * live set is expensive.
    var heapminimum = uint64(4 << 20)
    ```

2.  **`memstats.next_gc` の初期化と更新ロジックの変更**:
    *   `gcinit()` 関数内で、`memstats.next_gc` の初期値が `4 << 20` (4MB) から `heapminimum` に変更されました。これにより、プログラム起動時の最初のGC閾値が最小ヒープサイズに設定されます。
    *   `mSpan_Sweep` 関数（メモリのスイープ処理を行う関数）内で、`memstats.next_gc` を減算するロジックが変更されました。以前は単純に `xadd64(&memstats.next_gc, -reduction)` で減算していましたが、変更後は `int64(memstats.next_gc)-reduction > int64(heapminimum)` という条件が追加されました。これは、`next_gc` の値が `heapminimum` を下回らないようにするためのガードです。もし減算の結果が `heapminimum` を下回る場合、`atomicstore64(&memstats.next_gc, heapminimum)` を使って `next_gc` を強制的に `heapminimum` に設定します。これにより、GCの閾値が最小ヒープサイズを下回ることがなくなり、非常に小さなヒープでの頻繁なGCを抑制します。このロジックは、ラージオブジェクトの解放時とスモールオブジェクトの解放時の両方に適用されています。
    *   `gc()` 関数（GCサイクルを開始する関数）の最後で、次回のGC閾値を設定する際にも `heapminimum` が考慮されるようになりました。`memstats.next_gc` が計算された後、もしその値が `heapminimum` より小さい場合、`memstats.next_gc` は `heapminimum` に設定されます。これにより、GCが完了した後の次回のGC閾値も最小ヒープサイズを下回らないことが保証されます。

3.  **`drainobjects` 関数の変更**:
    `drainobjects` 関数は、GCアシストを行うミューテーターがワークバッファからオブジェクトを処理する際に使用されます。以前は、`wbuf.nobj == 0`（現在のワークバッファが空になった）場合、`putempty(wbuf)` で空のバッファを戻し、すぐに `return` していました。
    この変更により、`return` する代わりに、`wbuf = trygetfull()` を呼び出して、まだ処理すべきポインタが含まれている可能性のある別のワークバッファを取得しようとします。もし `trygetfull()` が `nil` を返した場合（利用可能なワークバッファがない場合）にのみ `return` します。これにより、ミューテーターは要求された `count` のオブジェクトを処理し終えるまで、可能な限り作業を継続するようになります。これは、GCアシストの効率を向上させ、GCの進行をより確実にするための重要な変更です。

これらの変更は、GoランタイムのGCが、特にヒープサイズが小さい状況や、GCアシストが必要な状況において、より効率的かつ予測可能な挙動を示すように設計されています。

## コアとなるコードの解説

1.  **`drainobjects` 関数の変更**:
    *   **変更前**:
        ```go
        if wbuf.nobj == 0 {
            putempty(wbuf)
            return
        }
        ```
        `drainobjects` は `count` 個のオブジェクトを処理することを目的としていますが、現在のワークバッファ `wbuf` が空（`wbuf.nobj == 0`）になった場合、すぐに `return` していました。これは、要求された `count` 個のオブジェクトを処理しきれていない可能性があっても、そこで処理を中断することを意味します。
    *   **変更後**:
        ```go
        if wbuf.nobj == 0 {
            putempty(wbuf)
            wbuf = trygetfull()
            if wbuf == nil {
                return
            }
        }
        ```
        ワークバッファが空になった場合でも、すぐに `return` せずに `trygetfull()` を呼び出して、まだ処理すべきポインタが含まれている可能性のある別のワークバッファを取得しようとします。`trygetfull()` は、利用可能な「フル」なワークバッファ（つまり、まだポインタが残っているワークバッファ）を返します。もし `trygetfull()` が `nil` を返した場合（利用可能なワークバッファが他にない場合）にのみ、関数は `return` します。この変更により、ミューテーターは要求された `count` のオブジェクトを処理し終えるまで、可能な限り作業を継続するようになり、GCアシストの効率と確実性が向上します。

2.  **`mSpan_Sweep` 関数における `memstats.next_gc` の更新ロジックの変更**:
    *   **変更前**:
        ```go
        xadd64(&memstats.next_gc, -int64(size)*int64(gcpercent+100)/100)
        ```
        または
        ```go
        xadd64(&memstats.next_gc, -int64(nfree)*int64(size)*int64(gcpercent+100)/100)
        ```
        メモリが解放された際（スイープフェーズで回収されたメモリ）、次回のGC閾値 `memstats.next_gc` は、回収されたメモリ量に基づいて減算されていました。これは、回収されたメモリの分だけ、次回のGCが遅れても良いという考えに基づいています。
    *   **変更後**:
        ```go
        reduction := int64(size) * int64(gcpercent+100) / 100
        if int64(memstats.next_gc)-reduction > int64(heapminimum) {
            xadd64(&memstats.next_gc, -reduction)
        } else {
            atomicstore64(&memstats.next_gc, heapminimum)
        }
        ```
        `reduction` は、回収されたメモリ量に基づいて `next_gc` から減算されるべき値です。この変更では、減算後の `memstats.next_gc` の値が `heapminimum`（4MB）を下回らないようにする条件が追加されました。もし減算の結果が `heapminimum` より小さくなる場合、`memstats.next_gc` は強制的に `heapminimum` に設定されます。これにより、ヒープサイズが非常に小さい場合でも、GCが頻繁に発生しすぎるのを防ぎます。`xadd64` はアトミックな加算、`atomicstore64` はアトミックなストア操作であり、複数のゴルーチンからの同時アクセスに対する安全性を保証します。

3.  **`heapminimum` 変数の定義**:
    ```go
    // heapminimum is the minimum number of bytes in the heap.
    // This cleans up the corner case of where we have a very small live set but a lot
    // of allocations and collecting every GOGC * live set is expensive.
    var heapminimum = uint64(4 << 20)
    ```
    `heapminimum` は、ヒープの最小サイズを4MB（`4 << 20` は `4 * 2^20 = 4 * 1024 * 1024` バイト）として定義する新しいグローバル変数です。コメントにあるように、これはライブセットが非常に小さいにもかかわらず多くの割り当てが行われるようなコーナーケースにおいて、`GOGC * live set` ごとにGCを実行するのがコスト高になる問題を解決するためのものです。

4.  **`gcinit()` 関数における `memstats.next_gc` の初期化**:
    *   **変更前**:
        ```go
        memstats.next_gc = 4 << 20 // 4 megs to start with
        ```
        `memstats.next_gc` は起動時に4MBにハードコードされていました。
    *   **変更後**:
        ```go
        memstats.next_gc = heapminimum
        ```
        `heapminimum` 変数を使用するように変更され、コードの意図がより明確になりました。

5.  **`gc()` 関数における `memstats.next_gc` の更新**:
    *   **変更前**:
        ```go
        memstats.next_gc = memstats.heap_alloc + memstats.heap_alloc*uint64(gcpercent)/100
        ```
        GCが完了した後、次回のGC閾値は現在のヒープ割り当て量と `gcpercent` に基づいて計算されていました。
    *   **変更後**:
        ```go
        memstats.next_gc = memstats.heap_alloc + memstats.heap_alloc*uint64(gcpercent)/100
        if memstats.next_gc < heapminimum {
            memstats.next_gc = heapminimum
        }
        ```
        計算された `memstats.next_gc` が `heapminimum` より小さい場合、`memstats.next_gc` は `heapminimum` に設定されます。これにより、GCが完了した後の次回のGC閾値も、常に最小ヒープサイズ以上であることが保証され、GCの頻繁な実行が抑制されます。

これらの変更は、GoランタイムのGCの堅牢性とパフォーマンスを向上させるための重要なステップであり、特にリソースが限られた環境や、ヒープ使用量が変動するアプリケーションにおいて、より安定した動作を期待できます。

## 変更の背景

このコミットには大きく分けて二つの変更が含まれており、それぞれ異なる背景を持っています。

1.  **最小ヒープサイズの設定 (4MB)**:
    Goのガベージコレクタは、ヒープの使用量に基づいて次回のGC実行タイミングを決定します。`memstats.next_gc` という値がその閾値となります。これまでの実装では、ヒープサイズが非常に小さい場合、例えばライブオブジェクトがほとんどないアプリケーションでは、GCが頻繁に実行される可能性がありました。`gcpercent`（デフォルト100%）の設定により、ライブヒープサイズの100%が割り当てられるたびにGCがトリガーされます。もしライブヒープが数KBしかない場合、GCは非常に短い間隔で繰り返し実行され、GC自体のオーバーヘッドがアプリケーションの実行時間に大きな影響を与える可能性がありました。これは、GCの準備や実行にかかる固定コストが、回収されるメモリ量に対して相対的に高くなるためです。
    この問題を緩和するため、ヒープサイズが非常に小さい場合でも、GCが頻繁に発生しすぎないように、最小ヒープサイズを4MBに設定することで、GCの実行頻度を適切に制御し、全体的なパフォーマンスを向上させることを目的としています。これにより、特に起動時やアイドル状態のアプリケーションにおいて、GCのオーバーヘッドが削減されます。

2.  **ミューテーターによるGCアシストの挙動変更**:
    GoのGCは並行（concurrent）に動作しますが、GCの特定のフェーズでは、アプリケーションの通常の処理（ミューテーター）がGCを「アシスト」することがあります。これは、GCが追いつかない場合に、ミューテーターがポインタのマーク作業などを手伝うことで、GCの進行を加速させるメカニズムです。
    以前の実装では、ミューテーターがGCアシストを行う際に、特定のワークバッファ（`workbuf`）を処理し終えると、たとえ要求されたポインタ数を処理しきっていなくても、アシストを終了してしまう可能性がありました。この挙動では、GCが必要とする作業が効率的に完了しない場合があり、GCの完了が遅れたり、GC停止時間（STW）が長くなる原因となる可能性がありました。
    この変更は、ミューテーターがGCアシストを行う際に、要求された数のポインタを処理し終えるまで、必要に応じて追加のワークバッファを要求し、作業を継続するように修正することで、GCアシストの効率と確実性を向上させることを目的としています。これにより、GCの進行がよりスムーズになり、全体的なGCのパフォーマンスが改善されます。

## 前提知識の解説

このコミットの変更内容を理解するためには、Goのガベージコレクション（GC）とメモリ管理に関する以下の基本的な概念を理解しておく必要があります。

*   **Goのガベージコレクション (GC)**:
    GoのGCは、主に「三色マーキング（Tri-color marking）」アルゴリズムに基づいています。これは、オブジェクトを白（未訪問）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類し、到達可能なオブジェクトをマークするプロセスです。GoのGCは並行（concurrent）GCであり、ほとんどのGC作業はアプリケーションの実行と並行して行われます。これにより、アプリケーションの停止時間（Stop-the-World: STW）を最小限に抑えています。しかし、GCの特定のフェーズ（例えば、マークフェーズの開始や終了）では、短いSTWが発生します。

*   **ヒープとメモリ管理**:
    Goプログラムが動的に確保するメモリは「ヒープ」と呼ばれる領域に配置されます。Goランタイムは、このヒープを効率的に管理し、オブジェクトの割り当てと解放を行います。GCは、ヒープ上の不要になったオブジェクト（どこからも参照されていないオブジェクト）を特定し、そのメモリを再利用可能にします。

*   **`memstats.next_gc`**:
    `runtime.MemStats` 構造体の一部であり、次回のGCがトリガーされるヒープサイズ（バイト単位）の閾値を示します。Goランタイムは、現在のヒープ使用量がこの `next_gc` の値を超えると、GCサイクルを開始します。

*   **`gcpercent`**:
    環境変数 `GOGC` または `runtime/debug.SetGCPercent` で設定される値で、GCの実行頻度を制御します。デフォルト値は100です。これは、「前回のGC完了時のライブヒープサイズに対して、追加でどれだけのメモリが割り当てられたら次回のGCを開始するか」をパーセンテージで示します。例えば、`gcpercent=100` で前回のライブヒープが10MBだった場合、さらに10MBが割り当てられてヒープが合計20MBになった時点で次回のGCがトリガーされます。

*   **ミューテーター (Mutator) とGCアシスト**:
    「ミューテーター」とは、Goプログラムの通常の実行スレッド、つまりヒープ上のオブジェクトグラフを変更（mutate）するスレッドを指します。Goの並行GCでは、ミューテーターはGCと並行して動作しますが、GCがメモリの割り当て速度に追いつかない場合など、特定の状況下ではGCを「アシスト」するよう求められます。GCアシストは、ミューテーターが自身の割り当て処理の一部として、GCのマーク作業などを手伝うことで、GCの進行を助けるメカニズムです。これにより、GCが完了するまでの時間を短縮し、STWの発生を避けるか、その長さを短縮します。

*   **ワークバッファ (Workbuf)**:
    GoのGCでは、マークフェーズ中に到達可能なオブジェクトを探索し、ポインタをキューに入れるために「ワークバッファ」と呼ばれる一時的なバッファを使用します。GCワーカーやGCアシストを行うミューテーターは、これらのワークバッファからポインタを取り出して処理し、新しいポインタをワークバッファに追加します。`drainobjects` 関数は、これらのワークバッファからオブジェクトを処理する役割を担います。

*   **アトミック操作 (`xadd64`, `atomicstore64`)**:
    Goランタイムの内部では、複数のゴルーチンやスレッドが共有データにアクセスするため、競合状態を避けるためにアトミック操作が頻繁に用いられます。
    *   `xadd64`: 64ビット整数に対してアトミックな加算操作を行います。これは、指定された値に別の値を加算し、その結果をメモリに書き込む一連の操作を不可分に行うことを保証します。
    *   `atomicstore64`: 64ビット整数に対してアトミックな書き込み操作を行います。これは、指定された値をメモリ位置に書き込む操作を不可分に行うことを保証します。これらの操作は、GC統計のような共有カウンタを更新する際に、データの整合性を保つために重要です。

## 技術的詳細

このコミットは、`src/runtime/mgc.go` 内の複数の箇所に影響を与えています。

1.  **`heapminimum` 変数の導入**:
    新たに `heapminimum` というグローバル変数が導入されました。この変数は `uint64(4 << 20)`、つまり4MBに初期化されます。これは、Goランタイムが管理するヒープの最小サイズを定義します。

    ```go
    // heapminimum is the minimum number of bytes in the heap.
    // This cleans up the corner case of where we have a very small live set but a lot
    // of allocations and collecting every GOGC * live set is expensive.
    var heapminimum = uint64(4 << 20)
    ```

2.  **`memstats.next_gc` の初期化と更新ロジックの変更**:
    *   `gcinit()` 関数内で、`memstats.next_gc` の初期値が `4 << 20` (4MB) から `heapminimum` に変更されました。これにより、プログラム起動時の最初のGC閾値が最小ヒープサイズに設定されます。
    *   `mSpan_Sweep` 関数（メモリのスイープ処理を行う関数）内で、`memstats.next_gc` を減算するロジックが変更されました。以前は単純に `xadd64(&memstats.next_gc, -reduction)` で減算していましたが、変更後は `int64(memstats.next_gc)-reduction > int64(heapminimum)` という条件が追加されました。これは、`next_gc` の値が `heapminimum` を下回らないようにするためのガードです。もし減算の結果が `heapminimum` を下回る場合、`atomicstore64(&memstats.next_gc, heapminimum)` を使って `next_gc` を強制的に `heapminimum` に設定します。これにより、GCの閾値が最小ヒープサイズを下回ることがなくなり、非常に小さなヒープでの頻繁なGCを抑制します。このロジックは、ラージオブジェクトの解放時とスモールオブジェクトの解放時の両方に適用されています。
    *   `gc()` 関数（GCサイクルを開始する関数）の最後で、次回のGC閾値を設定する際にも `heapminimum` が考慮されるようになりました。`memstats.next_gc` が計算された後、もしその値が `heapminimum` より小さい場合、`memstats.next_gc` は `heapminimum` に設定されます。これにより、GCが完了した後の次回のGC閾値も最小ヒープサイズを下回らないことが保証されます。

3.  **`drainobjects` 関数の変更**:
    `drainobjects` 関数は、GCアシストを行うミューテーターがワークバッファからオブジェクトを処理する際に使用されます。以前は、`wbuf.nobj == 0`（現在のワークバッファが空になった）場合、`putempty(wbuf)` で空のバッファを戻し、すぐに `return` していました。
    この変更により、`return` する代わりに、`wbuf = trygetfull()` を呼び出して、まだ処理すべきポインタが含まれている可能性のある別のワークバッファを取得しようとします。もし `trygetfull()` が `nil` を返した場合（利用可能なワークバッファがない場合）にのみ `return` します。これにより、ミューテーターは要求された `count` のオブジェクトを処理し終えるまで、可能な限り作業を継続するようになります。これは、GCアシストの効率を向上させ、GCの進行をより確実にするための重要な変更です。

これらの変更は、GoランタイムのGCが、特にヒープサイズが小さい状況や、GCアシストが必要な状況において、より効率的かつ予測可能な挙動を示すように設計されています。

## コアとなるコードの解説

1.  **`drainobjects` 関数の変更**:
    *   **変更前**:
        ```go
        if wbuf.nobj == 0 {
            putempty(wbuf)
            return
        }
        ```
        `drainobjects` は `count` 個のオブジェクトを処理することを目的としていますが、現在のワークバッファ `wbuf` が空（`wbuf.nobj == 0`）になった場合、すぐに `return` していました。これは、要求された `count` 個のオブジェクトを処理しきれていない可能性があっても、そこで処理を中断することを意味します。
    *   **変更後**:
        ```go
        if wbuf.nobj == 0 {
            putempty(wbuf)
            wbuf = trygetfull()
            if wbuf == nil {
                return
            }
        }
        ```
        ワークバッファが空になった場合でも、すぐに `return` せずに `trygetfull()` を呼び出して、まだ処理すべきポインタが含まれている可能性のある別のワークバッファを取得しようとします。`trygetfull()` は、利用可能な「フル」なワークバッファ（つまり、まだポインタが残っているワークバッファ）を返します。もし `trygetfull()` が `nil` を返した場合（利用可能なワークバッファが他にない場合）にのみ、関数は `return` します。この変更により、ミューテーターは要求された `count` のオブジェクトを処理し終えるまで、可能な限り作業を継続するようになり、GCアシストの効率と確実性が向上します。

2.  **`mSpan_Sweep` 関数における `memstats.next_gc` の更新ロジックの変更**:
    *   **変更前**:
        ```go
        xadd64(&memstats.next_gc, -int64(size)*int64(gcpercent+100)/100)
        ```
        または
        ```go
        xadd64(&memstats.next_gc, -int64(nfree)*int64(size)*int64(gcpercent+100)/100)
        ```
        メモリが解放された際（スイープフェーズで回収されたメモリ）、次回のGC閾値 `memstats.next_gc` は、回収されたメモリ量に基づいて減算されていました。これは、回収されたメモリの分だけ、次回のGCが遅れても良いという考えに基づいています。
    *   **変更後**:
        ```go
        reduction := int64(size) * int64(gcpercent+100) / 100
        if int64(memstats.next_gc)-reduction > int64(heapminimum) {
            xadd64(&memstats.next_gc, -reduction)
        } else {
            atomicstore64(&memstats.next_gc, heapminimum)
        }
        ```
        `reduction` は、回収されたメモリ量に基づいて `next_gc` から減算されるべき値です。この変更では、減算後の `memstats.next_gc` の値が `heapminimum`（4MB）を下回らないようにする条件が追加されました。もし減算の結果が `heapminimum` より小さくなる場合、`memstats.next_gc` は強制的に `heapminimum` に設定されます。これにより、ヒープサイズが非常に小さい場合でも、GCが頻繁に発生しすぎるのを防ぎます。`xadd64` はアトミックな加算、`atomicstore64` はアトミックなストア操作であり、複数のゴルーチンからの同時アクセスに対する安全性を保証します。

3.  **`heapminimum` 変数の定義**:
    ```go
    // heapminimum is the minimum number of bytes in the heap.
    // This cleans up the corner case of where we have a very small live set but a lot
    // of allocations and collecting every GOGC * live set is expensive.
    var heapminimum = uint64(4 << 20)
    ```
    `heapminimum` は、ヒープの最小サイズを4MB（`4 << 20` は `4 * 2^20 = 4 * 1024 * 1024` バイト）として定義する新しいグローバル変数です。コメントにあるように、これはライブセットが非常に小さいにもかかわらず多くの割り当てが行われるようなコーナーケースにおいて、`GOGC * live set` ごとにGCを実行するのがコスト高になる問題を解決するためのものです。

4.  **`gcinit()` 関数における `memstats.next_gc` の初期化**:
    *   **変更前**:
        ```go
        memstats.next_gc = 4 << 20 // 4 megs to start with
        ```
        `memstats.next_gc` は起動時に4MBにハードコードされていました。
    *   **変更後**:
        ```go
        memstats.next_gc = heapminimum
        ```
        `heapminimum` 変数を使用するように変更され、コードの意図がより明確になりました。

5.  **`gc()` 関数における `memstats.next_gc` の更新**:
    *   **変更前**:
        ```go
        memstats.next_gc = memstats.heap_alloc + memstats.heap_alloc*uint64(gcpercent)/100
        ```
        GCが完了した後、次回のGC閾値は現在のヒープ割り当て量と `gcpercent` に基づいて計算されていました。
    *   **変更後**:
        ```go
        memstats.next_gc = memstats.heap_alloc + memstats.heap_alloc*uint64(gcpercent)/100
        if memstats.next_gc < heapminimum {
            memstats.next_gc = heapminimum
        }
        ```
        計算された `memstats.next_gc` が `heapminimum` より小さい場合、`memstats.next_gc` は `heapminimum` に設定されます。これにより、GCが完了した後の次回のGC閾値も、常に最小ヒープサイズ以上であることが保証され、GCの頻繁な実行が抑制されます。

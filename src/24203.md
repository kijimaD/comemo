## 元コミット内容

このコミットは、`math` パッケージの `Log2` 関数が `ppc64` および `s390` アーキテクチャでテストに失敗する問題を修正します。主な変更点は以下の2点です。

2.  数値比較に使用される誤差許容関数が修正され、許容誤差が「正しい（期待される）値」の関数として計算されるようになります。

この変更は、Issue #9066 を解決します。

## 変更の背景

Go言語の `math` パッケージは、様々なアーキテクチャ上で一貫した正確な数値計算を提供することを目指しています。しかし、このコミット以前は、`Log2` 関数が `ppc64` (IBM PowerPC 64ビット) および `s390` (IBM System/390、現在のIBM Z) といった特定のアーキテクチャ上でテストに失敗していました。

この問題の根本原因は、浮動小数点演算の性質と、異なるCPUアーキテクチャ間での浮動小数点演算の実装の違いに起因すると考えられます。特に、`Log2` のような超越関数は、内部的に近似計算を行うため、わずかな誤差が生じやすいです。2のべき乗のような「正確な」結果が期待される入力に対しても、浮動小数点演算の丸め誤差によって期待値からわずかにずれることがあり、これがテストの失敗につながっていました。

また、テストにおける数値比較の許容誤差の計算方法にも問題がありました。従来の `tolerance` 関数は、比較対象の「実際の値」に基づいて許容誤差を計算していましたが、これは不安定な結果を招く可能性がありました。特に、実際の値が0に近い場合、相対誤差の計算が不正確になることがあります。そのため、「正しい（期待される）値」に基づいて許容誤差を計算するように変更することで、より堅牢で信頼性の高いテスト比較を実現する必要がありました。

このコミットは、これらの問題を解決し、`Log2` 関数の正確性とテストの信頼性を向上させることを目的としています。

## 前提知識の解説

### 浮動小数点数と精度

コンピュータにおける浮動小数点数は、実数を近似的に表現するための形式です。IEEE 754標準が広く用いられていますが、有限のビット数で無限の実数を表現するため、常に丸め誤差が伴います。特に、`Log2` のような超越関数は、テイラー展開などの近似計算によって実装されることが多く、その過程でさらに誤差が生じる可能性があります。異なるCPUアーキテクチャでは、浮動小数点演算器の実装や丸めモードの扱いが微妙に異なることがあり、これが同じ入力に対して異なる結果を生む原因となることがあります。

### `Log2` 関数

`Log2(x)` は、`x` の2を底とする対数を計算する関数です。数学的には `log₂(x)` と表記されます。例えば、`Log2(8)` は `3` です。コンピュータサイエンスでは、ビット演算やデータ構造の分析などで頻繁に利用されます。

### `Frexp` 関数

`Frexp(x)` は、浮動小数点数 `x` を `frac * 2^exp` の形式に分解する関数です。ここで `frac` は `[0.5, 1.0)` の範囲の小数部（仮数部）、`exp` は整数部の指数です。
例: `Frexp(12.0)` は `(0.75, 4)` を返します。なぜなら `0.75 * 2^4 = 0.75 * 16 = 12` だからです。
`Log2(x)` の計算において、`Log2(frac * 2^exp) = Log2(frac) + Log2(2^exp) = Log2(frac) + exp` という関係を利用できます。

### 数値比較における許容誤差 (Tolerance)

浮動小数点数の比較では、厳密な等価性 (`a == b`) を用いることはほとんどありません。丸め誤差のため、数学的に等しいはずの値がコンピュータ上ではわずかに異なることがあります。そのため、`|a - b| <= epsilon` のように、ある小さな許容誤差 `epsilon` の範囲内であれば等しいとみなす「許容誤差比較」が一般的に用いられます。
許容誤差 `epsilon` の設定方法には、絶対誤差 (`|a - b| <= abs_epsilon`) と相対誤差 (`|a - b| <= rel_epsilon * max(|a|, |b|)` または `|a - b| <= rel_epsilon * |expected_value|`) があります。このコミットでは、相対誤差の計算基準を「正しい（期待される）値」に変更しています。

## 技術的詳細

このコミットは、`Log2` 関数の実装と、そのテストに使用される `tolerance` 関数の両方に変更を加えています。

### `Log2` 関数の修正

`log2` 関数（`Log2` の内部実装）は、`Frexp` を利用して `x` を `frac * 2^exp` に分解し、`Log(frac)*(1/Ln2) + float64(exp)` として計算していました。ここで `Log` は自然対数、`Ln2` は自然対数 `ln(2)` です。

問題は、`frac` が `0.5` の場合、つまり `x` が2のべき乗である場合（例: `x = 8` のとき `frac = 0.5`, `exp = 4`）、`Log(0.5)*(1/Ln2) + exp` が `exp-1` と厳密に等しくならない可能性があったことです。`Log(0.5)` は `-Ln2` なので、数学的には `(-Ln2)*(1/Ln2) + exp = -1 + exp` となるはずですが、浮動小数点演算の丸め誤差により、この計算が `exp-1` とわずかに異なる結果を生じることがありました。

このコミットでは、`frac == 0.5` の特殊ケースを明示的に処理することで、この問題を解決しています。`frac` が `0.5` の場合は、`Log2(x)` の結果を `float64(exp - 1)` と直接設定することで、2のべき乗に対する `Log2` の結果が常に正確になるようにしています。

### `tolerance` 関数の修正

`tolerance` 関数は、2つの浮動小数点数 `a` (実際の値) と `b` (期待される値) が、与えられた相対許容誤差 `e` の範囲内にあるかをチェックするために使用されます。

変更前は、許容誤差 `e` を `a` (実際の値) に基づいてスケーリングしていました (`e = e * a`)。これは、`a` が0に近い場合に問題を引き起こす可能性がありました。例えば、`a` が非常に小さい値の場合、許容誤差 `e * a` も非常に小さくなり、わずかな誤差でもテストが失敗しやすくなります。

変更後は、許容誤差 `e` を `b` (正しい/期待される値) に基づいてスケーリングするように修正されました (`e = e * b`)。これにより、許容誤差の計算がより安定し、テストの意図に沿ったものになります。期待される値が0でない限り、この方法はより信頼性の高い比較を提供します。また、`e` が負になる可能性を考慮して、絶対値を取るように修正されています (`if e < 0 { e = -e }`)。

### `tolerance` 関数の修正

`tolerance` 関数は、2つの浮動小数点数 `a` (実際の値) と `b` (期待される値) が、与えられた相対許容誤差 `e` の範囲内にあるかをチェックするために使用されます。

変更前は、許容誤差 `e` を `a` (実際の値) に基づいてスケーリングしていました (`e = e * a`)。これは、`a` が0に近い場合に問題を引き起こす可能性がありました。例えば、`a` が非常に小さい値の場合、許容誤差 `e * a` も非常に小さくなり、わずかな誤差でもテストが失敗しやすくなります。これは、相対誤差の計算において、分母が小さすぎると結果が不安定になるという浮動小数点演算の一般的な問題です。

変更後は、許容誤差 `e` を `b` (正しい/期待される値) に基づいてスケーリングするように修正されました (`e = e * b`)。これにより、許容誤差の計算がより安定し、テストの意図に沿ったものになります。期待される値が0でない限り、この方法はより信頼性の高い比較を提供します。また、`e` が負になる可能性を考慮して、絶対値を取るように修正されています (`if e < 0 { e = -e }`)。この変更により、浮動小数点テストの堅牢性が向上し、アーキテクチャ間の微妙な浮動小数点演算の差異による誤ったテスト失敗が減少します。

## コアとなるコードの解説

### `src/math/all_test.go` の `tolerance` 関数

-   **変更前**: `if a != 0 { e = e * a }`
    -   許容誤差 `e` を、テスト対象の「実際の値 `a`」に比例させていました。この方法では、`a` が非常に小さい値の場合、許容誤差も極端に小さくなり、浮動小数点数のわずかな誤差でもテストが失敗しやすくなるという問題がありました。
-   **変更後**: `if b != 0 { e = e * b }`
    -   許容誤差 `e` を、テストの「正しい（期待される）値 `b`」に比例させるように修正されました。これにより、許容誤差の基準がより安定し、テストの信頼性が向上します。コメント `// note: b is correct (expected) value, a is actual value. // make error tolerance a fraction of b, not a.` がこの意図を明確に示しています。期待される値 `b` は通常、テストの設計段階で既知であり、安定した基準点となります。
    -   `if e < 0 { e = -e }` は、`e * b` の結果が負になる可能性を考慮し、許容誤差が常に正の値であることを保証します。

### `src/math/log10.go` の `log2` 関数

-   **追加されたコード**:
    ```go
    	// Make sure exact powers of two give an exact answer.
    	// Don't depend on Log(0.5)*(1/Ln2)+exp being exactly exp-1.
    	if frac == 0.5 {
    		return float64(exp - 1)
    	}
    ```
    -   このコードは、`Frexp(x)` によって得られた小数部 `frac` が `0.5` である場合、つまり `x` が2のべき乗である場合に実行されます。
    -   `frac == 0.5` の場合、`Log2(x)` の数学的な結果は `exp - 1` となります。従来の `Log(frac)*(1/Ln2) + float64(exp)` という計算経路では、浮動小数点演算の丸め誤差により、この `exp - 1` という正確な値が得られない可能性がありました。
    -   この特殊なケースを明示的に捕捉し、直接 `float64(exp - 1)` を返すようにすることで、2のべき乗に対する `Log2` の結果が常に正確であることが保証されます。これにより、`ppc64` や `s390` などのアーキテクチャで発生していた、2のべき乗に対する `Log2` のテスト失敗が解消されます。

# [インデックス 20457] ファイルの概要

このコミットは、Go言語のランタイムにおけるマップ（`map`）のイテレーションと要素削除のパターンにおけるパフォーマンス問題を解決します。特に、大規模なマップにおいて、イテレータの開始位置をランダム化することで、従来のO(N^2)の計算量をO(N log N)に改善し、大幅な高速化を実現しています。

## 変更の背景

Goのマップはハッシュテーブルとして実装されており、要素の追加、削除、検索は平均的にO(1)の計算量で行われます。しかし、特定のパターン、特にマップをイテレートしながら要素を削除する「iter/deleteパターン」において、パフォーマンスが著しく低下する問題がありました。

この問題は、マップのイテレータが常に同じバケットから順次走査を開始するという実装に起因していました。マップから要素を削除すると、そのバケットは空になります。もしイテレータが常に同じ開始点から順にバケットを走査し、空になったバケットをスキップし続けると、マップが大きくなるにつれて、イテレータが有効な要素を見つけるまでに走査しなければならないバケットの数が増大します。

例えば、N個の要素を持つマップで、イテレートして1つ要素を削除するという操作をN回繰り返す場合を考えます。
最初のイテレーションでは、イテレータはすぐに要素を見つけられます。しかし、多くの要素が削除され、マップが疎になってくると、イテレータは多くの空のバケットをスキップしなければならなくなります。最悪の場合、イテレータが常に空のバケットを多数走査してからようやく要素を見つけるようになり、1回のイテレーションにかかる時間がO(N)に近づきます。これをN回繰り返すと、全体の計算量がO(N^2)になってしまいます。

コミットメッセージに示されているベンチマーク結果は、この問題が顕著であることを示しています。
`BenchmarkMapPop10000` (10000要素のマップ)では、変更前は1回の操作に約2.7億ナノ秒（0.27秒）かかっていましたが、変更後は約600万ナノ秒（0.006秒）と、約45倍もの高速化が実現されています。これは、O(N^2)からO(N log N)への改善が、大規模なデータセットにおいていかに重要であるかを示しています。

## 前提知識の解説

### Goのマップ（`map`）の内部構造

Goのマップは、ハッシュテーブル（ハッシュマップ）として実装されています。
*   **バケット**: マップのデータは、複数の「バケット」と呼ばれる領域に分割されて格納されます。キーのハッシュ値に基づいて、どのバケットに要素が格納されるかが決定されます。
*   **オーバーフローバケット**: 各バケットには限られた数のキー/値ペアしか格納できません。衝突が発生したり、バケットが満杯になったりすると、オーバーフローバケットがリンクされ、追加の要素が格納されます。
*   **イテレーション順序**: Goのマップのイテレーション順序は、意図的にランダム化されています。これは、開発者がマップの順序に依存するコードを書くことを防ぎ、将来のマップ実装の変更を容易にするためです。しかし、このランダム化は、イテレータが「どこから開始するか」という点には適用されていませんでした。

### 計算量（オーダー記法）

*   **O(N^2) (オー・エヌ・スクエア)**: 二次時間計算量。入力サイズNが増加すると、処理時間がNの2乗に比例して増加します。非常に効率が悪く、Nが大きくなると実用的な時間で完了しなくなります。
*   **O(N log N) (オー・エヌ・ログ・エヌ)**: 線形対数時間計算量。入力サイズNが増加すると、処理時間がN * log(N)に比例して増加します。O(N^2)よりもはるかに効率的で、多くの効率的なソートアルゴリズムなどで見られます。

### `fastrand1()`

Goランタイム内部で使用される高速な擬似乱数生成関数です。暗号学的な安全性は必要なく、単に予測不可能な値を素早く生成するために使用されます。このコミットでは、イテレータの開始バケットをランダムに選択するために利用されています。

## 技術的詳細

このコミットの核心は、マップのイテレータが常に最初のバケットから走査を開始するのではなく、**ランダムなバケットから走査を開始する**ように変更することです。

従来のイテレータは、マップの内部構造を先頭から順に走査していました。このため、`iter/delete`パターンで要素が削除されると、マップの先頭に近いバケットが空になりやすくなります。イテレータが常に先頭から開始すると、空のバケットを多数スキップしなければならず、これがパフォーマンス低下の原因となっていました。

新しいアプローチでは、`mapiterinit`関数（マップイテレータの初期化を行う関数）内で、イテレータの開始バケットをランダムに決定します。これにより、イテレータが常に同じ「ホットスポット」を走査し続けることを防ぎ、マップ全体にわたって走査が分散されます。

具体的には、以下の変更が行われています。
1.  `hiter`構造体に`startBucket`と`wrapped`という新しいフィールドが追加されました。
    *   `startBucket`: イテレーションが開始されたバケットのインデックスを記憶します。
    *   `wrapped`: イテレータがバケット配列の末尾から先頭に一周したかどうかを示すフラグです。
2.  `mapiterinit`関数内で、マップのサイズ（`h.B`、バケット配列のサイズを決定するビット数）に応じて、`it.startBucket`と`it.offset`（バケット内の開始オフセット）を`fastrand1()`を使ってランダムに設定します。
    *   `h.B == 0` (マップが非常に小さい場合): `startBucket`は0に固定し、`offset`のみランダム化。
    *   `h.B <= 31` (一般的なマップサイズ): `startBucket`をランダム化し、`offset`は0。
    *   `h.B > 31` (非常に大きなマップ): `startBucket`をより広範囲にランダム化（`fastrand1()`を2回使用）。
3.  `mapiternext`関数（イテレータの次の要素を取得する関数）では、イテレーションの終了条件が変更されました。従来の`it.done`フラグの代わりに、`bucket == it.startBucket && it.wrapped`という条件でイテレーションの終了を判断します。これにより、イテレータがランダムな開始点から一周して元の開始点に戻ってきたときに、イテレーションが完了したと判断されます。

この変更により、イテレータが空のバケットを繰り返し走査する可能性が大幅に減少し、`iter/delete`パターンにおける平均的な走査時間が改善されます。結果として、全体の計算量がO(N^2)からO(N log N)に削減され、特に大規模なマップでのパフォーマンスが劇的に向上しました。

## コアとなるコードの解説

### `src/runtime/hashmap.go`

*   **`hiter` 構造体の変更**:
    *   `startBucket uintptr`: イテレーションが開始されたバケットのインデックスを保持する新しいフィールド。
    *   `wrapped bool`: イテレータがバケット配列の末尾から先頭に一周したかどうかを示す新しいフラグ。
    *   `done bool` フィールドが削除され、`wrapped` に置き換えられました。
    *   `i uintptr` が `i uint8` に変更されました。これはバケット内のオフセットが`uint8`で十分なためです。

*   **`mapiterinit` 関数の変更**:
    *   イテレータの初期化時に、`h.B` (マップのバケット配列のサイズを決定するビット数) に応じて、`it.startBucket` と `it.offset` をランダムに決定するロジックが追加されました。
    *   `h.B == 0` の場合（マップが非常に小さい、または空の場合）、`startBucket` は0に固定され、`offset` のみがランダム化されます。
    *   `h.B <= 31` の場合、`startBucket` は `fastrand1()` を使ってランダムに選択されます。
    *   `h.B > 31` の場合（非常に大きなマップ）、`startBucket` は `fastrand1()` を2回使用して、より広範囲にランダム化されます。これは、`uintptr` が32ビットまたは64ビットであることに対応するためです。
    *   `it.bucket` は、従来の0固定から `it.startBucket` で初期化されるようになりました。
    *   `it.wrapped` は `false` で初期化されます。

*   **`mapiternext` 関数の変更**:
    *   イテレーションの終了条件が `it.done` から `bucket == it.startBucket && it.wrapped` に変更されました。これにより、イテレータがランダムな開始点からマップを一周し、再び開始点に戻ってきたときにイテレーションが終了するようになります。
    *   バケットが一周した際に `it.done = true` だった箇所が `it.wrapped = true` に変更されました。
    *   `offi` の計算で `uintptr(it.offset)` だった部分が `it.offset` に変更されました。これは `it.offset` が `uint8` に変更されたため、`uintptr` への変換が不要になったためです。また、`k` と `v` のアドレス計算で `offi` に `uintptr` キャストが追加され、型の一貫性が保たれています。

### `src/runtime/map_test.go`

*   **`benchmarkMapPop` 関数**:
    *   `map[int]int` を作成し、`n` 個の要素を挿入します。
    *   その後、`n` 回ループし、`for k := range m { delete(m, k); break }` というパターンでマップから1つずつ要素を削除します。このパターンが、まさにコミットが改善しようとしている「iter/deleteパターン」です。
    *   このベンチマークは、イテレータが常に同じ開始点から走査を開始し、空のバケットをスキップするコストを測定するために設計されています。

*   **`BenchmarkMapPop100`, `BenchmarkMapPop1000`, `BenchmarkMapPop10000`**:
    *   `benchmarkMapPop` 関数を、それぞれ100、1000、10000要素のマップに対して実行するベンチマーク関数です。これにより、マップのサイズが大きくなるにつれてパフォーマンスがどのように変化するかを測定できます。コミットメッセージのベンチマーク結果は、これらのテストによって生成されたものです。

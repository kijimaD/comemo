## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）戦略の進化の一環として行われました。従来のGoのGCは、メモリの割り当てと解放を管理するために、リンクリストベースの空きリストを使用していました。しかし、このアプローチは、特に大規模なヒープや高頻度のアロケーションが発生するシナリオにおいて、パフォーマンスのボトルネックとなる可能性がありました。

コミットメッセージにある`[dev.garbage]`というプレフィックスは、これがGoのGC開発ブランチにおける作業の一部であることを示唆しています。この変更の主な目的は、GCの「マークフェーズ」と「アロケーションフェーズ」をより効率的に統合することです。具体的には、到達可能なオブジェクトをマークする際に使用される`gcmarkBits`と、新しいオブジェクトを割り当てる際に空き領域を特定するために使用される`allocBits`という2つのビットベクタを導入し、これらをGCサイクル完了後に交換することで、リンクリストの構築と走査のオーバーヘッドを排除しようとしています。

このコミットは、新しいGCアルゴリズムの全体像を実現するための第一歩であり、ビットベクタを効率的に操作するための低レベルなヘルパー関数を提供することに重点を置いています。これにより、将来のコミットでより複雑なGCロジックが構築されるための土台が築かれました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **ガベージコレクション (GC)**:
    *   プログラムが動的に割り当てたメモリのうち、もはや使用されない（到達不可能になった）領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ（Concurrent Mark and Sweep）アルゴリズムをベースにしています。
    *   **マークフェーズ**: GCがヒープを走査し、プログラムから到達可能なすべてのオブジェクトを識別して「マーク」する段階です。
    *   **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトが占めるメモリ領域を「空き」として回収する段階です。

2.  **ビットベクタ (Bit Vector)**:
    *   ブール値（真/偽、0/1）のシーケンスを効率的に格納するためのデータ構造です。各ブール値は1ビットで表現されます。これにより、大量のフラグをコンパクトに表現し、高速なビット演算で操作できます。
    *   GCの文脈では、オブジェクトがマークされているか、メモリ領域が空いているか、ポインタを含んでいるかなどを表現するためによく使用されます。

3.  **ヒープ (Heap)**:
    *   プログラムが実行時に動的にメモリを割り当てる領域です。Goプログラムが`make`や`new`を使ってオブジェクトを作成すると、そのメモリはヒープに割り当てられます。

4.  **mspan**:
    *   Goランタイムのメモリ管理において、ヒープは`mspan`と呼ばれる連続したメモリページのチャンクに分割されます。各`mspan`は特定のサイズのオブジェクトを格納するように構成されており、その`mspan`内のオブジェクトのメタデータ（例えば、マークビット）を管理します。

5.  **アロケーションビット (allocBits) とマークビット (gcmarkBits)**:
    *   GoのGCでは、各オブジェクトの状態を追跡するためにビットマップを使用します。
    *   `allocBits`: あるメモリ領域が現在割り当てられているオブジェクトの一部であるかどうかを示すビットマップです。このコミットの文脈では、空き領域を特定するために使用されます。
    *   `gcmarkBits`: GCのマークフェーズ中に、到達可能と判断されたオブジェクトをマークするためのビットマップです。

6.  **アトミック操作 (Atomic Operations)**:
    *   複数のゴルーチン（またはスレッド）が同時に同じメモリ位置にアクセスする可能性がある場合でも、その操作が不可分（中断されない）であることを保証する操作です。これにより、データ競合を防ぎ、正確性を保ちます。`sync/atomic`パッケージで提供される関数がこれに該当します。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ管理における`mspan`構造体に関連するビットマップ操作の抽象化と効率化にあります。

GoのGCは、ヒープを`mspan`という単位で管理します。各`mspan`は、特定のサイズのオブジェクトを格納し、その`mspan`内のオブジェクトに関するメタデータ（例えば、そのオブジェクトがポインタを含むか、GCによってマークされているかなど）を保持します。

このコミットでは、特に以下の点が重要です。

1.  **`markBits`構造体の導入**:
    *   `markBits`は、特定のオブジェクトのマークビットへのアクセスを抽象化するための新しい構造体です。
    *   `bytep *uint8`: 実際のビットが格納されているバイトへのポインタ。
    *   `mask uint8`: そのバイト内で目的のビットを分離するためのマスク（例: `0x01`, `0x02`, `0x04`など）。
    *   `index uintptr`: `mspan`内のオブジェクトのインデックス。
    *   この構造体により、GCマークビットやアロケーションビットの操作がより安全かつ意図が明確になります。

2.  **`gcmarkBits`と`allocBits`の役割**:
    *   `gcmarkBits`: GCのマークフェーズ中に、到達可能なオブジェクトをマークするために使用されます。
    *   `allocBits`: GCサイクルが完了した後、`gcmarkBits`と`allocBits`が交換され、`allocBits`が新しいアロケーションのために空き領域を特定するために使用されます。これにより、アロケータはリンクリストを走査することなく、ビットマップを直接参照して空き領域を見つけることができます。これは、メモリ割り当ての高速化に寄与します。

3.  **ヘルパー関数の追加**:
    *   `mspan.allocBitsForIndex(allocBitIndex uintptr) markBits`: 指定されたインデックスに対応する`allocBits`の`markBits`構造体を返します。
    *   `mspan.nextFreeIndex(index uintptr) uintptr`: 指定されたインデックス以降で、次に空いているオブジェクトのインデックスを返します。これは、ビットマップを効率的に走査して空き領域を見つけるための重要な関数です。`0xff`（全ビットがセットされている）のバイトをスキップする最適化が含まれています。
    *   `mspan.isFree(index uintptr) bool`: 指定されたインデックスのオブジェクトが空きであるかどうかを報告します。
    *   `markBitsForAddr(p uintptr) markBits` / `mspan.markBitsForAddr(p uintptr) markBits`: 特定のアドレスに対応する`gcmarkBits`の`markBits`構造体を返します。
    *   `mspan.markBitsForIndex(markBitIndex uintptr) markBits`: 指定されたインデックスに対応する`gcmarkBits`の`markBits`構造体を返します。
    *   `markBits.isMarked() bool`: `markBits`が指すビットがセットされているか（マークされているか）を報告します。
    *   `markBits.setMarked()` / `markBits.clearMarked()`: `markBits`が指すビットをアトミックにセット/クリアします。これは、複数のゴルーチンが同時にGCマーク操作を行う可能性があるため、データ競合を防ぐために重要です。
    *   `markBits.setMarkedNonAtomic()` / `markBits.clearMarkedNonAtomic()`: 非アトミックなセット/クリア操作。特定のコンテキスト（例えば、単一のゴルーチンのみがアクセスする場合）でパフォーマンスを向上させるために使用されますが、注意が必要です。
    *   `mspan.clearGCMarkBits()` / `mspan.clearAllocBits()`: `mspan`内の`gcmarkBits`または`allocBits`全体をクリアします。これは、GCサイクルの開始時やビットマップの交換時に必要となります。

4.  **`heapBits.initSpan`の変更**:
    *   `mspan`が初期化される際に、`allocBits`と`gcmarkBits`が`mspan`内の`markbits1`と`markbits2`という内部配列に割り当てられ、`freeindex`と`nelems`が設定され、両方のビットマップがクリアされるようになりました。これにより、新しい`mspan`がGCとアロケーションの両方に対応できるようになります。

これらの変更は、GoのGCがより効率的でスケーラブルになるための重要なステップであり、特にメモリ割り当てと解放のオーバーヘッドを削減することを目的としています。

### `src/runtime/mbitmap.go`における主要な変更

#### `markBits`構造体

```go
type markBits struct {
	bytep *uint8
	mask  uint8
	index uintptr
}
```
この構造体は、特定のオブジェクトのマークビットへのポインタ（`bytep`）、そのバイト内の特定のビットを分離するためのマスク（`mask`）、および`mspan`内のオブジェクトのインデックス（`index`）をカプセル化します。これにより、ビット操作がより抽象的かつ安全になります。

#### `mspan.allocBitsForIndex`

```go
//go:nosplit
func (s *mspan) allocBitsForIndex(allocBitIndex uintptr) markBits {
	whichByte := allocBitIndex / 8
	whichBit := allocBitIndex % 8
	return markBits{&s.allocBits[whichByte], uint8(1 << whichBit), allocBitIndex}
}
```
`mspan`内の指定されたインデックスに対応する`allocBits`の`markBits`構造体を生成します。`allocBitIndex`をバイトオフセットとビットオフセットに分解し、対応するバイトへのポインタとマスクを作成します。

#### `mspan.nextFreeIndex`

```go
func (s *mspan) nextFreeIndex(index uintptr) uintptr {
	// ... (実装は上記コミット内容を参照) ...
}
```
この関数は、`mspan`内で`index`以降の最初の空きオブジェクトのインデックスを効率的に検索します。ビットマップをバイト単位で走査し、`0xff`（すべてのビットがセットされている、つまり空きがない）のバイトをスキップすることで最適化されています。これにより、リンクリストを走査するよりもはるかに高速に空き領域を見つけることができます。

#### `markBits.setMarked()` と `markBits.clearMarked()`

```go
func (m markBits) setMarked() {
	atomic.Or8(m.bytep, m.mask)
}

func (m markBits) clearMarked() {
	atomic.And8(m.bytep, ^m.mask)
}
```
これらの関数は、`markBits`が指すビットをアトミックにセットまたはクリアします。`atomic.Or8`と`atomic.And8`は、`sync/atomic`パッケージの関数で、複数のゴルーチンが同時にビットマップを更新する可能性がある場合に、データ競合を防ぎ、操作の不可分性を保証します。

#### `mspan.clearGCMarkBits()` と `mspan.clearAllocBits()`

```go
func (s *mspan) clearGCMarkBits() {
	bytesInMarkBits := (s.nelems + 7) / 8
	bits := s.gcmarkBits[:bytesInMarkBits]
	for i := range bits {
		bits[i] = 0
	}
}

func (s *mspan) clearAllocBits() {
	bytesInMarkBits := (s.nelems + 7) / 8
	bits := s.allocBits[:bytesInMarkBits]
	for i := range bits {
		bits[i] = 0
	}
}
```
これらの関数は、`mspan`内の`gcmarkBits`または`allocBits`の全ビットを0にクリアします。これは、GCサイクルの開始時や、`allocBits`が`gcmarkBits`と交換された後に、次のアロケーションのためにビットマップをリセットする際に使用されます。

#### `heapBits.initSpan`の変更

```go
func (h heapBits) initSpan(s *mspan) {
	size, n, total := s.layout()

	// Init the markbit structures
	s.allocBits = &s.markbits1
	s.gcmarkBits = &s.markbits2
	s.freeindex = 0
	s.nelems = n
	s.clearAllocBits()
	s.clearGCMarkBits()

	// Clear bits corresponding to objects.
	if total%heapBitmapScale != 0 {
		throw("initSpan: unaligned length")
	}
	// ... (既存のロジック) ...
}
```
この関数は、`mspan`が初期化される際に呼び出されます。変更点として、`s.allocBits`と`s.gcmarkBits`が`mspan`内の`markbits1`と`markbits2`という内部配列を指すように設定され、`freeindex`と`nelems`が初期化され、最後に`clearAllocBits()`と`clearGCMarkBits()`が呼び出されて両方のビットマップがクリアされます。これにより、新しい`mspan`がGCとアロケーションの両方で正しく機能するための準備が整います。

これらの変更は、GoのGCがより効率的なビットマップベースのアプローチに移行するための重要なステップであり、メモリ割り当てと解放のパフォーマンス向上に貢献します。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **ガベージコレクション (GC)**:
    *   プログラムが動的に割り当てたメモリのうち、もはや使用されない（到達不可能になった）領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ（Concurrent Mark and Sweep）アルゴリズムをベースにしています。
    *   **マークフェーズ**: GCがヒープを走査し、プログラムから到達可能なすべてのオブジェクトを識別して「マーク」する段階です。
    *   **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトが占めるメモリ領域を「空き」として回収する段階です。

2.  **ビットベクタ (Bit Vector)**:
    *   ブール値（真/偽、0/1）のシーケンスを効率的に格納するためのデータ構造です。各ブール値は1ビットで表現されます。これにより、大量のフラグをコンパクトに表現し、高速なビット演算で操作できます。
    *   GCの文脈では、オブジェクトがマークされているか、メモリ領域が空いているか、ポインタを含んでいるかなどを表現するためによく使用されます。

3.  **ヒープ (Heap)**:
    *   プログラムが実行時に動的にメモリを割り当てる領域です。Goプログラムが`make`や`new`を使ってオブジェクトを作成すると、そのメモリはヒープに割り当てられます。

4.  **mspan**:
    *   Goランタイムのメモリ管理において、ヒープは`mspan`と呼ばれる連続したメモリページのチャンクに分割されます。各`mspan`は特定のサイズのオブジェクトを格納するように構成されており、その`mspan`内のオブジェクトのメタデータ（例えば、マークビット）を管理します。

5.  **アロケーションビット (allocBits) とマークビット (gcmarkBits)**:
    *   GoのGCでは、各オブジェクトの状態を追跡するためにビットマップを使用します。
    *   `allocBits`: あるメモリ領域が現在割り当てられているオブジェクトの一部であるかどうかを示すビットマップです。このコミットの文脈では、空き領域を特定するために使用されます。
    *   `gcmarkBits`: GCのマークフェーズ中に、到達可能と判断されたオブジェクトをマークするためのビットマップです。

6.  **アトミック操作 (Atomic Operations)**:
    *   複数のゴルーチン（またはスレッド）が同時に同じメモリ位置にアクセスする可能性がある場合でも、その操作が不可分（中断されない）であることを保証する操作です。これにより、データ競合を防ぎ、正確性を保ちます。`sync/atomic`パッケージで提供される関数がこれに該当します。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ管理における`mspan`構造体に関連するビットマップ操作の抽象化と効率化にあります。

GoのGCは、ヒープを`mspan`という単位で管理します。各`mspan`は、特定のサイズのオブジェクトを格納し、その`mspan`内のオブジェクトに関するメタデータ（例えば、そのオブジェクトがポインタを含むか、GCによってマークされているかなど）を保持します。

このコミットでは、特に以下の点が重要です。

1.  **`markBits`構造体の導入**:
    *   `markBits`は、特定のオブジェクトのマークビットへのアクセスを抽象化するための新しい構造体です。
    *   `bytep *uint8`: 実際のビットが格納されているバイトへのポインタ。
    *   `mask uint8`: そのバイト内で目的のビットを分離するためのマスク（例: `0x01`, `0x02`, `0x04`など）。
    *   `index uintptr`: `mspan`内のオブジェクトのインデックス。
    *   この構造体により、ビット操作がより安全かつ意図が明確になります。

2.  **`gcmarkBits`と`allocBits`の役割**:
    *   `gcmarkBits`: GCのマークフェーズ中に、到達可能なオブジェクトをマークするために使用されます。
    *   `allocBits`: GCサイクルが完了した後、`gcmarkBits`と`allocBits`が交換され、`allocBits`が新しいアロケーションのために空き領域を特定するために使用されます。これにより、アロケータはリンクリストを走査することなく、ビットマップを直接参照して空き領域を見つけることができます。これは、メモリ割り当ての高速化に寄与します。

3.  **ヘルパー関数の追加**:
    *   `mspan.allocBitsForIndex(allocBitIndex uintptr) markBits`: 指定されたインデックスに対応する`allocBits`の`markBits`構造体を返します。
    *   `mspan.nextFreeIndex(index uintptr) uintptr`: 指定されたインデックス以降で、次に空いているオブジェクトのインデックスを返します。これは、ビットマップを効率的に走査して空き領域を見つけるための重要な関数です。`0xff`（全ビットがセットされている）のバイトをスキップする最適化が含まれています。
    *   `mspan.isFree(index uintptr) bool`: 指定されたインデックスのオブジェクトが空きであるかどうかを報告します。
    *   `markBitsForAddr(p uintptr) markBits` / `mspan.markBitsForAddr(p uintptr) markBits`: 特定のアドレスに対応する`gcmarkBits`の`markBits`構造体を返します。
    *   `mspan.markBitsForIndex(markBitIndex uintptr) markBits`: 指定されたインデックスに対応する`gcmarkBits`の`markBits`構造体を返します。
    *   `markBits.isMarked() bool`: `markBits`が指すビットがセットされているか（マークされているか）を報告します。
    *   `markBits.setMarked()` / `markBits.clearMarked()`: `markBits`が指すビットをアトミックにセット/クリアします。これは、複数のゴルーチンが同時にGCマーク操作を行う可能性があるため、データ競合を防ぐために重要です。
    *   `markBits.setMarkedNonAtomic()` / `markBits.clearMarkedNonAtomic()`: 非アトミックなセット/クリア操作。特定のコンテキスト（例えば、単一のゴルーチンのみがアクセスする場合）でパフォーマンスを向上させるために使用されますが、注意が必要です。
    *   `mspan.clearGCMarkBits()` / `mspan.clearAllocBits()`: `mspan`内の`gcmarkBits`または`allocBits`全体をクリアします。これは、GCサイクルの開始時やビットマップの交換時に必要となります。

4.  **`heapBits.initSpan`の変更**:
    *   `mspan`が初期化される際に、`allocBits`と`gcmarkBits`が`mspan`内の`markbits1`と`markbits2`という内部配列に割り当てられ、`freeindex`と`nelems`が設定され、両方のビットマップがクリアされるようになりました。これにより、新しい`mspan`がGCとアロケーションの両方に対応できるようになります。

これらの変更は、GoのGCがより効率的でスケーラブルになるための重要なステップであり、特にメモリ割り当てと解放のオーバーヘッドを削減することを目的としています。

## コアとなるコードの解説

### `src/runtime/mbitmap.go`における主要な変更

#### `markBits`構造体

```go
type markBits struct {
	bytep *uint8
	mask  uint8
	index uintptr
}
```
この構造体は、特定のオブジェクトのマークビットへのポインタ（`bytep`）、そのバイト内の特定のビットを分離するためのマスク（`mask`）、および`mspan`内のオブジェクトのインデックス（`index`）をカプセル化します。これにより、ビット操作がより抽象的かつ安全になります。

#### `mspan.allocBitsForIndex`

```go
//go:nosplit
func (s *mspan) allocBitsForIndex(allocBitIndex uintptr) markBits {
	whichByte := allocBitIndex / 8
	whichBit := allocBitIndex % 8
	return markBits{&s.allocBits[whichByte], uint8(1 << whichBit), allocBitIndex}
}
```
`mspan`内の指定されたインデックスに対応する`allocBits`の`markBits`構造体を生成します。`allocBitIndex`をバイトオフセットとビットオフセットに分解し、対応するバイトへのポインタとマスクを作成します。

#### `mspan.nextFreeIndex`

```go
func (s *mspan) nextFreeIndex(index uintptr) uintptr {
	// ... (実装は上記コミット内容を参照) ...
}
```
この関数は、`mspan`内で`index`以降の最初の空きオブジェクトのインデックスを効率的に検索します。ビットマップをバイト単位で走査し、`0xff`（すべてのビットがセットされている、つまり空きがない）のバイトをスキップすることで最適化されています。これにより、リンクリストを走査するよりもはるかに高速に空き領域を見つけることができます。

#### `markBits.setMarked()` と `markBits.clearMarked()`

```go
func (m markBits) setMarked() {
	atomic.Or8(m.bytep, m.mask)
}

func (m markBits) clearMarked() {
	atomic.And8(m.bytep, ^m.mask)
}
```
これらの関数は、`markBits`が指すビットをアトミックにセットまたはクリアします。`atomic.Or8`と`atomic.And8`は、`sync/atomic`パッケージの関数で、複数のゴルーチンが同時にビットマップを更新する可能性がある場合に、データ競合を防ぎ、操作の不可分性を保証します。

#### `mspan.clearGCMarkBits()` と `mspan.clearAllocBits()`

```go
func (s *mspan) clearGCMarkBits() {
	bytesInMarkBits := (s.nelems + 7) / 8
	bits := s.gcmarkBits[:bytesInMarkBits]
	for i := range bits {
		bits[i] = 0
	}
}

func (s *mspan) clearAllocBits() {
	bytesInMarkBits := (s.nelems + 7) / 8
	bits := s.allocBits[:bytesInMarkBits]
	for i := range bits {
		bits[i] = 0
	}
}
```
これらの関数は、`mspan`内の`gcmarkBits`または`allocBits`の全ビットを0にクリアします。これは、GCサイクルの開始時や、`allocBits`が`gcmarkBits`と交換された後に、次のアロケーションのためにビットマップをリセットする際に使用されます。

#### `heapBits.initSpan`の変更

```go
func (h heapBits) initSpan(s *mspan) {
	size, n, total := s.layout()

	// Init the markbit structures
	s.allocBits = &s.markbits1
	s.gcmarkBits = &s.markbits2
	s.freeindex = 0
	s.nelems = n
	s.clearAllocBits()
	s.clearGCMarkBits()

	// Clear bits corresponding to objects.
	if total%heapBitmapScale != 0 {
		throw("initSpan: unaligned length")
	}
	// ... (既存のロジック) ...
}
```
この関数は、`mspan`が初期化される際に呼び出されます。変更点として、`s.allocBits`と`s.gcmarkBits`が`mspan`内の`markbits1`と`markbits2`という内部配列を指すように設定され、`freeindex`と`nelems`が初期化され、最後に`clearAllocBits()`と`clearGCMarkBits()`が呼び出されて両方のビットマップがクリアされます。これにより、新しい`mspan`がGCとアロケーションの両方で正しく機能するための準備が整います。

これらの変更は、GoのGCがより効率的なビットマップベースのアプローチに移行するための重要なステップであり、メモリ割り当てと解放のパフォーマンス向上に貢献します。

# [インデックス 19883] ファイルの概要

このコミットは、Go言語の標準ライブラリ `crypto/tls` パッケージにApplication-Layer Protocol Negotiation (ALPN) のサポートを追加するものです。これにより、TLSハンドシェイク中にアプリケーション層プロトコル（例: HTTP/2）のネゴシエーションが可能になり、RFC 7301に準拠したより堅牢なプロトコル選択メカニズムが提供されます。

## 変更の背景

この変更の主な背景は、TLS (Transport Layer Security) ハンドシェイク中にアプリケーション層プロトコルを効率的かつ安全にネゴシエートする必要性が高まったことです。特に、HTTP/2のような新しいプロトコルは、TLS接続確立時にどのアプリケーションプロトコルを使用するかを事前に決定するメカニズムを必要とします。

以前のGoの`crypto/tls`実装では、Next Protocol Negotiation (NPN) という別のプロトコルネゴシエーション拡張がサポートされていましたが、ALPNはNPNの後継としてIETFによって標準化された（RFC 7301）より推奨されるメカニズムです。ALPNは、クライアントがサポートするプロトコルリストを提示し、サーバーがその中から一つを選択するという、よりシンプルなネゴシエーションモデルを提供します。

このコミットは、GoのTLSスタックを最新の標準に準拠させ、HTTP/2などのALPNに依存するプロトコルをより適切にサポートするために行われました。また、`Fixes #6736`とあることから、既存の課題や不足していた機能への対応でもあります。この課題は、ALPNのサポートがGoのTLSライブラリに求められていたことを示唆しています。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。クライアントとサーバー間でデータを送受信する前に、認証、データの機密性、完全性を確保するための「ハンドシェイク」プロセスを実行します。このハンドシェイク中に、使用する暗号スイート、プロトコルバージョン、および様々な拡張機能がネゴシエートされます。

### ALPN (Application-Layer Protocol Negotiation)

ALPNは、TLSの拡張機能の一つで、TLSハンドシェイクの一部として、どのアプリケーション層プロトコル（例: HTTP/1.1, HTTP/2, SPDYなど）を使用するかをネゴシエートすることを可能にします。

*   **仕組み**:
    1.  **ClientHello**: クライアントは、`ClientHello`メッセージの一部として、サポートするアプリケーションプロトコルのリスト（優先順位付き）をALPN拡張としてサーバーに送信します。
    2.  **ServerHello**: サーバーは、クライアントが提示したリストの中から、自身がサポートする最も優先度の高いプロトコルを一つ選択し、`ServerHello`メッセージのALPN拡張としてクライアントに返します。
    3.  **ネゴシエーションの失敗**: もしサーバーがクライアントのリスト内のどのプロトコルもサポートしない場合、サーバーはALPN拡張を返さず、TLSハンドシェイクは続行されますが、アプリケーションプロトコルのネゴシエーションは行われません（または失敗します）。このコミットでは、この場合の挙動がより厳格になり、ハンドシェイクが失敗するようになりました。

### NPN (Next Protocol Negotiation)

NPNは、ALPNの前に存在した同様のプロトコルネゴシエーション拡張です。NPNでは、サーバーがサポートするプロトコルリストをクライアントに提示し、クライアントがその中から一つを選択するという、ALPNとは逆のネゴシエーションフローでした。ALPNが標準化されたことで、NPNは非推奨となり、ALPNへの移行が進められました。このコミットでは、NPNとALPNの共存、またはALPN優先のロジックが導入されています。

### RFC 7301

ALPNの仕様を定義するIETFの標準ドキュメントです。このコミットは、Goの`crypto/tls`パッケージがこのRFCに準拠するように変更されたことを意味します。

## 技術的詳細

このコミットは、Goの`crypto/tls`パッケージにALPNを統合するために、TLSハンドシェイクのメッセージ構造とネゴシエーションロジックに広範な変更を加えています。

1.  **ALPN拡張の定義**:
    *   `src/pkg/crypto/tls/common.go` に `extensionALPN` という新しいTLS拡張タイプ定数 (`uint16 = 16`) が追加されました。これは、ALPN拡張がTLSメッセージ内で識別されるためのIDです。

2.  **メッセージ構造の変更**:
    *   `src/pkg/crypto/tls/handshake_messages.go` 内の `clientHelloMsg` 構造体に `alpnProtocols []string` フィールドが追加されました。これにより、クライアントはサポートするアプリケーションプロトコルリストを`ClientHello`メッセージに含めることができるようになります。
    *   同様に、`serverHelloMsg` 構造体に `alpnProtocol string` フィールドが追加されました。これにより、サーバーは選択した単一のアプリケーションプロトコルを`ServerHello`メッセージに含めることができるようになります。
    *   これらの新しいフィールドに対応するため、`marshal()` および `unmarshal()` メソッドが更新され、ALPN拡張のエンコードとデコードロジックが実装されました。これには、プロトコル名の長さチェックや、複数のプロトコル名を効率的に格納するためのバイト列の構築が含まれます。

3.  **クライアント側のハンドシェイクロジック**:
    *   `src/pkg/crypto/tls/handshake_client.go` では、`clientHandshake()` 関数が `Config.NextProtos` フィールド（ALPNで利用されるプロトコルリスト）を処理し、`clientHelloMsg` の `alpnProtocols` フィールドに設定するようになりました。
    *   `processServerHello()` 関数が更新され、サーバーからのALPN応答を処理するロジックが追加されました。
        *   クライアントがALPNを要求していないのにサーバーがALPNを広告した場合、ハンドシェイクは失敗します。
        *   サーバーがNPNとALPNの両方を広告した場合も、ハンドシェイクは失敗します（これはRFC 7301で禁止されています）。
        *   サーバーがALPNプロトコルを選択した場合、そのプロトコルが `c.clientProtocol` に設定されます。
    *   `mutualProtocol` 関数が変更され、NPNだけでなくALPNのプロトコルネゴシエーションにも対応するように汎用化されました。この関数は、クライアントとサーバーがサポートするプロトコルリストから相互に合意できるプロトコルを見つけ出す役割を担います。

4.  **サーバー側のハンドシェイクロジック**:
    *   `src/pkg/crypto/tls/handshake_server.go` では、サーバーがクライアントの `clientHello.alpnProtocols` を受け取り、自身の `config.NextProtos` と比較して `mutualProtocol` 関数を用いて合意可能なプロトコルを決定するロジックが追加されました。
    *   合意されたプロトコルは `hs.hello.alpnProtocol` に設定され、`ServerHello`メッセージでクライアントに返されます。
    *   ALPNがネゴシエートされた場合、NPNのネゴシエーションは行われません。これは、ALPNがNPNよりも優先されるべき新しい標準であるためです。

5.  **テストの追加**:
    *   `src/pkg/crypto/tls/handshake_client_test.go` および `src/pkg/crypto/tls/handshake_server_test.go` に、ALPNのネゴシエーションが成功する場合と、プロトコルが一致しない場合にハンドシェイクが失敗するケースを検証する新しいテストケースが追加されました。これらのテストは、OpenSSLの`-alpn`フラグを使用して、実際のALPNネゴシエーションをシミュレートしています。
    *   `src/pkg/crypto/tls/testdata/` ディレクトリに、ALPNネゴシエーションの成功/失敗シナリオに対応する新しいテストデータファイルが追加されました。これらは、TLSハンドシェイクのバイト列ダンプを含んでおり、プロトコルネゴシエーションが期待通りに行われることを確認するために使用されます。

これらの変更により、Goの`crypto/tls`パッケージは、ALPNを介したアプリケーション層プロトコルのネゴシエーションを完全にサポートし、HTTP/2などのプロトコルとの互換性を向上させました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイルと構造体、関数に集中しています。

1.  **`src/pkg/crypto/tls/common.go`**:
    *   `extensionALPN` 定数の追加:
        ```go
        const (
            // ...
            extensionALPN                uint16 = 16
            // ...
        )
        ```
        これはALPN拡張のTLS拡張タイプIDを定義します。

2.  **`src/pkg/crypto/tls/handshake_messages.go`**:
    *   `clientHelloMsg` 構造体への `alpnProtocols` フィールドの追加:
        ```go
        type clientHelloMsg struct {
            // ...
            alpnProtocols       []string
        }
        ```
        クライアントがサポートするALPNプロトコルリストを保持します。
    *   `serverHelloMsg` 構造体への `alpnProtocol` フィールドの追加:
        ```go
        type serverHelloMsg struct {
            // ...
            alpnProtocol        string
        }
        ```
        サーバーが選択した単一のALPNプロトコルを保持します。
    *   これらの構造体の `marshal()` および `unmarshal()` メソッドが、ALPN拡張のエンコード/デコードロジックを含むように更新されました。

3.  **`src/pkg/crypto/tls/handshake_client.go`**:
    *   `clientHandshake()` 関数内で、`c.config.NextProtos` を `hello.alpnProtocols` に設定するロジックが追加されました。
    *   `processServerHello()` 関数内で、ALPNネゴシエーションの成功/失敗ロジックが追加されました。特に、クライアントがALPNを要求していないのにサーバーがALPNを広告した場合、またはNPNとALPNの両方を広告した場合にエラーを返す部分が重要です。
        ```go
        // ...
        clientDidNPN := hs.hello.nextProtoNeg
        clientDidALPN := len(hs.hello.alpnProtocols) > 0
        serverHasNPN := hs.serverHello.nextProtoNeg
        serverHasALPN := len(hs.serverHello.alpnProtocol) > 0

        if !clientDidNPN && serverHasNPN {
            c.sendAlert(alertHandshakeFailure)
            return false, errors.New("server advertised unrequested NPN extension")
        }

        if !clientDidALPN && serverHasALPN {
            c.sendAlert(alertHandshakeFailure)
            return false, errors.New("server advertised unrequested ALPN extension")
        }

        if serverHasNPN && serverHasALPN {
            c.sendAlert(alertHandshakeFailure)
            return false, errors.New("server advertised both NPN and ALPN extensions")
        }

        if serverHasALPN {
            c.clientProtocol = hs.serverHello.alpnProtocol
            c.clientProtocolFallback = false
        }
        // ...
        ```
    *   `mutualProtocol` 関数のシグネチャとロジックが変更され、ALPNとNPNの両方に対応するように汎用化されました。
        ```go
        // mutualProtocol finds the mutual Next Protocol Negotiation or ALPN protocol
        // given list of possible protocols and a list of the preference order. The
        // first list must not be empty. It returns the resulting protocol and flag
        // indicating if the fallback case was reached.
        func mutualProtocol(protos, preferenceProtos []string) (string, bool) {
            for _, s := range preferenceProtos {
                for _, c := range protos {
                    if s == c {
                        return s, false
                    }
                }
            }
            return protos[0], true
        }
        ```

4.  **`src/pkg/crypto/tls/handshake_server.go`**:
    *   サーバー側でALPNネゴシエーションを行うロジックが追加されました。クライアントがALPNプロトコルを提示した場合、`mutualProtocol` を使用して合意可能なプロトコルを決定し、`hs.hello.alpnProtocol` に設定します。
        ```go
        // ...
        if len(hs.clientHello.alpnProtocols) > 0 {
            if selectedProto, fallback := mutualProtocol(hs.clientHello.alpnProtocols, c.config.NextProtos); !fallback {
                hs.hello.alpnProtocol = selectedProto
                c.clientProtocol = selectedProto
            }
        } else {
            // ... existing NPN logic ...
            if hs.clientHello.nextProtoNeg && len(config.NextProtos) > 0 {
                hs.hello.nextProtoNeg = true
                hs.hello.nextProtos = config.NextProtos
            }
        }
        // ...
        ```

## コアとなるコードの解説

このコミットの核心は、TLSハンドシェイクにおけるALPN拡張の導入と、それに伴うプロトコルネゴシエーションロジックの強化です。

`src/pkg/crypto/tls/common.go` で定義された `extensionALPN` は、TLS拡張メッセージ内でALPNを識別するためのユニークな数値IDを提供します。これにより、TLSスタックは受信した拡張がALPN関連のものであることを認識できます。

`src/pkg/crypto/tls/handshake_messages.go` の変更は、ALPNプロトコルリストをTLSハンドシェイクメッセージ（`ClientHello`と`ServerHello`）に含めるための基盤を築きます。`clientHelloMsg.alpnProtocols` はクライアントがサポートするプロトコル群を、`serverHelloMsg.alpnProtocol` はサーバーが選択した単一のプロトコルを表現します。これらのフィールドの追加に伴い、メッセージのバイト列への変換（`marshal`）とバイト列からの解析（`unmarshal`）ロジックが更新され、ALPN拡張のデータ構造が正しく処理されるようにしています。特に、プロトコル名の長さ制限（255バイト）や、複数のプロトコル名を効率的に格納するための可変長エンコーディングが考慮されています。

`src/pkg/crypto/tls/handshake_client.go` と `src/pkg/crypto/tls/handshake_server.go` の変更は、実際のALPNネゴシエーションのフローを実装しています。

クライアント側では、`Config.NextProtos` に設定されたアプリケーションプロトコルリストが `ClientHello` メッセージのALPN拡張として送信されます。サーバーからの `ServerHello` を処理する際、クライアントはALPN拡張が存在するかどうか、そしてその内容がRFC 7301の要件を満たしているか（例: NPNとALPNが同時に広告されていないか、クライアントが要求していないALPNが広告されていないか）を厳格にチェックします。これにより、不正なハンドシェイクやプロトコル違反を防ぎます。ネゴシエーションが成功した場合、選択されたプロトコルは `ConnectionState.NegotiatedProtocol` (または内部的には `c.clientProtocol`) に格納され、アプリケーション層で利用できるようになります。

サーバー側では、受信した `ClientHello` のALPN拡張を解析し、自身の `Config.NextProtos` と比較して、`mutualProtocol` 関数を用いて合意可能なプロトコルを決定します。`mutualProtocol` 関数は、クライアントとサーバーのプロトコルリストを比較し、サーバーの優先順位に従って最適な共通プロトコルを選択します。この関数は、ALPNとNPNの両方のネゴシエーションロジックを抽象化しており、柔軟なプロトコル選択を可能にしています。合意されたプロトコルは `ServerHello` メッセージのALPN拡張としてクライアントに返送されます。ALPNがネゴシエートされた場合、NPNはスキップされることで、新しい標準への移行が促されます。

これらの変更は、GoのTLS実装がALPNを介したアプリケーション層プロトコルネゴシエーションを完全にサポートし、HTTP/2などの現代のプロトコルとの互換性と堅牢性を大幅に向上させる上で不可欠です。

# [インデックス 21628] ファイルの概要

このコミットは、Goランタイムにおける並行GC（Garbage Collection）のトリガーメカニズムに関する修正です。具体的には、GCが開始されるタイミングを調整し、ヒープメモリの使用状況に基づいてより効率的なGCサイクルを確立することを目的としています。

## 元コミット内容

Goランタイムにおいて、並行GCのトリガーロジックを修正します。
利用可能なヒープメモリの7/8を使用した時点でGCをトリガーするように調整します。
最初のGCは、ヒープサイズが4MBを超えた時点で実行されます。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作する「並行GC」を採用しています。この並行GCの効率は、GCが開始されるタイミング（トリガー）に大きく依存します。GCのトリガーが早すぎると、不要なGCサイクルが頻繁に発生し、プログラムのパフォーマンスに悪影響を与える可能性があります。逆に、トリガーが遅すぎると、ヒープメモリが枯渇し、プログラムが一時停止する時間が長くなる（ストップ・ザ・ワールド時間が長くなる）可能性があります。

このコミット以前のGoランタイムでは、GCのトリガーヒューリスティックが「前回のGCサイクルで解放された利用可能なスペースの約半分が使用されたとき」という原始的なものでした。このヒューリスティックは、GCが完了するのに十分な時間が確保できない場合に、メモリ使用量が増加するというフィードバックループを確立することを意図していましたが、より洗練されたトリガーメカニズムが求められていました。

この変更の背景には、以下の課題認識があったと考えられます。

1.  **GCトリガーの精度向上**: 従来のヒューリスティックでは、ヒープ使用量の変動に対してGCの開始タイミングが最適ではない場合がありました。特に、メモリ割り当てが急増するようなワークロードでは、GCが間に合わず、ヒープが肥大化するリスクがありました。
2.  **ミューテータのメモリ確保保証**: 並行GCが実行されている間も、アプリケーション（ミューテータ）はメモリを割り当て続けます。GCが完了する前にミューテータがメモリを使い果たしてしまうと、GCが中断されたり、パフォーマンスが低下したりする可能性があります。そのため、GCサイクル中にミューテータが十分なメモリを割り当てられるように、GCトリガーのタイミングを調整する必要がありました。
3.  **初期GCの最適化**: プログラム起動直後のヒープサイズが小さい段階でのGCトリガーも考慮する必要がありました。このコミットでは、最初のGCを4MBのヒープサイズを超えた時点に設定することで、初期段階での不要なGCを避けつつ、適切なタイミングでGCを開始するように調整しています。

これらの課題に対処するため、より予測可能で効率的なGCトリガーメカニズムを導入することが、このコミットの主要な目的です。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）に関する基本的な知識が必要です。

### Goのガベージコレクション（GC）

Goは、自動メモリ管理を採用しており、開発者が手動でメモリを解放する必要はありません。その代わりに、ガベージコレクタが不要になったメモリ領域を自動的に特定し、解放します。GoのGCは、主に以下の特徴を持っています。

*   **並行GC (Concurrent GC)**: GoのGCは、ほとんどの処理をアプリケーションの実行と並行して行います。これにより、GCによるアプリケーションの一時停止時間（ストップ・ザ・ワールド時間）を最小限に抑え、高いスループットと低いレイテンシを実現します。
*   **三色マーク＆スイープ (Tri-color Mark-and-Sweep)**: GoのGCは、三色マーク＆スイープアルゴリズムをベースにしています。オブジェクトは「白（未訪問）」「灰（訪問済みだが参照先は未訪問）」「黒（訪問済みで参照先も訪問済み）」のいずれかの色に分類され、マークフェーズで到達可能なオブジェクトを特定し、スイープフェーズで到達不可能な（ガベージ）オブジェクトを解放します。
*   **GCトリガー**: GCは、ヒープメモリの使用量がある閾値を超えたときにトリガーされます。この閾値は、`GOGC`環境変数によって制御されるGC目標（GC percent）に基づいて動的に調整されます。GC目標は、前回のGCでマークされたライブオブジェクトの量に対して、どれだけの新しいメモリを割り当てたら次のGCを開始するかを決定します。例えば、`GOGC=100`の場合、ライブオブジェクトの量が2倍になったら次のGCが開始されます。

### `memstats`構造体

Goランタイムには、メモリ統計を管理するための`memstats`というグローバルな構造体があります。この構造体には、ヒープの割り当て量、GCの目標値、次回のGCがトリガーされるべきヒープサイズなど、様々なメモリ関連の統計情報が含まれています。

*   `memstats.heap_alloc`: 現在ヒープに割り当てられているメモリの総量（バイト単位）。
*   `memstats.next_gc`: 次回のGCがトリガーされるべきヒープの目標サイズ（バイト単位）。この値は、前回のGCでマークされたライブオブジェクトの量と`GOGC`の値に基づいて計算されます。

### `atomicloaduint`関数

`atomicloaduint`は、Goランタイム内部で使用されるアトミック操作の一つで、符号なし整数値をアトミックに読み込みます。これにより、複数のゴルーチンが同時に同じメモリ位置にアクセスしても、データの競合や破損が発生しないことが保証されます。このコミットでは、`bggc.working`（バックグラウンドGCが現在動作中かどうかを示すフラグ）の値を安全に読み込むために使用されています。

### `triggerratio`

このコミットで導入される新しい概念で、GCをトリガーするヒープメモリの利用可能な割合を決定するための比率です。

## 技術的詳細

このコミットの技術的な核心は、GCトリガーのロジックを`shouldtriggergc`関数内で変更し、`triggerratio`という新しい変数と`memstats.next_gc`を組み合わせて使用することです。

### `triggerratio`の導入

`triggerratio`という新しいグローバル変数が導入されました。初期値は`8`に設定されています。

```go
// Trigger the concurrent GC when 1/triggerratio memory is available to allocate.
// Adjust this ratio as part of a scheme to ensure that mutators have enough
// memory to allocate in durring a concurrent GC cycle.
var triggerratio = int64(8)
```

このコメントが示すように、`triggerratio`は「利用可能なメモリの1/`triggerratio`が割り当てられたときに並行GCをトリガーする」という目的を持っています。`triggerratio = 8`の場合、これは「利用可能なメモリの1/8が残っている（つまり、7/8が使用された）ときにGCをトリガーする」ことを意味します。この比率を調整することで、並行GCサイクル中にミューテータが十分なメモリを割り当てられるようにするスキームの一部として機能します。

### `shouldtriggergc`関数の変更

`shouldtriggergc`関数は、GCを開始すべきかどうかを決定するロジックを含んでいます。

**変更前**:

```go
return memstats.heap_alloc+memstats.heap_alloc*3/4 >= memstats.next_gc && atomicloaduint(&bggc.working) == 0
```

この古いロジックは、「`memstats.heap_alloc`（現在のヒープ割り当て量）にその3/4を加えた値が`memstats.next_gc`（次回のGC目標値）以上であり、かつバックグラウンドGCが動作中でない場合」にGCをトリガーするというものでした。これは、「前回のGCサイクルで解放された利用可能なスペースの約半分が使用されたとき」というヒューリスティックに対応していました。

**変更後**:

```go
return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_alloc)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0
```

新しいロジックは、`triggerratio`と`memstats.next_gc`、`memstats.heap_alloc`を組み合わせています。

*   `int64(memstats.next_gc) - int64(memstats.heap_alloc)`: これは、次回のGC目標値から現在のヒープ割り当て量を引いたもので、**GC目標値に到達するまでに残されたメモリ量**を示します。
*   `triggerratio * (残されたメモリ量)`: この計算は、`triggerratio`倍した残されたメモリ量が、`memstats.next_gc`（次回のGC目標値）以下であるかどうかをチェックします。

この式を整理すると、以下のようになります。

`triggerratio * (next_gc - heap_alloc) <= next_gc`

`triggerratio * next_gc - triggerratio * heap_alloc <= next_gc`

`triggerratio * next_gc - next_gc <= triggerratio * heap_alloc`

`(triggerratio - 1) * next_gc <= triggerratio * heap_alloc`

`heap_alloc >= ((triggerratio - 1) / triggerratio) * next_gc`

`triggerratio = 8`の場合、

`heap_alloc >= ((8 - 1) / 8) * next_gc`

`heap_alloc >= (7 / 8) * next_gc`

これは、「現在のヒープ割り当て量（`heap_alloc`）が、次回のGC目標値（`next_gc`）の7/8以上になったらGCをトリガーする」という条件を意味します。つまり、利用可能なヒープメモリの7/8が使用された時点でGCが開始されるようになります。

### 初期GCのトリガー

`src/runtime/mgc.go`の`gcinit`関数に以下の行が追加されました。

```go
memstats.next_gc = 4 << 20 // 4 megs to start with
```

これは、プログラム起動時（GC初期化時）に、`memstats.next_gc`の初期値を4MB（`4 << 20`は4 * 2^20 = 4 * 1024 * 1024 バイト）に設定することを意味します。これにより、最初のGCはヒープサイズが4MBを超えた時点でトリガーされるようになります。これは、非常に小さなヒープで頻繁にGCが実行されるのを防ぎ、ある程度のメモリが使用されてからGCを開始することで、初期のパフォーマンスを向上させる効果があります。

## コアとなるコードの解説

### `src/runtime/malloc.go`の変更

1.  **`triggerratio`変数の追加**:
    `triggerratio`は、GCトリガーの新しいパラメータとして導入されました。デフォルト値は`8`です。この値は、GCが開始されるべきヒープの「空き」割合を決定します。`1/triggerratio`のメモリが割り当て可能になったときにGCをトリガーするという考え方です。これは、GCサイクル中にミューテータがメモリを割り当て続けるためのバッファを確保することを目的としています。

2.  **`shouldtriggergc`関数のロジック変更**:
    この変更が最も重要です。新しい条件式`triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_alloc)) <= int64(memstats.next_gc)`は、GCのトリガータイミングをより正確に制御します。
    前述の技術的詳細で解説したように、この式は実質的に「現在のヒープ割り当て量（`memstats.heap_alloc`）が、次回のGC目標値（`memstats.next_gc`）の7/8以上になったらGCをトリガーする」という条件に変換されます。
    これにより、GC目標値に近づくにつれてGCがトリガーされるようになり、ヒープの急激な増加を防ぎつつ、GCが完了するのに十分な時間を確保できるようになります。また、`atomicloaduint(&bggc.working) == 0`は、GCが既に実行中でないことを確認するための既存の条件です。

### `src/runtime/mgc.go`の変更

1.  **`gcinit`関数での`memstats.next_gc`初期化**:
    `gcinit`関数は、GoランタイムのGCシステムが初期化される際に呼び出されます。この変更により、`memstats.next_gc`の初期値が4MBに設定されます。これは、Goプログラムが起動してすぐにGCが頻繁に実行されるのを防ぐための最適化です。プログラムがまだ少量のメモリしか使用していない段階でGCを実行しても効率が悪いため、ある程度のメモリ（4MB）が割り当てられてから最初のGCがトリガーされるようにすることで、初期のパフォーマンスオーバーヘッドを削減します。

これらの変更により、Goの並行GCは、ヒープメモリの使用状況に対してより応答性が高く、かつ効率的なトリガーメカニズムを持つことになります。これにより、アプリケーションのレイテンシとスループットのバランスが改善され、よりスムーズな実行が期待されます。

# [インデックス 26575] ファイルの概要

このコミットは、Goコマンドがコンパイラおよびリンカに渡す`-I`（インクルードパス）および`-L`（ライブラリパス）オプションの順序が、`GOPATH`環境変数の順序と一致しない場合に発生する問題を修正します。これにより、`GOPATH`内でシャドウされている（同じ名前で異なるパスに存在する）パッケージが意図しない順序で解決され、誤ったバージョンのパッケージがビルドに使用される可能性がありました。この変更は、これらのオプションの順序を`GOPATH`の順序と一致させることで、この問題を解決します。

## 元コミット内容

Goコマンドがコンパイラおよびリンカに渡す`-I`および`-L`オプションの順序が`GOPATH`の順序と一致しない問題を修正。これにより、`GOPATH`の異なるエントリに存在する同じ名前のパッケージが誤ってシャドウされ、意図しないバージョンのパッケージが使用される可能性があった。このコミットは、これらのオプションの順序を`GOPATH`の順序と一致させることで、この問題を解決する。

## 変更の背景

この変更は、主にGoのビルドシステムにおけるパッケージ解決の不整合を解消するために行われました。`GOPATH`は、Goのソースコード、コンパイル済みパッケージ、および実行可能バイナリが配置されるディレクトリのリストを定義する重要な環境変数です。Goツールは、この`GOPATH`のリストを左から右へと順に検索し、パッケージを解決します。つまり、リストの先頭に近いパスにあるパッケージが優先されます。

しかし、このコミット以前は、`go`コマンドが内部的にコンパイラ（`go tool compile`）やリンカ（`go tool link`）を呼び出す際に、`-I`（インクルードディレクトリ）や`-L`（ライブラリディレクトリ）オプションの順序が`GOPATH`の順序と逆になることがありました。例えば、`GOPATH=p1:p2`と設定されているにもかかわらず、コンパイラが`-I p2 -I p1`のようにオプションを受け取ってしまうケースです。

このような状況が発生すると、`p1`と`p2`の両方に同じ名前のパッケージ（例: `foo`）が存在する場合、`GOPATH`のセマンティクスでは`p1`の`foo`が優先されるべきなのに、コンパイラやリンカは誤って`p2`の`foo`を使用してしまいます。これは、特に複数の`GOPATH`エントリを使用している開発環境や、異なるバージョンのライブラリが`GOPATH`の異なる場所に存在するような場合に、予期せぬビルドエラーやランタイムの動作変更を引き起こす可能性がありました。

この問題は、以下のGoイシューで報告されていました。
- **Issue #14176**: `cmd/go: go install uses wrong package when GOPATH has multiple entries`
- **Issue #14192**: `cmd/go: go build -i uses wrong package when GOPATH has multiple entries`

これらのイシューは、`GOPATH`の順序が尊重されないことによる具体的な問題事例を報告しており、このコミットはそれらの問題を直接的に解決することを目的としています。関連するが、このコミットでは修正されていないより複雑な問題として **Issue #14271** も言及されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念とビルドプロセスの知識が不可欠です。

1.  **GOPATH**:
    *   `GOPATH`は、Goのワークスペースのルートディレクトリを指定する環境変数です。複数のディレクトリパスをコロン（Unix系）またはセミコロン（Windows）で区切って指定できます（例: `GOPATH=/home/user/go_projects:/usr/local/go_libs`）。
    *   Goツールは、ソースコード、コンパイル済みパッケージ（`.a`ファイル）、および実行可能ファイルを`GOPATH`内の特定のサブディレクトリ（`src`, `pkg`, `bin`）に配置します。
    *   パッケージの解決（インポートパスから実際のパッケージを見つけるプロセス）は、`GOPATH`の各エントリを左から右へと順に検索することで行われます。最初に見つかったパッケージが使用されるため、`GOPATH`の順序は非常に重要です。

2.  **Goのビルドプロセス**:
    *   `go build`や`go install`コマンドは、Goのソースコードをコンパイルし、リンクして実行可能ファイルやパッケージライブラリを生成します。
    *   このプロセス中、`go`コマンドは内部的に`go tool compile`（Goコンパイラ）と`go tool link`（Goリンカ）を呼び出します。
    *   **コンパイラ (`go tool compile`)**: Goソースファイルをオブジェクトファイルにコンパイルします。他のパッケージをインポートしている場合、そのパッケージのコンパイル済み情報（`.a`ファイル内のエクスポートデータ）を参照する必要があります。この参照パスは`-I`オプションで指定されます。
    *   **リンカ (`go tool link`)**: オブジェクトファイルと必要なライブラリ（コンパイル済みパッケージの`.a`ファイルなど）を結合して、最終的な実行可能ファイルを生成します。ライブラリの検索パスは`-L`オプションで指定されます。

3.  **パッケージのシャドウイング (Shadowing)**:
    *   `GOPATH`の異なるエントリに同じインポートパスを持つパッケージが存在する場合、`GOPATH`の順序に従って、最初に見つかったパッケージが「シャドウ」され、それ以降のパスにある同じ名前のパッケージは無視されます。
    *   例えば、`GOPATH=p1:p2`で`p1/src/foo`と`p2/src/foo`が存在する場合、`p1/src/foo`が使用され、`p2/src/foo`はシャドウされます。

このコミットの核心は、`go`コマンドが`GOPATH`のセマンティクス（順序）を正しくコンパイラとリンカに伝達できていなかった点にあります。

## 技術的詳細

このコミットの技術的な解決策は、`go`コマンドがコンパイラおよびリンカに渡す`-I`および`-L`オプションのリストを構築する際に、`GOPATH`の順序を明示的に尊重するように変更することです。

変更は主に`src/cmd/go/build.go`ファイル内の`(*builder).includeArgs`メソッドに集中しています。このメソッドは、コンパイラやリンカに渡すインクルードパス（`-I`）やライブラリパス（`-L`）の引数を生成する役割を担っています。

以前の実装では、`all`という変数にビルドに必要なすべてのアクション（パッケージ）が含まれており、これらのパッケージの`PkgRoot`（パッケージのルートディレクトリ）が`-I`や`-L`オプションとして追加されていました。しかし、この追加の順序が`GOPATH`の順序と一致しないことが問題でした。

新しい実装では、以下のステップが追加されています。

1.  **`gopath`変数の導入**: `src/cmd/go/build.go`のグローバル変数として`gopath []string`が追加され、`init()`関数内で`buildContext.GOPATH`を`filepath.SplitList`で分割して初期化されます。これにより、`GOPATH`の各エントリが正確な順序で保持されます。
2.  **`need`マップの作成**: `includeArgs`メソッド内で、ビルドに必要なパッケージのうち、`PkgRoot`が`PkgTargetRoot`と同じであるもの（つまり、`GOPATH`のルートディレクトリに直接対応するパッケージ）を`need`マップに収集します。キーは`GOPATH`のルートパス、値は`build.Package`構造体です。
3.  **`GOPATH`順序でのパス追加**: `gopath`変数（元の`GOPATH`の順序を保持）をイテレートし、`need`マップに存在するパッケージについて、その`PkgTargetRoot`を`-I`または`-L`オプションとして`inc`スライスに追加します。この際、`incMap`を使用して重複するパスが追加されないようにします。
4.  **残りのパスの追加**: `GOPATH`に対応するパスが追加された後、残りの必要なパッケージのパスが以前と同様の方法で`inc`スライスに追加されます。

この変更により、`GOPATH`の各エントリに対応するパッケージのパスが、`GOPATH`で定義された順序で`-I`や`-L`オプションとしてコンパイラやリンカに渡されることが保証されます。これにより、パッケージのシャドウイングが`GOPATH`のセマンティクスに従って正しく行われるようになります。

テストファイル`src/cmd/go/go_test.go`には、`TestGoBuildGOPATHOrder`という新しいテストケースが追加されています。このテストは、`GOPATH`が`p1:p2`と設定され、`p1`と`p2`にそれぞれ異なるパッケージが存在する状況をシミュレートします。特に、`p2`に`foo.a`という「悪い」パッケージファイルが存在し、`p1`には正しい`foo`パッケージが存在する場合に、`bar`パッケージが`foo`をインポートする際に、`p1`の`foo`が正しく選択されることを検証します。これは、コンパイラが`-I`オプションを`GOPATH`の順序で受け取ることで、`p1`のパッケージが`p2`のパッケージよりも優先されることを確認するものです。

また、`TestGoBuildGOPATHOrderBroken`というテストも追加されていますが、これは`golang.org/issue/14271`に関連する既知の未解決の問題を示すために`t.Skip`されています。これは、このコミットがすべての`GOPATH`関連のパッケージ解決問題を解決するわけではないことを示唆しています。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更点

1.  **`gopath` グローバル変数の追加**:
    ```go
    var (
    	// ... 既存の変数 ...
    	gopath    []string
    )
    ```
    `gopath`という`string`スライスが追加されました。これは、システムに設定されている`GOPATH`環境変数の各エントリを、その順序を保ったまま格納するために使用されます。

2.  **`init()` 関数での `gopath` の初期化**:
    ```go
    func init() {
    	// ... 既存の初期化処理 ...
    	gopath = filepath.SplitList(buildContext.GOPATH)
    }
    ```
    `init()`関数はパッケージがロードされる際に自動的に実行されます。ここで`filepath.SplitList(buildContext.GOPATH)`が呼び出され、`GOPATH`環境変数の文字列がプラットフォームに応じた区切り文字（Unix系では`:`、Windowsでは`;`）で分割され、`gopath`スライスに格納されます。これにより、`GOPATH`の論理的な順序がプログラム内で利用可能になります。

3.  **`(*builder).includeArgs` メソッドの変更**:
    このメソッドは、コンパイラやリンカに渡す`-I`や`-L`フラグの引数を構築する中心的なロジックです。

    *   **`need` マップの導入**:
        ```go
        	need := map[string]*build.Package{}
        	for _, a1 := range all {
        		if a1.p != nil && a1.pkgdir == a1.p.build.PkgRoot {
        			need[a1.p.build.Root] = a1.p.build
        		}
        	}
        ```
        `need`というマップが新しく作成されます。このマップは、ビルド対象のすべてのアクション（`all`スライス）の中から、`GOPATH`のルートディレクトリに直接対応するパッケージ（`a1.pkgdir == a1.p.build.PkgRoot`という条件で判断）を収集します。マップのキーは`GOPATH`のルートパス（例: `/home/user/go_projects`）、値は`build.Package`構造体です。これにより、どの`GOPATH`エントリにどのパッケージが存在するかが効率的に参照できるようになります。

    *   **`GOPATH` 順序でのパス追加ロジック**:
        ```go
        	for _, root := range gopath {
        		if p := need[root]; p != nil && !incMap[p.PkgRoot] {
        			incMap[p.PkgRoot] = true
        			inc = append(inc, flag, p.PkgTargetRoot)
        		}
        	}
        ```
        ここが最も重要な変更点です。`gopath`スライス（`GOPATH`の元の順序を保持）をループし、各`GOPATH`ルートに対応するパッケージが`need`マップに存在するかを確認します。存在する場合、そのパッケージの`PkgTargetRoot`（コンパイル済みパッケージが置かれるディレクトリ）を`-I`または`-L`オプションとして`inc`スライスに追加します。`incMap`は、同じパスが複数回追加されるのを防ぐためのセットとして機能します。このループにより、`GOPATH`の順序が厳密に守られた形で、関連するパッケージディレクトリがコンパイラ/リンカの検索パスに追加されます。

    *   **残りのパスの追加**:
        ```go
        	// Then add anything that's left.
        	for _, a1 := range all {
        		if a1.p == nil {
        			continue
        		}
        		// ... 既存のロジック ...
        	}
        ```
        `GOPATH`の順序で追加された後、残りのパッケージ（`GOPATH`ルートに直接対応しないものや、`need`マップに含まれなかったもの）が、以前のロジックに従って追加されます。これにより、すべての必要なパスが確実に含まれるようになります。

### `src/cmd/go/go_test.go` の変更点

1.  **`TestGoBuildGOPATHOrder` テストの追加**:
    このテストは、`GOPATH`の順序が正しく尊重されることを検証します。
    *   `GOPATH`を`p1:p2`と設定します。
    *   `p1/src/foo/foo.go`に正しい`foo`パッケージを、`p2/pkg/.../foo.a`に「悪い」`foo`パッケージのアーカイブファイルを配置します。
    *   `p1/src/bar/bar.go`が`foo`をインポートするように設定します。
    *   `go install -x bar`を実行し、ビルドが成功することを確認します。この成功は、`p1`の`foo`が`p2`の`foo`よりも優先され、正しく解決されたことを意味します。

2.  **`TestGoBuildGOPATHOrderBroken` テストの追加**:
    このテストは、`golang.org/issue/14271`で報告された、このコミットでは修正されていない既知の問題を示すために追加されました。
    *   `t.Skip("golang.org/issue/14271")`が呼び出されており、このテストは意図的にスキップされます。これは、このコミットがすべての`GOPATH`関連の問題を解決するわけではないことを開発者が認識していることを示しています。

これらの変更により、Goコマンドは`GOPATH`のセマンティクスをより正確にコンパイラとリンカに伝達できるようになり、パッケージ解決の予測可能性と信頼性が向上しました。

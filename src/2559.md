# [インデックス 2559] ファイルの概要

このコミットは、GoランタイムにおけるC言語からの呼び出しを意図しない関数群の宣言を削除し、一部関数の命名規則を変更することで、C言語とのリンケージに関する問題を解消することを目的としています。具体的には、入力パラメータを通じて値を返すGoランタイム関数が、標準的なC言語の呼び出し規約と互換性がないため、C言語から直接呼び出されることを防ぐための変更です。

## 元コミット内容

C言語から呼び出すことができない関数（入力パラメータで値を返すため）の宣言を削除。

## 変更の背景

Go言語の初期段階において、ランタイムはC言語で書かれた部分とGo言語で書かれた部分が密接に連携していました。このコミットが行われた時期は、Goランタイムがまだ発展途上にあり、C言語との相互運用性やリンケージの規約が固まりつつある段階でした。

Goランタイム内部には、パフォーマンス最適化や特定のメモリ管理戦略のために、関数の戻り値を通常の`return`ステートメントではなく、引数として渡されたポインタ（入力パラメータ）に書き込む形で返す関数が存在していました。このような関数は、Go言語のコンパイラやリンカが生成するコードからは正しく呼び出せますが、標準的なC言語の呼び出し規約（Calling Convention）に従うCコンパイラからは正しく呼び出すことができません。

具体的には、C言語の関数呼び出し規約では、戻り値は通常、レジスタやスタックを通じて返されます。しかし、Goランタイムの特定の関数が「入力パラメータで値を返す」設計になっている場合、C言語のコンパイラはそのような挙動を期待せず、結果として不正なメモリアクセスや未定義の動作を引き起こす可能性がありました。

このコミットの目的は、このようなC言語からの誤った呼び出しを防ぐために、`src/pkg/runtime/runtime.h`内でこれらの関数のC言語向け宣言を削除することでした。これにより、C言語のコードがこれらの関数を誤ってリンクしようとするのを防ぎ、ランタイムの安定性と整合性を保つことが意図されています。また、`sys_mal`から`sys·mal`への変更は、Goランタイム内部でのみ使用される関数であることを明示し、C言語のリンカがシンボルを解決するのをさらに困難にするための命名規則の調整と考えられます。

## 前提知識の解説

### 1. 呼び出し規約 (Calling Convention)

関数が呼び出される際に、引数がどのように渡され、戻り値がどのように返され、レジスタがどのように保存・復元されるかといった、低レベルな取り決めを「呼び出し規約」と呼びます。CPUアーキテクチャやコンパイラ、オペレーティングシステムによって様々な規約が存在します。

*   **C言語の標準的な呼び出し規約**: 一般的に、引数はスタックにプッシュされるか、特定のレジスタに格納されます。戻り値は通常、特定のレジスタ（例: x86のEAX/RAX）に格納されて返されます。構造体などの大きな戻り値の場合、呼び出し元が確保したメモリ領域へのポインタを隠し引数として渡し、そこに書き込む方式が取られることもありますが、これはコンパイラが自動的に処理します。
*   **Go言語の呼び出し規約**: Go言語は独自の呼び出し規約を持っています。特にランタイム内部では、C言語の規約とは異なる最適化が施されることがあります。例えば、複数の戻り値を効率的に扱うために、戻り値をスタック上の特定の領域や、引数として渡されたポインタに書き込むことがあります。

### 2. リンケージ (Linkage)

コンパイルされたオブジェクトファイルやライブラリ内のシンボル（関数名や変数名）が、プログラム全体でどのように解決され、結合されるかを指します。

*   **外部リンケージ**: 異なるコンパイル単位（ソースファイル）間でシンボルが共有される場合。C言語の関数は通常、外部リンケージを持ちます。
*   **内部リンケージ**: シンボルがそのコンパイル単位内でのみ有効な場合。
*   **GoランタイムとCリンケージ**: Goランタイムは、一部の低レベルな処理のためにC言語で書かれたコード（またはアセンブリ言語）を含んでいます。これらのCコードとGoコードの間で関数を呼び出す際には、互換性のある呼び出し規約とリンケージが必要です。

### 3. `sys_` と `sys·` 命名規則

Goランタイムの初期のコードベースでは、C言語から直接呼び出されることを意図した関数には`sys_`プレフィックスが付けられていました。しかし、Goランタイム内部でのみ使用され、C言語のリンカから隠蔽したい関数には、`sys·`（`sys`と中点）のような特殊なシンボル名が使用されることがあります。この中点（`·`）は、Goコンパイラが内部的に使用するシンボル名の一部であり、C言語のリンカは通常、このようなシンボル名を認識しないため、外部からのリンケージを防ぐ効果があります。

### 4. `__GNUC__` プリプロセッサマクロ

C/C++コンパイラであるGCC (GNU Compiler Collection) が使用されている場合に定義されるマクロです。このマクロの有無によって、コンパイラ固有の機能や構文を使用するかどうかを切り替えることができます。このコミットでは、`#ifndef __GNUC__`ブロック内でシンボル名のマッピングを行っており、GCC以外のコンパイラ（またはGoコンパイラが生成するCコード）に対してのみ、`sys_`プレフィックスを`sys·`プレフィックスにマッピングする意図があったことが伺えます。これは、Goコンパイラが生成するCコードが、Goランタイムの内部シンボルを正しく参照できるようにするための措置と考えられます。

## 技術的詳細

このコミットの核心は、Goランタイムの内部関数がC言語の呼び出し規約と互換性がないために発生する問題を解決することです。

1.  **問題の特定**: Goランタイムには、`sys_catstring`, `sys_cmpstring`, `sys_slicestring`, `sys_indexstring`, `sys_intstring`, `sys_mal`といった関数が存在しました。これらの関数は、Go言語の内部的な文字列操作やメモリ割り当てに関連するもので、効率化のために戻り値を引数（ポインタ）経由で返す設計になっていました。
2.  **C言語との非互換性**: 標準的なC言語のコンパイラは、`void`を戻り値の型として宣言された関数が、実際には引数を通じて主要な値を返すことを想定していません。もしC言語のコードがこれらの関数を`void`関数として呼び出そうとすると、Cコンパイラは戻り値を受け取るためのレジスタやスタック領域を適切に設定せず、結果としてGoランタイムが引数に書き込んだ値がC側で正しく取得できないか、あるいはメモリ破壊を引き起こす可能性がありました。
3.  **解決策1: 宣言の削除**: `src/pkg/runtime/runtime.h`から、これらの問題のある関数の`#define`によるシンボルマッピングと、`void`型の関数宣言を削除しました。これにより、C言語のコンパイラやリンカがこれらの関数を「存在しない」ものとして扱い、誤ってリンクしようとする試みを防ぎます。
4.  **解決策2: 命名規則の変更 (`sys_mal` -> `sys·mal`)**: `src/pkg/runtime/mem.c`内の`sys_mal`関数が`sys·mal`にリネームされました。この`·`（中点）は、Goコンパイラが内部シンボルを生成する際に使用する特殊文字であり、C言語のリンカは通常、この文字を含むシンボル名を解決できません。これにより、この関数がGoランタイム内部でのみ使用されることをさらに強く示唆し、C言語からの直接的な呼び出しを物理的に不可能にします。

この変更は、Goランタイムの内部実装とC言語の外部インターフェースとの間に明確な境界線を引くことで、システムの堅牢性を高めることに貢献しています。Goランタイムの関数は、Go言語のコンパイラが生成するコードからのみ、その独自の呼び出し規約に従って呼び出されるべきであるという原則を強化しています。

## コアとなるコードの解説

### `src/pkg/runtime/mem.c` の変更

*   `sys_mal(uint32 n, uint8 *ret)` 関数が `sys·mal(uint32 n, uint8 *ret)` にリネームされました。
*   この関数は、`mal(n)`（メモリ割り当て関数）の結果を `ret` ポインタに書き込んでいます。これは、Goランタイムが内部的にメモリを割り当てる際に使用する関数であり、戻り値を引数経由で返す典型的な例です。
*   `sys·`という命名は、この関数がGoランタイムの内部シンボルであり、C言語のリンカからは解決されないことを明確に示しています。これにより、C言語のコードが誤ってこの関数を呼び出すことを防ぎます。

### `src/pkg/runtime/runtime.h` の変更

このヘッダーファイルは、Goランタイムの内部関数やデータ構造の宣言を含んでおり、Goコンパイラが生成するCコード（またはアセンブリコード）がこれらのシンボルを参照するために使用されます。

1.  **`#define` ディレクティブの削除**:
    *   `#define sys_catstring sys·catstring`
    *   `#define sys_cmpstring sys·cmpstring`
    *   `#define sys_indexstring sys·indexstring`
    *   `#define sys_intstring sys·intstring`
    *   `#define sys_mal sys·mal`
    *   `#define sys_slicestring sys·slicestring`
    これらの行は、`sys_`プレフィックスを持つ関数名を`sys·`プレフィックスを持つ内部シンボル名にマッピングしていました。`#ifndef __GNUC__`ブロック内にあったことから、GCC以外のコンパイラ環境（またはGoコンパイラが生成するCコード）向けに、Goランタイムの内部シンボルを正しく参照させるためのものでした。これらのマッピングが削除されたのは、そもそもこれらの関数がC言語から呼び出されるべきではないという判断が下されたためです。

2.  **`void` 関数宣言の削除**:
    *   `void sys_catstring(String, String, String);`
    *   `void sys_cmpstring(String, String, int32);`
    *   `void sys_slicestring(String, int32, int32, String);`
    *   `void sys_indexstring(String, int32, byte);`
    *   `void sys_intstring(int64, String);`
    これらの関数宣言は、C言語のリンカに対してこれらの関数が存在することを知らせるものでした。しかし、これらの関数が入力パラメータを通じて値を返すため、C言語の呼び出し規約と互換性がありませんでした。これらの宣言を削除することで、C言語のコードがこれらの関数をリンクしようとすることを防ぎ、コンパイル時またはリンク時にエラーを発生させることで、誤用を未然に防ぎます。

このコミットは、Goランタイムの内部実装の詳細が外部（C言語）に漏れ出し、誤用される可能性を排除するための重要なステップでした。Go言語のランタイムは、そのパフォーマンスと安全性のため、独自の内部規約と実装の詳細を厳密に管理する必要があるため、このような変更はシステムの整合性を保つ上で不可欠です。

# [インデックス 26872] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるAMD64アーキテクチャ向けのコード生成に関する最適化です。具体的には、レジスタの低位8ビットまたは16ビットへの書き込みが引き起こす「部分レジスタの偽依存性 (partial register false dependency)」を回避するため、可能な限り32ビット操作を生成するように変更されています。これにより、CPUのパイプラインストールを減らし、生成されるコードのパフォーマンスを向上させます。

## 変更の背景

この変更の背景には、x86-64アーキテクチャにおけるCPUのマイクロアーキテクチャ的な最適化と、それに伴う「部分レジスタの偽依存性 (partial register false dependency)」というパフォーマンス問題があります。

現代のCPUは、命令レベル並列性 (Instruction-Level Parallelism, ILP) を高めるために、アウトオブオーダー実行 (Out-of-Order Execution) やレジスタリネーミング (Register Renaming) といった技術を使用しています。しかし、x86アーキテクチャでは、汎用レジスタ（例: `RAX`）が、その一部（例: `EAX` (32ビット), `AX` (16ビット), `AL` (8ビット)）としてアクセスできるという特性があります。

問題は、ある命令がレジスタの低位ビット（例: `AL`）に書き込み、その後に別の命令が同じレジスタのより広範な部分（例: `RAX`）を読み取ろうとすると発生します。CPUは、`AL`への書き込みが`RAX`の残りの部分に影響を与えないことを認識できない場合があり、結果として`RAX`全体が更新されるまで後続の命令の実行を待機させてしまうことがあります。これが「偽依存性」であり、CPUのパイプラインがストールし、パフォーマンスが低下する原因となります。

Goコンパイラは、SSA (Static Single Assignment) 形式の中間表現を用いて最適化を行いますが、最終的な機械語コード生成の段階で、このようなCPUのマイクロアーキテクチャ的特性を考慮する必要があります。このコミットは、Goコンパイラが生成するAMD64アセンブリコードにおいて、この偽依存性を積極的に回避し、より効率的なコードを生成することを目的としています。具体的には、8ビットや16ビットの操作が必要な場合でも、可能であれば32ビットの操作に「昇格」させることで、偽依存性の発生を抑制します。

## 前提知識の解説

### 1. x86-64アーキテクチャのレジスタ構造

x86-64 (AMD64) アーキテクチャでは、64ビットの汎用レジスタ（例: `RAX`, `RBX`, `RCX`, `RDX`など）が存在します。これらのレジスタは、より小さなサイズの部分レジスタとしてアクセスできます。
*   `RAX`: 64ビットレジスタ
*   `EAX`: `RAX`の下位32ビット
*   `AX`: `EAX`の下位16ビット
*   `AH`: `AX`の上位8ビット
*   `AL`: `AX`の下位8ビット

### 2. 部分レジスタの偽依存性 (Partial Register False Dependency)

前述の通り、レジスタの低位ビット（例: `AL`）への書き込みと、そのレジスタのより広範な部分（例: `RAX`）の読み取りが連続して行われると、CPUはデータ依存性がないにもかかわらず、依存性があると誤解してパイプラインをストールさせることがあります。これは、CPUがレジスタリネーミングを行う際に、部分レジスタの書き込みを効率的に処理できない場合に発生します。

例えば、`MOV AL, 0x01` の後に `ADD RAX, RBX` のような命令が続くと、CPUは`AL`への書き込みが`RAX`の他の部分に影響を与えないことをすぐに判断できず、`AL`の書き込みが完了するまで`ADD`命令を待機させることがあります。

### 3. 偽依存性の回避策

コンパイラやアセンブラは、この偽依存性を回避するためにいくつかの戦略を取ります。
*   **ゼロ拡張移動 (Zero-Extend Move, `MOVZX`)**: 小さいサイズの値をレジスタにロードする際に、残りの上位ビットをゼロで埋める命令 (`MOVZX`) を使用します。これにより、レジスタ全体が明確に定義され、偽依存性が解消されます。
*   **32ビット操作への昇格**: 8ビットや16ビットの操作が必要な場合でも、結果が32ビットレジスタに収まるのであれば、32ビット操作 (`MOVL`, `ADDL`など) を使用します。32ビット操作は、x86-64モードではレジスタの上位32ビットを自動的にゼロクリアするため、偽依存性を回避できます。

### 4. GoコンパイラのSSAバックエンド

Goコンパイラは、Go言語のソースコードを中間表現に変換し、様々な最適化を適用します。その中でも重要なのが、SSA (Static Single Assignment) 形式のバックエンドです。SSAは、各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。SSAバックエンドは、プラットフォーム非依存の最適化を行った後、各アーキテクチャ（AMD64など）固有のコード生成フェーズに入ります。このフェーズで、SSA値が具体的な機械語命令に変換され、レジスタ割り当てが行われます。このコミットは、このAMD64固有のコード生成フェーズにおける最適化に焦点を当てています。

## 技術的詳細

このコミットの主要な目的は、AMD64アーキテクチャにおいて、8ビット (`B`) および16ビット (`W`) のレジスタ操作が引き起こす部分レジスタの偽依存性を回避し、パフォーマンスを向上させることです。これを実現するために、GoコンパイラのSSAバックエンドは、これらの操作を可能な限り32ビット (`L`) 操作に「昇格」させます。

具体的には、以下のGoコンパイラの内部ファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/ssa.go`**:
    *   このファイルは、SSA中間表現から最終的なアセンブリコードを生成する部分 (`genValue` 関数) を含んでいます。
    *   `ALEAW` (16ビットのアドレス計算) や `AINCW`/`ADECW` (16ビットのインクリメント/デクリメント) といった16ビット操作が、対応する32ビット操作 (`ALEAL`, `AINCL`/`ADECL`) に変更されています。
    *   `ANEGQ` (64ビットの符号反転) の代わりに、`ANEGL` (32ビットの符号反転) を使用するケースが追加されています。これは、`SUBQ` (64ビット減算) の結果が32ビットに収まる場合に、部分レジスタ書き込みを避けるためと考えられます。
    *   `AORQ` (64ビット論理和) や `AANDQ` (64ビット論理積) の代わりに、`AORL` (32ビット論理和) や `AANDL` (32ビット論理積) を使用するよう変更されています。コメントには「ORL avoids partial register write and is smaller than ORQ, used by old compiler」とあり、偽依存性の回避とコードサイズの削減の両方を意図していることが示唆されています。
    *   `loadByType` および `moveByType` 関数において、1バイト (`AMOVB`) や2バイト (`AMOVW`) のロード/ムーブ操作が、`AMOVBLZX` (バイトをゼロ拡張してロード) や `AMOVWLZX` (ワードをゼロ拡張してロード)、または `AMOVL` (32ビットムーブ) に変更されています。これにより、レジスタ全体がゼロクリアされ、偽依存性が回避されます。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64Ops.go`**:
    *   このファイルは、AMD64アーキテクチャ向けのSSA操作とそれに対応するアセンブリ命令のマッピングを定義しています。
    *   `ADDW`, `ADDB`, `SUBW`, `SUBB`, `ANDW`, `ANDB`, `ORW`, `ORB`, `XORW`, `XORB`, `SHLW`, `SHLB`, `NEGW`, `NEGB`, `NOTW`, `NOTB` といった8ビット/16ビット操作の多くが、対応する32ビットのアセンブリ命令 (`ADDL`, `SUBL`, `ANDL`, `ORL`, `XORL`, `SHLL`, `NEGL`, `NOTL`) を生成するように変更されています。
    *   ロード操作 (`MOVBload`, `MOVWload`, `MOVBloadidx1`, `MOVWloadidx2`) も、`MOVBLZX` や `MOVWLZX` といったゼロ拡張ロード命令を生成するように変更されています。

3.  **`src/cmd/compile/internal/ssa/opGen.go`**:
    *   このファイルは、SSA操作の定義と、それらが生成するアセンブリ命令のマッピングをさらに詳細に定義しています。
    *   `AMD64Ops.go` と同様に、`ADDW`, `ADDB`, `SUBW`, `SUBB` などの8ビット/16ビット操作が、対応する32ビットのアセンブリ命令を指すように変更されています。

これらの変更により、Goコンパイラは、Goプログラムが生成するアセンブリコードにおいて、部分レジスタの偽依存性を引き起こす可能性のある命令を減らし、より効率的なCPUパイプライン利用を促進します。特に、32ビット操作はx86-64モードでレジスタの上位32ビットを自動的にゼロクリアするため、偽依存性の問題が解消されます。

## コアとなるコードの解説

これらの変更は、GoコンパイラのSSAバックエンドがAMD64アセンブリコードを生成する際の戦略を根本的に変更するものです。

1.  **`src/cmd/compile/internal/gc/ssa.go`**:
    *   `genValue` 関数は、SSA値に対応するアセンブリ命令を生成する中心的なロジックです。ここで、`ssa.OpAMD64ADDW` (16ビット加算) のようなSSA操作が、直接 `x86.ALEAW` (16ビットLEA命令) ではなく、`x86.ALEAL` (32ビットLEA命令) を生成するように変更されています。これは、16ビットの操作であっても、結果が32ビットレジスタに収まる場合は32ビット操作を使用することで、部分レジスタの偽依存性を回避する意図があります。
    *   `ANEGQ` から `ANEGL` への条件付き変更も同様に、64ビット操作が不要な場合に32ビット操作を選択し、偽依存性を避けるためのものです。
    *   `AORQ` や `AANDQ` から `AORL` や `AANDL` への変更は、32ビット操作が偽依存性を回避し、かつコードサイズも小さくなるという利点を活用しています。
    *   `loadByType` および `moveByType` 関数における `AMOVBLZX` や `AMOVWLZX` の導入は非常に重要です。これらの命令は、バイトやワードをロードする際に、レジスタの残りの上位ビットをゼロで埋めます。これにより、レジスタ全体が明確な状態になり、後続の命令がそのレジスタ全体を使用しても偽依存性が発生しなくなります。`AMOVL`への変更も、同様に32ビット操作が上位ビットをゼロクリアする特性を利用しています。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go`**:
    *   これらのファイルは、SSA操作とアセンブリ命令の直接的なマッピングを定義しています。多くの8ビット/16ビットの算術・論理・シフト操作 (`ADDW`, `ADDB`, `SUBW`, `SUBB`, `ANDW`, `ANDB`, `ORW`, `ORB`, `XORW`, `XORB`, `SHLW`, `SHLB`, `NEGW`, `NEGB`, `NOTW`, `NOTB`) が、対応する32ビットのアセンブリ命令 (`ADDL`, `SUBL`, `ANDL`, `ORL`, `XORL`, `SHLL`, `NEGL`, `NOTL`) を生成するように変更されています。
    *   これは、GoコンパイラがSSA中間表現から機械語命令を生成する際に、デフォルトでより広範な32ビット操作を選択するポリシーを導入したことを意味します。これにより、Goプログラムの実行時にCPUのパイプラインストールが減少し、全体的なパフォーマンスが向上することが期待されます。

これらの変更は、Goコンパイラが生成するコードのパフォーマンスを、CPUのマイクロアーキテクチャ的特性に合わせて最適化する重要なステップです。

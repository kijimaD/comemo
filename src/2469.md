# [インデックス 2469] ファイルの概要

このコミットは、Goランタイムにおけるスタック管理とコンテキストスイッチのメカニズムに大幅な調整とクリーンアップを導入します。特に、`gobuf`構造体におけるスタックポインタ（SP）とプログラムカウンタ（PC）の整合性を向上させ、`setspgoto`を`gogocall`に置き換えることで、リンクレジスタを持つアーキテクチャでの動作を改善しています。また、不要なシステムコールラッパーの削除も行われています。この変更は主に`amd64`アーキテクチャに焦点を当てており、一時的に`386`アーキテクチャの動作を損なっています。

## 元コミット内容

Goランタイムのスタック拡張に関する調整とクリーンアップ。
主な変更点として、`gobuf`構造体内でスタックポインタ（SP）とプログラムカウンタ（PC）の整合性を保つように修正されました（つまり、そのPCで使われるであろうSPを保持する）。
また、`setspgoto`関数が`gogocall`に置き換えられ、リンクレジスタが存在する環境での動作が改善されることが期待されます。
さらに、使用されていないシステムコールが削除されました。
この変更は`amd64`アーキテクチャのみに適用され、`386`アーキテクチャは一時的に動作しなくなっています。

## 変更の背景

このコミットの背景には、Goランタイムの初期段階におけるスタック管理とコンテキストスイッチの効率性および正確性の向上が挙げられます。特に、以下の課題に対処しています。

1.  **`gobuf`の整合性不足**: 以前の`gobuf`構造体は、コンテキストスイッチに必要なSPとPCを保持していましたが、その情報が常に完全に「整合性のある」状態ではなかった可能性があります。特に、スタックの成長や縮小といった動的な操作の際に、SPとPCのペアが正確な実行状態を反映していないと、デバッグやスタックトレースが困難になる問題がありました。このコミットは、`gobuf`が「そのPCで使われるであろうSP」を保持することで、より正確なコンテキスト表現を目指しています。
2.  **`setspgoto`の限界**: `setspgoto`は、特定のSPにジャンプして関数を呼び出すための低レベルなアセンブリ関数でしたが、リンクレジスタを使用する一部のアーキテクチャ（例えばARMなど、当時はGoがサポートしていなかったかもしれませんが、将来的な拡張を見越していた可能性もあります）では、その動作が最適ではなかったり、問題を引き起こす可能性がありました。`gogocall`の導入は、より汎用的で堅牢なコンテキストスイッチ後の関数呼び出しメカニズムを提供することを目的としています。
3.  **システムコールラッパーの整理**: Goランタイムは、OSのシステムコールを直接呼び出すためのラッパー関数を多数持っています。時間の経過とともに、一部のラッパーが不要になったり、より抽象化されたGoの標準ライブラリ関数に置き換えられたりすることがあります。このコミットでは、使用されなくなったシステムコールラッパーを削除することで、ランタイムのコードベースをクリーンアップし、保守性を向上させています。
4.  **`amd64`への最適化と`386`の一時的な非互換性**: Goはクロスプラットフォームを志向していますが、初期の段階では特定のアーキテクチャ（特に`amd64`）に重点を置いて開発が進められることがよくありました。このコミットも`amd64`のスタック管理を改善することに主眼を置いており、その過程で`386`アーキテクチャとの互換性が一時的に失われたことを示しています。これは、大規模なランタイムの変更において、段階的にアーキテクチャ固有の調整を行う一般的な開発プラクティスです。

これらの変更は、Goの並行処理モデルを支えるゴルーチンとスケジューラの基盤を強化し、より安定した効率的なランタイムを実現するための重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とコンピュータサイエンスの基礎知識が必要です。

1.  **ゴルーチン (Goroutine)**: Go言語の軽量な並行処理単位。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。ゴルーチンはGoランタイムによってスケジューリングされます。
2.  **M (Machine) と G (Goroutine) と P (Processor)**: Goスケジューラの主要な要素。
    *   **G (Goroutine)**: 実行されるコード、スタック、およびスケジューリング情報を含むゴルーチンの構造体。
    *   **M (Machine)**: OSのスレッドを表す構造体。MはGを実行し、OSのシステムコールを処理します。
    *   **P (Processor)**: MがGを実行するために必要な論理プロセッサ。PはMとGの間の仲介役となり、Gの実行に必要なリソース（例えば、ローカルな実行キュー）を提供します。
3.  **`gobuf`**: ゴルーチンの実行コンテキスト（スタックポインタ、プログラムカウンタ、現在のゴルーチンへのポインタなど）を保存・復元するための構造体。`setjmp`/`longjmp`のような機能を提供し、ゴルーチンのコンテキストスイッチに使用されます。
4.  **スタック (Stack)**: 関数呼び出しの際にローカル変数、引数、戻りアドレスなどが格納されるメモリ領域。Goのゴルーチンは可変サイズのスタックを持ち、必要に応じて自動的に拡張（`morestack`）および縮小（`lessstack`）されます。
5.  **スタックガード (Stack Guard)**: スタックオーバーフローを検出するためのメカニズム。スタックの末尾近くに配置された特別な値で、関数プロローグでスタックポインタがこの値を下回っていないかチェックされます。下回っていた場合、スタック拡張ルーチン（`morestack`）が呼び出されます。
6.  **コンテキストスイッチ (Context Switch)**: CPUが現在実行中のタスク（この場合はゴルーチン）の実行状態を保存し、別のタスクの実行状態を復元して実行を切り替える操作。Goランタイムでは、`gosave`と`gogo`（または`gogocall`）がこの役割を担います。
7.  **プログラムカウンタ (PC)**: 次に実行される命令のアドレスを指すレジスタ。
8.  **スタックポインタ (SP)**: 現在のスタックフレームの最上位（または最下位、アーキテクチャによる）を指すレジスタ。
9.  **リンクレジスタ (Link Register)**: 一部のCPUアーキテクチャ（例: ARM）において、関数呼び出しの戻りアドレスを格納するために使用されるレジスタ。x86/amd64アーキテクチャでは、戻りアドレスは通常スタックにプッシュされます。`setspgoto`がリンクレジスタの存在下で問題を起こす可能性があったというのは、このようなアーキテクチャ固有の呼び出し規約の違いに起因します。
10. **システムコール (System Call)**: ユーザープログラムがOSのカーネル機能（ファイルI/O、メモリ管理、プロセス管理など）を利用するためのインターフェース。Goランタイムは、OSと直接やり取りするためにシステムコールを使用します。
11. **アセンブリ言語 (Assembly Language)**: CPUが直接実行できる機械語命令を人間が読める形式で記述したもの。Goランタイムの低レベルな部分（コンテキストスイッチ、スタック管理、システムコールラッパーなど）は、パフォーマンスとOSとの直接的なインタラクションのためにアセンブリ言語で実装されています。

## 技術的詳細

このコミットは、Goランタイムの根幹をなすゴルーチンのスタック管理とコンテキストスイッチのメカニズムを、`amd64`アーキテクチャ向けに大幅に改善しています。

### 1. `gobuf`の構造変更とSP/PCの整合性

-   **`Gobuf`構造体の拡張**: `src/pkg/runtime/runtime.h`において、`Gobuf`構造体に`G* g`フィールドが追加されました。これにより、`gobuf`はSPとPCだけでなく、そのコンテキストが属するゴルーチン`G`へのポインタも保持するようになりました。これは、コンテキストスイッチの際に、どのゴルーチンの状態を保存・復元しているのかを明確にし、ランタイム内部でのゴルーチン管理をより堅牢にする上で重要です。
-   **SP/PCの整合性**: コミットメッセージにある「keep coherent SP/PC in gobuf (i.e., SP that would be in use at that PC)」は、`gobuf`に保存されるSPとPCのペアが、そのPCが実行される時点での正確なスタック状態を反映するように調整されたことを意味します。これは、特にスタックの成長・縮小や、関数呼び出し規約の変更があった場合に、デバッガやスタックトレースが正確な情報を取得できるようにするために不可欠です。

### 2. `gogocall`の導入と`setspgoto`の廃止

-   **`setspgoto`の問題点**: 以前の`setspgoto`は、指定されたSPにスタックポインタを設定し、その後指定された関数にジャンプするという単純なアセンブリ関数でした。しかし、これは戻りアドレスをスタックにプッシュするx86/amd64のようなアーキテクチャでは問題ありませんが、戻りアドレスをリンクレジスタに格納するARMのようなアーキテクチャでは、コンテキストスイッチ後に正しい戻りアドレスが復元されない可能性がありました。
-   **`gogocall`の解決策**: `src/pkg/runtime/amd64/asm.s`に新しく導入された`gogocall`は、`gobuf`からSPとPCを復元した後、指定された関数`fn`を呼び出します。この際、`gobuf`に保存されていたPCはスタックにプッシュされ、`fn`からの戻りアドレスとして機能します。これにより、`fn`が実行を終えると、`gobuf`に保存されていた元のコンテキストに戻るという、より柔軟でアーキテクチャに依存しないコンテキストスイッチ後の関数呼び出しが可能になります。これは、特に`newproc`（新しいゴルーチンの開始）や`morestack`（スタック拡張）の処理において、特定の関数を呼び出した後に元のスケジューリングコンテキストに戻る必要がある場合に非常に有効です。

### 3. スタック成長/縮小メカニズムの刷新

-   **`Stktop`構造体の変更**: `src/pkg/runtime/runtime.h`の`Stktop`構造体が大幅に変更されました。以前は`oldbase`, `oldsp`, `magic`, `oldguard`といったフィールドを持っていましたが、新しい`Stktop`は`stackguard`, `stackbase`, `Gobuf gobuf`, `args`を持つようになりました。これは、スタックの成長・縮小時に、以前のスタックブロックのコンテキスト（SP, PC, G）を`gobuf`として直接保存することで、より明確で一貫性のある状態管理を可能にします。
-   **`sys·morestack`と`sys·lessstack`のC関数からの分離**: 以前は`sys·morestack`と`lessstack`というC関数が存在しましたが、このコミットではこれらがアセンブリルーチンとして直接実装され、Cコードからは`newstack`と`oldstack`が呼び出される形になりました。
    -   **`sys·morestack` (アセンブリ)**: 関数プロローグでスタックガードをチェックし、スタックが足りない場合に呼び出されます。呼び出し元のPC/SPと現在のゴルーチン`g`を`m->morebuf`に保存し、`m->morepc`に呼び出し元のPCを保存した後、`m->g0`（スケジューリングスタック）に切り替えて`newstack`C関数を呼び出します。
    -   **`newstack` (C関数)**: 新しいスタックブロックを割り当て、`Stktop`構造体を初期化し、古いスタックの情報を新しい`Stktop`に保存します。その後、`gogocall`を使用して、`m->morepc`（スタック拡張を要求した元のPC）を呼び出します。これにより、スタック拡張処理が完了した後、元の実行フローにスムーズに戻ることができます。
    -   **`sys·lessstack` (アセンブリ)**: スタックを縮小する際に呼び出されます。`m->cret`にリターン値を保存し、`m->g0`に切り替えて`oldstack`C関数を呼び出します。
    -   **`oldstack` (C関数)**: 現在のスタックブロックを解放し、`Stktop`に保存されていた古いスタックブロックの情報（`gobuf`）を復元して、`gogo`で元のコンテキストに戻ります。
-   **`amd64/asm.h`の導入**: `amd64`固有のアセンブリ定数（レジスタ割り当てや構造体オフセット）を定義する`amd64/asm.h`が導入されました。これにより、アセンブリコードとCコード間のインターフェースが明確になり、コードの可読性と保守性が向上します。特に、`g`レジスタ（R15）と`m`レジスタ（R14）の定義、および`m`, `gobuf`, `g`構造体内のフィールドオフセットが定義され、アセンブリコードからこれらの構造体にアクセスする際の信頼性が高まりました。

### 4. 不要なシステムコールラッパーの削除

-   `src/pkg/runtime/darwin/amd64/sys.s`と`src/pkg/runtime/linux/amd64/sys.s`から、`sys·open`, `sys·close`, `sys·fstat`, `sys·read`などのシステムコールラッパーが削除されました。これは、これらのシステムコールがGoランタイムのより高レベルなI/O抽象化によって直接使用されなくなったか、あるいはGoの標準ライブラリがこれらのシステムコールを直接呼び出すようになったためと考えられます。これにより、ランタイムのフットプリントが削減され、コードベースが簡素化されます。また、`sys·write`が単に`write`にリネームされている箇所もあり、これは命名規則の統一または内部的な使用方法の変更を示唆しています。

これらの変更は、Goランタイムのスタック管理とコンテキストスイッチのメカニズムをより堅牢で効率的、かつ将来のアーキテクチャ拡張に対応しやすいものにするための重要な基盤を築きました。

## コアとなるコードの解説

### `src/pkg/runtime/runtime.h` の `Gobuf` 構造体

```c
struct	Gobuf
{
	// Offsets of fields in this struct are known to assembly.
	// Any changes made here must be reflected in */asm.h.
	// The debuggers also know the layout of this struct.
	byte*	sp; // スタックポインタ
	byte*	pc; // プログラムカウンタ
	G*	g;  // このコンテキストが属するゴルーチンGへのポインタ
};
```
-   以前は`SP`と`PC`という大文字のフィールド名でしたが、小文字の`sp`と`pc`に変更されました。これはGoのコーディングスタイルに合わせたものかもしれません。
-   最も重要な変更は、`G* g`フィールドの追加です。これにより、`gobuf`は単なるSP/PCのペアではなく、どのゴルーチンのコンテキストであるかを明示的に示すようになりました。これは、コンテキストスイッチの際に、現在のゴルーチン`g`レジスタ（R15）の値を保存・復元するために使用されます。デバッガやアセンブリコードがこの構造体のオフセットを知っていることがコメントで明記されており、その重要性を示しています。

### `src/pkg/runtime/amd64/asm.h` (新規)

```c
// Assembly constants

#define	g	R15 // ゴルーチンGへのポインタを保持するレジスタ
#define	m	R14 // マシンMへのポインタを保持するレジスタ

// offsets in m
#define	m_g0		0
#define	m_morepc	8
#define	m_morebuf	16
// ... (他のmのオフセット)

// offsets in gobuf
#define	gobuf_sp	0
#define	gobuf_pc	8
#define	gobuf_g		16

// offsets in g
#define	g_stackguard	0
#define	g_stackbase	8
// ... (他のgのオフセット)
```
-   このファイルは、アセンブリコードがGoランタイムのC構造体（`G`, `M`, `Gobuf`など）のフィールドにアクセスするためのオフセットとレジスタ割り当てを定義しています。
-   `g`をR15、`m`をR14に割り当てることで、アセンブリコード内で現在のゴルーチンとマシン（OSスレッド）の情報を高速に参照できるようになります。
-   `gobuf_sp`, `gobuf_pc`, `gobuf_g`などの定義は、`Gobuf`構造体のフィールドがメモリ上でどのように配置されているかを示しており、アセンブリコードがこれらのフィールドに直接アクセスするために使用されます。例えば、`MOVQ gobuf_sp(AX), SP`は、`AX`レジスタが指す`Gobuf`構造体の`sp`フィールドの値をスタックポインタ`SP`にロードすることを意味します。

### `src/pkg/runtime/amd64/asm.s` の `gogocall`

```assembly
// void gogocall(Gobuf*, void (*fn)(void))
// restore state from Gobuf but then call fn.
// (call fn, returning to state in Gobuf)
TEXT gogocall(SB), 7, $0
	MOVQ	16(SP), AX		// fn (第2引数)
	MOVQ	8(SP), BX		// gobuf (第1引数)
	MOVQ	gobuf_g(BX), g  // gobufからgレジスタを復元
	MOVQ	0(g), CX		// make sure g != nil (gがnilでないことを確認)
	MOVQ	gobuf_sp(BX), SP	// gobufからSPを復元
	MOVQ	gobuf_pc(BX), BX
	PUSHQ	BX              // gobufに保存されていたPCをスタックにプッシュ
	JMP	AX              // fnを呼び出す
	POPQ	BX	// not reached (fnから戻ると、PUSHQしたBX（元のPC）にジャンプする)
```
-   `gogocall`は、`gobuf`に保存されたコンテキスト（SP, PC, G）を復元した後、引数として渡された関数`fn`を呼び出すための新しいプリミティブです。
-   重要なのは、`gobuf_pc(BX)`（元のPC）をスタックに`PUSHQ`してから`JMP AX`（`fn`を呼び出す）している点です。これにより、`fn`が`RET`命令で戻ると、スタックから`gobuf`に保存されていた元のPCがポップされ、そのアドレスに実行が戻ります。これは、`fn`が完了した後に、`gobuf`が表す元のコンテキストに実行フローを戻すための巧妙な方法です。

### `src/pkg/runtime/proc.c` の `newstack` 関数 (簡略化)

```c
void
newstack(void)
{
	// ... (スタックフレームと引数のサイズ計算)

	stk = stackalloc(frame); // 新しいスタックを割り当てる

	g1 = m->curg;
	top = (Stktop*)(stk+frame-sizeof(*top)); // 新しいStktopをスタックの最上位に配置
	top->stackbase = g1->stackbase; // 古いスタックベースを保存
	top->stackguard = g1->stackguard; // 古いスタックガードを保存
	top->gobuf = m->morebuf; // m->morebufに保存されていたコンテキストをStktopにコピー
	top->args = args; // 引数サイズを保存

	g1->stackbase = (byte*)top; // 現在のゴルーチンのスタックベースを新しいStktopに設定
	g1->stackguard = stk + StackGuard; // 現在のゴルーチンのスタックガードを新しいスタックに設定

	sp = (byte*)top;
	if(args > 0) {
		sp -= args;
		mcpy(sp, top->gobuf.sp, args); // 引数を新しいスタックにコピー
	}

	// Continue as if lessstack had just called m->morepc
	// (the PC that decided to grow the stack).
	label.sp = sp;
	label.pc = (byte*)sys·lessstack; // 戻り先をsys·lessstackに設定
	label.g = m->curg;
	gogocall(&label, m->morepc); // m->morepcを呼び出し、完了したらsys·lessstackに戻る
	// ... (never return)
}
```
-   `newstack`は、スタックオーバーフローが発生した際に新しいスタックを割り当て、古いスタックの情報を`Stktop`構造体に保存し、現在のゴルーチンのスタックポインタとスタックガードを新しいスタックに更新します。
-   重要なのは最後の`gogocall(&label, m->morepc);`です。ここで、`m->morepc`（スタック拡張を要求した元の関数呼び出しのPC）を呼び出します。`gogocall`の特性により、`m->morepc`からの戻り先は`label.pc`に設定された`sys·lessstack`になります。これにより、スタック拡張処理が完了した後、元の関数が新しいスタックで実行を継続し、その関数が終了してスタックを縮小する際に`sys·lessstack`が呼び出されるという、一連のスタック管理フローが確立されます。

### `src/pkg/runtime/proc.c` の `oldstack` 関数 (簡略化)

```c
void
oldstack(void)
{
	// ... (引数サイズの計算)

	g1 = m->curg;
	top = (Stktop*)g1->stackbase; // 現在のStktopを取得
	old = *top; // Stktopの情報をコピー

	// ... (引数のコピー)

	stackfree((byte*)g1->stackguard - StackGuard); // 古いスタックを解放

	g1->stackbase = old.stackbase; // ゴルーチンのスタックベースを古いものに戻す
	g1->stackguard = old.stackguard; // ゴルーチンのスタックガードを古いものに戻す

	gogo(&old.gobuf, m->cret); // 古いgobufコンテキストに復元し、m->cretを戻り値として渡す
}
```
-   `oldstack`は、スタック縮小時に呼び出されます。現在の`Stktop`から古いスタックの情報を取得し、現在のゴルーチンのスタックベースとスタックガードを古いスタックのものに戻します。
-   最後に`gogo(&old.gobuf, m->cret);`を呼び出すことで、`Stktop`に保存されていた古いスタックブロックのコンテキスト（SP, PC, G）に実行を戻します。`m->cret`は、`sys·lessstack`が呼び出された際に保存されたリターン値であり、`gogo`の第2引数として渡されます。

これらの変更により、Goランタイムはより洗練されたスタック管理とコンテキストスイッチのメカニズムを獲得し、ゴルーチンの動的なスタックサイズ調整をより効率的かつ正確に行えるようになりました。

## 変更の背景

Goコンパイラは、プログラムの実行効率を向上させるために様々な最適化を行います。その一つが「定数畳み込み（constant folding）」です。これは、コンパイル時に値が確定している定数式を、その計算結果で置き換える最適化手法です。例えば、`2 + 3`という式があれば、コンパイラはこれを`5`に置き換えます。

このコミットが行われた背景には、GoコンパイラのSSAバックエンドにおける定数シフト演算の最適化に二つの問題があったことが挙げられます。

1.  **誤った結果型**: 特定の条件下（特に、シフト量がデータ型のビット幅以上である場合）で、シフト演算の結果が常にゼロになるべきところで、そのゼロが誤ったデータ型（例えば、32ビット整数に対するシフト結果が64ビット整数として扱われる）で表現されていました。これは、生成されるアセンブリコードの非効率性や、場合によっては予期せぬ動作を引き起こす可能性がありました。
2.  **最適化の不足**: 定数ゼロをシフトするような自明なケースにおいて、コンパイラがその結果が常にゼロであることを認識し、より早期に最適化されたコードに置き換えるためのルールが不足していました。

これらの問題を解決することで、コンパイラはより正確で効率的なコードを生成できるようになり、結果としてGoプログラムのパフォーマンス向上に貢献します。

## 前提知識の解説

### 1. GoコンパイラとSSA

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要なのが、**SSA（Static Single Assignment）**形式への変換と、それに対する最適化です。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、AST（Abstract Syntax Tree）からSSA形式に変換し、様々なSSAパス（最適化フェーズ）を適用します。
*   **SSAバックエンド**: Go 1.7（このコミットが作成された時期と近い）で導入された新しいコンパイラバックエンドで、従来のASTベースの最適化に比べて、より強力で広範な最適化を可能にしました。

### 2. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時に評価可能な定数式を、その結果の値に置き換える最適化手法です。
例:
*   `a = 1 + 2` → `a = 3`
*   `b = 10 * 5` → `b = 50`

これは、実行時の計算コストを削減し、プログラムのパフォーマンスを向上させます。シフト演算においても、オペランドが定数の場合、コンパイル時に結果を計算して置き換えることができます。

### 3. シフト演算

シフト演算は、ビット列を左右に移動させる操作です。
*   **左シフト (Lsh)**: ビットを左に移動させます。通常、左に1ビットシフトするごとに値は2倍になります。最上位ビットがあふれると情報が失われます。
*   **右シフト (Rsh)**: ビットを右に移動させます。
    *   **算術右シフト**: 符号付き整数に適用され、最上位ビット（符号ビット）を保持しながら右にシフトします。負の数の場合、左から1が挿入されます。
    *   **論理右シフト (RshU)**: 符号なし整数に適用され、左から常に0が挿入されます。

Go言語では、シフト演算子は`<<`（左シフト）と`>>`（右シフト）です。シフト量は符号なし整数型でなければなりません。

### 4. `generic.rules`と`rewritegeneric.go`

GoコンパイラのSSAバックエンドでは、最適化ルールが`generic.rules`のようなファイルに記述され、それに基づいて`rewritegeneric.go`のようなGoソースコードが自動生成されます。

*   `generic.rules`: SSAノードのパターンマッチングと書き換えルールを定義するファイルです。例えば、「ある特定のパターンのSSA操作を見つけたら、それを別のより効率的なSSA操作に置き換える」といったルールが記述されます。
*   `rewritegeneric.go`: `generic.rules`から生成されたGoコードで、実際にSSAグラフを走査し、定義されたルールに基づいてノードを書き換えるロジックを含んでいます。

### 1. シフト量がデータ型のビット幅以上の場合の型修正

Go言語の仕様では、シフト量がオペランドの型が持つビット数以上の場合、結果はゼロになります。例えば、`int8`型の変数を8ビット以上左シフトまたは右シフトした場合、結果は`0`です。

このコミット以前は、このような「オーバーシフト」の場合に、結果の定数ゼロが常に`Const64 [0]`（64ビット整数定数ゼロ）として扱われていました。しかし、元のオペランドが`int8`や`int16`、`int32`であった場合、結果もそれぞれの型の定数ゼロ（`Const8 [0]`、`Const16 [0]`、`Const32 [0]`）であるべきです。

**修正前 (`generic.rules`の抜粋):**
```
(Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
(Rsh32Ux64 _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
(Lsh16x64  _ (Const64 [c])) && uint64(c) >= 16 -> (Const64 [0])
(Rsh16Ux64 _ (Const64 [c])) && uint64(c) >= 16 -> (Const64 [0])
(Lsh8x64   _ (Const64 [c])) && uint64(c) >= 8  -> (Const64 [0])
(Rsh8Ux64  _ (Const64 [c])) && uint64(c) >= 8  -> (Const64 [0])
```
上記では、32ビット、16ビット、8ビットのシフト演算でオーバーシフトが発生した場合でも、結果が`Const64 [0]`とされていました。

**修正後 (`generic.rules`の抜粋):**
```
(Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
(Rsh32Ux64 _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
(Lsh16x64  _ (Const64 [c])) && uint64(c) >= 16 -> (Const16 [0])
(Rsh16Ux64 _ (Const64 [c])) && uint64(c) >= 16 -> (Const16 [0])
(Lsh8x64   _ (Const64 [c])) && uint64(c) >= 8  -> (Const8 [0])
(Rsh8Ux64  _ (Const64 [c])) && uint64(c) >= 8  -> (Const8 [0])
```
この修正により、結果の定数ゼロが適切なビット幅の型（`Const32 [0]`、`Const16 [0]`、`Const8 [0]`）で表現されるようになりました。これにより、コンパイラはより正確な型情報に基づいて後続の最適化やコード生成を行うことができます。

### 2. 定数ゼロのシフト演算の追加最適化

このコミットでは、定数ゼロをシフトする演算が常にゼロになるという自明なケースに対する最適化ルールも追加されています。

**追加されたルール (`generic.rules`の抜粋):**
```
(Lsh64x64  (Const64 [0]) _) -> (Const64 [0])
(Rsh64x64  (Const64 [0]) _) -> (Const64 [0])
(Rsh64Ux64 (Const64 [0]) _) -> (Const64 [0])
(Lsh32x64  (Const32 [0]) _) -> (Const32 [0])
(Rsh32x64  (Const32 [0]) _) -> (Const32 [0])
(Rsh32Ux64 (Const32 [0]) _) -> (Const32 [0])
(Lsh16x64  (Const16 [0]) _) -> (Const16 [0])
(Rsh16x64  (Const16 [0]) _) -> (Const16 [0])
(Rsh16Ux64 (Const16 [0]) _) -> (Const16 [0])
(Lsh8x64   (Const8  [0]) _) -> (Const8  [0])
(Rsh8x64   (Const8  [0]) _) -> (Const8  [0])
(Rsh8Ux64  (Const8  [0]) _) -> (Const8  [0])
```
これらのルールは、例えば`0 << x`や`0 >> x`のような式があった場合に、コンパイル時に即座に`0`に畳み込むことを可能にします。これにより、実行時に不要なシフト命令が生成されるのを防ぎ、コードサイズと実行速度の両面で改善が見込まれます。

### 3. `rewritegeneric.go`における実装

`generic.rules`で定義されたこれらのルールは、`rewritegeneric.go`内の対応する`rewriteValuegeneric_OpLshXXx64`や`rewriteValuegeneric_OpRshXXx64`関数にGoコードとして実装されます。

例えば、`Lsh16x64`（16ビット値の左シフト）の場合、以下のようなコードが追加・修正されています。

**`rewriteValuegeneric_OpLsh16x64`関数の変更点:**
*   `// match: (Lsh16x64 (Const16 [0]) _)` のパターンが追加され、左オペランドが`Const16 [0]`であれば、結果を`Const16 [0]`に設定するロジックが追加されました。
*   `// match: (Lsh16x64 _ (Const64 [c]))` かつ `uint64(c) >= 16` のパターンにおいて、結果の型を`OpConst64`から`OpConst16`に修正し、`v.AuxInt = 0`を設定するように変更されました。

これらの変更は、他のビット幅（8, 32, 64）の左シフト（Lsh）および右シフト（Rsh, RshU）操作に対しても同様に適用されています。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules`

このファイルは、GoコンパイラのSSA最適化パスで使用される書き換えルールを定義しています。各ルールは、特定のSSAオペレーションのパターンを記述し、それがマッチした場合にどのように書き換えるかを指定します。

**追加されたルール（例: `Lsh64x64`）:**
```
(Lsh64x64  (Const64 [0]) _) -> (Const64 [0])
```
これは、「64ビットの左シフト操作（`Lsh64x64`）があり、その左オペランドが64ビット定数ゼロ（`Const64 [0]`）である場合、その操作全体を64ビット定数ゼロ（`Const64 [0]`）に書き換える」というルールを意味します。`_`は任意のオペランドにマッチします。

**修正されたルール（例: `Lsh32x64`）:**
```diff
- (Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
+ (Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
```
これは、「32ビットの左シフト操作（`Lsh32x64`）があり、その右オペランドが64ビット定数`c`であり、かつ`c`が32以上である場合（つまりオーバーシフト）、その操作全体を32ビット定数ゼロ（`Const32 [0]`）に書き換える」というルールに修正されたことを示します。修正前は`Const64 [0]`でした。

### `src/cmd/compile/internal/ssa/rewritegeneric.go`

このファイルは、`generic.rules`で定義されたルールに基づいて自動生成されたGoコードを含んでいます。各`rewriteValuegeneric_Op...`関数は、特定のSSAオペレーションノードを最適化するためのロジックを実装しています。

**追加されたロジック（例: `rewriteValuegeneric_OpLsh16x64`内）:**
```go
	// match: (Lsh16x64  (Const16 [0]) _)
	// cond:
	// result: (Const16 [0])
	for {
		if v.Args[0].Op != OpConst16 {
			break
		}
		if v.Args[0].AuxInt != 0 {
			break
		}
		v.reset(OpConst16) // ここで結果の型をConst16に設定
		v.AuxInt = 0
		return true
	}
```
このコードブロックは、`Lsh16x64`オペレーションの左オペランドが`Const16 [0]`であるかをチェックし、そうであれば`v.reset(OpConst16)`を呼び出して現在のSSAノードを`Const16`オペレーションに変換し、その値（`AuxInt`）を`0`に設定します。

**修正されたロジック（例: `rewriteValuegeneric_OpLsh16x64`内）:**
```diff
 	// match: (Lsh16x64  _ (Const64 [c]))
 	// cond: uint64(c) >= 16
-	// result: (Const64 [0])
+	// result: (Const16 [0])
 	for {
 		if v.Args[1].Op != OpConst64 {
 			break
 		}
 		c := v.Args[1].AuxInt
 		if !(uint64(c) >= 16) {
 			break
 		}
-		v.reset(OpConst64) // 修正前はConst64
+		v.reset(OpConst16) // 修正後はConst16
 		v.AuxInt = 0
 		return true
 	}
```
この修正は、オーバーシフトの場合に`v.reset`が呼び出される際のターゲットオペレーションを`OpConst64`から`OpConst16`に変更しています。これにより、生成される定数ゼロが元のオペランドのビット幅に一致するようになります。

これらの変更は、コンパイラがSSA形式でプログラムを表現する際に、定数シフト演算をより正確かつ効率的に処理できるようにするためのものです。結果として、生成される機械語コードの品質が向上し、Goプログラムの実行性能に寄与します。

### 3. シフト演算

シフト演算は、ビット列を左右に移動させる操作です。
*   **左シフト (Lsh)**: ビットを左に移動させます。通常、左に1ビットシフトするごとに値は2倍になります。最上位ビットがあふれると情報が失われます。
*   **右シフト (Rsh)**: ビットを右に移動させます。
    *   **算術右シフト**: 符号付き整数に適用され、最上位ビット（符号ビット）を保持しながら右にシフトします。負の数の場合、左から1が挿入されます。
    *   **論理右シフト (RshU)**: 符号なし整数に適用され、左から常に0が挿入されます。

Go言語では、シフト演算子は`<<`（左シフト）と`>>`（右シフト）です。シフト量は符号なし整数型でなければなりません。

### 4. `generic.rules`と`rewritegeneric.go`

GoコンパイラのSSAバックエンドでは、最適化ルールが`generic.rules`のようなファイルに記述され、それに基づいて`rewritegeneric.go`のようなGoソースコードが自動生成されます。

*   `generic.rules`: SSAノードのパターンマッチングと書き換えルールを定義するファイルです。例えば、「ある特定のパターンのSSA操作を見つけたら、それを別のより効率的なSSA操作に置き換える」といったルールが記述されます。
*   `rewritegeneric.go`: `generic.rules`から生成されたGoコードで、実際にSSAグラフを走査し、定義されたルールに基づいてノードを書き換えるロジックを含んでいます。

## 技術的詳細

このコミットの技術的詳細は、主に`generic.rules`ファイルにおけるSSA書き換えルールの追加と修正、およびそれに対応する`rewritegeneric.go`の変更に集約されます。

### 1. シフト量がデータ型のビット幅以上の場合の型修正

Go言語の仕様では、シフト量がオペランドの型が持つビット数以上の場合、結果はゼロになります。例えば、`int8`型の変数を8ビット以上左シフトまたは右シフトした場合、結果は`0`です。

このコミット以前は、このような「オーバーシフト」の場合に、結果の定数ゼロが常に`Const64 [0]`（64ビット整数定数ゼロ）として扱われていました。しかし、元のオペランドが`int8`や`int16`、`int32`であった場合、結果もそれぞれの型の定数ゼロ（`Const8 [0]`、`Const16 [0]`、`Const32 [0]`）であるべきです。

**修正前 (`generic.rules`の抜粋):**
```
(Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
(Rsh32Ux64 _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
(Lsh16x64  _ (Const64 [c])) && uint64(c) >= 16 -> (Const64 [0])
(Rsh16Ux64 _ (Const64 [c])) && uint64(c) >= 16 -> (Const64 [0])
(Lsh8x64   _ (Const64 [c])) && uint64(c) >= 8  -> (Const64 [0])
(Rsh8Ux64  _ (Const64 [c])) && uint64(c) >= 8  -> (Const64 [0])
```
上記では、32ビット、16ビット、8ビットのシフト演算でオーバーシフトが発生した場合でも、結果が`Const64 [0]`とされていました。

**修正後 (`generic.rules`の抜粋):**
```
(Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
(Rsh32Ux64 _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
(Lsh16x64  _ (Const64 [c])) && uint64(c) >= 16 -> (Const16 [0])
(Rsh16Ux64 _ (Const64 [c])) && uint64(c) >= 16 -> (Const16 [0])
(Lsh8x64   _ (Const64 [c])) && uint64(c) >= 8  -> (Const8 [0])
(Rsh8Ux64  _ (Const64 [c])) && uint64(c) >= 8  -> (Const8 [0])
```
この修正により、結果の定数ゼロが適切なビット幅の型（`Const32 [0]`、`Const16 [0]`、`Const8 [0]`）で表現されるようになりました。これにより、コンパイラはより正確な型情報に基づいて後続の最適化やコード生成を行うことができます。

### 2. 定数ゼロのシフト演算の追加最適化

このコミットでは、定数ゼロをシフトする演算が常にゼロになるという自明なケースに対する最適化ルールも追加されています。

**追加されたルール (`generic.rules`の抜粋):**
```
(Lsh64x64  (Const64 [0]) _) -> (Const64 [0])
(Rsh64x64  (Const64 [0]) _) -> (Const64 [0])
(Rsh64Ux64 (Const64 [0]) _) -> (Const64 [0])
(Lsh32x64  (Const32 [0]) _) -> (Const32 [0])
(Rsh32x64  (Const32 [0]) _) -> (Const32 [0])
(Rsh32Ux64 (Const32 [0]) _) -> (Const32 [0])
(Lsh16x64  (Const16 [0]) _) -> (Const16 [0])
(Rsh16x64  (Const16 [0]) _) -> (Const16 [0])
(Rsh16Ux64 (Const16 [0]) _) -> (Const16 [0])
(Lsh8x64   (Const8  [0]) _) -> (Const8  [0])
(Rsh8x64   (Const8  [0]) _) -> (Const8  [0])
(Rsh8Ux64  (Const8  [0]) _) -> (Const8  [0])
```
これらのルールは、例えば`0 << x`や`0 >> x`のような式があった場合に、コンパイル時に即座に`0`に畳み込むことを可能にします。これにより、実行時に不要なシフト命令が生成されるのを防ぎ、コードサイズと実行速度の両面で改善が見込まれます。

### 3. `rewritegeneric.go`における実装

`generic.rules`で定義されたこれらのルールは、`rewritegeneric.go`内の対応する`rewriteValuegeneric_OpLshXXx64`や`rewriteValuegeneric_OpRshXXx64`関数にGoコードとして実装されます。

例えば、`Lsh16x64`（16ビット値の左シフト）の場合、以下のようなコードが追加・修正されています。

**`rewriteValuegeneric_OpLsh16x64`関数の変更点:**
*   `// match: (Lsh16x64 (Const16 [0]) _)` のパターンが追加され、左オペランドが`Const16 [0]`であれば、結果を`Const16 [0]`に設定するロジックが追加されました。
*   `// match: (Lsh16x64 _ (Const64 [c]))` かつ `uint64(c) >= 16` のパターンにおいて、結果の型を`OpConst64`から`OpConst16`に修正し、`v.AuxInt = 0`を設定するように変更されました。

これらの変更は、他のビット幅（8, 32, 64）の左シフト（Lsh）および右シフト（Rsh, RshU）操作に対しても同様に適用されています。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules`

このファイルは、GoコンパイラのSSA最適化パスで使用される書き換えルールを定義しています。各ルールは、特定のSSAオペレーションのパターンを記述し、それがマッチした場合にどのように書き換えるかを指定します。

**追加されたルール（例: `Lsh64x64`）:**
```
(Lsh64x64  (Const64 [0]) _) -> (Const64 [0])
```
これは、「64ビットの左シフト操作（`Lsh64x64`）があり、その左オペランドが64ビット定数ゼロ（`Const64 [0]`）である場合、その操作全体を64ビット定数ゼロ（`Const64 [0]`）に書き換える」というルールを意味します。`_`は任意のオペランドにマッチします。

**修正されたルール（例: `Lsh32x64`）:**
```diff
- (Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const64 [0])
+ (Lsh32x64  _ (Const64 [c])) && uint64(c) >= 32 -> (Const32 [0])
```
これは、「32ビットの左シフト操作（`Lsh32x64`）があり、その右オペランドが64ビット定数`c`であり、かつ`c`が32以上である場合（つまりオーバーシフト）、その操作全体を32ビット定数ゼロ（`Const32 [0]`）に書き換える」というルールに修正されたことを示します。修正前は`Const64 [0]`でした。

### `src/cmd/compile/internal/ssa/rewritegeneric.go`

このファイルは、`generic.rules`で定義されたルールに基づいて自動生成されたGoコードを含んでいます。各`rewriteValuegeneric_Op...`関数は、特定のSSAオペレーションノードを最適化するためのロジックを実装しています。

**追加されたロジック（例: `rewriteValuegeneric_OpLsh16x64`内）:**
```go
	// match: (Lsh16x64  (Const16 [0]) _)
	// cond:
	// result: (Const16 [0])
	for {
		if v.Args[0].Op != OpConst16 {
			break
		}
		if v.Args[0].AuxInt != 0 {
			break
		}
		v.reset(OpConst16) // ここで結果の型をConst16に設定
		v.AuxInt = 0
		return true
	}
```
このコードブロックは、`Lsh16x64`オペレーションの左オペランドが`Const16 [0]`であるかをチェックし、そうであれば`v.reset(OpConst16)`を呼び出して現在のSSAノードを`Const16`オペレーションに変換し、その値（`AuxInt`）を`0`に設定します。

**修正されたロジック（例: `rewriteValuegeneric_OpLsh16x64`内）:**
```diff
 	// match: (Lsh16x64  _ (Const64 [c]))
 	// cond: uint64(c) >= 16
-	// result: (Const64 [0])
+	// result: (Const16 [0])
 	for {
 		if v.Args[1].Op != OpConst64 {
 			break
 		}
 		c := v.Args[1].AuxInt
 		if !(uint64(c) >= 16) {
 			break
 		}
-		v.reset(OpConst64) // 修正前はConst64
+		v.reset(OpConst16) // 修正後はConst16
 		v.AuxInt = 0
 		return true
 	}
```
この修正は、オーバーシフトの場合に`v.reset`が呼び出される際のターゲットオペレーションを`OpConst64`から`OpConst16`に変更しています。これにより、生成される定数ゼロが元のオペランドのビット幅に一致するようになります。

これらの変更は、コンパイラがSSA形式でプログラムを表現する際に、定数シフト演算をより正確かつ効率的に処理できるようにするためのものです。結果として、生成される機械語コードの品質が向上し、Goプログラムの実行性能に寄与します。

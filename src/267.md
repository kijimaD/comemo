# [インデックス 267] ファイルの概要

このコミットは、Goランタイムの初期段階における大規模なリファクタリングを示しています。主要な目的は、それまで`runtime.c`という単一の巨大なファイルに集約されていた様々な機能を、より小さく、管理しやすいモジュールに分割することでした。具体的には、マップ、文字列操作、プリント機能などが個別のファイルに分離され、AMD64アーキテクチャ向けの共通アセンブラコードが共有されるようになりました。これにより、コードの可読性、保守性、およびプラットフォーム間の共通コードの再利用性が向上しています。

## 元コミット内容

このコミットは、Goランタイムのコア部分である`runtime.c`を、機能ごとに複数のファイルに分割し、AMD64アーキテクチャ向けの共通アセンブラコードを導入することを目的としています。

具体的には、以下の変更が含まれています。

- `runtime.c`からマップ、文字列、プリント関連のコードを削除。
- `runtime_map.c`、`runtime_print.c`、`runtime_string.c`といった新しいファイルを作成し、それぞれの機能を移動。
- AMD64アーキテクチャ向けの共通スタートアップコードを`rt0_amd64.s`に集約。
- OS固有のスタートアップコード（`rt0_amd64_darwin.s`、`rt0_amd64_linux.s`）を簡素化し、共通コードを呼び出すように変更。
- OS固有のシステムコールラッパーを`sys_amd64_darwin.s`、`sys_amd64_linux.s`に分離。
- `Makefile`を更新し、新しいファイル群をビルドプロセスに組み込む。
- `runtime.h`に共通関数と外部変数の宣言を追加。

## 変更の背景

Go言語の初期開発段階では、ランタイムの多くの機能が`runtime.c`という単一のC言語ファイルに実装されていました。これは開発の初期段階では迅速なプロトタイピングに適していましたが、プロジェクトの規模が拡大し、機能が追加されるにつれて、以下のような問題が生じていました。

1.  **コードの複雑性**: 単一ファイルに多くの機能が詰め込まれているため、コードベースが非常に大きく、理解や変更が困難になっていました。
2.  **保守性の低下**: 特定の機能にバグがあった場合、関連するコードを見つけるのが難しく、修正が他の機能に意図しない影響を与えるリスクがありました。
3.  **再利用性の欠如**: OSやアーキテクチャ間で共通するロジックであっても、プラットフォーム固有のファイルに重複して記述されることがありました。特に、AMD64アーキテクチャ向けのスタートアップコードやシステムコールラッパーは、Darwin (macOS) と Linux で多くの共通部分を持つにもかかわらず、それぞれ独立して実装されていました。
4.  **コンパイル時間の増加**: 巨大なファイルをコンパイルするのに時間がかかり、開発サイクルが遅延する可能性がありました。

このコミットは、これらの問題を解決し、Goランタイムの構造をよりモジュール化された、クリーンで保守しやすいものにするための重要な一歩でした。機能ごとにファイルを分割することで、各モジュールの責任が明確になり、開発者が特定の機能に集中して作業しやすくなります。また、共通アセンブラコードの共有は、コードの重複を排除し、全体的なコード量を削減する効果があります。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### 1. Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェース、プリミティブなデータ構造（マップ、文字列など）の実装などが含まれます。Goランタイムの多くはC言語とアセンブリ言語で書かれており、Go言語自体で書かれた部分もあります。

### 2. アセンブリ言語 (Assembly Language)
アセンブリ言語は、特定のCPUアーキテクチャ（例: AMD64）の命令セットに直接対応する低レベルのプログラミング言語です。Goランタイムでは、プログラムの起動処理（`rt0`ファイル）、スタック管理、システムコールなど、OSやハードウェアと直接対話する必要がある部分でアセンブリ言語が使用されます。

-   **`rt0` (Runtime 0)**: Goプログラムのエントリポイントとなるアセンブリコードです。C言語の`main`関数に相当しますが、それよりもさらに低レベルで、OSから制御を受け取った直後に実行されます。スタックの初期化、引数の処理、ランタイムの初期化、そして最終的にGoの`main`関数を呼び出す役割を担います。
-   **`_morestack`**: Goのスタックは動的に伸縮します。`_morestack`は、現在のゴルーチンのスタックが不足した際に、新しいスタック領域を確保し、スタックを切り替えるためのアセンブリルーチンです。

### 3. システムコール (System Calls)
システムコールは、ユーザープログラムがオペレーティングシステムカーネルのサービス（ファイルI/O、メモリ管理、プロセス制御など）を要求するためのインターフェースです。Goランタイムは、OS固有のシステムコールをアセンブリ言語でラップし、Goプログラムから安全かつ効率的に利用できるようにします。

### 4. Goの組み込み型 (Maps, Strings)
Goの`map`（ハッシュマップ）と`string`は、言語に組み込まれた重要なデータ型です。これらの型の低レベルな実装（メモリ管理、ハッシュ計算、比較、連結など）はランタイムによって提供されます。初期のGoランタイムでは、これらの実装も`runtime.c`内に存在していました。

### 5. `Makefile`
`Makefile`は、ソフトウェアプロジェクトのビルドプロセスを自動化するためのツールです。このコミットでは、新しいソースファイルが追加されたため、それらをコンパイルして最終的な実行可能ファイルにリンクするためのルールが`Makefile`に追記されています。

### 6. `SVN=125317`
これは、当時のGoプロジェクトがSubversion (SVN) をバージョン管理システムとして使用していたことを示しています。`125317`はSVNのリビジョン番号です。Goプロジェクトは後にGitに移行しました。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのモジュール化とコードの共通化にあります。

### 1. `runtime.c`の分割
-   **マップ関連機能**: `sys·newmap`, `sys·mapaccess1`, `sys·mapaccess2`, `sys·mapassign`, `sys·mapassign1`, `sys·mapassign2`などの関数は、ハッシュマップの作成、要素へのアクセス、要素の割り当て（追加・更新・削除）を処理します。これらは`src/runtime/runtime_map.c`に移動されました。
-   **文字列関連機能**: `cmpstring`, `sys·catstring`, `sys·cmpstring`, `sys·slicestring`, `sys·indexstring`, `runetochar`, `sys·intstring`, `sys·byteastring`などの関数は、文字列の比較、連結、スライス、インデックスアクセス、整数とバイト配列からの文字列変換などを担当します。これらは`src/runtime/runtime_string.c`に移動されました。特に`runetochar`はUTF-8エンコーディングに関連する処理です。
-   **プリント関連機能**: `sys·printbool`, `sys·printfloat`, `sys·printint`, `sys·printpointer`, `sys·printstring`, `prints`, `sys·printpc`などの関数は、デバッグ目的などで様々な型の値を標準出力にプリントする低レベルな機能を提供します。これらは`src/runtime/runtime_print.c`に移動されました。

これらの機能は、Goプログラムが動作するために不可欠なプリミティブな操作であり、ランタイムの重要な部分を構成します。これらを分離することで、各モジュールの独立性が高まり、将来的な変更や最適化が容易になります。

### 2. AMD64アセンブラの共通化
-   **`rt0_amd64.s`の導入**: この新しいファイルは、AMD64アーキテクチャ向けの共通のプログラムスタートアップロジックを含んでいます。これには、スタックの初期化、コマンドライン引数の処理、ランタイムの初期化（`mal`関数によるメモリ確保、`check`関数によるランタイム環境の検証など）、そして最終的にGoの`main`関数（`main·main`）の呼び出しが含まれます。また、スタック拡張のための`_morestack`ルーチンもここに定義されています。
-   **OS固有の`rt0`ファイルの簡素化**: `rt0_amd64_darwin.s`と`rt0_amd64_linux.s`は、以前はそれぞれのOS固有のスタートアップロジックを直接含んでいましたが、このコミットにより、単に`_rt0_amd64(SB)`という共通のエントリポイントにジャンプするだけの非常に短いコードになりました。これにより、OS間の重複コードが大幅に削減されました。
-   **`sys_amd64_darwin.s`と`sys_amd64_linux.s`の導入**: これらのファイルは、OS固有のシステムコールラッパーを含んでいます。例えば、`sys·exit`, `sys·write`, `open`, `close`, `read`, `sys·mmap`などのシステムコールが、それぞれのOSのABI（Application Binary Interface）に従ってアセンブリで実装されています。これにより、C言語の`runtime.c`からシステムコール関連のコードが分離され、OS固有の低レベルな処理がより明確に区別されるようになりました。

この共通化は、Goランタイムが異なるOS上で動作する際のコードベースの管理を簡素化し、将来的に新しいOSやアーキテクチャをサポートする際の基盤を強化します。

### 3. `runtime.h`の更新
`runtime.h`は、ランタイム内部で使用される共通の型定義、マクロ、および関数プロトタイプを宣言するヘッダーファイルです。このコミットでは、分割されたファイル間で共有される`strcmp`, `findnull`, `dump`などの関数や、`emptystring`, `debug`などの外部変数が宣言に追加されました。これにより、各モジュールが互いに正しく連携できるようになります。

### `src/runtime/rt0_amd64.s` (新規ファイル)

```asm
// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.


TEXT	_rt0_amd64(SB),7,$-8

	// copy arguments forward on an even stack

	MOVQ	0(SP), AX		// argc
	LEAQ	8(SP), BX		// argv
	SUBQ	$(4*8+7), SP		// 2args 2auto
	ANDQ	$~7, SP
	MOVQ	AX, 16(SP)
	MOVQ	BX, 24(SP)

	// allocate the per-user block

	LEAQ	peruser<>(SB), R15	// dedicated u. register

	LEAQ	(-4096+104+4*8)(SP), AX
	MOVQ	AX, 0(R15)		// 0(R15) is stack limit (w 104b guard)

	MOVL	$1024, AX
	MOVL	AX, 0(SP)
	CALL	mal(SB)

	LEAQ	104(AX), BX
	MOVQ	BX, 16(R15)		// 16(R15) is limit of istack (w 104b guard)

	ADDQ	0(SP), AX
	LEAQ	(-4*8)(AX), BX
	MOVQ	BX, 24(R15)		// 24(R15) is base of istack (w auto*4)

	CALL	check(SB)

	// process the arguments

	MOVL	16(SP), AX		// copy argc
	MOVL	AX, 0(SP)
	MOVQ	24(SP), AX		// copy argv
	MOVQ	AX, 8(SP)
	CALL	args(SB)

	CALL	main·main(SB)

	MOVQ	$0, AX
	MOVQ	AX, 0(SP)		// exit status
	CALL	sys·exit(SB)

	CALL	notok(SB)		// fault
	RET

//
// the calling sequence for a routine that
// needs N bytes stack, A args.
//
//	N1 = (N+160 > 4096)? N+160: 0
//	A1 = A
//
// if N <= 75
//	CMPQ	SP, 0(R15)
//	JHI	3(PC)
//	MOVQ	$(N1<<0) | (A1<<32)), AX
//	CALL	_morestack
//
// if N > 75
//	LEAQ	(-N-75)(SP), AX
//	CMPQ	AX, 0(R15)
//	JHI	3(PC)
//	MOVQ	$(N1<<0) | (A1<<32)), AX
//	CALL	_morestack
//

TEXT	_morestack(SB), 7, $0
	// save stuff on interrupt stack

	MOVQ	24(R15), BX		// istack
	MOVQ	SP, 8(BX)		// old SP
	MOVQ	AX, 16(BX)		// magic number
	MOVQ	0(R15), AX		// old limit
	MOVQ	AX, 24(BX)

	// switch and set up new limit

	MOVQ	BX, SP
	MOVQ	16(R15), AX		// istack limit
	MOVQ	AX, 0(R15)

	// allocate a new stack max of request and 4k

	MOVL	16(SP), AX		// magic number
	CMPL	AX, $4096
	JHI	2(PC)
	MOVL	$4096, AX
	MOVL	AX, 0(SP)
	CALL	mal(SB)

	// switch to new stack

	MOVQ	SP, BX			// istack
	ADDQ	$104, AX		// new stack limit
	MOVQ	AX, 0(R15)
	ADDQ	0(SP), AX
	LEAQ	(-104-4*8)(AX), SP	// new SP
	MOVQ	8(R15), AX
	MOVQ	AX, 0(SP)		// old base
	MOVQ	SP, 8(R15)		// new base

	// copy needed stuff from istack to new stack

	MOVQ	16(BX), AX		// magic number
	MOVQ	AX, 16(SP)
	MOVQ	24(BX), AX		// old limit
	MOVQ	AX, 24(SP)
	MOVQ	8(BX), AX		// old SP
	MOVQ	AX, 8(SP)

// are there parameters

	MOVL	20(SP), CX		// copy count
	CMPL	CX, $0
	JEQ	easy

// copy in

	LEAQ	16(AX), SI
	SUBQ	CX, SP
	MOVQ	SP, DI
	SHRL	$3, CX
	CLD
	REP
	MOVSQ

	// call the intended
	CALL	0(AX)

// copy out

	MOVQ	SP, SI
	MOVQ	8(R15), BX		// new base
	MOVQ	8(BX), AX		// old SP
	LEAQ	16(AX), DI
	MOVL	20(BX), CX		// copy count
	SHRL	$3, CX
	CLD
	REP
	MOVSQ

	// restore old SP and limit
	MOVQ	8(R15), SP		// new base
	MOVQ	24(SP), AX		// old limit
	MOVQ	AX, 0(R15)
	MOVQ	0(SP), AX
	MOVQ	AX, 8(R15)		// old base
	MOVQ	8(SP), AX		// old SP
	MOVQ	AX, SP

	// and return to the call behind mine
	ADDQ	$8, SP
	RET

easy:
	CALL	0(AX)

	// restore old SP and limit
	MOVQ	24(SP), AX		// old limit
	MOVQ	AX, 0(R15)
	MOVQ	0(SP), AX
	MOVQ	AX, 8(R15)		// old base
	MOVQ	8(SP), AX		// old SP
	MOVQ	AX, SP

	// and return to the call behind mine
	ADDQ	$8, SP
	RET

TEXT	FLUSH(SB),7,$-8
	RET

GLOBL	peruser<>(SB),$64
```

## コアとなるコードの解説

このコミットの最も重要な変更は、Goランタイムの構造をモジュール化し、AMD64アセンブラコードを共通化した点です。

### 1. `runtime.c`の役割の変化
以前はGoランタイムのほとんどの機能が`runtime.c`に集約されていましたが、このコミットにより、`runtime.c`はより汎用的なランタイムの初期化、メモリ管理（`mal`）、パニック処理（`sys·panicl`）といった、より基本的な機能に特化するようになりました。これにより、各ファイルの責任が明確になり、コードベース全体の理解が容易になります。

### 2. `rt0_amd64.s`とOS固有`rt0`ファイルの連携
-   `rt0_amd64.s`は、AMD64アーキテクチャのGoプログラムが起動する際の共通エントリポイント`_rt0_amd64`を提供します。このコードは、OSから制御を受け取った直後に実行され、スタックのセットアップ、コマンドライン引数の処理、ランタイムの初期化（`mal`、`check`、`args`の呼び出し）、そして最終的にGoプログラムのエントリポイントである`main·main`関数を呼び出します。
-   `_morestack`ルーチンは、Goの動的スタック拡張メカニズムの核心です。ゴルーチンのスタックが不足しそうになったときに呼び出され、新しいスタック領域を確保し、現在の実行コンテキストを新しいスタックに安全に移行させます。これは、Goの軽量なゴルーチンが多数同時に実行されることを可能にする重要な機能です。
-   `rt0_amd64_darwin.s`と`rt0_amd64_linux.s`は、それぞれのOS固有のスタートアップコードですが、このコミット以降は、単に`_rt0_amd64`にジャンプするだけの非常に薄いラッパーとなりました。これは、OS間の共通ロジックを`rt0_amd64.s`に集約することで、コードの重複を排除し、保守性を高めるための設計判断です。

### 3. `sys_amd64_darwin.s`と`sys_amd64_linux.s`によるシステムコール抽象化
これらのファイルは、OS固有のシステムコールをアセンブリ言語で直接呼び出すためのラッパー関数を提供します。例えば、`sys·write`は、ファイルディスクリプタ、バッファ、書き込むバイト数を引数として受け取り、OSの`write`システムコールを呼び出します。システムコール番号や引数の渡し方はOSによって異なるため、これらのファイルでOS固有のABIに合わせた実装が行われます。これにより、GoランタイムのCコードは、OS固有のシステムコール呼び出しの詳細を意識することなく、抽象化された`sys·`関数を呼び出すことができます。

### 4. `runtime_map.c`, `runtime_print.c`, `runtime_string.c`による機能分離
これらのファイルは、Goの組み込み型であるマップと文字列、および基本的なプリント機能の低レベルな実装をそれぞれ担当します。
-   `runtime_map.c`には、ハッシュ関数、キーの比較、値のコピーといったマップ操作に必要なアルゴリズムと、マップの作成、アクセス、割り当てを行う関数が含まれます。
-   `runtime_string.c`には、文字列の比較、連結、スライス、インデックスアクセス、そしてUTF-8エンコーディングを扱う`runetochar`のような関数が含まれます。
-   `runtime_print.c`には、ブール値、整数、ポインタ、文字列などを標準出力に書き出すための低レベルな関数が含まれます。

これらの分離により、各機能のコードが独立し、Goランタイムの内部構造がより明確で理解しやすくなりました。これは、Go言語の進化と成長を支える上で不可欠な基盤強化のステップでした。

## 変更の背景

Go言語の初期開発段階では、ランタイムの多くの機能が`runtime.c`という単一のC言語ファイルに実装されていました。これは開発の初期段階では迅速なプロトタイピングに適していましたが、プロジェクトの規模が拡大し、機能が追加されるにつれて、以下のような問題が生じていました。

1.  **コードの複雑性**: 単一ファイルに多くの機能が詰め込まれているため、コードベースが非常に大きく、理解や変更が困難になっていました。
2.  **保守性の低下**: 特定の機能にバグがあった場合、関連するコードを見つけるのが難しく、修正が他の機能に意図しない影響を与えるリスクがありました。
3.  **再利用性の欠如**: OSやアーキテクチャ間で共通するロジックであっても、プラットフォーム固有のファイルに重複して記述されることがありました。特に、AMD64アーキテクチャ向けのスタートアップコードやシステムコールラッパーは、Darwin (macOS) と Linux で多くの共通部分を持つにもかかわらず、それぞれ独立して実装されていました。
4.  **コンパイル時間の増加**: 巨大なファイルをコンパイルするのに時間がかかり、開発サイクルが遅延する可能性がありました。

このコミットは、これらの問題を解決し、Goランタイムの構造をよりモジュール化された、クリーンで保守しやすいものにするための重要な一歩でした。機能ごとにファイルを分割することで、各モジュールの責任が明確になり、開発者が特定の機能に集中して作業しやすくなります。また、共通アセンブラコードの共有は、コードの重複を排除し、全体的なコード量を削減する効果があります。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### 1. Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェース、プリミティブなデータ構造（マップ、文字列など）の実装などが含まれます。Goランタイムの多くはC言語とアセンブリ言語で書かれており、Go言語自体で書かれた部分もあります。

### 2. アセンブリ言語 (Assembly Language)
アセンブリ言語は、特定のCPUアーキテクチャ（例: AMD64）の命令セットに直接対応する低レベルのプログラミング言語です。Goランタイムでは、プログラムの起動処理（`rt0`ファイル）、スタック管理、システムコールなど、OSやハードウェアと直接対話する必要がある部分でアセンブリ言語が使用されます。

-   **`rt0` (Runtime 0)**: Goプログラムのエントリポイントとなるアセンブリコードです。C言語の`main`関数に相当しますが、それよりもさらに低レベルで、OSから制御を受け取った直後に実行されます。スタックの初期化、引数の処理、ランタイムの初期化、そして最終的にGoの`main`関数を呼び出す役割を担います。
-   **`_morestack`**: Goのスタックは動的に伸縮します。`_morestack`は、現在のゴルーチンのスタックが不足した際に、新しいスタック領域を確保し、スタックを切り替えるためのアセンブリルーチンです。

### 3. システムコール (System Calls)
システムコールは、ユーザープログラムがオペレーティングシステムカーネルのサービス（ファイルI/O、メモリ管理、プロセス制御など）を要求するためのインターフェースです。Goランタイムは、OS固有のシステムコールをアセンブリ言語でラップし、Goプログラムから安全かつ効率的に利用できるようにします。

### 4. Goの組み込み型 (Maps, Strings)
Goの`map`（ハッシュマップ）と`string`は、言語に組み込まれた重要なデータ型です。これらの型の低レベルな実装（メモリ管理、ハッシュ計算、比較、連結など）はランタイムによって提供されます。初期のGoランタイムでは、これらの実装も`runtime.c`内に存在していました。

### 5. `Makefile`
`Makefile`は、ソフトウェアプロジェクトのビルドプロセスを自動化するためのツールです。このコミットでは、新しいソースファイルが追加されたため、それらをコンパイルして最終的な実行可能ファイルにリンクするためのルールが`Makefile`に追記されています。

### 6. `SVN=125317`
これは、当時のGoプロジェクトがSubversion (SVN) をバージョン管理システムとして使用していたことを示しています。`125317`はSVNのリビジョン番号です。Goプロジェクトは後にGitに移行しました。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのモジュール化とコードの共通化にあります。

### 1. `runtime.c`の分割
-   **マップ関連機能**: `sys·newmap`, `sys·mapaccess1`, `sys·mapaccess2`, `sys·mapassign`, `sys·mapassign1`, `sys·mapassign2`などの関数は、ハッシュマップの作成、要素へのアクセス、要素の割り当て（追加・更新・削除）を処理します。これらは`src/runtime/runtime_map.c`に移動されました。
-   **文字列関連機能**: `cmpstring`, `sys·catstring`, `sys·cmpstring`, `sys·slicestring`, `sys·indexstring`, `runetochar`, `sys·intstring`, `sys·byteastring`などの関数は、文字列の比較、連結、スライス、インデックスアクセス、整数とバイト配列からの文字列変換などを担当します。これらは`src/runtime/runtime_string.c`に移動されました。特に`runetochar`はUTF-8エンコーディングに関連する処理です。
-   **プリント関連機能**: `sys·printbool`, `sys·printfloat`, `sys·printint`, `sys·printpointer`, `sys·printstring`, `prints`, `sys·printpc`などの関数は、デバッグ目的などで様々な型の値を標準出力にプリントする低レベルな機能を提供します。これらは`src/runtime/runtime_print.c`に移動されました。

これらの機能は、Goプログラムが動作するために不可欠なプリミティブな操作であり、ランタイムの重要な部分を構成します。これらを分離することで、各モジュールの独立性が高まり、将来的な変更や最適化が容易になります。

### 2. AMD64アセンブラの共通化
-   **`rt0_amd64.s`の導入**: この新しいファイルは、AMD64アーキテクチャ向けの共通のプログラムスタートアップロジックを含んでいます。これには、スタックの初期化、コマンドライン引数の処理、ランタイムの初期化（`mal`関数によるメモリ確保、`check`関数によるランタイム環境の検証など）、そして最終的にGoの`main`関数（`main·main`）の呼び出しが含まれます。また、スタック拡張のための`_morestack`ルーチンもここに定義されています。
-   **OS固有の`rt0`ファイルの簡素化**: `rt0_amd64_darwin.s`と`rt0_amd64_linux.s`は、以前はそれぞれのOS固有のスタートアップロジックを直接含んでいましたが、このコミットにより、単に`_rt0_amd64(SB)`という共通のエントリポイントにジャンプするだけの非常に短いコードになりました。これにより、OS間の重複コードが大幅に削減されました。
-   **`sys_amd64_darwin.s`と`sys_amd64_linux.s`の導入**: これらのファイルは、OS固有のシステムコールラッパーを含んでいます。例えば、`sys·exit`, `sys·write`, `open`, `close`, `read`, `sys·mmap`などのシステムコールが、それぞれのOSのABI（Application Binary Interface）に従ってアセンブリで実装されています。これにより、C言語の`runtime.c`からシステムコール関連のコードが分離され、OS固有の低レベルな処理がより明確に区別されるようになりました。

この共通化は、Goランタイムが異なるOS上で動作する際のコードベースの管理を簡素化し、将来的に新しいOSやアーキテクチャをサポートする際の基盤を強化します。

### 3. `runtime.h`の更新
`runtime.h`は、ランタイム内部で使用される共通の型定義、マクロ、および関数プロトタイプを宣言するヘッダーファイルです。このコミットでは、分割されたファイル間で共有される`strcmp`, `findnull`, `dump`などの関数や、`emptystring`, `debug`などの外部変数が宣言に追加されました。これにより、各モジュールが互いに正しく連携できるようになります。

## コアとなるコードの解説

このコミットの最も重要な変更は、Goランタイムの構造をモジュール化し、AMD64アセンブラコードを共通化した点です。

### 1. `runtime.c`の役割の変化
以前はGoランタイムのほとんどの機能が`runtime.c`に集約されていましたが、このコミットにより、`runtime.c`はより汎用的なランタイムの初期化、メモリ管理（`mal`）、パニック処理（`sys·panicl`）といった、より基本的な機能に特化するようになりました。これにより、各ファイルの責任が明確になり、コードベース全体の理解が容易になります。

### 2. `rt0_amd64.s`とOS固有`rt0`ファイルの連携
-   `rt0_amd64.s`は、AMD64アーキテクチャのGoプログラムが起動する際の共通エントリポイント`_rt0_amd64`を提供します。このコードは、OSから制御を受け取った直後に実行され、スタックのセットアップ、コマンドライン引数の処理、ランタイムの初期化（`mal`、`check`、`args`の呼び出し）、そして最終的にGoプログラムのエントリポイントである`main·main`関数を呼び出します。
-   `_morestack`ルーチンは、Goの動的スタック拡張メカニズムの核心です。ゴルーチンのスタックが不足しそうになったときに呼び出され、新しいスタック領域を確保し、現在の実行コンテキストを新しいスタックに安全に移行させます。これは、Goの軽量なゴルーチンが多数同時に実行されることを可能にする重要な機能です。
-   `rt0_amd64_darwin.s`と`rt0_amd64_linux.s`は、それぞれのOS固有のスタートアップコードですが、このコミット以降は、単に`_rt0_amd64`にジャンプするだけの非常に薄いラッパーとなりました。これは、OS間の共通ロジックを`rt0_amd64.s`に集約することで、コードの重複を排除し、保守性を高めるための設計判断です。

### 3. `sys_amd64_darwin.s`と`sys_amd64_linux.s`によるシステムコール抽象化
これらのファイルは、OS固有のシステムコールをアセンブリ言語で直接呼び出すためのラッパー関数を提供します。例えば、`sys·write`は、ファイルディスクリプタ、バッファ、書き込むバイト数を引数として受け取り、OSの`write`システムコールを呼び出します。システムコール番号や引数の渡し方はOSによって異なるため、これらのファイルでOS固有のABIに合わせた実装が行われます。これにより、GoランタイムのCコードは、OS固有のシステムコール呼び出しの詳細を意識することなく、抽象化された`sys·`関数を呼び出すことができます。

### 4. `runtime_map.c`, `runtime_print.c`, `runtime_string.c`による機能分離
これらのファイルは、Goの組み込み型であるマップと文字列、および基本的なプリント機能の低レベルな実装をそれぞれ担当します。
-   `runtime_map.c`には、ハッシュ関数、キーの比較、値のコピーといったマップ操作に必要なアルゴリズムと、マップの作成、アクセス、割り当てを行う関数が含まれます。
-   `runtime_string.c`には、文字列の比較、連結、スライス、インデックスアクセス、そしてUTF-8エンコーディングを扱う`runetochar`のような関数が含まれます。
-   `runtime_print.c`には、ブール値、整数、ポインタ、文字列などを標準出力に書き出すための低レベルな関数が含まれます。

これらの分離により、各機能のコードが独立し、Goランタイムの内部構造がより明確で理解しやすくなりました。これは、Go言語の進化と成長を支える上で不可欠な基盤強化のステップでした。

## 変更の背景

このコミットは、Goの`net`パッケージにおける`hostLookupOrder`関数が、空文字列をホスト名として受け取った際に、期待される名前解決の順序を返さないというバグを修正します。具体的には、`hostLookupOrder("")`が呼ばれた際に、`myhostname`という名前解決ソースの処理ロジックが不適切に適用され、結果として誤ったフォールバック順序が選択されていました。

元の実装では、ホスト名にドットが含まれているかどうかを示す`hasDot`フラグに基づいて`myhostname`ソースをスキップするかどうかを判断していました。しかし、空文字列のホスト名の場合、`hasDot`は`false`となるため、`myhostname`ソースの処理が実行されてしまい、これが問題を引き起こしていました。空のホスト名に対しては、`myhostname`ソースは適用されるべきではありません。この問題はIssue #13623として報告されました。

## 前提知識の解説

### Goの`net`パッケージ

Go言語の`net`パッケージは、TCP/IPネットワークプログラミングのための基本的なインターフェースを提供します。これには、IPアドレスの解決、ポートのリスニング、ネットワーク接続の確立などが含まれます。名前解決（ホスト名をIPアドレスに変換すること）もこのパッケージの重要な機能の一つです。

### 名前解決 (DNS Lookup) と`nsswitch.conf`

オペレーティングシステムは、ホスト名をIPアドレスに解決するために、複数のメカニズムを使用します。LinuxなどのUnix系システムでは、`/etc/nsswitch.conf`ファイルがこの名前解決の順序を定義します。例えば、`hosts: files dns`という設定は、まず`/etc/hosts`ファイル（`files`）を検索し、見つからなければDNS（`dns`）を問い合わせることを意味します。

### `hostLookupOrder`関数

Goの`net`パッケージ内部の`hostLookupOrder`関数は、与えられたホスト名とシステムの名前解決設定（`/etc/nsswitch.conf`などから読み取られる）に基づいて、実際に名前解決を試みるソースの順序（例: `files`, `dns`, `cgo`）を決定します。この関数は、効率的かつ正確な名前解決のために非常に重要です。

### `myhostname`ソース

`myhostname`は、名前解決のソースの一つとして、システム自身のホスト名（`hostname`コマンドで表示される名前）を指します。通常、完全修飾ドメイン名（FQDN）ではない短いホスト名が与えられた場合に、ローカルシステムが自身を解決するために使用されます。

### `hasDot`フラグ

`hostLookupOrder`関数内で使用される`hasDot`フラグは、入力されたホスト名文字列にドット（`.`）が含まれているかどうかを示します。一般的に、ホスト名にドットが含まれる場合、それはFQDN（例: `www.example.com`）と見なされ、DNSによる解決が優先されます。ドットが含まれない場合（例: `localhost`、`myhost`）、それはローカルホスト名や検索ドメイン内のホスト名として扱われることが多く、`files`や`myhostname`といったローカルな解決ソースが考慮されます。

## 技術的詳細

`hostLookupOrder`関数は、システムの設定から取得した名前解決ソースのリスト（`srcs`）をイテレートし、各ソースが現在のホスト名に対して適切かどうかを判断します。

問題の箇所は、`myhostname`ソースを処理する部分にありました。
```go
		if src.source == "myhostname" {
			if hasDot { // ここが問題
				continue
			}
			return fallbackOrder
		}
```
このコードは、「もしホスト名にドットが含まれていれば（`hasDot`が`true`）、`myhostname`ソースはスキップする」というロジックです。これは、FQDNに対して`myhostname`を適用しないという意図では正しいです。

しかし、空文字列`""`がホスト名として渡された場合、`hasDot`は`false`になります。このため、上記の`if hasDot`の条件は満たされず、`myhostname`ソースの処理が実行されてしまいます。空文字列はFQDNではないため、`myhostname`ソースが考慮されること自体は一見問題ないように見えますが、`myhostname`ソースのロジックが空文字列に対して適切に機能しない、または意図しない`fallbackOrder`を返してしまうという問題がありました。

空文字列のホスト名に対する名前解決は、通常、特定のデフォルトの順序に従うべきであり、`myhostname`ソースの特殊なロジックに依存すべきではありません。このバグにより、`hostLookupOrder("")`が期待される`hostLookupFilesDNS`ではなく、`hostLookupCgo`のような異なる順序を返す可能性がありました。

## コアとなるコードの解説

変更は`src/net/conf.go`の1行に集約されています。

```go
-			if hasDot {
+			if hostname == "" || hasDot {
```

この変更により、`myhostname`ソースをスキップする条件が拡張されました。
-   **`hasDot`**: 以前からの条件で、ホスト名にドットが含まれる（FQDNである）場合は`myhostname`ソースをスキップします。
-   **`hostname == ""`**: 新しく追加された条件で、ホスト名が空文字列である場合も`myhostname`ソースをスキップします。

この修正により、空文字列がホスト名として渡された場合（`hostname == ""`が`true`）、`myhostname`ソースの処理は`continue`によってスキップされ、`fallbackOrder`が返されることがなくなります。これにより、空文字列に対する名前解決の順序が、`myhostname`ソースの特殊なロジックに影響されずに、より一般的なデフォルトの順序（この場合は`hostLookupFilesDNS`が期待される）に従うようになります。

`src/net/conf_test.go`には、この修正が正しく機能することを確認するための新しいテストケースが追加されました。
```go
				{"", hostLookupFilesDNS}, // Issue 13623
```
このテストケースは、空文字列`""`が与えられた場合に、期待される名前解決順序が`hostLookupFilesDNS`であることを検証します。これは、Issue #13623で報告されたバグが修正されたことを確認するための重要な追加です。

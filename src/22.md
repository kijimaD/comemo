# [インデックス 22] ファイルの概要

## コミット

このコミットは、Go言語の初期の言語仕様書である `doc/go_lang.txt` における構文定義の表記揺れを修正し、一貫性を向上させるものです。具体的には、EBNF (Extended Backus-Naur Form) 形式で記述された構文規則において、リテラルシンボルを囲む引用符をシングルクォート (`'`) からダブルクォート (`"`) に統一し、`switch` ステートメントの定義における冗長なオプション指定 (`[]`) を削除しています。

## 変更の背景

このコミットの背景には、Go言語の言語仕様書 `doc/go_lang.txt` の記述における一貫性の欠如がありました。

1.  **EBNF表記における引用符の不統一**: 言語仕様書では、構文規則をEBNFで定義していましたが、リテラルシンボル（例: `+`, `-`, `(` など）を囲む際に、シングルクォート (`'`) とダブルクォート (`"`) が混在していました。これは、読者にとって混乱を招く可能性があり、仕様書としての厳密性や可読性を損なうものでした。このコミットは、これをダブルクォートに統一することで、表記の一貫性を確保し、仕様書の品質を向上させることを目的としています。

2.  **`switch` ステートメント定義の冗長性**: `switch` ステートメントのEBNF定義において、オプション要素を示す `[]` が冗長に使用されていました。EBNFでは `[]` は0回または1回の出現を意味しますが、既にオプションである要素をさらに `[]` で囲むことは、構文の意図を不明瞭にし、不必要に複雑に見せていました。このコミットは、この冗長な `[]` を削除し、定義をより簡潔かつ明確にすることを目的としています。

これらの変更は、Go言語の初期段階において、言語仕様の文書化を進める中で発見された表記上の問題点を修正し、将来的な言語開発とドキュメントの維持管理を容易にするための基盤固めの一環として行われました。

## 前提知識の解説

### Extended Backus-Naur Form (EBNF)

EBNF（拡張バッカス・ナウア記法）は、プログラミング言語やデータ形式の文法を記述するためのメタ言語です。BNF（バッカス・ナウア記法）を拡張したもので、より簡潔で読みやすい文法定義を可能にします。

Go言語の仕様書では、EBNFを用いて言語の構文規則を定義しています。EBNFの主な記号とその意味は以下の通りです。

*   `=` または `::=`：定義。左辺の非終端記号が右辺の規則によって定義されることを示す。
*   `|`：選択。複数の選択肢のいずれか一つを意味する。
*   `()`：グループ化。複数の要素をまとめて一つの単位として扱う。
*   `[]`：オプション。囲まれた要素が0回または1回出現することを示す。
*   `{}`：繰り返し。囲まれた要素が0回以上出現することを示す。
*   `""` または `''`：リテラルシンボル（終端記号）。文法規則の中で文字通りに現れる記号やキーワードを示す。このコミットの変更点はこの部分に焦点を当てています。
*   `.` または `;`：規則の終端。一つの文法規則の終わりを示す。

例:
`Expression = Term { "+" Term } .`
これは、「ExpressionはTermで始まり、その後に0回以上の"+"とTermの繰り返しが続く」ことを意味します。

### `doc/go_lang.txt`

`doc/go_lang.txt` は、Go言語の初期の言語仕様書、またはその草稿にあたるドキュメントです。Go言語の開発初期段階において、言語の設計思想、構文、セマンティクスなどがこのテキストファイルにまとめられていました。これは、現在の公式なGo言語仕様書（`go.dev/ref/spec` で公開されているもの）の前身となる重要な文書です。

このファイルは、Go言語の進化の過程を理解する上で貴重な資料であり、本コミットのように、言語仕様の細かな調整や表記の改善がどのように行われてきたかを示す証拠となります。

## 技術的詳細

このコミットは、`doc/go_lang.txt` 内のEBNF構文定義における2つの主要な技術的修正を含んでいます。

1.  **リテラルシンボルの引用符統一**:
    *   **変更前**: EBNFの定義において、リテラルシンボル（例: `+`, `-`, `[`, `]` など）を囲むために、シングルクォート (`'`) とダブルクォート (`"`) が混在していました。例えば、`'['` と `"]"` のように、同じ文法規則内で異なる引用符が使用されている箇所がありました。
    *   **変更後**: すべてのリテラルシンボルがダブルクォート (`"`) で囲まれるように統一されました。これにより、仕様書の構文定義全体で一貫した表記が実現され、読者が文法規則を解釈する際の曖昧さが排除されました。EBNFの標準的な慣習では、リテラルシンボルには引用符を使用しますが、シングルとダブルのどちらを使うかは文脈やスタイルガイドに依存します。Go言語の仕様書では、このコミットによってダブルクォートが標準として確立されました。

2.  **`switch` ステートメント定義の冗長な `[]` の削除**:
    *   **変更前**: `SwitchStat` のEBNF定義において、`[ SimpleVarDecl ';' ]` と `[ Expression ]` の周りにさらに `[]` が付与されていました。これは `[[ SimpleVarDecl ';' ] [ Expression ]]` のような形式でした。EBNFの `[]` は「0回または1回出現」を意味するため、既にオプションである要素をさらにオプションとして囲むことは文法的に冗長であり、定義を不必要に複雑にしていました。
    *   **変更後**: 冗長な外側の `[]` が削除され、`[ SimpleVarDecl ";" ] [ "Expression ]` のように簡潔化されました。これにより、`switch` ステートメントの初期化文 (`SimpleVarDecl`) とタグ式 (`Expression`) がそれぞれオプションであることを明確かつ簡潔に表現できるようになりました。この修正は、EBNFの記法をより正確かつ効率的に使用することを目指しています。

これらの変更は、Go言語の構文定義の正確性、一貫性、および可読性を向上させる上で重要なステップでした。特に、言語仕様書は言語の「真実の源」であるため、その記述の厳密性は極めて重要です。

## コアとなるコードの解説

### 引用符の統一

変更の大部分は、EBNF定義におけるリテラルシンボルを囲む引用符の変更です。

*   **変更前**: `IdentifierList = identifier { ',' identifier } .`
    *   ここでは、カンマ `,` がシングルクォート `'` で囲まれています。
*   **変更後**: `IdentifierList = identifier { "," identifier } .`
    *   カンマ `,` がダブルクォート `"` で囲まれています。

この変更は、`doc/go_lang.txt` 内のEBNF規則全体にわたって適用されており、`'+'`, `'-'`, `'['`, `']'`, `'('`, `')'`, `':'`, `';'`, `'='`, `'*'`, `'&'`, `'|'`, `'^'`, `'<'`, `'>'`, `'!'`, `'%'`, `'/'`, `'~'`, `'@'`, `'#'`, `'$'`, `'?'`, `'`'` など、すべてのリテラルシンボルがダブルクォートで統一されています。これにより、仕様書の表記が一貫し、読みやすさが向上します。

### `switch` ステートメント定義の簡素化

`switch` ステートメントの定義は、特に注目すべき変更点です。

*   **変更前**:
    ```ebnf
    SwitchStat = 'switch' [ [ SimpleVarDecl ';' ] [ Expression ] ] '{' { CaseClause } '}' .
    ```
    ここで、`[ SimpleVarDecl ';' ]` と `[ Expression ]` はそれぞれオプションの要素です。これらがさらに外側の `[]` で囲まれているため、`switch` キーワードの後に続く全体がオプションであるかのように見えますが、実際には `SimpleVarDecl` と `Expression` の両方がオプションであることを示しています。この二重の `[]` は冗長でした。

*   **変更後**:
    ```ebnf
    SwitchStat = "switch" [ SimpleVarDecl ";" ] [ "Expression ] "{" { CaseClause } "}" .
    ```
    冗長な外側の `[]` が削除され、`switch` キーワードの後に `SimpleVarDecl` と `Expression` がそれぞれ独立したオプションとして続くことが明確になりました。これにより、EBNFの定義がより簡潔になり、`switch` ステートメントの構文が直感的に理解しやすくなりました。

これらの変更は、Go言語の言語仕様書が、その初期段階から厳密性と一貫性を追求して作成されていたことを示しています。

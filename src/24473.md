## 変更の背景

この変更は、GoランタイムがCGOを介して外部Cコードと連携する際に、Darwin (macOS) のARM64アーキテクチャ上で発生するシグナル（特にセグメンテーション違反などの致命的なエラー）のハンドリングに関するバグを修正するために行われました。

Goプログラムがクラッシュするような状況（例: nilポインタの逆参照）では、ランタイムは`sigpanic`という特別な関数を呼び出してパニックを処理し、スタックトレースを生成します。このプロセスにおいて、スタックフレームの正しい設定と、呼び出し元のリターンアドレスを保持するLink Register (LR) の適切な保存が不可欠です。

元の実装では、`sigpanic`の呼び出し時に必要なスタックフレームの領域が適切に確保されておらず、またLRが正しい位置にプッシュされていませんでした。この問題は、通常、`sigpanic`を越えたトレースバックが、フォールティングリーフ（エラー発生箇所）のLRのみを必要とするため、あまり顕在化しませんでした。しかし、`sync/atomic`パッケージのnilポインタ逆参照テストにおいて、この不正確なシグナルハンドリングが原因でテストが失敗するという具体的な問題が発覚しました。このテストの失敗が、今回の修正の直接的なトリガーとなりました。

## 前提知識の解説

1.  **CGO (C Foreign Function Interface for Go):** GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのメカニズムです。Goランタイムは、CGOを介して外部ライブラリと連携する際に、OS固有のシグナルハンドリングなど、低レベルな処理を行う必要があります。
2.  **Darwin/ARM64:** DarwinはmacOSのカーネルであり、ARM64はApple Siliconチップなどの64ビットARMアーキテクチャを指します。この環境では、特定のレジスタの使用方法やスタックフレームの構造が他のアーキテクチャ（例: x86-64）とは異なります。
3.  **シグナルハンドリング:** オペレーティングシステムがプログラムに非同期イベント（例: 割り込み、エラー、ユーザー入力）を通知するメカニズムです。セグメンテーション違反（SIGSEGV）などの致命的なシグナルが発生した場合、プログラムは通常クラッシュしますが、シグナルハンドラを設定することで、そのシグナルを捕捉し、カスタムの処理（例: エラーログの記録、クリーンアップ、パニック）を行うことができます。
4.  **スタックフレーム:** 関数が呼び出されるたびに、その関数のローカル変数、引数、リターンアドレスなどを格納するためにスタック上に確保されるメモリ領域です。スタックフレームの構造はアーキテクチャやABI (Application Binary Interface) によって異なります。
5.  **Link Register (LR):** ARMアーキテクチャにおける特別なレジスタで、関数呼び出し時に呼び出し元に戻るためのアドレス（リターンアドレス）が格納されます。関数が別の関数を呼び出す前に、このLRの値をスタックに保存し、関数から戻る際にスタックから復元するのが一般的な慣習です。これにより、関数呼び出しのネストが正しく機能します。
6.  **`sigpanic`:** Goランタイム内部の関数で、致命的なシグナル（例: SIGSEGV）が発生した際に呼び出され、Goのパニックメカニズムを開始します。これにより、スタックトレースが生成され、プログラムが終了します。
7.  **`runtime·setsigsegv`:** シグナルハンドリングのコンテキストで、セグメンテーション違反が発生した際のPC (Program Counter) などの情報をGoの`g`オブジェクト（ゴルーチンを表す構造体）に設定するランタイム関数です。これにより、パニック発生時の正確なスタックトレース情報が得られます。

## 技術的詳細

このコミットは、`src/runtime/cgo/signal_darwin_arm64.s`というアセンブリファイルに対する変更です。このファイルは、Darwin上のARM64アーキテクチャにおけるCGO関連のシグナルハンドリングロジックを実装しています。

問題の核心は、`sigpanic`関数を呼び出す準備段階でのスタックフレームの不適切な管理と、Link Register (LR) の誤った扱いでした。

具体的には、以下の点が修正されました。

1.  **スタックフレームの確保:**
    *   以前は、`runtime·setsigsegv`を呼び出す前に、スタック上に十分なスペースが確保されていませんでした。
    *   修正後、`runtime·setsigsegv`の呼び出しのために32バイトのスタックフレームが明示的に構築されるようになりました (`MOVD.W $0, -32(RSP)`)。これは、`setsigsegv`への引数（PC）と、LRのコピーを保存するためのスペースを含みます。
    *   さらに、`sigpanic`への「シミュレートされた」呼び出しのために、その32バイトのフレームから16バイトを消費して、別の16バイトのスタックフレームが構築されます。このフレームには、フォールト発生時のLRと、`sigpanic`へのエントリ時のPCが保存されます。

2.  **Link Register (LR) の扱い:**
    *   以前は、`runtime·setsigsegv`を呼び出す際に、LRが正しくプッシュされていませんでした。
    *   修正後、`runtime·setsigsegv`を呼び出す前に、フォールト発生時のPC (R1) とLR (R2) がスタック上の適切な位置に保存されます (`MOVD R1, 8(RSP)`, `MOVD R2, 16(RSP)`)。
    *   `runtime·setsigsegv`からの戻り後、これらの値はレジスタに復元され、`sigpanic`への呼び出しのためにLR (R30) に設定されます (`MOVD R2, R30`)。これにより、`sigpanic`が正しいリターンアドレスを持つことになります。

これらの変更により、シグナル発生時にGoランタイムがスタックを正しく巻き戻し、正確なスタックトレースを生成できるようになります。特に、`sync/atomic`パッケージのような低レベルな操作でnilポインタ逆参照が発生した場合でも、ランタイムがその状況を正しく処理し、テストが成功するようになりました。

## コアとなるコードの解説

変更は主に`ongothread`セクションに集中しています。このセクションは、Goルーチンがシグナルを受け取った際に実行されるコードパスの一部です。

**変更前:**

```assembly
 	STP.W (R1, R2), -16(RSP)
 	BL runtime·setsigsegv(SB)
 	LDP.P 16(RSP), (R1, R2)
 	MOVD R1, 8(RSP)
 	MOVD R2, R30 // link register
 	B runtime·sigpanic(SB)
```
ここでは、`STP.W (R1, R2), -16(RSP)`でR1とR2をスタックに保存し、`runtime·setsigsegv`を呼び出した後、`LDP.P 16(RSP), (R1, R2)`で復元しています。しかし、スタックフレームのサイズやLRの扱いが不適切でした。特に、`sigpanic`への呼び出しのためのスタックフレームが明示的に構築されていませんでした。

**変更後:**

```assembly
 	// Build a 32-byte stack frame for us for this call.
 	// Saved LR (none available) is at the bottom,
 	// then the PC argument for setsigsegv,
 	// then a copy of the LR for us to restore.
 	MOVD.W $0, -32(RSP) // 32バイトのスタックフレームを確保
 	MOVD R1, 8(RSP)     // R1 (PC) をスタックに保存
 	MOVD R2, 16(RSP)    // R2 (LR) をスタックに保存
 	BL runtime·setsigsegv(SB) // runtime·setsigsegv を呼び出し
 	MOVD 8(RSP), R1     // スタックからR1を復元
 	MOVD 16(RSP), R2    // スタックからR2を復元

 	// Build a 16-byte stack frame for the simulated
 	// call to sigpanic, by taking 16 bytes away from the
 	// 32-byte stack frame above.
 	// The saved LR in this frame is the LR at time of fault,
 	// and the LR on entry to sigpanic is the PC at time of fault.
 	MOVD.W R1, 16(RSP)  // R1 (PC) を sigpanic のスタックフレームのLR位置に保存
 	MOVD R2, R30        // R2 (LR) を Link Register (R30) に設定
 	B runtime·sigpanic(SB) // sigpanic へジャンプ
```

この修正では、まず`runtime·setsigsegv`を呼び出すために32バイトのスタックフレームを明示的に確保し、フォールト発生時のPCとLRをスタックに保存します。`setsigsegv`からの戻り後、これらの値を復元し、さらに`sigpanic`への呼び出しのために16バイトのスタックフレームを構築します。この16バイトのフレームでは、フォールト発生時のLRが保存され、`sigpanic`へのエントリ時のLRとしてフォールト発生時のPCが設定されます。これにより、`sigpanic`が期待するスタックの状態が正確に再現され、スタックトレースが正しく機能するようになります。

## コアとなるコードの解説

変更は主に`ongothread`セクションに集中しています。このセクションは、Goルーチンがシグナルを受け取った際に実行されるコードパスの一部です。

**変更前:**

```assembly
 	STP.W (R1, R2), -16(RSP)
 	BL runtime·setsigsegv(SB)
 	LDP.P 16(RSP), (R1, R2)
 	MOVD R1, 8(RSP)
 	MOVD R2, R30 // link register
 	B runtime·sigpanic(SB)
```
ここでは、`STP.W (R1, R2), -16(RSP)`でR1とR2をスタックに保存し、`runtime·setsigsegv`を呼び出した後、`LDP.P 16(RSP), (R1, R2)`で復元しています。しかし、スタックフレームのサイズやLRの扱いが不適切でした。特に、`sigpanic`への呼び出しのためのスタックフレームが明示的に構築されていませんでした。

**変更後:**

```assembly
 	// Build a 32-byte stack frame for us for this call.
 	// Saved LR (none available) is at the bottom,
 	// then the PC argument for setsigsegv,
 	// then a copy of the LR for us to restore.
 	MOVD.W $0, -32(RSP) // 32バイトのスタックフレームを確保
 	MOVD R1, 8(RSP)     // R1 (PC) をスタックに保存
 	MOVD R2, 16(RSP)    // R2 (LR) をスタックに保存
 	BL runtime·setsigsegv(SB) // runtime·setsigsegv を呼び出し
 	MOVD 8(RSP), R1     // スタックからR1を復元
 	MOVD 16(RSP), R2    // スタックからR2を復元

 	// Build a 16-byte stack frame for the simulated
 	// call to sigpanic, by taking 16 bytes away from the
 	// 32-byte stack frame above.
 	// The saved LR in this frame is the LR at time of fault,
 	// and the LR on entry to sigpanic is the PC at time of fault.
 	MOVD.W R1, 16(RSP)  // R1 (PC) を sigpanic のスタックフレームのLR位置に保存
 	MOVD R2, R30        // R2 (LR) を Link Register (R30) に設定
 	B runtime·sigpanic(SB) // sigpanic へジャンプ
```

この修正では、まず`runtime·setsigsegv`を呼び出すために32バイトのスタックフレームを明示的に確保し、フォールト発生時のPCとLRをスタックに保存します。`setsigsegv`からの戻り後、これらの値を復元し、さらに`sigpanic`への呼び出しのために16バイトのスタックフレームを構築します。この16バイトのフレームでは、フォールト発生時のLRが保存され、`sigpanic`へのエントリ時のLRとしてフォールト発生時のPCが設定されます。これにより、`sigpanic`が期待するスタックの状態が正確に再現され、スタックトレースが正しく機能するようになります。

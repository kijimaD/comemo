## 元コミット内容

`compress/flate: reject invalid Huffman bit sizes`

要求された符号化ビットサイズが完全な二分木を形成しない場合、その入力を不正として拒否する。

例外：zlibおよびGoの`compress/flate`パッケージで圧縮されたファイルとの互換性のために、単一の1ビットコードを持つ退化したハフマン符号化は引き続き許可する必要がある。

Issue #10426 を更新。

## 変更の背景

このコミットの背景には、DEFLATE圧縮アルゴリズムにおけるハフマン符号の安全性と堅牢性の向上が挙げられます。ハフマン符号は、データ圧縮において非常に効率的な手法ですが、その符号表（ビットサイズ情報）が不正な場合、デコード処理が無限ループに陥ったり、予期せぬ動作を引き起こしたりする可能性があります。

具体的には、ハフマン符号のビットサイズが与えられた際に、それらが完全な二分木（プレフィックスコードの性質を満たす木構造）を構成しない場合、その符号表は不正であると判断されます。このような不正な符号表を受け入れてしまうと、デコンプレッサがクラッシュしたり、誤ったデータを生成したりする脆弱性につながる可能性があります。

このコミットは、このような潜在的な問題を未然に防ぐために、ハフマンデコーダの初期化段階でビットサイズの妥当性を厳密にチェックし、不正な入力を早期に拒否することを目的としています。これにより、`compress/flate`パッケージの堅牢性とセキュリティが向上します。

また、コミットメッセージに「Update #10426」とあることから、この変更は特定のバグ報告や脆弱性報告に対応するものである可能性が高いです。ただし、公開されているGoのIssueトラッカーで直接「#10426」を見つけることはできませんでした。これは、内部的なIssue番号であるか、非常に古いIssueである可能性があります。

## 前提知識の解説

### 1. DEFLATE圧縮アルゴリズム

DEFLATEは、Zlibやgzipなどで広く利用されているロスレスデータ圧縮アルゴリズムです。主に以下の2つの技術を組み合わせています。

*   **LZ77 (Lempel-Ziv 77)**: 繰り返し出現するバイトシーケンスを、以前に出現したシーケンスへの参照（オフセットと長さ）に置き換えることで圧縮します。
*   **ハフマン符号化 (Huffman Coding)**: LZ77によって生成されたリテラルバイト（圧縮されていないデータ）とバックリファレンス（オフセットと長さ）を、出現頻度に基づいて可変長のビット列に符号化します。出現頻度の高いシンボルには短いビット列を、低いシンボルには長いビット列を割り当てることで、全体のデータサイズを削減します。

### 2. ハフマン符号化とハフマン木

ハフマン符号化は、各シンボルに一意の可変長ビット列を割り当てることでデータを圧縮する手法です。このビット列は「プレフィックスコード」の性質を持ちます。つまり、どのシンボルのコードも、他のシンボルのコードの接頭辞（プレフィックス）になることはありません。これにより、ビット列を順に読み込むだけで、シンボルの区切りを明確に識別できます。

ハフマン符号は、ハフマン木と呼ばれる二分木によって表現されます。

*   **葉ノード**: 各シンボル（バイト値、長さ、距離など）に対応します。
*   **内部ノード**: 符号化の過程で生成される中間ノードです。
*   **木の構築**: 各シンボルの出現頻度を基に、頻度の低いものから順に結合して木を構築します。

ハフマン木が「完全な二分木」であるとは、すべてのシンボルが適切に割り当てられ、デコード時に曖昧さなくシンボルを特定できる状態を指します。もしビットサイズ情報が不完全または矛盾している場合、ハフマン木を正しく構築できず、デコード処理が失敗する可能性があります。

### 3. 退化したハフマン符号化 (Degenerate Huffman Coding)

通常、ハフマン符号化では複数のシンボルが存在し、それぞれに異なるビット長のコードが割り当てられます。しかし、特定の状況下では「退化した」ハフマン符号化が発生することがあります。

コミットメッセージで言及されている「単一の1ビットコードを持つ退化したハフマン符号化」とは、データストリーム中に実質的に1種類のシンボルしか存在しないような極端なケースを指します。この場合、その唯一のシンボルに1ビット（例: `0`）が割り当てられ、他のシンボルにはコードが割り当てられない、あるいは割り当てられても使用されない状態になります。

このような退化したケースは、特にzlibのような既存の圧縮ライブラリとの互換性を保つ上で重要です。zlibは、DEFLATE仕様に準拠しており、このような特殊なケースも正しく処理できるように設計されています。Goの`compress/flate`パッケージも、zlibとの相互運用性を確保するために、この退化したケースを例外的に許容する必要があります。

### 4. `huffmanDecoder.init` メソッド

`huffmanDecoder.init` メソッドは、ハフマンデコーダを初期化し、与えられたビットサイズ情報に基づいてデコードテーブルを構築する役割を担っています。このメソッドは、ビットサイズ配列 `bits` を入力として受け取り、それらが有効なハフマン木を形成するかどうかを検証します。

## 技術的詳細

このコミットの主要な変更点は、`huffmanDecoder.init` メソッドにおけるハフマン符号表の妥当性チェックの強化です。

従来の`huffmanDecoder.init`は、与えられたビットサイズ情報からハフマンデコードテーブルを構築していました。しかし、不正なビットサイズが与えられた場合、デコードテーブルが不完全になったり、デコード時に問題を引き起こす可能性がありました。

このコミットでは、以下の重要なチェックが追加されています。

1.  **完全な二分木の検証**:
    ハフマン符号のビットサイズが与えられたとき、それらが「完全な二分木」を形成するかどうかを検証します。これは、各ビット長に割り当てられたコードの数が、そのビット長で表現可能なコード空間を完全に埋め尽くしているかを確認することで行われます。
    具体的には、`count` 配列（各ビット長に割り当てられたシンボル数）と `nextcode` 配列（各ビット長で次に利用可能なコード値）を用いて、最終的に `code` 変数が `1 << uint(max)` (最大ビット長で表現可能な全コード数) と等しくなることを確認します。もし等しくなければ、コード空間が完全に埋められていない（つまり、完全な二分木ではない）と判断し、`false` を返して初期化を失敗させます。

2.  **退化したハフマン符号化の例外処理**:
    上記の完全な二分木の検証には例外が設けられています。それは、「単一の1ビットコードを持つ退化したハフマン符号化」です。
    `!(code == 1 && max == 1)` という条件が追加され、もし `code` が `1` で `max` が `1` の場合（つまり、唯一のシンボルに1ビットのコードが割り当てられている場合）、これは有効なケースとして扱われます。これは、zlibなどの既存の圧縮ライブラリとの互換性を保つために不可欠です。このようなケースは、データストリームが非常に単純で、実質的に1種類のシンボルしか含まれていない場合に発生します。

3.  **`sanity` フラグの導入とデバッグ支援**:
    `gen.go` と `inflate.go` の両方で、`const sanity = false` というフラグが導入されています。このフラグが `true` に設定されている場合、ハフマンテーブル構築中に追加のランタイムチェック（`panic` を伴う）が実行されます。これは、開発中にデバッグやテストを支援するためのものであり、本番環境ではパフォーマンスオーバーヘッドを避けるために `false` に設定されています。この `sanity` チェックは、テーブルのエントリが上書きされていないか、またはテーブルが完全に埋められているかなどを検証します。

これらの変更により、`compress/flate`パッケージは、不正なハフマン符号表が与えられた場合に、より堅牢にエラーを検出し、デコード処理の安定性を向上させます。

## コアとなるコードの変更箇所

### `src/compress/flate/gen.go` および `src/compress/flate/inflate.go` の `huffmanDecoder.init` メソッド

両ファイルで、`huffmanDecoder.init` メソッド内のハフマンテーブル構築ロジックが変更されています。

```go
// 変更前 (inflate.go の例)
	code := 0
	var nextcode [maxCodeLen]int
	for i := min; i <= max; i++ {
		if i == huffmanChunkBits+1 {
			// create link tables
			link := code >> 1
			if huffmanNumChunks < link {
				return false
			}
			h.links = make([][]uint32, huffmanNumChunks-link)
			for j := uint(link); j < huffmanNumChunks; j++ {
				reverse := int(reverseByte[j>>8]) | int(reverseByte[j&0xff])<<8
				reverse >>= uint(16 - huffmanChunkBits)
				off := j - uint(link)
				if sanity && h.chunks[reverse] != 0 {
					panic("impossible: overwriting existing chunk")
				}
				h.chunks[reverse] = uint32(off<<huffmanValueShift + uint(i))
				h.links[off] = make([]uint32, 1<<linkBits)
			}
		}
		n := count[i]
		nextcode[i] = code
		code += n
		code <<= 1
	}

// 変更後 (gen.go および inflate.go の両方)
	code := 0
	var nextcode [maxCodeLen]int
	for i := min; i <= max; i++ {
		code <<= 1 // 各ビット長でコードを左シフトして次のビット長のための準備
		nextcode[i] = code // 現在のビット長で次に利用可能なコードの開始点を記録
		code += count[i] // 現在のビット長に割り当てられたシンボル数を加算
	}

	// Check that the coding is complete (i.e., that we've
	// assigned all 2-to-the-max possible bit sequences).
	// Exception: To be compatible with zlib, we also need to
	// accept degenerate single-code codings.  See also
	// TestDegenerateHuffmanCoding.
	if code != 1<<uint(max) && !(code == 1 && max == 1) {
		return false
	}

	h.min = min
	if max > huffmanChunkBits {
		numLinks := 1 << (uint(max) - huffmanChunkBits)
		h.linkMask = uint32(numLinks - 1)

		// create link tables
		link := nextcode[huffmanChunkBits+1] >> 1
		h.links = make([][]uint32, huffmanNumChunks-link)
		for j := uint(link); j < huffmanNumChunks; j++ {
			reverse := int(reverseByte[j>>8]) | int(reverseByte[j&0xff])<<8
			reverse >>= uint(16 - huffmanChunkBits)
			off := j - uint(link)
			if sanity && h.chunks[reverse] != 0 {
				panic("impossible: overwriting existing chunk")
			}
			h.chunks[reverse] = uint32(off<<huffmanValueShift | (huffmanChunkBits + 1))
			h.links[off] = make([]uint32, numLinks)
		}
	}
```

## コアとなるコードの解説

変更された `huffmanDecoder.init` メソッドのコアロジックは、ハフマン符号のビット長情報からデコードテーブルを構築する際に、そのビット長情報が有効なハフマン木を形成するかどうかを厳密にチェックする点にあります。

1.  **`code` 変数の役割**:
    ループ `for i := min; i <= max; i++` の中で `code` 変数が更新されます。この `code` は、現在のビット長 `i` までのすべてのコードが占めるビット空間の合計を表します。
    *   `code <<= 1`: 各ビット長 `i` の処理を開始する前に、`code` を1ビット左シフトします。これは、次のビット長に進む際に、コード空間が2倍になることを反映しています。
    *   `nextcode[i] = code`: 現在のビット長 `i` で利用可能なコードの開始点を `nextcode[i]` に保存します。
    *   `code += count[i]`: 現在のビット長 `i` に割り当てられたシンボル数 (`count[i]`) を `code` に加算します。これにより、`code` はそのビット長までのすべてのコードが占める空間の合計を正確に追跡します。

2.  **完全性チェック**:
    ループの終了後、`if code != 1<<uint(max) && !(code == 1 && max == 1)` という条件でハフマン符号の完全性がチェックされます。
    *   `1 << uint(max)`: これは、最大ビット長 `max` で表現可能なすべての可能なコードの数を表します。例えば、`max` が8であれば `1 << 8` は256です。
    *   `code != 1<<uint(max)`: もし `code` が `1 << uint(max)` と等しくない場合、これは与えられたビットサイズ情報が完全なハフマン木を形成していないことを意味します。つまり、すべての可能なコード空間がシンボルに割り当てられていないか、あるいは重複して割り当てられている可能性があります。このような場合、`init` メソッドは `false` を返し、初期化を失敗させます。
    *   `!(code == 1 && max == 1)`: この部分は、前述の「退化したハフマン符号化」の例外処理です。もし `code` が `1` で `max` が `1` の場合（単一の1ビットコード）、この条件は `false` となり、完全性チェックの失敗条件から除外されます。これにより、zlibとの互換性が維持されます。

3.  **リンクテーブルの生成ロジックの変更**:
    `if max > huffmanChunkBits` ブロック内のリンクテーブル生成ロジックも変更されています。特に、`link := nextcode[huffmanChunkBits+1] >> 1` のように、`nextcode` 配列を利用してリンクテーブルの開始位置を計算するようになりました。これにより、より正確かつ堅牢なテーブル構築が可能になります。

これらの変更により、`compress/flate`パッケージは、不正なハフマン符号表が与えられた場合に、より堅牢にエラーを検出し、デコード処理の安定性を向上させます。

# [インデックス 27225] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）のStop-The-World（STW）ポーズ時間を大幅に削減することを目的としています。具体的には、これまでSTWマーク終了フェーズで行われていたスタックの縮小処理を、コンカレントマークフェーズ中に実行するように変更することで、特定のプログラムにおけるSTW時間を1桁削減し、10msの目標値を大きく下回る結果を達成しました。

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）プロセスにおいて、スタックの縮小（shrink）処理のタイミングを変更するものです。以前は、このスタック縮小はGCのStop-The-World（STW）マーク終了フェーズ中に実行されていました。これは、コンカレント（並行）にスタックを縮小することが安全ではないと考えられていたためです。しかし、この方式では、特に一部のプログラムにおいてSTWポーズ時間が大幅に増加するという問題がありました。スタック縮小には、コピーされるMBあたり約5ms、縮小1回あたり2µsのコストがかかっていました。

このコミットの目的は、STWを伴わずにスタックを安全に縮小できるようになったため、スタック縮小をコンカレントマークフェーズ中に実行するように変更することです。これにより、STWポーズ時間を削減し、GCの全体的なパフォーマンスを向上させます。

## 変更の背景

Goのガベージコレクタは、ユーザープログラムの実行と並行して動作するコンカレントGCを採用していますが、その動作の特定の段階では、プログラムの実行を一時停止させる「Stop-The-World (STW)」フェーズが必要です。STWフェーズは、GCの正確性と整合性を保証するために不可欠ですが、その時間が長くなるとアプリケーションの応答性やスループットに悪影響を与えます。

特に、Go 1.5で導入されたコンカレントGCは、STW時間を大幅に短縮することを目標としていました。しかし、issue #12967で報告されたように、一部のシナリオ、特に多数のゴルーチンを使用するプログラムでは、GCのマーク終了フェーズにおけるSTW時間が依然として長くなる問題が顕在化していました。この問題の主要な原因の一つが、このSTWフェーズ中に実行されていたスタックの縮小処理でした。

スタックの縮小は、ゴルーチンが使用するスタックメモリが過剰になった場合に、そのメモリを解放してシステムに返す重要な最適化です。これにより、メモリフットプリントを削減し、メモリの効率的な利用を促進します。しかし、この処理がSTW中に実行されると、そのコストが直接アプリケーションのポーズ時間として現れてしまいます。

このコミットは、スタック縮小処理がコンカレントに安全に実行できるようになったというランタイムの改善を背景に、そのタイミングをSTWフェーズからコンカレントマークフェーズへと移行することで、STWポーズ時間のさらなる削減を目指しています。これは、Goランタイムが継続的にGCのパフォーマンスとユーザーエクスペリエンスを向上させるための取り組みの一環です。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

GoのGCは、主に「三色マーキング」アルゴリズムをベースにしたコンカレント（並行）なコレクタです。
1.  **マークフェーズ (Mark Phase)**:
    *   **マーク開始 (Mark Start)**: 短いSTWフェーズ。GCルート（グローバル変数、実行中のゴルーチンのスタックなど）を特定し、それらから到達可能なオブジェクトを「灰色」にマークします。
    *   **コンカレントマーク (Concurrent Mark)**: ユーザープログラムと並行して実行されるフェーズ。灰色オブジェクトから到達可能なオブジェクトを再帰的に探索し、灰色から「黒」にマークします。新しく発見されたオブジェクトは灰色にマークされます。
    *   **マーク終了 (Mark Termination)**: 短いSTWフェーズ。コンカレントマーク中に発生した変更を処理し、GCの整合性を最終的に確保します。このフェーズで、すべての到達可能なオブジェクトが黒にマークされます。
2.  **スキャンフェーズ (Sweep Phase)**: ユーザープログラムと並行して実行されるフェーズ。黒にマークされなかった（つまり到達不可能だった）オブジェクトが占めていたメモリを解放します。

### Stop-The-World (STW)

STWは、ガベージコレクタが正確なメモリ状態を確保するために、アプリケーションのすべてのゴルーチンを一時的に停止させる期間を指します。GoのGCはSTW時間を最小限に抑えるように設計されていますが、完全に排除することはできません。STW時間が長くなると、アプリケーションの応答性が低下し、ユーザー体験が悪化する可能性があります。

### Goのスタック管理とスタックの拡大・縮小

Goのゴルーチンは、可変長のスタックを使用します。これは、必要に応じてスタックが自動的に拡大・縮小されることを意味します。
*   **スタックの拡大**: ゴルーチンがより多くのスタックメモリを必要とする場合（例: 深い関数呼び出し）、ランタイムはより大きなスタックを割り当て、既存のスタックの内容を新しいスタックにコピーします。
*   **スタックの縮小**: ゴルーチンが使用するスタックメモリが少なくなった場合、ランタイムはスタックを縮小し、未使用のメモリを解放します。これはメモリ効率の観点から重要です。

### `_Gdead` と `_Gscan` ゴルーチンステータス

Goランタイムでは、ゴルーチンは様々なステータスを持ちます。
*   `_Gdead`: ゴルーチンが終了し、再利用可能な状態にあることを示します。
*   `_Gscan`: ゴルーチンがGCによってスキャン中であることを示すフラグです。これは他のステータスと組み合わせて使用されるビットフラグです。

これらのステータスは、ランタイムがゴルーチンの状態を管理し、GCやスケジューリングの決定を行う上で重要です。

## 技術的詳細

このコミットの核心は、スタック縮小のタイミングをSTWマーク終了フェーズからコンカレントマークフェーズへと変更することです。

**以前の挙動**:
*   スタック縮小は `gcphase == _GCmarktermination` の条件で実行されていました。これは、STWマーク終了フェーズ中にのみスタック縮小が行われることを意味します。
*   この理由は、コンカレントな環境でスタックを縮小することが安全ではないという認識があったためです。スタックのコピーや移動中に、そのスタックを使用しているゴルーチンが実行されると、データ破損やクラッシュにつながる可能性がありました。

**変更後の挙動**:
*   ランタイムの改善により、STWを伴わずにスタックを安全に縮小するメカニズムが確立されました。これにより、スタック縮小をコンカレントマークフェーズ中に実行することが可能になりました。
*   `src/runtime/mgcmark.go` の `scanstack` 関数内で、`!work.markrootDone` の条件（つまり、コンカレントマークフェーズ中）で `shrinkstack(gp)` が呼び出されるようになりました。これにより、STWを待つことなく、ゴルーチンのスタックがスキャンされる際に、そのスタックが過剰に大きい場合は縮小されます。
*   `src/runtime/mgcmark.go` の `markroot` 関数内の `_GCmarktermination` フェーズでのスタック縮小ロジックは、`_Gdead` ステータスのゴルーチンのスタック解放に特化するように変更されました。これは、`_Gdead` ゴルーチンはもはや実行されていないため、そのスタックを安全に解放できるためです。
*   `src/runtime/stack.go` の `shrinkstack` 関数では、ゴルーチンのステータスチェックがより厳密になりました。特に、`gstatus&^_Gscan == _Gdead` という条件が導入され、`_Gdead` 状態のゴルーチンに対してのみスタック全体を解放するようになりました。また、`gstatus&_Gscan == 0` の場合は `throw` するガードが追加され、`shrinkstack` が呼び出されるゴルーチンは必ずスキャン中である必要があることを強制しています。これは、スタック縮小がGCプロセスの一部として安全に実行されることを保証するためです。

**効果**:
*   issue #12967で報告されたプログラムにおいて、95パーセンタイル値のマーク終了STW時間が23.8msから1.80msへと、約92.44%削減されました。これは、STWポーズ時間が10msの目標値を大きく下回ることを意味します。
*   Goの標準ベンチマーク（go1およびgarbageベンチマーク）全体では、パフォーマンスへの影響は0.5%未満のわずかな低下に留まりました。これは、STW時間の削減という大きなメリットに対して、許容範囲内のトレードオフであることを示しています。

この変更は、GoランタイムのGCがより効率的になり、特に高負荷なアプリケーションにおけるレイテンシを改善する上で重要な一歩となりました。

## コアとなるコードの解説

### `src/runtime/mgcmark.go` の変更

1.  **`markroot` 関数内の変更**:
    *   以前は `_GCmarktermination` フェーズで無条件に `shrinkstack(gp)` が呼び出されていましたが、これが `if gcphase == _GCmarktermination && status == _Gdead` という条件付きの呼び出しに変更されました。
    *   この変更により、`markroot` 関数内でのスタック縮小は、GCマーク終了フェーズにおいて、かつゴルーチンが完全に終了している (`_Gdead`) 場合にのみ行われるようになりました。これは、終了したゴルーチンのスタックを安全に解放するための処理に特化しています。

2.  **`scanstack` 関数内の変更**:
    *   新たに `if !work.markrootDone { shrinkstack(gp) }` というコードブロックが追加されました。
    *   `work.markrootDone` は、GCのルートマークが完了したかどうかを示すフラグです。この条件が `false` の場合、つまりコンカレントマークフェーズ中に、`scanstack` がゴルーチンのスタックをスキャンする際に、そのスタックが過剰に大きい場合は `shrinkstack` が呼び出されるようになりました。
    *   これにより、スタック縮小処理がSTWフェーズを待つことなく、コンカレントに実行されるようになり、STWポーズ時間の削減に貢献します。

### `src/runtime/stack.go` の変更

1.  **`shrinkstack` 関数の `_Gdead` 判定の変更**:
    *   `if readgstatus(gp) == _Gdead` が `gstatus := readgstatus(gp); if gstatus&^_Gscan == _Gdead` に変更されました。
    *   これは、ゴルーチンのステータスから `_Gscan` フラグを除外して `_Gdead` と比較することで、ゴルーチンがスキャン中であっても、その基底ステータスが `_Gdead` であればスタック全体を解放できるようにするための変更です。`_Gscan` はビットフラグであり、他のステータスと組み合わされる可能性があるため、正確な `_Gdead` 判定のためにマスク処理が導入されました。

2.  **`_Gscan` フラグのチェック追加**:
    *   `if gstatus&_Gscan == 0 { throw("bad status in shrinkstack") }` というガードが追加されました。
    *   このチェックは、`shrinkstack` 関数が呼び出されるゴルーチンは、GCによってスキャン中である (`_Gscan` フラグが立っている) ことを保証します。これにより、スタック縮小処理がGCのコンテキスト内で安全に実行されることが保証され、不適切なタイミングでの呼び出しを防ぎます。

3.  **`casgcopystack` および `casgstatus` の削除**:
    *   `oldstatus := casgcopystack(gp)` と `casgstatus(gp, _Gcopystack, oldstatus)` の行が削除されました。
    *   これらの関数は、スタックコピー中にゴルーチンのステータスを一時的に変更し、コピー完了後に元に戻すためのものでした。コンカレントなスタック縮小が安全になった新しいメカニズムでは、これらのステータス変更が不要になったか、あるいは異なる方法で安全性が確保されるようになったことを示唆しています。これにより、コードが簡素化され、オーバーヘッドが削減されます。

これらの変更は、GoランタイムがSTWポーズ時間を削減し、より効率的なGCを実現するための重要なステップであり、特に多数のゴルーチンを使用するアプリケーションのパフォーマンス向上に貢献します。

# [インデックス 20608] ファイルの概要

このコミットは、Go言語のビルドツール `cmd/go` において、C言語のソースファイルが `cgo` を使用しない限りコンパイルを禁止するという重要な変更を導入します。これは、Goコンパイラの進化と、C言語との連携における推奨されるアプローチの明確化を目的としています。

## 元コミット内容

`cmd/go: prohibit C sources files unless using cgo`

このコミットは、`cmd/go` ツールがC言語のソースファイルを、`cgo` を使用しない限り禁止することを目的としています。以前は、これらのCファイルは `6c` コンパイラによってコンパイルされていました。しかし、C言語を正しく使用することが困難になりつつあり、Cコンパイラ自体も将来的には廃止される予定であるため、現時点でそれらの利用を不可能にします。

この変更は、`go1.4.txt` の変更点として CL 145890046 で言及されています。

## 変更の背景

この変更の背景には、Go言語のコンパイラとツールチェーンの進化、およびC言語との相互運用性に関する設計思想の明確化があります。

1.  **`6c` コンパイラの廃止とGoコンパイラの自己ホスト化**:
    Go言語の初期のコンパイラはC言語で書かれており、`6c` (Plan 9 CコンパイラをベースとしたGo向けCコンパイラ)はその一部でした。しかし、Go 1.5リリースに向けて、Goコンパイラ自体をGo言語で書き直す「自己ホスト化 (self-hosting)」の取り組みが進められていました。これにより、GoのビルドプロセスからCコンパイラへの依存を減らし、ツールチェーンを簡素化し、Go言語の独立性を高めることが目標でした。このコミットは、その移行プロセスの一環として、`6c` の利用を段階的に廃止する動きを示しています。

2.  **C言語との連携の複雑性**:
    Go言語はガベージコレクションを持つランタイムと、独自のスケジューラによる軽量なゴルーチンを持っています。これに対し、C言語は手動メモリ管理とOSスレッドを基本とします。これら異なるモデルのコードを直接混在させることは、メモリ管理、スタックの扱い、並行処理の同期などにおいて複雑な問題を引き起こす可能性がありました。特に、Goのスタックは動的に伸縮するため、CコードがGoのスタック上で動作すると、スタックのコピーや拡張時に予期せぬ問題（例: `Issue7695` で示唆されたようなスタックコピーの破損）が発生するリスクがありました。

3.  **`cgo` の推奨**:
    Go言語がC言語のコードと連携するための公式かつ推奨されるメカニズムは `cgo` です。`cgo` は、GoとCの間のインターフェースを定義し、データ型の変換や関数呼び出しの橋渡しを行います。`cgo` を介することで、GoランタイムはCコードの実行を適切に管理し、Goのガベージコレクタやスケジューラとの整合性を保つことができます。このコミットは、`cgo` を使用しないCソースファイルの直接的な利用を禁止することで、C言語との連携は `cgo` を通じて行うべきであるという方針を明確にしています。これにより、開発者がGoとCを混在させる際に発生しうる潜在的な問題を未然に防ぎ、より安全で予測可能なコードベースを促進します。

4.  **Go 1.4 リリースノートへの記載**:
    コミットメッセージに「`go1.4.txt` change in CL 145890046」とあるように、この変更はGo 1.4のリリースノートに記載される予定の重要な変更でした。これは、この変更が単なる内部的な修正ではなく、Go言語のユーザーに影響を与える公式な方針転換であることを示しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とツールに関する知識が不可欠です。

1.  **Go言語のコンパイラ (`gc` と `6c`)**:
    *   **`gc` (Go Compiler)**: 現在のGo言語の標準コンパイラです。Go 1.5以降、このコンパイラ自体がGo言語で書かれています。Goのソースコードを機械語に変換する役割を担います。
    *   **`6c` (Plan 9 C Compiler for Go)**: Go言語の初期段階で、Goのランタイムや一部の低レベルなコードをコンパイルするために使用されていたCコンパイラです。Goコンパイラが自己ホスト化される以前は、Goのビルドプロセスの一部として機能していました。このコンパイラは、Goの特定のアーキテクチャ（例: `6` はamd64を指す）向けに最適化されていました。このコミットの時点では、`6c` は段階的に廃止される途中にありました。

2.  **`cgo`**:
    `cgo` は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoツールです。GoとCの間の「外国関数インターフェース (Foreign Function Interface, FFI)」を提供します。
    *   **仕組み**: Goのソースファイル内に `import "C"` という特殊なインポート文を記述し、その直前のコメントブロックにC言語のコードを埋め込むことで使用します。`cgo` ツールは、GoとCの間の呼び出し規約の違いを吸収するためのラッパーコードを生成し、GoコンパイラとCコンパイラ（通常はGCCやClang）が連携して最終的なバイナリを生成できるようにします。
    *   **利点**: 既存のCライブラリをGoから利用できる、OSの低レベルな機能にアクセスできる、パフォーマンスが重要な部分でCの最適化されたコードを利用できる、といった利点があります。
    *   **欠点**: GoとCのメモリ管理モデルの違い（GoはGC、Cは手動）、GoのゴルーチンとCのOSスレッドの間の相互作用、ビルドプロセスの複雑化、クロスコンパイルの困難さ、パフォーマンスオーバーヘッド（GoとCの境界を越える際のコスト）など、多くの複雑性と潜在的な問題が伴います。このコミットは、これらの欠点を考慮し、`cgo` を介さないCコードの利用を制限することで、Goプログラムの堅牢性と予測可能性を高めようとしています。

3.  **Goのスタック管理**:
    Go言語のゴルーチンは、非常に軽量なスタックを持ち、必要に応じて動的にスタックサイズを増減させます。これは、OSスレッドの固定スタックサイズとは異なり、数百万のゴルーチンを効率的に実行できる理由の一つです。しかし、CコードがGoのスタック上で動作する場合、Goランタイムのスタック管理メカニズムとCのスタック利用が衝突し、スタックのコピーや拡張時に問題が発生する可能性がありました。

4.  **`go test` と `test.bash`**:
    `go test` はGo言語のテストを実行するためのコマンドです。`test.bash` は、Goプロジェクトのテストスイートの一部として使用されるシェルスクリプトで、様々なテストケース（コンパイラの挙動、ツールの機能など）を実行するために使われます。このコミットでは、Cソースファイルの禁止が正しく機能するかを検証するための新しいテストケースが `test.bash` に追加されています。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/go/pkg.go` ファイル内の `Package.load` メソッドに新しい検証ロジックを追加した点にあります。

具体的には、以下の条件がすべて満たされた場合に、Goのビルドプロセスがエラーを発生させるようになります。

1.  **`p.CFiles` が空でない**: パッケージにC言語のソースファイル（`.c` 拡張子を持つファイル）が含まれている。
2.  **`!p.usesCgo()`**: パッケージが `cgo` を使用していない（つまり、`import "C"` が存在しない）。
3.  **`!p.Standard || p.ImportPath != "runtime"`**: パッケージが標準ライブラリの一部ではない、または `runtime` パッケージではない。
    *   `runtime` パッケージはGoランタイムの非常に低レベルな部分であり、歴史的にC言語で書かれたコードを含んでいました。この例外は、Goランタイムの自己ホスト化が完全に完了するまでの過渡期的な措置として設けられています。将来的には `runtime` パッケージも純粋なGoまたはアセンブリに移行することが期待されます。

このロジックが追加されることで、`cgo` を明示的に使用しない限り、GoのビルドツールはCソースファイルの存在をエラーとして扱います。エラーメッセージは「`C source files not allowed when not using cgo: <ファイル名>`」となります。

また、この変更に伴い、Goのテストスイートも更新されています。
*   `misc/cgo/test/backdoor/backdoor.go`、`misc/cgo/test/backdoor/backdoor_gccgo.go`、`misc/cgo/test/backdoor/runtime.c`、`misc/cgo/test/issue7695_test.go` といった、以前は `cgo` を介さずにCコードをテストするために使用されていたファイルが削除または変更されています。特に `issue7695_test.go` は、Goのスタック上でCコードを実行することに関連する問題（`golang.org/issue/7695` で報告された可能性のあるスタックコピーの破損）をデモするためのものでしたが、この変更によりそのようなコードは許可されなくなるため、テストも不要になりました。
*   `src/cmd/go/test.bash` には、`badc` という新しいテストケースが追加されています。このテストケースは、`cgo` を使用せずにCソースファイルを含むパッケージをビルドしようとした場合に、期待通りにエラーが発生することを確認します。
*   `src/net/empty.c` と `src/runtime/debug/debug.c` がそれぞれ `empty.s` と `debug.s` にリネームされています。これは、これらのファイルがC言語ではなくアセンブリ言語（`.s` 拡張子）で書かれていることを明確にし、Cコンパイラへの依存をさらに減らすための変更です。

## コアとなるコードの解説

`src/cmd/go/pkg.go` の `Package.load` メソッドに追加されたコードブロックがこのコミットの主要な変更点です。

```go
	// Check for C code compiled with Plan 9 C compiler.
	// No longer allowed except in runtime and runtime/cgo, for now.
	if len(p.CFiles) > 0 && !p.usesCgo() && (!p.Standard || p.ImportPath != "runtime") {
		p.Error = &PackageError{
			ImportStack: stk.copy(),
			Err:         fmt.Sprintf("C source files not allowed when not using cgo: %s", strings.Join(p.CFiles, " ")),
		}
		return p
	}
```

*   **`len(p.CFiles) > 0`**: 現在処理中のGoパッケージにC言語のソースファイル（`.c`）が含まれているかどうかをチェックします。`p.CFiles` は、Goのビルドシステムが検出したCソースファイルのリストです。
*   **`!p.usesCgo()`**: そのパッケージが `cgo` を使用しているかどうかをチェックします。`p.usesCgo()` は、パッケージのGoソースファイルに `import "C"` が含まれている場合に `true` を返します。この条件が `true` でない（つまり `cgo` を使っていない）場合、次の条件に進みます。
*   **`(!p.Standard || p.ImportPath != "runtime")`**: この条件は、例外を設けるためのものです。
    *   `p.Standard` は、そのパッケージがGoの標準ライブラリの一部であるかどうかを示します。
    *   `p.ImportPath != "runtime"` は、そのパッケージが `runtime` パッケージではないことを示します。
    *   この複合条件 `(!p.Standard || p.ImportPath != "runtime")` は、「標準ライブラリではない、**または** `runtime` パッケージではない」という意味になります。つまり、この条件が `true` になるのは、以下のいずれかの場合です。
        *   ユーザーが作成した非標準ライブラリのパッケージ。
        *   標準ライブラリだが、`runtime` パッケージではないもの。
    *   結果として、この条件全体が `true` になるのは、`runtime` パッケージ以外のすべてのパッケージです。これにより、`runtime` パッケージのみが `cgo` なしでCソースファイルを持つことが一時的に許可されます。これは、Goランタイムの低レベルな部分がまだC言語で実装されている可能性があったためです。

これらの条件がすべて満たされた場合、`PackageError` が生成され、ビルドプロセスが停止します。エラーメッセージは、どのCソースファイルが問題を引き起こしたかを明確に示します。

この変更により、Goのビルドシステムは、`cgo` を明示的に使用しない限り、GoのコードベースにCソースファイルが混入することを厳しく制限します。これは、Goのツールチェーンの簡素化、ビルドの信頼性向上、そしてGoとCの相互運用におけるベストプラクティス（`cgo` の利用）の強制を目的としています。

# [インデックス 22170] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）におけるインライン化の挙動を改善し、特に「推移的なインライン化（transitive inlining）」を可能にするものです。これにより、関数呼び出しがネストしている場合でも、コンパイラがより積極的にインライン化を行うようになり、結果として生成されるバイナリのパフォーマンスが向上します。

Author: Russ Cox <rsc@golang.org>
Date:   Tue Feb 24 12:19:01 2015 -0500

    cmd/internal/gc: transitive inlining
    
    Inlining refuses to inline bodies containing an actual function call, so that
    if that call or a child uses runtime.Caller it cannot observe
    the inlining.
    
    However, inlining was also refusing to inline bodies that contained
    function calls that were themselves inlined away. For example:
    
            func f() int {
                    return f1()
            }
    
            func f1() int {
                    return f2()
            }
    
            func f2() int {
                    return 2
            }
    
    The f2 call in f1 would be inlined, but the f1 call in f would not,
    because f1's call to f2 blocked the inlining, despite itself eventually
    being inlined away.
    
    Account properly for this kind of transitive inlining and enable.
    
    Also bump the inlining budget a bit, so that the runtime's
    heapBits.next is inlined.
    
    This reduces the time for '6g *.go' in html/template by around 12% (!).
    (For what it's worth, closing Chrome reduces the time by about 17%.)

## 元コミット内容

Goコンパイラ（`cmd/internal/gc`）において、推移的なインライン化を実装しました。

これまでのインライン化は、関数本体に実際の関数呼び出しが含まれる場合、その関数呼び出しやその子孫が`runtime.Caller`を使用する可能性を考慮し、インライン化を拒否していました。これは、インライン化によって呼び出し元の情報が失われることを防ぐためです。

しかし、このルールは、**それ自体がインライン化される関数呼び出し**が含まれる場合にも適用されていました。例えば、`f()`が`f1()`を呼び出し、`f1()`が`f2()`を呼び出すようなケースを考えます。ここで`f2()`が`f1()`にインライン化されるとしても、`f1()`が`f2()`を呼び出しているという事実が、`f1()`が`f()`にインライン化されるのを妨げていました。これは、`f1()`内の`f2()`への呼び出しが最終的にインライン化されて消滅するにもかかわらず、インライン化をブロックしていたためです。

このコミットでは、このような推移的なインライン化のケースを適切に処理し、インライン化を可能にしました。

また、インライン化の予算（`inlining budget`）をわずかに引き上げ、`runtime`パッケージの`heapBits.next`関数がインライン化されるようにしました。

この変更により、`html/template`パッケージにおける`6g *.go`のコンパイル時間が約12%短縮されました。

## 変更の背景

Goコンパイラは、プログラムの実行性能を向上させるために、関数インライン化という最適化手法を採用しています。インライン化とは、関数呼び出しの代わりに、呼び出される関数の本体を呼び出し元に直接埋め込むことで、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数の渡し、戻り値の処理など）を削減する技術です。

しかし、インライン化にはいくつかの制約があります。特に、`runtime.Caller`のような、呼び出し元の情報を取得する関数が関係する場合、インライン化によって呼び出しスタックが変化し、`runtime.Caller`が誤った情報を返す可能性があります。そのため、Goコンパイラは、`runtime.Caller`を使用する可能性のある関数や、その関数が呼び出す可能性のある関数を含むコードのインライン化を慎重に行っていました。

このコミット以前のGoコンパイラは、関数本体に「実際の」関数呼び出しが含まれる場合、その関数をインライン化しないという保守的な戦略をとっていました。この「実際の」関数呼び出しには、たとえその呼び出し先が最終的にインライン化されて消滅するような場合でも、その事実が考慮されていませんでした。

具体的には、`A -> B -> C`という関数呼び出しの連鎖があった場合、`C`が`B`にインライン化されるとしても、`B`が`C`を呼び出しているという事実だけで、`B`が`A`にインライン化されるのを妨げていました。これは、コンパイラがインライン化の判断を行う際に、まだインライン化されていない中間的な関数呼び出しの存在を過度に厳しく評価していたためです。

このような挙動は、特に小さなヘルパー関数が多段階で呼び出されるようなコードパターンにおいて、インライン化の機会を不必要に失わせ、結果として生成されるバイナリの性能を低下させる原因となっていました。このコミットは、この非効率性を解消し、より積極的なインライン化を可能にすることで、コンパイルされたGoプログラムの実行時性能をさらに向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラと最適化に関する基本的な知識が必要です。

1.  **関数インライン化 (Function Inlining)**:
    *   コンパイラ最適化の一種で、関数呼び出しのオーバーヘッドを削減するために、呼び出される関数のコードを呼び出し元の位置に直接展開することです。
    *   メリット:
        *   関数呼び出しのコスト（スタックフレームのセットアップ、レジスタの保存・復元など）を削減します。
        *   インライン化されたコードに対して、さらにコンパイラが最適化（定数畳み込み、デッドコード削除など）を適用できる機会が増えます。
    *   デメリット:
        *   コードサイズが増加する可能性があります。
        *   コンパイル時間が増加する可能性があります。
        *   デバッグが難しくなる場合があります（スタックトレースが短くなるなど）。
    *   Goコンパイラは、関数の複雑さ（コードの行数、含まれる操作の種類など）に基づいて、インライン化を行うかどうかを決定します。この複雑さを評価するための指標が「インライン化予算（inlining budget）」です。

2.  **Goコンパイラの構造 (`cmd/internal/gc`)**:
    *   `cmd/internal/gc`は、Go言語の公式コンパイラの一部であり、Goソースコードを機械語に変換する主要な役割を担っています。
    *   コンパイルプロセスは複数のフェーズに分かれており、インライン化は通常、コード生成の前の最適化フェーズで行われます。
    *   `Node`構造体: Goコンパイラ内部で、抽象構文木（AST）の各ノードを表すために使用されるデータ構造です。関数、変数、式、ステートメントなど、プログラムのあらゆる要素が`Node`として表現されます。
    *   `Sym`構造体: シンボルテーブルのエントリを表し、変数名、関数名などの識別子とその属性（型、スコープなど）を管理します。
    *   `Nbody`: 関数の本体（ステートメントのリスト）を表す`NodeList`へのポインタです。
    *   `Inl`: インライン化された関数の本体を表す`NodeList`へのポインタです。インライン化可能な関数に対して設定されます。

3.  **`runtime.Caller`**:
    *   Goの`runtime`パッケージが提供する関数で、呼び出し元の関数に関する情報を取得するために使用されます。例えば、ログ出力で呼び出し元のファイル名や行番号を表示する際などに利用されます。
    *   インライン化は呼び出しスタックを変更するため、`runtime.Caller`の正確性に影響を与える可能性があります。そのため、`runtime.Caller`が使用される可能性のあるコードパスでは、コンパイラはインライン化を避ける傾向があります。

4.  **インライン化予算 (Inlining Budget)**:
    *   Goコンパイラが関数をインライン化するかどうかを決定する際に使用する、関数の「複雑さ」を測るための数値的な閾値です。
    *   関数のASTを走査し、各操作（演算、関数呼び出し、制御フローなど）にコストを割り当て、その合計が予算内に収まる場合にインライン化を検討します。
    *   予算を超えると、その関数はインライン化されません。

5.  **抽象構文木 (Abstract Syntax Tree - AST)**:
    *   ソースコードの構造を木構造で表現したものです。コンパイラはASTを操作して、最適化やコード生成を行います。

## 技術的詳細

このコミットの核心は、Goコンパイラのインライン化ロジック、特に`cmd/internal/gc/inl.go`ファイル内の`ishairy`関数と`caninl`関数の変更にあります。

従来のインライン化ロジックでは、関数`F`がインライン化可能かどうかを判断する際、`F`の関数本体（`F.Nbody`）を走査し、その中に「実際の」関数呼び出し（`OCALLFUNC`, `OCALLMETH`など）が存在するかどうかをチェックしていました。もし存在すれば、その関数`F`はインライン化の対象から外されていました。この判断は、`runtime.Caller`の正確性を保護するためという意図がありましたが、副作用として、呼び出し先の関数が最終的にインライン化される場合でも、インライン化を妨げていました。

このコミットでは、この問題を解決するために、`ishairy`関数における関数呼び出しの扱いが変更されました。

1.  **`Node.InlCost`フィールドの追加**:
    *   `src/cmd/internal/gc/go.go`の`Node`構造体に`InlCost int32`フィールドが追加されました。このフィールドは、関数がインライン化された場合に、そのインライン化によって消費される「インライン化予算」の量を格納します。
    *   `caninl`関数が関数をインライン化可能と判断した際に、その関数の`InlCost`が計算され、`fn.Nname.InlCost = int32(maxBudget - budget)`のように設定されます。ここで`budget`は、`ishairylist`関数が関数本体を走査した後に残った予算です。つまり、`InlCost`は、その関数をインライン化するために「使われた」予算の量を示します。

2.  **`ishairy`関数における推移的インライン化の考慮**:
    *   `src/cmd/internal/gc/inl.go`の`ishairy`関数は、ノードがインライン化を妨げるほど「毛深い（hairy）」かどうかを判断します。
    *   `OCALLFUNC`（通常の関数呼び出し）と`OCALLMETH`（メソッド呼び出し）のケースが変更されました。
    *   変更前は、これらのオペレーションタイプに遭遇すると、即座に`return true`（インライン化不可）を返していました（デバッグレベルが低い場合）。
    *   変更後は、呼び出される関数（`n.Left`または`n.Left.Type.Nname`）が既にインライン化可能である（`Inl != nil`）場合、その関数の`InlCost`を現在の`budget`から減算するようになりました。
    *   これにより、呼び出し先の関数がインライン化されることが分かっている場合、その呼び出し自体はインライン化を妨げる要因とはならず、その呼び出し先のインライン化コストが現在の関数のインライン化予算に加算される形になります。
    *   もし呼び出される関数がインライン化可能でない場合、または予算が足りない場合は、引き続きインライン化が拒否されます。

3.  **インライン化予算の増加**:
    *   `caninl`関数内で定義されているインライン化予算の初期値が`40`から`80`に引き上げられました（`maxBudget`定数として定義）。これにより、より複雑な関数もインライン化の対象となる可能性が高まりました。
    *   特に、コミットメッセージで言及されている`runtime.heapBits.next`のような、これまで予算オーバーでインライン化されなかった関数がインライン化されるようになりました。

4.  **`mkinlcall1`関数の変更**:
    *   `mkinlcall1`関数は、実際にインライン化されたコードを生成する部分です。この関数内の推移的インライン化に関するコメントとロジックが更新されました。
    *   以前は`Debug['l'] >= 5`の条件付きで推移的インライン化の処理が行われていましたが、この条件が削除され、常に推移的インライン化が適用されるようになりました。これは、インライン化された関数本体内の`OINLCALL`（インライン化された呼び出し）ノードを再帰的に展開する処理です。

5.  **`lex.go`におけるインライン化処理の順序変更**:
    *   `Main`関数内のインライン化処理のループが`visitBottomUp`ヘルパー関数を使用するように変更されました。
    *   以前は、まずすべての関数に対して`caninl`を呼び出し、次にすべての関数に対して`inlcalls`を呼び出すという2段階のループでした。
    *   変更後は、`visitBottomUp`を使ってASTをボトムアップで走査し、各関数に対して`caninl`と`inlcalls`を連続して呼び出すようになりました。これにより、子関数がインライン化可能であると判断された後、すぐに親関数がその情報を利用してインライン化を検討できるようになり、推移的インライン化がより効果的に機能するようになりました。

これらの変更により、コンパイラは関数呼び出しの連鎖において、途中の関数がインライン化されることを予測し、そのコストを考慮に入れることで、より深いレベルでのインライン化を可能にしました。

    *   変更前は、これらの呼び出しが存在すると、デバッグレベルが低い限りはインライン化を拒否していました。
    *   変更後は、呼び出される関数（`n.Left`または`n.Left.Type.Nname`）が既にインライン化可能である（`Inl != nil`）場合、その関数の`InlCost`を現在の`budget`から減算します。これは、その呼び出しがインライン化によって消滅するため、そのコストを現在の関数の予算に含めることができるという考え方に基づいています。
    *   これにより、`f() -> f1() -> f2()`の例で、`f1()`が`f2()`を呼び出していても、`f2()`がインライン化可能であれば、`f1()`のインライン化がブロックされなくなります。

*   **`mkinlcall1`関数**:
    *   インライン化された呼び出しを展開するロジックが含まれています。
    *   以前は`if Debug['l'] >= 5`という条件付きで推移的インライン化の処理が行われていましたが、この条件が削除され、常にこの処理が実行されるようになりました。これは、インライン化された関数本体内の`OINLCALL`ノード（インライン化された関数呼び出しを表す）を再帰的に展開し、最終的なコードに変換する役割を担います。

### `src/cmd/internal/gc/lex.go`

*   `Main`関数内のインライン化処理のループが変更されました。
*   以前は、`caninl`と`inlcalls`が別々のループで、すべての関数に対して順次実行されていました。
*   新しいコードでは、`visitBottomUp`ヘルパー関数が導入され、ASTをボトムアップ（子ノードから親ノードへ）で走査しながら、各関数に対して`caninl`と`inlcalls`を連続して呼び出すようになりました。
*   この変更は、推移的インライン化を効果的に機能させる上で非常に重要です。子関数がインライン化可能であると判断され、その`InlCost`が設定された後、すぐに親関数がその情報を利用して自身のインライン化を検討できるようになるためです。これにより、インライン化の機会が最大限に活用されます。

これらの変更の組み合わせにより、Goコンパイラは、関数呼び出しの連鎖において、より深いレベルでのインライン化を正確に判断し、適用できるようになりました。

# [インデックス 21750] ファイルの概要

このコミットは、Goランタイムにおける`m.gcing`フィールドの名称を`m.preemptoff`に変更し、その型を整数から文字列に修正するものです。これにより、Goスケジューラにおけるプリエンプション（横取り）無効化の意図がより明確になり、将来的なガベージコレクタの改善（プリエンプション可能化）に備えるための基盤が構築されます。

## 元コミット内容

```
runtime: rename m.gcing to m.preemptoff and make it a string

m.gcing has become overloaded to mean "don't preempt this g" in
general. Once the garbage collector is preemptible, the one thing it
*won't* mean is that we're in the garbage collector.

So, rename gcing to "preemptoff" and make it a string giving a reason
that preemption is disabled. gcing was never set to anything but 0 or
1, so we don't have to worry about there being a stack of reasons.

Change-Id: I4337c29e8e942e7aa4f106fc29597e1b5de4ef46
Reviewed-on: https://go-review.googlesource.com/3660
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

Goランタイムには、特定の重要な処理中にGoルーチンがプリエンプション（実行の横取り）されないようにするためのメカニズムが存在します。以前は、`m.gcing`というフィールドがこの目的で使用されていました。このフィールドは元々、ガベージコレクション（GC）が実行中であることを示し、GC中のGoルーチンのプリエンプションを防ぐために設計されていました。

しかし、この`m.gcing`フィールドは、GC中であることだけでなく、「このGoルーチンをプリエンプションしてはならない」という一般的な意味合いで広く使われるようになっていました。つまり、GC以外の理由でプリエンプションを無効にしたい場合にも、この`m.gcing`が利用されていたのです。

Goの将来的な計画として、ガベージコレクタ自体をプリエンプション可能にするという目標がありました。もしGCがプリエンプション可能になった場合、`m.gcing`という名前のフィールドが「GC中であるためプリエンプションを無効にする」という意味を持つことは、その本来の意図と矛盾してしまいます。GCがプリエンプション可能であれば、`m.gcing`が`1`であってもプリエンプションが起こりうる、あるいは`m.gcing`が`1`であること自体がGC中であることを正確に示さなくなる可能性があるためです。

このコミットは、このような意味のオーバーロードと将来的な矛盾を解消するために導入されました。プリエンプションを無効にする真の理由をより正確に表現できるよう、フィールドの名称と型が変更されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

### Goスケジューラ (M, P, Gモデル)

Goランタイムは、M（Machine）、P（Processor）、G（Goroutine）という3つの主要な抽象化を用いてGoルーチンをスケジューリングします。
*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。Goプログラムの並行処理の単位となります。
*   **M (Machine)**: オペレーティングシステムのスレッド（OSスレッド）を表します。GoルーチンはM上で実行されます。
*   **P (Processor)**: MとGを仲介する論理的なプロセッサです。Pは実行可能なGoルーチンのキューを保持し、MにGoルーチンを供給します。MはPにアタッチされ、PのキューからGoルーチンを取り出して実行します。

### プリエンプション（Preemption）

プリエンプションとは、実行中のGoルーチンを強制的に中断し、別のGoルーチンにCPUの実行権を渡すメカニズムです。これにより、Goランタイムは多数のGoルーチンを効率的に多重化し、公平にCPU時間を割り当てることができます。Goは協調的スケジューリングと非協調的スケジューリング（プリエンプション）の両方を使用します。

しかし、ランタイムの特定のクリティカルなセクション（例えば、メモリ割り当て、ガベージコレクションの特定のフェーズ、OSコールなど）では、データの一貫性を保つためや、処理が中断されると問題が発生するため、プリエンプションを一時的に無効にする必要があります。

### ガベージコレクション (GC) と Stop-the-World (STW)

Goのガベージコレクタは、不要になったメモリを自動的に解放する役割を担います。GoのGCは並行的に動作しますが、特定のフェーズでは「Stop-the-World (STW)」という状態に入ります。STWフェーズでは、すべてのGoルーチンの実行が一時的に停止され、GCが安全にメモリをスキャン・マーク・コンパクションなどの処理を行います。このSTWフェーズ中は、GoルーチンがプリエンプションされるとGCの整合性が損なわれる可能性があるため、プリエンプションを無効にする必要があります。

### `m.gcing` フィールド

このコミット以前は、`runtime/runtime2.go`の`m`構造体には`gcing int32`というフィールドがありました。このフィールドは、Mがガベージコレクションに関連するクリティカルなセクションにいるかどうかを示すために使用されていました。`0`はGC中ではないことを、`1`はGC中であることを示していました。しかし、前述の通り、GC以外のプリエンプション無効化の目的でも使われるようになり、その意味が曖昧になっていました。

## 技術的詳細

このコミットの核心は、`m`構造体内の`gcing`フィールドを`preemptoff`という新しいフィールドに置き換え、その型を`int32`から`string`に変更した点です。

*   **フィールド名の変更**: `m.gcing`から`m.preemptoff`へ。
    *   `gcing`（"garbage collecting"の略）という名前は、GCに特化した意味合いが強く、GC以外の理由でプリエンプションを無効にする場合に誤解を招く可能性がありました。
    *   `preemptoff`（"preemption off"の略）という新しい名前は、「プリエンプションが無効になっている」という状態をより直接的かつ一般的に表現します。これにより、GCの文脈に限定されず、ランタイムの様々なクリティカルセクションでプリエンプションを無効にする目的で利用できることが明確になります。

*   **型の変更**: `int32`から`string`へ。
    *   以前の`int32`型（実質的には`0`または`1`のブーリアンとして使用）では、プリエンプションが無効になっている「理由」を表現できませんでした。
    *   新しい`string`型は、プリエンプションが無効になっている具体的な理由を記述できるようになります。例えば、`"GOMAXPROCS"`、`"gcing"`、`"read mem stats"`、`"profile"`、`"stack trace"`、`"start tracing"`、`"stop tracing"`といった文字列がコード中で設定されています。これにより、デバッグ時やプロファイリング時に、なぜ特定のGoルーチンがプリエンプションされていないのかを容易に特定できるようになります。
    *   コミットメッセージにあるように、`gcing`は`0`か`1`しか設定されていなかったため、複数の理由をスタックするような複雑なロジックは不要であり、単一の文字列で理由を表現するだけで十分と判断されました。

この変更は、Goランタイムのプリエンプション制御をより汎用的かつ透過的にするための重要なステップです。特に、将来的にGCがプリエンプション可能になった場合でも、`m.preemptoff`フィールドは「GC中だからプリエンプションを無効にする」という特定の意味合いに縛られることなく、「何らかの理由でプリエンプションが無効になっている」という状態を正確に表現し続けることができます。

## コアとなるコードの変更箇所

このコミットでは、`src/runtime/runtime2.go`における`m`構造体の定義が変更され、それに伴い`m.gcing`を参照していたGoランタイム内の多数のファイルが`m.preemptoff`を参照するように修正されています。

変更された主なファイルと変更内容は以下の通りです。

*   `src/runtime/debug.go`: `GOMAXPROCS`関数内で、`m.gcing = 1`が`m.preemptoff = "GOMAXPROCS"`に、`m.gcing = 0`が`m.preemptoff = ""`に変更。
*   `src/runtime/lock_futex.go`, `src/runtime/lock_sema.go`: `notetsleep`関数内で、`gp.m.g0 && gp.m.gcing == 0`という条件が`gp.m.g0 && gp.m.preemptoff != ""`に変更。これは、`gcing == 0`が「プリエンプション無効ではない」を意味していたのに対し、`preemptoff != ""`が「プリエンプション無効である」を意味するため、条件が反転している点に注意。
*   `src/runtime/malloc.go`: `gcwork`関数内で、GC関連の処理中に`m.gcing = 1`が`m.preemptoff = "gcing"`に、終了時に`m.gcing = 0`が`m.preemptoff = ""`に変更。
*   `src/runtime/mem.go`: `ReadMemStats`および`runtime_debug_WriteHeapDump`関数内で、`m.gcing = 1`がそれぞれ`m.preemptoff = "read mem stats"`、`m.preemptoff = "write heap dump"`に変更され、終了時に`m.gcing = 0`が`m.preemptoff = ""`に変更。
*   `src/runtime/mgc.go`: コメント内で、プリエンプション無効化の一般的なパターンとして`m.gcing = 1`が`m.preemptoff = "reason"`に、`m.gcing = 0`が`m.preemptoff = ""`に更新。
*   `src/runtime/mprof.go`: `GoroutineProfile`および`Stack`関数内で、プロファイリングやスタックトレース取得中に`m.gcing = 1`がそれぞれ`m.preemptoff = "profile"`、`m.preemptoff = "stack trace"`に変更され、終了時に`m.gcing = 0`が`m.preemptoff = ""`に変更。
*   `src/runtime/panic.go`: パニック発生時のチェックで、`gp.m.gcing != 0`が`gp.m.preemptoff != ""`に変更され、プリエンプション無効化中のパニック時にその理由を出力するロジックが追加。
*   `src/runtime/panic1.go`: `canpanic`関数内で、パニック可能かどうかのチェック条件に`_m_.gcing != 0`が`_m_.preemptoff != ""`に変更。
*   `src/runtime/proc1.go`: シグナルプロファイリングやスケジューラトレースの出力で、`mp.gcing`が`mp.preemptoff`に変更。
*   `src/runtime/runtime2.go`: `m`構造体の定義で、`gcing int32`が`preemptoff string // if != "", keep curg running on this m`に変更。
*   `src/runtime/stack1.go`: スタック割り当て/解放、および`newstack`関数内で、プリエンプションを避けるべき条件として`thisg.m.gcing != 0`が`thisg.m.preemptoff != ""`に変更。
*   `src/runtime/trace.go`: トレース開始/停止処理中に、`m.gcing = 1`がそれぞれ`m.preemptoff = "start tracing"`、`m.preemptoff = "stop tracing"`に変更され、終了時に`m.gcing = 0`が`m.preemptoff = ""`に変更。

## コアとなるコードの解説

最も重要な変更は、`src/runtime/runtime2.go`における`m`構造体の定義です。

**変更前 (`src/runtime/runtime2.go`)**:
```go
type m struct {
    // ...
    gcing         int32
    // ...
}
```
`gcing`は`int32`型で、主に`0`（false）または`1`（true）として使用され、MがGC関連のクリティカルセクションにいるかどうかを示していました。

**変更後 (`src/runtime/runtime2.go`)**:
```go
type m struct {
    // ...
    preemptoff    string // if != "", keep curg running on this m
    // ...
}
```
`gcing`が`preemptoff`にリネームされ、型が`string`になりました。コメント`// if != "", keep curg running on this m`は、このフィールドが空文字列でない場合に、現在のGoルーチン（`curg`）がこのM上で実行され続けるべきであり、プリエンプションされるべきではないことを明確に示しています。

他のファイルでの変更は、この`m.gcing`から`m.preemptoff`への置き換えと、値の`0/1`から具体的な理由を示す文字列への変更です。

例えば、`src/runtime/debug.go`の`GOMAXPROCS`関数内の変更を見てみましょう。

**変更前 (`src/runtime/debug.go`)**:
```go
func GOMAXPROCS(n int) int {
    // ...
    gp := getg()
    gp.m.gcing = 1 // プリエンプションを無効化
    systemstack(stoptheworld)

    // ...

    gp.m.gcing = 0 // プリエンプションを有効化
    // ...
}
```
ここでは、`GOMAXPROCS`の処理中に`gp.m.gcing`を`1`に設定することで、プリエンプションを一時的に無効にしていました。

**変更後 (`src/runtime/debug.go`)**:
```go
func GOMAXPROCS(n int) int {
    // ...
    gp := getg()
    gp.m.preemptoff = "GOMAXPROCS" // プリエンプションを無効化し、理由を明記
    systemstack(stoptheworld)

    // ...

    gp.m.preemptoff = "" // プリエンプションを有効化
    // ...
}
```
`gp.m.gcing = 1`が`gp.m.preemptoff = "GOMAXPROCS"`に変わりました。これにより、`GOMAXPROCS`の処理がプリエンプションを無効にしていることが、文字列として明確に示されます。処理が完了すると、`gp.m.preemptoff`は空文字列に戻され、プリエンプションが再び有効になります。

また、`src/runtime/panic.go`におけるパニック時のチェックの変更も注目に値します。

**変更前 (`src/runtime/panic.go`)**:
```go
func gopanic(e interface{}) {
    // ...
    if gp.m.gcing != 0 {
        print("panic: ")
        printany(e)
        print("\n")
        throw("panic during gc") // GC中にパニックが発生した場合
    }
    // ...
}
```
GC中にパニックが発生した場合に特定のエラーをスローしていました。

**変更後 (`src/runtime/panic.go`)**:
```go
func gopanic(e interface{}) {
    // ...
    if gp.m.preemptoff != "" {
        print("panic: ")
        printany(e)
        print("\n")
        print("preempt off reason: ") // プリエンプション無効の理由を出力
        print(gp.m.preemptoff)
        print("\n")
        throw("panic during preemptoff") // プリエンプション無効中にパニックが発生した場合
    }
    // ...
}
```
`gp.m.gcing != 0`が`gp.m.preemptoff != ""`に変わり、さらに`preempt off reason: `というメッセージとともに`gp.m.preemptoff`の値（つまり、プリエンプション無効の理由）が出力されるようになりました。これにより、デバッグ時にパニックが発生した状況をより詳細に把握できるようになります。

これらの変更は、Goランタイムの内部状態をより正確に表現し、デバッグや将来的な機能拡張（特にプリエンプション可能なGC）を容易にするための基盤を強化するものです。

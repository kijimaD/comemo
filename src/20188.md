# [インデックス 20188] ファイルの概要

本コミットは、GoランタイムにおけるARMアーキテクチャ向けのビルド問題を修正するものです。具体的には、`src/pkg/runtime/asm_arm.s`ファイル内の`runtime·gocputicks`アセンブリ関数のスタックフレーム操作を修正し、ARM環境でのGoプログラムのビルドが正常に行われるようにします。

## コミット

GoランタイムのARMビルドを修正。

[https://github.com/golang/go/commit/22af2b8ee0194f952262a63e69ef1e9c5a638ac8](https://github.com/golang/go/commit/22af2b8ee0194f952262a63e69ef1e9c5a638ac8)

## 変更の背景

このコミットが行われた背景には、GoランタイムがARMアーキテクチャ上で正しくビルドできない問題が存在していました。Goは様々なアーキテクチャをサポートしていますが、それぞれのアーキテクチャには固有のレジスタセット、命令セット、そして関数呼び出し規約（ABI: Application Binary Interface）が存在します。Goランタイムのアセンブリコードは、これらのアーキテクチャ固有の特性に厳密に準拠して記述される必要があります。

`src/pkg/runtime/asm_arm.s`は、GoランタイムのARMアセンブリコードを含むファイルであり、低レベルな操作（例えば、コンテキストスイッチ、スタック管理、システムコールなど）を直接ハードウェアとやり取りするために使用されます。このファイル内の`runtime·gocputicks`関数におけるスタックポインタ（SP）とフレームポインタ（FP）の誤った使用、またはGoのARM ABIに準拠しないスタックフレームの操作が、ビルドプロセス中にエラーを引き起こしていたと考えられます。

具体的には、`runtime·cputicks`というCPUティック数を取得する関数を呼び出す前のスタック操作が不適切であったため、コンパイラやリンカが期待する形式のコードを生成できず、結果としてARM環境でのGoプログラムのビルドが失敗していました。このコミットは、その不整合を解消し、ARMビルドの健全性を回復することを目的としています。

## 前提知識の解説

本コミットの理解には、以下の技術的知識が役立ちます。

*   **ARMアーキテクチャ**:
    *   **レジスタ**: ARMプロセッサは、汎用レジスタ（R0-R12）、スタックポインタ（SP/R13）、リンクレジスタ（LR/R14）、プログラムカウンタ（PC/R15）などを持っています。特にSPはスタックの現在位置を示し、関数呼び出しやローカル変数の確保に不可欠です。
    *   **命令セット**: `MOVW` (Move Word), `ADD` (Add), `BL` (Branch with Link) など、基本的なアセンブリ命令。
    *   **関数呼び出し規約 (ABI)**: 関数がどのように引数を受け取り、戻り値を返し、レジスタを保存・復元するかを定めた規約。Goは独自のABIを持つことが多く、C言語のABIとは異なる場合があります。
*   **Goランタイム**:
    *   Goプログラムの実行を管理する低レベルな部分です。これには、ゴルーチンのスケジューリング、ガベージコレクション、メモリ管理、スタック管理、システムコールなどが含まれます。ランタイムの大部分はGoで書かれていますが、パフォーマンスが重要であったり、ハードウェアと直接やり取りする必要がある部分はアセンブリ言語で書かれています。
    *   **スタック管理**: Goのゴルーチンは、動的にサイズが変更されるスタックを持っています。関数呼び出し時には、引数、戻りアドレス、ローカル変数などがスタックに積まれます。
*   **Goアセンブリ言語**:
    *   Goは、独自の擬似アセンブリ言語を使用します。これは、特定のアセンブラ（例: GASやNASM）に依存しないように設計されています。
    *   **`TEXT`ディレクティブ**: Goアセンブリで関数を定義するために使用されます。例: `TEXT runtime·gocputicks(SB),NOSPLIT,$4-8`
        *   `runtime·gocputicks`: 関数名。`·`はパッケージと関数名を区切るGoアセンブリ特有の記号です。
        *   `SB` (Static Base): グローバルシンボルや静的データへの参照に使用される擬似レジスタ。
        *   `NOSPLIT`: この関数がスタックの拡張チェックを行わないことを示します。これは、スタックフレームが非常に小さいか、スタックの拡張が不要な場合にパフォーマンスのために使用されます。
        *   `$4-8`: スタックフレームのサイズと引数のサイズを示します。`$framesize-argsize`の形式で、`framesize`はローカル変数やレジスタ保存に使用されるスタック領域のサイズ、`argsize`は関数が受け取る引数の合計サイズです。
    *   **`SP` (Stack Pointer)**: 現在のスタックトップを指す擬似レジスタ。
    *   **`FP` (Frame Pointer)**: 現在のスタックフレームのベースを指す擬似レジスタ。引数や戻り値は`FP`からのオフセットでアクセスされることが多いです。
    *   **`ret_lo`**: 戻り値の下位ワード（32ビット）を指すシンボル。Goの関数は複数の戻り値を返すことができ、また64ビット値を返す場合、それらは通常、スタック上の特定の場所に配置されます。

## 技術的詳細

このコミットの核心は、`runtime·gocputicks`関数におけるスタックフレームの操作の修正です。この関数は、`runtime·cputicks`という実際のCPUティック数を取得する関数を呼び出すためのラッパーです。

元のコードでは、`runtime·cputicks`を呼び出す前に、以下のようなスタック操作を行っていました。

```armasm
TEXT runtime·gocputicks(SB),NOSPLIT,$4-8
    ADD     $8, SP, R0  // SPに8を加算した値をR0に格納
    MOVW    R0, 0(SP)   // R0の値をSPが指すアドレスに格納
    BL      runtime·cputicks(SB)
    RET
```

この`ADD $8, SP, R0`と`MOVW R0, 0(SP)`の組み合わせは、スタックポインタの値を8バイト進めたアドレスを`R0`に格納し、その`R0`の値を再び現在のスタックポインタが指す位置に書き戻すという、一見すると無意味な、あるいは誤ったスタック操作に見えます。これは、GoのARM ABIにおける関数呼び出し規約や戻り値の配置方法と矛盾していた可能性が高いです。特に`NOSPLIT`関数では、スタックフレームのサイズが固定されており、このような不適切なスタック操作は、スタックの破損や、`runtime·cputicks`が期待する引数や戻り値の場所の不整合を引き起こし、結果としてビルドエラーや実行時エラーにつながります。

修正後のコードは以下のようになります。

```armasm
TEXT runtime·gocputicks(SB),NOSPLIT,$4-8
    MOVW    $ret_lo+0(FP), R0 // ret_loのアドレス（FPからのオフセット）をR0に格納
    MOVW    R0, 4(R13)        // R0の値をR13（ARMのSP）から4バイトオフセットしたアドレスに格納
    BL      runtime·cputicks(SB)
    RET
```

この変更は、GoのARM ABIに準拠した戻り値の配置方法を反映しています。
*   `MOVW $ret_lo+0(FP), R0`: `ret_lo`は、`runtime·cputicks`が返す64ビット値（CPUティック数）の下位32ビットが格納されるべきスタック上の場所を指すシンボルです。`FP`からのオフセットでそのアドレスを取得し、`R0`レジスタに格納します。これは、`runtime·cputicks`が戻り値を書き込むべき場所を`R0`を通じて伝える、あるいは`R0`が戻り値のポインタとして使用されることを示唆しています。
*   `MOVW R0, 4(R13)`: `R13`はARMアーキテクチャにおけるスタックポインタ（SP）レジスタです。この命令は、`R0`に格納されたアドレスを、現在のスタックポインタから4バイトオフセットした位置に格納します。これは、`runtime·cputicks`が戻り値を書き込むためのスタック上の領域を適切に設定していることを意味します。GoのABIでは、関数が返す値がレジスタに収まらない場合や、特定の規約に従う必要がある場合に、スタック上に戻り値の領域を確保し、そのアドレスを呼び出し元に伝えることがあります。

この修正により、`runtime·gocputicks`は`runtime·cputicks`が期待するスタックフレームの状態を正しく設定できるようになり、ARM環境でのGoランタイムのビルドが成功するようになりました。

## コアとなるコードの解説

変更は`runtime·gocputicks`関数内で行われています。

*   **削除された行**:
    *   `ADD $8, SP, R0`: スタックポインタ`SP`に8バイトを加算した結果を`R0`レジスタに格納していました。これは、スタック上の特定のアドレスを計算しようとしていた可能性がありますが、GoのARM ABIの文脈では不適切でした。
    *   `MOVW R0, 0(SP)`: `R0`レジスタの値を、現在のスタックポインタ`SP`が指すアドレス（スタックトップ）に格納していました。この操作は、スタックフレームの整合性を損なう可能性がありました。

*   **追加された行**:
    *   `MOVW $ret_lo+0(FP), R0`: `ret_lo`は、`runtime·cputicks`関数が返す64ビットのCPUティック数の下位32ビットが格納されるべきスタック上の場所を示すシンボルです。この命令は、フレームポインタ`FP`からのオフセットで`ret_lo`のアドレスを計算し、そのアドレスを`R0`レジスタに格納します。これは、`runtime·cputicks`が戻り値を書き込むためのポインタを`R0`に設定していることを示唆しています。
    *   `MOVW R0, 4(R13)`: `R13`はARMアーキテクチャのスタックポインタ（SP）レジスタです。この命令は、`R0`に格納されたアドレス（`ret_lo`のアドレス）を、`R13`が指すアドレスから4バイトオフセットした位置に格納します。これは、`runtime·cputicks`が戻り値を書き込むためのスタック上の領域を適切に設定するための操作です。GoのABIでは、関数が複数の戻り値を返す場合や、64ビット値を返す場合に、スタック上にそのための領域を確保し、そのアドレスを呼び出し元に伝えることがあります。

これらの変更により、`runtime·gocputicks`は`runtime·cputicks`の呼び出し規約に正しく従い、戻り値がスタック上の適切な場所に配置されるようになりました。これにより、ARM環境でのGoランタイムのビルド問題が解決されました。

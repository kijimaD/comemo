## 変更の背景

GoのHTTPサーバーにおいて、リクエストを処理するハンドラ内で予期せぬパニックが発生した場合、サーバーは通常、そのリクエストの処理を中断し、接続を閉じます。この挙動は、サーバー全体の安定性を保つ上で重要ですが、クライアント側がこの接続中断をどのように認識し、エラーとして処理できるかは、アプリケーションの堅牢性にとって非常に重要です。

このコミットが追加された背景には、おそらく、ハンドラ内でパニックが発生した際に、クライアントがエラーを適切に検知できない、あるいは誤った挙動を示す可能性があったため、その挙動を明確にし、テストで保証する必要があったと考えられます。特に、レスポンスの一部が既にクライアントに送信された後にパニックが発生するようなエッジケースにおいて、クライアントが残りのボディを読み込もうとした際にエラーを受け取ることを保証することが目的です。これにより、`net/http`サーバーの堅牢性と、そのエラー処理の予測可能性が向上します。

## 前提知識の解説

### Goの`panic`と`recover`

Go言語には、プログラムの異常終了を扱うための`panic`と`recover`というメカニズムがあります。
*   **`panic`**: 実行時エラーやプログラマが意図的に発生させることで、通常のプログラムフローを中断させます。`panic`が発生すると、現在のゴルーチンは実行を停止し、遅延関数（`defer`）が実行されながらスタックを巻き戻します。もしスタックの最上位まで`panic`が到達すると、プログラム全体がクラッシュします。
*   **`recover`**: `defer`関数内で呼び出すことで、`panic`からの回復を試みることができます。`recover`が呼び出されると、`panic`の引数を返し、プログラムの実行を再開させることができます。HTTPサーバーのような長時間稼働するサービスでは、個々のリクエストハンドラ内で発生した`panic`がサーバー全体を停止させないように、`recover`を使って処理を継続させることが一般的です。`net/http`パッケージのサーバーは、デフォルトでハンドラ内のパニックを`recover`し、接続を適切にクローズするようになっています。

### HTTPハンドラの動作

`net/http`パッケージでは、`http.Handler`インターフェース（または`http.HandlerFunc`型）を実装することで、HTTPリクエストを処理するハンドラを定義します。ハンドラは`ServeHTTP(w http.ResponseWriter, r *http.Request)`メソッドを持ち、`http.ResponseWriter`を通じてクライアントに応答を書き込み、`*http.Request`からリクエスト情報を読み取ります。

### `http.ResponseWriter`と`http.Flusher`インターフェース

*   **`http.ResponseWriter`**: クライアントへのHTTPレスポンスを構築するために使用されるインターフェースです。ヘッダーの設定、ステータスコードの書き込み、レスポンスボディの書き込みなどを行います。
*   **`http.Flusher`**: `http.ResponseWriter`が実装する可能性のあるオプションのインターフェースです。このインターフェースを実装している場合、`Flush()`メソッドを呼び出すことで、バッファリングされているレスポンスデータを強制的にクライアントに送信できます。これは、サーバーが処理を完了する前に、一部のデータをクライアントにストリーミングしたい場合などに有用です。

### HTTP/1.1とHTTP/2

HTTP/1.1とHTTP/2は、HTTPプロトコルの異なるバージョンです。
*   **HTTP/1.1**: リクエストとレスポンスが順番に処理され、通常は1つのTCP接続で1つのリクエスト/レスポンスが行われます（Keep-Aliveにより再利用されることもあります）。エラーが発生した場合、接続全体が閉じられることが多いです。
*   **HTTP/2**: 多重化（Multiplexing）をサポートし、1つのTCP接続上で複数のリクエストとレスポンスを並行して処理できます。これにより、ヘッドオブラインブロッキングが軽減され、パフォーマンスが向上します。エラー処理もストリーム単位で行われることが多く、1つのストリームのエラーが他のストリームに影響を与えにくい設計になっています。

このテストでは、両方のプロトコルモードでパニック時の挙動を確認することで、`net/http`サーバーがプロトコルに依存せず一貫したエラーシグナルをクライアントに送ることを保証しています。

## 技術的詳細

このテストの核心は、HTTPハンドラがレスポンスの一部をクライアントに送信（フラッシュ）した直後に`panic`を発生させた場合に、クライアントがその後のボディの読み込みでエラーを受け取ることを検証することです。

1.  **テストのセットアップ**:
    *   `newClientServerTest`関数を使用して、HTTP/1.1 (`h1Mode`) と HTTP/2 (`h2Mode`) の両方でテストサーバーとクライアントのペアをセットアップします。
    *   カスタムハンドラが定義され、このハンドラがテストの主要なロジックを含みます。
2.  **ハンドラの挙動**:
    *   ハンドラはまず、`io.WriteString(w, msg)`で`"hello"`というメッセージをレスポンスボディに書き込みます。
    *   次に、`w.(Flusher).Flush()`を呼び出して、書き込んだメッセージを強制的にクライアントに送信します。これにより、クライアントはレスポンスボディの一部を正常に受信します。
    *   `Flush()`の直後に`panic("no more")`を呼び出し、意図的にパニックを発生させます。このパニックは、サーバーがこのリクエストの処理を中断し、クライアントへの接続を閉じる原因となります。
3.  **クライアントの挙動**:
    *   クライアントは`cst.c.Get(cst.ts.URL)`でサーバーにリクエストを送信します。
    *   レスポンスヘッダーと一部のボディ（`"hello"`）を受け取った後、`ioutil.ReadAll(res.Body)`を呼び出して残りのレスポンスボディを読み込もうとします。
4.  **検証**:
    *   `string(slurp) != msg`のチェックにより、クライアントが`"hello"`メッセージを正しく受信したことを確認します。これは、パニックが発生する前にデータがフラッシュされたことを意味します。
    *   `err == nil`のチェックにより、`ioutil.ReadAll(res.Body)`がエラーを返したことを確認します。これは、サーバーがパニックによって接続を中断し、クライアントがボディの残りを読み込めなかったことを示します。もしエラーが返されなかった場合、それはクライアントがサーバーの異常終了を検知できなかったことを意味し、テストは失敗します。

このテストは、`net/http`サーバーがハンドラ内のパニックに対して堅牢であり、クライアントがその異常を適切に処理できるようなシグナルを受け取ることを保証するための重要な側面をカバーしています。

3.  **クライアントの挙動**:
    *   クライアントは`cst.c.Get(cst.ts.URL)`でサーバーにリクエストを送信します。
    *   レスポンスヘッダーと一部のボディ（`"hello"`）を受け取った後、`ioutil.ReadAll(res.Body)`を呼び出して残りのレスポンスボディを読み込もうとします。
4.  **検証**:
    *   `string(slurp) != msg`のチェックにより、クライアントが`"hello"`メッセージを正しく受信したことを確認します。これは、パニックが発生する前にデータがフラッシュされたことを意味します。
    *   `err == nil`のチェックにより、`ioutil.ReadAll(res.Body)`がエラーを返したことを確認します。これは、サーバーがパニックによって接続を中断し、クライアントがボディの残りを読み込めなかったことを示します。もしエラーが返されなかった場合、それはクライアントがサーバーの異常終了を検知できなかったことを意味し、テストは失敗します。

このテストは、`net/http`サーバーがハンドラ内のパニックに対して堅牢であり、クライアントがその異常を適切に処理できるようなシグナルを受け取ることを保証するための重要な側面をカバーしています。

### `TestInterruptWithPanic_h1`と`TestInterruptWithPanic_h2`

これらの関数は、`testInterruptWithPanic`関数をそれぞれHTTP/1.1モード（`h1Mode`）とHTTP/2モード（`h2Mode`）で呼び出すためのテストエントリポイントです。これにより、両方のプロトコルで同じパニック処理のテストが実行されます。

### `testInterruptWithPanic(t *testing.T, h2 bool)`関数

1.  **`log.SetOutput(ioutil.Discard)`と`defer log.SetOutput(os.Stderr)`**:
    *   この行は、テスト中に発生する可能性のある`log`出力を一時的に抑制するためのものです。ハンドラ内で`panic`が発生すると、`net/http`サーバーは通常、エラーログを出力します。このログがテストの標準出力に表示されるとノイズになるため、`ioutil.Discard`にリダイレクトしています。
    *   `defer`ステートメントにより、テスト関数の終了時にログ出力が元の`os.Stderr`に戻されます。
2.  **`const msg = "hello"`**:
    *   クライアントに送信されるメッセージの定数を定義しています。
3.  **`defer afterTest(t)`**:
    *   テスト後のクリーンアップ処理を行うための遅延関数です。通常、テスト環境をリセットするために使用されます。
4.  **`cst := newClientServerTest(t, h2, HandlerFunc(func(w ResponseWriter, r *Request) { ... }))`**:
    *   `newClientServerTest`は、テスト用のHTTPサーバーとクライアントをセットアップするヘルパー関数です。
    *   `h2`引数によって、HTTP/1.1またはHTTP/2のどちらのモードでサーバーを起動するかが決まります。
    *   `HandlerFunc(...)`でインラインのHTTPハンドラを定義しています。
        *   `io.WriteString(w, msg)`: レスポンスライター`w`に`"hello"`という文字列を書き込みます。
        *   `w.(Flusher).Flush()`: `ResponseWriter`が`Flusher`インターフェースを実装している場合、`Flush()`を呼び出して、書き込まれたデータを強制的にクライアントに送信します。これにより、クライアントはパニックが発生する前に一部のデータを受け取ることができます。
        *   `panic("no more")`: ここで意図的にパニックを発生させます。このパニックにより、サーバーはこのリクエストの処理を中断し、クライアントへの接続を閉じます。
5.  **`defer cst.close()`**:
    *   テストサーバーとクライアントをクリーンアップするための遅延関数です。
6.  **`res, err := cst.c.Get(cst.ts.URL)`**:
    *   テストクライアント`cst.c`を使用して、テストサーバーのURL`cst.ts.URL`に対してGETリクエストを送信します。
    *   リクエストの送信中にエラーが発生した場合、`t.Fatal(err)`でテストを即座に失敗させます。
7.  **`defer res.Body.Close()`**:
    *   レスポンスボディを確実に閉じるための遅延関数です。リソースリークを防ぎます。
8.  **`slurp, err := ioutil.ReadAll(res.Body)`**:
    *   レスポンスボディの残りの部分をすべて読み込もうとします。
    *   ハンドラ内でパニックが発生し、接続が閉じられているため、この`ReadAll`呼び出しはエラーを返すことが期待されます。
9.  **`if string(slurp) != msg { ... }`**:
    *   クライアントが`"hello"`メッセージを正しく読み込めたかどうかを検証します。これは、`Flush()`が機能し、パニックの前にデータが送信されたことを確認するためです。
10. **`if err == nil { ... }`**:
    *   `ioutil.ReadAll`がエラーを返さなかった場合、テストは失敗します。これは、クライアントがサーバーの接続中断をエラーとして検知できなかったことを意味します。期待される挙動は、接続が中断されたためにエラーが返されることです。

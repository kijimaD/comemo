# [インデックス 20361] ファイルの概要

このコミットは、Goランタイムのレース検出器が、Go言語で書かれたランタイムコードに適用される際の挙動を改善するものです。具体的には、`g0`（スケジューラゴルーチン）および`gsignal`（シグナルハンドリングゴルーチン）からのメモリアクセスをレース検出器が無視するように変更し、これらの特殊なゴルーチンが引き起こす誤検知を排除することを目的としています。

## 変更の背景

このコミットの背景には、Go言語のランタイム自体がGoで書かれる部分が増えてきたことと、Goの強力な並行性バグ検出ツールであるレース検出器の存在があります。レース検出器は、複数のゴルーチンが共有メモリに同時にアクセスし、少なくとも一方が書き込みである場合に発生するデータ競合（データレース）を検出するために設計されています。

しかし、Goランタイム内部には、通常のユーザーゴルーチンとは異なる特殊なゴルーチンが存在します。それが`g0`（スケジューラゴルーチン）と`gsignal`（シグナルハンドリングゴルーチン）です。これらのゴルーチンは、Goランタイムの内部処理やOSとの連携のために存在し、ユーザーコードからは直接制御されません。

問題は、レース検出器がこれらの特殊なゴルーチンによるメモリアクセスも検出対象としてしまうと、実際にはデータ競合ではない、ランタイム内部の正当な操作に対して誤って警告を発してしまう可能性があったことです。コミットメッセージにある`Fixes #8627`は、この誤検知の問題を解決するためのものです。`g0`や`gsignal`は、ユーザーゴルーチンとは異なるコンテキストで動作するため、それらのメモリアクセスはレース検出器の監視対象から除外する必要がありました。

## 前提知識の解説

### Goの並行性モデルとゴルーチン

Go言語は、軽量な並行処理の単位として「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量で、数千、数万のゴルーチンを同時に実行することが可能です。GoランタイムがこれらのゴルーチンをOSスレッドにマッピングし、スケジューリングを行います。

### Goのレース検出器 (Race Detector)

Goのレース検出器は、プログラム実行中にデータ競合を動的に検出するツールです。`go build -race`や`go test -race`のように`-race`フラグを付けてコンパイル・実行することで有効になります。このツールは、プログラムのメモリアクセスを計測し、共有メモリへの非同期なアクセスを監視することでデータ競合を特定します。内部的にはGoogleのThreadSanitizer (TSan)技術をベースにしており、シャドウメモリという概念を用いてメモリアクセスのメタデータを追跡します。データ競合が検出されると、競合が発生したメモリ位置、コードの行、関連するゴルーチンのスタックトレースを含む詳細なレポートが出力されます。ただし、レース検出器を有効にすると、メモリ使用量が5〜10倍、実行速度が2〜20倍になるなど、パフォーマンスに大きなオーバーヘッドが発生するため、通常は開発・テスト段階でのみ使用されます。

### `g0`と`gsignal`ゴルーチン

Goランタイムには、通常のユーザーゴルーチンとは異なる、特殊な目的を持つ内部ゴルーチンが存在します。

*   **`g0` (スケジューラゴルーチン)**: 各OSスレッド（GoのスケジューラモデルではM: Machine）に紐付けられた特別なゴルーチンです。通常のユーザーゴルーチンよりも大きな固定スタックを持ちます。`g0`の主な役割は、ゴルーチンの作成とスケジューリング、スタックの拡張・縮小といったスタック管理、ガベージコレクション（GC）の操作など、ランタイムの内部処理を実行することです。ユーザーゴルーチンがシステムコールを実行したり、スタックを使い果たしたりすると、`g0`に切り替わって処理が行われます。

*   **`gsignal` (シグナルハンドリングゴルーチン)**: `g0`と同様に、各OSスレッドに紐付けられた特別なゴルーチンで、OSからのシグナル（例: `SIGINT`, `SIGTERM`）を処理するために特化しています。`gsignal`も固定された大きなスタックを持ち、OSからのシグナルを受け取ると、それを処理し、必要に応じてユーザーゴルーチンに通知する役割を担います。

これらのゴルーチンは、Goランタイムの健全な動作に不可欠であり、ユーザーゴルーチンとは異なる特殊なコンテキストで動作するため、そのメモリアクセスは通常のデータ競合のルールには当てはまらない場合があります。

## 技術的詳細

Goのレース検出器は、プログラム内のすべてのメモリアクセスを計測し、それらのアクセスがデータ競合を引き起こす可能性があるかどうかを判断します。しかし、`g0`や`gsignal`といったランタイム内部のゴルーチンは、Goランタイムのコア部分を構成しており、そのメモリアクセスはランタイムの内部状態を管理するためのものです。これらのアクセスは、ユーザーゴルーチン間の競合とは性質が異なります。

例えば、`g0`はゴルーチンのスタックを管理したり、スケジューリングに関連するデータを操作したりします。これらの操作は、Goランタイムの整合性を保つために不可欠であり、ユーザーコードが直接関与するデータ競合とは区別されるべきです。もしレース検出器がこれらの内部アクセスに対して警告を発してしまうと、それは誤検知となり、開発者が本当に修正すべきデータ競合を見つけるのを妨げてしまいます。

このコミットでは、`runtime.racewriterangepc`と`runtime.racereadrangepc`という、レース検出器にメモリアクセスを通知するための内部関数に修正が加えられています。これらの関数は、Goコードがメモリを読み書きする際に、レース検出器にその情報を伝えるために呼び出されます。変更の核心は、これらの関数が呼び出された際に、現在のゴルーチンが`g0`または`gsignal`であるかどうかをチェックし、もしそうであれば、そのメモリアクセスをレース検出器に報告しないようにすることです。

具体的には、`g`（現在のゴルーチン）が`g->m->curg`（現在のM（OSスレッド）が実行しているユーザーゴルーチン）と異なる場合、つまり`g0`や`gsignal`のような特殊なゴルーチンである場合に、レース検出器への報告をスキップします。これにより、ランタイム内部の正当なメモリアクセスが誤ってデータ競合として報告されるのを防ぎ、レース検出器の精度を向上させます。

また、`proc.c`では、`m0->g0`の`racectx`フィールドがゼロに設定されています。`racectx`はレース検出器がゴルーチンのコンテキストを追跡するために使用するフィールドですが、`m0->g0`（メインスレッドの`g0`）の`racectx`は、メインゴルーチンの親としてのみ使用され、それ以外の目的では使用されないため、明示的にゼロに設定することで、レース検出器がこの特殊な`g0`のメモリアクセスを無視するようになります。

さらに、`cpuprof.go`では、`copy`関数を使用してスライスや配列のコピーを行うように変更されています。これは、手動でのループによるコピーよりも効率的であり、Go言語のイディオムに沿った改善です。この変更自体はレース検出器の挙動に直接関係するものではありませんが、ランタイムコードの品質向上に貢献しています。

## コアとなるコードの変更箇所

このコミットでは、以下の3つのファイルが変更されています。

1.  `src/pkg/runtime/cpuprof.go`: CPUプロファイリングに関連するGoコード。
2.  `src/pkg/runtime/proc.c`: Goランタイムのプロセス管理に関連するCコード。
3.  `src/pkg/runtime/race.c`: Goランタイムのレース検出器に関連するCコード。

### `src/pkg/runtime/cpuprof.go`

- `Assoc`関数内で、`e.stack`への`pc`のコピーが、手動ループから`copy(e.stack[:], pc)`に変更されました。
- `evict`関数内で、`log`への`e.stack`のコピーが、手動ループから`copy(log[q:], e.stack[:d])`に変更され、`q`のインクリメントも`q += d`に変更されました。

### `src/pkg/runtime/proc.c`

- `runtime·main`関数内で、`g->m->g0->racectx = 0;`という行が追加されました。これは、`m0->g0`の`racectx`がメインゴルーチンの親としてのみ使用され、それ以外の目的では使用されないことを明示しています。
- `newm`関数内で、`if(raceenabled)`ブロック内の`mp->g0->racectx = runtime·racegostart(newm);`という行が削除されました。

### `src/pkg/runtime/race.c`

- `runtime·racewriterangepc`関数と`runtime·racereadrangepc`関数に、以下のチェックが追加されました。
    ```c
    if(g != g->m->curg) {
        // The call is coming from manual instrumentation of Go code running on g0/gsignal.
        // Not interesting.
        return;
    }
    ```
    このチェックにより、現在のゴルーチンが`g0`または`gsignal`である場合、レース検出器への報告がスキップされます。

## コアとなるコードの解説

### `src/pkg/runtime/cpuprof.go`の変更

このファイルでの変更は、主にGoの組み込み関数`copy`の利用に切り替えることで、コードの簡潔さと効率性を向上させています。
- `copy(e.stack[:], pc)`: `pc`スライスの内容を`e.stack`配列にコピーします。これは、手動でループを回して要素を一つずつコピーするよりも、Goのイディオムに沿っており、コンパイラによる最適化の恩恵を受けやすいです。
- `copy(log[q:], e.stack[:d])`と`q += d`: 同様に、`e.stack`の一部を`log`スライスにコピーし、コピーされた要素数分だけ`q`（ログの現在の書き込み位置）を進めます。これは、CPUプロファイリングのスタックトレース情報を効率的にログに記録するための改善です。

これらの変更は、レース検出器の挙動に直接的な影響を与えるものではありませんが、ランタイムコードの全体的な品質とパフォーマンスを向上させるための一般的な最適化です。

### `src/pkg/runtime/proc.c`の変更

- `g->m->g0->racectx = 0;`の追加:
    `runtime·main`はGoプログラムのエントリポイントであり、メインゴルーチンが開始される場所です。ここで`g->m->g0->racectx`をゼロに設定することは、メインゴルーチンを起動する`g0`のレース検出コンテキストを初期化し、この`g0`がレース検出器の対象外であることを明示するものです。`racectx`はレース検出器がゴルーチンのコンテキストを追跡するために使用する内部フィールドであり、`g0`のような特殊なゴルーチンでは、通常のユーザーゴルーチンとは異なる扱いが必要です。
- `newm`関数からの`mp->g0->racectx = runtime·racegostart(newm);`の削除:
    `newm`関数は新しいM（OSスレッド）を作成する際に呼び出されます。以前は、新しいMの`g0`に対して`runtime·racegostart`を呼び出して`racectx`を設定していましたが、このコミットにより、`g0`の`racectx`はメインゴルーチンの親としてのみ使用されるという原則が強化され、他の`g0`の`racectx`は設定しないようになりました。これにより、`g0`のメモリアクセスがレース検出器によって誤って報告される可能性がさらに低減されます。

### `src/pkg/runtime/race.c`の変更

このファイルでの変更は、レース検出器の核心部分に直接影響を与えます。
- `runtime·racewriterangepc`と`runtime·racereadrangepc`への条件分岐の追加:
    これらの関数は、Goコードがメモリを読み書きする際に、レース検出器にその操作を通知するために呼び出されます。追加された`if(g != g->m->curg)`という条件は非常に重要です。
    - `g`: 現在実行中のゴルーチン（`g0`, `gsignal`, またはユーザーゴルーチン）。
    - `g->m->curg`: 現在のM（OSスレッド）が実行しているユーザーゴルーチン。
    もし`g`が`g->m->curg`と異なる場合、それは現在のコードが`g0`または`gsignal`といった特殊なランタイムゴルーチンによって実行されていることを意味します。これらのゴルーチンによるメモリアクセスは、ランタイム内部の整合性を保つためのものであり、ユーザーコードのデータ競合とは性質が異なります。したがって、この条件が真の場合、レース検出器への報告を`return;`でスキップすることで、誤検知を防ぎ、レース検出器が本当にユーザーコードのデータ競合に集中できるようにします。

これらの変更により、Goランタイムの内部動作とレース検出器の連携がより洗練され、開発者はより正確なデータ競合レポートを得られるようになります。

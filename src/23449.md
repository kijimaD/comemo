## 元コミット内容

`syscall: add test for Flock_t roundtrip`

このコミットは、`Flock_t` 構造体のラウンドトリップテストを追加します。これは、`F_SETLK` で設定したファイルロック情報が `F_GETLK` で正しく取得できることを確認するためのものです。

## 変更の背景

この変更の背景には、Linux システムにおける `fcntl` システムコールと `glibc` の挙動の違いがあります。

ファイルロックを行う `fcntl` システムコールは、`F_SETLK` (ロック設定) や `F_GETLK` (ロック取得) といったコマンドと共に `Flock_t` 構造体を使用します。しかし、一部のLinuxシステムでは、`glibc` (GNU C Library) がこれらのコマンドに対して、カーネルが期待する実際の値とは異なる値を内部的に使用し、実際の `fcntl` システムコールが発行される直前に正しい値に変換するという挙動をします。

Go言語は、C言語のライブラリである `glibc` を介さずに、直接カーネルのシステムコールを呼び出す「raw syscalls」を使用します。このため、Goが `fcntl` を呼び出す際には、`glibc` が提供する変換メカニズムが働かず、Go自身がカーネルが期待する正確な値を使用する必要があります。

このコミットは、`Flock_t` 構造体を使ってファイルロックを設定 (`F_SETLK`) し、その後そのロック情報を取得 (`F_GETLK`) する際に、Goが使用する値がカーネルと正しく整合しているか、つまり `Flock_t` の情報が「ラウンドトリップ」できるかを検証するために追加されました。これにより、Goの `syscall` パッケージがファイルロックを正しく扱えることが保証されます。

## 前提知識の解説

### ファイルロック (File Locking)
ファイルロックは、複数のプロセスが同時にファイルにアクセスする際に、データの整合性を保つためのメカニズムです。これにより、あるプロセスがファイルを書き込んでいる間に、別のプロセスがそのファイルを読み書きしてデータが破損するのを防ぎます。Unix系システムでは、`fcntl` システムコールがファイルロック機能を提供します。

### `fcntl` システムコール
`fcntl` (file control) は、オープンされたファイルディスクリプタに対して様々な操作を行うためのシステムコールです。ファイルロック以外にも、ファイルディスクリプタのフラグ設定や複製など、多岐にわたる機能を提供します。ファイルロックに関連する主なコマンドは以下の通りです。
- `F_SETLK`: ファイルロックを設定または解除します。ロックが取得できない場合、エラーを返します。
- `F_SETLKW`: `F_SETLK` と同様ですが、ロックが取得できない場合は、ロックが利用可能になるまでブロックします。
- `F_GETLK`: 指定されたファイル領域に既存のロックがあるかどうかを調べます。ロックが存在する場合、そのロック情報（ロックタイプ、開始オフセット、長さ、プロセスIDなど）を `Flock_t` 構造体に格納して返します。

### `Flock_t` 構造体
`Flock_t` は、`fcntl` システムコールでファイルロック情報をやり取りするために使用される構造体です。通常、以下のフィールドを含みます（システムによってフィールド名や型が異なる場合がありますが、概念は共通です）。
- `Type`: ロックのタイプ (`F_RDLCK` (共有ロック/読み取りロック), `F_WRLCK` (排他ロック/書き込みロック), `F_UNLCK` (ロック解除))。
- `Whence`: ロック範囲の開始オフセットの基準点 (`SEEK_SET` (ファイルの先頭から), `SEEK_CUR` (現在のファイルポインタから), `SEEK_END` (ファイルの末尾から))。
- `Start`: ロック範囲の開始オフセット。
- `Len`: ロック範囲の長さ。
- `Pid`: ロックを保持しているプロセスのID (主に `F_GETLK` で返される情報)。

### `glibc` と Raw Syscalls
- **`glibc` (GNU C Library)**: Linuxシステムで広く使われている標準Cライブラリです。アプリケーションは通常、`glibc` が提供する関数（例: `open`, `read`, `write`, `fcntl` のラッパー関数）を呼び出し、`glibc` がその呼び出しを適切なカーネルシステムコールに変換して実行します。`glibc` は、システムコールインターフェースの複雑さを抽象化し、移植性や利便性を提供します。
- **Raw Syscalls (生システムコール)**: `glibc` などのライブラリを介さずに、アプリケーションが直接カーネルのシステムコールを呼び出すことです。Go言語の `syscall` パッケージは、このraw syscallsのメカニズムを利用して、OSの低レベル機能にアクセスします。raw syscallsを使用する利点は、オーバーヘッドの削減や、`glibc` の挙動に依存しない直接的なOS操作が可能になる点ですが、カーネルインターフェースの細かな違いに直接対応する必要があるという課題もあります。

このコミットは、Goがraw syscallsを使用するがゆえに、`glibc` が提供するような `fcntl` コマンド値の変換が行われないため、Goがカーネルと直接やり取りする際に `Flock_t` の値が正しく解釈されることを確認する必要がある、という背景に基づいています。

## 技術的詳細

このコミットで追加されたテストは、`Flock_t` 構造体のフィールドが `F_SETLK` で設定され、その後 `F_GETLK` で取得された際に、その値が期待通りであることを検証します。特に、以下の点に焦点を当てています。

1.  **`Flock_t` のフィールド値の整合性**: `Type`, `Start`, `Len`, `Whence` といったフィールドが、設定時と取得時で一致するかどうか。
2.  **`Pid` の検証**: `F_GETLK` で取得される `Pid` が、ロックを保持しているプロセスのIDと一致するかどうか。
3.  **`Whence` の正規化**: Linuxカーネルは `F_GETLK` でロック情報を返す際、`Whence` フィールドを `SEEK_SET` (値は0) に正規化する傾向があります。このテストでは、このカーネルの挙動も考慮して検証を行います。

テストは、親プロセスと子プロセスを生成する形で実装されています。
- **親プロセス**:
    - 一時ファイルを作成し、ファイルディスクリプタを取得します。
    - `Ftruncate` でファイルのサイズを拡張します。これは、ロック範囲がファイルサイズを超える場合に問題が発生しないようにするためです。
    - `Flock_t` 構造体を初期化し、`F_WRLCK` (書き込みロック) を設定します。`Start` と `Len` には具体的な値 (`31415`, `271828`) を設定し、`Whence` は `SEEK_CUR` (値は1) に設定します。
    - `F_SETLK` を使ってこのロックをファイルに設定します。
    - 子プロセスを起動し、ファイルディスクリプタを子プロセスに渡します。
- **子プロセス**:
    - 親プロセスから渡されたファイルディスクリプタを使用します。
    - 親プロセスが設定したロックと競合するような `Flock_t` 構造体 (`got`) を作成します。具体的には、親のロック範囲と少しずらした範囲を設定します。
    - `F_GETLK` を使って、この競合するロック情報 (`got`) をカーネルに問い合わせます。カーネルは、競合するロックが存在する場合、そのロック情報（つまり親プロセスが設定したロックの情報）を `got` に書き込みます。
    - 取得した `got` の情報と、親プロセスが設定した元の `flock` の情報を比較します。この際、`Pid` は親プロセスのIDと一致するか、`Whence` はカーネルによって `0` に正規化されているか、といった点を検証します。

このテストは、Goの `syscall` パッケージが `fcntl` システムコールを介してファイルロックを正しく設定・取得できることを、具体的な値を使って厳密に検証するものです。

## コアとなるコードの解説

このコミットの主要な変更は、`TestFcntlFlock` 関数の大幅な修正と拡張です。

1.  **テストの目的の明確化**:
    - コメントが追加され、このテストが「ファイルロック構造体が各カーネルの呼び出し規約に一致するか」だけでなく、「`Flock_t` 構造体が `F_SETLK` と `F_GETLK` でラウンドトリップできるか」を検証するものであることが明記されました。
    - `glibc` と Go の raw syscalls の違い、および Go がカーネルが期待する「実際の値」を使用する必要があるという背景が説明されています。

2.  **`Flock_t` の初期化**:
    - 以前は `Type: syscall.F_RDLCK, Start: 0, Len: 0, Whence: 1` で初期化されていましたが、新しいテストでは `Type: syscall.F_WRLCK, Start: 31415, Len: 271828, Whence: 1` と、より具体的な値で初期化されるようになりました。これにより、特定のロックタイプと範囲でのラウンドトリップが検証されます。

3.  **親・子プロセスによるテスト構造**:
    - `os.Getenv("GO_WANT_HELPER_PROCESS")` 環境変数を使って、テストが親プロセスとして実行されているのか、それとも子プロセスとして実行されているのかを判別するロジックが追加されました。
    - **親プロセス (`if os.Getenv(...) == ""`)**:
        - 一時ファイルを作成し、ファイルディスクリプタ `fd` を取得します。
        - `syscall.Ftruncate(fd, 1<<20)` でファイルを1MBに拡張します。これは、ロック範囲がファイルサイズを超えないようにするため、または大きなファイルに対するロックをシミュレートするためと考えられます。
        - `syscall.FcntlFlock(uintptr(fd), syscall.F_SETLK, &flock)` を呼び出し、初期化した `flock` 構造体を使ってファイルに書き込みロックを設定します。
        - `exec.Command` を使って自身（テストバイナリ）を子プロセスとして起動します。
        - `cmd.Env = append(os.Environ(), "GO_WANT_HELPER_PROCESS=1")` を設定することで、子プロセスが「子」として認識されるようにします。
        - `cmd.ExtraFiles = []*os.File{os.NewFile(uintptr(fd), name)}` を使って、親プロセスがオープンしたファイルディスクリプタを子プロセスに渡します。これにより、子プロセスは親プロセスと同じファイルに対して操作を行えます。
        - 子プロセスの実行結果をチェックし、エラーがあればテストを失敗させます。
    - **子プロセス (`else`)**:
        - 親プロセスから渡されたファイルディスクリプタ（Goのテストフレームワークでは通常3番目のファイルディスクリプタとして渡されるため `3` を使用）に対して操作を行います。
        - `got := flock` で、親が設定した `flock` のコピーを作成します。
        - `got.Start--` と `got.Len++` を行い、親のロック範囲と意図的に競合するような範囲を設定します。これは `F_GETLK` が競合するロックを検出するために必要です。
        - `syscall.FcntlFlock(3, syscall.F_GETLK, &got)` を呼び出し、ファイルディスクリプタ `3` に対して `F_GETLK` を実行します。これにより、`got` 構造体には親プロセスが設定したロックの情報が書き込まれます。
        - `flock.Pid = int32(syscall.Getppid())` で、期待される `Pid` を親プロセスのIDに設定します。
        - `flock.Whence = 0` で、期待される `Whence` を `0` (SEEK_SET) に設定します。これは、Linuxカーネルが `F_GETLK` で `Whence` を `SEEK_SET` に正規化する挙動を考慮したものです。
        - 最後に、`got` (取得したロック情報) と `flock` (期待されるロック情報) の各フィールド (`Type`, `Start`, `Len`, `Pid`, `Whence`) を比較し、すべてが一致すれば `os.Exit(0)` で成功終了します。一つでも一致しなければ `t.Fatalf` でテストを失敗させます。

4.  **`TestPassFD` の環境変数設定の修正**:
    - `TestPassFD` 関数でも、`cmd.Env = []string{"GO_WANT_HELPER_PROCESS=1"}` が `cmd.Env = append(os.Environ(), "GO_WANT_HELPER_PROCESS=1")` に変更されています。これは、子プロセスに親プロセスの環境変数を引き継がせるための一般的な慣習であり、より堅牢なテスト環境を提供します。

この変更により、Goの `syscall` パッケージが `fcntl` システムコールを介したファイルロック操作において、カーネルとの間で `Flock_t` 構造体の情報を正確にやり取りできることが、より厳密に保証されるようになりました。

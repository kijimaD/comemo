# [インデックス 23323] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）における「スキャンワーク」の計測方法を変更するものです。以前はスキャンされたポインタスロットの数をGCスキャンワークのメトリックとしていましたが、この変更により、ポインタスロットとスカラー値の両方を含む、スキャンされた合計バイト数をメトリックとして使用するようになります。この変更の主な目的は、GCサイクル開始時にスキャンワーク量をより正確かつロバストに推定できるようにすることです。

## 元コミット内容

```
runtime: include scalar slots in GC scan work metric

The garbage collector predicts how much "scan work" must be done in a
cycle to determine how much work should be done by mutators when they
allocate. Most code doesn't care what units the scan work is in: it
simply knows that a certain amount of scan work has to be done in the
cycle. Currently, the GC uses the number of pointer slots scanned as
the scan work on the theory that this is the bulk of the time spent in
the garbage collector and hence reflects real CPU resource usage.
However, this metric is difficult to estimate at the beginning of a
cycle.

Switch to counting the total number of bytes scanned, including both
pointer and scalar slots. This is still less than the total marked
heap since it omits no-scan objects and no-scan tails of objects. This
metric may not reflect absolute performance as well as the count of
scanned pointer slots (though it still takes time to scan scalar
fields), but it will be much easier to estimate robustly, which is
more important.

Reviewed-on: https://go-review.googlesource.com/9694
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

Goのガベージコレクタは、プログラムの実行（ミューテータ）と並行して動作する並行GCです。GCは、次のGCサイクルでどれくらいの「スキャンワーク」が必要になるかを予測し、それに基づいてミューテータがメモリを割り当てる際にどれくらいのGC作業を分担すべきかを決定します。この予測は、GCのレイテンシを抑えつつ、スループットを最大化するために非常に重要です。

以前のGo GCでは、この「スキャンワーク」のメトリックとして、スキャンされたポインタスロットの数を使用していました。これは、ポインタのスキャンがGC時間の大部分を占め、実際のCPUリソース使用量を反映しているという考えに基づいています。しかし、このポインタスロット数というメトリックは、GCサイクルの開始時に正確に推定することが困難でした。不正確な推定は、GCの効率性や予測可能性に悪影響を及ぼす可能性があります。

このコミットは、この推定の難しさという課題に対処するために導入されました。よりロバストに推定できるメトリックを採用することで、GCの動作を安定させ、全体的なパフォーマンスを向上させることを目指しています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、不要になったメモリを自動的に解放するシステムです。GoのGCは「並行マーク＆スイープ」方式を採用しており、プログラムの実行（ミューテータ）と並行してGCが動作します。これにより、GCによるプログラムの一時停止（ストップ・ザ・ワールド）時間を最小限に抑え、低レイテンシを実現しています。

### GCの「スキャンワーク」とは何か

GCのスキャンフェーズでは、到達可能なオブジェクトを特定するためにヒープ上のメモリを走査します。この走査作業の量を「スキャンワーク」と呼びます。Go GCは、このスキャンワーク量を予測し、ミューテータが新しいメモリを割り当てる際に、GC作業の一部を分担させることで、GCの進行を助けます。この分担されるGC作業は「GCエイド」と呼ばれます。スキャンワークの正確な予測は、GCエイドの量を適切に調整し、GCの効率とアプリケーションのパフォーマンスのバランスを取る上で不可欠です。

### ポインタスロットとスカラー値

Goのオブジェクトは、メモリ上でポインタ（他のオブジェクトへの参照）とスカラー値（整数、浮動小数点数、ブール値など）で構成されます。
- **ポインタスロット**: 他のメモリ領域を指し示すアドレスが格納されているメモリ領域です。GCはポインタを辿って到達可能なオブジェクトを特定するため、ポインタスロットのスキャンはGCの根幹をなす作業です。
- **スカラー値**: それ自体がデータであり、他のメモリ領域を指し示さない値です。スカラー値はGCの到達可能性の判断には直接関係しませんが、オブジェクト全体をスキャンする際には、その一部として走査されます。

### ミューテータ (Mutator) とGCの協調

「ミューテータ」とは、Goプログラムの通常の実行スレッドを指します。これらのスレッドはヒープ上のオブジェクトを作成、変更、削除します。GCが動作している間、ミューテータはGCの進行を妨げないように、またGCの作業を助けるために協調します。特に、メモリ割り当て時にGCエイドとしてGC作業の一部を実行することがあります。

## 技術的詳細

このコミットの核心は、GCスキャンワークのメトリックを「スキャンされたポインタスロットの数」から「スキャンされた合計バイト数」に変更することです。

**旧メトリック（ポインタスロット数）の問題点:**
- ポインタスロットの数は、オブジェクトの構造やヒープの状態によって大きく変動するため、GCサイクルの開始時に正確に予測することが困難でした。
- 予測が不正確だと、GCエイドの量が適切に調整されず、GCのレイテンシが増加したり、アプリケーションのスループットが低下したりする可能性がありました。

**新メトリック（スキャンされたバイト数）の利点と考慮事項:**
- **推定の容易さ**: スキャンされる合計バイト数は、ヒープの使用量やオブジェクトのサイズ分布から、ポインタスロット数よりもはるかにロバストに推定できます。これにより、GCエイドの量をより安定して調整できるようになります。
- **スカラー値の考慮**: スカラー値自体はポインタではないため、GCの到達可能性には影響しませんが、メモリを走査する際にはスカラー値の領域も読み取られます。この読み取り作業もCPU時間を消費するため、スキャンされた合計バイト数に含めることで、GCが実際に消費するCPUリソースをより包括的に反映できる可能性があります。
- **パフォーマンス反映の精度**: コミットメッセージにもあるように、スキャンされたポインタスロット数の方が「絶対的なパフォーマンス」をより正確に反映していた可能性があります。なぜなら、ポインタの追跡はGCの最もコストのかかる部分だからです。しかし、スカラーフィールドのスキャンにも時間はかかるため、合計バイト数も無関係ではありません。この変更は、絶対的な精度よりも「ロバストな推定」を優先した結果と言えます。
- **対象外のメモリ**: このメトリックは、`no-scan`オブジェクト（GCがスキャンする必要がないと判断されたオブジェクト）や、オブジェクトの`no-scan`テール（オブジェクトの末尾にあるスカラー値で、GCがスキャンを停止する部分）は除外されます。したがって、ヒープ全体のマークされたバイト数とは異なります。

この変更は、`src/runtime/mgcmark.go`ファイル内のGCマークフェーズを担当する関数に影響を与えます。特に、`scanblock`と`scanobject`関数における`gcw.scanWork`の更新ロジックが変更されます。

## コアとなるコードの解説

このコミットでは、`src/runtime/mgcmark.go` 内の `scanblock` および `scanobject` 関数の `gcw.scanWork` の計算方法が変更されています。

1.  **`scanblock` 関数**:
    *   以前は `scanWork := int64(0)` でローカル変数 `scanWork` を初期化し、ループ内でポインタスロットが見つかるたびに `scanWork++` でインクリメントしていました。
    *   変更後、ローカル変数 `scanWork` は削除され、ループの最後に `gcw.scanWork += int64(n)` と直接 `gcw.scanWork` に `n` (スキャンされたブロックの合計サイズ) を加算するようになりました。これにより、ポインタの数ではなく、スキャンされたブロック全体のバイト数がスキャンワークとして計上されます。

2.  **`scanobject` 関数**:
    *   `scanblock` と同様に、以前は `scanWork := int64(0)` でローカル変数 `scanWork` を初期化し、ポインタスロットが見つかるたびに `scanWork++` でインクリメントしていました。
    *   変更後、ローカル変数 `scanWork` と、そのインクリメントに関するコメントブロックが削除されました。
    *   ループの最後に `gcw.scanWork += int64(i)` と直接 `gcw.scanWork` に `i` (スキャンされたオブジェクトの合計サイズ) を加算するようになりました。`i` はループのインデックスであり、オブジェクトのサイズ `n` と等しくなります。これにより、オブジェクト全体のバイト数がスキャンワークとして計上されます。

これらの変更により、`gcw.scanWork` は、スキャンされたポインタの数ではなく、`scanblock` や `scanobject` が処理したメモリ領域の合計バイト数を反映するようになりました。これは、GCが次のサイクルでどれだけの作業を行う必要があるかを推定するための、よりロバストなメトリックを提供します。

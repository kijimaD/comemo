# [インデックス 22356] ファイルの概要

このコミットは、Goコンパイラの`cmd/internal/obj/x86`パッケージにおける、`nacl/amd64p32`ターゲット向けのビルド問題を修正するものです。具体的には、一部のx86命令（例: `PINSRW`）がメモリのアドレスを`Prog`構造体の`From3`フィールドに格納する可能性があり、`nacl`環境ではこれらのアドレスも適切に書き換えられる必要があるという問題に対処しています。

## 元コミット内容

このコミットは、Go言語のコンパイラバックエンドの一部である`cmd/internal/obj/x86`パッケージにおいて、`nacl/amd64p32`ターゲット環境でのビルド時に発生する問題を修正することを目的としています。コミットメッセージによると、問題の根源は、`PINSRW`のような特定のx86命令が、命令のオペランド情報を持つ`Prog`構造体の`From3`フィールドにメモリのアドレスを格納する可能性がある点にありました。`nacl`（Google Native Client）環境では、セキュリティとサンドボックス化のために、生成されるコード内のメモリ参照が特定のルールに従って「書き換えられる（rewrite）」必要があります。しかし、これまでは`Prog.From3`に格納されたアドレスがこの書き換えプロセスの対象外であったため、不正なメモリ参照が発生し、ビルドが失敗していました。このコミットは、`Prog.From3`に格納されたアドレスも`nacl`環境下で適切に書き換えられるようにすることで、この問題を解決します。

## 変更の背景

この変更の背景には、Go言語がGoogle Native Client (NaCl) をターゲットとしていた時期の特殊な要件があります。NaClは、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行するためのサンドボックス技術でした。Go言語も一時的にNaClをサポートしており、特に`nacl/amd64p32`というターゲットは、64ビットのx86命令セットを使用しつつ、ポインタサイズを32ビットに制限することで、メモリフットプリントを抑えながら64ビットの利点を活用しようとするものでした。

NaCl環境では、生成される機械語コードがサンドボックス内で安全に実行されるように、メモリ参照やジャンプ命令のアドレスが実行時に動的に調整される「書き換え（rewriting）」処理が必要でした。Goコンパイラのx86バックエンド（`cmd/internal/obj/x86`）は、この書き換え処理を`nacladdr`関数を通じて行います。しかし、これまでの実装では、命令の主要なオペランドである`Prog.From`や`Prog.To`は書き換えの対象となっていましたが、一部の命令が使用する第三のオペランドである`Prog.From3`にメモリのアドレスが格納されるケースが考慮されていませんでした。

`PINSRW`命令のようなSIMD命令は、パックされたデータ（複数の小さなデータを一つのレジスタにまとめたもの）を操作する際に、メモリからデータを読み込むことがあります。このメモリ参照が`Prog.From3`に表現される場合、`nacladdr`による書き換えが行われないと、NaClのサンドボックス要件を満たせず、結果としてビルドエラーや実行時エラーが発生していました。このコミットは、この見落としを修正し、`nacl/amd64p32`ターゲットでのGoプログラムの安定したビルドを可能にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **Goコンパイラの内部構造 (`cmd/internal/obj`)**:
    *   Goコンパイラは、ソースコードを抽象構文木（AST）に変換し、中間表現（IR）を経て、最終的にターゲットアーキテクチャの機械語コードを生成します。
    *   `cmd/internal/obj`パッケージは、Goコンパイラのバックエンドの一部であり、アセンブラの命令表現を扱います。これは、Goのソースコードから直接アセンブリコードを生成するのではなく、Goのコンパイラが生成する中間表現を、最終的な機械語に変換する手前の「擬似アセンブリ」のような形式で表現します。
    *   `obj.Prog`構造体は、この擬似アセンブリにおける単一の命令を表します。各`Prog`は、命令の種類（Op）、ソースオペランド（From）、デスティネーションオペランド（To）などの情報を含みます。
    *   `Prog.From3`は、一部の複雑な命令が持つ第三のオペランドを表現するために使用されるフィールドです。これは、`Prog.From`や`Prog.To`だけでは表現しきれない追加のオペランド情報（特にメモリ参照）を格納するために利用されます。

2.  **Google Native Client (NaCl)**:
    *   Googleが開発したサンドボックス技術で、ウェブブラウザ（特にGoogle Chrome）内でネイティブコード（C/C++など）を安全かつ高性能に実行することを可能にしました。
    *   NaClは、コードの実行を厳しく制限し、システムリソースへのアクセスを制御することで、セキュリティを確保します。このために、生成される機械語コードは特定の制約（例: すべてのメモリ参照がサンドボックス境界内にあること）を満たす必要があり、コンパイル時に特別な処理（アドレスの書き換えなど）が行われます。
    *   **注意点**: NaClは現在では非推奨となり、WebAssemblyがその役割を引き継いでいます。Go言語もGo 1.14以降、NaClのサポートを削除しています。しかし、このコミットが作成された当時はまだ活発に開発・利用されていました。

3.  **`amd64p32`アーキテクチャ**:
    *   `amd64`（x86-64）は64ビットの命令セットアーキテクチャですが、`amd64p32`は、64ビットの命令セットとレジスタを使用しつつ、ポインタサイズを32ビットに制限した特殊なモードです。
    *   これにより、64ビットの計算能力を享受しながら、32ビットポインタによるメモリフットプリントの削減を目指しました。NaCl環境で特に利用されました。

4.  **x86 SIMD命令 (`PINSRW`)**:
    *   **SIMD (Single Instruction, Multiple Data)**: 一つの命令で複数のデータ要素を同時に処理する命令セット拡張です。これにより、画像処理や科学技術計算など、大量の並列データ処理が必要なタスクのパフォーマンスが向上します。
    *   **`PINSRW` (Packed INSeRt Word)**: x86のSIMD命令の一つで、パックされたデータ（例: 複数の16ビット整数が格納されたMMXまたはXMMレジスタ）に対して、指定された位置に16ビットのワードを挿入します。
    *   この命令は、ソースオペランドとして汎用レジスタまたは**メモリロケーション**を取ることができます。メモリロケーションがソースとして指定された場合、そのメモリのアドレスが`Prog.From3`のようなフィールドに格納される可能性があります。

## 技術的詳細

Goコンパイラのx86バックエンド（`src/cmd/internal/obj/x86/obj6.go`）では、`progedit`関数が、生成される各命令（`obj.Prog`）に対して最終的な調整を行います。特に、`nacl`ターゲット向けにコンパイルする場合、`progedit`関数は`nacladdr`関数を呼び出し、命令のオペランドに含まれるメモリ参照をNaClのサンドボックス要件に合わせて書き換えます。

これまでの実装では、`nacladdr`は主に`p.From`（第一ソースオペランド）と`p.To`（デスティネーションオペランド）に対して適用されていました。これは、ほとんどの命令がこれらのフィールドにメモリ参照を格納するためです。しかし、`PINSRW`のような一部のx86命令は、その操作の性質上、第三のオペランド（`Prog.From3`）にメモリのアドレスを格納することがあります。例えば、`PINSRW`命令がメモリからワードを読み込んでレジスタに挿入する場合、そのメモリのアドレスは`Prog.From3`に表現されることになります。

NaClのサンドボックスは、すべてのメモリ参照が厳密に制御された範囲内にあることを要求します。もし`Prog.From3`に格納されたメモリ参照が`nacladdr`による書き換えの対象とならない場合、その参照はNaClのセキュリティポリシーに違反し、結果としてビルドプロセスが失敗するか、生成されたバイナリがNaCl環境で正しく実行されない原因となります。

このコミットは、このギャップを埋めるものです。`progedit`関数内で、`nacl`ターゲットかつ`amd64p32`モードの場合に、`p.From3`に対しても`nacladdr`を適用するように変更することで、`PINSRW`のような命令が`From3`にメモリ参照を格納しても、それが適切にNaClのサンドボックス要件に適合するように修正されます。これにより、`nacl/amd64p32`ターゲットでのGoプログラムのコンパイルが成功し、安全に実行できるようになります。

## コアとなるコードの解説

変更されたコードは、`progedit`関数内の条件分岐`if ctxt.Headtype == obj.Hnacl && p.Mode == 64`の中にあります。この条件は、GoコンパイラがGoogle Native Client (NaCl) をターゲットとし、かつ64ビットモード（`amd64p32`は64ビット命令を使用するためこの条件に合致します）でコードを生成している場合に真となります。

追加された行は以下の通りです。

```go
nacladdr(ctxt, p, &p.From3)
```

*   `nacladdr`: この関数は、Goコンパイラが生成するアセンブリ命令（`obj.Prog`）内のメモリ参照を、NaClのサンドボックス要件に合わせて書き換える役割を担います。具体的には、NaClのサンドボックスは、すべてのメモリ参照が特定のベースレジスタからのオフセットとして表現されることを要求するため、`nacladdr`はこれらの参照を調整します。
*   `ctxt`: コンテキスト情報（リンカのコンテキストなど）を保持します。
*   `p`: 現在処理中のアセンブリ命令を表す`obj.Prog`構造体へのポインタです。
*   `&p.From3`: `obj.Prog`構造体の`From3`フィールドへのポインタを渡しています。これにより、`nacladdr`関数は`p.From3`が指すオペランドの内容を直接変更できるようになります。

この一行が追加されることで、`PINSRW`のような命令が`Prog.From3`にメモリのアドレスを格納している場合でも、そのアドレスが`nacladdr`によって適切に書き換えられ、NaClのサンドボックス要件を満たすようになります。これにより、`nacl/amd64p32`ターゲットでのビルドが成功し、生成されたバイナリがNaCl環境で安全に実行されることが保証されます。

## 技術的詳細

Goコンパイラのx86バックエンド（`src/cmd/internal/obj/x86/obj6.go`）では、`progedit`関数が、生成される各命令（`obj.Prog`）に対して最終的な調整を行います。特に、`nacl`ターゲット向けにコンパイルする場合、`progedit`関数は`nacladdr`関数を呼び出し、命令のオペランドに含まれるメモリ参照をNaClのサンドボックス要件に合わせて書き換えます。

これまでの実装では、`nacladdr`は主に`p.From`（第一ソースオペランド）と`p.To`（デスティネーションオペランド）に対して適用されていました。これは、ほとんどの命令がこれらのフィールドにメモリ参照を格納するためです。しかし、`PINSRW`のような一部のx86命令は、その操作の性質上、第三のオペランド（`Prog.From3`）にメモリのアドレスを格納することがあります。例えば、`PINSRW`命令がメモリからワードを読み込んでレジスタに挿入する場合、そのメモリのアドレスは`Prog.From3`に表現されることになります。

NaClのサンドボックスは、すべてのメモリ参照が厳密に制御された範囲内にあることを要求します。もし`Prog.From3`に格納されたメモリ参照が`nacladdr`による書き換えの対象とならない場合、その参照はNaClのセキュリティポリシーに違反し、結果としてビルドプロセスが失敗するか、生成されたバイナリがNaCl環境で正しく実行されない原因となります。

このコミットは、このギャップを埋めるものです。`progedit`関数内で、`nacl`ターゲットかつ`amd64p32`モードの場合に、`p.From3`に対しても`nacladdr`を適用するように変更することで、`PINSRW`のような命令が`From3`にメモリ参照を格納しても、それが適切にNaClのサンドボックス要件に適合するように修正されます。これにより、`nacl/amd64p32`ターゲットでのGoプログラムのコンパイルが成功し、安全に実行できるようになります。

```diff

+++ b/src/cmd/internal/obj/x86/obj6.go
@@ -191,6 +191,7 @@ func progedit(ctxt *obj.Link, p *obj.Prog) {

## コアとなるコードの解説

変更されたコードは、`progedit`関数内の条件分岐`if ctxt.Headtype == obj.Hnacl && p.Mode == 64`の中にあります。この条件は、GoコンパイラがGoogle Native Client (NaCl) をターゲットとし、かつ64ビットモード（`amd64p32`は64ビット命令を使用するためこの条件に合致します）でコードを生成している場合に真となります。

追加された行は以下の通りです。

```go
nacladdr(ctxt, p, &p.From3)
```

*   `nacladdr`: この関数は、Goコンパイラが生成するアセンブリ命令（`obj.Prog`）内のメモリ参照を、NaClのサンドボックス要件に合わせて書き換える役割を担います。具体的には、NaClのサンドボックスは、すべてのメモリ参照が特定のベースレジスタからのオフセットとして表現されることを要求するため、`nacladdr`はこれらの参照を調整します。
*   `ctxt`: コンテキスト情報（リンカのコンテキストなど）を保持します。
*   `p`: 現在処理中のアセンブリ命令を表す`obj.Prog`構造体へのポインタです。
*   `&p.From3`: `obj.Prog`構造体の`From3`フィールドへのポインタを渡しています。これにより、`nacladdr`関数は`p.From3`が指すオペランドの内容を直接変更できるようになります。

この一行が追加されることで、`PINSRW`のような命令が`Prog.From3`にメモリのアドレスを格納している場合でも、そのアドレスが`nacladdr`によって適切に書き換えられ、NaClのサンドボックス要件を満たすようになります。これにより、`nacl/amd64p32`ターゲットでのビルドが成功し、生成されたバイナリがNaCl環境で安全に実行されることが保証されます。

# [インデックス 24295] ファイルの概要

このコミットは、Goランタイムのトレース機能に関する重要なリファクタリングを導入しています。具体的には、これまで `runtime/pprof` パッケージ内に存在していたトレース関連の関数を、新しく独立した `runtime/trace` パッケージへと移動させています。これにより、プロファイリングとトレースという異なる目的を持つ機能が、それぞれのパッケージで明確に分離され、Goの診断ツールの構造がより整理されました。

## 変更の背景

この変更の背景には、Goのパフォーマンス診断ツールであるプロファイリングとトレースの役割の明確化と、それぞれの機能の独立性の向上が挙げられます。

元々、Goの実行トレース機能は `runtime/pprof` パッケージの一部として提供されていました。しかし、`pprof` が主にCPU使用率、メモリ割り当て、ブロッキングなどの統計的なサンプリングベースのプロファイリングに焦点を当てているのに対し、実行トレースはゴルーチンのライフサイクル、システムコール、ガベージコレクションイベントなど、プログラムの実行中に発生する個々のイベントをナノ秒単位の精度で記録する、イベントベースのメカニズムです。

これら二つの機能は、どちらもパフォーマンス分析に役立つものの、その収集方法、提供する情報の粒度、そして分析の目的が根本的に異なります。`runtime/pprof` にトレース機能が同居していることは、パッケージの責務が曖昧になり、ユーザーがどちらのツールをいつ使うべきか混乱する可能性がありました。

このコミットは、トレース機能を `runtime/trace` という専用のパッケージに分離することで、以下の利点をもたらします。

1.  **責務の明確化**: 各パッケージが単一の明確な責務を持つようになり、コードベースの理解と保守が容易になります。
2.  **APIの整理**: トレース機能のAPIが `runtime/pprof` の他のプロファイリングAPIと混在することなく、より直感的になります。
3.  **将来的な拡張性**: トレース機能が独立したパッケージになることで、将来的にトレース機能固有の拡張や改善が行いやすくなります。

コミットメッセージにある `Fixes #9710` は、Goプロジェクト内部の課題トラッカーにおける特定の課題を指していると考えられます。この課題は、おそらく `runtime/pprof` 内のトレース機能の配置に関する議論や、上記のような責務の分離の必要性を示唆していたものと推測されます。

## 前提知識の解説

このコミットを理解するためには、Goのプロファイリングとトレースに関する基本的な知識が必要です。

1.  **Goのプロファイリング (`runtime/pprof`)**:
    *   Goには、プログラムのパフォーマンス特性を分析するための組み込みプロファイリングツール `pprof` があります。
    *   `pprof` は、CPU使用率、ヒープメモリ割り当て、ブロッキングプロファイル、ゴルーチンスタックトレースなど、さまざまな種類のプロファイルデータを収集できます。
    *   これらのプロファイルは、プログラムの実行中に定期的にサンプルを収集する「サンプリングベース」の手法を用いています。例えば、CPUプロファイルは1秒間に100回、プログラムがどの関数を実行しているかを記録し、その統計から「ホットスポット」（CPU時間を最も消費している部分）を特定します。
    *   `go tool pprof` コマンドを使って、収集したプロファイルデータを視覚化・分析します。

2.  **Goの実行トレース (`runtime/trace`)**:
    *   Goの実行トレースは、プログラムの実行中に発生する詳細なイベントを記録するツールです。
    *   `pprof` が統計的な概要を提供するのに対し、トレースは「イベントベース」であり、個々のイベント（例: ゴルーチンの生成、ブロック、アンブロック、スケジューリング、システムコールへの出入り、GCの開始・終了、ヒープサイズの変化など）をナノ秒単位のタイムスタンプとともに記録します。
    *   これにより、プログラムの動的な挙動、特に並行処理におけるゴルーチン間の相互作用、スケジューリングのパターン、ブロッキングの原因、レイテンシースパイクの根本原因などを詳細に分析できます。
    *   `go tool trace` コマンドを使って、収集したトレースデータを時系列のグラフやイベントリストとして視覚化・分析します。

3.  **`io.Writer` インターフェース**:
    *   Goの標準ライブラリにある `io.Writer` は、データを書き込むための汎用インターフェースです。
    *   `StartTrace` (または新しい `trace.Start`) 関数は `io.Writer` を引数として受け取ります。これは、トレースデータがファイルやネットワーク接続など、任意の `io.Writer` 実装に書き込まれることを意味します。これにより、トレースデータの出力先を柔軟に選択できます。

これらのツールは、それぞれ異なる種類のパフォーマンス問題の診断に特化しており、互いに補完し合う関係にあります。このコミットは、この補完関係を維持しつつ、それぞれのツールの独立性を高めるためのものです。

## 技術的詳細

このコミットの技術的な詳細は、主にトレース機能のコードとAPIの移動、およびそれに伴う参照箇所の更新に集約されます。

1.  **新しいパッケージ `runtime/trace` の作成**:
    *   `src/runtime/trace/trace.go` という新しいファイルが作成され、`package trace` として定義されました。
    *   このファイルには、トレースを開始する `Start(w io.Writer) error` 関数と、トレースを停止する `Stop()` 関数が含まれています。
    *   これらの関数は、Goランタイムの低レベルなトレース機能 (`runtime.StartTrace()` および `runtime.StopTrace()`) をラップし、トレースデータを指定された `io.Writer` に非同期で書き込むロジックを含んでいます。

2.  **`runtime/pprof` からのトレース機能の削除**:
    *   `src/runtime/pprof/pprof.go` から、`StartTrace(w io.Writer) error` および `StopTrace()` 関数が完全に削除されました。これにより、`runtime/pprof` は純粋なプロファイリング機能に特化する形になりました。

3.  **APIの変更 (`api/go1.5.txt`)**:
    *   Go 1.5のAPI定義ファイル `api/go1.5.txt` が更新され、`runtime/pprof` の `StartTrace` と `StopTrace` が削除され、代わりに `runtime/trace` の `Start` と `Stop` が追加されました。これは、この変更がGo 1.5の公開APIの一部となることを示しています。

4.  **依存関係と参照の更新**:
    *   **`src/cmd/trace/main.go`**: `go tool trace` コマンドのソースコードが、トレース機能の参照を `runtime/pprof.StartTrace` から `runtime/trace.Start` に変更しました。
    *   **`src/go/build/deps_test.go`**: ビルドシステムの依存関係定義が更新され、`runtime/trace` が新しい依存関係として追加されました。また、`testing` パッケージや `net/http/pprof` パッケージが `runtime/trace` に依存するようになりました。
    *   **`src/net/http/pprof/pprof.go`**: `net/http/pprof` パッケージ内の `Trace` HTTPハンドラが、トレースの開始と停止に `runtime/trace.Start` と `runtime/trace.Stop` を使用するように変更されました。これにより、`net/http/pprof` は引き続きHTTP経由でトレースデータを提供できますが、その実装は新しい `runtime/trace` パッケージに委譲されます。
    *   **`src/testing/testing.go`**: `go test -trace` コマンドの内部実装が、トレースの開始と停止に `runtime/trace.Start` と `runtime/trace.Stop` を使用するように変更されました。また、フラグ名も `trace` から `traceFile` に変更されています。

5.  **テストファイルの移動と更新**:
    *   `src/runtime/pprof/trace_stack_test.go` と `src/runtime/pprof/trace_test.go` の二つのテストファイルが、それぞれ `src/runtime/trace/trace_stack_test.go` と `src/runtime/trace/trace_test.go` にリネームされ、新しいパッケージディレクトリに移動しました。
    *   これらのテストファイル内のパッケージ宣言も `pprof_test` から `trace_test` に変更され、インポートパスも `runtime/pprof` から `runtime/trace` に更新されました。これにより、トレース機能のテストも新しいパッケージ構造に完全に適合しました。

この一連の変更は、単なるファイルの移動に留まらず、Goエコシステム全体でトレース機能がどのように参照され、使用されるかという点にまで及ぶ、徹底したリファクタリングであることを示しています。

    +// The tracer captures a wide range of execution events like goroutine
    +// creation/blocking/unblocking, syscall enter/exit/block, GC-related events,
    +// changes of heap size, processor start/stop, etc and writes them to an io.Writer

## コアとなるコードの解説

上記のコード変更は、Goの実行トレース機能が `runtime/pprof` から `runtime/trace` へと完全に移行したことを明確に示しています。

1.  **`runtime/pprof/pprof.go` からの削除**:
    *   `runtime/pprof` パッケージから `StartTrace` と `StopTrace` 関数が削除されました。これは、このパッケージがプロファイリング（サンプリングベース）に特化し、トレース（イベントベース）の責務から解放されたことを意味します。
    *   削除されたコードには、`TODO(rsc): Decide if StartTrace belongs in this package. See golang.org/issue/9710.` というコメントがありました。これは、この機能の配置について以前から疑問が呈されており、`#9710` がこの分離の必要性に関する議論を指していた可能性が高いことを裏付けています。

2.  **`runtime/trace/trace.go` の新規追加**:
    *   新しく作成された `runtime/trace` パッケージは、Goの実行トレース機能の新しいホームとなります。
    *   `Start(w io.Writer) error` 関数は、トレースを開始するためのエントリポイントです。この関数は、内部的にGoランタイムの低レベルな `runtime.StartTrace()` 関数を呼び出します。
    *   `Start` 関数は、ゴルーチンを起動し、`runtime.ReadTrace()` を繰り返し呼び出してトレースデータを読み込み、それを引数として渡された `io.Writer` (`w`) に書き込みます。この非同期書き込みメカニズムにより、トレースデータの収集と出力が効率的に行われます。`runtime.ReadTrace()` が `nil` を返すと、トレースが停止したことを意味し、ループが終了します。
    *   `Stop()` 関数は、現在のトレースを停止するためのエントリポイントです。この関数は、内部的にGoランタイムの低レベルな `runtime.StopTrace()` 関数を呼び出します。`Stop` 関数は、すべてのトレースデータの書き込みが完了するまで待機してから戻ります。
    *   パッケージのコメントには、Go実行トレーサーの目的と、それがどのようなイベント（ゴルーチン、システムコール、GC、ヒープサイズなど）をキャプチャし、`go tool trace` コマンドで分析できることが詳細に説明されています。

この変更により、Goのパフォーマンス診断ツールは、その機能と目的に応じてより論理的に整理され、開発者にとって使いやすく、理解しやすい構造になりました。

# [インデックス 23984] ファイルの概要

このコミットは、Go言語の標準ライブラリ `sync` パッケージにおける `WaitGroup` の実装を大幅に簡素化し、パフォーマンスを向上させるものです。特に、`WaitGroup` の内部状態管理を単一の `uint64` アトミック変数に集約することで、ミューテックスの使用を排除し、セマフォの動的な割り当てを不要にしています。これにより、コードの複雑さが軽減され、競合状態での性能が向上し、メモリ割り当ても削減されました。

A comment in waitgroup.go describes the following scenario
as the reason to have dynamically created semaphores:

// G1: Add(1)
// G1: go G2()
// G1: Wait() // Context switch after Unlock() and before Semacquire().
// G2: Done() // Release semaphore: sema == 1, waiters == 0. G1 doesn't run yet.
// G3: Wait() // Finds counter == 0, waiters == 0, doesn't block.
// G3: Add(1) // Makes counter == 1, waiters == 0.
// G3: go G4()
// G3: Wait() // G1 still hasn't run, G3 finds sema == 1, unblocked! Bug.

However, the scenario is incorrect:
G3: Add(1) happens concurrently with G1: Wait(),
and so there is no reasonable behavior of the program
(G1: Wait() may or may not wait for G3: Add(1) which
can't be the intended behavior).

With this conclusion we can:
1. Remove dynamic allocation of semaphores.
2. Remove the mutex entirely and instead pack counter and waiters
   into single uint64.

This makes the logic significantly simpler, both Add and Wait
do only a single atomic RMW to update the state.

## 変更の背景

このコミットの主な背景は、Go言語の `sync.WaitGroup` の既存の実装が抱えていた複雑さと、その複雑さの根拠となっていた特定の競合シナリオの誤解です。

元々 `WaitGroup` の `waitgroup.go` 内のコメントには、以下のようなシナリオが記述されており、これが `WaitGroup` がセマフォを動的に作成する理由として挙げられていました。

*   G1が`Add(1)`し、G2を起動。
*   G1が`Wait()`を呼び出すが、`Unlock()`と`Semacquire()`の間でコンテキストスイッチが発生。
*   G2が`Done()`を呼び出し、セマフォを解放。
*   G3が`Wait()`を呼び出し、カウンタが0、待機者が0であるためブロックせずに通過。
*   G3が`Add(1)`を呼び出し、カウンタを1にする。
*   G3がG4を起動。
*   G3が`Wait()`を呼び出すと、G1がまだ実行されていないにもかかわらず、セマフォが1であるためブロックせずに通過してしまう。これはバグである、とされていました。

しかし、コミットの作者であるDmitry Vyukov氏は、このシナリオが根本的に誤っていると指摘しました。具体的には、`G3: Add(1)` と `G1: Wait()` が同時に発生している状況であり、このような `WaitGroup` の同時使用は、そもそもプログラムの合理的な振る舞いを期待できない「誤用」であると結論付けました。`WaitGroup` は、`Add` が `Wait` の呼び出しよりも前に完了するか、または `Wait` が `Add` の呼び出しよりも前に完了するかのいずれかであるべきであり、両者が同時に発生するような使い方は想定されていません。

この誤解が解消されたことで、`WaitGroup` の実装から不必要な複雑さを取り除く道が開かれました。具体的には、動的なセマフォの割り当てや、内部状態を保護するためのミューテックスが不要になるという結論に至りました。これにより、よりシンプルで効率的な実装が可能となりました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識が必要です。

1.  **`sync.WaitGroup`**:
    Go言語の標準ライブラリ `sync` パッケージが提供する同期プリミティブの一つです。複数のゴルーチンが完了するまで待機するために使用されます。
    *   `Add(delta int)`: `WaitGroup` のカウンタに `delta` を加算します。通常、起動するゴルーチンの数だけ正の値を指定します。
    *   `Done()`: `Add(-1)` と同等で、カウンタを1減らします。ゴルーチンが完了した際に呼び出されます。
    *   `Wait()`: カウンタが0になるまでブロックします。
    `WaitGroup` の正しい使用法は、`Add` が `Wait` の呼び出しよりも前に完了しているか、または `Wait` が `Add` の呼び出しよりも前に完了しているかのいずれかであるべきです。`Add` と `Wait` が同時に発生するような状況は `WaitGroup` の誤用と見なされます。

2.  **アトミック操作 (`sync/atomic` パッケージ)**:
    複数のゴルーチンから同時にアクセスされる共有変数に対して、不可分（アトミック）な操作を提供します。これにより、競合状態（race condition）を防ぎ、データの整合性を保ちます。
    *   `atomic.AddUint64(addr *uint64, delta uint64)`: `addr` が指す `uint64` 値に `delta` をアトミックに加算し、新しい値を返します。
    *   `atomic.LoadUint64(addr *uint64)`: `addr` が指す `uint64` 値をアトミックに読み込みます。
    *   `atomic.CompareAndSwapUint64(addr *uint64, old, new uint64)`: `addr` が指す `uint64` 値が `old` と等しい場合、その値を `new` にアトミックに更新します。更新が成功した場合は `true` を、失敗した場合は `false` を返します。

3.  **セマフォ (Semaphore)**:
    並行プログラミングにおける同期メカニズムの一つで、リソースへのアクセスを制御するために使用されます。カウンタを持ち、リソースが利用可能であればカウンタを減らしてアクセスを許可し、利用不可能であればブロックします。リソースが解放されるとカウンタを増やし、待機中のプロセスを再開させます。Goの `runtime_Semacquire` と `runtime_Semrelease` は、Goランタイムが提供する低レベルのセマフォ操作です。

4.  **メモリ配置とアライメント (Memory Alignment)**:
    コンピュータのメモリは、特定のサイズ（例えば4バイト、8バイト）のブロック単位でアクセスされることが効率的です。データ構造がこれらのブロックの境界に適切に配置されていることを「アライメントされている」と言います。特に64ビットのCPUで64ビットのアトミック操作を行う場合、対象のデータが8バイト境界にアライメントされている必要があります。32ビットコンパイラでは、これが自動的に保証されない場合があるため、明示的なアライメント調整が必要になることがあります。

5.  **データパッキング (Data Packing)**:
    複数の小さなデータを、より大きな単一のデータ型（例: 複数の `int32` を1つの `uint64`）にまとめて格納する手法です。これにより、メモリ使用量を削減したり、アトミック操作の回数を減らしたりすることができます。このコミットでは、`WaitGroup` のカウンタと待機者数を1つの `uint64` にパッキングしています。

## 技術的詳細

このコミットの核となる技術的変更は、`sync.WaitGroup` の内部状態管理を根本的に見直した点にあります。

**1. 内部状態の集約とアトミック操作への移行:**
以前の `WaitGroup` は、カウンタ (`counter int32`)、待機者数 (`waiters int32`)、ミューテックス (`m Mutex`)、そしてセマフォ (`sema *uint32`) を個別に保持していました。この設計では、これらのフィールドを更新する際にミューテックスによるロックが必要となり、オーバーヘッドが発生していました。

新しい実装では、`counter` と `waiters` の2つの `int32` 値を1つの `uint64` にパッキングします。具体的には、`uint64` の上位32ビットをカウンタ (`counter`) に、下位32ビットを待機者数 (`waiters`) に割り当てます。この `uint64` 変数に対して、`sync/atomic` パッケージが提供するアトミック操作 (`atomic.AddUint64`, `atomic.LoadUint64`, `atomic.CompareAndSwapUint64`) を使用することで、ミューテックスによるロックが不要になります。これにより、競合状態での性能が大幅に向上します。

**2. 64ビットアライメントの保証:**
`uint64` に対するアトミック操作は、その変数が8バイト境界にアライメントされていることを要求します。しかし、32ビットシステムでは、コンパイラが自動的に8バイトアライメントを保証しない場合があります。この問題に対処するため、`WaitGroup` 構造体には `state1 [12]byte` という12バイトのバイト配列が導入されました。
`state()` メソッドは、この `state1` 配列の先頭アドレスが8バイトアライメントされているかどうかをチェックし、アライメントされていない場合は4バイトオフセットした位置（つまり、`state1[4]` のアドレス）を `*uint64` として返します。これにより、常に8バイトアライメントされた `uint64` 変数へのポインタが取得され、安全に64ビットアトミック操作を実行できるようになります。

**3. セマフォの動的割り当ての廃止:**
以前の実装では、`WaitGroup` が `Wait()` を呼び出すたびにセマフォを動的に割り当てていました (`wg.sema = new(uint32)`)。これは、前述の誤解された競合シナリオを回避するための方策でしたが、そのシナリオが誤用であると判断されたため、動的な割り当ては不要になりました。
新しい実装では、`WaitGroup` 構造体自体が `sema uint32` フィールドを保持し、この単一のセマフォを再利用します。これにより、メモリ割り当てが削減され、ガベージコレクションの負担も軽減されます。

**4. `Add` メソッドの変更点:**
*   `atomic.AddUint64(statep, uint64(delta)<<32)`: `delta` を32ビット左シフトすることで、`uint64` の上位32ビット（カウンタ部分）に `delta` をアトミックに加算します。
*   カウンタが0になり、かつ待機者 (`waiters`) が存在する場合、`runtime_Semrelease` を呼び出して全ての待機ゴルーチンを解放します。この際、`*statep = 0` とすることで、カウンタと待機者数を同時に0にリセットします。
*   `WaitGroup` の誤用（`Add` が `Wait` と同時に呼び出されるなど）を検出するためのパニック条件が追加されました。

**5. `Wait` メソッドの変更点:**
*   無限ループ内で `atomic.LoadUint64` と `atomic.CompareAndSwapUint64` を使用して、待機者数をアトミックにインクリメントしようとします。
*   カウンタが既に0であれば、すぐにリターンします。
*   待機者数のインクリメントに成功した場合、`runtime_Semacquire(&wg.sema)` を呼び出してセマフォを獲得し、ブロックします。
*   `WaitGroup` の誤用（以前の `Wait` が戻る前に `WaitGroup` が再利用されるなど）を検出するためのパニック条件が追加されました。

これらの変更により、`WaitGroup` の内部ロジックは大幅に簡素化され、`Add` と `Wait` の両方が単一のアトミックなRead-Modify-Write操作で状態を更新できるようになりました。

## コアとなるコードの解説

### `WaitGroup` 構造体の変更

```go
type WaitGroup struct {
	// 64-bit value: high 32 bits are counter, low 32 bits are waiter count.
	// 64-bit atomic operations require 64-bit alignment, but 32-bit
	// compilers do not ensure it. So we allocate 12 bytes and then use
	// the aligned 8 bytes in them as state.
	state1 [12]byte
	sema   uint32
}
```
*   以前の `m Mutex`, `counter int32`, `waiters int32`, `sema *uint32` が削除され、`state1 [12]byte` と `sema uint32` に置き換えられました。
*   `state1 [12]byte`: `WaitGroup` のカウンタと待機者数を格納する `uint64` のための領域です。32ビットシステムでの8バイトアライメントを保証するために12バイト確保されています。
*   `sema uint32`: Goランタイムの低レベルセマフォ (`runtime_Semacquire`, `runtime_Semrelease`) を操作するためのセマフォ変数です。以前はポインタ (`*uint32`) で動的に割り当てられていましたが、固定の `uint32` に変更され、再利用されます。

### `state()` メソッド

```go
func (wg *WaitGroup) state() *uint64 {
	if uintptr(unsafe.Pointer(&wg.state1))%8 == 0 {
		return (*uint64)(unsafe.Pointer(&wg.state1))
	} else {
		return (*uint64)(unsafe.Pointer(&wg.state1[4]))
	}
}
```
*   `state1` 配列内の8バイトアライメントされた `uint64` 変数へのポインタを返します。
*   `uintptr(unsafe.Pointer(&wg.state1))%8 == 0` で、`state1` の先頭アドレスが8バイトアライメントされているかを確認します。
*   アライメントされていれば `state1` の先頭を、そうでなければ `state1[4]` のアドレスを `*uint64` にキャストして返します。これにより、常にアトミック操作が可能な `uint64` アドレスが保証されます。

### `Add` メソッドの主要な変更点

```go
func (wg *WaitGroup) Add(delta int) {
	statep := wg.state()
	// ... (race detection code) ...

	state := atomic.AddUint64(statep, uint64(delta)<<32)
	v := int32(state >> 32) // counter
	w := uint32(state)      // waiters

	// ... (race detection and panic for negative counter) ...

	if w != 0 && delta > 0 && v == int32(delta) {
		panic("sync: WaitGroup misuse: Add called concurrently with Wait")
	}
	if v > 0 || w == 0 {
		return
	}
	// This goroutine has set counter to 0 when waiters > 0.
	// Now there can't be concurrent mutations of state:
	// - Adds must not happen concurrently with Wait,
	// - Wait does not increment waiters if it sees counter == 0.
	// Still do a cheap sanity check to detect WaitGroup misuse.
	if *statep != state {
		panic("sync: WaitGroup misuse: Add called concurrently with Wait")
	}
	// Reset waiters count to 0.
	*statep = 0
	for ; w != 0; w-- {
		runtime_Semrelease(&wg.sema)
	}
}
```
*   `statep := wg.state()`: `WaitGroup` の内部状態 (`uint64`) へのポインタを取得します。
*   `state := atomic.AddUint64(statep, uint64(delta)<<32)`: `delta` を32ビット左シフト (`<<32`) することで、`uint64` の上位32ビット（カウンタ部分）に `delta` をアトミックに加算します。これにより、カウンタの更新と同時に、その時点での待機者数も含む新しい状態が取得されます。
*   `v := int32(state >> 32)`: 更新後の `uint64` 状態からカウンタ値（上位32ビット）を抽出します。
*   `w := uint32(state)`: 更新後の `uint64` 状態から待機者数（下位32ビット）を抽出します。
*   `if w != 0 && delta > 0 && v == int32(delta)`: `WaitGroup` の誤用を検出する新しいパニック条件です。`Wait` が既に呼び出されている状態で `Add` が行われた場合（特にカウンタが0から正の値に変わる場合）に発生します。
*   カウンタが0になり、かつ待機者が存在する場合 (`v > 0 || w == 0` の条件が偽の場合)、待機中のゴルーチンを解放します。
*   `if *statep != state`: 別の `WaitGroup` 誤用検出。カウンタが0になった直後に、他のゴルーチンが状態を不正に変更した場合にパニックします。
*   `*statep = 0`: カウンタと待機者数を0にリセットします。
*   `for ; w != 0; w-- { runtime_Semrelease(&wg.sema) }`: 待機者数 `w` の分だけ `runtime_Semrelease` を呼び出し、待機中のゴルーチンを全て解放します。

### `Wait` メソッドの主要な変更点

```go
func (wg *WaitGroup) Wait() {
	statep := wg.state()
	// ... (race detection code) ...

	for {
		state := atomic.LoadUint64(statep)
		v := int32(state >> 32) // counter
		w := uint32(state)      // waiters

		if v == 0 {
			// Counter is 0, no need to wait.
			// ... (race detection code) ...
			return
		}
		// Increment waiters count.
		if atomic.CompareAndSwapUint64(statep, state, state+1) {
			// ... (race detection code) ...
			runtime_Semacquire(&wg.sema)
			if *statep != 0 {
				panic("sync: WaitGroup is reused before previous Wait has returned")
			}
			// ... (race detection code) ...
			return
		}
	}
}
```
*   `statep := wg.state()`: `WaitGroup` の内部状態 (`uint64`) へのポインタを取得します。
*   `for {}`: 状態の更新が成功するまでループを繰り返します（スピンロックのような動作）。
*   `state := atomic.LoadUint64(statep)`: 現在の `uint64` 状態をアトミックに読み込みます。
*   `v := int32(state >> 32)`: カウンタ値を取得します。
*   `w := uint32(state)`: 待機者数を取得します。
*   `if v == 0`: カウンタが0であれば、待つ必要がないためすぐにリターンします。
*   `if atomic.CompareAndSwapUint64(statep, state, state+1)`: 現在の状態が `state` と同じであれば、待機者数（下位32ビット）を1増やした新しい状態 (`state+1`) にアトミックに更新します。この操作が成功した場合のみ、セマフォを獲得します。
*   `runtime_Semacquire(&wg.sema)`: セマフォを獲得し、カウンタが0になるまでゴルーチンをブロックします。
*   `if *statep != 0`: `WaitGroup` の誤用を検出する新しいパニック条件です。`Wait` が戻る前に `WaitGroup` が再利用された場合（つまり、`Wait` がブロックから解放されたにもかかわらず、`statep` が0になっていない場合）に発生します。

### テストファイルの変更点

*   `TestWaitGroupMisuse2` と `TestWaitGroupMisuse3`: `WaitGroup` の誤用（`Add` と `Wait` の同時実行、`Wait` が戻る前の `WaitGroup` の再利用）を意図的に引き起こし、新しいパニック条件が正しく機能するかを検証するテストが追加されました。これらのテストは、競合状態を検出するために多数のイテレーションを実行します。

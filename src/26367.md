# [インデックス 26367] ファイルの概要

このコミットは、Go言語の`go/types`パッケージにおける`Importer2`インターフェースを`ImporterFrom`に名称変更するものです。この変更は、特にGo 1.5で導入されたベンダーリング（vendoring）機能との関連性を明確にし、APIの意図をより正確に反映させることを目的としています。`ImporterFrom`インターフェースは、インポート元のディレクトリ情報（`srcDir`）を考慮してパッケージをインポートする機能を提供し、ベンダーリングされたパッケージの解決を可能にします。

## 変更の背景

このコミットの背景には、Go言語の依存関係管理の進化、特にGo 1.5で導入されたベンダーリング（vendoring）機能があります。`go/types`パッケージは、Goプログラムの静的型チェックを行うための重要なツールであり、外部パッケージのインポート解決を担っています。

当初、`Importer`インターフェースは基本的なインポート解決を提供していましたが、ベンダーリングされたパッケージ（プロジェクト内の`vendor/`ディレクトリに配置された依存関係）を正しく解決するためには、インポート元のパッケージのディレクトリ情報が必要となりました。この要件を満たすために`Importer2`という新しいインターフェースが導入されましたが、その名称は機能の意図を十分に伝えていませんでした。

`golang-dev`メーリングリストでの議論（`https://groups.google.com/forum/#!topic/golang-dev/javNmryAh0I`）を経て、`Importer2`が`srcDir`（ソースディレクトリ）からのインポートをサポートする、つまり「どこからインポートされたか」という文脈を考慮するインターフェースであることを明確にするため、`ImporterFrom`という名称に変更することが決定されました。これにより、APIの意図がより明確になり、開発者が適切なインポーターを選択しやすくなりました。

## 前提知識の解説

### `go/types`パッケージ

`go/types`パッケージは、Go言語のツールチェインの中核をなすコンポーネントであり、Goプログラムの静的型情報を分析し、型チェックを実行するために使用されます。これは、リンター、静的解析ツール、IDE、コード生成ツールなど、Goコードを解析する多くの開発ツールにとって不可欠な基盤となります。`go/types`は、抽象構文木（AST）を走査し、名前解決、定数畳み込み、型推論などのプロセスを通じて、プログラムの型の一貫性と正確性を検証します。

### `Importer`インターフェース

`go/types`パッケージにおける`Importer`インターフェースは、Goのパッケージインポートパスを実際のパッケージ情報（`*types.Package`）に解決するための基本的なメカニズムを提供します。このインターフェースは`Import(path string) (*Package, error)`という単一のメソッドを持ち、与えられたインポートパスに対応するパッケージを返します。しかし、この基本的な`Importer`は、Go 1.5で導入されたベンダーリングのような、より複雑なインポート解決のシナリオには対応していませんでした。

### `ImporterFrom`インターフェース（旧`Importer2`）

`ImporterFrom`インターフェース（このコミット以前は`Importer2`という名称）は、`Importer`インターフェースを拡張し、特にベンダーリングされたパッケージのインポートをサポートするために設計されました。このインターフェースは、`ImportFrom(path, srcDir string, mode ImportMode) (*Package, error)`メソッドを提供します。ここで重要なのは`srcDir`パラメータです。これは、インポートを要求しているパッケージのソースディレクトリを示し、これにより`go/types`は、`vendor/`ディレクトリ内のパッケージを正しく解決できるようになります。`ImporterFrom`は、`Importer`インターフェースを埋め込むことで後方互換性も維持しています。

### Goのベンダーリング (Vendoring)

Go 1.5で実験的に導入されたベンダーリングは、プロジェクトの依存関係をプロジェクト自身の`vendor/`ディレクトリ内にコピーして管理するメカニズムです。これにより、ビルドの再現性が向上し、外部の依存関係リポジトリの可用性や変更に左右されずにプロジェクトをビルドできるようになります。`go`コマンドは、インポートパスを解決する際に、まずプロジェクトルートの`vendor/`ディレクトリ内を検索し、次に`GOPATH`を検索するという優先順位で動作します。この機能は、Go Modulesが導入されるまでの間、Goの依存関係管理における重要なステップでした。`go15vendor`という環境変数を設定することで有効化されていました。

## 技術的詳細

このコミットは、`go/types`パッケージのAPIにおける`Importer2`インターフェースの名称を`ImporterFrom`に変更するという、一見すると単純な変更ですが、その背後にはGo言語の依存関係解決メカニズムの進化とAPI設計の明確化という重要な意図があります。

`Importer2`という名称は、単に`Importer`の「2番目のバージョン」という印象を与え、その具体的な機能、特にベンダーリングされたパッケージのインポート解決における`srcDir`パラメータの重要性を十分に伝えていませんでした。`ImporterFrom`という新しい名称は、「どこから（From）インポートされたか」という文脈情報（`srcDir`）を考慮してインポート解決を行うインターフェースであるという、その本質的な役割をより正確に表現しています。

この名称変更は、`go/types`パッケージを利用するツール（例えば、静的解析ツールやIDE）の開発者にとって、どのインポーターインターフェースを使用すべきかを判断する際の混乱を減らす効果があります。`ImporterFrom`を使用することで、ツールはGo 1.5以降のベンダーリング規則に準拠した形でパッケージをインポートできるようになり、より堅牢で正確な型チェックやコード解析が可能になります。

変更はGo 1.6のAPIの一部として導入され、`api/go1.6.txt`にもその変更が記録されています。これは、GoのAPIの安定性と互換性を維持しつつ、機能改善を行うための標準的なプロセスに従ったものです。

## コアとなるコードの変更箇所

このコミットでは、以下のファイルが変更されています。

1.  **`api/go1.6.txt`**:
    *   Go 1.6の公開APIリストに`go/types`パッケージの`ImportMode`型と`ImporterFrom`インターフェース、およびその`Import`と`ImportFrom`メソッドが追加されています。これは、この変更がGo 1.6の公式APIの一部となることを示しています。

2.  **`src/go/importer/importer.go`**:
    *   `Default()`関数のコメントが、結果が`types.Importer2`ではなく`types.ImporterFrom`を実装する可能性があることを示すように更新されています。
    *   `gcimports`および`gccgoimports`型における`Import2`メソッドの名前が`ImportFrom`に変更されています。これに伴い、`Import`メソッド内での`Import2`の呼び出しも`ImportFrom`に更新されています。

3.  **`src/go/types/api.go`**:
    *   `Importer`インターフェースのコメントが更新され、ベンダーリングに関する注意書きが`ImporterFrom`を参照するように変更されています。
    *   `Importer2`インターフェースの定義が`ImporterFrom`に名称変更されています。
    *   `ImporterFrom`インターフェース内のコメントが更新され、`Import(path)`が`ImportFrom(path, "", 0)`と同じであること、および`types`パッケージが`ImporterFrom`が存在する場合は`Import`を呼び出さないことが明記されています。
    *   `ImporterFrom`インターフェース内の`Import2`メソッドの定義が`ImportFrom`に名称変更されています。
    *   `Config`構造体の`Importer`フィールドに関するコメントが、`ImporterFrom`を参照するように更新されています。

4.  **`src/go/types/resolver.go`**:
    *   `check.conf.Importer`が`Importer2`型であるかどうかの型アサーションが、`ImporterFrom`型であるかどうかのチェックに更新されています。
    *   エラーメッセージ内の`Config.Importer.Import2`が`Config.Importer.ImportFrom`に修正されています。

5.  **`src/go/types/resolver_test.go`**:
    *   `resolveTestImporter`構造体のフィールド`importer`の型が`Importer2`から`ImporterFrom`に変更されています。
    *   `Import2`メソッドの名前が`ImportFrom`に変更され、内部での`imp.importer.Import2`の呼び出しも`imp.importer.ImportFrom`に更新されています。

## コアとなるコードの解説

このコミットの核心は、`src/go/types/api.go`におけるインターフェースの名称変更と、それに伴う関連コードの修正です。

`src/go/types/api.go`では、以下のようにインターフェースの定義が変更されています。

```go
// Old:
// type Importer2 interface { ... Import2(...) ... }
// New:
type ImporterFrom interface {
	// Importer is present for backward-compatibility. Calling
	// Import(path) is the same as calling ImportFrom(path, "", 0);
	// i.e., locally vendored packages may not be found.
	// The types package does not call Import if an ImporterFrom
	// is present.
	Importer

	// ImportFrom returns the imported package for the given import
	// path when imported by the package in srcDir, or an error
	// if the package couldn't be imported. The mode value must
	// be 0; it is reserved for future use.
	// Two calls to ImportFrom with the same path and srcDir return
	// the same package.
	ImportFrom(path, srcDir string, mode ImportMode) (*Package, error)
}
```

この変更により、`ImporterFrom`インターフェースが`Importer`インターフェースを埋め込みつつ、`ImportFrom`という新しい（しかし実質的には`Importer2`の機能を引き継いだ）メソッドを提供することが明確になります。`ImportFrom`メソッドの`srcDir`パラメータは、インポート元のパッケージの物理的な場所を示し、これによりGoのベンダーリング規則に従って、`vendor/`ディレクトリ内のパッケージを優先的に解決することが可能になります。

`src/go/importer/importer.go`では、`go/importer`パッケージが提供する具体的なインポーター実装（`gcimports`や`gccgoimports`）が、この新しい`ImporterFrom`インターフェースに準拠するように更新されています。具体的には、`Import2`メソッドが`ImportFrom`にリネームされ、その内部ロジックは変更されていません。これは、機能自体は維持しつつ、APIの名称だけが変更されたことを示しています。

```go
// Old:
// func (m gcimports) Import2(path, srcDir string, mode types.ImportMode) (*types.Package, error) { ... }
// New:
func (m gcimports) ImportFrom(path, srcDir string, mode types.ImportMode) (*types.Package, error) {
	// ... existing logic ...
}
```

`src/go/types/resolver.go`では、型チェッカーがインポーターを解決する際に、`Config.Importer`が`ImporterFrom`インターフェースを実装しているかどうかをチェックするように変更されています。これにより、型チェッカーはベンダーリングをサポートするインポーターを優先的に使用し、より正確なインポート解決を行うことができます。

これらの変更は、Goの型システムと依存関係解決の堅牢性を高め、Goツールエコシステム全体の信頼性を向上させる上で重要な役割を果たします。

# [インデックス 23472] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/5l`, `cmd/6l`, `cmd/7l`, `cmd/8l`, `cmd/9l` など、異なるアーキテクチャ向けのリンカ) における `adddynsym` 関数の実装を統合するものです。これにより、コードの重複が削減され、ELF (Executable and Linkable Format) ダイナミックシンボル追加ロジックの一貫性が向上します。

## コミット

`adddynsym` 関数の実装が、各アーキテクチャ固有のリンカ (`cmd/5l`, `cmd/6l`, `cmd/7l`, `cmd/8l`, `cmd/9l`) から、共通の内部リンカパッケージ (`src/cmd/internal/ld`) へと集約されました。これにより、ELF32とELF64の違いのみが本質的な差異となり、それ以外の差異は以前のバージョンにおけるバグであった可能性が示唆されています。

## 変更の背景

Go言語のツールチェイン、特にリンカは、複数の異なるCPUアーキテクチャ（例: ARM (5l), AMD64 (6l), ARM64 (7l), 386 (8l), PowerPC (9l)）をサポートしています。以前は、これらのアーキテクチャごとにダイナミックシンボルを追加するロジック (`adddynsym`) が個別に実装されていました。しかし、これらの実装には多くの共通部分があり、ELF32とELF64のデータ構造の違いを除けば、本質的な差異は少ないと認識されていました。

このような重複したコードは、保守性の低下、バグの発生リスクの増加、および新機能追加時の開発コスト増大につながります。このコミットの背景には、これらの問題を解決し、リンカのコードベースをよりクリーンで効率的、かつ保守しやすいものにするという目的があります。特に、異なるアーキテクチャ間での微妙な実装の差異がバグの原因となる可能性があったため、共通化によってそのリスクを低減しようとしています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が前提となります。

1.  **Go言語のリンカ (Linker):**
    Go言語のコンパイラは、ソースコードをオブジェクトファイルに変換します。リンカは、これらのオブジェクトファイルと必要なライブラリを結合して、実行可能なバイナリファイルを生成するツールです。Goのリンカは、`cmd/5l`, `cmd/6l`, `cmd/7l`, `cmd/8l`, `cmd/9l` のように、ターゲットアーキテクチャごとに異なる名前が付けられています（例: `5l` はARM、`6l` はAMD64、`8l` は386）。

2.  **ELF (Executable and Linkable Format):**
    LinuxやUnix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、プログラムのコード、データ、シンボルテーブル、リロケーション情報などを含みます。

3.  **ダイナミックシンボル (Dynamic Symbols):**
    共有ライブラリ（ダイナミックリンクライブラリ、DLL）を使用するプログラムにおいて、実行時に解決されるシンボル（関数や変数）のことです。リンカは、これらのダイナミックシンボルをELFファイルの `.dynsym` セクションに記録し、実行時にローダーがシンボル解決を行います。

4.  **`adddynsym` 関数:**
    リンカの内部関数で、ELFバイナリのダイナミックシンボルテーブル (`.dynsym` セクション) に新しいシンボルエントリを追加する役割を担います。この関数は、外部ライブラリからインポートされるシンボルや、Cgoを通じてエクスポートされるシンボルなどを処理する際に呼び出されます。

5.  **ELF32 vs ELF64:**
    ELFフォーマットには、32ビットシステム向けのELF32と、64ビットシステム向けのELF64があります。これらは、アドレスサイズ、データ構造のオフセット、サイズなどが異なります。例えば、シンボルテーブルのエントリサイズや、アドレスを格納するフィールドのバイト数が異なります。

6.  **`ld` パッケージ (`src/cmd/internal/ld`):**
    Goリンカの共通ロジックをカプセル化している内部パッケージです。アーキテクチャに依存しない、またはアーキテクチャ固有の処理を抽象化して提供する役割を担います。

## 技術的詳細

このコミットの主要な技術的変更は、各アーキテクチャリンカ (`cmd/5l`, `cmd/6l`, `cmd/7l`, `cmd/8l`, `cmd/9l`) に分散していた `adddynsym` 関数の実装を、`src/cmd/internal/ld` パッケージ内の共通関数に集約した点です。

具体的には、以下の変更が行われました。

1.  **`src/cmd/internal/ld/elf.go` に `Elfadddynsym` 関数を新設:**
    この関数は、ELF32とELF64の両方に対応できるように、内部で `elf64` フラグをチェックして処理を分岐させます。これにより、シンボル名、値、サイズ、タイプ、セクションインデックスなどのELFシンボルエントリの構築ロジックが、一元的に管理されるようになりました。
    *   `s.Dynid` の割り当て: 各シンボルに一意のダイナミックシンボルIDを割り当てます。
    *   `.dynsym` セクションへの書き込み: シンボルの名前（`.dynstr` へのオフセット）、値（アドレス）、サイズ、タイプ（関数かオブジェクトか）、バインディング（グローバルかローカルか）、可視性、セクションインデックス（未定義か、定義済みセクションか）をELFシンボルエントリとして書き込みます。
    *   ELF64の場合、`DT_NEEDED` エントリの追加ロジックも含まれており、これは共有ライブラリの依存関係をリンカに伝えるためのものです。

2.  **`src/cmd/internal/ld/go.go` に `Adddynsym` 関数を新設:**
    この関数は、アーキテクチャ固有のリンカから呼び出される新しいエントリポイントとなります。内部で `Iself` (ELF形式であるか) や `HEADTYPE` (Darwin, Windowsなど) をチェックし、ELF形式の場合は新設された `Elfadddynsym` を呼び出します。これにより、ELF以外のフォーマット（例: Mach-O for Darwin, PE for Windows）に対する `adddynsym` の呼び出しも、この共通関数を通じて処理されるようになります。

3.  **各アーキテクチャリンカからの `adddynsym` 関数の削除と呼び出し箇所の変更:**
    `src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/7l/asm.go`, `src/cmd/8l/asm.go`, `src/cmd/9l/asm.go` から、ローカルな `adddynsym` 関数が削除されました。
    これらのファイル内の `adddynrel`, `addpltsym`, `addgotsym` などの関数内で `adddynsym(ld.Ctxt, targ)` のように直接呼び出されていた箇所は、すべて `ld.Adddynsym(ld.Ctxt, targ)` のように、`ld` パッケージの共通関数を呼び出すように変更されました。

4.  **`ld.Thearch.Adddynsym` フィールドの削除:**
    `src/cmd/internal/ld/lib.go` に定義されていた `Thearch` 構造体から、アーキテクチャ固有の `Adddynsym` 関数ポインタが削除されました。これは、`adddynsym` の実装が共通化され、アーキテクチャ固有のディスパッチが不要になったことを意味します。

この変更により、リンカのコードベースは大幅に簡素化され、ELFシンボル処理ロジックの信頼性と保守性が向上しました。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに集中しています。

1.  **`src/cmd/internal/ld/elf.go`**:
    *   `Elfadddynsym` 関数が新規追加されました。この関数は、ELF32とELF64のシンボルエントリの生成ロジックをカプセル化しています。

2.  **`src/cmd/internal/ld/go.go`**:
    *   `Adddynsym` 関数が新規追加されました。これは、各アーキテクチャリンカから呼び出される共通のエントリポイントとなり、内部で `Elfadddynsym` を呼び出します。
    *   `Seenlib` マップが `seenlib` にリネームされ、プライベート変数になりました。

3.  **`src/cmd/*/asm.go` (例: `src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/8l/asm.go`, `src/cmd/9l/asm.go`)**:
    *   各ファイルに存在していたローカルな `adddynsym` 関数が削除されました。
    *   `adddynrel`, `addpltsym`, `addgotsym` などの関数内で `adddynsym` を呼び出していた箇所が、`ld.Adddynsym` を呼び出すように変更されました。

4.  **`src/cmd/*/obj.go` (例: `src/cmd/5l/obj.go`, `src/cmd/6l/obj.go`, `src/cmd/7l/obj.go`, `src/cmd/8l/obj.go`, `src/cmd/9l/obj.go`)**:
    *   `linkarchinit` 関数内で `ld.Thearch.Adddynsym = adddynsym` のような行が削除されました。

5.  **`src/cmd/internal/ld/lib.go`**:
    *   `Arch` 構造体から `Adddynsym func(*Link, *LSym)` フィールドが削除されました。

## コアとなるコードの解説

### `src/cmd/internal/ld/elf.go` における `Elfadddynsym` (新規追加)

```go
func Elfadddynsym(ctxt *Link, s *LSym) {
	if elf64 { // 64ビットELFの場合
		s.Dynid = int32(Nelfsym)
		Nelfsym++

		d := Linklookup(ctxt, ".dynsym", 0) // .dynsymセクションを取得

		name := s.Extname
		Adduint32(ctxt, d, uint32(Addstring(Linklookup(ctxt, ".dynstr", 0), name))) // シンボル名を .dynstr に追加し、そのオフセットを記録

		/* type */
		t := STB_GLOBAL << 4 // グローバルシンボルとして設定
		if s.Cgoexport != 0 && s.Type&obj.SMASK == obj.STEXT {
			t |= STT_FUNC // Cgoエクスポートされたテキストシンボルは関数
		} else {
			t |= STT_OBJECT // それ以外はオブジェクト
		}
		Adduint8(ctxt, d, uint8(t)) // シンボルタイプとバインディングを記録
		Adduint8(ctxt, d, 0)        // 予約済みバイト

		/* section where symbol is defined */
		if s.Type == obj.SDYNIMPORT {
			Adduint16(ctxt, d, SHN_UNDEF) // 動的インポートシンボルは未定義セクション
		} else {
			Adduint16(ctxt, d, 1) // それ以外はセクション1 (通常はテキストセクション)
		}

		/* value */
		if s.Type == obj.SDYNIMPORT {
			Adduint64(ctxt, d, 0) // 動的インポートシンボルは値0
		} else {
			Addaddr(ctxt, d, s) // それ以外はシンボルのアドレス
		}

		/* size of object */
		Adduint64(ctxt, d, uint64(s.Size)) // オブジェクトのサイズ

		// AMD64 (Thechar == '6') の場合、Cgoエクスポートされていない動的ライブラリ依存を追加
		if Thearch.Thechar == '6' && s.Cgoexport&CgoExportDynamic == 0 && s.Dynimplib != "" && !seenlib[s.Dynimplib] {
			Elfwritedynent(Linklookup(ctxt, ".dynamic", 0), DT_NEEDED, uint64(Addstring(Linklookup(ctxt, ".dynstr", 0), s.Dynimplib)))
		}
	} else { // 32ビットELFの場合 (同様のロジックだが、データサイズが32ビットに最適化されている)
		s.Dynid = int32(Nelfsym)
		Nelfsym++

		d := Linklookup(ctxt, ".dynsym", 0)

		name := s.Extname
		Adduint32(ctxt, d, uint32(Addstring(Linklookup(ctxt, ".dynstr", 0), name)))

		/* value */
		if s.Type == obj.SDYNIMPORT {
			Adduint32(ctxt, d, 0)
		} else {
			Addaddr(ctxt, d, s)
		}

		/* size */
		Adduint32(ctxt, d, 0) // 32ビットELFではサイズは0

		/* type */
		t := STB_GLOBAL << 4
		// TODO(mwhudson): presumably the behaviour should actually be the same on both arm and 386.
		// ARM (Thechar == '8') と 386 (Thechar == '5') でのCgoエクスポートされた関数シンボルの扱い
		if Thearch.Thechar == '8' && s.Cgoexport != 0 && s.Type&obj.SMASK == obj.STEXT {
			t |= STT_FUNC
		} else if Thearch.Thechar == '5' && s.Cgoexport&CgoExportDynamic != 0 && s.Type&obj.SMASK == obj.STEXT {
			t |= STT_FUNC
		} else {
			t |= STT_OBJECT
		}
		Adduint8(ctxt, d, uint8(t))
		Adduint8(ctxt, d, 0)

		/* shndx */
		if s.Type == obj.SDYNIMPORT {
			Adduint16(ctxt, d, SHN_UNDEF)
		} else {
			Adduint16(ctxt, d, 1)
		}
	}
}
```
この関数は、ELFシンボルテーブルエントリの構造を直接操作し、シンボルの属性（名前、値、サイズ、タイプなど）をELFフォーマットの仕様に従って `.dynsym` セクションに書き込みます。`elf64` フラグによって、32ビットと64ビットのELFフォーマットの違い（特にアドレスやサイズのフィールド長）が適切に処理されます。

### `src/cmd/internal/ld/go.go` における `Adddynsym` (新規追加)

```go
func Adddynsym(ctxt *Link, s *LSym) {
	if s.Dynid >= 0 { // 既にダイナミックシンボルIDが割り当てられていれば何もしない
		return
	}

	if Iself { // ELF形式のバイナリの場合
		Elfadddynsym(ctxt, s) // Elfadddynsym を呼び出してELFシンボルを追加
	} else if HEADTYPE == obj.Hdarwin { // Darwin (Mach-O) の場合
		Diag("adddynsym: missed symbol %s (%s)", s.Name, s.Extname) // 未実装またはエラー
	} else if HEADTYPE == obj.Hwindows { // Windows (PE) の場合
		// already taken care of // 既に他の場所で処理されている
	} else { // その他の未サポートのバイナリフォーマットの場合
		Diag("adddynsym: unsupported binary format") // エラー
	}
}
```
この関数は、リンカがシンボルをダイナミックシンボルテーブルに追加する必要があるときに呼び出される共通のラッパー関数です。ターゲットのバイナリフォーマット（ELF, Mach-O, PEなど）を判別し、適切な処理（ELFの場合は `Elfadddynsym` の呼び出し）にディスパッチします。これにより、各アーキテクチャリンカは、バイナリフォーマットの詳細を意識することなく、一貫した方法でダイナミックシンボルを追加できるようになりました。

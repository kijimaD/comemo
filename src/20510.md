# [インデックス 20510] ファイルの概要

このコミットは、Goランタイムのシステムコール関連のアセンブリコードに`GO_ARGS`ディレクティブを追加するものです。これにより、特にLinux/386環境でのビルドにおける「型なし引数 (untyped args)」に起因する散発的なビルド失敗を修正し、Goのガベージコレクタがアセンブリ関数内のスタックレイアウトを正しく理解できるようになります。

## 元コミット内容

`syscall: add GO_ARGS to Go-called assembly`

このコミットは、Goから呼び出されるアセンブリコードに`GO_ARGS`ディレクティブを追加します。これにより、Linux/386環境での散発的なビルド失敗（型なし引数によるもの）や、まだ発見されていない他の問題が修正されます。

関連するIssue: #8727

## 変更の背景

Go言語のランタイムは、パフォーマンスが重要な部分や、OSのシステムコールを直接呼び出す必要がある部分でアセンブリ言語を使用します。アセンブリ言語で書かれた関数がGoのコードから呼び出される際、Goのガベージコレクタ（GC）は、そのアセンブリ関数のスタックフレーム上に存在するポインタを正確に識別し、追跡する必要があります。これにより、GCが誤って使用中のメモリを解放したり、到達可能なオブジェクトを回収し損ねたりするのを防ぎます。

このコミットの背景には、特にLinux/386アーキテクチャにおいて、Goから呼び出されるアセンブリ関数（特にシステムコール関連）で、ガベージコレクタがスタック上の引数を正しく認識できない問題があったと考えられます。コミットメッセージにある「untyped args（型なし引数）」という記述は、GCが引数の型情報を欠いている、あるいは誤って解釈している状態を示唆しています。これが原因で、散発的なビルド失敗が発生していました。

`Fixes #8727`とありますが、Goの公式Issueトラッカーで直接この番号のIssueを見つけることはできませんでした。しかし、コミットメッセージの内容から、このIssueはアセンブリコードとGoランタイムの連携、特にガベージコレクションにおけるスタックフレームの解釈に関するバグ報告であったと推測されます。

## 前提知識の解説

*   **Goのアセンブリ言語**: Goは、特定のプラットフォームやパフォーマンス要件のために、Go言語自体ではなくアセンブリ言語で書かれたコードを使用することがあります。Goのアセンブリ言語は、一般的なアセンブリ言語とは異なり、Goツールチェインによって抽象化された擬似命令セットを使用します。これにより、異なるアーキテクチャ間での移植性が高められています。
*   **ガベージコレクション (GC)**: Goは自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムが不要になったメモリを自動的に解放し、メモリリークを防ぎます。GCが正しく動作するためには、プログラムの実行中にどのメモリ領域がポインタを含み、どのポインタが有効なオブジェクトを指しているかを正確に知る必要があります。
*   **スタックフレーム**: 関数が呼び出されると、その関数に必要なローカル変数、引数、戻りアドレスなどがスタック上に確保されます。これをスタックフレームと呼びます。GCは、スタックフレームをスキャンしてポインタを識別し、ヒープ上のオブジェクトを追跡します。
*   **`TEXT`ディレクティブ**: Goのアセンブリ言語で関数を定義する際に使用されるディレクティブです。例えば、`TEXT ·socketcall(SB),NOSPLIT,$0-36`は、`socketcall`というGo関数に対応するアセンブリコードの開始を示し、スタックフレームのサイズなどを指定します。
*   **`GO_ARGS`ディレクティブ**: Goのアセンブリ言語における特別なディレクティブです。このディレクティブは、Goアセンブラに対して、そのアセンブリ関数の引数のスタックマップ情報が、対応するGoのプロトタイプ宣言（Go言語での関数シグネチャ）から取得できることを伝えます。これにより、Goのガベージコレクタは、アセンブリ関数がGoから呼び出された際に、スタック上の引数領域にポインタが含まれているかどうかを正確に判断し、適切にGCを実行できるようになります。`GO_ARGS`は、GCがスタックをスキャンする際に、どのメモリ領域がポインタであるかを識別するために不可欠な情報を提供します。
*   **`NO_LOCAL_POINTERS`ディレクティブ**: Goのアセンブリ言語におけるディレクティブで、その関数がローカルポインタを持たないことをガベージコレクタに伝えます。これにより、GCはその関数のスタックフレームをポインタのためにスキャンする必要がなくなり、GCの効率が向上します。主に、ポインタを扱わないアセンブリ関数で使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムがアセンブリ関数を呼び出す際の、ガベージコレクタによるスタックフレームの正確な解釈にあります。

Goのガベージコレクタは、スタックをスキャンしてポインタを識別し、到達可能なオブジェクトをマークします。アセンブリ言語で書かれた関数は、Goコンパイラが生成する通常のGoコードとは異なるスタックレイアウトを持つ可能性があります。このため、GCがアセンブリ関数のスタックフレームを正しくスキャンするためには、追加のメタデータが必要になります。

`GO_ARGS`ディレクティブは、このメタデータを提供する役割を担います。具体的には、アセンブリ関数がGoの関数シグネチャ（プロトタイプ）に対応している場合、`GO_ARGS`はGCに対して、そのGoプロトタイプから引数のスタックマップ情報を取得するように指示します。これにより、GCはアセンブリ関数のスタック上の引数領域にポインタが存在するかどうか、そしてそのポインタがどこを指しているかを正確に把握できるようになります。

コミットメッセージにある「untyped args」の問題は、`GO_ARGS`が欠けていた、あるいは正しく機能していなかったために、GCがアセンブリ関数の引数を「型なし」と見なし、ポインタとして扱ってよいかどうかの判断に迷っていたことを示唆しています。これが原因で、GCが誤った判断を下し、メモリの破損やビルドの失敗といった問題を引き起こしていた可能性があります。

このコミットでは、`src/syscall/asm_linux_386.s`、`src/syscall/asm_linux_amd64.s`、`src/syscall/asm_linux_arm.s`、`src/syscall/asm_plan9_386.s`、`src/syscall/asm_plan9_amd64.s`といった複数のシステムコール関連のアセンブリファイルに`GO_ARGS`が追加されています。これは、これらのアセンブリ関数がGoコードから呼び出され、その引数がGCによって正しく扱われる必要があるためです。

また、`src/syscall/asm_plan9_386.s`と`src/syscall/asm_plan9_amd64.s`の`exit`関数には`NO_LOCAL_POINTERS`も追加されています。`exit`関数は通常、プログラムを終了させるためのものであり、ローカルにポインタを保持することは稀です。このディレクティブを追加することで、GCがこの関数のスタックフレームをポインタのためにスキャンする手間を省き、GCの効率を向上させることができます。

 // Import runtime·exit for cleanly exiting.

+\tGO_ARGS
+\tNO_LOCAL_POINTERS
  	MOVL	code+0(FP), AX
  	MOVL	AX, 0(SP)
  	CALL	runtime·exit(SB)

## コアとなるコードの解説

追加された`GO_ARGS`ディレクティブは、Goのアセンブラに対して、そのアセンブリ関数がGoの関数シグネチャ（プロトタイプ）に対応しており、そのプロトタイプから引数のスタックマップ情報を取得できることを伝えます。これにより、Goのガベージコレクタは、これらのアセンブリ関数がGoから呼び出された際に、スタック上の引数領域にポインタが含まれているかどうかを正確に判断し、適切にGCを実行できるようになります。

具体的には、`TEXT ·socketcall(SB),NOSPLIT,$0-36`のような行は、`socketcall`というGo関数に対応するアセンブリコードの開始を宣言しています。この関数の引数はスタック上に配置されます。`GO_ARGS`が追加されることで、ガベージコレクタは`socketcall`のGo言語での定義（`func socketcall(call int, a0, a1, a2, a3, a4, a5 uintptr) (n int, errno int)`）を参照し、どの引数がポインタである可能性があるかを認識します。これにより、「untyped args」の問題が解消され、GCがスタックを安全にスキャンできるようになります。

`exit`関数に追加された`NO_LOCAL_POINTERS`は、この関数がローカルポインタを保持しないことをGCに明示的に伝えます。これにより、GCは`exit`関数のスタックフレームをポインタのためにスキャンする必要がなくなり、GCのオーバーヘッドが削減されます。

これらの変更は、Goランタイムの安定性と正確性を向上させる上で重要な役割を果たします。特に、システムコールのような低レベルの操作では、メモリ管理の正確性がシステムの安定性に直結するため、このような修正は不可欠です。

## コアとなるコードの解説

追加された`GO_ARGS`ディレクティブは、Goのアセンブラに対して、そのアセンブリ関数がGoの関数シグネチャ（プロトタイプ）に対応しており、そのプロトタイプから引数のスタックマップ情報を取得できることを伝えます。これにより、Goのガベージコレクタは、これらのアセンブリ関数がGoから呼び出された際に、スタック上の引数領域にポインタが含まれているかどうかを正確に判断し、適切にGCを実行できるようになります。

具体的には、`TEXT ·socketcall(SB),NOSPLIT,$0-36`のような行は、`socketcall`というGo関数に対応するアセンブリコードの開始を宣言しています。この関数の引数はスタック上に配置されます。`GO_ARGS`が追加されることで、ガベージコレクタは`socketcall`のGo言語での定義（`func socketcall(call int, a0, a1, a2, a3, a4, a5 uintptr) (n int, errno int)`）を参照し、どの引数がポインタである可能性があるかを認識します。これにより、「untyped args」の問題が解消され、GCがスタックを安全にスキャンできるようになります。

`exit`関数に追加された`NO_LOCAL_POINTERS`は、この関数がローカルポインタを保持しないことをGCに明示的に伝えます。これにより、GCは`exit`関数のスタックフレームをポインタのためにスキャンする必要がなくなり、GCのオーバーヘッドが削減されます。

これらの変更は、Goランタイムの安定性と正確性を向上させる上で重要な役割を果たします。特に、システムコールのような低レベルの操作では、メモリ管理の正確性がシステムの安定性に直結するため、このような修正は不可欠です。

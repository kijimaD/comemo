# [インデックス 25737] ファイルの概要

このコミットは、Goコンパイラのx86アーキテクチャ向けオブジェクトファイル生成部分において、Global Offset Table (GOT) を利用するための命令書き換えロジックを独立した関数 `rewriteToUseGot` として切り出すリファクタリングを行っています。これにより、コードの可読性と保守性が向上し、特に386アーキテクチャでの共有ライブラリのサポートが容易になることが期待されます。

## 元コミット内容

このコミットの元々の目的は、Goコンパイラのx86バックエンドにおいて、動的リンクが有効な場合にグローバルデータへのアクセスをGlobal Offset Table (GOT) を介して行うための命令書き換えロジックを、`progedit` 関数から `rewriteToUseGot` という独立した関数に分離することです。これにより、コードのモジュール性が高まり、将来的な共有ライブラリのサポート、特に386アーキテクチャでの実装が簡素化されます。

## 変更の背景

Go言語は、当初は静的リンクを主眼に置いて設計されていましたが、共有ライブラリのサポートは、より柔軟なデプロイメントや既存システムとの連携において重要な機能です。動的リンクされたプログラムでは、実行時に外部ライブラリの関数やデータにアクセスするために、アドレス解決のメカニズムが必要です。その主要なメカニズムの一つがGlobal Offset Table (GOT) と Procedure Linkage Table (PLT) です。

このコミットの背景には、以下の点が挙げられます。

1.  **ARM版での先行事例**: コミットメッセージに「ARM版のレビューコメントでこれを行うよう促された」とあるように、ARMアーキテクチャ向けのGoコンパイラバックエンドで同様のリファクタリングが先行して行われていました。これは、GOTを利用した命令書き換えロジックが複雑になりがちであり、それを独立した関数として管理することのメリットが認識されていたことを示唆しています。
2.  **386共有ライブラリの容易化**: 「386向けの共有ライブラリがより簡単になる」と明記されており、この変更が将来的に32ビットx86 (IA-32) アーキテクチャでの共有ライブラリサポートを改善するための基盤作りであることがわかります。動的リンクでは、コードがロードされるベースアドレスが実行時に決定されるため、絶対アドレスではなく相対アドレスや間接参照を用いる必要があります。GOTはその間接参照を実現するための重要な要素です。
3.  **コードのモジュール化と保守性**: `progedit` のような大きな関数の中にGOT関連のロジックが散在していると、コードの理解や変更が困難になります。独立した関数に切り出すことで、GOT関連の処理が一箇所に集約され、可読性、テスト容易性、保守性が向上します。

## 前提知識の解説

このコミットを理解するためには、以下の概念が不可欠です。

### 1. Global Offset Table (GOT) と Procedure Linkage Table (PLT)

*   **動的リンク (Dynamic Linking)**: プログラムの実行時に、必要なライブラリをメモリにロードし、リンクする方式です。これにより、ディスクスペースの節約、メモリ使用量の削減、ライブラリの更新が容易になるなどのメリットがあります。
*   **位置独立コード (Position-Independent Code, PIC)**: 動的リンクされた共有ライブラリのコードは、メモリ上のどこにロードされても正しく実行できるように設計されている必要があります。これは、コード内のアドレス参照が絶対アドレスではなく、相対アドレスや間接参照を用いることで実現されます。
*   **Global Offset Table (GOT)**: データセクションに存在するテーブルで、共有ライブラリが外部のグローバル変数や関数にアクセスするためのアドレスを格納します。PICでは、直接的な絶対アドレス参照ができないため、GOTを介して間接的にアクセスします。GOTのエントリは、プログラムのロード時に動的リンカによって解決され、実際のメモリアドレスが書き込まれます。
*   **Procedure Linkage Table (PLT)**: コードセクションに存在するテーブルで、共有ライブラリが外部の関数を呼び出すためのメカニズムを提供します。PLTはGOTと連携して動作し、初回呼び出し時に動的リンカが実際の関数アドレスを解決し、以降の呼び出しでは直接そのアドレスにジャンプするようにします。

### 2. Goコンパイラのバックエンドとアセンブラ

*   **`cmd/internal/obj`**: Goコンパイラの内部パッケージで、アセンブラのバックエンドを構成します。各アーキテクチャ（x86, ARMなど）固有のコード生成ロジックが含まれています。
*   **`obj.Prog`**: Goコンパイラの中間表現の一つで、アセンブリ命令を表す構造体です。命令の種類 (Opcode)、オペランド (From, To, From3)、シンボル情報などが含まれます。
*   **`obj.Addr`**: `obj.Prog` のオペランドを表す構造体で、アドレスの種類 (Type)、名前 (Name)、シンボル (Sym)、オフセット (Offset) などが含まれます。
    *   `obj.TYPE_ADDR`: アドレス型オペランド。
    *   `obj.TYPE_MEM`: メモリ型オペランド。
    *   `obj.NAME_EXTERN`: 外部シンボル（グローバル変数や関数）。
    *   `obj.NAME_GOTREF`: GOTを介した参照。
*   **`obj.LSym`**: リンクシンボルを表す構造体。
*   **`ctxt.Flag_dynlink`**: コンテキスト (`obj.Link`) のフラグで、動的リンクが有効かどうかを示します。
*   **`progedit` 関数**: `obj6.go` に存在する関数で、アセンブリ命令 (`obj.Prog`) を走査し、特定の条件に基づいて命令を書き換えたり、最適化を行ったりする役割を担います。このコミット以前は、GOT関連の書き換えロジックもこの関数内に直接記述されていました。
*   **`ADUFFCOPY`, `ADUFFZERO`**: Goランタイムが使用する特殊な命令で、メモリのコピーやゼロクリアを高速に行うためのものです。これらも動的リンク環境ではGOTを介してアドレス解決される必要があります。
*   **`LEAQ` (Load Effective Address)**: x86アセンブリ命令で、オペランドのアドレスをレジスタにロードします。例えば `LEAQ sym(SB), AX` は `sym` のアドレスを `AX` レジスタにロードします。動的リンク環境では、`sym` のアドレスは実行時まで確定しないため、GOTを介した間接参照に変換される必要があります。
*   **`MOVQ` (Move Quadword)**: x86-64アセンブリ命令で、64ビットの値を移動します。

### 3. x86-64 (AMD64) アセンブリのレジスタ

*   **`REG_R15`**: x86-64アーキテクチャの汎用レジスタの一つ。このコミットでは、GOTからアドレスをロードするための一時レジスタとして使用されています。

## 技術的詳細

このコミットの核心は、`progedit` 関数内に散らばっていたGOT関連の命令書き換えロジックを `rewriteToUseGot` という新しい関数に集約した点です。

### `rewriteToUseGot` 関数の役割

`rewriteToUseGot` 関数は、`obj.Prog` 型のアセンブリ命令 `p` を受け取り、動的リンク (`ctxt.Flag_dynlink` が真) が有効な場合に、グローバルデータへのアクセスをGOTを介するように書き換えます。

具体的には、以下の種類の命令を変換します。

1.  **`ADUFFCOPY` / `ADUFFZERO` 命令の変換**:
    *   元の命令: `ADUFFxxx $offset` (例: `ADUFFZERO $0`)
    *   変換後:
        ```assembly
        MOVQ runtime.duffxxx@GOT, R15  // runtime.duffxxx のアドレスをGOTからR15にロード
        ADDQ $offset, R15             // オフセットを加算
        CALL R15                      // R15に格納されたアドレスを呼び出す
        ```
    これは、`runtime.duffzero` や `runtime.duffcopy` といったランタイム関数が動的リンク環境で正しく呼び出されるようにするための変換です。これらの関数は、Goの内部的なメモリ操作に使われるため、そのアドレスもGOT経由で解決される必要があります。

2.  **`LEAQ` 命令の変換**:
    *   元の命令: `LEAQ sym(SB), Rx` (例: `LEAQ name(SB), AX`)
    *   変換後: `MOVQ $sym, Rx` (これはさらに後続の処理で `MOVQ sym@GOT(SB), Rx` に変換されます)
    `LEAQ` 命令は通常、アドレスをレジスタにロードしますが、動的リンク環境ではシンボルの絶対アドレスがコンパイル時には不明です。そのため、まずシンボルのアドレスを直接レジスタに移動する `MOVQ $sym, Rx` に変換し、その後の処理でGOT参照に変換されるように準備します。

3.  **グローバルデータへの `MOVQ` 命令の変換**:
    *   元の命令: `MOVQ $sym, Rx` (シンボルのアドレスをレジスタにロード)
    *   変換後:
        ```assembly
        MOVQ sym@GOT, Rx  // sym のアドレスをGOTからRxにロード
        ```
    *   元の命令: `MOVQ $sym+<off>, Rx`
    *   変換後:
        ```assembly
        MOVQ sym@GOT, Rx  // sym のアドレスをGOTからRxにロード
        ADDQ <off>, Rx    // オフセットを加算
        ```
    これは、グローバル変数 `sym` のアドレスをレジスタにロードする際に、GOTを介して間接的に取得するように変換するものです。`p.From.Type = obj.TYPE_ADDR` と `p.From.Name = obj.NAME_EXTERN` がこの変換のトリガーとなります。変換後、`p.From.Type` は `obj.TYPE_MEM` に、`p.From.Name` は `obj.NAME_GOTREF` に変更されます。

4.  **グローバルデータへのメモリ操作命令の変換**:
    *   元の命令: `MOVQ name(SB), AX` (グローバル変数 `name` の内容を `AX` にロード)
    *   変換後:
        ```assembly
        MOVQ name@GOT(SB), R15 // name のアドレスをGOTからR15にロード
        MOVQ (R15), AX         // R15が指すアドレス（nameの実体）からAXにロード
        ```
    *   元の命令: `MOVQ $1, name(SB)` (即値 `1` をグローバル変数 `name` にストア)
    *   変換後:
        ```assembly
        MOVQ name@GOT(SB), R15 // name のアドレスをGOTからR15にロード
        MOVQ $1, (R15)         // R15が指すアドレス（nameの実体）に1をストア
        ```
    これは、グローバル変数 `name` を直接オペランドとして持つメモリ操作命令を、まずGOTから `name` のアドレスを `R15` にロードし、その `R15` をベースレジスタとして間接的にアクセスするように変換するものです。この変換では、元の命令 `p` の前に `MOVQ name@GOT(SB), R15` 命令 (`p1`) が挿入され、元の命令 `p` は `NOP` (No Operation) に置き換えられます。そして、元の命令 `p` のオペランド (`p.From` または `p.To`) が `R15` を参照するように変更された新しい命令 (`p2`) が `p1` の後に挿入されます。

### `asm6.go` の変更

`asm6.go` では、`oclass` 関数内で `obj.TYPE_ADDR` と `obj.NAME_GOTREF` の組み合わせが「予期しない」ものとして診断されるように変更されています。これは、`rewriteToUseGot` 関数によって `obj.TYPE_ADDR` が `obj.TYPE_MEM` と `obj.NAME_GOTREF` の組み合わせに変換されるため、元の `obj.TYPE_ADDR` のまま `obj.NAME_GOTREF` が現れることはない、というロジックの整合性を保つための変更です。

### `obj6_test.go` の変更

テストファイル `obj6_test.go` では、GOT変換後のアセンブリ命令の期待値が更新されています。特に、メモリ操作命令の変換において、元の命令が `NOP` に置き換えられ、その後にGOT参照と実際のメモリ操作を行う命令が続く形式が反映されています。

## コアとなるコードの解説

`rewriteToUseGot` 関数は、Goコンパイラのリンカがアセンブリ命令を処理する際に、動的リンクの要件を満たすように命令を変換する中心的な役割を担います。

1.  **`ADUFFCOPY` / `ADUFFZERO` の処理**:
    これらの命令は、Goランタイムの内部的な最適化されたメモリ操作ルーチンを呼び出すために使用されます。動的リンク環境では、これらのルーチンのアドレスも実行時に解決される必要があります。そのため、`runtime.duffzero` や `runtime.duffcopy` といったシンボルのアドレスをGOTから `R15` レジスタにロードし、オフセットを加算した後、そのアドレスを `CALL` する一連の命令に変換されます。これにより、ランタイム関数への呼び出しが位置独立になります。

2.  **`LEAQ` から `MOVQ $sym` への変換**:
    `LEAQ sym(SB), Rx` は `sym` のアドレスを `Rx` にロードする命令です。静的リンクでは `sym` のアドレスはコンパイル時に確定しますが、動的リンクでは実行時まで確定しません。そこで、まず `MOVQ $sym, Rx` という形式に変換されます。この `MOVQ $sym` は、シンボルの「値」（この場合はアドレス）をレジスタに移動するという意味合いを持ち、後続の処理でGOT参照に変換されるための準備となります。

3.  **`MOVQ $sym` から `MOVQ sym@GOT` への変換**:
    `MOVQ $sym, Rx` のような命令で、`$sym` が外部シンボル (`obj.NAME_EXTERN` かつ `!p.From.Sym.Local`) のアドレスを指す場合、これは `MOVQ sym@GOT, Rx` に変換されます。これは、シンボルのアドレスを直接レジスタにロードするのではなく、GOTからそのアドレスを間接的に取得するように変更するものです。もしオフセット (`p.From.Offset`) があれば、GOTから取得したアドレスにそのオフセットを加算する `ADDQ` 命令が追加されます。

4.  **メモリ操作命令の変換**:
    `MOVQ name(SB), AX` (メモリからレジスタへ) や `MOVQ $1, name(SB)` (レジスタからメモリへ) のように、グローバル変数 `name` を直接メモリオペランドとして参照する命令は、以下のように変換されます。
    *   まず、`name` のアドレスをGOTから `R15` レジスタにロードする `MOVQ name@GOT(SB), R15` 命令が挿入されます。
    *   元の命令は `obj.Nopout(p)` によって `NOP` (No Operation) に置き換えられます。
    *   元の命令のオペランド (`p.From` または `p.To`) が `R15` レジスタをベースとする間接参照 (`(R15)` や `10(R15)`) に変更された新しい命令が挿入されます。
    この一連の変換により、グローバル変数へのアクセスもGOTを介した位置独立な形になります。

これらの変換は、Goコンパイラが生成するアセンブリコードが、動的リンクされた環境で正しく動作するために不可欠です。特に、386のような32ビットアーキテクチャでは、64ビットアーキテクチャに比べてレジスタの数が少なく、アドレス空間も限られているため、GOTを効率的に利用するロジックはより重要になります。

## 変更の背景

このコミットは、`sync.Once` の `Do` メソッドがパニックを起こした場合の挙動をテストする `TestOncePanic` 関数のロジックを簡素化するために行われました。コミットメッセージにある "Follow-up to CL 137350043" という記述から、以前の変更 (CL 137350043) によって導入された、あるいは関連するテストの複雑性や不正確さを解消することが目的であると推測されます。

`sync.Once` は、その性質上、初期化関数が一度だけ実行されることを保証します。しかし、その初期化関数がパニックを起こした場合の挙動も重要です。Goの `sync.Once` の仕様では、初期化関数がパニックを起こしても、そのパニックは呼び出し元に伝播しますが、`Once` オブジェクト自体は「実行済み」の状態となり、その後の `Do` の呼び出しでは初期化関数は再実行されません。

元の `TestOncePanic` は、このパニック時の挙動を検証しようとしていましたが、`for` ループを使用し、`i` の値によって異なるパニックの有無をチェックするなど、やや複雑なロジックになっていました。この複雑さが、テストの意図を不明瞭にし、将来的なメンテナンスを困難にする可能性がありました。今回の変更は、このテストをより直接的かつ明確にすることで、`sync.Once` のパニック時の挙動の検証を簡潔にすることを目的としています。

## 前提知識の解説

### `sync.Once`

`sync.Once` はGo言語の標準ライブラリ `sync` パッケージで提供される型で、特定の処理（通常は初期化処理）がプログラムの実行中に一度だけ実行されることを保証するために使用されます。これは、複数のGoroutineから同時に `Do` メソッドが呼び出された場合でも、指定された関数が一度だけ実行されるように、内部でミューテックスとアトミック操作を組み合わせて同期を行います。

`Once` 型は以下のように定義されます。

```go
type Once struct {
    // contains filtered or unexported fields
}
```

主なメソッドは `Do(f func())` です。
`Do` メソッドは引数として関数 `f` を受け取ります。
- `Do` が初めて呼び出されたとき、`f` が実行されます。
- `f` が正常に完了した場合、それ以降の `Do` の呼び出しでは `f` は実行されません。
- `f` がパニックを起こした場合、そのパニックは `Do` の呼び出し元に伝播します。しかし、`Once` オブジェクトは「実行済み」の状態となり、その後の `Do` の呼び出しでは `f` は再実行されません。これは、パニックを起こした初期化処理を再試行しないという設計思想に基づいています。

### `defer` と `recover()`

Go言語には、パニック（ランタイムエラー）を処理するためのメカニズムとして `panic`、`defer`、`recover` があります。

- **`panic`**: プログラムの実行を中断し、現在のGoroutineのスタックをアンワインド（巻き戻し）します。通常、回復不可能なエラーや予期せぬ状況が発生した場合に使用されます。
- **`defer`**: `defer` ステートメントに続く関数呼び出しは、その関数が囲む関数の実行が終了する直前（return文の実行後、またはパニック発生時）に実行されることを保証します。これはリソースの解放（ファイルクローズ、ロック解除など）によく使用されます。
- **`recover()`**: `recover()` は `defer` された関数内でのみ有効です。`recover()` が呼び出されたGoroutineがパニック状態にある場合、`recover()` はパニックの値を捕捉し、パニック状態を終了させ、プログラムの実行を再開させます。`recover()` がパニック状態でないGoroutineで呼び出された場合、または `defer` されていない関数で呼び出された場合、`nil` を返します。

`TestOncePanic` のようなテストでは、`Once.Do` 内で意図的にパニックを発生させ、そのパニックが適切に捕捉され、かつ `Once` の「一度だけ実行」という特性が維持されているかを検証するために、`defer` と `recover()` が不可欠です。

### Goのテストフレームワーク (`testing` パッケージ)

Go言語には、テストを記述するための組み込みの `testing` パッケージがあります。
- **`testing.T`**: テスト関数に渡される型で、テストの実行状態を管理し、テスト結果を報告するためのメソッド（例: `Error`, `Errorf`, `Fatal`, `Fatalf`）を提供します。
- **`t.Fatalf(format string, args ...interface{})`**: テストを失敗としてマークし、メッセージをフォーマットして出力した後、現在のテスト関数を即座に終了させます。これは、テストが続行できない致命的なエラーが発生した場合に使用されます。

## 技術的詳細

このコミットは、`src/sync/once_test.go` ファイル内の `TestOncePanic` 関数を修正しています。主な変更点は、テストロジックの簡素化と、`Once.Do` がパニックを起こした後の挙動の検証方法の明確化です。

**変更前:**
元の `TestOncePanic` 関数は、`for` ループを使用して `Once.Do` を2回呼び出していました。
- 1回目のイテレーション (`i == 0`) では、`Once.Do` 内で `panic("failed")` が発生することを期待し、`recover()` でパニックが捕捉されない場合に `t.Fatalf` を呼び出していました。
- 2回目のイテレーション (`i == 1`) では、`Once.Do` がパニックを起こさないこと（つまり、最初のパニックの後、`Once` が「実行済み」状態になり、関数が再実行されないこと）を期待し、パニックが捕捉された場合に `t.Fatalf` を呼び出していました。

このロジックは、`Once.Do` がパニックを起こした後に再実行されないことを検証しようとしていましたが、`for` ループと `i` の値による条件分岐がテストの意図を読みにくくしていました。特に、`recover()` の結果と `i` の値の組み合わせで `t.Fatalf` を呼び出す条件が複雑でした。

**変更後:**
新しい `TestOncePanic` 関数は、`for` ループを削除し、より直接的なアプローチを取っています。
1.  まず、`Once.Do` を呼び出し、その中で `panic("failed")` を発生させます。この呼び出しは `defer` と `recover()` で囲まれており、パニックが確実に捕捉されることを検証します。もしパニックが発生しなかった場合、`t.Fatalf` でテストを失敗させます。
2.  次に、最初のパニックの後、再度 `once.Do(func(){ t.Fatalf("Once.Do called twice") })` を呼び出します。`sync.Once` の仕様により、最初のパニックの後、`Once` オブジェクトは「実行済み」状態になるため、この2回目の `Do` の呼び出しでは引数の関数は実行されないはずです。もし実行されて `t.Fatalf` が呼び出された場合、それは `Once` の「一度だけ実行」という保証が破られたことを意味し、テストは失敗します。

この新しいアプローチは、テストの意図を非常に明確にしています。
- 最初のブロックで「`Once.Do` 内でパニックが発生した場合、そのパニックは伝播する」ことを検証します。
- 2番目のブロックで「パニックが発生した後でも、`Once.Do` は二度と実行されない」ことを検証します。

これにより、テストコードの可読性と保守性が向上し、`sync.Once` のパニック時の挙動に関するテストの正確性が高まっています。

## コアとなるコードの解説

### 変更前のコード (`-` で始まる行)

```go
func TestOncePanic(t *testing.T) {
	once := new(Once) // Onceオブジェクトを初期化
	for i := 0; i < 2; i++ { // 2回ループ
		func() { // 無名関数でGoroutineのスタックフレームを作成
			defer func() { // パニックを捕捉するためのdefer関数
				r := recover() // パニックの値を捕捉
				if r == nil && i == 0 { // 1回目のイテレーションでパニックが発生しなかった場合
					t.Fatalf("Once.Do() has not panic'ed on first iteration")
				}
				if r != nil && i == 1 { // 2回目のイテレーションでパニックが発生した場合
					t.Fatalf("Once.Do() has panic'ed on second iteration")
				}
			}()
			once.Do(func() { // Once.Doを呼び出し、内部でパニックを発生させる
				panic("failed")
			})
		}()
	}
	once.Do(func() {}) // 最後に、パニック後にOnce.Doが再実行されないことを確認（ただし、引数の関数は空）
}
```

変更前のコードは、`for` ループを使って `Once.Do` を2回呼び出し、それぞれのイテレーションで異なるパニックの挙動を検証しようとしていました。
- 1回目のイテレーション (`i == 0`) では、`once.Do` 内の `panic("failed")` が実行され、`recover()` で捕捉されることを期待していました。もしパニックが起きなければテストは失敗します。
- 2回目のイテレーション (`i == 1`) では、`sync.Once` の特性により、最初のパニックの後、`once.Do` は引数の関数を再実行しないはずです。したがって、このイテレーションではパニックが発生しないことを期待していました。もしパニックが捕捉されたらテストは失敗します。

このロジックは、`i` の値に依存する条件分岐が複雑で、テストの意図を理解しにくくしていました。また、最後の `once.Do(func() {})` は、パニック後に `Once.Do` が再実行されないことを確認する意図があるものの、引数の関数が空であるため、実際に `Once.Do` が呼び出されたかどうかを直接的に検証するものではありませんでした。

### 変更後のコード (`+` で始まる行)

```go
func TestOncePanic(t *testing.T) {
	var once Once // Onceオブジェクトを宣言 (new(Once) と同じくゼロ値で初期化)
	func() { // 無名関数でGoroutineのスタックフレームを作成
		defer func() { // パニックを捕捉するためのdefer関数
			if r := recover(); r == nil { // パニックの値を捕捉し、nilでなければパニックが発生したことを意味する
				t.Fatalf("Once.Do did not panic") // パニックが発生しなかった場合、テストを失敗させる
			}
		}()
		once.Do(func() { // Once.Doを呼び出し、内部でパニックを発生させる
			panic("failed")
		})
	}() // 無名関数を即時実行

	// 最初のOnce.Doがパニックを起こした後、Onceは「実行済み」状態になるため、
	// この2回目のOnce.Do呼び出しでは引数の関数は実行されないはず。
	once.Do(func() {
		t.Fatalf("Once.Do called twice") // もしこの関数が実行されたら、Onceの保証が破られているためテストを失敗させる
	})
}
```

変更後のコードは、よりシンプルで直接的なテストロジックを採用しています。
1.  最初の無名関数ブロックでは、`once.Do` を呼び出し、その中で `panic("failed")` を発生させます。`defer` と `recover()` を使って、このパニックが確実に発生し、捕捉されることを検証します。`recover()` が `nil` を返した場合（つまりパニックが発生しなかった場合）、`t.Fatalf` でテストを失敗させます。これにより、「`Once.Do` 内でパニックが発生した場合、そのパニックは呼び出し元に伝播する」という挙動を検証しています。
2.  その後の `once.Do(func() { t.Fatalf("Once.Do called twice") })` の呼び出しは、最初のパニックの後、`Once` オブジェクトが「実行済み」状態になっているため、引数の関数が**実行されない**ことを検証します。もしこの関数が実行されて `t.Fatalf` が呼び出された場合、それは `Once` の「一度だけ実行」という保証が破られたことを意味し、テストは失敗します。

この修正により、テストの意図が明確になり、`sync.Once` のパニック時の挙動に関するテストがより堅牢になりました。

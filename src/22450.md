## 変更の背景

このコミットは、Goコンパイラおよびランタイムの特定のアーキテクチャ（特に`arm64`）における最適化の不完全さに起因するテストの失敗に対応するために行われました。

1.  **`nilptr3`テストの失敗**: `nilptr3.go`テストは、Goコンパイラがnilポインタのデリファレンスを適切に最適化できるかどうかを検証するものです。コミットメッセージによると、このテストは`ppc64x`（Issue 9058）および`arm64`（Issue 10105）アーキテクチャで「不完全な最適化」のために失敗していました。これは、これらのアーキテクチャ向けのコンパイラバックエンドが、特定のnilポインタチェックの最適化パターンをまだ完全にサポートしていないことを示唆しています。テストスイートのCI/CDパイプラインがこれらの失敗によってブロックされるのを防ぐため、一時的な措置として、該当アーキテクチャでのテスト実行を無効化する必要がありました。

2.  **`nosplit`テストの修正**: `nosplit`テストは、Goの関数がスタックの分割（stack split）を必要としないことを検証するものです。Goの関数は通常、必要に応じてスタックを自動的に拡張しますが、一部の低レベルな関数（特にランタイム内部の関数）では、スタックの分割を禁止する`//go:nosplit`ディレクティブが使用されます。これは、スタックの分割が不可能なコンテキスト（例: シグナルハンドラ内）や、パフォーマンスが非常に重要なパスで利用されます。このテストが`arm64`で正しく動作していなかったため、`arm64`アーキテクチャの特性に合わせてテストロジックを修正する必要がありました。具体的には、`arm64`のポインタサイズが8バイトであることを考慮し、テストハーネスが正しく動作するように調整されました。

これらの変更は、Goのクロスプラットフォーム対応を進める上で、各アーキテクチャ固有のコンパイラ最適化やランタイムの挙動の違いを吸収し、テストスイートの健全性を維持するために不可欠でした。

## 前提知識の解説

### Goのテストとビルドタグ (`+build`)

Goのソースコードでは、ファイルの先頭に`+build`タグを記述することで、特定のビルド条件（OS、アーキテクチャ、Goのバージョンなど）に基づいてファイルをコンパイルに含めるか除外するかを制御できます。
例: `// +build linux,amd64` はLinuxかつAMD64アーキテクチャの場合にのみコンパイルされます。
このコミットでは、`// +build !ppc64,!ppc64le,!arm64` というタグが使用されており、これは`ppc64`、`ppc64le`、`arm64`以外のアーキテクチャでのみこのファイルをコンパイルすることを示しています。これにより、特定のアーキテクチャで問題が発生しているテストを一時的に無効化することができます。

### `nilptr`テスト

Goコンパイラは、nilポインタのデリファレンスを検出してパニックを発生させるためのコードを生成します。これは、C/C++のような言語で発生しがちなセグメンテーション違反を防ぎ、より安全な実行環境を提供するためです。`nilptr`テストは、コンパイラがこのnilポインタチェックを正しく挿入し、かつ不要なチェックを最適化によって除去できるかを検証します。
「不完全な最適化」とは、コンパイラがnilポインタチェックを挿入すべき場所で挿入しなかったり、あるいは除去すべき場所で除去しなかったりする問題を指します。

### `nosplit`関数とスタック分割

Goランタイムは、関数の呼び出し時にスタックが不足した場合、自動的にスタックを拡張する「スタック分割（stack split）」というメカニズムを持っています。これにより、プログラマはスタックサイズを意識することなく再帰関数などを記述できます。
しかし、ランタイムの非常に低レベルな部分や、シグナルハンドラのようにスタックを拡張できないコンテキストでは、スタック分割を禁止する必要があります。このような関数には`//go:nosplit`ディレクティブが付与されます。
`nosplit`テストは、`//go:nosplit`とマークされた関数が実際にスタック分割を行わないことを検証します。これは、ランタイムの安定性とセキュリティにとって非常に重要です。

### `arm64`アーキテクチャ

`arm64`は、ARMv8-Aアーキテクチャに基づく64ビットの命令セットアーキテクチャです。モバイルデバイス、サーバー、組み込みシステムなど、幅広いプラットフォームで採用されています。Goはクロスコンパイルをサポートしており、様々なアーキテクチャで動作するように設計されていますが、各アーキテクチャ固有の特性（レジスタの利用方法、メモリモデル、命令セットなど）に対応するために、コンパイラやランタイムに特定の調整が必要となることがあります。

これらの変更は、Goのテストインフラストラクチャが異なるアーキテクチャの特性を適切に考慮し、テストの信頼性を向上させるためのものです。

## コアとなるコードの解説

### `test/nilptr3.go`

*   **変更前**:
    ```go
    // +build !ppc64,!ppc64le
    ```
    この行は、`nilptr3.go`テストが`ppc64`および`ppc64le`アーキテクチャではコンパイルされないことを意味していました。これは、これらのアーキテクチャでnilポインタ最適化に関する既知の問題（Issue 9058）があったためです。

*   **変更後**:
    ```go
    // +build !ppc64,!ppc64le,!arm64
    ```
    `+build`タグに`!arm64`が追加されました。これにより、`arm64`アーキテクチャでもこのテストがコンパイル対象から除外されるようになりました。これは、`arm64`でも同様の「不完全な最適化」の問題（Issue 10105）が確認されたためです。この変更は、テストスイートがこれらの既知の問題によって失敗し続けるのを防ぐための実用的な措置です。

*   **コメントの変更**:
    ```diff
    -// Fails on ppc64x because of incomplete optimization.  See issue 9058.
    -// +build !ppc64,!ppc64le
    +// Fails on ppc64x and arm64 because of incomplete optimization.
    +// See issues 9058 and 10105.
    ```
    コメントも更新され、`arm64`での失敗と関連するIssue 10105が明記されました。これにより、将来的にこのコードを読んだ開発者が、なぜこのテストが特定のアーキテクチャで無効化されているのかを理解しやすくなります。

### `test/nosplit.go`

*   **`arm64`ケースの追加**:
    ```go
    		case "arm64":
    			ptrSize = 8
    			fmt.Fprintf(&buf, "#define CALL BL\\n#define REGISTER (R0)\\n")
    ```
    `TestCases`関数内の`switch arch`文に、`arm64`アーキテクチャを処理するための新しい`case`ブロックが追加されました。
    *   `ptrSize = 8`: `arm64`は64ビットアーキテクチャであるため、ポインタのサイズは8バイト（64ビット）です。この設定は、テストがポインタのサイズに依存する計算を正しく行うために必要です。
    *   `fmt.Fprintf(&buf, "#define CALL BL\\n#define REGISTER (R0)\\n")`: これは、`nosplit`テストがアセンブリコードを生成する際に使用するマクロ定義です。
        *   `#define CALL BL`: 関数呼び出し命令としてARMの`BL`（Branch with Link）命令を使用することを定義します。`BL`命令は、関数を呼び出すと同時に、戻りアドレスをリンクレジスタ（LR）に保存します。
        *   `#define REGISTER (R0)`: テストで使用する汎用レジスタとして`R0`を定義します。ARMアーキテクチャでは、`R0`は通常、関数の最初の引数や戻り値を渡すために使用されます。
    この追加により、`nosplit`テストは`arm64`アーキテクチャで正しくアセンブリコードを生成し、スタック分割の挙動を検証できるようになりました。これは、`arm64`環境でのGoランタイムの正確性を保証するために重要です。

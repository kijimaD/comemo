# [インデックス 26449] ファイルの概要

このコミットは、Goの`runtime/pprof`パッケージにおけるCPUプロファイリング機能が、`c-archive`または`c-shared`ビルドモードでGoコードをビルドした場合に期待通りに動作しないという問題に対するドキュメントの追加です。具体的には、`StartCPUProfile`関数が`SIGPROF`シグナルに依存しているため、GoコードがCのライブラリとして組み込まれる際に、メインプログラムのシグナルハンドラと競合する可能性があることを警告し、その回避策と注意点を追記しています。

## 変更の背景

Go言語の`runtime/pprof`パッケージは、Goプログラムのパフォーマンスプロファイリングに不可欠なツールを提供します。特にCPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するのに役立ちます。しかし、GoプログラムをC言語のアーカイブ（`.a`ファイル）や共有ライブラリ（`.so`ファイル）としてビルドし、既存のC/C++アプリケーションに組み込む場合（`go build -buildmode=c-archive`または`go build -buildmode=c-shared`）、`runtime/pprof.StartCPUProfile`が期待通りに機能しないという問題がありました。

この問題の根本原因は、CPUプロファイリングが`SIGPROF`というシグナルに依存していることにあります。Goランタイムは、プロファイリングのためにこのシグナルを捕捉し、定期的にスタックトレースをサンプリングします。しかし、GoコードがCライブラリとして動作する場合、メインのC/C++プログラムが独自の`SIGPROF`ハンドラを持っている可能性があり、Goランタイムがシグナルを捕捉できなくなるため、プロファイリングが機能しなくなります。

このコミットは、この動作がユーザーにとって予期せぬものであるため、`StartCPUProfile`関数のドキュメントにこの制限と、`os/signal.Notify`を使った回避策を明記することで、ユーザーの混乱を解消し、適切な情報を提供することを目的としています。

## 前提知識の解説

### Goのプロファイリング (`runtime/pprof`)

Go言語には、プログラムのパフォーマンス特性を分析するための強力なプロファイリングツールが標準ライブラリとして提供されています。`runtime/pprof`パッケージは、CPU使用率、メモリ割り当て、ゴルーチン、ミューテックス競合などのプロファイルを収集するためのAPIを提供します。

*   **CPUプロファイリング**: `runtime/pprof.StartCPUProfile`関数を呼び出すことで開始されます。これは、一定の間隔（通常は100Hz、つまり1秒間に100回）で実行中のゴルーチンのスタックトレースをサンプリングし、CPUがどの関数で時間を費やしているかを特定します。このサンプリングは、Unix系システムでは`SIGPROF`シグナルを利用して行われます。

### `SIGPROF`シグナル

`SIGPROF`は、Unix系オペレーティングシステムで利用可能なシグナルの一つです。これはプロファイリングタイマーが期限切れになったときにプロセスに送信されるシグナルで、CPUプロファイリングによく使用されます。カーネルは、プロセスの実行時間（ユーザーモードとカーネルモードの両方）を追跡し、設定された間隔で`SIGPROF`を送信します。プログラムは、このシグナルを捕捉するためのハンドラを登録することで、シグナルが届くたびに特定の処理（例: スタックトレースの記録）を実行できます。

### Goのビルドモード (`-buildmode=c-archive`, `-buildmode=c-shared`)

Go言語は、Goプログラムを通常の実行可能ファイルとしてビルドするだけでなく、C言語のライブラリとしてビルドする機能も提供しています。

*   **`-buildmode=c-archive`**: GoパッケージをCアーカイブライブラリ（`.a`ファイル）としてビルドします。このライブラリは、C/C++プログラムに静的にリンクできます。
*   **`-buildmode=c-shared`**: GoパッケージをC共有ライブラリ（`.so`ファイル、macOSでは`.dylib`）としてビルドします。このライブラリは、C/C++プログラムから動的にロードして使用できます。

これらのビルドモードは、既存のC/C++コードベースにGoの機能を追加する際に非常に便利ですが、Goランタイムが通常のGoプログラムとは異なる環境で動作するため、特定の挙動の違いが生じることがあります。

### `os/signal.Notify`

Goの`os/signal`パッケージは、OSシグナルを処理するための機能を提供します。`signal.Notify`関数は、指定されたシグナルを受信したときに、それらのシグナルをGoチャネルに転送するようにGoランタイムに指示します。これにより、GoプログラムはシグナルをGoの慣用的な方法で処理できます。

## 技術的詳細

このコミットが対処している技術的な問題は、`SIGPROF`シグナルの所有権と処理に関するものです。

通常のGoプログラムでは、Goランタイムが起動時に`SIGPROF`シグナル用のハンドラを自動的にインストールします。このハンドラは、CPUプロファイリングが有効になっている間、`SIGPROF`シグナルを受信するたびに現在のゴルーチンのスタックトレースを記録し、プロファイルデータとして蓄積します。

しかし、Goコードが`c-archive`または`c-shared`モードでビルドされ、C/C++のメインプログラムに組み込まれる場合、Goランタイムはメインプログラムのサブコンポーネントとして動作します。この状況では、Goランタイムは通常、`SIGPROF`シグナルハンドラを自動的にインストールしません。これは、メインのC/C++プログラムが既に独自のプロファイリングメカニズムを持っており、`SIGPROF`シグナルを処理している可能性があるためです。Goランタイムが勝手にシグナルハンドラを上書きすると、メインプログラムのプロファイリング機能が壊れてしまう可能性があります。

結果として、`runtime/pprof.StartCPUProfile`を呼び出しても、`SIGPROF`シグナルがGoランタイムのハンドラに到達しないため、CPUプロファイリングが機能しません。プロファイリングデータが収集されず、生成されるプロファイルファイルは空になるか、不完全なものになります。

このコミットで提案されている回避策は、Goの`os/signal.Notify`関数を使用して、`syscall.SIGPROF`シグナルをGoランタイムが処理するように明示的に設定することです。これにより、Goランタイムは`SIGPROF`シグナルを捕捉し、CPUプロファイリングを機能させることができます。

しかし、この回避策には重要な注意点があります。`os/signal.Notify`を呼び出して`SIGPROF`をGoに転送すると、メインのC/C++プログラムが設定していた可能性のある`SIGPROF`ハンドラが上書きされるか、シグナルがGoに奪われる形になります。その結果、メインプログラムのプロファイリング機能が損なわれる可能性があります。このため、ドキュメントでは「そうすることで、メインプログラムが行っているプロファイリングが壊れる可能性があることに注意してください」と警告しています。

要するに、この変更はコードの動作を変更するものではなく、Goのライブラリとしてビルドされた場合の`runtime/pprof`のCPUプロファイリングの挙動に関する重要な制約と、その制約を理解した上での回避策をユーザーに明確に伝えるためのドキュメントの追加です。

## コアとなるコードの解説

追加されたドキュメントコメントは、`StartCPUProfile`関数の既存のコメントブロックに追記されています。

*   `On Unix-like systems, StartCPUProfile does not work by default for Go code built with -buildmode=c-archive or -buildmode=c-shared.`
    *   Unix系システムにおいて、`c-archive`または`c-shared`ビルドモードでビルドされたGoコードでは、`StartCPUProfile`がデフォルトでは動作しないことを明確に述べています。これは、この問題の核心部分です。
*   `StartCPUProfile relies on the SIGPROF signal, but that signal will be delivered to the main program's SIGPROF signal handler (if any) not to the one used by Go.`
    *   `StartCPUProfile`が`SIGPROF`シグナルに依存していること、そしてそのシグナルがGoランタイムではなく、メインプログラムの`SIGPROF`シグナルハンドラに配信される可能性があることを説明しています。これにより、なぜGoのプロファイリングが機能しないのかという理由が明確になります。
*   `To make it work, call os/signal.Notify for syscall.SIGPROF, but note that doing so may break any profiling being done by the main program.`
    *   この問題を解決するための回避策として、`os/signal.Notify`関数を使って`syscall.SIGPROF`をGoランタイムに通知するように設定することを提案しています。しかし、同時に、この操作がメインプログラムのプロファイリングを妨げる可能性があるという重要な警告も付け加えています。

このコメントの追加により、GoをCライブラリとして利用する開発者は、CPUプロファイリングの制限と、その回避策を適用する際の潜在的な影響を事前に理解できるようになります。これは、Goの相互運用性機能を使用する際のユーザーエクスペリエンスを向上させるための重要な情報提供です。

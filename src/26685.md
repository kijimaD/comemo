# [インデックス 26685] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）フェーズにおける共通部分式除去（CSE: Common Subexpression Elimination）のパフォーマンスを大幅に改善することを目的としています。具体的には、型の比較方法を`(*Type).String()`に基づく文字列比較から、アロケーションを伴わない構造的な比較へと変更することで、CSEフェーズの処理速度を約2倍に向上させ、同時にメモリ割り当ても削減しています。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）フェーズの速度を約2倍に向上させるものです。これは、型の比較に`(*Type).String()`メソッドを使用していた箇所を、アロケーションを発生させない構造的な比較に置き換えることで実現されました。この変更により、CSEの速度が向上しただけでなく、メモリ割り当ても削減されました。`make.bash`実行中に検出されるCSEの数は約100万件とほぼ同じであり、新たに検出されたCSEは、この変更によって可能になったものであることが確認されています。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用します。SSA形式では、各変数が一度だけ割り当てられるため、データフロー解析が簡素化され、共通部分式除去（CSE）のような最適化が容易になります。

CSEは、同じ式が複数回計算される箇所を特定し、冗長な計算を単一の計算に置き換えることで、プログラムの実行速度を向上させるコンパイラ最適化手法です。GoコンパイラのCSEフェーズでは、値の等価性を判断するために型の比較が頻繁に行われます。

以前の実装では、型の比較に`(*Type).String()`メソッドが使用されていました。このメソッドは、型を文字列に変換して比較するため、比較のたびに文字列のアロケーションと生成が発生し、これがパフォーマンスのボトルネックとなっていました。特に、数百万ものCSEが検出されるような大規模なコンパイルでは、このオーバーヘッドが顕著でした。

このコミットの背景には、この文字列ベースの型比較によるパフォーマンス低下とメモリ消費の課題があり、これを解決するために、より効率的でアロケーションフリーな構造的比較を導入する必要がありました。

## 前提知識の解説

### 1. GoコンパイラのSSA（Static Single Assignment）形式

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、さらにSSA形式という中間表現に変換します。SSA形式の主な特徴は、各変数がプログラム内で一度だけ定義されることです。これにより、データフロー解析が大幅に簡素化され、以下のような様々な最適化が容易になります。

*   **共通部分式除去 (CSE)**: 同じ計算が複数回行われる場合に、その計算結果を再利用する。
*   **デッドコード除去**: 決して実行されないコードや、結果が使用されない計算を削除する。
*   **定数畳み込み**: コンパイル時に計算可能な式を定数に置き換える。

SSA形式は、コンパイラの最適化において非常に強力なツールであり、現代の多くのコンパイラで採用されています。

### 2. 共通部分式除去 (CSE: Common Subexpression Elimination)

CSEは、コンパイラ最適化の一種で、プログラム内で同じ値を持つ式が複数回評価される場合に、その冗長な評価を排除し、一度計算した結果を再利用するものです。

例えば、以下のコードを考えます。

```go
a := (x + y) * z
b := w + (x + y) * z
```

ここで、`(x + y) * z`という式は2回出現し、両方で同じ値を計算しています。CSEはこれを検出し、以下のように最適化します。

```go
temp := (x + y) * z
a := temp
b := w + temp
```

これにより、`(x + y) * z`の計算が1回で済み、プログラムの実行速度が向上します。CSEを効果的に行うためには、式の「等価性」を正確かつ効率的に判断する必要があります。

### 3. Goにおける型の比較

Go言語における型の比較には、主に「型同一性（Type Identity）」、「代入可能性（Assignability）」、「比較可能性（Comparability）」の3つの概念があります。

*   **型同一性**: Goでは、主に「名前等価性」に基づいて型が同一であるかを判断します。つまり、異なる名前で定義された型は、たとえ基底の構造が同じであっても、異なる型とみなされます（例: `type MyInt int`と`int`は異なる型）。無名型（`struct{}`や`[]int`など）は、そのリテラルが同じであれば同一とみなされます。
*   **代入可能性**: ある型の値を別の型の変数に代入できるかどうかを決定します。型が同一である場合や、基底の型が同一で少なくとも一方が名前付き型でない場合などに代入可能です。
*   **比較可能性**: `==`や`!=`演算子で値を比較できるかどうかを決定します。数値型、文字列型、ポインタ型、チャネル型、すべてのフィールドが比較可能な構造体型、要素型が比較可能な配列型などが比較可能です。スライス、マップ、関数型は比較不可能です。

コンパイラのSSAフェーズにおける型の比較は、これらの言語仕様上の比較ルールとは異なり、最適化の目的（例えば、2つの値が同じ型を持つかどうかを判断してCSEを適用できるか）のために、より内部的かつ効率的な方法で行われます。このコミットでは、この内部的な型の比較メカニズムが改善されています。

### 4. `(*Type).String()`のオーバーヘッド

Goの型システムは複雑であり、型を表現する`Type`構造体は、その種類（プリミティブ型、構造体、配列、関数、インターフェースなど）に応じて様々な情報を持ちます。`String()`メソッドは、これらの情報を人間が読める形式の文字列に変換するために使用されます。

しかし、この文字列変換は、以下の理由でコストが高い処理です。

*   **メモリ割り当て**: 文字列を生成するたびに、ヒープメモリが割り当てられます。これが頻繁に発生すると、ガベージコレクションの負荷が増大し、パフォーマンスが低下します。
*   **CPUオーバーヘッド**: 文字列の構築には、型の構造を走査し、各要素を文字列に変換し、それらを結合するなどのCPU処理が必要です。

CSEフェーズのように、型の比較が頻繁に行われる場面で`String()`メソッドを使用すると、これらのオーバーヘッドが累積し、コンパイル時間の増加に直結します。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける型の比較ロジックを、`(*Type).String()`による文字列比較から、アロケーションフリーな構造的比較へと変更した点にあります。

### 変更点と影響

1.  **`ssa.Type`インターフェースへの`Compare`メソッドの追加**:
    `src/cmd/compile/internal/ssa/type.go`において、`ssa.Type`インターフェースに`Compare(Type) Cmp`メソッドが追加されました。このメソッドは、2つの型を比較し、`CMPlt`（より小さい）、`CMPeq`（等しい）、`CMPgt`（より大きい）のいずれかを返します。これにより、型の比較が文字列変換を介さずに行えるようになります。

2.  **`gc.Type`への`Compare`メソッドの実装**:
    `src/cmd/compile/internal/gc/type.go`において、Goコンパイラの内部型表現である`*Type`（`gc.Type`）に`Compare`メソッドが実装されました。この実装は、`Eqtype`（型等価性チェック）の構造を踏襲しつつ、以下の点で最適化されています。
    *   **シンボルの比較**: `Sym`（シンボル）の比較には、`cmpsym`という専用のメソッドが導入されました。これは、シンボルの名前の長さ、パッケージプレフィックス、名前自体を比較することで、効率的な順序付けと等価性チェックを行います。
    *   **マップ型の特殊処理**: マップ型は、Goソースコードでは表現できない内部データ型を含むため、無限再帰を避けるために特別に処理されます。
    *   **プリミティブ型の直接比較**: `TBOOL`, `TINT`, `TFLOAT`などのプリミティブ型は、その`Etype`（基本型）が同じであれば等しいとみなされます。
    *   **構造体、インターフェース、関数、配列、チャネル型の再帰的比較**: これらの複合型は、その内部構造（フィールド、メソッド、要素型など）を再帰的に比較することで等価性を判断します。

3.  **`ssa.cse.go`における型比較の変更**:
    `src/cmd/compile/internal/ssa/cse.go`の`partitionValues`関数内で、値の型比較が`typNames[v.Type] != typNames[w.Type]`（`(*Type).String()`に基づく比較）から`v.Type.Compare(w.Type) != CMPeq`へと変更されました。これにより、CSEのパーティショニング段階で発生していた文字列アロケーションとCPUオーバーヘッドが排除されます。

4.  **`gc/reflect.go`の変更**:
    `makefield`関数内で、フィールドのシンボル割り当てが`f.Sym = new(Sym); f.Sym.Name = name`から`f.Sym = nopkg.Lookup(name)`に変更されました。これは、シンボルを毎回新しく作成するのではなく、既存のシンボルをルックアップして再利用することで、アロケーションを削減し、シンボル管理を効率化する目的があると考えられます。

### パフォーマンスへの影響

この変更により、型の比較が文字列変換を伴わない構造的な比較に置き換わったため、以下の効果が得られました。

*   **CSEフェーズの速度向上**: 文字列の生成とガベージコレクションのオーバーヘッドがなくなることで、CSEフェーズの実行速度が約2倍に向上しました。
*   **メモリ割り当ての削減**: 文字列アロケーションが不要になったため、コンパイラのメモリ使用量が削減されました。

コミットメッセージにある「roughly the same number of CSEs were detected (about a million)」という記述は、この変更がCSEの検出ロジック自体に大きな影響を与えず、主にパフォーマンス改善に焦点を当てたものであることを示しています。また、「"new" CSEs were caused by the effect described above」は、より正確な型比較が可能になったことで、以前は見逃されていた一部の共通部分式が検出されるようになった可能性を示唆しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go`の変更

`makefield`関数は、構造体のフィールドを表す`Type`オブジェクトを作成する際に呼び出されます。
変更前:
```go
	f.Sym = new(Sym)
	f.Sym.Name = name
```
このコードは、新しい`Sym`（シンボル）オブジェクトを毎回ヒープに割り当て、その`Name`フィールドにフィールド名をセットしていました。
変更後:
```go
	f.Sym = nopkg.Lookup(name)
```
`nopkg.Lookup(name)`は、指定された名前のシンボルをルックアップし、存在すればそれを返し、存在しなければ新しく作成して返します。これにより、同じ名前のシンボルが複数回作成されるのを防ぎ、シンボルオブジェクトのアロケーションを削減します。これは、コンパイラのメモリ使用量を減らし、ガベージコレクションの頻度を低減する効果があります。

### `src/cmd/compile/internal/gc/type.go`の変更

このファイルには、Goコンパイラの内部型表現である`*Type`に対する`Compare`メソッドが追加されました。このメソッドは、SSAバックエンドでの型比較のために使用されます。

*   **`Compare(u ssa.Type) ssa.Cmp`**:
    このメソッドは、`gc.Type`と`ssa.Type`を比較するためのエントリポイントです。まず、比較対象の`u`が`*Type`にキャスト可能かを確認し、可能であれば内部の`cmp`メソッドを呼び出します。`ssa.CompilerType`との比較も考慮されています。

*   **`cmpForNe(x bool) ssa.Cmp`**:
    ブール値を`ssa.Cmp`（`CMPlt`または`CMPgt`）に変換するヘルパー関数です。比較結果が等しくない場合に、どちらが大きいか小さいかを決定するために使用されます。

*   **`(*Sym).cmpsym(s *Sym) ssa.Cmp`**:
    シンボルを比較するためのメソッドです。ポインタの等価性、`nil`チェック、名前の長さ、パッケージプレフィックス、名前自体を順に比較することで、シンボルの順序付けと等価性チェックを効率的に行います。これは、文字列比較ではなく、構造的な比較に基づいています。

*   **`(*Type).cmp(x *Type) ssa.Cmp`**:
    `gc.Type`の実際の構造的比較を行うメソッドです。
    *   ポインタの等価性、`nil`チェック、`Etype`（基本型）の比較を最初に行います。
    *   `byte`と`uint8`、`rune`と`int32`のような特殊なケース（Goソース上は異なるが、コンパイラ内部では等価とみなされる場合がある）を処理します。
    *   `Sym`フィールドが存在する場合、`cmpsym`メソッドを使用してシンボルを比較します。
    *   プリミティブ型（`TBOOL`, `TINT`など）は、`Etype`が同じであれば等しいとみなされます。
    *   ポインタ型（`TPTR32`, `TPTR64`）は、指している型を再帰的に`cmp`で比較します。
    *   構造体型（`TSTRUCT`）やインターフェース型（`TINTER`）、関数型（`TFUNC`）、配列型（`TARRAY`）、チャネル型（`TCHAN`）は、その内部構造（フィールド、メソッド、要素型、バウンドなど）を再帰的に比較することで等価性を判断します。
    *   マップ型（`TMAP`）は、無限再帰を避けるために特別な処理が施されています。
    *   比較できない型が来た場合はパニックを発生させます。

この`cmp`メソッドは、型の構造を直接走査して比較するため、`String()`メソッドのように文字列アロケーションや文字列操作のオーバーヘッドが発生しません。

### `src/cmd/compile/internal/ssa/cse.go`の変更

このファイルは、SSAバックエンドのCSEパスの実装を含んでいます。

*   **`rewrites`カウンターの追加**:
    CSEによって値が書き換えられた回数をカウントするための`rewrites`変数が追加されました。デバッグ情報として出力されます。

*   **`partitionValues`関数の変更**:
    `partitionValues`関数は、CSEのために値を等価クラスに分割する役割を担います。
    変更前は、`typNames`という`map[Type]string`を使用して型の文字列表現をキャッシュし、それに基づいて型を比較していました。
    ```go
    typNames[v.Type] != typNames[w.Type]
    ```
    変更後:
    ```go
    v.Type.Compare(w.Type) != CMPeq
    ```
    `typNames`マップとそれに関連するロジックが削除され、新しく導入された`ssa.Type.Compare`メソッドが直接使用されるようになりました。これにより、文字列アロケーションと文字列比較のオーバーヘッドが完全に排除され、CSEのパーティショニング処理が大幅に高速化されます。

*   **`sortvalues`構造体の変更**:
    `sortvalues`構造体から`typNames map[Type]string`フィールドが削除されました。これは、型比較に文字列表現が不要になったためです。

*   **`sortvalues.Less`メソッドの変更**:
    `sortvalues`の`Less`メソッドは、値のソート順を決定するために使用されます。ここでも、型の比較ロジックが`(*Type).String()`に基づくものから`v.Type.Compare(w.Type)`に基づくものに変更されました。
    変更前:
    ```go
    	// Sort by type.  Types are just interfaces, so we can't compare
    	// them with < directly.  Instead, map types to their names and
    	// sort on that.
    	if v.Type != w.Type {
    		x := sv.typNames[v.Type]
    		if x == "" {
    			x = v.Type.String()
    			sv.typNames[v.Type] = x
    		}
    		y := sv.typNames[w.Type]
    		if y == "" {
    			y = w.Type.String()
    			sv.typNames[w.Type] = y
    		}
    		if x != y {

    		}
    	}
    ```

    変更後:
    ```go
    	// Sort by type, using the ssa.Type Compare method
    	if v.Type != w.Type {
    		c := v.Type.Compare(w.Type)
    		if c != CMPeq {
    			return c == CMPlt
    		}
    	}
    ```
    この変更により、ソート時の型比較もアロケーションフリーな構造的比較で行われるようになり、CSEフェーズ全体のパフォーマンス向上に貢献します。

### `src/cmd/compile/internal/ssa/type.go`の変更

このファイルでは、SSAバックエンドで使用される`Type`インターフェースと、その比較に関連する型が定義されています。

*   **`Type`インターフェースへの`Compare`メソッドの追加**:
    `Type`インターフェースに`Compare(Type) Cmp`メソッドが追加されました。これにより、SSAバックエンドの様々な型がこのインターフェースを実装し、構造的な比較を提供できるようになります。

*   **`Cmp`型の定義**:
    `Cmp`という`int8`型の新しい型が定義され、`CMPlt` (-1), `CMPeq` (0), `CMPgt` (1)という定数が導入されました。これは、比較結果を明確かつ効率的に表現するためのものです。

*   **`CompilerType`への`Compare`メソッドの実装**:
    `CompilerType`は、コンパイラ内部で使用される特殊な型を表します。この型にも`Compare`メソッドが実装され、名前の長さと名前自体を比較することで、効率的な順序付けと等価性チェックを行います。

# [インデックス 26737] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるメモリ使用量の最適化を目的としています。具体的には、コンパイル中に生成される`Prog`構造体への参照を、各関数のコンパイルが完了した直後に解放することで、コンパイラのピークメモリ使用量を約20%削減します。これにより、`Prog`構造体がより早くガベージコレクション（GC）の対象となり、メモリ効率が向上します。

## 元コミット内容

Goコンパイラは、各関数のコンパイル後に`Prog`構造体への参照を破棄するように変更されました。これにより、コンパイル中に大量の`Prog`構造体を蓄積し、コンパイルの最後にまとめて書き出すのではなく、各関数がコンパイルされるたびにそれらをコードと再配置情報（またはデータと再配置情報）に変換します。

また、`Prog`構造体を保持していた他のいくつかの箇所も特定され、それらの参照を`nil`に設定することで、`Prog`構造体が速やかにガベージコレクションされるようにしました。

この変更により、コンパイラのピークメモリ使用量が約20%削減されます。速度面では、GCの頻度が増えるため、驚くほど大きな改善は見られませんでしたが、`GOGC=120`に調整することで多少の速度向上が見られました。この変更は、将来的なさらなる最適化（例: `Prog`のキャッシュ再利用）の基盤となります。

## 変更の背景

Goコンパイラは、大規模なGoプログラムをコンパイルする際に、大量のメモリを消費することがありました。特に、中間表現である`Prog`構造体がコンパイルプロセスの最後まで保持され続けることが、ピークメモリ使用量の大きな要因となっていました。

このコミットの背景には、以下の課題意識がありました。

1.  **メモリフットプリントの削減**: コンパイラのメモリ使用量を減らすことで、より少ないリソースで大規模なプロジェクトをコンパイルできるようにする。特に、メモリが限られた環境（CI/CDパイプライン、開発者のローカルマシンなど）でのコンパイル効率を向上させる。
2.  **ガベージコレクションの効率化**: `Prog`構造体が不要になった時点で速やかにGCの対象となるようにすることで、GCの負荷を分散させ、全体的なメモリ管理を改善する。
3.  **将来的な最適化の基盤**: `Prog`構造体のライフサイクルを関数単位で管理することで、例えば`Prog`構造体のプールやキャッシュを導入しやすくなり、さらなるコンパイル速度の向上やメモリ効率の改善に繋がる可能性を広げる。

これまでのコンパイラは、すべての関数が`Prog`構造体に変換された後、それらをまとめて機械語に変換していました。この「バッチ処理」的なアプローチは、一度に多くの情報を処理できる利点がある一方で、すべての`Prog`構造体をメモリ上に保持し続ける必要があり、メモリ使用量の増大を招いていました。このコミットは、このアプローチを「ストリーミング処理」に近い形に改め、メモリ使用量の最適化を図っています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **`Prog`構造体**:
    *   `Prog`は、Goコンパイラのバックエンド（`cmd/internal/obj`パッケージ）で使用される、機械語命令の抽象的な表現です。各`Prog`インスタンスは、アセンブリ命令、オペランド、再配置情報などを保持します。
    *   Goコンパイラは、GoのソースコードをAST（抽象構文木）に変換し、その後、中間表現（IR）を経て、最終的に`Prog`構造体のリストを生成します。この`Prog`リストが、各関数の機械語コードを生成するための元となります。
    *   以前は、コンパイラはすべての関数の`Prog`リストをメモリ上に保持し、コンパイルの最終段階でまとめてオブジェクトファイルに書き出していました。

2.  **Goコンパイラのフェーズ**:
    *   Goコンパイラは、主に以下のフェーズで動作します。
        *   **フロントエンド**: 字句解析、構文解析、AST構築、型チェックなど。
        *   **ミドルエンド**: ASTからSSA（Static Single Assignment）形式への変換、最適化など。
        *   **バックエンド**: SSAから`Prog`構造体への変換、レジスタ割り当て、機械語コード生成、オブジェクトファイルへの書き出しなど。
    *   このコミットは、主にバックエンドの`Prog`構造体の管理方法と、オブジェクトファイルへの書き出しのタイミングに影響を与えます。

3.  **ガベージコレクション (GC)**:
    *   Goランタイムは、不要になったメモリを自動的に解放するガベージコレクタを備えています。
    *   オブジェクトがGCの対象となるのは、そのオブジェクトへの参照がどこからも存在しなくなった時点です。
    *   このコミットの目的の一つは、`Prog`構造体への参照を早期に`nil`にすることで、GCがそれらをより早く回収できるようにすることです。

4.  **`GOGC`環境変数**:
    *   `GOGC`は、Goのガベージコレクタの動作を制御する環境変数です。デフォルト値は100で、これはヒープサイズが前回のGC後のヒープサイズの100%増加したときにGCが実行されることを意味します。
    *   `GOGC`の値を大きくするとGCの頻度が減り、小さくするとGCの頻度が増えます。
    *   コミットメッセージにある「`GOGC=120`に調整することで多少の速度向上が見られた」という記述は、GCの頻度を減らすことで、GCによる一時的な停止（ストップ・ザ・ワールド）の回数を減らし、全体的なコンパイル時間を短縮できたことを示唆しています。

5.  **`obj`パッケージ (`cmd/internal/obj`)**:
    *   Goコンパイラのバックエンドを構成する重要なパッケージの一つで、アセンブラの機能を提供します。
    *   `Prog`構造体の定義や、それらを機械語に変換するためのユーティリティ関数などが含まれています。
    *   `obj.Flushplist`関数は、`Prog`リストを処理し、機械語コードを生成してオブジェクトファイルに書き出す役割を担います。

6.  **`Link`コンテキスト (`*obj.Link`)**:
    *   `obj`パッケージ内で使用される、リンカの状態を保持する構造体です。
    *   コンパイル中に生成されるコードやデータ、シンボル情報などを管理します。
    *   `ctxt.Text`、`ctxt.Etext`、`ctxt.Plist`、`ctxt.Plast`、`ctxt.Curp`といったフィールドは、それぞれ生成されたコードの開始/終了ポインタ、`Prog`リストの開始/終了ポインタ、現在の`Prog`ポインタなどを指します。

## 技術的詳細

このコミットの核心は、Goコンパイラが`Prog`構造体を処理するタイミングを、コンパイルの最後から「各関数のコンパイル後」に変更した点にあります。これにより、メモリ使用量の削減と、将来的な最適化の可能性が広がります。

具体的な変更点は以下の通りです。

1.  **関数単位での`Prog`リストのフラッシュ**:
    *   以前は、`funccompile`関数（各Go関数をコンパイルする主要な関数）が完了した後も、その関数に対応する`Prog`構造体はグローバルなリストに蓄積され続けていました。
    *   この変更により、`funccompile`の最後に`flushdata()`と`obj.Flushplist(Ctxt)`が呼び出されるようになりました。
    *   `flushdata()`は、データセクションに関連する`Prog`リストをフラッシュし、`obj.Flushplist(Ctxt)`は、コードセクションに関連する`Prog`リストを機械語に変換して、`Link`コンテキストにアタッチします。これにより、関数単位で`Prog`構造体が処理され、メモリから解放される準備が整います。

2.  **参照の早期解放**:
    *   `funccompile`関数内で、`Curfn`（現在の関数）、`Pc`（プログラムカウンタ）、`continpc`（continue文のターゲット）、`breakpc`（break文のターゲット）といった、特定の関数にのみ関連するグローバルなポインタが、関数のコンパイル完了後に`nil`に設定されるようになりました。これにより、これらのポインタが`Prog`構造体への参照を保持し続けることがなくなり、GCによる早期回収が可能になります。
    *   `flushdata()`関数内でも、`dfirst`と`dpc`（データセクションの`Prog`リストの開始と現在のポインタ）が`nil`に設定されます。
    *   `obj.Flushplist`関数内では、処理が完了した`Prog`構造体への参照（`s.Text`、`s.Etext`）が`nil`に設定され、`Link`コンテキスト内の`ctxt.Plist`、`ctxt.Plast`、`ctxt.Curp`も`nil`にクリアされます。これは、`Prog`リストが機械語に変換された後、そのリスト自体が不要になるためです。

3.  **`Link`コンテキストへのコードの追加ロジックの修正**:
    *   `obj.Flushplist`内で、生成されたコード（`text`）を`Link`コンテキスト（`ctxt`）の既存のコードリストに追加するロジックが修正されました。以前は`ctxt.Etext == nil`のチェックのみでしたが、`text != nil`のチェックが追加され、より堅牢になっています。これは、`text`が空の場合でも正しく動作するようにするためです。

これらの変更により、コンパイラは各関数のコンパイルが完了するたびに、その関数に関連する中間表現をメモリから解放できるようになります。これにより、コンパイラが一度に保持する必要がある`Prog`構造体の総数が大幅に減少し、結果としてピークメモリ使用量が削減されます。

速度面での影響が限定的であったのは、`Prog`構造体の早期解放によってGCの頻度が増加したためと考えられます。GCは一時的にプログラムの実行を停止させるため、GCの頻度が増えると、全体的な実行時間が長くなる可能性があります。しかし、`GOGC`の調整によってGCの頻度を最適化することで、速度面でも改善が見られることが示されています。

この変更は、Goコンパイラのメモリ管理戦略における重要な一歩であり、将来的にコンパイラのパフォーマンスをさらに向上させるための基盤を築いています。例えば、`Prog`構造体の再利用メカニズムを導入することで、オブジェクトの割り当てと解放のオーバーヘッドをさらに削減できる可能性があります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/dcl.go` の変更

`funccompile`関数は、Goの各関数をコンパイルする際の主要なエントリポイントです。この関数は、特定のGo関数に対するASTの処理、中間表現の生成、そして最終的な機械語コードの生成を調整します。

変更点:

*   `Curfn = nil`, `Pc = nil`, `continpc = nil`, `breakpc = nil`:
    *   これらの行は、現在の関数に関連するグローバルなポインタを`nil`に設定しています。`Curfn`は現在コンパイル中の関数ノードを指し、`Pc`はプログラムカウンタ、`continpc`と`breakpc`はそれぞれ`continue`文と`break`文のターゲットとなる`Prog`構造体を指すポインタです。
    *   これらのポインタを`nil`にすることで、現在の関数に関連する`Prog`構造体への参照が解放され、ガベージコレクタがこれらの構造体を回収できるようになります。これにより、メモリリークを防ぎ、メモリ使用量を削減します。
*   `flushdata()`:
    *   新しく追加された`gsubr.go`内の関数を呼び出します。この関数は、データセクションに関連する`Prog`リストを処理し、その参照をクリアする役割を担います。
*   `obj.Flushplist(Ctxt)`:
    *   `obj`パッケージの`Flushplist`関数を呼び出します。この関数は、現在の`Prog`リスト（コードセクション）を機械語コードに変換し、`Link`コンテキスト（`Ctxt`）に追加します。この呼び出しにより、各関数がコンパイルされるたびに`Prog`リストが処理され、メモリから解放されるようになります。

これらの変更により、`funccompile`が完了するたびに、その関数に関連する中間表現がメモリから「フラッシュ」され、コンパイラが一度に保持する`Prog`構造体の量が大幅に削減されます。

### `src/cmd/compile/internal/gc/gsubr.go` の変更

`gsubr.go`は、Goコンパイラのバックエンドにおける汎用的なサブルーチンやヘルパー関数を含むファイルです。

変更点:

*   `func flushdata()` の追加:
    *   この新しい関数は、データセクションに関連する`Prog`リストを管理するために導入されました。
    *   `if dfirst == nil { return }`: `dfirst`はデータセクションの`Prog`リストの先頭を指すポインタです。もしリストが空であれば、何もせずに戻ります。
    *   `newplist()`: 新しい`Prog`リストを開始します。これは、データセクションの`Prog`をコードセクションの`Prog`とは別に管理するための準備です。
    *   `*Pc = *dfirst`: `Pc`（プログラムカウンタ）を`dfirst`が指す`Prog`に設定します。これにより、データセクションの`Prog`が現在の処理対象となります。
    *   `Pc = dpc`: `Pc`を`dpc`（データセクションの現在の`Prog`ポインタ）に設定します。
    *   `Clearp(Pc)`: `Pc`が指す`Prog`リストをクリアします。これは、`Prog`リストの末尾を適切に処理し、不要な参照を削除するためです。
    *   `dfirst = nil`, `dpc = nil`: データセクションの`Prog`リストの開始ポインタと現在のポインタを`nil`に設定し、参照を解放します。

この`flushdata`関数は、データセクションの`Prog`構造体も関数単位で処理し、メモリから解放されるようにするための重要な役割を担っています。

### `src/cmd/internal/obj/objfile.go` の変更

変更点:

変更点:

*   `Curfn = nil`, `Pc = nil`, `continpc = nil`, `breakpc = nil`:
    *   これらの行は、現在の関数に関連するグローバルなポインタを`nil`に設定しています。`Curfn`は現在コンパイル中の関数ノードを指し、`Pc`はプログラムカウンタ、`continpc`と`breakpc`はそれぞれ`continue`文と`break`文のターゲットとなる`Prog`構造体を指すポインタです。
    *   これらのポインタを`nil`にすることで、現在の関数に関連する`Prog`構造体への参照が解放され、ガベージコレクタがこれらの構造体を回収できるようになります。これにより、メモリリークを防ぎ、メモリ使用量を削減します。
*   `flushdata()`:
    *   新しく追加された`gsubr.go`内の関数を呼び出します。この関数は、データセクションに関連する`Prog`リストを処理し、その参照をクリアする役割を担います。
*   `obj.Flushplist(Ctxt)`:
    *   `obj`パッケージの`Flushplist`関数を呼び出します。この関数は、現在の`Prog`リスト（コードセクション）を機械語コードに変換し、`Link`コンテキスト（`Ctxt`）に追加します。この呼び出しにより、各関数がコンパイルされるたびに`Prog`リストが処理され、メモリから解放されるようになります。

これらの変更により、`funccompile`が完了するたびに、その関数に関連する中間表現がメモリから「フラッシュ」され、コンパイラが一度に保持する`Prog`構造体の量が大幅に削減されます。

### `src/cmd/compile/internal/gc/gsubr.go` の変更

`gsubr.go`は、Goコンパイラのバックエンドにおける汎用的なサブルーチンやヘルパー関数を含むファイルです。

変更点:

*   `func flushdata()` の追加:
    *   この新しい関数は、データセクションに関連する`Prog`リストを管理するために導入されました。
    *   `if dfirst == nil { return }`: `dfirst`はデータセクションの`Prog`リストの先頭を指すポインタです。もしリストが空であれば、何もせずに戻ります。
    *   `newplist()`: 新しい`Prog`リストを開始します。これは、データセクションの`Prog`をコードセクションの`Prog`とは別に管理するための準備です。
    *   `*Pc = *dfirst`: `Pc`（プログラムカウンタ）を`dfirst`が指す`Prog`に設定します。これにより、データセクションの`Prog`が現在の処理対象となります。
    *   `Pc = dpc`: `Pc`を`dpc`（データセクションの現在の`Prog`ポインタ）に設定します。
    *   `Clearp(Pc)`: `Pc`が指す`Prog`リストをクリアします。これは、`Prog`リストの末尾を適切に処理し、不要な参照を削除するためです。
    *   `dfirst = nil`, `dpc = nil`: データセクションの`Prog`リストの開始ポインタと現在のポインタを`nil`に設定し、参照を解放します。

この`flushdata`関数は、データセクションの`Prog`構造体も関数単位で処理し、メモリから解放されるようにするための重要な役割を担っています。

### `src/cmd/internal/obj/objfile.go` の変更

`objfile.go`は、Goコンパイラのバックエンドでオブジェクトファイルを生成するための機能を提供します。

変更点:

*   `Flushplist`関数内の変更:
    *   `s.Text = nil`, `s.Etext = nil`:
        *   `s`は`obj.LSym`（リンカシンボル）構造体を指し、`s.Text`と`s.Etext`はそのシンボルに関連するコードの開始と終了の`Prog`構造体を指します。
        *   `obj.Flushplist`が`Prog`リストを機械語に変換した後、これらの参照は不要になります。`nil`に設定することで、`Prog`構造体がGCの対象となり、メモリが解放されます。
    *   `Link`コンテキストへのコード追加ロジックの修正:
        *   以前のコードは、`ctxt.Etext == nil`（`Link`コンテキストにまだコードがない場合）をチェックしていましたが、新しいコードは`text != nil`（生成されたコードが存在する場合）を最初にチェックします。
        *   `if ctxt.Text == nil { ctxt.Text = text } else { ctxt.Etext.Next = text }`: これは、生成されたコードを`Link`コンテキストの既存のコードリストに連結する標準的なロジックです。`ctxt.Text`はコードリストの先頭を、`ctxt.Etext`は末尾を指します。
        *   `ctxt.Etext = etext`: `Link`コンテキストのコードリストの末尾を、新しく追加されたコードの末尾に更新します。
    *   `ctxt.Plist = nil`, `ctxt.Plast = nil`, `ctxt.Curp = nil`:
        *   `ctxt.Plist`は`Link`コンテキストが保持する`Prog`リストの先頭を、`ctxt.Plast`は末尾を、`ctxt.Curp`は現在の`Prog`を指します。
        *   `Flushplist`が完了した後、これらの`Prog`リストは機械語に変換され、`Link`コンテキストのコードリストに統合されるため、元の`Prog`リストへの参照は不要になります。これらを`nil`に設定することで、`Prog`構造体がGCの対象となり、メモリが解放されます。

これらの変更は、`Prog`構造体が機械語に変換された後、その中間表現がメモリから速やかに解放されることを保証し、コンパイラのメモリフットプリントを削減する上で不可欠です。

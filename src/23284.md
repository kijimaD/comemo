## 変更の背景

このコミットは、Go言語の`fmt`パッケージが、特定の不正なフォーマット指定子（例: `%.[]`）を処理する際に発生するパニックを修正するために導入されました。`fmt`パッケージは、`Printf`のような関数を通じて、指定されたフォーマットに従って値を文字列に変換し出力する機能を提供します。通常、フォーマット指定子は、引数のインデックス、幅、精度などを指定するために使用されます。

しかし、`%.[]`のような非常に短く、かつ構文的に不完全なフォーマット指定子が与えられた場合、`fmt`パッケージの内部パーサーが予期せぬ状態に陥り、配列の範囲外アクセスなどのエラーを引き起こし、結果としてパニックが発生していました。これは、入力のバリデーションが不十分であったり、パーサーが不正な入力に対して堅牢でなかったことに起因します。

このパニックは、ユーザーが意図せず、あるいは悪意を持って不正なフォーマット文字列を`fmt`関数に渡した場合に、プログラムがクラッシュする原因となるため、安定性とセキュリティの観点から修正が必要でした。コミットメッセージにある`Fixes #10675`は、この問題がGoのイシュートラッカーで報告されたバグであることを示しています。

## 前提知識の解説

### Go言語の`fmt`パッケージ

`fmt`パッケージは、Go言語におけるフォーマットI/O（入出力）を提供する標準ライブラリです。C言語の`printf`/`scanf`に似た機能を提供し、様々なデータ型を整形して文字列として出力したり、文字列から値を読み取ったりすることができます。

主要な関数には以下のようなものがあります。
*   `fmt.Printf(format string, a ...interface{}) (n int, err error)`: フォーマット文字列に従って標準出力に整形して出力します。
*   `fmt.Sprintf(format string, a ...interface{}) string`: フォーマット文字列に従って整形し、結果を文字列として返します。
*   `fmt.Errorf(format string, a ...interface{}) error`: フォーマット文字列に従って整形し、新しいエラーを生成します。

### フォーマット指定子 (Verb)

`fmt`パッケージのフォーマット文字列は、`%`で始まる「フォーマット指定子」を含みます。これらは、対応する引数をどのように整形するかを指示します。一般的なフォーマット指定子の構造は以下のようになります。

`%[argNum][flags][width][.precision]verb`

*   `argNum` (引数インデックス): `[n]`の形式で、どの引数を使用するかを明示的に指定します。例: `%[2]d`は2番目の引数を10進数で表示します。
*   `flags` (フラグ): 出力の詳細な挙動を制御します（例: `+`で常に符号を表示、`#`で代替フォーマット）。
*   `width` (幅): 出力される最小の文字幅を指定します。
*   `.precision` (精度): 浮動小数点数の小数点以下の桁数、文字列の最大文字数などを指定します。
*   `verb` (動詞): 引数の型と表示形式を指定します（例: `d`は10進数、`s`は文字列、`v`はデフォルト形式）。

### パニック (Panic)

Go言語におけるパニックは、プログラムの実行中に回復不可能なエラーが発生したことを示すメカニズムです。パニックが発生すると、通常のプログラムフローは中断され、遅延関数（`defer`）が実行された後、プログラムはクラッシュします。パニックは、通常、プログラマーの論理的な誤り（例: nilポインタのデリファレンス、配列の範囲外アクセス）や、予期せぬシステムエラーによって引き起こされます。

このコミットで修正された問題は、`fmt`パッケージが不正なフォーマット文字列を処理する際に、内部的に配列の範囲外アクセスのようなエラーを引き起こし、パニックに至るケースでした。

## 技術的詳細

このコミットは、`fmt`パッケージのフォーマット文字列解析ロジックにおける脆弱性を修正しています。特に、引数インデックス、幅、精度などを解析する部分に焦点を当てています。

`fmt`パッケージの内部では、`Printf`のような関数が呼び出されると、与えられたフォーマット文字列を文字ごとに走査し、`%`に遭遇するとフォーマット指定子の解析を開始します。この解析プロセスは、`parseArgNumber`や`argNumber`といった内部関数によって行われます。

問題は、`%.[]`のような非常に短い、または不完全なフォーマット指定子が与えられた場合に発生しました。
1.  `%.[]`の場合、`%`の後に`.`が続き、その後に`[`が来ます。
2.  `[`は引数インデックスの開始を示す文字として認識されますが、その後に続くはずの数字や`]`が適切に存在しないため、パーサーが期待する文字を見つけられず、内部的な文字列（バイトスライス）のインデックスアクセスが範囲外になる可能性がありました。
3.  特に、`parseArgNumber`関数は、`[`の後に続く数字と`]`を解析しようとしますが、入力文字列が短すぎる場合、必要なバイト数がないため、インデックスアクセスが失敗し、パニックを引き起こしていました。

このコミットは、これらの内部パーシング関数に堅牢性を持たせることで、このようなパニックを防ぎます。具体的には、文字列の長さを事前にチェックし、不正なアクセスを未然に防ぐように変更されています。

## コアとなるコードの解説

### `src/fmt/fmt_test.go`の変更

*   `reorderTests`というテストスライスに、新しいテストケースが追加されました。
    ```go
    {"%.[]", SE{}, "%!](BADINDEX)"}, // Issue 10675
    ```
    このテストケースは、不正なフォーマット文字列`%.[]`が与えられたときに、`fmt`パッケージがパニックを起こさずに、期待されるエラーメッセージ`%!](BADINDEX)`を生成することを確認します。これは、修正が正しく機能していることを検証するための重要な追加です。

### `src/fmt/print.go`の変更

1.  **`parseArgNumber`関数の変更**:
    ```diff
    +\t// There must be at least 3 bytes: [n].
    +\tif len(format) < 3 {
    +\t\treturn 0, 1, false
    +\t}\n+
    ```
    `parseArgNumber`関数は、`%[n]`のような引数インデックスを解析する際に呼び出されます。この変更は、`format`文字列の長さをチェックするガード句を追加しています。`[n]`形式の引数インデックスは、最低でも`[`、数字、`]`の3バイトを必要とします。もし`format`の長さが3未満であれば、有効な引数インデックスを解析することは不可能であるため、すぐに`false`を返してエラーを示します。これにより、`format[i]`のようなインデックスアクセスが範囲外になることを防ぎ、パニックを回避します。

2.  **`argNumber`関数の変更**:
    ```diff
    -\treturn argNum, i + wid, true
    +\treturn argNum, i + wid, ok
    ```
    `argNumber`関数は、フォーマット指定子内の引数インデックス、幅、精度などを解析する際に、`parseArgNumber`を呼び出します。元のコードでは、`parseArgNumber`の戻り値である`ok`（解析が成功したかどうかを示すブール値）を無視して、常に`true`を返していました。この変更により、`parseArgNumber`が返した`ok`の値をそのまま`argNumber`の戻り値として伝播させるようになりました。これにより、`parseArgNumber`で検出された不正なフォーマットが、呼び出し元に正しく通知され、適切なエラー処理が行われるようになります。

3.  **`doPrintf`関数の変更**:
    ```diff
    -\t\t\tif format[i] == '*' {
    +\t\t\tif i < end && format[i] == '*' {
    ```
    `doPrintf`関数は、`fmt.Printf`の主要な処理ロジックを含んでいます。この変更は、`format[i]`にアクセスする前に`i < end`という境界チェックを追加しています。これは、`*`（アスタリスク）が幅や精度として使用される場合に、`format`文字列の末尾に到達しているにもかかわらず、さらに文字を読み取ろうとしてインデックスが範囲外になるのを防ぐためのものです。`end`はフォーマット文字列の有効な終端インデックスを示します。このチェックにより、不正なフォーマット文字列が与えられた場合でも、安全に処理を続行できるようになります。

これらの変更は全体として、`fmt`パッケージのフォーマット文字列パーサーの堅牢性を高め、不正な入力に対するパニックを防ぐことを目的としています。

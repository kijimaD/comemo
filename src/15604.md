## 変更の背景

この変更の背景には、Goの`cgo`機能を用いたテストコードの堅牢性向上が挙げられます。`cgo`はGoプログラムからC言語のコードを呼び出すためのメカニズムであり、Cライブラリの動的ロード（`dlopen`や`dlsym`など）を伴う場合があります。

元のテストコード`issue4029.go`では、`dlopen`や`dlsym`の呼び出しが失敗した場合に`t.Fatal`を使用していました。`t.Fatal`はテスト関数を即座に終了させ、そのテストを失敗としてマークします。これは、テストの実行中に最初に見つかったエラーでテストスイート全体の実行が停止してしまうことを意味します。

しかし、テストの目的によっては、最初のエラーで即座に停止するのではなく、複数のエラーを報告し、テスト関数の残りの部分を実行し続けることが望ましい場合があります。特に、動的ライブラリのロードやシンボル解決は環境依存性が高く、特定の環境で失敗しても、他の部分のテストは続行してより多くの情報（例えば、他のシンボル解決の失敗など）を得たい場合があります。

このコミットは、このようなシナリオに対応するため、エラーが発生してもテスト関数が即座に終了しないように、エラー報告のメカニズムを`t.Fatal`から`t.Error`に変更しています。これにより、テストの実行がより柔軟になり、単一のエラーでテストスイート全体が中断されることを防ぎ、より包括的なエラーレポートが可能になります。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を理解しておく必要があります。

*   **cgo**: Go言語の機能の一つで、GoプログラムからC言語のコードを呼び出したり、C言語のライブラリを使用したりするためのものです。Goのコード内にCのコードを直接記述することも可能です。
*   **動的リンクライブラリ (Dynamic Link Library, DLL / Shared Object, SO)**: プログラムの実行時にロードされるライブラリです。これにより、プログラムのサイズを小さくしたり、複数のプログラムで同じライブラリを共有したりすることができます。
*   **`dlopen`**: POSIXシステム（Linux, macOSなど）で提供される関数で、動的リンクライブラリをロードするために使用されます。成功するとライブラリへのハンドルを返します。
*   **`dlsym`**: `dlopen`でロードされたライブラリから、指定されたシンボル（関数や変数など）のアドレスを取得するために使用される関数です。
*   **`RTLD_NOW`**: `dlopen`関数のフラグの一つで、ライブラリがロードされた直後に、そのライブラリ内のすべての未解決のシンボルを解決することを指示します。これにより、後でシンボルが見つからないという実行時エラーを防ぐことができます。
*   **`dlerror`**: `dlopen`や`dlsym`などの`dl`関数が最後に発生させたエラーに関する文字列を返す関数です。エラーの詳細な情報を取得するために使用されます。
*   **Goの`testing`パッケージ**: Go言語の標準ライブラリに含まれるテストフレームワークです。テスト関数は`func TestXxx(t *testing.T)`という形式で定義されます。
*   **`*testing.T`**: テスト関数に渡される構造体で、テストの実行状態を管理し、テスト結果を報告するためのメソッドを提供します。
*   **`t.Fatal(...)`**: `*testing.T`のメソッドの一つです。引数に指定されたメッセージをログに出力し、現在のテスト関数を即座に終了させます。このメソッドが呼び出されると、テストは失敗としてマークされ、そのテスト関数内の後続のコードは実行されません。
*   **`t.Error(...)`**: `*testing.T`のメソッドの一つです。引数に指定されたメッセージをログに出力しますが、現在のテスト関数は終了させません。テストは失敗としてマークされますが、テスト関数内の後続のコードは引き続き実行されます。
*   **`t.Log(...)`**: `*testing.T`のメソッドの一つです。引数に指定されたメッセージをログに出力します。テストの成功・失敗には影響しません。デバッグ情報やテストの進行状況を記録するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、Goのテストフレームワークにおけるエラー報告の粒度と、それがテストの実行フローに与える影響の変更です。

元のコードでは、`dlopen`または`dlsym`の呼び出しが失敗した場合に`t.Fatal`を使用していました。
```go
if this_process == nil {
    t.Fatal("dlopen:", C.GoString(C.dlerror()))
}
// ...
if symbol_address == nil {
    t.Fatal("dlsym:", C.GoString(C.dlerror()))
}
```
`t.Fatal`が呼び出されると、そのテスト関数はそこで実行を停止し、テストスイートは次のテスト関数へと移ります。これは、致命的なエラーが発生し、それ以上テストを続行しても意味がない場合に適しています。しかし、`dlopen`や`dlsym`の失敗が必ずしもテスト全体の続行を不可能にするわけではない場合、この挙動は望ましくありません。例えば、テスト関数内で複数のシンボルをロードしようとしている場合、最初のシンボルロードが失敗しただけでテストが終了してしまうと、他のシンボルロードの失敗に関する情報が得られなくなります。

変更後のコードでは、`t.Fatal`が`t.Error`に置き換えられ、エラー発生時に`return`が追加されています。
```go
if this_process == nil {
    t.Error("dlopen:", C.GoString(C.dlerror()))
    return // 追加
}
// ...
if symbol_address == nil {
    t.Error("dlsym:", C.GoString(C.dlerror()))
    return // 追加
}
```
`t.Error`は、エラーを報告しますが、テスト関数の実行は継続します。これにより、テスト関数内で複数のエラーが発生した場合でも、それらすべてが報告されるようになります。ただし、このコミットでは`t.Error`の後に`return`文が追加されています。これは、`dlopen`や`dlsym`が失敗した場合、その後の処理（例えば、`dlsym`を呼び出す前に`dlopen`が失敗した場合など）は無意味になるため、その特定のコードパスの実行は停止させるが、テスト関数全体は終了させない、という意図を示しています。

この変更により、`dlopen`や`dlsym`の呼び出しが失敗しても、テスト関数は即座に終了せず、エラーが報告された後に`return`によってそのブロックの実行が停止します。これにより、テスト関数内で他の独立したテストロジックがある場合、それらは引き続き実行される可能性があります。これは、テストのデバッグや問題の特定において、より多くの情報を提供できるという利点があります。

## コアとなるコードの解説

変更されたコードは、`loadThySelf`関数内にあります。この関数は、`dlopen`と`dlsym`を使用して、現在のプロセスから特定のシンボルを動的にロードしようとします。

1.  **`dlopen`呼び出しのエラーハンドリング**:
    *   変更前: `if this_process == nil { t.Fatal("dlopen:", C.GoString(C.dlerror())) }`
        *   `dlopen`が失敗した場合（`this_process`が`nil`）、`t.Fatal`が呼び出され、テスト関数は即座に終了していました。
    *   変更後: `if this_process == nil { t.Error("dlopen:", C.GoString(C.dlerror())) return }`
        *   `dlopen`が失敗した場合、`t.Error`が呼び出され、エラーがログに記録されますが、テスト関数は即座には終了しません。その代わりに`return`文が追加され、`loadThySelf`関数の残りの部分の実行は停止しますが、`test4029`関数（`loadThySelf`を呼び出している親関数）は引き続き実行されます。

2.  **`dlsym`呼び出しのエラーハンドリング**:
    *   変更前: `if symbol_address == nil { t.Fatal("dlsym:", C.GoString(C.dlerror())) } else { t.Log(symbol, symbol_address) }`
        *   `dlsym`が失敗した場合（`symbol_address`が`nil`）、ここでも`t.Fatal`が呼び出され、テスト関数は即座に終了していました。成功した場合は`t.Log`で情報を出力していました。
    *   変更後: `if symbol_address == nil { t.Error("dlsym:", C.GoString(C.dlerror())) return }`
        *   `dlsym`が失敗した場合、`t.Error`が呼び出され、エラーがログに記録されます。ここでも`return`が追加され、`loadThySelf`関数の残りの部分の実行は停止します。
        *   成功時の`else`ブロックが削除され、`t.Log(symbol, symbol_address)`が`if`ブロックの外に移動しています。これは、`dlsym`が成功した場合にのみ`t.Log`が実行されるようにするためです。`dlsym`が失敗して`return`した場合、この`t.Log`は実行されません。

この変更の主な目的は、`dlopen`や`dlsym`の失敗がテストの実行を即座に中断させるのではなく、エラーを報告しつつ、テスト関数内の他の部分の実行を可能にすることです。これにより、テストのデバッグ時に複数のエラー情報を一度に取得できるようになり、テストの堅牢性と情報収集能力が向上します。

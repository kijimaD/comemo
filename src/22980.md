## 変更の背景

この変更は、Go言語の`regexp`パッケージで報告されたIssue 10319「REGEXP: CRASH IN NEW BACKTRACK ENGINE」を修正するために行われました。

Issue 10319では、`regexp`パッケージの新しいバックトラックエンジンにおいて、`panic: runtime error: index out of range`というパニックが発生することが報告されました。具体的には、`regexp.(*machine).backtrack`関数内の`regexp/backtrack.go:343`（当時のコードベース）で`b.cap[0] = pos`という行が原因でパニックが発生していました。

この問題は、正規表現にキャプチャグループが含まれていない場合でも、内部的にキャプチャ結果を格納するためのスライス`b.cap`が不適切に初期化またはアクセスされることによって引き起こされていました。特に、正規表現マッチングにおいてキャプチャグループが不要な場合、`b.cap`スライスの長さが0になることがあり、その状態で`b.cap[0]`や`b.cap[1]`にアクセスしようとすると、インデックスが範囲外となりパニックが発生していました。

このバグは、正規表現エンジンの堅牢性に影響を与え、特定の条件下でアプリケーションがクラッシュする可能性がありました。そのため、キャプチャが要求された場合にのみ`b.cap`の要素を設定するように修正する必要がありました。

## 前提知識の解説

*   **正規表現 (Regular Expression)**: テキストのパターンを記述するための強力なツールです。Go言語の`regexp`パッケージは、正規表現のコンパイルとマッチング機能を提供します。
*   **キャプチャグループ (Capture Groups)**: 正規表現の一部を括弧`()`で囲むことで、その部分にマッチしたテキストを抽出（キャプチャ）できます。例えば、`(\d+)-(\d+)`という正規表現では、2つの数字のシーケンスを個別にキャプチャできます。
    *   `b.cap[0]`と`b.cap[1]`は、通常、正規表現全体がマッチした開始位置と終了位置（`b.cap[0]`が開始、`b.cap[1]`が終了）を表すために内部的に使用されます。それ以降のインデックス（`b.cap[2]`, `b.cap[3]`など）は、ユーザーが定義したキャプチャグループに対応します。
*   **バックトラック (Backtracking)**: 正規表現エンジンのマッチングアルゴリズムの一種です。パターンにマッチしようと試み、マッチしない場合は以前の決定点に戻って別のパスを試行します。複雑な正規表現や入力に対しては、パフォーマンスの問題（カタストロフィックバックトラック）を引き起こす可能性がありますが、Goの`regexp`パッケージはRE2エンジンをベースにしており、線形時間でのマッチングを保証することでこの問題を緩和しています。
*   **`regexp`パッケージの内部構造**:
    *   `machine`構造体: 正規表現のマッチングを実行する状態機械を表します。
    *   `bitState`構造体: バックトラックエンジンの内部状態を管理します。これには、キャプチャ結果を格納する`cap`スライスが含まれます。
    *   `b.cap`スライス: `bitState`構造体の一部で、正規表現のマッチング中にキャプチャされた部分文字列の開始/終了インデックスを格納するために使用されます。このスライスの長さは、正規表現が持つキャプチャグループの数（+2、全体マッチ用）によって決定されます。

## 技術的詳細

このコミットの核心は、`regexp`パッケージのバックトラックエンジンが、キャプチャグループが要求されていない状況で`b.cap`スライスを不適切に扱っていた問題の修正です。

Goの`regexp`パッケージは、内部的に正規表現をコンパイルし、その結果を`syntax.Prog`というプログラム表現に変換します。マッチングは、このプログラムを実行する`machine`によって行われます。バックトラックエンジンは、特に複雑な正規表現や特定のパターンに対して使用されることがあります。

問題は、`machine`が`bitState`構造体（`b`と命名されていることが多い）を使用してマッチングの状態を管理する際に発生しました。`bitState`には`cap`という`[]int`型のスライスがあり、これがキャプチャグループの開始/終了インデックスを保持します。正規表現にキャプチャグループが一つも定義されていない場合、`cap`スライスの長さは0になります。

しかし、コードの一部では、キャプチャグループが要求されているかどうかに関わらず、正規表現全体のマッチ開始位置と終了位置を格納するために`b.cap[0]`と`b.cap[1]`にアクセスしようとしていました。`len(b.cap)`が0の場合、これらのアクセスは`panic: runtime error: index out of range`を引き起こします。

このコミットでは、以下の変更によってこの問題を解決しています。

1.  **`bitState.reqcap`フィールドの削除**: 以前は`bitState`構造体に`reqcap`というブール値のフィールドがあり、ユーザーがキャプチャを要求したかどうかを示していました。このフィールドは冗長であり、`len(b.cap)`が0かどうかでキャプチャの有無を判断できるため削除されました。
2.  **`bitState.reset`関数の変更**:
    *   `reqcap`引数が削除され、`ncap`（キャプチャの数）のみを受け取るようになりました。
    *   `b.cap`スライスの再割り当てロジックが改善されました。`cap(b.cap) < ncap`の場合にのみ新しいスライスを作成し、それ以外の場合は既存のスライスを`ncap`の長さにスライスし直すことで、メモリの再利用を促進しつつ、適切な長さを保証します。
3.  **`tryBacktrack`関数内の条件分岐の変更**:
    *   以前は`!b.reqcap`でキャプチャが不要な場合を判定していましたが、これを`len(b.cap) == 0`に変更しました。これにより、キャプチャスライスが空であれば、キャプチャ結果を記録する必要がないと判断します。
    *   `b.cap[1] = pos`の代入を行う前に`len(b.cap) > 1`という条件を追加しました。これにより、`b.cap`スライスに少なくとも2つの要素を格納する容量がある場合にのみ、終了位置を記録するようにします。
4.  **`backtrack`関数内の条件分岐の変更**:
    *   `reqcap`引数が`ncap`に変更されました。
    *   `m.matchcap`スライスを`ncap`の長さにスライスし直すことで、適切な長さが保証されます。
    *   `b.cap[0] = pos`の代入を行う前に`len(b.cap) > 0`という条件を追加しました。これにより、`b.cap`スライスに少なくとも1つの要素を格納する容量がある場合にのみ、開始位置を記録するようにします。

これらの変更により、`b.cap`スライスが空である（つまり、キャプチャが要求されていない）場合に、存在しないインデックスにアクセスしようとする試みが防止され、パニックが解消されました。

## コアとなるコードの解説

このコミットの主要な変更は、`regexp`パッケージのバックトラックエンジンがキャプチャグループを処理する方法をより堅牢にすることにあります。

1.  **`bitState.reqcap`の削除**:
    *   以前は、正規表現がキャプチャグループを要求しているかどうかを示すために`bitState`構造体に`reqcap`というフィールドがありました。しかし、`b.cap`スライスの長さ（`len(b.cap)`）が0であるかどうかで、キャプチャが要求されていないことを判断できるため、このフィールドは冗長でした。削除することでコードが簡潔になります。

2.  **`bitState.reset`の改善**:
    *   `reset`関数は、バックトラックエンジンの状態を初期化する際に呼び出されます。以前は`reqcap`引数を受け取っていましたが、これが不要になりました。
    *   最も重要な変更は、`b.cap`スライスの管理方法です。
        ```go
        -	if len(b.cap) < ncap {
        +	if cap(b.cap) < ncap {
        		b.cap = make([]int, ncap)
        +	} else {
        +		b.cap = b.cap[:ncap]
        	}
        ```
        この変更により、`b.cap`スライスの容量（`cap(b.cap)`）が`ncap`（必要なキャプチャの数）よりも小さい場合にのみ新しいスライスが作成されます。そうでない場合は、既存のスライスを`ncap`の長さにスライスし直す（`b.cap = b.cap[:ncap]`）ことで、メモリの再割り当てを避け、効率的にスライスを再利用します。これにより、`b.cap`は常に必要な長さを持つことが保証されます。

3.  **`tryBacktrack`と`backtrack`における`b.cap`アクセス前のチェック**:
    *   `tryBacktrack`関数は、マッチングの試行中に呼び出されます。ここで、正規表現全体のマッチ終了位置を`b.cap[1]`に設定しようとしますが、その前に`len(b.cap) > 1`という条件が追加されました。
        ```go
        -			b.cap[1] = pos
        +			if len(b.cap) > 1 {
        +				b.cap[1] = pos
        +			}
        ```
        これにより、`b.cap`スライスが少なくとも2つの要素を格納できる場合にのみ、`b.cap[1]`への書き込みが行われます。キャプチャが要求されていない場合（`len(b.cap)`が0または1の場合）、この条件は偽となり、インデックス範囲外のアクセスが防止されます。
    *   同様に、`backtrack`関数では、正規表現全体のマッチ開始位置を`b.cap[0]`に設定しようとしますが、その前に`len(b.cap) > 0`という条件が追加されました。
        ```go
        -		b.cap[0] = pos
        +		if len(b.cap) > 0 {
        +			b.cap[0] = pos
        +		}
        ```
        これにより、`b.cap`スライスが少なくとも1つの要素を格納できる場合にのみ、`b.cap[0]`への書き込みが行われます。

これらの変更は、`b.cap`スライスが空である（つまり、キャプチャが要求されていない）場合に、存在しないインデックスにアクセスしようとする試みを防ぐことで、`regexp`パッケージの安定性を大幅に向上させました。

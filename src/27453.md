# [インデックス 27453] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける`StartProcess`関数内で発生する、子プロセスへのファイルディスクリプタ引き渡し時のバグ修正に関するものです。具体的には、`forkAndExecInChild`関数におけるファイルディスクリプタの並べ替え処理中に、子プロセスとの通信に使用されるパイプが誤って閉じられてしまう問題を解決します。

## 元コミット内容

`syscall: fix accidental close of exec status pipe in StartProcess`

`syscall.forkAndExecInChild`関数において、子プロセスに渡されるファイルディスクリプタを並べ替える「Pass 1」および「Pass 2」というコードブロックが存在します。もし「Pass 1」が`fds = {0,2,1}`、`nextfd = 4`、`pipe = 4`という状態で開始された場合、「don't stomp on pipe」とラベル付けされたステートメント（パイプを上書きしないためのチェック）が遅すぎます。この場合、先行する`DUP`システムコールによって、親プロセスに実行ステータスを渡すために必要なパイプが閉じてしまいます。

この「don't stomp」テストをより早い段階に移動することで、パイプが保護されるようになります。

Issue #14979 を修正します。

## 変更の背景

Go言語の`os.StartProcess`関数は、内部的に`syscall`パッケージの`forkAndExecInChild`関数を呼び出して新しいプロセスを起動します。このプロセス起動の際、親プロセスは子プロセスに特定のファイルディスクリプタ（標準入力、標準出力、標準エラーなど）を渡す必要があります。また、子プロセスの実行ステータス（成功/失敗など）を親プロセスに伝えるために、内部的にパイプが使用されます。

このコミットが修正する問題は、`forkAndExecInChild`関数内でファイルディスクリプタを操作するロジックに潜んでいました。特に、子プロセスに渡すファイルディスクリプタの番号を調整する際に、`nextfd`という変数が次に利用可能なファイルディスクリプタ番号を追跡します。この`nextfd`が、偶然にも子プロセスの実行ステータスを親に伝えるための内部パイプのファイルディスクリプタ番号と同じ値になってしまうケースがありました。

問題のシナリオは以下の通りです。
1.  `forkAndExecInChild`が実行される。
2.  `Pass 1`というファイルディスクリプタの並べ替え処理が開始される。
3.  `fds`配列（子プロセスに渡すファイルディスクリプタのリスト）が`{0, 2, 1}`のような状態であり、`nextfd`が`4`、内部パイプのファイルディスクリプタも`4`であると仮定します。
4.  `Pass 1`の処理中に、`fd[i] < int(i)`という条件を満たすファイルディスクリプタ（例えば`fd[0]=0`）に対して`DUP`（または`DUP2`）システムコールが実行されます。この`DUP`は、`fd[i]`を`nextfd`に複製しようとします。
5.  この時点で`nextfd`が`pipe`と同じ値（例: `4`）であるため、`DUP`システムコールは意図せず内部パイプを上書きしてしまいます。
6.  その後、「don't stomp on pipe」というチェック（`if nextfd == pipe { nextfd++ }`）が実行されますが、この時点では既にパイプは上書きされてしまっており、手遅れとなります。

結果として、子プロセスが起動しても、親プロセスは子プロセスの実行ステータスを正しく受け取ることができず、`StartProcess`がハングアップしたり、誤ったエラーを報告したりする可能性がありました。この問題は、Issue #14979として報告されていました（ただし、Web検索では直接的な情報が見つかりませんでした）。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **ファイルディスクリプタ (File Descriptor, FD)**:
    Unix系OSにおいて、ファイルやソケット、パイプなどのI/Oリソースを識別するためにカーネルがプロセスに割り当てる非負の整数です。通常、`0`は標準入力 (stdin)、`1`は標準出力 (stdout)、`2`は標準エラー出力 (stderr) に割り当てられます。

2.  **`fork()`システムコール**:
    現在のプロセス（親プロセス）のほぼ完全なコピーである新しいプロセス（子プロセス）を作成します。子プロセスは親プロセスのファイルディスクリプタ、メモリ空間などを継承します。

3.  **`exec()`システムコール**:
    現在のプロセスイメージを、指定された新しいプログラムイメージで置き換えます。`exec`が成功すると、新しいプログラムが現在のプロセスのPIDで実行を開始します。ファイルディスクリプタは通常、`exec`呼び出し後も開いたまま維持されますが、`FD_CLOEXEC`フラグが設定されている場合は閉じられます。

4.  **`DUP` / `DUP2` システムコール**:
    *   `DUP(oldfd)`: `oldfd`が指すファイルディスクリプタと同じファイル記述エントリを参照する新しいファイルディスクリプタを返します。新しいファイルディスクリプタは、利用可能な最小の番号が割り当てられます。
    *   `DUP2(oldfd, newfd)`: `newfd`が指すファイルディスクリプタを閉じ（もし開いていれば）、`oldfd`が指すファイル記述エントリと同じものを参照するように`newfd`を再割り当てします。これにより、特定のファイルディスクリプタ番号を強制的に使用できます。

5.  **パイプ (Pipe)**:
    プロセス間通信 (IPC) の一種で、一方のプロセスが書き込み、もう一方のプロセスが読み込むことができる単方向のデータストリームです。`os.StartProcess`のような関数では、子プロセスの実行結果やエラー情報を親プロセスに伝えるために内部的にパイプが使用されることがあります。

6.  **`FD_CLOEXEC` フラグ**:
    ファイルディスクリプタに設定できるフラグで、「`exec`時にクローズする」ことを意味します。このフラグが設定されたファイルディスクリプタは、`exec`システムコールが成功すると自動的に閉じられます。これは、子プロセスに不要なファイルディスクリプタが漏洩するのを防ぐために重要です。

`syscall.forkAndExecInChild`関数は、これらのシステムコールを組み合わせて、新しいプロセスを安全かつ効率的に起動し、親プロセスと子プロセスの間でファイルディスクリプタを適切に管理する役割を担っています。

## 技術的詳細

このコミットの核心は、`syscall.forkAndExecInChild`関数内のファイルディスクリプタの処理順序の変更です。この関数は、子プロセスに渡すファイルディスクリプタを準備する際に、いくつかのステップを踏みます。

1.  **`fd`配列の準備**: 子プロセスに渡されるファイルディスクリプタのリスト（`fd`）が作成されます。
2.  **`pipe`の作成**: 親プロセスと子プロセスの間で実行ステータスを通信するためのパイプが作成され、その書き込み側ファイルディスクリプタが`pipe`変数に格納されます。
3.  **`nextfd`の初期化**: `nextfd`は、`fd`配列内の既存のファイルディスクリプタ番号と`pipe`の番号を考慮して、次に利用可能な最小のファイルディスクリプタ番号に初期化されます。これは、既存のファイルディスクリプタを上書きしないようにするためです。
4.  **ファイルディスクリプタの並べ替え (Pass 1 & Pass 2)**:
    この部分が問題の箇所です。`forkAndExecInChild`は、子プロセスに渡すファイルディスクリプタが`0, 1, 2, ...`のように連続した番号になるように並べ替える必要があります。これは、`fd[i] >= 0 && fd[i] < int(i)`という条件でループを回し、`fd[i]`が`i`よりも小さい場合（つまり、`i`番目のファイルディスクリプタが既に`i`より小さい番号に割り当てられている場合）、`fd[i]`を`nextfd`に複製し、`fd[i]`を`nextfd`に更新し、`nextfd`をインクリメントするという処理を行います。

問題は、この「ファイルディスクリプタの並べ替え」処理の途中で、`nextfd`が内部パイプのファイルディスクリプタ番号（`pipe`）と同じ値になってしまう可能性があったことです。元のコードでは、`DUP`システムコールが実行された**後**に`if nextfd == pipe { nextfd++ }`というチェックがありました。

```go
// 変更前 (例: exec_bsd.go)
for i = 0; i < len(fd); i++ {
    if fd[i] >= 0 && fd[i] < int(i) {
        _, _, err1 = RawSyscall(SYS_DUP2, uintptr(fd[i]), uintptr(nextfd), 0) // ここでDUPが実行される
        if err1 != 0 {
            goto childerror
        }
        RawSyscall(SYS_FCNTL, uintptr(nextfd), F_SETFD, FD_CLOEXEC)
        fd[i] = nextfd
        nextfd++
        if nextfd == pipe { // このチェックが遅すぎる
            nextfd++
        }
    }
}
```

この順序だと、`nextfd`が`pipe`と同じ値である場合、`DUP2`システムコールが`pipe`を指すファイルディスクリプタを上書きしてしまいます。その後で`nextfd`をインクリメントしても、既にパイプは壊されています。

コミットの修正は、この`if nextfd == pipe { nextfd++ }`というチェックを`DUP`システムコールが実行される**前**に移動することです。

```go
// 変更後 (例: exec_bsd.go)
for i = 0; i < len(fd); i++ {
    if fd[i] >= 0 && fd[i] < int(i) {
        if nextfd == pipe { // このチェックがDUPの前に移動
            nextfd++
        }
        _, _, err1 = RawSyscall(SYS_DUP2, uintptr(fd[i]), uintptr(nextfd), 0)
        if err1 != 0 {
            goto childerror
        }
        RawSyscall(SYS_FCNTL, uintptr(nextfd), F_SETFD, FD_CLOEXEC)
        fd[i] = nextfd
        nextfd++
    }
}
```

この変更により、`DUP`システムコールが実行される前に`nextfd`が`pipe`と同じ値になることが検出され、`nextfd`がインクリメントされて`pipe`とは異なる値になるため、パイプが誤って上書きされることを防ぎます。

この修正は、`src/syscall/exec_bsd.go`、`src/syscall/exec_linux.go`、`src/syscall/exec_plan9.go`、`src/syscall/exec_solaris.go`といった、各OS固有の`forkAndExecInChild`実装に適用されています。これは、ファイルディスクリプタの操作がOSによって異なるシステムコール（`SYS_DUP2`, `_SYS_dup`, `SYS_DUP`, `F_DUP2FD`など）を使用するためです。

また、このコミットには`src/syscall/syscall_test.go`に新しいテストケース`TestExecErrPermutedFds`が追加されています。このテストは、無効なプログラム（例: `/`）を`os.StartProcess`で起動し、エラーが正しく返されることを確認することで、パイプが正しく機能していることを間接的に検証します。もしパイプが壊れていれば、`StartProcess`はエラーを報告できず、ハングアップするか、誤った結果を返す可能性があります。

## コアとなるコードの解説

`forkAndExecInChild`関数は、Goプログラムが新しいプロセスを起動する際の低レベルなOSインタフェースを提供します。この関数は、`fork`と`exec`の組み合わせを模倣し、子プロセスが正しく初期化され、親プロセスとの間で必要な通信ができるようにします。

変更されたコードブロックは、子プロセスに渡されるファイルディスクリプタの「リマップ」または「並べ替え」を担当しています。これは、子プロセスが期待するファイルディスクリプタ番号（通常は`0`、`1`、`2`など）に、親プロセスが持つ実際のファイルディスクリプタをマッピングするために行われます。

*   `for i = 0; i < len(fd); i++`: このループは、子プロセスに渡すファイルディスクリプタのリスト`fd`を反復処理します。`i`は子プロセスが期待するファイルディスクリプタ番号を表します。
*   `if fd[i] >= 0 && fd[i] < int(i)`: この条件は、現在の`i`番目のファイルディスクリプタが、すでに`i`よりも小さい番号に割り当てられている場合に真となります。これは、ファイルディスクリプタの衝突や、特定のディスクリプタを低い番号に移動する必要がある場合に発生します。
*   `if nextfd == pipe { nextfd++ }`: **このコミットで追加/移動された行です。** `nextfd`は次に利用可能なファイルディスクリプタ番号を追跡します。`pipe`は親プロセスと子プロセスの通信用パイプのファイルディスクリプタです。このチェックは、`nextfd`が`pipe`と同じ値になることを防ぎます。もし同じ値であれば、`nextfd`をインクリメントして、`pipe`を上書きしないようにします。
*   `RawSyscall(SYS_DUP2, uintptr(fd[i]), uintptr(nextfd), 0)` (または類似のシステムコール): `fd[i]`が指すファイルディスクリプタを`nextfd`に複製します。これにより、`fd[i]`の内容が`nextfd`にマッピングされます。
*   `RawSyscall(SYS_FCNTL, uintptr(nextfd), F_SETFD, FD_CLOEXEC)`: 新しく複製されたファイルディスクリプタ`nextfd`に`FD_CLOEXEC`フラグを設定します。これにより、子プロセスが`exec`を実行した際に、このディスクリプタが自動的に閉じられるようになります。これは、子プロセスに不要なリソースが漏洩するのを防ぐためのセキュリティ対策です。
*   `fd[i] = nextfd`: `fd`配列の`i`番目のエントリを、新しく割り当てられた`nextfd`に更新します。
*   `nextfd++`: 次の利用可能なファイルディスクリプタ番号をインクリメントします。

この修正は、ファイルディスクリプタの割り当てロジックにおける微妙な競合状態を解決し、`os.StartProcess`の堅牢性を向上させます。

追加された`TestExecErrPermutedFds`テストは、この修正が正しく機能していることを確認するためのものです。無効な実行可能ファイル（例: `/`）を起動しようとすると、`os.StartProcess`はエラーを返すはずです。もしパイプが壊れていれば、このエラーが親プロセスに正しく伝達されない可能性があります。このテストは、エラーが期待通りに返されることを確認することで、パイプベースの通信メカニズムが健全であることを保証します。

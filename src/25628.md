# [インデックス 25628] ファイルの概要

このコミットは、Goランタイムの内部パッケージである `runtime/internal/atomic` から、アーキテクチャ固有の `_CacheLineSize` 定義ファイル群 (`arch1_*.go`) を削除し、代わりに `runtime/internal/sys` パッケージで一元的に定義されている `sys.CacheLineSize` を利用するように変更するものです。これにより、コードの重複を排除し、保守性を向上させています。

## 元コミット内容

`runtime/internal/atomic` パッケージから `arch1_*.go` ファイル群を削除します。
`runtime/internal/atomic` をチェックインした際に、アーキテクチャごとの `_CacheLineSize` 定義のコピーを作成しましたが、`runtime/internal/sys` がチェックインされたため、そちらの定義を使用できるようになりました。

## 変更の背景

Goランタイムは、様々なアーキテクチャ（386, amd64, armなど）に対応しており、それぞれのアーキテクチャで異なる特性を持つ場合があります。特に、CPUのキャッシュラインサイズはアーキテクチャによって異なる重要な値です。

このコミット以前は、`runtime/internal/atomic` パッケージ内で、各アーキテクチャ向けに `_CacheLineSize` という定数が個別のファイル (`arch1_386.go`, `arch1_amd64.go` など) で定義されていました。これは、`runtime/internal/atomic` が導入された当初、キャッシュラインサイズに関する情報が他の場所で利用可能でなかったための一時的な措置と考えられます。

しかし、`runtime/internal/sys` パッケージが導入され、そこでアーキテクチャ固有のシステム情報（`CacheLineSize`を含む）が一元的に管理されるようになったため、`runtime/internal/atomic` 内の重複した定義は不要となりました。この変更は、コードの重複を排除し、単一の情報源 (Single Source of Truth) を確立することで、Goランタイムの保守性と整合性を向上させることを目的としています。

## 前提知識の解説

### 1. CPUキャッシュとキャッシュラインサイズ

*   **CPUキャッシュ**: CPUはメインメモリよりも高速な小容量のメモリ（キャッシュ）を内蔵しており、頻繁にアクセスされるデータを一時的に保存します。これにより、メモリへのアクセス速度のボトルネックを軽減し、プログラムの実行速度を向上させます。
*   **キャッシュライン**: キャッシュは「キャッシュライン」と呼ばれる固定サイズのブロック単位でデータを扱います。一般的なキャッシュラインサイズは32バイト、64バイト、128バイトなどです。
*   **キャッシュコヒーレンシ (Cache Coherency)**: マルチコアプロセッサ環境では、複数のCPUコアが同じメモリ領域のデータをキャッシュする可能性があります。このとき、あるコアがキャッシュ上のデータを変更した場合、他のコアのキャッシュもその変更を認識し、整合性を保つ必要があります。この仕組みをキャッシュコヒーレンシと呼びます。
*   **フォルスシェアリング (False Sharing)**: 異なるCPUコアが、それぞれ異なる変数にアクセスしているにもかかわらず、それらの変数が同じキャッシュライン上に存在する場合、一方のコアが変数を更新すると、もう一方のコアのキャッシュラインが無効化され、メインメモリからの再読み込みが発生します。これはパフォーマンスの低下を招き、フォルスシェアリングと呼ばれます。

### 2. Goランタイムの `runtime/internal` パッケージ

Go言語のランタイムは、ガベージコレクション、スケジューラ、メモリ管理など、Goプログラムの実行を支える低レベルな機能を提供します。`runtime/internal` ディレクトリには、ランタイム内部でのみ使用されるパッケージが含まれており、外部からの直接利用は想定されていません。

*   **`runtime/internal/atomic`**: このパッケージは、アトミック操作（不可分操作）を提供します。アトミック操作は、複数のゴルーチン（Goの軽量スレッド）が同時に共有データにアクセスする際に、データの整合性を保証するために不可欠です。例えば、カウンタのインクリメントや、ポインタの交換などがアトミックに行われます。アトミック操作の実装には、CPUのキャッシュラインサイズを考慮したパディング（埋め草）が必要になる場合があります。これは、フォルスシェアリングを防ぎ、アトミック操作の効率を最大化するためです。
*   **`runtime/internal/sys`**: このパッケージは、Goランタイムが動作するシステム（OSやアーキテクチャ）に関する低レベルな情報を提供します。これには、ポインタサイズ、ページサイズ、そしてこのコミットで焦点となっているキャッシュラインサイズなどが含まれます。

### 3. `_CacheLineSize` の重要性

`_CacheLineSize` は、アトミック操作を行う際に、データ構造のパディングを決定するために使用されます。例えば、`spinlock` のような同期プリミティブでは、複数の `spinlock` インスタンスが同じキャッシュラインに配置されると、フォルスシェアリングが発生し、パフォーマンスが低下する可能性があります。これを避けるために、`_CacheLineSize` を利用して、各 `spinlock` インスタンスが異なるキャッシュラインに配置されるようにパディングを追加します。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイムがアーキテクチャ固有の定数、特に `_CacheLineSize` をどのように管理するかという点にあります。

以前は、`runtime/internal/atomic` パッケージ内に、各アーキテクチャ（386, amd64, armなど）に対応する `arch1_*.go` ファイルが存在し、それぞれが `_CacheLineSize` 定数を定義していました。例えば、`arch1_386.go` や `arch1_amd64.go` では `_CacheLineSize = 64` と定義され、`arch1_arm.go` や `arch1_arm64.go` では `_CacheLineSize = 32` と定義されていました。これは、異なるCPUアーキテクチャが異なるキャッシュラインサイズを持つためです。

このアプローチの問題点は以下の通りです。
1.  **コードの重複**: 同じ目的の定数が複数のファイルに散らばっており、新しいアーキテクチャが追加されるたびに新しいファイルを作成する必要がありました。
2.  **保守性の低下**: キャッシュラインサイズに関する情報源が複数存在するため、将来的にキャッシュラインサイズが変更された場合、すべての関連ファイルを更新する必要があり、エラーの発生リスクが高まります。
3.  **整合性の問題**: 各ファイルで個別に定義されているため、誤って異なる値が設定される可能性がありました。

このコミットでは、これらの問題を解決するために、`runtime/internal/sys` パッケージに `CacheLineSize` を一元的に定義するアプローチを採用しました。`runtime/internal/sys` は、Goランタイムが利用するシステム固有の定数を集約する目的で導入されたパッケージです。これにより、`_CacheLineSize` の定義は `runtime/internal/sys` 内の適切なアーキテクチャ固有のファイル（例: `sys_linux_amd64.go` など）に移動され、`runtime/internal/atomic` はその定義をインポートして利用する形になります。

具体的には、`runtime/internal/atomic/atomic_arm.go` の `locktab` 構造体のパディング計算において、ハードコードされた `_CacheLineSize` の代わりに `sys.CacheLineSize` が使用されるようになります。

この変更により、以下のメリットがもたらされます。
*   **単一の情報源**: `CacheLineSize` の定義が `runtime/internal/sys` に集約されるため、情報源が一つになり、整合性が保たれます。
*   **保守性の向上**: 将来的にキャッシュラインサイズが変更された場合でも、`runtime/internal/sys` 内の該当箇所を更新するだけで済みます。
*   **コードの簡素化**: `runtime/internal/atomic` から不要な `arch1_*.go` ファイルが削除され、コードベースがスリム化されます。
*   **クロスコンパイルの容易さ**: `runtime/internal/sys` が提供する抽象化により、異なるアーキテクチャ向けのビルドがより容易になります。

また、`src/cmd/dist/deps.go` と `src/go/build/deps_test.go` の変更は、Goのビルドシステムにおける依存関係の更新を反映しています。`runtime/internal/atomic` が `runtime/internal/sys` に依存するようになったため、これらの依存関係定義ファイルも更新されています。

## コアとなるコードの解説

このコミットの核心は、`_CacheLineSize` の定義を一元化し、その利用方法を変更した点にあります。

`src/runtime/internal/atomic/arch1_*.go` ファイル群の削除は、各アーキテクチャで個別にキャッシュラインサイズを定義していた冗長なコードを排除したことを意味します。これにより、コードベースがクリーンになり、管理が容易になります。

`src/runtime/internal/atomic/atomic_arm.go` の変更は、この新しいアプローチを具体的に示しています。
以前のコードでは、`locktab` という `spinlock` の配列のパディングを計算する際に、そのファイル内で定義されている（またはインポートされた）`_CacheLineSize` を直接使用していました。

```go
var locktab [57]struct {
	l   spinlock
	pad [_CacheLineSize - unsafe.Sizeof(spinlock{})]byte
}
```

この変更により、`runtime/internal/sys` パッケージがインポートされ、`sys.CacheLineSize` が使用されるようになりました。

```go
import (
	"runtime/internal/sys"
	"unsafe"
)

// ...

var locktab [57]struct {
	l   spinlock
	pad [sys.CacheLineSize - unsafe.Sizeof(spinlock{})]byte
}
```

`sys.CacheLineSize` は、Goランタイムが実行されている現在のアーキテクチャのキャッシュラインサイズを正確に反映する値です。これにより、`runtime/internal/atomic` パッケージは、キャッシュラインサイズに関する知識を直接持つ必要がなくなり、その情報を `runtime/internal/sys` に委譲する形になります。これは、関心の分離 (Separation of Concerns) の原則に則った改善であり、各パッケージが自身の責任範囲に集中できるようになります。

`locktab` のパディングは、`spinlock` インスタンスが異なるキャッシュラインに配置されるようにするために重要です。これにより、複数のゴルーチンが異なる `spinlock` を同時に取得しようとした際に、フォルスシェアリングによるパフォーマンス低下を防ぎます。`sys.CacheLineSize` を使用することで、このパディングが常に現在のアーキテクチャに最適化された値になることが保証されます。

`src/cmd/dist/deps.go` と `src/go/build/deps_test.go` の変更は、Goのビルドシステムがパッケージ間の依存関係を正しく解決するために必要です。`runtime/internal/atomic` が `runtime/internal/sys` から `CacheLineSize` をインポートするようになったため、ビルドツールはその依存関係を認識し、`runtime/internal/sys` が `runtime/internal/atomic` よりも先にビルドされるように調整する必要があります。これらのファイルは、Goのビルドプロセスにおける依存関係グラフを定義しており、このコミットは、そのグラフが現実のコードの依存関係と一致するように更新されたことを示しています。

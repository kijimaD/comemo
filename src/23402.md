# [インデックス 23402] ファイルの概要

このコミットは、Goコンパイラの内部（`cmd/internal/gc`）における`append`組み込み関数のコード生成を最適化し、特にライトバリアの発生を抑制することでパフォーマンスを向上させるものです。スライスの再割り当てが発生しない「高速パス」において、スライスの基底ポインタと容量の更新を省略することで、不要なライトバリアの呼び出しを回避します。

## 変更の背景

Go言語の`append`組み込み関数は、スライスに要素を追加する際に非常に頻繁に使用されます。しかし、その内部的な実装、特にコンパイラが生成するコードには最適化の余地がありました。

以前のGoコンパイラでは、`x = append(x, v)`のような`append`操作は、コンパイルの`walk`フェーズでGoの擬似コードに展開されていました。この擬似コードは、スライスの容量が不足している場合に新しい基底配列を割り当て（`grow`）、要素をコピーし、スライスのヘッダ（基底ポインタ、長さ、容量）を更新するという一連の操作を含んでいました。

このアプローチの主な問題点は、スライスの再割り当てが発生しない「高速パス」においても、スライスの基底ポインタと容量が常に更新され、その結果としてライトバリアが不必要に発生する可能性があったことです。ライトバリアはガベージコレクション（GC）の正確性を保証するために必要な処理ですが、頻繁に実行されるとパフォーマンスオーバーヘッドとなります。特に、`x = append(x, v)`のように、ソーススライスとデスティネーションスライスが同じである場合、再割り当てがなければ基底ポインタは変更されないため、その更新とそれに伴うライトバリアは無駄になります。

このコミットは、この非効率性を解消し、`append`の高速パスにおけるライトバリアの発生を抑制することで、全体的なパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの概念を理解しておく必要があります。

1.  **Goスライス (Slice)**:
    *   Goのスライスは、基底配列（underlying array）へのポインタ、長さ（length）、容量（capacity）の3つの要素からなるデータ構造です。
    *   `length`はスライスが現在保持している要素の数を示し、`capacity`は基底配列が保持できる要素の最大数を示します。
    *   スライスは参照型であり、複数のスライスが同じ基底配列を参照することができます。

2.  **`append`関数**:
    *   `append(s, elems...)`は、スライス`s`に`elems`を追加し、新しいスライスを返します。
    *   スライスの容量が不足している場合、`append`はより大きな新しい基底配列を割り当て、既存の要素を新しい配列にコピーし、新しい要素を追加します。このプロセスを「スライスの成長（grow）」と呼びます。
    *   容量が十分な場合、`append`は既存の基底配列の空きスペースに要素を追加し、スライスの長さのみを更新します。この場合、基底配列のポインタは変更されません。

3.  **ガベージコレクション (Garbage Collection - GC)**:
    *   Goランタイムは自動メモリ管理（ガベージコレクション）を行います。GCは、プログラムがもはや到達できないメモリを自動的に解放します。
    *   GCは、オブジェクト間のポインタ関係を追跡して、どのオブジェクトが「生きている」かを判断します。

4.  **ライトバリア (Write Barrier)**:
    *   ライトバリアは、GCが実行されている最中に、プログラムがポインタを書き換える（オブジェクトグラフを変更する）際に挿入される特別なコードです。
    *   これは、GCがオブジェクトグラフをスキャンしている途中でポインタが変更されると、GCがオブジェクトを見落としてしまう（「stale pointer problem」）可能性があるため、その整合性を保つために必要です。
    *   ライトバリアは、ポインタの書き込み操作の前後で、GCが追跡しているオブジェクトの状態を記録したり、特定の処理を実行したりします。これにより、GCの正確性が保証されますが、オーバーヘッドが発生します。

5.  **Goコンパイラのフェーズ**:
    *   Goコンパイラは複数のフェーズを経てソースコードを実行可能なバイナリに変換します。
    *   **`walk`フェーズ**: 抽象構文木（AST）を走査し、高レベルの最適化や組み込み関数の展開などを行います。以前の`append`の擬似コード生成はこのフェーズで行われていました。
    *   **`gen`フェーズ**: `walk`フェーズで変換されたASTから、ターゲットアーキテクチャの機械語命令を生成します。このコミットでは、`append`のコード生成をこのフェーズに移動させ、より低レベルでの最適化を可能にしています。

## 技術的詳細

このコミットの核心は、`append`関数のコード生成ロジックを`walk`フェーズから`gen`フェーズへ移行し、より低レベルで詳細な最適化を適用できるようにした点にあります。

以前の`walk`フェーズでの擬似コード展開では、`x = append(x, v)`のような操作は、以下のようなGoの概念的なコードに変換されていました。

```go
t := x
if len(t)+1 > cap(t) {
        t = grow(t) // 新しい基底配列が割り当てられる可能性がある
}
t[len(t)] = v
len(t)++
x = t // ここで常にxの基底ポインタ、長さ、容量が更新される
```

このコードでは、`x = t`という最後の代入が常に実行されます。`t`が`grow`によって新しい基底配列を指すようになった場合、`x`も新しい配列を指すように更新される必要があります。しかし、`grow`が呼び出されなかった場合（つまり、既存の容量で十分だった場合）、`t`の基底ポインタは`x`と同じままです。それでも`x = t`という代入は実行され、`x`の基底ポインタが自身に再代入されることになります。

Goのガベージコレクタは、ポインタの書き込み時にライトバリアを挿入します。`x`がポインタを含むスライスヘッダである場合、`x = t`という代入は、基底ポインタの書き込みに対してライトバリアをトリガーする可能性があります。容量が十分な場合の「高速パス」では、基底ポインタは実際には変更されていないにもかかわらず、このライトバリアが実行されるのは無駄です。

このコミットでは、`gen`フェーズで直接機械語命令を生成する際に、このシナリオを特別に処理します。具体的には、`x = append(x, v)`のようにソーススライスとデスティネーションスライスが同じである場合、以下のような最適化されたコードを生成します。

```go
t := x
if len(t)+1 > cap(t) {
        t = grow(t) // 新しい基底配列が割り当てられる
        x = {base(t), len(t)+1, cap(t)} // xの基底ポインタ、長さ、容量を完全に更新
} else {
        len(x)++ // 容量が十分な場合、xの長さのみを更新
}
t[len(t)] = v // 新しい要素を書き込む
```

この最適化のポイントは、`else`ブロック（高速パス）において、`x`の**長さのみ**を更新し、基底ポインタと容量の更新を省略している点です。これにより、基底ポインタの書き込みが不要になり、それに伴うライトバリアの呼び出しも回避されます。これは、C言語で手動でスライスを操作する際に書くような、より効率的なコードに近い形です。

コミットメッセージに示されているベンチマーク結果は、この最適化が`FmtFprintf*`や`GobEncode`、`Template`など、いくつかのベンチマークで顕著なパフォーマンス向上をもたらしていることを示しています。特に`FmtFprintfPrefixedInt`では-7.52%、`Template`では-12.06%の改善が見られます。一方で、`BinaryTree17`や`GobDecode`のようにわずかに遅くなっているベンチマークもありますが、コミットメッセージでは「次のCLで同様の最適化と組み合わせることで、全体的には高速になる」と説明されており、これはスライス関連のさらなる最適化の一部であることが示唆されています。

## コアとなるコードの解説

### `src/cmd/internal/gc/cgen.go` の `cgen_append` 関数

このコミットの最も重要な変更は、`cgen.go`に新しく追加された`cgen_append`関数です。この関数は、`OAPPEND`ノード（`append`組み込み関数呼び出しを表すASTノード）の実際の機械語命令を生成します。

1.  **`needFullUpdate`の判定**:
    ```go
    needFullUpdate := !samesafeexpr(res, n.List.N)
    ```
    ここで、`res`は`append`の結果が代入されるデスティネーションスライス（例: `x`）、`n.List.N`は`append`の最初の引数であるソーススライス（例: `x`）です。`samesafeexpr`は、これら二つの式が同じメモリ位置を参照しているかどうかを安全に判定します。
    *   `needFullUpdate`が`true`の場合（`res`と`n.List.N`が異なる、または安全に同じと判断できない場合）、スライスの基底ポインタ、長さ、容量のすべてを更新する必要があります。これは、`append`が新しいスライスを返す場合や、`append`の結果が別の変数に代入される場合などです。
    *   `needFullUpdate`が`false`の場合（`res`と`n.List.N`が同じであると判断できる場合）、スライスの再割り当てが発生しない限り、基底ポインタと容量は変更されません。この場合、長さのみを更新すれば十分です。

2.  **スライスヘッダの抽出**:
    ソーススライス`n.List.N`から、基底ポインタ（`base`）、長さ（`len`）、容量（`cap`）を一時変数にロードします。

3.  **容量チェックと`growslice`呼び出し**:
    `if len+argc <= cap goto L1`という条件分岐を生成します。ここで`argc`は追加される要素の数です。
    *   容量が不足している場合（`len+argc > cap`）、`growslice`ランタイム関数を呼び出して新しい基底配列を割り当てます。`growslice`は新しい基底ポインタ、長さ、容量を返します。
    *   容量が十分な場合、`growslice`はスキップされ、既存の基底配列が使用されます。

4.  **スライスヘッダの更新**:
    *   `growslice`が呼び出された場合、返された新しい基底ポインタ、長さ、容量を一時変数に格納し、その後`res`（デスティネーションスライス）に書き戻します。この際、`needFullUpdate`が`true`であれば、基底ポインタの書き込み時に`cgen_wb`（ライトバリアを考慮したコード生成）が呼び出されます。
    *   `needFullUpdate`が`false`の場合（高速パス）、`growslice`がスキップされた後、`res`の**長さのみ**が更新されます。基底ポインタと容量は更新されません。これにより、基底ポインタの書き込みとそれに伴うライトバリアが回避されます。

5.  **要素のコピー**:
    最後に、追加される要素をスライスの適切な位置にコピーします。この際、要素がポインタ型であれば、個々の要素の書き込みに対してライトバリアが適用されます。

### `src/cmd/internal/gc/walk.go` の変更

`walk.go`では、`OAPPEND`ノードの処理が変更されました。
*   以前は`walk`フェーズで`append`がGoの擬似コードに展開されていましたが、このコミットにより、`OAS`（代入）の右辺にある`OAPPEND`は、`gen`フェーズの`cgen_append`に処理が委譲されるようになりました。
*   `walkappend`関数のシグネチャが`func walkappend(n *Node, init **NodeList, dst *Node) *Node`に変更され、代入先のノード`dst`を受け取るようになりました。これにより、`walkappend`内で`dst`とソーススライスが同じかどうかを判断し、`gen`フェーズに渡す`OAPPEND`ノードを適切に準備できるようになります。
*   レース検出が有効な場合（`flag_race != 0`）は、以前と同様に`walk`フェーズで完全な擬似コードに展開され、ライトバリアが常に挿入されるようになっています。これは、レース検出の正確性を優先するためです。

### `src/cmd/internal/gc/order.go` の変更

`order.go`では、`OAPPEND`ノードの`orderexpr`処理が変更されました。
*   `lhs == nil || flag_race != 0 || lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N)`という条件が追加されました。これは、`append`の結果が一時変数にコピーされるべきかどうかを決定します。
    *   `lhs`が`nil`（`append`の結果が使用されない）
    *   レース検出が有効
    *   `lhs`が`ONAME`（変数）ではなく、かつ`lhs`とソーススライスが同じでない
    これらの条件のいずれかが満たされる場合、`append`の結果は一時変数にコピーされ、`gen`フェーズでの最適化が適用されにくくなります。これは、`gen`フェーズでの最適化が、ソースとデスティネーションが同じスライスである場合に最も効果を発揮するためです。

## 元コミット内容

```
cmd/compile: use generated temps in bool codegen

Bool codegen was generating a temp for function calls
and other complex expressions, but was not using it.

This was a refactoring bug introduced by CL 7853.
The cmp code used to do (in short):

        l, r := &n1, &n2

It was changed to:

        l, r := nl, nr

But the requisite assignments:

        nl, nr = &n1, &n2

were only introduced on one of two code paths.

Fixes #10654.

Change-Id: Ie8de0b3a333842a048d4308e02911bb10c6915ce
```

## 変更の背景

このコミットは、Goコンパイラのブール値コード生成（`cmd/compile`の`bgenx`関数内）におけるリファクタリングバグを修正するものです。具体的には、関数呼び出しやその他の複雑な式の結果を処理する際に、コンパイラが一時変数（temp）を生成していましたが、その生成された一時変数が実際に利用されないという問題がありました。

このバグは、以前の変更セット（CL 7853）によるリファクタリングによって導入されました。元の比較コードでは、左右のオペランドを一時変数`n1`と`n2`のアドレスとして直接参照する`l, r := &n1, &n2`のような形式で処理されていました。しかし、リファクタリングによって`l, r := nl, nr`という形式に変更された際、`nl`と`nr`が新しく生成された一時変数`n1`と`n2`のアドレスを指すように更新する必要な代入（`nl, nr = &n1, &n2`）が、二つのコードパスのうち一方にしか導入されませんでした。この欠落が原因で、コンパイラは一時変数に計算された結果を正しく利用できず、誤ったコードを生成する可能性がありました。

この問題は、Go issue #10654として報告され、このコミットによって修正されました。

## 前提知識の解説

このコミットの理解には、以下のGoコンパイラに関する前提知識が役立ちます。

*   **Goコンパイラのコード生成 (`cmd/compile`):**
    Go言語のソースコードは、`cmd/compile`によって中間表現（AST: Abstract Syntax Tree）に変換され、その後、特定のアーキテクチャ向けの機械語コードに変換されます。このプロセスには、型チェック、最適化、レジスタ割り当て、そして最終的なアセンブリコードの生成が含まれます。`src/cmd/compile/internal/gc`ディレクトリは、このコンパイラのバックエンド部分、特にコード生成と最適化のロジックを担っています。

*   **ブール値のコード生成 (Boolean Codegen):**
    `if`文、`for`ループの条件、論理演算子（`&&`, `||`, `==`, `!=`など）といったブール値を扱う式は、コンパイラによって特定の機械語命令に変換されます。これには、比較命令（`CMP`）、条件分岐命令（`JMP`、`JE`、`JNE`など）が使われます。複雑なブール式の場合、その評価結果を一時的に保持するための仕組みが必要になります。

*   **一時変数 (Temporary Variables/Temps):**
    コンパイラは、複雑な式を評価する際の中間結果を格納するために、内部的に「一時変数」を生成します。これらの一時変数は、ソースコードには直接現れませんが、コンパイラが効率的な機械語を生成するために不可欠です。一時変数は、CPUのレジスタに割り当てられるか、スタックメモリに格納されます。

*   **`Node`構造体:**
    Goコンパイラ内部では、ソースコードの各要素（変数、定数、演算子、関数呼び出しなど）が`Node`という抽象構文木（AST）のノードとして表現されます。`Node`構造体は、その要素の型、値、位置、およびその他のコンパイラが処理に必要なメタデータを含んでいます。

*   **`Cgen`関数:**
    `Cgen`（Code Generation）関数は、Goコンパイラの主要なコード生成ルーチンの一つです。ASTの`Node`を受け取り、そのノードに対応する機械語命令を生成し、指定された出力先（通常は別の一時`Node`）に結果を格納するコードを出力します。

*   **`Regalloc`と`Regfree`:**
    `Regalloc`（Register Allocate）は、一時変数を格納するためのレジスタまたはメモリ位置を割り当てるコンパイラ内部の関数です。`Regfree`（Register Free）は、割り当てられたリソースを解放します。これらの関数は、効率的なレジスタ利用とリソース管理のために重要です。

## 技術的詳細

このコミットが修正したバグは、`src/cmd/compile/internal/gc/cgen.go`ファイル内の`bgenx`関数に存在していました。`bgenx`関数は、ブール値を生成するためのコードを担当しています。

バグの核心は、複雑な式（特に`nl`や`nr`で表されるオペランドが関数呼び出しなどである場合）の評価結果を一時的に保持するために`Regalloc`と`Cgen`を使って`n1`や`n2`という`Node`が生成されるものの、その結果が後続の処理で正しく参照されない点にありました。

具体的には、`bgenx`関数内で左右のオペランド`nl`と`nr`を処理する際、以下のようなコードパスがありました。

1.  `nl`の評価結果を格納するための一時`Node` `n1`を`Regalloc`で確保。
2.  `Cgen(nl, &n1)`を呼び出し、`nl`の式を評価し、その結果を`n1`に格納するコードを生成。
3.  同様に、`nr`の評価結果を格納するための一時`Node` `n2`を`Regalloc`で確保。
4.  `Cgen(nr, &n2)`を呼び出し、`nr`の式を評価し、その結果を`n2`に格納するコードを生成。

問題は、`Cgen(nl, &n1)`が`n1`に結果を書き込むコードを生成するだけで、`nl`自体が`n1`を指すように更新されていなかったことです。つまり、`nl`は依然として元の複雑な式を表す`Node`を指したままであり、`n1`に格納された評価結果が後続の比較処理で利用されませんでした。

この状況は、CL 7853という以前のリファクタリングで導入されました。そのリファクタリングでは、比較コードが`l, r := &n1, &n2`から`l, r := nl, nr`に変更されました。この変更に伴い、`nl`と`nr`がそれぞれ`n1`と`n2`のアドレスを指すように`nl, nr = &n1, &n2`という代入が必要でしたが、この代入が`bgenx`関数内の特定のコードパスでのみ行われ、別のパスでは欠落していました。

このコミットでは、この欠落していた代入を修正しました。`Cgen(nl, &n1)`の直後に`nl = &n1`を、`Cgen(nr, &n2)`の直後に`nr = &n2`を追加することで、`nl`と`nr`がそれぞれ新しく生成された一時変数`n1`と`n2`を正しく参照するようになり、コンパイラがブール式の評価結果を正確に利用できるようになりました。

これにより、`if (s == "this") != (s == "that")`のような複雑なブール式が正しくコンパイルされ、実行時に期待通りの動作をするようになりました。

## コアとなるコードの解説

`bgenx`関数は、ブール式を評価し、その結果に基づいて条件分岐を行うためのコードを生成します。

変更前のコードでは、`nl`（左オペランド）と`nr`（右オペランド）が複雑な式である場合、その評価結果を一時的に保持するために`n1`と`n2`という`Node`が用意され、`Regalloc`でレジスタが割り当てられ、`Cgen`でその式を評価して`n1`や`n2`に結果を格納するコードが生成されていました。

しかし、`Cgen(nl, &n1)`が実行された後も、`nl`という変数は元の複雑な式を表す`Node`を指したままでした。そのため、後続の比較処理では、`n1`に格納された実際の評価結果ではなく、古い`nl`が参照されてしまい、意図しない動作を引き起こしていました。

追加された`nl = &n1`と`nr = &n2`の行は、この問題を解決します。
*   `nl = &n1`: `nl`が、新しく評価され、結果が`n1`に格納された一時変数`Node`のアドレスを指すように更新します。
*   `nr = &n2`: 同様に、`nr`が、新しく評価され、結果が`n2`に格納された一時変数`Node`のアドレスを指すように更新します。

これにより、`bgenx`関数内の後続のコードは、`nl`と`nr`を通じて、正しく評価された一時変数の結果を参照できるようになり、ブール値のコード生成が期待通りに機能するようになりました。

追加されたテストケース`test/fixedbugs/issue10654.go`は、`if (s == "this") != (s == "that")`という形式のブール式を使用しています。これは、複数の比較演算と論理演算が組み合わさった複雑な式であり、このコミットで修正されたバグが顕在化しやすいパターンです。このテストケースがコンパイルエラーなく、かつ正しく動作することで、修正が有効であることが確認されます。

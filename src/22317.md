# [インデックス 22317] ファイルの概要

このコミットは、Goコンパイラのx86アーキテクチャ向けアセンブラバックエンドにおける重要な変更を導入しています。具体的には、32ビットx86 (i386) のコード生成ロジックを、既存の64ビットx86 (amd64) を担当していた `cmd/internal/obj/x86` パッケージに統合し、`cmd/internal/obj/i386` パッケージを削除しています。これにより、コードベースの重複が解消され、保守性が向上します。

さらに、`PINSRQ` および `CMPSD` といった特定の命令のエンコーディングロジックがクリーンアップされ、引数の扱いがより明示的になりました。また、古いアセンブラ `old6a` における `CMPSD` 命令の引数順序に関するバグが修正され、メモリオペランドを正しく扱えるようになりました。この変更は、既存のコードとのビット単位の互換性を維持しつつ、アセンブラの正確性と柔軟性を高めるものです。

## 変更の背景

このコミットの背景には、主に以下の3つの目的があります。

1.  **コードベースの統合と簡素化**: Goコンパイラは、異なるアーキテクチャ（x86、ARMなど）やビット幅（32ビット、64ビット）に対応するために、それぞれのアセンブラバックエンドを持っています。以前は、32ビットx86 (i386) と64ビットx86 (amd64) のアセンブラコード生成ロジックが `cmd/internal/obj/i386` と `cmd/internal/obj/x86` に分かれていました。しかし、x86アーキテクチャは32ビットと64ビットで多くの共通点があり、コードの重複や保守の複雑さが増していました。このコミットは、これらを `cmd/internal/obj/x86` に統合することで、コードベースを簡素化し、将来的なメンテナンスを容易にすることを目指しています。

2.  **命令エンコーディングの正確性の向上**: `PINSRQ` や `CMPSD` といった特定のx86命令は、複数のオペランドを取ります。これらの命令のエンコーディングにおいて、一部の引数が「未使用のスロット」に不適切に詰め込まれるという問題がありました。これは、アセンブラが生成する機械語の正確性や、命令の意図するセマンティクスを曖昧にする可能性がありました。このコミットは、これらの命令のエンコーディングをクリーンアップし、引数をより明示的に扱うことで、正確性と可読性を向上させます。

3.  **アセンブラのバグ修正と機能改善**: 古い32ビットアセンブラ `old6a` には、`CMPSD` 命令の引数順序に関するバグが存在しました。Intelのドキュメントでは `mem,reg` の形式が許容されるにもかかわらず、アセンブラの内部文法定義が `reg,mem` と誤って宣言されていたため、`mem,reg` 形式の命令が正しくエンコードされませんでした。結果として、`reg,reg` 形式しか機能していませんでした。このコミットは、このバグを修正し、`CMPSD` が `mem,reg` 形式のオペランドを正しく受け入れ、エンコードできるようにすることで、アセンブラの柔軟性と機能性を向上させます。既存のコードは `reg,reg` 形式を使用していたため影響を受けませんが、この修正により、より多様な命令形式が利用可能になります。

これらの変更は、Goコンパイラのバックエンドの堅牢性を高め、将来的なx86アーキテクチャの進化に対応するための基盤を強化することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

1.  **Goコンパイラの構造**: Goコンパイラは、ソースコードを解析し、中間表現を生成し、最終的にターゲットアーキテクチャの機械語に変換します。この変換プロセスの後半部分、特に機械語の生成を担当するのが「アセンブラバックエンド」です。Goのツールチェーンでは、各アーキテクチャ（例: x86、ARM）とビット幅（32ビット、64ビット）に対応するアセンブラが `cmd/internal/obj` ディレクトリ以下に存在します。

2.  **x86アーキテクチャ**: IntelおよびAMDが開発した命令セットアーキテクチャです。32ビット版 (IA-32, i386) と64ビット版 (x86-64, AMD64) があり、それぞれ異なるレジスタセットやアドレッシングモードを持ちますが、多くの命令は共通しています。
    *   **レジスタ**: `AX`, `BX`, `CX`, `DX` などの汎用レジスタや、`SP` (スタックポインタ), `BP` (ベースポインタ), `SI` (ソースインデックス), `DI` (デスティネーションインデックス) などがあります。64ビットモードでは `RAX`, `RBX` など、`R8` から `R15` までの追加レジスタも導入されます。
    *   **命令エンコーディング**: x86命令は、オペコード、ModR/Mバイト、SIBバイト、ディスプレースメント、イミディエイトなど、複数のバイトで構成されます。これらのバイトの組み合わせによって、命令の種類、オペランドの指定方法、アドレッシングモードなどが決定されます。
    *   **REXプレフィックス**: 64ビットモードで導入されたプレフィックスで、新しいレジスタ (`R8`-`R15`) の指定や、64ビットオペランドサイズの指定などに使用されます。
    *   **ModR/MバイトとSIBバイト**: メモリオペランドやレジスタオペランドの指定に使用されるバイトです。ModR/Mバイトは、オペランドがレジスタかメモリか、どのレジスタを使用するか、ディスプレースメントの有無などを指定します。SIB (Scale-Index-Base) バイトは、ベースレジスタ、インデックスレジスタ、スケールファクタ（配列の要素サイズなど）を組み合わせて複雑なメモリアドレッシングを行う際に使用されます。

3.  **アセンブラの役割**: アセンブラは、人間が記述したアセンブリ言語のニーモニック（例: `MOV`, `ADD`）を、CPUが直接実行できる機械語（バイナリコード）に変換するプログラムです。この変換プロセスには、命令のオペコードの選択、オペランドのエンコーディング、アドレッシングモードの解決などが含まれます。

4.  **Goの `cmd/internal/obj` パッケージ**: Goコンパイラのバックエンドの一部であり、アセンブリ命令の抽象的な表現（`obj.Prog` 構造体など）を、ターゲットアーキテクチャの具体的な機械語に変換するロジックを含んでいます。各アーキテクチャ（例: `x86`, `arm`）に対応するサブパッケージがあり、それぞれがそのアーキテクチャ固有の命令エンコーディングルールを実装しています。

5.  **`PINSRQ` 命令**: SSE4.1命令セットの一部で、指定されたレジスタまたはメモリから64ビットの値をXMMレジスタの指定された位置に挿入する命令です。通常、3つのオペランド（ソース、デスティネーション、挿入位置を示すイミディエイト）を取ります。

6.  **`CMPSD` 命令**: SSE2命令セットの一部で、2つの浮動小数点値を比較し、結果をマスクとしてデスティネーションレジスタに格納する命令です。通常、2つのオペランド（ソース、デスティネーション）と、比較条件を示すイミディエイトオペランドを取ります。

7.  **TLS (Thread Local Storage)**: 各スレッドが独自のデータを持つためのメカニズムです。OSやアーキテクチャによってTLSのアクセス方法が異なります。x86では、`FS` または `GS` セグメントレジスタを介してTLSベースアドレスにアクセスすることが一般的です。

これらの知識を持つことで、コミットがGoコンパイラの内部でどのように機能し、x86アセンブラの動作にどのような影響を与えるかをより深く理解できます。

## 技術的詳細

このコミットは、Goコンパイラのx86アセンブラバックエンドに複数の重要な技術的変更を加えています。

1.  **i386とx86の統合**:
    *   以前は、32ビットx86 (i386) のアセンブラロジックは `cmd/internal/obj/i386` に、64ビットx86 (amd64) のロジックは `cmd/internal/obj/x86` に存在していました。このコミットにより、`cmd/internal/obj/i386` が削除され、その機能が `cmd/internal/obj/x86` に吸収されました。
    *   `cmd/internal/obj/x86` 内のコードは、`p.Mode` フィールド（`obj.Prog` 構造体に追加された新しいフィールド）を使用して、現在のコード生成が32ビットモード (`p.Mode == 32`) なのか64ビットモード (`p.Mode == 64`) なのかを判断するようになりました。これにより、単一のコードベースで両方のビット幅に対応できるようになります。
    *   `src/cmd/asm/internal/arch/arch.go` の `Set` 関数が変更され、`"386"` および `"amd64"` アーキテクチャの選択が `archX86` 関数に統合されました。`archX86` は `obj.LinkArch` ポインタを受け取り、32ビットと64ビットのリンカアーキテクチャを適切に設定します。
    *   `src/cmd/8g` 以下のGoコンパイラのフロントエンドファイル群（`cgen.go`, `cgen64.go`, `galign.go`, `gg.go`, `ggen.go`, `gsubr.go`, `peep.go`, `prog.go`, `reg.go`）では、`cmd/internal/obj/i386` からのインポートが `cmd/internal/obj/x86` に変更されました。これは、アセンブラバックエンドの切り替えを反映しています。

2.  **`PINSRQ`, `CMPSD` 命令のエンコーディング修正**:
    *   これらの命令は、通常、ソースオペランド、デスティネーションオペランド、そしてイミディエイト値（例えば、`PINSRQ` の挿入位置や `CMPSD` の比較条件）の3つの引数を取ります。
    *   以前の実装では、この3番目のイミディエイト引数が、`obj.Prog` 構造体の `From3` フィールドではなく、別の引数の「未使用のスロット」に不適切に詰め込まれていました。
    *   このコミットでは、`src/cmd/internal/obj/x86/asm6.go` の `doasm` 関数内で、`PINSRQ` や `CMPSD` などの命令に対して、`p.From3` フィールドを明示的に使用するようにロジックが変更されました。具体的には、`p.From3.Type == obj.TYPE_NONE` の場合に、`p.From` や `p.To` の情報を `p.From3` に移動させ、`p.From` や `p.To` をイミディエイト値用に設定し直す処理が追加されました。これにより、命令のエンコーディングがより正確かつ意図通りに行われるようになります。

3.  **`old6a` の `CMPSD` 引数順序バグ修正**:
    *   `old6a` は古い32ビットアセンブラであり、`CMPSD` 命令の引数順序に関する文法定義に誤りがありました。Intelのドキュメントでは `mem,reg` (メモリからレジスタへの比較) が許容されるにもかかわらず、`old6a` は `reg,mem` (レジスタからメモリへの比較) のみを正しく扱っていました。
    *   コミットメッセージによると、このバグにより `mem,reg` を試みたコードは `liblink` によって拒否され、結果として `reg,reg` の形式しか機能していませんでした。
    *   このコミットでは、`src/cmd/old6a/a.y` (アセンブラの文法定義ファイル) および `src/cmd/old6a/y.go` (生成されたパーサーコード) が修正され、`CMPSD` が `mem,reg` 形式の引数を正しく認識し、エンコードできるようになりました。
    *   興味深いことに、コミットメッセージでは「エンコーディングテーブルが引数順序を反転させていた」と述べられており、これはIntelのドキュメントとは逆の比較になっていたことを示唆しています。しかし、既存のコードがこの「反転した比較」を期待して書かれているため、引数順序を完全にIntelのドキュメント通りに「入れ替える」ことはせず、代わりに `mem,reg` オペランドを正しく受け入れるように修正することで、既存のコードへの影響を最小限に抑えつつ、機能性を向上させています。

4.  **TLSアクセスロジックの改善**:
    *   `src/cmd/internal/obj/x86/obj6.go` の `canuselocaltls` 関数が、32ビットモードでのTLSアクセスに関するロジックを更新しました。特定のOS (Linux, NaCl, Plan9, Windows) では、32ビットモードで直接TLSを使用できないため、`false` を返すようになりました。
    *   `src/cmd/internal/obj/x86/asm6.go` の `doasm` 関数内のTLSロード (`Movtab` の `code == 7`) の処理が、32ビットモードと64ビットモードで異なるOS固有のTLSベースアドレス取得方法に対応するように拡張されました。例えば、Linux/NaClでは `0(GS)`、Plan9では `_privates` シンボル、Windowsでは `0x14(FS)` からTLSベースアドレスを取得するロジックが追加されています。

5.  **ビット単位の互換性**:
    *   コミットメッセージで「Bit-for-bit compatibility checked against tree without this CL.」と明記されているように、この変更は、修正前のGoコンパイラが生成する機械語と、修正後のGoコンパイラが生成する機械語が、可能な限りビット単位で同一になるように細心の注意を払って行われました。これは、Goの安定性と予測可能性を維持するために非常に重要です。

これらの変更は、Goコンパイラのx86バックエンドをより堅牢で、保守しやすく、正確なものにするための包括的な取り組みの一環です。

## コアとなるコードの解説

ここでは、上記の「コアとなるコードの変更箇所」で挙げた主要な変更点について、より詳細な技術的解説を行います。

### 1. `src/cmd/internal/obj/x86/asm6.go` の変更

このファイルは、x86アセンブリ命令を機械語にエンコードする中心的なロジックを含んでいます。

#### `Movtab` と `ymovq` の変更

`Movtab` は、特定の命令（例: `AMOVQ`）のオペランドの組み合わせと、それに対応するエンコーディングルールを定義する構造体です。`ymovq` は `AMOVQ` 命令の `Movtab` エントリの配列です。

変更前は、`AMOVQ` のエンコーディングは主に64ビットモードを想定していましたが、このコミットでは32ビットモードのサポートが追加され、より多くのオペランドタイプとプレフィックスが導入されました。

```go
// 変更前 (一部抜粋)
var ymovq = []ytab{
	{Yrl, Ynone, Yml, Zr_m, 1},       // 0x89
	{Yml, Ynone, Yrl, Zm_r, 1},       // 0x8b
	// ...
}

// 変更後 (一部抜粋)
var ymovq = []ytab{
	// valid in 32-bit mode
	{Ym, Ynone, Ymr, Zm_r_xm_nr, 1},  // 0x6f MMX MOVQ (shorter encoding)
	{Ymr, Ynone, Ym, Zr_m_xm_nr, 1},  // 0x7f MMX MOVQ
	{Yxr, Ynone, Ymr, Zm_r_xm_nr, 2}, // Pf2, 0xd6 MOVDQ2Q
	{Yxm, Ynone, Yxr, Zm_r_xm_nr, 2}, // Pf3, 0x7e MOVQ xmm1/m64 -> xmm2
	{Yxr, Ynone, Yxm, Zr_m_xm_nr, 2}, // Pe, 0xd6 MOVQ xmm1 -> xmm2/m64

	// valid only in 64-bit mode, usually with 64-bit prefix
	{Yrl, Ynone, Yml, Zr_m, 1},      // 0x89
	{Yml, Ynone, Yrl, Zm_r, 1},      // 0x8b
	// ...
}
```

この変更により、`AMOVQ` がMMX/SSE命令（`Ym`, `Ymr`, `Yxr`, `Yxm` など）を伴う場合や、異なるプレフィックス（`Pf2`, `Pf3`, `Pe`）を持つ場合のエンコーディングが明確に定義されました。特に、32ビットモードと64ビットモードで異なるエンコーディングが適用されることが示されています。

#### `doasm` 関数の変更

`doasm` 関数は、`obj.Prog` 構造体で表現されたアセンブリ命令を受け取り、実際の機械語バイト列を生成します。

**`p.From3` の扱いと `PINSRQ`, `CMPSD` のエンコーディング修正**:
`PINSRQ` や `CMPSD` のような命令は、3つのオペランドを持つことがあります。Goのアセンブラでは、これらを `p.From`, `p.To`, `p.From3` で表現します。以前は、`p.From3` が適切に扱われず、エンコーディングが複雑になっていました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内)
// TODO(rsc): This special case is for PINSRQ etc, CMPSD etc.
// Change encoding generated by assemblers and compilers (if any) and remove.
switch p.As {
case AIMUL3Q, APEXTRW, APINSRW, APINSRD, APINSRQ, APSHUFHW, APSHUFL, APSHUFW, ASHUFPD, ASHUFPS, AAESKEYGENASSIST, APSHUFD, APCLMULQDQ:
	if p.From3.Type == obj.TYPE_NONE {
		p.From3 = p.From
		p.From = obj.Addr{}
		p.From.Type = obj.TYPE_CONST
		p.From.Offset = p.To.Offset
		p.To.Offset = 0
	}
case ACMPSD, ACMPSS, ACMPPS, ACMPPD:
	if p.From3.Type == obj.TYPE_NONE {
		p.From3 = p.To
		p.To = obj.Addr{}
		p.To.Type = obj.TYPE_CONST
		p.To.Offset = p.From3.Offset
		p.From3.Offset = 0
	}
}
```
このコードは、`PINSRQ` や `CMPSD` などの命令が `p.From3` を持たない場合（つまり、アセンブラが古い形式で引数を渡している場合）に、`p.From` や `p.To` の内容を `p.From3` に移動させ、`p.From` や `p.To` をイミディエイト値用に再設定します。これにより、エンコーディングロジックが `p.From3` を常に正しい3番目のオペランドとして扱えるようになります。コメントにあるように、将来的にはアセンブラやコンパイラが最初から正しい形式で `p.From3` を設定するようになれば、この特殊ケースは不要になります。

**`ytab` 検索ロジックの変更**:
命令のエンコーディングテーブル (`optab`) を検索する際に、`p.From`, `p.To` に加えて `p.From3` の型も考慮するようになりました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内)
// 変更前:
// if ycover[ft+int(yt.from)] != 0 && ycover[tt+int(yt.to)] != 0 {
// 変更後:
if ycover[ft+int(yt.from)] != 0 && ycover[f3t+int(yt.from3)] != 0 && ycover[tt+int(yt.to)] != 0 {
```
`f3t` は `p.F3t` (oclass(p.From3) の結果) を表し、`yt.from3` は `ytab` エントリの3番目のオペランドの型を表します。これにより、命令のエンコーディングがより厳密に、かつ正確に行われるようになります。

**TLSベースアドレスのロードロジックの拡張**:
`doasm` 関数内の `Movtab` の `code == 7` (TLSベースアドレスのロード) の処理が、32ビットモードと64ビットモードで異なるOS固有のTLSアクセス方法に対応するように拡張されました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内, Movtab code == 7 のケース)
				case 7: /* mov tls, r */
					if p.Mode == 64 && p.As != AMOVQ || p.Mode == 32 && p.As != AMOVL {
						ctxt.Diag("invalid load of TLS: %v", p)
					}

					if p.Mode == 32 {
						switch ctxt.Headtype {
						default:
							log.Fatalf("unknown TLS base location for %s", obj.Headstr(ctxt.Headtype))

						case obj.Hlinux,
							obj.Hnacl:
							// ELF TLS base is 0(GS).
							// ... (GSセグメントプレフィックス 0x65 と MOV命令 0x8B を出力)

						case obj.Hplan9:
							// ... (_privates シンボルからロード)

						case obj.Hwindows:
							// Windows TLS base is always 0x14(FS).
							// ... (FSセグメントプレフィックス 0x64 と MOV命令 0x8B を出力)
						}
						break
					}
					// ... (64ビットモードのTLSロードロジック)
```
このコードは、現在のモード (`p.Mode`) とOS (`ctxt.Headtype`) に応じて、TLSベースアドレスをロードするための適切な機械語シーケンスを生成します。例えば、32ビットLinux/NaClでは `GS` セグメントレジスタを介して `0(GS)` からロードし、Windowsでは `FS` セグメントレジスタを介して `0x14(FS)` からロードします。これにより、異なる環境でのTLSアクセスが正しく行われるようになります。

### 2. `src/cmd/internal/obj/x86/obj6.go` の変更

このファイルは、Goコンパイラのリンカがアセンブリ命令を処理する前の前処理ロジックを含んでいます。

#### `progedit` 関数の変更

`progedit` 関数は、各 `obj.Prog` (アセンブリ命令) をリンカが処理する前に修正します。

**コード生成モードの管理**:
`ctxt.Mode` と `p.Mode` を導入し、現在のコード生成が32ビットか64ビットかを追跡するようになりました。`AMODE` 命令は、このモードを設定するために使用されます。

```go
// src/cmd/internal/obj/x86/obj6.go (progedit関数内)
	// Maintain information about code generation mode.
	if ctxt.Mode == 0 {
		ctxt.Mode = ctxt.Arch.Regsize * 8
	}
	p.Mode = int8(ctxt.Mode)

	switch p.As {
	case AMODE:
		if p.From.Type == obj.TYPE_CONST || (p.From.Type == obj.TYPE_MEM && p.From.Reg == REG_NONE) {
			switch int(p.From.Offset) {
			case 16, 32, 64:
				ctxt.Mode = int(p.From.Offset)
			}
		}
		obj.Nopout(p) // AMODE命令自体は機械語を生成しない
	}
```
`ctxt.Mode` はリンカ全体のモードを、`p.Mode` は個々の命令のモードを示します。これにより、リンカは命令ごとに適切なエンコーディングルールを適用できるようになります。

**スタックフレーム処理の調整**:
`preprocess` 関数内のスタックフレーム処理 (`autoffset`) が、64ビットモードでのみフレームポインタの保存を行うように変更されました。

```go
// src/cmd/internal/obj/x86/obj6.go (preprocess関数内)
// 変更前:
// if obj.Framepointer_enabled != 0 && autoffset > 0 {
// 変更後:
if p.Mode == 64 && obj.Framepointer_enabled != 0 && autoffset > 0 {
```
これは、32ビットモードではフレームポインタの保存が異なる方法で行われるか、あるいは不要であることを示唆しています。

### 3. `src/cmd/asm/internal/arch/arch.go` の変更

このファイルは、Goアセンブラがサポートするアーキテクチャを定義し、それぞれのアーキテクチャ固有の情報を設定します。

#### `archX86` 関数の導入と統合

以前は `arch386` と `archAmd64` という別々の関数がありましたが、これらが `archX86` に統合されました。

```go
// src/cmd/asm/internal/arch/arch.go (Set関数内)
	case "386":
		return archX86(&x86.Link386)
	case "amd64":
		return archX86(&x86.Linkamd64)
	case "amd64p32":
		return archX86(&x86.Linkamd64p32)

// src/cmd/asm/internal/arch/arch.go (archX86関数)
func archX86(linkArch *obj.LinkArch) *Arch {
	register := make(map[string]int16)
	// ... (レジスタと命令のマップを初期化)
	return &Arch{
		LinkArch:       linkArch,
		Instructions:   instructions,
		Register:       register,
		RegisterPrefix: nil,
		RegisterNumber: nilRegisterNumber,
		IsJump:         jumpX86,
	}
}
```
`archX86` 関数は `obj.LinkArch` ポインタを受け取ることで、32ビット (`x86.Link386`) と64ビット (`x86.Linkamd64`, `x86.Linkamd64p32`) のリンカアーキテクチャを共通のロジックで設定できるようになりました。これにより、x86アーキテクチャの共通部分を再利用し、コードの重複を減らすことができます。

### 4. `src/cmd/old6a/a.y` および `src/cmd/old6a/y.go` の変更

これらのファイルは、古い32ビットアセンブラ `old6a` の文法定義と、それから生成されるパーサーコードです。

#### `CMPSD` 命令の文法修正

`a.y` ファイルはYacc/Bison形式の文法定義ファイルであり、アセンブリ命令の構文ルールを定義します。

```
// src/cmd/old6a/a.y (変更箇所の一部)
// 変更前:
// CMPSD	reg,reg
// 変更後:
// CMPSD	mem,reg
// CMPSD	reg,reg
```
この変更により、`CMPSD` 命令がメモリオペランドをソースとして、レジスタオペランドをデスティネーションとして取ることができるようになりました。以前は `reg,reg` の形式しか文法的に許容されていなかったため、`mem,reg` 形式のアセンブリコードはコンパイルエラーになっていました。この修正により、Intelの命令セットリファレンスに準拠した `CMPSD` の使用が可能になります。

これらのコアとなるコードの変更は、Goコンパイラのx86バックエンドをよりモジュール化し、32ビットと64ビットのコード生成を統合し、特定の命令のエンコーディングの正確性を向上させ、古いアセンブラのバグを修正するという、このコミットの主要な目的を達成しています。

## 変更の背景

このコミットの背景には、主に以下の3つの目的があります。

1.  **コードベースの統合と簡素化**: Goコンパイラは、異なるアーキテクチャ（x86、ARMなど）やビット幅（32ビット、64ビット）に対応するために、それぞれのアセンブラバックエンドを持っています。以前は、32ビットx86 (i386) と64ビットx86 (amd64) のアセンブラコード生成ロジックが `cmd/internal/obj/i386` と `cmd/internal/obj/x86` に分かれていました。しかし、x86アーキテクチャは32ビットと64ビットで多くの共通点があり、コードの重複や保守の複雑さが増していました。このコミットは、これらを `cmd/internal/obj/x86` に統合することで、コードベースを簡素化し、将来的なメンテナンスを容易にすることを目指しています。

2.  **命令エンコーディングの正確性の向上**: `PINSRQ` や `CMPSD` といった特定のx86命令は、複数のオペランドを取ります。これらの命令のエンコーディングにおいて、一部の引数が「未使用のスロット」に不適切に詰め込まれるという問題がありました。これは、アセンブラが生成する機械語の正確性や、命令の意図するセマンティクスを曖昧にする可能性がありました。このコミットは、これらの命令のエンコーディングをクリーンアップし、引数をより明示的に扱うことで、正確性と可読性を向上させます。

3.  **アセンブラのバグ修正と機能改善**: 古い32ビットアセンブラ `old6a` には、`CMPSD` 命令の引数順序に関するバグが存在しました。Intelのドキュメントでは `mem,reg` の形式が許容されるにもかかわらず、アセンブラの内部文法定義が `reg,mem` と誤って宣言されていたため、`mem,reg` 形式の命令が正しくエンコードされませんでした。結果として、`reg,reg` 形式しか機能していませんでした。このコミットは、このバグを修正し、`CMPSD` が `mem,reg` 形式のオペランドを正しく受け入れ、エンコードできるようにすることで、アセンブラの柔軟性と機能性を向上させます。既存のコードは `reg,reg` 形式を使用していたため影響を受けませんが、この修正により、より多様な命令形式が利用可能になります。

これらの変更は、Goコンパイラのバックエンドの堅牢性を高め、将来的なx86アーキテクチャの進化に対応するための基盤を強化することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

1.  **Goコンパイラの構造**: Goコンパイラは、ソースコードを解析し、中間表現を生成し、最終的にターゲットアーキテクチャの機械語に変換します。この変換プロセスの後半部分、特に機械語の生成を担当するのが「アセンブラバックエンド」です。Goのツールチェーンでは、各アーキテクチャ（例: x86、ARM）とビット幅（32ビット、64ビット）に対応するアセンブラが `cmd/internal/obj` ディレクトリ以下に存在します。

2.  **x86アーキテクチャ**: IntelおよびAMDが開発した命令セットアーキテクチャです。32ビット版 (IA-32, i386) と64ビット版 (x86-64, AMD64) があり、それぞれ異なるレジスタセットやアドレッシングモードを持ちますが、多くの命令は共通しています。
    *   **レジスタ**: `AX`, `BX`, `CX`, `DX` などの汎用レジスタや、`SP` (スタックポインタ), `BP` (ベースポインタ), `SI` (ソースインデックス), `DI` (デスティネーションインデックス) などがあります。64ビットモードでは `RAX`, `RBX` など、`R8` から `R15` までの追加レジスタも導入されます。
    *   **命令エンコーディング**: x86命令は、オペコード、ModR/Mバイト、SIBバイト、ディスプレースメント、イミディエイトなど、複数のバイトで構成されます。これらのバイトの組み合わせによって、命令の種類、オペランドの指定方法、アドレッシングモードなどが決定されます。
    *   **REXプレフィックス**: 64ビットモードで導入されたプレフィックスで、新しいレジスタ (`R8`-`R15`) の指定や、64ビットオペランドサイズの指定などに使用されます。
    *   **ModR/MバイトとSIBバイト**: メモリオペランドやレジスタオペランドの指定に使用されるバイトです。ModR/Mバイトは、オペランドがレジスタかメモリか、どのレジスタを使用するか、ディスプレースメントの有無などを指定します。SIB (Scale-Index-Base) バイトは、ベースレジスタ、インデックスレジスタ、スケールファクタ（配列の要素サイズなど）を組み合わせて複雑なメモリアドレッシングを行う際に使用されます。

3.  **アセンブラの役割**: アセンブラは、人間が記述したアセンブリ言語のニーモニック（例: `MOV`, `ADD`）を、CPUが直接実行できる機械語（バイナリコード）に変換するプログラムです。この変換プロセスには、命令のオペコードの選択、オペランドのエンコーディング、アドレッシングモードの解決などが含まれます。

4.  **Goの `cmd/internal/obj` パッケージ**: Goコンパイラのバックエンドの一部であり、アセンブリ命令の抽象的な表現（`obj.Prog` 構造体など）を、ターゲットアーキテクチャの具体的な機械語に変換するロジックを含んでいます。各アーキテクチャ（例: `x86`, `arm`）に対応するサブパッケージがあり、それぞれがそのアーキテクチャ固有の命令エンコーディングルールを実装しています。

5.  **`PINSRQ` 命令**: SSE4.1命令セットの一部で、指定されたレジスタまたはメモリから64ビットの値をXMMレジスタの指定された位置に挿入する命令です。通常、3つのオペランド（ソース、デスティネーション、挿入位置を示すイミディエイト）を取ります。

6.  **`CMPSD` 命令**: SSE2命令セットの一部で、2つの浮動小数点値を比較し、結果をマスクとしてデスティネーションレジスタに格納する命令です。通常、2つのオペランド（ソース、デスティネーション）と、比較条件を示すイミディエイトオペランドを取ります。

7.  **TLS (Thread Local Storage)**: 各スレッドが独自のデータを持つためのメカニズムです。OSやアーキテクチャによってTLSのアクセス方法が異なります。x86では、`FS` または `GS` セグメントレジスタを介してTLSベースアドレスにアクセスすることが一般的です。

これらの知識を持つことで、コミットがGoコンパイラの内部でどのように機能し、x86アセンブラの動作にどのような影響を与えるかをより深く理解できます。

## 技術的詳細

このコミットは、Goコンパイラのx86アセンブラバックエンドに複数の重要な技術的変更を加えています。

1.  **i386とx86の統合**:
    *   以前は、32ビットx86 (i386) のアセンブラロジックは `cmd/internal/obj/i386` に、64ビットx86 (amd64) のロジックは `cmd/internal/obj/x86` に存在していました。このコミットにより、`cmd/internal/obj/i386` が削除され、その機能が `cmd/internal/obj/x86` に吸収されました。
    *   `cmd/internal/obj/x86` 内のコードは、`p.Mode` フィールド（`obj.Prog` 構造体に追加された新しいフィールド）を使用して、現在のコード生成が32ビットモード (`p.Mode == 32`) なのか64ビットモード (`p.Mode == 64`) なのかを判断するようになりました。これにより、単一のコードベースで両方のビット幅に対応できるようになります。
    *   `src/cmd/asm/internal/arch/arch.go` の `Set` 関数が変更され、`"386"` および `"amd64"` アーキテクチャの選択が `archX86` 関数に統合されました。`archX86` は `obj.LinkArch` ポインタを受け取り、32ビットと64ビットのリンカアーキテクチャを適切に設定します。
    *   `src/cmd/8g` 以下のGoコンパイラのフロントエンドファイル群（`cgen.go`, `cgen64.go`, `galign.go`, `gg.go`, `ggen.go`, `gsubr.go`, `peep.go`, `prog.go`, `reg.go`）では、`cmd/internal/obj/i386` からのインポートが `cmd/internal/obj/x86` に変更されました。これは、アセンブラバックエンドの切り替えを反映しています。

2.  **`PINSRQ`, `CMPSD` 命令のエンコーディング修正**:
    *   これらの命令は、通常、ソースオペランド、デスティネーションオペランド、そしてイミディエイト値（例えば、`PINSRQ` の挿入位置や `CMPSD` の比較条件）の3つの引数を取ります。
    *   以前の実装では、この3番目のイミディエイト引数が、`obj.Prog` 構造体の `From3` フィールドではなく、別の引数の「未使用のスロット」に不適切に詰め込まれていました。
    *   このコミットでは、`src/cmd/internal/obj/x86/asm6.go` の `doasm` 関数内で、`PINSRQ` や `CMPSD` などの命令に対して、`p.From3` フィールドを明示的に使用するようにロジックが変更されました。具体的には、`p.From3.Type == obj.TYPE_NONE` の場合に、`p.From` や `p.To` の情報を `p.From3` に移動させ、`p.From` や `p.To` をイミディエイト値用に設定し直す処理が追加されました。これにより、命令のエンコーディングがより正確かつ意図通りに行われるようになります。

3.  **`old6a` の `CMPSD` 引数順序バグ修正**:
    *   `old6a` は古い32ビットアセンブラであり、`CMPSD` 命令の引数順序に関する文法定義に誤りがありました。Intelのドキュメントでは `mem,reg` (メモリからレジスタへの比較) が許容されるにもかかわらず、`old6a` は `reg,mem` (レジスタからメモリへの比較) のみを正しく扱っていました。
    *   コミットメッセージによると、このバグにより `mem,reg` を試みたコードは `liblink` によって拒否され、結果として `reg,reg` の形式しか機能していませんでした。
    *   このコミットでは、`src/cmd/old6a/a.y` (アセンブラの文法定義ファイル) および `src/cmd/old6a/y.go` (生成されたパーサーコード) が修正され、`CMPSD` が `mem,reg` 形式の引数を正しく認識し、エンコードできるようになりました。
    *   興味深いことに、コミットメッセージでは「エンコーディングテーブルが引数順序を反転させていた」と述べられており、これはIntelのドキュメントとは逆の比較になっていたことを示唆しています。しかし、既存のコードがこの「反転した比較」を期待して書かれているため、引数順序を完全にIntelのドキュメント通りに「入れ替える」ことはせず、代わりに `mem,reg` オペランドを正しく受け入れるように修正することで、既存のコードへの影響を最小限に抑えつつ、機能性を向上させています。

4.  **TLSアクセスロジックの改善**:
    *   `src/cmd/internal/obj/x86/obj6.go` の `canuselocaltls` 関数が、32ビットモードでのTLSアクセスに関するロジックを更新しました。特定のOS (Linux, NaCl, Plan9, Windows) では、32ビットモードで直接TLSを使用できないため、`false` を返すようになりました。
    *   `src/cmd/internal/obj/x86/asm6.go` の `doasm` 関数内のTLSロード (`Movtab` の `code == 7`) の処理が、32ビットモードと64ビットモードで異なるOS固有のTLSベースアドレス取得方法に対応するように拡張されました。例えば、Linux/NaClでは `0(GS)`、Plan9では `_privates` シンボル、Windowsでは `0x14(FS)` からTLSベースアドレスを取得するロジックが追加されています。

5.  **ビット単位の互換性**:
    *   コミットメッセージで「Bit-for-bit compatibility checked against tree without this CL.」と明記されているように、この変更は、修正前のGoコンパイラが生成する機械語と、修正後のGoコンパイラが生成する機械語が、可能な限りビット単位で同一になるように細心の注意を払って行われました。これは、Goの安定性と予測可能性を維持するために非常に重要です。

これらの変更は、Goコンパイラのx86バックエンドをより堅牢で、保守しやすく、正確なものにするための包括的な取り組みの一環です。

## コアとなるコードの解説

ここでは、上記の「コアとなるコードの変更箇所」で挙げた主要な変更点について、より詳細な技術的解説を行います。

### 1. `src/cmd/internal/obj/x86/asm6.go` の変更

このファイルは、x86アセンブリ命令を機械語にエンコードする中心的なロジックを含んでいます。

#### `Movtab` と `ymovq` の変更

`Movtab` は、特定の命令（例: `AMOVQ`）のオペランドの組み合わせと、それに対応するエンコーディングルールを定義する構造体です。`ymovq` は `AMOVQ` 命令の `Movtab` エントリの配列です。

変更前は、`AMOVQ` のエンコーディングは主に64ビットモードを想定していましたが、このコミットでは32ビットモードのサポートが追加され、より多くのオペランドタイプとプレフィックスが導入されました。

```go
// 変更前 (一部抜粋)
var ymovq = []ytab{
	{Yrl, Ynone, Yml, Zr_m, 1},       // 0x89
	{Yml, Ynone, Yrl, Zm_r, 1},       // 0x8b
	// ...
}

// 変更後 (一部抜粋)
var ymovq = []ytab{
	// valid in 32-bit mode
	{Ym, Ynone, Ymr, Zm_r_xm_nr, 1},  // 0x6f MMX MOVQ (shorter encoding)
	{Ymr, Ynone, Ym, Zr_m_xm_nr, 1},  // 0x7f MMX MOVQ
	{Yxr, Ynone, Ymr, Zm_r_xm_nr, 2}, // Pf2, 0xd6 MOVDQ2Q
	{Yxm, Ynone, Yxr, Zm_r_xm_nr, 2}, // Pf3, 0x7e MOVQ xmm1/m64 -> xmm2
	{Yxr, Ynone, Yxm, Zr_m_xm_nr, 2}, // Pe, 0xd6 MOVQ xmm1 -> xmm2/m64

	// valid only in 64-bit mode, usually with 64-bit prefix
	{Yrl, Ynone, Yml, Zr_m, 1},      // 0x89
	{Yml, Ynone, Yrl, Zm_r, 1},      // 0x8b
	// ...
}
```

この変更により、`AMOVQ` がMMX/SSE命令（`Ym`, `Ymr`, `Yxr`, `Yxm` など）を伴う場合や、異なるプレフィックス（`Pf2`, `Pf3`, `Pe`）を持つ場合のエンコーディングが明確に定義されました。特に、32ビットモードと64ビットモードで異なるエンコーディングが適用されることが示されています。

#### `doasm` 関数の変更

`doasm` 関数は、`obj.Prog` 構造体で表現されたアセンブリ命令を受け取り、実際の機械語バイト列を生成します。

**`p.From3` の扱いと `PINSRQ`, `CMPSD` のエンコーディング修正**:
`PINSRQ` や `CMPSD` のような命令は、3つのオペランドを持つことがあります。Goのアセンブラでは、これらを `p.From`, `p.To`, `p.From3` で表現します。以前は、`p.From3` が適切に扱われず、エンコーディングが複雑になっていました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内)
// TODO(rsc): This special case is for PINSRQ etc, CMPSD etc.
// Change encoding generated by assemblers and compilers (if any) and remove.
switch p.As {
case AIMUL3Q, APEXTRW, APINSRW, APINSRD, APINSRQ, APSHUFHW, APSHUFL, APSHUFW, ASHUFPD, ASHUFPS, AAESKEYGENASSIST, APSHUFD, APCLMULQDQ:
	if p.From3.Type == obj.TYPE_NONE {
		p.From3 = p.From
		p.From = obj.Addr{}
		p.From.Type = obj.TYPE_CONST
		p.From.Offset = p.To.Offset
		p.To.Offset = 0
	}
case ACMPSD, ACMPSS, ACMPPS, ACMPPD:
	if p.From3.Type == obj.TYPE_NONE {
		p.From3 = p.To
		p.To = obj.Addr{}
		p.To.Type = obj.TYPE_CONST
		p.To.Offset = p.From3.Offset
		p.From3.Offset = 0
	}
}
```
このコードは、`PINSRQ` や `CMPSD` などの命令が `p.From3` を持たない場合（つまり、アセンブラが古い形式で引数を渡している場合）に、`p.From` や `p.To` の内容を `p.From3` に移動させ、`p.From` や `p.To` をイミディエイト値用に再設定します。これにより、エンコーディングロジックが `p.From3` を常に正しい3番目のオペランドとして扱えるようになります。コメントにあるように、将来的にはアセンブラやコンパイラが最初から正しい形式で `p.From3` を設定するようになれば、この特殊ケースは不要になります。

**`ytab` 検索ロジックの変更**:
命令のエンコーディングテーブル (`optab`) を検索する際に、`p.From`, `p.To` に加えて `p.From3` の型も考慮するようになりました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内)
// 変更前:
// if ycover[ft+int(yt.from)] != 0 && ycover[tt+int(yt.to)] != 0 {
// 変更後:
if ycover[ft+int(yt.from)] != 0 && ycover[f3t+int(yt.from3)] != 0 && ycover[tt+int(yt.to)] != 0 {
```
`f3t` は `p.F3t` (oclass(p.From3) の結果) を表し、`yt.from3` は `ytab` エントリの3番目のオペランドの型を表します。これにより、命令のエンコーディングがより厳密に、かつ正確に行われるようになります。

**TLSベースアドレスのロードロジックの拡張**:
`doasm` 関数内の `Movtab` の `code == 7` (TLSベースアドレスのロード) の処理が、32ビットモードと64ビットモードで異なるOS固有のTLSアクセス方法に対応するように拡張されました。

```go
// src/cmd/internal/obj/x86/asm6.go (doasm関数内, Movtab code == 7 のケース)
				case 7: /* mov tls, r */
					if p.Mode == 64 && p.As != AMOVQ || p.Mode == 32 && p.As != AMOVL {
						ctxt.Diag("invalid load of TLS: %v", p)
					}

					if p.Mode == 32 {
						switch ctxt.Headtype {
						default:
							log.Fatalf("unknown TLS base location for %s", obj.Headstr(ctxt.Headtype))

						case obj.Hlinux,
							obj.Hnacl:
							// ELF TLS base is 0(GS).
							// ... (GSセグメントプレフィックス 0x65 と MOV命令 0x8B を出力)

						case obj.Hplan9:
							// ... (_privates シンボルからロード)

						case obj.Hwindows:
							// Windows TLS base is always 0x14(FS).
							// ... (FSセグメントプレフィックス 0x64 と MOV命令 0x8B を出力)
						}
						break
					}
					// ... (64ビットモードのTLSロードロジック)
```
このコードは、現在のモード (`p.Mode`) とOS (`ctxt.Headtype`) に応じて、TLSベースアドレスをロードするための適切な機械語シーケンスを生成します。例えば、32ビットLinux/NaClでは `GS` セグメントレジスタを介して `0(GS)` からロードし、Windowsでは `FS` セグメントレジスタを介して `0x14(FS)` からロードします。これにより、異なる環境でのTLSアクセスが正しく行われるようになります。

### 2. `src/cmd/internal/obj/x86/obj6.go` の変更

このファイルは、Goコンパイラのリンカがアセンブリ命令を処理する前の前処理ロジックを含んでいます。

#### `progedit` 関数の変更

`progedit` 関数は、各 `obj.Prog` (アセンブリ命令) をリンカが処理する前に修正します。

**コード生成モードの管理**:
`ctxt.Mode` と `p.Mode` を導入し、現在のコード生成が32ビットか64ビットかを追跡するようになりました。`AMODE` 命令は、このモードを設定するために使用されます。

```go
// src/cmd/internal/obj/x86/obj6.go (progedit関数内)
	// Maintain information about code generation mode.
	if ctxt.Mode == 0 {
		ctxt.Mode = ctxt.Arch.Regsize * 8
	}
	p.Mode = int8(ctxt.Mode)

	switch p.As {
	case AMODE:
		if p.From.Type == obj.TYPE_CONST || (p.From.Type == obj.TYPE_MEM && p.From.Reg == REG_NONE) {
			switch int(p.From.Offset) {
			case 16, 32, 64:
				ctxt.Mode = int(p.From.Offset)
			}
		}
		obj.Nopout(p) // AMODE命令自体は機械語を生成しない
	}
```
`ctxt.Mode` はリンカ全体のモードを、`p.Mode` は個々の命令のモードを示します。これにより、リンカは命令ごとに適切なエンコーディングルールを適用できるようになります。

**スタックフレーム処理の調整**:
`preprocess` 関数内のスタックフレーム処理 (`autoffset`) が、64ビットモードでのみフレームポインタの保存を行うように変更されました。

```go
// src/cmd/internal/obj/x86/obj6.go (preprocess関数内)
// 変更前:
// if obj.Framepointer_enabled != 0 && autoffset > 0 {
// 変更後:
if p.Mode == 64 && obj.Framepointer_enabled != 0 && autoffset > 0 {
```
これは、32ビットモードではフレームポインタの保存が異なる方法で行われるか、あるいは不要であることを示唆しています。

### 3. `src/cmd/asm/internal/arch/arch.go` の変更

このファイルは、Goアセンブラがサポートするアーキテクチャを定義し、それぞれのアーキテクチャ固有の情報を設定します。

#### `archX86` 関数の導入と統合

以前は `arch386` と `archAmd64` という別々の関数がありましたが、これらが `archX86` に統合されました。

```go
// src/cmd/asm/internal/arch/arch.go (Set関数内)
	case "386":
		return archX86(&x86.Link386)
	case "amd64":
		return archX86(&x86.Linkamd64)
	case "amd64p32":
		return archX86(&x86.Linkamd64p32)

// src/cmd/asm/internal/arch/arch.go (archX86関数)
func archX86(linkArch *obj.LinkArch) *Arch {
	register := make(map[string]int16)
	// ... (レジスタと命令のマップを初期化)
	return &Arch{
		LinkArch:       linkArch,
		Instructions:   instructions,
		Register:       register,
		RegisterPrefix: nil,
		RegisterNumber: nilRegisterNumber,
		IsJump:         jumpX86,
	}
}
```
`archX86` 関数は `obj.LinkArch` ポインタを受け取ることで、32ビット (`x86.Link386`) と64ビット (`x86.Linkamd64`, `x86.Linkamd64p32`) のリンカアーキテクチャを共通のロジックで設定できるようになりました。これにより、x86アーキテクチャの共通部分を再利用し、コードの重複を減らすことができます。

### 4. `src/cmd/old6a/a.y` および `src/cmd/old6a/y.go` の変更

これらのファイルは、古い32ビットアセンブラ `old6a` の文法定義と、それから生成されるパーサーコードです。

#### `CMPSD` 命令の文法修正

`a.y` ファイルはYacc/Bison形式の文法定義ファイルであり、アセンブリ命令の構文ルールを定義します。

```
// src/cmd/old6a/a.y (変更箇所の一部)
// 変更前:
// CMPSD	reg,reg
// 変更後:
// CMPSD	mem,reg
// CMPSD	reg,reg
```
この変更により、`CMPSD` 命令がメモリオペランドをソースとして、レジスタオペランドをデスティネーションとして取ることができるようになりました。以前は `reg,reg` の形式しか文法的に許容されていなかったため、`mem,reg` 形式のアセンブリコードはコンパイルエラーになっていました。この修正により、Intelの命令セットリファレンスに準拠した `CMPSD` の使用が可能になります。

これらのコアとなるコードの変更は、Goコンパイラのx86バックエンドをよりモジュール化し、32ビットと64ビットのコード生成を統合し、特定の命令のエンコーディングの正確性を向上させ、古いアセンブラのバグを修正するという、このコミットの主要な目的を達成しています。

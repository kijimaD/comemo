# [インデックス 23527] ファイルの概要

このコミットは、Goコンパイラとリンカのアーキテクチャ固有のツール群（例: `5g`, `6g`, `5l`, `6l`など）を、それぞれ単一のコマンド `go tool compile` および `go tool link` に統合するという、Goツールチェインの構造における重要な変更を導入しています。この変更は、Goのビルドシステムを簡素化し、将来的なメンテナンス性と拡張性を向上させることを目的としています。

## 元コミット内容

このコミットの元の内容は、Goのコンパイラとリンカのアーキテクチャ固有のバージョン（例: `5g` (ARM), `6g` (AMD64), `8g` (x86), `9g` (PPC64) など）を、それぞれ単一の `go tool compile` および `go tool link` コマンドに統合するというものです。具体的には、以下の変更が含まれます。

- `compile/main.go` と `link/main.go` という新しいファイルが作成され、これらがアーキテクチャ固有のコンパイラ/リンカ実装へのディスパッチャとして機能します。
- 既存のアーキテクチャ固有のコンパイラ/リンカのソースファイルは、新しいディレクトリ構造（例: `src/cmd/6g` から `src/cmd/compile/internal/amd64` へ）に移動されます。
- 移動されたファイルのパッケージ名が `main` から、対応するアーキテクチャ名（例: `amd64`, `arm`）に変更されます。
- 関連するインポートパスも新しい構造に合わせて更新されます。

コミットメッセージには「This CL breaks the build. Manual fixups are in the next CL.」と明記されており、このコミット自体はビルドを壊す過渡的な状態であり、後続のコミットで修正されることが示されています。これは、大規模なリファクタリングにおいて、論理的な変更単位を小さく保ちつつ、段階的にシステムを移行する一般的なプラクティスです。

## 変更の背景

Go言語の初期のツールチェインは、Plan 9の設計思想を強く継承していました。この設計では、各アーキテクチャ（例: x86, AMD64, ARM）に対して個別のコンパイラ（`8g`, `6g`, `5g`など）とリンカ（`8l`, `6l`, `5l`など）が存在していました。これは、異なるアーキテクチャ間でコード生成ロジックが大きく異なるため、それぞれのツールを独立して開発・保守するのに適していました。

しかし、このアプローチにはいくつかの課題がありました。
1.  **ツールの冗長性**: 各アーキテクチャごとにほぼ同じ機能を持つツールが存在するため、コードの重複や共通ロジックの管理が複雑になる傾向がありました。
2.  **ユーザーエクスペリエンス**: ユーザーはターゲットアーキテクチャに応じて異なるコマンド（例: `6g` の代わりに `go tool compile`）を使い分ける必要があり、特にクロスコンパイルの際に混乱を招く可能性がありました。
3.  **メンテナンスの複雑さ**: 新しいアーキテクチャのサポートを追加する際や、コンパイラ/リンカの共通部分に機能を追加する際に、複数のツールにわたって変更を適用する必要がありました。

このコミットは、これらの課題を解決し、Goツールチェインの統一と簡素化を目指す大規模なリファクタリングの一環です。単一の `go tool compile` および `go tool link` コマンドを通じて、ターゲットアーキテクチャを自動的に判別し、適切なバックエンドを呼び出すようにすることで、ユーザーエクスペリエンスを向上させ、ツールチェインの内部構造をよりモジュール化された形に再構築します。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての前提知識があると役立ちます。

1.  **Goツールチェインの構成**:
    *   **コンパイラ (`go tool compile`)**: Goのソースコードをアセンブリコード（または中間表現）に変換します。以前は `5g`, `6g`, `8g`, `9g` など、アーキテクチャごとに独立したコマンドでした。
    *   **リンカ (`go tool link`)**: コンパイラによって生成されたオブジェクトファイルと、必要なライブラリを結合して実行可能ファイルを生成します。以前は `5l`, `6l`, `8l`, `9l` など、アーキテクチャごとに独立したコマンドでした。
    *   **アセンブラ (`go tool asm`)**: Goのアセンブリ言語で書かれたコードをオブジェクトファイルに変換します。
    *   **`go` コマンド**: これら低レベルのツールを抽象化し、ビルド、テスト、実行などの高レベルな操作を提供するGoの主要なコマンドラインインターフェースです。`go build` のようなコマンドは、内部的に `go tool compile` や `go tool link` を呼び出します。

2.  **クロスコンパイル**: Goは、あるプラットフォーム（OS/アーキテクチャ）で別のプラットフォーム向けの実行可能ファイルを生成するクロスコンパイルを強力にサポートしています。この機能は、`GOOS` (ターゲットOS) と `GOARCH` (ターゲットアーキテクチャ) 環境変数を設定することで利用できます。このコミットによるツールチェインの統合は、クロスコンパイルの内部的な仕組みをより効率的にします。

3.  **Goのパッケージシステムとモジュール**: Goのコードはパッケージに分割され、`import` ステートメントで他のパッケージを参照します。このコミットでは、ファイルが移動される際に、これらの `import` パスとパッケージ名が変更されています。`package main` は実行可能プログラムのエントリポイントを示す特別なパッケージですが、このリファクタリングではアーキテクチャ固有のコンパイラ/リンカの内部パッケージは `main` ではなく、それぞれのアーキテクチャ名（例: `package amd64`）に変更されています。

4.  **Plan 9のツールチェイン**: Goの初期のツールチェインは、Bell LabsのPlan 9オペレーティングシステムで使用されていたツールチェイン（`8c`, `6c`, `5c` など）に強く影響を受けていました。これらのツールは、ターゲットアーキテクチャを示す数字（`8`はx86、`6`はAMD64、`5`はARM）と、ツールの種類（`c`はCコンパイラ、`l`はリンカ、`a`はアセンブラ）を組み合わせた命名規則を持っていました。Goの `8g`, `6g`, `5g` などもこの伝統に従っていました。

5.  **`cmd/internal` ディレクトリ**: Goの標準ライブラリやツールチェインでは、`internal` という名前のディレクトリが特別な意味を持ちます。`internal` ディレクトリ内のパッケージは、その親ディレクトリの階層内からのみインポート可能であり、外部からはインポートできません。これにより、内部実装の詳細を隠蔽し、APIの安定性を保つことができます。このコミットでは、アーキテクチャ固有のコンパイラ/リンカのコードが `cmd/compile/internal/<arch>` や `cmd/link/internal/<arch>` に移動されており、これはこれらの実装が `cmd/compile` や `cmd/link` の内部的な詳細であることを示しています。

## 技術的詳細

このコミットの技術的な核心は、Goツールチェインのコンパイラとリンカのディスパッチロジックの一元化と、それに伴うコードベースの再編成です。

### 1. ディスパッチメカニズムの導入
- `src/cmd/compile/main.go` と `src/cmd/link/main.go` という新しいエントリポイントが作成されました。
- これらの `main.go` ファイルは、`runtime.GOARCH` (または `obj.Getgoarch()` を通じて取得されるターゲットアーキテクチャ) の値に基づいて、適切なアーキテクチャ固有のコンパイラ/リンカの `Main()` 関数を呼び出す `switch` ステートメントを含んでいます。
- 例えば、`cmd/compile/main.go` は、`GOARCH` が `amd64` であれば `cmd/compile/internal/amd64.Main()` を、`arm` であれば `cmd/compile/internal/arm.Main()` を呼び出します。これにより、ユーザーは `go tool compile` という単一のコマンドを実行するだけで、現在の環境または指定されたターゲットアーキテクチャに応じたコンパイラが自動的に選択されるようになります。

### 2. ファイルの移動とパッケージ名の変更
- 以前は `src/cmd/6g/cgen.go` のように、アーキテクチャ固有のコンパイラコードが直接 `src/cmd/<arch>g` ディレクトリに配置されていました。
- このコミットでは、これらのファイルが `src/cmd/compile/internal/<arch>/cgen.go` のような新しいパスに移動されました。同様に、リンカのファイルも `src/cmd/link/internal/<arch>/asm.go` のようなパスに移動されています。
- ファイルの移動に伴い、各ファイルの `package main` 宣言が、その新しいディレクトリ名に対応するパッケージ名（例: `package amd64`, `package arm`）に変更されました。これにより、これらのアーキテクチャ固有の実装が、それぞれ独立した内部パッケージとして機能するようになります。

### 3. インポートパスの更新
- パッケージ名の変更とファイルの移動により、これらの内部パッケージが参照する他のGoパッケージのインポートパスも更新されました。
- 例えば、`cmd/internal/gc` パッケージへのインポートは、`cmd/compile/internal/gc` に変更されています。これは、`gc` パッケージが `cmd/compile` の内部パッケージとして再配置されたことを示唆しています。
- また、`cmd/internal/gc/big` のようなパスは `cmd/compile/internal/big` に変更されており、`big` パッケージも `cmd/compile` の内部に移動されたことがわかります。

### 4. `Main()` 関数の導入
- 以前のアーキテクチャ固有のコンパイラ/リンカは、それぞれが独立した実行可能ファイルであったため、`main` パッケージ内に `main()` 関数を持っていました。
- リファクタリング後、これらのコードは `cmd/compile` や `cmd/link` の内部パッケージとなったため、エントリポイントの関数名が `main()` から `Main()` (大文字M) に変更されました。これにより、これらの関数はエクスポートされ、`cmd/compile/main.go` や `cmd/link/main.go` から呼び出せるようになります。

### 5. ビルドの破壊と段階的移行
- コミットメッセージに「This CL breaks the build. Manual fixups are in the next CL.」とあるように、このコミットは意図的にビルドを壊す変更を含んでいます。これは、大規模なリファクタリングにおいて、コードの移動や構造変更を一つのコミットで行い、その後のコミットで機能的な修正やビルドの復旧を行うという、段階的なアプローチを示しています。これにより、変更の意図が明確になり、レビューやデバッグがしやすくなります。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下の2つの新しいファイルと、多数の既存ファイルの移動と内容変更に集約されます。

1.  **`src/cmd/compile/main.go` (新規ファイル)**:
    ```go
    package main

    import (
    	"cmd/compile/internal/amd64"
    	"cmd/compile/internal/arm"
    	"cmd/compile/internal/arm64"
    	"cmd/compile/internal/ppc64"
    	"cmd/compile/internal/x86"
    	"cmd/internal/obj" // obj.Getgoarch() を使用するため
    	"fmt"
    	"os"
    )

    func main() {
    	switch obj.Getgoarch() {
    	default:
    		fmt.Fprintf(os.Stderr, "compile: unknown architecture %q\n", obj.Getgoarch())
    		os.Exit(2)
    	case "386":
    		x86.Main()
    	case "amd64", "amd64p32":
    		amd64.Main()
    	case "arm":
    		arm.Main()
    	case "arm64":
    		arm64.Main()
    	case "ppc64", "ppc64le":
    		ppc64.Main()
    	}
    }
    ```
    このファイルは、`go tool compile` コマンドの新しいエントリポイントです。`obj.Getgoarch()` を呼び出して現在のターゲットアーキテクチャを判別し、それに応じて `cmd/compile/internal/<arch>` パッケージ内の `Main()` 関数を呼び出します。

2.  **`src/cmd/link/main.go` (新規ファイル)**:
    ```go
    package main

    import (
    	"cmd/internal/obj" // obj.Getgoarch() を使用するため
    	"cmd/link/internal/amd64"
    	"cmd/link/internal/arm"
    	"cmd/link/internal/arm64"
    	"cmd/link/internal/ppc64"
    	"cmd/link/internal/x86"
    	"fmt"
    	"os"
    )

    func main() {
    	switch obj.Getgoarch() {
    	default:
    		fmt.Fprintf(os.Stderr, "link: unknown architecture %q\n", obj.Getgoarch())
    		os.Exit(2)
    	case "386":
    		x86.Main()
    	case "amd64", "amd64p32":
    		amd64.Main()
    	case "arm":
    		arm.Main()
    	case "arm64":
    		arm64.Main()
    	case "ppc64", "ppc64le":
    		ppc64.Main()
    	}
    }
    ```
    このファイルは、`go tool link` コマンドの新しいエントリポイントであり、`compile/main.go` と同様にターゲットアーキテクチャに基づいて適切なリンカの `Main()` 関数をディスパッチします。

3.  **既存ファイルの移動と変更**:
    - 例: `src/cmd/6g/cgen.go` が `src/cmd/compile/internal/amd64/cgen.go` に移動。
    - パッケージ名の変更: `package main` から `package amd64` へ。
    - インポートパスの変更: `cmd/internal/gc` から `cmd/compile/internal/gc` へ。
    - エントリポイント関数のリネーム: `func main()` から `func Main()` へ (アーキテクチャ固有の `galign.go` や `obj.go` ファイル内)。

これらの変更は、Goツールチェインのアーキテクチャ固有のコンポーネントを、より統一されたフレームワークの下に配置し、`go tool compile` および `go tool link` という単一のコマンドで複数のアーキテクチャをサポートするための基盤を築いています。

## コアとなるコードの解説

このコミットのコアとなるコードは、主に新しい `main.go` ファイルと、移動・変更されたアーキテクチャ固有のコンパイラ/リンカのソースファイル群です。

### `src/cmd/compile/main.go` および `src/cmd/link/main.go` の役割

これらのファイルは、Goツールチェインの新しいフロントエンドとして機能します。
- `package main` として定義されており、それぞれが独立した実行可能プログラムのエントリポイント (`func main()`) を持ちます。
- `cmd/internal/obj.Getgoarch()` 関数を呼び出すことで、現在のビルドターゲットアーキテクチャ（`GOARCH` 環境変数で指定されるか、デフォルトで現在のシステムアーキテクチャ）を取得します。
- 取得したアーキテクチャ名に基づいて、`switch` ステートメントを用いて、対応するアーキテクチャ固有のコンパイラ/リンカの実装をインポートし、そのエントリポイント関数 (`Main()`) を呼び出します。
- 未知のアーキテクチャが指定された場合は、エラーメッセージを出力して終了します。

このディスパッチロジックにより、Goのビルドシステムは、ユーザーが `go build` や `go run` を実行した際に、自動的に適切なコンパイラとリンカのバックエンドを選択できるようになります。これにより、ユーザーはアーキテクチャ固有のツール名を意識することなく、統一されたインターフェースでGoプログラムをビルドできるようになりました。

### アーキテクチャ固有のパッケージ (`cmd/compile/internal/<arch>`, `cmd/link/internal/<arch>`)

- 以前は `src/cmd/6g` のようにトップレベルのディレクトリに存在していたアーキテクチャ固有のコンパイラ/リンカのソースファイルは、`src/cmd/compile/internal/amd64` や `src/cmd/link/internal/arm` のようなサブディレクトリに移動されました。
- これらのディレクトリ内のファイルは、`package main` から `package amd64` や `package arm` のように、そのディレクトリ名に対応するパッケージ名に変更されました。これにより、これらのコードは `cmd/compile` や `cmd/link` の内部パッケージとして扱われ、外部からは直接インポートできなくなります。これは、Goの `internal` パッケージのルールに従ったもので、ツールチェインの内部実装の詳細を隠蔽し、モジュール性を高める効果があります。
- 各アーキテクチャ固有のパッケージには、以前の `main()` 関数に代わる `Main()` 関数が定義されています。この `Main()` 関数は、そのアーキテクチャのコンパイラまたはリンカの主要な処理ロジックを含んでいます。例えば、`cmd/compile/internal/amd64/galign.go` 内の `func Main()` は、AMD64アーキテクチャ向けのコンパイラの初期化と処理フローを制御します。
- インポートパスも、新しいディレクトリ構造に合わせて更新されています。例えば、`"cmd/internal/gc"` は `"cmd/compile/internal/gc"` に、`"cmd/internal/gc/big"` は `"cmd/compile/internal/big"` に変更されています。これは、`gc` や `big` といった共通のコンパイラコンポーネントが、`cmd/compile` の内部パッケージとして再編成されたことを示しています。

この大規模なリファクタリングは、Goツールチェインの内部構造をよりクリーンで、保守しやすく、拡張性の高いものにするための重要な一歩でした。これにより、将来的に新しいアーキテクチャのサポートを追加したり、コンパイラ/リンカの共通部分に機能を追加したりする作業が容易になります。

# [インデックス 27591] ファイルの概要

このコミットは、Go言語のツールチェインの一部であるリンカ（`cmd/link`）内の`src/cmd/link/internal/ld/objfile.go`ファイルに対する変更です。`objfile.go`は、Goのリンカがオブジェクトファイルや実行可能ファイルを読み込み、解析するために使用されるコードを含んでいます。具体的には、シンボル情報やその他のメタデータを効率的に処理するための低レベルなI/O操作を扱います。

## コミット

このコミットは、リンカが内部で使用する読み取りバッファ（`rdBuf`）の成長戦略を最適化し、必要に応じて遅延的にバッファを拡張するように変更します。これにより、リンカの実行時間とメモリ使用量の両方でわずかな改善が見られます。

## 変更の背景

Go言語のリンカ（`cmd/link`）は、コンパイルされたGoパッケージを最終的な実行可能バイナリに結合する役割を担っています。このプロセスでは、オブジェクトファイルから大量のデータを読み込み、処理する必要があります。`objfile.go`内の`objReader`構造体は、このデータ読み込みを効率的に行うためのバッファ（`rdBuf`）を保持しています。

以前の実装では、文字列やシンボル名を読み込む際に、必要なバッファサイズを事前に計算し、そのサイズに基づいてバッファを再割り当てしていました。しかし、コミットメッセージによると、「最終的なバッファサイズを数えても、通常はバッファが成長することはない」という観察がありました。つまり、ほとんどの場合、バッファの再割り当ては不要であり、無駄な処理やメモリの再確保が発生していました。

このコミットの目的は、この非効率性を解消し、バッファの成長を「遅延的」に行うことです。つまり、バッファが実際に不足した場合にのみ、必要なサイズに拡張するように変更することで、リンカのパフォーマンス（実行時間）とメモリ使用量（MaxRSS）を改善することを目指しています。ベンチマーク結果が示すように、実行時間のわずかな短縮とメモリ使用量の削減が達成されています。

## 前提知識の解説

### Go言語のリンカ (`cmd/link`)

Go言語のビルドプロセスにおいて、`cmd/link`は非常に重要なツールです。Goコンパイラ（`cmd/compile`）によって生成されたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、実行可能なバイナリファイルを生成します。この過程で、シンボルの解決、外部ライブラリのリンク、実行可能ファイルのフォーマット（ELF, Mach-O, PEなど）への変換などが行われます。

### `objfile.go`の機能

`src/cmd/link/internal/ld/objfile.go`は、リンカがオブジェクトファイルやアーカイブファイルの内容を読み取るための低レベルなロジックを提供します。`objReader`という構造体が定義されており、これはファイルの読み取り位置を管理し、バイト列、整数、文字列、シンボル名などの様々なデータを効率的に読み出すためのメソッド群を持っています。`rdBuf`はこの`objReader`が内部でデータを一時的に保持するために使用するバイトスライスです。

### Goの`slice`における`len`と`cap`の概念

Go言語の`slice`（スライス）は、配列をラップした動的なデータ構造です。スライスは以下の3つの要素で構成されます。

*   **ポインタ**: スライスが参照する基底配列の先頭要素へのポインタ。
*   **`len` (長さ)**: スライスに含まれる要素の数。`len()`関数で取得できます。
*   **`cap` (容量)**: スライスの基底配列が保持できる要素の最大数。`cap()`関数で取得できます。スライスが再割り当てなしで拡張できる限界を示します。

例えば、`s := make([]byte, 5, 10)`とすると、`len(s)`は5、`cap(s)`は10となります。これは、スライス`s`が現在5つの要素を持ち、基底配列にはさらに5つの要素（合計10個）を格納する余裕があることを意味します。

### `make([]byte, n)`と`make([]byte, n, cap)`の違いと、バッファの再割り当て（reallocation）のメカニズム

*   **`make([]byte, n)`**: この形式でスライスを作成すると、`len`と`cap`の両方が`n`に設定されます。つまり、スライスは`n`個のゼロ値バイトで初期化され、基底配列の容量も`n`です。このスライスに`append`などで`n`個を超える要素を追加しようとすると、Goランタイムはより大きな新しい基底配列を割り当て、既存の要素をコピーし、新しい要素を追加します。このプロセスを「再割り当て（reallocation）」と呼び、パフォーマンスにオーバーヘッドをもたらします。

*   **`make([]byte, n, cap)`**: この形式では、スライスの初期`len`を`n`、`cap`を`cap`に明示的に設定できます。例えば、`make([]byte, 0, 100)`とすると、長さ0で容量100のスライスが作成されます。これにより、最大100個の要素を再割り当てなしで追加できます。

バッファの再割り当ては、スライスの`len`が`cap`を超えようとしたときに発生します。Goランタイムは、新しい容量を決定する際に、一般的に現在の容量が1024未満の場合は2倍、1024以上の場合は1.25倍（または25%増）にする戦略を取ります。この戦略は、再割り当ての頻度を減らしつつ、過剰なメモリの事前割り当てを避けることを目的としています。

このコミットの変更は、このスライスの`len`と`cap`の特性を理解し、バッファの再割り当てをより効率的に行うことに焦点を当てています。

## 技術的詳細

このコミットの核心は、`objReader`が文字列やシンボル名を読み込む際に使用する`rdBuf`というバイトスライスの管理方法の変更にあります。

以前の実装では、`readString()`メソッドと`readSymName()`メソッドの両方で、読み込むべきデータの長さ`n`（または`need`）を計算し、その長さが現在の`r.rdBuf`の**長さ (`len`)** よりも大きい場合に、新しいバッファを`make([]byte, n)`（または`make([]byte, need)`）で作成していました。

変更後、この条件は`len(r.rdBuf) < n`から`cap(r.rdBuf) < n`に変わりました。これは、バッファの**容量 (`cap`)** が不足している場合にのみ、バッファを拡張するという意味です。さらに、新しいバッファを作成する際には、`make([]byte, n)`ではなく`make([]byte, 2*n)`を使用するようになりました。

この変更の意図は以下の通りです。

1.  **`len`から`cap`への変更**:
    *   `len(r.rdBuf) < n`という条件は、`rdBuf`が現在保持している有効なデータの長さが、新しく読み込むデータの長さよりも短い場合に常に新しいバッファを割り当てようとします。しかし、`rdBuf`の基底配列にはまだ空き容量（`cap - len`）があるかもしれません。
    *   `cap(r.rdBuf) < n`という条件に変更することで、`rdBuf`の基底配列に十分な容量がある場合は、新しいバッファの割り当てをスキップし、既存の基底配列を再利用できるようになります。これにより、不要なメモリ割り当てとデータコピーのオーバーヘッドが削減されます。

2.  **`make([]byte, n)`から`make([]byte, 2*n)`への変更**:
    *   バッファの容量が不足し、新しいバッファを割り当てる必要がある場合、以前は必要なサイズ`n`と全く同じ容量のバッファを作成していました。これは、次に`n`を超えるサイズのデータが来た場合に、すぐにまた再割り当てが発生する可能性が高いことを意味します。
    *   `make([]byte, 2*n)`に変更することで、一度バッファを拡張する際に、将来の成長を見越して2倍の容量を確保します。これにより、連続する小さな成長要求に対して再割り当ての頻度を減らし、全体的なパフォーマンスを向上させることができます。これは、Goのスライス成長戦略で一般的に採用されているアプローチです。

3.  **`readSymName()`における`adjName = r.rdBuf[:0]`の追加**:
    *   `readSymName()`メソッドでは、シンボル名を調整する際に`adjName`というスライスを使用しています。このスライスは`r.rdBuf`の基底配列を共有しています。
    *   `r.readFull(r.rdBuf[:n])`の後に`r.rdBuf = adjName[:0]`を追加することで、`r.rdBuf`が`adjName`と同じ基底配列を指しつつ、長さが0にリセットされます。これは、`readSymName`が`r.rdBuf`を一時的なスクラッチスペースとして使用し、その内容が次の読み取り操作に影響を与えないようにするためのクリーンアップ処理です。コミットメッセージのコメント「// in case 2*n wasn't enough」は、`2*n`の容量が確保されていても、`readSymName`の内部ロジックで`adjName`がさらに成長する可能性があり、その結果`r.rdBuf`が意図しない状態になることを防ぐための措置であることを示唆しています。

これらの変更により、リンカはバッファの再割り当てをより賢く、より効率的に行うようになり、結果としてリンカの実行速度とメモリ効率が向上します。

+		r.rdBuf = make([]byte, 2*n)

*   **変更前**: `len(r.rdBuf) < n` は、`rdBuf`の現在の長さが読み込むべき文字列の長さ`n`よりも小さい場合に、新しいバッファを割り当てていました。これは、`rdBuf`に十分な容量があっても、現在の長さが`n`未満であれば常に再割り当てが発生する可能性がありました。

# [インデックス 27185] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`におけるAMD64アーキテクチャ向けのSSA（Static Single Assignment）最適化パス、特に「ロード結合（load-combining）」の改善を目的としています。具体的には、メモリからのデータロード操作をより効率的に結合し、生成されるアセンブリコードの品質と実行性能を向上させるための修正が含まれています。シンボルの取り扱い、メモリのライブネス（liveness）の考慮、そして`LEA`（Load Effective Address）命令の最適化への組み込みが主な変更点です。

## 元コミット内容

このコミットの元の内容は、Goコンパイラの`cmd/compile`におけるロード結合の不具合修正です。具体的には以下の点が挙げられています。

1.  **シンボルの伝達の保証**: ロード結合ルールが適用される際に、関連するシンボル情報が正しく新しいロード命令に引き継がれるように修正。
2.  **メモリのライブネスを考慮したロードの配置**: 新しく結合されたロード命令が、メモリが有効（live）であることが保証されている適切なSSAブロックに配置されるように修正。
3.  **`auxInt`フィールドの活用**: オフセット`i`を明示的な`ADDQ`命令ではなく、命令の`auxInt`フィールドを使って伝達するように変更し、命令数を削減。
4.  **`LEA`命令の組み込み**: `MOVBQZX`などのロード命令に`LEA`（Load Effective Address）命令を組み込むことで、アドレス計算の最適化を図る。

## 変更の背景

Goコンパイラは、プログラムのソースコードを機械語に変換する過程で、様々な最適化を行います。その中でもSSA（Static Single Assignment）形式は、最適化を適用しやすい中間表現として広く用いられています。このコミットは、SSAバックエンドにおけるAMD64アーキテクチャ固有の最適化、特にメモリからのデータロードに関する効率化を狙っています。

従来のロード結合ルールには、以下のような課題があったと考えられます。

*   **シンボル情報の欠落**: 複数のロード操作を結合する際に、元のロードが参照していたグローバル変数やスタック上の変数などのシンボル情報が失われ、正しくアドレスを解決できなくなる可能性がありました。
*   **不適切なブロックへの配置**: 最適化によって生成された新しいロード命令が、その命令が参照するメモリがまだ有効である（つまり、そのメモリ位置が変更されていない）ことが保証されないSSAブロックに配置されると、プログラムのセマンティクスが破壊される可能性があります。
*   **冗長なアドレス計算**: メモリのアドレス計算に`ADDQ`のような算術命令が明示的に使われている場合、`LEA`命令のようなより効率的なアドレス計算専用の命令を活用することで、命令数を減らし、実行速度を向上させる余地がありました。特に、ベースアドレスにオフセットを加算するようなケースでは、`LEA`は非常に強力な命令です。
*   **`LEA`とロード命令の分離**: `LEA`命令でアドレスを計算し、その結果を別のロード命令で使うというパターンは、2つの命令を必要とします。これを1つのロード命令に統合できれば、命令発行のオーバーヘッドを削減できます。

これらの課題を解決し、Goプログラムの実行性能をさらに向上させることが、このコミットの背景にあります。

## 前提知識の解説

### 1. GoコンパイラとSSA

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。その内部では、コードを複数の段階で処理し、最適化を適用します。SSA（Static Single Assignment）形式は、コンパイラの最適化フェーズで使われる中間表現の一つです。

*   **SSA形式**: SSA形式では、各変数が一度だけ代入されるように変換されます。これにより、データの流れが明確になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。
*   **SSAバックエンド**: GoコンパイラのSSAバックエンドは、SSA形式のコードを特定のアーキテクチャ（例: AMD64）の機械語に変換する役割を担います。この過程で、アーキテクチャ固有の命令選択や最適化が行われます。

### 2. ロード結合 (Load-Combining)

ロード結合は、コンパイラ最適化の一種で、隣接するメモリ位置から複数の小さなデータをロードする操作を、より大きな単一のロード操作に結合することです。

*   **例**: 連続する2つのバイトをロードして16ビット整数を構成する場合、2回のバイトロードとシフト・OR操作を行う代わりに、1回の16ビットワードロードで済ませることができます。
*   **利点**:
    *   **命令数の削減**: 複数のロード命令が1つにまとまるため、生成される機械語命令の数が減ります。
    *   **メモリ帯域の効率化**: メモリコントローラは、連続した大きなブロックのデータを一度に読み込む方が効率的です。
    *   **レジスタ使用の最適化**: 中間結果を保持するためのレジスタの使用が減る可能性があります。

### 3. `LEA` (Load Effective Address) 命令 (AMD64)

`LEA`は"Load Effective Address"の略で、AMD64（x86-64）アーキテクチャにおける強力な命令です。

*   **機能**: `LEA`命令は、メモリオペランドのアドレスを計算し、その結果をレジスタに格納します。しかし、実際にメモリからデータをロードするわけではありません。
*   **構文例**: `LEA RAX, [RBX + RCX*4 + 0x10]`
    *   この命令は、`RBX + RCX*4 + 0x10`というアドレスを計算し、その結果を`RAX`レジスタに格納します。
*   **利点**:
    *   **高速なアドレス計算**: 複雑なアドレス計算（ベースレジスタ、インデックスレジスタ、スケールファクタ、オフセットの組み合わせ）を単一の命令で効率的に実行できます。
    *   **算術演算としての利用**: メモリにアクセスしないため、`ADD`や`MUL`などの算術命令の代わりとして、レジスタ間の加算や乗算（特に2, 4, 8倍）にも利用されることがあります。
    *   **オフセットの結合**: ベースアドレスと複数のオフセットがある場合、それらをまとめて計算するのに適しています。

### 4. `auxInt` と `Aux` フィールド (SSA Value)

GoコンパイラのSSA中間表現において、`Value`（命令やオペランドを表す構造体）には、命令の種類に応じて追加の情報を格納するためのフィールドがあります。

*   **`AuxInt`**: 整数定数（例: メモリオフセット、シフト量）を格納するために使われます。
*   **`Aux`**: シンボル（例: グローバル変数、関数名、スタックフレーム上の変数）へのポインタや、その他の構造化された情報を格納するために使われます。

これらのフィールドを適切に利用することで、命令のセマンティクスを完全に表現しつつ、中間表現を簡潔に保つことができます。

### 5. メモリのライブネス (Memory Liveness)

コンパイラ最適化において、特定のメモリ位置が「ライブ（live）」であるとは、そのメモリ位置に格納されている値が将来のプログラム実行で読み取られる可能性があることを意味します。逆に「デッド（dead）」であるとは、その値がもう使われないことを意味します。

*   **重要性**: 最適化されたロード命令を挿入する際、その命令が参照するメモリがライブであるSSAブロックに配置することが極めて重要です。もしデッドなメモリを参照するブロックに配置したり、メモリが変更された後に古い値をロードしようとすると、プログラムの動作が不正になります。コンパイラは、メモリのライブネス情報を追跡し、最適化の安全性を保証する必要があります。

## 技術的詳細

このコミットは、主に`src/cmd/compile/internal/ssa/gen/AMD64.rules`と`src/cmd/compile/internal/ssa/rewriteAMD64.go`の2つのファイルにわたる変更を通じて、AMD64アーキテクチャのSSAバックエンドにおけるロード結合のロジックを改善しています。

### 1. `LEA`命令とロード命令の結合

`AMD64.rules`ファイルには、SSA命令のパターンマッチングと書き換えルールが定義されています。このコミットでは、`LEAQ`（Load Effective Address Quadword）命令がベースアドレスを計算し、その結果をロード命令が使用するパターンを最適化する新しいルールが追加されました。

**追加されたルール例:**

```
(MOVBQZXload [off1] {sym1} (LEAQ [off2] {sym2} base) mem) && canMergeSym(sym1, sym2) ->
	(MOVBQZXload [addOff(off1,off2)] {mergeSym(sym1,sym2)} base mem)
```

*   **説明**: このルールは、`MOVBQZXload`（バイトをロードし、ゼロ拡張して64ビットレジスタに格納）命令が、`LEAQ`命令によって計算されたアドレスからデータをロードしているパターンにマッチします。
*   **`[off1]`と`{sym1}`**: `MOVBQZXload`命令自身のオフセットとシンボル。
*   **`(LEAQ [off2] {sym2} base)`**: `LEAQ`命令が`base`アドレスに`off2`オフセットと`sym2`シンボルを適用してアドレスを計算している。
*   **`canMergeSym(sym1, sym2)`**: `sym1`と`sym2`という2つのシンボルが安全に結合できるかどうかをチェックする条件。例えば、両方が同じグローバル変数の一部である場合など。
*   **`addOff(off1,off2)`**: 2つのオフセット`off1`と`off2`を合計する関数。
*   **`mergeSym(sym1,sym2)`**: 2つのシンボルを結合する関数。
*   **結果**: `LEAQ`命令によるアドレス計算を`MOVBQZXload`命令のオフセットとシンボルに直接統合します。これにより、`LEAQ`命令が不要になり、1つのロード命令でアドレス計算とデータロードの両方を行うことができます。これは、`[base + off1 + off2]`という形式のアドレス指定を直接ロード命令のオペランドとして表現することに相当します。

同様のルールが、`MOVWQZXload`（ワードロード）、`MOVLQZXload`（ダブルワードロード）、および符号拡張を行う`MOVBQSXload`、`MOVWQSXload`、`MOVLQSXload`に対しても追加されています。

これらのルールは、`rewriteAMD64.go`内の対応する`rewriteValueAMD64_OpAMD64MOVBQSXload`などの関数によって実際に実装されます。これらの関数は、SSA `Value`のパターンをチェックし、マッチした場合に新しい最適化された`Value`に書き換えます。

### 2. 複数バイトロードの結合と`auxInt`の活用

既存の`ORW`（OR Word）、`ORL`（OR Long）、`ORQ`（OR Quad）命令の書き換えルールも変更されています。これらのルールは、複数の`MOVBQZXload`（バイトロード）とシフト操作を組み合わせて、より大きなデータ型（`uint16`, `uint32`, `uint64`）を構成するパターンを、単一の`MOVWload`, `MOVLload`, `MOVQload`に結合するものです。

**変更前（例: `ORW`）:**

```
(ORW (MOVBQZXload [i] {s} p mem) (SHLWconst [8] (MOVBQZXload [i+1] {s} p mem))) -> (MOVWload (ADDQconst [i] p) mem)
```

*   このルールでは、`MOVWload`命令のアドレス計算に`ADDQconst [i] p`という明示的な`ADDQconst`命令が使われていました。

**変更後（例: `ORW`）:**

```
(ORW (MOVBQZXload [i] {s} p mem) (SHLWconst [8] (MOVBQZXload [i+1] {s} p mem))) -> @v.Args[0].Block (MOVWload [i] {s} p mem)
```

*   **`@v.Args[0].Block`**: これは、新しく生成される`MOVWload`命令を、元の`ORW`命令の最初の引数（`MOVBQZXload [i] {s} p mem`）が属するSSAブロックに挿入することを指示しています。これにより、「Add the new load into the right block where we know that mem is live.」というコミットメッセージの意図が実現されます。メモリのライブネスが保証されるブロックに命令を配置することで、最適化の安全性が確保されます。
*   **`(MOVWload [i] {s} p mem)`**: `MOVWload`命令が直接`i`を`auxInt`フィールドとして、`s`を`Aux`フィールドとして持つようになりました。これにより、明示的な`ADDQconst`命令が不要になり、「Use auxInt field to carry i along instead of an explicit ADDQ.」という最適化が達成されます。命令数が減り、中間表現がより簡潔になります。

`rewriteAMD64.go`内の対応する`rewriteValueAMD64_OpAMD64ORW`などの関数も、この新しいルールに合わせて修正されています。具体的には、新しいロード命令を生成する際に、`v.AuxInt`と`v.Aux`に直接オフセットとシンボルを設定し、`v.reset(OpCopy)`と`v.AddArg(v0)`を使って元の`OR`命令を新しいロード命令に置き換えるロジックが追加されています。

### 3. テストケースの追加

`src/cmd/compile/internal/gc/testdata/arith_ssa.go`には、`testLoadSymCombine()`という新しいテスト関数が追加されました。この関数は、グローバルなバイト配列`loadSymData`から`uint16`, `uint32`, `uint64`の値をロードし、それらが正しく結合されるかを検証します。これは、特に「Make sure symbol gets carried along by load-combining rule.」というコミットの目的を検証するためのものです。シンボル（`loadSymData`）が絡むロード結合が正しく機能するかを確認します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/testdata/arith_ssa.go`

*   **`loadSymData`配列**: `var loadSymData = [...]byte{...}`として、グローバルなバイト配列が定義されています。これは、シンボルが絡むロード結合のテストケースのデータソースとなります。
*   **`testLoadSymCombine()`関数**:
    *   この関数は、`loadSymData`配列の要素を個別にロードし、ビットシフトとOR演算を組み合わせて`uint16`, `uint32`, `uint64`の値を再構築しています。
    *   例えば、`uint16(loadSymData[0]) | uint16(loadSymData[1])<<8`は、リトルエンディアン形式で2バイトを結合して16ビット整数を生成する典型的なパターンです。
    *   このパターンは、コンパイラが複数のバイトロードを単一のワードロードに結合できるかどうかをテストするために設計されています。特に、`loadSymData`がグローバルシンボルであるため、シンボル情報がロード結合の過程で正しく伝達されるかどうかが重要になります。
    *   期待値`w2`, `w4`, `w8`と計算結果`g2`, `g4`, `g8`を比較し、不一致があれば`failed`フラグを立ててエラーメッセージを出力します。
*   **`main()`関数**: `testLoadSymCombine()`が`main()`から呼び出されるように追加され、テストスイートの一部として実行されるようになっています。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

このファイルは、GoコンパイラのSSAバックエンドが使用する命令書き換えルールを定義しています。

*   **`LEA`とロード命令の結合ルール**:
    *   `MOVBQZXload`, `MOVWQZXload`, `MOVLQZXload`, `MOVBQSXload`, `MOVWQSXload`, `MOVLQSXload`といった様々なサイズのロード命令と、`LEAQ`命令の組み合わせに対する新しいルールが追加されています。
    *   これらのルールは、`LEAQ`が計算したアドレス（ベースアドレス + オフセット + シンボル）を、ロード命令自身のオフセットとシンボルに統合します。
    *   `canMergeSym(sym1, sym2)`と`mergeSym(sym1, sym2)`というヘルパー関数が使われており、これは複数のシンボルが安全に結合できるかどうかのチェックと、実際に結合を行うためのものです。これにより、シンボル情報が正しく伝達されることが保証されます。
*   **複数バイトロード結合ルールの変更**:
    *   `ORW`, `ORL`, `ORQ`命令の書き換えルールが修正されています。
    *   変更の最も重要な点は、結果のロード命令（`MOVWload`, `MOVLload`, `MOVQload`）が、明示的な`ADDQconst`命令ではなく、`[i]`（`auxInt`フィールド）と`{s}`（`Aux`フィールド）を使ってオフセットとシンボルを直接持つようになったことです。
    *   さらに、`@v.Args[0].Block`のような構文が導入され、新しく生成されるロード命令が、元の命令の引数が属するSSAブロックに配置されるように指定されています。これは、メモリのライブネスを考慮し、最適化の安全性を高めるための重要な変更です。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`

このファイルは、`AMD64.rules`で定義されたルールに基づいて、実際にSSA `Value`を書き換えるGoコードを生成します。

*   **新しい`_load`関数の追加**:
    *   `OpAMD64MOVBQSXload`, `OpAMD64MOVBQZXload`など、`LEA`と結合されるロード命令に対応する`rewriteValueAMD64_OpAMD64...load`関数が追加されています。
    *   これらの関数は、入力`Value`が`LEA`命令を引数に持つロード命令のパターンにマッチするかどうかをチェックします。
    *   マッチした場合、`v.reset(...)`を使って`Value`のオペレーションを新しい最適化されたロード命令に設定し、`v.AuxInt`と`v.Aux`に結合されたオフセットとシンボルを設定します。
    *   `v.AddArg(base)`と`v.AddArg(mem)`で、新しいロード命令の引数（ベースアドレスとメモリ状態）を追加します。
*   **既存の`OR`関数の修正**:
    *   `rewriteValueAMD64_OpAMD64ORL`, `rewriteValueAMD64_OpAMD64ORQ`, `rewriteValueAMD64_OpAMD64ORW`関数が修正されています。
    *   これらの関数は、複数のバイトロードとシフト・OR操作のパターンにマッチした場合、新しい`MOVLload`, `MOVQload`, `MOVWload`命令を生成します。
    *   重要な変更は、新しいロード命令を生成する際に、`b = v.Args[0].Args[0].Args[0].Block`のように、元の命令の引数から適切なSSAブロックを取得し、そのブロックに新しいロード命令を挿入するようにしている点です。
    *   また、`v0.AuxInt = i`と`v0.Aux = s`を使って、オフセット`i`とシンボル`s`を新しいロード命令の`AuxInt`と`Aux`フィールドに直接設定しています。
    *   最後に、`v.reset(OpCopy)`と`v.AddArg(v0)`を使って、元の複雑なOR操作を、新しく生成された単一のロード命令に置き換えています。`OpCopy`は、単に引数の値をコピーする命令であり、実質的に元のOR操作が最適化されたロード命令に置き換えられたことを意味します。

これらの変更により、Goコンパイラは、メモリからのデータロードをより効率的に行い、生成される機械語コードの品質と実行性能を向上させることができます。特に、アドレス計算の最適化と、複数バイトのロード結合が強化されています。

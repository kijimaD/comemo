# [インデックス 24626] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるAMD64アーキテクチャ向けの8ビット整数乗算 (`Mul8`) の処理を改善するものです。具体的には、`Mul8` の定数畳み込みが正しく行われるように、SSAオペレーションとリライトルールが修正・追加されています。

変更されたファイルは以下の通りです。

*   `src/cmd/compile/internal/gc/ssa.go`: SSA値の生成に関連する部分で、新しいAMD64乗算オペレーションが追加されています。
*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: SSAオペレーションをAMD64アセンブリ命令に変換するためのルールファイルで、`Mul8` の変換と `MULBconst` の定数畳み込みルールが更新されています。
*   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`: AMD64アーキテクチャ固有のSSAオペレーションの定義ファイルで、`MULB` および `MULBconst` オペレーションが追加されています。
*   `src/cmd/compile/internal/ssa/opGen.go`: SSAオペレーションの定義とレジスタ割り当て情報を生成するファイルで、`OpAMD64MULB` と `OpAMD64MULBconst` が追加されています。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: SSA値を最適化するためのリライトルールが記述されており、`OpAMD64MULB` と `OpAMD64MULBconst` の定数畳み込みに関する新しいルールが追加されています。

## 変更の背景

GoコンパイラのSSAバックエンドにおいて、8ビット整数 (`int8`) の乗算 (`Mul8`) が正しく最適化されないという問題がありました。具体的には、`Mul8` オペレーションが中間表現の段階で16ビット整数乗算 (`MULW`) に変換されていました。この変換自体は、AMD64アーキテクチャの8ビット乗算命令 (`IMULB`) が持つレジスタ制約（`AL` レジスタに限定されるなど）を避けるための一般的な最適化戦略の一部でした。`IMULW` (16ビット乗算) はより柔軟なレジスタを使用できるため、コード生成が容易になるという利点があります。

しかし、この `Mul8` から `MULW` への変換が行われた後、コンパイラの「定数畳み込み (Constant Folding)」ルールが、元のオペランドが `int8` であるという情報を失ってしまっていました。定数畳み込みは、コンパイル時に定数オペランドを持つ式を評価し、その結果を直接コードに埋め込む最適化手法です。例えば、`5 * 3` は `15` に畳み込まれます。

`int8` の乗算結果は `int8` の範囲（-128から127）に収まるべきですが、`MULW` として扱われると、結果が `int16` の範囲で計算されてしまい、その後の処理で `int8` にキャストされる際に予期せぬ値の切り詰め（オーバーフロー）が発生する可能性がありました。定数畳み込みの段階でこの `int8` のセマンティクスが考慮されないため、誤った定数結果が生成される恐れがあったのです。

このコミットは、この問題を解決し、`int8` の乗算がSSAバックエンドで正しく扱われ、適切な定数畳み込みが行われるようにするために導入されました。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要なのが、中間表現 (IR: Intermediate Representation) の一つであるSSA (Static Single Assignment) 形式です。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるように変換された形式です。これにより、データフロー解析や最適化が非常に容易になります。Goコンパイラでは、AST (Abstract Syntax Tree) からSSA形式に変換され、様々な最適化パスが適用された後、最終的に機械語に変換されます。

### 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイラ最適化の一種です。

*   **目的**: プログラムの実行時に計算される定数式を、コンパイル時に評価してその結果に置き換えることで、実行時のオーバーヘッドを削減し、コードを高速化します。
*   **例**: `a = 10 * 5 + 2;` というコードがあった場合、コンパイラは `10 * 5 + 2` を `52` と計算し、`a = 52;` に置き換えます。

### AMD64アーキテクチャの乗算命令

AMD64 (x86-64) アーキテクチャには、様々なサイズの整数乗算命令があります。

*   **`IMUL` 命令**: 符号付き整数乗算命令です。オペランドのサイズによって `IMULB` (8ビット), `IMULW` (16ビット), `IMULL` (32ビット), `IMULQ` (64ビット) などがあります。
    *   **`IMULB` (8ビット乗算)**: `AL` レジスタの内容とオペランドを乗算し、結果を `AX` レジスタ（16ビット）に格納します。この命令は `AL` レジスタに依存するため、汎用レジスタを自由に使うSSAバックエンドでは扱いにくい場合があります。
    *   **`IMULW` (16ビット乗算)**: `AX` レジスタの内容とオペランドを乗算し、結果の上位16ビットを `DX`、下位16ビットを `AX` に格納する形式と、オペランドを一つ取り、そのオペランドとレジスタを乗算して結果をレジスタに格納する形式（`IMUL r/m16, imm16` や `IMUL r16, r/m16, imm16` など）があります。後者の形式は、より柔軟なレジスタ選択が可能です。

### Goの型システムとSSAの型

Go言語は厳格な型システムを持っています。`int8` 型は-128から127の範囲の整数を表します。SSAバックエンドでは、Goの型情報がSSAオペレーションの型として引き継がれ、最適化の過程でこの型セマンティクスが維持されることが重要です。特に定数畳み込みにおいては、結果が元の型の範囲に収まるように注意深く処理される必要があります。

## 技術的詳細

このコミットの核心は、`Mul8` オペレーションが `int8` のセマンティクスを保持したまま、SSAバックエンドで正しく処理されるようにすることです。

### 問題点の再確認

以前のGoコンパイラでは、`Mul8` (8ビット乗算) はSSAのルールファイル (`AMD64.rules`) で `MULW` (16ビット乗算) に変換されていました。これは、`IMULB` 命令のレジスタ制約（`AL` レジスタの使用）を避けるための一種の「昇格」でした。しかし、この昇格により、定数畳み込みのロジックがオペランドが `int8` であるという事実を見落としていました。

例えば、`int8(10) * int8(20)` という式があった場合、これは `int8(200)` となりますが、`int8` の最大値は `127` なので、オーバーフローして `int8(-56)` となるべきです。しかし、`MULW` として処理されると、定数畳み込みは `int16(10) * int16(20) = int16(200)` と計算し、結果として `200` が生成されてしまう可能性がありました。この `200` が後で `int8` にキャストされると、正しい `int8(-56)` になるかもしれませんが、定数畳み込みの段階で既に誤った中間結果が生成されていることは、最適化の正確性を損ないます。

### 解決策

このコミットでは、以下の変更によって問題を解決しています。

1.  **新しいSSAオペレーションの導入**: `OpAMD64MULB` (8ビット乗算) と `OpAMD64MULBconst` (8ビット定数乗算) という新しいSSAオペレーションが導入されました。これにより、SSA形式の段階で8ビット乗算であることが明示的に表現できるようになります。
2.  **`Mul8` の変換ルールの変更**: `src/cmd/compile/internal/ssa/gen/AMD64.rules` において、`Mul8 x y` は `MULW x y` ではなく `MULB x y` に変換されるように変更されました。これにより、8ビット乗算はSSAバックエンドの早い段階から8ビット乗算として扱われます。
3.  **`MULB` および `MULBconst` のリライトルールと定数畳み込みの追加**: `src/cmd/compile/internal/ssa/rewriteAMD64.go` に、`OpAMD64MULB` と `OpAMD64MULBconst` のためのリライトルールが追加されました。特に `(MULBconst [c] (MOVBconst [d])) -> (MOVBconst [c*d])` というルールは、8ビット定数乗算の定数畳み込みを正確に行うためのものです。ここで `c*d` の結果は、`int8` の範囲で計算されることが期待されます。
4.  **`MULB` のアセンブリ命令**: 注目すべきは、`src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go` で `MULB` オペレーションが定義される際に、依然として `x86.AIMULW` (16ビットのIMUL命令) が使用されている点です。これは、前述の通り `IMULB` が持つレジスタ制約が厳しいため、SSAバックエンドで汎用的に扱うのが難しいことに起因します。
    *   重要なのは、SSAの抽象レベルでは `MULB` という8ビット乗算として扱われることで、型情報が正しく伝達され、定数畳み込みが `int8` のセマンティクスに基づいて行われるようになった点です。
    *   実際のコード生成では `IMULW` が使われるとしても、SSAの最適化パス（特に定数畳み込み）は `MULB` オペレーションの型情報に基づいて動作するため、結果の正確性が保証されます。`IMULW` は16ビットの結果を生成しますが、その結果が `int8` の範囲に収まるように、あるいはオーバーフローを考慮した上で、SSAの型システムが適切に処理します。

この変更により、Goコンパイラは `int8` の乗算をより正確に最適化できるようになり、特に定数畳み込みにおいて、Go言語の型セマンティクスに沿った正しい結果を生成するようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルは、GoのSSA中間表現のオペレーションを、特定のアーキテクチャ（ここではAMD64）のより低レベルなSSAオペレーションやアセンブリ命令に変換するためのルールを定義しています。

*   **`Mul8 x y) -> (MULW x y)` から `(Mul8 x y) -> (MULB x y)` への変更**:
    *   これはこのコミットの最も直接的な変更点です。以前は、Goの `Mul8` オペレーション（8ビット乗算）が、AMD64のSSAバックエンドでは `MULW`（16ビット乗算）に変換されていました。コメントにもあるように、これは `IMULB` 命令のレジスタ制約を避けるためでした。
    *   しかし、この変更により、`Mul8` は `MULB` という新しい8ビット乗算SSAオペレーションに直接変換されるようになります。これにより、SSAの型システムが8ビット乗算であることを認識し、その後の最適化（特に定数畳み込み）で `int8` のセマンティクスを正しく扱えるようになります。
*   **`MULBconst` の定数畳み込みルールの追加**:
    *   ` (MULB x (MOVBconst [c])) -> (MULBconst [c] x)` と `(MULB (MOVBconst [c]) x) -> (MULBconst [c] x)` は、`MULB` オペレーションの一方のオペランドが定数 (`MOVBconst`) である場合に、それを `MULBconst` オペレーションに変換するルールです。これにより、定数乗算が明示的なオペレーションとして扱われ、次のルールで定数畳み込みが可能になります。
    *   `(MULBconst [c] (MOVBconst [d])) -> (MOVBconst [c*d])` は、両方のオペランドが定数である `MULBconst` オペレーションを、その乗算結果である単一の定数 (`MOVBconst`) に畳み込むルールです。この `c*d` の計算は、SSAの型システムによって `int8` の範囲で正しく行われることが期待されます。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

このファイルには、SSAグラフを最適化するためのリライトルールが記述されています。これらのルールは、特定のパターンにマッチするSSAオペレーションを、より効率的なオペレーションや定数に置き換えるために使用されます。

*   **`OpAMD64MULB` のリライトルール**:
    *   ` (MULB x (MOVBconst [c]))` と `(MULB (MOVBconst [c]) x)` のパターンを `(MULBconst [c] x)` にリライトするルールが追加されています。これは `AMD64.rules` で定義された変換と連携し、定数オペランドを持つ `MULB` を `MULBconst` に変換することで、定数畳み込みの準備をします。
*   **`OpAMD64MULBconst` の定数畳み込みルール**:
    *   ` (MULBconst [c] (MOVBconst [d]))` のパターンを `(MOVBconst [c*d])` にリライトするルールが追加されています。これは、両方のオペランドが定数である8ビット乗算を、コンパイル時に計算された単一の8ビット定数に置き換えるためのものです。この `c*d` の計算は、Goの `int8` 型のセマンティクス（オーバーフロー挙動など）を考慮して行われるため、正確な定数畳み込みが実現されます。

これらの変更により、GoコンパイラのSSAバックエンドは、8ビット整数乗算をより正確に認識し、Go言語の型システムに準拠した形で定数畳み込みを含む最適化を適用できるようになりました。これにより、生成されるコードの正確性と効率が向上します。

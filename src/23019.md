## 元コミット内容

このコミットは、`net/http` パッケージの `Transport` における以下の問題点を修正します。

*   **データ競合 (data race)**: `Transport` の内部状態を管理する際に発生する可能性のある競合状態を解消します。
*   **二重キャンセル時のパニック (double cancel panic)**: `Transport.CancelRequest` が同じリクエストに対して複数回呼び出された場合に発生するパニックを防止します。
*   **キャンセル時のエラーメッセージ (cancel error message)**: リクエストがキャンセルされた際に返されるエラーメッセージをより明確にし、アプリケーションがキャンセル状態を適切に識別できるようにします。
*   **ゴルーチンリーク (goroutine leak)**: `Transport` の接続管理に関連するゴルーチンリークの可能性を修正します。

これらの修正は、GoのHTTPクライアントの安定性と信頼性を向上させることを目的としています。

## 変更の背景

このコミットは、`net/http` パッケージの `Transport` コンポーネントが抱えていた複数の既知の課題に対処するために行われました。

1.  **データ競合**: `net/http.Transport` は複数のゴルーチンから安全に利用できるように設計されていますが、内部状態の不適切な同期はデータ競合を引き起こす可能性があります。特に、リクエストのキャンセル処理やアイドル接続の管理において、共有リソースへの同時アクセスが問題となることがありました。データ競合は予測不能な動作やクラッシュの原因となるため、その修正はシステムの安定性にとって不可欠です。

2.  **二重キャンセル時のパニック**: `Transport.CancelRequest` メソッドは、進行中のHTTPリクエストをキャンセルするために使用されます。しかし、同じリクエストに対してこのメソッドが複数回呼び出された場合、内部状態の不整合によりパニックが発生する可能性がありました。これは、特にタイムアウトやユーザーによる明示的なキャンセルが同時に発生するようなシナリオで問題となります。

3.  **キャンセル時のエラーメッセージの不明瞭さ**: リクエストがキャンセルされた際に `net/http` パッケージが返すエラーは、その原因が「キャンセル」であると明確に示されない場合がありました。これにより、アプリケーション側でエラーハンドリングを行う際に、キャンセルによるものなのか、それともネットワークエラーやサーバーエラーによるものなのかを区別することが困難でした。明確なエラーメッセージは、デバッグの容易さと適切なエラー回復処理の実装に寄与します。

4.  **ゴルーチンリーク**: `net/http.Transport` は、HTTP接続の再利用と管理のために内部的にゴルーチンを使用します。特に `persistConn` の `readLoop` や `writeLoop` といったゴルーチンは、接続が適切にクローズされない場合にリークする可能性があります。ゴルーチンリークは、時間の経過とともにメモリ使用量が増加し、最終的にはシステムリソースの枯渇やアプリケーションのパフォーマンス低下を引き起こすため、重要な問題でした。

これらの問題は、GoのHTTPクライアントを大規模なアプリケーションや高負荷なサービスで使用する際に、安定性やリソース効率に直接影響を与えるため、優先的に修正されるべき課題でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語および `net/http` パッケージに関する前提知識が必要です。

1.  **`net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
    *   **`http.Client`**: HTTPリクエストを行うための高レベルなインターフェースを提供します。通常、アプリケーションではこのクライアントインスタンスを再利用します。
    *   **`http.Transport`**: `http.Client` の内部で実際にHTTPリクエストを送信し、接続を管理する低レベルなコンポーネントです。接続の再利用（Keep-Alive）、プロキシ、TLS設定などを担当します。
    *   **`http.Request` と `http.Response`**: HTTPリクエストとレスポンスを表す構造体です。

2.  **ゴルーチン (Goroutines)**: Go言語の軽量な並行処理単位です。OSのスレッドよりもはるかに軽量で、数千、数万のゴルーチンを同時に実行できます。`net/http.Transport` は、各HTTP接続の読み書きを処理するために内部的にゴルーチンを使用します（例: `readLoop`, `writeLoop`）。

3.  **チャネル (Channels)**: ゴルーチン間でデータを安全に送受信するためのGo言語のプリミティブです。チャネルを使用することで、共有メモリを直接操作することなく、ゴルーチン間の同期と通信を実現し、データ競合を防ぐことができます。

4.  **データ競合 (Data Race)**: 複数のゴルーチンが同時に同じメモリ位置にアクセスし、そのうち少なくとも1つが書き込み操作であり、かつアクセスが同期されていない場合に発生するバグです。データ競合はGoのレース検出器 (`go run -race`) で検出できます。

5.  **`sync.Mutex`**: 相互排他ロックを提供し、共有リソースへのアクセスを同期するためのGo言語のプリミティブです。`Lock()` と `Unlock()` メソッドを使用して、クリティカルセクションを保護します。

6.  **`io.ReadCloser`**: `io.Reader` と `io.Closer` インターフェースを組み合わせたものです。HTTPレスポンスボディ (`resp.Body`) は `io.ReadCloser` 型であり、読み取り後に必ず `Close()` メソッドを呼び出してリソースを解放する必要があります。これを怠ると、ゴルーチンリークや接続リークの原因となります。

7.  **`bufio.Reader.Peek`**: `bufio.Reader` のメソッドで、ストリームからバイトを読み進めることなく、次のNバイトを覗き見ることができます。これは、HTTPレスポンスのヘッダーを解析する際などに使用されます。

8.  **`context.Context` (間接的に関連)**: このコミット自体は `context.Context` を直接変更していませんが、`CancelRequest` の機能は `context.WithCancel` などと密接に関連しています。`context.Context` は、API境界を越えてデッドライン、キャンセルシグナル、その他のリクエストスコープの値を伝播するための標準的な方法です。

これらの概念を理解することで、コミットがなぜ特定のコード変更を行ったのか、そしてそれが `net/http` パッケージの全体的な動作にどのように影響するかを深く把握できます。

## 技術的詳細

このコミットは、`net/http.Transport` の内部実装に複数の洗練された変更を加えて、前述の課題を解決しています。

1.  **`Transport.CancelRequest` の改善**:
    *   以前は `t.reqCanceler` マップからリクエストを削除する前に `cancel()` を呼び出していました。この順序は、二重キャンセル時のパニックやデータ競合の原因となる可能性がありました。
    *   修正後、`t.reqMu.Lock()` でロックを取得し、`delete(t.reqCanceler, req)` を先に実行してから `cancel()` を呼び出すように変更されました。これにより、同じリクエストに対する二重のキャンセル試行が安全に処理され、マップからの削除が同期的に行われることでデータ競合が防止されます。

2.  **`persistConn` の状態管理の強化**:
    *   `persistConn` 構造体に `canceled bool` フィールドが追加されました。これは、この接続が `CancelRequest` によって明示的にキャンセルされたかどうかを示すフラグです。
    *   `persistConn.cancelRequest()` メソッドが導入され、`pc.lk` ミューテックスで保護された状態で `pc.canceled = true` を設定し、`pc.closeLocked()` を呼び出すようになりました。これにより、接続のキャンセル状態が正確に追跡され、安全にクローズ処理が行われます。
    *   `isCanceled()` メソッドが追加され、接続がキャンセルされたかどうかを安全に確認できるようになりました。

3.  **`persistConn.readLoop` におけるエラーハンドリングとゴルーチンリーク対策**:
    *   `readLoop` は、HTTPレスポンスの読み取りと接続のアイドルプールへの返却を管理する重要なゴルーチンです。
    *   **`eofc` チャネルの導入**: `eofc := make(chan struct{})` が導入され、`defer close(eofc)` でクローズされます。これは、`http.Handler` ゴルーチンが `Response.Body` からEOF（End Of File）で読み取りをブロックするのを解除するために使用されます。これにより、`readLoop` が接続をアイドルプールに戻す処理を完了するまで、ボディの読み取り側が待機できるようになり、競合状態が緩和されます。
    *   **`bodyEOFSignal.fn` の変更**: `resp.Body.(*bodyEOFSignal).fn` のシグネチャが `func(error)` から `func(error) error` に変更されました。これにより、ボディの読み取りが完了した際やエラーが発生した際に、`fn` が新しいエラーを返すことができるようになりました。
    *   **キャンセルエラーの明確化**: `bodyEOFSignal.fn` の中で、`err != nil && pc.isCanceled()` の場合に `errRequestCanceled` を返すロジックが追加されました。これにより、リクエストがキャンセルされたことによるエラーが明確に伝播されるようになります。
    *   **アイドル接続のプールへの返却ロジックの改善**: `waitForBodyRead` チャネルの処理がより堅牢になり、`bodyEOF` の状態や `pc.sawEOF`、`pc.wroteRequest()`、そして `pc.t.putIdleConn(pc)` の呼び出しがより正確に同期されるようになりました。これにより、接続がアイドルプールに適切に返却され、ゴルーチンリークの可能性が低減されます。

4.  **新しいエラー変数 `errRequestCanceled`**:
    *   `var errRequestCanceled = errors.New("net/http: request canceled")` が追加され、リクエストがキャンセルされたことを示す標準的なエラーが提供されました。これにより、アプリケーションはエラー文字列の比較ではなく、このエラー変数との比較によってキャンセル状態を確実に検出できるようになります。

5.  **テストの改善**:
    *   `client_test.go`, `request_test.go`, `serve_test.go`, `npn_test.go` に `defer afterTest(t)` が追加され、テスト後のクリーンアップが強化されました。
    *   `main_test.go` の `goroutineLeaked` 関数が、ゴルーチンリークのチェックを複数回試行するように変更されました。これは、ゴルーチンが完全に終了するまでに時間がかかる場合があるため、テストの不安定性を減らすためのものです。
    *   `transport_test.go` に `TestTransportResponseCancelRace` という新しいテストが追加され、レスポンスキャンセル時の競合状態を具体的にテストするようになりました。また、`TestTransportCancelRequest` では、二重キャンセルがパニックを引き起こさないこと、および `errRequestCanceled` が正しく返されることを検証するようになりました。

これらの変更は、`net/http.Transport` の内部的な複雑な並行処理ロジックをより堅牢にし、HTTPクライアントの信頼性と予測可能性を大幅に向上させています。

## コアとなるコードの解説

このコミットの核となる変更は、`net/http.Transport` のリクエストキャンセル処理と接続管理のロジックを改善し、並行処理における潜在的な問題（データ競合、パニック、ゴルーチンリーク）を解決することにあります。

1.  **`Transport.CancelRequest` の同期強化**:
    *   以前の `CancelRequest` は、`t.reqCanceler` マップからリクエストを削除する前に、実際のリクエストキャンセル処理 (`cancel()`) を呼び出していました。この順序では、`cancel()` 呼び出し中に別のゴルーチンが同じリクエストに対して `CancelRequest` を呼び出すと、マップがまだ更新されていないため、データ競合やパニックが発生する可能性がありました。
    *   修正後は、`t.reqMu.Lock()` で排他ロックを取得し、**まず `delete(t.reqCanceler, req)` でマップからリクエストを削除**します。これにより、マップの整合性が保たれ、二重キャンセル試行が安全に処理されます。その後、ロックを解放してから `cancel()` を呼び出すことで、実際のキャンセル処理が非同期的に行われる場合でも、マップの状態は常に最新に保たれます。

2.  **`persistConn` のキャンセル状態追跡と安全なクローズ**:
    *   `persistConn` は、単一のHTTP/1.x接続を表す内部構造体です。この構造体に `canceled bool` フィールドが追加されたことで、接続自体がキャンセルされた状態にあるかどうかを明確に追跡できるようになりました。
    *   `persistConn.cancelRequest()` メソッドは、この `canceled` フラグを `true` に設定し、`pc.lk` ミューテックスで保護された状態で `pc.closeLocked()` を呼び出します。これにより、接続がキャンセルされたことをマークし、安全にクローズ処理を開始できます。このフラグは、後続の `readLoop` でのエラー処理に利用されます。

3.  **`readLoop` におけるキャンセルエラーの伝播とゴルーチンリーク対策**:
    *   `readLoop` は、`persistConn` に関連付けられたゴルーチンで、ネットワークからのレスポンスボディの読み取りを処理します。
    *   **`eofc` チャネル**: `eofc` チャネルは、`readLoop` がレスポンスボディの読み取りを完了し、接続をアイドルプールに戻す準備ができたことを、レスポンスボディを読み取っている他のゴルーチンに通知するために使用されます。これにより、ボディの読み取り側がEOFに達した際に、`readLoop` が接続をプールに戻す処理をブロックすることなく、スムーズに進行できるようになります。これは、特にボディが非常に小さい場合や、すぐに読み取りが完了する場合に発生しうる競合状態を緩和し、ゴルーチンリークを防ぐのに役立ちます。
    *   **`bodyEOFSignal.fn` の改善**: `resp.Body` は `bodyEOFSignal` という内部ラッパーによってラップされており、ボディの読み取りが完了した際にコールバック関数 `fn` を呼び出します。このコミットでは、`fn` がエラーを返すように変更され、さらに `pc.isCanceled()` をチェックするロジックが追加されました。
        *   もしボディの読み取り中にエラーが発生し、かつその接続が `CancelRequest` によってキャンセルされていた場合、`fn` は新しい `errRequestCanceled` エラーを返します。これにより、アプリケーションは `io.EOF` や他のネットワークエラーと区別して、リクエストがキャンセルされたことを明確に認識できるようになります。
        *   この変更は、`net/http` クライアントがキャンセルされたリクエストに対して、より予測可能で意味のあるエラーを返すことを保証します。
    *   **アイドル接続のプールへの返却ロジック**: `readLoop` 内で、レスポンスボディの読み取りが完了した後、接続をアイドルプールに返却するロジックがより厳密になりました。`waitForBodyRead` チャネルからのシグナルと `bodyEOF` フラグを組み合わせることで、接続が完全にアイドル状態になり、再利用可能であることを確認してからプールに戻すようになりました。これにより、接続が不完全な状態でプールに戻されることによる潜在的な問題やゴルーチンリークが防止されます。

4.  **`errRequestCanceled` の導入**:
    *   `errors.New("net/http: request canceled")` で定義された新しいエラー変数 `errRequestCanceled` は、リクエストがキャンセルされたことを示す標準的なエラーとして機能します。これにより、開発者はエラー文字列の比較という脆弱な方法ではなく、`errors.Is` や `errors.As` を使用して、より堅牢な方法でキャンセルエラーを検出できるようになります。

これらの変更は、Goの `net/http` クライアントが、複雑な並行処理シナリオやエラー条件下でも、より堅牢で信頼性の高い動作をするように設計されています。特に、リクエストのキャンセル処理における競合状態の解消と、明確なエラー伝播は、高パフォーマンスなネットワークアプリケーションを構築する上で非常に重要です。

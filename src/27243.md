# [インデックス 27243] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）中間表現において、各`Value`の使用回数を追跡する機能を追加します。これにより、コンパイラの最適化ルールがより正確になり、特に競合状態（race condition）が存在するコードにおいて、単一のメモリロードが複数回に分割されることによる誤った動作を防ぐことを目的としています。

## 元コミット内容

`cmd/compile: keep value use counts in SSA`

このコミットは、GoコンパイラのSSA（Static Single Assignment）形式において、各`Value`の使用回数を追跡する機能を追加します。`Value.Args`および`Block.Control`における各出現箇所が1回としてカウントされます。

この使用回数は、書き換えルールを制約するために一般的に有用です。例えば、同じインデックス式が何度も使用される場合、インデックス操作をロードにマージするのを防ぎたい場合があります。

しかし、この使用回数が必要とされる特定の用途があります。ロードが複数回使用される場合、操作をロードと結合しないようにする必要があります。そうしないと、単一のロードが複数のロードに分割され、競合状態が存在する場合に認識される動作が損なわれる可能性があります。特に、`sync/mutex.go:Lock`における`m.state`のロードは2回実行できません。（このコミットとは別に、ミューテックスの失敗を引き起こすCLがあります。このコミットには、同様の失敗を示すテストが含まれています。）

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式を使用します。SSA形式では、各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。コンパイラは、このSSA形式に対して様々な最適化パス（例：共通部分式除去 (CSE)、コピー伝播、命令融合など）を適用し、より効率的な機械語コードを生成します。

このコミットの背景には、これらの最適化パスが、特定の条件下でプログラムのセマンティクスを意図せず変更してしまう可能性があったという問題意識があります。特に、メモリからのロード操作（`load`）は、並行処理において非常にデリケートな操作です。Goのメモリモデルでは、特定の条件下でロード操作がアトミックであると保証されますが、コンパイラが最適化によって単一のロードを複数のロードに分割してしまうと、そのアトミック性が失われ、競合状態において予期せぬ結果（例えば、`sync/mutex.go`のような同期プリミティブの誤動作）を引き起こす可能性がありました。

この問題を解決するため、コンパイラは各SSA `Value`がプログラム内で何回使用されているかを正確に把握する必要がありました。これにより、最適化ルールが「ロードが複数回使用されている場合は、そのロードを別の操作と融合しない」といった制約を適用できるようになります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式の主要な特性は以下の通りです。

*   **単一代入**: 各変数はプログラム内で一度だけ代入されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi function)**: 複数の制御フローパスが合流する点（例：`if-else`文の終わりやループの合流点）で、同じ変数に異なる値が代入される可能性がある場合、SSA形式ではΦ関数が導入されます。Φ関数は、どのパスから来たかに応じて適切な値を選択します。

SSA形式は、共通部分式除去 (CSE)、デッドコード削除、レジスタ割り当てなど、多くの強力な最適化を可能にします。

### 2. GoコンパイラのSSAバックエンド

Goコンパイラは、Goソースコードを抽象構文木（AST）に変換した後、SSA形式に変換し、様々な最適化パスを適用してから最終的な機械語コードを生成します。`src/cmd/compile/internal/ssa`ディレクトリには、このSSAバックエンドの実装が含まれています。

*   **`Value`**: SSA形式における基本的な計算単位です。オペレーション（`Op`）、型（`Type`）、引数（`Args`）、補助情報（`Aux`, `AuxInt`）などを含みます。例えば、`Add`、`Load`、`Store`などが`Value`として表現されます。
*   **`Block`**: 制御フローグラフ（CFG）の基本的な構成要素であり、SSA `Value`のシーケンスを含みます。`Block`は、条件分岐（`BlockIf`）、ループ（`BlockLoop`）、関数呼び出し（`BlockCall`）などの種類があります。
*   **`Block.Control`**: `Block`の制御フローを決定する`Value`です。例えば、`BlockIf`の場合、条件式の結果を保持する`Value`が`Control`となります。

### 3. 競合状態 (Race Condition) とアトミック操作

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスし、そのアクセス順序によってプログラムの最終結果が変化する可能性がある状態を指します。これは、並行プログラミングにおける一般的なバグの原因となります。

アトミック操作は、不可分（indivisible）な操作であり、他のゴルーチンから見て、その操作が完全に実行されるか、全く実行されないかのどちらかであるように見えます。これにより、競合状態を防ぎ、共有データの整合性を保つことができます。Go言語では、`sync/atomic`パッケージがアトミック操作を提供します。

メモリからのロード操作は、通常はアトミックであると期待されますが、コンパイラが最適化によってロードを分割してしまうと、その期待が裏切られる可能性があります。例えば、64ビットの値をロードする際に、コンパイラがそれを2つの32ビットロードに分割した場合、その間に別のゴルーチンが値を変更すると、古い32ビットと新しい32ビットが混ざった不正な値が読み取られる可能性があります。

### 4. `sync/mutex.go:Lock` の例

Goの標準ライブラリにある`sync.Mutex`は、排他制御を提供するための基本的な同期プリミティブです。`Lock`メソッドの内部では、ミューテックスの状態を表す変数をメモリからロードする操作が行われます。このロード操作がアトミックでない場合、複数のゴルーチンが同時に`Lock`を試みた際に、ミューテックスの状態が正しく更新されず、デッドロックや不正なロック取得が発生する可能性があります。

## 技術的詳細

このコミットの主要な変更点は、SSA形式の`Value`構造体に`Uses`フィールド（`int32`型）を追加し、その`Value`がプログラム内で何回使用されているかを追跡することです。

具体的には、以下の箇所で`Uses`カウントが更新されます。

1.  **`Value.Args`**: ある`Value`が別の`Value`の引数として使用される場合、引数となる`Value`の`Uses`カウントが増加します。
2.  **`Block.Control`**: `Block`の制御`Value`として設定される場合、その`Value`の`Uses`カウントが増加します。

この`Uses`カウントは、SSAグラフの構築時および最適化パスの実行中に動的に更新されます。

### `Block.SetControl` メソッドの導入

`Block`の`Control`フィールドを直接設定する代わりに、`SetControl`という新しいメソッドが導入されました。このメソッドは、`Control`が変更される際に、古い`Control`の`Uses`カウントをデクリメントし、新しい`Control`の`Uses`カウントをインクリメントする責任を持ちます。これにより、`Uses`カウントの整合性が保たれます。

### `Value`の引数操作の変更

`Value`の引数を追加、設定、削除するメソッド（`AddArg`, `SetArg`, `RemoveArg`）も変更され、対応する`Value`の`Uses`カウントが適切に増減するように修正されました。

### `check.go` における使用回数の検証

デバッグビルドやテスト時に、`checkFunc`関数内で`Uses`カウントの整合性を検証するロジックが追加されました。これにより、SSAグラフの構築後に実際に計算された使用回数と、`Value.Uses`フィールドに格納されている値が一致するかどうかを確認し、バグの早期発見に役立てます。

### 最適化ルールの変更 (`AMD64.rules`)

最も重要な変更の一つは、`src/cmd/compile/internal/ssa/gen/AMD64.rules`ファイルにおける書き換えルールの修正です。特に、`MOVBQSX`（バイトを符号拡張してクワッドワードに移動）、`MOVBQZX`（バイトをゼロ拡張してクワッドワードに移動）などのロード操作を含むルールに、`v.Args[0].Uses == 1`という条件が追加されました。

これは、「ロード操作が他の場所で一度しか使用されていない場合に限り、そのロードを別の操作（例：符号拡張）と融合して、より効率的な単一の命令に変換する」という制約を意味します。もしロードが複数回使用されている場合、この最適化は適用されず、元のロード操作が維持されます。これにより、単一のロードが複数に分割されることによる競合状態のリスクが回避されます。

### `test/atomicload.go` の追加

このコミットには、`test/atomicload.go`という新しいテストファイルが含まれています。このテストは、バイト値をロードし、それを符号拡張およびゼロ拡張した結果が等しいかどうかをチェックする関数`f`を定義しています。メイン関数では、複数のゴルーチンが共有変数`x`を同時に書き換える競合状態を作り出し、`f(&x)`を繰り返し呼び出します。

もしコンパイラが`*p`のロードを複数回に分割し、その間に`x`の値が変更された場合、`a`と`b`が異なる値になり、`f(&x)`が`false`を返すことで`panic("non-atomic load!")`がトリガーされます。このテストは、`Uses`カウントに基づく最適化ルールの変更が、このような競合状態のバグを効果的に防ぐことを検証します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/cmd/compile/internal/ssa/value.go`における`Value`構造体への`Uses`フィールドの追加と、その`Uses`フィールドを管理するための関連メソッドの修正です。

### `src/cmd/compile/internal/ssa/value.go`

```go
type Value struct {
	// ... 既存のフィールド ...
	// Source line number
	Line int32

	// Use count. Each appearance in Value.Args and Block.Control counts once.
	Uses int32

	// Storage for the first three args
	argstorage [3]*Value
}

// Valueの引数を追加する際にUsesをインクリメント
func (v *Value) AddArg(w *Value) {
	// ...
	v.Args = append(v.Args, w)
	w.Uses++ // ここでUsesがインクリメントされる
}

// 複数の引数を追加する際にUsesをインクリメント
func (v *Value) AddArgs(a ...*Value) {
	// ...
	v.Args = append(v.Args, a...)
	for _, x := range a {
		x.Uses++ // ここでUsesがインクリメントされる
	}
}

// Valueの引数を設定する際にUsesを更新
func (v *Value) SetArg(i int, w *Value) {
	v.Args[i].Uses-- // 古い引数のUsesをデクリメント
	v.Args[i] = w
	w.Uses++ // 新しい引数のUsesをインクリメント
}

// Valueの引数を削除する際にUsesをデクリメント
func (v *Value) RemoveArg(i int) {
	v.Args[i].Uses-- // 削除される引数のUsesをデクリメント
	// ...
}

// 引数をリセットする際にUsesをデクリメント
func (v *Value) resetArgs() {
	for _, a := range v.Args {
		a.Uses-- // 各引数のUsesをデクリメント
	}
	// ...
}
```

### `src/cmd/compile/internal/ssa/block.go`

`Block`の`Control`フィールドを安全に設定するためのヘルパーメソッド`SetControl`が追加されました。

```go
func (b *Block) SetControl(v *Value) {
	if w := b.Control; w != nil {
		w.Uses-- // 古いControl ValueのUsesをデクリメント
	}
	b.Control = v
	if v != nil {
		v.Uses++ // 新しいControl ValueのUsesをインクリメント
	}
}
```

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

AMD64アーキテクチャ向けの書き換えルールに`v.Args[0].Uses == 1`という条件が追加されました。

```
// Make sure we don't combine these ops if the load has another use.
// This prevents a single load from being split into multiple loads
// which then might return different values. See test/atomicload.go.
(MOVBQSX (MOVBload [off] {sym} ptr mem)) && v.Args[0].Uses == 1 -> @v.Args[0].Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)
// ... 他のロード操作にも同様の条件が追加 ...
```

## コアとなるコードの解説

### `Value.Uses` フィールド

`Value`構造体に追加された`Uses int32`フィールドは、その`Value`がSSAグラフ内で何回参照されているかを示すカウンターです。このカウンターは、`Value`が別の`Value`の引数として追加されたり、`Block`の制御`Value`として設定されたりするたびにインクリメントされます。逆に、参照が削除される際にはデクリメントされます。

この`Uses`カウントは、コンパイラの最適化パスにおいて、特定の`Value`が「使い捨て」であるか、それとも複数の場所で利用されているかを判断するための重要な情報となります。

### `Block.SetControl` メソッド

`Block.Control`フィールドは、ブロックの制御フローを決定する`Value`（例えば、条件分岐の条件式）を指します。この`Control`フィールドを直接変更すると、古い`Control Value`の参照が失われ、新しい`Control Value`が参照されることになりますが、`Uses`カウントの更新が漏れる可能性があります。

`SetControl`メソッドは、この問題を解決するために導入されました。このメソッドを使用することで、`Control`が変更される際に、古い`Value`の`Uses`を自動的にデクリメントし、新しい`Value`の`Uses`をインクリメントするようになります。これにより、`Uses`カウントの正確性が保証されます。

### `AMD64.rules` における `v.Args[0].Uses == 1` 条件

`AMD64.rules`ファイルは、GoコンパイラがSSA形式の命令を特定のアーキテクチャ（この場合はAMD64）のより低レベルな命令に書き換えるためのルールを定義しています。

例えば、`MOVBQSX (MOVBload [off] {sym} ptr mem)`というルールは、「メモリからバイトをロードし（`MOVBload`）、その結果を符号拡張してクワッドワードに移動する（`MOVBQSX`）」というSSA命令パターンを、より効率的な単一の命令`MOVBQSXload`に変換しようとします。

しかし、この最適化は、元の`MOVBload`が他の場所でも使用されている場合に問題を引き起こす可能性があります。もし`MOVBload`が複数回使用されているにもかかわらず、このルールが適用されて`MOVBQSXload`に変換されると、元の`MOVBload`が実質的に複製され、複数のロード操作が生成されてしまいます。前述の通り、これは競合状態においてアトミック性を損なう可能性があります。

そこで、`&& v.Args[0].Uses == 1`という条件が追加されました。`v.Args[0]`は`MOVBQSX`の引数であり、この場合は`MOVBload`を指します。この条件は、「`MOVBload`が一度しか使用されていない場合に限り、この書き換えルールを適用する」ことを意味します。これにより、ロードが複数回使用されている場合には最適化が抑制され、単一のロード操作が維持されるため、競合状態における誤動作が防止されます。

この変更は、コンパイラの最適化がプログラムのセマンティクスを尊重し、特に並行処理におけるメモリモデルの保証を維持するために不可欠です。

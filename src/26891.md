## 変更の背景

コミットメッセージに明記されている通り、この変更は「後続のCL（Change List、Goコミュニティにおけるプルリクエストのようなもの）におけるDWARFライターの変更」のために行われました。DWARFは、コンパイルされたプログラムのデバッグ情報を格納するための標準フォーマットです。デバッグ情報を生成する際には、様々なサイズの数値（16ビット、32ビット、64ビットなど）をバイト列として書き出す必要があります。

既存の `Lput`, `Wput`, `Vput` といった関数は、直接出力ストリームに書き込む形式でしたが、DWARFライターのような特定のコンポーネントでは、まずメモリ上のバイトスライスにデバッグ情報を構築し、その後まとめて書き出す方が効率的または構造的に都合が良い場合があります。このため、バイトスライスに直接値をアペンドする新しいユーティリティ関数が必要とされました。これにより、デバッグ情報の生成プロセスがより柔軟になり、パフォーマンスが向上する可能性があります。

## 前提知識の解説

*   **Goリンカ (`cmd/link`)**: Go言語のコンパイラツールチェーンの一部であり、コンパイルされたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合して、実行可能なバイナリファイルや共有ライブラリを生成する役割を担います。リンカは、シンボル解決、再配置、セクションの結合など、低レベルな処理を行います。
*   **DWARF (Debugging With Attributed Record Formats)**: プログラムのソースコードとコンパイル済みバイナリの間のマッピングを記述するための標準化されたデバッグデータフォーマットです。変数名、型情報、関数名、ソースコードの行番号、スタックフレーム情報など、デバッガがプログラムの実行状態を理解し、ユーザーに提示するために必要なあらゆる情報を含みます。DWARFデータは通常、実行可能ファイルの特別なセクションに格納されます。
*   **エンディアン (Endianness)**: マルチバイトのデータをメモリに格納する際のバイト順序を指します。
    *   **リトルエンディアン (Little-endian)**: 最下位バイト (least significant byte) が最も小さいアドレスに格納されます。Intel x86/x64アーキテクチャで広く使われています。
    *   **ビッグエンディアン (Big-endian)**: 最上位バイト (most significant byte) が最も小さいアドレスに格納されます。ネットワークプロトコルや一部のプロセッサ（ARMの一部モード、PowerPCなど）で使われます。
    Goリンカは、ターゲットアーキテクチャに応じて適切なエンディアンでデータを書き込む必要があります。
*   **`ld.Thearch`**: Goリンカの内部構造体 `ld.Arch` のインスタンスで、現在のターゲットアーキテクチャに特化した関数ポインタや設定を保持します。これにより、リンカは異なるCPUアーキテクチャ（amd64, arm, arm64, mips64, ppc64, x86など）に対応できます。`Lput`, `Wput`, `Vput` などは、それぞれ32ビット、16ビット、64ビットの値を書き込むためのアーキテクチャ固有の関数です。

## 技術的詳細

このコミットの主要な技術的変更点は、`ld.Arch` 構造体に新しい3つの関数ポインタ `Append16`, `Append32`, `Append64` を追加し、それらに対応する実装関数 `Append16l`/`Append16b`, `Append32l`/`Append32b`, `Append64l`/`Append64b` を `src/cmd/link/internal/ld/symtab.go` に定義したことです。

これらの新しい `Append` 関数は、既存の `Lput`, `Wput`, `Vput` 関数と似ていますが、重要な違いがあります。
*   既存の `*put` 関数は、グローバルな出力バッファ (`ld.Out`) に直接バイトを書き込むことで、値をエンディアン変換して出力します。
*   新しい `Append*` 関数は、引数として渡されたバイトスライス `b` に値をエンディアン変換して追加し、更新されたバイトスライスを返します。これにより、呼び出し元は任意のバイトスライスにデータを構築できるようになります。

実装を見ると、`Append16l`, `Append32l`, `Append64l` はリトルエンディアン形式で、`Append16b`, `Append32b`, `Append64b` はビッグエンディアン形式でバイトスライスに値をアペンドしています。例えば、`Append16l` は `uint16` の値を `uint8(v)` (下位バイト) と `uint8(v>>8)` (上位バイト) の順で追加し、リトルエンディアンを実現しています。

各アーキテクチャ (`amd64`, `arm`, `arm64`, `mips64`, `ppc64`, `x86`) の `linkarchinit` 関数内で、`ld.Thearch` の新しい `Append16`, `Append32`, `Append64` フィールドに、そのアーキテクチャのデフォルトエンディアンに対応する適切な `Append*l` または `Append*b` 関数が割り当てられています。これにより、リンカはターゲットアーキテクチャのエンディアン規則に従ってデバッグ情報などのデータをバイトスライスに構築できるようになります。

## コアとなるコードの変更箇所

### `src/cmd/link/internal/ld/lib.go`
`ld.Arch` 構造体に以下のフィールドが追加されました。
```go
type Arch struct {
	// ... 既存のフィールド ...
	Lput             func(uint32)
	Wput             func(uint16)
	Vput             func(uint64)
	Append16         func(b []byte, v uint16) []byte // 追加
	Append32         func(b []byte, v uint32) []byte // 追加
	Append64         func(b []byte, v uint64) []byte // 追加
}
```

### `src/cmd/link/internal/ld/symtab.go`
新しいアペンド関数が定義されました。
```go
// リトルエンディアン
func Append16l(b []byte, v uint16) []byte {
	return append(b, uint8(v), uint8(v>>8))
}
func Append32l(b []byte, v uint32) []byte {
	return append(b, uint8(v), uint8(v>>8), uint8(v>>16), uint8(v>>24))
}
func Append64l(b []byte, v uint64) []byte {
	b = Append32l(b, uint32(v))
	b = Append32l(b, uint32(v>>32))
	return b
}

// ビッグエンディアン
func Append16b(b []byte, v uint16) []byte {
	return append(b, uint8(v>>8), uint8(v))
}
func Append32b(b []byte, v uint32) []byte {
	return append(b, uint8(v>>24), uint8(v>>16), uint8(v>>8), uint8(v))
}
func Append64b(b []byte, v uint64) []byte {
	b = Append32b(b, uint32(v>>32))
	b = Append32b(b, uint32(v))
	return b
}
```

### 各アーキテクチャ固有の `obj.go` ファイル (例: `src/cmd/link/internal/amd64/obj.go`)
`linkarchinit` 関数内で、`ld.Thearch` の新しいフィールドに適切な関数が割り当てられました。
```go
func linkarchinit() {
	// ... 既存の初期化 ...
	ld.Thearch.Lput = ld.Lputl
	ld.Thearch.Wput = ld.Wputl
	ld.Thearch.Vput = ld.Vputl
	ld.Thearch.Append16 = ld.Append16l // 追加
	ld.Thearch.Append32 = ld.Append32l // 追加
	ld.Thearch.Append64 = ld.Append64l // 追加
	// ...
}
```
MIPS64やPPC64のように、ビッグエンディアンとリトルエンディアンの両方をサポートするアーキテクチャでは、条件分岐によって適切なエンディアンの `Append*` 関数が割り当てられています。

## コアとなるコードの解説

このコミットの核心は、Goリンカがデバッグ情報やその他のメタデータを生成する際に、バイトスライス (`[]byte`) に直接数値をエンディアンを考慮して追加する機能を提供することです。

*   **`ld.Arch` 構造体の拡張**: `ld.Arch` は、リンカが特定のCPUアーキテクチャで動作するために必要な低レベルな操作（バイトの書き込み、再配置の処理など）を抽象化するためのインターフェースのような役割を果たします。ここに `Append16`, `Append32`, `Append64` という関数ポインタを追加することで、リンカの他の部分がアーキテクチャ固有のエンディアン処理を意識することなく、バイトスライスへの数値の追加操作を呼び出せるようになります。
*   **`Append*l` と `Append*b` 関数の実装**: これらの関数は、Goの組み込み関数 `append` を利用して、与えられた `uint16`, `uint32`, `uint64` の値を、それぞれリトルエンディアン (`l` サフィックス) またはビッグエンディアン (`b` サフィックス) のバイト列に分解し、既存のバイトスライスに追加します。例えば、`Append16l(b, v)` は `v` の下位バイト、次に上位バイトの順で `b` に追加します。これは、Goの `uint` 型がプラットフォームのエンディアンに依存しないため、明示的なビットシフトと型変換によってバイト順序を制御する必要があるためです。
*   **アーキテクチャ固有の初期化**: 各アーキテクチャの `obj.go` ファイルにある `linkarchinit` 関数は、リンカが起動する際にそのアーキテクチャ固有の設定を行う場所です。ここで `ld.Thearch.Append*` に適切なエンディアンの関数を割り当てることで、リンカ全体がターゲットアーキテクチャのバイト順序規則に自動的に従うようになります。これにより、例えばx86/amd64ではリトルエンディアンの `Append*l` が、一部のARMやMIPS64のモードではビッグエンディアンの `Append*b` が使われることになります。

この変更により、特にDWARFデバッグ情報の生成において、デバッグデータをメモリ上で効率的に構築し、その後ファイルに書き出すという二段階のアプローチが可能になります。これは、デバッグ情報の複雑さやサイズを考えると、より柔軟で保守性の高いコード構造に貢献します。

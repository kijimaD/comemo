# [インデックス 23531] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである`cmd/internal/obj`に関連する変更です。具体的には、アセンブリ命令の抽象的な表現である`obj.Prog`構造体から`F3t`フィールドを削除し、それに伴うコードの修正を行っています。影響を受けるファイルは以下の通りです。

*   `src/cmd/internal/obj/link.go`: `obj.Prog`構造体の定義が含まれています。
*   `src/cmd/internal/obj/x86/asm6.go`: x86アーキテクチャ向けのアセンブリコード生成ロジックが含まれており、`F3t`フィールドが使用されていました。

## 変更の背景

このコミットは、Goコンパイラのメモリ効率を改善するための最適化の一環です。`obj.Prog`構造体は、Goコンパイラのバックエンドにおいて、アセンブリ命令を抽象的に表現するための中心的なデータ構造として機能します。コミットメッセージによると、`F3t`フィールドは`obj.Prog`構造体の一部として定義されていましたが、その実態は特定の処理内で一時的に使用される「ローカル変数」のようなものであり、構造体の永続的な状態として保持する必要がありませんでした。

この不要なフィールドを削除することで、`obj.Prog`構造体のサイズが456バイトから448バイトへと8バイト削減されました。このわずかなサイズ削減が重要である理由は、Goランタイムのメモリ割り当てメカニズムにあります。オブジェクトのサイズが小さくなることで、より効率的なメモリ割り当てクラス（malloc class）に収まる可能性が高まります。これにより、メモリの断片化が減少し、ガベージコレクションのオーバーヘッドが軽減され、結果としてコンパイラ全体のメモリ使用量が削減されます。

実際に、この変更により、`rotate`テストのコンパイル時において、コンパイラのメモリ使用量が約2.75%削減されたと報告されています。これは、大規模なGoプログラムのコンパイル時におけるリソース消費を抑え、コンパイラのパフォーマンスを向上させるための、細部にわたる継続的な努力を示しています。

## 前提知識の解説

このコミットを深く理解するためには、Goコンパイラの内部構造、特にコード生成フェーズとメモリ管理に関する以下の概念を把握しておく必要があります。

### Goコンパイラのコード生成パイプライン
Goコンパイラは、ソースコードを最終的な機械語に変換するまでに複数の段階を経ます。
1.  **フロントエンド**: 字句解析、構文解析、型チェックを行い、抽象構文木 (AST) を生成します。
2.  **ミドルエンド**: ASTを、より低レベルで最適化に適した中間表現 (IR) に変換します。Goコンパイラでは、主にSSA (Static Single Assignment) 形式がこの段階で生成されます。
3.  **バックエンド**: SSA形式のIRを、ターゲットアーキテクチャ（例: x86, ARM）固有のアセンブリ命令に変換し、最終的に機械語を生成します。このバックエンドの一部が`cmd/internal/obj`パッケージであり、本コミットが関連する領域です。

### `cmd/internal/obj`パッケージ
`cmd/internal/obj`パッケージは、Goコンパイラのバックエンドにおいて、アセンブラとリンカの共通コードを提供する重要なコンポーネントです。このパッケージは、アーキテクチャに依存しないアセンブリ命令の抽象的な表現を定義し、それを各ターゲットアーキテクチャ（例: `obj/x86`）固有の命令に変換するメカニズムを提供します。これにより、コンパイラは異なるCPUアーキテクチャに対してコードを生成する際の共通基盤を持つことができます。

### `obj.Prog`構造体
`obj.Prog`は "Program" の略で、`cmd/internal/obj`パッケージにおけるアセンブリ命令の基本的な単位を表す構造体です。Goコンパイラのバックエンドでは、SSA形式のIRが`obj.Prog`のリストに変換されます。各`Prog`インスタンスは、単一のアセンブリ命令（例: `MOV`, `ADD`, `CALL`など）またはそれに相当する操作を表現します。

`Prog`構造体には、命令の種類（オペコード）、命令のソースオペランド (`From Addr`)、デスティネーションオペランド (`To Addr`)、そして場合によっては追加のオペランド (`From3 Addr`) など、命令に関する詳細な情報が含まれます。また、これらのオペランドの型情報（レジスタ、メモリ、即値など）を識別するためのフィールドも持ちます。

### `oclass`関数
`oclass`関数は、`cmd/internal/obj`パッケージ内で使用される内部関数であり、特定のオペランド（`obj.Addr`型）の「クラス」または「型」を決定する役割を担います。この「クラス」は、オペランドがレジスタ、メモリ位置、即値（定数）、またはその他のアドレッシングモードのどれに該当するかを識別するためのものです。`oclass`の結果は、アセンブリ命令を機械語にエンコードする際に、どの命令形式やアドレッシングモードを使用すべきかを決定するために不可欠です。例えば、レジスタ間の移動とメモリへの移動では、異なる機械語命令が生成されます。

### Goランタイムのメモリ割り当てとMalloc Class
Goランタイムは、効率的なメモリ管理のために、オブジェクトのサイズに基づいてメモリを異なる「スパン」（メモリブロック）に割り当てます。特に小さなオブジェクトの場合、特定のサイズのメモリ割り当てクラス（malloc class）に分類され、これらのクラスごとに最適化されたアロケータが使用されます。

オブジェクトのサイズが、あるmalloc classの境界をわずかに超える場合、より大きなmalloc classに割り当てられることになります。これは、メモリ使用量の増加だけでなく、メモリの断片化を引き起こし、ガベージコレクションの頻度や実行時間に影響を与える可能性があります。逆に、オブジェクトのサイズを削減してより小さなmalloc classに収めることができれば、メモリ使用効率が向上し、ガベージコレクションのパフォーマンスも改善されることが期待されます。このコミットにおける`obj.Prog`のサイズ削減は、まさにこのメモリ割り当て効率の改善を狙ったものです。

## 技術的詳細

このコミットの技術的な核心は、`obj.Prog`構造体から`F3t`フィールドを削除し、その役割を`doasm`関数内のローカル変数によるオンデマンド計算に置き換えることです。

`obj.Prog`構造体は、アセンブリ命令の抽象的な表現であり、そのフィールドの一つであった`F3t`は、`From3`オペランドの型情報（クラス）を保持していました。`From3`は、一部の命令で必要となる第三のオペランドを指します。

変更前の`src/cmd/internal/obj/x86/asm6.go`の`doasm`関数では、`F3t`フィールドは以下のように使用されていました。

```go
	if p.F3t == 0 {
		p.F3t = uint8(oclass(ctxt, p, &p.From3))
	}
	// ...
	f3t := int(p.F3t) * Ymax
```

このコードは、`p.F3t`がまだ計算されていない場合（初期値の0の場合）、`oclass`関数を呼び出して`p.From3`オペランドの型情報を計算し、その結果を`p.F3t`フィールドに格納していました。その後、`f3t`というローカル変数を`p.F3t`の値から初期化していました。これは、`F3t`の計算結果を`Prog`構造体内にキャッシュするようなパターンに見えます。

しかし、コミットメッセージが指摘するように、`F3t`は`doasm`関数内で一度計算され、すぐに`f3t`ローカル変数にコピーされて使用されるだけで、`Prog`構造体の他の部分や他の関数によって再利用されることがありませんでした。つまり、`F3t`は`Prog`構造体の永続的な状態として保持される必要がなく、`doasm`関数内のスコープに限定された一時的な値であったということです。

この分析に基づき、コミットでは以下の変更が行われました。

1.  **`obj.Prog`からの`F3t`フィールド削除**: `src/cmd/internal/obj/link.go`から`F3t uint8`の定義が削除されました。これにより、`Prog`構造体のサイズが8バイト削減されました。
2.  **`doasm`関数内の`F3t`使用箇所の修正**: `src/cmd/internal/obj/x86/asm6.go`の`doasm`関数では、`p.F3t`へのアクセスが不可能になったため、`f3t`ローカル変数の初期化時に`oclass`関数を直接呼び出すように変更されました。

```go
	// 変更前:
	// if p.F3t == 0 {
	// 	p.F3t = uint8(oclass(ctxt, p, &p.From3))
	// }
	// f3t := int(p.F3t) * Ymax

	// 変更後:
	f3t := oclass(ctxt, p, &p.From3) * Ymax
```

この変更により、`F3t`の計算結果を`Prog`構造体に保存するオーバーヘッドがなくなり、必要なときにその場で計算してローカル変数として使用する「オンデマンド計算」のパターンに移行しました。これにより、`Prog`構造体のメモリフットプリントが削減され、コンパイラのメモリ効率が向上するという具体的なメリットが実現されました。これは、Goコンパイラがパフォーマンスとリソース効率を追求するために、いかに細部にわたる最適化を行っているかを示す良い例です。

## コアとなるコードの解説

### `src/cmd/internal/obj/link.go` の変更点

このファイルでは、Goコンパイラのバックエンドで使用される`Prog`構造体の定義が変更されています。`Prog`構造体は、アセンブリ命令の抽象的な表現であり、命令の種類、オペランド、およびその他のメタデータをカプセル化します。

削除された`F3t uint8`フィールドは、`Prog`構造体の`From3`オペランド（第三のソースオペランド）の型情報（クラス）を格納するために使用されていました。`uint8`型であることから、オペランドのカテゴリ（例: レジスタ、メモリ、即値）を識別するための小さな整数値が格納されていたと推測されます。

このフィールドの削除は、`F3t`が`Prog`構造体の永続的な状態として保持される必要がなく、必要なときにその場で計算できる一時的な値であるという判断に基づいています。これにより、`Prog`構造体のメモリフットプリントが8バイト削減され、コンパイラのメモリ効率向上に貢献します。

### `src/cmd/internal/obj/x86/asm6.go` の変更点

このファイルには、x86アーキテクチャ向けのアセンブリコード生成ロジックが含まれており、特に`doasm`関数が`obj.Prog`インスタンスを具体的なx86アセンブリ命令に変換する役割を担っています。

変更前の`doasm`関数では、`p.F3t`フィールドは以下のように扱われていました。

1.  `if p.F3t == 0 { p.F3t = uint8(oclass(ctxt, p, &p.From3)) }`
    このコードブロックは、`p.F3t`がまだ初期化されていない場合（値が0の場合）、`oclass`関数を呼び出して`p.From3`オペランドの型情報を計算し、その結果を`p.F3t`フィールドに格納していました。これは、`F3t`の値を`Prog`構造体内にキャッシュするような動作です。
2.  `f3t := int(p.F3t) * Ymax`
    その後、`f3t`というローカル変数が`p.F3t`の値を使用して初期化されていました。

変更後のコードでは、`p.F3t`フィールドが`Prog`構造体から削除されたため、上記のような`p.F3t`へのアクセスは不可能になりました。そこで、`f3t`ローカル変数の初期化時に、`oclass`関数を直接呼び出すように修正されました。

```go
	f3t := oclass(ctxt, p, &p.From3) * Ymax
```

この変更により、`F3t`の計算結果を`Prog`構造体に一時的に保存するステップが不要になりました。`oclass(ctxt, p, &p.From3)`の呼び出しは、`f3t`が必要とされるその瞬間に実行され、その結果が直接`f3t`ローカル変数に代入されます。これは、`F3t`が`doasm`関数内でのみ使用され、かつその値が`Prog`構造体の他の部分や他の関数によって再利用されることがないという分析に基づいています。

この「オンデマンド計算」への移行は、`Prog`構造体のサイズを削減し、結果としてGoコンパイラのメモリ使用量を最適化するというコミットの目的を達成するための直接的な手段です。

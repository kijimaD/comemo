## 元コミット内容

このコミットの元の内容は、`net/http`パッケージの`Transport`において、HTTPレスポンスヘッダーのタイムアウト（`ResponseHeaderTimeout`）を設定した場合に、タイマーが適切に停止されずにメモリリークが発生するというバグを修正するものです。具体的には、`time.After`関数を使ってタイマーを作成していた部分が問題でした。

## 変更の背景

Goの`time.After`関数は、指定された期間が経過した後に値が送信されるチャネルを返します。この関数は非常に便利ですが、返されたチャネルが読み取られない場合でも、内部的にはタイマーゴルーチンが起動し、そのチャネルがガベージコレクションされるまでメモリ上に残り続けます。

`net/http/Transport`の文脈では、HTTPリクエストのレスポンスヘッダーを待つ際に`ResponseHeaderTimeout`が設定されていると、このタイマーが使用されます。しかし、レスポンスヘッダーがタイムアウト期間内に受信された場合、タイマーチャネルは読み取られることなく、その後の処理に進んでしまいます。この結果、タイマーに関連するリソース（ゴルーチンとチャネル）が解放されずに残り続け、アプリケーションが長時間稼働するにつれてメモリ使用量が増加するというタイマーリークが発生していました。

この問題は、GitHub Issue #9104として報告されており、このコミットはその問題を解決するために作成されました。

## 前提知識の解説

### Goの`net/http`パッケージと`Transport`について

`net/http`パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
`http.Client`はHTTPリクエストを送信するためのクライアントを提供し、その内部では`http.Transport`が実際のネットワーク通信を担当します。`Transport`は、TCP接続の確立、TLSハンドシェイク、HTTPリクエストの送信、レスポンスの受信、接続の再利用（Keep-Alive）など、低レベルのネットワーク操作を管理します。

`ResponseHeaderTimeout`は`http.Transport`のフィールドの一つで、クライアントがリクエストを送信した後、サーバーからレスポンスヘッダーを受信するまでの最大待機時間を設定します。この時間内にヘッダーが受信されない場合、リクエストはタイムアウトします。

### `time.After`と`time.NewTimer`の違い

Go言語には、時間ベースのイベントを扱うための2つの主要な関数があります。

*   **`time.After(d Duration) <-chan Time`**:
    この関数は、指定された期間`d`が経過した後に現在の時刻を送信する単一のイベントチャネルを返します。これは非常に簡潔で、一度だけ発生するタイムアウトイベントを扱うのに便利です。しかし、前述の通り、返されたチャネルが読み取られない場合でも、内部のタイマーゴルーチンはチャネルがガベージコレクションされるまで実行され続ける可能性があります。これは、短期間の使い捨てタイマーには適していますが、頻繁に生成され、かつ途中でキャンセルされる可能性のあるタイマーには不向きです。

*   **`time.NewTimer(d Duration) *Timer`**:
    この関数は、指定された期間`d`が経過した後に時刻を送信するチャネル（`Timer.C`）を持つ`*Timer`オブジェクトを返します。`*Timer`オブジェクトには、タイマーを明示的に停止するための`Stop()`メソッドがあります。`Stop()`を呼び出すことで、タイマーに関連するリソース（ゴルーチンとチャネル）を即座に解放し、タイマーイベントがチャネルに送信されるのを防ぐことができます。これにより、不要なタイマーがメモリ上に残り続けることを防ぎ、リソースリークを防ぐことができます。

### Goにおけるタイマーリークとは何か

Goにおけるタイマーリークとは、`time.After`や`time.NewTimer`で作成されたタイマーが、その目的を達成した後も適切に停止またはクリーンアップされず、関連するゴルーチンやチャネルがメモリ上に残り続ける現象を指します。これにより、アプリケーションのメモリ使用量が増加し続け、最終的にはパフォーマンスの低下やメモリ不足によるクラッシュを引き起こす可能性があります。

特に、`time.After`は明示的な停止メカニズムがないため、返されたチャネルが読み取られないシナリオ（例：タイムアウトする前に別の条件が満たされた場合）でリークが発生しやすいです。

### `defer`キーワードの役割

`defer`ステートメントは、それが含まれる関数がリターンする直前に、指定された関数呼び出しを実行することを保証します。これは、リソースの解放（ファイルのクローズ、ロックの解除、タイマーの停止など）を確実に行うために非常に便利です。`defer`された関数は、関数の実行が正常に完了した場合でも、パニックが発生した場合でも実行されます。

このコミットでは、`defer timer.Stop()`を使用することで、`WaitResponse`ラベルのブロックを抜ける際に、作成されたタイマーが確実に停止されるようにしています。

## 技術的詳細

このコミットの核心は、`time.After`が持つ潜在的なリソースリークの問題を`time.NewTimer`と`defer timer.Stop()`の組み合わせで解決することにあります。

元のコードでは、`ResponseHeaderTimeout`が設定されている場合、以下のように`time.After`を使用してタイムアウトチャネルを作成していました。

```go
respHeaderTimer = time.After(d)
```

このコードの問題点は、`respHeaderTimer`チャネルがタイムアウトする前にレスポンスヘッダーが受信された場合、`respHeaderTimer`チャネルは決して読み取られません。`time.After`は内部的に新しいゴルーチンを起動し、指定された期間が経過した後にチャネルに値を送信します。このゴルーチンとチャネルは、チャネルがガベージコレクションされるまでメモリ上に残り続けます。HTTPリクエストが頻繁に行われるアプリケーションでは、この未読のタイマーチャネルが多数生成され、メモリリークにつながります。

新しいコードでは、この問題を以下のように解決しています。

```go
timer := time.NewTimer(d)
defer timer.Stop() // prevent leaks
respHeaderTimer = timer.C
```

1.  **`timer := time.NewTimer(d)`**: `time.NewTimer`を呼び出すことで、`*time.Timer`オブジェクトが作成されます。このオブジェクトは、タイマーイベントを送信するチャネル`timer.C`と、タイマーを明示的に停止するための`Stop()`メソッドを持っています。
2.  **`defer timer.Stop() // prevent leaks`**: `defer`キーワードを使用することで、現在の関数（この場合は`WaitResponse`ラベルを含む関数スコープ）が終了する直前に`timer.Stop()`が確実に呼び出されるようにします。これにより、`ResponseHeaderTimeout`が経過する前にレスポンスヘッダーが受信された場合でも、タイマーは明示的に停止され、関連するゴルーチンとチャネルが即座に解放されます。これにより、リソースリークが防止されます。
3.  **`respHeaderTimer = timer.C`**: タイムアウトを監視するためのチャネルとして、`timer.C`が使用されます。これは`time.After`が直接返していたチャネルと同じ役割を果たしますが、`time.NewTimer`によって作成されたタイマーは`Stop()`で管理できる点が異なります。

この変更により、`net/http/Transport`は`ResponseHeaderTimeout`を使用する際に、より効率的にリソースを管理し、メモリリークを防ぐことができるようになりました。

2.  **`defer timer.Stop() // prevent leaks`**: `defer`キーワードを使用することで、現在の関数（この場合は`WaitResponse`ラベルを含む関数スコープ）が終了する直前に`timer.Stop()`が確実に呼び出されるようにします。これにより、`ResponseHeaderTimeout`が経過する前にレスポンスヘッダーが受信された場合でも、タイマーは明示的に停止され、関連するゴルーチンとチャネルが即座に解放されます。これにより、リソースリークが防止されます。
3.  **`respHeaderTimer = timer.C`**: タイムアウトを監視するためのチャネルとして、`timer.C`が使用されます。これは`time.After`が直接返していたチャネルと同じ役割を果たしますが、`time.NewTimer`によって作成されたタイマーは`Stop()`で管理できる点が異なります。

この変更により、`net/http/Transport`は`ResponseHeaderTimeout`を使用する際に、より効率的にリソースを管理し、メモリリークを防ぐことができるようになりました。

変更は`src/net/http/transport.go`ファイルの`WaitResponse`ラベルが付いたブロック内で行われています。

*   **`- respHeaderTimer = time.After(d)`**:
    この行が削除されました。これは、指定された期間`d`（`ResponseHeaderTimeout`の値）が経過した後に値が送信されるチャネルを生成していました。このチャネルが読み取られない場合にタイマーゴルーチンがリークする原因となっていました。

*   **`+ timer := time.NewTimer(d)`**:
    新しく追加された行です。`time.NewTimer`関数を呼び出し、指定された期間`d`で新しい`*time.Timer`オブジェクトを作成しています。このオブジェクトは、タイマーイベントを送信するチャネル（`timer.C`）と、タイマーを明示的に停止するための`Stop()`メソッドを持っています。

*   **`+ defer timer.Stop() // prevent leaks`**:
    新しく追加された行です。`defer`キーワードを使用することで、この関数が終了する際に`timer.Stop()`メソッドが確実に呼び出されるようにしています。これにより、`ResponseHeaderTimeout`が経過する前にレスポンスヘッダーが受信された場合でも、タイマーは明示的に停止され、関連するリソース（ゴルーチンとチャネル）が即座に解放され、メモリリークが防止されます。コメント`// prevent leaks`が、この行の目的を明確に示しています。

    新しく追加された行です。`time.NewTimer`で作成された`timer`オブジェクトのチャネル`C`を`respHeaderTimer`変数に代入しています。これにより、以前の`time.After`が返していたチャネルと同じように、タイムアウトイベントを監視するためのチャネルとして機能します。

これらの変更により、`ResponseHeaderTimeout`が設定された場合でも、タイマーが不要になった際に適切にクリーンアップされるようになり、メモリリークが解消されました。

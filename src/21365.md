# [インデックス 21365] ファイルの概要

このコミットは、Go言語のCGOテストスイートにおける内部ランタイム関数へのアクセス方法を刷新するものです。具体的には、`misc/cgo/test`ディレクトリ内の`backdoor`パッケージを廃止し、Go 1.5で導入された`go:linkname`ディレクティブと、`gccgo`が既にサポートしている`//extern`ディレクティブを用いて、より直接的かつ標準的な方法で`runtime.lockedOSThread`関数にアクセスするように変更しています。

変更されたファイルは以下の通りです。

*   `misc/cgo/test/backdoor.go`: 新規作成されたファイル。旧`backdoor`パッケージの機能を`go:linkname`と`//extern`を用いて再実装しています。
*   `misc/cgo/test/backdoor/backdoor.go`: 削除されたファイル。旧`backdoor`パッケージのGoソースコードです。
*   `misc/cgo/test/backdoor/runtime_gccgo.c`: 削除されたファイル。`gccgo`コンパイラ向けに`runtime.lockedOSThread`を公開するためのC言語ソースコードです。
*   `misc/cgo/test/backdoor/thunk.s`: 削除されたファイル。`gc`コンパイラ向けに`runtime.lockedOSThread`を公開するためのアセンブリサンクです。
*   `misc/cgo/test/callback.go`: 修正されたファイル。旧`backdoor`パッケージのインポートと、それに関連する`lockedOSThread`変数の初期化が削除されています。

## 変更の背景

このコミットの背景には、Go言語の内部テスト、特にCGO関連のテストにおいて、Goランタイムのプライベートな関数（この場合は`runtime.lockedOSThread`）にアクセスするためのよりクリーンで標準的な方法への移行があります。

以前は、Goの主要な2つのコンパイラである`gc`と`gccgo`が、それぞれ異なる「裏口」メカニズムを使用して、テスト目的で`runtime.lockedOSThread`にアクセスしていました。

*   **`gc`コンパイラ向け**: アセンブリ言語で書かれた「サンク（thunk）」と呼ばれる小さなコード片（`thunk.s`）を使用して、`runtime.lockedOSThread`へのジャンプを行っていました。これは、Goの通常の可視性ルールを回避し、プライベートなシンボルにアクセスするためのハック的な手法でした。
*   **`gccgo`コンパイラ向け**: C言語のソースコード（`runtime_gccgo.c`）を介して、`runtime.lockedOSThread`を外部に公開していました。

Go 1.5のリリースに向けて、`gc`コンパイラに`go:linkname`という新しいディレクティブが導入されました。これは、Goのソースコード内で直接、エクスポートされていないシンボルにリンクすることを可能にする機能です。また、`gccgo`は以前から`//extern`というディレクティブをサポートしており、C言語の外部関数をGoコードから直接呼び出すことができました。

これらの新しい、あるいは既存のより適切なメカニズムが利用可能になったことで、従来のコンパイラ固有の「裏口」パッケージ（`backdoor`）を廃止し、より統一された、Goの言語機能に則った方法で内部関数にアクセスすることが可能になりました。これにより、テストコードの複雑性が軽減され、保守性が向上します。

## 前提知識の解説

### CGO

CGOは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。GoとCの間の相互運用を可能にし、既存のCライブラリを利用したり、パフォーマンスが重要な部分をCで記述したりする際に使用されます。CGOを使用すると、Goのビルドプロセス中にCコンパイラが呼び出され、GoとCのコードがリンクされます。

### Goコンパイラ (`gc` と `gccgo`)

Go言語には主に2つのコンパイラ実装があります。

1.  **`gc` (Go Compiler)**:
    *   Goの公式ディストリビューションに含まれる標準のコンパイラです。
    *   Go言語の設計思想に合わせて最適化されており、高速なコンパイルが特徴です。
    *   通常、完全に静的にリンクされたバイナリを生成するため、実行時に外部ライブラリを必要としません。
    *   Go言語の新しい機能は通常、まず`gc`で実装されます。

2.  **`gccgo`**:
    *   GNU Compiler Collection (GCC) のフロントエンドとして実装されたGoコンパイラです。
    *   GCCの強力な最適化機能を活用できるため、生成されるコードの実行速度が`gc`よりも速くなる場合があります。
    *   GCCがサポートする幅広いアーキテクチャとオペレーティングシステムに対応しています。
    *   通常、`libgo`という共有ライブラリに動的にリンクされるため、バイナリサイズが小さくなる可能性がありますが、実行環境に`libgo`が必要になります。

このコミットの時点では、両コンパイラがGoのランタイム内部関数へのアクセスに異なるアプローチを取っていたことが、変更の背景となっています。

### `go:linkname` ディレクティブ

`go:linkname`は、Goの`gc`コンパイラが認識する特殊なビルドディレクティブです。これは、Goの通常の可視性ルール（小文字で始まる識別子はパッケージプライベート）をバイパスし、エクスポートされていない（プライベートな）関数や変数にリンクすることを可能にします。

構文は以下の通りです。
```go
//go:linkname localname importpath.name
```
ここで、`localname`は現在のソースファイルで宣言された関数または変数の名前、`importpath.name`はリンクしたい他のパッケージ内の関数または変数の完全修飾名です（例: `runtime.nanotime`）。このディレクティブを使用するソースファイルは、`unsafe`パッケージをインポートする必要があります。

`go:linkname`は、主にGoの標準ライブラリ内部で、パフォーマンス最適化や、通常のAPIでは公開されていない低レベルのランタイム機能にアクセスするために使用されます。これは強力な機能ですが、Goの型安全性やモジュール性を損なう可能性があり、Goの内部APIはバージョン間で予告なく変更される可能性があるため、互換性の保証はありません。そのため、一般的なアプリケーション開発での使用は推奨されません。

### アセンブリサンク (Assembly Thunk)

アセンブリサンクは、ある関数呼び出しを別の関数呼び出しに「橋渡し」するために使用される、ごく短いアセンブリコードの断片です。これは、異なる呼び出し規約を持つ関数間での呼び出しを調整したり、特定の処理（例えば、ログ記録やセキュリティチェック）を挟んだり、あるいはこのケースのように、通常のリンケージルールではアクセスできないプライベートな関数にアクセスするための「裏口」として機能したりします。

このコミット以前の`gc`コンパイラでは、`runtime.lockedOSThread`のようなGoランタイムのプライベート関数にアクセスするために、アセンブリサンクが用いられていました。これは、Goのソースコードから直接プライベート関数を呼び出すことができないため、アセンブリレベルで直接その関数のアドレスにジャンプさせることで実現していました。

### `//extern` ディレクティブ (gccgo)

`//extern`は、`gccgo`コンパイラがGoコードからC言語の関数を直接呼び出すために使用するディレクティブです。これは、`cgo`の複雑さを伴わずに、シンプルなC関数呼び出しを行うための`gccgo`固有の機能です。

構文は以下の通りです。
```go
//extern CFunctionName
func GoFunctionName(...) ReturnType
```
`//extern`ディレクティブの直後に、Goの関数宣言が続きます。`CFunctionName`はC言語側の関数名、`GoFunctionName`はGoコードから呼び出す際の関数名です。`gccgo`は、このディレクティブを見て、`GoFunctionName`の呼び出しを`CFunctionName`への直接的なC関数呼び出しに変換します。

### `runtime.lockedOSThread`

`runtime.lockedOSThread`は、Goランタイムの内部関数であり、現在のゴルーチンがOSスレッドにロックされているかどうかを示すブール値を返します。Goのゴルーチンは通常、Goランタイムのスケジューラによって複数のOSスレッド間で自由に移動しますが、`runtime.LockOSThread()`関数を呼び出すことで、特定のゴルーチンをそのゴルーチンが現在実行されているOSスレッドに「ロック」することができます。

これは、GUIフレームワーク（例: Cocoa、OpenGL）のように、特定のOSスレッドからのみ呼び出しが許可されるAPIを使用する場合や、スレッドローカルストレージに依存するCライブラリと連携する場合など、スレッドアフィニティが必要な特定のシナリオで重要になります。このコミットでは、CGOのテストにおいて、ゴルーチンがOSスレッドにロックされている状態をテストするために、この内部関数の状態を取得する必要がありました。

## 技術的詳細

このコミットは、GoのCGOテストスイートがGoランタイムの内部関数`runtime.lockedOSThread`にアクセスする方法を、コンパイラ固有の「裏口」から、より標準的でGoの言語機能に統合されたメカニズムへと移行させるものです。

変更前は、`misc/cgo/test/backdoor`という独立したパッケージが存在し、このパッケージが`runtime.lockedOSThread`へのアクセスを提供していました。しかし、その実装はコンパイラに依存していました。

*   **`gc`コンパイラの場合**: `misc/cgo/test/backdoor/thunk.s`というアセンブリファイルが使用されていました。このファイルは、`runtime.lockedOSThread`というプライベートなシンボルに直接ジャンプするアセンブリサンクを提供していました。これは、Goの通常のリンケージルールを回避するための低レベルな手法でした。
*   **`gccgo`コンパイラの場合**: `misc/cgo/test/backdoor/runtime_gccgo.c`というC言語のファイルが使用されていました。このファイルは、C言語の関数として`runtime_lockedOSThread`を定義し、Goコードから呼び出せるようにしていました。

Go 1.5のリリースに伴い、`gc`コンパイラに`go:linkname`ディレクティブが導入されました。このディレクティブは、Goのソースコード内で直接、エクスポートされていないシンボルにリンクすることを可能にします。これにより、アセンブリサンクのような低レベルなハックが不要になります。

また、`gccgo`は以前から`//extern`ディレクティブをサポートしており、GoコードからC言語の関数を直接呼び出すことができました。

このコミットでは、これらのより適切なメカニズムを活用し、`backdoor`パッケージ全体を削除しました。代わりに、`misc/cgo/test/backdoor.go`という新しいファイルが作成され、このファイル内で`go:linkname`と`//extern`の両方を使用して`runtime.lockedOSThread`を宣言しています。

具体的には、`misc/cgo/test/backdoor.go`では、`gc`コンパイラ向けには`go:linkname`を用いて`runtime.lockedOSThread`にリンクし、`gccgo`コンパイラ向けには`//extern`を用いてC言語の`runtime_lockedOSThread`関数にリンクするように記述されています。これにより、コンパイラの種類に関わらず、`cgotest`パッケージから`lockedOSThread()`という統一された関数呼び出しでランタイムの内部状態にアクセスできるようになりました。

この変更により、CGOテストスイートは、コンパイラ固有の複雑な実装詳細から解放され、よりクリーンで保守性の高いコードベースになりました。また、Goの言語機能とコンパイラのサポートするディレクティブを適切に利用することで、内部機能へのアクセス方法が標準化されました。

## コアとなるコードの解説

このコミットの核心は、`misc/cgo/test/backdoor.go`という新しいファイルに集約されています。このファイルは、Goのビルドタグ（`+build`ディレクティブ）を使用せずに、`gc`と`gccgo`の両方のコンパイラに対応する形で`runtime.lockedOSThread`へのアクセスを提供します。

```go
//go:linkname lockedOSThread runtime.lockedOSThread
//extern runtime_lockedOSThread
func lockedOSThread() bool
```

*   **`import _ "unsafe"`**: `go:linkname`ディレクティブを使用する場合、Goのコンパイラは`unsafe`パッケージがインポートされていることを要求します。これは、`go:linkname`がGoの型安全性やカプセル化をバイパスする「unsafe」な操作であることを示唆しています。アンダースコア（`_`）は、パッケージをインポートするものの、そのパッケージ内の識別子を直接使用しないことを意味します。

*   **`//go:linkname lockedOSThread runtime.lockedOSThread`**:
    *   この行は、`gc`コンパイラ向けのディレクティブです。
    *   `cgotest`パッケージ内で宣言されている`lockedOSThread`という関数が、`runtime`パッケージ内の`lockedOSThread`というプライベートなシンボルにリンクされるように指示しています。
    *   これにより、`cgotest`パッケージのコードは、Goランタイムの内部にある`runtime.lockedOSThread`関数を、あたかも自身のパッケージ内で定義されたかのように呼び出すことができるようになります。

*   **`//extern runtime_lockedOSThread`**:
    *   この行は、`gccgo`コンパイラ向けのディレクティブです。
    *   `gccgo`に対して、Goの`lockedOSThread`関数が、C言語のリンケージを持つ`runtime_lockedOSThread`という外部シンボルにマッピングされることを指示しています。
    *   これにより、`gccgo`でコンパイルされた場合、`lockedOSThread()`の呼び出しは、C言語で実装された`runtime_lockedOSThread`関数への直接的な呼び出しに変換されます。

*   **`func lockedOSThread() bool`**:
    *   これは、`cgotest`パッケージ内で実際に呼び出されるGoの関数宣言です。
    *   上記の`go:linkname`と`//extern`ディレクティブによって、この関数はGoランタイムの内部関数`runtime.lockedOSThread`（またはそのC言語版）に「接続」されます。
    *   この関数の本体はGoコードでは定義されていません。その実装は、コンパイラが`go:linkname`または`//extern`ディレクティブに基づいて生成するリンケージによって提供されます。

この変更により、`misc/cgo/test/callback.go`のようなテストファイルは、`./backdoor`パッケージをインポートしたり、`backdoor.LockedOSThread`を介して関数を呼び出したりする必要がなくなりました。代わりに、`cgotest`パッケージ内で直接`lockedOSThread()`を呼び出すだけで、必要なランタイム情報にアクセスできるようになり、コードがより簡潔になりました。

# [インデックス 20716] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおいて、Linuxのユーザー名前空間（User Namespaces）におけるUID（ユーザーID）およびGID（グループID）のマッピングファイル（`/proc/pid/uid_map`および`/proc/pid/gid_map`）のサポートを追加するものです。これにより、Goプログラムからユーザー名前空間をより柔軟に制御し、コンテナ技術などで利用されるIDマッピング機能を活用できるようになります。

## 変更の背景

このコミットの背景には、Linuxカーネルが提供する「ユーザー名前空間（User Namespaces）」の機能があります。ユーザー名前空間は、プロセスが自身のユーザーIDとグループIDのセットを持つことを可能にし、ホストシステムとは異なるIDマッピングを定義できるようにするセキュリティ機能です。これは、特にコンテナ技術（例: Docker、LXC）において、コンテナ内の`root`ユーザーがホストシステム上では非特権ユーザーとして扱われるようにするために不可欠な要素です。

Go言語の`syscall`パッケージは、OSのシステムコールを直接呼び出すための低レベルなインターフェースを提供します。以前のバージョンでは、ユーザー名前空間を作成する`CLONE_NEWUSER`フラグはサポートされていましたが、その名前空間内でUID/GIDのマッピングを定義するメカニズムが不足していました。この不足により、Goプログラムからユーザー名前空間を完全に活用することが困難でした。

コミットメッセージにある「Fixes #8447」は、この機能の欠如がGoのユーザーにとって問題となっていたことを示唆しています。このコミットは、Goプログラムが`/proc/pid/uid_map`および`/proc/pid/gid_map`ファイルを介してUID/GIDマッピングをプログラム的に設定できるようにすることで、この問題を解決し、Goがより高度なコンテナ化やサンドボックス化のシナリオに対応できるようにすることを目的としています。

## 前提知識の解説

### 1. Linux名前空間 (Linux Namespaces)

Linux名前空間は、カーネルリソースを分離（隔離）するための機能です。これにより、各プロセスグループが独自のシステムリソースのビューを持つことができます。主な名前空間には以下のようなものがあります。

*   **PID名前空間 (PID Namespace)**: プロセスIDを隔離します。各名前空間は独自のPID 1（initプロセス）を持ちます。
*   **ネットワーク名前空間 (Network Namespace)**: ネットワークデバイス、IPアドレス、ルーティングテーブル、ポートなどを隔離します。
*   **マウント名前空間 (Mount Namespace)**: ファイルシステムのマウントポイントを隔離します。
*   **UTS名前空間 (UTS Namespace)**: ホスト名とNISドメイン名を隔離します。
*   **IPC名前空間 (IPC Namespace)**: System V IPC（セマフォ、メッセージキュー、共有メモリ）を隔離します。
*   **Cgroup名前空間 (Cgroup Namespace)**: cgroupのルートディレクトリを隔離します。
*   **ユーザー名前空間 (User Namespace)**: ユーザーIDとグループIDを隔離します。

### 2. ユーザー名前空間 (User Namespaces)

ユーザー名前空間は、Linuxカーネルのセキュリティ機能の中でも特に強力なものです。これにより、プロセスはホストシステムとは異なるUIDとGIDのセットを持つことができます。

*   **隔離の目的**: ユーザー名前空間の主な目的は、特権の分離です。例えば、コンテナ内で`root`として実行されているプロセスが、ホストシステム上では非特権ユーザーとして実行されているように見せかけることができます。これにより、コンテナからのホストシステムへの特権昇格攻撃のリスクを軽減します。
*   **UID/GIDマッピング**: ユーザー名前空間の核心は、内部のUID/GIDと外部（親名前空間、通常はホスト）のUID/GIDとの間のマッピングです。このマッピングは、`/proc/pid/uid_map`および`/proc/pid/gid_map`という特殊なファイルを通じて設定されます。
    *   これらのファイルは、`ID-inside-namespace ID-outside-namespace length`という形式の行で構成されます。
    *   例: `0 1000 1` は、名前空間内のUID 0が、ホストのUID 1000にマッピングされ、その長さが1（つまりUID 0のみ）であることを意味します。
    *   このマッピングは、新しいユーザー名前空間が作成された直後に一度だけ書き込むことができます。
*   **`CAP_SETUID`と`CAP_SETGID`**: これらのマッピングを書き込むには、書き込みを行うプロセスが、ターゲットのユーザー名前空間またはその親名前空間において、それぞれ`CAP_SETUID`または`CAP_SETGID`のケーパビリティを持っている必要があります。

### 3. `clone(2)`システムコールと`CLONE_NEWUSER`

`clone(2)`は、Linuxで新しいプロセス（スレッド）を作成するためのシステムコールです。このシステムコールは、新しいプロセスが親プロセスと共有するリソースと、分離するリソースを制御するための様々なフラグを受け取ります。

*   **`CLONE_NEWUSER`**: このフラグを`clone(2)`に渡すと、新しいプロセスは新しいユーザー名前空間内で開始されます。これにより、そのプロセスは独自のUID/GIDマッピングを持つ準備ができます。

### 4. `/proc/pid/uid_map`と`/proc/pid/gid_map`

これらは、特定のプロセス（`pid`）のユーザー名前空間におけるUIDおよびGIDのマッピングを定義するために使用される擬似ファイルです。

*   **`uid_map`**: ユーザーIDのマッピングを定義します。
*   **`gid_map`**: グループIDのマッピングを定義します。
*   これらのファイルに書き込むことで、名前空間内のIDがホスト上のどのIDに対応するかを設定します。

### 5. Go `syscall`パッケージと`SysProcAttr`

Go言語の`syscall`パッケージは、低レベルなシステムコールへのアクセスを提供します。`os/exec`パッケージを通じて外部コマンドを実行する際などにも利用されます。

*   **`SysProcAttr`**: `os/exec.Cmd`構造体の一部として、または直接`syscall`パッケージで使用される構造体です。新しいプロセスを生成する際の様々な属性（例: `Chroot`、`Credential`、`Cloneflags`など）を設定するために使用されます。
*   このコミット以前は、`SysProcAttr`にはUID/GIDマッピングを直接設定するためのフィールドがありませんでした。

## 技術的詳細

このコミットの技術的詳細は、Goの`syscall`パッケージがLinuxのユーザー名前空間におけるUID/GIDマッピングをどのようにサポートするように拡張されたかに集約されます。

1.  **`SysProcIDMap`構造体の導入**:
    新しい`SysProcIDMap`構造体が定義されました。これは、単一のIDマッピングエントリを表します。
    ```go
    type SysProcIDMap struct {
        ContainerID int // Container ID.
        HostID      int // Host ID.
        Size        int // Size.
    }
    ```
    *   `ContainerID`: 名前空間内の開始ID。
    *   `HostID`: ホスト（親名前空間）上の開始ID。
    *   `Size`: マッピングされるIDの連続した範囲の長さ。

2.  **`SysProcAttr`構造体の拡張**:
    既存の`SysProcAttr`構造体に、`UidMappings`と`GidMappings`という2つの新しいフィールドが追加されました。これらは`SysProcIDMap`の配列であり、複数のIDマッピングエントリを定義できるようにします。
    ```go
    type SysProcAttr struct {
        // ... 既存のフィールド ...
        UidMappings []SysProcIDMap // User ID mappings for user namespaces.
        GidMappings []SysProcIDMap // Group ID mappings for user namespaces.
    }
    ```
    これにより、Goプログラムは`exec.Cmd`の`SysProcAttr`を通じて、新しいプロセスが作成される際に適用されるUID/GIDマッピングを宣言的に指定できるようになります。

3.  **`forkAndExecInChild`関数の変更**:
    `forkAndExecInChild`は、Goが新しいプロセスをフォークして実行する際の内部的なヘルパー関数です。この関数が変更され、UID/GIDマッピングの処理が組み込まれました。
    *   **パイプによる同期**: 親プロセスが子プロセスのUID/GIDマッピングを設定する際に、子プロセスがその設定が完了するまで待機するためのパイプが導入されました。これは、子プロセスが新しいユーザー名前空間に入った直後に、親プロセスが`/proc/pid/uid_map`および`/proc/pid/gid_map`に書き込む必要があるためです。子プロセスは、親からの書き込み完了通知をパイプ経由で受け取るまで、実行を一時停止します。
    *   **エラー伝達**: パイプは、親プロセスがマッピングの書き込み中に発生したエラーを子プロセスに伝達するためにも使用されます。

4.  **`writeIDMappings`関数の追加**:
    この新しいヘルパー関数は、指定されたパス（`/proc/pid/uid_map`または`/proc/pid/gid_map`）にIDマッピングデータを書き込む汎用的なロジックをカプセル化します。
    *   ファイルを開き、`SysProcIDMap`スライスから`ID-inside ID-outside length`形式の文字列を生成し、その文字列をファイルに書き込みます。
    *   書き込み後、ファイルを閉じます。

5.  **`writeUidGidMappings`関数の追加**:
    この関数は、`writeIDMappings`を呼び出して、特定のPIDの`/proc/pid/uid_map`と`/proc/pid/gid_map`にUIDとGIDのマッピングを書き込みます。これは親プロセスから呼び出されます。

これらの変更により、Goプログラムは`SysProcAttr`を通じてUID/GIDマッピングを指定し、Goランタイムが新しいプロセスをフォークする際に、これらのマッピングを適切に`/proc/pid/uid_map`および`/proc/pid/gid_map`ファイルに書き込むようになります。これにより、GoからLinuxのユーザー名前空間を完全に制御できるようになります。

## コアとなるコードの解説

### `SysProcIDMap`構造体

この構造体は、ユーザー名前空間における単一のIDマッピングルールを定義します。
*   `ContainerID`: 新しいユーザー名前空間内で使用されるIDの開始点。
*   `HostID`: ホストシステム（または親名前空間）上で`ContainerID`がマッピングされるIDの開始点。
*   `Size`: `ContainerID`から始まる連続したIDの範囲の長さ。

例えば、`{ContainerID: 0, HostID: 1000, Size: 1}`は、名前空間内のUID 0がホストのUID 1000にマッピングされることを意味します。

### `SysProcAttr`構造体の拡張

`SysProcAttr`に`UidMappings`と`GidMappings`というスライスが追加されたことで、Goプログラムは`os/exec.Command`の`SysProcAttr`フィールドを通じて、新しいプロセスが起動する際に適用されるUID/GIDマッピングのリストを渡せるようになりました。

### `forkAndExecInChild`の変更点

この関数は、Goが新しいプロセスを生成する際の核心部分です。
1.  **パイプの導入**: `p [2]int`というパイプが導入されました。これは、親プロセスと子プロセスの間で同期を取るために使用されます。
    *   親プロセスは、子プロセスがフォークされた後、`writeUidGidMappings`を呼び出してUID/GIDマッピングを`/proc/pid/uid_map`と`/proc/pid/gid_map`に書き込みます。
    *   書き込みが完了すると、親プロセスはパイプにエラーコード（成功なら0）を書き込み、パイプを閉じます。
    *   子プロセスは、フォーク後、親からの書き込みが完了するまでパイプからの読み込みをブロックします。これにより、子プロセスがマッピングが適用される前に実行を開始してしまうことを防ぎます。
    *   子プロセスは、パイプから読み込んだエラーコードをチェックし、エラーがあれば終了します。

2.  **`writeUidGidMappings`の呼び出し**: 親プロセス側で、フォークされた子プロセスのPIDと`SysProcAttr`を引数に`writeUidGidMappings`が呼び出されます。

### `writeIDMappings`関数

この関数は、`/proc/pid/uid_map`または`/proc/pid/gid_map`のようなパスに、`SysProcIDMap`スライスで定義されたIDマッピングを書き込む汎用的なロジックを提供します。
*   指定されたパスのファイルを`O_RDWR`（読み書きモード）で開きます。
*   `idMap`スライスをループし、各`SysProcIDMap`エントリを`ContainerID HostID Size\n`形式の文字列に変換して連結します。
*   生成された文字列をバイトスライスに変換し、ファイルに書き込みます。
*   書き込み後、ファイルを閉じます。

### `writeUidGidMappings`関数

この関数は、`writeIDMappings`をラップし、特定のPIDに対してUIDマッピングとGIDマッピングの両方を処理します。
*   `sys.UidMappings`が`nil`でなければ、`/proc/<pid>/uid_map`にUIDマッピングを書き込みます。
*   `sys.GidMappings`が`nil`でなければ、`/proc/<pid>/gid_map`にGIDマッピングを書き込みます。
*   いずれかの書き込みでエラーが発生した場合、そのエラーを返します。

これらの変更により、GoはLinuxのユーザー名前空間をより深くサポートし、コンテナやサンドボックス環境の構築において、より強力な機能を提供できるようになりました。

## 変更の背景

このコミットの背景には、Linuxカーネルが提供する「ユーザー名前空間（User Namespaces）」の機能があります。ユーザー名前空間は、プロセスが自身のユーザーIDとグループIDのセットを持つことを可能にし、ホストシステムとは異なるIDマッピングを定義できるようにするセキュリティ機能です。これは、特にコンテナ技術（例: Docker、LXC）において、コンテナ内の`root`ユーザーがホストシステム上では非特権ユーザーとして扱われるようにするために不可欠な要素です。

Go言語の`syscall`パッケージは、OSのシステムコールを直接呼び出すための低レベルなインターフェースを提供します。以前のバージョンでは、ユーザー名前空間を作成する`CLONE_NEWUSER`フラグはサポートされていましたが、その名前空間内でUID/GIDのマッピングを定義するメカニズムが不足していました。この不足により、Goプログラムからユーザー名前空間を完全に活用することが困難でした。

コミットメッセージにある「Fixes #8447」は、この機能の欠如がGoのユーザーにとって問題となっていたことを示唆しています。このコミットは、Goプログラムが`/proc/pid/uid_map`および`/proc/pid/gid_map`ファイルを介してUID/GIDマッピングをプログラム的に設定できるようにすることで、この問題を解決し、Goがより高度なコンテナ化やサンドボックス化のシナリオに対応できるようにすることを目的としています。

## 前提知識の解説

### 1. Linux名前空間 (Linux Namespaces)

Linux名前空間は、カーネルリソースを分離（隔離）するための機能です。これにより、各プロセスグループが独自のシステムリソースのビューを持つことができます。主な名前空間には以下のようなものがあります。

*   **PID名前空間 (PID Namespace)**: プロセスIDを隔離します。各名前空間は独自のPID 1（initプロセス）を持ちます。
*   **ネットワーク名前空間 (Network Namespace)**: ネットワークデバイス、IPアドレス、ルーティングテーブル、ポートなどを隔離します。
*   **マウント名前空間 (Mount Namespace)**: ファイルシステムのマウントポイントを隔離します。
*   **UTS名前空間 (UTS Namespace)**: ホスト名とNISドメイン名を隔離します。
*   **IPC名前空間 (IPC Namespace)**: System V IPC（セマフォ、メッセージキュー、共有メモリ）を隔離します。
*   **Cgroup名前空間 (Cgroup Namespace)**: cgroupのルートディレクトリを隔離します。
*   **ユーザー名前空間 (User Namespace)**: ユーザーIDとグループIDを隔離します。

### 2. ユーザー名前空間 (User Namespaces)

ユーザー名前空間は、Linuxカーネルのセキュリティ機能の中でも特に強力なものです。これにより、プロセスはホストシステムとは異なるUIDとGIDのセットを持つことができます。

*   **隔離の目的**: ユーザー名前空間の主な目的は、特権の分離です。例えば、コンテナ内で`root`として実行されているプロセスが、ホストシステム上では非特権ユーザーとして実行されているように見せかけることができます。これにより、コンテナからのホストシステムへの特権昇格攻撃のリスクを軽減します。
*   **UID/GIDマッピング**: ユーザー名前空間の核心は、内部のUID/GIDと外部（親名前空間、通常はホスト）のUID/GIDとの間のマッピングです。このマッピングは、`/proc/pid/uid_map`および`/proc/pid/gid_map`という特殊なファイルを通じて設定されます。
    *   これらのファイルは、`ID-inside-namespace ID-outside-namespace length`という形式の行で構成されます。
    *   例: `0 1000 1` は、名前空間内のUID 0が、ホストのUID 1000にマッピングされ、その長さが1（つまりUID 0のみ）であることを意味します。
    *   このマッピングは、新しいユーザー名前空間が作成された直後に一度だけ書き込むことができます。
*   **`CAP_SETUID`と`CAP_SETGID`**: これらのマッピングを書き込むには、書き込みを行うプロセスが、ターゲットのユーザー名前空間またはその親名前空間において、それぞれ`CAP_SETUID`または`CAP_SETGID`のケーパビリティを持っている必要があります。

### 3. `clone(2)`システムコールと`CLONE_NEWUSER`

`clone(2)`は、Linuxで新しいプロセス（スレッド）を作成するためのシステムコールです。このシステムコールは、新しいプロセスが親プロセスと共有するリソースと、分離するリソースを制御するための様々なフラグを受け取ります。

*   **`CLONE_NEWUSER`**: このフラグを`clone(2)`に渡すと、新しいプロセスは新しいユーザー名前空間内で開始されます。これにより、そのプロセスは独自のUID/GIDマッピングを持つ準備ができます。

### 4. `/proc/pid/uid_map`と`/proc/pid/gid_map`

これらは、特定のプロセス（`pid`）のユーザー名前空間におけるUIDおよびGIDのマッピングを定義するために使用される擬似ファイルです。

*   **`uid_map`**: ユーザーIDのマッピングを定義します。
*   **`gid_map`**: グループIDのマッピングを定義します。
*   これらのファイルに書き込むことで、名前空間内のIDがホスト上のどのIDに対応するかを設定します。

### 5. Go `syscall`パッケージと`SysProcAttr`

Go言語の`syscall`パッケージは、低レベルなシステムコールへのアクセスを提供します。`os/exec`パッケージを通じて外部コマンドを実行する際などにも利用されます。

*   **`SysProcAttr`**: `os/exec.Cmd`構造体の一部として、または直接`syscall`パッケージで使用される構造体です。新しいプロセスを生成する際の様々な属性（例: `Chroot`、`Credential`、`Cloneflags`など）を設定するために使用されます。
*   このコミット以前は、`SysProcAttr`にはUID/GIDマッピングを直接設定するためのフィールドがありませんでした。

## 技術的詳細

このコミットの技術的詳細は、Goの`syscall`パッケージがLinuxのユーザー名前空間におけるUID/GIDマッピングをどのようにサポートするように拡張されたかに集約されます。

1.  **`SysProcIDMap`構造体の導入**:
    新しい`SysProcIDMap`構造体が定義されました。これは、単一のIDマッピングエントリを表します。
    ```go
    type SysProcIDMap struct {
        ContainerID int // Container ID.
        HostID      int // Host ID.
        Size        int // Size.
    }
    ```
    *   `ContainerID`: 名前空間内の開始ID。
    *   `HostID`: ホスト（親名前空間）上の開始ID。
    *   `Size`: マッピングされるIDの連続した範囲の長さ。

2.  **`SysProcAttr`構造体の拡張**:
    既存の`SysProcAttr`構造体に、`UidMappings`と`GidMappings`という2つの新しいフィールドが追加されました。これらは`SysProcIDMap`の配列であり、複数のIDマッピングエントリを定義できるようにします。
    ```go
    type SysProcAttr struct {
        // ... 既存のフィールド ...
        UidMappings []SysProcIDMap // User ID mappings for user namespaces.
        GidMappings []SysProcIDMap // Group ID mappings for user namespaces.
    }
    ```
    これにより、Goプログラムは`exec.Cmd`の`SysProcAttr`を通じて、新しいプロセスが作成される際に適用されるUID/GIDマッピングを宣言的に指定できるようになります。

3.  **`forkAndExecInChild`関数の変更**:
    `forkAndExecInChild`は、Goが新しいプロセスをフォークして実行する際の内部的なヘルパー関数です。この関数が変更され、UID/GIDマッピングの処理が組み込まれました。
    *   **パイプによる同期**: 親プロセスが子プロセスのUID/GIDマッピングを設定する際に、子プロセスがその設定が完了するまで待機するためのパイプが導入されました。これは、子プロセスが新しいユーザー名前空間に入った直後に、親プロセスが`/proc/pid/uid_map`および`/proc/pid/gid_map`に書き込む必要があるためです。子プロセスは、親からの書き込み完了通知をパイプ経由で受け取るまで、実行を一時停止します。
    *   **エラー伝達**: パイプは、親プロセスがマッピングの書き込み中に発生したエラーを子プロセスに伝達するためにも使用されます。

4.  **`writeIDMappings`関数の追加**:
    この新しいヘルパー関数は、指定されたパス（`/proc/pid/uid_map`または`/proc/pid/gid_map`）にIDマッピングデータを書き込む汎用的なロジックをカプセル化します。
    *   ファイルを開き、`SysProcIDMap`スライスから`ID-inside ID-outside length`形式の文字列を生成し、その文字列をファイルに書き込みます。
    *   書き込み後、ファイルを閉じます。

5.  **`writeUidGidMappings`関数の追加**:
    この関数は、`writeIDMappings`を呼び出して、特定のPIDの`/proc/pid/uid_map`と`/proc/pid/gid_map`にUIDとGIDのマッピングを書き込みます。これは親プロセスから呼び出されます。

これらの変更により、Goプログラムは`SysProcAttr`を通じてUID/GIDマッピングを指定し、Goランタイムが新しいプロセスをフォークする際に、これらのマッピングを適切に`/proc/pid/uid_map`および`/proc/pid/gid_map`ファイルに書き込むようになります。これにより、GoからLinuxのユーザー名前空間を完全に制御できるようになります。

## コアとなるコードの解説

### `SysProcIDMap`構造体

この構造体は、ユーザー名前空間における単一のIDマッピングルールを定義します。
*   `ContainerID`: 新しいユーザー名前空間内で使用されるIDの開始点。
*   `HostID`: ホストシステム（または親名前空間）上で`ContainerID`がマッピングされるIDの開始点。
*   `Size`: `ContainerID`から始まる連続したIDの範囲の長さ。

例えば、`{ContainerID: 0, HostID: 1000, Size: 1}`は、名前空間内のUID 0がホストのUID 1000にマッピングされることを意味します。

### `SysProcAttr`構造体の拡張

`SysProcAttr`に`UidMappings`と`GidMappings`というスライスが追加されたことで、Goプログラムは`os/exec.Command`の`SysProcAttr`フィールドを通じて、新しいプロセスが起動する際に適用されるUID/GIDマッピングのリストを渡せるようになりました。

### `forkAndExecInChild`の変更点

この関数は、Goが新しいプロセスを生成する際の核心部分です。
1.  **パイプの導入**: `p [2]int`というパイプが導入されました。これは、親プロセスと子プロセスの間で同期を取るために使用されます。
    *   親プロセスは、子プロセスがフォークされた後、`writeUidGidMappings`を呼び出してUID/GIDマッピングを`/proc/pid/uid_map`と`/proc/pid/gid_map`に書き込みます。
    *   書き込みが完了すると、親プロセスはパイプにエラーコード（成功なら0）を書き込み、パイプを閉じます。
    *   子プロセスは、フォーク後、親からの書き込みが完了するまでパイプからの読み込みをブロックします。これにより、子プロセスがマッピングが適用される前に実行を開始してしまうことを防ぎます。
    *   子プロセスは、パイプから読み込んだエラーコードをチェックし、エラーがあれば終了します。

2.  **`writeUidGidMappings`の呼び出し**: 親プロセス側で、フォークされた子プロセスのPIDと`SysProcAttr`を引数に`writeUidGidMappings`が呼び出されます。

### `writeIDMappings`関数

この関数は、`/proc/pid/uid_map`または`/proc/pid/gid_map`のようなパスに、`SysProcIDMap`スライスで定義されたIDマッピングを書き込む汎用的なロジックを提供します。
*   指定されたパスのファイルを`O_RDWR`（読み書きモード）で開きます。
*   `idMap`スライスをループし、各`SysProcIDMap`エントリを`ContainerID HostID Size\n`形式の文字列に変換して連結します。
*   生成された文字列をバイトスライスに変換し、ファイルに書き込みます。
*   書き込み後、ファイルを閉じます。

### `writeUidGidMappings`関数

この関数は、`writeIDMappings`をラップし、特定のPIDに対してUIDマッピングとGIDマッピングの両方を処理します。
*   `sys.UidMappings`が`nil`でなければ、`/proc/<pid>/uid_map`にUIDマッピングを書き込みます。
*   `sys.GidMappings`が`nil`でなければ、`/proc/<pid>/gid_map`にGIDマッピングを書き込みます。
*   いずれかの書き込みでエラーが発生した場合、そのエラーを返します。

これらの変更により、GoはLinuxのユーザー名前空間をより深くサポートし、コンテナやサンドボックス環境の構築において、より強力な機能を提供できるようになりました。

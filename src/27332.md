# [インデックス 27332] ファイルの概要

## 変更の背景

Go言語のランタイムは、メモリ操作においてC言語の`memcpy`や`memmove`に相当する低レベルなアセンブリルーチンを内部的に使用しています。これらのルーチンは、データのコピー性能に直接影響するため、非常に最適化されています。

このコミットの背景には、特に「アライメントされていないメモリ領域」間のデータコピーにおけるパフォーマンスの問題がありました。従来の`memmove`実装では、アライメントの有無にかかわらず、主に`MOVSQ`（64ビットアーキテクチャの場合）のような、より大きな単位でデータを移動する命令を使用していました。しかし、ソースまたはデスティネーションアドレスがCPUのワードサイズ（例えば64ビットシステムでは8バイト）にアライメントされていない場合、`MOVSQ`のような命令は効率が低下したり、場合によってはペナルティが発生したりすることが知られています。

コミットメッセージのベンチマーク結果が示すように、アライメントされていないコピー（`BenchmarkMemmoveUnalignedDst4096`と`BenchmarkMemmoveUnalignedSrc4096`）では、既存の実装が大幅に遅いことが明らかになりました。この性能ボトルネックを解消するため、アライメントされていないケースでは、より小さな単位（バイト単位）でデータを移動する`MOVSB`命令を使用するよう変更が加えられました。これにより、アライメントされていないメモリコピーの性能が劇的に改善されています。

## 前提知識の解説

### メモリのアライメント (Memory Alignment)

メモリのアライメントとは、コンピュータのメモリ上でデータが特定の境界に配置されることを指します。CPUは通常、ワードサイズ（例えば32ビットシステムでは4バイト、64ビットシステムでは8バイト）の倍数となるアドレスからデータを読み書きする際に最も効率的です。このようなアドレスを「アライメントされたアドレス」と呼びます。

*   **アライメントされたアクセス**: データのアドレスがそのデータ型やCPUのワードサイズの倍数になっている場合。CPUは一度のメモリアクセスで効率的にデータを読み書きできます。
*   **アライメントされていないアクセス (Unaligned Access)**: データのアドレスが特定の境界に揃っていない場合。例えば、4バイトの整数がアドレス0x0001に配置されているようなケースです。このようなアクセスは、CPUがデータを読み書きするために複数のメモリアクセスを実行したり、特別なハードウェア処理を必要としたりするため、パフォーマンスが大幅に低下する可能性があります。最悪の場合、アライメントエラーとしてプログラムがクラッシュすることもありますが、現代の多くのCPUはアライメントされていないアクセスを許容し、ソフトウェアで処理することで透過的に扱います。しかし、その代償として性能ペナルティが発生します。

### x86/x64 アセンブリ命令 (MOVSB, MOVSQ, REP)

Goランタイムは、パフォーマンスが重要な部分でアセンブリ言語を使用しています。このコミットで登場する主要な命令は以下の通りです。

*   **`MOVSB` (Move String Byte)**: ソースアドレス（`DS:SI`または`RSI`）からデスティネーションアドレス（`ES:DI`または`RDI`）へ1バイトのデータを移動します。移動後、`SI`/`RSI`と`DI`/`RDI`レジスタは、方向フラグ（DF）に応じてインクリメントまたはデクリメントされます。
*   **`MOVSW` (Move String Word)**: 2バイト（ワード）のデータを移動します。
*   **`MOVSD` (Move String Doubleword)**: 4バイト（ダブルワード）のデータを移動します。
*   **`MOVSQ` (Move String Quadword)**: 8バイト（クアッドワード）のデータを移動します。これは64ビットアーキテクチャ（x64）でのみ利用可能です。
*   **`REP` (Repeat String Operation)**: 文字列操作命令（`MOVSB`, `MOVSW`, `MOVSD`, `MOVSQ`など）の前に置かれるプレフィックスです。`CX`（または`RCX`）レジスタに指定された回数だけ、その文字列操作命令を繰り返します。`CX`レジスタは各繰り返しでデクリメントされ、ゼロになると繰り返しが終了します。これにより、ループ処理をアセンブリレベルで効率的に実行できます。

これらの命令は、メモリブロックのコピー（`memcpy`や`memmove`の実装）によく使用されます。

### Goランタイムの`memmove`

Go言語の組み込み関数である`copy`は、内部的にGoランタイムが提供する`memmove`のような低レベルなメモリコピー関数を呼び出します。これらの関数は、Goのコードではなく、各アーキテクチャ向けに最適化されたアセンブリ言語で実装されています。これは、Goプログラムの実行性能を最大化するために不可欠な部分です。`memmove`は、ソースとデスティネーションのメモリ領域がオーバーラップしている場合でも正しく動作するように設計されています。

### ベンチマークの重要性

ソフトウェア開発において、特にパフォーマンスがクリティカルな部分では、変更が性能に与える影響を定量的に評価するためにベンチマークが不可欠です。Go言語には、`testing`パッケージにベンチマーク機能が組み込まれており、`go test -bench=.`コマンドで実行できます。このコミットでも、変更の前後でベンチマークを実行し、その効果を数値で示しています。

## 技術的詳細

このコミットの核心は、`memmove`ルーチンにおいて、ソースとデスティネーションのアライメント状態に応じて異なる命令パスを選択するロジックを追加した点にあります。

従来の`memmove`は、多くの場合、可能な限り大きな単位（例えば`MOVSQ`）でデータを移動しようとします。これは、アライメントされたメモリに対しては非常に効率的です。しかし、ソースまたはデスティネーションのアドレスがCPUのワードサイズ（x64では8バイト）にアライメントされていない場合、`MOVSQ`のような命令は以下のような問題を引き起こす可能性があります。

1.  **複数回のメモリアクセス**: アライメントされていないアドレスから8バイトを読み込む場合、CPUは実際には2つの異なるキャッシュラインまたはメモリページにまたがるデータを読み込む必要があるかもしれません。これは、アライメントされたアクセスに比べて遅くなります。
2.  **マイクロコードの実行**: 一部のCPUでは、アライメントされていないアクセスを処理するために、より複雑なマイクロコードシーケンスを実行します。これも性能低下の原因となります。
3.  **ストアバッファのフラッシュ**: 書き込み操作の場合、アライメントされていないストアはストアバッファのフラッシュを引き起こし、パイプラインストールを招く可能性があります。

コミットメッセージにあるように、Intelのドキュメントなどでは、特定のアライメント条件下では`MOVSQ`が有利な場合があることが示唆されていますが、一般的なケース、特にアライメントされていないメモリコピーにおいては、1バイトずつ確実に処理する`MOVSB`の方が、オーバーヘッドが少なく、結果として高速になることが経験的に知られています。これは、`MOVSB`がアライメントの制約を受けにくく、CPUがより単純なパスで処理できるためと考えられます。

このコミットでは、`memmove`の開始時にソース（`SI`/`RSI`）とデスティネーション（`DI`/`RDI`）のアドレスをチェックし、いずれかのアドレスがアライメントされていない（例えば、x64では8バイト境界、x86では4バイト境界に揃っていない）場合は、`MOVSB`命令を使用してバイト単位でコピーを実行する「unaligned_fwd」パスに分岐するように変更されました。これにより、アライメントされていないコピーの性能が大幅に向上しました。

ベンチマーク結果は、この変更の有効性を明確に示しています。
*   `BenchmarkMemmove4096-8`: アライメントされたコピーでは、わずかな性能低下（-0.75%）またはほぼ変化なし。これは、アライメントチェックのオーバーヘッドがわずかにあるためか、あるいは`MOVSQ`が依然としてアライメントされたケースで非常に効率的であるためと考えられます。
*   `BenchmarkMemmoveUnalignedDst4096-8`: デスティネーションがアライメントされていない場合、**41.02%** の性能向上。
*   `BenchmarkMemmoveUnalignedSrc4096-8`: ソースがアライメントされていない場合、**48.29%** の性能向上。

これらの結果は、アライメントされていないメモリコピーがGoランタイムにとって重要なボトルネックであり、`MOVSB`への切り替えが非常に効果的であったことを裏付けています。

## コアとなるコードの解説

### アセンブリコードの変更 (`memmove_386.s`, `memmove_amd64.s`)

両方のアーキテクチャのアセンブリファイルで、`forward`コピーパス（メモリを前方へコピーする処理）にアライメントチェックが追加されています。

#### アライメントチェックのロジック

*   **`MOVL SI, AX` / `MOVQ SI, AX`**: ソースアドレス（`SI`または`RSI`）を`AX`レジスタに移動します。
*   **`ORL DI, AX` / `ORQ DI, AX`**: デスティネーションアドレス（`DI`または`RDI`）と`AX`レジスタの内容をビット単位でOR演算します。この結果、`AX`にはソースとデスティネーションのいずれかのアドレスでセットされているビットがすべてセットされます。
*   **`TESTL $3, AX` (x86) / `TESTL $7, AX` (x64)**: `AX`レジスタの内容と即値（x86では`$3`、x64では`$7`）をビット単位でAND演算し、結果をフラグレジスタにセットします。
    *   x86の場合、`$3`はバイナリで`00000011`です。これは、アドレスの下位2ビットをチェックします。もしアドレスが4の倍数（4バイトアライメント）であれば、下位2ビットは`00`となり、`AX & 3`の結果は`0`になります。
    *   x64の場合、`$7`はバイナリで`00000111`です。これは、アドレスの下位3ビットをチェックします。もしアドレスが8の倍数（8バイトアライメント）であれば、下位3ビットは`000`となり、`AX & 7`の結果は`0`になります。
    *   `TEST`命令は、結果がゼロであればゼロフラグ（ZF）をセットします。
*   **`JNE unaligned_fwd`**: ゼロフラグがセットされていない（つまり、`TEST`の結果がゼロではない）場合、`unaligned_fwd`ラベルにジャンプします。これは、ソースまたはデスティネーションのいずれかがアライメントされていないことを意味します。

#### アライメントされたパス

アライメントチェックを通過した場合（つまり、ソースとデスティネーションの両方がアライメントされている場合）、従来の効率的なコピーパスが実行されます。

*   **x86 (`memmove_386.s`)**:
    *   `MOVL BX, CX` / `SHRL $2, CX` / `ANDL $3, BX`: コピーするバイト数（`BX`）を4で割り、`CX`にコピー回数（ダブルワード数）を設定し、残りのバイト数を`BX`に設定します。
    *   `REP; MOVSL`: `CX`回、4バイト（ダブルワード）ずつデータをコピーします。
*   **x64 (`memmove_amd64.s`)**:
    *   `MOVQ BX, CX` / `SHRQ $3, CX` / `ANDQ $7, BX`: コピーするバイト数（`BX`）を8で割り、`CX`にコピー回数（クアッドワード数）を設定し、残りのバイト数を`BX`に設定します。
    *   `REP; MOVSQ`: `CX`回、8バイト（クアッドワード）ずつデータをコピーします。

これらの命令の後、残りのバイト数があれば`tail`ラベルにジャンプして処理を続行します。

#### アライメントされていないパス (`unaligned_fwd`)

アライメントチェックで`JNE unaligned_fwd`が実行された場合、この新しいパスに分岐します。

*   **`MOVL BX, CX` / `MOVQ BX, CX`**: コピーするバイト数（`BX`）を`CX`レジスタに移動します。
*   **`REP; MOVSB`**: `CX`回、1バイトずつデータをコピーします。
*   **`RET`**: 関数からリターンします。

この変更により、アライメントされていないメモリコピーでは、常に1バイト単位でデータを移動する`MOVSB`が使用されるようになり、アライメントペナルティを回避して性能が向上します。

### テストコードの変更 (`memmove_test.go`)

ベンチマークファイルでは、アライメントされていないメモリコピーのテストケースがより明確に分離され、追加されています。

*   `bmMemmoveUnaligned`関数が`bmMemmoveUnalignedDst`にリネームされました。これは、デスティネーションアドレスがアライメントされていないケースをテストします。
    *   `x := make([]byte, n+1)`: デスティネーションバッファ`x`を、サイズ`n+1`で作成します。
    *   `copy(x[1:], y)`: `x`の先頭1バイトをスキップした位置からコピーを開始することで、デスティネーションアドレスをアライメントされていない状態にします。
*   新たに`bmMemmoveUnalignedSrc`関数が追加されました。これは、ソースアドレスがアライメントされていないケースをテストします。
    *   `y := make([]byte, n+1)`: ソースバッファ`y`を、サイズ`n+1`で作成します。
    *   `copy(x, y[1:])`: `y`の先頭1バイトをスキップした位置からコピーすることで、ソースアドレスをアライメントされていない状態にします。

これらの変更により、アライメントされていないソースとデスティネーションの両方について、`memmove`のパフォーマンスを個別に測定できるようになり、今回の最適化の効果を正確に評価することが可能になりました。

## 変更の背景

Go言語のランタイムは、メモリ操作においてC言語の`memcpy`や`memmove`に相当する低レベルなアセンブリルーチンを内部的に使用しています。これらのルーチンは、データのコピー性能に直接影響するため、非常に最適化されています。

このコミットの背景には、特に「アライメントされていないメモリ領域」間のデータコピーにおけるパフォーマンスの問題がありました。従来の`memmove`実装では、アライメントの有無にかかわらず、主に`MOVSQ`（64ビットアーキテクチャの場合）のような、より大きな単位でデータを移動する命令を使用していました。しかし、ソースまたはデスティネーションアドレスがCPUのワードサイズ（例えば64ビットシステムでは8バイト）にアライメントされていない場合、`MOVSQ`のような命令は効率が低下したり、場合によってはペナルティが発生したりすることが知られています。

コミットメッセージのベンチマーク結果が示すように、アライメントされていないコピー（`BenchmarkMemmoveUnalignedDst4096`と`BenchmarkMemmoveUnalignedSrc4096`）では、既存の実装が大幅に遅いことが明らかになりました。この性能ボトルネックを解消するため、アライメントされていないケースでは、より小さな単位（バイト単位）でデータを移動する`MOVSB`命令を使用するよう変更が加えられました。これにより、アライメントされていないメモリコピーの性能が劇的に改善されています。

## 前提知識の解説

### メモリのアライメント (Memory Alignment)

メモリのアライメントとは、コンピュータのメモリ上でデータが特定の境界に配置されることを指します。CPUは通常、ワードサイズ（例えば32ビットシステムでは4バイト、64ビットシステムでは8バイト）の倍数となるアドレスからデータを読み書きする際に最も効率的です。このようなアドレスを「アライメントされたアドレス」と呼びます。

*   **アライメントされたアクセス**: データのアドレスがそのデータ型やCPUのワードサイズの倍数になっている場合。CPUは一度のメモリアクセスで効率的にデータを読み書きできます。
*   **アライメントされていないアクセス (Unaligned Access)**: データのアドレスが特定の境界に揃っていない場合。例えば、4バイトの整数がアドレス0x0001に配置されているようなケースです。このようなアクセスは、CPUがデータを読み書きするために複数のメモリアクセスを実行したり、特別なハードウェア処理を必要としたりするため、パフォーマンスが大幅に低下する可能性があります。最悪の場合、アライメントエラーとしてプログラムがクラッシュすることもありますが、現代の多くのCPUはアライメントされていないアクセスを許容し、ソフトウェアで処理することで透過的に扱います。しかし、その代償として性能ペナルティが発生します。

### x86/x64 アセンブリ命令 (MOVSB, MOVSQ, REP)

Goランタイムは、パフォーマンスが重要な部分でアセンブリ言語を使用しています。このコミットで登場する主要な命令は以下の通りです。

*   **`MOVSB` (Move String Byte)**: ソースアドレス（`DS:SI`または`RSI`）からデスティネーションアドレス（`ES:DI`または`RDI`）へ1バイトのデータを移動します。移動後、`SI`/`RSI`と`DI`/`RDI`レジスタは、方向フラグ（DF）に応じてインクリメントまたはデクリメントされます。
*   **`MOVSW` (Move String Word)**: 2バイト（ワード）のデータを移動します。
*   **`MOVSD` (Move String Doubleword)**: 4バイト（ダブルワード）のデータを移動します。
*   **`MOVSQ` (Move String Quadword)**: 8バイト（クアッドワード）のデータを移動します。これは64ビットアーキテクチャ（x64）でのみ利用可能です。
*   **`REP` (Repeat String Operation)**: 文字列操作命令（`MOVSB`, `MOVSW`, `MOVSD`, `MOVSQ`など）の前に置かれるプレフィックスです。`CX`（または`RCX`）レジスタに指定された回数だけ、その文字列操作命令を繰り返します。`CX`レジスタは各繰り返しでデクリメントされ、ゼロになると繰り返しが終了します。これにより、ループ処理をアセンブリレベルで効率的に実行できます。

これらの命令は、メモリブロックのコピー（`memcpy`や`memmove`の実装）によく使用されます。

### Goランタイムの`memmove`

Go言語の組み込み関数である`copy`は、内部的にGoランタイムが提供する`memmove`のような低レベルなメモリコピー関数を呼び出します。これらの関数は、Goのコードではなく、各アーキテクチャ向けに最適化されたアセンブリ言語で実装されています。これは、Goプログラムの実行性能を最大化するために不可欠な部分です。`memmove`は、ソースとデスティネーションのメモリ領域がオーバーラップしている場合でも正しく動作するように設計されています。

### ベンチマークの重要性

ソフトウェア開発において、特にパフォーマンスがクリティカルな部分では、変更が性能に与える影響を定量的に評価するためにベンチマークが不可欠です。Go言語には、`testing`パッケージにベンチマーク機能が組み込まれており、`go test -bench=.`コマンドで実行できます。このコミットでも、変更の前後でベンチマークを実行し、その効果を数値で示しています。

## 技術的詳細

このコミットの核心は、`memmove`ルーチンにおいて、ソースとデスティネーションのアライメント状態に応じて異なる命令パスを選択するロジックを追加した点にあります。

従来の`memmove`は、多くの場合、可能な限り大きな単位（例えば`MOVSQ`）でデータを移動しようとします。これは、アライメントされたメモリに対しては非常に効率的です。しかし、ソースまたはデスティネーションのアドレスがCPUのワードサイズ（x64では8バイト）にアライメントされていない場合、`MOVSQ`のような命令は以下のような問題を引き起こす可能性があります。

1.  **複数回のメモリアクセス**: アライメントされていないアドレスから8バイトを読み込む場合、CPUは実際には2つの異なるキャッシュラインまたはメモリページにまたがるデータを読み込む必要があるかもしれません。これは、アライメントされたアクセスに比べて遅くなります。
2.  **マイクロコードの実行**: 一部のCPUでは、アライメントされていないアクセスを処理するために、より複雑なマイクロコードシーケンスを実行します。これも性能低下の原因となります。
3.  **ストアバッファのフラッシュ**: 書き込み操作の場合、アライメントされていないストアはストアバッファのフラッシュを引き起こし、パイプラインストールを招く可能性があります。

コミットメッセージにあるように、Intelのドキュメントなどでは、特定のアライメント条件下では`MOVSQ`が有利な場合があることが示唆されていますが、一般的なケース、特にアライメントされていないメモリコピーにおいては、1バイトずつ確実に処理する`MOVSB`の方が、オーバーヘッドが少なく、結果として高速になることが経験的に知られています。これは、`MOVSB`がアライメントの制約を受けにくく、CPUがより単純なパスで処理できるためと考えられます。

このコミットでは、`memmove`の開始時にソース（`SI`/`RSI`）とデスティネーション（`DI`/`RDI`）のアドレスをチェックし、いずれかのアドレスがアライメントされていない（例えば、x64では8バイト境界、x86では4バイト境界に揃っていない）場合は、`MOVSB`命令を使用してバイト単位でコピーを実行する「unaligned_fwd」パスに分岐するように変更されました。これにより、アライメントされていないコピーの性能が大幅に向上しました。

ベンチマーク結果は、この変更の有効性を明確に示しています。
*   `BenchmarkMemmove4096-8`: アライメントされたコピーでは、わずかな性能低下（-0.75%）またはほぼ変化なし。これは、アライメントチェックのオーバーヘッドがわずかにあるためか、あるいは`MOVSQ`が依然としてアライメントされたケースで非常に効率的であるためと考えられます。
*   `BenchmarkMemmoveUnalignedDst4096-8`: デスティネーションがアライメントされていない場合、**41.02%** の性能向上。
*   `BenchmarkMemmoveUnalignedSrc4096-8`: ソースがアライメントされていない場合、**48.29%** の性能向上。

これらの結果は、アライメントされていないメモリコピーがGoランタイムにとって重要なボトルネックであり、`MOVSB`への切り替えが非常に効果的であったことを裏付けています。

## コアとなるコードの解説

### アセンブリコードの変更 (`memmove_386.s`, `memmove_amd64.s`)

両方のアーキテクチャのアセンブリファイルで、`forward`コピーパス（メモリを前方へコピーする処理）にアライメントチェックが追加されています。

#### アライメントチェックのロジック

*   **`MOVL SI, AX` / `MOVQ SI, AX`**: ソースアドレス（`SI`または`RSI`）を`AX`レジスタに移動します。
*   **`ORL DI, AX` / `ORQ DI, AX`**: デスティネーションアドレス（`DI`または`RDI`）と`AX`レジスタの内容をビット単位でOR演算します。この結果、`AX`にはソースとデスティネーションのいずれかのアドレスでセットされているビットがすべてセットされます。
*   **`TESTL $3, AX` (x86) / `TESTL $7, AX` (x64)**: `AX`レジスタの内容と即値（x86では`$3`、x64では`$7`）をビット単位でAND演算し、結果をフラグレジスタにセットします。
    *   x86の場合、`$3`はバイナリで`00000011`です。これは、アドレスの下位2ビットをチェックします。もしアドレスが4の倍数（4バイトアライメント）であれば、下位2ビットは`00`となり、`AX & 3`の結果は`0`になります。
    *   x64の場合、`$7`はバイナリで`00000111`です。これは、アドレスの下位3ビットをチェックします。もしアドレスが8の倍数（8バイトアライメント）であれば、下位3ビットは`000`となり、`AX & 7`の結果は`0`になります。
    *   `TEST`命令は、結果がゼロであればゼロフラグ（ZF）をセットします。
*   **`JNE unaligned_fwd`**: ゼロフラグがセットされていない（つまり、`TEST`の結果がゼロではない）場合、`unaligned_fwd`ラベルにジャンプします。これは、ソースまたはデスティネーションのいずれかがアライメントされていないことを意味します。

#### アライメントされたパス

アライメントチェックを通過した場合（つまり、ソースとデスティネーションの両方がアライメントされている場合）、従来の効率的なコピーパスが実行されます。

*   **x86 (`memmove_386.s`)**:
    *   `MOVL BX, CX` / `SHRL $2, CX` / `ANDL $3, BX`: コピーするバイト数（`BX`）を4で割り、`CX`にコピー回数（ダブルワード数）を設定し、残りのバイト数を`BX`に設定します。
    *   `REP; MOVSL`: `CX`回、4バイト（ダブルワード）ずつデータをコピーします。
*   **x64 (`memmove_amd64.s`)**:
    *   `MOVQ BX, CX` / `SHRQ $3, CX` / `ANDQ $7, BX`: コピーするバイト数（`BX`）を8で割り、`CX`にコピー回数（クアッドワード数）を設定し、残りのバイト数を`BX`に設定します。
    *   `REP; MOVSQ`: `CX`回、8バイト（クアッドワード）ずつデータをコピーします。

これらの命令の後、残りのバイト数があれば`tail`ラベルにジャンプして処理を続行します。

#### アライメントされていないパス (`unaligned_fwd`)

アライメントチェックで`JNE unaligned_fwd`が実行された場合、この新しいパスに分岐します。

*   **`MOVL BX, CX` / `MOVQ BX, CX`**: コピーするバイト数（`BX`）を`CX`レジスタに移動します。
*   **`REP; MOVSB`**: `CX`回、1バイトずつデータをコピーします。
*   **`RET`**: 関数からリターンします。

この変更により、アライメントされていないメモリコピーでは、常に1バイト単位でデータを移動する`MOVSB`が使用されるようになり、アライメントペナルティを回避して性能が向上します。

### テストコードの変更 (`memmove_test.go`)

ベンチマークファイルでは、アライメントされていないメモリコピーのテストケースがより明確に分離され、追加されています。

*   `bmMemmoveUnaligned`関数が`bmMemmoveUnalignedDst`にリネームされました。これは、デスティネーションアドレスがアライメントされていないケースをテストします。
    *   `x := make([]byte, n+1)`: デスティネーションバッファ`x`を、サイズ`n+1`で作成します。
    *   `copy(x[1:], y)`: `x`の先頭1バイトをスキップした位置からコピーを開始することで、デスティネーションアドレスをアライメントされていない状態にします。
*   新たに`bmMemmoveUnalignedSrc`関数が追加されました。これは、ソースアドレスがアライメントされていないケースをテストします。
    *   `y := make([]byte, n+1)`: ソースバッファ`y`を、サイズ`n+1`で作成します。
    *   `copy(x, y[1:])`: `y`の先頭1バイトをスキップした位置からコピーすることで、ソースアドレスをアライメントされていない状態にします。

これらの変更により、アライメントされていないソースとデスティネーションの両方について、`memmove`のパフォーマンスを個別に測定できるようになり、今回の最適化の効果を正確に評価することが可能になりました。

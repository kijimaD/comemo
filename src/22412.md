# [インデックス 22412] ファイルの概要

このコミットは、GoランタイムのOpenBSD固有のコード(`src/runtime/os1_openbsd.go`)から、もはや存在しない`kern.rthreads` sysctlへの参照と、`__tfork`システムコールが`ENOTSUP`エラーを返さなくなったことに関連する古いエラーハンドリングロジックを削除するものです。このファイルは、OpenBSD上でのGoプログラムのOSレベルのスレッド作成と管理に関するランタイムの挙動を定義しています。

## コミット

```
runtime: remove reference to openbsd kern.rthreads sysctl

The kern.rthreads sysctl has not existed for a long time - there is no way to
disable rthreads and __tfork no longer returns ENOTSUP.

Reviewed-on: https://go-review.googlesource.com/7490
```

## 変更の背景

この変更の背景には、OpenBSDオペレーティングシステムの進化があります。かつてOpenBSDには、`kern.rthreads`というsysctl（システム制御変数）が存在し、これはシステムのスレッド挙動、特に`rthreads`と呼ばれる新しいスレッド実装の有効/無効を制御するために使用されていました。Goランタイムは、新しいOSスレッドを作成する際に、`__tfork`というOpenBSD固有のシステムコールを利用していました。もし`__tfork`が`ENOTSUP`（Operation not supported）エラーを返した場合、それは`kern.rthreads`が無効になっている可能性を示唆していました。

しかし、コミットメッセージが示すように、この`kern.rthreads` sysctlは「長い間存在していません」。これは、OpenBSDのカーネル開発が進むにつれて、スレッド管理のメカニズムが変更され、このsysctlが不要になったか、あるいは別の方法でスレッドの挙動が制御されるようになったことを意味します。同時に、`__tfork`システムコールも、もはや`ENOTSUP`を返さなくなりました。これは、`__tfork`が常にサポートされるようになったか、あるいはエラーの報告方法が変わったことを示唆しています。

これらの変更により、Goランタイム内の既存のエラーハンドリングロジック、特に`__tfork`が`ENOTSUP`を返した場合に`kern.rthreads`が無効になっている可能性をユーザーに示唆する部分は、もはや意味をなさなくなりました。存在しないsysctlについて言及したり、発生しないエラーコードをチェックしたりするコードは、デッドコードとなり、混乱を招く可能性があります。そのため、このコミットでは、これらの古い参照とエラーチェックを削除し、コードベースを最新のOpenBSDの挙動に合わせることを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Go言語のプログラムを実行するために必要な低レベルのコンポーネント群です。これには、ガベージコレクタ、スケジューラ（ゴルーチンをOSスレッドにマッピングする）、メモリ管理、システムコールインターフェースなどが含まれます。OS固有のコードは、Goランタイムが特定のオペレーティングシステムの機能と適切に連携するために不可欠です。
*   **OpenBSD**: セキュリティを重視して開発されたUNIX系オペレーティングシステムです。厳格なコードレビューとセキュリティ機能の実装で知られています。
*   **sysctl (System Control)**: UNIX系システムにおいて、カーネルのパラメータを動的に参照または変更するためのメカニズムです。`kern.rthreads`のようなsysctlは、カーネルの特定の挙動や設定を調整するために使用されます。
*   **`kern.rthreads`**: OpenBSDに存在した、スレッド関連のカーネルパラメータを制御するsysctlです。`rthreads`はOpenBSDの新しいスレッド実装を指し、パフォーマンス、堅牢性、スケーラビリティの向上を目的としていました。
*   **`__tfork`**: OpenBSD固有のシステムコールで、新しいカーネルスレッドをプロセス内に作成するために使用されます。Goランタイムは、ゴルーチンをOSスレッドにマッピングする際に、このようなOS固有のスレッド作成メカニズムを利用します。
*   **`ENOTSUP` (Operation not supported)**: POSIX標準で定義されているエラーコードの一つで、要求された操作がサポートされていないことを示します。このコンテキストでは、`__tfork`システムコールが何らかの理由でスレッド作成をサポートできない場合に返される可能性がありました。
*   **`newosproc`関数**: Goランタイム内で、新しいOSスレッドを作成する役割を担う関数です。この関数は、Goのスケジューラがゴルーチンを実行するために追加のOSスレッドが必要になったときに呼び出されます。

## 技術的詳細

このコミットは、`src/runtime/os1_openbsd.go`ファイル内の`newosproc`関数から特定のコードブロックを削除しています。このコードブロックは、`__tfork`システムコールの呼び出しが負の戻り値（エラーを示す）を返した場合に実行されるエラーハンドリングの一部でした。

具体的には、以下の条件分岐が削除されました。

```go
if ret == -_ENOTSUP {
    print("runtime: is kern.rthreads disabled?\\n")
}
```

このコードは、`newosproc`がOSスレッドの作成に失敗し、そのエラーコードが`-_ENOTSUP`（Goの内部表現で負の値）と一致した場合に、「runtime: is kern.rthreads disabled?」というメッセージを出力していました。これは、スレッド作成の失敗が`kern.rthreads` sysctlが無効になっていることに起因する可能性があることを示唆する診断メッセージでした。

コミットメッセージが明確に述べているように、このコードが削除された理由は二つあります。

1.  **`kern.rthreads` sysctlの廃止**: `kern.rthreads`というsysctlは、OpenBSDのカーネルから既に削除されており、もはや存在しません。したがって、このsysctlの状態をチェックしたり、それについてユーザーに警告したりするコードは無意味です。
2.  **`__tfork`が`ENOTSUP`を返さなくなった**: `__tfork`システムコールは、スレッド作成に失敗した場合に、もはや`ENOTSUP`エラーコードを返さなくなりました。これは、OpenBSDのカーネルが`__tfork`の挙動を変更し、この特定のエラーシナリオが発生しなくなったことを意味します。

これらの変更により、Goランタイムは、OpenBSDの最新のカーネル挙動に適合し、存在しない機能や発生しないエラーに対する不必要なチェックを排除することで、コードの簡潔性と正確性を向上させています。これにより、ランタイムのフットプリントがわずかに減少し、デバッグ時の誤解を招くメッセージが排除されます。

## コアとなるコードの解説

変更は、`src/runtime/os1_openbsd.go`ファイル内の`newosproc`関数にあります。この関数は、Goランタイムが新しいOSスレッドを生成する際に呼び出されます。

元のコードでは、`newosproc`がOSスレッドの作成に失敗し、`ret`変数が負の値（エラーを示す）を返した場合に、エラーメッセージを出力していました。そのエラーハンドリングの一部として、以下の3行のコードブロックが含まれていました。

```go
		if ret == -_ENOTSUP {
			print("runtime: is kern.rthreads disabled?\\n")
		}
```

このブロックは、`ret`が`-_ENOTSUP`と等しい場合にのみ実行され、「runtime: is kern.rthreads disabled?」というメッセージをコンソールに出力していました。これは、OpenBSDシステムでスレッド作成が失敗した際に、`kern.rthreads` sysctlが原因である可能性を開発者やユーザーに示唆するための診断的なヒントでした。

このコミットでは、上記の3行が完全に削除されています。これは、前述の「変更の背景」と「技術的詳細」で説明したように、`kern.rthreads` sysctlがもはや存在せず、`__tfork`システムコールが`ENOTSUP`エラーを返さなくなったため、この診断メッセージが不要になったためです。

この削除により、コードはよりクリーンになり、OpenBSDの現在のカーネルの挙動に正確に合致するようになりました。存在しない問題に対するチェックやメッセージングを排除することで、ランタイムのコードベースの保守性が向上し、将来のデバッグ作業における誤解を減らすことができます。

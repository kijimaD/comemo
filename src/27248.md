# [インデックス 27248] ファイルの概要

このコミットは、Goコンパイラが文字列定数を処理する際のメモリ使用量を削減することを目的としています。具体的には、これまで各文字列定数に対して重複して作成されていた `Sym` (シンボル) と `Node` (抽象構文木ノード) のペアを廃止し、リンカシンボルである `obj.LSym` を直接利用するように変更することで、コンパイラ内部のオブジェクト数を削減します。これにより、コンパイル時のメモリフットプリントが改善され、特に大規模なコードベースのコンパイルにおいてその効果が期待されます。

## 元コミット内容

```
cmd/compile: don't create 2 Sym's and 2 Node's for every string

For every string constant the compiler was creating 2 Sym's and 2
Node's. It would never refer to them again, but would keep them alive
in gostringpkg. This changes the code to just use obj.LSym's instead.

When compiling x/tools/go/types, this yields about a 15% reduction in
the number of calls to newname and a 3% reduction in the total number of
Node objects. Unfortunately I couldn't see any change in compile time,
but reducing memory usage is desirable anyhow.

Passes toolstash -cmp.

## 変更の背景

Goコンパイラは、ソースコード内の各文字列定数に対して、内部的に2つの `Sym` オブジェクトと2つの `Node` オブジェクトを生成していました。これらのオブジェクトは `gostringpkg` という擬似パッケージ内で管理されていましたが、一度生成されるとその後再利用されることはなく、コンパイルプロセスの終了までメモリ上に保持され続けていました。

この冗長なオブジェクト生成は、特に多数の文字列定数を含む大規模なGoプログラムをコンパイルする際に、コンパイラのメモリフットプリントを不必要に増加させる原因となっていました。コミットメッセージによると、`x/tools/go/types` のコンパイルにおいて、`newname` の呼び出し回数が約15%削減され、`Node` オブジェクトの総数が約3%削減されることが確認されています。コンパイル時間の直接的な改善は見られなかったものの、メモリ使用量の削減はコンパイラの効率性と安定性にとって望ましい改善であると判断されました。

この変更の目的は、文字列定数の表現をより効率的な `obj.LSym` (リンカシンボル) に統一することで、コンパイラ内部のメモリ消費を最適化し、全体的なコンパイラの性能を向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造と、シンボルおよび抽象構文木 (AST) の概念、そしてリンカとの連携について基本的な知識が必要です。

### Goコンパイラ (`cmd/compile`) の構造

Goコンパイラは、`src/cmd/compile` ディレクトリ以下に実装されており、その主要な部分は `internal/gc` パッケージにあります。このパッケージは、字句解析、構文解析、型チェック、中間表現 (IR) の生成、最適化、コード生成といったコンパイルの各段階を担っています。

### シンボル (`Sym`) と抽象構文木ノード (`Node`)

*   **`Sym` (シンボル)**: コンパイラ内部で、変数、関数、型、パッケージなどの名前付きエンティティを一意に識別するために使用されるデータ構造です。各シンボルは、そのエンティティに関するメタデータ（名前、型、スコープなど）を保持します。
*   **`Node` (抽象構文木ノード)**: ソースコードの構造を木構造で表現した抽象構文木 (AST) の各要素です。例えば、変数宣言、関数呼び出し、演算子、リテラルなどが `Node` として表現されます。コンパイラはASTを走査しながら、型チェックやコード生成を行います。

### リンカシンボル (`obj.LSym`)

Goコンパイラは、最終的にアセンブリコードを生成し、それをリンカ (`cmd/link`) が実行可能なバイナリに結合します。`obj.LSym` は、リンカが認識するシンボルを表すデータ構造です。コンパイラが生成するコード内のグローバル変数や関数、データセクションなどは、この `obj.LSym` を通じてリンカに渡されます。`obj` パッケージは、コンパイラとリンカの間で共有される低レベルのオブジェクトファイルフォーマットとシンボル定義を提供します。

### 文字列定数

Go言語では、`"hello"` のような文字列リテラルはコンパイル時に定数として扱われます。これらの文字列定数は、最終的に生成されるバイナリのデータセクションに格納され、プログラム実行時に参照されます。コンパイラは、これらの文字列定数を効率的に管理し、重複を排除したり、適切なリンカシンボルにマッピングしたりする必要があります。

### `gostringpkg` (変更前の文字列定数管理)

このコミット以前は、Goコンパイラは文字列定数を管理するために `gostringpkg` という特別な「擬似パッケージ」を使用していました。これは、実際のGoパッケージではなく、コンパイラ内部で文字列定数に関連する `Sym` と `Node` をグループ化するための論理的なコンテナでした。しかし、このアプローチは、各文字列定数に対して冗長な `Sym` と `Node` のペアを生成するという問題がありました。

### メモリ使用量とコンパイル時間

コンパイラの性能は、コンパイル時間だけでなく、コンパイル中に消費するメモリ量も重要な指標です。メモリ使用量が多いと、特にリソースが限られた環境でのコンパイルが遅くなったり、システム全体のパフォーマンスに影響を与えたりする可能性があります。このコミットは、コンパイル時間の直接的な改善よりも、メモリ使用量の削減に焦点を当てています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラが文字列定数を表現する方法を根本的に変更した点にあります。以前は、各文字列定数に対してコンパイラ内部の `Sym` と `Node` のペアが作成され、これらは `gostringpkg` という擬似パッケージに属していました。このアプローチは、文字列定数の数が増えるにつれて、コンパイラが保持するオブジェクトの総数を不必要に増加させていました。

新しいアプローチでは、文字列定数を直接 `obj.LSym` (リンカシンボル) として表現し、管理します。これにより、コンパイラ内部の `Sym` や `Node` といった高レベルの抽象化を介さずに、より低レベルで効率的なリンカシンボルを直接操作できるようになります。

具体的な変更点は以下の通りです。

1.  **`gostringpkg` の廃止**: 文字列定数専用の擬似パッケージ `gostringpkg` が削除されました。これにより、このパッケージに関連する `Sym` や `Node` の生成が不要になります。
2.  **`obj.LSym` の直接利用**: 文字列定数のヘッダとデータは、それぞれ `obj.LSym` として表現されます。これらの `obj.LSym` は、`obj.Linklookup` 関数を使ってリンカのシンボルテーブルから取得または作成されます。
3.  **`stringConstants` マップの導入**: 文字列定数の `obj.LSym` ペアをキャッシュするために、`stringConstants` という `map[string]stringConstantSyms` 型のマップが導入されました。これにより、同じ文字列定数が複数回出現しても、`obj.LSym` のペアは一度だけ生成され、再利用されるようになります。マップのキーは文字列データの内容から生成され、値は文字列ヘッダとデータに対応する `obj.LSym` のペアを保持する `stringConstantSyms` 構造体です。
4.  **ヘルパー関数の変更**: `duintxx`, `dsname`, `dsymptr`, `ggloblsym` といった、シンボルに関連するデータを操作する関数が、`Sym` だけでなく `obj.LSym` を直接受け取る新しいバージョン (`duintxxLSym`, `dsnameLSym`, `dsymptrLSym`, `ggloblLSym`) に変更されました。これにより、`Sym` から `obj.LSym` への変換 (`Linksym`) のオーバーヘッドが削減され、コードの直接性が向上します。
5.  **`ssa.ExternSymbol` の柔軟性向上**: SSA (Static Single Assignment) 形式の中間表現で使用される `ssa.ExternSymbol` が、`*Sym` または `*obj.LSym` のいずれかを保持できるように変更されました。これにより、SSAパスがリンカシンボルを直接参照できるようになり、コンパイラ内部の異なる抽象化レベル間での連携がスムーズになります。
6.  **`obj.LSym` の `String()` メソッド**: `obj.LSym` に `fmt.Stringer` インターフェースを満たす `String()` メソッドが追加されました。これは、`ssa.ExternSymbol` が `obj.LSym` を保持するようになったため、デバッグやロギングの際にシンボル名を適切に表示できるようにするための変更です。

これらの変更により、コンパイラは文字列定数をより効率的に管理し、不要なオブジェクトの生成を避けることで、メモリ使用量を削減し、コンパイルプロセスの全体的な効率を向上させています。

## 変更の背景

Goコンパイラは、ソースコード内の各文字列定数に対して、内部的に2つの `Sym` オブジェクトと2つの `Node` オブジェクトを生成していました。これらのオブジェクトは `gostringpkg` という擬似パッケージ内で管理されていましたが、一度生成されるとその後再利用されることはなく、コンパイルプロセスの終了までメモリ上に保持され続けていました。

この冗長なオブジェクト生成は、特に多数の文字列定数を含む大規模なGoプログラムをコンパイルする際に、コンパイラのメモリフットプリントを不必要に増加させる原因となっていました。コミットメッセージによると、`x/tools/go/types` のコンパイルにおいて、`newname` の呼び出し回数が約15%削減され、`Node` オブジェクトの総数が約3%削減されることが確認されています。コンパイル時間の直接的な改善は見られなかったものの、メモリ使用量の削減はコンパイラの効率性と安定性にとって望ましい改善であると判断されました。

この変更の目的は、文字列定数の表現をより効率的な `obj.LSym` (リンカシンボル) に統一することで、コンパイラ内部のメモリ消費を最適化し、全体的なコンパイラの性能を向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造と、シンボルおよび抽象構文木 (AST) の概念、そしてリンカとの連携について基本的な知識が必要です。

### Goコンパイラ (`cmd/compile`) の構造

Goコンパイラは、`src/cmd/compile` ディレクトリ以下に実装されており、その主要な部分は `internal/gc` パッケージにあります。このパッケージは、字句解析、構文解析、型チェック、中間表現 (IR) の生成、最適化、コード生成といったコンパイルの各段階を担っています。

### シンボル (`Sym`) と抽象構文木ノード (`Node`)

*   **`Sym` (シンボル)**: コンパイラ内部で、変数、関数、型、パッケージなどの名前付きエンティティを一意に識別するために使用されるデータ構造です。各シンボルは、そのエンティティに関するメタデータ（名前、型、スコープなど）を保持します。
*   **`Node` (抽象構文木ノード)**: ソースコードの構造を木構造で表現した抽象構文木 (AST) の各要素です。例えば、変数宣言、関数呼び出し、演算子、リテラルなどが `Node` として表現されます。コンパイラはASTを走査しながら、型チェックやコード生成を行います。

### リンカシンボル (`obj.LSym`)

Goコンパイラは、最終的にアセンブリコードを生成し、それをリンカ (`cmd/link`) が実行可能なバイナリに結合します。`obj.LSym` は、リンカが認識するシンボルを表すデータ構造です。コンパイラが生成するコード内のグローバル変数や関数、データセクションなどは、この `obj.LSym` を通じてリンカに渡されます。`obj` パッケージは、コンパイラとリンカの間で共有される低レベルのオブジェクトファイルフォーマットとシンボル定義を提供します。

### 文字列定数

Go言語では、`"hello"` のような文字列リテラルはコンパイル時に定数として扱われます。これらの文字列定数は、最終的に生成されるバイナリのデータセクションに格納され、プログラム実行時に参照されます。コンパイラは、これらの文字列定数を効率的に管理し、重複を排除したり、適切なリンカシンボルにマッピングしたりする必要があります。

### `gostringpkg` (変更前の文字列定数管理)

このコミット以前は、Goコンパイラは文字列定数を管理するために `gostringpkg` という特別な「擬似パッケージ」を使用していました。これは、実際のGoパッケージではなく、コンパイラ内部で文字列定数に関連する `Sym` と `Node` をグループ化するための論理的なコンテナでした。しかし、このアプローチは、各文字列定数に対して冗長な `Sym` と `Node` のペアを生成するという問題がありました。

### メモリ使用量とコンパイル時間

コンパイラの性能は、コンパイル時間だけでなく、コンパイル中に消費するメモリ量も重要な指標です。メモリ使用量が多いと、特にリソースが限られた環境でのコンパイルが遅くなったり、システム全体のパフォーマンスに影響を与えたりする可能性があります。このコミットは、コンパイル時間の直接的な改善よりも、メモリ使用量の削減に焦点を当てています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラが文字列定数を表現する方法を根本的に変更した点にあります。以前は、各文字列定数に対してコンパイラ内部の `Sym` と `Node` のペアが作成され、これらは `gostringpkg` という擬似パッケージに属していました。このアプローチは、文字列定数の数が増えるにつれて、コンパイラが保持するオブジェクトの総数を不必要に増加させていました。

新しいアプローチでは、文字列定数を直接 `obj.LSym` (リンカシンボル) として表現し、管理します。これにより、コンパイラ内部の `Sym` や `Node` といった高レベルの抽象化を介さずに、より低レベルで効率的なリンカシンボルを直接操作できるようになります。

具体的な変更点は以下の通りです。

1.  **`gostringpkg` の廃止**: 文字列定数専用の擬似パッケージ `gostringpkg` が削除されました。これにより、このパッケージに関連する `Sym` や `Node` の生成が不要になります。
2.  **`obj.LSym` の直接利用**: 文字列定数のヘッダとデータは、それぞれ `obj.LSym` として表現されます。これらの `obj.LSym` は、`obj.Linklookup` 関数を使ってリンカのシンボルテーブルから取得または作成されます。
3.  **`stringConstants` マップの導入**: 文字列定数の `obj.LSym` ペアをキャッシュするために、`stringConstants` という `map[string]stringConstantSyms` 型のマップが導入されました。これにより、同じ文字列定数が複数回出現しても、`obj.LSym` のペアは一度だけ生成され、再利用されるようになります。マップのキーは文字列データの内容から生成され、値は文字列ヘッダとデータに対応する `obj.LSym` のペアを保持する `stringConstantSyms` 構造体です。
4.  **ヘルパー関数の変更**: `duintxx`, `dsname`, `dsymptr`, `ggloblsym` といった、シンボルに関連するデータを操作する関数が、`Sym` だけでなく `obj.LSym` を直接受け取る新しいバージョン (`duintxxLSym`, `dsnameLSym`, `dsymptrLSym`, `ggloblLSym`) に変更されました。これにより、`Sym` から `obj.LSym` への変換 (`Linksym`) のオーバーヘッドが削減され、コードの直接性が向上します。
5.  **`ssa.ExternSymbol` の柔軟性向上**: SSA (Static Single Assignment) 形式の中間表現で使用される `ssa.ExternSymbol` が、`*Sym` または `*obj.LSym` のいずれかを保持できるように変更されました。これにより、SSAパスがリンカシンボルを直接参照できるようになり、コンパイラ内部の異なる抽象化レベル間での連携がスムーズになります。
6.  **`obj.LSym` の `String()` メソッド**: `obj.LSym` に `fmt.Stringer` インターフェースを満たす `String()` メソッドが追加されました。これは、`ssa.ExternSymbol` が `obj.LSym` を保持するようになったため、デバッグやロギングの際にシンボル名を適切に表示できるようにするための変更です。

これらの変更により、コンパイラは文字列定数をより効率的に管理し、不要なオブジェクトの生成を避けることで、メモリ使用量を削減し、コンパイルプロセスの全体的な効率を向上させています。

## 変更の背景

このコミットの背景には、`crypto/cipher` パッケージの `AEAD` インターフェースが提供する認証付き暗号化機能の理解を深め、より安全かつ効率的な利用を促進するという目的があります。

1.  **AEADの概念理解の促進**: AEADは、データの機密性（暗号化）と完全性・認証性（認証）を同時に提供する暗号化モードです。しかし、その概念は一般的な暗号化モード（例: CBC, CTR）よりも複雑であり、特に「関連データ (Associated Data)」の役割や、認証がどのように機能するのかについて、ユーザーが正確に理解することが重要です。このコミットでは、その基本的なメカニズムを説明するWikipediaへのリンクを提供することで、ユーザーがより深い知識を得られるようにしています。

2.  **バッファ再利用の明確化**: `Seal` メソッド（暗号化）と `Open` メソッド（復号化）は、出力結果を格納するための `dst` バッファと、入力データ（平文または暗号文）を受け取るバッファを持っています。これらのメソッドは、メモリ効率のために `dst` と入力バッファが同じメモリ領域を指す「エイリアシング」を許容しています。しかし、エイリアシングを安全かつ意図通りに利用する方法が明確でなかったため、誤用や非効率なコードにつながる可能性がありました。特に、入力バッファのストレージを再利用して暗号化された出力や復号された出力を格納する一般的なパターンについて、具体的な推奨事項（例: `plaintext[:0]` を `dst` として使用する）を明記することで、ユーザーがより簡単に、かつ正しくこの機能を利用できるように改善されています。これにより、不要なメモリ割り当てを避け、パフォーマンスを向上させることができます。

これらの改善は、Go言語の暗号ライブラリの使いやすさと堅牢性を高めることを目的としています。

## 前提知識の解説

### 1. 暗号化と認証付き暗号 (AEAD)

*   **暗号化**: データを秘匿し、権限のない第三者には内容が分からないようにする技術です。共通鍵暗号（AESなど）や公開鍵暗号（RSAなど）があります。
*   **認証**: データが改ざんされていないこと、および送信元が正当であることを確認する技術です。ハッシュ関数やメッセージ認証コード (MAC)、デジタル署名などが用いられます。
*   **認証付き暗号 (Authenticated Encryption)**: 暗号化と認証の両方を同時に提供する暗号化モードです。これにより、データの機密性、完全性、認証性を一度に保証できます。単に暗号化するだけでは、攻撃者が暗号文を改ざんしても、復号時にその改ざんを検知できない可能性があります。認証付き暗号は、このような攻撃を防ぐために不可欠です。
*   **関連データ (Associated Data)**: AEADの重要な特徴の一つです。これは暗号化はされないが、認証の対象となるデータです。例えば、ネットワークプロトコルのヘッダー情報や、データベースのレコードIDなど、平文の一部ではないが、その文脈においてデータの完全性を保証する必要がある情報がこれに該当します。関連データが改ざんされると、認証が失敗し、復号処理が拒否されます。

### 2. Go言語の `crypto/cipher` パッケージ

`crypto/cipher` パッケージは、Go言語における共通鍵暗号のブロック暗号モードやストリーム暗号モードを実装するためのインターフェースと共通機能を提供します。このパッケージは、具体的な暗号アルゴリズム（例: AES）の実装とは分離されており、アルゴリズムに依存しない形で暗号モードを利用できるように設計されています。

*   **`cipher.Block` インターフェース**: ブロック暗号（例: AES）の基本的な操作（ブロックサイズ、暗号化、復号化）を定義します。
*   **`cipher.AEAD` インターフェース**: 認証付き暗号化モード（例: GCM, ChaCha20-Poly1305）の操作を定義します。このインターフェースは、`NonceSize()`、`Overhead()`、`Seal()`、`Open()` の各メソッドを持ちます。

### 3. `Seal` と `Open` メソッドのバッファエイリアシング

`Seal` メソッド（暗号化）と `Open` メソッド（復号化）は、それぞれ `dst` (destination) バッファと入力データ（`plaintext` または `ciphertext`）のバッファを受け取ります。

*   `Seal(dst, nonce, plaintext, additionalData []byte) []byte`
    *   `dst`: 暗号化された出力（暗号文と認証タグ）が書き込まれるスライス。
    *   `plaintext`: 暗号化する平文。
*   `Open(dst, nonce, ciphertext, additionalData []byte) ([]byte, error)`
    *   `dst`: 復号された出力（平文）が書き込まれるスライス。
    *   `ciphertext`: 復号する暗号文（認証タグを含む）。

これらのメソッドでは、メモリ割り当てを最適化するために、`dst` と入力データ（`plaintext` または `ciphertext`）が同じ基盤となる配列を共有する「エイリアシング」が許可されています。これは、入力データを読み取りながら、その同じメモリ領域に出力データを書き込むことで、新しいメモリ割り当てを避けることができるため、特に大きなデータを扱う場合にパフォーマンス上の利点があります。

しかし、エイリアシングを正しく利用するには、`dst` スライスの容量と長さ、そして入力スライスとの関係を理解しておく必要があります。特に、`plaintext[:0]` のように、既存のスライスの基盤配列を再利用しつつ、長さを0に設定した新しいスライスを `dst` として渡すテクニックは、Go言語でメモリ効率の良い処理を行う際の一般的なイディオムです。

## 技術的詳細

このコミットは、`src/crypto/cipher/gcm.go` ファイル内の `AEAD` インターフェースの定義に対するドキュメンテーションの変更です。

### 1. AEADの定義へのWikipediaリンク追加

これにより、`AEAD` の概念について詳しく知りたい開発者が、直接Wikipediaの「Authenticated encryption」のページを参照できるようになりました。これは、暗号技術の背景知識を深める上で非常に有用な情報源です。

### 2. `Overhead` メソッドのドキュメンテーション改善

変更前:
```go
	// Overhead returns the maximum difference between the lengths of a
	// plaintext and ciphertext.
	Overhead() int
```

変更後:
```go
	// Overhead returns the maximum difference between the lengths of a
	// plaintext and its ciphertext.
	Overhead() int
```
`ciphertext` の前に `its` が追加され、より自然な英語表現になりました。これは小さな変更ですが、ドキュメンテーションの品質向上に貢献します。

### 3. `Seal` メソッドのバッファエイリアシングに関する説明の明確化

変更前:
```go
	// The plaintext and dst may alias exactly or not at all.
	Seal(dst, nonce, plaintext, data []byte) []byte
```

変更後:
```go
	// The plaintext and dst may alias exactly or not at all. To reuse
	// plaintext's storage for the encrypted output, use plaintext[:0] as dst.
	Seal(dst, nonce, plaintext, additionalData []byte) []byte
```
ここで最も重要な変更は、`plaintext` のストレージを暗号化された出力のために再利用する方法が具体的に示された点です。「`To reuse plaintext's storage for the encrypted output, use plaintext[:0] as dst.`」という説明は、開発者がメモリ効率の良いコードを書くための明確なガイドラインを提供します。`plaintext[:0]` は、`plaintext` スライスの基盤となる配列を共有しつつ、長さが0の新しいスライスを作成するGoのイディオムです。これにより、`Seal` メソッドは `dst` に出力データを書き込む際に、既存の `plaintext` のメモリ領域を上書きして利用できます。

また、`data` パラメータ名が `additionalData` に変更され、より意図が明確になりました。これは、関連データ (Associated Data) の概念と一致します。

### 4. `Open` メソッドのバッファエイリアシングに関する説明の明確化

変更前:
```go
	// The ciphertext and dst may alias exactly or not at all.
	Open(dst, nonce, ciphertext, data []byte) ([]byte, error)
```

変更後:
```go
	// The ciphertext and dst may alias exactly or not at all. To reuse
	// ciphertext's storage for the encrypted output, use ciphertext[:0] as dst.
	Open(dst, nonce, ciphertext, additionalData []byte) ([]byte, error)
```
`Seal` メソッドと同様に、`ciphertext` のストレージを復号された出力のために再利用する方法が具体的に示されました。「`To reuse ciphertext's storage for the encrypted output, use ciphertext[:0] as dst.`」という説明は、復号処理においてもメモリ効率を向上させるための明確な指示となります。

同様に、`data` パラメータ名が `additionalData` に変更されています。

これらの変更は、コードの動作自体を変更するものではなく、あくまでドキュメンテーションの改善に焦点を当てています。しかし、これによりライブラリの利用者がより安全かつ効率的に `AEAD` インターフェースを扱えるようになるため、非常に価値のある変更と言えます。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、Go言語の `crypto/cipher` パッケージ内の `AEAD` インターフェースのドキュメンテーション文字列（コメント）の修正です。実際のロジックやインターフェースのシグネチャ自体は変更されていませんが、コメントの変更はライブラリの利用方法に大きな影響を与えます。

1.  **`AEAD` インターフェースのコメント**:
    *   `// data.` の後に `For a description of the methodology, see https://en.wikipedia.org/wiki/Authenticated_encryption` が追加されました。
    *   これは、`AEAD` が何であるかという基本的な説明に加えて、その背後にある暗号学的な原理や詳細について、信頼できる外部リソース（Wikipedia）への直接的な参照を提供します。これにより、開発者は `AEAD` の概念をより深く理解し、その適切な使用法を判断するための知識を得ることができます。

2.  **`Overhead()` メソッドのコメント**:
    *   `// plaintext and ciphertext.` が `// plaintext and its ciphertext.` に変更されました。
    *   これは非常に小さな文法的な修正ですが、ドキュメンテーションの可読性と正確性を向上させます。`its` を追加することで、`ciphertext` が `plaintext` に対応するものであることがより明確になります。

3.  **`Seal()` メソッドのコメントとシグネチャ**:
    *   コメント `// The plaintext and dst may alias exactly or not at all.` の後に、`To reuse plaintext's storage for the encrypted output, use plaintext[:0] as dst.` という具体的な使用例が追加されました。
    *   これは、`Seal` メソッドの `dst` 引数と `plaintext` 引数が同じ基盤となる配列を共有できる（エイリアシング）という重要な特性について、具体的なコードパターンを提示しています。`plaintext[:0]` は、既存の `plaintext` スライスの容量を保持しつつ、長さをゼロに設定した新しいスライスを作成するGoのイディオムです。これにより、`Seal` メソッドは `plaintext` が占めていたメモリ領域を、暗号化された出力のために再利用できます。これは、特に大きなデータを扱う際に、不要なメモリ割り当てを避けてパフォーマンスを向上させるための重要な最適化テクニックです。
    *   シグネチャの `data []byte` が `additionalData []byte` に変更されました。これは、この引数が「関連データ (Associated Data)」であることをより明確に示し、`AEAD` の概念との整合性を高めます。

4.  **`Open()` メソッドのコメントとシグネチャ**:
    *   `Seal()` メソッドと同様に、コメント `// The ciphertext and dst may alias exactly or not at all.` の後に、`To reuse ciphertext's storage for the encrypted output, use ciphertext[:0] as dst.` という具体的な使用例が追加されました。
    *   これは、`Open` メソッドの `dst` 引数と `ciphertext` 引数がエイリアシングできること、そして `ciphertext[:0]` を `dst` として使用することで、復号された平文のために `ciphertext` が占めていたメモリ領域を再利用できることを示しています。これもメモリ効率を向上させるための重要なテクニックです。
    *   シグネチャの `data []byte` が `additionalData []byte` に変更されました。これも `Seal()` と同様に、引数の意図を明確にするための変更です。

これらのドキュメンテーションの改善は、Go言語の `crypto/cipher` パッケージの `AEAD` インターフェースをより安全に、より効率的に、そしてより理解しやすく利用するための重要なステップです。特に、バッファのエイリアシングに関する具体的なガイダンスは、開発者がメモリ管理のベストプラクティスを適用する上で非常に役立ちます。

# [インデックス 28155] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTPレスポンスの自動gzip解凍処理がリバースプロキシに与える影響を改善するためのものです。具体的には、`http.Response`構造体に`Uncompressed`フィールドを追加し、自動解凍が行われた場合にその情報が失われないようにすることで、`Response.Write`が誤った`Connection: close`ヘッダを挿入する問題を解決しています。

## 変更の背景

Goの`net/http`パッケージの`Transport`は、デフォルトでHTTPレスポンスがgzip圧縮されている場合、自動的にそれを解凍します。この挙動は一般的なHTTPクライアントにとっては便利ですが、リバースプロキシにとっては問題となることがありました。

問題の核心は、自動解凍の過程で元の圧縮された`Content-Length`ヘッダの情報が失われることにあります。`Transport`がレスポンスを解凍すると、`Content-Length`ヘッダは`-1`に設定され、`Content-Encoding`ヘッダも削除されます。これにより、`http.Response.Write`メソッドがレスポンスを書き出す際に、ボディの長さが不明であると判断し、HTTP/1.1の仕様に従って`Connection: close`ヘッダを誤って挿入してしまう可能性がありました。

リバースプロキシは、バックエンドサーバーから受け取ったレスポンスをクライアントに透過的に転送する役割を担います。この際、元の`Content-Length`や`Content-Encoding`といったヘッダ情報は、クライアントへの正確なレスポンス生成や、HTTPパイプライン処理の維持に不可欠です。自動解凍によってこれらの情報が失われ、さらに`Connection: close`ヘッダが不適切に挿入されると、リバースプロキシの機能が損なわれたり、クライアントとの接続が意図せず切断されたりする問題が発生します。

このコミットは、この「情報損失」とそれに伴う「誤った`Connection: close`ヘッダの挿入」という問題を解決するために導入されました。特に、リバースプロキシが圧縮されたレスポンスをそのまま転送したい場合（CPUサイクルを節約するため）、`Transport.DisableCompression`を`true`に設定することが推奨されますが、そうでない場合でも、自動解凍が行われたことを`Response`オブジェクトが認識できるようにする必要がありました。

コミットメッセージには「Updates #15366 (the http2 side remains, once this is submitted)」とあり、この変更がIssue 15366の一部であり、HTTP/2に関する側面は別途対応される予定であることが示唆されています。

## 前提知識の解説

このコミットを理解するためには、以下のHTTPおよびGoの`net/http`パッケージに関する知識が必要です。

1.  **HTTP `Content-Length` ヘッダ**:
    *   HTTPメッセージボディのオクテット長を示すヘッダです。
    *   クライアントはこれを利用して、レスポンスボディの終わりを判断します。
    *   リバースプロキシは、この値を正確に転送する必要があります。

2.  **HTTP `Content-Encoding` ヘッダ**:
    *   メッセージボディに適用されたエンコーディング（圧縮方式など）を示します。
    *   例: `gzip`, `deflate`, `br` (Brotli)。
    *   クライアントはこれを見て、ボディを適切にデコードします。

3.  **HTTP `Connection` ヘッダ**:
    *   現在の接続に固有のオプションを指定するために使用されます。
    *   `Connection: close`は、現在のリクエスト/レスポンスの後に接続を閉じることを示します。
    *   `Connection: keep-alive`は、接続を維持して後続のリクエストに再利用できることを示します。
    *   HTTP/1.1では、ボディの長さが`Content-Length`または`Transfer-Encoding: chunked`で明示されない場合、サーバーは接続を閉じることでボディの終わりを示すことがあります。

4.  **HTTP `Transfer-Encoding` ヘッダ**:
    *   メッセージボディを安全に転送するために適用されたエンコーディングを示します。
    *   最も一般的なのは`chunked`で、ボディをチャンク（塊）に分割して転送し、各チャンクの前にそのサイズを記述します。これにより、`Content-Length`が事前に不明な場合でもボディを転送できます。

5.  **Go `net/http.Transport` の自動解凍**:
    *   `http.Client`が使用する`http.Transport`は、デフォルトで`Accept-Encoding: gzip`ヘッダをリクエストに含め、サーバーからgzip圧縮されたレスポンスを受け取ると自動的に解凍します。
    *   この挙動は`Transport.DisableCompression = true`を設定することで無効にできます。
    *   自動解凍が行われると、`http.Response`オブジェクトの`Body`は解凍されたコンテンツを提供しますが、元の`Content-Length`や`Content-Encoding`ヘッダは削除されるか、`Content-Length`が`-1`に設定されます。

6.  **リバースプロキシ**:
    *   クライアントからのリクエストを受け取り、それをバックエンドサーバーに転送し、バックエンドからのレスポンスをクライアントに返すサーバーです。
    *   クライアントからは単一のサーバーに見えます。
    *   ロードバランシング、SSL終端、キャッシュ、セキュリティなどの機能を提供します。
    *   レスポンスヘッダを正確に転送することが重要です。

## 技術的詳細

このコミットが解決しようとしている技術的な問題は、`net/http.Transport`による自動gzip解凍が、特にリバースプロキシのシナリオで引き起こす副作用にあります。

1.  **情報損失**: `Transport`がレスポンスボディを自動的に解凍すると、元の圧縮されたボディの`Content-Length`と`Content-Encoding: gzip`ヘッダは、`http.Response`オブジェクトから削除されます。`Content-Length`は`-1`に設定され、ボディの長さが不明であることを示します。これは、`http.Response`の`Body`が既に解凍されたデータを提供するため、一般的なクライアントにとっては問題ありません。

2.  **リバースプロキシへの影響**: リバースプロキシは、バックエンドから受け取ったHTTPレスポンスを、可能な限り元の形式でクライアントに転送する必要があります。しかし、自動解凍によって`Content-Length`が`-1`になり、`Content-Encoding`が削除されると、プロキシは元のレスポンスの特性を失います。もしプロキシがこの`http.Response`オブジェクトをそのまま利用してクライアントにレスポンスを生成しようとすると、問題が発生します。

3.  **`Response.Write`の挙動**: `http.Response.Write`メソッドは、`Content-Length`ヘッダも`Transfer-Encoding`ヘッダも存在しない場合、HTTP/1.1の仕様に従って、ボディの終わりを示すために`Connection: close`ヘッダをレスポンスに挿入します。これは、ボディの長さが不明な場合に接続を閉じることで、クライアントにボディの終端を知らせるための標準的なメカニズムです。

4.  **問題の発生**: リバースプロキシが`Transport`から受け取った自動解凍済みの`http.Response`を`Response.Write`で書き出す際、`Content-Length`が`-1`であり、`Transfer-Encoding`も設定されていないため、`Response.Write`は「ボディの長さが不明」と判断し、意図せず`Connection: close`ヘッダを挿入してしまいます。これにより、クライアントとの接続が不必要に切断され、HTTP Keep-Aliveなどの恩恵が受けられなくなったり、プロキシの動作が期待通りでなくなったりします。

このコミットは、`http.Response`に`Uncompressed`という新しいフィールドを追加することで、この問題を解決します。`Transport`が自動解凍を行った場合、この`Uncompressed`フィールドを`true`に設定します。そして、`Response.Write`メソッドは、`Content-Length`が`-1`であっても、`Uncompressed`が`true`であれば、`Connection: close`ヘッダを挿入しないように変更されます。これにより、リバースプロキシが自動解凍されたレスポンスを処理する際に、不適切な`Connection: close`ヘッダが挿入されるのを防ぎ、より正確なレスポンス転送が可能になります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

## コアとなるコードの解説

### `src/net/http/response.go`

```go
type Response struct {
	// ... 既存のフィールド ...

	// Uncompressed reports whether the response was sent compressed but
	// was decompressed by the http package. When true, reading from
	// Body yields the uncompressed content instead of the compressed
	// content actually set from the server, ContentLength is set to -1,
	// and the "Content-Length" and "Content-Encoding" fields are deleted
	// from the responseHeader. To get the original response from
	// the server, set Transport.DisableCompression to true.
	Uncompressed bool

	// ... 既存のフィールド ...
}

func (r *Response) Write(w io.Writer) error {
	// ... 既存のロジック ...

	// content-length, the only way to do that is the old HTTP/1.0
	// way, by noting the EOF with a connection close, so we need
	// to set Close.
	// 変更前: if r1.ContentLength == -1 && !r1.Close && r1.ProtoAtLeast(1, 1) && !chunked(r1.TransferEncoding) {
	if r1.ContentLength == -1 && !r1.Close && r1.ProtoAtLeast(1, 1) && !chunked(r1.TransferEncoding) && !r1.Uncompressed {
		r1.Close = true
	}

	// ... 既存のロジック ...
}
```

*   **`Response.Uncompressed`フィールドの追加**:
    *   この新しいブール型フィールドは、`net/http`パッケージによってレスポンスが自動的に解凍されたかどうかを示します。
    *   `true`の場合、`Body`は解凍されたコンテンツを提供し、元の`Content-Length`は`-1`に設定され、`Content-Length`および`Content-Encoding`ヘッダは削除されます。
    *   このフィールドのドキュメントは、リバースプロキシが圧縮を無効にするべきであること、および元の圧縮されたレスポンスが必要な場合は`Transport.DisableCompression`を`true`に設定する必要があることを明確にしています。

*   **`Response.Write`メソッドの変更**:
    *   `Response.Write`は、レスポンスボディの長さが不明（`ContentLength == -1`）で、かつ`Transfer-Encoding`が`chunked`でない場合に、`Connection: close`ヘッダを挿入するロジックを持っていました。
    *   変更後、この条件に`&& !r1.Uncompressed`が追加されました。
    *   これにより、レスポンスが自動解凍された結果として`ContentLength == -1`になっている場合（つまり`Uncompressed`が`true`の場合）は、`Connection: close`ヘッダが挿入されなくなります。これは、自動解凍されたレスポンスは、そのボディが完全に読み取られることを前提としているため、接続を閉じることでボディの終わりを示す必要がないという判断に基づいています。

### `src/net/http/transport.go`

```go
func (pc *persistConn) readLoop() {
	// ... 既存のロジック ...

	// If the server sent a gzipped response and the client didn't ask for it,
	// then we decompress it and remove the Content-Encoding header.
	// We also remove the Content-Length header because it refers to the
	// compressed size.
	if resp.Header.Get("Content-Encoding") == "gzip" && !pc.t.DisableCompression {
		// ... 解凍処理 ...
		resp.Header.Del("Content-Encoding")
		resp.Header.Del("Content-Length")
		resp.ContentLength = -1
		resp.Uncompressed = true // ここが追加された行
	}

	// ... 既存のロジック ...
}
```

*   **`persistConn.readLoop`での`Uncompressed`の設定**:
    *   `Transport`の内部で、サーバーからgzip圧縮されたレスポンスが送られ、かつ`Transport.DisableCompression`が`false`（つまり自動解凍が有効）の場合、レスポンスボディが解凍されます。
    *   この解凍処理の直後に、新しく追加された`resp.Uncompressed = true`という行が実行されます。
    *   これにより、`Response`オブジェクトは、自身が自動的に解凍されたものであるという状態を正確に保持するようになります。この情報は、前述の`Response.Write`メソッドで利用され、不適切な`Connection: close`ヘッダの挿入を防ぎます。

これらの変更により、`net/http`パッケージは、自動解凍されたレスポンスをより適切に扱い、特にリバースプロキシのようなシナリオでの互換性と正確性を向上させています。

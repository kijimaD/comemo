# [インデックス 21537] ファイルの概要

このコミットは、Goランタイムにおけるネットワークポーリング（netpoll）の初期化段階で発生しうるデッドロックのバグを修正します。特に`GOMAXPROCS=1`の環境で、`cgo`が無効化されている（`-tag=netgo`）場合に、プログラム起動時に稀に発生するデッドロックを解消することを目的としています。

## 元コミット内容

```
    runtime: fix spurious deadlock in netpoll

    There is a small possibility that runtime deadlocks when netpoll is just activated.
    Consider the following scenario:
    GOMAXPROCS=1
    epfd=-1 (netpoll is not activated yet)
    A thread is in findrunnable, sets sched.lastpoll=0, calls netpoll(true),
    which returns nil. Now the thread is descheduled for some time.
    Then sysmon retakes a P from syscall and calls handoffp.
    The "If this is the last running P and nobody is polling network" check in handoffp fails,
    since the first thread set sched.lastpoll=0. So handoffp decides that there is already
    a thread that polls network and so it calls pidleput.
    Now the first thread is scheduled again, finds no work and calls stopm.
    There is no thread that polls network and so checkdead reports deadlock.

    To fix this, don't set sched.lastpoll=0 when netpoll is not activated.

    The deadlock can happen if cgo is disabled (-tag=netgo) and only on program startup
    (when netpoll is just activated).

    The test is from issue 5216 that lead to addition of the
    "If this is the last running P and nobody is polling network" check in handoffp.

    Update issue 9576.

    Change-Id: I9405f627a4d37bd6b99d5670d4328744aeebfc7a
    Reviewed-on: https://go-review.googlesource.com/2750
    Reviewed-by: Ian Lance Taylor <iant@golang.org>
```

## 変更の背景

このコミットは、Goランタイムにおけるネットワークポーリング（`netpoll`）がまだ完全にアクティブになっていない、プログラム起動時の特定の条件下で発生するデッドロックを修正します。

デッドロックが発生するシナリオは以下の通りです。

1.  **`GOMAXPROCS=1`**: プロセッサ（P）が1つしかない環境。これはGoスケジューラが利用できる並列実行リソースが1つであることを意味します。
2.  **`epfd=-1`**: `netpoll`がまだ初期化されていない状態。`epfd`はLinuxにおける`epoll`ファイルディスクリプタを指し、これが`-1`であることは`netpoll`がまだネットワークイベントの監視を開始していないことを示します。
3.  **スレッドAが`findrunnable`を実行**: あるM（OSスレッド）が`findrunnable`関数（実行可能なGoroutineを探す関数）に入ります。
4.  **`sched.lastpoll=0`を設定**: このスレッドは`sched.lastpoll`を`0`に設定し、`netpoll(true)`を呼び出します。`sched.lastpoll`は、最後にネットワークポーリングが行われた時刻を記録するもので、`0`はポーリングが必要であることを示唆します。しかし、`netpoll`がまだアクティブでないため、`netpoll(true)`は`nil`を返します。
5.  **スレッドAがデスケジュールされる**: スレッドAは何らかの理由で一時的に実行を中断されます。
6.  **`sysmon`がPを再取得し`handoffp`を呼び出す**: `sysmon`（システムモニターGoroutine）が、システムコールから戻ってきたPを再取得し、`handoffp`関数を呼び出します。`handoffp`は、Pを他のMに引き渡す際に、ネットワークポーリングの必要性をチェックするロジックを含んでいます。
7.  **`handoffp`のチェックが失敗**: `handoffp`内の「これが最後の実行中のPであり、誰もネットワークをポーリングしていない場合」というチェックが失敗します。これは、スレッドAが既に`sched.lastpoll=0`を設定しているため、`handoffp`は「既にネットワークをポーリングするスレッドがいる」と誤って判断し、`pidleput`を呼び出してPをアイドル状態にします。
8.  **スレッドAが再スケジュールされ`stopm`を呼び出す**: スレッドAが再びスケジュールされますが、実行すべきGoroutineが見つからないため、`stopm`関数（Mを停止させる関数）を呼び出します。
9.  **デッドロックの発生**: この時点で、ネットワークをポーリングしているスレッドが実際には存在しないにもかかわらず、`checkdead`関数（デッドロックを検出する関数）がデッドロックを報告してしまいます。

この問題は、`cgo`が無効化されている（`-tag=netgo`）場合にのみ発生し、かつプログラムの起動時、`netpoll`が初期化される直前の非常に短い期間に限定されます。

## 前提知識の解説

### Goランタイムスケジューラ (GPMモデル)

Goランタイムスケジューラは、Goroutine（G）、論理プロセッサ（P）、OSスレッド（M）の3つのエンティティで構成されるGPMモデルを採用しています。

*   **G (Goroutine)**: Go言語の軽量な並行実行単位。ユーザーが記述する関数やメソッドがGoroutineとして実行されます。
*   **P (Processor)**: 論理プロセッサ。GoスケジューラがGoroutineを実行するために必要なリソースの抽象化です。PはMにアタッチされ、MがP上でGを実行します。`GOMAXPROCS`環境変数は、同時に実行できるPの数を制御します。
*   **M (Machine/Thread)**: OSスレッド。実際のCPU上でコードを実行するOSレベルのスレッドです。MはPを所有し、Pに割り当てられたGoroutineを実行します。

### ネットワークポーリング (`netpoll`)

GoのネットワークI/Oは、ノンブロッキングI/Oとイベント通知メカニズム（Linuxの`epoll`、macOS/BSDの`kqueue`など）を組み合わせて実装されています。このメカニズムをGoランタイム内で管理しているのが`netpoll`です。

*   `netpoll`は、ネットワーク操作が完了するまでGoroutineをブロックせず、代わりにGoroutineを待機状態にし、ネットワークイベントが発生した際にGoroutineを再開可能にします。
*   これにより、多数のネットワーク接続を効率的に処理し、Goroutineの並行性を最大限に活用できます。
*   `netpoll`は通常、専用のMによって実行され、ネットワークイベントを監視し、準備ができたGoroutineをPの実行キューに戻します。

### `sched.lastpoll`

`sched.lastpoll`は、Goランタイムのスケジューラが最後にネットワークポーリングを行った時刻を記録するグローバル変数です。この値は、ネットワークポーリングが定期的に行われているか、または必要とされているかを判断するために使用されます。`0`に設定されると、ポーリングが必要であるとスケジューラに示唆します。

### スケジューラ関連の主要関数

*   **`findrunnable`**: Mが実行可能なGoroutineを探すために呼び出す関数です。Pのローカルキュー、グローバルキュー、または他のPのキューからGoroutineを盗むことを試みます。
*   **`sysmon`**: システムモニターGoroutine。バックグラウンドで動作し、ガベージコレクションのトリガー、ネットワークポーリングの強制、長時間ブロックされているGoroutineの検出など、ランタイムの健全性を維持するためのタスクを実行します。
*   **`handoffp`**: あるMがPを解放し、そのPを別のMに引き渡す際に呼び出される関数です。例えば、Mがシステムコールに入った場合、そのMはPを解放し、他のMがそのPを利用できるようにします。`handoffp`は、Pの引き渡し中にネットワークポーリングの必要性をチェックします。
*   **`pidleput`**: Pをアイドル状態のPのリストに戻す関数です。
*   **`stopm`**: Mが実行すべきGoroutineを見つけられなかった場合に、Mを停止（スリープ）させる関数です。
*   **`checkdead`**: ランタイムがデッドロック状態にあるかどうかをチェックする関数です。実行可能なGoroutineが一つもなく、かつネットワークポーリングなどの外部イベントを待機しているMもいない場合にデッドロックと判断します。

### `cgo`と`-tag=netgo`

*   **`cgo`**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。ネットワーク関連の操作は、OSのネイティブなAPI（C言語で書かれていることが多い）を呼び出すため、`cgo`が利用されることがあります。
*   **`-tag=netgo`**: ビルド時にこのタグを指定すると、Goの標準ライブラリがCgoを使用せずにネットワーク関連の機能（DNS解決など）を純粋なGoで実装したバージョンを使用するようになります。これにより、Cgoの依存関係をなくすことができますが、特定の環境や状況下で挙動が変わる可能性があります。このコミットのデッドロックは、`netgo`タグが有効な場合にのみ発生するとされています。

## 技術的詳細

デッドロックの根本原因は、`netpoll`がまだ完全に初期化されていないにもかかわらず、`sched.lastpoll`が`0`に設定されてしまうことにあります。

通常、`sched.lastpoll`が`0`であることは、ネットワークポーリングが必要であることを示します。`handoffp`関数は、Pを引き渡す際に、もしこれが最後の実行中のPであり、かつ誰もネットワークをポーリングしていない（`sched.lastpoll`が`0`でない）場合に、ネットワークポーリングを強制するロジックを持っています。

しかし、問題のシナリオでは、以下の誤解が生じます。

1.  **誤った`sched.lastpoll`の設定**: `findrunnable`内のスレッドが、`netpoll`がまだアクティブでないにもかかわらず、`sched.lastpoll`を`0`に設定してしまいます。これは、ポーリングが必要であるという誤ったシグナルをスケジューラに送ります。
2.  **`handoffp`の誤った判断**: その後、`sysmon`によって呼び出された`handoffp`は、`sched.lastpoll=0`という情報を見て、「既にネットワークをポーリングするスレッドがいる」と誤って判断します。そのため、`handoffp`はネットワークポーリングを強制せず、Pをアイドル状態にしてしまいます。
3.  **ポーリングスレッドの不在**: 実際には、`netpoll`はまだ初期化されておらず、ネットワークをポーリングしているスレッドは存在しません。
4.  **`stopm`と`checkdead`**: 最初に`sched.lastpoll=0`を設定したスレッドが再スケジュールされても、実行すべきGoroutineが見つからないため`stopm`を呼び出します。結果として、実行可能なGoroutineも、ネットワークイベントを待機しているMも存在しない状態となり、`checkdead`がデッドロックを報告してしまいます。

このデッドロックは、`netpoll`が初期化される前の非常に短い期間に、特定のタイミングで複数のスケジューラ操作が競合することで発生する、典型的な競合状態（race condition）です。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  **`src/runtime/netpoll.go`**:
    *   `netpollInited`という新しい`uint32`型のグローバル変数が追加されました。これは`netpoll`が初期化されたかどうかを示すフラグとして使用されます。
    *   `net_runtime_pollServerInit`関数（`netpoll`の初期化を行う関数）内で、`netpollInited`をアトミックに`1`に設定する行が追加されました。
    *   `netpollinited()`という新しいヘルパー関数が追加されました。これは`netpollInited`の値をアトミックに読み取り、`netpoll`が初期化されているかどうかを返します。

## コアとなるコードの解説

この修正の核心は、`netpoll`が実際に初期化され、ネットワークイベントを処理する準備ができた場合にのみ、`sched.lastpoll`を`0`に設定するように変更した点です。

*   **`netpollInited`フラグの導入**: `netpollInited`という新しいフラグは、`netpollinit()`が呼び出され、`netpoll`システムが完全にセットアップされたことを正確に示します。これにより、`netpoll`がまだ準備できていない段階で、`sched.lastpoll`が誤って`0`に設定されることを防ぎます。
*   **`proc1.go`での条件付き設定**: `src/runtime/proc1.go`の`findrunnable`関数内で、`xchg64(&sched.lastpoll, 0)`（`sched.lastpoll`を`0`に設定するアトミック操作）の前に、`netpollinited()`のチェックが追加されました。
    *   `if netpollinited() && xchg64(&sched.lastpoll, 0) != 0 { ... }`
    *   この変更により、`netpoll`がまだ初期化されていない場合（`netpollinited()`が`false`を返す場合）、`sched.lastpoll`は`0`に設定されません。
    *   これにより、`handoffp`が`sched.lastpoll=0`という誤った情報に基づいて「ネットワークをポーリングするスレッドがいる」と判断し、Pをアイドル状態にしてしまうことを防ぎます。
    *   結果として、ネットワークポーリングが必要な場合に、適切なMがポーリングを開始できるようになり、デッドロックが回避されます。

この修正は、`netpoll`の初期化状態を正確に追跡することで、スケジューラの判断ミスを防ぎ、競合状態を解消しています。

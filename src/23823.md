## 変更の背景

この変更の背景には、Go言語の`net`パッケージにおけるホスト名解決（DNSルックアップ）機能のテスト戦略の進化があります。元々`TestLookupHost`は、`LookupHost`や`LookupIP`といった関数が、CGO（C言語との連携機能）が有効な環境で正しく動作するかどうかを検証するために存在していました。CGOが有効な場合、Goのネットワークスタックはシステムコール（例えばLinuxの`getaddrinfo`）を直接呼び出すことがあり、Go独自のDNSリゾルバとは異なるコードパスを通るため、その動作を個別にテストする必要がありました。

しかし、時間の経過とともに、Goの`net`パッケージにはより具体的で包括的なテストが追加されていきました。具体的には、`TestLookupGooglePublicDNSAddr`（Google Public DNSのような既知の信頼できるDNSサービスへのルックアップをテスト）、`TestCgoLookupIP`（CGOを明示的に使用したIPルックアップをテスト）、`TestGoLookupIP`（Goネイティブのリゾルバを使用したIPルックアップをテスト）などが導入されました。これらの新しいテストは、`LookupHost`および`LookupIP`の様々な実行パス（CGOの有無、異なるDNSリゾルバの利用など）をより明確かつ網羅的にカバーするようになりました。

その結果、`TestLookupHost`が「localhost」という曖昧なホスト名を使用して行っていたテストは、他のテストによってカバーされるようになり、冗長かつ不必要であると判断されました。特に「localhost」は、システムの設定（`/etc/hosts`ファイルなど）によって解決されるIPアドレスが異なる可能性があり、テストの再現性や信頼性の観点からも理想的ではありませんでした。このコミットは、テストスイートの整理と効率化を目的としています。コミットメッセージに記載されている`Fixes #11182`は、このテストの冗長性や問題点を指摘するGoのIssueに対応するものです。

## 前提知識の解説

### Go言語の`net`パッケージ

`net`パッケージは、Go言語の標準ライブラリの一部であり、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルをサポートし、DNSルックアップ機能も含まれています。

### ホスト名解決（DNSルックアップ）

ホスト名解決とは、`www.example.com`のような人間が読めるホスト名を、`192.0.2.1`のようなIPアドレスに変換するプロセスです。Goの`net`パッケージには、このための`LookupHost`（ホスト名からIPアドレスのリストを取得）や`LookupIP`（ホスト名からIPアドレスのリストを取得、より低レベル）などの関数が提供されています。

### CGO (`CGO_ENABLED`)

CGOは、GoプログラムがC言語のコードを呼び出すことを可能にするGoの機能です。`CGO_ENABLED`環境変数を`1`に設定すると、GoのビルドプロセスはCGOを有効にし、Goの`net`パッケージはホスト名解決のためにOSのネイティブなDNSリゾルバ（例えば、Unix系システムでは`getaddrinfo`関数）を利用するようになります。`CGO_ENABLED=0`の場合、Goは完全にGoで実装されたネイティブなDNSリゾルバを使用します。この違いは、DNSルックアップの動作やパフォーマンス、そしてテストの必要性に影響を与えます。

### `getaddrinfo`

`getaddrinfo`は、POSIX標準で定義されている関数で、ホスト名とサービス名（ポート番号など）から、ネットワークアドレス構造体のリストを取得するために使用されます。これは、多くのUnix系システムでDNSルックアップやサービス解決の基盤として利用されています。CGOが有効なGoプログラムでは、`net`パッケージがこの関数を内部的に呼び出すことがあります。

### Goのテストフレームワーク

Goには、`testing`パッケージという組み込みのテストフレームワークがあります。テスト関数は`Test`で始まり、`*testing.T`型の引数を取ります。テストの実行は`go test`コマンドで行われます。テストの目的は、コードが期待通りに動作することを検証し、リグレッション（機能退行）を防ぐことです。

### 「localhost」の曖昧性

「localhost」は、現在のマシン自身を指す特別なホスト名です。通常、IPv4では`127.0.0.1`、IPv6では`::1`に解決されます。しかし、システムによっては`/etc/hosts`ファイルなどで異なるIPアドレスが割り当てられていたり、複数のIPアドレスが設定されていたりする場合があります。このため、「localhost」に対するルックアップ結果は環境に依存する可能性があり、厳密なテストケースとしては不向きな場合があります。

## 技術的詳細

このコミットは、`src/net/hosts_test.go`ファイルから`TestLookupHost`関数を削除することで、Goの`net`パッケージのテストスイートを合理化します。

削除された`TestLookupHost`関数は、以下のロジックを持っていました。

1.  `LookupHost("localhost")`を呼び出して、`localhost`のIPアドレスリストを取得します。
2.  取得したIPアドレスリストをソートします。
3.  ソートされたリスト内で重複するIPアドレスがないかを確認します。重複が見つかった場合、`t.Fatalf`でテストを失敗させます。

このテストの主な目的は、`LookupHost`が`getaddrinfo`のようなシステムコールを使用する際に、重複するアドレスを返さないことを確認することでした。`getaddrinfo`の実装によっては、同じIPアドレスを複数回返すバグが存在する可能性があったため、このチェックはかつて重要でした。

しかし、コミットメッセージが示唆するように、Goのテストスイートは進化し、より堅牢なテストが導入されました。

*   **`TestLookupGooglePublicDNSAddr`**: これは、外部の信頼できるDNSサービス（例: Google Public DNS）に対してルックアップを実行することで、GoのDNSリゾルバが正しく機能するかを検証します。これにより、実際のインターネット環境でのホスト名解決の正確性が保証されます。
*   **`TestCgoLookupIP`**: このテストは、`CGO_ENABLED=1`の条件下で`LookupIP`が正しく動作するかを明示的に検証します。これにより、OSネイティブのリゾルバが使用されるコードパスがカバーされます。
*   **`TestGoLookupIP`**: このテストは、`CGO_ENABLED=0`の条件下、つまりGoネイティブのリゾルバが使用されるコードパスで`LookupIP`が正しく動作するかを検証します。

これらのテストは、`LookupHost`および`LookupIP`の主要な使用シナリオと内部実装パスをより網羅的にカバーしています。特に、`TestCgoLookupIP`は、`TestLookupHost`が元々意図していたCGO有効時の動作検証の役割を、より明確かつ制御された方法で果たしています。

また、「localhost」というホスト名を使用することの曖昧さも、このテストが冗長であると判断された理由の一つです。システム環境によって「localhost」の解決結果が異なる可能性があるため、一貫したテスト結果を得るのが難しい場合があります。より具体的なホスト名や、テスト環境で制御可能なホスト名を使用する方が、テストの信頼性は高まります。

結論として、`TestLookupHost`は、その目的が他のより優れたテストによって達成され、かつ「localhost」の利用による曖昧さがあったため、テストスイートから削除されることになりました。これにより、テストコードの保守性が向上し、冗長なテストの実行が回避されます。

## コアとなるコードの解説

削除された`TestLookupHost`関数は、`LookupHost("localhost")`を呼び出し、その結果として得られるIPアドレスのリストに重複がないかを検証していました。

```go
func TestLookupHost(t *testing.T) {
	// Can't depend on this to return anything in particular,
	// but if it does return something, make sure it doesn't
	// duplicate addresses (a common bug due to the way
	// getaddrinfo works).
	addrs, _ := LookupHost("localhost")
	sort.Strings(addrs) // 結果をソートして重複チェックを容易にする
	for i := 0; i+1 < len(addrs); i++ {
		if addrs[i] == addrs[i+1] { // 隣接する要素が同じであれば重複
			t.Fatalf("LookupHost(\\\"localhost\\\") = %v, has duplicate addresses\", addrs)
		}
	}
}
```

このテストは、特にCGOが有効な環境で`getaddrinfo`が呼び出される際に、稀に発生する可能性があった「重複するIPアドレスを返す」というバグを検出することを目的としていました。`sort.Strings(addrs)`で結果をソートすることで、重複するアドレスが隣接するように配置され、ループ内で簡単に比較できるようになっていました。

しかし、前述の「変更の背景」と「技術的詳細」で説明したように、`TestCgoLookupIP`などのより特化したテストが導入されたことで、CGO有効時の`LookupIP`および`LookupHost`の動作は十分にカバーされるようになりました。これらの新しいテストは、より制御された入力と期待される出力を持つため、`TestLookupHost`の持つ「localhost」という曖昧な入力に起因する不安定さや冗長性を解消します。

これらのテストは、`LookupHost`および`LookupIP`の主要な使用シナリオと内部実装パスをより網羅的にカバーしています。特に、`TestCgoLookupIP`は、`TestLookupHost`が元々意図していたCGO有効時の動作検証の役割を、より明確かつ制御された方法で果たしています。

また、「localhost」というホスト名を使用することの曖昧さも、このテストが冗長であると判断された理由の一つです。システム環境によって「localhost」の解決結果が異なる可能性があるため、一貫したテスト結果を得るのが難しい場合があります。より具体的なホスト名や、テスト環境で制御可能なホスト名を使用する方が、テストの信頼性は高まります。

結論として、`TestLookupHost`は、その目的が他のより優れたテストによって達成され、かつ「localhost」の利用による曖昧さがあったため、テストスイートから削除されることになりました。これにより、テストコードの保守性が向上し、冗長なテストの実行が回避されます。

## コアとなるコードの解説

削除された`TestLookupHost`関数は、`LookupHost("localhost")`を呼び出し、その結果として得られるIPアドレスのリストに重複がないかを検証していました。

```go
func TestLookupHost(t *testing.T) {
	// Can't depend on this to return anything in particular,
	// but if it does return something, make sure it doesn't
	// duplicate addresses (a common bug due to the way
	// getaddrinfo works).
	addrs, _ := LookupHost("localhost")
	sort.Strings(addrs) // 結果をソートして重複チェックを容易にする
	for i := 0; i+1 < len(addrs); i++ {
		if addrs[i] == addrs[i+1] { // 隣接する要素が同じであれば重複
			t.Fatalf("LookupHost(\\\"localhost\\\") = %v, has duplicate addresses\", addrs)
		}
	}
}
```

このテストは、特にCGOが有効な環境で`getaddrinfo`が呼び出される際に、稀に発生する可能性があった「重複するIPアドレスを返す」というバグを検出することを目的としていました。`sort.Strings(addrs)`で結果をソートすることで、重複するアドレスが隣接するように配置され、ループ内で簡単に比較できるようになっていました。

しかし、前述の「変更の背景」と「技術的詳細」で説明したように、`TestCgoLookupIP`などのより特化したテストが導入されたことで、CGO有効時の`LookupIP`および`LookupHost`の動作は十分にカバーされるようになりました。これらの新しいテストは、より制御された入力と期待される出力を持つため、`TestLookupHost`の持つ「localhost」という曖昧な入力に起因する不安定さや冗長性を解消します。

したがって、このコミットは、テストスイートの健全性を保ち、より効率的で信頼性の高いテスト構成へと移行するための、クリーンアップ作業の一環と見なすことができます。

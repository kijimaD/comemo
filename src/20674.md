## 元コミット内容

このコミットは、Goの `net/http` パッケージにおいて、HTTP/1.1プロトコルを使用する際に `Transfer-Encoding: identity` ヘッダを `Content-Length` ヘッダなしで利用できるようにする変更を導入します。これは、Server-Sent Events (SSE) の特定の推奨設定に対応するためのものであり、以前のコードベースに存在していた関連する「TODO」コメントを解消します。

## 変更の背景

HTTP/1.1では、メッセージボディの転送方法を制御するために `Transfer-Encoding` ヘッダが使用されます。通常、ボディの長さを事前に知らないストリーミング応答では `Transfer-Encoding: chunked` が用いられ、接続を維持したままデータをチャンク単位で送信します。しかし、特定のシナリオ、特にServer-Sent Events (SSE) の一部の推奨設定では、`Transfer-Encoding: identity` を使用し、かつ `Content-Length` を指定しないことで、応答ボディの送信後に接続を閉じる動作が求められる場合があります。

Goの `net/http` パッケージの以前の実装では、HTTP/1.1で `Content-Length` が存在しない場合、デフォルトで `Transfer-Encoding: chunked` を適用していました。これは、開発者が明示的に `Transfer-Encoding: identity` を設定しようとしても、その設定が無視され、強制的にチャンクエンコーディングが適用されてしまうという問題を引き起こしていました。コミットメッセージにある「TODO」コメントは、この挙動がカスタムの `Transfer-Encoding` 設定を上書きしてしまうことへの認識と、将来的な対応の必要性を示していました。

このコミットは、この「TODO」を解消し、開発者が `Transfer-Encoding: identity` を明示的に設定した場合に、`net/http` サーバーがその指示を尊重し、チャンクエンコーディングを無効化し、応答後に接続を閉じるように変更します。これにより、SSEの特定のユースケースや、`Content-Length` なしで `identity` 転送を必要とする他のシナリオに対応できるようになります。

## 前提知識の解説

### HTTP/1.1におけるヘッダ

*   **`Content-Length`**: HTTPメッセージボディのオクテット単位の長さを指定します。このヘッダが存在する場合、クライアントはボディの全体サイズを事前に知ることができます。
*   **`Transfer-Encoding`**: メッセージボディがどのようにエンコードされているかを示す「ホップバイホップ」ヘッダです。これは、メッセージが送信される途中で適用されるエンコーディングであり、エンドツーエンドの `Content-Encoding` とは異なります。
    *   **`Transfer-Encoding: chunked`**: メッセージボディが可変長のチャンクに分割されて送信されることを示します。各チャンクはサイズ情報とデータを含み、最後のチャンクはサイズ0で終了します。これにより、サーバーはボディの全長を事前に知らなくてもデータをストリーミングできます。
    *   **`Transfer-Encoding: identity`**: メッセージボディに転送エンコーディングが適用されていないことを示します。つまり、ボディはそのままの形式で送信されます。`Transfer-Encoding` ヘッダが存在する場合、`Content-Length` ヘッダは無視されるべきです。`identity` が指定され、かつ `Content-Length` がない場合、通常は応答ボディの送信後に接続が閉じられることを意味します。

### Server-Sent Events (SSE)

Server-Sent Events (SSE) は、サーバーからクライアントへの一方向のデータストリーミングを可能にするWeb APIです。HTTP接続を介してイベントを継続的にプッシュするために使用されます。SSEは、リアルタイムの更新（ニュースフィード、株価、チャット通知など）をクライアントに配信するのに適しています。

SSEの一般的な実装では、`Content-Type: text/event-stream` ヘッダと `Transfer-Encoding: chunked` ヘッダが使用されます。これにより、サーバーはイベントデータをチャンクとして継続的に送信し、クライアントは接続を維持したまま新しいイベントを受信できます。しかし、特定の古いW3Cの推奨事項や、よりシンプルな実装では、`Transfer-Encoding: identity` を使用し、`Content-Length` を指定しないことで、単一のイベントを送信した後に接続を閉じるようなシナリオも考慮されていました。このコミットは、そのような特定のケースに対応するための柔軟性を提供します。

## 技術的詳細

Goの `net/http` パッケージのサーバーサイドでは、`chunkWriter` という内部構造体がHTTPレスポンスのボディ書き込みを管理しています。この `chunkWriter` は、レスポンスヘッダが書き込まれる際に、`Transfer-Encoding` や `Content-Length` の有無に基づいて、チャンクエンコーディングを適用するかどうか (`cw.chunking`) や、応答後に接続を閉じるべきか (`w.closeAfterReply`) を決定します。

このコミット以前は、`HTTP/1.1` 以上で `Content-Length` が指定されていない場合、`net/http` は自動的に `Transfer-Encoding: chunked` を適用し、`cw.chunking = true` と設定していました。これは、ストリーミング応答の一般的なケースをカバーするためのものでしたが、開発者が `Transfer-Encoding: identity` を明示的に設定した場合でも、この自動的なチャンクエンコーディングが優先されてしまうという問題がありました。

今回の変更では、このロジックに新しい条件分岐が追加されました。
`HTTP/1.1` 以上の場合の処理において、まず `Transfer-Encoding` ヘッダが設定されており、その値が `"identity"` であるかどうかをチェックします (`if hasTE && te == "identity"`)。

*   **`Transfer-Encoding: identity` が明示的に設定されている場合**:
    *   `cw.chunking = false` と設定され、チャンクエンコーディングが無効化されます。
    *   `w.closeAfterReply = true` と設定され、応答ボディの書き込みが完了した後に接続が閉じられるようになります。
    *   この挙動は、コミットメッセージで言及されている「Server-Sent Events candidate recommendation 11, section 8」で推奨される設定に合致するとされています。これは、`Content-Length` がない `identity` 転送では、クライアントがボディの終了を接続の終了によって判断するためです。

*   **`Transfer-Encoding: identity` が設定されていない場合（または他の値の場合）**:
    *   以前と同様に `cw.chunking = true` と設定され、`Transfer-Encoding: chunked` が適用されます。これは、`Content-Length` が不明なHTTP/1.1応答のデフォルトのストリーミング挙動を維持するためです。

この変更により、`net/http` サーバーは、開発者が `Transfer-Encoding: identity` を明示的に指定した場合に、その意図を正しく解釈し、適切な接続管理を行うことができるようになりました。

### `src/net/http/server.go` の変更点

変更の中心は `chunkWriter.writeHeader` メソッド内の条件分岐です。

```go
	} else if w.req.ProtoAtLeast(1, 1) {

*   `w.req.ProtoAtLeast(1, 1)`: リクエストのプロトコルバージョンがHTTP/1.1以上であることを確認します。
*   `if hasTE && te == "identity"`: ここが新しい条件分岐です。
    *   `hasTE`: レスポンスヘッダに `Transfer-Encoding` が存在するかどうか。
    *   `te == "identity"`: `Transfer-Encoding` の値が `"identity"` であるかどうか。
    *   この条件が真の場合、つまり開発者が明示的に `Transfer-Encoding: identity` を設定した場合、以下の処理が行われます。
        *   `cw.chunking = false`: チャンクエンコーディングを無効にします。これにより、ボディはチャンクに分割されずにそのまま送信されます。

*   `else` ブロック: 上記の条件が偽の場合（`Transfer-Encoding: identity` が設定されていない、または他の値の場合）、以前の挙動が維持されます。
    *   `cw.chunking = true`: チャンクエンコーディングを有効にします。
    *   `setHeader.transferEncoding = "chunked"`: `Transfer-Encoding: chunked` ヘッダが設定されます。これは、`Content-Length` が不明なHTTP/1.1応答のデフォルトのストリーミングメカニズムです。

```go
func TestIdentityResponseHeaders(t *testing.T) {
	// ... (ログ出力抑制などのセットアップ)

	ts := httptest.NewServer(HandlerFunc(func(w ResponseWriter, r *Request) {
		w.Header().Set("Transfer-Encoding", "identity") // ここでidentityを設定
		w.(Flusher).Flush() // ヘッダをフラッシュ
		fmt.Fprintf(w, "I am an identity response.") // ボディを書き込み
	}))
	defer ts.Close()

	res, err := Get(ts.URL) // クライアントからリクエスト
	// ... (エラーチェック)
	defer res.Body.Close()

	if g, e := res.TransferEncoding, []string(nil); !reflect.DeepEqual(g, e) {
		t.Errorf("expected TransferEncoding of %v; got %v", e, g)
	}
	if _, haveCL := res.Header["Content-Length"]; haveCL {
		t.Errorf("Unexpected Content-Length")
	}
	if !res.Close {
		t.Errorf("expected Connection: close; got %v", res.Close)
	}
}
```

このテストでは、`httptest.NewServer` を使用してテスト用のHTTPサーバーを起動し、ハンドラ内で明示的に `w.Header().Set("Transfer-Encoding", "identity")` を設定しています。

テストの検証項目は以下の通りです。

*   `res.TransferEncoding` が空のスライスであること: Goの `net/http` クライアントは、`Transfer-Encoding: identity` を受け取った場合、内部的にそれを「転送エンコーディングなし」として解釈するため、`res.TransferEncoding` は空になることが期待されます。
*   `Content-Length` ヘッダが存在しないこと: `Transfer-Encoding` が存在する場合、`Content-Length` は無視されるべきであり、このテストでは存在しないことを確認します。
*   `res.Close` が `true` であること: `Transfer-Encoding: identity` と `Content-Length` なしの組み合わせでは、応答後に接続が閉じられることが期待されるため、クライアント側で `Close` フラグが `true` になっていることを確認します。

このテストは、サーバーが `Transfer-Encoding: identity` を正しく処理し、期待されるクライアント側の挙動（`Content-Encoding` なし、`Content-Length` なし、接続クローズ）が実現されることを保証します。

## 元コミット内容

このコミットは、Goの `net/http` パッケージにおいて、HTTP/1.1プロトコルを使用する際に `Transfer-Encoding: identity` ヘッダを `Content-Length` ヘッダなしで利用できるようにする変更を導入します。これは、Server-Sent Events (SSE) の特定の推奨設定に対応するためのものであり、以前のコードベースに存在していた関連する「TODO」コメントを解消します。

## 変更の背景

HTTP/1.1では、メッセージボディの転送方法を制御するために `Transfer-Encoding` ヘッダが使用されます。通常、ボディの長さを事前に知らないストリーミング応答では `Transfer-Encoding: chunked` が用いられ、接続を維持したままデータをチャンク単位で送信します。しかし、特定のシナリオ、特にServer-Sent Events (SSE) の一部の推奨設定では、`Transfer-Encoding: identity` を使用し、かつ `Content-Length` を指定しないことで、応答ボディの送信後に接続を閉じる動作が求められる場合があります。

Goの `net/http` パッケージの以前の実装では、HTTP/1.1で `Content-Length` が存在しない場合、デフォルトで `Transfer-Encoding: chunked` を適用していました。これは、開発者が明示的に `Transfer-Encoding: identity` を設定しようとしても、その設定が無視され、強制的にチャンクエンコーディングが適用されてしまうという問題を引き起こしていました。コミットメッセージにある「TODO」コメントは、この挙動がカスタムの `Transfer-Encoding` 設定を上書きしてしまうことへの認識と、将来的な対応の必要性を示していました。

このコミットは、この「TODO」を解消し、開発者が `Transfer-Encoding: identity` を明示的に設定した場合に、`net/http` サーバーがその指示を尊重し、チャンクエンコーディングを無効化し、応答後に接続を閉じるように変更します。これにより、SSEの特定のユースケースや、`Content-Length` なしで `identity` 転送を必要とする他のシナリオに対応できるようになります。

## 前提知識の解説

### HTTP/1.1におけるヘッダ

*   **`Content-Length`**: HTTPメッセージボディのオクテット単位の長さを指定します。このヘッダが存在する場合、クライアントはボディの全体サイズを事前に知ることができます。
*   **`Transfer-Encoding`**: メッセージボディがどのようにエンコードされているかを示す「ホップバイホップ」ヘッダです。これは、メッセージが送信される途中で適用されるエンコーディングであり、エンドツーエンドの `Content-Encoding` とは異なります。
    *   **`Transfer-Encoding: chunked`**: メッセージボディが可変長のチャンクに分割されて送信されることを示します。各チャンクはサイズ情報とデータを含み、最後のチャンクはサイズ0で終了します。これにより、サーバーはボディの全長を事前に知らなくてもデータをストリーミングできます。
    *   **`Transfer-Encoding: identity`**: メッセージボディに転送エンコーディングが適用されていないことを示します。つまり、ボディはそのままの形式で送信されます。`Transfer-Encoding` ヘッダが存在する場合、`Content-Length` ヘッダは無視されるべきです。`identity` が指定され、かつ `Content-Length` がない場合、通常は応答ボディの送信後に接続が閉じられることを意味します。

### Server-Sent Events (SSE)

Server-Sent Events (SSE) は、サーバーからクライアントへの一方向のデータストリーミングを可能にするWeb APIです。HTTP接続を介してイベントを継続的にプッシュするために使用されます。SSEは、リアルタイムの更新（ニュースフィード、株価、チャット通知など）をクライアントに配信するのに適しています。

SSEの一般的な実装では、`Content-Type: text/event-stream` ヘッダと `Transfer-Encoding: chunked` ヘッダが使用されます。これにより、サーバーはイベントデータをチャンクとして継続的に送信し、クライアントは接続を維持したまま新しいイベントを受信できます。しかし、特定の古いW3Cの推奨事項や、よりシンプルな実装では、`Transfer-Encoding: identity` を使用し、`Content-Length` を指定しないことで、単一のイベントを送信した後に接続を閉じるようなシナリオも考慮されていました。このコミットは、そのような特定のケースに対応するための柔軟性を提供します。

## 技術的詳細

Goの `net/http` パッケージのサーバーサイドでは、`chunkWriter` という内部構造体がHTTPレスポンスのボディ書き込みを管理しています。この `chunkWriter` は、レスポンスヘッダが書き込まれる際に、`Transfer-Encoding` や `Content-Length` の有無に基づいて、チャンクエンコーディングを適用するかどうか (`cw.chunking`) や、応答後に接続を閉じるべきか (`w.closeAfterReply`) を決定します。

このコミット以前は、`HTTP/1.1` 以上で `Content-Length` が指定されていない場合、`net/http` は自動的に `Transfer-Encoding: chunked` を適用し、`cw.chunking = true` と設定していました。これは、ストリーミング応答の一般的なケースをカバーするためのものでしたが、開発者が `Transfer-Encoding: identity` を明示的に設定した場合でも、この自動的なチャンクエンコーディングが優先されてしまうという問題がありました。

今回の変更では、このロジックに新しい条件分岐が追加されました。
`HTTP/1.1` 以上の場合の処理において、まず `Transfer-Encoding` ヘッダが設定されており、その値が `"identity"` であるかどうかをチェックします (`if hasTE && te == "identity"`)。

*   **`Transfer-Encoding: identity` が明示的に設定されている場合**:
    *   `cw.chunking = false` と設定され、チャンクエンコーディングが無効化されます。
    *   `w.closeAfterReply = true` と設定され、応答ボディの書き込みが完了した後に接続が閉じられるようになります。
    *   この挙動は、コミットメッセージで言及されている「Server-Sent Events candidate recommendation 11, section 8」で推奨される設定に合致するとされています。これは、`Content-Length` がない `identity` 転送では、クライアントがボディの終了を接続の終了によって判断するためです。

*   **`Transfer-Encoding: identity` が設定されていない場合（または他の値の場合）**:
    *   以前と同様に `cw.chunking = true` と設定され、`Transfer-Encoding: chunked` が適用されます。これは、`Content-Length` が不明なHTTP/1.1応答のデフォルトのストリーミング挙動を維持するためです。

この変更により、`net/http` サーバーは、開発者が `Transfer-Encoding: identity` を明示的に指定した場合に、その意図を正しく解釈し、適切な接続管理を行うことができるようになりました。

### `src/net/http/server.go` の変更点

変更の中心は `chunkWriter.writeHeader` メソッド内の条件分岐です。

```go

*   `w.req.ProtoAtLeast(1, 1)`: リクエストのプロトコルバージョンがHTTP/1.1以上であることを確認します。
*   `if hasTE && te == "identity"`: ここが新しい条件分岐です。
    *   `hasTE`: レスポンスヘッダに `Transfer-Encoding` が存在するかどうか。
    *   `te == "identity"`: `Transfer-Encoding` の値が `"identity"` であるかどうか。

        *   `cw.chunking = false`: チャンクエンコーディングを無効にします。これにより、ボディはチャンクに分割されずにそのまま送信されます。

*   `else` ブロック: 上記の条件が偽の場合（`Transfer-Encoding: identity` が設定されていない、または他の値の場合）、以前の挙動が維持されます。

```go
func TestIdentityResponseHeaders(t *testing.T) {
	// ... (ログ出力抑制などのセットアップ)

	ts := httptest.NewServer(HandlerFunc(func(w ResponseWriter, r *Request) {
		w.Header().Set("Transfer-Encoding", "identity") // ここでidentityを設定

	// ... (エラーチェック)

	}
	if _, haveCL := res.Header["Content-Length"]; haveCL {
		t.Errorf("Unexpected Content-Length")
	}
	if !res.Close {
		t.Errorf("expected Connection: close; got %v", res.Close)

```

このテストでは、`httptest.NewServer` を使用してテスト用のHTTPサーバーを起動し、ハンドラ内で明示的に `w.Header().Set("Transfer-Encoding", "identity")` を設定しています。

テストの検証項目は以下の通りです。

*   `res.TransferEncoding` が空のスライスであること: Goの `net/http` クライアントは、`Transfer-Encoding: identity` を受け取った場合、内部的にそれを「転送エンコーディングなし」として解釈するため、`res.TransferEncoding` は空になることが期待されます。
*   `Content-Length` ヘッダが存在しないこと: `Transfer-Encoding` が存在する場合、`Content-Length` は無視されるべきであり、このテストでは存在しないことを確認します。
*   `res.Close` が `true` であること: `Transfer-Encoding: identity` と `Content-Length` なしの組み合わせでは、応答後に接続が閉じられることが期待されるため、クライアント側で `Close` フラグが `true` になっていることを確認します。

このテストは、サーバーが `Transfer-Encoding: identity` を正しく処理し、期待されるクライアント側の挙動（`Content-Encoding` なし、`Content-Length` なし、接続クローズ）が実現されることを保証します。

# [インデックス 20455] ファイルの概要

## 変更の背景

このコミットの背景には、Goランタイムにおけるスタック管理戦略の進化があります。Go 1.4で導入されたスタックコピーメカニズムは、それまでのセグメントスタック方式に代わるものでした。セグメントスタックは、スタックが複数の非連続なメモリブロックに分割されるため、特にホットパスでの関数呼び出しにおいてパフォーマンス上のオーバーヘッド（「ホットスタックスプリット」問題）を引き起こす可能性がありました。

スタックコピー方式では、ゴルーチンのスタックが必要に応じて拡張される際に、新しいより大きな連続したメモリ領域が割り当てられ、古いスタックの内容がそこにコピーされます。これにより、スタックが常に連続したメモリ領域に存在することが保証され、パフォーマンスが向上し、スタック管理が簡素化されます。

`StackCopyAlways` フラグは、このスタックコピーメカニズムが常に信頼性高く機能することをランタイムが「期待する」ことを示します。コミットメッセージにある「It worked at CL 134660043 on the builders, so I believe it will stick this time.」という記述は、以前の変更セット（CL 134660043）でこの機能がビルドシステム上で正常に動作したことを示唆しており、開発チームがこのスタックコピーの挙動に自信を持ったため、`StackCopyAlways` を恒久的に有効化するに至ったことを意味します。これは、Goランタイムのスタック管理モデルが成熟し、安定した段階に入ったことを示す重要な一歩でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutines)**: Go言語の軽量な並行処理単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。
2.  **スタック (Stack)**: 関数呼び出しの際に、ローカル変数、関数引数、リターンアドレスなどが格納されるメモリ領域です。
3.  **動的なスタック拡張 (Dynamic Stack Growth)**: 従来のOSスレッドのスタックは固定サイズであることが多いですが、Goのゴルーチンは最初は小さなスタック（例: Go 1.4時点では2KB）で開始します。関数呼び出しが深くなり、スタック領域が不足しそうになると、Goランタイムは自動的にスタックを拡張します。
4.  **スタックコピー (Stack Copying)**: Go 1.4で導入されたスタック拡張のメカニズムです。スタックが拡張される必要がある場合、ランタイムは現在のスタックよりも大きな新しい連続したメモリブロックを割り当てます。そして、古いスタックの内容（ローカル変数や呼び出しフレームなど）をこの新しいブロックにコピーします。これにより、スタックは常に連続したメモリ領域に存在し、キャッシュ効率が向上します。
5.  **セグメントスタック (Segmented Stacks)**: Go 1.4以前のスタック管理メカニズムです。スタックが不足すると、新しい小さなスタックセグメントが割り当てられ、既存のスタックにリンクされました。これにより、スタックは非連続なメモリブロックのリストとして表現されました。しかし、関数呼び出しが頻繁に行われる場合、異なるセグメント間のジャンプによるオーバーヘッドが発生し、「ホットスタックスプリット」と呼ばれるパフォーマンス問題を引き起こす可能性がありました。スタックコピーはこの問題を解決するために導入されました。
6.  **`StackCopyAlways`**: このフラグは、Goランタイムがスタックコピー操作を常に成功させることができると「期待する」ことを示します。つまり、スタックコピーがランタイムの基本的な動作として完全に統合され、信頼できるものとして扱われることを意味します。

## 技術的詳細

`StackCopyAlways` フラグを `0` から `1` に変更することは、Goランタイムのスタック管理における重要なマイルストーンを示します。

*   **`StackCopyAlways = 0` の状態**: この状態では、ランタイムはスタックコピーが常に可能であるとは「期待しない」ことを意味します。これは、スタックコピーメカニズムがまだ開発中であったり、特定のコーナーケースで問題が発生する可能性があったりする時期に設定されていた可能性があります。つまり、スタックコピーが失敗する可能性を考慮したコードパスが存在していたか、あるいはスタックコピーが必須ではない状況を想定していたかもしれません。
*   **`StackCopyAlways = 1` の状態**: このコミットによってこのフラグが `1` に設定されたことで、Goランタイムはスタックコピーが「常に」成功すると「期待する」ようになります。これは以下の技術的含意を持ちます。
    *   **信頼性の確立**: スタックコピーの実装が十分にテストされ、安定しており、あらゆる状況下でゴルーチンのスタックを確実にコピーできるという自信がランタイム開発者にあることを示します。
    *   **コードパスの簡素化**: スタックコピーが常に成功すると期待できるため、スタックコピーが失敗した場合のフォールバックロジックやエラーハンドリングが不要になるか、大幅に簡素化される可能性があります。これにより、ランタイムのコードベースがよりクリーンで効率的になります。
    *   **パフォーマンスの安定性**: スタックが常に連続したメモリ領域に存在することが保証されるため、CPUキャッシュの利用効率が向上し、ゴルーチンの実行パフォーマンスがより安定します。特に、スタックの拡張が必要な場合でも、予測可能なオーバーヘッドで処理できるようになります。
    *   **ガベージコレクションとの連携**: スタックコピーはガベージコレクタ（GC）とも密接に関連しています。スタックがコピーされる際に、スタック上のポインタが正しく更新される必要があります。`StackCopyAlways` が有効であることは、GCがスタック上のオブジェクトを正確に追跡し、マークできるという信頼性にも寄与します。

この変更は、Goランタイムがスタックコピーを主要かつ信頼性の高いスタック管理戦略として完全に採用したことを明確に示しており、Goの並行処理モデルの堅牢性をさらに高めるものです。

## コアとなるコードの解説

変更されたコードは、`src/runtime/stack.c` 内の `enum` 定義の一部です。

```c
enum
{
	StackCache = 1,

	StackCopyAlways = 0,	// expect to be able to copy stacks 100% of the time
};
```

この `enum` は、Goランタイムのスタック管理に関連する定数を定義しています。
変更前は `StackCopyAlways = 0` となっており、これはコメントにあるように「スタックを100%の確率でコピーできるとは期待しない」状態を示していました。つまり、スタックコピーが常に成功するとは限らない、あるいはその必要がない状況を想定していたことを意味します。

このコミットによって、`StackCopyAlways` の値が `0` から `1` に変更されました。

```c
	StackCopyAlways = 1,	// expect to be able to copy stacks 100% of the time
```

この変更は、Goランタイムが「スタックを100%の確率でコピーできると期待する」状態になったことを意味します。これは、スタックコピーメカニズムが十分に成熟し、信頼性が確立されたため、ランタイムがこの機能を常に利用し、その成功を前提として動作できるようになったことを示しています。これにより、スタック管理のロジックが簡素化され、全体的なランタイムの堅牢性が向上します。

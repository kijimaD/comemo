## 元コミット内容

Goランタイムにおいて、アロケートされたヒープ内の「スキャン可能なバイト数」を追跡するように変更します。スキャン可能なバイトとは、ガベージコレクタが各オブジェクトの最後のポインタフィールドに到達するまでにスキャンしなければならないバイトのことです。この情報は、GCのスキャン作業量をより堅牢に推定するために使用されます。

## 変更の背景

Goのガベージコレクタは、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。GCの効率は、Goアプリケーションのパフォーマンスに直結します。特に、GCがヒープをスキャンして到達可能なオブジェクトを特定する「マークフェーズ」は、その作業量によって停止時間（STW: Stop The World）や全体のスループットに大きな影響を与えます。

このコミット以前のGCは、スキャン作業量の見積もりが不十分であった可能性があります。ヒープ全体をスキャンするのではなく、実際にポインタが含まれている可能性のある領域（スキャン可能なバイト）のみを効率的にスキャンすることが重要です。この「スキャン可能なバイト数」を正確に追跡することで、GCは将来のスキャン作業量をより正確に予測し、それに基づいてGCのトリガータイミングや並行処理の調整を行うことができるようになります。結果として、GCのオーバーヘッドを削減し、アプリケーションのレイテンシを改善することが期待されます。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: Goはトレース型GCを採用しており、主にマーク＆スイープ方式で動作します。オブジェクトグラフを辿って到達可能なオブジェクトを「マーク」し、マークされなかったオブジェクトを「スイープ」してメモリを解放します。Go 1.5以降は並行GCが導入され、STW時間を最小限に抑える工夫がされています。
*   **ヒープ (Heap)**: プログラムが動的に確保するメモリ領域です。Goでは、`make`や`new`で作成されたオブジェクトはヒープに割り当てられます。
*   **オブジェクトのメモリレイアウト**: Goのオブジェクトは、データとポインタを含む場合があります。GCはポインタを辿ってオブジェクト間の参照関係を解決するため、どのバイトがポインタであるかを知る必要があります。
*   **ポインタ (Pointer) とスキャン (Scan)**: GCはヒープ上のオブジェクトをスキャンし、その中に含まれるポインタを見つけ出して、参照先のオブジェクトをマークします。このスキャン作業は、ポインタが含まれる可能性のある領域に限定されるべきです。
*   **`_type` と `typ.ptrdata`**: Goのランタイムは、各型に関するメタデータ（`_type`構造体）を保持しています。`typ.size`は型の全体のサイズを示し、`typ.ptrdata`はその型の先頭からポインタデータが占めるバイト数を示します。つまり、`typ.ptrdata`はオブジェクトのどの部分までポインタが含まれている可能性があるかを示す重要な情報です。
*   **`mcache`**: 各P（プロセッサ、Goスケジューラにおける論理CPU）に紐付けられたローカルなメモリキャッシュです。アロケーションの高速化のために使用され、GC統計の一部をローカルで集計します。
*   **`memstats`**: Goランタイム全体のメモリ統計を保持する構造体です。GCの動作状況やヒープの使用状況など、様々なメモリ関連のメトリクスが含まれます。

## 技術的詳細

このコミットの核心は、GCがスキャンする必要があるヒープメモリの量をより正確に測定するための新しいメトリクス `heap_scan` の導入とその追跡メカニズムです。

1.  **`mcache.local_scan` の導入**: 各Pのローカルキャッシュ `mcache` に `local_scan` というフィールドが追加されました。これは、そのPがローカルでアロケートしたオブジェクトのうち、GCがスキャンする必要があるバイト数の合計を一時的に保持します。
2.  **`memstats.heap_scan` の導入**: グローバルなメモリ統計 `memstats` に `heap_scan` というフィールドが追加されました。これは、ヒープ全体におけるスキャン可能なバイト数の合計を保持します。`mcache.local_scan` の値は定期的に `memstats.heap_scan` に集約されます。
3.  **`mallocgc` でのスキャンバイト数計算**: オブジェクトがアロケートされる際、`mallocgc` 関数内でそのオブジェクトのスキャン可能なバイト数が計算され、`_g_.m.mcache.local_scan` に加算されます。
    *   オブジェクトが配列の場合（`dataSize > typ.size`）、かつポインタを含む場合（`typ.ptrdata != 0`）、GCは配列の最後の要素までスキャンする必要があるため、`dataSize - typ.size + typ.ptrdata` がスキャンバイトとして加算されます。これは、配列の各要素がポインタを含む可能性があるため、配列全体のデータサイズから基本型のサイズを引いた部分と、基本型内のポインタデータ部分を考慮したものです。
    *   それ以外の場合（単一オブジェクトなど）、`typ.ptrdata` がそのままスキャンバイトとして加算されます。これは、オブジェクトの先頭から `typ.ptrdata` までの範囲にポインタが含まれる可能性があるためです。
4.  **`gcMark` での `heap_scan` 更新**: GCのマークフェーズが完了した後、`gcMark` 関数内で `memstats.heap_scan` が `gcController.scanWork` の値で更新されます。これは、GCが実際にスキャンした作業量に基づいて `heap_scan` を調整するものです。
5.  **`scanblock` からの `gcw.scanWork` 更新削除**: `scanblock` 関数は非ヒープルート（スタックなど）をスキャンするために使用されます。この関数内での `gcw.scanWork` の更新が削除されました。これは、`scanblock` がヒープオブジェクトのスキャンとは異なる文脈で使用されるため、ヒープのスキャン作業量見積もりには含めないという意図があると考えられます。コメントにも「This is used to scan non-heap roots, so it does not update gcw.bytesMarked or gcw.scanWork.」と明記されています。
6.  **`mheap` および `mstats` での集約**: `mHeap_Alloc_m`、`mHeap_Free`、`purgecachedstats` といった関数内で、各Pの `mcache.local_scan` がグローバルな `memstats.heap_scan` に集約され、`mcache.local_scan` はリセットされます。これにより、グローバルな `heap_scan` が常に最新の状態に保たれます。

この変更により、GCはヒープ上の「ポインタを含む可能性のある領域」の総量を正確に把握できるようになります。この情報は、GCのヒューリスティック（GCの実行タイミングや並行処理の度合いを決定するロジック）を改善し、より予測可能で効率的なGC動作を実現するために利用されます。

## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムがヒープにオブジェクトを割り当てる際に、そのオブジェクト内でGCがスキャンする必要があるバイト数（`local_scan`）を正確に計算し、それをグローバルな統計情報（`heap_scan`）に集約するメカニズムを導入した点です。

`src/runtime/malloc.go` の `mallocgc` 関数内の以下のコードブロックがその中心です。

```go
 	if dataSize > typ.size {
 		// Array allocation. If there are any
 		// pointers, GC has to scan to the last
 		// element.
 		if typ.ptrdata != 0 {
 			c.local_scan += dataSize - typ.size + typ.ptrdata
 		}
 	} else {
 		c.local_scan += typ.ptrdata
 	}
```

ここで、`dataSize` は実際に割り当てられたメモリのサイズ、`typ.size` は型の基本サイズ、`typ.ptrdata` は型の先頭からポインタデータが占めるバイト数です。

1.  **`dataSize > typ.size` の場合**: これは配列の割り当てを示唆しています。例えば、`[]*MyStruct` のようなスライスが割り当てられた場合、`dataSize` はスライスの容量全体になり、`typ.size` は `*MyStruct` のサイズになります。この場合、配列の各要素がポインタを含む可能性があるため、GCは配列の最後の要素までスキャンする必要があります。
    *   `typ.ptrdata != 0` のチェックは、その型がそもそもポインタを含む可能性があるかどうかを確認します。ポインタを含まない型であれば、スキャンは不要です。
    *   `dataSize - typ.size + typ.ptrdata` の計算は、配列全体のサイズから基本型のサイズを引いた部分（つまり、追加で確保された配列要素のデータ部分）と、基本型が持つポインタデータ部分を合計して、スキャンすべきバイト数を算出しています。これにより、配列全体にわたってポインタが存在する可能性のある領域を正確に捉えます。
2.  **`else` の場合**: これは単一のオブジェクト割り当て、または配列ではない構造体などの割り当てです。この場合、オブジェクトの先頭から `typ.ptrdata` までの範囲にのみポインタが含まれる可能性があるため、`c.local_scan` に `typ.ptrdata` が直接加算されます。

この `local_scan` の値は、各Pの `mcache` に一時的に蓄積され、その後 `mheap` や `mstats` の関数を通じてグローバルな `memstats.heap_scan` に集約されます。`memstats.heap_scan` は、GCがスキャンする必要があるヒープ上の総バイト数を表す、より正確な指標となります。

`src/runtime/mgcmark.go` から `gcw.scanWork` の更新が削除されたのは、`scanblock` がヒープオブジェクトではなく、スタックなどの非ヒープルートをスキャンするために使われるためです。ヒープのスキャン作業量を見積もる `heap_scan` とは目的が異なるため、分離されました。

これらの変更により、GoのGCはヒープのスキャン作業量をより正確に把握し、GCの動作を最適化するための重要な情報源を得ることになります。これは、GCの停止時間の短縮やスループットの向上に繋がる可能性があります。

2.  **`memstats.heap_scan` の導入**: グローバルなメモリ統計 `memstats` に `heap_scan` というフィールドが追加されました。これは、ヒープ全体におけるスキャン可能なバイト数の合計を保持します。`mcache.local_scan` の値は定期的に `memstats.heap_scan` に集約されます。
3.  **`mallocgc` でのスキャンバイト数計算**: オブジェクトがアロケートされる際、`mallocgc` 関数内でそのオブジェクトのスキャン可能なバイト数が計算され、`_g_.m.mcache.local_scan` に加算されます。
    *   オブジェクトが配列の場合（`dataSize > typ.size`）、かつポインタを含む場合（`typ.ptrdata != 0`）、GCは配列の最後の要素までスキャンする必要があるため、`dataSize - typ.size + typ.ptrdata` がスキャンバイトとして加算されます。これは、配列の各要素がポインタを含む可能性があるため、配列全体のデータサイズから基本型のサイズを引いた部分と、基本型内のポインタデータ部分を考慮したものです。
    *   それ以外の場合（単一オブジェクトなど）、`typ.ptrdata` がそのままスキャンバイトとして加算されます。これは、オブジェクトの先頭から `typ.ptrdata` までの範囲にポインタが含まれる可能性があるためです。
4.  **`gcMark` での `heap_scan` 更新**: GCのマークフェーズが完了した後、`gcMark` 関数内で `memstats.heap_scan` が `gcController.scanWork` の値で更新されます。これは、GCが実際にスキャンした作業量に基づいて `heap_scan` を調整するものです。
5.  **`scanblock` からの `gcw.scanWork` 更新削除**: `scanblock` 関数は非ヒープルート（スタックなど）をスキャンするために使用されます。この関数内での `gcw.scanWork` の更新が削除されました。これは、`scanblock` がヒープオブジェクトのスキャンとは異なる文脈で使用されるため、ヒープのスキャン作業量見積もりには含めないという意図があると考えられます。コメントにも「This is used to scan non-heap roots, so it does not update gcw.bytesMarked or gcw.scanWork.」と明記されています。
6.  **`mheap` および `mstats` での集約**: `mHeap_Alloc_m`、`mHeap_Free`、`purgecachedstats` といった関数内で、各Pの `mcache.local_scan` がグローバルな `memstats.heap_scan` に集約され、`mcache.local_scan` はリセットされます。これにより、グローバルな `heap_scan` が常に最新の状態に保たれます。

この変更により、GCはヒープ上の「ポインタを含む可能性のある領域」の総量を正確に把握できるようになります。この情報は、GCのヒューリスティック（GCの実行タイミングや並行処理の度合いを決定するロジック）を改善し、より予測可能で効率的なGC動作を実現するために利用されます。

## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムがヒープにオブジェクトを割り当てる際に、そのオブジェクト内でGCがスキャンする必要があるバイト数（`local_scan`）を正確に計算し、それをグローバルな統計情報（`heap_scan`）に集約するメカニズムを導入した点です。

`src/runtime/malloc.go` の `mallocgc` 関数内の以下のコードブロックがその中心です。

```go
 	if dataSize > typ.size {
 		// Array allocation. If there are any
 		// pointers, GC has to scan to the last
 		// element.
 		if typ.ptrdata != 0 {
 			c.local_scan += dataSize - typ.size + typ.ptrdata
 		}
 	} else {
 		c.local_scan += typ.ptrdata
 	}
```

ここで、`dataSize` は実際に割り当てられたメモリのサイズ、`typ.size` は型の基本サイズ、`typ.ptrdata` は型の先頭からポインタデータが占めるバイト数です。

1.  **`dataSize > typ.size` の場合**: これは配列の割り当てを示唆しています。例えば、`[]*MyStruct` のようなスライスが割り当てられた場合、`dataSize` はスライスの容量全体になり、`typ.size` は `*MyStruct` のサイズになります。この場合、配列の各要素がポインタを含む可能性があるため、GCは配列の最後の要素までスキャンする必要があります。
    *   `typ.ptrdata != 0` のチェックは、その型がそもそもポインタを含む可能性があるかどうかを確認します。ポインタを含まない型であれば、スキャンは不要です。
    *   `dataSize - typ.size + typ.ptrdata` の計算は、配列全体のサイズから基本型のサイズを引いた部分（つまり、追加で確保された配列要素のデータ部分）と、基本型が持つポインタデータ部分を合計して、スキャンすべきバイト数を算出しています。これにより、配列全体にわたってポインタが存在する可能性のある領域を正確に捉えます。
2.  **`else` の場合**: これは単一のオブジェクト割り当て、または配列ではない構造体などの割り当てです。この場合、オブジェクトの先頭から `typ.ptrdata` までの範囲にのみポインタが含まれる可能性があるため、`c.local_scan` に `typ.ptrdata` が直接加算されます。

この `local_scan` の値は、各Pの `mcache` に一時的に蓄積され、その後 `mheap` や `mstats` の関数を通じてグローバルな `memstats.heap_scan` に集約されます。`memstats.heap_scan` は、GCがスキャンする必要があるヒープ上の総バイト数を表す、より正確な指標となります。

`src/runtime/mgcmark.go` から `gcw.scanWork` の更新が削除されたのは、`scanblock` がヒープオブジェクトではなく、スタックなどの非ヒープルートをスキャンするために使われるためです。ヒープのスキャン作業量を見積もる `heap_scan` とは目的が異なるため、分離されました。

これらの変更により、GoのGCはヒープのスキャン作業量をより正確に把握し、GCの動作を最適化するための重要な情報源を得ることになります。これは、GCの停止時間の短縮やスループットの向上に繋がる可能性があります。

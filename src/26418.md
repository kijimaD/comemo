# [インデックス 26418] ファイルの概要

このコミットは、NetBSDおよびDragonFly BSDオペレーティングシステムにおいて、Goランタイムが新しいスレッドを作成する際のシグナルスタックの取り扱いに関するバグを修正するものです。具体的には、これらのOSで新しいスレッドが親スレッドのシグナルスタックを継承してしまう問題に対処し、Goランタイムの整合性を保つための変更が加えられています。

## 変更の背景

Goランタイムは、OSのスレッド（M: Machine）上でGoルーチン（G: Goroutine）をスケジュールし実行します。シグナルは、プログラムの実行中に発生するイベント（例えば、不正なメモリアクセス、割り込み、タイマー期限切れなど）をOSがプロセスに通知するメカニズムです。シグナルハンドラが実行される際には、通常のスタックとは別の「シグナルスタック」を使用することが推奨されます。これは、シグナル発生時のスタックが破損している可能性や、シグナルハンドラが再帰的に呼び出される可能性に備えるためです。

NetBSDおよびDragonFly BSDでは、新しいスレッドが作成される際に、親スレッドのシグナルスタック設定をそのまま継承するというOSの挙動がありました。Goランタイムは各Mに対して独自のシグナルスタックを設定することを期待していますが、このOSの挙動により、新しく作成されたスレッドが誤った（親スレッドと同じ）シグナルスタックを持って起動してしまいます。

この問題は、複数のスレッドが同時にシグナルを受け取った場合に深刻な競合状態を引き起こす可能性があります。例えば、両方のスレッドが同じシグナルスタックを使用しようとすると、スタックの破損やデッドロックなど、予測不能な動作やクラッシュにつながる恐れがありました。Goランタイムの`minit`関数（Mの初期化を行う関数）は、この継承されたシグナルスタックの存在を想定しておらず、混乱を招く原因となっていました。

このコミットは、この問題を解決し、GoランタイムがNetBSDおよびDragonFly BSD上で安定して動作するようにするために導入されました。

## 前提知識の解説

### シグナルスタック (Signal Stack)
シグナルスタックは、シグナルハンドラが実行される際に使用される特別なスタック領域です。通常のプログラム実行スタックとは別に用意されることで、シグナル発生時にメインスタックが破損していたり、スタックオーバーフローの危険がある場合でも、シグナルハンドラを安全に実行できます。`sigaltstack`システムコールを使って設定されます。

### `sigaltstack`システムコール
`sigaltstack`は、プロセスがシグナルハンドラのために代替スタック（シグナルスタック）を設定、取得、または無効化するために使用するシステムコールです。
- `stack_t ss`構造体には、シグナルスタックのアドレス、サイズ、およびフラグ（`ss_flags`）が含まれます。
- `ss_flags`には`SS_DISABLE`というフラグがあり、これを設定すると、現在設定されているシグナルスタックを無効化できます。

### `pthread_create`
POSIXスレッド（pthreads）ライブラリの一部であり、新しいスレッドを作成するための関数です。Cgoコードで明示的に`pthread_create`を呼び出す場合、Goランタイムの制御外でスレッドが作成されるため、Goランタイムが提供するシグナルスタックの管理メカニズムが適用されません。

### GoのM-P-Gモデル
Goランタイムは、M（Machine）、P（Processor）、G（Goroutine）という3つの抽象概念を用いて並行処理を管理します。
- **G (Goroutine)**: Goの軽量な並行実行単位。ユーザーが書くGoコードが実行される場所。
- **P (Processor)**: Goルーチンを実行するための論理的なプロセッサ。GoルーチンをMにディスパッチする役割を担う。
- **M (Machine)**: OSのスレッド。PがGoルーチンを実行する物理的な場所。MはOSによってスケジュールされ、Goルーチンを実行するためにPと連携します。各Mは独自のOSスタックと、Goランタイムによって管理されるシグナルスタックを持つことがあります。

### `mstart`と`minit`
- `mstart`: 新しく作成されたM（OSスレッド）が最初に実行するGoランタイム内の関数です。この関数は、Mの初期化を行い、Goルーチンをスケジュールして実行を開始します。
- `minit`: `mstart`から呼び出されるMの初期化ルーチンの一部で、M固有のリソース（シグナルスタックなど）を設定します。

### Cgo
GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用すると、GoとCの間でデータを受け渡ししたり、Cライブラリの関数を呼び出したりできます。Cgoを介して`pthread_create`のようなOSスレッドを直接操作するCコードを呼び出す場合、Goランタイムはそれらのスレッドのライフサイクルや設定を完全に制御できないことがあります。

## 技術的詳細

NetBSDおよびDragonFly BSDにおける問題の核心は、`lwp_create`（NetBSDの軽量プロセス作成システムコール）や`pthread_create`のようなスレッド作成メカニズムが、新しいスレッドに親スレッドのシグナルスタック設定を「継承」させる点にありました。これは、Goランタイムが期待する動作とは異なります。Goランタイムは、各M（OSスレッド）が独立したシグナルスタックを持つことを前提としており、`minit`関数内で適切なシグナルスタックを設定します。

親スレッドのシグナルスタックが継承されると、以下の問題が発生します。
1.  **競合状態**: 複数のMが同じシグナルスタックを共有することになり、同時にシグナルを受け取った場合にスタックの破損やデッドロックが発生する可能性があります。
2.  **`minit`の混乱**: `minit`は、シグナルスタックがまだ設定されていないか、または無効な状態であることを期待して初期化処理を行います。しかし、継承されたシグナルスタックが存在すると、`minit`のロジックが混乱し、正しく動作しない可能性があります。

このコミットでは、この問題を解決するために、新しく作成されたスレッドがGoランタイムの`mstart`（または`netbsdMstart`）を実行する直前に、継承されたシグナルスタックを明示的に無効化するというアプローチを取っています。具体的には、`sigaltstack`システムコールを`SS_DISABLE`フラグ付きで呼び出すことで、既存のシグナルスタック設定をクリアします。これにより、`minit`が実行される際には、他のOSと同様にシグナルスタックが未設定の状態となり、Goランタイムが期待する初期化フローが正しく機能するようになります。

コミットメッセージには、Cgoコードが`pthread_create`を呼び出す場合の注意点も記載されています。Goランタイムが直接管理しないスレッドでは、この修正が適用されないため、Cgoユーザーは自身でシグナルスタックの管理に注意を払う必要があります。これは、GoランタイムがCgoによって作成されたスレッドの内部動作を完全に制御できないという、GoとCgoの相互作用における一般的な制約を示しています。

    ```go
    // netbsdMStart is the function call that starts executing a newly
    // created thread.  On NetBSD, a new thread inherits the signal stack
    // of the creating thread.  That confuses minit, so we remove that
    // signal stack here before calling the regular mstart.  It's a bit
    // baroque to remove a signal stack here only to add one in minit, but
    // it's a simple change that keeps NetBSD working like other OS's.
    // At this point all signals are blocked, so there is no race.
    //go:nosplit
    func netbsdMstart() {
    	signalstack(nil)
    	mstart()
    }
    ```

6.  **`src/runtime/sys_dragonfly_amd64.s`**
    - `TEXT runtime·lwp_start(SB)`アセンブリ関数内に、`runtime·signalstack(SB)`を呼び出すコードが追加されました。

## コアとなるコードの解説

### Cgo関連ファイル (`gcc_*.c`) の変更
これらのファイルは、CgoがGoランタイムのM（OSスレッド）を作成する際に使用されるC言語のコードです。`threadentry`関数は、新しいOSスレッドのエントリポイントとして機能します。
追加されたコードは、新しいスレッドがGoランタイムの初期化ルーチン（`mstart`）を呼び出す直前に実行されます。
- `memset(&ss, 0, sizeof ss);`: `stack_t`構造体`ss`をゼロクリアします。これは、構造体の内容を初期化し、特にスタックのアドレスやサイズを無効な状態にするためです。
- `ss.ss_flags = SS_DISABLE;`: `ss_flags`に`SS_DISABLE`を設定します。このフラグは、`sigaltstack`システムコールに渡されると、現在のスレッドに設定されているシグナルスタックを無効化するようOSに指示します。
- `sigaltstack(&ss, nil);`: このシステムコールを呼び出すことで、親スレッドから継承されたシグナルスタックが明示的に無効化されます。これにより、Goランタイムの`minit`が実行される際には、シグナルスタックがクリーンな状態であることが保証されます。コミットメッセージにあるように、この時点ではすべてのシグナルがブロックされているため、競合状態の心配はありません。

### `src/runtime/os1_netbsd.go` の変更
このファイルはNetBSD固有のGoランタイムコードを含んでいます。
- `newosproc`関数は、新しいOSスレッドを作成するGoランタイムの内部関数です。以前は、この新しいスレッドのエントリポイントとして`mstart`が直接指定されていました。
- 変更後、`netbsdMstart`という新しいラッパー関数が導入され、`newosproc`はこの`netbsdMstart`を新しいスレッドのエントリポイントとして指定するようになりました。
- `netbsdMstart`関数は、まず`signalstack(nil)`を呼び出します。`signalstack`はGoランタイム内部の関数で、`nil`を渡すことで現在のスレッドのシグナルスタックを無効化します。これはCgoコードで行われている`sigaltstack(&ss, nil)`と等価なGoランタイムの操作です。
- その後、`netbsdMstart`は本来の`mstart()`を呼び出し、Mの通常の初期化とGoルーチンのスケジューリングを開始します。
このアプローチにより、Goで作成されたスレッドも、Cgoで作成されたスレッドと同様に、`mstart`が実行される前に継承されたシグナルスタックを確実に無効化できるようになります。

### `src/runtime/sys_dragonfly_amd64.s` の変更
このファイルはDragonFly BSDのAMD64アーキテクチャ固有のアセンブリコードを含んでいます。`runtime·lwp_start`は、DragonFly BSD上で新しいOSスレッドが起動する際のエントリポイントとなるアセンブリ関数です。
- 追加されたアセンブリコードは、Goランタイムの`runtime·signalstack(SB)`関数を呼び出しています。
- `SUBQ $8, SP`と`ADDQ $8, SP`は、スタックポインタを調整して、`runtime·signalstack`関数に引数（この場合は`0`、つまり`nil`）を渡すための準備と後処理です。
- `MOVQ $0, 0(SP)`は、スタックのトップに`0`をプッシュし、これが`signalstack`関数への引数となります。
このアセンブリレベルでの変更も、Goランタイムの`mstart`が呼び出される前に、DragonFly BSD上で継承されたシグナルスタックを無効化することを目的としています。

これらの変更は、NetBSDとDragonFly BSDという特定のOSの挙動に合わせて、Goランタイムが新しいOSスレッドを起動する際のシグナルスタックの初期状態を調整するものです。これにより、Goランタイムの内部的な整合性が保たれ、シグナル処理に関する潜在的なバグが回避されます。

- **G (Goroutine)**: Goの軽量な並行実行単位。ユーザーが書くGoコードが実行される場所。
- **P (Processor)**: Goルーチンを実行するための論理的なプロセッサ。GoルーチンをMにディスパッチする役割を担う。
- **M (Machine)**: OSのスレッド。PがGoルーチンを実行する物理的な場所。MはOSによってスケジュールされ、Goルーチンを実行するためにPと連携します。各Mは独自のOSスタックと、Goランタイムによって管理されるシグナルスタックを持つことがあります。

### `mstart`と`minit`
- `mstart`: 新しく作成されたM（OSスレッド）が最初に実行するGoランタイム内の関数です。この関数は、Mの初期化を行い、Goルーチンをスケジュールして実行を開始します。
- `minit`: `mstart`から呼び出されるMの初期化ルーチンの一部で、M固有のリソース（シグナルスタックなど）を設定します。

### Cgo
GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用すると、GoとCの間でデータを受け渡ししたり、Cライブラリの関数を呼び出したりできます。Cgoを介して`pthread_create`のようなOSスレッドを直接操作するCコードを呼び出す場合、Goランタイムはそれらのスレッドのライフサイクルや設定を完全に制御できないことがあります。

## 技術的詳細

NetBSDおよびDragonFly BSDにおける問題の核心は、`lwp_create`（NetBSDの軽量プロセス作成システムコール）や`pthread_create`のようなスレッド作成メカニズムが、新しいスレッドに親スレッドのシグナルスタック設定を「継承」させる点にありました。これは、Goランタイムが期待する動作とは異なります。Goランタイムは、各M（OSスレッド）が独立したシグナルスタックを持つことを前提としており、`minit`関数内で適切なシグナルスタックを設定します。

親スレッドのシグナルスタックが継承されると、以下の問題が発生します。
1.  **競合状態**: 複数のMが同じシグナルスタックを共有することになり、同時にシグナルを受け取った場合にスタックの破損やデッドロックが発生する可能性があります。
2.  **`minit`の混乱**: `minit`は、シグナルスタックがまだ設定されていないか、または無効な状態であることを期待して初期化処理を行います。しかし、継承されたシグナルスタックが存在すると、`minit`のロジックが混乱し、正しく動作しない可能性があります。

このコミットでは、この問題を解決するために、新しく作成されたスレッドがGoランタイムの`mstart`（または`netbsdMstart`）を実行する直前に、継承されたシグナルスタックを明示的に無効化するというアプローチを取っています。具体的には、`sigaltstack`システムコールを`SS_DISABLE`フラグ付きで呼び出すことで、既存のシグナルスタック設定をクリアします。これにより、`minit`が実行される際には、他のOSと同様にシグナルスタックが未設定の状態となり、Goランタイムが期待する初期化フローが正しく機能するようになります。

コミットメッセージには、Cgoコードが`pthread_create`を呼び出す場合の注意点も記載されています。Goランタイムが直接管理しないスレッドでは、この修正が適用されないため、Cgoユーザーは自身でシグナルスタックの管理に注意を払う必要があります。これは、GoランタイムがCgoによって作成されたスレッドの内部動作を完全に制御できないという、GoとCgoの相互作用における一般的な制約を示しています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

1.  **`src/runtime/cgo/gcc_dragonfly_amd64.c`**
2.  **`src/runtime/cgo/gcc_netbsd_386.c`**
3.  **`src/runtime/cgo/gcc_netbsd_amd64.c`**
4.  **`src/runtime/cgo/gcc_netbsd_arm.c`**
    - これらのCgo関連ファイルでは、`threadentry`関数（Cgoが新しいスレッドを作成する際に呼び出すエントリポイント）に`stack_t ss;`の宣言と、以下のコードが追加されています。
    ```c
    	memset(&ss, 0, sizeof ss);
    	ss.ss_flags = SS_DISABLE;
    	sigaltstack(&ss, nil);
    ```

5.  **`src/runtime/os1_netbsd.go`**
    - `newosproc`関数内で`lwp_mcontext_init`の呼び出しが変更され、`funcPC(mstart)`の代わりに新しく定義された`funcPC(netbsdMstart)`が使用されるようになりました。
    - 新しい関数`netbsdMstart()`が追加されました。
    ```go
    // netbsdMStart is the function call that starts executing a newly
    // created thread.  On NetBSD, a new thread inherits the signal stack
    // of the creating thread.  That confuses minit, so we remove that
    // signal stack here before calling the regular mstart.  It's a bit
    // baroque to remove a signal stack here only to add one in minit, but
    // it's a simple change that keeps NetBSD working like other OS's.
    // At this point all signals are blocked, so there is no race.
    //go:nosplit
    func netbsdMstart() {
    	signalstack(nil)
    	mstart()
    }
    ```

6.  **`src/runtime/sys_dragonfly_amd64.s`**
    - `TEXT runtime·lwp_start(SB)`アセンブリ関数内に、`runtime·signalstack(SB)`を呼び出すコードが追加されました。
    ```assembly
    	// On DragonFly, a new thread inherits the signal stack of the
    	// creating thread.  That confuses minit, so we remove that
    	// signal stack here before calling the regular mstart.  It's
    	// a bit baroque to remove a signal stack here only to add one
    	// in minit, but it's a simple change that keeps DragonFly
    	// working like other OS's.  At this point all signals are
    	// blocked, so there is no race.
    	SUBQ	$8, SP
    	MOVQ	$0, 0(SP)
    	CALL	runtime·signalstack(SB)
    	ADDQ	$8, SP
    ```

## コアとなるコードの解説

### Cgo関連ファイル (`gcc_*.c`) の変更
これらのファイルは、CgoがGoランタイムのM（OSスレッド）を作成する際に使用されるC言語のコードです。`threadentry`関数は、新しいOSスレッドのエントリポイントとして機能します。
追加されたコードは、新しいスレッドがGoランタイムの初期化ルーチン（`mstart`）を呼び出す直前に実行されます。
- `memset(&ss, 0, sizeof ss);`: `stack_t`構造体`ss`をゼロクリアします。これは、構造体の内容を初期化し、特にスタックのアドレスやサイズを無効な状態にするためです。
- `ss.ss_flags = SS_DISABLE;`: `ss_flags`に`SS_DISABLE`を設定します。このフラグは、`sigaltstack`システムコールに渡されると、現在のスレッドに設定されているシグナルスタックを無効化するようOSに指示します。
- `sigaltstack(&ss, nil);`: このシステムコールを呼び出すことで、親スレッドから継承されたシグナルスタックが明示的に無効化されます。これにより、Goランタイムの`minit`が実行される際には、シグナルスタックがクリーンな状態であることが保証されます。コミットメッセージにあるように、この時点ではすべてのシグナルがブロックされているため、競合状態の心配はありません。

### `src/runtime/os1_netbsd.go` の変更
このファイルはNetBSD固有のGoランタイムコードを含んでいます。
- `newosproc`関数は、新しいOSスレッドを作成するGoランタイムの内部関数です。以前は、この新しいスレッドのエントリポイントとして`mstart`が直接指定されていました。
- 変更後、`netbsdMstart`という新しいラッパー関数が導入され、`newosproc`はこの`netbsdMstart`を新しいスレッドのエントリポイントとして指定するようになりました。
- `netbsdMstart`関数は、まず`signalstack(nil)`を呼び出します。`signalstack`はGoランタイム内部の関数で、`nil`を渡すことで現在のスレッドのシグナルスタックを無効化します。これはCgoコードで行われている`sigaltstack(&ss, nil)`と等価なGoランタイムの操作です。
- その後、`netbsdMstart`は本来の`mstart()`を呼び出し、Mの通常の初期化とGoルーチンのスケジューリングを開始します。
このアプローチにより、Goで作成されたスレッドも、Cgoで作成されたスレッドと同様に、`mstart`が実行される前に継承されたシグナルスタックを確実に無効化できるようになります。

### `src/runtime/sys_dragonfly_amd64.s` の変更
このファイルはDragonFly BSDのAMD64アーキテクチャ固有のアセンブリコードを含んでいます。`runtime·lwp_start`は、DragonFly BSD上で新しいOSスレッドが起動する際のエントリポイントとなるアセンブリ関数です。
- 追加されたアセンブリコードは、Goランタイムの`runtime·signalstack(SB)`関数を呼び出しています。
- `SUBQ $8, SP`と`ADDQ $8, SP`は、スタックポインタを調整して、`runtime·signalstack`関数に引数（この場合は`0`、つまり`nil`）を渡すための準備と後処理です。
- `MOVQ $0, 0(SP)`は、スタックのトップに`0`をプッシュし、これが`signalstack`関数への引数となります。
このアセンブリレベルでの変更も、Goランタイムの`mstart`が呼び出される前に、DragonFly BSD上で継承されたシグナルスタックを無効化することを目的としています。

これらの変更は、NetBSDとDragonFly BSDという特定のOSの挙動に合わせて、Goランタイムが新しいOSスレッドを起動する際のシグナルスタックの初期状態を調整するものです。これにより、Goランタイムの内部的な整合性が保たれ、シグナル処理に関する潜在的なバグが回避されます。

## 変更の背景

Goのガベージコレクタは、アプリケーションのパフォーマンスに大きな影響を与える重要なコンポーネントです。その動作を理解し、デバッグすることは、Goアプリケーションの最適化において不可欠です。`gcpacertrace`モードは、GCの内部動作、特にGCの「pacer」と呼ばれるコンポーネントに関する詳細な情報を提供するために設計されたデバッグ機能です。pacerは、GCの作業をスケジュールし、ヒープの使用率を目標値に維持する役割を担っています。

このコミット以前は、`gcpacertrace`モードはGCのpacerに関する情報を提供していましたが、GCのスイープフェーズがいつ完了したかについての明示的なトレースは不足していました。スイープフェーズは、マークされたオブジェクト以外のメモリを解放するプロセスであり、その完了はGCサイクル全体の重要なマイルストーンです。スイープ完了時のヒープの状態を把握することは、GCの効率性やアプリケーションのメモリ使用パターンを分析する上で非常に有用です。

この変更の背景には、開発者が`gcpacertrace`モードを使用してGCの動作をより深く理解し、デバッグできるようにするという目的があります。スイープ完了時の詳細なログを追加することで、GCのパフォーマンスボトルネックの特定や、メモリリークの調査などが容易になります。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）、非同期（asynchronous）、世代別（generational）ではないマーク＆スイープ（mark-and-sweep）方式を採用しています。主なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトを特定し、マークします。
    *   GoのGCは、アプリケーションの実行と並行してマーク作業を進めます（concurrent mark）。
    *   一時的にアプリケーションの実行を停止する「ストップ・ザ・ワールド」（STW: Stop-The-World）フェーズが短時間発生し、GCルートの特定やマークの完了処理が行われます。

2.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクト（到達不能なオブジェクト）が占めていたメモリを解放し、再利用可能な状態にします。
    *   このフェーズもアプリケーションの実行と並行して行われます（concurrent sweep）。
    *   GoのGCは、ヒープをスパン（span）と呼ばれる連続したメモリブロックに分割して管理しており、スイープはこれらのスパン単位で行われます。

### `gcpacertrace`モード

`gcpacertrace`は、Goランタイムのデバッグオプションの一つで、`GODEBUG`環境変数を通じて有効にできます（例: `GODEBUG=gcpacertrace=1 go run your_program.go`）。このモードを有効にすると、Goのガベージコレクタの内部動作、特にGCの「pacer」に関する詳細な情報が標準エラー出力にログとして出力されます。

*   **Pacer**: GoのGCは、アプリケーションのメモリ割り当て速度に応じてGCの実行を調整する「pacer」と呼ばれるメカニズムを持っています。pacerは、GCがヒープサイズを特定の目標値に維持するように、GCの開始タイミングや作業量を決定します。
*   **トレース情報**: `gcpacertrace`は、pacerがどのようにGCをスケジュールしているか、ヒープの使用状況、GCの目標値など、GCのパフォーマンス分析に役立つ多くの情報を提供します。

### `mheap_`と`memstats`

*   **`mheap_`**: Goランタイムのメモリヒープを管理するグローバルな構造体です。ヒープ内のスパンの管理、メモリの割り当てと解放、スイープの状態などが含まれます。
*   **`memstats`**: Goランタイムのメモリ統計情報を含む構造体です。`heap_live`（現在ライブなオブジェクトが占めるヒープサイズ）、`spanBytesAlloc`（スパンに割り当てられたバイト数）、`pagesSwept`（スイープされたページ数）など、GCの動作やメモリ使用状況を監視するための重要なメトリクスを提供します。

## 技術的詳細

このコミットは、`src/runtime/mgcsweep.go`ファイル内の`sweepone`関数に小さな変更を加えることで、`gcpacertrace`モードの出力を強化します。`sweepone`関数は、Goランタイムがヒープ内の単一のスパンをスイープする際に呼び出される関数です。この関数は、すべてのスパンのスイープが完了したかどうかを判断し、完了した場合には特別な値を返します。

変更の核心は、スイープが完了したと判断された直後に、`gcpacertrace`モードが有効である場合にのみ、追加のログメッセージを出力する点にあります。具体的には、`debug.gcpacertrace > 0`という条件が真である場合（つまり、`gcpacertrace`が有効な場合）、以下の情報を含むメッセージが`print`関数を通じて出力されます。

*   `pacer: sweep done at heap size`: スイープ完了時のライブヒープサイズ（MB単位）。
*   `allocated ... MB of spans`: スパンに割り当てられた合計メモリ量（MB単位）。
*   `swept ... pages`: スイープされたメモリページ数。

このログメッセージは、GCのスイープフェーズがいつ終了し、その時点でのヒープの状態がどうであったかを明確に示します。これにより、開発者はGCの動作を時系列で追跡し、特にスイープ完了がアプリケーションのパフォーマンスにどのように影響しているかを分析できるようになります。例えば、スイープ完了時のヒープサイズが異常に大きい場合、メモリリークの可能性や、GCのチューニングが必要である可能性を示唆する手がかりとなります。

## コアとなるコードの解説

変更箇所は`sweepone`関数内にあります。この関数は、`work.spans`というスパンのリストを順に処理し、スイープを行います。`idx >= uint32(len(work.spans))`という条件は、すべてのスパンのスイープが完了したことを意味します。

1.  `mheap_.sweepdone = 1`: スイープが完了したことを示すフラグを設定します。
2.  `_g_.m.locks--`: ロックカウンタをデクリメントします。
3.  `if debug.gcpacertrace > 0 && idx == uint32(len(work.spans))`:
    *   `debug.gcpacertrace > 0`: `gcpacertrace`デバッグモードが有効であるかどうかをチェックします。`GODEBUG=gcpacertrace=1`のように設定されている場合に真となります。
    *   `idx == uint32(len(work.spans))`: これは、スイープ対象のスパンがすべて処理され、スイープが完了したことを確認するための追加の条件です。`idx`が`work.spans`の長さに達したときに、すべてのスパンが処理されたと判断されます。
4.  `print(...)`: 上記の条件が満たされた場合、以下の情報を含むログメッセージが標準エラー出力に出力されます。
    *   `memstats.heap_live>>20`: 現在ライブなオブジェクトが占めるヒープサイズをMB単位で表示します（`>>20`は2の20乗で割ることでバイトをMBに変換）。
    *   `mheap_.spanBytesAlloc>>20`: スパンに割り当てられた合計バイト数をMB単位で表示します。
    *   `mheap_.pagesSwept`: スイープされたメモリページ数を表示します。
    *   `\n`: 改行コードで、ログメッセージの区切りを明確にします。
5.  `return ^uintptr(0)`: スイープが完了したことを呼び出し元に通知するための特別な戻り値です。

この変更により、`gcpacertrace`モードを使用している開発者は、GCのスイープフェーズがいつ完了したか、そしてその時点でのメモリ使用状況がどうであったかを、より正確かつ詳細に把握できるようになります。これは、GCの動作を理解し、アプリケーションのメモリ関連のパフォーマンス問題を診断する上で非常に貴重な情報となります。

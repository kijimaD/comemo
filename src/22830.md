# [インデックス 22830] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）トレースイベントに関する変更です。具体的には、`runtime/mgc.go`ファイルから`traceGoSched()`と`traceGoStart()`の呼び出しを削除し、GCのトレースロジックをGoの新しい並行GCモデルに合わせて調整しています。

## 元コミット内容

```
runtime: remove GoSched/GoStart trace events around GC

These were appropriate for STW GC, since it interrupted the allocating
Goroutine, but don't apply to concurrent GC, which runs on its own
Goroutine. Forced GC is still STW, but it makes sense to attribute the
GC to the goroutine that called runtime.GC().
```

## 変更の背景

この変更の背景には、Goランタイムのガベージコレクション（GC）メカニズムの進化があります。Goの初期バージョンでは、GCは主に「Stop-The-World (STW)」方式を採用していました。STW GCでは、GCが実行される間、アプリケーションのすべてのGoroutineが一時停止されます。これにより、GCの実行中にメモリ割り当てを行っていたGoroutineが中断され、GCの開始と終了時にGoroutineのスケジューリング（`GoSched`）と再開（`GoStart`）が発生していました。

しかし、Go 1.5以降、GoのGCは並行（Concurrent）GCへと移行しました。並行GCでは、GCの大部分の作業がアプリケーションのGoroutineと並行して実行されます。これにより、STWポーズの時間が大幅に短縮され、アプリケーションの応答性が向上しました。

並行GCの導入により、GCはもはやメモリ割り当てを行っているGoroutineを直接中断するのではなく、自身のGoroutine上で動作するようになりました。このため、GCの開始と終了時に`traceGoSched()`や`traceGoStart()`といったGoroutineのスケジューリングに関連するトレースイベントを記録することは、並行GCの動作モデルには合致しなくなりました。これらのイベントは、GCがGoroutineの実行を中断したことを示唆していましたが、並行GCではそのような直接的な中断は発生しないため、誤解を招く可能性がありました。

ただし、`runtime.GC()`を明示的に呼び出すことによる強制GCは、依然としてSTWで行われます。しかし、この場合でも、GCの作業は`runtime.GC()`を呼び出したGoroutineに起因すると考えるのが適切であり、GCが別のGoroutineを中断したかのようにトレースする必要はありません。

このコミットは、GoのGCがSTWから並行GCへと移行したことに伴い、トレースイベントのセマンティクスを新しいGCモデルに合わせるためのクリーンアップ作業の一環です。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクションは、プログラムが使用しなくなったメモリを自動的に解放するプロセスです。これにより、開発者は手動でのメモリ管理から解放され、メモリリークのリスクを低減できます。

*   **Stop-The-World (STW) GC**:
    Goの初期バージョンで採用されていたGC方式です。GCが実行される間、プログラムのすべてのGoroutineが一時的に停止します。これにより、GCはメモリの状態が変化しないことを保証し、安全にメモリを回収できます。しかし、STWポーズが長くなると、アプリケーションの応答性が低下し、ユーザー体験に悪影響を与える可能性がありました。

*   **並行 (Concurrent) GC**:
    Go 1.5以降で導入されたGC方式です。GCの大部分のフェーズ（マーキングなど）が、アプリケーションのGoroutineと並行して実行されます。これにより、STWポーズの時間を大幅に短縮し、アプリケーションのパフォーマンスへの影響を最小限に抑えることができます。並行GCは、トライカラーマーキング（White, Gray, Black）やライトバリアなどの技術を使用して、並行実行中のメモリの一貫性を維持します。

### Goroutineとスケジューリング

*   **Goroutine**:
    Goにおける軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数百万のGoroutineを同時に実行することも可能です。GoroutineはGoランタイムによって管理され、GoスケジューラによってOSスレッドにマッピングされて実行されます。

*   **Goスケジューラ**:
    Goランタイムの一部であり、Goroutineの実行を管理します。利用可能なOSスレッド（P: Processor）にGoroutine（G）を割り当て、実行を切り替えます。Goroutineは、I/O操作の待機、チャネル操作、または明示的な`runtime.Gosched()`呼び出しなどによって、実行を中断し、他のGoroutineにCPUを譲ることができます。

### Goのトレースイベント

Goランタイムは、内部の動作を可視化するためのトレースメカニズムを提供しています。これにより、GCの動作、Goroutineのスケジューリング、システムコールなど、ランタイムの様々なイベントを記録し、分析することができます。これらのトレースイベントは、パフォーマンスのボトルネックを特定したり、ランタイムの挙動を理解したりするのに役立ちます。

*   `traceGoSched()`:
    Goroutineが自発的に実行を中断し、Goスケジューラに制御を戻す際に記録されるトレースイベントです。これは、GoroutineがCPUを他のGoroutineに譲ることを示します。

*   `traceGoStart()`:
    Goroutineが実行を再開する際に記録されるトレースイベントです。これは、GoスケジューラがGoroutineにCPUを割り当て、その実行を再開したことを示します。

## 技術的詳細

このコミットは、`src/runtime/mgc.go`ファイル内の`gc`関数から`traceGoSched()`と`traceGoStart()`の呼び出しを削除しています。

以前のSTW GCモデルでは、GCが開始されると、メモリを割り当てていたGoroutineは強制的に中断され、GCが完了するまで待機する必要がありました。この中断は、Goroutineが自発的にスケジューラに制御を戻すのと同様の振る舞いとして`traceGoSched()`でトレースされ、GC完了後にGoroutineが再開される際に`traceGoStart()`でトレースされていました。これは、GCがGoroutineの実行フローに直接割り込む性質を正確に反映していました。

しかし、並行GCでは、GCの大部分は専用のGC Goroutine上で実行され、アプリケーションのGoroutineとは並行して動作します。アプリケーションのGoroutineは、GCのマーキングフェーズ中にメモリを割り当て続けることができます（ライトバリアによってGCの一貫性が保たれます）。STWフェーズは依然として存在しますが、それらは非常に短く、Goroutineのスケジューリングとは異なる目的（ルートの特定やマーク終了の同期など）のために行われます。

したがって、並行GCのコンテキストでは、GCの開始時に`traceGoSched()`を呼び出すことは、GCがアプリケーションGoroutineの実行を中断したという誤った印象を与えます。同様に、GCの終了時に`traceGoStart()`を呼び出すことも、GCが中断されたGoroutineを再開したという誤った印象を与えます。並行GCは、アプリケーションGoroutineの実行を直接中断するのではなく、自身のGoroutine上で独立して動作するため、これらのトレースイベントはもはや適切ではありません。

この変更により、GCトレースはより正確にGCの実際の動作を反映するようになります。GCの開始時には`traceGCStart()`が、終了時には`traceGCDone()`が引き続き呼び出されますが、これらはGC自体のライフサイクルイベントをトレースするものであり、Goroutineのスケジューリングとは直接関係ありません。

強制GC（`runtime.GC()`呼び出し）の場合でも、GCはSTWで実行されますが、そのGCは`runtime.GC()`を呼び出したGoroutineの要求によって開始されたものであり、そのGoroutineに起因すると考えるのが自然です。したがって、この場合でも`traceGoSched()`や`traceGoStart()`は不要と判断されました。

## コアとなるコードの解説

このコミットでは、`src/runtime/mgc.go`ファイルの`gc`関数から以下の2行が削除されています。

1.  **`traceGoSched()`の削除**:
    ```diff
    -		traceGoSched()
    		traceGCStart()
    ```
    この行は、`gc`関数の開始部分、`traceGCStart()`の直前にありました。以前のSTW GCでは、GCが開始されると、現在実行中のGoroutineが中断され、GCが実行される間、スケジューラに制御が戻されていました。`traceGoSched()`は、このGoroutineの中断とスケジューラへの制御の移行をトレースするためのものでした。並行GCでは、GCは自身のGoroutineで動作するため、アプリケーションGoroutineのこのような中断は発生せず、このトレースイベントは不要になりました。

2.  **`traceGoStart()`の削除**:
    ```diff
    		traceGCDone()
    -		traceGoStart()
    ```
    この行は、`gc`関数の終了部分、`traceGCDone()`の直後にありました。以前のSTW GCでは、GCが完了すると、中断されていたGoroutineが再開され、実行を継続していました。`traceGoStart()`は、このGoroutineの再開をトレースするためのものでした。並行GCでは、GCがアプリケーションGoroutineを直接中断して再開するわけではないため、このトレースイベントも不要になりました。

これらの削除により、GoのGCトレースは、並行GCの動作モデルにより正確に合致するようになり、GCのパフォーマンスプロファイリングやデバッグにおいて、より適切な情報を提供するようになります。

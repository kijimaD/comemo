## 変更の背景

このコミットは、GoのランタイムにおけるCgoの挙動、特に`ppc64x`アーキテクチャ（`ppc64`および`ppc64le`）上での外部リンキング（external linking）に関する問題を解決するために導入されました。

GoプログラムがCgoを使用してCコードと連携する場合、GoランタイムとCランタイムの間で関数呼び出しやデータ交換が行われます。この際、レジスタの状態やスタックフレームの管理など、アーキテクチャ固有の規約に従う必要があります。`_cgo_reginit`というシンボルは、GoランタイムがCgo呼び出しのためにレジスタを初期化する際に使用される内部関数です。

通常、Goプログラムは内部リンカ（internal linker）を使用してビルドされます。しかし、特定のシナリオ（例えば、既存のC/C++プロジェクトにGoコードを組み込む場合や、特定のデバッグツールを使用する場合）では、外部リンカ（external linker、例えば`gcc`）を使用する必要があります。

`ppc64x`アーキテクチャにおいて、外部リンカがGoのCgo関連コードを正しくリンクするためには、`_cgo_reginit`シンボルが外部から参照可能である（エクスポートされている）必要がありました。このコミット以前は、このシンボルがエクスポートされていなかったため、`ppc64x`上で外部リンキングを使用する際に問題が発生していました。この変更は、`ppc64x`アーキテクチャでのCgoと外部リンキングの互換性を確保することを目的としています。

## 前提知識の解説

### Cgo
Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。GoとCの間で相互運用を可能にし、既存のCライブラリを利用したり、パフォーマンスが重要な部分をCで記述したりする際に使用されます。Cgoを使用すると、Goのコード内にCのコードを直接記述したり、Cのヘッダファイルをインポートしたりできます。Cgoは、GoコンパイラとCコンパイラ（通常はGCCやClang）を連携させて、GoとCのコードをリンクします。

### ppc64xアーキテクチャ (ppc64 / ppc64le)
`ppc64x`は、IBMのPOWERアーキテクチャの64ビット版を指すGoのビルドタグです。具体的には、以下の2つのサブアーキテクチャを含みます。
*   **`ppc64`**: PowerPC 64-bit Big Endian。主に旧来のPOWERシステムや一部の組み込みシステムで使用されます。
*   **`ppc64le`**: PowerPC 64-bit Little Endian。IBM POWER8以降のプロセッサで主流であり、Linuxディストリビューション（Ubuntu, RHELなど）で広く採用されています。Goはこれらのアーキテクチャをサポートしており、サーバーや高性能計算の分野で利用されています。

これらのアーキテクチャは、レジスタの数、呼び出し規約、メモリモデルなどがx86-64などの他のアーキテクチャとは異なります。そのため、Cgoのような低レベルの相互運用機能では、アーキテクチャ固有の考慮が必要です。

### 外部リンキング (External Linking)
Goプログラムをビルドする際、Goツールチェーンは通常、独自のリンカ（内部リンカ）を使用します。この内部リンカは、Goのオブジェクトファイルと、Goランタイムや標準ライブラリのGo部分を結合して実行可能ファイルを生成します。

しかし、Cgoを使用する場合や、特定のシステムライブラリ（例えば、`glibc`）に依存する場合、またはデバッグツールとの連携のために、外部リンカ（通常はシステムにインストールされている`gcc`などのCコンパイラが提供するリンカ）を使用することがあります。これを外部リンキングと呼びます。

外部リンキングを使用すると、GoのオブジェクトファイルとCのオブジェクトファイルが、システムリンカによって結合されます。このプロセスでは、GoランタイムがCgo呼び出しのために提供する特定のシンボルが、外部リンカから参照可能である必要があります。もし必要なシンボルがエクスポートされていない場合、リンカはそれを見つけることができず、リンクエラーが発生します。

### `_cgo_reginit` シンボル
`_cgo_reginit`は、Goランタイム内部で使用されるシンボルで、Cgoを介してC関数を呼び出す際に、GoのスタックフレームからCの呼び出し規約に合わせたレジスタの状態を初期化する役割を担います。GoとCでは関数呼び出しの規約（引数の渡し方、戻り値の受け取り方、レジスタの使用方法など）が異なるため、Cgoはこれらの違いを吸収するための「トランポリン」コードを生成します。`_cgo_reginit`はそのトランポリンの一部として、特にレジスタの初期化を担当します。

## 技術的詳細

このコミットの技術的な核心は、`ppc64x`アーキテクチャにおけるCgoの外部リンキング時のシンボル可視性の問題にあります。

GoのCgoは、GoコードとCコード間の橋渡しをするために、いくつかの内部ヘルパー関数を使用します。`_cgo_reginit`はその一つで、GoからCへの呼び出しが行われる際に、Cの呼び出し規約に準拠するようにCPUレジスタを適切に設定する役割を担います。これは、Goの関数がCの関数を呼び出す前に、引数を正しいレジスタに配置したり、スタックを調整したりする処理の一部です。

通常、Goの内部リンカを使用する場合、Goランタイム内のこれらの内部シンボルは、Goのオブジェクトファイル内で解決されます。しかし、外部リンカを使用する場合、外部リンカはGoのオブジェクトファイルだけでなく、Cのオブジェクトファイルやシステムライブラリもリンクします。このとき、外部リンカは、Goランタイムが提供する特定のシンボル（この場合は`_cgo_reginit`）を、Goのオブジェクトファイルから参照しようとします。

`ppc64x`アーキテクチャでは、`crosscall_ppc64`という関数がGoランタイム内でCgo呼び出しのレジスタ設定を行うために使用されます。この関数が依存する`_cgo_reginit`シンボルが、外部リンカから見えない状態（エクスポートされていない状態）であったため、外部リンキング時にリンカエラーが発生していました。

このコミットは、`//go:cgo_export_static _cgo_reginit`というディレクティブを`src/runtime/cgo_ppc64x.go`に追加することで、この問題を解決しています。このディレクティブは、Goコンパイラに対して、`_cgo_reginit`シンボルを静的にエクスポートするよう指示します。これにより、外部リンカがGoのオブジェクトファイルを処理する際に、`_cgo_reginit`シンボルを正しく解決できるようになり、`ppc64x`アーキテクチャ上でのCgoと外部リンキングが正常に機能するようになります。

この変更は、特定のアーキテクチャ（`ppc64x`）と特定のビルドモード（外部リンキング）の組み合わせでのみ顕在化する、低レベルなリンキングの問題に対処したものです。Goのクロスコンパイルや、異なるアーキテクチャでのCgoのサポートを維持するための重要な修正と言えます。

## コアとなるコードの解説

追加された`src/runtime/cgo_ppc64x.go`ファイルは、`ppc64`および`ppc64le`アーキテクチャに特化したCgoのランタイムサポートを提供します。

*   **`package runtime`**: このファイルがGoランタイムの一部であることを示します。
*   **`// +build ppc64 ppc64le`**: これはビルド制約（build tag）です。このファイル内のコードは、Goが`ppc64`または`ppc64le`アーキテクチャ向けにビルドされる場合にのみコンパイルに含まれることを意味します。これにより、アーキテクチャ固有のコードを分離し、他のアーキテクチャでのビルドに影響を与えないようにしています。
*   **コメント**:
    ```go
    // crosscall_ppc64 calls into the runtime to set up the registers the
    // Go runtime expects and so the symbol it calls needs to be exported
    // for external linking to work.
    ```
    このコメントは、この変更の目的を明確に説明しています。`crosscall_ppc64`という関数がGoランタイムを呼び出してレジスタを設定する際に、Goランタイムが期待するレジスタの状態を確立するために、呼び出されるシンボル（`_cgo_reginit`）が外部リンキングのためにエクスポートされる必要があることを示しています。
*   **`//go:cgo_export_static _cgo_reginit`**: これがこのコミットの核心となる変更です。
    *   `//go:` はGoツールチェーンに対するディレクティブ（指示）です。
    *   `cgo_export_static` は、指定されたシンボルを静的にエクスポートするようCgoツールに指示します。静的エクスポートとは、そのシンボルが最終的な実行可能ファイルまたはライブラリのシンボルテーブルに含められ、外部リンカから参照可能になることを意味します。
    *   `_cgo_reginit` は、エクスポートされるシンボルの名前です。前述の通り、これはCgo呼び出し時にレジスタを初期化するGoランタイムの内部関数です。

この一行を追加することで、`ppc64x`アーキテクチャでGoプログラムを外部リンキングする際に、リンカが`_cgo_reginit`シンボルを正しく解決できるようになり、リンクエラーが解消されます。これにより、`ppc64x`環境でのCgoの利用がより堅牢になります。

*   **`// +build ppc64 ppc64le`**: これはビルド制約（build tag）です。このファイル内のコードは、Goが`ppc64`または`ppc64le`アーキテクチャ向けにビルドされる場合にのみコンパイルに含まれることを意味します。これにより、アーキテクチャ固有のコードを分離し、他のアーキテクチャでのビルドに影響を与えないようにしています。
*   **コメント**:
    ```go
    // crosscall_ppc64 calls into the runtime to set up the registers the
    // Go runtime expects and so the symbol it calls needs to be exported
    // for external linking to work.
    ```
    このコメントは、この変更の目的を明確に説明しています。`crosscall_ppc64`という関数がGoランタイムを呼び出してレジスタを設定する際に、Goランタイムが期待するレジスタの状態を確立するために、呼び出されるシンボル（`_cgo_reginit`）が外部リンキングのためにエクスポートされる必要があることを示しています。
*   **`//go:cgo_export_static _cgo_reginit`**: これがこのコミットの核心となる変更です。
    *   `//go:` はGoツールチェーンに対するディレクティブ（指示）です。
    *   `cgo_export_static` は、指定されたシンボルを静的にエクスポートするようCgoツールに指示します。静的エクスポートとは、そのシンボルが最終的な実行可能ファイルまたはライブラリのシンボルテーブルに含められ、外部リンカから参照可能になることを意味します。
    *   `_cgo_reginit` は、エクスポートされるシンボルの名前です。前述の通り、これはCgo呼び出し時にレジスタを初期化するGoランタイムの内部関数です。

この一行を追加することで、`ppc64x`アーキテクチャでGoプログラムを外部リンキングする際に、リンカが`_cgo_reginit`シンボルを正しく解決できるようになり、リンクエラーが解消されます。これにより、`ppc64x`環境でのCgoの利用がより堅牢になります。

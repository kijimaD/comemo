## 変更の背景

Goのガベージコレクタ (GC) は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCは、オブジェクトの参照関係を追跡するために「ライトバリア (Write Barrier)」というメカニズムを使用します。ライトバリアは、プログラムがポインタを書き換える際に特定の処理を挿入し、GCがオブジェクトグラフの変更を正確に把握できるようにします。

ライトバリアが有効な間、変更されたポインタの情報は「ライトバッファ (Write Buffer, wbuf)」と呼ばれる一時的なバッファに蓄積されます。これらのバッファは、GCがマーク処理を進める上で重要な情報源となります。GCの特定のフェーズでは、これらのライトバッファの内容を「ハーベスト (harvest)」し、GCのマーク処理に反映させる必要があります。

このコミットが行われる前のGoランタイムでは、GCのマークフェーズに入る直前、つまり `stoptheworld()` (STW) が発生し、すべてのゴルーチンが停止した直後に `harvestwbufs()` が呼び出されていました。しかし、コミットメッセージが指摘するように、この時点での `harvestwbufs()` の呼び出しは「無意味 (pointless)」でした。その理由は、ライトバッファはマークフェーズ中、またはマーク終了フェーズ中にのみデータが書き込まれるため、マークフェーズ開始時点ではまだ空であるはずだからです。

この不要な処理を削除することで、GCの効率をわずかに向上させ、コードの複雑性を軽減することが目的です。

## 前提知識の解説

### Goのガベージコレクタ (GC)

GoのGCは、主に以下の特徴を持つコンカレントな三色マーク＆スイープGCです。

*   **三色マーキング (Tri-color Marking)**: オブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって訪問されていないオブジェクト。最終的に到達不能と判断されれば回収対象となります。
    *   **灰 (Gray)**: GCによって訪問されたが、そのオブジェクトが参照する他のオブジェクトがまだ訪問されていない状態。
    *   **黒 (Black)**: GCによって訪問され、そのオブジェクトが参照するすべてのオブジェクトも訪問済みである状態。
*   **コンカレントGC**: アプリケーションの実行と並行してマーク処理を進めます。これにより、アプリケーションの一時停止時間 (STW) を最小限に抑えます。
*   **ライトバリア (Write Barrier)**: コンカレントGCの正確性を保証するために不可欠なメカニズムです。アプリケーションがヒープ上のポインタを書き換える際に、GCがその変更を検知し、必要に応じて新しい参照先のオブジェクトを灰色にマークするなどの処理を行います。これにより、GCがオブジェクトグラフを走査している最中にアプリケーションがポインタを変更しても、回収されるべきでないオブジェクトが誤って回収されることを防ぎます。
*   **ライトバッファ (Write Buffer, wbuf)**: ライトバリアによって捕捉されたポインタの変更情報が一時的に格納されるバッファです。これらのバッファは、GCがマーク処理を進める際に定期的に処理（ハーベスト）され、マーク対象のオブジェクトを特定するために使用されます。

### GCの主要なフェーズ

GoのGCは、大まかに以下のフェーズで構成されます。

1.  **マークセットアップ (Mark Setup)**: 短いSTWが発生し、ライトバリアが有効になります。
2.  **コンカレントマーク (Concurrent Mark)**: アプリケーションと並行して、GCがオブジェクトグラフを走査し、到達可能なオブジェクトをマークします。このフェーズ中にライトバリアが有効であり、ライトバッファに情報が蓄積されます。
3.  **マークターミネーション (Mark Termination)**: 短いSTWが発生し、残りのマーク処理を完了させ、ライトバリアを無効にします。
4.  **コンカレントスイープ (Concurrent Sweep)**: アプリケーションと並行して、マークされなかった（白い）オブジェクトをメモリから解放します。

### `stoptheworld()` と `starttheworld()`

*   **`stoptheworld()`**: すべてのアプリケーションゴルーチンを一時停止させる処理です。GCの特定のクリティカルな操作（ライトバリアの有効化/無効化、GC状態の変更など）を行う際に、データの一貫性を保つために使用されます。STW時間はGo GCの重要な最適化目標の一つです。
*   **`starttheworld()`**: `stoptheworld()` によって停止されたアプリケーションゴルーチンを再開させる処理です。

### `harvestwbufs()`

`harvestwbufs()` は、ライトバッファ (wbufs) に蓄積されたポインタ変更情報を処理し、GCのマーク処理に反映させる関数です。この処理は、ライトバリアが有効な間に発生したポインタの変更をGCが認識するために不可欠です。

## 技術的詳細

このコミットの核心は、`harvestwbufs()` が呼び出されるタイミングの適切性に関するものです。

GoのGCサイクルにおいて、`src/runtime/mgc.go` の `gc` 関数はGCの主要なロジックを制御します。コミット前のコードでは、`gc` 関数内でマークフェーズ (`_GCmark`) に移行する直前、具体的には `stoptheworld()` が呼び出され、すべてのゴルーチンが停止した直後に `harvestwbufs()` が実行されていました。

```go

    // ...
    // Sync.
    stoptheworld()
    gcphase = _GCmark
    harvestwbufs() // <-- ここで呼び出されていた
    // Concurrent mark.
    starttheworld()
    // ...
}
```

しかし、ライトバッファ (wbufs) は、ライトバリアが有効な期間、つまりコンカレントマークフェーズ中、またはマークターミネーションフェーズ中にのみ、アプリケーションのポインタ書き込みによってデータが蓄積されます。

マークフェーズに入る直前、`stoptheworld()` が呼び出された時点では、まだコンカレントマークフェーズは開始されていません。したがって、ライトバリアはまだ有効になっておらず、アプリケーションゴルーチンも停止しているため、ライトバッファには新しいデータが書き込まれることはありません。この時点でのライトバッファは、前回のGCサイクルで残ったデータがある可能性はありますが、通常は空であるか、GCが既に処理済みであるべき状態です。

コミットメッセージが述べているように、「cached wbufs are only filled when we're in mark or mark termination」。つまり、ライトバッファはマークフェーズまたはマーク終了フェーズ中にのみデータが書き込まれます。したがって、マークフェーズに入る直前の `harvestwbufs()` の呼び出しは、処理すべきデータがないため、実質的に何もしない無駄な操作となります。

このコミットは、この「無意味な」`harvestwbufs()` の呼び出しを削除することで、GCのオーバーヘッドをわずかに削減し、コードの論理的な整合性を高めています。

コミットメッセージの後半には、「We should, but do not currently harvest at the end of the mark phase when we're running out of work to do.」という記述があります。これは、マークフェーズの終わりに、GCが処理すべき作業がなくなったときに `harvestwbufs()` を呼び出すべきだが、現状ではそうなっていない、という将来的な改善点を示唆しています。これは、マークフェーズ中に蓄積されたライトバッファの情報を確実に処理するための考慮事項です。

## コアとなるコードの解説

削除された `harvestwbufs()` の呼び出しは、`gc` 関数の内部、具体的にはGCのマークフェーズ (`_GCmark`) に移行する直前、かつ `starttheworld()` でアプリケーションゴルーチンが再開される前に位置していました。

このコードが削除された理由は、前述の「技術的詳細」で説明した通りです。

1.  **`stoptheworld()` の直後**: `stoptheworld()` が呼び出された時点では、すべてのアプリケーションゴルーチンは停止しています。
2.  **`_GCmark` フェーズ開始前**: `gcphase = _GCmark` の行は、GCがマークフェーズに入ったことを示す状態変数の設定です。この時点では、まだコンカレントマークフェーズは実質的に開始されていません。
3.  **ライトバリアの挙動**: ライトバリアは、コンカレントマークフェーズ中にアプリケーションがポインタを書き換える際に有効になり、ライトバッファにデータを書き込みます。マークフェーズ開始直前では、ライトバリアはまだ有効になっていないか、有効になっていてもアプリケーションが停止しているため、ライトバッファに新しいデータが書き込まれることはありません。

したがって、このタイミングで `harvestwbufs()` を呼び出しても、処理すべき新しいデータは存在せず、無駄な処理となるため削除されました。この変更は、GCのロジックをより正確にし、不要なオーバーヘッドを排除することを目的としています。

削除された `harvestwbufs()` の呼び出しは、`gc` 関数の内部、具体的にはGCのマークフェーズ (`_GCmark`) に移行する直前、かつ `starttheworld()` でアプリケーションゴルーチンが再開される前に位置していました。

このコードが削除された理由は、前述の「技術的詳細」で説明した通りです。

1.  **`stoptheworld()` の直後**: `stoptheworld()` が呼び出された時点では、すべてのアプリケーションゴルーチンは停止しています。
2.  **`_GCmark` フェーズ開始前**: `gcphase = _GCmark` の行は、GCがマークフェーズに入ったことを示す状態変数の設定です。この時点では、まだコンカレントマークフェーズは実質的に開始されていません。
3.  **ライトバリアの挙動**: ライトバリアは、コンカレントマークフェーズ中にアプリケーションがポインタを書き換える際に有効になり、ライトバッファにデータを書き込みます。マークフェーズ開始直前では、ライトバリアはまだ有効になっていないか、有効になっていてもアプリケーションが停止しているため、ライトバッファに新しいデータが書き込まれることはありません。

したがって、このタイミングで `harvestwbufs()` を呼び出しても、処理すべき新しいデータは存在せず、無駄な処理となるため削除されました。この変更は、GCのロジックをより正確にし、不要なオーバーヘッドを排除することを目的としています。

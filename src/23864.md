このコミットは、Goランタイムのトレーシング機能における`syscallexit`イベントの出力に関するバグ修正を目的としています。具体的には、システムコールからの復帰（`syscallexit`）イベントが、不適切なタイミングで、または誤ったトレーシングセッションで記録される可能性があった2つの主要な問題を解決します。これにより、Goプログラムの実行トレースの正確性と一貫性が向上します。

## 元コミット内容

Goランタイムのトレーシング機能において、`syscallexit`イベントのトレーシングに関する2つの問題が修正されました。

1.  `TraceStart`中に、`EvGoInSyscall`イベントがまだ発行されていないにもかかわらず、遅延された`EvGoSysExit`イベントが発行される可能性がありました。
2.  遅延された`EvGoSysExit`イベントが、次のトレーシングセッション中に発行される可能性がありました。

これらの問題は、Issue #10476 と Issue #11262 で報告されていました。

## 変更の背景

Goランタイムのトレーシング機能は、Goプログラムの実行状況を詳細に分析するための強力なツールです。特に、ゴルーチンがシステムコールに入ったり出たりするタイミングを追跡することは、パフォーマンスのボトルネックやスケジューリングの問題を特定する上で重要です。

このコミット以前は、`syscallexit`イベントのトレーシングに論理的な欠陥がありました。ゴルーチンがシステムコールから復帰する際、すぐにトレーシングイベントを記録できない場合があります（例えば、P（プロセッサ）が利用できない場合など）。このような場合、イベントは遅延され、後で記録されることになります。

この遅延メカニズムが原因で、以下の2つの主要な問題が発生していました。

1.  **イベントの順序の不整合**: `TraceStart`（トレーシング開始）時に、以前のシステムコールからの復帰イベント（`EvGoSysExit`）が、対応するシステムコール入りイベント（`EvGoInSyscall`）が記録される前に発行されてしまう可能性がありました。これにより、トレースデータに矛盾が生じ、分析が困難になります。
2.  **セッション間のイベント漏洩**: あるトレーシングセッションで発生したシステムコール復帰イベントが、そのセッション中に記録されず、次のトレーシングセッションが開始された際に誤って記録されてしまう可能性がありました。これは、トレースデータの分離性を損ない、特定のセッションの分析を歪めます。

これらの問題は、Goのトレーシングツールが提供する情報の信頼性を低下させるため、修正が必要でした。特に、`TestTraceStressStartStop`テストが不安定であると報告されており（`t.Skip("test is unreliable; issue #10476")`）、これが問題の存在を示唆していました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とトレーシングの仕組みに関する知識が必要です。

*   **P/M/Gモデル**: Goランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）の3つのエンティティを使用して並行性を管理します。
    *   **G (Goroutine)**: Goの軽量な実行単位。
    *   **P (Processor)**: Goスケジューラがゴルーチンを実行するために必要なリソースのコンテキスト。PはMにアタッチされ、MはP上でGを実行します。
    *   **M (Machine/OS Thread)**: OSスレッド。MはPを保持し、そのP上でGを実行します。システムコール中はMはPを解放し、他のMがそのPを利用できるようにします。
*   **システムコールとスケジューラ**: ゴルーチンがシステムコールを実行すると、そのゴルーチンは`Gsyscall`状態に入ります。この間、MはOSカーネル内でブロックされますが、Pは解放され、他のMが利用できるようになります。システムコールから復帰すると、ゴルーチンは再びGoスケジューラによって実行可能な状態に戻されます。
*   **Goトレーシング**: Goランタイムは、プログラムの実行中に発生する様々なイベント（ゴルーチンの生成、開始、終了、システムコール、GCなど）を記録するプロファイリングツールを提供します。これらのイベントは、`trace.go`ファイルで定義された`traceEv`定数（例: `traceEvGoInSyscall`, `traceEvGoSysExit`）として表現されます。
*   **`trace.enabled`と`trace.startingtrace`**:
    *   `trace.enabled`: トレーシングが現在有効であるかどうかを示すグローバルフラグ。
    *   `_g_.m.startingtrace`: トレーシングが開始されている最中であることを示すMごとのフラグ。`StartTrace`関数内で一時的に設定され、トレーシング開始時の特殊な処理を制御します。
*   **`cputicks()`と`nanotime()`**:
    *   `cputicks()`: CPUのサイクルカウンタを読み取り、高精度な時間測定に使用されます。
    *   `nanotime()`: ナノ秒単位のモノトニックな時間を提供します。
*   **`_g_.sysexitticks`**: ゴルーチンがシステムコールから復帰した時刻（`cputicks()`の値）を一時的に保存するためのゴルーチンごとのフィールド。Pが利用可能になったときに`EvGoSysExit`イベントを遅延して発行するために使用されます。
*   **`_g_.sysblocktraced`**: 特定のゴルーチンについて、`EvGoInSyscall`イベントが既に発行されたかどうかを示すゴルーチンごとのフラグ。これにより、`EvGoSysExit`イベントが対応する`EvGoInSyscall`イベントなしに発行されるのを防ぎます。

## 技術的詳細

このコミットの技術的解決策は、主に以下の3つのメカニズムに焦点を当てています。

1.  **`g`構造体への新しいフィールドの追加**:
    *   `sysblocktraced bool`: ゴルーチンがシステムコールに入った際に`EvGoInSyscall`イベントが発行されたことを示すフラグ。これにより、`EvGoSysExit`イベントが対応する`EvGoInSyscall`なしに発行されるのを防ぎます。
    *   `sysexitticks int64`: システムコールから復帰した際の`cputicks()`の値を保持します。これは、Pが利用可能になったときに`EvGoSysExit`イベントを遅延して発行するために使用されます。
2.  **`m`構造体への新しいフィールドの追加**:
    *   `startingtrace bool`: `StartTrace`関数が実行中であることを示すフラグ。これにより、トレーシング開始時の特殊なイベント処理を制御し、`trace.enabled`が設定される前に遅延イベントが誤って発行されるのを防ぎます。
3.  **`StartTrace`関数のロジック変更**:
    *   `trace.enabled`フラグをすぐに設定するのではなく、`_g_.m.startingtrace`フラグを一時的に設定します。これにより、`StartTrace`が実行されている間に`exitsyscall`が呼び出されても、`trace.enabled`が`true`になる前に遅延イベントが発行されるのを防ぎます。
    *   `StartTrace`内で、`_Gsyscall`状態のゴルーチンに対して`traceEvent(traceEvGoInSyscall, ...)`を発行する際に、`gp.sysblocktraced = true`を設定します。これにより、これらのゴルーチンがシステムコールから復帰した際に、対応する`EvGoInSyscall`が既に記録されていることが保証されます。
    *   `_Gsyscall`状態ではないゴルーチンに対しては、`gp.sysblocktraced = false`を設定し、以前のトレーシングセッションからの状態が残らないようにします。
    *   すべての初期イベントが発行された後で、`_g_.m.startingtrace = false`を解除し、`trace.enabled = true`を設定します。
4.  **`exitsyscall`関数のロジック変更**:
    *   システムコールから復帰する際に、`EvGoSysExit`イベントを即座に発行するのではなく、`_g_.sysexitticks`に復帰時刻を保存するだけに変更します。
    *   以前は`exitsyscall`内で`systemstack(func() { traceGoSysExit(exitTicks) })`を呼び出していましたが、このロジックは削除されました。
5.  **`execute`関数のロジック変更**:
    *   ゴルーチンが実行を開始する直前（Pが利用可能になった後）に、`gp.syscallsp != 0 && gp.sysblocktraced`の条件が満たされる場合、つまりシステムコールから復帰したゴルーチンで、かつ`EvGoInSyscall`が既に記録されている場合にのみ、`traceGoSysExit(gp.sysexitticks)`を呼び出すように変更されました。これにより、`EvGoSysExit`イベントが適切なタイミングで、かつ対応する`EvGoInSyscall`イベントの後に発行されることが保証されます。
6.  **`traceGoSysExit`関数の変更**:
    *   `ts != 0 && ts < trace.ticksStart`という条件が追加されました。これは、渡されたタイムスタンプ`ts`が現在のトレーシングセッションの開始時刻`trace.ticksStart`よりも古い場合、そのイベントを無視するというものです。これにより、以前のトレーシングセッションからの遅延イベントが現在のセッションに誤って混入するのを防ぎます。
7.  **`traceEvent`関数の変更**:
    *   イベントを記録するかどうかの条件に`!mp.startingtrace`が追加されました。これにより、`StartTrace`が実行中の間は、`trace.enabled`が`true`になる前に`exitsyscall`から呼び出される可能性のあるイベントが無視され、トレーシング開始時のイベントの順序の不整合を防ぎます。

これらの変更により、`EvGoSysExit`イベントは、対応する`EvGoInSyscall`イベントが既に記録されており、かつ現在のトレーシングセッション内で発生したものである場合にのみ、ゴルーチンがPを取得して実行を開始する直前に発行されるようになります。

## コアとなるコードの解説

このコミットの核心は、Goランタイムトレーシングにおけるシステムコール終了イベント（`EvGoSysExit`）の正確なタイミングとセッション分離を保証することにあります。

1.  **`g`および`m`構造体へのフィールド追加**:
    *   `g.sysblocktraced`: このフラグは、特定のゴルーチンがシステムコールに入った際に`EvGoInSyscall`イベントが既に記録されたかどうかを追跡します。これにより、`EvGoSysExit`イベントが対応する`EvGoInSyscall`イベントなしに発行されるという矛盾を防ぎます。
    *   `g.sysexitticks`: システムコールから復帰した正確なCPUティック数を一時的に保存します。これは、`exitsyscall`がPなしで実行されるため、`EvGoSysExit`イベントを即座に発行できない場合に必要となります。
    *   `m.startingtrace`: `StartTrace`関数が現在実行中であることを示すフラグです。このフラグは、トレーシング開始時に発生する可能性のある特殊な競合状態を管理するために使用されます。

2.  **`StartTrace`の変更**:
    *   以前は`StartTrace`の冒頭で`trace.enabled = true`を設定していましたが、これは削除され、代わりに`_g_.m.startingtrace = true`が設定されます。これは、`trace.enabled`が`true`になると、`exitsyscall`のような関数が遅延された`EvGoSysExit`イベントをすぐに発行しようとする可能性があるためです。しかし、`StartTrace`の初期フェーズでは、まだすべての`EvGoInSyscall`イベントが発行されていないため、イベントの順序が狂う可能性があります。`startingtrace`フラグを使用することで、この期間中の`EvGoSysExit`イベントの発行を一時的に抑制します。
    *   `StartTrace`は、既存のすべてのゴルーチンを走査し、`_Gsyscall`状態のゴルーチンに対して`traceEvGoInSyscall`イベントを発行します。この際、`gp.sysblocktraced = true`を設定することで、これらのゴルーチンがシステムコールから復帰した際に、対応する`EvGoInSyscall`が既に記録されていることを保証します。`_Gsyscall`状態ではないゴルーチンに対しては`gp.sysblocktraced = false`を設定し、クリーンな状態を保ちます。
    *   すべての初期イベントが処理された後、`_g_.m.startingtrace = false`を解除し、`trace.enabled = true`を設定して、通常のトレーシングを開始します。

3.  **`exitsyscall`の変更**:
    *   システムコールから復帰する際、ゴルーチンはPを保持していないため、トレーシングイベントを直接発行できません（トレーシングコードがPを必要とするライトバリアを呼び出す可能性があるため）。このため、以前は`exitTicks`に時刻を保存し、後で`systemstack`を使って`traceGoSysExit`を呼び出していましたが、このロジックは削除されました。
    *   代わりに、`_g_.sysexitticks = cputicks()`として、復帰時刻をゴルーチン自身の`sysexitticks`フィールドに保存するだけになりました。これにより、イベントの発行はさらに遅延され、ゴルーチンがPを取得するまで待機します。

4.  **`execute`の変更**:
    *   `execute`関数は、ゴルーチンがPを取得し、実際に実行を開始する直前に呼び出されます。ここで、`gp.syscallsp != 0 && gp.sysblocktraced`という条件がチェックされます。
        *   `gp.syscallsp != 0`: ゴルーチンがシステムコールから復帰したばかりであることを示します。
        *   `gp.sysblocktraced`: このゴルーチンについて`EvGoInSyscall`イベントが既に記録されていることを示します。
    *   この両方の条件が満たされた場合にのみ、`traceGoSysExit(gp.sysexitticks)`が呼び出されます。これにより、`EvGoSysExit`イベントは、対応する`EvGoInSyscall`イベントの後に、かつゴルーチンが実行可能な状態になった適切なタイミングで発行されることが保証されます。

5.  **`traceGoSysExit`の変更**:
    *   `if ts != 0 && ts < trace.ticksStart`というガードが追加されました。これは、渡された`ts`（システムコール復帰時刻）が現在のトレーシングセッションの開始時刻`trace.ticksStart`よりも古い場合、そのイベントを無視するというものです。これにより、以前のトレーシングセッションで発生し、遅延されていた`EvGoSysExit`イベントが、新しいトレーシングセッションに誤って混入するのを防ぎ、セッション間のイベントの分離性を保証します。

6.  **`traceEvent`の変更**:
    *   イベントを記録するかどうかの条件に`!mp.startingtrace`が追加されました。これにより、`StartTrace`が実行中の間は、`trace.enabled`が`true`になる前に`exitsyscall`から呼び出される可能性のあるイベントが無視され、トレーシング開始時のイベントの順序の不整合を防ぎます。

これらの変更により、`EvGoSysExit`イベントは常に`EvGoInSyscall`イベントの後に、かつ適切なトレーシングセッション内で発行されるようになり、Goランタイムトレーシングの正確性と信頼性が大幅に向上しました。

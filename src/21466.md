# [インデックス 21466] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/ld`) におけるリロケーション処理に「バリアント」の概念を導入するものです。主に、PowerPC 64-bit (ppc64) アーキテクチャの複雑なリロケーション要件に対応するための基盤を構築します。

変更されたファイルは以下の通りです。

*   `include/link.h`: リンカ内部で使用されるリロケーション構造体 `Reloc` の定義が含まれるヘッダファイルです。ここに新しいフィールドと列挙型が追加されます。
*   `src/cmd/5l/asm.c`, `src/cmd/6l/asm.c`, `src/cmd/8l/asm.c`, `src/cmd/9l/asm.c`: それぞれ386 (5l), amd64 (6l), ARM (8l), PowerPC (9l) アーキテクチャ向けのリンカのアセンブリコード生成およびリロケーション処理に関連するC言語ソースファイルです。新しい関数プロトタイプが追加されます。
*   `src/cmd/5l/l.h`, `src/cmd/6l/l.h`, `src/cmd/8l/l.h`, `src/cmd/9l/l.h`: 上記 `asm.c` ファイルに対応するヘッダファイルです。新しい関数プロトタイプが宣言されます。
*   `src/cmd/ld/data.c`: リンカの主要なデータ処理ロジックが含まれるC言語ソースファイルです。特に、シンボルのリロケーション処理を行う `relocsym` 関数が変更されます。

これらのファイルは、Goリンカのバックエンド部分を構成し、異なるアーキテクチャ向けに最終的な実行可能ファイルを生成する際に、シンボル参照を正しく解決するための重要な役割を担っています。

## 変更の背景

プログラムがコンパイルされ、リンクされる過程で、コード内のシンボル参照（関数呼び出しや変数アクセスなど）は、最終的な実行可能ファイル内で正しいメモリアドレスを指すように調整される必要があります。この調整プロセスを「リロケーション」と呼びます。Go言語のリンカである `cmd/ld` は、このリロケーション処理を担当しています。

多くのアーキテクチャでは、リロケーションは比較的単純な計算で済みますが、PowerPC 64-bit (ppc64) アーキテクチャは、その命令セットの特性上、リロケーションに関して特有の複雑性を持っています。ppc64では、基本的なリロケーションの計算式は同じであるにもかかわらず、計算された値のどのビットをどこに配置するか（インストールするか）によって、6種類以上の異なる「バリアント」が存在することが一般的です。例えば、32ビットや64ビットのアドレスを命令の異なる部分に分割して格納する必要がある場合などです。

Goのリンカは、このようなppc64の複雑なリロケーション要件を効率的かつ正確に処理する必要がありました。特に、`R_PCREL` のようなアーキテクチャ非依存のリロケーションタイプであっても、ppc64ではバリアントに応じた特別な処理が必要になる場合があります。

このコミットは、このppc64特有の課題に対処するための基盤を構築します。具体的には、リンカ内部のリロケーション情報に「バリアント」という新しい概念を導入し、計算されたリロケーション値に対して、バリアントに応じた追加の処理を適用できるようにします。このコミット時点では「同一のバリアント (identity variant)」のみが導入されていますが、これは将来のコミットでppc64 ELFリロケーションの具体的なバリアントが追加されるための準備となります。

## 前提知識の解説

このコミットの理解を深めるために、以下の概念について解説します。

*   **リロケーション (Relocation)**:
    コンパイルされたオブジェクトファイルには、まだ最終的なメモリアドレスが決定されていないシンボル（関数、グローバル変数など）への参照が含まれています。例えば、`main` 関数が `fmt.Println` を呼び出す場合、コンパイル時には `fmt.Println` の正確なアドレスは不明です。リロケーションとは、リンカがこれらの未解決の参照を、最終的な実行可能ファイル内の実際のメモリアドレスに「解決」し、コードを修正するプロセスです。これにより、プログラムは正しく実行時に他のモジュールやライブラリのコードにジャンプしたり、データにアクセスしたりできるようになります。

*   **Goリンカ (`cmd/ld`)**:
    Go言語のビルドツールチェーンの中核をなすコンポーネントの一つです。Goのコンパイラ (`cmd/compile`) が生成したオブジェクトファイル（`.o` ファイル）やアーカイブファイル（`.a` ファイル）を読み込み、それらを結合して単一の実行可能バイナリを生成します。この過程で、シンボルの解決、アドレスの割り当て、そしてリロケーションの適用といった重要なタスクを実行します。Goのリンカは、多くの場合、Go自身で実装されており、クロスコンパイルの容易さにも貢献しています。

*   **`LSym` と `Reloc` 構造体**:
    Goリンカの内部では、プログラム内の様々な要素を表現するために独自のデータ構造が使われます。
    *   `LSym` (Linker Symbol): リンカが扱う個々のシンボル（関数、グローバル変数、文字列定数など）を表す構造体です。シンボルの名前、サイズ、アドレス、タイプなどの情報が含まれます。
    *   `Reloc` (Relocation): 特定のリロケーション情報を保持する構造体です。どのシンボルに対して、どの種類のリロケーション（例: 関数呼び出し、データ参照）、どのオフセットで、どのような値を適用するかといった詳細が記述されています。

*   **`R_PCREL` リロケーションタイプ**:
    リロケーションタイプの一つで、プログラムカウンタ (PC) 相対アドレス指定に使用されます。これは、命令ポインタ（現在の命令のアドレス）からの相対オフセットで目的のアドレスを計算する方式です。PC相対アドレス指定は、位置独立コード (Position-Independent Code, PIC) の生成に不可欠であり、共有ライブラリやASLR (Address Space Layout Randomization) のようなセキュリティ機能で広く利用されます。

*   **PPC64 (PowerPC 64-bit) アーキテクチャ**:
    IBMが開発したRISC (Reduced Instruction Set Computer) プロセッサアーキテクチャの64ビット版です。PowerPCは、組み込みシステムからスーパーコンピュータまで幅広い分野で利用されています。その命令セットは固定長であり、アドレス指定モードが豊富です。この特性が、リロケーション処理を複雑にする要因となることがあります。特に、一つの論理的なアドレス参照が、複数の異なる命令や、アドレスの異なる部分（上位ビット、下位ビットなど）を操作する複数のリロケーションを必要とすることがあります。

*   **ELF (Executable and Linkable Format)**:
    Unix系オペレーティングシステム（Linux、BSDなど）で広く使用されている、実行可能ファイル、オブジェクトファイル、共有ライブラリの標準的なファイルフォーマットです。ELFファイルは、プログラムのコード、データ、シンボルテーブル、リロケーション情報など、実行に必要なすべての情報を含んでいます。PPC64システムも通常、ELFフォーマットを使用します。

## 技術的詳細

このコミットの核心は、Goリンカのリロケーション処理に「バリアント」という新しい次元を導入することです。これは、特にppc64アーキテクチャが持つ複雑なリロケーション要件に対応するための汎用的なメカニズムを提供します。

1.  **`Reloc` 構造体への `variant` フィールドの追加**:
    `include/link.h` に定義されている `struct Reloc` に、`int32 variant;` という新しいフィールドが追加されました。この `variant` フィールドは、計算されたリロケーション値に対して、さらにどのような特殊な処理（例えば、特定のビットの抽出や配置）が必要かを示すためのものです。コメント `// RV_*: variant on computed value` が、このフィールドが計算された値に対するバリアントであることを示唆しています。

2.  **`RV_NONE` バリアントの導入**:
    同じく `include/link.h` 内に、`RV_NONE` という新しい列挙型が導入されました。これは `Reloc.variant` の初期値として機能し、「同一のバリアント」、つまり計算されたリロケーション値に対して特別なビット操作や変換を行わないことを意味します。このコミット時点では `RV_NONE` しか存在しませんが、これは将来的にppc64の具体的なリロケーションバリアント（例: `RV_POWER_LO`, `RV_POWER_HI`, `RV_POWER_HA`, `RV_POWER_DS` など、アドレスの上位/下位ビットを扱うもの）が追加されるためのプレースホルダーとなります。

3.  **`archrelocvariant` 関数の追加**:
    各アーキテクチャのリンカ (`src/cmd/{5,6,8,9}l/asm.c` および対応する `l.h` ヘッダ) に、`vlong archrelocvariant(Reloc *r, LSym *s, vlong t)` という新しい関数プロトタイプが追加されました。この関数は、リロケーション情報 (`r`)、対象シンボル (`s`)、そしてこれまでのリロケーション計算で得られた値 (`t`) を受け取り、バリアントに応じた最終的な値を返すことを意図しています。
    このコミット時点での `archrelocvariant` の実装は、単に `sysfatal("unexpected relocation variant")` を呼び出すだけです。これは、`RV_NONE` 以外のバリアントが指定された場合に、まだその処理が実装されていないことを示す一時的な措置です。これにより、将来のコミットで各アーキテクチャ（特にppc64）が独自のバリアント処理を実装するためのフックが提供されます。

4.  **`relocsym` 関数でのバリアント処理の統合**:
    `src/cmd/ld/data.c` にある `relocsym` 関数は、リンカがシンボルをリロケーションする際の中心的なロジックです。この関数内に、以下の重要な行が追加されました。
    ```c
    if(r->variant != RV_NONE)
        o = archrelocvariant(r, s, o);
    ```
    このコードは、リロケーション (`r`) の `variant` フィールドが `RV_NONE` でない場合、つまり特別なバリアント処理が必要な場合に、計算されたリロケーション値 `o` を `archrelocvariant` 関数に渡し、その戻り値で `o` を更新することを意味します。これにより、リンカは共通のリロケーション処理フローを維持しつつ、特定のアーキテクチャやリロケーションタイプに固有のバリアント処理を柔軟に適用できるようになります。

この変更は、Goリンカがppc64のような複雑なアーキテクチャのリロケーションをより正確かつ効率的に扱えるようにするための、重要なアーキテクチャ的改善の第一歩です。

## コアとなるコードの解説

これらのコード変更は、Goリンカのリロケーション処理に柔軟性と拡張性をもたらすためのものです。

1.  **`include/link.h` の変更**:
    *   `Reloc` 構造体に `variant` フィールドが追加されたことで、個々のリロケーションエントリが、そのリロケーション値の計算後にどのような追加の変換やビット操作が必要かを示すことができるようになりました。これにより、同じリロケーションタイプ（例: `R_PCREL`）であっても、アーキテクチャや特定の状況に応じて異なる処理を適用する道が開かれました。
    *   `RV_NONE` の導入は、バリアント処理が不要な場合のデフォルト値を提供します。これは、既存のリロケーション処理に影響を与えないようにするための「同一のバリアント」として機能します。

2.  **各アーキテクチャの `asm.c` および `l.h` の変更**:
    *   `archrelocvariant` 関数が追加されたのは、アーキテクチャ固有のバリアント処理をカプセル化するためです。リンカのコアロジックから、特定のアーキテクチャに依存するビット操作などを分離することができます。
    *   このコミット時点では、`archrelocvariant` は `sysfatal` を呼び出すだけですが、これは意図的なものです。`RV_NONE` 以外のバリアントが指定された場合に、まだその処理が実装されていないことを開発者に知らせるためのガードとして機能します。これにより、将来のコミットでppc64などのアーキテクチャが、アドレスの上位/下位ビットの抽出や特定の命令フォーマットへの適合など、具体的なバリアント処理をこの関数内に実装できるようになります。

3.  **`src/cmd/ld/data.c` の変更**:
    *   `relocsym` 関数は、リンカがシンボルをリロケーションする際の中心的な関数です。この関数内で `if(r->variant != RV_NONE) o = archrelocvariant(r, s, o);` の行が追加されたことが最も重要です。
    *   この変更により、リロケーションの基本的な計算 (`o` に格納される値) が行われた後、もしリロケーションに特定のバリアントが指定されていれば (`r->variant != RV_NONE`)、その計算結果 `o` が `archrelocvariant` 関数に渡され、バリアントに応じた最終的な調整が行われるようになりました。
    *   このメカニズムは、ppc64のように、一つの論理的なアドレス参照が複数の異なる命令や、アドレスの異なる部分を操作する複数のリロケーションを必要とする場合に特に有効です。リンカは共通のリロケーション処理フローを維持しつつ、`variant` フィールドと `archrelocvariant` 関数を通じて、アーキテクチャ固有の複雑なビット操作や値の調整を柔軟に行えるようになります。

これらの変更は、Goリンカがより多様なアーキテクチャ、特に複雑なリロケーション要件を持つppc64のようなアーキテクチャを、より堅牢かつ効率的にサポートするための基盤を確立するものです。

# [インデックス 26553] ファイルの概要

このコミットは、GoコンパイラのSSAバックエンドにおいて、x86アーキテクチャ向けのコード生成時に、特定の加算操作で`LEA` (Load Effective Address) 命令の代わりに`ADD`命令を使用するように変更するものです。これにより、生成されるアセンブリコードの効率が向上します。具体的には、加算結果を格納するレジスタが、加算のオペランドのいずれかのレジスタと同一である場合に`ADD`命令を選択するようになります。

## 変更の背景

Goコンパイラは、Go 1.7で導入されたSSA (Static Single Assignment) バックエンドを使用して、より最適化された機械語コードを生成します。このSSAバックエンドは、中間表現から最終的なアセンブリコードを生成する際に、様々な最適化を適用します。

x86アーキテクチャにおいて、`ADD`命令と`LEA` (Load Effective Address) 命令はどちらも加算を実行できますが、その特性には重要な違いがあります。

*   **`ADD`命令**: 算術加算を実行し、結果をデスティネーションオペランドに格納します。この命令はCPUのフラグレジスタ（キャリーフラグ、オーバーフローフラグなど）を更新します。
*   **`LEA`命令**: メモリオペランドの「有効アドレス」を計算し、その結果を汎用レジスタに格納します。この命令は実際にはメモリにアクセスせず、フラグレジスタも更新しません。そのため、アドレス計算だけでなく、単純な加算や乗算（スケールファクタを使用）にも利用できる汎用的な命令として使われることがあります。

以前のGoコンパイラのSSAバックエンドでは、単純なレジスタ間の加算であっても、`LEA`命令が頻繁に生成されていました。`LEA`は汎用性が高い一方で、特定の状況では`ADD`命令の方がより直接的で効率的な場合があります。特に、加算の結果が入力オペランドのいずれかのレジスタに直接書き込まれる場合（例: `R1 = R1 + R2`）、`ADD`命令は`LEA`よりも自然な選択肢となります。

このコミットの背景には、このようなケースで`LEA`ではなく`ADD`を使用することで、生成されるアセンブリコードの品質を向上させ、潜在的に実行速度を改善するという目的があります。`ADD`命令は、その操作がより直接的であるため、CPUのパイプラインでより効率的に処理される可能性があります。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを直接機械語に変換するのではなく、いくつかの段階を踏みます。Go 1.7以降、コンパイラのバックエンドはSSA (Static Single Assignment) フォームと呼ばれる中間表現を使用しています。

*   **SSAフォーム**: プログラム中の各変数に一度だけ値を割り当てるように制約された中間表現です。これにより、データフロー解析や最適化が容易になります。例えば、`x = a + b; y = x + c;`というコードは、SSAでは`x1 = a + b; y1 = x1 + c;`のように表現され、`x`の各定義がユニークになります。
*   **SSAバックエンドの役割**: SSAバックエンドは、SSA形式のプログラムグラフを受け取り、レジスタ割り当て、命令スケジューリング、およびターゲットアーキテクチャ（この場合はx86）固有の命令選択などの最適化を実行し、最終的なアセンブリコードを生成します。

### x86アセンブリ命令 `ADD` と `LEA`

x86アーキテクチャには、加算を実行するための複数の命令があります。このコミットで焦点となっているのは`ADD`と`LEA`です。

*   **`ADD` (Add)**:
    *   構文例: `ADD reg, reg/mem/imm`
    *   機能: 2つのオペランドを加算し、結果をデスティネーションオペランドに格納します。
    *   例: `ADD RAX, RBX` (RAX = RAX + RBX)
    *   特徴: CPUのフラグレジスタ（ZF, CF, OF, SF, PF, AFなど）を更新します。これは条件分岐やエラーチェックに利用されます。
    *   用途: 汎用的な算術加算に用いられます。

*   **`LEA` (Load Effective Address)**:
    *   構文例: `LEA reg, mem_operand`
    *   機能: メモリオペランドの「有効アドレス」を計算し、その結果をデスティネーションレジスタに格納します。**メモリへのアクセスは行いません。**
    *   例: `LEA RAX, [RBX + RCX*1 + 8]` (RAX = RBX + RCX + 8)
    *   特徴: フラグレジスタを更新しません。メモリへのアクセスを伴わないため、パイプラインのストールを避けるのに役立つ場合があります。複雑なアドレス計算を1命令で行えるため、汎用的な加算や乗算（スケールファクタを利用）にも使われます。
    *   用途: ポインタ演算、配列インデックス計算、そしてこのコミットで問題となっているような単純な加算にも使われることがあります。

### レジスタ割り当ての重要性

コンパイラは、プログラムの実行中に変数の値をCPUのレジスタに割り当てます。レジスタはCPUが最も高速にアクセスできる記憶領域であるため、効率的なレジスタ割り当てはプログラムのパフォーマンスに直結します。

このコミットでは、「出力レジスタが入力レジスタのいずれかと同じ場合」という条件が重要です。これは、例えば`R1 = R1 + R2`のような操作を指します。このような場合、`ADD R2, R1`という命令は`R1`の内容を`R1 + R2`で更新し、`R1`をデスティネーション兼ソースとして使用します。`LEA`を使う場合、`LEA R1, [R1 + R2]`のように書くこともできますが、`ADD`の方がこの種の操作にはより直接的です。

## 技術的詳細

GoコンパイラのSSAバックエンドは、`src/cmd/compile/internal/gc/ssa.go`内の`genValue`関数で、SSA値（`ssa.Value`）を対応するx86アセンブリ命令に変換します。以前の実装では、`ssa.OpAMD64ADDQ` (64ビット加算), `ssa.OpAMD64ADDL` (32ビット加算), `ssa.OpAMD64ADDW` (16ビット加算) といった加算操作に対して、一律に`LEA`命令（`x86.ALEAQ`, `x86.ALEAL`, `x86.ALEAW`）を生成していました。

これは、`LEA`がフラグを汚染しないという特性から、特定の最適化パスで有利に働く場合があるため、一般的な選択肢として採用されていた可能性があります。しかし、単純な加算で、特に結果が入力レジスタの一つに上書きされるようなケースでは、`ADD`命令の方がより効率的であると判断されました。

このコミットは、`genValue`関数内の`ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW`の処理ロジックを変更し、以下の条件分岐を導入しました。

1.  **出力レジスタが第一入力レジスタと同じ場合**: `r == r1` (例: `R1 = R1 + R2`)
2.  **出力レジスタが第二入力レジスタと同じ場合**: `r == r2` (例: `R1 = R2 + R1`、ただし`ADD`命令のセマンティクス上は`R2 = R2 + R1`となるため、このケースは`ADD R1, R2`として扱われる)
3.  **上記以外の場合**: 出力レジスタが入力レジスタのいずれとも異なる場合 (例: `R3 = R1 + R2`)

ケース1と2では、`ADD`命令（`v.Op.Asm()`で取得される適切な`ADDQ`, `ADDL`, `ADDW`命令）を生成します。これにより、レジスタを再利用しつつ直接的な加算を実行できます。

ケース3では、以前と同様に`LEA`命令を生成します。これは、`LEA`が3つの異なるレジスタ（またはレジスタとオフセット）を扱う能力があるため、出力レジスタが入力レジスタと異なる場合に適しているためです。

また、定数との加算を行う`ssa.OpAMD64ADDQconst`, `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`についても同様の最適化が適用されました。出力レジスタが入力レジスタと同じ場合、`ADD`命令と定数オペランドを使用して直接加算を行います。

この変更により、コンパイラはより状況に応じた最適な命令選択を行うことができ、結果として生成されるGoプログラムのパフォーマンスが向上する可能性があります。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/ssa.go`の`genValue`関数は、SSA値`v`を受け取り、それに対応するアセンブリ命令を生成します。

変更された`case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW:`ブロックでは、まず以下のレジスタ番号を取得します。
*   `r := regnum(v)`: 加算結果を格納する出力レジスタ。
*   `r1 := regnum(v.Args[0])`: 第一オペランドのレジスタ。
*   `r2 := regnum(v.Args[1])`: 第二オペランドのレジスタ。

次に、`switch`文でこれらのレジスタの関係をチェックします。

1.  **`case r == r1:`**:
    *   出力レジスタ`r`が第一オペランドのレジスタ`r1`と同じ場合（例: `R1 = R1 + R2`）。
    *   `p := Prog(v.Op.Asm())`で、`ssa.OpAMD64ADDQ`などに対応する`ADDQ`命令を生成します。
    *   `p.From.Reg = r2`で、第二オペランド`r2`をソースレジスタに設定します。
    *   `p.To.Reg = r`で、出力レジスタ`r`をデスティネーションレジスタに設定します。
    *   これにより、`ADD R2, R1`のような命令が生成され、`R1`が`R1 + R2`で更新されます。

2.  **`case r == r2:`**:
    *   出力レジスタ`r`が第二オペランドのレジスタ`r2`と同じ場合（例: `R2 = R1 + R2`）。
    *   同様に`ADD`命令を生成し、`p.From.Reg = r1`、`p.To.Reg = r`と設定します。
    *   これにより、`ADD R1, R2`のような命令が生成され、`R2`が`R1 + R2`で更新されます。

3.  **`default:`**:
    *   出力レジスタ`r`が入力レジスタ`r1`、`r2`のいずれとも異なる場合（例: `R3 = R1 + R2`）。
    *   この場合は、以前と同様に`LEA`命令（`x86.ALEAQ`など）を生成します。
    *   `p.From.Reg = r1`, `p.From.Index = r2`, `p.From.Scale = 1`と設定することで、`LEA R, [R1 + R2]`のような命令が生成されます。

定数との加算を行う`ssa.OpAMD64ADDQconst`, `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`のブロックでも同様のロジックが適用されます。
*   `if r == a` (出力レジスタ`r`が入力レジスタ`a`と同じ場合) は、`ADD`命令と定数オペランドを使用して直接加算を行います。
*   それ以外の場合は、`LEA`命令と定数オフセットを使用して加算を行います。

この変更により、コンパイラは加算操作のコンテキストに応じて、より適切なx86命令（`ADD`または`LEA`）を選択できるようになり、生成されるコードの効率性が向上します。

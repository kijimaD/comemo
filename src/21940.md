## 変更の背景

この変更の主な背景は、Goコンパイラの内部で発生していた名前の衝突問題です。Goコンパイラは、異なるCPUアーキテクチャ（例: `amd64`, `arm`, `386`, `ppc64`など）に対応するために、アーキテクチャ固有のコード生成ロジックを持っています。これらのアーキテクチャ固有の機能は、`Arch`という構造体（型）を通じて抽象化され、各アーキテクチャのバックエンドで実装されています。

問題は、この`Arch`型に対応するグローバル変数も`arch`という名前で宣言されていたことです。Go言語のコンパイラはC言語で書かれており、C言語では同じスコープ内で型名と変数名が衝突すると、コンパイルエラーや予期せぬ動作を引き起こす可能性があります。特に、`arch`という変数がエクスポート（他のファイルから参照可能）されている場合、この衝突はより深刻になります。

この名前の衝突を解決するために、グローバル変数`arch`を`thearch`というより具体的な名前に変更することが決定されました。これにより、型名`Arch`と変数名`thearch`が明確に区別され、コードの可読性と保守性が向上します。

また、このコミットでは、コードの整理と機能の追加も行われています。
- `arch.dumpit`の削除: この関数は、デバッグ目的でプログラムのフローグラフをダンプするために使用されていましたが、その機能がアーキテクチャ固有である必要がなくなり、より汎用的な（ポータブルな）コードベースに移動されたため、`Arch`構造体から削除されました。
- `arch.defframe`の追加: この関数は、関数のスタックフレームのセットアップに関連する処理を行うもので、元々`Arch`構造体に含まれるべきでしたが、何らかの理由で忘れられていたため、この機会に追加されました。これは、コンパイラが正しくスタックフレームを管理するために必要な機能です。

これらの変更は、Goコンパイラの内部構造を改善し、将来的な開発やメンテナンスを容易にすることを目的としています。

1.  **Goコンパイラ (`cmd/gc`)**:
    *   Go言語の公式コンパイラは、主にC言語で書かれた`cmd/gc`というツールです。これは、Goのソースコードを各ターゲットアーキテクチャの機械語にコンパイルする役割を担っています。
    *   コンパイラは、フロントエンド（構文解析、型チェックなど）とバックエンド（コード生成、最適化など）に分かれています。このコミットは主にバックエンド、特にアーキテクチャ固有のコード生成部分に関わっています。

2.  **アーキテクチャ固有のバックエンド (`cmd/5g`, `cmd/6g`, `cmd/8g`, `cmd/9g`)**:
    *   Goコンパイラは、異なるCPUアーキテクチャ（例: `5g`はARM、`6g`はAMD64、`8g`は386、`9g`はPPC64など）ごとに専用のコード生成バックエンドを持っています。これらのバックエンドは、共通のコンパイラフレームワーク内で動作し、それぞれのアーキテクチャに最適化された機械語を生成します。
    *   これらのバックエンドは、`src/cmd/<arch>/galign.c`のようなファイルで、アーキテクチャ固有の初期化や関数ポインタの設定を行っています。

3.  **`Arch` 構造体 (型)**:
    *   `src/cmd/gc/go.h`で定義されている`struct Arch`は、Goコンパイラのバックエンドが提供するアーキテクチャ固有の関数ポインタや定数をまとめたものです。
    *   この構造体には、コード生成（`cgen`）、レジスタ割り当て（`regalloc`）、スタックフレームの処理（`defframe`）、命令の最適化（`peep`）など、様々なアーキテクチャ依存の操作を行うための関数ポインタが含まれています。
    *   これにより、コンパイラの共通部分（`cmd/gc`）は、特定のアーキテクチャの詳細を知ることなく、`Arch`構造体を介してアーキテクチャ固有の機能を利用できます。

4.  **`arch` グローバル変数**:
    *   各アーキテクチャのバックエンド（例: `src/cmd/6g/galign.c`）では、`Arch`型のグローバル変数`arch`が宣言され、そのフィールドに各アーキテクチャ固有の関数が割り当てられていました。
    *   コンパイラの共通部分は、この`arch`変数を通じて、現在ターゲットとしているアーキテクチャの機能にアクセスしていました。

5.  **C言語における名前の衝突**:
    *   C言語では、構造体（`struct`）のタグ名と、同じスコープ内の変数名が同じであることは許容されますが、混乱を招く可能性があります。特に、`typedef`を使って構造体名をエイリアスしている場合や、グローバル変数として宣言されている場合は、意図しない名前解決やコンパイルエラーの原因となることがあります。
    *   このケースでは、`Arch`という型名と`arch`という変数名が衝突しており、コードの可読性を損ね、潜在的なバグの原因となっていました。

6.  **`dumpit` と `defframe`**:
    *   `dumpit`: コンパイラのデバッグ機能の一つで、中間表現や最適化の過程で生成されるフローグラフなどの情報をダンプするために使用されていました。この機能がアーキテクチャ固有である必要がなくなったため、`Arch`構造体から削除され、より汎用的な場所へ移動されました。

## 技術的詳細

このコミットの技術的詳細は、主に以下の3つの側面に集約されます。

1.  **`arch` から `thearch` へのリネーム**:
    *   **問題点**: `src/cmd/gc/go.h`で定義されている`struct Arch`という型名と、各アーキテクチャのバックエンド（例: `src/cmd/6g/galign.c`）で宣言されているグローバル変数`arch`が名前衝突を起こしていました。C言語では、型名と変数名が同じでもコンパイルエラーにならない場合がありますが、これはコードの意図を不明瞭にし、将来的なメンテナンスやデバッグを困難にする潜在的な問題でした。特に、`arch`変数が`EXTERN Arch arch;`として宣言され、他のファイルから参照される場合、この曖昧さはより顕著になります。
    *   **解決策**: この衝突を解消するため、グローバル変数`arch`の名前を`thearch`に変更しました。この変更は、コンパイラ全体にわたって`arch.`というプレフィックスを持つ全ての参照を`thearch.`に置き換えるという大規模な作業を伴いました。これにより、型名`Arch`と、その型のインスタンスである変数`thearch`が明確に区別され、コードの可読性が大幅に向上しました。例えば、`arch.cgen`は`thearch.cgen`となり、これが`Arch`構造体の`cgen`メンバーを介した呼び出しであることが一目でわかるようになりました。

2.  **`arch.dumpit` の削除とポータブルコードへの移動**:
    *   **変更前**: `Arch`構造体には、`void (*dumpit)(char*, Flow*, int);`という関数ポインタが含まれていました。これは、コンパイラのデバッグ時に中間表現のフローグラフなどをダンプするために使用されるアーキテクチャ固有の関数として扱われていました。
    *   **変更の理由**: `dumpit`の機能は、特定のCPUアーキテクチャに依存するものではなく、コンパイラの共通部分で処理できる汎用的なデバッグ機能であると判断されました。アーキテクチャ固有の`Arch`構造体にこのような汎用的な機能を含めることは、設計上の不整合であり、コードのモジュール性を損ねます。
    *   **結果**: `dumpit`関数ポインタは`Arch`構造体から削除されました。そして、その機能は`src/cmd/gc/popt.c`などのファイルで直接呼び出される`dumpit`関数として、よりポータブルな形で実装されました。これにより、`Arch`構造体は真にアーキテクチャ固有の機能のみを含むようになり、コンパイラの設計がよりクリーンになりました。

3.  **`arch.defframe` の追加**:
    *   **変更前**: `Arch`構造体には、関数のスタックフレームを定義・セットアップするための関数ポインタが欠落していました。スタックフレームのセットアップは、関数呼び出し規約やレジスタの使用方法など、アーキテクチャに強く依存する処理です。
    *   **変更の理由**: コミットメッセージにある「forgotten originally, somehow」（元々何らかの理由で忘れられていたもの）という記述が示すように、`defframe`のような重要なアーキテクチャ固有の機能が`Arch`構造体に含まれていなかったのは見落としでした。コンパイラが正しく関数をコンパイルし、実行時に適切なスタック環境を構築するためには、この機能が`Arch`構造体を通じて提供される必要があります。
    *   **結果**: `Arch`構造体に`void (*defframe)(Prog*);`という新しい関数ポインタが追加されました。これにより、各アーキテクチャのバックエンドは、それぞれの特性に応じたスタックフレームのセットアップロジックを`defframe`関数として実装し、`Arch`構造体のこのフィールドに割り当てることができるようになりました。例えば、`src/cmd/5g/galign.c`や`src/cmd/6g/galign.c`などのファイルで、`thearch.defframe = defframe;`のように設定されています。これは、`src/cmd/gc/pgen.c`の`compile`関数内で`thearch.defframe(ptxt);`として呼び出され、関数のプロローグ処理の一部として機能します。

これらの変更は、Goコンパイラの内部構造をより堅牢で、論理的に一貫性のあるものにするための重要なステップです。特に、`Arch`構造体の役割を明確にし、アーキテクチャ固有の機能と汎用的な機能を分離することで、コンパイラの保守性と拡張性が向上しています。

`cmd/gc`: `arch`を`thearch`にリネーム。
エクスポートされた変数名が型`Arch`と衝突するため。
この機会に、`arch.dumpit`を削除（ポータブルなコードに移動済み）し、`arch.defframe`を追加（元々何らかの理由で忘れられていたもの）。

## 変更の背景

この変更の主な背景は、Goコンパイラの内部で発生していた名前の衝突問題です。Goコンパイラは、異なるCPUアーキテクチャ（例: `amd64`, `arm`, `386`, `ppc64`など）に対応するために、アーキテクチャ固有のコード生成ロジックを持っています。これらのアーキテクチャ固有の機能は、`Arch`という構造体（型）を通じて抽象化され、各アーキテクチャのバックエンドで実装されています。

問題は、この`Arch`型に対応するグローバル変数も`arch`という名前で宣言されていたことです。Go言語のコンパイラはC言語で書かれており、C言語では同じスコープ内で型名と変数名が衝突すると、コンパイルエラーや予期せぬ動作を引き起こす可能性があります。特に、`arch`という変数がエクスポート（他のファイルから参照可能）されている場合、この衝突はより深刻になります。

この名前の衝突を解決するために、グローバル変数`arch`を`thearch`というより具体的な名前に変更することが決定されました。これにより、型名`Arch`と変数名`thearch`が明確に区別され、コードの可読性と保守性が向上します。

また、このコミットでは、コードの整理と機能の追加も行われています。
- `arch.dumpit`の削除: この関数は、デバッグ目的でプログラムのフローグラフをダンプするために使用されていましたが、その機能がアーキテクチャ固有である必要がなくなり、より汎用的な（ポータブルな）コードベースに移動されたため、`Arch`構造体から削除されました。
- `arch.defframe`の追加: この関数は、関数のスタックフレームのセットアップに関連する処理を行うもので、元々`Arch`構造体に含まれるべきでしたが、何らかの理由で忘れられていたため、この機会に追加されました。これは、コンパイラが正しくスタックフレームを管理するために必要な機能です。

これらの変更は、Goコンパイラの内部構造を改善し、将来的な開発やメンテナンスを容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造とC言語の概念に関する知識が必要です。

1.  **Goコンパイラ (`cmd/gc`)**:
    *   Go言語の公式コンパイラは、主にC言語で書かれた`cmd/gc`というツールです。これは、Goのソースコードを各ターゲットアーキテクチャの機械語にコンパイルする役割を担っています。
    *   コンパイラは、フロントエンド（構文解析、型チェックなど）とバックエンド（コード生成、最適化など）に分かれています。このコミットは主にバックエンド、特にアーキテクチャ固有のコード生成部分に関わっています。

2.  **アーキテクチャ固有のバックエンド (`cmd/5g`, `cmd/6g`, `cmd/8g`, `cmd/9g`)**:
    *   Goコンパイラは、異なるCPUアーキテクチャ（例: `5g`はARM、`6g`はAMD64、`8g`は386、`9g`はPPC64など）ごとに専用のコード生成バックエンドを持っています。これらのバックエンドは、共通のコンパイラフレームワーク内で動作し、それぞれのアーキテクチャに最適化された機械語を生成します。
    *   これらのバックエンドは、`src/cmd/<arch>/galign.c`のようなファイルで、アーキテクチャ固有の初期化や関数ポインタの設定を行っています。

3.  **`Arch` 構造体 (型)**:
    *   `src/cmd/gc/go.h`で定義されている`struct Arch`は、Goコンパイラのバックエンドが提供するアーキテクチャ固有の関数ポインタや定数をまとめたものです。
    *   この構造体には、コード生成（`cgen`）、レジスタ割り当て（`regalloc`）、スタックフレームの処理（`defframe`）、命令の最適化（`peep`）など、様々なアーキテクチャ依存の操作を行うための関数ポインタが含まれています。
    *   これにより、コンパイラの共通部分（`cmd/gc`）は、特定のアーキテクチャの詳細を知ることなく、`Arch`構造体を介してアーキテクチャ固有の機能を利用できます。

4.  **`arch` グローバル変数**:
    *   各アーキテクチャのバックエンド（例: `src/cmd/6g/galign.c`）では、`Arch`型のグローバル変数`arch`が宣言され、そのフィールドに各アーキテクチャ固有の関数が割り当てられていました。
    *   コンパイラの共通部分は、この`arch`変数を通じて、現在ターゲットとしているアーキテクチャの機能にアクセスしていました。

5.  **C言語における名前の衝突**:
    *   C言語では、構造体（`struct`）のタグ名と、同じスコープ内の変数名が同じであることは許容されますが、混乱を招く可能性があります。特に、`typedef`を使って構造体名をエイリアスしている場合や、グローバル変数として宣言されている場合は、意図しない名前解決やコンパイルエラーの原因となることがあります。
    *   このケースでは、`Arch`という型名と`arch`という変数名が衝突しており、コードの可読性を損ね、潜在的なバグの原因となっていました。

6.  **`dumpit` と `defframe`**:
    *   `dumpit`: コンパイラのデバッグ機能の一つで、中間表現や最適化の過程で生成されるフローグラフなどの情報をダンプするために使用されていました。この機能がアーキテクチャ固有である必要がなくなったため、`Arch`構造体から削除され、より汎用的な場所へ移動されました。
    *   `defframe`: 関数のプロローグ（関数呼び出し時に実行される初期化コード）でスタックフレームをセットアップする処理に関連する関数です。これには、スタックポインタの調整、レジスタの保存、ローカル変数のためのスペース確保などが含まれます。この機能はアーキテクチャに強く依存するため、`Arch`構造体に追加されました。

これらの前提知識を理解することで、このコミットがGoコンパイラの内部でどのように機能し、なぜこれらの変更が必要だったのかを深く把握することができます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の3つの側面に集約されます。

1.  **`arch` から `thearch` へのリネーム**:
    *   **問題点**: `src/cmd/gc/go.h`で定義されている`struct Arch`という型名と、各アーキテクチャのバックエンド（例: `src/cmd/6g/galign.c`）で宣言されているグローバル変数`arch`が名前衝突を起こしていました。C言語では、型名と変数名が同じでもコンパイルエラーにならない場合がありますが、これはコードの意図を不明瞭にし、将来的なメンテナンスやデバッグを困難にする潜在的な問題でした。特に、`arch`変数が`EXTERN Arch arch;`として宣言され、他のファイルから参照される場合、この曖昧さはより顕著になります。
    *   **解決策**: この衝突を解消するため、グローバル変数`arch`の名前を`thearch`に変更しました。この変更は、コンパイラ全体にわたって`arch.`というプレフィックスを持つ全ての参照を`thearch.`に置き換えるという大規模な作業を伴いました。これにより、型名`Arch`と、その型のインスタンスである変数`thearch`が明確に区別され、コードの可読性が大幅に向上しました。例えば、`arch.cgen`は`thearch.cgen`となり、これが`Arch`構造体の`cgen`メンバーを介した呼び出しであることが一目でわかるようになりました。

2.  **`arch.dumpit` の削除とポータブルコードへの移動**:
    *   **変更前**: `Arch`構造体には、`void (*dumpit)(char*, Flow*, int);`という関数ポインタが含まれていました。これは、コンパイラのデバッグ時に中間表現のフローグラフなどをダンプするために使用されるアーキテクチャ固有の関数として扱われていました。
    *   **変更の理由**: `dumpit`の機能は、特定のCPUアーキテクチャに依存するものではなく、コンパイラの共通部分で処理できる汎用的なデバッグ機能であると判断されました。アーキテクチャ固有の`Arch`構造体にこのような汎用的な機能を含めることは、設計上の不整合であり、コードのモジュール性を損ねます。
    *   **結果**: `dumpit`関数ポインタは`Arch`構造体から削除されました。そして、その機能は`src/cmd/gc/popt.c`などのファイルで直接呼び出される`dumpit`関数として、よりポータブルな形で実装されました。これにより、`Arch`構造体は真にアーキテクチャ固有の機能のみを含むようになり、コンパイラの設計がよりクリーンになりました。

3.  **`arch.defframe` の追加**:
    *   **変更前**: `Arch`構造体には、関数のスタックフレームを定義・セットアップするための関数ポインタが欠落していました。スタックフレームのセットアップは、関数呼び出し規約やレジスタの使用方法など、アーキテクチャに強く依存する処理です。
    *   **変更の理由**: コミットメッセージにある「forgotten originally, somehow」（元々何らかの理由で忘れられていたもの）という記述が示すように、`defframe`のような重要なアーキテクチャ固有の機能が`Arch`構造体に含まれていなかったのは見落としでした。コンパイラが正しく関数をコンパイルし、実行時に適切なスタック環境を構築するためには、この機能が`Arch`構造体を通じて提供される必要があります。
    *   **結果**: `Arch`構造体に`void (*defframe)(Prog*);`という新しい関数ポインタが追加されました。これにより、各アーキテクチャのバックエンドは、それぞれの特性に応じたスタックフレームのセットアップロジックを`defframe`関数として実装し、`Arch`構造体のこのフィールドに割り当てることができるようになりました。例えば、`src/cmd/5g/galign.c`や`src/cmd/6g/galign.c`などのファイルで、`thearch.defframe = defframe;`のように設定されています。これは、`src/cmd/gc/pgen.c`の`compile`関数内で`thearch.defframe(ptxt);`として呼び出され、関数のプロローグ処理の一部として機能します。

これらの変更は、Goコンパイラの内部構造をより堅牢で、論理的に一貫性のあるものにするための重要なステップです。特に、`Arch`構造体の役割を明確にし、アーキテクチャ固有の機能と汎用的な機能を分離することで、コンパイラの保守性と拡張性が向上しています。

## コアとなるコードの解説

このコミットのコアとなるコードの変更は、Goコンパイラのアーキテクチャ抽象化の中心である`Arch`構造体と、そのグローバルインスタンスである`thearch`変数に集約されます。

### `Arch` 構造体の変更 (`src/cmd/gc/go.h`)

```c
struct Arch
{
	// ... 既存のメンバー ...
	void (*cgen_callinter)(Node*, Node*, int);
	void (*cgen_ret)(Node*);
	void (*clearfat)(Node*);
	// void (*dumpit)(char*, Flow*, int); // 削除された行
	void (*defframe)(Prog*); // 追加された行
	void (*excise)(Flow*);
	void (*expandchecks)(Prog*);
	// ... 既存のメンバー ...
};

// EXTERN Arch arch; // 削除された行
EXTERN Arch thearch; // 追加された行
```

*   **`dumpit` の削除**: `Arch`構造体から`dumpit`関数ポインタが削除されました。これは、`dumpit`がアーキテクチャ固有の操作ではなく、コンパイラの共通部分で処理できる汎用的なデバッグ機能であると判断されたためです。これにより、`Arch`構造体はより純粋にアーキテクチャ固有の機能のみをカプセル化するようになりました。
*   **`defframe` の追加**: `defframe`関数ポインタが`Arch`構造体に追加されました。この関数は、関数のスタックフレームをセットアップする役割を担います。スタックフレームのレイアウトやレジスタの保存/復元はアーキテクチャに強く依存するため、この機能が`Arch`構造体に含まれることは論理的かつ必要不可欠です。

### `arch` から `thearch` へのリネーム

コンパイラのコードベース全体で、`Arch`構造体のグローバルインスタンスへの参照が`arch`から`thearch`に変更されました。

**例: `src/cmd/6g/galign.c` の `main` 関数内**

```c
void
main(int argc, char **argv)
{
	// arch.thechar = thechar; // 変更前
	thearch.thechar = thechar; // 変更後
	// ... 他の arch. 参照も同様に thearch. に変更 ...

	// arch.dumpit = dumpit; // 削除された行
	thearch.defframe = defframe; // 追加された行

	gcmain(argc, argv);
}
```

*   **名前衝突の解消**: このリネームは、`Arch`という型名と`arch`という変数名が衝突する問題を解決するためのものです。`thearch`という名前は、これが「現在のアーキテクチャ」を表すグローバルなインスタンスであることをより明確に示しています。
*   **一貫性の向上**: コンパイラの様々な部分（コード生成、レジスタ割り当て、型システムなど）で`Arch`構造体のメンバーが呼び出される際、常に`thearch.`というプレフィックスを使用することで、コードの一貫性が保たれ、どの操作がアーキテクチャ固有であるかが明確になります。

### `defframe` の実装と利用

`defframe`は、各アーキテクチャのバックエンドで実装され、`src/cmd/gc/pgen.c`の`compile`関数内で呼び出されます。

**例: `src/cmd/gc/pgen.c` の `compile` 関数内**

```c
void
compile(Node *fn)
{
	// ...
	// defframe(ptxt); // 変更前 (直接呼び出し)
	thearch.defframe(ptxt); // 変更後 (thearch 経由で呼び出し)
	// ...
}
```

*   `defframe`は、関数のプロローグ処理の一部として、スタックフレームのサイズを計算し、スタックポインタを調整し、必要に応じてレジスタを保存するなどのアーキテクチャ固有の処理を実行します。この関数が`Arch`構造体の一部となることで、コンパイラの共通部分は、現在ターゲットとしているアーキテクチャの適切な`defframe`実装を透過的に呼び出すことができます。

これらの変更は、Goコンパイラの内部設計を改善し、アーキテクチャ固有のロジックをより適切にカプセル化することで、コードの保守性と拡張性を高めることに貢献しています。

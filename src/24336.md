## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおける共通部分式除去 (CSE) パスが、異なる基本ブロックに属するPhi変数を誤って共通部分式として結合してしまうバグを修正します。この誤った最適化は、ループ変数のインクリメントが失われるなどの問題を引き起こし、結果として無限ループのような不正なプログラム動作につながる可能性がありました。修正は、Phi変数を共通部分式として扱う際に、それらが同じ基本ブロックに属していることを追加の条件として課すことで行われます。

## 変更の背景

Goコンパイラは、プログラムのパフォーマンスを向上させるために様々な最適化パスを実行します。その一つがSSA (Static Single Assignment) 形式上で行われる共通部分式除去 (CSE) です。CSEは、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除する最適化手法です。

しかし、このコミットで示された具体的な例（ネストされたループと`continue`文を含むGoコード）において、CSEパスが誤動作することが判明しました。問題は、内側のループ変数`i`を表すPhi変数`v82`と、外側のループ変数`j`に関連する別のPhi変数`v49`が、CSEによって共通部分式と見なされてしまった点にあります。

コミットメッセージの例では、`f_ssa`関数内の内側ループのインクリメント部分（`i++`）が、SSA形式では`v29 = Add <int> v82 v28`として表現されます。ここで`v82`はループ変数`i`の現在の値を表すPhi変数です。CSEが`v82`と`v49`を共通と判断し、`v82`を`v49`に置き換えてしまうと、`v29`の計算が`v29 = Add <int> v49 v28`となり、本来`i`をインクリメントするはずの処理が、`j`に関連する値を使って行われることになります。

結果として、`v82`はもはやどこからも参照されなくなり「dead (デッド)」とマークされ、最終的にコンパイラによって削除されます。これにより、内側ループのインクリメント処理が完全に失われ、ループが無限に実行されるという重大なバグが発生しました。この問題は、Phi変数がその定義される基本ブロックに強く依存するというSSAの特性をCSEが十分に考慮していなかったために生じました。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現の一種です。SSA形式の主要な特性は、プログラム中の全ての変数が「静的に一度だけ」代入されるという点です。つまり、変数が代入されるたびに新しいバージョン（新しい名前）が割り当てられます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。

例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

SSA形式では、これは次のように表現されるかもしれません。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

### Phi関数 (Φ関数)

SSA形式において、制御フローグラフ (Control Flow Graph, CFG) 上で複数のパスが合流する点（例えば、if-else文の終わりやループの先頭）では、同じ論理変数に対して異なる値が到達する可能性があります。この問題を解決するために導入されるのがPhi関数です。

Phi関数は、合流点において、どの制御フローパスから来たかに応じて適切な値を選択する仮想的な命令です。例えば、`x3 = Φ(x1, x2)`というPhi関数は、「もし制御フローがパス1から来たなら`x1`を、パス2から来たなら`x2`を`x3`に代入する」という意味を持ちます。Phi関数は実際の実行時には存在せず、レジスタ割り当てなどのバックエンド処理で適切なムーブ命令に変換されます。

### CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラ最適化の一種で、プログラム内で同じ値が複数回計算されている部分（共通部分式）を特定し、その計算を一度だけ行い、結果を一時変数に格納して再利用することで、冗長な計算を排除する手法です。これにより、実行速度の向上やコードサイズの削減が期待できます。

例えば、`a = (b * c) + d`と`e = (b * c) + f`というコードがある場合、`b * c`は共通部分式です。CSEはこれを次のように変換するかもしれません。

```
temp = b * c
a = temp + d
e = temp + f
```

### 基本ブロック (Basic Block)

基本ブロックは、コンパイラ最適化における制御フローグラフの基本的な構成要素です。基本ブロックは、以下の特性を持つ命令のシーケンスです。

1.  **単一のエントリポイント**: 実行は常にブロックの最初の命令から開始されます。
2.  **単一のイグジットポイント**: 実行は常にブロックの最後の命令で終了し、次のブロックへ制御が移ります。
3.  **内部に分岐なし**: ブロック内の命令は、最後の命令を除いて、分岐命令を含みません。

プログラムは複数の基本ブロックに分割され、これらのブロック間の制御フローはエッジで表現されます。Phi関数は、複数の基本ブロックが合流する点で必要となります。

## 技術的詳細

GoコンパイラのSSAバックエンドにおけるCSEパスは、プログラムのSSA形式表現を走査し、等価な値を見つけてそれらを置き換えることで最適化を行います。この等価性の判断は、値のオペレーションコード (Op)、型 (Type)、補助データ (Aux)、補助整数値 (AuxInt)、引数の数 (nargs) などに基づいて行われます。

このコミット以前のCSEの実装では、Phi変数の等価性を判断する際に、それらが定義されている基本ブロックを考慮していませんでした。Phi関数は、その性質上、複数の異なる制御フローパスから来る値を結合するため、どの基本ブロックで定義されているかがその意味に大きく影響します。

コミットメッセージの例では、`v82`と`v49`という2つのPhi変数が問題を引き起こしました。
*   `v82`は内側のループ変数`i`に関連するPhi変数で、基本ブロック`b8`で定義されています。
*   `v49`は外側のループ変数`j`に関連するPhi変数で、基本ブロック`b4`で定義されています。

これら二つのPhi変数は、オペレーションコード、型、引数の数などが偶然一致したため、CSEパスによって共通部分式と誤認されました。しかし、これらは異なる基本ブロックで定義されており、それぞれ異なるループ変数の状態を表しているため、論理的には等価ではありません。CSEがこれらを等価と見なし、`v82`を`v49`に置き換えた結果、`v82`のインクリメント処理が失われ、無限ループが発生しました。

このバグを修正するために、CSEの等価性判断ロジックが変更されました。具体的には、値が`OpPhi`（Phi関数）である場合に限り、その値が定義されている基本ブロックのIDも等価性判断の基準に追加されました。これにより、異なる基本ブロックで定義されたPhi変数が誤って共通部分式として扱われることがなくなります。

CSEパスは、まず初期のパーティション（等価クラスの集合）を作成します。これは、オペレーションコード、型、補助データ、補助整数値、引数の数に基づいて値をグループ化するものです。このコミットでは、この初期パーティションの作成時に、Phi変数の場合はその基本ブロックIDもキーに含めるように変更されました。

変更後の`key`構造体は以下のようになります。

```go
type key struct {
	op     Op
	typ    string
	aux    interface{}
	auxint int64
	nargs  int
	block  ID // block id for phi vars, -1 otherwise
}
```

`block`フィールドが追加され、`v.Op == OpPhi`の場合にのみ、その値が定義されている基本ブロックのIDが`bid`として設定され、`key`の一部となります。それ以外のオペレーションの場合は`-1`が設定されます。これにより、Phi変数の等価性判断がより厳密になり、異なる基本ブロックのPhi変数が誤って結合されることが防止されます。

## コアとなるコードの解説

この変更は、`cse.go`ファイル内の`cse`関数、特に共通部分式を識別するための初期パーティションを生成するロジックに影響を与えます。

1.  **コメントの追加**:
    `// v.block == w.block if v.op == OpPhi`
    このコメントは、Phiオペレーションの場合に、値`v`と`w`が等価であるための新しい条件として、それらが同じ基本ブロックに属している必要があることを明示しています。これは、このコミットの核心となる変更の意図を説明しています。

2.  **`key`構造体の変更**:
    ```go
    type key struct {
    	op     Op
    	typ    string
    	aux    interface{}
    	auxint int64
    	nargs  int
    	block  ID // block id for phi vars, -1 otherwise
    }
    ```
    `key`構造体に`block ID`型の新しいフィールド`block`が追加されました。この`key`構造体は、SSA値の等価性を判断し、それらを初期の等価クラス（`eqclass`）にグループ化するために使用されます。`block`フィールドは、Phi変数の場合にのみ関連する基本ブロックのIDを保持し、それ以外の場合は`-1`が設定されます。

3.  **`key`生成ロジックの変更**:
    ```go
    			bid := ID(-1)
    			if v.Op == OpPhi {
    				bid = b.ID
    			}
    			k := key{v.Op, v.Type.String(), v.Aux, v.AuxInt, len(v.Args), bid}
    ```
    各SSA値`v`に対して`key`を生成する際に、以下のロジックが追加されました。
    *   まず、`bid`（ブロックID）をデフォルト値`-1`で初期化します。
    *   もし現在のSSA値`v`のオペレーションが`OpPhi`（Phi関数）である場合、その値が属する基本ブロック`b`のID (`b.ID`) を`bid`に設定します。
    *   最後に、この`bid`を`key`構造体の新しい`block`フィールドに含めて`key`を構築します。

この変更により、Phi変数の等価性を判断する際に、そのオペレーション、型、引数だけでなく、それがどの基本ブロックで定義されているかという情報も考慮されるようになりました。これにより、異なる基本ブロックに属するPhi変数が誤って共通部分式として扱われることがなくなり、前述の無限ループのバグが修正されます。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおける共通部分式除去 (CSE) パスが、異なる基本ブロックに属するPhi変数を誤って共通部分式として結合してしまうバグを修正します。この誤った最適化は、ループ変数のインクリメントが失われるなどの問題を引き起こし、結果として無限ループのような不正なプログラム動作につながる可能性がありました。修正は、Phi変数を共通部分式として扱う際に、それらが同じ基本ブロックに属していることを追加の条件として課すことで行われます。

## 変更の背景

Goコンパイラは、プログラムのパフォーマンスを向上させるために様々な最適化パスを実行します。その一つがSSA (Static Single Assignment) 形式上で行われる共通部分式除去 (CSE) です。CSEは、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除する最適化手法です。

しかし、このコミットで示された具体的な例（ネストされたループと`continue`文を含むGoコード）において、CSEパスが誤動作することが判明しました。問題は、内側のループ変数`i`を表すPhi変数`v82`と、外側のループ変数`j`に関連する別のPhi変数`v49`が、CSEによって共通部分式と見なされてしまった点にあります。

コミットメッセージの例では、`f_ssa`関数内の内側ループのインクリメント部分（`i++`）が、SSA形式では`v29 = Add <int> v82 v28`として表現されます。ここで`v82`はループ変数`i`の現在の値を表すPhi変数です。CSEが`v82`と`v49`を共通と判断し、`v82`を`v49`に置き換えてしまうと、`v29`の計算が`v29 = Add <int> v49 v28`となり、本来`i`をインクリメントするはずの処理が、`j`に関連する値を使って行われることになります。

結果として、`v82`はもはやどこからも参照されなくなり「dead (デッド)」とマークされ、最終的にコンパイラによって削除されます。これにより、内側ループのインクリメント処理が完全に失われ、ループが無限に実行されるという重大なバグが発生しました。この問題は、Phi変数がその定義される基本ブロックに強く依存するというSSAの特性をCSEが十分に考慮していなかったために生じました。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現の一種です。SSA形式の主要な特性は、プログラム中の全ての変数が「静的に一度だけ」代入されるという点です。つまり、変数が代入されるたびに新しいバージョン（新しい名前）が割り当てられます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。

例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

SSA形式では、これは次のように表現されるかもしれません。

```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

### Phi関数 (Φ関数)

SSA形式において、制御フローグラフ (Control Flow Graph, CFG) 上で複数のパスが合流する点（例えば、if-else文の終わりやループの先頭）では、同じ論理変数に対して異なる値が到達する可能性があります。この問題を解決するために導入されるのがPhi関数です。

Phi関数は、合流点において、どの制御フローパスから来たかに応じて適切な値を選択する仮想的な命令です。例えば、`x3 = Φ(x1, x2)`というPhi関数は、「もし制御フローがパス1から来たなら`x1`を、パス2から来たなら`x2`を`x3`に代入する」という意味を持ちます。Phi関数は実際の実行時には存在せず、レジスタ割り当てなどのバックエンド処理で適切なムーブ命令に変換されます。

### CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラ最適化の一種で、プログラム内で同じ値が複数回計算されている部分（共通部分式）を特定し、その計算を一度だけ行い、結果を一時変数に格納して再利用することで、冗長な計算を排除する手法です。これにより、実行速度の向上やコードサイズの削減が期待されます。

例えば、`a = (b * c) + d`と`e = (b * c) + f`というコードがある場合、`b * c`は共通部分式です。CSEはこれを次のように変換するかもしれません。

```
temp = b * c
a = temp + d
e = temp + f
```

### 基本ブロック (Basic Block)

基本ブロックは、コンパイラ最適化における制御フローグラフの基本的な構成要素です。基本ブロックは、以下の特性を持つ命令のシーケンスです。

1.  **単一のエントリポイント**: 実行は常にブロックの最初の命令から開始されます。
2.  **単一のイグジットポイント**: 実行は常にブロックの最後の命令で終了し、次のブロックへ制御が移ります。
3.  **内部に分岐なし**: ブロック内の命令は、最後の命令を除いて、分岐命令を含みません。

プログラムは複数の基本ブロックに分割され、これらのブロック間の制御フローはエッジで表現されます。Phi関数は、複数の基本ブロックが合流する点で必要となります。

## 技術的詳細

GoコンパイラのSSAバックエンドにおけるCSEパスは、プログラムのSSA形式表現を走査し、等価な値を見つけてそれらを置き換えることで最適化を行います。この等価性の判断は、値のオペレーションコード (Op)、型 (Type)、補助データ (Aux)、補助整数値 (AuxInt)、引数の数 (nargs) などに基づいて行われます。

このコミット以前のCSEの実装では、Phi変数の等価性を判断する際に、それらが定義されている基本ブロックを考慮していませんでした。Phi関数は、その性質上、複数の異なる制御フローパスから来る値を結合するため、どの基本ブロックで定義されているかがその意味に大きく影響します。

コミットメッセージの例では、`v82`と`v49`という2つのPhi変数が問題を引き起こしました。
*   `v82`は内側のループ変数`i`に関連するPhi変数で、基本ブロック`b8`で定義されています。
*   `v49`は外側のループ変数`j`に関連するPhi変数で、基本ブロック`b4`で定義されています。

これら二つのPhi変数は、オペレーションコード、型、引数の数などが偶然一致したため、CSEパスによって共通部分式と誤認されました。しかし、これらは異なる基本ブロックで定義されており、それぞれ異なるループ変数の状態を表しているため、論理的には等価ではありません。CSEがこれらを等価と見なし、`v82`を`v49`に置き換えた結果、`v82`のインクリメント処理が失われ、無限ループが発生しました。

このバグを修正するために、CSEの等価性判断ロジックが変更されました。具体的には、値が`OpPhi`（Phi関数）である場合に限り、その値が定義されている基本ブロックのIDも等価性判断の基準に追加されました。これにより、異なる基本ブロックで定義されたPhi変数が誤って共通部分式として扱われることがなくなります。

CSEパスは、まず初期のパーティション（等価クラスの集合）を作成します。これは、オペレーションコード、型、補助データ、補助整数値、引数の数に基づいて値をグループ化するものです。このコミットでは、この初期パーティションの作成時に、Phi変数の場合はその基本ブロックIDもキーに含めるように変更されました。

変更後の`key`構造体は以下のようになります。

```go
type key struct {
	op     Op
	typ    string
	aux    interface{}
	auxint int64
	nargs  int
	block  ID // block id for phi vars, -1 otherwise
}
```

`block`フィールドが追加され、`v.Op == OpPhi`の場合にのみ、その値が定義されている基本ブロックのIDが`bid`として設定され、`key`の一部となります。それ以外のオペレーションの場合は`-1`が設定されます。これにより、Phi変数の等価性判断がより厳密になり、異なる基本ブロックのPhi変数が誤って結合されることが防止されます。

## コアとなるコードの解説

この変更は、`cse.go`ファイル内の`cse`関数、特に共通部分式を識別するための初期パーティションを生成するロジックに影響を与えます。

1.  **コメントの追加**:
    `// v.block == w.block if v.op == OpPhi`
    このコメントは、Phiオペレーションの場合に、値`v`と`w`が等価であるための新しい条件として、それらが同じ基本ブロックに属している必要があることを明示しています。これは、このコミットの核心となる変更の意図を説明しています。

2.  **`key`構造体の変更**:
    ```go
    type key struct {
    	op     Op
    	typ    string
    	aux    interface{}
    	auxint int64
    	nargs  int
    	block  ID // block id for phi vars, -1 otherwise
    }
    ```
    `key`構造体に`block ID`型の新しいフィールド`block`が追加されました。この`key`構造体は、SSA値の等価性を判断し、それらを初期の等価クラス（`eqclass`）にグループ化するために使用されます。`block`フィールドは、Phi変数の場合にのみ関連する基本ブロックのIDを保持し、それ以外の場合は`-1`が設定されます。

3.  **`key`生成ロジックの変更**:
    ```go
    			bid := ID(-1)
    			if v.Op == OpPhi {
    				bid = b.ID
    			}
    			k := key{v.Op, v.Type.String(), v.Aux, v.AuxInt, len(v.Args), bid}
    ```
    各SSA値`v`に対して`key`を生成する際に、以下のロジックが追加されました。
    *   まず、`bid`（ブロックID）をデフォルト値`-1`で初期化します。
    *   もし現在のSSA値`v`のオペレーションが`OpPhi`（Phi関数）である場合、その値が属する基本ブロック`b`のID (`b.ID`) を`bid`に設定します。
    *   最後に、この`bid`を`key`構造体の新しい`block`フィールドに含めて`key`を構築します。

この変更により、Phi変数の等価性を判断する際に、そのオペレーション、型、引数だけでなく、それがどの基本ブロックで定義されているかという情報も考慮されるようになりました。これにより、異なる基本ブロックに属するPhi変数が誤って共通部分式として扱われることがなくなり、前述の無限ループのバグが修正されます。

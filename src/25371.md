    regexp: fix slice bounds out of range panics
    
    Regular expressions involving a (x){0} term are
    simplified by removing this term from the
    expression, just before the expression is compiled.
    
    The number of subexpressions is evaluated before
    the simplification. The number of capture instructions
    in the compiled expressions is not necessarily in line
    with the number of subexpressions.
    
    When the ReplaceAll(String) methods are used, a number
    of capture slots (nmatch) is evaluated as 2*(s+1)
    (s being the number of subexpressions).
    
    In some case, it can be higher than the number of capture
    instructions evaluated at compile time, resulting in a 
    panic when the internal slices of regexp.machine
    are resized to this value.
    
    Fixed by capping the number of capture slots to the number
    of capture instructions.
    
    I must say I do not really see the benefits of setting
    nmatch lower than re.prog.NumCap using this 2*(s+1) formula,
    so perhaps this can be further simplified.

## 元コミット内容

このコミットは、Go言語の`regexp`パッケージにおいて、正規表現の置換処理中に発生する可能性のある「slice bounds out of range」パニックを修正します。特に、`(x){0}`のようなゼロ回繰り返しを含む正規表現が関与する場合に問題が発生していました。

問題の根源は、正規表現のコンパイル前に`(x){0}`のような項が簡略化されることと、サブ式の数（`s`）に基づいてキャプチャスロットの数（`nmatch`）が`2*(s+1)`として評価されることの間の不整合にありました。この`nmatch`が、コンパイル時に評価される実際のキャプチャ命令の数（`re.prog.NumCap`）よりも大きくなる場合があり、その結果、`regexp.machine`の内部スライスがリサイズされる際に範囲外アクセス（パニック）を引き起こしていました。

この修正は、`nmatch`の値を`re.prog.NumCap`で上限を設けることで、この不整合を解消します。これにより、スライスの範囲外アクセスが防止されます。

## 変更の背景

この変更は、Go言語の正規表現エンジンにおける特定のバグ報告（Issue #11178 および #11176）に対応するために行われました。これらのIssueは、正規表現の置換機能、特に`ReplaceAll`や`ReplaceAllString`メソッドを使用する際に、`(x){0}`のようなゼロ回繰り返しを含むパターンが原因で発生するランタイムパニックを報告していました。

具体的には、正規表現エンジンが最適化のために`(x){0}`のようなパターンをコンパイル前に削除する一方で、キャプチャグループの数を計算するロジックがこの最適化を考慮していなかったことが問題でした。これにより、正規表現の実行時に必要なキャプチャスロットの数が過剰に見積もられ、実際に利用可能なキャプチャ命令の数を超えてしまい、結果としてスライスへの不正なアクセスが発生していました。

このバグは、ユーザーが正規表現の置換機能を利用する際に、予期せぬプログラムのクラッシュを引き起こす可能性があり、Go言語の安定性と信頼性を損なうものでした。そのため、この問題の修正は、`regexp`パッケージの堅牢性を向上させる上で重要でした。

## 前提知識の解説

このコミットの理解には、以下の概念が前提となります。

1.  **正規表現 (Regular Expression)**: テキスト内のパターンを記述するための強力なツールです。Go言語の`regexp`パッケージは、この正規表現を扱うための機能を提供します。
2.  **キャプチャグループ (Capturing Group)**: 正規表現において、括弧`()`で囲まれた部分を指します。これにより、マッチしたテキストの一部を抽出できます。例えば、`(a)(b)`という正規表現では、`a`と`b`がそれぞれ別のキャプチャグループとなります。
3.  **ゼロ回繰り返し (Zero-width assertion / Zero-repetition)**: 正規表現の量指定子`{0}`は、直前の要素が0回繰り返されることを意味します。例えば、`(x){0}`は`x`が0回出現することを示します。これは実質的に何もマッチしない（空文字列にマッチする）ことと同じですが、正規表現の構造としては存在します。
4.  **正規表現のコンパイル**: 正規表現文字列は、効率的なマッチングのために内部的な命令セット（プログラム）に変換されます。このプロセスをコンパイルと呼びます。
5.  **サブ式 (Subexpression)**: 正規表現の構文ツリーにおける個々の構成要素を指します。キャプチャグループもサブ式の一種です。
6.  **`regexp.machine`**: Goの`regexp`パッケージ内部で、正規表現のマッチングを実行するステートマシンです。このマシンは、マッチング中にキャプチャされた部分文字列を格納するための内部スライス（配列）を保持しています。
7.  **`ReplaceAll` / `ReplaceAllString` メソッド**: `regexp`パッケージが提供する関数で、正規表現にマッチする部分をすべて指定された文字列で置換します。置換文字列には、`$1`, `$2`などのキャプチャグループを参照するプレースホルダーを含めることができます。
8.  **`slice bounds out of range` パニック**: Go言語でスライス（配列）の範囲外のインデックスにアクセスしようとしたときに発生するランタイムエラーです。これはプログラムのクラッシュを引き起こします。

## 技術的詳細

このバグは、`regexp`パッケージの内部処理におけるキャプチャスロットの管理方法に起因していました。

1.  **正規表現の簡略化**: `regexp`パッケージは、正規表現をコンパイルする前に、一部のパターンを最適化のために簡略化します。この最適化の一環として、`(x){0}`のようなゼロ回繰り返しパターンは、実質的に意味がないため、正規表現の内部表現から削除されることがあります。
2.  **`nmatch`の計算**: `ReplaceAll`や`ReplaceAllString`メソッドが呼び出される際、内部的に`nmatch`という変数が計算されます。これは、マッチング中にキャプチャされる可能性のある部分文字列を格納するために必要なスロットの総数を表します。この`nmatch`は、正規表現のサブ式の数`s`に基づいて`2*(s+1)`という式で計算されていました。ここで`s`は、簡略化前の正規表現のサブ式の数を参照していました。
3.  **`re.prog.NumCap`**: 一方、正規表現がコンパイルされた後、実際にキャプチャ命令として存在するキャプチャグループの数は`re.prog.NumCap`として保持されます。簡略化によって`(x){0}`のようなパターンが削除されると、`re.prog.NumCap`の値は、簡略化前のサブ式の数から計算された`nmatch`よりも小さくなる可能性がありました。
4.  **パニックの発生**: `regexp.machine`は、マッチング中にキャプチャ結果を格納するために、`nmatch`のサイズで内部スライスを確保しようとします。しかし、実際にコンパイルされた正規表現が持つキャプチャ命令の数（`re.prog.NumCap`）が`nmatch`よりも小さい場合、`regexp.machine`が`nmatch`のサイズでスライスを操作しようとすると、`re.prog.NumCap`で定義された実際のキャプチャ命令の範囲を超えてアクセスしようとすることがありました。これが「slice bounds out of range」パニックの原因でした。

このコミットでは、`src/regexp/regexp.go`内の`replaceAll`関数において、`nmatch`の値を`re.prog.NumCap`で上限を設けることでこの問題を解決しています。具体的には、`if nmatch > re.prog.NumCap { nmatch = re.prog.NumCap }`というガード句が追加されました。これにより、`regexp.machine`が確保しようとするキャプチャスロットの数が、実際にコンパイルされた正規表現が持つキャプチャ命令の数を超えることがなくなり、パニックが回避されます。

コミットメッセージには、「I must say I do not really see the benefits of setting nmatch lower than re.prog.NumCap using this 2*(s+1) formula, so perhaps this can be further simplified.」というコメントがあり、`nmatch`の計算式自体が将来的に見直される可能性も示唆されています。

## コアとなるコードの解説

`src/regexp/regexp.go`の`replaceAll`関数に追加された以下の4行が、この修正の核心です。

```go
	if nmatch > re.prog.NumCap {
		nmatch = re.prog.NumCap
	}
```

*   `nmatch`: これは、正規表現のマッチング中にキャプチャされた部分文字列を格納するために必要なスロットの数を表す変数です。元々は、正規表現のサブ式の数`s`に基づいて`2*(s+1)`として計算されていました。
*   `re.prog.NumCap`: これは、コンパイルされた正規表現プログラムが実際に持っているキャプチャ命令の総数を表します。正規表現の簡略化によって、一部のキャプチャグループが削除されると、この値は`nmatch`よりも小さくなる可能性があります。

この`if`文は、もし`nmatch`が`re.prog.NumCap`よりも大きい場合（つまり、必要と見積もられたスロット数が、実際に存在するキャプチャ命令の数を超えている場合）、`nmatch`の値を`re.prog.NumCap`に切り詰めます。

これにより、`regexp.machine`が内部スライスを操作する際に、実際に存在するキャプチャ命令の範囲を超えてアクセスしようとすることがなくなり、`slice bounds out of range`パニックが効果的に防止されます。この修正は、過剰に見積もられたリソース要求を、実際に利用可能なリソースの範囲内に収めることで、システムの安定性を確保しています。

`src/regexp/all_test.go`に追加されたテストケースは、この修正が意図した通りに機能し、以前パニックを引き起こしていた特定の正規表現パターンが正しく処理されることを検証します。

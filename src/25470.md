## 変更の背景

Goコンパイラは、プログラムの実行速度を向上させるために、小さな関数を呼び出し元に直接展開する「インライン化」という最適化を行います。しかし、特定の状況、特にテストやプロファイリングのシナリオでは、このインライン化が望ましくない場合があります。例えば、正確なスタックトレースを検証したい場合や、特定の関数の呼び出し回数やメモリ割り当てを測定したい場合などです。

`//go:noinline` ディレクティブがGo言語に導入される以前は、開発者はコンパイラが関数をインライン化しないように「騙す」ための様々な非公式な手法を用いていました。これには、無限ループに見えるが実際には実行されないコード（`for false {}`）、再帰呼び出し（`if c { f() }`）、パニックの発生（`panic("")`）、`runtime.GC()` の呼び出し、あるいは空の `defer` ステートメントの追加などが含まれていました。

これらの手法は、コンパイラの挙動に依存しており、コンパイラの最適化ロジックが変更されると、意図せずインライン化されてしまうリスクがありました。また、コードの可読性を損ない、なぜそのような「奇妙な」コードが存在するのかを理解するのに余分な労力を要しました。

このコミットは、`//go:noinline` ディレクティブが安定して利用可能になったことを受け、これらの非公式な手法を公式かつ明確なディレクティブに置き換えることで、テストコードの堅牢性、可読性、および保守性を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラのインライン化 (Inlining)

インライン化は、コンパイラ最適化の一種で、関数呼び出しのオーバーヘッド（スタックフレームのセットアップ、引数のプッシュ、戻り値の処理など）を削減するために、呼び出される関数の本体を呼び出し元のコードに直接埋め込む処理です。これにより、プログラムの実行速度が向上する可能性があります。Goコンパイラは、関数のサイズや複雑さ、呼び出し回数などのヒューリスティックに基づいて、自動的にインライン化を行うかどうかを決定します。

### インライン化の防止 (Inlining Prevention)

インライン化は通常は望ましい最適化ですが、以下のようなケースでは意図的に防止したい場合があります。

1.  **正確なスタックトレースの取得**: デバッグやエラー報告の際に、特定の関数がスタックトレースに明確に表示される必要がある場合。インライン化されると、その関数はスタックトレースから消えてしまいます。
2.  **プロファイリングの精度**: メモリプロファイリングやCPUプロファイリングにおいて、特定の関数のリソース消費を正確に測定したい場合。インライン化されると、その関数のコストが呼び出し元に分散されてしまい、正確な測定が困難になります。
3.  **特定のコードパスのテスト**: コンパイラの最適化によって特定のコードパスが削除されたり、実行順序が変わったりするのを防ぎ、テストの意図通りにコードが実行されることを保証したい場合。
4.  **ベンチマークの安定性**: ベンチマークテストにおいて、コンパイラの最適化による変動を最小限に抑え、安定した測定結果を得たい場合。

### `//go:noinline` ディレクティブ

`//go:noinline` は、Goコンパイラに対する特別な指示（プラグマ）です。このディレクティブが関数の宣言の直前にコメントとして記述されている場合、コンパイラはその関数をインライン化しないように強制されます。これは、Goコンパイラが提供する公式かつ推奨されるインライン化防止メカニズムです。

例:
```go
//go:noinline
func myFunc() {
    // この関数はインライン化されない
}
```

### 以前のインライン化防止のハック

`//go:noinline` が導入される前、Go開発者は以下のような「ハック」を用いてインライン化を防止していました。

*   **`for false {}`**: 常に偽となる条件を持つループを関数内に挿入することで、コンパイラに「この関数は複雑でインライン化すべきではない」と誤認させる試み。
*   **`if someGlobalBool { recursiveCall() }`**: グローバル変数に依存する条件付き再帰呼び出しを挿入し、コンパイラが呼び出しグラフを完全に解析できないようにする。
*   **`panic("")`**: 実行されないパニックを挿入することで、コンパイラが関数の制御フローを複雑だと判断するように仕向ける。
*   **`defer func() {}()`**: 空の `defer` ステートメントは、コンパイラにとって追加の処理を意味するため、インライン化を抑制する効果がある場合がありました。
*   **`runtime.GC()`**: ガベージコレクションの呼び出しは、コンパイラにとってコストの高い操作であり、インライン化の判断に影響を与えることがありました。
*   **ダミーのスタック操作**: `var pleaseDoNotInlineMe stack; pleaseDoNotInlineMe.push(1); _ = pleaseDoNotInlineMe.pop()` のように、意味のないスタック操作を挿入して、関数が複雑であると見せかける。

これらのハックは、コンパイラの内部実装に依存しており、Goのバージョンアップによって挙動が変わる可能性がありました。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの進化と、それに対応する開発プラクティスの標準化にあります。`//go:noinline` ディレクティブは、Go 1.4で導入され、Go 1.5でより広範に利用可能になりました。このディレクティブの導入により、インライン化の制御がより明示的かつ安定したものになりました。

コミットは、Goプロジェクト内の広範なテストファイル群を対象に、以下のパターンで変更を適用しています。

1.  **既存のインライン化防止ハックの特定**: `for false {}`、`if c { f() }`、`panic("")`、`defer func() {}()`、`runtime.GC()`、ダミーのスタック操作など、様々な非公式なインライン化防止策が使用されている箇所を特定します。
2.  **ハックの削除**: 特定された非公式なコードを削除します。これにより、コードが簡潔になり、本来のロジックが明確になります。
3.  **`//go:noinline` ディレクティブの追加**: 削除されたハックの代わりに、インライン化を防止したい関数の宣言の直前に `//go:noinline` コメントを追加します。

この変更により、コンパイラは関数のインライン化に関する明確な指示を受け取ることになり、テストの意図がより正確に反映されるようになります。また、将来のコンパイラの最適化アルゴリズムの変更によって、以前のハックが機能しなくなるリスクが排除されます。これは、Go言語の長期的な安定性と保守性にとって重要な改善です。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの進化と、それに対応する開発プラクティスの標準化にあります。`//go:noinline` ディレクティブは、Go 1.4で導入され、Go 1.5でより広範に利用可能になりました。このディレクティブの導入により、インライン化の制御がより明示的かつ安定したものになりました。

コミットは、Goプロジェクト内の広範なテストファイル群を対象に、以下のパターンで変更を適用しています。

1.  **既存のインライン化防止ハックの特定**: `for false {}`、`if c { f() }`、`panic("")`、`defer func() {}()`、`runtime.GC()`、ダミーのスタック操作など、様々な非公式なインライン化防止策が使用されている箇所を特定します。
2.  **ハックの削除**: 特定された非公式なコードを削除します。これにより、コードが簡潔になり、本来のロジックが明確になります。
3.  **`//go:noinline` ディレクティブの追加**: 削除されたハックの代わりに、インライン化を防止したい関数の宣言の直前に `//go:noinline` コメントを追加します。

この変更により、コンパイラは関数のインライン化に関する明確な指示を受け取ることになり、テストの意図がより正確に反映されるようになります。また、将来のコンパイラの最適化アルゴリズムの変更によって、以前のハックが機能しなくなるリスクが排除されます。これは、Go言語の長期的な安定性と保守性にとって重要な改善です。

## コアとなるコードの解説

いくつかの具体的な変更例を見てみましょう。

### `src/runtime/gc_test.go` の `testIfaceEqual` 関数

変更前:
```go
func testIfaceEqual(x interface{}) {
	if x == "abc" {
		// Prevent inlining
		panic("")
	}
}
```
変更後:
```go
var a bool

//go:noinline
func testIfaceEqual(x interface{}) {
	if x == "abc" {
		a = true
	}
}
```
ここでは、インライン化防止のために意図的に `panic("")` を呼び出すというハックが削除され、関数の直前に `//go:noinline` ディレクティブが追加されています。また、`panic` の代わりにダミーのグローバル変数 `a` を設定するコードに置き換えられています。

### `src/runtime/pprof/mprof_test.go` の `allocateTransient2M` 関数

変更前:
```go
func allocateTransient2M() {
	// prevent inlining
	if memSink == nil {
		panic("bad")
	}
	memSink = make([]byte, 2<<20)
}
```
変更後:
```go
//go:noinline
func allocateTransient2M() {
	memSink = make([]byte, 2<<20)
}
```
ここでも同様に、`if memSink == nil { panic("bad") }` というインライン化防止のハックが削除され、`//go:noinline` が追加されています。これにより、関数本体のロジックがより明確になっています。

### `test/fixedbugs/bug401.go` の `cplx` メソッド

変更前:
```go
func (T) cplx() complex128 {
	for false {
	} // avoid inlining
	return complex(1, 0)
}
```
変更後:
```go
//go:noinline
func (T) cplx() complex128 {
	return complex(1, 0)
}
```
`for false {}` という、常に実行されないループを挿入してインライン化を回避する手法が削除され、`//go:noinline` に置き換えられています。これにより、コードの無駄が省かれ、意図が明確になります。

### `test/fixedbugs/issue10441.go` の `foo` 関数

変更前:
```go
func foo(f *func()) func() {
	defer func() {}() // prevent inlining of foo
	return *f
}
```
変更後:
```go
//go:noinline
func foo(f *func()) func() {
	return *f
}
```
空の `defer` ステートメントを利用してインライン化を防止する手法が削除され、`//go:noinline` が追加されています。

### `test/fixedbugs/issue8036.go` の `G` 関数と `F` 関数

変更前:
```go
func G() (t TI) {
	t[0] = 1
	t[1] = 2
	t[2] = 3
	runtime.GC() // prevent inlining
	return
}

func F() (t T) {
	t.X = newint()
	t.Y = t.X
	t.Z = t.Y
	runtime.GC() // prevent inlining
	return
}
```
変更後:
```go
//go:noinline
func G() (t TI) {
	t[0] = 1
	t[1] = 2
	t[2] = 3
	return
}

//go:noinline
func F() (t T) {
	t.X = newint()
	t.Y = t.X
	t.Z = t.Y
	return
}
```
`runtime.GC()` を呼び出すことでインライン化を防止する手法が削除され、`//go:noinline` が追加されています。

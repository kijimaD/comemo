# [インデックス 24448] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）における`nosplit`関数のスタックオーバーフローチェックロジックを簡素化するものです。以前は`runtime.morestack`への呼び出しが特別扱いされていましたが、これはスタックポインタ（SP）情報の不正確さという根本的なバグに対する回避策でした。先行するコミット（CL 12144）でこのバグが修正されたため、本コミットではその特別扱いロジックを削除し、コードのクリーンアップと簡素化を行っています。この変更は、ARM64のフレームサイズ調整作業中に発生したバグの修正にも寄与しました。

## 元コミット内容

このコミットは、Goリンカの`nosplit`関数に対するスタックオーバーフローチェックの修正を目的としています。具体的には、`runtime.morestack`関数が呼び出される際のスタックポインタ（SP）情報が不正確であるという問題に対し、以前はリンカ側で特別扱いする回避策が講じられていました。しかし、この根本的なSP情報のバグは、先行する変更リスト（CL 12144）で修正されました。

CL 12144での修正により、`morestack`を特別扱いする必要がなくなったため、本コミットではその複雑な回避策ロジックを削除し、コードを簡素化しています。このクリーンアップと簡素化は、ARM64アーキテクチャのフレームサイズ調整作業中に発生したバグを修正するための第一歩でしたが、結果的にこのクリーンアップ自体でバグが解消されました。この変更は、GoのIssue #9880に関連しています。

## 変更の背景

Goランタイムでは、ゴルーチンのスタックは必要に応じて動的に拡張されます。この拡張プロセスは、スタックが不足しそうになったときに`runtime.morestack`関数を呼び出すことでトリガーされます。しかし、`nosplit`関数（スタックチェックを行わない関数）のスタックオーバーフローチェックにおいて、`morestack`が呼び出される際のスタックポインタ情報に不正確な点がありました。

この不正確さに対処するため、Goリンカは`morestack`への呼び出しを特別扱いするロジックを持っていました。これは、`morestack`がコード内のどこに現れても、それが関数のエントリポイントで発生したかのようにスタック制限を調整することで、フローに依存しないスタックチェックの誤認識を回避しようとするものでした。しかし、この特別扱いはコードを複雑にし、潜在的なバグの原因となっていました。

先行するCL 12144で、このスタックポインタ情報の不正確さという根本的なバグが修正されました。これにより、`morestack`を特別扱いする必要がなくなり、リンカのコードを簡素化できる状況が生まれました。本コミットは、この簡素化を実行し、不要になった特別扱いロジックを削除することで、コードの保守性を向上させ、さらにARM64のフレームサイズ調整中に発見された関連バグも解消しました。

## 前提知識の解説

*   **Goランタイムのスタック管理**: Goのゴルーチンは、固定サイズのスタックではなく、必要に応じて動的に拡張・縮小するスタックを使用します。これにより、スタックオーバーフローを回避しつつ、メモリ効率を向上させています。
*   **`morestack`**: ゴルーチンのスタックが不足した際に、ランタイムが自動的に呼び出す特殊な関数です。この関数は、より大きなスタックフレームを割り当て、現在のスタックの内容を新しいスタックにコピーし、実行を新しいスタックで再開します。`morestack`自体は、スタックチェックを行わない`nosplit`関数として実装されています。
*   **`nosplit`関数**: Goコンパイラによって生成される関数の中には、スタックチェックのプロローグ（関数エントリ時にスタックが十分かを確認するコード）を持たないものがあります。これらは`nosplit`関数と呼ばれ、非常に短い関数や、スタックチェックのオーバーヘッドが許容されないクリティカルなパス（例: `morestack`自身）で使用されます。`nosplit`関数は、呼び出し元が十分なスタックを確保していることを前提とします。
*   **スタックオーバーフローチェック**: Goの関数呼び出しでは、通常、関数エントリ時に現在のスタックポインタとスタックリミットを比較し、スタックが不足している場合は`morestack`を呼び出すコード（スタックチェックプロローグ）が挿入されます。
*   **`cmd/link`**: Goツールチェーンの一部であるリンカです。コンパイラが生成したオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイルや共有ライブラリを生成します。この過程で、スタックチェックのプロローグの挿入や、リロケーションの解決など、様々な低レベルの処理を行います。
*   **`LSym`**: リンカが内部的に使用するシンボル（関数、グローバル変数など）の構造体です。
*   **`obj.StackLimit`**: Goランタイムが定義する、スタックの最小許容サイズを示す定数です。
*   **`callsize()`**: 特定のアーキテクチャにおける関数呼び出しに必要なスタックフレームのサイズを計算するヘルパー関数です。
*   **`R_CALL`**: リンカが処理するリロケーションタイプの一つで、関数呼び出し命令（例: `CALL`命令）のターゲットアドレスを解決するために使用されます。

## 技術的詳細

このコミットの核心は、Goリンカが`nosplit`関数のスタックオーバーフローチェックを行う際の`morestack`呼び出しに対する特別な処理を削除した点にあります。

以前のリンカのロジックでは、`morestack`が呼び出される際のスタックポインタ（SP）情報が不正確であるという問題がありました。これは、`morestack`がスタックを拡張する際に、その呼び出し時点でのSPが、実際にスタックが不足している状況を正確に反映していない可能性があったためです。このため、リンカは`stkcheck`関数内で、`morestack`への呼び出しを特別に検出し、その呼び出しが関数のエントリポイントで発生したかのようにスタック制限を調整する複雑なロジックを持っていました。このロジックは、`s.R`（シンボルのリロケーションリスト）を走査し、`runtime.morestack`への`R_CALL`リロケーションを見つけると、スタックチェックのロジックを調整するというものでした。

しかし、CL 12144でこの根本的なSP情報の不正確さが修正されたことで、`morestack`呼び出しを特別扱いする必要がなくなりました。SP情報が正確になったため、リンカは`morestack`呼び出しを他の通常の関数呼び出しと同様に、スタックチェックのロジック内で自然に処理できるようになりました。

本コミットでは、以下の主要な変更が行われました。

1.  **`newstack`シンボルの削除**: `runtime.newstack`は`morestack`の内部実装に関連するシンボルでしたが、リンカが直接参照する必要がなくなったか、`morestack`の処理ロジックに統合されたため、その宣言と初期化が削除されました。
2.  **`morestack`特別扱いロジックの削除**: `stkcheck`関数内にあった、`morestack`への呼び出しを特別に処理するための大規模な`for`ループが完全に削除されました。これにより、スタックチェックのコードが大幅に簡素化されました。
3.  **`morestack`スキップロジックの削除**: 以前のロジックでは、`morestack`が特別扱いされた後、通常の関数呼び出しの処理ループで再度`morestack`への呼び出しを処理しないようにスキップする条件分岐がありました。特別扱いがなくなったため、このスキップロジックも不要となり削除されました。
4.  **`stkprint`での`(nosplit)`タグ追加**: `stkprint`関数（スタックトレースの表示などデバッグ用途で使用される可能性のある関数）において、`nosplit`属性を持つシンボルに対して`(nosplit)`というタグを名前に追加するようになりました。これは、デバッグ時の可読性向上を目的とした補助的な変更です。

これらの変更により、Goリンカのスタックチェックロジックはよりシンプルで堅牢になり、`morestack`呼び出しが他の関数呼び出しと同様に一貫して扱われるようになりました。

## コアとなるコードの解説

1.  **`newstack`シンボルの削除**:
    *   `var ( morestack *LSym; newstack *LSym )` から `var morestack *LSym` へと変更され、`newstack = Linklookup(Ctxt, "runtime.newstack", 0)` の行も削除されました。
    *   これは、リンカが`runtime.newstack`シンボルを直接追跡または参照する必要がなくなったことを示しています。`runtime.morestack`の内部実装が変更されたか、リンカのスタックチェックロジックから`newstack`への直接的な依存が取り除かれたためと考えられます。

2.  **`morestack`特別扱いロジックの削除**:
    *   `stkcheck`関数内の、`morestack`への呼び出しを特別扱いしていた大規模な`for`ループが削除されました。このループは、`s.R`（シンボルのリロケーションリスト）を走査し、`runtime.morestack`への`R_CALL`リロケーションを検出すると、スタック制限を調整していました。
    *   この削除は、CL 12144で根本的なSP情報の不正確さが修正されたため、`morestack`呼び出しを他の通常の関数呼び出しと同様に扱えるようになったことを意味します。これにより、スタックチェックのロジックが大幅に簡素化され、コードの複雑性が軽減されました。

3.  **`morestack`スキップロジックの削除**:
    *   通常の関数呼び出しを処理するループ内で、`strings.HasPrefix(r.Sym.Name, "runtime.morestack")` をチェックして`morestack`への呼び出しをスキップしていた条件分岐が削除されました。
    *   これは、`morestack`がもはや特別扱いされず、通常の関数呼び出しと同様にスタックチェックのロジック内で処理されるようになったため、以前のスキップロジックが不要になったことを示しています。

4.  **`stkprint`での`(nosplit)`タグ追加**:
    *   `stkprint`関数内で、`ch.sym.Nosplit != 0` の場合に`name += " (nosplit)"` という行が追加されました。
    *   これは、スタックトレースやデバッグ出力において、`nosplit`関数であることを明示的に示すための変更です。これにより、デバッグ時の情報がより豊富になり、`nosplit`関数の挙動を理解しやすくなります。

これらの変更は全体として、Goリンカのスタックチェック機構をよりシンプルで、より正確なスタックポインタ情報に基づいたものへと進化させています。

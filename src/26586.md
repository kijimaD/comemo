# [インデックス 26586] ファイルの概要

このコミットは、Goランタイムにおける`mmap`および`mincore`システムコールのエラーコード（`errno`）の符号に関する不整合を修正するものです。特定のアーキテクチャ（`linux-arm64`、`nacl-386`、`linux-mips64x`、`linux-ppc64x`）において、システムコールが返す`errno`の符号が、Goランタイムの呼び出し側が期待する符号と異なっていた問題を解決します。具体的には、`mmap`では正の`errno`が、`mincore`では負の`errno`が期待されるにもかかわらず、逆の符号が返されるケースがあったため、アセンブリコードレベルで符号を反転させる修正が加えられました。また、`mmap`のエラー符号を検証するための新しいテストも追加されています。

## 変更の背景

Goランタイムは、オペレーティングシステム（OS）のシステムコールを直接呼び出して、メモリ管理などの低レベルな操作を行います。システムコールがエラーを返した場合、そのエラー情報は通常、`errno`というグローバル変数（またはスレッドローカル変数）に設定されるか、システムコールの戻り値として特定の形式で返されます。

このコミットの背景にある問題は、Goランタイムが特定のシステムコール（`mmap`と`mincore`）の戻り値から`errno`を解釈する際に、OSやアーキテクチャによって異なる`errno`の符号規則に起因する不整合が生じていたことです。

具体的には、以下の状況が発生していました。

1.  **`mmap`システムコール**:
    *   一般的なUNIX系システムでは、`mmap`は成功時にマップされたメモリ領域の開始アドレスを返し、失敗時には`MAP_FAILED`（通常は`-1`）を返し、エラーの詳細は`errno`に正の値で設定されます。
    *   しかし、`linux-arm64`および`nacl-386`環境のGoランタイムが直接呼び出すシステムコールでは、エラー時に戻り値として負の`errno`値が返される実装になっていました。Goランタイムの内部ロジック（特に`mem_bsd.go`、`mem_darwin.go`、`mem_linux.go`の`sysMap`関数など）は、`errno`が正の値であることを前提としていたため、この不整合が問題を引き起こしていました。

2.  **`mincore`システムコール**:
    *   `mincore`システムコールは、指定されたメモリ領域のページが物理メモリに存在するかどうかを問い合わせるものです。このシステムコールは、成功時には`0`を返し、失敗時には`-1`を返し、`errno`にエラーコードを設定します。
    *   コミットメッセージによると、`mincore`の呼び出し側はエラー時に負の`errno`値を期待するという「一貫性のない」規則がありました。しかし、`linux-mips64x`および`linux-ppc64x`環境のシステムコールでは、エラー時に正の`errno`値が返されていました。これもまた、Goランタイムの期待と実際の挙動の間に不整合を生じさせていました。

これらの不整合は、Goプログラムが特定の環境でメモリ関連の操作を行う際に、誤ったエラー処理や予期せぬ挙動を引き起こす可能性がありました。このコミットは、これらのアーキテクチャ固有の`errno`符号の差異を吸収し、Goランタイム全体で一貫したエラー処理が行われるようにするために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

### 1. システムコール (System Call)

システムコールは、ユーザー空間のプログラムがオペレーティングシステムカーネルのサービスを要求するためのメカニズムです。ファイルI/O、メモリ管理、プロセス制御など、特権的な操作を行う際に使用されます。Goランタイムは、メモリ確保や解放のために`mmap`や`mincore`といったシステムコールを直接利用します。

### 2. `mmap`システムコール

`mmap` (memory map) は、ファイルやデバイスをプロセスのアドレス空間にマッピングするためのシステムコールです。これにより、ファイルの内容をメモリのように直接アクセスできるようになります。また、匿名マッピング（ファイルに関連付けられないメモリ領域）を作成するためにも使用され、これはGoランタイムがヒープメモリを確保する際などに利用します。

*   **成功時の戻り値**: マッピングされたメモリ領域の開始アドレス（`void *`型）。
*   **失敗時の戻り値**: `MAP_FAILED`（通常は`(void *)-1`）。
*   **エラー情報**: 失敗時には、グローバル変数`errno`にエラーコード（例: `ENOMEM`、`EACCES`など）が設定されます。UNIX系システムでは、これらのエラーコードは通常、正の整数です。

### 3. `mincore`システムコール

`mincore` (minimum core) は、指定されたメモリ領域の各ページが現在物理メモリ（RAM）上に存在するかどうかを問い合わせるシステムコールです。これは、メモリの常駐性（residency）をチェックするために使用され、メモリ管理の最適化やデバッグに役立ちます。

*   **成功時の戻り値**: `0`。
*   **失敗時の戻り値**: `-1`。
*   **エラー情報**: 失敗時には、グローバル変数`errno`にエラーコードが設定されます。コミットメッセージによると、`mincore`の呼び出し側はエラー時に負の`errno`値を期待するという「一貫性のない」規則が存在するとのことです。これは、一部のシステムコールラッパーやライブラリが、エラーを示すために負の値を返す慣習に従っていることを示唆しています。

### 4. `errno`とエラーハンドリング

`errno`は、システムコールやライブラリ関数がエラーを報告するために使用する整数型のグローバル変数（またはスレッドローカル変数）です。各エラーコードは、特定のエラー条件（例: `ENOMEM`はメモリ不足、`EPERM`は権限不足）に対応しています。

*   **一般的な慣習**: 多くのUNIX系システムコールは、成功時に非負の値を返し、失敗時に`-1`を返し、`errno`に正のエラーコードを設定します。
*   **Goランタイムの期待**: Goランタイムの内部では、システムコールから返されるエラーコードの符号について特定の期待値があります。このコミットは、その期待値と実際のシステムコールの挙動が一部のアーキテクチャで異なっていたことを示しています。特に、アセンブリレベルでシステムコールを直接呼び出す場合、OSカーネルが返す生の値がそのままGoランタイムに渡されるため、このような符号の不整合が発生しやすくなります。

### 5. アセンブリ言語とシステムコールラッパー

Goランタイムは、パフォーマンスや低レベルな制御のために、一部のシステムコールをGo言語ではなくアセンブリ言語で直接呼び出します。これにより、C言語の標準ライブラリ（libc）を介さずにカーネルと直接対話できます。この直接呼び出しの際に、システムコールの戻り値の解釈や`errno`の処理が、Goランタイムの期待する形式に合うように調整される必要があります。今回の修正は、このアセンブリレベルでの調整が不十分だったために発生したものです。

### 6. `NOSPLIT`関数

Goランタイムのアセンブリコードには、`NOSPLIT`というディレクティブが付与された関数がよく見られます。これは、その関数がスタックを拡張しないことをコンパイラに指示するものです。ランタイムの非常に低レベルな部分（例えば、スタック管理自体に関わる部分）で、スタックの拡張ができない、あるいは望ましくない場合に用いられます。`mmap`や`mincore`のようなシステムコールラッパーは、しばしば`NOSPLIT`として実装されます。

## 技術的詳細

このコミットの技術的詳細は、主にGoランタイムがシステムコールを呼び出す際のエラーコード（`errno`）の処理方法と、特定のアーキテクチャにおけるアセンブリコードの修正に焦点を当てています。

### `errno`の符号に関する不整合

Goランタイムは、`mmap`システムコールからのエラーコードを正の値として期待しています。これは、Goの内部メモリ管理ルーチン（例: `sysMap`）が`ENOMEM`などのエラーコードを直接比較する際に、正の値として扱われることを前提としているためです。しかし、`linux-arm64`および`nacl-386`環境では、カーネルがエラー時に戻り値として負の`errno`値を返していました。例えば、`ENOMEM`が`12`である場合、システムコールは`-12`を返していたことになります。

一方、`mincore`システムコールに関しては、Goランタイムの呼び出し側はエラー時に負の`errno`値を期待するという、やや特殊な慣習がありました。これは、一部のシステムコールラッパーがエラーを示すために負の値を返す設計になっていることに起因する可能性があります。しかし、`linux-mips64x`および`linux-ppc64x`環境では、システムコールがエラー時に正の`errno`値を返していました。例えば、`EFAULT`が`14`である場合、システムコールは`14`を返していたことになります。

これらの不整合は、Goランタイムがシステムコールからのエラーを正しく識別・処理できない原因となっていました。

### アセンブリコードによる符号の修正

この問題を解決するため、各アーキテクチャ固有のアセンブリコードに、システムコールの戻り値の符号を調整する命令が追加されました。

#### `mmap`の修正 (`linux-arm64`, `nacl-386`)

*   **`src/runtime/sys_linux_arm64.s`**:
    `mmap`システムコールが完了した後、`R0`レジスタ（システムコールの戻り値を保持）の値をチェックします。
    ```assembly
    	CMN	$4095, R0   // R0 + 4095 を計算し、フラグを設定
    	BCC	2(PC)       // キャリーフラグがクリアされていれば（R0が負でなければ）スキップ
    	NEG	R0,R0       // R0が負の場合、R0を反転（正にする）
    ```
    `CMN`命令は`R0`に`4095`を加算し、その結果に基づいてフラグを設定します。`4095`という値は、Linuxカーネルがエラーを示すために返す負の値の範囲（通常`-1`から`-4095`）をカバーするためのマジックナンバーです。`BCC` (Branch if Carry Clear) は、`R0`が負の値（エラーを示す）である場合に`NEG`命令を実行するように制御します。これにより、負の`errno`値が正に変換されます。

*   **`src/runtime/sys_nacl_386.s`**:
    `mmap`システムコールが完了した後、`AX`レジスタ（システムコールの戻り値を保持）の値をチェックします。
    ```assembly
    	CMPL	AX, $-4095  // AX と -4095 を比較
    	JNA	2(PC)       // AX <= -4095 でなければスキップ
    	NEGL	AX          // AXが負の場合、AXを反転（正にする）
    ```
    `CMPL`命令で`AX`と`-4095`を比較し、`JNA` (Jump if Not Above) 命令で`AX`が負の値（エラーを示す）である場合に`NEGL`命令を実行するように制御します。これも`linux-arm64`と同様に、負の`errno`値を正に変換します。

#### `mincore`の修正 (`linux-mips64x`, `linux-ppc64x`)

*   **`src/runtime/sys_linux_mips64x.s`**:
    `mincore`システムコールが完了した後、`R2`レジスタ（システムコールの戻り値を保持）の値を調整します。
    ```assembly
    	SUBVU	R2, R0, R2	// caller expects negative errno
    ```
    この命令は、`R0`から`R2`を減算し、結果を`R2`に格納します。`mincore`の成功時の戻り値は`0`であり、エラー時には`R2`に正の`errno`が設定されるため、`0 - errno`を計算することで負の`errno`値を得ています。

*   **`src/runtime/sys_linux_ppc64x.s`**:
    `mincore`システムコールが完了した後、`R3`レジスタ（システムコールの戻り値を保持）の値を調整します。
    ```assembly
    	NEG	R3		// caller expects negative errno
    ```
    `NEG`命令は`R3`の値を反転させます。`mincore`が正の`errno`を`R3`に返した場合、この命令によって負の`errno`に変換されます。

### テストの追加と変更

*   **`src/runtime/export_mmap_test.go`の追加**:
    `mmap`システムコールとその関連定数（`ENOMEM`, `MAP_ANON`, `MAP_PRIVATE`）をテストパッケージからアクセスできるようにエクスポートするための新しいファイルです。これにより、`runtime_mmap_test.go`で`mmap`の挙動をテストできるようになります。

*   **`src/runtime/runtime_mmap_test.go`の追加**:
    `TestMmapErrorSign`という新しいテスト関数が追加されました。このテストは、`mmap`が非常に大きな（無効な）アドレス範囲を要求することで意図的にメモリ不足エラー（`ENOMEM`）を発生させ、その際に`mmap`が返すエラーコードがGoランタイムが期待する正の`ENOMEM`値と一致するかどうかを検証します。
    ```go
    func TestMmapErrorSign(t *testing.T) {
    	p := runtime.Mmap(nil, ^uintptr(0)&^(sys.PhysPageSize-1), 0, runtime.MAP_ANON|runtime.MAP_PRIVATE, -1, 0)
    	// ...
    	if v != runtime.ENOMEM {
    		t.Errorf("mmap = %v, want %v", v, runtime.ENOMEM)
    	}
    }
    ```
    `^uintptr(0)&^(sys.PhysPageSize-1)`は、システムが割り当てることができないような非常に大きな、ページサイズにアラインされたアドレス範囲を生成するためのイディオムです。これにより、確実に`ENOMEM`エラーを発生させることができます。

*   **`src/runtime/export_linux_test.go`と`src/runtime/export_test.go`の変更**:
    `mincore`のエクスポートが`export_test.go`から`export_linux_test.go`に移動されました。これは、`mincore`がLinux固有のシステムコールであるため、より適切な場所に配置し、テストのスコープを明確にするための変更と考えられます。

*   **`src/runtime/mem_bsd.go`と`src/runtime/os2_nacl.go`の変更**:
    `_ENOMEM`定数の定義に関する微調整が行われています。`os2_nacl.go`では`_ENOMEM`の定義がコメントアウトされ、「`_ENOMEM`は`mem_bsd.go`でnacl用に定義されている」というコメントが追加されています。これは、定数の重複定義を避け、一貫した定義元を使用するための整理です。

これらの変更により、Goランタイムは異なるアーキテクチャやOS環境下でも、`mmap`および`mincore`システムコールからのエラーを正しく解釈し、一貫したエラー処理ロジックを適用できるようになりました。

    ```diff
    +		t.Errorf("mmap = %v, want %v", v, runtime.ENOMEM)
    +	}
    +}
    ```

## コアとなるコードの解説

### アセンブリコードの符号調整

Goランタイムは、OSのシステムコールを直接呼び出す際に、その戻り値をGoの内部ロジックが期待する形式に変換する必要があります。このコミットでは、特に`errno`の符号に関する変換が行われています。

#### `mmap`のエラー符号修正 (`linux-arm64`, `nacl-386`)

Linuxカーネルのシステムコールは、エラーが発生した場合に、戻り値として負の整数（`-errno`）を返すことがあります。しかし、Goランタイムの`mmap`を呼び出す高レベルなコード（`sysMap`など）は、`errno`が正の値であることを前提としています。

*   **`linux-arm64` (`sys_linux_arm64.s`)**:
    `SVC`命令（システムコール呼び出し）の後、`R0`レジスタにはシステムコールの戻り値が格納されます。
    `CMN $4095, R0`は、`R0`に`4095`を加算し、その結果に基づいてステータスフラグ（特にキャリーフラグ）を設定します。Linuxカーネルが返す負のエラーコードは通常`-1`から`-4095`の範囲にあるため、`R0`がこの範囲の負の値であれば、`R0 + 4095`は正の値になり、キャリーフラグはクリアされます。
    `BCC 2(PC)`は、「キャリーフラグがクリアされていれば（つまり`R0`が負のエラーコードでなければ）、次の2バイト（`NEG R0,R0`命令をスキップする）にジャンプする」という意味です。
    もし`R0`が負のエラーコードであれば、`BCC`はジャンプせず、`NEG R0,R0`が実行されます。これは`R0`の値を反転させ、負の`errno`を正の`errno`に変換します。

*   **`nacl-386` (`sys_nacl_386.s`)**:
    `NACL_SYSCALL(SYS_mmap)`の後、`AX`レジスタにはシステムコールの戻り値が格納されます。
    `CMPL AX, $-4095`は、`AX`レジスタの値と即値`-4095`を比較します。
    `JNA 2(PC)`は、「`AX`が`-4095`より大きくない（つまり`AX <= -4095`）ならば、次の2バイト（`NEGL AX`命令をスキップする）にジャンプする」という意味です。これは、`AX`が負のエラーコード（`-1`から`-4095`の範囲）である場合に`NEGL AX`を実行しないように見えますが、実際には`JNA`は「Not Above」であり、符号付き比較では`AX <= -4095`が真の場合にジャンプします。つまり、`AX`が`-4095`より大きい負の値（例: `-12`）の場合に`NEGL AX`が実行され、正の`errno`に変換されます。

#### `mincore`のエラー符号修正 (`linux-mips64x`, `linux-ppc64x`)

`mincore`システムコールの場合、Goランタイムの呼び出し側はエラー時に負の`errno`値を期待するという特殊な要件がありました。

*   **`linux-mips64x` (`sys_linux_mips64x.s`)**:
    `SYSCALL`命令の後、`R2`レジスタにはシステムコールの戻り値が格納されます。成功時は`0`、エラー時は正の`errno`です。
    `SUBVU R2, R0, R2`は、`R0`（通常は`0`）から`R2`の値を減算し、結果を`R2`に格納します。これにより、`0 - errno`が計算され、正の`errno`が負の`errno`に変換されます。

*   **`linux-ppc64x` (`sys_linux_ppc64x.s`)**:
    `SYSCALL $SYS_mincore`の後、`R3`レジスタにはシステムコールの戻り値が格納されます。成功時は`0`、エラー時は正の`errno`です。
    `NEG R3`は、`R3`レジスタの値を反転させます。これにより、正の`errno`が負の`errno`に変換されます。

### `mmap`エラー符号テスト (`runtime_mmap_test.go`)

新しく追加された`TestMmapErrorSign`は、`mmap`システムコールがエラー時に正しい符号の`errno`を返すことを保証するための重要なテストです。

テストでは、`runtime.Mmap`関数を呼び出し、非常に大きな（システムが割り当てられない）メモリ領域を要求することで、意図的に`ENOMEM`（メモリ不足）エラーを発生させます。
`^uintptr(0)&^(sys.PhysPageSize-1)`という式は、`uintptr`型の最大値からページサイズにアラインされた値を引くことで、非常に大きな、かつページ境界に揃ったアドレス範囲を生成します。これにより、`mmap`が確実に失敗し、`ENOMEM`エラーを返すことが期待されます。

テストの核心は、`runtime.Mmap`が返した値`v`が、Goランタイムが期待する正の`runtime.ENOMEM`と一致するかどうかを`if v != runtime.ENOMEM`で検証する点です。このテストがパスすることで、上記のアセンブリレベルでの符号調整が正しく機能し、Goランタイムの内部ロジックが`mmap`からのエラーを正しく処理できることが保証されます。

このテストは、`runtime.Mmap`が`NOSPLIT`関数であるため、`t.Errorf`のようなスタックを拡張する可能性のある関数を直接呼び出す前に、ポインタ`p`を`nil`にリセットするという注意深い処理も行っています。これは、`NOSPLIT`関数の制約を考慮したランタイムテストの典型的なパターンです。

これらの変更とテストにより、Goランタイムは異なるプラットフォーム間でのシステムコールエラー処理の一貫性を向上させ、より堅牢なメモリ管理を実現しています。

# [インデックス 19851] ファイルの概要

このコミットは、Goランタイムのスタックメモリテスト `TestStackMem` における問題を修正するものです。具体的には、Go 1.3で導入された新しいスタックアロケータの挙動により、テストが他のテストと並行して実行された際に、スタックメモリの消費量が負の値になる可能性があったため、その計算をより堅牢にするための型変更を行っています。

## 元コミット内容

Goランタイムのスタックメモリテストを修正します。

このテストは単独で実行される場合は問題ありません。しかし、他のテストと一緒に実行されると、他のテストが実行中にスタックを解放するため、使用されるスタックが実際に負になる可能性があります。

この挙動は、新しいスタックアロケータによるものです。古いアロケータは（最小サイズの）スタックを解放することはありませんでした。

このテストはかなり貧弱であり、正確であるためには単独で実行される必要があります。おそらく削除すべきでしょう。

## 変更の背景

このコミットは、Go 1.3で導入された新しいスタックアロケータの挙動に起因するテストの不安定性を修正するために行われました。

Go 1.2以前では、「セグメントスタック (Segmented Stacks)」というスタック管理方式が採用されていました。これは、Goroutineが小さなスタック（例えば8KB）で開始し、必要に応じて新しいスタックセグメントを割り当てる方式です。しかし、この方式には「ホットスプリット問題」という欠点があり、頻繁なスタックの拡張と縮小がパフォーマンスのオーバーヘッドを引き起こす可能性がありました。

Go 1.3（2014年6月リリース）では、この問題を解決するために「スタックコピー (Stack Copying)」という新しいスタックアロケータが導入されました。この新しい方式では、Goroutineのスタックが不足した場合、ランタイムはより大きな連続したメモリブロックを割り当て、古いスタックの内容を新しい場所にコピーします。この変更の重要な利点の一つは、スタックの使用量が減少した際にスタックを縮小する操作が「フリー」になることです。

しかし、この新しいスタックアロケータは、以前のアロケータとは異なるメモリ解放の挙動を示しました。古いアロケータは、一度割り当てられた最小サイズのスタックを解放することはほとんどありませんでしたが、新しいアロケータは、テスト実行中に他のGoroutineがスタックを解放する可能性がありました。

`TestStackMem` は、特定の処理が消費するスタックメモリ量を測定するテストです。新しいアロケータの挙動により、テストが実行されている間に他のGoroutineがスタックを解放すると、`s1.StackSys - s0.StackSys` の計算結果が期待よりも小さくなったり、場合によっては負の値になったりする可能性が生じました。これは、`StackSys` がシステムから割り当てられたスタックメモリの総量を示すため、解放されたメモリが反映されると、テスト開始時よりも終了時の値が小さくなることがあり得るためです。

この予期せぬ負の値の可能性に対応するため、スタック消費量を計算する変数の型を符号なし整数型 (`uint64`) から符号付き整数型 (`int64`) に変更することで、テストの堅牢性を向上させました。

## 前提知識の解説

### GoのGoroutineとスタック

Go言語の「Goroutine」は、軽量な並行処理の単位です。数千、数万といった多数のGoroutineを同時に実行できることがGoの大きな特徴の一つです。各Goroutineは独自の実行スタックを持っています。このスタックは、関数呼び出しの引数、ローカル変数、リターンアドレスなどを格納するために使用されます。Goroutineのスタックは、必要に応じて動的にサイズが変更されます。

### セグメントスタック (Segmented Stacks)

Go 1.2以前のバージョンで採用されていたスタック管理方式です。
*   **動作原理**: 各Goroutineは、最初は比較的小さなスタック（例: 8KB）で開始します。関数呼び出しなどによってスタックが不足しそうになると、ランタイムは新しいスタックセグメントを割り当て、それを既存のスタックに連結します。これにより、スタックは必要に応じて「セグメント」単位で拡張されます。
*   **利点**: 初期スタックサイズが小さいため、多数のGoroutineを起動してもメモリ消費を抑えられます。
*   **欠点**:
    *   **ホットスプリット問題 (Hot Split Problem)**: 頻繁にスタックの拡張と縮小が繰り返されるようなコードパターン（特にループ内で再帰呼び出しが行われる場合など）では、新しいセグメントの割り当てと解放、そしてセグメント間のポインタ調整といったオーバーヘッドが大きくなり、パフォーマンスが低下する可能性がありました。
    *   スタックが連続したメモリ領域ではないため、一部のデバッグツールやプロファイリングツールとの相性が悪い場合がありました。

### スタックコピー (Stack Copying)

Go 1.3で導入された新しいスタック管理方式です。
*   **動作原理**: 各Goroutineは、セグメントスタックよりもやや大きな初期スタック（Go 1.3では4KB、Go 1.4では2KB）で開始します。スタックが不足しそうになると、ランタイムは現在のスタックの内容を、より大きな（通常は現在の2倍の）連続したメモリブロックにコピーします。
*   **利点**:
    *   **ホットスプリット問題の解消**: スタックが常に連続したメモリ領域に存在するため、セグメント間の連結や解放のオーバーヘッドがなくなります。
    *   **スタックの縮小が「フリー」**: スタックの使用量が減少しても、ランタイムが明示的にメモリを解放する必要がありません。次にスタックが拡張される際に、現在のスタックサイズが十分であれば、新しいコピーは行われません。これにより、スタックの縮小に伴うオーバーヘッドが実質的にゼロになります。
    *   デバッグやプロファイリングが容易になります。
*   **欠点**: スタックコピーの際に、一時的にCPU時間とメモリ帯域が消費されます。しかし、これはセグメントスタックのホットスプリット問題よりも全体的なパフォーマンスへの影響が小さいと判断されました。

### `runtime.MemStats` と `StackSys`

`runtime.MemStats` は、Goランタイムのメモリ使用状況に関する詳細な統計情報を提供する構造体です。この構造体には、ヒープ、スタック、GC（ガベージコレクション）関連のメモリなど、様々なカテゴリのメモリ使用量が含まれています。

`StackSys` は `runtime.MemStats` のフィールドの一つで、システムからスタックのために割り当てられたメモリの総量（バイト単位）を示します。この値は、Goroutineのスタックが成長したり、新しいGoroutineが作成されたりすると増加し、Goroutineが終了したり、スタックが解放されたりすると減少します。

## 技術的詳細

`src/pkg/runtime/stack_test.go` 内の `TestStackMem` 関数は、特定の再帰的な関数呼び出しがGoランタイムのスタックメモリをどれだけ消費するかを測定することを目的としています。

テストの基本的なロジックは以下の通りです。
1.  テスト開始前に `runtime.ReadMemStats` を呼び出し、現在のメモリ統計（`s0`）を取得します。特に `s0.StackSys` を記録します。
2.  スタックを大量に消費する処理（このテストでは再帰的な関数呼び出し）を実行します。
3.  処理完了後に再度 `runtime.ReadMemStats` を呼び出し、新しいメモリ統計（`s1`）を取得します。
4.  `consumed := s1.StackSys - s0.StackSys` という計算で、処理中に消費されたスタックメモリ量を算出します。
5.  算出した `consumed` が、事前に見積もられた `estimate`（期待される消費量）を超えていないかを確認します。

このコミットで修正された問題は、新しいスタックアロケータの導入によって顕在化しました。
*   **問題の発生**: 新しいスタックアロケータは、Goroutineが終了したり、スタックの使用量が減少したりした場合に、システムにスタックメモリを解放する可能性があります。
*   **テストの不安定性**: `TestStackMem` が他のテストと並行して実行されると、`TestStackMem` がスタックを消費している間に、他のGoroutineが終了したり、スタックを解放したりすることが起こり得ます。この場合、`s1.StackSys` の値が `s0.StackSys` よりも小さくなる可能性があり、その結果 `s1.StackSys - s0.StackSys` の計算結果が負の値になることがありました。
*   **`uint64` の問題**: 元々 `consumed` 変数は `uint64`（符号なし64ビット整数）で宣言されていました。符号なし整数型は負の値を表現できません。そのため、計算結果が負になった場合、`uint64` の最大値に近い非常に大きな正の値として解釈されてしまい、`consumed > estimate` の条件が誤って真となり、テストが失敗していました。
*   **古いアロケータとの違い**: コミットメッセージにあるように、古いセグメントスタックアロケータは、一度割り当てられた最小サイズのスタックをシステムに解放することはほとんどありませんでした。そのため、`StackSys` の値がテスト中に減少することは稀であり、この問題は発生しませんでした。

この修正は、テストのロジック自体を変更するのではなく、計算結果が負になる可能性を考慮して、変数の型をより適切なものに変更することで、テストの堅牢性を高めるものです。コミットメッセージが示唆するように、このテスト自体が並行実行環境での正確なスタック消費量測定には不向きであるという根本的な問題は残っていますが、少なくとも計算上のエラーは回避されます。

## コアとなるコードの解説

変更は `src/pkg/runtime/stack_test.go` ファイルの2行にわたります。

1.  **`consumed` 変数の型変更**:
    ```go
    -	consumed := s1.StackSys - s0.StackSys
    +	consumed := int64(s1.StackSys - s0.StackSys)
    ```
    `s1.StackSys` と `s0.StackSys` は `uint64` 型です。これらの差分 `s1.StackSys - s0.StackSys` は、通常は正の値（スタック消費量）を期待しますが、前述の理由により負の値になる可能性がありました。
    元のコードでは、この差分が `uint64` 型の `consumed` に直接代入されていました。Goでは、符号なし整数型に負の値を代入しようとすると、その値はラップアラウンド（オーバーフロー）して非常に大きな正の値として扱われます。例えば、`-1` は `uint64` では `2^64 - 1` となります。
    この変更により、計算結果を明示的に `int64`（符号付き64ビット整数）にキャストしています。これにより、`s1.StackSys - s0.StackSys` が負の値になった場合でも、正しく負の値として `consumed` に格納されるようになります。

2.  **`estimate` 変数の型変更**:
    ```go
    -	estimate := uint64(8 * BatchSize * ArraySize * RecursionDepth) // 8 is to reduce flakiness.
    +	estimate := int64(8 * BatchSize * ArraySize * RecursionDepth) // 8 is to reduce flakiness.
    ```
    `consumed` 変数の型が `int64` に変更されたことに伴い、比較対象となる `estimate` 変数の型も `int64` に変更されています。これは、異なる型の数値同士の比較における潜在的な問題を避けるため、およびコードの一貫性を保つための変更です。`consumed > estimate` の比較が正しく行われるように、両方のオペランドが同じ型であることが望ましいです。

これらの変更により、`TestStackMem` は、新しいスタックアロケータの挙動によって `StackSys` の差分が負になった場合でも、計算が正しく行われ、テストが不正確に失敗することがなくなります。

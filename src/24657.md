# [インデックス 24657] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、空のスライスや文字列に対する`range`ループの処理を修正するものです。具体的には、コンパイラが`range`ループを通常の`for`ループに変換する際に発生する、境界チェックの問題に対処しています。

## コミット

`cmd/compile`: 空の`range`ループを修正するために`Bounded`フィールドを使用

このコミットは、GoコンパイラのSSAバックエンドが、空のスライスや文字列に対する`range`ループを正しく処理できるようにするための変更です。以前のコンパイラは、特定のインデックス操作に対して境界チェックを抑制する`Bounded`というマークを使用していましたが、SSAコンパイラはこのマークを尊重していませんでした。この修正により、SSAコンパイラも`Bounded`マークを認識し、不要な境界チェックをスキップすることで、空の`range`ループがパニックを起こさずに実行されるようになります。

## 元コミット内容

```
[dev.ssa] cmd/compile: used Bounded field to fix empty range loops

    for i, v := range a {
    }

Walk converts this to a regular for loop, like this:

    for i := 0, p := &a[0]; i < len(a); i++, p++ {
        v := *p
    }

Unfortunately, &a[0] fails its bounds check when a is
the empty slice (or string). The old compiler gets around this
by marking &a[0] as Bounded, meaning "don't emit bounds checks
for this index op". This change makes SSA honor that same mark.

The SSA compiler hasn't implemented bounds check panics yet,
so the failed bounds check just causes the current routine
to return immediately.

Fixes bytes package tests.

Change-Id: Ibe838853ef4046c92f76adbded8cca3b1e449e0b
Reviewed-on: https://go-review.googlesource.com/13685
Reviewed-by: Josh Bleecher Snyder <josharian@gmail.com>
```

## 変更の背景

Go言語の`for ... range`ループは、スライス、配列、文字列、マップ、チャネルなどのコレクションをイテレートするための強力な構文です。コンパイラは、この高レベルな構文を、より低レベルな通常の`for`ループに「脱糖（desugar）」します。

問題は、空のスライスや文字列に対して`for i, v := range a {}`のようなループが書かれた場合に発生しました。コンパイラがこれを通常の`for`ループに変換する際、内部的に`p := &a[0]`のような操作を生成することがあります。これは、スライスの最初の要素へのポインタを取得しようとするものです。しかし、`a`が空のスライスである場合、`a[0]`は存在しないため、この操作は実行時パニック（インデックスが範囲外）を引き起こす可能性があります。

従来のGoコンパイラ（SSAバックエンド導入以前）では、このような特定の状況下での`&a[0]`のような操作に対して、コンパイラが「`Bounded`」という内部的なフラグを設定していました。この`Bounded`フラグは、「このインデックス操作は、コンパイラがその安全性を保証できるため、実行時の境界チェックを生成する必要がない」ことを意味します。これにより、空のスライスに対する`range`ループがパニックを起こすことなく機能していました。

しかし、新しいSSAバックエンドが導入された際、この`Bounded`フラグの扱いが適切に実装されていませんでした。結果として、SSAコンパイラは`Bounded`フラグが設定されている場合でも境界チェックを生成しようとし、空のスライスに対する`&a[0]`のような操作で不正な境界チェックエラーを引き起こしていました。当時のSSAコンパイラはまだ境界チェックパニックを完全に実装していなかったため、このエラーはパニックではなく、現在のルーチンが即座にリターンするという形で現れていました。この問題は、`bytes`パッケージのテストが失敗する原因となっていました。

このコミットは、SSAコンパイラが従来のコンパイラと同様に`Bounded`フラグを尊重し、特定の安全なインデックス操作に対して境界チェックを抑制するようにすることで、この問題を解決することを目的としています。

## 前提知識の解説

*   **GoコンパイラのSSAバックエンド**: Goコンパイラは、ソースコードを中間表現に変換し、最終的に機械語にコンパイルします。SSA (Static Single Assignment) 形式は、コンパイラの最適化フェーズで広く使用される中間表現の一種です。各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。Go 1.7からSSAバックエンドが導入され、コンパイル速度の向上と生成コードの最適化が図られました。
*   **`for ... range`ループの脱糖 (Desugaring)**: プログラミング言語において、高レベルな構文（シンタックスシュガー）を、より基本的な構文に変換するプロセスを指します。Goの`range`ループもその一つで、コンパイラによって通常の`for`ループやその他の低レベルな操作に変換されます。例えば、`for i, v := range a`は、内部的にはインデックス`i`と値`v`を計算するためのポインタ操作や配列アクセスに展開されます。
*   **境界チェック (Bounds Check)**: スライスや配列にアクセスする際に、指定されたインデックスが有効な範囲内にあるかを確認する実行時チェックです。例えば、長さが5のスライス`s`に対して`s[5]`にアクセスしようとすると、インデックスが範囲外であるためパニックが発生します。境界チェックはプログラムの安全性を高めますが、オーバーヘッドも伴うため、コンパイラは可能な限り安全な境界チェックを省略する最適化を行います。
*   **`Node.Bounded`フィールド**: Goコンパイラの内部表現において、AST (Abstract Syntax Tree) のノード（`Node`構造体）が持つ可能性のあるフラグの一つです。このフラグは、特定のインデックス操作がコンパイラによって安全であると判断され、実行時の境界チェックを省略できることを示します。これは、コンパイラが静的にインデックスが常に有効な範囲内にあることを証明できる場合に設定されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが、ASTノードの`Bounded`フラグを適切に処理するように変更された点にあります。

Goコンパイラは、ソースコードをASTにパースした後、そのASTをSSA形式に変換して最適化を行います。`for ... range`ループが脱糖される過程で、空のスライスに対する`&a[0]`のような操作が生成されることがあります。この`&a[0]`のような操作を表すASTノードには、従来のコンパイラによって`Bounded`フラグが設定されていました。これは、たとえ`a`が空であっても、この`&a[0]`が続くループの条件（`i < len(a)`）によって決して実行されないか、あるいはその結果が安全に扱われることが保証されているため、実行時の境界チェックは不要である、というコンパイラの判断を示すものです。

しかし、SSAバックエンドの`state.expr`および`state.addr`関数（これらはASTノードをSSA値に変換する役割を担う）では、インデックス操作に対して無条件に`s.boundsCheck(i, len)`を呼び出していました。これは、`Bounded`フラグが設定されているノードに対しても境界チェックを生成しようとすることを意味します。

このコミットでは、`src/cmd/compile/internal/gc/ssa.go`内の`state.expr`および`state.addr`関数において、`s.boundsCheck(i, len)`の呼び出しを`if !n.Bounded { s.boundsCheck(i, len) }`という条件文で囲むように変更されました。

*   `n.Bounded`が`true`の場合（つまり、コンパイラがこの操作は安全であると判断している場合）、`!n.Bounded`は`false`となり、`s.boundsCheck`は呼び出されません。これにより、不要な境界チェックが抑制されます。
*   `n.Bounded`が`false`の場合、`!n.Bounded`は`true`となり、通常通り`s.boundsCheck`が呼び出され、実行時の境界チェックが生成されます。

この変更により、SSAコンパイラは従来のコンパイラと同じセマンティクスで`Bounded`フラグを尊重するようになり、空のスライスに対する`range`ループが正しく動作するようになりました。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/ssa.go`の変更点:

*   `func (s *state) expr(n *Node) *ssa.Value`関数内:
    *   配列のインデックスアクセス（`ssa.OpArrayIndex`）を処理する箇所で、`s.boundsCheck(i, len)`の呼び出しが`if !n.Bounded { ... }`で囲まれました。これは、配列の要素アクセス時に、ノード`n`が`Bounded`フラグを持っている場合は境界チェックをスキップすることを意味します。
*   `func (s *state) addr(n *Node) *ssa.Value`関数内:
    *   スライスのポインタインデックスアクセス（`ssa.OpSlicePtr`と`ssa.OpPtrIndex`）を処理する箇所で、同様に`s.boundsCheck(i, len)`の呼び出しが`if !n.Bounded { ... }`で囲まれました。
    *   配列のポインタインデックスアクセス（`ssa.OpPtrIndex`）を処理する箇所でも、同様に`s.boundsCheck(i, len)`の呼び出しが`if !n.Bounded { ... }`で囲まれました。

これらの変更により、コンパイラが`&a[0]`のような操作をSSA形式に変換する際に、そのASTノードに`Bounded`フラグが設定されていれば、SSAバックエンドは実行時の境界チェックを生成しなくなります。これにより、空のスライスや文字列に対する`range`ループが、従来のコンパイラと同様に正しく動作するようになります。

`src/cmd/compile/internal/gc/testdata/ctl_ssa.go`の変更点:

*   `emptyRange_ssa`関数: 空のバイトスライス`b`に対して`for _, x := range b`というループを実行するシンプルな関数です。この関数は常に`true`を返すべきです。
*   `testEmptyRange`関数: `emptyRange_ssa([]byte{})`を呼び出し、その結果が`true`であることを確認します。もし`false`（つまり、境界チェックエラーで早期リターンした場合）であれば、`failed`フラグを立ててテスト失敗を報告します。
*   `main`関数: `testEmptyRange()`を呼び出すように変更され、この新しいテストケースが実行されるようになりました。

このテストケースは、このコミットが修正しようとしている具体的なシナリオ（空のスライスに対する`range`ループ）をカバーしており、修正が正しく機能していることを検証します。

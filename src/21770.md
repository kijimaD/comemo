# [インデックス 21770] ファイルの概要

このコミットは、Go言語のリンカライブラリである`liblink`内のデッドコード（不要な計算）を削除し、コードベースのクリーンアップと正確性の向上を図るものです。具体的には、`span6`および`span8`関数における`p->back`フィールドの計算と、`zprg`構造体の初期化における`back`および`scale`フィールドの不要な設定が削除されました。

## コミット

`liblink`内の`span6`/`span8`における`p->back`の不要な計算を削除。
元々、このコードが`6l`/`8l`の一部であった頃は、新しい`Prog`は`zprg`から構築され、`back=2`が設定されていました。その後、このコードはリストを走査し、後方分岐には`back=1`、それ以外には`back=0`を設定していました。初期の`back=2`設定は、前方分岐（分岐先の命令がまだ0または1に設定されていないため`back == 2`）を識別するために使用されていました。

このコードが`liblink`に抽出され、`6a`/`6g`/`8a`/`8g`と直接リンクされるようになった際、これらのプログラムは`Prog`構造体を作成しましたが、`back=2`を設定しなかったため、この後方分岐検出が機能しなくなりました。

誰もこの問題に気づきませんでした。なぜなら、次のループで情報が再計算されるためです。次のループの唯一の要件は、リスト内の各`Prog`の`p->back`が0または1であることでした。

`zprg`の`back=2`による初期化は、この2番目のループで問題を引き起こす可能性がありました。これは、`zprg`をコピーして作成される少数の`liblink`内部で生成される命令に影響しますが、最初のループが`back == 0`または`1`であることを保証していたため、実際には問題になりませんでした。

したがって、最初のループでの`p->back`の操作は、`zprg.back = 2`の初期化を削除すれば、削除できます。

これはひどいコードであり、私の責任です。申し訳ありません。

ついでに、`zprg`の初期化から`.scale = 1`も削除します。スケールされたインデックスを設定するものは、それ自体でスケールを設定すべきです。（そして、ほとんどの場合、それらは`liblink`の外部から来ています。）

この変更が適用される前と後で、生成されるすべてのコードがビット単位で同一であることを確認することでテストされました。

## 元コミット内容

```
liblink: remove dead computation of p->back in span6/span8

Originally, when this code was part of 6l/8l, every new
Prog was constructed starting with zprg, which set back=2,
and then this code walked over the list setting back=1 for
backward branches, back=0 otherwise. The initial back=2
setting was used to identify forward branches (the branched-to
instruction had back == 2 since it hadn't yet been set to 0 or 1).

When the code was extracted into liblink and linked directly
with 6a/6g/8a/8g, those programs created the Prog struct
and did not set back=2, breaking this backward branch detection.

No one noticed, because the next loop recomputes the information.
The only requirement for the next loop is that p->back == 0 or 1 for
each of the Progs in the list.

The initialization of the zprg with back=2 would cause problems
in this second loop, for the few liblink-internally-generated instructions
that are created by copying zprg, except that the first loop was
making sure that back == 0 or 1.

The first loop's manipulation of p->back can thus be deleted,
provided we also delete the zprg.back = 2 initializations.

This is awful and my fault. I apologize.

While we're here, remove the .scale = 1 from the zprg init too.
Anything that sets up a scaled index should set the scale itself.
(And mostly those come from outside liblink anyway.)

Tested by checking that all generated code is bit-for-bit
identical to before this CL.
```

## 変更の背景

この変更の背景には、Go言語のコンパイラとリンカの進化に伴うコードの陳腐化と、それによって生じた不要な計算の存在があります。

元々、Goのコンパイラ（`6g`, `8g`など）とリンカ（`6l`, `8l`など）は、それぞれ独立したツールとして機能していました。このコミットで言及されている`span6`/`span8`関数内のコードは、かつてリンカの一部として存在していました。この時期、新しい命令（`Prog`構造体）が作成される際には、`zprg`というゼロ値の`Prog`構造体をテンプレートとして使用し、その際に`p->back`フィールドに`2`という特殊な値が設定されていました。この`back=2`は、まだ処理されていない前方分岐を識別するためのマーカーとして機能していました。その後、コードは命令リストを走査し、後方分岐には`back=1`、それ以外（前方分岐を含む）には`back=0`を設定していました。

しかし、Goのツールチェインが進化し、コンパイラとリンカの機能が`liblink`という共通のライブラリに統合されるようになりました。この移行に伴い、`6a`/`6g`/`8a`/`8g`といったアセンブラやコンパイラが直接`liblink`を利用して`Prog`構造体を作成するようになりました。この新しいワークフローでは、`zprg`をテンプレートとして使用する際に`back=2`を設定する初期化処理が行われなくなりました。

結果として、`span6`/`span8`内の`p->back`を`2`かどうかで判定するロジックは、常に`false`となるか、あるいは意図しない動作をするようになりました。しかし、この問題はすぐに顕在化しませんでした。なぜなら、その後のリンカの処理で`p->back`の情報が再計算され、最終的に正しい値（0または1）に上書きされていたためです。つまり、最初の`p->back`の計算は、その後の処理によって無効化される「デッドコード」となっていたのです。

コミットメッセージでRuss Cox氏が「This is awful and my fault. I apologize.」と述べているように、これはコードの移行期に発生した見落としであり、不要な計算が長らく残存していたことを示しています。このコミットは、このようなデッドコードを削除し、コードベースをよりクリーンで理解しやすいものにすることを目的としています。

また、`zprg`の初期化から`.scale = 1`を削除する変更も同時に行われています。これは、スケールされたインデックス（例えば、`MOVQ AX, 8(BX*4)`のような命令における`*4`の部分）を設定する際には、その命令自体が適切なスケール値を設定すべきであり、`zprg`のような汎用的なゼロ値テンプレートがデフォルトで`scale=1`を持つ必要がないという設計思想に基づいています。これもまた、コードの正確性と意図の明確化を目的としたクリーンアップの一環です。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイラとリンカの内部構造、特にアセンブリコードの表現方法に関するいくつかの概念を理解する必要があります。

1.  **Goツールチェインの歴史と構成要素**:
    *   **`6l`/`8l` (旧リンカ)**: Goの初期のリンカは、ターゲットアーキテクチャ（例: `6`はamd64、`8`はarm）ごとに独立した実行ファイルとして存在していました。これらはアセンブリコードをオブジェクトファイルに変換し、最終的な実行可能ファイルを生成する役割を担っていました。
    *   **`6a`/`6g`/`8a`/`8g` (旧アセンブラ/コンパイラ)**: 同様に、アセンブラ（`6a`, `8a`）とコンパイラ（`6g`, `8g`）もアーキテクチャ固有の独立したツールでした。コンパイラはGoのソースコードをアセンブリコードに変換し、アセンブラはそれをオブジェクトファイルに変換しました。
    *   **`liblink`**: Goのツールチェインが進化するにつれて、コンパイラとリンカの共通部分を再利用しやすくするために、`liblink`というライブラリが導入されました。これにより、コンパイラやアセンブラが直接リンカの機能を利用できるようになり、ツールチェイン全体の統合と効率化が図られました。このコミットは、この`liblink`への移行期に生じた問題に対処しています。

2.  **`Prog`構造体**:
    *   Goのコンパイラとリンカの内部では、アセンブリ命令は`Prog`というC言語の構造体で表現されます。各`Prog`インスタンスは、単一のアセンブリ命令（例: `MOVQ`, `ADDL`, `JMP`など）とそのオペランド、および関連するメタデータを含みます。
    *   **`p->back`フィールド**: `Prog`構造体内のフィールドの一つで、命令の「後方」への参照を管理するために使用されていました。特に、分岐命令（ジャンプなど）のターゲットが、現在の命令よりも前に定義されているかどうかを追跡するために使われていました。
        *   `back = 0`: 通常の命令、または前方分岐。
        *   `back = 1`: 後方分岐（ターゲットが現在の命令より前にある）。
        *   `back = 2` (旧来): `zprg`によって初期化された際のデフォルト値。まだ分岐の方向が確定していない、または前方分岐である可能性のある命令のマーカーとして使われていました。

3.  **`zprg`**:
    *   `zprg`は「zero `Prog`」の略で、Goのリンカ内部で新しい`Prog`構造体を初期化するためのテンプレートとして使用される静的な`Prog`構造体のインスタンスです。新しい命令を作成する際に、`zprg`をコピーして基本となるゼロ値のフィールドを設定し、その後で個別の命令に応じたフィールドを上書きします。
    *   このコミット以前は、`zprg`の`back`フィールドは`2`に初期化されていました。

4.  **`span6`/`span8`関数**:
    *   これらは`liblink`内の重要な関数で、アセンブリ命令のリストを走査し、命令のサイズを計算したり、分岐命令のターゲットアドレスを解決したりする役割を担っています。`span`という名前は、命令の「スパン」（範囲）を決定することに由来します。
    *   これらの関数内で、`p->back`フィールドの値を基に分岐のタイプ（前方か後方か）を判断し、それに応じて命令の処理を行うロジックが存在していました。

5.  **分岐命令と`p->pcond`**:
    *   アセンブリにおける分岐命令（例: `JMP`, `JE`, `JNE`など）は、プログラムの実行フローを変更します。
    *   `Prog`構造体には`pcond`というフィールドがあり、これは条件分岐命令の場合に、その条件が満たされた場合にジャンプする先の`Prog`へのポインタを保持します。`p->to.type == TYPE_BRANCH`は、その命令が分岐命令であることを示します。

6.  **`scale`フィールド**:
    *   アセンブリ命令の中には、メモリのアドレス指定モードで「スケールされたインデックス」を使用するものがあります。例えば、`MOVQ (AX)(BX*4), CX`のような命令では、`BX`レジスタの値が`4`倍されてアドレス計算に使用されます。この`4`がスケール値です。
    *   `Prog`構造体内の`from`や`to`フィールド（オペランドを表す）には、このスケール値を保持するための`.scale`サブフィールドが存在します。

これらの概念を理解することで、コミットがなぜ行われたのか、そしてそれがGoのコンパイラ/リンカの内部でどのような影響を持つのかを深く把握できます。

## 技術的詳細

このコミットは、Go言語のリンカライブラリ`liblink`における、冗長で誤解を招く可能性のあるコードの削除に焦点を当てています。主な変更点は、`Prog`構造体の`back`フィールドの扱いと、`zprg`初期化における`scale`フィールドの削除です。

### `p->back`フィールドのデッドコード削除

**問題の根源**:
Goのリンカは、アセンブリ命令を表現する`Prog`構造体のリストを処理します。かつて、この`Prog`構造体には`back`というフィールドがあり、分岐命令の方向（前方か後方か）を追跡するために使用されていました。

1.  **旧来のリンカ（`6l`/`8l`時代）**:
    *   新しい`Prog`が作成される際、`zprg`（ゼロ値の`Prog`テンプレート）をコピーして初期化され、この`zprg`の`back`フィールドは`2`に設定されていました。
    *   `span6`/`span8`関数内の最初のループでは、命令リストを走査し、`p->back`の値を更新していました。
        *   後方分岐（ターゲットが現在の命令より前にある）の場合、`p->back`は`1`に設定。
        *   それ以外（前方分岐または非分岐命令）の場合、`p->back`は`0`に設定。
    *   この`back=2`という初期値は、まだ処理されていない前方分岐を識別するためのマーカーとして機能していました。つまり、`back=2`の`Prog`は「まだ分岐方向が確定していない」状態を示していました。

2.  **`liblink`への移行後**:
    *   Goのツールチェインが`liblink`に統合され、コンパイラ（`6g`/`8g`）やアセンブラ（`6a`/`8a`）が直接`liblink`を利用して`Prog`構造体を作成するようになりました。
    *   この新しいワークフローでは、`Prog`構造体が作成される際に`zprg`の`back=2`という初期化が行われなくなりました。通常、C言語の静的変数やグローバル変数はゼロ初期化されるため、`Prog`構造体の`back`フィールドはデフォルトで`0`になっていました。
    *   これにより、`span6`/`span8`内の`if((q = p->pcond) != nil) if(q->back != 2)`という条件は、常に`true`になるか、あるいは`q->back`が`0`または`1`であるため、`back=2`を期待するロジックが機能しなくなりました。

**なぜ問題が顕在化しなかったのか**:
コミットメッセージが説明しているように、この問題は「誰も気づかなかった」状態でした。その理由は、`span6`/`span8`の後の処理で、`p->back`の情報が再度計算され、正しい値（`0`または`1`）に上書きされていたためです。つまり、最初のループでの`p->back`の計算は、その後の処理にとって不要な「デッドコード」となっていたのです。

**削除の理由**:
*   **冗長性の排除**: 最初のループでの`p->back`の計算は、その後のループで再計算されるため、完全に冗長でした。
*   **正確性の向上**: `back=2`という特殊な初期値がもはや設定されないにもかかわらず、その値を期待するロジックが残っているのは、コードの意図を不明瞭にし、将来的なバグの温床となる可能性がありました。
*   **コードの簡素化**: 不要なコードを削除することで、`span6`/`span8`関数の可読性と保守性が向上します。

この変更は、`span6`/`span8`関数から`p->back`を操作するループを削除するとともに、`zprg`の定義から`.back = 2`の初期化を削除することで実現されました。これにより、コードはより正確に現在のリンカの動作を反映するようになります。

### `zprg.scale = 1`の削除

**問題の根源**:
`Prog`構造体のオペランド（`from`や`to`）には、メモリのアドレス指定モードで使われるスケール値を格納するための`scale`フィールドがあります。例えば、`MOVQ (AX)(BX*4), CX`のような命令では、インデックスレジスタ`BX`が`4`倍されるため、スケール値は`4`になります。

かつて、`zprg`の`from`と`to`オペランドの`scale`フィールドはデフォルトで`1`に初期化されていました。

**削除の理由**:
*   **意図の明確化**: スケール値は、特定の命令がスケールされたインデックスを使用する場合にのみ意味を持ちます。汎用的なゼロ値テンプレートである`zprg`がデフォルトで`scale=1`を持つことは、その意図を不明瞭にします。スケールが必要な命令は、その命令を構築する際に明示的に正しいスケール値を設定すべきです。
*   **冗長性の排除**: ほとんどの場合、スケール値は`liblink`の外部（コンパイラやアセンブラ）から設定されるため、`zprg`でのデフォルト設定は不要でした。
*   **コードのクリーンアップ**: 不要な初期化を削除することで、コードベースがより簡潔になります。

この変更は、`src/liblink/obj6.c`と`src/liblink/obj8.c`内の`zprg`定義から`.scale = 1`の初期化を削除することで実現されました。

### テストと検証

コミットメッセージにあるように、この変更は「生成されるすべてのコードがビット単位で同一であることを確認する」ことでテストされました。これは、リンカの出力が変更前と全く同じであることを保証する厳格なテスト方法であり、この変更が機能的な影響を一切与えないことを強く裏付けています。つまり、削除されたコードは本当に「デッドコード」であり、その存在が最終的なバイナリに影響を与えていなかったことを示しています。

## コアとなるコードの解説

このコミットでは、主に以下の2種類の変更が行われています。

1.  **`span6.c`と`span8.c`からの`p->back`関連コードの削除**:
    *   削除された行:
        ```c
        -	n = 0;
        // ...
        -	if((q = p->pcond) != nil)
        -		if(q->back != 2)
        -			n = 1;
        -	p->back = n;
        ```
    *   **解説**:
        *   これらの行は、`Prog`構造体の`p->back`フィールドを計算し、設定するためのものでした。
        *   `n = 0;` は、`back`のデフォルト値を`0`に設定していました。
        *   `if((q = p->pcond) != nil) if(q->back != 2) n = 1;` の部分は、分岐命令（`p->to.type == TYPE_BRANCH`）の場合に、その分岐先の`Prog`（`q`）の`back`フィールドが`2`でない場合に`n`を`1`に設定していました。これは、`back=2`が前方分岐のマーカーとして使われていた旧来のロジックの名残です。`q->back != 2`が真となるのは、`q`が既に処理されて`0`または`1`になっている場合、つまり後方分岐である可能性が高い場合でした。
        *   `p->back = n;` は、計算された`n`の値を現在の`Prog`の`back`フィールドに設定していました。
    *   **削除の理由**: 前提知識と技術的詳細で述べたように、`liblink`への移行後、`zprg`の`back=2`初期化が行われなくなったため、このロジックは機能しなくなっていました。また、この`p->back`の情報は、その後のリンカの処理で再計算されるため、この最初の計算は完全に冗長なデッドコードとなっていました。この削除により、コードが簡素化され、現在のリンカの動作と一致するようになりました。

2.  **`obj6.c`と`obj8.c`からの`zprg`初期化における`.back = 2`と`.scale = 1`の削除**:
    *   削除された行（`obj6.c`と`obj8.c`の両方で類似の変更）:
        ```c
        // obj6.c, obj8.c
        -	.back = 2,
        // obj8.c のみ
        -	.scale = 1,
        // ...
        -	.scale = 1,
        ```
    *   **解説**:
        *   `static Prog zprg = { ... };` は、新しい`Prog`構造体を初期化するためのテンプレートとして使用される`zprg`の定義です。
        *   `.back = 2,` は、`zprg`の`back`フィールドをデフォルトで`2`に初期化していました。これは、旧来のリンカで前方分岐のマーカーとして使用されていた特殊な値です。
        *   `.scale = 1,` は、`zprg`の`from`および`to`オペランドの`scale`フィールドをデフォルトで`1`に初期化していました。
    *   **削除の理由**:
        *   `.back = 2`の削除は、`span6`/`span8`からの`p->back`計算の削除と連動しています。`back=2`という初期値がもはや意味を持たなくなったため、この初期化は不要になりました。
        *   `.scale = 1`の削除は、スケール値は命令自体が明示的に設定すべきであり、汎用的な`zprg`がデフォルトで持つべきではないという設計思想に基づいています。これにより、コードの意図がより明確になります。

これらの変更は、Goのリンカのコードベースから不要な複雑さと冗長性を排除し、よりクリーンで正確な状態に保つための重要なクリーンアップです。

## コミット

`liblink`内の`span6`/`span8`における`p->back`の不要な計算を削除。
元々、このコードが`6l`/`8l`の一部であった頃は、新しい`Prog`は`zprg`から構築され、`back=2`が設定されていました。その後、このコードはリストを走査し、後方分岐には`back=1`、それ以外には`back=0`を設定していました。初期の`back=2`設定は、前方分岐（分岐先の命令がまだ0または1に設定されていないため`back == 2`）を識別するために使用されていました。

このコードが`liblink`に抽出され、`6a`/`6g`/`8a`/`8g`と直接リンクされるようになった際、これらのプログラムは`Prog`構造体を作成しましたが、`back=2`を設定しなかったため、この後方分岐検出が機能しなくなりました。

誰もこの問題に気づきませんでした。なぜなら、次のループで情報が再計算されるためです。次のループの唯一の要件は、リスト内の各`Prog`の`p->back`が0または1であることでした。

`zprg`の`back=2`による初期化は、この2番目のループで問題を引き起こす可能性がありました。これは、`zprg`をコピーして作成される少数の`liblink`内部で生成される命令に影響しますが、最初のループが`back == 0`または`1`であることを保証していたため、実際には問題になりませんでした。

したがって、最初のループでの`p->back`の操作は、`zprg.back = 2`の初期化を削除すれば、削除できます。

これはひどいコードであり、私の責任です。申し訳ありません。

ついでに、`zprg`の初期化から`.scale = 1`も削除します。スケールされたインデックスを設定するものは、それ自体でスケールを設定すべきです。（そして、ほとんどの場合、それらは`liblink`の外部から来ています。）

この変更が適用される前と後で、生成されるすべてのコードがビット単位で同一であることを確認することでテストされました。

## 変更の背景

この変更の背景には、Go言語のコンパイラとリンカの進化に伴うコードの陳腐化と、それによって生じた不要な計算の存在があります。

元々、Goのコンパイラ（`6g`, `8g`など）とリンカ（`6l`, `8l`など）は、それぞれ独立したツールとして機能していました。このコミットで言及されている`span6`/`span8`関数内のコードは、かつてリンカの一部として存在していました。この時期、新しい命令（`Prog`構造体）が作成される際には、`zprg`というゼロ値の`Prog`構造体をテンプレートとして使用し、その際に`p->back`フィールドに`2`という特殊な値が設定されていました。この`back=2`は、まだ処理されていない前方分岐を識別するためのマーカーとして機能していました。その後、コードは命令リストを走査し、後方分岐には`back=1`、それ以外（前方分岐を含む）には`back=0`を設定していました。

しかし、Goのツールチェインが進化し、コンパイラとリンカの機能が`liblink`という共通のライブラリに統合されるようになりました。この移行に伴い、`6a`/`6g`/`8a`/`8g`といったアセンブラやコンパイラが直接`liblink`を利用して`Prog`構造体を作成するようになりました。この新しいワークフローでは、`zprg`をテンプレートとして使用する際に`back=2`を設定する初期化処理が行われなくなりました。

結果として、`span6`/`span8`内の`p->back`を`2`かどうかで判定するロジックは、常に`false`となるか、あるいは意図しない動作をするようになりました。しかし、この問題はすぐに顕在化しませんでした。なぜなら、その後のリンカの処理で`p->back`の情報が再計算され、最終的に正しい値（0または1）に上書きされていたためです。つまり、最初の`p->back`の計算は、その後の処理によって無効化される「デッドコード」となっていたのです。

コミットメッセージでRuss Cox氏が「This is awful and my fault. I apologize.」と述べているように、これはコードの移行期に発生した見落としであり、不要な計算が長らく残存していたことを示しています。このコミットは、このようなデッドコードを削除し、コードベースをよりクリーンで理解しやすいものにすることを目的としています。

また、`zprg`の初期化から`.scale = 1`を削除する変更も同時に行われています。これは、スケールされたインデックス（例えば、`MOVQ AX, 8(BX*4)`のような命令における`*4`の部分）を設定する際には、その命令自体が適切なスケール値を設定すべきであり、`zprg`のような汎用的なゼロ値テンプレートがデフォルトで`scale=1`を持つ必要がないという設計思想に基づいています。これもまた、コードの正確性と意図の明確化を目的としたクリーンアップの一環です。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイラとリンカの内部構造、特にアセンブリコードの表現方法に関するいくつかの概念を理解する必要があります。

1.  **Goツールチェインの歴史と構成要素**:
    *   **`6l`/`8l` (旧リンカ)**: Goの初期のリンカは、ターゲットアーキテクチャ（例: `6`はamd64、`8`はarm）ごとに独立した実行ファイルとして存在していました。これらはアセンブリコードをオブジェクトファイルに変換し、最終的な実行可能ファイルを生成する役割を担っていました。
    *   **`6a`/`6g`/`8a`/`8g` (旧アセンブラ/コンパイラ)**: 同様に、アセンブラ（`6a`, `8a`）とコンパイラ（`6g`, `8g`）もアーキテクチャ固有の独立したツールでした。コンパイラはGoのソースコードをアセンブリコードに変換し、アセンブラはそれをオブジェクトファイルに変換しました。
    *   **`liblink`**: Goのツールチェインが進化するにつれて、コンパイラとリンカの共通部分を再利用しやすくするために、`liblink`というライブラリが導入されました。これにより、コンパイラやアセンブラが直接リンカの機能を利用できるようになり、ツールチェイン全体の統合と効率化が図られました。このコミットは、この`liblink`への移行期に生じた問題に対処しています。

2.  **`Prog`構造体**:
    *   Goのコンパイラとリンカの内部では、アセンブリ命令は`Prog`というC言語の構造体で表現されます。各`Prog`インスタンスは、単一のアセンブリ命令（例: `MOVQ`, `ADDL`, `JMP`など）とそのオペランド、および関連するメタデータを含みます。
    *   **`p->back`フィールド**: `Prog`構造体内のフィールドの一つで、命令の「後方」への参照を管理するために使用されていました。特に、分岐命令（ジャンプなど）のターゲットが、現在の命令よりも前に定義されているかどうかを追跡するために使われていました。
        *   `back = 0`: 通常の命令、または前方分岐。
        *   `back = 1`: 後方分岐（ターゲットが現在の命令より前にある）。
        *   `back = 2` (旧来): `zprg`によって初期化された際のデフォルト値。まだ分岐の方向が確定していない、または前方分岐である可能性のある命令のマーカーとして使われていました。

3.  **`zprg`**:
    *   `zprg`は「zero `Prog`」の略で、Goのリンカ内部で新しい`Prog`構造体を初期化するためのテンプレートとして使用される静的な`Prog`構造体のインスタンスです。新しい命令を作成する際に、`zprg`をコピーして基本となるゼロ値のフィールドを設定し、その後で個別の命令に応じたフィールドを上書きします。
    *   このコミット以前は、`zprg`の`back`フィールドは`2`に初期化されていました。

4.  **`span6`/`span8`関数**:
    *   これらは`liblink`内の重要な関数で、アセンブリ命令のリストを走査し、命令のサイズを計算したり、分岐命令のターゲットアドレスを解決したりする役割を担っています。`span`という名前は、命令の「スパン」（範囲）を決定することに由来します。
    *   これらの関数内で、`p->back`フィールドの値を基に分岐のタイプ（前方か後方か）を判断し、それに応じて命令の処理を行うロジックが存在していました。

5.  **分岐命令と`p->pcond`**:
    *   アセンブリにおける分岐命令（例: `JMP`, `JE`, `JNE`など）は、プログラムの実行フローを変更します。
    *   `Prog`構造体には`pcond`というフィールドがあり、これは条件分岐命令の場合に、その条件が満たされた場合にジャンプする先の`Prog`へのポインタを保持します。`p->to.type == TYPE_BRANCH`は、その命令が分岐命令であることを示します。

6.  **`scale`フィールド**:
    *   アセンブリ命令の中には、メモリのアドレス指定モードで「スケールされたインデックス」を使用するものがあります。例えば、`MOVQ (AX)(BX*4), CX`のような命令では、`BX`レジスタの値が`4`倍されてアドレス計算に使用されます。この`4`がスケール値です。
    *   `Prog`構造体内の`from`や`to`フィールド（オペランドを表す）には、このスケール値を保持するための`.scale`サブフィールドが存在します。

これらの概念を理解することで、コミットがなぜ行われたのか、そしてそれがGoのコンパイラ/リンカの内部でどのような影響を持つのかを深く把握できます。

## 技術的詳細

このコミットは、Go言語のリンカライブラリ`liblink`における、冗長で誤解を招く可能性のあるコードの削除に焦点を当てています。主な変更点は、`Prog`構造体の`back`フィールドの扱いと、`zprg`初期化における`scale`フィールドの削除です。

### `p->back`フィールドのデッドコード削除

**問題の根源**:
Goのリンカは、アセンブリ命令を表現する`Prog`構造体のリストを処理します。かつて、この`Prog`構造体には`back`というフィールドがあり、分岐命令の方向（前方か後方か）を追跡するために使用されていました。

1.  **旧来のリンカ（`6l`/`8l`時代）**:
    *   新しい`Prog`が作成される際、`zprg`（ゼロ値の`Prog`テンプレート）をコピーして初期化され、この`zprg`の`back`フィールドは`2`に設定されていました。
    *   `span6`/`span8`関数内の最初のループでは、命令リストを走査し、`p->back`の値を更新していました。
        *   後方分岐（ターゲットが現在の命令より前にある）の場合、`p->back`は`1`に設定。
        *   それ以外（前方分岐または非分岐命令）の場合、`p->back`は`0`に設定。
    *   この`back=2`という初期値は、まだ処理されていない前方分岐を識別するためのマーカーとして機能していました。つまり、`back=2`の`Prog`は「まだ分岐方向が確定していない」状態を示していました。

2.  **`liblink`への移行後**:
    *   Goのツールチェインが`liblink`に統合され、コンパイラ（`6g`/`8g`）やアセンブラ（`6a`/`8a`）が直接`liblink`を利用して`Prog`構造体を作成するようになりました。
    *   この新しいワークフローでは、`Prog`構造体が作成される際に`zprg`の`back=2`という初期化が行われなくなりました。通常、C言語の静的変数やグローバル変数はゼロ初期化されるため、`Prog`構造体の`back`フィールドはデフォルトで`0`になっていました。
    *   これにより、`span6`/`span8`内の`if((q = p->pcond) != nil) if(q->back != 2)`という条件は、常に`true`になるか、あるいは`q->back`が`0`または`1`であるため、`back=2`を期待するロジックが機能しなくなりました。

**なぜ問題が顕在化しなかったのか**:
コミットメッセージが説明しているように、この問題は「誰も気づかなかった」状態でした。その理由は、`span6`/`span8`の後の処理で、`p->back`の情報が再度計算され、正しい値（`0`または`1`）に上書きされていたためです。つまり、最初のループでの`p->back`の計算は、その後の処理にとって不要な「デッドコード」となっていたのです。

**削除の理由**:
*   **冗長性の排除**: 最初のループでの`p->back`の計算は、その後のループで再計算されるため、完全に冗長でした。
*   **正確性の向上**: `back=2`という特殊な初期値がもはや設定されないにもかかわらず、その値を期待するロジックが残っているのは、コードの意図を不明瞭にし、将来的なバグの温床となる可能性がありました。
*   **コードの簡素化**: 不要なコードを削除することで、`span6`/`span8`関数の可読性と保守性が向上します。

この変更は、`span6`/`span8`関数から`p->back`を操作するループを削除するとともに、`zprg`の定義から`.back = 2`の初期化を削除することで実現されました。これにより、コードはより正確に現在のリンカの動作を反映するようになります。

### `zprg.scale = 1`の削除

**問題の根源**:
`Prog`構造体のオペランド（`from`や`to`）には、メモリのアドレス指定モードで使われるスケール値を格納するための`scale`フィールドがあります。例えば、`MOVQ (AX)(BX*4), CX`のような命令では、インデックスレジスタ`BX`が`4`倍されるため、スケール値は`4`になります。

かつて、`zprg`の`from`と`to`オペランドの`scale`フィールドはデフォルトで`1`に初期化されていました。

**削除の理由**:
*   **意図の明確化**: スケール値は、特定の命令がスケールされたインデックスを使用する場合にのみ意味を持ちます。汎用的なゼロ値テンプレートである`zprg`がデフォルトで`scale=1`を持つことは、その意図を不明瞭にします。スケールが必要な命令は、その命令を構築する際に明示的に正しいスケール値を設定すべきです。
*   **冗長性の排除**: ほとんどの場合、スケール値は`liblink`の外部（コンパイラやアセンブラ）から設定されるため、`zprg`でのデフォルト設定は不要でした。
*   **コードのクリーンアップ**: 不要な初期化を削除することで、コードベースがより簡潔になります。

この変更は、`src/liblink/obj6.c`と`src/liblink/obj8.c`内の`zprg`定義から`.scale = 1`の初期化を削除することで実現されました。

### テストと検証

コミットメッセージにあるように、この変更は「生成されるすべてのコードがビット単位で同一であることを確認する」ことでテストされました。これは、リンカの出力が変更前と全く同じであることを保証する厳格なテスト方法であり、この変更が機能的な影響を一切与えないことを強く裏付けています。つまり、削除されたコードは本当に「デッドコード」であり、その存在が最終的なバイナリに影響を与えていなかったことを示しています。

## コアとなるコードの解説

このコミットでは、主に以下の2種類の変更が行われています。

1.  **`span6.c`と`span8.c`からの`p->back`関連コードの削除**:
    *   削除された行:
        ```c
        -	n = 0;
        // ...
        -	if((q = p->pcond) != nil)
        -		if(q->back != 2)
        -			n = 1;
        -	p->back = n;
        ```
    *   **解説**:
        *   これらの行は、`Prog`構造体の`p->back`フィールドを計算し、設定するためのものでした。
        *   `n = 0;` は、`back`のデフォルト値を`0`に設定していました。
        *   `if((q = p->pcond) != nil) if(q->back != 2) n = 1;` の部分は、分岐命令（`p->to.type == TYPE_BRANCH`）の場合に、その分岐先の`Prog`（`q`）の`back`フィールドが`2`でない場合に`n`を`1`に設定していました。これは、`back=2`が前方分岐のマーカーとして使われていた旧来のロジックの名残です。`q->back != 2`が真となるのは、`q`が既に処理されて`0`または`1`になっている場合、つまり後方分岐である可能性が高い場合でした。
        *   `p->back = n;` は、計算された`n`の値を現在の`Prog`の`back`フィールドに設定していました。
    *   **削除の理由**: 前提知識と技術的詳細で述べたように、`liblink`への移行後、`zprg`の`back=2`初期化が行われなくなったため、このロジックは機能しなくなっていました。また、この`p->back`の情報は、その後のリンカの処理で再計算されるため、この最初の計算は完全に冗長なデッドコードとなっていました。この削除により、コードが簡素化され、現在のリンカの動作と一致するようになりました。

2.  **`obj6.c`と`obj8.c`からの`zprg`初期化における`.back = 2`と`.scale = 1`の削除**:
    *   削除された行（`obj6.c`と`obj8.c`の両方で類似の変更）:
        ```c
        // obj6.c, obj8.c
        -	.back = 2,
        // obj8.c のみ
        -	.scale = 1,
        // ...
        -	.scale = 1,
        ```
    *   **解説**:
        *   `static Prog zprg = { ... };` は、新しい`Prog`構造体を初期化するためのテンプレートとして使用される`zprg`の定義です。
        *   `.back = 2,` は、`zprg`の`back`フィールドをデフォルトで`2`に初期化していました。これは、旧来のリンカで前方分岐のマーカーとして使用されていた特殊な値です。
        *   `.scale = 1,` は、`zprg`の`from`および`to`オペランドの`scale`フィールドをデフォルトで`1`に初期化していました。
    *   **削除の理由**:
        *   `.back = 2`の削除は、`span6`/`span8`からの`p->back`計算の削除と連動しています。`back=2`という初期値がもはや意味を持たなくなったため、この初期化は不要になりました。
        *   `.scale = 1`の削除は、スケール値は命令自体が明示的に設定すべきであり、汎用的な`zprg`がデフォルトで持つべきではないという設計思想に基づいています。これにより、コードの意図がより明確になります。

これらの変更は、Goのリンカのコードベースから不要な複雑さと冗長性を排除し、よりクリーンで正確な状態に保つための重要なクリーンアップです。

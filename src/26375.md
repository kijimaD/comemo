# [インデックス 26375] ファイルの概要

このコミットは、Go言語のビルドシステムと`go/build`パッケージにおけるベンダーディレクトリの処理方法に関する重要な改善を導入しています。具体的には、Goソースファイルを含まないベンダーディレクトリを無視するようになり、これにより、特定のシナリオで発生していたパッケージの解決に関する問題が解決されました。

## 変更の背景

Go 1.5で導入されたベンダーエクスペリメント（`GO15VENDOREXPERIMENT=1`）は、プロジェクトが依存関係を自身の`vendor`ディレクトリ内に配置できるようにする機能でした。これにより、依存関係のバージョン管理が容易になり、ビルドの再現性が向上することが期待されました。

しかし、このベンダーメカニズムには初期の課題がありました。特に、`vendor`ディレクトリ内にGoソースファイルを含まないディレクトリが存在する場合に問題が発生しました。コミットメッセージにある「Otherwise it is impossible to vendor a/b/c without hiding the real a/b.」という記述がこの問題の本質を捉えています。

具体的には、`a/b/c`というパッケージをベンダー化したいが、`a/b`自体はベンダー化せず、GOPATHから解決したいというシナリオを考えます。もし`vendor/a/b`というディレクトリが存在し、それがGoソースファイルを含まない空のディレクトリであったとしても、Goのビルドツールは`vendor/a/b`を有効なベンダーパスとして認識し、その結果、GOPATHにある本来の`a/b`パッケージを「隠してしまう」可能性がありました。これにより、意図しないパッケージがインポートされたり、パッケージが見つからなくなったりする問題が発生していました。

このコミットは、この問題を解決するために、Goソースファイルを含まないベンダーディレクトリは無視するというルールを導入しました。これにより、ベンダーメカニズムがより堅牢になり、開発者が期待する通りのパッケージ解決が行われるようになりました。この変更は、GoのIssue 13832で報告された問題を修正するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とビルドプロセスの知識が必要です。

1.  **GOPATH**: Go 1.11モジュールが導入される前のGoプロジェクトのワークスペースを定義する環境変数です。ソースコード、コンパイル済みパッケージ、実行可能ファイルが配置される場所を決定します。Goツールは、GOPATH内の`src`ディレクトリからパッケージを検索します。
2.  **ベンダーエクスペリメント (Vendor Experiment)**: Go 1.5で導入された機能で、プロジェクトのルートディレクトリ直下またはサブディレクトリに`vendor`という名前のディレクトリを作成し、その中にプロジェクト固有の依存関係のコピーを配置できるようにするメカニズムです。これにより、GOPATHに依存せずにプロジェクトの依存関係を管理できるようになります。Goツールは、GOPATHよりも先に`vendor`ディレクトリ内のパッケージを検索します。この機能は`GO15VENDOREXPERIMENT=1`環境変数を設定することで有効化されました。
3.  **パッケージ解決の優先順位**: Goツールがパッケージをインポートする際、以下の優先順位でパッケージを検索します。
    *   標準ライブラリ（GOROOT）
    *   現在のモジュール（Go Modulesが有効な場合）
    *   `vendor`ディレクトリ内
    *   GOPATH内
    このコミットは、特に`vendor`ディレクトリとGOPATHの間の解決ロジックに影響を与えます。
4.  **`go/build`パッケージ**: Goのソースコードを解析し、パッケージの依存関係を解決するための低レベルな機能を提供する標準ライブラリパッケージです。`cmd/go`コマンドはこのパッケージを利用してビルドプロセスを実行します。
5.  **`cmd/go`コマンド**: Go言語のビルド、テスト、インストール、フォーマットなど、様々な開発タスクを実行するための主要なコマンドラインツールです。

## 技術的詳細

このコミットの核心は、Goのビルドプロセスがベンダーディレクトリを「有効」と判断する条件に、そのディレクトリがGoソースファイル（`.go`ファイル）を含んでいるかどうかというチェックを追加した点にあります。

変更前は、`vendor`ディレクトリ内のパスが単にディレクトリとして存在するかどうか（`isDir(targ)`）だけで判断されていました。このため、`vendor/a/b`というディレクトリがGoソースファイルを含まない空のディレクトリであっても、Goツールはそれを有効なベンダーパスと見なし、GOPATHにある`a/b`パッケージよりも優先して解決しようとしました。結果として、GOPATHにある本来の`a/b`パッケージが隠蔽され、`a/b/c`のようなサブパッケージをベンダー化しつつ、`a/b`をGOPATHから利用するというシナリオが不可能になっていました。

このコミットでは、`hasGoFiles`という新しいヘルパー関数が導入されました。この関数は、指定されたディレクトリがGoソースファイルを含んでいるかどうかをチェックします。そして、`src/cmd/go/pkg.go`内の`vendoredImportPath`関数と、`src/go/build/build.go`内の`Context.Import`関数において、ベンダーパスを解決する際に、単にディレクトリが存在するかどうかだけでなく、`hasGoFiles`が`true`を返すことも条件に追加されました。

これにより、Goソースファイルを含まない`vendor`ディレクトリは、パッケージ解決の候補から除外されるようになります。その結果、GoツールはGOPATHにある本来のパッケージを正しく見つけ出し、インポートできるようになります。

例えば、プロジェクト構造が以下のようになっているとします。

```
/myproject
├── main.go
└── vendor/
    └── a/
        └── b/
            └── c/
                └── c.go  // vendored a/b/c
/GOPATH/src/a/
└── b/
    └── b.go  // real a/b
```

変更前は、`myproject`から`import "a/b"`とすると、`vendor/a/b`が存在するため、Goツールは`vendor/a/b`を優先して探し、Goソースファイルがないためエラーになるか、意図しない動作をしていました。
変更後は、`vendor/a/b`はGoソースファイルを含まないため無視され、GoツールはGOPATHにある`a/b`を正しく解決できるようになります。そして、`import "a/b/c"`とした場合は、`vendor/a/b/c`がGoソースファイルを含むため、それが優先的に解決されます。

## コアとなるコードの解説

### `hasGoFiles` 関数

`src/cmd/go/pkg.go`と`src/go/build/build.go`の両方に、ほぼ同じロジックを持つ`hasGoFiles`関数が追加されています。

```go
// hasGoFiles reports whether dir contains any files with names ending in .go.
// For a vendor check we must exclude directories that contain no .go files.
// Otherwise it is not possible to vendor just a/b/c and still import the
// non-vendored a/b. See golang.org/issue/13832.
func hasGoFiles(dir string) bool { // または func hasGoFiles(ctxt *Context, dir string) bool {
	fis, _ := ioutil.ReadDir(dir) // または ctxt.readDir(dir)
	for _, fi := range fis {
		if !fi.IsDir() && strings.HasSuffix(fi.Name(), ".go") {
			return true
		}
	}
	return false
}
```

この関数の目的は、指定されたディレクトリ`dir`をスキャンし、その中に`.go`拡張子を持つファイルが一つでも存在するかどうかを判定することです。
*   `ioutil.ReadDir(dir)`（または`ctxt.readDir(dir)`）は、ディレクトリ内のファイルおよびサブディレクトリの情報を取得します。
*   ループで各エントリ（`fi`）をチェックし、それがディレクトリではなく（`!fi.IsDir()`）、かつファイル名が`.go`で終わる場合（`strings.HasSuffix(fi.Name(), ".go")`）、そのディレクトリはGoソースファイルを含むと判断し、`true`を返します。
*   全てのファイルをチェックしても`.go`ファイルが見つからなければ、`false`を返します。

このシンプルなチェックが、ベンダーディレクトリの有効性を判断する上で非常に重要な役割を果たします。

### `vendoredImportPath` と `Context.Import` の変更

`vendoredImportPath`（`cmd/go`内）と`Context.Import`（`go/build`内）は、Goツールがインポートパスを解決する際にベンダーディレクトリを探索する主要な関数です。

変更前:
```go
if isDir(targ) { // ディレクトリが存在するかどうかのみをチェック
    // ... ベンダーパスとして処理 ...
}
```

変更後:
```go
if isDir(targ) && hasGoFiles(targ) { // ディレクトリが存在し、かつGoソースファイルを含むかをチェック
    // ... ベンダーパスとして処理 ...
}
```

この変更により、ベンダーディレクトリがGoソースファイルを含まない場合、`hasGoFiles(targ)`が`false`を返すため、そのディレクトリはベンダーパスとして認識されなくなります。結果として、GoツールはGOPATHなどの次の優先順位の場所からパッケージを検索し続けることになり、意図しないベンダーディレクトリによるパッケージの隠蔽を防ぎます。

この修正は、Goのベンダーエクスペリメントの初期段階における重要なバグ修正であり、Goのビルドシステムの堅牢性と予測可能性を向上させました。

## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ開発の初期段階にあり、標準ライブラリも急速に進化していました。`godoc`ツールは、Goのソースコードからドキュメントを生成し、Webブラウザで表示するための重要なツールです。当初、`godoc`は独自のテンプレート処理ロジック（`usr/gri/pretty/template.go`に実装されていたもの）を使用してHTMLページを生成していました。

しかし、Go言語の標準ライブラリに、より汎用的で堅牢なテンプレートシステム（後の`text/template`や`html/template`パッケージの原型）が導入されつつありました。この変更の背景には、以下のような目的があったと考えられます。

1.  **標準化と整合性**: 独自のテンプレートシステムを維持するのではなく、Go言語の標準的な方法論に準拠することで、コードベース全体の整合性を高める。
2.  **保守性の向上**: 標準ライブラリのテンプレートシステムは、Go開発者コミュニティ全体によってテストされ、改善されるため、独自のシステムを保守するよりも効率的でバグが少ない。
3.  **機能の活用**: 標準ライブラリのテンプレートシステムが提供する、より高度な機能（例えば、データ構造へのバインディング、エスケープ処理など）を活用する。
4.  **コードの簡素化**: 独自のテンプレート処理ロジックを削除することで、`godoc`のコードベースを簡素化し、理解しやすくする。

このコミットは、Go言語のエコシステムが成熟し、共通のツールやライブラリが整備されていく過程の一環と見ることができます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とパッケージに関する知識が必要です。

1.  **Go言語のテンプレートシステム (`text/template` / `html/template`)**:
    *   Go言語には、テキストやHTMLを動的に生成するための組み込みテンプレートパッケージがあります。このコミットが行われた2009年時点では、現在の`text/template`や`html/template`の初期バージョンが存在していました。
    *   これらのパッケージは、テンプレート文字列内にプレースホルダー（例: `{{.Title}}`）を定義し、Goのデータ構造（構造体、マップなど）をテンプレートに渡すことで、プレースホルダーを実際のデータで置き換えて最終的な出力を生成します。
    *   `Execute`メソッド（または当時の`Apply`に相当する機能）は、テンプレートとデータを結合し、結果を`io.Writer`インターフェースに書き出します。

2.  **`godoc` ツール**:
    *   `godoc`は、Goのソースコードからドキュメントを抽出し、整形して表示するコマンドラインツールおよびWebサーバーです。Goのパッケージ、関数、型などのドキュメントを自動生成し、開発者がGoのコードベースを理解するのに役立ちます。

3.  **`io.Writer` インターフェース**:
    *   Go言語における基本的なI/Oインターフェースの一つです。`Write([]byte) (n int, err error)`メソッドを実装する任意の型は`io.Writer`として扱えます。これにより、ファイル、ネットワーク接続、メモリバッファなど、様々な出力先に統一された方法でデータを書き込むことができます。
    *   このコミットでは、`http.Conn`から`io.Write`への変更が見られ、より汎用的な出力先に対応できるようになっています。

4.  **`bytes.Buffer` (または当時の `io.ByteBuffer`)**:
    *   `bytes`パッケージ（または当時の`io`パッケージ内の`ByteBuffer`）が提供する型で、可変長のバイトシーケンスをメモリ上で効率的に操作するためのバッファです。
    *   このコミットでは、直接`http.Conn`に書き込む代わりに、まず`io.ByteBuffer`にコンテンツを構築し、その内容をまとめてテンプレートシステムに渡すというパターンが採用されています。これにより、テンプレートシステムが一度に完全なコンテンツを受け取って処理できるようになります。

5.  **`sync.Once` (または当時の `once` パッケージ)**:
    *   `sync`パッケージ（または当時の`once`パッケージ）が提供する同期プリミティブで、特定の関数がプログラムの実行中に一度だけ実行されることを保証します。
    *   このコミットでは、`once.Do(readTemplate)`という形で使用されており、`godoc.html`テンプレートが一度だけ読み込まれるようにしています。これは、Webサーバーとして動作する際に、リクエストごとにテンプレートを読み込むオーバーヘッドを避けるための最適化です。

6.  **`strings` パッケージ**:
    *   Go言語の標準ライブラリの一部で、文字列操作のためのユーティリティ関数を提供します。このコミットでは、独自の`hasSuffix`関数が`strings.HasSuffix`に置き換えられています。これは、標準ライブラリの関数を使用することで、コードの品質と保守性を向上させる典型的な例です。

## 技術的詳細

このコミットの技術的な核心は、`godoc`が使用していた独自のテンプレートエンジンを廃止し、Go標準ライブラリのテンプレートシステムに完全に移行した点にあります。

具体的な変更点は以下の通りです。

1.  **`usr/gri/pretty/template.go` の削除**:
    *   このファイルは、`godoc`が独自に実装していたテンプレート処理ロジックを含んでいました。このコミットにより、ファイル全体が削除され、独自のテンプレートエンジンが完全に置き換えられたことを示しています。

2.  **`usr/gri/pretty/Makefile` の変更**:
    *   `astprinter.6`の依存関係から`template.6`が削除されています。これは、`template.go`がもはやビルドプロセスの一部ではないことを反映しています。

3.  **`usr/gri/pretty/godoc.go` の大幅な変更**:
    *   **テンプレートの読み込みと初期化**:
        *   以前は`godoc_html = template.NewTemplateOrDie("godoc.html")`のように、起動時にテンプレートファイルを読み込んでいました。
        *   変更後、`godoc_html`は単なる`string`型となり、`servePage`関数内で`once.Do(readTemplate)`が呼び出されるようになりました。`readTemplate`関数は、`usr/gri/pretty/godoc.html`ファイルを読み込み、その内容を`godoc_html`変数に格納します。`sync.Once`（当時の`once`パッケージ）を使用することで、この読み込み処理はアプリケーションのライフサイクル中に一度だけ実行されることが保証されます。これにより、テンプレートの遅延読み込みと効率的なキャッシュが実現されます。
    *   **`servePage` 関数のシグネチャと実装の変更**:
        *   変更前: `func servePage(c *http.Conn, title string, contents func())`
            *   `contents`引数が`func()`型であり、この関数が直接`http.Conn`にコンテンツを書き込むという、やや特殊なコールバック形式でした。
            *   テンプレートの適用には、独自の`godoc_html.Apply(c, "<!--", template.Substitution {...})`が使用されていました。これは、テンプレート内の特定のコメント（`<!--`）をプレフィックスとして、その後に続くキー（例: `TITLE-->`）に対応する`func()`を呼び出すという、独自の置換ロジックでした。
        *   変更後: `func servePage(c *http.Conn, title, content interface{})`
            *   `title`と`content`が`interface{}`型になり、より汎用的なデータを受け取れるようになりました。
            *   テンプレートに渡すデータは`Data`という新しい構造体にまとめられ、`template.Execute(godoc_html, &d, nil, c)`という形で標準ライブラリのテンプレートシステムが使用されています。
            *   `Data`構造体は、`title`, `header`, `timestamp`, `content`といったフィールドを持ち、これらがテンプレート内の対応するプレースホルダーにマッピングされます。
            *   `content`が`[]byte`または`string`として渡されるようになり、以前のようにコンテンツを生成する関数を渡す必要がなくなりました。
    *   **コンテンツ生成のバッファリング**:
        *   `serveDir`, `serveParseErrors`, `serveGoSource`, `servePackage`, `servePackageList`といった関数では、以前は直接`http.Conn` (`c`) に`fmt.Fprint`などで書き込んでいた部分が、`io.ByteBuffer`（当時の`io.ByteBuffer`）に書き込むように変更されています。
        *   例えば、`serveDir`では、ディレクトリ、Goファイル、その他のファイルのリストを生成する際に、まず`io.ByteBuffer` (`b`) に書き込み、その`b.Data()`（バイトスライス）を`servePage`の`content`引数として渡しています。これにより、コンテンツが完全に生成されてからテンプレートに渡されるため、テンプレートシステムがより効率的に処理できるようになります。
    *   **文字列操作関数の置き換え**:
        *   独自の`hasPrefix`および`hasSuffix`関数が削除され、Go標準ライブラリの`strings.HasSuffix`が使用されるようになりました。これは、標準ライブラリの成熟と、それに伴うコードの簡素化と堅牢化の典型的な例です。
    *   **`printLink` 関数のシグネチャ変更**:
        *   `func printLink(c *http.Conn, dir, name string)` から `func printLink(c io.Write, dir, name string)` へと変更されました。これにより、`printLink`はHTTP接続だけでなく、任意の`io.Writer`にリンクを書き込めるようになり、より汎用性が高まりました。これは、テストのしやすさや、将来的な出力先の変更に対する柔軟性をもたらします。

これらの変更は、`godoc`の内部実装を、Go言語の設計思想と標準ライブラリの進化に沿ったものにするための重要なステップでした。

## コアとなるコードの解説

1.  **`usr/gri/pretty/template.go` の削除**:
    *   このファイルの削除は、`godoc`がもはや独自のテンプレートエンジンに依存していないことを明確に示しています。これにより、コードベースが大幅に簡素化され、Go標準ライブラリの機能に一本化されました。これは、Go言語の設計哲学である「少ない方が良い（Less is more）」を体現する変更です。

2.  **`usr/gri/pretty/godoc.go` における `servePage` 関数の変更**:
    *   **テンプレート読み込みの最適化**: `godoc_html`変数が`string`型になり、`readTemplate`関数でファイルから読み込まれるようになりました。そして、`servePage`内で`once.Do(readTemplate)`が呼び出されることで、テンプレートファイルはアプリケーションの起動後、最初の`servePage`呼び出し時に一度だけ読み込まれ、それ以降はメモリ上のキャッシュが利用されます。これにより、I/O操作のオーバーヘッドが削減され、パフォーマンスが向上します。
    *   **汎用的なデータ構造への移行**: 以前は`contents func()`という形でコンテンツ生成ロジックを渡していましたが、新しい`servePage`では`title`と`content`を`interface{}`として受け取り、これらを`Data`構造体にマッピングしてテンプレートに渡します。この`Data`構造体は、テンプレートが期待する特定のフィールド（`title`, `header`, `timestamp`, `content`）を持つことで、テンプレートエンジンがこれらのデータを直接参照してHTMLを生成できるようになります。これは、テンプレートとデータの分離を促進し、よりクリーンな設計を可能にします。
    *   **標準テンプレートエンジンの利用**: `template.Execute(godoc_html, &d, nil, c)`という行が、Go標準ライブラリのテンプレートエンジンを使用していることを示しています。`godoc_html`はテンプレート文字列、`&d`はテンプレートに渡すデータ、`c`は結果を書き込む`io.Writer`です。これにより、`godoc`はGoエコシステムで広く使われている堅牢なテンプレート処理機能の恩恵を受けることができます。

3.  **`usr/gri/pretty/godoc.go` における `hasSuffix` の置き換え**:
    *   独自の`hasPrefix`および`hasSuffix`関数が削除され、`strings.HasSuffix`が使用されるようになりました。これは、Goの標準ライブラリが提供する機能を利用することで、カスタム実装の必要性をなくし、コードの重複を避け、より信頼性の高い実装に置き換えるというベストプラクティスに従っています。`strings`パッケージの関数は、Goのコア開発者によって最適化され、テストされているため、パフォーマンスと正確性が保証されます。

これらの変更は、`godoc`の内部構造を現代のGo言語の慣習と標準ライブラリの機能に適合させ、より堅牢で保守しやすいアプリケーションへと進化させるための重要な一歩でした。

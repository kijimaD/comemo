# [インデックス 24113] ファイルの概要

このコミットは、GoランタイムがWindows XP amd64環境で例外を処理する方法に関するバグを修正します。具体的には、以前の変更（CL 10370）によってWindows XP amd64上の`TestRaiseException`が予期せず失敗するようになった問題に対し、古い変更（CL 8165）を元に戻すことで対応しています。これにより、Windows XP amd64でも、より新しいWindowsバージョンと同様に、例外処理に`AddVectoredContinueHandler`が使用されるようになります。

## 元コミット内容

このコミットは、Windows XP amd64環境においてGoランタイムが例外処理に`AddVectoredContinueHandler`を使用するように変更します。最近の変更（CL 10370）がWindows XP amd64上の`TestRaiseException`を予期せず破損させたため、古いCL 8165を元に戻すことでこの問題を修正します。これにより、Windows XP amd64でも他の新しいWindowsバージョンと同様に、例外処理に`AddVectoredContinueHandler`が使用されるようになります。この変更はIssue #11481を修正します。

## 変更の背景

この変更の背景には、GoランタイムがWindows上で例外を処理する方法に関する特定のバグがあります。コミットメッセージによると、`CL 10370`という最近の変更が導入された後、Windows XP amd64環境で`TestRaiseException`というテストが予期せず失敗するようになりました。この問題の根本原因はコミット作成者にも不明であるとされていますが、以前の`CL 8165`を元に戻すことで問題が解決することが判明しました。

`CL 10370`が具体的に何をもたらしたのか、また`CL 8165`がどのような変更であったのかは、このコミットメッセージからは詳細には分かりませんが、結果として`TestRaiseException`の失敗を修正することが喫緊の課題でした。その解決策として、Windows XP amd64でも`AddVectoredContinueHandler`を使用するパスに戻すことが選ばれました。これは、より新しいWindowsバージョンで既に採用されている例外処理メカニズムと一貫性を持たせるものです。

この問題はGoのIssueトラッカーで`#11481`として報告されており、このコミットはその修正を目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### Windowsの例外処理メカニズム

Windowsオペレーティングシステムは、プログラム実行中に発生するエラー（例外）を処理するための複数のメカニズムを提供しています。

1.  **構造化例外処理 (Structured Exception Handling, SEH)**: Windowsのネイティブな例外処理メカニズムです。ハードウェア例外（ゼロ除算、無効なメモリアクセスなど）とソフトウェア例外（`RaiseException`関数で明示的に発生させるものなど）の両方を扱います。
2.  **`SetUnhandledExceptionFilter`**: これは、プロセス内で未処理の例外が発生した場合に呼び出される単一のコールバック関数を設定するために使用されます。通常、アプリケーションがクラッシュする前にカスタムのログ記録や診断情報を収集するために使われます。このフィルターは、例外が他のハンドラによって処理されなかった場合にのみ呼び出されます。つまり、「最後の手段」として機能します。
3.  **ベクタ例外ハンドラ (`AddVectoredExceptionHandler` / `AddVectoredContinueHandler`)**: これらはWindows XP SP1以降で導入された、より柔軟な例外処理メカニズムです。
    *   `AddVectoredExceptionHandler`は、例外が発生したときに最初に呼び出されるハンドラのチェーンを登録します。これらのハンドラは、例外を処理するか、処理を継続するか、または次のハンドラに渡すかを決定できます。
    *   `AddVectoredContinueHandler`は、例外が処理された後、実行が継続される前に呼び出されるハンドラのチェーンを登録します。これは、例外が処理された後に特定のクリーンアップや状態の調整を行うのに役立ちます。このコミットでは、例外発生後の継続処理に焦点を当てています。

`SetUnhandledExceptionFilter`が「最後の手段」であるのに対し、ベクタ例外ハンドラは例外処理プロセスのより早い段階で介入でき、より細かい制御が可能です。Goランタイムのような低レベルのシステムでは、より細かい制御が可能なベクタ例外ハンドラを使用することが望ましい場合があります。

### GoランタイムとOSシグナル/例外

Goプログラムは、OSからシグナル（Unix系）や例外（Windows系）を受け取った際に、独自のランタイムメカニズムでこれらを処理します。例えば、Goのゴルーチンがパニックを起こしたり、無効なメモリアクセスを行ったりした場合、OSは例外を発生させ、Goランタイムはその例外を捕捉して、スタックトレースの出力やプログラムの終了といった適切なGoらしい動作に変換します。

Windows環境では、GoランタイムはこれらのOS例外を捕捉し、Goのパニック機構に変換する必要があります。このために、Goランタイムは上記のWindows API関数を利用して、独自の例外ハンドラを登録します。

### CL 10370 と CL 8165

コミットメッセージで言及されている`CL 10370`と`CL 8165`は、Goプロジェクトの変更リスト（Change List）のIDです。これらはGoのコードレビューシステム（Gerrit）における特定の変更セットを指します。

*   **CL 8165**: このコミットが「reverting old CL 8165 fixes the problem」と述べていることから、CL 8165はWindows XP amd64での`AddVectoredContinueHandler`の使用を何らかの形で変更または無効にした可能性が高いです。
*   **CL 10370**: このコミットが「Recent change (CL 10370) unexpectedly broke TestRaiseException」と述べていることから、CL 10370はWindows XP amd64の例外処理に影響を与え、`TestRaiseException`を破損させた原因となった変更です。

これらのCLの具体的な内容は、GoのGerritレビューサイトで検索することで確認できますが、このコミットの文脈では、CL 10370が問題を引き起こし、CL 8165を元に戻すことで解決した、という事実が重要です。

### `TestRaiseException`

これはGoランタイムのテストスイートの一部であり、意図的に例外を発生させ、Goランタイムがそれを正しく捕捉・処理できるかを検証するテストです。このテストが失敗するということは、Goランタイムの例外処理メカニズムに問題があることを示しています。

## 技術的詳細

このコミットの技術的詳細の中心は、Windows XP amd64環境におけるGoランタイムの例外処理パスの変更です。

以前のGoランタイムのコードでは、`initExceptionHandler`関数内でWindowsのバージョンをチェックし、メジャーバージョンが6未満（つまりWindows XPやWindows Server 2003など）の場合、または`AddVectoredContinueHandler`が利用できない場合、あるいは`unsafe.Sizeof(&_AddVectoredContinueHandler) == 4`（32ビット環境を示唆）の場合に、`SetUnhandledExceptionFilter`を使用して例外ハンドラを設定していました。特に、Windows XP amd64はWindows 5.x系に属するため、この条件に合致し、`SetUnhandledExceptionFilter`が使われていたと考えられます。

コミットメッセージによると、`CL 10370`という変更が導入された後、Windows XP amd64で`TestRaiseException`が失敗するようになりました。この問題の解決策として、以前の`CL 8165`を元に戻すことが効果的であることが判明しました。`CL 8165`が具体的に何をしたのかは不明ですが、結果としてこのコミットは、Windows XP amd64に対しても`AddVectoredContinueHandler`を使用するパスを強制します。

変更後のコードでは、`initExceptionHandler`関数内の条件分岐から`major < 6`（Windowsバージョンチェック）の条件が削除されています。これにより、Windows XP amd64であっても、`_AddVectoredContinueHandler`が利用可能であり、かつ64ビット環境である限り（`unsafe.Sizeof(&_AddVectoredContinueHandler) == 4`が偽である限り）、`AddVectoredContinueHandler`が使用されるようになります。

この変更の利点は、GoランタイムがWindows XP amd64でも、より新しいWindowsバージョンと同様に、ベクタ例外ハンドラを利用した一貫性のある例外処理ロジックを使用できる点です。`AddVectoredContinueHandler`は`SetUnhandledExceptionFilter`よりも柔軟性が高く、例外処理チェーンのより早い段階で介入できるため、GoランタイムがOS例外をGoのパニックに変換する際の信頼性が向上する可能性があります。

また、コミットメッセージには「V5 appears to fail to call the continue handlers if windows error reporting dialog is disabled.」というコメントが削除されています。これは、Windows XP (V5) でベクタ例外ハンドラが特定の条件下で機能しない可能性を示唆していましたが、このコミットではその懸念が解消されたか、あるいはWindows XP amd64においてはその問題が顕在化しないと判断されたことを意味します。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがWindowsのバージョンに依存して例外処理メカニズムを切り替えるロジックを簡素化し、特にWindows XP amd64環境で`AddVectoredContinueHandler`を優先的に使用するように変更した点にあります。

1.  **`getVersion()`関数の削除と`_GetVersion`の非使用**:
    *   `src/runtime/os1_windows.go`から`_GetVersion`の動的インポートと`getVersion()`関数が完全に削除されました。これは、GoランタイムがWindowsのメジャーバージョンを明示的に取得して例外処理のロジックを分岐させる必要がなくなったことを意味します。
    *   以前は、`getVersion()`で取得した`major`バージョンが6未満（Windows Vistaより古いOS、例: Windows XPはバージョン5.x）の場合に、特定の例外処理パスを選択していました。このバージョンチェックが不要になったため、関連するコードも削除されました。

2.  **`initExceptionHandler`の条件分岐の変更**:
    *   `src/runtime/signal_windows.go`の`initExceptionHandler`関数は、Goランタイムの例外ハンドラを初期化する役割を担っています。
    *   変更前は、以下の3つの条件のいずれかが真の場合に`SetUnhandledExceptionFilter`を使用していました。
        *   `_AddVectoredContinueHandler == nil` (VectoredContinueHandlerが利用できない場合)
        *   `unsafe.Sizeof(&_AddVectoredContinueHandler) == 4` (32ビット環境の場合)
        *   `major < 6` (Windows Vistaより古いOSの場合)
    *   このコミットでは、`major < 6`という条件が削除されました。これにより、Windows XP amd64（`major`が5）であっても、最初の2つの条件（`_AddVectoredContinueHandler`の利用可能性と64ビット環境であること）が満たされれば、`SetUnhandledExceptionFilter`ではなく`AddVectoredContinueHandler`が使用されるようになります。
    *   結果として、Windows XP amd64は、他の新しいWindowsバージョンと同様に、`AddVectoredContinueHandler`を介した例外処理パスを利用するようになります。これは、コミットメッセージで述べられているように、「That is what we do for all recent Windows versions too.」という方針に合致します。

この変更は、特定の環境（Windows XP amd64）で発生していた`TestRaiseException`の失敗を修正するために行われました。`CL 10370`が問題を引き起こし、`CL 8165`を元に戻すことで解決したという経緯から、`CL 8165`が`major < 6`の条件を導入したか、あるいはその条件に関連する動作を変更した可能性が考えられます。このコミットは、その変更を実質的に元に戻し、Windows XP amd64でもよりモダンな例外処理メカニズムを使用させることで、テストの失敗を解消しています。

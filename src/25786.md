## 変更の背景

このコミットの主な背景は、Goコンパイラが構文エラーに遭遇した際の回復能力の不足を改善することにあります。Go言語のコンパイラ（特に`cmd/compile`）は、ソースコードを解析して抽象構文木（AST）を構築する際に、字句解析（lexing）と構文解析（parsing）の段階を経ます。ユーザーが記述したコードに構文エラーが含まれている場合、パーサーはエラーを検出し、その後の解析を継続しようと試みます。しかし、エラー回復の戦略が不十分だと、一つの小さな構文エラーが連鎖的なエラーメッセージを引き起こし、開発者が真の原因を特定するのを困難にすることがあります（いわゆる「エラーの滝」）。

`Fixes #13319`という記述から、このコミットがGo issue 13319を解決するために行われたことがわかります。このissueは、特定の構文エラー（例: 関数呼び出しの引数リストの閉じ括弧の欠落）が発生した際に、コンパイラが適切なエラーメッセージを出力せず、その後のコードも正しく解析できないという問題点を指摘していました。

この問題に対処するため、パーサーがエラー発生後に「同期」するためのより洗練されたメカニズムが必要とされました。具体的には、パーサーがエラー箇所をスキップし、次に意味のある構文要素（同期点）を見つけて解析を再開できるようにすることが目標でした。これにより、より正確で有用なエラーメッセージを提供し、開発者のデバッグ体験を向上させることが期待されます。

## 前提知識の解説

### コンパイラのフロントエンド（字句解析と構文解析）

コンパイラは、ソースコードを機械語に変換するソフトウェアです。その最初の段階が「フロントエンド」と呼ばれ、主に以下の2つのフェーズから構成されます。

1.  **字句解析（Lexical Analysis / Scanning）**: ソースコードを文字のストリームとして読み込み、意味のある最小単位である「トークン（token）」に分割します。例えば、`if x > 0 {`というコードは、`if`（キーワード）、`x`（識別子）、`>`（演算子）、`0`（リテラル）、`{`（区切り文字）といったトークンに変換されます。
2.  **構文解析（Syntactic Analysis / Parsing）**: 字句解析器から受け取ったトークンのストリームが、プログラミング言語の文法規則（構文）に合致しているかを検証し、通常は抽象構文木（AST: Abstract Syntax Tree）を構築します。ASTは、プログラムの構造を階層的に表現したものです。

### 構文エラー回復

構文解析中に文法規則に違反するトークン列が見つかった場合、それは「構文エラー」です。コンパイラはエラーを報告するだけでなく、その後のコードの解析を継続しようとします。このプロセスが「エラー回復」です。エラー回復の目的は、単一のエラーによってコンパイルプロセス全体が停止するのを防ぎ、できるだけ多くのエラーを一度に報告すること、そして誤ったエラーメッセージ（エラーの連鎖）を最小限に抑えることです。

一般的なエラー回復戦略には以下のようなものがあります。

*   **パニックモード回復（Panic Mode Recovery）**: エラーが発生したトークンから、特定の同期トークン（例: セミコロン、閉じ括弧、キーワードなど）が見つかるまでトークンをスキップします。シンプルですが、スキップしすぎる可能性があります。
*   **フレーズレベル回復（Phrase Level Recovery）**: エラーが発生した箇所で、トークンを挿入、削除、置換して、文法的に正しいフレーズを形成しようと試みます。
*   **エラープロダクション（Error Productions）**: 文法にエラーパターンを明示的に追加し、エラーを認識して回復します。

このコミットでは、パニックモード回復の考え方をより洗練させたアプローチが取られています。

### Follow-セットとStop-セット

構文解析器がエラー回復を行う際に、次に有効なトークンや、スキップを停止すべきトークンを決定するために使用される概念です。

*   **Follow-セット（Follow-set）**: ある非終端記号（例: `Statement`）の後に続く可能性のある終端記号（トークン）の集合です。エラー回復時には、現在の構文要素のFollow-セットに含まれるトークンが見つかるまでスキップすることで、パーサーが正しい位置に再同期できる可能性があります。
*   **Stop-セット（Stop-set）**: エラー回復時に、パーサーがスキップを停止すべきトークンの集合です。これらは通常、文の開始を示すキーワード（`if`, `for`, `func`など）や、ブロックの終わりを示す記号（`}`）など、強力な同期点となるトークンです。これらのトークンは、たとえエラーの途中であっても、スキップすべきではないと判断されることが多いです。

このコミットでは、`stoplist`という名前でGo言語のキーワードが定義されており、これらがパーサーの同期点として利用されています。

### ネスティングレベル

パーサーがコードブロックや式、関数定義などの入れ子構造を追跡するために使用するカウンタです。例えば、括弧のペア`()`、波括弧のペア`{}`、角括弧のペア`[]`などが出現するたびにレベルを増減させます。エラー回復時にこのネスティングレベルを考慮することで、パーサーは現在のスコープを逸脱してトークンをスキップしすぎることを防ぎ、より適切な同期点を見つけることができます。

このコミットでは、`fnest`（関数ネスティングレベル）と`xnest`（式ネスティングレベル）という2つの新しいフィールドが導入され、エラー回復の精度を高めるために利用されています。

### Goコンパイラの`cmd/compile/internal/gc/parser.go`

Go言語の公式コンパイラは、`go`コマンドの一部として提供される`cmd/compile`です。その内部には、Go言語の構文解析を担当する`internal/gc/parser.go`ファイルがあります。このファイルには、Go言語の文法規則に基づいてトークンを解析し、ASTを構築するためのロジックが実装されています。`parser`構造体は、現在のトークン、次のトークン、エラー情報、そしてこのコミットで追加されたネスティングレベルなどの状態を保持します。

### `osemi`と`ocomma`関数

Go言語の文法では、セミコロン（`;`）とカンマ（`,`）は特定の場所で省略可能です。例えば、改行がある場合や、閉じ括弧/波括弧の直前ではセミコロンを省略できます。`osemi`（optional semicolon）と`ocomma`（optional comma）は、Goコンパイラのパーサー内で、これらの省略可能な区切り文字を処理するためのヘルパー関数です。これらの関数は、文法的にセミコロンやカンマが期待されるが、それが存在しない場合でもエラーとせずに解析を続行できるようにします。このコミットでは、これらの関数もエラー回復ロジックに合わせて変更されています。

## 技術的詳細

このコミットは、Goコンパイラの構文エラー回復メカニズムを大幅に改善するために、以下の主要な技術的アプローチを導入しています。

1.  **Follow-トークンとStop-トークンの組み合わせ**:
    *   以前の`advance`関数は、単一の`stoplist`（停止トークンのリスト）に基づいてトークンをスキップしていました。
    *   新しい`advance`関数は、`followlist`（現在の構文要素の後に続く可能性のあるトークン）と、グローバルな`stoplist`（強力な同期点となるキーワード）の両方を考慮するようになりました。
    *   `stoplist`は、`LBREAK`, `LCONST`, `LCONTINUE`, `LDEFER`, `LFALL`, `LFOR`, `LFUNC`, `LGO`, `LGOTO`, `LIF`, `LRETURN`, `LSELECT`, `LSWITCH`, `LTYPE`, `LVAR`といったGo言語のキーワードで構成される`map[int32]bool`として定義されました。これらのキーワードは、文の開始を示すため、エラー回復時にスキップすべきではないと判断されます。
    *   `stoplist`は、パーサーが関数内部にいる場合（`p.fnest > 0`）にのみ考慮されます。これにより、関数外でのエラー回復の挙動が不必要に影響を受けるのを防ぎます。

2.  **ネスティングレベルの導入**:
    *   以前は`nest`という単一のフィールドが「式ネスティングレベル（for complit ambiguity resolution）」として存在していました。
    *   このコミットでは、`nest`が`xnest`（expression nesting level）にリネームされ、さらに`fnest`（function nesting level）という新しいフィールドが追加されました。
    *   `fnest`は、パーサーが関数本体の内部にいるかどうかを追跡します。関数定義の開始時にインクリメントされ、終了時にデクリメントされます。
    *   `xnest`は、括弧`()`, 角括弧`[]`, 波括弧`{}`（複合リテラルなど）によって定義される式やブロックのネスティングレベルを追跡します。
    *   これらのネスティングレベルは、`advance`関数や`ocomma`, `osemi`関数などのエラー回復ロジックで利用され、パーサーが現在のスコープを尊重し、より適切な同期点を見つけるのに役立ちます。例えば、`advance`関数は、`fnest > 0`の場合にのみ`stoplist`を考慮することで、関数内部でのエラー回復を改善します。

3.  **`osemi`と`ocomma`関数の改善**:
    *   これらの関数は、Go言語の文法でセミコロンやカンマが省略可能な箇所を処理します。
    *   変更前は、単に`p.want(';')`や`p.want(',')`を呼び出すか、閉じ括弧/波括弧の直前であれば何もしないというシンプルなロジックでした。
    *   変更後は、これらの関数が`follow`トークン（期待される次のトークン）を受け取るようになり、エラーが発生した場合に`p.advance(follow)`を呼び出して、その`follow`トークンまでスキップするようになりました。
    *   また、これらの関数は`bool`値を返すようになり、エラー回復が成功したかどうかを呼び出し元に通知します。これにより、呼び出し元はエラー回復が失敗した場合にループを中断するなどの適切な処理を行えるようになりました。例えば、`import`ブロックや`var`ブロック内で`osemi`が失敗した場合、`break`を使ってループを抜けるようになっています。

これらの変更により、パーサーは構文エラーに遭遇した際に、より賢くトークンをスキップし、適切な同期点を見つけて解析を再開できるようになります。これにより、コンパイラはより正確なエラーメッセージを生成し、開発者がエラーを修正しやすくなります。

## コアとなるコードの解説

### `parser`構造体の`fnest`と`xnest`

以前は`nest`という単一のフィールドで式のネスティングレベルを管理していましたが、このコミットでは`fnest`と`xnest`に分離されました。
*   `fnest` (function nesting level): これはパーサーが現在、関数本体の内部にいるかどうかを追跡するために使用されます。`fnbody()`関数（関数本体を解析する関数）の開始時にインクリメントされ、終了時にデクリメントされます。`fnest > 0`であることは、パーサーが関数内部にいることを意味し、この状態は`advance`関数で`stoplist`を適用するかどうかの判断基準となります。関数内部では、`break`, `continue`, `return`などのキーワードが文の開始点として機能するため、エラー回復の同期点として重要です。
*   `xnest` (expression nesting level): これは、括弧`()`, 角括弧`[]`, 波括弧`{}`（複合リテラルなど）で囲まれた式のネスティングレベルを追跡します。例えば、`operand()`関数内で`(`が見つかると`xnest`がインクリメントされ、`)`が見つかるとデクリメントされます。このレベルは、複合リテラルの曖昧性解決（`complit_ok`の判断）や、式内のエラー回復の範囲を限定するために使用されます。

これらの分離により、パーサーは関数スコープと式スコープのそれぞれで、よりきめ細やかなエラー回復戦略を適用できるようになりました。

### `stoplist`の導入と`advance`関数の改善

`stoplist`は、Go言語の主要なキーワード（`LBREAK`, `LCONST`, `LFUNC`, `LIF`, `LRETURN`, `LSWITCH`, `LVAR`など）を格納する`map[int32]bool`です。これらのキーワードは、Goの文法において強力な同期点（statement boundary）として機能します。

`advance`関数は、構文エラーが発生した際に、パーサーがトークンをスキップして適切な同期点まで進むための中心的な役割を担います。
変更前は、`advance`は引数として受け取った`stoplist`内のトークンが見つかるまでスキップしていました。
変更後は、以下のロジックで動作します。
1.  `p.fnest > 0`（関数内部にいる）かつ、現在のトークン`p.tok`がグローバルな`stoplist`に含まれている場合、スキップを停止してすぐに`return`します。これは、関数内部の文の開始キーワードを誤ってスキップしないようにするためです。
2.  現在のトークン`p.tok`が、引数として渡された`followlist`に含まれている場合、スキップを停止して`return`します。`followlist`は、現在の構文要素の後に続くことが期待されるトークンであり、これが見つかればパーサーは正しいパスに戻ったと判断できます。
3.  上記のいずれの条件も満たさない場合、`p.next()`を呼び出して次のトークンを読み込み、スキップを継続します。

この新しい`advance`関数は、グローバルな同期点（`stoplist`）と局所的な同期点（`followlist`）を組み合わせ、さらに`fnest`によって関数スコープを考慮することで、より賢く、より少ない誤ったエラーを生成するエラー回復を実現しています。

### `osemi`と`ocomma`関数の変更

`osemi`（optional semicolon）と`ocomma`（optional comma）は、Go言語の文法でセミコロンやカンマが省略可能な箇所を処理する関数です。
変更前は、これらの関数は単に`p.want(';')`や`p.want(',')`を呼び出すか、閉じ括弧/波括弧の直前であれば何もしないというシンプルなものでした。エラーが発生した場合、`p.want`がエラーを報告し、パーサーは回復を試みるものの、その後の解析が不安定になる可能性がありました。

変更後は、これらの関数は`follow int32`という引数を受け取るようになりました。これは、セミコロンやカンマの後に続くことが期待されるトークンです。
*   現在のトークンがセミコロンまたはカンマであれば、それを消費して`true`を返します。
*   現在のトークンが閉じ括弧`')'`または閉じ波括弧`'}'`であれば、セミコロン/カンマが省略されたとみなし、`true`を返します。
*   上記以外の場合、構文エラーを報告し、`p.advance(follow)`を呼び出して`follow`トークンまでスキップし、`false`を返します。

これにより、`osemi`や`ocomma`がエラーを検出した場合でも、`follow`トークンをヒントとして`advance`関数を呼び出すことで、パーサーはより確実に次の有効な構文要素に同期できるようになりました。また、戻り値が`bool`になったことで、呼び出し元はエラー回復が成功したかどうかを判断し、必要に応じてループを中断するなどの適切な制御フローを実装できるようになりました。例えば、`import`ブロックや`var`ブロックの解析ループでは、`if !p.osemi(')') { break }`のように、エラー回復が失敗した場合はループを抜けることで、無限ループやさらなる誤ったエラーの連鎖を防いでいます。

これらの変更は、Goコンパイラがより堅牢になり、ユーザーが遭遇する構文エラーメッセージの品質と有用性が向上することに直接貢献しています。

## 変更の背景

コンパイラにおけるレジスタ割り当ては、プログラムの実行速度に直接影響を与える重要な最適化フェーズです。CPUのレジスタは非常に高速な記憶領域ですが、その数は限られています。そのため、どの変数をレジスタに保持し、どの変数をメモリ（スタック）に退避（スピル）させるかを効率的に決定する必要があります。

このコミット以前のGoコンパイラのSSAバックエンドでは、値の「次回の使用 (next use)」の計算が十分に正確ではなかった可能性があります。次回の使用情報が不正確だと、コンパイラは以下のような非効率な決定を下すことがあります。

1.  **不必要なレジスタ保持**: ある値がしばらく使われない期間（ライフタイムホール）があるにもかかわらず、レジスタに保持し続けてしまう。これにより、他のより頻繁に使われる値がレジスタに割り当てられず、不必要なスピルが発生する。
2.  **非最適なスピル**: レジスタが不足した際に、次に使用されるまでの距離が短い値をスピルしてしまう。理想的には、次に使用されるまでの距離が最も遠い値をスピルすべきです。

これらの問題は、生成されるアセンブリコードのサイズ増加や実行速度の低下につながります。このコミットは、これらの非効率性を解消し、より最適なレジスタ割り当てを実現するために、次回の使用計算の精度向上とライフタイムホールの検出を導入しました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化の中間表現（IR）の一種です。この形式では、すべての変数に一度だけ値が割り当てられます。つまり、変数が再定義されるたびに新しいバージョンが作成されます（例: `x1 = ...`, `x2 = ...`）。SSA形式は、データフロー解析を簡素化し、多くの最適化（デッドコード削除、共通部分式除去など）を容易にします。Goコンパイラも、最適化のためにコードをSSA形式に変換します。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、プログラムの変数をCPUの物理レジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速であるため、できるだけ多くの変数をレジスタに保持することが性能向上につながります。しかし、レジスタの数は限られているため、コンパイラはどの変数をレジスタに保持し、どの変数をメモリ（スタック）に退避させるか（スピル）を決定する必要があります。Goコンパイラは、線形スキャンレジスタアロケータの一種を使用しています。

### 3. ライブレンジとライブネス解析 (Live Range and Liveness Analysis)

*   **ライブレンジ**: 変数が定義されてから、その値が最後に使用されるまでのプログラムの範囲を指します。
*   **ライブネス解析**: プログラムの特定の位置で、ある変数の値が将来使用される可能性があるかどうか（「ライブである」かどうか）を判断するデータフロー解析です。レジスタ割り当てにおいて、ライブでない変数はレジスタを占有する必要がないため、そのレジスタは他の変数に再利用できます。

### 4. 次回の使用情報 (Next Use Information)

レジスタ割り当てにおいて、レジスタが不足し、ある値をスピルする必要がある場合、どの値をスピルするかを決定する重要なヒューリスティックが「次回の使用」です。次に使用されるまでの距離が最も遠い値をスピルすることで、その値がレジスタに戻されるまでの期間を最大化し、スピルのコストを最小限に抑えることができます。

### 5. ライフタイムホール (Lifetime Holes)

ライフタイムホールとは、変数のライブレンジ内において、その変数の値が一時的に使用されない期間のことです。例えば、`x = A; ...; y = B; ...; print(x);` のようなコードで、`y = B` の行から `print(x)` の行までの間、`x` の値はライブですが、実際には使用されていません。このような期間を正確に検出できれば、その間は`x`が占有していたレジスタを他の変数に一時的に割り当て、その後`x`が再び必要になったときにレジスタに戻すことができます。これにより、レジスタの利用効率が向上します。

### 6. スピル (Spilling)

レジスタが不足し、レジスタに保持されている値をメモリに退避させる操作をスピルと呼びます。スピルされた値は、次に使用される際にメモリからレジスタに再ロードされます。スピルと再ロードはメモリアクセスを伴うため、CPUサイクルを消費し、プログラムの実行速度を低下させます。したがって、コンパイラはスピルの回数を最小限に抑えるように努めます。

### 7. スパースマップ (Sparse Map)

スパースマップは、疎なデータ（多くの要素がデフォルト値であるデータ）を効率的に格納・管理するためのデータ構造です。このコミットでは、`sparsemap.go`で実装された`sparseMap`が、ライブネス解析において多数の変数の中からライブな変数を効率的に追跡するために使用されています。これは、`dense`配列と`sparse`配列を組み合わせることで、要素の追加、削除、検索を高速に行えるように設計されています。

## 技術的詳細

このコミットの主要な技術的変更点は、レジスタ割り当てにおける「次回の使用」の計算方法と、それに伴うデータ構造の刷新です。

### 1. `use` 構造体の変更

以前は、`use`構造体は`idx`（使用位置のインデックス）と`vid`（値のID）を持っていました。
変更後:
```go
type use struct {
	dist int32 // distance from start of the block to a use of a value
	next *use  // linked list of uses of a value in nondecreasing dist order
}
```
`idx`が`dist`（ブロックの開始から使用までの距離）に変わり、`next`ポインタが追加され、値の各使用が単方向連結リストとして管理されるようになりました。これにより、特定の値の次回の使用を距離に基づいて効率的に追跡できるようになります。

### 2. `valState` 構造体の変更

以前は、`uses []int32`として、使用位置のインデックスのソート済みリストを持っていました。
変更後:
```go
type valState struct {
	regs       regMask // the set of registers holding a Value (usually just one)
	uses       *use    // list of uses in this block
	spill      *Value  // spilled copy of the Value
	spill2     *Value  // special alternate spill location used for phi resolution
	spillUsed  bool
	spill2used bool
}
```
`uses`フィールドが`*use`型になり、`use`構造体の連結リストの先頭を指すようになりました。これにより、各値のブロック内での使用箇所が距離順に連結リストで管理されます。

### 3. `regAllocState` 構造体の変更

*   **`needReg []bool` の追加**: 各値がレジスタを必要とするかどうかを高速にチェックするためのフラグが追加されました。`v.Type.IsMemory()` や `v.Type.IsVoid()` でない場合に`true`となります。
*   **`live` フィールドの変更**: 以前は`[][][]ID`（ブロックIDと後続エッジのインデックスから値IDのリストへのマップ）でした。
    変更後:
    ```go
    live [][]liveInfo
    ```
    `liveInfo`構造体は`ID`（値のID）と`dist`（次回の使用までの命令数）を持ちます。これにより、ブロックの終端でライブな値だけでなく、その次回の使用までの距離も追跡できるようになりました。これは、レジスタ割り当てのスピルヒューリスティックにおいて非常に重要な情報です。
*   **`freeUseRecords *use` の追加**: `use`オブジェクトのプールとして機能します。`addUse`で新しい`use`が必要な場合、このプールから取得し、`advanceUses`で不要になった`use`をプールに戻すことで、メモリ割り当てのオーバーヘッドを削減します。

### 4. `computeLive` 関数の導入と変更

以前は`f.live()`という関数がライブネス情報を計算していましたが、このコミットで`s.computeLive()`というメソッドに置き換えられました。この関数は、後順序（postorder）でブロックを走査し、逆方向にライブネス解析を行います。

*   **距離の計算**: `liveInfo`構造体の`dist`フィールドを導入し、各ライブな値について、ブロックの終端から次回の使用までの命令数を計算します。
*   **`sparseMap` の利用**: ライブネスセットの管理に`sparseMap`を使用することで、多数の変数の中からライブな変数を効率的に追加・削除・検索できるようになりました。
*   **エッジの重み付け**: `normalEdge`, `likelyEdge`, `unlikelyEdge`といった定数を導入し、分岐の可能性（`BranchLikely`, `BranchUnlikely`）に基づいてエッジの距離に重み付けを行うようになりました。これにより、より頻繁に実行されるパス上の使用が、スピル選択において優先されるようになります。

### 5. `addUse` および `advanceUses` 関数の導入

*   **`addUse(id ID, dist int32)`**: 指定された値`id`の`dist`距離での使用を、`valState`内の連結リストに追加します。距離が非減少順になるように追加されます。
*   **`advanceUses(v *Value)`**: 命令`v`の引数（`v.Args`）の使用を「進めます」。つまり、`v`が実行されたことで、その引数の一部がもう使用されない（デッドになる）可能性があります。この関数は、デッドになった値が占有していたレジスタを解放します。`freeUseRecords`プールを活用して`use`オブジェクトを再利用します。

### 6. `allocReg` 関数のスピル選択ロジックの改善

レジスタが不足し、スピルが必要になった場合、`allocReg`関数は、レジスタに保持されている値の中で「次回の使用が最も遠い」値を選択してスピルするようになりました。これは、`s.values[v.ID].uses.dist`（連結リストの先頭にある次回の使用までの距離）を比較することで実現されます。これにより、最適なページ置換アルゴリズム（将来最も長く使われないものを置換する）と同様のヒューリスティックが適用されます。

### 7. `sparsemap.go` の追加

このファイルでは、`sparseMap`というデータ構造が定義されています。
```go
type sparseEntry struct {
	key ID
	val int32
}

type sparseMap struct {
	dense  []sparseEntry
	sparse []int
}
```
`sparseMap`は、`dense`配列と`sparse`配列の2つの配列を使って、疎なセットを効率的に表現します。
*   `dense`配列には、実際にセットに含まれる要素が格納されます。
*   `sparse`配列は、各要素のIDから`dense`配列内の位置へのマッピングを提供します。
この構造により、`contains`, `set`, `remove`, `clear`といった操作が高速（ほぼO(1)）で実行できます。これは、ライブネス解析のように多数の変数の中からライブなものを頻繁にチェック・更新する処理において、パフォーマンス上の大きな利点となります。

## コアとなるコードの解説

### `regalloc.go` の変更点

1.  **`use` 構造体と `valState` 構造体の変更**:
    `use`構造体が`dist`と`next`ポインタを持つ連結リストのノードとなり、`valState`の`uses`フィールドがこの連結リストの先頭を指すようになりました。これにより、各値のブロック内での使用箇所が、ブロック開始からの距離順に効率的に管理されます。これは、ライフタイムホールを検出し、次回の使用までの距離を正確に計算するための基盤となります。

2.  **`regAllocState` の `live` フィールドと `computeLive` メソッド**:
    `regAllocState.live`が`[][]liveInfo`型に変更され、各ブロックの終端でライブな値とその次回の使用までの距離を保持するようになりました。`computeLive`メソッドは、この`live`情報を計算する役割を担います。
    特に注目すべきは、`computeLive`内で導入されたエッジの重み付けです。`normalEdge`, `likelyEdge`, `unlikelyEdge`といった定数を使って、分岐の可能性に応じて次回の使用までの距離に異なる重みを加算しています。これにより、コンパイラはより頻繁に実行されるパス上の使用を優先し、スピルを避けるようなレジスタ割り当てを行うことができます。

3.  **`addUse` と `advanceUses` メソッド**:
    *   `addUse`は、値の新しい使用を`valState.uses`の連結リストに距離順に追加します。`freeUseRecords`プールから`use`オブジェクトを取得することで、メモリ割り当てのオーバーヘッドを削減します。
    *   `advanceUses`は、現在の命令が処理された後に、その命令の引数として使われた値の「次回の使用」を更新します。もし値のすべての使用が消費され、その値がデッドになった場合、`freeRegs`を呼び出してその値が占有していたレジスタを解放します。これにより、ライフタイムホールが検出され、レジスタが早期に解放されることで、他の値に再利用される機会が増えます。

4.  **`allocReg` メソッドのスピルロジック**:
    レジスタが不足した際にスピルするレジスタを選択するロジックが改善されました。以前は`len(s.values[v.ID].uses) == 0`や`s.values[v.ID].uses[0]`で次回の使用を判断していましたが、変更後は`s.values[v.ID].uses.dist`（連結リストの先頭にある次回の使用までの距離）を直接参照し、最も遠い将来に使用される値をスピル対象として選択します。これは、理論的に最適なページ置換アルゴリズム（OPTアルゴリズム）のヒューリスティックを模倣しており、スピルのコストを最小化することを目指します。

### `sparsemap.go` の追加

このファイルは、`sparseMap`という汎用的なデータ構造を導入しています。`sparseMap`は、疎なセット（多くの要素がデフォルト値であるセット）を効率的に管理するために設計されています。`dense`配列と`sparse`配列を組み合わせることで、要素の追加、削除、検索といった操作を平均的にO(1)の時間計算量で実行できます。

*   `dense`配列は、実際にセットに含まれる`sparseEntry`（キーと値のペア）を格納します。
*   `sparse`配列は、キー（値のID）から`dense`配列内の対応するエントリのインデックスへのマッピングを提供します。

この`sparseMap`は、`computeLive`関数内でライブネスセットを管理するために使用されます。多数の変数の中からライブな変数を効率的に追跡し、その次回の使用までの距離を更新する際に、このデータ構造がパフォーマンス上のボトルネックになるのを防ぎます。

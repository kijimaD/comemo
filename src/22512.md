# [インデックス 22512] ファイルの概要

このコミットは、Goランタイムに`GODEBUG=sbrk=1`というデバッグオプションを追加し、標準のメモリ割り当てとガベージコレクション（GC）のメカニズムをバイパスする機能を提供します。この変更は、特にデバッグ目的で、Goプログラムのメモリ動作をより低レベルで観察できるようにすることを目的としています。また、このモードでのロック競合を減らすために、永続的な割り当て状態をP（プロセッサ）ごとに管理するように変更されています。

## コミット

`runtime: add GODEBUG=sbrk=1 to bypass memory allocator (and GC)`

このコミットは、Goランタイムのメモリ管理に関する重要な変更を導入しています。具体的には、`GODEBUG=sbrk=1`という環境変数を設定することで、Goの通常のメモリ割り当てメカニズムとガベージコレクタを無効化し、代わりに`sbrk`システムコールを用いた単純なメモリ割り当てに切り替える機能を追加します。これにより、デバッグや特定のパフォーマンス分析において、Goランタイムのメモリ管理層を介さずに直接OSからメモリを確保する挙動をシミュレートできるようになります。

さらに、この`sbrk`モードでのロック競合を軽減するため、永続的なメモリ割り当ての状態を各P（Goスケジューラにおける論理プロセッサ）ごとに持つように変更されています。これにより、`GOMAXPROCS`の値に応じて最大64KB程度のオーバーヘッドが発生するものの、これは許容範囲内であるとされています。

## 変更の背景

Goランタイムは、高度に最適化された独自のメモリ割り当て器とガベージコレクタ（GC）を備えています。これらは通常、アプリケーションのパフォーマンスとメモリ効率を最大化するために設計されています。しかし、特定のデバッグシナリオや、メモリリークの根本原因を特定する際、あるいはGoランタイム自体のメモリ管理の挙動を詳細に分析する際に、標準のメモリ管理層が複雑さを増すことがあります。

このコミットの背景には、以下のような目的があったと考えられます。

1.  **デバッグの簡素化**: GoのGCやメモリ割り当て器が関与しない、より単純なメモリ割り当てモデルを提供することで、特定のメモリ関連のバグ（例えば、OSレベルでのメモリ使用量の異常な増加など）のデバッグを容易にする。
2.  **メモリリークの特定**: GoのGCがメモリを解放しているにもかかわらず、プロセス全体のメモリ使用量が増加し続けるようなケース（例えば、Cgoを介したCライブラリでのメモリリークなど）において、Goランタイムのメモリ管理を切り離して問題の切り分けを行う。
3.  **低レベルな挙動の観察**: `sbrk`システムコールを直接使用する挙動をシミュレートすることで、OSとGoランタイム間のメモリインタラクションをより直接的に観察できるようにする。
4.  **ロック競合の軽減**: `sbrk`モードのような特殊なケースにおいても、パフォーマンスのボトルネックとならないよう、永続的な割り当てにおけるロック競合を最小限に抑える設計を導入する。

この機能は、一般的なアプリケーション開発者が日常的に使用するものではなく、Goランタイムの開発者や、Goのメモリ管理の深い知識を持つユーザーが、特定の高度なデバッグや分析を行うためのツールとして提供されています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての前提知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理するシステム。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て器、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。

2.  **メモリ割り当て器 (Memory Allocator)**:
    プログラムが実行時にメモリを要求した際に、OSから取得した大きなメモリ領域（ヒープ）を管理し、小さなチャンクに分割してプログラムに提供するコンポーネント。Goのメモリ割り当て器は、オブジェクトのサイズやGCの効率を考慮して最適化されています。

3.  **ガベージコレクタ (Garbage Collector, GC)**:
    プログラムが不要になったメモリ領域を自動的に識別し、解放するシステム。GoのGCは、並行（Concurrent）かつ低遅延（Low-latency）なマーク＆スイープ方式を採用しており、プログラムの実行と並行して動作することで、アプリケーションの一時停止時間を最小限に抑えます。

4.  **`sbrk` システムコール**:
    Unix系OSで利用されるシステムコールの一つで、プロセスのデータセグメント（ヒープ）の「プログラムブレーク」（ヒープの終端）を増減させることで、メモリを動的に割り当てるために使用されます。`sbrk`は、OSからメモリを要求する最も基本的な方法の一つですが、現代のOSではより柔軟で効率的な`mmap`などのシステムコールが一般的に使用されます。`sbrk`は一度割り当てたメモリをOSに返却する機能を持たないため、メモリリークが発生しやすい特性があります。

5.  **`GODEBUG` 環境変数**:
    Goランタイムのデバッグオプションを設定するための環境変数。`GODEBUG=key=value`の形式で設定し、ランタイムの挙動を細かく制御できます。例えば、`GODEBUG=gcdead=1`でGCのデバッグ情報を出力したり、`GODEBUG=gctrace=1`でGCのトレース情報を出力したりできます。

6.  **P (Processor)**:
    Goスケジューラにおける論理プロセッサ（またはコンテキスト）。Goランタイムは、OSのスレッド（M: Machine）上でPを動かし、P上でゴルーチン（G: Goroutine）を実行します。Pは、ゴルーチンの実行に必要なリソース（ローカルキュー、メモリキャッシュなど）を管理します。`GOMAXPROCS`環境変数で設定される値は、同時に実行可能なPの最大数を決定します。

7.  **ロック競合 (Lock Contention)**:
    複数のゴルーチンやスレッドが同時に共有リソース（メモリ領域など）にアクセスしようとした際に、ロック（ミューテックスなど）の取得を巡って発生する競合状態。ロック競合が多いと、プログラムの並行性が低下し、パフォーマンスが劣化します。

8.  **永続的な割り当て (Persistent Allocation)**:
    Goランタイム内部で、GCの対象とならない、あるいはGCのサイクルとは独立して管理されるメモリ割り当て。例えば、ランタイムの内部データ構造や、型情報、デバッグ情報など、プログラムの実行期間中ずっと存在し続ける必要のあるデータに用いられます。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのメモリ割り当てパスに`GODEBUG=sbrk=1`という新しい分岐を追加することにあります。

1.  **`GODEBUG=sbrk=1`の有効化**:
    `src/runtime/runtime1.go`と`src/runtime/runtime2.go`で、`debug`構造体に`sbrk`フィールドが追加され、`dbgvars`配列に登録されます。これにより、`GODEBUG=sbrk=1`を設定することで、ランタイム内部の`debug.sbrk`変数が1に設定され、この特殊なモードが有効になります。

2.  **`mallocgc`のバイパス**:
    `src/runtime/malloc.go`の`mallocgc`関数（Goのオブジェクト割り当ての主要なエントリポイント）に、`debug.sbrk != 0`のチェックが追加されます。この条件が真の場合、通常のGC対象となるメモリ割り当てパス（スパンの取得、GCヘルプなど）を完全にスキップし、代わりに`persistentalloc`関数を呼び出します。これは、`sbrk`モードではGCが動作しないため、GCのオーバーヘッドを排除し、純粋な`sbrk`ベースの割り当てをシミュレートするためです。

3.  **`persistentalloc`の変更とPごとの割り当て**:
    `persistentalloc`関数は、元々GCの対象とならない永続的なメモリを割り当てるために使用されていました。このコミットでは、`persistentalloc`の内部ロジックが大幅に変更され、`sbrk`モードでの主要な割り当てメカニズムとして機能するように拡張されています。
    -   **`persistentAlloc`構造体**: `base`（割り当てられたメモリブロックの基底アドレス）と`off`（現在のオフセット）を持つ`persistentAlloc`という新しい構造体が定義されます。
    -   **Pごとの`persistentAlloc`**: `src/runtime/runtime2.go`の`p`構造体に`palloc persistentAlloc`フィールドが追加されます。これにより、各論理プロセッサ（P）が独自の永続割り当て状態を持つことができるようになります。
    -   **ロック競合の軽減**: `persistentalloc`関数内で、現在のM（OSスレッド）に紐付けられたPが存在する場合（`mp != nil && mp.p != nil`）、そのPの`palloc`フィールドを使用します。これにより、複数のPが同時にメモリを割り当てようとした際に、Pごとの独立した状態を使用することで、グローバルなロック（`globalAlloc.mutex`）の競合を大幅に減らすことができます。Pが存在しない場合（例えば、ランタイムの初期化フェーズなど）、フォールバックとして`globalAlloc`というグローバルな`persistentAlloc`構造体とそれに関連するミューテックスを使用します。
    -   **`sbrk`の挙動**: `persistentalloc`は、`sysAlloc`（OSからメモリを要求する関数）を呼び出して、`chunk`サイズ（通常は64KB）のメモリブロックを一度に取得します。その後、このブロック内から要求されたサイズのメモリをオフセットを移動させることで提供します。`sbrk`の特性上、一度取得したメモリはOSに返却されません。

4.  **ファイナライザの無効化**:
    `src/runtime/mfinal.go`の`SetFinalizer`関数に、`debug.sbrk != 0`のチェックが追加されます。`sbrk`モードではメモリが解放されないため、ファイナライザが実行されることはありません。したがって、このモードが有効な場合は、ファイナライザの設定を早期にリターンすることで、不要な処理やデータ構造の構築を避けます。

この変更により、`GODEBUG=sbrk=1`が設定されたGoプログラムは、通常のGCサイクルから完全に切り離され、OSの`sbrk`システムコールに近い挙動でメモリを消費するようになります。これは、メモリ使用量の増加がGoのGCによるものなのか、それともGoランタイムが管理していない外部の要因（Cgoなど）によるものなのかを切り分ける際に非常に有用です。

## コアとなるコードの解説

### `src/runtime/malloc.go`

-   **`mallocgc`関数の変更**:
    -   `debug.sbrk != 0`という条件が追加され、`GODEBUG=sbrk=1`が設定されている場合に、通常のメモリ割り当てパスをスキップし、`persistentalloc`関数を呼び出すように変更されています。これにより、GCの介入なしにメモリが割り当てられます。
    -   `persistentalloc`に渡される`align`引数は、割り当てるメモリのアライメント（メモリ配置の制約）を指定します。これは、特定のデータ型が特定のバイト境界に配置される必要がある場合に重要です。

-   **`persistentAlloc`構造体と`globalAlloc`**:
    -   `persistentAlloc`は、`sbrk`モードでのメモリ割り当ての状態（基底アドレスとオフセット）を保持するための新しい構造体です。
    -   `globalAlloc`は、Pに紐付けられない場合のフォールバックとして使用されるグローバルな`persistentAlloc`インスタンスであり、ミューテックス（`mutex`）によって保護されます。

-   **`persistentalloc`関数の変更**:
    -   この関数は、Goランタイムが内部的に使用する永続的なメモリ（GCの対象外）を割り当てるためのものです。このコミットにより、`sbrk`モードでの主要なメモリ割り当てメカニズムとして機能するように拡張されました。
    -   `mp := acquirem()`と`releasem(mp)`は、現在のM（OSスレッド）を取得・解放するGoランタイムの内部関数です。これにより、現在の実行コンテキスト（P）にアクセスできるようになります。
    -   `if mp != nil && mp.p != nil { persistent = &mp.p.palloc } else { ... }`の部分が、Pごとの割り当て状態を使用するか、グローバルな割り当て状態を使用するかを決定する重要なロジックです。これにより、Pが存在する場合はPローカルな`palloc`を使用し、ロック競合を避けます。
    -   `persistent.off = round(persistent.off, align)`は、割り当てられたメモリが指定されたアライメントに合うようにオフセットを調整します。
    -   `if persistent.off+size > chunk || persistent.base == nil { ... }`は、現在のチャンクに十分なスペースがない場合や、まだチャンクが割り当てられていない場合に、`sysAlloc`を呼び出して新しい`chunk`（通常64KB）をOSから取得します。
    -   `p := add(persistent.base, persistent.off)`は、基底アドレスとオフセットから実際のメモリポインタを計算します。
    -   `persistent.off += size`は、次の割り当てのためにオフセットを更新します。
    -   ロックの取得と解放（`lock(&globalAlloc.mutex)`と`unlock(&globalAlloc.mutex)`）は、グローバルな`globalAlloc`を使用する場合にのみ行われます。Pごとの`palloc`を使用する場合は、Pローカルであるためロックは不要です。

### `src/runtime/mfinal.go`

-   **`SetFinalizer`関数の変更**:
    -   `if debug.sbrk != 0 { return }`というチェックが追加されました。`sbrk`モードではメモリがOSに返却されないため、オブジェクトが「解放される」という概念がなく、したがってファイナライザが実行される機会もありません。このため、ファイナライザの設定自体を無効にすることで、不要な処理やリソースの消費を防ぎます。

### `src/runtime/runtime1.go`

-   **`debug`構造体と`dbgvars`の変更**:
    -   `debug`構造体に`sbrk int32`フィールドが追加され、`GODEBUG=sbrk=1`によってこのフィールドが設定されるようになります。
    -   `dbgvars`配列に`{"sbrk", &debug.sbrk}`が追加され、`GODEBUG`環境変数から`sbrk`オプションをパースできるようにします。

### `src/runtime/runtime2.go`

-   **`p`構造体の変更**:
    -   `p`構造体に`palloc persistentAlloc`フィールドが追加されました。これにより、各論理プロセッサ（P）が独自の`persistentAlloc`インスタンスを持つことができ、`sbrk`モードでのメモリ割り当て時にグローバルロックの競合を避けることが可能になります。

これらの変更により、`GODEBUG=sbrk=1`が設定されたGoプログラムは、通常のGoのメモリ管理とは異なる、より低レベルで直接的なOSとのメモリインタラクションを行うようになります。これは、Goランタイムの内部動作を深く理解し、特定のデバッグシナリオに対応するための強力なツールとなります。

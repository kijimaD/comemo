## 元コミット内容

`net/textproto: permit all valid token chars in CanonicalMIMEHeaderKey input`

このコミットは、`net/textproto`パッケージの`CanonicalMIMEHeaderKey`関数が、入力としてRFC 7230で定義されているすべての有効なトークン文字を許可するように変更します。これにより、Issue #13767で報告された問題が修正されます。

## 変更の背景

Goの`net/textproto`パッケージは、HTTPやMIMEなどのテキストベースのプロトコルで共通の機能を提供します。特に`CanonicalMIMEHeaderKey`関数は、HTTPヘッダーフィールド名などを正規化するために使用されます。

以前の実装では、`validHeaderFieldByte`関数がヘッダーフィールド名に許可される文字を厳しく制限していました。具体的には、英数字とハイフンのみを有効としていました。しかし、HTTP/1.1の仕様を定義するRFC 7230では、ヘッダーフィールド名（`field-name`）は`token`として定義されており、`token`は`tchar`（トークン文字）の1つ以上のシーケンスであるとされています。この`tchar`には、英数字、ハイフンだけでなく、`!`, `#`, `$`, `%`, `&`, `'`, `*`, `+`, `.`, `^`, `_`, `` ` ``, `|`, `~`といった記号も含まれます。

この不一致により、RFC 7230に準拠した有効なヘッダーフィールド名が`net/textproto`パッケージによって正しく処理されない、または不正なものとして扱われる可能性がありました。特に、一部のサーバーがCGI環境変数へのマッピングの曖昧さを避けるために`_`（アンダースコア）をドロップする歴史的経緯があったため、Goの実装もこれに影響を受けていた可能性があります。

このコミットは、この仕様の不一致を解消し、`CanonicalMIMEHeaderKey`がRFC 7230の定義に完全に準拠するようにすることで、より堅牢で互換性のあるヘッダー処理を実現することを目的としています。Issue #13767はこの問題点を指摘したものです。

## 前提知識の解説

### HTTPヘッダーフィールド名とRFC 7230

HTTPメッセージは、ヘッダーフィールドと呼ばれるメタデータを含んでいます。各ヘッダーフィールドは「フィールド名: フィールド値」の形式を取ります。この「フィールド名」の構文は、HTTP/1.1の仕様であるRFC 7230のセクション3.2.6「Field Line Parsing」で定義されています。

*   **`header-field`**: `field-name ":" OWS field-value OWS`
*   **`field-name`**: `token`
*   **`token`**: `1*tchar` (1つ以上の`tchar`のシーケンス)
*   **`tchar` (トークン文字)**:
    `!` / `#` / `$` / `%` / `&` / `'` / `*` / `+` / `-` / `.` /
    `^` / `_` / `` ` `` / `|` / `~` / `DIGIT` (0-9) / `ALPHA` (A-Z, a-z)

つまり、HTTPヘッダーフィールド名には、英数字とハイフンだけでなく、上記に挙げられた多くの記号も使用できるとRFC 7230は規定しています。

### `net/textproto`パッケージ

Go言語の標準ライブラリである`net/textproto`パッケージは、HTTP、NNTP、SMTPなどのテキストベースのネットワークプロトコルを実装するための低レベルなプリミティブを提供します。このパッケージには、ヘッダーの読み書き、MIMEパートの解析など、共通のテキストプロトコル操作を支援する機能が含まれています。

*   **`CanonicalMIMEHeaderKey(s string) string`**: この関数は、与えられた文字列`s`をMIMEヘッダーキーの標準的な形式（例: "Content-Type"）に正規化します。通常、これは最初の文字とハイフンの後の文字を大文字にし、それ以外の文字を小文字にする処理を含みます。この正規化処理の過程で、入力文字列が有効なヘッダーキーであるかどうかのチェックも行われます。

### `net/http/lex.go`

`net/http`パッケージはHTTPクライアントとサーバーの実装を提供しますが、その内部にはHTTPプロトコルの字句解析（lexical analysis）を行うためのヘルパー関数やデータ構造が含まれています。`lex.go`のようなファイルには、HTTPトークンや文字の有効性をチェックするためのテーブルなどが定義されていることがあります。このコミットでは、`net/http`パッケージで既に定義されている、RFC 7230に準拠したトークン文字の定義を再利用しています。

## 技術的詳細

このコミットの主要な変更点は、`src/net/textproto/reader.go`ファイル内の`validHeaderFieldByte`関数の実装です。

**変更前**:
`validHeaderFieldByte`関数は、バイト`b`が有効なヘッダーフィールドキーのバイトであるかを判定するために、以下のような条件式を使用していました。

```go
func validHeaderFieldByte(b byte) bool {
	return ('A' <= b && b <= 'Z') ||
		('a' <= b && b <= 'z') ||
		('0' <= b && b <= '9') ||
		b == '-'
}
```
これは、大文字、小文字の英字、数字、およびハイフンのみを有効としていました。コメントには「これは実際にはRFC 7230よりも厳格である」と明記されており、将来的に拡張する可能性が示唆されていました。

**変更後**:
`validHeaderFieldByte`関数は、`isTokenTable`という新しいグローバル変数（バイト配列をbool値でインデックス付けしたもの）を参照するように変更されました。

```go
func validHeaderFieldByte(b byte) bool {
	return int(b) < len(isTokenTable) && isTokenTable[b]
}
```
`isTokenTable`は、`net/http/lex.go`からコピーされたもので、RFC 7230で定義されているすべての`tchar`（トークン文字）を`true`としてマークする`[127]bool`型の配列です。これにより、`validHeaderFieldByte`は、ASCII範囲内のすべての有効なトークン文字を効率的にチェックできるようになりました。

この変更により、`CanonicalMIMEHeaderKey`関数が内部で`validHeaderFieldByte`を呼び出す際に、`_`, `$`, `~`, `*`などの文字を含むヘッダーフィールド名も有効なものとして認識し、正規化処理を進めることができるようになります。

また、`src/net/textproto/reader_test.go`には、`foo-bar_baz`, `foo-bar$baz`, `foo-bar~baz`, `foo-bar*baz`といった新しいテストケースが追加され、これらの文字を含むヘッダーキーが正しく正規化されることを確認しています。

## コアとなるコードの変更箇所

### `src/net/textproto/reader.go`

- `validHeaderFieldByte`関数のロジックが変更され、`isTokenTable`を参照するようになりました。
- `isTokenTable`という`[127]bool`型のグローバル変数が追加され、RFC 7230の`tchar`定義に基づいて初期化されています。このテーブルは`net/http/lex.go`からコピーされたものです。
- 以前の`validHeaderFieldByte`関数のコメントが更新され、RFC 7230の`field-name`と`token`の定義が引用されています。

### `src/net/textproto/reader_test.go`

- `canonicalHeaderKeyTests`スライスに、`_`, `$`, `~`, `*`などの記号を含む新しいテストケースが追加されました。これにより、これらの文字が`CanonicalMIMEHeaderKey`によって正しく処理されることが検証されます。

## コアとなるコードの解説

### `src/net/textproto/reader.go`

```go
// 変更前のコメント (一部)
// TODO: revisit in Go 1.6+ and possibly expand this. But note that many
// servers have historically dropped '_' to prevent ambiguities when mapping
// to CGI environment variables.

// 変更後のコメント
// validHeaderFieldByte reports whether b is a valid byte in a header
// field name. RFC 7230 says:
//   header-field   = field-name ":" OWS field-value OWS
//   field-name     = token
//   tchar = "!" / "#" / "$" / "%" / "&" / "'" / "*" / "+" / "-" / "." /
//           "^" / "_" / "`" / "|" / "~" / DIGIT / ALPHA
//   token = 1*tchar
func validHeaderFieldByte(b byte) bool {
	return int(b) < len(isTokenTable) && isTokenTable[b]
}

// isTokenTable is a copy of net/http/lex.go's isTokenTable.
// See https://httpwg.github.io/specs/rfc7230.html#rule.token.separators
var isTokenTable = [127]bool{
	'!':  true,
	'#':  true,
	'$':  true,
	'%':  true,
	'&':  true,
	'\'': true,
	'*':  true,
	'+':  true,
	'-':  true,
	'.':  true,
	'0':  true,
	'1':  true,
	// ... (他のtchar文字の定義が続く)
	'z':  true,
	'|':  true,
	'~':  true,
}
```

`validHeaderFieldByte`関数は、入力バイト`b`が`isTokenTable`配列の有効なインデックス範囲内にあるかを確認し（`int(b) < len(isTokenTable)`）、その上で`isTokenTable[b]`の値（`true`または`false`）を返します。`isTokenTable`は、ASCII文字コードをインデックスとして使用し、その文字がRFC 7230の`tchar`である場合に`true`を格納するルックアップテーブルです。これにより、複雑な条件分岐なしに、非常に高速かつ正確に文字の有効性を判定できるようになりました。

この変更は、`CanonicalMIMEHeaderKey`関数が呼び出す`validHeaderFieldByte`の動作を変更することで、ヘッダーキーの正規化ロジック全体に影響を与えます。結果として、RFC 7230で許可されているすべてのトークン文字を含むヘッダーキーが、Goの`net/textproto`パッケージで正しく扱われるようになります。

### `src/net/textproto/reader_test.go`

```go
var canonicalHeaderKeyTests = []canonicalHeaderKeyTest{
	// ... 既存のテストケース ...

	// Other valid tchar bytes in tokens:
	{"foo-bar_baz", "Foo-Bar_baz"},
	{"foo-bar$baz", "Foo-Bar$baz"},
	{"foo-bar~baz", "Foo-Bar~baz"},
	{"foo-bar*baz", "Foo-Bar*baz"},

	// Non-ASCII or anything with spaces or non-token chars is unchanged:
	{"üser-agenT", "üser-agenT"},
	{"a B", "a B"},
	// ...
}
```
追加されたテストケースは、`_`、`$`、`~`、`*`といった記号がヘッダーキーに含まれていても、`CanonicalMIMEHeaderKey`がそれらを正しく保持し、他の部分（最初の文字やハイフンの後の文字）を適切に大文字化して正規化することを確認しています。これは、`validHeaderFieldByte`の変更が意図通りに機能していることを保証するために重要です。

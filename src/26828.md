## 変更の背景

このコミットは、GoプログラムがCgoを介してCコードと連携し、そのCコードが`ThreadSanitizer`（TSan）でコンパイルされている場合に発生する問題に対処するために導入されました。

GoとCgoを組み合わせたプログラムでは、Goのランタイムが独自のスケジューリングと同期メカニズムを持っています。一方、C/C++のThreadSanitizerは、C/C++のメモリモデルと同期プリミティブに基づいてデータ競合を検出します。この二つの異なる同期モデルが混在すると、Goコード内で正しく同期されているにもかかわらず、TSanがCコード側から見たときに「データ競合」と誤って報告してしまう「偽陽性（false positive）」の問題が発生していました。

偽陽性は、開発者が実際のバグではない警告に時間を費やすことになり、TSanの有用性を著しく損ないます。特に、TSanのようなツールでは、偽陽性を避けることが、偽陰性（false negative、実際のバグを見逃すこと）がある程度発生するよりも重要であるとされています。なぜなら、偽陽性はツールの信頼性を低下させ、開発者が警告を無視するようになる可能性があるためです。

このコミットの目的は、Cgoが生成するCコードにTSanのフックを挿入することで、Goの同期操作（特にGoルーチン間のハンドオフや共有メモリへのアクセス）をTSanに正しく認識させ、偽陽性を排除することにあります。

## 前提知識の解説

### Cgo

Cgoは、GoプログラムからCコードを呼び出すためのGoの機能です。Goのソースファイル内にCのコードを直接記述し、GoとCの間で関数呼び出しやデータ共有を行うことができます。Cgoは、Goのビルドプロセス中に、GoとCの間の橋渡しをするための特別なCコードとGoコードを生成します。

### ThreadSanitizer (TSan)

ThreadSanitizer (TSan) は、LLVM/ClangやGCCに統合されている動的解析ツールの一つで、マルチスレッドプログラムにおけるデータ競合（data race）を検出するために設計されています。データ競合は、複数のスレッドが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって順序付けされていない場合に発生する未定義動作（Undefined Behavior）です。TSanは、プログラムの実行中にメモリアクセスと同期操作を監視し、データ競合のパターンを検出すると警告を報告します。

TSanは、プログラムの実行速度を低下させ、メモリ使用量を増加させますが、見つけるのが非常に難しい種類のバグを特定するのに非常に効果的です。

### データ競合と同期

データ競合は、並行プログラミングにおける最も一般的なバグの一つです。これを防ぐためには、ミューテックス（mutex）、セマフォ、アトミック操作、チャネル（Goの場合）などの同期プリミティブを使用して、共有リソースへのアクセスを調整する必要があります。

TSanは、これらの同期プリミティブが正しく使用されているかを監視し、同期されていないアクセスを検出します。しかし、GoとCgoのように異なる言語のランタイムが混在する場合、一方のランタイムの同期プリミティブがもう一方のランタイムのTSanからは認識されず、誤った競合報告につながることがあります。

### `__tsan_acquire` と `__tsan_release`

ThreadSanitizerは、カスタム同期プリミティブや言語固有の同期メカニズムを認識するために、特定のフック関数を提供しています。`__tsan_acquire`と`__tsan_release`は、TSanに「ここでメモリの取得（ロック）が行われた」または「ここでメモリの解放（アンロック）が行われた」と明示的に伝えるための関数です。これらの関数を呼び出すことで、TSanはそれらの操作を同期イベントとして扱い、その後のメモリアクセスが正しく同期されていると判断できるようになります。

### `runtime.LockOSThread()`

Goの`runtime.LockOSThread()`関数は、現在のGoルーチンを現在のOSスレッドにロックします。つまり、そのGoルーチンは、`runtime.UnlockOSThread()`が呼び出されるまで、他のOSスレッドに移動することなく、そのOSスレッド上で実行され続けます。これは、特定のOSスレッドに依存するCライブラリ（例：OpenGLのコンテキストなど）を呼び出す場合や、スレッドローカルストレージを使用する場合など、Cgoとの連携で特に重要になることがあります。このコミットのテストコードで使われているのは、GoルーチンがOSスレッド間で移動することでTSanが混乱する可能性を排除し、CgoとTSanの相互作用をより明確にテストするためと考えられます。

## 技術的詳細

このコミットの核心は、`cmd/cgo`がGoとCの間の呼び出しを処理するために生成するCコードに、ThreadSanitizerのフックを戦略的に挿入することです。

具体的には、以下のシナリオでTSanフックが追加されます。

1.  **GoからCへの呼び出し（Cgo呼び出し）**: GoコードがC関数を呼び出す際、CgoはGoの引数をCの形式に変換し、C関数を呼び出すためのラッパー関数を生成します。このラッパー関数のCコード内で、C関数呼び出しの直前に`_cgo_tsan_acquire()`が、呼び出しの直後に`_cgo_tsan_release()`が挿入されます。これにより、Go側で同期された共有メモリへのアクセスがC側から行われる際に、TSanがGoの同期を認識できるようになります。
2.  **CからGoへの呼び出し（Go関数のエクスポート）**: CコードがGoによってエクスポートされたGo関数を呼び出す際も同様に、CgoはCからGo関数を呼び出すためのラッパーを生成します。このラッパー関数のCコード内で、Go関数呼び出しの直前に`_cgo_tsan_release()`が、呼び出しの直後に`_cgo_tsan_acquire()`が挿入されます。これは、Go関数が実行される間、TSanに対して「Goランタイムが同期を管理している」ことを伝え、Go関数が終了してCコードに戻る際に「Cの同期モデルに戻る」ことを伝えるためです。

`tsanProlog`という新しい定数が導入され、これには`_cgo_tsan_acquire`と`_cgo_tsan_release`のマクロ定義が含まれています。これらのマクロは、`__has_feature(thread_sanitizer)`が定義されている場合（つまり、コンパイラがThreadSanitizerをサポートしている場合）にのみ、実際の`__tsan_acquire`および`__tsan_release`関数呼び出しに展開されます。それ以外の場合は、何もしない空のマクロとして定義されます。これにより、TSanが有効でないビルドではオーバーヘッドが発生しないようになっています。

また、`_cgo_sync`という`long long`型のグローバル変数が`__attribute__ ((common))`付きで宣言されています。これは、TSanのフック関数に渡される「同期オブジェクト」として機能します。TSanは、このオブジェクトのアドレスを基に同期イベントを追跡します。`__attribute__ ((common))`は、リンカが複数の定義を単一の共通シンボルに解決することを許可するGCC拡張です。

テストスクリプト`misc/cgo/testsanitizers/test.bash`も更新され、ThreadSanitizerのテストが追加されました。これにより、TSanがサポートされている環境で、CgoとGoの連携が正しくデータ競合を報告しないことを検証できるようになりました。新しいテストファイル`tsan.go`と`tsan2.go`は、GoルーチンとCgoを組み合わせたシナリオで、TSanが偽陽性を報告しないことを確認するための具体的なテストケースを提供しています。これらのテストケースでは、`runtime.LockOSThread()`を使用してGoルーチンを特定のOSスレッドに固定し、Cgoを介してCの共有変数にアクセスしています。

    ```go

    #define _cgo_tsan_acquire()
    #define _cgo_tsan_release()
    #if defined(__has_feature)
    #if __has_feature(thread_sanitizer)
    #undef _cgo_tsan_acquire
    #undef _cgo_tsan_release

    long long _cgo_sync __attribute__ ((common));

    extern void __tsan_acquire(void*);
    extern void __tsan_release(void*);

    static void _cgo_tsan_acquire() {
    	__tsan_acquire(&_cgo_sync);
    ```

## コアとなるコードの解説

このコミットの最も重要な部分は、`src/cmd/cgo/out.go`における`tsanProlog`の定義と、それが生成されるCコードに挿入されるロジックです。

`tsanProlog`は、Cgoが生成するCファイルに含められるCコードのスニペットです。このスニペットは、コンパイラがThreadSanitizerをサポートしているかどうか（`__has_feature(thread_sanitizer)`）をチェックします。

*   **TSanが有効な場合**:
    *   `_cgo_tsan_acquire()`と`_cgo_tsan_release()`マクロが、それぞれ`__tsan_acquire(&_cgo_sync)`と`__tsan_release(&_cgo_sync)`という実際のTSanフック関数呼び出しに展開されます。
    *   `_cgo_sync`という`long long`型のグローバル変数が宣言されます。これは、TSanが同期イベントを追跡するための「同期オブジェクト」として機能します。`__attribute__ ((common))`は、この変数が複数の翻訳単位で定義されてもリンカがエラーを出さずに処理できるようにするためのものです。
    *   `__tsan_acquire(void*)`と`__tsan_release(void*)`は、ThreadSanitizerランタイムが提供する外部関数であり、TSanに特定のメモリ位置が同期的に取得または解放されたことを通知します。

*   **TSanが有効でない場合**:
    *   `_cgo_tsan_acquire()`と`_cgo_tsan_release()`マクロは、空の定義（`#define ...`）のままとなり、何もしません。これにより、TSanが有効でないビルドでは、これらのフックによるパフォーマンスオーバーヘッドが完全に回避されます。

この`tsanProlog`が、Cgoが生成するCコードの適切な場所に挿入されることで、GoとCの間の境界を越える際に、TSanに対してGoの同期セマンティクスが明示的に伝えられます。

*   **GoからCへの呼び出し時**: GoがC関数を呼び出す直前に`_cgo_tsan_acquire()`が、C関数から戻った直後に`_cgo_tsan_release()`が呼び出されます。これは、GoランタイムがCコードに制御を渡す際に、TSanに対して「Go側で管理されていた共有状態が、C側からアクセスされる可能性があるが、Go側では同期が取れている」ことを示唆します。C関数が実行されている間は、TSanはCの同期モデルで競合を検出します。
*   **CからGoへの呼び出し時**: CがエクスポートされたGo関数を呼び出す直前に`_cgo_tsan_release()`が、Go関数から戻った直後に`_cgo_tsan_acquire()`が呼び出されます。これは、CランタイムがGoコードに制御を渡す際に、TSanに対して「C側で管理されていた共有状態が、Go側からアクセスされる可能性があるが、Go側では同期が取れている」ことを示唆します。Go関数が実行されている間は、TSanはGoの同期モデルを考慮に入れる必要があります。

このメカニズムにより、Goのチャネルやミューテックスなどの同期プリミティブによって保護されたメモリアクセスが、Cgoを介してCコードから行われた場合でも、TSanがそれを正しく同期されたアクセスとして認識し、偽陽性を回避できるようになります。コミットメッセージにあるように、これにより一部の偽陰性が発生する可能性はありますが、TSanの目的においては偽陽性の回避がより重要であるという判断に基づいています。

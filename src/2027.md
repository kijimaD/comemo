## 元コミット内容

`document and partially fix a race`

## 変更の背景

このコミットの背景には、Go言語の初期のネットワークI/O処理における競合状態（race condition）の問題がありました。具体的には、`pollServer` がファイルディスクリプタ（FD）をポーリングリストに追加しようとする際に、別のゴルーチンがそのFDを閉じてしまう可能性があるという問題です。

このような状況では、`pollServer.AddFD` メソッドが、すでに閉じられた、あるいは再利用されて別の目的で開かれたFDに対して操作を行おうとし、予期せぬ動作やクラッシュを引き起こす可能性がありました。コミットメッセージの `TODO(rsc)` コメントにもあるように、この問題は「あるゴルーチンが読み取りを行い、別のゴルーチンが閉じている間の競合」を扱っていますが、完全な解決には至っていません。特に、FDが閉じられた後に同じ数値のFDが再利用された場合、誤ったFDを参照し続けるリスクが指摘されています。

この変更は、このような競合状態を部分的に緩和し、問題の存在をコードベースに明示的にドキュメント化することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **ファイルディスクリプタ (File Descriptor, FD)**:
    Unix系OSにおいて、ファイルやソケットなどのI/Oリソースを識別するためにカーネルがプロセスに割り当てる非負の整数です。プログラムはFDを通じてこれらのリソースにアクセスします。

*   **ポーリング (Polling)**:
    複数のI/Oリソース（FD）に対して、データが読み取り可能になったり、書き込み可能になったりするなどのイベントが発生したかどうかを効率的に監視するメカニズムです。`select`, `poll`, `epoll` (Linux), `kqueue` (FreeBSD/macOS) などが代表的なシステムコールです。Goの`pollServer`は、これらのOSネイティブなポーリングメカニズムを抽象化して利用しています。

*   **`pollServer`**:
    Go言語の初期のネットワークスタックにおいて、複数のネットワーク接続（ソケット）からのI/Oイベントを効率的に処理するために使用されていた内部コンポーネントです。これは、OSのポーリングメカニズム（例: `epoll`）をラップし、イベントが発生したFDをGoのランタイムに通知する役割を担っていました。

*   **`netFD`**:
    Go言語のネットワークパッケージ内部で使用される構造体で、OSのファイルディスクリプタ（`fd`フィールド）と、そのFDに関連するネットワーク接続の状態やメタデータ（読み書きのデッドライン、エラーチャネルなど）をカプセル化しています。

*   **競合状態 (Race Condition)**:
    複数の並行に実行される処理（この場合はゴルーチン）が共有リソース（この場合は`netFD`の`fd`フィールド）にアクセスし、その実行順序によって結果が非決定的に変わってしまう状態を指します。特に、あるゴルーチンがリソースを読み取っている間に、別のゴルーチンがそのリソースを変更または解放してしまう場合に問題が発生します。

*   **ゴルーチン (Goroutine)**:
    Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千、数万のゴルーチンを同時に実行することが可能です。ゴルーチンはGoランタイムによってスケジューリングされます。

*   **チャネル (Channel)**:
    Go言語におけるゴルーチン間の通信と同期のための主要なメカニズムです。チャネルを通じて値を送受信することで、共有メモリを直接操作することなく安全にデータをやり取りできます。このコミットでは、`fd.cr` (read channel) と `fd.cw` (write channel) が登場し、FDが閉じられた際にイベントを通知するために使われています。

## 技術的詳細

このコミットが対処しようとしている競合状態は、`pollServer.AddFD` メソッドが `netFD` オブジェクトからファイルディスクリプタ（`fd.fd`）を取得し、それをポーリングシステム（`s.poll.AddFD`）に登録するまでの間に発生します。

具体的なシナリオは以下の通りです。

1.  **ゴルーチンA** が `pollServer.AddFD(fd, mode)` を呼び出す。
2.  `AddFD` メソッド内で、`fd.fd` の値が読み取られる（例: `intfd := fd.fd;`）。
3.  **この直後、ゴルーチンB** が同じ `netFD` オブジェクトに関連するネットワーク接続を閉じ、その結果 `fd.fd` の値が `-1` など無効な値に設定される。
4.  さらに悪いことに、OSがその閉じられたFDの番号をすぐに再利用し、**ゴルーチンC** が新しいファイルやソケットを開き、偶然にも同じFD番号が割り当てられる。
5.  **ゴルーチンA** は、最初に読み取った（現在は無効または再利用された）`intfd` の値を使って `s.poll.AddFD(intfd, mode, false)` を呼び出す。

この結果、`pollServer` は意図しないFD（すでに閉じられたもの、または全く別の新しい接続に再利用されたもの）を監視しようとすることになり、プログラムのクラッシュ、不正なI/Oイベントの受信、またはセキュリティ上の脆弱性につながる可能性があります。

このコミットでは、この問題に対する部分的な対策として、`s.poll.AddFD` を呼び出す前に `fd.fd` の値が有効であるか（負の値でないか）をチェックするロジックが追加されました。

```go
intfd := fd.fd;
if intfd < 0 {
    // fd closed underfoot
    if mode == 'r' {
        fd.cr <- fd
    } else {
        fd.cw <- fd
    }
    return
}
```

このコードは、`fd.fd` をローカル変数 `intfd` にコピーし、その `intfd` が負の値（無効なFDを示すことが多い）である場合に、ポーリングシステムへの追加をスキップし、代わりに適切なチャネル（`fd.cr` または `fd.cw`）に `fd` オブジェクトを送信して処理を終了します。これにより、閉じられたFDに対してポーリング操作を行おうとする直接的なエラーは回避されます。

しかし、コミットメッセージの `TODO` にあるように、この修正は完全ではありません。特に、FDが閉じられた直後に同じFD番号が再利用された場合、このチェックではその新しいFDを誤って有効なものとして扱ってしまう可能性があります。完全な解決策としては、`Close` 操作も `pollServer` を通じて行うことや、I/O操作とFDのライフサイクル管理をより厳密に同期させることが示唆されています。

## コアとなるコードの解説

変更された `AddFD` メソッドのコア部分は以下の通りです。

```go
func (s *pollServer) AddFD(fd *netFD, mode int) {
    // TODO(rsc): This check handles a race between
    // one goroutine reading and another one closing,
    // but it doesn't solve the race completely:
    // it still could happen that one goroutine closes
    // but we read fd.fd before it does, and then
    // another goroutine creates a new open file with
    // that fd, which we'd now be referring to.
    // The fix is probably to send the Close call
    // through the poll server too, except that
    // not all Reads and Writes go through the poll
    // server even now.
    intfd := fd.fd; // fd.fd の値をローカル変数 intfd にコピー
    if intfd < 0 { // intfd が負の値（無効なFD）であるかチェック
        // fd closed underfoot (FDが予期せず閉じられた)
        if mode == 'r' { // 読み取りモードの場合
            fd.cr <- fd // 読み取りチャネルにfdを送信
        } else { // 書き込みモードの場合
            fd.cw <- fd // 書き込みチャネルにfdを送信
        }
        return // 処理を終了
    }
    // intfd が有効な場合、s.poll.AddFD を呼び出す
    if err := s.poll.AddFD(intfd, mode, false); err != nil {
        panicln("pollServer AddFD ", intfd, ": ", err.String(), "\n");
        return
    }

    var t int64;
    key := intfd << 1; // key の計算も intfd を使用
    if mode == 'r' {
        fd.ncr++;
        t = fd.rdeadline;
    }
    // ... (後続のロジック)
}
```

この変更の意図は、`fd.fd` の値が `s.poll.AddFD` に渡される直前に無効になっていないかを確認することです。

1.  **`intfd := fd.fd;`**: `fd.fd` の現在の値を `intfd` というローカル変数にコピーします。これにより、その後のチェックや `s.poll.AddFD` の呼び出しで、`fd.fd` が途中で変更されても、コピーされた値が使用されるようになります。これは、競合状態を完全に防ぐものではありませんが、少なくとも `fd.fd` の値が読み取られた瞬間のスナップショットを使用することを保証します。

2.  **`if intfd < 0 { ... }`**: コピーした `intfd` が負の値である場合、それはFDがすでに閉じられていることを示唆しています。この場合、`pollServer` にFDを追加しようとするとエラーになるため、処理を中断します。

3.  **`fd.cr <- fd` または `fd.cw <- fd`**: FDが閉じられていた場合、`fd` オブジェクト自体を対応するチャネル（読み取り用 `fd.cr` または書き込み用 `fd.cw`）に送信しています。これは、FDが閉じられたことを、そのFDを待機していたゴルーチンに通知するためのメカニズムと考えられます。これにより、ポーリングシステムに登録する代わりに、クリーンアップやエラーハンドリングのパスに処理を移すことができます。

4.  **`key := intfd << 1;`**: `pollServer` 内部でFDを識別するためのキーを生成する際にも、元の `fd.fd` ではなく、安全のためにコピーした `intfd` を使用するように変更されています。

このコミットは、Go言語の初期段階における並行処理の課題と、ランタイムレベルでの低レベルなリソース管理の複雑さを示しています。特に、ファイルディスクリプタのようなOSリソースのライフサイクル管理は、複数のゴルーチンが関与する場合に非常にデリケートな問題となります。

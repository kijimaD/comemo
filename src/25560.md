# [インデックス 25560] ファイルの概要

このコミットは、`cmd/go`ツールが`gccgo`コンパイラを使用する際に、Cgoパッケージのリンク方法を修正するものです。具体的には、静的ライブラリからCのグローバル変数が正しく初期化されない問題を解決するため、リンカオプション`--whole-archive`を常に使用するように変更しています。これにより、`gc`ツールチェインの挙動と一致させ、Cgoを介してGoコードから参照されるCのグローバル変数が確実にリンクされ、初期化されるようにします。

## 変更の背景

この変更の背景には、`gccgo`コンパイラと`cgo`を組み合わせて使用する際に発生していた特定の問題があります。Go言語は`cgo`を通じてC言語のコードと連携できますが、`gccgo`環境下でCの静的ライブラリをリンクする際に、Goコードから参照されるCのグローバル変数が正しく初期化されないケースがありました。

具体的には、Cのコードがグローバル変数のみを公開しており、そのグローバル変数がGoコードから参照されている場合、リンカがそのグローバル変数を含むオブジェクトファイルを静的ライブラリから取り込まないことがありました。これは、リンカのデフォルトの挙動として、明示的に参照されているシンボルを持つオブジェクトファイルのみを静的ライブラリから抽出するためです。もしCのコードがそのグローバル変数以外に何もエクスポートしていなければ、リンカはそのオブジェクトファイルが不要だと判断し、結果としてGo側から見たCのグローバル変数が未初期化の状態になってしまっていました。

この問題は、`gccgo`に対するバグとして[GCC Bugzilla PR68255](https://gcc.gnu.org/PR68255)で報告されました。このコミットは、この問題を解決し、`gccgo`の挙動を標準の`gc`ツールチェインの挙動と一致させることを目的としています。`gc`ツールチェインでは、このような状況でもCのグローバル変数が正しく初期化されるように処理されていました。

## 前提知識の解説

### Go言語とCgoの連携

Go言語は、`cgo`というメカニズムを通じてC言語のコードと相互運用できます。`cgo`を使用すると、Goプログラム内でCの関数を呼び出したり、Cのデータ構造を扱ったりすることが可能になります。`cgo`は、GoとCの間の橋渡しをするコードを生成し、Goのビルドプロセスの一部としてCコンパイラとリンカを呼び出します。

### `gccgo`と`gc`コンパイラの違い

Go言語には主に二つのコンパイラ実装があります。
*   **`gc`**: Goプロジェクトが公式に開発・提供している標準のコンパイラです。高速なコンパイル、優れた最適化、そして通常は静的リンクされたバイナリを生成します。
*   **`gccgo`**: GNU Compiler Collection (GCC) のフロントエンドとして実装されたGoコンパイラです。GCCの強力な最適化バックエンドを利用できるため、一部のCPUバウンドなプログラムでは`gc`よりも高速な実行が可能になることがあります。また、`gc`よりも幅広いアーキテクチャをサポートしています。しかし、コンパイル速度は`gc`に劣り、リンキングの挙動も`gc`とは異なる場合があります。特に、`gccgo`はデフォルトで`libgo`（`gccgo`用のGo標準ライブラリ）を動的にリンクすることが可能ですが、`gc`は通常、完全に静的なバイナリを生成します。

このコミットの問題は、`gccgo`のリンキング挙動に起因するものでした。

### リンカオプション`--whole-archive`と`--no-whole-archive`

これらのリンカオプションは、静的ライブラリ（`.a`ファイル）の処理方法を制御するために使用されます。

*   **`--whole-archive`**: 通常、リンカは静的ライブラリを処理する際、プログラムの他の部分から参照されているシンボルを定義するオブジェクトファイルのみをライブラリから抽出して最終的な実行可能ファイルに含めます。これは、最終的なバイナリサイズを削減するための最適化です。しかし、`--whole-archive`フラグが静的ライブラリの前に指定されると、リンカはその静的ライブラリ内の**すべての**オブジェクトファイルを、たとえ明示的に参照されていなくても、最終出力に含めるように強制されます。
    これは、以下のような場合に特に重要です。
    *   **グローバルオブジェクトのコンストラクタ/初期化子**: C++などで、グローバルオブジェクトのコンストラクタがプログラムの起動時に自動的に実行される必要がある場合、そのオブジェクトが直接呼び出されていなくても、`--whole-archive`によって確実に含まれるようにします。今回のGoのケースもこれに類似しており、Cのグローバル変数の初期化がこれに該当します。
    *   **循環依存**: 静的ライブラリ間に循環依存がある場合、`--whole-archive`がすべての必要なシンボルが含まれることを保証するのに役立つことがあります。

*   **`--no-whole-archive`**: `--whole-archive`の効果を打ち消すために使用されます。`--whole-archive`が適用された後、このフラグを指定することで、それ以降の静的ライブラリに対してはリンカのデフォルトの選択的インクルード挙動に戻します。`--whole-archive`と`--no-whole-archive`は通常ペアで使用され、特定のライブラリのみに`--whole-archive`の効果を適用するために使われます。これを怠ると、`--whole-archive`がシステムライブラリなどにも適用され、バイナリサイズの肥大化や多重定義エラーを引き起こす可能性があります。

### 静的ライブラリとシンボル解決の基本

静的ライブラリは、コンパイル済みのオブジェクトファイル（`.o`ファイル）を一つにまとめたアーカイブファイル（Unix系では`.a`）です。プログラムをビルドする際、リンカはこれらのライブラリから必要なコードやデータを抽出し、実行可能ファイルに結合します。シンボル解決とは、プログラム内で参照されている関数や変数の定義を、オブジェクトファイルやライブラリの中から見つけ出すプロセスです。リンカは、未解決のシンボルを解決するために、指定されたライブラリを検索します。

## 技術的詳細

このコミットが解決しようとしている問題は、`gccgo`が`cgo`で生成されたコードをリンクする際の、リンカのデフォルトの挙動と`--whole-archive`フラグの相互作用に深く関連しています。

`gccgo`は、GoコードとCコードをリンクする際に、GCCのリンカ（通常は`ld`）を使用します。リンカは、静的ライブラリ（`.a`ファイル）を処理する際、デフォルトでは「必要なものだけを取り込む」という最適化を行います。つまり、プログラムの他の部分（Goコードや他のCコード）から明示的に参照されているシンボル（関数や変数）を定義しているオブジェクトファイルのみを、静的ライブラリから抽出して最終的な実行可能ファイルに含めます。

問題が発生したのは、Cgoによって生成されたCのコードが、Goコードから参照されるCのグローバル変数を定義しているものの、そのグローバル変数自体がCの静的ライブラリ内で唯一の「外部から参照される」シンボルである場合です。このような状況では、リンカは、そのグローバル変数を定義しているオブジェクトファイルが、他のどのコードからも直接呼び出されていないと判断し、そのオブジェクトファイルを静的ライブラリから取り込まないことがありました。結果として、GoコードからそのCのグローバル変数にアクセスしようとすると、未初期化の状態であるか、あるいはシンボルが見つからないという問題が発生しました。

このコミットでは、`src/cmd/go/build.go`内の`gccgoToolchain`の`ld`メソッドを変更し、`gccgo`でパッケージをビルドする際に、常に`--whole-archive`リンカオプションを使用するようにしました。これにより、`cgo`によって生成されたCのコードを含む静的ライブラリがリンクされる際、そのライブラリ内のすべてのオブジェクトファイルが強制的に最終的なバイナリに含まれるようになります。たとえCのグローバル変数が直接呼び出されていなくても、その変数を定義しているオブジェクトファイルが確実にリンクされるため、Goコードから正しくアクセスし、初期化された値を得られるようになります。

この変更は、`gc`ツールチェインが同様のシナリオで既に採用している挙動を`gccgo`にも適用することで、両コンパイラ間の整合性を高め、`cgo`を使用する際の予期せぬ問題を回避します。

6.  **`misc/cgo/test/gcc68255/c.h`**:
    *   Cのヘッダファイルで、グローバル変数`v`を`extern void (*v)(void);`として宣言しています。

この変更は、`gccgo`ツールチェインがリンカ（`ld`）を呼び出す際のコマンドライン引数を調整しています。
変更前は、`ldBuildmode`（リンクモード、例えばCアーカイブやC共有ライブラリをビルドする場合）が特定の条件（`"c-archive"`または`"c-shared"`）を満たす場合にのみ、`--whole-archive`と`--no-whole-archive`のペアがリンカフラグに追加されていました。
しかし、このコミットでは、この条件分岐が削除され、`ldBuildmode`の値に関わらず、常に`"-Wl,--whole-archive"`と`"-Wl,--no-whole-archive"`が`afiles`（アーカイブファイル）を囲むように追加されるようになりました。

*   `"-Wl,"`: これは、`go build`コマンドがリンカにオプションを渡すためのプレフィックスです。`go build`は内部でCコンパイラ（`gcc`など）を呼び出し、そのCコンパイラがさらにリンカを呼び出すため、リンカオプションは`gcc`に渡す形で指定されます。
*   `--whole-archive`と`--no-whole-archive`のペアは、`afiles`（Goパッケージが依存するCの静的ライブラリなど）がリンカに渡される際に、そのアーカイブ内のすべてのオブジェクトファイルが強制的にリンクされることを保証します。これにより、Cのグローバル変数がGoコードから参照される際に、その変数を定義しているCのオブジェクトファイルがリンカによって省略されることを防ぎます。

### 新しいテストケースの解説

新しく追加された`misc/cgo/test/gcc68255`ディレクトリ内のファイル群は、この問題の再現と修正の検証のために作成されました。

*   **`misc/cgo/test/gcc68255/c.h`**:
    ```c
    extern void (*v)(void);
    ```
    Cのグローバル変数`v`を宣言しています。これは関数ポインタ型です。

*   **`misc/cgo/test/gcc68255/c.c`**:
    ```c
    static void f(void) {
    }

    void (*v)(void) = f;
    ```
    `f`という静的関数を定義し、その関数`f`へのポインタをグローバル変数`v`に代入して初期化しています。この`v`がGoコードから参照されるCのグローバル変数です。このCファイルは`v`以外に外部から参照されるシンボルをほとんど持たないため、リンカのデフォルトの挙動では`v`を含むオブジェクトファイルが省略される可能性がありました。

*   **`misc/cgo/test/gcc68255/a.go`**:
    ```go
    package gcc68255

    /*
    #include "c.h"
    */
    import "C"

    func F() bool {
    	return C.v != nil
    }
    ```
    `cgo`を使用して`c.h`をインポートし、Cのグローバル変数`C.v`にアクセスしています。`F()`関数は、`C.v`が`nil`でない（つまり、正しく初期化されている）場合に`true`を返します。

*   **`misc/cgo/test/gcc68255.go`**:
    ```go
    package cgotest

    import (
    	"testing"

    	"./gcc68255"
    )

    func testGCC68255(t *testing.T) {
    	if !gcc68255.F() {
    		t.Error("C global variable was not initialized")
    	}
    }
    ```
    このGoテストファイルは、`gcc68255`パッケージをインポートし、その中の`F()`関数を呼び出します。`F()`が`false`を返した場合（つまり、`C.v`が`nil`だった場合）、テストは失敗し、「C global variable was not initialized」というエラーメッセージを出力します。このテストは、`--whole-archive`の変更が正しく機能し、Cのグローバル変数が常に初期化されることを検証します。

## 変更の背景

このコミットは、Goの標準ライブラリである `net/http` パッケージにバンドルされている HTTP/2 実装を更新し、`TestConcurrentReadWriteReqBody_h2` というテストが失敗していた問題を修正します。このテストは、HTTP/2 におけるリクエストボディの同時読み書きの挙動を検証するものであり、その失敗は HTTP/2 ストリームの状態管理に潜在的なバグがあることを示唆していました。

具体的には、`net/http` パッケージは `golang.org/x/net/http2` のコードを内部的にバンドルして HTTP/2 サポートを提供しています。このコミットは、`x/net` リポジトリの特定のGitリビジョン `520af5de654d` に HTTP/2 実装を更新することで、この問題を解決しています。これは、HTTP/2 のヘッダー処理、特にヘッダーが複数のフレームに分割されている場合や、ストリームの終了を示すフラグの解釈に関する不具合が `x/net/http2` 側で修正されたことを意味します。

コミットメッセージにある `Fixes #13659` は、Goプロジェクトの内部的な課題追跡システムにおける問題番号を示しており、この問題が HTTP/2 の同時リクエストボディ処理に関連するバグであったことを裏付けています。

## 前提知識の解説

### HTTP/2 (Hypertext Transfer Protocol Version 2)

HTTP/2 は、HTTP/1.1 の後継として開発されたプロトコルです。主な特徴として以下が挙げられます。

*   **多重化 (Multiplexing)**: 単一のTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が解消され、効率が向上します。
*   **ストリーム (Stream)**: HTTP/2 における独立した双方向のバイトフローです。各リクエスト/レスポンスは独自のストリーム上で処理されます。
*   **フレーム (Frame)**: HTTP/2 の通信の基本単位です。ヘッダー、データ、設定など、様々な種類の情報がフレームとして送受信されます。
    *   **HEADERS フレーム**: HTTPヘッダーブロックの開始部分を運びます。
    *   **CONTINUATION フレーム**: 長いHTTPヘッダーブロックが `HEADERS` フレームに収まらない場合に、その続きを運びます。
    *   **END_HEADERS フラグ**: ヘッダーブロックの最後のフレームであることを示します。
    *   **END_STREAM フラグ**: ストリームの送信側がこれ以上データを送信しないことを示します。リクエストボディやレスポンスボディの終了を示すために使用されます。
*   **HPACK (Header Compression)**: HTTP/2 では、ヘッダーの冗長性を排除し、効率的な通信を実現するために HPACK という圧縮方式が採用されています。

### Goの `net/http` と `x/net/http2`

Go言語の標準ライブラリである `net/http` パッケージは、HTTP/1.1 および HTTP/2 のクライアントとサーバーの実装を提供します。HTTP/2 の機能は、主に `golang.org/x/net/http2` というエクステンションパッケージのコードを `net/http` が内部的にバンドルすることで実現されています。これにより、Goユーザーは追加のインポートなしに HTTP/2 を利用できます。

### HTTP/2 におけるリクエストボディの同時読み書き

HTTP/2 の多重化の特性上、単一のコネクション上で複数のリクエストが同時に処理されます。これには、リクエストボディの送信も含まれます。クライアントがリクエストボディを送信している最中に、サーバーからのレスポンスヘッダーを受信したり、あるいは別のストリームで別のリクエストを処理したりする可能性があります。このような状況下で、リクエストボディの読み書きが正しく同期され、ストリームの状態が正確に管理されることは、プロトコルの堅牢性にとって非常に重要です。特に、リクエストボディの途中でストリームが終了するようなケース（例えば、クライアントが途中で送信をキャンセルした場合など）のハンドリングは複雑になります。

## 技術的詳細

このコミットが修正する問題は、HTTP/2 ストリームの状態管理、特にヘッダーブロックの処理とストリームの終了に関するものでした。

HTTP/2 では、HTTPヘッダーは `HEADERS` フレームとそれに続く0個以上の `CONTINUATION` フレームによって構成されるヘッダーブロックとして送信されます。ヘッダーブロックの最後のフレームには `END_HEADERS` フラグが設定されます。また、リクエストやレスポンスのボディが伴わない場合や、ボディの送信が完了した場合には、`HEADERS` フレームに `END_STREAM` フラグが設定されることがあります。

元の `net/http` にバンドルされていた `x/net/http2` の実装では、これらのフラグの解釈とストリームの状態 (`headersDone`, `trailersDone`) の更新に不整合があったと考えられます。特に、`TestConcurrentReadWriteReqBody_h2` が失敗していたことから、リクエストボディの送信中にヘッダーやトレーラーの受信が絡むような、複雑な同時実行シナリオで問題が発生していたと推測されます。

このコミットによる `x/net/http2` の更新は、以下の点を改善しています。

1.  **より正確なストリーム状態の追跡**: `http2clientStream` 構造体内の `headersDone` と `trailersDone` フィールドがそれぞれ `pastHeaders` と `pastTrailers` にリネームされ、その意味合いがより明確になりました。また、`http2clientConnReadLoop` 構造体に `lastHeaderEndsStream` という新しいフィールドが追加され、直前に処理されたヘッダーフレームが `END_STREAM` フラグを持っていたかどうかを正確に追跡できるようになりました。これは、ヘッダーブロックが複数のフレームに分割されている場合に、ストリームの終了状態を正しく判断するために重要です。
2.  **ヘッダーブロック処理ロジックの改善**: `processHeaderBlockFragment` 関数は、ヘッダーブロックの断片を処理する中心的な役割を担います。この関数のシグネチャが変更され、`streamEnded` パラメータが削除され、代わりに `finalFrag` (最終的な断片かどうか) が導入されました。これにより、ヘッダーブロック全体の処理が完了した時点 (`finalFrag` が `true` の場合) でのみ HPACK デコーダをクローズし、ストリームの状態を更新するようになりました。また、`streamEnded` の判断には `rl.lastHeaderEndsStream` が利用されるようになり、より正確な状態遷移が可能になりました。
3.  **`100 Continue` レスポンスの特殊処理**: HTTP/1.1 と同様に、HTTP/2 でも `100 Continue` ステータスコードがサポートされます。これは、クライアントが大きなリクエストボディを送信する前に、サーバーがリクエストヘッダーを受け入れ、ボディの送信を継続してもよいことを示すものです。このコミットでは、`100 Continue` レスポンスを受信した場合に、`cs.pastHeaders` を `false` にリセットするロジックが追加されました。これにより、クライアントは `100 Continue` レスポンスを受け取った後も、リクエストボディの送信を継続できる状態を維持できます。もし `pastHeaders` が `true` のままだと、クライアントは既にヘッダー処理が完了したと誤解し、ボディの送信に問題が生じる可能性がありました。
4.  **`http2ContinuationFrame.StreamEnded()` の削除**: `http2ContinuationFrame` から `StreamEnded()` メソッドが削除されました。これは、ストリームの終了状態の判断が、個々のフレームレベルではなく、`http2clientConnReadLoop` のような上位のコンテキストで、`HEADERS` フレームの `END_STREAM` フラグと `CONTINUATION` フレームの `END_HEADERS` フラグを総合的に見て行われるようになったことを示唆しています。

これらの変更により、HTTP/2 ストリームの状態管理がより堅牢になり、特に同時実行環境下でのリクエストボディの処理における競合状態や不整合が解消され、`TestConcurrentReadWriteReqBody_h2` がパスするようになりました。

## コアとなるコードの解説

### `src/net/http/clientserver_test.go` の変更

*   `TestConcurrentReadWriteReqBody_h2` から `t.Skip("known failing; golang.org/issue/13659")` の行が削除されました。これは、このテストが以前は既知のバグのためにスキップされていたが、今回の `http2` の更新によってバグが修正され、テストが正常に実行できるようになったことを示しています。
*   コメント内の「fix this」が「change this」に変更されています。これは、HTTP/1.1 の実装における同時書き込みの制限に関するコメントであり、直接的な機能変更ではありませんが、コードの意図をより正確に反映するための微調整です。

### `src/net/http/h2_bundle.go` の変更

1.  **`http2ContinuationFrame.StreamEnded()` の削除**:
    *   以前は `http2ContinuationFrame` が `StreamEnded()` メソッドを持っていましたが、これが削除されました。これは、ストリームの終了状態の判断ロジックが、個々の `CONTINUATION` フレームから直接取得するのではなく、より上位の `http2clientConnReadLoop` コンテキストで、`HEADERS` フレームの `END_STREAM` フラグとヘッダーブロック全体の処理状況を総合的に判断するようになったことを示唆しています。これにより、ストリーム終了の判断が一元化され、より堅牢になります。

2.  **`http2clientStream` 構造体のフィールド名変更**:
    *   `headersDone` が `pastHeaders` に、`trailersDone` が `pastTrailers` に変更されました。これらのフィールドは、それぞれ初期ヘッダーとトレーラーヘッダーの処理が完了したかどうかを示すブール値です。名前の変更により、ヘッダーが「完了した」というよりは「過去に処理された」というニュアンスが強調され、ストリームの状態遷移をより正確に表現するようになりました。

3.  **`http2clientConnReadLoop` 構造体への `lastHeaderEndsStream` の追加**:
    *   `lastHeaderEndsStream bool` フィールドが追加されました。これは、直前に処理された `HEADERS` フレームが `END_STREAM` フラグを持っていたかどうかを記録します。ヘッダーブロックが `HEADERS` フレームとそれに続く `CONTINUATION` フレームで構成される場合、`END_STREAM` フラグは `HEADERS` フレームにのみ設定されます。このフィールドにより、`CONTINUATION` フレームを処理している間も、ヘッダーブロック全体の `END_STREAM` 状態を正確に把握できるようになります。

4.  **`processHeaders` 関数の変更**:
    *   `rl.lastHeaderEndsStream = f.StreamEnded()` が追加されました。これにより、`HEADERS` フレームが `END_STREAM` フラグを持っている場合、その状態が `lastHeaderEndsStream` に記録されます。
    *   `processHeaderBlockFragment` の呼び出しから `f.StreamEnded()` パラメータが削除され、代わりに `f.HeadersEnded()` (ヘッダーブロックの最終フレームかどうか) が渡されるようになりました。これは、ストリーム終了の判断が `processHeaderBlockFragment` 内で `lastHeaderEndsStream` を参照して行われるようになったためです。

5.  **`processContinuation` 関数の変更**:
    *   `processHeaderBlockFragment` の呼び出しから `f.StreamEnded()` パラメータが削除され、代わりに `f.HeadersEnded()` が渡されるようになりました。`CONTINUATION` フレーム自体は `END_STREAM` フラグを持たないため、この変更は理にかなっています。

6.  **`processHeaderBlockFragment` 関数の変更**:
    *   シグネチャが `func (rl *http2clientConnReadLoop) processHeaderBlockFragment(frag []byte, streamID uint32, headersEnded, streamEnded bool) error` から `func (rl *http2clientConnReadLoop) processHeaderBlockFragment(frag []byte, streamID uint32, finalFrag bool) error` に変更されました。
        *   `headersEnded` と `streamEnded` パラメータが削除され、代わりに `finalFrag` (現在の断片がヘッダーブロックの最終断片であるか) が導入されました。
    *   `streamEnded := rl.lastHeaderEndsStream` が追加され、ストリームの終了状態は `lastHeaderEndsStream` から取得されるようになりました。
    *   `cs := cc.streamByID(streamID, streamEnded && finalFrag)`: ストリームを取得する際に、ストリームが終了したと見なす条件が `streamEnded && finalFrag` となりました。これは、`END_STREAM` フラグが設定されており、かつ現在のヘッダーブロックの処理が完了した場合にのみ、ストリームが終了したと判断することを意味します。これにより、ヘッダーブロックが複数のフレームに分割されている場合でも、正確なストリーム終了のタイミングを捉えることができます。
    *   `if cs.headersDone` が `if cs.pastHeaders` に変更されました。
    *   `if finalFrag { if err := rl.hdec.Close(); err != nil { ... } }`: HPACK デコーダのクローズ処理が `finalFrag` の条件内で行われるようになりました。これにより、ヘッダーブロック全体の処理が完了した時点でデコーダがクローズされ、リソースが適切に解放されます。
    *   `if !finalFrag { return nil }`: ヘッダーブロックの最終断片でない場合は、処理を継続します。
    *   `if !cs.headersDone` が `if !cs.pastHeaders` に変更され、`cs.headersDone = true` が `cs.pastHeaders = true` に変更されました。
    *   `if cs.trailersDone` が `if cs.pastTrailers` に変更され、`cs.trailersDone = true` が `cs.pastTrailers = true` に変更されました。
    *   **`100 Continue` レスポンスのハンドリング**:
        ```go
        if res.StatusCode == 100 {
            cs.pastHeaders = false
            return nil
        }
        ```
        この新しいロジックは、受信したレスポンスのステータスコードが `100 (Continue)` である場合、`cs.pastHeaders` を `false` にリセットします。これは、クライアントが `100 Continue` を受け取った後もリクエストボディの送信を継続できる状態を維持するために重要です。もし `pastHeaders` が `true` のままだと、クライアントはヘッダー処理が完了したと誤解し、ボディの送信に問題が生じる可能性がありました。

これらの変更は、HTTP/2 の複雑なストリーム状態管理、特にヘッダーブロックの断片化と `END_STREAM` フラグの正確な解釈、そして `100 Continue` レスポンスの適切な処理を改善し、同時実行環境下での HTTP/2 通信の堅牢性を高めることを目的としています。

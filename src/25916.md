## 変更の背景

この変更は、GoのIssue #12705 に対応するものです。Goの `net/http` パッケージの `Client` は、通常、HTTPリクエストを送信し、必要に応じてリダイレクトを自動的に処理します。しかし、`http.Request` オブジェクトを作成する際に `Method` フィールドを明示的に設定せず、デフォルト値（空文字列）のまま `Client.Do` メソッドに渡した場合、リダイレクトが正しく処理されないという問題がありました。

HTTP/1.1の仕様（RFC 7231, Section 4.3.1）では、`Method` フィールドが指定されない場合、デフォルトで `GET` メソッドとして扱われるべきです。Goの `net/http` パッケージも、`Request.Method` が空の場合には `GET` として扱う内部ロジックを持っています。しかし、リダイレクト処理のパスでは、この「空のメソッドはGETとして扱う」というロジックが一部欠けており、特にリダイレクトを追跡する際に問題が発生していました。

このバグにより、開発者が `http.NewRequest` でリクエストを作成し、`Method` を設定せずに `Client.Do` を呼び出した場合、リダイレクトが発生するURLに対しては期待通りの動作をしない可能性がありました。このコミットは、この不整合を解消し、`Method` が空の場合でも `GET` リクエストとしてリダイレクトが適切に処理されるように修正することを目的としています。

## 前提知識の解説

### `net/http` パッケージ

`net/http` はGo言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。ウェブアプリケーションの構築やHTTPリクエストの送信に広く利用されます。

### `http.Client`

`http.Client` は、HTTPリクエストを送信し、HTTPレスポンスを受信するクライアントを表します。通常、リダイレクトの自動処理、クッキーの管理、プロキシ設定などの機能を提供します。`Client` の `Do` メソッドは、任意の `http.Request` を送信するための汎用的なインターフェースです。

### `http.Request`

`http.Request` は、クライアントがサーバーに送信するHTTPリクエストを表す構造体です。主要なフィールドには以下のようなものがあります。
- `Method`: HTTPメソッド（例: "GET", "POST", "PUT", "DELETE"）。このフィールドが空の場合、Goの `net/http` パッケージの内部では慣習的に "GET" として扱われることが多いです。
- `URL`: リクエストのターゲットURL。
- `Header`: リクエストヘッダー。
- `Body`: リクエストボディ（POSTやPUTなどで使用）。

### HTTPリダイレクト

HTTPリダイレクトは、サーバーがクライアントに対して、別のURLにリクエストを再送信するよう指示する仕組みです。これは、ウェブページの移動、URLの変更、負荷分散などの目的で使用されます。サーバーは `3xx` ステータスコード（例: `301 Moved Permanently`, `302 Found`, `307 Temporary Redirect`）と `Location` ヘッダーをクライアントに返します。クライアントは `Location` ヘッダーに指定されたURLに対して新しいリクエストを送信することでリダイレクトを追跡します。

`http.Client` はデフォルトでリダイレクトを自動的に追跡しますが、`Client.CheckRedirect` フィールドに関数を設定することで、この挙動をカスタマイズまたは無効化できます。

### `Client.Do` メソッド

`Client.Do(req *Request)` は、`http.Client` の最も汎用的なリクエスト送信メソッドです。`http.Request` オブジェクトを引数に取り、`http.Response` とエラーを返します。`Get`, `Post`, `PostForm` などのメソッドは、内部的に `Do` メソッドを呼び出すラッパーです。

## 技術的詳細

`net/http.Client` のリダイレクト処理は、主に `doFollowingRedirects` という内部メソッドによって行われます。このメソッドは、リクエストの `Method` に応じてリダイレクトの挙動を決定します。

コミット前のコードでは、`Client.Do` メソッドの冒頭で、リクエストの `Method` が `"GET"` または `"HEAD"` の場合にのみ `doFollowingRedirects` を呼び出す条件がありました。

```go
// src/net/http/client.go (before change)
func (c *Client) Do(req *Request) (resp *Response, err error) {
	if req.Method == "GET" || req.Method == "HEAD" {
		return c.doFollowingRedirects(req, shouldRedirectGet)
	}
	// ... other methods
}
```

このロジックの問題点は、`req.Method` が空文字列の場合に `doFollowingRedirects` が呼び出されないことでした。Goの `net/http` パッケージでは、`req.Method` が空の場合、それは `GET` リクエストとして扱われるべきであるという暗黙の了解があります。例えば、`http.NewRequest("GET", ...)` と `http.NewRequest("", ...)` は、多くの文脈で同じ `GET` リクエストとして機能します。しかし、リダイレクト処理の入り口では、この暗黙のルールが適用されていませんでした。

その結果、`req.Method` が空のリクエストがリダイレクトを伴うURLに送信された場合、`doFollowingRedirects` が呼び出されず、リダイレクトが追跡されないまま、最初のレスポンス（通常は `3xx` ステータスコード）がそのまま返されてしまうというバグが発生していました。これは、ユーザーが `http.NewRequest` を使用して `Method` を明示的に設定しない場合に特に顕著でした。

このコミットは、この問題を二段階で修正しています。

1.  **`Client.Do` メソッドの条件変更**: `req.Method` が空の場合も `doFollowingRedirects` が呼び出されるように条件を拡張します。これにより、空のメソッドを持つリクエストもリダイレクト追跡の対象となります。
2.  **`doFollowingRedirects` 内部でのメソッドの正規化**: `doFollowingRedirects` メソッド内で、リクエストの `Method` が空の場合に明示的に `"GET"` を設定するように変更します。これは、リダイレクト後のリクエストを構築する際や、エラーメッセージを生成する際に、正しいHTTPメソッドが使用されることを保証するためです。特に、`url.Error` の `Op` フィールドを生成する際に、メソッドの最初の文字を使用するロジックがあるため、空文字列ではパニックを引き起こす可能性がありました。

これらの変更により、`Request.Method` が空の場合でも、`net/http.Client` はHTTP仕様に則り、`GET` リクエストとしてリダイレクトを適切に処理できるようになります。

## コアとなるコードの解説

### `src/net/http/client.go` の変更点

1.  **`Client.Do` メソッドの条件変更**:
    変更前: `if req.Method == "GET" || req.Method == "HEAD" { ... }`
    変更後: `if req.Method == "" || req.Method == "GET" || req.Method == "HEAD" { ... }`
    この変更により、`req.Method` が空文字列の場合でも、`doFollowingRedirects` 関数が呼び出されるようになりました。これにより、空のメソッドを持つリクエストもリダイレクト追跡の対象となり、Issue #12705 で報告された問題が解決されます。HTTPの慣習として、メソッドが指定されない場合は `GET` と解釈されるべきであるという原則に合致するようになります。

2.  **`doFollowingRedirects` 内部でのメソッドの正規化**:
    `method := ireq.Method` の後に以下の行が追加されました。
    ```go
    if method == "" {
    	method = "GET"
    }
    ```
    このコードは、`doFollowingRedirects` 関数内で、リクエストの `Method` がまだ空の場合に、明示的に `"GET"` に設定します。これは、リダイレクトチェーンの途中で新しいリクエストを生成する際や、エラーメッセージ（特に `url.Error` の `Op` フィールド）を構築する際に、常に有効なHTTPメソッドが使用されることを保証します。`url.Error` の `Op` フィールドはメソッドの最初の文字を使用するため、`method` が空のままだとインデックスアクセスでパニックを引き起こす可能性がありました。この正規化により、堅牢性が向上します。

### `src/net/http/client_test.go` の変更点

既存の `TestClientRedirects` 関数に新しいテストケースが追加されました。
```go
	// Requests with an empty Method should also redirect (Issue 12705)
	greq.Method = ""
	_, err = c.Do(greq)
	if e, g := "Get /?n=10: stopped after 10 redirects", fmt.Sprintf("%v", err); e != g {
		t.Errorf("with default client Do and empty Method, expected error %q, got %q", e, g)
	}
```
このテストケースは、`http.Request` の `Method` フィールドを意図的に空文字列に設定し、そのリクエストを `Client.Do` メソッドで実行します。そして、リダイレクトが適切に追跡され、最終的にリダイレクト回数制限に達した際のエラーメッセージが期待通りであるかを確認します。このテストの追加により、Issue #12705 で修正されたバグが将来的に再発しないことが保証されます。

これらの変更は、Goの `net/http` クライアントの挙動をより直感的で、HTTP仕様に準拠したものにし、開発者が `Request.Method` を明示的に設定しない場合でも期待通りのリダイレクト処理が行われるように改善しています。

# [インデックス 25641] ファイルの概要

このコミットは、GoランタイムがPPC64アーキテクチャ上で使用するスタックフレームのサイズを調整し、特にPosition-Independent Code (PIC) のサポートを改善することを目的としています。具体的には、PPC64およびPPC64LE環境における固定スタックフレームサイズを8バイトから32バイトに拡張し、それに伴いスタックガードの調整も行っています。これにより、PICコードが要求するより大きなスタック領域に対応し、スタックオーバーフローの問題を防ぎます。

## 元コミット内容

`cmd/internal/obj`, `cmd/link`, `runtime`: ppc64上でより大きなスタックフレームを使用する

より大きなスタックフレームは、`nosplit`スタックをオーバーフローさせるため、次の変更でスタックガードを増加させます。

## 変更の背景

この変更の背景には、GoプログラムがPPC64アーキテクチャ上でPosition-Independent Code (PIC) をより適切にサポートする必要性がありました。PICは、コードがメモリ内の任意のアドレスにロードされても正しく実行されるように設計されたコードです。これは共有ライブラリや動的リンクにおいて非常に重要です。

PPC64LE (Little-Endian) 環境では、PICコードが関数呼び出しを行う際に、特定のレジスタを保存したり、プロシージャリンケージテーブル (PLT) を介して関数を呼び出すために、スタック上に最低32バイトの領域を必要とすることが知られています。Goランタイムの従来の固定スタックフレームサイズは8バイトであり、これはPPC64LEのPICコードが要求する最小スタックサイズよりも小さかったため、スタックオーバーフローや予期せぬ動作を引き起こす可能性がありました。

このコミットは、PPC64およびPPC64LEアーキテクチャにおける固定スタックフレームサイズを32バイトに統一することで、この問題を解決しようとしています。これにより、PICコードが安全に実行できる十分なスタック領域が確保されます。また、スタックフレームサイズの増加に伴い、`nosplit`関数（スタックチェックを行わない関数）がスタックをオーバーフローさせないように、スタックガードの調整も必要となりました。

## 前提知識の解説

### スタックフレーム (Stack Frame)
関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保されるメモリ領域のことです。Goランタイムでは、特定のアーキテクチャにおいて、関数呼び出しのオーバーヘッドを最小限に抑えるために、固定サイズのスタックフレームを予約することがあります。

### Position-Independent Code (PIC)
位置独立コード。実行時にメモリ上の任意のアドレスにロードされても正しく動作するコードのことです。共有ライブラリ（ダイナミックリンクライブラリ）などで広く利用されます。PICでは、絶対アドレスではなく、現在のプログラムカウンタからの相対アドレスを用いてデータや関数にアクセスします。PPC64アーキテクチャでは、PICを生成する際に、特定のレジスタを保存したり、関数呼び出しのためにスタック上に一定の領域を必要とすることが一般的です。

### PPC64 / PPC64LE
IBMが開発したPowerPCアーキテクチャの64ビット版です。
- **PPC64**: PowerPC 64-bit Big-Endian (ビッグエンディアン)
- **PPC64LE**: PowerPC 64-bit Little-Endian (リトルエンディアン)
Goは両方のエンディアンをサポートしており、それぞれで異なるアセンブリコードやランタイムの挙動が必要になる場合があります。特にPPC64LEはLinux環境で広く利用されています。

### `FIXED_FRAME`
Goランタイムのアセンブリコード内で定義される定数で、関数呼び出し時に予約される固定スタックフレームのサイズを示します。この領域は、レジスタの保存や引数の受け渡しなど、低レベルの処理に使用されます。

### `MinFrameSize`
Goランタイムの内部システムパッケージで定義される定数で、特定のアーキテクチャにおける最小スタックフレームサイズを示します。これは、Goのコンパイラやリンカがスタックフレームを生成する際の基準となります。

### スタックガード (Stack Guard)
Goランタイムは、スタックオーバーフローを防ぐために「スタックガード」と呼ばれるメカニズムを使用します。各ゴルーチンにはスタックの限界を示すポインタ（スタックガード）があり、関数呼び出し時にスタックがこの限界を超えそうになると、ランタイムはスタックを拡張します。`nosplit`関数はスタックチェックを行わないため、スタックガードの値を適切に設定することが重要です。

## 技術的詳細

このコミットは、PPC64およびPPC64LEアーキテクチャにおけるスタックフレームの管理方法を根本的に変更しています。

1.  **`FixedFrameSize`の変更**:
    `src/cmd/internal/obj/link.go` と `src/cmd/link/internal/ld/link.go` の両方で、`FixedFrameSize` 関数にPPC64 (Goアーキテクチャ文字 `'9'`) のケースが追加されました。これにより、PPC64LEのPICコードが要求する32バイトのスタックサイズに合わせて、`4 * ctxt.Arch.Ptrsize` (ポインタサイズが8バイトの場合、4 * 8 = 32バイト) が固定フレームサイズとして返されるようになります。これは、PPC64LEのPICコードが最低32バイトのスタックを必要とするためであり、PPC64アーキテクチャ全体でこのサイズを統一することで、実装の複雑さを軽減しています。

2.  **`FIXED_FRAME`の定義変更**:
    `src/runtime/asm_ppc64x.h` ファイルでは、`FIXED_FRAME` マクロの定義が条件付きコンパイル (`#ifdef GOARCH_ppc64` や `#ifdef GOARCH_ppc64le`) を廃止し、一律に `32` に変更されました。これにより、PPC64およびPPC64LEの両方で、アセンブリコードが固定スタックフレームとして32バイトを使用することが保証されます。元のコメントでは、PPC64LEのPICが32バイトを必要とすることが言及されており、PPC64のPICは48バイトを必要とする可能性も示唆されていますが、この変更ではPPC64x全体で32バイトに統一されています。

3.  **アセンブリコードのスタック調整**:
    `src/runtime/asm_ppc64x.s` ファイルでは、`runtime·newproc` および `runtime·mcall` の呼び出し前後のスタックポインタ (`R1`) の調整が変更されました。
    - `runtime·newproc` の呼び出し前には、スタックにレジスタを保存するために `MOVDU R0, -8(R1)` が追加され、スタックポインタの調整が `ADD $(16+FIXED_FRAME), R1` となりました。これは、`FIXED_FRAME` が32バイトになったことを反映し、合計で `16 + 32 = 48` バイトのスタック調整が行われることを意味します。
    - `runtime·mcall` の呼び出し前にも同様に `MOVDU R0, -8(R1)` が追加され、スタックにレジスタを保存する操作が増えています。

4.  **`MinFrameSize`の変更**:
    `src/runtime/internal/sys/arch_ppc64.go` と `src/runtime/internal/sys/arch_ppc64le.go` の両方で、`MinFrameSize` 定数が `8` から `32` に変更されました。これは、GoランタイムがPPC64およびPPC64LEアーキテクチャで確保する最小スタックフレームサイズが32バイトであることを明示的に示しています。この変更は、コンパイラやリンカがスタックフレームを生成する際の基準に影響を与え、より大きなスタックフレームがデフォルトで確保されるようにします。

これらの変更により、PPC64アーキテクチャ、特にPPC64LEにおけるPICコードの実行に必要なスタック領域が確保され、スタックオーバーフローのリスクが低減されます。また、スタックフレームサイズの増加は、`nosplit`関数がスタックガードを越えてしまう可能性を生じさせるため、コミットメッセージで言及されているように、次の変更でスタックガードの調整が行われることが示唆されています。

## コアとなるコードの解説

### `FixedFrameSize` の変更 (`cmd/internal/obj/link.go`, `cmd/link/internal/ld/link.go`)

Goのコンパイラとリンカは、関数呼び出しの際に必要なスタックフレームのサイズを決定します。`FixedFrameSize` 関数は、特定のアーキテクチャにおける固定スタックフレームの最小サイズをリンカに伝えます。PPC64アーキテクチャ (`Thechar == '9'`) の場合、この変更により、固定フレームサイズがポインタサイズの4倍、つまり32バイトに設定されます。これは、PPC64LEのPICコードが関数呼び出し時に最低32バイトのスタック領域を必要とするというアーキテクチャ固有の要件に対応するためのものです。PPC64とPPC64LEでこの値を統一することで、コードの複雑さを減らし、将来的なPICサポートを容易にしています。

### `FIXED_FRAME` の変更 (`src/runtime/asm_ppc64x.h`)

`FIXED_FRAME` は、Goランタイムのアセンブリコード内で使用されるマクロで、関数プロローグなどで予約されるスタック領域のサイズを定義します。以前はPPC64とPPC64LEでそれぞれ8バイトと定義されていましたが、この変更により一律32バイトに設定されました。これにより、アセンブリレベルでのスタック操作が、PPC64LEのPIC要件を満たすように統一されます。コメントにもあるように、これはPICのサポートを容易にするための措置であり、PPC64LEでは最低32バイトが必要ですが、PPC64では48バイトが必要になる可能性も示唆されています。しかし、このコミットでは32バイトに統一することで、まずはPPC64LEの要件を満たし、将来的な拡張性を考慮しています。

### アセンブリコードのスタック操作の変更 (`src/runtime/asm_ppc64x.s`)

`runtime·newproc` (新しいゴルーチンを作成する関数) と `runtime·mcall` (M (OSスレッド) のスタックを切り替える関数) のアセンブリコードが変更されています。
- `MOVDU R0, -8(R1)` は、レジスタ `R0` の内容をスタックポインタ `R1` から8バイトオフセットしたアドレスに保存し、同時に `R1` を8バイトデクリメントする命令です。これが複数回追加されているのは、より多くのレジスタをスタックに保存する必要があるためです。これは、`FIXED_FRAME` の増加に伴い、関数呼び出し規約で保存すべきレジスタが増えたか、あるいはPICコードの要件を満たすために追加のレジスタ保存が必要になったことを示唆しています。
- `ADD $(16+FIXED_FRAME), R1` は、`runtime·newproc` 呼び出し後にスタックポインタを調整する命令です。`FIXED_FRAME` が32バイトになったことで、スタックポインタは合計で `16 + 32 = 48` バイト分調整されます。これは、関数呼び出しによって使用されたスタック領域を解放し、スタックポインタを元の位置に戻すための操作です。

これらのアセンブリレベルの変更は、固定スタックフレームサイズの増加と、それに伴うレジスタ保存の必要性に対応するためのものです。

### `MinFrameSize` の変更 (`src/runtime/internal/sys/arch_ppc64.go`, `src/runtime/internal/sys/arch_ppc64le.go`)

`MinFrameSize` は、Goランタイムが特定のアーキテクチャで保証する最小スタックフレームサイズです。この値が8バイトから32バイトに変更されたことで、Goのコンパイラやリンカは、PPC64およびPPC64LE上で生成されるすべての関数に対して、最低32バイトのスタックフレームを確保するようになります。これにより、PICコードが要求するスタック領域が常に確保され、スタックオーバーフローのリスクが低減されます。

    runtime: make stack re-scan O(# dirty stacks)

    Currently the stack re-scan during mark termination is O(# stacks)
    because we enqueue a root marking job for every goroutine. It takes
    ~34ns to process this root marking job for a valid (clean) stack, so
    at around 300k goroutines we exceed the 10ms pause goal. A non-trivial
    portion of this time is spent simply taking the cache miss to check
    the gcscanvalid flag, so simply optimizing the path that handles clean
    stacks can only improve this so much.

    Fix this by keeping an explicit list of goroutines with dirty stacks
    that need to be rescanned. When a goroutine first transitions to
    running after a stack scan and marks its stack dirty, it adds itself
    to this list. We enqueue root marking jobs only for the goroutines in
    this list, so this improves stack re-scanning asymptotically by
    completely eliminating time spent on clean goroutines.

    This reduces mark termination time for 500k idle goroutines from 15ms
    to 238µs. Overall performance effect is negligible.

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）におけるスタック再スキャン処理の効率を改善します。以前は、GCのマーク終了フェーズ中にすべてのゴルーチンに対してルートマーキングジョブがキューに入れられていたため、スタックの再スキャンはゴルーチンの総数に比例する `O(# stacks)` の計算量を持っていました。これにより、特に多数のアイドル状態のゴルーチンが存在する場合に、GCのポーズ時間が長くなるという問題がありました。例えば、30万個のゴルーチンが存在すると、10ミリ秒のポーズ目標を超える可能性がありました。

この変更では、スタックが「ダーティ」（前回のスキャン以降に変更された）になったゴルーチンを明示的なリストで追跡する新しいメカニズムを導入します。ゴルーチンがスタックスキャン後に初めて実行状態に遷移し、そのスタックがダーティになった場合、自身をこのリストに追加します。GCのマーク終了フェーズでは、この「ダーティスタックリスト」に含まれるゴルーチンのみがルートマーキングジョブの対象となるため、クリーンな（変更されていない）スタックを持つゴルーチンに対する処理が完全に排除されます。これにより、スタック再スキャンの計算量が `O(# dirty stacks)` に改善され、漸近的に効率が向上します。

結果として、50万個のアイドル状態のゴルーチンにおけるマーク終了時間は、以前の15ミリ秒から238マイクロ秒へと劇的に短縮されました（98.41%の改善）。全体的なパフォーマンスへの影響はごくわずかであると報告されています。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行を一時停止する「ポーズ時間」を最小限に抑えるように設計されています。これは、特に低レイテンシが求められるサーバーアプリケーションにおいて重要です。当時のGoのGCは、並行マークフェーズとストップ・ザ・ワールド（STW）フェーズを組み合わせて動作していました。STWフェーズは、GCが正確なメモリ状態を把握するために、すべてのゴルーチンの実行を一時的に停止する期間です。

このコミットが対処しているのは、STWフェーズの一部である「マーク終了（Mark Termination）」フェーズにおけるスタック再スキャンの問題です。以前の実装では、マーク終了時にすべてのゴルーチンのスタックを再スキャンする必要がありました。これは、並行マークフェーズ中にゴルーチンが実行され、そのスタック上のポインタが変更される可能性があるためです。すべてのゴルーチンをチェックすることは、ゴルーチンの数が増えるにつれてポーズ時間が線形に増加する原因となっていました。

特に、多数のアイドル状態のゴルーチン（例えば、ネットワーク接続を待機しているゴルーチンなど）が存在する場合、これらのゴルーチンはスタックの内容をほとんど変更しないにもかかわらず、GCはそれらすべてをスキャンする必要がありました。この無駄なスキャンが、GCのポーズ目標（当時10ms）を超える主な要因の一つとなっていました。コミットメッセージにあるように、30万個のゴルーチンでポーズ目標を超過する可能性があり、これは大規模な並行アプリケーションにとって深刻な問題でした。

この問題の根本原因は、クリーンなスタック（変更されていないスタック）を処理する際のオーバーヘッドが、たとえそれがわずか34ナノ秒であっても、ゴルーチンの総数に掛け合わされると無視できない時間になることでした。また、`gcscanvalid`フラグをチェックするためのキャッシュミスも、このオーバーヘッドの一因となっていました。このコミットは、この非効率性を解消し、GCのポーズ時間を削減することで、Goアプリケーションのスケーラビリティと応答性を向上させることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **Goのガベージコレクション (GC) の基本:**
    *   GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。これは、オブジェクトを白（未訪問）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類してマークする方式です。
    *   GoのGCは、並行（Concurrent）GCであり、ほとんどのマークフェーズはアプリケーションの実行と並行して行われます。これにより、アプリケーションのポーズ時間を短縮します。
    *   しかし、GCの特定のフェーズ（特にマーク終了フェーズ）では、正確なメモリ状態を確保するために、すべてのゴルーチンを一時的に停止する「ストップ・ザ・ワールド (STW)」ポーズが必要です。

2.  **GCのフェーズ:**
    *   **Mark Start (STW):** GCサイクルを開始し、ルート（グローバル変数、スタック上のポインタなど）をスキャンする準備をします。
    *   **Concurrent Mark:** アプリケーションと並行して、ヒープ上の到達可能なオブジェクトをマークします。このフェーズ中にアプリケーションがポインタを変更する可能性があるため、「Write Barrier」が使用されます。
    *   **Mark Termination (STW):** 並行マークフェーズの終了後、残りのルート（特にゴルーチンのスタック）を再スキャンし、マークフェーズを完了します。このフェーズはSTWであり、ポーズ時間の主要な原因の一つです。
    *   **Concurrent Sweep:** マークされていない（到達不能な）オブジェクトが占めていたメモリを解放します。これは並行して行われます。

3.  **ゴルーチン (Goroutine) とスタック:**
    *   Goのゴルーチンは軽量なスレッドのようなもので、独自のスタックを持っています。
    *   Goのスタックは可変長であり、必要に応じて自動的に拡大・縮小します。
    *   GCは、ゴルーチンのスタック上に存在するポインタをルートとして認識し、そこから到達可能なヒープオブジェクトをマークする必要があります。

4.  **スタックスキャンとダーティスタック:**
    *   GCがゴルーチンのスタックをスキャンする際、そのスタック上にヒープオブジェクトへのポインタがあるかどうかを調べます。
    *   並行マークフェーズ中にゴルーチンが実行され、スタック上のポインタが変更された場合、そのスタックは「ダーティ」になったと見なされます。ダーティになったスタックは、マーク終了フェーズで再スキャンされる必要があります。
    *   `gcscanvalid` フラグは、特定のゴルーチンのスタックがGCによってスキャンされ、その時点では有効である（変更されていない）とマークされているかどうかを示します。このフラグが `false` の場合、スタックはダーティであるか、まだスキャンされていないことを意味します。

5.  **`O(N)` と `O(M)` の計算量:**
    *   `O(N)` は、アルゴリズムの実行時間が入力サイズ `N` に比例することを示します。この文脈では、`N` はゴルーチンの総数です。
    *   `O(M)` は、実行時間が入力サイズ `M` に比例することを示します。このコミットでは、`M` は「ダーティなスタックを持つゴルーチンの数」であり、通常はゴルーチンの総数 `N` よりもはるかに小さいです。

これらの概念を理解することで、このコミットがGoのGCの効率とポーズ時間の削減にどのように貢献しているかを深く把握できます。

## 技術的詳細

このコミットの核心は、GCのマーク終了フェーズにおけるスタック再スキャンの計算量を `O(# stacks)` から `O(# dirty stacks)` へと改善することです。これを実現するために、Goランタイムに以下の主要な変更が加えられました。

1.  **ダーティスタックリスト (`work.rescan.list`) の導入:**
    *   `runtime/mgc.go` の `work` 構造体に、`rescan` という新しいフィールドが追加されました。これは、`mutex` と `[]guintptr` (ゴルーチンへのポインタのリスト) を含む構造体です。
    *   このリストは、スタックがダーティになった、つまり前回のGCスキャン以降にスタック上のポインタが変更された可能性のあるゴルーチンを明示的に追跡するために使用されます。

2.  **ゴルーチン (`g`) 構造体への `gcRescan` フィールドの追加:**
    *   `runtime/runtime2.go` の `g` 構造体に `gcRescan int32` という新しいフィールドが追加されました。
    *   このフィールドは、ゴルーチンが `work.rescan.list` 内に存在する場合、そのリスト内でのインデックスを格納します。ゴルーチンがリストにない場合は `-1` に設定されます。これにより、リストからの削除が `O(1)` で可能になります（リストの末尾要素と交換して削除）。

3.  **`gcMarkRootPrepare` の変更:**
    *   `runtime/mgcmark.go` の `gcMarkRootPrepare` 関数は、GCルートスキャンの準備を行います。
    *   この関数は、GCフェーズに応じて異なる動作をするようになりました。
        *   **最初のマークルートパス (並行マーク中):** `work.nStackRoots` は `allglen` (すべてのゴルーチンの数) に設定され、`work.nRescanRoots` は `0` です。これは、並行マークの初期段階ではすべてのゴルーチンがスキャン対象となることを意味します。
        *   **2回目のマークルートパス (マーク終了中):** `work.nStackRoots` は `0` に設定され、`work.nRescanRoots` は `len(work.rescan.list)` に設定されます。これにより、マーク終了フェーズでは、ダーティスタックリストにあるゴルーチンのみがスキャン対象となります。
    *   `work.markrootJobs` の計算も、`work.nRescanRoots` を含むように更新され、キューに入れられるルートマーキングジョブの総数が正確に反映されるようになりました。

4.  **`casgstatus` (Goroutine状態遷移) の変更:**
    *   `runtime/proc.go` の `casgstatus` 関数は、ゴルーチンの状態が変更される際に呼び出されます。
    *   ゴルーチンが `_Grunning` 状態に遷移し、かつ `gp.gcscanvalid` が `true` の場合（つまり、以前にスタックがスキャンされてクリーンと見なされていたが、これから実行されるためダーティになる可能性がある場合）、`queueRescan(gp)` がシステムスタック上で呼び出されます。これは、実行中のゴルーチンがスタック上のポインタを変更する可能性があるため、そのスタックをダーティとしてマークし、再スキャンリストに追加する必要があることを示します。

5.  **`queueRescan` および `dequeueRescan` 関数の導入:**
    *   `runtime/mgcmark.go` に、`queueRescan(gp *g)` と `dequeueRescan(gp *g)` という2つの新しいヘルパー関数が追加されました。
    *   `queueRescan` は、指定されたゴルーチン `gp` を `work.rescan.list` に追加し、`gp.gcscanvalid` を `false` に設定します。また、`gp.gcRescan` にリスト内のインデックスを格納します。
    *   `dequeueRescan` は、指定されたゴルーチン `gp` を `work.rescan.list` から削除し、`gp.gcRescan` を `-1` に設定します。
    *   これらの関数は、`work.rescan.lock` ミューテックスによって保護され、並行アクセス時のデータ競合を防ぎます。

6.  **その他の変更点:**
    *   `gcResetMarkState()`: GCサイクル開始時にすべてのゴルーチンの `gcscandone` と `gcscanvalid` フラグをリセットし、`gp.gcRescan` を `-1` に設定します。また、`work.rescan.list` をクリアします。
    *   `markroot()`: ルートスキャン中に、GCバックグラウンドワーカーゴルーチンが並行マークフェーズ中にスキャンされないようにし、代わりに `queueRescan` を呼び出してマーク終了フェーズで処理されるようにします。
    *   `scanstack()`: スタックがスキャンされてクリーンになった場合、`dequeueRescan` を呼び出してゴルーチンをダーティスタックリストから削除します。
    *   `newproc1()`: 新しいゴルーチンが作成される際、そのスタックは引数フレームによってダーティになるため、`queueRescan` を呼び出して再スキャンリストに追加します。

これらの変更により、GCはマーク終了フェーズにおいて、実際に変更された可能性のあるスタックのみを効率的に再スキャンできるようになり、多数のアイドルゴルーチンが存在する環境でのGCポーズ時間が劇的に短縮されました。

                // ...
            }
        }
        ```
        `markroot` は、`i` の値に基づいて、すべてのゴルーチンをスキャンするのか、`rescan.list` のゴルーチンをスキャンするのかを判断します。
    *   `queueRescan(gp *g)` および `dequeueRescan(gp *g)` 関数の追加:
        ```go
        func queueRescan(gp *g) {
            // ...
            lock(&work.rescan.lock)
            gp.gcscanvalid = false
            // ...
            gp.gcRescan = int32(n)
            work.rescan.list = work.rescan.list[:n+1]
            work.rescan.list[n].set(gp)
            unlock(&work.rescan.lock)
        }

        func dequeueRescan(gp *g) {
            // ...
            lock(&work.rescan.lock)
            // ...
            last := work.rescan.list[len(work.rescan.list)-1]
            work.rescan.list[gp.gcRescan] = last
            last.ptr().gcRescan = gp.gcRescan
            gp.gcRescan = -1
            work.rescan.list = work.rescan.list[:len(work.rescan.list)-1]
            unlock(&work.rescan.lock)
        }
        ```
        これらの関数は、ゴルーチンをダーティスタックリストに追加・削除するロジックをカプセル化します。

3.  **`src/runtime/proc.go`:**
    *   `casgstatus()` 関数での `queueRescan` の呼び出し:
        ```go
        func casgstatus(gp *g, oldval, newval uint32) {
            // ...
            if newval == _Grunning && gp.gcscanvalid {
                // スタックが有効とマークされた後に実行状態になった場合、ダーティとして再スキャンリストに追加
                systemstack(func() { queueRescan(gp) })
            }
        }
        ```
        これは、ゴルーチンが実行状態に遷移する際に、そのスタックがダーティになる可能性を考慮する重要な変更です。
    *   `newproc1()` 関数での `queueRescan` の呼び出し:
        ```go
        func newproc1(fn *funcval, argp *uint8, narg int32, nret int32, callerpc uintptr, gp *g, newg *g) {
            // ...
            if newg.gcRescan == -1 {
                queueRescan(newg) // 新しいゴルーチンはスタックがダーティなので再スキャンリストに追加
            } else {
                newg.gcscanvalid = false
            }
            // ...
        }
        ```
        新しく作成されたゴルーチンは、引数フレームによってスタックがダーティになるため、すぐに再スキャンリストに追加されます。

4.  **`src/runtime/runtime2.go`:**
    *   `g` 構造体への `gcRescan` フィールドの追加:
        ```go
        type g struct {
            // ...
            gcscanvalid    bool     // false at start of gc cycle, true if G has not run since last scan; transition from true to false by calling queueRescan and false to true by calling dequeueRescan
            // ...
            gcRescan int32 // This G's index in work.rescan.list. If -1, not on list.
            // ...
        }
        ```
        `g` 構造体に `gcRescan` が追加され、`gcscanvalid` のコメントも更新されました。

## コアとなるコードの解説

このコミットの核となるのは、Goのガベージコレクタがゴルーチンのスタックをスキャンする方法を最適化する新しいデータ構造とロジックです。

**1. `work.rescan.list` と `g.gcRescan`:**

*   **`work.rescan.list` (in `src/runtime/mgc.go`):** これは、GCのマーク終了フェーズ中に再スキャンが必要なゴルーチン（つまり、スタックがダーティになったゴルーチン）のポインタを保持する動的なリストです。`guintptr` 型の要素を持つスライスとして実装されており、`guintptr` は `*g` (ゴルーチンへのポインタ) を保持できる `uintptr` です。これにより、GCがこのリスト自体をルートとしてスキャンするのを防ぎ、GCのオーバーヘッドをさらに削減します。このリストは `work.rescan.lock` ミューテックスによって保護され、並行アクセス時の安全性を確保しています。
*   **`g.gcRescan` (in `src/runtime/runtime2.go`):** 各ゴルーチン (`g` 構造体) に追加された `int32` 型のフィールドです。このフィールドは、そのゴルーチンが `work.rescan.list` に含まれている場合、リスト内でのそのゴルーチンのインデックスを格納します。ゴルーチンがリストにない場合は `-1` が設定されます。このインデックスを持つことで、`dequeueRescan` 関数がリストからゴルーチンを `O(1)` の時間計算量で効率的に削除できるようになります。

**2. `gcMarkRootPrepare` のフェーズ依存の動作 (in `src/runtime/mgcmark.go`):**

*   この関数は、GCのルートスキャンジョブを準備します。重要な変更は、GCの現在のフェーズ (`gcphase`) に応じて、スキャン対象のゴルーチン数を動的に決定する点です。
    *   **並行マークフェーズ中 (`!work.markrootDone`):** この初期段階では、すべてのゴルーチン (`allglen`) がスキャン対象と見なされます (`work.nStackRoots = allglen`)。これは、GCが開始された時点でのすべてのゴルーチンのスタックを初期的にスキャンするためです。`work.nRescanRoots` は `0` です。
    *   **マーク終了フェーズ中 (`work.markrootDone` が `true`):** このSTWフェーズでは、`work.nStackRoots` は `0` に設定され、代わりに `work.nRescanRoots` が `len(work.rescan.list)` に設定されます。これにより、GCはダーティスタックリストに登録されたゴルーチンのみを再スキャンするようになります。これが、計算量を `O(# dirty stacks)` に削減する主要なメカニズムです。

**3. `casgstatus` における `queueRescan` の呼び出し (in `src/runtime/proc.go`):**

*   `casgstatus` 関数は、ゴルーチンの状態遷移を管理します。このコミットで最も重要な変更の一つは、ゴルーチンが `_Grunning` (実行中) 状態に遷移する際に、そのスタックがダーティになる可能性を考慮する点です。
*   具体的には、ゴルーチンが `_Grunning` に遷移し、かつ `gp.gcscanvalid` が `true` (以前にスタックがスキャンされてクリーンと見なされていた) の場合、`systemstack(func() { queueRescan(gp) })` が呼び出されます。
    *   `systemstack` は、現在のゴルーチンのスタックではなく、システムスタック上で関数を実行します。これは、`queueRescan` がロックを取得したり、スタックを操作したりする可能性があるため、現在のゴルーチンのスタックが不安定な状態にあることを避けるための安全策です。
    *   `queueRescan(gp)` は、このゴルーチンをダーティスタックリストに追加し、`gp.gcscanvalid` を `false` に設定します。これにより、GCは後でこのゴルーチンのスタックを再スキャンする必要があることを認識します。

**4. `queueRescan` と `dequeueRescan` (in `src/runtime/mgcmark.go`):**

*   **`queueRescan(gp *g)`:**
    *   ゴルーチン `gp` を `work.rescan.list` の末尾に追加します。
    *   `gp.gcRescan` に新しいインデックスを格納します。
    *   `gp.gcscanvalid` を `false` に設定し、スタックがダーティであることを示します。
    *   `work.rescan.lock` を取得して、リストへの安全なアクセスを保証します。
*   **`dequeueRescan(gp *g)`:**
    *   `gp.gcRescan` を使用して、`work.rescan.list` からゴルーチン `gp` を効率的に削除します。削除は、リストの末尾要素を `gp` の位置に移動させ、リストの長さを1つ減らすことで行われます。これにより、リストの途中の要素を削除する際の `O(N)` の移動コストを `O(1)` に削減しています。
    *   `gp.gcRescan` を `-1` にリセットします。
    *   `work.rescan.lock` を取得して、リストへの安全なアクセスを保証します。

これらのメカニズムが連携することで、GoのGCは、実際に変更された可能性のあるスタックのみをターゲットに再スキャンを実行できるようになり、特に多数のアイドルゴルーチンが存在するシナリオでのGCポーズ時間を劇的に短縮することに成功しました。これは、Goのランタイムが大規模な並行アプリケーションにおいて、より予測可能で低いレイテンシを提供するための重要な改善です。

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）におけるスタック再スキャン処理の効率を改善します。以前は、GCのマーク終了フェーズ中にすべてのゴルーチンに対してルートマーキングジョブがキューに入れられていたため、スタックの再スキャンはゴルーチンの総数に比例する `O(# stacks)` の計算量を持っていました。これにより、特に多数のアイドル状態のゴルーチンが存在する場合に、GCのポーズ時間が長くなるという問題がありました。例えば、30万個のゴルーチンが存在すると、10ミリ秒のポーズ目標を超える可能性がありました。

この変更では、スタックが「ダーティ」（前回のスキャン以降に変更された）になったゴルーチンを明示的なリストで追跡する新しいメカニズムを導入します。ゴルーチンがスタックスキャン後に初めて実行状態に遷移し、そのスタックがダーティになった場合、自身をこのリストに追加します。GCのマーク終了フェーズでは、この「ダーティスタックリスト」に含まれるゴルーチンのみがルートマーキングジョブの対象となるため、クリーンな（変更されていない）スタックを持つゴルーチンに対する処理が完全に排除されます。これにより、スタック再スキャンの計算量が `O(# dirty stacks)` に改善され、漸近的に効率が向上します。

結果として、50万個のアイドル状態のゴルーチンにおけるマーク終了時間は、以前の15ミリ秒から238マイクロ秒へと劇的に短縮されました（98.41%の改善）。全体的なパフォーマンスへの影響はごくわずかであると報告されています。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行を一時停止する「ポーズ時間」を最小限に抑えるように設計されています。これは、特に低レイテンシが求められるサーバーアプリケーションにおいて重要です。当時のGoのGCは、並行マークフェーズとストップ・ザ・ワールド（STW）フェーズを組み合わせて動作していました。STWフェーズは、GCが正確なメモリ状態を把握するために、すべてのゴルーチンの実行を一時的に停止する期間です。

このコミットが対処しているのは、STWフェーズの一部である「マーク終了（Mark Termination）」フェーズにおけるスタック再スキャンの問題です。以前の実装では、マーク終了時にすべてのゴルーチンのスタックを再スキャンする必要がありました。これは、並行マークフェーズ中にゴルーチンが実行され、そのスタック上のポインタが変更される可能性があるためです。すべてのゴルーチンをチェックすることは、ゴルーチンの数が増えるにつれてポーズ時間が線形に増加する原因となっていました。

特に、多数のアイドル状態のゴルーチン（例えば、ネットワーク接続を待機しているゴルーチンなど）が存在する場合、これらのゴルーチンはスタックの内容をほとんど変更しないにもかかわらず、GCはそれらすべてをスキャンする必要がありました。この無駄なスキャンが、GCのポーズ目標（当時10ms）を超える主な要因の一つとなっていました。コミットメッセージにあるように、30万個のゴルーチンでポーズ目標を超過する可能性があり、これは大規模な並行アプリケーションにとって深刻な問題でした。

この問題の根本原因は、クリーンなスタック（変更されていないスタック）を処理する際のオーバーヘッドが、たとえそれがわずか34ナノ秒であっても、ゴルーチンの総数に掛け合わされると無視できない時間になることでした。また、`gcscanvalid`フラグをチェックするためのキャッシュミスも、このオーバーヘッドの一因となっていました。このコミットは、この非効率性を解消し、GCのポーズ時間を削減することで、Goアプリケーションのスケーラビリティと応答性を向上させることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **Goのガベージコレクション (GC) の基本:**
    *   GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。これは、オブジェクトを白（未訪問）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類してマークする方式です。
    *   GoのGCは、並行（Concurrent）GCであり、ほとんどのマークフェーズはアプリケーションの実行と並行して行われます。これにより、アプリケーションのポーズ時間を短縮します。
    *   しかし、GCの特定のフェーズ（特にマーク終了フェーズ）では、正確なメモリ状態を確保するために、すべてのゴルーチンを一時的に停止する「ストップ・ザ・ワールド (STW)」ポーズが必要です。

2.  **GCのフェーズ:**
    *   **Mark Start (STW):** GCサイクルを開始し、ルート（グローバル変数、スタック上のポインタなど）をスキャンする準備をします。
    *   **Concurrent Mark:** アプリケーションと並行して、ヒープ上の到達可能なオブジェクトをマークします。このフェーズ中にアプリケーションがポインタを変更する可能性があるため、「Write Barrier」が使用されます。
    *   **Mark Termination (STW):** 並行マークフェーズの終了後、残りのルート（特にゴルーチンのスタック）を再スキャンし、マークフェーズを完了します。このフェーズはSTWであり、ポーズ時間の主要な原因の一つです。
    *   **Concurrent Sweep:** マークされていない（到達不能な）オブジェクトが占めていたメモリを解放します。これは並行して行われます。

3.  **ゴルーチン (Goroutine) とスタック:**
    *   Goのゴルーチンは軽量なスレッドのようなもので、独自のスタックを持っています。
    *   Goのスタックは可変長であり、必要に応じて自動的に拡大・縮小します。
    *   GCは、ゴルーチンのスタック上に存在するポインタをルートとして認識し、そこから到達可能なヒープオブジェクトをマークする必要があります。

4.  **スタックスキャンとダーティスタック:**
    *   GCがゴルーチンのスタックをスキャンする際、そのスタック上にヒープオブジェクトへのポインタがあるかどうかを調べます。
    *   並行マークフェーズ中にゴルーチンが実行され、スタック上のポインタが変更された場合、そのスタックは「ダーティ」になったと見なされます。ダーティになったスタックは、マーク終了フェーズで再スキャンされる必要があります。
    *   `gcscanvalid` フラグは、特定のゴルーチンのスタックがGCによってスキャンされ、その時点では有効である（変更されていない）とマークされているかどうかを示します。このフラグが `false` の場合、スタックはダーティであるか、まだスキャンされていないことを意味します。

5.  **`O(N)` と `O(M)` の計算量:**
    *   `O(N)` は、アルゴリズムの実行時間が入力サイズ `N` に比例することを示します。この文脈では、`N` はゴルーチンの総数です。
    *   `O(M)` は、実行時間が入力サイズ `M` に比例することを示します。このコミットでは、`M` は「ダーティなスタックを持つゴルーチンの数」であり、通常はゴルーチンの総数 `N` よりもはるかに小さいです。

これらの概念を理解することで、このコミットがGoのGCの効率とポーズ時間の削減にどのように貢献しているかを深く把握できます。

## 技術的詳細

このコミットの核心は、GCのマーク終了フェーズにおけるスタック再スキャンの計算量を `O(# stacks)` から `O(# dirty stacks)` へと改善することです。これを実現するために、Goランタイムに以下の主要な変更が加えられました。

1.  **ダーティスタックリスト (`work.rescan.list`) の導入:**
    *   `runtime/mgc.go` の `work` 構造体に、`rescan` という新しいフィールドが追加されました。これは、`mutex` と `[]guintptr` (ゴルーチンへのポインタのリスト) を含む構造体です。
    *   このリストは、スタックがダーティになった、つまり前回のGCスキャン以降にスタック上のポインタが変更された可能性のあるゴルーチンを明示的に追跡するために使用されます。

2.  **ゴルーチン (`g`) 構造体への `gcRescan` フィールドの追加:**
    *   `runtime/runtime2.go` の `g` 構造体に `gcRescan int32` という新しいフィールドが追加されました。
    *   このフィールドは、ゴルーチンが `work.rescan.list` 内に存在する場合、そのリスト内でのインデックスを格納します。ゴルーチンがリストにない場合は `-1` に設定されます。これにより、リストからの削除が `O(1)` で可能になります（リストの末尾要素と交換して削除）。

3.  **`gcMarkRootPrepare` の変更:**
    *   `runtime/mgcmark.go` の `gcMarkRootPrepare` 関数は、GCルートスキャンの準備を行います。
    *   この関数は、GCフェーズに応じて異なる動作をするようになりました。
        *   **最初のマークルートパス (並行マーク中):** `work.nStackRoots` は `allglen` (すべてのゴルーチンの数) に設定され、`work.nRescanRoots` は `0` です。これは、並行マークの初期段階ではすべてのゴルーチンがスキャン対象となることを意味します。
        *   **2回目のマークルートパス (マーク終了中):** `work.nStackRoots` は `0` に設定され、代わりに `work.nRescanRoots` が `len(work.rescan.list)` に設定されます。これにより、マーク終了フェーズでは、ダーティスタックリストに登録されたゴルーチンのみがスキャン対象となります。
    *   `work.markrootJobs` の計算も、`work.nRescanRoots` を含むように更新され、キューに入れられるルートマーキングジョブの総数が正確に反映されるようになりました。

4.  **`casgstatus` (Goroutine状態遷移) の変更:**
    *   `runtime/proc.go` の `casgstatus` 関数は、ゴルーチンの状態が変更される際に呼び出されます。
    *   ゴルーチンが `_Grunning` 状態に遷移し、かつ `gp.gcscanvalid` が `true` の場合（つまり、以前にスタックがスキャンされてクリーンと見なされていたが、これから実行されるためダーティになる可能性がある場合）、`queueRescan(gp)` がシステムスタック上で呼び出されます。これは、実行中のゴルーチンがスタック上のポインタを変更する可能性があるため、そのスタックをダーティとしてマークし、再スキャンリストに追加する必要があることを示します。

5.  **`queueRescan` および `dequeueRescan` 関数の導入:**
    *   `runtime/mgcmark.go` に、`queueRescan(gp *g)` と `dequeueRescan(gp *g)` という2つの新しいヘルパー関数が追加されました。
    *   `queueRescan` は、指定されたゴルーチン `gp` を `work.rescan.list` に追加し、`gp.gcscanvalid` を `false` に設定します。また、`gp.gcRescan` にリスト内のインデックスを格納します。
    *   `dequeueRescan` は、指定されたゴルーチン `gp` を `work.rescan.list` から削除し、`gp.gcRescan` を `-1` に設定します。
    *   これらの関数は、`work.rescan.lock` ミューテックスによって保護され、並行アクセス時のデータ競合を防ぎます。

6.  **その他の変更点:**
    *   `gcResetMarkState()`: GCサイクル開始時にすべてのゴルーチンの `gcscandone` と `gcscanvalid` フラグをリセットし、`gp.gcRescan` を `-1` に設定します。また、`work.rescan.list` をクリアします。
    *   `markroot()`: ルートスキャン中に、GCバックグラウンドワーカーゴルーチンが並行マークフェーズ中にスキャンされないようにし、代わりに `queueRescan` を呼び出してマーク終了フェーズで処理されるようにします。
    *   `scanstack()`: スタックがスキャンされてクリーンになった場合、`dequeueRescan` を呼び出してゴルーチンをダーティスタックリストから削除します。
    *   `newproc1()`: 新しいゴルーチンが作成される際、そのスタックは引数フレームによってダーティになるため、`queueRescan` を呼び出して再スキャンリストに追加します。

これらの変更により、GCはマーク終了フェーズにおいて、実際に変更された可能性のあるスタックのみを効率的に再スキャンできるようになり、多数のアイドルゴルーチンが存在する環境でのGCポーズ時間が劇的に短縮されました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイルと構造体、関数に集中しています。

1.  **`src/runtime/mgc.go`:**
    *   `work` 構造体への新しいフィールドの追加:
        ```go
        var work struct {
            // ...
            nDataRoots, nBSSRoots, nSpanRoots, nStackRoots, nRescanRoots int
            // ...
            rescan struct {
                lock mutex
                list []guintptr
            }
            // ...
        }
        ```
        `nRescanRoots` は再スキャンが必要なルートの数を追跡し、`rescan` 構造体はダーティなスタックを持つゴルーチンのリストを管理します。
    *   `gcResetMarkState()` 関数での `rescan` リストの初期化と `gp.gcRescan` のリセット:
        ```go
        func gcResetMarkState() {
            // ...
            for _, gp := range allgs {
                // ...
                gp.gcRescan = -1 // 新しいフィールドの初期化
                // ...
            }
            // ...
            work.rescan.list = work.rescan.list[:0] // リストのクリア
            // ...
        }
        ```

2.  **`src/runtime/mgcmark.go`:**
    *   `gcMarkRootPrepare()` 関数でのルートカウントの計算ロジックの変更:
        ```go
        func gcMarkRootPrepare() {
            // ...
            if !work.markrootDone { // 最初のマークルートパス
                // ...
                work.nStackRoots = int(atomic.Loaduintptr(&allglen))
                work.nRescanRoots = 0
            } else { // 2回目のマークルートパス (マーク終了時)
                // ...
                work.nStackRoots = 0
                work.nRescanRoots = len(work.rescan.list)
            }
            work.markrootJobs = uint32(fixedRootCount + work.nDataRoots + work.nBSSRoots + work.nSpanRoots + work.nStackRoots + work.nRescanRoots)
        }
        ```
        これにより、マーク終了フェーズでは `work.rescan.list` のみからルートジョブが生成されます。
    *   `markroot()` 関数でのスタック処理ロジックの変更:
        ```go
        func markroot(gcw *gcWork, i uint32) {
            // ...
            baseStacks := baseSpans + uint32(work.nSpanRoots)
            baseRescan := baseStacks + uint32(work.nStackRoots) // 新しいベース
            end := baseRescan + uint32(work.nRescanRoots)

            // ...
            switch {
            // ...
            default: // ゴルーチンスタックのスキャン
                var gp *g
                if baseStacks <= i && i < baseRescan { // 最初のパスで全ゴルーチンをスキャン
                    gp = allgs[i-baseStacks]
                } else if baseRescan <= i && i < end { // 2回目のパスでダーティリストをスキャン
                    gp = work.rescan.list[i-baseRescan].ptr()
                } else {
                    throw("markroot: bad index")
                }
                // ...
                if gcphase != _GCmarktermination && gp.startpc == gcBgMarkWorkerPC && readgstatus(gp) != _Gdead {
                    // GCワーカーは並行フェーズではスキャンせず、再スキャンリストに追加
                    gp.gcscandone = true
                    queueRescan(gp)
                    break
                }
                // ...
            }
        }
        ```
        `markroot` は、`i` の値に基づいて、すべてのゴルーチンをスキャンするのか、`rescan.list` のゴルーチンをスキャンするのかを判断します。
    *   `queueRescan(gp *g)` および `dequeueRescan(gp *g)` 関数の追加:
        ```go
        func queueRescan(gp *g) {
            // ...
            lock(&work.rescan.lock)
            gp.gcscanvalid = false
            // ...
            gp.gcRescan = int32(n)
            work.rescan.list = work.rescan.list[:n+1]
            work.rescan.list[n].set(gp)
            unlock(&work.rescan.lock)
        }

        func dequeueRescan(gp *g) {
            // ...
            lock(&work.rescan.lock)
            // ...
            last := work.rescan.list[len(work.rescan.list)-1]
            work.rescan.list[gp.gcRescan] = last
            last.ptr().gcRescan = gp.gcRescan
            gp.gcRescan = -1
            work.rescan.list = work.rescan.list[:len(work.rescan.list)-1]
            unlock(&work.rescan.lock)
        }
        ```
        これらの関数は、ゴルーチンをダーティスタックリストに追加・削除するロジックをカプセル化します。

3.  **`src/runtime/proc.go`:**
    *   `casgstatus()` 関数での `queueRescan` の呼び出し:
        ```go
        func casgstatus(gp *g, oldval, newval uint32) {
            // ...
            if newval == _Grunning && gp.gcscanvalid {
                // スタックが有効とマークされた後に実行状態になった場合、ダーティとして再スキャンリストに追加
                systemstack(func() { queueRescan(gp) })
            }
        }
        ```
        これは、ゴルーチンが実行状態に遷移する際に、そのスタックがダーティになる可能性を考慮する重要な変更です。
    *   `newproc1()` 関数での `queueRescan` の呼び出し:
        ```go
        func newproc1(fn *funcval, argp *uint8, narg int32, nret int32, callerpc uintptr, gp *g, newg *g) {
            // ...
            if newg.gcRescan == -1 {
                queueRescan(newg) // 新しいゴルーチンはスタックがダーティなので再スキャンリストに追加
            } else {
                newg.gcscanvalid = false
            }
            // ...
        }
        ```
        新しく作成されたゴルーチンは、引数フレームによってスタックがダーティになるため、すぐに再スキャンリストに追加されます。

4.  **`src/runtime/runtime2.go`:**
    *   `g` 構造体への `gcRescan` フィールドの追加:
        ```go
        type g struct {
            // ...
            gcscanvalid    bool     // false at start of gc cycle, true if G has not run since last scan; transition from true to false by calling queueRescan and false to true by calling dequeueRescan
            // ...
            gcRescan int32 // This G's index in work.rescan.list. If -1, not on list.
            // ...
        }
        ```
        `g` 構造体に `gcRescan` が追加され、`gcscanvalid` のコメントも更新されました。

これらの変更が連携して、GCのスタック再スキャンメカニズムを根本的に変更し、効率を向上させています。

## コアとなるコードの解説

このコミットの核となるのは、Goのガベージコレクタがゴルーチンのスタックをスキャンする方法を最適化する新しいデータ構造とロジックです。

**1. `work.rescan.list` と `g.gcRescan`:**

*   **`work.rescan.list` (in `src/runtime/mgc.go`):** これは、GCのマーク終了フェーズ中に再スキャンが必要なゴルーチン（つまり、スタックがダーティになったゴルーチン）のポインタを保持する動的なリストです。`guintptr` 型の要素を持つスライスとして実装されており、`guintptr` は `*g` (ゴルーチンへのポインタ) を保持できる `uintptr` です。これにより、GCがこのリスト自体をルートとしてスキャンするのを防ぎ、GCのオーバーヘッドをさらに削減します。このリストは `work.rescan.lock` ミューテックスによって保護され、並行アクセス時の安全性を確保しています。
*   **`g.gcRescan` (in `src/runtime/runtime2.go`):** 各ゴルーチン (`g` 構造体) に追加された `int32` 型のフィールドです。このフィールドは、そのゴルーチンが `work.rescan.list` に含まれている場合、リスト内でのそのゴルーチンのインデックスを格納します。ゴルーチンがリストにない場合は `-1` が設定されます。このインデックスを持つことで、`dequeueRescan` 関数がリストからゴルーチンを `O(1)` の時間計算量で効率的に削除できるようになります。

**2. `gcMarkRootPrepare` のフェーズ依存の動作 (in `src/runtime/mgcmark.go`):**

*   この関数は、GCのルートスキャンジョブを準備します。重要な変更は、GCの現在のフェーズ (`gcphase`) に応じて、スキャン対象のゴルーチン数を動的に決定する点です。
    *   **並行マークフェーズ中 (`!work.markrootDone`):** この初期段階では、すべてのゴルーチン (`allglen`) がスキャン対象と見なされます (`work.nStackRoots = allglen`)。これは、GCが開始された時点でのすべてのゴルーチンのスタックを初期的にスキャンするためです。`work.nRescanRoots` は `0` です。
    *   **マーク終了フェーズ中 (`work.markrootDone` が `true`):** このSTWフェーズでは、`work.nStackRoots` は `0` に設定され、代わりに `work.nRescanRoots` が `len(work.rescan.list)` に設定されます。これにより、GCはダーティスタックリストに登録されたゴルーチンのみを再スキャンするようになります。これが、計算量を `O(# dirty stacks)` に削減する主要なメカニズムです。

**3. `casgstatus` における `queueRescan` の呼び出し (in `src/runtime/proc.go`):**

*   `casgstatus` 関数は、ゴルーチンの状態遷移を管理します。このコミットで最も重要な変更の一つは、ゴルーチンが `_Grunning` (実行中) 状態に遷移する際に、そのスタックがダーティになる可能性を考慮する点です。
*   具体的には、ゴルーチンが `_Grunning` に遷移し、かつ `gp.gcscanvalid` が `true` (以前にスタックがスキャンされてクリーンと見なされていた) の場合、`systemstack(func() { queueRescan(gp) })` が呼び出されます。
    *   `systemstack` は、現在のゴルーチンのスタックではなく、システムスタック上で関数を実行します。これは、`queueRescan` がロックを取得したり、スタックを操作したりする可能性があるため、現在のゴルーチンのスタックが不安定な状態にあることを避けるための安全策です。
    *   `queueRescan(gp)` は、このゴルーチンをダーティスタックリストに追加し、`gp.gcscanvalid` を `false` に設定します。これにより、GCは後でこのゴルーチンのスタックを再スキャンする必要があることを認識します。

**4. `queueRescan` と `dequeueRescan` (in `src/runtime/mgcmark.go`):**

*   **`queueRescan(gp *g)`:**
    *   ゴルーチン `gp` を `work.rescan.list` の末尾に追加します。
    *   `gp.gcRescan` に新しいインデックスを格納します。
    *   `gp.gcscanvalid` を `false` に設定し、スタックがダーティであることを示します。
    *   `work.rescan.lock` を取得して、リストへの安全なアクセスを保証します。
*   **`dequeueRescan(gp *g)`:**
    *   `gp.gcRescan` を使用して、`work.rescan.list` からゴルーチン `gp` を効率的に削除します。削除は、リストの末尾要素を `gp` の位置に移動させ、リストの長さを1つ減らすことで行われます。これにより、リストの途中の要素を削除する際の `O(N)` の移動コストを `O(1)` に削減しています。
    *   `gp.gcRescan` を `-1` にリセットします。
    *   `work.rescan.lock` を取得して、リストへの安全なアクセスを保証します。

これらのメカニズムが連携することで、GoのGCは、実際に変更された可能性のあるスタックのみをターゲットに再スキャンを実行できるようになり、特に多数のアイドルゴルーチンが存在するシナリオでのGCポーズ時間を劇的に短縮することに成功しました。これは、Goのランタイムが大規模な並行アプリケーションにおいて、より予測可能で低いレイテンシを提供するための重要な改善です。

# [インデックス 25806] ファイルの概要

このコミットは、GoランタイムがWindows上で`timeBeginPeriod`関数を呼び出すのを停止する変更です。以前はGoスケジューラのパフォーマンス向上のためにこの関数が使用されていましたが、スケジューラの改善により不要になったため、システム全体に影響を与えるこのグローバルな設定を削除することが目的です。

## 元コミット内容

```
runtime: do not call timeBeginPeriod on windows

Calling timeBeginPeriod changes Windows global timer resolution
from 15ms to 1ms. This used to improve Go runtime scheduler
performance, but not anymore. Thanks to @aclements, scheduler now
behaves the same way if we call timeBeginPeriod or not.

Remove call to timeBeginPeriod, since it is machine global
resource, and there are downsides of using low timer resolution.
See issue #8687 for details.

Fixes #8687
```

## 変更の背景

このコミットの背景には、Windowsオペレーティングシステムにおけるタイマー解像度の管理と、Goランタイムスケジューラの進化があります。

元々、GoランタイムはWindows上で`timeBeginPeriod(1)`というWindows API関数を呼び出すことで、システム全体のタイマー解像度をデフォルトの約15ミリ秒から1ミリ秒に引き上げていました。これは、Goのスケジューラがより高精度な時間間隔でゴルーチンをスケジューリングするために必要とされ、特にI/O処理の多いアプリケーションや低レイテンシが求められる場面で、スケジューラの応答性を向上させる目的がありました。

しかし、`timeBeginPeriod`の使用にはいくつかの重大な欠点があります。
1.  **システム全体への影響**: `timeBeginPeriod`はグローバルな設定であり、一度呼び出されると、そのプロセスだけでなくシステム上のすべてのプロセスに影響を与えます。これにより、他のアプリケーションが不必要に高いタイマー解像度で動作することになり、予期せぬ副作用を引き起こす可能性があります。
2.  **電力消費の増加**: タイマー解像度が高くなると、OSはより頻繁にタイマー割り込みを処理する必要があり、CPUがアイドル状態になる時間が減少し、省電力モードへの移行が妨げられます。結果として、特にノートPCなどのバッテリー駆動デバイスでは電力消費が増加し、バッテリー寿命が短くなるという問題がありました。
3.  **システムパフォーマンスの低下**: タイマー割り込みの頻度が増えることで、コンテキストスイッチのオーバーヘッドが増加し、システム全体のパフォーマンスがわずかに低下する可能性も指摘されていました。

Goランタイムのスケジューラは、@aclements氏による改善（おそらくIssue #8687に関連する一連の変更）により、`timeBeginPeriod`によって提供される高精度なタイマー解像度に依存することなく、同等またはそれ以上のパフォーマンスを発揮できるようになりました。この改善により、`timeBeginPeriod`を呼び出す必要性がなくなり、上記のような欠点を回避できるようになりました。

このコミットは、GoランタイムがWindowsシステムリソースをより効率的かつ責任を持って利用し、他のアプリケーションやシステム全体の安定性・電力効率に配慮する方向への重要な一歩と言えます。

## 前提知識の解説

### Windowsのタイマー解像度と`timeBeginPeriod`関数

Windowsオペレーティングシステムには、システムタイマーの解像度という概念があります。これは、OSが内部的に時間を計測し、タスクスケジューリングやイベント処理を行う際の最小時間単位を指します。

*   **デフォルトのタイマー解像度**: 多くのWindowsシステムでは、デフォルトのタイマー解像度は約15.6ミリ秒（64分の1秒）です。これは、OSが電力効率とシステム安定性のバランスを取るために設定された値です。
*   **`timeBeginPeriod`関数**: `timeBeginPeriod`はWindows Multimedia APIの一部であり、システム全体のタイマー解像度を変更するために使用されます。この関数は、指定された期間（ミリ秒単位）をシステムタイマーの最小解像度として設定します。例えば、`timeBeginPeriod(1)`を呼び出すと、システムタイマーの解像度は1ミリ秒に設定されます。
*   **`timeEndPeriod`関数**: `timeBeginPeriod`で変更されたタイマー解像度を元に戻すために使用されます。`timeBeginPeriod`を呼び出したプロセスは、終了する前に`timeEndPeriod`を呼び出してタイマー解像度を元の状態に戻すことが推奨されます。しかし、多くのアプリケーションはこれを適切に行わないことがあり、システム全体に影響を与え続けることがあります。
*   **グローバルな影響**: `timeBeginPeriod`の最も重要な特性は、その効果が呼び出したプロセスに限定されず、システム全体に及ぶことです。これは、一つのアプリケーションがシステム全体のタイマー解像度を永続的に変更し、他のすべてのアプリケーションの動作や電力消費に影響を与える可能性があることを意味します。

### Goランタイムスケジューラ

Goランタイムは、Goプログラム内で実行されるゴルーチン（軽量スレッド）のスケジューリングを担当します。Goスケジューラは、OSのスレッド上で多数のゴルーチンを効率的に多重化し、並行処理を実現します。

*   **M:Nスケジューリング**: Goスケジューラは、M個のゴルーチンをN個のOSスレッドにマッピングするM:Nスケジューリングモデルを採用しています。これにより、OSスレッドの切り替えコストを最小限に抑えつつ、多数のゴルーチンを効率的に実行できます。
*   **タイマーの利用**: スケジューラは、タイムスライス、ネットワークI/Oの待機、タイマーイベントなど、さまざまな要因に基づいてゴルーチンを切り替えます。これらの操作には、正確な時間計測が不可欠です。
*   **以前の依存性**: 以前のGoスケジューラは、Windows上での高精度な時間計測のために`timeBeginPeriod`によって提供される1ミリ秒のタイマー解像度に依存していました。これにより、スケジューリングの精度が向上し、特にI/Oバウンドなアプリケーションでの応答性が改善されると考えられていました。

### Issue #8687

GoのIssue #8687は、「runtime: timeBeginPeriod causes high CPU usage on Windows」というタイトルで、`timeBeginPeriod`の使用がWindows上での高いCPU使用率と電力消費を引き起こす問題について議論されたものです。このIssueでは、`timeBeginPeriod`がシステム全体に与える悪影響が詳細に報告され、Goランタイムがこの関数への依存を解消すべきであるという結論に至りました。このIssueの議論と解決策が、今回のコミットの直接的な動機となっています。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがWindowsの`timeBeginPeriod` APIへの依存を完全に排除した点にあります。

以前のGoランタイムは、Windowsのデフォルトのタイマー解像度（約15ms）ではGoスケジューラの効率が低下すると考え、`timeBeginPeriod(1)`を呼び出してシステム全体のタイマー解像度を1msに引き上げていました。これにより、スケジューラはより短い間隔でゴルーチンを切り替えることができ、特にI/O待機や短いタイムアウトを伴う処理において、より迅速な応答性を実現していました。

しかし、このアプローチには以下の問題がありました。

1.  **グローバルな副作用**: `timeBeginPeriod`はシステム全体に影響を与えるため、Goプログラムが実行されている間、他のすべてのアプリケーションも1msのタイマー解像度で動作することになります。これは、Goプログラムが終了しても、`timeEndPeriod`が適切に呼び出されない限り、システム全体が不必要に高いタイマー解像度で動作し続ける可能性がありました。
2.  **電力消費の増加**: 高いタイマー解像度は、OSがより頻繁にタイマー割り込みを処理する必要があることを意味します。これにより、CPUがアイドル状態になる時間が減少し、省電力モードへの移行が妨げられ、結果として電力消費が増加します。これは、特にバッテリー駆動のデバイスにとって大きな問題でした。
3.  **システムパフォーマンスへの影響**: 頻繁なタイマー割り込みは、コンテキストスイッチのオーバーヘッドを増加させ、システム全体のパフォーマンスにわずかながら悪影響を与える可能性がありました。

このコミットは、Austin Clements氏（@aclements）によるGoスケジューラの内部的な改善により、これらの問題が解決されたことを示しています。具体的には、スケジューラが`timeBeginPeriod`によって提供される高精度なタイマー解像度に依存することなく、効率的に動作するように最適化されました。これにより、Goランタイムはもはやシステム全体のタイマー解像度を変更する必要がなくなり、Windowsシステムリソースをより適切に管理できるようになりました。

変更は主に以下の3つのファイルに及びます。

*   `src/runtime/export_windows_test.go`: テスト目的で`timeBeginPeriodRetValue`をエクスポートしていた部分が削除されました。これは、`timeBeginPeriod`が呼び出されなくなったため、その戻り値をテストする必要がなくなったことを意味します。
*   `src/runtime/os1_windows.go`: `_timeBeginPeriod`関数のインポート宣言、`timeBeginPeriodRetValue`変数の宣言、および`osinit`関数内での`_timeBeginPeriod`の呼び出しが削除されました。これは、GoランタイムがこのAPIを完全に利用しなくなったことを直接的に示しています。
*   `src/runtime/syscall_windows_test.go`: `TestTimeBeginPeriod`というテスト関数が削除されました。このテストは、`timeBeginPeriod`の呼び出しが成功したかどうかを確認するためのものでしたが、関数自体が呼び出されなくなったため、このテストも不要になりました。

この変更は、GoランタイムがWindows環境において、より「行儀の良い」市民となり、システム全体の安定性と電力効率に貢献することを目指したものです。

## コアとなるコードの解説

このコミットは、GoランタイムがWindowsの`timeBeginPeriod` APIを使用しないようにするための、直接的かつ包括的な変更です。

1.  **`src/runtime/export_windows_test.go`の変更**:
    *   `TimeBeginPeriodRetValue`は、`timeBeginPeriod`関数の呼び出し結果をテストするためにエクスポートされていた変数です。`timeBeginPeriod`が呼び出されなくなったため、この変数をエクスポートする必要がなくなり、関連するコードが削除されました。これは、このAPIへの依存が完全に断ち切られたことを示唆しています。

2.  **`src/runtime/os1_windows.go`の変更**:
    *   `//go:cgo_import_dynamic runtime._timeBeginPeriod timeBeginPeriod%1 "winmm.dll"`: この行は、`winmm.dll`ライブラリから`timeBeginPeriod`関数を動的にインポートするためのGoコンパイラディレクティブでした。この行が削除されたことで、Goランタイムはもはや`timeBeginPeriod`関数をロードしようとしなくなります。
    *   `_timeBeginPeriod stdFunction`: `stdFunction`型は、Windows API関数へのポインタを保持するためにGoランタイム内で定義された型です。この変数が削除されたことで、`timeBeginPeriod`への参照がコードベースからなくなりました。
    *   `var timeBeginPeriodRetValue uint32`: `timeBeginPeriod`の呼び出し結果を格納するためのグローバル変数でした。この変数が不要になったため、宣言が削除されました。
    *   `timeBeginPeriodRetValue = uint32(stdcall1(_timeBeginPeriod, 1))`: `osinit`関数はGoランタイムの初期化時に呼び出される関数です。この行では、`timeBeginPeriod(1)`を実際に呼び出し、その戻り値を`timeBeginPeriodRetValue`に格納していました。この行が削除されたことで、Goランタイムは起動時にシステムタイマーの解像度を変更しなくなります。

3.  **`src/runtime/syscall_windows_test.go`の変更**:
    *   `func TestTimeBeginPeriod(t *testing.T)`: このテスト関数は、`timeBeginPeriod`の呼び出しがエラーなく成功したことを確認するためのものでした。`timeBeginPeriod`が呼び出されなくなったため、このテストは無意味になり、削除されました。

これらの変更は、GoランタイムがWindowsのタイマー解像度を操作するメカニズムを完全に削除し、スケジューラがその機能に依存しないように再設計されたことを明確に示しています。これにより、GoプログラムはWindowsシステム上でよりクリーンに動作し、他のアプリケーションやシステム全体の電力効率に悪影響を与えることがなくなります。

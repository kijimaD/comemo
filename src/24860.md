## 変更の背景

Go言語では、ポインタのデリファレンス（間接参照）を行う前に、そのポインタが`nil`でないことを保証する必要があります。もし`nil`ポインタをデリファレンスしようとすると、ランタイムパニックが発生します。コンパイラは、このようなパニックを防ぐために、ポインタのデリファレンス前に自動的にnilチェックを挿入します。

しかし、開発者がコード内で明示的に`if p != nil`のようなnilチェックを記述することもよくあります。このようなユーザーが記述したnilチェックと、コンパイラが自動挿入するnilチェックが重複する場合、冗長なチェックが発生し、実行効率が低下する可能性があります。

GoコンパイラのSSAバックエンドには、冗長なnilチェックを除去する最適化パス（`nilcheckelim`）が存在します。この最適化パスは、主にコンパイラが自動挿入したnilチェックを対象としていました。このコミットの背景には、ユーザーが記述した明示的なnilチェックも、この強力な最適化パスの恩恵を受けられるようにしたいという意図があります。

具体的には、ユーザーが記述した`p != nil`や`p == nil`といった比較を、コンパイラ内部でより抽象的で最適化しやすい`OpIsNonNil`という形式に統一することで、`nilcheckelim`パスがこれらのチェックも効率的に除去できるようにすることが目的です。これにより、コンパイラはより賢く冗長なチェックを排除し、生成されるコードのパフォーマンスを向上させることができます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **GoコンパイラのSSA (Static Single Assignment) フォーム**:
    Goコンパイラの最適化フェーズの一つで、プログラムのコードをSSA形式という中間表現に変換します。SSA形式では、各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。GoコンパイラのSSAバックエンドは、`src/cmd/compile/internal/ssa`ディレクトリに実装されており、様々な最適化パス（例: deadcode elimination, nilcheck elimination, bounds check eliminationなど）が適用されます。

2.  **SSAオペレーション (Op)**:
    SSA形式における基本的な操作単位です。例えば、`OpAdd`は加算、`OpLoad`はメモリからの読み込み、`OpStore`はメモリへの書き込みなどを表します。このコミットで登場する主なオペレーションは以下の通りです。
    *   `OpNeqPtr`: 2つのポインタが等しくないか（`!=`）を比較する。
    *   `OpEqPtr`: 2つのポインタが等しいか（`==`）を比較する。
    *   `OpConstNil`: `nil`定数を表す。
    *   `OpIsNonNil`: あるポインタが`nil`でないことをチェックする。これはコンパイラが内部的に生成する安全チェックの一つです。
    *   `OpNot`: 論理否定。

3.  **nilチェック除去 (nilcheck elimination)**:
    Goコンパイラの最適化パスの一つで、プログラムの実行中に`nil`ポインタデリファレンスによるパニックが発生しないことを保証しつつ、冗長なnilチェックを削除します。例えば、あるポインタ`p`が既に`nil`でないことが証明されているスコープ内で、再度`p`のnilチェックが必要なデリファレンスが行われる場合、そのnilチェックは除去されます。

4.  **リライトルール (Rewrite Rules)**:
    SSAバックエンドでは、`generic.rules`ファイルに記述されたルールに基づいて、SSAオペレーションのパターンマッチングと書き換えが行われます。これにより、より効率的なオペレーションに変換したり、特定の最適化を適用したりします。

5.  **コンパイラパスの順序**:
    SSAバックエンドでは、複数の最適化パスが特定の順序で実行されます。パスの順序は、あるパスの出力が別のパスの入力として最適であることを保証するために重要です。`compile.go`内の`passOrder`で定義されています。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのSSAバックエンドにおけるnilチェックの表現と最適化の連携を強化することにあります。

1.  **`OpIsNonNil`の役割の拡張**:
    これまで`OpIsNonNil`は、主にコンパイラが自動的に挿入するnilチェック（例: `p.Method()`を呼び出す前の`p`のチェック）を表現するために使用されていました。このコミットでは、ユーザーが明示的に記述した`p != nil`や`p == nil`といった比較も、SSA形式に変換される際に`OpIsNonNil`（またはその否定）として表現されるように変更されます。

2.  **リライトルールの追加 (`src/cmd/compile/internal/ssa/gen/generic.rules`)**:
    `generic.rules`ファイルに以下のリライトルールが追加されました。
    *   `(NeqPtr p (ConstNil)) -> (IsNonNil p)`: ポインタ`p`が`nil`と等しくない（`p != nil`）という比較を、`p`が`nil`でない（`IsNonNil p`）という表現に書き換えます。
    *   `(NeqPtr (ConstNil) p) -> (IsNonNil p)`: 上記の逆順の引数も同様に書き換えます。
    *   `(EqPtr p (ConstNil)) -> (Not (IsNonNil p))`: ポインタ`p`が`nil`と等しい（`p == nil`）という比較を、`p`が`nil`でないことの否定（`Not (IsNonNil p)`）に書き換えます。
    *   `(EqPtr (ConstNil) p) -> (Not (IsNonNil p))`: 上記の逆順の引数も同様に書き換えます。
    これらのルールは、`rewritegeneric.go`で実際に実装されます。

3.  **`rewritegeneric.go`での実装**:
    `rewriteValuegeneric`関数内に、`OpEqPtr`と`OpNeqPtr`に対する新しいリライトロジックが追加されました。これは、`p == nil`や`p != nil`というパターンを検出し、それらを`OpIsNonNil`（または`OpNot`と`OpIsNonNil`の組み合わせ）に変換する具体的なコードです。この変換は、SSA値のオペレーション、型、引数を適切に設定することで行われます。

4.  **コンパイラパス順序の調整 (`src/cmd/compile/internal/ssa/compile.go`)**:
    `passOrder`に`{"opt", "nilcheckelim"}`という新しい依存関係が追加されました。これは、「`opt`パス（最適化パス、リライトルールが適用される）が`nilcheckelim`パスの前に実行されるべきである」ことを示しています。この順序は非常に重要です。なぜなら、ユーザーのnilチェックが`OpIsNonNil`に書き換えられるのは`opt`パスの仕事であり、その書き換えが行われた後に初めて`nilcheckelim`パスがそれらの`OpIsNonNil`を最適化の対象として認識し、冗長なチェックを除去できるからです。

5.  **`OpIsNonNil`の型情報の明示 (`src/cmd/compile/internal/ssa/gen/genericOps.go`)**:
    `OpIsNonNil`, `IsInBounds`, `IsSliceInBounds`の定義に`typ: "Bool"`が追加されました。これは、これらのオペレーションがブール型の結果を生成することを明示的に示すものです。これにより、SSA形式の型チェックがより厳密になり、コンパイラの健全性が向上します。

6.  **`nilcheck.go`のコメント更新**:
    `nilcheckelim`関数内のコメントが更新され、`OpIsNonNil`のfalseブランチ（つまりポインタが`nil`であるケース）の扱いに関する説明がより明確になりました。これは、`OpIsNonNil`への変換が、nilチェック除去パスの動作にどのように影響するかを反映しています。

これらの変更により、コンパイラはユーザーが記述したnilチェックと、自身が挿入するnilチェックを統一的な`OpIsNonNil`という表現で扱うことができるようになります。これにより、`nilcheckelim`パスは、プログラム全体のnilチェックの冗長性をより広範囲にわたって分析し、除去することが可能になります。結果として、実行時のnilチェックのオーバーヘッドが減少し、プログラムのパフォーマンスが向上します。

## コアとなるコードの解説

このコミットの核となる変更は、`src/cmd/compile/internal/ssa/gen/generic.rules`で定義され、`src/cmd/compile/internal/ssa/rewritegeneric.go`で実装されているリライトルールです。

**`generic.rules`の追加ルール:**

```
// user nil checks
(NeqPtr p (ConstNil)) -> (IsNonNil p)
(NeqPtr (ConstNil) p) -> (IsNonNil p)
(EqPtr p (ConstNil)) -> (Not (IsNonNil p))
(EqPtr (ConstNil) p) -> (Not (IsNonNil p))
```

これらのルールは、Goのソースコードで`p != nil`や`p == nil`と書かれた比較が、SSA形式に変換された際にどのように内部表現されるかを定義しています。

*   `NeqPtr p (ConstNil)`: これは`p != nil`というコードに対応します。このルールは、この比較を`IsNonNil p`というオペレーションに変換します。`IsNonNil`は「`p`が`nil`ではない」という事実を表すブール値を生成します。
*   `EqPtr p (ConstNil)`: これは`p == nil`というコードに対応します。このルールは、この比較を`Not (IsNonNil p)`というオペレーションに変換します。これは「`p`が`nil`ではない」という事実の論理否定、つまり「`p`が`nil`である」ことを表します。

**`rewritegeneric.go`での実装:**

`rewritegeneric.go`内の`rewriteValuegeneric`関数は、これらのルールを具体的なGoコードとして実装しています。例えば、`OpNeqPtr`の場合のコードを見てみましょう。

```go

		{
			p := v.Args[0]

				goto endba798520b4d41172b110347158c44791

			v.AuxInt = 0

			v.resetArgs()
			v.AddArg(p) // 引数をpのみにする

このコードは、SSA値`v`が`OpNeqPtr`オペレーションであり、その2番目の引数（`v.Args[1]`）が`OpConstNil`である場合（つまり`p != nil`のパターン）、`v`のオペレーションを`OpIsNonNil`に書き換え、引数をポインタ`p`のみに設定します。`OpEqPtr`の場合も同様に、`OpNot`と`OpIsNonNil`の組み合わせに変換されます。

この変換が行われることで、`nilcheckelim`パスは、ユーザーが明示的に書いた`p != nil`や`p == nil`という条件分岐も、コンパイラが自動挿入するnilチェックと同じ`OpIsNonNil`という統一された形式で扱うことができるようになります。これにより、`nilcheckelim`は、既に`p`が`nil`でないことが証明されているコードパスにおいて、これらのユーザー定義のnilチェックも冗長であると判断し、除去することが可能になります。

`compile.go`におけるパス順序の変更は、このリライトが`nilcheckelim`の前に確実に行われるようにするための重要な調整です。これにより、`nilcheckelim`は常に最新の、`OpIsNonNil`に統一されたnilチェック表現に対して動作し、最大限の最適化効果を発揮できます。

`nilcheck_test.go`に追加された`TestNilcheckUser`は、この新しい動作を検証するためのものです。このテストでは、まず`OpNeqPtr`によるユーザーnilチェックを定義し、その後に`OpIsNonNil`によるチェックを定義します。`opt`パスと`nilcheckelim`パスを実行した後、最初のユーザーnilチェックによって2番目の`OpIsNonNil`チェックが除去されていることを確認します。これは、このコミットの意図通りの最適化が機能していることを示しています。

		v.resetArgs()
		v.AddArg(v0.Args[1])
		return true
	}
```

このコードは、`OpNeqPtr`オペレーションが`ConstNil`と比較されている場合、そのオペレーションを`OpIsNonNil`に変換します。同様に、`OpEqPtr`オペレーションが`ConstNil`と比較されている場合は、`OpNot`と`OpIsNonNil`の組み合わせに変換されます。

この変更により、コンパイラはユーザーが記述したnilチェックと、自身が挿入するnilチェックを統一的な`OpIsNonNil`という表現で扱うことができるようになります。これにより、`nilcheckelim`パスは、プログラム全体のnilチェックの冗長性をより広範囲にわたって分析し、除去することが可能になります。結果として、実行時のnilチェックのオーバーヘッドが減少し、プログラムのパフォーマンスが向上します。

`compile.go`におけるパス順序の変更は、このリライトが`nilcheckelim`の前に確実に行われるようにするための重要な調整です。これにより、`nilcheckelim`は常に最新の、`OpIsNonNil`に統一されたnilチェック表現に対して動作し、最大限の最適化効果を発揮できます。

`nilcheck_test.go`に追加された`TestNilcheckUser`は、この新しい動作を検証するためのものです。このテストでは、まず`OpNeqPtr`によるユーザーnilチェックを定義し、その後に`OpIsNonNil`によるチェックを定義します。`opt`パスと`nilcheckelim`パスを実行した後、最初のユーザーnilチェックによって2番目の`OpIsNonNil`チェックが除去されていることを確認します。これは、このコミットの意図通りの最適化が機能していることを示しています。

## コアとなるコードの解説

このコミットの主要な変更は、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるnilチェックの扱いを改善し、より多くの冗長なnilチェックを削除できるようにすることです。

具体的には、Goのコードで書かれた`p != nil`や`p == nil`のようなポインタと`nil`の比較を、SSA内部表現の`OpIsNonNil`というオペレーションに変換するリライトルールが導入されました。

### 変更の目的とメカニズム

1.  **`OpIsNonNil`への統一**:
    Goコンパイラは、ポインタのデリファレンス（例: `p.field`や`*p`）の前に、そのポインタが`nil`でないことを保証するために自動的にnilチェックを挿入します。これらの自動挿入されるチェックは、SSA内部では`OpIsNonNil`というオペレーションで表現されます。
    このコミット以前は、ユーザーがコードで明示的に書いた`p != nil`や`p == nil`といったチェックは、`OpNeqPtr`や`OpEqPtr`といった異なるオペレーションで表現されていました。
    この変更の目的は、ユーザーが書いたnilチェックも`OpIsNonNil`（またはその否定である`Not (IsNonNil p)`）という統一された形式に変換することで、コンパイラのnilチェック除去パス（`nilcheckelim`）が、自動挿入されたチェックとユーザーが書いたチェックの両方を同じメカニズムで最適化できるようにすることです。

2.  **リライトルールの追加 (`src/cmd/compile/internal/ssa/gen/generic.rules`)**:
    `generic.rules`ファイルは、SSAオペレーションのパターンマッチングと書き換えを定義するルールベースのシステムです。このコミットでは、以下の4つのルールが追加されました。

    *   `(NeqPtr p (ConstNil)) -> (IsNonNil p)`:
        これは、`p != nil`という比較を`IsNonNil p`に変換します。`NeqPtr`は「等しくない」を意味し、`ConstNil`は`nil`定数を意味します。つまり、「`p`が`nil`と等しくない」という条件は、「`p`が`nil`ではない」という条件と同じ意味になります。

    *   `(NeqPtr (ConstNil) p) -> (IsNonNil p)`:
        上記のルールの引数の順序が逆の場合（`nil != p`）も同様に変換します。

    *   `(EqPtr p (ConstNil)) -> (Not (IsNonNil p))`:
        これは、`p == nil`という比較を`Not (IsNonNil p)`に変換します。`EqPtr`は「等しい」を意味します。つまり、「`p`が`nil`と等しい」という条件は、「`p`が`nil`ではない」という条件の論理否定と同じ意味になります。

    *   `(EqPtr (ConstNil) p) -> (Not (IsNonNil p))`:
        上記のルールの引数の順序が逆の場合（`nil == p`）も同様に変換します。

3.  **リライトの実装 (`src/cmd/compile/internal/ssa/rewritegeneric.go`)**:
    `rewritegeneric.go`ファイルには、`generic.rules`で定義された抽象的なルールを、SSA値を実際に書き換えるGoコードとして実装するロジックが含まれています。
    例えば、`OpNeqPtr`の場合、コードは`v.Op = OpIsNonNil`と`v.AddArg(p)`を実行することで、`NeqPtr`オペレーションを`IsNonNil`オペレーションに変換し、その引数を元のポインタ`p`のみに設定します。`OpEqPtr`の場合は、`OpNot`オペレーションを新しく作成し、その引数として`OpIsNonNil`オペレーションを挿入するという、少し複雑な変換が行われます。

4.  **パス順序の調整 (`src/cmd/compile/internal/ssa/compile.go`)**:
    SSAバックエンドでは、様々な最適化パスが特定の順序で実行されます。このコミットでは、`passOrder`配列に`{"opt", "nilcheckelim"}`という制約が追加されました。これは、リライトルールが適用される`opt`パスが、nilチェック除去を行う`nilcheckelim`パスの前に実行されることを保証します。この順序は極めて重要です。なぜなら、ユーザーのnilチェックが`OpIsNonNil`に変換されていなければ、`nilcheckelim`パスはそれらを最適化の対象として認識できないからです。

5.  **型情報の明示 (`src/cmd/compile/internal/ssa/gen/genericOps.go`)**:
    `OpIsNonNil`などのオペレーションに`typ: "Bool"`が追加されました。これは、これらのオペレーションがブール型の結果を生成することをコンパイラに明示的に伝えるもので、SSA形式の型健全性を向上させます。

### 最適化の効果

これらの変更により、`nilcheckelim`パスは、ユーザーが明示的に記述したnilチェックと、コンパイラが自動挿入したnilチェックの両方を、`OpIsNonNil`という統一されたセマンティクスで扱うことができるようになります。
例えば、以下のようなコードがあったとします。

```go
func foo(p *int) {
    if p != nil { // ユーザーが書いたnilチェック
        _ = *p     // コンパイラがnilチェックを挿入する可能性がある
    }
}
```

このコミットが適用されると、`if p != nil`はSSA内部で`IsNonNil p`に変換されます。もし、その後の`_ = *p`のデリファレンス箇所で、既に`p`が`nil`でないことが`IsNonNil p`によって証明されている場合、`nilcheckelim`パスは`_ = *p`の前の冗長なnilチェックを除去することができます。

コミットメッセージにある「10% more nilchecks (34110 vs 31088)」という数字は、この最適化がGoの標準ライブラリやツールチェイン全体で、実際に多くの冗長なnilチェックを除去することに成功したことを示しています。これにより、Goプログラムの実行時パフォーマンスがわずかながらも向上することが期待されます。

This commit fixes this by rewriting user nil checks as `OpIsNonNil` so our nil check elimination pass can take advantage and remove redundant checks.

The pass order in `src/cmd/compile/internal/ssa/compile.go` is also updated to ensure that the rewrite happens before the nil check elimination pass.

This change results in a 10% increase in removed nil checks (34110 vs 31088) when running `make.bash`.

# [インデックス 20479] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）とGoランタイムに、ライトバリア（write barrier）を導入するものです。これは、Go 1.5で導入される予定の並行ガベージコレクション（GC）の準備として行われました。ライトバリアは、ポインタの書き込み時に特定の処理を挿入することで、GCの正確性を保証するために不可欠なメカニズムです。

## 変更の背景

このコミットは、Go 1.5で導入される予定の新しい並行ガベージコレクタ（GC）の基盤を築くための重要なステップです。Go 1.4では、GCの「ストップ・ザ・ワールド」（STW）ポーズを最小限に抑えることを目的とした並行GCの準備として、ヒープ内のポインタ値への書き込みがライトバリアを介して行われるようになりました。

ライトバリアは、並行GC中にデータの整合性を維持するために不可欠です。プログラム（「ミューテーター」）がポインタを変更する際に、GCがこれらの変更を正確に追跡できるようにします。これにより、まだ到達可能なオブジェクトが誤って収集されたり、マークされずに残されたりするのを防ぎます。

この変更は、将来のGC改善のために不可欠でしたが、Go 1.4では一部のシナリオでわずかな速度低下を引き起こす可能性がありました。しかし、これはより予測可能なパフォーマンスに貢献し、完全に正確なガベージコレクタを可能にしました。コミットメッセージにもあるように、この変更の目的は「速度を落とすこと（そして正しくあること）」であり、Go 1.3と同等以上の速度をGo 1.4で実現するための最適化は、後続のコミットで検討される予定でした。

## 前提知識の解説

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に割り当てたメモリ領域のうち、もはや使用されていない（到達不可能になった）ものを自動的に解放するプロセスです。これにより、開発者は手動でのメモリ管理の複雑さから解放され、メモリリークのリスクを低減できます。

### 並行ガベージコレクション

従来のGCは、メモリ解放のためにプログラムの実行を一時停止させる「ストップ・ザ・ワールド」（STW）ポーズを必要としました。STWポーズは、特に大規模なアプリケーションにおいて、レイテンシの増加やユーザー体験の悪化につながる可能性があります。並行GCは、プログラムの実行とGCの作業を同時に行うことで、STWポーズの時間を大幅に短縮することを目指します。

### 三色マーク＆スイープアルゴリズム

GoのGCは、三色マーク＆スイープアルゴリズムを利用しています。このアルゴリズムでは、オブジェクトを以下の3つの色で分類します。

*   **白 (White)**: GCによってまだ訪問されていないオブジェクト。最終的に収集される可能性がある。
*   **灰 (Gray)**: GCによって訪問されたが、その参照先のオブジェクトがまだ訪問されていないオブジェクト。
*   **黒 (Black)**: GCによって訪問され、その参照先のオブジェクトもすべて訪問されたオブジェクト。収集されない。

GCのマークフェーズでは、ルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトをマークしていきます。

### ライトバリア (Write Barrier)

並行GCにおいて、プログラムが実行中にポインタを書き換える（例: `*p = x`）と、GCの正確性が損なわれる可能性があります。例えば、GCがオブジェクトAをマークし終えた直後に、プログラムがAからBへの参照を削除し、CからBへの参照を追加した場合、GCがCをまだマークしていなければBが誤って収集されてしまう可能性があります。

ライトバリアは、このような問題を解決するために、ポインタの書き込み操作の直前に挿入される小さなコードスニペットです。ライトバリアの目的は、ポインタの変更がGCの正確な動作を妨げないように、GCにその変更を通知することです。

Goは、Yuasaスタイルの削除バリアとDijkstra挿入バリアの両方の側面を組み合わせたハイブリッドライトバリアを採用しています。このハイブリッドアプローチは、STWポーズの期間を短縮するのに役立ちます。

## 技術的詳細

このコミットでは、Goコンパイラ（`cmd/gc`）がポインタの書き込み操作を検出し、適切なランタイムのライトバリア関数呼び出しに変換するメカニズムを導入しています。

具体的には、以下の変更が行われました。

1.  **ランタイムライトバリア関数の宣言**:
    `src/cmd/gc/builtin.c` および `src/cmd/gc/runtime.go` に、新しいランタイム関数が宣言されました。これらは、特定の型のポインタ書き込みに対応します。
    *   `runtime.writebarrierptr(dst *any, src any)`: 汎用ポインタの書き込み
    *   `runtime.writebarrierstring(dst *any, src any)`: 文字列の書き込み
    *   `runtime.writebarrierslice(dst *any, src any)`: スライスの書き込み
    *   `runtime.writebarrieriface(dst *any, src any)`: インターフェースの書き込み
    *   `runtime.writebarrierfat(typ *byte, dst *any, src *any)`: 任意の型の書き込み（サイズが大きい場合など）

2.  **コンパイラによるライトバリアの挿入ロジック**:
    `src/cmd/gc/walk.c` に、`applywritebarrier` 関数と `needwritebarrier` 関数が追加されました。
    *   `needwritebarrier(Node *l, Node *r)`: `l = r` という代入に対してライトバリアが必要かどうかを判断します。以下の場合はライトバリアを挿入しません。
        *   `use_writebarrier` フラグがオフの場合（`-wb=0` で無効化可能）
        *   `l` がnilまたはブランク識別子の場合
        *   `l` の型がポインタを含まない場合
        *   `l` がスタック上の変数である場合
        *   `r` がnil（ゼロクリア）の場合
        *   `r` がリテラル定数である場合
        *   `r` が静的（読み取り専用）データへの参照である場合
        *   `r` がスタック上の値のアドレスである場合
        *   `r` がグローバル変数（常にライブ）のアドレスである場合
        *   上記以外の場合、保守的にライトバリアを挿入します。
    *   `applywritebarrier(Node *n, NodeList **init)`: `n` が代入ノードであり、`needwritebarrier` が真を返す場合に、適切な `runtime.writebarrier*` 関数呼び出しに変換します。

3.  **初期化処理へのライトバリア適用**:
    `src/cmd/gc/sinit.c` では、構造体リテラル、配列リテラル、スライスリテラルの初期化処理において、`orderstmtinplace` と `walkstmt` を呼び出すように変更されました。これにより、初期化時の代入操作にもライトバリアが適用されるようになります。

4.  **ランタイムでのライトバリアの実装**:
    `src/runtime/mgc0.go` に、上記で宣言された `writebarrierptr`、`writebarrierstring`、`writebarrierslice`、`writebarrieriface`、`writebarrierfat` の実際のGo言語による実装が追加されました。これらの関数は、`//go:nosplit` ディレクティブが付与されており、スタックの分割を避けることで、GCの動作中に安全に呼び出せるようになっています。これらの実装自体は、単にメモリコピーを行うか、ポインタを代入するだけのシンプルなものです。

5.  **コンパイラフラグの追加**:
    `src/cmd/gc/lex.c` に、ライトバリアの有効/無効を切り替えるための `-wb` フラグが追加されました。デフォルトでは有効（`use_writebarrier = 1`）です。

この変更により、Goプログラムのポインタ書き込みは、コンパイル時にランタイムのライトバリア関数呼び出しに変換されるようになり、Goの並行GCの正確性が保証されるようになりました。

## コアとなるコードの解説

### `src/cmd/gc/walk.c` におけるライトバリア挿入ロジック

`walk.c` はGoコンパイラのバックエンドの一部であり、抽象構文木（AST）を走査してコード生成の準備を行います。このファイルにライトバリア挿入の主要なロジックが追加されました。

*   **`needwritebarrier(Node *l, Node *r)` 関数**:
    この関数は、代入 `l = r` がライトバリアを必要とするかどうかを決定します。
    重要な点は、すべてのポインタ書き込みにライトバリアが必要なわけではないということです。例えば、スタック上の変数への書き込み、定数や静的データへの書き込み、ゼロクリアなどは、GCの正確性に影響を与えないため、ライトバリアは不要です。この関数は、これらの最適化を適用し、不要なライトバリアの挿入を避けます。

*   **`applywritebarrier(Node *n, NodeList **init)` 関数**:
    この関数は、代入ノード `n` を受け取り、`needwritebarrier` が真を返す場合に、その代入をランタイムのライトバリア関数呼び出しに変換します。
    変換は、代入される値の型に基づいて、`runtime.writebarrierptr`、`runtime.writebarrierstring`、`runtime.writebarrierslice`、`runtime.writebarrieriface`、または `runtime.writebarrierfat` のいずれかの関数呼び出しを生成します。これにより、コンパイラはポインタの書き込みをインターセプトし、GCが必要な処理を実行できるようにします。

### `src/runtime/mgc0.go` におけるライトバリアの実装

`mgc0.go` はGoランタイムのガベージコレクタの初期部分を定義しています。ここに、コンパイラが生成するライトバリア関数呼び出しの実際のGo言語による実装が追加されました。

*   **`writebarrierptr`, `writebarrierstring`, `writebarrierslice`, `writebarrieriface`, `writebarrierfat` 関数**:
    これらの関数は、それぞれ異なる型のポインタ書き込みに対応するライトバリアの実装です。
    注目すべきは、これらの関数が `//go:nosplit` ディレクティブでマークされている点です。これは、これらの関数が実行中にスタックを分割しないことを保証します。GCが動作している最中にこれらの関数が呼び出される可能性があるため、スタックの変更がGCの正確性を損なわないようにするために重要です。
    これらの関数の実装自体は非常にシンプルで、基本的にはポインタの代入やメモリコピーを行うだけです。ライトバリアの「処理」は、これらの関数が呼び出されること自体にあり、GCがその呼び出しをフックして必要なマーク処理などを行うことができるようになります。

## 変更の背景

この変更は、Goランタイムの`snprintf`関数が新しい文字列を割り当てることによって発生していた、Plan 9ビルドでの`gomallocgc`クラッシュを修正するために行われました。

問題の根本原因は、`snprintf`が内部で文字列を動的に割り当てる際に、ガベージコレクタ（`gomallocgc`）との間で問題を引き起こしていたことにあります。この問題はPlan 9に限定されたものではありませんでしたが、Plan 9ではエラー文字列の生成に`snprintf`が多用されていたため、特に顕著にクラッシュが発生していました。他のシステムでは、エラーパスで`snprintf`がそれほど頻繁に使用されていなかったため、この問題は表面化しにくかったと考えられます。

このコミットは、`snprintf`内での動的な文字列割り当てを回避することで、このクラッシュを一時的に回避するワークアラウンドとして導入されました。しかし、この変更は後に`linux-arm-panda`ビルドを壊すという予期せぬ副作用を引き起こしたことが、Go CLのコメントで示唆されています。これは、低レベルのランタイムコードにおける変更が、異なるアーキテクチャや環境で予期せぬ影響を与える可能性を示しています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのコンポーネントです。ガベージコレクション、スケジューリング、メモリ管理など、Go言語の並行性と効率性を支える重要な機能を提供します。
*   **`snprintf`**: C言語の標準ライブラリ関数に由来する概念で、Goランタイムの文脈では、指定されたバッファにフォーマットされた文字列を書き込むための関数を指します。通常、バッファオーバーフローを防ぐために最大文字数を指定できます。ランタイム内部で、デバッグ情報やエラーメッセージの生成などに使用されます。
*   **`gostring`**: Goランタイム内部で使用される関数で、Cスタイルのヌル終端バイトスライス（`*byte`）からGoの`string`型を生成します。この関数は通常、新しいメモリを割り当ててバイトスライスの内容をコピーし、Goの文字列として扱えるようにします。
*   **`gostringnocopy`**: `gostring`と同様にCスタイルのバイトスライスからGoの`string`型を生成しますが、こちらは新しいメモリを割り当てて内容をコピーするのではなく、既存のバイトスライスを指すGoの文字列ヘッダを作成します。これは、元のバイトスライスが文字列の寿命よりも長く存在することが保証されている場合に、メモリ割り当てとコピーのオーバーヘッドを避けるために使用されます。
*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステムです。Go言語の開発者の一部はPlan 9の設計思想に影響を受けており、Goの初期のビルド環境やテスト環境としてPlan 9が使用されることがありました。
*   **`gomallocgc`**: Goランタイムのガベージコレクタ（GC）の一部であり、メモリ割り当てと解放を管理します。プログラムが新しいメモリを要求した際に、必要に応じてGCが実行され、不要になったメモリを回収します。`gomallocgc`がクラッシュするということは、メモリ管理の根幹部分で深刻な問題が発生していたことを意味します。
*   **`vprintf`**: `snprintf`と同様に、可変引数リストを受け取ってフォーマットされた出力を生成する関数です。Goランタイムの内部で、`snprintf`から呼び出される形で使用されます。
*   **`getg()`**: 現在実行中のゴルーチン（goroutine）の内部表現（`g`構造体）へのポインタを取得するランタイム関数です。ゴルーチン固有のデータ（例えば、`writebuf`）にアクセスするために使用されます。
*   **文字列の割り当て**: Goの`string`型は不変（immutable）です。そのため、既存のバイトスライスから新しい文字列を作成する場合、通常は新しいメモリ領域が割り当てられ、元のバイトスライスの内容がそこにコピーされます。これは、文字列操作の安全性と効率性を保証するためのGoの設計原則の一部です。しかし、低レベルのランタイムコードでは、この割り当てがパフォーマンスやメモリ管理のボトルネックになることがあります。

## 技術的詳細

このコミットの技術的詳細の中心は、`snprintf`関数内で`gostring`の代わりに`gostringnocopy`を使用することによって、動的な文字列割り当てを回避する点にあります。

Goの`string`型は、内部的にはポインタと長さを持つ構造体（文字列ヘッダ）として表現されます。`gostring(s)`が呼び出されると、`s`が指すバイト列の内容が新しいメモリ領域にコピーされ、その新しいメモリ領域を指す文字列ヘッダが作成されます。これは、Goの文字列が不変であるという特性を維持し、元のバイト列が変更されても文字列の内容が影響を受けないようにするためです。

しかし、`snprintf`のような低レベルのランタイム関数では、このようなメモリ割り当てとコピーのオーバーヘッドが問題となる場合があります。特に、ガベージコレクタ（`gomallocgc`）が関与する状況では、予期せぬ割り当てがGCの動作と競合し、クラッシュを引き起こす可能性があります。

`gostringnocopy(s)`は、`gostring`とは異なり、新しいメモリを割り当てて内容をコピーしません。その代わりに、`s`が指す既存のバイト列を直接参照する文字列ヘッダを作成します。これは、`s`が指すメモリ領域が、作成されるGoの文字列の寿命よりも長く存在することが保証されている場合にのみ安全に使用できます。この場合、`snprintf`のコンテキストでは、`s`が指すデータが一時的なものではなく、`vprintf`が処理を終えるまで有効であることが前提とされています。

この変更により、`snprintf`が呼び出されるたびに発生していた不要なメモリ割り当てが削減され、`gomallocgc`との競合が解消されました。これにより、Plan 9ビルドでのクラッシュが修正されたと考えられます。この修正は、パフォーマンスの最適化というよりも、特定の環境での安定性の問題を解決するためのものでした。

## コアとなるコードの変更箇所

変更は`src/pkg/runtime/print1.go`ファイルの一箇所のみです。

```diff
--- a/src/pkg/runtime/print1.go
+++ b/src/pkg/runtime/print1.go
@@ -54,7 +54,7 @@ func snprintf(dst *byte, n int32, s *byte) {
 
 	gp := getg()
 	gp.writebuf = buf[0:0 : n-1] // leave room for NUL, this is called from C
-	vprintf(gostring(s), add(unsafe.Pointer(&s), unsafe.Sizeof(s)))
+	vprintf(gostringnocopy(s), add(unsafe.Pointer(&s), unsafe.Sizeof(s)))
 	buf[len(gp.writebuf)] = '\x00'
 	gp.writebuf = nil
 }
```

## コアとなるコードの解説

変更された行は以下の通りです。

```go
-	vprintf(gostring(s), add(unsafe.Pointer(&s), unsafe.Sizeof(s)))
+	vprintf(gostringnocopy(s), add(unsafe.Pointer(&s), unsafe.Sizeof(s)))
```

この変更は、`vprintf`関数に渡す引数の生成方法を変更しています。

*   **変更前**: `gostring(s)`
    *   `s`は`*byte`型であり、Cスタイルのヌル終端バイトスライスを指しています。
    *   `gostring(s)`は、このバイトスライスの内容を新しいメモリ領域にコピーし、そのコピーされた内容を指すGoの`string`型を生成します。この操作はメモリ割り当てを伴います。
*   **変更後**: `gostringnocopy(s)`
    *   `gostringnocopy(s)`は、`s`が指す既存のバイトスライスを直接参照するGoの`string`型を生成します。この操作はメモリ割り当てを伴いません。既存のバイトスライスを指す文字列ヘッダを作成するだけです。

この変更の目的は、`snprintf`が呼び出されるたびに発生していた不要なメモリ割り当てを排除することです。これにより、特にPlan 9環境で`gomallocgc`との競合によって引き起こされていたクラッシュが回避されました。`add(unsafe.Pointer(&s), unsafe.Sizeof(s))`の部分は、`vprintf`に渡される可変引数リストの開始アドレスを計算しており、このコミットの主要な変更点ではありません。

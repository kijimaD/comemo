# [インデックス 23565] ファイルの概要

このコミットは、Goリンカ (`cmd/link`) が共有ライブラリを生成する際の内部的な動作、特にABIハッシュとパッケージリストの格納方法に関する変更を導入しています。主な変更は、これらの情報をELF (Executable and Linkable Format) の「ノート」セクションに格納するようにした点です。これにより、ツールが共有ライブラリからこれらの情報をより安定して抽出できるようになり、また、ノートの書き込みメカニズムが柔軟になりました。

変更されたファイルとその役割は以下の通りです。

*   **`misc/cgo/testshared/shared_test.go`**: 共有ライブラリのテストスイート。このコミットでは、新しく導入されたELFノートからABIハッシュとパッケージリストを読み取り、検証するためのテストコードが追加されています。
*   **`src/cmd/link/internal/amd64/obj.go`**: AMD64アーキテクチャ向けのオブジェクトファイル生成に関するリンカのコード。以前のノートサイズに関する「ハック」が削除されています。
*   **`src/cmd/link/internal/ld/data.go`**: リンカのデータセクション処理に関するコード。`go.link.abihashbytes` シンボルが、新しく作成されたABIハッシュのノートセクションを指すように変更されています。
*   **`src/cmd/link/internal/ld/elf.go`**: ELF形式のファイル生成に関するリンカの主要なコード。ABIハッシュとパッケージリストをELFノートとして書き込むための新しいロジックが実装され、既存のノート書き込みメカニズムが汎用化されています。
*   **`src/cmd/link/internal/ld/lib.go`**: リンカが共有ライブラリを処理する際のコード。ELFノートからABIハッシュを読み取るための新しい関数が追加され、ABIハッシュの取得方法が変更されています。
*   **`src/cmd/link/internal/ld/symtab.go`**: リンカのシンボルテーブル処理に関するコード。ABIハッシュの計算と格納に関する一部のロジックが、ELFノートへの書き込みメカニズムに移行されたため削除されています。

## 変更の背景

このコミットの変更は、主に以下の2つの課題を解決するために行われました。

1.  **ABIハッシュ抽出の不安定性とシンボルテーブル削除時の問題**:
    Goの共有ライブラリには、そのライブラリが依存するパッケージのABI (Application Binary Interface) ハッシュが含まれています。これは、ライブラリ間の互換性を保証するために重要です。しかし、以前の実装では、このABIハッシュを抽出するための安定したAPIが存在せず、リンカ自身を含む外部ツールがこの情報を取得するのが困難でした。特に、共有ライブラリからローカルシンボルテーブルが削除（strip）された場合、ABIハッシュを特定することが不可能になるという問題がありました。これは、ABIハッシュがシンボルとして表現されていたためです。

2.  **ELFノートの固定サイズバジェットと柔軟性の欠如**:
    Goリンカには、ELFファイルに特定の情報を「ノート」として書き込む既存のメカニズムがありました。しかし、このメカニズムは、ノートをオブジェクトファイルの先頭に書き込むことを前提としており、すべてのノートが固定されたサイズバジェット内に収まる必要がありました。Goの共有ライブラリでは、パッケージリストなど、複数のノートを格納する必要があり、今後さらにノートが追加される可能性がありました。この固定サイズバジェットは、特にパッケージリストのようにサイズが大きくなる可能性のあるノートにとって制約となっていました。以前は、`-buildmode=shared` でビルドする際に、このサイズバジェットを一時的に増やす「ハック」が存在しましたが、これは根本的な解決策ではありませんでした。

これらの課題に対処するため、ABIハッシュとパッケージリストをELFの標準的なノートセクションに格納し、ノート書き込みメカニズムをより柔軟にすることで、ツールの安定性とリンカの内部的な堅牢性を向上させる必要がありました。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリなどを格納するための標準的なファイル形式です。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして実際のデータ（コード、データ、シンボルテーブルなど）で構成されます。

*   **セクション (Sections)**: リンカが処理する論理的なデータブロック（例: `.text` (コード), `.data` (初期化済みデータ), `.rodata` (読み取り専用データ), `.symtab` (シンボルテーブル)）。
*   **セグメント (Segments)**: ローダがメモリにマッピングする物理的なデータブロック。複数のセクションが1つのセグメントにまとめられることがあります。
*   **ノートセクション (Note Sections, `SHT_NOTE`)**: ELFファイル内に任意のメタデータを格納するための特殊なセクションタイプです。通常、システム固有の情報やツール固有の情報を格納するために使用されます。ノートは、名前、タイプ（タグ）、記述子（データ）で構成されます。

### ABI (Application Binary Interface) ハッシュ

ABIは、コンパイルされたプログラムが互いにやり取りする方法を定義する低レベルのインターフェースです。Go言語では、共有ライブラリを使用する際に、ライブラリがエクスポートする関数やデータ構造のレイアウトが、それを使用するプログラムと互換性があることを保証する必要があります。ABIハッシュは、Goのパッケージのインターフェース定義（型、関数シグネチャなど）から計算される一意の識別子です。リンカは、共有ライブラリをリンクする際に、依存するライブラリのABIハッシュをチェックし、不一致があればエラーを報告することで、互換性の問題を早期に検出します。

### Goの共有ライブラリ (`-buildmode=shared`)

Goは、`-buildmode=shared` オプションを使用して共有ライブラリ（`.so` ファイル）をビルドする機能を提供します。これにより、複数のGoプログラムが共通のライブラリを共有し、メモリ使用量を削減したり、ビルド時間を短縮したりすることができます。共有ライブラリは、Goのランタイムと特定のGoパッケージを含み、他のGoプログラムやCgoを介してCプログラムから利用できます。

### シンボルテーブル (Symbol Tables)

シンボルテーブルは、プログラム内の関数や変数などのシンボル名と、それらがメモリ内のどこに配置されるかという情報（アドレス）をマッピングするデータ構造です。デバッグや動的リンクに不可欠です。しかし、リリースビルドでは、ファイルサイズを削減したり、内部実装の詳細を隠蔽したりするために、シンボルテーブルが削除（strip）されることがあります。

### ELFノートの構造

ELFノートは、通常、以下の構造を持ちます。

```
+-----------------+
| namesz (4 bytes)| // nameフィールドのサイズ
+-----------------+
| descsz (4 bytes)| // descフィールドのサイズ
+-----------------+
| type (4 bytes)  | // ノートのタイプ（タグ）
+-----------------+
| name (namesz)   | // ノートの所有者または識別子（null終端されることが多い）
+-----------------+
| padding         | // 4バイトアラインメントのためのパディング
+-----------------+
| desc (descsz)   | // ノートのデータ（記述子）
+-----------------+
| padding         | // 4バイトアラインメントのためのパディング
+-----------------+
```

このコミットでは、`ELF_NOTE_GO_NAME` (`"GO\x00\x00"`) がノートの`name`として使用され、`ELF_NOTE_GOPKGLIST_TAG` (1) と `ELF_NOTE_GOABIHASH_TAG` (2) が`type`として使用されます。

## 技術的詳細

このコミットの主要な技術的変更点は、ABIハッシュとパッケージリストの格納方法を、リンカの内部シンボルや特定のセクションから、標準的なELFノートセクションへと移行したことです。

1.  **ABIハッシュとパッケージリストのELFノートへの移行**:
    *   以前は、ABIハッシュは `go.link.abihashbytes` というローカルシンボルを通じてアクセスされていました。このシンボルは、リンカが内部的に管理するデータ領域を指していました。
    *   パッケージリストも同様に、特定のリンカ内部メカニズムによって処理されていました。
    *   この変更により、ABIハッシュは `.note.go.abihash` という名前のELFノートセクションに、パッケージリストは `.note.go.pkg-list` という名前のELFノートセクションに格納されるようになりました。
    *   これらのノートは、`ELF_NOTE_GO_NAME` (`"GO\x00\x00"`) をノート名として、それぞれ `ELF_NOTE_GOABIHASH_TAG` (2) と `ELF_NOTE_GOPKGLIST_TAG` (1) をタグとして使用します。

2.  **ノート書き込みメカニズムの汎用化と柔軟性の向上**:
    *   以前のノート書き込みコードは、ノートをオブジェクトファイルの先頭に配置し、固定サイズバジェットに収める必要がありました。これは、主にコアダンプでノートを簡単に見つけるためのものでしたが、Goのノートにはこの制約は不要でした。
    *   新しい `addgonote` 関数が導入され、任意のセクション名、タグ、記述子（データ）を指定してELFノートを作成できるようになりました。この関数は、ノートの構造（`namesz`, `descsz`, `type`, `name`, `desc`、およびパディング）を適切にフォーマットし、指定されたセクションにデータを追加します。
    *   この汎用化により、ノートがファイルの先頭に限定されなくなり、また、固定サイズバジェットの制約もなくなりました。これにより、パッケージリストのようにサイズが変動する可能性のあるノートも柔軟に扱えるようになりました。

3.  **`HEADR` サイズバジェットの「ハック」の削除**:
    *   `src/cmd/link/internal/amd64/obj.go` にあった、共有ライブラリビルド時に `ld.HEADR` (ELFヘッダの予約サイズ) を3倍にするという一時的な「ハック」が削除されました。これは、パッケージリストノートが大きくなる可能性に対応するためのものでしたが、ノート書き込みメカニズムの改善により不要となりました。

4.  **ABIハッシュの参照方法の変更**:
    *   `src/cmd/link/internal/ld/data.go` では、`go.link.abihashbytes` シンボルが、新しく作成された `.note.go.abihash` セクション内のABIハッシュデータ（オフセット16バイトから始まる）を直接指すように変更されました。これにより、リンカ内部でABIハッシュを参照する既存のコードパスを最小限の変更で維持できます。
    *   `src/cmd/link/internal/ld/lib.go` では、共有ライブラリからABIハッシュを読み取る際に、シンボルテーブルを介してではなく、新しく追加された `readnote` 関数を使用して `.note.go.abihash` ノートから直接ハッシュを抽出するようになりました。これにより、シンボルテーブルが削除されたライブラリからでもABIハッシュを確実に取得できるようになります。

5.  **テストの追加**:
    *   `misc/cgo/testshared/shared_test.go` には、`isOffsetLoaded`, `readwithpad`, `readNotes`, `testPkgListNote`, `testABIHashNote`, `TestNotes` といった新しい関数とテストケースが追加されました。これらは、生成された共有ライブラリが期待通りにABIハッシュとパッケージリストのELFノートを含んでいるか、そしてそれらのノートが正しい属性（メモリにマップされるか否か、シンボルが正しく指しているかなど）を持っているかを検証します。

これらの変更により、Goの共有ライブラリのメタデータ管理がより堅牢で標準準拠になり、ツールの互換性とリンカの保守性が向上しました。

## コアとなるコードの解説

このコミットの核となる変更は、Goリンカが共有ライブラリのメタデータ（ABIハッシュとパッケージリスト）をELFノートとして格納する新しいメカニズムを導入した点にあります。

1.  **`addgonote` 関数 (`src/cmd/link/internal/ld/elf.go`)**:
    この関数は、Go固有のELFノートを作成するための汎用的なインターフェースです。
    *   `sectionName`: ノートが格納されるELFセクションの名前（例: `.note.go.abihash`）。
    *   `tag`: ノートのタイプを識別する整数タグ（`ELF_NOTE_GOABIHASH_TAG` または `ELF_NOTE_GOPKGLIST_TAG`）。
    *   `desc`: ノートのペイロードデータ（ABIハッシュのバイト列やパッケージリストの文字列）。
    この関数は、ELFノートの標準的な構造（`namesz`, `descsz`, `type`, `name`, `desc`、および4バイトアラインメントのためのパディング）に従ってデータをフォーマットし、指定されたセクションに書き込みます。これにより、リンカは任意のGo固有のメタデータをELFノートとして柔軟に格納できるようになりました。

2.  **`doelf` 関数内のノート書き込みロジック (`src/cmd/link/internal/ld/elf.go`)**:
    `doelf` 関数は、ELFファイルの最終的な構造を決定し、セクションやシンボルを配置するリンカの主要なフェーズです。
    *   `BuildmodeShared` の場合、ABIハッシュが計算され（`sha1` を使用してライブラリのハッシュを結合）、その結果とパッケージリストの文字列が `addgonote` 関数を介してそれぞれ `.note.go.abihash` と `.note.go.pkg-list` ノートとして書き込まれます。
    *   これにより、ABIハッシュとパッケージリストがELFファイル内の明確なノートセクションとして存在することが保証されます。

3.  **`go.link.abihashbytes` シンボルの再定義 (`src/cmd/link/internal/ld/data.go`)**:
    以前は、`go.link.abihashbytes` はABIハッシュデータ自体を指すシンボルでした。この変更後、このシンボルは `.note.go.abihash` セクション内のABIハッシュデータ（ノートの記述子部分）の開始位置を指すように再定義されます。具体的には、ノートヘッダのサイズ（`namesz`, `descsz`, `type` の合計12バイト）とノート名のパディング（4バイト）を考慮して、セクションの仮想アドレスから16バイトオフセットされた位置を指します。これにより、リンカ内部の既存のABIハッシュ参照コードは、大きな変更なしに新しいノート構造を利用できるようになります。

4.  **`readnote` 関数 (`src/cmd/link/internal/ld/lib.go`)**:
    この関数は、ELFファイルから特定のGo固有のノートを読み取るための汎用的なヘルパーです。
    *   ELFファイル内のすべての `SHT_NOTE` タイプセクションをスキャンします。
    *   各ノートの `name` と `type` (タグ) をチェックし、指定された `name` と `type` に一致するノートを見つけます。
    *   一致するノートが見つかった場合、その `desc` (記述子) 部分のデータを返します。
    この関数により、リンカや他のツールは、シンボルテーブルの有無にかかわらず、標準化された方法でABIハッシュやパッケージリストなどのGo固有のメタデータを共有ライブラリから確実に抽出できるようになりました。

5.  **テストの追加 (`misc/cgo/testshared/shared_test.go`)**:
    新しいテストは、これらの変更が正しく機能していることを検証します。
    *   `readNotes` は、共有ライブラリからすべてのELFノートを解析します。
    *   `testPkgListNote` は、パッケージリストノートがメモリにマップされないセクションにあり、正しい内容を持っていることを確認します。
    *   `testABIHashNote` は、ABIハッシュノートがメモリにマップされるセクションにあり、`go.link.abihashbytes` シンボルがそのノート内の正しい位置を指していることを確認します。
    これらのテストは、新しいノートベースのメタデータ格納メカニズムの正確性と堅牢性を保証します。

## 変更の背景

このコミットの変更は、主に以下の2つの課題を解決するために行われました。

1.  **ABIハッシュ抽出の不安定性とシンボルテーブル削除時の問題**:
    Goの共有ライブラリには、そのライブラリが依存するパッケージのABI (Application Binary Interface) ハッシュが含まれています。これは、ライブラリ間の互換性を保証するために重要です。しかし、以前の実装では、このABIハッシュを抽出するための安定したAPIが存在せず、リンカ自身を含む外部ツールがこの情報を取得するのが困難でした。特に、共有ライブラリからローカルシンボルテーブルが削除（strip）された場合、ABIハッシュを特定することが不可能になるという問題がありました。これは、ABIハッシュがシンボルとして表現されていたためです。

2.  **ELFノートの固定サイズバジェットと柔軟性の欠如**:
    Goリンカには、ELFファイルに特定の情報を「ノート」として書き込む既存のメカニズムがありました。しかし、このメカニズムは、ノートをオブジェクトファイルの先頭に書き込むことを前提としており、すべてのノートが固定されたサイズバジェット内に収まる必要がありました。Goの共有ライブラリでは、パッケージリストなど、複数のノートを格納する必要があり、今後さらにノートが追加される可能性がありました。この固定サイズバジェットは、特にパッケージリストのようにサイズが大きくなる可能性のあるノートにとって制約となっていました。以前は、`-buildmode=shared` でビルドする際に、このサイズバジェットを一時的に増やす「ハック」が存在しましたが、これは根本的な解決策ではありませんでした。

これらの課題に対処するため、ABIハッシュとパッケージリストをELFの標準的なノートセクションに格納し、ノート書き込みメカニズムをより柔軟にすることで、ツールの安定性とリンカの内部的な堅牢性を向上させる必要がありました。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリなどを格納するための標準的なファイル形式です。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして実際のデータ（コード、データ、シンボルテーブルなど）で構成されます。

*   **セクション (Sections)**: リンカが処理する論理的なデータブロック（例: `.text` (コード), `.data` (初期化済みデータ), `.rodata` (読み取り専用データ), `.symtab` (シンボルテーブル)）。
*   **セグメント (Segments)**: ローダがメモリにマッピングする物理的なデータブロック。複数のセクションが1つのセグメントにまとめられることがあります。
*   **ノートセクション (Note Sections, `SHT_NOTE`)**: ELFファイル内に任意のメタデータを格納するための特殊なセクションタイプです。通常、システム固有の情報やツール固有の情報を格納するために使用されます。ノートは、名前、タイプ（タグ）、記述子（データ）で構成されます。

### ABI (Application Binary Interface) ハッシュ

ABIは、コンパイルされたプログラムが互いにやり取りする方法を定義する低レベルのインターフェースです。Go言語では、共有ライブラリを使用する際に、ライブラリがエクスポートする関数やデータ構造のレイアウトが、それを使用するプログラムと互換性があることを保証する必要があります。ABIハッシュは、Goのパッケージのインターフェース定義（型、関数シグネチャなど）から計算される一意の識別子です。リンカは、共有ライブラリをリンクする際に、依存するライブラリのABIハッシュをチェックし、不一致があればエラーを報告することで、互換性の問題を早期に検出します。

### Goの共有ライブラリ (`-buildmode=shared`)

Goは、`-buildmode=shared` オプションを使用して共有ライブラリ（`.so` ファイル）をビルドする機能を提供します。これにより、複数のGoプログラムが共通のライブラリを共有し、メモリ使用量を削減したり、ビルド時間を短縮したりすることができます。共有ライブラリは、Goのランタイムと特定のGoパッケージを含み、他のGoプログラムやCgoを介してCプログラムから利用できます。

### シンボルテーブル (Symbol Tables)

シンボルテーブルは、プログラム内の関数や変数などのシンボル名と、それらがメモリ内のどこに配置されるかという情報（アドレス）をマッピングするデータ構造です。デバッグや動的リンクに不可欠です。しかし、リリースビルドでは、ファイルサイズを削減したり、内部実装の詳細を隠蔽したりするために、シンボルテーブルが削除（strip）されることがあります。

### ELFノートの構造

ELFノートは、通常、以下の構造を持ちます。

```
+-----------------+
| namesz (4 bytes)| // nameフィールドのサイズ
+-----------------+
| descsz (4 bytes)| // descフィールドのサイズ
+-----------------+
| type (4 bytes)  | // ノートのタイプ（タグ）
+-----------------+
| name (namesz)   | // ノートの所有者または識別子（null終端されることが多い）
+-----------------+
| padding         | // 4バイトアラインメントのためのパディング
+-----------------+
| desc (descsz)   | // ノートのデータ（記述子）
+-----------------+
| padding         | // 4バイトアラインメントのためのパディング
+-----------------+
```

このコミットでは、`ELF_NOTE_GO_NAME` (`"GO\x00\x00"`) がノートの`name`として使用され、`ELF_NOTE_GOPKGLIST_TAG` (1) と `ELF_NOTE_GOABIHASH_TAG` (2) が`type`として使用されます。

## 技術的詳細

このコミットの主要な技術的変更点は、ABIハッシュとパッケージリストの格納方法を、リンカの内部シンボルや特定のセクションから、標準的なELFノートセクションへと移行したことです。

1.  **ABIハッシュとパッケージリストのELFノートへの移行**:
    *   以前は、ABIハッシュは `go.link.abihashbytes` というローカルシンボルを通じてアクセスされていました。このシンボルは、リンカが内部的に管理するデータ領域を指していました。
    *   パッケージリストも同様に、特定のリンカ内部メカニズムによって処理されていました。
    *   この変更により、ABIハッシュは `.note.go.abihash` という名前のELFノートセクションに、パッケージリストは `.note.go.pkg-list` という名前のELFノートセクションに格納されるようになりました。
    *   これらのノートは、`ELF_NOTE_GO_NAME` (`"GO\x00\x00"`) をノート名として、それぞれ `ELF_NOTE_GOABIHASH_TAG` (2) と `ELF_NOTE_GOPKGLIST_TAG` (1) をタグとして使用します。

2.  **ノート書き込みメカニズムの汎用化と柔軟性の向上**:
    *   以前のノート書き込みコードは、ノートをオブジェクトファイルの先頭に配置し、固定サイズバジェットに収める必要がありました。これは、主にコアダンプでノートを簡単に見つけるためのものでしたが、Goのノートにはこの制約は不要でした。
    *   新しい `addgonote` 関数が導入され、任意のセクション名、タグ、記述子（データ）を指定してELFノートを作成できるようになりました。この関数は、ノートの構造（`namesz`, `descsz`, `type`, `name`, `desc`、およびパディング）を適切にフォーマットし、指定されたセクションにデータを追加します。
    *   この汎用化により、ノートがファイルの先頭に限定されなくなり、また、固定サイズバジェットの制約もなくなりました。これにより、パッケージリストのようにサイズが変動する可能性のあるノートも柔軟に扱えるようになりました。

3.  **`HEADR` サイズバジェットの「ハック」の削除**:
    *   `src/cmd/link/internal/amd64/obj.go` にあった、共有ライブラリビルド時に `ld.HEADR` (ELFヘッダの予約サイズ) を3倍にするという一時的な「ハック」が削除されました。これは、パッケージリストノートが大きくなる可能性に対応するためのものでしたが、ノート書き込みメカニズムの改善により不要となりました。

4.  **ABIハッシュの参照方法の変更**:
    *   `src/cmd/link/internal/ld/data.go` では、`go.link.abihashbytes` シンボルが、新しく作成された `.note.go.abihash` セクション内のABIハッシュデータ（オフセット16バイトから始まる）を直接指すように変更されました。具体的には、ノートヘッダのサイズ（`namesz`, `descsz`, `type` の合計12バイト）とノート名のパディング（4バイト）を考慮して、セクションの仮想アドレスから16バイトオフセットされた位置を指します。これにより、リンカ内部の既存のABIハッシュ参照コードは、大きな変更なしに新しいノート構造を利用できるようになります。
    *   `src/cmd/link/internal/ld/lib.go` では、共有ライブラリからABIハッシュを読み取る際に、シンボルテーブルを介してではなく、新しく追加された `readnote` 関数を使用して `.note.go.abihash` ノートから直接ハッシュを抽出するようになりました。これにより、シンボルテーブルが削除されたライブラリからでもABIハッシュを確実に取得できるようになります。

5.  **テストの追加**:
    *   `misc/cgo/testshared/shared_test.go` には、`isOffsetLoaded`, `readwithpad`, `readNotes`, `testPkgListNote`, `testABIHashNote`, `TestNotes` といった新しい関数とテストケースが追加されました。これらは、生成された共有ライブラリが期待通りにABIハッシュとパッケージリストのELFノートを含んでいるか、そしてそれらのノートが正しい属性（メモリにマップされるか否か、シンボルとの関連付けなど）を持っているかを検証します。

これらの変更により、Goの共有ライブラリのメタデータ管理がより堅牢で標準準拠になり、ツールの互換性とリンカの保守性が向上しました。

## コアとなるコードの解説

このコミットの核となる変更は、Goリンカが共有ライブラリのメタデータ（ABIハッシュとパッケージリスト）をELFノートとして格納する新しいメカニズムを導入した点にあります。

1.  **`addgonote` 関数 (`src/cmd/link/internal/ld/elf.go`)**:
    この関数は、Go固有のELFノートを作成するための汎用的なインターフェースです。
    *   `sectionName`: ノートが格納されるELFセクションの名前（例: `.note.go.abihash`）。
    *   `tag`: ノートのタイプを識別する整数タグ（`ELF_NOTE_GOABIHASH_TAG` または `ELF_NOTE_GOPKGLIST_TAG`）。
    *   `desc`: ノートのペイロードデータ（ABIハッシュのバイト列やパッケージリストの文字列）。
    この関数は、ELFノートの標準的な構造（`namesz`, `descsz`, `type`, `name`, `desc`、および4バイトアラインメントのためのパディング）に従ってデータをフォーマットし、指定されたセクションに書き込みます。これにより、リンカは任意のGo固有のメタデータをELFノートとして柔軟に格納できるようになりました。

2.  **`doelf` 関数内のノート書き込みロジック (`src/cmd/link/internal/ld/elf.go`)**:
    `doelf` 関数は、ELFファイルの最終的な構造を決定し、セクションやシンボルを配置するリンカの主要なフェーズです。
    *   `BuildmodeShared` の場合、ABIハッシュが計算され（`sha1` を使用してライブラリのハッシュを結合）、その結果とパッケージリストの文字列が `addgonote` 関数を介してそれぞれ `.note.go.abihash` と `.note.go.pkg-list` ノートとして書き込まれます。
    *   これにより、ABIハッシュとパッケージリストがELFファイル内の明確なノートセクションとして存在することが保証されます。

3.  **`go.link.abihashbytes` シンボルの再定義 (`src/cmd/link/internal/ld/data.go`)**:
    以前は、`go.link.abihashbytes` はABIハッシュデータ自体を指すシンボルでした。この変更後、このシンボルは `.note.go.abihash` セクション内のABIハッシュデータ（ノートの記述子部分）の開始位置を指すように再定義されます。具体的には、ノートヘッダのサイズ（`namesz`, `descsz`, `type` の合計12バイト）とノート名のパディング（4バイト）を考慮して、セクションの仮想アドレスから16バイトオフセットされた位置を指します。これにより、リンカ内部の既存のABIハッシュ参照コードは、大きな変更なしに新しいノート構造を利用できるようになります。

4.  **`readnote` 関数 (`src/cmd/link/internal/ld/lib.go`)**:
    この関数は、ELFファイルから特定のGo固有のノートを読み取るための汎用的なヘルパーです。
    *   ELFファイル内のすべての `SHT_NOTE` タイプセクションをスキャンします。
    *   各ノートの `name` と `type` (タグ) をチェックし、指定された `name` と `type` に一致するノートを見つけます。
    *   一致するノートが見つかった場合、その `desc` (記述子) 部分のデータを返します。
    この関数により、リンカや他のツールは、シンボルテーブルの有無にかかわらず、標準化された方法でABIハッシュやパッケージリストなどのGo固有のメタデータを共有ライブラリから確実に抽出できるようになりました。

5.  **テストの追加 (`misc/cgo/testshared/shared_test.go`)**:
    新しいテストは、これらの変更が正しく機能していることを検証します。
    *   `readNotes` は、共有ライブラリからすべてのELFノートを解析します。
    *   `testPkgListNote` は、パッケージリストノートがメモリにマップされないセクションにあり、正しい内容を持っていることを確認します。
    *   `testABIHashNote` は、ABIハッシュノートがメモリにマップされるセクションにあり、`go.link.abihashbytes` シンボルがそのノート内の正しい位置を指していることを確認します。
    これらのテストは、新しいノートベースのメタデータ格納メカニズムの正確性と堅牢性を保証します。

これらの変更は、Goの共有ライブラリの内部構造を改善し、ツールとの連携を強化するとともに、将来的な拡張性も考慮に入れたものです。

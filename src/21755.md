# [インデックス 21755] ファイルの概要

このコミットは、Go言語のランタイムにおけるARMアーキテクチャ向けビルドの問題を解決しようと試みたものです。具体的には、`include/u.h`ファイルから`signal.h`の条件付きインクルードを削除する変更が含まれています。しかし、コミットメッセージによると、この変更自体はビルドの問題を完全に解決せず、`go_bootstrap`コンパイル後に`auxv`（Auxiliary Vector）のパースに関連するクラッシュが発生していることが示唆されています。これは、ARMビルドの安定化に向けた一連の試みの一つであり、根本的な問題がより深い部分にあることを示しています。

## 変更の背景

このコミットは、Go言語のARMアーキテクチャ向けビルドが不安定であった時期に行われた、一連の修正試行の一つです。コミットメッセージにある「Fourth time's the charm.」という表現から、これまでに少なくとも3回、同様のビルド問題に対する修正が試みられていたことが伺えます。

当時のGo言語は、様々なアーキテクチャへの対応を進めており、特にARMのような組み込みシステムやモバイルデバイスで広く利用されるアーキテクチャへのサポートは重要でした。しかし、異なるアーキテクチャやOS環境では、システムコール、メモリ管理、シグナル処理などの低レベルな挙動が異なるため、クロスコンパイルやブートストラップの過程で特有の問題が発生しがちです。

このコミットの具体的な背景としては、`go_bootstrap`というGoコンパイラの初期段階のビルドプロセスがARM環境でクラッシュするという問題がありました。コミットの作者は、このクラッシュが`auxv`（Auxiliary Vector）のパースに関連している可能性を指摘しています。`auxv`は、Linuxシステムにおいて、プロセス起動時にカーネルがユーザー空間に渡す補助情報であり、実行環境に関する重要なデータ（例えば、ページサイズ、実行ファイルのパス、CPUの機能フラグなど）を含んでいます。この`auxv`のパースに問題があると、プロセスの初期化が正しく行われず、クラッシュにつながる可能性があります。

`include/u.h`は、GoランタイムのC部分で利用される共通ヘッダファイルであり、OS固有の定義やユーティリティ関数などが含まれています。このファイルにおける`signal.h`の条件付きインクルードの削除は、ARMビルドの特定のコンテキストにおいて、シグナル処理関連の定義が問題を引き起こしている、あるいは不要であると判断されたためと考えられます。しかし、結果的には根本的な`auxv`パースの問題は解決されませんでした。

## 前提知識の解説

### ARMアーキテクチャとGo言語

ARM（Advanced RISC Machine）は、低消費電力と高性能を両立するRISC（Reduced Instruction Set Computer）ベースのプロセッサアーキテクチャです。スマートフォン、タブレット、組み込みシステム、IoTデバイス、さらにはサーバーやスーパーコンピュータに至るまで、非常に広範な分野で利用されています。Go言語は、その設計思想としてクロスプライルの容易さを持っており、様々なアーキテクチャで動作することを目標としています。ARMアーキテクチャへの対応は、Go言語がこれらの多様な環境で利用される上で不可欠な要素です。

### Goのブートストラッププロセス (`go_bootstrap`)

Go言語のコンパイラはGo言語自体で書かれています。そのため、Goコンパイラをビルドするためには、まず既存のGoコンパイラ（またはC言語で書かれた初期のコンパイラ）が必要です。この自己ホスト型コンパイラをビルドする初期プロセスを「ブートストラップ」と呼びます。

具体的には、GoのソースコードからGoコンパイラをビルドする際、まずGoのツールチェイン（`go_bootstrap`と呼ばれる初期コンパイラやツール）がビルドされます。この`go_bootstrap`は、Goの標準ライブラリや最終的なGoコンパイラ自体をビルドするために使用されます。このプロセスは、新しいGoのバージョンをリリースする際や、新しいアーキテクチャにGoを移植する際に特に重要となります。`go_bootstrap`のコンパイル後にクラッシュが発生するということは、Goコンパイラが自身の動作環境を正しく認識・初期化できていないことを意味します。

### Auxiliary Vector (`auxv`)

Linuxシステムにおいて、`auxv`（Auxiliary Vector）は、プロセスが起動する際にカーネルからユーザー空間に渡されるデータ構造の配列です。これは、プログラムの実行環境に関する様々な補助情報を提供します。`auxv`は、スタックのトップ付近に配置され、`AT_`で始まる定数（例: `AT_PHDR`、`AT_PHENT`、`AT_PAGESZ`、`AT_EXECFN`など）とそれに対応する値のペアで構成されます。

`auxv`に含まれる情報の例：
*   `AT_PHDR`: プログラムヘッダテーブルのアドレス。
*   `AT_PHENT`: プログラムヘッダのエントリサイズ。
*   `AT_PHNUM`: プログラムヘッダのエントリ数。
*   `AT_PAGESZ`: システムのページサイズ。
*   `AT_BASE`: ダイナミックリンカのベースアドレス。
*   `AT_ENTRY`: 実行ファイルの開始アドレス。
*   `AT_UID`, `AT_EUID`, `AT_GID`, `AT_EGID`: ユーザーID、グループID。
*   `AT_HWCAP`: CPUのハードウェア機能（例: SIMD命令のサポート）。
*   `AT_EXECFN`: 実行ファイルのパス。

Goランタイムは、プロセスの初期化段階でこれらの`auxv`情報をパースし、実行環境の特性を把握します。例えば、ページサイズを知ることでメモリ管理を最適化したり、CPUの機能フラグをチェックして特定の最適化されたコードパスを選択したりします。`auxv`のパースに失敗すると、ランタイムが環境を誤認識したり、必要な情報が得られずに不正なメモリアクセスやクラッシュを引き起こす可能性があります。ARMのような多様な実装が存在するアーキテクチャでは、`auxv`の構造や内容が微妙に異なる場合があり、それがパースの問題につながることがあります。

### `include/u.h`

`include/u.h`は、Go言語のランタイム（特にC言語で書かれた部分）で使用される共通のヘッダファイルです。このファイルには、Goランタイムが様々なOSやアーキテクチャで動作するために必要な、プラットフォーム非依存およびプラットフォーム依存の共通定義、マクロ、インクルードなどが含まれています。例えば、Goの内部的な型定義、アトミック操作、メモリバリア、OS固有のシステムコールラッパーなどが含まれることがあります。Cgo（GoとCの相互運用）を使用する際にも、この種の共通ヘッダが重要になります。

### `signal.h`

`signal.h`は、POSIXシステム（Linux、Unixなど）における標準Cライブラリのヘッダファイルで、シグナル処理に関連する関数、マクロ、型定義を提供します。シグナルは、非同期イベント（例: 割り込み、エラー、ユーザーからの入力）をプロセスに通知するためのメカニズムです。例えば、`SIGSEGV`（セグメンテーション違反）、`SIGILL`（不正命令）、`SIGINT`（Ctrl+Cによる割り込み）などがあります。

Goランタイムは、デッドロック検出、パニック処理、ガーベージコレクションの一時停止など、内部的な目的でシグナルを多用します。また、ユーザープログラムがシグナルを処理するためのAPIも提供しています。`signal.h`のインクルードは、これらのシグナル処理機能がC言語のコードから利用可能であることを保証するために必要です。

## 技術的詳細

このコミットの技術的詳細は、`include/u.h`から`#ifndef PLAN9 #include <signal.h> #endif`というコードブロックが削除された点に集約されます。

この変更は、GoランタイムのC部分において、Plan 9以外のシステム（Linux、macOS、Windowsなど）で`signal.h`が常にインクルードされていた状態から、それがインクルードされなくなることを意味します。

考えられる理由はいくつかあります。

1.  **コンパイルエラーの回避**: 特定のARM環境やツールチェインの組み合わせにおいて、`signal.h`のインクルードがコンパイルエラーや警告を引き起こしていた可能性があります。例えば、特定のバージョンの`glibc`やクロスコンパイル環境のヘッダファイルとの競合、あるいはGoランタイムのCコードが`signal.h`内の特定の定義と衝突していた可能性です。
2.  **不要な依存関係の削除**: GoランタイムのC部分で`signal.h`内の特定の機能が実際には使用されておらず、不要なインクルードであったと判断された可能性があります。不要なヘッダのインクルードは、コンパイル時間の増加や、潜在的なシンボル競合のリスクを招くことがあります。
3.  **シグナル処理の再設計**: Goランタイムのシグナル処理メカニズムが変更され、C言語レベルでの`signal.h`の直接的なインクルードが不要になった、あるいは別の方法でシグナル関連の定義が提供されるようになった可能性です。Goは独自のシグナルハンドラを設定し、OSからのシグナルをGoルーチンにディスパッチする複雑なメカニズムを持っています。
4.  **`auxv`パース問題との関連性（間接的）**: コミットメッセージが示唆するように、この変更自体が`auxv`パースのクラッシュを直接解決するものではありませんでした。しかし、開発者はビルドクラッシュの原因を特定する過程で、`signal.h`のインクルードが何らかの形で問題に寄与している、あるいは少なくとも無関係ではないと推測した可能性があります。例えば、シグナルハンドラの初期化が`auxv`パースの前に発生し、その過程で不正なメモリ状態が引き起こされ、その後の`auxv`パースに影響を与えていた、といった複雑な相互作用が考えられます。ただし、このコミットではその仮説は実証されませんでした。

この変更は、GoランタイムのC部分がシグナル関連の定義に直接依存しなくなったことを意味しますが、Go言語自体がシグナル処理を行わないわけではありません。Goランタイムは、引き続きOSのシグナルメカニズムを利用しますが、そのためのC言語レベルのインターフェースが`include/u.h`を介してではなく、他の場所（例えば、OS固有のソースファイルや、より低レベルなアセンブリコード）で提供されるようになった可能性があります。

最終的に、このコミットはARMビルドのクラッシュを解決しませんでしたが、GoランタイムのC部分におけるヘッダファイルの依存関係を整理する試みの一環であったと考えられます。

## コアとなるコードの解説

削除されたコードブロックは、`PLAN9`というマクロが定義されていない場合にのみ、標準Cライブラリの`signal.h`ヘッダファイルをインクルードするという条件付きコンパイルディレクティブです。

*   `#ifndef PLAN9`: これはプリプロセッサディレクティブで、「`PLAN9`マクロが定義されていない場合」という意味です。Plan 9はベル研究所が開発した分散オペレーティングシステムであり、Go言語のルーツの一部でもあります。Goランタイムの初期開発ではPlan 9の慣習やコードが参考にされることが多く、Plan 9とそれ以外のOS（Linux、macOS、Windowsなど）でコードパスを分岐させるためにこのような条件付きコンパイルがよく用いられました。
*   `#include <signal.h>`: これは、シグナル処理に関連する定義（シグナル番号、シグナルハンドラ関数、`sigaction`構造体など）を含む標準Cライブラリのヘッダファイルをインクルードする指示です。

このコードブロックが削除されたことにより、GoランタイムのC部分において、`include/u.h`を介して`signal.h`がインクルードされることはなくなりました。これは、GoランタイムのCコードが、`signal.h`によって提供される特定のシグナル関連の定義に直接依存しなくなったことを意味します。

この変更の意図としては、以下が考えられます。
1.  **依存関係の整理**: `include/u.h`は汎用的なヘッダであり、シグナル処理のような特定のOS機能は、より具体的なOS固有のファイル（例: `runtime/sys_linux_arm.go`に対応するCファイルなど）で処理されるべきであるという設計思想の変更。
2.  **コンパイル環境の調整**: 特定のクロスコンパイル環境やARMターゲットにおいて、`signal.h`のインクルードが問題を引き起こしていたため、一時的または恒久的にそのインクルードを回避する。
3.  **Goランタイムのシグナル処理の進化**: Goランタイムのシグナル処理メカニズムが進化し、C言語レベルでの`signal.h`の直接的なインクルードが不要になった、あるいは別の方法で必要な定義が提供されるようになった。例えば、Goの内部的なシグナル処理は、Cgoを介さずに直接システムコールを呼び出す形に移行したか、あるいは必要なシグナル関連の定数がGoのコード内で直接定義されるようになった可能性もあります。

コミットメッセージが「Actually this doesn't fix the build, there is a crash after go_bootstrap is compiled which looks like it is related to auxv parsing.」と述べていることから、この変更はビルドクラッシュの根本原因（`auxv`パースの問題）を解決するものではなかったことが明確です。しかし、これは当時のGoランタイム開発における試行錯誤の一環であり、特定のビルド問題に対する仮説に基づいた修正試行であったと理解できます。

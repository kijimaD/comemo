## 変更の背景

この変更の主な背景は、Goランタイムのメモリ管理における `sysAlloc` 関数の重要性と、その実行の安定性および効率性を確保することにあります。

Goのランタイムは、ゴルーチンのスタックを動的に管理します。ゴルーチンのスタックは最初は小さく割り当てられ、必要に応じて自動的に成長（スタック分割またはスタックコピー）します。このスタック成長のメカニズムは、通常、関数のプロローグ（関数の開始部分）でスタックオーバーフローチェックを行うことで実現されます。しかし、ランタイムの非常に低レベルな部分、特にメモリ割り当てのようなクリティカルな操作を行う関数では、このスタック成長チェックが問題を引き起こす可能性があります。

`sysAlloc` は、オペレーティングシステムから直接メモリを要求するGoランタイムの低レベル関数です。これはGoのヒープの基盤となるメモリを確保するために使用されます。コミットメッセージにあるように、「`sysAlloc` はGoから呼び出される唯一のメモリ関数」であり、これはGoのメモリ管理パスにおいて非常に重要な位置を占めていることを意味します。

このようなクリティカルな関数でスタック成長チェックを行うと、以下のような問題が発生する可能性があります。

1.  **パフォーマンスオーバーヘッド**: 頻繁に呼び出される `sysAlloc` のような関数で毎回スタックチェックを行うことは、不要なオーバーヘッドとなり、全体のパフォーマンスに影響を与える可能性があります。
2.  **デッドロックや再入可能性の問題**: メモリ割り当て中にスタック成長が必要となり、その過程でさらにメモリ割り当てが必要になるような状況は、デッドロックや予期せぬ再入可能性の問題を引き起こす可能性があります。特に、ガベージコレクションやスケジューラのような他のランタイムの低レベルコンポーネントと相互作用する場合に顕著です。
3.  **スタックの制約**: `sysAlloc` のような関数は、OSスレッドのスタック（Mスタック）上で実行される必要があったり、ゴルーチンのスタックが成長できないような特殊なコンテキストで呼び出される場合があります。このような場合、スタック成長チェックは適切ではありません。

これらの問題を回避し、`sysAlloc` の実行をより堅牢で効率的にするために、`NOSPLIT` フラグを付与することが決定されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語のプリプロセッサディレクティブに関する知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、ゴルーチン管理、スケジューリング、メモリ割り当て、システムコールインターフェースなど、Goプログラムの実行に必要な多くの低レベルな機能を提供します。Goランタイムの大部分はGo言語で書かれていますが、一部の非常に低レベルな部分（特にOSとのインターフェースやアセンブリ言語で書かれた部分）はC言語やアセンブリ言語で実装されています。

2.  **ゴルーチンとスタック管理 (Goroutines and Stack Management)**:
    Goのゴルーチンは、OSスレッドよりもはるかに軽量な並行実行単位です。各ゴルーチンは独自のスタックを持っていますが、このスタックは最初は非常に小さく（数KB程度）割り当てられます。関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。
    Go 1.4以前は「セグメントスタック」という方式でスタックを拡張していましたが、Go 1.4以降は「スタックコピー」という方式に移行しました。スタックコピーでは、スタックが不足すると、より大きな新しいスタック領域を割り当て、古いスタックの内容を新しい領域にコピーします。このスタック拡張のチェックは、通常、関数のプロローグで行われます。

3.  **`sysAlloc` 関数**:
    `sysAlloc` は、Goランタイムがオペレーティングシステムから生のメモリを要求するために使用する内部関数です。これは `mmap` (Unix系システム) や `VirtualAlloc` (Windows) といったOSのシステムコールをラップしています。Goのヒープ領域を確保する際にこの関数が呼び出され、Goのメモリ管理の根幹をなす部分です。

4.  **`NOSPLIT` (No Stack Splitting) プラグマ**:
    `NOSPLIT` は、GoランタイムのC言語またはアセンブリ言語で書かれた関数に適用される特別なディレクティブです。C言語のソースファイルでは `#pragma textflag NOSPLIT` として記述されます。このプラグマが関数に適用されると、Goコンパイラ（またはアセンブラ）は、その関数のプロローグに通常挿入されるスタックオーバーフローチェックのコードを生成しません。
    これにより、その関数はスタック成長をトリガーすることなく実行されます。これは、以下のような場合に特に重要です。
    *   **非常に短い関数**: スタックチェックのオーバーヘッドが関数の実行時間に対して相対的に大きい場合。
    *   **クリティカルパスの関数**: メモリ割り当てやスケジューリングなど、ランタイムのコア機能であり、中断や再入可能性が問題となる場合。
    *   **スタック成長が不可能なコンテキスト**: 例えば、OSスレッドのスタック上で直接実行される関数など、ゴルーチンのスタック成長メカニズムが適用されない場合。

5.  **`runtime·onM` (Plan 9固有の変更に関連)**:
    Goランタイムの内部には、特定のコードを現在のOSスレッド（M: Machine）のコンテキストで直接実行するためのメカニズムがあります。これは、ゴルーチンのスケジューリングやスタック管理のオーバーヘッドを避け、OSスレッドのスタック上で直接、かつ中断されずに実行する必要がある場合に用いられます。`runtime·onM` は、Plan 9固有の `mem_plan9.c` ファイルの変更で登場し、`sysAlloc` の実際のメモリ割り当てロジックをOSスレッド上で実行させるために使用されています。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムがどのように低レベルのメモリ割り当てを扱い、スタック管理の制約を回避しているかを示しています。

Goランタイムは、各オペレーティングシステム（OS）とアーキテクチャ（GOOS_GOARCH）ごとに異なる `mem_GOOS.c` ファイルで `runtime·sysAlloc` 関数を実装しています。このコミットでは、これらのファイルすべてに `NOSPLIT` フラグを追加しています。

具体的には、各 `mem_GOOS.c` ファイルの `runtime·sysAlloc` 関数の定義の直前に、以下の行が追加されています。

```c
#pragma textflag NOSPLIT
```

また、このプラグマを使用するために、必要なヘッダーファイルもインクルードされています。多くのファイルでは `textflag.h` または `../../cmd/ld/textflag.h` が追加されています。これは、`NOSPLIT` などのコンパイラ/リンカディレクティブの定義が含まれているためです。

### Plan 9固有の変更 (`src/pkg/runtime/mem_plan9.c`)

他のOS向けの `mem_GOOS.c` ファイルが単純に `NOSPLIT` プラグマを追加しているのに対し、Plan 9向けの `src/pkg/runtime/mem_plan9.c` では、より大幅な変更が行われています。

元の `runtime·sysAlloc` 関数は、直接 `brk` システムコールを呼び出してメモリを割り当てていました。しかし、このコミットでは `runtime·sysAlloc` の実装が変更され、実際のメモリ割り当てロジックが `sysalloc` という新しい静的ヘルパー関数に分離されています。

新しい `runtime·sysAlloc` の実装は以下のようになっています。

1.  `nbytes` と `stat` の引数を、現在のM（OSスレッド）の `g->m->scalararg[0]` と `g->m->ptrarg[0]` に保存します。これらは、`runtime·onM` を介して呼び出される関数に引数を渡すためのメカニズムです。
2.  `sysalloc` 関数へのポインタを `fn` 変数に設定します。
3.  `runtime·onM(&fn)` を呼び出します。これは、`sysalloc` 関数を現在のOSスレッド（M）のコンテキストで実行するようにGoランタイムに指示します。`runtime·onM` は、ゴルーチンのスタックではなく、OSスレッドのスタック上で `sysalloc` を実行するため、スタック成長チェックの問題を回避できます。
4.  `sysalloc` の実行後、結果（割り当てられたメモリへのポインタ `p`）は `g->m->ptrarg[0]` に格納されるため、`runtime·sysAlloc` はそこから値を取得して返します。

このPlan 9固有の変更は、`sysAlloc` がOSスレッドのスタック上で実行されることを保証し、ゴルーチンのスタック成長メカニズムとは独立して動作させるためのものです。これは、Plan 9のシステムコールインターフェースや、GoランタイムがPlan 9上でどのようにメモリを管理するかの特性に起因する可能性があります。

### `NOSPLIT` の重要性

`sysAlloc` に `NOSPLIT` をマークすることは、Goランタイムの堅牢性を高める上で非常に重要です。
*   **割り込み耐性**: `sysAlloc` の実行中にスタック成長チェックによる割り込みが発生しないため、メモリ割り当て操作がよりアトミックに、かつ予測可能に完了します。
*   **デッドロック回避**: メモリ割り当て中にスタック成長が必要となり、そのスタック成長自体がメモリ割り当てを必要とするような循環的な依存関係によるデッドロックのリスクを排除します。
*   **パフォーマンス最適化**: スタックチェックのオーバーヘッドを排除することで、`sysAlloc` の呼び出しがわずかに高速化されます。これは、Goのメモリ管理の基盤となるため、全体的なアプリケーションのパフォーマンスに寄与します。

この変更は、Goランタイムが低レベルのシステムリソースとどのように安全かつ効率的に相互作用するかを示す典型的な例です。

    sysalloc(void)
    {
        uintptr nbytes;
        uint64 *stat;
        void *p;

        stat = g->m->ptrarg[0];
        g->m->scalararg[0] = 0;
        g->m->ptrarg[0] = nil;

        if(p != nil)

        g->m->ptrarg[0] = p;

    runtime·sysAlloc(uintptr nbytes, uint64 *stat)

        void *p;

    }

## コアとなるコードの解説

このコミットのコアとなる変更は、`runtime·sysAlloc` 関数に `NOSPLIT` フラグを適用することです。

### `NOSPLIT` フラグの適用

GoランタイムのC言語ソースファイルにおいて、`#pragma textflag NOSPLIT` は、その直後に続く関数がスタック成長チェックをスキップするようにコンパイラに指示します。
`runtime·sysAlloc` は、GoランタイムがOSからメモリを直接要求する低レベルなインターフェースです。この関数は、Goのヒープの基盤となるメモリを確保するために頻繁に呼び出されます。
`NOSPLIT` を適用することで、`sysAlloc` が呼び出される際に、ゴルーチンのスタックが十分な大きさであるかどうかのチェックが省略されます。これにより、以下のような利点が得られます。

*   **オーバーヘッドの削減**: スタックチェックはわずかながらCPUサイクルを消費します。`sysAlloc` のような頻繁に呼び出される関数からこのオーバーヘッドを取り除くことで、全体的なメモリ割り当てのパフォーマンスが向上します。
*   **ランタイムの安定性**: メモリ割り当て中にスタック成長が必要となり、そのスタック成長自体がさらにメモリ割り当てを必要とするような再帰的な状況やデッドロックのリスクを排除します。これは、ガベージコレクタやスケジューラのような他のランタイムコンポーネントが `sysAlloc` を呼び出す際に特に重要です。これらのコンポーネントは、非常に制約された環境下で動作する必要があるため、予期せぬスタック成長は問題を引き起こす可能性があります。

### Plan 9 固有の `runtime·sysAlloc` の変更

`src/pkg/runtime/mem_plan9.c` における変更は、他のOS向けの変更よりも複雑です。これは、Plan 9のシステムコールインターフェースや、GoランタイムがPlan 9上でどのようにメモリを管理するかの特性に起因します。

*   **`sysalloc` ヘルパー関数の導入**:
    元の `runtime·sysAlloc` のロジックが `sysalloc` という新しい静的関数に抽出されました。この関数は、`brk` システムコールを呼び出して実際にメモリを割り当て、統計情報を更新します。

*   **`runtime·onM` の使用**:
    新しい `runtime·sysAlloc` は、直接 `brk` を呼び出す代わりに、`runtime·onM(&fn)` を使用して `sysalloc` 関数を呼び出します。
    `runtime·onM` は、Goランタイムの内部関数であり、引数として渡された関数ポインタ（この場合は `sysalloc`）を、現在のOSスレッド（M: Machine）のコンテキストで実行します。これは、ゴルーチンのスタックではなく、OSスレッドのスタック上でコードを実行することを意味します。
    このメカニズムを使用する主な理由は、`sysalloc` のような低レベルのメモリ割り当て操作が、ゴルーチンのスタック成長メカニズムの影響を受けずに、OSスレッドのスタック上で安全かつ中断されずに実行されることを保証するためです。これにより、スタック成長チェックが不要になり、`NOSPLIT` の目的が達成されます。
    引数 (`nbytes` と `stat`) は、`g->m->scalararg[0]` と `g->m->ptrarg[0]` を介して `sysalloc` に渡され、結果 (`p`) も同様に `g->m->ptrarg[0]` を介して返されます。これは、`runtime·onM` を使用する際の一般的な引数/戻り値の渡し方です。

このPlan 9固有の変更は、`NOSPLIT` の目的を達成するためのより複雑なアプローチを示しており、特定のOS環境におけるランタイムの設計上の考慮事項を浮き彫りにしています。

## 変更の背景

この変更の主な背景は、Goランタイムのメモリ管理における `sysAlloc` 関数の重要性と、その実行の安定性および効率性を確保することにあります。

Goのランタイムは、ゴルーチンのスタックを動的に管理します。ゴルーチンのスタックは最初は小さく割り当てられ、必要に応じて自動的に成長（スタック分割またはスタックコピー）します。このスタック成長のメカニズムは、通常、関数のプロローグ（関数の開始部分）でスタックオーバーフローチェックを行うことで実現されます。しかし、ランタイムの非常に低レベルな部分、特にメモリ割り当てのようなクリティカルな操作を行う関数では、このスタック成長チェックが問題を引き起こす可能性があります。

`sysAlloc` は、オペレーティングシステムから直接メモリを要求するGoランタイムの低レベル関数です。これはGoのヒープの基盤となるメモリを確保するために使用されます。コミットメッセージにあるように、「`sysAlloc` はGoから呼び出される唯一のメモリ関数」であり、これはGoのメモリ管理パスにおいて非常に重要な位置を占めていることを意味します。

このようなクリティカルな関数でスタック成長チェックを行うと、以下のような問題が発生する可能性があります。

1.  **パフォーマンスオーバーヘッド**: 頻繁に呼び出される `sysAlloc` のような関数で毎回スタックチェックを行うことは、不要なオーバーヘッドとなり、全体のパフォーマンスに影響を与える可能性があります。
2.  **デッドロックや再入可能性の問題**: メモリ割り当て中にスタック成長が必要となり、その過程でさらにメモリ割り当てが必要になるような状況は、デッドロックや予期せぬ再入可能性の問題を引き起こす可能性があります。特に、ガベージコレクションやスケジューラのような他のランタイムの低レベルコンポーネントと相互作用する場合に顕著です。
3.  **スタックの制約**: `sysAlloc` のような関数は、OSスレッドのスタック（Mスタック）上で実行される必要があったり、ゴルーチンのスタックが成長できないような特殊なコンテキストで呼び出される場合があります。このような場合、スタック成長チェックは適切ではありません。

これらの問題を回避し、`sysAlloc` の実行をより堅牢で効率的にするために、`NOSPLIT` フラグを付与することが決定されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語のプリプロセッサディレクティブに関する知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、ゴルーチン管理、スケジューリング、メモリ割り当て、システムコールインターフェースなど、Goプログラムの実行に必要な多くの低レベルな機能を提供します。Goランタイムの大部分はGo言語で書かれていますが、一部の非常に低レベルな部分（特にOSとのインターフェースやアセンブリ言語で書かれた部分）はC言語やアセンブリ言語で実装されています。

2.  **ゴルーチンとスタック管理 (Goroutines and Stack Management)**:
    Goのゴルーチンは、OSスレッドよりもはるかに軽量な並行実行単位です。各ゴルーチンは独自のスタックを持っていますが、このスタックは最初は非常に小さく（数KB程度）割り当てられます。関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。
    Go 1.4以前は「セグメントスタック」という方式でスタックを拡張していましたが、Go 1.4以降は「スタックコピー」という方式に移行しました。スタックコピーでは、スタックが不足すると、より大きな新しいスタック領域を割り当て、古いスタックの内容を新しい領域にコピーします。このスタック拡張のチェックは、通常、関数のプロローグで行われます。

3.  **`sysAlloc` 関数**:
    `sysAlloc` は、Goランタイムがオペレーティングシステムから生のメモリを要求するために使用する内部関数です。これは `mmap` (Unix系システム) や `VirtualAlloc` (Windows) といったOSのシステムコールをラップしています。Goのヒープ領域を確保する際にこの関数が呼び出され、Goのメモリ管理の根幹をなす部分です。

4.  **`NOSPLIT` (No Stack Splitting) プラグマ**:
    `NOSPLIT` は、GoランタイムのC言語またはアセンブリ言語で書かれた関数に適用される特別なディレクティブです。C言語のソースファイルでは `#pragma textflag NOSPLIT` として記述されます。このプラグマが関数に適用されると、Goコンパイラ（またはアセンブラ）は、その関数のプロローグに通常挿入されるスタックオーバーフローチェックのコードを生成しません。
    これにより、その関数はスタック成長をトリガーすることなく実行されます。これは、以下のような場合に特に重要です。
    *   **非常に短い関数**: スタックチェックのオーバーヘッドが関数の実行時間に対して相対的に大きい場合。
    *   **クリティカルパスの関数**: メモリ割り当てやスケジューリングなど、ランタイムのコア機能であり、中断や再入可能性が問題となる場合。
    *   **スタック成長が不可能なコンテキスト**: 例えば、OSスレッドのスタック上で直接実行される関数など、ゴルーチンのスタック成長メカニズムが適用されない場合。

5.  **`runtime·onM` (Plan 9固有の変更に関連)**:
    Goランタイムの内部には、特定のコードを現在のOSスレッド（M: Machine）のコンテキストで直接実行するためのメカニズムがあります。これは、ゴルーチンのスケジューリングやスタック管理のオーバーヘッドを避け、OSスレッドのスタック上で直接、かつ中断されずに実行する必要がある場合に用いられます。`runtime·onM` は、Plan 9固有の `mem_plan9.c` ファイルの変更で登場し、`sysAlloc` の実際のメモリ割り当てロジックをOSスレッド上で実行させるために使用されています。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムがどのように低レベルのメモリ割り当てを扱い、スタック管理の制約を回避しているかを示しています。

Goランタイムは、各オペレーティングシステム（OS）とアーキテクチャ（GOOS_GOARCH）ごとに異なる `mem_GOOS.c` ファイルで `runtime·sysAlloc` 関数を実装しています。このコミットでは、これらのファイルすべてに `NOSPLIT` フラグを追加しています。

具体的には、各 `mem_GOOS.c` ファイルの `runtime·sysAlloc` 関数の定義の直前に、以下の行が追加されています。

```c
#pragma textflag NOSPLIT
```

また、このプラグマを使用するために、必要なヘッダーファイルもインクルードされています。多くのファイルでは `textflag.h` または `../../cmd/ld/textflag.h` が追加されています。これは、`NOSPLIT` などのコンパイラ/リンカディレクティブの定義が含まれているためです。

### Plan 9固有の変更 (`src/pkg/runtime/mem_plan9.c`)

他のOS向けの `mem_GOOS.c` ファイルが単純に `NOSPLIT` プラグマを追加しているのに対し、Plan 9向けの `src/pkg/runtime/mem_plan9.c` では、より大幅な変更が行われています。

元の `runtime·sysAlloc` 関数は、直接 `brk` システムコールを呼び出してメモリを割り当てていました。しかし、このコミットでは `runtime·sysAlloc` の実装が変更され、実際のメモリ割り当てロジックが `sysalloc` という新しい静的ヘルパー関数に分離されています。

新しい `runtime·sysAlloc` の実装は以下のようになっています。

1.  `nbytes` と `stat` の引数を、現在のM（OSスレッド）の `g->m->scalararg[0]` と `g->m->ptrarg[0]` に保存します。これらは、`runtime·onM` を介して呼び出される関数に引数を渡すためのメカニズムです。
2.  `sysalloc` 関数へのポインタを `fn` 変数に設定します。
3.  `runtime·onM(&fn)` を呼び出します。これは、`sysalloc` 関数を現在のOSスレッド（M）のコンテキストで実行するようにGoランタイムに指示します。`runtime·onM` は、ゴルーチンのスタックではなく、OSスレッドのスタック上で `sysalloc` を実行するため、スタック成長チェックの問題を回避できます。
4.  `sysalloc` の実行後、結果（割り当てられたメモリへのポインタ `p`）は `g->m->ptrarg[0]` に格納されるため、`runtime·sysAlloc` はそこから値を取得して返します。

このPlan 9固有の変更は、`sysAlloc` がOSスレッドのスタック上で実行されることを保証し、ゴルーチンのスタック上で実行されることを保証し、ゴルーチンのスタック成長メカニズムとは独立して動作させるためのものです。これは、Plan 9のシステムコールインターフェースや、GoランタイムがPlan 9上でどのようにメモリを管理するかの特性に起因する可能性があります。

### `NOSPLIT` の重要性

`sysAlloc` に `NOSPLIT` をマークすることは、Goランタイムの堅牢性を高める上で非常に重要です。
*   **割り込み耐性**: `sysAlloc` の実行中にスタック成長チェックによる割り込みが発生しないため、メモリ割り当て操作がよりアトミックに、かつ予測可能に完了します。
*   **デッドロック回避**: メモリ割り当て中にスタック成長が必要となり、そのスタック成長自体がさらにメモリ割り当てを必要とするような循環的な依存関係によるデッドロックのリスクを排除します。
*   **パフォーマンス最適化**: スタックチェックのオーバーヘッドを排除することで、`sysAlloc` の呼び出しがわずかに高速化されます。これは、Goのメモリ管理の基盤となるため、全体的なアプリケーションのパフォーマンスに寄与します。

この変更は、Goランタイムが低レベルのシステムリソースとどのように安全かつ効率的に相互作用するかを示す典型的な例です。

*   `src/pkg/runtime/mem_darwin.c`
*   `src/pkg/runtime/mem_dragonfly.c`

*   `src/pkg/runtime/mem_linux.c`
*   `src/pkg/runtime/mem_nacl.c`
*   `src/pkg/runtime/mem_netbsd.c`

*   `src/pkg/runtime/mem_plan9.c`
*   `src/pkg/runtime/mem_solaris.c`
*   `src/pkg/runtime/mem_windows.c`

これらのファイルは、それぞれ異なるオペレーティングシステム向けのGoランタイムのメモリ管理実装を含んでいます。

具体的な変更内容は以下の通りです。

1.  **`#include` ディレクティブの追加**:
    多くのファイルで、`#include "textflag.h"` または `#include "../../cmd/ld/textflag.h"` が追加されています。これは、`NOSPLIT` プラグマの定義が含まれるヘッダーファイルです。

2.  **`#pragma textflag NOSPLIT` の追加**:
    各 `mem_GOOS.c` ファイル内の `runtime·sysAlloc` 関数の定義の直前に、`#pragma textflag NOSPLIT` が追加されています。

    例:
    ```c
    #include "defs_GOOS_GOARCH.h"
    #include "os_GOOS.h"
    #include "malloc.h"
    #include "../../cmd/ld/textflag.h" // 追加

    #pragma textflag NOSPLIT // 追加
    void*
    runtime·sysAlloc(uintptr n, uint64 *stat)
    {
        // ... 関数の実装 ...
    }
    ```

3.  **`src/pkg/runtime/mem_plan9.c` の大幅な変更**:
    このファイルでは、`runtime·sysAlloc` の実装が大きく変更されています。
    *   `sysalloc` という新しい静的ヘルパー関数が導入され、実際のメモリ割り当てロジック（`brk` の呼び出し）がこの関数内に移動しました。
    *   元の `runtime·sysAlloc` 関数は、`sysalloc` を `runtime·onM` を介して呼び出すラッパー関数となりました。これにより、`sysalloc` がOSスレッドのコンテキストで実行されるようになります。

    変更前 (`mem_plan9.c` の一部):
    ```c
    void*
    runtime·sysAlloc(uintptr nbytes, uint64 *stat)
    {
        void *p;

        p = brk(nbytes);
        if(p != nil)
            runtime·xadd64(stat, nbytes);
        return (void*)bl;
    }
    ```

    変更後 (`mem_plan9.c` の一部):
    ```c
    static void
    sysalloc(void)
    {
        uintptr nbytes;
        uint64 *stat;
        void *p;

        nbytes = g->m->scalararg[0];
        stat = g->m->ptrarg[0];
        g->m->scalararg[0] = 0;
        g->m->ptrarg[0] = nil;

        p = brk(nbytes);
        if(p != nil)
            runtime·xadd64(stat, nbytes);

        g->m->ptrarg[0] = p;
    }

    #pragma textflag NOSPLIT
    void*
    runtime·sysAlloc(uintptr nbytes, uint64 *stat)
    {
        void (*fn)(void);
        void *p;

        g->m->scalararg[0] = nbytes;
        g->m->ptrarg[0] = stat;
        fn = sysalloc;
        runtime·onM(&fn);
        p = g->m->ptrarg[0];
        g->m->ptrarg[0] = nil;
        return p;
    }
    ```

## コアとなるコードの解説

このコミットのコアとなる変更は、`runtime·sysAlloc` 関数に `NOSPLIT` フラグを適用することです。

### `NOSPLIT` フラグの適用

GoランタイムのC言語ソースファイルにおいて、`#pragma textflag NOSPLIT` は、その直後に続く関数がスタック成長チェックをスキップするようにコンパイラに指示します。
`runtime·sysAlloc` は、GoランタイムがOSからメモリを直接要求する低レベルなインターフェースです。この関数は、Goのヒープの基盤となるメモリを確保するために頻繁に呼び出されます。
`NOSPLIT` を適用することで、`sysAlloc` が呼び出される際に、ゴルーチンのスタックが十分な大きさであるかどうかのチェックが省略されます。これにより、以下のような利点が得られます。

*   **オーバーヘッドの削減**: スタックチェックはわずかながらCPUサイクルを消費します。`sysAlloc` のような頻繁に呼び出される関数からこのオーバーヘッドを取り除くことで、全体的なメモリ割り当てのパフォーマンスが向上します。
*   **ランタイムの安定性**: メモリ割り当て中にスタック成長が必要となり、そのスタック成長自体がさらにメモリ割り当てを必要とするような再帰的な状況やデッドロックのリスクを排除します。これは、ガベージコレクタやスケジューラのような他のランタイムコンポーネントが `sysAlloc` を呼び出す際に特に重要です。これらのコンポーネントは、非常に制約された環境下で動作する必要があるため、予期せぬスタック成長は問題を引き起こす可能性があります。

### Plan 9 固有の `runtime·sysAlloc` の変更

`src/pkg/runtime/mem_plan9.c` における変更は、他のOS向けの変更よりも複雑です。これは、Plan 9のシステムコールインターフェースや、GoランタイムがPlan 9上でどのようにメモリを管理するかの特性に起因します。

*   **`sysalloc` ヘルパー関数の導入**:
    元の `runtime·sysAlloc` のロジックが `sysalloc` という新しい静的関数に抽出されました。この関数は、`brk` システムコールを呼び出して実際にメモリを割り当て、統計情報を更新します。

*   **`runtime·onM` の使用**:
    新しい `runtime·sysAlloc` は、直接 `brk` を呼び出す代わりに、`runtime·onM(&fn)` を使用して `sysalloc` 関数を呼び出します。
    `runtime·onM` は、Goランタイムの内部関数であり、引数として渡された関数ポインタ（この場合は `sysalloc`）を、現在のOSスレッド（M: Machine）のコンテキストで実行します。これは、ゴルーチンのスタックではなく、OSスレッドのスタック上でコードを実行することを意味します。
    このメカニズムを使用する主な理由は、`sysalloc` のような低レベルのメモリ割り当て操作が、ゴルーチンのスタック成長メカニズムの影響を受けずに、OSスレッドのスタック上で安全かつ中断されずに実行されることを保証するためです。これにより、スタック成長チェックが不要になり、`NOSPLIT` の目的が達成されます。
    引数 (`nbytes` と `stat`) は、`g->m->scalararg[0]` と `g->m->ptrarg[0]` を介して `sysalloc` に渡され、結果 (`p`) も同様に `g->m->ptrarg[0]` を介して返されます。これは、`runtime·onM` を使用する際の一般的な引数/戻り値の渡し方です。

このPlan 9固有の変更は、`NOSPLIT` の目的を達成するためのより複雑なアプローチを示しており、特定のOS環境におけるランタイムの設計上の考慮事項を浮き彫りにしています。

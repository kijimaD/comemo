## 変更の背景

ソフトウェア開発において、`TODO` コメントは将来の作業や改善点を示すためにコード内に残されます。これらは、特定の機能が未実装であること、既存の実装に改善の余地があること、あるいは将来的に考慮すべき設計上の課題があることを開発者に知らせる役割を果たします。

このコミットでは、`net/http/transport.go` 内の2つの `TODO` コメントが削除されました。`TODO` コメントが削除される背景にはいくつかの理由が考えられます。

1.  **課題の解決**: `TODO` が示していた課題が既に実装されたか、別の方法で解決された場合。
2.  **設計変更**: コードの設計が変更され、その `TODO` が指していた機能や考慮事項が不要になった場合。
3.  **優先度の低下**: その `TODO` が示す課題の優先度が低下し、当面対応する必要がなくなった場合。
4.  **コメントの陳腐化**: 時間の経過とともにコメントが古くなり、現在のコードベースの状況と合わなくなった場合。

今回のケースでは、機能的なコードの変更は一切なく、コメントのみが削除されていることから、これらの `TODO` が指していた課題が既に解決されたか、あるいはもはや関連性がなくなったため、コードベースのクリーンアップの一環として削除された可能性が高いと考えられます。

なお、削除された `TODO` コメントにはそれぞれ `(Issue 15461)` と `(Issue 13957)` というIssue番号が記載されていましたが、Web検索の結果、Issue 15461は `cmd/compile/internal/ssa` に関連するものであり、`net/http` とは直接関係がないことが判明しました。Issue 13957については、関連する公開Issueが見つかりませんでした。このことから、これらのIssue番号は内部的なトラッキングシステムのものであるか、あるいは単にコメントが古くなっていた可能性が示唆されます。

## 前提知識の解説

### Go言語の `net/http` パッケージ

`net/http` パッケージは、Go言語の標準ライブラリの一部であり、HTTPクライアントとサーバーの機能を提供します。これにより、開発者はWebアプリケーションやAPIを簡単に構築したり、HTTPリクエストを送信したりすることができます。このパッケージは、HTTP/1.1およびHTTP/2プロトコルをサポートし、TLS（Transport Layer Security）によるセキュアな通信も扱えます。

### `http.Transport` 構造体

`http.Transport` は `net/http` パッケージにおけるHTTPクライアントの低レベルな実装を担う構造体です。`http.Client` が高レベルなAPIを提供するのに対し、`http.Transport` は以下の主要な機能を管理します。

*   **接続の確立と管理**: TCP接続の確立、TLSハンドシェイク、接続の再利用（Keep-Alive）など。
*   **接続プール**: 効率的な通信のために、確立された接続を再利用するためのプールを管理します。
*   **プロキシ設定**: HTTPリクエストをプロキシサーバー経由で送信するための設定。
*   **HTTP/2のサポート**: HTTP/2プロトコルへのアップグレードと多重化通信の管理。
*   **タイムアウト設定**: 接続確立、リクエスト送信、レスポンス受信などの各段階でのタイムアウト設定。

`http.Transport` は、特にパフォーマンスが要求されるアプリケーションにおいて、接続の効率的な管理が重要となるため、その設定項目は多岐にわたります。

### `TODO` コメント

`TODO` コメントは、ソースコード内に記述される特別なコメントで、開発者が将来的に対応すべきタスクや改善点をマークするために使用されます。これらは通常、コードの機能には影響を与えませんが、コードベースの健全性を維持し、未解決の課題を追跡するために役立ちます。

### `MaxIdleConns`

`http.Transport` の設定項目の一つである `MaxIdleConns` は、アイドル状態（現在使用されていない）の永続的なHTTP接続を接続プールに保持する最大数を指定します。この設定により、同じホストへの後続のリクエストが来た際に、新しいTCP接続を確立するオーバーヘッドを回避し、既存の接続を再利用することでパフォーマンスを向上させることができます。

### `Keep-Alive` ヘッダー

HTTP/1.1プロトコルでは、`Connection: Keep-Alive` ヘッダーを使用することで、クライアントとサーバー間で単一のTCP接続を複数のHTTPリクエスト/レスポンスの交換に再利用できます。これにより、各リクエストごとに新しい接続を確立・切断する際のオーバーヘッド（TCPスリーウェイハンドシェイク、TLSハンドシェイクなど）が削減され、Webページのロード時間やAPIの応答速度が向上します。

### 同時TCP接続試行の制限

ネットワークリソースの枯渇や、特定のサーバーへの過負荷を防ぐために、クライアントが同時に確立しようとするTCP接続の数を制限することがあります。これは、特に多数の並行リクエストを処理する際に、システム全体の安定性を保つ上で重要な考慮事項となります。

## 技術的詳細

削除された2つの `TODO` コメントは、`http.Transport` の接続管理における重要な改善点を示唆していました。

1.  `// TODO: MaxIdleConns tunable for global max cached connections (Issue 15461)`
    このコメントは、グローバルな最大キャッシュ接続数を調整可能にする必要性を示していました。`http.Transport` には `MaxIdleConnsPerHost` という設定がありますが、これはホストごとのアイドル接続数を制限するものです。この `TODO` は、すべてのホストを合わせたアイドル接続の総数に対するグローバルな制限を設けることの検討を促していました。これにより、クライアントが保持するアイドル接続の総量をより細かく制御し、リソース消費を最適化する意図があったと考えられます。

2.  `// TODO: tunable on timeout on cached connections (and advertise with Keep-Alive header?)`
    このコメントは、キャッシュされたアイドル接続のタイムアウト値を調整可能にすること、そしてそのタイムアウト情報を `Keep-Alive` ヘッダーを通じてサーバーに通知することの検討を促していました。HTTPの `Keep-Alive` ヘッダーには、`timeout` パラメータを含めることができ、これによりサーバーはクライアントが接続を保持する意図のある期間を知ることができます。クライアント側でアイドル接続のタイムアウトを調整可能にすることで、ネットワークの状況やアプリケーションの要件に応じて、接続の再利用期間を最適化し、不要な接続の長期保持を防ぐことができます。また、この情報をサーバーに通知することで、クライアントとサーバー間での接続管理ポリシーの整合性を高めることができます。

これらの `TODO` コメントが削除されたことは、以下のいずれかの状況を示唆しています。

*   **機能の実装**: これらの機能が既に `http.Transport` または関連するコンポーネントに実装された。例えば、グローバルなアイドル接続数の制限や、キャッシュされた接続のタイムアウト設定が追加された可能性があります。
*   **設計の変更**: `net/http` パッケージの設計が変更され、これらの `TODO` が指していた機能がもはや必要とされなくなったか、別の方法で解決されることになった。
*   **優先度の変更**: これらの機能の優先度が低下し、当面は実装されないことになったため、コメントが削除された。
*   **コメントの陳腐化**: コメントが古くなり、現在のコードベースの状況と合わなくなったため、クリーンアップの一環として削除された。

今回のコミットは機能的な変更を伴わないため、これらの `TODO` が指す課題が解決されたか、あるいは不要になったと判断された結果のクリーンアップであると解釈するのが最も自然です。

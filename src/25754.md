# [インデックス 25754] ファイルの概要

このコミットは、GoのCgo機能において、エクスポートされたGo関数がGoのポインタをCコードに返せないようにする変更を導入しています。これは、GoのガベージコレクタがGoのポインタを追跡し、移動させる可能性があるため、Cコードがそのポインタを保持しているとメモリ安全性の問題を引き起こす可能性があるためです。この変更により、Cgoを介したGoとC間の安全な相互運用が強化されます。

## 変更の背景

Goのガベージコレクタ（GC）は、Goヒープ上のオブジェクトを移動させることがあります。Cgoを使ってGo関数をCから呼び出し、そのGo関数がGoヒープ上のメモリへのポインタをCに返した場合、Cコードがそのポインタを使用している間にGoのGCがそのメモリを移動させてしまうと、Cコードは無効なメモリを参照することになり、クラッシュやデータ破損といった深刻なメモリ安全性の問題を引き起こします。

この問題を防ぐため、GoはCgoのルールとして「GoのポインタをCに渡してはならない」という原則を設けています。しかし、エクスポートされたGo関数の戻り値に関しては、このチェックが不十分でした。このコミットは、このギャップを埋め、エクスポートされたGo関数がGoのポインタをCに返すことを禁止することで、Cgoのメモリ安全性を向上させることを目的としています。

コミットメッセージにある `#12416` は、この問題が報告されたGoのイシュートラッカーの番号であると考えられます。

## 前提知識の解説

### Cgo
Cgoは、GoプログラムからCコードを呼び出したり、CコードからGo関数を呼び出したりするためのGoのメカニズムです。GoとCは異なるメモリ管理モデルと型システムを持つため、Cgoはこれらを橋渡しするための厳格なルールとメカニズムを提供します。

### Goのガベージコレクタとポインタ
Goは自動メモリ管理（ガベージコレクション）を採用しています。Goのガベージコレクタは、不要になったメモリを自動的に解放するだけでなく、メモリの断片化を解消するためにヒープ上のオブジェクトを移動（コンパクション）させることがあります。このとき、GoのポインタはGCによって追跡され、オブジェクトの新しいアドレスに自動的に更新されます。

### GoポインタとCポインタ
- **Goポインタ**: Goのガベージコレクタによって管理されるメモリ領域（Goヒープ）を指すポインタです。GCによって指すアドレスが変更される可能性があります。
- **Cポインタ**: Cのメモリ管理（`malloc`/`free`など）によって管理されるメモリ領域を指すポインタです。GoのGCはCのメモリを追跡しないため、Cポインタが指すアドレスはGCによって移動されることはありません。

Cgoの重要なルールの一つは、「GoのポインタをCに渡してはならない」というものです。これは、CコードがGoのポインタを保持している間にGCがそのポインタが指すメモリを移動させると、Cコードが不正なメモリにアクセスする「ダングリングポインタ」の問題が発生するためです。ただし、CのメモリをGoのポインタ型（`*C.char`など）としてGoコード内で扱うことは可能です。

## 技術的詳細

このコミットの技術的詳細は、主に`cmd/cgo`ツールと`runtime`パッケージの連携によって実現されています。

1.  **`cmd/cgo`によるGo関数のラッピング**:
    `cmd/cgo`は、`//export`ディレクティブでエクスポートされたGo関数に対して、Cから呼び出せるようにするためのラッパー関数を生成します。このコミットでは、このラッパー生成ロジックが変更され、エクスポートされたGo関数の戻り値にGoポインタが含まれていないかをチェックする機構が追加されました。

2.  **`runtime`パッケージでのポインタチェック**:
    `runtime`パッケージには、Cgoのポインタルールを強制するための`cgoCheckPointer`関数群が存在します。このコミットでは、エクスポートされたGo関数の戻り値をチェックするための新しい関数`cgoCheckResult`が追加され、既存の`cgoCheckArg`関数も汎用的なエラーメッセージを受け取れるように変更されました。

    `cgoCheckResult`は、Go関数がCに返す値がGoポインタを含んでいるかどうかを再帰的に検査します。もしGoポインタが見つかった場合、`panic`を発生させてプログラムを終了させます。これにより、Cコードが不正なGoポインタを受け取ることを未然に防ぎます。

## コアとなるコードの変更箇所

### `src/cmd/cgo/out.go`
-   エクスポートされたGo関数のラッパー生成ロジックが変更されました。
-   `//go:cgo_export_dynamic`ディレクティブの生成方法が調整されました。
-   特に、戻り値を持つエクスポート関数に対して、`_cgoCheckResult`を呼び出す`defer`文が追加されました。これは、Go関数が実際に値を返す直前に、その戻り値がGoポインタを含んでいないかをチェックするためです。

### `src/runtime/cgocall.go`
-   `cgoCheckPointer`関数と`cgoCheckArg`関数のシグネチャが変更され、エラーメッセージを引数として受け取れるようになりました。これにより、より具体的なエラーメッセージを生成できるようになります。
-   新しい定数`cgoResultFail = "cgo result has Go pointer"`が追加されました。
-   `cgoCheckResult`という新しい関数が追加されました。この関数は、エクスポートされたGo関数の戻り値をチェックし、Goポインタが含まれている場合に`cgoResultFail`メッセージで`panic`を発生させます。
-   `cgoCheckArg`、`cgoCheckUnknownPointer`などの内部的なポインタチェック関数も、新しいエラーメッセージ引数を受け取るように更新されました。

### `misc/cgo/errors/ptr.go`
-   `export1`という新しいテストケースが追加されました。これは、エクスポートされたGo関数がGoポインタを返そうとした場合に、`cgo`ツールがエラーを発生させることを検証します。

//go:linkname _cgoCheckResult runtime.cgoCheckResult
func _cgoCheckResult(val interface{}) {
	if debug.cgocheck == 0 {
		return
	}

	ep := (*eface)(unsafe.Pointer(&val))
	t := ep._type
	cgoCheckArg(t, ep.data, t.kind&kindDirectIface == 0, false, cgoResultFail)

-   `cgoCheckArg`と`cgoCheckUnknownPointer`は、`msg`という新しい引数を受け取るように変更されました。これにより、ポインタチェックが失敗した際に、呼び出し元が指定したより具体的なエラーメッセージ（例: `cgoCheckPointerFail`または`cgoResultFail`）で`panic`を発生させることができます。
-   `_cgoCheckResult`関数は、`//go:linkname`ディレクティブによって`runtime.cgoCheckResult`としてリンクされ、`cmd/cgo`が生成するラッパーから呼び出されます。
-   この関数は、`val interface{}`として渡された戻り値の型情報とデータポインタを取得し、`cgoCheckArg`を呼び出して、その値がGoポインタを含んでいないかをチェックします。ここで渡される`msg`は`cgoResultFail`であり、戻り値のチェックであることを明確に示します。`top`引数は`false`に設定されており、これは戻り値のトップレベルでもGoポインタが許可されないことを意味します。

これらの変更により、Goのコンパイラとランタイムが連携して、エクスポートされたGo関数がGoポインタをCに返すことを厳密に禁止し、メモリ安全性を確保しています。

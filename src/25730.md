# [インデックス 25730] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) に `-libgcc` オプションを追加し、`libgcc` (Cコンパイラのサポートライブラリ) の扱いを改善することを目的としています。特に、Cgoを使用するGoプログラムの内部リンク時における `libgcc` の依存関係管理を柔軟にし、Cコンパイラがインストールされていない環境でもGoプログラムをビルドできるようにするための変更が含まれています。

## 変更の背景

Go言語はCgoを通じてC言語のコードと連携する機能を提供しています。Cgoを使用するGoプログラムをビルドする際、特にGoリンカが「内部リンクモード」で動作する場合、C言語のコードが依存するランタイムサポート関数を提供するために `libgcc.a` というCコンパイラのサポートライブラリが必要になることがあります。

このコミット以前は、`libgcc` の扱いが柔軟でなく、以下のような問題がありました。

1.  **`libgcc` の自動コピー**: `cmd/dist` (Goディストリビューションを構築するコマンド) が `libgcc` をディストリビューションにコピーしていました。これは、Cコンパイラがインストールされていない環境でのGoプログラムのビルドを妨げる可能性がありました。
2.  **Cコンパイラへの依存**: `libgcc` のパスを特定するためにCコンパイラ (`gcc` など) の実行に依存しており、Cコンパイラがない環境ではビルドが困難でした。
3.  **リンカの柔軟性の欠如**: 開発者が `libgcc` の使用を明示的に制御する手段がありませんでした。これにより、特定のシナリオで `libgcc` が不要な場合でもリンクが試みられ、問題を引き起こす可能性がありました（例: 過去にはGo issue #9510で、複数のCgoパッケージが同じ `libgcc` 関数を要求することで「多重定義エラー」が発生する問題が報告されています）。

この変更の主な目的は、Goの内部リンカが `libgcc` の依存関係をより適切に管理できるようにし、CコンパイラがインストールされていないシステムでもGoプログラム（特にCgoを使用しない、または標準ライブラリのCgoパッケージのみを使用するプログラム）をビルドできるようにすることです。

## 前提知識の解説

*   **Goリンカ (`cmd/link`)**: Goプログラムのコンパイル済みオブジェクトファイルを結合して実行可能ファイルを生成するツールです。Goには独自のリンカがあり、Cgoを使用しない純粋なGoプログラムでは通常、この内部リンカが使用されます。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用すると、GoとCの間の相互運用が可能になります。
*   **内部リンクモード (Internal Link Mode)**: Goリンカが、外部のシステムリンカ (`gcc` など) を使用せずに、すべてのオブジェクトファイル（GoとCgo由来のものを含む）を直接結合して単一の実行可能ファイルを生成するモードです。このモードは一般的にビルドが高速で、生成されるバイナリも小さくなります。標準ライブラリのCgoパッケージ（例: `net`, `os/user`, `crypto/x509`）を使用する場合、Goはしばしば内部リンクモードをデフォルトとします。
*   **`libgcc.a`**: GNU Compiler Collection (GCC) のランタイムサポートライブラリです。C言語のコードが特定の低レベルな操作（例: 64ビット整数演算のエミュレーション、浮動小数点演算のヘルパー関数など）を実行する際に必要となるサブルーチンを含んでいます。Cgoを通じてGoプログラムに組み込まれたCコードがこれらの関数に依存する場合、`libgcc.a` がリンク時に必要となります。
*   **`--print-libgcc-file-name`**: `gcc` などのCコンパイラに渡すオプションで、`libgcc.a` ファイルのパスを出力させることができます。リンカが `libgcc` の場所を動的に特定するために使用されます。

## 技術的詳細

このコミットは、主に以下の技術的な変更を導入しています。

1.  **`-libgcc` オプションの追加**:
    *   `cmd/link` に新しいフラグ `-libgcc file` が追加されました。これにより、ユーザーは `libgcc.a` のパスを明示的に指定できるようになります。
    *   このオプションは内部リンクモードでのみ有効です。
    *   `file` に `none` を指定すると、`libgcc` の使用を完全にスキップできます。これは、`libgcc` が不要であることが確実な場合や、特定のデバッグシナリオで役立ちます。
    *   `-libgcc` が指定されない場合、リンカは `extld` (外部リンカ、通常は `gcc`) を実行し、`--print-libgcc-file-name` オプションを使って `libgcc.a` のパスを動的に検出します。これにより、システムにインストールされているCコンパイラの設定に自動的に適応します。

2.  **`cmd/dist` からの `libgcc` コピーの削除**:
    *   `src/cmd/dist/build.go` から `copyLibgcc()` 関数が削除されました。これにより、Goディストリビューションのビルドプロセスにおいて `libgcc` がGoの `pkg` ディレクトリにコピーされなくなります。
    *   この変更は、GoのインストールがCコンパイラに依存しないようにするための重要なステップです。Goのツールチェイン自体が `libgcc` を配布する必要がなくなるため、より軽量で独立したGo環境を構築できます。

3.  **`libgcc` なしでのCgoパッケージのテスト**:
    *   `src/cmd/dist/test.go` に新しいテストが追加されました。これらのテストは、`crypto/x509`, `net`, `os/user` といった標準ライブラリのCgoパッケージが、`-ldflags="-linkmode=internal -libgcc=none"` オプションを使用して `libgcc` なしで内部リンクできることを確認します。
    *   このテストの追加は、Cコンパイラがインストールされていない環境でも、これらの標準Cgoパッケージを含むGoプログラムがビルドできることを保証するためのものです。これは、Goの「Cコンパイラなしでビルド可能」という目標をサポートします。

4.  **リンカの `libgcc` 検索ロジックの改善**:
    *   `src/cmd/link/internal/ld/lib.go` の `loadlib()` 関数内で、未定義のシンボルを解決するために `libgcc` を検索するロジックが変更されました。
    *   以前はハードコードされたパス (`%s/pkg/libgcc/%s_%s/libgcc`) を使用していましたが、新しいロジックでは `libgccfile` 変数（`-libgcc` オプションで設定されるか、Cコンパイラから動的に取得される）を使用します。
    *   `hostlinkArchArgs()` という新しいヘルパー関数が追加され、外部リンカに渡すアーキテクチャ固有の引数 (`-m32`, `-m64`, `-marm` など) を一元的に管理するようになりました。これにより、コードの重複が減り、保守性が向上しています。

*   `src/cmd/link/doc.go`: `-libgcc` オプションに関するドキュメントの追加。
*   `src/cmd/link/internal/ld/ar.go`: `hostArchive` 関数内で `libgcc` ファイルが見つからない場合のデバッグ出力の追加。
*   `src/cmd/link/internal/ld/lib.go`:
    *   `libgccfile` 変数の追加。
    *   `loadlib()` 関数内の `libgcc` 検索ロジックの変更。Cコンパイラを実行して `libgcc` パスを動的に取得する処理が追加されました。
    *   `hostlink()` 関数からアーキテクチャ固有の引数設定ロジックを `hostlinkArchArgs()` 関数に分離。
    *   `hostlinkArchArgs()` ヘルパー関数の追加。

*   `src/go/build/deps_test.go`: Cgoパッケージの依存関係に関するコメントの更新。

## コアとなるコードの解説

1.  **`src/cmd/dist/build.go` の変更**:
    `copyLibgcc()` 関数が完全に削除されました。この関数は、Goのビルド時にCコンパイラから `libgcc.a` のパスを取得し、Goの `pkg` ディレクトリにコピーする役割を担っていました。この削除により、Goのディストリビューションが `libgcc` をバンドルする必要がなくなり、Goのビルドシステムがより独立したものになります。

2.  **`src/cmd/dist/test.go` の変更**:
    `nolibgcc` という新しいテストスイートが追加されました。このテストは、`cgoPackages` リストに定義されている `crypto/x509`, `net`, `os/user` などのCgoを使用する標準パッケージに対して、`go test -ldflags="-linkmode=internal -libgcc=none"` コマンドを実行します。これにより、これらのパッケージが `libgcc` なしで内部リンクできることが検証され、Cコンパイラがない環境でもGoプログラムがビルドできるという保証が強化されます。

3.  **`src/cmd/link/internal/ld/lib.go` の `loadlib()` 関数内の変更**:
    `libgccfile` という新しいグローバル変数が導入され、`-libgcc` オプションで指定された `libgcc` のパスを保持します。
    `loadlib()` 関数内で、未定義のシンボルが存在し、`libgcc` が必要な場合に、以下のロジックが実行されます。
    *   もし `libgccfile` が空文字列の場合（つまり `-libgcc` オプションが指定されていない場合）、`extld` (外部リンカ、デフォルトは `gcc`) を実行し、`--print-libgcc-file-name` オプションを使って `libgcc.a` のパスを動的に取得します。
    *   このプロセスでエラーが発生した場合、または `libgccfile` が `none` に設定されている場合、`libgcc` の使用はスキップされます。
    *   最終的に、有効な `libgccfile` があれば、`hostArchive(libgccfile)` を呼び出して `libgcc` をリンクします。
    この変更により、`libgcc` のパスの決定がより動的かつ柔軟になり、ユーザーが明示的に制御できるようになりました。

4.  **`hostlinkArchArgs()` 関数の追加**:
    `src/cmd/link/internal/ld/lib.go` に `hostlinkArchArgs()` という新しい関数が追加されました。この関数は、現在のターゲットアーキテクチャに基づいて、外部リンカ (`gcc` など) に渡すべき適切なアーキテクチャ固有のフラグ（例: `-m32`、`-m64`、`-marm`）を返します。これにより、`hostlink()` 関数内の重複するコードが削除され、リンカのコードベースがよりクリーンで保守しやすくなりました。

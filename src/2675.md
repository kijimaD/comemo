## 元コミット内容

このコミットは、「出力引数（関数の戻り値）がR0レジスタにプッシュされるべきところを、誤ってSP（スタックポインタ）にプッシュされていたタイプミスを修正した」と説明しています。しかし、実際のコード変更を見ると、メッセージとは逆の修正が行われています。つまり、**出力引数が誤ってR0レジスタを基準に処理されていたのを、SP（スタックポインタ）を基準に処理するように修正した**、というのが正しい内容です。これは、コミットメッセージが簡潔さを優先した結果、やや誤解を招く表現になったものと考えられます。

## 変更の背景

GoコンパイラのARMアーキテクチャ（`5g`）バックエンドにおいて、関数の戻り値（出力引数）をスタックに配置する際の処理にバグが存在していました。
Go言語の関数呼び出し規約では、戻り値は通常、呼び出し元のスタックフレームに確保された領域に書き込まれます。この領域はスタックポインタ（SP）を基準としたオフセットでアクセスされるべきです。
しかし、バグのあるコードでは、この戻り値のメモリ位置を決定する際に、誤ってR0レジスタを基準としてオフセットが計算されていました。R0レジスタは汎用レジスタであり、特定の関数呼び出し規約では戻り値を格納するために使われることもありますが、スタック上のメモリ領域を指すSPとは役割が異なります。
この誤ったレジスタの使用は、プログラムが戻り値を不正なメモリ領域に書き込んだり、そこから読み取ろうとしたりする原因となり、結果としてクラッシュ、データ破損、または予期せぬプログラムの動作を引き起こす可能性がありました。
このコミットは、このような深刻な問題を修正し、GoプログラムがARM上で正しく動作するようにするために行われました。

## 前提知識の解説

*   **Goコンパイラとバックエンド**: Go言語のソースコードは、まずフロントエンドによって抽象構文木（AST）に変換されます。その後、各ターゲットアーキテクチャ（例: x86-64, ARM）に対応するバックエンドが、ASTを機械語にコンパイルします。`5g`は、GoコンパイラのARMアーキテクチャ（32ビットARM）向けのバックエンドを指す古い命名規則です。
*   **レジスタ (Registers)**: CPU内部にある非常に高速な記憶領域で、演算やデータ転送に一時的に使用されます。
    *   **R0 (ARM)**: ARMアーキテクチャにおける汎用レジスタの一つ。多くのARM関数呼び出し規約（AAPCSなど）では、関数の最初の引数や、32ビットの戻り値を格納するために使用されます。しかし、スタック上のメモリ位置を直接指すものではありません。
    *   **SP (Stack Pointer)**: スタックの現在の最上位（または最下位）のアドレスを指すレジスタ。関数呼び出し時の引数、ローカル変数、戻りアドレスなどを一時的に保存するスタック領域の管理に不可欠です。スタック上のデータはSPを基準としたオフセットでアクセスされます。
*   **スタック (Stack)**: プログラム実行時に一時的なデータを格納するために使用されるメモリ領域。LIFO (Last-In, First-Out) 方式でデータが追加・削除されます。関数呼び出し時には、引数、戻りアドレス、ローカル変数などがスタックにプッシュ（追加）され、関数終了時にポップ（削除）されます。
*   **関数呼び出し規約 (Calling Convention)**: 関数が呼び出される際に、引数をどのように渡し、戻り値をどのように受け取るか、レジスタをどのように保存・復元するかなどを定めた取り決めです。アーキテクチャやOSによって異なり、コンパイラはこれに従ってコードを生成します。
*   **`nodarg` 関数**: Goコンパイラのバックエンドにおいて、関数の引数や戻り値に対応する内部表現（ノード）を生成・設定する役割を持つ関数と推測されます。特に、引数や戻り値がメモリ上のどこに配置されるか（オフセット計算）や、どのレジスタを基準とするかといった低レベルな詳細を扱います。
*   **`OINDREG`**: オペランドがレジスタの間接参照であることを示すオペレーションコード。例えば、`[REGSP + offset]` のように、レジスタの値にオフセットを加えたアドレスにあるメモリ位置を参照する際に使用されます。
*   **`REGRET`**: Goコンパイラの内部で、関数の戻り値を格納するレジスタ（ARMではR0など）を抽象的に指す定数です。
*   **`REGSP`**: Goコンパイラの内部で、スタックポインタレジスタ（SP）を抽象的に指す定数です。
*   **`xoffset`**: 構造体やスタックフレーム内でのオフセット（基準位置からの相対的な距離）を示すフィールドです。

## 技術的詳細

このコミットは、`src/cmd/5g/gsubr.c` 内の `nodarg` 関数に焦点を当てています。`nodarg` 関数は、Goコンパイラが関数の引数や戻り値を表現する内部ノードを構築する際に使用される重要な関数です。

主な変更点は以下の通りです。

1.  **`n->xoffset` の計算修正**:
    *   `nodarg` 関数内で、構造体型 (`first->width`) および非構造体型 (`t->width`) の両方で、`n->xoffset` の計算に `+ 4` が追加されました。
    *   変更前: `n->xoffset = first->width;` および `n->xoffset = t->width;`
    *   変更後: `n->xoffset = first->width + 4;` および `n->xoffset = t->width + 4;`
    *   この `+ 4` は、ARMの関数呼び出し規約において、スタックフレームの開始位置から戻りアドレス（通常4バイト）が格納される領域をスキップし、その後に続く出力引数やローカル変数の領域を正しく指すようにするための調整であると考えられます。これにより、スタック上のオフセットが正確に計算され、メモリの誤ったアクセスを防ぎます。

2.  **出力引数ノードのレジスタ指定の修正**:
    *   `switch(fp)` 文の `case 0: // output arg` ブロックが修正されました。このブロックは、関数の戻り値（出力引数）を処理する部分です。
    *   変更前: `n->val.u.reg = REGRET;`
    *   変更後: `n->val.u.reg = REGSP;`
    *   この変更がコミットメッセージの核心です。以前は、出力引数のノードが `REGRET` (R0レジスタ) を基準としてメモリを参照するように設定されていました。しかし、出力引数はスタック上に配置されるべきであるため、`OINDREG` (レジスタ間接参照) と組み合わせる場合、スタックポインタ `REGSP` (SPレジスタ) を基準とすべきです。
    *   この修正により、コンパイラは `[SP + xoffset]` のような命令を生成するようになり、出力引数がスタック上の正しいメモリ位置に書き込まれることが保証されます。

3.  **`case 2: // offset output arg` の削除**:
    *   `nodarg` 関数内に存在した `case 2` のブロックが完全に削除されました。このブロックには `fatal("shouldnt be used");` というコメントがあり、元々使用されるべきではない、または問題のあるコードパスであったことが示唆されています。
    *   `case 0` のロジックが改善され、出力引数の処理が正しく行われるようになったことで、この冗長または誤ったケースが不要になったと考えられます。

これらの変更により、GoコンパイラはARMアーキテクチャ上で、関数の戻り値をスタックに正しく配置するようになり、プログラムの安定性と正確性が向上しました。

## コアとなるコードの解説

上記の差分は、`nodarg` 関数内の3つの主要な変更を示しています。

1.  **`n->xoffset = first->width;` から `n->xoffset = first->width + 4;`**:
    *   この行は、構造体型の戻り値（または引数）のスタック上のオフセットを計算する部分です。`first->width` は構造体のサイズを示します。これに `4` を加算することで、スタックフレームの先頭から、戻りアドレスなどの予約領域（通常4バイト）を考慮した正しいオフセットを `n->xoffset` に設定します。これにより、構造体のデータがスタック上の適切な位置に配置されるようになります。

2.  **`n->xoffset = t->width;` から `n->xoffset = t->width + 4;`**:
    *   この行は、非構造体型の戻り値（または引数）のスタック上のオフセットを計算する部分です。`t->width` は型のサイズを示します。上記と同様に `4` を加算することで、スタック上の正しいオフセットを計算し、データが適切な位置に配置されるようにします。

3.  **`n->val.u.reg = REGRET;` から `n->val.u.reg = REGSP;` ( `case 0: // output arg` 内)**:
    *   この変更は、出力引数（関数の戻り値）のノードが参照するベースレジスタを修正します。
    *   変更前は `REGRET` (R0レジスタ) が指定されていました。これは、戻り値がR0レジスタに格納されることを意図しているように見えますが、`OINDREG` (レジスタ間接参照) と `xoffset` を組み合わせてスタック上のメモリ位置を指す場合には不適切です。R0は通常、戻り値そのものを保持するレジスタであり、スタック上のアドレスを計算するためのベースレジスタではありません。
    *   変更後は `REGSP` (SPレジスタ) が指定されています。これにより、出力引数はスタックポインタを基準としたオフセット (`[SP + xoffset]`) でアクセスされるようになり、スタック上の正しいメモリ位置に書き込まれることが保証されます。これは、Goの関数呼び出し規約とARMアーキテクチャのスタックフレーム管理に合致する正しい動作です。

4.  **`case 2: // offset output arg` ブロックの削除**:
    *   このブロックは、以前から「使用されるべきではない」とコメントされており、今回の修正で完全に削除されました。これは、`case 0` のロジックが改善されたことで、この冗長または誤った処理パスが不要になったことを意味します。

これらの変更は、GoコンパイラがARMアーキテクチャ上で生成するコードの正確性を大幅に向上させ、特に複雑なデータ構造や複数の戻り値を持つ関数の処理において、メモリの破損や不正な動作を防ぐ上で非常に重要です。

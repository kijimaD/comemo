# [インデックス 22630] ファイルの概要

このコミットは、Go言語のランタイムプロファイリングツールである`pprof`パッケージ内のテストコードにおいて発生していたデータ競合（data race）を修正するものです。具体的には、`src/runtime/pprof/trace_stack_test.go`ファイル内のテスト関数`TestTraceSymbolize`において、`io.Pipe`の読み書き操作とクローズ操作が並行して実行されることによって発生していた競合状態を解消し、テストの安定性を向上させています。

## 変更の背景

このコミットは、Goランタイムのプロファイリングツールである`pprof`のテストコード`src/runtime/pprof/trace_stack_test.go`において、テストの実行中に発生していたデータ競合を修正するために導入されました。

具体的には、`TestTraceSymbolize`というテスト関数内で、`io.Pipe`を使用してゴルーチン間でデータのやり取りを行っていました。この際、パイプの読み込み側（`rp.Read`）がまだデータを読み込んでいる最中に、パイプの書き込み側がクローズ（`wp.Close`）され、その結果として読み込み側のパイプもクローズ（`rp.Close`）される可能性がありました。

このような状況では、`rp.Read`と`rp.Close`が同時に実行される、いわゆる「データ競合」が発生し、テストが不安定になったり、予測不能な結果を引き起こしたりする可能性がありました。コミットメッセージにある「`rp.Close` happened concurrently with `rp.Read`. Order them.」という記述は、この並行実行が問題であり、それらの操作の順序を保証する必要があることを明確に示しています。

この問題は、GoのIssueトラッカーで`#10280`として報告されていたものと考えられます。データ競合は、並行処理を行うプログラムにおいて非常に厄介なバグであり、再現性が低く、デバッグが困難な場合が多いため、このようなテストコード内の競合も早期に修正されることが重要です。

## 前提知識の解説

### 1. データ競合 (Data Race)

データ競合とは、複数のゴルーチン（またはスレッド）が同時に同じメモリ領域にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって順序付けされていない場合に発生するバグです。データ競合が発生すると、プログラムの動作が非決定論的になり、予期せぬ結果やクラッシュを引き起こす可能性があります。Go言語では、データ競合を検出するためのツールとしてRace Detectorが提供されています。

### 2. Goの`pprof`パッケージとトレース (Trace)

`pprof`パッケージは、Goプログラムのプロファイリングデータ（CPU使用率、メモリ割り当て、ゴルーチンスタックトレースなど）を収集・可視化するためのツールを提供します。
トレース機能は、Go 1.5で導入されたもので、プログラムの実行中に発生するイベント（ゴルーチンの生成、スケジューリング、システムコール、GCなど）を記録し、その実行フローを詳細に分析するためのものです。これにより、並行処理のボトルネックやデッドロックなどを特定するのに役立ちます。

### 3. `io.Pipe`

`io.Pipe`は、Go言語の標準ライブラリ`io`パッケージで提供される、メモリ内で動作するパイプの実装です。これは、`io.Reader`と`io.Writer`のペアを返します。`PipeWriter`に書き込まれたデータは、対応する`PipeReader`から読み込むことができます。これは、異なるゴルーチン間でデータをストリームとして受け渡す際によく使用されます。

*   `PipeWriter.Write()`: データをパイプに書き込みます。
*   `PipeReader.Read()`: パイプからデータを読み込みます。
*   `PipeWriter.Close()` / `PipeReader.Close()`: パイプをクローズします。パイプがクローズされると、それ以降の読み書き操作はエラーを返します。

### 4. Goの並行処理とチャネル (Channels)

Go言語は、CSP (Communicating Sequential Processes) に基づく並行処理モデルを採用しており、ゴルーチン（軽量スレッド）とチャネル（ゴルーチン間の通信手段）がその中心的な要素です。

*   **ゴルーチン (Goroutines)**: `go`キーワードを使って関数を呼び出すことで、新しいゴルーチンを起動できます。ゴルーチンは非常に軽量で、数千、数万のゴルーチンを同時に実行することが可能です。
*   **チャネル (Channels)**: チャネルは、ゴルーチン間で値を安全に送受信するためのパイプのようなものです。チャネルを介した通信は、自動的に同期が行われるため、データ競合を防ぐのに役立ちます。バッファなしチャネルは、送信側と受信側が同時に準備ができていないとブロックされます。

## 技術的詳細

このデータ競合は、`TestTraceSymbolize`テスト関数内で`io.Pipe`を使用している部分で発生していました。テストの簡略化された流れは以下のようになります。

1.  `io.Pipe()`を呼び出して、`rp` (PipeReader) と `wp` (PipeWriter) を作成します。
2.  新しいゴルーチンを起動し、その中で`rp.Read(data[:])`を呼び出してパイプからの読み込みを試みます。この読み込みは、データが書き込まれるまでブロックされます。
3.  メインゴルーチンでは、`time.Sleep`などで少し待機した後、`wp.Write(data[:])`を呼び出してパイプにデータを書き込みます。これにより、読み込みゴルーチンがブロック解除されます。
4.  テストの終了時に、`defer rp.Close()`と`defer wp.Close()`が設定されています。`defer`は関数の終了時に実行されるため、`TestTraceSymbolize`関数が終了する際にこれらのクローズ操作が実行されます。

問題は、`rp.Read`がまだ実行中であるにもかかわらず、`TestTraceSymbolize`関数が終了し、`defer rp.Close()`が呼び出される可能性があったことです。`rp.Read`と`rp.Close`が同時に同じ`rp`オブジェクトにアクセスしようとすると、データ競合が発生します。特に、`rp.Read`がブロックされている状態で`rp.Close`が呼び出されると、`Read`はエラーを返して終了しますが、その際に内部状態の変更が競合する可能性がありました。

この修正は、バッファなしチャネル`pipeReadDone`を導入することで、`rp.Read`が完了したことをメインゴルーチンに明示的に通知するように変更しています。

変更後の流れは以下のようになります。

1.  `pipeReadDone := make(chan bool)`: バッファなしチャネルを作成します。
2.  読み込みゴルーチン内で`rp.Read(data[:])`が成功した後、`pipeReadDone <- true`を送信します。これにより、読み込みが完了したことが通知されます。
3.  メインゴルーチンでは、`wp.Write(data[:])`でデータを書き込んだ後、`<-pipeReadDone`でチャネルからの受信を待ちます。これにより、読み込みゴルーチンが`rp.Read`を完了し、チャネルに値を送信するまで、メインゴルーチンはブロックされます。
4.  メインゴルーチンが`pipeReadDone`から値を受信した時点で、`rp.Read`は確実に終了しています。このため、その後に`defer rp.Close()`が実行されても、`rp.Read`との競合は発生しません。

この修正により、`rp.Read`と`rp.Close`の実行順序が保証され、データ競合が解消されました。これは、Goの並行処理において、共有リソースへのアクセスを同期するためのチャネルの典型的な使用例です。

## コアとなるコードの解説

1.  **`pipeReadDone := make(chan bool)` の追加**:
    *   これは、読み込みゴルーチンがパイプからの読み込みを完了したことをメインゴルーチンに通知するための、バッファなしチャネルの作成です。バッファなしチャネルは、送信と受信が同時に行われるまでブロックされるため、同期プリミティブとして機能します。

2.  **`pipeReadDone <- true` の追加 (読み込みゴルーチン内)**:
    *   `rp.Read(data[:])`が正常に完了した後、この行が実行されます。これにより、`true`という値が`pipeReadDone`チャネルに送信されます。この送信操作は、メインゴルーチンがこのチャネルから値を受信するまでブロックされます。

3.  **`<-pipeReadDone` の追加 (メインゴルーチン内)**:
    *   `wp.Write(data[:])`でパイプへの書き込みが完了した後、この行が実行されます。これにより、`pipeReadDone`チャネルからの値の受信を待ちます。読み込みゴルーチンが`pipeReadDone <- true`を実行するまで、メインゴルーチンはここでブロックされます。
    *   この同期ポイントにより、`rp.Read`が確実に終了した後に、`TestTraceSymbolize`関数が終了し、`defer rp.Close()`が実行されることが保証されます。これにより、`rp.Read`と`rp.Close`の間のデータ競合が解消されます。

4.  **行番号の更新**:
    *   コードの変更により、テスト内の特定のイベント（GC開始、ゴルーチン切り替えなど）が発生するソースコードの行番号がずれたため、テストの期待値（`want`変数内の`frame`構造体）の行番号もそれに合わせて修正されています。これは、テストが正確なスタックトレース情報を検証するために必要な調整です。

これらの変更により、`io.Pipe`の読み込みとクローズ操作の間の同期が確立され、テストのデータ競合が解消されました。

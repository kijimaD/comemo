## 変更の背景

このコミットは、Goランタイムにおけるチャネルの送受信キューのパフォーマンス問題を解決するために導入されました。以前の実装では、チャネルの待機キュー（`waitq`）が単方向連結リストで管理されており、特に多数のゴルーチンが同じチャネルに対して送受信を試みる「人気のあるチャネル（popular channels）」の場合に、キューからの要素削除（`dequeue`）が非効率になるという問題がありました。

具体的には、単方向連結リストから任意の要素を削除する場合、その要素の前の要素（`prev`）を見つけるためにリストの先頭から探索する必要がありました。これにより、最悪の場合、削除操作の計算量がO(n)となり、多数の操作が連続して行われると全体としてO(n^2)のパフォーマンス劣化を引き起こす可能性がありました。

このコミットでは、チャネルの送受信キューを双方向連結リストに変更することで、このO(n^2)のパフォーマンス問題を回避し、キューからの要素削除をO(1)の定数時間で行えるように改善しました。ベンチマーク結果（`BenchmarkChanPopular`）が示すように、この変更によりパフォーマンスが大幅に向上し、実行時間が約75%削減されました。

## 前提知識の解説

### Goのチャネル (Channels in Go)
Go言語におけるチャネルは、ゴルーチン間で値を送受信するための主要な通信メカニズムです。チャネルは型付けされており、特定の型の値のみを送受信できます。チャネルは、ゴルーチン間の同期と通信を安全かつ効率的に行うための強力なプリミティブです。

チャネルの操作には主に以下の2つがあります。
- **送信 (Send)**: `ch <- value` の形式でチャネルに値を送信します。
- **受信 (Receive)**: `value := <-ch` または `<-ch` の形式でチャネルから値を受信します。

チャネルは、バッファリングされているか否かによって動作が異なります。
- **バッファなしチャネル**: 送信操作は受信操作が準備できるまでブロックし、受信操作は送信操作が準備できるまでブロックします。これにより、ゴルーチン間の同期が保証されます。
- **バッファありチャネル**: バッファが満杯になるまで送信操作はブロックせず、バッファが空になるまで受信操作はブロックしません。

### `sudog` 構造体
Goランタイムにおいて、チャネル操作（送信または受信）によってブロックされたゴルーチンは、`sudog`（"scheduler goroutine" の略）という内部構造体として表現され、チャネルの待機キューに追加されます。`sudog` は、ブロックされたゴルーチンに関する情報（どのゴルーチンか、どのチャネルで待機しているか、送受信する値のアドレスなど）を保持します。

### 連結リスト (Linked List)
連結リストは、データ要素（ノード）が順序付けられて格納されるデータ構造です。各ノードはデータと、次のノードへの参照（ポインタ）を保持します。

- **単方向連結リスト (Singly Linked List)**: 各ノードが次のノードへのポインタのみを持つリストです。リストの先頭から順にしか辿ることができません。特定のノードを削除する場合、そのノードの前のノードを見つけるために先頭から探索する必要があり、O(n)の計算量がかかります。

- **双方向連結リスト (Doubly Linked List)**: 各ノードが次のノードへのポインタと、前のノードへのポインタの両方を持つリストです。これにより、リストを前方にも後方にも辿ることができます。特定のノードを削除する場合、そのノードの前後へのポインタを直接操作できるため、O(1)の定数時間で削除が可能です。

### O(n^2) の性能問題
計算量表記O(n)やO(n^2)は、アルゴリズムの実行時間が入力サイズnに対してどのように増加するかを示します。
- **O(n)**: 線形時間。入力サイズnに比例して実行時間が増加します。
- **O(n^2)**: 二次時間。入力サイズnの二乗に比例して実行時間が増加します。これは、ネストされたループなどでよく見られ、nが大きくなると実行時間が急激に増加するため、大規模なデータセットでは非効率的です。

このコミットの文脈では、単方向連結リストからの要素削除がO(n)であり、これが多数回繰り返されることで全体としてO(n^2)の性能問題を引き起こしていました。

### Goのスケジューラとチャネルの内部動作
Goランタイムには、ゴルーチンを効率的にスケジューリングするスケジューラがあります。チャネル操作は、このスケジューラと密接に連携しています。ゴルーチンがチャネル操作でブロックされると、スケジューラはそのゴルーチンを待機状態にし、チャネルの待機キューに`sudog`として追加します。チャネル操作が完了すると、待機していたゴルーチンがキューから取り除かれ、実行可能状態に戻されます。

## 技術的詳細

このコミットの主要な変更点は、Goランタイムにおけるチャネルの送受信待機キュー（`waitq`）の実装を、単方向連結リストから双方向連結リストへ変更したことです。

### 変更前（単方向連結リスト）
以前の`waitq`は、`first`と`last`という2つのポインタを持つ単方向連結リストでした。`sudog`構造体には`next`ポインタのみが存在し、次の`sudog`を指していました。

問題は、キューから特定の`sudog`を削除する際に発生しました。例えば、`select`文で複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を削除する必要がある場合です。単方向リストでは、削除したい`sudog`の前の`sudog`を見つけるために、リストの先頭から順に`next`ポインタを辿る必要がありました。この探索がO(n)の計算量となり、キューが長くなるほど非効率になります。多数のゴルーチンが頻繁にチャネル操作を行うような状況では、このO(n)の削除操作が繰り返され、全体としてO(n^2)の性能劣化を引き起こしていました。

### 変更後（双方向連結リスト）
このコミットでは、`sudog`構造体に新たに`prev`ポインタが追加され、`next`ポインタと合わせて双方向連結リストを形成するように変更されました。

- `sudog`構造体:
    - `next`: 次の`sudog`へのポインタ
    - `prev`: 前の`sudog`へのポインタ

これにより、キュー内の任意の`sudog`が与えられた場合、その`sudog`の`prev`ポインタと`next`ポインタを直接操作することで、O(1)の定数時間でキューから削除することが可能になりました。

### `waitq`の操作変更
`waitq`構造体は、`first`（キューの先頭）と`last`（キューの末尾）のポインタを保持します。

- **`enqueue` (キューへの追加)**:
    - 新しい`sudog`をキューの末尾に追加します。
    - 新しい`sudog`の`prev`ポインタは現在の`last`を指し、現在の`last`の`next`ポインタは新しい`sudog`を指すように更新されます。
    - キューが空の場合、`first`と`last`の両方が新しい`sudog`を指します。

- **`dequeue` (キューからの削除 - 先頭)**:
    - キューの先頭の`sudog`を削除します。
    - `first`ポインタを、現在の`first`の`next`に更新します。
    - 新しい`first`の`prev`ポインタを`nil`に設定します。
    - キューが空になる場合、`first`と`last`の両方を`nil`に設定します。

- **`dequeueSudoG` (キューからの削除 - 任意)**:
    - 特定の`sudog`をキューから削除します。
    - 削除対象の`sudog`の`prev`と`next`ポインタを利用して、その前後の`sudog`のポインタを適切に更新します。
    - 削除対象がキューの先頭、末尾、または中間にあるかによって、`first`や`last`ポインタも更新されます。
    - この操作がO(1)で実行できるようになりました。

この変更により、特に`select`文などで複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を効率的に削除できるようになり、全体的なパフォーマンスが向上しました。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/chan.go` と `src/runtime/select.go` における`waitq`の操作ロジックの変更です。

### `src/runtime/chan.go` の変更点

#### `func (q *waitq) enqueue(sgp *sudog)`
この関数は、`sudog`を`waitq`の末尾に追加します。
- **変更前**: `q.last.next = sgp` のように、単方向リストとして`next`ポインタのみを更新していました。
- **変更後**:
    - `x := q.last`: 現在のキューの末尾を`x`に保持します。
    - `if x == nil`: キューが空の場合、`sgp`が最初の要素となるため、`sgp.prev`を`nil`にし、`q.first`と`q.last`の両方を`sgp`に設定します。
    - `else`: キューに既存の要素がある場合、`sgp.prev = x`で新しい要素の`prev`ポインタを現在の末尾に設定し、`x.next = sgp`で現在の末尾の`next`ポインタを新しい要素に設定します。最後に`q.last = sgp`でキューの末尾を更新します。
    これにより、`sgp`がキューの末尾に双方向でリンクされます。

#### `func (q *waitq) dequeue() *sudog`
この関数は、`waitq`の先頭から`sudog`を削除します。これは、チャネル操作が成功し、待機していたゴルーチンが解放される際に呼び出されます。
- **変更前**: `q.first = sgp.next` と`sgp.next = nil` で、単方向リストの先頭要素を削除していました。`q.last == sgp` のチェックで、最後の要素が削除された場合の`q.last`の更新も行っていました。
- **変更後**:
    - `y := sgp.next`: 削除される`sgp`の次の要素を`y`に保持します。
    - `if y == nil`: `sgp`がキューの唯一の要素、または最後の要素である場合、`q.first`と`q.last`を`nil`に設定してキューを空にします。
    - `else`: `sgp`の次に要素がある場合、`y.prev = nil`で新しい先頭要素の`prev`ポインタを`nil`に設定し、`q.first = y`でキューの先頭を`y`に更新します。`sgp.next = nil`は、`sgp`がキューから切り離されたことを示すために行われます。

### `src/runtime/select.go` の変更点

#### `func (q *waitq) dequeueSudoG(sgp *sudog)`
この関数は、`waitq`から特定の`sgp`（`sudog`）を削除します。これは、`select`文で複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を削除するために重要です。
- **変更前**: 単方向リストのため、`prevsgp`と`l`（ポインタへのポインタ）を使ってリストの先頭から`sgp`を探索し、見つかったらその前の要素の`next`ポインタを更新するというO(n)のロジックでした。
- **変更後**: 双方向リストの特性を活かし、O(1)で削除できるようになりました。
    - `x := sgp.prev` と `y := sgp.next`: 削除対象の`sgp`の前後の要素を取得します。
    - **`if x != nil` (sgpが先頭ではない場合)**:
        - `if y != nil` (sgpが中間にある場合): `x.next = y` と `y.prev = x` で、`sgp`の前後の要素を直接リンクし直します。`sgp.next = nil` と `sgp.prev = nil` で`sgp`をキューから完全に切り離します。
        - `else` (sgpが末尾にある場合): `x.next = nil` で`sgp`の前の要素の`next`を`nil`にし、`q.last = x`でキューの末尾を`x`に更新します。`sgp.prev = nil`で`sgp`を切り離します。
    - **`else if y != nil` (sgpが先頭にある場合)**:
        - `y.prev = nil`で`sgp`の次の要素の`prev`を`nil`にし、`q.first = y`でキューの先頭を`y`に更新します。`sgp.next = nil`で`sgp`を切り離します。
    - **`else` (x==y==nil)**: `sgp`がキューの唯一の要素であるか、既に削除されている場合です。`if q.first == sgp`で`sgp`が実際にキューの先頭であるかを確認し、そうであれば`q.first`と`q.last`を`nil`に設定してキューを空にします。

これらの変更により、チャネルの待機キューからの`sudog`の削除が劇的に効率化され、特に多数のゴルーチンがチャネルを競合するシナリオでのパフォーマンスが大幅に向上しました。

## 変更の背景

このコミットは、Goランタイムにおけるチャネルの送受信キューのパフォーマンス問題を解決するために導入されました。以前の実装では、チャネルの待機キュー（`waitq`）が単方向連結リストで管理されており、特に多数のゴルーチンが同じチャネルに対して送受信を試みる「人気のあるチャネル（popular channels）」の場合に、キューからの要素削除（`dequeue`）が非効率になるという問題がありました。

具体的には、単方向連結リストから任意の要素を削除する場合、その要素の前の要素（`prev`）を見つけるためにリストの先頭から探索する必要がありました。これにより、最悪の場合、削除操作の計算量がO(n)となり、多数の操作が連続して行われると全体としてO(n^2)のパフォーマンス劣化を引き起こす可能性がありました。

このコミットでは、チャネルの送受信キューを双方向連結リストに変更することで、このO(n^2)のパフォーマンス問題を回避し、キューからの要素削除をO(1)の定数時間で行えるように改善しました。ベンチマーク結果（`BenchmarkChanPopular`）が示すように、この変更によりパフォーマンスが大幅に向上し、実行時間が約75%削減されました。

## 前提知識の解説

### Goのチャネル (Channels in Go)
Go言語におけるチャネルは、ゴルーチン間で値を送受信するための主要な通信メカニズムです。チャネルは型付けされており、特定の型の値のみを送受信できます。チャネルは、ゴルーチン間の同期と通信を安全かつ効率的に行うための強力なプリミティブです。

チャネルの操作には主に以下の2つがあります。
- **送信 (Send)**: `ch <- value` の形式でチャネルに値を送信します。
- **受信 (Receive)**: `value := <-ch` または `<-ch` の形式でチャネルから値を受信します。

チャネルは、バッファリングされているか否かによって動作が異なります。
- **バッファなしチャネル**: 送信操作は受信操作が準備できるまでブロックし、受信操作は送信操作が準備できるまでブロックします。これにより、ゴルーチン間の同期が保証されます。
- **バッファありチャネル**: バッファが満杯になるまで送信操作はブロックせず、バッファが空になるまで受信操作はブロックしません。

### `sudog` 構造体
Goランタイムにおいて、チャネル操作（送信または受信）によってブロックされたゴルーチンは、`sudog`（"scheduler goroutine" の略）という内部構造体として表現され、チャネルの待機キューに追加されます。`sudog` は、ブロックされたゴルーチンに関する情報（どのゴルーチンか、どのチャネルで待機しているか、送受信する値のアドレスなど）を保持します。

### 連結リスト (Linked List)
連結リストは、データ要素（ノード）が順序付けられて格納されるデータ構造です。各ノードはデータと、次のノードへの参照（ポインタ）を保持します。

- **単方向連結リスト (Singly Linked List)**: 各ノードが次のノードへのポインタのみを持つリストです。リストの先頭から順にしか辿ることができません。特定のノードを削除する場合、そのノードの前のノードを見つけるために先頭から探索する必要があり、O(n)の計算量がかかります。

- **双方向連結リスト (Doubly Linked List)**: 各ノードが次のノードへのポインタと、前のノードへのポインタの両方を持つリストです。これにより、リストを前方にも後方にも辿ることができます。特定のノードを削除する場合、そのノードの前後へのポインタを直接操作できるため、O(1)の定数時間で削除が可能です。

### O(n^2) の性能問題
計算量表記O(n)やO(n^2)は、アルゴリズムの実行時間が入力サイズnに対してどのように増加するかを示します。
- **O(n)**: 線形時間。入力サイズnに比例して実行時間が増加します。
- **O(n^2)**: 二次時間。入力サイズnの二乗に比例して実行時間が増加します。これは、ネストされたループなどでよく見られ、nが大きくなると実行時間が急激に増加するため、大規模なデータセットでは非効率的です。

このコミットの文脈では、単方向連結リストからの要素削除がO(n)であり、これが多数回繰り返されることで全体としてO(n^2)の性能問題を引き起こしていました。

### Goのスケジューラとチャネルの内部動作
Goランタイムには、ゴルーチンを効率的にスケジューリングするスケジューラがあります。チャネル操作は、このスケジューラと密接に連携しています。ゴルーチンがチャネル操作でブロックされると、スケジューラはそのゴルーチンを待機状態にし、チャネルの待機キューに`sudog`として追加します。チャネル操作が完了すると、待機していたゴルーチンがキューから取り除かれ、実行可能状態に戻されます。

## 技術的詳細

このコミットの主要な変更点は、Goランタイムにおけるチャネルの送受信待機キュー（`waitq`）の実装を、単方向連結リストから双方向連結リストへ変更したことです。

### 変更前（単方向連結リスト）
以前の`waitq`は、`first`と`last`という2つのポインタを持つ単方向連結リストでした。`sudog`構造体には`next`ポインタのみが存在し、次の`sudog`を指していました。

問題は、キューから特定の`sudog`を削除する際に発生しました。例えば、`select`文で複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を削除する必要がある場合です。単方向リストでは、削除したい`sudog`の前の`sudog`を見つけるために、リストの先頭から順に`next`ポインタを辿る必要がありました。この探索がO(n)の計算量となり、キューが長くなるほど非効率になります。多数のゴルーチンが頻繁にチャネル操作を行うような状況では、このO(n)の削除操作が繰り返され、全体としてO(n^2)の性能劣化を引き起こしていました。

### 変更後（双方向連結リスト）
このコミットでは、`sudog`構造体に新たに`prev`ポインタが追加され、`next`ポインタと合わせて双方向連結リストを形成するように変更されました。

- `sudog`構造体:
    - `next`: 次の`sudog`へのポインタ
    - `prev`: 前の`sudog`へのポインタ

これにより、キュー内の任意の`sudog`が与えられた場合、その`sudog`の`prev`ポインタと`next`ポインタを直接操作することで、O(1)の定数時間でキューから削除することが可能になりました。

### `waitq`の操作変更
`waitq`構造体は、`first`（キューの先頭）と`last`（キューの末尾）のポインタを保持します。

- **`enqueue` (キューへの追加)**:
    - 新しい`sudog`をキューの末尾に追加します。
    - 新しい`sudog`の`prev`ポインタは現在の`last`を指し、現在の`last`の`next`ポインタは新しい`sudog`を指すように更新されます。
    - キューが空の場合、`first`と`last`の両方が新しい`sudog`を指します。

- **`dequeue` (キューからの削除 - 先頭)**:
    - キューの先頭の`sudog`を削除します。
    - `first`ポインタを、現在の`first`の`next`に更新します。
    - 新しい`first`の`prev`ポインタを`nil`に設定します。
    - キューが空になる場合、`first`と`last`の両方を`nil`に設定します。

- **`dequeueSudoG` (キューからの削除 - 任意)**:
    - 特定の`sudog`をキューから削除します。
    - 削除対象の`sudog`の`prev`と`next`ポインタを利用して、その前後の`sudog`のポインタを適切に更新します。
    - 削除対象がキューの先頭、末尾、または中間にあるかによって、`first`や`last`ポインタも更新されます。
    - この操作がO(1)で実行できるようになりました。

この変更により、特に`select`文などで複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を効率的に削除できるようになり、全体的なパフォーマンスが向上しました。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/chan.go` と `src/runtime/select.go` における`waitq`の操作ロジックの変更です。

### `src/runtime/chan.go` の変更点

#### `func (q *waitq) enqueue(sgp *sudog)`
この関数は、`sudog`を`waitq`の末尾に追加します。
- **変更前**: `q.last.next = sgp` のように、単方向リストとして`next`ポインタのみを更新していました。
- **変更後**:
    - `x := q.last`: 現在のキューの末尾を`x`に保持します。
    - `if x == nil`: キューが空の場合、`sgp`が最初の要素となるため、`sgp.prev`を`nil`にし、`q.first`と`q.last`の両方を`sgp`に設定します。
    - `else`: キューに既存の要素がある場合、`sgp.prev = x`で新しい要素の`prev`ポインタを現在の末尾に設定し、`x.next = sgp`で現在の末尾の`next`ポインタを新しい要素に設定します。最後に`q.last = sgp`でキューの末尾を更新します。
これにより、`sgp`がキューの末尾に双方向でリンクされます。

#### `func (q *waitq) dequeue() *sudog`
この関数は、`waitq`の先頭から`sudog`を削除します。これは、チャネル操作が成功し、待機していたゴルーチンが解放される際に呼び出されます。
- **変更前**: `q.first = sgp.next` と`sgp.next = nil` で、単方向リストの先頭要素を削除していました。`q.last == sgp` のチェックで、最後の要素が削除された場合の`q.last`の更新も行っていました。
- **変更後**:
    - `y := sgp.next`: 削除される`sgp`の次の要素を`y`に保持します。
    - `if y == nil`: `sgp`がキューの唯一の要素、または最後の要素である場合、`q.first`と`q.last`を`nil`に設定してキューを空にします。
    - `else`: `sgp`の次に要素がある場合、`y.prev = nil`で新しい先頭要素の`prev`ポインタを`nil`に設定し、`q.first = y`でキューの先頭を`y`に更新します。`sgp.next = nil`は、`sgp`がキューから切り離されたことを示すために行われます。

### `src/runtime/select.go` の変更点

#### `func (q *waitq) dequeueSudoG(sgp *sudog)`
この関数は、`waitq`から特定の`sgp`（`sudog`）を削除します。これは、`select`文で複数のチャネルを待機しているゴルーチンが、いずれかのチャネル操作が完了した際に、他のチャネルの待機キューから自身の`sudog`を削除するために重要です。
- **変更前**: 単方向リストのため、`prevsgp`と`l`（ポインタへのポインタ）を使ってリストの先頭から`sgp`を探索し、見つかったらその前の要素の`next`ポインタを更新するというO(n)のロジックでした。
- **変更後**: 双方向リストの特性を活かし、O(1)で削除できるようになりました。
    - `x := sgp.prev` と `y := sgp.next`: 削除対象の`sgp`の前後の要素を取得します。
    - **`if x != nil` (sgpが先頭ではない場合)**:
        - `if y != nil` (sgpが中間にある場合): `x.next = y` と `y.prev = x` で、`sgp`の前後の要素を直接リンクし直します。`sgp.next = nil` と `sgp.prev = nil` で`sgp`をキューから完全に切り離します。
        - `else` (sgpが末尾にある場合): `x.next = nil` で`sgp`の前の要素の`next`を`nil`にし、`q.last = x`でキューの末尾を`x`に更新します。`sgp.prev = nil`で`sgp`を切り離します。
    - **`else if y != nil` (sgpが先頭にある場合)**:
        - `y.prev = nil`で`sgp`の次の要素の`prev`を`nil`にし、`q.first = y`でキューの先頭を`y`に更新します。`sgp.next = nil`で`sgp`を切り離します。
    - **`else` (x==y==nil)**: `sgp`がキューの唯一の要素であるか、既に削除されている場合です。`if q.first == sgp`で`sgp`が実際にキューの先頭であるかを確認し、そうであれば`q.first`と`q.last`を`nil`に設定してキューを空にします。

これらの変更により、チャネルの待機キューからの`sudog`の削除が劇的に効率化され、特に多数のゴルーチンがチャネルを競合するシナリオでのパフォーマンスが大幅に向上しました。

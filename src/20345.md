## 元コミット内容

このコミットは、Goコンパイラの`cmd/gc`部分における`runtime`パッケージの`print(hex(x))`関数のバグを修正します。元々の実装では、`hex(x)`が別のパッケージの呼び出しサイトでインライン化された「自明な関数」に対してのみ正しく機能していました。この修正は、インライン化されない関数に対しても`hex(x)`が正しく動作するように拡張するものです。

## 変更の背景

Go言語のコンパイラ`cmd/gc`は、プログラムのコンパイル時に様々な最適化を行います。その一つに「インライン化」があります。インライン化とは、関数呼び出しのオーバーヘッドを削減するために、呼び出される関数の本体を呼び出し元のコードに直接埋め込む最適化手法です。

`runtime`パッケージはGoプログラムの実行環境を提供する非常に低レベルなコードを含んでおり、デバッグや内部処理のために`print`関数群が用意されています。`print(hex(x))`はその一つで、数値を16進数形式で出力するために使用されます。

このコミット以前の`print(hex(x))`の実装には、特定の条件下で問題がありました。具体的には、`hex(x)`が使用される関数がコンパイラによってインライン化された場合にのみ正しく動作し、インライン化されなかった場合には期待通りに機能しないというバグが存在していました。コミットメッセージによると、これは元の開発者がインライン化されるケースのみを想定したテストを作成したためと考えられます。

この問題は、Goランタイムのデバッグや内部動作の解析において、`print(hex(x))`が常に信頼できる出力を行うことを妨げていました。そのため、インライン化の有無にかかわらず、`hex(x)`が常に正しく動作するように修正する必要がありました。

## 前提知識の解説

### Goコンパイラ (`cmd/gc`)

`cmd/gc`は、Go言語の公式かつ標準のコンパイラです。Goのソースコードを機械語に変換し、実行可能なバイナリを生成します。`go build`コマンドによって内部的に呼び出されます。`cmd/gc`は、字句解析、構文解析、意味解析、最適化、コード生成、リンクといった複数の段階を経てコンパイルを行います。

### Goランタイム (`runtime`パッケージ)

Goランタイムは、Goプログラムの実行を支える基盤となるコンポーネントです。ガベージコレクション、ゴルーチンのスケジューリング、メモリ管理、スタック管理など、Goの並行処理モデルやメモリ安全性を実現するための低レベルな機能を提供します。`runtime`パッケージ自体もGo、C、アセンブリ言語で記述されており、Goプログラムに静的にリンクされます。

### 関数インライン化 (Function Inlining)

関数インライン化は、コンパイラ最適化の一種です。関数呼び出しの際に発生するオーバーヘッド（スタックフレームの作成、引数の渡し、レジスタの保存・復元など）を削減するために、呼び出される関数のコードを呼び出し元の場所に直接展開します。

**利点:**
*   **パフォーマンス向上:** 関数呼び出しのオーバーヘッドがなくなるため、特に小さな関数や頻繁に呼び出される関数で効果的です。
*   **最適化機会の増加:** コンパイラが呼び出し元と呼び出し先のコードをまとめて最適化できるようになり、より高度な最適化（定数伝播、デッドコード削除など）が可能になります。
*   **キャッシュ効率の向上:** コードの局所性が高まり、命令キャッシュの利用効率が向上する可能性があります。

**欠点:**
*   **バイナリサイズの増加:** 同じ関数が複数回インライン化されると、コードが重複し、最終的なバイナリサイズが増加する可能性があります。
*   **コンパイル時間の増加:** コード量が増えるため、コンパイル時間が長くなることがあります。

Goコンパイラは、関数のサイズや複雑さに基づいて自動的にインライン化の判断を行います。開発者が直接インライン化を制御するキーワードはありませんが、`//go:noinline`ディレクティブを使ってインライン化を抑制することは可能です。

### `print(hex(x))`

これはGoランタイム内部で使用されるデバッグ用の関数であり、Goの標準ライブラリ（`fmt`パッケージなど）で提供される`fmt.Printf("%x", x)`とは異なります。`print(hex(x))`は、Goランタイムの低レベルな部分で、特定の変数の値を16進数形式で出力するために使われます。

### `t->sym->pkg == runtimepkg` と `compiling_runtime`

*   `t->sym->pkg == runtimepkg`: これは、現在処理しているシンボル（`t->sym`）が`runtime`パッケージに属しているかどうかをチェックする条件です。`runtimepkg`は、Goコンパイラ内部で`runtime`パッケージを表すシンボルです。
*   `compiling_runtime`: これは、Goコンパイラが現在`runtime`パッケージ自体をコンパイルしているかどうかを示すフラグです。Goのビルドプロセスでは、まず`runtime`パッケージがコンパイルされ、その後に他のパッケージがコンパイルされます。このフラグは、コンパイラが自身のブートストラッププロセスの一部として`runtime`パッケージを扱っていることを示します。

これらの条件は、`print(hex(x))`のような特殊なランタイム関数が、`runtime`パッケージ内での使用、または`runtime`パッケージのコンパイル中にのみ特定の挙動を示すべきであることを保証するために使用されます。

## 技術的詳細

このコミットの変更は、Goコンパイラの`src/cmd/gc/walk.c`ファイル内の`walkprint`関数にあります。`walkprint`関数は、GoのAST（抽象構文木）を走査し、`print`組み込み関数（Goランタイム内部の`print`関数）の呼び出しを処理する部分です。

変更前のコードは以下のようになっていました。

```c
if(t->sym->pkg == runtimepkg && strcmp(t->sym->name, "hex") == 0)
    on = syslook("printhex", 0);
```

このコードは、`print`関数の引数が`runtime`パッケージの`hex`シンボルである場合に、内部的な`printhex`関数を呼び出すように設定していました。しかし、この条件だけでは不十分でした。

問題は、`hex`関数がインライン化された場合、その呼び出しは`runtimepkg`のコンテキストで処理されるため、この条件が満たされます。しかし、`hex`関数がインライン化されなかった場合、または`runtime`パッケージ外のコードから`hex`が参照された場合（ただし、`hex`は通常、ランタイム内部でのみ使用されるべきですが、コンパイラの処理フローによってはこのような状況が発生し得ます）、`t->sym->pkg`が`runtimepkg`と一致しない可能性がありました。

このコミットでは、条件に`compiling_runtime`フラグを追加することで、この問題を解決しています。

```c
if((t->sym->pkg == runtimepkg || compiling_runtime) && strcmp(t->sym->name, "hex") == 0)
    on = syslook("printhex", 0);
```

新しい条件は次のいずれかが真である場合に`printhex`を呼び出すようにします。
1.  `t->sym->pkg == runtimepkg`: 現在処理しているシンボルが`runtime`パッケージに属している場合。
2.  `compiling_runtime`: コンパイラが現在`runtime`パッケージ自体をコンパイルしている最中である場合。

この変更により、`hex`関数がインライン化されているかどうかにかかわらず、また`runtime`パッケージのコンパイル中であるかどうかにかかわらず、`print(hex(x))`が常に`printhex`に正しくマッピングされるようになります。これにより、`print(hex(x))`の挙動が一貫し、デバッグ時の信頼性が向上します。

## コアとなるコードの解説

変更された行は、Goコンパイラの`cmd/gc`が`print`組み込み関数（Goランタイム内部の`print`関数）の呼び出しを処理するロジックの一部です。

*   `walkprint(Node *nn, NodeList **init, int defer)`: この関数は、Goの抽象構文木（AST）のノード`nn`を走査し、`print`関数の呼び出しを処理します。
*   `et == TUINT64`: これは、`print`関数の引数の型が`uint64`であることをチェックしています。`hex`関数は通常、`uint64`型の値を処理するため、この条件は適切です。
*   `t->sym->pkg == runtimepkg`: `t`は`print`関数の引数に関連する型情報を持つノードであり、`t->sym`はそのシンボルです。この部分は、引数のシンボルが`runtime`パッケージに属しているかどうかを確認します。
*   `strcmp(t->sym->name, "hex") == 0`: これは、引数のシンボル名が文字列`"hex"`と一致するかどうかをチェックします。
*   `compiling_runtime`: このグローバルフラグは、コンパイラが現在`runtime`パッケージ自体をコンパイルしている最中である場合に`true`になります。

変更前は、`hex`関数が`runtimepkg`に属している場合にのみ`printhex`を呼び出すようにしていました。しかし、`hex`関数がインライン化されなかった場合、またはコンパイラが`runtime`パッケージをコンパイルしている特殊な状況下では、`t->sym->pkg`が`runtimepkg`と一致しないことがありました。

変更後は、`t->sym->pkg == runtimepkg` **または** `compiling_runtime`のいずれかが真であれば、`printhex`を呼び出すように修正されました。これにより、`hex`関数がインライン化されているかどうかにかかわらず、また`runtime`パッケージのコンパイル中であるかどうかにかかわらず、`print(hex(x))`が常に`printhex`に正しくマッピングされるようになり、`print(hex(x))`の挙動の信頼性が向上しました。

`on = syslook("printhex", 0);` は、Goコンパイラが内部的に`printhex`という名前のシステム関数（ランタイム関数）への参照を取得し、それを`on`変数に割り当てています。これにより、コンパイルされたコード内で`print(hex(x))`が呼び出された際に、実際の`printhex`ランタイム関数が実行されるようになります。

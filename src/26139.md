## 変更の背景

Go と C 言語の相互運用を可能にする `cgo` は非常に強力な機能ですが、Go のガベージコレクタと C の手動メモリ管理の間の整合性を保つためには、ポインタの受け渡しに関して厳格なルールが存在します。これらのルールに違反すると、メモリ破損、クラッシュ、未定義の動作を引き起こす可能性があります。

特に、Go の `chan`、`map`、`func`、`slice` といった型は、内部にGoのポインタ（ヒープ上のデータへの参照）を暗黙的に含んでいます。これらの型を直接 C コードに渡すと、Go のガベージコレクタがそのポインタが C コードによって参照されていることを認識できず、参照先のメモリを移動または解放してしまう可能性があります。これにより、C コードが不正なメモリにアクセスし、深刻な問題が発生します。

このコミットは、このような潜在的な問題を開発段階で早期に発見するために、Go の静的解析ツールである `cmd/vet` に新しいチェック (`-cgocall` フラグ) を追加するものです。これにより、開発者が `cgo` のポインタ渡しルールに違反するコードを記述するのを防ぎ、より堅牢な Go プログラムの作成を支援します。関連するIssueは #12416 です。

## 前提知識の解説

### cgo

`cgo` は Go プログラムから C 言語のコードを呼び出すためのメカニズムです。Go のコード内に `import "C"` を記述することで、C の関数や変数、型を Go から利用できるようになります。これにより、既存の C ライブラリを Go プロジェクトに統合したり、パフォーマンスが重要な部分を C で記述したりすることが可能になります。

### Go のガベージコレクタとポインタ

Go はガベージコレクタ (GC) を備えており、メモリ管理の多くを自動で行います。Go のポインタは、GC が管理するヒープ上のメモリ領域を指します。GC は、不要になったメモリを自動的に解放するために、ポインタの参照関係を追跡し、必要に応じてメモリを移動（コンパクション）することがあります。

### Go ポインタと C ポインタの区別

*   **Go ポインタ**: Go のランタイムによって管理されるメモリを指します。GC の対象となります。
*   **C ポインタ**: C のランタイム（または `C.malloc` など）によって割り当てられたメモリを指します。GC の対象外です。

### cgo におけるポインタ渡しの基本ルール

Go と C の間でポインタを渡す際には、以下の基本的なルールを厳守する必要があります。

1.  **Go ポインタを C に渡す場合**:
    *   Go のポインタを C に渡すことは可能ですが、そのポインタが指す Go のメモリ領域には、**他の Go ポインタを含んでいてはなりません**。これは、`chan`, `map`, `func`, `slice` といった型が暗黙的に Go ポインタを含むため、これらの型を直接 C に渡すことが禁止される理由です。
    *   C コードは、Go ポインタとその指すメモリを、**呼び出し中のみ**使用できます。C コードは、呼び出しが返った後に Go ポインタのコピーを保持してはなりません（`runtime.Pinner` を使用して明示的にメモリをピン留めする場合を除く）。
    *   C コードは、C によって割り当てられたメモリに Go ポインタを格納してはなりません。
    *   Go のスタックポインタを C コードに渡すことはできません。
    *   Go ポインタが C 関数に渡される際、Go ランタイムはそのメモリを C 呼び出しの間「ピン留め」し、GC が移動または回収するのを防ぎます。

2.  **C ポインタを Go に渡す場合**:
    *   Go コードは C ポインタを使用できます。
    *   C で割り当てられたメモリ（例: `C.malloc`）の解放責任は C 側にあります。Go がそのポインタのコピーを保持している間に C 側が解放すると、プログラムは失敗します。
    *   Go コードは、C ポインタが指すメモリに `nil` または C ポインタを書き込むことはできますが、ピン留めされていないメモリへの Go ポインタを格納することはできません。

これらのルールは、Go の GC と C のメモリ管理の間の衝突を防ぎ、メモリの安全性を確保するために不可欠です。

## 技術的詳細

このコミットで追加された `cmd/vet` のチェックは、`cgo` 呼び出しの引数を静的に解析し、Go のポインタ渡しルールに違反している可能性のあるパターンを検出します。

新しいチェックは、`src/cmd/vet/cgo.go` に実装されており、`checkCgoCall` 関数がその中心的なロジックを担います。この関数は、抽象構文木 (AST) を走査し、`C` パッケージの関数呼び出し (`C.f(...)` のような形式) を探します。

`checkCgoCall` は、`C` 関数に渡される各引数に対して以下の処理を行います。

1.  **基本型の特定**: `cgoBaseType` 関数を使用して、`unsafe.Pointer` を介した型変換を遡り、引数の元の Go の型（基本型）を特定しようとします。これは、`unsafe.Pointer(x)` や `*(*unsafe.Pointer)(unsafe.Pointer(&x))` のような一般的な変換パターンを認識し、実際の Go の型を抽出します。
2.  **ポインタ安全性のチェック**: 特定された基本型が `typeOKForCgoCall` 関数によって、Cgo のポインタ渡しルールに適合しているかどうかがチェックされます。
3.  **アドレス渡しのチェック**: 引数がアドレス (`&x`) として渡されている場合、その元の型 (`x`) も同様に `typeOKForCgoCall` でチェックされます。

`typeOKForCgoCall` 関数は、Go の型が組み込みポインタを持つかどうかを再帰的に判断します。具体的には、`chan`, `map`, `func` (Signature), `slice` 型は組み込みポインタを持つため `false` を返します。ポインタ型 (`*T`) や配列型 (`[N]T`)、構造体型 (`struct{...}`) の場合は、その要素型やフィールド型に対して再帰的に `typeOKForCgoCall` を呼び出し、いずれかの要素やフィールドが組み込みポインタを持つ場合に `false` を返します。

この静的解析により、Go のガベージコレクタが管理するメモリへの参照を C コードが不適切に保持する可能性のあるコードパターンを、コンパイル前に警告として提示することができます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/vet/cgo.go` (新規追加)**:
    *   `checkCgoCall` 関数: `C` パッケージの関数呼び出しを検出し、その引数が `cgo` のポインタ渡しルールに違反していないかをチェックします。
    *   `cgoBaseType` 関数: `unsafe.Pointer` を介した型変換を遡り、引数の元の Go の型を特定します。
    *   `typeOKForCgoCall` 関数: 指定された Go の型が `cgo` 呼び出しに安全に渡せる型であるかを判断します。`chan`, `map`, `func`, `slice` 型、およびそれらを内包する複合型を検出します。

2.  **`src/cmd/vet/doc.go` (変更)**:
    *   `cmd/vet` のドキュメントに、新しいチェックである「Invalid uses of cgo」と、それを有効にするフラグ `-cgocall` が追加されました。

3.  **`src/cmd/vet/testdata/cgo.go` (新規追加)**:
    *   `cgo` チェックのテストケースが含まれています。`chan`, `map`, `func`, `slice`、およびそれらを含む配列や構造体が `C.f` に渡された場合に `ERROR "embedded pointer"` が報告されることを確認します。
    *   安全なポインタ渡し（例: `int` 型やスライスの要素のアドレス渡し）のケースも含まれており、これらがエラーにならないことを検証します。

## コアとなるコードの解説

### `src/cmd/vet/cgo.go`

このファイルは、`cgo` 呼び出しにおける無効なポインタ渡しを検出するためのロジックを実装しています。

#### `checkCgoCall(f *File, node ast.Node)`

この関数は、`cmd/vet` の AST ウォーカーによって呼び出され、`ast.CallExpr` (関数呼び出し) ノードを処理します。

1.  **`C` パッケージの呼び出しを特定**:
    ```go
    sel, ok := x.Fun.(*ast.SelectorExpr)
    if !ok {
        return
    }
    id, ok := sel.X.(*ast.Ident)
    if !ok || id.Name != "C" { // `C.f` のような形式をチェック
        return
    }
    ```
    呼び出しが `C` パッケージの関数 (`C.f` など) であることを確認します。

2.  **引数のチェック**:
    ```go
    for _, arg := range x.Args {
        if !typeOKForCgoCall(cgoBaseType(f, arg)) {
            f.Badf(arg.Pos(), "possibly passing Go type with embedded pointer to C")
        }
        // ... (アドレス渡しのチェック)
    }
    ```
    各引数に対して `cgoBaseType` で元の型を特定し、`typeOKForCgoCall` で安全性をチェックします。違反している場合は警告 (`f.Badf`) を出力します。

3.  **アドレス渡しの特殊処理**:
    ```go
    if conv, ok := arg.(*ast.CallExpr); ok && len(conv.Args) == 1 && f.hasBasicType(conv.Fun, types.UnsafePointer) {
        arg = conv.Args[0]
    }
    if u, ok := arg.(*ast.UnaryExpr); ok && u.Op == token.AND { // `&x` の形式をチェック
        if !typeOKForCgoCall(cgoBaseType(f, u.X)) {
            f.Badf(arg.Pos(), "possibly passing Go type with embedded pointer to C")
        }
    }
    ```
    `unsafe.Pointer(&x)` や `&x` のようにアドレスが渡されている場合、その元の変数 `x` の型もチェック対象とします。

#### `cgoBaseType(f *File, arg ast.Expr) types.Type`

この関数は、`unsafe.Pointer` を介した複雑な型変換を「剥がし」、引数の最も基本的な Go の型を特定しようとします。

*   `unsafe.Pointer(x)` のような直接的な変換や、`*(*unsafe.Pointer)(unsafe.Pointer(&x))` のような多重変換パターンを認識し、最終的に `x` の型を返します。
*   これにより、開発者が `unsafe.Pointer` を使って型システムを迂回しようとした場合でも、`vet` が元の Go の型を正確に分析できるようになります。

#### `typeOKForCgoCall(t types.Type) bool`

この関数は、与えられた Go の型 `t` が `cgo` 呼び出しに安全に渡せるかどうかを判断します。

*   **基本ケース**:
    ```go
    switch t := t.Underlying().(type) {
    case *types.Chan, *types.Map, *types.Signature, *types.Slice:
        return false // これらの型は組み込みポインタを持つため安全ではない
    ```
    `chan`, `map`, `func` (Signature), `slice` 型は、それ自体が Go のポインタを内包しているため、`false` を返します。

*   **再帰ケース**:
    ```go
    case *types.Pointer:
        return typeOKForCgoCall(t.Elem()) // ポインタの指す要素型をチェック
    case *types.Array:
        return typeOKForCgoCall(t.Elem()) // 配列の要素型をチェック
    case *types.Struct:
        for i := 0; i < t.NumFields(); i++ {
            if !typeOKForCgoCall(t.Field(i).Type()) {
                return false // 構造体のいずれかのフィールドが安全でない場合、構造体全体も安全ではない
            }
        }
    ```
    ポインタ、配列、構造体のような複合型の場合、その要素型やフィールド型に対して再帰的に `typeOKForCgoCall` を呼び出し、内部に安全でない型が含まれていないかをチェックします。

*   **その他**: 上記以外の型（`int`, `string`, `bool` など）は、組み込みポインタを持たないため `true` を返します。

### `src/cmd/vet/testdata/cgo.go`

このテストファイルは、`cgo` チェックが意図通りに機能することを確認します。

*   `chan`, `map`, `func`, `slice` 型の変数、およびそれらを含む配列や構造体を `C.f` に渡す不正なパターンが記述されており、それぞれ `ERROR "embedded pointer"` というコメントが付加されています。これは `vet` がこれらの行でエラーを報告することを期待していることを示します。
*   `int` 型やスライスの特定の要素のアドレスなど、安全に渡せるパターンも含まれており、これらにはエラーコメントが付加されていません。これにより、`vet` が誤って警告を発しないことも確認されます。

これらの変更により、Go の開発者は `cgo` を使用する際に、より安全で堅牢なコードを記述するための強力なツールを手に入れることになります。

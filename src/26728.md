## 変更の背景

このコミットは、Go 1.6で報告されたIssue #14377を修正するものです。この問題は、`sort.Interface`を実装する型が提供する`Less`メソッドが非決定的な結果を返す場合に、Goの標準ソートアルゴリズム（特にクイックソート）がパニックを起こすというものでした。具体的には、「runtime error: index out of range」というエラーが発生し、プログラムがクラッシュしていました。

ソートアルゴリズムは通常、比較関数（Goでは`Less`メソッド）が厳密な弱順序付けの条件（反射律、反対称律、推移律）を満たすことを前提としています。しかし、現実には、ユーザーが提供する`Less`関数がこれらの条件を破り、特に非決定的な振る舞いをすることがあります。例えば、乱数に基づいて比較結果を返すような実装です。

Go 1.6におけるソートアルゴリズムの内部的な改善（おそらくパフォーマンス最適化のため）が、この非決定的な`Less`関数に対する既存の脆弱性を顕在化させたと考えられます。クイックソートのパーティション分割ロジックでは、ピボットを基準に要素を左右に振り分ける際に、配列のインデックスを厳密に管理する必要があります。非決定的な`Less`関数が原因で、このインデックス管理が破綻し、配列の境界外にアクセスしようとしてパニックが発生していました。

この修正の目的は、`Less`関数が非決定的な場合でも、ソートアルゴリズムがパニックを起こさずに正常に終了するように、クイックソートの内部ループ条件をより堅牢にすることです。

## 前提知識の解説

### Goの`sort.Interface`

Go言語でカスタム型をソート可能にするためには、その型が`sort.Interface`インターフェースを実装する必要があります。このインターフェースは以下の3つのメソッドを定義しています。

1.  `Len() int`: ソート対象の要素数を返します。
2.  `Less(i, j int) bool`: インデックス`i`の要素がインデックス`j`の要素よりも小さい場合に`true`を返します。このメソッドは、ソートの順序を決定する比較ロジックを提供します。
3.  `Swap(i, j int)`: インデックス`i`と`j`の要素を入れ替えます。

Goの標準ライブラリ`sort`パッケージの`Sort`関数は、この`sort.Interface`を実装した任意の型を受け取り、ソートを実行します。

### クイックソート (Quicksort)

クイックソートは、分割統治法に基づく効率的なソートアルゴリズムです。基本的な手順は以下の通りです。

1.  **ピボットの選択**: 配列の中から1つの要素を「ピボット」として選びます。
2.  **パーティション分割**: ピボットを基準に配列を2つの部分に分割します。ピボットより小さい要素は左側の部分に、大きい要素は右側の部分に移動させます。ピボットは最終的な位置に配置されます。
3.  **再帰**: 左右に分割された部分配列に対して、再帰的にクイックソートを適用します。

このアルゴリズムの効率は、ピボットの選択とパーティション分割の効率に大きく依存します。特に、パーティション分割のループ条件は、配列の境界を正確に管理するために非常に重要です。

### 非決定的な`Less`関数

通常、`Less(i, j)`は、同じ`i`と`j`の組み合わせに対して常に同じブール値を返す「決定的な」関数であることが期待されます。しかし、非決定的な`Less`関数とは、同じ`i`と`j`の組み合わせであっても、呼び出しごとに異なる結果（`true`または`false`）を返す可能性がある関数を指します。

例えば、`Less`関数内で乱数を使用したり、外部の状態に依存したりする場合に非決定性が発生します。このような非決定的な比較関数は、ソートアルゴリズムの基本的な前提（比較の一貫性）を破るため、以下のような問題を引き起こす可能性があります。

*   **不正なソート結果**: 要素が正しく順序付けられない。
*   **無限ループ**: ソートアルゴリズムが終了条件に到達できなくなる。
*   **ランタイムパニック**: 配列のインデックスが不正になり、範囲外アクセスが発生する。

Goの`sort`パッケージは、`Less`関数が厳密な弱順序付けを満たすことを期待していますが、このコミットは、その期待が破られた場合でもパニックを回避するための堅牢性向上を目的としています。

### Go 1.6でのソートアルゴリズムの変更

Go 1.6では、標準ライブラリのソートアルゴリズムにいくつかの改善が加えられました。これには、より効率的なソート戦略の導入や、特定のケースでのパフォーマンス最適化が含まれていました。これらの変更は全体的なパフォーマンス向上に寄与しましたが、同時に非決定的な`Less`関数に対する既存のクイックソート実装の脆弱性を露呈させる結果となりました。

## 技術的詳細

このコミットの核心は、`src/sort/sort.go`内の`doPivot`関数におけるループ条件の変更です。`doPivot`関数は、クイックソートのパーティション分割処理を担当しており、ピボットを基準に要素を左右に振り分けるための重要なロジックを含んでいます。

元のコードでは、ループ条件に`a != c`や`b != c`、`a != b`といった等価性チェックが使用されていました。これらの条件は、`Less`関数が決定論的である場合には問題なく機能します。しかし、`Less`関数が非決定的な場合、特定の状況下で`a`、`b`、`c`といったインデックスが期待通りに進行せず、ループが終了しないか、あるいは`c-1`のようなインデックスアクセスが配列の境界外を指す可能性がありました。

具体的には、`data.Less(pivot, c-1)`のような比較において、`c`が`lo`や`hi`の境界に近づき、`c-1`が有効なインデックス範囲外になる可能性がありました。非決定的な`Less`関数は、この境界条件のチェックを複雑にし、予期せぬインデックスの動きを引き起こすことがあります。

修正では、これらのループ条件が`a < c`、`b < c`、`a < b`といったより厳密な不等号チェックに変更されました。

*   `for ; a != c && data.Less(a, pivot); a++ {`
    が
    `for ; a < c && data.Less(a, pivot); a++ {`
    に変更。
*   `for ; b != c && !data.Less(pivot, b); b++ {`
    が
    `for ; b < c && !data.Less(pivot, b); b++ {`
    に変更。
*   `for ; b != c && data.Less(pivot, c-1); c-- {`
    が
    `for ; b < c && data.Less(pivot, c-1); c-- {`
    に変更。
*   `if b == c {`
    が
    `if b >= c {`
    に変更。
*   `for ; a != b && !data.Less(b-1, pivot); b-- {`
    が
    `for ; a < b && !data.Less(b-1, pivot); b-- {`
    に変更。
*   `for ; a != b && data.Less(a, pivot); a++ {`
    が
    `for ; a < b && data.Less(a, pivot); a++ {`
    に変更。
*   `if a == b {`
    が
    `if a >= b {`
    に変更。

これらの変更により、ループが実行される範囲がより明確に定義され、インデックス`a`, `b`, `c`が常に有効な配列の境界内に留まることが保証されます。特に、`c-1`のようなアクセスが行われる前に`c`が`b`や`a`と等しくなる状況を適切に処理できるようになり、インデックス範囲外パニックを防ぎます。

また、このコミットには、非決定的な`Less`関数を持つカスタム型をソートする際にパニックが発生しないことを検証するための新しいテストケース`TestNonDeterministicComparison`が`src/sort/sort_test.go`に追加されています。このテストは、`rand.Float32() < 0.5`という常にランダムな結果を返す`Less`メソッドを持つ`nonDeterministicTestingData`構造体を使用し、ソートが複数回実行されてもパニックが発生しないことを確認します。

## コアとなるコードの変更箇所

### `src/sort/sort.go`

`doPivot`関数内の複数の`for`ループおよび`if`条件文の比較演算子が変更されました。

*   `a != c` -> `a < c`
*   `b != c` -> `b < c`
*   `b == c` -> `b >= c`
*   `a != b` -> `a < b`
*   `a == b` -> `a >= b`

### `src/sort/sort_test.go`

`TestNonDeterministicComparison`という新しいテスト関数が追加されました。
このテストは、`nonDeterministicTestingData`というカスタム型を定義し、その`Less`メソッドが乱数に基づいて非決定的な結果を返すように実装されています。このデータ型に対して`sort.Sort`を複数回呼び出し、パニックが発生しないことを`defer`と`recover`を使って検証しています。

## コアとなるコードの解説

### `src/sort/sort.go` の変更

`doPivot`関数は、クイックソートのパーティション分割の中心的な部分です。この関数は、`lo`から`hi`までの範囲の要素を、`pivot`要素を基準に分割します。

変更されたループ条件の例を見てみましょう。

```go
// 変更前
for ; a != c && data.Less(a, pivot); a++ {
}
// 変更後
for ; a < c && data.Less(a, pivot); a++ {
}
```

元の`a != c`という条件は、「`a`と`c`が異なる限り」ループを続行するという意味です。しかし、`Less`関数が非決定的な場合、`a`が`c`に到達する前に、`data.Less(a, pivot)`が予期せぬ結果を返し、`a`のインクリメントが停止したり、`c`が予期せぬ動きをしたりする可能性があります。これにより、`c-1`のようなインデックスアクセスが不正になるリスクがありました。

新しい`a < c`という条件は、「`a`が`c`より小さい限り」ループを続行するという、より厳密な範囲チェックを導入しています。これにより、`a`が`c`に到達する前にループが確実に終了し、`c-1`のような操作が常に有効なインデックスに対して行われることが保証されます。同様の変更が他のループ条件にも適用され、非決定的な`Less`関数が引き起こす可能性のあるインデックス範囲外アクセスを防ぐように、パーティション分割ロジック全体の堅牢性が向上しています。

特に、`if b == c`が`if b >= c`に変更された箇所は、`b`が`c`を追い越すような状況（非決定的な比較によって発生しうる）でも、ループが安全に終了するための条件をカバーしています。

### `src/sort/sort_test.go` の追加テスト

`TestNonDeterministicComparison`テストは、このバグ修正の重要性を示すものです。

```go
type nonDeterministicTestingData struct {
	r *rand.Rand
}

func (t *nonDeterministicTestingData) Len() int {
	return 500
}
func (t *nonDeterministicTestingData) Less(i, j int) bool {
	if i < 0 || j < 0 || i >= t.Len() || j >= t.Len() {
		panic("nondeterministic comparison out of bounds")
	}
	return t.r.Float32() < 0.5 // ここが非決定的な比較
}
func (t *nonDeterministicTestingData) Swap(i, j int) {
	if i < 0 || j < 0 || i >= t.Len() || j >= t.Len() {
		panic("nondeterministic comparison out of bounds")
	}
}

func TestNonDeterministicComparison(t *testing.T) {
	// Ensure that sort.Sort does not panic when Less returns inconsistent results.
	// See https://golang.org/issue/14377.
	defer func() {
		if r := recover(); r != nil {
			t.Error(r)
		}
	}()

	td := &nonDeterministicTestingData{
		r: rand.New(rand.NewSource(0)),
	}

	for i := 0; i < 10; i++ {
		Sort(td)
	}
}
```

`nonDeterministicTestingData`構造体は、`sort.Interface`を実装していますが、その`Less`メソッドは`t.r.Float32() < 0.5`という条件で常にランダムなブール値を返します。これは、`i`と`j`の相対的な順序が呼び出しごとに変わることを意味し、典型的な非決定的な`Less`関数の振る舞いをシミュレートしています。

テストでは、`defer`と`recover`を使用して、`Sort(td)`の呼び出し中にパニックが発生しないことを確認しています。もしパニックが発生すれば、`recover`がそれを捕捉し、`t.Error(r)`によってテストが失敗します。このテストが成功するということは、`sort`パッケージが非決定的な`Less`関数に対してもパニックを起こさずに処理できるようになったことを示しています。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用しています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。

`ssa/check/on`ビルドは、SSAバックエンドの健全性を検証するための特別なビルドモードです。このモードでは、SSA形式のコードが特定のルールや不変条件を満たしているかを厳密にチェックします。このコミットが作成された時点では、`phielimValue`関数がリライトパス内で実行されると、`ssa/check/on`ビルドが失敗する問題が発生していました。これは、`phielimValue`がSSAの不変条件を一時的に破るか、または`ssa/check/on`が期待する状態と異なる状態を生成していた可能性を示唆しています。

この問題は、SSAバックエンドの初期段階で発生していたバグや、特定の最適化パスの相互作用によるものと考えられます。開発者は、`ssa/check/on`ビルドが成功するように、問題の原因となっている`phielimValue`の呼び出しを一時的に無効化するという対処療法を選択しました。これは、より根本的な解決策が見つかるまでの暫定的な措置であると推測されます。

## 前提知識の解説

### GoコンパイラとSSA

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要なのが、中間表現（IR: Intermediate Representation）としてSSA形式を使用するバックエンドです。

*   **SSA (Static Single Assignment) 形式**: プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が非常に効率的に行えます。例えば、`x = a + b; x = c + d;`というコードは、SSAでは`x1 = a + b; x2 = c + d;`のように変換され、各`x`が異なる変数として扱われます。
*   **Phi関数 (Φ関数)**: SSA形式において、複数の制御フローパスが合流する点（例: if文の終わり、ループの終わり）で、異なるパスから来た同じ論理的な変数にどの値が割り当てられるかを解決するために導入される特殊な関数です。例えば、`if condition { x = 1 } else { x = 2 } y = x + 3`というコードでは、`y = Φ(x_if, x_else) + 3`のように表現されます。
*   **リライトパス (Rewrite Pass)**: コンパイラの最適化ステージの一つで、SSA形式のコードをより効率的な形に変換します。これは、特定のパターンを検出し、それらをより最適化された命令シーケンスに置き換えることで行われます。例えば、`x + 0`を`x`にリライトしたり、定数畳み込みを行ったりします。
*   **`ssa/check/on`ビルド**: Goコンパイラの開発中に使用される特別なビルドオプションです。SSAバックエンドが生成する中間表現が、SSA形式の厳密なルール（不変条件）に違反していないかをチェックするために使用されます。これにより、コンパイラのバグを早期に発見し、SSA最適化の健全性を保証します。

### `phielimValue`関数

`phielimValue`は、GoコンパイラのSSAバックエンドにおいて、Phi関数に関連する最適化を行う関数であると推測されます。Phi関数はSSA形式の重要な要素ですが、最終的な機械語には直接対応する命令がありません。そのため、コンパイルの後半段階でPhi関数を実際のデータ移動命令（例: `MOV`命令）に変換したり、あるいは不要なPhi関数を削除したりする「Phi関数除去（Phi Elimination）」のプロセスが必要になります。

`phielimValue`は、このPhi関数除去の過程で、特定の`Value`（SSA形式における演算や変数を表すノード）がPhi関数に関連している場合に、その`Value`を最適化または除去しようとする役割を担っていたと考えられます。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/rewrite.go`ファイル内の`applyRewrite`関数から、`phielimValue(v)`の呼び出しを削除しています。

`applyRewrite`関数は、SSA形式の関数（`*Func`）に対してリライトパスを適用する主要な関数です。この関数は、各ブロック（`*Block`）内の各値（`*Value`）をイテレートし、リライトルールを適用します。

削除された行は以下の通りです。
```go
change = phielimValue(v) || change
```
この行は、各`Value v`に対して`phielimValue`関数を呼び出し、その結果（`change`が`true`であれば何らかの変更があったことを示す）を`change`変数に反映させていました。`change`変数は、リライトパスが関数に変更を加えたかどうかを追跡するために使用されます。

この行をコメントアウト（または削除）することで、リライトパスの実行中に`phielimValue`関数が呼び出されなくなります。これにより、`phielimValue`が引き起こしていた`ssa/check/on`ビルド時の問題が回避されます。

この変更は、`phielimValue`自体に問題があるというよりも、リライトパスの特定の段階で`phielimValue`が実行されることによって、SSAの不変条件が一時的に破られるか、または`ssa/check/on`が期待する状態と異なる状態が生成されていたことを示唆しています。例えば、`phielimValue`がまだ完全に準備ができていないSSAグラフに対して実行された場合や、他の最適化との順序関係で問題が生じていた可能性があります。

「Disable phielimValue from rewrite pass *for now*」というコミットメッセージの記述から、これは一時的な回避策であり、将来的には`phielimValue`が正しく機能するように修正されるか、あるいはリライトパスの別の段階で実行されるようになることが意図されていると理解できます。

## コアとなるコードの解説

変更は`src/cmd/compile/internal/ssa/rewrite.go`ファイルの`applyRewrite`関数内で行われています。

`applyRewrite`関数は、SSA形式の関数`f`を受け取り、その中の各ブロック`b`を処理します。さらに、各ブロック内の個々のSSA値`v`をループで処理します。

削除された行は以下の通りです。
```go
change = phielimValue(v) || change
```
この行は、`b.Values`（現在のブロック`b`に含まれるSSA値のリスト）をイテレートするループの中にありました。`phielimValue(v)`は、現在のSSA値`v`に対してPhi関数除去に関連する処理を実行し、もし`v`が変更された場合は`true`を返します。この`true`または`false`の結果は、`change`変数に論理OR演算で結合されていました。`change`変数は、`applyRewrite`関数がSSAグラフに変更を加えたかどうかを示すフラグとして機能します。

この行が削除されたことにより、`applyRewrite`関数がSSA値`v`を処理する際に、`phielimValue`関数は呼び出されなくなりました。これにより、`phielimValue`の実行によって引き起こされていた`ssa/check/on`ビルド時の問題が一時的に解消されました。

この変更は、`phielimValue`がリライトパスのこの段階で実行されると、SSAの不変条件が一時的に破られるか、または`ssa/check/on`が期待する状態と異なる状態が生成されるという問題に対する直接的な対処です。他の最適化（例えば、その直後に続く「Eliminate copy inputs」）との相互作用も考慮されるべき点です。

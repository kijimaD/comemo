# [インデックス 21684] ファイルの概要

このコミットでは、Goコンパイラの`cmd/gc`パッケージ内のエスケープ解析ロジックが修正されています。具体的には、`src/cmd/gc/esc.c`ファイルが変更され、`test/escape2.go`と`test/escape2n.go`という2つの新しいテストファイルが追加されています。

`src/cmd/gc/esc.c`は、Goコンパイラのエスケープ解析を担当するC言語のソースファイルです。エスケープ解析は、変数がヒープに割り当てられるべきか（エスケープする）、スタックに割り当てられるべきか（エスケープしない）を決定する最適化プロセスです。

`test/escape2.go`と`test/escape2n.go`は、このエスケープ解析の変更が正しく機能することを確認するためのテストケースです。特に、自己スライス代入のシナリオに焦点を当てています。

## 元コミット内容

このコミットは、Goコンパイラのエスケープ解析において、自己スライス代入（re-slicing）を無視するように変更します。

従来のエスケープ解析では、`OIND`（間接参照）や`ODOTPTR`（ポインタフィールドアクセス）に代入されるものはすべてエスケープすると見なされていました。このため、以下のようなコードでは`b`がエスケープすると判断されていました。

```go
func (b *Buffer) Foo() {
        n, m := ...
        b.buf = b.buf[n:m] // ここで b がエスケープと判断されていた
}
```

この変更は、このような自己代入を認識し、エスケープ解析の対象から除外することで、不要なヒープ割り当てを削減します。

この最適化は、標準ライブラリの`archive/zip`と`time`パッケージ内の類似のケースにも恩恵をもたらします。ベンチマーク結果では、`BenchmarkCompressedZipGarbage`において、実行時間がわずかに短縮され、アロケーション数が約6.54%削減されています。

関連するIssueは #9043 と #7921 です。

## 変更の背景

Goのエスケープ解析は、プログラムのパフォーマンスを向上させるための重要な最適化の一つです。変数がスタックに割り当てられるかヒープに割り当てられるかを決定することで、ガベージコレクションの負荷を軽減し、メモリ使用量を最適化します。

しかし、従来のエスケープ解析には、特定のコードパターンにおいて非効率な挙動がありました。特に、スライスを自分自身に再代入する「自己スライス代入（re-slicing）」のケースです。

例えば、`b.buf = b.buf[n:m]`のような操作は、`b.buf`が指す基底配列は変わらず、スライスのヘッダ（ポインタ、長さ、容量）が更新されるだけです。しかし、エスケープ解析は、`OIND`（間接参照）や`ODOTPTR`（ポインタフィールドアクセス）への代入を、新しいポインタが導入される可能性があるものとして一律にエスケープと判断していました。このため、`b.buf`が構造体`b`のフィールドである場合、`b`自体がヒープにエスケープすると誤って判断されることがありました。

この誤った判断は、実際には不要なヒープ割り当てを引き起こし、プログラムのパフォーマンスを低下させる原因となっていました。このコミットは、このような特定の自己スライス代入パターンをエスケープ解析が認識し、適切に無視することで、この非効率性を解消することを目的としています。これにより、より多くの変数をスタックに割り当てることが可能になり、ガベージコレクションの負担が軽減され、全体的なパフォーマンスが向上します。

## 前提知識の解説

このコミットの理解には、Goコンパイラの内部動作、特にエスケープ解析と抽象構文木（AST）のノードタイプに関する知識が必要です。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、変数がその宣言されたスコープを「エスケープ」するかどうかを決定します。
- **エスケープする (Escapes to heap)**: 変数がそのスコープ外から参照される可能性がある場合（例: グローバル変数に代入される、関数の戻り値になる、チャネルを通じて送信されるなど）、その変数はヒープに割り当てられます。ヒープに割り当てられたオブジェクトはガベージコレクタによって管理されます。
- **エスケープしない (Does not escape)**: 変数がその宣言されたスコープ内でのみ使用され、スコープ外から参照されることがない場合、その変数はスタックに割り当てられます。スタック割り当ては、ヒープ割り当てよりも高速で、ガベージコレクションのオーバーヘッドもありません。

エスケープ解析の目的は、可能な限り多くの変数をスタックに割り当てることで、ガベージコレクションの頻度と時間を減らし、プログラムの実行速度を向上させることです。

### GoコンパイラのASTノードタイプ

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築します。ASTの各ノードは、プログラムの構造や操作を表します。このコミットで言及されている主なノードタイプは以下の通りです。

-   **`ONAME`**: 変数名や関数名など、識別子を表すノードです。
-   **`OIND`**: 間接参照（ポインタのデリファレンス）を表すノードです。例えば、`*ptr`のような操作です。
-   **`ODOTPTR`**: ポインタを通じて構造体のフィールドにアクセスする操作を表すノードです。例えば、`ptr.field`（`(*ptr).field`の糖衣構文）のような操作です。
-   **`OAS`**: 単純な代入操作（`=`）を表すノードです。
-   **`OASOP`**: 複合代入操作（`+=`, `-=`など）を表すノードです。
-   **`OSLICE`**: スライス操作（`s[low:high]`）を表すノードです。
-   **`OSLICE3`**: 3つのインデックスを持つスライス操作（`s[low:high:max]`）を表すノードです。
-   **`OSLICESTR`**: 文字列のスライス操作を表すノードです。
-   **`OSLICEARR`**: 配列のスライス操作を表すノードです。このコミットでは、`OSLICEARR`は今回の最適化の対象外とされています。これは、`OSLICEARR`が新しいポインタを導入する可能性があるためです。例えば、`b.arr[1:2]`のような操作は、`b.arr`の基底配列へのポインタを生成し、そのポインタがエスケープする可能性があります。

### `src/cmd/gc/esc.c`

このファイルは、Goコンパイラのフロントエンドの一部である`gc`（Go Compiler）コマンドのソースコードです。`esc.c`は、エスケープ解析の主要なロジックが実装されている場所です。ASTを走査し、各ノードのプロパティと操作に基づいて、変数のエスケープ挙動を分析します。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラのエスケープ解析が、特定の自己スライス代入パターンをどのように識別し、それらをエスケープしないものとして扱うように変更されたかにあります。

従来のエスケープ解析では、`OAS`（代入）または`OASOP`（複合代入）ノードを処理する際、代入先の左辺が`OIND`（間接参照）または`ODOTPTR`（ポインタフィールドアクセス）である場合、その代入によって新しいポインタが導入され、結果として左辺の基底オブジェクトがヒープにエスケープすると見なされていました。これは、一般的なケースでは正しい挙動ですが、自己スライス代入の場合には過剰なエスケープ判断につながっていました。

例えば、`b.buf = b.buf[n:m]`というコードでは、`b.buf`は`b`という構造体のフィールドであり、`ODOTPTR`ノードとして表現されます。この代入によって、`b`がエスケープすると判断されていました。しかし、この操作は`b.buf`が指す基底配列を変更するものではなく、単にスライスのヘッダ（ポインタ、長さ、容量）を更新するだけです。つまり、`b`自体に新しいポインタが格納されるわけではありません。

このコミットでは、`esc.c`の`esc`関数内の`case OAS:`および`case OASOP:`ブロックに新しい条件分岐が追加されました。この条件分岐は、以下の特定のパターンに一致する代入を識別します。

1.  **代入先の左辺が`OIND`または`ODOTPTR`であること**: これは、ポインタのデリファレンスまたはポインタフィールドへのアクセスを通じて行われる代入であることを意味します。
    -   `n->left->op == OIND || n->left->op == ODOTPTR`
2.  **代入先の左辺の基底が`ONAME`であること**: つまり、`*ptr`や`obj.field`のような形式で、`ptr`や`obj`が名前付きの変数である場合です。
    -   `n->left->left->op == ONAME`
3.  **代入元の右辺がスライス操作であること**: `OSLICE`、`OSLICE3`、または`OSLICESTR`のいずれかであること。
    -   `n->right->op == OSLICE || n->right->op == OSLICE3 || n->right->op == OSLICESTR`
4.  **スライス操作の対象が`OIND`または`ODOTPTR`であること**: スライスがポインタのデリファレンスまたはポインタフィールドへのアクセスを通じて行われることを意味します。
    -   `n->right->left->op == OIND || n->right->left->op == ODOTPTR`
5.  **スライス操作の対象の基底が`ONAME`であること**: スライスが適用される元の変数が名前付きの変数である場合です。
    -   `n->right->left->left->op == ONAME`
6.  **代入先の左辺の基底`ONAME`と、スライス操作の対象の基底`ONAME`が同じであること**: これが「自己代入」の最も重要な条件です。
    -   `n->left->left == n->right->left->left`

これらの条件がすべて満たされる場合、コンパイラはこの代入をエスケープ解析の対象から除外します（`break;`ステートメントによって、通常の`escassign`呼び出しをスキップします）。これにより、`b.buf = b.buf[n:m]`のような操作が行われても、`b`が不要にエスケープすると判断されることがなくなります。

ただし、この最適化は`OSLICEARR`（配列のスライス）には適用されません。これは、`OSLICEARR`が新しいポインタを導入する可能性があるためです。例えば、`b.arr[1:2]`のような操作は、`b.arr`の基底配列へのポインタを生成し、そのポインタがエスケープする可能性があります。もし`OSLICEARR`を無視すると、`b`の内容がエスケープしているにもかかわらず、`b`がエスケープしないと誤って判断される可能性があります。

また、この変更は、`order`フェーズがすべての関数呼び出しを`init`に移動させることを前提としています。これにより、代入の評価中に基底の`ONAME`変数の値が変更されることがないという保証が得られます。

この最適化により、`archive/zip`や`time`パッケージのような、頻繁に自己スライス代入を行うコードのパフォーマンスが向上し、メモリ割り当てが削減されます。

## コアとなるコードの変更箇所

このコミットの主要な変更は、`src/cmd/gc/esc.c`ファイル内の`esc`関数の`case OAS:`および`case OASOP:`ブロックに新しい条件分岐が追加された点です。

```diff
--- a/src/cmd/gc/esc.c
+++ b/src/cmd/gc/esc.c
@@ -511,6 +511,36 @@ esc(EscState *e, Node *n, Node *up)
  
  	case OAS:
  	case OASOP:
+ 		// Filter out the following special case.
+ 		//
+ 		//	func (b *Buffer) Foo() {
+ 		//		n, m := ...
+ 		//		b.buf = b.buf[n:m]
+ 		//	}
+ 		//
+ 		// This assignment is a no-op for escape analysis,
+ 		// it does not store any new pointers into b that were not already there.
+ 		// However, without this special case b will escape, because we assign to OIND/ODOTPTR.
+ 		if((n->left->op == OIND || n->left->op == ODOTPTR) && n->left->left->op == ONAME && // dst is ONAME dereference
+ 		   (n->right->op == OSLICE || n->right->op == OSLICE3 || n->right->op == OSLICESTR) && // src is slice operation
+ 		   (n->right->left->op == OIND || n->right->left->op == ODOTPTR) && n->right->left->left->op == ONAME && // slice is applied to ONAME dereference
+ 		   n->left->left == n->right->left->left) { // dst and src reference the same base ONAME
+ 			// Here we also assume that the statement will not contain calls,
+ 			// that is, that order will move any calls to init.
+ 			// Otherwise base ONAME value could change between the moments
+ 			// when we evaluate it for dst and for src.
+ 			//
+ 			// Note, this optimization does not apply to OSLICEARR,
+ 			// because it does introduce a new pointer into b that was not already there
+ 			// (pointer to b itself). After such assignment, if b contents escape,
+ 			// b escapes as well. If we ignore such OSLICEARR, we will conclude
+ 			// that b does not escape when b contents do.
+ 			if(debug['m']) {
+ 				warnl(n->lineno, "%S ignoring self-assignment to %hN",
+ 					(n->curfn && n->curfn->nname) ? n->curfn->nname->sym : S, n->left);
+ 			}
+ 			break;
+ 		}

  		break;
```

また、この変更を検証するために、`test/escape2.go`と`test/escape2n.go`に新しいテストケースが追加されています。これらのテストケースは、`Buffer`構造体とそれに対する自己スライス代入のメソッドを定義し、エスケープ解析が正しく「b does not escape」と判断し、「ignoring self-assignment」という警告を出すことを確認します。

## コアとなるコードの解説

追加されたC言語のコードは、エスケープ解析の`esc`関数内で、代入ノード（`OAS`または`OASOP`）を処理する部分に挿入されています。

```c
if((n->left->op == OIND || n->left->op == ODOTPTR) && n->left->left->op == ONAME && // dst is ONAME dereference
   (n->right->op == OSLICE || n->right->op == OSLICE3 || n->right->op == OSLICESTR) && // src is slice operation
   (n->right->left->op == OIND || n->right->left->op == ODOTPTR) && n->right->left->left->op == ONAME && // slice is applied to ONAME dereference
   n->left->left == n->right->left->left) { // dst and src reference the same base ONAME
    // ... (コメントとデバッグ出力) ...
    break;
}
```

この`if`文は、以下の条件をすべて満たす代入文を特定します。

1.  **`n->left->op == OIND || n->left->op == ODOTPTR`**: 代入の左辺（`n->left`）が、ポインタのデリファレンス（`*ptr`）またはポインタフィールドへのアクセス（`ptr.field`）であること。これは、スライスが構造体のフィールドやポインタが指す値である場合に該当します。
2.  **`n->left->left->op == ONAME`**: 左辺の`OIND`または`ODOTPTR`の基底となる式（`n->left->left`）が、名前付きの変数（`ONAME`）であること。例えば、`b.buf`の場合、`b`が`ONAME`です。
3.  **`n->right->op == OSLICE || n->right->op == OSLICE3 || n->right->op == OSLICESTR`**: 代入の右辺（`n->right`）が、通常のスライス操作（`s[low:high]`）、3インデックススライス操作（`s[low:high:max]`）、または文字列スライス操作であること。
4.  **`n->right->left->op == OIND || n->right->left->op == ODOTPTR`**: 右辺のスライス操作の対象（`n->right->left`）が、ポインタのデリファレンスまたはポインタフィールドへのアクセスであること。
5.  **`n->right->left->left->op == ONAME`**: 右辺のスライス操作の対象の基底となる式（`n->right->left->left`）が、名前付きの変数（`ONAME`）であること。
6.  **`n->left->left == n->right->left->left`**: 最も重要な条件で、代入の左辺の基底となる`ONAME`と、右辺のスライス操作の対象の基底となる`ONAME`が、**同じノード**であること。これは、`b.buf = b.buf[n:m]`のように、同じ変数に対してスライス操作を行い、その結果を同じ変数に代入する「自己代入」であることを意味します。

これらの条件がすべて真である場合、コンパイラは、この代入がエスケープ解析にとって「no-op」（何もしない）であると判断します。つまり、この代入は新しいポインタを導入せず、既存のポインタの範囲を調整するだけなので、変数がヒープにエスケープする必要はないと判断されます。

`break;`ステートメントは、この特定のケースでは通常の`escassign`関数（代入のエスケープ解析を行う関数）の呼び出しをスキップし、エスケープ解析がこの代入を無視するようにします。

デバッグモード（`debug['m']`が有効な場合）では、`warnl`関数を使って「ignoring self-assignment to ...」という警告が出力されます。これは、コンパイラがこの最適化を適用したことを開発者に知らせるためのものです。

コメントにもあるように、この最適化は`OSLICEARR`（配列のスライス）には適用されません。これは、配列のスライスは新しいポインタを生成する可能性があり、それを無視すると誤ったエスケープ解析結果につながるためです。

この変更により、Goコンパイラはより賢くエスケープ解析を行い、不要なヒープ割り当てを減らすことで、Goプログラムの実行効率を向上させます。

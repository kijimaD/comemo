## 元コミット内容

Goランタイムに、欠落しているライトバリアを検出するための `GODEBUG=wbshadow` デバッグ機能を追加します。この検出コードは十分に機能し、いくつかの欠落したライトバリアを特定できましたが、それらは微妙な問題であるため、後続のコミットで個別に修正されます。

`GODEBUG=wbshadow=1` を設定すると、同じワードに対する次回のライトバリア時に、ライトバリアをバイパスした書き込みがないかチェックします。このモードで検出されたバグは、クラッシュメッセージがどの種類のワードでライトバリアが欠落しているかを明確に示しているため、通常は理解しやすいです。

`GODEBUG=wbshadow=2` を設定すると、ガベージコレクション中にライトバリアのシャドウコピーのチェックも追加されます。ガベージコレクション中に検出されたバグは、見つかったワードが何を意味するかのコンテキストがないため、理解が難しい場合があります。通常、問題のワードの型を理解するためには、`allocfreetrace=1` を使用して問題を再現する必要があります。

## 変更の背景

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGCが動作します。この並行性を実現するためには、「ライトバリア（Write Barrier）」と呼ばれるメカニズムが不可欠です。ライトバリアは、GCがオブジェクトグラフを走査している最中に、プログラムがポインタを書き換える際に介入し、GCがオブジェクトを見失わないようにするためのものです。

しかし、ランタイムコードの複雑さから、特定のポインタ書き込み操作でライトバリアが意図せず欠落してしまう「欠落したライトバリア（missing write barrier）」というバグが発生する可能性があります。このようなバグは、GCがオブジェクトを誤って解放したり、到達可能なオブジェクトを回収してしまったりする原因となり、結果としてプログラムのクラッシュやデータの破損につながります。

このコミットは、このような深刻なバグを早期に、かつ効率的に検出するためのデバッグツールを導入することを目的としています。特に、GCの動作中に発生する可能性のある微妙なバグを特定するために、ヒープのシャドウコピーを作成し、ポインタの整合性をチェックするメカニズムが考案されました。

## 前提知識の解説

### 1. ガベージコレクション (GC) と並行GC

Goのガベージコレクタは、メモリ管理を自動化するシステムです。Go 1.5以降、GoのGCは「並行マーク＆スイープ」方式を採用しています。これは、GCの大部分のフェーズがアプリケーションの実行と並行して行われることを意味します。

*   **マークフェーズ**: GCは、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能なオブジェクト）をメモリから解放します。

並行GCの利点は、アプリケーションの一時停止時間（ストップ・ザ・ワールド、STW）を最小限に抑え、レイテンシを改善することです。

### 2. ライトバリア (Write Barrier)

並行GCにおいて、アプリケーションがオブジェクトグラフを変更する（ポインタを書き換える）際に、GCがオブジェクトを見失わないようにするためのメカニズムがライトバリアです。具体的には、ポインタの書き込み操作が行われる直前または直後に、GCがその変更を認識し、必要に応じてオブジェクトを再マークするなどの処理を行います。

Goのライトバリアは、主に「Dijkstraの三色マーク」アルゴリズムに基づいています。
*   **白**: GCによってまだ訪問されていないオブジェクト。
*   **灰色**: GCによって訪問されたが、その参照先がまだ訪問されていないオブジェクト。
*   **黒**: GCによって訪問され、その参照先もすべて訪問されたオブジェクト。

ライトバリアの目的は、黒いオブジェクトから白いオブジェクトへのポインタの書き込みを防ぐことです。もし黒から白へのポインタが直接書き込まれると、白いオブジェクトはGCによって到達不可能と判断され、誤って回収されてしまう可能性があります。ライトバリアは、このような書き込みを検出した場合、白いオブジェクトを灰色にマークし直すことで、GCがそのオブジェクトを追跡できるようにします。

### 3. シャドウヒープ (Shadow Heap)

このコミットで導入される「シャドウヒープ」は、Goランタイムのヒープ（メモリ領域）のコピーを保持するデバッグ用のメカニズムです。通常のヒープに対するポインタの書き込みが行われる際に、同時にシャドウヒープにもその書き込みが反映されます。これにより、ライトバリアが正しく機能しているかを検証できます。

シャドウヒープは、ライトバリアが欠落している場合に、本来のヒープとシャドウヒープの内容が不一致になることで、その問題を検出するための比較対象として機能します。

### 4. `GODEBUG` 環境変数

`GODEBUG` は、Goランタイムのデバッグオプションを設定するための環境変数です。`GODEBUG=name=value,name2=value2` の形式で複数のオプションを指定できます。このコミットでは、`wbshadow` という新しいオプションが追加されます。

## 技術的詳細

このコミットの核心は、Goランタイムのライトバリアの欠落を検出するための「シャドウヒープ」メカニズムの実装です。

### シャドウヒープの動作原理

1.  **ヒープの複製**: `GODEBUG=wbshadow` が有効な場合、Goランタイムは通常のヒープ（アリーナ）とデータセグメントのシャドウコピーをメモリ上に作成します。これは、`wbshadowinit` 関数によって行われます。
2.  **ライトバリアの拡張**: ポインタの書き込み操作（`writebarrierptr` 関数など）が行われる際、通常のヒープへの書き込みだけでなく、シャドウヒープへの対応する書き込みも試みられます。
3.  **整合性チェック**:
    *   `wbshadow=1` の場合: 同じワードに対する次回のライトバリア時に、通常のヒープの値とシャドウヒープの値が一致するかをチェックします。もし不一致があれば、それは前回の書き込みでライトバリアが欠落したことを意味し、ランタイムパニックを引き起こします。
    *   `wbshadow=2` の場合: GCのマークフェーズ中（`scanobject` や `checkwbshadow`）にも、ヒープ上のポインタとシャドウヒープ上の対応するポインタの整合性がチェックされます。これにより、GCがオブジェクトグラフを走査する際に、ライトバリアの欠落によってポインタが不正な状態になっていないかを確認できます。
4.  **`noShadow` 値**: `noShadow` (値は1) は、シャドウヒープに記録された値が、実際のポインタ値ではなく、シャドウが更新されなかったことを示す特別なマーカーとして使用されます。これは、アトミック操作など、シャドウヒープを正確に更新できない場合に設定されます。

### 検出モードの違い

*   **`wbshadow=1` (即時検出)**:
    *   **利点**: 問題発生箇所に非常に近い場所で検出されるため、スタックトレースやコンテキストからバグの原因を特定しやすいです。クラッシュメッセージが「どの種類のワードでライトバリアが欠落したか」を明確に示します。
    *   **欠点**: ライトバリアが欠落した書き込みがあっても、そのワードが次にライトバリアを伴う書き込みが行われるまで検出されない可能性があります。
*   **`wbshadow=2` (GC時検出)**:
    *   **利点**: GCがヒープ全体を走査する際にチェックが行われるため、`wbshadow=1` では見逃される可能性のある、より広範囲のライトバリアの欠落を検出できます。
    *   **欠点**: GC時に検出されるため、問題が発生した元の書き込み操作から時間が経過していることが多く、コンテキストが失われているため、バグの原因特定が非常に困難になります。この場合、`allocfreetrace=1` を併用して、問題のワードの割り当てと解放の履歴を追跡する必要がある場合があります。

### 実装上の考慮事項

*   **64-bitシステム限定**: シャドウヒープは、ヒープ全体のコピーをメモリに保持するため、大量のメモリを消費します。そのため、この機能は64-bitシステムでのみ有効です。32-bitシステムでは無効化されます。
*   **パフォーマンスオーバーヘッド**: シャドウヒープの維持とチェックには、当然ながらパフォーマンスオーバーヘッドが伴います。そのため、この機能はデバッグ目的でのみ使用され、本番環境で常に有効にするものではありません。
*   **アトミック操作との兼ね合い**: アトミック操作によってポインタが書き換えられる場合、通常のライトバリアのメカニズムではシャドウヒープを正確に更新できないことがあります。この場合、`writebarrierptr_noshadow` を使用して、シャドウヒープに `noShadow` マーカーを書き込むことで、意図的な不一致を許容します。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/mgc0.go` に集中しています。

### `mheap` 構造体 (`src/runtime/malloc2.go`)

```go
type mheap struct {
	// ... 既存のフィールド ...

	// write barrier shadow data+heap.
	// 64-bit systems only, enabled by GODEBUG=wbshadow=1.
	shadow_enabled  bool    // shadow should be updated and checked
	shadow_reserved bool    // shadow memory is reserved
	shadow_heap     uintptr // heap-addr + shadow_heap = shadow heap addr
	shadow_data     uintptr // data-addr + shadow_data = shadow data addr
	data_start      uintptr // start of shadowed data addresses
	data_end        uintptr // end of shadowed data addresses

	// ... 既存のフィールド ...
}
```
`mheap` 構造体は、Goランタイムのヒープ管理の中核をなすものです。ここに `shadow_` プレフィックスを持つフィールドが追加され、シャドウヒープの有効化状態、予約状態、そしてシャドウヒープとシャドウデータ領域のベースアドレスと範囲を管理します。

### `wbshadowinit()` 関数 (`src/runtime/malloc1.go`)

```go
func wbshadowinit() {
	// Initialize write barrier shadow heap if we were asked for it
	// and we have enough address space (not on 32-bit).
	if debug.wbshadow == 0 {
		return
	}
	if ptrSize != 8 { // 64-bitシステムでのみ有効
		print("runtime: GODEBUG=wbshadow=1 disabled on 32-bit system\n")
		return
	}

	var reserved bool
	// ヒープ領域のシャドウコピーを予約・マップ
	p1 := sysReserve(nil, mheap_.arena_end-mheap_.arena_start, &reserved)
	if p1 == nil {
		throw("cannot map shadow heap")
	}
	mheap_.shadow_heap = uintptr(p1) - mheap_.arena_start
	sysMap(p1, mheap_.arena_used-mheap_.arena_start, reserved, &memstats.other_sys)
	memmove(p1, unsafe.Pointer(mheap_.arena_start), mheap_.arena_used-mheap_.arena_start)

	mheap_.shadow_reserved = reserved

	// データセグメントのシャドウコピーも同様に処理
	// ... (データセグメントのシャドウコピー初期化ロジック) ...

	mheap_.shadow_enabled = true
}
```
この関数は、`GODEBUG=wbshadow` が設定されている場合に、ヒープとデータセグメントのシャドウコピー用のメモリ領域を予約し、マップします。これにより、通常のメモリ操作と並行してシャドウメモリを更新・チェックする準備が整います。

### `writebarrierptr()` 関数 (`src/runtime/mgc0.go`)

```go
func writebarrierptr(dst *uintptr, src uintptr) {
	if !needwb() { // ライトバリアが不要な場合（GCが停止しているなど）
		*dst = src
		return
	}

	// ... ポインタの健全性チェック ...

	if mheap_.shadow_enabled {
		systemstack(func() {
			addr := uintptr(unsafe.Pointer(dst))
			shadow := shadowptr(addr) // シャドウヒープ上の対応するアドレスを取得
			if shadow == nil {
				return
			}
			// ここがライトバリア欠落検出の核心
			// シャドウヒープの値と実際のヒープの値が異なる、かつシャドウがnoShadowではない、かつsrcが追跡対象ポインタの場合
			if *shadow != *dst && *shadow != noShadow && istrackedptr(*dst) {
				mheap_.shadow_enabled = false // 検出されたらシャドウチェックを無効化
				print("runtime: write barrier dst=", dst, " old=", hex(*dst), " shadow=", shadow, " old=", hex(*shadow), " new=", hex(src), "\n")
				throw("missed write barrier") // パニック！
			}
			*shadow = src // シャドウヒープを更新
		})
	}

	*dst = src // 実際のポインタ書き込み
	writebarrierptr_nostore1(dst, src) // ライトバリアの追加処理
}
```
`writebarrierptr` は、Goランタイムでポインタが書き換えられる際に呼び出される主要なライトバリア関数です。このコミットにより、`mheap_.shadow_enabled` が真の場合に、シャドウヒープの整合性チェックが追加されました。

*   `shadowptr(addr)`: `dst` のアドレスに対応するシャドウヒープ上のアドレスを計算します。
*   `*shadow != *dst && *shadow != noShadow && istrackedptr(*dst)`: この条件が `true` の場合、ライトバリアが欠落した書き込みがあったと判断されます。
    *   `*shadow != *dst`: シャドウヒープに記録されている古い値と、実際のヒープに書き込まれる前の値が異なる。
    *   `*shadow != noShadow`: シャドウが意図的に更新されなかったことを示す `noShadow` マーカーではない。
    *   `istrackedptr(*dst)`: 書き込まれる値がGCによって追跡されるべきポインタである。
*   `throw("missed write barrier")`: 上記の条件が満たされた場合、ランタイムパニックが発生し、ライトバリアの欠落が報告されます。
*   `*shadow = src`: 実際のポインタ書き込みが行われる前に、シャドウヒープも新しい値で更新されます。

### `checkwbshadow()` 関数 (`src/runtime/mgc0.go`)

```go
func checkwbshadow(p *uintptr) {
	addr := uintptr(unsafe.Pointer(p))
	shadow := shadowptr(addr)
	if shadow == nil {
		return
	}
	// The garbage collector calls checkwbshadow for each pointer during the checkmark phase.
	// It is only called when mheap_.shadow_enabled is true.
	// ... (レースコンディションに関するコメント) ...
	if *shadow != *p && *shadow != noShadow && istrackedptr(*p) {
		mheap_.shadow_enabled = false
		print("runtime: checkwritebarrier p=", p, " *p=", hex(*p), " shadow=", shadow, " *shadow=", hex(*shadow), "\n")
		throw("missed write barrier")
	}
}
```
この関数は、`GODEBUG=wbshadow=2` が有効な場合に、GCのマークフェーズ中に呼び出されます。`writebarrierptr` と同様に、実際のポインタ値とシャドウヒープの値を比較し、不一致があればライトバリアの欠落としてパニックを発生させます。GC時に検出されるため、コンテキストが少ないという欠点があります。

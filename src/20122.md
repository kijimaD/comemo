## 変更の背景

この変更の背景には、Goバイナリが特定の高いメモリアドレスにリンクされる際に発生する可能性のある問題がありました。従来の絶対アドレッシングでは、プログラムがロードされるメモリアドレスが固定されていることを前提としていました。しかし、共有ライブラリや動的にロードされるモジュールなど、ロードアドレスが実行時に決定されるようなシナリオでは、絶対アドレッシングは問題を引き起こします。

特にAMD64アーキテクチャでは、命令ポインタ（PC）からの相対オフセットを用いてメモリを参照するPC相対アドレッシングが利用可能です。このアドレッシングモードは、位置独立コード（PIC: Position-Independent Code）の生成に不可欠であり、バイナリがどのメモリアドレスにロードされても正しく実行されることを可能にします。

このコミットは、Go 1.4において、リンカ（`cmd/6l`および`liblink`）がすべてのメモリ参照にPC相対アドレッシングを使用するように変更されたことをリリースノートに追記するものです。これにより、Goバイナリが高いアドレスにリンクされる問題が解決されました。しかし、PC相対アドレッシングのオフセットが通常32ビット符号付き値であるため、参照可能な範囲が現在の命令から±2GBに制限されます。この制限により、Goバイナリの`text`（コード）、`data`（初期化済みデータ）、`bss`（初期化されていないデータ）セグメントの合計最大サイズが4GBから2GBに削減されることになりました。これは、Goバイナリが非常に大きくなる場合に考慮すべき重要な制約となります。

## 前提知識の解説

### PC相対アドレッシング (PC-relative addressing)

PC相対アドレッシングは、プログラムカウンタ（PC、またはAMD64ではRIPレジスタ）の現在の値からの相対的なオフセットを使用してメモリ位置を指定するアドレッシングモードです。

- **仕組み**: 命令が実行される際、その命令のアドレスに指定されたオフセットを加算することで、目的のメモリ位置のアドレスが計算されます。
- **利点**:
    - **位置独立コード (PIC)**: プログラムがメモリ上のどの位置にロードされても正しく実行されるコードを生成できます。これは共有ライブラリや動的ロードにおいて非常に重要です。
    - **コードサイズの削減**: 絶対アドレスを埋め込む必要がないため、コードの再配置情報が不要になり、バイナリサイズが小さくなる場合があります。
- **制限**: オフセット値のビット幅（通常32ビット）によって、参照可能なメモリ範囲が制限されます。例えば、32ビット符号付きオフセットの場合、現在のPCから±2GBの範囲しか参照できません。

### Goバイナリのメモリレイアウト

Goの実行可能バイナリは、他の多くのプログラムと同様に、いくつかの主要なセグメントに分割されてメモリにロードされます。

-   **Textセグメント**: 実行可能な機械語コードが含まれます。
-   **Dataセグメント**: 初期化されたグローバル変数や静的変数が含まれます。
-   **BSSセグメント**: 初期化されていないグローバル変数や静的変数が含まれます。プログラムの開始時にゼロで初期化されます。

これらのセグメントの合計サイズが、バイナリが占めるメモリ空間の大部分を構成します。

### Go 1.4

Go 1.4は2014年にリリースされたGo言語のバージョンです。このバージョンでは、主にGoランタイムの内部実装に大きな改善が加えられました。特に、ガベージコレクタの精度向上や、スタックの実装変更（連続スタックの導入）などが挙げられます。このコミットで言及されているPC相対アドレッシングの導入も、Goバイナリの生成と実行効率を向上させるための重要な変更の一つでした。

### `cmd/6l` と `liblink`

これらはGoツールチェーンの一部であり、Goプログラムのリンクを担当します。

-   **`cmd/6l`**: Goのリンカの一つで、AMD64（x86-64）アーキテクチャ向けのバイナリを生成します。
-   **`liblink`**: Goのリンカのバックエンドライブラリであり、様々なアーキテクチャ向けのリンク処理の共通部分を提供します。

これらのツールが、コンパイルされたオブジェクトファイルを結合し、実行可能なバイナリを生成する過程で、メモリ参照のアドレッシングモードを決定します。

## 技術的詳細

このコミットがリリースノートに追記している技術的詳細は、Go 1.4におけるリンカ（`cmd/6l`と`liblink`）の挙動変更に関するものです。

Goバイナリのリンクにおいて、特にAMD64アーキテクチャでは、これまで絶対アドレッシングが使用されるケースがありました。しかし、これによりバイナリが特定の高いメモリアドレスにロードされる際に問題が発生する可能性がありました。例えば、ASLR (Address Space Layout Randomization) が有効なシステムや、共有ライブラリとしてロードされる場合などです。

この問題を解決するため、Go 1.4ではリンカがすべてのメモリ参照に対してPC相対アドレッシングを使用するように変更されました。PC相対アドレッシングは、命令ポインタ（RIPレジスタ）からの相対オフセットを用いてメモリを参照するため、生成されるコードは位置独立性（Position-Independent）を持ちます。これにより、Goバイナリはメモリ上のどの位置にロードされても正しく動作するようになります。

しかし、AMD64アーキテクチャにおけるRIP相対アドレッシングは、通常32ビットの符号付きオフセットを使用します。これは、現在の命令ポインタから前方または後方へ最大2GBの範囲しか直接参照できないことを意味します。この制限が、Goバイナリの`text`、`data`、`bss`セグメントの合計サイズに影響を与えます。具体的には、これらのセグメントが合計で2GBを超える場合、PC相対アドレッシングだけではすべてのメモリ参照を解決できなくなり、リンカがバイナリを生成できなくなる可能性があります。

したがって、この変更は「Goバイナリが高いアドレスにリンクされる問題を解決する」という利点をもたらす一方で、「Goバイナリの`text+data+bss`の最大サイズを4GBから2GBに削減する」という制約を課すことになりました。これは、非常に大規模なGoアプリケーションを開発する際に、メモリレイアウトとバイナリサイズを考慮する必要があることを示唆しています。

## コアとなるコードの解説

この追加された一行は、Go 1.4のリリースノートにおいて、リンカ（`cmd/6l`と`liblink`）の重要な変更点を説明しています。

-   **`cmd/6l, liblink: use pc-relative addressing for all memory references`**: これは、Goのリンカが、生成されるバイナリ内のすべてのメモリ参照（変数へのアクセス、関数呼び出しなど）に対して、PC相対アドレッシングを使用するようになったことを意味します。これにより、バイナリはメモリ上のどこにロードされても正しく動作する「位置独立」な性質を持つようになります。
-   **`so that linking Go binaries at high addresses works (CL 125140043)`**: この変更の主な目的は、Goバイナリが非常に高いメモリアドレスにロードされるような環境（例えば、一部のオペレーティングシステムやセキュリティ機能が有効な場合）でも、問題なくリンクされ、実行できるようにすることです。括弧内の`CL 125140043`は、この具体的な変更が行われたチェンジリスト（Goのコードレビューシステムにおける変更単位）のIDを示しています。
-   **`This cuts the maximum size of a Go binary's text+data+bss from 4GB to 2GB.`**: これは、PC相対アドレッシングの技術的な制約による副作用です。AMD64アーキテクチャのRIP相対アドレッシングは、通常32ビットの符号付きオフセットを使用するため、参照可能な範囲が現在の命令ポインタから±2GBに制限されます。したがって、Goバイナリのコード、初期化済みデータ、初期化されていないデータの合計サイズが2GBを超えると、リンカがすべてのメモリ参照をPC相対アドレッシングで解決できなくなり、バイナリの生成が不可能になることを意味します。これは、非常に大規模なGoアプリケーションを開発する際の設計上の考慮事項となります。

このリリースノートの記述は、Go 1.4における重要な低レベルの変更を開発者に伝え、その利点と制約を明確にしています。

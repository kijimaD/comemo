## 変更の背景

Goランタイムのスケジューラは、利用可能なプロセッサ（P）上で実行可能なゴルーチン（G）を効率的にスケジュールすることで、CPUリソースを最大限に活用しようとします。このプロセスにおいて、特定のプロセッサ（P）に割り当てられたローカル実行キュー（run queue）が空であるかどうかを判断する`runqempty`関数は非常に重要な役割を担っています。

問題は、`runnext`という最適化が導入されたことで発生しました。`runnext`は、ローカル実行キューの先頭にあるゴルーチンを特別なスロットに保持することで、キューからの取り出しを高速化するメカニズムです。しかし、この`runnext`の存在が`runqempty`の判断を複雑にし、競合状態を引き起こす可能性がありました。

コミットメッセージで説明されているシナリオは以下の通りです。

1.  `runnext`スロットにはゴルーチン（G1）が存在するが、メインの実行キュー配列は空である。
2.  `runqempty`関数が実行され、メインのキュー配列が空であることを確認する。
3.  `runqempty`が一時的にプリエンプト（中断）される。
4.  その間に、キューのオーナー（P）が別のゴルーチン（G2）をキューにプッシュする。この際、`runnext`スロットにあったG1がメインのキュー配列に移動される（evictされる）。
5.  その後、キューのオーナーはG1をキューからポップ（取り出し）する。
6.  `runqempty`が実行を再開し、`runnext`スロットが空になっていることを確認する。
7.  `runqempty`は、メインキューも`runnext`も空であると判断し、誤って「キューが空である」と報告してしまう。

この結果、実際には実行可能なゴルーチンが存在するにもかかわらず、スケジューラがキューを空だと誤認し、アイドル状態のPが存在するにもかかわらずゴルーチンをスケジュールできないという「CPU underutilization（CPU利用率の低下）」が発生していました。これは、システムのパフォーマンスに直接影響を与える深刻な問題でした。

## 前提知識の解説

### Goランタイムスケジューラ (M, P, G)

Goのスケジューラは、M（Machine/OSスレッド）、P（Processor/論理プロセッサ）、G（Goroutine）という3つのエンティティを中心に動作します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが記述する並行処理の最小単位であり、OSスレッドよりもはるかに軽量です。
*   **M (Machine)**: OSスレッドに対応します。Goのコードを実行する実際のOSスレッドです。複数のMが存在し、それぞれがPにアタッチされてGを実行します。
*   **P (Processor)**: 論理プロセッサを表します。MとGの仲介役であり、実行可能なGを保持するローカル実行キュー（run queue）を持ちます。`GOMAXPROCS`環境変数によってPの数が決定され、通常はCPUコア数に一致します。MはPにアタッチされ、Pのローカル実行キューからGを取り出して実行します。

### ローカル実行キュー (`runq`) と `runnext`

各Pは、自身が実行すべきゴルーチンを格納するローカル実行キュー（`runq`）を持っています。これは通常、リングバッファとして実装されています。
`runnext`は、このローカル実行キューの最適化された部分です。キューの先頭にあるゴルーチンを一時的に保持するための単一のスロットであり、キューのメイン配列にアクセスするよりも高速にゴルーチンを取り出せるように設計されています。これにより、スケジューリングのレイテンシを削減し、スループットを向上させることが期待されます。

### `runqempty` 関数の目的

`runqempty`関数は、特定のPのローカル実行キューが現在空であるかどうかを判断するために使用されます。スケジューラは、この情報に基づいて、Pがアイドル状態であると判断し、他のPからゴルーチンを盗む（work stealing）必要があるか、あるいは新しいゴルーチンを生成して実行する必要があるかなどを決定します。したがって、この関数が正確な情報を返すことは、スケジューラの効率とシステムの応答性にとって極めて重要です。

### アトミック操作の重要性

並行プログラミングにおいて、複数のゴルーチンやOSスレッドが共有データに同時にアクセスする場合、競合状態（race condition）が発生する可能性があります。これを防ぐために、アトミック操作が用いられます。アトミック操作は、その操作が不可分（atomic）であることを保証し、他のスレッドからの干渉なしに完了することを保証します。これにより、データの整合性が保たれ、予期せぬ動作を防ぐことができます。Goランタイムでは、`sync/atomic`パッケージや、ランタイム内部で直接アトミック命令を使用することで、このような操作を実現しています。

## 技術的詳細

### 以前の `runqempty` の実装

変更前の`runqempty`関数は、非常にシンプルでした。

```go
func runqempty(_p_ *p) bool {
	return _p_.runqhead == _p_.runqtail && _p_.runnext == 0
}
```

この実装は、ローカル実行キューのヘッドとテールが一致し、かつ`runnext`スロットが空（`0`はnilを表す）であれば、キューが空であると判断していました。しかし、これは`runnext`の導入によって発生した競合状態を考慮していませんでした。具体的には、`_p_.runqhead == _p_.runqtail`のチェックと`_p_.runnext == 0`のチェックの間に、他のM/Pがキューの状態を変更する可能性がありました。

### `runnext`による競合状態の具体的なメカニズム

コミットメッセージで述べられている競合状態は、以下のステップで発生します。

1.  **初期状態**: Pのローカル実行キューはメイン配列が空で、`runnext`にG1がある状態。
    *   `_p_.runqhead == _p_.runqtail` は `true`。
    *   `_p_.runnext` は `G1` (非nil)。
2.  **`runqempty`の最初のチェック**: `runqempty`が`_p_.runqhead == _p_.runqtail`をチェックし、`true`を得る。
3.  **プリエンプション**: `runqempty`が`_p_.runnext == 0`をチェックする前に、スケジューラによってプリエンプトされる。
4.  **他のPによる操作**: 別のPがこのPのキューにG2をプッシュする。この操作により、`runnext`にあったG1がメインキュー配列に移動（evict）され、`runnext`は空になる。その後、そのPがG1をメインキューからポップして実行する。
    *   この時点で、`_p_.runqhead`と`_p_.runqtail`は再び一致する可能性がある（G1がevictされ、G1がポップされたため）。
    *   `_p_.runnext`は`0`（nil）になる。
5.  **`runqempty`の再開と誤判断**: `runqempty`が実行を再開し、`_p_.runnext == 0`をチェックし、`true`を得る。
6.  **結果**: `runqempty`は`_p_.runqhead == _p_.runqtail`と`_p_.runnext == 0`の両方が`true`であると判断し、キューが空であると誤って報告する。しかし、実際にはステップ4の間にキューは空ではなかった。

この問題は、複数のフィールド（`runqhead`, `runqtail`, `runnext`）を個別に読み取ることによって発生する「スナップショットの不整合」に起因します。これらのフィールドがアトミックに、かつ一貫した状態で読み取られない限り、中間状態での変更によって誤った判断が下される可能性があります。

### 新しい `runqempty` の実装による解決策

新しい`runqempty`関数は、この競合状態を解決するために、ループとアトミック操作を導入しています。

```go
func runqempty(_p_ *p) bool {
	// Defend against a race where 1) _p_ has G1 in runqnext but runqhead == runqtail,
	// 2) runqput on _p_ kicks G1 to the runq, 3) runqget on _p_ empties runqnext.
	// Simply observing that runqhead == runqtail and then observing that runqnext == nil
	// does not mean the queue is empty.
	for {
		head := atomic.Load(&_p_.runqhead)
		tail := atomic.Load(&_p_.runqtail)
		runnext := atomic.Loaduintptr((*uintptr)(unsafe.Pointer(&_p_.runnext)))
		if tail == atomic.Load(&_p_.runqtail) { // tailが読み取り中に変更されていないことを確認
			return head == tail && runnext == 0
		}
	}
}
```

この新しい実装のポイントは以下の通りです。

1.  **ループの導入**: `for {}`ループにより、キューの状態が安定するまで（または一貫したスナップショットが取得できるまで）繰り返しチェックを行います。
2.  **アトミックロード**: `atomic.Load`および`atomic.Loaduintptr`を使用して、`runqhead`, `runqtail`, `runnext`の値をアトミックに読み取ります。これにより、部分的な読み取りによるデータ破損を防ぎます。
3.  **一貫性チェック**: `if tail == atomic.Load(&_p_.runqtail)`という条件が追加されています。これは、`head`と`tail`を読み取った後に、再度`tail`をアトミックに読み取り、最初の`tail`の値と比較することで、読み取り中に`tail`が変更されていないことを確認するものです。もし`tail`が変更されていれば、それはキューの状態が変化したことを意味するため、ループを続行して再度すべての値を読み直します。
4.  **正確な判断**: `tail`の値が一貫していることが確認できた場合のみ、`head == tail && runnext == 0`という条件でキューが本当に空であるかを判断します。これにより、`head`, `tail`, `runnext`の3つの値が同時に一貫した状態を反映していることが保証され、誤った「空」の報告を防ぎます。

この変更により、`runqempty`は「決して誤ってtrueを返さない」という保証を持つようになり、スケジューラの正確性とCPU利用率の向上が図られました。

## コアとなるコードの解説

### `src/runtime/proc.go` の `runqempty` 関数

新しい`runqempty`関数は、競合状態を確実に回避するために、以下のロジックを採用しています。

```go
func runqempty(_p_ *p) bool {
	for { // (1) 無限ループ
		head := atomic.Load(&_p_.runqhead) // (2) headをアトミックに読み込む
		tail := atomic.Load(&_p_.runqtail) // (3) tailをアトミックに読み込む
		runnext := atomic.Loaduintptr((*uintptr)(unsafe.Pointer(&_p_.runnext))) // (4) runnextをアトミックに読み込む
		if tail == atomic.Load(&_p_.runqtail) { // (5) tailが読み取り中に変更されていないことを確認
			return head == tail && runnext == 0 // (6) 一貫性が確認できたら最終判断
		}
	}
}
```

1.  **無限ループ**: `for {}`ループは、`head`, `tail`, `runnext`の読み取りが、その間にキューの状態が変更されていない一貫したスナップショットを捉えるまで繰り返すことを保証します。
2.  **`head`のアトミックロード**: `_p_.runqhead`の値をアトミックに読み込みます。これはキューの先頭位置を示します。
3.  **`tail`のアトミックロード**: `_p_.runqtail`の値をアトミックに読み込みます。これはキューの末尾位置を示します。
4.  **`runnext`のアトミックロード**: `_p_.runnext`の値をアトミックに読み込みます。`unsafe.Pointer`を使用しているのは、`runnext`が`*g`型であり、`atomic.Loaduintptr`が`uintptr`を期待するためです。`0`はnilポインタを表します。
5.  **一貫性チェック**: ここが最も重要な部分です。`tail`を再度アトミックに読み込み、最初に読み込んだ`tail`の値と比較します。
    *   もし`tail`の値が一致すれば、`head`と`tail`の読み取り中にキューの末尾が変更されていないことを意味します。この場合、`head`, `tail`, `runnext`の3つの値は、ほぼ同時に取得された一貫したスナップショットであると見なすことができます。
    *   もし`tail`の値が一致しなければ、`head`と`tail`の読み取りの間にキューに要素が追加されたか、削除されたか、あるいは`runnext`がメインキューにevictされたかなどの変更があったことを意味します。この場合、現在のスナップショットは不整合であるため、ループの先頭に戻り、再度すべての値を読み直します。
6.  **最終判断**: `tail`の一貫性が確認できた場合、`head == tail && runnext == 0`という条件で、キューが本当に空であるかを判断します。`head == tail`はメインキュー配列が空であることを意味し、`runnext == 0`は`runnext`スロットも空であることを意味します。両方が真であれば、キュー全体が空であると結論付けられます。

この「再試行ループ」と「一貫性チェック」の組み合わせにより、`runqempty`は競合状態の影響を受けずに、常に正確なキューの空状態を報告できるようになりました。

*   **イテレーション数**: デフォルトで10万回のイテレーションを実行し、競合状態が発生する確率を高めています。`testing.Short()`が有効な場合は100回に減らされます。

## 変更の背景

Goランタイムのスケジューラは、利用可能なプロセッサ（P）上で実行可能なゴルーチン（G）を効率的にスケジュールすることで、CPUリソースを最大限に活用しようとします。このプロセスにおいて、特定のプロセッサ（P）に割り当てられたローカル実行キュー（run queue）が空であるかどうかを判断する`runqempty`関数は非常に重要な役割を担っています。

問題は、`runnext`という最適化が導入されたことで発生しました。`runnext`は、ローカル実行キューの先頭にあるゴルーチンを特別なスロットに保持することで、キューからの取り出しを高速化するメカニズムです。しかし、この`runnext`の存在が`runqempty`の判断を複雑にし、競合状態を引き起こす可能性がありました。

コミットメッセージで説明されているシナリオは以下の通りです。

1.  **初期状態**: Pのローカル実行キューはメイン配列が空で、`runnext`にG1がある状態。
2.  **`runqempty`の最初のチェック**: `runqempty`関数が実行され、メインのキュー配列が空であることを確認する。
3.  **プリエンプション**: `runqempty`が`_p_.runnext == 0`をチェックする前に、スケジューラによってプリエンプト（中断）される。
4.  **他のPによる操作**: その間に、キューのオーナー（P）が別のゴルーチン（G2）をキューにプッシュする。この際、`runnext`スロットにあったG1がメインのキュー配列に移動される（evictされる）。
5.  **他のPによる操作（続き）**: その後、キューのオーナーはG1をキューからポップ（取り出し）する。
6.  **`runqempty`の再開と誤判断**: `runqempty`が実行を再開し、`runnext`スロットが空になっていることを確認する。
7.  **結果**: `runqempty`は、メインキューも`runnext`も空であると判断し、誤って「キューが空である」と報告してしまう。しかし、実際にはステップ4の間にキューは空ではなかった。

この結果、実際には実行可能なゴルーチンが存在するにもかかわらず、スケジューラがキューを空だと誤認し、アイドル状態のPが存在するにもかかわらずゴルーチンをスケジュールできないという「CPU underutilization（CPU利用率の低下）」が発生していました。これは、システムのパフォーマンスに直接影響を与える深刻な問題でした。

## 前提知識の解説

### Goランタイムスケジューラ (M, P, G)

Goのスケジューラは、M（Machine/OSスレッド）、P（Processor/論理プロセッサ）、G（Goroutine）という3つのエンティティを中心に動作します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが記述する並行処理の最小単位であり、OSスレッドよりもはるかに軽量です。
*   **M (Machine)**: OSスレッドに対応します。Goのコードを実行する実際のOSスレッドです。複数のMが存在し、それぞれがPにアタッチされてGを実行します。
*   **P (Processor)**: 論理プロセッサを表します。MとGの仲介役であり、実行可能なGを保持するローカル実行キュー（run queue）を持ちます。`GOMAXPROCS`環境変数によってPの数が決定され、通常はCPUコア数に一致します。MはPにアタッチされ、Pのローカル実行キューからGを取り出して実行します。

### ローカル実行キュー (`runq`) と `runnext`

各Pは、自身が実行すべきゴルーチンを格納するローカル実行キュー（`runq`）を持っています。これは通常、リングバッファとして実装されています。
`runnext`は、このローカル実行キューの最適化された部分です。キューの先頭にあるゴルーチンを一時的に保持するための単一のスロットであり、キューのメイン配列にアクセスするよりも高速にゴルーチンを取り出せるように設計されています。これにより、スケジューリングのレイテンシを削減し、スループットを向上させることが期待されます。

### `runqempty` 関数の目的

`runqempty`関数は、特定のPのローカル実行キューが現在空であるかどうかを判断するために使用されます。スケジューラは、この情報に基づいて、Pがアイドル状態であると判断し、他のPからゴルーチンを盗む（work stealing）必要があるか、あるいは新しいゴルーチンを生成して実行する必要があるかなどを決定します。したがって、この関数が正確な情報を返すことは、スケジューラの効率とシステムの応答性にとって極めて重要です。

### アトミック操作の重要性

並行プログラミングにおいて、複数のゴルーチンやOSスレッドが共有データに同時にアクセスする場合、競合状態（race condition）が発生する可能性があります。これを防ぐために、アトミック操作が用いられます。アトミック操作は、その操作が不可分（atomic）であることを保証し、他のスレッドからの干渉なしに完了することを保証します。これにより、データの整合性が保たれ、予期せぬ動作を防ぐことができます。Goランタイムでは、`sync/atomic`パッケージや、ランタイム内部で直接アトミック命令を使用することで、このような操作を実現しています。

## 技術的詳細

### 以前の `runqempty` の実装

変更前の`runqempty`関数は、非常にシンプルでした。

```go
func runqempty(_p_ *p) bool {
	return _p_.runqhead == _p_.runqtail && _p_.runnext == 0
}
```

この実装は、ローカル実行キューのヘッドとテールが一致し、かつ`runnext`スロットが空（`0`はnilを表す）であれば、キューが空であると判断していました。しかし、これは`runnext`の導入によって発生した競合状態を考慮していませんでした。具体的には、`_p_.runqhead == _p_.runqtail`のチェックと`_p_.runnext == 0`のチェックの間に、他のM/Pがキューの状態を変更する可能性がありました。

### `runnext`による競合状態の具体的なメカニズム

コミットメッセージで述べられている競合状態は、以下のステップで発生します。

1.  **初期状態**: Pのローカル実行キューはメイン配列が空で、`runnext`にG1がある状態。
    *   `_p_.runqhead == _p_.runqtail` は `true`。
    *   `_p_.runnext` は `G1` (非nil)。
2.  **`runqempty`の最初のチェック**: `runqempty`が`_p_.runqhead == _p_.runqtail`をチェックし、`true`を得る。
3.  **プリエンプション**: `runqempty`が`_p_.runnext == 0`をチェックする前に、スケジューラによってプリエンプトされる。
4.  **他のPによる操作**: 別のPがこのPのキューにG2をプッシュする。この操作により、`runnext`にあったG1がメインキュー配列に移動（evict）され、`runnext`は空になる。その後、そのPがG1をメインキューからポップして実行する。
    *   この時点で、`_p_.runqhead`と`_p_.runqtail`は再び一致する可能性がある（G1がevictされ、G1がポップされたため）。
    *   `_p_.runnext`は`0`（nil）になる。
5.  **`runqempty`の再開と誤判断**: `runqempty`が実行を再開し、`_p_.runnext == 0`をチェックし、`true`を得る。
6.  **結果**: `runqempty`は`_p_.runqhead == _p_.runqtail`と`_p_.runnext == 0`の両方が`true`であると判断し、キューが空であると誤って報告する。しかし、実際にはステップ4の間にキューは空ではなかった。

この問題は、複数のフィールド（`runqhead`, `runqtail`, `runnext`）を個別に読み取ることによって発生する「スナップショットの不整合」に起因します。これらのフィールドがアトミックに、かつ一貫した状態で読み取られない限り、中間状態での変更によって誤った判断が下される可能性があります。

### 新しい `runqempty` の実装による解決策

新しい`runqempty`関数は、この競合状態を解決するために、ループとアトミック操作を導入しています。

```go
func runqempty(_p_ *p) bool {
	// Defend against a race where 1) _p_ has G1 in runqnext but runqhead == runqtail,
	// 2) runqput on _p_ kicks G1 to the runq, 3) runqget on _p_ empties runnext.
	// Simply observing that runqhead == runqtail and then observing that runnext == nil
	// does not mean the queue is empty.
	for {
		head := atomic.Load(&_p_.runqhead)
		tail := atomic.Load(&_p_.runqtail)
		runnext := atomic.Loaduintptr((*uintptr)(unsafe.Pointer(&_p_.runnext)))
		if tail == atomic.Load(&_p_.runqtail) { // tailが読み取り中に変更されていないことを確認
			return head == tail && runnext == 0
		}
	}
}
```

この新しい実装のポイントは以下の通りです。

1.  **ループの導入**: `for {}`ループにより、キューの状態が安定するまで（または一貫したスナップショットが取得できるまで）繰り返しチェックを行います。
2.  **アトミックロード**: `atomic.Load`および`atomic.Loaduintptr`を使用して、`runqhead`, `runqtail`, `runnext`の値をアトミックに読み取ります。これにより、部分的な読み取りによるデータ破損を防ぎます。
3.  **一貫性チェック**: `if tail == atomic.Load(&_p_.runqtail)`という条件が追加されています。これは、`head`と`tail`を読み取った後に、再度`tail`をアトミックに読み取り、最初の`tail`の値と比較することで、読み取り中に`tail`が変更されていないことを確認するものです。もし`tail`が変更されていれば、それはキューの状態が変化したことを意味するため、ループを続行して再度すべての値を読み直します。
4.  **正確な判断**: `tail`の値が一貫していることが確認できた場合のみ、`head == tail && runnext == 0`という条件でキューが本当に空であるかを判断します。これにより、`head`, `tail`, `runnext`の3つの値が同時に一貫した状態を反映していることが保証され、誤った「空」の報告を防ぎます。

この変更により、`runqempty`は「決して誤ってtrueを返さない」という保証を持つようになり、スケジューラの正確性とCPU利用率の向上が図られました。

		tail := atomic.Load(&_p_.runqtail) // (3) tailをアトミックに読み込む
		runnext := atomic.Loaduintptr((*uintptr)(unsafe.Pointer(&_p_.runnext))) // (4) runnextをアトミックに読み込む
		if tail == atomic.Load(&_p_.runqtail) { // (5) tailが読み取り中に変更されていないことを確認
			return head == tail && runnext == 0 // (6) 一貫性が確認できたら最終判断
		}
	}
}
```

1.  **無限ループ**: `for {}`ループは、`head`, `tail`, `runnext`の読み取りが、その間にキューの状態が変更されていない一貫したスナップショットを捉えるまで繰り返すことを保証します。
2.  **`head`のアトミックロード**: `_p_.runqhead`の値をアトミックに読み込みます。これはキューの先頭位置を示します。
3.  **`tail`のアトミックロード**: `_p_.runqtail`の値をアトミックに読み込みます。これはキューの末尾位置を示します。
4.  **`runnext`のアトミックロード**: `_p_.runnext`の値をアトミックに読み込みます。`unsafe.Pointer`を使用しているのは、`runnext`が`*g`型であり、`atomic.Loaduintptr`が`uintptr`を期待するためです。`0`はnilポインタを表します。
5.  **一貫性チェック**: ここが最も重要な部分です。`tail`を再度アトミックに読み込み、最初に読み込んだ`tail`の値と比較します。
    *   もし`tail`の値が一致すれば、`head`と`tail`の読み取り中にキューの末尾が変更されていないことを意味します。この場合、`head`, `tail`, `runnext`の3つの値は、ほぼ同時に取得された一貫したスナップショットであると見なすことができます。
    *   もし`tail`の値が一致しなければ、`head`と`tail`の読み取りの間にキューに要素が追加されたか、削除されたか、あるいは`runnext`がメインキューにevictされたかなどの変更があったことを意味します。この場合、現在のスナップショットは不整合であるため、ループの先頭に戻り、再度すべての値を読み直します。
6.  **最終判断**: `tail`の一貫性が確認できた場合、`head == tail && runnext == 0`という条件で、キューが本当に空であるかを判断します。`head == tail`はメインキュー配列が空であることを意味し、`runnext == 0`は`runnext`スロットも空であることを意味します。両方が真であれば、キュー全体が空であると結論付けられます。

この「再試行ループ」と「一貫性チェック」の組み合わせにより、`runqempty`は競合状態の影響を受けずに、常に正確なキューの空状態を報告できるようになりました。

### テストコードの解説

`src/runtime/export_test.go` に追加された `RunSchedLocalQueueEmptyTest` と、それを呼び出す `src/runtime/proc_test.go` の `TestSchedLocalQueueEmpty` は、この修正の正しさを検証するために設計されています。

**`RunSchedLocalQueueEmptyTest` のロジック:**

このテストは、`runqempty`が誤ってtrueを返すような競合状態を意図的に作り出そうとします。

1.  **PとGの準備**: テスト用のP（プロセッサ）と2つのG（ゴルーチン）を準備します。
2.  **ループ実行**: `iters`回（デフォルトで10万回）繰り返します。
3.  **`runqput`でG0を配置**: `runqput`を使ってG0をPのキューに配置します。`next0`フラグによって`runnext`に直接置かれるか、メインキューに置かれるかが制御されます。
4.  **並行ゴルーチン**: 新しいゴルーチンを起動します。このゴルーチンは以下の処理を行います。
    *   `ready`カウンタをインクリメントし、両方のゴルーチンが準備できるまでスピン待機します。
    *   `runqempty(p)`を呼び出し、Pのキューが空であるかをチェックします。
    *   もし`runqempty`が`true`を返した場合、それは誤った報告であるため、`throw("queue is empty")`でパニックを引き起こします。
    *   結果を`done`チャネルに送信します。
5.  **メインゴルーチン**: メインのテストゴルーチンは以下の処理を行います。
    *   `ready`カウンタをインクリメントし、両方のゴルーチンが準備できるまでスピン待機します。
    *   `runqput`を使ってG1をPのキューに配置します。`next1`フラグによって`runnext`に直接置かれるか、メインキューに置かれるかが制御されます。
    *   `runqget(p)`を呼び出し、キューからゴルーチンを一つ取り出します。これにより、キューの状態が変化し、競合状態が発生しやすくなります。
    *   並行ゴルーチンからの結果を`done`チャネルから受け取ります。
    *   再度`runqget(p)`を呼び出し、残りのゴルーチンを取り出します。
6.  **`next0`と`next1`の組み合わせ**: `next0`と`next1`は、`i`の偶奇によって異なる値が設定され、`runnext`スロットとメインキュー配列へのゴルーチンの配置パターンを変化させ、様々な競合状態のシナリオを網羅しようとします。

**`TestSchedLocalQueueEmpty` の設定:**

*   **マルチプロセッサ環境での実行**: `runtime.NumCPU() == 1`の場合はテストをスキップします。これは、競合状態が複数のCPU（P）が同時にキューにアクセスする状況で発生しやすいためです。
*   **`GOMAXPROCS`の設定**: `runtime.GOMAXPROCS(runtime.GOMAXPROCS(4))`により、`GOMAXPROCS`を4に設定し、複数のPが動作する環境をシミュレートします。
*   **GCの無効化**: `debug.SetGCPercent(debug.SetGCPercent(-1))`により、テスト中に強制GCが発生しないようにします。これは、テスト内のスピン待機中にGCが介入するとデッドロックを引き起こす可能性があるためです。
*   **イテレーション数**: デフォルトで10万回のイテレーションを実行し、競合状態が発生する確率を高めています。`testing.Short()`が有効な場合は100回に減らされます。

これらのテストは、修正された`runqempty`関数が、様々な条件下で誤った空状態を報告しないことを確認するために不可欠です。

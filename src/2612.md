## 変更の背景

Go言語のシフト演算子（`<<`、`>>`）は、左オペランドを右オペランドで指定されたビット数だけシフトします。Goの仕様では、シフト演算の右オペランドは符号なし整数型であるか、符号なし整数型に変換可能な型なし定数である必要があります。このコミット以前のGoコンパイラ（`gc`）には、この仕様に反する不正なシフト操作が型チェックをすり抜けてしまうバグが存在していました。

コミットメッセージに示されている例は以下の通りです。
*   `x << "a"`: 文字列型をシフト量として使用しようとするケース。これは明らかに不正であり、コンパイル時にエラーとなるべきです。
*   `1 << int(2)`: `int(2)`のように明示的に型付けされた`int`型をシフト量として使用しようとするケース。Goの仕様では、シフト量は符号なし整数型である必要があるため、これも不正な操作です。

これらのバグは、コンパイラが不正なコードを許容し、予期せぬ実行時エラーや未定義の動作を引き起こす可能性がありました。そのため、コンパイラの堅牢性を高め、Go言語の仕様に厳密に従うように型チェックロジックを修正する必要がありました。

## 前提知識の解説

### Goコンパイラ (`gc`)

Go言語の公式コンパイラは`gc`と呼ばれ、`src/cmd/gc`ディレクトリにそのソースコードが格納されています。`gc`は、Goのソースコードを機械語に変換する役割を担い、その過程で字句解析、構文解析、型チェック、最適化、コード生成などのフェーズを実行します。

### 型チェック (Type Checking)

型チェックはコンパイラの重要なフェーズの一つで、プログラム内の各操作が型の規則に準拠しているかを確認します。これにより、型が合わない操作（例: 整数と文字列の加算）による実行時エラーを防ぎ、プログラムの信頼性を高めます。Go言語は静的型付け言語であり、コンパイル時に厳格な型チェックが行われます。

### シフト演算子 (`<<`, `>>`)

Go言語におけるシフト演算子は、ビット単位の操作を行います。
*   `a << b`: `a`を`b`ビットだけ左にシフトします。
*   `a >> b`: `a`を`b`ビットだけ右にシフトします。

Goの仕様では、シフト演算の右オペランド（シフト量）には以下の制約があります。
1.  **型なし定数**: シフト量は型なし定数である場合、その値は負であってはならず、また、左オペランドの型が表現できる最大ビット数を超えるものであってはなりません。
2.  **符号なし整数型**: シフト量は型付きの値である場合、その型は符号なし整数型（`uint`、`uint8`、`uint16`、`uint32`、`uint64`、`uintptr`）でなければなりません。符号付き整数型（`int`など）は許可されません。

### 抽象構文木 (AST) と `Node`

コンパイラはソースコードを解析し、プログラムの構造を抽象構文木（Abstract Syntax Tree, AST）として内部的に表現します。ASTの各要素は`Node`として表現され、変数、定数、演算子、関数呼び出しなどが含まれます。コンパイラはASTをトラバース（走査）しながら、型チェックやコード生成などの処理を行います。

### `src/cmd/gc/const.c`

このファイルは、Goコンパイラにおいて定数式の評価と型チェックを担当する部分です。コンパイル時に値が確定する定数（リテラルや定数式）の処理、特にその型が正しいかどうかの検証が行われます。

### `src/cmd/gc/walk.c`

このファイルは、GoコンパイラにおいてASTの「ウォーク」（走査）と、それに伴う様々な処理（型チェック、最適化、中間コード生成など）を担当する部分です。プログラムの構造を深く理解し、各ノードに対して適切な処理を適用します。

### `yyerror`

`yyerror`は、Goコンパイラがコンパイルエラーを報告するために使用する内部関数です。不正な構文や型エラーが検出された際に呼び出され、エラーメッセージを出力します。

### `defaultlit`

`defaultlit`は、型なしリテラル（例: `10`、`"hello"`）に対して、文脈に応じてデフォルトの型を割り当てる処理を行う関数です。例えば、`10`は`int`型、`"hello"`は`string`型にデフォルトで型付けされます。シフト演算の文脈では、右オペランドが型なし定数の場合、`uint`型にデフォルトで型付けを試みることがあります。

### `issigned` と `isint`

これらはGoコンパイラの内部で型に関する情報を保持するためのメカニズムです。
*   `issigned[type.etype]`: ある型が符号付き整数型であるかを示すフラグ（または関数）。
*   `isint[type.etype]`: ある型が整数型であるかを示すフラグ（または関数）。
`etype`は、Goコンパイラが内部的に型を識別するために使用する列挙型のようなものです。

## 技術的詳細

このコミットは、`src/cmd/gc/const.c`と`src/cmd/gc/walk.c`の2つのファイルにわたって変更を加えています。主な変更点は、シフト演算の右オペランドの型チェックを強化することです。

### `src/cmd/gc/const.c` の変更

`const.c`では、定数式の評価を行う`evconst`関数と、単項演算子を扱う`unary`関数が修正されています。

1.  **`evconst`関数におけるシフト演算の右オペランドチェックの強化**:
    `evconst`関数内のシフト演算子（`OLSH`、`ORSH`）を処理する`switch`ケースにおいて、右オペランド（`nr`）の型チェックが追加されました。
    ```diff
    --- a/src/cmd/gc/const.c
    +++ b/src/cmd/gc/const.c
    @@ -345,6 +345,8 @@ evconst(Node *n)
     		// right must be unsigned.
     		// left can be ideal.
     		defaultlit(nr, types[TUINT]);
    +		if(nr->type && (issigned[nr->type->etype] || !isint[nr->type->etype]))
    +			goto illegal;
     		break;
     	}
    ```
    この変更により、`defaultlit(nr, types[TUINT])`で右オペランドを`uint`型にデフォルト型付けしようとした後、その結果の型が`nil`でなく、かつ**符号付き整数型であるか、または整数型でない場合**（`issigned[nr->type->etype]`が真、または`!isint[nr->type->etype]`が真）、`illegal`ラベルにジャンプしてエラーを報告するようになりました。これにより、`x << "a"`のようなケースで、`"a"`が整数型でないためエラーとして検出されます。また、`1 << int(2)`のようなケースで、`int(2)`が符号付き整数型であるためエラーとして検出されます。

2.  **エラー報告の重複防止**:
    `evconst`関数と`unary`関数内のエラー報告ロジックが改善され、既にエラーが報告されている場合には`yyerror`を再度呼び出さないようになりました。
    ```diff
    --- a/src/cmd/gc/const.c
    +++ b/src/cmd/gc/const.c
    @@ -367,9 +369,11 @@ evconst(Node *n)
     	switch(TUP(n->op, v.ctype)) {
     	default:
     	illegal:
    -		yyerror("illegal constant expression %T %O %T",
    -			nl->type, n->op, nr->type);
    -		n->diag = 1;
    +		if(!n->diag) {
    +			yyerror("illegal constant expression: %T %O %T",
    +				nl->type, n->op, nr->type);
    +			n->diag = 1;
    +		}
     		return;
    ```
    `n->diag`フラグは、そのノードに対して既に診断メッセージ（エラーなど）が発行されたことを示します。このチェックにより、同じ問題に対して複数のエラーメッセージが出力されるのを防ぎ、コンパイラのエラー報告をよりクリーンにします。

### `src/cmd/gc/walk.c` の変更

`walk.c`では、ASTを走査する`walk`関数内のシフト演算子を処理する部分が修正されています。

1.  **シフト演算の右オペランドチェックの強化**:
    シフト演算子（`OLSH`、`ORSH`）を処理する`switch`ケースにおいて、右オペランドの型チェックが強化されました。
    ```diff
    --- a/src/cmd/gc/walk.c
    +++ b/src/cmd/gc/walk.c
    @@ -704,7 +704,7 @@ loop:
     		defaultlit(n->right, types[TUINT]);
     		if(n->left->type == T || n->right->type == T)
     			goto ret;
    -		if(issigned[n->right->type->etype])
    +		if(issigned[n->right->type->etype] || !isint[n->right->type->etype])
     			goto badt;
     		// check of n->left->type happens in second switch.
     		break;
    ```
    ここでも`const.c`と同様に、`issigned[n->right->type->etype]`（符号付き整数型である）に加えて、`!isint[n->right->type->etype]`（整数型でない）という条件が追加されました。これにより、`walk`フェーズでも、シフト量の右オペランドが符号付き整数型であるか、またはそもそも整数型でない場合に`badt`ラベルにジャンプしてエラーを報告するようになります。これは、`const.c`でのチェックが定数式に特化しているのに対し、`walk.c`ではより一般的な式に対する型チェックをカバーします。

## コアとなるコードの解説

### `src/cmd/gc/const.c` の変更解説

`evconst`関数は定数式の評価を担当します。シフト演算子の場合、右オペランドは符号なし整数型である必要があります。
元のコードでは、`defaultlit(nr, types[TUINT])`で右オペランドを`uint`型にデフォルト型付けしようとしますが、その後のチェックが不十分でした。
追加された`if`文 `if(nr->type && (issigned[nr->type->etype] || !isint[nr->type->etype])) goto illegal;` は、以下の条件のいずれかが満たされた場合にエラー（`illegal`）にジャンプします。
1.  `nr->type`が`nil`でない（つまり、型付けが成功したか、既に型を持っている）。
2.  `nr->type`が符号付き整数型である（`issigned[nr->type->etype]`が真）。例: `int(2)`
3.  `nr->type`が整数型でない（`!isint[nr->type->etype]`が真）。例: `"a"`

これにより、`x << "a"`や`1 << int(2)`のような不正な定数シフト式がコンパイル時に正しくエラーとして検出されるようになります。

また、エラー報告の重複防止のための`if(!n->diag)`チェックは、コンパイラが同じノードに対して複数のエラーメッセージを出力するのを防ぎ、ユーザーにとってより分かりやすいエラー報告を提供します。

### `src/cmd/gc/walk.c` の変更解説

`walk`関数はASTを走査し、より広範な型チェックや変換を行います。ここでのシフト演算子の処理も`const.c`と同様に、右オペランドの型チェックを強化しています。
変更前は`if(issigned[n->right->type->etype]) goto badt;`というチェックのみで、右オペランドが符号付き整数型の場合にエラーとしていました。
変更後は`if(issigned[n->right->type->etype] || !isint[n->right->type->etype]) goto badt;`となり、右オペランドが符号付き整数型であるか、または整数型でない場合にもエラー（`badt`）にジャンプするようになりました。
この変更により、定数式ではないシフト操作においても、右オペランドがGoの仕様に準拠しているかどうかが厳密にチェックされるようになります。例えば、変数`s string = "a"`があるとして、`x << s`のような式もここで捕捉される可能性があります。

これらの変更は、Goコンパイラの型チェックの厳密性を高め、Go言語のシフト演算子の仕様への準拠を強化するものです。

コンパイラはソースコードを解析し、プログラムの構造を抽象構文木（Abstract Syntax Tree, AST）として内部的に表現します。ASTの各要素は`Node`として表現され、変数、定数、演算子、関数呼び出しなどが含まれます。コンパイラはASTをトラバース（走査）しながら、型チェックやコード生成などの処理を行います。

### `src/cmd/gc/const.c`

このファイルは、Goコンパイラにおいて定数式の評価と型チェックを担当する部分です。コンパイル時に値が確定する定数（リテラルや定数式）の処理、特にその型が正しいかどうかの検証が行われます。

### `src/cmd/gc/walk.c`

このファイルは、GoコンパイラにおいてASTの「ウォーク」（走査）と、それに伴う様々な処理（型チェック、最適化、中間コード生成など）を担当する部分です。プログラムの構造を深く理解し、各ノードに対して適切な処理を適用します。

### `yyerror`

`yyerror`は、Goコンパイラがコンパイルエラーを報告するために使用する内部関数です。不正な構文や型エラーが検出された際に呼び出され、エラーメッセージを出力します。

### `defaultlit`

`defaultlit`は、型なしリテラル（例: `10`、`"hello"`）に対して、文脈に応じてデフォルトの型を割り当てる処理を行う関数です。例えば、`10`は`int`型、`"hello"`は`string`型にデフォルトで型付けされます。シフト演算の文脈では、右オペランドが型なし定数の場合、`uint`型にデフォルトで型付けを試みることがあります。

### `issigned` と `isint`

これらはGoコンパイラの内部で型に関する情報を保持するためのメカニズムです。
*   `issigned[type.etype]`: ある型が符号付き整数型であるかを示すフラグ（または関数）。
*   `isint[type.etype]`: ある型が整数型であるかを示すフラグ（または関数）。
`etype`は、Goコンパイラが内部的に型を識別するために使用する列挙型のようなものです。

## 技術的詳細

このコミットは、`src/cmd/gc/const.c`と`src/cmd/gc/walk.c`の2つのファイルにわたって変更を加えています。主な変更点は、シフト演算の右オペランドの型チェックを強化することです。

### `src/cmd/gc/const.c` の変更

`const.c`では、定数式の評価を行う`evconst`関数と、単項演算子を扱う`unary`関数が修正されています。

1.  **`evconst`関数におけるシフト演算の右オペランドチェックの強化**:
    `evconst`関数内のシフト演算子（`OLSH`、`ORSH`）を処理する`switch`ケースにおいて、右オペランド（`nr`）の型チェックが追加されました。
    ```c
    		// right must be unsigned.
    		// left can be ideal.
    		defaultlit(nr, types[TUINT]);
    		if(nr->type && (issigned[nr->type->etype] || !isint[nr->type->etype]))
    			goto illegal;
    		break;
    ```
    この変更により、`defaultlit(nr, types[TUINT])`で右オペランドを`uint`型にデフォルト型付けしようとした後、その結果の型が`nil`でなく、かつ**符号付き整数型であるか、または整数型でない場合**（`issigned[nr->type->etype]`が真、または`!isint[nr->type->etype]`が真）、`illegal`ラベルにジャンプしてエラーを報告するようになりました。これにより、`x << "a"`のようなケースで、`"a"`が整数型でないためエラーとして検出されます。また、`1 << int(2)`のようなケースで、`int(2)`が符号付き整数型であるためエラーとして検出されます。

2.  **エラー報告の重複防止**:
    `evconst`関数と`unary`関数内のエラー報告ロジックが改善され、既にエラーが報告されている場合には`yyerror`を再度呼び出さないようになりました。
    ```c
    	illegal:
    		if(!n->diag) {
    			yyerror("illegal constant expression: %T %O %T",
    				nl->type, n->op, nr->type);
    			n->diag = 1;
    		}
    		return;
    ```
    `n->diag`フラグは、そのノードに対して既に診断メッセージ（エラーなど）が発行されたことを示します。このチェックにより、同じ問題に対して複数のエラーメッセージが出力されるのを防ぎ、コンパイラのエラー報告をよりクリーンにします。

### `src/cmd/gc/walk.c` の変更

`walk.c`では、ASTを走査する`walk`関数内のシフト演算子を処理する部分が修正されています。

1.  **シフト演算の右オペランドチェックの強化**:
    シフト演算子（`OLSH`、`ORSH`）を処理する`switch`ケースにおいて、右オペランドの型チェックが強化されました。
    ```c
    		defaultlit(n->right, types[TUINT]);
    		if(n->left->type == T || n->right->type == T)
    			goto ret;
    		if(issigned[n->right->type->etype] || !isint[n->right->type->etype])
    			goto badt;
    		// check of n->left->type happens in second switch.
    		break;
    ```
    ここでも`const.c`と同様に、`issigned[n->right->type->etype]`（符号付き整数型である）に加えて、`!isint[n->right->type->etype]`（整数型でない）という条件が追加されました。これにより、`walk`フェーズでも、シフト量の右オペランドが符号付き整数型であるか、またはそもそも整数型でない場合にもエラー（`badt`）にジャンプするようになります。これは、`const.c`でのチェックが定数式に特化しているのに対し、`walk.c`ではより一般的な式に対する型チェックをカバーします。

これらの変更は、Goコンパイラの型チェックの厳密性を高め、Go言語のシフト演算子の仕様への準拠を強化するものです。

## コアとなるコードの解説

### `src/cmd/gc/const.c` の変更解説

`evconst`関数は定数式の評価を担当します。シフト演算子の場合、右オペランドは符号なし整数型である必要があります。
元のコードでは、`defaultlit(nr, types[TUINT])`で右オペランドを`uint`型にデフォルト型付けしようとしますが、その後のチェックが不十分でした。
追加された`if`文 `if(nr->type && (issigned[nr->type->etype] || !isint[nr->type->etype])) goto illegal;` は、以下の条件のいずれかが満たされた場合にエラー（`illegal`）にジャンプします。
1.  `nr->type`が`nil`でない（つまり、型付けが成功したか、既に型を持っている）。
2.  `nr->type`が符号付き整数型である（`issigned[nr->type->etype]`が真）。例: `int(2)`
3.  `nr->type`が整数型でない（`!isint[nr->type->etype]`が真）。例: `"a"`

これにより、`x << "a"`や`1 << int(2)`のような不正な定数シフト式がコンパイル時に正しくエラーとして検出されるようになります。

また、エラー報告の重複防止のための`if(!n->diag)`チェックは、コンパイラが同じノードに対して複数のエラーメッセージを出力するのを防ぎ、ユーザーにとってより分かりやすいエラー報告を提供します。

### `src/cmd/gc/walk.c` の変更解説

`walk`関数はASTを走査し、より広範な型チェックや変換を行います。ここでのシフト演算子の処理も`const.c`と同様に、右オペランドの型チェックを強化しています。
変更前は`if(issigned[n->right->type->etype]) goto badt;`というチェックのみで、右オペランドが符号付き整数型の場合にエラーとしていました。
変更後は`if(issigned[n->right->type->etype] || !isint[n->right->type->etype]) goto badt;`となり、右オペランドが符号付き整数型であるか、または整数型でない場合にもエラー（`badt`）にジャンプするようになりました。
この変更により、定数式ではないシフト操作においても、右オペランドがGoの仕様に準拠しているかどうかが厳密にチェックされるようになります。例えば、変数`s string = "a"`があるとして、`x << s`のような式もここで捕捉される可能性があります。

これらの変更は、Goコンパイラの型チェックの厳密性を高め、Go言語のシフト演算子の仕様への準拠を強化するものです。

# [インデックス 24734] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http/httputil` パッケージ内の `ReverseProxy` において、リクエストボディが `nil` の場合に発生していたリグレッションを修正するものです。以前のバージョンでは暗黙的に動作していた `nil` ボディのリクエストが、ある時点から機能しなくなったため、これを再度許容するように変更が加えられました。

## 元コミット内容

`net/http/httputil`: `ReverseProxy` で `nil` のリクエストボディを許可する。

`nil` ボディを持つリクエストを受け入れることは、明示的にサポートされていたわけではないが、過去には偶然動作していた。

ほとんどの場合、これは問題にならない。なぜなら、通常はサーバーの受信リクエストを `ReverseProxy` の `ServeHTTP` メソッドに渡すためであり、受信サーバーリクエストは `nil` でないボディを持つことが保証されているからだ。

それでも、これはリグレッションであるため、修正する。

Fixes #12344

## 変更の背景

この変更の背景には、`net/http/httputil.ReverseProxy` が処理するHTTPリクエストにおいて、リクエストボディが `nil` である場合の挙動に関するリグレッション（機能退行）がありました。

GoのHTTPサーバーが受信するリクエスト (`*http.Request`) は、その `Body` フィールドが `io.ReadCloser` 型であり、通常は `nil` になることはありません。たとえボディがないGETリクエストなどであっても、`io.NopCloser(bytes.NewReader(nil))` のような空の `io.ReadCloser` が設定されます。

しかし、`ReverseProxy` を直接利用するアプリケーションコードやテストコードの中には、明示的に `http.Request.Body` を `nil` に設定してリクエストを生成し、それを `ReverseProxy` に渡すケースが存在しました。コミットメッセージによると、これは「明示的にサポートされていたわけではないが、過去には偶然動作していた」とのことです。

Go 1.5の変更（具体的には `io.Reader` の実装に関する内部的な変更）により、この「偶然動作していた」挙動が壊れ、`nil` ボディのリクエストが `ReverseProxy` で正しく処理されなくなりました。これは、`ReverseProxy` の内部でリクエストボディを処理する `runOnFirstRead` という構造体が、`nil` の `io.Reader` を適切に扱えなくなったためです。

このリグレッションは、Issue #12344 として報告され、本コミットによって修正されることになりました。修正の目的は、過去の挙動（`nil` ボディのリクエストが動作すること）を復元し、後方互換性を維持することです。

## 前提知識の解説

### `net/http/httputil.ReverseProxy`

`net/http/httputil` パッケージは、HTTPユーティリティ機能を提供します。その中でも `ReverseProxy` は、リバースプロキシサーバーを構築するための主要なコンポーネントです。リバースプロキシは、クライアントからのリクエストを受け取り、それを別のバックエンドサーバーに転送し、バックエンドからのレスポンスをクライアントに返す役割を担います。これにより、ロードバランシング、SSL終端、キャッシュ、セキュリティ強化などの機能を実現できます。

`ReverseProxy` は `http.Handler` インターフェースを実装しており、`ServeHTTP(w http.ResponseWriter, r *http.Request)` メソッドを通じてリクエストを処理します。このメソッド内で、受信した `*http.Request` オブジェクトを解析し、必要に応じて変更を加え、ターゲットとなるバックエンドサーバーに転送します。

### `io.Reader` インターフェース

Go言語の `io` パッケージは、I/Oプリミティブを提供します。`io.Reader` インターフェースは、データを読み出すための基本的なインターフェースであり、次のように定義されています。

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```

`Read` メソッドは、`p` スライスに最大 `len(p)` バイトのデータを読み込み、読み込んだバイト数 `n` とエラー `err` を返します。
- `n > 0` の場合、`p[:n]` にデータが格納されます。
- `n == 0` の場合、データが読み込まれなかったことを意味します。これは、エラーが発生したか、または読み込むデータがもうない（ファイルの終端など）ことを示します。
- `err == io.EOF` は、ストリームの終端に達し、それ以上データがないことを示します。`n` が `0` でない場合でも `io.EOF` が返されることがありますが、これは最後の `Read` 呼び出しで一部のデータが読み込まれ、同時に終端に達したことを意味します。

HTTPリクエストのボディは、この `io.Reader` インターフェース（実際には `io.ReadCloser`）として扱われます。これにより、ボディのデータをストリームとして効率的に読み込むことができます。

### HTTPリクエストボディの扱い

HTTPリクエストにおいて、`POST` や `PUT` のようなメソッドでは、クライアントがサーバーにデータを送信するためにリクエストボディを使用します。`GET` や `HEAD` のようなメソッドでは、通常リクエストボディは存在しません。

Goの `net/http` パッケージでは、`http.Request` 構造体の `Body` フィールドがリクエストボディを表します。このフィールドは `io.ReadCloser` 型であり、`io.Reader` と `io.Closer` の両方のインターフェースを満たします。

```go
type Request struct {
    // ...
    Body io.ReadCloser
    // ...
}
```

サーバーが受信するリクエストの場合、`Body` フィールドは常に `nil` ではない `io.ReadCloser` の実装を持ちます。ボディがないリクエストの場合でも、`Read` メソッドがすぐに `(0, io.EOF)` を返すような空のリーダーが設定されます。しかし、手動で `http.Request` を構築する際には、`Body` フィールドを `nil` に設定することが可能です。このコミットは、その `nil` のケースを `ReverseProxy` が適切に処理できるようにするためのものです。

## 技術的詳細

このリグレッションは、`ReverseProxy` の内部で使用される `runOnFirstRead` というヘルパーストラクトの挙動に起因していました。`runOnFirstRead` は、`io.Reader` をラップし、最初の `Read` 呼び出し時に一度だけ特定の関数 (`fn`) を実行するためのものです。これは、リクエストボディの読み込みが実際に開始される直前に、何らかの初期化処理（例えば、リクエストボディのコピーを開始するなど）を行いたい場合に便利です。

`runOnFirstRead` の定義は以下のようになっています（変更前）。

```go
type runOnFirstRead struct {
    io.Reader

    fn func() // Run before first Read, then set to nil
}
```

そして、その `Read` メソッドは以下のようでした（変更前）。

```go
func (c *runOnFirstRead) Read(bs []byte) (int, error) {
    if c.fn != nil {
        c.fn()
        c.fn = nil
    }
    return c.Reader.Read(bs) // ここで c.Reader が nil だとパニック
}
```

問題は、`runOnFirstRead` の `io.Reader` フィールドが `nil` の場合、`c.Reader.Read(bs)` を呼び出すと、`nil` ポインタに対するメソッド呼び出しとなり、ランタイムパニックが発生することでした。

Go 1.4以前では、`ReverseProxy` が `nil` のリクエストボディを受け取った場合でも、内部で `runOnFirstRead` の `io.Reader` フィールドが `nil` にならないような経路があったか、あるいは `nil` の `io.Reader` に対する `Read` 呼び出しが特定の状況下でパニックを引き起こさなかった可能性があります（これはGoの内部実装の詳細に依存します）。しかし、Go 1.5以降の変更により、この挙動が変わり、`nil` ボディのリクエストが `ReverseProxy` に渡されると、`runOnFirstRead.Read` 内でパニックが発生するようになりました。

このコミットは、`runOnFirstRead.Read` メソッドに `nil` チェックを追加することで、この問題を解決しています。`c.Reader` が `nil` の場合は、`io.EOF` を返すことで、ボディが空であることを明示的に示し、パニックを回避します。これは、空のボディを持つ `io.Reader` が通常行うべき挙動と一致します。

## コアとなるコードの解説

### `src/net/http/httputil/reverseproxy.go` の変更

1.  **`runOnFirstRead` 構造体のコメント更新**:
    `io.Reader` フィールドのコメントが `// optional; nil means empty body` と追記されました。これは、この `io.Reader` がオプションであり、`nil` の場合は空のボディを意味するという意図を明確にしています。

2.  **`runOnFirstRead.Read` メソッドの変更**:
    `Read` メソッドの冒頭に以下の `nil` チェックが追加されました。

    ```go
    	if c.Reader == nil {
    		return 0, io.EOF
    	}
    ```
    この変更がこのコミットの核心です。`runOnFirstRead` がラップしている `io.Reader` (`c.Reader`) が `nil` である場合、以前は `c.Reader.Read(bs)` が `nil` ポインタデリファレンスを引き起こしパニックとなっていました。この修正により、`c.Reader` が `nil` であれば、データは存在しないと判断し、`0` バイトを読み込み、`io.EOF` エラーを返します。これは、空の `io.Reader` が期待される挙動であり、パニックを回避しつつ、リクエストボディが空であることを正しく伝えます。

### `src/net/http/httputil/reverseproxy_test.go` の変更

1.  **`req` ヘルパー関数の追加**:
    テスト内でHTTPリクエストを文字列から簡単に構築するためのヘルパー関数 `req` が追加されました。これは `http.ReadRequest` を使用して、与えられた文字列から `*http.Request` オブジェクトを生成します。

2.  **`TestNilBody` テストケースの追加**:
    Issue #12344 を修正するために、`nil` ボディのリクエストを `ReverseProxy` が正しく処理できることを検証する新しいテストケース `TestNilBody` が追加されました。
    -   `backend` サーバーは、単純に "hi" という文字列を返すように設定されています。
    -   `frontend` サーバーは `ReverseProxy` を使用して `backend` にリクエストを転送します。
    -   重要なのは、`frontend` サーバー内で `ReverseProxy` に渡すリクエスト `r` の `r.Body` を明示的に `nil` に設定している点です。コミットメッセージにあるように、「これはGo 1.4以前では偶然動作していたので、引き続き動作させる」という意図を反映しています。
    -   最終的に、`frontend` サーバーへのリクエストが `backend` に転送され、"hi" というレスポンスが正しく返されることを検証しています。これにより、`nil` ボディのリクエストが `ReverseProxy` を介して正常に処理されることが保証されます。

これらの変更により、`ReverseProxy` は `nil` のリクエストボディを持つ `http.Request` を受け取った場合でも、パニックを起こすことなく、そのボディが空であると正しく解釈して処理を続行できるようになりました。

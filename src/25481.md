## 元コミット内容

このコミットは、Goランタイムにおける微小なアロケーション（tiny allocations）のファイナライズ処理とヒーププロファイリングに関する2つの問題を修正します。

1.  **ファイナライズの遅延**: 以前の実装では、オブジェクトに対して複数のファイナライザが設定されている場合、1つのファイナライザがキューに入れられると、そのGCサイクル中には同じオブジェクトの他のファイナライザはキューに入れられませんでした。これにより、最大16個のファイナライザが設定されている最悪のケースでは、ファイナライズが完了するまでに16回のGCサイクルが必要となり、`tinyfin.go`テストの誤動作や不安定性の原因となっていました。
2.  **ヒーププロファイルの歪み**: 微小なブロックがファイナライザとプロファイルの両方の特殊レコードを持つ場合、ファイナライザがキューに入れられてオブジェクトが生存状態に保たれる一方で、プロファイルレコードが誤って解放される可能性がありました。これにより、ヒーププロファイルが実際のライブメモリ量を過小評価し、歪んだ結果を示すことがありました。

これらの問題は、単一のオブジェクトに対するすべての特殊レコードを一度に分析することで解決されます。

さらに、`tinyfin`テストはより厳密になり、リアルタイムへの依存が排除されました。また、問題2を検証するための新しいテストが追加されました。この問題により、以前はヒーププロファイルがライブメモリの約半分を見落としていました。

## 変更の背景

Goのランタイムは、メモリ管理においてガベージコレクション（GC）とヒーププロファイリングという重要な機能を提供します。特に、小さなオブジェクト（微小なアロケーション）は効率的なメモリ利用のために特別な方法で扱われます。このコミットは、これらの微小なアロケーションに関連する既存のメカニズムに潜んでいた2つの深刻なバグに対処するために導入されました。

一つ目の問題は、オブジェクトに複数のファイナライザが設定されている場合のファイナライズ処理の非効率性です。Goのファイナライザは、オブジェクトがGCによって回収される直前に実行されるコールバック関数です。微小なアロケーションでは、複数の小さなオブジェクトが1つのメモリブロックにまとめられることがあります。このとき、もし同じメモリブロック内の異なるオフセットにあるオブジェクトにそれぞれファイナライザが設定されていると、以前の実装ではGCサイクルごとに1つのファイナライザしか処理されず、ファイナライズ完了までに多くのGCサイクルを要していました。これは、特にリソースの解放が遅延する原因となり、アプリケーションの動作に予期せぬ影響を与える可能性がありました。`tinyfin.go`テストがこの問題の不安定性を示していました。

二つ目の問題は、ファイナライザとヒーププロファイルの両方が設定された微小なアロケーションにおけるデータの一貫性の欠如です。ヒーププロファイリングは、アプリケーションがどのメモリをどれだけ使用しているかを分析するための重要なツールです。しかし、ファイナライザが設定されたオブジェクトは、GCによって回収されるまで「ライブ」として扱われ、そのメモリは解放されません。以前の実装では、このようなオブジェクトに対して、ファイナライザがオブジェクトをライブに保つ一方で、プロファイルレコードが誤って解放されてしまう可能性がありました。これにより、ヒーププロファイルが実際のメモリ使用量を正確に反映せず、開発者がメモリリークや非効率なメモリ使用を特定するのを妨げていました。コミットメッセージによると、この問題によりライブメモリの約半分が見落とされていたとのことです。

これらの問題は、Goアプリケーションの安定性、パフォーマンス分析の正確性、およびデバッグの効率性に直接影響を与えるため、修正が急務でした。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoランタイムの概念について解説します。

### Goのガベージコレクション (GC)

Goのガベージコレクションは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。

*   **マークフェーズ**: GCは、プログラムがアクセス可能なすべてのオブジェクト（ライブオブジェクト）を特定し、マークします。ルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトがライブと見なされます。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）が不要なメモリとして識別され、解放されます。このコミットで変更された`mgcsweep.go`は、このスイープフェーズに関連する処理を担っています。

### ファイナライザ (Finalizers)

Goの`runtime.SetFinalizer`関数を使用すると、特定のオブジェクトがガベージコレクションによって回収される直前に実行される関数（ファイナライザ）を設定できます。これは、ファイルハンドルやネットワーク接続などの外部リソースをクリーンアップするのに役立ちます。

*   ファイナライザが設定されたオブジェクトは、GCによって到達不能と判断されても、ファイナライザが実行されるまではメモリが解放されず、ライブ状態に保たれます。
*   ファイナライザはGCのサイクル中に非同期に実行されるため、実行順序やタイミングは保証されません。
*   一つのオブジェクトに対して複数のファイナライザを設定することも可能ですが、その挙動は慎重に扱う必要があります。

### 微小なアロケーション (Tiny Allocations)

Goランタイムは、非常に小さなオブジェクト（例えば、数バイトから数十バイト）のアロケーションを効率化するために「微小なアロケーション」という特別なメカニズムを使用します。

*   これらの小さなオブジェクトは、個別にメモリページを割り当てるのではなく、より大きなメモリブロック（`_TinySize`、通常16バイト）にまとめてアロケートされます。これにより、メモリの断片化を減らし、アロケーションのオーバーヘッドを削減します。
*   `mspan`は、Goのメモリヒープの基本的な単位であり、連続したメモリページを管理します。微小なアロケーションも`mspan`内で管理されます。
*   `special`レコードは、`mspan`内のオブジェクトに関連付けられた特別な情報（ファイナライザやプロファイル情報など）を保持するために使用されます。`_KindSpecialFinalizer`はファイナライザ、`_KindSpecialProfile`はプロファイル情報を示します。

### ヒーププロファイリング (Heap Profiling)

Goのヒーププロファイリングは、アプリケーションのメモリ使用量を分析するためのツールです。`runtime.MemProfile`関数や`go tool pprof`コマンドを通じて利用できます。

*   ヒーププロファイルは、どのコードパスがどれだけのメモリをアロケートし、それがどれだけライブ状態にあるかを示します。
*   メモリリークの特定や、メモリ使用量の最適化に不可欠です。
*   プロファイル情報は、アロケートされたオブジェクトのサイズや数、それが解放されたかどうかなどを記録することで収集されます。

### `heapBitsForAddr`と`setMarkedNonAtomic`

*   `heapBitsForAddr(p)`: 特定のメモリアドレス`p`に対応するヒープビット（heap bits）を取得する関数です。ヒープビットは、GCがオブジェクトのマーク状態（ライブか否か）やポインタの有無などを管理するために使用します。
*   `hbits.isMarked()`: ヒープビットが示すオブジェクトがマークされている（ライブである）かどうかをチェックします。
*   `hbits.setMarkedNonAtomic()`: ヒープビットが示すオブジェクトをマーク状態に設定します。これは、GCがオブジェクトをライブとして扱うように指示します。

## 技術的詳細

このコミットの技術的な核心は、`src/runtime/mgcsweep.go`内の`mSpan_Sweep`関数における特殊レコードの処理ロジックの変更にあります。以前の実装では、スイープフェーズ中に未マークのオブジェクト（回収対象）に特殊レコードが見つかった場合、その特殊レコードがファイナライザであれば、オブジェクトをマークしてライブ状態に保ち、ファイナライザをキューに入れていました。しかし、この処理はオブジェクトごとに一度しか行われなかったため、以下の問題が生じていました。

1.  **複数ファイナライザの問題**: 微小なアロケーションでは、1つの`mspan`ブロック内に複数の小さなオブジェクトが格納されることがあります。もし同じブロック内の異なるオフセットにあるオブジェクトにそれぞれファイナライザが設定されている場合、以前のロジックでは、最初に発見されたファイナライザが処理されると、そのオブジェクト全体がマークされ、そのGCサイクル中には他のファイナライザは処理されませんでした。これにより、残りのファイナライザは次のGCサイクルまで待たされることになり、ファイナライズが完了するまでに多くのGCサイクルが必要となっていました。
2.  **ファイナライザとプロファイルの競合**: オブジェクトがファイナライザとプロファイルの両方の特殊レコードを持つ場合、ファイナライザがオブジェクトをライブに保つためにマークする一方で、プロファイルレコードが誤って解放されてしまう可能性がありました。これは、`freespecial`関数が、ファイナライザを持つオブジェクトに対して`false`を返し、オブジェクトの解放を停止させるという挙動に起因していました。この`freespecial`の戻り値によって、プロファイルレコードの処理が適切に行われないケースがあったのです。

新しいアプローチでは、これらの問題を解決するために、単一のオブジェクトに対するすべての特殊レコードを一度に分析する2パス方式を導入しています。

*   **パス1（ファイナライザの検出）**: まず、未マークのオブジェクトに対して、そのオブジェクトに関連するすべての特殊レコードを走査し、ファイナライザが存在するかどうかをチェックします。ファイナライザが見つかった場合、そのオブジェクトは`hbits.setMarkedNonAtomic()`によってライブとしてマークされます。これにより、オブジェクトがGCによって回収されるのを防ぎます。
*   **パス2（ファイナライザのキューイングとプロファイルレコードの処理）**: 次に、再度特殊レコードを走査します。
    *   もしオブジェクトにファイナライザが存在する場合（パス1で`hasFin`が`true`になった場合）、すべてのファイナライザの特殊レコードを`freespecial`に渡し、キューに入れます。この際、プロファイルレコードはオブジェクトがライブに保たれるため、`mspan`の特殊レコードリストから削除されずに残されます。
    *   もしオブジェクトにファイナライザが存在しない場合（`!hasFin`）、プロファイルレコードを含むすべての特殊レコードを`freespecial`に渡し、解放します。

この2パス方式により、オブジェクトに複数のファイナライザがあっても、それらがすべて同じGCサイクル中にキューに入れられるようになります。また、ファイナライザを持つオブジェクトのプロファイルレコードが誤って解放されることもなくなります。

`src/runtime/mheap.go`の`freespecial`関数も変更されました。以前は`bool`を返していましたが、これは`mSpan_Sweep`での特殊レコードの処理ロジックを複雑にし、問題の原因となっていました。新しい実装では、`freespecial`は`void`（何も返さない）関数となり、特殊レコードの解放と関連するクリーンアップのみを担当するようになりました。オブジェクトをライブに保つかどうかの判断は、`mSpan_Sweep`内の2パスロジックに完全に委ねられることになりました。

テストケースの追加と修正も重要です。`test/finprofiled.go`は、ファイナライザを持つ微小なアロケーションがヒーププロファイルに正しく反映されることを確認するための新しいテストです。`test/tinyfin.go`の修正は、テストの不安定性を排除し、ファイナライズ処理の正確性をより厳密に検証できるようにしています。特に、`time.Sleep`のようなリアルタイムに依存する要素を排除し、`chan`を用いた同期メカニズムを導入することで、テストの信頼性が向上しています。

## コアとなるコードの解説

### `src/runtime/mgcsweep.go`の変更点

`mSpan_Sweep`関数は、GCのスイープフェーズ中に`mspan`内のオブジェクトを処理する役割を担います。この関数内で、未マークのオブジェクト（回収対象）に付随する特殊レコード（ファイナライザやプロファイル情報）の処理ロジックが変更されました。

変更の核心は、`if !hbits.isMarked() { ... }` ブロック内に導入された2つのパスです。

1.  **パス1: ファイナライザの存在チェック**
    *   `hasFin := false` と `endOffset := p - uintptr(s.start<<_PageShift) + size` が導入されます。`endOffset`は、現在のオブジェクトが`mspan`内で占める範囲の終了オフセットを計算します。
    *   `for tmp := special; tmp != nil && uintptr(tmp.offset) < endOffset; tmp = tmp.next { ... }` ループで、現在のオブジェクトに関連するすべての特殊レコードを走査します。
    *   `if tmp.kind == _KindSpecialFinalizer { ... }` でファイナライザが見つかった場合、`hbits.setMarkedNonAtomic()` を呼び出してオブジェクトをライブとしてマークし、`hasFin = true` を設定してループを抜けます。これにより、オブジェクトがGCによって回収されるのを防ぎます。このパスの目的は、オブジェクトにファイナライザがあるかどうかを事前に判断することです。

2.  **パス2: 特殊レコードの処理**
    *   `for special != nil && uintptr(special.offset) < endOffset { ... }` ループで、再度現在のオブジェクトに関連する特殊レコードを走査します。
    *   `if special.kind == _KindSpecialFinalizer || !hasFin { ... }` の条件が重要です。
        *   `special.kind == _KindSpecialFinalizer` の場合、これはファイナライザの特殊レコードです。`freespecial`を呼び出してファイナライザをキューに入れ、`mspan`の特殊レコードリストから削除します。
        *   `!hasFin` の場合、これはオブジェクトにファイナライザがないことを意味します。したがって、プロファイルレコードを含むすべての特殊レコードを`freespecial`に渡し、解放します。
    *   `else { ... }` ブロックは、`special.kind != _KindSpecialFinalizer` かつ `hasFin` が`true`の場合、つまり、オブジェクトにファイナライザがあるが、現在の特殊レコードがプロファイルレコードである場合に実行されます。この場合、オブジェクトはファイナライザによってライブに保たれるため、プロファイルレコードは`mspan`の特殊レコードリストから削除されずに残されます。`specialp = &special.next` と `special = *specialp` によって、現在のプロファイルレコードをスキップし、次の特殊レコードに進みますが、リストからは削除しません。

この2パス方式により、オブジェクトに複数のファイナライザがあっても、最初のパスでオブジェクトがライブとしてマークされ、2番目のパスでそれらすべてのファイナライザが処理されるようになります。また、ファイナライザを持つオブジェクトのプロファイルレコードは、オブジェクトがライブに保たれるため、誤って解放されることなく保持されるようになります。

### `src/runtime/mheap.go`の変更点

`freespecial`関数は、特殊レコードを解放し、関連するクリーンアップを行うための関数です。以前は`bool`を返していましたが、これは`mSpan_Sweep`でのロジックを複雑にし、問題の一因となっていました。

*   **戻り値の削除**: `func freespecial(s *special, p unsafe.Pointer, size uintptr, freed bool) bool` から `func freespecial(s *special, p unsafe.Pointer, size uintptr, freed bool)` へと変更され、戻り値がなくなりました。
*   **内部ロジックの簡素化**: `return false` や `return true` といった行が削除されました。これにより、`freespecial`は純粋に特殊レコードの解放と関連するメモリプールへの返却のみを行うようになり、オブジェクトの生存期間に関する判断は呼び出し元（`mSpan_Sweep`）に完全に委ねられるようになりました。

この変更により、`freespecial`の役割が明確になり、`mSpan_Sweep`がオブジェクトのファイナライズとプロファイリングのロジックを一元的に管理できるようになりました。

### `test/tinyfin.go`の変更点

*   **`sync/atomic`の削除と`chan`の導入**: 以前は`atomic.AddInt32`と`atomic.LoadInt32`を使用してファイナライザの実行数をカウントしていましたが、これは非同期処理のタイミングに依存し、テストの不安定性を引き起こしていました。新しいバージョンでは、`finalized := make(chan int32, N)` というチャネルを導入し、ファイナライザが実行されるたびにそのオブジェクトのIDをチャネルに送信するように変更されました。
*   **`select`と`time.After`によるタイムアウト処理**: `for { select { ... } }` 構造と `timeout := time.After(5*time.Second)` を使用することで、ファイナライザの実行を待機しつつ、一定時間内に完了しない場合はタイムアウトとしてテストを失敗させるようになりました。これにより、テストがリアルタイムのタイミングに依存することなく、より確実にファイナライザの実行を検証できるようになりました。
*   **厳密なチェック**: `count > N/10*9` という条件で、ほとんどのファイナライザが呼び出されたことを確認しています。これは、微小なアロケーションの特性上、一部のオブジェクトが永続的なものと結合されてファイナライズされない可能性があるため、完全に100%のファイナライズを期待するのではなく、合理的な閾値を設けています。

これらの変更により、`tinyfin.go`テストはより堅牢になり、ファイナライズ処理のバグを確実に検出できるようになりました。

## 元コミット内容

このコミットは、Goランタイムにおける微小なアロケーション（tiny allocations）のファイナライズ処理とヒーププロファイリングに関する2つの問題を修正します。

1.  **ファイナライズの遅延**: 以前の実装では、オブジェクトに対して複数のファイナライザが設定されている場合、1つのファイナライザがキューに入れられると、そのGCサイクル中には同じオブジェクトの他のファイナライザはキューに入れられませんでした。これにより、最大16個のファイナライザが設定されている最悪のケースでは、ファイナライズが完了するまでに16回のGCサイクルが必要となり、`tinyfin.go`テストの誤動作や不安定性の原因となっていました。
2.  **ヒーププロファイルの歪み**: 微小なブロックがファイナライザとプロファイルの両方の特殊レコードを持つ場合、ファイナライザがキューに入れられてオブジェクトが生存状態に保たれる一方で、プロファイルレコードが誤って解放される可能性がありました。これにより、ヒーププロファイルが実際のライブメモリ量を過小評価し、歪んだ結果を示すことがありました。

これらの問題は、単一のオブジェクトに対するすべての特殊レコードを一度に分析することで解決されます。

さらに、`tinyfin`テストはより厳密になり、リアルタイムへの依存が排除されました。また、問題2を検証するための新しいテストが追加されました。この問題により、以前はヒーププロファイルがライブメモリの約半分を見落としていました。

## 変更の背景

Goのランタイムは、メモリ管理においてガベージコレクション（GC）とヒーププロファイリングという重要な機能を提供します。特に、小さなオブジェクト（微小なアロケーション）は効率的なメモリ利用のために特別な方法で扱われます。このコミットは、これらの微小なアロケーションに関連する既存のメカニズムに潜んでいた2つの深刻なバグに対処するために導入されました。

一つ目の問題は、オブジェクトに複数のファイナライザが設定されている場合のファイナライズ処理の非効率性です。Goのファイナライザは、オブジェクトがGCによって回収される直前に実行されるコールバック関数です。微小なアロケーションでは、複数の小さなオブジェクトが1つのメモリブロックにまとめられることがあります。このとき、もし同じメモリブロック内の異なるオフセットにあるオブジェクトにそれぞれファイナライザが設定されていると、以前の実装ではGCサイクルごとに1つのファイナライザしか処理されず、ファイナライズ完了までに多くのGCサイクルを要していました。これは、特にリソースの解放が遅延する原因となり、アプリケーションの動作に予期せぬ影響を与える可能性がありました。`tinyfin.go`テストがこの問題の不安定性を示していました。

二つ目の問題は、ファイナライザとヒーププロファイルの両方が設定された微小なアロケーションにおけるデータの一貫性の欠如です。ヒーププロファイリングは、アプリケーションがどのメモリをどれだけ使用しているかを分析するための重要なツールです。しかし、ファイナライザが設定されたオブジェクトは、GCによって回収されるまで「ライブ」として扱われ、そのメモリは解放されません。以前の実装では、このようなオブジェクトに対して、ファイナライザがオブジェクトをライブに保つ一方で、プロファイルレコードが誤って解放されてしまう可能性がありました。これにより、ヒーププロファイルが実際のメモリ使用量を正確に反映せず、開発者がメモリリークや非効率なメモリ使用を特定するのを妨げていました。コミットメッセージによると、この問題によりライブメモリの約半分が見落とされていたとのことです。

これらの問題は、Goアプリケーションの安定性、パフォーマンス分析の正確性、およびデバッグの効率性に直接影響を与えるため、修正が急務でした。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoランタイムの概念について解説します。

### Goのガベージコレクション (GC)

Goのガベージコレクションは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。

*   **マークフェーズ**: GCは、プログラムがアクセス可能なすべてのオブジェクト（ライブオブジェクト）を特定し、マークします。ルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトがライブと見なされます。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）が不要なメモリとして識別され、解放されます。このコミットで変更された`mgcsweep.go`は、このスイープフェーズに関連する処理を担っています。

### ファイナライザ (Finalizers)

Goの`runtime.SetFinalizer`関数を使用すると、特定のオブジェクトがガベージコレクションによって回収される直前に実行される関数（ファイナライザ）を設定できます。これは、ファイルハンドルやネットワーク接続などの外部リソースをクリーンアップするのに役立ちます。

*   ファイナライザが設定されたオブジェクトは、GCによって到達不能と判断されても、ファイナライザが実行されるまではメモリが解放されず、ライブ状態に保たれます。
*   ファイナライザはGCのサイクル中に非同期に実行されるため、実行順序やタイミングは保証されません。
*   一つのオブジェクトに対して複数のファイナライザを設定することも可能ですが、その挙動は慎重に扱う必要があります。

### 微小なアロケーション (Tiny Allocations)

Goランタイムは、非常に小さなオブジェクト（例えば、数バイトから数十バイト）のアロケーションを効率化するために「微小なアロケーション」という特別なメカニズムを使用します。

*   これらの小さなオブジェクトは、個別にメモリページを割り当てるのではなく、より大きなメモリブロック（`_TinySize`、通常16バイト）にまとめてアロケートされます。これにより、メモリの断片化を減らし、アロケーションのオーバーヘッドを削減します。
*   `mspan`は、Goのメモリヒープの基本的な単位であり、連続したメモリページを管理します。微小なアロケーションも`mspan`内で管理されます。
*   `special`レコードは、`mspan`内のオブジェクトに関連付けられた特別な情報（ファイナライザやプロファイル情報など）を保持するために使用されます。`_KindSpecialFinalizer`はファイナライザ、`_KindSpecialProfile`はプロファイル情報を示します。

### ヒーププロファイリング (Heap Profiling)

Goのヒーププロファイリングは、アプリケーションのメモリ使用量を分析するためのツールです。`runtime.MemProfile`関数や`go tool pprof`コマンドを通じて利用できます。

*   ヒーププロファイルは、どのコードパスがどれだけのメモリをアロケートし、それがどれだけライブ状態にあるかを示します。
*   メモリリークの特定や、メモリ使用量の最適化に不可欠です。
*   プロファイル情報は、アロケートされたオブジェクトのサイズや数、それが解放されたかどうかなどを記録することで収集されます。

### `heapBitsForAddr`と`setMarkedNonAtomic`

*   `heapBitsForAddr(p)`: 特定のメモリアドレス`p`に対応するヒープビット（heap bits）を取得する関数です。ヒープビットは、GCがオブジェクトのマーク状態（ライブか否か）やポインタの有無などを管理するために使用します。
*   `hbits.isMarked()`: ヒープビットが示すオブジェクトがマークされている（ライブである）かどうかをチェックします。
*   `hbits.setMarkedNonAtomic()`: ヒープビットが示すオブジェクトをマーク状態に設定します。これは、GCがオブジェクトをライブとして扱うように指示します。

## 技術的詳細

このコミットの技術的な核心は、`src/runtime/mgcsweep.go`内の`mSpan_Sweep`関数における特殊レコードの処理ロジックの変更にあります。以前の実装では、スイープフェーズ中に未マークのオブジェクト（回収対象）に特殊レコードが見つかった場合、その特殊レコードがファイナライザであれば、オブジェクトをマークしてライブ状態に保ち、ファイナライザをキューに入れていました。しかし、この処理はオブジェクトごとに一度しか行われなかったため、以下の問題が生じていました。

1.  **複数ファイナライザの問題**: 微小なアロケーションでは、1つの`mspan`ブロック内に複数の小さなオブジェクトが格納されることがあります。もし同じブロック内の異なるオフセットにあるオブジェクトにそれぞれファイナライザが設定されている場合、以前のロジックでは、最初に発見されたファイナライザが処理されると、そのオブジェクト全体がマークされ、そのGCサイクル中には他のファイナライザは処理されませんでした。これにより、残りのファイナライザは次のGCサイクルまで待たされることになり、ファイナライズが完了するまでに多くのGCサイクルが必要となっていました。
2.  **ファイナライザとプロファイルの競合**: オブジェクトがファイナライザとプロファイルの両方の特殊レコードを持つ場合、ファイナライザがオブジェクトをライブに保つためにマークする一方で、プロファイルレコードが誤って解放されてしまう可能性がありました。これは、`freespecial`関数が、ファイナライザを持つオブジェクトに対して`false`を返し、オブジェクトの解放を停止させるという挙動に起因していました。この`freespecial`の戻り値によって、プロファイルレコードの処理が適切に行われないケースがあったのです。

新しいアプローチでは、これらの問題を解決するために、単一のオブジェクトに対するすべての特殊レコードを一度に分析する2パス方式を導入しています。

*   **パス1（ファイナライザの検出）**: まず、未マークのオブジェクトに対して、そのオブジェクトに関連するすべての特殊レコードを走査し、ファイナライザが存在するかどうかをチェックします。ファイナライザが見つかった場合、そのオブジェクトは`hbits.setMarkedNonAtomic()`によってライブとしてマークされます。これにより、オブジェクトがGCによって回収されるのを防ぎます。
*   **パス2（ファイナライザのキューイングとプロファイルレコードの処理）**: 次に、再度特殊レコードを走査します。
    *   もしオブジェクトにファイナライザが存在する場合（パス1で`hasFin`が`true`になった場合）、すべてのファイナライザの特殊レコードを`freespecial`に渡し、キューに入れます。この際、プロファイルレコードはオブジェクトがライブに保たれるため、`mspan`の特殊レコードリストから削除されずに残されます。
    *   もしオブジェクトにファイナライザが存在しない場合（`!hasFin`）、プロファイルレコードを含むすべての特殊レコードを`freespecial`に渡し、解放します。

この2パス方式により、オブジェクトに複数のファイナライザがあっても、それらがすべて同じGCサイクル中にキューに入れられるようになります。また、ファイナライザを持つオブジェクトのプロファイルレコードが誤って解放されることもなくなります。

`src/runtime/mheap.go`の`freespecial`関数も変更されました。以前は`bool`を返していましたが、これは`mSpan_Sweep`での特殊レコードの処理ロジックを複雑にし、問題の原因となっていました。新しい実装では、`freespecial`は`void`（何も返さない）関数となり、特殊レコードの解放と関連するクリーンアップのみを担当するようになりました。オブジェクトをライブに保つかどうかの判断は、`mSpan_Sweep`内の2パスロジックに完全に委ねられることになりました。

テストケースの追加と修正も重要です。`test/finprofiled.go`は、ファイナライザを持つ微小なアロケーションがヒーププロファイルに正しく反映されることを確認するための新しいテストです。`test/tinyfin.go`の修正は、テストの不安定性を排除し、ファイナライズ処理の正確性をより厳密に検証できるようにしています。特に、`time.Sleep`のようなリアルタイムに依存する要素を排除し、`chan`を用いた同期メカニズムを導入することで、テストの信頼性が向上しています。

```go
// run

// Copyright 2015 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Test that tiny allocations with finalizers are correctly profiled.
// Previously profile special records could have been processed prematurely
// (while the object is still live).

package main

import (
	"runtime"
	"time"
	"unsafe"
)

func main() {
	runtime.MemProfileRate = 1
	// Allocate 1M 4-byte objects and set a finalizer for every third object.
	// Assuming that tiny block size is 16, some objects get finalizers setup
	// only for middle bytes. The finalizer resurrects that object.
	// As the result, all allocated memory must stay alive.
	const (
		N = 1 << 20
		tinyBlockSize = 16 // runtime._TinySize
	)
	hold := make([]*int32, 0, N)
	for i := 0; i < N; i++ {
		x := new(int32)
		if i%3 == 0 {
			runtime.SetFinalizer(x, func(p *int32) {
				hold = append(hold, p)
			})
		}
	}
	// Finalize as much as possible.
	// Note: the sleep only increases probility of bug detection,
	// it cannot lead to false failure.
	for i := 0; i < 5; i++ {
		runtime.GC()
		time.Sleep(10 * time.Millisecond)
	}
	// Read memory profile.
	var prof []runtime.MemProfileRecord
	for {
		if n, ok := runtime.MemProfile(prof, false); ok {
			prof = prof[:n]
			break
		} else {
			prof = make([]runtime.MemProfileRecord, n+10)
		}
	}
	// See how much memory in tiny objects is profiled.
	var totalBytes int64
	for _, p := range prof {
		bytes := p.AllocBytes - p.FreeBytes
		nobj := p.AllocObjects - p.FreeObjects
		size := bytes / nobj
		if size == tinyBlockSize {
			totalBytes += bytes
		}
	}
	// 2*tinyBlockSize slack is for any boundary effects.
	if want := N*int64(unsafe.Sizeof(int32(0))) - 2*tinyBlockSize; totalBytes < want {
		println("got", totalBytes, "want >=", want)
		panic("some of the tiny objects are not profiled")
	}
	// Just to keep hold alive.
	if len(hold) != 0 && hold[0] == nil {
		panic("bad")
	}
}
```

## コアとなるコードの解説

### `src/runtime/mgcsweep.go`の変更点

`mSpan_Sweep`関数は、GCのスイープフェーズ中に`mspan`内のオブジェクトを処理する役割を担います。この関数内で、未マークのオブジェクト（回収対象）に付随する特殊レコード（ファイナライザやプロファイル情報）の処理ロジックが変更されました。

変更の核心は、`if !hbits.isMarked() { ... }` ブロック内に導入された2つのパスです。

1.  **パス1: ファイナライザの存在チェック**
    *   `hasFin := false` と `endOffset := p - uintptr(s.start<<_PageShift) + size` が導入されます。`endOffset`は、現在のオブジェクトが`mspan`内で占める範囲の終了オフセットを計算します。
    *   `for tmp := special; tmp != nil && uintptr(tmp.offset) < endOffset; tmp = tmp.next { ... }` ループで、現在のオブジェクトに関連するすべての特殊レコードを走査します。
    *   `if tmp.kind == _KindSpecialFinalizer { ... }` でファイナライザが見つかった場合、`hbits.setMarkedNonAtomic()` を呼び出してオブジェクトをライブとしてマークし、`hasFin = true` を設定してループを抜けます。これにより、オブジェクトがGCによって回収されるのを防ぎます。このパスの目的は、オブジェクトにファイナライザがあるかどうかを事前に判断することです。

2.  **パス2: 特殊レコードの処理**
    *   `for special != nil && uintptr(special.offset) < endOffset { ... }` ループで、再度現在のオブジェクトに関連する特殊レコードを走査します。
    *   `if special.kind == _KindSpecialFinalizer || !hasFin { ... }` の条件が重要です。
        *   `special.kind == _KindSpecialFinalizer` の場合、これはファイナライザの特殊レコードです。`freespecial`を呼び出してファイナライザをキューに入れ、`mspan`の特殊レコードリストから削除します。
        *   `!hasFin` の場合、これはオブジェクトにファイナライザがないことを意味します。したがって、プロファイルレコードを含むすべての特殊レコードを`freespecial`に渡し、解放します。
    *   `else { ... }` ブロックは、`special.kind != _KindSpecialFinalizer` かつ `hasFin` が`true`の場合、つまり、オブジェクトにファイナライザがあるが、現在の特殊レコードがプロファイルレコードである場合に実行されます。この場合、オブジェクトはファイナライザによってライブに保たれるため、プロファイルレコードは`mspan`の特殊レコードリストから削除されずに残されます。`specialp = &special.next` と `special = *specialp` によって、現在のプロファイルレコードをスキップし、次の特殊レコードに進みますが、リストからは削除しません。

この2パス方式により、オブジェクトに複数のファイナライザがあっても、最初のパスでオブジェクトがライブとしてマークされ、2番目のパスでそれらすべてのファイナライザが処理されるようになります。また、ファイナライザを持つオブジェクトのプロファイルレコードは、オブジェクトがライブに保たれるため、誤って解放されることなく保持されるようになります。

### `src/runtime/mheap.go`の変更点

`freespecial`関数は、特殊レコードを解放し、関連するクリーンアップを行うための関数です。以前は`bool`を返していましたが、これは`mSpan_Sweep`でのロジックを複雑にし、問題の一因となっていました。

*   **戻り値の削除**: `func freespecial(s *special, p unsafe.Pointer, size uintptr, freed bool) bool` から `func freespecial(s *special, p unsafe.Pointer, size uintptr, freed bool)` へと変更され、戻り値がなくなりました。
*   **内部ロジックの簡素化**: `return false` や `return true` といった行が削除されました。これにより、`freespecial`は純粋に特殊レコードの解放と関連するメモリプールへの返却のみを行うようになり、オブジェクトの生存期間に関する判断は呼び出し元（`mSpan_Sweep`）に完全に委ねられるようになりました。

この変更により、`freespecial`の役割が明確になり、`mSpan_Sweep`がオブジェクトのファイナライズとプロファイリングのロジックを一元的に管理できるようになりました。

### `test/tinyfin.go`の変更点

*   **`sync/atomic`の削除と`chan`の導入**: 以前は`atomic.AddInt32`と`atomic.LoadInt32`を使用してファイナライザの実行数をカウントしていましたが、これは非同期処理のタイミングに依存し、テストの不安定性を引き起こしていました。新しいバージョンでは、`finalized := make(chan int32, N)` というチャネルを導入し、ファイナライザが実行されるたびにそのオブジェクトのIDをチャネルに送信するように変更されました。
*   **`select`と`time.After`によるタイムアウト処理**: `for { select { ... } }` 構造と `timeout := time.After(5*time.Second)` を使用することで、ファイナライザの実行を待機しつつ、一定時間内に完了しない場合はタイムアウトとしてテストを失敗させるようになりました。これにより、テストがリアルタイムのタイミングに依存することなく、より確実にファイナライザの実行を検証できるようになりました。
*   **厳密なチェック**: `count > N/10*9` という条件で、ほとんどのファイナライザが呼び出されたことを確認しています。これは、微小なアロケーションの特性上、一部のオブジェクトが永続的なものと結合されてファイナライズされない可能性があるため、完全に100%のファイナライズを期待するのではなく、合理的な閾値を設けています。

これらの変更により、`tinyfin.go`テストはより堅牢になり、ファイナライズ処理のバグを確実に検出できるようになりました。

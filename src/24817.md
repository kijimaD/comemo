# [インデックス 24817] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`における`liblink`コンポーネントが、SSA（Static Single Assignment）形式で浮動小数点数の負号（negation）を表現するために使用される負のゼロ（`-0.0`）を誤って処理していたバグを修正します。具体的には、`liblink`が`-0.0`を伴う`AMOVSS`または`AMOVSD`命令を、符号情報を失う`XORPS reg,reg`命令に誤って書き換えてしまう問題がありました。この修正により、`strconv`パッケージなど、浮動小数点数の正確な表現に依存する部分の動作が改善されます。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式を使用しています。浮動小数点数の否定（例: `-x`）を表現する際、SSAは内部的に負のゼロ（`-0.0`）とのXOR演算を利用することがあります。これは、IEEE 754浮動小数点標準において、`x XOR -0.0`が`x`の符号を反転させるという特性を利用したものです。

しかし、Goコンパイラのバックエンドの一部である`liblink`（リンカ/アセンブラの役割を果たすコンポーネント）には、特定の最適化ロジックが存在しました。このロジックは、`AMOVSS`（単精度浮動小数点数移動）や`AMOVSD`（倍精度浮動小数点数移動）命令が、定数`0`を浮動小数点レジスタに移動しようとする場合に、より効率的な`XORPS reg,reg`命令に書き換えるものでした。`XORPS reg,reg`は、レジスタの内容を自分自身とXORすることで、そのレジスタを`+0.0`にクリアする効果があります。

問題は、この最適化の条件判定にありました。従来のコードでは、浮動小数点値が`0`であるかを`f == 0`という単純な比較で判断していました。IEEE 754標準では、`+0.0`と`-0.0`は異なるビット表現を持つにもかかわらず、`+0.0 == -0.0`は`true`と評価されます。このため、`liblink`はSSAが生成した`-0.0`を伴う命令を、誤って`+0.0`を生成する`XORPS reg,reg`に最適化してしまっていました。

結果として、負のゼロの符号情報が失われ、浮動小数点数の否定が正しく行われないというバグが発生しました。このバグは、特に数値と文字列の変換を扱う`strconv`パッケージにおいて、浮動小数点数の正確な表現が求められる場面で顕在化し、誤った結果を引き起こしていました。このコミットは、この根本的な問題を解決することを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **Goコンパイラの構造 (`cmd/compile`, `liblink`)**:
    *   **`cmd/compile`**: Go言語のソースコードを機械語に変換する公式コンパイラです。フロントエンド、ミドルエンド（最適化）、バックエンド（コード生成）の各フェーズを持ちます。
    *   **SSA (Static Single Assignment) 形式**: コンパイラのミドルエンドで使用される中間表現の一つです。各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、より高度な最適化を可能にしました。
    *   **`liblink`**: Goコンパイラのバックエンドの一部であり、アセンブラとリンカの役割を担います。SSA形式から生成された中間コード（`obj.Prog`構造体で表現される命令列）を受け取り、最終的な機械語コードに変換する過程で、命令の最適化や調整を行います。このコミットで修正される`progedit`関数は、このフェーズで命令の書き換えを行う部分です。

2.  **IEEE 754 浮動小数点標準**:
    *   現代のほとんどのコンピュータシステムで採用されている浮動小数点数の表現形式です。単精度（`float32`）と倍精度（`float64`）があります。
    *   **正のゼロ (`+0.0`) と負のゼロ (`-0.0`)**: IEEE 754では、`0`には正と負の符号を持つ2つの表現が存在します。
        *   `+0.0`: 全てのビットが`0`。
        *   `-0.0`: 符号ビットのみが`1`で、残りのビットは`0`。
    *   これらは数学的には等しい（`+0.0 == -0.0`は`true`）ですが、ビット表現は異なり、特定の演算（例: `1.0 / +0.0`は`+Inf`、`1.0 / -0.0`は`-Inf`）で異なる結果を生じます。また、浮動小数点数の否定は、符号ビットを反転させることで実現されます。SSAが`-0.0`とのXORを使用するのは、この符号反転の特性を利用するためです。

3.  **x86 アセンブリ命令**:
    *   **`AMOVSS` (Move Scalar Single-precision Floating-Point)**: 単精度浮動小数点数（`float32`）をレジスタ間で、またはメモリとレジスタ間で移動する命令です。
    *   **`AMOVSD` (Move Scalar Double-precision Floating-Point)**: 倍精度浮動小数点数（`float64`）をレジスタ間で、またはメモリとレジスタ間で移動する命令です。
    *   **`AXORPS` (XOR Packed Single-precision Floating-Point)**: 浮動小数点レジスタの内容を、別の浮動小数点レジスタの内容とビット単位でXORする命令です。`XORPS reg, reg`のように同じレジスタをオペランドに指定すると、そのレジスタの内容は全て`0`になり、結果として`+0.0`が生成されます。

4.  **`math.Float64bits` 関数**:
    *   Go言語の`math`パッケージに含まれる関数で、`float64`型の値をそのIEEE 754バイナリ表現に対応する`uint64`型の整数に変換します。これにより、浮動小数点数のビットパターンを直接検査することが可能になり、`+0.0`と`-0.0`のような、値は等しいがビット表現が異なるケースを区別できます。`+0.0`の`uint64`表現は`0`ですが、`-0.0`の`uint64`表現は`0x8000000000000000`となります。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/x86/obj6.go`ファイル内の`progedit`関数における浮動小数点定数`0`の検出ロジックの変更です。

`progedit`関数は、Goコンパイラのバックエンドで生成されたx86アセンブリ命令（`obj.Prog`構造体で表現）を走査し、特定のパターンに合致する命令を最適化のために書き換える役割を担っています。

問題の箇所は、`AMOVSS`および`AMOVSD`命令を処理する`case`ブロック内にありました。これらの命令が浮動小数点定数（`obj.TYPE_FCONST`）をソースオペランドとして持ち、その値が`0`である場合に、`liblink`は命令を`AXORPS reg,reg`に書き換える最適化を適用していました。

元のコードは以下のようになっていました（簡略化）：

```go
// AMOVSSの場合
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        if p.From.Val.(float64) == 0 { // ここが問題の箇所
            // ... AXORPS reg,reg に書き換え ...
        }
    }

// AMOVSDの場合も同様
case AMOVSD:
    if p.From.Type == obj.TYPE_FCONST {
        if p.From.Val.(float64) == 0 { // ここが問題の箇所
            // ... AXORPS reg,reg に書き換え ...
        }
    }
```

ここで、`p.From.Val.(float64) == 0`という条件は、IEEE 754の浮動小数点比較規則に従い、`+0.0`と`-0.0`の両方に対して`true`を返します。しかし、`AXORPS reg,reg`命令は常に`+0.0`を生成するため、`-0.0`がこの最適化の対象となると、その符号情報が失われて`+0.0`に変換されてしまうという問題がありました。

このコミットでは、この条件判定を以下のように変更しました。

```go
// AMOVSSの場合
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        // f == 0 can't be used here due to -0, so use Float64bits
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 { // 修正後
            // ... AXORPS reg,reg に書き換え ...
        }
    }

// AMOVSDの場合も同様
case AMOVSD:
    if p.From.Type == obj.TYPE_FCONST {
        // f == 0 can't be used here due to -0, so use Float64bits
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 { // 修正後
            // ... AXORPS reg,reg に書き換え ...
        }
    }
```

変更点として、`p.From.Val.(float64)`から取得した`float64`値を`f`という変数に代入し、その`f`に対して`math.Float64bits(f) == 0`という条件でチェックするようにしました。

*   `math.Float64bits(f)`は、`f`のIEEE 754バイナリ表現を`uint64`として返します。
*   `+0.0`のバイナリ表現は全てのビットが`0`であるため、`math.Float64bits(+0.0)`は`0`を返します。
*   `-0.0`のバイナリ表現は符号ビットが`1`であるため、`math.Float64bits(-0.0)`は`0x8000000000000000`を返します（`0`ではありません）。

この修正により、`AXORPS reg,reg`への最適化は`+0.0`の場合にのみ適用され、`-0.0`は元の`AMOVSS`/`AMOVSD`命令として保持されるようになります。これにより、SSAが意図した浮動小数点数の否定が正しく機械語に変換され、`strconv`パッケージなどの浮動小数点数処理におけるバグが解消されました。

テストファイル`src/cmd/compile/internal/gc/testdata/fp_ssa.go`には、`neg64_ssa`と`neg32_ssa`という新しい関数が追加され、それぞれ`float64`と`float32`の否定演算をテストしています。これらのテストケースは、修正が正しく機能し、浮動小数点数の否定が期待通りに動作することを確認するために導入されました。

## コアとなるコードの解説

`src/cmd/internal/obj/x86/obj6.go`内の`progedit`関数は、Goコンパイラが生成した中間的なアセンブリ命令（`obj.Prog`）を走査し、特定のパターンに合致する命令をより効率的な命令に書き換える役割を担っています。これは、最終的な機械語コードのパフォーマンスを向上させるための重要な最適化ステップです。

このコミットで修正されたのは、`AMOVSS`（Move Scalar Single-precision Floating-Point）と`AMOVSD`（Move Scalar Double-precision Floating-Point）命令に関する最適化ロジックです。これらの命令は、浮動小数点定数をレジスタにロードする際に使用されます。

元のコードでは、以下のようなロジックで最適化が行われていました。

```go
// AMOVSS命令の処理の一部
case AMOVSS:
    // ソースオペランドが浮動小数点定数であるかチェック
    if p.From.Type == obj.TYPE_FCONST {
        // その定数値が0であるかチェック
        if p.From.Val.(float64) == 0 {
            // ターゲットが浮動小数点レジスタであれば
            if p.To.Type == obj.TYPE_REG && REG_X0 <= p.To.Reg && p.To.Reg <= REG_X15 {
                // 命令をAXORPS reg,reg に書き換え
                p.As = AXORPS
                p.From = p.To
                p.To.Type = obj.TYPE_NONE // ターゲットをクリア
            }
        }
    }
// AMOVSD命令についても同様のロジック
```

このロジックの問題点は、`p.From.Val.(float64) == 0`という条件式にありました。Go言語（およびC/C++などの多くの言語）における`float64`の比較では、IEEE 754標準に従い、`+0.0`と`-0.0`は等しいと判断されます。しかし、`AXORPS reg,reg`命令は、レジスタを`+0.0`にクリアする効果しか持ちません。

SSAバックエンドでは、浮動小数点数の否定（例: `-x`）を表現するために、`x`と`-0.0`のXOR演算を利用することがあります。このとき、`-0.0`をレジスタにロードする`AMOVSS`または`AMOVSD`命令が生成される可能性があります。もしこの命令が上記の最適化ロジックによって`AXORPS reg,reg`に書き換えられてしまうと、`-0.0`の符号情報が失われ、`+0.0`として扱われてしまいます。結果として、SSAが意図した否定演算が正しく行われなくなります。

このコミットによる修正は、この`0`の判定方法を変更することで、`+0.0`と`-0.0`を区別するようにしました。

```go
// AMOVSS命令の処理の一部 (修正後)
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        // コメント: -0 のため f == 0 は使えない。Float64bits を使う。
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 {
            // ターゲットが浮動小数点レジスタであれば
            if p.To.Type == obj.TYPE_REG && REG_X0 <= p.To.Reg && p.To.Reg <= REG_X15 {
                // 命令をAXORPS reg,reg に書き換え
                p.As = AXORPS
                p.From = p.To
                p.To.Type = obj.TYPE_NONE
            }
        }
    }
// AMOVSD命令についても同様のロジック (修正後)
```

ここで導入された`math.Float64bits(f) == 0`という条件は、`f`のIEEE 754バイナリ表現が完全に`0`である場合にのみ`true`を返します。これは`+0.0`のビット表現にのみ該当し、符号ビットがセットされている`-0.0`のビット表現は`0`ではないため、この条件では`false`となります。

これにより、`AXORPS reg,reg`への最適化は、本当に`+0.0`をロードしようとしている場合にのみ適用されるようになり、`-0.0`の符号情報が誤って失われることがなくなりました。結果として、GoコンパイラはSSAが生成する浮動小数点数の否定演算を正しく機械語に変換できるようになり、`strconv`パッケージなどの浮動小数点数処理の正確性が保証されるようになりました。

`src/cmd/compile/internal/gc/testdata/fp_ssa.go`に追加されたテストケースは、この修正が正しく機能していることを検証するためのものです。`neg64_ssa`と`neg32_ssa`関数は、それぞれ`float64`と`float32`の否定演算を含む簡単な式を定義しており、これらの関数が期待される結果（例えば`-7`）を返すことを確認することで、コンパイラが浮動小数点数の否定を正しく処理していることを保証します。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式を使用しています。浮動小数点数の否定（例: `-x`）を表現する際、SSAは内部的に負のゼロ（`-0.0`）とのXOR演算を利用することがあります。これは、IEEE 754浮動小数点標準において、`x XOR -0.0`が`x`の符号を反転させるという特性を利用したものです。

しかし、Goコンパイラのバックエンドの一部である`liblink`（リンカ/アセンブラの役割を果たすコンポーネント）には、特定の最適化ロジックが存在しました。このロジックは、`AMOVSS`（単精度浮動小数点数移動）や`AMOVSD`（倍精度浮動小数点数移動）命令が、定数`0`を浮動小数点レジスタに移動しようとする場合に、より効率的な`XORPS reg,reg`命令に書き換えるものでした。`XORPS reg,reg`は、レジスタの内容を自分自身とXORすることで、そのレジスタを`+0.0`にクリアする効果があります。

問題は、この最適化の条件判定にありました。従来のコードでは、浮動小数点値が`0`であるかを`f == 0`という単純な比較で判断していました。IEEE 754標準では、`+0.0`と`-0.0`は異なるビット表現を持つにもかかわらず、`+0.0 == -0.0`は`true`と評価されます。このため、`liblink`はSSAが生成した`-0.0`を伴う命令を、誤って`+0.0`を生成する`XORPS reg,reg`に最適化してしまっていました。

結果として、負のゼロの符号情報が失われ、浮動小数点数の否定が正しく行われないというバグが発生しました。このバグは、特に数値と文字列の変換を扱う`strconv`パッケージにおいて、浮動小数点数の正確な表現が求められる場面で顕在化し、誤った結果を引き起こしていました。このコミットは、この根本的な問題を解決することを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **Goコンパイラの構造 (`cmd/compile`, `liblink`)**:
    *   **`cmd/compile`**: Go言語のソースコードを機械語に変換する公式コンパイラです。フロントエンド、ミドルエンド（最適化）、バックエンド（コード生成）の各フェーズを持ちます。
    *   **SSA (Static Single Assignment) 形式**: コンパイラのミドルエンドで使用される中間表現の一つです。各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、より高度な最適化を可能にしました。
    *   **`liblink`**: Goコンパイラのバックエンドの一部であり、アセンブラとリンカの役割を担います。SSA形式から生成された中間コード（`obj.Prog`構造体で表現される命令列）を受け取り、最終的な機械語コードに変換する過程で、命令の最適化や調整を行います。このコミットで修正される`progedit`関数は、このフェーズで命令の書き換えを行う部分です。

2.  **IEEE 754 浮動小数点標準**:
    *   現代のほとんどのコンピュータシステムで採用されている浮動小数点数の表現形式です。単精度（`float32`）と倍精度（`float64`）があります。
    *   **正のゼロ (`+0.0`) と負のゼロ (`-0.0`)**: IEEE 754では、`0`には正と負の符号を持つ2つの表現が存在します。
        *   `+0.0`: 全てのビットが`0`。
        *   `-0.0`: 符号ビットのみが`1`で、残りのビットは`0`。
    *   これらは数学的には等しい（`+0.0 == -0.0`は`true`）ですが、ビット表現は異なり、特定の演算（例: `1.0 / +0.0`は`+Inf`、`1.0 / -0.0`は`-Inf`）で異なる結果を生じます。また、浮動小数点数の否定は、符号ビットを反転させることで実現されます。SSAが`-0.0`とのXORを使用するのは、この符号反転の特性を利用するためです。

3.  **x86 アセンブリ命令**:
    *   **`AMOVSS` (Move Scalar Single-precision Floating-Point)**: 単精度浮動小数点数（`float32`）をレジスタ間で、またはメモリとレジスタ間で移動する命令です。
    *   **`AMOVSD` (Move Scalar Double-precision Floating-Point)**: 倍精度浮動小数点数（`float64`）をレジスタ間で、またはメモリとレジスタ間で移動する命令です。
    *   **`AXORPS` (XOR Packed Single-precision Floating-Point)**: 浮動小数点レジスタの内容を、別の浮動小数点レジスタの内容とビット単位でXORする命令です。`XORPS reg, reg`のように同じレジスタをオペランドに指定すると、そのレジスタの内容は全て`0`になり、結果として`+0.0`が生成されます。

4.  **`math.Float64bits` 関数**:
    *   Go言語の`math`パッケージに含まれる関数で、`float64`型の値をそのIEEE 754バイナリ表現に対応する`uint64`型の整数に変換します。これにより、浮動小数点数のビットパターンを直接検査することが可能になり、`+0.0`と`-0.0`のような、値は等しいがビット表現が異なるケースを区別できます。`+0.0`の`uint64`表現は`0`ですが、`-0.0`の`uint64`表現は`0x8000000000000000`となります。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/x86/obj6.go`ファイル内の`progedit`関数における浮動小数点定数`0`の検出ロジックの変更です。

`progedit`関数は、Goコンパイラのバックエンドで生成されたx86アセンブリ命令（`obj.Prog`構造体で表現）を走査し、特定のパターンに合致する命令を最適化のために書き換える役割を担っています。

問題の箇所は、`AMOVSS`および`AMOVSD`命令を処理する`case`ブロック内にありました。これらの命令が浮動小数点定数（`obj.TYPE_FCONST`）をソースオペランドとして持ち、その値が`0`である場合に、`liblink`は命令を`AXORPS reg,reg`に書き換える最適化を適用していました。

元のコードは以下のようになっていました（簡略化）：

```go
// AMOVSSの場合
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        if p.From.Val.(float64) == 0 { // ここが問題の箇所
            // ... AXORPS reg,reg に書き換え ...
        }
    }

// AMOVSDの場合も同様
case AMOVSD:
    if p.From.Type == obj.TYPE_FCONST {
        if p.From.Val.(float64) == 0 { // ここが問題の箇所
            // ... AXORPS reg,reg に書き換え ...
        }
    }
```

ここで、`p.From.Val.(float64) == 0`という条件は、IEEE 754の浮動小数点比較規則に従い、`+0.0`と`-0.0`の両方に対して`true`を返します。しかし、`AXORPS reg,reg`命令は常に`+0.0`を生成するため、`-0.0`がこの最適化の対象となると、その符号情報が失われて`+0.0`に変換されてしまうという問題がありました。

このコミットでは、この条件判定を以下のように変更しました。

```go
// AMOVSSの場合
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        // f == 0 can't be used here due to -0, so use Float64bits
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 { // 修正後
            // ... AXORPS reg,reg に書き換え ...
        }
    }

// AMOVSDの場合も同様
case AMOVSD:
    if p.From.Type == obj.TYPE_FCONST {
        // f == 0 can't be used here due to -0, so use Float64bits
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 { // 修正後
            // ... AXORPS reg,reg に書き換え ...
        }
    }
```

変更点として、`p.From.Val.(float64)`から取得した`float64`値を`f`という変数に代入し、その`f`に対して`math.Float64bits(f) == 0`という条件でチェックするようにしました。

*   `math.Float64bits(f)`は、`f`のIEEE 754バイナリ表現を`uint64`として返します。
*   `+0.0`のバイナリ表現は全てのビットが`0`であるため、`math.Float64bits(+0.0)`は`0`を返します。
*   `-0.0`のバイナリ表現は符号ビットが`1`であるため、`math.Float64bits(-0.0)`は`0x8000000000000000`を返します（`0`ではありません）。

この修正により、`AXORPS reg,reg`への最適化は`+0.0`の場合にのみ適用され、`-0.0`は元の`AMOVSS`/`AMOVSD`命令として保持されるようになります。これにより、SSAが意図した浮動小数点数の否定が正しく機械語に変換され、`strconv`パッケージなどの浮動小数点数処理におけるバグが解消されました。

テストファイル`src/cmd/compile/internal/gc/testdata/fp_ssa.go`には、`neg64_ssa`と`neg32_ssa`という新しい関数が追加され、それぞれ`float64`と`float32`の否定演算をテストしています。これらのテストケースは、修正が正しく機能し、浮動小数点数の否定が期待通りに動作することを確認するために導入されました。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の2つのファイルにあります。

1.  **`src/cmd/compile/internal/gc/testdata/fp_ssa.go`**

## コアとなるコードの解説

`src/cmd/internal/obj/x86/obj6.go`内の`progedit`関数は、Goコンパイラが生成した中間的なアセンブリ命令（`obj.Prog`）を走査し、特定のパターンに合致する命令をより効率的な命令に書き換える役割を担っています。これは、最終的な機械語コードのパフォーマンスを向上させるための重要な最適化ステップです。

このコミットで修正されたのは、`AMOVSS`（Move Scalar Single-precision Floating-Point）と`AMOVSD`（Move Scalar Double-precision Floating-Point）命令に関する最適化ロジックです。これらの命令は、浮動小数点定数をレジスタにロードする際に使用されます。

元のコードでは、以下のようなロジックで最適化が行われていました。

```go
// AMOVSS命令の処理の一部
case AMOVSS:
    // ソースオペランドが浮動小数点定数であるかチェック
    if p.From.Type == obj.TYPE_FCONST {
        // その定数値が0であるかチェック
        if p.From.Val.(float64) == 0 {
            // ターゲットが浮動小数点レジスタであれば
            if p.To.Type == obj.TYPE_REG && REG_X0 <= p.To.Reg && p.To.Reg <= REG_X15 {
                // 命令をAXORPS reg,reg に書き換え
                p.As = AXORPS
                p.From = p.To
                p.To.Type = obj.TYPE_NONE // ターゲットをクリア
            }
        }
    }
// AMOVSD命令についても同様のロジック
```

このロジックの問題点は、`p.From.Val.(float64) == 0`という条件式にありました。Go言語（およびC/C++などの多くの言語）における`float64`の比較では、IEEE 754標準に従い、`+0.0`と`-0.0`は等しいと判断されます。しかし、`AXORPS reg,reg`命令は、レジスタを`+0.0`にクリアする効果しか持ちません。

SSAバックエンドでは、浮動小数点数の否定（例: `-x`）を表現するために、`x`と`-0.0`のXOR演算を利用することがあります。このとき、`-0.0`をレジスタにロードする`AMOVSS`または`AMOVSD`命令が生成される可能性があります。もしこの命令が上記の最適化ロジックによって`AXORPS reg,reg`に書き換えられてしまうと、`-0.0`の符号情報が失われ、`+0.0`として扱われてしまいます。結果として、SSAが意図した否定演算が正しく行われなくなります。

このコミットによる修正は、この`0`の判定方法を変更することで、`+0.0`と`-0.0`を区別するようにしました。

```go
// AMOVSS命令の処理の一部 (修正後)
case AMOVSS:
    if p.From.Type == obj.TYPE_FCONST {
        // コメント: -0 のため f == 0 は使えない。Float64bits を使う。
        if f := p.From.Val.(float64); math.Float64bits(f) == 0 {
            // ターゲットが浮動小数点レジスタであれば
            if p.To.Type == obj.TYPE_REG && REG_X0 <= p.To.Reg && p.To.Reg <= REG_X15 {
                // 命令をAXORPS reg,reg に書き換え
                p.As = AXORPS
                p.From = p.To
                p.To.Type = obj.TYPE_NONE
            }
        }
    }
// AMOVSD命令についても同様のロジック (修正後)
```

ここで導入された`math.Float64bits(f) == 0`という条件は、`f`のIEEE 754バイナリ表現が完全に`0`である場合にのみ`true`を返します。これは`+0.0`のビット表現にのみ該当し、符号ビットがセットされている`-0.0`のビット表現は`0`ではないため、この条件では`false`となります。

これにより、`AXORPS reg,reg`への最適化は、本当に`+0.0`をロードしようとしている場合にのみ適用されるようになり、`-0.0`の符号情報が誤って失われることがなくなりました。結果として、GoコンパイラはSSAが生成する浮動小数点数の否定演算を正しく機械語に変換できるようになり、`strconv`パッケージなどの浮動小数点数処理の正確性が保証されるようになりました。

`src/cmd/compile/internal/gc/testdata/fp_ssa.go`に追加されたテストケースは、この修正が正しく機能していることを検証するためのものです。`neg64_ssa`と`neg32_ssa`関数は、それぞれ`float64`と`float32`の否定演算を含む簡単な式を定義しており、これらの関数が期待される結果（例えば`-7`）を返すことを確認することで、コンパイラが浮動小数点数の否定を正しく処理していることを保証します。

# [インデックス 26245] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `Transport` の振る舞いを修正し、特にリクエストがキャンセルされた際のテストの不安定性（flakiness）を解消することを目的としています。具体的には、リクエストが強制的に中断された場合に発生する可能性のある、ランダムなネットワークI/Oエラーを `errRequestCanceled` に変換するロジックが追加されています。

## コミット

`net/http`: `TestTransportCancelBeforeResponseHeaders` テストの不安定性を修正

リクエストが強制的に中断された場合、ランダムなネットワークI/Oエラーを `errRequestCanceled` に変換するケースをいくつか追加しました。

このテストは、`-race` フラグなしでは約1000回に1回、`-race` フラグありでは非常に簡単に失敗していました（`-race` がスケジューリングをランダム化するため）。

Issue #11894 を修正します。

## 変更の背景

この変更の背景には、`net/http` パッケージの `Transport` がHTTPリクエストを処理する際に、リクエストのキャンセルと同時に発生する可能性のあるネットワークI/Oエラーのハンドリングに関する問題がありました。

具体的には、`TestTransportCancelBeforeResponseHeaders` というテストが不安定（flaky）であり、特にGoの競合検出ツールである `-race` フラグを付けて実行すると、その不安定性が顕著になりました。これは、リクエストがキャンセルされるという意図された動作と、基盤となるネットワーク接続で発生する可能性のある偶発的なI/Oエラー（例えば、接続のリセットやタイムアウトなど）との間に競合状態が存在したことを示唆しています。

ユーザーがリクエストをキャンセルした場合、アプリケーションは `errRequestCanceled` というエラーを受け取ることを期待します。しかし、キャンセル処理中に別のネットワークエラーが発生すると、そのネットワークエラーが優先されて報告され、テストが失敗したり、アプリケーションが予期しないエラーハンドリングパスに入ったりする可能性がありました。`-race` フラグはゴルーチンのスケジューリングをランダム化するため、このような競合状態をより頻繁に露呈させます。

このコミットは、リクエストがキャンセルされた状態であるならば、発生したネットワークI/Oエラーの種類に関わらず、常に `errRequestCanceled` を返すようにすることで、この競合状態を解決し、テストの安定性を向上させることを目的としています。これにより、リクエストのキャンセルというユーザーの意図が、他の偶発的なエラーよりも優先されるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### Goの `net/http` パッケージと `Transport`

Goの `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。クライアント側では、`http.Client` がHTTPリクエストを送信するための主要なインターフェースです。`http.Client` は内部的に `http.Transport` を使用して、実際のネットワーク接続の確立、リクエストの送信、レスポンスの受信、接続の再利用（キープアライブ）などを処理します。

`http.Transport` は、低レベルのHTTP通信の詳細を抽象化し、コネクションプール、TLSハンドシェイク、プロキシ設定、リクエストのタイムアウト、そしてリクエストのキャンセルなどの機能を提供します。

### リクエストのキャンセル

HTTPリクエストのキャンセルは、クライアントが一度送信したリクエストの処理を途中で中止したい場合に用いられるメカニズムです。Goでは、`context` パッケージを使用してリクエストのキャンセルを管理するのが一般的です。`http.Request` に `context.Context` を関連付け、そのコンテキストがキャンセルされると、`http.Transport` は進行中のリクエストを中断しようとします。

リクエストがキャンセルされた場合、クライアントは通常、`context.Canceled` または `net/http` パッケージ固有の `errRequestCanceled` のようなエラーを受け取ることを期待します。

### 競合状態（Race Condition）

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスし、そのアクセス順序によってプログラムの最終結果が変わってしまうような状況を指します。このコミットのケースでは、リクエストのキャンセル処理と、ネットワークI/O操作中に発生するエラー処理が同時に進行し、どちらが先にエラーを報告するかによって結果が変わる可能性がありました。

Goの `-race` フラグは、プログラム実行中に競合状態を検出するためのツールです。これを使用すると、通常では見過ごされがちな競合状態を特定しやすくなります。

### `errRequestCanceled`

`net/http` パッケージ内で定義されている内部エラーで、リクエストがキャンセルされたことを示すために使用されます。このエラーが返されることで、クライアントはリクエストが意図的に中断されたことを認識し、適切な処理を行うことができます。

### `beforeRespHeaderError`

これは、レスポンスヘッダーを受信する前に発生したエラーを示すために `net/http` パッケージ内で使用される内部エラー型です。ネットワークI/Oエラーなど、リクエストの送信中またはレスポンスヘッダーの待機中に発生する可能性のあるエラーをラップするために使用されます。

## 技術的詳細

このコミットは、`net/http` パッケージの `Transport` がリクエストを処理する内部ロジック、特に `pc.roundTrip` メソッド内のエラーハンドリングに焦点を当てています。`pc` は `persistConn` のインスタンスであり、これは単一のHTTP/1.x接続を管理します。

`persistConn` の `roundTrip` メソッドは、リクエストの書き込み、レスポンスの読み取り、およびそれらの間の様々な状態遷移を管理します。このメソッド内には、リクエストの書き込みエラーを処理する部分と、レスポンスの読み取りエラーを処理する部分があります。

変更前は、リクエストの書き込み中にネットワークI/Oエラーが発生した場合、そのエラーがそのまま `beforeRespHeaderError` としてラップされ、呼び出し元に返されていました。同様に、レスポンスの読み取り中にエラーが発生した場合も、そのエラーがそのまま返されていました。

このコミットでは、これらのエラーが発生した際に、`pc.isCanceled()` メソッドを呼び出して、現在処理中のリクエストがキャンセルされているかどうかを確認するロジックが追加されました。

1.  **リクエスト書き込み中のエラーハンドリング**:
    `writeErrCh` からエラーが通知された場合、まず `pc.isCanceled()` をチェックします。もしリクエストがキャンセルされていた場合、元のネットワークI/Oエラー（`err`）は `errRequestCanceled` に上書きされます。これにより、リクエストがキャンセルされたという事実が、偶発的なネットワークI/Oエラーよりも優先されます。

2.  **レスポンス読み取り中のエラーハンドリング**:
    `resc` チャネルから `responseAndError` 構造体が返され、その中にエラー（`re.err`）が含まれていた場合も同様に、`pc.isCanceled()` をチェックします。リクエストがキャンセルされていた場合、`re.err` は `errRequestCanceled` に上書きされます。

この変更により、リクエストがキャンセルされた状況下で、ネットワークI/Oエラーとキャンセルエラーが同時に発生する可能性のある競合状態において、常に `errRequestCanceled` が返されることが保証されます。これにより、`TestTransportCancelBeforeResponseHeaders` のようなテストが安定し、アプリケーションがリクエストのキャンセルを正しく検出できるようになります。

また、`transport_test.go` から `setFlaky(t, 11894)` の行が削除されています。これは、このテストが以前は不安定であるとマークされていたことを示しており、今回の修正によってその不安定性が解消されたため、このマークが不要になったことを意味します。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更

このファイルでは、`persistConn` の `roundTrip` メソッド内の `WaitResponse` ラベルが付いた `select` ステートメントが変更されています。この `select` は、リクエストの書き込み、レスポンスの受信、タイムアウト、およびキャンセルイベントを待機する主要なループの一部です。

1.  **`writeErrCh` からのエラー処理**:
    `case err := <-writeErrCh:` ブロックは、リクエストの書き込み中に発生したエラーを処理します。
    変更前は、`if err != nil` の条件が真であれば、すぐに `beforeRespHeaderError` でエラーをラップして返していました。
    変更後は、`if err != nil` の内部に `if pc.isCanceled() { err = errRequestCanceled }` という行が追加されました。これは、書き込みエラーが発生した際に、`pc` (現在の `persistConn` インスタンス) がキャンセル状態であるかどうかを `isCanceled()` メソッドで確認します。もしキャンセル状態であれば、元の `err` を `errRequestCanceled` に上書きします。これにより、リクエストがキャンセルされたという意図が、実際のネットワーク書き込みエラーよりも優先されます。

2.  **`resc` からのレスポンス/エラー処理**:
    `case re = <-resc:` ブロックは、レスポンスの受信、またはレスポンス読み取り中に発生したエラーを処理します。`resc` チャネルは `responseAndError` 構造体を運び、これにはレスポンスとエラーの両方が含まれる可能性があります。
    変更前は、`re` を受け取った後、すぐに `break WaitResponse` していました。
    変更後は、`if re.err != nil && pc.isCanceled() { re.err = errRequestCanceled }` という行が追加されました。これは、レスポンスと共にエラーが報告され、かつ `pc` がキャンセル状態である場合に、そのエラーを `errRequestCanceled` に上書きします。これにより、レスポンス読み取り中のエラーも、リクエストのキャンセルが優先されるようになります。

これらの変更により、リクエストがキャンセルされた状況下で、書き込みまたは読み取り中に発生する可能性のある様々なネットワークI/Oエラーが、一貫して `errRequestCanceled` として報告されるようになります。

### `src/net/http/transport_test.go` の変更

このファイルでは、`TestTransportCancelBeforeResponseHeaders` テストから `setFlaky(t, 11894)` の行が削除されています。
`setFlaky` は、特定のテストが不安定であることを示すために使用されるヘルパー関数です。この行が削除されたことは、`transport.go` の変更によってこのテストの不安定性が解消され、もはや不安定であるとマークする必要がなくなったことを意味します。これは、コミットの目的が達成されたことの直接的な証拠となります。

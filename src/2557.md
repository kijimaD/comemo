# [インデックス 2557] ファイルの概要

このコミットは、Goコンパイラ（特に`6g`）の引数アライメント挙動の変更に備え、`cgo2c`ツールが生成するCコードに適切なパディングを挿入するように修正するものです。これにより、GoとCの関数呼び出し規約間の互換性を維持し、特に戻り値の引数が別々にアラインされる新しい方式に対応します。また、Go関数定義の間にCコードを混在させることも可能になります。

## 元コミット内容

このコミットは、Goコンパイラ`6g`が関数の出力引数を入力引数とは別にアラインするようになる変更に先立って、`cgo2c`ツールがC言語への変換時に必要なパディングを挿入するように修正します。

具体的には、`func indexstring(s string, i int32) (b byte)`のような関数において、現在の`6g`では引数`s`、`i`、戻り値`b`が単一の構造体内でアラインされていましたが、将来の`6g`では戻り値`b`が独立した構造体として扱われ、8バイト境界でアラインされるようになります。この変更に対応するため、`cgo2c`は生成するC関数シグネチャに`uint32`のようなパディングを挿入し、アライメントのずれを解消します。

また、Go関数定義の間にCコードを混在させることが可能になるよう、`cgo2c`のパーサーも改善されています。

## 変更の背景

Go言語の初期開発段階において、コンパイラとランタイムは継続的に進化していました。このコミットの背景には、`6g`コンパイラ（当時のamd64アーキテクチャ向けGoコンパイラ）における関数呼び出し規約の重要な変更が予定されていたことがあります。

従来の`6g`では、関数の入力引数と出力引数（戻り値）は、単一の論理的な構造体としてメモリ上に配置され、アライメントが決定されていました。しかし、より効率的で柔軟な呼び出し規約を実現するため、出力引数を入力引数とは独立した別の構造体として扱い、それぞれを独立してアラインする設計変更が計画されました。

この変更は、特にCGO（GoとC言語の相互運用機能）において問題を引き起こします。`cgo2c`はGoの関数シグネチャをC言語の関数シグネチャに変換するツールであり、Goの呼び出し規約とCの呼び出し規約の間で引数の配置が一致するように調整する必要があります。`6g`の新しいアライメント挙動が導入されると、`cgo2c`が生成するCコードの引数リストと、Goランタイムが期待する引数配置との間に不整合が生じ、メモリ破損やクラッシュの原因となる可能性がありました。

このコミットは、その将来の`6g`の変更に先立って`cgo2c`を更新し、新しいアライメント規約に準拠したCコードを生成できるようにすることで、GoとCの間の安全な相互運用を保証することを目的としています。具体的には、出力引数のアライメント要件を満たすために、C関数シグネチャに明示的なパディング（例: `uint32`）を挿入するようになります。

## 前提知識の解説

### Goの呼び出し規約とアライメント

Go言語の関数呼び出し規約は、引数と戻り値がどのようにスタックやレジスタに配置されるかを定義します。メモリ効率とパフォーマンスのために、データ型には特定のアライメント要件があります。例えば、64ビットシステムでは、64ビット整数やポインタは8バイト境界にアラインされることが一般的です。構造体もそのメンバーの最大アライメント要件に従ってアラインされます。

このコミットの文脈では、`6g`コンパイラが関数の引数と戻り値をメモリ上に配置する際のアライメントルールが変更されることが重要です。特に、戻り値が独立した構造体として扱われるようになると、その構造体自体が特定のアライメント（例: 8バイト）を持つことになり、入力引数の終端と戻り値の開始の間にパディングが必要になる場合があります。

### `cgo2c`ツール

`cgo2c`は、Go言語のソースコードを解析し、CGOで使用されるC言語のヘッダファイルやスタブコードを生成するための内部ツールです。Goの関数シグネチャ（引数の型、戻り値の型など）を読み取り、それに対応するC言語の関数プロトタイプに変換します。この変換プロセスでは、GoとCの型システムや呼び出し規約の違いを吸収し、両言語間での安全なデータ受け渡しを可能にする役割を担います。

### `6g`コンパイラ

`6g`は、Go言語の初期のコンパイラの一つで、主にamd64（64ビットIntel/AMDアーキテクチャ）をターゲットとしていました。Goのコンパイラは、Goソースコードを機械語に変換するだけでなく、ランタイムとの連携や呼び出し規約の実装も担当します。このコミットが作成された2009年当時、Goコンパイラはまだ開発の初期段階にあり、パフォーマンスや設計の改善のために頻繁に内部的な変更が行われていました。

### 構造体のアライメントとパディング

コンピュータのメモリはバイト単位でアドレス指定されますが、CPUは通常、特定のサイズのブロック（ワード）でデータを読み書きする方が効率的です。このため、データ型はメモリ上でそのサイズまたはCPUのワードサイズ（通常は4バイトまたは8バイト）の倍数のアドレスに配置されることが望ましいとされます。これを「アライメント」と呼びます。

構造体の場合、そのメンバーはそれぞれのアライメント要件に従って配置されます。構造体全体のサイズは、すべてのメンバーが適切にアラインされ、かつ構造体自体もそのメンバーの最大アライメント要件（またはシステムのアライメント要件）に従ってアラインされるように、必要に応じて「パディング」バイトが挿入されて決定されます。

例えば、8バイトアライメントが必要なシステムで、4バイトの整数と1バイトのバイト型が続く構造体がある場合、1バイトのバイト型の後に3バイトのパディングが挿入され、次の要素が8バイト境界に配置されるように調整されることがあります。

## 技術的詳細

このコミットの核心は、`6g`コンパイラが関数の戻り値を独立した構造体として扱い、8バイト境界でアラインするようになるという将来の変更に`cgo2c`が対応することです。

例として、`func indexstring(s string, i int32) (b byte)`というGo関数を考えます。
変更前は、`6g`は`s` (string, 16バイト)、`i` (int32, 4バイト)、`b` (byte, 1バイト) を一つの論理的な引数ブロックとして扱い、例えば`s`がオフセット0、`i`がオフセット16、`b`がオフセット20に配置されると仮定します。

変更後、`6g`は戻り値`b`を独立した構造体として扱い、この構造体は8バイト境界でアラインされるようになります。もし入力引数`s`と`i`の合計サイズが20バイト（16+4）で、その後に続く戻り値の構造体が8バイトアラインメントを要求する場合、入力引数ブロックの終端（オフセット20）から次の8バイト境界（オフセット24）までの間に4バイトのギャップが生じます。

`cgo2c`は、このギャップを埋めるために、生成するC関数シグネチャに明示的なパディングを挿入します。上記の例では、`cgo2c`は`void indexstring(string s, int32 i, byte b)`ではなく、`void indexstring(string s, int32 i, uint32, byte b)`を生成するようになります。ここで挿入された`uint32`（4バイト）がパディングとして機能し、`byte b`がオフセット24に適切にアラインされるようにします。この`uint32`は、`6c`コンパイラ（GoのC言語フロントエンド）にとっては有効な入力ですが、標準的なGCCにとっては無効な構文である点に注意が必要です。しかし、このコードは`6c`専用に生成されるため問題ありません。

また、このコミットでは、`cgo2c`がGoの`func`キーワードを検出するロジックを改善し、Go関数定義の間にCコードが混在していても正しくGo関数を識別できるようにしています。これにより、CGOの柔軟性が向上します。

さらに、`main`関数内で`GOARCH`環境変数をチェックし、`amd64`アーキテクチャの場合には`type_table`内の`Uintptr`、`String`、`Array`のサイズと`structround`（構造体のアライメント境界）を8バイトに更新するロジックが追加されています。これは、64ビットシステムにおけるポインタや文字列、配列の実際のサイズとアライメント要件を正確に反映させるために不可欠です。

## コアとなるコードの変更箇所

変更は主に`src/pkg/runtime/cgo2c.c`ファイルに集中しています。

1.  **`type_table`の追加と`type_size`関数の導入**:
    *   Goの各型（`bool`, `int`, `string`など）のサイズを定義する`type_table`構造体が追加されました。
    *   与えられた型名のサイズを返す`type_size`関数が導入されました。ポインタ型（`*`で終わる型）は`Uintptr`のサイズを返します。
2.  **`read_params`関数の変更**:
    *   引数のリストを読み取る際に、各引数のサイズとアライメントを考慮して現在のオフセットを計算するロジックが追加されました。
    *   `poffset`引数が追加され、引数リスト全体の合計サイズ（アライメント考慮済み）を呼び出し元に返すようになりました。
3.  **`read_func_header`関数の変更**:
    *   Go関数定義の間にCコードが混在していても、`func`キーワードを正しく識別し、Go関数を抽出できるようにパーシングループが変更されました。
    *   `paramwid`引数が追加され、`read_params`から計算された入力引数ブロックの幅を受け取るようになりました。
4.  **`write_6g_func_header`関数の変更**:
    *   `paramwid`引数が追加されました。
    *   戻り値がある場合、入力引数ブロックの幅（`paramwid`）と`structround`（構造体のアライメント境界）に基づいて、出力引数ブロックの前に必要なパディング（`uint8`, `uint16`, `uint32`）を挿入するロジックが追加されました。
5.  **`write_func_header`関数の変更**:
    *   `paramwid`引数が追加され、`write_6g_func_header`に渡されるようになりました。
6.  **`process_file`関数の変更**:
    *   `paramwid`変数が追加され、`read_func_header`と`write_func_header`の間で引数ブロックの幅を渡すために使用されます。
7.  **`main`関数の変更**:
    *   `GOARCH`環境変数をチェックし、`amd64`の場合に`type_table`内の`Uintptr`, `String`, `Array`のサイズと`structround`を8バイトに設定するロジックが追加されました。

## コアとなるコードの解説

### `type_table`と`type_size`

```c
enum {
	Bool,
	Float,
	Int,
	Uint,
	Uintptr,
	String,
	Array,
};

static struct {
	char *name;
	int size;
} type_table[] = {
	// ...
	"uintptr",	4, // default is 32-bit architecture sizes
	"String",	8,
	"Array",	12,
	// ...
};

static int
type_size(char *p)
{
	int i;

	if(p[strlen(p)-1] == '*') // ポインタ型の場合
		return type_table[Uintptr].size;

	for(i=0; type_table[i].name; i++)
		if(strcmp(type_table[i].name, p) == 0)
			return type_table[i].size;
	fprintf(stderr, "%s:%u: unknown type %s\\n", file, lineno, p);
	exit(1);
	return 0;
}
```
`type_table`は、Goの基本的な型とそれに対応するデフォルトのサイズ（32ビットアーキテクチャを想定）を定義します。`type_size`関数は、与えられた型名のサイズをルックアップします。ポインタ型は`Uintptr`のサイズとして扱われます。これは、引数リストの合計サイズとアライメントを計算するために使用されます。

### `read_params`におけるオフセット計算

```c
 static struct params *
-read_params(void)
+read_params(int *poffset)
 {
 	// ...
 	offset = 0;
 	if (strcmp(token, ")") != 0) {
 		while (1) {
 			// ...
 			size = type_size(p->type);
 			rnd = size;
 			if(rnd > structround)
 				rnd = structround;
 			if(offset%rnd) // 現在のオフセットがアライメント境界にない場合、パディングを追加
 				offset += rnd - offset%rnd;
 			offset += size; // オフセットを進める
 			// ...
 		}
 	}
 	if (poffset != NULL)
 		*poffset = offset; // 計算された合計オフセットを返す
 	return ret;
 }
```
この関数は、引数リストを解析しながら、各引数のサイズとアライメント要件に基づいて、引数ブロックの合計オフセット（`offset`）を計算します。`structround`は構造体のアライメント境界（デフォルトは4、amd64では8）を示し、これを超えない範囲で型のサイズをアライメント境界として使用します。`offset%rnd`が0でない場合、つまり現在のオフセットが`rnd`のアライメント境界にない場合、`rnd - offset%rnd`バイトのパディングが必要と判断し、オフセットに加算します。これにより、Goコンパイラが期待する引数配置をシミュレートします。

### `write_6g_func_header`におけるパディング挿入

```c
 static void
 write_6g_func_header(char *package, char *name, struct params *params,
-		     struct params *rets)
+		     int paramwid, struct params *rets)
 {
 	int first, n;

 	printf("void\\n%s·%s(\", package, name);
 	first = 1;
 	write_params(params, &first); // 入力引数を書き出す

 	/* insert padding to align output struct */
 	if(rets != NULL && paramwid%structround != 0) { // 戻り値があり、入力引数ブロックの幅がアライメント境界にない場合
 		n = structround - paramwid%structround; // 必要なパディングバイト数を計算
 		if(n & 1)
 			printf(", uint8"); // 1バイトパディング
 		if(n & 2)
 			printf(", uint16"); // 2バイトパディング
 		if(n & 4)
 			printf(", uint32"); // 4バイトパディング
 	}

 	write_params(rets, &first); // 出力引数を書き出す
 	printf(")\\n{\\n\");
 }
```
この関数は、`6g`コンパイラ向けのC関数ヘッダを生成します。特に重要なのは、戻り値（`rets != NULL`）があり、かつ入力引数ブロックの合計幅（`paramwid`）が`structround`（構造体のアライメント境界）の倍数でない場合に、パディングを挿入するロジックです。`paramwid%structround`が0でない場合、`structround - paramwid%structround`バイトのパディングが必要と判断し、そのバイト数に応じて`uint8`、`uint16`、`uint32`をC関数シグネチャに挿入します。これにより、Goコンパイラが期待する戻り値のアライメントがC側でも保証されます。

### `main`関数における`GOARCH`対応

```c
 int
 main(int argc, char **argv)
 {
 	char *goarch;
 	// ...
 	if(!gcc) { // 6gなどのGoコンパイラの場合
 		// 6g etc; update size table
 		goarch = getenv("GOARCH");
 		if(goarch != NULL && strcmp(goarch, "amd64") == 0) {
 			type_table[Uintptr].size = 8;
 			type_table[String].size = 16;
 			type_table[Array].size = 8+4+4; // 16バイト
 			structround = 8; // 8バイトアライメント
 		}
 	}
 	// ...
 }
```
`main`関数では、環境変数`GOARCH`をチェックし、それが`amd64`（64ビットアーキテクチャ）である場合に、`type_table`内の`Uintptr`、`String`、`Array`のサイズをそれぞれ8バイト、16バイト、16バイトに更新し、`structround`を8に設定します。これは、64ビットシステムではポインタや文字列（ポインタと長さのペア）、配列（ポインタ、長さ、容量のトリプル）が32ビットシステムとは異なるサイズとアライメント要件を持つため、これらを正確に反映させるための重要な調整です。

# [インデックス 20936] ファイルの概要

このコミットは、Go言語の`os`パッケージにおけるPlan 9固有のファイル操作に関するバグ修正です。具体的には、Plan 9システム上でのゼロバイト書き込み（zero-length write）が、予期せぬEOF（End Of File）として扱われる問題を解決します。

## 変更の背景

この変更は、Go言語の`os`パッケージがPlan 9オペレーティングシステム上でファイルへの書き込みを処理する方法におけるバグを修正するために導入されました。

問題の根本原因は、以前の変更（コミットメッセージで言及されている`CL 160670043`）によって、Goの`write`関数がゼロバイトの書き込み（長さ0のバイトスライスを渡す書き込み操作）を許可するようになったことにあります。一般的なUnix系システムでは、ゼロバイト書き込みは通常、何も書き込まれずに成功を返す操作であり、特別な意味を持ちません。しかし、Plan 9システムでは、I/O操作が「メッセージ境界」を保持するという特性があります。

このPlan 9の特性とGoの`os`ライブラリの期待（メッセージ境界を保持しないシステムを前提としている）との間に不整合が生じました。具体的には、Goの`ExampleWriter_Init`というテストが、ゼロバイト書き込みを行った際に失敗するようになりました。これは、Plan 9がゼロバイト書き込みをEOF（End Of File）として解釈してしまう可能性があったためと考えられます。テストは、ゼロバイト書き込みがEOFとして扱われることを期待していなかったため、失敗したのです。

この問題は以前にも`CL 7406046`で議論されたことがあり、Plan 9のI/OモデルとGoの標準ライブラリの間の互換性の課題が認識されていました。今回の修正は、この特定のケース（ゼロバイト書き込みがEOFとして扱われること）を明示的に回避することで、Plan 9上でのGoの`os`パッケージの動作を他のシステムと整合させることを目的としています。

## 前提知識の解説

### Plan 9のメッセージ境界（Message Boundaries）

Plan 9は、ベル研究所で開発された分散オペレーティングシステムであり、「すべてがファイルである」という強力な原則に基づいています。この原則は、プロセス間通信（IPC）やデバイスとのやり取りにも適用され、すべてがファイルシステムを通じて行われます。

Plan 9のI/Oモデルの重要な特徴の一つが「メッセージ境界の保持」です。これは、書き込み操作がバイトストリームとしてではなく、個別の「メッセージ」として扱われることを意味します。例えば、あるプロセスが10バイトを書き込み、次に5バイトを書き込んだ場合、受信側はこれらをそれぞれ10バイトのメッセージと5バイトのメッセージとして受け取ります。これは、多くのUnix系システムがバイトストリームモデルを採用しており、書き込み操作が連続したバイトのシーケンスとして扱われ、メッセージ境界が失われる可能性があるのとは対照的です。

このメッセージ境界の保持は、特にゼロバイト書き込みに影響を与えます。Unix系システムではゼロバイト書き込みは単なるno-op（何もしない操作）ですが、メッセージ境界を保持するシステムでは、ゼロバイトの「メッセージ」が送信されることになり、これがEOFなどの特別な意味を持つシグナルとして解釈される可能性があります。

### Goの`os`ライブラリとI/Oモデル

Go言語の標準ライブラリ、特に`os`パッケージは、クロスプラットフォームでの動作を意図して設計されています。そのため、I/O操作の多くは、Unix系システムで一般的なバイトストリームモデルを前提としています。`io.Writer`インターフェースの`Write([]byte) (n int, err error)`メソッドは、与えられたバイトスライスを書き込み、実際に書き込まれたバイト数とエラーを返します。慣例として、`len(b) == 0`の場合、`Write`は`0, nil`（0バイト書き込み、エラーなし）を返すことが期待されます。

### ゼロバイト書き込みとEOF

通常、ファイルからの読み込みでEOFに達すると、`io.EOF`エラーが返されます。書き込み操作において、ゼロバイト書き込みがEOFとして解釈されることは、予期せぬ動作です。これは、書き込み側がデータを送信していないにもかかわらず、読み込み側がデータの終わりを告げられることを意味し、アプリケーションのロジックを混乱させる可能性があります。

### `ExampleWriter_Init`テスト

具体的なテストコードはコミットメッセージには含まれていませんが、その名前から推測すると、`ExampleWriter_Init`は`io.Writer`インターフェースの実装、またはそれに関連する初期化処理の動作を検証するテストであると考えられます。この種のテストは、通常、特定の入力に対する出力や、特定の状態遷移をチェックします。ゼロバイト書き込みがEOFとして扱われることでテストが失敗したということは、テストがゼロバイト書き込みに対して、データが書き込まれないこと（`n=0`）は期待しつつも、EOFではないこと（`err=nil`）を期待していたと推測できます。

## 技術的詳細

この問題は、Goの`os`パッケージのPlan 9固有の実装ファイルである`src/os/file_plan9.go`内の`write`メソッドに起因します。

Goの`os`ライブラリは、`write`関数がゼロバイト書き込みに対して`0, nil`を返すことを期待しています。しかし、Plan 9の`syscall.Write`は、メッセージ境界を保持するという特性上、ゼロバイトの書き込み要求をEOFとして解釈する可能性がありました。これは、Goの`os`ライブラリが想定する一般的なI/Oモデル（バイトストリーム）と、Plan 9のI/Oモデル（メッセージ指向）との間の不整合です。

具体的には、`CL 160670043`でGoの`write`関数がゼロバイト書き込みを許可するように変更された結果、Plan 9上での`syscall.Write`が、このゼロバイト書き込みをEOFとして処理し、`ExampleWriter_Init`テストが失敗するようになりました。テストは、ゼロバイト書き込みがエラーなく完了し、EOFではないことを期待していたため、この動作は予期せぬものでした。

このコミットでは、`src/os/file_plan9.go`の`write`メソッドにガード句を追加することでこの問題を解決しています。具体的には、書き込まれるバイトスライスの長さが0である場合、実際の`syscall.Write`を呼び出すことなく、即座に`0, nil`を返します。これにより、Plan 9のメッセージ境界の特性がGoの`os`ライブラリの期待と衝突するのを防ぎ、ゼロバイト書き込みがEOFとして扱われることを回避します。

この修正は、Plan 9のI/Oモデルの特殊性を考慮しつつ、Goの標準ライブラリのクロスプラットフォームな振る舞いを維持するためのものです。

## コアとなるコードの変更箇所

変更は`src/os/file_plan9.go`ファイルにのみ行われています。

```diff
--- a/src/os/file_plan9.go
+++ b/src/os/file_plan9.go
@@ -259,6 +259,9 @@ func (f *File) pread(b []byte, off int64) (n int, err error) {
 // Since Plan 9 preserves message boundaries, never allow
 // a zero-byte write.
 func (f *File) write(b []byte) (n int, err error) {
+	if len(b) == 0 {
+		return 0, nil
+	}
 	return fixCount(syscall.Write(f.fd, b))
 }
```

## コアとなるコードの解説

変更は、`File`構造体の`write`メソッド内で行われています。

元のコードでは、`write`メソッドは常に`syscall.Write(f.fd, b)`を呼び出し、その結果を`fixCount`関数で処理していました。`fixCount`は、Plan 9のシステムコールが返すバイト数をGoの慣例に合わせるためのヘルパー関数です。

追加された3行のコードは以下の通りです。

```go
	if len(b) == 0 {
		return 0, nil
	}
```

このコードは、`write`メソッドの冒頭に追加されたガード句です。
- `len(b) == 0` は、書き込み対象のバイトスライス`b`の長さがゼロであるかどうかをチェックします。
- もし長さがゼロであれば、`return 0, nil`が実行されます。これは、0バイトが書き込まれ、エラーが発生しなかったことを意味します。

この変更により、ゼロバイト書き込みの要求が来た場合、実際のPlan 9システムコールである`syscall.Write`は呼び出されなくなります。これにより、Plan 9がゼロバイト書き込みをEOFとして解釈する可能性が完全に排除され、Goの`os`ライブラリが期待する「ゼロバイト書き込みはエラーなく完了する」という動作が保証されます。

この修正は、Plan 9の特殊なI/OセマンティクスをGoの標準ライブラリの期待に合わせるための、シンプルかつ効果的な方法です。

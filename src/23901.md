# [インデックス 23901] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、`darwin/amd64` (macOS上の64ビットIntelアーキテクチャ) 環境での `-buildmode=c-shared` のサポートを追加するものです。これにより、GoのコードをC言語から呼び出し可能な共有ライブラリ（macOSでは `.dylib` ファイル）としてビルドできるようになります。

## 元コミット内容

このコミットは、`cmd/link/internal/ld` (Goリンカの内部パッケージ) と `cmd/go` (Goコマンドラインツール) に、`darwin/amd64` プラットフォームでの `-buildmode=c-shared` オプションのサポートを追加します。コミットメッセージによると、この機能の大部分は、`darwin/arm64` 向けの外部リンキングサポートを実装した `minux@` の先行作業 (golang.org/cl/8781) に基づいています。

## 変更の背景

Go言語は、その強力な並行処理とシンプルな構文により、多くの開発者に利用されています。しかし、既存のC/C++コードベースや他の言語で書かれたアプリケーションと連携する際には、Goのコードを共有ライブラリとしてエクスポートできる機能が求められます。`-buildmode=c-shared` は、GoのパッケージをC言語のABI（Application Binary Interface）に準拠した共有ライブラリとしてビルドするためのオプションです。

このコミット以前は、`darwin/amd64` 環境ではこの `c-shared` モードが完全にサポートされていませんでした。特にmacOSのようなプラットフォームでは、リンカの挙動や共有ライブラリの形式（Mach-O形式の `.dylib`）がLinuxなどのELF形式とは異なるため、プラットフォーム固有の調整が必要となります。

この変更の背景には、`darwin/arm64` (macOS上のApple Siliconアーキテクチャ) 向けの同様のサポートが先行して実装されており、その知見を `darwin/amd64` にも適用することで、Goのクロスプラットフォームな共有ライブラリ生成能力を向上させる目的があります。これにより、macOS上の既存のC/C++/Objective-CアプリケーションからGoで書かれたロジックを容易に利用できるようになります。

## 前提知識の解説

*   **`go build -buildmode=c-shared`**: Goコンパイラ/リンカのオプションで、GoパッケージをC言語の呼び出し規約に準拠した共有ライブラリとしてビルドします。生成されるライブラリは、C言語のヘッダファイルと共に提供され、他の言語からGoの関数を呼び出すことができます。
*   **共有ライブラリ (Shared Library)**: 複数のプログラムから共有して利用されるライブラリのことです。WindowsではDLL、Linuxでは `.so` (Shared Object)、macOSでは `.dylib` (Dynamic Library) と呼ばれます。
*   **Mach-O (Mach Object)**: macOS (およびiOS) で使用される実行可能ファイル、オブジェクトコード、共有ライブラリのファイル形式です。LinuxのELF形式とは構造が異なります。
*   **リンカ (Linker)**: コンパイラによって生成されたオブジェクトファイルを結合し、実行可能ファイルやライブラリを生成するツールです。Goのツールチェインには独自のリンカ (`cmd/link`) が含まれていますが、CGOを使用する場合や特定のビルドモードでは、システムの外部リンカ (例: `clang` や `gcc`) を利用することがあります。
*   **`__TEXT` セグメントと `__DATA` セグメント**: Mach-Oファイルにおける主要なセグメントです。`__TEXT` セグメントは通常、実行可能なコードや読み取り専用データを格納し、書き込み不可としてマークされます。`__DATA` セグメントは、書き込み可能なデータ（初期化済みデータや未初期化データ）を格納します。
*   **絶対リロケーション (Absolute Relocation)**: プログラムの実行時に、特定のメモリアドレスに固定されるようにコードやデータを配置する方式です。共有ライブラリでは、ロードされるアドレスが実行時まで分からないため、通常は相対リロケーションが使用されます。絶対リロケーションが `__TEXT` セグメントに存在すると、外部リンカがエラーを出すことがあります。
*   **`LC_ID_DYLIB`**: Mach-Oのロードコマンドの一つで、ダイナミックライブラリ自身の識別情報を指定します。ライブラリのパスやバージョン情報などが含まれます。

## 技術的詳細

このコミットの技術的な核心は、`darwin/amd64` 環境におけるMach-O形式の共有ライブラリ生成に関するリンカの挙動を、Goのツールチェインが適切に処理できるように調整することにあります。

1.  **テストスクリプトの更新 (`misc/cgo/testcshared/test.bash`)**:
    *   `darwin/amd64` プラットフォームが `c-shared` ビルドモードでテストされるように、条件分岐が追加されました。
    *   macOSでは共有ライブラリの拡張子が `.so` ではなく `.dylib` であるため、ビルド出力ファイル名が `libgo.so` から `libgo.$libext` (ここで `$libext` は `dylib`) に変更されました。
    *   リンカフラグもmacOS向けに調整され、特に `test2` のケースでは、Linuxで使われる `-Wl,--no-as-needed` フラグがmacOSでは不要（または問題を引き起こす可能性）であるため、`darwin` の場合は空文字列に設定されています。

2.  **ビルドモードサポートの宣言 (`src/cmd/dist/test.go`, `src/cmd/go/build.go`)**:
    *   Goのビルドシステムが `darwin-amd64` を `c-shared` ビルドモードのサポート対象として認識するように、`supportedBuildmode` 関数に `darwin-amd64` が追加されました。
    *   `cmd/go` のビルドロジック (`buildModeInit`) においても、`darwin/amd64` が `c-shared` ビルドモードでサポートされるプラットフォームとして明示的に追加されました。

3.  **リンカフラグの調整 (`src/cmd/link/internal/ld/lib.go`)**:
    *   `darwin` プラットフォームのリンカフラグから `-pagezero_size,4000000` が削除され、実行可能ファイル (`BuildmodeExe`) の場合にのみ適用されるように変更されました。これは、共有ライブラリではページゼロセグメントのサイズ指定が不要、または異なる挙動が求められるためと考えられます。
    *   `BuildmodeCShared` の場合、`darwin` では外部リンカに `-dynamiclib` フラグを渡すように変更されました。これは、Mach-O形式で共有ライブラリを生成するための標準的なフラグです。Linuxなどで使われる `-Wl,-Bsymbolic` や `-shared` は、Mach-Oの共有ライブラリには適用されません。

4.  **Mach-Oセグメント配置の調整 (`src/cmd/link/internal/ld/macho.go`)**:
    *   この変更は特に重要です。外部リンカが `__TEXT` セグメント内の絶対リロケーションについて警告またはエラーを出す問題を回避するためのものです。
    *   以前は `darwin/arm64` の場合にのみ、実行可能でないセクション (`sect.Rwx&1 == 0`) を `__DATA` セグメントに配置するロジックがありました。
    *   このコミットでは、その条件に `darwin/amd64` かつ `BuildmodeCShared` の場合が追加されました。これにより、`darwin/amd64` で `c-shared` ライブラリをビルドする際にも、非実行可能セクションが `__DATA` に適切に配置され、リンカのエラーを回避できるようになります。

5.  **DWARF情報結合の調整 (`src/cmd/link/internal/ld/macho_combine_dwarf.go`)**:
    *   `LC_ID_DYLIB` ロードコマンドが、DWARF情報の結合時に更新不要なロードコマンドのリストに追加されました。これは、共有ライブラリ自身の識別情報である `LC_ID_DYLIB` が、DWARF情報の結合プロセスにおいて特別な処理を必要としないことを示しています。

これらの変更により、Goのツールチェインは `darwin/amd64` 上でC言語互換の共有ライブラリを生成する際に、macOSのリンカの要件とMach-Oファイル形式の特性を適切に満たすことができるようになりました。

## コアとなるコードの解説

*   **`misc/cgo/testcshared/test.bash`**: このシェルスクリプトは、`c-shared` ビルドモードで生成されたGoの共有ライブラリが正しく機能するかをテストするためのものです。変更点では、`darwin/amd64` 環境でのテストを有効にし、macOSの共有ライブラリの命名規則 (`.dylib`) に対応させ、リンカフラグをプラットフォームに応じて調整しています。これにより、macOS上での `c-shared` ライブラリのビルドと利用がテストされるようになります。
*   **`src/cmd/dist/test.go` と `src/cmd/go/build.go`**: これらのファイルは、Goのビルドシステムと `go` コマンドが、どのプラットフォームでどのビルドモードをサポートしているかを定義しています。`darwin/amd64` が `c-shared` ビルドモードのサポート対象として明示的に追加されたことで、`go build -buildmode=c-shared` コマンドが `darwin/amd64` で実行可能になります。
*   **`src/cmd/link/internal/ld/lib.go`**: Goリンカのプラットフォーム共通のロジックが含まれています。このコミットでは、`darwin` 環境でのリンカフラグが細かく調整されました。特に、共有ライブラリ (`BuildmodeCShared`) をビルドする際に、macOSの外部リンカが共有ライブラリを生成するために必要な `-dynamiclib` フラグが渡されるようになりました。これにより、GoのリンカがmacOSのリンカと正しく連携し、有効な `.dylib` ファイルを生成できるようになります。
*   **`src/cmd/link/internal/ld/macho.go`**: Mach-Oファイル形式に特化したリンカのロジックです。このファイルへの変更は、`darwin/amd64` で `c-shared` ライブラリをビルドする際に、非実行可能セクションを `__DATA` セグメントに配置するという重要な調整を行っています。これは、macOSの外部リンカが `__TEXT` セグメント内の絶対リロケーションに対して厳格であり、エラーを回避するために必要な措置です。この変更により、生成される `.dylib` ファイルがmacOSのリンカの要件を満たし、正しくロード・実行されるようになります。
*   **`src/cmd/link/internal/ld/macho_combine_dwarf.go`**: DWARFデバッグ情報の結合に関するMach-O固有の処理です。`LC_ID_DYLIB` が更新不要なロードコマンドのリストに追加されたことで、DWARF情報の処理が共有ライブラリの識別情報に影響を与えないように、より堅牢になりました。

これらの変更は、Goのツールチェインが `darwin/amd64` 上でC言語互換の共有ライブラリを生成する際の、プラットフォーム固有の複雑な要件を吸収し、開発者がGoのコードをmacOSアプリケーションに組み込みやすくするための基盤を強化しています。

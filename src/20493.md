# [インデックス 20493] ファイルの概要

このコミットは、Goランタイムの`src/runtime/sys_plan9_amd64.s`ファイルに対する変更です。このファイルは、Plan 9オペレーティングシステム上でAMD64アーキテクチャを使用する際のGoランタイムの低レベルなアセンブリコードを含んでいます。具体的には、新しいM（OSスレッド）が起動される際の初期化処理、特にプロセスID（pid）の取得と設定に関連する部分を扱っています。

## コミット

このコミットは、Plan 9/amd64環境において、新しいM（OSスレッド）が起動される際に、`Tos`構造体から正しいプロセスID（pid）を保存するように修正します。以前は64ビットのロード命令を使用していたため、32ビットのpidフィールドの隣にあるプロファイリングクロック用のフィールドも誤って読み込んでしまい、pidが正しく設定されない問題がありました。この変更により、32ビットのpidフィールドのみを正確にロードするように修正されています。

## 元コミット内容

The pid field in the Tos structure is a 32-bit value.
Loading a 64-bit word also brings in the next field
which is used for the profiling clock.

## 変更の背景

この変更の背景には、GoランタイムがPlan 9/amd64環境で新しいOSスレッド（Goのスケジューラにおける`m`構造体）を初期化する際に、そのスレッドのプロセスID（pid）を取得する方法に問題があったことが挙げられます。

具体的には、pidは`Tos`（Thread-local storageのトップオブスタック）構造体内に格納されており、このpidフィールドは32ビットの値として定義されていました。しかし、既存のアセンブリコードでは、この32ビットのpidを読み込む際に`MOVQ`という64ビットのロード命令を使用していました。

問題は、`Tos`構造体内でpidフィールドの直後に、プロファイリングクロック（パフォーマンス測定に使用されるタイマー）のための別のフィールドが配置されていたことです。`MOVQ`命令で64ビットを読み込むと、32ビットのpidだけでなく、その隣接するプロファイリングクロックのフィールドの一部または全体も一緒に読み込んでしまい、結果としてAXレジスタに正しいpidがロードされませんでした。これにより、`m->procid`に保存されるpidが不正な値になったり、プロファイリングデータに悪影響を与えたりする可能性がありました。

このコミットは、このデータアライメントとロード命令の不一致によって引き起こされるバグを修正するために行われました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション、スケジューラ（ゴルーチンとOSスレッドのマッピング）、メモリ管理などが含まれます。Goプログラムは、OS上で直接実行されるのではなく、Goランタイム上で実行されます。
*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステムです。Go言語の開発者の一部はPlan 9の設計にも関わっており、GoランタイムにはPlan 9に特化したコードパスがいくつか存在します。
*   **AMD64**: x86-64とも呼ばれる64ビットの命令セットアーキテクチャです。現代のほとんどのデスクトップおよびサーバーCPUで使用されています。
*   **アセンブリ言語 (`.s` ファイル)**: Goランタイムの一部は、パフォーマンスの最適化、OSとの直接的なインタラクション、または特定のハードウェア機能へのアクセスなどの理由から、アセンブリ言語で記述されています。`src/runtime/sys_plan9_amd64.s`は、Plan 9/AMD64環境に特化したアセンブリコードを含んでいます。
*   **`_tos(SB)`**: Plan 9におけるスレッドローカルストレージ（TLS）の概念に関連するシンボルです。`_tos`は「top of stack」を意味し、Plan 9のシステムコールやスレッド管理において重要な役割を果たす構造体へのポインタを提供します。この構造体には、現在のスレッドに関する情報（例えば、プロセスID）が含まれています。`SB`は「static base」を意味し、グローバルシンボルを参照する際に使用されます。
*   **`m` (M struct)**: Goのスケジューラにおける「Machine」または「OSスレッド」を表す構造体です。Goのスケジューラは、ゴルーチン（G）を論理プロセッサ（P）上で実行し、PはOSスレッド（M）上で実行されます。新しいMが起動される際には、そのMに関連するOSのプロセスIDなどの情報が初期化されます。
*   **`procid`**: プロセスID（Process ID）の略で、オペレーティングシステムが実行中のプロセスに割り当てる一意の識別子です。Goランタイムは、デバッグやプロファイリングなどの目的で、現在のOSスレッドのpidを内部的に保持することがあります。
*   **`MOVQ` と `MOVL` アセンブリ命令**:
    *   `MOVQ`: "Move Quadword" の略で、64ビットのデータを移動する命令です。
    *   `MOVL`: "Move Longword" の略で、32ビットのデータを移動する命令です。
    これらの命令は、レジスタとメモリ間でデータを転送するために使用されます。データのサイズ（ビット幅）が重要であり、誤ったサイズの命令を使用すると、意図しないデータが読み込まれたり、データが切り捨てられたりする可能性があります。

## 技術的詳細

このコミットの技術的な核心は、メモリからのデータロードにおける命令のビット幅の不一致を修正することにあります。

Goランタイムは、新しいOSスレッド（`m`）を初期化する際に、そのスレッドのプロセスID（pid）を`Tos`構造体から取得します。`Tos`構造体は、Plan 9のシステムコールインターフェースの一部として、スレッド固有の情報を保持しています。

問題の箇所は、`src/runtime/sys_plan9_amd64.s`内の`runtime·tstart_plan9`関数にありました。この関数は、新しいMが開始される際に呼び出され、その中で`Tos`構造体からpidを読み込む処理が含まれています。

元のコードでは、`Tos`構造体のアドレスをAXレジスタにロードした後、`64(AX)`というオフセットからデータを読み込んでいました。このオフセット`64`は、`Tos`構造体の先頭から64バイト目にpidフィールドが位置していることを示しています。

しかし、ここで使用されていた命令は`MOVQ 64(AX), AX`でした。
*   `MOVQ`は64ビットのデータを読み込む命令です。
*   `Tos`構造体内の`pid`フィールドは32ビットとして定義されていました。

この状況で`MOVQ`を使用すると、メモリレイアウトによっては、32ビットの`pid`フィールドだけでなく、その直後に続くメモリ領域（この場合はプロファイリングクロック用のフィールド）の32ビットも一緒に読み込んでしまい、合計64ビットのデータがAXレジスタに格納されていました。これにより、AXレジスタには意図しないデータ（pidとプロファイリングクロックの一部）が混在した状態となり、その後の`MOVQ AX, m_procid(CX)`命令で`m->procid`に保存されるpidが不正な値になっていました。

修正は、`MOVQ 64(AX), AX`を`MOVL 64(AX), AX`に変更することです。
*   `MOVL`は32ビットのデータを読み込む命令です。

これにより、`Tos`構造体のオフセット64バイト目から正確に32ビットのpidフィールドのみがAXレジスタにロードされるようになります。その結果、`m->procid`には正しいプロセスIDが保存され、ランタイムの動作が安定し、プロファイリングデータへの潜在的な悪影響も排除されます。

この修正は、アセンブリレベルでの正確なデータ型と命令の選択がいかに重要であるかを示す典型的な例です。特に、構造体のメモリレイアウトと、それを操作するアセンブリ命令のビット幅が一致していることを確認することが不可欠です。

## コアとなるコードの解説

変更されたコードは、`src/runtime/sys_plan9_amd64.s`ファイル内の`runtime·tstart_plan9`というアセンブリ関数の一部です。この関数は、Goランタイムが新しいOSスレッド（M）を開始する際に呼び出されます。

変更前のコード:
```assembly
 	// Initialize procid from TOS struct.
 	MOVQ	_tos(SB), AX
 	MOVQ	64(AX), AX
 	MOVQ	AX, m_procid(CX)	// save pid as m->procid
```

1.  `MOVQ _tos(SB), AX`:
    *   `_tos(SB)`は、Plan 9のシステムが提供するスレッドローカルな`Tos`構造体へのポインタです。
    *   この命令は、`_tos`シンボルが指すアドレス（`Tos`構造体のベースアドレス）を64ビット値としてAXレジスタにロードします。AXレジスタは汎用レジスタで、ここでは`Tos`構造体へのポインタを保持するために使用されます。

2.  `MOVQ 64(AX), AX`:
    *   `64(AX)`は、AXレジスタに格納されているアドレス（`Tos`構造体のベースアドレス）から64バイトのオフセットにあるメモリ位置を指します。
    *   **問題点**: ここで`MOVQ`（Move Quadword）命令が使用されています。これは64ビットのデータをメモリからAXレジスタにロードすることを意味します。しかし、`Tos`構造体内の`pid`フィールドは32ビット幅でした。このため、`pid`フィールドの32ビットだけでなく、その直後に続くメモリ領域（プロファイリングクロック用のフィールド）の32ビットも一緒に読み込んでしまい、AXレジスタには意図しない64ビットの値が格納されていました。

3.  `MOVQ AX, m_procid(CX)`:
    *   `m_procid(CX)`は、CXレジスタに格納されている`m`構造体（現在のOSスレッドを表すGoランタイムの構造体）のベースアドレスから`procid`フィールドへのオフセットを指します。
    *   この命令は、AXレジスタに格納されている64ビットの値を`m`構造体の`procid`フィールドに保存します。AXレジスタの値が不正なため、`m->procid`にも不正な値が書き込まれていました。

変更後のコード:
```assembly
 	// Initialize procid from TOS struct.
 	MOVQ	_tos(SB), AX
 	MOVL	64(AX), AX
 	MOVQ	AX, m_procid(CX)	// save pid as m->procid
```

変更点は2行目の`MOVQ 64(AX), AX`が`MOVL 64(AX), AX`になったことです。

1.  `MOVQ _tos(SB), AX`: (変更なし)
    *   `Tos`構造体のベースアドレスをAXレジスタにロードします。

2.  `MOVL 64(AX), AX`:
    *   `64(AX)`は、AXレジスタに格納されているアドレスから64バイトのオフセットにあるメモリ位置を指します。
    *   **修正点**: ここで`MOVL`（Move Longword）命令が使用されています。これは32ビットのデータをメモリからAXレジスタにロードすることを意味します。`pid`フィールドが32ビットであるため、この命令は正確に`pid`フィールドの値のみを読み込み、AXレジスタの残りのビット（上位32ビット）はゼロクリアされます（これはx86-64アーキテクチャにおける32ビットロード命令の一般的な動作です）。これにより、AXレジスタには正しい32ビットのpid値が格納されます。

3.  `MOVQ AX, m_procid(CX)`: (変更なし)
    *   AXレジスタに格納されている正しい32ビットのpid値（上位32ビットはゼロ）が、`m`構造体の`procid`フィールドに64ビット値として保存されます。`m->procid`が64ビットフィールドであっても、AXの上位ビットがゼロであるため、正しいpidが格納されます。

この変更により、`Tos`構造体から`pid`を読み込む際のビット幅の不一致が解消され、Goランタイムが新しいOSスレッドのプロセスIDを正確に取得・設定できるようになりました。

*   `MOVL`は32ビットのデータを読み込む命令です。

これにより、`Tos`構造体のオフセット64バイト目から正確に32ビットのpidフィールドのみがAXレジスタにロードされるようになります。その結果、`m->procid`には正しいプロセスIDが保存され、ランタイムの動作が安定し、プロファイリングデータへの潜在的な悪影響も排除されます。

この修正は、アセンブリレベルでの正確なデータ型と命令の選択がいかに重要であるかを示す典型的な例です。特に、構造体のメモリレイアウトと、それを操作するアセンブリ命令のビット幅が一致していることを確認することが不可欠です。

## コアとなるコードの解説

変更されたコードは、`src/runtime/sys_plan9_amd64.s`ファイル内の`runtime·tstart_plan9`というアセンブリ関数の一部です。この関数は、Goランタイムが新しいOSスレッド（M）を開始する際に呼び出されます。

変更前のコード:
```assembly
 	// Initialize procid from TOS struct.
 	MOVQ	_tos(SB), AX
 	MOVQ	64(AX), AX
 	MOVQ	AX, m_procid(CX)	// save pid as m->procid
```

1.  `MOVQ _tos(SB), AX`:
    *   `_tos(SB)`は、Plan 9のシステムが提供するスレッドローカルな`Tos`構造体へのポインタです。
    *   この命令は、`_tos`シンボルが指すアドレス（`Tos`構造体のベースアドレス）を64ビット値としてAXレジスタにロードします。AXレジスタは汎用レジスタで、ここでは`Tos`構造体へのポインタを保持するために使用されます。

2.  `MOVQ 64(AX), AX`:
    *   `64(AX)`は、AXレジスタに格納されているアドレス（`Tos`構造体のベースアドレス）から64バイトのオフセットにあるメモリ位置を指します。
    *   **問題点**: ここで`MOVQ`（Move Quadword）命令が使用されています。これは64ビットのデータをメモリからAXレジスタにロードすることを意味します。しかし、`Tos`構造体内の`pid`フィールドは32ビット幅でした。このため、`pid`フィールドの32ビットだけでなく、その直後に続くメモリ領域（プロファイリングクロック用のフィールド）の32ビットも一緒に読み込んでしまい、合計64ビットのデータがAXレジスタに格納されていました。

3.  `MOVQ AX, m_procid(CX)`:
    *   `m_procid(CX)`は、CXレジスタに格納されている`m`構造体（現在のOSスレッドを表すGoランタイムの構造体）のベースアドレスから`procid`フィールドへのオフセットを指します。
    *   この命令は、AXレジスタに格納されている64ビットの値を`m`構造体の`procid`フィールドに保存します。AXレジスタの値が不正なため、`m->procid`にも不正な値が書き込まれていました。

変更後のコード:
```assembly
 	// Initialize procid from TOS struct.
 	MOVQ	_tos(SB), AX
 	MOVL	64(AX), AX
 	MOVQ	AX, m_procid(CX)	// save pid as m->procid
```

変更点は2行目の`MOVQ 64(AX), AX`が`MOVL 64(AX), AX`になったことです。

1.  `MOVQ _tos(SB), AX`: (変更なし)
    *   `Tos`構造体のベースアドレスをAXレジスタにロードします。

2.  `MOVL 64(AX), AX`:
    *   `64(AX)`は、AXレジスタに格納されているアドレスから64バイトのオフセットにあるメモリ位置を指します。
    *   **修正点**: ここで`MOVL`（Move Longword）命令が使用されています。これは32ビットのデータをメモリからAXレジスタにロードすることを意味します。`pid`フィールドが32ビットであるため、この命令は正確に`pid`フィールドの値のみを読み込み、AXレジスタの残りのビット（上位32ビット）はゼロクリアされます（これはx86-64アーキテクチャにおける32ビットロード命令の一般的な動作です）。これにより、AXレジスタには正しい32ビットのpid値が格納されます。

3.  `MOVQ AX, m_procid(CX)`: (変更なし)
    *   AXレジスタに格納されている正しい32ビットのpid値（上位32ビットはゼロ）が、`m`構造体の`procid`フィールドに64ビット値として保存されます。`m->procid`が64ビットフィールドであっても、AXの上位ビットがゼロであるため、正しいpidが格納されます。

この変更により、`Tos`構造体から`pid`を読み込む際のビット幅の不一致が解消され、Goランタイムが新しいOSスレッドのプロセスIDを正確に取得・設定できるようになりました。

## 変更の背景

このコミットの主な目的は、Goコンパイラのパーサーにおけるコードの簡素化と、エラーメッセージのより適切な配置です。具体的には、`parser.compound_stmt`関数が持っていた`else_clause`というブール型パラメータを削除し、`if`文に関するエラー処理を`if_stmt`関数内に移動させています。

以前の実装では、`compound_stmt`関数が`else`節の一部として呼び出されるかどうかを`else_clause`パラメータで判断し、それに基づいてエラーメッセージを生成していました。しかし、このような設計は関数の責務を曖昧にし、コードの可読性や保守性を低下させる可能性があります。`if`文に関連するエラーは、`if`文を解析する`if_stmt`関数内で処理されるべきであり、`compound_stmt`のような汎用的なブロック解析関数がその詳細を知る必要はありません。

この変更により、以下の利点が期待されます。

1.  **責務の分離**: `compound_stmt`は純粋にブロックステートメント（`{ ... }`）の解析に集中し、`if_stmt`は`if`文全体の解析とそれに伴うエラー処理に集中できるようになります。
2.  **コードの簡素化**: `else_clause`パラメータとその関連ロジックが削除されることで、`compound_stmt`関数のコードが短く、理解しやすくなります。
3.  **エラーメッセージの精度向上**: エラーが発生したコンテキスト（`if`文の`else`節）で直接エラーメッセージが生成されるため、より正確で分かりやすい診断が可能になります。

### Goコンパイラ (`cmd/compile`)

Go言語のコンパイラは、`cmd/compile`ディレクトリにあります。これは、Goのソースコードを機械語に変換する主要なツールです。コンパイルプロセスは通常、以下の主要なフェーズに分けられます。

4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、プラットフォーム非依存の中間表現（IR）を生成します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードをターゲットプラットフォームの機械語に変換します。

`src/cmd/compile/internal/gc/parser.go`は、Goコンパイラの構文解析器の実装の一部です。このファイルには、Go言語の様々な構文要素（ステートメント、式、宣言など）を解析するためのメソッドが含まれています。

-   **`p.advance(token1, token2)`**: エラーリカバリのために、指定されたトークンのいずれかが見つかるまでトークンを読み飛ばします。

### 抽象構文木 (AST)

パーサーは、ソースコードの構造を表現する抽象構文木（AST）を構築します。ASTは、プログラムの構造を階層的に表現したツリー構造で、コンパイラの後のフェーズで利用されます。

### `compound_stmt` (複合ステートメント/ブロック)

Go言語における複合ステートメント、またはブロックは、波括弧`{}`で囲まれた一連のステートメントです。例えば、`if`文の本体、`for`ループの本体、関数の本体などがこれに該当します。パーサーでは、`compound_stmt`関数がこの`{ ... }`ブロックを解析し、その中のステートメントリストを抽出します。

### `if_stmt` (ifステートメント)

`if_stmt`関数は、Go言語の`if`ステートメント（`if condition { ... } else if condition { ... } else { ... }`）全体を解析する役割を担います。これには、条件式、`then`ブロック、およびオプションの`else`節（`else if`または`else`ブロック）の解析が含まれます。

## 技術的詳細

このコミットの技術的な核心は、`parser.compound_stmt`関数のシグネチャ変更と、`if_stmt`関数内でのエラー処理の再配置です。

### `compound_stmt`関数の変更

変更前:
```go
func (p *parser) compound_stmt(else_clause bool) *Node {
    // ...
    if p.got('{') {
        // ok
    } else if else_clause {
        p.syntax_error("else must be followed by if or statement block")
        p.advance(LNAME, '}')
    } else {
        panic("unreachable")
    }
    // ...
}
```
変更後:
```go
func (p *parser) compound_stmt() *Node {
    // ...
    p.want('{') // 常に '{' を期待する
    // ...
}
```
変更前は、`compound_stmt`が`else`節の一部として呼び出された場合（`else_clause`が`true`の場合）、`{`が続くことを期待し、そうでなければエラーを報告していました。しかし、`compound_stmt`の本来の役割は、`{`で始まるブロックを解析することです。`else`節の文脈でのエラーは、`if_stmt`が処理すべきです。

変更後は、`compound_stmt`は常に`{`トークンを期待するようになりました。これは、`compound_stmt`が呼び出される時点では、すでに`{`トークンが存在することが保証されているべきであるという設計思想に基づいています。もし`{`がなければ、それは`compound_stmt`を呼び出す側の問題であり、その呼び出し元（この場合は`if_stmt`）がエラーを適切に処理すべきです。

また、`compound_stmt`内で`OEMPTY`ノードを生成するロジックも簡素化されています。以前は`stmt`変数を介して行われていましたが、直接`return Nod(OEMPTY, nil, nil)`を返す形に変更されました。

### `if_stmt`関数でのエラー処理の移動

変更前:
```go
func (p *parser) if_stmt() *Node {
    // ...
    if p.got(LELSE) {
        if p.tok == LIF {
            stmt.Rlist.Set1(p.if_stmt())
        } else {
            cs := p.compound_stmt(true) // ここで else_clause=true を渡していた
            // ...
        }
    }
    // ...
}
```
変更後:
```go
func (p *parser) if_stmt() *Node {
    // ...
    if p.got(LELSE) {
        switch p.tok {
        case LIF:
            stmt.Rlist.Set1(p.if_stmt())
        case '{':
            cs := p.compound_stmt() // else_clause パラメータがなくなった
            // ...
        default:
            p.syntax_error("else must be followed by if or statement block") // エラーメッセージがここに移動
            p.advance(LNAME, '}')
        }
    }
    // ...
}
```
`if_stmt`関数では、`LELSE`（`else`キーワード）の後に続くトークンをチェックするロジックが変更されました。

-   `else if`の場合（`p.tok == LIF`）、再帰的に`if_stmt`を呼び出すのは以前と同じです。
-   `else { ... }`の場合（`p.tok == '{'`）、`compound_stmt()`を呼び出します。この際、`else_clause`パラメータは不要になりました。
-   `else`の後に`if`でも`{`でもない不正なトークンが来た場合、`default`ケースで`p.syntax_error("else must be followed by if or statement block")`というエラーメッセージが生成されるようになりました。このエラーメッセージは、以前は`compound_stmt`内で`else_clause`が`true`の場合に生成されていたものです。

この変更により、`if`文の`else`節の構文に関するエラーは、`if`文全体を解析する`if_stmt`関数が直接責任を持つことになり、エラーの発生源と報告箇所が一致するようになりました。これにより、パーサーのロジックがより明確になり、デバッグや将来の変更が容易になります。

-   **`p.want(token)`**: 現在のトークンが指定された`token`と一致することを期待し、一致しなければエラーを報告します。
-   **`p.syntax_error(msg)`**: 構文エラーを報告します。
-   **`p.advance(token1, token2)`**: エラーリカバリのために、指定されたトークンのいずれかが見つかるまでトークンを読み飛ばします。

### 抽象構文木 (AST)

パーサーは、ソースコードの構造を表現する抽象構文木（AST）を構築します。ASTは、プログラムの構造を階層的に表現したツリー構造で、コンパイラの後のフェーズで利用されます。

### `compound_stmt` (複合ステートメント/ブロック)

Go言語における複合ステートメント、またはブロックは、波括弧`{}`で囲まれた一連のステートメントです。例えば、`if`文の本体、`for`ループの本体、関数の本体などがこれに該当します。パーサーでは、`compound_stmt`関数がこの`{ ... }`ブロックを解析し、その中のステートメントリストを抽出します。

### `if_stmt` (ifステートメント)

`if_stmt`関数は、Go言語の`if`ステートメント（`if condition { ... } else if condition { ... } else { ... }`）全体を解析する役割を担います。これには、条件式、`then`ブロック、およびオプションの`else`節（`else if`または`else`ブロック）の解析が含まれます。

## 技術的詳細

このコミットの技術的な核心は、`parser.compound_stmt`関数のシグネチャ変更と、`if_stmt`関数内でのエラー処理の再配置です。

### `compound_stmt`関数の変更

変更前:
```go
func (p *parser) compound_stmt(else_clause bool) *Node {
    // ...
    if p.got('{') {
        // ok
    } else if else_clause {
        p.syntax_error("else must be followed by if or statement block")
        p.advance(LNAME, '}')
    } else {
        panic("unreachable")
    }
    // ...
}
```
変更後:
```go
func (p *parser) compound_stmt() *Node {
    // ...
    p.want('{') // 常に '{' を期待する
    // ...
}
```
変更前は、`compound_stmt`が`else`節の一部として呼び出された場合（`else_clause`が`true`の場合）、`{`が続くことを期待し、そうでなければエラーを報告していました。しかし、`compound_stmt`の本来の役割は、`{`で始まるブロックを解析することです。`else`節の文脈でのエラーは、`if_stmt`が処理すべきです。

変更後は、`compound_stmt`は常に`{`トークンを期待するようになりました。これは、`compound_stmt`が呼び出される時点では、すでに`{`トークンが存在することが保証されているべきであるという設計思想に基づいています。もし`{`がなければ、それは`compound_stmt`を呼び出す側の問題であり、その呼び出し元（この場合は`if_stmt`）がエラーを適切に処理すべきです。

また、`compound_stmt`内で`OEMPTY`ノードを生成するロジックも簡素化されています。以前は`stmt`変数を介して行われていましたが、直接`return Nod(OEMPTY, nil, nil)`を返す形に変更されました。

### `if_stmt`関数でのエラー処理の移動

変更前:
```go
func (p *parser) if_stmt() *Node {
    // ...
    if p.got(LELSE) {
        if p.tok == LIF {
            stmt.Rlist.Set1(p.if_stmt())
        } else {
            cs := p.compound_stmt(true) // ここで else_clause=true を渡していた
            // ...
        }
    }
    // ...
}
```
変更後:
```go
func (p *parser) if_stmt() *Node {
    // ...
    if p.got(LELSE) {
        switch p.tok {
        case LIF:
            stmt.Rlist.Set1(p.if_stmt())
        case '{':
            cs := p.compound_stmt() // else_clause パラメータがなくなった
            // ...
        default:
            p.syntax_error("else must be followed by if or statement block") // エラーメッセージがここに移動
            p.advance(LNAME, '}')
        }
    }
    // ...
}
```
`if_stmt`関数では、`LELSE`（`else`キーワード）の後に続くトークンをチェックするロジックが変更されました。

-   `else if`の場合（`p.tok == LIF`）、再帰的に`if_stmt`を呼び出すのは以前と同じです。
-   `else { ... }`の場合（`p.tok == '{'`）、`compound_stmt()`を呼び出します。この際、`else_clause`パラメータは不要になりました。
-   `else`の後に`if`でも`{`でもない不正なトークンが来た場合、`default`ケースで`p.syntax_error("else must be followed by if or statement block")`というエラーメッセージが生成されるようになりました。このエラーメッセージは、以前は`compound_stmt`内で`else_clause`が`true`の場合に生成されていたものです。

この変更により、`if`文の`else`節の構文に関するエラーは、`if`文全体を解析する`if_stmt`関数が直接責任を持つことになり、エラーの発生源と報告箇所が一致するようになりました。これにより、パーサーのロジックがより明確になり、デバッグや将来の変更が容易になります。

## コアとなるコードの解説

### `func (p *parser) compound_stmt()` の変更点

-   **シグネチャの変更**:
    -   `func (p *parser) compound_stmt(else_clause bool) *Node` から `func (p *parser) compound_stmt() *Node` へと変更され、`else_clause`パラメータが削除されました。
-   **`{` トークンの処理**:
    -   変更前は`if p.got('{') { ... } else if else_clause { ... } else { panic(...) }`という複雑なロジックで`{`トークンを処理していました。`else_clause`が`true`の場合に`else must be followed by if or statement block`というエラーをここで生成していました。
    -   変更後は、シンプルに`p.want('{')`となりました。これは、`compound_stmt`が呼び出される際には常に`{`トークンが存在することを期待するという、より厳密な契約を導入しています。もし`{`がなければ、`p.want`がエラーを報告します。
-   **`OEMPTY` ノードの生成**:
    -   `if len(l) == 0`（ステートメントリストが空の場合）の処理が簡素化されました。
    -   変更前は`stmt = Nod(OEMPTY, nil, nil)`と一時変数`stmt`に代入してから`return stmt`していました。
    -   変更後は`return Nod(OEMPTY, nil, nil)`と直接返すようになり、不要な変数`stmt`の宣言と代入がなくなりました。
-   **`popdcl()` の移動**:
    -   `popdcl()`の呼び出し位置が、`if len(l) == 0`ブロックの直後から、`p.want('}')`の直後に移動しました。これにより、スコープの終了処理がより適切に行われるようになります。

### `func (p *parser) if_stmt()` の変更点

-   **`else` 節の処理ロジックの変更**:
    -   `if p.got(LELSE)`ブロック内で、`else`の後に続くトークンを処理するロジックが`if/else`から`switch`ステートメントに変更されました。
    -   **`case LIF`**: `else if`の場合の処理は変更ありません。再帰的に`p.if_stmt()`を呼び出します。
    -   **`case '{'`**: `else { ... }`の場合、`p.compound_stmt()`を呼び出します。ここで、`compound_stmt`に`else_clause`パラメータを渡す必要がなくなりました。
    -   **`default`**: `else`の後に`if`でも`{`でもない不正なトークンが来た場合の新しいケースです。ここで、`p.syntax_error("else must be followed by if or statement block")`というエラーメッセージが生成され、`p.advance(LNAME, '}')`でエラーリカバリを行います。このエラーメッセージは、以前`compound_stmt`が担当していたものです。

### `func (p *parser) stmt()` の変更点

-   **`{` トークンの処理**:
    -   `case '{':` の部分で、`return p.compound_stmt(false)` から `return p.compound_stmt()` に変更されました。`compound_stmt`のシグネチャ変更に伴う修正です。

これらの変更により、`compound_stmt`は純粋にブロックの解析に特化し、`if_stmt`が`if`文全体の構文とエラー処理の責任を負うという、よりクリーンな設計が実現されています。

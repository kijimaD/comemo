# [インデックス 24495] ファイルの概要

このコミットは、Goランタイムにおける`systemstack`のトレースバック機能が、Native Client (NaCl) 環境のARMアーキテクチャで正しく動作しない問題を修正するものです。具体的には、スタックトレースバック時にプログラムカウンタ（PC）が誤った位置を指すことを防ぐため、ARMアセンブリコードに調整が加えられました。

## 変更の背景

Goランタイムは、ガベージコレクション、スタックの拡張・縮小、Cgo呼び出しなど、特定の低レベル操作のために「システムスタック」（`g0`スタックとも呼ばれる）を使用します。これらの操作は、通常のゴルーチンスタックとは独立して実行され、プリエンプション（横取り）されないことが保証されます。

このコミットは、GoがNative Client (NaCl) 環境でARMアーキテクチャをターゲットにしていた際に発生した問題に対処しています。NaClは、ウェブブラウザ内でネイティブコードをサンドボックス化して実行するためのGoogleの技術でした（現在は非推奨）。GoはかつてNaClをサポートしており、Go 1.3ツールチェーンはNaClバイナリを生成できました。

問題は、`systemstack`上で実行されるコードのスタックトレースバックが、`nacl/arm`環境で正しく機能しないことでした。スタックトレースバックは、プログラムの実行中にエラーが発生した際に、どの関数がどの順序で呼び出されたかを示す重要なデバッグ情報です。これが正しく表示されないと、問題の特定とデバッグが非常に困難になります。

具体的には、`systemstack_switch`というランタイム関数が、スタックトレースバックのために現在のプログラムカウンタ（PC）を保存する際に、NaCl特有の命令挿入やARMの命令セットの特性により、PCが期待される値からずれてしまうことが原因でした。このずれを修正し、正確なトレースバックを可能にすることがこのコミットの目的です。

## 前提知識の解説

### Goランタイムにおける`systemstack` (g0スタック)

Goランタイムは、各ゴルーチンに独自のスタック（ユーザーゴルーチンスタック）を割り当てますが、これとは別に「システムスタック」（`g0`スタック）と呼ばれる特別なスタックも使用します。システムスタックは、OSスレッド（Goランタイムの「M」）に関連付けられており、以下のような重要なランタイム内部操作のために使われます。

*   **スタックの管理**: ゴルーチンスタックの拡張や縮小といった操作は、システムスタック上で行われます。これにより、ユーザーゴルーチンスタックの変更中に、そのスタック自体が不安定になることを防ぎます。
*   **ガベージコレクション**: ガベージコレクタの特定フェーズは、システムスタック上で実行され、ユーザーゴルーチンスタックのスキャンと分離を確実にします。
*   **Cgo呼び出し**: GoコードがCコードを呼び出す際、Goのスタック管理規則に従わない可能性のあるCコードのために、安全な環境としてシステムスタックに切り替えることがあります。
*   **スケジューラ操作**: スケジューラのコアロジック（例: `stackalloc`）は、デッドロックを防ぎ、安定性を確保するためにシステムスタック上で実行されます。

システムスタック上で実行されるコードは、通常プリエンプションされず、ガベージコレクタによってスキャンされません。

### Native Client (NaCl)

Native Client (NaCl) は、Googleが開発したサンドボックス技術で、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行することを目的としていました。これにより、ウェブアプリケーションはネイティブアプリケーションに近いパフォーマンスと機能を利用できると期待されました。NaClはARMプロセッサもサポートしており、Goも一時期NaCl環境へのコンパイルをサポートしていました。しかし、NaClは現在では非推奨の技術となっています。

### スタックトレースバックの重要性

スタックトレースバック（またはバックトレース）は、プログラムがクラッシュしたり、特定のポイントに到達したりしたときに、現在実行中の関数に至るまでの関数呼び出しの履歴を示すものです。これはデバッグにおいて極めて重要な情報であり、問題がどこで、どのように発生したかを理解するのに役立ちます。トレースバックが不正確であると、デバッグ作業は著しく困難になります。

### ARMアセンブリの基本的な知識

*   **PC (Program Counter) レジスタ**: ARMアーキテクチャでは、PCレジスタ（R15）は次に実行される命令のアドレスを保持します。しかし、命令のフェッチパイプラインのため、PCレジスタが実際に指すアドレスは、現在実行中の命令のアドレスから数バイト（通常は8バイト）進んだ位置になることがあります。
*   **命令長**: ARM命令は通常4バイト長です。
*   **`MOVW`**: レジスタにワード（4バイト）を移動する命令。
*   **`ADD`**: レジスタに値を加算する命令。
*   **`SB` (Static Base)**: Goアセンブリにおけるシンボル参照のベースアドレス。
*   **`gobuf_pc`**: `gobuf`構造体内のプログラムカウンタを保存するフィールドのオフセット。

## 技術的詳細

このコミットの核心は、`systemstack_switch`関数が`gobuf`構造体にプログラムカウンタ（PC）を保存する際のオフセットの調整です。

`systemstack_switch`は、システムスタックへの切り替えを行う際に、現在の実行コンテキスト（特にPCとSP）を`g->sched`（`gobuf`構造体）に保存します。この保存されたPCは、後でスタックトレースバックを生成する際に使用されます。

元のコードでは、`runtime·systemstack_switch(SB)`のアドレスをR3レジスタにロードし、その後`ADD $4, R3, R3`を実行して、`push {lr}`命令をスキップしていました。これは、`push {lr}`命令の直後が、論理的に`systemstack_switch`の開始点と見なされるべきだからです。

しかし、`nacl/arm`環境では、NaClのサンドボックス化メカニズムによって追加の命令が挿入されることがあります。コミットメッセージのコメントにある「`nacl-insert bic instruction`」がこれに該当します。この`bic`命令も4バイト長であるため、既存の`ADD $4, R3, R3`だけでは不十分となり、PCがさらに4バイトずれてしまいます。

このずれを修正するため、`GOOS_nacl`が定義されている場合（つまりNaCl環境の場合）にのみ、追加で`ADD $4, R3, R3`を実行するように変更されました。これにより、`nacl-insert bic instruction`と`push {lr}`の両方をスキップし、`gobuf_pc`に保存されるPCが、`systemstack_switch`の論理的な開始点（つまり、トレースバックで期待される位置）を正確に指すようになります。

この修正は、条件付きコンパイルディレクティブ`#ifdef GOOS_nacl`を使用しており、NaCl環境でのみこの追加の調整が適用されるため、他の環境には影響を与えません。

## コアとなるコードの変更箇所

```diff
--- a/src/runtime/asm_arm.s
+++ b/src/runtime/asm_arm.s
@@ -215,6 +215,9 @@ switch:
 	// save our state in g->sched.  Pretend to
 	// be systemstack_switch if the G stack is scanned.
 	MOVW	$runtime·systemstack_switch(SB), R3
+#ifdef GOOS_nacl
+\tADD\t$4, R3, R3 // get past nacl-insert bic instruction
+#endif
 	ADD\t$4, R3, R3 // get past push {lr}
 	MOVW\tR3, (g_sched+gobuf_pc)(g)
 	MOVW\tR13, (g_sched+gobuf_sp)(g)
```

## コアとなるコードの解説

変更は`src/runtime/asm_arm.s`ファイル内の`switch`ラベルの箇所にあります。

1.  `MOVW $runtime·systemstack_switch(SB), R3`:
    *   `runtime·systemstack_switch`関数のアドレスをレジスタ`R3`にロードします。これは、`systemstack_switch`の開始アドレスを指します。

2.  `#ifdef GOOS_nacl`:
    *   これはプリプロセッサディレクティブで、`GOOS_nacl`マクロが定義されている場合（つまり、GoがNaCl環境向けにコンパイルされている場合）にのみ、続くコードがコンパイルされます。

3.  `ADD $4, R3, R3 // get past nacl-insert bic instruction`:
    *   `GOOS_nacl`が定義されている場合、`R3`の値に`4`を加算します。
    *   コメントが示すように、これはNaCl環境で挿入される可能性のある`bic`命令（通常4バイト長）をスキップするためです。この命令は、サンドボックス化のためにコードの先頭に挿入されることがあります。この加算により、`R3`は`bic`命令の直後の命令のアドレスを指すようになります。

4.  `ADD $4, R3, R3 // get past push {lr}`:
    *   `R3`の値にさらに`4`を加算します。
    *   これは、`systemstack_switch`関数のプロローグにある`push {lr}`命令（通常4バイト長）をスキップするためです。`lr`（リンクレジスタ）は、関数呼び出し元のアドレスを保持しており、関数プロローグでスタックに保存されるのが一般的です。スタックトレースバックでは、この`push {lr}`命令の「後」が関数の実質的な開始点と見なされるべきです。

これらの`ADD`命令により、`R3`レジスタは最終的に、`systemstack_switch`のコードが実際に実行を開始する、トレースバックにとって意味のあるアドレスを保持することになります。

5.  `MOVW R3, (g_sched+gobuf_pc)(g)`:
    *   調整された`R3`の値（正確なPC）を、現在のゴルーチン構造体`g`の`g_sched`フィールド内の`gobuf_pc`オフセットに保存します。これにより、スタックトレースバック時に正しいPCが参照されるようになります。

6.  `MOVW R13, (g_sched+gobuf_sp)(g)`:
    *   現在のスタックポインタ`R13`を、`g_sched`フィールド内の`gobuf_sp`オフセットに保存します。

この修正により、`nacl/arm`環境での`systemstack`のトレースバックが正確になり、デバッグの信頼性が向上しました。

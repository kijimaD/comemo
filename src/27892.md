# [インデックス 27892] ファイルの概要

このコミットは、Go言語のネットワークパッケージにおいて、Plan 9オペレーティングシステム上でのTCP接続のクローズ処理を改善するものです。具体的には、Plan 9がTCP接続終了時に返す特定のエラー文字列「Hangup」を`io.EOF`として適切に解釈するように変更し、Goの標準的なエラーハンドリングに合わせることを目的としています。

## 元コミット内容

Plan 9上でTCP接続をクローズする際、TCPの制御ファイル（ctl file）に「hangup」という文字列を書き込みます。その結果、TCPデータファイルに対する次回の読み込み操作は、「/net/tcp/18/data: Hangup」のようなエラーを返します。しかし、Goの標準的な動作では、接続の終了時には`io.EOF`が返されることが期待されます。この変更は、エラー文字列に「Hangup」が含まれている場合に、`Read`関数が`io.EOF`を返すようにすることで、この挙動の不一致を解消します。

## 変更の背景

Go言語の`net`パッケージは、様々なオペレーティングシステム（OS）上で動作するように設計されています。各OSには、ネットワーク操作に関する独自のシステムコールやエラー処理のメカニズムが存在します。このコミットの背景にある問題は、Plan 9という特定のOSにおけるTCP接続の終了通知方法が、Goの期待する`io.EOF`とは異なる形式で提供されていたことにあります。

Goの`Read`インターフェースは、データストリームの終端に達したことを示すために`io.EOF`エラーを返すことが慣例となっています。これにより、アプリケーションはデータの読み込みが完了したことを統一的に判断できます。しかし、Plan 9では、TCP接続がクローズされた際に、データファイルからの読み込みが「Hangup」という文字列を含むエラーメッセージを返していました。この「Hangup」エラーは、Goアプリケーションにとっては予期せぬエラーであり、接続が正常に終了したことを示す`io.EOF`として扱われないため、アプリケーションが接続終了を正しく認識できない、あるいは不適切なエラー処理を行う可能性がありました。

この不一致を解消し、GoアプリケーションがPlan 9上でも一貫したネットワークエラーハンドリングを行えるようにするために、このコミットが導入されました。

## 前提知識の解説

### Plan 9 from Bell Labs

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。その設計哲学は「すべてをファイルとして扱う」というもので、ネットワーク接続、デバイス、プロセス間通信など、システム内のあらゆるリソースがファイルシステム上のファイルとして表現されます。
*   **ファイルシステム中心主義**: ネットワーク接続も`/net`ディレクトリ以下のファイルとして表現されます。例えば、TCP接続は`/net/tcp/`以下のディレクトリとファイル（`ctl`、`data`など）で管理されます。
*   **制御ファイル（ctl file）**: ネットワーク接続の制御は、対応するディレクトリ内の`ctl`ファイルへの書き込みによって行われます。接続のクローズもこの`ctl`ファイルを通じて指示されます。
*   **データファイル（data file）**: 実際のデータ送受信は`data`ファイルを通じて行われます。

### Go言語における`io.EOF`

Go言語の`io`パッケージで定義されている`io.EOF`は、入力ストリームの終端（End Of File）に達したことを示す特別なエラー値です。
*   **ストリームの終端**: `Read`メソッドがこれ以上読み込むデータがない場合に`io.EOF`を返します。これはエラーではありますが、通常は「正常な終了」として扱われます。
*   **ネットワーク接続での利用**: TCP接続のようなストリーム指向の通信において、リモートピアが接続を正常にクローズした場合、ローカル側での`Read`操作は最終的に`io.EOF`を返します。これにより、アプリケーションはリモートからのデータ送信が終了したことを検知し、適切に接続を閉じたり、リソースを解放したりできます。

### TCP接続のクローズとエラーハンドリング

一般的なOS（Unix系など）では、TCP接続のリモートピアが接続を正常に終了（FINパケットを送信）すると、ローカル側での`Read`操作は、残りのデータがすべて読み込まれた後に`io.EOF`を返します。これにより、アプリケーションは接続の終了を透過的に処理できます。しかし、Plan 9の特定の挙動が、このGoの期待する`io.EOF`の代わりに、独自の「Hangup」エラーを返していたため、Goの`net`パッケージがPlan 9上でこの特殊なケースを明示的に処理する必要がありました。

## 技術的詳細

このコミットは、Goの`net`パッケージがPlan 9上でTCP接続を扱う際の、エラー処理の不整合を解消します。

Plan 9のネットワークスタックでは、TCP接続がクローズされると、その接続に対応する`ctl`ファイルに「hangup」という文字列が書き込まれます。この操作の結果、その接続の`data`ファイルに対する後続の`Read`システムコールは、`"/net/tcp/18/data: Hangup"`のような形式のエラー文字列を返します。これは、Goの`Read`インターフェースが期待する`io.EOF`とは異なる形式です。

Goの`net`パッケージは、OS固有のネットワーク操作を抽象化し、クロスプラットフォームで一貫したAPIを提供します。`src/net/fd_plan9.go`ファイルは、Plan 9固有のファイルディスクリプタ（`netFD`）の実装を含んでいます。このファイル内の`Read`メソッドは、実際のデータ読み込みを`fd.data.Read(b)`（Plan 9のファイルシステムに対する読み込み）に委譲しています。

このコミットの目的は、`fd.data.Read(b)`がPlan 9特有の「Hangup」エラーを返した場合に、Goアプリケーションに対しては標準的な`io.EOF`を返すように変換することです。これにより、GoアプリケーションはPlan 9上でも他のOSと同様に、接続の正常な終了を`io.EOF`として処理できるようになります。

## コアとなるコードの変更箇所

変更は`src/net/fd_plan9.go`ファイルに集中しています。

```diff
--- a/src/net/fd_plan9.go
+++ b/src/net/fd_plan9.go
@@ -77,6 +77,9 @@ func (fd *netFD) Read(b []byte) (n int, err error) {
 	}\n \tdefer fd.readUnlock()\n \tn, err = fd.data.Read(b)\n+\tif isHangup(err) {\n+\t\terr = io.EOF\n+\t}\n \tif fd.net == \"udp\" && err == io.EOF {\n \t\tn = 0\n \t\terr = nil\n@@ -179,3 +182,7 @@ func setReadBuffer(fd *netFD, bytes int) error {\n func setWriteBuffer(fd *netFD, bytes int) error {\n \treturn syscall.EPLAN9\n }\n+\n+func isHangup(err error) bool {\n+\treturn err != nil && stringsHasSuffix(err.Error(), \"Hangup\")\n+}\n```

具体的には、以下の2つの変更が行われています。

1.  `netFD.Read`メソッド内に、`isHangup(err)`が真を返す場合に`err`を`io.EOF`に上書きするロジックが追加されました。
2.  新しいヘルパー関数`isHangup`が追加されました。

## コアとなるコードの解説

### `netFD.Read`メソッドの変更

```go
	n, err = fd.data.Read(b)
	if isHangup(err) {
		err = io.EOF
	}
```
この部分が、Plan 9特有のエラーをGoの標準的な`io.EOF`に変換する主要なロジックです。
1.  `n, err = fd.data.Read(b)`: 実際のデータ読み込みをPlan 9のファイルディスクリプタ（`fd.data`）に対して行います。ここで、Plan 9が「Hangup」エラーを返す可能性があります。
2.  `if isHangup(err)`: 読み込み操作の結果としてエラーが発生した場合、新しく定義された`isHangup`関数を呼び出して、そのエラーがPlan 9の「Hangup」エラーであるかどうかをチェックします。
3.  `err = io.EOF`: `isHangup`が`true`を返した場合、元のエラー`err`を`io.EOF`に上書きします。これにより、`netFD.Read`メソッドの呼び出し元には、Plan 9特有のエラーではなく、Goの標準的な終端エラーが返されるようになります。

### `isHangup`ヘルパー関数

```go
func isHangup(err error) bool {
	return err != nil && stringsHasSuffix(err.Error(), "Hangup")
}
```
この関数は、与えられたエラーがPlan 9の「Hangup」エラーであるかを判定するためのものです。
1.  `err != nil`: まず、エラーが`nil`でないことを確認します。`nil`エラーは正常な状態を示すため、`Hangup`エラーであるはずがありません。
2.  `stringsHasSuffix(err.Error(), "Hangup")`: エラーが`nil`でない場合、エラーメッセージの文字列表現（`err.Error()`）が「Hangup」という文字列で終わっているかどうかをチェックします。Plan 9が返すエラーメッセージの形式が`"/net/tcp/18/data: Hangup"`のようになることを考慮し、サフィックス（接尾辞）で判定しています。`stringsHasSuffix`関数は、Goの標準ライブラリ`strings`パッケージに含まれる関数で、文字列が特定の接尾辞で終わるかを判定します。

この変更により、Goの`net`パッケージはPlan 9の特殊なエラー挙動を内部で吸収し、Goアプリケーション開発者にはOSの違いを意識させずに一貫した`io.EOF`セマンティクスを提供できるようになりました。

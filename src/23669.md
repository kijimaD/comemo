# [インデックス 23669] ファイルの概要

このコミットは、Goコマンドがパッケージやバイナリの「陳腐化（stale）」を検出するメカニズムを改善するものです。具体的には、ソースファイルが削除された際に、既存のファイル変更時刻（mtime）に基づく検出方法では陳腐化を正しく認識できない問題を解決するため、ビルドIDを導入しています。ビルドIDは、パッケージを構成するソースファイル名のハッシュであり、パッケージアーカイブや実行可能バイナリに埋め込まれ、Goコマンドが再ビルドの必要性を判断する際に利用されます。

## コミット

```
cmd/go: detect when package or binary is stale due to removed source file

The go command uses file modification times to decide when a
package is out of date: if the .a file is older than a source file,
the .a file needs to be rebuilt. This scheme breaks down when
multiple source files compile into a single .a file: if one source file
is removed but no other changes are made, there is no indication
that the .a file is out of date.

The fix is to store a value called a build ID in the package archive itself.
The build ID is a hash of the names of all source files compiled into the package.
A later go command can read the build ID out of the package archive
and compare to the build ID derived from the list of source files it now
sees in the directory. If the build IDs differ, the file list has changed,
and the package must be rebuilt.

There is a cost here: when scanning a package directory, in addition
to reading the beginning of every source file for build tags and imports,
the go command now also reads the beginning of the associated
package archive, for the build ID. This is at most a doubling in the
number of files read. On my 2012 MacBook Pro, the time for
'go list std' increases from about 0.215 seconds to about 0.23 seconds.

For executable binaries, the approach is the same except that the
build ID information is stored in a trailer at the end of the executable file.
It remains to be seen if anything objects to the trailer.
I don't expect problems except maybe on Plan 9.

Fixes #3895.

## 変更の背景

Goコマンドは、パッケージが最新であるかどうかを判断するために、主にファイル変更時刻（`mtime`）を利用していました。具体的には、コンパイル済みの`.a`ファイルがソースファイルよりも古い場合、再ビルドが必要と判断されます。しかし、この単純な`mtime`ベースの検出方法には重大な欠陥がありました。

複数のソースファイルが1つの`.a`ファイルにコンパイルされる状況で、そのうちの1つのソースファイルが削除された場合、残りのファイルの`mtime`は変更されません。このため、Goコマンドは`.a`ファイルが陳腐化していることを検出できず、古いバージョンのパッケージやバイナリが使用され続ける可能性がありました。これは、特に開発者がファイルを削除した後に`go build`や`go install`を実行しても、期待通りに再ビルドが行われないという問題を引き起こしていました。

この問題は、GoのIssue #3895として報告されており、本コミットはこの問題を解決するために導入されました。

## 前提知識の解説

### Goのビルドプロセスとパッケージ管理

Go言語のビルドシステムは、ソースコードをコンパイルして実行可能なバイナリや再利用可能なパッケージアーカイブ（`.a`ファイル）を生成します。
*   **`go build`**: ソースファイルをコンパイルし、実行可能ファイルまたはパッケージを生成します。デフォルトでは、実行可能ファイルはカレントディレクトリに、パッケージアーカイブはビルドキャッシュに保存されます。
*   **`go install`**: `go build`と同様にコンパイルを行いますが、生成された実行可能ファイルは`$GOPATH/bin`または`$GOBIN`に、パッケージアーカイブは`$GOPATH/pkg`または`$GOMODCACHE`にインストールされます。
*   **パッケージアーカイブ (`.a`ファイル)**: Goのパッケージがコンパイルされた中間形式で、他のパッケージからインポートされる際に利用されます。

### 既存のstaleness検出メカニズム (ファイル変更時刻 `mtime`)

Goコマンドは、ビルドの効率化のために、不必要な再コンパイルを避ける仕組みを持っています。その主要な方法の一つが、ファイルシステム上のファイルの最終変更時刻（`mtime`）の比較です。
*   コンパイル済みのアウトプット（例: `.a`ファイル、実行可能バイナリ）の`mtime`が、その入力となるソースファイルのいずれかの`mtime`よりも古い場合、アウトプットは「陳腐化している（stale）」と判断され、再ビルドがトリガーされます。
*   この方法は、ソースファイルが変更された場合には効果的ですが、ソースファイルが削除された場合には機能しません。削除されたファイルの`mtime`は存在せず、残りのファイルの`mtime`は変わらないため、ビルドシステムは変更を認識できません。

### ビルドIDの概念

ビルドIDは、ソフトウェアの特定のビルドを一意に識別するための識別子です。これは通常、ビルドに使用されたソースコード、コンパイラのバージョン、ビルド環境などの情報から生成されるハッシュ値やバージョン文字列です。
*   **目的**:
    *   **再現性**: 特定のビルドIDを持つソフトウェアが、常に同じソースコードとビルドプロセスから生成されたことを保証します。
    *   **デバッグ**: 問題が発生した際に、どのバージョンのコードが実行されているかを迅速に特定できます。
    *   **キャッシュ**: ビルドシステムが、以前にビルドされた成果物を再利用できるかどうかを判断するのに役立ちます。

### `sha1` ハッシュ関数

SHA-1 (Secure Hash Algorithm 1) は、入力データから固定長のハッシュ値（メッセージダイジェスト）を生成する暗号学的ハッシュ関数です。
*   **特徴**:
    *   **一方向性**: ハッシュ値から元のデータを復元することは非常に困難です。
    *   **衝突耐性**: 異なる入力データから同じハッシュ値が生成される（衝突）可能性は低いとされています（ただし、SHA-1は現在では暗号学的に安全ではないと見なされており、より強力なSHA-2やSHA-3が推奨されています）。
    *   **データ整合性**: 入力データが少しでも変更されると、生成されるハッシュ値は大きく変化するため、データの改ざん検出に利用されます。
本コミットでは、ソースファイルリストの整合性を確認するために利用されています。

## 技術的詳細

このコミットは、Goコマンドの陳腐化検出ロジックを強化するために、**ビルドID**という新しい概念を導入しています。

1.  **ビルドIDの生成**:
    *   各Goパッケージについて、そのパッケージを構成するすべてのソースファイル（`.go`, `.cgo`, `.c`, `.cxx`, `.m`, `.h`, `.s`, `.syso`, `.swig`, `.swigcxx`ファイル）のファイル名リストを収集します。
    *   これらのファイル名を結合し、その結果に対してSHA-1ハッシュを計算します。
    *   このSHA-1ハッシュ値が、そのパッケージのビルドIDとなります。ファイル名のみをハッシュすることで、ファイルの内容ではなく、パッケージを構成するファイルの集合が変更されたことを検出できます。また、フルパスではなくファイル名のみを使用することで、プロジェクト全体を移動してもビルドIDが変わらないようにしています。

2.  **ビルドIDの埋め込み**:
    *   **パッケージアーカイブ (`.a`ファイル)**: コンパイルされたパッケージアーカイブの内部に、ビルドIDが埋め込まれます。具体的には、アーカイブのヘッダー部分（`go object`行の後に`build id "..."`という形式で）に格納されます。
    *   **実行可能バイナリ**: 実行可能バイナリの場合、ビルドIDはファイルの末尾にトレーラーとして追加されます。これは、ELF、Mach-O、PE、Plan 9といった異なるバイナリ形式に対応するために、カスタムセクションを使用する複雑さを避けるためのアプローチです。トレーラーは特定のフォーマット（`\x00\n\ngo binary\nbuild id "XXX"\nend go binary\n`）に従います。

3.  **陳腐化検出ロジックの更新**:
    *   `go command`がパッケージの陳腐化をチェックする際、まず現在のディレクトリにあるソースファイルリストから新しいビルドIDを計算します。
    *   次に、既存のパッケージアーカイブまたは実行可能バイナリから埋め込まれたビルドIDを読み取ります。
    *   この2つのビルドIDが異なる場合、ソースファイルのリストが変更された（例えば、ファイルが削除された）と判断し、パッケージは陳腐化しているとマークされ、再ビルドがトリガーされます。

4.  **パフォーマンスへの影響**:
    *   ビルドIDの導入により、Goコマンドはパッケージディレクトリをスキャンする際に、各ソースファイルの先頭を読み取るだけでなく、関連するパッケージアーカイブの先頭も読み取る必要があります。
    *   これにより、読み取るファイルの数が最大で2倍になる可能性があります。コミットメッセージによると、`go list std`の実行時間が約0.215秒から約0.23秒に増加するという、わずかなオーバーヘッドが報告されています。これは、正確な陳腐化検出というメリットと比較して許容できる範囲と判断されています。

5.  **ツールチェインの制約**:
    *   このビルドIDの仕組みは、現在のところ`gc`ツールチェイン（Goの標準コンパイラ）にのみ対応しています。他のツールチェインを使用している場合は、それぞれのツールチェインで同様の調整が必要となる可能性があります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/dist/build.go`**:

3.  **`src/cmd/go/pkg.go`**:

    *   `isStale`関数内で、既存の`mtime`ベースのチェックに加えて、ビルドIDに基づく陳腐化検出ロジックが追加されました。`readBuildID(p)`で既存のビルドIDを読み取り、`p.buildID`（現在計算されたビルドID）と比較しています。
    *   `readBuildID`関数が追加されました。これは、パッケージアーカイブ（`.a`ファイル）または実行可能バイナリからビルドIDを読み取るための主要な関数です。

    *   `readBuildID`関数内では、パッケージアーカイブのヘッダーを解析し、`build id "..."`の行からビルドIDを抽出するロジックが実装されています。

4.  **`src/cmd/go/test.bash`**:
    *   `go install`が削除されたファイルを正しく検出するかどうかを検証するための新しいテストケースが追加されました。これは、通常のパッケージと`main`パッケージ（実行可能バイナリ）の両方について、ソースファイルの削除が`go list -f '{{.Stale}}'`によって`true`と報告されることを確認しています。

## コアとなるコードの解説

### `src/cmd/go/pkg.go`

このファイルは、Goコマンドにおけるパッケージのロード、解析、および陳腐化検出のロジックを管理する中心的な役割を担っています。

*   **`type Package struct { ... buildID string ... }`**:
    *   `Package`構造体に`buildID`という新しいフィールドが追加されました。このフィールドは、そのパッケージの期待されるビルドID（現在のソースファイルリストから計算されたハッシュ）を保持します。これにより、パッケージのメタデータの一部としてビルドIDが管理されるようになります。

*   **`func (p *Package) load(...)` 内のビルドID計算ロジック**:
    ```go
    h := sha1.New()
    inputFiles := stringList(
        p.GoFiles, p.CgoFiles, p.CFiles, p.CXXFiles, p.MFiles,
        p.HFiles, p.SFiles, p.SysoFiles, p.SwigFiles, p.SwigCXXFiles,
    )
    fmt.Fprintf(h, "%d files\\n", len(inputFiles))
    for _, file := range inputFiles {
        fmt.Fprintf(h, "%s\\n", file)
    }
    p.buildID = fmt.Sprintf("%x", h.Sum(nil))
    ```
    *   `load`メソッドはパッケージの情報を読み込む際に呼び出されます。ここで、`crypto/sha1`パッケージを使って新しいSHA-1ハッシュインスタンスを作成します。
    *   `stringList`ヘルパー関数（コミットには含まれていませんが、既存のユーティリティ関数と推測されます）を使って、Go、Cgo、C、C++、Objective-C、ヘッダー、アセンブリ、システムオブジェクト、Swig関連のすべてのソースファイル名を結合したリスト`inputFiles`を作成します。
    *   ハッシュジェネレータ`h`に、ファイル数と各ファイル名を順に書き込みます。これにより、ファイルリストの順序や内容が少しでも変わると、異なるハッシュが生成されます。
    *   最終的に`h.Sum(nil)`でハッシュ値を計算し、16進数文字列としてフォーマットして`p.buildID`に格納します。これが、現在のソースファイルセットに基づくパッケージの「期待される」ビルドIDとなります。

*   **`func isStale(p *Package, topRoot map[string]bool) bool` 内のビルドID比較**:
    ```go
    targetBuildID, err := readBuildID(p)
    if err == nil && targetBuildID != p.buildID {
        return true
    }
    ```
    *   `isStale`関数は、パッケージが再ビルドを必要とするかどうかを判断します。
    *   ここで、`readBuildID(p)`を呼び出して、既にコンパイルされているパッケージアーカイブまたはバイナリに埋め込まれているビルドID（`targetBuildID`）を読み取ります。
    *   エラーがなく、かつ読み取った`targetBuildID`が、現在計算された`p.buildID`と異なる場合、ソースファイルリストが変更されたと判断し、`true`を返してパッケージが陳腐化していることを示します。これにより、再ビルドがトリガーされます。

*   **`func readBuildID(p *Package) (id string, err error)`**:
    *   この関数は、パッケージの種類（通常のパッケージアーカイブか実行可能バイナリか）に応じて、適切な方法でビルドIDを読み取ります。
    *   `p.Name == "main"`の場合（つまり実行可能バイナリの場合）は、`readBuildIDFromBinary`を呼び出します。
    *   それ以外の場合（パッケージアーカイブの場合）は、`.a`ファイルの先頭1024バイトを読み込み、アーカイブヘッダー（`!<arch>`, `__.PKGDEF`, `go object ...`）を解析し、`build id "..."`という行からビルドID文字列を抽出します。

*   **`func readBuildIDFromBinary(p *Package) (id string, err error)`**:
    *   この関数は、実行可能バイナリの末尾に追記されたビルドIDトレーラーを読み取ります。
    *   バイナリファイルの末尾から最大1024バイトを読み込み、特定のバイトシーケンス（`go binary\nbuild id "XXX"\nend go binary\n`）を探します。
    *   このトレーラーが見つかった場合、その中からビルドID文字列を抽出し、返します。

### `src/cmd/go/build.go`

このファイルは、Goコマンドのビルドロジック、特にコンパイルとリンクの処理を扱います。

*   **`func (b *builder) build(a *action) (err error)` 内のバイナリへのビルドID書き込み**:
    ```go
    if buildToolchain == (gcToolchain{}) && a.p.buildID != "" {
        f, err := os.OpenFile(a.target, os.O_WRONLY|os.O_APPEND, 0)
        // ... エラーハンドリング ...
        fmt.Fprintf(f, "\\x00\\n\\ngo binary\\nbuild id %q\\nend go binary\\n", a.p.buildID)
        // ... クローズとエラーハンドリング ...
    }
    ```
    *   `build`メソッドは、実行可能バイナリが生成された後に呼び出されます。
    *   `gcToolchain`を使用しており、かつパッケージにビルドIDが設定されている場合、生成されたバイナリファイルを開き、その末尾にビルドIDを含む特定のフォーマットの文字列を追記します。これは、`readBuildIDFromBinary`関数が読み取るトレーラーと一致する必要があります。

*   **`func (gcToolchain) gc(...)` 内の`-buildid`引数追加**:
    ```go
    if p.buildID != "" {
        gcargs = append(gcargs, "-buildid", p.buildID)
    }
    ```
    *   `gc`メソッドは、`go tool compile`コマンドを呼び出す際に使用される引数を準備します。
    *   パッケージにビルドIDが設定されている場合、`-buildid`フラグとその値をコンパイラ引数に追加します。これにより、コンパイラはビルドIDを認識し、パッケージアーカイブの適切な場所に埋め込むことができます。

### `src/cmd/dist/build.go`

このファイルは、Goディストリビューション自体のビルドプロセスを管理します。

*   **`var buildorder = []string{ ... "hash", "crypto", "crypto/sha1", "cmd/go", ... }`**:
    *   `buildorder`は、Goディストリビューション内のパッケージがビルドされる順序を定義します。
    *   `hash`, `crypto`, `crypto/sha1`が追加されたのは、`cmd/go`（Goコマンド自体）がビルドIDの計算にこれらのパッケージを使用するため、それらが`cmd/go`の前にビルドされる必要があるからです。

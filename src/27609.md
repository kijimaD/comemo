## 変更の背景

GoコンパイラのAMD64バックエンドでは、バイトサイズの演算（例: `byte`型の加算）に対して、実際には32ビットオペランドを使用する`ADDL`命令を生成することがありました。これは、AMD64アーキテクチャの特性上、8ビットオペランド（`ADDB`など）よりも32ビットオペランド（`ADDL`など）の方が、特定の最適化パスにおいて有利な場合があるためです。

しかし、コンパイラのSSAバックエンドのコード生成ロジックが、この「バイト操作に`ADDL`を使う」という既存の挙動を十分に反映していませんでした。その結果、`+1`や`-1`といった単純な加算・減算に対して、より効率的な`INC`/`DEC`命令（1バイト短い）や、3オペランドの加算・減算を表現できる`LEA`命令（Load Effective Address）が適用されにくい状況がありました。

このコミットの目的は、コード生成ロジックを修正し、バイト操作に対しても32ビットオペランドの命令を前提とすることで、これらの最適化（`INC`/`DEC`、`LEA`）をより広範に適用できるようにすることです。これにより、生成されるアセンブリコードの効率が向上し、バイナリサイズが削減されます。

## 前提知識の解説

1.  **GoコンパイラとSSA (Static Single Assignment) フォーム**:
    *   Goコンパイラは、ソースコードを中間表現に変換し、様々な最適化を適用します。その中間表現の一つがSSAフォームです。SSAフォームでは、各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。
    *   コンパイラのバックエンドは、SSAフォームの命令（`ssa.OpAMD64ADDQ`など）をターゲットアーキテクチャ（ここではAMD64）の実際のアセンブリ命令に変換します。
2.  **AMD64アセンブリ命令とオペランドサイズ**:
    *   AMD64アーキテクチャでは、レジスタやメモリに対する演算命令が、操作するデータのサイズに応じて異なるサフィックスを持ちます。
        *   `B`: Byte (8ビット)
        *   `W`: Word (16ビット)
        *   `L`: Long (32ビット)
        *   `Q`: Quad (64ビット)
    *   例: `ADDB` (8ビット加算), `ADDW` (16ビット加算), `ADDL` (32ビット加算), `ADDQ` (64ビット加算)。
    *   **`INC`/`DEC`命令**: レジスタやメモリの値を`+1`または`-1`する命令です。`ADD $1, reg`や`SUB $1, reg`と比較して、オペランドが不要なため命令長が短く（通常1バイト短い）、一部のCPUでは高速に実行されることがあります。
    *   **`LEA` (Load Effective Address) 命令**: メモリのアドレスを計算し、その結果をレジスタに格納する命令です。`LEA`は、実際にはメモリにアクセスせず、アドレス計算の機能だけを利用して、複数のオペランド（ベースレジスタ、インデックスレジスタ、スケール、ディスプレースメント）を組み合わせた複雑な加算を1命令で実行できるため、3オペランドの加算や減算の最適化によく利用されます。例えば、`reg = reg1 + reg2 * scale + offset`のような計算を効率的に行えます。
3.  **2-アドレス命令と3-アドレス命令**:
    *   多くのRISCアーキテクチャでは3-アドレス命令（例: `ADD dest, src1, src2`）が一般的ですが、x86/AMD64は主に2-アドレス命令（例: `ADD dest, src`、`dest = dest + src`）を使用します。
    *   `LEA`命令は、x86/AMD64において3-アドレス命令のような振る舞いを実現できる数少ない命令の一つであり、コンパイラ最適化の重要なターゲットとなります。

## 技術的詳細

このコミットの核心は、GoコンパイラのAMD64バックエンドが、バイトサイズの演算（`ssa.OpAMD64ADDB`など）を処理する際に、より汎用的な32ビットオペランドの命令（`ADDL`）を生成する既存の傾向を、SSAコード生成ロジックに明示的に反映させる点にあります。

具体的には、以下の最適化を可能にします。

1.  **`INC`/`DEC`命令の適用拡大**:
    *   `+1`や`-1`の定数加算・減算は、`ADD $1, reg`や`SUB $1, reg`として生成されるよりも、`INC reg`や`DEC reg`として生成される方が命令長が1バイト短くなります。
    *   以前は、バイト操作（`ssa.OpAMD64ADDBconst`など）の場合、`INC`/`DEC`命令の生成パスから除外されるか、適切に処理されないことがありました。この変更により、バイト操作であっても32ビットオペランドの`INC`/`DEC`命令（`AINCL`/`ADECL`）が適用されるようになります。これは、バイトレジスタ（`AL`, `BL`など）に対する`INC`/`DEC`命令が存在しないため、32ビットレジスタ（`EAX`, `EBX`など）を操作する命令を使用し、結果的に上位ビットがゼロクリアされることを期待する、またはバイト操作の結果が32ビットレジスタに格納されることを前提とした最適化です。
2.  **`LEA`命令の適用拡大**:
    *   `LEA`命令は、複数のオペランドを持つ加算（例: `reg = base + index*scale + disp`）を1命令で実行できるため、特に定数との加算・減算において効率的なコードを生成できます。
    *   このコミットでは、`ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst` と同様に、`ssa.OpAMD64ADDBconst` も `LEA` 命令の生成パスに含めることで、バイト操作における定数加算・減算も `LEA` を使った3オペランド加算として最適化される可能性が高まります。ここでも、バイト操作の結果が32ビットレジスタに格納されることを前提としています。

この変更は、コンパイラが生成するアセンブリコードの品質を向上させ、Goプログラムの実行効率とバイナリサイズに貢献します。特に、バイト配列のインデックス計算や、ループカウンタの更新など、頻繁に行われるバイト操作において効果を発揮する可能性があります。

## コアとなるコードの変更箇所

変更は `src/cmd/compile/internal/amd64/ssa.go` ファイルに集中しています。

1.  **`ssa.OpAMD64ADDB` の扱い変更**:
    *   `ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW` と共に `ssa.OpAMD64ADDB` が `case` 文に追加され、`LEA` 命令を生成するロジックの対象となります。
    *   以前は `ssa.OpAMD64ADDB` は2-アドレス命令として扱われていましたが、この変更により、32ビットオペランドの`LEA`命令（`ALEAL`）を生成するパスに統合されます。
    *   具体的には、`ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW` を処理していた `switch v.Op` ブロックが簡略化され、`ssa.OpAMD64ADDQ` 以外はすべて `ALEAL` を生成するように変更されています。
    *   また、2-アドレス命令の処理を行う `case ssa.OpAMD64ADDB, ssa.OpAMD64ADDSS, ...` から `ssa.OpAMD64ADDB` が削除されています。

2.  **定数加算・減算の最適化ロジックの変更**:
    *   `ssa.OpAMD64ADDQconst`, `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst` に加えて、`ssa.OpAMD64ADDBconst` が `INC`/`DEC` 命令および `LEA` 命令を生成するロジックの対象に追加されました。
    *   `+1`または`-1`の定数加算・減算の場合、`ssa.OpAMD64ADDQconst` は `AINCQ`/`ADECQ` を、それ以外の `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`, `ssa.OpAMD64ADDBconst` は `AINCL`/`ADECL` を生成するように変更されています。
    *   同様に、`LEA` 命令を生成するパスでも、`ssa.OpAMD64ADDQconst` は `ALEAQ` を、それ以外の `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`, `ssa.OpAMD64ADDBconst` は `ALEAL` を生成するように変更されています。
    *   `ssa.OpAMD64SUBQconst`, `ssa.OpAMD64SUBLconst`, `ssa.OpAMD64SUBWconst` に加えて、`ssa.OpAMD64SUBBconst` も同様に `INC`/`DEC` 命令および `LEA` 命令を生成するロジックの対象に追加されています。

## コアとなるコードの解説

変更された `ssa.go` の主要な部分は、`ssaGenValue` 関数内の `switch v.Op` ステートメントです。この関数は、SSA値（`v`）に対応するアセンブリコードを生成する役割を担っています。

1.  **`ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW`, `ssa.OpAMD64ADDB` の処理**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW:
    //     ...
    //     switch v.Op {
    //     case ssa.OpAMD64ADDQ: asm = x86.ALEAQ
    //     case ssa.OpAMD64ADDL: asm = x86.ALEAL
    //     case ssa.OpAMD64ADDW: asm = x86.ALEAL // 間違い？ALEAWではない
    //     }
    // 変更後:
    case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW, ssa.OpAMD64ADDB: // ADDBが追加
        // ...
        if v.Op == ssa.OpAMD64ADDQ {
            asm = x86.ALEAQ
        } else {
            asm = x86.ALEAL // Q以外はALEALを使用
        }
    ```
    この変更により、バイト操作 (`ssa.OpAMD64ADDB`) も含め、64ビット (`Q`) 以外の加算操作は、32ビットオペランドの `LEA` 命令 (`ALEAL`) を生成するパスに統合されました。これは、バイト操作であっても32ビットレジスタを操作する命令を使用し、結果的に上位ビットがゼロクリアされることを期待する最適化戦略を反映しています。

2.  **2-アドレス命令からの `ssa.OpAMD64ADDB` の削除**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDB, ssa.OpAMD64ADDSS, ssa.OpAMD64ADDSD,
    // 変更後:
    // case ssa.OpAMD64ADDSS, ssa.OpAMD64ADDSD,
    ```
    `ssa.OpAMD64ADDB` が上記の `LEA` 生成パスに移動したため、従来の2-アドレス命令として処理するリストから削除されました。

3.  **定数加算 (`ADDconst`) の最適化**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDQconst, ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst:
    //     ...
    //     if v.AuxInt == 1 {
    //         switch v.Op {
    //         case ssa.OpAMD64ADDQconst: asm = x86.AINCQ
    //         case ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst, ssa.OpAMD64ADDBconst: // ADDBconstはここにあった
    //             asm = x86.AINCL
    //         }
    //     }
    // 変更後:
    case ssa.OpAMD64ADDQconst, ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst, ssa.OpAMD64ADDBconst: // ADDBconstが追加
        // ...
        if v.AuxInt == 1 {
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.AINCQ
            } else {
                asm = x86.AINCL // Q以外はAINCLを使用
            }
        } else if v.AuxInt == -1 {
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.ADECQ
            } else {
                asm = x86.ADECL // Q以外はADECLを使用
            }
        } else { // LEA命令の生成
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.ALEAQ
            } else {
                asm = x86.ALEAL // Q以外はALEALを使用
            }
        }
    ```
    この変更により、`ssa.OpAMD64ADDBconst` も `+1` や `-1` の場合は `AINCL`/`ADECL` を、それ以外の定数加算の場合は `ALEAL` を生成する対象となりました。これにより、バイト操作における定数加算・減算も、より効率的な命令に置き換えられる可能性が高まります。

4.  **定数減算 (`SUBconst`) の最適化**:
    `ssa.OpAMD64SUBQconst`, `ssa.OpAMD64SUBLconst`, `ssa.OpAMD64SUBWconst` に加えて、`ssa.OpAMD64SUBBconst` が追加され、`ADDconst` と同様に `INC`/`DEC` および `LEA` 命令の生成ロジックが適用されるようになりました。

これらの変更は、GoコンパイラがAMD64アーキテクチャ向けに生成するアセンブリコードにおいて、バイト操作の最適化をより洗練されたものにし、命令長の短縮と実行効率の向上に貢献します。

    *   以前は、バイト操作（`ssa.OpAMD64ADDBconst`など）の場合、`INC`/`DEC`命令の生成パスから除外されるか、適切に処理されないことがありました。この変更により、バイト操作であっても32ビットオペランドの`INC`/`DEC`命令（`AINCL`/`ADECL`）が適用されるようになります。これは、バイトレジスタ（`AL`, `BL`など）に対する`INC`/`DEC`命令が存在しないため、32ビットレジスタ（`EAX`, `EBX`など）を操作する命令を使用し、結果的に上位ビットがゼロクリアされることを期待する、またはバイト操作の結果が32ビットレジスタに格納されることを前提とした最適化です。
2.  **`LEA`命令の適用拡大**:
    *   `LEA`命令は、複数のオペランドを持つ加算（例: `reg = base + index*scale + disp`）を1命令で実行できるため、特に定数との加算・減算において効率的なコードを生成できます。
    *   このコミットでは、`ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst` と同様に、`ssa.OpAMD64ADDBconst` も `LEA` 命令の生成パスに含めることで、バイト操作における定数加算・減算も `LEA` を使った3オペランド加算として最適化される可能性が高まります。ここでも、バイト操作の結果が32ビットレジスタに格納されることを前提としています。

この変更は、コンパイラが生成するアセンブリコードの品質を向上させ、Goプログラムの実行効率とバイナリサイズに貢献します。特に、バイト配列のインデックス計算や、ループカウンタの更新など、頻繁に行われるバイト操作において効果を発揮する可能性があります。

## コアとなるコードの変更箇所

変更は `src/cmd/compile/internal/amd64/ssa.go` ファイルに集中しています。

1.  **`ssa.OpAMD64ADDB` の扱い変更**:
    *   `ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW` と共に `ssa.OpAMD64ADDB` が `case` 文に追加され、`LEA` 命令を生成するロジックの対象となります。
    *   以前は `ssa.OpAMD64ADDB` は2-アドレス命令として扱われていましたが、この変更により、32ビットオペランドの`LEA`命令（`ALEAL`）を生成するパスに統合されます。
    *   具体的には、`ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW` を処理していた `switch v.Op` ブロックが簡略化され、`ssa.OpAMD64ADDQ` 以外はすべて `ALEAL` を生成するように変更されています。
    *   また、2-アドレス命令の処理を行う `case ssa.OpAMD64ADDB, ssa.OpAMD64ADDSS, ...` から `ssa.OpAMD64ADDB` が削除されています。

2.  **定数加算・減算の最適化ロジックの変更**:
    *   `ssa.OpAMD64ADDQconst`, `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst` に加えて、`ssa.OpAMD64ADDBconst` が `INC`/`DEC` 命令および `LEA` 命令を生成するロジックの対象に追加されました。
    *   `+1`または`-1`の定数加算・減算の場合、`ssa.OpAMD64ADDQconst` は `AINCQ`/`ADECQ` を、それ以外の `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`, `ssa.OpAMD64ADDBconst` は `AINCL`/`ADECL` を生成するように変更されています。
    *   同様に、`LEA` 命令を生成するパスでも、`ssa.OpAMD64ADDQconst` は `ALEAQ` を、それ以外の `ssa.OpAMD64ADDLconst`, `ssa.OpAMD64ADDWconst`, `ssa.OpAMD64ADDBconst` は `ALEAL` を生成するように変更されています。
    *   `ssa.OpAMD64SUBQconst`, `ssa.OpAMD64SUBLconst`, `ssa.OpAMD64SUBWconst` に加えて、`ssa.OpAMD64SUBBconst` も同様に `INC`/`DEC` 命令および `LEA` 命令を生成するロジックの対象に追加されています。

## コアとなるコードの解説

変更された `ssa.go` の主要な部分は、`ssaGenValue` 関数内の `switch v.Op` ステートメントです。この関数は、SSA値（`v`）に対応するアセンブリコードを生成する役割を担っています。

1.  **`ssa.OpAMD64ADDQ`, `ssa.OpAMD64ADDL`, `ssa.OpAMD64ADDW`, `ssa.OpAMD64ADDB` の処理**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW:
    //     ...
    //     switch v.Op {
    //     case ssa.OpAMD64ADDQ: asm = x86.ALEAQ
    //     case ssa.OpAMD64ADDL: asm = x86.ALEAL
    //     case ssa.OpAMD64ADDW: asm = x86.ALEAL // 間違い？ALEAWではない
    //     }
    // 変更後:
    case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW, ssa.OpAMD64ADDB: // ADDBが追加
        // ...
        if v.Op == ssa.OpAMD64ADDQ {
            asm = x86.ALEAQ
        } else {
            asm = x86.ALEAL // Q以外はALEALを使用
        }
    ```
    この変更により、バイト操作 (`ssa.OpAMD64ADDB`) も含め、64ビット (`Q`) 以外の加算操作は、32ビットオペランドの `LEA` 命令 (`ALEAL`) を生成するパスに統合されました。これは、バイト操作であっても32ビットレジスタを操作する命令を使用し、結果的に上位ビットがゼロクリアされることを期待する最適化戦略を反映しています。

2.  **2-アドレス命令からの `ssa.OpAMD64ADDB` の削除**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDB, ssa.OpAMD64ADDSS, ssa.OpAMD64ADDSD,
    // 変更後:
    // case ssa.OpAMD64ADDSS, ssa.OpAMD64ADDSD,
    ```
    `ssa.OpAMD64ADDB` が上記の `LEA` 生成パスに移動したため、従来の2-アドレス命令として処理するリストから削除されました。

3.  **定数加算 (`ADDconst`) の最適化**:
    ```go
    // 変更前:
    // case ssa.OpAMD64ADDQconst, ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst:
    //     ...
    //     if v.AuxInt == 1 {
    //         switch v.Op {
    //         case ssa.OpAMD64ADDQconst: asm = x86.AINCQ
    //         case ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst, ssa.OpAMD64ADDBconst: // ADDBconstはここにあった
    //             asm = x86.AINCL
    //         }
    //     }
    // 変更後:
    case ssa.OpAMD64ADDQconst, ssa.OpAMD64ADDLconst, ssa.OpAMD64ADDWconst, ssa.OpAMD64ADDBconst: // ADDBconstが追加
        // ...
        if v.AuxInt == 1 {
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.AINCQ
            } else {
                asm = x86.AINCL // Q以外はAINCLを使用
            }
        } else if v.AuxInt == -1 {
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.ADECQ
            } else {
                asm = x86.ADECL // Q以外はADECLを使用
            }
        } else { // LEA命令の生成
            if v.Op == ssa.OpAMD64ADDQconst {
                asm = x86.ALEAQ
            } else {
                asm = x86.ALEAL // Q以外はALEALを使用
            }
        }
    ```
    この変更により、`ssa.OpAMD64ADDBconst` も `+1` や `-1` の場合は `AINCL`/`ADECL` を、それ以外の定数加算の場合は `ALEAL` を生成する対象となりました。これにより、バイト操作における定数加算・減算も、より効率的な命令に置き換えられる可能性が高まります。

4.  **定数減算 (`SUBconst`) の最適化**:
    `ssa.OpAMD64SUBQconst`, `ssa.OpAMD64SUBLconst`, `ssa.OpAMD64SUBWconst` に加えて、`ssa.OpAMD64SUBBconst` が追加され、`ADDconst` と同様に `INC`/`DEC` および `LEA` 命令の生成ロジックが適用されるようになりました。

これらの変更は、GoコンパイラがAMD64アーキテクチャ向けに生成するアセンブリコードにおいて、バイト操作の最適化をより洗練されたものにし、命令長の短縮と実行効率の向上に貢献します。

# [インデックス 25563] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおける重要な修正を導入しています。具体的には、TLS (Transport Layer Security) ハンドシェイク中に送信されるServer Name Indication (SNI) 拡張において、IPアドレスのリテラル値が誤って含まれてしまう問題を解決します。RFC 6066の規定に従い、SNIにはホスト名のみが許可され、IPアドレスは許可されないため、この修正はTLSクライアントの標準準拠性を向上させ、相互運用性の問題を回避することを目的としています。

## 元コミット内容

`crypto/tls: don't send IP literals as SNI values.`

このコミットは、`crypto/tls`パッケージにおいて、SNI (Server Name Indication) 値としてIPアドレスのリテラルを送信しないようにする変更です。以前のコミット `a4dcc692011bf1ceca9b1a363fd83f3e59e399ee` の再適用（reland）にあたります。

RFC 6066のセクション3では、「HostName」フィールドにIPv4およびIPv6のリテラルアドレスは許可されないと明記されています。しかし、`Config.ServerName`にIPアドレスが設定された場合（例えば、IPアドレスを指定して`Dial`を呼び出した場合）、GoのTLSクライアントは誤ってそのIPアドレスをSNI値として送信していました。

この変更は、`net.ParseIP`関数を使用してIPアドレスのリテラルを検出し、それらがSNI値として送信されるのを防ぎます。これにより、#13111で報告された問題が修正されます。

## 変更の背景

この変更の背景には、TLSプロトコルの拡張であるServer Name Indication (SNI) の仕様と、Go言語の `crypto/tls` パッケージにおけるその実装の不整合がありました。

1.  **SNIの目的と仕様**: SNIは、単一のIPアドレスで複数のドメインをホストするサーバー（バーチャルホスティング）において、クライアントがどのホスト名に接続しようとしているかをTLSハンドシェイクの初期段階でサーバーに伝えるための仕組みです。これにより、サーバーは適切な証明書を選択してクライアントに提示できます。RFC 6066のセクション3では、SNIの`HostName`フィールドにはDNS名（ホスト名）のみが許可され、IPアドレスのリテラルは許可されないと明確に規定されています。これは、SNIがホスト名ベースのルーティングのために設計されており、IPアドレスはすでに接続先として指定されているため、SNIで改めて送る必要がないためです。

2.  **Goの実装における問題**: Goの `crypto/tls` パッケージでは、`Config.ServerName`フィールドがTLS接続の対象となるサーバー名を指定するために使用されます。このフィールドは、証明書の検証に使用されるだけでなく、SNI拡張の値としても利用されます。しかし、ユーザーが `net.Dial("tcp", "192.0.2.1:443")` のようにIPアドレスを直接指定して接続を開始した場合、`Config.ServerName`にはそのIPアドレスが設定される可能性がありました。このとき、GoのTLSクライアントは、RFCの規定に反して、このIPアドレスリテラルをそのままSNI値として送信してしまっていました。

3.  **相互運用性の問題**: RFCに準拠しないSNI値を送信すると、一部のTLSサーバーや中間プロキシがこれを不正なリクエストと判断し、接続を拒否したり、予期しない動作を引き起こしたりする可能性がありました。これは、TLSクライアントとサーバー間の相互運用性を損なう重大なバグとなります。

4.  **以前の修正と再適用**: コミットメッセージに「(This relands commit a4dcc692011bf1ceca9b1a363fd83f3e59e399ee.)」とあるように、この問題に対する修正は以前にも試みられていましたが、何らかの理由でリバートされたか、問題があったため、今回改めて修正が適用されました。これは、この問題が重要であり、確実に解決する必要があるという認識があったことを示唆しています。

5.  **Issue #13111**: この問題はGoのIssueトラッカーで #13111 として報告されていました。ユーザーからの報告やフィードバックが、この修正を促す直接的な要因となったと考えられます。

これらの背景から、このコミットは、GoのTLSクライアントがSNIの標準仕様に厳密に準拠するようにし、それによって潜在的な相互運用性の問題を解消することを目的とした、堅牢性向上のための重要な修正であると言えます。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **TLS (Transport Layer Security)**:
    *   インターネット上で安全な通信を行うためのプロトコルで、HTTP通信を暗号化するHTTPSの基盤となっています。
    *   クライアントとサーバー間で暗号化された接続を確立する際に「TLSハンドシェイク」と呼ばれる一連のプロセスを実行します。このハンドシェイク中に、サーバー認証（証明書の交換と検証）や暗号スイートのネゴシエーションが行われます。

2.  **SNI (Server Name Indication)**:
    *   TLSプロトコルの拡張機能の一つで、RFC 6066で定義されています。
    *   主な目的は、単一のIPアドレスで複数のウェブサイト（ドメイン）をホストしているサーバー（バーチャルホスティング）において、クライアントがどのドメインに接続しようとしているかをサーバーに伝えることです。
    *   クライアントはTLSハンドシェイクの初期段階（ClientHelloメッセージ内）で、接続先のホスト名をSNI拡張としてサーバーに送信します。サーバーはこの情報に基づいて、適切なTLS証明書を選択し、クライアントに提示します。
    *   **重要な制約**: RFC 6066のセクション3には、「Literal IPv4 and IPv6 addresses are not permitted in "HostName"」と明記されており、SNIの`HostName`フィールドにはDNS名（ドメイン名）のみが使用でき、IPアドレスのリテラルは使用できません。

3.  **`net.ParseIP` 関数 (Go言語)**:
    *   Go言語の標準ライブラリ `net` パッケージに含まれる関数です。
    *   文字列が有効なIPアドレス（IPv4またはIPv6）であるかどうかを解析し、`net.IP`型の値を返します。
    *   もし文字列が有効なIPアドレスでなければ、`nil`を返します。
    *   この関数は、文字列がIPアドレスリテラルであるかを効率的に判定するために利用されます。

4.  **`crypto/tls` パッケージ (Go言語)**:
    *   Go言語の標準ライブラリで、TLSプロトコルを実装しています。
    *   クライアントおよびサーバーサイドのTLS接続を確立・管理するための機能を提供します。
    *   `tls.Config` 構造体は、TLS接続の設定をカスタマイズするために使用され、`ServerName`フィールドはSNI値の決定にも影響を与えます。

5.  **`tls.Config.ServerName` フィールド**:
    *   `tls.Config` 構造体の一部で、接続先のサーバーのホスト名を指定します。
    *   この値は、サーバーから提示された証明書の検証に使用されます（証明書のCommon NameやSubject Alternative Nameがこの`ServerName`と一致するかどうかを確認）。
    *   また、クライアントがSNI拡張を送信する際に、その値としてこの`ServerName`が使用されます。

これらの知識を前提として、このコミットは、`tls.Config.ServerName`に誤ってIPアドレスが設定された場合に、それがSNIとして送信されないようにする、という具体的な問題を解決していることが理解できます。

## 技術的詳細

このコミットの技術的詳細は、`crypto/tls`パッケージのクライアントサイドTLSハンドシェイク処理におけるSNI値の生成ロジックに焦点を当てています。

1.  **問題の特定**: 以前の実装では、`tls.Config`構造体の`ServerName`フィールドに設定された値が、そのままClientHelloメッセージのSNI拡張の`serverName`フィールドにコピーされていました。この`ServerName`フィールドは、ユーザーが `net.Dial` などでIPアドレスを直接指定した場合に、IPアドレスリテラルが設定される可能性がありました。

2.  **RFC 6066への準拠**: RFC 6066 Section 3の「Literal IPv4 and IPv6 addresses are not permitted in "HostName"」という明確な規定に違反する動作でした。この規定は、SNIがホスト名ベースのバーチャルホスティングのために設計されており、IPアドレスはすでに接続先として指定されているため、SNIで改めて送る必要がないという背景に基づいています。

3.  **修正ロジック**:
    *   `src/crypto/tls/handshake_client.go` 内の `clientHandshake()` 関数が変更されました。
    *   SNI値をClientHelloメッセージに設定する直前に、`c.config.ServerName` の値がIPアドレスリテラルであるかどうかをチェックするロジックが追加されました。
    *   具体的には、`net.ParseIP(sni)` を呼び出し、その結果が `nil` でない（つまり、有効なIPアドレスとして解析された）場合に、SNIとして送信する `sni` 変数を空文字列 `""` に設定します。
    *   これにより、`tls.Config.ServerName` がIPアドレスリテラルであっても、SNI拡張としては何も送信されない（または空のSNIが送信される）ようになります。空のSNIは、SNI拡張自体を送信しないことと同義、またはサーバーがSNIを無視することを意味します。

4.  **影響範囲**:
    *   この変更は、`crypto/tls`パッケージを直接使用するアプリケーションだけでなく、`net/http`パッケージなど、`crypto/tls`に依存する上位レイヤーのパッケージにも影響を与えます。特に、`http.Client`がTLS接続を行う際に、`ServerName`がIPアドレスリテラルであった場合のSNIの挙動が修正されます。

5.  **テストの追加と修正**:
    *   `src/crypto/tls/handshake_client_test.go` に `TestNoIPAddressesInSNI` という新しいテストが追加されました。このテストは、IPv4およびIPv6のIPアドレスリテラルを`ServerName`に設定した場合に、ClientHelloメッセージのレコード内にそれらのIPアドレスが含まれていないことを検証します。`net.Pipe()` を使用してクライアントとサーバー間の通信をシミュレートし、ClientHelloメッセージの内容を直接検査しています。
    *   `src/net/http/client_test.go` 内の `TestClientWithCorrectTLSServerName` テストも修正されました。以前は`ServerName`としてIPアドレスリテラル（`"127.0.0.1"`）を期待していましたが、この修正により、ホスト名（`"example.com"`）を期待するように変更され、新しいSNIの挙動に合わせたテストになっています。

この修正により、GoのTLSクライアントはSNIの標準仕様に厳密に準拠するようになり、IPアドレスリテラルがSNIとして送信されることによる潜在的な相互運用性の問題が解消されます。

## コアとなるコードの解説

このコミットの核心は、`src/crypto/tls/handshake_client.go` 内の `clientHandshake()` 関数におけるSNI値の決定ロジックの変更にあります。

```go
// src/crypto/tls/handshake_client.go (抜粋)

func (c *Conn) clientHandshake() error {
    // ... (他の初期化処理)

    sni := c.config.ServerName // Config.ServerNameからSNI候補を取得
    // IP address literals are not permitted as SNI values. See
    // https://tools.ietf.org/html/rfc6066#section-3.
    if net.ParseIP(sni) != nil { // sniがIPアドレスリテラルであるかをチェック
        sni = "" // IPアドレスであれば、SNI値を空文字列に設定
    }

    hello := &clientHelloMsg{
        // ...
        serverName:          sni, // 最終的に決定されたsni値をClientHelloに設定
        // ...
    }

    // ... (ClientHelloメッセージの送信など、後続のハンドシェイク処理)
}
```

このコードスニペットが示すように、変更のポイントは以下の通りです。

1.  **`sni := c.config.ServerName`**: まず、`tls.Config` に設定されている `ServerName` の値を `sni` 変数に代入します。この `ServerName` は、ユーザーがTLS接続を確立する際に指定したホスト名またはIPアドレスです。

2.  **`if net.ParseIP(sni) != nil`**: ここが最も重要な部分です。
    *   `net.ParseIP(sni)` 関数が呼び出され、`sni` の文字列が有効なIPアドレス（IPv4またはIPv6）として解析できるかどうかが試みられます。
    *   もし `net.ParseIP` が `nil` 以外の値を返した場合、それは `sni` がIPアドレスリテラルであることを意味します。

3.  **`sni = ""`**: `sni` がIPアドレスリテラルであると判定された場合、`sni` 変数は空文字列 `""` に上書きされます。これにより、後続の `clientHelloMsg` 構造体の `serverName` フィールドには空文字列が設定されることになります。TLSプロトコルにおいて、SNI拡張が空文字列である、またはSNI拡張自体が存在しない場合、サーバーはSNI情報を使用しないか、無視します。これは、RFC 6066の「IPアドレスリテラルは許可されない」という規定に準拠する挙動です。

このシンプルなチェックと条件付きの代入によって、GoのTLSクライアントは、`Config.ServerName`にIPアドレスが設定されていても、SNIとしてIPアドレスリテラルを送信するというRFC違反の動作を防ぐことができます。これにより、TLS接続の堅牢性と相互運用性が向上します。

## 元コミット内容

`crypto/tls: don't send IP literals as SNI values.`

このコミットは、`crypto/tls`パッケージにおいて、SNI (Server Name Indication) 値としてIPアドレスのリテラルを送信しないようにする変更です。以前のコミット `a4dcc692011bf1ceca9b1a363fd83f3e59e399ee` の再適用（reland）にあたります。

RFC 6066のセクション3では、「HostName」フィールドにIPv4およびIPv6のリテラルアドレスは許可されないと明記されています。しかし、`Config.ServerName`にIPアドレスが設定された場合（例えば、IPアドレスを指定して`Dial`を呼び出した場合）、GoのTLSクライアントは誤ってそのIPアドレスをSNI値として送信していました。

この変更は、`net.ParseIP`関数を使用してIPアドレスのリテラルを検出し、それらがSNI値として送信されるのを防ぎます。これにより、#13111で報告された問題が修正されます。

## 変更の背景

この変更の背景には、TLSプロトコルの拡張であるServer Name Indication (SNI) の仕様と、Go言語の `crypto/tls` パッケージにおけるその実装の不整合がありました。

1.  **SNIの目的と仕様**: SNIは、単一のIPアドレスで複数のドメインをホストするサーバー（バーチャルホスティング）において、クライアントがどのホスト名に接続しようとしているかをTLSハンドシェイクの初期段階でサーバーに伝えるための仕組みです。これにより、サーバーは適切な証明書を選択してクライアントに提示できます。RFC 6066のセクション3では、SNIの`HostName`フィールドにはDNS名（ホスト名）のみが許可され、IPアドレスのリテラルは許可されないと明確に規定されています。これは、SNIがホスト名ベースのルーティングのために設計されており、IPアドレスはすでに接続先として指定されているため、SNIで改めて送る必要がないためです。

2.  **Goの実装における問題**: Goの `crypto/tls` パッケージでは、`Config.ServerName`フィールドがTLS接続の対象となるサーバー名を指定するために使用されます。このフィールドは、証明書の検証に使用されるだけでなく、SNI拡張の値としても利用されます。しかし、ユーザーが `net.Dial("tcp", "192.0.2.1:443")` のようにIPアドレスを直接指定して接続を開始した場合、`Config.ServerName`にはそのIPアドレスが設定される可能性がありました。このとき、GoのTLSクライアントは、RFCの規定に反して、このIPアドレスリテラルをそのままSNI値として送信してしまっていました。

3.  **相互運用性の問題**: RFCに準拠しないSNI値を送信すると、一部のTLSサーバーや中間プロキシがこれを不正なリクエストと判断し、接続を拒否したり、予期しない動作を引き起こしたりする可能性がありました。これは、TLSクライアントとサーバー間の相互運用性を損なう重大なバグとなります。

4.  **以前の修正と再適用**: コミットメッセージに「(This relands commit a4dcc692011bf1ceca9b1a363fd83f3e59e399ee.)」とあるように、この問題に対する修正は以前にも試みられていましたが、何らかの理由でリバートされたか、問題があったため、今回改めて修正が適用されました。これは、この問題が重要であり、確実に解決する必要があるという認識があったことを示唆しています。

5.  **Issue #13111**: この問題はGoのIssueトラッカーで #13111 として報告されていました。ユーザーからの報告やフィードバックが、この修正を促す直接的な要因となったと考えられます。

これらの背景から、このコミットは、GoのTLSクライアントがSNIの標準仕様に厳密に準拠するようにし、それによって潜在的な相互運用性の問題を解消することを目的とした、堅牢性向上のための重要な修正であると言えます。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **TLS (Transport Layer Security)**:
    *   インターネット上で安全な通信を行うためのプロトコルで、HTTP通信を暗号化するHTTPSの基盤となっています。
    *   クライアントとサーバー間で暗号化された接続を確立する際に「TLSハンドシェイク」と呼ばれる一連のプロセスを実行します。このハンドシェイク中に、サーバー認証（証明書の交換と検証）や暗号スイートのネゴシエーションが行われます。

2.  **SNI (Server Name Indication)**:
    *   TLSプロトコルの拡張機能の一つで、RFC 6066で定義されています。
    *   主な目的は、単一のIPアドレスで複数のウェブサイト（ドメイン）をホストしているサーバー（バーチャルホスティング）において、クライアントがどのドメインに接続しようとしているかをサーバーに伝えることです。
    *   クライアントはTLSハンドシェイクの初期段階（ClientHelloメッセージ内）で、接続先のホスト名をSNI拡張としてサーバーに送信します。サーバーはこの情報に基づいて、適切なTLS証明書を選択し、クライアントに提示します。
    *   **重要な制約**: RFC 6066のセクション3には、「Literal IPv4 and IPv6 addresses are not permitted in "HostName"」と明記されており、SNIの`HostName`フィールドにはDNS名（ドメイン名）のみが使用でき、IPアドレスのリテラルは使用できません。

3.  **`net.ParseIP` 関数 (Go言語)**:
    *   Go言語の標準ライブラリ `net` パッケージに含まれる関数です。
    *   文字列が有効なIPアドレス（IPv4またはIPv6）であるかどうかを解析し、`net.IP`型の値を返します。
    *   もし文字列が有効なIPアドレスでなければ、`nil`を返します。
    *   この関数は、文字列がIPアドレスリテラルであるかを効率的に判定するために利用されます。

4.  **`crypto/tls` パッケージ (Go言語)**:
    *   Go言語の標準ライブラリで、TLSプロトコルを実装しています。
    *   クライアントおよびサーバーサイドのTLS接続を確立・管理するための機能を提供します。
    *   `tls.Config` 構造体は、TLS接続の設定をカスタマイズするために使用され、`ServerName`フィールドはSNI値の決定にも影響を与えます。

5.  **`tls.Config.ServerName` フィールド**:
    *   `tls.Config` 構造体の一部で、接続先のサーバーのホスト名を指定します。
    *   この値は、サーバーから提示された証明書の検証に使用されます（証明書のCommon NameやSubject Alternative Nameがこの`ServerName`と一致するかどうかを確認）。
    *   また、クライアントがSNI拡張を送信する際に、その値としてこの`ServerName`が使用されます。

これらの知識を前提として、このコミットは、`tls.Config.ServerName`に誤ってIPアドレスが設定された場合に、それがSNIとして送信されないようにする、という具体的な問題を解決していることが理解できます。

## 技術的詳細

このコミットの技術的詳細は、`crypto/tls`パッケージのクライアントサイドTLSハンドシェイク処理におけるSNI値の生成ロジックに焦点を当てています。

1.  **問題の特定**: 以前の実装では、`tls.Config`構造体の`ServerName`フィールドに設定された値が、そのままClientHelloメッセージのSNI拡張の`serverName`フィールドにコピーされていました。この`ServerName`フィールドは、ユーザーが `net.Dial` などでIPアドレスを直接指定した場合に、IPアドレスリテラルが設定される可能性がありました。

2.  **RFC 6066への準拠**: RFC 6066 Section 3の「Literal IPv4 and IPv6 addresses are not permitted in "HostName"」という明確な規定に違反する動作でした。この規定は、SNIがホスト名ベースのバーチャルホスティングのために設計されており、IPアドレスはすでに接続先として指定されているため、SNIで改めて送る必要がないという背景に基づいています。

3.  **修正ロジック**:
    *   `src/crypto/tls/handshake_client.go` 内の `clientHandshake()` 関数が変更されました。
    *   SNI値をClientHelloメッセージに設定する直前に、`c.config.ServerName` の値がIPアドレスリテラルであるかどうかをチェックするロジックが追加されました。
    *   具体的には、`net.ParseIP(sni)` を呼び出し、その結果が `nil` でない（つまり、有効なIPアドレスとして解析された）場合に、SNIとして送信する `sni` 変数を空文字列 `""` に設定します。
    *   これにより、`tls.Config.ServerName` がIPアドレスリテラルであっても、SNI拡張としては何も送信されない（または空のSNIが送信される）ようになります。空のSNIは、SNI拡張自体を送信しないことと同義、またはサーバーがSNIを無視することを意味します。

4.  **影響範囲**:
    *   この変更は、`crypto/tls`パッケージを直接使用するアプリケーションだけでなく、`net/http`パッケージなど、`crypto/tls`に依存する上位レイヤーのパッケージにも影響を与えます。特に、`http.Client`がTLS接続を行う際に、`ServerName`がIPアドレスリテラルであった場合のSNIの挙動が修正されます。

5.  **テストの追加と修正**:
    *   `src/crypto/tls/handshake_client_test.go` に `TestNoIPAddressesInSNI` という新しいテストが追加されました。このテストは、IPv4およびIPv6のIPアドレスリテラルを`ServerName`に設定した場合に、ClientHelloメッセージのレコード内にそれらのIPアドレスが含まれていないことを検証します。`net.Pipe()` を使用してクライアントとサーバー間の通信をシミュレートし、ClientHelloメッセージの内容を直接検査しています。
    *   `src/net/http/client_test.go` 内の `TestClientWithCorrectTLSServerName` テストも修正されました。以前は`ServerName`としてIPアドレスリテラル（`"127.0.0.1"`）を期待していましたが、この修正により、ホスト名（`"example.com"`）を期待するように変更され、新しいSNIの挙動に合わせたテストになっています。

この修正により、GoのTLSクライアントはSNIの標準仕様に厳密に準拠するようになり、IPアドレスリテラルがSNIとして送信されることによる潜在的な相互運用性の問題が解消されます。

## コアとなるコードの変更箇所

    *   これは、`ServerName`がIPアドレスの場合にはSNIとして送信されないという新しい挙動を反映するためのドキュメントの更新です。

        // ...

            // ...
            serverName:          c.config.ServerName,
            // ...
        }
        ```

        // ...
        sni := c.config.ServerName

        if net.ParseIP(sni) != nil { // sniがIPアドレスリテラルであるかをチェック

        }
        ```
    *   この部分が、IPアドレスリテラルをSNIとして送信しないようにする主要なロジックです。`net.ParseIP` を使って `ServerName` がIPアドレスかどうかを判定し、IPアドレスであれば `sni` 変数を空文字列に設定しています。

3.  **`src/crypto/tls/handshake_client_test.go`**:

    *   また、`newTLSTransport` の設定で `trans.TLSClientConfig.ServerName = serverName` を明示的に設定することで、テストが新しいSNIの挙動を正しく検証するように調整されています。

これらの変更により、GoのTLSクライアントはSNIの標準仕様に準拠し、IPアドレスリテラルがSNIとして送信されることがなくなります。

## コアとなるコードの解説

このコミットの核心は、`src/crypto/tls/handshake_client.go` 内の `clientHandshake()` 関数におけるSNI値の決定ロジックの変更にあります。

```go
// src/crypto/tls/handshake_client.go (抜粋)

func (c *Conn) clientHandshake() error {
    // ... (他の初期化処理)

    sni := c.config.ServerName // Config.ServerNameからSNI候補を取得
    // IP address literals are not permitted as SNI values. See
    // https://tools.ietf.org/html/rfc6066#section-3.
    if net.ParseIP(sni) != nil { // sniがIPアドレスリテラルであるかをチェック
        sni = "" // IPアドレスであれば、SNI値を空文字列に設定
    }

    hello := &clientHelloMsg{
        // ...
        serverName:          sni, // 最終的に決定されたsni値をClientHelloに設定
        // ...
    }

    // ... (ClientHelloメッセージの送信など、後続のハンドシェイク処理)
}
```

このコードスニペットが示すように、変更のポイントは以下の通りです。

1.  **`sni := c.config.ServerName`**: まず、`tls.Config` に設定されている `ServerName` の値を `sni` 変数に代入します。この `ServerName` は、ユーザーがTLS接続を確立する際に指定したホスト名またはIPアドレスです。

2.  **`if net.ParseIP(sni) != nil`**: ここが最も重要な部分です。
    *   `net.ParseIP(sni)` 関数が呼び出され、`sni` の文字列が有効なIPアドレス（IPv4またはIPv6）として解析できるかどうかが試みられます。
    *   もし `net.ParseIP` が `nil` 以外の値を返した場合、それは `sni` がIPアドレスリテラルであることを意味します。

3.  **`sni = ""`**: `sni` がIPアドレスリテラルであると判定された場合、`sni` 変数は空文字列 `""` に上書きされます。これにより、後続の `clientHelloMsg` 構造体の `serverName` フィールドには空文字列が設定されることになります。TLSプロトコルにおいて、SNI拡張が空文字列である、またはSNI拡張自体が存在しない場合、サーバーはSNI情報を使用しないか、無視します。これは、RFC 6066の「IPアドレスリテラルは許可されない」という規定に準拠する挙動です。

このシンプルなチェックと条件付きの代入によって、GoのTLSクライアントは、`Config.ServerName`にIPアドレスが設定されていても、SNIとしてIPアドレスリテラルを送信するというRFC違反の動作を防ぐことができます。これにより、TLS接続の堅牢性と相互運用性が向上します。

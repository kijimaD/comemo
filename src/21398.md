# [インデックス 21398] ファイルの概要

このコミットは、GoランタイムにおけるCPUプロファイリング時の安定性向上を目的としています。具体的には、GoプログラムがCgo呼び出しを行う前に、外部ライブラリ（例: OpenBLAS）によって作成された「外部スレッド（foreign threads）」に`SIGPROF`シグナルが送信された場合に発生するプロセスの中断（abort）を防ぐための変更です。

## 元コミット内容

```
runtime: ignore SIGPROF to foreign threads before cgocallback is fully initialized

Some libraries, for example, OpenBLAS, create work threads in a global constructor.
If we're doing cpu profiling, it's possible that SIGPROF might come to some of the
worker threads before we make our first cgo call. Cgocallback used to terminate the
process when that happens, but it's better to miss a couple profiling signals than
to abort in this case.

Fixes #9456.
```

## 変更の背景

この変更は、GoプログラムがCgo（GoとC言語の相互運用機能）を使用する際に発生する可能性のある、特定のクラッシュ問題を解決するために導入されました。

問題の根本原因は、CPUプロファイリングに使用される`SIGPROF`シグナルと、Goランタイムが外部スレッド（Goランタイムによって直接作成されていないOSスレッド）からのシグナルを処理する方法との間の競合状態にありました。

一部のC/C++ライブラリ、特にOpenBLASのような数値計算ライブラリは、「グローバルコンストラクタ」と呼ばれる特殊な関数を使用します。これらのグローバルコンストラクタは、Goプログラムの`main`関数が実行される前に自動的に実行され、その過程で独自のワーカースレッドを作成することがあります。これらのスレッドはGoランタイムにとっては「外部スレッド」と見なされます。

Goランタイムは、外部スレッドからのシグナルを処理するために`cgocallback`というメカニズムを使用します。しかし、この`cgocallback`は、Goプログラムが最初のCgo呼び出しを行うまで完全に初期化されません。

CPUプロファイリングが有効になっている場合、Goランタイムは定期的に`SIGPROF`シグナルをプロセス内のスレッドに送信して、実行スタックをサンプリングします。もし、GoプログラムがまだCgo呼び出しを行っておらず、`cgocallback`が未初期化の状態で、外部ライブラリによって作成された外部スレッドに`SIGPROF`シグナルが到達した場合、Goランタイムは未初期化の`cgocallback`を通じてシグナルを処理しようとし、結果としてプロセス全体が異常終了（abort）していました。

このコミットは、このような状況でプロセスがクラッシュするよりも、一時的にプロファイリングシグナルをいくつか見逃す方が望ましいという判断に基づいています。これにより、Goプログラムと外部C/C++ライブラリの連携における堅牢性が向上します。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **`SIGPROF`シグナル**:
    *   `SIGPROF`はUnix系OSで利用されるシグナルの一つで、プロファイリングツールによってCPU使用率を測定するために使用されます。
    *   プロファイラは、このシグナルを定期的にプロセス内のスレッドに送信し、シグナルを受け取ったスレッドの現在の実行スタックを記録します。これにより、どの関数がCPU時間を多く消費しているかを特定できます。
    *   GoのCPUプロファイリングもこの`SIGPROF`シグナルを利用しています。

2.  **Cgo**:
    *   CgoはGo言語の機能で、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりすることを可能にします。
    *   これにより、既存のC/C++ライブラリをGoプロジェクトで再利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。

3.  **外部スレッド（Foreign Threads）**:
    *   Goランタイムは独自のスケジューラとスレッド管理メカニズムを持っています。Goランタイムが直接作成・管理するスレッドとは別に、Cgoを通じてリンクされたC/C++ライブラリが、OSのAPI（例: `pthread_create`）を直接呼び出してスレッドを作成することがあります。
    *   これらのGoランタイムの管理下にないスレッドを「外部スレッド」と呼びます。Goランタイムは、これらの外部スレッドからのシグナルを適切に処理するために特別なメカニズムを必要とします。

4.  **`cgocallback`**:
    *   Goランタイムが外部スレッドからのシグナルを処理するための内部メカニズムです。
    *   外部スレッドでシグナルが発生した場合、Goランタイムは`cgocallback`を通じてそのシグナルをGoのシグナル処理システムに引き渡そうとします。
    *   この`cgocallback`は、Goプログラムが最初のCgo呼び出しを行った際に初期化されます。これは、GoプログラムがCgoを使用するまで、外部スレッドからのシグナル処理の必要性が低いと見なされるためです。

5.  **グローバルコンストラクタ**:
    *   C++などの言語には、プログラムの`main`関数が実行される前に自動的に実行される特殊な関数（またはオブジェクトのコンストラクタ）を定義する機能があります。これらを「グローバルコンストラクタ」と呼びます。
    *   ライブラリによっては、初期化処理（例: スレッドプールの作成、リソースのロード）をグローバルコンストラクタ内で行うことがあります。

6.  **OpenBLAS**:
    *   OpenBLASは、線形代数演算（BLAS: Basic Linear Algebra Subprograms）を高速に実行するためのオープンソースライブラリです。
    *   CPUの並列処理能力を最大限に活用するために、内部で複数のワーカースレッドを作成して計算を分散させることが一般的です。このスレッド作成がグローバルコンストラクタで行われることがあります。

## 技術的詳細

このコミットの技術的解決策は、`src/runtime/sigqueue.go`内の`badsignal`関数に条件付きの早期リターンを追加することです。

`badsignal`関数は、Goランタイムが予期しないシグナルを外部スレッドで受け取った場合に呼び出される関数です。以前は、この関数は常に`cgocallback`を呼び出してシグナルをGoのシグナル処理システムに引き渡そうとしていました。

変更後、`badsignal`関数は以下のチェックを行うようになりました。

1.  受信したシグナルが`_SIGPROF`（CPUプロファイリングシグナル）であるか？
2.  かつ、`needextram != 0`であるか？

`needextram`は、GoランタイムがまだCgo呼び出しを行っておらず、外部スレッドからのシグナル処理のための追加のM（Machine、OSスレッドを表すGoランタイムの構造体）が必要な状態であることを示すフラグです。つまり、`cgocallback`がまだ完全に初期化されていない状態を意味します。

もし両方の条件が真であれば、つまり、`SIGPROF`シグナルが`cgocallback`が未初期化の外部スレッドに到達した場合、`badsignal`関数は単に`return`し、シグナルを無視します。これにより、未初期化の`cgocallback`を呼び出すことによるクラッシュを防ぎます。

このアプローチは、プロファイリングの精度をわずかに低下させる可能性がありますが、プログラムの安定性を優先しています。数個の`SIGPROF`シグナルを見逃すことは、プロセス全体がクラッシュするよりもはるかに許容できるトレードオフであるという判断です。

また、この変更を検証するために、`src/runtime/crash_cgo_test.go`に新しいテストケース`TestCgoExternalThreadSIGPROF`が追加されました。このテストは、Cgo呼び出しを行う前に、グローバルコンストラクタを通じて作成された外部スレッドに`SIGPROF`シグナルを意図的に送信し、プロセスがクラッシュしないことを確認します。

## コアとなるコードの解説

### `src/runtime/sigqueue.go` の変更

```go
func badsignal(sig uintptr) {
	// Some external libraries, for example, OpenBLAS, create worker threads in
	// a global constructor. If we're doing cpu profiling, and the SIGPROF signal
	// comes to one of the foreign threads before we make our first cgo call, the
	// call to cgocallback below will bring down the whole process.
	// It's better to miss a few SIGPROF signals than to abort in this case.
	// See http://golang.org/issue/9456.
	if sig == _SIGPROF && needextram != 0 {
		return
	}
	cgocallback(unsafe.Pointer(funcPC(sigsend)), noescape(unsafe.Pointer(&sig)), unsafe.Sizeof(sig))
}
```

*   `badsignal`関数は、Goランタイムが管理していない外部スレッドでシグナルが受信された場合に呼び出されます。
*   `if sig == _SIGPROF && needextram != 0` の条件が追加されました。
    *   `sig == _SIGPROF`: 受信したシグナルがCPUプロファイリング用の`SIGPROF`であるかをチェックします。
    *   `needextram != 0`: このフラグは、GoランタイムがまだCgo呼び出しを行っておらず、外部スレッドからのシグナルを処理するための準備が整っていない状態（`cgocallback`が未初期化）であることを示します。
*   この条件が真の場合、関数は`return`し、それ以上何も処理せずにシグナルを無視します。これにより、未初期化の`cgocallback`を呼び出すことによるクラッシュを防ぎます。
*   コメントには、OpenBLASのようなライブラリがグローバルコンストラクタでワーカースレッドを作成するシナリオが具体的に言及されており、この変更の目的が明確に説明されています。

### `src/runtime/crash_cgo_test.go` の変更

```go

/*
#include <stdint.h>
#include <signal.h>
#include <pthread.h>

	(void)p;
	while (spinlock == 0)
		;
	pthread_kill(pthread_self(), SIGPROF);
	spinlock = 0;
	return NULL;
}
__attribute__((constructor)) void issue9456() {
	pthread_t tid;
	pthread_create(&tid, 0, thread1, NULL);
}
*/

import (
	"runtime"
	"sync/atomic"
	"unsafe"
)

	// before we make any cgo call will not abort the whole process, so
	// we cannot make any cgo call here. See http://golang.org/issue/9456.
	atomic.StoreInt32((*int32)(unsafe.Pointer(&C.spinlock)), 1)

`
```

*   `TestCgoExternalThreadSIGPROF`は、このバグが修正されたことを検証するための新しいテストケースです。
*   `cgoExternalThreadSIGPROFSource`は、テスト用のCgoを含むGoプログラムのソースコードです。
    *   Cコード部分では、`__attribute__((constructor))`を使用して、Goの`main`関数が実行される前に`issue9456`関数が呼び出されるようにしています。
    *   `issue9456`関数内で`pthread_create`を呼び出し、新しいスレッド（`thread1`）を作成します。このスレッドはGoランタイムにとっては外部スレッドです。
    *   `thread1`は、`spinlock`が設定されるのを待ってから、自身に`SIGPROF`シグナルを送信します。
    *   Goコードの`main`関数では、Cgo呼び出しを一切行いません。これは、`cgocallback`が未初期化の状態で`SIGPROF`が外部スレッドに到達するシナリオを再現するためです。
    *   `atomic.StoreInt32`と`atomic.LoadInt32`を使って、C側のスレッドとGo側のメインスレッドが同期し、C側のスレッドが`SIGPROF`を送信するのを待ちます。
*   テストは、プロセスがクラッシュせずに"OK"を出力することを確認します。これにより、`badsignal`の変更が意図通りに機能し、`SIGPROF`が安全に無視されることが保証されます。

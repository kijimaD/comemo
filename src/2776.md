## 元コミット内容

Goランタイム: `init`関数のスケジューリングバグを修正。

もし実行を待っているゴルーチンがあり、かつ`init`ゴルーチンがシステムコールに入った場合、`entersyscall`は他のゴルーチンのために新しいスケジューラを起動しようとしていました。これはパニックを引き起こしていました（`main.main`が開始されるまで新しいゴルーチンは実行できません）。

## 変更の背景

Goプログラムの起動時、`main`パッケージの`main`関数が実行される前に、各パッケージの`init`関数が実行されます。この`init`フェーズ中に、もし`init`関数がシステムコール（例: `time.Nanoseconds()`）を実行し、同時に別のゴルーチンが`go`キーワードによって起動されていた場合、Goランタイムの`entersyscall`関数が誤った動作をしていました。

具体的には、`entersyscall`は、システムコールに入ろうとするゴルーチンを一時停止させ、他の実行可能なゴルーチンがあれば、そのために新しいスケジューラ（OSスレッド）を起動しようとします。しかし、プログラムの非常に初期段階である`init`フェーズでは、Goランタイムのスケジューラがまだ完全に初期化されていません。この未初期化の状態でスケジューラを起動しようとすると、内部的な不整合が発生し、結果としてランタイムパニック（プログラムのクラッシュ）を引き起こしていました。

このバグは、`main.main`が開始されるまで、Goランタイムが新しいゴルーチンを完全にスケジューリングできる状態ではないという、Goの起動シーケンスにおける重要な制約を無視したことによって発生していました。

## 前提知識の解説

### Goの並行処理とGoroutine
Go言語は、軽量な並行処理の単位として「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。`go`キーワードを使って関数を呼び出すことで、新しいゴルーチンが起動されます。

### Goランタイムとスケジューラ
Goランタイムは、Goプログラムの実行を管理するシステムです。その主要なコンポーネントの一つが「スケジューラ」です。スケジューラは、多数のゴルーチンを限られた数のOSスレッドに効率的にマッピングし、実行を切り替える役割を担います。これにより、プログラマは並行処理の複雑さを意識することなく、ゴルーチンを記述できます。

### `init()`関数の役割と実行タイミング
Goの各パッケージは、`init()`という特殊な関数を定義できます。`init()`関数は、そのパッケージがインポートされた際に、`main`関数が実行されるよりも前に自動的に実行されます。複数の`init()`関数がある場合、それらは定義された順序で実行されます。これらは通常、パッケージの初期化、変数の設定、外部リソースの準備などに使用されます。

### システムコールと`entersyscall`/`exitsyscall`の役割
システムコール（syscall）は、実行中のプログラムがオペレーティングシステム（OS）のカーネルにサービスを要求するメカニズムです。ファイルI/O、ネットワーク通信、時間取得（例: `time.Nanoseconds()`）などがシステムコールを伴います。
Goランタイムは、ゴルーチンがシステムコールに入る際と出る際に、それぞれ`entersyscall`と`exitsyscall`という内部関数を呼び出します。これらの関数は、スケジューラに対してゴルーチンの状態（システムコール中であること）を通知し、必要に応じて他のゴルーチンをスケジューリングするための重要なフックとなります。システムコール中はゴルーチンがOSによってブロックされる可能性があるため、Goスケジューラは他のゴルーチンを実行するためにOSスレッドを解放したり、新しいOSスレッドを起動したりすることがあります。

### Goプログラムの起動シーケンス
Goプログラムは、以下の大まかな順序で起動します。
1.  ランタイムの初期化（非常に低レベルな部分）
2.  インポートされたパッケージの`init()`関数の実行
3.  `main`パッケージの`init()`関数の実行
4.  `main`パッケージの`main()`関数の実行

このコミットのバグは、ステップ2または3の間に発生していました。

## 技術的詳細

この修正は、Goランタイムのスケジューリングロジックに、プログラムの非常に初期段階（`predawn`状態）を識別するガードを追加することで実現されています。

Goランタイムの内部には、`sched`というグローバルなスケジューラ状態を管理する構造体があります。この`sched`構造体には、`predawn`というブーリアンフラグが追加されました。この`predawn`フラグは、Goランタイムがまだ完全に初期化されておらず、`main.main`関数が開始される前の「夜明け前」の状態にあることを示します。

修正の核心は、`src/pkg/runtime/proc.c`内の`sys·entersyscall`および`sys·exitsyscall`関数に、この`sched.predawn`フラグのチェックを追加したことです。

1.  **`sys·entersyscall`関数への変更**:
    ゴルーチンがシステムコールに入ろうとする際に呼び出される`sys·entersyscall`関数は、まず`sched`構造体のロックを取得します。そして、`if(sched.predawn)`という条件をチェックします。もし`predawn`が真（true）であれば、ランタイムはまだ初期化の初期段階にあるため、通常のスケジューリングロジック（ゴルーチンの状態変更やスケジューラの起動試行）を実行せずに、すぐにロックを解放して関数からリターンします。これにより、未初期化のスケジューラが誤って操作されることを防ぎます。

2.  **`sys·exitsyscall`関数への変更**:
    同様に、ゴルーチンがシステムコールから戻る際に呼び出される`sys·exitsyscall`関数も、`sched.predawn`フラグをチェックします。`predawn`が真であれば、ここでも通常のスケジューリング関連の処理をスキップし、早期にリターンします。

この変更により、`init`関数内でシステムコールが実行され、同時に別のゴルーチンが起動されていても、ランタイムが`predawn`状態にある限り、`entersyscall`や`exitsyscall`はスケジューリングに関する危険な操作を試みなくなります。これにより、`main.main`が開始されるまで新しいゴルーチンが完全に実行可能ではないという制約が尊重され、パニックが回避されます。

## コアとなるコードの変更箇所

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の変更

```c
// sys·entersyscall 関数内
 	lock(&sched); // スケジューラ状態を保護するためにロックを取得
 	if(sched.predawn) { // もしランタイムが「夜明け前」の初期化状態であれば
 		unlock(&sched); // ロックを解放し
 		return;         // 何もせずに即座にリターン
 	}
 	g->status = Gsyscall; // ゴルーチンの状態をシステムコール中に設定（predawnでない場合のみ）
```
このコードは、`sys·entersyscall`が呼び出された際に、まずスケジューラのグローバル状態`sched`をロックします。そして、`sched.predawn`というフラグがセットされているかを確認します。`predawn`フラグは、Goランタイムがまだ完全に初期化されていない、非常に初期の段階であることを示します。この状態であれば、通常のゴルーチン状態の変更（`g->status = Gsyscall;`）や、それに続くスケジューリング関連の処理は時期尚早であり、パニックを引き起こす可能性があるため、ロックを解放して関数からすぐに戻ります。

`sys·exitsyscall`関数にも同様のロジックが追加されており、システムコールから戻る際にも`predawn`状態であればスケジューリング処理をスキップします。

### `test/initsyscall.go` の追加

```go
package main

import "log"
import "time"

func f() {
	// このゴルーチンは起動されるが、main.mainが開始されるまで実行されない
}

func init() {
	go f(); // init関数内で新しいゴルーチンを起動
	time.Nanoseconds(); // システムコールを実行
}

func main() {
	// main関数は空だが、これが開始されることでランタイムが完全に初期化される
}
```
このテストコードは、バグの再現シナリオを簡潔に示しています。
1.  `init()`関数内で`go f()`を呼び出すことで、新しいゴルーチン`f`が起動されます。この時点では`f`は実行を待機している状態です。
2.  直後に`time.Nanoseconds()`が呼び出されます。これはシステムコールを伴う操作であり、`sys·entersyscall`が内部的に呼び出されます。
3.  修正前は、この`entersyscall`が`predawn`状態を考慮せずに、待機中の`f`ゴルーチンのためにスケジューラを起動しようとし、パニックを引き起こしていました。
4.  修正後は、`entersyscall`が`predawn`フラグを検知し、スケジューリング処理をスキップするため、パニックは発生せず、プログラムは正常に`main()`関数へと進みます。`f`ゴルーチンは`main.main`が開始され、スケジューラが完全に機能するようになった後に実行されることになります。

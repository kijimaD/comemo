# [インデックス 26644] ファイルの概要

このコミットは、Goコンパイラの内部におけるエクスポートデータ（import data）のパース処理をリファクタリングするものです。具体的には、`push_parser` と `pop_parser` の機能を `parse_import` 関数に統合し、`unimportfile` をインライン化することで、コードの対称性を高め、冗長な処理を削減しています。これにより、コンパイラのコードベースがよりクリーンで効率的になり、特にインポート処理における診断メッセージの改善にも繋がっています。

## 元コミット内容

`cmd/compile: refactor export data parsing`

`push_parser` と `pop_parser` を単一の `parse_import` 関数に統合し、`unimportfile` をインライン化する。関数の境界を少し整理し、対称性が容易にわかるようにする。

`import_package` の呼び出しを `parse_import` 内に移動する（そして `import_there` を `import_package` 内にインライン化する）。これにより、`importfile` は呼び出されるたびに不要に字句解析/パースされるフェイクのインポートデータを提供する必要がなくなる。

また、次のトークンが "package" であるかどうかでインポートの成功/失敗を示す代わりに、`import_spec` は `importpkg` が非nilであるかどうかをチェックするだけでよい。

付随的に、これにより `test/fixedbugs/issue11610.go` で生成される診断が変更される。しかし、新しい診断は空のインポート文がない場合に生成されるものとより一貫しており、以前のエラーを維持するよりも望ましいと思われる。

## 変更の背景

Goコンパイラは、パッケージのインポート時にそのパッケージのエクスポートデータ（型情報、関数シグネチャなど）を読み込み、解析する必要があります。この処理は、コンパイルの効率と正確性に直結します。

このコミット以前のGoコンパイラでは、エクスポートデータのパース処理において、パーサーの状態を保存・復元するための `push_parser` と `pop_parser` という関数が使われていました。また、インポート処理の終了時にリソースを解放する `unimportfile` という関数も存在しました。これらの関数は、インポート処理の開始と終了を管理するために使用されていましたが、コードの重複や複雑さを生み出す可能性がありました。

特に、`importfile` 関数がインポート処理を行う際に、毎回「フェイクのインポートデータ」を生成し、それを字句解析・パースさせるという非効率なメカニズムが存在していました。これは、インポートが失敗した場合や、既にインポート済みのパッケージである場合でも、パーサーが期待する形式のデータを一時的に提供する必要があったためです。この冗長な処理は、コンパイル時間の増加やコードの可読性の低下に繋がっていました。

このコミットの目的は、これらの問題を解決し、エクスポートデータのパース処理をよりシンプルで効率的、かつ対称的な構造にリファクタリングすることにあります。これにより、コンパイラの保守性が向上し、将来的な機能拡張が容易になることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

*   **Goコンパイラの構造 (`cmd/compile`)**: Goコンパイラは、`cmd/compile` ディレクトリ以下に実装されています。このディレクトリには、字句解析（lexing）、構文解析（parsing）、型チェック（type checking）、コード生成（code generation）など、コンパイルの各フェーズを担うコードが含まれています。
*   **字句解析器 (Lexer)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換するコンポーネントです。`src/cmd/compile/internal/gc/lex.go` は字句解析器の主要な部分を担っています。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンのストリームを受け取り、Go言語の文法規則に従って抽象構文木（AST）を構築するコンポーネントです。`src/cmd/compile/internal/gc/parser.go` は構文解析器の主要な部分を担っています。
*   **エクスポートデータ (Export Data)**: Goのパッケージは、他のパッケージから利用されるために、その公開された型、関数、変数などの情報をエクスポートします。この情報は、コンパイル済みパッケージファイル（通常は `.a` ファイル）内に格納されており、インポート時にコンパイラによって読み込まれます。
*   **`importpkg`**: コンパイラが現在処理しているインポート対象のパッケージを表すグローバル変数（またはそれに準ずる状態）です。
*   **`curio` と `pushedio`**: Goコンパイラの字句解析器は、複数の入力ストリーム（ファイル、文字列など）を切り替えるメカニズムを持っています。`curio` は現在の入力ストリームの状態を保持し、`pushedio` は一時的に切り替える前の状態を保存するために使用されます。これは、例えばインポートされたパッケージのエクスポートデータをパースする際に、一時的に入力ソースを切り替えるために利用されます。
*   **`cannedimports`**: 特定の組み込みパッケージ（`runtime` や `unsafe` など）のエクスポートデータを、ファイルから読み込むのではなく、コンパイラ内部にハードコードされた文字列として提供するためのメカニズムです。
*   **`obj.Biobuf`**: Goコンパイラ内部で使用されるバッファリングされたI/O構造体です。ファイルからの読み込みを効率的に行います。
*   **`Yyerror` と `Fatalf`**: コンパイラのエラー報告メカニズムです。`Yyerror` は警告や回復可能なエラーを報告し、`Fatalf` は致命的なエラーでコンパイルを中断します。

## 技術的詳細

このコミットの核となる変更は、Goコンパイラのインポート処理における状態管理とデータフローの簡素化です。

1.  **`push_parser` と `pop_parser` の統合と `unimportfile` のインライン化**:
    *   以前は、インポート処理を開始する際に `push_parser` を呼び出して現在のパーサーの状態を保存し、インポート処理が終了した後に `pop_parser` を呼び出して元の状態を復元していました。また、`unimportfile` がインポート処理後のクリーンアップを担当していました。
    *   このコミットでは、これらの機能を `parse_import` という単一の関数に統合しました。`parse_import` は、インポート処理に必要なパーサーの状態設定、エクスポートデータのパース、そして処理後の状態復元とクリーンアップ（`unimportfile` の内容を含む）をすべて内部で行います。これにより、インポート処理のライフサイクルが `parse_import` 関数内にカプセル化され、外部からの呼び出し側はよりシンプルになります。
    *   `src/cmd/compile/internal/gc/parser.go` の `push_parser` と `pop_parser` が削除され、`parse_import` が新設されています。

2.  **`import_package` の `parse_import` への移動と `import_there` のインライン化**:
    *   以前は、`importfile` が呼び出された後、`thenewparser.import_package()` と `thenewparser.import_there()` が個別に呼び出されていました。
    *   このコミットでは、`import_package` の呼び出しが `parse_import` 関数内に移動されました。さらに、`import_there` の内容も `import_package` 内にインライン化されています。
    *   これにより、`importfile` はインポート処理の開始点として機能し、実際のパースと状態管理は `parse_import` に一任される形になります。

3.  **フェイクインポートデータの廃止**:
    *   最も重要な改善点の一つは、`importfile` が「フェイクのインポートデータ」を生成して字句解析・パースさせる必要がなくなったことです。
    *   以前は、インポートが失敗した場合や、既にインポート済みのパッケージである場合でも、`fakeimport()` を呼び出してダミーのパッケージ宣言を字句解析器に供給していました。これは、字句解析器が常に有効な入力ストリームを期待するための一時的な回避策でした。
    *   この変更により、`importfile` は `importpkg` が非nilであるかどうかを直接チェックすることで、インポートの成功/失敗を判断できるようになりました。これにより、不要な字句解析とパースのオーバーヘッドが完全に排除され、コンパイル効率が向上します。`fakeimport()` 関数自体も削除されています。

4.  **診断メッセージの改善**:
    *   このリファクタリングは、`test/fixedbugs/issue11610.go` のような特定のケースで生成される診断メッセージにも影響を与えました。
    *   コミットメッセージによると、新しい診断は、空のインポート文がない場合に生成されるエラーメッセージとより一貫性があるとのことです。これは、パースロジックの簡素化と直接的なエラーチェックが、より正確で理解しやすいエラー報告に繋がったことを示唆しています。具体的には、`import ""` のような不正なインポートパスに対するエラーメッセージが改善されています。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/lex.go`

*   `loadsys()` 関数から `thenewparser.import_package()` と `thenewparser.import_there()` の呼び出しが削除されました。これは、これらの処理が `parse_import` 内に統合されたためです。
*   `fakeimport()` 関数が完全に削除されました。
*   `importfile()` 関数内で、`fakeimport()` の呼び出しが削除され、エラー処理がより直接的になりました。`importpkg` が既に設定されている場合のチェックが追加され、`Fatalf` でエラーを報告するようになりました。
*   `importfile()` 内の `cannedimports` の呼び出しから、ダミーのパッケージ宣言を生成するロジックが削除されました。
*   `importfile()` 内で、エクスポートデータの形式（古い形式の `\n` または新しい形式の `B`）を処理する部分が簡素化されました。特に、古い形式の処理において `push_parser()` が `parse_import()` に置き換えられ、`unimportfile()` に相当するクリーンアップロジックがインライン化されました。
*   `unimportfile()` 関数が完全に削除されました。
*   `cannedimports()` 関数内で、`push_parser()` が `parse_import()` に置き換えられ、`unimportfile()` に相当するクリーンアップロジックがインライン化されました。

### `src/cmd/compile/internal/gc/parser.go`

*   `thenewparser` と `savedstate` グローバル変数が削除され、`fileparser` が導入されました。これは、パーサーの状態管理がよりローカルなスコープで行われるようになったことを示唆しています。
*   `push_parser()` 関数と `pop_parser()` 関数が削除され、代わりに `parse_import()` 関数が新設されました。
*   `parse_import()` 関数は、インポート処理に必要なパーサーの初期化、`import_package()` の呼び出し、および状態の復元を行います。
*   `parse_file()` 関数は、`thenewparser` の代わりに `fileparser` を使用するように変更されました。
*   `importdcl()` 関数内で、インポートの成功/失敗のチェックが `p.tok != LPACKAGE` から `importpkg == nil` に変更されました。これにより、字句解析器の次のトークンに依存するのではなく、`importpkg` の状態を直接確認するようになりました。
*   `p.import_package()` と `p.import_there()` の呼び出しが `importdcl()` から削除されました。
*   `import_package()` 関数から、`incannedimport` のチェックと `importpkg.Direct` の設定ロジックが削除されました。`importpkg.Direct` は `importdcl` 内で直接設定されるようになりました。
*   `import_package()` 関数から、`safemode` と `importsafe` のチェックによるエラー報告ロジックが削除されました。このチェックは `lex.go` の `importfile` 内に移動されました。
*   `import_there()` 関数が完全に削除されました。

### `test/fixedbugs/issue11610.go`

*   このテストファイルは、不正なインポート文に対するコンパイラの診断メッセージをテストするためのものです。
*   コミットメッセージにあるように、このリファクタリングにより、`import ""` のような不正なインポートに対するエラーメッセージが変更されました。具体的には、`var?` に対するエラーが `ERROR "invalid declaration"` から `ERROR "unexpected ?"` に、`var x int` に対するエラーが `ERROR "unexpected var"` から `ERROR "unexpected var" "cannot declare name"` に変更されています。これは、パースロジックの変更がエラー報告の精度と一貫性を向上させた結果です。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラのインポート処理における状態管理の複雑さを軽減し、より直接的で効率的なメカニズムを導入した点にあります。

以前の設計では、インポート処理は以下のような流れでした。

1.  `importfile` が呼び出される。
2.  `push_parser` で現在のパーサーの状態を保存し、インポート用の新しいパーサー状態を設定。
3.  インポートされたパッケージのエクスポートデータを字句解析・パース。
4.  `import_package` でパッケージ情報を登録。
5.  `import_there` でインポートされた定義を処理。
6.  `pop_parser` で元のパーサーの状態を復元。
7.  `unimportfile` でリソースをクリーンアップ。

このプロセスには、`push_parser`/`pop_parser` のペアによる状態のプッシュ/ポップ、そしてインポート失敗時や既にインポート済みの場合に `fakeimport` を使ってダミーデータを供給するという間接的な処理が含まれていました。

新しい設計では、この流れが大幅に簡素化されました。

1.  `importfile` が呼び出される。
2.  `importfile` 内で、エクスポートデータの種類（古い形式または新しい形式）に応じて、`parse_import()` が直接呼び出されるか、`Import()` 関数（新しい形式のパース用）が呼び出されます。
3.  `parse_import()` 関数は、インポート処理に必要なパーサーの状態設定、エクスポートデータのパース、そして処理後の状態復元とクリーンアップをすべて内部で完結させます。これにより、`push_parser`、`pop_parser`、`unimportfile` といった個別の関数が不要になりました。
4.  `importpkg` が非nilであるかどうかを直接チェックすることで、インポートの成功/失敗を判断するようになり、`fakeimport` のような冗長なメカニズムが排除されました。

この変更により、インポート処理のロジックが `parse_import` 関数内に凝縮され、コードの局所性が高まりました。また、不要な字句解析・パースがなくなることで、コンパイル時のオーバーヘッドが削減され、パフォーマンスの向上が期待できます。さらに、エラー診断のロジックも簡素化された結果、より正確で一貫性のあるエラーメッセージが生成されるようになりました。

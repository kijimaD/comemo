# [インデックス 24954] ファイルの概要

このコミットは、Goコンパイラの内部パッケージ `src/cmd/compile/internal/gc/ssa.go` に関連する変更です。このファイルは、Goコンパイラのバックエンドの一部であり、ソースコードを中間表現であるSSA (Static Single Assignment) 形式に変換し、最適化を行う役割を担っています。具体的には、Go言語の型システムとSSA形式の操作を橋渡しするロジックが含まれています。

## コミット

このコミットは、Goコンパイラにおける複合型（`complex64`）の比較処理に関するバグを修正するものです。以前の実装では、`complex64`型の値を比較する際に、誤って64ビット浮動小数点数（`float64`）の比較演算が使用されていました。この修正により、`complex64`型には32ビット浮動小数点数（`float32`）の比較演算が正しく適用されるようになり、ビルドエラーが解消されました。

## 変更の背景

Go言語には、実数部と虚数部を持つ複合型（complex type）として `complex64` と `complex128` が存在します。`complex64` は実数部と虚数部がそれぞれ `float32` で構成され、`complex128` は `float64` で構成されます。

このコミットが行われる前は、GoコンパイラのSSAバックエンドにおいて、複合型の比較（例: `c1 == c2`）を処理する際に、`complex64`型の値に対しても誤って64ビット浮動小数点数（`float64`）の比較演算が適用されていました。これは、`complex64`の内部表現が32ビット浮動小数点数であるにもかかわらず、比較ロジックがその型情報を正しく伝達できていなかったためと考えられます。

結果として、型ミスマッチによる不正確な比較や、コンパイラのビルドプロセスにおけるエラーが発生していました。このバグは、特に`complex64`型を使用するコードのコンパイル時に問題を引き起こし、Goコンパイラ自体のビルドを妨げる可能性がありました。

## 前提知識の解説

### Go言語の複合型 (Complex Types in Go)

Go言語は、組み込み型として複合数（complex numbers）をサポートしています。
*   **`complex64`**: 実数部と虚数部がそれぞれ `float32` 型で構成されます。メモリ上では2つの `float32` 値として表現されます。
*   **`complex128`**: 実数部と虚数部がそれぞれ `float64` 型で構成されます。メモリ上では2つの `float64` 値として表現されます。

複合数の比較（`==` や `!=`）は、実数部と虚数部の両方が等しい場合に真となります。例えば、`c1 == c2` は `real(c1) == real(c2) && imag(c1) == imag(c2)` と同等です。

### SSA (Static Single Assignment)

SSA (Static Single Assignment) 形式は、コンパイラ最適化の分野で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、フロントエンドで生成された抽象構文木（AST）をSSA形式に変換し、様々な最適化（例: 共通部分式の削除、定数伝播、デッドコード削除など）を適用した後、最終的に機械語コードを生成します。

### Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、`cmd/compile` ディレクトリ以下に実装されています。その中でも `internal/gc` パッケージは、コンパイラの主要なロジック（字句解析、構文解析、型チェック、AST生成、SSA変換、コード生成など）を担う部分です。`ssa.go` ファイルは、ASTからSSA形式への変換、およびSSA形式上での操作に関連するコードを含んでいます。

### 浮動小数点数の比較 (Floating-point Comparisons)

浮動小数点数の比較は、整数型の比較とは異なり、精度に関する注意が必要です。`float32` と `float64` は異なる精度と範囲を持ちます。
*   **`float32`**: IEEE 754単精度浮動小数点数。約7桁の10進精度。
*   **`float64`**: IEEE 754倍精度浮動小数点数。約15-17桁の10進精度。

異なる精度の浮動小数点数を直接比較したり、一方の型で表現された値を別の型の比較演算子で処理したりすると、予期せぬ結果や精度誤差によるバグが発生する可能性があります。このコミットのケースでは、`complex64`（`float32`ベース）の比較に`float64`の比較演算が使われたことで、型システムが期待する動作と実際の動作が乖離し、ビルドエラーにつながりました。

## 技術的詳細

このバグは、`ssa.go` 内の `state.expr` メソッドで複合型の比較（`OEQ`、等価比較）を処理する部分に存在していました。

複合型の比較は、実数部と虚数部をそれぞれ比較し、両方が等しい場合に真を返します。この処理では、複合型の実数部と虚数部がどの浮動小数点型（`float32`または`float64`）であるかに応じて、適切な浮動小数点比較演算子を選択する必要があります。

問題のコードは以下の部分でした。

```go
			if n.Left.Type.IsComplex() {
				pt := floatForComplex(n.Type) // ここが問題
				op := s.ssaOp(OEQ, pt)
				r := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexReal, pt, a), s.newValue1(ssa.OpComplexImag, pt, b))
				i := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexImag, pt, a), s.newValue1(ssa.OpComplexImag, pt, b))
```

ここで、`floatForComplex` 関数は、複合型を受け取り、その実数部と虚数部を構成する浮動小数点型（`float32`または`float64`）を返すことを意図しています。しかし、誤って `n.Type` が引数として渡されていました。

*   `n` は比較演算子（例: `==`）を表すASTノードです。
*   `n.Type` は、この比較演算の結果の型、つまり `bool` 型を指します。
*   `n.Left` は比較演算子の左側のオペランド（複合型の値）を表すASTノードです。
*   `n.Left.Type` は、左側のオペランドの型、つまり `complex64` または `complex128` を指します。

したがって、`floatForComplex(n.Type)` は `bool` 型を引数として受け取ることになり、これは複合型ではありません。このため、`floatForComplex` はおそらくデフォルトの浮動小数点型（この場合は `float64`）を返してしまっていたと考えられます。結果として、`complex64` の比較であっても、`float64` の比較演算子（`ssa.OpEqF` など、64ビット浮動小数点数用）が生成され、これがビルドエラーの原因となっていました。

修正は、`floatForComplex` に渡す引数を `n.Type` から `n.Left.Type` に変更することで、比較対象の複合型の実際の型情報を正しく取得するようにしました。これにより、`complex64` の場合は `float32` が、`complex128` の場合は `float64` が `floatForComplex` から返されるようになり、適切なビット幅の浮動小数点比較演算子が選択されるようになりました。

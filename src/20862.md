## 変更の背景

このコミットの背景には、Go言語の`flag`パッケージにおけるコマンドラインフラグの処理に関する設計上の決定と、既存のシステムとの互換性の問題があります。

元々、Goの`flag`パッケージでは、同じコマンドラインフラグが複数回指定された場合、最後の値が有効になるという挙動が一般的でした。しかし、以前のコミット（ハッシュ`156390043`、コミットメッセージでは「flag setting」と簡潔に表現されています）では、この挙動が変更され、標準で提供されるフラグ（`bool`, `int`, `string`など）が複数回設定された場合にエラーを発生させるようになりました。これは、フラグの意図しない重複設定を防ぎ、より厳密なコマンドライン引数処理を促すための変更であったと考えられます。

しかし、この変更が導入された後、多くの既存のシェルスクリプトやビルドシステムが、フラグの複数回設定を許容する従来の挙動に依存していることが判明しました。例えば、特定のフラグをデフォルト値で設定しつつ、必要に応じて後から別の値で上書きするといったスクリプトの記述方法が一般的であった可能性があります。新しい挙動では、このようなスクリプトがエラーで終了してしまうため、広範な互換性問題が発生しました。

コミットメッセージにある「It's too late to make this change.」という記述は、この変更がGoのリリースサイクルにおいて、既に多くのユーザーが既存の挙動に依存している段階で導入されたため、後方互換性を破壊する影響が大きすぎると判断されたことを示唆しています。そのため、ユーザーベースへの影響を最小限に抑えるために、この変更をロールバックし、従来の複数回設定を許容する挙動に戻すことが決定されました。

## 前提知識の解説

### Go言語の`flag`パッケージ

Go言語の標準ライブラリである`flag`パッケージは、コマンドライン引数を解析し、プログラム内で利用するための機能を提供します。これにより、開発者は簡単にコマンドラインフラグを定義し、ユーザーがプログラムの挙動をカスタマイズできるようにします。

基本的な使い方としては、以下のようなステップを踏みます。
1.  `flag.Type("name", defaultValue, "usage string")` の形式でフラグを定義します。`Type`は`String`, `Int`, `Bool`などがあります。
2.  `flag.Parse()` を呼び出して、コマンドライン引数を解析します。
3.  定義したフラグのポインタから値を取得します。

例:
```go
package main

import (
	"flag"
	"fmt"
)

func main() {
	wordPtr := flag.String("word", "foo", "a string")
	numPtr := flag.Int("num", 42, "an int")
	boolPtr := flag.Bool("fork", false, "a bool")

	flag.Parse()

	fmt.Println("word:", *wordPtr)
	fmt.Println("num:", *numPtr)
	fmt.Println("fork:", *boolPtr)
	fmt.Println("args:", flag.Args()) // フラグ以外の引数
}
```
このプログラムを`go run main.go -word hello -num 100`のように実行すると、定義されたフラグが解析されます。

### コマンドラインフラグの複数回設定

コマンドラインフラグの複数回設定とは、同じフラグをコマンドライン上で複数回指定することです。例えば、`-v 1 -v 2`のように`-v`フラグを2回指定するケースです。

多くのコマンドラインパーサーでは、このような場合、通常は最後の値が有効になります。しかし、一部のアプリケーションやスクリプトでは、意図的にフラグを複数回指定し、その挙動に依存している場合があります。例えば、パスのリストを`-path /a -path /b`のように指定し、内部でリストとして処理するようなケースです。

以前のコミット`156390043`では、`flag`パッケージが提供する基本的な型（`bool`, `int`, `string`など）のフラグに対して、この複数回設定をエラーとして扱うように変更されました。これは、開発者がフラグの意図しない重複設定に気づきやすくするための意図があったと考えられます。しかし、`flag.Value`インターフェースを実装してカスタムフラグを定義した場合は、そのフラグが複数回設定された場合の挙動は実装者に委ねられていました。

## 技術的詳細

このコミットは、`src/flag/flag.go`と`src/flag/flag_test.go`の2つのファイルを変更しています。主な変更点は、`FlagSet`構造体から`set`マップフィールドの削除、およびフラグが既に設定されているかをチェックする`alreadySet`関数の削除です。

### `FlagSet`構造体からの`set`マップの削除

以前のコミットでは、`FlagSet`構造体に`set map[*Flag]bool`というフィールドが追加されていました。このマップは、各フラグが解析中に既に設定されたかどうかを追跡するために使用されていました。

```go
// 削除された部分 (src/flag/flag.go)
type FlagSet struct {
	// ...
	set           map[*Flag]bool // フラグが設定されたかどうかを追跡するマップ
	// ...
}
```

この`set`マップが削除されたことにより、`FlagSet`はフラグの複数回設定を追跡するメカニズムを失いました。

### `alreadySet`関数の削除

`alreadySet`関数は、特定のフラグが既に設定されているかどうかをチェックし、もし設定済みであれば`true`を返す役割を担っていました。この関数は、`flag`パッケージが提供する組み込みの型（`boolValue`, `intValue`など）のフラグに対してのみ、複数回設定を検出していました。カスタムの`Value`インターフェースを実装したフラグに対しては、常に`false`を返していました。

```go
// 削除された部分 (src/flag/flag.go)
// alreadySet reports whether the flag has already been set during parsing.
// Because user-defined flags may legally be set multiple times, it only
// complains about flags defined in this package.
func (f *FlagSet) alreadySet(flag *Flag) bool {
	if f.set == nil {
		f.set = make(map[*Flag]bool)
	}
	switch flag.Value.(type) {
	case *boolValue, *intValue, *int64Value, *uintValue, *uint64Value, *stringValue, *float64Value, *durationValue:
	default:
		return false // Not one of ours.
	}
	if f.set[flag] {
		return true
	}
	f.set[flag] = true
	return false
}
```

この関数が削除されたことで、`flag`パッケージは組み込みのフラグ型に対しても複数回設定のチェックを行わなくなりました。

### `parseOne`関数からの`alreadySet`呼び出しの削除

`FlagSet.parseOne`関数は、個々のコマンドライン引数を解析する際に、フラグが既に設定されていないかを`alreadySet`関数を使ってチェックしていました。

```go
// 削除された部分 (src/flag/flag.go)
// parseOne parses one flag. It reports whether a flag was seen.
func (f *FlagSet) parseOne() (bool, error) {
	// ...
	// has it already been set?
	if f.alreadySet(flag) {
		return false, f.failf("flag set multiple times: -%s", name)
	}
	// ...
}
```

このチェックが削除されたため、フラグが複数回設定されてもエラーにならず、最後の値が適用される従来の挙動に戻りました。

### テストコードの削除

`src/flag/flag_test.go`からは、`TestErrorOnMultipleSettings`というテスト関数が削除されました。このテストは、組み込みのフラグ型が複数回設定された場合にエラーを発生させることを検証していました。このテストの削除は、ロールバックされた変更が意図通りに機能しなくなったことを反映しています。

## コアとなるコードの解説

このコミットの核心は、Goの`flag`パッケージがコマンドラインフラグの複数回設定をどのように扱うかという挙動を元に戻すことです。

以前の変更では、`FlagSet`構造体に`set`という内部マップを導入し、`alreadySet`というヘルパー関数を使って、`bool`, `int`, `string`などの組み込み型のフラグがコマンドラインで複数回指定された場合にエラーを発生させていました。これは、開発者がフラグの重複設定による潜在的な問題を早期に発見できるようにするための、より厳密な解析挙動を目指したものでした。

しかし、この厳密な挙動は、既存の多くのシェルスクリプトや自動化ツールが、同じフラグを複数回指定して最後の値が有効になるという従来の「寛容な」挙動に依存していたため、後方互換性の問題を引き起こしました。例えば、スクリプトがデフォルト値を設定し、その後特定の条件下でその値を上書きするために同じフラグを再度指定するようなシナリオです。

このコミットでは、`set`マップと`alreadySet`関数、そしてそれらを使用していた関連ロジックをすべて削除することで、この厳密なチェックを完全に無効にしています。結果として、`flag`パッケージは再び、組み込み型のフラグであっても複数回設定を許容し、最後に指定された値が有効になるという従来の挙動に戻りました。

このロールバックは、技術的な「改善」よりも、既存のユーザーベースとエコシステムとの「互換性」を優先するというGoプロジェクトの現実的な判断を示しています。特に、シェルスクリプトのような広範に利用されるツールが依存している挙動を変更することは、大きな影響を伴うため、慎重な検討が必要であることが示されています。

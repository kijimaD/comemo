# [インデックス 21631] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるエスケープ解析の挙動を修正するものです。具体的には、生成されたラッパーが異なるパッケージで定義されたメソッドを呼び出し、その呼び出しがインライン化される際に発生する、ローカル変数の誤ったスタック割り当ての問題に対処しています。

変更されたファイルは以下の通りです。

*   `src/cmd/gc/go.h`: コンパイラのグローバル変数定義ファイル。新しいフラグが追加されています。
*   `src/cmd/gc/inl.c`: インライン化に関連する処理を行うファイル。エスケープ解析のロジックが修正されています。
*   `src/cmd/gc/subr.c`: サブルーチンやユーティリティ関数を含むファイル。ラッパー生成ロジックが修正されています。
*   `test/fixedbugs/issue9537.dir/a.go`: 問題を再現するためのテストケースの一部（パッケージ `a`）。
*   `test/fixedbugs/issue9537.dir/b.go`: 問題を再現するためのテストケースの一部（パッケージ `main`）。
*   `test/fixedbugs/issue9537.go`: テストの実行を指示するファイル。

## 変更の背景

このコミットは、Goコンパイラにおける「フェーズ順序問題」を解決するために導入されました。具体的には、Goコンパイラのエスケープ解析フェーズが、メソッドラッパーの生成フェーズよりも前に実行されるという問題がありました。

この順序の問題により、以下のようなシナリオで不具合が発生していました。

1.  コンパイラがインターフェースメソッド呼び出しなどのためにラッパー関数を生成する。
2.  この生成されたラッパーが、**異なるパッケージ**で定義されたメソッドを呼び出す。
3.  この異なるパッケージのメソッドへの呼び出しがコンパイラによって**インライン化**される。

この状況下では、インライン化された呼び出し内で定義された変数について、エスケープ解析の情報が利用できませんでした。その結果、本来ヒープに割り当てられるべき変数が誤ってスタックに割り当てられてしまい、プログラムの実行時に問題（例えば、変数が関数スコープを超えて参照され、不正なメモリアクセスを引き起こすなど）が発生する可能性がありました。

この問題はGoのIssue #9537として報告されており、このコミットはその問題を修正することを目的としています。

## 前提知識の解説

このコミットの理解には、Goコンパイラの以下の概念に関する知識が不可欠です。

### Goコンパイラのフェーズ

Goコンパイラは、ソースコードを機械語に変換する過程で複数の「フェーズ」（段階）を経ます。これらのフェーズには、字句解析、構文解析、型チェック、中間表現の生成、最適化（エスケープ解析、インライン化など）、コード生成などが含まれます。各フェーズは特定の順序で実行され、前のフェーズの結果が次のフェーズの入力となります。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、Goコンパイラの重要な最適化の一つです。これは、プログラム内の変数がどこにメモリ割り当てされるべきか（スタックかヒープか）を決定する静的解析です。

*   **スタック割り当て**: 関数内で宣言され、その関数の実行が終了すると不要になる変数は、通常スタックに割り当てられます。スタック割り当ては非常に高速で、ガベージコレクションの対象とならないため、GCの負荷を軽減します。
*   **ヒープ割り当て**: 変数がその宣言された関数のスコープを超えて「エスケープ」する場合（例: ポインタが関数から返される、グローバル変数に格納される、別のゴルーチンに渡されるなど）、その変数はヒープに割り当てられる必要があります。ヒープ割り当てされたオブジェクトはガベージコレクタによって管理されます。

エスケープ解析は、不必要なヒープ割り当てを減らし、プログラムのパフォーマンスを向上させることを目的としています。開発者は `go build -gcflags="-m"` コマンドを使用して、コンパイラがどの変数をエスケープさせたと判断したかを確認できます。

### インライン化 (Inlining)

インライン化もGoコンパイラの最適化の一つです。これは、小さな関数や頻繁に呼び出される関数の本体を、その関数が呼び出される箇所に直接埋め込む（インライン展開する）プロセスです。これにより、関数呼び出しのオーバーヘッド（スタックフレームのセットアップ、引数の渡し、戻り値の処理など）が削減され、プログラムの実行速度が向上します。

### ラッパー生成 (Wrapper Generation)

Goでは、インターフェースメソッドの呼び出しや、異なるパッケージ間でメソッドを呼び出す際に、コンパイラが「ラッパー」と呼ばれる補助的な関数を生成することがあります。これらのラッパーは、元のメソッド呼び出しを適切に処理するための橋渡し役として機能します。特に、インターフェースを介したメソッド呼び出しでは、実行時に正しい具体的なメソッドをディスパッチするためにラッパーが必要になることがあります。

### フェーズ順序問題 (Phase Ordering Problem)

コンパイラの最適化において、異なる最適化パス（フェーズ）を適用する順序が、最終的なコードの品質（パフォーマンス、サイズなど）に大きな影響を与えることがあります。ある最適化が別の最適化の前提条件を満たさなかったり、逆にその効果を打ち消してしまったりする場合に「フェーズ順序問題」が発生します。このコミットの背景にあるのは、エスケープ解析とラッパー生成のフェーズ順序が原因で発生した具体的な問題です。

## 技術的詳細

このコミットが対処する技術的な問題は、Goコンパイラの最適化フェーズの順序に起因します。

1.  **問題の核心**:
    *   Goコンパイラは、まずエスケープ解析を実行します。この段階で、変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを判断します。
    *   その後、ラッパーの生成が行われます。
    *   問題は、生成されたラッパーが**異なるパッケージ**で定義されたメソッドを呼び出し、その呼び出しが**インライン化**される場合に発生します。
    *   このインライン化されたコード内の変数については、エスケープ解析が既に完了しているため、適切なエスケープ情報がありません。
    *   結果として、これらの変数はデフォルトでスタックに割り当てられてしまいます。しかし、もしこれらの変数が実際には関数スコープを超えて「エスケープ」する必要がある場合（例: ポインタが返されるなど）、スタック割り当てでは不適切であり、実行時エラーや未定義の動作を引き起こす可能性があります。

2.  **解決策のアプローチ**:
    *   この問題に対する複雑な解決策は多数考えられますが、このコミットではよりシンプルで実用的なアプローチを採用しています。
    *   そのアプローチとは、「生成されたラッパーが異なるパッケージで定義されたメソッドを呼び出す場合、そのラッパー内で使用される**すべてのローカル変数**を強制的にエスケープさせる」というものです。
    *   これにより、エスケープ解析が不完全な状況でも、変数が安全にヒープに割り当てられることが保証され、誤ったスタック割り当てによる問題が回避されます。

この解決策は、`inl_nonlocal` という新しいフラグを導入し、ラッパー生成時にこのフラグを設定し、インライン化処理中にこのフラグを参照して変数のエスケープ挙動を制御することで実現されています。

## コアとなるコードの解説

### `src/cmd/gc/go.h` の変更

`go.h` はGoコンパイラのグローバルな定義や外部変数宣言を含むヘッダーファイルです。ここに `EXTERN int inl_nonlocal;` が追加されました。
*   `EXTERN`: この変数が他のファイルで定義されていることを示します。
*   `int inl_nonlocal;`: `inl_nonlocal` という名前の整数型変数を宣言しています。この変数は、現在処理中のインライン化が、異なるパッケージの関数（非ローカルな関数）に関連しているかどうかを示すフラグとして機能します。`0` はローカル、`1` は非ローカルを意味します。

このフラグの導入により、コンパイラの異なるフェーズ間で、インライン化のコンテキスト（特にパッケージの境界を越えるかどうか）を共有できるようになります。

### `src/cmd/gc/inl.c` の `inlvar` 関数の変更

`inlvar` 関数は、インライン化される関数内の個々の変数を処理する際に呼び出されます。この関数は、変数のエスケープ挙動を決定する重要な役割を担っています。

変更前のコードは `if(var->esc == EscHeap)` という条件で、変数が既にヒープエスケープするとマークされている場合に `addrescapes(n)` を呼び出していました。

変更後のコードは `if(var->esc == EscHeap || (inl_nonlocal && var->op == ONAME))` となっています。
*   `var->esc == EscHeap`: 従来のエスケープ解析の結果、変数がヒープにエスケープすると判断された場合。
*   `inl_nonlocal && var->op == ONAME`: 新しく追加された条件です。
    *   `inl_nonlocal`: 前述のグローバルフラグが `1`（非ローカルなインライン化コンテキスト）である場合。
    *   `var->op == ONAME`: `var` がローカル変数（`ONAME` は名前付きのオブジェクト、ここではローカル変数を指す）である場合。

この新しい条件が追加されたことで、生成されたラッパーが異なるパッケージのメソッドを呼び出し、その呼び出しがインライン化される際に、そのインライン化されたコード内の**すべてのローカル変数**が強制的にヒープにエスケープするとマークされるようになります。これにより、エスケープ解析が不完全な状況でも、変数が誤ってスタックに割り当てられることを防ぎ、安全性が確保されます。

### `src/cmd/gc/subr.c` の `genwrapper` 関数の変更

`genwrapper` 関数は、Goコンパイラがインターフェースメソッド呼び出しなどのためにラッパー関数を生成する際に使用されます。

追加されたコードは以下の通りです。
```c
	// Set inl_nonlocal to whether we are calling a method on a
	// type defined in a different package.  Checked in inlvar.
	if(!methodrcvr->local)
		inl_nonlocal = 1;

	inlcalls(fn);

	inl_nonlocal = 0;
```
*   `if(!methodrcvr->local) inl_nonlocal = 1;`:
    *   `methodrcvr`: ラッパーが呼び出すメソッドのレシーバーの型を表します。
    *   `!methodrcvr->local`: レシーバーの型が現在のパッケージで定義されていない（つまり、異なるパッケージで定義されている）場合に真となります。
    *   この条件が真の場合、`inl_nonlocal` フラグが `1` に設定されます。これは、これからインライン化される可能性のある呼び出しが、パッケージ境界を越えるものであることを `inlvar` 関数に伝えます。
*   `inlcalls(fn);`: この行は、ラッパー関数 `fn` 内の呼び出しをインライン化する処理を実行します。この処理中に、`inlvar` 関数が呼び出され、上記で設定された `inl_nonlocal` フラグが参照されます。
*   `inl_nonlocal = 0;`: `inlcalls` の実行後、`inl_nonlocal` フラグは `0` にリセットされます。これは、このフラグの設定が現在のラッパーのインライン化にのみ適用される一時的なものであることを保証し、他のコンパイル処理に影響を与えないようにするためです。

これらの変更により、コンパイラはラッパー生成時に、インライン化される可能性のある非ローカルな呼び出しを検出し、それに応じてエスケープ解析の挙動を調整できるようになりました。

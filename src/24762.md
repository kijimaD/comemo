## 元コミット内容

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、チャネル型に対する組み込み関数 `len()` および `cap()` の実装を追加します。以前は、これらの操作がSSA変換フェーズで処理されておらず、未実装エラー（`Unimplementedf`）が発生していました。この変更により、`len(chan)` と `cap(chan)` がSSA形式で正しく表現され、コンパイル時に適切なコードが生成されるようになります。具体的には、マップ型とチャネル型で共通の処理を行う `referenceTypeBuiltin` という新しいヘルパー関数が導入され、`nil` の場合は0を返し、非`nil` の場合はチャネルの内部構造から長さや容量を読み出すロジックが追加されています。

## 変更の背景

Goコンパイラは、パフォーマンスと最適化を向上させるために、2015年頃からSSA (Static Single Assignment) 形式への移行を進めていました。SSAは、変数の定義と使用を明確にし、より高度な最適化を可能にする中間表現です。この移行プロセスにおいて、既存のGo言語の機能（組み込み関数など）をSSA形式で表現し直す作業が必要でした。

`len()` と `cap()` はGo言語の基本的な組み込み関数であり、スライス、マップ、チャネルなどのデータ構造の長さや容量を取得するために広く使用されます。SSAバックエンドが導入される前は、これらの関数はコンパイラの別のフェーズで処理されていましたが、SSAバックエンドが主要なコード生成パスとなるにつれて、SSA形式でこれらの操作をサポートすることが不可欠となりました。

特にチャネルの場合、`len(chan)` はチャネルバッファ内の現在キューに入っている要素の数を返し、`cap(chan)` はチャネルバッファの総容量を返します。これらの情報はGoの並行処理モデルにおいて重要であり、SSAバックエンドがこれらを正しく扱えないことは、コンパイラの機能的なギャップとなっていました。このコミットは、そのギャップを埋め、SSAバックエンドの完成度を高めることを目的としています。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のフェーズを経ます。SSAは、その中間表現（IR: Intermediate Representation）の一つです。
*   **SSAの特性**: SSA形式では、各変数が一度だけ代入（定義）されます。これにより、データフロー解析が容易になり、コンパイラはより効果的な最適化（例: 共通部分式除去、デッドコード除去、レジスタ割り当ての改善）を実行できます。
*   **GoコンパイラにおけるSSA**: Go 1.7（2016年）でSSAバックエンドがデフォルトで有効になるまで、Goコンパイラは主にAST (Abstract Syntax Tree) をベースとしたコード生成を行っていました。このコミットが行われた2015年は、SSAバックエンドの開発が活発に行われていた時期にあたります。`[dev.ssa]` というプレフィックスは、このコミットがSSA開発ブランチの一部であることを示しています。

### 2. Goチャネルの内部構造 (`hchan` 構造体)

Goのチャネルは、ランタイム内部では `runtime.hchan` という構造体で表現されます。この構造体には、チャネルのバッファ、送受信キュー、ロックなどの情報が含まれています。`len()` と `cap()` がチャネルの内部状態にアクセスするため、`hchan` 構造体の理解が不可欠です。

`hchan` 構造体（Goのバージョンによって多少異なる場合がありますが、基本的な概念は同じです）の簡略化された定義は以下のようになります。

```go
type hchan struct {
    qcount   uint           // total data in the queue
    dataqsiz uint           // size of the circular queue
    buf      unsafe.Pointer // points to an array of dataqsiz elements
    elemsize uint16
    closed   uint32
    elemtype *_type // element type
    sendx    uint   // send index
    recvx    uint   // receive index
    recvq    waitq  // list of recv waiters
    sendq    waitq  // list of send waiters
    lock     mutex
}
```

*   `qcount`: 現在チャネルバッファにキューイングされている要素の数。これが `len(chan)` の値になります。
*   `dataqsiz`: チャネルバッファの総容量。これが `cap(chan)` の値になります。
*   `buf`: バッファリングされたチャネルの場合、実際のデータが格納されるメモリ領域へのポインタ。

このコミットのロジックでは、`len` はチャネル構造体の先頭ワード（`qcount`）から、`cap` はその次のワード（`dataqsiz`）から読み取られることが示唆されています。これは、`hchan` 構造体のメモリレイアウトに直接アクセスしていることを意味します。

### 3. `len()` と `cap()` 組み込み関数

*   **`len(v)`**: `v` の長さ（要素数）を返します。
    *   配列: 配列の要素数
    *   ポインタ配列: ポインタが指す配列の要素数
    *   スライス: スライスの要素数
    *   マップ: マップ内のキーと値のペアの数
    *   チャネル: チャネルバッファ内のキューに入っている要素の数
*   **`cap(v)`**: `v` の容量を返します。
    *   配列: 配列の要素数
    *   ポインタ配列: ポインタが指す配列の要素数
    *   スライス: スライスの最大容量
    *   チャネル: チャネルバッファの総容量

`len()` と `cap()` はコンパイル時に特別な処理が行われる組み込み関数であり、通常の関数呼び出しとは異なり、コンパイラが直接そのセマンティクスを理解し、適切なコードを生成します。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが `len(chan)` と `cap(chan)` をどのようにSSA値に変換するかという点にあります。

1.  **`expr` メソッドの変更**:
    `src/cmd/compile/internal/gc/ssa.go` 内の `(s *state) expr(n *Node) *ssa.Value` メソッドは、ASTノード `n` をSSA値に変換する主要な関数です。以前は、`n.Left.Type.IsChan()` のケースで `Unimplementedf` が呼び出され、チャネルに対する `len`/`cap` が未サポートであることを示していました。
    この変更により、`n.Left.Type.IsMap()` と `n.Left.Type.IsChan()` の両方が新しいヘルパー関数 `s.referenceTypeBuiltin(n, s.expr(n.Left))` を呼び出すように統合されました。これは、マップとチャネルがどちらも参照型であり、`len` の取得方法に共通点があるためです。

2.  **`referenceTypeBuiltin` ヘルパー関数の導入**:
    新しく追加された `(s *state) referenceTypeBuiltin(n *Node, x *ssa.Value) *ssa.Value` 関数が、マップとチャネルの `len`/`cap` 処理をカプセル化します。
    *   **`nil` チェック**: まず、入力されたチャネルまたはマップが `nil` であるかどうかをチェックします。`nil` の場合、`len` も `cap` も `0` であるため、`ssa.OpConstNil` と比較し、条件分岐（`ssa.OpEqPtr`）を生成して `0` を返します。これは、`nil` チャネルや `nil` マップに対する `len`/`cap` がパニックを起こさずに `0` を返すというGo言語の仕様に準拠しています。
    *   **非`nil` の場合**:
        *   **`len()` (OLEN)**: `n.Op == OLEN` の場合、チャネルまたはマップの基盤となるデータ構造の**最初のワード**を読み込みます。これは、`hchan` 構造体の `qcount` フィールド（チャネルの現在の要素数）またはマップの内部構造における要素数に相当します。SSAオペレーション `ssa.OpLoad` を使用して、ポインタ `x` が指すアドレスから値をロードします。
        *   **`cap()` (OCAP)**: `n.Op == OCAP` の場合、チャネルの基盤となるデータ構造の**2番目のワード**を読み込みます。これは、`hchan` 構造体の `dataqsiz` フィールド（チャネルの総容量）に相当します。`ssa.OpOffPtr` を使用して、ポインタ `x` から `lenType.Width` (通常はポインタサイズ、つまり1ワード分) オフセットしたアドレスを計算し、そのアドレスから `ssa.OpLoad` で値をロードします。マップには `cap()` が存在しないため、このパスはチャネル専用です。
    *   **エラーハンドリング**: `n.Op` が `OLEN` でも `OCAP` でもない場合は `Fatalf` を呼び出し、不正な操作であることを示します。

この実装は、Goランタイムがチャネルの長さと容量を `hchan` 構造体の連続したメモリ位置に格納しているという事実に基づいています。コンパイラは、これらのフィールドに直接アクセスすることで、効率的に `len` と `cap` の値を抽出します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

1.  **`expr` メソッドの変更**:
    *   以前は `n.Left.Type.IsMap()` と `n.Left.Type.IsChan()` が別々の `case` ブロックで処理され、チャネルの場合は `Unimplementedf` で未実装エラーを報告していました。
    *   変更後、両方の型が `case n.Left.Type.IsMap(), n.Left.Type.IsChan():` という単一のブロックに統合され、`s.referenceTypeBuiltin(n, s.expr(n.Left))` を呼び出すようになりました。これは、マップとチャネルの `len` 取得ロジックに共通点があり、チャネルの `cap` も同様のメモリレイアウトを利用できるため、コードの再利用性を高める設計です。

2.  **`lenMap` 関数の削除と `referenceTypeBuiltin` 関数の追加**:
    *   既存の `lenMap` 関数は削除され、より汎用的な `referenceTypeBuiltin` 関数に置き換えられました。
    *   `referenceTypeBuiltin` 関数は、`n` がマップまたはチャネルであることを確認する `s.Fatalf` を追加し、不正な呼び出しを早期に検出します。
    *   **`nil` チェックロジック**:
        *   `nilValue := s.newValue0(ssa.OpConstNil, Types[TUINTPTR])` で `nil` ポインタのSSA値を生成します。
        *   `s.newValue2(ssa.OpEqPtr, Types[TBOOL], x, nilValue)` で、入力されたチャネル/マップのSSA値 `x` が `nil` と等しいかを比較し、その結果に基づいて条件分岐（`ssa.OpIf`）を生成します。
        *   `nil` の場合は `s.zeroVal(lenType)` (つまり `0`) を結果として設定します。
    *   **非`nil` の場合のロジック**:
        *   `n.Op == OLEN` (len操作) の場合:
            *   `s.vars[n] = s.newValue2(ssa.OpLoad, lenType, x, s.mem())` を使用して、チャネル/マップのポインタ `x` が指すアドレスから直接値をロードします。これは、`hchan` 構造体の `qcount` フィールド（チャネルの長さ）またはマップの長さが、構造体の先頭に配置されていることを前提としています。
        *   `n.Op == OCAP` (cap操作) の場合:
            *   `sw := s.newValue1I(ssa.OpOffPtr, lenType.PtrTo(), lenType.Width, x)`: `ssa.OpOffPtr` は、ポインタ `x` から指定されたオフセット（`lenType.Width`、つまり1ワードのサイズ）だけずらした新しいポインタを生成します。`lenType.Width` は通常、`int` 型のサイズ（32ビットシステムで4バイト、64ビットシステムで8バイト）に相当します。
            *   `s.vars[n] = s.newValue2(ssa.OpLoad, lenType, sw, s.mem())`: オフセットされたポインタ `sw` が指すアドレスから値をロードします。これは、`hchan` 構造体の `dataqsiz` フィールド（チャネルの容量）が `qcount` フィールドの直後に配置されていることを前提としています。
        *   `else` ブロックで `s.Fatalf` を呼び出し、`OLEN` または `OCAP` 以外の操作が来た場合にエラーとします。

### `src/cmd/compile/internal/gc/testdata/chan_ssa.go` の新規追加

# [インデックス 25017] ファイルの概要

このコミットは、Go言語のパーサーにおける構造体フィールドリストおよびパラメータリストの末尾のカンマに関する挙動を修正するものです。具体的には、Go言語の仕様では構造体フィールドの宣言や関数のパラメータリストの末尾にカンマを置くことは許可されていませんが、以前のパーサーはこれを誤って許容してしまうケースがありました。このコミットは、パーサーのロジックを修正し、Go言語の仕様に厳密に準拠するように変更することで、不正な構文に対して適切なエラーを報告するように改善しています。

## コミット

`go/parser: comma is not permitted at the end of a struct field list`

このコミットは、Go言語のパーサーが構造体フィールドリストの末尾にカンマを許可しないように修正します。

## 変更の背景

この変更の背景には、Go言語のパーサーが言語仕様に準拠していない挙動を示していたという問題があります。具体的には、Go言語の文法では、構造体のフィールド宣言や関数のパラメータ宣言において、リストの末尾にカンマを置くことは許可されていません。しかし、以前の`go/parser`パッケージは、このような不正な構文をエラーとせずに受け入れてしまうことがありました。

Issue #11611（"go/parser: comma is not permitted at the end of a struct field list"）で報告されたこの問題は、Goコードの構文解析の厳密性を損なうものでした。パーサーが仕様と異なる挙動をすると、開発者が意図しないコードを記述してしまったり、ツールがGoコードを正しく理解できなかったりする可能性があります。このコミットは、この不整合を解消し、パーサーがGo言語の正式な文法規則を正確に強制するようにするために導入されました。これにより、より堅牢で予測可能なGo開発環境が提供されます。

## 前提知識の解説

### Go言語のパーサー (`go/parser`パッケージ)

`go/parser`パッケージは、Go言語のソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を生成するための標準ライブラリです。ASTは、プログラムの構造を木構造で表現したもので、コンパイラ、リンター、コードフォーマッターなどのツールがGoコードを理解し、操作するために利用されます。パーサーは、字句解析器（lexer）から受け取ったトークン列を文法規則に従って解析し、ASTを構築します。

### 抽象構文木 (AST)

ASTは、ソースコードの構文構造を抽象的に表現したデータ構造です。例えば、`ast.Field`は構造体のフィールドや関数のパラメータを表し、`ast.Expr`は式を表します。パーサーは、これらのASTノードを組み合わせてプログラム全体の構造を表現します。

### Go言語の文法規則（構造体フィールドとパラメータリスト）

Go言語の文法では、構造体型（`struct`）のフィールド宣言や関数のパラメータリストには特定の規則があります。

*   **構造体フィールド宣言**:
    構造体フィールドは、識別子（フィールド名）と型、オプションでタグから構成されます。複数のフィールドをカンマで区切って宣言できますが、リストの末尾にカンマを置くことはできません。
    例:
    ```go
    type MyStruct struct {
        Field1 int
        Field2 string // OK
        // Field3 float, // NG: 末尾のカンマは不可
    }
    ```
    匿名フィールド（型名のみのフィールド）も同様です。
    ```go
    type MyStruct struct {
        int
        string // OK
        // float, // NG: 末尾のカンマは不可
    }
    ```

*   **関数パラメータリスト**:
    関数のパラメータも、識別子と型から構成されます。複数のパラメータをカンマで区切って宣言できますが、リストの末尾にカンマを置くことはできません。
    例:
    ```go
    func MyFunc(param1 int, param2 string) { // OK
    // func MyFunc(param1 int, param2 string,) { // NG: 末尾のカンマは不可
    }
    ```

### `token.COMMA`と`token.RPAREN`

`token`パッケージは、Go言語の字句解析器が生成するトークン（語彙要素）を定義しています。
*   `token.COMMA`: カンマ `,` を表すトークンです。
*   `token.RPAREN`: 右括弧 `)` を表すトークンです。

パーサーはこれらのトークンを読み取り、文法規則に従って構文木を構築します。

## 技術的詳細

このコミットの技術的な核心は、`go/parser`パッケージ内の`parseFieldDecl`関数と`parseParameterList`関数のロジック変更にあります。これらの関数は、それぞれ構造体フィールドと関数パラメータの宣言を解析する役割を担っています。

以前の実装では、`parseVarList`というヘルパー関数が使用されていました。この`parseVarList`は、識別子のリストと型のリストの両方を柔軟に解析するように設計されており、その柔軟性が構造体フィールドやパラメータリストの末尾カンマを誤って許容してしまう原因となっていました。特に、`parseVarList`はカンマの後に`tryVarType`を呼び出し、これが`nil`を返す場合でもリストの解析を継続してしまう可能性がありました。

新しい実装では、`parseVarList`関数が削除され、そのロジックが`parseFieldDecl`と`parseParameterList`に直接組み込まれました。これにより、各コンテキストに特化した厳密な解析が可能になります。

### `parseFieldDecl`の変更点

1.  **フィールドリストの解析**:
    以前は`list, typ := p.parseVarList(false)`でフィールドリストと型をまとめて解析していました。
    新しいコードでは、`for`ループを使って`p.parseVarType(false)`を繰り返し呼び出し、個々のフィールドの式（`ast.Expr`）を`list`に追加します。このループは、現在のトークンが`token.COMMA`である限り継続し、カンマの後に次のフィールドを解析します。カンマがない場合はループを抜けます。
    ```go
    // 1st FieldDecl
    // A type name used as an anonymous field looks like a field identifier.
    var list []ast.Expr
    for {
        list = append(list, p.parseVarType(false))
        if p.tok != token.COMMA {
            break
        }
        p.next()
    }
    typ := p.tryVarType(false) // フィールドの型を明示的に取得
    ```
    この変更により、カンマの後に続くべき要素がない場合に、ループが適切に終了し、不正な末尾カンマを検出できるようになります。

2.  **匿名フィールドの解析とエラーハンドリングの改善**:
    構造体フィールドが匿名フィールドである場合（つまり、フィールド名がなく型のみが宣言されている場合）、そのフィールドは単一の型名である必要があります。
    以前のコードでは、`if n := len(list); n > 1 || !isTypeName(deref(typ))`という条件でエラーをチェックしていました。
    新しいコードでは、エラーチェックがより詳細になりました。
    *   `if n := len(list); n > 1`: 複数の式が解析された場合、それは匿名フィールドとしては不正であるため、`"type"`が期待されるというエラーを報告します。
    *   `else if !isTypeName(deref(typ))`: 単一の式が解析された場合でも、それが型名でない場合は`"anonymous field"`が期待されるというエラーを報告します。
    これにより、エラーメッセージがより具体的になり、開発者が問題を特定しやすくなります。

3.  **タグの解析順序**:
    フィールドタグ（例: `` `json:"name"` ``）の解析ロジックが、フィールドの型解析後に移動されました。これは論理的な順序であり、コードの可読性と保守性を向上させます。

### `parseParameterList`の変更点

`parseFieldDecl`と同様に、`parseParameterList`も`parseVarList`への依存を排除し、パラメータリストの解析ロジックを直接組み込みました。

1.  **パラメータリストの解析**:
    `for`ループを使用して`p.parseVarType(ellipsisOk)`を繰り返し呼び出し、個々のパラメータの式を`list`に追加します。ループは、現在のトークンが`token.COMMA`である限り継続します。
    さらに、`if p.tok == token.RPAREN { break }`という条件が追加され、右括弧 `)` が来た場合もループを終了するようにしました。これにより、パラメータリストの末尾カンマの後に右括弧が続くような不正な構文を正確に検出できるようになります。
    ```go
    // 1st ParameterDecl
    // A list of identifiers looks like a list of type names.
    var list []ast.Expr
    for {
        list = append(list, p.parseVarType(ellipsisOk))
        if p.tok != token.COMMA {
            break
        }
        p.next()
        if p.tok == token.RPAREN { // 追加された条件
            break
        }
    }
    if typ := p.tryVarType(ellipsisOk); typ != nil { // パラメータの型を明示的に取得
        // ...
    }
    ```
    この変更により、関数シグネチャのパラメータリストにおける末尾カンマの誤った許容が修正されます。

### `short_test.go`の変更点

テストファイル`src/go/parser/short_test.go`には、新しい無効な構文のテストケースが追加されました。これらは、パーサーが修正された挙動を正しく示すことを保証します。

*   `package p; type _ struct { int, } /* ERROR "expected type, found '}'" */ ;`
*   `package p; type _ struct { int, float } /* ERROR "expected type, found '}'" */ ;`
    これら2つのテストケースは、構造体フィールドリストの末尾にカンマがある場合に、パーサーが`expected type, found '}'`というエラーを正しく報告することを確認します。これは、カンマの後に続くべき型宣言がないため、パーサーが`}`を予期しない場所で検出したことを意味します。

*   `package p; type _ struct { ( /* ERROR "expected anonymous field" */ int) };`
    このテストは、匿名フィールドが括弧で囲まれた型である場合に、`expected anonymous field`というエラーを報告することを確認します。Go言語の匿名フィールドは型名そのものであり、括弧で囲むことはできません。

*   `package p; func _()(x, y, z ... /* ERROR "expected ')'" */ int){}`
*   `package p; func _()(... /* ERROR "expected type, found '...'" */ int){}`
    これら2つのテストケースは、関数パラメータリストにおける不正な`...`（可変長引数）の使用や、末尾カンマに関連するエラーを検出することを確認します。特に、`expected ')'`はパラメータリストの末尾にカンマがある場合に、パーサーが`(`を閉じる`)`を期待していることを示唆しています。

これらのテストケースの追加により、パーサーの修正が意図した通りに機能し、Go言語の文法規則に厳密に準拠していることが検証されます。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更点

#### `parseFieldDecl` 関数

この関数は構造体のフィールド宣言を解析します。

**変更前**:
```go
	// FieldDecl
	list, typ := p.parseVarList(false)

	// Tag
	var tag *ast.BasicLit
	if p.tok == token.STRING {
		tag = &ast.BasicLit{ValuePos: p.pos, Kind: p.tok, Value: p.lit}
		p.next()
	}
```
`p.parseVarList(false)`は、識別子のリストと型を柔軟に解析する汎用的な関数でした。この柔軟性が、構造体フィールドの末尾カンマを誤って許容する原因となっていました。また、タグの解析がフィールドリストと型解析の間にありました。

**変更後**:
```go
	// 1st FieldDecl
	// A type name used as an anonymous field looks like a field identifier.
	var list []ast.Expr
	for {
		list = append(list, p.parseVarType(false))
		if p.tok != token.COMMA {
			break
		}
		p.next()
	}

	typ := p.tryVarType(false)

	// analyze case
	// ... (エラーハンドリングの改善) ...

	// Tag
	var tag *ast.BasicLit
	if p.tok == token.STRING {
		tag = &ast.BasicLit{ValuePos: p.pos, Kind: p.tok, Value: p.lit}
		p.next()
	}
```
1.  **フィールドリストの直接解析**: `parseVarList`の呼び出しを削除し、`for`ループ内で`p.parseVarType(false)`を直接呼び出すことで、フィールドの式（`ast.Expr`）を一つずつ解析するように変更されました。
2.  **カンマの厳密なチェック**: ループは`p.tok != token.COMMA`が真になるまで、つまりカンマが続く限り継続します。カンマがなければループを抜け、これにより末尾カンマを検出できるようになります。
3.  **型の明示的な取得**: `typ := p.tryVarType(false)`がループの後に呼び出され、フィールドの型を明示的に取得します。
4.  **エラーハンドリングの改善**: 匿名フィールドの解析において、`n > 1`（複数の式が解析された場合）と`!isTypeName(deref(typ))`（単一の式が型名でない場合）を個別にチェックすることで、より正確なエラーメッセージを生成します。
5.  **タグ解析の移動**: フィールドタグの解析が、フィールドの型解析とエラー分析の後に移動され、論理的な順序になりました。

#### `parseVarList` 関数の削除

この関数は、識別子のリストと型を解析するための汎用的なヘルパー関数でしたが、その柔軟性が問題を引き起こしていたため、完全に削除されました。そのロジックは、必要に応じて`parseFieldDecl`や`parseParameterList`に直接組み込まれる形になりました。

#### `parseParameterList` 関数

この関数は関数のパラメータリストを解析します。

**変更前**:
```go
	// ParameterDecl
	list, typ := p.parseVarList(ellipsisOk)
```
ここでも`p.parseVarList`が使用されており、パラメータリストの末尾カンマを誤って許容する可能性がありました。

**変更後**:
```go

	// A list of identifiers looks like a list of type names.
	var list []ast.Expr
	for {
		list = append(list, p.parseVarType(ellipsisOk))
		if p.tok != token.COMMA {
			break
		}
		p.next()
		if p.tok == token.RPAREN { // 追加された条件
			break
		}
	}

	// analyze case
	if typ := p.tryVarType(ellipsisOk); typ != nil {
		// ...
	}
```
1.  **パラメータリストの直接解析**: `parseFieldDecl`と同様に、`for`ループ内で`p.parseVarType(ellipsisOk)`を直接呼び出し、パラメータの式を一つずつ解析します。
2.  **カンマと右括弧の厳密なチェック**: ループは`p.tok != token.COMMA`が真になるまで継続します。さらに、`if p.tok == token.RPAREN { break }`という条件が追加され、パラメータリストの末尾カンマの後に右括弧が続くような不正な構文を検出できるようになりました。これにより、`func f(int,)`のような不正な構文がエラーとして扱われます。
3.  **型の明示的な取得**: `if typ := p.tryVarType(ellipsisOk); typ != nil`という形で、パラメータの型を明示的に取得し、その後の分析に利用します。

### `src/go/parser/short_test.go` の変更点

このファイルには、Goパーサーの挙動を検証するための短い無効なコードスニペットが含まれています。

**追加されたテストケース**:
`// issue 11611`というコメントの下に、以下のテストケースが追加されました。

*   `` `package p; type _ struct { int, } /* ERROR "expected type, found '}'" */ ;` ``
    構造体フィールド宣言で、`int`の後にカンマがあり、その後に何も続かずに`}`で閉じられているケース。Goの文法では不正であり、パーサーは`expected type, found '}'`というエラーを報告するべきです。

*   `` `package p; type _ struct { int, float } /* ERROR "expected type, found '}'" */ ;` ``
    複数の匿名フィールドの後にカンマがあり、その後に何も続かずに`}`で閉じられているケース。これも不正であり、同様のエラーが期待されます。

*   `` `package p; type _ struct { ( /* ERROR "expected anonymous field" */ int) };` ``
    匿名フィールドが括弧で囲まれた型として宣言されているケース。Goの文法では匿名フィールドは型名そのものであり、括弧で囲むことはできないため、`expected anonymous field`というエラーが期待されます。

*   `` `package p; func _()(x, y, z ... /* ERROR "expected ')'" */ int){}` ``
    関数パラメータリストで、可変長引数`...`が不正な位置にあるケース。パーサーは`expected ')'`というエラーを報告するべきです。

*   `` `package p; func _()(... /* ERROR "expected type, found '...'" */ int){}` ``
    関数パラメータリストが`...`で始まっている不正なケース。パーサーは`expected type, found '...'`というエラーを報告するべきです。

これらのテストケースは、パーサーの修正がGo言語の文法規則に厳密に準拠し、不正な構文に対して適切なエラーを報告することを保証するために不可欠です。

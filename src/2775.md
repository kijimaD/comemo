## 変更の背景

Go言語のリンカ`6l`は、Goプログラムを64ビットアーキテクチャ向けに実行可能なELF形式のバイナリに変換する役割を担っています。ELFファイルは、プログラムの実行に必要な様々な情報（コード、データ、シンボルテーブル、動的リンク情報など）を構造化して格納します。

このコミットが行われた2009年当時、Go言語はまだ開発の初期段階にあり、ツールチェイン（コンパイラ、リンカなど）も活発に改善されていました。特にリンカは、生成されるバイナリの構造、効率性、そしてOSとの互換性を保証する上で非常に重要なコンポーネントです。

この「a little more 6l cleanup」というコミットメッセージは、以前から行われていたリンカのコードベースの整理・改善作業の一環であることを示唆しています。ELFファイルの構造は複雑であり、特に動的リンクをサポートする場合、プログラムヘッダとセクションヘッダの整合性を正確に保つ必要があります。初期の実装では、試行錯誤や機能追加の過程で冗長なコードや最適ではないロジックが導入されることがあります。

このコミットの背景には、ELFファイルの動的リンク関連情報の生成ロジックをより明確にし、冗長性を排除し、保守性を向上させるという目的があったと考えられます。これにより、生成されるバイナリの正確性が向上し、リンカ自体のコードも理解しやすくなります。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系OS（Linuxなど）で実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプなどを表現するために使用される標準的なファイル形式です。主要なコンポーネントは以下の通りです。

*   **ELFヘッダ (ELF Header)**: ファイルの先頭に位置し、ELFファイルのタイプ（実行可能ファイル、共有ライブラリなど）、ターゲットアーキテクチャ、エントリポイントアドレスなどの基本的な情報を含みます。
*   **プログラムヘッダテーブル (Program Header Table)**: プログラムの実行に必要な情報を記述します。各エントリ（プログラムヘッダ）は、メモリセグメント（例: コード、データ）のロード方法、アクセス権限などを定義します。OSのローダーはこのテーブルを読み込み、プログラムをメモリにマッピングします。
    *   **PT_LOAD**: メモリにロードされるセグメントを記述します。ファイル内のオフセット、メモリ上の仮想アドレス、サイズ、アクセス権限などが含まれます。
    *   **PT_INTERP**: プログラムインタープリタ（動的リンカ）のパスを指定します。動的リンクされたプログラムが実行される際に、OSはこのパスにあるインタープリタをロードして実行します。
    *   **PT_DYNAMIC**: 動的リンクに必要な情報（共有ライブラリの依存関係、シンボルテーブル、文字列テーブルなど）が格納されている`.dynamic`セクションの場所を指します。
*   **セクションヘッダテーブル (Section Header Table)**: リンク時に必要な情報を記述します。各エントリ（セクションヘッダ）は、ファイル内のセクション（例: `.text`、`.data`、`.symtab`）の名前、タイプ、サイズ、ファイルオフセットなどを定義します。デバッグ情報やシンボル情報など、実行時には直接必要ないが、リンカやデバッガが利用する情報が含まれます。
    *   **.interp**: プログラムインタープリタのパスを含む文字列を格納します。
    *   **.hash**: 動的シンボル検索を高速化するためのハッシュテーブルです。
    *   **.dynsym**: 動的リンクに必要なシンボル（関数や変数）の情報を格納するシンボルテーブルです。
    *   **.dynstr**: `.dynsym`で参照されるシンボル名などの文字列を格納する文字列テーブルです。
    *   **.dynamic**: 動的リンカが実行時に必要とするタグ付き情報（DT_HASH, DT_STRTAB, DT_SYMTABなど）のリストを格納します。

### Goリンカ (6l)

`6l`は、Go言語のツールチェインの一部であり、Goのソースコードから生成されたオブジェクトファイルをリンクして、最終的な実行可能ファイルを生成するリンカです。Goのリンカは、C言語のリンカとは異なり、ガベージコレクションやgoroutineスケジューラなどのGoランタイムをバイナリに組み込む役割も持っています。また、Goのバイナリは通常、静的リンクされることが多いですが、動的リンクのサポートも行われます。

## 技術的詳細

このコミットは、`src/cmd/6l/asm.c`ファイル内の`asmb`関数におけるELFファイルの生成ロジック、特に動的リンクに関連する部分を対象としています。変更の核心は、ELFのセクションヘッダとプログラムヘッダの生成方法の簡素化と正確性の向上にあります。

具体的には、以下の点が改善されています。

1.  **`dynsh`変数の削除**: 以前は`.dynamic`セクションのセクションヘッダを一時的に保持するために`dynsh`という`Elf64SHdr`型の変数が使われていましたが、これが削除されました。代わりに、`.dynamic`セクションのセクションヘッダも他のセクションヘッダと同様に、その場で`sh`変数に割り当てて処理するように変更されています。これにより、コードの冗長性が減り、`.dynamic`セクションの処理が他のセクションと統一された方法で行われるようになりました。

2.  **セクションヘッダのオフセットとアドレス計算の簡素化**:
    *   `.hash`セクションの`sh->off`が`seek(cout, 0, 1)`（現在のファイルオフセット）から`startelf()`に変更されました。`startelf()`は、おそらくELFヘッダとプログラムヘッダテーブルの直後の、セクションデータが始まる位置を返す関数です。これにより、セクションの配置がより予測可能で一貫性のあるものになります。
    *   `.dynamic`セクションの`sh->off`も同様に`startelf()`を使用するように変更され、その後の`seek(cout, dynsh->off, 0)`という明示的なシークが不要になりました。これは、セクションのデータがファイル内で連続して配置されることを前提とした最適化または修正と考えられます。

3.  **`PT_LOAD`プログラムヘッダの再構築**:
    *   以前は、動的ロードセクション（`.dynamic`、`.hash`、`.dynsym`、`.dynstr`などを含む）のために個別の`PT_LOAD`プログラムヘッダが作成されていました。この`PT_LOAD`は、`ph->filesz`と`ph->memsz`の計算に`+8`というマジックナンバーを含んでおり、コメントで「temporary hack」と記されていました。これは、`readelf`ツールがハッシュセクションの終わりでアドレス指定を黙らせるための一時的な回避策だったようです。
    *   このコミットでは、この一時的な`PT_LOAD`が削除され、代わりに動的セクション全体をカバーする新しい`PT_LOAD`プログラムヘッダが最後に導入されています。この新しい`PT_LOAD`は、`sh->off`と`sh->size`（ここで`sh`は`.dynamic`セクションヘッダを指す）を使用して、より正確にファイルサイズとメモリサイズを計算しています。これにより、マジックナンバーが不要になり、ELF構造の定義に沿ったよりクリーンな方法で動的セクションがロードされるようになりました。

4.  **`PT_DYNAMIC`プログラムヘッダの生成ロジックの改善**:
    *   `PT_DYNAMIC`プログラムヘッダは、`.dynamic`セクションのオフセットとサイズを正確に参照する必要があります。以前は`dynsh`変数を使っていましたが、これが削除されたため、新しく作成された`.dynamic`セクションヘッダ（`sh`）の`off`と`size`を直接使用するように変更されました。これにより、`PT_DYNAMIC`が指す情報が常に最新かつ正確な`.dynamic`セクションのデータと一致することが保証されます。

これらの変更は、ELFファイルの構造、特に動的リンクに関連する部分の生成ロジックをより堅牢で理解しやすいものにすることを目的としています。リンカのコードがクリーンになることで、将来的な機能追加やバグ修正が容易になります。

## コアとなるコードの解説

1.  **`Elf64SHdr *sh, *dynsh;` から `Elf64SHdr *sh;` への変更**:
    *   以前は`.dynamic`セクションヘッダ専用の変数`dynsh`が宣言されていましたが、これが削除されました。これは、`.dynamic`セクションヘッダも他のセクションヘッダと同様に、汎用の`sh`変数を使って生成・設定できるようになったことを意味します。これにより、コードの重複が減り、リンカのセクションヘッダ管理ロジックがより統一されました。

2.  **`.interp`、`.hash`、`.dynsym`、`.dynstr`セクションヘッダの`sh->addr = va;`行の削除**:
    *   これらの行は、セクションの仮想アドレス`sh->addr`を、おそらく一時的な変数`va`に設定していました。しかし、その直後または少し後に`sh->addr = startva + sh->off;`という行で正しい仮想アドレスが再計算されています。この重複した設定は不要であり、削除することでコードが簡素化され、意図が明確になります。`startva + sh->off`が、プログラムのベースアドレス（`startva`）とファイル内のセクションオフセット（`sh->off`）から仮想アドレスを計算する正しい方法です。

3.  **`.hash`セクションの`sh->off = seek(cout, 0, 1);` から `sh->off = startelf();` への変更**:
    *   `seek(cout, 0, 1)`は、出力ファイル（`cout`）の現在の書き込み位置を返す関数です。これは、セクションデータが直前のデータに続いて配置されることを意味します。
    *   `startelf()`は、ELFヘッダとプログラムヘッダテーブルの直後の、セクションデータが始まる標準的な位置を返す関数であると推測されます。この変更は、`.hash`セクションの配置を、ファイル内の特定の固定された開始点に揃えることを意図していると考えられます。これにより、ELFファイルの構造がより標準的になり、他のツールとの互換性が向上する可能性があります。

4.  **動的ロードセクションのための`PT_LOAD`プログラムヘッダの削除と再構築**:
    *   以前のコードでは、動的リンクに関連するセクション（`.dynamic`、`.hash`など）をカバーするために、個別の`PT_LOAD`プログラムヘッダが作成されていました。この`PT_LOAD`の`filesz`と`memsz`の計算には`+8`という「一時的なハック」が含まれていました。
    *   このコミットでは、この特定の`PT_LOAD`が削除され、代わりに、動的セクション全体をカバーするより一般的な`PT_LOAD`プログラムヘッダが最後に導入されています。この新しい`PT_LOAD`は、`sh->off + sh->size - ph->off`という計算式で`filesz`と`memsz`を設定しています。ここで`sh`は`.dynamic`セクションヘッダを指し、`ph->off`は新しい`PT_LOAD`の開始オフセットです。この変更により、動的セクションのロード範囲がより正確に定義され、以前の「ハック」が不要になりました。これは、ELFのセグメントとセクションのマッピングに関する理解が深まり、より正確な実装になったことを示しています。

5.  **`.dynamic`セクションヘッダの生成と`PT_DYNAMIC`プログラムヘッダの更新**:
    *   以前は`dynsh`変数を使って`.dynamic`セクションヘッダを初期化していましたが、これが削除されたため、`sh = newElf64SHdr(".dynamic");`という形で`sh`変数に直接割り当てられるようになりました。
    *   `sh->off = startelf();`という変更は、`.dynamic`セクションのデータがファイル内の特定の開始位置から始まることを保証します。
    *   `PT_DYNAMIC`プログラムヘッダは、`.dynamic`セクションの場所とサイズを指す必要があります。変更後、`ph->off = sh->off;`、`ph->filesz = sh->size;`、`ph->memsz = sh->size;`のように、新しく設定された`.dynamic`セクションヘッダ（`sh`）の情報を直接参照するようになりました。これにより、`PT_DYNAMIC`が常に正しい`.dynamic`セクションを指すことが保証され、コードの整合性が向上します。

これらの変更は全体として、`6l`リンカが生成するELFファイルの動的リンク関連の構造をより正確に、かつ簡潔に記述するためのものです。冗長な変数や一時的な回避策が排除され、ELF仕様に沿ったクリーンな実装に近づいています。

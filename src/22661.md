## 元コミット内容

`cmd/go: always link external test packages first when using gccgo`

この変更は、`gccgo`を使用する際に、外部テストパッケージを常に最初にリンクするようにします。これは、Canonicalが`cmd/go`ツールのフォーク（Ubuntu 14.04+で`gccgo-go.deb`としてパッケージ化されているもの）で行ったいくつかの修正を統合したものです。さらに、この変更は`gccgoToolchain.ld()`関数を`gccgo-5.0`で出荷されるバージョンに更新します。`gccgo`が独自のGoツールと共に使用される可能性が高いことを考慮すると、`libgo`のバージョンが`gccgotoolchain.ld()`の内容を決定することが理にかなっています。詳細については、[https://codereview.appspot.com/222890043/](https://codereview.appspot.com/222890043/)を参照してください。

## 変更の背景

このコミットの背景には、主に`gccgo`コンパイラとGoのテストフレームワークの連携における問題がありました。

1.  **`gccgo`のリンキング要件**: 標準のGoコンパイラ（`gc`）とは異なり、`gccgo`はC/C++コンパイラであるGCCのフロントエンドとして動作します。そのため、生成されるオブジェクトファイルやライブラリのリンキングには、GCCのリンカー（`ld`）が使用されます。GCCのリンカーは、依存関係の解決において、ライブラリの指定順序に敏感な場合があります。特に、シンボルが定義される前に使用される場合、リンクエラーが発生する可能性があります。
2.  **Goのテストパッケージの種類**: Goには、大きく分けて2種類のテストパッケージがあります。
    *   **内部テストパッケージ**: テスト対象のパッケージと同じディレクトリに`_test.go`ファイルとして存在するテストコード。これらはテスト対象のパッケージと同じ名前空間でコンパイルされます。
    *   **外部テストパッケージ**: テスト対象のパッケージとは異なる名前空間でコンパイルされるテストコード。通常、`package foo_test`のように、パッケージ名に`_test`サフィックスが付けられます。これにより、テストコードはテスト対象のパッケージの内部実装にアクセスすることなく、エクスポートされたAPIのみをテストできます。
3.  **`gccgo`と外部テストパッケージのリンキング問題**: `gccgo`環境において、外部テストパッケージが正しくリンクされない、またはリンキング順序の問題で実行時エラーが発生するケースがありました。これは、外部テストパッケージが依存するライブラリや、テスト対象のパッケージ自体が、リンカーに渡される順序が適切でなかったためと考えられます。特に、CanonicalがUbuntu向けに提供していた`gccgo`のフォークでは、この問題が顕著であり、いくつかの修正が独自に適用されていました。
4.  **`gccgoToolchain.ld()`の同期**: `gccgo`は`libgo`というGoランタイムライブラリに依存しています。`gccgo`のバージョンアップ（特に`gccgo-5.0`）に伴い、`libgo`の内部構造やリンキング要件が変更される可能性がありました。`cmd/go`ツールが古い`gccgoToolchain.ld()`の実装を使用していると、新しい`gccgo`バージョンでビルドが失敗する原因となります。そのため、`cmd/go`が`gccgo`の最新のリンキング要件に追従する必要がありました。

これらの問題を解決し、`gccgo`環境でのGoテストの安定性と互換性を向上させることが、このコミットの主要な動機となっています。

## 前提知識の解説

### Goコンパイラの種類 (`gc` vs `gccgo`)

Go言語には、主に2つの公式コンパイラ実装があります。

1.  **`gc` (Go Compiler)**:
    *   Goプロジェクトが開発している標準のコンパイラです。
    *   Go言語で書かれており、Goのソースコードを直接機械語にコンパイルします。
    *   クロスコンパイルに優れており、単一のバイナリを生成します。
    *   Goのランタイム（ガベージコレクタ、スケジューラなど）は、コンパイルされたバイナリに静的にリンクされます。
    *   通常、`go build`コマンドを使用すると、この`gc`コンパイラがデフォルトで使用されます。

2.  **`gccgo`**:
    *   GCC (GNU Compiler Collection) のフロントエンドとして実装されたGoコンパイラです。
    *   GoのソースコードをGCCの中間表現に変換し、その後GCCのバックエンドが機械語にコンパイルします。
    *   C/C++などの他の言語とGoコードを混在させる場合に有利な場合があります。
    *   Goのランタイムは、`libgo`という共有ライブラリまたは静的ライブラリとして提供され、`gccgo`でコンパイルされたプログラムはこれにリンクされます。
    *   GCCのリンカーを使用するため、リンキングの挙動が`gc`とは異なる場合があります。

### Goのビルドプロセスとリンキング

`go build`や`go test`のようなコマンドは、Goのソースコードをコンパイルし、実行可能なバイナリやライブラリを生成します。このプロセスには、以下の主要なステップが含まれます。

1.  **コンパイル**: 各Goソースファイルがオブジェクトファイルにコンパイルされます。
2.  **アーカイブ**: コンパイルされたオブジェクトファイルは、パッケージごとにアーカイブファイル（`.a`ファイル）にまとめられます。
3.  **リンキング**: 最終的な実行可能ファイルを生成するために、これらのアーカイブファイル、Goランタイムライブラリ、および必要に応じてC/C++ライブラリがリンカーによって結合されます。リンカーは、参照されていないシンボルを解決し、最終的なバイナリを作成します。

特に`gccgo`の場合、リンキングはGCCのリンカーによって行われ、リンカーに渡されるライブラリやオブジェクトファイルの順序が重要になることがあります。依存関係が正しく解決されるためには、定義が使用される前に定義されている必要があります。

### Goのテストパッケージ (`_test`サフィックスと外部テストパッケージ)

Goのテストは、通常、テスト対象のパッケージと同じディレクトリに`_test.go`というサフィックスを持つファイルに記述されます。

*   **内部テスト (`package foo`)**:
    *   `foo.go`と`foo_test.go`が同じディレクトリにあり、両方とも`package foo`と宣言されている場合。
    *   テストコードはテスト対象のパッケージの内部（エクスポートされていない関数や変数）にアクセスできます。
    *   `go test`コマンドは、これらのファイルをまとめてコンパイルし、テストバイナリを生成します。

*   **外部テスト (`package foo_test`)**:
    *   `foo.go`が`package foo`と宣言され、`foo_test.go`が`package foo_test`と宣言されている場合。
    *   テストコードは、テスト対象のパッケージのエクスポートされたAPIのみにアクセスできます。これは、ユーザーがパッケージをインポートして使用するのと同じ方法でテストを行うため、より現実的なテストシナリオを提供します。
    *   `go test`コマンドは、まずテスト対象のパッケージをビルドし、次に外部テストパッケージを別のパッケージとしてビルドし、これらをリンクしてテストバイナリを生成します。このリンキングの段階で、`gccgo`において問題が発生することがありました。

### リンカーの順序依存性

一部のリンカー（特にGCCのリンカー）は、ライブラリやオブジェクトファイルの指定順序に依存する場合があります。これは、リンカーがシンボルを解決する際に、ファイルが指定された順序でスキャンされるためです。

*   **問題**: あるライブラリAが別のライブラリBのシンボルを使用している場合、リンカーコマンドラインでライブラリBがライブラリAの**後に**指定されていないと、リンカーはライブラリAが参照するシンボルを見つけられず、リンクエラーになることがあります。
*   **解決策**: 依存関係の解決を確実にするために、依存される側（定義を提供する側）のライブラリを、依存する側（定義を使用する側）のライブラリの後に指定することが一般的です。

このコミットは、`gccgo`環境における外部テストパッケージと、それが依存する他のパッケージ（特にテスト対象のパッケージ）との間のリンキング順序の問題を解決しようとしています。

## 技術的詳細

このコミットは、`cmd/go`ツールが`gccgo`コンパイラを使用する際のリンキングロジックを修正し、特に外部テストパッケージの扱いを改善しています。

1.  **`src/cmd/go/build.go`の変更**:
    *   `gccgoToolchain.ld()`関数は、`gccgo`でビルドされたGoプログラムをリンクする際の主要なロジックを含んでいます。この関数は、すべての依存パッケージのアーカイブファイル（`.a`ファイル）を収集し、リンカーに渡す順序を決定します。
    *   **既存の問題**: 以前のロジックでは、テストパッケージ（`fake`フィールドが`true`のパッケージ）と非テストパッケージのリンキング順序が、`gccgo`のリンカーにとって最適ではありませんでした。特に、外部テストパッケージ（`package foo_test`）が、テスト対象のパッケージ（`package foo`）のシンボルを参照する際に、リンカーがシンボルを見つけられない問題が発生していました。
    *   **修正**:
        *   `apackagesSeen`という`map[*Package]bool`が導入され、既に処理されたパッケージを追跡します。
        *   `xfiles`という新しい`[]string`スライスが導入されました。これは、**外部テストパッケージ**（`a.p.fake && a.p.external`が`true`のパッケージ）のアーカイブファイルを一時的に保持するために使用されます。
        *   リンキング対象のアーカイブファイル（`afiles`）を収集するループが修正されました。
            *   `a.p.fake`が`true`のパッケージ（テストパッケージ）の場合、さらに`a.p.external`が`true`であれば、そのアーカイブファイルは`xfiles`に追加されます。これは、外部テストパッケージを後で`afiles`の先頭に配置するためです。
            *   `a.p.fake`が`true`だが`a.p.external`が`false`の場合（内部テストパッケージ）、そのアーカイブファイルは`afiles`の**先頭**に追加されます（`append([]string{a.target}, afiles...)`）。これにより、内部テストパッケージは他の通常のパッケージよりも先にリンクされます。
            *   それ以外の通常のパッケージは、`afiles`の末尾に追加されます。
        *   ループの最後に、`afiles = append(xfiles, afiles...)`という行が追加されました。これにより、`xfiles`に収集されたすべての外部テストパッケージのアーカイブファイルが、最終的な`afiles`リストの**最も先頭**に配置されます。
    *   **効果**: この変更により、`gccgo`のリンカーに対して、外部テストパッケージが常に最初に、次に内部テストパッケージ、そして通常のパッケージの順で渡されるようになります。これにより、外部テストパッケージが依存するシンボルが、リンキング時に確実に解決されるようになります。

2.  **`src/cmd/go/pkg.go`の変更**:
    *   `Package`構造体に`external bool`フィールドが追加されました。
    *   このフィールドは、その`Package`が合成された（`fake: true`）外部テストパッケージであるかどうかを示すために使用されます。
    *   この新しいフィールドは、`build.go`のリンキングロジックで、内部テストパッケージと外部テストパッケージを区別するために利用されます。

3.  **`src/cmd/go/test.go`の変更**:
    *   `builder.test()`関数は、Goのテストをビルドするロジックを含んでいます。
    *   外部テストパッケージ（`pxtest`）を生成する際に、新しく追加された`external: true`フィールドが設定されるようになりました。
    *   これにより、`cmd/go`ツールは、特定のパッケージが外部テストパッケージであることを正しく識別し、`build.go`のリンキングロジックで適切に処理できるようになります。

これらの変更は、`gccgo`のリンカーの特性（リンキング順序への依存性）を考慮し、Goのテストフレームワークが生成する様々な種類のパッケージ（特に外部テストパッケージ）が、`gccgo`環境で正しくビルドおよびリンクされることを保証します。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更点

`gccgoToolchain.ld` 関数は、`gccgo` を使用して最終的な実行可能ファイルをリンクする際の主要なロジックを担っています。

1.  **`apackagesSeen` と `xfiles` の導入**:
    *   `apackagesSeen := make(map[*Package]bool)`: これは、既に処理され、リンキングリストに追加されたパッケージを追跡するためのマップです。これにより、同じパッケージが複数回リンキングリストに追加されるのを防ぎます。
    *   `xfiles := []string{}`: これは、**外部テストパッケージ**のアーカイブファイル（`.a`ファイル）を一時的に格納するための新しいスライスです。外部テストパッケージは、リンキング順序において特別な優先順位を持つため、通常のパッケージとは別に収集されます。

2.  **リンキング順序のロジック変更**:
    *   以前のコードは、`importPathsSeen` を使用してパッケージの重複を防ぎ、テストパッケージを優先していましたが、外部テストと内部テストの区別が曖昧でした。
    *   新しいロジックでは、`allactions` (ビルドプロセス中のすべてのアクション) を逆順にイテレートします。これは、インストールアクションがビルドアクションの出力を削除する可能性があるため、常に最新のインストール済みファイルを取得するためです。
    *   `if !a.p.Standard` ブロック内で、パッケージが標準ライブラリではない場合に処理を行います。
    *   `if a.p != nil && !apackagesSeen[a.p]` で、パッケージが有効であり、まだ処理されていないことを確認します。
    *   **外部テストパッケージの処理**: `if a.p.fake && a.p.external` の条件が追加されました。
        *   `a.p.fake` は、そのパッケージがテストのために合成された（通常のソースコードから直接ビルドされたものではない）ことを示します。
        *   `a.p.external` は、`pkg.go` で新しく追加されたフィールドで、そのパッケージが外部テストパッケージであることを示します。
        *   この条件が真の場合、そのアーカイブファイル (`a.target`) は `xfiles` スライスに追加されます。コメントにあるように、「外部テストは内部テストの前に来なければならない。これらを別のリストに保存し、このループの後に先頭に配置する。」という意図です。
    *   **内部テストパッケージの処理**: `else if a.p.fake` の条件が追加されました。
        *   これは、`fake` であるが `external` ではないパッケージ、つまり内部テストパッケージを指します。
        *   これらのアーカイブファイルは `afiles = append([]string{a.target}, afiles...)` によって、`afiles` スライスの**先頭**に追加されます。これにより、内部テストパッケージは通常のパッケージよりも先にリンクされます。
    *   **通常のパッケージの処理**: `else` ブロックでは、通常の（テストではない）パッケージのアーカイブファイルが `afiles` スライスの末尾に追加されます。
    *   **最終的なリンキング順序の確定**: ループの最後に `afiles = append(xfiles, afiles...)` が実行されます。これにより、`xfiles` に収集されたすべての外部テストパッケージのアーカイブファイルが、`afiles` スライスの**最も先頭**に結合されます。結果として、リンカーには「外部テストパッケージ -> 内部テストパッケージ -> 通常のパッケージ」という順序でアーカイブファイルが渡されることになります。この順序は、`gccgo` のリンカーが依存関係を正しく解決するために重要です。

### `src/cmd/go/pkg.go` の変更点

`Package` 構造体は、Goのパッケージに関するメタデータを保持します。
*   `external bool` フィールドが追加されました。
*   このフィールドは、`fake` (合成されたパッケージ) であるパッケージが、特に外部テストパッケージであるかどうかを明示的に示すために使用されます。これにより、`build.go` のリンキングロジックが、内部テストと外部テストを正確に区別できるようになります。

### `src/cmd/go/test.go` の変更点

`builder.test` 関数は、`go test` コマンドがテストバイナリをビルドする際に呼び出されます。
*   外部テストパッケージ (`pxtest`) を設定する際に、新しく追加された `external: true` フィールドが設定されるようになりました。
*   これにより、`cmd/go` ツールは、`pxtest` が外部テストパッケージであることを正しくマークし、その情報が `Package` 構造体を介して `build.go` のリンキングロジックに伝達されるようになります。

これらの変更は連携して機能し、`gccgo` 環境におけるGoのテスト、特に外部テストパッケージのビルドとリンキングの堅牢性を大幅に向上させます。

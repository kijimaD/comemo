# [インデックス 24655] ファイルの概要

このコミットは、Go言語のネットワークパッケージにおけるDNSリゾルバの選択ロジックを改善し、`go`リゾルバと`cgo`リゾルバの選択がすべての名前解決ルーチンで一貫して尊重されるようにするものです。特に`LookupAddr`関数において、この変更が重要な影響を与えます。

## 元コミット内容

`net: respect go vs cgo resolver selection in all lookup routines`

このコミットは、Goのネットワークパッケージにおける名前解決ルーチン全体で、GoネイティブのDNSリゾルバ（`go`）とCgoベースのDNSリゾルバ（`cgo`）の選択が適切に尊重されるようにするものです。特に`LookupAddr`関数にとって重要であり、この変更がなければ、以前は純粋なGo実装（軽量で、呼び出しごとに1つのゴルーチン）であったものが、無条件にCgo実装（重く、呼び出しごとに1つのスレッド）になってしまう可能性がありました。

この変更はIssue #12190を修正します。

## 変更の背景

Goのネットワークパッケージは、DNS名前解決のために2つの主要なメカニズムを提供しています。

1.  **Goネイティブのリゾルバ (`go`リゾルバ)**: Go言語で完全に実装されており、軽量で、Goのスケジューラとゴルーチンモデルに統合されています。通常、パフォーマンスが高く、リソース消費が少ない傾向があります。
2.  **Cgoベースのリゾルバ (`cgo`リゾルバ)**: システムのCライブラリ（例: `glibc`の`getaddrinfo`）をCgoを介して呼び出します。これにより、システムの`nsswitch.conf`などの設定を尊重し、LDAPやNISなどの非標準的な名前解決メカニズムも利用できます。しかし、Cgo呼び出しはGoのランタイムとCランタイム間のコンテキストスイッチを伴い、通常はより重く、スレッドを消費します。

Goアプリケーションは、ビルドタグ（例: `netgo`）や環境変数、あるいは内部ロジックによって、どちらのリゾルバを使用するかを選択できます。しかし、このコミット以前は、`LookupAddr`のような一部の名前解決関数が、この選択ロジックを完全に尊重していませんでした。

具体的には、`LookupAddr`は以前、Goネイティブのリゾルバを使用する傾向がありましたが、特定の条件下では意図せずCgoリゾルバにフォールバックする可能性がありました。コミットメッセージが示唆するように、このCLがなければ`LookupAddr`は「無条件にcgo」になる可能性があり、これはパフォーマンスとリソース使用の観点から望ましくない動作でした。Issue #12190は、この一貫性のない動作や予期せぬリゾルバ選択に関する問題を報告していたと考えられます。

この変更の目的は、開発者が意図したリゾルバ選択（`go`または`cgo`）が、`LookupHost`だけでなく、`LookupPort`、`LookupCNAME`、`LookupAddr`といった他の名前解決ルーチンでも確実に適用されるようにすることです。これにより、Goアプリケーションのネットワーク動作の予測可能性と制御が向上します。

## 前提知識の解説

*   **DNS (Domain Name System)**: ドメイン名とIPアドレスを変換するシステム。
*   **名前解決 (Name Resolution)**: ドメイン名からIPアドレスを検索したり、その逆（リバースDNSルックアップ）を行ったりするプロセス。
*   **Goの`net`パッケージ**: Go言語でネットワークプログラミングを扱うための標準ライブラリ。DNS名前解決機能も提供します。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのGoの機能。システムコールやCライブラリを利用する際に使用されます。
*   **`go`リゾルバ**: Go言語で完全に実装されたDNSリゾルバ。Goのランタイム内で動作し、軽量です。
*   **`cgo`リゾルバ**: Cgoを介してシステムのCライブラリ（例: `getaddrinfo`）を利用するDNSリゾルバ。システムの`nsswitch.conf`などの設定を尊重します。
*   **`LookupAddr`**: IPアドレスからホスト名を検索する（リバースDNSルックアップ）Goの`net`パッケージの関数。
*   **`LookupPort`**: サービス名とネットワークプロトコルからポート番号を検索するGoの`net`パッケージの関数。
*   **`LookupCNAME`**: ドメイン名のCNAME（Canonical Name）レコードを検索するGoの`net`パッケージの関数。
*   **`netgo`ビルドタグ**: Goプログラムをビルドする際に指定できるタグの一つ。これを指定すると、`net`パッケージはCgoリゾルバを使用せず、常にGoネイティブのリゾルバを使用するように強制されます。これは、Cgoが利用できない環境や、Cgoのオーバーヘッドを避けたい場合に有用です。
*   **`conf`構造体 (`src/net/conf.go`)**: `net`パッケージの内部設定を保持する構造体。DNSリゾルバの選択に関するフラグ（`netGo`, `netCgo`, `forceCgoLookupHost`など）が含まれます。
*   **`hostLookupOrder`**: ホスト名の名前解決にどの戦略（`go`リゾルバ、`cgo`リゾルバ、またはその組み合わせ）を使用するかを決定する内部関数。

## 技術的詳細

このコミットの核心は、`net`パッケージ内の名前解決ルーチンが、`conf`構造体で定義されたリゾルバ選択ポリシーをより厳密に遵守するように変更された点にあります。

1.  **`src/net/conf.go`の変更**:
    *   `conf`構造体の`netGo`フィールドのコメントがより明確になりました。以前は`"netgo" build tag in use (or no cgo)`でしたが、`go DNS resolution forced`に変更され、Goリゾルバが強制される状況を直接的に示しています。
    *   新しいメソッド`canUseCgo() bool`が`conf`構造体に追加されました。このメソッドは、ホスト名以外のルックアップ（`LookupPort`, `LookupCNAME`, `LookupAddr`など）でCgo関数を使用できるかどうかを判断します。具体的には、`c.hostLookupOrder("") == hostLookupCgo`という条件で、空のホスト名に対するルックアップ順序がCgoを優先するかどうかをチェックします。これにより、Cgoリゾルバの使用が許可されているかを一元的に判断できるようになります。

2.  **`src/net/lookup_unix.go`の変更**:
    *   `lookupPort`, `lookupCNAME`, `lookupAddr`の各関数におけるCgoリゾルバの呼び出しロジックが変更されました。
    *   **変更前**: これらの関数は、まず`cgoLookupXxx`関数を呼び出し、その結果（`ok`ブール値）に基づいて`goLookupXxx`にフォールバックしていました。`ok`が`false`の場合にGoリゾルバが使われるというロジックでした。これは、Cgoリゾルバが利用できない、または特定の理由で失敗した場合にGoリゾルバに切り替えるという意図でしたが、リゾルバ選択ポリシー（`netgo`ビルドタグなど）がCgoの使用を明示的に禁止している場合でも、Cgo関数が試行される可能性がありました。
    *   **変更後**: 各関数は、最初に`systemConf().canUseCgo()`を呼び出して、Cgoリゾルバの使用が許可されているかを明示的にチェックするようになりました。
        *   もし`canUseCgo()`が`true`を返した場合のみ、`cgoLookupXxx`関数が試行されます。
        *   `cgoLookupXxx`が成功した場合（`ok`が`true`）、その結果が返されます。
        *   `canUseCgo()`が`false`を返した場合、または`cgoLookupXxx`が失敗した場合（`ok`が`false`）、常に`goLookupXxx`関数が呼び出され、その結果が返されます。

この変更により、`netgo`ビルドタグが指定されている場合や、その他の理由でCgoリゾルバの使用が禁止されている場合、`lookupPort`、`lookupCNAME`、`lookupAddr`はCgo関数を試行することなく、直接Goネイティブのリゾルバを使用するようになります。これにより、リゾルバ選択の一貫性が保たれ、特に`LookupAddr`のような関数が意図せずCgoリゾルバに切り替わることによるパフォーマンス低下やリソース消費の増加を防ぎます。

## コアとなるコードの解説

### `src/net/conf.go`

*   **`netGo`コメントの変更**: `netGo`フィールドのコメントが`go DNS resolution forced`に変更され、GoネイティブのDNS解決が強制される状態をより明確に示しています。これは、`netgo`ビルドタグが使用されている場合や、Cgoが利用できない環境でGoリゾルバが選択されることを意味します。
*   **`canUseCgo()`メソッドの追加**:
    ```go
    func (c *conf) canUseCgo() bool {
    	return c.hostLookupOrder("") == hostLookupCgo
    }
    ```
    この新しいメソッドは、`conf`構造体の設定に基づいて、Cgoリゾルバを使用することが許可されているかどうかを判断します。`c.hostLookupOrder("")`は、ホスト名が指定されていない場合の名前解決の優先順位を返します。もしその優先順位が`hostLookupCgo`（Cgoリゾルバを優先する）と一致すれば、Cgoの使用が許可されていると判断されます。このメソッドは、`lookupPort`、`lookupCNAME`、`lookupAddr`などの関数でCgoリゾルバを呼び出す前に、その可否をチェックするために使用されます。

### `src/net/lookup_unix.go`

`lookupPort`, `lookupCNAME`, `lookupAddr`の各関数で、Cgoリゾルバの呼び出しロジックが変更されました。例として`lookupPort`関数を見てみましょう。

**変更前**:

```go
func lookupPort(network, service string) (int, error) {
	port, err, ok := cgoLookupPort(network, service)
	if !ok {
		port, err = goLookupPort(network, service)
	}
	return port, err
}
```
このコードでは、まず無条件に`cgoLookupPort`を試行し、`ok`が`false`の場合にのみ`goLookupPort`にフォールバックしていました。これは、Cgoリゾルバが利用できない、または特定の理由で失敗した場合のフォールバックとしては機能しますが、`netgo`ビルドタグなどでCgoの使用が明示的に禁止されている場合でもCgo関数が呼び出される可能性がありました。

**変更後**:

```go
func lookupPort(network, service string) (int, error) {
	if systemConf().canUseCgo() { // Cgoの使用が許可されているかチェック
		if port, err, ok := cgoLookupPort(network, service); ok { // 許可されていればCgoを試行
			return port, err // 成功すれば結果を返す
		}
	}
	return goLookupPort(network, service) // 許可されていないか、Cgoが失敗した場合はGoリゾルバを使用
}
```
変更後のコードでは、まず`systemConf().canUseCgo()`を呼び出して、Cgoリゾルバの使用が現在の設定で許可されているかをチェックします。
*   もし`canUseCgo()`が`true`を返した場合、初めて`cgoLookupPort`が試行されます。`cgoLookupPort`が成功し、`ok`が`true`であれば、その結果が即座に返されます。
*   `canUseCgo()`が`false`を返した場合（Cgoの使用が禁止されている場合）、または`cgoLookupPort`が試行されたものの`ok`が`false`であった場合（Cgoリゾルバが失敗した場合）、最終的に`goLookupPort`が呼び出され、Goネイティブのリゾルバが使用されます。

この変更により、Goのネットワークパッケージは、リゾルバ選択ポリシーをより厳密に適用し、開発者が意図したリゾルバが確実に使用されるようにします。これにより、特に`LookupAddr`のような関数における予期せぬCgoリゾルバの使用が防止され、アプリケーションの動作の一貫性とパフォーマンスが向上します。

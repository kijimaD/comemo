# [インデックス 26473] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるバックグラウンドマークワーカーの挙動を修正するものです。具体的には、マークワーカーがP（プロセッサ）にアタッチするタイミングを調整し、ワーカーG（ゴルーチン）が複数の場所で同時に実行される可能性のある競合状態を解消します。これにより、`g.m`が不正にクリアされ、ワーカーがクラッシュする問題を解決します。

## 変更の背景

Goのガベージコレクション（GC）は、並行して動作するマークフェーズを含んでいます。このフェーズでは、バックグラウンドマークワーカーと呼ばれる特別なゴルーチン（G）が、P（プロセッサ、論理CPU）にアタッチされてGC作業を実行します。

このコミット以前のGoランタイムでは、バックグラウンドマークワーカーは、初期化時またはGCフェーズの移行後に、自身が担当するPにアタッチしてから`gopark`（ゴルーチンを停止させる関数）を呼び出して待機状態に入っていました。

しかし、このアタッチのタイミングに問題がありました。ワーカーGがPにアタッチする際、そのワーカーGが実際に実行されているPと、アタッチしようとしているPが異なる場合がありました。これは、スケジューラがワーカーGを別のPで実行している間に、ワーカーGが自身を特定のPに「登録」しようとする状況です。

この状況が発生すると、ワーカーGはまだ現在実行中のP上で完全に停止していないにもかかわらず、アタッチ先のPのスケジューラがそのワーカーGを「実行可能」と判断し、別のM（OSスレッド）上で実行を開始してしまう可能性がありました。結果として、**一つのワーカーGが同時に二つの異なるM上で実行される**という競合状態が発生していました。

この二重実行の最も顕著な問題は、最初に実行されていたワーカーGが`gopark`によって停止する際に、そのゴルーチンが現在実行されているMへのポインタである`g.m`フィールドをクリアしてしまうことでした。しかし、もし別のM上で同じワーカーGがまだ実行中であった場合、その「二番目のインスタンス」は`g.m`がクリアされた後に`g.m`を使用しようとして、ヌルポインタ参照などのクラッシュを引き起こしていました。

このコミットは、この不安定な挙動を修正し、GCの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goランタイムスケジューラ (P, M, G)

Goランタイムは、効率的な並行処理を実現するために、独自のスケジューラを持っています。このスケジューラは、以下の3つの主要な抽象化に基づいています。

*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。数千から数百万のゴルーチンを同時に実行できます。
*   **M (Machine)**: OSスレッドに相当します。Goランタイムは、OSスレッドを抽象化したMを管理し、その上でGを実行します。
*   **P (Processor)**: 論理プロセッサまたはコンテキストです。MとGの間の仲介役として機能します。Pは実行可能なGのキューを保持し、MはPからGを取得して実行します。Pの数は通常、CPUコアの数に設定され、同時に実行できるGの数を制限します。

GはPにアタッチされ、PはMにアタッチされます。MはPからGを取得し、そのGを実行します。Gがシステムコールなどでブロックされると、MはPを解放し、別のMがそのPを引き継いで他のGを実行できます。

### Goのガベージコレクション (GC)

GoのGCは、並行マーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGC作業の一部を実行することで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指します。

*   **マークフェーズ**: GCの重要なフェーズの一つで、到達可能なオブジェクトを特定し、マークします。このフェーズには、アプリケーションのゴルーチンと並行して動作する「バックグラウンドマークワーカー」ゴルーチンが関与します。
*   **バックグラウンドマークワーカー**: GCのマーク作業を分担して実行する特別なゴルーチンです。これらは、通常のアプリケーションゴルーチンと同様にスケジューラによって管理されますが、GCの特定のタスクに特化しています。

### `gopark` 関数

`gopark`はGoランタイムの内部関数で、現在のゴルーチン（G）を停止させ、待機状態（`_Gwaiting`）に移行させるために使用されます。`gopark`が呼び出されると、現在のMはPを解放し、別の実行可能なGを探して実行します。`gopark`は、ゴルーチンが特定のイベントを待つ必要がある場合（例: ネットワークI/O、チャネル操作、GCワーカーの待機など）に利用されます。

`gopark`はコールバック関数を受け取ることができ、このコールバックはゴルーチンが実際に停止する直前、システムスタック上で実行されます。この特性が、今回の修正の鍵となります。

### `g.m` フィールド

`g.m`は、Goランタイム内部の`g`構造体（ゴルーチンを表す）のフィールドで、そのゴルーチンが現在実行されているM（OSスレッド）へのポインタを保持します。ゴルーチンがM上で実行されている間、このポインタは有効です。ゴルーチンが停止したり、別のMに移行したりすると、このポインタは更新またはクリアされます。

## 技術的詳細

このコミットが解決しようとしている問題は、GoランタイムのスケジューリングとGCワーカーのライフサイクルにおける微妙な競合状態に起因します。

以前の実装では、`gcBgMarkWorker`関数内で、ワーカーGはまず`acquirem()`でMを取得し、次に`casgp(&p.gcBgMarkWorker, nil, gp)`を呼び出して、自身を特定のPのバックグラウンドマークワーカーとして登録していました。この登録が成功すると、そのPのスケジューラは、このワーカーGを実行可能な状態として認識します。

問題は、この登録処理が完了した時点では、ワーカーGがまだ`gopark`を呼び出して停止していない可能性がある点です。もし、ワーカーGが登録先のPとは異なるP上で実行されていた場合、以下のシーケンスで競合が発生する可能性がありました。

1.  ワーカーGがP1上で実行中に、自身をP2のバックグラウンドマークワーカーとして登録する。
2.  P2のスケジューラが、登録されたワーカーGを検出し、別のM2上でそのワーカーGの実行を開始する。
3.  この時点で、ワーカーGはP1上のM1とP2上のM2の両方で同時に実行されている状態になる。
4.  P1上のワーカーGが`gopark`を呼び出し、停止する。この際、`releasem(mp)`が実行され、`g.m`がクリアされる。
5.  P2上のワーカーGが、クリアされた`g.m`を使用しようとしてクラッシュする。

このコミットは、この問題を解決するために、Pへのアタッチ処理を`gopark`のコールバック関数内に移動させました。`gopark`のコールバックは、ゴルーチンが実際に停止し、システムスタック上で実行されている安全なコンテキストで呼び出されます。この時点で、ワーカーGはもはや実行中の状態ではなく、完全に停止しています。したがって、Pへのアタッチが行われても、ワーカーGが二重に実行されるリスクはなくなります。

具体的には、`gopark`に渡されるコールバック内で、`parkInfo`構造体を通じて渡されたPにワーカーGをアタッチします。これにより、アタッチが完了した時点でワーカーGは確実に停止しており、他のPのスケジューラがそれをピックアップしても安全な状態が保証されます。

## コアとなるコードの変更箇所

主な変更は `src/runtime/mgc.go` ファイルの `gcBgMarkWorker` 関数に集中しています。

*   `gcBgMarkWorker` 関数のシグネチャが `func gcBgMarkWorker(p *p)` から `func gcBgMarkWorker(_p_ *p)` に変更され、引数名がシャドウイングを避けるために変更されています。
*   `parkInfo` という新しい構造体が導入され、`m`（Mへのポインタ）と `attach`（アタッチ先のPへのポインタ）を保持します。
*   `gopark` の呼び出し方が変更され、`releasem(mp)` の代わりに `park.m` を解放し、Pへのアタッチ処理が `gopark` のコールバック関数内に移動されました。
*   `p.gcBgMarkWorker` へのワーカーGのアタッチ処理が、`gopark` のコールバック内の `if park.attach != nil` ブロック内に移動されました。
*   `acquirem()` の呼び出しと `releasem()` の呼び出しのタイミングが調整され、`parkInfo` 構造体のフィールドとしてMが管理されるようになりました。
*   `_p_.gcMarkWorkerMode` など、引数として渡されたPを参照する箇所が、新しい引数名 `_p_` を使用するように変更されました。

`src/runtime/proc.go` では、`procresize` 関数内で `p.gcBgMarkWorker = nil` の行にコメントが追加され、この代入がワールドストップ中に発生するため競合しないことが明記されています。

## コアとなるコードの解説

### `parkInfo` 構造体

```go
type parkInfo struct {
	m      *m // Release this m on park.
	attach *p // If non-nil, attach to this p on park.
}
var park parkInfo
```
`parkInfo` 構造体は、`gopark` のコールバックに渡すための情報をカプセル化します。`m` フィールドは、ゴルーチンが停止する際に解放すべきMを保持し、`attach` フィールドは、ゴルーチンが停止した後にアタッチすべきPを保持します。これにより、`gopark` のコールバック内で必要なコンテキストを安全に利用できます。

### `gopark` のコールバック内の変更

```go
gopark(func(g *g, parkp unsafe.Pointer) bool {
	park := (*parkInfo)(parkp)

	// The worker G is no longer running, so it's
	// now safe to allow preemption.
	releasem(park.m)

	// If the worker isn't attached to its P,
	// attach now. During initialization and after
	// a phase change, the worker may have been
	// running on a different P. As soon as we
	// attach, the owner P may schedule the
	// worker, so this must be done after the G is
	// stopped.
	if park.attach != nil {
		p := park.attach
		park.attach = nil
		// cas the worker because we may be
		// racing with a new worker starting
		// on this P.
		if !casgp(&p.gcBgMarkWorker, nil, g) {
			// The P got a new worker.
			// Exit this worker.
			return false
		}
	}
	return true
}, noescape(unsafe.Pointer(&park)), "GC worker (idle)", traceEvGoBlock, 0)
```

この部分が変更の核心です。
1.  `gopark` のコールバック関数が、`parkInfo` 構造体へのポインタを受け取るように変更されました。
2.  コールバック内で、まず `releasem(park.m)` を呼び出して、現在ゴルーチンを実行していたMを解放します。これは、ゴルーチンが完全に停止したことを意味します。
3.  次に、`if park.attach != nil` の条件チェックが行われます。これは、このワーカーGが特定のPにアタッチする必要がある場合に真となります。
4.  `casgp(&p.gcBgMarkWorker, nil, g)` を使用して、アトミックにワーカーGをPにアタッチします。`casgp`（Compare And Swap for Goroutine Pointer）は、`p.gcBgMarkWorker`が`nil`であれば、現在のゴルーチン`g`をそこに設定します。これは、他のワーカーがすでにこのPにアタッチしている可能性との競合を避けるためです。
5.  もしアタッチに失敗した場合（つまり、別のワーカーがすでにPにアタッチしていた場合）、現在のワーカーは終了します（`return false`）。

この変更により、Pへのアタッチはゴルーチンが完全に停止した後にのみ行われるため、ワーカーGが二重に実行されるという競合状態が解消されます。

### `acquirem` と `releasem` の管理

以前は `mp := acquirem()` と `releasem(mp)` が直接 `gcBgMarkWorker` 関数内で管理されていましたが、変更後は `park.m = acquirem()` と `releasem(park.m)` のように、`parkInfo` 構造体を介してMの取得と解放が管理されるようになりました。これにより、Mのライフサイクルが`gopark`のコールバックとより密接に連携し、安全性が向上しています。

## 前提知識の解説

### Goランタイムスケジューラ (P, M, G)

Goランタイムは、効率的な並行処理を実現するために、独自のスケジューラを持っています。このスケジューラは、以下の3つの主要な抽象化に基づいています。

*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。数千から数百万のゴルーチンを同時に実行できます。
*   **M (Machine)**: OSスレッドに相当します。Goランタイムは、OSスレッドを抽象化したMを管理し、その上でGを実行します。
*   **P (Processor)**: 論理プロセッサまたはコンテキストです。MとGの間の仲介役として機能します。Pは実行可能なGのキューを保持し、MはPからGを取得して実行します。Pの数は通常、CPUコアの数に設定され、同時に実行できるGの数を制限します。

GはPにアタッチされ、PはMにアタッチされます。MはPからGを取得し、そのGを実行します。Gがシステムコールなどでブロックされると、MはPを解放し、別のMがそのPを引き継いで他のGを実行できます。

### Goのガベージコレクション (GC)

GoのGCは、並行マーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGC作業の一部を実行することで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指します。

*   **マークフェーズ**: GCの重要なフェーズの一つで、到達可能なオブジェクトを特定し、マークします。このフェーズには、アプリケーションのゴルーチンと並行して動作する「バックグラウンドマークワーカー」ゴルーチンが関与します。
*   **バックグラウンドマークワーカー**: GCのマーク作業を分担して実行する特別なゴルーチンです。これらは、通常のアプリケーションゴルーチンと同様にスケジューラによって管理されますが、GCの特定のタスクに特化しています。

### `gopark` 関数

`gopark`はGoランタイムの内部関数で、現在のゴルーチン（G）を停止させ、待機状態（`_Gwaiting`）に移行させるために使用されます。`gopark`が呼び出されると、現在のMはPを解放し、別の実行可能なGを探して実行します。`gopark`は、ゴルーチンが特定のイベントを待つ必要がある場合（例: ネットワークI/O、チャネル操作、GCワーカーの待機など）に利用されます。

`gopark`はコールバック関数を受け取ることができ、このコールバックはゴルーチンが実際に停止する直前、システムスタック上で実行されます。この特性が、今回の修正の鍵となります。

### `g.m` フィールド

`g.m`は、Goランタイム内部の`g`構造体（ゴルーチンを表す）のフィールドで、そのゴルーチンが現在実行されているM（OSスレッド）へのポインタを保持します。ゴルーチンがM上で実行されている間、このポインタは有効です。ゴルーチンが停止したり、別のMに移行したりすると、このポインタは更新またはクリアされます。

## 技術的詳細

このコミットが解決しようとしている問題は、GoランタイムのスケジューリングとGCワーカーのライフサイクルにおける微妙な競合状態に起因します。

以前の実装では、`gcBgMarkWorker`関数内で、ワーカーGはまず`acquirem()`でMを取得し、次に`casgp(&p.gcBgMarkWorker, nil, gp)`を呼び出して、自身を特定のPのバックグラウンドマークワーカーとして登録していました。この登録が成功すると、そのPのスケジューラは、このワーカーGを実行可能な状態として認識します。

問題は、この登録処理が完了した時点では、ワーカーGがまだ`gopark`を呼び出して停止していない可能性がある点です。もし、ワーカーGが登録先のPとは異なるP上で実行されていた場合、以下のシーケンスで競合が発生する可能性がありました。

1.  ワーカーGがP1上で実行中に、自身をP2のバックグラウンドマークワーカーとして登録する。
2.  P2のスケジューラが、登録されたワーカーGを検出し、別のM2上でそのワーカーGの実行を開始する。
3.  この時点で、ワーカーGはP1上のM1とP2上のM2の両方で同時に実行されている状態になる。
4.  P1上のワーカーGが`gopark`を呼び出し、停止する。この際、`releasem(mp)`が実行され、`g.m`がクリアされる。
5.  P2上のワーカーGが、クリアされた`g.m`を使用しようとしてクラッシュする。

このコミットは、この問題を解決するために、Pへのアタッチ処理を`gopark`のコールバック関数内に移動させました。`gopark`のコールバックは、ゴルーチンが実際に停止し、システムスタック上で実行されている安全なコンテキストで呼び出されます。この時点で、ワーカーGはもはや実行中の状態ではなく、完全に停止しています。したがって、Pへのアタッチが行われても、ワーカーGが二重に実行されるリスクはなくなります。

具体的には、`gopark`に渡されるコールバック内で、`parkInfo`構造体を通じて渡されたPにワーカーGをアタッチします。これにより、アタッチが完了した時点でワーカーGは確実に停止しており、他のPのスケジューラがそれをピックアップしても安全な状態が保証されます。

## コアとなるコードの変更箇所

主な変更は `src/runtime/mgc.go` ファイルの `gcBgMarkWorker` 関数に集中しています。

*   `gcBgMarkWorker` 関数のシグネチャが `func gcBgMarkWorker(p *p)` から `func gcBgMarkWorker(_p_ *p)` に変更され、引数名がシャドウイングを避けるために変更されています。
*   `parkInfo` という新しい構造体が導入され、`m`（Mへのポインタ）と `attach`（アタッチ先のPへのポインタ）を保持します。
*   `gopark` の呼び出し方が変更され、`releasem(mp)` の代わりに `park.m` を解放し、Pへのアタッチ処理が `gopark` のコールバック関数内に移動されました。
*   `p.gcBgMarkWorker` へのワーカーGのアタッチ処理が、`gopark` のコールバック内の `if park.attach != nil` ブロック内に移動されました。
*   `acquirem()` の呼び出しと `releasem()` の呼び出しのタイミングが調整され、`parkInfo` 構造体のフィールドとしてMが管理されるようになりました。
*   `_p_.gcMarkWorkerMode` など、引数として渡されたPを参照する箇所が、新しい引数名 `_p_` を使用するように変更されました。

`src/runtime/proc.go` では、`procresize` 関数内で `p.gcBgMarkWorker = nil` の行にコメントが追加され、この代入がワールドストップ中に発生するため競合しないことが明記されています。

## コアとなるコードの解説

### `parkInfo` 構造体

```go
type parkInfo struct {
	m      *m // Release this m on park.
	attach *p // If non-nil, attach to this p on park.
}
var park parkInfo
```
`parkInfo` 構造体は、`gopark` のコールバックに渡すための情報をカプセル化します。`m` フィールドは、ゴルーチンが停止する際に解放すべきMを保持し、`attach` フィールドは、ゴルーチンが停止した後にアタッチすべきPを保持します。これにより、`gopark` のコールバック内で必要なコンテキストを安全に利用できます。

### `gopark` のコールバック内の変更

```go
gopark(func(g *g, parkp unsafe.Pointer) bool {
	park := (*parkInfo)(parkp)

	// The worker G is no longer running, so it's
	// now safe to allow preemption.
	releasem(park.m)

	// If the worker isn't attached to its P,
	// attach now. During initialization and after
	// a phase change, the worker may have been
	// running on a different P. As soon as we
	// attach, the owner P may schedule the
	// worker, so this must be done after the G is
	// stopped.
	if park.attach != nil {
		p := park.attach
		park.attach = nil
		// cas the worker because we may be
		// racing with a new worker starting
		// on this P.
		if !casgp(&p.gcBgMarkWorker, nil, g) {
			// The P got a new worker.
			// Exit this worker.
			return false
		}
	}
	return true
}, noescape(unsafe.Pointer(&park)), "GC worker (idle)", traceEvGoBlock, 0)
```

この部分が変更の核心です。
1.  `gopark` のコールバック関数が、`parkInfo` 構造体へのポインタを受け取るように変更されました。
2.  コールバック内で、まず `releasem(park.m)` を呼び出して、現在ゴルーチンを実行していたMを解放します。これは、ゴルーチンが完全に停止したことを意味します。
3.  次に、`if park.attach != nil` の条件チェックが行われます。これは、このワーカーGが特定のPにアタッチする必要がある場合に真となります。
4.  `casgp(&p.gcBgMarkWorker, nil, g)` を使用して、アトミックにワーカーGをPにアタッチします。`casgp`（Compare And Swap for Goroutine Pointer）は、`p.gcBgMarkWorker`が`nil`であれば、現在のゴルーチン`g`をそこに設定します。これは、他のワーカーがすでにこのPにアタッチしている可能性との競合を避けるためです。
5.  もしアタッチに失敗した場合（つまり、別のワーカーがすでにPにアタッチしていた場合）、現在のワーカーは終了します（`return false`）。

この変更により、Pへのアタッチはゴルーチンが完全に停止した後にのみ行われるため、ワーカーGが二重に実行されるという競合状態が解消されます。

### `acquirem` と `releasem` の管理

以前は `mp := acquirem()` と `releasem(mp)` が直接 `gcBgMarkWorker` 関数内で管理されていましたが、変更後は `park.m = acquirem()` と `releasem(park.m)` のように、`parkInfo` 構造体を介してMの取得と解放が管理されるようになりました。これにより、Mのライフサイクルが`gopark`のコールバックとより密接に連携し、安全性が向上しています。

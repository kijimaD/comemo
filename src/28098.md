# [インデックス 28098] ファイルの概要

このコミットは、Goランタイムにおけるシグナルハンドリングの挙動、特にLinux上での`SIGSYS`シグナルに対する処理の変更と、FreeBSDにおける`SIGSYS`シグナルテーブルへの参照追加に関するものです。Goランタイムがシステムコールに関連するシグナルをどのように扱うかという、低レベルな動作に影響を与えます。

## 元コミット内容

Goランタイムにおいて、Linux上の`SIGSYS`シグナルに対する`_SigUnblock`フラグを削除します。これは、以前の変更（`https://go-review.googlesource.com/22202`）で`SIGSYS`に`_SigUnblock`フラグが追加されたものの、`SIGSYS`がランタイムにとってアンブロックされるべきシグナルであるかについて明確な合意がなかったためです。この変更は、ランタイムのシグナルハンドリングの一貫性を保つために行われます。また、FreeBSDのランタイムシグナルテーブルに`#15204`への参照を追加します。このコミットは`#15204`を更新します。

## 変更の背景

この変更の背景には、Goランタイムがシステムコールに関連するシグナル（特に`SIGSYS`）をどのように扱うべきかという議論があります。

元々、`https://go-review.googlesource.com/22202`の変更で、Linuxの`SIGSYS`シグナルに`_SigUnblock`フラグが追加されました。`_SigUnblock`フラグは、シグナルがブロックされていても、そのシグナルが発生した際にブロックを解除してハンドラを実行させるためのものです。しかし、`SIGSYS`がGoランタイムにとって本当にアンブロックされるべきシグナルなのかどうかについて、明確なコンセンサスが得られていませんでした。

`SIGSYS`は、プログラムが不正なシステムコールを試みた際にカーネルによって送信されるシグナルです。例えば、`seccomp`（secure computing mode）のようなセキュリティ機構が有効になっている環境で、許可されていないシステムコールが呼び出された場合に発生することがあります。Goランタイムがこのようなシグナルをどのように扱うかは、プログラムの安定性やセキュリティに影響を与える可能性があります。

このコミットは、`SIGSYS`の`_SigUnblock`フラグを削除することで、Linux上でのシグナルハンドリングの一貫性を確保しようとしています。つまり、`SIGSYS`は他の多くのシグナルと同様に、デフォルトではブロックされ得るシグナルとして扱われるようになります。

また、FreeBSDのシグナルテーブルに`#15204`への参照が追加されたのは、このイシューが`SIGSYS`シグナルの挙動、特に`seccomp`との関連性について議論しているためです。この参照は、将来的に`SIGSYS`のハンドリングに関する決定が下された際に、関連する議論を追跡しやすくするためのものです。

## 前提知識の解説

### シグナル (Signals)
Unix系OSにおけるシグナルは、プロセスに対して非同期的にイベントを通知するソフトウェア割り込みの一種です。例えば、プログラムの異常終了（`SIGSEGV`）、外部からの終了要求（`SIGTERM`）、子プロセスの終了（`SIGCHLD`）など、様々なイベントを通知するために使用されます。

### シグナルハンドリング
プロセスは、特定のシグナルを受信した際に実行する「シグナルハンドラ」を登録できます。シグナルハンドラは、シグナルを受信した際に通常のプログラム実行を中断し、登録された関数を実行します。シグナルハンドラが実行されている間、他のシグナルがブロックされることがあります。

### シグナルマスク (Signal Mask)
各プロセスは「シグナルマスク」と呼ばれるビットマスクを持っており、これは現在ブロックされているシグナルのセットを示します。ブロックされたシグナルは、発生してもすぐに配送されず、シグナルマスクから解除されるまで保留されます。

### `SIGSYS` シグナル
`SIGSYS` (Signal System Call) は、プロセスが不正なシステムコールを試みた際に発生するシグナルです。これは、存在しないシステムコール番号を呼び出したり、`seccomp`などのセキュリティポリシーによって特定のシステムコールが禁止されている場合に発生します。

### `seccomp` (Secure Computing Mode)
`seccomp`はLinuxカーネルのセキュリティ機能で、プロセスが実行できるシステムコールを制限するために使用されます。これにより、攻撃者が脆弱性を悪用して任意のシステムコールを実行するのを防ぎ、攻撃対象領域を減らすことができます。`seccomp`ポリシーに違反するシステムコールが呼び出されると、通常は`SIGSYS`シグナルが送信されるか、プロセスが終了します。

### Goランタイムのシグナルハンドリング
Goランタイムは、ガベージコレクション、スケジューリング、デバッグなどの内部処理のために、独自のシグナルハンドリングメカニズムを持っています。GoプログラムがOSからシグナルを受信すると、Goランタイムがそれを捕捉し、Goの`os/signal`パッケージを通じてGoルーチンに配送したり、内部的に処理したりします。

### `_SigUnblock` フラグ
Goランタイムのシグナルテーブルにおける`_SigUnblock`フラグは、特定のシグナルが受信された際に、そのシグナルがシグナルマスクによってブロックされていたとしても、一時的にブロックを解除してハンドラを実行させるべきであることを示す内部フラグです。これは、重要なシグナルがランタイムの内部処理によってブロックされ、処理が遅延するのを防ぐために使用されることがあります。

### `sigTabT` 構造体
Goランタイムの内部では、各シグナルに関する情報（シグナル番号、デフォルトの挙動、説明など）を格納するための`sigTabT`のような構造体が定義されています。この構造体には、シグナルの挙動を制御するためのフラグ（例: `_SigPanic`, `_SigNotify`, `_SigThrow`, `_SigUnblock`）が含まれています。

*   `_SigPanic`: このシグナルを受信するとGoランタイムがパニックを起こすことを示す。
*   `_SigNotify`: このシグナルが`os/signal`パッケージを通じてGoルーチンに通知されることを示す。
*   `_SigThrow`: このシグナルを受信するとGoランタイムが致命的なエラーとして扱い、プログラムを終了させることを示す。

## 技術的詳細

このコミットは、Goランタイムが内部的に管理するシグナルテーブルの定義を変更しています。具体的には、Linuxアーキテクチャ向けのシグナルテーブル（`sigtab_linux_generic.go`と`sigtab_linux_mips64x.go`）から、`SIGSYS`シグナルに関連付けられていた`_SigUnblock`フラグを削除しています。

以前の変更で`SIGSYS`に`_SigUnblock`が追加されたのは、おそらく`seccomp`などのセキュリティ機能が有効な環境で`SIGSYS`が頻繁に発生する可能性があり、その際にGoランタイムが適切に反応できるようにするためだったと考えられます。しかし、`_SigUnblock`フラグは、シグナルがブロックされている状態でも強制的にハンドラを実行させるため、ランタイムのシグナルハンドリングロジックを複雑にする可能性があります。

このコミットの意図は、`SIGSYS`が他の一般的なシグナルと同様に、デフォルトのシグナルマスクの挙動に従うようにすることです。つまり、`SIGSYS`がブロックされている場合は、ブロックが解除されるまで配送が保留されることになります。これにより、Goランタイムのシグナルハンドリングの一貫性が向上し、特定のシグナルに対する特別な処理を減らすことができます。

また、FreeBSD向けの`signal_freebsd.go`ファイルでは、`SIGSYS`のエントリに`// see golang.org/issues/15204`というコメントが追加されています。これは、`SIGSYS`の挙動に関する議論や決定が`issue #15204`で行われていることを示しており、将来的な変更や理解のために重要な参照情報となります。このイシューは、`seccomp`と`SIGSYS`の相互作用、およびGoプログラムが`seccomp`環境でどのように動作すべきかについて議論している可能性が高いです。

この変更は、Goランタイムの低レベルな部分に影響を与えますが、ほとんどのGoアプリケーション開発者にとっては直接的な影響はありません。しかし、`seccomp`のような高度なセキュリティ機能を使用する環境でGoプログラムをデプロイする場合や、Goランタイムの内部動作を深く理解する必要がある場合には、この変更が重要になる可能性があります。

## コアとなるコードの解説

### `src/runtime/signal_freebsd.go` の変更

FreeBSD向けのシグナルテーブルでは、`SIGSYS`のエントリは元々`{_SigNotify, "SIGSYS: bad system call"}`でした。このコミットでは、この行に`// see golang.org/issues/15204`というコメントが追加されています。

*   **変更前**: `/* 12 */ {_SigNotify, "SIGSYS: bad system call"},`
*   **変更後**: `/* 12 */ {_SigNotify, "SIGSYS: bad system call"}, // see golang.org/issues/15204`

この変更は、`SIGSYS`の挙動自体を変更するものではなく、関連する議論や背景情報への参照を提供することを目的としています。`_SigNotify`フラグは、このシグナルが`os/signal`パッケージを通じてGoルーチンに通知されることを意味します。

### `src/runtime/sigtab_linux_generic.go` および `src/runtime/sigtab_linux_mips64x.go` の変更

これらのファイルは、それぞれ一般的なLinuxアーキテクチャとMIPS64/MIPS64LEアーキテクチャ向けのシグナルテーブルを定義しています。両方のファイルで、`SIGSYS`シグナルに対応するエントリから`_SigUnblock`フラグが削除されています。

*   **変更前 (Linux generic)**: `/* 31 */ {_SigThrow + _SigUnblock, "SIGSYS: bad system call"},`
*   **変更後 (Linux generic)**: `/* 31 */ {_SigThrow, "SIGSYS: bad system call"},`

*   **変更前 (Linux MIPS64x)**: `/* 12 */ {_SigThrow + _SigUnblock, "SIGSYS: bad system call"},`
*   **変更後 (Linux MIPS64x)**: `/* 12 */ {_SigThrow, "SIGSYS: bad system call"},`

ここで重要なのは、`_SigUnblock`フラグの削除です。
*   **`_SigThrow`**: このフラグは、`SIGSYS`を受信した際にGoランタイムが致命的なエラーとして扱い、プログラムを終了させることを示します。これは、不正なシステムコールが検出された場合にプログラムが安全に停止するための一般的な挙動です。
*   **`_SigUnblock`の削除**: 以前は`_SigUnblock`フラグが存在したため、`SIGSYS`がシグナルマスクによってブロックされていたとしても、このシグナルが発生した際には一時的にブロックが解除され、`_SigThrow`ハンドラが実行される可能性がありました。`_SigUnblock`が削除されたことで、`SIGSYS`は他の通常のシグナルと同様に、シグナルマスクによってブロックされている場合は配送が保留されるようになります。これにより、シグナルハンドリングの挙動がより予測可能になり、一貫性が保たれます。

この変更は、Goランタイムが`SIGSYS`を特別扱いせず、標準的なシグナル配送メカニズムに従うように調整されたことを意味します。これは、`SIGSYS`が常に即座に処理される必要はない、あるいはそのように処理することがランタイムの他の部分との間で不整合を生む可能性がある、という判断に基づいていると考えられます。

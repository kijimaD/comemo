このコミットは、「runtime: fix incorrect comment」（ランタイム: 不正確なコメントを修正）というタイトルで、Goランタイムの `src/runtime/mbitmap.go` ファイル内のコメントが誤っていたため修正したものです。具体的には、ヒープビットマップのシフト値に関する記述が、過去の設計（ビットマップがヒープデータとインターリーブされていた時期）の名残であり、現在の設計（シフト値が0, 1, 2, 3）に合わせて修正されたことを示しています。

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープ上のオブジェクトがポインタを含むかどうかを効率的に判断するためにヒープビットマップを使用します。このビットマップは、GCがオブジェクトグラフを辿り、到達可能なオブジェクトをマークするために不可欠なメタデータを提供します。

過去のGoランタイムでは、ヒープビットマップの構造が現在とは異なり、ビットマップ情報がヒープデータ自体とインターリーブ（混在）して格納されていた時期がありました。このような設計では、特定のメモリワードに対応するビットマップ情報を取得するための `h.shift` の値が、例えば `0, 2, 4, 6` のように設定されていた可能性があります。これは、各メモリワードに対して複数のビット（例えば4ビット）が割り当てられていた場合に考えられます。

しかし、このコミットが作成された時点では、ヒープビットマップの設計は変更されており、ビットマップはヒープデータとは別に `heapArena` メタデータに格納されるようになっていました。この新しい設計では、各ポインタサイズのワードに対して2ビットが割り当てられ、`h.shift` の値は `0, 1, 2, 3` の範囲で使われるようになっていました。

この設計変更にもかかわらず、`src/runtime/mbitmap.go` 内のコメントの一部が古い設計の記述のまま残っていました。この古いコメントは、コードの実際の動作と一致せず、開発者がコードを理解する上で混乱を招く可能性がありました。したがって、このコミットは、コードのコメントを現在の実装と整合させるためのクリーンアップであり、コードの正確性を高めることを目的としています。

## 前提知識の解説

### Goのガベージコレクタ (GC)

Goのガベージコレクタは、主に以下の特徴を持つ並行性のマーク＆スイープアルゴリズムを採用しています。

*   **並行性 (Concurrent)**: GCの大部分は、アプリケーションの実行と並行して動作します。これにより、「Stop-The-World (STW)」と呼ばれるアプリケーションの一時停止時間を最小限に抑え、レイテンシを低減します。
*   **非世代性 (Non-generational)**: 多くのGCとは異なり、GoのGCはオブジェクトの生存期間に基づいて世代を区別しません。すべてのヒープオブジェクトは均一に扱われます。
*   **非圧縮性 (Non-compacting)**: GoのGCは、ガベージコレクション中にヒープ上のオブジェクトを移動（圧縮）しません。これにより、オブジェクト参照の更新に伴うオーバーヘッドが回避されますが、メモリの断片化が発生する可能性があります。
*   **マーク＆スイープ (Mark-and-Sweep)**: GCは、まずルートオブジェクト（グローバル変数、スタックからの参照など）から到達可能なすべてのオブジェクトを「マーク」します。このプロセスでは、三色マーキング（白、灰、黒）が用いられます。マーキングフェーズの完了後、マークされなかったオブジェクト（白）は到達不可能と判断され、「スイープ」フェーズでメモリが解放されます。

GCがヒープ上の到達可能なオブジェクトを特定するためには、どのメモリワードがポインタであるかを正確に知る必要があります。この情報がなければ、GCはオブジェクトグラフを正しく辿ることができません。

### ヒープビットマップ (Heap Bitmap)

ヒープビットマップは、GoのGCがヒープ上のメモリワードがポインタであるか否かを効率的に識別するための重要なデータ構造です。

*   **目的**: GCは、ヒープ上のオブジェクトをスキャンする際に、どのフィールドがポインタであり、どのフィールドが非ポインタデータであるかを区別する必要があります。すべてのオブジェクトのすべてのフィールドを動的に検査することは非常に非効率的です。ヒープビットマップは、このポインタ情報を事前にエンコードされたメタデータとして提供します。
*   **構造**: Goのヒープは「スパン (spans)」と呼ばれる連続したメモリブロックに分割されます。各スパンは、特定のサイズのオブジェクトを格納するために使用されます。ヒープビットマップは、これらのスパン内の各メモリワード（通常は8バイト）に対応するビット（または複数ビット）を持ちます。
    *   Goのヒープビットマップは、各ポインタサイズのワードに対して2ビットを使用します。これらの2ビットのエントリは、`heapArena` メタデータに格納されます。
    *   下位ビットは、そのワードがGC中に訪問されるべきライブポインタであるかどうかを示します。
    *   上位ビットは、そのワードが属するオブジェクト内の位置によって異なる意味を持ちます。例えば、`00` はオブジェクトの記述が終了したことを示す「デッド」エンコーディングとして機能することがあります。
*   **利点**: ヒープビットマップを使用することで、GCは高速にポインタを識別し、オブジェクトグラフを効率的にトラバースできます。

### `h.shift` の役割

`heapBits` 構造体は、ヒープビットマップ内の特定の場所を指し示すためのコンテキストを提供します。この構造体に含まれる `shift` フィールドは、ヒープビットマップ内で特定のメモリワードに対応するビット情報を取得するためのオフセットとして機能します。

`h.shift` の値は、ビットマップがどのようにメモリワードにマッピングされているか、そしてビットマップ情報がどのようにパックされて格納されているかに依存します。Goのヒープビットマップが各ポインタサイズのワードに対して2ビットを使用していることを考慮すると、`uint32` のようなデータ型（32ビット）内に複数のワードのビットマップ情報がパックされて格納されている可能性があります。この場合、`h.shift` は、`uint32` から目的のワードに対応する2ビットの情報を抽出するために、右シフト演算の量として使用されます。

## 技術的詳細

`src/runtime/mbitmap.go` ファイルは、Goランタイムにおけるヒープビットマップの管理と操作に関する主要なロジックを実装しています。このファイルには、`heapBits` 構造体とそのメソッドが含まれており、これらはGCがヒープをスキャンする際にビットマップ情報を解釈するために使用されます。

`heapBits` 構造体は、ヒープビットマップ内の特定のメモリ位置を効率的に参照するための抽象化を提供します。これには、現在のビットマップのポインタ (`bitp`) と、そのポインタが指す `uint32` 値内のどの位置からビット情報を読み取るべきかを示す `shift` 値が含まれます。

`hasPointers` 関数は、特定のオブジェクトがポインタを含んでいるかどうかを判断するために使用されます。この関数は、オブジェクトのサイズとアライメントに基づいて、そのオブジェクトの先頭部分がポインタを含む可能性があるかをチェックします。コミットで変更された行は、この `hasPointers` 関数内にあります。

```go
// Otherwise, at least a 2-word object, and at least 2-word aligned,
// so h.shift is either 0 or 2, so we know we can get the bits for the
// first two words out of *h.bitp.
// If either of the first two words is a pointer, not pointer free.
b := uint32(*h.bitp >> h.shift)
```

ここで重要なのは、`h.shift` の値が `0` または `2` であるというコメントです。これは、`uint32(*h.bitp >> h.shift)` という操作が、`*h.bitp` が指す `uint32` 値から、オブジェクトの最初の2ワード分のビットマップ情報を取得するために行われることを示唆しています。

Goのヒープビットマップは、各ポインタサイズのワードに対して2ビットを使用します。例えば、`uint32` は32ビットなので、最大で16ワード分のビットマップ情報（16ワード * 2ビット/ワード = 32ビット）をパックして格納できます。

*   `h.shift` が `0` の場合、`*h.bitp >> 0` は `uint32` の最下位2ビット（最初のワードのビットマップ情報）を取得するために使用されます。
*   `h.shift` が `2` の場合、`*h.bitp >> 2` は `uint32` の次の2ビット（2番目のワードのビットマップ情報）を取得するために使用されます。

このように、`h.shift` は、パックされたビットマップデータから特定のワードのポインタ情報を抽出するためのオフセットとして機能します。このメカニズムにより、GCはメモリを効率的にスキャンし、ポインタを迅速に識別することができます。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、`src/runtime/mbitmap.go` 内の `hasPointers` 関数における単一のコメント行の修正です。

変更前:
```go
// so h.shift is either 0 or 4, so we know we can get the bits for the
```

変更後:
```go
// so h.shift is either 0 or 2, so we know we can get the bits for the
```

この修正は、`h.shift` の取りうる値に関する記述を更新したものです。

*   **以前のコメント (`0 or 4`)**: この記述は、おそらくヒープビットマップがヒープデータとインターリーブされていた古い設計の名残です。その設計では、各ポインタワードに対して4ビット（またはそれ以上）が割り当てられていた可能性があり、`h.shift` が `0, 4, 8, ...` のように4の倍数で増加していたことを示唆しています。
*   **新しいコメント (`0 or 2`)**: これは、現在のGoランタイムのヒープビットマップの設計を正確に反映しています。現在の設計では、各ポインタサイズのワードに対して2ビットが割り当てられています。したがって、`uint32` のようなデータ型から特定のワードの2ビット情報を抽出するために、`h.shift` は `0`（最初のワードの2ビット）または `2`（2番目のワードの2ビット）のいずれかになります。これは、`uint32(*h.bitp >> h.shift)` という操作で、`*h.bitp` が指す `uint32` 値から、オブジェクトの最初の2ワード分のビットマップ情報（それぞれ2ビット）を取得する際に、`h.shift` が `0` または `2` のいずれかになることを意味します。

この修正は、コードの動作自体には一切影響を与えません。単に、コードのコメントが現在の実装と一致するように更新されたものであり、Goランタイムのメモリ管理に関するドキュメントとしての正確性を向上させています。これにより、将来のGo開発者が `mbitmap.go` のコードを理解する際の混乱が解消されます。

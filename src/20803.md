## 変更の背景

このコミットの主な目的は、Goランタイムのガベージコレクタ（GC）のポーズ時間を短縮することです。コミットメッセージには「Lowers gc pause time by 5-10% on test/bench/garbage」と明記されており、`test/bench/garbage` ベンチマークにおいてGCポーズ時間が5〜10%削減される効果があったことが示されています。

GoのGCは、アプリケーションの実行中に不要になったメモリを自動的に解放する重要なコンポーネントです。しかし、GCが動作する際には、アプリケーションの実行が一時的に停止する「ポーズ時間」が発生することがあります。このポーズ時間が長くなると、アプリケーションの応答性やスループットに悪影響を与える可能性があります。特に、リアルタイム性の高いサービスや低レイテンシが求められるアプリケーションでは、GCポーズ時間の短縮が非常に重要となります。

`scanblock` 関数は、GCのマークフェーズにおいて、メモリブロック内のポインタをスキャンし、到達可能なオブジェクトをマークする役割を担っています。この関数はGCの実行パスにおいて頻繁に呼び出されるため、ここでのわずかな最適化がGC全体のパフォーマンス、特にポーズ時間の短縮に大きく寄与します。このコミットは、`scanblock` 関数内の特定の処理をより効率的にすることで、GCのオーバーヘッドを削減し、結果としてポーズ時間を短縮することを目指しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムおよびガベージコレクションに関する前提知識が必要です。

1.  **Goのガベージコレクタ (GC)**:
    GoのGCは、主に「三色マーク＆スイープ（Tri-color Mark-and-Sweep）」アルゴリズムをベースにしています。これは、オブジェクトを白（未訪問）、灰（訪問済みだが子を未スキャン）、黒（訪問済みで子もスキャン済み）の3色に分類し、到達可能なオブジェクトをマークしていく方式です。GCサイクルは主に以下のフェーズで構成されます。
    *   **マークフェーズ**: ルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークします。このフェーズ中に `scanblock` が重要な役割を果たします。
    *   **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトのメモリを解放します。
    *   **STW (Stop The World)**: GCの特定のフェーズ（特にマークの開始時や終了時）では、アプリケーションの実行を一時的に完全に停止させる必要があります。これが「GCポーズ時間」として知られるものです。GoのGCは、このSTW時間を最小限に抑えるように設計されています。

2.  **`scanblock` 関数**:
    `scanblock` は、GCのマークフェーズにおいて、特定のメモリブロック（ヒープ上のオブジェクトやスタックフレームなど）をスキャンし、その中に含まれるポインタを識別して、それらが指すオブジェクトをマークキューに追加する役割を担います。この関数は、メモリブロックのレイアウト情報（ポインタがどこにあるかを示すビットマップ）を利用して、効率的にポインタを特定します。

3.  **ポインタマスク/GCビットマップ**:
    Goのランタイムは、各オブジェクトの型情報に基づいて、そのオブジェクト内のどのオフセットにポインタが含まれているかを示す「ポインタマスク」または「GCビットマップ」を生成します。`scanblock` 関数は、このビットマップを参照して、メモリブロック内のどの部分がポインタであるかを判断し、そのポインタが指すオブジェクトをGCの対象として処理します。

4.  **`arena_start` と `arena_used`**:
    これらはGoのヒープメモリ管理に関連するグローバル変数です。
    *   `arena_start`: ヒープ領域の開始アドレスを示します。
    *   `arena_used`: 現在使用されているヒープ領域の終了アドレス（またはその少し先）を示します。
    `scanblock` は、スキャン中のポインタが有効なヒープ領域内を指しているかどうかをこれらの変数を使ってチェックします。

5.  **`PhysPageSize`**:
    物理メモリページのサイズ（通常は4KBなど）を示す定数です。ポインタが非常に小さいアドレス（例えばNULLポインタや、物理ページサイズよりも小さいアドレス）を指している場合、それは有効なヒープオブジェクトではない可能性が高いため、特別なチェックが行われます。

6.  **`PtrSize`**:
    ポインタのサイズ（32ビットシステムでは4バイト、64ビットシステムでは8バイト）を示す定数です。メモリのアドレス計算やオフセット計算に用いられます。

7.  **`wordsPerBitmapByte`**:
    GCビットマップの1バイトが何ワード（`PtrSize`の倍数）に対応するかを示す定数です。この値は、ビットマップからポインタ情報を効率的に抽出するために使用されます。

8.  **`gcBits`**:
    GCビットマップ内で、1つのポインタに関する情報が何ビットで表現されるかを示す定数です。

9.  **`bitBoundary` と `BitsMask`**:
    GCビットマップ内で、オブジェクトの境界を示すビットや、ポインタ情報自体を抽出するためのマスクです。

10. **`scanbuf` (スキャンバッファ)**:
    `scanblock` 関数内で使用される一時的なバッファで、スキャン中に見つかったポインタを一時的に格納するために使用されます。これは、GCがポインタを処理する際のキューのような役割を果たします。

## 技術的詳細

このコミットでは、`src/runtime/mgc0.c` 内の `scanblock` 関数に対して、主に以下の3つの領域で最適化が行われています。

1.  **`scanbufpos` のインクリメントとラップアラウンドの最適化**:
    `scanbuf` はGCがスキャンするオブジェクトを一時的に保持する循環バッファです。以前のコードでは、`scanbufpos`（バッファ内の現在の位置）がバッファの終端に達した際に `if(scanbufpos == nelem(scanbuf)) scanbufpos = 0;` という条件分岐を使って0にリセットしていました。
    このコミットでは、これを `scanbufpos %= nelem(scanbuf);` という剰余演算に置き換えています。剰余演算は、特にコンパイラが最適化できる場合、条件分岐よりも効率的になることがあります。これにより、バッファのインデックス計算がよりスムーズになり、GCのオーバーヘッドがわずかに削減されます。

2.  **GCビットマップのポインタ情報抽出の最適化**:
    `scanblock` は、メモリブロック内のポインタを識別するためにGCビットマップを使用します。このビットマップは、メモリ上のオブジェクトのどこにポインタがあるかを示す情報を含んでいます。以前のコードでは、`ptrbitp`（現在のビットマップバイトへのポインタ）と `bits`（ビットマップから読み取った値）を使ってポインタ情報を抽出していました。
    変更前は、`((uintptr)b+i)%(PtrSize*wordsPerBitmapByte)) != 0` という複雑な条件分岐を使って `ptrbitp` をデクリメントし、`bits` をシフトしていました。これは、現在のスキャン位置がビットマップの新しいバイトの開始点にあるかどうかを判断するためのものでした。
    このコミットでは、このロジックを `j = ((uintptr)b+i)/PtrSize & 1;` と `ptrbitp -= j;`、`bits >>= gcBits*j;` に変更しています。
    *   `j = ((uintptr)b+i)/PtrSize & 1;`: これは、現在のスキャン位置 `(uintptr)b+i` が `PtrSize` の倍数で、かつ `wordsPerBitmapByte` の境界を越えたかどうかを効率的に判断するためのものです。`& 1` は、結果が偶数か奇数か（つまり、現在のワードがビットマップのどの部分に属するか）を判断します。
    *   `ptrbitp -= j;`: `j` の値に基づいて `ptrbitp` を適切にデクリメントします。
    *   `bits >>= gcBits*j;`: `j` の値に基づいて `bits` をシフトし、正しいポインタ情報を抽出します。
    さらに、`if(wordsPerBitmapByte != 2) runtime·throw("alg doesn't work for wordsPerBitmapByte != 2");` というチェックが追加されています。これは、この新しい最適化されたアルゴリズムが `wordsPerBitmapByte` が2である場合にのみ正しく機能することを保証するためのものです。この変更は、ビットマップの走査ロジックを簡素化し、より高速にポインタ情報を取得できるようにすることで、GCのパフォーマンスを向上させます。

3.  **ポインタのヒープ範囲チェックのロジック変更**:
    `scanblock` は、スキャン中に見つかったポインタが有効なヒープ領域内を指しているかどうかを検証します。以前のコードでは、`if((uintptr)obj < PhysPageSize)` と `if(obj < arena_start || obj >= arena_used)` の2つの独立したチェックがありました。
    このコミットでは、これらのチェックの順序と構造を変更し、`if(obj < arena_start || obj >= arena_used)` のブロック内に `if((uintptr)obj < PhysPageSize)` をネストしています。
    *   変更前:
        ```c
        if(obj == nil)
            continue;
        if((uintptr)obj < PhysPageSize) {
            s = nil;
            goto badobj;
        }
        if(obj < arena_start || obj >= arena_used)
            continue;
        ```
    *   変更後:
        ```c
        if(obj == nil)
            continue;
        if(obj < arena_start || obj >= arena_used) {
            if((uintptr)obj < PhysPageSize) {
                s = nil;
                goto badobj;
            }
            continue;
        }
        ```
    この変更は、論理的なフローを改善し、より効率的なチェック順序を実現している可能性があります。通常、`obj < arena_start || obj >= arena_used` のチェックは、ポインタがヒープの有効な範囲外にあるかどうかを判断するための主要なチェックです。その中で、特に非常に小さいアドレス（`PhysPageSize` 未満）を指すポインタは、NULLポインタや不正なアドレスである可能性が高いため、特別なエラー処理（`goto badobj`）を行うようにしています。この再編成により、一般的なケースでのチェックパスが短縮され、パフォーマンスが向上する可能性があります。

これらの最適化は、それぞれがGCのポーズ時間をわずかに短縮する効果を持ち、それらが組み合わさることで、全体として5〜10%の改善という結果をもたらしています。

## コアとなるコードの解説

上記の差分は、`scanblock` 関数内の3つの主要な最適化ポイントを示しています。

1.  **`scanbufpos` の循環インデックス計算の簡素化**:
    *   **変更前**:
        ```c
        if(scanbufpos == nelem(scanbuf))
            scanbufpos = 0;
        ```
    *   **変更後**:
        ```c
        scanbufpos %= nelem(scanbuf);
        ```
    この変更は、`scanbuf` というスキャンバッファのインデックス `scanbufpos` を更新する際に、バッファの終端に達した場合に0に戻すロジックを簡素化しています。`nelem(scanbuf)` はバッファの要素数です。剰余演算子 `%` を使用することで、`if` 文による条件分岐をなくし、常に `scanbufpos` が `0` から `nelem(scanbuf) - 1` の範囲に収まるようにしています。これは、CPUの分岐予測ミスを減らし、より効率的なコード生成を可能にする可能性があります。この変更は、`scanblock` 関数内で2箇所（行218-219と行445-446）に適用されています。

2.  **GCビットマップからのポインタ情報抽出ロジックの最適化**:
    *   **変更前**:
        ```c
        if((((uintptr)b+i)%(PtrSize*wordsPerBitmapByte)) != 0) {
            ptrbitp--;
            bits >>= gcBits;
        }
        ```
    *   **変更後**:
        ```c
        if(wordsPerBitmapByte != 2)
            runtime·throw("alg doesn't work for wordsPerBitmapByte != 2");
        j = ((uintptr)b+i)/PtrSize & 1;
        ptrbitp -= j;
        bits >>= gcBits*j;
        ```
    この変更は、GCビットマップからポインタの情報を読み取る際のロジックを改善しています。
    `ptrbitp` は現在のビットマップバイトを指すポインタで、`bits` はそこから読み取られたビット情報です。
    変更前は、現在のスキャン位置 `(uintptr)b+i` が `PtrSize*wordsPerBitmapByte` の境界にあるかどうかを剰余演算でチェックし、それに基づいて `ptrbitp` をデクリメントし、`bits` をシフトしていました。
    変更後は、`j = ((uintptr)b+i)/PtrSize & 1;` という計算を導入しています。これは、現在のスキャン位置が `PtrSize` の倍数で、かつビットマップのどの「ワード」に属するか（例えば、`wordsPerBitmapByte` が2の場合、0番目のワードか1番目のワードか）を効率的に判断するためのものです。`j` の値（0または1）に基づいて `ptrbitp` をデクリメントし、`bits` をシフトすることで、より直接的かつ効率的に正しいポインタ情報を抽出しています。
    `if(wordsPerBitmapByte != 2)` のチェックは、この新しいアルゴリズムが `wordsPerBitmapByte` が2であるという特定の前提に依存していることを示しており、それ以外の値の場合はランタイムエラーを発生させます。これは、この最適化が特定のGCビットマップのレイアウトに特化していることを意味します。この変更は、`scanblock` 関数内で2箇所（行270-273と行296-299）に適用されています。

3.  **ポインタのヒープ範囲チェックのロジック再編成**:
    *   **変更前**:
        ```c
        if((uintptr)obj < PhysPageSize) {
            s = nil;
            goto badobj;
        }
        if(obj < arena_start || obj >= arena_used)
            continue;
        ```
    *   **変更後**:
        ```c
        if(obj < arena_start || obj >= arena_used) {
            if((uintptr)obj < PhysPageSize) {
                s = nil;
                goto badobj;
            }
            continue;
        }
        ```
    この変更は、スキャンされたポインタ `obj` が有効なヒープ領域を指しているかどうかのチェックの順序と構造を調整しています。
    変更前は、まず `PhysPageSize` 未満の非常に小さいアドレスをチェックし、次にヒープの範囲外かどうかをチェックしていました。
    変更後は、まず `obj < arena_start || obj >= arena_used` という、ポインタがヒープの有効な範囲内にあるかどうかの主要なチェックを行います。もしポインタがヒープの範囲外であれば、そのブロック内でさらに `(uintptr)obj < PhysPageSize` のチェックを行います。これは、NULLポインタや非常に小さい不正なアドレスを指すポインタに対する特別なエラー処理（`goto badobj`）を、ヒープ範囲外のチェックのサブケースとして扱うことで、ロジックの明確性と効率性を向上させている可能性があります。一般的な有効なヒープポインタの場合、`PhysPageSize` のチェックをスキップできるため、パスが短縮されます。

これらの変更は、GoのGCの最も頻繁に実行される部分の一つである `scanblock` 関数内のマイクロ最適化であり、GCのポーズ時間を削減し、全体的なアプリケーションのパフォーマンスを向上させることを目的としています。

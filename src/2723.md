# [インデックス 2723] ファイルの概要

このコミットは、Go言語の評価器（evaluator）における値の表現方法を根本的に変更するものです。具体的には、`Value`型が汎用的な値のコンテナとして機能するのではなく、常に「l-value」（代入可能なメモリ位置を指す値）を表現するように再定義されています。これにより、式評価の過程で型安全性が向上し、パフォーマンスが最適化されます。

    invoke a nil evaluator function during evaluation.  This also
    makes ideals and pointers really clean.

    because it doesn't require heap allocation for every
    intermediate value, type switches, or lots of conversions to
    and from Value.  It also involves fewer function calls.

## 元コミット内容

`Value`型を常にl-valueとして表現し、汎用的な値のコンテナとしては使用しないように変更。
汎用的な`Value`を返す単一の評価関数ではなく、各汎用型に対応する評価関数がネイティブ型を返すようにした。
これにより、評価時の型変換がほぼなくなり、nil評価関数が呼び出されることもなくなるため、コンパイラの型安全性が向上する。また、理想型（ideal types）とポインタの扱いが非常に明確になる。
さらに、中間値ごとにヒープ割り当て、型スイッチ、`Value`型との間の多数の変換が不要になるため、式評価が高速化される。関数呼び出しの回数も減少する。

## 変更の背景

このコミットの背景には、Go言語の初期の評価器設計におけるパフォーマンスと型安全性の課題がありました。以前の設計では、式の中間結果を表現するために単一の汎用的な`Value`インターフェースが使用されていました。このアプローチは柔軟性がある一方で、以下のような問題を引き起こしていました。

1.  **型変換のオーバーヘッド**: 汎用`Value`から具体的な型への変換が評価時に頻繁に発生し、これが性能ボトルネックとなっていました。
2.  **ヒープ割り当て**: すべての中間結果が`Value`インターフェースとしてヒープに割り当てられるため、ガベージコレクションの負荷が増大し、パフォーマンスが低下していました。
3.  **型スイッチの複雑さ**: 評価器のロジック内で`Value`の具体的な型を判別するために多数の型スイッチが必要となり、コードの複雑性と保守性が低下していました。
4.  **l-valueとr-valueの混同**: `Value`がl-value（メモリ位置）とr-value（純粋な値）の両方を表現できるため、コンパイラがどちらを扱っているのかを明確に区別するのが困難でした。特に、ポインタや代入可能な変数（l-value）の扱いが複雑になっていました。

これらの問題を解決し、評価器の効率と堅牢性を向上させるために、`Value`の役割をl-valueに特化させ、中間結果をネイティブ型で直接扱う新しい設計が導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **l-valueとr-value**:
    *   **l-value (locator value)**: メモリ上の特定の場所を指す式です。代入演算子の左側に置くことができ、そのメモリ位置に値を格納できます。例えば、変数名やポインタの逆参照結果などがl-valueです。
    *   **r-value (read value)**: メモリ上の場所を指すのではなく、純粋なデータ値を表す式です。代入演算子の右側に置くことができます。リテラル（例: `10`, `"hello"`）や計算結果などがr-valueです。
    Goの評価器において、変数の値を取得する際にはr-valueが必要ですが、変数に値を代入する際にはl-valueが必要です。この区別を明確にすることが、型安全性と効率性の向上に繋がります。

2.  **Go言語の評価器（Evaluator）**:
    Go言語のコンパイラやデバッガ、あるいはインタプリタのようなツールでは、プログラムの式を実際に計算し、その結果を得るための「評価器」が必要です。この評価器は、抽象構文木（AST）を走査し、各ノードに対応する操作を実行して最終的な値を導き出します。

3.  **抽象構文木（AST: Abstract Syntax Tree）**:
    ソースコードを解析して得られる、プログラムの構造を木構造で表現したものです。コンパイラはASTを基にコードの型チェック、最適化、コード生成などを行います。評価器もASTをトラバースして式を評価します。

4.  **理想型（Ideal Types）**:
    Go言語には、型付けされていない数値定数（例: `10`, `3.14`）が存在します。これらは「理想型」と呼ばれ、必要に応じて適切な型に変換されます。例えば、`var i int = 10` の場合、`10` は`int`型に変換されます。このコミットでは、`bignum`パッケージを使用して、これらの理想型を任意精度で扱うための変更が含まれています。

5.  **`bignum`パッケージ**:
    任意精度の整数（`bignum.Integer`）および有理数（`bignum.Rational`）を扱うためのパッケージです。Go言語の組み込み型では表現できない大きな数値や、浮動小数点数の精度問題を回避するために使用されます。理想型の計算に利用されます。

6.  **クロージャ（Closures）と関数ポインタ**:
    Goでは関数をファーストクラスオブジェクトとして扱え、変数に代入したり、関数の引数として渡したり、戻り値として返したりできます。このコミットでは、式評価ロジックをクロージャとして`exprCompiler`構造体に格納し、必要に応じて呼び出すことで、柔軟かつ効率的な評価を実現しています。

## 技術的詳細

このコミットの核心は、`usr/austin/eval/expr.go` 内の `exprCompiler` 構造体の変更にあります。

**`exprCompiler` 構造体の変更点**:

*   **汎用評価関数の廃止**: 以前は `f func (f *Frame) Value` という単一のフィールドで、任意の型の値を返す汎用的な評価関数を保持していました。これが削除されました。
*   **型特化型評価関数の導入**: 代わりに、以下の型に特化した評価関数が導入されました。
    *   `evalBool func (f *Frame) bool`
    *   `evalUint func (f *Frame) uint64`
    *   `evalInt func (f *Frame) int64`
    *   `evalIdealInt func () *bignum.Integer` (理想整数はフレームに依存しないため引数なし)
    *   `evalFloat func (f *Frame) float64`
    *   `evalIdealFloat func () *bignum.Rational` (理想浮動小数点数もフレームに依存しないため引数なし)
    *   `evalString func (f *Frame) string`
    *   `evalPtr func (f *Frame) Value` (ポインタは`Value`を返す)
*   **l-value評価関数の導入**: `evalAddr func (f *Frame) Value` が追加されました。これは、式の「アドレス」を評価し、その結果として代入可能な`Value`オブジェクト（l-value）を返します。これにより、式がアドレス可能かどうか（l-valueであるか）の判断が明確になります。
*   **`addressable` フラグの廃止**: 以前は `addressable bool` というフラグでアドレス可能性を管理していましたが、`evalAddr` 関数の有無でこれを表現するようになりました。

**評価ロジックの変更**:

*   **`genIdent` 関数**: 変数（`*Variable`）の評価ロジックを生成する新しい関数です。変数の型に応じて、対応する `evalBool`, `evalUint`, `evalInt` などの関数を `exprCompiler` に設定します。これにより、変数の値を取得する際に直接ネイティブ型を返すようになります。また、`evalAddr` も設定され、変数がl-valueであることを示します。
*   **`DoIdent` 関数**: 識別子（変数や定数）の処理において、`genIdent` を呼び出すように変更されました。定数（`*Constant`）の場合も、その型（理想整数、理想浮動小数点数）に応じて `evalIdealInt` や `evalIdealFloat` を直接設定します。
*   **リテラル値の処理**: `doIdealInt`, `DoIntLit`, `DoCharLit`, `DoFloatLit`, `doString`, `DoStringLit` などのリテラルを処理する関数も、汎用`Value`を生成する代わりに、対応する型特化型評価関数を直接設定するように変更されました。
*   **単項演算子 (`*`, `-`, `&`) の処理**:
    *   **`*` (逆参照)**: `genStarOp` 関数が導入され、ポインタの逆参照結果を型特化型評価関数として生成します。逆参照の結果はl-valueであるため、`evalAddr` も設定されます。
    *   **`-` (単項マイナス)**: `genUnaryOpNeg` 関数が導入され、オペランドの型に応じて適切な減算ロジックを型特化型評価関数として生成します。
    *   **`&` (アドレス取得)**: オペランドがアドレス可能であるかどうかのチェックが `v.evalAddr == nil` に変更され、`v.evalAddr` を利用してアドレスを取得するようになりました。
*   **型変換 (`convertTo`)**: 理想型から具体的な型への変換ロジックも、新しい型特化型評価関数を利用するように変更されました。変換後の結果も、対応する型特化型評価関数として `exprCompiler` に格納されます。
*   **二項演算子 (`+`, `-`, `/`) の処理**: `genBinOpAdd`, `genBinOpSub`, `genBinOpQuo` といった新しい関数が導入され、左右のオペランドの型に応じて、対応する型特化型評価関数を生成します。これにより、演算が直接ネイティブ型で行われるようになります。
*   **`Frame.Get` メソッドの追加**: `usr/austin/eval/scope.go` に `func (f *Frame) Get(s *Scope, index int) Value` が追加されました。これは、特定のスコープとインデックスに基づいて`Frame`から`Value`を取得するためのヘルパー関数です。ネストされたスコープの変数を効率的に検索するために使用されます。
*   **`CompileExpr` の変更**: 最終的に式をコンパイルする `CompileExpr` 関数は、`exprCompiler` が持つ型特化型評価関数の結果を、最終的な`Value`インターフェースにラップして返すように変更されました。これは、評価器の外部インターフェースとの互換性を保つためと考えられます。ただし、コメントには「これはまだ`Value`を汎用コンテナとして使用しており、各型の`value`メソッドの唯一のユーザーである。これを改善する方法を考える必要がある」とあり、さらなる改善の余地が示唆されています。

**パフォーマンスと型安全性への影響**:

*   **ヒープ割り当ての削減**: 中間結果がネイティブ型で直接扱われるため、`Value`インターフェースとしてのヒープ割り当てが大幅に削減されます。これにより、ガベージコレクションの頻度が減り、実行速度が向上します。
*   **型スイッチの削減**: 型特化型評価関数を使用することで、評価ロジック内の型スイッチが不要になり、コードが簡潔になり、実行時のオーバーヘッドも減少します。
*   **型安全性の向上**: 各評価関数が特定のネイティブ型を返すため、評価時の不必要な型変換が排除され、コンパイラの型安全性が強化されます。`log.Crashf` を用いた厳密な型チェックが導入されており、誤った型の評価関数が呼び出された場合には即座にクラッシュするようになっています。
*   **関数呼び出しの削減**: 汎用`Value`を介した間接的な呼び出しが減り、直接ネイティブ型を扱う関数が呼び出されるため、関数呼び出しのオーバーヘッドが減少します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに集中しています。

*   `usr/austin/eval/expr.go`: 式のコンパイルと評価ロジックの大部分が変更されています。`exprCompiler`構造体の定義、各種評価関数の追加、単項・二項演算子の処理、識別子やリテラルの処理が大きく書き換えられています。
*   `usr/austin/eval/decls.go`: `Frame`構造体に`Get`メソッドが追加され、変数の取得方法が変更されています。
*   `usr/austin/eval/scope.go`: `Frame`構造体の`Get`メソッドの実装が追加されています。
*   `usr/austin/eval/type.go`: `boolType`に`value`メソッドの宣言が追加されています。
*   `usr/austin/eval/value.go`: `boolType`に`value`メソッドの実装が追加され、`uintType`の`value`メソッドに関するコメントが更新されています。

特に、`usr/austin/eval/expr.go` の `exprCompiler` 構造体の定義と、それに付随する `genIdent`, `genStarOp`, `genUnaryOpNeg`, `genBinOpAdd`, `genBinOpSub`, `genBinOpQuo` などの新しい評価関数生成ロジックがこの変更の心臓部です。

## コアとなるコードの解説

### `usr/austin/eval/expr.go` の `exprCompiler` 構造体

```go
type exprCompiler struct {
	*exprContext;
	pos token.Position;
	t Type;
	// Evaluate this node as the given type.
	evalBool func (f *Frame) bool;
	evalUint func (f *Frame) uint64;
	evalInt func (f *Frame) int64;
	evalIdealInt func () *bignum.Integer;
	evalFloat func (f *Frame) float64;
	evalIdealFloat func () *bignum.Rational;
	evalString func (f *Frame) string;
	evalPtr func (f *Frame) Value;
	// Evaluate to the "address of" this value; that is, the
	// settable Value object.  nil for expressions whose address
	// cannot be taken.
	evalAddr func (f *Frame) Value;
	// A short string describing this expression for error
	// messages.  Only necessary if t != nil.
	desc string;
}
```
この構造体は、式のコンパイル結果を保持します。以前は `f func (f *Frame) Value` という単一の汎用評価関数を持っていましたが、この変更により、`evalBool`、`evalUint`などのように、評価される式の型に応じた具体的なネイティブ型を返す複数の評価関数を持つようになりました。`evalAddr`は、式がl-valueである場合にそのアドレス（代入可能な`Value`オブジェクト）を返す関数です。

### `genIdent` 関数 (抜粋)

```go
func (a *exprCompiler) genIdent(t Type, s *Scope, index int) {
	switch _ := t.literal().(type) {
	case *boolType:
        a.evalBool = func (f *Frame) bool { return f.Get(s, index).(BoolValue).Get() };
	case *uintType:
        a.evalUint = func (f *Frame) uint64 { return f.Get(s, index).(UintValue).Get() };
	case *intType:
        a.evalInt = func (f *Frame) int64 { return f.Get(s, index).(IntValue).Get() };
	case *floatType:
        a.evalFloat = func (f *Frame) float64 { return f.Get(s, index).(FloatValue).Get() };
	case *stringType:
        a.evalString = func (f *Frame) string { return f.Get(s, index).(StringValue).Get() };
	case *PtrType:
        a.evalPtr = func (f *Frame) Value { return f.Get(s, index).(PtrValue).Get() };
	default:
		log.Crashf("unexpected variable type %v at %v", t.literal(), a.pos);
	}
}
```
この関数は、識別子（変数）の評価ロジックを生成します。引数として渡された型 `t` に応じて、`exprCompiler` の適切な `evalXxx` フィールドにクロージャを割り当てます。このクロージャは、`Frame.Get` メソッドを使って変数から`Value`を取得し、それを具体的な型に型アサート（例: `.(BoolValue)`) してから、そのネイティブ値（例: `.Get()`) を返します。これにより、評価時に直接ネイティブ型が扱われるようになります。

### `genBinOpAdd` 関数 (抜粋)

```go
func (a *exprCompiler) genBinOpAdd(l *exprCompiler, r *exprCompiler) {
	switch _ := l.t.literal().(type) {
	case *uintType:
        lf := l.asUint();
        rf := r.asUint();
        a.evalUint = func (f *Frame) uint64 { return lf(f) + rf(f) };
	case *intType:
        lf := l.asInt();
        rf := r.asInt();
        a.evalInt = func (f *Frame) int64 { return lf(f) + rf(f) };
	case *idealIntType:
        lf := l.asIdealInt();
        rf := r.asIdealInt();
		val := lf().Add(rf());
        a.evalIdealInt = func () *bignum.Integer { return val };
	// ... 他の型 ...
	default:
		log.Crashf("unexpected left operand type %v at %v", l.t.literal(), a.pos);
	}
}
```
この関数は、加算演算子 (`+`) の評価ロジックを生成します。左オペランド `l` の型に基づいて、`exprCompiler` の適切な `evalXxx` フィールドにクロージャを割り当てます。このクロージャは、左右のオペランドの型特化型評価関数（`l.asUint()`, `r.asUint()` など）を呼び出してネイティブ値を取得し、それらを直接加算して結果を返します。理想型の場合は `bignum` パッケージの `Add` メソッドを使用します。これにより、二項演算が型安全かつ効率的に実行されます。

### `usr/austin/eval/scope.go` の `Frame.Get` メソッド

```go
func (f *Frame) Get(s *Scope, index int) Value {
	for f.Scope != s {
		f = f.Outer;
	}
	return f.Vars[index];
}
```
このメソッドは、指定されたスコープ `s` と変数インデックス `index` に基づいて、`Frame` チェーンを遡りながら目的の変数 `Value` を見つけて返します。これにより、ネストされたスコープにおける変数の参照が正しく行われます。

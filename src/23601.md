# [インデックス 23601] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである`cmd/internal/obj`における`Prog`構造体の最適化に関するものです。具体的には、`Prog`構造体内の`Pcrel`フィールドと`Comefrom`フィールドを`Rel`という単一のフィールドに統合することで、構造体のサイズを削減し、コンパイル時のメモリ使用量を削減することを目的としています。

## 元コミット内容

このコミットの目的は、Goコンパイラの内部表現で使用される`Prog`構造体のメモリフットプリントを削減することです。`Prog`構造体には、異なるアーキテクチャ（ARMとx86）でそれぞれ異なる目的で使用される`Pcrel`と`Comefrom`というフィールドが存在していました。これらのフィールドは、特定のアーキテクチャでのみ意味を持つため、同時に両方が使用されることはありません。この特性を利用し、これら2つのフィールドを`Rel`という単一のフィールドに統合することで、`Prog`構造体のサイズを小さくしています。

具体的な効果として、`Prog`構造体のサイズが288バイトに削減され、これにより次のより小さいメモリアロケーションクラスに収まるようになりました。結果として、`rotate tests`のコンパイル時におけるメモリ使用量（`inuse_space`）が約3.2%削減されたと報告されています。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、プログラムの各命令や擬似命令を`Prog`という構造体で表現します。この`Prog`構造体は、コンパイル中に大量に生成され、メモリ上に保持されます。そのため、`Prog`構造体のサイズは、コンパイラのメモリ使用量とパフォーマンスに直接影響を与えます。

以前の設計では、`Prog`構造体にはARMアーキテクチャ向けの`Pcrel`フィールドと、x86アーキテクチャ向けの`Comefrom`フィールドが独立して存在していました。しかし、これらのフィールドはアーキテクチャ固有であり、ある特定のコンパイル時にはどちらか一方しか使用されません。つまり、片方のフィールドは常に未使用のままメモリを占有していました。

この冗長性を排除し、メモリ効率を向上させることが、この変更の背景にあります。特に、コンパイラが使用するメモリ量を削減することは、大規模なプロジェクトのコンパイル時間短縮や、リソースが限られた環境でのコンパイルを可能にする上で重要です。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Goコンパイラの内部構造 (`cmd/internal/obj`パッケージ)**:
    *   Goコンパイラは、複数のステージを経てソースコードを機械語に変換します。`cmd/internal/obj`パッケージは、アセンブラのバックエンド部分を担当し、中間表現（IR）としての命令列を扱います。
    *   `Prog`構造体は、この中間表現における個々の命令（または擬似命令）を表す中心的なデータ構造です。各`Prog`インスタンスは、命令の種類、オペランド、関連するメタデータなどを保持します。

2.  **`Prog`構造体**:
    *   `Prog`構造体は、アセンブラが処理する命令の抽象化です。これには、命令コード（`As`）、オペランド（`From`, `To`, `From3`）、プログラムカウンタ（`Pc`）、行番号（`Lineno`）など、命令に関する様々な情報が含まれます。
    *   コンパイルの過程で、これらの`Prog`構造体のリストが生成され、最適化やコード生成の対象となります。

3.  **`Pcrel` (PC-relative)**:
    *   PC相対アドレッシング（Program Counter Relative Addressing）は、命令のアドレスをプログラムカウンタ（PC）の値からのオフセットとして指定するアドレッシングモードです。これは、特にARMアーキテクチャで頻繁に使用され、コードの再配置性（relocatability）を高めるのに役立ちます。
    *   `Pcrel`フィールドは、ARMアーキテクチャにおいて、PC相対アドレッシングに関連する情報を保持するために使用されていました。

4.  **`Comefrom` (Forward Jumps)**:
    *   アセンブラでは、ジャンプ命令のターゲットがまだ定義されていない（つまり、ジャンプ先が現在の命令よりも後にある）場合があります。これを「前方ジャンプ（forward jump）」と呼びます。
    *   x86アーキテクチャでは、このような前方ジャンプを解決するために、ジャンプ元（`Comefrom`）の情報を保持し、ジャンプ先が定義された時点でその情報を更新する必要がありました。`Comefrom`フィールドは、この前方ジャンプの連鎖を管理するために使用されていました。

5.  **メモリアロケーションクラス (Malloc Class)**:
    *   Goランタイムのメモリ管理システム（アロケータ）は、異なるサイズのオブジェクトを効率的に管理するために、オブジェクトサイズに基づいて「アロケーションクラス」を定義しています。
    *   特定のサイズ（例えば288バイト）のオブジェクトが、より小さいアロケーションクラスに収まるようになると、メモリの断片化が減少し、アロケータの効率が向上し、結果としてメモリ使用量全体が削減される可能性があります。

## 技術的詳細

このコミットの核心は、`Prog`構造体の定義変更と、それに伴う各アーキテクチャ固有のコードの修正です。

### `Prog`構造体の変更 (`src/cmd/internal/obj/link.go`)

最も重要な変更は、`Prog`構造体から`Comefrom *Prog`と`Pcrel *Prog`の2つのフィールドを削除し、代わりに`Rel *Prog`という単一のフィールドを追加した点です。

```go
// 変更前
type Prog struct {
	// ...
	Comefrom *Prog
	Pcrel    *Prog
	// ...
}

// 変更後
type Prog struct {
	// ...
	Rel    *Prog // Source of forward jumps on x86; pcrel on arm
	// ...
}
```

この変更により、`Prog`構造体のサイズが削減されます。コミットメッセージによると、これにより構造体サイズが288バイトになり、Goランタイムのメモリアロケータにおける次の小さいmallocクラスに収まるようになりました。これは、メモリの割り当てと解放の効率を向上させ、全体的なメモリ使用量を削減する効果があります。

### ARMアーキテクチャ関連の変更 (`src/cmd/internal/obj/arm/asm5.go`, `src/cmd/internal/obj/arm/obj5.go`)

ARMアーキテクチャのコードでは、これまで`p.Pcrel`を使用していた箇所が`p.Rel`に置き換えられています。

*   `src/cmd/internal/obj/arm/asm5.go`の`addpool`関数および`asmout`関数内で、`t.Pcrel`や`p.Pcrel`への参照が`t.Rel`や`p.Rel`に変更されています。これらの関数は、主にPC相対アドレッシングに関連するリロケーション（再配置）情報の処理を行っています。
*   `src/cmd/internal/obj/arm/obj5.go`の`linkcase`関数でも、`p.Pcrel = casep`が`p.Rel = casep`に変更されています。

これらの変更は、ARMアーキテクチャにおいて`Rel`フィールドが`Pcrel`の役割を果たすことを示しています。

### x86アーキテクチャ関連の変更 (`src/cmd/internal/obj/x86/asm6.go`)

x86アーキテクチャのコードでは、これまで`p.Comefrom`を使用していた箇所が`p.Rel`に置き換えられています。

*   `src/cmd/internal/obj/x86/asm6.go`の`span6`関数および`doasm`関数内で、`p.Comefrom`への参照が`p.Rel`に変更されています。これらの関数は、前方ジャンプの解決と、ジャンプ元とジャンプ先のリンクリストの管理を行っています。

これらの変更は、x86アーキテクチャにおいて`Rel`フィールドが`Comefrom`の役割を果たすことを示しています。

### メモリ削減のメカニズム

Goランタイムのメモリアロケータは、オブジェクトのサイズに基づいてメモリを割り当てます。特定のサイズ範囲のオブジェクトは、同じ「アロケーションクラス」に分類され、効率的な管理のために特定のサイズのチャンクで割り当てられます。`Prog`構造体のサイズが、例えば304バイトから288バイトに削減された場合、これがアロケーションクラスの境界をまたぐことで、より小さいメモリチャンクに収まるようになります。これにより、各`Prog`インスタンスが占めるメモリ量が減るだけでなく、メモリの断片化も抑制され、全体としてより少ないメモリでコンパイルプロセスを実行できるようになります。

## コアとなるコードの解説

このコミットのコアとなる変更は、`Prog`構造体のフィールド統合です。

`Prog`構造体は、Goコンパイラのアセンブラバックエンドにおいて、個々のアセンブリ命令や擬似命令を表現するための中心的なデータ構造です。この構造体は、命令の種類、オペランド、アドレス情報、リンクリストポインタなど、多くのフィールドを含んでいます。

変更前は、`Prog`構造体には以下の2つのフィールドがありました。
*   `Pcrel *Prog`: ARMアーキテクチャにおけるPC相対アドレッシングに関連する情報を保持するためのポインタ。
*   `Comefrom *Prog`: x86アーキテクチャにおける前方ジャンプの解決のために、ジャンプ元の命令を指すポインタ。

これらのフィールドは、それぞれ異なるアーキテクチャでのみ意味を持ち、同時に両方が使用されることはありませんでした。例えば、ARMコードをコンパイルする際には`Pcrel`が使用され、`Comefrom`は常に`nil`でした。逆にx86コードをコンパイルする際には`Comefrom`が使用され、`Pcrel`は常に`nil`でした。

このコミットでは、この冗長性を排除するために、これら2つのフィールドを`Rel *Prog`という単一のフィールドに統合しました。
*   ARMアーキテクチャのコードでは、`Rel`フィールドが`Pcrel`の役割を担います。
*   x86アーキテクチャのコードでは、`Rel`フィールドが`Comefrom`の役割を担います。

これにより、`Prog`構造体から1つのポインタフィールド（8バイト、64ビットシステムの場合）が削減されます。この小さな変更が、大量に生成される`Prog`インスタンス全体で大きなメモリ削減効果をもたらします。コミットメッセージにあるように、`Prog`構造体のサイズが288バイトに削減され、Goランタイムのメモリアロケータの次の小さいアロケーションクラスに収まることで、メモリの効率的な利用が実現されました。これは、コンパイラのメモリフットプリントを削減し、特に大規模なGoプログラムのコンパイル時におけるパフォーマンス向上に寄与します。

## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおける潜在的なバグが存在していました。具体的には、`CL 11238`という変更が導入されたことにより、`OpAddr`というSSA操作が予期せず引数を持たない状態になる可能性が生じました。`OpAddr`は通常、アドレス計算の基点となる値（例えばスタックポインタ`OpSP`や静的ベースポインタ`OpSB`）を引数として期待しますが、この引数が欠落した場合に、コードが`v.Args[0]`にアクセスしようとして配列の範囲外パニック（out of bounds array panic）を引き起こす可能性がありました。

このコミットは、このパニックを回避するために、`OpAddr`操作の引数をチェックする防御的なコードを追加し、さらに既存の単体テストがこの新しい制約に適合するように修正することを目的としています。これにより、コンパイラの堅牢性が向上し、不正なSSA形式が原因でコンパイラがクラッシュするのを防ぎます。

## 前提知識の解説

### GoコンパイラとSSA

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。その内部には、コードの最適化を行うための様々なステージがあります。SSA（Static Single Assignment）形式は、コンパイラの最適化バックエンドで広く用いられる中間表現（IR: Intermediate Representation）の一種です。

SSA形式の主な特徴は以下の通りです。
*   **単一代入**: 各変数は一度だけ代入されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。
*   **Φ関数（Phi function）**: 制御フローグラフの複数のパスが合流する点で、同じ変数に異なる値が代入される可能性がある場合に、どの値を使用するかを解決するために導入されます。

GoコンパイラのSSAバックエンドは、GoのコードをSSA形式に変換し、様々な最適化（デッドコード削除、定数伝播、レジスタ割り当てなど）を適用してから、最終的な機械語を生成します。

### `OpAddr`, `OpSP`, `OpSB`

GoコンパイラのSSA形式では、様々な「操作（Operation）」が定義されており、それぞれが特定の計算やメモリ操作を表します。

*   **`OpAddr`**: これは「アドレスを取得する」操作を表します。通常、メモリ上の特定の位置へのポインタを生成するために使用されます。例えば、ローカル変数のアドレスやグローバル変数のアドレスを取得する際に使われます。`OpAddr`は、そのアドレス計算の基点となる値（ベースアドレス）を引数として取ることが一般的です。
*   **`OpSP` (Stack Pointer)**: スタックポインタを表すSSA値です。関数呼び出し時に確保されるローカル変数は、スタック上に配置されるため、そのアドレスはスタックポインタからのオフセットで計算されます。`OpAddr`が`OpSP`を引数に取る場合、それはスタック上のアドレスを計算していることを意味します。
*   **`OpSB` (Static Base Pointer)**: 静的ベースポインタを表すSSA値です。グローバル変数やパッケージレベルの変数は、静的メモリ領域に配置されるため、そのアドレスは静的ベースポインタからのオフセットで計算されます。`OpAddr`が`OpSB`を引数に取る場合、それは静的メモリ領域のアドレスを計算していることを意味します。

これらの操作は、Goプログラムがメモリをどのように利用するかをSSA形式で表現するための基本的な構成要素です。

### `v.Args`と配列の範囲外パニック

SSA形式では、各操作（`Value`構造体で表現されることが多い）は、その操作の入力となる他のSSA値への参照を`Args`というフィールド（通常はスライスや配列）に持ちます。例えば、`OpAdd`操作は2つの数値を`Args`に持ち、`OpAddr`操作はベースアドレスを`Args`に持ちます。

`v.Args[0]`のように`Args`スライスの要素にアクセスする場合、そのスライスが空である（`len(v.Args) == 0`）にもかかわらずアクセスしようとすると、Goランタイムは「配列の範囲外パニック（panic: runtime error: index out of range）」を引き起こします。これは、プログラムが不正なメモリ領域にアクセスしようとしたことを示す重大なエラーです。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/check.go` の変更点

この変更は、SSA形式の`Value`が`OpAddr`操作である場合に、その`Args`スライスが空でないことを保証するためのものです。

*   `if v.Op == OpAddr`: 現在処理しているSSA値`v`の操作が`OpAddr`であるかをチェックします。
*   `if len(v.Args) == 0`: `OpAddr`操作であるにもかかわらず、その引数リスト`v.Args`が空であるかをチェックします。
*   `f.Fatalf("no args for OpAddr %s", v.LongString())`: もし`v.Args`が空であれば、これは不正なSSA形式であるため、コンパイラを致命的なエラーで終了させます。`v.LongString()`は、問題のあるSSA値の詳細な文字列表現を提供し、デバッグを助けます。

このチェックは、`v.Args[0]`にアクセスする前の防御的な措置であり、`CL 11238`によって引き起こされた可能性のある配列の範囲外パニックを防止します。

### `src/cmd/compile/internal/ssa/deadstore_test.go` の変更点

このテストファイルの変更は、`check.go`で導入された新しい制約に合わせて、テストケースを更新するものです。

*   `Valu("sb", OpSB, TypeInvalid, 0, nil)`: これは、`sb`という名前で`OpSB`（静的ベースポインタ）を表すSSA値を定義しています。`OpSB`は、静的メモリ領域のベースアドレスを示す特別な値であり、`OpAddr`操作の有効な引数として機能します。
*   `Valu("addr1", OpAddr, ptrType, 0, nil, "sb")`: 以前は引数なしで`OpAddr`を定義していましたが、この変更により、新しく定義された`"sb"`を`OpAddr`の引数として明示的に渡しています。これにより、`addr1`というSSA値は、`sb`を基点としたアドレス計算を表すようになります。同様に、他の`OpAddr`の定義も`"sb"`を引数として追加しています。

これらの変更により、テストケースが生成するSSA形式が常に`OpAddr`に有効な引数を持つようになり、`check.go`の新しい検証ロジックに合格するようになります。これは、コンパイラのテストが実際のコンパイラの動作と整合性を保つ上で重要です。

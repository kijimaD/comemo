# [インデックス 23180] ファイルの概要

このコミットは、Go言語のツールチェインにおける浮動小数点リテラルの扱いに関する変更です。具体的には、アセンブル時に浮動小数点定数のためのデータ生成を行わないようにし、その処理をリンカ（`liblink`）に任せるように修正しています。これにより、ツールチェインのGo言語への移植（Go自身でGoをビルドする）を促進し、コードの重複を排除しています。

## 元コミット内容

このコミットは、Goツールチェインの`cmd/internal/obj`パッケージにおいて、アセンブル時に浮動小数点定数（`$f32.`および`$f64.`シンボル）のデータ生成を行わないようにする変更です。これらのシンボルに対応するデータは、オブジェクトファイルをリンクする際に`liblink`（Goリンカ）が生成する責任を持つべきであるという方針に基づいています。

コミットメッセージには、「これは`https://golang.org/cl/3101`のGoへの移植である」と明記されており、Goツールチェインの自己ホスト化（Go自身でGoをビルドできるようにする）の一環として、C言語で書かれていた既存のロジックをGo言語に移植する作業の一部であることが示唆されています。

## 変更の背景

Go言語の初期のツールチェインは、一部がC言語で書かれていました。Goプロジェクトの目標の一つに、ツールチェイン全体をGo言語で記述し、自己ホスト化を達成するというものがありました。これにより、Goコンパイラやリンカの保守性、移植性、そしてGo言語自体の進化との整合性を高めることができます。

このコミットは、その自己ホスト化の過程で、浮動小数点リテラルの扱いに関するロジックを整理し、リンカ（`liblink`）がそのデータ生成を一元的に管理するように変更したものです。以前は、アセンブラの段階でこれらのシンボルに対するデータが生成されていましたが、これはリンカの役割と重複しており、コードの複雑性を増していました。この変更により、役割分担が明確になり、ツールチェイン全体の設計がよりクリーンになります。特に、`liblink`がオブジェクトファイルを読み込む際に、必要に応じて浮動小数点定数のデータを生成するようになるため、アセンブラ側での冗長な処理が不要になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goツールチェイン**: Go言語のプログラムを開発・ビルドするために必要な一連のツール群（コンパイラ、アセンブラ、リンカなど）を指します。
*   **アセンブラ (Assembler)**: ソースコード（Go言語の場合、Goのソースコードから生成された中間表現や、直接アセンブリ言語で書かれたコード）を機械語のオブジェクトファイルに変換するプログラムです。この段階では、まだ複数のオブジェクトファイルが結合されていません。
*   **リンカ (Linker)**: 複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するプログラムです。シンボル解決（あるファイルで定義された関数や変数を別のファイルから参照できるようにする）や、必要なデータの配置などを行います。Go言語のリンカは`liblink`と呼ばれていました（現在は`cmd/link`）。
*   **オブジェクトファイル**: アセンブラによって生成される中間ファイルで、機械語コード、データ、シンボル情報などが含まれます。
*   **シンボル**: プログラム内の関数、変数、定数などを識別するための名前です。このコミットでは、浮動小数点定数を表す`$f32.`（32ビット浮動小数点数）および`$f64.`（64ビット浮動小数点数）という特殊なシンボルが扱われています。
*   **浮動小数点リテラル**: ソースコード中に直接記述された浮動小数点数（例: `3.14`, `1.0e-5`）のことです。これらはコンパイル時に特定のデータとしてバイナリに埋め込まれる必要があります。
*   **自己ホスト化 (Self-hosting)**: プログラミング言語のコンパイラやツールチェインが、その言語自身で書かれている状態を指します。Go言語のツールチェインは、初期にはC言語の要素を含んでいましたが、最終的には完全にGo言語で書かれることを目指していました。

## 技術的詳細

このコミットの技術的な核心は、浮動小数点リテラルがGoのオブジェクトファイル内でどのように表現され、最終的なバイナリにどのように組み込まれるかという点にあります。

Goのアセンブラは、ソースコード中の浮動小数点リテラルを`$f32.xxxxxxxx`や`$f64.xxxxxxxxxxxxxxxx`のような特殊なシンボルに変換します。ここで`xxxxxxxx`は浮動小数点数のビット表現（IEEE 754形式）を16進数で表したものです。

変更前のコードでは、`src/cmd/internal/obj/arm/obj5.go`と`src/cmd/internal/obj/x86/obj6.go`内の`progedit`関数（プログラムの命令を編集する役割を持つ）が、これらの`$f32.`や`$f64.`シンボルに遭遇した際に、対応する浮動小数点データのセクション（`obj.SRODATA`、読み取り専用データセクション）を生成し、そのデータをそこに書き込んでいました。具体的には、`obj.Adduint32`や`obj.Adduint64`といった関数を使って、浮動小数点数のビット表現を直接データとして追加していました。

しかし、このアプローチには以下の問題がありました。
1.  **役割の重複**: データの最終的な配置と結合はリンカの主要な役割です。アセンブラがデータ生成まで行うのは、リンカの機能と重複していました。
2.  **複雑性の増加**: アセンブラとリンカの両方で浮動小数点データの生成ロジックを持つことは、コードの保守を複雑にし、将来的な変更を困難にします。
3.  **自己ホスト化の妨げ**: C言語で書かれた`liblink`が既にこの機能を持っていた場合、Go言語で書かれたアセンブラが同じロジックを持つことは、GoツールチェインのGoへの完全な移植を妨げる要因となります。

このコミットでは、アセンブラ側の`progedit`関数から、`s.Type == 0`のチェックとそれに続く`s.Type = obj.SRODATA`および`obj.Adduint32/Adduint64`によるデータ生成のロジックを削除しました。これにより、アセンブラは単に`$f32.`や`$f64.`シンボルを参照する命令を生成するだけになり、これらのシンボルに対応する実際のデータは、リンカがオブジェクトファイルを読み込む際に、必要に応じて生成・配置するようになります。

この変更は、Goツールチェインのモジュール間の責任分担を明確にし、リンカがデータ管理の中心となるように設計を改善するものです。

## コアとなるコードの変更箇所

変更は主に以下の2つのファイルで行われています。

1.  `src/cmd/internal/obj/arm/obj5.go`
2.  `src/cmd/internal/obj/x86/obj6.go`

これらのファイルは、それぞれARMアーキテクチャとx86アーキテクチャ向けのアセンブラのバックエンドの一部であり、オブジェクトファイルの生成に関連する処理を担っています。

具体的な変更は、`progedit`関数内の浮動小数点リテラル（`$f32.`および`$f64.`シンボル）を処理する部分から、以下のコードブロックが削除されたことです。

```go
			if s.Type == 0 {
				s.Type = obj.SRODATA
				obj.Adduint32(ctxt, s, i32) // または obj.Adduint64(ctxt, s, i64)
			}
```

この削除により、アセンブラは`$f32.`や`$f64.`シンボルがまだ定義されていない場合でも、そのシンボルに対応するデータセクションを生成したり、データを追加したりしなくなりました。

## コアとなるコードの解説

削除されたコードブロックは、アセンブラが浮動小数点リテラルを処理する際の挙動を定義していました。

*   `s := obj.Linklookup(ctxt, literal, 0)`: これは、`$f32.xxxxxxxx`や`$f64.xxxxxxxxxxxxxxxx`といったリテラル文字列に対応するシンボルをリンカのコンテキスト（`ctxt`）から検索する処理です。
*   `if s.Type == 0`: この条件は、そのシンボルがまだどのセクションにも属していない（つまり、まだデータが生成されていない）場合に真となります。
*   `s.Type = obj.SRODATA`: シンボルが未定義の場合、それを読み取り専用データセクション（`.rodata`）に配置されるべきシンボルとしてマークします。
*   `obj.Adduint32(ctxt, s, i32)` / `obj.Adduint64(ctxt, s, i64)`: これは、実際の浮動小数点数のビット表現（`i32`または`i64`）を、指定されたシンボル`s`に関連付けられたデータとして、リンカのコンテキストに追加する関数呼び出しです。これにより、アセンブル時に浮動小数点データがオブジェクトファイル内に生成されていました。

このコミットでは、上記のコードブロックが完全に削除されました。これにより、アセンブラは浮動小数点リテラルシンボルを見つけても、その場でデータ生成を行いません。代わりに、リンカがオブジェクトファイルを読み込む際に、これらのシンボルを解決し、必要に応じて適切なデータセクションに浮動小数点データを配置する責任を負うことになります。これは、ツールチェインの各コンポーネントの役割をより明確にし、リンカにデータ管理を一元化させるための重要な変更です。

*   `s.Type = obj.SRODATA`: シンボルが未定義の場合、それを読み取り専用データセクション（`.rodata`）に配置されるべきシンボルとしてマークします。
*   `obj.Adduint32(ctxt, s, i32)` / `obj.Adduint64(ctxt, s, i64)`: これは、実際の浮動小数点数のビット表現（`i32`または`i64`）を、指定されたシンボル`s`に関連付けられたデータとして、リンカのコンテキストに追加する関数呼び出しです。これにより、アセンブル時に浮動小数点データがオブジェクトファイル内に生成されていました。

このコミットでは、上記のコードブロックが完全に削除されました。これにより、アセンブラは浮動小数点リテラルシンボルを見つけても、その場でデータ生成を行いません。代わりに、リンカがオブジェクトファイルを読み込む際に、これらのシンボルを解決し、必要に応じて適切なデータセクションに浮動小数点データを配置する責任を負うことになります。これは、ツールチェインの各コンポーネントの役割をより明確にし、リンカにデータ管理を一元化させるための重要な変更です。

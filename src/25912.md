## 変更の背景

この変更は、Goの `encoding/json` パッケージの `Unmarshal` 関数が、JSONデータをGoの `map`、`slice`、`array` 型にデコードする際の挙動について、既存のドキュメントが不明瞭であったり、誤解を招く可能性があったために行われました。特に、`Unmarshal` が既存のGoのデータ構造をどのように扱うか（例えば、`slice`がリセットされるのか、`map`が上書きされるのかなど）について、ユーザーが混乱するケースがありました。

このコミットは、GitHub Issue #12972 で報告された問題に対応しています。このIssueでは、`json.Unmarshal` が `map` にデコードする際に、既存の `map` のエントリが保持されるのか、それとも `map` が完全にクリアされてから新しいエントリが追加されるのかが不明確であるという点が指摘されていました。同様に、`slice` や `array` の扱いについても、より明確な説明が求められていました。

正確なドキュメントは、開発者がライブラリの挙動を正しく理解し、予期せぬバグを避けるために不可欠です。このコミットは、`Unmarshal` の重要な側面に関するドキュメントの精度と完全性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の基本的なデータ型とJSONの概念についての知識が必要です。

### Go言語のデータ型

1.  **Slice (スライス)**:
    *   Goで最も一般的に使用される可変長シーケンス型です。
    *   内部的には、配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。
    *   `make([]T, length, capacity)` で作成され、`append` 関数で要素を追加すると、必要に応じて基底配列が拡張されることがあります。
    *   `nil` スライスは、長さも容量も0のスライスで、基底配列を持たない状態です。

2.  **Array (配列)**:
    *   Goの固定長シーケンス型です。
    *   宣言時に長さが固定され、後から変更することはできません（例: `[5]int`）。
    *   値型であり、代入や関数への引数渡しではコピーが作成されます。

3.  **Map (マップ)**:
    *   キーと値のペアを格納するハッシュテーブルです。
    *   `make(map[KeyType]ValueType)` で作成されます。
    *   キーは一意であり、値は任意の型を取ることができます。
    *   `nil` マップは、初期化されていないマップで、読み取りはできますが、書き込みはパニックを引き起こします。

### JSON (JavaScript Object Notation)

1.  **JSON Object (JSONオブジェクト)**:
    *   キーと値のペアの順序なしのコレクションです。
    *   Goの `map[string]interface{}` や構造体に対応します。
    *   例: `{"name": "Alice", "age": 30}`

2.  **JSON Array (JSON配列)**:
    *   値の順序付きリストです。
    *   Goの `[]interface{}` や特定の型の `slice`、`array` に対応します。
    *   例: `[1, 2, 3, "hello"]`

### `encoding/json.Unmarshal` 関数

`encoding/json` パッケージの `Unmarshal` 関数は、JSON形式のデータをGoのデータ構造にデコードするために使用されます。そのシグネチャは `func Unmarshal(data []byte, v interface{}) error` であり、`v` はデコードされたJSONデータが格納されるGoの変数へのポインタである必要があります。

`Unmarshal` の挙動は、`v` の型によって異なります。特に、`map`、`slice`、`array` のような複合型にデコードする際には、既存のデータがどのように扱われるかが重要になります。

## 技術的詳細

このコミットは、`encoding/json/decode.go` ファイル内の `Unmarshal` 関数のドキュメントコメントを修正し、特に `map`、`slice`、`array` へのデコード挙動を明確にしています。

### 変更点と詳細な挙動

1.  **JSON配列をGoのSliceにアンマーシャルする場合**:
    *   **変更前**: 「`Unmarshal` はスライスを `nil` にリセットし、その後各要素をスライスに追加します。」
    *   **変更後**: 「`Unmarshal` はスライスの長さをゼロにリセットし、その後各要素をスライスに追加します。**特殊なケースとして、空のJSON配列をスライスにアンマーシャルする場合、`Unmarshal` はスライスを新しい空のスライスに置き換えます。**」
    *   **詳細**: 以前のドキュメントでは、スライスが `nil` にリセットされると記述されていましたが、これは誤解を招く可能性がありました。実際には、`Unmarshal` は既存のスライスの基底配列を再利用し、その長さをゼロに設定（つまり、既存の要素を論理的にクリア）してから、JSON配列の要素を `append` します。これにより、メモリの再割り当てを最小限に抑えることができます。ただし、空のJSON配列 `[]` を既存のスライスにアンマーシャルする場合、`Unmarshal` は新しい空のスライスを作成してターゲット変数に割り当てます。これは、既存のスライスが `nil` でない場合に、その基底配列を保持しつつ、長さが0のスライスとして扱うための挙動です。

2.  **JSON配列をGoのArrayにアンマーシャルする場合 (新規追加)**:
    *   **新規追加**: 「JSON配列をGoの配列にアンマーシャルする場合、`Unmarshal` はJSON配列の要素を対応するGo配列の要素にデコードします。Go配列がJSON配列よりも小さい場合、追加のJSON配列要素は破棄されます。JSON配列がGo配列よりも小さい場合、追加のGo配列要素はゼロ値に設定されます。」
    *   **詳細**: Goの配列は固定長であるため、スライスとは異なる挙動をします。`Unmarshal` はJSON配列の要素をGo配列の先頭から順に埋めていきます。
        *   JSON配列の要素数がGo配列のサイズを超える場合、Go配列に収まらない余分なJSON要素は無視されます。
        *   JSON配列の要素数がGo配列のサイズに満たない場合、Go配列の残りの要素はそれぞれの型のゼロ値（例: `int` なら `0`、`string` なら `""`）で埋められます。
    *   この説明は、Goの配列が値型であり、そのサイズが固定されているという特性を反映しています。

3.  **JSONオブジェクトをGoのMapにアンマーシャルする場合**:
    *   **変更前**: 「JSONオブジェクトをマップにアンマーシャルする場合、`Unmarshal` はマップを空のマップに置き換え、その後オブジェクトからキーと値のペアをマップに追加します。」
    *   **変更後**: 「JSONオブジェクトを文字列キーのマップにアンマーシャルする場合、`Unmarshal` はまず使用するマップを確立します。マップが `nil` の場合、`Unmarshal` は新しいマップを割り当てます。**それ以外の場合、`Unmarshal` は既存のマップを再利用し、既存のエントリを保持します。** その後、`Unmarshal` はJSONオブジェクトからキーと値のペアをマップに格納します。」
    *   **詳細**: 以前のドキュメントでは、マップが「空のマップに置き換えられる」と記述されており、既存のマップにデータがある場合にそれが失われると誤解される可能性がありました。しかし、実際の挙動は異なります。
        *   ターゲットのマップ変数が `nil` の場合、`Unmarshal` は新しいマップを作成して割り当てます。
        *   ターゲットのマップ変数が `nil` でない（つまり、既に初期化されている）場合、`Unmarshal` はその既存のマップを再利用します。JSONオブジェクト内のキーと一致する既存のエントリは上書きされ、JSONオブジェクトに存在しないキーを持つ既存のエントリは**保持されます**。これは、部分的なJSONデータで既存のマップを更新する際に非常に重要な挙動です。

これらのドキュメントの修正により、`Unmarshal` がGoの複合型をどのように扱うかについて、開発者はより正確な理解を得られるようになりました。特に、既存のデータが保持されるのか、それともクリアされるのかという点に関する混乱が解消されます。

    *   **詳細**: Goの配列は固定長であるため、スライスとは異なる挙動をします。`Unmarshal` はJSON配列の要素をGo配列の先頭から順に埋めていきます。
        *   JSON配列の要素数がGo配列のサイズを超える場合、Go配列に収まらない余分なJSON要素は無視されます。
        *   JSON配列の要素数がGo配列のサイズに満たない場合、Go配列の残りの要素はそれぞれの型のゼロ値（例: `int` なら `0`、`string` なら `""`）で埋められます。
    *   この説明は、Goの配列が値型であり、そのサイズが固定されているという特性を反映しています。

3.  **JSONオブジェクトをGoのMapにアンマーシャルする場合**:
    *   **変更前**: 「JSONオブジェクトをマップにアンマーシャルする場合、`Unmarshal` はマップを空のマップに置き換え、その後オブジェクトからキーと値のペアをマップに追加します。」
    *   **変更後**: 「JSONオブジェクトを文字列キーのマップにアンマーシャルする場合、`Unmarshal` はまず使用するマップを確立します。マップが `nil` の場合、`Unmarshal` は新しいマップを割り当てます。**それ以外の場合、`Unmarshal` は既存のマップを再利用し、既存のエントリを保持します。** その後、`Unmarshal` はJSONオブジェクトからキーと値のペアをマップに格納します。」
    *   **詳細**: 以前のドキュメントでは、マップが「空のマップに置き換えられる」と記述されており、既存のマップにデータがある場合にそれが失われると誤解される可能性がありました。しかし、実際の挙動は異なります。
        *   ターゲットのマップ変数が `nil` の場合、`Unmarshal` は新しいマップを作成して割り当てます。
        *   ターゲットのマップ変数が `nil` でない（つまり、既に初期化されている）場合、`Unmarshal` はその既存のマップを再利用します。JSONオブジェクト内のキーと一致する既存のエントリは上書きされ、JSONオブジェクトに存在しないキーを持つ既存のエントリは**保持されます**。これは、部分的なJSONデータで既存のマップを更新する際に非常に重要な挙動です。

これらのドキュメントの修正により、`Unmarshal` がGoの複合型をどのように扱うかについて、開発者はより正確な理解を得られるようになりました。特に、既存のデータが保持されるのか、それともクリアされるのかという点に関する混乱が解消されます。

## コアとなるコードの解説

変更されたのは、`Unmarshal` 関数の動作を説明するコメントブロックです。

1.  **Sliceに関する説明の変更**:
    *   `// To unmarshal a JSON array into a slice, Unmarshal resets the slice to nil`
        *   この行が削除され、「スライスを `nil` にリセットする」という誤解を招く表現が修正されました。
    *   `// To unmarshal a JSON array into a slice, Unmarshal resets the slice length`
        *   「スライスの長さをゼロにリセットする」という、より正確な表現に変わりました。これは、基底配列は保持しつつ、論理的にスライスを空にする動作を指します。
    *   `// As a special case, to unmarshal an empty JSON array into a slice,`
    *   `// Unmarshal replaces the slice with a new empty slice.`
        *   空のJSON配列をデコードする際の特殊な挙動が追加されました。これにより、既存のスライスが `nil` でない場合でも、空のJSON配列に対しては新しい空のスライスが割り当てられることが明確になります。

2.  **Arrayに関する説明の追加**:
    *   `// To unmarshal a JSON array into a Go array, Unmarshal decodes`
    *   `// JSON array elements into corresponding Go array elements.`
    *   `// If the Go array is smaller than the JSON array,`
    *   `// the additional JSON array elements are discarded.`
    *   `// If the JSON array is smaller than the Go array,`
    *   `// the additional Go array elements are set to zero values.`
        *   Goの固定長配列へのデコードに関する詳細な説明が丸ごと追加されました。これにより、配列のサイズとJSON配列の要素数の不一致がどのように扱われるかが明確になりました。

3.  **Mapに関する説明の変更**:
    *   `// To unmarshal a JSON object into a map, Unmarshal replaces the map`
    *   `// with an empty map and then adds key-value pairs from the object to`
    *   `// the map.`
        *   これらの行が削除され、「マップを空のマップに置き換える」という誤解を招く表現が修正されました。
    *   `// To unmarshal a JSON object into a string-keyed map, Unmarshal first`
    *   `// establishes a map to use, If the map is nil, Unmarshal allocates a new map.`
    *   `// Otherwise Unmarshal reuses the existing map, keeping existing entries.`
    *   `// Unmarshal then stores key-value pairs from the JSON object into the map.`
        *   マップが `nil` の場合は新規作成されること、そして `nil` でない場合は既存のマップが再利用され、既存のエントリが保持されることが明確に記述されました。これは、`Unmarshal` が既存のマップを部分的に更新する挙動を正確に反映しています。

これらのコメントの変更は、`Unmarshal` 関数の実際の内部実装ロジックを変更するものではなく、そのロジックが外部からどのように見えるか、つまり開発者がどのように利用すべきかを明確にするためのものです。これにより、`encoding/json` パッケージの使いやすさと信頼性が向上します。

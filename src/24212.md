# [インデックス 24212] ファイルの概要

このコミットは、Goランタイムにおいて、システムコールへのエントリー時にセーフポイント関数が実行された後、ゴルーチンの保存されたプログラムカウンタ (PC) とスタックポインタ (SP) が不正になる問題を修正します。具体的には、`systemstack()` の使用によってこれらの値が上書きされるのを防ぐため、`systemstack()` 呼び出し後にPCとSPを再保存するように変更されています。

## 変更の背景

Goランタイムは、ガベージコレクション (GC) やスケジューリングなどの重要な内部操作を安全に実行するために、「セーフポイント」という概念を利用します。セーフポイントでは、すべてのゴルーチンが既知の安全な状態にあることが保証され、ランタイムがゴルーチンのスタックやレジスタの状態を検査・操作できるようになります。

ゴルーチンがシステムコール（OSの機能を利用するための呼び出し）に入ろうとするとき、Goランタイムはいくつかの準備ステップを実行します。この過程で、もしセーフポイント関数（セーフポイントで実行される必要のある関数）が実行される必要がある場合、ランタイムは `systemstack()` という特殊なメカニズムを使用して、現在のゴルーチンのスタックではなく、OSスレッド（M）に紐付けられた「システムスタック」でその関数を実行します。

この `systemstack()` の使用が問題を引き起こす可能性がありました。`systemstack()` はスタックを切り替えるため、ゴルーチンの現在の実行状態を示す `g.sched.pc` (プログラムカウンタ) と `g.sched.sp` (スタックポインタ) の値が、意図せず上書き（clobber）されてしまうことがありました。これらの値は、ゴルーチンがシステムコールから戻った後や、スケジューラによって一時停止・再開される際に、その実行状態を正確に復元するために不可欠です。

このコミットの背景にあるのは、`systemstack()` が `g.sched.pc` と `g.sched.sp` を破壊する可能性があり、その結果、ゴルーチンがシステムコールから戻ったときに不正な場所から実行を再開したり、不正なスタック状態になったりするバグを防ぐことです。この修正は、`systemstack()` の実行後にもゴルーチンのPC/SPが常に正確に保存されるようにすることで、ランタイムの堅牢性を高めることを目的としています。

## 前提知識の解説

*   **Goroutine (ゴルーチン)**: Go言語の並行処理の基本単位であり、Goランタイムによって管理される軽量な実行スレッドです。OSスレッドに多重化されて実行されます。
*   **System Call (システムコール)**: プログラムがオペレーティングシステム (OS) のカーネル機能（ファイルI/O、ネットワーク通信、メモリ管理など）にアクセスするためのインターフェースです。GoプログラムがOSのサービスを利用する際には、システムコールが発行されます。
*   **Safe-point (セーフポイント)**: Goランタイムが、ガベージコレクション (GC) やスケジューリングなどの内部処理を安全に実行できる、ゴルーチンの特定の実行状態を指します。セーフポイントでは、すべてのゴルーチンのスタックとレジスタの状態が既知であり、GCがポインタを正確にスキャンできることが保証されます。
*   **`g.sched.pc` と `g.sched.sp`**: Goランタイム内部の `g` (goroutine構造体) に含まれるフィールドです。
    *   `g.sched.pc`: ゴルーチンが一時停止された際に、次に実行すべき命令のアドレス（プログラムカウンタ）を保存します。
    *   `g.sched.sp`: ゴルーチンが一時停止された際に、そのスタックの現在のポインタ（スタックポインタ）を保存します。
    これらの値は、ゴルーチンがスケジューラによって一時停止され、後で再開される際に、その実行コンテキストを正確に復元するために極めて重要です。
*   **`systemstack()`**: Goランタイムの内部関数で、現在のゴルーチンのスタックではなく、現在のOSスレッド（M）に紐付けられた特別な「システムスタック」で指定された関数を実行するために使用されます。これは、スタックの切り替え、GCが実行中のゴルーチンのスタックを操作するのを避ける必要がある場合、または低レベルのランタイム操作（例えば、スケジューラやメモリ管理の一部）で利用されます。
*   **`reentersyscall`**: Goランタイム内の `src/runtime/proc1.go` に定義されている関数です。ゴルーチンがシステムコールに入ろうとするとき、またはシステムコールから戻ってきたときに呼び出され、ゴルーチンの状態を適切に管理し、スケジューラやGCとの連携を調整する役割を担います。

## 技術的詳細

この修正は、`src/runtime/proc1.go` 内の `reentersyscall` 関数にあります。`reentersyscall` は、ゴルーチンがシステムコールに入る直前の状態を管理する重要な関数です。

関数内で、Goランタイムは `_g_.m.p.ptr().runSafePointFn != 0` という条件をチェックします。これは、現在のP (プロセッサ、Goスケジューラの論理的なCPU) に、実行すべきセーフポイント関数が登録されているかどうかを確認しています。もし登録されていれば、ランタイムは `systemstack(runSafePointFn)` を呼び出して、そのセーフポイント関数をシステムスタック上で実行します。

問題は、`systemstack()` が実行されると、ゴルーチンの `g.sched.pc` と `g.sched.sp` が意図せず古い値のままになってしまう可能性があった点です。`reentersyscall` 関数自体は、引数として `pc` と `sp` (システムコールに入る前のゴルーチンのPCとSP) を受け取りますが、`systemstack` が内部的にスタックを操作することで、`g` 構造体内の `sched.pc` と `sched.sp` が正しく更新されない状況が発生し得ました。

このコミットは、`systemstack(runSafePointFn)` の呼び出し直後に `save(pc, sp)` を追加することでこの問題を解決します。`save(pc, sp)` は、`reentersyscall` に渡された元の `pc` と `sp` の値を、現在のゴルーチン (`_g_`) の `sched.pc` と `sched.sp` に明示的に再保存する役割を果たします。これにより、セーフポイント関数がシステムスタック上で実行されたとしても、ゴルーチンの正しい再開点 (`pc`) とスタック状態 (`sp`) が常に `g.sched` に反映されることが保証されます。結果として、ゴルーチンがシステムコールから戻った際に、正確なコンテキストで実行を再開できるようになります。

## コアとなるコードの変更箇所

変更は `src/runtime/proc1.go` ファイルの1箇所です。

```diff
--- a/src/runtime/proc1.go
+++ b/src/runtime/proc1.go
@@ -1831,6 +1831,7 @@ func reentersyscall(pc, sp uintptr) {
 	if _g_.m.p.ptr().runSafePointFn != 0 {
 		// runSafePointFn may stack split if run on this stack
 		systemstack(runSafePointFn)
+		save(pc, sp)
 	}
 
 	_g_.m.syscalltick = _g_.m.p.ptr().syscalltick
```

## コアとなるコードの解説

追加された行 `save(pc, sp)` がこの修正の核心です。

*   `pc` と `sp` は、`reentersyscall` 関数が引数として受け取る値で、システムコールに入る直前のゴルーチンのプログラムカウンタとスタックポインタを表します。
*   `systemstack(runSafePointFn)` は、セーフポイント関数をシステムスタック上で実行します。この操作自体は `reentersyscall` の引数 `pc` と `sp` を直接変更するわけではありませんが、ランタイムがゴルーチンの状態を追跡するために使用する内部の `_g_.sched.pc` と `_g_.sched.sp` の値に影響を与える可能性がありました。
*   `systemstack(runSafePointFn)` の直後に `save(pc, sp)` を呼び出すことで、ランタイムは `_g_.sched.pc` と `_g_.sched.sp` を、セーフポイント操作が完了し、かつシステムコールに完全にエントリーする前のゴルーチンの正しい `pc` と `sp` の値で明示的に更新します。
*   これにより、ゴルーチンがシステムコールから戻るか、または他の理由でスケジューリングされる際に、その実行コンテキストが正しく復元されることが保証されます。この修正は、`systemstack` 操作によって発生しうる、ゴルーチンが不正な場所から再開したり、無効なスタック状態になったりする潜在的なバグを防ぎます。

## 変更の背景

Go言語の `net/http` パッケージは、ウェブアプリケーション開発において中心的な役割を担っています。HTTP/1.1は長らくウェブの基盤プロトコルでしたが、より効率的な通信を実現するためにHTTP/2が導入されました。GoはHTTP/2のサポートを積極的に進めており、`net/http` パッケージもHTTP/2に対応しています。

しかし、プロトコルが異なることで、同じアプリケーションコードでもHTTP/1とHTTP/2で微妙に異なる動作をする可能性があります。特に、ヘッダーの処理、ストリームの管理、エラーハンドリングなど、低レベルな部分で差異が生じることがあります。これらの差異が予期せぬバグや非互換性を引き起こさないようにするためには、両方のプロトコルで徹底的にテストを行うことが不可欠です。

このコミットの背景には、Goの `net/http` パッケージがHTTP/2を完全にサポートする過程で、既存のテストがHTTP/1の動作のみを想定しているという課題がありました。HTTP/2の導入に伴い、既存のテストがHTTP/2環境下でも期待通りに動作するか、あるいはHTTP/2特有の動作を適切にテストできているかを確認する必要が生じました。

コミットメッセージで言及されているIssue #6891は、GoにおけるHTTP/2サポートの全体的な進捗を追跡する主要なIssueです。このコミットは、その大きな目標の一部として、テストインフラを整備するものです。また、#13315, #13316, #13317といったIssueは、HTTP/1とHTTP/2の間で動作が異なることが判明した特定のケースを指しており、このコミットで追加されたスキップされたテストは、これらの既知の不具合を浮き彫りにし、将来の修正を促す役割を果たします。

## 前提知識の解説

### HTTP/1.1とHTTP/2

*   **HTTP/1.1**: 従来のHTTPプロトコルで、リクエストとレスポンスが順番に処理される「リクエスト-レスポンス」モデルに基づいています。各リクエストは通常、新しいTCP接続を必要とするか、パイプライン処理（ただし、ヘッドオブラインブロッキングの問題がある）を使用します。ヘッダーはテキスト形式で送信され、冗長になりがちです。
*   **HTTP/2**: HTTP/1.1のパフォーマンス上の課題を解決するために設計された新しいプロトコルです。主な特徴は以下の通りです。
    *   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングが解消され、効率が向上します。
    *   **ヘッダー圧縮 (HPACK)**: ヘッダーを効率的に圧縮することで、帯域幅の使用量を削減します。
    *   **サーバープッシュ (Server Push)**: サーバーがクライアントに、リクエストされる前にリソースをプッシュできます。
    *   **バイナリフレーミング**: HTTP/1.1のテキストベースのプロトコルとは異なり、HTTP/2はバイナリ形式でデータを送受信します。

### Goの `net/http` パッケージ

`net/http` はGoの標準ライブラリの一部であり、HTTPクライアントとサーバーの実装を提供します。Goのウェブ開発において非常に広く利用されており、高いパフォーマンスと使いやすさを特徴としています。HTTP/2のサポートは、このパッケージに統合されており、HTTPS接続を使用する場合には自動的にHTTP/2がネゴシエートされるようになっています。

### `httptest` パッケージ

`net/http/httptest` は、HTTPハンドラーやサーバーのテストを容易にするためのユーティリティを提供するパッケージです。テスト用のHTTPサーバーを簡単に起動したり、HTTPリクエストをシミュレートしたりすることができます。

### `golang.org/x/net/http2` パッケージ

`net/http` パッケージは基本的なHTTP/2サポートを提供しますが、より詳細な制御や低レベルなHTTP/2機能にアクセスしたい場合、または標準ライブラリにバンドルされているバージョンよりも新しいHTTP/2パッケージを使用したい場合には、`golang.org/x/net/http2` パッケージが利用されます。このパッケージには、`http.Transport` や `http.Server` をHTTP/2用に明示的に設定するための `ConfigureTransport` や `ConfigureServer` といった関数が含まれています。

## 技術的詳細

このコミットの主要な技術的変更点は、`net/http` のテストハーネスをHTTP/2に対応させるための基盤を構築していることです。

1.  **`clientServerTest` ヘルパーの導入**:
    `src/net/http/main_test.go` に `clientServerTest` という新しい構造体が導入されました。これは、HTTPクライアントとサーバーのテストを抽象化するためのヘルパーです。この構造体は、テスト対象のハンドラー、HTTP/2を使用するかどうかのフラグ (`h2 bool`)、`httptest.Server` インスタンス、および `http.Client` インスタンスをカプセル化します。

2.  **`ExportHttp2ConfigureServer` と `ExportHttp2ConfigureTransport` の公開**:
    `src/net/http/export_test.go` に、`http2ConfigureServer` と `http2ConfigureTransport` が `ExportHttp2ConfigureServer` および `ExportHttp2ConfigureTransport` として公開されました。これらは、`golang.org/x/net/http2` パッケージから提供される関数であり、`net/http` の内部テストからHTTP/2の構成を可能にするためにエクスポートされています。これにより、テストコードは `net/http` の内部実装に依存することなく、HTTP/2のクライアントとサーバーをセットアップできます。

3.  **既存テストの `_h1` / `_h2` バリアントへの分割**:
    `src/net/http/serve_test.go` では、`TestChunkedResponseHeaders` と `Test304Responses` の2つのテストが、それぞれ `TestChunkedResponseHeaders_h1` / `TestChunkedResponseHeaders_h2` および `Test304Responses_h1` / `Test304Responses_h2` に分割されました。
    *   `_h1` バリアントはHTTP/1.1でテストを実行します。
    *   `_h2` バリアントはHTTP/2でテストを実行します。
    *   `_h2` バリアントでは、`t.Skip("known failing test; golang.org/issue/13316")` のように、既知の失敗するテストとしてスキップされています。これは、HTTP/2での動作がHTTP/1と異なるため、現時点では失敗することが予想されることを示しています。これらのスキップされたテストは、将来のコミットでHTTP/2の動作が修正された際にパスするように設計されています。

4.  **`TestTransportResponse_h12` の追加**:
    `src/net/http/transport_test.go` に `TestTransportResponse_h12` という新しいテストが追加されました。このテストもまた、HTTP/1とHTTP/2の両方でレスポンスの動作を比較することを目的としていますが、現時点ではスキップされています。これは、HTTP/1とHTTP/2の間でレスポンスの処理に差異があることを示しており、Issue #13315に関連しています。

これらの変更は、`net/http` パッケージがHTTP/2を完全にサポートし、両プロトコル間で一貫した動作を保証するための重要なステップです。テストインフラを整備することで、将来のHTTP/2関連のバグ修正や機能追加がより安全かつ効率的に行えるようになります。

## コアとなるコードの解説

このコミットの核となるのは、`clientServerTest` ヘルパーと、それを利用して既存のテストをHTTP/1とHTTP/2の両方で実行できるようにするアプローチです。

`clientServerTest` 構造体は、テストに必要な `*testing.T`、HTTP/2を使用するかどうかを示す `h2` フラグ、テスト対象の `http.Handler`、`httptest.Server`、`http.Transport`、そして `http.Client` を保持します。

`newClientServerTest` 関数は、この `clientServerTest` のインスタンスを生成し、`h2` フラグに基づいてHTTP/1またはHTTP/2のテスト環境をセットアップします。
*   `h2` が `false` の場合（HTTP/1テスト）、通常の `httptest.NewServer(h)` を使用してHTTP/1.1サーバーを起動します。クライアントはデフォルトの `http.Transport` を使用します。
*   `h2` が `true` の場合（HTTP/2テスト）、`httptest.NewUnstartedServer(h)` でサーバーを起動し、`http.ExportHttp2ConfigureServer(cst.ts.Config, nil)` を呼び出してHTTP/2を有効にします。`cst.ts.TLS = cst.ts.Config.TLSConfig` と `cst.ts.StartTLS()` を使用してTLSを有効にし、HTTP/2のネゴシエーションを可能にします。クライアント側では、`http.Transport` の `TLSClientConfig` を設定し、`http.ExportHttp2ConfigureTransport(cst.tr)` を呼び出してHTTP/2クライアントとして構成します。`InsecureSkipVerify: true` は、テスト環境で自己署名証明書を使用する場合に必要です。

このヘルパーを使用することで、各テスト関数は `newClientServerTest` を呼び出し、`h2` フラグを切り替えるだけで、HTTP/1とHTTP/2の両方で同じテストロジックを実行できるようになります。

例えば、`TestChunkedResponseHeaders` は `testChunkedResponseHeaders` という内部関数にリファクタリングされ、`TestChunkedResponseHeaders_h1` と `TestChunkedResponseHeaders_h2` という2つのエントリポイントが追加されました。
`TestChunkedResponseHeaders_h1` は `testChunkedResponseHeaders(t, false)` を呼び出し、HTTP/1でテストを実行します。
`TestChunkedResponseHeaders_h2` は `testChunkedResponseHeaders(t, true)` を呼び出し、HTTP/2でテストを実行します。この際、`if h2 { t.Skip("known failing test; golang.org/issue/13316") }` の行により、HTTP/2でのテストは意図的にスキップされます。これは、HTTP/2におけるチャンクエンコーディングのヘッダー処理がHTTP/1と異なる可能性があり、まだ修正が必要な問題があることを示しています。

このように、`clientServerTest` ヘルパーと `_h1` / `_h2` バリアントの導入は、`net/http` パッケージのテストカバレッジをHTTP/2に拡張し、両プロトコル間での動作の一貫性を検証するための堅牢なフレームワークを提供します。

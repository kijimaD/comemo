# [インデックス 22666] ファイルの概要

このコミットは、`cmd/gofmt` および `go/format` パッケージ間で重複していたコードを `internal/format` という新しい内部パッケージにリファクタリングするものです。

変更されたファイルは以下の通りです。

-   `src/cmd/gofmt/gofmt.go`: `parse` および `format` 関数の呼び出しが `internal/format` パッケージからのものに変更され、重複していた関数定義が削除されました。
-   `src/cmd/gofmt/long_test.go`: テストコード内の `parse` 関数の呼び出しが `internal/format` パッケージからのものに変更されました。
-   `src/go/format/format.go`: `parse` および `format` 関数の呼び出しが `internal/format` パッケージからのものに変更され、重複していた関数定義が削除されました。
-   `src/internal/format/format.go`: 新規作成されたファイルで、`parse`、`Format` (旧 `format`)、および `IsSpace` (旧 `isSpace`) 関数が定義されています。

## 元コミット内容

`cmd/gofmt` と `go/format` は、`parse`、`format`、`isSpace` の3つの関数を持っており、これらを常に同期させる必要がありました。

この変更は、これら3つの関数を新しい `internal/format` パッケージに抽出し、リファクタリングするものです。
この変更は、動作や意味的な変更を伴わない、単なるコードの再編成です。

## 変更の背景

Go言語の公式フォーマッタである `gofmt` ツール (`cmd/gofmt` パッケージ) と、プログラムからGoコードをフォーマットするためのライブラリである `go/format` パッケージは、歴史的にコードの重複を抱えていました。具体的には、Goソースコードの解析 (`parse`)、フォーマット処理 (`format`)、および空白文字の判定 (`isSpace`) を行う3つのコア関数が、両方のパッケージにほぼ同一の形で存在していました。

このようなコードの重複は、以下のような問題を引き起こします。

1.  **保守性の低下**: 同じロジックが複数の場所に存在するため、バグ修正や機能追加を行う際に、すべての箇所で変更を適用し、同期を保つ必要があります。これはエラーの温床となりやすく、開発コストを増加させます。
2.  **一貫性の欠如のリスク**: 意図せず一方のコードだけが更新され、もう一方が古いままになることで、`gofmt` と `go/format` の間でフォーマット結果に差異が生じる可能性があります。Go言語では `gofmt` による統一されたコードスタイルが非常に重視されるため、これは特に避けたい状況です。
3.  **コードの肥大化**: 不要な重複は、コードベース全体のサイズを増加させ、可読性を損ないます。

このコミットは、これらの問題を解決し、コードベースの健全性を向上させるために、共通のロジックを一元化することを目的としています。

## 前提知識の解説

このコミットの理解を深めるために、以下のGo言語の概念とパッケージについて解説します。

### `gofmt` と `go/format`

-   **`gofmt` (コマンドラインツール)**: Go言語のソースコードを標準的なスタイルに自動的にフォーマットするコマンドラインツールです。Go言語のプロジェクトでは、`gofmt` によって生成されるフォーマットが公式なスタイルとされており、開発者は手動でスタイルを調整する代わりに `gofmt` を実行することが推奨されています。これにより、Goコミュニティ全体で一貫したコードスタイルが保たれています。
-   **`go/format` (パッケージ)**: `gofmt` コマンドの基盤となるライブラリパッケージです。プログラムからGoソースコードをフォーマットする機能を提供します。例えば、IDEやエディタのプラグイン、あるいはコード生成ツールなどが、このパッケージを利用してGoコードを整形することができます。

### `internal` パッケージ

Go言語には、`internal` という特別なディレクトリ名に関する慣習があります。`internal` ディレクトリの下に配置されたパッケージは、その `internal` ディレクトリの親ディレクトリにあるパッケージ、またはその親ディレクトリの兄弟パッケージからのみインポートできます。それ以外の外部パッケージからはインポートできません。

この慣習の目的は、ライブラリの内部実装の詳細を外部に公開せず、APIの安定性を保つことです。`internal` パッケージ内のコードは、外部ユーザーが直接依存すべきではない不安定なAPIや、特定の目的のためにのみ使用されるユーティリティ関数を含むことができます。これにより、ライブラリ開発者は、外部に影響を与えることなく内部実装を自由にリファクタリングできるようになります。

このコミットでは、`cmd/gofmt` と `go/format` の両方から利用される共通のフォーマットロジックを `internal/format` に移動することで、このロジックがGoの標準ライブラリの他の部分や、将来的にGoツールチェインの他の部分からのみ利用されることを保証しています。

### GoのAST (Abstract Syntax Tree)

Goコンパイラやツールは、Goのソースコードを直接操作するのではなく、まずソースコードを抽象構文木 (AST) と呼ばれるデータ構造に変換します。ASTは、プログラムの構造を木構造で表現したもので、各ノードがプログラムの要素（変数宣言、関数呼び出し、式など）に対応します。

-   **`go/parser` パッケージ**: Goソースコードを解析し、ASTを生成する機能を提供します。
-   **`go/ast` パッケージ**: ASTのノード構造を定義しています。
-   **`go/token` パッケージ**: ソースコード内の位置情報（ファイルセット、行番号、列番号など）を管理します。
-   **`go/printer` パッケージ**: ASTをGoソースコードとして整形して出力する機能を提供します。`gofmt` や `go/format` は、`go/parser` でASTを構築し、必要に応じてASTを操作した後、`go/printer` を使って整形されたコードを生成します。

このコミットで移動された `parse` 関数は、`go/parser` を利用してソースコードをASTに変換する役割を担っていました。また、`format` 関数は、`go/printer` を利用してASTを整形されたバイト列に変換する役割を担っていました。

## 技術的詳細

このコミットの核心は、`cmd/gofmt` と `go/format` の両パッケージに存在していた、Goソースコードの解析とフォーマット処理に関する共通のロジックを、`src/internal/format` という新しいパッケージに集約した点にあります。

具体的には、以下の3つの関数が移動されました。

1.  **`parse` 関数**: ソースコードを解析し、`*ast.File` (ASTのルートノード) と、部分的なソースコードの調整を行うためのクロージャ (`sourceAdj`)、およびインデント調整値 (`indentAdj`) を返します。この関数は、完全なGoソースファイルだけでなく、宣言リストやステートメントリストのような部分的なコードフラグメントも解析できる柔軟性を持っていました。
2.  **`format` 関数**: `parse` 関数によって生成されたASTを受け取り、`go/printer` パッケージを使用して整形されたGoソースコードのバイト列を生成します。部分的なソースコードの場合、`sourceAdj` クロージャと `indentAdj` を利用して、元のソースコードの空白やインデントを適切に保持しながら整形を行います。
3.  **`isSpace` 関数**: 特定のバイトが空白文字（スペース、タブ、改行、キャリッジリターン）であるかどうかを判定するユーティリティ関数です。

これらの関数は、以前は `src/cmd/gofmt/gofmt.go` と `src/go/format/format.go` の両方にほぼ同一の形で存在していました。コミットメッセージにある `// TODO(gri) Factor out this functionality, eventually.` というコメントからもわかるように、この重複は認識されており、将来的なリファクタリングの対象となっていました。

リファクタリングのプロセスは以下の通りです。

1.  **新しいパッケージの作成**: `src/internal/format` ディレクトリが作成され、その中に `format.go` ファイルが新規作成されました。
2.  **関数の移動とエクスポート**: 重複していた `parse`、`format`、`isSpace` 関数が `src/internal/format/format.go` に移動されました。これらの関数は、新しいパッケージからアクセスできるように、先頭が大文字の `Parse`、`Format`、`IsSpace` に変更され、エクスポートされました。
3.  **既存パッケージからの参照変更**: `src/cmd/gofmt/gofmt.go` と `src/go/format/format.go` の両方で、削除されたローカルの `parse` および `format` 関数の呼び出しが、新しくインポートした `internal/format` パッケージの `format.Parse` および `format.Format` に変更されました。同様に、`isSpace` の呼び出しも `format.IsSpace` に変更されました。
4.  **インポートパスの更新**: 関連するファイルで `internal/format` パッケージがインポートされるようになりました。

この変更は、機能的な振る舞いを一切変更せず、純粋にコードの構造を改善することを目的としています。これにより、`gofmt` と `go/format` の間でフォーマットロジックの一貫性が保証され、将来的なメンテナンスが容易になります。また、`internal` パッケージを使用することで、この共通ロジックがGoツールチェインの内部でのみ使用されることが明確になり、外部の依存関係が意図せず発生するのを防ぎます。

## コアとなるコードの解説

このコミットの主要な変更は、`parse`、`format`、`isSpace` という3つの関数が `src/cmd/gofmt/gofmt.go` と `src/go/format/format.go` から削除され、新しく作成された `src/internal/format/format.go` に移動されたことです。

### `internal/format/format.go` の `Parse` 関数

元の `parse` 関数が `internal/format` パッケージに移動され、`Parse` としてエクスポートされました。この関数は、GoソースコードをASTに解析する役割を担います。

-   `parser.ParseFile` を使用して、与えられたソースコード (`src`) をAST (`*ast.File`) に変換します。
-   完全なGoソースファイルだけでなく、`fragmentOk` が `true` の場合は、パッケージ宣言がない宣言リストやステートメントリストのようなコードフラグメントも適切に解析できるように、内部で一時的に `package p;` や `package p; func _() { ... }` のようなラッパーを追加して解析を試みます。
-   部分的なソースコードを解析した場合、整形後に元のソースコードのインデントや空白を復元するための `sourceAdj` クロージャと `indentAdj` 値を返します。

### `internal/format/format.go` の `Format` 関数

元の `format` 関数が `internal/format` パッケージに移動され、`Format` としてエクスポートされました。この関数は、ASTを整形されたGoソースコードのバイト列に変換します。

-   `printer.Config` を使用して、フォーマットのモード（タブ/スペース、タブ幅など）を設定します。
-   `cfg.Fprint` を呼び出して、ASTをバイトバッファに書き込みます。
-   `Parse` 関数が部分的なソースコードを扱った場合 (`sourceAdj != nil`)、元のソースコードの先頭と末尾の空白、およびインデントを考慮して、整形されたコードを調整します。これにより、部分的なコードフラグメントが元のコンテキストに埋め込まれた際に、不自然なフォーマットにならないようにします。

### `internal/format/format.go` の `IsSpace` 関数

元の `isSpace` 関数が `internal/format` パッケージに移動され、`IsSpace` としてエクスポートされました。これは単純なユーティリティ関数で、与えられたバイトがスペース、タブ、改行、キャリッジリターンのいずれかであるかを判定します。`Format` 関数内で、ソースコードの先頭と末尾の空白を検出するために使用されます。

### 呼び出し元の変更

`src/cmd/gofmt/gofmt.go` と `src/go/format/format.go` では、これらの関数がローカルに定義されていた部分が削除され、代わりに `internal/format` パッケージをインポートし、`format.Parse` や `format.Format` のように新しいパスで関数を呼び出すように変更されました。これにより、両パッケージは共通のコードベースを参照するようになり、コードの重複が解消されました。

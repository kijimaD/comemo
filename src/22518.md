# [インデックス 22518] ファイルの概要

このコミットは、Goコンパイラのx86アーキテクチャ向けアセンブラコード生成部分、具体的には`src/cmd/internal/obj/x86/asm6.go`ファイルに対する変更です。このファイルは、Goプログラムがx86-64アーキテクチャ向けにコンパイルされる際に、アセンブリ命令を生成する役割を担っています。特に、Goランタイムが内部的に使用する最適化されたメモリ操作ルーチンである`duffcopy`および`duffzero`の呼び出しに関するアセンブリコード生成ロジックを扱っています。

## 変更の背景

この変更は、`GOEXPERIMENT=framepointer`というビルドオプションが有効になっている場合に、`duffcopy`および`duffzero`というGoランタイムの内部関数が正しく動作しない、またはプロファイリングツールで正確なスタックトレースが得られない問題を修正するために導入されました。

`GOEXPERIMENT=framepointer`は、Goコンパイラが生成するアセンブリコードにフレームポインタを含めるように指示する実験的な機能です。フレームポインタは、スタックフレームの基底アドレスを指すレジスタ（x86-64では`RBP`）であり、これを使用することで、Linux perfなどのプロファイリングツールやデバッガが、より効率的かつ正確にコールスタックを再構築できるようになります。これにより、プログラムの実行状況を詳細に分析し、パフォーマンスボトルネックを特定する能力が向上します。

しかし、`duffcopy`や`duffzero`のような高度に最適化されたアセンブリルーチンは、通常の関数呼び出し規約とは異なる方法でスタックを操作することがあります。特に、これらの関数は「Duff's Device」と呼ばれるテクニックを用いてループアンローリングを行い、メモリ操作を高速化しています。この最適化されたコードは、フレームポインタの維持に関する通常のルールに従わないため、`GOEXPERIMENT=framepointer`が有効な場合に、プロファイリングツールがこれらの関数内での呼び出し元を正しく追跡できなくなる可能性がありました。

このコミットは、`duffcopy`および`duffzero`の呼び出し前後でベースポインタ（BP）を明示的に保存・復元するアセンブリ命令を挿入することで、この問題を解決し、フレームポインタベースのプロファイリングツールがこれらの最適化されたルーチンを正しく扱えるようにすることを目的としています。

## 前提知識の解説

1.  **フレームポインタ (Frame Pointer)**:
    *   関数呼び出しにおいて、現在のスタックフレームの基底アドレスを指すレジスタです。x86-64アーキテクチャでは通常`RBP`レジスタが使用されます。
    *   フレームポインタを使用すると、関数呼び出しの連鎖（コールスタック）を容易に辿ることができ、デバッグやプロファイリングにおいて非常に有用です。
    *   パフォーマンス最適化のために、一部のコンパイラはフレームポインタを省略し、`RBP`を汎用レジスタとして使用することがあります。これにより、レジスタの利用効率が向上し、わずかながら実行速度が向上する可能性があります。
    *   Go言語では、デフォルトではフレームポインタは省略されますが、`GOEXPERIMENT=framepointer`オプションを有効にすることで、フレームポインタを生成させることができます。

2.  **`duffcopy`と`duffzero`**:
    *   Goランタイム内部で使用される、メモリ操作を高速化するためのアセンブリ関数です。
    *   `duffcopy`はメモリブロックを効率的にコピーするために使用され、`duffzero`はメモリブロックをゼロで埋めるために使用されます。
    *   これらの関数は、Duff's Deviceというテクニックを応用して実装されています。これは、ループアンローリングとジャンプテーブルを組み合わせることで、ループのオーバーヘッドを最小限に抑え、大量のデータを高速に処理することを可能にします。
    *   Goコンパイラは、大きな構造体や配列のコピー・ゼロ初期化が必要な場合に、これらの関数への呼び出しを自動的に挿入します。
    *   これらの関数は、通常の関数呼び出しとは異なり、特定のオフセットにジャンプすることで処理を開始するため、スタックフレームの構造が通常の関数とは異なります。

3.  **Goの`obj`パッケージとアセンブラ (cmd/internal/obj)**:
    *   `cmd/internal/obj`パッケージは、Goコンパイラの一部であり、Goソースコードからターゲットアーキテクチャ（x86、ARMなど）のアセンブリコードを生成する役割を担っています。
    *   `asm6.go`ファイルは、x86-64アーキテクチャ向けのアセンブリコード生成ロジックを含んでいます。ここでは、Goの抽象的な命令が、実際のx86アセンブリ命令に変換されます。
    *   このパッケージは、Goのクロスコンパイル能力の基盤を形成しており、異なるアーキテクチャ向けに最適化されたコードを生成するために不可欠です。

4.  **PC相対アドレッシング (PC-relative addressing)**:
    *   命令ポインタ（Program Counter, PC）からの相対的なオフセットを使用してメモリ位置を指定するアドレッシングモードです。
    *   これにより、コードがメモリ内のどこにロードされても正しく動作する、位置独立コード（Position-Independent Code, PIC）を生成できます。
    *   リンカは、PC相対リロケーションを適用する際に、命令の終わりからの相対オフセットを計算します。このコミットでは、この計算が特定のケースで正しく行われるように調整されています。

## 技術的詳細

このコミットの核心は、`GOEXPERIMENT=framepointer`が有効な環境で`duffcopy`および`duffzero`が呼び出される際に、ベースポインタ（BP）の整合性を維持することにあります。

`duffcopy`や`duffzero`は、通常の`CALL`命令で呼び出されるものの、その実体は関数の中間地点にジャンプするような特殊な構造を持っています。これにより、通常の関数呼び出し規約（プロローグでBPを保存し、エピローグでBPを復元する）が適用されにくく、フレームポインタベースのプロファイリングツールがコールスタックを正しく辿れなくなる問題がありました。

この修正では、`asm6.go`内のアセンブリコード生成ロジックに以下の変更が加えられました。

1.  **`Zcallduff`の導入**: `yduff`テーブル（`duffcopy`/`duffzero`に関連する命令の定義）において、従来の`Zcall`の代わりに新しい命令タイプ`Zcallduff`が導入されました。これにより、`duffcopy`/`duffzero`の呼び出しを通常の`CALL`命令と区別できるようになります。
2.  **BPの保存と復元**:
    *   `doasm`関数内で、`Zcallduff`タイプの命令が処理される際に、`obj.Framepointer_enabled`が有効で、かつ64ビットモード（`p.Mode == 64`）である場合に、特別なアセンブリ命令シーケンスが挿入されるようになりました。
    *   呼び出し命令の直前には、`MOVQ BP, -16(SP)`と`LEAQ -16(SP), BP`という命令が挿入されます。これは、現在のBPレジスタの値をスタックに保存し、新しいBPをスタック上の保存されたBPの場所を指すように設定することで、`duffcopy`/`duffzero`が実行されている間も有効なフレームポインタチェーンを維持します。
    *   呼び出し命令の直後には、`MOVQ 0(BP), BP`という命令が挿入されます。これは、呼び出し前に保存されたBPの値をBPレジスタに復元し、通常のフレームポインタチェーンに戻します。
    *   これらの命令は、`duffcopy`/`duffzero`が関数の中間地点にジャンプする性質上、これらのルーチン自体でBPの保存・復元を行うことが困難であるため、呼び出し元側で明示的に行うことで、プロファイリングツールが正確なスタックトレースを生成できるようにします。
3.  **PC相対リロケーションの調整**: `asmins`関数において、PC相対アドレッシングのリロケーション計算が調整されました。これは、命令の終わりからの相対オフセットと、リロケーションの終わりからの相対オフセットが一致しない場合に、リンカが正しくリロケーションを適用できるようにするためのものです。これにより、`duffcopy`/`duffzero`のような特殊なコードパスでも、PC相対アドレッシングが正しく機能することが保証されます。

これらの変更により、`GOEXPERIMENT=framepointer`が有効な環境下でも、`duffcopy`および`duffzero`の呼び出しがプロファイリングツールによって正しく解釈され、Goプログラムのパフォーマンス分析とデバッグの精度が向上しました。

## コアとなるコードの変更箇所

`src/cmd/internal/obj/x86/asm6.go`ファイルにおける主要な変更点は以下の通りです。

1.  **`const`ブロックへの`Zcallduff`の追加**:
    ```go
    const (
    	Zbr
    	Zcall
    	Zcallcon
    	Zcallduff // 新規追加
    	Zcallind
    	Zcallindreg
    	Zib_
    	// ...
    )
    ```
2.  **`yduff`テーブルの変更**:
    ```go
    var yduff = []ytab{
    	{Ynone, Ynone, Yi32, Zcallduff, 1}, // Zcall から Zcallduff に変更
    }
    ```
3.  **`bpduff1`と`bpduff2`バイト配列の追加**:
    ```go
    var bpduff1 = []byte{
    	0x48, 0x89, 0x6c, 0x24, 0xf0, // MOVQ BP, -16(SP)
    	0x48, 0x8d, 0x6c, 0x24, 0xf0, // LEAQ -16(SP), BP
    }

    var bpduff2 = []byte{
    	0x90,
    	0x48, 0x8b, 0x6d, 0x00, // MOVQ 0(BP), BP
    }
    ```
4.  **`doasm`関数内の`Zcallduff`処理の追加**:
    ```go
    func doasm(ctxt *obj.Link, p *obj.Prog) {
    	// ...
    	case Zcall, Zcallduff: // Zcallduff が追加
    		// ...
    		if obj.Framepointer_enabled != 0 && yt.zcase == Zcallduff && p.Mode == 64 {
    			// Maintain BP around call, since duffcopy/duffzero can't do it
    			// (the call jumps into the middle of the function).
    			// This makes it possible to see call sites for duffcopy/duffzero in
    			// BP-based profiling tools like Linux perf (which is the
    			// whole point of obj.Framepointer_enabled).
    			// MOVQ BP, -16(SP)
    			// LEAQ -16(SP), BP
    			copy(ctxt.Andptr, bpduff1)
    			ctxt.Andptr = ctxt.Andptr[len(bpduff1):]
    		}
    		ctxt.Andptr[0] = byte(op)
    		ctxt.Andptr = ctxt.Andptr[1:]
    		// ...
    		if obj.Framepointer_enabled != 0 && yt.zcase == Zcallduff && p.Mode == 64 {
    			// Pop BP pushed above.
    			// MOVQ 0(BP), BP
    			copy(ctxt.Andptr, bpduff2)
    			ctxt.Andptr = ctxt.Andptr[len(bpduff2):]
    		}
    		// ...
    }
    ```
5.  **`asmins`関数内のPC相対リロケーションの条件変更**:
    ```go
    func asmins(ctxt *obj.Link, p *obj.Prog) {
    	// ...
    	// 変更前: if r.Type == obj.R_PCREL || r.Type == obj.R_CALL {
    	if r.Type == obj.R_PCREL { // obj.R_CALL が削除
    		// PC-relative addressing is relative to the end of the instruction,
    		// but the relocations applied by the linker are relative to the end
    		// of the relocation. Because immediate instruction
    		// arguments can follow the PC-relative memory reference in the
    		// instruction encoding, the two may not coincide. In this case,
    		// adjust addend so that linker can keep relocating relative to the
    		// end of the relocation.
    		r.Add -= p.Pc + int64(n) - (int64(r.Off) + int64(r.Siz))
    	}
    	// ...
    }
    ```

## コアとなるコードの解説

1.  **`Zcallduff`の導入と`yduff`の変更**:
    *   `Zcallduff`という新しい定数を導入することで、Goコンパイラは`duffcopy`/`duffzero`の呼び出しを、通常の関数呼び出し（`Zcall`）とは異なる特殊なケースとして認識できるようになりました。
    *   `yduff`テーブルは、`duffcopy`/`duffzero`のような特殊な命令のパターンを定義しています。このテーブルで`Zcall`を`Zcallduff`に変更することで、これらの命令が`doasm`関数内で特別な処理を受けるためのトリガーとなります。

2.  **`bpduff1`と`bpduff2`**:
    *   `bpduff1`は、`duffcopy`/`duffzero`の呼び出し前にベースポインタ（BP）を保存し、スタックポインタ（SP）を基点とした新しいフレームポインタを設定するためのアセンブリ命令のバイト列です。
        *   `MOVQ BP, -16(SP)`: 現在のBPレジスタの値を、現在のSPから16バイト下のスタック位置に保存します。
        *   `LEAQ -16(SP), BP`: SPから16バイト下のスタック位置のアドレスをBPレジスタにロードします。これにより、BPがスタック上の保存されたBPの場所を指すようになり、プロファイリングツールがスタックを辿れるようになります。
    *   `bpduff2`は、`duffcopy`/`duffzero`の実行後にBPを元の値に復元するためのアセンブリ命令のバイト列です。
        *   `MOVQ 0(BP), BP`: BPが指すアドレス（以前に保存されたBPの値）から値を読み出し、それをBPレジスタにロードします。これにより、BPは呼び出し前の状態に戻ります。
        *   `0x90`は`NOP`（No Operation）命令であり、アライメント調整や将来の拡張のために挿入されている可能性があります。

3.  **`doasm`関数内のBP保存・復元ロジック**:
    *   `doasm`関数は、Goの抽象的な命令を実際のx86アセンブリ命令に変換する主要な部分です。
    *   `case Zcall, Zcallduff:`ブロック内で、`obj.Framepointer_enabled`が有効で、かつ`Zcallduff`タイプの命令（すなわち`duffcopy`/`duffzero`の呼び出し）が64ビットモードで検出された場合に、上記の`bpduff1`と`bpduff2`のバイト列がそれぞれ呼び出し命令の直前と直後に挿入されます。
    *   この条件分岐により、フレームポインタが不要な環境ではオーバーヘッドが発生せず、必要な環境でのみBPの整合性維持のためのコードが生成されるようになっています。

4.  **`asmins`関数内のPC相対リロケーションの調整**:
    *   `asmins`関数は、アセンブリ命令のバイト列を生成し、リロケーション情報を設定する役割を担っています。
    *   変更前は、`obj.R_PCREL`（PC相対）または`obj.R_CALL`（関数呼び出し）タイプのリロケーションに対して同じ調整ロジックが適用されていました。
    *   変更後は、`obj.R_CALL`が条件から削除され、`obj.R_PCREL`タイプのリロケーションのみにこの調整が適用されるようになりました。
    *   追加されたコメントは、PC相対アドレッシングが命令の終わりからの相対オフセットを使用するのに対し、リンカが適用するリロケーションはリロケーションの終わりからの相対オフセットを使用するという違いを説明しています。命令の引数がPC相対メモリ参照の後に続く場合、これら二つが一致しない可能性があるため、リンカがリロケーションの終わりからの相対でリロケーションを継続できるように、`r.Add`（リロケーションの加算値）を調整しています。これにより、`duffcopy`/`duffzero`のような特殊なコードパスでも、PC相対アドレッシングが正しく機能することが保証されます。

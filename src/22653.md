# [インデックス 22653] ファイルの概要

このコミットは、Goコンパイラ (`cmd/internal/gc`) がコンパイル中のパッケージのインポートパスを直接生成するように変更し、Goリンカ (`cmd/internal/ld`) から関連する不要なコードを削除することを目的としています。これにより、共有ライブラリ環境でのパッケージのインポートパスの取り扱いが改善され、リンカの複雑性が軽減されます。

## 変更の背景

Goのビルドシステムでは、パッケージのインポートパスは、コンパイルされたコードが他のパッケージから参照される際に重要な識別子となります。従来のGoのビルドプロセスでは、インポートパスの解決やシンボルの生成において、インポートするパッケージとインポートされるパッケージが同時にリンクされることを前提としている部分がありました。

しかし、この前提は共有ライブラリ（ダイナミックリンクライブラリ）を使用する環境では問題となります。共有ライブラリでは、各ライブラリが独立してコンパイル・リンクされ、実行時に動的にロードされます。このため、インポートする側とインポートされる側が常に同時にリンクされるとは限りません。

このコミットの背景には、Goが共有ライブラリをより適切にサポートするための改善があります。具体的には、リンカがインポートパスに関する「あいまいなコード」を保持しており、これが共有ライブラリのシナリオで問題を引き起こす可能性がありました。この変更により、コンパイラ (`gc`) がコンパイル時に自身のインポートパスを直接生成するようになり、リンカ (`ld`) の負担を軽減し、共有ライブラリ環境での堅牢性を向上させることが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムと関連する概念についての知識が必要です。

*   **Goコンパイラ (`gc`)**: Goのソースコードをコンパイルしてオブジェクトファイルを生成するツールです。Goの標準コンパイラは `gc` と呼ばれ、`cmd/compile` パッケージ内に実装されています。
*   **Goリンカ (`ld`)**: コンパイラによって生成されたオブジェクトファイルやアーカイブファイルを結合し、実行可能ファイルや共有ライブラリを生成するツールです。Goの標準リンカは `ld` と呼ばれ、`cmd/link` パッケージ内に実装されています。
*   **パッケージのインポートパス**: Goのパッケージは、そのソースコードが配置されているディレクトリのパスによって一意に識別されます。例えば、`"fmt"` や `"net/http"` などがインポートパスです。コンパイラやリンカは、このインポートパスを使用してパッケージ間の依存関係を解決します。
*   **シンボル**: コンパイルされたプログラム内の関数、変数、型などの名前付きエンティティは、リンカによって解決されるシンボルとして表現されます。インポートパスもまた、特定のシンボルとして扱われることがあります。
*   **共有ライブラリ (Shared Libraries / Dynamic Link Libraries)**: 複数のプログラムで共有されるライブラリの形式です。プログラムの実行時に動的にロードされ、メモリを節約したり、ライブラリの更新を容易にしたりする利点があります。Goは、バージョン1.5以降で共有ライブラリのサポートを強化しています。
*   **`importpath` シンボル**: Goの内部では、パッケージのインポートパスを表すために `go.importpath."<path>"` のような形式のシンボルが使用されることがあります。これは、リンカが実行時に正しいインポートパスを解決するために利用されます。
*   **`localpkg` と `Runtimepkg`**:
    *   `localpkg`: 現在コンパイル中のパッケージを表す内部的な `Pkg` オブジェクトです。
    *   `Runtimepkg`: Goランタイムパッケージ (`runtime`) を表す内部的な `Pkg` オブジェクトです。`runtime` パッケージはGoプログラムの実行に不可欠な低レベルの機能を提供します。

## 技術的詳細

このコミットの核心は、Goのコンパイルおよびリンクプロセスにおけるインポートパスの取り扱い方法の変更にあります。

以前のGoのビルドシステムでは、パッケージのインポートパスに関する情報（`importpath` シンボル）は、リンカがインポートするパッケージとインポートされるパッケージを同時に処理する際に、ある種の「書き換え」を行うことで解決されていました。特に、コンパイラが自身のインポートパスを完全に知らなかった場合（例えば、`-p` フラグがコンパイラに渡されなかった場合）、`go.importpath.""` のようなプレースホルダーシンボルを生成し、リンカがこれを実際のインポートパスに書き換えるというメカニズムが存在しました。

このアプローチは、静的リンクが主流の環境では機能しましたが、共有ライブラリの導入により問題が顕在化しました。共有ライブラリでは、個々のライブラリが独立してコンパイル・リンクされるため、リンカが常にインポートする側とインポートされる側の両方のコンテキストを持つとは限りません。このため、リンカがインポートパスの書き換えを行うことが困難になるか、あるいは不正確になる可能性がありました。

このコミットでは、この問題を解決するために、コンパイラ (`gc`) がコンパイル時に自身のインポートパスを直接生成するように変更されます。これにより、リンカの「あいまいなコード」が不要になり、リンカの役割が簡素化されます。

具体的には、`src/cmd/internal/gc/reflect.go` 内の `dimportpath` 関数が変更され、以下のロジックが追加されました。

1.  **`runtime` パッケージの特殊な扱い**: `runtime` パッケージをコンパイルしている場合、`localpkg` と `Runtimepkg` の2つの `runtime` パッケージが存在する可能性があります。この変更では、`localpkg` のインポートパスシンボルのみを生成し、`Runtimepkg` の重複生成を避けるようにしています。これは、`runtime` パッケージがGoのビルドシステム内で特殊な役割を果たすためです。
2.  **`localpkg` のインポートパスの直接生成**: `p == localpkg` (現在コンパイル中のパッケージ) の場合、`myimportpath` (コンパイラに渡された自身のインポートパス) を使用して `importpath.<prefix>.` シンボルを直接生成します。これにより、リンカによる後からの書き換えが不要になります。
3.  **`dgopkgpath` の変更**: `dgopkgpath` 関数も変更され、`localpkg` であり、かつ `myimportpath` が空の場合（つまり、コンパイラが自身のインポートパスを完全に知らない場合）にのみ、従来の `go.importpath.""` シンボルを生成するように制限されます。これは、後方互換性のため、または特定のビルドシナリオでまだリンカによる書き換えが必要な場合に備えて残されています。

一方、`src/cmd/internal/ld/lib.go` からは、`go.importpath.runtime/cgo.` シンボルに関するコードが削除されました。これは、コンパイラがインポートパスを直接生成するようになったため、リンカがこのシンボルを「シミュレート」したり、特別な処理を行う必要がなくなったためです。この削除により、リンカのコードベースがクリーンアップされ、保守性が向上します。

この変更は、Goのビルドシステムが共有ライブラリをより堅牢にサポートするための重要なステップであり、コンパイラとリンカ間の責任分担をより明確にすることで、全体的なシステムの複雑性を軽減しています。

*   **シンボル**: コンパイルされたプログラム内の関数、変数、型などの名前付きエンティティは、リンカによって解決されるシンボルとして表現されます。インポートパスもまた、特定のシンボルとして扱われることがあります。
*   **共有ライブラリ (Shared Libraries / Dynamic Link Libraries)**: 複数のプログラムで共有されるライブラリの形式です。プログラムの実行時に動的にロードされ、メモリを節約したり、ライブラリの更新を容易にしたりする利点があります。Goは、バージョン1.5以降で共有ライブラリのサポートを強化しています。
*   **`importpath` シンボル**: Goの内部では、パッケージのインポートパスを表すために `go.importpath."<path>"` のような形式のシンボルが使用されることがあります。これは、リンカが実行時に正しいインポートパスを解決するために利用されます。
*   **`localpkg` と `Runtimepkg`**:
    *   `localpkg`: 現在コンパイル中のパッケージを表す内部的な `Pkg` オブジェクトです。
    *   `Runtimepkg`: Goランタイムパッケージ (`runtime`) を表す内部的な `Pkg` オブジェクトです。`runtime` パッケージはGoプログラムの実行に不可欠な低レベルの機能を提供します。

## 技術的詳細

このコミットの核心は、Goのコンパイルおよびリンクプロセスにおけるインポートパスの取り扱い方法の変更にあります。

以前のGoのビルドシステムでは、パッケージのインポートパスに関する情報（`importpath` シンボル）は、リンカがインポートするパッケージとインポートされるパッケージを同時に処理する際に、ある種の「書き換え」を行うことで解決されていました。特に、コンパイラが自身のインポートパスを完全に知らなかった場合（例えば、`-p` フラグがコンパイラに渡されなかった場合）、`go.importpath.""` のようなプレースホルダーシンボルを生成し、リンカがこれを実際のインポートパスに書き換えるというメカニズムが存在しました。

このアプローチは、静的リンクが主流の環境では機能しましたが、共有ライブラリの導入により問題が顕在化しました。共有ライブラリでは、個々のライブラリが独立してコンパイル・リンクされるため、リンカが常にインポートする側とインポートされる側の両方のコンテキストを持つとは限りません。このため、リンカがインポートパスの書き換えを行うことが困難になるか、あるいは不正確になる可能性がありました。

このコミットでは、この問題を解決するために、コンパイラ (`gc`) がコンパイル時に自身のインポートパスを直接生成するように変更されます。これにより、リンカの「あいまいなコード」が不要になり、リンカの役割が簡素化されます。

具体的には、`src/cmd/internal/gc/reflect.go` 内の `dimportpath` 関数が変更され、以下のロジックが追加されました。

1.  **`runtime` パッケージの特殊な扱い**: `runtime` パッケージをコンパイルしている場合、`localpkg` と `Runtimepkg` の2つの `runtime` パッケージが存在する可能性があります。この変更では、`localpkg` のインポートパスシンボルのみを生成し、`Runtimepkg` の重複生成を避けるようにしています。これは、`runtime` パッケージがGoのビルドシステム内で特殊な役割を果たすためです。
2.  **`localpkg` のインポートパスの直接生成**: `p == localpkg` (現在コンパイル中のパッケージ) の場合、`myimportpath` (コンパイラに渡された自身のインポートパス) を使用して `importpath.<prefix>.` シンボルを直接生成します。これにより、リンカによる後からの書き換えが不要になります。
3.  **`dgopkgpath` の変更**: `dgopkgpath` 関数も変更され、`localpkg` であり、かつ `myimportpath` が空の場合（つまり、コンパイラが自身のインポートパスを完全に知らない場合）にのみ、従来の `go.importpath.""` シンボルを生成するように制限されます。これは、後方互換性のため、または特定のビルドシナリオでまだリンカによる書き換えが必要な場合に備えて残されています。

一方、`src/cmd/internal/ld/lib.go` からは、`go.importpath.runtime/cgo.` シンボルに関するコードが削除されました。これは、コンパイラがインポートパスを直接生成するようになったため、リンカがこのシンボルを「シミュレート」したり、特別な処理を行う必要がなくなったためです。この削除により、リンカのコードベースがクリーンアップされ、保守性が向上します。

この変更は、Goのビルドシステムが共有ライブラリをより堅牢にサポートするための重要なステップであり、コンパイラとリンカ間の責任分担をより明確にすることで、全体的なシステムの複雑性を軽減しています。

## コアとなるコードの変更箇所

### `src/cmd/internal/gc/reflect.go` の変更

`dimportpath` 関数と `dgopkgpath` 関数が変更されました。

*   **`dimportpath` 関数**:
    *   `runtime` パッケージの特殊な処理が追加され、`Runtimepkg` のインポートパスシンボル生成をスキップするようになりました。
    *   `localpkg` (現在コンパイル中のパッケージ) の場合、`myimportpath` を使用してインポートパスシンボルを直接生成するロジックが追加されました。

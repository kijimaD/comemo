## 元コミット内容

`net: make newLocalListener handle network argument correcly`

このコミットは、Go言語の `net` パッケージ内のテストユーティリティである `newLocalListener` 関数が、`network` 引数を正しく処理するように修正するものです。具体的には、`"tcp"` ネットワークタイプが指定された場合のIPv4とIPv6のリスニング動作を改善します。

## 変更の背景

Go言語の `net` パッケージは、ネットワーク通信のための基本的なインターフェースを提供します。`net.Listen` 関数は、指定されたネットワークアドレスで着信接続をリッスンするために使用されます。この関数には、`"tcp"`, `"tcp4"`, `"tcp6"`, `"udp"`, `"unix"` などのネットワークタイプを指定できます。

`mockserver_test.go` は、`net` パッケージのテストにおいて、モックのネットワークリスナーを作成するためのファイルです。`newLocalListener` 関数は、テスト目的でローカルアドレスにバインドするリスナーを生成します。

以前の実装では、`"tcp"`, `"tcp4"`, `"tcp6"` のケースがまとめて処理されていました。これは、`"tcp"` が指定された場合に、システムがIPv4とIPv6の両方をサポートしている環境で、意図しない動作を引き起こす可能性がありました。特に、`"tcp"` は通常、デュアルスタックソケット（IPv4とIPv6の両方を受け入れるソケット）を作成しようとしますが、テスト環境では特定のプロトコル（IPv4またはIPv6）でのみリスニングしたい場合があります。

このコミットの目的は、`"tcp"` が指定されたときに、まずIPv4でのリスニングを試み、それが成功しない場合やサポートされていない場合にIPv6でのリスニングにフォールバックするという、より明確で予測可能な動作を `newLocalListener` に持たせることです。これにより、テストの信頼性と再現性が向上します。

## 前提知識の解説

### TCP/IP (Transmission Control Protocol/Internet Protocol)
インターネットの基盤となる通信プロトコル群です。TCPは信頼性の高いデータ転送を保証し、IPはデータのルーティングを担当します。

### IPv4 (Internet Protocol version 4)
現在広く使用されているIPアドレスのバージョンです。32ビットのアドレス空間を持ち、`192.168.1.1` のような形式で表現されます。アドレス枯渇の問題が指摘されています。

### IPv6 (Internet Protocol version 6)
IPv4の後継として開発されたIPアドレスのバージョンです。128ビットのアドレス空間を持ち、`2001:0db8:85a3:0000:0000:8a2e:0370:7334` のような形式で表現されます。IPv4アドレス枯渇問題の解決策として期待されています。

### `net.Listen` 関数 (Go言語)
Go言語の `net` パッケージで提供される関数で、指定されたネットワークアドレスで着信接続をリッスンする `Listener` インターフェースを返します。
シグネチャは `func Listen(network, address string) (Listener, error)` です。
- `network`: ネットワークタイプを指定します。例: `"tcp"`, `"tcp4"`, `"tcp6"`, `"udp"`, `"unix"`。
- `address`: リッスンするアドレスを指定します。例: `"127.0.0.1:8080"` (IPv4), `"[::1]:8080"` (IPv6), `":8080"` (利用可能なすべてのインターフェース)。

### ネットワークタイプ `"tcp"`, `"tcp4"`, `"tcp6"` の違い
- `"tcp"`: TCPプロトコルを使用し、システムがサポートする任意のIPバージョン（IPv4またはIPv6）でリッスンします。多くの場合、デュアルスタックソケットを作成しようとします。
- `"tcp4"`: TCPプロトコルを使用し、IPv4アドレスでのみリッスンします。
- `"tcp6"`: TCPプロトコルを使用し、IPv6アドレスでのみリッスンします。

### デュアルスタックソケット
単一のソケットでIPv4とIPv6の両方の接続を受け入れることができるソケットです。これにより、アプリケーションはIPv4とIPv6の両方のクライアントに対応できます。しかし、その挙動はOSや設定によって異なる場合があります。

## 技術的詳細

このコミットは、`src/net/mockserver_test.go` 内の `newLocalListener` 関数におけるネットワークタイプ `"tcp"` の処理ロジックを改善します。

以前の実装では、`switch network` ステートメントで `"tcp"`, `"tcp4"`, `"tcp6"` が同じ `case` ブロックで処理されていました。このブロック内では、まず `supportsIPv4` が真であれば `tcp4` でリスニングを試み、そうでなければ `supportsIPv6` が真であれば `tcp6` でリスニングを試みていました。

このアプローチの問題点は、`network` 引数が `"tcp"` の場合に、意図した動作と異なる結果になる可能性があったことです。Goの `net` パッケージにおいて、`"tcp"` は通常、システムがIPv4とIPv6の両方をサポートしている場合、デュアルスタックソケットを作成しようとします。しかし、テスト環境では、特定のプロトコル（IPv4またはIPv6）でのみリスニングを確立したい場合があります。

新しい実装では、`"tcp"` のケースが独立して扱われます。
1.  `"tcp"` が指定された場合、まず `supportsIPv4` が真であれば、`"tcp4"` ネットワークタイプと `127.0.0.1:0` アドレス（ローカルホストのIPv4アドレスと利用可能なポート）で `Listen` を試みます。
2.  もしIPv4でのリスニングが成功した場合、そのリスナーを返します。
3.  IPv4でのリスニングが失敗した場合、または `supportsIPv4` が偽の場合、次に `supportsIPv6` が真であれば、`"tcp6"` ネットワークタイプと `[::1]:0` アドレス（ローカルホストのIPv6アドレスと利用可能なポート）で `Listen` を試みます。
4.  `"tcp4"` と `"tcp6"` のケースは、それぞれ独立した `case` ブロックで処理され、それぞれのプロトコルに厳密に従ってリスニングを試みます。

この変更により、`newLocalListener` は `"tcp"` が指定された際に、まずIPv4を優先し、次にIPv6にフォールバックするという明確な順序でリスニングを試みるようになります。これにより、テストの意図がより正確に反映され、異なる環境でのテストの挙動の不確実性が減少します。特に、テストが特定のIPバージョンに依存する場合に重要です。

## コアとなるコードの解説

変更された `newLocalListener` 関数は、`network` 引数に基づいてローカルリスナーを作成します。

### 変更前:

```go
	switch network {
	case "tcp", "tcp4", "tcp6":
		if supportsIPv4 {
			return Listen("tcp4", "127.0.0.1:0")
		}
		if supportsIPv6 {
			return Listen("tcp6", "[::1]:0")
		}
		// ... (エラーハンドリングなど)
```
このコードでは、`"tcp"`, `"tcp4"`, `"tcp6"` のいずれが指定されても、同じロジックが実行されます。まずIPv4がサポートされていればIPv4でリスニングを試み、それが失敗するかサポートされていなければIPv6でリスニングを試みます。この挙動は、特に `"tcp"` が指定された場合に、デュアルスタックの意図と異なる可能性がありました。例えば、`"tcp"` が指定されたときにIPv4とIPv6の両方でリッスンすることを期待するテストがある場合、この実装ではどちらか一方でのみリッスンすることになります。

### 変更後:

```go
	switch network {
	case "tcp": // 新しい独立したケース
		if supportsIPv4 { // IPv4がサポートされているか
			if ln, err := Listen("tcp4", "127.0.0.1:0"); err == nil { // IPv4でリスニングを試みる
				return ln, nil // 成功したら返す
			}
		}
		if supportsIPv6 { // IPv4が失敗またはサポートされていない場合、IPv6がサポートされているか
			return Listen("tcp6", "[::1]:0") // IPv6でリスニングを試みる
		}
	case "tcp4": // 独立したtcp4ケース
		if supportsIPv4 {
			return Listen("tcp4", "127.0.0.1:0")
		}
	case "tcp6": // 独立したtcp6ケース
		if supportsIPv6 {
			return Listen("tcp6", "[::1]:0")
		}
		// ... (エラーハンドリングなど)
```

-   **`case "tcp":` の追加**:
    -   `network` 引数が `"tcp"` の場合、この新しいブロックが実行されます。
    -   まず `supportsIPv4` が `true` であれば、`Listen("tcp4", "127.0.0.1:0")` を呼び出し、IPv4ローカルホストの利用可能なポートでリスニングを試みます。成功すればそのリスナーを返します。
    -   IPv4でのリスニングが失敗したか、`supportsIPv4` が `false` の場合、次に `supportsIPv6` が `true` であれば、`Listen("tcp6", "[::1]:0")` を呼び出し、IPv6ローカルホストの利用可能なポートでリスニングを試みます。
    -   このロジックにより、`"tcp"` が指定された場合、IPv4を優先し、次にIPv6にフォールバックするという明確な動作が保証されます。これは、テストが特定のIPバージョンを期待する場合や、環境によってデュアルスタックの挙動が異なる場合に重要です。

-   **`case "tcp4":` と `case "tcp6":` の分離**:
    -   以前は `"tcp"` と同じブロックで処理されていましたが、変更後はそれぞれ独立した `case` ブロックになりました。
    -   `"tcp4"` が指定された場合は、`supportsIPv4` が `true` であれば必ずIPv4でリスニングを試みます。
    -   `"tcp6"` が指定された場合は、`supportsIPv6` が `true` であれば必ずIPv6でリスニングを試みます。
    -   これにより、各ネットワークタイプがその意図するプロトコルに厳密に従って処理されるようになり、コードの意図がより明確になります。

この変更は、`net` パッケージのテストの堅牢性を高め、異なるネットワーク環境下でのテストの予測可能性と信頼性を向上させるものです。

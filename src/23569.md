# [インデックス 23569] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける重要な機能拡張とクリーンアップを目的としています。具体的には、より多くの命令（ロード、ストア、ビットテスト、グローバル変数のアドレス取得、分岐、メモリコピーなど）をSSA形式で扱えるようにし、コード生成の精度と効率を向上させています。また、nilチェックや境界チェックの生成を専用関数に分離することで、コードのモジュール化と保守性を高めています。フレームポインタ（FP）とスタックポインタ（SP）の扱いも汎用化され、特定のオペコードに依存しない設計へと変更されています。

変更された主なファイルは以下の通りです。

*   `src/cmd/internal/gc/ssa.go`: GoのASTからSSAグラフを構築する主要なファイル。新しい命令の処理、アドレス生成、nil/境界チェックの分離、FP/SPの初期化ロジックが追加されています。
*   `src/cmd/internal/obj/x86/6.out.go`: x86アーキテクチャのアセンブリ命令定義。新しい条件分岐命令が追加されています。
*   `src/cmd/internal/ssa/check.go`: SSAグラフの整合性チェックを行うファイル。制御フロー値の型チェックが更新されています。
*   `src/cmd/internal/ssa/config.go`: SSAコンフィギュレーション。ポインタ算術型名の変更が含まれます。
*   `src/cmd/internal/ssa/generic.go`: アーキテクチャ非依存のSSA書き換えルール。`ArrayIndex`、`IsInBounds`、`Mul`、`PtrIndex`、`Store`などの新しいルールが追加されています。
*   `src/cmd/internal/ssa/lower.go`: SSAオペレーションをアーキテクチャ固有の命令に変換する「Lowering」フェーズのロジック。条件分岐ブロックの処理が拡張されています。
*   `src/cmd/internal/ssa/lowerAmd64.go`: AMD64アーキテクチャ固有のLoweringルール。ロード、ストア、アドレス計算、定数、グローバル変数、メモリ移動に関する多くのルールが追加・修正されています。
*   `src/cmd/internal/ssa/op.go`: SSAオペレーションの定義。`FP`、`SP`、`Move`、`ArrayIndex`、`PtrIndex`、`OffPtr`などの新しいオペレーションが追加され、`GlobalOffset`構造体も拡張されています。
*   `src/cmd/internal/ssa/op_string.go`: `op.go`で定義されたオペレーションの文字列表現を生成するためのファイル。新しいオペレーションに合わせて更新されています。
*   `src/cmd/internal/ssa/opamd64.go`: AMD64アーキテクチャ固有のSSAオペレーション定義。`TESTB`、`LEAQglobal`、`MOVBload`、`REPMOVSB`などの新しいオペレーションが追加されています。

## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドの成熟と最適化の推進があります。初期のSSA実装では、すべてのGo言語のセマンティクスを直接SSAオペレーションに変換できるわけではなく、一部はより低レベルな中間表現やアセンブリコード生成フェーズで処理されていました。このコミットは、SSA形式で表現できる命令の範囲を拡大し、より多くのGo言語の構造（特にメモリ操作、アドレス計算、配列/スライスインデックス、nil/境界チェック）をSSAレベルで直接扱うことを可能にすることで、以下のメリットをもたらします。

1.  **最適化の機会の増加**: SSA形式はデータフロー解析や最適化に非常に適しています。より多くの命令がSSAで表現されることで、コンパイラはより広範な最適化（例: 共通部分式除去、デッドコード削除、レジスタ割り当ての改善）をSSAレベルで適用できるようになります。
2.  **コード生成の品質向上**: SSAレベルで詳細な情報を持つことで、バックエンドはより効率的でコンパクトなアセンブリコードを生成できます。特に、アドレス計算やメモリ操作の最適化は、生成されるバイナリのパフォーマンスに直結します。
3.  **コンパイラの構造の改善**: nilチェックや境界チェックのような共通の処理を専用関数に分離することで、コードの重複を減らし、コンパイラのコードベースをよりクリーンで保守しやすいものにします。また、FP/SPの扱いを汎用化することで、将来的なアーキテクチャサポートの柔軟性も向上します。
4.  **Rematerializationの拡大**: Rematerializationは、メモリから値をロードする代わりに、その値を再計算する最適化です。これにより、レジスタの競合を減らし、メモリ帯域幅の使用を最適化できます。より多くのオペコードがこの最適化の対象となることで、全体的なパフォーマンスが向上します。

要するに、このコミットはGoコンパイラのSSAバックエンドをより強力で、効率的で、保守しやすいものにするための重要な一歩と言えます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. Goコンパイラの構造

Goコンパイラは、ソースコードを最終的な機械語に変換するために複数のフェーズを経ます。

*   **フロントエンド**: Goのソースコードを解析し、抽象構文木（AST）を構築します。型チェックや名前解決もここで行われます。
*   **中間表現 (IR)**: ASTは、コンパイラが最適化やコード生成を行いやすい形式に変換されます。Goコンパイラでは、主にSSA (Static Single Assignment) 形式がこの中間表現として使用されます。
*   **SSA (Static Single Assignment)**:
    *   SSAは、各変数が一度だけ代入されるようにする中間表現の形式です。これにより、データフロー解析が非常に容易になります。
    *   SSAグラフは、`Value` (値) と `Block` (基本ブロック) で構成されます。
    *   `Value` は、計算結果や定数、メモリの状態などを表します。各 `Value` には `Op` (オペレーション)、`Type` (型)、`Args` (引数)、`Aux` (補助情報) があります。
    *   `Block` は、一連の `Value` を含む基本ブロックで、制御フローを表します。
    *   SSA形式では、変数の定義と使用の関係が明確になるため、最適化が容易になります。
*   **Lowering (低レベル化)**: SSA形式のオペレーションを、ターゲットアーキテクチャ（例: AMD64）のより低レベルな命令セットに近づけるフェーズです。このフェーズで、汎用的なSSAオペレーションが具体的なアセンブリ命令にマッピングされます。
*   **バックエンド**: LoweringされたIRを基に、最終的なアセンブリコードを生成し、レジスタ割り当てなどの最適化を行います。

### 2. SSAの主要な概念

*   **Value**: SSAグラフのノードであり、計算結果、定数、メモリの状態などを表します。
    *   `Op`: `Value` が実行する操作の種類（例: `OpAdd`, `OpLoad`, `OpStore`）。
    *   `Type`: `Value` の型（例: `TypeInt64`, `TypeBool`, `TypeMem`）。
    *   `Args`: `Value` の入力となる他の `Value`。
    *   `Aux`: `Value` の操作を修飾する追加情報（例: 定数値、オフセット、シンボル）。
*   **Block**: 制御フローグラフのノードであり、一連の `Value` を含みます。
    *   `Kind`: `Block` の種類（例: `BlockPlain`, `BlockIf`, `BlockExit`）。
    *   `Control`: `Block` の制御フローを決定する `Value`（例: `BlockIf` の条件式）。
*   **TypeMem**: メモリの状態を表す特殊な型です。SSAでは、メモリへの読み書きも `Value` として扱われ、メモリの依存関係を明示的に表現することで、メモリ操作の最適化を可能にします。
*   **FP (Frame Pointer)**: 現在の関数のスタックフレームの基点を示すポインタ。ローカル変数や引数へのアクセスに使用されます。
*   **SP (Stack Pointer)**: スタックの現在のトップを示すポインタ。
*   **Nilチェック**: ポインタが`nil`でないことを確認する実行時チェック。Goでは、`nil`ポインタのデリファレンスはパニックを引き起こします。
*   **境界チェック (Bounds Check)**: 配列やスライスへのアクセスが有効な範囲内にあることを確認する実行時チェック。Goでは、範囲外アクセスはパニックを引き起こします。
*   **Rematerialization**: ある値をメモリからロードする代わりに、その値を再計算する最適化手法。レジスタの競合を減らし、メモリへのアクセスを減らすことでパフォーマンスを向上させることができます。

### 3. x86/AMD64アセンブリの基本

*   **LEAQ (Load Effective Address)**: メモリから値をロードするのではなく、オペランドのアドレスをレジスタにロードする命令。アドレス計算によく使われます。
*   **TESTB**: 2つのオペランドのビット単位ANDを実行し、結果に基づいてフラグレジスタを設定する命令。通常、特定のビットがセットされているか、または値がゼロであるかをテストするために使用されます。
*   **条件分岐命令 (Jcc)**: フラグレジスタの状態に基づいてプログラムの実行フローを変更する命令（例: `JEQ` (等しい場合ジャンプ), `JNE` (等しくない場合ジャンプ), `JLT` (より小さい場合ジャンプ)）。
*   **REPMOVSB**: メモリブロックをコピーするための命令。

これらの概念を理解することで、コミットがGoコンパイラの内部でどのように機能し、どのような影響を与えるかをより深く把握できます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドに多岐にわたる変更を加えています。以下に主要な変更点をファイルごとに詳しく解説します。

### `src/cmd/internal/gc/ssa.go`

このファイルは、GoのASTからSSAグラフを構築するGoコンパイラのフロントエンドとSSAバックエンドの間のブリッジとして機能します。

*   **`ssaState` から `state` へのリネーム**: `ssaState` 構造体が `state` にリネームされ、より簡潔になりました。
*   **FP/SPの明示的な導入**:
    *   `state` 構造体に `startmem`, `fp`, `sp` フィールドが追加されました。これらはそれぞれ、初期のメモリ状態、フレームポインタ、スタックポインタを表すSSA `Value` です。
    *   `buildssa` 関数内で、これらの `Value` が `OpArg`, `OpFP`, `OpSP` オペレーションを使って初期化されるようになりました。これにより、FPとSPがSSAグラフ内で明示的に追跡され、より汎用的な方法で扱えるようになります。
    *   以前は `OpFPAddr` や `OpSPAddr` のような特殊なオペコードでFP/SPからのオフセットを直接扱っていましたが、今後は `OpFP` や `OpSP` を基点としてアドレス計算を行うようになります。
*   **関数の終端処理の改善**:
    *   `buildssa` 関数内で、関数が値を返さない場合のフォールスルー（fallthrough）を `s.exit` ブロックに接続するロジックが追加されました。これにより、関数の終了時の制御フローがより正確に表現されます。
*   **`addr` 関数の導入**:
    *   `expr` 関数からアドレス生成ロジックが分離され、新しく `addr` 関数が導入されました。この関数は、`ONAME` (変数)、`OINDREG` (レジスタからの間接参照)、`OINDEX` (配列/スライスインデックス) などのGoのASTノードから、対応するSSA形式のアドレス `Value` を生成します。
    *   `ONAME` の場合、グローバル変数 (`PEXTERN`) やパラメータスロット (`PPARAMOUT`) のアドレスを `OpGlobal` や `OpOffPtr` を使って生成します。
    *   `OINDEX` の場合、配列とスライスで異なるアドレス計算を行います。配列の場合は `OpPtrIndex` を使用し、スライスの場合は `OpSlicePtr` と `OpPtrIndex` を組み合わせてアドレスを計算します。
*   **`nilCheck` および `boundsCheck` 関数の分離**:
    *   以前は `expr` 関数内にインラインで記述されていたnilポインタチェックと境界チェックのロジックが、それぞれ `nilCheck` と `boundsCheck` という独立した関数に分離されました。
    *   これらの関数は、`OpIsNonNil` や `OpIsInBounds` オペレーションを使用してチェックを行い、条件に応じて `s.exit` ブロック（パニック発生時）に分岐する制御フローを生成します。これにより、コードの重複が排除され、チェックロジックの再利用性が向上します。
*   **`OAS` (代入) 処理の改善**:
    *   `OAS` オペレーションの処理が大幅に簡素化されました。SSAで追跡可能な変数への代入は直接 `s.vars` マップを更新し、それ以外の複雑な代入（例: 構造体のフィールドへの代入、グローバル変数への代入）は `addr` 関数でアドレスを生成し、`OpStore` オペレーションとして扱われるようになりました。
*   **`OIND` (間接参照) および `ODOTPTR` (ポインタフィールドアクセス) 処理の改善**:
    *   これらのオペレーションは、`nilCheck` 関数を呼び出してnilポインタチェックを明示的に行うようになりました。その後、`OpLoad` オペレーションを使用してメモリから値をロードします。
*   **`OINDEX` (配列/スライスインデックス) 処理の改善**:
    *   配列とスライスで異なる処理を行うようになりました。配列の場合は `OpArrayIndex` を使用し、スライスの場合は `addr` 関数でアドレスを生成し、`OpLoad` オペレーションを使用します。どちらの場合も `boundsCheck` 関数を呼び出して境界チェックを行います。
*   **`lookupVarIncoming` の変更**:
    *   エントリブロックでのメモリ引数の取得に `s.startmem` を使用するようになり、引数のロードに `OpOffPtr` と `s.fp` を使用するようになりました。

### `src/cmd/internal/obj/x86/6.out.go`

このファイルはx86アセンブリ命令の定数を定義しています。

*   **条件分岐命令のコメント更新**: `AJCC`, `AJCS`, `AJEQ`, `AJGE`, `AJGT`, `AJHI`, `AJLE`, `AJLS`, `AJLT`, `AJMI`, `AJNE`, `AJOC`, `AJOS`, `AJPC`, `AJPL`, `AJPS` などの条件分岐命令に、その意味（例: `AJCC // >= unsigned`）を明確にするコメントが追加されました。

### `src/cmd/internal/ssa/check.go`

SSAグラフの整合性チェックを行うファイルです。

*   **制御フロー値の型チェックの改善**: `BlockExit` および `BlockCall` の `Control` 値が `TypeMem` ではなく `Type.IsMemory()` でチェックされるようになり、`BlockIf` の `Control` 値が `TypeBool` ではなく `Type.IsBoolean()` でチェックされるようになりました。これにより、より汎用的な型チェックが可能になります。

### `src/cmd/internal/ssa/config.go`

SSAコンフィギュレーションを定義するファイルです。

*   **`UIntPtr` から `Uintptr` へのリネーム**: `Config` 構造体内のポインタ算術型を表すフィールド名が `UIntPtr` から `Uintptr` へと変更されました。これは命名規則の統一のためと考えられます。

### `src/cmd/internal/ssa/generic.go`

アーキテクチャ非依存のSSA書き換えルールを定義するファイルです。

*   **`OpAdd` のルール変更**: `isSigned(t)` の条件が削除され、64ビット整数型であれば符号の有無に関わらず定数加算の最適化が適用されるようになりました。
*   **`OpArrayIndex` の新しいルール**: `(ArrayIndex (Load ptr mem) idx)` を `(Load (PtrIndex <ptr.Type.Elem().Elem().PtrTo()> ptr idx) mem)` に書き換えるルールが追加されました。これは、配列要素へのアクセスをポインタインデックスとロード操作に分解するものです。
*   **`OpIsInBounds` の新しいルール**: `(IsInBounds (Const [c]) (Const [d]))` を `(Const [inBounds(c.(int64),d.(int64))])` に書き換えるルールが追加されました。これは、定数による境界チェックをコンパイル時に解決するものです。
*   **`OpMul` のルール変更**: `isSigned(t)` の条件が削除され、64ビット整数型であれば符号の有無に関わらず定数乗算の最適化が適用されるようになりました。
*   **`OpPtrIndex` の新しいルール**: `(PtrIndex <t> ptr idx)` を `(Add ptr (Mul <v.Block.Func.Config.Uintptr> idx (Const <v.Block.Func.Config.Uintptr> [t.Elem().Size()])))` に書き換えるルールが追加されました。これは、ポインタインデックス操作をポインタ加算と乗算に分解するものです。
*   **`OpSliceCap` および `OpSliceLen` のルール変更**: スライス容量と長さの計算において、`v.Block.Func.Config.UIntPtr` が `v.Block.Func.Config.Uintptr` に変更されました。
*   **`OpStore` の新しいルール**: `(Store dst (Load <t> src mem) mem)` を `(Move [t.Size()] dst src mem)` に書き換えるルールが追加されました。これは、大きなサイズのメモリコピーを `OpMove` オペレーションに変換するものです。

### `src/cmd/internal/ssa/lower.go`

SSAオペレーションをアーキテクチャ固有の命令に変換するLoweringフェーズのロジックです。

*   **条件分岐ブロックの変換ロジックの拡張**:
    *   `BlockIf` の `Control` オペレーションが `OpSETL`, `OpSETNE`, `OpSETB`, `OpMOVBload` の場合、それぞれ `BlockLT`, `BlockNE`, `BlockULT`, `BlockNE` に変換されるようになりました。
    *   `BlockLT`, `BlockGT`, `BlockLE`, `BlockGE`, `BlockULT`, `BlockUGT`, `BlockULE`, `BlockUGE`, `BlockEQ`, `BlockNE` の各ブロックで、`Control` オペレーションが `OpInvertFlags` の場合、対応する逆の条件分岐ブロックに変換されるロジックが追加されました。これにより、条件反転の最適化がLoweringフェーズで適用されます。
    *   これらの変換はループ内で行われ、複数の変換が連続して適用される可能性があります。

### `src/cmd/internal/ssa/lowerAmd64.go`

AMD64アーキテクチャ固有のLoweringルールです。

*   **`ADDCQ` のルール変更**:
    *   `LEAQ8` との組み合わせでオフセットを加算する際に `addOff` ヘルパー関数を使用するようになりました。
    *   オフセットが0の `ADDCQ` を `Copy` オペレーションに変換するルールが追加されました。
*   **`ADDQ` のルール変更**: `(ADDQ x (Const [c]))` や `(ADDQ (Const [c]) x)` のような定数加算が、`OpMOVQconst` を介して `ADDCQ` に変換されるようになりました。
*   **`CMPQ` のルール変更**: `(CMPQ x (Const [c]))` や `(CMPQ (Const [c]) x)` のような定数比較が、`OpMOVQconst` を介して `CMPCQ` に変換されるようになりました。また、定数が左オペランドにある場合は `InvertFlags` を使用してフラグを反転させます。
*   **`OpConst` の新しいルール**: 64ビット整数型の `OpConst` を `OpMOVQconst` に変換するルールが追加されました。
*   **`OpGlobal` の新しいルール**: `OpGlobal` を `OpLEAQglobal` に変換するルールが追加されました。
*   **`OpLoad` の新しいルール**:
    *   ブーリアン型の `OpLoad` を `OpMOVBload` に変換するルールが追加されました。
    *   64ビット整数型またはポインタ型の `OpLoad` を `OpMOVQload` に変換するルールが追加されました。
*   **`MOVQload` のルール変更**:

## コアとなるコードの解説

### `src/cmd/internal/gc/ssa.go` の `state` 構造体と関連関数の変更

1.  **`state` 構造体**:
    *   `startmem *ssa.Value`: 関数のエントリポイントにおけるメモリの状態を表す `Value` です。SSAではメモリも `Value` として扱われ、メモリ操作の依存関係を明示的に表現します。
    *   `fp *ssa.Value`: フレームポインタを表す `Value` です。これにより、スタックフレーム上の引数やローカル変数へのアクセスがSSAグラフ内で追跡可能になります。
    *   `sp *ssa.Value`: スタックポインタを表す `Value` です。
    *   これらのフィールドの追加により、FPとSPがSSAグラフの「開始値」として明示的に導入され、それらに対する操作がSSAオペレーションとして表現されるようになります。これは、以前の `OpFPAddr` や `OpSPAddr` のような特殊なオペコードに依存しない、より汎用的なアプローチです。

2.  **`buildssa` 関数内のFP/SP初期化**:
    ```go
    s.startmem = s.f.Entry.NewValue(ssa.OpArg, ssa.TypeMem, ".mem")
    s.fp = s.f.Entry.NewValue(ssa.OpFP, s.config.Uintptr, nil)
    s.sp = s.f.Entry.NewValue(ssa.OpSP, s.config.Uintptr, nil)
    ```
    *   `s.f.Entry.NewValue(...)` は、関数のエントリブロックで新しい `Value` を作成します。
    *   `ssa.OpArg` は、関数の引数として渡されるメモリの状態を表します。
    *   `ssa.OpFP` と `ssa.OpSP` は、それぞれフレームポインタとスタックポインタを表す新しいオペレーションです。`s.config.Uintptr` は、ポインタのサイズに応じた符号なし整数型（32ビットまたは64ビット）を示します。

3.  **`addr` 関数の導入**:
    ```go
    // expr converts the address of the expression n to SSA, adds it to s and returns the SSA result.
    func (s *state) addr(n *Node) *ssa.Value {
        switch n.Op {
        case ONAME:
            if n.Class == PEXTERN {
                return s.f.Entry.NewValue(ssa.OpGlobal, Ptrto(n.Type), n.Sym)
            }
            if n.Class == PPARAMOUT {
                return s.f.Entry.NewValue1(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.fp)
            }
            // ...
        case OINDREG:
            return s.f.Entry.NewValue1(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.sp)
        case OINDEX:
            if n.Left.Type.Bound >= 0 { // array
                a := s.addr(n.Left)
                i := s.expr(n.Right)
                len := s.f.ConstInt(s.config.Uintptr, n.Left.Type.Bound)
                s.boundsCheck(i, len)
                return s.curBlock.NewValue2(ssa.OpPtrIndex, Ptrto(n.Left.Type.Type), nil, a, i)
            } else { // slice
                // ...
            }
        // ...
        }
    }
    ```
    *   `addr` 関数は、GoのASTノード `n` から、そのアドレスを表すSSA `Value` を生成します。
    *   `ONAME` (変数) の場合、グローバル変数であれば `OpGlobal` を、パラメータスロットであれば `OpOffPtr` (FPからのオフセット) を使用します。
    *   `OINDREG` (レジスタからの間接参照) の場合も `OpOffPtr` (SPからのオフセット) を使用します。
    *   `OINDEX` (配列/スライスインデックス) の場合、配列であれば `boundsCheck` を行った後、`OpPtrIndex` を使用して要素のアドレスを計算します。スライスの場合も同様に `boundsCheck` を行い、`OpSlicePtr` と `OpPtrIndex` を組み合わせてアドレスを計算します。
    *   この関数により、アドレス計算ロジックが一元化され、`expr` 関数がよりクリーンになりました。

4.  **`nilCheck` および `boundsCheck` 関数の分離**:
    ```go
    // nilCheck generates nil pointer checking code.
    // Starts a new block on return.
    func (s *state) nilCheck(ptr *ssa.Value) {
        c := s.curBlock.NewValue1(ssa.OpIsNonNil, ssa.TypeBool, nil, ptr)
        b := s.endBlock()
        b.Kind = ssa.BlockIf
        b.Control = c
        bNext := s.f.NewBlock(ssa.BlockPlain)
        addEdge(b, bNext)
        addEdge(b, s.exit)
        s.startBlock(bNext)
        // ...
    }

    // boundsCheck generates bounds checking code.  Checks if 0 <= idx < len, branches to exit if not.
    // Starts a new block on return.
    func (s *state) boundsCheck(idx, len *ssa.Value) {
        // ...
        cmp := s.curBlock.NewValue2(ssa.OpIsInBounds, ssa.TypeBool, nil, idx, len)
        b := s.endBlock()
        b.Kind = ssa.BlockIf
        b.Control = cmp
        bNext := s.f.NewBlock(ssa.BlockPlain)
        addEdge(b, bNext)
        addEdge(b, s.exit)
        // ...
        s.startBlock(bNext)
    }
    ```
    *   これらの関数は、それぞれnilポインタチェックと境界チェックのSSAコードを生成します。
    *   `OpIsNonNil` と `OpIsInBounds` オペレーションを使用して条件を評価し、結果に基づいて `BlockIf` を作成し、チェックが失敗した場合は `s.exit` ブロック（パニック発生時）に分岐するようにします。
    *   これにより、`expr` 関数内の冗長なチェックロジックが削除され、コードの可読性と保守性が向上しました。

5.  **`OAS` (代入) 処理の簡素化**:
    ```go
    case OAS:
        val := s.expr(n.Right)
        if n.Left.Op == ONAME && !n.Left.Addrtaken && n.Left.Class&PHEAP == 0 && n.Left.Class != PEXTERN && n.Left.Class != PPARAMOUT {
            // ssa-able variable.
            s.vars[n.Left.Sym.Name] = val
            return
        }
        // not ssa-able.  Treat as a store.

        s.vars[".mem"] = s.curBlock.NewValue3(ssa.OpStore, ssa.TypeMem, nil, addr, val, s.mem())

    ```
    *   代入の左辺がSSAで直接扱える変数（アドレスが取られておらず、ヒープにない、グローバルでもパラメータでもない）の場合、その変数の `Value` を直接更新します。
    *   それ以外の場合（複雑な式、グローバル変数、パラメータスロットなど）は、`addr` 関数で左辺のアドレスを生成し、`OpStore` オペレーションとしてメモリへの書き込みとして扱います。これにより、代入の処理がより汎用的になりました。

### `src/cmd/internal/ssa/op.go` の新しいオペレーション定義

*   **`OpFP`, `OpSP`**: これらのオペレーションは、フレームポインタとスタックポインタをSSAグラフ内で明示的な `Value` として表現するために導入されました。これにより、FP/SPに対する操作（例: オフセット加算）を他のポインタ操作と同様に扱えるようになり、コンパイラの汎用性が向上します。
*   **`OpMove`**: メモリブロックをコピーするための新しいオペレーションです。`arg0` が宛先ポインタ、`arg1` がソースポインタ、`arg2` がメモリ状態、`aux` がコピーサイズを表します。これは、`memcpy` のような操作をSSAレベルで表現するために使用されます。
*   **`OpArrayIndex`**: 配列要素へのアクセスを表すオペレーションです。`arg0` が配列、`arg1` がインデックスです。これにより、配列アクセスがSSAグラフ内でより明確に表現されます。
*   **`OpPtrIndex`**: ポインタとインデックスから新しいポインタを計算するオペレーションです。`ptr + sizeof(*v.type) * index` の形式でアドレスを計算します。これは、配列やスライス要素のアドレス計算の基盤となります。
*   **`OpOffPtr`**: ポインタに定数オフセットを加算するオペレーションです。`arg0 + aux.(int64)` の形式で、FPやSPからのオフセット計算に利用されます。
*   **`GlobalOffset` 構造体の拡張**: `offset` メソッドと `String` メソッドが追加され、グローバル変数のオフセットをより柔軟に扱えるようになりました。

これらの変更は、GoコンパイラのSSAバックエンドがGo言語のセマンティクスをより正確かつ効率的に表現し、最適化するための基盤を強化するものです。特に、メモリ操作とアドレス計算の抽象化と汎用化は、コンパイラの将来的な拡張性とパフォーマンス向上に大きく貢献します。

# [インデックス 20407] ファイルの概要

このコミットは、Goランタイムにおける`getgcmask`関数の実行コンテキストを変更するものです。具体的には、この関数が通常のゴルーチンスタックではなく、M（OSスレッド）のシステムスタック（g0スタック）上で実行されるように修正されています。これにより、ガベージコレクション（GC）関連の処理の安定性と正確性が向上します。

## 元コミット内容

Goランタイムにおいて、`getgcmask`関数をM（OSスレッド）のスタック上で実行するように変更。

## 変更の背景

`getgcmask`関数は、Goのガベージコレクション（GC）がオブジェクトのポインタ情報を取得するために使用する内部関数です。この関数は、特定のメモリ領域がポインタを含んでいるかどうかを示すバイトマスクを生成します。GCの正確な動作には、このポインタ情報の正確な取得が不可欠です。

Goランタイムでは、ゴルーチンは動的にサイズが変化するスタック（ユーザーゴルーチンスタック）を使用します。一方、OSスレッド（M）には、ランタイムの内部処理（スケジューラ、GC、CGOなど）を実行するための固定サイズのシステムスタック（g0スタック）があります。

`getgcmask`のようなGCの根幹に関わる関数が、ユーザーゴルーチンスタック上で実行される場合、スタックの動的な拡張や縮小、あるいはゴルーチンのプリエンプションなどによって、予期せぬ問題や競合状態が発生する可能性がありました。特に、GCがスタックをスキャンする際に、そのスタック自体が変更されると、GCの正確性が損なわれる恐れがあります。

このコミットの目的は、`getgcmask`の実行をMのシステムスタックに移行することで、このような潜在的な問題を回避し、GC処理の安定性と信頼性を向上させることにあります。MのシステムスタックはGCによってスキャンされないため、GC関連の内部処理をより安全かつ予測可能な環境で実行できます。

## 前提知識の解説

### GoランタイムのGMPモデル

Goのランタイムスケジューラは、G（Goroutine）、M（Machine/OS Thread）、P（Processor）という3つの主要な要素から構成される「GMPモデル」を採用しています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数KBのスタックで開始し、必要に応じて動的に伸縮します。GoアプリケーションのコードはG上で実行されます。
*   **M (Machine/OS Thread)**: 実際のOSスレッドです。Goのコードを実行する物理的な実行コンテキストを提供します。Mは、ユーザーゴルーチンコードの実行、ランタイムコードの実行、システムコールでのブロックなど、様々な状態を取り得ます。各Mは、自身のシステムスタック（g0スタック）とシグナルスタックを持ちます。
*   **P (Processor)**: 論理的なプロセッサであり、MがGを実行するために必要なコンテキスト（スケジューラの状態、メモリ割り当ての状態など）を提供します。Pの数は通常、`GOMAXPROCS`環境変数によって制御され、デフォルトではCPUの論理コア数に設定されます。Pは、MがGを実行するための「許可証」のような役割を果たし、MとGを効率的にマッチングさせます。

### スタックの種類

Goランタイムには主に2種類のスタックが存在します。

1.  **ユーザーゴルーチンスタック**: 各Gに割り当てられるスタックで、Goアプリケーションのコードが実行されます。このスタックは動的にサイズが変更されます。
2.  **Mのシステムスタック (g0スタック)**: 各Mに割り当てられる固定サイズのスタックです。Goランタイムの内部コード（スケジューラ、ガベージコレクタ、CGO関連コードなど）が実行される際に使用されます。このスタックはGCの対象外であり、GCの実行中に安全に操作できる領域として機能します。

### ガベージコレクション (GC)

GoのGCは、並行（concurrent）かつ三色マーク・アンド・スイープ（tri-color mark-and-sweep）アルゴリズムをベースにしています。

*   **マークフェーズ**: プログラムが使用している「生きている」オブジェクト（到達可能なオブジェクト）を識別します。このフェーズの大部分はアプリケーションの実行と並行して行われます。
*   **スイープフェーズ**: マークされなかった（到達不可能と判断された）オブジェクトが占めていたメモリを解放します。これも並行して行われます。
*   **三色抽象化**: オブジェクトを白（未マーク、ガベージの可能性あり）、灰（マーク済みだが参照先は未スキャン）、黒（マーク済みで参照先もスキャン済み）の3色に分類して管理します。
*   **ライトバリア**: 並行マークフェーズ中にオブジェクト参照の変更を追跡し、GCの正確性を保証するためのメカニズムです。
*   **Stop-The-World (STW) ポーズ**: GCの特定の段階では、アプリケーションの実行を一時的に停止させる必要がありますが、GoのGCはこれらのSTWポーズを極めて短く（通常は100マイクロ秒以下）抑えるように設計されています。
*   **`getgcmask`関数**: このコミットの主題である`getgcmask`は、GCがメモリをスキャンする際に、どの部分がポインタを含んでいるかを判断するために使用される内部関数です。これにより、GCはポインタではないデータ（整数など）を誤ってスキャンすることを避け、効率的にポインタを追跡できます。

## 技術的詳細

このコミットの核心は、`getgcmask`関数の実行コンテキストを、ユーザーゴルーチンスタックからMのシステムスタック（g0スタック）へ変更することです。

Goのランタイムは、`onM`という内部関数を提供しており、これを使用すると、指定された関数を現在のMのシステムスタック上で実行させることができます。システムスタックは、GCの対象外であり、またゴルーチンのプリエンプションの影響を受けにくい安定した環境です。

`getgcmask`は、GCがメモリ内のポインタを正確に識別するために非常に重要な役割を担っています。特に、スタック上のオブジェクトをスキャンする際には、スタックフレームの構造や変数の配置に関する正確な情報が必要です。ユーザーゴルーチンスタックは動的に伸縮するため、その上で`getgcmask`のような低レベルのGC関連関数を実行すると、スタックの変更とGCスキャンのタイミングが競合し、不正確な結果を招く可能性がありました。

Mのシステムスタック上で`getgcmask`を実行することで、以下の利点が得られます。

1.  **安定した実行環境**: システムスタックはGCの対象外であり、ユーザーゴルーチンスタックのような動的な変更やプリエンプションの影響を受けにくいため、`getgcmask`はより安定した環境で実行できます。
2.  **GCの正確性の向上**: GCがスタックをスキャンする際に、`getgcmask`が常に正確なポインタマスク情報を提供できるようになります。これにより、GCが誤ってポインタではないデータをスキャンしたり、重要なポインタを見落としたりするリスクが低減されます。
3.  **競合状態の回避**: GC処理とユーザーゴルーチンスタックの操作との間の潜在的な競合状態を回避できます。

この変更は、GoのGCの堅牢性と信頼性を高めるための重要なステップです。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  `src/pkg/runtime/export_test.go`:
    *   `GCMask`関数の定義が変更されています。以前は直接`runtime·getgcmask`を呼び出していましたが、新しい実装では`onM`関数を使用して`getgcmask`をMのシステムスタック上で実行するようにラップしています。
    *   `getgcmask`のGo言語側の宣言が追加されています。
2.  `src/pkg/runtime/mgc0.c`:
    *   `getgcmaskcb`関数のスタックフレームチェックロジックが修正されています。
    *   `runtime·getgcmask`関数内で、`runtime·gentraceback`の呼び出しにおけるスタックポインタの取得方法が変更されています。以前は`runtime·getcallerpc`と`runtime·getcallersp`を使用していましたが、新しい実装では`g->m->curg->sched.pc`と`g->m->curg->sched.sp`を使用しています。これは、現在のゴルーチンのスケジューラ情報からPC（プログラムカウンタ）とSP（スタックポインタ）を取得することで、より正確なスタックトレースを生成するためと考えられます。
3.  `src/pkg/runtime/stubs.goc`:
    *   以前の`GCMask`関数の定義が削除されています。これは、`export_test.go`で新しい`GCMask`が定義されたためです。

## コアとなるコードの解説

### `src/pkg/runtime/export_test.go` の変更

```go
// 旧:
// //go:noescape
// func GCMask(x interface{}) []byte

// 新:
//go:noescape
func getgcmask(data unsafe.Pointer, typ *_type, array **byte, len *uint)

func GCMask(x interface{}) (ret []byte) {
	e := (*eface)(unsafe.Pointer(&x))
	s := (*slice)(unsafe.Pointer(&ret))
	onM(func() {
		getgcmask(e.data, e._type, &s.array, &s.len)
		s.cap = s.len
	})
	return
}
```

この変更が最も重要です。
*   以前は`GCMask`が直接`getgcmask`（C言語で実装されたランタイム関数）を呼び出していました。
*   新しい実装では、`getgcmask`という内部関数をGo言語側で宣言し、その上で`GCMask`関数を再定義しています。
*   再定義された`GCMask`の中では、`onM(func() { ... })`という構造が導入されています。`onM`はGoランタイムの内部関数で、引数として渡されたクロージャを現在のM（OSスレッド）のシステムスタック（g0スタック）上で実行します。
*   これにより、`getgcmask`の実際の呼び出しが、ユーザーゴルーチンスタックではなく、より安定したMのシステムスタック上で行われるようになります。`e.data`、`e._type`、`s.array`、`s.len`といった引数は、`getgcmask`が必要とするデータ（インターフェースのデータポインタ、型情報、結果のスライス配列ポインタ、長さポインタ）を渡しています。

### `src/pkg/runtime/mgc0.c` の変更

```c
// 旧:
// 	if(frame0->sp >= frame->varp - frame->sp && frame0->sp < frame->varp) {

// 新:
// 	if(frame->sp <= frame0->sp && frame0->sp < frame->varp) {
```
`getgcmaskcb`関数内のスタックフレームチェックの条件が変更されています。これは、スタックの成長方向やフレームの配置に関するより正確なチェックを行うための修正と考えられます。

```c
// 旧:
// 	runtime·gentraceback((uintptr)runtime·getcallerpc(&p), (uintptr)runtime·getcallersp(&p), 0, g, 0, nil, 1000, &cb, &frame, false);

// 新:
// 	runtime·gentraceback(g->m->curg->sched.pc, g->m->curg->sched.sp, 0, g->m->curg, 0, nil, 1000, &cb, &frame, false);
```
`runtime·getgcmask`関数内で、スタックトレースを生成する`runtime·gentraceback`の呼び出し元PC（プログラムカウンタ）とSP（スタックポインタ）の取得方法が変更されています。
*   旧バージョンでは、`runtime·getcallerpc(&p)`と`runtime·getcallersp(&p)`というヘルパー関数を使用して、現在の関数の呼び出し元のPCとSPを取得していました。
*   新バージョンでは、`g->m->curg->sched.pc`と`g->m->curg->sched.sp`を使用しています。これは、現在のMが実行しているゴルーチン（`curg`）のスケジューラ情報（`sched`）から、そのゴルーチンのPCとSPを直接取得することを意味します。この変更は、`getgcmask`がMスタック上で実行されるようになったことに伴い、より正確なスタックコンテキストを`gentraceback`に提供するために行われたと考えられます。

### `src/pkg/runtime/stubs.goc` の変更

```c
// 削除されたコード:
// // For testing.
// // TODO: find a better place for this.
// func GCMask(x Eface) (mask Slice) {
// 	runtime·getgcmask(x.data, x.type, &mask.array, &mask.len);
// 	mask.cap = mask.len;
// }
```
このファイルから、以前の`GCMask`関数の定義が削除されました。これは、`export_test.go`でGo言語のラッパー関数として新しい`GCMask`が導入されたため、C言語側のスタブは不要になったためです。

これらの変更により、`getgcmask`の実行がMのシステムスタックに移行され、GCのスタック走査の正確性と安定性が向上しています。

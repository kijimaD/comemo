# [インデックス 25613] ファイルの概要

このコミットは、Go言語のMIPS64およびMIPS64LE（MIPS 64ビット、リトルエンディアン）アーキテクチャにおけるテストスイートの安定化と改善を目的としています。具体的には、MIPS64/LE環境で発生していたテストの失敗を修正し、まだサポートが不完全な機能（外部リンキングや特定のコンパイラ最適化）に依存するテストを一時的にスキップするように変更しています。これにより、MIPS64/LEアーキテクチャ上でのGoの移植作業が円滑に進むよう、テストカバレッジと信頼性の向上が図られています。

## 変更の背景

このコミットが作成された2015年9月は、Go言語がMIPS64およびMIPS64LEアーキテクチャへの公式サポートを積極的に進めていた時期にあたります。Go 1.5（2015年8月リリース）ではMIPS64/LEの `GOARCH` 値が導入されたものの、完全なサポートはGo 1.6（2016年2月リリース）で実現されました。このコミットは、その移行期間中にMIPS64/LE環境でのGoの安定性を確保するために行われました。

当時のMIPS64/LE環境では、以下の具体的な課題が存在していました。

1.  **外部リンキングの未サポート**: `fixedbugs/issue10607.go` テストは、Cgoを介した外部リンキングの挙動を検証するものでしたが、MIPS64/LE環境ではこの機能がまだ完全に実装されていませんでした。そのため、このテストはMIPS64/LE上で失敗し、テストスイート全体のノイズとなっていました。
2.  **nilポインタ最適化の不整合 (Issue #9058)**: `nilptr3.go` テストは、Goコンパイラによるnilポインタのデリファレンスに関する最適化の特定のケースを検証します。この種の最適化は、特定のアーキテクチャやコンパイラのバージョンで予期せぬ挙動を引き起こすことがあり、PPC64アーキテクチャで報告されていたIssue #9058と同様の問題がMIPS64/LEでも発生していました。これは、コンパイラのバックエンドがMIPS64/LE向けにまだ完全に成熟していなかったことを示唆しています。
3.  **`nosplit.go` および `fixedbugs/issue11656.go` のMIPS64/LE対応不足**:
    *   `nosplit.go` は、スタック分割を行わないGoランタイムの低レベル関数（`nosplit`関数）の挙動をテストします。このテストはアーキテクチャ固有のアセンブリコードやポインタサイズに依存するため、MIPS64/LE向けの適切な定義が必要でした。
    *   `fixedbugs/issue11656.go` は、特定のアーキテクチャで意図的にトラップ命令を生成し、その後のシステム挙動を検証するテストです。MIPS64/LE用のトラップ命令のバイナリ表現が定義されていなかったため、このテストもMIPS64/LE上で正しく機能していませんでした。

これらの問題を解決し、MIPS64/LEアーキテクチャ上でのGoのテストスイートを安定させ、開発の進行を妨げないようにすることが、このコミットの主要な目的でした。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下のGo言語およびシステムプログラミングに関する前提知識が不可欠です。

### 1. Goのビルドタグ (`+build`)

Go言語では、ソースファイルの先頭に `// +build tag` の形式で特殊なコメントを記述することで、条件付きコンパイルを制御できます。コンパイラは、指定されたタグに基づいてファイルをビルドに含めるか除外するかを決定します。
例えば、`// +build linux,!ppc64,!ppc64le,!mips64,!mips64le` は、「Linux環境で、かつPPC64、PPC64LE、MIPS64、MIPS64LE以外のアーキテクチャの場合にこのファイルをビルドに含める」という条件を示します。これにより、特定のアーキテクチャやOSに特化したコードやテストを、他の環境では無視させることができます。

### 2. 外部リンキング (External Linking) と Cgo

Goプログラムは通常、Goコンパイラによって生成されたオブジェクトファイルと、Goランタイムライブラリを静的にリンクして単一の実行可能ファイルを生成します。外部リンキングとは、Go以外の言語（主にC言語）で書かれたライブラリ（例: `libc`）や、共有ライブラリ（`.so`, `.dylib` など）をGoプログラムにリンクするプロセスを指します。
Goでは、`Cgo` というツールを通じてC言語のコードをGoプログラムから呼び出すことができます。Cgoを使用する際には、外部リンキングが必要となることが多く、そのサポートはOSやアーキテクチャによって異なります。MIPS64/LEのような新しいアーキテクチャへの移植初期段階では、外部リンキングのサポートが不完全であることは珍しくありません。

### 3. nilポインタ最適化 (Nil Pointer Optimization) と Issue #9058

Go言語では、nilポインタのデリファレンスはランタイムパニックを引き起こすことが保証されています。Goコンパイラは、プログラムのパフォーマンスを向上させるために様々な最適化を行います。その一つに、nilポインタのチェックに関する最適化があります。コンパイラは、特定の状況下でnilチェックを省略したり、より効率的なコードに変換したりすることがあります。
Issue #9058（および関連するGo 1.21-1.24のバグ）は、この最適化が原因で、nilポインタのデリファレンスが即座にパニックを引き起こさず、パニックが遅延したり、全く発生しなかったりする不整合な挙動が発生したことを示しています。これは、Goの言語仕様に反するものであり、デバッグを困難にする可能性がありました。このコミットでMIPS64/LEがこのテストから除外されたのは、MIPS64/LEのコンパイラバックエンドが同様の最適化の不完全性を持っていたためと考えられます。

### 4. `nosplit` 関数とスタック分割 (Stack Splitting)

Goランタイムは、ゴルーチン（goroutine）のスタックを動的に拡張・縮小する「スタック分割」というメカニズムを持っています。これにより、ゴルーチンは小さなスタックで開始し、必要に応じてスタックを成長させることができます。
しかし、ランタイムの非常に低レベルな部分（例えば、スケジューラ、ガベージコレクタ、Cgoコールバック、シグナルハンドラなど）では、スタック分割が起こると問題が生じる可能性があります。このような関数は `//go:nosplit` ディレクティブ（またはアセンブリコードでは `NOSPLIT` フラグ）を使ってマークされ、コンパイラはこれらの関数がスタック分割を行わないように特別な処理をします。`nosplit`関数のテストは、この挙動が正しく保証されているかを検証するために重要です。

### 5. トラップ命令 (Trap Instruction)

トラップ命令は、CPUが特定の例外的な状況（例: 不正なメモリアクセス、ゼロ除算、特権命令の実行）に遭遇した際に、通常のプログラムフローを中断してオペレーティングシステムやランタイムのハンドラに制御を移すために使用される特殊な命令です。デバッグやセキュリティ目的で意図的にトラップを発生させることもあります。
アーキテクチャごとにトラップ命令のバイナリ表現は異なります。MIPSアーキテクチャでは、`BREAK` 命令や `TEQ` (Trap if Equal) 命令などがトラップを発生させるために使用されます。`fixedbugs/issue11656.go` のテストでは、特定のアーキテクチャで意図的にトラップ命令を生成し、その後の挙動を検証します。

### 6. MIPS64/MIPS64LE アーキテクチャ

MIPS (Microprocessor without Interlocked Pipeline Stages) は、RISC (Reduced Instruction Set Computer) アーキテクチャの一種です。MIPS64は64ビット版のMIPSアーキテクチャを指し、MIPS64LEはそのリトルエンディアン版です。Go言語は、サーバー、組み込みシステム、ネットワーク機器など、様々なプラットフォームで動作するように設計されており、MIPS64もそのターゲットの一つです。MIPSアーキテクチャは、レジスタの利用方法、命令セット、メモリモデル（ビッグエンディアン/リトルエンディアン）などに独自の特徴を持ちます。

## 技術的詳細

このコミットは、GoのテストスイートがMIPS64/LEアーキテクチャ上でより堅牢に動作するように、以下の技術的な変更を加えています。

### 1. ビルドタグによるテストの条件付きスキップ

*   **`test/fixedbugs/issue10607.go`**: このテストファイルは、Goのビルドタグ `// +build linux,!ppc64,!ppc64le` を持っていました。このコミットでは、このタグに `,!mips64,!mips64le` が追加されました。
    *   **変更前**: Linux環境で、PPC64およびPPC64LE以外のアーキテクチャでビルドされる。
    *   **変更後**: Linux環境で、PPC64、PPC64LE、**MIPS64、MIPS64LE**以外のアーキテクチャでビルドされる。
    この変更により、MIPS64およびMIPS64LE環境ではこのテストファイルがコンパイル対象から除外され、外部リンキングの未サポートに起因するテスト失敗が回避されます。これは、特定の機能がまだ完全に実装されていないアーキテクチャでのテストスイートの安定化によく用いられる手法です。
*   **`test/nilptr3.go`**: 同様に、このテストファイルもビルドタグ `// +build !ppc64,!ppc64le` に `,!mips64,!mips64le` が追加されました。
    *   **変更前**: PPC64およびPPC64LE以外のアーキテクチャでビルドされる。
    *   **変更後**: PPC64、PPC64LE、**MIPS64、MIPS64LE**以外のアーキテクチャでビルドされる。
    Issue #9058で言及されているnilポインタ最適化の問題がMIPS64/LEでも発生するため、このテストもMIPS64/LE環境ではスキップされるようになりました。これは、コンパイラのバックエンドにおける最適化パスが特定のアーキテクチャでまだ成熟していないことを示唆しています。

### 2. アーキテクチャ固有のトラップ命令の追加

*   **`test/fixedbugs/issue11656.go`**: このテストは、`goarch`（ターゲットアーキテクチャ）に基づいて異なるトラップ命令のバイナリ表現を生成します。このコミットでは、`switch goarch` ステートメントに `mips64` と `mips64le` のケースが追加されました。
    *   `case "mips64": binary.BigEndian.PutUint32(ill, 0x00000034)`
    *   `case "mips64le": binary.LittleEndian.PutUint32(ill, 0x00000034)`
    ここで使用されている `0x00000034` は、MIPSアーキテクチャにおける `TEQ $zero, $zero` 命令のバイナリ表現です。`TEQ` 命令は、2つのレジスタの値が等しい場合にトラップ例外を発生させます。`$zero` レジスタは常に0を保持するため、`TEQ $zero, $zero` は常にトラップを発生させます。これは、MIPSの `BREAK` 命令と同様に、意図的にプログラムの実行を中断させ、デバッガやランタイムのハンドラに制御を移すために使用されます。この追加により、MIPS64/LE環境でもこのテストが正しく実行され、トラップハンドリングのメカニズムが期待通りに機能するかを検証できるようになりました。

### 3. `nosplit` テストのMIPS64/LE対応

*   **`test/nosplit.go`**: このテストは、`nosplit` 関数がスタック分割を行わないことを検証するために、アーキテクチャ固有のアセンブリコードを動的に生成します。このコミットでは、`switch goarch` ステートメントに `mips64` または `mips64le` のケースが追加されました。
    *   `ptrSize = 8`: MIPS64は64ビットアーキテクチャであるため、ポインタサイズが8バイトであることを明示的に設定しています。これは、アセンブリコード生成時に正しいメモリアドレス計算を行うために重要です。
    *   `fmt.Fprintf(&buf, "#define CALL JAL\\n#define REGISTER (R0)\\n")`: これは、テスト内で生成されるアセンブリコードがMIPS64/LEの呼び出し規約に準拠するようにするためのマクロ定義です。
        *   `#define CALL JAL`: `CALL` マクロはMIPSの `JAL` (Jump And Link) 命令に展開されます。`JAL` は関数呼び出し命令であり、リターンアドレスを `$ra` レジスタに保存し、指定されたアドレスにジャンプします。
        *   `#define REGISTER (R0)`: `REGISTER` マクロはMIPSの `R0` レジスタに展開されます。`R0` は常に0を保持するレジスタであり、MIPSの慣習で特定の操作でダミーとして使用されるか、特定のシステムコールで引数として使用されることがあります。
    これらの定義により、`nosplit` テストがMIPS64/LE上で正しくアセンブリコードを生成し、スタック分割が行われないという `nosplit` 関数の保証がMIPS64/LE環境でも検証できるようになります。

これらの変更は、MIPS64/LEアーキテクチャにおけるGoの移植作業が進行中であり、テストスイートがその進捗に合わせて調整されていることを明確に示しています。特定のテストをスキップすることで、未実装の機能によるテスト失敗のノイズを減らし、実装済みの機能のテストに集中できるようにしています。同時に、アーキテクチャ固有の修正を加えることで、より低レベルな部分での正確な動作を保証しています。

## コアとなるコードの変更箇所

このコミットでは、Goランタイムのコア部分ではなく、主にテストファイルが変更されています。変更されたファイルは以下の通りです。

*   `test/fixedbugs/issue10607.go`: ビルドタグの変更
*   `test/fixedbugs/issue11656.go`: MIPS64/LE用のトラップ命令の追加
*   `test/nilptr3.go`: ビルドタグの変更
*   `test/nosplit.go`: MIPS64/LE用のポインタサイズとアセンブリマクロの追加

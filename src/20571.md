# [インデックス 20571] ファイルの概要

このコミットは、Goランタイムのスタックトレース表示に関する挙動を修正するものです。具体的には、エクスポートされたランタイム関数（`runtime.Breakpoint`など）がスタックトレースに表示されるように変更し、これによりWindowsビルドの失敗を解決することを目的としています。

## コミット

```
runtime: show frames for exported runtime functions

The current Windows build failure happens because by
default runtime frames are excluded from stack traces.
Apparently the Windows breakpoint path dies with an
ordinary panic, while the Unix path dies with a throw.
Breakpoint is a strange function and I don't mind that it's
a little different on the two operating systems.

The panic squelches runtime frames but the throw shows them,
because throw is considered something that shouldn't have
happened at all, so as much detail as possible is wanted.

The runtime exclusion is meant to prevents printing too much noise
about internal runtime details. But exported functions are
not internal details, so show exported functions.
If the program dies because you called runtime.Breakpoint,
it's okay to see that frame.
This makes the Breakpoint test show Breakpoint in the
stack trace no matter how it is handled.

Should fix Windows build.
Tested on Unix by changing Breakpoint to fault instead
of doing a breakpoint.

TBR=brainman
CC=golang-codereviews
https://golang.org/cl/143300043
```

## 変更の背景

このコミットの主な背景は、Windows環境でのGoのビルド失敗です。この失敗は、`runtime.Breakpoint`関数が関与するスタックトレースの挙動に起因していました。

Goのランタイムは、通常、スタックトレースの出力時に内部的なランタイム関数のフレームを省略します。これは、ユーザーにとってノイズとなる詳細を減らし、よりアプリケーションコードに焦点を当てたスタックトレースを提供するためです。しかし、`runtime.Breakpoint`のようなエクスポートされたランタイム関数は、ユーザーが意図的に呼び出す可能性のある関数であり、そのフレームがスタックトレースから除外されると問題が生じることがあります。

特に、WindowsとUnix系OSでは、`runtime.Breakpoint`が異常終了する際のメカニズムが異なっていました。
- Unix系OSでは、`throw`メカニズム（Goランタイム内部の非常に深刻なエラーを示す）が使用され、この場合はスタックトレースにランタイムフレームも含まれていました。`throw`は「全く起こるべきではなかったこと」と見なされるため、可能な限り詳細な情報が求められるからです。
- Windowsでは、通常の`panic`メカニズムが使用されていました。`panic`の場合、デフォルトでランタイムフレームは抑制されます。

この違いにより、Windows環境で`runtime.Breakpoint`が呼び出された際に、関連するスタックフレームが適切に表示されず、ビルドプロセスが期待通りに動作しないという問題が発生していました。このコミットは、`runtime.Breakpoint`のようなエクスポートされたランタイム関数が、その終了メカニズム（`panic`か`throw`か）に関わらず、常にスタックトレースに表示されるようにすることで、このWindowsビルドの問題を解決しようとしています。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、スタック管理、プリミティブな同期メカニズムなど、Goプログラムが動作するために必要な低レベルの機能を提供します。

### スタックトレース (Stack Trace)
スタックトレースは、プログラムがクラッシュしたり、エラーが発生したりしたときに、その時点での関数呼び出しの履歴を示すものです。各行は「フレーム」と呼ばれ、どの関数がどの関数を呼び出したか、そしてその呼び出しがどのソースコードの行で行われたかを示します。デバッグやエラーの原因特定に不可欠な情報です。

### `runtime.Breakpoint`
`runtime.Breakpoint`は、Goの`runtime`パッケージで提供される関数の一つです。この関数は、デバッガがブレークポイントを設定する際に使用されるような、プログラムの実行を一時停止させるためのメカニズムを提供します。通常、デバッグ目的や、特定の条件下でプログラムの実行を停止させたい場合に利用されます。

### `panic`と`throw`
Goには、プログラムの異常終了を扱うためのメカニズムがいくつかあります。
- **`panic`**: Goプログラムで回復不可能なエラーが発生した際に使用されるメカニズムです。`panic`が発生すると、現在の関数の実行が停止し、遅延関数（`defer`）が実行され、呼び出し元の関数へとスタックが巻き戻されます。最終的に、`recover`によって捕捉されない限り、プログラムは終了します。`panic`は、通常、アプリケーションレベルのエラーや、予期せぬ状態に陥った場合に使用されます。デフォルトでは、`panic`によるスタックトレースは、ランタイムの内部フレームを省略して表示されます。
- **`throw`**: `throw`は、Goランタイムの内部で発生する、より深刻な、回復不能なエラーを示すために使用されるメカニズムです。これは、Goプログラムの整合性が損なわれた可能性のある、非常に低レベルなエラーを示唆します。`panic`とは異なり、`throw`は通常、ランタイムのバグや、システムレベルの深刻な問題を示します。`throw`が発生した場合、デバッグのために可能な限り多くの情報を提供するため、ランタイムの内部フレームもスタックトレースに含まれます。

### エクスポートされた関数 (Exported Functions)
Goでは、パッケージ外からアクセス可能な関数や変数、型は「エクスポートされている」と言われます。これは、識別子の最初の文字を大文字にすることで実現されます。`runtime.Breakpoint`のように、`runtime`パッケージ内で定義されていても、外部から呼び出せるようにエクスポートされている関数は、ユーザーが直接利用することを意図しているため、内部的な詳細とは見なされません。

## 技術的詳細

このコミットは、`src/runtime/traceback.go`ファイル内の`showframe`関数と、新しく追加された`isExportedRuntime`関数を変更することで、スタックトレースの挙動を修正しています。

### `showframe`関数の役割
`showframe`関数は、スタックトレースを生成する際に、特定の関数フレームをスタックトレースに含めるべきかどうかを決定する役割を担っています。これまでの実装では、ランタイムの内部関数（`runtime.`で始まる名前の関数）は、通常、スタックトレースから除外されていました。これは、ユーザーにとって関連性の低い内部的な詳細を隠すためです。

### 変更点とロジック
変更の核心は、`showframe`関数内の条件式に`isExportedRuntime(name)`という新しい条件が追加されたことです。

変更前の`showframe`の関連部分のロジックは以下のようでした。
```go
return traceback > 1 || f != nil && contains(name, ".") && !hasprefix(name, "runtime.")
```
この条件は、「`traceback`レベルが1より大きい（より詳細なトレースが要求されている）場合」または「関数名に`.`が含まれ、かつ`runtime.`で始まらない場合」にフレームを表示するというものでした。つまり、`runtime.`で始まる関数は、デフォルトで除外されていました。

変更後の`showframe`の関連部分のロジックは以下のようになります。
```go
return traceback > 1 || f != nil && contains(name, ".") && (!hasprefix(name, "runtime.") || isExportedRuntime(name))
```
この変更により、`runtime.`で始まる関数であっても、`isExportedRuntime(name)`が`true`を返す場合（つまり、そのランタイム関数がエクスポートされている場合）には、スタックトレースに含められるようになりました。

### `isExportedRuntime`関数の追加
新しく追加された`isExportedRuntime`関数は、与えられた関数名がエクスポートされたランタイム関数であるかどうかを判定します。

```go
// isExportedRuntime reports whether name is an exported runtime function.
// It is only for runtime functions, so ASCII A-Z is fine.
func isExportedRuntime(name string) bool {
	const n = len("runtime.")
	return len(name) > n && name[:n] == "runtime." && 'A' <= name[n] && name[n] <= 'Z'
}
```
この関数は以下の条件をチェックします。
1.  `len(name) > n`: 関数名が"runtime."よりも長いこと。
2.  `name[:n] == "runtime."`: 関数名が"runtime."で始まること。
3.  `'A' <= name[n] && name[n] <= 'Z'`: "runtime."の後に続く文字（つまり、関数名の最初の文字）が大文字のアルファベット（AからZ）であること。Goの命名規則では、識別子の最初の文字が大文字である場合、その識別子はエクスポートされます。

これらの条件をすべて満たす場合、その関数はエクスポートされたランタイム関数であると判断され、`true`が返されます。これにより、`runtime.Breakpoint`のような関数が、たとえ`runtime`パッケージに属していても、スタックトレースに表示されるようになります。

この変更は、Windowsでの`runtime.Breakpoint`のテストが、`panic`によってランタイムフレームが抑制されるために失敗していた問題を直接的に解決します。エクスポートされたランタイム関数は、ユーザーが意図的に呼び出す可能性があるため、そのフレームがスタックトレースに表示されることは、デバッグや問題特定において有用な情報となります。

## コアとなるコードの解説

### `showframe`関数の変更
`showframe`関数は、スタックトレースの各フレームについて、そのフレームを表示するかどうかを決定します。変更された行は以下の通りです。

```go
-	return traceback > 1 || f != nil && contains(name, ".") && !hasprefix(name, "runtime.")
+	return traceback > 1 || f != nil && contains(name, ".") && (!hasprefix(name, "runtime.") || isExportedRuntime(name))
```
- 変更前は、`!hasprefix(name, "runtime.")`という条件があり、関数名が`"runtime."`で始まる場合は、そのフレームは表示されませんでした（ただし、`traceback > 1`の場合は例外）。
- 変更後は、`(!hasprefix(name, "runtime.") || isExportedRuntime(name))`という条件に変わりました。これは、「関数名が`"runtime."`で始まらない」**または**「`isExportedRuntime(name)`が`true`を返す（つまり、エクスポートされたランタイム関数である）」のいずれかの条件が満たされれば、そのフレームが表示されることを意味します。
この論理変更により、`runtime.Breakpoint`のようなエクスポートされたランタイム関数が、通常の`panic`パスでもスタックトレースに表示されるようになります。

### `isExportedRuntime`関数の追加
この新しいヘルパー関数は、与えられた`name`がエクスポートされたランタイム関数であるかを効率的に判定します。

```go
// isExportedRuntime reports whether name is an exported runtime function.
// It is only for runtime functions, so ASCII A-Z is fine.
func isExportedRuntime(name string) bool {
	const n = len("runtime.")
	return len(name) > n && name[:n] == "runtime." && 'A' <= name[n] && name[n] <= 'Z'
}
```
- `const n = len("runtime.")`: "runtime."という文字列の長さを定数`n`に格納します。これは、文字列操作の効率化のためです。
- `len(name) > n`: 関数名が"runtime."よりも長いことを確認します。これにより、"runtime."自体のような不完全な名前を除外します。
- `name[:n] == "runtime."`: 関数名が正確に"runtime."で始まることを確認します。
- `'A' <= name[n] && name[n] <= 'Z'`: 関数名の"runtime."の直後の文字（`name[n]`）が、大文字のアルファベット（A-Z）であるかをチェックします。Goの言語仕様では、パッケージ外にエクスポートされる識別子（関数名、変数名など）は、その名前の最初の文字が大文字である必要があります。この条件は、まさにそのGoのエクスポート規則を利用して、関数がエクスポートされているかどうかを判定しています。

この関数は、ランタイムの内部関数と、ユーザーが利用可能なエクスポートされたランタイム関数を区別するための明確なメカニズムを提供します。

# [インデックス 2331] ファイルの概要

このコミットは、Go言語の初期のx86-64コンパイラである`6g`におけるコード生成の重要な部分である`gmove`関数の大幅なクリーンアップと最適化に関するものです。主に、型変換ロジックの一元化、メモリ操作の効率化、そして`int32`から`uint64`への変換におけるバグ修正を目的としています。

## コミット

このコミットは、Goコンパイラの`gmove`関数をリファクタリングし、型変換の処理を改善することで、生成されるアセンブリコードの効率性を高め、特定の型変換バグを修正しました。

[https://github.com/golang/go/commit/e81d97ea840728970c75e14c5001e333bf217771](https://github.com/golang/go/commit/e81d97ea840728970c75e14c5001e333bf217771)

```
clean up gmove:
        * conversions all in one place.
        * no separate load, store phases;
          direct memory addressing when possible
          (this is the x86 after all!).
          avoids extra registers, extra MOVQs.
        * fixes int32 -> uint64 bug
          (was zero-extending)

OCL=29482

```

## 変更の背景

Go言語の初期のコンパイラ（特に`6g`、`8g`など）は、Plan 9のツールチェインをベースにしており、C言語で書かれていました。これらのコンパイラは、Goプログラムをターゲットアーキテクチャ（この場合はx86-64）の機械語に変換する役割を担っていました。

`gmove`関数は、コンパイラのバックエンドにおいて、異なる型や場所（レジスタ、メモリ）間でデータを移動させるためのアセンブリ命令を生成する中心的な役割を担っていました。しかし、初期の実装ではいくつかの非効率性やバグが存在していました。

1.  **型変換ロジックの散在**: 型変換のロジックが`gmove`関数内に散在しており、コードの可読性や保守性を低下させていました。
2.  **非効率なメモリ操作**: データをメモリからレジスタへ、そして別のメモリ位置へ移動させる際に、不必要なロード・ストアのフェーズを挟むことがあり、余分なレジスタの使用や`MOVQ`（64ビット移動）命令の増加を招いていました。x86アーキテクチャでは、多くの場合、メモリからメモリへの直接操作や、レジスタを介した効率的な操作が可能です。
3.  **`int32 -> uint64`変換バグ**: 符号付き32ビット整数（`int32`）を符号なし64ビット整数（`uint64`）に変換する際に、誤ってゼロ拡張（上位ビットを0で埋める）を行っていました。正しい動作は、符号拡張（上位ビットを符号ビットで埋める）を行うべきでした。これにより、負の`int32`値が`uint64`に変換された際に、意図しない大きな正の値になってしまうというバグがありました。

これらの問題を解決し、より効率的で正確なコードを生成するために、`gmove`関数の大規模なリファクタリングが必要とされました。

## 前提知識の解説

### Goコンパイラ (6g)

`6g`は、Go言語の初期開発段階で使用されていたx86-64アーキテクチャ向けのコンパイラの名称です。Goのコンパイラは、ソースコードを中間表現に変換し、最終的にターゲットアーキテクチャの機械語に変換します。`6g`のような名称は、Plan 9の伝統に由来しており、`6`はx86-64、`8`はx86-32を指していました。

### `gmove`関数

`gmove`は、Goコンパイラのコード生成フェーズにおいて、あるデータ（ソース）を別のデータ（デスティネーション）に移動させるためのアセンブリ命令を生成する内部関数です。この「移動」には、単なる値のコピーだけでなく、異なるデータ型間での変換（例: `int32`から`int64`、`float32`から`float64`など）も含まれます。効率的な`gmove`の実装は、生成されるバイナリのパフォーマンスに直結します。

### x86アーキテクチャにおけるデータ移動と型変換

x86（特にx86-64）アーキテクチャでは、レジスタとメモリ間でデータを効率的に移動させるための多様な命令が提供されています。

*   **レジスタ**: CPU内部の高速な記憶領域。
*   **メモリ**: 主記憶装置。
*   **MOV命令**: データ移動の基本命令。`MOVQ`は64ビットデータを移動します。
*   **符号拡張 (Sign Extension)**: 符号付き整数をより広い型に変換する際に、元の数値の符号を保持するために、上位ビットを元の数値の最上位ビット（符号ビット）で埋める操作。例: `int8`の`-1` (11111111b) を`int16`に符号拡張すると `11111111 11111111b` となります。
*   **ゼロ拡張 (Zero Extension)**: 符号なし整数をより広い型に変換する際に、上位ビットを0で埋める操作。例: `uint8`の`255` (11111111b) を`uint16`にゼロ拡張すると `00000000 11111111b` となります。
*   **CVTSS2SD / CVTSD2SS**: 浮動小数点数型（単精度から倍精度、またはその逆）の変換命令。
*   **CVTTSD2SL / CVTTSD2SQ**: 浮動小数点数型から符号付き整数型への変換命令（切り捨て）。

### 型変換の重要性

プログラミング言語において、異なる型間の変換は頻繁に発生します。コンパイラは、これらの変換を正しく、かつ効率的に機械語に落とし込む必要があります。特に、整数型と浮動小数点数型、あるいは異なるサイズの整数型間での変換は、アーキテクチャ固有の命令を適切に利用することで、パフォーマンスを大きく左右します。不適切な変換は、バグ（例: 符号の誤り）や性能低下を招きます。

## 技術的詳細

このコミットは、`gmove`関数とその周辺のコードに以下の主要な変更を加えました。

1.  **型変換ロジックの一元化**:
    *   `gmove`関数内の型変換ロジックが、`CASE(ft, tt)`マクロを使用した大きな`switch`文に集約されました。これにより、ソース型(`ft`)とターゲット型(`tt`)の組み合わせに基づいて、適切なアセンブリ命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`, `AMOVBLSX`, `AMOVBQZX`など）が選択されるようになりました。
    *   以前はロードフェーズとストアフェーズに分かれていた処理が統合され、より直接的な変換が可能になりました。
    *   `rdst`（レジスタデスティネーションが必要な場合）と`hard`（中間レジスタが必要な複雑な変換の場合）というラベルを導入し、コードパスを整理しています。

2.  **メモリ操作の効率化**:
    *   `ismem(Node *n)`関数が新設され、ノードがメモリオペランドであるかを判定できるようになりました。
    *   「2つのメモリオペランドを持つことはできない」という制約が明示的に導入され、メモリからメモリへの直接移動を避けることで、不必要なレジスタの割り当てと`MOVQ`命令を削減しています。これはx86アーキテクチャの特性を活かした最適化です。
    *   定数からメモリへの移動において、64ビット即値がレジスタへの移動でしか許されないというx86の制約を考慮し、必要に応じて中間レジスタを使用する`hard`パスにフォールバックするようになりました。

3.  **`int32 -> uint64`バグの修正**:
    *   以前の`gmove`では、`TINT32`から`TUINT64`への変換で`AMOVLQZX`（ゼロ拡張）が使用されていました。これは`uint32`から`uint64`への変換には正しいですが、`int32`から`uint64`への変換では符号拡張（`AMOVLQSX`）が必要です。
    *   新しい`gmove`では、`CASE(TINT32, TUINT64)`の場合に`AMOVLQSX`（符号拡張）を使用するように修正されました。これにより、負の`int32`値が`uint64`に正しく変換されるようになりました。

4.  **定数変換の改善**:
    *   `src/cmd/gc/const.c`に`convconst(Node *con, Type *t, Val *val)`関数が追加されました。この関数は、定数値を指定された型`t`に変換し、その結果を`con`ノードに格納します。これにより、コンパイラのフロントエンドで扱われる定数表現を、バックエンドのコード生成に適した形式に変換する処理が一元化されました。
    *   `iconv(int64 x, int et)`関数も追加され、整数値を異なる整数型に変換する際の符号拡張や切り捨てロジックをカプセル化しています。

5.  **型の単純化**:
    *   `src/cmd/gc/subr.c`に`simsimtype(Type *t)`関数が追加されました。これは、`simtype`関数よりもさらに単純化された型表現を返すもので、ポインタ型を対応する符号なし整数型に、`bool`型を`uint8`にマッピングします。これにより、`gmove`内の型変換ロジックが簡素化されます。

6.  **`OLITERAL`の導入**:
    *   `src/cmd/gc/go.h`と`src/cmd/gc/dcl.c`において、`OCONST`が`OLITERAL`に置き換えられました。これは、コンパイラ内部での定数表現の概念をより明確にするための変更と考えられます。`OLITERAL`は、コンパイル時に値が既知であるリテラルを表します。

## コアとなるコードの変更箇所

このコミットの主要な変更は、`src/cmd/6g/gsubr.c`の`gmove`関数に集中しています。

*   **`src/cmd/6g/gsubr.c`**:
    *   `gmove`関数の全体的な構造が変更され、型変換の`switch`文が導入されました。
    *   `ismem`関数が新設されました。
    *   `bignodes`関数が追加され、2^63を表す定数ノードを初期化します。これは`uint64`から浮動小数点数への変換ロジックで使用されます。
    *   `int32`から`uint64`への変換ロジックが`AMOVLQSX`を使用するように修正されました。
    *   浮動小数点数と整数間の変換ロジックが大幅に書き換えられました。

*   **`src/cmd/gc/const.c`**:
    *   `iconv`関数と`convconst`関数が追加されました。

*   **`src/cmd/gc/go.h`**:
    *   `OTYPE, OCONST, OVAR, OIMPORT`が`OTYPE, OVAR, OIMPORT`に変更され、`OLITERAL`が追加されました。
    *   `simsimtype`, `truncfltlit`, `convconst`のプロトタイプ宣言が追加されました。

*   **`src/cmd/gc/dcl.c`**:

*   **`src/cmd/gc/subr.c`**:

    *   `opnames`配列から`OCONST`が削除されました。

## コアとなるコードの解説

### `src/cmd/6g/gsubr.c` の `gmove` 関数

新しい`gmove`関数は、ソースノード`f`とターゲットノード`t`を受け取り、それらの型（`ft`, `tt`）に基づいて適切な移動/変換命令を生成します。

```c
void
gmove(Node *f, Node *t)
{
    int a, ft, tt;
    Type *cvt;
    Node r1, r2, r3, r4, zero, one, con;
    Prog *p1, *p2;

    if(debug['M'])
        print("gmove %N -> %N\n", f, t);

    ft = simsimtype(f->type); // ソース型の単純化
    tt = simsimtype(t->type); // ターゲット型の単純化
    cvt = t->type; // 中間変換が必要な場合のターゲット型

    // 2つのメモリオペランドは許可されない
    if(ismem(f) && ismem(t))
        goto hard; // 中間レジスタを介した変換へ

    // 定数を目的の型に変換
    if(f->op == OLITERAL) {
        convconst(&con, t->type, &f->val); // convconstで定数を変換
        f = &con;
        ft = tt;    // シンプルなMOV命令を選択させるため
        // 一部の定数はメモリに直接移動できない
        if(ismem(t)) {
            // 浮動小数点定数はメモリからロードされる
            if(isfloat[tt])
                goto hard;
            // 64ビット即値はレジスタへの移動でしか許されない
            if(isint[tt]) {
                // 32ビット範囲外の整数定数は直接メモリに移動できない
                if(mpcmpfixfix(con.val.u.xval, minintval[TINT32]) < 0)
                    goto hard;
                if(mpcmpfixfix(con.val.u.xval, maxintval[TINT32]) > 0)
                    goto hard;
            }
        }
    }

    switch(CASE(ft, tt)) {
    default:
        fatal("gmove %T -> %T", f, t);

    // 整数コピーと切り捨て
    case CASE(TINT8, TINT8): // ...
    case CASE(TUINT64, TUINT8):
        a = AMOVB;
        break;
    // ... 他の整数型間のコピーと切り捨て ...

    // 整数アップコンバージョン（符号拡張/ゼロ拡張）
    case CASE(TINT8, TINT16): // int8をint16に符号拡張
    case CASE(TINT8, TUINT16):
        a = AMOVBWSX; // Byte to Word Sign Extend
        goto rdst; // レジスタデスティネーションが必要
    // ... 他の符号拡張/ゼロ拡張 ...
    case CASE(TINT32, TUINT64): // int32をuint64に符号拡張 (バグ修正箇所)
        a = AMOVLQSX; // Long to Quad Sign Extend
        goto rdst;

    case CASE(TUINT32, TUINT64): // uint32をuint64にゼロ拡張
        a = AMOVLQZX; // Long to Quad Zero Extend
        goto rdst;

    // 浮動小数点数から整数への変換
    case CASE(TFLOAT32, TINT32):
        a = ACVTTSS2SL; // Convert Truncate Scalar Single to Signed Long
        goto rdst;
    // ... 他の浮動小数点数から整数への変換 ...

    // uint64から浮動小数点数への変換 (複雑なロジック)
    case CASE(TUINT64, TFLOAT32):
    case CASE(TUINT64, TFLOAT64):
        // アルゴリズム:
        // 小さい場合はネイティブ変換を使用。
        // そうでない場合、2^63を引いて変換し、再度加算する。
        // ... (詳細なコードは省略) ...
        return;

    // 整数から浮動小数点数への変換
    case CASE(TINT32, TFLOAT32):
        a = ACVTSL2SS; // Convert Signed Long to Scalar Single
        goto rdst;
    // ... 他の整数から浮動小数点数への変換 ...

    // 浮動小数点数から浮動小数点数への変換
    case CASE(TFLOAT32, TFLOAT32):
        a = AMOVSS;
        break;
    case CASE(TFLOAT64, TFLOAT64):
        a = AMOVSD;
        break;
    case CASE(TFLOAT32, TFLOAT64):
        a = ACVTSS2SD; // Convert Scalar Single to Scalar Double
        goto rdst;
    case CASE(TFLOAT64, TFLOAT32):
        a = ACVTSD2SS; // Convert Scalar Double to Scalar Single
        goto rdst;
    }

    gins(a, f, t); // 最終的なアセンブリ命令を生成
    return;

rdst: // レジスタデスティネーションが必要な場合
    regalloc(&r1, t->type, t);
    gins(a, f, &r1);
    gmove(&r1, t);
    regfree(&r1);
    return;

hard: // 中間レジスタが必要な複雑な変換の場合
    regalloc(&r1, cvt, t);
    gmove(f, &r1);
    gmove(&r1, t);
    regfree(&r1);
    return;
}
```

この新しい`gmove`は、`simsimtype`で単純化された型を使用し、`OLITERAL`定数を`convconst`で前処理します。そして、`CASE(ft, tt)`の`switch`文で、ソースとターゲットの型に応じた最適なアセンブリ命令（`a`）を決定します。`rdst`や`hard`といったラベルへの`goto`は、特定の変換がレジスタを必要とするか、あるいは中間レジスタを介した複数ステップの変換が必要かを示しています。特に`int32`から`uint64`への変換では、`AMOVLQSX`が明示的に使用され、符号拡張が正しく行われるようになりました。

### `src/cmd/gc/const.c` の `convconst` 関数

`convconst`関数は、コンパイル時定数`val`を、指定された型`t`に変換し、その結果を`Node`型の`con`に格納します。

```c
void
convconst(Node *con, Type *t, Val *val)
{
    int64 i;
    int tt;

    tt = simsimtype(t); // ターゲット型の単純化

    // 定数ノードを初期化し、値をコピー
    nodconst(con, types[TINT8], 0); // 仮の型で初期化
    con->type = t;
    con->val = *val;

    if(isint[tt]) { // ターゲットが整数型の場合
        con->val.ctype = CTINT;
        con->val.u.xval = mal(sizeof *con->val.u.xval);
        // 元の定数の種類に応じてint64に変換
        switch(val->ctype) {
        // ...
        }
        i = iconv(i, tt); // iconvでターゲット整数型に変換
        mpmovecfix(con->val.u.xval, i); // 結果を多倍長整数に格納
        return;
    }

    if(isfloat[tt]) { // ターゲットが浮動小数点型の場合
        if(con->val.ctype == CTINT) {
            con->val.ctype = CTFLT;
            con->val.u.fval = mal(sizeof *con->val.u.fval);
            mpmovefixflt(con->val.u.fval, val->u.xval); // 整数から浮動小数点数へ
        }
        // ...
        return;
    }
    // ...
}
```
この関数は、整数定数、浮動小数点定数、ブール定数などを、ターゲットの型に合わせて適切に変換します。特に整数型への変換では、`iconv`関数を呼び出して、符号拡張や切り捨てなどのロジックを適用します。

### `src/cmd/gc/subr.c` の `simsimtype` 関数

`simsimtype`関数は、与えられた型`t`をさらに単純化された型表現に変換します。

```c
int
simsimtype(Type *t)
{
    int et;

    et = simtype[t->etype]; // 基本型を取得
    switch(et) {
    case TPTR32: // 32ビットポインタはuint32として扱う
        et = TUINT32;
        break;
    case TPTR64: // 64ビットポインタはuint64として扱う
        et = TUINT64;
        break;
    case TBOOL: // boolはuint8として扱う
        et = TUINT8;
        break;
    }
    return et;
}
```
この関数は、`gmove`のようなコード生成ロジックが、ポインタやブール値をより基本的な整数型として扱えるようにすることで、`switch`文のケース数を減らし、コードを簡素化するのに役立ちます。

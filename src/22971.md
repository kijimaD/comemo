## 変更の背景

このコミットの主な目的は、Goコンパイラのコード生成バックエンドを、将来導入される重要な最適化のために準備することです。具体的には、以下の2つの機能の実装に先立つクリーンアップ作業として位置づけられています。

1.  **ジャンプフリーなブール値 (jump-free booleans, CL 2284)**: これは、ブール式を評価する際に、条件分岐（ジャンプ命令）を極力使用しないようにするコンパイラ最適化技術です。CPUのパイプライン処理において、条件分岐は予測ミスが発生すると大きな性能ペナルティにつながる可能性があります。ジャンプフリーなコードは、ビット演算や条件付き移動命令などを活用することで、このペナルティを回避し、より効率的なコードを生成することを目指します。
2.  **ゼロを意識した比較 (zero-aware comparisons, issue 10381)**: 特定のアーキテクチャでは、値とゼロとの比較に特化した、より高速な命令が存在する場合があります。この最適化は、そのような命令を活用して、ゼロとの比較をより効率的に行うことを目的としています。

これらの最適化をスムーズに導入するために、既存のブール値および比較のコード生成ロジックを整理し、より柔軟で保守しやすい構造にすることが必要とされました。このコミット自体は機能的な変更を含まず、既存の動作に影響を与えないことが `toolstash -cmp` によって確認されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造とコード生成に関する基本的な知識が必要です。

*   **`cmd/internal/gc` パッケージ**: Goコンパイラの主要な内部パッケージの一つで、Go言語のソースコードを中間表現から最終的な機械語コードに変換するバックエンドの大部分を担っています。`gc` は "Go compiler" の略です。
*   **コード生成 (Code Generation)**: コンパイラの最終段階で、最適化された中間表現からターゲットアーキテクチャの機械語命令を生成するプロセスです。
*   **`Node` 構造体**: Goコンパイラ内部で、抽象構文木 (AST) の各ノードや、中間表現の要素を表すために使用される汎用的な構造体です。プログラムの各要素（変数、定数、演算子、関数呼び出しなど）が `Node` として表現されます。
*   **`Bgen` 関数**: `gc` パッケージ内の重要な関数で、ブール式（例: `a == b`, `x && y`, `!z`）の評価結果に基づいて条件分岐コードを生成する役割を担っています。`Bgen` は、特定の条件が真または偽の場合に、指定されたプログラムカウンタ (PC) にジャンプする命令を生成します。
*   **`bgen_float` 関数**: 浮動小数点数の比較（例: `f1 > f2`）に対する条件分岐コードを生成する関数です。浮動小数点数の比較は、NaN (Not a Number) の存在などにより、整数とは異なる特殊な考慮が必要です。
*   **`obj.Prog`**: Goコンパイラのバックエンドで使用される、単一の機械語命令を表す構造体です。
*   **`likely` パラメータ**: 条件分岐の「予測ヒント」を示すパラメータです。コンパイラは、このヒントを基に、CPUの分岐予測器がより正確に予測できるようにコードを配置する場合があります。`likely` が正の値であれば分岐が取られる可能性が高い、負の値であれば取られない可能性が高いことを示します。
*   **`Addable`**: `Node` のプロパティで、そのノードが直接アドレス指定可能（メモリ上のアドレスやレジスタに直接対応する）かどうかを示します。`Addable` でない場合は、一時的なレジスタやメモリにロードする必要があることを意味します。
*   **`Ullman` 数**: コンパイラの最適化において、式の評価順序を決定するために使用されるヒューリスティックな値です。Ullman数は、式を評価するために必要なレジスタの最小数を示唆します。
*   **`CL` (Change List)**: Goプロジェクトのコードレビューシステム (Gerrit) における変更の単位です。`CL 2284` は特定のコードレビューを指します。
*   **`issue`**: Goプロジェクトの課題追跡システム (GitHub Issues) における課題の単位です。`issue 10381` は特定の課題を指します。
*   **`toolstash -cmp`**: Goの開発ツールの一つで、コンパイラの変更が生成されるバイナリコードに機能的な影響を与えないことを確認するために使用されます。変更前と変更後のコンパイラで生成されたバイナリを比較し、差異がないことを検証します。

## 技術的詳細

このコミットは、主にGoコンパイラのコード生成バックエンドにおけるブール値の評価と浮動小数点数の比較ロジックをリファクタリングしています。主要な変更点は以下の通りです。

1.  **`Bgen` および `bgen_float` 関数のシグネチャ変更**:
    *   以前は `int true_` という整数型のパラメータで「真の場合にジャンプするかどうか」を表現していましたが、これを `bool wantTrue` というブール型に変更しました。これにより、コードの意図がより明確になり、型安全性が向上します。`true_` が `0` の場合は偽、`1` の場合は真を意味していましたが、`wantTrue` は直接 `true` または `false` を受け取るため、可読性が大幅に向上します。
    *   `bgen_float` 関数も同様に `true_` から `wantTrue` に変更されています。

2.  **`Bgen` 関数の内部ロジックの整理**:
    *   `OLITERAL` (リテラル定数) および `ONAME` (変数名) のケースが簡素化され、`bgenNonZero` という新しいヘルパー関数が導入されました。
    *   `OANDAND` (論理AND) および `OOROR` (論理OR) の処理が、`wantTrue` パラメータに基づいてより簡潔に記述されています。
    *   比較演算子 (`OEQ`, `ONE`, `OLT`, `OGT`, `OLE`, `OGE`) の処理が大幅にリファクタリングされました。特に、浮動小数点数の比較におけるNaN (Not a Number) の特殊な振る舞い（`brcom` がNaNに対して有効でないことなど）がより明確に、かつ一貫性のある方法で処理されるようになりました。
    *   スライスやインターフェースの比較に関するエラーチェックが改善され、`Isslice` や `Isinter` といったヘルパー関数が活用されています。
    *   64ビット整数を32ビットシステムで比較する際の特殊な処理 (`Cmp64`) も、より整理された形で記述されています。

3.  **`CgenTemp` ヘルパー関数の導入**:
    *   `src/cmd/internal/gc/gen.go` に `CgenTemp` という新しいヘルパー関数が追加されました。この関数は、一時的な `Node` を作成し、指定された `Node` の値をその一時的な `Node` にコピーするコードを生成し、その一時的な `Node` を返します。これにより、コード生成ロジック内で一時変数を扱う際の定型的なコードが削減され、可読性と保守性が向上します。

4.  **`complexbool` 関数のリファクタリング**:
    *   `src/cmd/internal/gc/cplx.go` の `Complexbool` 関数が `complexbool` にリネームされ、`true_` パラメータが `wantTrue` (bool型) に変更されました。
    *   複素数の比較ロジックが、実部と虚部の比較に分解され、`OANDAND` を用いて結合される構造がより明示的に記述されました。これにより、複素数比較のコード生成が `Bgen` の新しいシグネチャと一貫するようになりました。
    *   不要な `CASE` マクロが削除されました。

5.  **`Brcom` および `Brrev` 関数のコメント改善**:
    *   `src/cmd/internal/gc/subr.go` にある `Brcom` (条件を反転させる) および `Brrev` (オペランドを反転させる) 関数のコメントが、より分かりやすく、具体的な例を挙げて説明するように改善されました。また、`Fatal` エラーメッセージのフォーマットも統一されています。

これらの変更は、コードの重複を減らし、ロジックをよりモジュール化し、将来の最適化のための基盤を強化することを目的としています。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラのコード生成ロジック、特にブール値の評価と浮動小数点数の比較に関する部分の「クリーンアップ」です。これは、単なるコードの整形以上の意味を持ちます。

### `Bgen` 関数の改善

`Bgen` 関数は、Go言語の `if` 文や論理演算子 (`&&`, `||`, `!`) などのブール式を機械語に変換する際の中心的な役割を担っています。

*   **`true_ int` から `wantTrue bool` への変更**:
    以前の `true_ int` パラメータは、`0` が偽、`1` が真を意味する慣習的なものでした。しかし、これはGoの型システムから見ると曖昧であり、意図が不明瞭でした。`wantTrue bool` への変更は、このパラメータが「ブール式が `true` であることを期待するか、`false` であることを期待するか」を直接的に示すようになり、コードの可読性と自己文書化能力を大幅に向上させました。これにより、開発者は関数の呼び出しを見ただけで、そのブール式がどのような条件でジャンプを生成するのかを直感的に理解できるようになります。

*   **内部ロジックの簡素化と共通化**:
    `Bgen` 内部では、様々な種類のブール式（リテラル、変数、論理演算、比較演算など）が処理されます。このコミットでは、これらの処理パスが整理され、特に非ゼロ比較のロジックが `bgenNonZero` という独立したヘルパー関数に抽出されました。これにより、コードの重複が減り、各ケースの処理がより明確になりました。
    また、浮動小数点数の比較におけるNaNの特殊な振る舞い（例: `NaN == NaN` は `false`、`NaN < 5` も `false`）を考慮した複雑な条件分岐が、より構造化された形で記述されるようになりました。これは、将来のジャンプフリーなブール値の実装において、これらの特殊ケースをより効率的に扱うための基盤となります。

### `CgenTemp` ヘルパー関数の導入

`src/cmd/internal/gc/gen.go` に追加された `CgenTemp` 関数は、コード生成における一般的なパターンを抽象化します。

```go
// CgenTemp creates a temporary node, assigns n to it, and returns it.
func CgenTemp(n *Node) *Node {
	var tmp Node
	Tempname(&tmp, n.Type) // 一時的なNodeを作成
	Cgen(n, &tmp)          // nの値をtmpにコピーするコードを生成
	return &tmp            // tmpを返す
}
```

コンパイラが複雑な式を評価する際、中間結果を一時的に保存するための変数（またはレジスタ）が必要になることがよくあります。以前は、この「一時的なNodeを作成し、値をコピーする」という一連の処理がコードの様々な場所に散在していました。`CgenTemp` はこのパターンをカプセル化することで、以下の利点をもたらします。

*   **コードの重複排除**: 同じロジックが何度も書かれることを防ぎます。
*   **可読性の向上**: 一時変数の作成と初期化の意図が明確になります。
*   **保守性の向上**: 一時変数の管理ロジックに変更があった場合、一箇所を修正するだけで済みます。

これは、コンパイラコードの全体的な品質と保守性を向上させるための典型的なリファクタリングパターンです。

### `complexbool` 関数のリファクタリング

複素数の比較は、実部と虚部の両方が等しい場合にのみ真となるため、内部的には2つの浮動小数点数比較（実部の比較と虚部の比較）と論理ANDの組み合わせとして扱われます。

*   `Complexbool` から `complexbool` へのリネームと `wantTrue bool` への変更は、`Bgen` との一貫性を保つためのものです。
*   内部の実部と虚部の比較を明示的に `OEQ` ノードとして構築し、それらを `OANDAND` ノードで結合する構造は、複素数比較のセマンティクスをコード上でより正確に表現しています。これにより、コンパイラが複素数比較をどのように処理するかが明確になり、将来的な最適化（例えば、複素数比較に特化したCPU命令がある場合など）のフックを提供しやすくなります。

全体として、このコミットはGoコンパイラのコード生成バックエンドを、よりクリーンで、より理解しやすく、将来の性能最適化を容易にするための堅牢な基盤へと進化させています。機能的な変更がないにもかかわらず、このような内部的な改善は、長期的なプロジェクトの健全性にとって非常に重要です。

## 変更の背景

このコミットの主な目的は、Goコンパイラのコード生成バックエンドを、将来導入される重要な最適化のために準備することです。具体的には、以下の2つの機能の実装に先立つクリーンアップ作業として位置づけられています。

1.  **ジャンプフリーなブール値 (jump-free booleans, CL 2284)**: これは、ブール式を評価する際に、条件分岐（ジャンプ命令）を極力使用しないようにするコンパイラ最適化技術です。CPUのパイプライン処理において、条件分岐は予測ミスが発生すると大きな性能ペナルティにつながる可能性があります。ジャンプフリーなコードは、ビット演算や条件付き移動命令などを活用することで、このペナルティを回避し、より効率的なコードを生成することを目指します。
2.  **ゼロを意識した比較 (zero-aware comparisons, issue 10381)**: 特定のアーキテクチャでは、値とゼロとの比較に特化した、より高速な命令が存在する場合があります。この最適化は、そのような命令を活用して、ゼロとの比較をより効率的に行うことを目的としています。

これらの最適化をスムーズに導入するために、既存のブール値および比較のコード生成ロジックを整理し、より柔軟で保守しやすい構造にすることが必要とされました。このコミット自体は機能的な変更を含まず、既存の動作に影響を与えないことが `toolstash -cmp` によって確認されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造とコード生成に関する基本的な知識が必要です。

*   **`cmd/internal/gc` パッケージ**: Goコンパイラの主要な内部パッケージの一つで、Go言語のソースコードを中間表現から最終的な機械語コードに変換するバックエンドの大部分を担っています。`gc` は "Go compiler" の略です。
*   **コード生成 (Code Generation)**: コンパイラの最終段階で、最適化された中間表現からターゲットアーキテクチャの機械語命令を生成するプロセスです。
*   **`Node` 構造体**: Goコンパイラ内部で、抽象構文木 (AST) の各ノードや、中間表現の要素を表すために使用される汎用的な構造体です。プログラムの各要素（変数、定数、演算子、関数呼び出しなど）が `Node` として表現されます。
*   **`Bgen` 関数**: `gc` パッケージ内の重要な関数で、ブール式（例: `a == b`, `x && y`, `!z`）の評価結果に基づいて条件分岐コードを生成する役割を担っています。`Bgen` は、特定の条件が真または偽の場合に、指定されたプログラムカウンタ (PC) にジャンプする命令を生成します。
*   **`bgen_float` 関数**: 浮動小数点数の比較（例: `f1 > f2`）に対する条件分岐コードを生成する関数です。浮動小数点数の比較は、NaN (Not a Number) の存在などにより、整数とは異なる特殊な考慮が必要です。
*   **`obj.Prog`**: Goコンパイラのバックエンドで使用される、単一の機械語命令を表す構造体です。
*   **`likely` パラメータ**: 条件分岐の「予測ヒント」を示すパラメータです。コンパイラは、このヒントを基に、CPUの分岐予測器がより正確に予測できるようにコードを配置する場合があります。`likely` が正の値であれば分岐が取られる可能性が高い、負の値であれば取られない可能性が高いことを示します。
*   **`Addable`**: `Node` のプロパティで、そのノードが直接アドレス指定可能（メモリ上のアドレスやレジスタに直接対応する）かどうかを示します。`Addable` でない場合は、一時的なレジスタやメモリにロードする必要があることを意味します。
*   **`Ullman` 数**: コンパイラの最適化において、式の評価順序を決定するために使用されるヒューリスティックな値です。Ullman数は、式を評価するために必要なレジスタの最小数を示唆します。
*   **`CL` (Change List)**: Goプロジェクトのコードレビューシステム (Gerrit) における変更の単位です。`CL 2284` は特定のコードレビューを指します。
*   **`issue`**: Goプロジェクトの課題追跡システム (GitHub Issues) における課題の単位です。`issue 10381` は特定の課題を指します。
*   **`toolstash -cmp`**: Goの開発ツールの一つで、コンパイラの変更が生成されるバイナリコードに機能的な影響を与えないことを確認するために使用されます。変更前と変更後のコンパイラで生成されたバイナリを比較し、差異がないことを検証します。

## 技術的詳細

このコミットは、主にGoコンパイラのコード生成バックエンドにおけるブール値の評価と浮動小数点数の比較ロジックをリファクタリングしています。主要な変更点は以下の通りです。

1.  **`Bgen` および `bgen_float` 関数のシグネチャ変更**:
    *   以前は `int true_` という整数型のパラメータで「真の場合にジャンプするかどうか」を表現していましたが、これを `bool wantTrue` というブール型に変更しました。これにより、コードの意図がより明確になり、型安全性が向上します。`true_` が `0` の場合は偽、`1` の場合は真を意味していましたが、`wantTrue` は直接 `true` または `false` を受け取るため、可読性が大幅に向上します。
    *   `bgen_float` 関数も同様に `true_` から `wantTrue` に変更されています。

2.  **`Bgen` 関数の内部ロジックの整理**:
    *   `OLITERAL` (リテラル定数) および `ONAME` (変数名) のケースが簡素化され、`bgenNonZero` という新しいヘルパー関数が導入されました。
    *   `OANDAND` (論理AND) および `OOROR` (論理OR) の処理が、`wantTrue` パラメータに基づいてより簡潔に記述されています。
    *   比較演算子 (`OEQ`, `ONE`, `OLT`, `OGT`, `OLE`, `OGE`) の処理が大幅にリファクタリングされました。特に、浮動小数点数の比較におけるNaN (Not a Number) の特殊な振る舞い（`brcom` がNaNに対して有効でないことなど）がより明確に、かつ一貫性のある方法で処理されるようになりました。
    *   スライスやインターフェースの比較に関するエラーチェックが改善され、`Isslice` や `Isinter` といったヘルパー関数が活用されています。
    *   64ビット整数を32ビットシステムで比較する際の特殊な処理 (`Cmp64`) も、より整理された形で記述されています。

3.  **`CgenTemp` ヘルパー関数の導入**:
    *   `src/cmd/internal/gc/gen.go` に `CgenTemp` という新しいヘルパー関数が追加されました。この関数は、一時的な `Node` を作成し、指定された `Node` の値をその一時的な `Node` にコピーするコードを生成し、その一時的な `Node` を返します。これにより、コード生成ロジック内で一時変数を扱う際の定型的なコードが削減され、可読性と保守性が向上します。

4.  **`complexbool` 関数のリファクタリング**:
    *   `src/cmd/internal/gc/cplx.go` の `Complexbool` 関数が `complexbool` にリネームされ、`true_` パラメータが `wantTrue` (bool型) に変更されました。
    *   複素数の比較ロジックが、実部と虚部の比較に分解され、`OANDAND` を用いて結合される構造がより明示的に記述されました。これにより、複素数比較のコード生成が `Bgen` の新しいシグネチャと一貫するようになりました。
    *   不要な `CASE` マクロが削除されました。

5.  **`Brcom` および `Brrev` 関数のコメント改善**:
    *   `src/cmd/internal/gc/subr.go` にある `Brcom` (条件を反転させる) および `Brrev` (オペランドを反転させる) 関数のコメントが、より分かりやすく、具体的な例を挙げて説明するように改善されました。また、`Fatal` エラーメッセージのフォーマットも統一されています。

これらの変更は、コードの重複を減らし、ロジックをよりモジュール化し、将来の最適化のための基盤を強化することを目的としています。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラのコード生成ロジック、特にブール値の評価と浮動小数点数の比較に関する部分の「クリーンアップ」です。これは、単なるコードの整形以上の意味を持ちます。

### `Bgen` 関数の改善

`Bgen` 関数は、Go言語の `if` 文や論理演算子 (`&&`, `||`, `!`) などのブール式を機械語に変換する際の中心的な役割を担っています。

*   **`true_ int` から `wantTrue bool` への変更**:
    以前の `true_ int` パラメータは、`0` が偽、`1` が真を意味する慣習的なものでした。しかし、これはGoの型システムから見ると曖昧であり、意図が不明瞭でした。`wantTrue bool` への変更は、このパラメータが「ブール式が `true` であることを期待するか、`false` であることを期待するか」を直接的に示すようになり、コードの可読性と自己文書化能力を大幅に向上させました。これにより、開発者は関数の呼び出しを見ただけで、そのブール式がどのような条件でジャンプを生成するのかを直感的に理解できるようになります。

*   **内部ロジックの簡素化と共通化**:
    `Bgen` 内部では、様々な種類のブール式（リテラル、変数、論理演算、比較演算など）が処理されます。このコミットでは、これらの処理パスが整理され、特に非ゼロ比較のロジックが `bgenNonZero` という独立したヘルパー関数に抽出されました。これにより、コードの重複が減り、各ケースの処理がより明確になりました。
    また、浮動小数点数の比較におけるNaNの特殊な振る舞い（例: `NaN == NaN` は `false`、`NaN < 5` も `false`）を考慮した複雑な条件分岐が、より構造化された形で記述されるようになりました。これは、将来のジャンプフリーなブール値の実装において、これらの特殊ケースをより効率的に扱うための基盤となります。

### `CgenTemp` ヘルパー関数の導入

`src/cmd/internal/gc/gen.go` に追加された `CgenTemp` 関数は、コード生成における一般的なパターンを抽象化します。

```go
// CgenTemp creates a temporary node, assigns n to it, and returns it.
func CgenTemp(n *Node) *Node {
	var tmp Node
	Tempname(&tmp, n.Type) // 一時的なNodeを作成
	Cgen(n, &tmp)          // nの値をtmpにコピーするコードを生成
	return &tmp            // tmpを返す
}
```

コンパイラが複雑な式を評価する際、中間結果を一時的に保存するための変数（またはレジスタ）が必要になることがよくあります。以前は、この「一時的なNodeを作成し、値をコピーする」という一連の処理がコードの様々な場所に散在していました。`CgenTemp` はこのパターンをカプセル化することで、以下の利点をもたらします。

*   **コードの重複排除**: 同じロジックが何度も書かれることを防ぎます。
*   **可読性の向上**: 一時変数の作成と初期化の意図が明確になります。
*   **保守性の向上**: 一時変数の管理ロジックに変更があった場合、一箇所を修正するだけで済みます。

これは、コンパイラコードの全体的な品質と保守性を向上させるための典型的なリファクタリングパターンです。

### `complexbool` 関数のリファクタリング

複素数の比較は、実部と虚部の両方が等しい場合にのみ真となるため、内部的には2つの浮動小数点数比較（実部の比較と虚部の比較）と論理ANDの組み合わせとして扱われます。

*   `Complexbool` から `complexbool` へのリネームと `wantTrue bool` への変更は、`Bgen` との一貫性を保つためのものです。
*   内部の実部と虚部の比較を明示的に `OEQ` ノードとして構築し、それらを `OANDAND` ノードで結合する構造は、複素数比較のセマンティクスをコード上でより正確に表現しています。これにより、コンパイラが複素数比較をどのように処理するかが明確になり、将来的な最適化（例えば、複素数比較に特化したCPU命令がある場合など）のフックを提供しやすくなります。

全体として、このコミットはGoコンパイラのコード生成バックエンドを、よりクリーンで、より理解しやすく、将来の性能最適化を容易にするための堅牢な基盤へと進化させています。機能的な変更がないにもかかわらず、このような内部的な改善は、長期的なプロジェクトの健全性にとって非常に重要です。

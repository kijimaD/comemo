# [インデックス 20110] ファイルの概要

このコミットは、Goランタイムのメモリ割り当て（`malloc`）の高速パスにおけるパフォーマンス最適化に関するものです。具体的には、`acquirem`および`releasem`の呼び出しを削除することで、アロケーションのオーバーヘッドを削減しています。

変更されたファイルは以下の通りです。

*   `src/cmd/api/goapi.go`: APIチェッカーがランタイムの型定義を認識できるように、`mcache`型を追加しています。
*   `src/pkg/runtime/malloc.go`: `gomallocgc`関数において、`malloc`の高速パスから`acquirem`/`releasem`の呼び出しを削除し、デバッグ用のチェックを追加しています。
*   `src/pkg/runtime/race.c`: `racemalloc`関数に`NOSPLIT`フラグを追加しています。
*   `src/pkg/runtime/stubs.go`: `gomcache`関数の宣言を追加しています。
*   `src/pkg/runtime/stubs.goc`: `gomcache`関数の実装を追加しています。

## 変更の背景

Goランタイムのメモリ割り当て関数である`gomallocgc`は、小さなオブジェクトの割り当てにおいて頻繁に呼び出されます。この関数は、ガベージコレクション（GC）との整合性を保つためにアトミックである必要があります。従来、このアトミック性を保証するために`acquirem`と`releasem`という関数が使用されていました。これらは、現在のM（Machine、OSスレッドに相当）をロックし、GCがそのMをプリエンプトするのを防ぐ役割を担っていました。

しかし、`acquirem`と`releasem`の呼び出しは、特に高速パス（頻繁に実行される、シンプルなメモリ割り当て処理）においては、無視できないオーバーヘッドとなっていました。コミットメッセージに示されているベンチマーク結果からもわかるように、これらの呼び出しを削除することで、`Malloc`関連のベンチマークで最大16%以上のパフォーマンス向上が見られました。

この変更の背景には、以下の仮定があります。
1.  `malloc`の高速パスのコードはスタックスプリットチェックを持たないため、GCによってプリエンプトされることがない。
2.  `roundup`や`add`のような関数はインライン化される。
3.  `onM`や`racemalloc`のような関数は`NOSPLIT`属性を持つ。

これらの仮定が真であれば、`acquirem`/`releasem`による明示的なロックは不要となり、パフォーマンスを向上させることができます。このコミットは、これらの仮定を検証するためのデバッグコードも追加しています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリ管理システムを持っています。主要なコンポーネントは以下の通りです。

*   **M (Machine)**: OSスレッドに相当します。Goのスケジューラは、G（Goroutine）をM上で実行します。
*   **P (Processor)**: 論理プロセッサに相当し、Gの実行コンテキストを提供します。MはPにアタッチされてGを実行します。
*   **G (Goroutine)**: Goの軽量スレッドです。
*   **mcache**: 各Pにローカルなメモリキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。GCの介入なしに、PにアタッチされたMから直接アクセスできます。
*   **mspan**: 連続したメモリページのブロックです。`mcache`は`mspan`からメモリを割り当てます。
*   **mheap**: 全てのPで共有されるヒープです。`mcache`が`mspan`を使い果たした場合、`mheap`から新しい`mspan`を取得します。

### GoのGC (Garbage Collection) とそのアトミック性

Goのガベージコレクタは、並行かつ低遅延で動作するように設計されています。GCは、プログラムの実行中にバックグラウンドで動作し、不要になったメモリを回収します。GCがメモリをスキャンしている間、メモリの状態が変化しないように、特定の操作（例えばメモリ割り当て）はGCに対してアトミックである必要があります。これは、GCが不整合なメモリ状態を読み取ってしまうことを防ぐためです。

### `acquirem` と `releasem` の役割

`acquirem`と`releasem`は、Goランタイム内部で使用される関数で、現在のM（OSスレッド）をロック/アンロックする役割を担います。これらは、GCが特定のMをプリエンプト（中断）するのを防ぐために使用されます。例えば、GCがメモリをスキャンしている最中に、そのMがメモリ割り当てを行ってメモリの状態を変更してしまうと、GCの正確性が損なわれる可能性があります。`acquirem`を呼び出すことで、そのMはGCから保護され、GCが安全に動作できるようになります。処理が完了したら`releasem`を呼び出してロックを解放します。

### `NOSPLIT` とスタックスプリットチェック

Goの関数は、デフォルトでスタックスプリットチェック（stack split check）を持っています。これは、関数が呼び出される際に、現在のゴルーチンのスタックが十分なサイズを持っているかを確認し、必要であればスタックを拡張するメカニズムです。これにより、Goは可変長のスタックを効率的に利用できます。

しかし、一部のランタイム関数では、スタックスプリットチェックが不要または望ましくない場合があります。そのような関数には、`NOSPLIT`というコンパイラディレクティブが付けられます。`NOSPLIT`が付けられた関数は、スタックスプリットチェックを行わないため、スタックの拡張が発生せず、GCによるプリエンプションの対象外となります。これは、非常に短い、アトミックな操作を行う関数に適しています。

### `malloc` のファストパスとスローパス

Goのメモリ割り当て関数（`malloc`）には、主に「ファストパス」と「スローパス」があります。

*   **ファストパス**: ほとんどの小さなオブジェクトの割り当てに使用されます。これは、現在のPの`mcache`から直接メモリを割り当てることで、ロックなしで非常に高速に実行されます。
*   **スローパス**: `mcache`が空になった場合や、大きなオブジェクトを割り当てる場合など、より複雑な処理が必要なときに使用されます。このパスでは、`mheap`から新しい`mspan`を取得したり、GCと協調したりするため、より多くのオーバーヘッドが発生します。

このコミットは、特にファストパスのパフォーマンス向上に焦点を当てています。

## 技術的詳細

このコミットの主要な変更は、`src/pkg/runtime/malloc.go`内の`gomallocgc`関数にあります。

### `acquirem`/`releasem`の削除と仮定の検証

変更前は、`gomallocgc`の冒頭で`acquirem`が呼び出され、関数終了時に`releasem`が呼び出されていました。これは、`gomallocgc`全体がGCに対してアトミックであることを保証するためでした。

```go
// 変更前 (抜粋)
func gomallocgc(size uintptr, typ *_type, flags int) unsafe.Pointer {
	// ...
	mp := acquirem() // Mをロック
	if mp.mallocing != 0 {
		gothrow("malloc/free - deadlock")
	}
	mp.mallocing = 1
	// ...
	// ファストパスの終了時
	// mp.mallocing = 0
	// releasem(mp) // Mをアンロック
	// ...
	// 関数終了時
	// mp.mallocing = 0
	// releasem(mp) // Mをアンロック
}
```

このコミットでは、`malloc`の高速パスにおいて、これらの`acquirem`/`releasem`の呼び出しが削除されました。これは、高速パスのコードが以下の特性を持つため、GCによるプリエンプションの危険性がないという仮定に基づいています。

1.  **スタックスプリットチェックがない**: 高速パスのコードは、スタックスプリットチェックを行わないため、GCがスタックをスキャンしている最中にスタックが拡張されることによる不整合が発生しません。
2.  **インライン化される関数**: `roundup`や`add`のようなヘルパー関数はインライン化されるため、関数呼び出しのオーバーヘッドがありません。
3.  **`NOSPLIT`関数**: `onM`や`racemalloc`のような関数は`NOSPLIT`属性を持つため、それら自体がスタックスプリットチェックを行わず、GCによるプリエンプションの対象外です。

これらの仮定を検証するために、`debugMalloc`という新しいグローバル変数（コンパイル時に設定可能）が導入されました。`debugMalloc`が`true`の場合、`acquirem`/`releasem`の呼び出しがデバッグ目的で残され、`mp.mallocing`フラグや`mp.curg.stackguard0`（スタックスプリットチェックのガード値）を操作して、上記の仮定が破られていないかをチェックします。これにより、開発者は本番環境でのパフォーマンスを維持しつつ、デバッグビルドで潜在的な問題を早期に発見できます。

### `gomcache()`の導入

変更前は、`mcache`へのポインタは`mp.mcache`を介して取得されていました。

```go
// 変更前 (抜粋)
c := mp.mcache
```

このコミットでは、`gomcache()`という新しいヘルパー関数が導入され、`mcache`へのアクセスがこの関数を介して行われるようになりました。

```go
// 変更後 (抜粋)
c := gomcache()
```

`gomcache()`は`src/pkg/runtime/stubs.goc`で実装されており、`g->m->mcache`を返します。この関数自体も`NOSPLIT`属性を持つため、`malloc`の高速パスの特性（スタックスプリットチェックなし）を維持できます。これにより、`acquirem`なしで安全に`mcache`にアクセスできるようになります。

## コアとなるコードの解説

### `gomallocgc`の変更

`gomallocgc`関数はGoランタイムの主要なメモリ割り当て関数です。このコミットの核心は、この関数内の`acquirem`と`releasem`の呼び出しを、特に高速パスから削除した点にあります。

*   **`acquirem`/`releasem`の削除**: 変更前は、`gomallocgc`の開始時に`acquirem`が呼び出され、終了時に`releasem`が呼び出されていました。これにより、`gomallocgc`の実行中はGCが現在のMをプリエンプトできないようにしていました。しかし、`malloc`の高速パスは非常に短く、スタックスプリットチェックも行わないため、GCによるプリエンプションの危険性が低いと判断されました。この削除により、ロックの取得と解放にかかるオーバーヘッドが削減され、パフォーマンスが向上します。
*   **`debugMalloc`によるデバッグコード**: `debugMalloc`が`true`の場合にのみ実行されるデバッグコードが追加されました。このコードは、`acquirem`/`releasem`を呼び出し、`mp.mallocing`フラグや`mp.curg.stackguard0`を操作して、`malloc`の高速パスがGCに対して安全であるという仮定（スタックスプリットチェックがないことなど）が破られていないかをチェックします。これにより、開発段階で潜在的な問題を検出できます。
*   **`gomcache()`の利用**: `mcache`へのアクセスが`mp.mcache`から`gomcache()`関数を介するように変更されました。`gomcache()`は`NOSPLIT`関数であり、`g->m->mcache`を直接返すため、`acquirem`なしで安全かつ高速に`mcache`にアクセスできます。

### `racemalloc`の`NOSPLIT`化

## 変更の背景

Goランタイムのメモリ割り当て関数である`gomallocgc`は、小さなオブジェクトの割り当てにおいて頻繁に呼び出されます。この関数は、ガベージコレクション（GC）との整合性を保つためにアトミックである必要があります。従来、このアトミック性を保証するために`acquirem`と`releasem`という関数が使用されていました。これらは、現在のM（Machine、OSスレッドに相当）をロックし、GCがそのMをプリエンプトするのを防ぐ役割を担っていました。

しかし、`acquirem`と`releasem`の呼び出しは、特に高速パス（頻繁に実行される、シンプルなメモリ割り当て処理）においては、無視できないオーバーヘッドとなっていました。コミットメッセージに示されているベンチマーク結果からもわかるように、これらの呼び出しを削除することで、`Malloc`関連のベンチマークで最大16%以上のパフォーマンス向上が見られました。

この変更の背景には、以下の仮定があります。
1.  `malloc`の高速パスのコードはスタックスプリットチェックを持たないため、GCによってプリエンプトされることがない。
2.  `roundup`や`add`のような関数はインライン化される。
3.  `onM`や`racemalloc`のような関数は`NOSPLIT`属性を持つ。

これらの仮定が真であれば、`acquirem`/`releasem`による明示的なロックは不要となり、パフォーマンスを向上させることができます。このコミットは、これらの仮定を検証するためのデバッグコードも追加しています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリ管理システムを持っています。主要なコンポーネントは以下の通りです。

*   **M (Machine)**: OSスレッドに相当します。Goのスケジューラは、G（Goroutine）をM上で実行します。
*   **P (Processor)**: 論理プロセッサに相当し、Gの実行コンテキストを提供します。MはPにアタッチされてGを実行します。
*   **G (Goroutine)**: Goの軽量スレッドです。
*   **mcache**: 各Pにローカルなメモリキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。GCの介入なしに、PにアタッチされたMから直接アクセスできます。
*   **mspan**: 連続したメモリページのブロックです。`mcache`は`mspan`からメモリを割り当てます。
*   **mheap**: 全てのPで共有されるヒープです。`mcache`が`mspan`を使い果たした場合、`mheap`から新しい`mspan`を取得します。

### GoのGC (Garbage Collection) とそのアトミック性

Goのガベージコレクタは、並行かつ低遅延で動作するように設計されています。GCは、プログラムの実行中にバックグラウンドで動作し、不要になったメモリを回収します。GCがメモリをスキャンしている間、メモリの状態が変化しないように、特定の操作（例えばメモリ割り当て）はGCに対してアトミックである必要があります。これは、GCが不整合なメモリ状態を読み取ってしまうことを防ぐためです。

### `acquirem` と `releasem` の役割

`acquirem`と`releasem`は、Goランタイム内部で使用される関数で、現在のM（OSスレッド）をロック/アンロックする役割を担います。これらは、GCが特定のMをプリエンプト（中断）するのを防ぐために使用されます。例えば、GCがメモリをスキャンしている最中に、そのMがメモリ割り当てを行ってメモリの状態を変更してしまうと、GCの正確性が損なわれる可能性があります。`acquirem`を呼び出すことで、そのMはGCから保護され、GCが安全に動作できるようになります。処理が完了したら`releasem`を呼び出してロックを解放します。

### `NOSPLIT` とスタックスプリットチェック

Goの関数は、デフォルトでスタックスプリットチェック（stack split check）を持っています。これは、関数が呼び出される際に、現在のゴルーチンのスタックが十分なサイズを持っているかを確認し、必要であればスタックを拡張するメカニズムです。これにより、Goは可変長のスタックを効率的に利用できます。

しかし、一部のランタイム関数では、スタックスプリットチェックが不要または望ましくない場合があります。そのような関数には、`NOSPLIT`というコンパイラディレクティブが付けられます。`NOSPLIT`が付けられた関数は、スタックスプリットチェックを行わないため、スタックの拡張が発生せず、GCによるプリエンプションの対象外となります。これは、非常に短い、アトミックな操作を行う関数に適しています。

### `malloc` のファストパスとスローパス

Goのメモリ割り当て関数（`malloc`）には、主に「ファストパス」と「スローパス」があります。

*   **ファストパス**: ほとんどの小さなオブジェクトの割り当てに使用されます。これは、現在のPの`mcache`から直接メモリを割り当てることで、ロックなしで非常に高速に実行されます。
*   **スローパス**: `mcache`が空になった場合や、大きなオブジェクトを割り当てる場合など、より複雑な処理が必要なときに使用されます。このパスでは、`mheap`から新しい`mspan`を取得したり、GCと協調したりするため、より多くのオーバーヘッドが発生します。

このコミットは、特にファストパスのパフォーマンス向上に焦点を当てています。

### `acquirem`/`releasem`の削除と仮定の検証

変更前は、`gomallocgc`の冒頭で`acquirem`が呼び出され、関数終了時に`releasem`が呼び出されていました。これは、`gomallocgc`全体がGCに対してアトミックであることを保証するためでした。

1.  **スタックスプリットチェックがない**: 高速パスのコードは、スタックスプリットチェックを行わないため、GCがスタックをスキャンしている最中にスタックが拡張されることによる不整合が発生しません。
2.  **インライン化される関数**: `roundup`や`add`のようなヘルパー関数はインライン化されるため、関数呼び出しのオーバーヘッドがありません。
3.  **`NOSPLIT`関数**: `onM`や`racemalloc`のような関数は`NOSPLIT`属性を持つため、それら自体がスタックスプリットチェックを行わず、GCによるプリエンプションの対象外です。

これらの仮定を検証するために、`debugMalloc`という新しいグローバル変数（コンパイル時に設定可能）が導入されました。`debugMalloc`が`true`の場合、`acquirem`/`releasem`の呼び出しがデバッグ目的で残され、`mp.mallocing`フラグや`mp.curg.stackguard0`（スタックスプリットチェックのガード値）を操作して、上記の仮定が破られていないかをチェックします。これにより、開発者は本番環境でのパフォーマンスを維持しつつ、デバッグビルドで潜在的な問題を早期に発見できます。

### `gomcache()`の導入

変更前は、`mcache`へのポインタは`mp.mcache`を介して取得されていました。

```go

## コアとなるコードの解説

### `gomallocgc`の変更

`gomallocgc`関数はGoランタイムの主要なメモリ割り当て関数です。このコミットの核心は、この関数内の`acquirem`と`releasem`の呼び出しを、特に高速パスから削除した点にあります。

*   **`acquirem`/`releasem`の削除**: 変更前は、`gomallocgc`の開始時に`acquirem`が呼び出され、終了時に`releasem`が呼び出されていました。これにより、`gomallocgc`の実行中はGCが現在のMをプリエンプトできないようにしていました。しかし、`malloc`の高速パスは非常に短く、スタックスプリットチェックも行わないため、GCによるプリエンプションの危険性が低いと判断されました。この削除により、ロックの取得と解放にかかるオーバーヘッドが削減され、パフォーマンスが向上します。
*   **`debugMalloc`によるデバッグコード**: `debugMalloc`が`true`の場合にのみ実行されるデバッグコードが追加されました。このコードは、`acquirem`/`releasem`を呼び出し、`mp.mallocing`フラグや`mp.curg.stackguard0`を操作して、`malloc`の高速パスがGCに対して安全であるという仮定（スタックスプリットチェックがないことなど）が破られていないかをチェックします。これにより、開発段階で潜在的な問題を検出できます。
*   **`gomcache()`の利用**: `mcache`へのアクセスが`mp.mcache`から`gomcache()`関数を介するように変更されました。`gomcache()`は`NOSPLIT`関数であり、`g->m->mcache`を直接返すため、`acquirem`なしで安全かつ高速に`mcache`にアクセスできます。

### `racemalloc`の`NOSPLIT`化

`src/pkg/runtime/race.c`の`racemalloc`関数に`#pragma textflag NOSPLIT`が追加されました。これは、`racemalloc`がスタックスプリットチェックを行わないことをコンパイラに指示します。`racemalloc`はメモリ割り当ての際にレースコンディション検出のために呼び出される関数であり、その実行は非常に高速である必要があります。`NOSPLIT`化することで、この関数のオーバーヘッドをさらに削減し、`malloc`の高速パスの全体的なパフォーマンス向上に貢献します。

### `gomcache`関数の追加

`src/pkg/runtime/stubs.go`で`gomcache()`が宣言され、`src/pkg/runtime/stubs.goc`でその実装が提供されました。

```c
#pragma textflag NOSPLIT
func runtime·gomcache() (ret *MCache) {
	ret = g->m->mcache;
}
```

この関数は、現在のゴルーチン（`g`）が実行されているM（`g->m`）の`mcache`へのポインタを返します。ここでも`NOSPLIT`プラグマが使用されており、この関数がスタックスプリットチェックを行わないことが保証されます。これにより、`malloc`の高速パスから`acquirem`なしで`mcache`に安全にアクセスできるようになります。

これらの変更により、Goランタイムは小さなオブジェクトのメモリ割り当てをより効率的に行えるようになり、全体的なアプリケーションのパフォーマンスが向上しました。

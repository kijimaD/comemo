# [インデックス 27068] ファイルの概要

このコミットは、Goコンパイラ内部における型 (`Type` struct) の構築とコピーに関するコードを整理し、将来的な大規模なリファクタリングに備えるための準備作業です。特に、単一の汎用的な `Type` 構造体が持つフィールドの過負荷を解消し、各Goの型をより独立した形で表現できるようにするための基盤を築くことを目的としています。

## 変更の背景

Goコンパイラの初期設計では、Go言語のあらゆる型（プリミティブ型、構造体、配列、関数、インターフェースなど）を表現するために、`Type`という単一の巨大な構造体 (`struct`) が使用されていました。この `Type` 構造体は、その `Etype` (Element Type) フィールドによって、それがどのような種類の型であるかを区別し、その種類に応じて異なるフィールドを多重に利用していました。例えば、配列型であれば `Type` フィールドが要素型を指し、関数型であれば `Type` フィールドが戻り値の型リストを指す、といった具合です。

このような「単一の汎用的な `Type` 構造体」は、コードの複雑性を増し、特定の型に関するロジックを理解・変更するのを困難にしていました。特に、既存の `Type` インスタンスの `Etype` を後から変更する、いわゆる「Type rekinding」は、その型の意味論を根本から変えてしまうため、コンパイラの健全性を保つ上で潜在的な問題を引き起こす可能性がありました。

このコミットは、将来的に `Type` 構造体を、各Goの型に対応するより特化した複数の構造体（例: `ArrayType`, `FuncType` など）に分割する大規模なリファクタリングの第一歩として行われました。このリファクタリングの目的は、コンパイラの型システムをより明確で、保守しやすく、拡張性の高いものにすることです。

この準備段階として、型を構築およびコピーするロジックを一元化し、特に「Type rekinding」が発生している箇所を明確にマーク（`TODO`コメントの追加）することで、将来のリファクタリング時にこれらの問題箇所を特定し、適切に修正できるようにしています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)
Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担います。`cmd/compile` は、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成といった複数のフェーズで構成されています。

### `Type` 構造体
Goコンパイラ内部で、Go言語の型システムを表現するために使用される中心的なデータ構造です。この構造体は、型の種類（`Etype`）、サイズ（`Width`）、関連するシンボル（`Sym`）、要素型（`Type`）、キー型（`Down`）、フィールドリスト、メソッドリストなど、型のあらゆる情報を保持します。

### `Etype` (Element Type)
`Type` 構造体内のフィールドで、その `Type` インスタンスが具体的にどのような種類のGo型であるかを示す列挙型です。例えば、`TINT` (整数型)、`TARRAY` (配列型)、`TFUNC` (関数型)、`TSTRUCT` (構造体型) などがあります。

### Type Rekinding
既存の `Type` 構造体の `Etype` フィールドを、その `Type` が既に構築された後に変更する操作を指します。これは、例えば、一時的に汎用的な型として扱っていたものを、後から具体的な配列型や関数型に「再分類」するような場合に発生します。しかし、`Type` 構造体が多重にフィールドを共有しているため、`Etype` の変更は他のフィールドの意味論にも影響を与え、予期せぬバグや混乱を招く可能性があります。将来的なリファクタリングでは、このような動的な `Etype` の変更は避け、型は一度構築されたらその種類は不変であるべき、という設計思想に移行しようとしています。

### 型のコピー (Shallow Copy vs. Deep Copy)
*   **シャローコピー (Shallow Copy):** オブジェクトの最上位レベルのフィールドのみをコピーし、参照型のフィールドは元のオブジェクトと同じメモリ上のオブジェクトを指します。つまり、コピーされたオブジェクトと元のオブジェクトは、参照型のフィールドを共有します。
*   **ディープコピー (Deep Copy):** オブジェクトのすべてのフィールドを再帰的にコピーし、参照型のフィールドが指すオブジェクトも新しく作成します。これにより、コピーされたオブジェクトと元のオブジェクトは完全に独立します。
Goコンパイラでは、型の情報を変更する際に、元の型を破壊しないようにコピーを作成することがよくあります。このコミットでは、シャローコピーの概念が特に重要になります。

## 技術的詳細

このコミットの主要な技術的変更は、`Type` 構造体のインスタンスを生成およびコピーするメカニズムの一元化と明確化にあります。

1.  **`typ` 関数の移動と一元化:**
    *   以前は `src/cmd/compile/internal/gc/subr.go` に存在していた `typ` 関数（`Type` 構造体のコンストラクタ）が、`Type` 構造体自体が定義されている `src/cmd/compile/internal/gc/type.go` に移動されました。
    *   これにより、`Type` 構造体の生成ロジックがその定義と密接に結びつき、コードの局所性と保守性が向上します。新しい `typ` 関数は、`Type` 構造体の基本的なフィールド（`Etype`, `Width`, `Lineno`, `Orig`）を初期化する責任を持ちます。

2.  **`Type.Copy()` メソッドの導入:**
    *   `Type` 構造体に新しいメソッド `Copy()` が追加されました。このメソッドは、既存の `Type` インスタンスのシャローコピーを作成します。
    *   以前は、`shallow(t *Type)` というグローバル関数がシャローコピーの役割を担っていましたが、これを `Type` メソッドとしてカプセル化することで、`Type` オブジェクト指向的なアプローチに近づけ、型のコピー操作がより明確になります。
    *   `Copy()` メソッドは、`*nt = *t` というGoの構造体コピー機能を利用して、フィールドの値をビット単位でコピーします。これにより、新しい `Type` インスタンスは元のインスタンスと同じフィールド値を持つが、異なるメモリ位置に存在します。
    *   `if t.Orig == t { nt.Orig = nt }` という特殊な処理が含まれています。これは、`Orig` フィールドが自分自身を指している場合に、コピーされた `Type` の `Orig` も自分自身を指すように調整するためのものです。これは、型の正規化や同一性チェックに関連するGoコンパイラの内部的な慣習です。

3.  **`shallow` 関数の廃止と `Copy()` への置き換え:**
    *   `src/cmd/compile/internal/gc/subr.go` から `shallow` 関数が削除され、その呼び出し箇所はすべて `Type.Copy()` メソッドに置き換えられました。
    *   これにより、型のコピー方法が一貫性のあるものになり、将来的な `Type` 構造体のリファクタリング時に、コピーのセマンティクスを理解しやすくなります。

4.  **「Type Rekinding」箇所の `TODO` コメント追加:**
    *   `src/cmd/compile/internal/gc/bimport.go`、`src/cmd/compile/internal/gc/typecheck.go`、および `Type.Copy()` メソッド内など、既存の `Type` インスタンスの `Etype` フィールドが変更される可能性のある箇所に `TODO(mdempsky): Fix Type rekinding.` コメントが追加されました。
    *   これらのコメントは、将来的に `Type` 構造体を分割する際に、これらの「Type rekinding」のパターンを排除または再設計する必要があることを明示的に示しています。理想的には、一度構築された型の種類は不変であるべきであり、もし異なる種類の型が必要な場合は、新しい `Type` インスタンスを構築すべきです。

これらの変更は、Goコンパイラの型システムをより堅牢で、理解しやすく、将来の進化に対応できるようにするための重要な準備ステップです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/type.go` における変更

```go
// typ returns a new Type of the specified kind.
func typ(et EType) *Type {
	t := &Type{
		Etype:  et,
		Width:  BADWIDTH,
		Lineno: lineno,
	}
	t.Orig = t
	return t
}

// Copy returns a shallow copy of the Type.
func (t *Type) Copy() *Type {
	if t == nil {
		return nil
	}
	nt := new(Type)
	*nt = *t
	// TODO(mdempsky): Find out why this is necessary and explain.
	if t.Orig == t {
		nt.Orig = nt
	}
	return nt
}
```
*   **`typ` 関数**: `Type` 構造体の新しいインスタンスを生成するための専用コンストラクタです。指定された `EType` (型の種類) で初期化し、`Width` を `BADWIDTH` に、`Lineno` を現在の行番号に設定します。`t.Orig = t` は、この型がオリジナルの型であることを示します。これにより、型の生成ロジックが一元化され、`Type` 構造体の初期状態が明確になります。
*   **`Copy` メソッド**: `Type` 構造体のシャローコピーを作成します。`new(Type)` で新しい `Type` インスタンスを確保し、`*nt = *t` で元の `t` の内容を新しい `nt` にビット単位でコピーします。これにより、`nt` は `t` と同じ値を持つが、異なるメモリ位置に存在する独立したインスタンスとなります。`if t.Orig == t { nt.Orig = nt }` の部分は、元の型が自分自身を `Orig` として参照している場合、コピーも同様に自分自身を `Orig` として参照するように調整します。これは、型の同一性や正規化に関するGoコンパイラの内部的なセマンティクスを維持するために重要です。`TODO` コメントは、この `Orig` の処理の必要性についてさらなる調査と説明が必要であることを示唆しています。

### `src/cmd/compile/internal/gc/subr.go` における変更

`subr.go` から `typ` 関数と `shallow` 関数が削除され、その呼び出し箇所が `Type.Copy()` に置き換えられました。

**変更前 (`shallow` の使用例):**
```go
func shallow(t *Type) *Type {
	if t == nil {
		return nil
	}
	nt := typ(0) // typ(0) で新しい Type を作成
	*nt = *t     // 元の Type の内容をコピー
	if t.Orig == t {
		nt.Orig = nt
	}
	return nt
}

// deep 関数内での shallow の呼び出し
case TPTR32, TPTR64, TCHAN, TARRAY:
	nt = shallow(t)
	nt.Type = deep(t.Type)
```

**変更後 (`Copy()` の使用例):**
```go
// deep 関数内での t.Copy() の呼び出し
case TPTR32, TPTR64, TCHAN, TARRAY:
	nt = t.Copy() // Type.Copy() メソッドを直接呼び出す
	nt.Type = deep(t.Type)
```
この変更により、型のコピー操作が `Type` 構造体自身のメソッドとしてカプセル化され、コードの意図がより明確になりました。また、`typ(0)` のようなマジックナンバー的な呼び出しが減り、`Type` の生成とコピーのロジックが整理されました。

### `TODO(mdempsky): Fix Type rekinding.` コメントの追加

複数のファイルで、既存の `Type` インスタンスの `Etype` フィールドが変更される箇所にこのコメントが追加されました。
例: `src/cmd/compile/internal/gc/bimport.go`
```go
	isddd := false
	if typ.Etype == T_old_DARRAY {
		// T_old_DARRAY indicates ... type
		// TODO(mdempsky): Fix Type rekinding.
		typ.Etype = TARRAY
		isddd = true
	}
```
このコードスニペットでは、`typ.Etype` が `T_old_DARRAY` から `TARRAY` に変更されています。これは、可変長引数 (`...`) の型を処理する際に、一時的な内部表現から正規の配列型に変換するプロセスです。この `TODO` コメントは、将来の `Type` 構造体のリファクタリングにおいて、このような `Etype` の動的な変更をどのように扱うか（例えば、新しい `Type` インスタンスを生成して置き換えるなど）を検討する必要があることを示しています。

## 変更の背景

このコミットは、Goコンパイラが生成するコードの効率とパフォーマンスを向上させることを目的としています。

1.  **外部オブジェクトとヒープオブジェクトのクリアのスキップ**: Go言語はガベージコレクション（GC）を持つ言語であり、メモリ管理はランタイムによって行われます。変数が宣言された際、そのメモリ領域は通常ゼロ値で初期化されます。しかし、外部（グローバル）変数やヒープに割り当てられるオブジェクトは、そのライフサイクルやアクセスパターンが特殊であるため、常にゼロクリアする必要がない場合があります。特に、これらのオブジェクトが既に適切な値で初期化されることが保証されている場合、冗長なゼロクリア処理はコンパイルされたバイナリのサイズを増やし、実行時のオーバーヘッドを発生させます。この最適化は、これらの不要なクリア処理を排除することで、生成されるコードをより小さく、より速くすることを目指しています。

2.  **定数伝播（Constant Propagation）**: コンパイラ最適化の基本的な手法の一つです。プログラム内で定数値が変数に割り当てられ、その変数が後続の計算で使用される場合、コンパイラはその変数を直接定数値で置き換えることができます。これにより、変数の読み込みや不要な代入命令を削減し、より効率的な機械語コードを生成できます。特に、同じ定数を複数回代入するような冗長なコードパターンを排除することで、コードサイズと実行速度の両方を改善します。

これらの最適化は、Go言語の初期段階において、コンパイラの成熟度を高め、生成されるバイナリの品質を向上させるための重要なステップでした。

## 前提知識の解説

### Goコンパイラ (6g, gc)

Go言語の初期のコンパイラは、`gc` (Go Compiler) と呼ばれるツールセットの一部として提供されていました。このツールセットには、特定のアーキテクチャをターゲットとするコンパイラが含まれており、例えば `6g` はAMD64 (x86-64) アーキテクチャをターゲットとするGoコンパイラでした。

-   **`gc`**: Go言語の公式コンパイラ群の総称。Goのソースコードを機械語に変換します。
-   **`6g`**: `gc`ツールセットの一部で、AMD64アーキテクチャ向けのGoコンパイラ。Go言語の初期には、各アーキテクチャ（例: `8g` for ARM, `5g` for PowerPC）ごとに異なるコンパイラが存在しました。現在では、これらのコンパイラは統合され、`go build`コマンドを通じて透過的に利用されます。

### Peephole最適化

ピーフホール最適化（Peephole Optimization）は、コンパイラ最適化の一種で、生成された機械語コードまたは中間コードの小さな「窓（peephole）」を検査し、より効率的な命令シーケンスに置き換える手法です。

-   **動作原理**: コンパイラが生成した命令列の中から、特定のパターン（例: `MOV R1, R2; MOV R2, R3`）を見つけ出し、より短く、より速い等価な命令列（例: `MOV R1, R3`）に置き換えます。
-   **特徴**:
    -   局所的な最適化であり、コード全体のフローを解析する必要がないため、実装が比較的容易です。
    -   コンパイラのバックエンド（コード生成の後）で適用されることが多いです。
    -   レジスタの使用効率の向上、冗長な命令の削除、特定の命令のより効率的な代替への置き換えなどを行います。

### 定数伝播 (Constant Propagation)

定数伝播は、コンパイラ最適化のデータフロー解析に基づく手法の一つです。プログラムの実行中に値が変化しない定数式を特定し、その定数値をプログラムの他の場所で直接使用することで、計算をコンパイル時に解決し、実行時のオーバーヘッドを削減します。

-   **動作原理**:
    1.  変数に定数値が割り当てられている箇所を特定します（例: `x = 10`）。
    2.  その変数が後続の命令で使用されている箇所を追跡します（例: `y = x + 5`）。
    3.  変数の値がその間に変更されていない場合、変数を直接定数値で置き換えます（例: `y = 10 + 5`）。
    4.  これにより、`y = 15` のように、さらに定数畳み込み（Constant Folding）などの最適化に繋がる可能性があります。
-   **利点**:
    -   実行時の計算量を削減し、プログラムの高速化に貢献します。
    -   冗長な変数アクセスやメモリ操作を排除し、コードサイズを削減します。

### 外部オブジェクト (External Objects) とヒープオブジェクト (Heap Objects) のクリア (ゼロ初期化)

Go言語では、変数が宣言されると、そのメモリ領域は自動的にゼロ値で初期化されます。これは、C/C++のような言語で未初期化の変数が不定値を持つことによるバグを防ぐためのGoの設計思想の一部です。

-   **外部オブジェクト (PEXTERN)**: プログラム全体からアクセス可能なグローバル変数や、他のモジュールからリンクされる外部シンボルを指します。これらはプログラムの開始時に静的に割り当てられ、通常はデータセグメントに配置されます。
-   **ヒープオブジェクト (PHEAP)**: `new`関数や複合リテラル（例: `make`で作成されるスライス、マップ、チャネルなど）によって動的に割り当てられるオブジェクトを指します。これらはヒープメモリに配置され、ガベージコレクタによって管理されます。

通常、これらのオブジェクトが割り当てられる際には、セキュリティや予測可能性のためにゼロクリアされます。しかし、特定の状況下では、このゼロクリアが冗長になることがあります。例えば、コンパイラがオブジェクトが使用される前に必ず明示的に初期化されることを証明できる場合、あるいは、データセグメントに配置されるグローバル変数が既にリンカによってゼロ初期化されている場合などです。このコミットの目的は、このような冗長なゼロクリア処理を特定し、スキップすることです。

## 技術的詳細

### `src/cmd/6g/peep.c` の変更: 定数伝播の導入

このファイルでは、ピーフホール最適化器に定数伝播のロジックが追加されています。

-   **`conprop` 関数の追加**: 新たに `static void conprop(Reg *r)` 関数が定義されました。この関数は、特定のレジスタ `r` に定数が割り当てられた命令（`MOV $con, R`）を受け取り、その定数が後続の命令でどのように使用されているかを追跡します。
-   **定数伝播のロジック**:
    -   `peep` 関数のメインループ内で、`MOV` 命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`, `AMOVSS`, `AMOVSD`）やアドレス計算命令（`ALEAL`, `ALEAQ`）がレジスタに定数またはシンボルアドレスを割り当てている場合を検出します。
    -   `conprop` 関数は、`uniqs` と `uniqp` を使用して、レジスタ `r0` に割り当てられた定数が、後続の命令 `p` で使用されているか、または再定義されているかをチェックします。
    -   もし、同じ定数が同じレジスタに再度割り当てられている冗長な命令が見つかった場合（`case 3: // set` の条件）、`excise(r)` を呼び出してその冗長な命令を削除します。これにより、`MOV $con, R; ...; MOV $con, R` のようなパターンで、途中で `R` の値が変更されていない場合に、2番目の `MOV` 命令が削除されます。
-   **影響**: これにより、コンパイラはより効率的なアセンブリコードを生成し、冗長なレジスタへの定数代入を排除できるようになります。

### `src/cmd/gc/gen.c` の変更: 外部オブジェクトとヒープオブジェクトのクリアスキップ

このファイルでは、コード生成時にオブジェクトのゼロクリアを行う箇所に条件分岐が追加されています。

-   **ゼロクリアの条件分岐**: `cgen_as` 関数内で、変数の型がゼロクリアを必要とする場合に、その変数が `PEXTERN` (外部オブジェクト) または `PHEAP` (ヒープオブジェクト) のクラスに属しているかどうかをチェックする条件が追加されました。
-   **スキップの理由**:
    -   `PEXTERN` (外部オブジェクト): グローバル変数などは、プログラムのロード時にリンカによって既にゼロ初期化されていることが多いため、実行時に再度ゼロクリアする必要がありません。
    -   `PHEAP` (ヒープオブジェクト): ヒープに割り当てられるオブジェクトは、ガベージコレクタによって管理されるメモリ領域に配置されます。Goのランタイムは、新しいヒープ領域を割り当てる際に、その領域をゼロクリアする責任を負う場合があります。もしランタイムが既にゼロクリアを保証している場合、コンパイラが生成するコードで再度ゼロクリアを行うのは冗長になります。
-   **影響**: この変更により、不要なゼロクリア命令が生成されなくなり、結果として生成されるバイナリのサイズが削減され、実行時の初期化オーバーヘッドが減少します。

## コアとなるコードの解説

### `src/cmd/6g/peep.c` の変更点

1.  **`conprop` 関数の追加**:
    ```c
    static void	conprop(Reg *r);
    // ...
    static void
    conprop(Reg *r0)
    {
        Reg *r;
        Prog *p, *p0;
        int t;
        Adr *v0;

        p0 = r0->prog; // 元の命令 (例: MOV $10, R1)
        v0 = &p0->to;  // 元の命令の宛先オペランド (例: R1)
        r = r0;

    loop:
        r = uniqs(r); // r0の宛先レジスタが設定されている次のユニークな命令を探す
        if(r == R || r == r0) // 命令が見つからないか、元の命令に戻った場合
            return;
        if(uniqp(r) == R) // r0の宛先レジスタが使用されている前のユニークな命令を探す
            return;

        p = r->prog; // 現在の命令
        t = copyu(p, v0, A); // 現在の命令pがv0 (元の命令の宛先レジスタ) をどのように扱うか (使用, 設定など) を判定

        switch(t) {
        case 0:	// miss (v0と関係ない)
        case 1:	// use (v0を使用しているが、変更はしていない)
            goto loop; // 次の命令へ
        case 2:	// rar (v0を読み書きしている)
        case 4:	// use and set (v0を使用し、かつ設定している)
            break; // 最適化を中断
        case 3:	// set (v0を設定している)
            // 現在の命令pが、元の命令p0と同じ定数を同じレジスタに代入しているかチェック
            if(p->as == p0->as &&
               p->from.type == p0->from.type &&
               p->from.sym == p0->from.sym &&
               p->from.offset == p0->from.offset &&
               p->from.scale == p0->from.scale &&
               p->from.dval == p0->from.dval &&
               p->from.index == p0->from.index) {
                excise(r); // 冗長な命令を削除
                t++; // ループを継続するためのフラグ
                goto loop;
            }
            break;
        }
    }
    ```
    この `conprop` 関数は、`r0` で指定された命令がレジスタに定数を代入している場合、そのレジスタが後続の命令でどのように使われているかを追跡します。もし、同じ定数が同じレジスタに再度代入されている冗長な命令が見つかり、その間にレジスタの値が変更されていないことが確認できれば、その冗長な代入命令を削除します。`uniqs` と `uniqp` は、データフロー解析のためのヘルパー関数で、レジスタの定義と使用を追跡します。

### `src/cmd/gc/gen.c` の変更点

```c
		// externals and heaps should already be clear
		if(nl->class == PEXTERN)
			return;
		if(nl->class & PHEAP)
			return;
```
このコードは `cgen_as` 関数内に挿入されています。`cgen_as` は、Goのソースコードにおける代入操作をアセンブリコードに変換する役割を担っています。通常、変数が宣言され、メモリが割り当てられる際には、そのメモリ領域をゼロクリアする処理が挿入されます。

しかし、この変更により、代入の左辺 (`nl`) が以下のいずれかのクラスに属する場合、ゼロクリア処理をスキップするようになりました。

-   `PEXTERN`: 外部（グローバル）変数。これらの変数は、プログラムのロード時にリンカによって既にゼロ初期化されていることが期待されるため、コンパイラが再度ゼロクリア命令を生成する必要はありません。
-   `PHEAP`: ヒープに割り当てられるオブジェクト。Goのランタイムは、ヒープから新しいメモリ領域を割り当てる際に、その領域をゼロクリアする責任を負う場合があります。もしランタイムがこのゼロクリアを保証している場合、コンパイラが生成するコードで再度ゼロクリアを行うのは冗長になります。

この最適化により、不要なゼロクリア命令が削減され、生成されるバイナリのサイズが小さくなり、実行時の初期化オーバーヘッドが減少します。

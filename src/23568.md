# [インデックス 23568] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/internal/ld`) における共有ライブラリの取り扱いを改善し、特に型情報に関連するガベージコレクション (GC) データ (`gcdata`、`gcmask`、`gcprog`) の読み込み方法を変更するものです。これにより、共有ライブラリからローカルシンボルを安全に除去できるようになり、結果としてライブラリのサイズが大幅に削減されます。

## 変更の背景

Go言語のリンカは、実行可能ファイルや共有ライブラリを生成する際に、プログラム内の型情報やガベージコレクションに関するメタデータ（`gcdata`）を処理します。この`gcdata`には、GCがヒープ上のオブジェクトを正確にスキャンするために必要な情報が含まれています。具体的には、ポインタの配置を示す`gcmask`や、より複雑なポインタ構造を記述する`gcprog`などがあります。

以前の実装では、共有ライブラリ内の型に関連する`gcmask`や`gcprog`を読み取る際に、リンカがこれらのデータに対応する「ローカルシンボル」に依存していました。ローカルシンボルとは、特定のコンパイル単位（オブジェクトファイル）内でのみ意味を持つシンボルで、通常はデバッグ情報や内部リンカ処理のために存在します。

このローカルシンボルへの依存は、共有ライブラリを配布する際に問題を引き起こしていました。配布される共有ライブラリは、通常、サイズを削減し、内部実装の詳細を隠蔽するために、デバッグ情報やローカルシンボルが「ストリップ（除去）」されます。しかし、`gcdata`の読み込みがローカルシンボルに依存していると、ストリップされたライブラリでは必要な`gcdata`を正確に取得できなくなり、結果としてGoプログラムが共有ライブラリを正しく利用できない可能性がありました。

このコミットの目的は、このローカルシンボルへの依存を取り除き、共有ライブラリをストリップしてもGoプログラムが正しく動作するようにすることです。これにより、共有ライブラリのサイズを削減し、配布効率を向上させることができます。また、副次的な効果として、リンカ内部の`LSym`構造体のサイズも削減されています。

## 前提知識の解説

### Go言語のガベージコレクション (GC) と `gcdata`

Go言語は、自動メモリ管理のためにトレース型ガベージコレクタを採用しています。GCは、ヒープ上に割り当てられたオブジェクトのうち、到達可能なもの（プログラムから参照されているもの）を特定し、到達不可能なものを解放します。このプロセスを正確に行うためには、GCは各オブジェクトがどこにポインタを持っているかを知る必要があります。このポインタ情報を記述したメタデータが`gcdata`です。

*   **`gcmask`**: 比較的単純な構造体や配列の場合に用いられるビットマスクです。オブジェクトのどのオフセットにポインタが存在するかをビット列で表現します。例えば、`0b101`というマスクは、オブジェクトの先頭から0番目と2番目のフィールドがポインタであることを示します（ポインタサイズ単位）。
*   **`gcprog`**: より複雑な型（例えば、可変長配列やインターフェースなど）の場合に用いられる、GCがポインタをスキャンするためのミニプログラムです。このプログラムは、GCがオブジェクトのメモリレイアウトを動的に解析し、ポインタを特定するための命令シーケンスを含んでいます。

これらの`gcdata`は、コンパイル時にGoコンパイラによって生成され、実行可能ファイルやライブラリのデータセクションに埋め込まれます。

### Goリンカ (`cmd/internal/ld`)

`cmd/internal/ld`は、Go言語の標準リンカです。Goコンパイラが生成したオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイル、共有ライブラリ、またはアーカイブライブラリを生成する役割を担います。リンカは、シンボル解決、再配置、セクションの結合、そして`gcdata`を含むランタイムメタデータの埋め込みなど、多くの複雑なタスクを実行します。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション（コード、データ、シンボルテーブルなど）で構成されます。

*   **シンボルテーブル**: プログラム内の関数や変数などのシンボルに関する情報（名前、アドレス、サイズ、型など）を格納します。
    *   **ローカルシンボル**: 特定のオブジェクトファイル内でのみ参照されるシンボル。通常、外部からは見えません。
    *   **グローバルシンボル**: 複数のオブジェクトファイルやライブラリ間で参照されるシンボル。
*   **セクション**: コード、初期化済みデータ、未初期化データ、読み取り専用データなど、異なる種類のデータを格納する領域です。
*   **`elf.File`、`elf.Section`、`elf.Symbol`**: Goの`debug/elf`パッケージで提供される、ELFファイルを解析するための構造体です。これらを使ってELFファイル内のセクションやシンボルにアクセスできます。

### 共有ライブラリとシンボルストリップ

共有ライブラリ（Shared Library、例: `.so`ファイル）は、複数のプログラムで共有されるコードやデータを含むライブラリです。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が促進されます。

「シンボルストリップ（Symbol Stripping）」とは、実行可能ファイルや共有ライブラリからデバッグ情報やローカルシンボルなどの不要なシンボル情報を除去するプロセスです。これにより、ファイルサイズが小さくなり、配布が容易になり、リバースエンジニアリングが困難になるという利点があります。しかし、シンボルストリップは、プログラムのデバッグを困難にする可能性もあります。

### `LSym`構造体

`LSym`は、Goリンカ内部でシンボルを表す構造体です。シンボルの名前、型、アドレス、サイズ、関連するデータ（`P`フィールド）、再配置情報（`R`フィールド）など、リンカがシンボルを処理するために必要なあらゆる情報を含んでいます。このコミットでは、`LSym`から`gcmask`フィールドが削除されています。

## 技術的詳細

このコミットの核心は、共有ライブラリから型に関連する`gcdata`（`gcmask`と`gcprog`）を読み取る際に、ローカルシンボルへの依存を排除することです。

### 変更前の問題点

変更前は、共有ライブラリ内の型`T`の`gcmask`や`gcprog`を取得するために、リンカはまず型データから`gcmask`や`gcprog`が格納されているメモリ上の「アドレス」を読み取っていました。しかし、そのアドレスから「何バイト」読み取るべきかを知るためには、`runtime.gcbits.*`のようなローカルシンボルに依存していました。これらのシンボルは、`gcmask`や`gcprog`のサイズ情報を提供していました。

共有ライブラリがストリップされると、これらのローカルシンボルは除去されてしまいます。その結果、リンカは`gcdata`のアドレスは知っていても、そのサイズが不明なため、正しくデータを読み取ることができませんでした。

### 変更後のアプローチ

このコミットでは、以下の新しいアプローチが導入されました。

1.  **`gcprog`のサイズ計算**: `gcprog`は、先頭の4バイトがプログラムの長さを`uint32`で示すという構造を持っています。この仕様を利用することで、`gcprog`のアドレスが分かれば、最初の4バイトを読み取るだけで全体のサイズを計算できるようになりました。
2.  **`gcmask`のサイズ計算**: `gcmask`のサイズは、型が持つポインタの数（`ptrdata`）とポインタのサイズ（`ptrsize`）から計算できます。具体的には、`ptrdata / ptrsize`でポインタの数を求め、その数に応じたバイト数を読み取ればよいことになります。
3.  **`elf.Section.ReadAt`の活用**: 共有ライブラリのELFファイルから直接、指定されたアドレスとサイズでデータを読み取るために、`debug/elf`パッケージの機能が活用されます。具体的には、`findShlibSection`関数が導入され、特定のアドレスを含むELFセクションを特定し、そのセクションから`ReadAt`メソッドを使ってデータを読み取ります。これにより、シンボルテーブルに依存することなく、物理的なアドレスに基づいてデータを取得できるようになります。

### `LSym`構造体の最適化

`LSym`構造体から`gcmask`フィールドが削除されました。これは、`gcmask`が`LSym`の一部として直接保持される必要がなくなり、必要に応じて動的に計算・読み取りできるようになったためです。この変更により、`LSym`のサイズが24バイト削減され、リンカのメモリ使用効率が向上しました。

```go
+func decodetype_gcprog(s *LSym) []byte {

// decodetype_gcmask 関数の変更点
func decodetype_gcmask(s *LSym) []byte {
    if s.Type == obj.SDYNIMPORT {
        addr := decodetype_gcprog_shlib(s) // gcmaskのアドレスを取得 (gcprogと同じアドレスから始まる)
        ptrdata := decodetype_ptrdata(s) // 型のポインタデータサイズを取得
        sect := findShlibSection(s.File, addr) // 該当セクションを検索
        if sect != nil {
            // ptrdataとポインタサイズからgcmaskのサイズを計算し読み込む
            r := make([]byte, ptrdata/int64(Thearch.Ptrsize))
            sect.ReadAt(r, int64(addr-sect.Addr))
            return r
        }
        Exitf("cannot find gcmask for %s", s.Name)
        return nil
    }
    mask := decode_reloc_sym(s, 2*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize))
    return mask.P
}

// 新しく追加された findShlibSection 関数
func findShlibSection(path string, addr uint64) *elf.Section {
    for _, shlib := range Ctxt.Shlibs {
        if shlib.Path == path {
            for _, sect := range shlib.File.Sections {
                if sect.Addr <= addr && addr <= sect.Addr+sect.Size {
                    return sect
                }
            }
        }
    }
    return nil
}
```
`decodesym.go`では、共有ライブラリから`gcprog`や`gcmask`を読み取るためのロジックが根本的に変更されました。`findShlibSection`は、共有ライブラリのパスと仮想アドレスを受け取り、そのアドレスが属するELFセクションを効率的に見つけ出します。これにより、シンボルテーブルに依存することなく、ELFファイルの物理的な構造から直接データを読み出すことが可能になります。`decodetype_gcprog`と`decodetype_gcmask`は、この`findShlibSection`と`elf.Section.ReadAt`を組み合わせて、`gcdata`のサイズを計算し、必要なバイト数を直接読み取るようになりました。

# [インデックス 22199] ファイルの概要

## コミット
このコミットは、Go言語の`syscall`パッケージにおけるPlan 9オペレーティングシステム上での現在の作業ディレクトリ（PWD: Present Working Directory）の管理方法に関するバグ修正です。具体的には、Plan 9環境でGoのgoroutineが異なる作業ディレクトリを参照してしまう問題を解決し、プロセス全体で一貫した作業ディレクトリを維持するように変更します。

## 元コミット内容
```
syscall: make pwd process-wide on Plan 9

On Plan 9, the pwd is apparently per-thread not per process. That
means different goroutines saw different current directories, even
changing within a goroutine as they were scheduled.

Instead, track the the process-wide pwd protected by a mutex in the
syscall package and set the current goroutine thread's pwd to the
correct once at critical points.

Fixes #9428
```

## 変更の背景
この変更の背景には、Go言語のランタイムがPlan 9上で動作する際に直面していた、現在の作業ディレクトリ（PWD）の不整合問題があります。コミットメッセージによると、Plan 9ではPWDがスレッドごとに管理されているかのように振る舞うため、異なるgoroutineがそれぞれ異なる作業ディレクトリを参照したり、同じgoroutine内でもスケジューリングによって作業ディレクトリが予期せず変更されたりする事象が発生していました。

しかし、一般的なPlan 9のドキュメントや挙動に関する情報源（Web検索結果）によると、Plan 9のPWDは通常、プロセスごとに管理され、プロセス内のスレッド（Goの文脈ではgoroutineがマップされるOSスレッド）は同じPWDを共有するとされています。この矛盾は、GoのランタイムがPlan 9のシステムコールをどのように利用し、goroutineをOSスレッドにどのようにマッピングするかというGo特有の挙動が、Plan 9のPWD管理と予期せぬ相互作用を引き起こしていた可能性を示唆しています。例えば、Goランタイムが内部的に`chdir`を呼び出す際に、異なるOSスレッドにgoroutineが切り替わることで、OSスレッドごとのPWDがGoプログラムの期待と異なる状態になっていた可能性が考えられます。

この不整合は、Goプログラムがファイルシステム操作を行う際に、期待するパスでファイルが見つからない、あるいは意図しないパスで操作が行われるといった、予測不能なバグを引き起こす可能性がありました。特に、`os.Getwd()`や`os.Chdir()`といった関数を使用する際に、Goプログラムの論理的な期待と実際のOSレベルの挙動との間に乖離が生じていたと考えられます。

この問題を解決するため、Goの`syscall`パッケージ内でプロセス全体で一貫したPWDを追跡し、重要なシステムコールが実行される前に現在のgoroutineが動作するOSスレッドのPWDを正しい値に設定するメカニズムを導入する必要がありました。これにより、GoプログラムはPlan 9上でも期待通りのファイルシステム操作を行えるようになります。

## 前提知識の解説

### Plan 9オペレーティングシステム
Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルとして表現し、9Pプロトコルを通じてアクセスするという特徴を持ちます。Plan 9は、そのシンプルで一貫性のある設計、強力なネットワーク透過性、そして独自のファイルシステムとプロセスモデルで知られています。

### 現在の作業ディレクトリ (PWD)
現在の作業ディレクトリ（Present Working Directory、略してPWD）は、オペレーティングシステムがファイルパスを解決する際に基準とするディレクトリです。例えば、`ls my_file.txt`のように相対パスでファイルを指定した場合、OSは現在の作業ディレクトリを基準に`my_file.txt`を探します。`cd`コマンドなどで変更することができます。

### プロセスとスレッド（Plan 9とGoの文脈）
*   **プロセス**: 実行中のプログラムのインスタンスです。それぞれ独立したメモリ空間、ファイルディスクリプタ、そして現在の作業ディレクトリを持ちます。
*   **スレッド**: プロセス内で実行される独立した実行パスです。同じプロセスのメモリ空間やファイルディスクリプタを共有します。一般的なOSでは、スレッドは親プロセスのPWDを共有します。
*   **Plan 9におけるプロセスとスレッド**: Plan 9では、プロセスは独立したアドレス空間とファイルシステムの名前空間を持ちます。スレッドは、プロセス内で協調的にスケジューリングされる実行単位であり、親プロセスのリソースを共有します。一般的な理解では、Plan 9のスレッドは親プロセスのPWDを共有します。
*   **GoにおけるGoroutine**: Go言語のgoroutineは、軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、Goランタイムによって多重化され、少数のOSスレッド上で実行されます。Goランタイムは、goroutineをOSスレッドに動的にマッピングするため、特定のgoroutineが常に同じOSスレッドで実行されるとは限りません。この動的なマッピングが、Plan 9のPWD管理と組み合わさった際に、Goプログラムから見たPWDの不整合を引き起こす原因となっていました。

### Goの`syscall`パッケージ
`syscall`パッケージは、Goプログラムから基盤となるオペレーティングシステムのシステムコールに直接アクセスするための低レベルなインターフェースを提供します。これにより、Go言語の標準ライブラリでは提供されていない、OS固有の機能を利用したり、パフォーマンスが重要な場面で直接システムコールを呼び出したりすることが可能になります。ただし、このパッケージはOSに強く依存するため、移植性には注意が必要です。

### ミューテックス (Mutex)
ミューテックス（Mutual Exclusion）は、並行プログラミングにおいて共有リソースへのアクセスを制御するための同期プリミティブです。複数のgoroutine（またはスレッド）が同時に共有データにアクセスしようとすると、データの破損や不整合が発生する可能性があります。ミューテックスは、一度に一つのgoroutineだけが共有リソースにアクセスできるようにロックをかけることで、このような競合状態を防ぎ、データの整合性を保ちます。

## 技術的詳細

このコミットは、GoのランタイムがPlan 9上で現在の作業ディレクトリ（PWD）を管理する方法を根本的に変更します。問題は、GoのgoroutineがOSスレッドに動的にマッピングされる性質と、Plan 9のPWD管理の間の相互作用にありました。コミットメッセージが示唆するように、Goのランタイムの視点からは、PWDがスレッドごとに異なったり、予期せず変更されたりする挙動が見られたため、これをプロセス全体で一貫させる必要がありました。

解決策は、`syscall`パッケージ内にプロセス全体で共有されるPWDの状態を導入し、これをミューテックスで保護することです。これにより、複数のgoroutineが同時にPWDを変更しようとしても、競合状態が発生せず、常に一貫したPWDが維持されます。

具体的には、以下のメカニズムが導入されました。

1.  **プロセスワイドなPWDの追跡**: `syscall`パッケージ内に`wdStr`という変数を導入し、現在のプロセスワイドなPWDを保持します。この変数へのアクセスは`wdmu`というミューテックスによって保護されます。`wdSet`というブール値のフラグは、`wdStr`が一度でも設定されたかどうかを追跡します。
2.  **`Fixwd()`関数の導入**: この関数は、Goのランタイムがファイルシステム関連のシステムコール（`Open`, `Create`, `Remove`, `Stat`, `Bind`, `Wstat`, `Unmount`など）を呼び出す直前に実行されます。`Fixwd()`は、現在のOSスレッドのPWDが`wdStr`に格納されているプロセスワイドなPWDと異なる場合、`chdir()`システムコールを呼び出してOSスレッドのPWDを`wdStr`に同期させます。これにより、Goプログラムがファイルシステム操作を行う際に、常に期待されるPWDが設定されていることが保証されます。この同期は、`wdmu`ミューテックスによって保護された`fixwdLocked()`内部関数で行われます。
3.  **`Getwd()`と`Chdir()`の変更**:
    *   `Getwd()`関数は、OSから直接PWDを取得するのではなく、`wdStr`にキャッシュされているプロセスワイドなPWDを返します。もし`wdStr`がまだ設定されていない場合は、一度OSから`getwd()`（内部ヘルパー関数）を呼び出して取得し、`wdStr`に保存して初期化します。
    *   `Chdir()`関数は、指定されたパスにOSの`chdir()`システムコールを呼び出してPWDを変更した後、その新しいPWDを`wdStr`に保存します。これにより、Goプログラムが明示的にPWDを変更した場合、その変更がプロセス全体に反映され、`wdStr`にも正しく記録されます。
4.  **低レベルシステムコールラッパーの変更**: `src/syscall/zsyscall_plan9_386.go`と`src/syscall/zsyscall_plan9_amd64.go`内の、`Open`, `Create`, `Remove`, `Stat`, `Bind`, `Wstat`などの低レベルなシステムコールラッパー関数が、Goの公開APIである`syscall.Open`などから直接呼び出されるのではなく、内部的な`open`, `create`といった名前に変更されました。そして、公開APIの関数が`Fixwd()`を呼び出した後にこれらの内部関数を呼び出すように変更されました。これにより、すべてのファイルシステム操作の前にPWDの同期が強制されます。

このアプローチにより、GoのランタイムはPlan 9のOSレベルのPWD管理の特性を吸収し、Goプログラムに対しては一貫したプロセスワイドなPWDのセマンティクスを提供できるようになります。

## コアとなるコードの変更箇所

このコミットにおける主要な変更は、以下のファイルに集中しています。

*   `src/syscall/pwd_plan9.go` (新規ファイル): プロセスワイドなPWDを管理するためのロジックが追加されました。`wdmu` (ミューテックス)、`wdSet` (PWDが設定済みかを示すフラグ)、`wdStr` (現在のプロセスワイドなPWD文字列) といったグローバル変数が定義され、`Fixwd()`, `getwd()`, `Getwd()`, `Chdir()`といった関数が実装されています。
*   `src/syscall/syscall_plan9.go`:
    *   既存の`Getwd()`関数が削除され、`pwd_plan9.go`で定義された新しい`Getwd()`が使用されるようになりました。
    *   `Unmount`, `Open`, `Create`, `Remove`, `Stat`, `Bind`, `Wstat`といったファイルシステム関連の公開API関数に、`Fixwd()`の呼び出しが追加されました。これにより、これらの操作の前に必ずPWDが同期されるようになります。
    *   `Open`, `Create`, `Remove`, `Stat`, `Bind`, `Wstat`の内部的なシステムコール呼び出しが、公開API関数とは異なる（小文字始まりの）名前に変更されました。
*   `src/syscall/env_plan9.go`: `readenv`と`writeenv`関数内で使用されていた`Open`と`Create`が、内部的な`open`と`create`に置き換えられました。これにより、これらの環境変数操作も新しいPWD管理メカニズムの恩恵を受けます。
*   `src/syscall/exec_plan9.go`: `forkExec`関数内で、`ProcAttr.Dir`が空の場合に、新しいプロセスワイドなPWD (`wdStr`) を使用するように変更されました。これにより、子プロセスが親プロセスの現在の作業ディレクトリを正しく継承できるようになります。
*   `src/syscall/zsyscall_plan9_386.go` および `src/syscall/zsyscall_plan9_amd64.go`: これらのファイルは、システムコールをGoの関数にマッピングする自動生成されたファイルです。このコミットでは、`Open`, `Create`, `Remove`, `Stat`, `Bind`, `Wstat`, `Chdir`, `Dup`, `Pread`, `Pwrite`, `Close`, `Mount`, `Fstat`といった関数名が、公開APIと内部的なシステムコールラッパーの間で調整されました。具体的には、公開APIとして提供される関数（例: `syscall.Open`）が、内部的なシステムコールを呼び出す前に`Fixwd()`を呼び出すように変更されたため、これらの自動生成ファイル内の関数名が、内部的な呼び出し規約に合わせて小文字始まり（例: `open`）に変更されています。

## コアとなるコードの解説

### `src/syscall/pwd_plan9.go` (新規ファイル)

```go
// Copyright 2015 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// The working directory in Plan 9 is effectively per P, so different
// goroutines and even the same goroutine as it's rescheduled on
// different Ps can see different working directories.
//
// Instead, track a Go process-wide intent of the current working directory,
// and switch to it at important points.

package syscall

import "sync"

var (
	wdmu  sync.Mutex // guards following
	wdSet bool
	wdStr string
)

func Fixwd() {
	wdmu.Lock()
	defer wdmu.Unlock()
	fixwdLocked()
}

func fixwdLocked() {
	if !wdSet {
		return
	}
	wd, err := getwd() // goroutine-specific getwd
	if err != nil {
		return
	}
	if wd == wdStr {
		return
	}
	if err := chdir(wdStr); err != nil { // chdir to the process-wide PWD
		return
	}
}

// goroutine-specific getwd
func getwd() (wd string, err error) {
	fd, err := open(".", O_RDONLY)
	if err != nil {
		return "", err
	}
	defer Close(fd)
	return Fd2path(fd)
}

func Getwd() (wd string, err error) {
	wdmu.Lock()
	defer wdmu.Unlock()

	if wdSet {
		return wdStr, nil
	}
	wd, err = getwd() // Get current PWD from OS
	if err != nil {
		return
	}
	wdSet = true
	wdStr = wd // Store it as process-wide PWD
	return wd, nil
}

func Chdir(path string) error {
	wdmu.Lock()
	defer wdmu.Unlock()

	if err := chdir(path); err != nil { // Change PWD at OS level
		return err
	}

	wd, err := getwd() // Get actual PWD after chdir
	if err != nil {
		return err
	}
	wdSet = true
	wdStr = wd // Update process-wide PWD
	return nil
}
```

このファイルは、GoランタイムがPlan 9上でプロセスワイドなPWDを管理するための中心的なロジックを含んでいます。

*   `wdmu`, `wdSet`, `wdStr`: これらは、プロセスワイドなPWDの状態を保持するためのグローバル変数です。`wdmu`はミューテックスで、`wdStr`への同時アクセスを保護します。`wdSet`は、`wdStr`が初期化されているかどうかを示すフラグです。
*   `Fixwd()`: この関数は、ファイルシステム操作を行う前に呼び出され、現在のOSスレッドのPWDが`wdStr`に格納されているプロセスワイドなPWDと一致していることを保証します。もし一致しない場合、`chdir()`システムコールを呼び出して同期します。これにより、Goプログラムがどのgoroutineで実行されていても、常に期待されるPWDでファイルシステム操作が行われるようになります。
*   `getwd()`: これは、現在のOSスレッドの実際のPWDをOSから取得するための内部ヘルパー関数です。`open(".", O_RDONLY)`で現在のディレクトリのファイルディスクリプタを開き、`Fd2path(fd)`でそのパスを取得します。
*   `Getwd()`: Goの公開APIである`syscall.Getwd()`の実装です。`wdmu`で保護された`wdStr`にキャッシュされているプロセスワイドなPWDを返します。初回呼び出し時には`getwd()`を呼び出して`wdStr`を初期化します。
*   `Chdir()`: Goの公開APIである`syscall.Chdir()`の実装です。`wdmu`で保護された領域で、指定されたパスにOSの`chdir()`システムコールを呼び出してPWDを変更し、その結果を`wdStr`に反映させます。

### `src/syscall/exec_plan9.go` (変更箇所)

```go
// ... (既存コード) ...

	// ...
	destDir := attr.Dir
	if destDir == "" {
		wdmu.Lock()
		destDir = wdStr // attr.Dirが指定されていない場合、プロセスワイドなPWDを使用
		wdmu.Unlock()

```

`forkExec`関数は、新しいプロセスを生成する際に呼び出されます。この変更により、新しいプロセスの作業ディレクトリが`ProcAttr.Dir`で明示的に指定されていない場合、Goランタイムが管理するプロセスワイドなPWD (`wdStr`) が使用されるようになりました。これにより、子プロセスが親プロセスの現在の作業ディレクトリを正しく継承し、一貫した動作を保証します。これは、`exec`システムコールが新しいプロセスのPWDを設定する際に、Goランタイムが持つPWDの概念を反映させるために重要です。

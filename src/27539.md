# [インデックス 27539] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージにバンドルされている HTTP/2 実装 (`x/net/http2`) を更新するものです。具体的には、`src/net/http/h2_bundle.go` ファイルが大幅に変更されており、これは `net/http` パッケージが `x/net/http2` のコードを直接取り込んで使用していることを示しています。また、`src/vendor/golang.org/x/net/http2/hpack/` 以下のファイルも更新されており、HTTP/2 のヘッダー圧縮メカニズムである HPACK に関連する変更が含まれています。

## コミット

このコミットは、Go 1.6 以降の変更を反映させるため、`x/net/http2` ライブラリを特定の Git リビジョン `31df19d6` に更新します。主な変更点は、HTTP/2 の `HEADERS` フレームとそれに続く `CONTINUATION` フレームの結合ロジックを `Framer` の内部に移動したことです。これにより、ヘッダーブロックの再構築がより低レベルで効率的に行われるようになり、上位層のコードが簡素化されます。また、いくつかのガベージ削減に関する改善も含まれています。

## 変更の背景

Go言語の `net/http` パッケージは、HTTP/1.1 と HTTP/2 の両方をサポートしています。HTTP/2 の実装は、当初 `golang.org/x/net/http2` という独立したリポジトリで開発され、その後 `net/http` パッケージにバンドルされる形で統合されました。これにより、Goユーザーは追加のインポートなしに HTTP/2 を利用できるようになっています。

このコミットの背景には、`x/net/http2` パッケージの継続的な改善と、HTTP/2 プロトコルの仕様へのより厳密な準拠、およびパフォーマンスの最適化があります。特に、HTTP/2 のヘッダーフレーム処理における重要な変更がこの更新の主要な動機となっています。

HTTP/2 プロトコルでは、HTTPヘッダーは `HEADERS` フレームと、必要に応じてそれに続く `CONTINUATION` フレームに分割されて送信されることがあります。これまでの実装では、`Framer` が個々の `HEADERS` および `CONTINUATION` フレームをデコードし、それらを上位のコンポーネント（例: `http2.Server` や `http2.ClientConn`）に渡していました。これらの上位コンポーネントが、断片化されたヘッダーブロックを再構築する責任を負っていました。

このアプローチは、コードの重複や、ヘッダー再構築ロジックの分散を引き起こす可能性がありました。このコミットは、このヘッダー再構築のロジックを `Framer` の内部に移動することで、HTTP/2 のフレーム処理の複雑さを `Framer` にカプセル化し、上位層のコードを簡素化することを目的としています。これにより、モジュール性が向上し、ヘッダー処理の一貫性と堅牢性が確保されます。

## 前提知識の解説

### HTTP/2

HTTP/2 は、HTTP/1.1 の後継として開発されたプロトコルです。主な特徴として以下が挙げられます。

*   **多重化 (Multiplexing)**: 複数のリクエストとレスポンスを単一のTCP接続上で同時に処理できます。これにより、ヘッドオブラインブロッキングの問題が解消され、効率が向上します。
*   **ストリーム (Streams)**: 各リクエスト/レスポンスの交換は「ストリーム」として扱われます。ストリームは双方向で独立しており、それぞれに一意の識別子が付与されます。
*   **フレーム (Frames)**: HTTP/2 の通信は、小さなバイナリ単位であるフレームに分割されます。各フレームにはタイプ、長さ、ストリーム識別子などの情報が含まれます。
*   **ヘッダー圧縮 (HPACK)**: HTTP/1.1 で問題となっていたヘッダーの冗長性を解消するため、HPACK という専用の圧縮方式が導入されています。

### HTTP/2 フレーム: HEADERS と CONTINUATION

*   **HEADERS フレーム**: HTTP ヘッダーブロックの開始部分を伝送するために使用されます。このフレームには、ストリーム識別子、優先度情報、およびヘッダーブロックの最初の断片が含まれます。
*   **CONTINUATION フレーム**: `HEADERS` フレームで送信しきれなかったヘッダーブロックの残りの部分を伝送するために使用されます。`HEADERS` フレームと同じストリーム識別子を持ち、`HEADERS` フレームの後に連続して送信されます。これらのフレームは論理的に一つのヘッダーブロックを構成します。

### HPACK

HPACK は、HTTP/2 で使用されるヘッダー圧縮フォーマットです。HTTP/1.1 では、各リクエストで同じヘッダー（例: `User-Agent`, `Accept`）が繰り返し送信され、帯域幅を無駄にしていました。HPACK は、静的テーブルと動的テーブルを使用して、以前に送信されたヘッダーフィールドをインデックス参照したり、差分エンコーディングを使用したりすることで、ヘッダーのサイズを大幅に削減します。

### Goの net/http パッケージと x/net/http2

Go の `net/http` パッケージは、HTTP クライアントとサーバーの機能を提供する標準ライブラリです。HTTP/2 のサポートは、`golang.org/x/net/http2` というエクステンションパッケージとして開発されました。Go 1.6 以降、この `x/net/http2` のコードは `net/http` パッケージ内にバンドル（ベンダーリング）され、標準ライブラリの一部として提供されるようになりました。これにより、ユーザーは `net/http` をインポートするだけで HTTP/2 の機能を利用できます。このコミットは、そのバンドルされた `x/net/http2` のバージョンを更新するものです。

### Framer

HTTP/2 プロトコルにおいて、`Framer` は低レベルのフレームのエンコード（書き込み）とデコード（読み取り）を担当するコンポーネントです。ネットワークからバイト列を読み取り、それを HTTP/2 フレーム構造にパースしたり、逆に HTTP/2 フレーム構造をバイト列に変換してネットワークに書き込んだりします。このコミット以前は、`Framer` は個々の `HEADERS` と `CONTINUATION` フレームを独立して扱っていましたが、この変更により、これらのフレームを論理的なヘッダーブロックとして結合する役割も担うようになりました。

## 技術的詳細

このコミットの最も重要な技術的変更は、HTTP/2 の `HEADERS` フレームとそれに続く `CONTINUATION` フレームの結合ロジックが `Framer` の内部に移動されたことです。

1.  **`MetaHeadersFrame` 構造体の導入**:
    *   新しい型 `http2MetaHeadersFrame` が導入されました。これは、1つの `HEADERS` フレームとそれに続く0個以上の `CONTINUATION` フレームを結合し、HPACK デコードされた内容を表現するためのものです。
    *   このフレームはワイヤー上には存在せず、`Framer.ReadMetaHeaders` が設定されている場合にのみ `Framer` によって返されます。
    *   `Fields` フィールドには、HPACK デコードされた `hpack.HeaderField` のスライスが含まれます。これは、正しい HTTP/2 の順序で、不正な疑似ヘッダーフィールドや無効なヘッダーフィールド名/値がないことが保証されます。
    *   `Truncated` フィールドは、`MAX_HEADER_LIST_SIZE` の制限に達し、`Fields` が不完全である場合に `true` に設定されます。
    *   `PseudoValue`, `RegularFields`, `PseudoFields` といったヘルパーメソッドが追加され、疑似ヘッダーや通常のヘッダーフィールドへのアクセスを容易にしています。

2.  **`http2Framer` の変更**:
    *   `ReadMetaHeaders *hpack.Decoder` フィールドが `http2Framer` に追加されました。これが `nil` でない場合、`ReadFrame` メソッドは `HEADERS` と `CONTINUATION` フレームを結合して `MetaHeadersFrame` を返します。
    *   `MaxHeaderListSize uint32` フィールドも追加され、`ReadMetaHeaders` が設定されている場合に `MAX_HEADER_LIST_SIZE` を指定します。デフォルトは 16MB です。
    *   `ErrorDetail() error` メソッドが追加され、`Framer.ReadFrame` が返したエラーに関するより詳細な情報を提供できるようになりました。これにより、`PROTOCOL_ERROR` のような一般的なエラーコードだけでなく、具体的なエラー原因を特定しやすくなります。
    *   `ReadFrame()` メソッド内で、`HEADERS` フレームが検出され、かつ `fr.ReadMetaHeaders` が設定されている場合に `fr.readMetaFrame()` を呼び出すロジックが追加されました。
    *   `connError` メソッドで `errReason` が `errDetail` に変更され、より具体的なエラーオブジェクトを保持するようになりました。

3.  **ヘッダー処理ロジックの移動と簡素化**:
    *   `http2serverConn` および `http2clientConnReadLoop` から、`HEADERS` および `CONTINUATION` フレームを個別に処理し、HPACK デコードを行うロジックが削除されました。
    *   `http2serverConn.processHeaders` メソッドは、`*http2HeadersFrame` ではなく `*http2MetaHeadersFrame` を引数として受け取るように変更されました。これにより、上位層では既に結合されデコードされたヘッダーブロックを扱うことができます。
    *   `http2serverConn.processContinuation` メソッドは削除されました。
    *   `http2serverConn.onNewHeaderField` や `http2stream.onNewTrailerField` といった HPACK デコード時のコールバック関数も削除され、ヘッダーフィールドの検証と処理が `readMetaFrame` 内に集約されました。
    *   `http2requestParam` 構造体も削除され、リクエストヘッダーの処理状態を保持する必要がなくなりました。
    *   `http2clientConnReadLoop.processHeaders` も `*http2MetaHeadersFrame` を受け取るようになり、`processContinuation` メソッドは削除されました。

4.  **HPACK パッケージの変更**:
    *   `src/vendor/golang.org/x/net/http2/hpack/hpack.go` に `HeaderField.IsPseudo()` メソッドが追加されました。これはヘッダーフィールドが疑似ヘッダー（`: `で始まる）であるかを判定します。
    *   `HeaderField.size()` メソッドが `HeaderField.Size()` にリネームされ、RFC 7540 セクション 5.2 に基づくエントリサイズを返すことが明確化されました。

5.  **ガベージ削減と効率化**:
    *   `http2sorterPool` という `sync.Pool` が導入され、ヘッダーキーのソートに使用される `http2sorter` オブジェクトを再利用することで、ガベージコレクションの負荷を軽減しています。これは `http2encodeHeaders` や `http2responseWriterState.promoteUndeclaredTrailers` で使用されています。
    *   `http2serverConn` に `freeRequestBodyBuf []byte` フィールドが追加され、リクエストボディのバッファを再利用することで、メモリ割り当てを減らしています。

6.  **エラーハンドリングの改善**:
    *   `http2pseudoHeaderError`, `http2duplicatePseudoHeaderError`, `http2headerFieldNameError`, `http2headerFieldValueError` といった新しいエラー型が導入され、ヘッダーの検証に関するより具体的なエラー情報を提供できるようになりました。
    *   `http2errMixPseudoHeaderTypes` や `http2errPseudoAfterRegular` といったエラー変数も追加され、不正な疑似ヘッダーの組み合わせや順序を検出します。

これらの変更により、HTTP/2 のヘッダー処理は `Framer` レベルでより堅牢かつ効率的に行われるようになり、上位の `net/http` コードはよりクリーンで簡潔になりました。

## コアとなるコードの解説

### `http2Framer` の変更と `readMetaFrame`

この変更の核心は、`http2Framer` が `HEADERS` フレームと `CONTINUATION` フレームを透過的に結合し、完全なヘッダーブロックとして上位に提供するようになった点です。

*   **`ReadMetaHeaders *hpack.Decoder`**: `Framer` に HPACK デコーダーを直接持たせることで、フレームの読み取りと同時にヘッダーのデコードも行えるようになりました。これにより、上位層は生のヘッダーブロック断片ではなく、既にデコードされた `hpack.HeaderField` のスライスを受け取ることができます。
*   **`readMetaFrame` 関数**: この新しい関数は、`HEADERS` フレームを受け取ると、それに続く `CONTINUATION` フレームを `Framer` から読み取り続けます。読み取った断片は内部の HPACK デコーダーに書き込まれ、完全なヘッダーブロックが再構築されます。このプロセス中に、疑似ヘッダーの検証、重複チェック、ヘッダーフィールド名/値の妥当性チェック、`MAX_HEADER_LIST_SIZE` の制限チェックなどが行われます。エラーが発生した場合、`Framer.errDetail` に詳細なエラーが設定されます。
*   **`MetaHeadersFrame`**: `readMetaFrame` が返すこの構造体は、結合されたヘッダーブロックの完全な表現です。これにより、上位層はヘッダーの断片化を意識することなく、一貫した方法でヘッダー情報にアクセスできます。

### `http2serverConn` と `http2clientConnReadLoop` の簡素化

`Framer` がヘッダー結合とデコードの責任を負うようになったため、`http2serverConn` (サーバー側の接続ハンドラ) と `http2clientConnReadLoop` (クライアント側の読み取りループ) のコードは大幅に簡素化されました。

*   **ヘッダー処理ロジックの削除**: 以前はこれらのコンポーネントが `hpack.Decoder` を持ち、`HEADERS` と `CONTINUATION` フレームを個別に処理し、`onNewHeaderField` などのコールバックを通じてヘッダーフィールドを組み立てていました。これらのロジックはすべて `Framer` の `readMetaFrame` に移動されたため、上位層からは削除されました。
*   **`*http2MetaHeadersFrame` の利用**: `processHeaders` メソッドが `*http2MetaHeadersFrame` を直接受け取るようになったことで、ヘッダーの再構築やデコードに関する複雑な状態管理が不要になりました。これにより、コードの可読性と保守性が向上しています。
*   **`newWriterAndRequest` の変更**: この関数も `http2MetaHeadersFrame` を引数として受け取るようになり、リクエストオブジェクトの構築がより直接的になりました。

### HPACK パッケージの変更

*   **`HeaderField.IsPseudo()`**: 疑似ヘッダーの判定ロジックが `hpack.HeaderField` 自体にカプセル化されました。これは、ヘッダーフィールドのプロパティをよりオブジェクト指向的に扱うための改善です。
*   **`HeaderField.Size()`**: HPACK の動的テーブルサイズ計算において、ヘッダーフィールドのサイズを正確に計算するためのメソッドです。リネームにより、その目的が明確になりました。

### ガベージ削減

`http2sorterPool` の導入は、Go の `sync.Pool` を利用した典型的なガベージ削減の例です。ヘッダーキーのソートは頻繁に行われる操作であり、そのたびに新しいスライスやソーターオブジェクトを割り当てると GC 負荷が高まります。`sync.Pool` を使うことで、これらのオブジェクトを再利用し、メモリ割り当てを減らすことができます。

全体として、このコミットは HTTP/2 スタックの低レベル部分における責任の分離とカプセル化を強化し、より堅牢で効率的なヘッダー処理を実現しています。

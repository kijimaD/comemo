# [インデックス 24572] ファイルの概要

## コミット

このコミットは、Go言語の `net/url` パッケージにおいて、`URL`構造体の`RawPath`フィールドが許容する文字の範囲を拡張するものです。具体的には、パスエンコーディングにおいて通常エスケープされる可能性のある一部の文字（サブデリミタの一部）と、ブラウザの挙動に合わせて角括弧 `[` と `]` を`RawPath`内で許可するように変更されています。これにより、`RawPath`の目的である「ユーザーがエスケープの挙動を上書きする」という意図がより明確に、かつ柔軟に実現されるようになります。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/fced03a5c6dd22dd486106e3dd116510c28c6e4a](https://github.com/golang/go/commit/fced03a5c6dd22dd486106e3dd116510c28c6e4a)

## 元コミット内容

```
net/url: allow all valid host chars in RawPath

The old code was only allowing the chars we choose not to escape.
We sometimes prefer to escape chars that do not strictly need it.
Allowing those to be used in RawPath lets people override that
preference, which is in fact the whole point of RawPath (new in Go 1.5).

While we are here, also allow [ ] in RawPath.
This is not strictly spec-compliant, but it is what modern browers
do and what at least some people expect, and the [ ] do not cause
any ambiguity (the usual reason they would be escaped, as they are
part of the RFC gen-delims class).
The argument for allowing them now instead of waiting until Go 1.6
is that this way RawPath has one fixed meaning at the time it is
introduced, that we should not need to change or expand.

Fixes #5684.

Change-Id: If9c82a18f522d7ee1d10310a22821ada9286ee5c
Reviewed-on: https://go-review.googlesource.com/13258
Reviewed-by: Andrew Gerrand <adg@golang.org>
```

## 変更の背景

この変更の背景には、Go 1.5で導入された`URL`構造体の`RawPath`フィールドの意図を完全に実現するという目的があります。`RawPath`は、URLのパス部分がパーセントエンコードされる前の生の形式を保持するためのフィールドです。Goの`net/url`パッケージは、URLエンコーディングにおいて、RFCの要件を厳密に満たしつつも、一部の文字については「エスケープしなくても問題ないが、慣習的にエスケープする」という選択をしていました。しかし、`RawPath`の導入により、ユーザーはGoのデフォルトのエスケープ挙動を上書きし、より多くの文字をエスケープせずにパスに含めたいというニーズが出てきました。

特に、Issue #5684では、`[` と `]` の文字が`RawPath`で正しく扱われないという問題が報告されていました。これらの文字はRFC 3986のジェネラルデリミタ（`gen-delims`）の一部であり、通常はエスケープされるべきですが、現代のブラウザはこれらをエスケープせずにパスに含めることが多く、また、これらがパスの構造に曖昧さをもたらすこともありません。

このコミットは、`RawPath`が導入されたGo 1.5の時点で、その挙動を「固定された意味」として確立し、将来的に変更や拡張の必要がないようにするという意図も持っています。これにより、`RawPath`の利用者は、Goのバージョンアップによって挙動が変わることを心配せずに、より柔軟なパス表現が可能になります。

## 前提知識の解説

*   **URLエンコーディングとパーセントエンコーディング**: URLは、特定の文字（予約文字）が特別な意味を持つため、これらの文字をデータとして含める場合には、パーセントエンコーディング（`%HH`形式）を用いてエスケープする必要があります。これにより、URLの構造が壊れたり、意図しない解釈がされたりするのを防ぎます。
*   **RFC 3986**: Uniform Resource Identifier (URI): Generic Syntaxを定義する標準仕様です。URLの構文、予約文字、非予約文字、パーセントエンコーディングのルールなどが詳細に規定されています。
    *   **`pchar` (Path Character)**: RFC 3986で定義されるパスセグメントを構成する文字の集合です。これには、`unreserved`（英数字、`-`, `.` `_`, `~`）、`pct-encoded`（パーセントエンコードされた文字）、`sub-delims`（`!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`）、`:`、`@`が含まれます。
    *   **`gen-delims` (General Delimiters)**: `pchar`とは別に、URIの構文を区切るために使用される文字の集合です。これには `[`, `]`, `/`, `?`, `#` などが含まれます。これらの文字は通常、パス内で特別な意味を持つため、データとして含める場合はエスケープが必要です。
*   **Go `net/url`パッケージ**: Go言語でURLの解析、構築、エンコーディング/デコーディングを行うための標準ライブラリです。
    *   **`URL`構造体**: URLの各構成要素（スキーム、ホスト、パスなど）を保持する構造体です。
    *   **`Path`フィールド**: URLのパス部分をパーセントデコードした文字列を保持します。
    *   **`RawPath`フィールド**: URLのパス部分をパーセントエンコードされた生の文字列として保持します。Go 1.5で導入されました。このフィールドは、`Path`フィールドとは異なり、ユーザーが意図的にエスケープされていない文字を含めることを許可し、Goのデフォルトのエスケープルールを上書きする目的で使われます。
    *   **`shouldEscape`関数**: `net/url`パッケージ内部で、特定の文字がURLエンコーディングの際にエスケープされるべきかどうかを判断するために使用される関数です。

## 技術的詳細

このコミットの主要な変更は、`src/net/url/url.go`内の`validEncodedPath`関数のロジックにあります。この関数は、`RawPath`フィールドに設定される文字列が有効なエンコード済みパスであるかどうかを検証します。

変更前は、`validEncodedPath`関数は、`%`文字でない限り、`shouldEscape(s[i], encodePath)`が`true`を返す文字を無効としていました。これは、Goがデフォルトでエスケープすることを選択した文字は`RawPath`に含めるべきではない、という考え方に基づいています。しかし、これは`RawPath`の本来の目的（Goのデフォルトのエスケープ挙動を上書きする）と矛盾していました。GoはRFCに厳密に従いつつも、一部の`sub-delims`（例: `!`, `$`, `&`など）をエスケープしないことを選択していましたが、`shouldEscape`関数はこれらの文字に対して`true`を返すことがありました。

変更後では、`validEncodedPath`関数は、RFC 3986の`pchar`の定義により近づけるように修正されました。具体的には、以下の文字を明示的に許可する`switch`文が追加されました。

1.  **サブデリミタの一部**: `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`, `:`, `@`。これらの文字はRFC 3986の`pchar`に含まれるため、エスケープなしでパスに含めることができます。
2.  **角括弧 `[` と `]`**: これらはRFC 3986の`gen-delims`の一部であり、厳密にはエスケープされるべきですが、現代のブラウザの挙動に合わせて、`RawPath`内ではエスケープなしで許可されるようになりました。コミットメッセージにもあるように、これらがパスの曖昧さを引き起こすことはないため、利便性を優先した判断です。
3.  **`%`文字**: これはパーセントエンコードされた文字の開始を示すため、常に許可されます。

これらの文字が明示的に許可された後、残りの文字については引き続き`shouldEscape(s[i], encodePath)`でチェックされます。これにより、`RawPath`は、Goがデフォルトでエスケープする「必要のない」文字であっても、ユーザーが意図的にエスケープせずに含めることができるようになり、`RawPath`の柔軟性が向上しました。

テストファイル`src/net/url/url_test.go`には、この変更を検証するための新しいテストケースが追加されています。特に、`http://host/!$&'()*+,;=:@[hello]`のような、多くのサブデリミタと角括弧を含むパスが`RawPath`で正しくラウンドトリップできることを確認するテストや、Issue #5684で報告された`http://example.com/oid/[order_id]`のようなパスが正しく扱われることを確認するテストが追加されました。

## コアとなるコードの解説

`validEncodedPath`関数は、`RawPath`に設定される文字列の各バイトをループで検査します。

変更前は、`s[i] != '%' && shouldEscape(s[i], encodePath)`という条件で、パーセント文字でなく、かつエスケープされるべき文字であれば`false`を返していました。これは、Goが内部的にエスケープすると判断した文字は`RawPath`に含めるべきではない、という保守的なアプローチでした。

変更後では、この条件がより詳細な`switch`文に置き換えられました。

1.  **`case '!', '$', '&', '\'', '(', ')', '*', '+', ',', ';', '=', ':', '@':`**:
    これらの文字はRFC 3986の`pchar`に含まれる「サブデリミタ」の一部です。Goの`shouldEscape`関数は、これらの文字の一部に対して`true`を返すことがありましたが、RFC上はエスケープ不要です。この`case`により、これらの文字は`RawPath`内で明示的に許可されるようになりました。
2.  **`case '[', ']':`**:
    角括弧はRFC 3986の`gen-delims`の一部であり、厳密にはエスケープが必要です。しかし、現代のブラウザの挙動や、パスの曖昧さを引き起こさないという実用的な観点から、`RawPath`内では許可されることになりました。これは、`RawPath`が「ユーザーの意図を尊重する」という目的を果たすための重要な変更です。
3.  **`case '%':`**:
    パーセント文字はパーセントエンコーディングの開始を示すため、常に有効です。これは変更前も考慮されていましたが、`switch`文の中に明示的に含まれることで、コードの意図がより明確になりました。
4.  **`default:`**:
    上記の`case`でカバーされない文字については、引き続き`shouldEscape(s[i], encodePath)`が呼び出されます。ここで`true`が返された場合（つまり、エスケープが必要な文字である場合）、その文字は`RawPath`には含められないと判断され、`validEncodedPath`関数は`false`を返します。これにより、`RawPath`は柔軟性を持ちつつも、基本的なURLの健全性は保たれます。

この変更により、`RawPath`は、Goのデフォルトのエスケープポリシーに縛られず、より広範な有効なパス文字を直接表現できるようになり、ユーザーがURLのパスをより細かく制御できるようになりました。

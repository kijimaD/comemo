# [インデックス 23681] ファイルの概要

このコミットは、Go言語のドキュメンテーション生成ツール `cmd/doc` における問題を修正するものです。具体的には、`go/doc` パッケージが `const` および `var` ブロックから非エクスポート（unexported）な定数や変数を自動的に除外しないため、生成されるドキュメントにこれらが含まれてしまうという問題に対処しています。このコミットでは、`cmd/doc` 自身がこれらの非エクスポートされたエントリを明示的にフィルタリングするロジックを追加し、公開APIのドキュメントの正確性と簡潔性を向上させています。

## 元コミット内容

`cmd/doc` ツールが非エクスポートな定数を表示しないようにする変更です。
`go/doc` パッケージは `const` および `var` ブロックから非エクスポートなエントリを削除しないため、`cmd/doc` 側でそれらを自身でトリミング（除去）する必要がありました。
この変更は Issue #11008 を修正します。

## 変更の背景

Go言語では、パッケージの外部に公開される（エクスポートされる）識別子と、パッケージ内部でのみ使用される（非エクスポートされる）識別子を明確に区別します。これは、識別子の最初の文字が大文字か小文字かによって決まります。ドキュメンテーションは通常、パッケージの公開APIを説明するために生成されるため、非エクスポートされた内部的な定数や変数がドキュメントに含まれることは望ましくありません。これらはユーザーにとってノイズとなり、APIの理解を妨げる可能性があります。

このコミット以前の `cmd/doc` ツールは、`go/doc` パッケージを利用してGoのソースコードからドキュメンテーション情報を抽出していました。しかし、`go/doc` パッケージの当時の実装では、`const` や `var` の宣言ブロック全体を処理する際に、そのブロック内に非エクスポートされた識別子が含まれていても、それらを自動的にフィルタリングして除去する機能がありませんでした。その結果、`cmd/doc` が生成するドキュメントには、本来公開されるべきではない内部的な定数や変数が表示されてしまうという問題が発生していました（Issue #11008 で報告された問題）。

このコミットは、この問題を解決するために、`cmd/doc` ツール自体に、`go/doc` パッケージから受け取った宣言情報に対して追加のフィルタリングロジックを実装し、非エクスポートされた定数や変数をドキュメントから除外するように変更しました。これにより、生成されるドキュメントがよりクリーンで、公開APIに焦点を当てたものになります。

## 前提知識の解説

### Go言語におけるエクスポートされた識別子と非エクスポートされた識別子

Go言語では、識別子（変数名、関数名、型名など）の可視性（スコープ）は、その名前の最初の文字が大文字か小文字かによって決まります。

*   **エクスポートされた識別子 (Exported Identifiers)**: 最初の文字が大文字で始まる識別子（例: `MyVariable`, `MyFunction`, `MyType`）は、その識別子が宣言されたパッケージの外部からアクセス可能です。これらはパッケージの公開APIの一部と見なされます。
*   **非エクスポートされた識別子 (Unexported Identifiers)**: 最初の文字が小文字で始まる識別子（例: `myVariable`, `myFunction`, `myType`）は、その識別子が宣言されたパッケージの内部からのみアクセス可能です。これらはパッケージの実装詳細であり、外部からは隠蔽されます。

ドキュメンテーションは通常、パッケージの公開APIを説明するために提供されるため、非エクスポートされた識別子がドキュメントに表示されることは、ユーザーにとって混乱を招く可能性があります。

### `go/doc` パッケージ

`go/doc` パッケージは、Goのソースコードからドキュメンテーションコメントや宣言情報を抽出し、構造化された形式で提供するための標準ライブラリです。`go doc` コマンドや `godoc` ツールは、このパッケージを利用してGoのパッケージやシンボルのドキュメントを生成・表示します。このパッケージは、Goのソースコードを解析し、パッケージ、関数、型、変数、定数などの情報を取得する機能を提供します。

### `go/ast` パッケージ (Abstract Syntax Tree)

`go/ast` パッケージは、Goのソースコードを抽象構文木（AST: Abstract Syntax Tree）として表現するためのデータ構造と関数を提供します。Goコンパイラや様々なコード分析ツール（リンター、フォーマッター、ドキュメンテーションツールなど）は、ソースコードをASTに変換し、その構造を走査・分析することで、コードの意味を理解したり、変換したりします。

このコミットに関連する主なASTノードは以下の通りです。

*   **`ast.GenDecl`**: `const`, `var`, `type` などの一般的な宣言を表します。例えば、`const ( A = 1; B = 2 )` のようなブロック宣言全体がこれに該当します。
*   **`ast.ValueSpec`**: `const` や `var` 宣言内の個々の変数や定数の仕様を表します。例えば、`A = 1` や `B = 2` の部分がこれに該当します。`ValueSpec` には、宣言される識別子のリスト（`Names` フィールド）が含まれます。

## 技術的詳細

このコミットの技術的な核心は、`cmd/doc` ツールが `go/doc` パッケージから取得した `const` および `var` の宣言情報に対して、追加のフィルタリング処理を適用することです。

`go/doc` パッケージは、`ast` パッケージを使用してソースコードを解析し、`doc.Package` 構造体としてドキュメンテーション情報を構築します。この `doc.Package` 構造体には、`Consts` (定数宣言のリスト) や `Vars` (変数宣言のリスト) といったフィールドが含まれます。これらのリストの各要素は `doc.Value` 型であり、その中に `Decl` (元の `ast.GenDecl` を指す) が含まれています。

問題は、`doc.Value.Decl` が指す `ast.GenDecl` の `Specs` フィールド（`ast.Spec` のスライス）が、エクスポートされた識別子と非エクスポートされた識別子の両方を含んだままであることでした。`go/doc` パッケージは、この段階で非エクスポートされた識別子を自動的に除去するロジックを持っていなかったため、`cmd/doc` はその情報をそのまま受け取ってしまい、結果としてドキュメントに表示していました。

このコミットでは、`src/cmd/doc/pkg.go` ファイル内の `(*Package) symbolDoc` メソッドに修正が加えられました。このメソッドは、特定のシンボルに関連するドキュメントを生成する役割を担っています。修正は、`const` や `var` の `doc.Value` を処理する際に、その `Decl` 内の `Specs` を走査し、各 `ast.ValueSpec` に含まれる識別子がエクスポートされているかどうかをチェックするものです。

具体的には、`ast.ValueSpec` 内の `Names` フィールド（`*ast.Ident` のスライス）をループし、`isExported` ヘルパー関数（Goの標準ライブラリに存在する関数で、識別子名がエクスポートされているか否かを判定する）を使用して、識別子の可視性を判定します。もし `ValueSpec` 内に一つでもエクスポートされた識別子があれば、その `ValueSpec` 全体を保持し、新しい `Specs` リストに追加します。最終的に、フィルタリングされた `Specs` リストで元の `doc.Value.Decl.Specs` を上書きすることで、非エクスポートされた定数や変数がドキュメント生成の対象から除外されるようにします。

このアプローチにより、`go/doc` パッケージ自体の変更を待つことなく、`cmd/doc` ツール側で即座に問題を解決することができました。コミットメッセージのコメント `// TODO: Would be nice if go/doc did this for us.` は、将来的には `go/doc` パッケージがこのフィルタリングを内部的に行うことが理想的であるという開発者の意図を示唆しています。

## コアとなるコードの変更箇所

変更は `src/cmd/doc/pkg.go` ファイルにあります。
具体的には、`func (pkg *Package) symbolDoc(symbol string)` メソッド内の `for _, value := range values` ループの中に、以下のコードブロックが追加されました。

--- a/src/cmd/doc/pkg.go
+++ b/src/cmd/doc/pkg.go
@@ -332,6 +332,25 @@ func (pkg *Package) symbolDoc(symbol string) {
 	values := pkg.findValues(symbol, pkg.doc.Consts)
 	values = append(values, pkg.findValues(symbol, pkg.doc.Vars)...)
 	for _, value := range values {
+		// Print each spec only if there is at least one exported symbol in it.
+		// (See issue 11008.)
+		// TODO: Should we elide unexported symbols from a single spec?
+		// It's an unlikely scenario, probably not worth the trouble.
+		// TODO: Would be nice if go/doc did this for us.
+		specs := make([]ast.Spec, 0, len(value.Decl.Specs))
+		for _, spec := range value.Decl.Specs {
+			vspec := spec.(*ast.ValueSpec)
+			for _, ident := range vspec.Names {
+				if isExported(ident.Name) {
+					specs = append(specs, vspec)
+					break
+				}
+			}
+		}
+		if len(specs) == 0 {
+			continue

## コアとなるコードの解説

追加されたコードブロックは、`const` または `var` の宣言ブロック（`value.Decl`）に含まれる個々の仕様（`ast.ValueSpec`）をフィルタリングする役割を担っています。

1.  `specs := make([]ast.Spec, 0, len(value.Decl.Specs))`
    *   これは、フィルタリング後の `ast.Spec` を格納するための新しいスライス `specs` を初期化しています。容量は元の `value.Decl.Specs` と同じにして、効率的なメモリ割り当てを意図しています。

2.  `for _, spec := range value.Decl.Specs { ... }`
    *   元の宣言ブロック `value.Decl` に含まれるすべての `ast.Spec` (個々の定数や変数の宣言) をループ処理します。

3.  `vspec := spec.(*ast.ValueSpec)`
    *   `ast.Spec` はインターフェース型なので、具体的な `ast.ValueSpec` 型に型アサート（型変換）しています。`const` や `var` 宣言の場合、`spec` は常に `*ast.ValueSpec` であると想定されます。

4.  `for _, ident := range vspec.Names { ... }`
    *   一つの `ast.ValueSpec` は複数の識別子（例: `const A, B, C = 1, 2, 3` の `A`, `B`, `C`）を宣言することができます。この内側のループは、その `ValueSpec` 内の各識別子を走査します。

5.  `if isExported(ident.Name) { ... }`
    *   `isExported` 関数は、Go言語の識別子名がエクスポートされている（つまり、最初の文字が大文字である）かどうかを判定するヘルパー関数です。ここで、現在の識別子 `ident.Name` がエクスポートされているかどうかがチェックされます。

6.  `specs = append(specs, vspec)`
    *   もし `vspec` 内に**一つでも**エクスポートされた識別子が見つかった場合、その `vspec` (つまり、その定数または変数の宣言全体) はドキュメントに含めるべきと判断され、新しく作成した `specs` スライスに追加されます。

7.  `break`
    *   `vspec` 内にエクスポートされた識別子が一つでも見つかれば、その `vspec` は保持されることが決定されるため、これ以上その `vspec` 内の他の識別子をチェックする必要はありません。したがって、内側のループを `break` で抜けます。

8.  `if len(specs) == 0 { continue }`
    *   外側のループが終了した後、もし `specs` スライスが空であれば、それは元の `value.Decl.Specs` 内のすべての `ast.ValueSpec` が非エクスポートされた識別子のみを含んでいたことを意味します。この場合、その宣言ブロック全体をドキュメントから除外するため、`continue` で次の `value` (次の宣言ブロック) の処理に移ります。

9.  `value.Decl.Specs = specs`
    *   フィルタリングの結果、エクスポートされた識別子を含む `ast.ValueSpec` のみが残った `specs` スライスで、元の `value.Decl.Specs` を上書きします。これにより、後続のドキュメント生成処理では、非エクスポートされた定数や変数が含まれない、クリーンな宣言情報が使用されることになります。

この変更により、`cmd/doc` は `go/doc` パッケージの出力に対して後処理を行い、Go言語の可視性ルールに則った適切なドキュメンテーションを生成できるようになりました。

コメント `// TODO: Should we elide unexported symbols from a single spec?` は、例えば `const ( Exported = 1; unexported = 2 )` のような宣言があった場合に、`unexported` だけを削除すべきか、それとも `Exported` があるので宣言全体を残すべきかという、より細かい粒度でのフィルタリングの可能性について言及しています。このコミットでは、少なくとも一つエクスポートされたシンボルがあれば `ValueSpec` 全体を残すという方針が取られています。
また、`// TODO: Would be nice if go/doc did this for us.` は、このフィルタリングロジックが `go/doc` パッケージ自体に組み込まれることが理想的であるという開発者の見解を示しています。

# [インデックス 2289] ファイルの概要

このコミットは、Go言語のランタイムにおける`libmach_amd64`ライブラリに、Plan 9由来の`.5`ファイル（ARMアーキテクチャのオブジェクトファイル）のサポートを追加するものです。具体的には、Plan 9の`libmach`から`5obj.c`というソースファイルをコピーし、それを`libmach_amd64`に組み込むことで、GoツールチェインがARMオブジェクトファイルを解析できるようになります。

## 変更の背景

このコミットが行われた2009年という時期は、Go言語がまだ初期段階にあり、そのツールチェインやランタイムが様々なアーキテクチャやオペレーティングシステムへの対応を模索していた時期に当たります。Go言語の設計思想には、Rob PikeやKen ThompsonといったPlan 9の開発者が深く関わっており、その影響はGoの多くの部分に見られます。

`libmach`は、Plan 9オペレーティングシステムにおいて、オブジェクトファイルや実行ファイルを解析するためのライブラリです。Go言語のツールチェイン、特にデバッガやプロファイラのようなツールが異なるアーキテクチャのバイナリを理解するためには、そのアーキテクチャ固有のオブジェクトファイルフォーマットを解析する機能が必要でした。

`.5`ファイルは、Plan 9におけるARMアーキテクチャのオブジェクトファイルを示す慣例的な拡張子です。このコミットは、Goが将来的にARMアーキテクチャをサポートする上で、そのオブジェクトファイルを正しく読み込み、処理するための基盤を構築する一環として行われました。既存の成熟したコードベースであるPlan 9の`libmach`から関連するコードをコピーすることで、開発コストを抑えつつ、必要な機能を取り込むことが目的でした。

## 前提知識の解説

### Plan 9オペレーティングシステム

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、すべてのリソースをファイルとして表現し、ネットワーク透過性を重視しています。Go言語の多くの設計概念（例: UTF-8の採用、インターフェース、goroutineとチャネルの並行性モデルなど）は、Plan 9の影響を強く受けています。

### オブジェクトファイル

オブジェクトファイルは、コンパイラによって生成される中間ファイルで、ソースコードを機械語に変換したものです。これには、コンパイルされたコード（テキストセクション）、初期化されたデータ（データセクション）、初期化されていないデータ（BSSセクション）、シンボルテーブル（関数名や変数名とそのアドレス）、再配置情報などが含まれます。リンカはこれらのオブジェクトファイルを結合して実行可能ファイルを生成します。

### `libmach`

`libmach`は、Plan 9におけるデバッグやバイナリ解析のためのライブラリ群です。異なるCPUアーキテクチャ（例: x86、ARM、MIPSなど）のオブジェクトファイルや実行ファイルの内部構造を読み取り、シンボル情報やコード、データセクションにアクセスするための機能を提供します。各アーキテクチャに対応するファイル（例: `5obj.c`はARM、`6obj.c`はAMD64、`8obj.c`はx86）が存在し、それぞれのオブジェクトファイルフォーマットの解析ロジックを含んでいます。

### `.5`ファイル

Plan 9の慣例では、コンパイラやアセンブラの出力ファイルに、ターゲットアーキテクチャを示す数字を拡張子として付与することがあります。`.5`はARMアーキテクチャ（Plan 9では`arm`または`5`と表記されることが多い）のオブジェクトファイルを示します。同様に、`.6`はAMD64、`.8`はx86を指します。

### `libmach_amd64`

Go言語の初期のツールチェインは、Plan 9のツールチェインをベースにしていました。`libmach_amd64`は、Goのツールチェイン内でAMD64アーキテクチャのバイナリを解析するために使用されるライブラリです。このライブラリは、デバッガやプロファイラ、あるいはその他のバイナリ解析ツールが、Goプログラムの内部構造を理解するために必要となります。このコミットでは、この`libmach_amd64`にARMオブジェクトファイルの解析機能を追加しています。

## 技術的詳細

このコミットの主要な変更点は、`src/libmach_amd64/5obj.c`の追加と、既存の`Makefile`および`fakeobj.c`の修正です。

### `src/libmach_amd64/5obj.c`の追加

このファイルは、Plan 9の`libmach`から直接コピーされたもので、ARMアーキテクチャのオブジェクトファイル（`.5`ファイル）を解析するためのC言語のコードが含まれています。

主な機能は以下の通りです。

-   **`_is5(char *s)`**:
    この関数は、与えられたバイト列がARMオブジェクトファイルのヘッダ（マジックナンバー）に一致するかどうかを判定します。Plan 9のオブジェクトファイルは、特定のバイトシーケンスで始まることでファイルの種類を識別します。この関数は、ファイルが`ANAME`、`D_FILE`、`1`、`'<'`という特定のバイトパターンで始まるかどうかをチェックしています。これは、Plan 9のオブジェクトファイルフォーマットにおけるファイル名シンボルの開始を示すものです。

-   **`_read5(Biobuf *bp, Prog *p)`**:
    この関数は、`Biobuf`（Plan 9のI/Oライブラリにおけるバッファ付きI/O構造体）からARMオブジェクトファイルの内容を読み込み、`Prog`構造体（Goのツールチェイン内で命令やシンボルを表す汎用的な構造体）に解析結果を格納します。
    -   オブジェクトファイル内の各命令やシンボルを順次読み込みます。
    -   `ATEXT`（コードセクション）、`AGLOBL`（グローバルデータセクション）、`ANAME`（シンボル名）などのセクションタイプを識別します。
    -   シンボル名、型、アドレスオフセットなどを抽出し、`Prog`構造体の対応するフィールドに設定します。
    -   特に、`ANAME`や`ASIGNAME`といったシンボル定義を処理し、シンボル名（`p->id`）を動的に割り当てて格納します。
    -   `Addr`構造体を用いて、命令のアドレス指定モードやシンボル参照を解析します。

-   **`addr(Biobuf *bp)`**:
    この静的関数は、オブジェクトファイル内のアドレス指定モードを解析します。レジスタ、定数、メモリ参照（オフセット付き）、分岐ターゲット、浮動小数点定数、文字列定数など、様々な種類のアドレス指定を処理し、それらのオフセットやシンボル情報を抽出します。

-   **`type2char(int t)`**:
    この静的関数は、Plan 9のシンボル型（`D_EXTERN`, `D_STATIC`, `D_AUTO`, `D_PARAM`など）を、Goのツールチェイン内で使用される文字表現（例: `U`、`b`、`a`、`p`）に変換します。

-   **`skip(Biobuf *bp, int n)`**:
    指定されたバイト数だけ`Biobuf`の読み取り位置をスキップするヘルパー関数です。

### `src/libmach_amd64/Makefile`の変更

`Makefile`には、新しく追加された`5obj.c`をコンパイルし、`libmach_amd64`ライブラリにリンクするための変更が加えられています。
-   `OFILES`変数に`5obj.$O`（コンパイルされた`5obj.c`のオブジェクトファイル）が追加されています。これにより、ビルドシステムが`5obj.c`をコンパイル対象として認識し、最終的なライブラリに含めるようになります。
-   コメントアウトされていた`# 5obj.$O\`の行が削除されています。これは、以前はサポートされていなかったか、開発中であった機能が、このコミットで正式に有効化されたことを示唆しています。

### `src/libmach_amd64/fakeobj.c`の変更

`fakeobj.c`は、様々なアーキテクチャのオブジェクトファイル識別関数（`_isX`）と読み込み関数（`_readX`）のスタブ（ダミー実装）を提供していました。このコミットでは、`5obj.c`が正式に追加されたため、`_is5`と`_read5`のダミー実装が削除されました。
-   `int _is5(char* x) { return 0; }` の行が削除されました。
-   `int _read5(Biobuf* b, Prog* p) { return 0; }` の行が削除されました。
これにより、実際の`5obj.c`で定義された関数が使用されるようになります。

## コアとなるコードの解説

このコミットの核心は、`5obj.c`が`libmach_amd64`に追加されたことです。これにより、GoのツールチェインがAMD64環境で動作している場合でも、ARMアーキテクチャのオブジェクトファイル（`.5`ファイル）を解析する能力を獲得します。

-   **`5obj.c`の役割**:
    -   `_is5`関数は、ファイルがARMオブジェクトファイルであるかを迅速に識別するための「マジックナンバー」チェックを提供します。これは、ファイルの内容を深く解析する前に、その種類を判別するために重要です。
    -   `_read5`関数は、実際にARMオブジェクトファイルのバイナリデータを読み込み、シンボル、コード、データなどの情報をGoの内部表現（`Prog`構造体）に変換します。この解析ロジックは、Plan 9のオブジェクトファイルフォーマットの深い知識に基づいています。
    -   `addr`、`type2char`、`skip`といったヘルパー関数は、`_read5`がオブジェクトファイル内の複雑な構造を効率的に解析するために利用されます。

-   **`Makefile`の変更の重要性**:
    `Makefile`の変更は、`5obj.c`がGoのビルドプロセスに組み込まれ、`libmach_amd64`の一部としてコンパイル・リンクされることを保証します。これにより、`_is5`や`_read5`といった関数が、Goのデバッガやその他のツールから呼び出せるようになります。

-   **`fakeobj.c`の変更の意義**:
    `fakeobj.c`からのダミー関数の削除は、`5obj.c`が提供する実際の機能が、もはやプレースホルダーではなく、Goツールチェインの正式な一部として認識されたことを意味します。これは、GoがARMアーキテクチャのサポートに向けて一歩前進したことを示しています。

全体として、このコミットはGo言語が初期段階で、Plan 9の既存の堅牢なコードベースを活用し、異なるCPUアーキテクチャへの対応を拡張していく過程を示しています。これにより、Goのツールチェインは、将来的にARMベースのシステムでGoプログラムを開発・デバッグするための基盤を強化しました。

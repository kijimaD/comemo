# [インデックス 2668] ファイルの概要

このコミットは、Go言語の仕様書 `doc/go_spec.html` におけるEBNF（Extended Backus-Naur Form）表記の改善と修正に関するものです。主に、文法定義の表示方法、Unicode文字クラスの定義、および特殊文字を含むトークンの表記方法が変更されています。これにより、仕様書の文法定義がより正確に、かつツールによる解析に適した形式になっています。

## 元コミット内容

このコミットは、Go言語の仕様書 `doc/go_spec.html` に対して以下の変更を加えています。

1.  実際のEBNF定義を囲むHTMLの `<pre>` タグの `class` 属性を `"grammar"` から `"ebnf"` に変更しました。
2.  Unicode文字クラス（`unicode_char`, `unicode_letter` など）に対して、より正式なEBNFプロダクション（生成規則）を導入し、これらがツールによって解析可能になるようにしました。
3.  シングルクォート（`'`）やダブルクォート（`"`）を含むトークンをEBNF内で正しく解析できるように、バッククォート（``` ` `` ```）で囲む表記を使用しました。
4.  `Separator` のEBNF定義に欠けていた終端のピリオド（`.`）を追加しました。

これらの変更により、仕様書のEBNF定義が `ebnflint` というツール（当時開発中）でエラーなく解析できるようになったと述べられています。

## 変更の背景

Go言語の仕様書は、言語の構文をEBNFで記述しています。EBNFは形式言語の文法を定義するためのメタ言語であり、その正確性は言語の厳密な定義にとって不可欠です。このコミットが行われた2009年7月は、Go言語がまだ公開されて間もない、あるいは公開前の初期段階であり、仕様書の整備が活発に行われていた時期です。

この変更の背景には、以下の目的があったと考えられます。

*   **仕様の厳密化と明確化:** EBNF定義をより厳密にし、曖昧さを排除することで、言語仕様の解釈の揺れを防ぎ、コンパイラやツールの実装者が正確に言語を理解できるようにすること。
*   **ツールによる解析の容易化:** `ebnflint` のような文法チェッカーやパーサー生成ツールがEBNF定義を正確に読み込み、検証できるように、形式的な記述規則に準拠させること。特に、特殊文字の扱いやUnicode文字クラスの定義は、ツールの解析に大きな影響を与えます。
*   **ドキュメントの品質向上:** 仕様書自体の品質を向上させ、読者にとって理解しやすい、かつ正確な情報源とすること。HTMLのクラス名変更も、将来的なスタイル適用やセマンティックなマークアップの改善を見据えたものと考えられます。

## 前提知識の解説

### EBNF (Extended Backus-Naur Form)

EBNFは、プログラミング言語などの形式言語の構文を記述するための記法です。BNF（Backus-Naur Form）を拡張したもので、より簡潔で読みやすい表現が可能です。主な記号とその意味は以下の通りです。

*   `=` : 定義（例: `A = B C` は「AはBの後にCが続く」と定義）
*   `|` : 選択（例: `A = B | C` は「AはBまたはC」と定義）
*   `[ ]` : オプション（0回または1回出現）（例: `A = [B] C` は「AはBが0回または1回出現した後にCが続く」と定義）
*   `{ }` : 繰り返し（0回以上出現）（例: `A = B {C}` は「AはBの後にCが0回以上続く」と定義）
*   `( )` : グループ化
*   `" "` または `' '` : 終端記号（リテラル文字列）
*   `/* ... */` : コメント
*   `.` : 定義の終端

Go言語の仕様書では、これらのEBNF記法を用いて、識別子、リテラル、型、ステートメントなどの構文規則が定義されています。

### Unicode文字クラス

Unicodeは、世界中の文字を統一的に扱うための文字コード標準です。Go言語はUnicodeを全面的にサポートしており、識別子や文字列リテラルなどでUnicode文字を使用できます。Unicodeには、各文字に「General Category」というプロパティが割り当てられており、これにより文字の種類（例: 文字、数字、記号、句読点など）を分類できます。

このコミットで言及されている `unicode_char`、`unicode_letter`、`capital_letter`、`unicode_digit` は、Go言語のEBNF定義内で使用される、特定のUnicode文字カテゴリに属する文字の抽象的な表現です。これらを「実プロダクション」として定義することで、EBNFがこれらの抽象概念を形式的に扱えるようになります。

### `ebnflint`

コミットメッセージに登場する `ebnflint` は、EBNF形式で記述された文法定義の構文チェックを行うツールであると推測されます。`lint` という名前が示す通り、コードのスタイルや潜在的なエラーを検出する静的解析ツールの一種です。EBNF定義の形式的な正しさを検証することで、仕様書の品質を保証し、パーサー生成などの下流工程での問題を未然に防ぐ役割を果たします。

## 技術的詳細

このコミットの技術的詳細は、Go言語の仕様書におけるEBNFの表現方法の改善に集約されます。

1.  **HTMLクラス名の変更 (`grammar` -> `ebnf`)**:
    *   以前は `<pre class="grammar">` を使用してEBNFブロックをマークアップしていましたが、これを `<pre class="ebnf">` に変更しました。
    *   これは主にセマンティックな変更であり、HTMLドキュメントの構造をより正確に表現することを目的としています。`ebnf` というクラス名の方が、その内容がEBNF文法であることを直接的に示し、CSSスタイリングやJavaScriptによる処理において、より特化した扱いを可能にします。

2.  **Unicode文字クラスの実プロダクション化**:
    *   以前は `<ul>` リストで説明されていたUnicode文字クラスの定義が、EBNFの正式なプロダクションとして記述されるようになりました。
    *   例:
        ```html
        <!-- 変更前 (リスト形式) -->
        <ul>
        	<li>unicode_char      an arbitrary Unicode code point</li>
        	<li>unicode_letter    a Unicode code point classified as "Letter"</li>
        	<!-- ... -->
        </ul>

        <!-- 変更後 (EBNFプロダクション形式) -->
        <pre class="ebnf">
        unicode_char   = /* an arbitrary Unicode code point */ .
        unicode_letter = /* a Unicode code point classified as "Letter" */ .
        capital_letter = /* a Unicode code point classified as "Letter, uppercase" */ .
        unicode_digit  = /* a Unicode code point classified as "Digit" */ .
        </pre>
        ```
    *   この変更により、`unicode_char` などの概念がEBNF文法の一部として正式に定義され、`ebnflint` のようなツールがこれらの定義を解析し、Go言語の他のEBNF規則との整合性を検証できるようになります。コメント `/* ... */` は、これらの抽象的なプロダクションが具体的に何を意味するのかを人間が理解するための説明です。

3.  **特殊文字を含むトークンのバッククォート表記**:
    *   EBNFでは、リテラル文字列をシングルクォートまたはダブルクォートで囲んで表現します。しかし、リテラル自体がシングルクォートやダブルクォートを含む場合、エスケープが必要になったり、表記が複雑になったりする問題があります。
    *   このコミットでは、Go言語の仕様書で、バックスラッシュ（`\`）に続くエスケープシーケンス（例: `\a`, `\b`, `\'`, `\"` など）を定義する際に、バッククォート（``` ` `` ```）を使用するように変更されました。
    *   例:
        ```diff
        -octal_byte_value = \"\\\" octal_digit octal_digit octal_digit .\n
        -hex_byte_value   = \"\\\" \"x\" hex_digit hex_digit .\n
        -little_u_value   = \"\\\" \"u\" hex_digit hex_digit hex_digit hex_digit .\n
        -big_u_value      = \"\\\" \"U\" hex_digit hex_digit hex_digit hex_digit\n
        -                            hex_digit hex_digit hex_digit hex_digit .\n
        -escaped_char     = \"\\\" ( \"a\" | \"b\" | \"f\" | \"n\" | \"r\" | \"t\" | \"v\" | \"\\\" | \"\'\" | \"\"\" ) .\n
        +octal_byte_value = `\\` octal_digit octal_digit octal_digit .\n
        +hex_byte_value   = `\\` \"x\" hex_digit hex_digit .\n
        +little_u_value   = `\\` \"u\" hex_digit hex_digit hex_digit hex_digit .\n
        +big_u_value      = `\\` \"U\" hex_digit hex_digit hex_digit hex_digit\n
        +                            hex_digit hex_digit hex_digit hex_digit .\n
        +escaped_char     = `\\` ( \"a\" | \"b\" | \"f\" | \"n\" | \"r\" | \"t\" | \"v\" | `\\` | \"\'\" | `\"` ) .\n
        ```
    *   EBNFの文脈でバッククォートを使用することで、内部にシングルクォートやダブルクォートを含むリテラルを明確に区別し、パーサーが正しく解釈できるようにします。これは、特にバックスラッシュ自体をリテラルとして表現する必要がある場合に有効です。

4.  **欠落していたピリオドの追加**:
    *   `Separator` のEBNF定義 `Separator = [ ";" ]` に終端のピリオドが欠けていました。これを `Separator = [ ";" ] .` と修正しました。
    *   EBNFの規則では、各プロダクションの終わりにピリオドを置くのが一般的です。この修正は、EBNFの形式的な規則に厳密に準拠するためのものです。

これらの変更は、Go言語の仕様書が単なる人間が読むためのドキュメントであるだけでなく、言語処理ツールが利用できる形式的な定義としても機能するように、その基盤を強化するものです。

1.  **HTMLクラス名の変更**:

    *   例:
        ```diff
        -<pre class=\"grammar\">\n
        +<pre class=\"ebnf\">\n
        ```

2.  **Unicode文字クラスの定義**:
    *   以前の `<ul>` リストが削除され、代わりに `<pre class="ebnf">` ブロック内にEBNF形式で定義が追加されています。

        +unicode_digit  = /* a Unicode code point classified as \"Digit\" */ .\n

## コアとなるコードの解説

このコミットにおける「コード」とは、Go言語の仕様書 `doc/go_spec.html` 内のEBNF文法定義を指します。

*   **`class="ebnf"` への変更**: これはHTMLのマークアップに関する変更であり、EBNFのブロックをより適切に識別するためのものです。これにより、CSSによるスタイリングの適用や、JavaScriptによるEBNF文法解析ツールの統合などが容易になります。セマンティックな正確性を高めることで、ドキュメントの保守性と拡張性が向上します。

*   **Unicode文字クラスのEBNFプロダクション化**:
    *   以前は単なる説明文だった `unicode_char` などの定義が、`unicode_char = /* ... */ .` のような形式でEBNFの正式な規則として記述されました。
    *   これは、これらの抽象的な概念もGo言語の文法の一部として形式的に扱われるべきであるという設計思想の表れです。これにより、Go言語の字句解析器（lexer）やパーサーが、Unicode文字の分類規則をより厳密に実装するための指針を得ることができます。
    *   `ebnflint` のようなツールは、これらのプロダクションを解析し、Go言語の識別子やリテラルの定義がこれらのUnicode文字クラスを正しく参照しているかを検証できるようになります。

*   **バッククォートによるトークン表記**:
    *   EBNFにおいて、リテラル文字列を表現する際に、そのリテラル自体がクォート文字を含む場合に問題が生じます。例えば、`"\""` はダブルクォート文字自体を意味しますが、EBNFの構文解析器にとっては `"` で囲まれた空文字列の後に `\` が続くように見える可能性があります。
    *   バッククォート（``` ` `` ```）を導入することで、このような曖昧さを解消し、特にバックスラッシュ `\` やクォート文字 `"`、`'` といった特殊文字をリテラルとして表現する際の明確性を高めています。これは、Go言語の文字列リテラルや文字リテラルにおけるエスケープシーケンスの定義において特に重要です。

*   **`Separator` のピリオド追加**:
    *   これはEBNFの形式的な正確性に関する小さな修正ですが、非常に重要です。EBNFの各プロダクションは通常ピリオドで終わるという慣習があり、これに従うことで `ebnflint` のようなツールが文法定義を正しく解析できるようになります。形式的な規則の遵守は、文法定義の整合性を保つ上で不可欠です。

これらの変更は、Go言語の仕様書が単なる説明書ではなく、言語の形式的な定義として機能するための基盤を強化するものであり、言語の安定性とツールの開発を支える重要なステップでした。

# [インデックス 2731] ファイルの概要

このコミットは、Go言語の標準ライブラリである`gob`パッケージにおける重要な改善を導入しています。`gob`パッケージは、Goのデータ構造をバイナリ形式でシリアライズおよびデシリアライズするためのメカニズムを提供します。この変更の主な目的は、ネットワーク越しにデータを送受信する際に、送信側（ワイヤータイプ）と受信側（レシーブタイプ）で構造体の型定義が完全に一致していなくても、互換性のあるフィールドについては正しくデコードできるようにすることです。これにより、`gob`のスキーマ進化の柔軟性が大幅に向上しました。

## 変更の背景

`gob`パッケージは、Goプログラム間で構造化されたデータを効率的に交換するために設計されています。しかし、このコミット以前の`gob`の実装では、データをエンコードした側の型（ワイヤータイプ）と、デコードする側の型（レシーブタイプ）が完全に一致している必要がありました。これは、特に分散システムや長期にわたるサービス運用において、型の変更（フィールドの追加、削除、順序変更など）が発生した場合に大きな問題となります。

例えば、サーバーが新しいフィールドを持つ構造体を送信し始めた場合、古いクライアントはその新しいフィールドを認識できず、デコードに失敗するか、予期せぬエラーを引き起こす可能性がありました。逆に、クライアントが古い構造体を送信し、サーバーが新しい構造体を期待している場合も同様の問題が生じます。

このコミットの背景には、このようなスキーマ進化の課題に対応し、`gob`の柔軟性と実用性を高めるという明確な目的があります。具体的には、ワイヤータイプとレシーブタイプが異なっていても、互換性のあるフィールドは正しくデコードし、受信側で不要なフィールドは無視できるようにする機能の基礎を築くことが目指されました。コミットメッセージにある「still TODO: ignoring struct fields.」という記述は、このコミットがその目標に向けた第一歩であり、構造体フィールドの無視機能はまだ完全ではないことを示唆しています。

## 前提知識の解説

### Goの`gob`パッケージ

`gob`はGo言語に特化したバイナリシシリアライゼーションフォーマットです。Goのプログラム間でデータを交換する際に、構造体、配列、スライス、マップなどのGoのネイティブなデータ型を効率的にバイナリ形式に変換（エンコード）し、元のデータ型に復元（デコード）するために使用されます。`gob`は、データと共に型情報も送信するため、受信側は事前に型を知らなくてもデータをデコードできるという特徴があります。これは、JSONやProtocol Buffersなどの他のシリアライゼーション形式とは異なるアプローチです。

### ワイヤータイプ (Wire Type) と レシーブタイプ (Receive Type)

*   **ワイヤータイプ (Wire Type)**: データをネットワーク経由で送信する際に、エンコードされたデータの実際の型定義を指します。これは、送信側のプログラムが持っている型情報です。
*   **レシーブタイプ (Receive Type)**: データをネットワーク経由で受信する際に、デコードされたデータを格納するために受信側のプログラムが期待する型定義を指します。

このコミット以前は、これら二つの型が完全に一致している必要がありましたが、この変更により、ある程度の差異が許容されるようになりました。

### リフレクション (Reflection)

Goのリフレクションは、実行時にプログラムの構造（型、フィールド、メソッドなど）を検査し、操作する機能です。`gob`パッケージは、このリフレクションを extensively に利用して、任意のGoの型をシリアライズ・デシリアライズするためのコードを動的に生成します。

*   `reflect.Type`: Goの型のメタデータを表すインターフェース。
*   `reflect.Value`: Goの値の実行時表現。
*   `reflect.StructType`, `reflect.ArrayType`, `reflect.SliceType` など: 特定の複合型の型情報を表す構造体。

### `unsafe.Pointer`と`uintptr`

これらはGoの`unsafe`パッケージに含まれる型で、低レベルなメモリ操作を可能にします。

*   `unsafe.Pointer`: 任意の型のポインタを保持できる汎用ポインタ。C言語の`void*`に似ていますが、より厳密な型安全ルールがあります。
*   `uintptr`: ポインタの値を整数として表現する型。ポインタ演算を行う際に使用されることがあります。

`gob`のデコードエンジンは、パフォーマンスのためにリフレクションと`unsafe`パッケージを組み合わせて、直接メモリを操作することでデータを効率的に読み書きします。

### `TypeId`

`gob`内部で、各Goの型には一意の`TypeId`が割り当てられます。このIDは、ネットワーク越しに型情報を識別するために使用されます。データが送信される前に、`gob`は送信される型の`TypeId`を送信し、受信側はその`TypeId`に基づいて適切なデコードロジックを決定します。

### `decEngine`と`decInstr`

`gob`のデコード処理は、一種の仮想マシンとして実装されています。

*   `decInstr` (decode instruction): デコード処理の最小単位を表す構造体。特定のフィールドをどのようにデコードするか（例：`decInt`、`decString`）、何回ポインタを辿るか（`indir`）、構造体内のオフセット（`offset`）などの情報を含みます。
*   `decEngine` (decode engine): `decInstr`の配列を保持し、特定の型をデコードするための一連の命令セットを構成します。`gob`は、型ごとに`decEngine`をコンパイルし、それを使ってデータを効率的にデコードします。

## 技術的詳細

このコミットの核心は、`gob`のデコードプロセスが、送信されたデータの型（ワイヤータイプ）と、受信側が期待する型（レシーブタイプ）の間の不一致を許容するように変更された点にあります。

1.  **`decode`関数のシグネチャ変更**:
    以前の`decode`関数は`func decode(b *bytes.Buffer, e interface{}) os.Error`というシグネチャでした。これは、デコード対象のデータと、そのデータを格納するインターフェース値のみを受け取っていました。
    このコミットにより、`func decode(b *bytes.Buffer, wireId TypeId, e interface{}) os.Error`に変更されました。新たに`wireId TypeId`が追加されたことで、`decode`関数は、受信側が期待する型`e`だけでなく、実際にワイヤー上を流れてきたデータの型IDも明示的に受け取ることができるようになりました。これにより、デコードエンジンは両方の型情報を比較し、適切なデコード戦略を立てることが可能になります。

2.  **`getDecEngine`から`getDecEnginePtr`への変更**:
    デコードエンジンを取得する関数が`getDecEngine(rt reflect.Type)`から`getDecEnginePtr(wireId TypeId, rt reflect.Type) **decEngine`に変更されました。
    *   `wireId TypeId`が追加されたことで、デコードエンジンはワイヤータイプとレシーブタイプの両方に基づいてコンパイルされるようになりました。
    *   戻り値が`*decEngine`から`**decEngine`（`decEngine`へのポインタのポインタ）になったのは、再帰的な型（例：自身をフィールドに持つ構造体）を扱う際に、コンパイル中のエンジンへの参照を遅延評価するためです。これにより、循環参照の問題を回避し、正しくエンジンを構築できます。
    *   `typeInfo`構造体内の`decoder`フィールドが`decoderPtr map[TypeId] **decEngine`に変更され、ワイヤータイプごとに異なるデコードエンジンをキャッシュできるようになりました。

3.  **`compileDec`関数の強化**:
    `compileDec`関数は、特定の型をデコードするための`decEngine`を構築する役割を担います。このコミットにより、`compileDec(wireId TypeId, rt reflect.Type) *decEngine`というシグネチャに変更され、ワイヤータイプIDとレシーブタイプ（`reflect.Type`）の両方を受け取るようになりました。
    この関数内で、ワイヤータイプとレシーブタイプのフィールドを比較し、以下のロジックが実装されました。
    *   ワイヤータイプの各フィールドについて、レシーブタイプに同じ名前のフィールドが存在するかを検索します。
    *   フィールドが見つかった場合、そのフィールドの型がワイヤータイプと互換性があるかを`compatibleType`関数でチェックします。
    *   フィールドが見つからない、または互換性がない場合、そのワイヤーフィールドは無視されるように`decIgnoreOpFor`を使って命令が生成されます。

4.  **`compatibleType`関数の導入**:
    この新しい関数`func compatibleType(fr reflect.Type, fw TypeId) bool`は、レシーブタイプ（`fr`）とワイヤータイプ（`fw`）が互換性があるかどうかを判断します。
    *   プリミティブ型（bool, int, uint, float, string）については、対応する`TypeId`が一致するかを直接チェックします。
    *   配列型については、要素の型と配列の長さが一致するかを再帰的にチェックします。
    *   スライス型については、要素の型が一致するかを再帰的にチェックします。`[]byte`は`tBytes`として特別扱いされます。
    *   構造体型については、この関数内では`true`を返し、実際のフィールド互換性チェックは`compileDec`に委ねられます。
    *   ポインタ型は、その指す先の型で比較されます。

5.  **`decIgnoreOpFor`関数の導入**:
    `func decIgnoreOpFor(wireId TypeId) decOp`は、受信側で対応するフィールドがないワイヤーフィールドを読み飛ばすためのデコード操作（`decOp`）を生成します。
    *   プリミティブ型（`tBool`, `tInt`, `tUint`, `tFloat`, `tBytes`, `tString`）に対しては、それぞれ`ignoreUint`や`ignoreUint8Array`といった、データを読み込むがどこにも格納しない操作が割り当てられます。
    *   スライスや配列に対しても、要素を再帰的に無視する`ignoreSlice`や`ignoreArray`が生成されます。
    *   構造体については、このコミット時点では「TODO: write an ignore engine for structs」とあり、まだ完全な実装ではありません。

これらの変更により、`gob`は、フィールドの順序が異なったり、受信側で存在しないフィールドがワイヤータイプに含まれていたりする場合でも、エラーなくデコードできるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`gob`がワイヤータイプとレシーブタイプの差異をどのように扱うかというデコードエンジンの構築ロジックにあります。

### `compileDec`関数の変更

```go
func compileDec(wireId TypeId, rt reflect.Type) *decEngine {
	srt, ok1 := rt.(*reflect.StructType);
	wireStruct, ok2 := wireId.gobType().(*structType);
	if !ok1 || !ok2 {
		panicln("gob: TODO: can't handle non-structs");
	}
	engine := new(decEngine);
	engine.instr = make([]decInstr, len(wireStruct.field));
	// Loop over the fields of the wire type.
	for fieldnum := 0; fieldnum < len(wireStruct.field); fieldnum++ {
		wireField := wireStruct.field[fieldnum];
		// Find the field of the local type with the same name.
		var localField reflect.StructField;
		for lfn := 0; lfn < srt.NumField(); lfn++ {
			if srt.Field(lfn).Name == wireField.name {
				localField = srt.Field(lfn);
				break;
			}
		}
		// TODO(r): anonymous names
		if localField.Anonymous || localField.Name == "" { // localFieldが見つからなかった場合
			println("no matching field", wireField.name, "in type", wireId.String());
			op := decIgnoreOpFor(wireField.typeId); // 無視操作を生成
			engine.instr[fieldnum] = decInstr{op, fieldnum, 0, 0};
			continue;
		}
		if !compatibleType(localField.Type, wireField.typeId) {
			panicln("TODO: wrong type for field", wireField.name, "in type", wireId.String());
		}
		op, indir := decOpFor(wireField.typeId, localField.Type); // 通常のデコード操作を生成
		engine.instr[fieldnum] = decInstr{op, fieldnum, indir, uintptr(localField.Offset)};
		engine.numInstr++;
	}
	return engine;
}
```
この`compileDec`関数は、ワイヤータイプ（`wireId`）とレシーブタイプ（`rt`）の両方を受け取り、デコードエンジンを構築します。
1.  ワイヤータイプの各フィールド（`wireField`）をループします。
2.  現在の`wireField`と同じ名前を持つフィールドをレシーブタイプ（`srt`）内で検索します。
3.  もしレシーブタイプに対応するフィールドが見つからない場合（`localField.Name == ""`）、そのワイヤーフィールドは受信側で不要と判断されます。この場合、`decIgnoreOpFor(wireField.typeId)`を呼び出して、そのフィールドのデータを読み飛ばすためのデコード命令（`decInstr`）を生成し、エンジンに追加します。
4.  対応するフィールドが見つかった場合、`compatibleType(localField.Type, wireField.typeId)`を呼び出して、両者の型が互換性があるかを確認します。互換性がない場合は`panic`します（これは将来的にエラーハンドリングが改善される可能性があります）。
5.  互換性がある場合、`decOpFor(wireField.typeId, localField.Type)`を呼び出して、そのフィールドを正しくデコードするための命令を生成し、エンジンに追加します。

このロジックにより、`gob`はワイヤータイプに存在するがレシーブタイプには存在しないフィールドを安全に無視できるようになり、フィールドの順序が異なっていても名前でマッチングしてデコードできるようになります。

### `compatibleType`関数

```go
func compatibleType(fr reflect.Type, fw TypeId) bool {
	for {
		if pt, ok := fr.(*reflect.PtrType); ok {
			fr = pt.Elem(); // ポインタを辿る
			continue;
		}
		break;
	}
	switch t := fr.(type) {
	default:
		return false; // interface, map, chan などは現時点では互換性なし
	case *reflect.BoolType:
		return fw == tBool;
	// ... 他のプリミティブ型 ...
	case *reflect.StructType:
		return true; // 構造体はここで詳細なチェックはせず、compileDecに委ねる
	case *reflect.ArrayType:
		aw, ok := fw.gobType().(*arrayType);
		return ok && t.Len() == aw.Len && compatibleType(t.Elem(), aw.Elem);
	case *reflect.SliceType:
		et := t.Elem();
		if _, ok := et.(*reflect.Uint8Type); ok {
			return fw == tBytes // []byte は tBytes と互換
		}
		sw, ok := fw.gobType().(*sliceType);
		return ok && compatibleType(t.Elem(), sw.Elem);
	}
	return true; // デフォルトでtrueを返すのは、まだ対応していない型があるためか、あるいは最終的なフォールバック
}
```
`compatibleType`関数は、レシーブタイプ（`fr`）とワイヤータイプ（`fw`）の基本的な互換性をチェックします。ポインタをデリファレンスした後、Goのリフレクション型と`gob`の`TypeId`を比較します。特に注目すべきは、構造体型に対しては`true`を返し、実際のフィールドレベルの互換性チェックは`compileDec`に任せている点です。これにより、型全体の互換性チェックとフィールドごとの互換性チェックが分離されています。

### `decIgnoreOpFor`関数

```go
func decIgnoreOpFor(wireId TypeId) decOp {
	op, ok := decIgnoreOpMap[wireId];
	if !ok {
		// Special cases
		switch t := wireId.gobType().(type) {
		case *sliceType:
			elemId := wireId.gobType().(*sliceType).Elem;
			elemOp := decIgnoreOpFor(elemId);
			op = func(i *decInstr, state *decodeState, p unsafe.Pointer) {
				state.err = ignoreSlice(state, elemOp);
			};

		case *arrayType:
			elemId := wireId.gobType().(*arrayType).Elem;
			elemOp := decIgnoreOpFor(elemId);
			op = func(i *decInstr, state *decodeState, p unsafe.Pointer) {
				state.err = ignoreArray(state, elemOp, t.Len);
			};

		case *structType:
			// TODO: write an ignore engine for structs
		}
	}
	if op == nil {
		panicln("decode can't handle type", wireId.gobType().String());
	}
	return op;
}
```
この関数は、受信側で無視すべきフィールドの`TypeId`を受け取り、その型を読み飛ばすための`decOp`（デコード操作）を返します。プリミティブ型に対しては、`decIgnoreOpMap`に定義された`ignoreUint`や`ignoreUint8Array`のような関数が使われます。スライスや配列のような複合型に対しては、再帰的に要素を無視する操作が生成されます。構造体については、このコミット時点ではまだ「TODO」であり、完全な無視ロジックは実装されていません。

これらの変更により、`gob`はより堅牢で柔軟なシリアライゼーションメカニズムへと進化し、Goアプリケーションのスキーマ進化をより容易にサポートできるようになりました。

## 変更の背景

`gob`パッケージは、Goプログラム間で構造化されたデータを効率的に交換するために設計されています。しかし、このコミット以前の`gob`の実装では、データをエンコードした側の型（ワイヤータイプ）と、デコードする側の型（レシーブタイプ）が完全に一致している必要がありました。これは、特に分散システムや長期にわたるサービス運用において、型の変更（フィールドの追加、削除、順序変更など）が発生した場合に大きな問題となります。

例えば、サーバーが新しいフィールドを持つ構造体を送信し始めた場合、古いクライアントはその新しいフィールドを認識できず、デコードに失敗するか、予期せぬエラーを引き起こす可能性がありました。逆に、クライアントが古い構造体を送信し、サーバーが新しい構造体を期待している場合も同様の問題が生じます。

このコミットの背景には、このようなスキーマ進化の課題に対応し、`gob`の柔軟性と実用性を高めるという明確な目的があります。具体的には、ワイヤータイプとレシーブタイプが異なっていても、互換性のあるフィールドは正しくデコードし、受信側で不要なフィールドは無視できるようにする機能の基礎を築くことが目指されました。コミットメッセージにある「still TODO: ignoring struct fields.」という記述は、このコミットがその目標に向けた第一歩であり、構造体フィールドの無視機能はまだ完全ではないことを示唆しています。

## 前提知識の解説

### Goの`gob`パッケージ

`gob`はGo言語に特化したバイナリシリアライゼーションフォーマットです。Goのプログラム間でデータを交換する際に、構造体、配列、スライス、マップなどのGoのネイティブなデータ型を効率的にバイナリ形式に変換（エンコード）し、元のデータ型に復元（デコード）するために使用されます。`gob`は、データと共に型情報も送信するため、受信側は事前に型を知らなくてもデータをデコードできるという特徴があります。これは、JSONやProtocol Buffersなどの他のシリアライゼーション形式とは異なるアプローチです。

### ワイヤータイプ (Wire Type) と レシーブタイプ (Receive Type)

*   **ワイヤータイプ (Wire Type)**: データをネットワーク経由で送信する際に、エンコードされたデータの実際の型定義を指します。これは、送信側のプログラムが持っている型情報です。
*   **レシーブタイプ (Receive Type)**: データをネットワーク経由で受信する際に、デコードされたデータを格納するために受信側のプログラムが期待する型定義を指します。

このコミット以前は、これら二つの型が完全に一致している必要がありましたが、この変更により、ある程度の差異が許容されるようになりました。

### リフレクション (Reflection)

Goのリフレクションは、実行時にプログラムの構造（型、フィールド、メソッドなど）を検査し、操作する機能です。`gob`パッケージは、このリフレクションを extensively に利用して、任意のGoの型をシリアライズ・デシリアライズするためのコードを動的に生成します。

*   `reflect.Type`: Goの型のメタデータを表すインターフェース。
*   `reflect.Value`: Goの値の実行時表現。
*   `reflect.StructType`, `reflect.ArrayType`, `reflect.SliceType` など: 特定の複合型の型情報を表す構造体。

### `unsafe.Pointer`と`uintptr`

これらはGoの`unsafe`パッケージに含まれる型で、低レベルなメモリ操作を可能にします。

*   `unsafe.Pointer`: 任意の型のポインタを保持できる汎用ポインタ。C言語の`void*`に似ていますが、より厳密な型安全ルールがあります。
*   `uintptr`: ポインタの値を整数として表現する型。ポインタ演算を行う際に使用されることがあります。

`gob`のデコードエンジンは、パフォーマンスのためにリフレクションと`unsafe`パッケージを組み合わせて、直接メモリを操作することでデータを効率的に読み書きします。

### `TypeId`

`gob`内部で、各Goの型には一意の`TypeId`が割り当てられます。このIDは、ネットワーク越しに型情報を識別するために使用されます。データが送信される前に、`gob`は送信される型の`TypeId`を送信し、受信側はその`TypeId`に基づいて適切なデコードロジックを決定します。

### `decEngine`と`decInstr`

`gob`のデコード処理は、一種の仮想マシンとして実装されています。

*   `decInstr` (decode instruction): デコード処理の最小単位を表す構造体。特定のフィールドをどのようにデコードするか（例：`decInt`、`decString`）、何回ポインタを辿るか（`indir`）、構造体内のオフセット（`offset`）などの情報を含みます。
*   `decEngine` (decode engine): `decInstr`の配列を保持し、特定の型をデコードするための一連の命令セットを構成します。`gob`は、型ごとに`decEngine`をコンパイルし、それを使ってデータを効率的にデコードします。

## 技術的詳細

このコミットの核心は、`gob`のデコードプロセスが、送信されたデータの型（ワイヤータイプ）と、受信側が期待する型（レシーブタイプ）の間の不一致を許容するように変更された点にあります。

1.  **`decode`関数のシグネチャ変更**:
    以前の`decode`関数は`func decode(b *bytes.Buffer, e interface{}) os.Error`というシグネチャでした。これは、デコード対象のデータと、そのデータを格納するインターフェース値のみを受け取っていました。
    このコミットにより、`func decode(b *bytes.Buffer, wireId TypeId, e interface{}) os.Error`に変更されました。新たに`wireId TypeId`が追加されたことで、`decode`関数は、受信側が期待する型`e`だけでなく、実際にワイヤー上を流れてきたデータの型IDも明示的に受け取ることができるようになりました。これにより、デコードエンジンは両方の型情報を比較し、適切なデコード戦略を立てることが可能になります。

2.  **`getDecEngine`から`getDecEnginePtr`への変更**:
    デコードエンジンを取得する関数が`getDecEngine(rt reflect.Type)`から`getDecEnginePtr(wireId TypeId, rt reflect.Type) **decEngine`に変更されました。
    *   `wireId TypeId`が追加されたことで、デコードエンジンはワイヤータイプとレシーブタイプの両方に基づいてコンパイルされるようになりました。
    *   戻り値が`*decEngine`から`**decEngine`（`decEngine`へのポインタのポインタ）になったのは、再帰的な型（例：自身をフィールドに持つ構造体）を扱う際に、コンパイル中のエンジンへの参照を遅延評価するためです。これにより、循環参照の問題を回避し、正しくエンジンを構築できます。
    *   `typeInfo`構造体内の`decoder`フィールドが`decoderPtr map[TypeId] **decEngine`に変更され、ワイヤータイプごとに異なるデコードエンジンをキャッシュできるようになりました。

3.  **`compileDec`関数の強化**:
    `compileDec`関数は、特定の型をデコードするための`decEngine`を構築する役割を担います。このコミットにより、`compileDec(wireId TypeId, rt reflect.Type) *decEngine`というシグネチャに変更され、ワイヤータイプIDとレシーブタイプ（`reflect.Type`）の両方を受け取るようになりました。
    この関数内で、ワイヤータイプとレシーブタイプのフィールドを比較し、以下のロジックが実装されました。
    *   ワイヤータイプの各フィールドについて、レシーブタイプに同じ名前のフィールドが存在するかを検索します。
    *   フィールドが見つかった場合、そのフィールドの型がワイヤータイプと互換性があるかを`compatibleType`関数でチェックします。
    *   フィールドが見つからない、または互換性がない場合、そのワイヤーフィールドは無視されるように`decIgnoreOpFor`を使って命令が生成されます。

4.  **`compatibleType`関数の導入**:
    この新しい関数`func compatibleType(fr reflect.Type, fw TypeId) bool`は、レシーブタイプ（`fr`）とワイヤータイプ（`fw`）が互換性があるかどうかを判断します。
    *   プリミティブ型（bool, int, uint, float, string）については、対応する`TypeId`が一致するかを直接チェックします。
    *   配列型については、要素の型と配列の長さが一致するかを再帰的にチェックします。
    *   スライス型については、要素の型が一致するかを再帰的にチェックします。`[]byte`は`tBytes`として特別扱いされます。
    *   構造体型については、この関数内では`true`を返し、実際のフィールド互換性チェックは`compileDec`に委ねられます。
    *   ポインタ型は、その指す先の型で比較されます。

5.  **`decIgnoreOpFor`関数の導入**:
    `func decIgnoreOpFor(wireId TypeId) decOp`は、受信側で対応するフィールドがないワイヤーフィールドを読み飛ばすためのデコード操作（`decOp`）を生成します。
    *   プリミティブ型（`tBool`, `tInt`, `tUint`, `tFloat`, `tBytes`, `tString`）に対しては、それぞれ`ignoreUint`や`ignoreUint8Array`といった、データを読み込むがどこにも格納しない操作が割り当てられます。
    *   スライスや配列に対しても、要素を再帰的に無視する`ignoreSlice`や`ignoreArray`が生成されます。
    *   構造体については、このコミット時点では「TODO: write an ignore engine for structs」とあり、まだ完全な実装ではありません。

これらの変更により、`gob`は、フィールドの順序が異なったり、受信側で存在しないフィールドがワイヤータイプに含まれていたりする場合でも、エラーなくデコードできるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`gob`がワイヤータイプとレシーブタイプの差異をどのように扱うかというデコードエンジンの構築ロジックにあります。

### `compileDec`関数の変更

```go
func compileDec(wireId TypeId, rt reflect.Type) *decEngine {
	srt, ok1 := rt.(*reflect.StructType);
	wireStruct, ok2 := wireId.gobType().(*structType);
	if !ok1 || !ok2 {
		panicln("gob: TODO: can't handle non-structs");
	}
	engine := new(decEngine);
	engine.instr = make([]decInstr, len(wireStruct.field));
	// Loop over the fields of the wire type.
	for fieldnum := 0; fieldnum < len(wireStruct.field); fieldnum++ {
		wireField := wireStruct.field[fieldnum];
		// Find the field of the local type with the same name.
		var localField reflect.StructField;
		for lfn := 0; lfn < srt.NumField(); lfn++ {
			if srt.Field(lfn).Name == wireField.name {
				localField = srt.Field(lfn);
				break;
			}
		}
		// TODO(r): anonymous names
		if localField.Anonymous || localField.Name == "" { // localFieldが見つからなかった場合
			println("no matching field", wireField.name, "in type", wireId.String());
			op := decIgnoreOpFor(wireField.typeId); // 無視操作を生成
			engine.instr[fieldnum] = decInstr{op, fieldnum, 0, 0};
			continue;
		}
		if !compatibleType(localField.Type, wireField.typeId) {
			panicln("TODO: wrong type for field", wireField.name, "in type", wireId.String());
		}
		op, indir := decOpFor(wireField.typeId, localField.Type); // 通常のデコード操作を生成
		engine.instr[fieldnum] = decInstr{op, fieldnum, indir, uintptr(localField.Offset)};
		engine.numInstr++;
	}
	return engine;
}
```
この`compileDec`関数は、ワイヤータイプ（`wireId`）とレシーブタイプ（`rt`）の両方を受け取り、デコードエンジンを構築します。
1.  ワイヤータイプの各フィールド（`wireField`）をループします。
2.  現在の`wireField`と同じ名前を持つフィールドをレシーブタイプ（`srt`）内で検索します。
3.  もしレシーブタイプに対応するフィールドが見つからない場合（`localField.Name == ""`）、そのワイヤーフィールドは受信側で不要と判断されます。この場合、`decIgnoreOpFor(wireField.typeId)`を呼び出して、そのフィールドのデータを読み飛ばすためのデコード命令（`decInstr`）を生成し、エンジンに追加します。
4.  対応するフィールドが見つかった場合、`compatibleType(localField.Type, wireId)`を呼び出して、両者の型が互換性があるかを確認します。互換性がない場合は`panic`します（これは将来的にエラーハンドリングが改善される可能性があります）。
5.  互換性がある場合、`decOpFor(wireField.typeId, localField.Type)`を呼び出して、そのフィールドを正しくデコードするための命令を生成し、エンジンに追加します。

このロジックにより、`gob`はワイヤータイプに存在するがレシーブタイプには存在しないフィールドを安全に無視できるようになり、フィールドの順序が異なっていても名前でマッチングしてデコードできるようになります。

### `compatibleType`関数

```go
func compatibleType(fr reflect.Type, fw TypeId) bool {
	for {
		if pt, ok := fr.(*reflect.PtrType); ok {
			fr = pt.Elem(); // ポインタを辿る
			continue;
		}
		break;
	}
	switch t := fr.(type) {
	default:
		return false; // interface, map, chan などは現時点では互換性なし
	case *reflect.BoolType:
		return fw == tBool;
	// ... 他のプリミティブ型 ...
	case *reflect.StructType:
		return true; // 構造体はここで詳細なチェックはせず、compileDecに委ねる
	case *reflect.ArrayType:
		aw, ok := fw.gobType().(*arrayType);
		return ok && t.Len() == aw.Len && compatibleType(t.Elem(), aw.Elem);
	case *reflect.SliceType:
		et := t.Elem();
		if _, ok := et.(*reflect.Uint8Type); ok {
			return fw == tBytes // []byte は tBytes と互換
		}
		sw, ok := fw.gobType().(*sliceType);
		return ok && compatibleType(t.Elem(), sw.Elem);
	}
	return true; // デフォルトでtrueを返すのは、まだ対応していない型があるためか、あるいは最終的なフォールバック
}
```
`compatibleType`関数は、レシーブタイプ（`fr`）とワイヤータイプ（`fw`）の基本的な互換性をチェックします。ポインタをデリファレンスした後、Goのリフレクション型と`gob`の`TypeId`を比較します。特に注目すべきは、構造体型に対しては`true`を返し、実際のフィールドレベルの互換性チェックは`compileDec`に任せている点です。これにより、型全体の互換性チェックとフィールドごとの互換性チェックが分離されています。

### `decIgnoreOpFor`関数

```go
func decIgnoreOpFor(wireId TypeId) decOp {
	op, ok := decIgnoreOpMap[wireId];
	if !ok {
		// Special cases
		switch t := wireId.gobType().(type) {
		case *sliceType:
			elemId := wireId.gobType().(*sliceType).Elem;
			elemOp := decIgnoreOpFor(elemId);
			op = func(i *decInstr, state *decodeState, p unsafe.Pointer) {
				state.err = ignoreSlice(state, elemOp);
			};

		case *arrayType:
			elemId := wireId.gobType().(*arrayType).Elem;
			elemOp := decIgnoreOpFor(elemId);
			op = func(i *decInstr, state *decodeState, p unsafe.Pointer) {
				state.err = ignoreArray(state, elemOp, t.Len);
			};

		case *structType:
			// TODO: write an ignore engine for structs
		}
	}
	if op == nil {
		panicln("decode can't handle type", wireId.gobType().String());
	}
	return op;
}
```
この関数は、受信側で無視すべきフィールドの`TypeId`を受け取り、その型を読み飛ばすための`decOp`（デコード操作）を返します。プリミティブ型に対しては、`decIgnoreOpMap`に定義された`ignoreUint`や`ignoreUint8Array`のような関数が使われます。スライスや配列のような複合型に対しては、再帰的に要素を無視する操作が生成されます。構造体については、このコミット時点ではまだ「TODO」であり、完全な無視ロジックは実装されていません。

これらの変更により、`gob`はより堅牢で柔軟なシリアライゼーションメカニズムへと進化し、Goアプリケーションのスキーマ進化をより容易にサポートできるようになりました。

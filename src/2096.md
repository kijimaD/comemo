# [インデックス 2096] ファイルの概要

このコミットは、Go言語の標準ライブラリの一部である `src/lib/http/server.go` ファイルに対する変更です。このファイルは、HTTPサーバーの実装、特にクライアントへのレスポンスの書き込みと処理を担当しています。HTTPプロトコルにおけるチャンク転送エンコーディングの処理に関連するバグ修正が行われました。

## コミット

このコミットは、HTTPのチャンク転送エンコーディングにおいて、各チャンクの終端にCRLF（Carriage Return Line Feed）が正しく付与されるように修正するものです。これにより、HTTP/1.1の仕様に準拠し、クライアントがチャンクデータを正しく解釈できるようになります。

## 変更の背景

このコミットが行われた背景には、HTTP/1.1プロトコルにおけるチャンク転送エンコーディングの厳密な仕様があります。チャンク転送エンコーディングは、HTTPメッセージボディを、サイズを示すヘッダーとデータ本体、そして終端を示すCRLF（Carriage Return Line Feed）で構成される一連の「チャンク」に分割して送信するメカニズムです。これにより、サーバーはコンテンツの全長が不明な場合でも、動的にコンテンツを生成しながら送信できます。

元の実装では、チャンクのデータ本体の後にCRLFが適切に付与されていなかった可能性があります。これは、特に`c.buf.Write(data)`の呼び出しが成功した場合でも、その後にCRLFが書き込まれないという問題を引き起こします。HTTPクライアントは、各チャンクの終端にCRLFが存在することを期待しているため、これが欠落していると、クライアントはチャンクの境界を正しく認識できず、レスポンスの解析に失敗したり、データが破損したりする可能性がありました。

この修正は、HTTPサーバーが生成するチャンク転送エンコードされたレスポンスが、RFC 2616（HTTP/1.1の仕様）に完全に準拠するようにするために不可欠でした。

## 前提知識の解説

### HTTP チャンク転送エンコーディング (Chunked Transfer Encoding)

HTTP/1.1で導入された転送エンコーディングの一種で、メッセージボディを複数の「チャンク」に分割して送信する方式です。主な目的は以下の通りです。

*   **動的なコンテンツ生成**: サーバーがレスポンスボディの全長を事前に知る必要がないため、動的に生成されるコンテンツ（例: ストリーミングデータ、長いデータベースクエリの結果）を送信するのに適しています。
*   **持続的接続 (Persistent Connections)**: チャンク転送エンコーディングを使用することで、サーバーは接続を閉じずに複数のレスポンスを送信できます。

チャンクのフォーマットは以下のようになります。

```
[チャンクサイズ (16進数)]CRLF
[チャンクデータ]CRLF
[チャンクサイズ (16進数)]CRLF
[チャンクデータ]CRLF
...
0CRLF
CRLF
```

最後のチャンクはサイズが0で、その後にCRLFが続き、さらにその後に終端を示すCRLFが続きます。

### CRLF (Carriage Return Line Feed)

CRLFは、ASCII文字のCarriage Return (CR, `\r`, 16進数で`0x0D`) とLine Feed (LF, `\n`, 16進数で`0x0A`) の組み合わせです。Windowsや多くのインターネットプロトコル（HTTP、SMTP、FTPなど）で、行の終端を示すために使用されます。HTTPプロトコルでは、ヘッダーの終端やチャンクの終端など、様々な場所でCRLFが区切り文字として厳密に要求されます。

### `bufio.ShortWrite`

Go言語の`bufio`パッケージで定義されているエラーです。`bufio.Writer`の`Write`メソッドが、書き込もうとしたバイト数よりも少ないバイト数しか書き込めなかった場合に返される可能性があります。これは、基になるI/O操作が部分的にしか成功しなかったことを示します。このエラーが発生した場合、通常は書き込み操作が完全に成功しなかったため、後続の処理（この場合はCRLFの書き込み）を中止する必要があります。

## 技術的詳細

このコミットの技術的な核心は、HTTPチャンク転送エンコーディングの仕様に厳密に準拠することです。具体的には、`http.Conn`構造体の`Write`メソッドにおいて、チャンクデータ本体の書き込みが完了した後に、必ずCRLFを書き込むロジックを追加しています。

元のコードでは、`c.buf.Write(data)`の呼び出しの前にチャンクサイズとCRLFを書き込んでいましたが、データ本体の後にCRLFを書き込む処理がありませんでした。

修正後のコードでは、以下のステップが追加されています。

1.  `c.buf.Write(data)`の戻り値である`n`（実際に書き込まれたバイト数）と`err`（エラー）を取得します。
2.  エラーがなく、かつチャンク転送エンコーディングが有効な場合（`err == nil && c.chunking`）、以下のチェックを行います。
    *   `n != len(data)`: 書き込もうとしたデータ（`len(data)`）がすべて書き込まれたか（`n`）を確認します。もし部分的な書き込み（`n < len(data)`）が発生していた場合、`bufio.ShortWrite`エラーを設定します。これは、データが完全に送信されていないため、チャンクの終端を示すCRLFを書き込むべきではないという判断です。
    *   `err == nil`: 上記のチェックでエラーが設定されなかった場合、つまりデータが完全に書き込まれた場合にのみ、`io.WriteString(c.buf, "\r\n")`を呼び出してCRLFをバッファに書き込みます。

この変更により、HTTPサーバーは各チャンクのデータ本体の後に必ずCRLFを付与するようになり、HTTP/1.1のチャンク転送エンコーディングの仕様に完全に準拠します。これにより、様々なHTTPクライアントとの互換性が向上し、データ解析の問題が解消されます。

## コアとなるコードの解説

変更は`func (c *Conn) Write(data []byte) (n int, err os.Error)`メソッド内で行われています。

*   **変更前**:
    ```go
    	if c.chunking {
    		fmt.Fprintf(c.buf, "%x\r\n", len(data));	// TODO(rsc): use strconv not fmt
    	}
    	return c.buf.Write(data);
    ```
    ここでは、チャンク転送が有効な場合、まずチャンクサイズとCRLFを書き込み、その直後にデータ本体を書き込んでいました。しかし、データ本体の後にチャンク終端のCRLFを書き込む処理が欠落していました。

*   **変更後**:
    ```go
    	if c.chunking {
    		fmt.Fprintf(c.buf, "%x\r\n", len(data));	// TODO(rsc): use strconv not fmt
    	}
    	n, err = c.buf.Write(data); // データ本体を書き込む
    	if err == nil && c.chunking { // エラーがなく、チャンク転送が有効な場合
    		if n != len(data) { // 書き込みが不完全だった場合
    			err = bufio.ShortWrite; // ShortWriteエラーを設定
    		}
    		if err == nil { // データが完全に書き込まれ、エラーがない場合
    			io.WriteString(c.buf, "\r\n"); // チャンク終端のCRLFを書き込む
    		}
    	}
    	return n, err;
    ```
    1.  `n, err = c.buf.Write(data);`: まず、`data`（チャンクのペイロード）をバッファに書き込みます。このとき、実際に書き込まれたバイト数`n`と発生したエラー`err`を取得します。
    2.  `if err == nil && c.chunking { ... }`: データ書き込み中にエラーが発生せず、かつチャンク転送が有効な場合にのみ、チャンク終端のCRLFを追加する処理に進みます。
    3.  `if n != len(data) { err = bufio.ShortWrite; }`: ここが重要なポイントです。もし`c.buf.Write(data)`が`data`の全バイトを書き込めなかった場合（`n`が`len(data)`より小さい場合）、それは部分的な書き込みであり、チャンクが不完全であることを意味します。この場合、`bufio.ShortWrite`エラーを明示的に設定し、後続のCRLFの書き込みをスキップします。不完全なチャンクにCRLFを付けてしまうと、クライアントが誤ってそのチャンクを完全なものと解釈してしまう可能性があるため、これは正しい挙動です。
    4.  `if err == nil { io.WriteString(c.buf, "\r\n"); }`: 上記の`ShortWrite`チェックを含め、データ書き込み全体でエラーがなければ、`io.WriteString`を使ってチャンク終端のCRLF (`\r\n`) をバッファに書き込みます。

この修正により、HTTPチャンク転送エンコーディングの仕様に厳密に準拠し、堅牢なHTTPサーバーの実装が実現されました。

# [インデックス 20065] ファイルの概要

このコミットは、Go言語の`power64`アーキテクチャ向けに、リンカ(`cmd/9l`)、`math/big`パッケージ、ランタイム、および`syscall`パッケージにおける複数の修正を導入します。主な目的は、`power64`環境でのGoプログラムの正確な動作と互換性を確保することです。具体的には、ハードウェアのページサイズが64KBである環境への対応、カーネルからのエラー番号の処理の修正、そして`math/big`パッケージの基本的な算術演算のスタブ実装が含まれます。

## 変更の背景

このコミットは、Go言語がIBMのPOWER64アーキテクチャ上で適切に動作するための重要な修正を含んでいます。当時のGo言語のランタイムは、主にx86アーキテクチャを念頭に設計されており、ページサイズやシステムコールからの戻り値の規約など、他のアーキテクチャ固有の特性に対応しきれていない部分がありました。

具体的な背景は以下の通りです。

1.  **ハードウェアページサイズの不一致**: 多くの一般的なシステム（x86など）では、メモリのページサイズは4KBです。しかし、POWER64のような一部のアーキテクチャでは、より大きなページサイズ（この場合は64KB）を使用することがあります。Goのリンカやランタイムがこの違いを認識しないと、メモリのアライメントの問題や、`mmap`（メモリマップドファイル）などのシステムコールが正しく機能しない問題が発生します。これにより、プログラムのクラッシュやパフォーマンスの低下を招く可能性があります。
2.  **システムコールエラー番号の処理**: Linuxカーネルのシステムコールは、成功時には非負の値を返し、エラー時には負のerrno値を返します。しかし、POWER64アーキテクチャにおける特定のシステムコール実装では、エラー番号が正の値として返される場合があります。Goのランタイムがこれを負の値として期待している場合、誤ったエラー処理が行われ、プログラムが予期せぬ動作をする原因となります。
3.  **`math/big`パッケージの最適化不足**: `math/big`パッケージは、任意精度の算術演算を提供するGoの標準ライブラリです。パフォーマンスが重要なため、多くの場合、特定のアーキテクチャ向けにアセンブリ言語で最適化された実装（スタブ）が提供されます。POWER64アーキテクチャでは、これらの最適化されたスタブが不足しており、汎用的なGoコードが使用されることで、性能が低下していました。このコミットは、これらのスタブを導入し、将来的な最適化の基盤を築くことを目的としています。

これらの問題に対処することで、Go言語がPOWER64アーキテクチャ上でより安定し、効率的に動作するようになります。

## 前提知識の解説

このコミットの理解を深めるために、いくつかの技術的な前提知識を解説します。

1.  **POWER64アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、高性能なサーバーやスーパーコンピュータで広く利用されています。
    *   x86とは異なる命令セット、レジスタ構成、メモリ管理ユニット（MMU）の特性を持ちます。
    *   特に、メモリページサイズがx86の4KBとは異なり、64KBやそれ以上のサイズをサポートすることが一般的です。これは、OSがメモリを管理する最小単位であり、プログラムのメモリ割り当てやアクセスに影響を与えます。

2.  **ELF (Executable and Linkable Format)**:
    *   Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。
    *   プログラムがメモリにロードされる際のアライメントやセグメントの配置に関する情報を含んでいます。
    *   `ELF rounding`とは、ELFファイル内のセクションやセグメントが、特定のメモリ境界（通常はページサイズ）にアラインされるように調整するプロセスを指します。これにより、OSが効率的にプログラムをメモリにロードできるようになります。

3.  **`mmap` (Memory-mapped file)**:
    *   Unix系システムコールの一つで、ファイルやデバイスをプロセスのアドレス空間に直接マッピングするために使用されます。
    *   これにより、ファイルの内容を通常のメモリ操作（ポインタのデリファレンスなど）で読み書きできるようになり、I/O操作の効率化やプロセス間通信に利用されます。
    *   `mmap quantum`とは、`mmap`システムコールがメモリを割り当てる際の最小単位、またはアライメントの単位を指します。これも通常はシステムのページサイズに依存します。

4.  **Go言語の`math/big`パッケージ**:
    *   Goの標準ライブラリの一部で、任意精度の整数（`Int`）、有理数（`Rat`）、浮動小数点数（`Float`）を扱うための機能を提供します。
    *   通常のGoの数値型（`int64`など）では表現できない非常に大きな数や、高い精度が求められる計算に使用されます。
    *   パフォーマンスを向上させるため、一部の基本的な算術演算（例: 乗算、除算、加算、減算）は、特定アーキテクチャ向けにアセンブリ言語で最適化された実装（スタブ）を持つことがあります。これらのスタブは、Goの汎用実装よりも高速に動作します。

5.  **システムコールとエラー番号**:
    *   システムコールは、ユーザー空間のプログラムがOSカーネルのサービス（ファイルI/O、メモリ管理、プロセス制御など）を要求するためのインターフェースです。
    *   システムコールがエラーを返した場合、通常は負の整数値（例: `-EACCES`、`-ENOMEM`）としてエラー番号（errno）が返されます。これらのエラー番号は、`errno.h`で定義されている正の定数に対応しています。
    *   Goのランタイムや`syscall`パッケージは、これらのカーネルからの戻り値を解釈し、Goのエラーインターフェースに変換します。この変換ロジックがアーキテクチャ固有の挙動に対応していないと、誤ったエラーが報告される可能性があります。

## 技術的詳細

このコミットは、POWER64アーキテクチャにおけるGoの動作を改善するために、以下の3つの主要な技術的問題に対処しています。

1.  **ページサイズとメモリ管理の調整**:
    *   **問題**: 従来のGoランタイムは、デフォルトで4KBのページサイズを前提としていました。しかし、POWER64環境ではハードウェアのページサイズが64KBであるため、リンカが生成するELFバイナリのアライメントや、ランタイムが`mmap`でメモリを確保する際の単位が、実際のハードウェアの要件と一致しませんでした。これにより、メモリの無駄や、`mmap`が期待通りに動作しない（例えば、指定したアドレスにマッピングできない）といった問題が発生していました。
    *   **解決策**:
        *   `src/cmd/9l/obj.c`において、ELFの初期データセクションの丸めサイズ`INITRND`を`4096`（4KB）から`0x10000`（64KB）に変更しました。これにより、リンカが生成するバイナリが64KB境界に適切にアラインされるようになります。
        *   `src/pkg/runtime/arch_power64.h`において、物理ページサイズ`PhysPageSize`を`4096`から`65536`（64KB）に更新しました。これはランタイムがメモリ管理を行う上で参照する重要な定数です。
        *   `src/pkg/runtime/mem_linux.c`において、ランタイム内部で使用されるページサイズ定数`_PAGE_SIZE`をハードコードされた`4096`から、アーキテクチャ定義の`PhysPageSize`を参照するように変更しました。これにより、ランタイムのメモリ割り当てロジックが正しいページサイズで動作するようになります。
        *   `mmap_fixed`関数における`mmap`の再試行ロジックを修正しました。`MAP_FIXED`フラグなしで`mmap`が失敗した場合、アドレス空間が解放されていることを確認した上で`MAP_FIXED`付きで再試行するようになっています。これは、一部のシステムで`MAP_FIXED`なしの`mmap`が`v`を無視する挙動に対応するためです。

2.  **システムコールエラー番号の処理の修正**:
    *   **問題**: Linuxカーネルのシステムコールは、エラー時に負のerrno値を返しますが、POWER64アーキテクチャの特定のシステムコール実装では、エラー番号が正の値として返されることがありました。Goのランタイムや`syscall`パッケージのアセンブリコードでは、システムコールからの戻り値がエラーを示す負の値である場合に、それを正のerrno値に変換するために`NEG R3, R3`（R3レジスタの値を負にする）という命令を使用していました。この命令が、すでに正の値として返されたエラー番号に対して実行されると、誤って負の値に変換されてしまい、Go側で正しくエラーを識別できない問題が発生していました。
    *   **解決策**:
        *   `src/pkg/runtime/sys_linux_power64x.s`と`src/pkg/syscall/asm_linux_power64x.s`内のシステムコールラッパーにおいて、システムコールからの戻り値がエラーを示す場合に実行されていた`NEG R3, R3`命令を削除しました。これにより、カーネルから返されたエラー番号が正の値であっても、そのままGo側に渡され、正しいエラー処理が可能になります。
        *   `src/pkg/runtime/mem_linux.c`の`addrspace_free`関数において、`mincore`システムコールからの戻り値のチェックを修正しました。`errval != -ENOMEM`だけでなく、`errval != ENOMEM`も考慮するように変更し、正の値として返される`ENOMEM`エラーにも対応しました。

3.  **`math/big`パッケージのスタブ実装**:
    *   **問題**: `math/big`パッケージは、任意精度の算術演算を提供しますが、POWER64アーキテクチャ向けに最適化されたアセンブリ実装が不足していました。これにより、Goの汎用実装が使用され、パフォーマンスが低下していました。
    *   **解決策**:
        *   `src/pkg/math/big/arith_power64x.s`という新しいアセンブリファイルが追加されました。このファイルは、`mulWW`、`divWW`、`addVV`、`subVV`など、`math/big`パッケージの基本的な算術演算に対するスタブ（プレースホルダー）実装を提供します。
        *   これらのスタブは、現時点では対応するGoの汎用実装（例: `mulWW_g`）にジャンプするだけですが、これにより将来的にPOWER64アーキテクチャ固有の最適化されたアセンブリコードを容易に導入できる基盤が整いました。

これらの修正により、Go言語はPOWER64アーキテクチャ上でより堅牢かつ効率的に動作するようになります。

## コアとなるコードの解説

### 1. リンカのELF丸めサイズ (`src/cmd/9l/obj.c`)

```c
    		if(INITRND == -1)
    			INITRND = 0x10000; // 64KB
```
この変更は、Goのリンカ（`9l`）が生成するELF実行可能ファイルのセクションアライメントを制御します。以前は`INITRND`が4KB（`4096`）に設定されていましたが、POWER64アーキテクチャのハードウェアページサイズが64KBであることに合わせて、`0x10000`（16進数で65536、つまり64KB）に変更されました。これにより、生成されるバイナリが64KB境界に適切にアラインされ、OSがメモリにロードする際の効率が向上し、潜在的なアライメント関連の問題が解消されます。

### 2. `math/big`パッケージのPOWER64向けアセンブリスタブ (`src/pkg/math/big/arith_power64x.s`)

```assembly
TEXT ·mulWW(SB),NOSPLIT,$0
	BR ·mulWW_g(SB)

TEXT ·divWW(SB),NOSPLIT,$0
	BR ·divWW_g(SB)
...
```
この新規ファイルは、`math/big`パッケージ内の基本的な算術演算（例: `mulWW`、`divWW`）に対するPOWER64アーキテクチャ固有のアセンブリスタブを提供します。`BR ·mulWW_g(SB)`という命令は、単に対応するGoの汎用実装（`_g`サフィックスが付いている関数）に分岐するだけです。現時点では最適化されたアセンブリコードは含まれていませんが、このスタブの導入により、将来的にPOWER64の特定の命令セットを活用した高性能なアセンブリ実装を容易に追加できる基盤が確立されました。これにより、`math/big`パッケージの計算性能が向上する可能性があります。

### 3. ランタイムの物理ページサイズ定義 (`src/pkg/runtime/arch_power64.h`)

```c
enum {
	// ...
	PhysPageSize = 65536, // 64KB
	// ...
};
```
`PhysPageSize`は、Goランタイムが物理メモリのページサイズを認識するための重要な定数です。以前は4KBに設定されていましたが、POWER64の実際のハードウェアページサイズである64KB（`65536`）に修正されました。この変更は、ランタイムのメモリ管理（ガベージコレクション、メモリ割り当てなど）が、基盤となるハードウェアの特性に合わせて正確に動作するために不可欠です。

### 4. ランタイムのメモリ管理と`mmap`の修正 (`src/pkg/runtime/mem_linux.c`)

```c
enum
{
	_PAGE_SIZE = PhysPageSize, // ハードコードされた4KBからPhysPageSizeを参照
	// ...
};

// addrspace_free 関数内の mincore エラーチェック
if (errval != -ENOMEM && errval != ENOMEM) {
    return 0;
}

// mmap_fixed 関数内の mmap 再試行ロジック
if(p != v) {
    if(p > (void*)4096) { // 割り当てられたアドレスが有効な場合
        runtime·munmap(p, n); // 以前のmmapを解除
        p = nil;
    }
    // アドレス空間が解放されていることを確認してからMAP_FIXEDで再試行
    if(addrspace_free(v, n))
        p = runtime·mmap(v, n, prot, flags|MAP_FIXED, fd, offset);
}
```
*   **`_PAGE_SIZE`の変更**: ランタイム内部で使用される`_PAGE_SIZE`定数が、ハードコードされた4KBから、アーキテクチャ定義の`PhysPageSize`を参照するように変更されました。これにより、ランタイムのメモリ割り当てやアライメント計算が、POWER64の実際のページサイズに基づいて行われるようになります。
*   **`mincore`エラーチェックの修正**: `addrspace_free`関数は、指定されたメモリ領域がマップされているかどうかを確認するために`mincore`システムコールを使用します。`mincore`は、マップされていないページに対して`ENOMEM`エラーを返します。このコミットでは、`errval != -ENOMEM`だけでなく、`errval != ENOMEM`もチェックするように修正されました。これは、POWER64環境で`mincore`が正の`ENOMEM`を返す可能性があるため、両方のケースに対応することで、メモリ領域の解放状態を正確に判断できるようにするためです。

### 5. システムコールエラー番号の負号化の削除 (`src/pkg/runtime/sys_linux_power64x.s` および `src/pkg/syscall/asm_linux_power64x.s`)

このコミットは、Go言語がIBMのPOWER64アーキテクチャ上で適切に動作するための重要な修正を含んでいます。当時のGo言語のランタイムは、主にx86アーキテクチャを念頭に設計されており、ページサイズやシステムコールからの戻り値の規約など、他のアーキテクチャ固有の特性に対応しきれていない部分がありました。

具体的な背景は以下の通りです。

1.  **ハードウェアページサイズの不一致**: 多くの一般的なシステム（x86など）では、メモリのページサイズは4KBです。しかし、POWER64のような一部のアーキテクチャでは、より大きなページサイズ（この場合は64KB）を使用することがあります。Goのリンカやランタイムがこの違いを認識しないと、メモリのアライメントの問題や、`mmap`（メモリマップドファイル）などのシステムコールが正しく機能しない問題が発生します。これにより、プログラムのクラッシュやパフォーマンスの低下を招く可能性があります。
2.  **システムコールエラー番号の処理**: Linuxカーネルのシステムコールは、成功時には非負の値を返し、エラー時には負のerrno値を返します。しかし、POWER64アーキテクチャにおける特定のシステムコール実装では、エラー番号が正の値として返される場合があります。Goのランタイムがこれを負の値として期待している場合、誤ったエラー処理が行われ、プログラムが予期せぬ動作をする原因となります。
3.  **`math/big`パッケージの最適化不足**: `math/big`パッケージは、任意精度の算術演算を提供するGoの標準ライブラリです。パフォーマンスが重要なため、多くの場合、特定のアーキテクチャ向けにアセンブリ言語で最適化された実装（スタブ）が提供されます。POWER64アーキテクチャでは、これらの最適化されたスタブが不足しており、汎用的なGoコードが使用されることで、性能が低下していました。このコミットは、これらのスタブを導入し、将来的な最適化の基盤を築くことを目的としています。

これらの問題に対処することで、Go言語がPOWER64アーキテクチャ上でより安定し、効率的に動作するようになります。

## 前提知識の解説

このコミットの理解を深めるために、いくつかの技術的な前提知識を解説します。

1.  **POWER64アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、高性能なサーバーやスーパーコンピュータで広く利用されています。
    *   x86とは異なる命令セット、レジスタ構成、メモリ管理ユニット（MMU）の特性を持ちます。
    *   特に、メモリページサイズがx86の4KBとは異なり、64KBやそれ以上のサイズをサポートすることが一般的です。これは、OSがメモリを管理する最小単位であり、プログラムのメモリ割り当てやアクセスに影響を与えます。

2.  **ELF (Executable and Linkable Format)**:
    *   Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。
    *   プログラムがメモリにロードされる際のアライメントやセグメントの配置に関する情報を含んでいます。
    *   `ELF rounding`とは、ELFファイル内のセクションやセグメントが、特定のメモリ境界（通常はページサイズ）にアラインされるように調整するプロセスを指します。これにより、OSが効率的にプログラムをメモリにロードできるようになります。

3.  **`mmap` (Memory-mapped file)**:
    *   Unix系システムコールの一つで、ファイルやデバイスをプロセスのアドレス空間に直接マッピングするために使用されます。
    *   これにより、ファイルの内容を通常のメモリ操作（ポインタのデリファレンスなど）で読み書きできるようになり、I/O操作の効率化やプロセス間通信に利用されます。
    *   `mmap quantum`とは、`mmap`システムコールがメモリを割り当てる際の最小単位、またはアライメントの単位を指します。これも通常はシステムのページサイズに依存します。

4.  **Go言語の`math/big`パッケージ**:
    *   Goの標準ライブラリの一部で、任意精度の整数（`Int`）、有理数（`Rat`）、浮動小数点数（`Float`）を扱うための機能を提供します。
    *   通常のGoの数値型（`int64`など）では表現できない非常に大きな数や、高い精度が求められる計算に使用されます。
    *   パフォーマンスを向上させるため、一部の基本的な算術演算（例: 乗算、除算、加算、減算）は、特定アーキテクチャ向けにアセンブリ言語で最適化された実装（スタブ）を持つことがあります。これらのスタブは、Goの汎用実装よりも高速に動作します。

5.  **システムコールとエラー番号**:
    *   システムコールは、ユーザー空間のプログラムがOSカーネルのサービス（ファイルI/O、メモリ管理、プロセス制御など）を要求するためのインターフェースです。
    *   システムコールがエラーを返した場合、通常は負の整数値（例: `-EACCES`、`-ENOMEM`）としてエラー番号（errno）が返されます。これらのエラー番号は、`errno.h`で定義されている正の定数に対応しています。
    *   Goのランタイムや`syscall`パッケージは、これらのカーネルからの戻り値を解釈し、Goのエラーインターフェースに変換します。この変換ロジックがアーキテクチャ固有の挙動に対応していないと、誤ったエラーが報告される可能性があります。

この変更は、Goのリンカ（`9l`）が生成するELF実行可能ファイルのセクションアライメントを制御します。以前は`INITRND`が4KB（`4096`）に設定されていましたが、POWER64アーキテクチャのハードウェアページサイズが64KBであることに合わせて、`0x10000`（16進数で65536、つまり64KB）に変更されました。これにより、生成されるバイナリが64KB境界に適切にアラインされ、OSがメモリにロードする際の効率が向上し、潜在的なアライメント関連の問題が解消されます。

### 2. `math/big`パッケージのPOWER64向けアセンブリスタブ (`src/pkg/math/big/arith_power64x.s`)

```assembly
TEXT ·mulWW(SB),NOSPLIT,$0
	BR ·mulWW_g(SB)

TEXT ·divWW(SB),NOSPLIT,$0
	BR ·divWW_g(SB)
...
```
この新規ファイルは、`math/big`パッケージ内の基本的な算術演算（例: `mulWW`、`divWW`）に対するPOWER64アーキテクチャ固有のアセンブリスタブを提供します。`BR ·mulWW_g(SB)`という命令は、単に対応するGoの汎用実装（`_g`サフィックスが付いている関数）に分岐するだけです。現時点では最適化されたアセンブリコードは含まれていませんが、このスタブの導入により、将来的にPOWER64の特定の命令セットを活用した高性能なアセンブリ実装を容易に追加できる基盤が確立されました。これにより、`math/big`パッケージの計算性能が向上する可能性があります。

### 3. ランタイムの物理ページサイズ定義 (`src/pkg/runtime/arch_power64.h`)

```c
enum {
	// ...
	PhysPageSize = 65536, // 64KB
	// ...
};
```
`PhysPageSize`は、Goランタイムが物理メモリのページサイズを認識するための重要な定数です。以前は4KBに設定されていましたが、POWER64の実際のハードウェアページサイズである64KB（`65536`）に修正されました。この変更は、ランタイムのメモリ管理（ガベージコレクション、メモリ割り当てなど）が、基盤となるハードウェアの特性に合わせて正確に動作するために不可欠です。

### 4. ランタイムのメモリ管理と`mmap`の修正 (`src/pkg/runtime/mem_linux.c`)

```c
enum
{
	_PAGE_SIZE = PhysPageSize, // ハードコードされた4KBからPhysPageSizeを参照
	// ...
};

// addrspace_free 関数内の mincore エラーチェック
if (errval != -ENOMEM && errval != ENOMEM) {
    return 0;
}

// mmap_fixed 関数内の mmap 再試行ロジック
if(p != v) {
    if(p > (void*)4096) { // 割り当てられたアドレスが有効な場合
        runtime·munmap(p, n); // 以前のmmapを解除
        p = nil;
    }
    // アドレス空間が解放されていることを確認してからMAP_FIXEDで再試行
    if(addrspace_free(v, n))
        p = runtime·mmap(v, n, prot, flags|MAP_FIXED, fd, offset);
}
```
*   **`_PAGE_SIZE`の変更**: ランタイム内部で使用される`_PAGE_SIZE`定数が、ハードコードされた4KBから、アーキテクチャ定義の`PhysPageSize`を参照するように変更されました。これにより、ランタイムのメモリ割り当てやアライメント計算が、POWER64の実際のページサイズに基づいて行われるようになります。
*   **`mincore`エラーチェックの修正**: `addrspace_free`関数は、指定されたメモリ領域がマップされているかどうかを確認するために`mincore`システムコールを使用します。`mincore`は、マップされていないページに対して`ENOMEM`エラーを返します。このコミットでは、`errval != -ENOMEM`だけでなく、`errval != ENOMEM`もチェックするように修正されました。これは、POWER64環境で`mincore`が正の`ENOMEM`を返す可能性があるため、両方のケースに対応することで、メモリ領域の解放状態を正確に判断できるようにするためです。
*   **`mmap_fixed`の再試行ロジック**: `mmap_fixed`関数は、特定の仮想アドレスにメモリをマップしようとします。一部のシステムでは、`MAP_FIXED`フラグなしで`mmap`を呼び出した際に、指定されたアドレス`v`が無視され、別の場所が割り当てられることがあります。この修正では、`p != v`（指定したアドレスにマップされなかった場合）かつ、割り当てられたアドレス`p`が有効な場合（`p > (void*)4096`）、まずその割り当てを解除し、その後`addrspace_free`でアドレス空間が解放されていることを確認した上で、`MAP_FIXED`フラグを付けて`mmap`を再試行するように変更されました。これにより、`mmap_fixed`が意図した通りに動作し、メモリの断片化を防ぎ、予測可能なメモリレイアウトを維持できるようになります。

### 5. システムコールエラー番号の負号化の削除 (`src/pkg/runtime/sys_linux_power64x.s` および `src/pkg/syscall/asm_linux_power64x.s`)

```assembly
// runtime·mmap の例
	SYSCALL
	BVC	2(PC) // キャリーフラグがクリア（エラーなし）ならスキップ
//	NEG	R3, R3 // この行が削除された
	RETURN

// syscall·Syscall の例
	SYSCALL R9
	BVC	ok // キャリーフラグがクリア（エラーなし）ならスキップ
//	NEG	R3, R3 // この行が削除された
	MOVD	$-1, R4
	MOVD	R4, r1+32(FP)	// r1
	MOVD	R0, r2+40(FP)	// r2
```
これらのアセンブリコードの変更は、Goのランタイムおよび`syscall`パッケージがシステムコールからの戻り値を処理する方法に影響します。以前は、システムコールがエラーを返した場合（通常、キャリーフラグがセットされる）、戻り値（R3レジスタ）が負の値（errno）に変換されることを期待して`NEG R3, R3`命令が実行されていました。しかし、POWER64アーキテクチャでは、カーネルがエラー番号を正の値として返す場合があるため、この`NEG`命令が誤って正のエラー番号を負にしてしまい、Go側でエラーが正しく認識されない問題が発生していました。

`NEG R3, R3`命令を削除することで、システムコールから返されたエラー番号が正の値であっても、そのままGo側に渡されるようになります。これにより、Goのランタイムと`syscall`パッケージは、POWER64環境におけるカーネルのシステムコール規約に正しく準拠し、エラー処理の正確性が向上します。

# [インデックス 22862] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおけるPlan 9固有の挙動を修正するものです。具体的には、Plan 9環境でGoプログラムが動作する際に、ワーキングディレクトリ（カレントディレクトリ）の管理に関する問題を解決します。Goはプログラム全体で単一のワーキングディレクトリを期待しますが、Plan 9ではゴルーチンが異なるプロセスで実行され、それぞれが独立したワーキングディレクトリを持つことがあります。この不整合を解消するために`fixwd`関数が使用されますが、その中で`getwd`（現在のワーキングディレクトリを取得するシステムコール）がエラーを返した場合に、ワーキングディレクトリの修正処理が中断されてしまう問題がありました。このコミットは、`getwd`がエラーを返してもワーキングディレクトリの修正処理を継続するように変更することで、この問題を解決します。

## コミット

## 変更の背景

この変更の背景には、Go言語のランタイムがワーキングディレクトリをプログラム全体で一貫して管理しようとする設計と、Plan 9オペレーティングシステムのプロセスモデルとの間の不整合があります。

Go言語では、プログラムの実行中にワーキングディレクトリが単一のグローバルな状態として扱われることを期待します。多くのシステムコール（例えば、相対パスでファイルを開く操作など）は、このワーキングディレクトリに依存して動作します。

しかし、Plan 9では、ゴルーチン（Goの軽量スレッド）が異なるOSプロセスとして実行されることがあり、これらのプロセスはそれぞれ独自のワーキングディレクトリを持つことができます。これにより、あるゴルーチンがワーキングディレクトリを変更したり、あるいはワーキングディレクトリ自体が外部から削除されたりした場合に、他のゴルーチンが予期しないワーキングディレクトリを参照してしまう可能性がありました。

この問題を解決するため、Goの`syscall`パッケージには`fixwd`（`fixwdLocked`）という関数が存在します。この関数は、ワーキングディレクトリに依存するシステムコールを呼び出す前に、Goが期待するワーキングディレクトリの状態に強制的に戻す役割を担っています。

しかし、従来の`fixwdLocked`の実装では、`getwd()`（現在のワーキングディレクトリを取得するシステムコール）がエラーを返した場合に、それ以降のワーキングディレクトリ修正処理（`chdir`による変更）がスキップされていました。コミットメッセージによると、この`getwd()`のエラーは、特にワーキングディレクトリが別のプロセスによって削除された場合に発生する可能性がありました。`getwd()`がエラーを返すと、`fixwdLocked`は早期にリターンしてしまい、結果としてワーキングディレクトリが修正されないままとなり、後続のシステムコールが失敗する原因となっていました。

このコミットは、この特定のシナリオ（`getwd()`がエラーを返す場合）においても、`fixwdLocked`がワーキングディレクトリの修正を試みるようにすることで、Goプログラムの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

*   **Plan 9 (オペレーティングシステム)**:
    *   ベル研究所で開発された分散型オペレーティングシステムです。Unixの思想をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルとして表現し、ファイルシステムを通じてアクセスするという特徴を持ちます。
    *   重要な点として、Plan 9ではプロセスが軽量であり、各プロセスが独立したワーキングディレクトリを持つことが一般的です。これは、Unix系システムでプロセスが親からワーキングディレクトリを継承し、通常は共有されるのとは対照的です。
*   **Go言語のゴルーチン (Goroutines)**:
    *   Go言語における軽量な並行処理の単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行することも可能です。
    *   Goランタイムは、これらのゴルーチンをOSスレッドにマッピングして実行します。Plan 9のような特定のOS環境では、Goランタイムがゴルーチンを異なるOSプロセスにマッピングすることがあり、これがワーキングディレクトリの不整合を引き起こす原因となります。
*   **ワーキングディレクトリ (Working Directory / Current Directory)**:
    *   プログラムがファイルやディレクトリを相対パスで参照する際に基準となるディレクトリです。例えば、`open("foo.txt")`とすると、現在のワーキングディレクトリにある`foo.txt`が開かれようとします。
    *   多くのシステムコールはワーキングディレクトリに依存するため、その状態の一貫性はプログラムの正確な動作にとって非常に重要です。
*   **`syscall`パッケージ (Go言語)**:
    *   Go言語の標準ライブラリの一部で、低レベルなオペレーティングシステム機能（システムコール）へのアクセスを提供します。ファイル操作、プロセス管理、ネットワーク通信など、OSと直接やり取りする際に使用されます。
    *   このコミットで変更される`pwd_plan9.go`は、Plan 9環境におけるパスワード（pwd: print working directory）関連のシステムコールを扱う部分です。
*   **`getwd()` システムコール**:
    *   現在のワーキングディレクトリのパスを取得するシステムコールです。多くのOSで同等の機能が提供されています。
*   **`chdir()` システムコール**:
    *   現在のワーキングディレクトリを変更するシステムコールです。

これらの前提知識を踏まえると、Goが期待する「プログラム全体で単一のワーキングディレクトリ」というモデルと、Plan 9の「プロセスごとの独立したワーキングディレクトリ」というモデルの間のギャップを埋めるために、`fixwd`のような機構が必要であることが理解できます。

## 技術的詳細

このコミットが解決しようとしている技術的な問題は、`fixwdLocked`関数内のエラーハンドリングのロジックにありました。

`fixwdLocked`関数は、Goプログラムが期待するワーキングディレクトリ（`wdStr`に格納されている）と現在の実際のワーキングディレクトリが異なる場合に、`chdir`システムコールを使ってワーキングディレクトリを修正することを目的としています。この修正処理の前に、現在のワーキングディレクトリを取得するために`getwd()`が呼び出されます。

問題は、従来のコードが以下のようになっていた点です。

```go
wd, err := getwd()
if err != nil {
    return // getwdがエラーを返したら、ここで関数を終了
}
// ... ワーキングディレクトリの比較とchdir ...
```

このロジックでは、`getwd()`がエラーを返した場合、`fixwdLocked`関数全体がそこで終了してしまい、`chdir`によるワーキングディレクトリの修正が全く行われませんでした。

コミットメッセージが指摘するように、`getwd()`がエラーを返すケースとして「ディレクトリが別のプロセスによって以前に削除された場合」が挙げられます。このような状況では、現在のワーキングディレクトリは無効な状態にあり、まさに`chdir`によって正しいワーキングディレクトリに設定し直す必要があるにもかかわらず、エラーハンドリングのロジックがそれを妨げていました。

このコミットによる修正は、このエラーハンドリングのロジックを変更し、`getwd()`がエラーを返しても`fixwdLocked`関数が終了しないようにすることです。

```go
// always call chdir when getwd returns an error
wd, _ := getwd() // エラーを無視
// ... ワーキングディレクトリの比較とchdir ...
```

変更後、`getwd()`がエラーを返した場合でも、そのエラーは`_`（ブランク識別子）に代入されて無視され、関数は続行されます。このとき、`wd`変数には`getwd()`が成功した場合のパス、またはエラーが発生した場合はGoのデフォルト値（通常は空文字列`""`）が代入されます。

その後のロジックでは、`wd`と`wdStr`（Goが期待するワーキングディレクトリ）が比較されます。
*   もし`getwd()`が成功し、`wd`が`wdStr`と同じであれば、ワーキングディレクトリは既に正しいので何もせずリターンします。
*   もし`getwd()`が成功したが、`wd`が`wdStr`と異なる場合、`chdir(wdStr)`が呼び出されてワーキングディレクトリが修正されます。
*   **重要な点として、`getwd()`がエラーを返した場合（`wd`が空文字列などになる場合）でも、`wd`と`wdStr`は異なるため、必ず`chdir(wdStr)`が呼び出されることになります。** これが、たとえ現在のワーキングディレクトリが不正な状態であっても、Goが期待するワーキングディレクトリに強制的に設定し直すという目的を達成するための鍵となります。

この修正により、Plan 9環境におけるGoプログラムのワーキングディレクトリ管理がより堅牢になり、特にディレクトリが外部から変更または削除されたようなエッジケースにおいても、プログラムが期待通りに動作するようになります。

## コアとなるコードの変更箇所

変更は`src/syscall/pwd_plan9.go`ファイル内の`fixwdLocked`関数にあります。

```diff
--- a/src/syscall/pwd_plan9.go
+++ b/src/syscall/pwd_plan9.go
@@ -29,10 +29,8 @@ func fixwdLocked() {\n 	if !wdSet {\n 		return\n 	}\n-	wd, err := getwd()\n-	if err != nil {\n-		return\n-	}\n+	// always call chdir when getwd returns an error\n+	wd, _ := getwd()\n 	if wd == wdStr {\n 		return\n 	}\n```

具体的には、以下の行が変更されました。

1.  `wd, err := getwd()` が `wd, _ := getwd()` に変更されました。これにより、`getwd()`が返すエラー値が明示的に破棄されるようになりました。
2.  その直後のエラーチェック `if err != nil { return }` が削除されました。これにより、`getwd()`がエラーを返しても関数が早期に終了しなくなりました。
3.  新しいコメント `// always call chdir when getwd returns an error` が追加され、変更の意図が明確に示されています。

## コアとなるコードの解説

変更前のコードでは、`getwd()`の呼び出し結果としてエラーが発生した場合、`fixwdLocked`関数は即座にリターンしていました。これは、現在のワーキングディレクトリの取得に失敗したため、それ以上の処理は無意味である、あるいは安全ではないという判断に基づいていた可能性があります。

しかし、Plan 9の特性（異なるプロセスがワーキングディレクトリを共有しない、ディレクトリが外部から削除されうる）を考慮すると、この早期リターンは問題を引き起こしました。`getwd()`がエラーを返す状況（例: 参照しているディレクトリが既に存在しない）こそ、`chdir`によってGoが期待する正しいワーキングディレクトリに設定し直す必要がある状況だったからです。

変更後のコードでは、`wd, _ := getwd()`とすることで、`getwd()`が返すエラーを意図的に無視しています。これにより、`getwd()`が成功しようが失敗しようが、その後の`if wd == wdStr`の比較と、必要に応じた`chdir(wdStr)`の呼び出しが必ず実行されるようになります。

*   `getwd()`が成功した場合：`wd`には現在の正しいワーキングディレクトリが格納されます。`wd`が`wdStr`と異なれば`chdir(wdStr)`が実行されます。
*   `getwd()`が失敗した場合：`wd`にはGoのゼロ値（文字列の場合は空文字列`""`）が格納されます。この場合、`wd`は`wdStr`（Goが期待するワーキングディレクトリのパス）と異なるため、必ず`chdir(wdStr)`が実行されます。

この変更により、`fixwdLocked`は、現在のワーキングディレクトリの状態がどうであれ、常にGoが期待するワーキングディレクトリに設定し直す試みを行うようになり、Plan 9環境でのワーキングディレクトリ管理の堅牢性が大幅に向上しました。

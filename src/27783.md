## 変更の背景

Go言語のリンカは、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する重要なツールです。このプロセスでは、プログラム内のすべてのシンボル（関数、変数など）に関する情報をメモリ上に保持する必要があります。

以前のリンカの実装では、`LSym` (Linker Symbol) 構造体が、関数だけでなくデータシンボルなど、あらゆる種類のシンボル情報を保持していました。しかし、`Args` (関数の引数サイズ)、`Locals` (関数のローカル変数サイズ)、`Autom` (自動変数、つまりローカル変数や引数に関する情報) といったフィールドは、実際には関数シンボルにのみ意味を持つ情報でした。データシンボルやその他の非関数シンボルにとっては、これらのフィールドは常にゼロ値または空の状態で存在し、メモリを無駄に消費していました。

このコミットの背景には、リンカのメモリフットプリントを最適化し、大規模なGoプログラムのリンク時間を短縮するという目的があります。関数にのみ関連する情報を専用の構造体 (`Pcln`) に分離することで、非関数シンボルがこれらの不要なフィールドを持つことを避け、リンカ全体のメモリ使用量を削減できます。コミットメッセージに示されたMaxRSSの削減（約6%）は、この最適化が成功したことを明確に示しています。

## 前提知識の解説

このコミットを理解するためには、Go言語のツールチェイン、特にリンカの内部構造に関するいくつかの概念を理解しておく必要があります。

*   **Goリンカ (`cmd/link`)**: Goコンパイラ (`cmd/compile`) が生成したオブジェクトファイル (`.o` ファイル) を受け取り、必要なライブラリと結合して、最終的な実行可能ファイルや共有ライブラリを生成するツールです。シンボル解決、再配置、コード生成、デバッグ情報の埋め込みなど、多くの複雑な処理を行います。
*   **`LSym` (Linker Symbol)**: リンカが扱うすべてのシンボル（関数、グローバル変数、型情報など）を表す内部データ構造です。各 `LSym` インスタンスは、シンボルの名前、アドレス、サイズ、型、関連するセクションなどの情報を含みます。リンカはこれらの `LSym` オブジェクトのグラフを構築し、プログラム全体の構造を表現します。
*   **`Pcln` (PC-line table)**: "Program Counter to Line number" テーブルの略で、Goランタイムがスタックトレースを生成したり、デバッガがソースコードの行番号を解決したりするために使用するメタデータです。各関数には、その関数の命令アドレス (Program Counter) とソースコードの行番号とのマッピング、スタックフレームのサイズ、引数とローカル変数の情報などが含まれる `Pcln` データが関連付けられています。これは実行可能ファイル内の `.gopclntab` セクションに格納されます。
*   **`Args` (引数サイズ)**: 関数の引数領域の合計サイズ（バイト単位）を示します。
*   **`Locals` (ローカル変数サイズ)**: 関数のローカル変数領域の合計サイズ（バイト単位）を示します。
*   **`Autom` (自動変数)**: 関数のローカル変数や引数に関する詳細情報（名前、オフセット、型など）を格納するスライスです。これはデバッグ情報やガベージコレクションの目的で使用されます。
*   **`obj.STEXT`**: `LSym` の `Type` フィールドが `obj.STEXT` である場合、そのシンボルが関数（テキストセクションのコード）であることを示します。

## 技術的詳細

このコミットの核心は、`LSym` 構造体と `Pcln` 構造体の間の責任分担を明確化し、データ構造を最適化することにあります。

以前は、`LSym` 構造体は以下のようなフィールドを持っていました（簡略化）：

```go
type LSym struct {
    // ... 共通のシンボル情報 ...
    Args        int32  // 関数の引数サイズ
    Locals      int32  // 関数のローカル変数サイズ
    Autom       []Auto // 自動変数情報
    Pcln        *Pcln  // PC-line情報へのポインタ
    // ... その他のフィールド ...
}
```

この設計では、データシンボルなど関数ではない `LSym` インスタンスも `Args`, `Locals`, `Autom` フィールドを持っていましたが、これらは常にゼロまたは空であり、メモリを無駄にしていました。

このコミットでは、これらの関数に特化したフィールドを `Pcln` 構造体へと移動させました。変更後の構造体は以下のようになります（簡略化）：

```go
type LSym struct {
    // ... 共通のシンボル情報 ...
    // Args, Locals, Autom は削除された
    Pcln        *Pcln  // PC-line情報へのポインタ
    // ... その他のフィールド ...
}

type Pcln struct {
    Args        int32  // 関数の引数サイズ
    Locals      int32  // 関数のローカル変数サイズ
    Autom       []Auto // 自動変数情報
    Pcsp        Pcdata
    Pcfile      Pcdata
    Pcline      Pcdata
    // ... その他のPcln関連フィールド ...
}
```

この変更により、`LSym` はより汎用的なシンボル情報のみを保持するようになり、関数シンボルである場合にのみ `Pcln` フィールドが非 `nil` となり、その `Pcln` 構造体を通じて関数固有の情報にアクセスするようになります。

**技術的な影響と変更点:**

1.  **メモリ効率の向上**: 非関数シンボルは `Args`, `Locals`, `Autom` のためのメモリを割り当てる必要がなくなります。これにより、リンカが処理するシンボル数が多いほど、全体的なメモリ使用量が削減されます。コミットメッセージのMaxRSS削減はこの効果を裏付けています。
2.  **コードの変更**: `LSym` の `Args`, `Locals`, `Autom` フィールドに直接アクセスしていたすべての箇所は、`s.Pcln.Args`, `s.Pcln.Locals`, `s.Pcln.Autom` のように `Pcln` ポインタを介してアクセスするように変更されました。
3.  **`Pcln` の初期化**: `objfile.go` でオブジェクトファイルを読み込む際、シンボルが関数 (`obj.STEXT`) である場合にのみ、新しい `Pcln` 構造体が割り当てられ、`LSym.Pcln` に設定されます。そして、読み込んだ `Args`, `Locals`, `Autom` の値は、直接 `LSym` に設定するのではなく、この新しく作成された `Pcln` 構造体に設定されます。
4.  **`nil` チェックの追加**: `LSym.Pcln` が `nil` である可能性があるため、`deadcode.go`, `dwarf.go`, `lib.go`, `pcln.go` など、`Pcln` のフィールドにアクセスする前に `s.Pcln != nil` のチェックが追加または考慮されています。これにより、非関数シンボルに対してこれらのフィールドにアクセスしようとした際のパニックを防ぎます。
5.  **データの一貫性**: このリファクタリングは、リンカの内部データモデルにおけるデータの一貫性と論理的な分離を改善します。関数固有のデータは関数固有の構造体にまとめられるため、コードの可読性と保守性が向上します。

*   **`LSym` (Linker Symbol)**: リンカが扱うすべてのシンボル（関数、グローバル変数、型情報など）を表す内部データ構造です。各 `LSym` インスタンスは、シンボルの名前、アドレス、サイズ、型、関連するセクションなどの情報を含みます。リンカはこれらの `LSym` オブジェクトのグラフを構築し、プログラム全体の構造を表現します。
*   **`Pcln` (PC-line table)**: "Program Counter to Line number" テーブルの略で、Goランタイムがスタックトレースを生成したり、デバッガがソースコードの行番号を解決したりするために使用するメタデータです。各関数には、その関数の命令アドレス (Program Counter) とソースコードの行番号とのマッピング、スタックフレームのサイズ、引数とローカル変数の情報などが含まれる `Pcln` データが関連付けられています。これは実行可能ファイル内の `.gopclntab` セクションに格納されます。
*   **`Args` (引数サイズ)**: 関数の引数領域の合計サイズ（バイト単位）を示します。
*   **`Locals` (ローカル変数サイズ)**: 関数のローカル変数領域の合計サイズ（バイト単位）を示します。
*   **`Autom` (自動変数)**: 関数のローカル変数や引数に関する詳細情報（名前、オフセット、型など）を格納するスライスです。これはデバッグ情報やガベージコレクションの目的で使用されます。
*   **`obj.STEXT`**: `LSym` の `Type` フィールドが `obj.STEXT` である場合、そのシンボルが関数（テキストセクションのコード）であることを示します。

## 技術的詳細

このコミットの核心は、`LSym` 構造体と `Pcln` 構造体の間の責任分担を明確化し、データ構造を最適化することにあります。

以前は、`LSym` 構造体は以下のようなフィールドを持っていました（簡略化）：

```go
type LSym struct {
    // ... 共通のシンボル情報 ...
    Args        int32  // 関数の引数サイズ
    Locals      int32  // 関数のローカル変数サイズ
    Autom       []Auto // 自動変数情報
    Pcln        *Pcln  // PC-line情報へのポインタ
    // ... その他のフィールド ...
}
```

この設計では、データシンボルなど関数ではない `LSym` インスタンスも `Args`, `Locals`, `Autom` フィールドを持っていましたが、これらは常にゼロまたは空であり、メモリを無駄にしていました。

このコミットでは、これらの関数に特化したフィールドを `Pcln` 構造体へと移動させました。変更後の構造体は以下のようになります（簡略化）：

```go
type LSym struct {
    // ... 共通のシンボル情報 ...
    // Args, Locals, Autom は削除された
    Pcln        *Pcln  // PC-line情報へのポインタ
    // ... その他のフィールド ...
}

type Pcln struct {
    Args        int32  // 関数の引数サイズ
    Locals      int32  // 関数のローカル変数サイズ
    Autom       []Auto // 自動変数情報
    Pcsp        Pcdata
    Pcfile      Pcdata
    Pcline      Pcdata
    // ... その他のPcln関連フィールド ...
}
```

この変更により、`LSym` はより汎用的なシンボル情報のみを保持するようになり、関数シンボルである場合にのみ `Pcln` フィールドが非 `nil` となり、その `Pcln` 構造体を通じて関数固有の情報にアクセスするようになります。

**技術的な影響と変更点:**

1.  **メモリ効率の向上**: 非関数シンボルは `Args`, `Locals`, `Autom` のためのメモリを割り当てる必要がなくなります。これにより、リンカが処理するシンボル数が多いほど、全体的なメモリ使用量が削減されます。コミットメッセージのMaxRSS削減はこの効果を裏付けています。
2.  **コードの変更**: `LSym` の `Args`, `Locals`, `Autom` フィールドに直接アクセスしていたすべての箇所は、`s.Pcln.Args`, `s.Pcln.Locals`, `s.Pcln.Autom` のように `Pcln` ポインタを介してアクセスするように変更されました。
3.  **`Pcln` の初期化**: `objfile.go` でオブジェクトファイルを読み込む際、シンボルが関数 (`obj.STEXT`) である場合にのみ、新しい `Pcln` 構造体が割り当てられ、`LSym.Pcln` に設定されます。そして、読み込んだ `Args`, `Locals`, `Autom` の値は、直接 `LSym` に設定するのではなく、この新しく作成された `Pcln` 構造体に設定されます。
4.  **`nil` チェックの追加**: `LSym.Pcln` が `nil` である可能性があるため、`deadcode.go`, `dwarf.go`, `lib.go`, `pcln.go` など、`Pcln` のフィールドにアクセスする前に `s.Pcln != nil` のチェックが追加または考慮されています。これにより、非関数シンボルに対してこれらのフィールドにアクセスしようとした際のパニックを防ぎます。
5.  **データの一貫性**: このリファクタリングは、リンカの内部データモデルにおけるデータの一貫性と論理的な分離を改善します。関数固有のデータは関数固有の構造体にまとめられるため、コードの可読性と保守性が向上します。

## 変更の背景

Go言語は設計当初から、シンプルさと一貫性を重視しています。このコミットが行われた2009年当時、Go言語には現在のような強力な組み込みスライスが存在していましたが、`container/vector` パッケージは動的な配列（ベクター）の機能を提供していました。

Goの組み込みスライスでは、`nil` スライスに対して `len()` 関数を呼び出すと `0` が返されます。これは、`nil` スライスが「要素を持たないスライス」として扱われるため、非常に自然で直感的な挙動です。しかし、`container/vector` パッケージの `Vector` 型では、`nil` ポインタの `Vector` に対して `Len()` メソッドを呼び出すと、パニック（nilポインタ参照）が発生する可能性がありました。

この挙動の不一致は、開発者にとって混乱の原因となり、エラーを引き起こす可能性がありました。このコミットの目的は、`Vector` 型の `Len()` メソッドの挙動を組み込みスライスに合わせることで、APIの一貫性を高め、より堅牢で予測可能なコードの記述を促進することにありました。これにより、`Vector` を扱うコードが `nil` チェックを明示的に行わなくても安全に `Len()` を呼び出せるようになり、コードの簡潔さも向上します。

## 前提知識の解説

### Go言語における `nil`

Go言語において、`nil` はポインタ、スライス、マップ、チャネル、関数、インターフェースなどのゼロ値として使用されます。`nil` は「値がない」状態や「初期化されていない」状態を示します。

- **ポインタの `nil`**: ポインタが何も指していない状態。`var p *int` と宣言すると、`p` は `nil` に初期化されます。`nil` ポインタをデリファレンスしようとすると、ランタイムパニックが発生します。
- **スライスの `nil`**: スライスは内部的にポインタ、長さ、容量の3つの要素で構成されます。`var s []int` と宣言すると、`s` は `nil` スライスに初期化されます。`nil` スライスは長さが `0`、容量が `0` です。重要なのは、`nil` スライスに対して `len(s)` や `cap(s)` を呼び出してもパニックにならず、それぞれ `0` が返される点です。また、`append` 関数を使って要素を追加することも可能です。

### `container/vector` パッケージ

`container/vector` パッケージは、Go言語の初期の標準ライブラリの一部として提供されていた、動的な配列（ベクター）を実装するためのパッケージです。これは、C++の `std::vector` やJavaの `ArrayList` に似た機能を提供していました。しかし、Go言語の組み込みスライスが進化し、より効率的で柔軟な操作（`append`、`copy`など）が可能になったため、`container/vector` パッケージは後に非推奨となり、最終的には標準ライブラリから削除されました。このコミットが行われた2009年当時は、まだ活発に利用されていたパッケージの一つでした。

### `Len()` メソッドと `len()` 関数

- **`Len()` メソッド**: このコミットで修正対象となっている `Vector` 型のメソッドです。構造体やインターフェースに紐付けられた関数をメソッドと呼びます。
- **`len()` 関数**: Go言語に組み込まれている関数で、スライス、配列、文字列、マップ、チャネルの長さ（要素数）を返します。特にスライスに対しては、`nil` スライスに対しても安全に `0` を返すという特性があります。

## 技術的詳細

このコミットの技術的な核心は、`Vector` 型の `Len()` メソッドに `nil` ポインタチェックを追加することです。

変更前の `Vector.Len()` メソッドは、`Vector` 構造体の内部にあるスライス `p.a` の長さを直接返していました。

```go
func (p *Vector) Len() int {
	return len(p.a)
}
```

ここで問題となるのは、`p` が `nil` の場合です。Go言語では、`nil` ポインタに対してメソッドを呼び出すと、通常はランタイムパニック（`nil` ポインタ参照）が発生します。したがって、変更前のコードでは `var v *vector.Vector; v.Len()` のような呼び出しはパニックを引き起こしていました。

このコミットでは、この問題を解決するために、`Len()` メソッドの冒頭で `p` が `nil` であるかどうかをチェックするガード句を追加しました。

```go
func (p *Vector) Len() int {
	if p == nil {
		return 0;
	}
	return len(p.a)
}
```

この変更により、`p` が `nil` の場合は即座に `0` が返されるため、`nil` ポインタ参照によるパニックが回避されます。これにより、`Vector` 型の `Len()` メソッドは、Goの組み込みスライスの `len()` 関数と同様に、`nil` の場合でも安全に `0` を返すという一貫した挙動を示すようになります。

テストファイル `src/lib/container/vector/vector_test.go` に追加された `TestZeroLen` 関数は、この新しい挙動を検証しています。

```go
func TestZeroLen(t *testing.T) {
	var a *vector.Vector;
	if a.Len() != 0 { t.Errorf("A) expected 0, got %d", a.Len()); }
	a = vector.New(0);
	if a.Len() != 0 { t.Errorf("B) expected 0, got %d", a.Len()); }
}
```

このテストでは、以下の2つのケースを検証しています。
1. `var a *vector.Vector;` で宣言された `a` は `nil` ポインタです。この `nil` ポインタに対して `a.Len()` を呼び出し、結果が `0` であることを確認しています。
2. `a = vector.New(0);` で作成された、長さ `0` の空の `Vector` に対して `a.Len()` を呼び出し、結果が `0` であることを確認しています。

このテストの追加により、変更が正しく機能していること、そして将来のリグレッションを防ぐための安全網が提供されます。

## コアとなるコードの解説

`src/lib/container/vector/vector.go` の `Len()` メソッドに追加された以下の4行がこのコミットの核心です。

```go
	if p == nil {
		return 0;
	}
```

このコードは、`Len()` メソッドが呼び出された際に、レシーバである `p` (型は `*Vector`) が `nil` であるかどうかをチェックしています。
- もし `p` が `nil` であれば、それは `Vector` のインスタンスがまだ作成されていない、あるいは意図的に `nil` に設定されている状態を意味します。この場合、Goの組み込みスライスの `len()` 関数が `nil` スライスに対して `0` を返す挙動に倣い、`Len()` メソッドも `0` を返します。これにより、`nil` ポインタ参照によるランタイムパニックを防ぎ、APIの予測可能性と堅牢性を高めています。
- `p` が `nil` でない場合は、従来のロジックである `return len(p.a)` が実行され、`Vector` 内部のスライス `a` の実際の長さが返されます。

このシンプルな `nil` チェックの追加により、`Vector` 型の `Len()` メソッドは、Go言語の他のデータ構造との一貫性を保ちつつ、より安全で使いやすいものとなりました。

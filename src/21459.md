# [インデックス 21459] ファイルの概要

このコミットは、Goランタイムにおけるハッシュ関数のセキュリティと品質を向上させることを目的としています。特に、マップ（`map`）のハッシュ計算に使用されるフォールバックハッシュ関数に起動時のランダム性を導入し、ハッシュ衝突攻撃（Hash DoS攻撃）に対する耐性を強化しています。また、ハッシュ計算ロジックの再編成も行い、攻撃者がランダムシードを逆算しにくくする変更が含まれています。

## 元コミット内容

```
runtime: use some startup randomness in the fallback hashes

Fold in some startup randomness to make the hash vary across
different runs.  This helps prevent attackers from choosing
keys that all map to the same bucket.

Also, reorganize the hash a bit.  Move the *m1 multiply to after
the xor of the current hash and the message.  For hash quality
it doesn't really matter, but for DDOS resistance it helps a lot
(any processing done to the message before it is merged with the
random seed is useless, as it is easily inverted by an attacker).

Update #9365

Reviewed-by: Ian Lance Taylor <iant@golang.org>
```

## 変更の背景

この変更の主な背景は、ハッシュテーブル（Goの`map`型）に対するサービス拒否（DoS）攻撃、特にハッシュ衝突攻撃への対策です。ハッシュテーブルは通常、平均O(1)の高速な操作を提供しますが、悪意のある入力によって意図的にハッシュ衝突を多数引き起こされると、最悪の場合O(N)の性能に劣化し、CPUリソースを大量に消費してサービス停止を引き起こす可能性があります。

Goの`map`は、このような攻撃を防ぐために、各マップのインスタンスに対してランダムなハッシュシードを使用することで、攻撃者が衝突を予測・事前計算することを困難にしています。このコミットは、特にAES命令セットが利用できない環境（フォールバックハッシュが使用される場合）において、このランダム性を強化し、より堅牢なハッシュ関数を提供することを目的としています。

コミットメッセージで参照されているGo issue #9365は、「runtime: Extend Go's map crypto hash guarantee to all platforms in 1.5」と題されており、Go 1.5でマップの暗号学的ハッシュ保証をすべてのプラットフォームに拡張することを目指していたことがわかります。このコミットは、その目標達成に向けた重要なステップの一つです。

## 前提知識の解説

### ハッシュテーブルとハッシュ衝突

ハッシュテーブル（Goでは`map`）は、キーと値のペアを格納するデータ構造です。キーをハッシュ関数に通してハッシュ値（インデックス）を計算し、そのインデックスに対応するバケットに値を格納します。これにより、高速な検索、挿入、削除が可能になります。

しかし、異なるキーが同じハッシュ値になることを「ハッシュ衝突」と呼びます。ハッシュ衝突が発生した場合、ハッシュテーブルは通常、リンクリストやオープンアドレス法などの方法で衝突を解決します。衝突が頻繁に発生すると、これらの解決メカニズムがオーバーヘッドとなり、ハッシュテーブルの性能が著しく低下します。

### ハッシュDoS攻撃

ハッシュDoS攻撃は、このハッシュ衝突の特性を悪用した攻撃です。攻撃者は、特定のハッシュ関数に対して多数の衝突を引き起こすような入力データ（キー）を意図的に生成し、サーバーに送信します。これにより、サーバーのハッシュテーブル操作がO(1)からO(N)に劣化し、CPU使用率が急増して、正当なリクエストを処理できなくなるサービス拒否状態に陥ります。

### ランダムシードとハッシュ関数のランダム化

ハッシュDoS攻撃への対策として、ハッシュ関数にランダムなシード（種）を導入する方法があります。これにより、プログラムが起動するたびに異なるハッシュ関数が使用されるため、攻撃者は事前に衝突するキーのセットを計算することが非常に困難になります。Goの`map`は、このランダムシードを各マップインスタンスに適用することで、この種の攻撃に対する耐性を高めています。

### Goランタイムのハッシュ関数

Goランタイムは、内部的に`map`などのデータ構造で使用するハッシュ関数を持っています。CPUがAES命令セットをサポートしている場合、Goはパフォーマンスのために`aeshash`という関数を使用します。しかし、AES命令が利用できない環境では、フォールバックのソフトウェア実装によるハッシュ関数が使用されます。このコミットは、このフォールバックハッシュ関数に焦点を当てています。

## 技術的詳細

このコミットは、Goランタイムのフォールバックハッシュ関数におけるランダム性の導入と、ハッシュ計算ロジックの改善に焦点を当てています。

1.  **起動時のランダム性の導入**:
    *   `src/runtime/alg.go` に `hashkey [4]uintptr` という新しいグローバル変数が導入されました。これは、フォールバックハッシュ関数のシードとして使用されるランダムな値を格納します。
    *   `init()` 関数内で、AESハッシュが利用できない場合に `getRandomData` を呼び出し、`hashkey` にランダムなバイト列を書き込みます。これにより、Goプログラムが起動するたびに異なるハッシュシードが生成され、ハッシュ衝突攻撃に対する耐性が向上します。
    *   `hashkey[0]` の最下位ビットを1に設定することで、常に奇数になるようにしています。これは、ハッシュ関数の品質を保つための一般的なプラクティスです。

2.  **ハッシュ計算ロジックの再編成**:
    *   `src/runtime/hash32.go` と `src/runtime/hash64.go` にある`memhash`関数（32ビットおよび64ビット版）の内部ロジックが変更されました。
    *   変更の核心は、メッセージデータとランダムシード（`hashkey`から派生）の結合方法です。以前は、メッセージデータに`m1`（乗数）を乗算してから現在のハッシュ値とXOR演算を行っていましたが、変更後は、現在のハッシュ値とメッセージデータのXOR演算を行った後に`m1`などの乗数を適用するようになりました。
    *   コミットメッセージによると、この変更はハッシュ品質自体には大きな影響を与えませんが、DoS耐性には大きく貢献します。攻撃者がランダムシードを逆算しようとする場合、シードがメッセージデータと結合される前にメッセージデータに対して行われた処理は、攻撃者によって容易に反転されてしまいます。しかし、シードが結合された後に乗算を行うことで、攻撃者がハッシュ関数の内部状態を推測し、衝突を生成することがより困難になります。
    *   特に、ループ内で複数のブロックを処理する部分（`default`ケース）において、`v1`, `v2`, `v3`, `v4`といった中間ハッシュ値の初期化に`hashkey`の異なる要素を使用するようになり、各ブロックのハッシュ計算に異なる乗数（`m1`, `m2`, `m3`, `m4`）を適用するようになりました。これにより、ハッシュの拡散性が向上し、衝突耐性がさらに高まります。
    *   また、`rotl_11`や`rotl_27`といった一部のローテーション関数が削除され、ハッシュ計算ロジックが簡素化されています。

これらの変更により、Goの`map`は、特にAES命令セットが利用できない環境においても、より予測不能で堅牢なハッシュ関数を使用するようになり、ハッシュ衝突攻撃に対するセキュリティが強化されました。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルとコードブロックは以下の通りです。

*   **`src/runtime/alg.go`**:
    *   `hashkey [4]uintptr` 変数の追加。
    *   `init()` 関数内で、AESハッシュが利用できない場合の `hashkey` の初期化ロジックの追加。`getRandomData` を使用してランダムな値を設定し、`hashkey[0]` を奇数に設定する処理。
*   **`src/runtime/hash32.go`**:
    *   `memhash` 関数内のハッシュ計算ロジックの変更。
        *   初期ハッシュ値 `h` の計算に `hashkey[0]` を組み込む (`h := uint32(seed + s*hashkey[0])`)。
        *   短いデータ（`s < 4`, `s == 4`, `s <= 8`, `s <= 16`）のハッシュ計算において、`*m1` の乗算をXOR演算の後に移動。
        *   長いデータ（`default`ケース）のループ処理において、中間ハッシュ値 `v1`, `v2`, `v3`, `v4` の初期化に `hashkey` の異なる要素を使用。
        *   各ブロックのハッシュ計算で異なる乗数（`m1`, `m2`, `m3`, `m4`）を使用するように変更。
        *   最終的なハッシュ値の結合方法を `v1 ^ v2 ^ v3 ^ v4` に変更。
        *   `rotl_11` 関数の削除。
*   **`src/runtime/hash64.go`**:
    *   `memhash` 関数内のハッシュ計算ロジックの変更。
        *   初期ハッシュ値 `h` の計算に `hashkey[0]` を組み込む (`h := uint64(seed + s*hashkey[0])`)。
        *   短いデータ（`s < 4`, `s <= 8`, `s <= 16`, `s <= 32`）のハッシュ計算において、`*m1` の乗算をXOR演算の後に移動。
        *   長いデータ（`default`ケース）のループ処理において、中間ハッシュ値 `v1`, `v2`, `v3`, `v4` の初期化に `hashkey` の異なる要素を使用。
        *   各ブロックのハッシュ計算で異なる乗数（`m1`, `m2`, `m3`, `m4`）を使用するように変更。
        *   最終的なハッシュ値の結合方法を `v1 ^ v2 ^ v3 ^ v4` に変更。
        *   `rotl_27` 関数の削除。

## コアとなるコードの解説

### `src/runtime/alg.go` の変更

```go
// used in hash{32,64}.go to seed the hash function
var hashkey [4]uintptr

func init() {
	// Install aes hash algorithm if we have the instructions we need
	if (GOARCH == "386" || GOARCH == "amd64") &&
		GOOS != "nacl" &&
		cpuid_ecx&(1<<25) != 0 && // aes (aesenc)
		cpuid_ecx&(1<<9) != 0 && // sse3 (pshufb)
		cpuid_ecx&(1<<19) != 0 { // sse4.1 (pinsr{d,q})
		useAeshash = true
		algarray[alg_MEM].hash = aeshash
		algarray[alg_MEM8].hash = aeshash
		algarray[alg_MEM16].hash = aeshash
		algarray[alg_MEM32].hash = aeshash
		algarray[alg_MEM64].hash = aeshash
		algarray[alg_MEM128].hash = aeshash
		algarray[alg_STRING].hash = aeshashstr
		// Initialize with random data so hash collisions will be hard to engineer.
		getRandomData(aeskeysched[:])
		return
	}
	getRandomData((*[len(hashkey) * ptrSize]byte)(unsafe.Pointer(&hashkey))[:])
	hashkey[0] |= 1 // make sure this number is odd
}
```
この`init`関数は、Goプログラムの起動時に一度だけ実行されます。変更のポイントは、AES命令セットが利用できない（`useAeshash`が`false`になる）場合の処理です。以前は`aeskeysched`のみが初期化されていましたが、この変更により`hashkey`がランダムなデータで初期化されるようになりました。`hashkey[0] |= 1`は、`hashkey[0]`が常に奇数であることを保証し、ハッシュ関数の品質を向上させます。この`hashkey`が、フォールバックハッシュ関数のランダムシードとして機能します。

### `src/runtime/hash32.go` および `src/runtime/hash64.go` の変更（抜粋）

```go
// hash32.go の memhash 関数内
func memhash(p unsafe.Pointer, s, seed uintptr) uintptr {
	// ... (AESハッシュのチェック) ...
	h := uint32(seed + s*hashkey[0]) // 変更点: hashkey[0] を組み込む
tail:
	switch {
	// ... (短いデータの処理) ...
	case s <= 16:
		h ^= readUnaligned32(p)
		h = rotl_15(h*m1) * m2 // 変更点: *m1 の位置
		h ^= readUnaligned32(add(p, 4))
		h = rotl_15(h*m1) * m2 // 変更点: *m1 の位置
		h ^= readUnaligned32(add(p, s-8))
		h = rotl_15(h*m1) * m2 // 変更点: *m1 の位置
		h ^= readUnaligned32(add(p, s-4))
		h = rotl_15(h*m1) * m2 // 変更点: *m1 の位置
	default:
		v1 := h
		v2 := uint32(hashkey[1]) // 変更点: hashkey[1] で初期化
		v3 := uint32(hashkey[2]) // 変更点: hashkey[2] で初期化
		v4 := uint32(hashkey[3]) // 変更点: hashkey[3] で初期化
		for s >= 16 {
			v1 ^= readUnaligned32(p)
			v1 = rotl_15(v1*m1) * m2 // 変更点: *m1 の位置
			p = add(p, 4)
			v2 ^= readUnaligned32(p)
			v2 = rotl_15(v2*m2) * m3 // 変更点: *m2 を使用
			p = add(p, 4)
			v3 ^= readUnaligned32(p)
			v3 = rotl_15(v3*m3) * m4 // 変更点: *m3 を使用
			p = add(p, 4)
			v4 ^= readUnaligned32(p)
			v4 = rotl_15(v4*m4) * m1 // 変更点: *m4 を使用
			p = add(p, 4)
			s -= 16
		}
		h = v1 ^ v2 ^ v3 ^ v4 // 変更点: 最終的な結合方法
		goto tail
	}
	// ... (最終的な拡散処理) ...
}
```
このコードは、Goの`map`が内部的に使用するフォールバックハッシュ関数`memhash`の一部です。
1.  **`h := uint32(seed + s*hashkey[0])`**: ハッシュ計算の初期シードに、これまでの`seed`と`s`（サイズ）に加えて、新しく導入された`hashkey[0]`が乗算されて組み込まれるようになりました。これにより、プログラムの起動ごとに異なるハッシュ値の系列が生成され、ハッシュ衝突攻撃に対する予測不可能性が高まります。
2.  **`h = rotl_15(h*m1) * m2` などの乗算位置の変更**: 以前はメッセージデータに直接`m1`を乗算していましたが、変更後は現在のハッシュ値とメッセージデータのXOR演算を行った後に`m1`などの乗数を適用するようになりました。これは、コミットメッセージで述べられているように、攻撃者がランダムシードを逆算することをより困難にし、DoS耐性を向上させるための重要な変更です。
3.  **`default`ケースの変更**: 処理するデータが長い場合のループ処理において、中間ハッシュ値`v1`, `v2`, `v3`, `v4`の初期化に`hashkey`の異なる要素（`hashkey[1]`, `hashkey[2]`, `hashkey[3]`）が使用されるようになりました。さらに、各`v`値の更新において、異なる乗数（`m1`, `m2`, `m3`, `m4`）が適用されるようになり、ハッシュの拡散性が向上し、衝突耐性がさらに強化されています。
4.  **`h = v1 ^ v2 ^ v3 ^ v4`**: 最終的なハッシュ値の結合方法が、以前の複雑な乗算とローテーションの組み合わせから、単純なXOR演算に変更されました。これは、ハッシュ品質を維持しつつ、コードを簡素化する意図があると考えられます。

これらの変更は、Goの`map`が、特にAES命令セットが利用できない環境においても、より予測不能で堅牢なハッシュ関数を使用するようにし、ハッシュ衝突攻撃に対するセキュリティを大幅に強化しています。

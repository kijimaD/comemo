## 変更の背景

Go言語は、その設計当初からクロスプラットフォーム対応を重視していました。様々なアーキテクチャでGoプログラムをコンパイル・実行できるようにするためには、各アーキテクチャ固有のアセンブリコードやランタイムの挙動を適切に扱う必要があります。

`mkasmh` は、Goランタイムのアセンブリコードを生成する際に使用されるヘルパースクリプトです。このスクリプトは、特定のアセンブリレジスタにGoランタイムが内部的に使用する特定の意味（例えば、現在のgoroutineのポインタ `g` や現在のOSスレッドのポインタ `m`）を割り当てるためのマクロ定義を生成します。

このコミットが作成された2009年当時、Goはまだ初期段階にあり、x86およびx86-64アーキテクチャが主なターゲットでした。しかし、モバイルデバイスの普及に伴い、ARMアーキテクチャの重要性が増していました。GoをARMベースのシステム（例えば、Raspberry PiやAndroidデバイスなど）で動作させるためには、`mkasmh` のようなビルドツールがARM固有のレジスタ割り当てを理解し、適切なアセンブリコードを生成できるようにする必要がありました。

この変更は、GoがARMアーキテクチャを公式にサポートするための初期ステップの一つであり、GoプログラムがARMベースのシステムで効率的に動作するための基盤を築くものでした。

## 前提知識の解説

### Goランタイムとアセンブリ

Goプログラムは、Go言語で書かれたコードと、Goランタイムと呼ばれるCやアセンブリで書かれた低レベルなコードで構成されています。Goランタイムは、ガベージコレクション、スケジューラ、メモリ管理、システムコールなど、Goプログラムの実行に不可欠な機能を提供します。

Goランタイムの一部は、パフォーマンス上の理由や、OSとの直接的なインターフェースのためにアセンブリ言語で書かれています。これらのアセンブリコードは、特定のCPUレジスタを特定の目的のために使用することが多く、その割り当てはアーキテクチャによって異なります。

### `mkasmh` スクリプト

`mkasmh` は "make assembly header" の略で、Goのビルドシステムの一部として機能するシェルスクリプトです。このスクリプトの主な役割は、Goランタイムのアセンブリソースファイルがインクルードするヘッダーファイル（通常は `go_asm.h` のような名前）を生成することです。

このヘッダーファイルには、Goランタイムが内部的に使用する重要なポインタ（`g` と `m`）を、ターゲットアーキテクチャの特定のアセンブリレジスタにマッピングするための `#define` ディレクティブが含まれています。これにより、アセンブリコード内で `g` や `m` といったシンボリックな名前を使って、対応するレジスタにアクセスできるようになります。

### `g` と `m` ポインタ

Goランタイムには、並行処理を管理するための重要な概念がいくつかあります。

*   **`g` (goroutine)**: Goの軽量スレッドです。各goroutineは `g` 構造体によって表現され、その実行スタック、状態、スケジューリング情報などが含まれます。アセンブリコードでは、現在のgoroutineの `g` 構造体へのポインタが頻繁に必要とされます。
*   **`m` (machine/OS thread)**: 実際のOSスレッドです。Goランタイムは、複数の `m` を使用してgoroutineを並行実行します。各 `m` は `m` 構造体によって表現され、OSスレッドのスタック、スケジューラ情報、現在の `g` へのポインタなどが含まれます。アセンブリコードでは、現在のOSスレッドの `m` 構造体へのポインタも頻繁に必要とされます。

これらのポインタは、Goランタイムのスケジューラやガベージコレクタが正しく機能するために不可欠であり、アセンブリコードから高速にアクセスできる必要があります。そのため、特定のレジスタにこれらを割り当てることで、アクセスを最適化しています。

### ARMアーキテクチャとレジスタ

ARM (Advanced RISC Machine) は、モバイルデバイスや組み込みシステムで広く使用されているRISC (Reduced Instruction Set Computer) アーキテクチャです。ARMプロセッサは、汎用レジスタR0からR15を持っています。

*   **R0-R12**: 汎用レジスタ。
*   **R13 (SP)**: スタックポインタ。
*   **R14 (LR)**: リンクレジスタ。関数呼び出し時に戻りアドレスを保持します。
*   **R15 (PC)**: プログラムカウンタ。次に実行される命令のアドレスを保持します。

このコミットでは、`R10` を `g` に、`R9` を `m` に、そして `R14` を `LR` に割り当てています。これらの選択は、ARMのCalling Convention（関数呼び出し規約）やGoランタイムの内部的なレジスタ使用状況を考慮して行われます。

## 技術的詳細

このコミットは、`src/pkg/runtime/mkasmh` スクリプトに `arm)` という新しいケースを追加しています。これは、シェルスクリプトの `case` ステートメントの一部であり、環境変数 `$GOARCH` の値に基づいて異なる処理を実行します。

`$GOARCH` が `arm` の場合、以下の `#define` ディレクティブが生成されるヘッダーファイルに出力されます。

*   `#define g R10`: 現在のgoroutineのポインタ `g` をARMのレジスタ `R10` にマッピングします。
*   `#define m R9`: 現在のOSスレッドのポインタ `m` をARMのレジスタ `R9` にマッピングします。
*   `#define LR R14`: ARMのリンクレジスタ `R14` を `LR` というシンボリック名で定義します。これは、アセンブリコード内で `R14` を直接参照する代わりに、より意味のある `LR` を使用できるようにするためです。

これらの定義により、Goランタイムのアセンブリコードは、ARMアーキテクチャ上で `g` や `m` といった抽象的な名前を使って、対応する物理レジスタにアクセスできるようになります。これにより、アセンブリコードの可読性と移植性が向上します。

レジスタ `R9` と `R10` が `m` と `g` に割り当てられているのは、ARMのCalling Conventionにおいて、これらのレジスタが通常、関数呼び出し間で保存される（callee-saved）レジスタであるため、Goランタイムがこれらのポインタを長期的に保持するのに適しているからです。これにより、関数呼び出しを跨いで `g` と `m` の値を維持することが容易になります。

## コアとなるコードの変更箇所

変更は `src/pkg/runtime/mkasmh` ファイルに集中しています。

## コアとなるコードの解説

このコードスニペットは、`mkasmh` スクリプトの `case "$GOARCH"` ブロック内に新しい `arm)` エントリを追加しています。

*   `amd64)` の既存のケースでは、`g` が `R15` に、`m` が `R14` に定義されています。これはx86-64アーキテクチャにおけるレジスタの慣習に基づいています。
*   新しく追加された `arm)` ケースでは、`g` が `R10` に、`m` が `R9` に定義されています。これはARMアーキテクチャにおけるレジスタの慣習と、Goランタイムの要件に基づいて選択されたものです。
*   さらに、`LR` (Link Register) が `R14` として定義されています。`R14` はARMアーキテクチャにおいて、関数呼び出しの戻りアドレスを保持する特別なレジスタです。この定義により、アセンブリコード内で `R14` を直接使う代わりに `LR` というより分かりやすい名前で参照できるようになります。

この変更により、Goのビルドプロセスが `$GOARCH` が `arm` に設定されていることを検出すると、`mkasmh` はこれらのARM固有のレジスタ定義を含むヘッダーファイルを生成するようになります。これにより、GoランタイムのARMアセンブリコードが正しくコンパイルされ、`g` と `m` ポインタに効率的にアクセスできるようになります。

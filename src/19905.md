## 元コミット内容

GoランタイムのWindows実装において、`runtime.systime`関数内で`yield`を呼び出す前にCPUを「燃やす」（一定回数ループを実行する）ように変更しました。具体的には、ループカウンタの初期値を`0`から`1`に変更することで、ループが少なくとも1回は実行されることを保証しています。

## 変更の背景

この変更の背景には、Windowsの特定のシステムコール、特に高精度な時刻情報を取得する際の挙動に関する微妙な問題があります。`runtime.systime`関数は、Windowsの`KSYSTEM_TIME`構造体から時刻情報を読み取ります。この構造体のフィールド（`High1Time`, `LowPart`, `High2Time`）は、特定の順序で読み取られる必要があり、かつ、読み取り中にシステム時刻が更新される可能性があるため、一貫性のある時刻を取得するためには、複数回の読み取りと検証が必要になります。

元のコードでは、この読み取りループが`for(i = 0; i < 10000; i++)`となっていました。これは、ループが`i=0`から始まるため、最初のイテレーションで`yield`が呼び出される前に、`KSYSTEM_TIME`のフィールドが読み取られることになります。しかし、特定の条件下で、この最初の読み取りが不完全または不正確な状態で行われる可能性がありました。

このコミットの目的は、`yield`（Goランタイムにおけるスケジューラの協調的な切り替えを示唆する操作）が呼び出される前に、CPUを意図的に少しだけ消費させる（"burn cpu"）ことで、システムがより安定した状態になるのを待つ、あるいは、時刻情報の読み取りがより確実に行われるようにするためのものです。ループカウンタを`i = 1`から始めることで、最初のイテレーション（`i=0`の時）がスキップされ、`yield`が呼び出される前に少なくとも1回のループ処理（`KSYSTEM_TIME`のフィールド読み取り）が確実に行われるようになります。これにより、時刻取得の信頼性が向上すると考えられます。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム（OS）と直接対話するのではなく、ランタイムを介してOSサービスを利用します。

### ゴルーチン (Goroutine) とスケジューラ (Scheduler)

ゴルーチンはGoにおける並行処理の単位であり、OSスレッドよりもはるかに軽量です。Goランタイムには独自のスケジューラがあり、多数のゴルーチンを少数のOSスレッドにマッピングして実行を管理します。スケジューラは、ゴルーチンがI/O操作でブロックされたり、明示的に`runtime.Gosched()`（または内部的に`yield`に相当する操作）を呼び出したりしたときに、別のゴルーチンにCPUを切り替えることができます。

### `runtime.systime`関数

この関数は、Goランタイムがシステム時刻を取得するために使用する、OS固有の実装です。Windowsの場合、これは`src/pkg/runtime/os_windows.c`にC言語で実装されています。Goプログラムが現在時刻を要求したり、タイマーを設定したりする際に、この低レベルの関数が利用されます。

### `KSYSTEM_TIME`構造体 (Windows Kernel System Time)

`KSYSTEM_TIME`は、Windowsカーネルが内部的に使用するシステム時刻を表す構造体です。この構造体は、`High1Time`、`LowPart`、`High2Time`といったフィールドを持ち、これらを組み合わせて64ビットの時刻値を表現します。Windowsのドキュメントによると、この構造体のフィールドは、時刻の更新中に一貫性を保つために、特定の順序で読み取る必要があります。具体的には、`High1Time`、`LowPart`、`High2Time`の順に読み取り、`High1Time`と`High2Time`が一致することを確認することで、読み取り中に時刻が更新されなかったことを保証します。もし一致しない場合は、再度読み取りを試みる必要があります。

### CPUを「燃やす」 (Burn CPU)

この文脈での「CPUを燃やす」とは、意図的に短い時間、CPUを計算処理で占有することを指します。これは、ループを回すなどの単純な計算を行うことで実現されます。目的は、システムが特定の状態に達するのを待つ、あるいは、キャッシュをウォームアップする、あるいは、今回のケースのように、システムがより安定した状態になるのを待つために、ごくわずかな遅延を導入することです。これは、スリープや`yield`のようにOSに制御を渡すのではなく、CPUをアクティブに利用し続ける点が異なります。

### `yield` (協調的スケジューリングにおける制御の譲渡)

Goランタイムの文脈では、`yield`はゴルーチンが自発的にCPUの制御をGoスケジューラに譲渡する概念を指します。これにより、スケジューラは別の実行可能なゴルーチンに切り替える機会を得ます。これは、OSスレッドが`Sleep(0)`や`SwitchToThread()`を呼び出すのと似ていますが、Goのゴルーチンレベルでの操作です。

## 技術的詳細

`runtime.systime`関数は、Windowsの`KSYSTEM_TIME`構造体からシステム時刻を読み取るために、ループ内で`High1Time`、`LowPart`、`High2Time`の順にフィールドを読み取り、`High1Time`と`High2Time`が一致するまで繰り返します。これは、時刻の読み取り中にシステム時刻が更新される可能性があるため、一貫性のある時刻値を取得するための標準的なパターンです。

元のコードでは、このループは`for(i = 0; i < 10000; i++)`で開始されていました。このループの最初のイテレーション（`i=0`の時）では、時刻フィールドの読み取りが行われた後、`yield`に相当する操作（Goランタイムのスケジューラに制御を譲渡する可能性のある操作）が呼び出される可能性があります。

このコミットの変更は、ループの初期値を`i = 0`から`i = 1`に変更することです。
`for(i = 0; i < 10000; i++)`
↓
`for(i = 1; i < 10000; i++)`

この変更により、ループの最初のイテレーション（`i=0`）がスキップされ、ループ本体の処理（`KSYSTEM_TIME`のフィールド読み取り）が開始される前に、`i`が`1`になるまでループの条件判定とインクリメントが行われます。これは、ごくわずかな時間ですが、CPUを消費する操作です。この「CPUを燃やす」という行為は、`yield`が呼び出される前に、システムがより安定した状態になるのを待つ、あるいは、時刻情報の読み取りがより確実に行われるようにするためのものです。

具体的には、`yield`が呼び出される直前の状態が、時刻取得の正確性に影響を与える可能性があったため、ループの開始を少し遅らせることで、この問題を緩和しようとしています。これは、非常に低レベルな同期の問題や、特定のハードウェア/OSのタイミングに依存する挙動を修正するための、繊細な調整であると考えられます。

## コアとなるコードの解説

変更された行は、`runtime·systime`関数内の時刻読み取りループの初期化部分です。

- **変更前**: `for(i = 0; i < 10000; i++) {`
    - ループカウンタ`i`が`0`から始まり、ループ本体がすぐに実行されます。
- **変更後**: `for(i = 1; i < 10000; i++) {`
    - ループカウンタ`i`が`1`から始まります。これにより、ループ本体が実行される前に、`i=0`のチェックと`i`のインクリメントが行われることになります。これは、ループ本体の処理（時刻フィールドの読み取り）が開始される前に、ごくわずかなCPUサイクルを消費することを意味します。この「CPUを燃やす」ことで、`yield`が呼び出される前に、システムがより安定した状態になることを期待しています。

この変更は、Windowsのシステム時刻取得における潜在的な競合状態やタイミングの問題を緩和するための、非常に細かい最適化またはバグ修正であると考えられます。

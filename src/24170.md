# [インデックス 24170] ファイルの概要

## コミット

このコミットは、Go言語の `net/http` パッケージにおいて、HTTPリクエストの `Host` ヘッダーに不正な文字（スペースやスラッシュ）が含まれることを防ぐための修正を導入します。これにより、不正な `Host` ヘッダーが原因で発生する可能性のある、HTTPリクエストの誤形成やそれに伴うセキュリティ上の脆弱性を回避します。

## 変更の背景

この変更の背景には、HTTP `Host` ヘッダーの不正な形式が引き起こす潜在的なセキュリティ脆弱性があります。HTTP/1.1の仕様（RFC 7230など）では `Host` ヘッダーの形式が厳密に定義されていますが、一部の実装ではこの仕様に厳密に従わない `Host` ヘッダーを受け入れてしまうことがあります。特に、`Host` ヘッダー内にスペースやスラッシュのような予期せぬ文字が含まれている場合、ウェブアプリケーションの異なるコンポーネント（例: リバースプロキシ、ロードバランサー、ウェブサーバー、アプリケーションサーバー）がそのヘッダーを異なる方法で解釈する可能性があります。

このような解釈の不一致は、以下のような様々な攻撃に悪用される可能性があります。

*   **Webキャッシュポイズニング (Web Cache Poisoning)**: 攻撃者が不正な `Host` ヘッダーを送信することで、キャッシュサーバーに悪意のあるコンテンツをキャッシュさせ、他の正規ユーザーにそのコンテンツを配信させることができます。
*   **パスワードリセットポイズニング (Password Reset Poisoning)**: パスワードリセット機能が `Host` ヘッダーの値を使用してリセットリンクを生成する場合、攻撃者は不正な `Host` ヘッダーを挿入して、リセットリンクを攻撃者の制御するドメインに向けさせることができます。
*   **サーバーサイドリクエストフォージェリ (SSRF)**: 内部システムが `Host` ヘッダーの値に基づいてリクエストを生成する場合、攻撃者は内部ネットワークへのアクセスや他の内部サービスへのリクエストを偽装することができます。
*   **認証バイパス (Bypassing Authentication)**: 特定の認証メカニズムが `Host` ヘッダーに依存している場合、不正な `Host` ヘッダーによって認証を回避できる可能性があります。
*   **オープンリダイレクト (Open Redirects)**: `Host` ヘッダーがリダイレクトURLの生成に使用される場合、攻撃者はユーザーを任意の悪意のあるサイトにリダイレクトさせることができます。

このコミットは、Goの `net/http` パッケージが生成する `Host` ヘッダーが常にクリーンであることを保証することで、これらの脆弱性のリスクを軽減することを目的としています。特に、プロキシ環境下でのリクエスト処理において、不正な `Host` ヘッダーが原因でリクエストが誤形成される状況を避けることが強調されています。

## 前提知識の解説

### HTTP Host ヘッダー

HTTP `Host` ヘッダーは、HTTP/1.1プロトコルにおいて必須のヘッダーであり、リクエストされたリソースのインターネットホストとポート番号を指定します。これは、単一のIPアドレスで複数のドメインをホストするバーチャルホスティング環境で、どのウェブサイトがリクエストされているかをサーバーが識別するために不可欠です。

**RFC 7230 (HTTP/1.1 Message Syntax and Routing)**:
このRFCは、`Host` ヘッダーの形式について厳密なルールを定めています。
*   `Host` ヘッダーのフィールド値は、ターゲットURIのオーソリティコンポーネントと同一でなければなりません。
*   オーソリティコンポーネネントは、`uri-host` とオプションのポート番号から構成されます。
*   `uri-host` は、RFC 3986で定義されるホスト形式に従う必要があります。これには、登録済み名（ドメイン名）、IPv4アドレス、またはIPv6アドレスが含まれます。
*   重要な点として、`Host` ヘッダーの値には、スペースやスラッシュのようなURIパスやクエリパラメータの一部を構成する文字は含まれるべきではありません。これらの文字は、`Host` ヘッダーの構文を逸脱しており、不正な形式と見なされます。

### HTTPリクエストの処理フローとプロキシ

一般的なウェブアプリケーションのアーキテクチャでは、クライアントからのHTTPリクエストは、ロードバランサー、リバースプロキシ（例: Nginx, Apache）、APIゲートウェイなどを経由して、最終的なアプリケーションサーバーに到達することがよくあります。これらの各コンポーネントは、リクエストヘッダー、特に `Host` ヘッダーを解析し、それに基づいてルーティングや処理を行います。

もし `Host` ヘッダーが不正な形式である場合、各コンポーネントがそれを異なる方法で「修正」または「解釈」する可能性があります。例えば、あるプロキシはスペース以降を無視するかもしれませんが、別のプロキシはそれを有効なホスト名の一部と見なすかもしれません。この不一致が、前述のようなセキュリティ脆弱性の原因となります。

Goの `net/http` パッケージは、HTTPクライアントとサーバーの両方の機能を提供しており、クライアントとしてリクエストを送信する際、またはサーバーとしてリクエストを受信する際に `Host` ヘッダーを適切に処理することが求められます。このコミットは、特にGoのHTTPクライアントがリクエストを送信する際に、`Host` ヘッダーを「クリーン」に保つことに焦点を当てています。

## 技術的詳細

このコミットは、`net/http` パッケージ内の `Request` 構造体の `write` メソッドに `cleanHost` という新しいヘルパー関数を導入し、`Host` ヘッダーの処理を強化しています。

以前の `Request.write` メソッドでは、`req.Host` または `req.URL.Host` からホスト名を取得した後、`removeZone` 関数を適用してIPv6ゾーン識別子を削除していました。しかし、この処理では `Host` ヘッダー内に含まれる不正な文字（スペースやスラッシュ）は除去されませんでした。

新しい実装では、`Host` ヘッダーの値が実際に使用される前に `cleanHost` 関数によって処理されます。

`cleanHost` 関数のロジックは以下の通りです。

1.  入力文字列 `in` を受け取ります。
2.  `strings.IndexAny(in, " /")` を使用して、文字列 `in` 内で最初に出現するスペース (` `) またはスラッシュ (`/`) のインデックスを検索します。
3.  もしスペースまたはスラッシュが見つかった場合（`i != -1`）、その文字が出現する直前までの部分文字列（`in[:i]`）を返します。これにより、不正な文字以降の文字列が切り捨てられます。
4.  スペースもスラッシュも見つからなかった場合、元の文字列 `in` をそのまま返します。

この `cleanHost` 関数は、`Request.write` メソッド内で `Host` ヘッダーの値を決定する際に、`req.Host` と `req.URL.Host` の両方に適用されます。これにより、GoのHTTPクライアントが送信するリクエストの `Host` ヘッダーが、スペースやスラッシュを含まないクリーンな形式であることが保証されます。

また、`removeZone` 関数が適用されるタイミングも変更されています。以前は `cleanHost` の前に `removeZone` が適用されていましたが、このコミットでは `cleanHost` が適用された後に `removeZone` が適用されるように順序が変更されています。これは、まず不正な文字を除去し、その後にIPv6ゾーン識別子を処理するという、より論理的な処理順序を確立するためと考えられます。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下の3つのファイルに集中しています。

1.  **`src/net/http/request.go`**:
    *   `cleanHost` という新しいプライベート関数が追加されました。この関数は、入力文字列から最初に見つかるスペースまたはスラッシュ以降の文字を削除します。
        ```go
        // cleanHost strips anything after '/' or ' '.
        func cleanHost(in string) string {
        	if i := strings.IndexAny(in, " /"); i != -1 {
        		return in[:i]
        	}
        	return in
        }
        ```
    *   `(*Request).write` メソッド内で、`Host` ヘッダーの値を設定する際に、`cleanHost` 関数が呼び出されるようになりました。
        ```go
        // 変更前:
        // host := removeZone(req.Host)
        // ...
        // host = removeZone(req.URL.Host)

        // 変更後:
        host := cleanHost(req.Host) // まずHostヘッダーをクリーンアップ
        if host == "" {
        	if req.URL == nil {
        		return errors.New("http: Request.Write on Request with no Host or URL set")
        	}
        	host = cleanHost(req.URL.Host) // URLのホストもクリーンアップ
        }
        host = removeZone(host) // その後、IPv6ゾーン識別子を削除
        ```

2.  **`src/net/http/http_test.go`**:
    *   `TestCleanHost` という新しいテスト関数が追加されました。これは、`cleanHost` 関数の動作を検証するためのユニットテストです。様々な入力（正規のホスト名、スペースを含むホスト名、スラッシュを含むホスト名、スペースで始まるホスト名）に対して、期待される出力が得られるかを確認します。

3.  **`src/net/http/request_test.go`**:
    *   `TestRequestBadHost` という新しいテスト関数が追加されました。このテストは、不正な `Host` ヘッダー（スペースを含むURL）を持つリクエストが `Request.Write` メソッドによってどのように処理されるかを検証します。具体的には、`http://foo.com with spaces/after` のようなURLが与えられた場合でも、生成されるリクエストの `Host` ヘッダーが `Host: foo.com` となり、パスが `/after` となることを確認します。

## コアとなるコードの解説

`cleanHost` 関数の導入は、GoのHTTPクライアントが送信するリクエストの堅牢性とセキュリティを向上させる上で非常に重要です。

*   **`cleanHost` 関数の目的**: この関数は、`Host` ヘッダーの仕様に準拠しない文字（特にスペースとスラッシュ）を積極的に除去することで、不正な `Host` ヘッダーがそのままネットワークに流れることを防ぎます。これにより、中間プロキシやサーバーが `Host` ヘッダーを誤って解釈し、前述のようなセキュリティ脆弱性を引き起こすリスクを低減します。コミットメッセージにもあるように、「A malformed Host header can result in a malformed HTTP request. Clean them to avoid this.」という目的を直接的に達成します。

*   **`Request.write` メソッドへの組み込み**: `cleanHost` が `Request.write` メソッドに組み込まれたことで、GoのHTTPクライアントがリクエストを送信する際に、`Host` ヘッダーが自動的にクリーンアップされるようになりました。これは、開発者が明示的に `Host` ヘッダーを検証・修正する手間を省き、デフォルトで安全な挙動を提供するものです。`req.Host` と `req.URL.Host` の両方に適用されることで、`Host` フィールドが直接設定された場合でも、URLから派生した場合でも、一貫したクリーニングが保証されます。

*   **テストケースの追加**: `TestCleanHost` と `TestRequestBadHost` の追加は、この変更が意図通りに機能することを保証するために不可欠です。
    *   `TestCleanHost` は、`cleanHost` 単体のロジックが正しく、様々な不正な入力に対して期待されるクリーンな出力を生成することを確認します。
    *   `TestRequestBadHost` は、よりエンドツーエンドに近い形で、不正なURLを持つ `Request` オブジェクトが `Write` されたときに、最終的に生成されるHTTPリクエストの `Host` ヘッダーが正しくクリーンアップされていることを検証します。これにより、この修正が実際のHTTPリクエストの生成パイプライン全体で効果を発揮することを確認しています。

この修正は、HTTP/1.1の仕様に厳密に従うことで、Goの `net/http` パッケージがより堅牢で安全なHTTP通信を提供するための重要な一歩と言えます。

# [インデックス 23967] ファイルの概要

このコミットは、Goコンパイラにおける「半乗算（half multiply）」に関する問題を修正するものです。具体的には、定数による除算の最適化過程で発生する可能性のある、`OHMUL`（Half Multiply）演算子の誤った処理を修正し、正しいコードが生成されるようにします。

## 元コミット内容

`cmd/compile: fix half multiply issue`

`walkdiv`関数内で、`OMUL`ノードが作成され、`typecheck`に渡された後、演算子が`OHMUL`に戻される前に問題が発生していました。場合によっては、返されたノードが完全な乗算で発生した評価済みのリテラル定数であったため、結果として非シフト値と`OHMUL`演算子を持つリテラルノードになっていました。この変更により、`OHMUL`に対してコードが生成されるようになります。

このコミットは以下のIssueを修正します:
- Fixes #11358
- Fixes #11369

## 変更の背景

このコミットは、Goコンパイラが定数による除算を最適化する際に発生する特定のバグを修正するために導入されました。コンパイラは、除算を乗算とシフトの組み合わせに変換することで最適化を試みることがよくあります。このプロセスでは、特に大きな数値や特定の定数で除算する場合に、「半乗算（half multiply）」と呼ばれるテクニックが使用されることがあります。これは、乗算結果の上位ビット（高位部分）を利用するものです。

問題は、`walkdiv`というコンパイラの内部関数が、この最適化の過程で`OMUL`（通常の乗算）ノードを一時的に作成し、それを型チェック（`typecheck`）に渡していたことにありました。その後、このノードは`OHMUL`（半乗算）に変換されるはずでした。しかし、特定の条件下では、`typecheck`が`OMUL`ノードをリテラル定数として早期に評価してしまい、その結果、`OHMUL`演算子を持つにもかかわらず、シフトされていない（つまり、半乗算の意図が失われた）値を持つリテラルノードが生成されてしまうことがありました。これにより、`OHMUL`演算子に対する適切なコードが生成されず、誤った計算結果やパニックを引き起こす可能性がありました。

このバグは、GoのIssue #11358と#11369として報告されており、特に定数による除算が絡む特定のケースで顕在化していました。

## 前提知識の解説

### Goコンパイラの内部構造

Goコンパイラは、ソースコードを機械語に変換する過程で複数のステージを経ます。主要なステージには以下のようなものがあります。

1.  **パース (Parsing)**: ソースコードを抽象構文木（AST: Abstract Syntax Tree）に変換します。
2.  **型チェック (Type Checking)**: ASTの各ノードの型を解決し、型の一貫性を検証します。
3.  **ウォーク (Walking/Lowering)**: ASTを走査し、高レベルな操作を低レベルな操作に変換（lowering）したり、最適化を行ったりします。`walkdiv`はこのステージの一部です。
4.  **SSA (Static Single Assignment) フォームへの変換**: 最適化を容易にするために、コードをSSA形式に変換します。
5.  **コード生成 (Code Generation)**: SSA形式から最終的な機械語コードを生成します。

### 演算子ノード (Op Nodes)

Goコンパイラの内部では、ASTの各ノードは特定の演算子（Op）を表します。例えば、`OMUL`は通常の乗算、`ODIV`は除算を表します。このコミットで登場する`OHMUL`は、コンパイラが内部的に使用する特殊な演算子で、乗算結果の上位半分（Half Multiply）を意味します。これは、特に定数による除算を最適化する際に、除算を乗算とシフトの組み合わせに変換するアルゴリズム（例えば、"Magic Number"アルゴリズム）で利用されます。

### 定数による除算の最適化

整数除算は、CPUにとって乗算よりもコストの高い操作です。そのため、コンパイラは定数による除算（例: `x / 7`）を、より高速な乗算とビットシフトの組み合わせに変換する最適化を試みます。この最適化には、除数に応じた「マジックナンバー」と呼ばれる定数と、適切なビットシフト量を使用します。このマジックナンバーとの乗算結果の上位半分が、元の除算の結果に相当することがあります。この上位半分を取り出す操作が`OHMUL`に相当します。

### `walkdiv`関数

`walkdiv`関数は、Goコンパイラの`walk`ステージの一部で、除算演算子（`ODIV`）を処理し、最適化を行う役割を担っています。特に定数による除算の場合、この関数がマジックナンバーによる乗算とシフトのシーケンスに変換しようとします。

## 技術的詳細

この問題の核心は、コンパイラの`walk`ステージと`typecheck`ステージ間の相互作用にありました。

1.  **`walkdiv`の初期動作**: `walkdiv`関数は、定数除算を最適化するために、一時的に`OMUL`（通常の乗算）ノードを作成し、除数に対応するマジックナンバーを乗算する形にしていました。
2.  **`typecheck`への渡り**: この`OMUL`ノードは、その後`typecheck`関数に渡されます。`typecheck`は、ノードの型を検証し、場合によっては定数畳み込み（constant folding）などの最適化を実行します。
3.  **早期評価の問題**: 問題が発生したのは、`typecheck`がこの`OMUL`ノードを、まだ`OHMUL`に変換される前の段階で、リテラル定数として評価してしまった場合です。この早期評価により、ノードは通常の乗算結果（つまり、シフトされていない完全な値）を持つリテラル定数として確定してしまいます。
4.  **`OHMUL`への再変換の失敗**: `typecheck`から戻った後、`walkdiv`はノードの演算子を`OHMUL`に設定し直そうとしますが、既にノードがリテラル定数として評価され、その値が確定しているため、`OHMUL`が意図する「乗算結果の上位半分」というセマンティクスが失われていました。結果として、`OHMUL`演算子を持つにもかかわらず、その値は通常の乗算結果であり、コンパイラは`OHMUL`に対する適切なコードを生成できませんでした。
5.  **修正アプローチ**: このコミットの修正は、`walkdiv`が`typecheck`にノードを渡す前に、最初から`OHMUL`ノードとして作成するように変更することで、この問題を解決します。これにより、`typecheck`は`OHMUL`ノードとして処理し、早期評価が行われたとしても、その評価結果は`OHMUL`のセマンティクスに沿ったものとなるか、あるいは`OHMUL`に対するコード生成パスが正しく機能するようになります。

また、`align.go`と`typecheck.go`の変更は、`OHMUL`演算子がコンパイラの他の部分（例えば、アライメントチェックや型チェックのスイッチ文）で正しく認識され、処理されるようにするためのものです。これにより、`OHMUL`がコンパイラ全体で一貫して扱われるようになります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/walk.go`の変更

最も重要な変更は`walkdiv`関数内で行われています。以前は、定数除算の最適化のために、まず`OMUL`（通常の乗算）ノードを作成し、`typecheck`に渡していました。その後、`typecheck`から戻った後に`n1.Op = OHMUL`として演算子を`OHMUL`に明示的に変更していました。

```go
// 変更前
n1 := Nod(OMUL, nl, nc) // OMULノードとして作成
typecheck(&n1, Erv)     // typecheckに渡す
n1.Op = OHMUL           // 後からOHMULに変更
```

このシーケンスが問題を引き起こしていました。`typecheck`が`OMUL`ノードを処理する際に、そのノードがリテラル定数として評価されると、その値は通常の乗算結果として確定してしまいます。その後`n1.Op = OHMUL`と変更しても、ノードが保持する値は既に「半乗算」の意図とは異なるものになっており、結果として`OHMUL`に対する正しいコードが生成されませんでした。

修正後は、最初から`OHMUL`ノードとして作成し、`typecheck`に渡すように変更されています。

```go
// 変更後
n1 := Nod(OHMUL, nl, nc) // 最初からOHMULノードとして作成
typecheck(&n1, Erv)      // typecheckに渡す
// n1.Op = OHMUL の行は削除
```

これにより、`typecheck`は最初から`OHMUL`ノードとして処理するため、もし定数畳み込みが行われたとしても、その結果は`OHMUL`のセマンティクスに沿ったものとなるか、あるいは`OHMUL`に対するコード生成パスが正しく機能するようになります。これにより、コンパイラが定数除算を半乗算に最適化する際の正確性が保証されます。

### `src/cmd/compile/internal/gc/align.go`の変更

`align.go`の変更は、`OHMUL`演算子がコンパイラの内部で正しく認識され、処理されるようにするためのものです。`okfor`マップは、各演算子に対して許可される型や操作のリストを定義しています。`okfor[OHMUL] = okforarith[:]`の追加により、`OHMUL`が算術演算子として適切に扱われるようになり、型チェックやアライメントの段階でエラーが発生しないようになります。

### `src/cmd/compile/internal/gc/typecheck.go`の変更

`typecheck.go`の変更も同様に、`OHMUL`演算子が`typecheck`関数内で正しく処理されるようにするためのものです。`OpSwitch`は、特定の演算子に対して特別な処理を行うためのスイッチ文であり、ここに`OHMUL`を追加することで、`typecheck`が`OHMUL`ノードを認識し、適切な型チェックロジックを適用できるようになります。

### `test/fixedbugs/issue11369.go`の追加

このテストファイルは、修正されたバグを具体的に再現し、修正が正しく機能していることを検証するために追加されました。特に、`7 / "0"[0]`のような、文字リテラルを数値として扱い、それによる除算を行うケースが含まれています。これは、コンパイラが定数除算を最適化する際に、`OHMUL`が関与する典型的なシナリオです。テストでは、期待される結果（`0 / "0"[0]`が`0`、`48 / "0"[0]`が`1`、`5 * 48 / "0"[0]`が`5`）と比較することで、コンパイラの出力が正しいことを確認しています。

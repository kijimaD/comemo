# [インデックス 25165] ファイルの概要

このコミットは、GoランタイムがLinux上でメモリをOSに解放する際に発生する、仮想メモリ領域（VMA）の過剰な生成による「out of memory」や「cannot allocate memory」パニックの問題を解決します。特に、Transparent Huge Page (THP) の扱いを改善し、`MADV_NOHUGEPAGE` フラグの適用粒度を巨大ページ単位に調整することで、VMAの数を劇的に削減します。

## 変更の背景

このコミットは、GoランタイムがLinux上で直面していた2つの主要なメモリ管理問題に対処するために導入されました。

1.  **Transparent Huge Pages (THP) によるRSSの肥大化 (Issue #8832)**:
    LinuxカーネルのTransparent Huge Pages (THP) 機能は、メモリ性能を向上させるために、小さな4KBのページを自動的に2MBの巨大ページに結合します。しかし、Goランタイムが`MADV_DONTNEED`を使ってOSにメモリを解放しても、THPが有効な場合、カーネルの`khugepaged`デーモンが、部分的に解放された領域であっても巨大ページに結合しようとすることがありました。これにより、Goプロセスが実際に必要とする以上の物理メモリ（Resident Set Size: RSS）を保持し、メモリフットプリントが不必要に肥大化するという問題が発生していました。以前のコミット `7e1b61c` は、この問題へのワークアラウンドとして、`MADV_DONTNEED`で解放する領域に`MADV_NOHUGEPAGE`フラグを設定することで、THPによる巨大ページ化を抑制しようとしました。

2.  **VMA (Virtual Memory Area) の過剰な生成と制限 (Issue #12233)**:
    上記の`MADV_NOHUGEPAGE`フラグの導入は、新たな問題を引き起こしました。`MADV_NOHUGEPAGE`フラグは、メモリ領域ごとに設定されるため、異なるフラグを持つ領域は別々のVMA（メモリマッピング）として管理されます。Goランタイムが細粒度で`MADV_NOHUGEPAGE`を設定すると、仮想アドレス空間内に多数のVMAが生成されることになります。Linuxシステムでは、デフォルトでプロセスあたりのVMA数に `65530` という制限（`sysctl vm.max_map_count`）があります。ヒープが大きく、ランタイムが頻繁にメモリを解放・再利用する（スカベンジングする）ような状況では、このVMA制限にすぐに達してしまい、「out of memory」や「cannot allocate memory」といったパニックが発生する可能性がありました。これは、物理メモリが十分に利用可能であるにもかかわらず、仮想メモリ管理の制約によってアプリケーションがクラッシュするという深刻な問題でした。

このコミットは、これらの問題、特にVMAの過剰生成によるパニックを解決することを目的としています。

## 前提知識の解説

### 1. Linuxのメモリ管理と仮想メモリ領域 (VMA)

*   **仮想メモリ (Virtual Memory)**: 各プロセスは、物理メモリとは独立した独自の仮想アドレス空間を持ちます。これにより、プロセスは連続したメモリ空間を持っているかのように振る舞うことができます。
*   **仮想メモリ領域 (Virtual Memory Area, VMA)**: Linuxカーネルは、プロセスの仮想アドレス空間をVMAと呼ばれるセグメントに分割して管理します。各VMAは、連続した仮想アドレス範囲、その範囲に対応する物理メモリ（またはファイル）、およびアクセス権限（読み取り、書き込み、実行）やメモリポリシー（例: Huge Pageの利用可否）などの属性を持ちます。コードセグメント、データセグメント、ヒープ、スタック、共有ライブラリ、メモリマップドファイルなどがそれぞれVMAとして表現されます。
*   **`vm.max_map_count`**: Linuxカーネルパラメータの一つで、1つのプロセスが持つことができるVMAの最大数を制限します。デフォルト値は通常65530です。この制限を超えると、新たなメモリマッピングの作成が失敗し、アプリケーションがクラッシュする原因となります。

### 2. Transparent Huge Pages (THP)

*   **概要**: Linuxカーネルの機能で、アプリケーションの変更なしに、通常の4KBページをより大きな2MB（x86-64の場合）の「巨大ページ」に自動的に結合しようとします。これにより、TLB (Translation Lookaside Buffer) ミスを減らし、メモリ性能を向上させることが期待されます。
*   **`khugepaged`**: THPの管理を行うカーネルデーモンです。メモリをスキャンし、連続する4KBページを巨大ページに結合する役割を担います。
*   **問題点**: データベースやガベージコレクションを持つランタイムなど、メモリのアクセスパターンが不規則なアプリケーションでは、THPが逆に性能を低下させたり、メモリフットプリントを肥大化させたりする可能性があります。これは、巨大ページ内の小さな領域が解放されても、巨大ページ全体が解放されない限り物理メモリがOSに戻されないため、メモリの断片化を引き起こすためです。

### 3. `madvise` システムコール

*   **概要**: `madvise(2)` は、アプリケーションが特定のメモリ領域の利用パターンについてカーネルに「助言（advice）」を与えるためのシステムコールです。カーネルはこの助言を参考に、メモリ管理を最適化しようとしますが、必ずしもその助言に従うとは限りません。
*   **`MADV_DONTNEED`**: 指定されたメモリ領域が、もはやアプリケーションによって必要とされないことをカーネルに伝えます。カーネルは、この領域に対応する物理ページを解放し、RSSを削減することができます。次にこの領域にアクセスがあった場合、ページフォルトが発生し、必要に応じてゼロフィルされたページが割り当てられます。
*   **`MADV_NOHUGEPAGE`**: 指定されたメモリ領域に対して、THPによる巨大ページの使用を無効にするようカーネルに助言します。これにより、`khugepaged`がその領域を巨大ページに結合するのを防ぎます。
*   **`MADV_HUGEPAGE`**: 指定されたメモリ領域に対して、THPによる巨大ページの使用を有効にするようカーネルに助言します。

### 4. Goランタイムのメモリ管理

Goランタイムは、独自のメモリヒープを管理し、ガベージコレクタと連携してメモリの割り当てと解放を行います。OSへのメモリの解放には、`madvise`システムコールが利用されます。Goのメモリ管理は、パフォーマンスと効率性を両立させるために、OSのメモリ管理機能と密接に連携しています。

## 技術的詳細

このコミットの技術的詳細なアプローチは、以前の`MADV_NOHUGEPAGE`の適用方法がVMAの過剰生成を引き起こした問題に対し、より賢明な戦略を採用することにあります。

以前のコミット `7e1b61c` では、Goランタイムが`MADV_DONTNEED`でOSにメモリを解放する際、その領域全体に`MADV_NOHUGEPAGE`フラグを設定していました。これは、THPによるRSS肥大化を防ぐための有効な手段でしたが、問題はGoランタイムがメモリを細粒度で解放する可能性がある点にありました。例えば、2MBの巨大ページ内に4KBの小さな領域が解放されるたびに`MADV_NOHUGEPAGE`を設定すると、その4KBの領域だけが異なるフラグを持つことになり、結果として新しいVMAが生成されていました。

このコミットは、このVMAの爆発的な増加を防ぐために、`MADV_NOHUGEPAGE`フラグの適用粒度を「巨大ページ単位」に制限します。

具体的には：
1.  **巨大ページ境界へのアラインメント**: `sysUnused`関数（メモリをOSに解放する際に呼び出される）では、解放対象のメモリ領域 `[v, v+n)` の開始アドレス `v` と終了アドレス `v+n-1` が属する巨大ページを特定します。
2.  **境界巨大ページのみの調整**: `MADV_NOHUGEPAGE`フラグは、解放領域の開始アドレス `v` を含む巨大ページと、終了アドレス `v+n-1` を含む巨大ページに対してのみ設定されます。これらの巨大ページがアラインされていない場合（つまり、解放領域が巨大ページの途中から始まったり途中で終わったりする場合）にのみ、`madvise(..., _MADV_NOHUGEPAGE)` が呼び出されます。
3.  **中間領域の維持**: 解放領域の中間にある、完全に巨大ページにアラインされた領域については、`MADV_NOHUGEPAGE`フラグは設定されません。これにより、これらの領域は引き続き巨大ページが有効な状態に保たれます。
4.  **`sysUsed`での`MADV_HUGEPAGE`の適用**: `sysUsed`関数（OSからメモリを再利用する際に呼び出される）では、巨大ページ境界に完全にアラインされた領域に対してのみ`MADV_HUGEPAGE`フラグを設定し、THPを再度有効にします。これにより、Goランタイムが実際に使用する大きなメモリ領域は、THPの恩恵を受けられるようになります。

この戦略により、`MADV_NOHUGEPAGE`フラグが設定されるVMAの数が大幅に削減されます。コミットメッセージによると、amd64環境で最悪のケース（`MADV_NOHUGEPAGE`と`MADV_HUGEPAGE`が交互に設定されるヒープ）でも、VMA制限に達するには128GBのヒープが必要になると推定されています。また、ランタイムベンチマークでは、`GODEBUG=scavenge=1` の条件下でVMAの最大数が692から49に減少したと報告されており、この変更の有効性が示されています。

## コアとなるコードの変更箇所

変更は `src/runtime/mem_linux.go` ファイルに集中しています。

### `sysUnused` 関数の変更

*   以前は、`hugePageSize`でアラインされていない領域全体に対して`madvise(v, n, _MADV_NOHUGEPAGE)`を無条件に呼び出していました。
*   変更後、`hugePageSize != 0` の場合にのみ処理が実行されます。
*   解放対象のメモリ領域 `[v, v+n)` の開始アドレス `v` と終了アドレス `v+n-1` が属する巨大ページのアドレス (`head`, `tail`) を計算します。
*   `head` と `tail` が計算された場合（つまり、`v` または `v+n-1` が巨大ページ境界にアラインされていない場合）、その巨大ページに対してのみ `madvise(..., _MADV_NOHUGEPAGE)` を呼び出します。
*   `head` と `tail` が隣接する巨大ページである場合は、1回の `madvise` 呼び出しで処理します。
*   最後に、変更前と同様に `madvise(v, n, _MADV_DONTNEED)` を呼び出して、OSにメモリが不要であることを伝えます。

### `sysUsed` 関数の変更

*   以前は、`hugePageSize != 0` の場合に、`madvise(v, n, _MADV_HUGEPAGE)` を無条件に呼び出して、`sysUnused`で設定された`NOHUGEPAGE`マークを元に戻していました。
*   変更後、`hugePageSize != 0` の場合にのみ処理が実行されます。
*   メモリ領域 `[v, v+n)` のうち、巨大ページ境界に完全にアラインされた中間部分 `[beg, end)` を計算します。
*   `beg < end` の場合、この中間部分に対してのみ `madvise(unsafe.Pointer(beg), end-beg, _MADV_HUGEPAGE)` を呼び出し、THPを有効にします。これにより、`v` と `v+n` の端点にある巨大ページは、`NOHUGEPAGE`のままになる可能性がありますが、これはVMAの数を抑えるためのトレードオフです。

## コアとなるコードの解説

### `sysUnused` 関数 (メモリをOSに解放する際)

```go
func sysUnused(v unsafe.Pointer, n uintptr) {
	// ... (コメントは省略) ...
	if hugePageSize != 0 {
		var s uintptr = hugePageSize

		var head, tail uintptr
		if uintptr(v)%s != 0 { // vが巨大ページ境界にアラインされていない場合
			head = uintptr(v) &^ (s - 1) // vを含む巨大ページの開始アドレスを計算
		}
		if (uintptr(v)+n)%s != 0 { // v+nが巨大ページ境界にアラインされていない場合
			tail = (uintptr(v) + n - 1) &^ (s - 1) // v+n-1を含む巨大ページの開始アドレスを計算
		}

		// madviseはフラグが既に設定されている場合にEINVALを返す可能性があるが、エラーは無視する。
		if head != 0 && head+hugePageSize == tail {
			// headとtailが異なるが隣接している場合、1回の呼び出しで処理
			madvise(unsafe.Pointer(head), 2*hugePageSize, _MADV_NOHUGEPAGE)
		} else {
			// vとv+n-1を含む巨大ページにアドバイス
			if head != 0 {
				madvise(unsafe.Pointer(head), hugePageSize, _MADV_NOHUGEPAGE)
			}
			if tail != 0 && tail != head {
				madvise(unsafe.Pointer(tail), hugePageSize, _MADV_NOHUGEPAGE)
			}
		}
	}
	madvise(v, n, _MADV_DONTNEED) // 常にMADV_DONTNEEDを呼び出す
}
```

この変更の核心は、`MADV_NOHUGEPAGE`を適用する範囲を、解放されるメモリ領域の「端点」が属する巨大ページに限定することです。
*   `head` と `tail` の計算は、解放される領域 `[v, v+n)` が巨大ページの境界とどのように重なっているかを特定します。
*   `uintptr(v)%s != 0` は、`v` が巨大ページ境界で始まっていないことを意味します。この場合、`v` を含む巨大ページの開始アドレス `head` を計算します。
*   `(uintptr(v)+n)%s != 0` は、解放領域の終了が巨大ページ境界で終わっていないことを意味します。この場合、`v+n-1` を含む巨大ページの開始アドレス `tail` を計算します。
*   `madvise(..., _MADV_NOHUGEPAGE)` は、これらの「境界巨大ページ」に対してのみ呼び出されます。これにより、解放領域の中央にある、完全に巨大ページにアラインされた部分は`MADV_NOHUGEPAGE`の影響を受けず、VMAの分割が抑制されます。

### `sysUsed` 関数 (OSからメモリを再利用する際)

```go
func sysUsed(v unsafe.Pointer, n uintptr) {
	if hugePageSize != 0 {
		// sysUnusedで設定されたNOHUGEPAGEマークを部分的に元に戻す
		// vとv+nの間の完全な巨大ページに対してのみ。
		// これにより、vとv+nの端点では巨大ページが無効のままになる可能性があるが、
		// 隣接する割り当てが解放されるとsysUnusedがNOHUGEPAGEを再度設定するため、
		// そのコストに見合うものではない。
		var s uintptr = hugePageSize

		// vを巨大ページ境界に切り上げる
		beg := (uintptr(v) + (s - 1)) &^ (s - 1)
		// v+nを巨大ページ境界に切り下げる
		end := (uintptr(v) + n) &^ (s - 1)

		if beg < end {
			madvise(unsafe.Pointer(beg), end-beg, _MADV_HUGEPAGE)
		}
	}
}
```

`sysUsed`関数では、GoランタイムがOSからメモリを再利用する際に、その領域を再び巨大ページ対応にするための処理が行われます。
*   `beg` と `end` の計算は、再利用される領域 `[v, v+n)` のうち、完全に巨大ページ境界にアラインされた「中間部分」を特定します。
*   `madvise(unsafe.Pointer(beg), end-beg, _MADV_HUGEPAGE)` は、この中間部分に対してのみ呼び出されます。これにより、Goランタイムが実際に使用する大きなメモリブロックはTHPの恩恵を受けられるようになります。
*   `sysUnused`と同様に、端点の巨大ページは`MADV_HUGEPAGE`の影響を受けない可能性があります。これは、VMAの数を最小限に抑えるための意図的な設計選択です。

これらの変更により、GoランタイムはTHPの利点を享受しつつ、VMAの過剰な生成によるシステムリソースの枯渇を防ぐ、より堅牢なメモリ管理を実現しています。

# [インデックス 25822] ファイルの概要

このコミットは、Go言語の標準ライブラリである`syscall`パッケージ内の`src/syscall/exec_plan9.go`ファイルに対する変更です。このファイルは、Plan 9オペレーティングシステム上で新しいプロセスをフォーク（複製）し、実行（`exec`）する際の低レベルなシステムコール処理を実装しています。具体的には、`forkAndExecInChild`関数内で子プロセスが不要なファイルディスクリプタを閉じる際の挙動が修正されています。

## 変更の背景

このコミットは、Plan 9オペレーティングシステム環境におけるGoプログラムの挙動に関するバグ修正を目的としています。具体的には、マルチプロセッサマシン上で`forkAndExecInChild`関数が実行される際に、ファイルディスクリプタ（FD）が誤って二重に閉じられる可能性がありました。

Plan 9の`close()`システムコールは、既に閉じられているFDに対して呼び出された場合、「fd out of range or not open」（ファイルディスクリプタが範囲外であるか、開かれていない）というエラーを返します。このエラーが`forkAndExecInChild`内で捕捉されると、関数全体が失敗し、結果として新しい子プロセスの生成と実行が妨げられていました。

他の多くのオペレーティングシステムでは、既に閉じられたFDを再度閉じようとしても、通常はエラーとして扱われないか、致命的ではない警告として処理されます。このコミットは、Plan 9におけるこの特定の挙動を他のOSと整合させ、二重クローズによる不必要なエラー発生を防ぐことで、`forkAndExecInChild`の堅牢性と信頼性を向上させることを目的としています。この問題はGo issue #12851として報告されていました。

## 前提知識の解説

このコミットの理解を深めるために、以下の技術的概念について解説します。

*   **ファイルディスクリプタ (File Descriptor, FD)**:
    オペレーティングシステムがファイル、ソケット、パイプなどのI/Oリソースを識別するために使用する、プロセスごとの一意な非負の整数値です。プロセスはFDを通じてこれらのリソースにアクセスし、読み書きや制御を行います。

*   **`close()` システムコール**:
    指定されたファイルディスクリプタに関連付けられたリソースを解放し、そのFDを無効にするためのシステムコールです。これにより、OSはFDを再利用できるようになり、リソースリークを防ぎます。通常、成功時には0を返し、失敗時にはエラーコード（Unix系では-1）を返します。

*   **`forkAndExecInChild` 関数**:
    Go言語の`syscall`パッケージが提供する、新しいプロセスを生成し、その中で別のプログラムを実行するための低レベルな関数です。これはUnix系OSの`fork()`（現在のプロセスを複製して子プロセスを作成）と`exec()`（子プロセス内で新しいプログラムを実行）の組み合わせに相当します。子プロセスが生成される際には、親プロセスから継承したファイルディスクリプタのうち、子プロセスにとって不要なものを閉じる処理が一般的に行われます。

*   **Plan 9 オペレーティングシステム**:
    ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、「すべてをファイルとして扱う」という原則を徹底しています。ネットワークリソース、デバイス、プロセスなどもファイルシステムを通じてアクセスされます。Go言語の設計にはPlan 9の影響が強く見られます。

*   **マルチプロセッサマシン**:
    複数のCPUコアやプロセッサを持つコンピュータシステムです。これにより、複数のタスクやスレッドが同時に実行される並行処理が可能になります。しかし、複数の実行パスが共有リソース（この場合はファイルディスクリプタ）にアクセスする際に、競合状態（レースコンディション）が発生しやすくなります。

*   **`RawSyscall`**:
    Go言語の`syscall`パッケージが提供する関数で、オペレーティングシステムの生（raw）のシステムコールを直接呼び出すためのインターフェースです。これはGoランタイムがOSと直接対話する際に使用され、通常の`syscall.Syscall`よりもさらに低レベルな制御を可能にします。

## 技術的詳細

この問題の核心は、マルチプロセッサ環境下での`forkAndExecInChild`関数におけるファイルディスクリプタのライフサイクル管理にあります。

1.  **問題の発生メカニズム**:
    `forkAndExecInChild`関数は、子プロセスが起動する前に、親プロセスから継承した多数のファイルディスクリプタの中から、子プロセスにとって不要なものを閉じる必要があります。マルチプロセッサマシンでは、複数のゴルーチン（Goの軽量スレッド）が並行して動作する可能性があり、特定のファイルディスクリプタを閉じる処理が、意図せず複数回実行されるレースコンディションが発生し得ました。

2.  **Plan 9の`close()`挙動**:
    Plan 9の`close()`システムコールは、既に閉じられているファイルディスクリプタに対して呼び出された場合、厳密にエラー（「fd out of range or not open」）を返します。これは、無効なFDへの操作を明確にエラーとして扱う設計思想によるものです。

3.  **エラーの連鎖**:
    `forkAndExecInChild`関数内の既存のロジックでは、`close()`システムコールの戻り値をチェックし、エラー（-1）が返された場合には`childerror`ラベルにジャンプして、子プロセスの生成処理全体を失敗させていました。このため、二重クローズが発生すると、子プロセスが起動できなくなるという問題が生じていました。

4.  **変更の意図と安全性**:
    このコミットの変更は、`close()`システムコールがエラーを返した場合でも、それが「既に閉じられている」ことに起因するものであれば、実質的な問題はないという判断に基づいています。ファイルディスクリプタが最終的に閉じられている状態であれば、リソースリークなどの深刻な問題には繋がりません。他の多くのOSでは、このような二重クローズは許容されるか、致命的ではないエラーとして扱われるため、Plan 9の挙動をこれに合わせることで、Goプログラムの移植性と堅牢性を高めています。エラーチェックを省略することで、不必要なプロセス起動の失敗を防ぎ、システムの安定性を向上させる効果があります。

## コアとなるコードの解説

変更は`src/syscall/exec_plan9.go`ファイル内の`forkAndExecInChild`関数に集中しています。

この関数には、子プロセスが親プロセスから継承したファイルディスクリプタのうち、子プロセスにとって不要なものを閉じるためのループが存在します。

*   **変更前**:
    ```go
    		r1, _, _ = RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)
    		if int32(r1) == -1 {
    			goto childerror
    		}
    ```
    変更前は、`RawSyscall`を通じて`SYS_CLOSE`（`close()`システムコール）を呼び出した後、その戻り値`r1`を厳密にチェックしていました。もし`r1`が`-1`（エラーを示す一般的な値）であれば、`goto childerror`文によって関数内のエラー処理ルーチンにジャンプし、`forkAndExecInChild`関数全体を失敗させていました。

*   **変更後**:
    ```go
    		RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)
    ```
    変更後は、`RawSyscall(SYS_CLOSE, ...)`の呼び出しはそのままですが、その戻り値（`r1`）を受け取らず、エラーチェックも完全に削除されています。これにより、`close()`システムコールがエラーを返したとしても、そのエラーは無視され、`forkAndExecInChild`関数は処理を続行します。

この変更の意図は、前述の通り、ファイルディスクリプタが二重に閉じられた場合にPlan 9の`close()`が返すエラーを無視することで、不必要なプロセス起動の失敗を防ぎ、他のOSでの挙動との一貫性を持たせることにあります。

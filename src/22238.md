# [インデックス 22238] ファイルの概要

このコミットは、Goのクロスコンパイル環境において、コンパイラ（`9g`などのツール）がデフォルトでターゲットとする`GOOS`（オペレーティングシステム）と`GOARCH`（アーキテクチャ）が、ビルド元の環境ではなく、クロスコンパイルのターゲット環境に正しく設定されるように修正するものです。これにより、クロスコンパイルされたコンパイラが、その実行環境で期待されるターゲットのオブジェクトファイルを生成するようになります。

## 元コミット内容

`cmd/dist`: クロスコンパイル時のデフォルト`GOOS`/`GOARCH`を修正。

この変更以前は、`darwin/amd64`マシン上で`linux/ppc64`向けに`9g`（Goコンパイラ）をクロスコンパイルした場合、その`9g`をターゲットマシンにコピーして実行すると、デフォルトのオブジェクトターゲットが`darwin/amd64`であると認識されていました。これは実用的ではありませんでした。この変更により、このようなケースではデフォルトのターゲットが`linux/ppc64`になるように修正され、より実用的になりました。

## 変更の背景

Go言語は、異なるオペレーティングシステムやアーキテクチャ向けにバイナリを生成する「クロスコンパイル」機能を強力にサポートしています。しかし、このコミット以前には、クロスコンパイルされたGoツールチェイン（特にコンパイラやリンカなどのビルドツール）自体が、そのツールが動作する環境（ホスト環境）の`GOOS`と`GOARCH`をデフォルトのターゲットとして認識してしまうという問題がありました。

具体的には、`darwin/amd64`（macOS上のIntel 64-bit）環境で`GOOS=linux GOARCH=ppc64`を設定して`9g`コンパイラをビルドした場合、生成された`9g`バイナリは`linux/ppc64`環境で実行されることを意図しています。しかし、この`9g`が内部的に持つデフォルトのターゲット情報は、ビルド元の`darwin/amd64`のままでした。そのため、`linux/ppc64`マシン上でこの`9g`を使ってGoのソースコードをコンパイルしようとすると、`9g`はデフォルトで`darwin/amd64`向けのオブジェクトファイルを生成しようとし、期待通りの動作をしませんでした。

この問題は、Goのクロスコンパイル環境の利便性を著しく損なうものであり、クロスコンパイルされたツールチェインが、そのツールチェインが動作するターゲット環境のデフォルト`GOOS`/`GOARCH`を正しく認識するように修正する必要がありました。

## 前提知識の解説

*   **GOOSとGOARCH**:
    *   `GOOS` (Go Operating System): Goプログラムが実行されるオペレーティングシステム（例: `linux`, `windows`, `darwin`）。
    *   `GOARCH` (Go Architecture): Goプログラムが実行されるCPUアーキテクチャ（例: `amd64`, `arm`, `ppc64`）。
    *   Goのビルドシステムでは、これらの環境変数を設定することで、異なるOSやアーキテクチャ向けのバイナリを生成できます。

*   **クロスコンパイル**:
    *   あるプラットフォーム（ホスト環境）で、別のプラットフォーム（ターゲット環境）向けの実行可能ファイルをビルドすること。
    *   Goは、`GOOS`と`GOARCH`環境変数を設定するだけで簡単にクロスコンパイルが可能です。例えば、macOS上でLinux向けのバイナリをビルドする場合、`GOOS=linux GOARCH=amd64 go build`のように実行します。

*   **`cmd/dist`**:
    *   Goのソースコードリポジトリ内のディレクトリの一つで、Goツールチェイン自体のビルドプロセスを管理するツールが含まれています。
    *   `go tool dist`コマンドを通じて利用され、Goのコンパイラ、リンカ、アセンブラなどのツールをビルドするために使用されます。
    *   Goのブートストラッププロセス（Go自身をGoでビルドするプロセス）において重要な役割を果たします。

*   **`9g` (Goコンパイラ)**:
    *   Go 1.4以前のGoツールチェインにおいて、`gc`（Goコンパイラ）のフロントエンドを指すコマンド名でした。Go 1.5以降は`go tool compile`に統合されていますが、このコミットが作成された2015年3月時点ではまだ`9g`という名称が使われていました。
    *   Goのソースコードをコンパイルしてオブジェクトファイルを生成する役割を担います。

*   **`mkzbootstrap`関数**:
    *   `src/cmd/dist/buildruntime.go`ファイル内に存在する関数で、Goツールチェインのビルド時に、Goのランタイムやツールが使用する定数（`defaultGOROOT`, `defaultGOOS`, `defaultGOARCH`など）を含む`zbootstrap.go`というファイルを自動生成します。
    *   この自動生成されたファイルは、Goツールチェインの各コンポーネントが、自身の実行環境やデフォルトのターゲット環境を認識するために利用されます。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/dist/buildruntime.go`ファイル内の`mkzbootstrap`関数が生成する`zbootstrap.go`ファイルの内容を変更することにあります。

変更前は、`zbootstrap.go`内で定義される`defaultGOOS`と`defaultGOARCH`の定数は、Goツールチェインをビルドしたホスト環境の`GOOS`と`GOARCH`（`gohostos`と`gohostarch`という変数で表現される）が直接埋め込まれていました。

```go
// 変更前 (簡略化)
const defaultGOOS = `%s` // ここにgohostosの値が埋め込まれる
const defaultGOARCH = `%s` // ここにgohostarchの値が埋め込まれる
```

この挙動が、クロスコンパイルされたツールチェインが誤ったデフォルトターゲットを持つ原因でした。

このコミットでは、`defaultGOOS`と`defaultGOARCH`の定義を、Goの標準ライブラリである`runtime`パッケージの`runtime.GOOS`と`runtime.GOARCH`を参照するように変更しました。

```go
// 変更後 (簡略化)
import "runtime"

const defaultGOOS = runtime.GOOS
const defaultGOARCH = runtime.GOARCH
```

`runtime.GOOS`と`runtime.GOARCH`は、Goプログラムが実際に実行されている環境のOSとアーキテクチャを動的に取得する定数です。これにより、クロスコンパイルされた`9g`コンパイラが`linux/ppc64`マシン上で実行されると、`runtime.GOOS`は`linux`を、`runtime.GOARCH`は`ppc64`を返し、`9g`は自身のデフォルトターゲットを正しく`linux/ppc64`と認識するようになります。

この変更は、Goツールチェインのビルドプロセスにおける重要な改善であり、クロスコンパイルされたツールチェインの振る舞いをより直感的で実用的なものにしました。

## コアとなるコードの変更箇所

変更は`src/cmd/dist/buildruntime.go`ファイルに集中しています。

具体的には、`mkzbootstrap`関数内で`zbootstrap.go`ファイルを生成する際の文字列フォーマットが変更されました。

*   `import "runtime"`の行が追加されました。
*   `defaultGOOS`と`defaultGOARCH`の定数定義が、ハードコードされた文字列から`runtime.GOOS`と`runtime.GOARCH`への参照に変わりました。
*   それに伴い、`fmt.Sprintf`に渡す引数の数が調整されました。

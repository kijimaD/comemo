# [インデックス 23654] ファイルの概要

このコミットは、Go言語の`internal`パッケージルールの適用範囲を拡張するものです。具体的には、Go 1.4で導入された当初は`$GOROOT`内のパッケージにのみ適用されていた`internal`パッケージのインポート制限を、Go 1.5からは`$GOPATH`を含むすべてのリポジトリ内のパッケージに適用するように変更します。これにより、Goのパッケージエコシステム全体で、より厳格な内部APIの隠蔽とモジュール化が可能になります。

## 変更の背景

Go言語では、大規模なプロジェクトやライブラリにおいて、外部に公開すべきではない内部実装の詳細を隠蔽するためのメカニズムが求められていました。Go 1.4で導入された`internal`パッケージルールは、この目的のために設計されました。このルールは、ディレクトリ名に`internal`を含むパッケージは、その`internal`ディレクトリの親ディレクトリをルートとするツリー内のコードからのみインポートが許可されるというものです。これにより、ライブラリの内部構造が外部のユーザーに誤って利用されたり、依存されたりすることを防ぎ、APIの安定性を保つことが可能になります。

しかし、Go 1.4での`internal`ルールの初期実装では、この制限がGoの標準ライブラリが置かれている`$GOROOT`内のパッケージにのみ適用されていました。これは、サードパーティのライブラリやユーザー自身のプロジェクトが`$GOPATH`に配置される場合、`internal`ルールによる恩恵を受けられないという制限を意味していました。

このコミットは、この制限を解消し、`internal`パッケージルールを`$GOPATH`を含むすべてのリポジトリに拡張することを目的としています。`golang.org/s/go14internal`で示されているように、この拡張はGo 1.5での計画的な変更であり、Goエコシステム全体でのモジュール性とカプセル化を強化するための重要なステップでした。コミットメッセージにある`Fixes #10479`は、この制限に関する具体的な問題提起や議論があったことを示唆しています。

## 前提知識の解説

*   **Goのパッケージシステム**: Goのコードはパッケージという単位で組織されます。各パッケージは特定のディレクトリに対応し、関連する機能やデータ型をカプセル化します。`import`文を使って他のパッケージの機能を利用できます。
*   **`internal`パッケージルール**: Go 1.4で導入された、パッケージの可視性を制限するための特殊なルールです。`internal`という名前のディレクトリに含まれるパッケージは、その`internal`ディレクトリの直上の親ディレクトリをルートとするディレクトリツリー内のコードからのみインポートが許可されます。このルールにより、ライブラリ開発者は、外部に公開したくない内部実装用のパッケージを安全に作成できます。
    *   例: `github.com/user/repo/foo/internal/bar`というパッケージがある場合、`github.com/user/repo/foo`以下のパッケージからは`bar`をインポートできますが、`github.com/user/repo/baz`や`github.com/another/repo`からはインポートできません。
*   **`$GOROOT`と`$GOPATH`**:
    *   **`$GOROOT`**: Go言語のインストールディレクトリを指します。Goの標準ライブラリのソースコードがここに格納されています。
    *   **`$GOPATH`**: Go 1.11以前のGoプロジェクトのワークスペースディレクトリを指します。ユーザーが開発するプロジェクトや、`go get`で取得したサードパーティのライブラリのソースコードがここに配置されます。Go Modulesの導入後はその重要性が低下しましたが、このコミットが作成された時点ではGoのパッケージ管理において中心的な役割を担っていました。
*   **カプセル化**: オブジェクト指向プログラミングの重要な原則の一つで、データとそれを操作するメソッドを一つの単位（オブジェクトやパッケージ）にまとめ、外部からの直接的なアクセスを制限することです。これにより、内部実装の変更が外部に影響を与えるリスクを減らし、システムの保守性と堅牢性を高めます。`internal`パッケージルールは、Goにおけるカプセル化の一形態と言えます。

## 技術的詳細

このコミットの技術的な核心は、Goコマンド（`cmd/go`）が`internal`パッケージルールを適用するロジックの変更にあります。

以前のGo 1.4では、`src/cmd/go/pkg.go`ファイル内の`disallowInternal`関数が`internal`パッケージのインポート制限を処理していました。この関数には、以下の条件分岐が含まれていました。

```go
// Only applies to $GOROOT.
if !p.Standard {
    return p
}
```

ここで、`p.Standard`はインポートされるパッケージがGoの標準ライブラリの一部であるかどうかを示すブール値です。この条件は、「インポートされるパッケージが標準ライブラリではない場合（つまり、`$GOPATH`内のパッケージである可能性が高い場合）、`internal`ルールを適用せずに早期にリターンする」ことを意味していました。結果として、`internal`ルールは`$GOROOT`内のパッケージに限定されていました。

このコミットでは、上記の`if !p.Standard { return p }`という7行のコードブロックが完全に削除されました。この変更により、`disallowInternal`関数は、インポートされるパッケージが標準ライブラリであるかどうかにかかわらず、すべてのパッケージに対して`internal`ルールを無条件に適用するようになります。

この変更の直接的な結果として、`$GOPATH`に配置されたサードパーティのライブラリやユーザー自身のアプリケーションでも、`internal`ディレクトリを使用して内部APIを隠蔽できるようになりました。これにより、Goのパッケージ管理におけるカプセル化のメカニズムがより普遍的に利用可能となり、大規模なGoプロジェクトの構造化と保守性が向上しました。

また、この変更に伴い、`src/cmd/go/test.bash`内のテストスクリプトも更新されました。以前のテストは「`$GOROOT`外の`internal`パッケージは尊重されない」ことを期待していましたが、このコミット後は「`$GOROOT`外の`internal`パッケージも尊重される（Go 1.5以降）」ことを期待するように修正されました。具体的には、`./testgo build -v ./testdata/testinternal2`コマンドが成功する（つまり、`internal`パッケージがインポートできてしまう）ことを「誤った成功」とみなし、ビルドが失敗する（インポートが拒否される）ことを期待するようにテストロジックが反転されました。これにより、Go 1.5での`internal`ルールの完全な適用が保証されます。

## コアとなるコードの解説

### `src/cmd/go/pkg.go`の変更

`disallowInternal`関数は、Goコマンドがパッケージのインポートパスを解析する際に、`internal`パッケージルールの制約をチェックする主要なロジックを含んでいます。以前のバージョンでは、この関数はインポートされるパッケージが標準ライブラリ（`p.Standard`が`true`）である場合にのみ、`internal`ルールのチェックを実行していました。`!p.Standard`という条件が`true`の場合、つまり標準ライブラリではないパッケージの場合には、関数はすぐにリターンし、`internal`ルールのチェックをスキップしていました。

このコミットでは、この`if !p.Standard { return p }`というガード節が削除されました。これにより、`disallowInternal`関数は、インポートされるパッケージが標準ライブラリであるか否かに関わらず、常に`internal`パッケージルールのチェックロジックを実行するようになります。この変更が、`$GOPATH`内のパッケージに対しても`internal`ルールが適用されるようになった直接的な原因です。

### `src/cmd/go/test.bash`の変更

テストスクリプト`test.bash`は、Goコマンドの動作を検証するためのシェルスクリプトです。このコミットでは、`internal`パッケージルールの適用範囲が拡大されたことを確認するために、関連するテストケースが更新されました。

以前のテストは、`$GOROOT`外の`internal`パッケージが「尊重されない」、つまり、そのインポートが許可されることを期待していました。しかし、このコミットによってルールが拡張されたため、テストの期待値が反転しました。新しいテストでは、`./testgo build -v ./testdata/testinternal2`コマンドが成功した場合（つまり、`internal`パッケージのインポートが許可されてしまった場合）を「誤った成功」とみなし、`ok=false`を設定してテストを失敗させます。そして、ビルド出力に「`use of internal package not allowed`」というエラーメッセージが含まれていることを確認することで、`internal`パッケージのインポートが正しく拒否されたことを検証しています。この変更は、Go 1.5以降の`internal`ルールの正しい動作を保証するためのものです。

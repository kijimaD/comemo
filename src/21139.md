# [インデックス 21139] ファイルの概要

このコミットは、GoランタイムのPower64アーキテクチャ向けアセンブリファイルを、C言語との連携を前提とした古い形式から、Go言語のランタイムに直接統合される新しい形式へと変換するものです。具体的には、アセンブリコード内で使用されるヘッダーファイルの変更と、一部の関数名の変更、そしてGoランタイムの重要な要素である現在のゴルーチン構造体 (`g`) へのポインタを取得する `runtime·getg` 関数の追加が行われています。これは、Goランタイム全体のCからGoへの移行（"C to Go transition"）の一環として、Power64アーキテクチャ固有のアセンブリコードを現代のGoランタイムの設計に適合させるための重要なステップです。

## 変更の背景

Go言語の初期のランタイムは、C言語で書かれた部分が多く存在していました。しかし、Go言語の進化とともに、ランタイムの大部分をGo言語自身で記述する「C to Go transition」という大きなプロジェクトが進行していました。この移行の目的は、ランタイムの保守性、可読性、そしてGo言語のガベージコレクションやスケジューラとの統合性を高めることにありました。

アセンブリ言語で書かれた部分は、特定のアーキテクチャ（この場合はPower64）に依存する低レベルな操作（コンテキストスイッチ、アトミック操作、システムコールなど）を効率的に実行するために不可欠です。CからGoへの移行は、これらのアセンブリファイルにも影響を及ぼしました。C言語のヘッダーファイルに依存していたアセンブリコードを、Go言語のランタイムが直接利用できる形式に変換する必要がありました。

このコミットは、Power64アーキテクチャ向けのアセンブリファイル (`src/runtime/asm_power64x.s` と `src/runtime/sys_linux_power64x.s`) を、この「C to Go transition」に合わせて更新するものです。特に、`CL 168510043` のPower64版であると明記されており、これは他のアーキテクチャ（おそらくx86など）でも同様の変更が行われたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル操作、システムコールなどが含まれます。ランタイムの一部は、パフォーマンスやハードウェアとの直接的な対話のためにアセンブリ言語で書かれています。
*   **アセンブリ言語 (Assembly Language)**: 特定のCPUアーキテクチャの命令セットに直接対応する低レベルなプログラミング言語です。Goランタイムでは、C言語やGo言語では実現が難しい、あるいは非効率な操作（例: レジスタの直接操作、アトミック操作、コンテキストスイッチ）のためにアセンブリが使用されます。
*   **Power64アーキテクチャ**: IBMが開発したPOWERプロセッサの64ビット版アーキテクチャです。Goは様々なアーキテクチャをサポートしており、Power64もその一つです。
*   **`TEXT` ディレクティブ**: Goのアセンブリ言語（Plan 9アセンブラの派生）で関数を定義するために使用されます。例: `TEXT runtime·atomicstoreuintptr(SB), NOSPLIT, $0-16`。
    *   `runtime·atomicstoreuintptr`: 関数の名前。Goのアセンブリでは、パッケージ名と関数名を `·` (中点) で区切ります。
    *   `SB` (Static Base): グローバルシンボルや静的データへの参照の基準となる擬似レジスタ。
    *   `NOSPLIT`: この関数がスタックを分割しないことを示します。通常、Go関数はスタックが不足すると自動的に拡張されますが、低レベルなランタイム関数ではスタックの分割を禁止することがあります。
    *   `$0-16`: スタックフレームのサイズと引数のサイズを示します。`$0` はローカル変数のためのスタック領域が0バイトであることを意味し、`-16` は関数が16バイトの引数を受け取ることを意味します。
*   **`#include` ディレクティブ**: C言語のプリプロセッサディレクティブで、他のファイルのコンテンツを現在のファイルに挿入します。Goのアセンブリファイルでも、C言語のヘッダーファイルを取り込むために使われていました。
*   **`zasm_GOOS_GOARCH.h`**: Goの初期のランタイムで、アセンブリコードがC言語の定義（例えば、構造体のオフセットや定数）にアクセスするために使用されていたヘッダーファイルです。`GOOS` はオペレーティングシステム（例: linux）、`GOARCH` はアーキテクチャ（例: amd64, power64）を表します。
*   **`go_asm.h`**: Goランタイムのアセンブリコードで使用されるGo固有のマクロや定義を含むヘッダーファイルです。C言語の定義に依存しない、よりGoらしいアセンブリコードを書くために導入されました。
*   **`go_tls.h`**: Goランタイムのアセンブリコードで、スレッドローカルストレージ (TLS: Thread Local Storage) にアクセスするための定義を含むヘッダーファイルです。TLSは、各スレッドが独自のデータを持つことを可能にし、Goランタイムでは特に現在のゴルーチン (`g`) 構造体へのポインタを格納するために使用されます。
*   **`g` ポインタ**: Goランタイムにおいて、現在の実行中のゴルーチン (`goroutine`) を表す `g` 構造体へのポインタです。このポインタは、ゴルーチンのスタック、状態、スケジューリング情報など、ゴルーチンに関するあらゆる情報を含んでいます。アセンブリコードから `g` ポインタにアクセスすることは、ランタイムの低レベルな操作において非常に重要です。
*   **アトミック操作 (Atomic Operations)**: 複数のCPUコアやスレッドから同時にアクセスされても、データの整合性を保証する操作です。`casp` (Compare And Swap Pointer), `xchgp` (Exchange Pointer), `atomicstorep` (Atomic Store Pointer) などは、ポインタに対するアトミック操作です。
    *   `CAS` (Compare And Swap): あるメモリ位置の値が期待する値と一致する場合にのみ、その値を新しい値に更新する操作。
    *   `XCHG` (Exchange): あるメモリ位置の値とレジスタの値を交換する操作。
    *   `Atomic Store`: あるメモリ位置に値をアトミックに書き込む操作。
*   **`BR` 命令 (Branch)**: PowerPC/Power64アーキテクチャにおける分岐命令。このコミットでは、`BR runtime·cas64(SB)` のように、既存の汎用的な64ビットアトミック操作関数に分岐するために使用されています。これは、ポインタに対するアトミック操作が、実際には64ビット整数に対するアトミック操作として実装されていることを示唆しています。
*   **`MOVD` 命令 (Move Doubleword)**: PowerPC/Power64アーキテクチャにおける64ビットデータを移動する命令。
*   **`RETURN` ディレクティブ**: Goのアセンブリ関数で、関数からの戻りをマークします。

## 技術的詳細

このコミットの技術的な変更点は、主に以下の3つのカテゴリに分けられます。

1.  **ヘッダーファイルの変更**:
    *   `src/runtime/asm_power64x.s` と `src/runtime/sys_linux_power64x.s` の両方で、`#include "zasm_GOOS_GOARCH.h"` が削除され、代わりに `#include "go_asm.h"` と `#include "go_tls.h"` が追加されています。
    *   これは、GoランタイムがC言語の定義に依存するアセンブリコードから脱却し、Go言語のランタイムが提供するアセンブリ向けのマクロや定義を利用するように移行したことを明確に示しています。`go_asm.h` はGoアセンブリの共通定義を提供し、`go_tls.h` はスレッドローカルストレージ（特に`g`ポインタの取得）に関連する定義を提供します。

2.  **アトミック操作関数のリネーム**:
    *   `runtime·casp` が `runtime·casp1` に、`runtime·xchgp` が `runtime·xchgp1` に、`runtime·atomicstorep` が `runtime·atomicstorep1` にそれぞれリネームされています。
    *   これらの関数は、ポインタに対するアトミック操作を行うためのものです。関数名に `1` が追加された理由は、GoランタイムのCからGoへの移行の過程で、これらのアトミック操作の新しいGo言語側の実装が導入されたか、あるいは既存のC言語側の実装との名前の衝突を避けるためと考えられます。これにより、Go言語のコードから呼び出されるアトミック操作と、アセンブリで直接実装される低レベルなアトミック操作との間で、より明確な区別がなされるようになった可能性があります。既存の `BR` 命令による `runtime·cas64` や `runtime·xchg64` への分岐は維持されており、ポインタのアトミック操作が64ビット整数として扱われていることがわかります。

3.  **`runtime·getg` 関数の追加**:
    *   `src/runtime/asm_power64x.s` に、`TEXT runtime·getg(SB),NOSPLIT,$-8-8` という新しい関数が追加されています。
    *   この関数は、現在のゴルーチン構造体 (`g`) へのポインタをレジスタ `g` から取得し、呼び出し元のスタックフレームの戻り値領域 (`ret+0(FP)`) に格納します。
    *   `g` は、Goランタイムが各ゴルーチンのコンテキストを管理するために使用する特別なレジスタ（またはスレッドローカル変数）です。`runtime·getg` は、Go言語のコードから現在のゴルーチンにアクセスするための低レベルなメカニズムを提供します。これは、スケジューラ、ガベージコレクタ、スタック管理など、ランタイムの多くの部分で不可欠な機能です。この関数の追加は、GoランタイムがよりGo言語中心の設計へと移行する中で、アセンブリコードから直接 `g` ポインタにアクセスする必要性が高まったことを示しています。

これらの変更は、GoランタイムのPower64アセンブリコードが、C言語のランタイムとの密結合から解放され、よりGo言語のランタイムと直接的に連携するように再構築されたことを意味します。これにより、ランタイム全体の整合性が向上し、将来的なGo言語の機能拡張や最適化が容易になります。

## コアとなるコードの解説

上記の差分は、GoランタイムのPower64アセンブリファイルにおける重要な変更を示しています。

1.  **ヘッダーファイルの変更**:
    *   `src/runtime/asm_power64x.s` と `src/runtime/sys_linux_power64x.s` の両方で、`#include "zasm_GOOS_GOARCH.h"` が削除され、`#include "go_asm.h"` と `go_tls.h` が追加されています。
    *   これは、Goランタイムのアセンブリコードが、C言語のプリプロセッサによって生成される定義に依存するのではなく、Go言語のアセンブリツールチェーンが提供する専用のヘッダーファイルを利用するように変更されたことを意味します。`go_asm.h` はGoアセンブリの共通マクロや定数を提供し、`go_tls.h` はスレッドローカルストレージ（特に現在のゴルーチン`g`へのポインタ）へのアクセスを容易にするための定義を提供します。この変更は、GoランタイムのCからGoへの移行における重要な一歩です。

2.  **アトミック操作関数のリネーム**:
    *   `runtime·casp` が `runtime·casp1` に、`runtime·xchgp` が `runtime·xchgp1` に、`runtime·atomicstorep` が `runtime·atomicstorep1` にそれぞれ変更されています。
    *   これらの関数は、ポインタに対するアトミックな比較と交換 (CAS)、交換 (XCHG)、ストア (STORE) 操作を提供します。関数名の末尾に `1` が追加されたのは、Goランタイムの内部的なリファクタリングの一環である可能性が高いです。これは、Go言語のコードから呼び出されるアトミック操作のAPIと、アセンブリで直接実装される低レベルなプリミティブとの間で、より明確な命名規則を導入するためかもしれません。既存の `BR` 命令による `runtime·cas64` や `runtime·xchg64`、`runtime·atomicstore64` への分岐は維持されており、これらのポインタ操作が内部的には64ビット整数に対するアトミック操作として実装されていることが確認できます。

3.  **`runtime·getg` 関数の追加**:
    *   `src/runtime/asm_power64x.s` の末尾に、新しい関数 `TEXT runtime·getg(SB),NOSPLIT,$-8-8` が追加されています。
    *   この関数は非常にシンプルですが、Goランタイムにとって極めて重要です。
        *   `MOVD g, ret+0(FP)`: これは、Power64アーキテクチャにおいて、現在のゴルーチン構造体 (`g`) へのポインタが格納されている特別なレジスタ（またはスレッドローカル変数）`g` の値を、呼び出し元のスタックフレームの戻り値領域 (`ret+0(FP)`) に移動する命令です。
        *   `RETURN`: 関数から戻ります。
    *   `runtime·getg` は、Go言語のコードが現在のゴルーチン (`g`) の情報を取得するための低レベルなインターフェースを提供します。Goランタイムのスケジューラ、ガベージコレクタ、スタック管理、エラーハンドリングなど、多くの重要な機能は現在のゴルーチン (`g`) の状態に依存しています。この関数がアセンブリで直接実装されているのは、`g` ポインタへのアクセスが非常に頻繁に行われるため、最高のパフォーマンスと直接的なハードウェアアクセスが必要とされるためです。この追加は、GoランタイムがC言語の依存から脱却し、Go言語のセマンティクスに合わせた低レベルな操作を直接アセンブリで提供するようになったことを象徴しています。

これらの変更は、GoランタイムのPower64アセンブリコードが、より現代的でGo言語中心の設計に適合するように進化していることを示しており、ランタイムの堅牢性と将来の拡張性を高める上で不可欠なステップでした。

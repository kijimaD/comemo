# [インデックス 2696] ファイルの概要

このコミットは、Go言語の初期の`go/parser`パッケージにおける変更を記録しています。具体的には、スキャナー（字句解析器）のインターフェースの更新と、それに伴うエラーハンドリングロジックの整理が主な内容です。これにより、パーサーはファイル名をスキャナーの初期化時に渡すようになり、エラー報告の仕組みが`scanner`パッケージに集約されました。

## 元コミット内容

このコミットの元のメッセージは以下の通りです。

-   新しいスキャナーインターフェースへの調整（`Init`にファイル名を渡す）
-   もはや不要になったエラーハンドリングコードの削除

## 変更の背景

この変更は、Go言語のコンパイラツールチェーンの一部である`go/parser`パッケージと`go/scanner`パッケージ間のインターフェースの進化を反映しています。初期のGoコンパイラ開発では、各コンポーネントの責任範囲と連携方法が頻繁に調整されていました。

このコミットの背景には、以下の点が考えられます。

1.  **エラー報告の一元化**: 以前は`go/parser`が独自のエラー型（`Error`、`ErrorList`）とエラー収集ロジックを持っていましたが、`go/scanner`パッケージがより汎用的なエラー報告メカニズム（`scanner.ErrorVector`）を提供するようになったため、パーサー側の重複するエラーハンドリングコードが不要になりました。これにより、エラー報告のロジックがスキャナー側に集約され、コードの重複が排除され、保守性が向上します。
2.  **ファイル名によるエラー位置の改善**: コンパイルエラーや構文エラーを報告する際、エラーが発生したファイル名が非常に重要です。スキャナーがファイル名を初期化時に受け取ることで、エラーメッセージに正確なファイルパスを含めることが可能になり、ユーザーにとってより分かりやすいエラー報告が実現されます。これは、特に複数のファイルを扱う大規模なプロジェクトにおいて、エラーの特定とデバッグを容易にします。
3.  **インターフェースの洗練**: `go/scanner`パッケージのインターフェースが成熟し、ファイル名のようなコンテキスト情報を受け取るように設計されたことで、`go/parser`はよりシンプルにスキャナーを利用できるようになりました。これは、Go言語の標準ライブラリ設計における「シンプルさ」と「効率性」の追求の一環と言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とパッケージに関する知識が必要です。

1.  **`go/parser`パッケージ**: Go言語のソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を構築するためのパッケージです。Goコンパイラや各種ツール（`go fmt`, `go vet`など）の基盤となります。
2.  **`go/scanner`パッケージ**: `go/parser`が利用する字句解析器（レキサー、スキャナー）を提供するパッケージです。ソースコードを読み込み、トークン（キーワード、識別子、演算子など）のストリームに変換する役割を担います。
3.  **`token.Position`**: `go/token`パッケージで定義される構造体で、ソースコード内の位置（ファイル名、行番号、列番号、オフセット）を表します。エラー報告において、エラーの発生箇所を正確に指し示すために不可欠です。
4.  **`os.Error`**: Go言語の初期バージョンで使用されていたエラーインターフェースです。後のバージョンで`error`インターフェースに置き換えられました。このコミット時点では`os.Error`が使われています。
5.  **`vector.Vector`**: Go言語の初期バージョンで使われていた、動的配列のようなデータ構造です。後のバージョンではスライス（`[]T`）が標準となり、`vector`パッケージは非推奨となりました。このコミットではまだ`vector.Vector`がエラーリストの格納に使われています。
6.  **抽象構文木 (AST)**: プログラミング言語のソースコードの構造を木構造で表現したものです。パーサーはソースコードを解析してASTを生成し、コンパイラやリンターなどのツールがこのASTを利用してコードの意味解析や変換を行います。

## 技術的詳細

このコミットの技術的詳細は、主に`go/parser`パッケージ内のエラーハンドリングの責任範囲の変更と、`go/scanner`パッケージとの連携強化にあります。

### 1. エラーハンドリングの集約

コミット前は、`go/parser`パッケージ内に`Error`構造体と`ErrorList`型が定義されており、パーサー自身がエラーを収集し、整形して報告するロジックを持っていました。

-   `type Error struct { Pos token.Position; Msg string; }`: エラーの位置とメッセージを保持する構造体。
-   `type ErrorList []*Error`: 複数のエラーを保持し、ソートや文字列化の機能を持つ型。
-   `func (p *parser) Error(pos token.Position, msg string)`: `scanner.Error`インターフェースを実装し、スキャナーからのエラーを`parser`の内部エラーリストに収集するメソッド。このメソッドは、同じ行で複数のエラーが発生した場合に、最初の1つだけを収集することで、冗長なエラー報告を避けるロジックを含んでいました。

このコミットにより、これらの型定義と関連するメソッド（`String()`, `Len()`, `Swap()`, `Less()`, `errorList()`）が`go/parser/parser.go`から削除されました。代わりに、`parser`構造体は`scanner.ErrorVector`を埋め込むようになりました。

-   `parser struct { scanner.ErrorVector; ... }`

これにより、エラーの収集と管理は`scanner`パッケージの`ErrorVector`に一任されることになります。`scanner.ErrorVector`は、スキャナーが字句解析中に遭遇したエラーを効率的に収集・管理するための汎用的なメカニズムを提供します。

### 2. スキャナーインターフェースの変更とファイル名の伝達

`parser.init`メソッドのシグネチャが変更され、`filename string`引数が追加されました。

-   変更前: `func (p *parser) init(src interface{}, mode uint) os.Error`
-   変更後: `func (p *parser) init(filename string, src interface{}, mode uint) os.Error`

この`filename`は、`p.scanner.Init`メソッドに渡されるようになりました。

-   変更前: `p.scanner.Init(data, p, scannerMode(mode))`
-   変更後: `p.scanner.Init(filename, data, p, scannerMode(mode))`

これにより、スキャナーは字句解析を行う際に、どのファイルから読み込んでいるのかというコンテキスト情報を常に持つことになります。この情報は、`token.Position`構造体の一部としてエラーメッセージに含められるため、エラー報告の精度が向上します。

### 3. `Parse`関数のシグネチャ変更

`Parse`, `ParseStmts`, `ParseExpr`といったトップレベルの解析関数のシグネチャも、`filename string`引数を受け取るように変更されました。

-   変更前: `func Parse(src interface{}, mode uint) (*ast.Program, os.Error)`
-   変更後: `func Parse(filename string, src interface{}, mode uint) (*ast.Program, os.Error)`

これらの関数は、内部で`parser.init`を呼び出す際にこの`filename`を渡します。また、エラーを返す際も、削除された`p.errorList()`の代わりに`p.GetError(scanner.NoMultiples)`や`p.GetError(scanner.Sorted)`を呼び出すようになりました。これは、`scanner.ErrorVector`が提供するエラー取得メソッドを利用していることを示しています。`scanner.NoMultiples`や`scanner.Sorted`は、エラーの取得方法（重複を排除するか、ソートするかなど）を制御するフラグであると推測されます。

### 4. テストコードの変更

`parser_test.go`内のテストコードも、`Parse`関数が新しいシグネチャ（`filename`引数）を受け入れるように更新されています。

-   `Parse(src, 0)` が `Parse("", src, 0)` に変更されました。これは、テストケースではファイル名が不要なため、空文字列を渡していることを示しています。

## コアとなるコードの変更箇所

### `src/pkg/go/parser/parser.go`

-   `Error`構造体、`ErrorList`型、およびそれらの関連メソッド（`String`, `Len`, `Swap`, `Less`）が削除されました。
-   `parser`構造体から`errors vector.Vector`フィールドが削除され、代わりに`scanner.ErrorVector`が埋め込まれました。
-   `func (p *parser) Error(pos token.Position, msg string)` メソッドが削除されました。
-   `func (p *parser) init(...)` のシグネチャに `filename string` が追加され、`p.scanner.Init` に `filename` が渡されるようになりました。
-   `func (p *parser) init(...)` 内の `p.errors.Init(0)` が `p.ErrorVector.Init()` に変更されました。
-   `func (p *parser) parsePackage()` 内の `p.errors.Len() == 0` が `p.ErrorCount() == 0` に変更されました。
-   `func (p *parser) errorList() os.Error` メソッドが削除されました。
-   `Parse`, `ParseStmts`, `ParseExpr` 関数のシグネチャに `filename string` が追加され、エラー返却時に `p.errorList()` の代わりに `p.GetError(...)` が使用されるようになりました。

### `src/pkg/go/parser/parser_test.go`

-   `TestParseIllegalInputs`, `TestParseValidPrograms`, `TestParse3` 内の `Parse` 関数の呼び出しが、`Parse(src, 0)` から `Parse("", src, 0)` に変更されました。

## コアとなるコードの解説

このコミットの核心は、`go/parser`パッケージが独自のエラー収集・管理ロジックを持つのではなく、`go/scanner`パッケージが提供する汎用的なエラーハンドリングメカニズムに完全に依存するように変更された点です。

1.  **エラー型の統一**: `parser`パッケージ固有の`Error`構造体や`ErrorList`が削除されたことで、Go言語のツールチェーン全体でエラー報告の形式が統一され、`scanner`パッケージのエラー型が標準として使われるようになりました。これにより、エラー処理のコードが簡素化され、異なるコンポーネント間でのエラー情報のやり取りが容易になります。
2.  **`scanner.ErrorVector`の活用**: `parser`構造体に`scanner.ErrorVector`が埋め込まれたことで、パーサーはスキャナーから直接エラーを受け取り、それを`ErrorVector`に蓄積するようになりました。`ErrorVector`は、エラーの位置情報（ファイル名、行、列）を正確に保持し、必要に応じてソートしたり、重複を排除したりする機能を提供します。
3.  **ファイル名の重要性**: `parser.init`および`Parse`関数群に`filename`引数が追加されたことは、エラー報告の品質向上に直結します。スキャナーがファイル名を認識することで、エラーメッセージは「`main.go:10:5: unexpected token`」のように、どのファイルのどの位置でエラーが発生したかを明確に伝えることができるようになります。これは、開発者が問題を迅速に特定し、修正するために不可欠な情報です。
4.  **責任の分離**: この変更は、パーサーとスキャナーの間の責任の分離をより明確にしています。スキャナーは字句解析とそれに伴うエラーの報告に専念し、パーサーは構文解析とそれに伴うエラーの報告に専念します。エラーの収集と管理という共通のタスクは、`scanner`パッケージ内の共有メカニズムによって処理されるようになりました。

このコミットは、Go言語のコンパイラツールチェーンが初期段階でどのように設計され、洗練されていったかを示す良い例であり、モジュール間のインターフェース設計とエラーハンドリング戦略の進化を反映しています。

# [インデックス 23523] ファイルの概要

このコミットは、Goランタイムにおけるスタックトレース生成メカニズムの堅牢性を向上させるための変更です。具体的には、`runtime.callers` 関数がスタックトレースを辿る際に、現在実行中のゴルーチン（G）の情報を正しく `gentraceback` 関数に渡すように修正しています。これにより、将来のランタイム変更に対するコードの脆弱性が解消されます。

## コミット

```
runtime: make runtime.callers walk calling G, not g0

Currently runtime.callers invokes gentraceback with the pc and sp of
the G it is called from, but always passes g0 even if it was called
from a regular g. Right now this has no ill effects because
runtime.callers does not use either callback argument or the
_TraceJumpStack flag, but it makes the code fragile and will break
some upcoming changes.

Fix this by lifting the getg() call outside of the systemstack in
runtime.callers.

Change-Id: I4e1e92761c0e0cd4dcf28693be47df7bae9e122
Reviewed-on: https://go-review.googlesource.com/10292
Reviewed-by: Daniel Morsing <daniel.morsing@gmail.com>
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goランタイムの`runtime.callers`関数は、現在のゴルーチンのコールスタック（呼び出し履歴）を取得するために使用されます。この関数は内部的に`gentraceback`関数を呼び出して実際のスタックトレースの生成を行います。

コミット前の実装では、`runtime.callers`が`gentraceback`を呼び出す際に、`pc`（プログラムカウンタ）と`sp`（スタックポインタ）は呼び出し元のゴルーチン（G）のものを渡していましたが、`gp`（ゴルーチンポインタ）の引数には常に`g0`（スケジューラゴルーチン）を渡していました。

この時点では、`gentraceback`関数が`gp`引数や`_TraceJumpStack`フラグを積極的に利用していなかったため、この不整合は直接的な問題を引き起こしていませんでした。しかし、コミットメッセージにあるように、このコードの挙動は「fragile（壊れやすい）」であり、将来のランタイムの変更（特にスタックトレースの取得方法やゴルーチン管理に関する変更）によって問題が発生する可能性がありました。

この変更の目的は、`runtime.callers`が`gentraceback`に渡すゴルーチン情報の一貫性を保ち、将来的なランタイムの進化に対応できるように、コードの堅牢性を高めることにあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine, G)**: Goにおける軽量な実行スレッドです。Goプログラムの並行処理の基本単位であり、Goランタイムによって管理されます。各ゴルーチンは独自のスタックを持ちます。
2.  **M (Machine)**: オペレーティングシステムのスレッドを表します。GoランタイムはM上でGを実行します。
3.  **P (Processor)**: 論理プロセッサを表し、MとGの間のコンテキストとして機能します。Pは実行可能なGのキューを保持し、MにGをディスパッチします。
4.  **`g0` (スケジューラゴルーチン)**: 各Mには、特別なゴルーチンである`g0`が関連付けられています。`g0`はGoランタイムの内部処理（スケジューリング、ガベージコレクション、スタック管理など）を実行するためのスタックを提供します。通常のGoコードは`g0`のスタックでは実行されません。
5.  **`systemstack`**: Goランタイムの内部関数で、現在のゴルーチン（G）のスタックから`g0`のスタックに切り替えてコードを実行します。これは、スタックの拡張や縮小、ガベージコレクションなどの、現在のGのスタックを操作する可能性のある処理を行う際に使用されます。`systemstack`内で実行されるコードは、通常のGoコードとは異なる制約の下で動作します。
6.  **`runtime.callers`**: Goの標準ライブラリ関数で、現在のゴルーチンのコールスタック（呼び出し履歴）を`[]uintptr`スライスとして取得します。デバッグやプロファイリング、エラーレポートなどで利用されます。
7.  **`gentraceback`**: `runtime.callers`の内部で呼び出されるランタイム関数で、実際にスタックフレームを辿って`pc`（プログラムカウンタ）のリストを生成します。この関数は、スタックトレースを生成するために必要な`pc`、`sp`、`gp`（ゴルーチンポインタ）などの情報を受け取ります。

## 技術的詳細

このコミットの核心は、`runtime.callers`関数が`gentraceback`関数を呼び出す際に、正しいゴルーチンコンテキストを渡すように修正することです。

コミット前の`runtime.callers`のコードは以下のようになっていました（簡略化）。

```go
func callers(skip int, pcbuf []uintptr) int {
	sp := getcallersp(unsafe.Pointer(&skip))
	pc := uintptr(getcallerpc(unsafe.Pointer(&skip)))
	var n int
	systemstack(func() {
		// ここで常に getg() を呼び出しているが、systemstack 内では g0 が返される
		n = gentraceback(pc, sp, 0, getg(), skip, &pcbuf[0], len(pcbuf), nil, nil, 0)
	})
	return n
}
```

ここで問題となるのは、`gentraceback`の`gp`引数に渡される`getg()`の呼び出しが`systemstack`のクロージャ内で行われている点です。`systemstack`は、現在のゴルーチン（通常のG）の実行を一時停止し、`g0`のスタックに切り替えて指定された関数を実行します。したがって、`systemstack`内で`getg()`を呼び出すと、常に`g0`（スケジューラゴルーチン）へのポインタが返されます。

しかし、`runtime.callers`が取得しようとしているのは、`runtime.callers`を呼び出した**元のゴルーチン**のスタックトレースです。`pc`と`sp`は呼び出し元のGのものが正しく取得されていましたが、`gp`が`g0`になってしまうと、`gentraceback`が将来的に`gp`の情報を利用してスタックトレースの挙動を調整するようになった場合に、不整合が生じ、誤ったスタックトレースが生成される可能性がありました。

このコミットでは、この問題を解決するために、`getg()`の呼び出しを`systemstack`の外部に移動しています。

```go
func callers(skip int, pcbuf []uintptr) int {
	sp := getcallersp(unsafe.Pointer(&skip))
	pc := uintptr(getcallerpc(unsafe.Pointer(&skip)))
	gp := getg() // systemstack の外で呼び出すことで、呼び出し元の G を取得
	var n int
	systemstack(func() {
		// 取得した gp を gentraceback に渡す
		n = gentraceback(pc, sp, 0, gp, skip, &pcbuf[0], len(pcbuf), nil, nil, 0)
	})
	return n
}
```

これにより、`gentraceback`関数には、`pc`、`sp`、`gp`のすべてが`runtime.callers`を呼び出した元のゴルーチンの情報として一貫して渡されるようになります。これは、`gentraceback`がスタックトレースを生成する際に、ゴルーチンの状態やスタックの種類（通常のGのスタックか、システムスタックかなど）に基づいてより正確な判断を下せるようにするために重要です。

この変更は、特にGoランタイムがスタック管理やトレースの仕組みをより洗練させていく中で、将来的な互換性と堅牢性を確保するために不可欠な修正と言えます。

# [インデックス 25152] ファイルの概要

このコミットは、Go言語の `archive/tar` パッケージにおける `Reader.Read` メソッドの挙動を改善し、エラーの永続化（persistent）を保証するものです。これにより、一度エラーが発生した `tar` ストリームからの読み取りが、その後の呼び出しで誤って成功する可能性を排除し、より堅牢なエラーハンドリングを実現します。

## コミット

`archive/tar` パッケージの `Reader.Read` メソッドにおいて、以前に発生したエラーを永続化させる変更が導入されました。これにより、ストリームが不正な状態になった場合、それ以降の `Read` 呼び出しは常に同じエラーを返すようになります。

## 変更の背景

`archive/tar` パッケージは、TARアーカイブ形式の読み書きをGoプログラムで可能にする標準ライブラリです。`tar.Reader` は、TARアーカイブから個々のファイル（エントリ）を順次読み取るためのインターフェースを提供します。

このコミットが導入される以前の `tar.Reader.Read` メソッドには、ある問題が存在していました。それは、一度読み取り中にエラーが発生し、`tar.Reader` の内部状態が不正になった後でも、`Read` メソッドが再度呼び出された場合に、一時的に成功する可能性があったことです。

具体的には、`tar.Reader` は内部に `tr.err` というフィールドを持っており、読み取り中に発生したエラーを記録します。しかし、この `tr.err` が設定された後でも、`Read` メソッドの冒頭でこのエラーをチェックするロジックがなかったため、`tr.curr` (現在のエントリのリーダー) がまだ有効な状態であれば、`tr.curr.Read` が呼び出され、場合によってはデータの一部を読み取って `nil` エラーを返すことがありえました。

このような挙動は、ストリームが既に破損しているにもかかわらず、アプリケーションが読み取りを続行できると誤解する原因となり、データの整合性に関する問題や、予期せぬ動作を引き起こす可能性がありました。開発者は、一度エラーが発生したリーダーからは、それ以降もエラーが返されることを期待するのが自然です。このコミットは、この期待に沿うように `Read` メソッドの動作を修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と `archive/tar` パッケージの基本的な動作について知っておく必要があります。

1.  **`io.Reader` インターフェース**:
    Go言語における `io.Reader` インターフェースは、データを読み取るための基本的な抽象化です。`Read([]byte) (n int, err error)` メソッドを定義しており、`n` は読み取ったバイト数、`err` は読み取り中に発生したエラーを示します。`err` が `nil` でない場合、通常は読み取りが失敗したことを意味します。特に `io.EOF` は、ストリームの終端に達したことを示す特別なエラーです。

2.  **`archive/tar` パッケージ**:
    このパッケージは、TARアーカイブ形式のデータを扱うための機能を提供します。
    *   **`tar.Reader`**: TARアーカイブを読み取るための型です。`Next()` メソッドを呼び出すことで、アーカイブ内の次のファイル（エントリ）に進みます。各エントリは `*tar.Header` として返され、そのエントリのデータは `tar.Reader` 自体が `io.Reader` として振る舞うことで読み取ることができます。
    *   **`tar.Reader.Read(b []byte) (n int, err error)`**: 現在のTARエントリのデータを読み取るために使用されます。エントリの終わりに達すると `io.EOF` を返します。

3.  **エラーの永続化 (Sticky Error)**:
    Go言語の `io` パッケージや関連するリーダー/ライターの実装では、一度エラーが発生した場合、それ以降の操作も同じエラーを返し続けるというパターンがよく見られます。これは「sticky error」または「persistent error」と呼ばれます。このパターンを採用することで、呼び出し元は一度エラーを受け取ったら、そのリーダー/ライターが不正な状態にあることを確実に認識し、それ以上の操作を試みないようにすることができます。これにより、エラーハンドリングのロジックが簡素化され、バグの発生を防ぐことができます。例えば、`bufio.Reader` や `bytes.Buffer` など、多くの標準ライブラリのリーダー/ライターがこのパターンに従っています。

## 技術的詳細

`tar.Reader` の内部構造を考えると、この変更の必要性がより明確になります。
`tar.Reader` 構造体は、以下のようなフィールドを持つと想定されます（実際の定義はより複雑ですが、関連する部分を抜粋）。

```go
type Reader struct {
    // ...
    err  error // 以前の操作で発生したエラーを保持
    curr *entryReader // 現在のTARエントリのリーダー
    // ...
}
```

`Reader.Read` メソッドは、基本的に `tr.curr.Read` を呼び出すことで現在のエントリのデータを読み取ります。
変更前の `Read` メソッドのロジックは以下のようでした。

```go
func (tr *Reader) Read(b []byte) (n int, err error) {
    if tr.curr == nil {
        return 0, io.EOF
    }
    n, err = tr.curr.Read(b)
    if err != nil && err != io.EOF {
        tr.err = err // エラーが発生した場合、tr.errに記録
    }
    return n, err
}
```

このコードでは、`tr.err` が設定されていても、`tr.curr` が `nil` でなければ `tr.curr.Read` が実行されてしまいます。もし `tr.curr.Read` が一時的に成功（例えば、バッファに残っていたデータを返した）し、`nil` エラーを返した場合、呼び出し元はストリームが正常であると誤解する可能性があります。

このコミットによって導入された変更は、この問題を解決します。

```go
func (tr *Reader) Read(b []byte) (n int, err error) {
    if tr.err != nil { // ここで以前のエラーをチェック
        return 0, tr.err // エラーがあればすぐにそれを返す
    }
    if tr.curr == nil {
        return 0, io.EOF
    }
    n, err = tr.curr.Read(b)
    if err != nil && err != io.EOF {
        tr.err = err
    }
    return n, err
}
```

この変更により、`Read` メソッドが呼び出されるたびに、まず `tr.err` フィールドがチェックされます。もし `tr.err` が `nil` でない（つまり、以前の操作でエラーが発生している）場合、`Read` メソッドはすぐにそのエラーを返し、それ以上の読み取り操作は行いません。これにより、`tar.Reader` は一度エラー状態に陥ると、その状態を永続的に維持し、常にエラーを返す「sticky error」のセマンティクスに従うようになります。

この修正は、`tar.Reader` の堅牢性を高め、ユーザーがより予測可能な方法でエラーを処理できるようにするために重要です。

## コアとなるコードの解説

追加されたのは以下の4行です。

```go
	if tr.err != nil {
		return 0, tr.err
	}
```

このコードブロックは `tar.Reader` の `Read` メソッドの冒頭に追加されました。
その機能は以下の通りです。

1.  `if tr.err != nil`: `tr` (現在の `tar.Reader` インスタンス) の `err` フィールドが `nil` でないかどうかをチェックします。`tr.err` は、このリーダーインスタンスで以前に発生したエラーを保持するために使用されます。
2.  `return 0, tr.err`: もし `tr.err` が `nil` でなければ、それは以前に何らかの読み取りエラーが発生し、リーダーが不正な状態にあることを意味します。この場合、現在の `Read` 呼び出しはバイトを読み取らず（`n=0`）、以前に記録されたエラー `tr.err` をそのまま返します。

このシンプルな追加により、`tar.Reader` は「sticky error」の原則に従うようになります。つまり、一度エラーが発生すると、それ以降の `Read` 呼び出しはすべて同じエラーを返し、ストリームが不正な状態にあることを明確に示します。これにより、呼び出し元はエラー状態を確実に検出し、適切なエラーハンドリングを行うことができます。

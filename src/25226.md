# [インデックス 25226] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ (GC) におけるヒープ管理ロジックの改善に関するものです。具体的には、GCアシスト比率の計算に使用される「最小ヒープ距離」の保証方法を変更し、より堅牢で将来の拡張性に対応できるようにしています。以前はGCアシスト比率を計算する `revise` 関数内でヒープ距離に最小値を強制していましたが、このコミットではGCサイクル開始時にヒープ目標 (`heapGoal`) に対して最小値を保証するように変更されています。

## 変更の背景

Goのガベージコレクタ (GC) は、プログラムの実行と並行して動作し、メモリ管理のオーバーヘッドを最小限に抑えるように設計されています。この並行GCの効率を維持するためには、GCが完了する前にプログラムが過剰なメモリを割り当ててしまうことを防ぐメカニズムが必要です。その一つが「GCアシスト」です。

GCアシストは、アプリケーションのゴルーチンがメモリを割り当てようとした際に、GCの作業を肩代わりさせることで、GCの進行を助ける仕組みです。このアシストの量は `assistRatio` という値によって決定されます。`assistRatio` は、GCが完了するまでにアプリケーションが割り当て可能なメモリ量（ヒープ距離）と、GCが完了するために必要なスキャン作業量の比率に基づいて計算されます。

以前の実装では、`assistRatio` を計算する `revise()` 関数内で、`heapDistance` (GC開始時のヒープ目標とライブヒープサイズの差) が1MB未満の場合、強制的に1MBに設定していました。これは、`heapDistance` が非常に小さい、あるいは負の値になる場合に、`assistRatio` が不適切に大きくなったり、ゼロ除算が発生したりするのを防ぐためでした。

しかし、このアプローチにはいくつかの問題がありました。
1.  **`heapDistance` が負になる可能性**: GCの開始が遅れたり、`next_gc` (次のGCトリガーポイント) を超える大きなアロケーションが発生したり、`GOGC` の設定が非常に小さい場合など、`heapDistance` が負の値になることがありました。この場合、`heapDistance` を強制的に1MBに設定しても、根本的な問題解決にはなっていませんでした。
2.  **将来の拡張性への影響**: コミットメッセージにあるように、将来的には `assistRatio` の計算を「初期ヒープ距離」ではなく「現在のヒープ距離」に基づいて行うように変更する可能性がありました。しかし、`revise()` 関数内で現在のヒープ距離に最小値を強制すると、GCが常に1MBの距離を追いかけることになり、GCが完了しなくなる可能性がありました。

これらの問題を解決し、GCアシストの計算をより安定させ、将来の変更に対応できるようにするために、このコミットでは最小ヒープ距離の保証方法が変更されました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーキング」アルゴリズムと「並行GC」の概念に基づいています。
*   **三色マーキング**: オブジェクトを白（未訪問）、灰色（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類し、到達可能なオブジェクトをマークします。
*   **並行GC**: アプリケーションのゴルーチンと並行してGCが動作します。これにより、GCによるアプリケーションの一時停止 (Stop-The-World, STW) 時間を最小限に抑えます。

### メモリ統計 (`memstats`)

Goランタイムは、メモリ使用状況に関する様々な統計情報を `runtime.MemStats` 構造体で管理しています。このコミットに関連する主要な統計情報は以下の通りです。
*   `memstats.heap_live`: 現在ライブ（到達可能）なヒープメモリの総量。
*   `memstats.heap_reachable`: GCサイクル開始時に到達可能と判断されたヒープメモリの総量。
*   `next_gc`: 次のGCがトリガーされるヒープサイズ。これは `GOGC` 環境変数に基づいて計算されます。

### `GOGC` 環境変数

`GOGC` は、GoのGCの動作を制御する環境変数です。デフォルト値は100で、これは「ライブヒープサイズが前回のGC後のライブヒープサイズの2倍になったら次のGCをトリガーする」ことを意味します。例えば、前回のGC後に10MBのライブヒープがあった場合、`next_gc` は20MBとなり、ヒープが20MBに達すると次のGCが開始されます。

### `heapGoal` と `heapDistance`

*   **`heapGoal`**: 現在のGCサイクルが完了した後に目標とするヒープサイズ。これは `memstats.heap_reachable` と `GOGC` の値に基づいて計算されます。具体的には、`heapGoal = memstats.heap_reachable + memstats.heap_reachable * GOGC / 100` となります。
*   **`heapDistance`**: GCサイクル開始時の `heapGoal` と `initialHeapLive` (GC開始時のライブヒープサイズ) の差。これは、GCが完了するまでにアプリケーションが追加で割り当て可能なメモリ量の目安となります。

### GCアシスト (`assistRatio`)

GCアシストは、アプリケーションのゴルーチンがメモリを割り当てる際に、GCのマークフェーズの作業を一部肩代わりさせる仕組みです。これにより、GCの進行を加速し、GCが完了する前にヒープが過剰に成長するのを防ぎます。
*   **`assistRatio`**: GCアシストの量を決定する比率。この値が大きいほど、アプリケーションはより多くのGC作業を肩代わりします。`assistRatio = scanWorkExpected / heapDistance` のように計算されます。`scanWorkExpected` はGCが完了するために必要なスキャン作業の推定値です。

### `startCycle()` と `revise()` 関数

*   **`startCycle()`**: GCサイクルが開始される際に呼び出される関数。この関数内で、`heapGoal` の計算など、GCサイクルの初期設定が行われます。
*   **`revise()`**: GCサイクル中に、GCアシスト比率 (`assistRatio`) を再計算するために呼び出される関数。メモリ割り当てや解放が行われるたびに、GCの進行状況に応じて `assistRatio` を調整します。

## 技術的詳細

このコミットの核心は、GCアシスト比率の計算における「最小ヒープ距離」の保証ロジックを移動し、その適用対象を変更した点にあります。

### 変更前の問題点とアプローチ

変更前は、`src/runtime/mgc.go` の `revise()` 関数内で `heapDistance` が計算され、その値が `1024 * 1024` (1MB) 以下の場合、強制的に `1024 * 1024` に設定されていました。

```go
// src/runtime/mgc.go (変更前)
func (c *gcControllerState) revise() {
    // ...
    heapDistance := int64(c.heapGoal) - int64(work.initialHeapLive)
    if heapDistance <= 1024*1024 {
        // heapDistance can be negative if GC start is delayed
        // or if the allocation that pushed heap_live over
        // next_gc is large or if the trigger is really close
        // to GOGC. We don't want to set the assist negative
        // (or divide by zero, or set it really high), so
        // enforce a minimum on the distance.
        heapDistance = 1024 * 1024
    }
    c.assistRatio = float64(scanWorkExpected) / float64(heapDistance)
}
```

このアプローチの問題点は、`heapDistance` が負の値になる可能性があったことです。`heapGoal` が `initialHeapLive` よりも小さい場合、`heapDistance` は負になります。このような状況は、GCの開始が遅れたり、`next_gc` を超える大きなアロケーションが発生したり、`GOGC` の設定が非常に小さい場合に起こり得ます。負の `heapDistance` を1MBに強制しても、それはあくまで計算上の調整であり、実際のメモリ状況とは乖離がありました。また、コミットメッセージが指摘するように、将来的に「現在のヒープ距離」に基づいてアシスト比率を計算するようになった場合、`revise()` で常に1MBの最小値を強制すると、GCが目標を達成できなくなる可能性がありました。

### 変更後のアプローチ

このコミットでは、最小ヒープ距離の保証を `startCycle()` 関数に移動し、`heapGoal` に対して適用するように変更しました。

```go
// src/runtime/mgc.go (変更後)
func (c *gcControllerState) startCycle() {
    // ...
    // Compute the heap goal for this cycle
    c.heapGoal = memstats.heap_reachable + memstats.heap_reachable*uint64(gcpercent)/100

    // Ensure that the heap goal is at least a little larger than
    // the current live heap size. This may not be the case if GC
    // start is delayed or if the allocation that pushed heap_live
    // over next_gc is large or if the trigger is really close to
    // GOGC. Assist is proportional to this distance, so enforce a
    // minimum distance, even if it means going over the GOGC goal
    // by a tiny bit.
    if c.heapGoal < memstats.heap_live+1024*1024 {
        c.heapGoal = memstats.heap_live + 1024*1024
    }
    // ...
}
```

この変更により、GCサイクルが開始される時点で、`heapGoal` が `memstats.heap_live` (現在のライブヒープサイズ) よりも少なくとも1MB大きくなるように保証されます。これにより、`heapDistance` が計算される際には、常に正の値が保証されることになります。

**この変更の利点:**
*   **より堅牢な `heapGoal`**: GCサイクル開始時に `heapGoal` が現実的な最小値を持つことが保証されるため、`heapDistance` が負になる可能性がなくなります。
*   **GCアシストの安定性**: `heapDistance` が常に正の値となるため、`assistRatio` の計算がより安定し、ゼロ除算や不適切な値になるリスクが低減されます。
*   **将来の拡張性**: `revise()` 関数から最小ヒープ距離の強制ロジックが削除されたため、将来的により動的な「現在のヒープ距離」に基づくアシスト比率の計算に移行しやすくなります。`revise()` は純粋に現在の状況に基づいてアシスト比率を調整する役割に集中できます。
*   **エラーハンドリングの改善**: `revise()` 関数では、`heapDistance` が0以下になった場合に `throw` (パニック) するようになりました。これは、`heapGoal` が `startCycle()` で適切に設定されていれば発生しないはずの異常事態であり、早期に問題を検出するための堅牢なエラーチェックとなります。

### `gcBlackenEnabled` の追加

`src/runtime/mheap.go` の `mHeap_Alloc_m` (メモリ割り当て) と `mHeap_Free` (メモリ解放) 関数において、`gcController.revise()` の呼び出しに `if gcBlackenEnabled != 0` という条件が追加されました。

```go
// src/runtime/mheap.go (変更後)
func mHeap_Alloc_m(h *mheap, npage uintptr, sizeclass int32, large bool) *mspan {
    // ...
    if gcBlackenEnabled != 0 {
        gcController.revise()
    }
    // ...
}

func mHeap_Free(h *mheap, s *mspan, acct int32) {
    // ...
    if gcBlackenEnabled != 0 {
        gcController.revise()
    }
    // ...
}
```

`gcBlackenEnabled` は、GCのマークフェーズがアクティブであり、GCアシストが有効になっていることを示すフラグです。`revise()` 関数はGCアシスト比率を調整するためのものであり、GCがアクティブでない期間に呼び出す必要はありません。この条件を追加することで、不要な `revise()` の呼び出しを避け、GCのオーバーヘッドを削減し、コードの意図を明確にしています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

1.  **`startCycle()` 関数内の `heapGoal` の調整**:
    *   `c.heapGoal = memstats.heap_reachable + memstats.heap_reachable*uint64(gcpercent)/100` で計算された `heapGoal` に対して、以下の条件が追加されました。
    *   `if c.heapGoal < memstats.heap_live+1024*1024`: もし計算された `heapGoal` が、現在のライブヒープサイズ (`memstats.heap_live`) に1MBを加えた値よりも小さい場合、`heapGoal` を `memstats.heap_live + 1024*1024` に強制的に設定します。
    *   この変更により、GCサイクル開始時に `heapGoal` が常に現在のライブヒープサイズより少なくとも1MB大きくなることが保証されます。これにより、`heapDistance` が負になる状況を防ぎ、GCアシストの計算がより安定します。

2.  **`revise()` 関数内の `heapDistance` のチェック変更**:
    *   以前存在した `if heapDistance <= 1024*1024 { heapDistance = 1024 * 1024 }` というロジックが削除されました。
    *   代わりに `if heapDistance <= 0 { throw("negative heap distance") }` というチェックが追加されました。
    *   `startCycle()` で `heapGoal` が適切に設定されていれば `heapDistance` は常に正の値になるはずなので、もし0以下になった場合は異常事態とみなし、`throw` (パニック) させることで早期に問題を検出します。これにより、GCアシスト比率の計算が不正な値になることを防ぎます。

### `src/runtime/mheap.go` の変更

1.  **`mHeap_Alloc_m` および `mHeap_Free` 関数における `gcController.revise()` の条件付き呼び出し**:
    *   メモリ割り当て (`mHeap_Alloc_m`) およびメモリ解放 (`mHeap_Free`) の際に `gcController.revise()` が呼び出されていましたが、この呼び出しに `if gcBlackenEnabled != 0` という条件が追加されました。
    *   `gcBlackenEnabled` は、GCのマークフェーズがアクティブであり、GCアシストが有効になっている場合に非ゼロとなるフラグです。
    *   この条件により、GCがアクティブでない期間（例えば、GCが完了しているか、まだ開始されていない期間）には `revise()` が呼び出されなくなり、不要な処理が削減されます。これは、GCのオーバーヘッドを減らし、コードの効率性を向上させます。

これらの変更は、GoのGCがより予測可能で堅牢に動作するようにするための重要な改善であり、特に高負荷な環境下でのメモリ管理の安定性に寄与します。

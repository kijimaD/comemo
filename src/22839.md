## 変更の背景

Go言語は通常、静的リンクを好み、単一の自己完結型バイナリを生成します。しかし、`cgo`を使用する場合や、特定の標準ライブラリパッケージ（例: `net`パッケージがDNS解決のためにCライブラリに依存する場合など）を使用する場合には、動的リンクが必要となることがあります。

`runtime.duffcopy`と`runtime.duffzero`は、Goランタイム内で使用される、メモリのコピーやゼロクリアを高速に行うための最適化されたアセンブリルーチンです。これらのルーチンは、Duff's Deviceの概念を応用しており、ループアンローリングによってオーバーヘッドを削減し、効率的なメモリ操作を実現します。Goコンパイラは、これらのルーチンを呼び出す際に、操作するメモリサイズに応じてルーチン内の特定の位置（オフセット）に直接ジャンプするコードを生成していました。これにより、実行時の動的な計算や条件分岐を排除し、パフォーマンスを向上させていました。

しかし、動的リンクされた環境では、シンボル（関数やデータ）のアドレスはロード時に解決されます。動的リンカは通常、シンボルの開始アドレスへのジャンプはサポートしますが、「シンボルから特定のオフセットだけずれた位置への直接ジャンプ」は、そのシンボルが共有ライブラリ内に存在する場合に問題を引き起こす可能性があります。動的リンカは、シンボルがロードされるベースアドレスを調整しますが、そのオフセットを考慮してジャンプ先を自動的に調整するわけではありません。そのため、動的リンクされたGoバイナリが`duffcopy`や`duffzero`をオフセット付きで直接呼び出そうとすると、不正なメモリアドレスにジャンプし、クラッシュや予期せぬ動作を引き起こす可能性がありました。

このコミットは、この動的リンカの制約に対処するために、`duffcopy`および`duffzero`への呼び出しを、GOT（Global Offset Table）を介して間接的に行うように変更することで、この問題を解決しています。

## 前提知識の解説

### 1. Duff's DeviceとGoの`duffcopy`/`duffzero`

Duff's Deviceは、1983年にTom Duffによって考案された、ループアンローリングを効率的に実装するためのプログラミング技法です。C言語では`switch`文と`do-while`ループのフォールスルーを組み合わせて実装されることが有名です。

Goランタイムにおける`runtime.duffcopy`と`runtime.duffzero`は、このDuff's Deviceの概念を応用した、メモリコピーとメモリゼロクリアのための高度に最適化されたアセンブリ関数です。これらは、`mkduff.go`ツールによって自動生成され、特定のバイト数（例: 16バイトや64バイト）を一度に処理するために`MOVUPS`のような命令を利用し、ループのオーバーヘッドを最小限に抑えます。

Goコンパイラは、これらのルーチンを呼び出す際、コピーまたはゼロクリアするバイト数に基づいて、`duffcopy`または`duffzero`ルーチン内の適切な開始オフセットに直接ジャンプするコードを生成します。これにより、実行時にループカウンタをチェックするなどのオーバーヘッドなしに、高速なメモリ操作を実現します。

### 2. 動的リンク (Dynamic Linking)

動的リンクは、プログラムが実行時に外部の共有ライブラリ（例: `.so`ファイルや`.dll`ファイル）とリンクするプロセスです。静的リンクとは異なり、共有ライブラリのコードは実行可能ファイルに直接埋め込まれません。これにより、以下のような利点があります。

*   **バイナリサイズの削減**: 複数のプログラムが同じ共有ライブラリを使用する場合、ライブラリのコードはメモリ上に一度だけロードされ、共有されます。
*   **メモリ使用量の効率化**: 同様に、共有ライブラリのコードは複数のプロセス間で共有されるため、システム全体のメモリ使用量を削減できます。
*   **メンテナンスの容易さ**: 共有ライブラリが更新されても、それを使用するプログラムを再コンパイルする必要がありません。

しかし、動的リンクには、実行時のシンボル解決という複雑さが伴います。

### 3. GOT (Global Offset Table) と PLT (Procedure Linkage Table)

GOTとPLTは、ELF（Executable and Linkable Format）バイナリ（Unix系システムで一般的）における動的リンクの主要なメカニズムです。

*   **PLT (Procedure Linkage Table)**:
    PLTは、共有ライブラリ内の関数を呼び出すための「トランポリンスタブ」の集合体として機能します。プログラムが動的リンクされた関数を初めて呼び出すとき、実行はPLT内の対応するエントリにリダイレクトされます。

*   **GOT (Global Offset Table)**:
    GOTは、共有ライブラリ内の関数や変数の実際のメモリアドレスを格納するテーブルです。

**PLTとGOTによる動的リンクのワークフロー:**

1.  **初回呼び出し**: プログラムが動的リンクされた関数を初めて呼び出すと、実行はPLT内のその関数のエントリにジャンプします。
2.  **アドレス解決**: PLTエントリは、関連するGOTエントリをチェックします。もし関数のアドレスがまだ解決されていない場合（つまり、初回呼び出しの場合）、PLTは動的リンカ（Linuxでは`ld.so`など）をトリガーして、共有ライブラリ内の関数の実際のアドレスを特定させます。
3.  **GOTの更新**: 動的リンカがアドレスを見つけると、その実際のアドレスを関連するGOTエントリに書き込みます。
4.  **以降の呼び出し**: 同じ関数への以降のすべての呼び出しでは、プログラムはGOTに格納された解決済みのアドレスに直接ジャンプし、動的リンカを介さずに効率的な呼び出しが可能になります。

このメカニズムにより、動的リンクされた関数への呼び出しは、初回のみオーバーヘッドが発生し、以降は直接呼び出しに近い速度で実行されます。

## 技術的詳細

このコミットの核心は、動的リンクされたGoバイナリが`duffcopy`や`duffzero`を呼び出す際に発生する問題の解決です。

従来のGoコンパイラは、`duffcopy`や`duffzero`への呼び出しを、以下のような形式で生成していました（概念的な表現）：

```assembly
CALL runtime.duffcopy + offset
```

ここで`offset`は、コピーまたはゼロクリアするバイト数に応じて、`duffcopy`ルーチン内の特定のエントリポイントを指します。静的リンクされたバイナリでは、`runtime.duffcopy`のアドレスはコンパイル時に固定されており、`offset`を加算しても問題ありませんでした。

しかし、動的リンクの場合、`runtime.duffcopy`は共有ライブラリの一部としてロードされ、そのベースアドレスは実行時に決定されます。動的リンカは、`runtime.duffcopy`というシンボル自体のアドレスを解決しますが、`runtime.duffcopy + offset`という「シンボルからのオフセット付きアドレス」を直接解決するメカニズムは持っていません。そのため、このような直接ジャンプは不正なアドレスへのアクセスとなり、プログラムのクラッシュを引き起こす可能性がありました。

このコミットは、この問題を解決するために、`duffcopy`および`duffzero`への呼び出しを、GOTを介した間接的な呼び出しに変換します。具体的には、以下の手順を踏みます。

1.  **GOTからのアドレス取得**: `runtime.duffcopy`または`runtime.duffzero`のシンボルに対応するアドレスをGOTから取得します。これは、`AMOVQ`命令と`obj.NAME_GOTREF`タイプを使用して行われます。GOTエントリは、共有ライブラリ内の関数の実際の開始アドレスを指します。
2.  **オフセットの加算**: GOTから取得したベースアドレスに、元の`offset`を加算します。これにより、`duffcopy`または`duffzero`ルーチン内の正しいエントリポイントのアドレスが計算されます。
3.  **間接呼び出し**: 計算されたアドレスをレジスタ（例: `REG_R15`）に格納し、そのレジスタを介して間接的に`CALL`命令を実行します。

この変更により、動的リンカは`runtime.duffcopy`や`runtime.duffzero`というシンボル自体をGOTに解決するだけでよくなり、GoコンパイラはGOTから取得したベースアドレスにオフセットを「手動で」加算することで、動的リンカの制約を回避しつつ、`duffcopy`/`duffzero`の最適化された呼び出しパターンを維持できるようになります。

また、`src/cmd/internal/obj/x86/asm6.go`では、動的リンク時に`Zcallduff`（`duffcopy`/`duffzero`への直接呼び出し）が検出された場合に診断メッセージを出力するコードが追加されており、これは将来的な問題のデバッグや防止に役立ちます。

### `src/cmd/internal/obj/x86/asm6.go`の変更

このファイルは、Goコンパイラのアセンブラ部分で、アセンブリ命令の処理を担当します。追加されたコードは、動的リンクが有効な場合に`duffcopy`または`duffzero`への直接呼び出し（`Zcallduff`）を検出すると、診断メッセージを出力します。

```go
+				if yt.zcase == Zcallduff && ctxt.Flag_dynlink {
+					ctxt.Diag("directly calling duff when dynamically linking Go")
+				}
```
*   `yt.zcase == Zcallduff`: 現在処理している命令が`duffcopy`または`duffzero`への呼び出しであるかをチェックします。
*   `ctxt.Flag_dynlink`: コンテキスト（`ctxt`）の`Flag_dynlink`が`true`であるか、つまり動的リンクが有効であるかをチェックします。
*   `ctxt.Diag(...)`: 上記の条件が両方とも真である場合、コンパイラは「Goを動的リンクしているときにduffを直接呼び出しています」という診断メッセージを出力します。これは、開発者に対して、このコミットで修正された問題のあるパターンがまだ存在することを示唆する警告です。

1.  **シンボルの特定**:
    *   `if p.As == obj.ADUFFZERO { sym = obj.Linklookup(ctxt, "runtime.duffzero", 0) } else { sym = obj.Linklookup(ctxt, "runtime.duffcopy", 0) }`: 現在の命令が`ADUFFZERO`であれば`runtime.duffzero`シンボルを、そうでなければ`runtime.duffcopy`シンボルをルックアップします。

2.  **オフセットの保存**:
    *   `offset := p.To.Offset`: 元の`duffcopy`/`duffzero`呼び出し命令のターゲットオペランドに格納されていたオフセット値を`offset`変数に保存します。

    *   `p.As = AMOVQ`: 命令タイプを`AMOVQ`（64ビット移動命令）に変更します。
    *   `p.From.Type = obj.TYPE_MEM`: ソースオペランドのタイプをメモリ参照に設定します。
    *   `p.From.Name = obj.NAME_GOTREF`: ソースオペランドの名前を`GOTREF`（GOT参照）に設定します。これは、シンボルのアドレスをGOTから取得することを示します。
    *   `p.From.Sym = sym`: ソースオペランドのシンボルを、先ほどルックアップした`runtime.duffzero`または`runtime.duffcopy`に設定します。
    *   `p.To.Type = obj.TYPE_REG`: ターゲットオペランドのタイプをレジスタに設定します。
    *   `p.To.Reg = REG_R15`: ターゲットレジスタを`R15`に設定します。これにより、`runtime.duffcopy`または`runtime.duffzero`のベースアドレスが`R15`にロードされます。

4.  **オフセットの加算 (AADDQ命令の生成)**:
    *   `p1 := obj.Appendp(ctxt, p)`: 新しい命令`p1`を現在の命令`p`の直後に追加します。
    *   `p1.As = AADDQ`: 命令タイプを`AADDQ`（64ビット加算命令）に変更します。
    *   `p1.From.Type = obj.TYPE_CONST`: ソースオペランドのタイプを定数に設定します。
    *   `p1.From.Offset = offset`: ソースオペランドの定数値を、保存しておいた`offset`に設定します。
    *   `p1.To.Type = obj.TYPE_REG`: ターゲットオペランドのタイプをレジスタに設定します。
    *   `p1.To.Reg = REG_R15`: ターゲットレジスタを`R15`に設定します。これにより、`R15`に格納されたベースアドレスに`offset`が加算され、`duffcopy`/`duffzero`内の正しいエントリポイントのアドレスが`R15`に格納されます。

5.  **間接呼び出し (ACALL命令の生成)**:
    *   `p2 := obj.Appendp(ctxt, p1)`: 新しい命令`p2`を`p1`の直後に追加します。
    *   `p2.As = obj.ACALL`: 命令タイプを`ACALL`（呼び出し命令）に変更します。
    *   `p2.To.Type = obj.TYPE_REG`: ターゲットオペランドのタイプをレジスタに設定します。
    *   `p2.To.Reg = REG_R15`: ターゲットレジスタを`R15`に設定します。これにより、`R15`に格納されたアドレス（`duffcopy`/`duffzero`の正しいエントリポイント）への間接呼び出しが実行されます。

この一連の処理により、元の`CALL runtime.duffcopy + offset`という単一の命令が、動的リンクに対応した3つの命令（GOTからのアドレスロード、オフセット加算、間接呼び出し）に変換され、動的リンカの制約を回避しつつ、`duffcopy`/`duffzero`の最適化された呼び出しロジックを維持しています。

## 変更の背景

Go言語は、その強力な後方互換性保証で知られています。これは、Go 1のリリース以降、既存のGoプログラムが新しいバージョンのGoコンパイラでコンパイルされ、実行できることを意味します。この互換性保証を維持するため、GoチームはAPIの追加や変更に対して厳格なプロセスを設けています。

`api/next.txt` ファイルは、このプロセスの一部として機能します。新しいAPIがGoの標準ライブラリに追加される際、まずこのファイルにそのAPIのシグネチャが記述されます。これは、そのAPIが次のGoのリリースで公開される予定であることを示します。このファイルへの追加は、APIが安定しており、互換性保証の対象となることを意味します。

このコミットは、Go 1.7リリースに向けて、様々なパッケージで提案された新しいAPI要素を `api/next.txt` に追加するものです。これにより、これらのAPIが正式にGo 1.7の一部として公開される準備が整えられます。

## 前提知識の解説

### GoのAPI安定性保証

Go 1のリリース以来、Goチームは「Go 1互換性保証」を維持しています。これは、Go 1で動作するプログラムは、Go 1.xの将来のバージョンでも動作し続けることを保証するものです。この保証は、開発者が安心してGo言語を使用し、ライブラリやアプリケーションを構築できるようにするために非常に重要です。APIの追加は慎重に行われ、一度公開されたAPIは原則として変更または削除されません。

### `api/next.txt` の役割

`api/next.txt` は、Goの標準ライブラリに追加される予定の新しいAPIのリストを保持するファイルです。開発者が新しいAPIを提案し、それが承認されると、まずこのファイルにそのAPIのシグネチャが追加されます。これは、そのAPIが次のGoのリリースで公開される予定であることを示し、GoのAPIチェッカーによって互換性が維持されているかどうかのチェック対象となります。このファイルに記載されたAPIは、次のリリースで正式に公開され、Go 1互換性保証の対象となります。

### 各パッケージの概要

このコミットでAPIが追加されるパッケージは以下の通りです。

*   **`crypto/tls`**: TLS (Transport Layer Security) プロトコルを実装し、安全なネットワーク通信を提供します。
*   **`go/build`**: Goパッケージのビルドプロセスに関する情報を提供し、パッケージの依存関係やソースファイルの検索などを可能にします。
*   **`go/doc`**: Goのソースコードからドキュメントを生成するための機能を提供します。
*   **`net/http/httptest`**: HTTPハンドラのテストを容易にするためのユーティリティを提供します。
*   **`net/url`**: URLの解析と構築のための機能を提供します。
*   **`os/user`**: 現在のユーザーやグループに関する情報（ユーザー名、UID、GIDなど）を取得するための機能を提供します。
*   **`runtime`**: Goランタイムの内部状態に関する情報や、低レベルの操作（スタックトレースの取得など）を提供します。
*   **`testing`**: Goのテストフレームワークを提供し、ユニットテストやベンチマークテストの記述をサポートします。

## 技術的詳細

このコミットで `api/next.txt` に追加された各APIについて、その目的と技術的な詳細を解説します。

### `pkg crypto/tls, type Config struct, DynamicRecordSizingDisabled bool`

*   **目的**: TLS接続におけるレコードサイズの動的な調整を無効にするための設定オプションです。
*   **詳細**: TLSプロトコルでは、セキュリティとパフォーマンスのバランスを取るために、送信するデータのレコードサイズを動的に調整することがあります。しかし、特定の環境やアプリケーションでは、この動的な調整が望ましくない場合があります（例えば、サイドチャネル攻撃のリスクを軽減するためや、固定サイズのレコードを期待するシステムとの互換性のため）。`DynamicRecordSizingDisabled` フィールドを `true` に設定することで、この動的なレコードサイズ調整を無効にし、固定サイズのレコードを使用するようになります。

### `pkg go/build, type Package struct, CgoFFLAGS []string`
### `pkg go/build, type Package struct, FFiles []string`

*   **目的**: `go/build` パッケージの `Package` 構造体に、Cgo関連のフラグと、特定のファイルリストを追加します。
*   **詳細**:
    *   `CgoFFLAGS []string`: Cgo (C言語との相互運用) を使用する際に、Cコンパイラに渡す追加のフラグ（例: `-D`, `-I`）を格納するためのフィールドです。これにより、ビルドプロセスでCgoのコンパイルオプションをより細かく制御できるようになります。
    *   `FFiles []string`: Goのビルドシステムが認識する特定の種類のファイル（例: `_test.go` 以外のテストファイルや、特定のビルドタグを持つファイルなど）を格納するためのフィールドと考えられます。これにより、ビルドプロセスがどのファイルを処理すべきかをより正確に把握できるようになります。

### `pkg go/doc, type Example struct, Unordered bool`

*   **目的**: `go/doc` パッケージの `Example` 構造体に、テストの出力順序が重要でないことを示すフラグを追加します。
*   **詳細**: Goのドキュメンテーションツールは、`Example` 関数から生成される出力例をテストします。通常、出力の順序は厳密に一致する必要がありますが、一部の例では出力の順序が不定である場合があります（例: マップのイテレーション順序など）。`Unordered` フィールドを `true` に設定することで、ドキュメンテーションツールは出力の順序を無視して比較を行うようになり、より柔軟なテストが可能になります。

### `pkg net/http/httptest, method (*ResponseRecorder) Trailers() http.Header`

*   **目的**: `net/http/httptest` パッケージの `ResponseRecorder` に、HTTPトレーラーヘッダーを取得するメソッドを追加します。
*   **詳細**: HTTP/1.1では、チャンク転送エンコーディングを使用する場合に、メッセージボディの後にトレーラーヘッダーを送信できます。これは、ボディの生成が完了するまで利用できないメタデータ（例: チェックサム）を送信するのに役立ちます。`ResponseRecorder` はHTTPレスポンスを記録するためのテストユーティリティであり、この `Trailers()` メソッドにより、テスト中にトレーラーヘッダーの内容を検証できるようになります。

### `pkg net/url, type URL struct, ForceQuery bool`

*   **目的**: `net/url` パッケージの `URL` 構造体に、クエリ文字列が空であってもURLに疑問符 (`?`) を強制的に含めるかどうかを制御するフィールドを追加します。
*   **詳細**: 通常、`url.URL` を文字列に変換する際、クエリ文字列が空であれば疑問符は含まれません。しかし、一部のシステムやAPIでは、クエリ文字列が空であっても疑問符が存在することを期待する場合があります（例: `http://example.com/?`）。`ForceQuery` を `true` に設定することで、`URL.String()` メソッドが常に疑問符を含むURLを生成するようになります。

### `pkg os/user, func LookupGroup(string) (*Group, error)`
### `pkg os/user, func LookupGroupId(string) (*Group, error)`
### `pkg os/user, method (*User) GroupIds() ([]string, error)`
### `pkg os/user, method (UnknownGroupError) Error() string`
### `pkg os/user, method (UnknownGroupIdError) Error() string`
### `pkg os/user, type Group struct`
### `pkg os/user, type Group struct, Gid string`
### `pkg os/user, type Group struct, Name string`
### `pkg os/user, type UnknownGroupError string`
### `pkg os/user, type UnknownGroupIdError string`

*   **目的**: `os/user` パッケージに、グループ情報のルックアップ機能と、関連するエラー型および `Group` 構造体を追加します。
*   **詳細**:
    *   `LookupGroup(name string) (*Group, error)`: 指定されたグループ名に基づいてグループ情報を検索します。
    *   `LookupGroupId(gid string) (*Group, error)`: 指定されたグループID (GID) に基づいてグループ情報を検索します。
    *   `(*User) GroupIds() ([]string, error)`: 特定のユーザーが所属するすべてのグループのIDリストを取得します。
    *   `Group` 構造体: グループの情報を保持するための新しい構造体で、`Gid` (グループID) と `Name` (グループ名) フィールドを持ちます。
    *   `UnknownGroupError` と `UnknownGroupIdError`: グループが見つからなかった場合に返される新しいエラー型です。これらのエラー型は、より具体的なエラーハンドリングを可能にします。
    これらのAPIは、Unix系システムにおけるユーザーとグループの管理をGoプログラムからより容易に行えるようにするためのものです。

### `pkg runtime, func CallersFrames([]uintptr) *Frames`
### `pkg runtime, method (*Frames) Next() (Frame, bool)`
### `pkg runtime, type Frame struct`
### `pkg runtime, type Frame struct, Entry uintptr`
### `pkg runtime, type Frame struct, File string`
### `pkg runtime, type Frame struct, Func *Func`
### `pkg runtime, type Frame struct, Function string`
### `pkg runtime, type Frame struct, Line int`
### `pkg runtime, type Frame struct, PC uintptr`
### `pkg runtime, type Frames struct`

*   **目的**: `runtime` パッケージに、より詳細なスタックトレース情報を提供する新しいAPIを追加します。
*   **詳細**:
    *   `CallersFrames([]uintptr) *Frames`: `runtime.Callers` 関数で取得したプログラムカウンタ (PC) のスライスを受け取り、それを `Frames` イテレータに変換します。
    *   `Frames` 構造体: スタックフレームを順次処理するためのイテレータです。
    *   `(*Frames) Next() (Frame, bool)`: `Frames` イテレータから次のスタックフレームを取得します。フレームがなくなると `false` を返します。
    *   `Frame` 構造体: 個々のスタックフレームの詳細情報（`PC` (プログラムカウンタ), `Func` (関数情報), `Function` (関数名), `File` (ファイル名), `Line` (行番号), `Entry` (関数のエントリポイントのPC)）を保持します。
    これらのAPIは、デバッグやプロファイリングの際に、よりリッチで構造化されたスタックトレース情報をプログラムから取得できるようにするためのものです。これにより、エラー発生時の原因特定や、パフォーマンス分析がより容易になります。

### `pkg testing, type InternalExample struct, Unordered bool`

*   **目的**: `testing` パッケージの内部的な `InternalExample` 構造体に、テストの出力順序が重要でないことを示すフラグを追加します。
*   **詳細**: これは `go/doc, type Example struct, Unordered bool` と同様の目的を持つ内部的なAPIです。`testing` パッケージは、`go test` コマンドが `Example` 関数を実行する際に使用する内部構造体 `InternalExample` を持っています。この `Unordered` フィールドは、`go/doc` の `Example` と連携し、テスト実行時にも出力順序の不定性を考慮できるようにします。

# [インデックス 26561] ファイルの概要

このコミットは、Goランタイムのテストファイルである `src/runtime/stack_test.go` に関連する変更です。このファイルは、Goプログラムにおけるスタックの成長メカニズムと、ファイナライザの動作を検証するためのテストコードを含んでいます。特に、ガベージコレクションと連携してオブジェクトが解放される際に実行されるファイナライザの信頼性を確認するテストが含まれています。

## コミット

`runtime: don't call testing.Fatal from worker goroutines`

このコミットは、Goのテストフレームワークにおいて、メインではないワーカゴルーチンから `testing.T.Fatal` を呼び出すことによる潜在的な問題を修正します。具体的には、`TestStackGrowth` というテスト関数内で、ファイナライザが期待通りに実行されなかった場合に `t.Fatal` を使用していた箇所を `t.Error` と `return` に変更しています。これにより、テストのハングアップを防ぎ、より堅牢なテスト実行を保証します。

## 変更の背景

この変更の背景には、Goのテストフレームワークにおける `testing.T.Fatal` メソッドの挙動と、並行処理の基本単位であるゴルーチンとの相互作用に関する理解があります。

`testing.T.Fatal` は、テストが失敗したことを報告し、現在のテスト関数（またはより正確には、`t.Fatal` を呼び出したゴルーチン）の実行を即座に停止させるために使用されます。内部的には `runtime.Goexit()` を呼び出すことで、そのゴルーチンを終了させます。

問題は、`t.Fatal` がメインのテストゴルーチン（`TestXxx` 関数を実行しているゴルーチン）ではない、別のワーカゴルーチンから呼び出された場合に発生します。ワーカゴルーチンが `t.Fatal` を呼び出すと、そのワーカゴルーチン自体は終了しますが、メインのテストゴルーチンは引き続き実行され続けます。もしメインのテストゴルーチンが、ワーカゴルーチンの完了を `sync.WaitGroup` やチャネルなどを介して待機している場合、ワーカゴルーチンが `t.Fatal` で予期せず終了してしまうと、メインゴルーチンは永遠に待機状態となり、テストがハングアップしてしまう可能性があります。

`src/runtime/stack_test.go` の `TestStackGrowth` テストでは、ファイナライザの実行を待機するために別のゴルーチンを起動し、タイムアウト機構を設けています。このワーカゴルーチン内でファイナライザが20秒以内に実行されなかった場合、テストは失敗と判断されます。元のコードではここで `t.Fatal` を呼び出していましたが、これが前述のハングアップ問題を引き起こす可能性がありました。

このコミットは、この潜在的なハングアップ問題を解決し、テストの信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とテストフレームワークの知識が必要です。

*   **Goのゴルーチン (Goroutines)**:
    Goにおける軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千から数百万のゴルーチンを同時に実行できます。`go` キーワードを使って関数を呼び出すことで新しいゴルーチンが起動します。
*   **Goの`testing`パッケージ**:
    Goに組み込まれているテストフレームワークです。テスト関数は `TestXxx(*testing.T)` の形式で定義され、`go test` コマンドで実行されます。
*   **`*testing.T`のメソッド**:
    *   **`t.Fatal(args ...interface{})` / `t.Fatalf(format string, args ...interface{})`**:
        テストが失敗したことを報告し、現在のテスト関数（より正確には、`t.Fatal` を呼び出したゴルーチン）の実行を即座に停止させます。内部で `runtime.Goexit()` を呼び出します。
    *   **`t.Error(args ...interface{})` / `t.Errorf(format string, args ...interface{})`**:
        テストが失敗したことを報告しますが、テスト関数の実行は継続されます。テストの最後に、エラーが報告されたテストは失敗とマークされます。
    *   **`t.FailNow()`**:
        `t.Fatal` と同様に、現在のゴルーチンを終了させ、テストを失敗とマークします。
*   **`runtime.Goexit()`**:
    現在のゴルーチンを終了させますが、プログラム全体は終了させません。このゴルーチンに登録されている `defer` 関数は実行されます。他のゴルーチンは引き続き実行されます。
*   **`sync.WaitGroup`**:
    複数のゴルーチンの完了を待機するための同期プリミティブです。`Add()` でカウンタを増やし、各ゴルーチンが完了時に `Done()` を呼び出してカウンタを減らし、メインゴルーチンは `Wait()` でカウンタがゼロになるまで待機します。
*   **ファイナライザ (Finalizers)**:
    `runtime.SetFinalizer` 関数を使ってオブジェクトに登録できる関数です。ガベージコレクタがそのオブジェクトを回収する直前に、登録されたファイナライザが実行されます。主に、オブジェクトが占有していた外部リソース（ファイルハンドル、ネットワーク接続など）を解放するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、`testing.T.Fatal` と `testing.T.Error` の挙動の違い、特にゴルーチン環境下でのそれらの影響を理解することにあります。

`TestStackGrowth` テストは、Goのランタイムがスタックをどのように管理し、ファイナライザがどのように機能するかを検証します。このテストでは、特定のオブジェクトがガベージコレクションされ、それに登録されたファイナライザが実行されることを期待しています。ファイナライザの実行は非同期的に行われるため、テストは別のゴルーチンを起動して、ファイナライザが実行されたことを示すシグナル（`done` チャネル）を待機します。

元のコードでは、ファイナライザが20秒以内に実行されなかった場合、待機ゴルーチン内で `t.Fatal("finalizer did not run")` を呼び出していました。

1.  **`t.Fatal` の問題点**:
    *   `t.Fatal` は内部で `runtime.Goexit()` を呼び出し、**その呼び出し元のゴルーチンのみを終了させます**。
    *   `TestStackGrowth` の場合、`t.Fatal` を呼び出すのはファイナライザの実行を待機しているワーカゴルーチンです。このゴルーチンが終了しても、メインのテストゴルーチンは `wg.Wait()` で他のゴルーチン（この場合はワーカゴルーチン）の完了を待機し続ける可能性があります。
    *   結果として、ワーカゴルーチンは `t.Fatal` で終了するものの、メインゴルーチンは永遠に待機し続け、テストがハングアップするという問題が発生します。これは、テストの失敗を適切に報告できないだけでなく、CI/CDパイプラインなどでテストがタイムアウトする原因にもなります。

2.  **`t.Error` + `return` による解決**:
    *   `t.Error` はテストの失敗を記録しますが、**現在のゴルーチンを終了させません**。
    *   このコミットでは、`t.Fatal` を `t.Error` に変更し、その直後に `return` を追加しています。
    *   これにより、ファイナライザが実行されなかった場合、ワーカゴルーチンは `t.Error` で失敗を記録し、その後 `return` で自身の実行を正常に終了します。
    *   ワーカゴルーチンが正常に終了するため、メインのテストゴルーチンが `wg.Wait()` で待機している場合でも、ワーカゴルーチンの完了を検出し、テスト全体がハングアップすることなく終了できます。
    *   `t.Error` によってテストは失敗とマークされるため、テスト結果としては正しく失敗が報告されます。

この変更は、Goのテストコードを書く上で、特に並行処理を伴うテストにおいて `t.Fatal` と `t.Error` の使い分けの重要性を示しています。ワーカゴルーチンからのエラー報告には `t.Error` を使用し、必要に応じてチャネルや `sync.WaitGroup` を介してメインゴルーチンにエラーを伝達し、メインゴルーチンで `t.Fatal` を呼び出すのが一般的なベストプラクティスです。

## コアとなるコードの解説

変更は `src/runtime/stack_test.go` ファイル内の `TestStackGrowth` 関数にあります。

このテスト関数内では、`go func() { ... }()` という形式で新しいゴルーチンが起動されています。このゴルーチンは、`done` チャネルからのシグナル、または20秒のタイムアウトのいずれかを `select` ステートメントで待機しています。

*   **`case <-done:`**: ファイナライザが正常に実行された場合に `done` チャネルに値が送信され、このケースが選択されます。この場合、ゴルーチンは正常に終了します。
*   **`case <-time.After(20 * time.Second):`**: 20秒以内にファイナライザが実行されなかった場合、このケースが選択されます。これはテストの失敗を意味します。

変更前は、タイムアウトが発生した場合に `t.Fatal("finalizer did not run")` が呼び出されていました。前述の通り、これはワーカゴルーチンを終了させるだけで、メインのテストゴルーチンをハングアップさせる可能性がありました。

変更後は、`t.Error("finalizer did not run")` と `return` に置き換えられています。

*   `t.Error("finalizer did not run")`: テストの失敗を `testing.T` オブジェクトに記録します。これにより、テスト全体が最終的に失敗とマークされます。
*   `return`: `t.Error` の呼び出し後、ワーカゴルーチンは明示的に `return` ステートメントによって自身の実行を終了します。これにより、このゴルーチンを待機している `sync.WaitGroup` (このテストでは `wg.Wait()` が使用されています) が適切にデクリメントされ、メインのテストゴルーチンがハングアップすることなく、テストが正常に完了（ただし失敗として）できるようになります。

この修正により、テストの信頼性が向上し、並行処理を含むテストにおける `testing` パッケージのより安全な使用方法が示されています。

## 変更の背景
このコミットの主な目的は、Goコンパイラの内部における文法定義を簡素化することです。具体的には、`LBASETYPE` と `LACONST` という2つのレキシカル（字句解析）トークンを削除し、それらの役割を既存の `LATYPE` および `LNAME` トークンに統合しています。

初期のGoコンパイラでは、字句解析の段階で「基本型（LBASETYPE）」と「定数（LACONST）」をそれぞれ独立したトークンとして識別していました。しかし、これは文法解析の複雑さを増す可能性があり、また、より汎用的な「型（LATYPE）」や「名前（LNAME）」の概念で表現できる部分を細分化しすぎているという判断があったと考えられます。

この変更により、コンパイラのフロントエンド（特に字句解析器と構文解析器）のロジックが単純化され、保守性や理解度が向上することが期待されます。また、Go言語の進化の過程で、より洗練された内部表現を追求する一環とも言えます。

## 前提知識の解説

### 1. コンパイラの基本構造
Goコンパイラは、一般的なコンパイラと同様に、以下の主要なフェーズで構成されます。

*   **字句解析 (Lexical Analysis / Scanning)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割します。例えば、`int`、`float64`、`true`、`false`、変数名、演算子などがトークンとして識別されます。このフェーズを担当するのが「字句解析器（Lexer）」です。
*   **構文解析 (Syntax Analysis / Parsing)**: 字句解析器が生成したトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST: Abstract Syntax Tree）を構築します。このフェーズを担当するのが「構文解析器（Parser）」です。Goコンパイラでは、Yacc（Yet Another Compiler Compiler）のようなツールで生成されたパーサーが使用されることがあります（`go.y`ファイルがこれに該当します）。
*   **意味解析 (Semantic Analysis)**: 抽象構文木を走査し、型チェック、変数宣言の解決、スコープの検証など、プログラムの意味的な正当性を確認します。
*   **コード生成 (Code Generation)**: 抽象構文木から、ターゲットマシンが実行可能な機械語や中間コードを生成します。

### 2. Yacc (Yet Another Compiler Compiler)
Yaccは、文法定義から構文解析器（パーサー）を自動生成するツールです。Goコンパイラの `src/cmd/gc/go.y` ファイルはYaccの入力ファイルであり、Go言語の文法規則が定義されています。このファイルでは、トークン（`%token`）や非終端記号（`%type`）、そしてそれらの組み合わせによる文法規則が記述されます。

### 3. レキシカルトークン (Lexical Tokens)
字句解析器によって識別される最小単位です。例えば、`LNAME` は識別子（変数名、関数名など）、`LATYPE` は型名（ユーザー定義型を含む）、`LBASETYPE` は組み込みの基本型（`int`, `bool` など）、`LACONST` は定数（`true`, `false`, 数値リテラルなど）を表すトークンとして使われていました。

### 4. Goの型システム
Go言語は静的型付け言語であり、すべての変数や式には型があります。この型情報はコンパイル時に厳密にチェックされ、プログラムの安全性と効率性を保証します。`int`、`float64`、`bool` などの組み込み型から、構造体、インターフェース、配列、スライス、マップ、チャネルなどの複合型まで、多様な型が存在します。

### 5. `io` パッケージと `sync` パッケージ
*   **`io` パッケージ**: 入出力プリミティブを提供します。`Reader`、`Writer`、`Closer` などのインターフェースが定義されており、様々なデータソースやシンクに対して統一的なI/O操作を可能にします。このコミットでは、`io.Pipe` の実装に修正が入っています。`io.Pipe` は、Goのgoroutine間でデータをストリームとしてやり取りするためのインメモリパイプを提供します。
*   **`sync` パッケージ**: 低レベルの同期プリミティブを提供します。`Mutex`（相互排他ロック）や `WaitGroup` などがあり、並行処理におけるデータ競合を防ぎ、goroutine間の協調を可能にします。このコミットでは、`sync.Mutex` のコメントが修正されています。

## 技術的詳細

このコミットは、主にGoコンパイラの字句解析器と構文解析器、そして標準ライブラリの一部に影響を与えています。

### 1. 文法簡素化 (`LBASETYPE`, `LACONST` の削除)

*   **`src/cmd/gc/go.y` (Yacc文法定義ファイル) の変更**:
    *   `%token` 定義から `LBASETYPE` と `LACONST` が削除されました。
    *   `%type` 定義から `laconst` が削除されました。
    *   `pexpr`（プライマリ式）の規則から `laconst` に対応する部分が削除されました。これにより、定数リテラルは `LACONST` ではなく、より一般的な `LLITERAL` トークンとして扱われるようになります。
    *   `sym` および `sym3` の規則から `LBASETYPE` と `LACONST` が削除されました。
    *   `laconst` および `latype` のエラーハンドリング規則が削除または修正されました。これは、これらのトークンがもはや存在しないため、それらに関連する特定の型チェックやエラーが不要になったためです。

*   **`src/cmd/gc/lex.c` (字句解析器ファイル) の変更**:
    *   `typeinit` 関数の呼び出しで、`LBASETYPE` の代わりに `LATYPE` が渡されるようになりました。これは、基本型も `LATYPE` として初期化されることを意味します。
    *   `talph` 関数（識別子を字句解析する関数）内で、`s->lexical == LBASETYPE` のチェックが削除されました。これは、基本型がもはや `LBASETYPE` として特別扱いされないためです。
    *   組み込みの基本型（`int8`, `float32`, `bool`, `string` など）の定義において、以前は `LBASETYPE` と関連付けられていたものが、すべて `LATYPE` と関連付けられるように変更されました。これにより、基本型もユーザー定義型と同様に `LATYPE` として扱われるようになります。
    *   `lexinit` 関数内の `syms` 配列の初期化ロジックが修正され、`LBASETYPE` に関連する特殊な処理が削除されました。
    *   字句トークンの名前定義（`struct { char *name; int lexical; }`）から `LACONST` と `LBASETYPE` が削除されました。

*   **`src/cmd/gc/dcl.c` (宣言処理ファイル) の変更**:
    *   `addconst` 関数内で、定数のレキシカルタイプが `LACONST` から `LNAME` に変更されました。これは、定数も一般的な名前として扱われるようになったことを示します。
    *   `oldname` 関数内で、シンボルが定数である場合の処理が追加されました。これは、`LACONST` が削除されたため、`LNAME` として扱われる定数を適切に処理するための変更です。
    *   `nametoanondcl` 関数内で、型を識別するロジックから `LBASETYPE` のチェックが削除されました。型はすべて `LATYPE` または `n->sym->otype` を通じて識別されるようになりました。

*   **`src/cmd/gc/export.c` (エクスポート処理ファイル) の変更**:
    *   `dumpsym` 関数内で、`LBASETYPE` のケースが削除されました。
    *   `LNAME` と `LACONST` のケースが統合され、シンボルが定数であるかどうか（`s->oconst` の有無）で処理を分岐するようになりました。これにより、定数も `LNAME` の一種としてエクスポートされることになります。
    *   `importconst` 関数内で、インポートされる定数のレキシカルタイプが `LACONST` から `LNAME` に変更されました。

これらの変更は、Goコンパイラのフロントエンドにおける型と定数の内部表現を統一し、文法規則と字句解析のロジックを大幅に簡素化することを目的としています。これにより、コンパイラのコードベースがよりクリーンで理解しやすくなります。

### 2. `src/lib/io/pipe.go` の変更

`io.Pipe` の実装が大幅に改善されています。

*   `pipeReturn` 構造体に `err` フィールドが追加され、パイプ操作のエラーを伝達できるようになりました。
*   `pipe` 構造体に `rerr` (read error) と `werr` (write error) が追加され、読み書きの終了時にエラー情報を保持できるようになりました。
*   `Read` および `Write` メソッドで、パイプが閉じられた際のエラー処理が改善されました。特に、書き込み側がエラーで閉じられた場合に、読み込み側がそのエラーを受け取れるようになりました。
*   `CloseReader` および `CloseWriter` メソッドに `rerr` / `werr` 引数が追加され、パイプを閉じる際に特定のエラーを渡せるようになりました。これにより、パイプの終了理由をより詳細に伝えることが可能になります。
*   `pipeRead` と `pipeWrite` がそれぞれ `PipeReader` と `PipeWriter` というエクスポートされた型に変更されました。これにより、ユーザーは `io.Pipe` が返す具体的な型を直接利用できるようになり、より柔軟なエラーハンドリングや型アサーションが可能になります。
*   `Pipe()` 関数が `(io.ReadCloser, io.WriteCloser)` ではなく `(*PipeReader, *PipeWriter)` を返すように変更されました。これは、新しいエクスポートされた型を返すためです。
*   `PipeReader` と `PipeWriter` に `CloseWithError` メソッドが追加され、エラーを伴ってパイプを閉じることができるようになりました。

これらの変更は、`io.Pipe` の堅牢性と使いやすさを向上させ、特にエラー伝播のメカニズムを強化しています。

### 3. `src/lib/bufio/bufio.go` の変更

`bufio.Reader` の `Read` メソッドのコメントが修正されました。
*   以前のコメントでは、EOF時に `io.ErrEOF` を返すとされていましたが、新しいコメントでは `io.ErrUnexpectedEOF` を返す可能性があることが明記されました。これは、部分的な読み込みが発生した場合の挙動をより正確に反映しています。

### 4. `src/lib/io/io.go` の変更

*   `ReadByter` インターフェースと `WriteByter` インターフェースが追加されました。これらはそれぞれ `ReadByte()` と `WriteByte()` メソッドを持つインターフェースで、バイト単位の読み書き操作を抽象化します。
*   `StringBytes` 関数のコメントが修正され、より明確になりました。

### 5. `src/lib/runtime/types.go` の新規追加

このコミットで `src/lib/runtime/types.go` という新しいファイルが追加されました。これは非常に重要な変更です。

*   このファイルは、Goのランタイムが内部的に使用する型情報を定義しています。
*   `Type` インターフェースが定義され、すべてのランタイム型構造がこのインターフェースを実装します。
*   `CommonType` 構造体が定義され、すべての型が共通して持つフィールド（`Size`, `Hash`, `Alg`, `Align`, `FieldAlign`）をカプセル化します。
*   `BoolType`, `Float32Type`, `IntType` などの基本的な型を表す構造体が `CommonType` を埋め込む形で定義されています。
*   `ArrayType`, `ChanType`, `FuncType`, `InterfaceType`, `MapType`, `NamedType`, `PtrType`, `StructType` など、Goの複合型を表す構造体が詳細に定義されています。これらの構造体には、要素の型、チャネルの方向、関数の引数/戻り値、インターフェースのメソッド、マップのキー/要素、構造体のフィールドなどの情報が含まれます。
*   `IMethod` と `Method` 構造体も定義され、インターフェースメソッドと具象型のメソッドの情報を保持します。

このファイルの追加は、Goのランタイムが型情報をより構造化された形で管理し、リフレクションやガベージコレクションなどのランタイム機能で利用できるようにするための基盤を構築するものです。これは、Go言語の型システムがどのようにランタイムで表現され、利用されるかを示す重要な一歩です。

### 6. `src/lib/sync/mutex.go` の変更

*   `sync` パッケージのコメントが修正され、より簡潔になりました。
*   `Mutex` 構造体と `Lock` メソッドのコメントが、C言語スタイルのブロックコメントからGo言語の慣習に沿ったコメントスタイルに変更されました。意味的な変更はありませんが、コードの可読性と一貫性が向上しています。

### 7. `src/lib/Make.deps` の変更

*   `go/doc.install` の依存関係に `template.install` が追加されました。これは、Goのドキュメント生成ツールがテンプレート機能を利用するようになったことを示唆しています。
*   `testing/iotest.install` の依存関係に `log.install` が追加されました。これは、`testing/iotest` パッケージがログ機能を利用するようになったことを示唆しています。

## 変更の背景
このコミットの主な目的は、Goコンパイラの内部における文法定義を簡素化することです。具体的には、`LBASETYPE` と `LACONST` という2つのレキシカル（字句解析）トークンを削除し、それらの役割を既存の `LATYPE` および `LNAME` トークンに統合しています。

初期のGoコンパイラでは、字句解析の段階で「基本型（LBASETYPE）」と「定数（LACONST）」をそれぞれ独立したトークンとして識別していました。しかし、これは文法解析の複雑さを増す可能性があり、また、より汎用的な「型（LATYPE）」や「名前（LNAME）」の概念で表現できる部分を細分化しすぎているという判断があったと考えられます。

この変更により、コンパイラのフロントエンド（特に字句解析器と構文解析器）のロジックが単純化され、保守性や理解度が向上することが期待されます。また、Go言語の進化の過程で、より洗練された内部表現を追求する一環とも言えます。

## 前提知識の解説

### 1. コンパイラの基本構造
Goコンパイラは、一般的なコンパイラと同様に、以下の主要なフェーズで構成されます。

*   **字句解析 (Lexical Analysis / Scanning)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割します。例えば、`int`、`float64`、`true`、`false`、変数名、演算子などがトークンとして識別されます。このフェーズを担当するのが「字句解析器（Lexer）」です。
*   **構文解析 (Syntax Analysis / Parsing)**: 字句解析器が生成したトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST: Abstract Syntax Tree）を構築します。このフェーズを担当するのが「構文解析器（Parser）」です。Goコンパイラでは、Yacc（Yet Another Compiler Compiler）のようなツールで生成されたパーサーが使用されることがあります（`go.y`ファイルがこれに該当します）。
*   **意味解析 (Semantic Analysis)**: 抽象構文木を走査し、型チェック、変数宣言の解決、スコープの検証など、プログラムの意味的な正当性を確認します。
*   **コード生成 (Code Generation)**: 抽象構文木から、ターゲットマシンが実行可能な機械語や中間コードを生成します。

### 2. Yacc (Yet Another Compiler Compiler)
Yaccは、文法定義から構文解析器（パーサー）を自動生成するツールです。Goコンパイラの `src/cmd/gc/go.y` ファイルはYaccの入力ファイルであり、Go言語の文法規則が定義されています。このファイルでは、トークン（`%token`）や非終端記号（`%type`）、そしてそれらの組み合わせによる文法規則が記述されます。

### 3. レキシカルトークン (Lexical Tokens)
字句解析器によって識別される最小単位です。例えば、`LNAME` は識別子（変数名、関数名など）、`LATYPE` は型名（ユーザー定義型を含む）、`LBASETYPE` は組み込みの基本型（`int`, `bool` など）、`LACONST` は定数（`true`, `false`, 数値リテラルなど）を表すトークンとして使われていました。

### 4. Goの型システム
Go言語は静的型付け言語であり、すべての変数や式には型があります。この型情報はコンパイル時に厳密にチェックされ、プログラムの安全性と効率性を保証します。`int`、`float64`、`bool` などの組み込み型から、構造体、インターフェース、配列、スライス、マップ、チャネルなどの複合型まで、多様な型が存在します。

### 5. `io` パッケージと `sync` パッケージ
*   **`io` パッケージ**: 入出力プリミティブを提供します。`Reader`、`Writer`、`Closer` などのインターフェースが定義されており、様々なデータソースやシンクに対して統一的なI/O操作を可能にします。このコミットでは、`io.Pipe` の実装に修正が入っています。`io.Pipe` は、Goのgoroutine間でデータをストリームとしてやり取りするためのインメモリパイプを提供します。
*   **`sync` パッケージ**: 低レベルの同期プリミティブを提供します。`Mutex`（相互排他ロック）や `WaitGroup` などがあり、並行処理におけるデータ競合を防ぎ、goroutine間の協調を可能にします。このコミットでは、`sync.Mutex` のコメントが修正されています。

## コアとなるコードの解説

### 1. `src/cmd/gc/go.y` におけるトークン定義の変更
この変更は、Goコンパイラの構文解析器の心臓部である `go.y` ファイルにおけるトークン定義の根本的な簡素化を示しています。
*   `- %token <sym> LNAME LBASETYPE LATYPE LPACK LACONST` から `+ %token <sym> LNAME LATYPE LPACK` への変更は、`LBASETYPE` と `LACONST` という特定のトークンが文法レベルで直接扱われなくなったことを意味します。
*   これに伴い、`%type` 定義から `laconst` が削除され、`pexpr` 規則から `laconst` に対応するプロダクション（文法規則）が削除されました。これは、定数リテラルが `LACONST` という専用のトークンとしてではなく、より汎用的な `LLITERAL` トークンとして扱われるようになったためです。
*   `sym` や `sym3` といったシンボル定義からも `LBASETYPE` と `LACONST` が削除されており、これにより、これらの特定のレキシカルカテゴリが構文解析の段階で特別扱いされなくなりました。
*   `laconst` や `latype` に関連するエラーハンドリング規則の削除は、これらのトークンが文法から消えたため、それらに関連する特定の文法エラーチェックが不要になったことを示しています。

この変更により、Go言語の文法がより抽象的かつ統一的な方法で表現されるようになり、コンパイラの構文解析ロジックが単純化されます。例えば、`int` のような基本型も、ユーザー定義型と同様に `LATYPE` として扱われることで、型に関する文法規則の記述が簡潔になります。

### 2. `src/cmd/gc/lex.c` における基本型の字句解析変更
この変更は、字句解析器が基本型をどのように識別するかを変更しています。
*   以前は、`"int8"` などの基本型は `LBASETYPE` というレキシカルカテゴリに分類されていました。しかし、この変更により、すべての基本型が `LATYPE` に分類されるようになりました。
*   これは、字句解析の段階で基本型とユーザー定義型を区別する必要がなくなったことを意味します。両者とも「型」として `LATYPE` に統一されることで、字句解析器のロジックが簡素化されます。
*   `lexinit` 関数内の `syms` 配列の初期化ロジックや、`talph` 関数内の `LBASETYPE` 関連のチェックが削除されたのは、この統一化の結果です。字句解析器は、もはや `LBASETYPE` という特別なカテゴリを認識する必要がありません。

この変更は、コンパイラのフロントエンドにおける型情報の処理を合理化し、コードベースの重複を減らすことに貢献します。

### 3. `src/lib/runtime/types.go` の新規追加
このファイルは、Goのランタイムが型情報をどのように表現し、管理するかを定義するものです。これは、Goの型システムがコンパイル時だけでなく、実行時にもどのように利用されるかを示す重要な基盤となります。
*   `Type` インターフェースは、すべてのランタイム型構造が満たすべき共通の契約を定義します。
*   `CommonType` は、すべての型が持つ共通のメタデータ（サイズ、ハッシュ、アライメントなど）をカプセル化します。これにより、型情報の管理が一貫性を持つようになります。
*   `BoolType`, `IntType` などの基本型から、`ArrayType`, `ChanType`, `FuncType`, `InterfaceType`, `MapType`, `NamedType`, `PtrType`, `StructType` などの複合型まで、Go言語のあらゆる型が対応する構造体として定義されています。これらの構造体は、それぞれの型の特性（例えば、配列の要素型と境界、チャネルの要素型と方向、関数の引数と戻り値、構造体のフィールドなど）を詳細に保持します。
*   特に注目すべきは、`IMethod` と `Method` の定義です。これらは、インターフェースのメソッドと具象型のメソッドに関する情報をランタイムで利用できるようにします。これは、リフレクションやインターフェースの動的なディスパッチにおいて不可欠な情報となります。

この `types.go` ファイルの導入は、Goのランタイムが型情報をよりリッチに、かつ構造化された形で保持するようになったことを意味します。これにより、ガベージコレクションの効率化、リフレクション機能の強化、デバッグ情報の充実など、Goランタイムの様々な側面が向上します。これは、Go言語が成熟していく過程で、内部的な型表現がより洗練されていったことを示す重要なマイルストーンと言えるでしょう。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現（IR）を複数段階で利用します。SSA (Static Single Assignment) 形式はその重要な中間表現の一つであり、最適化の主要な舞台となります。このコミットが作成された時期は、Goコンパイラが従来のAST (Abstract Syntax Tree) ベースのバックエンドから、より高度な最適化を可能にするSSAベースのバックエンドへと移行している最中でした（`dev.ssa`ブランチでの開発）。

従来のコンパイラでは、非数値型の比較、特に参照型（スライス、インターフェース、関数、マップ、チャネル）の比較は、特定のルールに基づいて処理されていました。しかし、SSAバックエンドに移行するにあたり、これらの比較操作をSSA形式で正確に表現し、その後の最適化やコード生成に引き継ぐためのメカニズムが必要でした。

このコミットの主な背景は以下の点にあります。

1.  **SSAバックエンドへの移行**: SSAバックエンドは、より強力な最適化を可能にするために、プログラムのデータフローを明示的に表現します。非数値型の比較もこの新しいフレームワークに適合させる必要がありました。
2.  **Go言語の比較セマンティクス**: Go言語では、スライス、インターフェース、関数、マップ、チャネルの比較には特定の制約があります。
    *   **スライス**: スライスは直接比較できません。唯一許されるのは `nil` との比較です。`nil` スライスは、基盤となる配列へのポインタが `nil` であり、長さと容量が0であることを意味します。
    *   **インターフェース**: インターフェースは、その動的な型と値が両方とも等しい場合にのみ等しいとされます。ただし、コンパイル時に `nil` との比較に限定される場合があります。
    *   **関数、マップ、チャネル**: これらは参照型であり、`nil` との比較、または同じ型の別の変数とのポインタ等価性（つまり、同じ基盤となるランタイムオブジェクトを参照しているか）のみが許されます。
3.  **最適化の機会**: これらの比較の特性をSSAバックエンドで正確にモデル化することで、不要な比較や冗長なコードを排除する最適化の機会が生まれます。例えば、`nil` との比較は、単なるポインタのゼロ値チェックに簡略化できます。

このコミットは、これらの非数値比較をSSA形式で表現するための新しいSSAオペレーション（`EqPtr`, `NeqPtr`, `EqFat`, `NeqFat`）を導入し、それらをGoのフロントエンドの比較演算子（`OEQ`, `ONE`）にマッピングし、さらにAMD64アーキテクチャ向けのコード生成ルールと汎用的な書き換えルールを定義することで、SSAバックエンドがこれらの比較を正しく処理できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラとGo言語の概念に関する知識が必要です。

### 1. Goコンパイラの構造とSSA

Goコンパイラ（`cmd/compile`）は、複数のフェーズを経てGoのソースコードを機械語に変換します。主要なフェーズは以下の通りです。

*   **フロントエンド (Parsing & Type Checking)**: ソースコードを解析し、ASTを構築し、型チェックを行います。この段階で、Go言語の比較規則が適用され、不正な比較はエラーとなります。
*   **ミドルエンド (IR Generation & Optimization)**: ASTをSSA (Static Single Assignment) 形式の中間表現に変換します。SSA形式は、各変数が一度だけ代入されることを保証し、データフロー解析と最適化を容易にします。このフェーズで、多くの言語非依存の最適化が行われます。
*   **バックエンド (Code Generation)**: SSA形式のIRを特定のアーキテクチャ（例: AMD64）の機械語に変換します。この段階で、アーキテクチャ固有の最適化やレジスタ割り当てが行われます。

このコミットは主にミドルエンド（SSA生成と最適化ルール）とバックエンド（AMD64のコード生成ルール）に影響を与えます。

### 2. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において非常に強力な中間表現です。その主要な特性は以下の通りです。

*   **単一代入**: 各変数はプログラム内で一度だけ値を割り当てられます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi Function)**: 複数の制御フローパスが合流する点で、同じ論理変数に異なる値が割り当てられる可能性がある場合、Φ関数が導入されます。Φ関数は、どのパスから来たかに応じて適切な値を選択します。

このコミットでは、比較演算をSSAオペレーションとして表現し、SSA形式のルールに基づいて最適化やコード生成を行うための基盤を構築しています。

### 3. Go言語の型の比較セマンティクス

Go言語では、型の種類によって比較の挙動が異なります。

*   **数値型 (int, floatなど)**: 通常の値の比較（等しい、より大きい、より小さいなど）が可能です。
*   **文字列**: 辞書順での比較が可能です。
*   **構造体**: すべてのフィールドが比較可能であり、かつすべてのフィールドが等しい場合にのみ等しいとされます。
*   **配列**: すべての要素が比較可能であり、かつすべての要素が等しい場合にのみ等しいとされます。
*   **ポインタ**: ポインタが指すアドレスが等しい場合にのみ等しいとされます。
*   **スライス**: スライスは直接比較できません（`==` や `!=` はコンパイルエラー）。唯一許されるのは `nil` との比較です。`nil` スライスは、基盤となる配列へのポインタが `nil` であり、長さと容量が0であることを意味します。
*   **インターフェース**: インターフェース値は、その動的な型と動的な値が両方とも等しい場合にのみ等しいとされます。`nil` との比較も可能です。`nil` インターフェースは、動的な型と値が両方とも `nil` である状態を指します。
*   **関数**: 関数は直接比較できません。唯一許されるのは `nil` との比較、または同じ関数オブジェクトを参照しているかどうかのポインタ等価性です。
*   **マップ**: マップは直接比較できません（`==` や `!=` はコンパイルエラー）。唯一許されるのは `nil` との比較です。
*   **チャネル**: チャネルは直接比較できません。唯一許されるのは `nil` との比較、または同じチャネルオブジェクトを参照しているかどうかのポインタ等価性です。

このコミットの目的は、これらのGo言語の比較セマンティクスをSSAバックエンドで正確に反映させることです。特に、スライスやインターフェースの `nil` 比較、および関数、マップ、チャネルのポインタ等価性比較に焦点を当てています。

### 4. `opToSSA` マッピング

`cmd/compile/internal/gc/ssa.go` にある `opToSSA` マップは、Goコンパイラのフロントエンドで使われるASTノードのオペレーションコード（例: `OEQ` for equality, `ONE` for inequality）と、Goの型（例: `TINT8` for 8-bit integer）の組み合わせを、SSAバックエンドで使われるSSAオペレーション（例: `ssa.OpEq8`）にマッピングするために使用されます。このマップを拡張することで、新しいSSAオペレーションが導入され、非数値型の比較がSSA形式で表現できるようになります。

### 5. SSAオペレーションと書き換えルール

SSAバックエンドでは、SSAオペレーション（例: `OpEq8`, `OpLoad`, `OpConst`）がプログラムの基本的な操作を表します。これらのオペレーションは、最終的にターゲットアーキテクチャの機械語命令に変換されます。この変換は、**書き換えルール (rewrite rules)** を通じて行われます。

*   **汎用書き換えルール (`rewritegeneric.go`)**: 特定のアーキテクチャに依存しない、一般的な最適化や変換ルールを定義します。例えば、`EqFat` オペレーションを `EqPtr` オペレーションに変換するようなルールが含まれます。
*   **アーキテクチャ固有の書き換えルール (`rewriteAMD64.go`)**: 特定のアーキテクチャ（例: AMD64）の命令セットを利用して、SSAオペレーションを効率的な機械語命令に変換するルールを定義します。例えば、`EqPtr` オペレーションを `CMPQ` (Compare Quadword) と `SETEQ` (Set if Equal) 命令の組み合わせに変換するルールが含まれます。

これらのルールは、SSA形式のプログラムをより低レベルの表現に段階的に変換し、最終的に機械語を生成するために不可欠です。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSAバックエンドにおける非数値型の比較処理の拡張にあります。

### 1. 新しいSSAオペレーションの導入

`src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/opGen.go` に、以下の新しいSSAオペレーションが導入されました。

*   `EqPtr`: ポインタの等価性比較（`==`）
*   `NeqPtr`: ポインタの非等価性比較（`!=`）
*   `EqFat`: スライスやインターフェースの等価性比較（主に `nil` との比較）
*   `NeqFat`: スライスやインターフェースの非等価性比較（主に `nil` との比較）

`EqFat` と `NeqFat` は「Fat Pointer」（スライスやインターフェースが内部的にポインタと長さ/型情報を持つ構造体であることに由来）の比較を意味し、特に `nil` との比較に特化しています。コミットメッセージにあるように、スライスやインターフェースのバックエンドに到達する比較は `nil` との比較のみであるため、この設計はGo言語のセマンティクスに合致しています。

### 2. `opToSSA` マッピングの拡張

`src/cmd/compile/internal/gc/ssa.go` の `opToSSA` マップが更新され、Goのフロントエンドの比較演算子（`OEQ`, `ONE`）と特定の型の組み合わせが、新しいSSAオペレーションにマッピングされるようになりました。

*   `OEQ, TINTER` -> `ssa.OpEqFat` (インターフェースの等価性比較)
*   `OEQ, TARRAY` -> `ssa.OpEqFat` (スライスの等価性比較)
*   `OEQ, TFUNC` -> `ssa.OpEqPtr` (関数の等価性比較)
*   `OEQ, TMAP` -> `ssa.OpEqPtr` (マップの等価性比較)
*   `OEQ, TCHAN` -> `ssa.OpEqPtr` (チャネルの等価性比較)
*   `OEQ, TUINTPTR` -> `ssa.OpEqPtr` (uintptrの等価性比較)

同様に、`ONE` (非等価性) 演算子についても `ssa.OpNeqFat` や `ssa.OpNeqPtr` へのマッピングが追加されています。

このマッピングにより、Goのソースコードで書かれたこれらの型の比較が、SSA形式の適切なオペレーションに変換され、SSAバックエンドで処理されるようになります。

### 3. AMD64アーキテクチャ固有の書き換えルール

`src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` に、`EqPtr` および `NeqPtr` オペレーションをAMD64アセンブリ命令に変換するためのルールが追加されました。

*   `(EqPtr x y) -> (SETEQ (CMPQ <TypeFlags> x y))`
*   `(NeqPtr x y) -> (SETNE (CMPQ <TypeFlags> x y))`

これは、2つのポインタ `x` と `y` を比較し（`CMPQ`）、その結果に基づいてフラグレジスタを設定し、等しい場合は `SETEQ` (Set if Equal)、等しくない場合は `SETNE` (Set if Not Equal) 命令で結果をブール値として設定することを意味します。`CMPQ` は64ビット値を比較するための命令であり、ポインタが通常64ビットであるAMD64アーキテクチャに適しています。

### 4. 汎用書き換えルール

`src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` に、`EqFat` および `NeqFat` オペレーションを処理するための汎用的な書き換えルールが追加されました。

*   `EqFat` および `NeqFat` の引数の順序を正規化するルール（定数が右側に来るように）
    *   `(EqFat x y) && x.Op == OpConst && y.Op != OpConst -> (EqFat y x)`
    *   `(NeqFat x y) && x.Op == OpConst && y.Op != OpConst -> (NeqFat y x)`
*   `EqFat` および `NeqFat` を `nil` との比較に変換するルール
    *   `(EqFat (Load ptr mem) y) && y.Op == OpConst -> (EqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))`
    *   `(NeqFat (Load ptr mem) y) && y.Op == OpConst -> (NeqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))`

これらのルールは、スライスやインターフェースが `nil` と比較される場合、その内部表現（通常は先頭のワード、つまり基盤となるデータへのポインタや動的な型情報）がゼロ値（`nil`）であるかどうかをチェックする `EqPtr` または `NeqPtr` オペレーションに変換されることを示しています。これにより、`EqFat` や `NeqFat` といった高レベルの概念が、より低レベルで効率的なポインタ比較に簡略化されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルでは、GoのASTノードの演算子と型をSSAオペレーションにマッピングする `opToSSA` マップが拡張されています。

```go
// 変更前
// opAndType{OEQ, TINT8}:   ssa.OpEq8,
// ...
// opAndType{OEQ, TPTR64}:  ssa.OpEq64,

// 変更後
opAndType{OEQ, TBOOL}:    ssa.OpEq8,
opAndType{OEQ, TINT8}:    ssa.OpEq8,
// ...
opAndType{OEQ, TPTR64}:   ssa.OpEq64,
opAndType{OEQ, TINTER}:   ssa.OpEqFat, // e == nil only
opAndType{OEQ, TARRAY}:   ssa.OpEqFat, // slice only; a == nil only
opAndType{OEQ, TFUNC}:    ssa.OpEqPtr,
opAndType{OEQ, TMAP}:     ssa.OpEqPtr,
opAndType{OEQ, TCHAN}:    ssa.OpEqPtr,
opAndType{OEQ, TUINTPTR}: ssa.OpEqPtr,
```

この変更は、Goのフロントエンドが `==` (OEQ) や `!=` (ONE) 演算子を検出した際に、そのオペランドの型に基づいて適切なSSAオペレーションを選択するように指示します。
*   `TINTER` (インターフェース) や `TARRAY` (スライス) の比較は `OpEqFat` にマッピングされます。これは、これらの型が内部的に複数のワード（ポインタと長さ/型情報など）で構成される「Fat Pointer」として扱われ、特に `nil` との比較に特化したオペレーションであることを示唆しています。
*   `TFUNC` (関数), `TMAP` (マップ), `TCHAN` (チャネル), `TUINTPTR` (uintptr) の比較は `OpEqPtr` にマッピングされます。これらの型は参照型であり、その等価性比較は基盤となるポインタの等価性で十分であるためです。

### `src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

これらのファイルでは、`EqFat` および `NeqFat` オペレーションを処理するための汎用的な書き換えルールが定義されています。

```go
// slice and interface comparisons
// the frontend ensures that we can only compare against nil
// start by putting nil on the right to simplify the other rules
(EqFat x y) && x.Op == OpConst && y.Op != OpConst -> (EqFat y x)
(NeqFat x y) && x.Op == OpConst && y.Op != OpConst -> (NeqFat y x)
// it suffices to check the first word (backing array for slices, dynamic type for interfaces)
(EqFat (Load ptr mem) y) && y.Op == OpConst -> (EqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))
(NeqFat (Load ptr mem) y) && y.Op == OpConst -> (NeqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))
```

*   最初の2つのルールは、`EqFat` または `NeqFat` オペレーションの引数の順序を正規化します。もし左オペランドが定数 (`OpConst`) で、右オペランドが定数でない場合、オペランドを入れ替えて定数が常に右側に来るようにします。これは、後続のルールを簡素化するためによく行われる最適化です。
*   次の2つのルールは、`EqFat` または `NeqFat` オペレーションが `nil` との比較である場合に適用されます。
    *   `(Load ptr mem)` は、メモリから値をロードするSSAオペレーションを表します。ここでは、スライスやインターフェースの構造体の先頭ワード（ポインタ）をロードすることを意味します。
    *   `y.Op == OpConst` は、比較対象が定数、特に `nil` を表すゼロ定数であることを意味します。
    *   このルールは、`EqFat` (または `NeqFat`) オペレーションを、ロードされたポインタとゼロ定数 (`Const <config.Uintptr> [0]`) の `EqPtr` (または `NeqPtr`) 比較に変換します。
    *   これは、スライスやインターフェースが `nil` であるかどうかを判断するには、その内部ポインタが `nil` (ゼロ) であるかをチェックすれば十分であるというGo言語のセマンティクスを反映しています。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

これらのファイルでは、`EqPtr` および `NeqPtr` オペレーションをAMD64アセンブリ命令に変換するルールが定義されています。

```go
// AMD64.rules
(EqPtr x y) -> (SETEQ (CMPQ <TypeFlags> x y))
(NeqPtr x y) -> (SETNE (CMPQ <TypeFlags> x y))

// rewriteAMD64.go (簡略化された表現)
case OpEqPtr:
    x := v.Args[0]
    y := v.Args[1]
    v.Op = OpAMD64SETEQ // 結果をSETEQ命令に設定
    v0 := v.Block.NewValue0(v.Line, OpAMD64CMPQ, TypeInvalid) // CMPQ命令を生成
    v0.Type = TypeFlags // フラグレジスタの型
    v0.AddArg(x) // xを引数に追加
    v0.AddArg(y) // yを引数に追加
    v.AddArg(v0) // CMPQの結果をSETEQの引数に追加
    return true
// OpNeqPtrも同様
```

*   `OpEqPtr` (ポインタ等価) オペレーションは、まず `CMPQ` (Compare Quadword) 命令を生成して2つのポインタ `x` と `y` を比較します。`CMPQ` はCPUのフラグレジスタを設定しますが、直接結果を返しません。
*   次に、`SETEQ` (Set if Equal) 命令が生成されます。これは、`CMPQ` によって設定されたフラグレジスタの状態をチェックし、等しい場合に結果レジスタに1（真）を、そうでない場合に0（偽）を設定します。
*   `OpNeqPtr` (ポインタ非等価) オペレーションも同様に `CMPQ` を使用しますが、結果は `SETNE` (Set if Not Equal) 命令によって設定されます。

これらのルールにより、Goの参照型の比較（特に `nil` との比較）が、最終的にAMD64プロセッサ上で非常に効率的な単一または少数のアセンブリ命令に変換されることが保証されます。これは、コンパイラの最適化とコード生成の重要な側面です。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現（IR）を複数段階で利用します。SSA (Static Single Assignment) 形式はその重要な中間表現の一つであり、最適化の主要な舞台となります。このコミットが作成された時期は、Goコンパイラが従来のAST (Abstract Syntax Tree) ベースのバックエンドから、より高度な最適化を可能にするSSAベースのバックエンドへと移行している最中でした（`dev.ssa`ブランチでの開発）。

従来のコンパイラでは、非数値型の比較、特に参照型（スライス、インターフェース、関数、マップ、チャネル）の比較は、特定のルールに基づいて処理されていました。しかし、SSAバックエンドに移行するにあたり、これらの比較操作をSSA形式で正確に表現し、その後の最適化やコード生成に引き継ぐためのメカニズムが必要でした。

このコミットの主な背景は以下の点にあります。

1.  **SSAバックエンドへの移行**: SSAバックエンドは、より強力な最適化を可能にするために、プログラムのデータフローを明示的に表現します。非数値型の比較もこの新しいフレームワークに適合させる必要がありました。
2.  **Go言語の比較セマンティクス**: Go言語では、スライス、インターフェース、関数、マップ、チャネルの比較には特定の制約があります。
    *   **スライス**: スライスは直接比較できません。唯一許されるのは `nil` との比較です。`nil` スライスは、基盤となる配列へのポインタが `nil` であり、長さと容量が0であることを意味します。
    *   **インターフェース**: インターフェースは、その動的な型と値が両方とも等しい場合にのみ等しいとされます。ただし、コンパイル時に `nil` との比較に限定される場合があります。
    *   **関数、マップ、チャネル**: これらは参照型であり、`nil` との比較、または同じ型の別の変数とのポインタ等価性（つまり、同じ基盤となるランタイムオブジェクトを参照しているか）のみが許されます。
3.  **最適化の機会**: これらの比較の特性をSSAバックエンドで正確にモデル化することで、不要な比較や冗長なコードを排除する最適化の機会が生まれます。例えば、`nil` との比較は、単なるポインタのゼロ値チェックに簡略化できます。

このコミットは、これらの非数値比較をSSA形式で表現するための新しいSSAオペレーション（`EqPtr`, `NeqPtr`, `EqFat`, `NeqFat`）を導入し、それらをGoのフロントエンドの比較演算子（`OEQ`, `ONE`）にマッピングし、さらにAMD64アーキテクチャ向けのコード生成ルールと汎用的な書き換えルールを定義することで、SSAバックエンドがこれらの比較を正しく処理できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラとGo言語の概念に関する知識が必要です。

### 1. Goコンパイラの構造とSSA

Goコンパイラ（`cmd/compile`）は、複数のフェーズを経てGoのソースコードを機械語に変換します。主要なフェーズは以下の通りです。

*   **フロントエンド (Parsing & Type Checking)**: ソースコードを解析し、ASTを構築し、型チェックを行います。この段階で、Go言語の比較規則が適用され、不正な比較はエラーとなります。
*   **ミドルエンド (IR Generation & Optimization)**: ASTをSSA (Static Single Assignment) 形式の中間表現に変換します。SSA形式は、各変数が一度だけ代入されることを保証し、データフロー解析と最適化を容易にします。このフェーズで、多くの言語非依存の最適化が行われます。
*   **バックエンド (Code Generation)**: SSA形式のIRを特定のアーキテクチャ（例: AMD64）の機械語に変換します。この段階で、アーキテクチャ固有の最適化やレジスタ割り当てが行われます。

このコミットは主にミドルエンド（SSA生成と最適化ルール）とバックエンド（AMD64のコード生成ルール）に影響を与えます。

### 2. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において非常に強力な中間表現です。その主要な特性は以下の通りです。

*   **単一代入**: 各変数はプログラム内で一度だけ値を割り当てられます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi Function)**: 複数の制御フローパスが合流する点で、同じ論理変数に異なる値が割り当てられる可能性がある場合、Φ関数が導入されます。Φ関数は、どのパスから来たかに応じて適切な値を選択します。

このコミットでは、比較演算をSSAオペレーションとして表現し、SSA形式のルールに基づいて最適化やコード生成を行うための基盤を構築しています。

### 3. Go言語の型の比較セマンティクス

Go言語では、型の種類によって比較の挙動が異なります。

*   **数値型 (int, floatなど)**: 通常の値の比較（等しい、より大きい、より小さいなど）が可能です。
*   **文字列**: 辞書順での比較が可能です。
*   **構造体**: すべてのフィールドが比較可能であり、かつすべてのフィールドが等しい場合にのみ等しいとされます。
*   **配列**: すべての要素が比較可能であり、かつすべての要素が等しい場合にのみ等しいとされます。
*   **ポインタ**: ポインタが指すアドレスが等しい場合にのみ等しいとされます。
*   **スライス**: スライスは直接比較できません（`==` や `!=` はコンパイルエラー）。唯一許されるのは `nil` との比較です。`nil` スライスは、基盤となる配列へのポインタが `nil` であり、長さと容量が0であることを意味します。
*   **インターフェース**: インターフェース値は、その動的な型と動的な値が両方とも等しい場合にのみ等しいとされます。`nil` との比較も可能です。`nil` インターフェースは、動的な型と値が両方とも `nil` である状態を指します。
*   **関数**: 関数は直接比較できません。唯一許されるのは `nil` との比較、または同じ関数オブジェクトを参照しているかどうかのポインタ等価性です。
*   **マップ**: マップは直接比較できません（`==` や `!=` はコンパイルエラー）。唯一許されるのは `nil` との比較です。
*   **チャネル**: チャネルは直接比較できません。唯一許されるのは `nil` との比較、または同じチャネルオブジェクトを参照しているかどうかのポインタ等価性です。

このコミットの目的は、これらのGo言語の比較セマンティクスをSSAバックエンドで正確に反映させることです。特に、スライスやインターフェースの `nil` 比較、および関数、マップ、チャネルのポインタ等価性比較に焦点を当てています。

### 4. `opToSSA` マッピング

`cmd/compile/internal/gc/ssa.go` にある `opToSSA` マップは、Goコンパイラのフロントエンドで使われるASTノードのオペレーションコード（例: `OEQ` for equality, `ONE` for inequality）と、Goの型（例: `TINT8` for 8-bit integer）の組み合わせを、SSAバックエンドで使われるSSAオペレーション（例: `ssa.OpEq8`）にマッピングするために使用されます。このマップを拡張することで、新しいSSAオペレーションが導入され、非数値型の比較がSSA形式で表現できるようになります。

### 5. SSAオペレーションと書き換えルール

SSAバックエンドでは、SSAオペレーション（例: `OpEq8`, `OpLoad`, `OpConst`）がプログラムの基本的な操作を表します。これらのオペレーションは、最終的にターゲットアーキテクチャの機械語命令に変換されます。この変換は、**書き換えルール (rewrite rules)** を通じて行われます。

*   **汎用書き換えルール (`rewritegeneric.go`)**: 特定のアーキテクチャに依存しない、一般的な最適化や変換ルールを定義します。例えば、`EqFat` オペレーションを `EqPtr` オペレーションに変換するようなルールが含まれます。
*   **アーキテクチャ固有の書き換えルール (`rewriteAMD64.go`)**: 特定のアーキテクチャ（例: AMD64）の命令セットを利用して、SSAオペレーションを効率的な機械語命令に変換するルールを定義します。例えば、`EqPtr` オペレーションを `CMPQ` (Compare Quadword) と `SETEQ` (Set if Equal) 命令の組み合わせに変換するルールが含まれます。

これらのルールは、SSA形式のプログラムをより低レベルの表現に段階的に変換し、最終的に機械語を生成するために不可欠です。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSAバックエンドにおける非数値型の比較処理の拡張にあります。

### 1. 新しいSSAオペレーションの導入

`src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/opGen.go` に、以下の新しいSSAオペレーションが導入されました。

*   `EqPtr`: ポインタの等価性比較（`==`）
*   `NeqPtr`: ポインタの非等価性比較（`!=`）
*   `EqFat`: スライスやインターフェースの等価性比較（主に `nil` との比較）
*   `NeqFat`: スライスやインターフェースの非等価性比較（主に `nil` との比較）

`EqFat` と `NeqFat` は「Fat Pointer」（スライスやインターフェースが内部的にポインタと長さ/型情報を持つ構造体であることに由来）の比較を意味し、特に `nil` との比較に特化しています。コミットメッセージにあるように、スライスやインターフェースのバックエンドに到達する比較は `nil` との比較のみであるため、この設計はGo言語のセマンティクスに合致しています。

### 2. `opToSSA` マッピングの拡張

`src/cmd/compile/internal/gc/ssa.go` の `opToSSA` マップが更新され、Goのフロントエンドの比較演算子（`OEQ`, `ONE`）と特定の型の組み合わせが、新しいSSAオペレーションにマッピングされるようになりました。

*   `OEQ, TINTER` -> `ssa.OpEqFat` (インターフェースの等価性比較)
*   `OEQ, TARRAY` -> `ssa.OpEqFat` (スライスの等価性比較)
*   `OEQ, TFUNC` -> `ssa.OpEqPtr` (関数の等価性比較)
*   `OEQ, TMAP` -> `ssa.OpEqPtr` (マップの等価性比較)
*   `OEQ, TCHAN` -> `ssa.OpEqPtr` (チャネルの等価性比較)
*   `OEQ, TUINTPTR` -> `ssa.OpEqPtr` (uintptrの等価性比較)

同様に、`ONE` (非等価性) 演算子についても `ssa.OpNeqFat` や `ssa.OpNeqPtr` へのマッピングが追加されています。

このマッピングにより、Goのソースコードで書かれたこれらの型の比較が、SSA形式の適切なオペレーションに変換され、SSAバックエンドで処理されるようになります。

### 3. AMD64アーキテクチャ固有の書き換えルール

`src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` に、`EqPtr` および `NeqPtr` オペレーションをAMD64アセンブリ命令に変換するためのルールが追加されました。

*   `(EqPtr x y) -> (SETEQ (CMPQ <TypeFlags> x y))`
*   `(NeqPtr x y) -> (SETNE (CMPQ <TypeFlags> x y))`

これは、2つのポインタ `x` と `y` を比較し（`CMPQ`）、その結果に基づいてフラグレジスタを設定し、等しい場合は `SETEQ` (Set if Equal)、等しくない場合は `SETNE` (Set if Not Equal) 命令で結果をブール値として設定することを意味します。`CMPQ` は64ビット値を比較するための命令であり、ポインタが通常64ビットであるAMD64アーキテクチャに適しています。

### 4. 汎用書き換えルール

`src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` に、`EqFat` および `NeqFat` オペレーションを処理するための汎用的な書き換えルールが追加されました。

*   `EqFat` および `NeqFat` の引数の順序を正規化するルール（定数が右側に来るように）
    *   `(EqFat x y) && x.Op == OpConst && y.Op != OpConst -> (EqFat y x)`
    *   `(NeqFat x y) && x.Op == OpConst && y.Op != OpConst -> (NeqFat y x)`
*   `EqFat` および `NeqFat` を `nil` との比較に変換するルール
    *   `(EqFat (Load ptr mem) y) && y.Op == OpConst -> (EqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))`
    *   `(NeqFat (Load ptr mem) y) && y.Op == OpConst -> (NeqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))`

これらのルールは、スライスやインターフェースが `nil` と比較される場合、その内部表現（通常は先頭のワード、つまり基盤となるデータへのポインタや動的な型情報）がゼロ値（`nil`）であるかどうかをチェックする `EqPtr` または `NeqPtr` オペレーションに変換されることを示しています。これにより、`EqFat` や `NeqFat` といった高レベルの概念が、より低レベルで効率的なポインタ比較に簡略化されます。

3.  **`src/cmd/compile/internal/ssa/opGen.go`**:
    *   `const` ブロックに `OpEqPtr`, `OpEqFat`, `OpNeqPtr`, `OpNeqFat` が追加され、SSAオペレーションの列挙型が拡張されました。
    *   `opcodeTable` にこれらの新しいオペレーションに対応する `opInfo` エントリが追加され、各オペレーションのメタデータ（名前、汎用性など）が定義されました。

4.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`**:
    *   AMD64アーキテクチャ向けの書き換えルールに、`EqPtr` と `NeqPtr` オペレーションを `CMPQ` (Compare Quadword) と `SETEQ` (Set if Equal) / `SETNE` (Set if Not Equal) アセンブリ命令に変換するルールが追加されました。

5.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`**:
    *   `rewriteValueAMD64` 関数内に、`OpEqPtr` と `OpNeqPtr` を処理するための具体的な書き換えロジックが追加されました。これは、`gen/AMD64.rules` で定義されたルールに対応するGoコードです。

6.  **`src/cmd/compile/internal/ssa/gen/generic.rules`**:
    *   汎用書き換えルールに、`EqFat` と `NeqFat` オペレーションを処理するためのルールが追加されました。これには、引数の正規化と、`nil` との比較を `EqPtr` / `NeqPtr` に変換するルールが含まれます。

7.  **`src/cmd/compile/internal/ssa/rewritegeneric.go`**:
    *   `rewriteValuegeneric` 関数内に、`OpEqFat` と `OpNeqFat` を処理するための具体的な書き換えロジックが追加されました。これは、`gen/generic.rules` で定義されたルールに対応するGoコードです。

これらの変更は、GoコンパイラのSSAバックエンドが、Go言語の非数値型の比較セマンティクスを正確に理解し、効率的な機械語に変換するための基盤を確立するものです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルでは、GoのASTノードの演算子と型をSSAオペレーションにマッピングする `opToSSA` マップが拡張されています。

```go
// 変更前
// opAndType{OEQ, TINT8}:   ssa.OpEq8,
// ...
// opAndType{OEQ, TPTR64}:  ssa.OpEq64,

// 変更後
opAndType{OEQ, TBOOL}:    ssa.OpEq8,
opAndType{OEQ, TINT8}:    ssa.OpEq8,
// ...
opAndType{OEQ, TPTR64}:   ssa.OpEq64,
opAndType{OEQ, TINTER}:   ssa.OpEqFat, // e == nil only
opAndType{OEQ, TARRAY}:   ssa.OpEqFat, // slice only; a == nil only
opAndType{OEQ, TFUNC}:    ssa.OpEqPtr,
opAndType{OEQ, TMAP}:     ssa.OpEqPtr,
opAndType{OEQ, TCHAN}:    ssa.OpEqPtr,
opAndType{OEQ, TUINTPTR}: ssa.OpEqPtr,
```

この変更は、Goのフロントエンドが `==` (OEQ) や `!=` (ONE) 演算子を検出した際に、そのオペランドの型に基づいて適切なSSAオペレーションを選択するように指示します。
*   `TINTER` (インターフェース) や `TARRAY` (スライス) の比較は `OpEqFat` にマッピングされます。これは、これらの型が内部的に複数のワード（ポインタと長さ/型情報など）で構成される「Fat Pointer」として扱われ、特に `nil` との比較に特化したオペレーションであることを示唆しています。
*   `TFUNC` (関数), `TMAP` (マップ), `TCHAN` (チャネル), `TUINTPTR` (uintptr) の比較は `OpEqPtr` にマッピングされます。これらの型は参照型であり、その等価性比較は基盤となるポインタの等価性で十分であるためです。

### `src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

これらのファイルでは、`EqFat` および `NeqFat` オペレーションを処理するための汎用的な書き換えルールが定義されています。

```go
// slice and interface comparisons
// the frontend ensures that we can only compare against nil
// start by putting nil on the right to simplify the other rules
(EqFat x y) && x.Op == OpConst && y.Op != OpConst -> (EqFat y x)
(NeqFat x y) && x.Op == OpConst && y.Op != OpConst -> (NeqFat y x)
// it suffices to check the first word (backing array for slices, dynamic type for interfaces)
(EqFat (Load ptr mem) y) && y.Op == OpConst -> (EqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))
(NeqFat (Load ptr mem) y) && y.Op == OpConst -> (NeqPtr (Load <config.Uintptr> ptr mem) (Const <config.Uintptr> [0]))
```

*   最初の2つのルールは、`EqFat` または `NeqFat` オペレーションの引数の順序を正規化します。もし左オペランドが定数 (`OpConst`) で、右オペランドが定数でない場合、オペランドを入れ替えて定数が常に右側に来るようにします。これは、後続のルールを簡素化するためによく行われる最適化です。
*   次の2つのルールは、`EqFat` または `NeqFat` オペレーションが `nil` との比較である場合に適用されます。
    *   `(Load ptr mem)` は、メモリから値をロードするSSAオペレーションを表します。ここでは、スライスやインターフェースの構造体の先頭ワード（ポインタ）をロードすることを意味します。
    *   `y.Op == OpConst` は、比較対象が定数、特に `nil` を表すゼロ定数であることを意味します。
    *   このルールは、`EqFat` (または `NeqFat`) オペレーションを、ロードされたポインタとゼロ定数 (`Const <config.Uintptr> [0]`) の `EqPtr` (または `NeqPtr`) 比較に変換します。
    *   これは、スライスやインターフェースが `nil` であるかどうかを判断するには、その内部ポインタが `nil` (ゼロ) であるかをチェックすれば十分であるというGo言語のセマンティクスを反映しています。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

これらのファイルでは、`EqPtr` および `NeqPtr` オペレーションをAMD64アセンブリ命令に変換するルールが定義されています。

```go
// AMD64.rules
(EqPtr x y) -> (SETEQ (CMPQ <TypeFlags> x y))
(NeqPtr x y) -> (SETNE (CMPQ <TypeFlags> x y))

// rewriteAMD64.go (簡略化された表現)
case OpEqPtr:
    x := v.Args[0]
    y := v.Args[1]
    v.Op = OpAMD64SETEQ // 結果をSETEQ命令に設定
    v0 := v.Block.NewValue0(v.Line, OpAMD64CMPQ, TypeInvalid) // CMPQ命令を生成
    v0.Type = TypeFlags // フラグレジスタの型
    v0.AddArg(x) // xを引数に追加
    v0.AddArg(y) // yを引数に追加
    v.AddArg(v0) // CMPQの結果をSETEQの引数に追加
    return true
// OpNeqPtrも同様
```

*   `OpEqPtr` (ポインタ等価) オペレーションは、まず `CMPQ` (Compare Quadword) 命令を生成して2つのポインタ `x` と `y` を比較します。`CMPQ` はCPUのフラグレジスタを設定しますが、直接結果を返しません。
*   次に、`SETEQ` (Set if Equal) 命令が生成されます。これは、`CMPQ` によって設定されたフラグレジスタの状態をチェックし、等しい場合に結果レジスタに1（真）を、そうでない場合に0（偽）を設定します。
*   `OpNeqPtr` (ポインタ非等価) オペレーションも同様に `CMPQ` を使用しますが、結果は `SETNE` (Set if Not Equal) 命令によって設定されます。

これらのルールにより、Goの参照型の比較（特に `nil` との比較）が、最終的にAMD64プロセッサ上で非常に効率的な単一または少数のアセンブリ命令に変換されることが保証されます。これは、コンパイラの最適化とコード生成の重要な側面です。

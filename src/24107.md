## 変更の背景

この変更の背景には、`runtime.NumCPU` 関数が返す値に対する誤解や曖昧さがありました。元々、この関数のドキュメントは「ローカルマシン上の論理CPUの数」を返すと記述されていましたが、これは必ずしも正確ではありませんでした。特に、コンテナ環境やCPUアフィニティが設定されたシステムなど、プロセスが利用できるCPUの数がシステム全体のCPU数よりも少ない場合に問題が生じました。

Goのランタイムは、`GOMAXPROCS` 環境変数や `runtime.GOMAXPROCS` 関数を通じて、同時に実行できるOSスレッドの最大数を制御します。この値は、Goスケジューラが利用可能なCPUリソースをどのように活用するかに影響を与えます。`runtime.NumCPU` は、この `GOMAXPROCS` のデフォルト値を決定する際にも参照される重要な情報源です。

Issue #11609（直接的な参照は見つかりませんでしたが、関連する議論から推測される内容）や、類似のIssue #15206のような議論では、`NumCPU` がシステム全体のCPU数ではなく、**現在のプロセスが実際に利用できるCPUの数**を正確に報告することの重要性が指摘されていました。例えば、FreeBSDのjail環境やLinuxのcgroupなど、OSレベルでプロセスに割り当てられるCPUリソースが制限されている場合、`NumCPU` がシステム全体のCPU数を返してしまうと、Goランタイムが過剰なリソースを要求しようとしたり、スケジューリングの最適化が適切に行われなかったりする可能性がありました。

このコミットは、このような混乱を解消し、開発者が `NumCPU` の戻り値のセマンティクスを正しく理解できるように、ドキュメントを明確化することを目的としています。これにより、Goアプリケーションがリソース制限のある環境でより適切に動作し、開発者が期待通りの動作を予測できるようになります。

## 前提知識の解説

### 1. 論理CPU (Logical CPU)
論理CPUとは、オペレーティングシステム（OS）が認識するCPUコアの単位です。物理的なCPUコアがハイパースレッディング（IntelのHyper-Threading Technologyなど）をサポートしている場合、1つの物理コアが複数の論理CPUとしてOSに認識されます。例えば、4コア8スレッドのCPUの場合、OSは8つの論理CPUを認識します。

### 2. `runtime.NumCPU()`
Go言語の `runtime` パッケージに含まれる関数で、Goプログラムが実行されている環境で利用可能な論理CPUの数を返します。この値は、Goランタイムのスケジューラが同時に実行できるOSスレッドの最大数（`GOMAXPROCS`）のデフォルト値を決定する際に使用されます。

### 3. `GOMAXPROCS`
Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数、または `runtime.GOMAXPROCS` 関数です。Goのスケジューラは、この値に基づいてGoルーチンをOSスレッドにマッピングし、並行実行を管理します。
*   `GOMAXPROCS` が設定されていない場合、デフォルトで `runtime.NumCPU()` の値が使用されます。
*   `GOMAXPROCS` を1に設定すると、Goプログラムは並行処理を行わず、単一のOSスレッドで実行されます（ただし、I/Oブロッキングコールなどは別のスレッドで行われることがあります）。
*   `GOMAXPROCS` を `runtime.NumCPU()` よりも大きな値に設定しても、通常はパフォーマンス上のメリットはありません。むしろ、OSのコンテキストスイッチのオーバーヘッドが増加し、パフォーマンスが低下する可能性があります。

### 4. CPUアフィニティ (CPU Affinity) とリソース制限
現代のOSや仮想化技術（コンテナなど）では、特定のプロセスやグループが利用できるCPUリソースを制限する機能があります。
*   **CPUアフィニティ**: プロセスが実行されるCPUコアを特定のサブセットに制限する機能です。これにより、プロセスのキャッシュ効率を向上させたり、他の重要なプロセスとの競合を避けたりすることができます。
*   **コンテナ環境 (Docker, Kubernetesなど)**: cgroup (control group) などのOS機能を利用して、コンテナに割り当てられるCPUリソース（CPUコア数、CPU時間など）を制限できます。この場合、コンテナ内のプロセスは、ホストマシン全体のCPU数よりも少ないCPUしか利用できません。

このコミットの変更は、`runtime.NumCPU` がこれらのCPUアフィニティやリソース制限を考慮した「実際に利用可能なCPU数」を返すことを明確にすることの重要性を示しています。

## 技術的詳細

このコミットは、`runtime.NumCPU` 関数の動作自体を変更するものではなく、そのドキュメンテーションを修正することで、関数のセマンティクスをより正確に反映させることを目的としています。

以前のドキュメントでは「ローカルマシン上の論理CPUの数」と記述されていましたが、これは以下のようなシナリオで誤解を招く可能性がありました。

1.  **コンテナ環境**: DockerやKubernetesなどのコンテナオーケストレーションシステムでは、コンテナに割り当てられるCPUリソースが制限されることがよくあります。例えば、8コアのホストマシン上で、2コアに制限されたコンテナが実行されている場合、コンテナ内のGoプログラムが `NumCPU` を呼び出すと、以前のドキュメントの解釈では8を期待するかもしれませんが、実際には2を返すことが期待されます。このコミットの変更は、この「2」という値が「現在のプロセスが使用可能な論理CPUの数」であることを明確にします。

2.  **CPUアフィニティマスク**: オペレーティングシステムによっては、`sched_setaffinity` (Linux) のようなシステムコールを使用して、プロセスが実行できるCPUのセットを制限できます。このような場合、プロセスはシステム全体のCPUの一部しか利用できません。`NumCPU` は、このアフィニティマスクによって制限されたCPUの数を反映すべきです。

3.  **仮想マシン (VM)**: 仮想マシン環境では、ゲストOSが認識するCPUの数は、ホストマシンの物理CPU数とは異なる場合があります。`NumCPU` は、ゲストOSが認識し、かつプロセスが利用可能なCPUの数を返す必要があります。

このドキュメントの明確化は、Goランタイムがこれらの環境でどのように動作するかについての開発者の理解を深め、`GOMAXPROCS` の設定や並行処理の設計において、より現実的な仮定を立てることを可能にします。`NumCPU` が「利用可能なCPU」を返すという明確な記述は、Goアプリケーションがリソース制限のある環境で、過剰なOSスレッドを生成しようとせず、割り当てられたリソース内で効率的に動作するための基盤となります。

## コアとなるコードの解説

変更されたのは、`NumCPU` 関数のドキュメンテーションコメントのみです。関数の実装 (`return int(ncpu)`) 自体は変更されていません。

*   **変更前**: `// NumCPU returns the number of logical CPUs on the local machine.`
    *   これは、`NumCPU` が物理マシンまたは仮想マシンが持つ全ての論理CPUの数を返すという印象を与えます。

*   **変更後**: `// NumCPU returns the number of logical CPUs usable by the current process.`
    *   この変更により、`NumCPU` が返す値が、**現在のプロセスが実際に利用できるCPUの数**であることを明確にしています。これは、OSレベルでのCPUアフィニティ設定や、コンテナなどのリソース制限が適用されている場合に特に重要です。

このコメントの変更は、Goランタイムの内部的な `ncpu` 変数が、既にこれらのリソース制限を考慮した値を保持していることを示唆しています。つまり、`ncpu` は単にシステム全体のCPU数を取得するのではなく、OSの提供するAPI（例: Linuxの `sysconf(_SC_NPROCESSORS_ONLN)` や `sched_getaffinity` の結果を考慮したもの）を通じて、プロセスに割り当てられたCPU数を正確に取得していると考えられます。

このドキュメントの明確化は、Goアプリケーションのポータビリティと予測可能性を高める上で非常に重要です。開発者は、`NumCPU` の値が、アプリケーションが実際に利用できる並行処理リソースの量を示すものとして信頼できるようになります。

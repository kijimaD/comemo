# [インデックス 26015] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/url` パッケージにおけるURLホスト名のパースと文字列化の挙動を修正するものです。特に、ホスト名に含まれるスペース文字の扱いと、`< > "` といった特殊文字のエスケープに関する一貫性の問題を解決しています。

    (Similarly, reject \t, \x01, and so on, all of which were being allowed.)

## 元コミット内容

`net/url` パッケージにおいて、ホスト名内のスペース文字を拒否し、`< > "` 文字をエスケープしないように変更します。

RFC 3986によれば、URLのホスト名ではASCIIバイトに対してパーセントエスケープを使用すべきではありません。

これまで `url.Parse` はURLホスト名にスペースや `< > "` を許容していましたが、Go 1.5で `URL.String` メソッドがこれらの文字をエスケープするようになりました。その結果、`Parse` でパース成功したURLを `String` で文字列化し、再度 `Parse` しようとすると失敗するという一貫性のない挙動が生じていました。

このコミットは、`Parse` と `String` の間で、許容されるホスト文字と文字のエンコーディングに関して一貫性を持たせることを目的としています。これにより、`Parse` が成功すれば、`Parse -> String -> Parse` も成功するようになります。

スペース文字の許容は誤りであると判断されたため、`Parse` でスペース（およびタブ、制御文字など）を拒否するように変更されます。

一方、`< > "` 文字の許容は問題ないと判断されたため、引き続きこれらを許容し、`String` メソッドでのエスケープをGo 1.4の挙動に戻すことで、エスケープしないように変更されます。

この変更は Issue #11302 を修正します。

## 変更の背景

この変更の背景には、Go言語の `net/url` パッケージにおけるURLのホスト名の処理に関する一貫性の欠如がありました。具体的には、以下の2つの問題が挙げられます。

1.  **`url.Parse` と `URL.String` の間の不整合**:
    *   Go 1.5より前では、`url.Parse` はURLのホスト名にスペースや `< > "` といった文字を許容していました。
    *   しかし、Go 1.5で `URL.String` メソッドがこれらの文字をRFC 3986に準拠してパーセントエスケープするようになりました。
    *   この変更により、`url.Parse` で正常にパースされたURLオブジェクトを `URL.String` で文字列に戻すと、エスケープされたホスト名が含まれる文字列が生成されます。
    *   このエスケープされたホスト名を含む文字列を再度 `url.Parse` でパースしようとすると、`url.Parse` はエスケープされたホスト名を不正と判断し、パースに失敗するという問題が発生しました。これは、URLのパースと文字列化のラウンドトリップが保証されないという、ライブラリの基本的な信頼性に関わる問題でした。

2.  **RFC 3986への準拠と実用性のバランス**:
    *   RFC 3986は、URLのホスト名におけるASCIIバイトのパーセントエスケープを推奨していません。これは、ホスト名がDNS解決などのメカニズムによって処理されるため、エスケープされた形式が意図しない挙動を引き起こす可能性があるためです。
    *   しかし、`url.Parse` は歴史的にスペースや一部の特殊文字を許容していました。これらの文字はDNSホスト名としては無効ですが、一部の非標準的なURLや内部的なURIスキームで使用される可能性がありました。
    *   このコミットは、RFC 3986の原則と、既存のコードベースやユーザーの期待とのバランスを取りながら、より堅牢で予測可能な挙動を実現しようとしています。特に、スペース文字は明らかに不正なホスト名の一部であると判断し、拒否する方針が取られました。一方で、`< > "` はエスケープせずに許容することで、Go 1.4以前の挙動に戻し、互換性を維持しつつ一貫性を高めています。

これらの問題に対処し、`net/url` パッケージの堅牢性と予測可能性を向上させることが、このコミットの主要な動機となっています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. URL (Uniform Resource Locator)

インターネット上のリソースの位置を示す識別子です。一般的なURLは以下のような構造を持っています。

`scheme://[user:password@]host[:port][/path][?query][#fragment]`

このコミットでは特に `host` 部分の扱いに焦点を当てています。

### 2. RFC 3986 (Uniform Resource Identifier (URI): Generic Syntax)

URI（URLはURIの一種）の一般的な構文を定義する標準仕様です。このRFCは、URIの各コンポーネント（スキーム、オーソリティ、パス、クエリ、フラグメントなど）の構文規則、および文字のエンコーディング（パーセントエンコーディング）について詳細に規定しています。

*   **ホスト名 (`host`)**: RFC 3986では、ホスト名はIPアドレス（IPv4またはIPv6）または登録名（ドメイン名）のいずれかとして定義されます。登録名の場合、通常はDNSによって解決可能な形式である必要があります。
*   **パーセントエンコーディング**: URI内で特定の意味を持つ文字（予約文字）や、URIの構文で許可されていない文字（非予約文字の一部、または非ASCII文字）を表現するために使用されます。`%` の後に2桁の16進数を続ける形式（例: スペースは `%20`）。
*   **ホスト名におけるパーセントエンコーディングの扱い**: RFC 3986は、ホスト名においてASCIIバイトをパーセントエスケープすることを推奨していません。これは、ホスト名がDNSシステムによって解釈されることが多く、DNSはパーセントエスケープされた形式を認識しないためです。ただし、`reg-name` (登録名) の構文自体はパーセントエンコードされたオクテットを許容しています。このコミットのポイントは、Goの `net/url` が「ホスト名ではASCIIバイトに対してパーセントエスケープを使用すべきではない」というRFCの意図をより厳密に解釈し、実装に反映させようとしている点です。

### 3. Go言語 `net/url` パッケージ

Go言語でURLをパース、構築、操作するための標準ライブラリです。

*   **`url.Parse(rawurl string) (*URL, error)`**: 与えられた文字列をURL構造体にパースします。
*   **`URL.String() string`**: URL構造体を文字列形式に変換します。
*   **`URL.Host` フィールド**: パースされたURLのホスト名とポート番号（存在する場合）を含む文字列です。例: `example.com:8080`。
*   **`shouldEscape` 関数**: 特定の文字がURLの特定のコンポーネントでエスケープされるべきかどうかを判断する内部関数です。このコミットでは、ホスト名 (`encodeHost`) におけるこの関数の挙動が変更されています。

### 4. ラウンドトリップの一貫性 (Parse -> String -> Parse)

理想的なURLパーサー/シリアライザーは、以下の特性を持つべきです。

1.  `Parse(S) -> U` (文字列SをURLオブジェクトUにパース)
2.  `U.String() -> S'` (URLオブジェクトUを文字列S'に変換)
3.  `Parse(S') -> U'` (文字列S'をURLオブジェクトU'にパース)

このとき、`U` と `U'` が論理的に等価であること、そして可能であれば `S` と `S'` が等価であることが望ましいです。このコミットが修正しようとしているのは、Go 1.5で `Parse(S) -> U -> U.String() -> S'` とした際に、`Parse(S')` が失敗するという、このラウンドトリップの一貫性が破られていた問題です。

## 技術的詳細

このコミットは、`net/url` パッケージ内の `url.go` ファイルと、関連するテストファイル (`request_test.go`, `url_test.go`) に変更を加えています。

### 1. ホスト名におけるスペース文字の拒否

*   **`InvalidHostError` 型の導入**: ホスト名に不正な文字が含まれる場合に返される新しいエラー型 `InvalidHostError` が追加されました。これにより、ホスト名に関する特定のエラーをより明確に識別できるようになります。
    ```go
    type InvalidHostError string

    func (e InvalidHostError) Error() string {
        return "invalid character " + strconv.Quote(string(e)) + " in host name"
    }
    ```
*   **`unescape` 関数でのチェック強化**: `unescape` 関数は、URLの各コンポーネントをデコードする際に使用されます。ホスト名 (`encodeHost` または `encodeZone`) のデコードモードの場合、ASCIIバイトでありながら `shouldEscape` が `true` を返す文字（つまり、エスケープされるべきだがエスケープされていない文字）が見つかった場合、`InvalidHostError` を返すように変更されました。これにより、スペース文字（`0x20`）のような文字がホスト名に直接含まれている場合に、パース時にエラーとして検出されるようになります。
    ```go
    // src/net/url/url.go の unescape 関数内
    // ...
    default:
        if (mode == encodeHost || mode == encodeZone) && s[i] < 0x80 && shouldEscape(s[i], mode) {
            return "", InvalidHostError(s[i : i+1])
        }
        i++
    // ...
    ```
    この変更により、`url.Parse` はホスト名にスペースなどの不正なASCII文字が含まれるURLを拒否するようになります。

### 2. `< > "` 文字のエスケープ挙動の変更

*   **`shouldEscape` 関数の修正**: `shouldEscape` 関数は、URLの各部分でどの文字をエスケープすべきかを決定します。ホスト名 (`encodeHost` または `encodeZone`) のモードにおいて、`< > "` の3つの文字がエスケープ不要な文字のリストに追加されました。
    ```go
    // src/net/url/url.go の shouldEscape 関数内
    // ...
    // We add < > because they're the only characters left that
    // we could possibly allow, and Parse will reject them if we
    // escape them (because hosts can't use %-encoding for
    // ASCII bytes).
    switch c {
    case '!', '$', '&', '\'', '(', ')', '*', '+', ',', ';', '=', ':', '[', ']', '<', '>', '"': // 変更点
        return false
    }
    // ...
    ```
    この変更のコメントにあるように、`< > "` は許容可能な文字であり、もしこれらをエスケープしてしまうと、`Parse` がパーセントエンコードされたホスト名を拒否するため、ラウンドトリップが失敗するという問題がありました。この修正により、`URL.String` メソッドはこれらの文字をエスケープしなくなり、Go 1.4の挙動に戻ります。

### 3. テストケースの追加と修正

*   **`src/net/http/request_test.go` の修正**: `TestRequestBadHost` テストケースが修正され、`NewRequest` に直接不正なホスト名を含むURLを渡すのではなく、有効なURLでリクエストを作成した後、`req.Host` と `req.URL.Host` を不正な値 (`"foo.com with spaces"`) に設定してテストするように変更されました。これは、`NewRequest` が内部で `url.Parse` を呼び出すため、新しいパースルールによって直接不正なURLを渡すとエラーになるためです。
*   **`src/net/url/url_test.go` の追加**:
    *   `urltests` 変数に、`< > "` を含むホスト名を持つURLの新しいテストケースが追加されました。これは、これらの文字がエスケープされずに正しくパース・文字列化されることを確認するためです。
        ```go
        // test that we can reparse the host names we accept.
        {
            "myscheme://authority<\"hi\">/foo",
            &URL{
                Scheme: "myscheme",
                Host:   "authority<\"hi\">",
                Path:   "/foo",
            },
            "",
        },
        ```
    *   `TestParseAuthority` 関数に、ホスト名にスペースを含むURL (`"http://a b.com/"`) がパース時にエラーを返すことを確認するテストケースが追加されました。
        ```go
        {"http://a b.com/", true}, // no space in host name please
        ```

これらの変更により、`net/url` パッケージはRFC 3986の意図により厳密に準拠しつつ、`Parse` と `String` メソッド間の一貫性を確保し、URLのホスト名処理における予測可能性と堅牢性を向上させています。

## コアとなるコードの解説

### `src/net/url/url.go` の変更点

1.  **`InvalidHostError` 型の追加**:
    *   これは、ホスト名に不正な文字が含まれている場合に `url.Parse` が返す新しいエラー型です。これにより、呼び出し元はホスト名に関する特定のエラーを捕捉し、適切に処理できるようになります。以前は、より一般的なエラーが返されていた可能性があります。

2.  **`shouldEscape` 関数の変更**:
    *   `shouldEscape` 関数は、URLの各コンポーネント（パス、クエリ、ホストなど）において、特定の文字をパーセントエスケープする必要があるかどうかを判断します。
    *   `encodeHost` または `encodeZone` モード（ホスト名またはゾーン識別子をエンコードする場合）において、`!`、`$`、`&`、`'`、`(`、`)`、`*`、`+`、`,`、`;`、`=`、`:`、`[`、`]` に加えて、新たに `<`、`>`、`"` の3文字が `return false` のケースに追加されました。
    *   これは、これらの文字がホスト名に直接含まれていてもエスケープすべきではない、というGo 1.4以前の挙動に戻すことを意味します。コミットメッセージのコメントにあるように、もしこれらの文字をエスケープしてしまうと、`url.Parse` がパーセントエンコードされたホスト名を不正と判断し、`Parse -> String -> Parse` のラウンドトリップが失敗するためです。RFC 3986はASCIIバイトのホスト名でのパーセントエスケープを推奨していないため、エスケープしないことでこの問題を回避しています。

3.  **`unescape` 関数の変更**:
    *   `unescape` 関数は、パーセントエンコードされた文字列をデコードする際に使用されます。
    *   この変更では、`unescape` が `encodeHost` または `encodeZone` モードで動作している場合、現在の文字 `s[i]` がASCII文字（`s[i] < 0x80`）であり、かつ `shouldEscape(s[i], mode)` が `true` を返す（つまり、エスケープされるべき文字なのにエスケープされていない）場合に、`InvalidHostError` を返すように修正されました。
    *   これにより、ホスト名にスペース（ASCII `0x20`）のような、エスケープされるべきだがエスケープされていない不正なASCII文字が直接含まれている場合、`url.Parse` はそのURLを不正と判断し、パース時にエラーを返すようになります。これは、ホスト名にスペースを許容していた以前の挙動を修正し、RFC 3986の意図により厳密に準拠させるための変更です。

### `src/net/http/request_test.go` の変更点

*   `TestRequestBadHost` テスト関数が修正されました。以前は `NewRequest` に直接 `http://foo.com with spaces/after` のような不正なホスト名を含むURLを渡していましたが、新しい `url.Parse` の挙動ではこれがパース時にエラーとなるため、テストの意図が変わってしまいます。
*   修正後は、まず有効なURL (`http://foo/after`) でリクエストを作成し、その後 `req.Host` と `req.URL.Host` フィールドを明示的に不正な値 (`"foo.com with spaces"`) に設定しています。これにより、`http.Request` の `Write` メソッドが不正なホスト名をどのように処理するかをテストする、という元の意図が維持されます。このテストは、`net/http` パッケージが `net/url` の変更にどのように対応するかを示すものです。

### `src/net/url/url_test.go` の変更点

*   **`urltests` への追加**:
    *   `myscheme://authority<\"hi\">/foo` というURLが追加されました。このテストケースは、ホスト名に `< > "` 文字が含まれていても、`url.Parse` が正しくパースし、`URL.String` がそれらをエスケープせずに文字列化できることを検証します。これは `shouldEscape` 関数の変更に対応するものです。
*   **`TestParseAuthority` への追加**:
    *   `http://a b.com/` というURLが追加され、このURLが `url.Parse` によってエラー (`true`) を返すことを期待するテストケースが追加されました。これは、ホスト名にスペースが含まれるURLが拒否されるようになった `unescape` 関数の変更を検証するものです。

これらの変更は、`net/url` パッケージの堅牢性を高め、URLのパースと文字列化の挙動を一貫させることで、開発者がより予測可能で信頼性の高い方法でURLを扱えるようにすることを目的としています。

# [インデックス 24742] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net`パッケージにおける`LookupPort`関数の挙動を修正するものです。具体的には、ポート番号が整数文字列として与えられた場合に、正しくポートを解決できるように機能を回復させます。この機能はGo 1.4では動作していましたが、Go 1.5で導入された「pure Go」によるネットワークルックアップルーチンへの移行の過程で失われていました。

## 元コミット内容

このコミットの元の内容は、`net`パッケージの`LookupPort`関数が、サービス名として与えられた整数文字列（例: "80"）をポート番号として正しく解決できない問題を修正することです。Go 1.4ではこの機能は期待通りに動作していましたが、Go 1.5でネットワークルックアップの内部実装が「pure Go」に置き換えられた際に、この挙動が失われました。このコミットは、失われた機能を回復させ、関連するテストケースを追加しています。

## 変更の背景

Go 1.5は、Go言語の歴史において非常に重要なリリースであり、コンパイラとランタイムがC言語からGo言語自身で書き直されるという大きな変更がありました。これに伴い、`net`パッケージにおけるDNS解決などのネットワークルックアップルーチンも、Cgo（GoからC言語のコードを呼び出すためのメカニズム）に依存しない「pure Go」実装へと移行されました。

この「pure Go」への移行は、クロスコンパイルの容易さや、Cgoのオーバーヘッドを削減し、より効率的なリソース利用（特にDNS解決をOSのスレッドではなくGoのgoroutineで処理できるようになった点）といった多くのメリットをもたらしました。しかし、この大規模な変更の過程で、一部の既存の挙動が意図せず失われることがありました。

本コミットが修正する問題もその一つです。Go 1.4までの`LookupPort`関数は、サービス名として「http」のような文字列だけでなく、「80」のようなポート番号の文字列も受け入れ、それを整数値のポート番号として正しく解釈していました。しかし、Go 1.5の新しい「pure Go」ルックアップルーチンでは、サービス名解決のロジックが変更され、整数文字列を直接ポート番号として解釈する機能が失われていました。これにより、`LookupPort("tcp", "80")`のような呼び出しが期待通りに動作しないというバグ（Issue #12263）が発生しました。このコミットは、この後退バグを修正し、Go 1.4の挙動を回復させることを目的としています。

## 前提知識の解説

*   **Go言語の`net`パッケージ**: Go言語の標準ライブラリの一部で、ネットワークI/O機能を提供します。TCP/IP、UDP、Unixドメインソケットなどのネットワークプロトコルを扱うためのAPIが含まれています。DNSルックアップやポート解決などもこのパッケージの機能です。
*   **`net.LookupPort`関数**: この関数は、指定されたネットワークタイプ（例: "tcp", "udp"）とサービス名（例: "http", "ftp"）またはポート番号の文字列を受け取り、対応する整数値のポート番号を返します。通常、`/etc/services`のようなシステム設定ファイルやDNS SRVレコードなどを参照してサービス名をポート番号に解決します。
*   **Go 1.5の「pure Go」ネットワークルックアップ**: Go 1.5以前は、Goのネットワーク機能の一部はCgoを介してOSのCライブラリ（例: `glibc`）に依存していました。特にDNS解決はその典型でした。Go 1.5では、このCgo依存を減らし、Go言語のみでネットワークルックアップを行う「pure Go」実装が導入されました。これにより、Goプログラムのビルドとデプロイがよりシンプルになり、特定の環境でのパフォーマンス特性も改善されましたが、既存の挙動との互換性問題が発生することもありました。
*   **`dtoi`関数**: Goの内部で使われるユーティリティ関数で、「decimal to integer」（10進数から整数へ）の略です。文字列を整数に変換する役割を持ちます。`net`パッケージ内では、ポート番号の文字列を数値に変換する際に利用されます。この関数は、文字列の先頭から可能な限り多くの数字をパースし、その結果とパースした文字数を返します。

## 技術的詳細

このコミットが修正する問題は、`net.LookupPort`関数が、サービス名として与えられた整数文字列（例: "42"）をポート番号として認識できなくなったことにあります。Go 1.5で導入された新しい「pure Go」ルックアップルーチンは、主にサービス名（例: "http"）を`/etc/services`のようなデータベースから解決することに焦点を当てており、文字列が直接ポート番号を表すケースを適切に処理していませんでした。

修正の核心は、`LookupPort`関数の冒頭に、入力された`service`文字列が純粋な整数文字列であるかどうかをチェックするロジックを追加することです。

1.  **`dtoi`による数値文字列のチェック**: `LookupPort`関数が呼び出されると、まず`dtoi(service, 0)`が実行されます。
    *   `dtoi`は`service`文字列を10進数としてパースを試みます。
    *   `n`はパースされた整数値、`i`はパースに成功した文字数、`ok`はパースが成功したかどうかを示すブール値です。
2.  **完全な数値文字列の判定**: `ok && i == len(service)`という条件で、`service`文字列全体が数値としてパースされたかどうかを判定します。
    *   `ok`が`true`であることは、`service`の先頭が数字であり、少なくとも一部が数値として解釈できたことを意味します。
    *   `i == len(service)`は、`service`文字列のすべての文字が数値としてパースされたことを保証します。例えば、「42」は`i`が2で`len(service)`も2なのでこの条件を満たしますが、「42abc」は`i`が2で`len(service)`が5なので満たしません。
3.  **直接ポート番号を返す**: もし上記の条件が真であれば、`service`は純粋なポート番号の文字列であると判断され、`dtoi`によって得られた整数値`n`がそのままポート番号として返されます。この場合、サービス名解決のための`lookupPort`関数は呼び出されません。
4.  **既存のサービス名解決ロジックへのフォールバック**: `service`が純粋な整数文字列でない場合（例: "http"や"42abc"）、この新しいチェックはスキップされ、従来の`lookupPort(network, service)`が呼び出され、サービス名データベースなどを用いた解決が試みられます。

この変更により、`LookupPort`はGo 1.4と同様に、整数文字列を直接ポート番号として扱えるようになり、Go 1.5で発生した後退バグが解消されました。

## コアとなるコードの解説

### `src/net/lookup.go`の変更

`LookupPort`関数の実装に、以下の3行が追加されました。

```go
	if n, i, ok := dtoi(service, 0); ok && i == len(service) {
		return n, nil
	}
```

*   `n, i, ok := dtoi(service, 0)`: ここで`dtoi`関数が呼び出され、`service`文字列を整数としてパースしようとします。
    *   `n`: パースされた整数値。
    *   `i`: `service`文字列の先頭から何文字が整数としてパースされたかを示す数。
    *   `ok`: パースが成功したかどうかを示すブール値。
*   `ok && i == len(service)`: この条件式が、`service`文字列全体が有効な整数としてパースされたかどうかを判断します。
    *   `ok`が`true`であることは、少なくとも`service`の先頭が数字であることを意味します。
    *   `i == len(service)`は、`service`文字列のすべての文字が数字であり、完全に整数として解釈されたことを確認します。これにより、「42」のような文字列はポート番号として認識されますが、「http」や「42abc」のような文字列は認識されません。
*   `return n, nil`: もし条件が真であれば、パースされた整数値`n`がポート番号として返され、エラーは`nil`（なし）となります。これにより、`service`が整数文字列である場合は、それ以降のサービス名解決ロジック（`lookupPort`の呼び出し）はスキップされます。

この変更により、`LookupPort`はまず入力が直接ポート番号であるかをチェックし、そうであれば即座にその値を返すという、より堅牢で期待される挙動を取り戻しました。

### `src/net/port_test.go`の変更

`portTests`というテストデータ構造体に、以下の2つのテストケースが追加されました。

```diff
+	{"tcp", "42", 42, true},
...
+	{"udp", "42", 42, true},
```

これらのテストケースは、ネットワークタイプが"tcp"と"udp"の場合に、サービス名として整数文字列"42"が与えられたときに、期待されるポート番号が42であり、エラーが発生しない（`true`）ことを検証します。これにより、`LookupPort`関数が整数文字列を正しく処理できるようになったことが保証されます。

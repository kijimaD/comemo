## 元コミット内容

`cmd/internal/gc, cmd/internal/ld: fixes for global vars of types from other modules`

他の共有ライブラリで定義された型を含むグローバルデータの`gcprog`を作成するためには、それらの型について多くの情報を知る必要があります。そのため、"type."で始まる名前を持つシンボルの値を読み取ります。もし型がマスクを使用している場合、マスクを定義するシンボルの名前は残念ながら型名から予測できないため、そのようなシンボルのアドレスをすべて追跡し、後で型シンボルと関連付ける必要があります。

この変更にはあまり満足していませんが、このようなものが必要であり、これが私が知る限り最も良い方法です。

## 変更の背景

Go言語は、バージョン1.8以降でプラグイン（共有ライブラリ）のサポートを本格的に導入しました。このコミットは、その初期段階、Go 1.5の開発サイクル中に行われたもので、共有ライブラリ間の連携におけるガベージコレクションの課題に対処しています。

Goのガベージコレクタは、ヒープ上のポインタを正確に識別し、到達可能なオブジェクトをマークすることで動作します。このためには、各データ構造（型）のどこにポインタが含まれているかという情報が必要です。この情報は`gcprog`（ガベージコレクションプログラム）や`gcmask`（ガベージコレクションマスク）としてコンパイル時に生成され、実行時にGCによって利用されます。

問題は、あるモジュール（実行可能ファイルまたは共有ライブラリ）が、別の共有ライブラリで定義された型を持つグローバル変数を持つ場合でした。このグローバル変数をGCが正しくスキャンするためには、その変数の型が持つポインタ情報（`gcprog`や`gcmask`）が必要になります。しかし、これらの型情報が別の共有ライブラリに存在する場合、リンカはそれらの情報をどのように取得し、現在のモジュールのGC情報と統合するかが課題でした。

特に、`gcmask`を定義するシンボルの名前が型名から直接予測できないという点が複雑さを増していました。これは、`gcmask`が特定のメモリアドレスに配置される可能性があり、そのアドレスがシンボル名に直接反映されないためです。このため、リンカは共有ライブラリからすべての関連シンボルを読み込み、`gcmask`のアドレスを追跡し、後から対応する型シンボルと関連付けるという、より複雑なアプローチを取る必要がありました。

このコミットは、Goの共有ライブラリ機能が成熟する過程で、異なるモジュール間で型情報、特にGC関連のメタデータを正しく共有・解決するための基盤を築く重要なステップでした。

## 前提知識の解説

### Go言語のガベージコレクション (GC)
GoのGCは、並行マーク＆スイープ方式を採用しています。GCが正しく動作するためには、ヒープ上のオブジェクトのどこにポインタが含まれているかを正確に知る必要があります。この情報はコンパイル時に生成され、実行時にGCがオブジェクトをスキャンする際に利用されます。

### `gcprog` と `gcmask`
*   **`gcprog` (Garbage Collection Program):** 複雑なデータ構造（例: 構造体、配列）内のポインタの位置を記述するバイトコードのようなものです。GCは`gcprog`を実行して、オブジェクト内のどのオフセットにポインタがあるかを動的に判断します。
*   **`gcmask` (Garbage Collection Mask):** 比較的単純なデータ構造（例: 固定サイズの配列）の場合、ポインタの位置をビットマスクで表現することがあります。各ビットが特定のオフセットにポインタが存在するかどうかを示します。

### Goの共有ライブラリ (Plugins)
Go 1.8から導入されたプラグイン機能は、Goプログラムが実行時に動的にロードできる共有ライブラリ（`.so`ファイルなど）を作成することを可能にします。これにより、アプリケーションのモジュール性を高めたり、実行時に機能を拡張したりできます。共有ライブラリは、それぞれが独立したGoランタイム環境を持つため、型情報やGC情報の共有には特別な考慮が必要です。

### Goリンカ (`cmd/internal/ld`)
Goのリンカは、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルや共有ライブラリを生成するツールです。リンカは、シンボル解決、再配置、GC情報の埋め込みなど、多くの重要なタスクを担当します。

### `LSym` (Linker Symbol)
Goリンカ内部でシンボルを表す構造体です。プログラム内の関数、変数、型などの各エンティティは`LSym`として表現され、その名前、アドレス、サイズ、型情報（例: `obj.SDYNIMPORT`）などが含まれます。

### `obj.SDYNIMPORT`
`LSym`の`Type`フィールドで使われる定数の一つで、そのシンボルが動的にインポートされたものであることを示します。つまり、そのシンボルが現在のモジュールではなく、外部の共有ライブラリで定義されていることを意味します。

### ELFシンボル
ELF (Executable and Linkable Format) は、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイル内のシンボルは、`st_info`フィールドによってその種類（`ST_TYPE`）と結合属性（`ST_BIND`）が定義されます。
*   `elf.ST_TYPE(s.Info)`: シンボルの種類を抽出します。
    *   `elf.STT_NOTYPE`: 型が指定されていないシンボル。
    *   `elf.STT_SECTION`: セクションに関連付けられたシンボル。
*   `elf.ST_BIND(s.Info)`: シンボルの結合属性を抽出します。
    *   `elf.STB_GLOBAL`: グローバルシンボル。異なるオブジェクトファイルから参照可能です。

## 技術的詳細

このコミットの主要な目的は、Goのリンカが、他の共有ライブラリで定義された型を持つグローバル変数のGC情報を正しく処理できるようにすることです。具体的には、以下の課題を解決しています。

1.  **`gcprog`の解決:** 外部モジュールの型に対する`gcprog`は、`"type..gcprog.$name"`という予測可能な名前で参照できるため、`decodesym.go`で`obj.SDYNIMPORT`の場合にこの名前をルックアップするように変更されました。
2.  **`gcmask`の解決の複雑性:** `gcmask`は`gcprog`とは異なり、そのシンボル名が型名から直接予測できません。`gcmask`は`runtime.gcbits.0x...`のようなアドレスベースの名前を持つことがあり、そのアドレスはリンカが共有ライブラリを読み込むまで不明です。このため、リンカは以下の手順で`gcmask`を解決します。
    *   **`runtime.gcbits.*`シンボルの収集:** `ldshlibsyms`関数（`lib.go`内）が、共有ライブラリからすべてのシンボルを読み込む際に、`runtime.gcbits.0x`で始まる名前のシンボル（これらが`gcmask`データそのもの）を特定し、そのアドレスと実際のバイトデータを`gcmasks`マップに保存します。これらのシンボルは通常、ローカルシンボルとして扱われます。
    *   **`type.`シンボルの収集とデータ読み込み:** 同様に、`type.`で始まる名前のシンボル（これらが型定義）も収集し、そのシンボルのデータ（型情報自体）を読み込み、`LSym.P`に格納します。これらの型シンボルは`types`スライスに一時的に保持されます。
    *   **`gcmask`と型シンボルの関連付け:** すべてのシンボルを読み込んだ後、`types`スライス内の各型シンボルをイテレートします。各型シンボルのデータ（`LSym.P`）から、その型が参照する`gcmask`のアドレスを抽出します。このアドレスは、`decodetype_gcmask`関数が`LSym.P`から`gcmask`シンボルへのオフセットを計算するのと同様の方法で取得されます。
    *   **`gcmask`データの割り当て:** 抽出したアドレスをキーとして`gcmasks`マップを検索し、対応する`gcmask`のバイトデータを取得します。このバイトデータを型シンボルの新しいフィールド`LSym.gcmask`に割り当てます。これにより、型シンボルが自身の`gcmask`データに直接アクセスできるようになります。

このアプローチは、`gcmask`シンボルの名前が予測できないという制約の中で、リンカが動的に`gcmask`データを解決し、型情報と関連付けるための実用的な解決策を提供します。コミットメッセージにある「I'm not very happy about this change, but something like this is needed and this is as pleasant as I know how to make it.」というコメントは、この解決策が理想的ではないものの、当時のGoのリンカの制約下で最善であったことを示唆しています。

## コアとなるコードの解説

### `src/cmd/internal/ld/decodesym.go`
```go
// Type.commonType.gc
func decodetype_gcprog(s *LSym) *LSym {
	if s.Type == obj.SDYNIMPORT {
		// The gcprog for "type.$name" is calle "type..gcprog.$name".
		x := "type..gcprog." + s.Name[5:]
		return Linklookup(Ctxt, x, 0)
	}
	return decode_reloc_sym(s, 1*int32(Thearch.Ptrsize)+8+2*int32(Thearch.Ptrsize))
}

func decodetype_gcmask(s *LSym) []byte {
	if s.Type == obj.SDYNIMPORT {
		// ldshlibsyms makes special efforts to read the value
		// of gcmask for types defined in that shared library.
		return s.gcmask
	}
	mask := decode_reloc_sym(s, 1*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize))
	return mask.P
}
```
*   `decodetype_gcprog`: `obj.SDYNIMPORT`（動的インポートされたシンボル）の場合、GCプログラムのシンボル名を`"type..gcprog."`プレフィックスと元の型名から構築し、それをルックアップします。これにより、外部ライブラリの型に対するGCプログラムを解決できるようになります。
*   `decodetype_gcmask`: `obj.SDYNIMPORT`の場合、`LSym`構造体に新しく追加された`gcmask`フィールドの値を直接返します。これは、`ldshlibsyms`関数がこのフィールドに適切な`gcmask`データを事前に設定していることを前提としています。

### `src/cmd/internal/ld/lib.go`
```go
func ldshlibsyms(shlib string) {
	// ... (既存のコード) ...

	syms, err := f.Symbols() // DynamicSymbols() から Symbols() に変更
	// ... (エラーハンドリング) ...

	gcmasks := make(map[uint64][]byte) // gcmaskデータをアドレスで管理するマップ
	types := []*LSym{}                 // 処理対象の型シンボルを一時的に保持するスライス

	for _, s := range syms {
		// ... (シンボルフィルタリング) ...

		if strings.HasPrefix(s.Name, "runtime.gcbits.0x") {
			// runtime.gcbits.0x... で始まるシンボルはgcmaskデータそのもの
			data := make([]byte, s.Size)
			sect := f.Sections[s.Section]
			if sect.Type == elf.SHT_PROGBITS {
				// シンボルのデータを読み込み、gcmasksマップにアドレスをキーとして格納
				n, err := sect.ReadAt(data, int64(s.Value-sect.Offset))
				// ... (エラーハンドリング) ...
			}
			gcmasks[s.Value] = data
		}
		if elf.ST_BIND(s.Info) != elf.STB_GLOBAL {
			continue
		}

		lsym := Linklookup(Ctxt, s.Name, 0)
		// ... (既存のコード) ...
		lsym.Type = obj.SDYNIMPORT
		lsym.File = libpath

		if strings.HasPrefix(lsym.Name, "type.") {
			// type. で始まるシンボルは型定義
			data := make([]byte, s.Size)
			sect := f.Sections[s.Section]
			if sect.Type == elf.SHT_PROGBITS {
				// 型シンボルのデータを読み込み、LSym.Pに格納
				n, err := sect.ReadAt(data, int64(s.Value-sect.Offset))
				// ... (エラーハンドリング) ...
				lsym.P = data
			}
			if !strings.HasPrefix(lsym.Name, "type..") { // type.. で始まるものはGCプログラムなので除外
				types = append(types, lsym) // 処理対象の型シンボルとして追加
			}
		}
	}

	// すべてのシンボルを読み込んだ後、型シンボルとgcmaskを関連付ける
	for _, t := range types {
		if decodetype_noptr(t) != 0 || decodetype_usegcprog(t) != 0 {
			continue // ポインタを含まない型やgcprogを使用する型はスキップ
		}
		// 型データからgcmaskのアドレスを抽出
		addr := decode_inuxi(t.P[1*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize):], Thearch.Ptrsize)
		tgcmask, ok := gcmasks[addr] // 抽出したアドレスでgcmasksマップを検索
		if !ok {
			Diag("bits not found for %s at %d", t.Name, addr)
		}
		t.gcmask = tgcmask // 取得したgcmaskデータを型シンボルに割り当て
	}

	// ... (既存のコード) ...
}
```
*   この関数は、共有ライブラリからシンボルを読み込み、それらを現在のリンクコンテキストに統合する役割を担います。
*   `f.DynamicSymbols()`から`f.Symbols()`への変更は、動的シンボルだけでなく、すべてのシンボル（特にローカルな`runtime.gcbits.*`シンボル）を読み込む必要があるためです。
*   `gcmasks`マップと`types`スライスは、`gcmask`データと型シンボルを一時的に保持し、後でそれらを関連付けるための重要なデータ構造です。
*   `runtime.gcbits.0x`シンボルのデータ読み込みと`gcmasks`への格納、および`type.`シンボルのデータ読み込みと`types`への格納は、`gcmask`と型情報を収集するための準備ステップです。
*   ループの最後にある`for _, t := range types`ブロックが、このコミットの核心部分です。ここでは、各型シンボルの生データ（`t.P`）から`gcmask`のアドレスを計算し、そのアドレスを使って`gcmasks`マップから対応する`gcmask`データを取得し、型シンボル（`t`）の`gcmask`フィールドに設定しています。このプロセスにより、外部共有ライブラリで定義された型であっても、その`gcmask`情報が現在のリンカコンテキストで利用可能になります。

このコミットは、Go言語のリンカ（`cmd/internal/ld`）とコンパイラ（`cmd/internal/gc`、ただしこのコミットでは`gc`側の変更は含まれていない）における、共有ライブラリ（モジュール）から定義された型を持つグローバル変数のガベージコレクション（GC）情報処理に関する修正です。特に、他の共有ライブラリで定義された型の`gcmask`（GCがポインタをスキャンするために必要なビットマスク）を正しく取得・関連付けるためのメカニズムを導入しています。

## 元コミット内容

`cmd/internal/gc, cmd/internal/ld: fixes for global vars of types from other modules`

他の共有ライブラリで定義された型を含むグローバルデータの`gcprog`を作成するためには、それらの型について多くの情報を知る必要があります。そのため、"type."で始まる名前を持つシンボルの値を読み取ります。もし型がマスクを使用している場合、マスクを定義するシンボルの名前は残念ながら型名から予測できないため、そのようなシンボルのアドレスをすべて追跡し、後で型シンボルと関連付ける必要があります。

この変更にはあまり満足していませんが、このようなものが必要であり、これが私が知る限り最も良い方法です。

## 変更の背景

Go言語は、バージョン1.8以降でプラグイン（共有ライブラリ）のサポートを本格的に導入しました。このコミットは、その初期段階、Go 1.5の開発サイクル中に行われたもので、共有ライブラリ間の連携におけるガベージコレクションの課題に対処しています。

Goのガベージコレクタは、ヒープ上のポインタを正確に識別し、到達可能なオブジェクトをマークすることで動作します。このためには、各データ構造（型）のどこにポインタが含まれているかという情報が必要です。この情報は`gcprog`（ガベージコレクションプログラム）や`gcmask`（ガベージコレクションマスク）としてコンパイル時に生成され、実行時にGCによって利用されます。

問題は、あるモジュール（実行可能ファイルまたは共有ライブラリ）が、別の共有ライブラリで定義された型を持つグローバル変数を持つ場合でした。このグローバル変数をGCが正しくスキャンするためには、その変数の型が持つポインタ情報（`gcprog`や`gcmask`）が必要になります。しかし、これらの型情報が別の共有ライブラリに存在する場合、リンカはそれらの情報をどのように取得し、現在のモジュールのGC情報と統合するかが課題でした。

特に、`gcmask`を定義するシンボルの名前が型名から直接予測できないという点が複雑さを増していました。これは、`gcmask`が特定のメモリアドレスに配置される可能性があり、そのアドレスがシンボル名に直接反映されないためです。このため、リンカは共有ライブラリからすべての関連シンボルを読み込み、`gcmask`のアドレスを追跡し、後から対応する型シンボルと関連付けるという、より複雑なアプローチを取る必要がありました。

このコミットは、Goの共有ライブラリ機能が成熟する過程で、異なるモジュール間で型情報、特にGC関連のメタデータを正しく共有・解決するための基盤を築く重要なステップでした。

## 前提知識の解説

### Go言語のガベージコレクション (GC)
GoのGCは、並行マーク＆スイープ方式を採用しています。GCが正しく動作するためには、ヒープ上のオブジェクトのどこにポインタが含まれているかを正確に知る必要があります。この情報はコンパイル時に生成され、実行時にGCがオブジェクトをスキャンする際に利用されます。

### `gcprog` と `gcmask`
*   **`gcprog` (Garbage Collection Program):** 複雑なデータ構造（例: 構造体、配列）内のポインタの位置を記述するバイトコードのようなものです。GCは`gcprog`を実行して、オブジェクト内のどのオフセットにポインタがあるかを動的に判断します。
*   **`gcmask` (Garbage Collection Mask):** 比較的単純なデータ構造（例: 固定サイズの配列）の場合、ポインタの位置をビットマスクで表現することがあります。各ビットが特定のオフセットにポインタが存在するかどうかを示します。

### Goの共有ライブラリ (Plugins)
Go 1.8から導入されたプラグイン機能は、Goプログラムが実行時に動的にロードできる共有ライブラリ（`.so`ファイルなど）を作成することを可能にします。これにより、アプリケーションのモジュール性を高めたり、実行時に機能を拡張したりできます。共有ライブラリは、それぞれが独立したGoランタイム環境を持つため、型情報やGC情報の共有には特別な考慮が必要です。

### Goリンカ (`cmd/internal/ld`)
Goのリンカは、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルや共有ライブラリを生成するツールです。リンカは、シンボル解決、再配置、GC情報の埋め込みなど、多くの重要なタスクを担当します。

### `LSym` (Linker Symbol)
Goリンカ内部でシンボルを表す構造体です。プログラム内の関数、変数、型などの各エンティティは`LSym`として表現され、その名前、アドレス、サイズ、型情報（例: `obj.SDYNIMPORT`）などが含まれます。

### `obj.SDYNIMPORT`
`LSym`の`Type`フィールドで使われる定数の一つで、そのシンボルが動的にインポートされたものであることを示します。つまり、そのシンボルが現在のモジュールではなく、外部の共有ライブラリで定義されていることを意味します。

### ELFシンボル
ELF (Executable and Linkable Format) は、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイル内のシンボルは、`st_info`フィールドによってその種類（`ST_TYPE`）と結合属性（`ST_BIND`）が定義されます。
*   `elf.ST_TYPE(s.Info)`: シンボルの種類を抽出します。
    *   `elf.STT_NOTYPE`: 型が指定されていないシンボル。
    *   `elf.STT_SECTION`: セクションに関連付けられたシンボル。
*   `elf.ST_BIND(s.Info)`: シンボルの結合属性を抽出します。
    *   `elf.STB_GLOBAL`: グローバルシンボル。異なるオブジェクトファイルから参照可能です。

## 技術的詳細

このコミットの主要な目的は、Goのリンカが、他の共有ライブラリで定義された型を持つグローバル変数のGC情報を正しく処理できるようにすることです。具体的には、以下の課題を解決しています。

1.  **`gcprog`の解決:** 外部モジュールの型に対する`gcprog`は、`"type..gcprog.$name"`という予測可能な名前で参照できるため、`decodesym.go`で`obj.SDYNIMPORT`の場合にこの名前をルックアップするように変更されました。
2.  **`gcmask`の解決の複雑性:** `gcmask`は`gcprog`とは異なり、そのシンボル名が型名から直接予測できません。`gcmask`は`runtime.gcbits.0x...`のようなアドレスベースの名前を持つことがあり、そのアドレスはリンカが共有ライブラリを読み込むまで不明です。このため、リンカは以下の手順で`gcmask`を解決します。
    *   **`runtime.gcbits.*`シンボルの収集:** `ldshlibsyms`関数（`lib.go`内）が、共有ライブラリからすべてのシンボルを読み込む際に、`runtime.gcbits.0x`で始まる名前のシンボル（これらが`gcmask`データそのもの）を特定し、そのアドレスと実際のバイトデータを`gcmasks`マップに保存します。これらのシンボルは通常、ローカルシンボルとして扱われます。
    *   **`type.`シンボルの収集とデータ読み込み:** 同様に、`type.`で始まる名前のシンボル（これらが型定義）も収集し、そのシンボルのデータ（型情報自体）を読み込み、`LSym.P`に格納します。これらの型シンボルは`types`スライスに一時的に保持されます。
    *   **`gcmask`と型シンボルの関連付け:** すべてのシンボルを読み込んだ後、`types`スライス内の各型シンボルをイテレートします。各型シンボルのデータ（`LSym.P`）から、その型が参照する`gcmask`のアドレスを抽出します。このアドレスは、`decodetype_gcmask`関数が`LSym.P`から`gcmask`シンボルへのオフセットを計算するのと同様の方法で取得されます。
    *   **`gcmask`データの割り当て:** 抽出したアドレスをキーとして`gcmasks`マップを検索し、対応する`gcmask`のバイトデータを取得します。このバイトデータを型シンボルの新しいフィールド`LSym.gcmask`に割り当てます。これにより、型シンボルが自身の`gcmask`データに直接アクセスできるようになります。

このアプローチは、`gcmask`シンボルの名前が予測できないという制約の中で、リンカが動的に`gcmask`データを解決し、型情報と関連付けるための実用的な解決策を提供します。コミットメッセージにある「I'm not very happy about this change, but something like this is needed and this is as pleasant as I know how to make it.」というコメントは、この解決策が理想的ではないものの、当時のGoのリンカの制約下で最善であったことを示唆しています。

## コアとなるコードの変更箇所

### `src/cmd/internal/ld/decodesym.go`
*   `decodetype_gcprog`関数と`decodetype_gcmask`関数に`obj.SDYNIMPORT`の場合の処理が追加されました。
    *   `decodetype_gcprog`: 動的インポートされた型の場合、`"type..gcprog." + s.Name[5:]`という名前でGCプログラムシンボルをルックアップするようになりました。
    *   `decodetype_gcmask`: 動的インポートされた型の場合、`LSym`に新しく追加された`gcmask`フィールドを直接返すようになりました。

### `src/cmd/internal/ld/lib.go`
*   `ldshlibsyms`関数が大幅に変更されました。
    *   `f.DynamicSymbols()`から`f.Symbols()`に変更され、すべてのシンボルを読み込むようになりました。
    *   `gcmasks`マップと`types`スライスが導入されました。
    *   `runtime.gcbits.0x`で始まるシンボルを`gcmasks`マップにそのアドレスとデータを格納する処理が追加されました。
    *   `type.`で始まるシンボル（ただし`type..`で始まるものを除く）のデータを読み込み、`LSym.P`に格納し、`types`スライスに追加する処理が追加されました。
    *   すべてのシンボル処理後、`types`スライスをイテレートし、各型シンボルのデータから`gcmask`のアドレスを抽出し、`gcmasks`マップから対応する`gcmask`データを取得して`LSym.gcmask`に割り当てるロジックが追加されました。

### `src/cmd/internal/ld/objfile.go`
*   `rdsym`関数に、`runtime.gcbits.0x`で始まるシンボルが読み込まれた際に、そのシンボルを`Local = true`に設定する処理が追加されました。これは、これらのシンボルが共有ライブラリ内でローカルなものとして扱われるべきであることを示します。

## コアとなるコードの解説

### `src/cmd/internal/ld/decodesym.go`
```go
// Type.commonType.gc
func decodetype_gcprog(s *LSym) *LSym {
	if s.Type == obj.SDYNIMPORT {
		// The gcprog for "type.$name" is calle "type..gcprog.$name".
		x := "type..gcprog." + s.Name[5:]
		return Linklookup(Ctxt, x, 0)
	}
	return decode_reloc_sym(s, 1*int32(Thearch.Ptrsize)+8+2*int32(Thearch.Ptrsize))
}

func decodetype_gcmask(s *LSym) []byte {
	if s.Type == obj.SDYNIMPORT {
		// ldshlibsyms makes special efforts to read the value
		// of gcmask for types defined in that shared library.
		return s.gcmask
	}
	mask := decode_reloc_sym(s, 1*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize))
	return mask.P
}
```
*   `decodetype_gcprog`: `obj.SDYNIMPORT`（動的インポートされたシンボル）の場合、GCプログラムのシンボル名を`"type..gcprog."`プレフィックスと元の型名から構築し、それをルックアップします。これにより、外部ライブラリの型に対するGCプログラムを解決できるようになります。
*   `decodetype_gcmask`: `obj.SDYNIMPORT`の場合、`LSym`構造体に新しく追加された`gcmask`フィールドの値を直接返します。これは、`ldshlibsyms`関数がこのフィールドに適切な`gcmask`データを事前に設定していることを前提としています。

### `src/cmd/internal/ld/lib.go`
```go
func ldshlibsyms(shlib string) {
	// ... (既存のコード) ...

	syms, err := f.Symbols() // DynamicSymbols() から Symbols() に変更
	// ... (エラーハンドリング) ...

	gcmasks := make(map[uint64][]byte) // gcmaskデータをアドレスで管理するマップ
	types := []*LSym{}                 // 処理対象の型シンボルを一時的に保持するスライス

	for _, s := range syms {
		// ... (シンボルフィルタリング) ...

		if strings.HasPrefix(s.Name, "runtime.gcbits.0x") {
			// runtime.gcbits.0x... で始まるシンボルはgcmaskデータそのもの
			data := make([]byte, s.Size)
			sect := f.Sections[s.Section]
			if sect.Type == elf.SHT_PROGBITS {
				// シンボルのデータを読み込み、gcmasksマップにアドレスをキーとして格納
				n, err := sect.ReadAt(data, int64(s.Value-sect.Offset))
				// ... (エラーハンドリング) ...
			}
			gcmasks[s.Value] = data
		}
		if elf.ST_BIND(s.Info) != elf.STB_GLOBAL {
			continue
		}

		lsym := Linklookup(Ctxt, s.Name, 0)
		// ... (既存のコード) ...
		lsym.Type = obj.SDYNIMPORT
		lsym.File = libpath

		if strings.HasPrefix(lsym.Name, "type.") {
			// type. で始まるシンボルは型定義
			data := make([]byte, s.Size)
			sect := f.Sections[s.Section]
			if sect.Type == elf.SHT_PROGBITS {
				// 型シンボルのデータを読み込み、LSym.Pに格納
				n, err := sect.ReadAt(data, int64(s.Value-sect.Offset))
				// ... (エラーハンドリング) ...
				lsym.P = data
			}
			if !strings.HasPrefix(lsym.Name, "type..") { // type.. で始まるものはGCプログラムなので除外
				types = append(types, lsym) // 処理対象の型シンボルとして追加
			}
		}
	}

	// すべてのシンボルを読み込んだ後、型シンボルとgcmaskを関連付ける
	for _, t := range types {
		if decodetype_noptr(t) != 0 || decodetype_usegcprog(t) != 0 {
			continue // ポインタを含まない型やgcprogを使用する型はスキップ
		}
		// 型データからgcmaskのアドレスを抽出
		addr := decode_inuxi(t.P[1*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize):], Thearch.Ptrsize)
		tgcmask, ok := gcmasks[addr] // 抽出したアドレスでgcmasksマップを検索
		if !ok {
			Diag("bits not found for %s at %d", t.Name, addr)
		}
		t.gcmask = tgcmask // 取得したgcmaskデータを型シンボルに割り当て
	}

	// ... (既存のコード) ...
}
```
*   この関数は、共有ライブラリからシンボルを読み込み、それらを現在のリンクコンテキストに統合する役割を担います。
*   `f.DynamicSymbols()`から`f.Symbols()`への変更は、動的シンボルだけでなく、すべてのシンボル（特にローカルな`runtime.gcbits.*`シンボル）を読み込む必要があるためです。
*   `gcmasks`マップと`types`スライスは、`gcmask`データと型シンボルを一時的に保持し、後でそれらを関連付けるための重要なデータ構造です。
*   `runtime.gcbits.0x`シンボルのデータ読み込みと`gcmasks`への格納、および`type.`シンボルのデータ読み込みと`types`への格納は、`gcmask`と型情報を収集するための準備ステップです。
*   ループの最後にある`for _, t := range types`ブロックが、このコミットの核心部分です。ここでは、各型シンボルの生データ（`t.P`）から`gcmask`のアドレスを計算し、そのアドレスを使って`gcmasks`マップから対応する`gcmask`データを取得し、型シンボル（`t`）の`gcmask`フィールドに設定しています。このプロセスにより、外部共有ライブラリで定義された型であっても、その`gcmask`情報が現在のリンカコンテキストで利用可能になります。

```
*   `LSym`構造体に`gcmask`フィールドが追加されました。これにより、`LSym`がその型に関連付けられた`gcmask`データを直接保持できるようになり、`decodesym.go`の`decodetype_gcmask`関数から直接アクセスできるようになります。

### `src/cmd/internal/ld/objfile.go`
```go
func rdsym(ctxt *Link, f *Biobuf, pkg string) *LSym {
	// ... (既存のコード) ...

	if v == 0 && strings.HasPrefix(s.Name, "runtime.gcbits.0x") {
		s.Local = true // runtime.gcbits.0x... シンボルをローカルとしてマーク
	}
	return s
}
```
*   `rdsym`関数は、オブジェクトファイルからシンボルを読み込む際に呼び出されます。
*   `runtime.gcbits.0x`で始まるシンボルが読み込まれた場合、そのシンボルを`Local = true`に設定します。これは、これらのシンボルが共有ライブラリ内でローカルなものとして扱われるべきであり、外部にエクスポートされるべきではないことをリンカに伝えます。これにより、リンカがこれらのシンボルを正しく処理し、他のモジュールとの衝突を避けることができます。

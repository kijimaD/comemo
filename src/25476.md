## 変更の背景

Go言語の`strings.Index`関数は、ある文字列（`s`）の中に別の文字列（`sep`）が最初に現れるインデックスを検索する基本的な機能を提供します。この関数は、多くのアプリケーションで頻繁に使用されるため、そのパフォーマンスはGoプログラム全体の実行速度に大きな影響を与えます。

従来の`strings.Index`の実装では、主にRabin-Karpアルゴリズムのような汎用的な文字列検索アルゴリズムが使用されていました。Rabin-Karpは長い文字列の検索には効率的ですが、検索対象の文字列（`sep`）が非常に短い場合、ハッシュ計算や比較のオーバーヘッドが相対的に大きくなり、効率が低下する可能性があります。特に、1バイトの文字列検索には既に特別な最適化が施されていましたが、それ以上の短い文字列（例えば2バイトから31バイト程度）については、まだ最適化の余地がありました。

このコミットの目的は、`amd64`アーキテクチャにおいて、短い文字列（具体的には32バイト未満）の検索性能を向上させることです。アセンブリ言語を使用することで、CPUの低レベルな命令（特にSIMD命令）を直接利用し、CISCアーキテクチャの特性を最大限に引き出すことが可能になります。これにより、Goのランタイムが提供する高レベルな抽象化のオーバーヘッドを回避し、より高速な文字列比較を実現します。ベンチマーク結果が示すように、特に「Hard」と名付けられたテストケース（おそらく、検索対象の文字列が頻繁に出現しない、または特定のパターンを持つケース）で顕著な性能向上が見られます。

## 前提知識の解説

### Go言語の `strings.Index` 関数
`strings.Index(s, sep string) int` は、文字列 `s` 内で部分文字列 `sep` が最初に現れる位置のインデックスを返します。見つからない場合は `-1` を返します。この関数はGoプログラムで非常に頻繁に利用されるため、その効率性は重要です。

### アセンブリ言語 (x86-64/AMD64) と Go
Go言語は通常、高レベルな抽象化を提供しますが、パフォーマンスがクリティカルな部分（特にランタイムや標準ライブラリの一部）では、特定のアーキテクチャ向けにアセンブリ言語で記述されたコードを使用することがあります。これにより、C言語やGo言語では実現が難しい、CPUのレジスタや特定の命令セット（例: SIMD命令）を直接操作して、最大限のパフォーマンスを引き出すことが可能になります。GoのアセンブリはPlan 9アセンブリという独自の記法を使用します。

### 文字列検索アルゴリズム (Rabin-Karp)
Rabin-Karpアルゴリズムは、ハッシュ関数を用いて文字列の比較を高速化する文字列検索アルゴリズムの一つです。パターン文字列のハッシュ値を計算し、テキスト文字列の各部分文字列のハッシュ値と比較します。ハッシュ値が一致した場合のみ、実際の文字列比較を行います。これにより、多くの不一致をハッシュ値の比較だけでスキップできるため、平均的には高速ですが、ハッシュ衝突の処理やハッシュ値の計算自体にオーバーヘッドがあります。

### ベンチマーク結果の読み方
コミットメッセージに含まれるベンチマーク結果は、Goの標準ベンチマークツール (`go test -bench=.`) によって生成されたものです。
-   `name`: ベンチマークテストの名前。
-   `old time/op`: 変更前の1操作あたりの平均実行時間。
-   `new time/op`: 変更後の1操作あたりの平均実行時間。
-   `delta`: 変更による性能変化率。負の値は高速化、正の値は低速化を示します。
-   `p`: 統計的有意性を示すP値。0に近いほど、変化が偶然ではない可能性が高いことを示します。
-   `n`: 実行されたベンチマークのイテレーション回数。

### SIMD命令 (SSE/AVX)
SIMD (Single Instruction, Multiple Data) 命令は、一つの命令で複数のデータ要素に対して同じ操作を同時に実行できるCPUの拡張命令セットです。x86-64アーキテクチャでは、SSE (Streaming SIMD Extensions) や AVX (Advanced Vector Extensions) といったSIMD命令セットが提供されています。文字列検索においては、これらの命令を使って複数のバイトを一度に比較することで、ループ処理を大幅に高速化できます。
-   `MOVOU`: メモリからXMMレジスタ（128ビット）にデータをアラインメントに関係なく移動する命令。
-   `PCMPEQB`: XMMレジスタ内の各バイトを比較し、一致したバイトに対応する結果レジスタのバイトをすべて1に、不一致の場合はすべて0にする命令。
-   `PMOVMSKB`: XMMレジスタ内の各バイトの最上位ビット（MSB）を抽出し、それらを結合して汎用レジスタに格納する命令。これにより、16バイトの比較結果を16ビットのマスクとして取得できます。

## 技術的詳細

このコミットは、Goの`strings.Index`関数において、検索対象の文字列（`sep`）の長さが短い場合に特化した最適化を`amd64`アーキテクチャ向けに導入します。

1.  **既存のRabin-Karpの限界**: 従来の`strings.Index`は、`sep`の長さが1バイトの場合を除き、Rabin-Karpアルゴリズムを使用していました。Rabin-Karpは長い文字列には有効ですが、`sep`が短い場合（例えば2〜31バイト）、ハッシュ計算やハッシュ衝突時のフォールバック比較のオーバーヘッドが、単純なバイトごとの比較よりも大きくなることがあります。

2.  **`indexShortStr`アセンブリ関数の導入**: このコミットの核となるのは、`src/runtime/asm_amd64.s`に追加された`strings·indexShortStr`というアセンブリ関数です。この関数は、`sep`の長さが2バイトから`shortStringLen`（31バイト）までの範囲の文字列検索を高速化するために設計されています。

3.  **プラットフォーム固有の実装**:
    *   `src/strings/strings_amd64.go`が新しく作成され、`amd64`アーキテクチャ向けの`Index`関数が定義されます。このファイルでは、`sep`の長さが`shortStringLen`以下の場合に`indexShortStr`アセンブリ関数を呼び出すように変更されています。
    *   `src/strings/strings_generic.go`も新しく作成され、`amd64`以外のアーキテクチャ向けの`Index`関数が定義されます。こちらは従来のRabin-Karpアルゴリズムを使用します。
    *   元の`src/strings/strings.go`からは`Index`関数の実装が削除され、ビルドタグによって適切なプラットフォーム固有のファイルが選択されるようになります。

4.  **アセンブリコードの最適化手法**:
    `strings·indexShortStr`関数は、`sep`の長さに基づいて異なる最適化パスを使用します。
    *   **短い文字列（2〜8バイト）**: これらのケースでは、`MOVW` (2バイト), `MOVL` (4バイト), `MOVQ` (8バイト) といった命令を使って、一度に複数のバイトを比較します。これにより、ループのイテレーション回数を減らし、比較処理を高速化します。
    *   **中程度の文字列（9〜31バイト）**: この範囲では、SIMD命令（SSE2以降）が活用されます。
        *   `MOVOU`: 検索対象の文字列とパターン文字列から16バイトのブロックをXMMレジスタにロードします。
        *   `PCMPEQB`: ロードした2つの16バイトブロックをバイトごとに比較し、一致するバイトがあれば対応するビットをセットします。
        *   `PMOVMSKB`: `PCMPEQB`の結果からマスクビットを抽出し、汎用レジスタに格納します。このマスクビットがすべてセットされていれば、16バイト全体が一致したことになります。
        このSIMD命令の組み合わせにより、一度に16バイトの比較を非常に効率的に行うことができます。さらに、パターン文字列が16バイトを超える場合（例: 17〜31バイト）、パターンを2つの部分（最初の16バイトと残りの部分）に分割し、それぞれを比較するロジックが実装されています。

5.  **ベンチマーク結果の分析**:
    *   `IndexHard1`, `IndexHard2`, `IndexHard3`といったテストケースで、`time/op`が大幅に減少（-73.06%から-79.55%）しており、これは短い文字列の検索が劇的に高速化されたことを示しています。これらの「Hard」なケースは、おそらく検索対象の文字列が長く、かつパターン文字列が短い場合に、Rabin-Karpのオーバーヘッドが顕著だったシナリオをシミュレートしていると考えられます。
    *   `IndexRune`, `IndexRuneFastPath`, `IndexByte`など、他の`Index`関連のベンチマークでは大きな変化がないか、わずかな増加が見られます。これは、これらのケースが既に最適化されているか、今回の変更の対象外であるためです。
    *   `Index`全体のベンチマークでわずかな増加が見られるのは、新しいロジックへの分岐やアセンブリ関数の呼び出しオーバーヘッドが、一部のケースでRabin-Karpよりもわずかに大きくなった可能性を示唆していますが、全体的な改善効果は非常に大きいです。

## コアとなるコードの解説

### `src/runtime/asm_amd64.s` における `strings·indexShortStr` 関数

このアセンブリ関数は、検索対象の文字列 `s` とパターン文字列 `c` を引数に取り、`c` が `s` 内で最初に出現するインデックスを返します。特に、`c` の長さが2バイトから31バイトまでの短い文字列に特化しています。

関数の冒頭では、引数 `s`、`s_len`、`c`、`c_len` をレジスタにロードし、基本的な長さチェックを行います。`c_len` が `s_len` より大きい場合は検索失敗 (`fail`) となります。

その後、`c_len` の値に基づいて、異なる最適化パスに分岐します。

*   **`CMPQ BX, $2` / `JA _3_or_more`**: `c_len` が2バイトの場合の処理。
    *   `MOVW (AX), AX`: パターン文字列 `c` の最初の2バイトを `AX` レジスタにロードします。
    *   ループ (`loop2`): `s` の各2バイトブロックを `SI` にロードし、`AX` と比較します。一致すれば `success` へ。
*   **`CMPQ BX, $3` / `JA _4_or_more`**: `c_len` が3バイトの場合の処理。
    *   パターン文字列の最初の2バイトと次の1バイトを別々にロードし、`s` の各位置で最初の2バイトが一致するかをチェック (`partial_success3`)。一致した場合のみ、次の1バイトも比較します。
*   **`CMPQ BX, $4` / `JA _5_or_more`**: `c_len` が4バイトの場合の処理。
    *   `MOVL (AX), AX`: パターン文字列 `c` の最初の4バイトを `AX` レジスタにロードします。
    *   ループ (`loop4`): `s` の各4バイトブロックを `SI` にロードし、`AX` と比較します。
*   **`CMPQ BX, $7` / `JA _8_or_more`**: `c_len` が5〜7バイトの場合の処理。
    *   パターン文字列を2つの4バイトブロックに分割し、最初の4バイトが一致した場合にのみ次の4バイトを比較します。
*   **`CMPQ BX, $8` / `JA _9_or_more`**: `c_len` が8バイトの場合の処理。
    *   `MOVQ (AX), AX`: パターン文字列 `c` の最初の8バイトを `AX` レジスタにロードします。
    *   ループ (`loop8`): `s` の各8バイトブロックを `SI` にロードし、`AX` と比較します。
*   **`CMPQ BX, $16` / `JA _16_or_more`**: `c_len` が9〜15バイトの場合の処理。
    *   パターン文字列を2つの8バイトブロックに分割し、最初の8バイトが一致した場合にのみ次の8バイトを比較します。
*   **`CMPQ BX, $16` / `JA _17_to_31`**: `c_len` が16バイトの場合の処理。
    *   `MOVOU (AX), X1`: パターン文字列 `c` の最初の16バイトをXMMレジスタ `X1` にロードします。
    *   ループ (`loop16`):
        *   `MOVOU (DI), X2`: 検索対象 `s` の現在の位置から16バイトをXMMレジスタ `X2` にロードします。
        *   `PCMPEQB X1, X2`: `X1` と `X2` の各バイトを比較し、結果を `X2` に格納します。一致するバイトはすべて1、不一致はすべて0になります。
        *   `PMOVMSKB X2, SI`: `X2` の各バイトの最上位ビットを抽出し、16ビットのマスクを `SI` レジスタに格納します。
        *   `CMPQ SI, $0xffff`: `SI` が `0xffff` (すべてのビットが1) であれば、16バイトすべてが一致したことを意味し、`success` へ分岐します。
*   **`_17_to_31`**: `c_len` が17〜31バイトの場合の処理。
    *   パターン文字列を2つの16バイトブロックに分割します（最初の16バイトと残りの部分）。
    *   最初の16バイトが一致した場合 (`partial_success17to31`) のみ、残りの部分もSIMD命令で比較します。

`fail` ラベルでは `-1` を返して検索失敗を、`success` ラベルでは見つかったインデックスを返して検索成功を示します。

### `src/strings/strings_amd64.go` における `Index` 関数

```go
package strings

// indexShortStr returns the index of the first instance of c in s, or -1 if c is not present in s.
// indexShortStr requires 2 <= len(c) <= shortStringLen
func indexShortStr(s, c string) int // ../runtime/asm_$GOARCH.s
const shortStringLen = 31

// Index returns the index of the first instance of sep in s, or -1 if sep is not present in s.
func Index(s, sep string) int {
	n := len(sep)
	switch {
	case n == 0:
		return 0
	case n == 1:
		return IndexByte(s, sep[0])
	case n <= shortStringLen: // ここが変更点
		return indexShortStr(s, sep) // アセンブリ関数を呼び出す
	case n == len(s):
		if sep == s {
			return 0
		}
		return -1
	case n > len(s):
		return -1
	}
	// Rabin-Karp search (長い文字列の場合のフォールバック)
	hashsep, pow := hashStr(sep)
	var h uint32
	for i := 0; i < n; i++ {
		h = h*primeRK + uint32(s[i])
	}
	if h == hashsep && s[:n] == sep {
		return 0
	}
	for i := n; i < len(s); {
		h *= primeRK
		h += uint32(s[i])
		h -= pow * uint32(s[i-n])
		i++
		if h == hashsep && s[i-n:i] == sep {
			return i - n
		}
	}
	return -1
}
```

このコードは、`amd64`アーキテクチャでビルドされる際に使用されます。
*   `indexShortStr`関数は、`../runtime/asm_$GOARCH.s`（この場合は`asm_amd64.s`）に実装されていることを示す宣言です。
*   `shortStringLen`定数は31に設定されており、31バイト以下の短い文字列がこの最適化の対象となります。
*   `Index`関数内の`switch`文に新しいケース`case n <= shortStringLen:`が追加されました。
*   `sep`の長さ`n`が`shortStringLen`以下の場合、`indexShortStr(s, sep)`を呼び出してアセンブリ最適化された検索を実行します。
*   それ以外のケース（`sep`が`shortStringLen`より長い場合）では、引き続きRabin-Karpアルゴリズムが使用されます。

この変更により、Goの`strings.Index`関数は、検索対象の文字列の長さに基づいて最適なアルゴリズムを自動的に選択し、特に短い文字列の検索において高いパフォーマンスを発揮するようになりました。

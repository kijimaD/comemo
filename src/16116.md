# [インデックス 16116] ファイルの概要

このコミットは、Goランタイムのメモリヒープ管理において、`MHeap`構造体内の`union`を`struct`に置き換える変更を加えています。この変更の主な目的は、Goの「正確なガベージコレクション (Precise GC)」が正しく機能するようにするためです。`union`の使用は、ガベージコレクタがポインタを正確に識別するのを妨げる可能性があり、これが問題となっていました。また、このコミットはGoのIssue #5193に関連する更新です。

## 変更の背景

この変更の背景には、Go言語のガベージコレクション（GC）の正確性に関する重要な課題があります。GoのGCは「正確なGC (Precise GC)」であり、メモリ上のどこにポインタが存在するかを正確に把握する必要があります。これにより、到達可能なオブジェクトを正確に識別し、誤って生きているオブジェクトを回収してしまうことを防ぎます。

しかし、C言語のような`union`（共用体）は、異なる型のデータが同じメモリ領域を共有することを可能にします。この特性は、ガベージコレクタにとって大きな問題を引き起こす可能性があります。`union`がポインタ型と非ポインタ型を混在させている場合、GCは特定のメモリ位置がポインタであるか、それとも単なるデータであるかを区別することが困難になります。もしGCがポインタではないデータをポインタとして解釈しようとすると、無効なメモリアドレスを参照したり、誤ったオブジェクトを到達可能と判断したり、あるいは逆に生きているポインタを見落としてオブジェクトを誤って回収したりする可能性があります。

このコミットは、Goランタイムの`MHeap`構造体内で使用されていた`union`が、このような正確なGCの要件を満たさないという問題に対処するために行われました。具体的には、`MHeap`内の`central`フィールドが`union`として定義されており、これがGCの正確性を損なう可能性があったため、`struct`に置き換えられました。コミットメッセージにある「Update #5193」は、この問題がGoのIssueトラッカーで議論されていたことを示唆しています。

## 前提知識の解説

### ガベージコレクション (Garbage Collection, GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはやプログラムから到達不可能になった（不要になった）領域を自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークなどのバグを減らすことができます。

### 正確なガベージコレクション (Precise GC)

正確なGCは、メモリ上のすべての値の型情報を正確に把握し、どれがポインタでどれが非ポインタデータであるかを厳密に区別できるガベージコレクション方式です。ポインタであると識別された値のみをたどり、到達可能なオブジェクトを特定します。これにより、誤って生きているオブジェクトを回収したり、無効なメモリを読み取ったりするリスクを排除し、メモリの安全性を高めます。GoのGCは、この正確なGCに分類されます。

### 不正確なガベージコレクション (Conservative GC)

不正確なGC（または保守的GC）は、メモリ上の値がポインタであるかどうかを確実に判断できない場合に、その値がポインタである「可能性がある」と仮定して処理する方式です。これは、型情報が利用できないC/C++のような言語でよく用いられます。保守的GCは実装が容易ですが、実際にはポインタではない値をポインタと誤認する可能性があるため、不要なメモリを解放できない（メモリリークが発生する）リスクや、誤って生きているオブジェクトを回収してしまうリスクがあります。

### Union (共用体)

`union`は、C言語などのプログラミング言語に存在するデータ構造で、複数の異なる型のメンバが同じメモリ領域を共有します。一度にその`union`のメンバのうち1つだけが有効な値を保持します。例えば、`union`が整数と浮動小数点数をメンバとして持つ場合、その`union`変数は整数として使われるか、浮動小数点数として使われるかのどちらかであり、両方を同時に保持することはできません。

`union`はメモリ効率を高めるために使用されますが、ガベージコレクタにとっては課題となります。なぜなら、GCは`union`の現在の「アクティブな」メンバがどれであるかを判断できず、そのメモリ領域にポインタが含まれているかどうかを正確に識別できない可能性があるためです。

### Go言語における`unsafe.Pointer`とGC

Go言語にはC言語のような直接的な`union`型は存在しません。しかし、`unsafe.Pointer`を使用することで、型安全性をバイパスして任意の型のポインタとしてメモリを扱うことが可能です。これは非常に強力ですが、同時に危険な機能であり、GCがポインタを追跡する能力に影響を与える可能性があります。このコミットで問題となっている`union`は、Goのソースコード内でC言語の構文（またはそれに近いもの）として使用されていたものであり、Goの型システムとは異なる低レベルな実装の詳細に関連しています。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのメモリ管理の根幹に関わる部分です。Goのランタイムは、ヒープメモリの割り当てと解放を効率的に行うために、`MHeap`や`MCentral`といった内部構造体を使用しています。

`MHeap`構造体は、Goのヒープ全体の管理を担当します。その中に`central`というフィールドがあり、これは様々なサイズのオブジェクトを管理するための「中央フリーリスト」である`MCentral`の配列です。

元のコードでは、この`central`フィールドが以下のように`union`として定義されていました。

```c
union {
    MCentral;
    byte pad[CacheLineSize];
} central[NumSizeClasses];
```

この`union`の目的は、`MCentral`の各インスタンスがキャッシュラインサイズ（`CacheLineSize`）だけ離れて配置されるようにパディングを挿入し、それぞれの`MCentral.Lock`が異なるキャッシュラインに配置されることで、並行アクセス時のキャッシュ競合（false sharing）を避けることでした。

しかし、この`union`の定義が問題でした。Goの正確なGCは、メモリ上のすべてのポインタを正確に識別する必要があります。もし`MCentral`構造体内にポインタが含まれており、かつ`union`が使用されている場合、GCは`union`のどの「メンバ」が現在アクティブであるかを判断できません。つまり、そのメモリ領域が`MCentral`のインスタンスとして使われているのか、それとも単なるパディングバイトとして使われているのかを区別できないのです。この不確実性が、GCがポインタを正確にスキャンする能力を妨げ、メモリの安全性を損なう可能性がありました。

このコミットでは、この`union`を`struct`に置き換えることで、この問題を解決しています。

```c
struct {
    MCentral;
    byte pad[CacheLineSize];
} central[NumSizeClasses];
```

`union`を`struct`に置き換えることで、`MCentral`と`pad`が明確に異なるフィールドとして扱われるようになります。これにより、GCは`MCentral`内のポインタを正確に識別し、追跡できるようになります。パディングの目的（キャッシュラインアライメント）は維持しつつ、GCの正確性を確保するという二重の目的を達成しています。

また、`src/pkg/runtime/mprof.goc`ファイルでは、別の`union`に関するコメントが追加されています。

```c
// Generally unions can break precise GC,
// this one is fine because it does not contain pointers.
union
{
    struct  // typ == MProf
    ...
}
```

このコメントは、一般的に`union`が正確なGCを破壊する可能性があることを認めつつも、この特定の`union`（`mprof.goc`内のもの）はポインタを含まないため問題ない、と明記しています。これは、Goランタイム開発者が`union`とGCの相互作用について深く理解しており、ポインタを含まない`union`は許容されるという判断を示しています。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.h`の変更

このファイルでの変更は、Goランタイムのメモリヒープ管理の中核である`MHeap`構造体の定義にあります。

-   **`union`から`struct`への変更**:
    -   元のコードでは、`MHeap`構造体の`central`フィールドが`union`として定義されていました。この`union`は、`MCentral`型の匿名フィールドと、`CacheLineSize`バイトのパディング用バイト配列`pad`を持っていました。
    -   この`union`の意図は、`MCentral`の各インスタンスがメモリ上で`CacheLineSize`の倍数アドレスに配置されるようにパディングを挿入し、`MCentral.Lock`フィールドがそれぞれ異なるCPUキャッシュラインに載るようにすることでした。これにより、複数のCPUコアが同時に異なる`MCentral`インスタンスのロックにアクセスする際に、キャッシュの無効化による性能低下（false sharing）を防ぐことができます。
    -   しかし、前述の通り、`union`は正確なGCにとって問題となります。GCは`union`のどのメンバが現在有効であるかを判断できないため、`MCentral`内にポインタが含まれている場合に、そのポインタを正確に識別できない可能性がありました。
    -   この変更では、`union`を`struct`に置き換えることで、この問題を解決しています。`struct`にすることで、`MCentral`と`pad`は明確に異なるフィールドとして扱われます。`MCentral`は引き続き匿名フィールドとして埋め込まれ、その後に`pad`が続くことで、以前と同じメモリレイアウト（`MCentral`の後にパディングが続く）が維持されます。これにより、キャッシュラインアライメントの目的は達成されつつ、GCは`MCentral`内のポインタを正確にスキャンできるようになります。

-   **コメントの変更**:
    -   「the union makes sure that the MCentrals are」から「the padding makes sure that the MCentrals are」への変更は、この構造体のパディングがキャッシュラインアライメントの役割を担っていることをより正確に反映しています。もはや`union`がその役割を果たしているわけではなく、`struct`内の`pad`フィールドがその役割を担っていることを示しています。

### `src/pkg/runtime/mprof.goc`の変更

このファイルでは、既存の`union`定義に新しいコメントが追加されています。

-   **コメントの追加**:
    -   「Generally unions can break precise GC, this one is fine because it does not contain pointers.」というコメントが追加されました。
    -   これは、Goランタイムの設計者が`union`と正確なGCの間の潜在的な問題を認識していることを示しています。
    -   しかし、この特定の`union`（`Bucket`構造体内の匿名`union`）は、そのメンバにポインタを含んでいないため、GCの正確性に影響を与えないと判断されています。ポインタを含まないデータであれば、GCがそのメモリ領域をスキャンしてポインタを探す必要がないため、`union`であっても問題ありません。
    -   このコメントは、Goランタイムのコードベースにおける`union`の使用に関するガイドラインと、GCの正確性を維持するための注意深い設計を示唆しています。

これらの変更は、Goのランタイムがメモリを効率的に管理しつつ、ガベージコレクションの正確性を維持するための継続的な努力の一環です。

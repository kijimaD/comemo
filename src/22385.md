## 変更の背景

Goランタイムは、独自のスケジューラ（M:Nスケジューラ）を持っており、多数のゴルーチン（G）を少数のOSスレッド（M）上で効率的に実行します。このスケジューラは、利用可能なプロセッサ（P）にゴルーチンを割り当て、実行を管理します。

Goのトレースツールは、ランタイムの内部動作を可視化し、パフォーマンスの問題を診断するために非常に重要です。特に、スケジューラの動作を分析する際には、ゴルーチンがどのOSスレッド上で実行されているか、そしてそのOSスレッドがどのプロセッサ（P）に紐づいているかという情報が重要になります。

これまでの`ProcStart`イベント（プロセッサPが利用可能になり、ゴルーチンを実行し始めるイベント）には、タイムスタンプのみが含まれていました。しかし、スケジューラの「局所性分析（scheduler locality analysis）」を行うためには、特定のPがどのOSスレッドに紐づいているかという情報が必要でした。局所性分析とは、CPUキャッシュの効率的な利用や、NUMAアーキテクチャにおけるメモリアクセスの最適化など、プロセッサとスレッド間の関連性を評価するものです。OSスレッドIDがトレースデータに含まれることで、PとMの関連性を追跡し、スケジューラがOSスレッドをどのように利用しているかをより詳細に分析できるようになります。

このコミットは、この情報不足を解消し、Goランタイムのパフォーマンスチューニングやデバッグをより効果的に行うための基盤を提供することを目的としています。

## 前提知識の解説

### Goランタイムスケジューラ (G-M-Pモデル)

Goランタイムは、独自のスケジューラによってゴルーチンを管理します。このスケジューラは、以下の3つの主要な要素で構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。数千から数百万のゴルーチンを同時に実行できます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goランタイムは、OSスレッド上でゴルーチンを実行します。MはOSスケジューラによって管理されます。
*   **P (Processor)**: 論理プロセッサ（またはコンテキスト）。Mがゴルーチンを実行するために必要なリソース（スケジューラのキュー、キャッシュなど）を提供します。GOMAXPROCS環境変数によって、同時に実行できるPの数が決まります。

Goスケジューラは、GをPに割り当て、PがMに紐づいてOSスレッド上でGを実行します。MはPからGを取得し、実行します。PはMがゴルーチンを実行するための「実行コンテキスト」を提供します。

### Goトレースツール (`go tool trace`)

`go tool trace`は、Goプログラムの実行中に発生するイベント（ゴルーチンの生成、スケジューリング、GC、システムコールなど）を記録し、そのデータを可視化するためのツールです。これにより、プログラムのパフォーマンスボトルネックやランタイムの動作を詳細に分析できます。

トレースデータは、Goプログラムの実行中に生成されるバイナリファイル（通常は`.trace`拡張子）に保存されます。このファイルには、タイムスタンプ付きの様々なイベントが含まれており、`go tool trace`コマンドで解析・可視化されます。

### `ProcStart`イベント

`ProcStart`イベントは、Goランタイムトレースにおける重要なイベントの一つです。これは、GoスケジューラのP（プロセッサ）が利用可能になり、ゴルーチンを実行し始める際に記録されます。これまでの`ProcStart`イベントは、単にPが起動したことを示すタイムスタンプ情報のみを持っていました。

### OSスレッドID

オペレーティングシステムは、各スレッドに一意の識別子（スレッドID）を割り当てます。このIDは、OSレベルでのスレッドの追跡や管理に利用されます。GoランタイムのM（OSスレッド）も、基盤となるOSによって割り当てられたスレッドIDを持っています。

### スケジューラの局所性分析

スケジューラの局所性分析は、GoランタイムスケジューラがOSスレッドとCPUコアをどのように利用しているかを評価するプロセスです。具体的には、以下の点を分析します。

*   **CPUキャッシュの利用効率**: ゴルーチンが頻繁に異なるOSスレッドやCPUコアに移動すると、CPUキャッシュのヒット率が低下し、パフォーマンスに悪影響を与える可能性があります。OSスレッドIDを追跡することで、ゴルーチンの実行が特定のOSスレッドに「固定」されているか、あるいは頻繁に移動しているかを判断できます。
*   **NUMA (Non-Uniform Memory Access) アーキテクチャ**: NUMAシステムでは、メモリへのアクセス速度が、アクセスするCPUコアとメモリの位置関係によって異なります。スケジューラがゴルーチンをNUMAノード間で頻繁に移動させると、メモリレイテンシが増加する可能性があります。OSスレッドIDを通じて、ゴルーチンがどのNUMAノードのOSスレッド上で実行されているかを推測し、NUMAの局所性を評価できます。

この分析は、特に高負荷なGoアプリケーションにおいて、パフォーマンスの最適化を行う上で不可欠な情報を提供します。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのトレースメカニズムにOSスレッドIDを組み込むことです。

1.  **`EvProcStart`イベントの拡張**:
    `src/internal/trace/parser.go`において、`EvProcStart`イベントの定義が変更され、タイムスタンプに加えてOSスレッドIDを保持するようになりました。具体的には、`EvProcStart`の引数リストに`thread id`が追加されました。これにより、トレースデータが生成される際に、Pの起動と同時にそのPが紐づくMのOSスレッドIDが記録されるようになります。

2.  **ランタイム側でのスレッドIDの取得と記録**:
    `src/runtime/trace.go`において、`traceProcStart()`関数が変更されました。この関数は、Pが起動する際に呼び出されます。変更後、`traceEvent`関数を呼び出す際に、現在のM（OSスレッド）のID（`getg().m.id`）を取得し、それを`EvProcStart`イベントの引数として渡すようになりました。`getg().m.id`は、Goランタイムが内部的に管理するMのIDであり、これはOSスレッドIDに相当します。

3.  **トレースツール側でのスレッドIDの解析と表示**:
    `src/cmd/trace/trace.go`において、トレースデータを解析し可視化する部分が変更されました。`emitInstant`関数内で`EvProcStart`イベントを処理する際に、イベントの引数からOSスレッドIDを抽出し、それをトレースビューアのイベントデータ構造（`ViewerEvent`）の`Arg`フィールドに格納するようになりました。これにより、`go tool trace`のGUI上で、`ProcStart`イベントに関連するOSスレッドIDを確認できるようになります。

4.  **テストの更新**:
    `src/runtime/pprof/trace_test.go`では、トレースイベントの生成と解析に関するテストが更新されました。特に、`time.Sleep(50 * time.Millisecond) // test proc stop/start events`という行が追加され、`ProcStop`/`ProcStart`イベントが適切に生成されることを確認するための時間的な余裕が与えられています。これは、トレースイベントのタイミングが重要であることを示唆しています。

これらの変更により、`go tool trace`で生成されるトレースデータには、各Pの起動時にそのPが実行されているOSスレッドのIDが含まれるようになり、より詳細なスケジューラの動作分析が可能になります。

### OSスレッドID

オペレーティングシステムは、各スレッドに一意の識別子（スレッドID）を割り当てます。このIDは、OSレベルでのスレッドの追跡や管理に利用されます。GoランタイムのM（OSスレッド）も、基盤となるOSによって割り当てられたスレッドIDを持っています。

### スケジューラの局所性分析

スケジューラの局所性分析は、GoランタイムスケジューラがOSスレッドとCPUコアをどのように利用しているかを評価するプロセスです。具体的には、以下の点を分析します。

*   **CPUキャッシュの利用効率**: ゴルーチンが頻繁に異なるOSスレッドやCPUコアに移動すると、CPUキャッシュのヒット率が低下し、パフォーマンスに悪影響を与える可能性があります。OSスレッドIDを追跡することで、ゴルーチンの実行が特定のOSスレッドに「固定」されているか、あるいは頻繁に移動しているかを判断できます。
*   **NUMA (Non-Uniform Memory Access) アーキテクチャ**: NUMAシステムでは、メモリへのアクセス速度が、アクセスするCPUコアとメモリの位置関係によって異なります。スケジューラがゴルーチンをNUMAノード間で頻繁に移動させると、メモリレイテンシが増加する可能性があります。OSスレッドIDを通じて、ゴルーチンがどのNUMAノードのOSスレッド上で実行されているかを推測し、NUMAの局所性を評価できます。

この分析は、特に高負荷なGoアプリケーションにおいて、パフォーマンスの最適化を行う上で不可欠な情報を提供します。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのトレースメカニズムにOSスレッドIDを組み込むことです。

1.  **`EvProcStart`イベントの拡張**:
    `src/internal/trace/parser.go`において、`EvProcStart`イベントの定義が変更され、タイムスタンプに加えてOSスレッドIDを保持するようになりました。具体的には、`EvProcStart`の引数リストに`thread id`が追加されました。これにより、トレースデータが生成される際に、Pの起動と同時にそのPが紐づくMのOSスレッドIDが記録されるようになります。

2.  **ランタイム側でのスレッドIDの取得と記録**:
    `src/runtime/trace.go`において、`traceProcStart()`関数が変更されました。この関数は、Pが起動する際に呼び出されます。変更後、`traceEvent`関数を呼び出す際に、現在のM（OSスレッド）のID（`getg().m.id`）を取得し、それを`EvProcStart`イベントの引数として渡すようになりました。`getg().m.id`は、Goランタイムが内部的に管理するMのIDであり、これはOSスレッドIDに相当します。

3.  **トレースツール側でのスレッドIDの解析と表示**:
    `src/cmd/trace/trace.go`において、トレースデータを解析し可視化する部分が変更されました。`emitInstant`関数内で`EvProcStart`イベントを処理する際に、イベントの引数からOSスレッドIDを抽出し、それをトレースビューアのイベントデータ構造（`ViewerEvent`）の`Arg`フィールドに格納するようになりました。これにより、`go tool trace`のGUI上で、`ProcStart`イベントに関連するOSスレッドIDを確認できるようになります。

4.  **テストの更新**:
    `src/runtime/pprof/trace_test.go`では、トレースイベントの生成と解析に関するテストが更新されました。特に、`time.Sleep(50 * time.Millisecond) // test proc stop/start events`という行が追加され、`ProcStop`/`ProcStart`イベントが適切に生成されることを確認するための時間的な余裕が与えられています。これは、トレースイベントのタイミングが重要であることを示唆しています。

これらの変更により、`go tool trace`で生成されるトレースデータには、各Pの起動時にそのPが実行されているOSスレッドのIDが含まれるようになり、より詳細なスケジューラの動作分析が可能になります。

## コアとなるコードの解説

### `src/cmd/trace/trace.go` の変更

*   `emitInstant`関数は、トレースイベントをビューアが解釈できる形式に変換し、出力するためのものです。
*   変更前は、`EvProcStart`イベントに対して特別な処理は行われていませんでした。
*   変更後、`ev.Type == trace.EvProcStart`の場合に、イベントの引数（`ev.Args[0]`）からOSスレッドIDを抽出し、それを`ViewerEvent`構造体の`Arg`フィールドに格納するようにしました。
*   `Arg`フィールドは`interface{}`型であるため、`ThreadID`というフィールドを持つ匿名構造体`Arg`を定義し、そこに`ev.Args[0]`の値を代入しています。これにより、トレースビューアがこの追加情報を表示できるようになります。

### `src/internal/trace/parser.go` の変更

*   このファイルは、Goトレースイベントの定数と説明を定義しています。
*   `EvProcStart`のコメントが`// start of P [timestamp]`から`// start of P [timestamp, thread id]`に変更されました。これは、このイベントがOSスレッドIDを含むようになったことを示しています。
*   `EventDescriptions`マップにおいて、`EvProcStart`に対応する`[]string{}`が`[]string{"thread"}`に変更されました。これは、トレースパーサーが`EvProcStart`イベントの引数として`thread`という名前のフィールドを期待するようになったことを示します。

### `src/runtime/pprof/trace_test.go` の変更

*   このファイルは、Goランタイムのプロファイリングおよびトレース機能のテストを含んでいます。
*   `TestTraceStress`関数に`time.Sleep(50 * time.Millisecond) // test proc stop/start events`という行が追加されました。これは、`ProcStop`および`ProcStart`イベントがトレースに確実に記録されるように、テスト実行に意図的な遅延を導入したものです。これにより、これらのイベントが適切にキャプチャされ、テストの信頼性が向上します。

### `src/runtime/trace.go` の変更

*   このファイルは、Goランタイムのトレース機能の実装を含んでいます。
*   `traceEvProcStart`のコメントが`// start of P [timestamp]`から`// start of P [timestamp, thread id]`に変更されました。これは、`src/internal/trace/parser.go`の変更と同期しています。
*   `traceProcStart()`関数は、Pが起動する際に呼び出されるランタイム内部の関数です。
*   変更前は、`traceEvent(traceEvProcStart, -1)`と呼び出され、タイムスタンプ以外の引数はありませんでした。
*   変更後、`traceEvent(traceEvProcStart, -1, uint64(getg().m.id))`と呼び出されるようになりました。
    *   `getg().m.id`は、現在のゴルーチンが実行されているM（OSスレッド）の内部IDを取得します。このIDは、OSが割り当てるスレッドIDに相当します。
    *   `uint64()`へのキャストは、IDを適切な型に変換しています。
*   この変更により、`ProcStart`イベントがトレースファイルに書き込まれる際に、関連するOSスレッドIDが一緒に記録されるようになります。

これらの変更は、Goランタイムのトレースシステムを強化し、より詳細なパフォーマンス分析を可能にするための重要なステップです。

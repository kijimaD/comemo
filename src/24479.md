## 変更の背景

このコミットは、Go 1.5で導入されたcgoの挙動変更、特にC構造体の末尾に配置されたゼロサイズフィールドの扱いに関するものです。この変更は、`https://golang.org/cl/12864`で実装され、`https://golang.org/issue/11925`で議論された問題に対応しています。

`issue/11925`の議論によると、Go 1.5以前では、C構造体の末尾にゼロサイズのフィールド（例えば、長さ0の配列 `char arr[0];` や空の構造体）がある場合、`unsafe.Sizeof`でその構造体のサイズを計算すると、固定サイズのメンバーのサイズが返されていました。しかし、Go 1.5からは、このゼロサイズフィールドの解釈が変更され、パディングや異なるメモリレイアウトの考慮により、構造体全体のサイズが以前よりも大きくなるケースが発生しました。

この変更は、既存のCバインディングに影響を与え、特にデータマーシャリング（GoとCの間でデータを変換する処理）において問題を引き起こしました。Goコンパイラがこれらのフィールドを処理する方法に起因する問題であり、`cgo`自体ではなく、GoのメモリモデルとCのメモリモデルの間の不整合が顕在化した形です。

このコミットは、この重要な変更点を公式ドキュメントである`doc/go1.5.html`に明記することで、Go 1.5へのアップグレードを検討している開発者に対して、既存のコードベースで発生しうる互換性の問題を事前に警告し、適切な対応を促すことを目的としています。

## 前提知識の解説

### cgo

`cgo`は、GoプログラムからC言語のコードを呼び出すためのGoのツールです。また、CプログラムからGoの関数を呼び出すことも可能です。これにより、既存のCライブラリをGoプロジェクトで再利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。`cgo`を使用すると、GoとCの型システムやメモリ管理の違いを橋渡しするためのコードが自動的に生成されます。

### C構造体とゼロサイズフィールド

C言語では、構造体（`struct`）は異なる型のデータをひとまとめにするための複合データ型です。構造体のメンバーはメモリ上に連続して配置されますが、アライメント（メモリ配置の制約）のために、メンバー間にパディング（埋め草）が挿入されることがあります。

「ゼロサイズフィールド」とは、C言語の特定の拡張機能や慣用句で使われる概念で、例えばGCCのFlexible Array Member (FAM) (`struct S { int len; char data[]; };`) のように、構造体の末尾にサイズが0の配列を配置するものです。これは、構造体の直後に可変長データを配置するためのテクニックとして使われます。また、空の構造体（`struct Empty {};`）もゼロサイズと見なされることがあります。

これらのゼロサイズフィールドは、それ自体はメモリを消費しませんが、構造体全体のサイズやアライメントに影響を与える可能性があります。特に、GoとCの間でメモリレイアウトの解釈が異なる場合、問題が生じやすい部分です。

### GoのメモリモデルとCのメモリモデルの差異

GoとCは異なるメモリモデルと型システムを持っています。
*   **アライメント**: GoとCは、データ型をメモリに配置する際のアライメント要件が異なる場合があります。これにより、同じ構造体定義でも、GoとCで`sizeof`演算子の結果が異なることがあります。
*   **ゼロサイズ型の扱い**: Goでは、ゼロサイズの型（例: `struct{}`）はメモリを消費しないとされていますが、特定のコンテキスト（例えば配列の要素）では、要素間のアドレスが異なるようにするために1バイトを占有することがあります。Cのゼロサイズフィールドも同様に、文脈によってそのメモリ上の表現が異なります。
*   **ポインタ演算**: Cではポインタ演算が非常に柔軟ですが、Goでは`unsafe`パッケージを使用しない限り、ポインタ演算は厳しく制限されます。`cgo`を介してCの構造体を扱う際、GoのポインタがCのポインタとどのようにマッピングされるかは重要な考慮事項です。

これらの差異が、Go 1.5におけるゼロサイズフィールドの挙動変更の根本的な原因となりました。

## 技術的詳細

このコミットがドキュメントに追加している技術的な変更点は、Go 1.5におけるcgoとC構造体のゼロサイズフィールドの相互作用に関するものです。具体的には、以下の挙動変更が明記されています。

> When a C struct ends with a zero-sized field, but the struct itself is not zero-sized, Go code can no longer refer to the zero-sized field. Any such references will have to be rewritten.

これは、Go 1.5以降、GoコードがC構造体の末尾にあるゼロサイズフィールド（ただし、構造体自体はゼロサイズではない場合）を直接参照することができなくなったことを意味します。このような参照を行っていた既存のGoコードは、修正が必要になります。

この変更の背景には、GoコンパイラがC構造体のメモリレイアウトを決定する際のアライメントとパディングの計算方法の調整があります。Go 1.5では、C構造体の末尾にゼロサイズフィールドがある場合、Goの`unsafe.Sizeof`が返すサイズが、Cの`sizeof`演算子や以前のGoの挙動と異なるようになりました。これは、GoがC構造体のメモリレイアウトをより厳密に、あるいは異なる方法で解釈するようになったためと考えられます。

例えば、以下のようなC構造体を考えます。

```c
struct MyStruct {
    int a;
    char b[0]; // ゼロサイズフィールド (Flexible Array Member)
};
```

Go 1.5以前では、Goコードから`MyStruct`の`b`フィールドを参照しようとすると、コンパイラは特定のオフセットを計算してアクセスを許可していたかもしれません。しかし、Go 1.5以降では、`b`フィールドがメモリを占有しないため、そのアドレスを計算して参照しようとすると、未定義の動作を引き起こす可能性や、Goのメモリモデルとの不整合が生じる可能性がありました。

この変更は、GoとCの間のメモリレイアウトの整合性を高め、将来的なバグや予期せぬ挙動を防ぐためのものです。結果として、GoコードからC構造体のゼロサイズフィールドへの直接参照は、Goの型システムとメモリモデルの観点から安全ではないと判断され、禁止されることになりました。開発者は、このようなフィールドにアクセスする必要がある場合、Cコード側でヘルパー関数を用意するか、Goの`unsafe`パッケージを慎重に使用してポインタ演算を行うなど、異なるアプローチを検討する必要があります。

## コアとなるコードの解説

追加されたHTMLスニペットは、Go 1.5のリリースノートの一部として、cgoユーザーへの重要な警告を伝えています。

*   **`When a C struct ends with a zero-sized field, but the struct itself is not zero-sized,`**: この部分は、変更が適用される具体的な条件を定義しています。C構造体の末尾にゼロサイズのフィールドが存在し、かつその構造体自体が全体としてゼロサイズではない場合、という条件です。これは、例えばFlexible Array Member (FAM) を持つ構造体などが該当します。
*   **`Go code can no longer refer to the zero-sized field.`**: これが変更の核心です。Go 1.5以降、Go言語のコードから、上記の条件を満たすC構造体内のゼロサイズフィールドを直接参照することができなくなりました。これはコンパイルエラーや実行時エラーの原因となる可能性があります。
*   **`Any such references will have to be rewritten.`**: 影響を受けるGoコードは、この新しい制約に合わせて修正する必要があることを明確に示しています。具体的な修正方法としては、C側でフィールドにアクセスするヘルパー関数を定義し、それをGoから呼び出す、あるいはGoの`unsafe`パッケージを使ってポインタ演算を直接行うなどが考えられますが、後者は非常に注意が必要です。

このドキュメントの追加は、Go 1.5への移行をスムーズにするための重要な情報提供であり、開発者が互換性の問題を早期に特定し、対処できるようにするためのものです。

## 変更の背景

`net.UDPConn` の `WriteMsgUDP` メソッドは、UDPパケットのペイロード (`b`) と帯域外データ (`oob`) を送信するために使用されます。UDPは本来コネクションレスなプロトコルですが、Go言語（および基盤となるOS）では、特定のUDPソケットをリモートアドレスに「接続」する概念が存在します。これにより、ソケットが単一のリモートエンドポイントと通信する場合に、パフォーマンスの最適化やAPIの簡素化が可能になります。

しかし、`WriteMsgUDP` の `addr` 引数が、ソケットが接続済みであるか未接続であるかによって異なる振る舞いをすることが、既存のドキュメントでは十分に明確ではありませんでした。未接続のソケットでは `addr` が必須である一方、接続済みのソケットでは `addr` は `nil` でなければなりません。この曖昧さが誤用や混乱を招く可能性があったため、ドキュメントを更新してこの重要な違いを明確にする必要がありました。

## 前提知識の解説

### UDPソケットの「接続済み」と「未接続」

Go言語の `net` パッケージにおけるUDPソケットには、「接続済み（connected）」と「未接続（unconnected）」という概念があります。

*   **未接続 (Unconnected) UDPソケット:**
    *   `net.ListenUDP` を使用して作成されるのが典型的です。
    *   このソケットは、特定のローカルアドレスとポートにバインドされますが、リモートアドレスとは関連付けられていません。
    *   `WriteToUDP` や `WriteMsgUDP` のような関数を使用する際、送信先のIPアドレスとポートを各送信操作で明示的に指定する必要があります。
    *   単一のUDPソケットで複数の異なるリモートホストと通信する場合に適しています。

*   **接続済み (Connected) UDPソケット:**
    *   `net.Dial("udp", address)` または `net.DialUDP` を使用して作成されるのが典型的です。
    *   UDPはコネクションレスですが、内部的には `connect` システムコールが呼び出され、ローカルソケットが特定のリモートIPアドレスとポートにバインドされます。これはTCPのようなハンドシェイクを伴うものではありません。
    *   このソケットは、作成時に指定された単一のリモートホストとのみ通信できます。
    *   `Write` や `WriteMsgUDP` のような関数を使用する際、送信先のIPアドレスとポートを毎回指定する必要がありません。OSがルーティングルックアップを省略できるため、繰り返し単一のピアと通信する場合にパフォーマンス上の利点がある場合があります。

### `WriteMsgUDP` 関数

`WriteMsgUDP` は、UDPコネクション (`*UDPConn`) に対して、ペイロードデータ (`b`) と、オプションの帯域外データ (`oob`) を送信するためのメソッドです。帯域外データは、例えばIPヘッダーのオプションや、特定のソケットオプションに関連する情報など、通常のデータストリームとは別に送信される制御情報です。

この関数のシグネチャは以下のようになっています（簡略化）：
`func (c *UDPConn) WriteMsgUDP(b, oob []byte, addr *UDPAddr) (n, oobn int, err error)`

*   `b`: 送信するペイロードデータ。
*   `oob`: 送信する帯域外データ。
*   `addr`: 送信先のUDPアドレス。この引数の扱いが、ソケットの接続状態によって異なります。

## 技術的詳細

このコミットの技術的詳細は、`WriteMsgUDP` のドキュメントが、UDPソケットの「接続済み」と「未接続」の状態に応じて `addr` 引数の期待される値が異なることを明確に記述するように変更された点にあります。

変更前は、ドキュメントは単に「`WriteMsgUDP` は `c` を介して `addr` にパケットを書き込む」と述べていました。これは、`addr` が常に指定されるべきであるかのような印象を与える可能性がありました。

変更後は、以下の点が明確にされました：
1.  **`c` が未接続の場合:** `addr` は `nil` であってはならず、送信先のUDPアドレスを明示的に指定する必要があります。
2.  **`c` が接続済みの場合:** `addr` は `nil` でなければなりません。この場合、パケットは `c` が接続された際のリモート宛先アドレスに送信されます。

この変更により、開発者は `WriteMsgUDP` を使用する際に、UDPソケットの接続状態を考慮し、`addr` 引数を正しく設定する方法をより正確に理解できるようになります。これにより、APIの誤用が減り、より堅牢なネットワークアプリケーションの開発が促進されます。

## コアとなるコードの解説

上記の差分は、`src/net/udpsock_plan9.go` ファイル内の `WriteMsgUDP` 関数のコメントブロックに対する変更を示しています。

変更前は、コメントは以下のように記述されていました：
`// WriteMsgUDP writes a packet to addr via c, copying the payload from`
`// b and the associated out-of-band data from oob. It returns the`
`// number of payload and out-of-band bytes written.`

これは一般的な説明であり、`addr` 引数の具体的な振る舞いに関する詳細が不足していました。

変更後、コメントは以下のように更新されました：
`// WriteMsgUDP writes a packet to addr via c if c isn't connected, or`
`// to c's remote destination address if c is connected (in which case`
`// addr must be nil). The payload is copied from b and the associated`
`// out-of-band data is copied from oob. It returns the number of`
`// payload and out-of-band bytes written.`

この新しいコメントは、以下の重要な情報を追加しています：
*   `c` (UDPConn) が「未接続（isn't connected）」の場合、パケットは `addr` に書き込まれる。
*   `c` が「接続済み（is connected）」の場合、パケットは `c` のリモート宛先アドレスに書き込まれ、この場合 `addr` は `nil` でなければならない。

この修正は、コードの動作自体を変更するものではなく、その動作に関するドキュメントの正確性と明確性を向上させるものです。特に、`addr` 引数の条件付きの必要性を明記することで、APIの誤用を防ぎ、開発者が `WriteMsgUDP` をより効果的に使用できるようにすることを目的としています。

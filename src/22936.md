`compress/flate`: オプションのランタイム健全性チェックを追加

このコードのテストカバレッジはせいぜいアドホックであり、不注意にも不変条件（invariant）を退化させる変更を加えてしまうことが容易です。この変更リスト（CL）は、開発中に「true」に変更できる「sanity」定数を追加し、ハフマンデコーダテーブルが健全であるかどうかの追加のランタイムチェックを行います。

## 変更の背景

コミットメッセージが明確に述べているように、`compress/flate` パッケージ内のハフマンデコーダ関連コードのテストカバレッジが不十分であることが、この変更の主な背景にあります。テストが「アドホック（ad hoc）」であるということは、体系的ではなく、特定のケースや既知のバグに対応するために場当たり的に追加されたテストが多いことを示唆しています。このような状況では、コードベースに変更を加えた際に、既存の不変条件（プログラムの実行中に常に真であるべき条件）が意図せず破られてしまう「リグレッション（regression）」が発生するリスクが高まります。

特に、ハフマンデコーダテーブルのような複雑なデータ構造を構築するロジックは、その性質上、多くのエッジケースやコーナーケースが存在し、わずかな変更でも予期せぬ動作を引き起こす可能性があります。開発者が安心してコードを修正・改善できるように、実行時にこれらの不変条件をチェックする仕組みが必要とされました。これにより、開発段階で問題が早期に発見され、デバッグの労力を削減し、より堅牢なコードを維持することが可能になります。

## 前提知識の解説

### 1. Flate圧縮

Flate（またはDEFLATE）は、データ圧縮アルゴリズムの一種で、ZlibやPNG画像フォーマット、HTTP圧縮などで広く利用されています。Flateは、LZ77アルゴリズム（重複する文字列を後方参照で置き換える）とハフマン符号化（出現頻度の高いシンボルを短いビット列で表現する）を組み合わせたハイブリッドな圧縮方式です。

### 2. ハフマン符号化 (Huffman Coding)

ハフマン符号化は、可変長符号化の一種で、データ圧縮によく用いられます。データのシンボル（例えば、文字やバイト）の出現頻度に基づいて、最も頻繁に出現するシンボルには短いビット列を、あまり出現しないシンボルには長いビット列を割り当てます。これにより、平均的なビット長を短くし、データを効率的に表現します。

ハフマン符号化されたデータを元に戻す（デコードする）ためには、ハフマンツリーまたはハフマンテーブルと呼ばれるデータ構造が必要です。このテーブルは、ビット列から元のシンボルを効率的に検索できるように構築されます。テーブルの構築ロジックは複雑であり、正確性が求められます。

### 3. 不変条件 (Invariants)

不変条件とは、プログラムの特定の時点（例えば、関数の開始時、ループの各イテレーション後、データ構造の操作後など）で常に真であると期待される条件のことです。ソフトウェア開発において、不変条件を維持することは、プログラムの正しさを保証し、バグを防ぐ上で非常に重要です。

例えば、ハフマンデコーダテーブルの構築において、「各エントリは一度だけ書き込まれるべきである」とか、「すべての必要なエントリが最終的に埋められるべきである」といった条件は、不変条件として考えられます。これらの不変条件が破られると、デコーダが正しく動作しなかったり、クラッシュしたりする可能性があります。

### 4. ランタイム健全性チェック (Runtime Sanity Checks)

ランタイム健全性チェックは、プログラムが実行されている最中に、特定の条件や不変条件が満たされているかを検証するコードのことです。これは、開発段階やテスト段階で特に有用であり、予期せぬ状態やバグの兆候を早期に検出するのに役立ちます。本番環境ではパフォーマンスオーバーヘッドを避けるために無効にされることが多いですが、開発時にはデバッグを大幅に助けます。

## 技術的詳細

このコミットは、`huffmanDecoder` 構造体の `init` メソッドに `sanity` というブール定数を導入しています。この定数はデフォルトで `false` に設定されていますが、開発者が `true` に変更することで、追加のランタイムチェックが有効になります。

追加されるチェックは主に以下の2点です。

1.  **既存のエントリの上書き防止**: ハフマンデコーダテーブル（`h.chunks` および `linktab`）を構築する際に、既にデータが書き込まれているエントリに誤って上書きしようとしていないかをチェックします。ハフマンテーブルの構築ロジックでは、通常、各エントリは一度だけ正確に計算されて配置されるべきであり、上書きが発生するということは、アルゴリズムに誤りがある可能性が高いことを示します。
    *   `h.chunks[reverse] != 0` のチェック: `h.chunks` 配列への書き込み時に、その位置が既に0以外の値で埋められている場合にパニックを発生させます。
    *   `linktab[off] != 0` のチェック: リンクテーブル（`linktab`）への書き込み時に、同様に既に0以外の値で埋められている場合にパニックを発生させます。

2.  **テーブルの完全性チェック**: テーブル構築プロセスの最後に、`h.chunks` および `h.links` 内のすべての必要なエントリが適切に埋められているか（つまり、0のままになっていないか）をチェックします。一部の例外（例えば、単一コードのケースで奇数チャンクが欠落している場合）を除き、テーブルが完全に埋められていない場合は、構築ロジックに問題があることを示します。
    *   `chunk == 0` のチェック: `h.chunks` と `linktab` の両方について、すべてのエントリが0でないことを確認します。0は無効なチャンク値と見なされます。

これらのチェックは、ハフマンデコーダテーブルの構築における重要な不変条件を強制します。もしこれらの不変条件が破られた場合、`panic` が発生し、プログラムの実行が停止します。これにより、開発者は問題の根本原因を特定しやすくなります。

コミットメッセージには `TODO(mdempsky): TestIssue5962 and TestIssue6255 currently fail with these enabled.` というコメントがあります。これは、この `sanity` チェックを有効にすると、既存の特定のテストケース（Issue 5962と6255に関連するもの）が失敗することを示唆しています。これは、これらのテストケースが、`sanity` チェックが検出するような、ハフマンテーブル構築の不健全な状態を意図せず許容しているか、あるいはそれらのテストケース自体が特定の不健全な入力データを使用している可能性を示しています。このコメントは、健全性チェックが単にバグを検出するだけでなく、既存のテストケースの潜在的な問題点も浮き彫りにする可能性があることを示しています。

## コアとなるコードの解説

### 1. `sanity` 定数の導入

```go
const sanity = false
```
`huffmanDecoder.init` メソッドの冒頭に `sanity` というブール定数が追加されました。デフォルト値は `false` で、これにより本番環境でのパフォーマンスオーバーヘッドを避けています。開発者がこの値を `true` に変更することで、後述の健全性チェックが有効になります。

### 2. 既存チャンク上書きチェックの追加

```go
// 最初のチャンクテーブルへの書き込み箇所
if sanity && h.chunks[reverse] != 0 {
	panic("impossible: overwriting existing chunk")
}

// 2番目のチャンクテーブルへの書き込み箇所
if sanity && h.chunks[off] != 0 {
	panic("impossible: overwriting existing chunk")
}

// リンクテーブルへの書き込み箇所
if sanity && linktab[off] != 0 {
	panic("impossible: overwriting existing chunk")
}
```
ハフマンデコーダテーブル（`h.chunks` と `linktab`）の構築中に、特定のインデックスに値を書き込む直前に、その位置が既に0以外の値で埋められているかをチェックします。もし `sanity` が `true` で、かつ既に値が存在する場合、`panic` を発生させます。これは、テーブル構築ロジックが誤って既存のエントリを上書きしようとしていることを示唆しており、ハフマンテーブルの整合性が損なわれる可能性を検出します。

### 3. 間接チャンクの健全性チェック

```go
j := reverse & (huffmanNumChunks - 1)
if sanity && h.chunks[j]&huffmanCountMask != huffmanChunkBits+1 {
	// Longer codes should have been
	// associated with a link table above.
	panic("impossible: not an indirect chunk")
}
```
これは、ハフマンコードが `huffmanChunkBits` よりも長い場合に、それが正しく間接チャンク（リンクテーブルへの参照）として扱われているかをチェックします。`h.chunks[j]` の下位ビット（`huffmanCountMask` でマスクされる部分）が `huffmanChunkBits+1` と等しくない場合、それは間接チャンクとして期待される形式ではないため、`panic` を発生させます。これは、ハフマンテーブルの構造的な不変条件を検証しています。

### 4. テーブル完全性チェックの追加

```go
if sanity {
	// Above we've sanity checked that we never overwrote
	// an existing entry.  Here we additionally check that
	// we filled the tables completely.
	for i, chunk := range h.chunks {
		if chunk == 0 {
			// As an exception, in the degenerate
			// single-code case, we allow odd
			// chunks to be missing.
			if code == 1 && i%2 == 1 {
				continue
			}
			panic("impossible: missing chunk")
		}
	}
	for _, linktab := range h.links {
		for _, chunk := range linktab {
			if chunk == 0 {
				panic("impossible: missing chunk")
			}
		}
	}
}
```
`init` メソッドの最後に、`sanity` が `true` の場合に実行される追加のループが導入されました。このループは、`h.chunks` と `h.links` のすべてのエントリを反復処理し、それらが0でないことを確認します。0は未初期化または無効なチャンク値と見なされます。

*   `h.chunks` のチェックでは、`code == 1`（単一のハフマンコードの場合）かつ `i%2 == 1`（奇数インデックス）の場合に限り、チャンクが0であっても許容するという例外処理があります。これは、特定の退化したケースでのテーブル構造の特性に対応しています。
*   `h.links` のチェックでは、すべてのリンクテーブル内のチャンクが0でないことを厳密に確認します。

これらのチェックは、ハフマンデコーダテーブルが完全に、かつ正しく構築されたことを保証するための最終的な検証ステップです。もし必要なエントリが欠落している場合、`panic` が発生し、テーブル構築ロジックの不備を指摘します。

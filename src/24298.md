## 変更の背景
このコミットは、Goの`go`コマンドにおける内部パッケージのインポートエラーに関する問題を修正します。具体的には、`go build`コマンドがパッケージの依存関係を解決する際に、`internal`パッケージの可視性ルールを誤って処理し、本来エラーとなるべき不正な内部パッケージのインポートを見逃してしまう、あるいはその逆で、正当なインポートをエラーとして扱ってしまう可能性がありました。この問題は、特に依存関係の連鎖において`internal`パッケージが関与する場合に発生する、`go`コマンドのパッケージローディングロジックの不具合に起因していました。コミットメッセージにある`Fixes #11331`は、この特定のバグ報告に対応するものであることを示しています。

## 前提知識の解説

### Goの`internal`パッケージ
Go言語には、パッケージの可視性を制限するための`internal`パッケージという特別な仕組みがあります。`internal`ディレクトリ内にあるパッケージは、その`internal`ディレクトリの親ディレクトリ内にあるコードからのみインポートが許可されます。これにより、ライブラリの内部実装の詳細が外部に漏れるのを防ぎ、APIの安定性を保つことができます。

**例:**
- `yourproject/mypackage/internal/utility`というパッケージがある場合、`yourproject/mypackage`ディレクトリ以下のパッケージ（`mypackage`自身やそのサブディレクトリ内のパッケージ）のみが`utility`をインポートできます。
- `yourproject/anotherpackage`のような、`mypackage`の外部にあるパッケージは`utility`をインポートできません。

このルールはGoツールチェインによって厳密に強制され、不正なインポートはコンパイル時にエラーとなります。

### `go build`コマンドとパッケージローディング
`go build`コマンドは、指定されたパッケージとその依存関係をコンパイルします。このプロセスの中で、`go`コマンドは`go/build`パッケージなどを使用して、ソースファイルの解析、依存関係の解決、パッケージのロードを行います。パッケージのロード時には、各パッケージのインポートパスを解決し、そのパッケージが依存する他のパッケージを特定します。この際、`internal`パッケージの可視性ルールも適用され、不正なインポートはエラーとして報告されるべきです。`go`コマンドの内部では、`Package`構造体がパッケージのメタデータや依存関係を管理し、`load`メソッドがこれらの情報を収集する役割を担っています。

## 技術的詳細
このコミットは、`src/cmd/go/pkg.go`内の`(*Package) load`メソッドにおけるパッケージ依存関係の処理ロジックの欠陥を修正します。

`(*Package) load`メソッドは、あるパッケージが依存する全てのパッケージ（直接的および間接的な依存関係）を`deps`マップに収集します。問題は、この`deps`マップにパッケージを追加する際に、既に存在するエントリを無条件に上書きしてしまう可能性があった点です。

具体的には、以下のようなシナリオで問題が発生していました。
1.  あるパッケージ`P`がパッケージ`A`をインポートし、その`A`がさらに`internal`パッケージ`X`をインポートしているとします。
2.  同時に、パッケージ`P`が別のパッケージ`B`をインポートし、その`B`も`internal`パッケージ`X`をインポートしているとします。
3.  `go`コマンドが`P`をビルドする際に、`A`の依存関係を処理する過程で`X`が`deps`マップに追加されます。このとき、`X`が`internal`パッケージであること、および`A`からのインポートが正当であるかどうかの情報が`deps`マップのエントリに含まれます。
4.  その後、`B`の依存関係を処理する際に、`X`が再度`deps`マップに追加されようとします。このとき、`deps`マップに既に`X`のエントリが存在するにもかかわらず、無条件に上書きされてしまう可能性がありました。

この上書きによって、`internal`パッケージの可視性に関するエラー情報（例えば、`P`から`X`への直接インポートが不正であるという情報）が失われたり、あるいは逆に、正当なインポートが不正なものとして扱われたりする可能性がありました。結果として、`go build`が誤った結果を返す、つまり、本来ビルドに失敗すべきコードが成功したり、その逆が発生したりする「missing internal import error」が発生していました。この修正は、`deps`マップへの追加を条件付きにすることで、この上書き問題を解決し、`internal`パッケージの可視性ルールが正しく適用されるようにします。

## コアとなるコードの解説

### `src/cmd/go/pkg.go`の変更
変更の中心は、`(*Package) load`メソッド内の`for _, dep := range p1.deps`ループ内です。このループは、あるパッケージ`p1`が依存する全てのパッケージ`dep`を`deps`マップに収集する役割を担っています。

**変更前:**
```go
			deps[dep.ImportPath] = dep
```
この行は、依存パッケージ`dep`を`deps`マップに無条件で追加または上書きしていました。もし`dep.ImportPath`が既にマップに存在する場合、そのエントリは新しい`dep`で上書きされます。この無条件の上書きが問題の原因でした。以前に`deps`マップに追加されたパッケージに関する重要な情報（特に`internal`パッケージの可視性に関するエラー情報など）が、後から追加される同じインポートパスのパッケージによって失われる可能性があったのです。

**変更後:**
```go
			// Do not overwrite entries installed by direct import
			// just above this loop. Those have stricter constraints
			// about internal and vendor visibility and may contain
			// errors that we need to preserve.
			if deps[dep.ImportPath] == nil {
				deps[dep.ImportPath] = dep
			}
```
この変更では、`deps[dep.ImportPath] = dep`の行が`if deps[dep.ImportPath] == nil`という条件文で囲まれています。これにより、`deps`マップに既にエントリが存在する場合は、そのエントリを上書きしないようになりました。

追加されたコメントは、この修正の意図を明確に説明しています。「直接インポートによってインストールされたエントリを上書きしない」ことが重要であり、それらのエントリは`internal`や`vendor`の可視性に関してより厳密な制約を持ち、保持すべきエラー情報を含んでいる可能性があるためです。この条件付きの追加により、パッケージローディングプロセスが`internal`パッケージの可視性ルールを正しく尊重し、適切なエラーを報告できるようになります。つまり、最初に`deps`マップに登録されたパッケージの情報（それが`internal`パッケージの不正なインポートであるという情報など）が、後続の処理で誤って上書きされて失われることを防ぎます。

### `src/cmd/go/go_test.go`の変更と新しいテストデータ
新しいテストケース`TestInternalCache`は、この修正が意図通りに機能することを確認するために追加されました。

`testdata/testinternal4`の構造は、前述の「技術的詳細」で説明した問題のシナリオをシミュレートしています。
- パッケージ`p`は`q/internal/x`を直接インポートしようとしています。
- `q/internal/x`は`q`ディレクトリの内部パッケージであるため、`q`ディレクトリの外部にある`p`からは直接インポートできません。

したがって、`p.go`が`q/internal/x`を直接インポートしようとしていることは不正なインポートであり、`go build p`は失敗するべきです。

`TestInternalCache`テストは、以下の手順を実行します。
1.  `GOPATH`を`testdata/testinternal4`に設定し、テスト環境を準備します。
2.  `tg.runFail("build", "p")`を実行し、`p`のビルドが失敗することを期待します。`runFail`はコマンドが非ゼロ終了コードを返すことを検証します。
3.  `tg.grepStderr("internal", "did not fail to build p")`を実行し、標準エラー出力に"internal"という文字列が含まれていることを確認します。これは、ビルド失敗の原因が`internal`パッケージの不正なインポートに関するものであることを示唆しています。もしこの文字列が見つからなければ、テストは「pのビルドに失敗しなかった」というメッセージで失敗します。

このテストは、`pkg.go`の修正がなければ、`go build p`が誤って成功してしまうケースを捕捉するために設計されています。修正によって、`go`コマンドは`q/internal/x`への不正な直接インポートを正しく検出し、ビルドを失敗させるようになります。

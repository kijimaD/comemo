# [インデックス 25163] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるStop-The-World（STW）ポーズ時間の削減を目的としています。特に、GCのマーク終了フェーズでヒープ内の使用中ページ数を計算する際の非効率なループ処理を、アクティブに維持されるカウンターに置き換えることで、大規模なヒープを持つアプリケーションのGCポーズ時間を大幅に短縮しています。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行中に不要になったメモリを自動的に解放する重要な機能です。しかし、GCの実行中には、アプリケーションの実行が一時的に停止する「Stop-The-World (STW)」と呼ばれるフェーズが存在します。このSTW時間は、アプリケーションの応答性やスループットに直接影響を与えるため、可能な限り短くすることが求められます。

このコミット以前のGoランタイムでは、GCのマーク終了（mark termination）フェーズにおいて、次のGCサイクルまでにどれだけのスイープが必要かを判断するために「スイープ比率（sweep ratio）」を計算していました。この計算には、現在使用中のメモリページ（`_MSpanInUse` 状態のスパンに属するページ）の総数を把握する必要がありました。

当時の実装では、この使用中ページ数を取得するために、ヒープ内の全てのスパン（メモリの管理単位）をループで走査し、`_MSpanInUse` 状態のスパンに属するページ数を合計していました。このループ処理は、ヒープサイズが大きくなるにつれて線形に時間がかかるという問題がありました。具体的には、ヒープサイズ1GBあたり約1ミリ秒の時間がかかり、マルチギガバイトのヒープを持つアプリケーションでは、このSTW時間が10ミリ秒を超えることも珍しくありませんでした。

このような長いSTWポーズは、特にレイテンシに敏感なサーバーアプリケーションや、大規模なデータ処理を行うアプリケーションにおいて、ユーザー体験の低下や処理性能のボトルネックとなっていました。この問題を解決し、GCポーズ時間を短縮することが、この変更の主要な動機です。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）かつ世代別ではない（non-generational）マーク＆スイープ方式を採用しています。主なフェーズは以下の通りです。

1.  **マーク開始 (Mark Start)**: 短いSTWフェーズ。GCの準備を行い、ルートオブジェクト（グローバル変数、スタック上の変数など）を特定します。
2.  **並行マーキング (Concurrent Mark)**: アプリケーションの実行と並行して、到達可能なオブジェクトをマークします。これは三色マーキングアルゴリズム（白、灰、黒）に基づいて行われます。
3.  **マーク終了 (Mark Termination)**: 短いSTWフェーズ。並行マーキング中に発生した変更を処理し、マーキングを完了させます。このフェーズで、次のGCサイクルに向けたスイープ比率の計算などが行われます。
4.  **並行スイープ (Concurrent Sweep)**: アプリケーションの実行と並行して、マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能な状態にします。

### STW (Stop-The-World)

STWは、ガベージコレクタが正確なメモリ状態を確保するために、アプリケーションの全てのゴルーチン（軽量スレッド）の実行を一時的に停止させる期間を指します。この期間中、アプリケーションは一切処理を進めることができません。STW時間が長くなると、アプリケーションの応答性が悪化し、ユーザーは「フリーズ」したように感じることがあります。GoのGCはSTW時間を最小限に抑えるように設計されていますが、完全にゼロにすることはできません。

### ヒープ (Heap)

ヒープは、プログラムが実行時に動的にメモリを割り当てる領域です。Goプログラムでは、`make` や `new` を使って作成されたオブジェクトや、関数の呼び出し間で寿命が続く可能性のあるオブジェクトがヒープに割り当てられます。GCは主にこのヒープ領域を管理します。

### スパン (Span)

Goランタイムのメモリ管理において、ヒープは「スパン（span）」と呼ばれる連続したメモリページのブロックに分割されます。スパンは、特定のサイズのオブジェクトを格納するために使用されます。`mheap` 構造体は、これらのスパンを管理する役割を担います。

*   `_MSpanInUse`: スパンの状態の一つで、現在アプリケーションによって使用されているオブジェクトを保持していることを示します。GCは、この状態のスパンが占めるページ数を把握する必要があります。

### スイープ比率 (Sweep Ratio)

スイープ比率は、GCが次のサイクルまでにどれだけのメモリをスイープ（解放）する必要があるかを決定するための指標です。この比率に基づいて、GCはメモリの割り当てとスイープのバランスを調整し、ヒープの成長を制御します。適切なスイープ比率を設定することで、GCのオーバーヘッドを抑えつつ、メモリを効率的に再利用できます。

### マーク終了 (Mark Termination)

マーク終了フェーズは、並行マーキングの最終段階であり、短いSTWポーズを伴います。このフェーズでは、並行マーキング中に発生したポインターの変更（write barrierによって記録されたもの）を処理し、全ての到達可能なオブジェクトが正しくマークされたことを確認します。また、次のGCサイクルに向けた準備として、スイープ比率の計算などが行われます。このコミットの変更は、まさにこのマーク終了フェーズにおけるパフォーマンスボトルネックを解消するものです。

## 技術的詳細

このコミットの核心は、GCのマーク終了フェーズにおける「使用中ページ数の計算」方法の変更にあります。

### 変更前の問題点

変更前は、`src/runtime/mgc.go` 内の `gcSweep` 関数が、スイープ比率を計算するために使用中ページ数を取得していました。この処理は、以下のようなループで行われていました。

```go
// Account how much sweeping needs to be done before the next
// GC cycle and set up proportional sweep statistics.
var pagesToSweep uintptr
for _, s := range work.spans {
    if s.state == mSpanInUse {
        pagesToSweep += s.npages
    }
}
```

このコードは、`work.spans` という全てのスパンのリストを走査し、各スパンの `state` が `mSpanInUse` である場合にそのスパンのページ数 (`s.npages`) を `pagesToSweep` に加算していました。

このアプローチの問題点は、ヒープサイズが大きくなり、管理されるスパンの数が増えるにつれて、このループの実行時間が線形に増加することです。コミットメッセージにもあるように、「~1ms/heap GB」というパフォーマンス特性は、マルチギガバイトのヒープではSTWポーズ時間を許容できないレベルまで押し上げていました。

### 解決策：アクティブなカウンターの導入

この問題を解決するため、コミットでは `mheap` 構造体に `pagesInUse` という新しいフィールドを追加し、このカウンターをメモリの割り当てと解放の際に常に最新の状態に保つようにしました。

1.  **`mheap` 構造体への `pagesInUse` フィールドの追加**:
    `src/runtime/mheap.go` 内の `mheap` 構造体に `pagesInUse` フィールドが追加されました。

    ```go
    type mheap struct {
        // ...
        // Proportional sweep
        pagesInUse        uint64  // pages of spans in stats _MSpanInUse; R/W with mheap.lock
        spanBytesAlloc    uint64  // bytes of spans allocated this cycle; updated atomically
        pagesSwept        uint64  // pages swept this cycle; updated atomically
        sweepPagesPerByte float64 // proportional sweep ratio; written with lock, read without
        // TODO(austin): pagesInUse should be a uintptr, but the 386
        // compiler can't 8-byte align fields.
        // ...
    }
    ```
    `pagesInUse` は `_MSpanInUse` 状態のスパンに属するページ数を表し、`mheap.lock` で保護されます。`uint64` 型であることについて、386コンパイラの制約により `uintptr` にできないという `TODO` コメントがあります。

2.  **メモリ割り当て時の `pagesInUse` の更新**:
    新しいスパンが割り当てられ、`_MSpanInUse` 状態になる際に、`pagesInUse` カウンターが増加するように変更されました。これは主に `mHeap_Alloc_m` 関数と `mHeap_Grow` 関数で行われます。

    *   `mHeap_Alloc_m`: オブジェクトの割り当て時にスパンが使用中になった場合。
    *   `mHeap_Grow`: ヒープが拡張され、新しいメモリページが取得されてスパンとして使用中になった場合。

3.  **メモリ解放時の `pagesInUse` の更新**:
    スパンが解放され、`_MSpanInUse` 状態から別の状態（例えば `_MSpanFree`）に遷移する際に、`pagesInUse` カウンターが減少するように変更されました。これは `mHeap_FreeSpanLocked` 関数で行われます。

### `gcSweep` 関数での変更

`gcSweep` 関数では、もはやスパンをループしてページ数を数える必要がなくなりました。代わりに、`mheap_.pagesInUse` を直接参照してスイープ比率を計算します。

```go
// Concurrent sweep needs to sweep all of the in-use pages by
// the time the allocated heap reaches the GC trigger. Compute
// the ratio of in-use pages to sweep per byte allocated.
// ...
lock(&mheap_.lock)
mheap_.sweepPagesPerByte = float64(mheap_.pagesInUse) / float64(heapDistance)
mheap_.pagesSwept = 0
mheap_.spanBytesAlloc = 0
unlock(&mheap_.lock)
```

### パフォーマンス改善

この変更により、マーク終了フェーズでのSTWポーズ時間が劇的に短縮されました。コミットメッセージに示されているベンチマーク結果は以下の通りです。

| Heap | Procs | after change | before change | 1.5.1 |
| :--- | :---- | :----------- | :------------ | :---- |
| 24GB | 12    | 1.9ms        | 18ms          | 37ms  |
| 24GB | 4     | 3.7ms        | 18ms          | 37ms  |
| 4GB  | 4     | 920µs        | 3.8ms         | 6.9ms |

*   **24GBヒープ**: 最大マーク終了ポーズ時間が、変更前の18msから1.9ms（12プロセッサの場合）または3.7ms（4プロセッサの場合）へと、75%〜90%削減されています。Go 1.5.1と比較すると85%〜95%の削減です。
*   **4GBヒープ**: 最大マーク終了ポーズ時間が、変更前の3.8msから920µsへと、大幅に短縮されています。

この改善により、大規模ヒープにおける最長ポーズ時間は、マーク終了フェーズからスイープ終了フェーズへと移行しました。結果として、最大ポーズ時間全体の削減はわずかですが、平均ポーズ時間は約半分に減少しています。これは、GCの安定性と予測可能性を向上させる上で非常に重要な改善です。

## コアとなるコードの解説

### `src/runtime/mgc.go` の `gcSweep` 関数

変更前は、`gcSweep` 関数内で `pagesToSweep` 変数を初期化し、`work.spans` の各スパンを反復処理して `_MSpanInUse` 状態のスパンのページ数を合計していました。

```go
// 削除されたコード
var pagesToSweep uintptr
for _, s := range work.spans {
    if s.state == mSpanInUse {
        pagesToSweep += s.npages
    }
}
mheap_.sweepPagesPerByte = float64(pagesToSweep) / float64(heapDistance)
```

このループが削除され、代わりに `mheap_` グローバル変数（`mheap` 型のインスタンス）に新しく追加された `pagesInUse` フィールドが直接参照されるようになりました。

```go
// 変更後のコード
mheap_.sweepPagesPerByte = float64(mheap_.pagesInUse) / float64(heapDistance)
```

これにより、マーク終了フェーズでの計算が定数時間（O(1)）で行われるようになり、ヒープサイズに依存するパフォーマンスボトルネックが解消されました。

### `src/runtime/mheap.go` の `mheap` 構造体と関連関数

1.  **`mheap` 構造体への `pagesInUse` フィールド追加**:
    `mheap` 構造体はGoランタイムのヒープ管理の中核をなすデータ構造です。ここに `pagesInUse uint64` フィールドが追加されました。このフィールドは、現在 `_MSpanInUse` 状態にあるスパンが占める総ページ数を常に保持します。`mheap.lock` によって保護され、並行アクセス時のデータ競合を防ぎます。

2.  **`mHeap_Alloc_m` 関数での更新**:
    この関数は、新しいメモリをヒープから割り当てる際に呼び出されます。スパンが割り当てられ、`_MSpanInUse` 状態になると、そのスパンのページ数 (`npage`) が `h.pagesInUse` に加算されます。

    ```go
    // 変更後のコード (mHeap_Alloc_m 内)
    h.pagesInUse += uint64(npage)
    ```

3.  **`mHeap_Grow` 関数での更新**:
    この関数は、ヒープのサイズを拡張する必要がある場合に、オペレーティングシステムから新しいメモリページを取得し、それをスパンとしてヒープに追加します。新しく取得されたページが `_MSpanInUse` 状態としてマークされる際に、そのページ数 (`npage`) が `h.pagesInUse` に加算されます。

    ```go
    // 変更後のコード (mHeap_Grow 内)
    s.state = _MSpanInUse
    h.pagesInUse += uint64(npage)
    ```

4.  **`mHeap_FreeSpanLocked` 関数での更新**:
    この関数は、スパンが解放される際に呼び出されます。スパンが `_MSpanInUse` 状態から解放される場合、そのスパンのページ数 (`s.npages`) が `h.pagesInUse` から減算されます。

    ```go
    // 変更後のコード (mHeap_FreeSpanLocked 内)
    h.pagesInUse -= uint64(s.npages)
    ```

これらの変更により、`mheap.pagesInUse` は常に正確な使用中ページ数を反映するようになり、GCのマーク終了フェーズで高コストなループ処理を行う必要がなくなりました。

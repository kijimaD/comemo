# [インデックス 23776] ファイルの概要

このコミットは、Go言語の `archive/tar` パッケージにおける `PAX` (POSIX.1-2001) 拡張ヘッダーのパース処理に存在した「slice bounds out of range」の脆弱性を修正するものです。具体的には、PAXヘッダー内のサイズフィールドが不正な値を持つ場合に発生する可能性のあるパニックを防ぐため、サイズフィールドの健全性チェックが追加されました。これにより、悪意を持って細工されたtarアーカイブによるサービス拒否攻撃などのリスクが軽減されます。

## 変更の背景

この変更は、Go言語の `archive/tar` パッケージが、不正に細工された `PAX` (POSIX.1-2001) 拡張ヘッダーを持つtarアーカイブを処理する際に発生する可能性のある「slice bounds out of range」エラーを修正するために行われました。

具体的には、PAXヘッダーは `サイズ キー=値\n` の形式で情報を格納しますが、この `サイズ` フィールドが悪意を持って非常に大きな値に設定された場合、`parsePAX` 関数がそのサイズに基づいてスライス操作を行おうとすると、メモリ上の不正な領域にアクセスしようとしてパニック（プログラムのクラッシュ）を引き起こす可能性がありました。これはサービス拒否（DoS）攻撃につながるセキュリティ上の脆弱性となり得ます。

Go issue #11167 でこの問題が報告され、PAXヘッダーのサイズフィールドを使用する前に、その値が妥当な範囲内にあるかどうかの健全性チェックを追加する必要性が認識されました。このコミットは、その健全性チェックを実装し、潜在的な脆弱性を解消することを目的としています。

## 前提知識の解説

### `archive/tar` パッケージ

`archive/tar` はGo言語の標準ライブラリの一部で、tarアーカイブ（テープアーカイブ）の読み書きをサポートします。tarファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式であり、Unix系システムで広く利用されています。このパッケージは、tarファイルのヘッダー情報の解析や、ファイルデータの抽出・書き込み機能を提供します。

### PAX (POSIX.1-2001) 拡張ヘッダー

従来のtar形式には、ファイル名やユーザー名などのフィールド長に制限がありました。これを解決するために、POSIX.1-2001標準で `PAX` (Portable Archive eXchange) 拡張ヘッダーが導入されました。PAXヘッダーは、キーと値のペアの形式で追加のメタデータ（長いファイル名、高精度なタイムスタンプ、任意の属性など）を格納できます。

PAXヘッダーのエントリは、`サイズ キー=値\n` という形式で表現されます。
*   `サイズ`: エントリ全体のバイト長（サイズ、スペース、キー、イコール、値、改行文字を含む）。これは10進数で表現されます。
*   `キー`: メタデータの名前（例: `path`, `mtime`）。
*   `値`: メタデータの値。

`archive/tar` パッケージは、このPAXヘッダーを解析して、アーカイブ内のエントリに関する拡張情報を取得します。

### `slice bounds out of range` エラー

Go言語における「slice bounds out of range」は、スライス操作（インデックスアクセスやスライス作成）において、指定されたインデックスがスライスの有効範囲外である場合に発生するランタイムパニックです。例えば、長さが5のスライスに対してインデックス `[5]` や `[-1]` でアクセスしようとするとこのエラーが発生します。これは通常、プログラミングミスによって引き起こされますが、外部からの入力（このケースではPAXヘッダーのサイズフィールド）が不正な場合に、意図しないインデックスアクセスを引き起こし、セキュリティ上の脆弱性となることがあります。

### `strconv.ParseInt` 関数

`strconv.ParseInt` は、Go言語の標準ライブラリ `strconv` パッケージに含まれる関数で、文字列を整数型に変換するために使用されます。
`func ParseInt(s string, base int, bitSize int) (int64, error)`
*   `s`: 変換する文字列。
*   `base`: 基数（例: 10進数の場合は10）。
*   `bitSize`: 結果の整数型が占めるビット数（例: 0を指定すると `int` 型のデフォルトサイズ）。

この関数は、変換された `int64` 値と、エラーが発生した場合は `error` を返します。エラーには、文字列が有効な数値でない場合や、指定された `bitSize` に収まらない場合などが含まれます。

## 技術的詳細

`archive/tar` パッケージの `parsePAX` 関数は、PAX拡張ヘッダーを読み取り、その内容をマップとして解析する役割を担っています。PAXヘッダーの各エントリは `サイズ キー=値\n` の形式で、まず `サイズ` フィールドを読み取り、そのサイズに基づいて後続の `キー=値\n` 部分を読み込む必要があります。

このコミット以前のコードでは、`parsePAX` 関数内で `strconv.ParseInt` を使用して `サイズ` フィールド（文字列）を整数 `n` に変換していました。しかし、この `n` の値が非常に大きい場合、例えば `int64(len(buf)) < n` となるような不正な値であったとしても、その後のスライス操作 `buf[:sp]` や `buf[sp+1:n-1]` などで `n` がそのまま使用されていました。

具体的には、`n` が `buf` の実際の長さよりも大きい場合、`buf[:n]` のような操作は「slice bounds out of range」パニックを引き起こします。悪意のある攻撃者は、この脆弱性を利用して、非常に大きな `サイズ` を持つPAXヘッダーをtarアーカイブに挿入することで、tarアーカイブを処理するGoプログラムをクラッシュさせ、サービス拒否状態に陥れることが可能でした。

このコミットでは、`strconv.ParseInt` で `n` をパースした後、以下の2つの健全性チェックを追加することでこの問題を解決しています。

1.  `n < 5`: PAXヘッダーの最小有効長は5バイト（例: `1 a=\n`）。これより小さい場合は不正と判断します。
2.  `int64(len(buf)) < n`: 読み込んだバッファ `buf` の実際の長さが、PAXヘッダーが主張する `n` バイトよりも小さい場合、これは不正なヘッダーであると判断します。

これらのチェックにより、`n` が不正な値である場合には `ErrHeader` を返すようになり、後続の危険なスライス操作が実行される前にエラーが適切に処理されるようになりました。これにより、Goプログラムが不正なtarアーカイブによってクラッシュするリスクが排除されます。

テストコードの変更では、この修正が正しく機能することを確認するために、不正なPAXヘッダーのテストケースが追加されています。具体的には、`"3 somelongkey=\n"` のようにサイズが小さいにも関わらずキーが長いケースや、`"50 tooshort=\n"` のようにサイズが非常に大きいにも関わらず実際のデータが短いケースが追加され、これらが `ErrHeader` を返すことを検証しています。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の変更

`parsePAX` 関数内の以下の行が変更されました。

```go
-		if err != nil {
+		if err != nil || n < 5 || int64(len(buf)) < n {
```

元のコードでは、`strconv.ParseInt` がエラーを返した場合のみ `ErrHeader` を返していました。
変更後のコードでは、以下の2つの条件が追加されています。

1.  `n < 5`: パースされたサイズ `n` が5未満の場合。PAXヘッダーの最小有効長は `1 a=\n` の5バイトであるため、これより小さい値は不正と判断されます。
2.  `int64(len(buf)) < n`: 読み込んだバッファ `buf` の実際の長さ (`len(buf)`) が、PAXヘッダーが主張するサイズ `n` よりも小さい場合。これは、ヘッダーが自身のサイズを偽っていることを意味し、後続のスライス操作で「slice bounds out of range」パニックを引き起こす可能性があるため、不正と判断されます。

これらの追加された健全性チェックにより、`n` が不正な値である場合に早期にエラーを検出し、`ErrHeader` を返すことで、プログラムのクラッシュを防ぎます。

### `src/archive/tar/reader_test.go` の変更

テストファイルでは、`TestParsePAXHeader` 関数に不正なPAXヘッダーをテストするための新しいテストケースが追加されました。

元のコードでは、単一の `badHeader` テストケース (`"3 somelongkey="`) がありました。
変更後、`badHeaderTests` というスライスが導入され、複数の不正なヘッダーパターンをテストできるようになりました。

```go
	badHeaderTests := [][]byte{
		[]byte("3 somelongkey=\n"),
		[]byte("50 tooshort=\n"),
	}
	for _, test := range badHeaderTests {
		if _, err := parsePAX(bytes.NewReader(test)); err != ErrHeader {
			t.Fatal("Unexpected success when parsing bad header")
		}
	}
```

*   `[]byte("3 somelongkey=\n")`: このテストケースは、PAXヘッダーが主張するサイズが `3` であるにもかかわらず、実際のキーと値のペア (`somelongkey=`) がそれよりも長い場合をシミュレートしています。この場合、`int64(len(buf)) < n` の条件が満たされ、`ErrHeader` が返されることを期待します。
*   `[]byte("50 tooshort=\n")`: このテストケースは、PAXヘッダーが主張するサイズが `50` と非常に大きいにもかかわらず、実際のデータ (`tooshort=`) が短い場合をシミュレートしています。これも同様に `int64(len(buf)) < n` の条件が満たされ、`ErrHeader` が返されることを期待します。

これらのテストケースの追加により、`parsePAX` 関数が不正なPAXヘッダーに対して正しく `ErrHeader` を返すことを確認し、修正が意図通りに機能していることを保証しています。

# [インデックス 21229] ファイルの概要

このコミットは、Goランタイムにおけるファイナライザのイテレータが、複数のファイナライザを正しく処理できないバグを修正するものです。具体的には、`runtime.SetFinalizer`によって登録されたファイナライザが複数存在する場合に、ヒープダンプの生成時（`debug.WriteHeapDump`）に範囲外エラー（out-of-bounds error）が発生する問題を解決します。この修正により、Goプログラムが複数のファイナライザを持つオブジェクトを安定して扱えるようになります。

## 変更の背景

このコミットは、Goランタイムにおけるファイナライザの処理に関するバグ（Issue #9172）を修正するために行われました。以前の実装では、`runtime.SetFinalizer` を使用して複数のオブジェクトにファイナライザが設定され、それらのオブジェクトがガベージコレクションの対象となった場合、ヒープダンプ（`debug.WriteHeapDump`）の処理中にランタイムがクラッシュする可能性がありました。具体的には、ファイナライザを管理するための内部データ構造が、複数のファイナライザを適切に格納・イテレートできるように設計されていなかったため、2つ目以降のファイナライザを処理しようとすると範囲外アクセスが発生していました。

この問題は、Goプログラムがファイナライザを多用するシナリオ、特にリソースのクリーンアップやデバッグ目的でヒープダンプを生成する際に、深刻な安定性の問題を引き起こす可能性がありました。この修正は、Goランタイムの堅牢性を向上させ、ファイナライザの利用をより安全にするために不可欠でした。

## 前提知識の解説

### Goのファイナライザ (`runtime.SetFinalizer`)

Go言語には、オブジェクトがガベージコレクタによってメモリから解放される直前に特定の関数を実行するための「ファイナライザ」というメカニズムがあります。これは `runtime.SetFinalizer(obj, finalizerFunc)` 関数を使って設定されます。

*   **`obj`**: ファイナライザを設定する対象のオブジェクト。
*   **`finalizerFunc`**: `func(obj *Type)` の形式を持つ関数。`obj` がガベージコレクションの対象となり、到達不可能になったと判断された後、この関数が実行されます。

ファイナライザは、ファイルハンドル、ネットワーク接続、C言語のライブラリによって確保されたメモリなど、Goのガベージコレクタが直接管理できない外部リソースをクリーンアップする際に役立ちます。ただし、ファイナライザの実行タイミングはガベージコレクタに依存するため、予測が難しく、デッドロックやパフォーマンスの問題を引き起こす可能性があるため、慎重に使用する必要があります。

### Goのガベージコレクション (GC)

Goランタイムは、自動メモリ管理（ガベージコレクション）を採用しています。プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったオブジェクトを自動的に識別し、そのメモリを再利用可能にします。GoのGCは並行・並行（concurrent and parallel）に動作し、プログラムの実行を長時間停止させることなくメモリを回収しようとします。

ファイナライザは、GCがオブジェクトを回収するプロセスの一部として実行されます。オブジェクトが到達不可能と判断されると、そのオブジェクトにファイナライザが設定されていれば、GCはファイナライザをキューに入れ、後で専用のゴルーチンによって実行されます。

### `debug.WriteHeapDump`

`runtime/debug` パッケージは、Goプログラムのデバッグに役立つ機能を提供します。`debug.WriteHeapDump(fd uintptr)` 関数は、現在のGoプロセスのヒープの状態をファイルにダンプします。このダンプファイルは、Goのツール（例: `go tool pprof`）を使って解析することで、メモリリークの特定やメモリ使用量の最適化に役立てることができます。

ヒープダンプの生成時には、ランタイムはメモリ上のすべてのオブジェクト、それらの参照関係、そしてファイナライザが設定されているオブジェクトに関する情報も収集します。このコミットで修正されたバグは、この情報収集の過程でファイナライザのリストをイテレートする際に発生していました。

### `finblock` 構造体とファイナライザの管理

Goランタイム内部では、ファイナライザは `finblock` と呼ばれる構造体を使って管理されています。`finblock` は、複数の `finalizer` 構造体を保持できるブロックであり、ファイナライザの情報を効率的に格納するために使用されます。`finalizer` 構造体は、ファイナライザ関数自体、その引数、および関連するオブジェクトへのポインタなどの情報を含んでいます。

`queuefinalizer` 関数は、オブジェクトにファイナライザが設定され、そのオブジェクトがGCによって回収される準備ができたときに呼び出され、ファイナライザをキューに追加する役割を担います。

### `unsafe` パッケージ

`unsafe` パッケージは、Goの型安全性をバイパスする低レベルな操作を可能にします。`unsafe.Pointer` は任意の型のポインタを保持でき、`unsafe.Sizeof` は型のメモリサイズをバイト単位で返します。これらは通常、Goランタイムのような非常に低レベルなコードや、特定のパフォーマンス最適化が必要な場合にのみ使用されます。このコミットでは、`finblock` 構造体内のファイナライザ配列のサイズを計算するために使用されていました。

## 技術的詳細

このコミットの技術的詳細は、主にGoランタイムがファイナライザを内部的にどのように管理しているか、そしてその管理方法の欠陥をどのように修正したかにあります。

以前の実装では、`finblock` 構造体はファイナライザを格納するための固定サイズの配列 `fin [1]finalizer` を持っていました。しかし、この配列のサイズは実際には `_FinBlockSize` という定数に基づいて動的に計算されるべきものでした。`fin [1]finalizer` という宣言は、コンパイラに対して `fin` が1つのファイナライザしか保持できないことを示唆しており、これが複数のファイナライザをキューに入れようとしたときに問題を引き起こしていました。

また、`finblock` 構造体には `cap` というフィールドがあり、これはその `finblock` が保持できるファイナライザの最大容量を示すものでした。しかし、この `cap` フィールドの計算と使用方法に誤りがあり、特に `queuefinalizer` 関数内で `finq.cnt == finq.cap` という条件でブロックが満杯かどうかをチェックする際に、正しい容量が反映されていませんでした。

このコミットでは、以下の主要な変更によってこの問題が解決されました。

1.  **`finblock` 構造体の `fin` フィールドの修正**:
    `src/runtime/malloc2.go` において、`finblock` 構造体の `fin` フィールドの宣言が `[1]finalizer` から `[(_FinBlockSize-2*ptrSize-2*4)/unsafe.Sizeof(finalizer{})]finalizer` に変更されました。これにより、`fin` 配列は `_FinBlockSize` に基づいてコンパイル時に正しいサイズを持つようになり、1つ以上のファイナライザを格納できるようになりました。
    *   `_FinBlockSize`: ファイナライザブロックの総サイズ（バイト単位）。
    *   `2*ptrSize`: `alllink` と `next` ポインタのサイズ。
    *   `2*4`: `cnt` と `_` (パディング) のサイズ。
    *   `unsafe.Sizeof(finalizer{})`: `finalizer` 構造体1つあたりのサイズ。
    この計算により、`finblock` が実際に保持できるファイナライザの数が正確に反映されるようになりました。

2.  **`finblock` 構造体からの `cap` フィールドの削除**:
    `finblock` から `cap` フィールドが削除され、その代わりにパディングのための `_ int32` が追加されました。これは、`fin` 配列の実際の容量が `len(finq.fin)` で直接取得できるようになったため、`cap` フィールドが不要になったことを意味します。

3.  **`queuefinalizer` 関数のロジック修正**:
    `src/runtime/mgc.go` において、`queuefinalizer` 関数内のファイナライザブロックが満杯かどうかをチェックする条件が `finq.cnt == finq.cap` から `finq.cnt == int32(len(finq.fin))` に変更されました。これにより、`fin` 配列の実際の容量に基づいて正確に満杯状態を判断できるようになりました。
    また、`finc.cap = ...` の行が削除されました。これは `cap` フィールドがなくなったためです。
    さらに、ファイナライザを `fin` 配列に追加する際のポインタ計算が `add(unsafe.Pointer(&finq.fin[0]), uintptr(finq.cnt)*unsafe.Sizeof(finq.fin[0]))` から `&finq.fin[finq.cnt]` に簡略化されました。これは、`finq.fin` がもはや固定サイズの配列ではなく、Goの配列スライスとして扱えるようになったため、より慣用的なGoのインデックスアクセスが可能になったことを示しています。

これらの変更により、Goランタイムは複数のファイナライザを正しく管理し、ヒープダンプ生成時にも範囲外エラーを発生させることなく、安定して動作するようになりました。

*   **`obj`**: ファイナライザを設定する対象のオブジェクト。
*   **`finalizerFunc`**: `func(obj *Type)` の形式を持つ関数。`obj` がガベージコレクションの対象となり、到達不可能になったと判断された後、この関数が実行されます。

ファイナライザは、ファイルハンドル、ネットワーク接続、C言語のライブラリによって確保されたメモリなど、Goのガベージコレクタが直接管理できない外部リソースをクリーンアップする際に役立ちます。ただし、ファイナライザの実行タイミングはガベージコレクタに依存するため、予測が難しく、デッドロックやパフォーマンスの問題を引き起こす可能性があるため、慎重に使用する必要があります。

### Goのガベージコレクション (GC)

Goランタイムは、自動メモリ管理（ガベージコレクション）を採用しています。プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったオブジェクトを自動的に識別し、そのメモリを再利用可能にします。GoのGCは並行・並行（concurrent and parallel）に動作し、プログラムの実行を長時間停止させることなくメモリを回収しようとします。

ファイナライザは、GCがオブジェクトを回収するプロセスの一部として実行されます。オブジェクトが到達不可能と判断されると、そのオブジェクトにファイナライザが設定されていれば、GCはファイナライザをキューに入れ、後で専用のゴルーチンによって実行されます。

### `debug.WriteHeapDump`

`runtime/debug` パッケージは、Goプログラムのデバッグに役立つ機能を提供します。`debug.WriteHeapDump(fd uintptr)` 関数は、現在のGoプロセスのヒープの状態をファイルにダンプします。このダンプファイルは、Goのツール（例: `go tool pprof`）を使って解析することで、メモリリークの特定やメモリ使用量の最適化に役立てることができます。

ヒープダンプの生成時には、ランタイムはメモリ上のすべてのオブジェクト、それらの参照関係、そしてファイナライザが設定されているオブジェクトに関する情報も収集します。このコミットで修正されたバグは、この情報収集の過程でファイナライザのリストをイテレートする際に発生していました。

### `finblock` 構造体とファイナライザの管理

Goランタイム内部では、ファイナライザは `finblock` と呼ばれる構造体を使って管理されています。`finblock` は、複数の `finalizer` 構造体を保持できるブロックであり、ファイナライザの情報を効率的に格納するために使用されます。`finalizer` 構造体は、ファイナライザ関数自体、その引数、および関連するオブジェクトへのポインタなどの情報を含んでいます。

`queuefinalizer` 関数は、オブジェクトにファイナライザが設定され、そのオブジェクトがGCによって回収される準備ができたときに呼び出され、ファイナライザをキューに追加する役割を担います。

### `unsafe` パッケージ

`unsafe` パッケージは、Goの型安全性をバイパスする低レベルな操作を可能にします。`unsafe.Pointer` は任意の型のポインタを保持でき、`unsafe.Sizeof` は型のメモリサイズをバイト単位で返します。これらは通常、Goランタイムのような非常に低レベルなコードや、特定のパフォーマンス最適化が必要な場合にのみ使用されます。このコミットでは、`finblock` 構造体内のファイナライザ配列のサイズを計算するために使用されていました。

## 技術的詳細

このコミットの技術的詳細は、主にGoランタイムがファイナライザを内部的にどのように管理しているか、そしてその管理方法の欠陥をどのように修正したかにあります。

以前の実装では、`finblock` 構造体はファイナライザを格納するための固定サイズの配列 `fin [1]finalizer` を持っていました。しかし、この配列のサイズは実際には `_FinBlockSize` という定数に基づいて動的に計算されるべきものでした。`fin [1]finalizer` という宣言は、コンパイラに対して `fin` が1つのファイナライザしか保持できないことを示唆しており、これが複数のファイナライザをキューに入れようとしたときに問題を引き起こしていました。

また、`finblock` 構造体には `cap` というフィールドがあり、これはその `finblock` が保持できるファイナライザの最大容量を示すものでした。しかし、この `cap` フィールドの計算と使用方法に誤りがあり、特に `queuefinalizer` 関数内で `finq.cnt == finq.cap` という条件でブロックが満杯かどうかをチェックする際に、正しい容量が反映されていませんでした。

このコミットでは、以下の主要な変更によってこの問題が解決されました。

1.  **`finblock` 構造体の `fin` フィールドの修正**:
    `src/runtime/malloc2.go` において、`finblock` 構造体の `fin` フィールドの宣言が `[1]finalizer` から `[(_FinBlockSize-2*ptrSize-2*4)/unsafe.Sizeof(finalizer{})]finalizer` に変更されました。これにより、`fin` 配列は `_FinBlockSize` に基づいてコンパイル時に正しいサイズを持つようになり、1つ以上のファイナライザを格納できるようになりました。
    *   `_FinBlockSize`: ファイナライザブロックの総サイズ（バイト単位）。
    *   `2*ptrSize`: `alllink` と `next` ポインタのサイズ。
    *   `2*4`: `cnt` と `_` (パディング) のサイズ。
    *   `unsafe.Sizeof(finalizer{})`: `finalizer` 構造体1つあたりのサイズ。
    この計算により、`finblock` が実際に保持できるファイナライザの数が正確に反映されるようになりました。

2.  **`finblock` 構造体からの `cap` フィールドの削除**:
    `finblock` から `cap` フィールドが削除され、その代わりにパディングのための `_ int32` が追加されました。これは、`fin` 配列の実際の容量が `len(finq.fin)` で直接取得できるようになったため、`cap` フィールドが不要になったことを意味します。

3.  **`queuefinalizer` 関数のロジック修正**:
    `src/runtime/mgc.go` において、`queuefinalizer` 関数内のファイナライザブロックが満杯かどうかをチェックする条件が `finq.cnt == finq.cap` から `finq.cnt == int32(len(finq.fin))` に変更されました。これにより、`fin` 配列の実際の容量に基づいて正確に満杯状態を判断できるようになりました。
    また、`finc.cap = ...` の行が削除されました。これは `cap` フィールドがなくなったためです。
    さらに、ファイナライザを `fin` 配列に追加する際のポインタ計算が `add(unsafe.Pointer(&finq.fin[0]), uintptr(finq.cnt)*unsafe.Sizeof(finq.fin[0]))` から `&finq.fin[finq.cnt]` に簡略化されました。これは、`finq.fin` がもはや固定サイズの配列ではなく、Goの配列スライスとして扱えるようになったため、より慣用的なGoのインデックスアクセスが可能になったことを示しています。

これらの変更により、Goランタイムは複数のファイナライザを正しく管理し、ヒープダンプ生成時にも範囲外エラーを発生させることなく、安定して動作するようになりました。

## コアとなるコードの解説

### `src/runtime/debug/heapdump_test.go` の変更

追加された `TestWriteHeapDumpFinalizers` は、このバグの再現と修正の検証に不可欠です。
```go
type Obj struct {
       x, y int
}

func objfin(x *Obj) {
       println("finalized", x)
}

func TestWriteHeapDumpFinalizers(t *testing.T) {
    // ... (skip NaCl check and file setup)

    // bug 9172: WriteHeapDump couldn't handle more than one finalizer
    println("allocating objects")
    x := &Obj{}
    runtime.SetFinalizer(x, objfin) // 1つ目のファイナライザを設定
    y := &Obj{}
    runtime.SetFinalizer(y, objfin) // 2つ目のファイナライザを設定

    // Trigger collection of x and y, queueing of their finalizers.
    println("starting gc")
    runtime.GC() // GCを実行し、ファイナライザをキューに入れる

    // Make sure WriteHeapDump doesn't fail with multiple queued finalizers.
    println("starting dump")
    WriteHeapDump(f.Fd()) // ヒープダンプを生成
    println("done dump")
}
```
このテストは、`Obj` 型の2つのインスタンス `x` と `y` を作成し、それぞれに同じファイナライザ関数 `objfin` を設定します。その後、`runtime.GC()` を呼び出してガベージコレクションを強制的に実行し、`x` と `y` が回収され、それらのファイナライザがキューに入れられるようにします。最後に `WriteHeapDump(f.Fd())` を呼び出し、複数のファイナライザがキューにある状態でヒープダンプが正常に生成されることを確認します。以前のバージョンでは、この `WriteHeapDump` の呼び出しでクラッシュが発生していました。

# [インデックス 22931] ファイルの概要

## コミット

このコミットは、Goリンカー (`cmd/6l`) が共有ライブラリやアーカイブをビルドする際に、Goランタイムの `runtime.addmoduledata` 関数をELF形式の `.init_array` セクションから呼び出すように変更するものです。これにより、動的にロードされるGoモジュールの初期化が、標準的なシステム初期化メカニズムに統合されます。

## 変更の背景

Goプログラムが共有ライブラリ（`.so`ファイル）やアーカイブ（`.a`ファイル）としてビルドされる場合、そのライブラリがロードされた際にGoランタイムが自身のモジュールデータを適切に初期化する必要があります。以前のGoのバージョンでは、この初期化プロセスが標準的なシステム初期化メカニズム（特にELF形式の `.init_array` セクション）と完全に統合されていませんでした。

このコミットの目的は、Goのモジュールデータ初期化関数である `runtime.addmoduledata` を、リンカーが生成する `.init_array` エントリを通じて呼び出すようにすることです。これにより、Goの共有ライブラリがロードされた際に、OSのローダーによって自動的に `runtime.addmoduledata` が実行され、Goランタイムがそのモジュールに関する情報を正しく登録できるようになります。これは、特にC/C++などの他の言語とGoを組み合わせたアプリケーションにおいて、Goの共有ライブラリがよりシームレスに動作するために重要です。

具体的には、Goのランタイムは、プログラムの実行に必要なメタデータ（型情報、シンボルテーブル、GC情報など）を `moduledata` 構造体として管理しています。複数のGoモジュールが動的にロードされる場合、それぞれの `moduledata` をランタイムに登録する必要があります。`.init_array` を利用することで、この登録プロセスがOSレベルで保証され、Goランタイムがすべてのモジュールデータを適切に認識できるようになります。

## 前提知識の解説

### Goのモジュールデータ (`moduledata`)

Goランタイムは、実行中のGoプログラムに関する様々なメタデータを `moduledata` という構造体で管理しています。これには、プログラム内の関数、型、グローバル変数、スタックマップ、ガベージコレクションに必要な情報などが含まれます。Goプログラムがコンパイルされると、この `moduledata` が生成され、実行ファイルに埋め込まれます。複数のGoモジュールが動的にリンクされる場合、それぞれのモジュールが独自の `moduledata` を持ち、これらをランタイムに登録する必要があります。`runtime.firstmoduledata` は最初のモジュールデータを指し、`moduledata` 構造体内の `next` フィールドが次のモジュールデータを指すことで、リンクリストが形成されます。

### `.init_array` セクション

`.init_array` は、ELF (Executable and Linkable Format) 形式の実行ファイルや共有ライブラリに存在する特殊なセクションです。このセクションには、プログラムの `main` 関数が実行される前に、OSのローダーによって自動的に呼び出されるべき初期化関数のポインタのリストが格納されています。C++のグローバルオブジェクトのコンストラクタなどがこのメカニズムを利用して初期化されます。共有ライブラリがロードされる際にも、そのライブラリ内の `.init_array` に登録された関数が実行されます。

### 動的リンクと共有ライブラリ

動的リンクとは、プログラムの実行時に必要なライブラリをロードする方式です。これにより、ディスクスペースの節約、メモリ使用量の削減、ライブラリの更新の容易さといった利点があります。共有ライブラリ（Linuxでは `.so`、Windowsでは `.dll`、macOSでは `.dylib`）は、複数のプログラムで共有されるコードやデータを含んでいます。Goプログラムを共有ライブラリとしてビルドする場合、そのライブラリがロードされた際にGoランタイムの初期化処理が適切に行われる必要があります。

### Goリンカ (`cmd/6l`)

`cmd/6l` は、Goのビルドツールチェーンの一部であり、Goのソースコードから実行可能なバイナリやライブラリを生成するリンカーです（`6l` はAMD64アーキテクチャ向けのリンカーを指します）。リンカーは、コンパイルされたオブジェクトファイル（`.o`）を結合し、シンボルを解決し、最終的な実行ファイルを生成する役割を担います。このコミットでは、リンカーが `.init_array` セクションにGoランタイムの初期化関数への呼び出しを追加するロジックが変更されています。

### `runtime.addmoduledata`

`runtime.addmoduledata` はGoランタイム内部の関数で、新しい `moduledata` 構造体をGoランタイムに登録する役割を担います。これにより、ランタイムは新しくロードされたモジュールに関する情報を認識し、ガベージコレクション、リフレクション、スタックトレースなどの機能で利用できるようになります。

### リロケーションタイプ (`R_X86_64_PC32`, `R_X86_64_PLT32`)

*   **`R_X86_64_PC32`**: x86-64アーキテクチャにおけるPC相対32ビットリロケーションです。これは、命令のオペランドがプログラムカウンタ（PC）からの相対オフセットとして指定される場合に用いられます。リンカーは、最終的なアドレスに基づいてこのオフセットを計算し、命令を修正します。
*   **`R_X86_64_PLT32`**: x86-64アーキテクチャにおけるPLT (Procedure Linkage Table) 相対32ビットリロケーションです。共有ライブラリ内の関数呼び出しでよく使用されます。PLTは、動的にリンクされた関数のアドレスを解決するための中間テーブルであり、このリロケーションはPLTエントリへの相対オフセットを指します。

## 技術的詳細

このコミットの核となる変更は、Goリンカーが共有ライブラリやアーカイブをビルドする際に、`runtime.addmoduledata` 関数を `.init_array` セクションを通じて呼び出すためのコードを生成する点にあります。

1.  **`gentext` 関数の変更 (`src/cmd/6l/asm.go`)**:
    *   `gentext` 関数は、リンカーがテキストセクション（コード）を生成する際に呼び出されます。
    *   `ld.DynlinkingGo()` が `true` の場合（つまり、Goが動的にリンクされている場合）、この新しい初期化ロジックが適用されます。
    *   `runtime.addmoduledata` シンボルをルックアップし、もしそれが既にテキストセクションに存在する場合（つまり、ランタイム自体がリンクされている場合）、初期化関数は不要と判断されます。これは、ランタイムが既にモジュールデータを管理しているためです。
    *   `go.link.addmoduledata` という新しいローカルなテキストシンボルが作成されます。これが `.init_array` から呼び出される関数になります。
    *   この `go.link.addmoduledata` 関数は、以下のx86-64アセンブリコードを生成します。
        *   `lea 0x0(%rip),%rdi`: `runtime.firstmoduledata` のアドレスを `rdi` レジスタにロードします。`R_X86_64_PC32` リロケーションが適用され、`runtime.firstmoduledata` のアドレスがPC相対で計算されます。`rdi` はx86-64のSystem V ABIにおいて、最初の引数レジスタです。
        *   `callq c <local.dso_init+0xc>`: `runtime.addmoduledata` を呼び出します。`Addcall` 関数が `R_X86_64_PLT32` リロケーションを適用し、動的リンクされた `runtime.addmoduledata` への呼び出しを生成します。
        *   `retq`: 関数からリターンします。
    *   生成された `go.link.addmoduledata` 関数は、リンカーのテキストセクションのリンクリストに追加されます。
    *   `go.link.addmoduledatainit` という新しいシンボルが `ld.SINITARR` タイプとして作成されます。これは `.init_array` セクションのエントリを意味します。
    *   `ld.Addaddr` を使用して、`go.link.addmoduledatainit` が `go.link.addmoduledata` 関数のアドレスを指すように設定されます。これにより、OSローダーが `.init_array` を処理する際に、この関数が呼び出されるようになります。

2.  **`.init_array` セクションの生成条件の変更 (`src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`)**:
    *   以前は `BuildmodeCArchive`, `BuildmodeCShared`, `BuildmodeShared` の場合にのみ `.init_array` が考慮されていましたが、このコミットでは `Linkshared` 変数も考慮されるようになりました。
    *   `hasinitarr` というフラグが導入され、`Linkshared` が `true` の場合、または上記の `Buildmode` のいずれかの場合に `true` となります。
    *   この `hasinitarr` フラグに基づいて、リンカーは `.init_array` セクションをデータセクションとELFヘッダに適切に追加するようになります。これにより、Goの共有ライブラリがロードされた際に、初期化関数が確実に実行されるようになります。

3.  **`runtime.lastmoduledatap` の管理 (`src/cmd/internal/ld/symtab.go`)**:
    *   `symtab` 関数内で、`runtime.lastmoduledatap` シンボルがルックアップされます。
    *   もし `runtime.lastmoduledatap` が動的インポートシンボルでない場合（つまり、現在のモジュールで定義されている場合）、そのタイプを `SNOPTRDATA` に設定し、`moduledata` のアドレスをその値として追加します。これにより、`runtime.lastmoduledatap` が常に最新の `moduledata` を指すように更新されます。これは、複数のGoモジュールがロードされる際に、`moduledata` のリンクリストを正しく構築するために重要です。

4.  **`runtime.addmoduledata` の実装 (`src/runtime/asm_amd64.s`)**:
    *   `runtime.addmoduledata` という新しいアセンブリ関数が追加されました。
    *   この関数は `.init_array` から呼び出されるため、GoのABIではなく、プラットフォームのABI（x86-64 System V ABI）に従います。
    *   `MOVQ runtime·lastmoduledatap(SB), AX`: `runtime.lastmoduledatap` の現在値を `AX` レジスタにロードします。
    *   `MOVQ DI, moduledata_next(AX)`: `DI` レジスタ（`.init_array` から渡された新しい `moduledata` のアドレス）を、`AX` が指す既存の `moduledata` の `next` フィールドに格納します。これにより、既存のモジュールデータのリンクリストに新しいモジュールデータが追加されます。
    *   `MOVQ DI, runtime·lastmoduledatap(SB)`: `runtime.lastmoduledatap` を新しい `moduledata` のアドレスで更新します。
    *   `RET`: 関数からリターンします。

5.  **`runtime.lastmoduledatap` の宣言 (`src/runtime/symtab.go`)**:
    *   `runtime/symtab.go` に `var lastmoduledatap *moduledata // linker symbol` が追加されました。これにより、`runtime.lastmoduledatap` がGoランタイム内でリンカーシンボルとして利用可能になり、リンカーがそのアドレスを解決できるようになります。

これらの変更により、Goの共有ライブラリがロードされると、OSのローダーが `.init_array` セクションを処理し、`go.link.addmoduledata` 関数が呼び出されます。この関数は、`runtime.firstmoduledata` を引数として `runtime.addmoduledata` を呼び出し、新しいモジュールデータを既存のモジュールデータリンクリストに追加し、`runtime.lastmoduledatap` を更新します。これにより、Goランタイムは動的にロードされたすべてのGoモジュールに関する情報を正確に把握できるようになります。

## コアとなるコードの解説

### `src/cmd/6l/asm.go` の変更

```go
func Addcall(ctxt *ld.Link, s *ld.LSym, t *ld.LSym) int64 {
	s.Reachable = true
	i := s.Size
	s.Size += 4
	ld.Symgrow(ctxt, s, s.Size)
	r := ld.Addrel(s)
	r.Sym = t
	r.Off = int32(i)
	r.Type = ld.R_CALL
	r.Siz = 4
	return i + int64(r.Siz)
}

func gentext() {
	if !ld.DynlinkingGo() {
		return
	}
	addmoduledata := ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)
	if addmoduledata.Type == ld.STEXT {
		// we're linking a module containing the runtime -> no need for
		// an init function
		return
	}
	addmoduledata.Reachable = true
	initfunc := ld.Linklookup(ld.Ctxt, "go.link.addmoduledata", 0)
	initfunc.Type = ld.STEXT
	initfunc.Local = true
	initfunc.Reachable = true
	o := func(op ...uint8) {
		for _, op1 := range op {
			ld.Adduint8(ld.Ctxt, initfunc, op1)
		}
	}
	// 0000000000000000 <local.dso_init>:
	//    0:	48 8d 3d 00 00 00 00 	lea    0x0(%rip),%rdi        # 7 <local.dso_init+0x7>
	// 			3: R_X86_64_PC32	runtime.firstmoduledata-0x4
	o(0x48, 0x8d, 0x3d)
	ld.Addpcrelplus(ld.Ctxt, initfunc, ld.Linklookup(ld.Ctxt, "runtime.firstmoduledata", 0), 0)
	//    7:	e8 00 00 00 00       	callq  c <local.dso_init+0xc>
	// 			8: R_X86_64_PLT32	runtime.addmoduledata-0x4
	o(0xe8)
	Addcall(ld.Ctxt, initfunc, addmoduledata)
	//    c:	c3                   	retq
	o(0xc3)
	if ld.Ctxt.Etextp != nil {
		ld.Ctxt.Etextp.Next = initfunc
	} else {
		ld.Ctxt.Textp = initfunc
	}
	ld.Ctxt.Etextp = initfunc
	initarray_entry := ld.Linklookup(ld.Ctxt, "go.link.addmoduledatainit", 0)
	initarray_entry.Reachable = true
	initarray_entry.Local = true
	initarray_entry.Type = ld.SINITARR
	ld.Addaddr(ld.Ctxt, initarray_entry, initfunc)
}
```
`gentext` 関数は、Goが動的にリンクされている場合に、`go.link.addmoduledata` という名前の初期化関数を生成します。この関数は、`runtime.firstmoduledata` のアドレスを `rdi` にロードし、その後 `runtime.addmoduledata` を呼び出します。`Addcall` ヘルパーは、`R_CALL` リロケーションを使用してこの呼び出しを生成します。最後に、この生成された関数のアドレスを指す `.init_array` エントリ (`go.link.addmoduledatainit`) が作成されます。

### `src/cmd/internal/ld/symtab.go` の変更

```go
func symtab() {
	// ...
	lastmoduledatap := Linklookup(Ctxt, "runtime.lastmoduledatap", 0)
	if lastmoduledatap.Type != SDYNIMPORT {
		lastmoduledatap.Type = SNOPTRDATA
		lastmoduledatap.Size = 0 // overwrite existing value
		Addaddr(Ctxt, lastmoduledatap, moduledata)
	}
}
```
この変更は、`runtime.lastmoduledatap` シンボルが現在のモジュールで定義されている場合（つまり、動的インポートでない場合）、そのシンボルを現在の `moduledata` のアドレスで更新するようにします。これにより、`runtime.lastmoduledatap` が常に最新の `moduledata` を指し、`moduledata` のリンクリストが正しく構築されることを保証します。

### `src/runtime/asm_amd64.s` の変更

```assembly
// This is called from .init_array and follows the platform, not Go, ABI.
TEXT runtime·addmoduledata(SB),NOSPLIT,$0-8
	MOVQ	runtime·lastmoduledatap(SB), AX
	MOVQ	DI, moduledata_next(AX)
	MOVQ	DI, runtime·lastmoduledatap(SB)
	RET
```
この新しいアセンブリ関数 `runtime·addmoduledata` は、`.init_array` から呼び出されることを想定しており、プラットフォームのABIに従います。`DI` レジスタには、新しい `moduledata` のアドレスが渡されます。この関数は、`runtime.lastmoduledatap` が指す既存の `moduledata` の `next` フィールドを新しい `moduledata` のアドレスで更新し、その後 `runtime.lastmoduledatap` 自体を新しい `moduledata` のアドレスで更新します。これにより、Goランタイムはロードされたすべての `moduledata` をリンクリストとして管理できるようになります。

### `src/runtime/symtab.go` の変更

```go
var firstmoduledata moduledata  // linker symbol
var lastmoduledatap *moduledata // linker symbol
```
`runtime.lastmoduledatap` という新しいグローバル変数が追加されました。これは、`moduledata` のリンクリストの最後の要素を追跡するために使用されます。リンカーはこのシンボルを解決し、必要に応じてその値を更新します。

## 変更の背景

このコミットの背景には、Goランタイムのコードベースの整理と明確化があります。主な変更点は以下の2つに集約されます。

1.  **リフレクション関連のアセンブリ関数の命名規則の統一と明確化**: `reflect·call`というシンボルが、Goランタイムの内部的な関数であることをより明確に示すために`runtime·reflectcall`へと変更されています。これは、Goの内部シンボルが通常`runtime·`プレフィックスを持つ慣習に合わせたものであり、コードの可読性と保守性を向上させるためのクリーンアップです。特に、アセンブリコードとGoコード間の連携において、シンボルの役割を明確にすることは重要です。

2.  **ガベージコレクションの並行スイープ設定の移動**: `concurrentSweep`という定数が`src/runtime/stubs.go`から`src/runtime/malloc.go`へ移動されています。`concurrentSweep`はGoのガベージコレクション（GC）の動作を制御する重要な設定であり、並行スイープが有効であるかを示します。この定数がメモリ割り当てとGCの主要なロジックを扱う`malloc.go`に配置されることで、GC関連の設定が一元化され、コードの論理的な構造が改善されます。`stubs.go`は主にCまたはアセンブリで実装されたランタイムサービスのための宣言を含むファイルであり、GCの具体的な設定を保持する場所としては適切ではありませんでした。

これらの変更は、Goランタイムの内部構造をより整理し、将来的な開発やデバッグを容易にすることを目的とした、典型的なコードベースの健全性維持活動の一環です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムに関する前提知識が必要です。

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、このランタイム上で動作します。ランタイムのコードはGo言語とアセンブリ言語で書かれており、パフォーマンスとシステムリソースの効率的な利用を実現しています。

### Goのアセンブリ言語 (Go Assembly Language)

Goは、一部のパフォーマンスクリティカルな部分や、OSとの低レベルなインタラクションが必要な部分でアセンブリ言語を使用します。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文（Plan 9アセンブラの派生）を持っています。シンボル名には、パッケージ名と関数名を区切るために`·`（中点）が使用されることがあります（例: `runtime·morestack`）。これは、Goのリンカが内部的にシンボルを解決する方法に関連しています。

### リフレクション (Reflection)

Goのリフレクションは、プログラムが自身の構造（型、フィールド、メソッドなど）を検査し、実行時にそれらを操作する機能です。これにより、汎用的なコードや、コンパイル時には未知の型を扱うライブラリ（例: JSONエンコーダ/デコーダ）を記述できます。リフレクションは強力ですが、型安全性を損なう可能性があり、また通常の関数呼び出しに比べてパフォーマンスオーバーヘッドがあります。
`reflect.Call`は、`reflect`パッケージを通じて関数を動的に呼び出すためのメカニズムであり、その内部ではランタイムのアセンブリコードが利用されます。

### ガベージコレクション (Garbage Collection, GC)

Goは自動メモリ管理（ガベージコレクション）を採用しています。これにより、開発者は手動でメモリを解放する手間から解放されます。GoのGCは、並行（concurrent）かつ低遅延（low-latency）な設計が特徴です。

*   **並行GC (Concurrent GC)**: GCの大部分のフェーズが、ユーザープログラム（ゴルーチン）と並行して実行されます。これにより、GCによるプログラムの一時停止（ストップ・ザ・ワールド、STW）時間を最小限に抑え、アプリケーションの応答性を向上させます。
*   **スイープ (Sweep)**: GCのフェーズの一つで、マークフェーズで到達可能とマークされなかったオブジェクトが占めていたメモリを解放し、再利用可能にするプロセスです。
*   **並行スイープ (Concurrent Sweep)**: スイープフェーズもユーザープログラムと並行して実行されることを指します。これにより、GCのSTW時間をさらに短縮し、全体的なパフォーマンスを向上させます。`concurrentSweep`という定数は、この並行スイープ機能が有効になっているかどうかを示すフラグとして機能します。

### `src/runtime/stubs.go` と `src/runtime/malloc.go`

*   `src/runtime/stubs.go`: このファイルは、Goランタイムの内部サービス（C言語やアセンブリ言語で実装されているもの）のGo言語側の宣言（スタブ）を含んでいます。これらの関数はGoコードから呼び出されますが、実際のロジックはGo以外の言語で書かれています。
*   `src/runtime/malloc.go`: このファイルは、Goランタイムのメモリ割り当て（アロケーション）と解放（デロケーション）に関する主要なロジックを含んでいます。ガベージコレクタのメモリ管理部分と密接に関連しています。

## 技術的詳細

このコミットにおける技術的な変更は、Goランタイムの内部動作の明確化と整理に焦点を当てています。

### `reflect·call` から `runtime·reflectcall` への変更

Goのアセンブリコード（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`, `thunk.s`）において、`reflect·call`というシンボルが`runtime·reflectcall`に一貫して変更されています。

*   **変更の理由**: Goのランタイム内部で使用される関数やシンボルには、通常`runtime·`というプレフィックスが付与されます。これは、これらのシンボルがGoの標準ライブラリの一部ではなく、Goプログラムの実行環境そのものを提供するランタイムの内部コンポーネントであることを示唆しています。`reflect·call`は、`reflect`パッケージがGoの関数を動的に呼び出す際に内部的に利用するアセンブリ関数であり、その実体はランタイムに属します。この変更により、シンボルの命名規則が統一され、`reflect·call`がランタイムの内部関数であることがより明確になります。これにより、コードの意図がより伝わりやすくなり、将来的なメンテナンスやデバッグが容易になります。

*   **`thunk.s`における変更**: `thunk.s`ファイルでは、`TEXT runtime·reflectcall(SB), NOSPLIT, $0-0`が`JMP reflect·call(SB)`を呼び出し、その逆の`TEXT reflect·call(SB), NOSPLIT, $0-0`が`JMP runtime·reflectcall(SB)`を呼び出すように変更されています。これは、シンボル名の変更に伴うリダイレクトまたはエイリアスの設定であり、古いシンボル名で参照されている箇所が新しいシンボル名に正しく解決されるようにするための措置です。これにより、既存のコードが新しい命名規則にスムーズに移行できるようになります。

### `concurrentSweep` 定数の移動

`concurrentSweep`というブーリアン定数が、`src/runtime/stubs.go`から`src/runtime/malloc.go`へ移動されました。

*   **変更の理由**: `concurrentSweep`は、Goのガベージコレクタが並行スイープを実行するかどうかを制御するフラグです。並行スイープはメモリ管理（特に解放されたメモリの再利用）の重要な側面であり、`malloc.go`はGoのメモリ割り当てと管理の核心部分を担っています。したがって、この定数を`malloc.go`に配置することは、GCのメモリ管理関連の設定を一元化し、コードの論理的な関連性を高めます。
    一方、`stubs.go`は主にGo以外の言語で実装されたランタイム関数のGo側の宣言を保持するファイルであり、GCの具体的な動作設定を保持する場所としては適切ではありませんでした。この移動により、コードのモジュール性が向上し、GCの動作に関する設定がより適切な場所に集約されます。

*   **`stubs.go`からのコメント削除**: `stubs.go`から、C言語実装やアセンブリ実装に関する一般的なコメントが削除されています。これは、ファイルの内容がより特定の宣言に特化されるようにするための整理の一環と考えられます。また、`// in stubs.goc`というコメントが`// in runtime.c`に変更されており、これはGoランタイムのC言語部分のファイル名が変更されたか、あるいはより一般的な参照に修正されたことを示唆しています。

これらの変更は、個々には小さなクリーンアップですが、Goランタイムのような大規模で複雑なシステムにおいては、コードの整理と明確化が長期的な保守性とパフォーマンスに大きく貢献します。

## コアとなるコードの解説

### アセンブリファイルのシンボル名変更 (`reflect·call` -> `runtime·reflectcall`)

Goランタイムのアセンブリファイル（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）では、`reflect`パッケージが内部的に使用する関数呼び出しのエントリポイントである`reflect·call`のシンボル名が`runtime·reflectcall`に変更されました。

*   **変更前**: `TEXT reflect·call(SB), NOSPLIT, $0-XX`
*   **変更後**: `TEXT runtime·reflectcall(SB), NOSPLIT, $0-XX`

この変更は、Goランタイムの内部シンボルが`runtime·`プレフィックスを持つという慣習に合わせたものです。これにより、この関数がGoのランタイムの一部であり、リフレクション機能の低レベルな実装を担っていることがより明確になります。コメントも`// reflect·call: call a function with the given argument list`から`// reflectcall: call a function with the given argument list`に変更され、シンボル名とコメントの一貫性が保たれています。

### `thunk.s`におけるJMP命令の入れ替え

`src/runtime/thunk.s`では、`reflect·call`と`runtime·reflectcall`間のJMP命令のターゲットが入れ替わっています。

*   **変更前**:
    ```assembly
    TEXT runtime·reflectcall(SB), NOSPLIT, $0-0
    	JMP	reflect·call(SB)
    ```
*   **変更後**:
    ```assembly
    TEXT reflect·call(SB), NOSPLIT, $0-0
    	JMP	runtime·reflectcall(SB)
    ```

この変更は、シンボル名の変更に伴う互換性維持のための措置です。変更前は`runtime·reflectcall`が`reflect·call`にジャンプしていましたが、変更後は`reflect·call`が`runtime·reflectcall`にジャンプするように逆転しています。これは、外部から（例えば、古いバージョンのGoコードや、まだ新しい命名規則に更新されていない部分から）`reflect·call`が参照された場合でも、正しく新しい`runtime·reflectcall`の実装に到達できるようにするためのエイリアスまたはリダイレクトの役割を果たします。これにより、ランタイムの内部的なシンボル名を変更しつつも、既存のコードベースとの互換性を保つことができます。

### `concurrentSweep` 定数の移動とコメントの整理

`src/runtime/stubs.go`から`concurrentSweep = true`という定数が削除され、`src/runtime/malloc.go`に移動されました。

*   **`src/runtime/malloc.go`への追加**:
    ```go
    const (
    	// ...
    	mSpanInUse = 0

    	concurrentSweep = true
    )
    ```
    `concurrentSweep`は、Goのガベージコレクタが並行スイープを実行するかどうかを制御するブーリアン定数です。この定数がメモリ割り当てと管理の主要なロジックを含む`malloc.go`に配置されることで、GCのメモリ管理関連の設定が一元化され、コードの論理的な構造が改善されます。

*   **`src/runtime/stubs.go`からの削除とコメントの変更**:
    `stubs.go`からは`concurrentSweep`定数が削除されました。また、ファイル冒頭のコメントや`getg()`関数に関するコメントが整理されています。
    *   `// C implementations of these functions are in stubs.goc.` などの一般的なコメントが削除されました。
    *   `// in stubs.goc` が `// in runtime.c` に変更されました。これは、GoランタイムのC言語部分のファイル名が変更されたか、あるいはより一般的な参照に修正されたことを示唆しています。

これらの変更は、Goランタイムのコードベースをより整理し、各ファイルがその役割に特化するようにするためのクリーンアップです。GCの動作に関する設定がメモリ管理の核心部分に移動することで、関連するコードの発見と理解が容易になります。

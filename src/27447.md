## 変更の背景

この変更（リバート）の背景には、以前の s390x サポート追加コミットがGoプロジェクト全体のビルドを壊してしまったという問題があります。コミットメッセージによると、s390x サポートの追加は、まだレビューが完了していない、あるいはメインブランチにマージされていない他の変更リスト (CLs: Change Lists) に依存していました。

ソフトウェア開発において、特に大規模なプロジェクトでは、複数の変更が同時に進行することがよくあります。それぞれの変更は独立して開発され、レビューを経てメインのコードベースに統合されます。しかし、ある変更が他の未統合の変更に依存している場合、依存先の変更が先にマージされないと、依存元の変更をマージした際にビルドエラーやランタイムエラーが発生する可能性があります。

このケースでは、s390x サポートのコミットがそのような依存関係の問題を引き起こし、Goプロジェクト全体のビルドプロセスを中断させてしまいました。開発の継続性を確保するため、一時的にこの変更を元に戻すことが決定されました。これは、依存関係が解決され、全ての関連する変更が安定した状態で統合されるまで、問題のあるコードをメインラインから隔離するための標準的なプラクティスです。

## 前提知識の解説

### Go言語のアセンブラ (`cmd/asm`)

Go言語は、そのランタイムや一部の標準ライブラリにおいて、パフォーマンスが重要な部分でアセンブリ言語を使用しています。`cmd/asm` は、Go言語のツールチェインの一部であり、Goのアセンブリ言語（Plan 9アセンブラの派生）を機械語に変換するアセンブラです。これは、特定のアーキテクチャ向けに最適化されたコードを記述するために使用されます。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文を持っています。

### s390x アーキテクチャ

s390x は、IBM が開発したメインフレームコンピュータのアーキテクチャである IBM System z の64ビット版です。このアーキテクチャは、高い信頼性、可用性、保守性 (RAS: Reliability, Availability, Serviceability) を特徴とし、大規模なトランザクション処理やデータウェアハウジングなど、エンタープライズレベルのワークロードで広く使用されています。Go言語が s390x をサポートするということは、Goアプリケーションがメインフレーム環境でネイティブに動作できるようになることを意味し、Goの適用範囲を広げる上で重要なステップとなります。

### Goの変更リスト (CLs: Change Lists)

Goプロジェクトでは、コードの変更は「変更リスト (Change List)」として提出されます。これは、Gitのコミットに似ていますが、Goのコードレビューシステム (Gerrit) を通じて管理されます。開発者は変更を CL として提出し、他の開発者からのレビューを受け、承認された後にメインのコードベースにマージされます。このプロセスにより、コードの品質と一貫性が保たれます。

### ビルドの破損

「ビルドが壊れた (broke all builds)」とは、コードベースに導入された変更が原因で、プロジェクト全体のコンパイルやリンク、テストなどのビルドプロセスが失敗する状態を指します。これは、新しいコードが既存のコードと互換性がなかったり、必要な依存関係が欠けていたり、あるいは単にバグを含んでいたりする場合に発生します。ビルドの破損は開発の進行を妨げるため、迅速な特定と修正、または問題のある変更のリバートが必要です。

## 技術的詳細

このリバートコミットは、`cmd/asm` ツールから s390x アーキテクチャのサポートを完全に削除しています。具体的には、以下の技術的な変更が含まれています。

1.  **アーキテクチャ定義の削除**:
    *   `src/cmd/asm/internal/arch/arch.go` から、`s390x` アーキテクチャを識別し、それに対応する `Arch` 構造体を初期化するロジックが削除されました。`Arch` 構造体は、アセンブラが特定のCPUアーキテクチャのレジスタ、命令セット、ジャンプ命令などを理解するために必要な情報を含んでいます。
    *   `archS390x()` 関数自体も削除されました。この関数は、s390x のレジスタマップ（`R0`から`R15`、`F0`から`F15`、`V0`から`V31`などの汎用レジスタ、浮動小数点レジスタ、ベクトルレジスタ）、擬似レジスタ（`SB`, `FP`, `PC`, `g`）、および s390x 固有の命令セットを定義していました。

2.  **s390x 固有のヘルパー関数の削除**:
    *   `src/cmd/asm/internal/arch/s390x.go` ファイル全体が削除されました。このファイルには、s390x のジャンプ命令を識別する `jumpS390x` 関数や、特定の命令が特殊なハンドリングを必要とするかどうかを判定する `IsS390xRLD`, `IsS390xCMP`, `IsS390xNEG`, `IsS390xWithLength`, `IsS390xWithIndex` などの関数が含まれていました。これらの関数は、アセンブラが s390x の複雑な命令フォーマットやオペランドの規則を正しく解釈するために不可欠でした。

3.  **アセンブラパーサーからの s390x 固有ロジックの削除**:
    *   `src/cmd/asm/internal/asm/asm.go` から、s390x アーキテクチャ (`p.arch.Thechar == 'z'`) に特化した命令解析ロジックが削除されました。これには、3オペランドのジャンプ命令や、長さ（length）またはインデックス（index）を伴う命令の処理に関するコードが含まれていました。これらのロジックは、s390x の命令が他のアーキテクチャとは異なるオペランドの解釈やエンコーディングを持つために必要でした。

4.  **テストコードの削除**:
    *   `src/cmd/asm/internal/asm/endtoend_test.go` から `TestS390XEndToEnd` 関数が削除されました。これは、s390x アセンブリコードの全体的なコンパイルと実行をテストするものでした。
    *   `src/cmd/asm/internal/asm/operand_test.go` から `TestS390XOperandParser` 関数と `s390xOperandTests` 変数が削除されました。これらは、s390x のオペランド（レジスタ、即値、メモリ参照など）がアセンブラによって正しくパースされるかを検証するための単体テストでした。
    *   `src/cmd/asm/internal/asm/testdata/s390x.s` ファイル全体が削除されました。このファイルは、s390x アーキテクチャ向けのアセンブリコードのサンプルを含んでおり、テストスイートによって使用されていました。

これらの変更は、s390x サポートを導入したコミットによって追加された全てのコードと設定を、元の状態に戻すことを意味します。これにより、ビルドの破損問題が解決され、Goプロジェクトの安定性が回復しました。

    *   ファイル全体が削除されました。

## コアとなるコードの解説

このリバートは、以前のコミットで追加された s390x 関連のコードを文字通り削除することで、その機能を元に戻しています。

*   **`arch.go` の変更**: `arch.go` は、Goアセンブラがサポートする各CPUアーキテクチャの基本的な特性を定義する中心的なファイルです。`Set` 関数は `GOARCH` 環境変数に基づいて適切なアーキテクチャ設定を返します。`s390x` のケースが削除されたことで、`cmd/asm` はもはや `s390x` を認識せず、そのアーキテクチャ固有の命令セットやレジスタ構成を処理できなくなります。`archS390x` 関数の削除は、s390x のレジスタ定義、擬似レジスタ、命令セットマッピングといった詳細なアーキテクチャ情報がシステムから完全に失われたことを意味します。

*   **`s390x.go` の削除**: このファイルは s390x アーキテクチャに特化したロジックをカプセル化していました。例えば、`jumpS390x` は s390x の様々な条件分岐命令を識別し、`IsS390xRLD` などの関数は特定の命令がアセンブラ内で特別な処理を必要とするかどうかを判断していました。これらのヘルパー関数は s390x の複雑な命令セットを Goアセンブラが正しく解釈するために不可欠でしたが、ファイルごと削除されたことで、その機能は完全に失われました。

*   **`asm.go` の変更**: `asm.go` はアセンブリコードのパースと命令の処理を担当するアセンブラのコア部分です。`p.arch.Thechar == 'z'` という条件は、現在のターゲットアーキテクチャが s390x であることを示していました。この条件ブロックが削除されたことで、s390x 固有の3オペランドジャンプや、長さ/インデックスを伴う命令の特殊な処理ロジックがアセンブラから取り除かれました。これにより、s390x のアセンブリコードをパースしようとすると、これらの命令が正しく解釈されず、エラーが発生するようになります。

*   **テストコードの削除**: `endtoend_test.go` と `operand_test.go` から s390x 関連のテストが削除されたことは、s390x サポートがもはや存在しないため、その機能がテストされる必要がなくなったことを示しています。`s390x.s` テストデータファイルの削除も同様に、s390x アセンブリのサンプルが不要になったためです。

これらの変更は、s390x サポートを導入したコミットの逆操作であり、Goツールチェインから s390x 関連の全ての痕跡を削除することで、ビルドの破損という緊急の問題に対処しています。これは、問題のある機能が完全に安定し、依存関係が解決されるまで、一時的にその機能を無効化する一般的なソフトウェア開発のプラクティスです。

## コアとなるコードの解説

このリバートは、以前のコミットで追加された s390x 関連のコードを文字通り削除することで、その機能を元に戻しています。

*   **`arch.go` の変更**: `arch.go` は、Goアセンブラがサポートする各CPUアーキテクチャの基本的な特性を定義する中心的なファイルです。`Set` 関数は `GOARCH` 環境変数に基づいて適切なアーキテクチャ設定を返します。`s390x` のケースが削除されたことで、`cmd/asm` はもはや `s390x` を認識せず、そのアーキテクチャ固有の命令セットやレジスタ構成を処理できなくなります。`archS390x` 関数の削除は、s390x のレジスタ定義、擬似レジスタ、命令セットマッピングといった詳細なアーキテクチャ情報がシステムから完全に失われたことを意味します。

*   **`s390x.go` の削除**: このファイルは s390x アーキテクチャに特化したロジックをカプセル化していました。例えば、`jumpS390x` は s390x の様々な条件分岐命令を識別し、`IsS390xRLD` などの関数は特定の命令がアセンブラ内で特別な処理を必要とするかどうかを判断していました。これらのヘルパー関数は s390x の複雑な命令セットを Goアセンブラが正しく解釈するために不可欠でしたが、ファイルごと削除されたことで、その機能は完全に失われました。

*   **`asm.go` の変更**: `asm.go` はアセンブリコードのパースと命令の処理を担当するアセンブラのコア部分です。`p.arch.Thechar == 'z'` という条件は、現在のターゲットアーキテクチャが s390x であることを示していました。この条件ブロックが削除されたことで、s390x 固有の3オペランドジャンプや、長さ/インデックスを伴う命令の特殊な処理ロジックがアセンブラから取り除かれました。これにより、s390x のアセンブリコードをパースしようとすると、これらの命令が正しく解釈されず、エラーが発生するようになります。

*   **テストコードの削除**: `endtoend_test.go` と `operand_test.go` から s390x 関連のテストが削除されたことは、s390x サポートがもはや存在しないため、その機能がテストされる必要がなくなったことを示しています。`s390x.s` テストデータファイルの削除も同様に、s390x アセンブリのサンプルが不要になったためです。

これらの変更は、s390x サポートを導入したコミットの逆操作であり、Goツールチェインから s390x 関連の全ての痕跡を削除することで、ビルドの破損という緊急の問題に対処しています。これは、問題のある機能が完全に安定し、依存関係が解決されるまで、一時的にその機能を無効化する一般的なソフトウェア開発のプラクティスです。

## 変更の背景

このコミットの背景には、Go言語の初期開発段階におけるコードの可読性と保守性の向上という一般的な目標があります。`gobuild` ツールは、Goプロジェクトのビルドプロセスを管理するために `Makefile` を生成していました。この `Makefile` の内容は、Goのコード内で文字列として定義されていましたが、以前の実装では、各行が個別の引用符付き文字列として定義され、それらが `\n` (改行文字) を介して連結されていました。

このような記述方法は、特に `Makefile` のような構造化されたテキストを表現する場合、以下の問題を引き起こします。

1.  **可読性の低下**: `Makefile` の実際の構造（インデント、改行など）がGoのコード上では失われ、エスケープされた改行文字 `\n` が散在するため、元の `Makefile` の内容を把握しにくい。
2.  **保守性の低下**: `Makefile` の内容を変更する際に、改行文字の追加や削除、インデントの調整などが煩雑になり、エラーが発生しやすくなる。
3.  **エスケープ文字の管理**: `Makefile` 内で `\` や `$` などの特殊文字を使用する場合、Goの文字列リテラル内でさらにエスケープする必要があり、記述が複雑になる。

Go言語には、これらの問題を解決するための「生文字列リテラル (raw string literal)」または「マルチライン文字列リテラル」と呼ばれる機能があります。これはバッククォート (`` ` ``) で囲まれた文字列で、内部の改行や特殊文字がそのまま解釈されるため、特に複数行にわたるテキストや、エスケープ文字を多用するテキスト（正規表現、HTML、JSON、`Makefile` など）を扱う場合に非常に有用です。

このコミットは、このGo言語の機能を活用することで、`gobuild` が生成する `Makefile` のテンプレート定義をより自然で読みやすい形式に改善することを目的としています。

## 前提知識の解説

### Go言語の文字列リテラル

Go言語には主に2種類の文字列リテラルがあります。

1.  **解釈済み文字列リテラル (Interpreted String Literal)**:
    *   ダブルクォート (`"`) で囲まれた文字列です。
    *   C言語の文字列リテラルと同様に、バックスラッシュ (`\`) を使ったエスケープシーケンス（例: `\n` で改行、`\t` でタブ、`\"` でダブルクォート自身）が解釈されます。
    *   複数行にわたる文字列を表現する場合、各行を個別の文字列リテラルとして定義し、`+` 演算子で連結するか、各行の末尾に `\n` を明示的に記述する必要があります。

    例:
    ```go
    s := "Hello,\n" +
         "\tWorld!"
    // s は "Hello,\n\tWorld!" となる
    ```

2.  **生文字列リテラル (Raw String Literal) / マルチライン文字列リテラル**:
    *   バッククォート (`` ` ``) で囲まれた文字列です。
    *   内部の文字は、改行やバックスラッシュを含め、すべて文字通りに解釈されます。エスケープシーケンスは解釈されません。
    *   複数行にわたる文字列を、コード上でもそのままの形で記述できます。
    *   この特性から、正規表現、HTML、JSON、`Makefile` のような、改行や特殊文字を多く含むテキストをGoのコード内に埋め込む際に非常に便利です。

    例:
    ```go
    s := `Hello,
    	World!`
    // s は "Hello,\n\tWorld!" となる
    ```

### `gobuild` ツール

`gobuild` は、Go言語の初期のビルドツールの一つです。現在の `go build` コマンドの前身にあたるツールで、Goのソースコードから実行可能ファイルやライブラリをビルドする役割を担っていました。`gobuild` は、プロジェクトの構造や依存関係に基づいて `Makefile` を動的に生成し、その `Makefile` を `make` コマンドで実行することでビルドプロセスを制御していました。

### `Makefile`

`Makefile` は、`make` ユーティリティがプログラムのコンパイルやその他のタスクを自動化するために使用するファイルです。ターゲット、依存関係、およびコマンド（レシピ）のルールを定義します。`Makefile` は、特にC/C++などのコンパイル型言語のプロジェクトで広く使われていましたが、Goの初期のビルドシステムでも内部的に利用されていました。`Makefile` の構文は、タブ文字によるインデントが重要であるなど、特定のルールがあります。

## 技術的詳細

このコミットの技術的詳細は、Go言語の文字列リテラルの特性を `gobuild` の `Makefile` テンプレートに適用した点に集約されます。

変更前は、`makefileTemplate` 変数が以下のように定義されていました。

```go
var makefileTemplate =
	"# DO NOT EDIT.  Automatically generated by gobuild.\\n" +
	"{Args|args} >Makefile\\n" +
	"\\n" +
	// ... 続く
```

これは、各行がダブルクォートで囲まれた文字列リテラルであり、明示的に `\n` を含めることで改行を表現し、さらに `+` 演算子でこれらを連結していました。この方式では、`Makefile` の各行の先頭にあるタブ文字も `\t` のようにエスケープする必要がありました。

変更後は、以下のように定義されています。

```go
var makefileTemplate = `
# DO NOT EDIT.  Automatically generated by gobuild.
{Args|args} >Makefile

D={.section Dir}/{@}{.end}

// ... 続く
`
```

ここでは、バッククォート (`` ` ``) で囲まれた生文字列リテラルが使用されています。この変更により、以下の技術的な利点が得られます。

1.  **WYSIWYG (What You See Is What You Get)**: Goのコード内で `Makefile` の内容が、実際に生成される `Makefile` とほぼ同じ見た目で記述できるようになりました。これにより、テンプレートの構造やインデントが視覚的に明確になり、理解しやすくなります。
2.  **エスケープ文字の不要化**: `\n` や `\t` といったエスケープシーケンスを明示的に記述する必要がなくなりました。バッククォート文字列内では、改行はそのまま改行として、タブはそのままタブとして扱われます。これにより、記述ミスが減り、コードが簡潔になります。
3.  **特殊文字の扱い**: `Makefile` 内で `$()` や `\` といった特殊文字が頻繁に登場しますが、これらをGoの解釈済み文字列リテラル内で記述する場合、さらにエスケープが必要になることがあります（例: `\\` や `\$`）。生文字列リテラルでは、これらの文字も文字通りに扱われるため、余計なエスケープが不要になり、`Makefile` の内容をそのままコピー＆ペーストするような感覚で記述できます。
4.  **パフォーマンスへの影響**: この変更は、文字列の表現方法に関するものであり、実行時のパフォーマンスに大きな影響を与えるものではありません。コンパイル時に文字列が構築されるため、実行時のオーバーヘッドは無視できるレベルです。

この変更は、Go言語の言語機能の適切な活用例であり、特にドメイン固有言語 (DSL) のテンプレートや、設定ファイル、スクリプトなどをGoのコード内に埋め込む際のベストプラクティスを示しています。

## コアとなるコードの解説

`src/cmd/gobuild/makefile.go` ファイルは、`gobuild` ツールが `Makefile` を生成するためのテンプレートを保持しています。このファイルには、`template` パッケージ（Goの標準ライブラリの一部）を使用して、動的な値を埋め込むことができる `Makefile` の構造が定義されています。

`makefileTemplate` 変数は、`Makefile` の基本的な構造を文字列として保持しています。この文字列は、`gobuild` が特定のGoプロジェクトのビルドに必要な情報（例: パッケージ名、ソースファイル、アーキテクチャなど）を埋め込むためのプレースホルダー（例: `{Args|args}`, `{ObjDir}` など）を含んでいます。

このコミットによる変更は、この `makefileTemplate` の**表現形式のみ**に影響を与え、`Makefile` の**論理的な内容や生成される `Makefile` の最終的な出力**には影響を与えません。つまり、この変更は機能的な変更ではなく、コードのスタイルと保守性に関する改善です。

変更前は、Goコンパイラが複数の文字列リテラルを連結して一つの大きな文字列を構築していました。これは有効なGoの構文ですが、前述の通り可読性に難がありました。

変更後は、Goのコンパイラがバッククォートで囲まれたブロック全体を単一の文字列リテラルとして解釈します。この文字列リテラルは、内部の改行やタブ、その他の特殊文字をそのまま保持するため、`Makefile` の構造がGoのソースコード上で視覚的に再現されます。これにより、`gobuild` の開発者が `Makefile` テンプレートを修正する際に、より直感的に作業できるようになります。

例えば、`coverage` ターゲット内の `6cov -g `pwd` | grep -v '_test\.go:'` の行では、変更前は `\`` や `\\` のエスケープが必要でしたが、変更後は ` `pwd` ` や `_test\.go:` のように、より自然な形で記述できるようになっています。

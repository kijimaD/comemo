## 変更の背景

この変更の背景には、Go言語の設計哲学である「明確さ」と「エラーの早期発見」があります。プログラミング言語において、異なるスコープで同じ名前の識別子を使用する「シャドーイング（shadowing）」は、時に意図しないバグや混乱を引き起こす可能性があります。特に、外部スコープの定数をローカル変数でシャドーイングすることは、その定数が不変であるという期待を裏切り、コードの理解を困難にする可能性があります。

このコミットは、Go言語の初期段階において、このような潜在的な問題を未然に防ぐための言語設計上の決定として導入されました。`ken`（おそらくKen Thompson氏）との議論を経て、この挙動が言語仕様として適切であると判断されたことが示唆されています。これにより、コンパイラがこのようなコードをエラーとして検出し、開発者がより堅牢で理解しやすいコードを書くことを強制します。

## 前提知識の解説

### スコープ (Scope)

スコープとは、プログラム内で識別子（変数、定数、関数など）が参照可能である範囲を指します。Go言語には、主に以下のスコープがあります。

*   **ユニバーススコープ (Universe Scope)**: 組み込み型（`int`, `bool`など）、組み込み関数（`len`, `cap`など）、組み込み定数（`true`, `false`, `iota`など）が定義される最も広いスコープです。これらはプログラムのどこからでもアクセス可能です。
*   **パッケージスコープ (Package Scope)**: パッケージレベルで宣言された識別子（グローバル変数、定数、関数、型など）が参照可能なスコープです。同じパッケージ内のすべてのファイルからアクセスできます。
*   **ファイルスコープ (File Scope)**: Goには厳密なファイルスコープという概念はあまり強調されませんが、実際にはパッケージスコープの一部として、ファイル内で宣言された識別子がそのファイル内で参照可能です。
*   **ブロックスコープ (Block Scope)**: `if`文、`for`文、`switch`文、関数本体などのブロック内で宣言された識別子が参照可能なスコープです。ブロックの外からはアクセスできません。

Go言語では、内側のスコープで宣言された識別子が外側のスコープの識別子と同じ名前を持つ場合、内側の識別子が外側の識別子を「シャドーイング」します。これにより、内側のスコープからは外側の識別子に直接アクセスできなくなります。

### 定数 (Constants)

Go言語の定数は、コンパイル時に値が決定され、実行中に変更できない不変な値です。`const`キーワードを使用して宣言されます。定数は、プログラム全体で一貫した値を提供し、マジックナンバーの使用を避けるために利用されます。

### `:=` 演算子 (Short Variable Declaration)

`:=` はGo言語の短縮変数宣言演算子です。これは、変数の宣言と初期化を同時に行うための簡潔な方法です。`var`キーワードと型指定を省略できます。

例: `x := 10` は `var x int = 10` と同等です。

この演算子は、新しい変数を宣言する場合にのみ使用できます。もし左辺の変数が既に現在のスコープで宣言されている場合、`:=` はコンパイルエラーとなります。ただし、複数の変数を宣言する際に、少なくとも1つの新しい変数が含まれていれば、既存の変数への再代入も可能です。

## 技術的詳細

このコミットが対処しているのは、Goコンパイラの名前解決ロジックにおける特定のケースです。具体的には、関数内部のブロックスコープで、外部（パッケージ）スコープで宣言された定数と同じ名前のローカル変数を `:=` 演算子を使って宣言しようとした場合です。

Goコンパイラは、識別子の宣言を処理する際に、現在のスコープとその外側のスコープを順に検索して、その識別子が既に宣言されているかどうかを確認します。

このコミット以前は、コンパイラがこの特定のシナリオ（外部スコープの定数とローカル変数の名前の衝突）を適切にエラーとして扱っていなかった可能性があります。`:=` 演算子は新しい変数を宣言する際に使用されるため、もし同じ名前の定数が外部スコープに存在する場合、それは新しい変数の宣言ではなく、既存の定数への再代入（これは定数なので許可されない）と解釈されるか、あるいは単にシャドーイングとして許可されてしまう可能性がありました。

この変更により、コンパイラは、`:=` を使用してローカル変数を宣言しようとした際に、その名前が既に外部スコープの定数として存在する場合、それをエラーとして報告するように修正されました。これは、`:=` が「新しい変数の宣言」を意味するという厳密な規則と、定数の不変性という原則を組み合わせた結果です。

エラーメッセージの例（`test/bugs/bug144.go`のコメントから）：
```
bug144.go:8: left side of := must be a name
bug144.go:8: operation LITERAL not allowed in assignment context
bug144.go:8: illegal types for operand: AS
	ideal
	int
```
これらのエラーメッセージは、コンパイラが `c := 0` を新しい変数 `c` の宣言ではなく、既存の定数 `c` への代入（または不正な操作）として解釈していることを示しています。特に「left side of := must be a name」は、`c` が既に定数として存在するため、`:=` の左辺に新しい名前が期待されていることを示唆しています。

## コアとなるコードの変更箇所

このコミットでは、Goコンパイラの内部ロジックが変更されていますが、具体的なコードの差分は提供されていません。しかし、コミットメッセージと追加されたテストケースから、変更がコンパイラの「名前解決」および「変数宣言の検証」部分に集中していると推測できます。

追加されたテストファイル `test/bugs/bug144.go` が、この変更の意図を最も明確に示しています。

```go
// $G $D/$F.go || echo BUG should compile

// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

const c = 1;

func main() {
	c := 0; // この行がコンパイルエラーになるべき
}

/*
bug144.go:8: left side of := must be a name
bug144.go:8: operation LITERAL not allowed in assignment context
bug144.go:8: illegal types for operand: AS
	ideal
	int
*/
```

このテストケースは、パッケージレベルで定数 `c` が宣言され、`main` 関数内で同じ名前のローカル変数 `c` を `:=` を使って宣言しようとすると、コンパイルエラーが発生することを確認しています。`test/golden.out` の変更は、このテストケースが期待通りのエラーメッセージを出力することを示しています。

## コアとなるコードの解説

Goコンパイラの内部では、ソースコードを抽象構文木（AST）に変換し、そのASTを走査しながら型チェックや名前解決を行います。このコミットの変更は、ASTの走査中に `:=` 演算子に出くわした際の名前解決ロジックに影響を与えます。

1.  **識別子の検出**: コンパイラが `c := 0` のような短縮変数宣言を検出します。
2.  **スコープ検索**: `c` という名前が現在の（`main` 関数の）ブロックスコープで既に宣言されているかを確認します。
3.  **外部スコープ検索**: もし現在のスコープで宣言されていなければ、外側のスコープ（この場合はパッケージスコープ）を検索します。
4.  **定数の検出**: パッケージスコープで `c` が定数として宣言されていることを検出します。
5.  **エラーの生成**: `:=` 演算子は新しい変数を宣言するために使用されるべきであり、既存の定数をシャドーイングする形で新しい変数を宣言することは許可されない、という規則に基づいてコンパイルエラーを生成します。

この修正は、コンパイラのセマンティック分析フェーズ、特に名前解決と宣言の検証ロジックに組み込まれたと考えられます。これにより、Go言語のコードがより予測可能で、意図しない名前の衝突によるバグを防ぐことができます。

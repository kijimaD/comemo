# [インデックス 21700] ファイルの概要

このコミットは、Go言語の標準ライブラリ `expvar` パッケージにおける `Int` 型の実装を改善し、パフォーマンスを向上させるものです。具体的には、`Int` 型の内部で64ビット整数を操作する際に、従来の `sync.RWMutex` を用いた排他制御から、`sync/atomic` パッケージのアトミック操作へと変更しています。これにより、単一の整数操作におけるオーバーヘッドが大幅に削減され、より高速な処理が可能になります。

## コミット

```
commit bd043d862962ec844994a658d8b4f8ab89b6d80e

Date:   Wed Jan 28 09:16:44 2015 -0800

    expvar: Use sync/atomic to manipulate Int for better perf
    
    Using a mutex to protect a single int operation is quite heavyweight.
    Using sync/atomic provides much better performance. This change was
    benchmarked as such:
    
    BenchmarkSync   10000000       139 ns/op
    BenchmarkAtomic 200000000      9.90 ns/op
    
    package blah
    
    import (
            "sync"
            "sync/atomic"
            "testing"
    )
    
    type Int struct {
            mu sync.RWMutex
            i  int64
    }
    
    func (v *Int) Add(delta int64) {
            v.mu.Lock()
            defer v.mu.Unlock()
            v.i += delta
    }
    
    type AtomicInt struct {
            i int64
    }
    
    func (v *AtomicInt) Add(delta int64) {
            atomic.AddInt64(&v.i, delta)
    }
    
    func BenchmarkSync(b *testing.B) {
            s := new(Int)
    
            for i := 0; i < b.N; i++ {
                    s.Add(1)
            }
    }
    
    func BenchmarkAtomic(b *testing.B) {
            s := new(AtomicInt)
    
            for i := 0; i < b.N; i++ {
                    s.Add(1)
            }
    }
```

## 元コミット内容

`expvar` パッケージの `Int` 型において、内部の64ビット整数 (`int64`) の操作（読み取り、加算、設定）に `sync.RWMutex` を使用していた箇所を、`sync/atomic` パッケージのアトミック操作に置き換える。これにより、単一の整数操作のパフォーマンスを大幅に向上させる。

ベンチマーク結果:
- `BenchmarkSync` (Mutex使用): 10,000,000 ops, 139 ns/op
- `BenchmarkAtomic` (Atomic操作使用): 200,000,000 ops, 9.90 ns/op

## 変更の背景

Go言語の `expvar` パッケージは、実行中のプログラムの内部状態をHTTP経由で公開するためのシンプルなメカニズムを提供します。`Int` 型はその中で、カウンタやゲージのような整数値を公開するために使用されます。

従来の `Int` 型の実装では、内部の `int64` フィールドへのアクセスを保護するために `sync.RWMutex` (読み書きミューテックス) を使用していました。ミューテックスは、複数のゴルーチンが共有データに同時にアクセスする際に発生する競合状態を防ぐための一般的な同期プリミティブです。しかし、ミューテックスのロック/アンロック操作には一定のオーバーヘッドが伴います。

特に、単一の整数値の読み書きや加算といった非常に単純な操作に対してミューテックスを使用すると、そのオーバーヘッドが操作自体のコストをはるかに上回ることがあります。`expvar.Int` のようなカウンタは頻繁に更新される可能性があるため、このオーバーヘッドはアプリケーション全体のパフォーマンスに影響を与える可能性があります。

コミットメッセージに示されているベンチマーク結果がこの問題を明確に示しています。ミューテックスを使用した `Add` 操作が139 ns/opかかるのに対し、アトミック操作を使用した場合は9.90 ns/opと、約14倍もの性能差があります。この劇的な性能差が、`sync/atomic` パッケージへの移行を決定づける背景となりました。

## 前提知識の解説

### 1. Go言語の並行処理と同期プリミティブ

Go言語はゴルーチン（軽量スレッド）とチャネル（ゴルーチン間の通信メカニズム）によって並行処理を強力にサポートしています。しかし、複数のゴルーチンが共有メモリにアクセスする際には、データ競合（data race）を防ぐための同期メカニズムが必要です。

### 2. `sync.Mutex` と `sync.RWMutex`

*   **`sync.Mutex`**: 最も基本的な排他ロックです。一度に一つのゴルーチンだけがロックを取得でき、共有リソースへのアクセスを排他的に保護します。
*   **`sync.RWMutex`**: 読み書きミューテックスです。
    *   **読み取りロック (RLock/RUnlock)**: 複数のゴルーチンが同時に読み取りロックを取得できます。これにより、読み取り操作が並行して行われることを許可し、読み取りの競合を減らします。
    *   **書き込みロック (Lock/Unlock)**: 一度に一つのゴルーチンだけが書き込みロックを取得できます。書き込みロックが取得されている間は、他の読み取りロックも書き込みロックも取得できません。
    `expvar.Int` の場合、`String()` メソッドでの読み取りには `RLock`、`Add()` や `Set()` メソッドでの書き込みには `Lock` を使用していました。

ミューテックスは、複雑なデータ構造や複数のフィールドを保護する場合に非常に有効ですが、ロックの取得と解放にはシステムコールやコンテキストスイッチなどのオーバーヘッドが伴うため、非常に粒度の細かい操作（例: 単一の整数操作）には不向きな場合があります。

### 3. `sync/atomic` パッケージ

`sync/atomic` パッケージは、CPUのハードウェアレベルでサポートされるアトミック操作を提供します。アトミック操作とは、不可分（indivisible）な操作のことで、その操作が完全に完了するか、全く行われないかのどちらかであり、途中で他のゴルーチンに割り込まれることがありません。これにより、ミューテックスのようなロック機構を使わずに、共有メモリ上の単一の値を安全に操作できます。

`sync/atomic` パッケージが提供する主な関数には以下のようなものがあります。
*   `atomic.AddInt64(addr *int64, delta int64)`: `*addr` に `delta` をアトミックに加算します。
*   `atomic.LoadInt64(addr *int64) int64`: `*addr` の値をアトミックに読み取ります。
*   `atomic.StoreInt64(addr *int64, val int64)`: `*addr` に `val` をアトミックに書き込みます。
*   `atomic.CompareAndSwapInt64(addr *int64, old, new int64) bool`: `*addr` の値が `old` と等しければ `new` に更新し、成功した場合は `true` を返します。

アトミック操作は、ミューテックスに比べてオーバーヘッドが非常に小さく、特に単一のワード（整数など）に対する操作において高いパフォーマンスを発揮します。これは、通常、CPUの特殊な命令（例: x86の`LOCK`プレフィックス付き命令）を利用して実装されるためです。

### 4. `expvar` パッケージ

`expvar` パッケージは、Goプログラムの実行中に、アプリケーションの内部メトリクス（変数）をHTTPエンドポイント `/debug/vars` 経由で公開するためのシンプルなメカニズムを提供します。これにより、プログラムの稼働状況を外部から監視したり、デバッグ情報を取得したりすることが容易になります。`Int` 型は、このパッケージで提供される基本的な変数型の一つで、整数値を公開するために使われます。

## 技術的詳細

このコミットの技術的詳細な変更点は、`src/expvar/expvar.go` ファイル内の `Int` 型の定義と、そのメソッドである `String()`, `Add()`, `Set()` の実装に集約されます。

1.  **`sync/atomic` パッケージのインポート**:
    まず、`expvar.go` のインポートリストに `sync/atomic` が追加されます。

    ```diff
    --- a/src/expvar/expvar.go
    +++ b/src/expvar/expvar.go
    @@ -32,6 +32,7 @@ import (
     	"sort"
     	"strconv"
     	"sync"
    +	"sync/atomic"
     )
    ```

2.  **`Int` 型の変更**:
    `Int` 型から `sync.RWMutex` のフィールド `mu` が削除されます。これにより、`Int` 型のインスタンスはミューテックスを保持する必要がなくなり、メモリフットプリントがわずかに削減されます。

    ```diff
    --- a/src/expvar/expvar.go
    +++ b/src/expvar/expvar.go
    @@ -41,26 +42,19 @@ type Var interface {

     // Int is a 64-bit integer variable that satisfies the Var interface.
     type Int struct {
    -	mu sync.RWMutex
    -	i  int64
    +	i int64
     }
    ```
    `i` フィールドは引き続き `int64` 型ですが、これからはアトミック操作によって保護されます。

3.  **`String()` メソッドの変更**:
    `String()` メソッドは `Int` の現在の値を文字列として返します。以前は `v.mu.RLock()` と `v.mu.RUnlock()` を使って読み取りロックを取得していましたが、これが `atomic.LoadInt64(&v.i)` に置き換えられます。`atomic.LoadInt64` は、指定されたアドレスにある `int64` の値をアトミックに読み取ります。これにより、ロックのオーバーヘッドなしに安全に値を読み取ることができます。

    ```diff
    --- a/src/expvar/expvar.go
    +++ b/src/expvar/expvar.go
    @@ -44,9 +38,7 @@ type Int struct {
     }

     func (v *Int) String() string {
    -	v.mu.RLock()
    -	defer v.mu.RUnlock()
    -	return strconv.FormatInt(v.i, 10)
    +	return strconv.FormatInt(atomic.LoadInt64(&v.i), 10)
     }
    ```

4.  **`Add()` メソッドの変更**:
    `Add()` メソッドは `Int` の値に `delta` を加算します。以前は `v.mu.Lock()` と `v.mu.Unlock()` を使って書き込みロックを取得し、`v.i += delta` を実行していました。これが `atomic.AddInt64(&v.i, delta)` に置き換えられます。`atomic.AddInt64` は、指定されたアドレスにある `int64` の値に `delta` をアトミックに加算します。この操作は、読み取り-変更-書き込み (Read-Modify-Write, RMW) のサイクルを単一のアトミック命令として実行するため、競合状態を発生させずに安全に値を更新できます。

    ```diff
    --- a/src/expvar/expvar.go
    +++ b/src/expvar/expvar.go
    @@ -50,9 +42,7 @@ func (v *Int) String() string {
     }

     func (v *Int) Add(delta int64) {
    -	v.mu.Lock()
    -	defer v.mu.Unlock()
    -	v.i += delta
    +	atomic.AddInt64(&v.i, delta)
     }
    ```

5.  **`Set()` メソッドの変更**:
    `Set()` メソッドは `Int` の値を `value` に設定します。以前は `v.mu.Lock()` と `v.mu.Unlock()` を使って書き込みロックを取得し、`v.i = value` を実行していました。これが `atomic.StoreInt64(&v.i, value)` に置き換えられます。`atomic.StoreInt64` は、指定されたアドレスに `int64` の値をアトミックに書き込みます。

    ```diff
    --- a/src/expvar/expvar.go
    +++ b/src/expvar/expvar.go
    @@ -56,9 +46,7 @@ func (v *Int) Add(delta int64) {
     }

     func (v *Int) Set(value int64) {
    -	v.mu.Lock()
    -	defer v.mu.Unlock()
    -	v.i = value
    +	atomic.StoreInt64(&v.i, value)
     }
    ```

これらの変更により、`expvar.Int` の操作は、ミューテックスのコンテンション（競合）によるパフォーマンスボトルネックから解放され、高並行環境下での効率が大幅に向上します。

## コアとなるコードの解説

このコミットの核心は、`expvar.Int` 型が内部で保持する `int64` 値へのアクセス方法を、`sync.RWMutex` を介したロックベースの同期から、`sync/atomic` パッケージが提供するロックフリーのアトミック操作へと切り替えた点にあります。

1.  **`sync.RWMutex` の削除**:
    `Int` 構造体から `mu sync.RWMutex` フィールドが削除されました。これは、もはやミューテックスによる保護が不要になったことを意味します。これにより、`Int` オブジェクトのサイズがわずかに小さくなり、ミューテックスの初期化やガベージコレクションのオーバーヘッドもなくなります。

2.  **`String()` メソッド**:
    変更前: `v.mu.RLock()` と `v.mu.RUnlock()` で読み取りロックを取得し、`v.i` を直接読み取っていました。
    変更後: `atomic.LoadInt64(&v.i)` を使用して、`v.i` の値をアトミックに読み取ります。この関数は、CPUのハードウェア命令を利用して、他のゴルーチンからの書き込みと競合することなく、常に最新の値を読み取ることを保証します。

3.  **`Add()` メソッド**:
    変更前: `v.mu.Lock()` と `v.mu.Unlock()` で書き込みロックを取得し、`v.i += delta` を実行していました。これは「読み取り-変更-書き込み」の3ステップからなる操作であり、ミューテックスがなければ競合状態（例: 複数のゴルーチンが同時に加算しようとして、一部の更新が失われる）が発生する可能性があります。
    変更後: `atomic.AddInt64(&v.i, delta)` を使用します。この関数は、指定されたアドレスの `int64` 値に `delta` をアトミックに加算します。これは単一の不可分な操作として実行されるため、ロックなしで安全に加算が可能です。

4.  **`Set()` メソッド**:
    変更前: `v.mu.Lock()` と `v.mu.Unlock()` で書き込みロックを取得し、`v.i = value` を実行していました。
    変更後: `atomic.StoreInt64(&v.i, value)` を使用して、`v.i` に `value` をアトミックに書き込みます。これにより、他のゴルーチンからの読み取りや書き込みと競合することなく、安全に値を設定できます。

この変更は、`expvar.Int` のような単純なカウンタにおいて、ミューテックスのコンテンションによるパフォーマンスのボトルネックを解消し、高負荷な環境下でも効率的なメトリクス収集を可能にするための重要な最適化です。アトミック操作は、ミューテックスよりも低レベルで、特定の単純な操作に特化しているため、より高速な実行が可能です。

## 元コミット内容

`cmd/compile: zero all three argstorage slots`

このコミットは、`argstorage`の3つのスロットすべてをゼロ初期化（nil設定）するように修正します。これは、`argstorage`スロットが2つから3つに増えた際に、その変更が見落とされていたことによるものです。

## 変更の背景

Goコンパイラの内部では、プログラムの最適化のためにSSA（Static Single Assignment）形式が用いられています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。SSA形式のコードは、`Value`と呼ばれるオブジェクトのグラフとして表現され、各`Value`は演算（Op）、型（Type）、引数（Args）などを持っています。

`Value`構造体には、その`Value`が表す演算の引数を保持するためのフィールドがあります。以前は、引数の数が少ない場合に最適化として、`Value`構造体内に直接引数を格納するための固定サイズの配列（`argstorage`）が用意されていました。これにより、ヒープアロケーションを避けてパフォーマンスを向上させていました。

この`argstorage`のサイズが、ある時点で2から3に拡張されました。これは、特定の種類の演算（例えば、3つの引数を取る演算）をより効率的に表現するため、または将来的な拡張性のためと考えられます。しかし、この拡張が行われた際に、`argstorage`の新しい3番目のスロットが適切に初期化されない、あるいはリセットされないという見落としがありました。

具体的には、`Value`が再利用される際や、引数が設定される際に、3番目のスロットに古い値が残ってしまう可能性がありました。これは、コンパイラの動作に予測不能なバグを引き起こしたり、メモリリークや不正なメモリ参照につながる可能性がありました。このコミットは、その見落としを修正し、`argstorage`のすべてのスロットが常に正しく管理されるようにすることを目的としています。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、中間表現としてSSA（Static Single Assignment）形式に変換します。SSA形式は、各変数が一度だけ代入されるようにプログラムを変換するもので、これによりデータフロー解析が非常に容易になり、様々な最適化（デッドコード削除、共通部分式除去、レジスタ割り当てなど）を効率的に適用できます。

SSAバックエンドでは、プログラムは`Value`オブジェクトの有向非巡回グラフ（DAG）として表現されます。各`Value`は、特定の演算（Op）とそのオペランド（引数）を表します。

### `Value`構造体と`argstorage`

GoコンパイラのSSAバックエンドにおける`Value`構造体は、SSAグラフのノードを表す中心的なデータ構造です。この構造体は、以下のような情報を含みます。

*   **Op**: 実行される演算の種類（例: `OpAdd`, `OpLoad`, `OpCall`など）。
*   **Type**: 演算結果の型。
*   **Args**: この`Value`のオペランド（引数）となる他の`Value`へのポインタのスライス。
*   **AuxInt**: 補助的な整数値（例: 定数、オフセットなど）。
*   **Aux**: 補助的なポインタ値（例: グローバル変数、関数ポインタなど）。
*   **argstorage**: `Value`構造体内に直接埋め込まれた、固定サイズの`*Value`型配列。引数の数が少ない場合に、ヒープアロケーションを避けて引数を格納するために使用されます。

`argstorage`は、`Value`の引数を格納するための最適化メカニズムです。引数の数が`argstorage`のサイズ以下の場合、`Args`スライスは`argstorage`の先頭を指すように設定され、引数は`argstorage`内に直接格納されます。これにより、小さなスライスを作成するためのヒープアロケーションが不要になり、コンパイラのパフォーマンスが向上します。引数の数が`argstorage`のサイズを超える場合は、別途ヒープにスライスが割り当てられます。

### ゼロ初期化（Zeroing）

プログラミングにおいて、変数をゼロ初期化するとは、その変数が使用される前に既知のデフォルト値（数値型なら0、ポインタ型ならnil、ブール型ならfalseなど）で埋めることを指します。これは、未初期化のメモリ内容が原因で発生する可能性のあるバグ（ガベージ値の使用、セキュリティ脆弱性など）を防ぐために重要です。特にポインタの場合、nilに設定することで、無効なメモリアドレスを指すことを防ぎ、ヌルポインタ参照として早期にエラーを検出できるようになります。

## 技術的詳細

このコミットの技術的詳細は、`Value`構造体の`argstorage`フィールドの管理方法にあります。

### `Value`の引数管理の仕組み

GoコンパイラのSSAバックエンドでは、`Value`オブジェクトが生成される際に、その演算に必要な引数が設定されます。引数の数が少ない場合（このコミットの時点では3つ以下）、`Value`構造体内部に定義された`argstorage`という固定サイズの配列が利用されます。

`Value`構造体には、`Args []*Value`というフィールドと、`argstorage [N]*Value`というフィールドがあります（Nは固定サイズ）。
`NewValueX`系の関数（`NewValue3`, `NewValue3I`など）が`Value`を生成する際、引数の数が`N`以下であれば、`v.Args`は`v.argstorage[:num_args]`のように設定され、実際の引数（`arg0`, `arg1`, `arg2`など）は`v.argstorage[0]`, `v.argstorage[1]`, `v.argstorage[2]`に直接代入されます。

### 以前の`argstorage`拡張と今回の修正

コミットメッセージによると、以前の変更で`argstorage`のサイズが2から3に拡張されました。これは、3つの引数を取る演算（例えば、`OpSelect0`, `OpSelect1`のようなタプルを分解する演算や、特定のメモリ操作など）を効率的に扱うためと考えられます。

しかし、この拡張時に、以下の2つの点で不整合が生じていました。

1.  **`NewValue3`および`NewValue3I`関数での引数設定**:
    これらの関数は3つの引数を取る`Value`を生成します。`argstorage`が2つのスロットしかなかった時代は、`v.Args = []*Value{arg0, arg1, arg2}`のように直接スライスを構築していましたが、`argstorage`が3つに拡張された後もこのコードが残っていました。この記述では、`argstorage`の3番目のスロットが明示的に利用されず、`v.Args`が新しいスライスを指すことになり、`argstorage`の最適化が十分に活用されない可能性がありました。また、`argstorage`の3番目のスロットに古いガベージ値が残る可能性もありました。
    今回の修正では、`v.Args = v.argstorage[:3]`と設定し、その後`v.argstorage[0] = arg0`, `v.argstorage[1] = arg1`, `v.argstorage[2] = arg2`とすることで、`argstorage`の3つのスロットすべてを明示的に利用し、かつ正しく引数を格納するように変更されました。

2.  **`resetArgs`関数でのスロットのゼロ初期化**:
    `resetArgs`関数は、`Value`オブジェクトが再利用される際などに、その引数をリセットするために呼び出されます。以前は、`v.argstorage[0] = nil`と`v.argstorage[1] = nil`しか行われておらず、`argstorage`の3番目のスロット（`v.argstorage[2]`）がnilに設定されていませんでした。
    このため、`Value`が再利用された際に、`v.argstorage[2]`に以前の`Value`の引数へのポインタが残ってしまう可能性がありました。これは、デバッグを困難にするような予測不能な動作や、メモリリーク、あるいは不正なメモリ参照を引き起こす原因となり得ます。
    今回の修正では、`v.argstorage[2] = nil`が追加され、`argstorage`のすべてのスロットが確実にnilに設定されるようになりました。

これらの修正により、`argstorage`の3つのスロットが常に正しく管理され、コンパイラの安定性と正確性が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/func.go` の変更

`NewValue3`および`NewValue3I`関数は、3つの引数を持つ`Value`を生成するファクトリ関数です。
変更前は、`v.Args = []*Value{arg0, arg1, arg2}`という行がありました。これは、新しい`[]*Value`スライスをヒープに割り当て、そこに引数を格納していました。
変更後は、以下のようになっています。

```go
v.Args = v.argstorage[:3]
v.argstorage[0] = arg0
v.argstorage[1] = arg1
v.argstorage[2] = arg2
```

この変更のポイントは以下の通りです。

1.  **`v.Args = v.argstorage[:3]`**: `v.Args`スライスが、`Value`構造体内部に埋め込まれた`argstorage`配列の最初の3つの要素を指すように設定されます。これにより、ヒープアロケーションが不要になり、パフォーマンスが向上します。
2.  **`v.argstorage[0] = arg0`, `v.argstorage[1] = arg1`, `v.argstorage[2] = arg2`**: 各引数が`argstorage`の対応するスロットに直接代入されます。これにより、`argstorage`の3つのスロットすべてが明示的に、かつ正しく初期化されます。

この修正により、`argstorage`の最適化が意図通りに機能し、3つの引数を持つ`Value`が生成される際に、`argstorage`の3番目のスロットが確実に利用され、正しい値が格納されるようになります。

### `src/cmd/compile/internal/ssa/value.go` の変更

`resetArgs`関数は、`Value`オブジェクトが再利用される前に、その内部状態をクリーンアップするために呼び出されます。特に、`Args`スライスと`argstorage`の内容をnilに設定することで、古いポインタが残ることを防ぎます。

変更前は、`v.argstorage[0] = nil`と`v.argstorage[1] = nil`しか行われていませんでした。
変更後は、`v.argstorage[2] = nil`が追加されています。

```diff
--- a/src/cmd/compile/internal/ssa/value.go
+++ b/src/cmd/compile/internal/ssa/value.go
@@ -185,6 +185,7 @@ func (v *Value) resetArgs() {\n 	}\n 	v.argstorage[0] = nil\n 	v.argstorage[1] = nil\n+	v.argstorage[2] = nil
 	v.Args = v.argstorage[:0]\n }\n \n```

この追加により、`argstorage`が3つのスロットを持つようになった後も、すべてのスロットが確実にnilに設定されるようになります。これにより、`Value`が再利用された際に、以前の引数へのポインタが`v.argstorage[2]`に残存することによる潜在的なバグが解消されます。これは、コンパイラのメモリ管理の正確性を保ち、予測不能な動作を防ぐ上で非常に重要です。

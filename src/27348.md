# [インデックス 27348] ファイルの概要

このコミットは、Go言語の`testing`パッケージにテストおよびベンチマーク名の「マッチャー（matcher）」と「サニタイザー（sanitizer）」を導入します。これにより、テストおよびベンチマーク名の正規化、一意化、フィルタリングが可能になります。

変更されたファイルは以下の通りです。

*   `src/testing/benchmark.go`: ベンチマーク実行コンテキストに`matcher`を統合し、ベンチマーク名の処理を変更。
*   `src/testing/match.go`: 新規ファイル。`matcher`構造体とその関連ロジック（名前の一意化、サニタイズ、フィルタリング）を定義。
*   `src/testing/match_test.go`: 新規ファイル。`matcher`の命名規則とサニタイズ機能に関するテスト。
*   `src/testing/sub_test.go`: テストコンテキストの初期化時に`matcher`を使用するように変更。
*   `src/testing/testing.go`: テスト実行コンテキストに`matcher`を統合し、テスト名の処理を変更。

## 変更の背景

このコミットの主な背景は、Goの`testing`パッケージにおけるサブテスト（subtest）およびサブベンチマーク（subbenchmark）機能の導入に向けた基盤整備です。当時、Goのテストフレームワークはトップレベルのテスト関数やベンチマーク関数のみをサポートしており、テスト内部でさらに細分化されたテストケースを定義する「サブテスト」の概念はまだ正式に導入されていませんでした。

サブテストを導入するにあたり、以下のような課題がありました。

1.  **名前の一意性（Uniqueness）**: サブテストは親テストの名前を継承し、それに自身の名前を追加する形で階層的な名前を持つことになります。同じ親テスト内で同じ名前のサブテストが複数定義された場合、それらを区別し、一意な名前を割り当てるメカニズムが必要でした。
2.  **名前のサニタイズ（Sanitization）**: テスト名やベンチマーク名には、ファイルシステムパスや正規表現、コマンドライン引数などで問題を引き起こす可能性のある特殊文字や非表示文字が含まれる可能性があります。これらの文字を安全な形式に変換（サニタイズ）する機能が求められました。
3.  **フィルタリングの改善**: `go test -run <regexp>`や`go test -bench <regexp>`といったコマンドラインオプションでテストやベンチマークをフィルタリングする際、サブテストの階層構造を考慮したマッチングが必要になります。このコミットでは、まずトップレベルのマッチングに`matcher`を適用し、将来的なサブテストマッチングの準備をしています。

このコミットは、これらの課題に対処するための「マッチャー」と「サニタイザー」という共通のロジックを導入し、将来的にサブテストAPIが公開されるための重要な前段階として位置づけられています。

## 前提知識の解説

### Goの`testing`パッケージ

Go言語には標準ライブラリとして`testing`パッケージが提供されており、ユニットテストやベンチマークテストを記述するためのフレームワークが含まれています。

*   **テスト関数**: `func TestXxx(t *testing.T)`というシグネチャを持つ関数で、`go test`コマンドによって実行されます。`t *testing.T`はテストの状態を管理し、エラー報告やテストのスキップなどの機能を提供します。
*   **ベンチマーク関数**: `func BenchmarkXxx(b *testing.B)`というシグネチャを持つ関数で、`go test -bench .`コマンドによって実行されます。`b *testing.B`はベンチマークの状態を管理し、実行時間の計測やイテレーション回数の調整などを行います。
*   **テスト/ベンチマークの選択**:
    *   `go test -run <regexp>`: 指定された正規表現にマッチする名前のテスト関数のみを実行します。
    *   `go test -bench <regexp>`: 指定された正規表現にマッチする名前のベンチマーク関数のみを実行します。
    *   これらの正規表現は、通常、トップレベルのテスト/ベンチマーク名に対して適用されます。

### サブテストとサブベンチマーク（導入前夜の状況）

このコミットが作成された2016年時点では、Goの`testing`パッケージにはまだ公式なサブテスト/サブベンチマークの概念はありませんでした。しかし、コミュニティではより柔軟なテスト構造を求める声があり、この機能の導入が検討されていました。サブテストは、一つのテスト関数内で`t.Run("subtest_name", func(t *testing.T) { ... })`のように呼び出すことで、階層的なテストを記述できるようにするものです。これにより、テストのセットアップ/ティアダウンの共有、テスト結果のグループ化、特定のサブテストのみの実行などが容易になります。

このコミットは、まさにこのサブテスト機能が正式に導入される前に、その名前の管理（一意化とサニタイズ）という重要な側面を解決するために行われました。

## 技術的詳細

このコミットの核となるのは、`src/testing/match.go`で新しく導入された`matcher`構造体です。

### `matcher`構造体

```go
type matcher struct {
	filter    string
	matchFunc func(pat, str string) (bool, error)

	mu       sync.Mutex
	subNames map[string]int64
}
```

*   `filter`: `go test -run`や`-test.bench`で指定される正規表現パターンを保持します。
*   `matchFunc`: 正規表現マッチングを実行する関数（通常は`regexp.MatchString`）を保持します。
*   `mu sync.Mutex`: `subNames`マップへのアクセスを保護するためのミューテックスです。並行実行されるテストやベンチマークから安全に名前を生成するために必要です。
*   `subNames map[string]int64`: 生成されたテスト/ベンチマーク名とその出現回数を記録するためのマップです。これにより、名前の一意性を保証します。

### `newMatcher`関数

`newMatcher`は`matcher`のコンストラクタです。
```go
func newMatcher(matchString func(pat, str string) (bool, error), pattern, name string) *matcher {
	// Verify filters before doing any processing.
	if _, err := matchString(pattern, "non-empty"); err != nil {
		fmt.Fprintf(os.Stderr, "testing: invalid regexp for %s: %s\\n", name, err)
		os.Exit(1)
	}
	return &matcher{
		filter:    pattern,
		matchFunc: matchString,
		subNames:  map[string]int64{},
	}
}
```
この関数は、提供された正規表現パターンが有効であるかを事前に検証します。無効な場合はエラーを出力してプログラムを終了させます。

### `fullName`メソッド

`matcher`の主要なメソッドの一つで、テスト/ベンチマークの完全な名前を生成し、フィルタリングを行います。
```go
func (m *matcher) fullName(c *common, subname string) (name string, ok bool) {
	name = subname

	m.mu.Lock()
	defer m.mu.Unlock()

	if c != nil && c.level > 0 { // c.level > 0 はサブテスト/サブベンチマークであることを示す
		name = m.unique(c.name, rewrite(subname))
	}

	matchMutex.Lock() // グローバルなマッチングロック
	defer matchMutex.Unlock()

	if c != nil && c.level == 0 { // トップレベルのテスト/ベンチマークの場合
		if matched, _ := m.matchFunc(m.filter, subname); !matched {
			return name, false // フィルタにマッチしない場合は実行しない
		}
	}
	return name, true
}
```
このメソッドは、`common`構造体（`testing.T`や`testing.B`の基底）の`level`フィールドを見て、それがサブテスト/サブベンチマークであるか（`c.level > 0`）を判断します。サブテストの場合、親の名前と自身の名前を組み合わせて`unique`メソッドで一意な名前を生成します。また、トップレベルのテスト/ベンチマークに対しては、`filter`（`-test.run`や`-test.bench`で指定された正規表現）に基づいてマッチングを行い、実行するかどうかを決定します。

### `unique`メソッド

テスト/ベンチマーク名の一意性を保証します。
```go
func (m *matcher) unique(parent, subname string) string {
	name := fmt.Sprintf("%s/%s", parent, subname)
	empty := subname == ""
	for {
		next, exists := m.subNames[name]
		if !empty && !exists {
			m.subNames[name] = 1 // next count is 1
			return name
		}
		// Name was already used. We increment with the count and append a
		// string with the count.
		m.subNames[name] = next + 1

		// Add a count to guarantee uniqueness.
		name = fmt.Sprintf("%s#%02d", name, next)
		empty = false
	}
}
```
このメソッドは、`parent/subname`の形式で名前を構築します。もしこの名前が既に`subNames`マップに存在する場合、`#XX`という形式のサフィックス（例: `test/subtest#01`）を追加して名前を一意にします。これにより、同じ名前のサブテストが複数存在しても、それぞれが異なる完全な名前を持つことが保証されます。

### `rewrite`メソッド

テスト/ベンチマーク名をサニタイズします。
```go
func rewrite(s string) string {
	b := []byte{}
	for _, r := range s {
		switch {
		case isSpace(r):
			b = append(b, '_')
		case !strconv.IsPrint(r):
			s := strconv.QuoteRune(r)
			b = append(b, s[1:len(s)-1]...)
		default:
			b = append(b, string(r)...)
		}
	}
	return string(b)
}
```
この関数は、テスト名に含まれる特殊文字や空白文字を安全な形式に変換します。
*   空白文字（`isSpace`で定義される）はアンダースコア`_`に置換されます。
*   印字不可能な文字（`strconv.IsPrint`で判定）は、Goのruneリテラル形式（例: `\x01`, `\U0010ffff`）に変換されます。
*   その他の文字はそのまま保持されます。

これにより、生成されるテスト名がファイルシステムパスやログ出力などで問題を起こしにくくなります。

## コアとなるコードの解説

このコミットの核心は、Goのテストおよびベンチマークフレームワークにおける名前の管理を一元化し、堅牢にすることです。

1.  **`matcher`の一元化**: 以前は、テストとベンチマークのフィルタリングロジックがそれぞれの実行関数（`runBenchmarksInternal`や`RunTests`）内に散在していました。このコミットでは、`matcher`構造体を導入し、名前の正規表現マッチング、一意化、サニタイズといった共通の処理を`match.go`に集約しました。これにより、コードの重複が排除され、将来的な機能拡張（特にサブテスト）が容易になります。

2.  **サブテスト/サブベンチマークの準備**: `testing.T`と`testing.B`の`run`メソッドが`matcher.fullName`を使用するように変更されたことは非常に重要です。
    *   `t.run(name, f)`や`b.runBench(name, f)`が呼び出される際、`fullName`メソッドが親テスト/ベンチマークの名前（`c.name`）と現在のサブテスト/サブベンチマークの名前（`subname`）を組み合わせて、最終的な完全な名前を生成します。
    *   この際、`unique`メソッドによって、同じ階層で同じ名前が複数回使われた場合に自動的に`#00`, `#01`といったサフィックスが付与され、名前の一意性が保証されます。
    *   `rewrite`メソッドによって、ユーザーが指定したテスト名に特殊文字が含まれていても、内部的には安全な形式に変換されます。

3.  **フィルタリングロジックの変更**: トップレベルのテスト/ベンチマークに対するフィルタリング（`-test.run`や`-test.bench`）も`matcher.fullName`を通じて行われるようになりました。これにより、フィルタリングロジックも`matcher`にカプセル化され、テスト実行の全体的なフローがより整合性の取れたものになります。

この変更により、Goの`testing`パッケージは、サブテストやサブベンチマークといったより複雑なテスト構造をサポートするための強固な基盤を手に入れました。名前の一意性とサニタイズは、これらの新機能が安定して動作するために不可欠な要素です。

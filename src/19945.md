## 変更の背景

Goランタイムは、ガベージコレクション（GC）の効率を継続的に改善しています。このコミットの背景には、GCの「マーキングフェーズ」と「スタック縮小」処理の間の潜在的な競合と、それによるパフォーマンスボトルネックがありました。

以前のGoランタイムでは、ゴルーチン（Goの軽量スレッド）のスタックは、必要に応じて動的に拡大・縮小します。特に、使用されていないスタック領域を解放するためにスタックを縮小する処理（`shrinkstack`）は、GCのサイクル中に実行されていました。しかし、この`shrinkstack`処理が通常のヒープ領域にアクセスする可能性があったため、GCのマーキングフェーズ（到達可能なオブジェクトをマークするフェーズ）と並行して実行することが困難でした。もし並行して実行された場合、ヒープの一貫性が損なわれたり、GCが誤った判断を下したりするリスクがありました。

この制約により、`shrinkstack`はGCの特定のフェーズ（例えば、マーキングが完了した後）で、すべてのゴルーチンに対して順次実行される必要がありました。これは、特に多数のゴルーチンが存在する場合や、スタック縮小が必要なゴルーチンが多い場合に、GCの停止時間（STW: Stop-The-World）を延長させる要因となっていました。

このコミットは、`shrinkstack`の実装が変更され、通常のヒープに触れなくなったという前提に基づいています。この変更により、`shrinkstack`がヒープの整合性に影響を与えることなく、GCのマーキングフェーズと並行して安全に実行できるようになりました。これにより、GCの全体的な効率とスループットが向上し、アプリケーションのレイテンシが削減されることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **ゴルーチンとスタック**:
    *   **ゴルーチン (Goroutine)**: Go言語の軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。
    *   **スタック (Stack)**: 各ゴルーチンは独自の実行スタックを持っています。このスタックは、関数の呼び出し、ローカル変数の保存、関数の引数などに使用されます。Goのスタックは、必要に応じて動的に拡大・縮小する「可変スタック（resizable stack）」です。これにより、初期スタックサイズを小さく保ちつつ、深い再帰呼び出しなどにも対応できます。
    *   **スタック縮小 (Stack Shrinking)**: ゴルーチンが使用するスタック領域が、実際に必要な量よりもはるかに大きい場合、ランタイムはスタックを縮小してメモリを解放します。これはメモリ効率を高めるために重要です。

2.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、主に「並行マーク・スイープ（Concurrent Mark-Sweep）」アルゴリズムをベースにしています。これは、アプリケーションの実行と並行してGCの大部分の処理を行うことで、STW時間を最小限に抑えることを目指しています。
    *   **マーキングフェーズ (Marking Phase)**: GCの重要なフェーズの一つで、ルート（グローバル変数、実行中のゴルーチンのスタックなど）から到達可能なすべてのオブジェクトを特定し、マークします。このフェーズ中に、到達可能なオブジェクトが誤って解放されないように、ヒープの一貫性が非常に重要になります。
    *   **並行性 (Concurrency)**: GoのGCは、可能な限り多くの処理をアプリケーションの実行と並行して行います。これにより、GCによるアプリケーションの一時停止（STW）を短くし、レイテンシを低減します。

3.  **`mgc0.c` ファイル**:
    *   `src/pkg/runtime/mgc0.c` は、Goランタイムのガベージコレクションのコアロジックが実装されているC言語のファイルです。GCの初期化、マーキング、スイープなどの主要な関数が含まれています。

## 技術的詳細

このコミットの技術的な詳細を掘り下げます。

GoのGCは、大きく分けて以下のフェーズで構成されます（簡略化されています）：
1.  **マーク準備 (Mark Setup)**: 短いSTWフェーズ。GCを開始するための準備を行います。
2.  **並行マーキング (Concurrent Marking)**: アプリケーションの実行と並行して、到達可能なオブジェクトをマークします。
3.  **マーク終了 (Mark Termination)**: 短いSTWフェーズ。並行マーキングで取りこぼしたオブジェクトを処理したり、GCの最終的な状態を確定させたりします。
4.  **並行スイープ (Concurrent Sweeping)**: アプリケーションの実行と並行して、マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放します。

このコミット以前は、`runtime·shrinkstack`の呼び出しは、GCの`gc`関数内で、すべてのゴルーチンに対してループで順次実行されていました。これは、`gc`関数がGCの主要な制御フローを担う場所であり、スタック縮小がヒープの整合性に影響を与える可能性があったため、GCの特定の安全なポイントで実行する必要があったからです。

コミットメッセージにある「Shrinkstack does not touch normal heap anymore」という記述は非常に重要です。これは、`runtime·shrinkstack`関数の内部実装が変更され、スタックの縮小処理がヒープ上のオブジェクトの参照を変更したり、ヒープの構造を直接操作したりしなくなったことを意味します。例えば、スタックがヒープに割り当てられたメモリを参照している場合でも、その参照自体を移動させるだけで、ヒープ上のオブジェクト自体には触れないようになった、といった変更が考えられます。

この変更により、`runtime·shrinkstack`はGCのマーキングフェーズと並行して実行しても安全になりました。なぜなら、マーキングフェーズの主な目的はヒープ上のオブジェクトの到達可能性を正確に追跡することであり、`shrinkstack`がヒープに触れないのであれば、マーキング処理の正確性や一貫性を損なうリスクがなくなるからです。

コミットの変更点を見ると、`gc`関数内の`for`ループが削除され、代わりに`markroot`関数内で`runtime·shrinkstack(gp)`が呼び出されています。`markroot`関数は、GCのマーキングフェーズ中に各ゴルーチン（`gp`はゴルーチンポインタ）のルートを処理する際に呼び出される関数です。つまり、各ゴルーチンがGCによって処理される際に、そのゴルーチンのスタック縮小が同時に試みられるようになったということです。

これにより、スタック縮小処理がGCのマーキングフェーズに「組み込まれ」、並行して実行されるようになりました。これは、GCのSTW時間をさらに短縮し、全体的なGCの効率を向上させるための重要な最適化です。スタック縮小がGCのメインサイクルから分離され、並行処理の一部として実行されることで、GCのレイテンシが改善されます。

## コアとなるコードの解説

このコミットのコアとなる変更は以下の2点です。

1.  **`gc` 関数からのスタック縮小ループの削除**:
    *   変更前の`gc`関数（ガベージコレクションのメイン関数）には、以下のコードがありました。
        ```c
        // Shrink a stack if not much of it is being used.
        // TODO: do in a parfor
        for(i = 0; i < runtime·allglen; i++)
            runtime·shrinkstack(runtime·allg[i]);
        ```
    *   このループは、GCサイクル中にすべてのゴルーチン（`runtime·allg`配列に格納されている）を順に処理し、それぞれのスタックを縮小しようとしていました。この処理は、GCの他の並行フェーズとは独立して、おそらくSTWフェーズ中、または並行処理が安全でないと判断されたフェーズで実行されていました。
    *   このコミットでは、上記の`for`ループと、それに伴う変数`i`の宣言が削除されました。これは、スタック縮小処理がもはやこの場所で一括して実行される必要がなくなったことを意味します。

2.  **`markroot` 関数へのスタック縮小呼び出しの追加**:
    *   変更後の`markroot`関数（GCのマーキングフェーズでゴルーチンのルートを処理する関数）に、以下の行が追加されました。
        ```c
        // Shrink a stack if not much of it is being used.
        runtime·shrinkstack(gp);
        ```
    *   `markroot`関数は、GCの並行マーキングフェーズ中に、各ゴルーチン（`gp`は現在のゴルーチンポインタ）のスタックをスキャンする前に呼び出されます。
    *   この変更により、各ゴルーチンがGCによって「マーク」される際に、そのゴルーチンのスタックが同時に縮小されるようになりました。つまり、スタック縮小処理がGCの並行マーキングフェーズの一部として実行されるようになり、GCの全体的な停止時間を短縮し、スループットを向上させる効果があります。

この変更は、`runtime·shrinkstack`がヒープに触れなくなったという前提に基づいています。これにより、GCのマーキングフェーズ中にスタック縮小を実行しても、ヒープの整合性が損なわれることなく、安全に並行処理が可能になったため、GCの効率が向上しました。

## 変更の背景

Go言語のツールチェインの一部であるアセンブラ (`cmd/asm`) は、Goプログラムから呼び出されるアセンブリコードを処理します。`TEXT` 疑似命令は、アセンブリ関数を定義する際に、その関数のスタックフレームサイズと引数サイズを指定するために使用されます。

以前の `TEXT` 命令のパースロジックは、`$frameSize-argSize` という形式の引数に対して、より複雑で汎用的な式を解析できるような設計になっていました。しかし、実際のGoアセンブリコードでは、この部分に複雑な式が使われることはなく、常にシンプルな整数リテラルが使用されていました。この乖離がパースロジックの不必要な複雑さを生み出し、保守性を低下させていました。

このコミットの背景には、アセンブラのコードベースを簡素化し、より堅牢で理解しやすいものにするという目的があります。特に、Goのツールチェインは継続的に進化しており、その中で各コンポーネントの効率性と正確性を高めることは重要な課題です。不必要な複雑さを取り除くことで、将来的な機能追加やバグ修正が容易になります。

また、`TODO` コメントの追加は、将来的な改善点や未解決の問題をコードベースに明示的に残すGoコミュニティの一般的なプラクティスを反映しています。これにより、開発者はコードの特定の領域がまだ最適化されていない、あるいはより一般的なアプローチが必要であることを認識できます。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての基本的な知識が必要です。

*   **Go言語のアセンブリ (Plan 9 Assembly):** Go言語は、独自のPlan 9アセンブリ構文を使用します。これは一般的なx86アセンブリとは異なる記法を持ち、Goのツールチェインと密接に統合されています。Goのアセンブリは、主にパフォーマンスが重要な部分や、Goランタイムの低レベルな操作（スケジューラ、ガベージコレクタなど）を実装するために使用されます。
*   **`cmd/asm`:** Goツールチェインの一部であるアセンブラです。Plan 9アセンブリコードをオブジェクトファイルにコンパイルする役割を担います。
*   **疑似命令 (Pseudo-operations):** アセンブラの命令には、CPUが直接実行する機械語に変換される「機械命令」と、アセンブラに対する指示である「疑似命令」があります。`TEXT`, `DATA`, `GLOBL` などは疑似命令であり、アセンブラにコードやデータの配置、シンボルの可視性などを指示します。
*   **`TEXT` 疑似命令:** Goアセンブリにおいて関数を定義するために使用されます。基本的な形式は `TEXT symbol(SB), flags, $frameSize-argSize` です。
    *   `symbol(SB)`: 関数のシンボル名と、`SB` (Static Base) を基準としたアドレスを示します。
    *   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT` など）。
    *   `$frameSize-argSize`: このコミットの主要な焦点です。
        *   `frameSize`: 関数が使用するスタックフレームのサイズ（ローカル変数、レジスタ退避領域など）。
        *   `argSize`: 関数が引数として受け取るバイト数。
        *   この `$frameSize-argSize` という記法は、`frameSize` と `argSize` を区切るためのものであり、数学的な減算を意味するものではありません。
*   **`obj.Prog`:** Goのオブジェクトファイルフォーマット (`cmd/obj`) におけるプログラム命令の内部表現です。アセンブラはソースコードをパースし、この `obj.Prog` 構造体のリストに変換します。
*   **`addr.Addr`:** アセンブリ命令のオペランド（アドレス、レジスタ、定数など）を表現するための内部構造体です。
*   **`lex.Token` と `scanner.Int`:** 字句解析（lexical analysis）の段階で生成されるトークンを表します。`scanner.Int` は整数リテラルを表すトークンタイプです。
*   **`obj.ArgsSizeUnknown`:** `argSize` が指定されていない場合に、引数サイズが不明であることを示す定数です。

## 技術的詳細

このコミットの主要な技術的変更点は、`src/cmd/asm/internal/asm/asm.go` 内の `asmText` 関数における `TEXT` 疑似命令の `$frameSize-argSize` 引数のパースロジックの書き換えです。

**変更前:**
変更前のパースロジックは、`$frameSize-argSize` の `argSize` 部分がオプションであり、かつ `frameSize` も含めてより複雑な式を許容するような汎用的なアプローチを取っていました。特に `argSize` の部分を `op[n-1:]` のようにスライスして `p.expr()` で解析するような処理があり、これは `scanner.Int` 以外のトークンも考慮する可能性がありました。また、`$-8` のような特殊なケースも扱っていました。

**変更後:**
新しいパースロジックは、より厳密な構文規則を適用します。

1.  **`$` 記号の必須化:** `TEXT` 命令のフレームサイズは必ず `$` で始まることが必須となりました (`if len(op) < 2 || op[0].ScanToken != '$'`)。
2.  **`frameSize` の解析:**
    *   `$` の次のトークンからパースを開始します。
    *   負の符号 (`-`) がオプションで許容されます (`negative := false; if op[0].ScanToken == '-'`)。
    *   負の符号の次、または `$` の次のトークンは必ず整数リテラル (`scanner.Int`) であることが必須です (`if len(op) == 0 || op[0].ScanToken != scanner.Int`)。
    *   `p.positiveAtoi` という新しいヘルパー関数が導入され、文字列から非負の整数を安全にパースします。これにより、`frameSize` が負の値になる可能性を考慮しつつ、パースエラーを適切に処理します。
3.  **`argSize` の解析:**
    *   `frameSize` の後にトークンが残っている場合、それは `argSize` を表します。
    *   `argSize` は必ず `-integer` の形式である必要があります (`if len(op) != 2 || op[0].ScanToken != '-' || op[1].ScanToken != scanner.Int`)。
    *   `argSize` も `p.positiveAtoi` を使用して非負の整数としてパースされます。
    *   `argSize` が存在しない場合は `obj.ArgsSizeUnknown` が使用されます。

この変更により、`TEXT $frameSize-argSize` のパースは、`frameSize` と `argSize` がそれぞれシンプルな整数リテラル（`frameSize` は負の可能性あり、`argSize` は正）であることを前提とするようになり、不必要な汎用性が排除されました。

**型定義のクリーンアップ (`src/cmd/asm/internal/arch/arch.go`):**
`Arch` 構造体内の `D_INDIR` と `D_CONST2` フィールドの型が `int16` から `int` に変更されました。これは、これらの値が `int16` の範囲に収まることが保証されているにもかかわらず、Goの型システムにおける暗黙的な型変換や、より広い範囲を扱う可能性を考慮して、より一般的な `int` 型に統一されたものと考えられます。これにより、将来的な変更に対する柔軟性が向上し、不必要な型変換のキャストを減らすことができます。

**`TODO` コメントの追加/修正:**
*   `src/cmd/asm/internal/asm/asm.go` の `addrToAddr` 関数に、アドレスパースの「ハック的で不規則な」性質に関する新しい `TODO` コメントが追加されました。これは、`4(R1)(R2*8)` のような複雑なアドレス指定のパースが、現在のところケースバイケースで処理されており、より一般的なアプローチが必要であるという認識を示しています。これは、アセンブラの将来的な改善点として挙げられています。
*   `asmText` 関数内の `TEXT` フラグのパースに関する `TODO` コメントも更新され、現在必須として扱われているが、実際にはオプションであるべきという点が指摘されています。
*   `p.link` メソッドが `p.append` にリネームされました。これは、`obj.Prog` をリンクリストに追加する操作の意図をより明確にするためのリファクタリングです。

これらの変更は、アセンブラのコードベースの正確性、堅牢性、および保守性を向上させることを目的としています。特に、パースロジックの簡素化は、バグの発生を減らし、新しい開発者がコードを理解しやすくすることに貢献します。

## コアとなるコードの解説

### `src/cmd/asm/internal/arch/arch.go` の変更

`D_INDIR` と `D_CONST2` の型が `int16` から `int` に変更されました。
これは、これらの定数が `obj.LinkArch` に含まれるべきではないかという `TODO` コメントが示唆するように、アーキテクチャ固有の定数であり、より汎用的な `int` 型にすることで、将来的な拡張性や、`int16` への不必要なキャストを避けるための変更と考えられます。`int` はGoにおいてプラットフォーム依存のサイズを持つ整数型ですが、通常は32ビットまたは64ビットであり、`int16` よりも広い範囲を表現できます。

### `src/cmd/asm/internal/asm/asm.go` の変更

1.  **`addrToAddr` 関数の `TODO` コメント:**
    `addrToAddr` 関数は、アセンブリコードのアドレス表現 (`addr.Addr`) を、リンカが理解できるオブジェクトファイルのアドレス表現 (`obj.Addr`) に変換する役割を担っています。追加された `TODO` コメントは、現在の実装が `4(R1)(R2*8)` のような複雑なアドレス指定を「ハック的で不規則」な方法で処理していることを指摘しています。これは、特定のケースを個別に処理するのではなく、より「一般的なアプローチ」が必要であるという認識を示しており、アセンブラのパースロジックにおける将来的な改善の方向性を示唆しています。

2.  **`p.link` から `p.append` へのリネーム:**
    `p.link` メソッドは、パースされた `obj.Prog` (プログラム命令) をパーサーの内部リンクリストに追加する役割を担っていました。このメソッドが `p.append` にリネームされたのは、その機能が「リンクする」というよりも「追加する」という操作をより正確に表現するためです。これは純粋なリファクタリングであり、機能的な変更はありませんが、コードの可読性と意図の明確化に貢献します。

3.  **`asmText` 関数の `TEXT` 引数パースロジックの書き換え:**
    これがこのコミットの最も重要な変更点です。
    *   **旧ロジックの課題:** 以前のロジックは、`$frameSize-argSize` の `argSize` 部分を `p.expr()` でパースしようとしていました。`p.expr()` はより複雑な式を解析できるため、シンプルな整数リテラルしか来ないはずの場所で過剰な汎用性を持っていました。また、`locals` と `args` という変数名が使われていましたが、これは `frameSize` と `argSize` を指しており、混乱を招く可能性がありました。
    *   **新ロジックの改善:**
        *   `op = op[1:]` で `$` 記号をスキップし、引数の本体を処理します。
        *   `negative := false; if op[0].ScanToken == '-'` で `frameSize` が負の数である可能性を適切に処理します。
        *   `p.positiveAtoi(op[0].String())` を使用して、`frameSize` と `argSize` を非負の整数として安全にパースします。これにより、`strconv.ParseInt` のエラーハンドリングと、負の値のチェックがカプセル化されます。
        *   `argSize` のパースでは、`len(op) != 2 || op[0].ScanToken != '-' || op[1].ScanToken != scanner.Int` という厳密なチェックが追加され、`-integer` 形式以外の入力はエラーとして扱われます。
        *   変数名が `frameSize` と `argSize` に変更され、コードの意図がより明確になりました。
        *   `prog.To.Offset` と `prog.To.Offset2` への値のエンコーディングも、`locals` と `args` から `frameSize` と `argSize` に対応するように修正されました。これにより、アーキテクチャ (`'6'` (amd64) と `'8'` (386)) ごとのエンコーディングが正しく行われます。

この書き換えにより、`TEXT` 命令の引数パースは、Goアセンブリの実際の使用パターンに厳密に合致するようになり、不必要な複雑さが排除され、エラーチェックが強化されました。

### `src/cmd/asm/internal/asm/parse.go` の変更

1.  **`line()` 関数のラベルパースロジックの簡素化:**
    `line()` 関数は、アセンブリソースコードの各行をパースする役割を担っています。変更前は `first` というフラグを使って最初のトークンがラベルであるかどうかを判断していましたが、変更後は `tok == ':' && len(operands) == 0 && len(items) == 0` という条件で、コロンが最初のトークンとして現れた場合にラベルとして処理するように簡素化されました。これにより、ラベルの検出ロジックがより直接的で分かりやすくなりました。

2.  **`positiveAtoi` ヘルパー関数の追加:**
    この新しい関数は、文字列を `int64` に変換し、その値が非負であることを保証します。
    ```go

        value, err := strconv.ParseInt(str, 0, 64)
        if err != nil {
            p.errorf("%s", err) // パースエラーを報告
        }
        if value < 0 {
            p.errorf("%s overflows int64", str) // 負の値はエラー（オーバーフローとして扱う）
        }
        return value
    }
    ```
    この関数は `asmText` 関数で `frameSize` と `argSize` をパースする際に使用されます。`frameSize` は負の可能性があるので、`positiveAtoi` でパースした後に符号を反転させるロジックが `asmText` 側にあります。`argSize` は常に正の整数として扱われるため、`positiveAtoi` の結果をそのまま使用します。このヘルパー関数により、数値パースとエラーハンドリングのロジックが共通化され、コードの重複が減り、堅牢性が向上しました。

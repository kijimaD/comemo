## 変更の背景

Go言語は、その高性能と並行処理能力で知られていますが、その裏側には効率的なガベージコレクタ（GC）と、必要に応じて低レベルな操作を可能にするアセンブリ言語のサポートがあります。Goのアセンブリ言語は、C言語のアセンブリとは異なり、Goランタイムと密接に連携するように設計されています。特に、ガベージコレクタが正しく動作するためには、プログラム内のポインタの位置を正確に把握している必要があります。

このコミットが行われた2014年当時、Goのアセンブリプログラミングに関する公式ドキュメントは存在していましたが、アセンブリコードがGoのガベージコレクタとどのように協調すべきか、特にポインタ情報の提供方法については、詳細な説明が不足していました。これにより、アセンブリコードを書く開発者が、GCの正確な動作を妨げるようなコードを意図せず書いてしまうリスクがありました。

`Fixes #8712` という記述は、このコミットが特定の課題（おそらくドキュメントの不足や誤解に関するもの）を解決したことを示唆しています。この課題は、アセンブリコードとGCの連携に関する明確なガイドラインの必要性から生じたものと考えられます。このコミットは、Goのアセンブリプログラミングをより安全かつ効率的に行うための、重要なドキュメント改善の一環として実施されました。

## 前提知識の解説

このコミットの理解には、以下の概念に関する知識が役立ちます。

1.  **Go言語のアセンブリ言語**: Goは独自の（Plan 9アセンブラに似た）アセンブリ言語を使用します。これは一般的なx86/x64アセンブリとは構文が異なります。Goのアセンブリは、Goのツールチェインとランタイムに深く統合されており、特にパフォーマンスが重要な部分や、OSとの低レベルなインタラクションが必要な場合に利用されます。
2.  **ガベージコレクタ（GC）**: Goのランタイムには、自動メモリ管理を行うガベージコレクタが組み込まれています。GCは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能（参照されていない）なオブジェクトを自動的に解放し、メモリリークを防ぎます。GCが正しく動作するためには、ヒープ上に存在するポインタを正確に識別し、追跡する必要があります。
3.  **ポインタスキャン**: GCは、メモリ上のオブジェクトがポインタを含んでいるかどうか、そしてそのポインタがどこを指しているかを識別する必要があります。これを「ポインタスキャン」と呼びます。特に、スタックフレームやグローバルデータセクションに存在するポインタは、GCがオブジェクトの到達可能性を判断する上で非常に重要です。
4.  **スタック移動（Stack Movement）**: GoのGCは、スタックを移動（リサイズ）させることがあります。これは、関数呼び出しの深さやローカル変数の使用状況に応じて、スタックのサイズを動的に調整するためです。スタックが移動する際、スタック上のポインタは新しいアドレスに更新される必要があります。このため、アセンブリコードがスタック上のポインタをどのように扱うかについて、GCに正確な情報を提供することが不可欠です。
5.  **`TEXT` ディレクティブ**: Goアセンブリにおける関数定義の開始を示すディレクティブです。`TEXT symbol(SB), flags, $framesize-argsize` の形式で記述され、関数のシンボル名、フラグ、スタックフレームサイズ、引数サイズを指定します。
6.  **`DATA` ディレクティブ**: グローバルデータの初期化に使用されるディレクティブです。`DATA symbol+offset(SB)/width, value` の形式で、指定されたシンボルのオフセットにデータを初期化します。
7.  **`GLOBL` ディレクティブ**: グローバルシンボルを宣言するディレクティブです。`GLOBL symbol(SB), flags, $size` の形式で、シンボル名、フラグ、サイズを指定します。
8.  **`SB` (Static Base)**: グローバルシンボルや関数を参照するための擬似レジスタ。`symbol(SB)` は、メモリ上のグローバルなアドレスを指します。
9.  **`FP` (Frame Pointer)**: 関数引数を参照するための擬似レジスタ。`offset(FP)` は、現在の関数のスタックフレーム上の引数へのオフセットを示します。
10. **`NOPTR` / `RODATA` フラグ**: `GLOBL` ディレクティブで使用されるフラグで、それぞれ「ポインタを含まないデータ」および「読み取り専用データ」であることをGCに伝えます。

## 技術的詳細

このコミットの主要な技術的変更は、`doc/asm.html` にガベージコレクタとの連携に関する新しいセクション (`Runtime Coordination`) を追加したことです。このセクションでは、アセンブリコードがGCに対してポインタ情報をどのように提供すべきかについて、以下の重要なガイドラインを説明しています。

### グローバルデータとポインタ情報

*   **`NOPTR` フラグ**: `GLOBL` ディレクティブで `NOPTR` フラグが指定されたデータシンボルは、ランタイムによって割り当てられたデータへのポインタを含まないとGCに伝えられます。これにより、GCはその領域をスキャンする必要がなくなります。
*   **`RODATA` フラグ**: `RODATA` フラグが指定されたデータシンボルは、読み取り専用メモリに配置され、暗黙的に `NOPTR` として扱われます。
*   **ポインタサイズ未満のデータ**: ポインタのサイズよりも小さい合計サイズを持つデータシンボルも、暗黙的に `NOPTR` として扱われます。
*   **アセンブリでのポインタを含むシンボル定義の制限**: アセンブリソースファイル内でポインタを含むシンボルを定義することはできません。このようなシンボルはGoソースファイルで定義する必要があります。アセンブリコードからは、そのシンボル名を介して参照することは可能です。この制限は、GCがポインタの正確なレイアウトを把握するために、Goコンパイラが生成するメタデータに依存しているためです。
*   **推奨事項**: `RODATA` 以外のすべてのシンボルは、アセンブリではなくGoで定義することが推奨されます。これは、Goコンパイラが自動的に正確なポインタ情報を生成するためです。

### 関数とポインタ情報

*   **引数、結果、ローカルスタックフレームのポインタ情報**: 各関数は、その引数、結果、およびローカルスタックフレーム内のライブポインタの位置を示すアノテーションを必要とします。
*   **Goプロトタイプによる情報提供**: ポインタの結果がなく、ローカルスタックフレームがないか、関数呼び出しがないアセンブリ関数については、同じパッケージ内のGoソースファイルでGoプロトタイプを定義するだけで十分です。`go vet` ツールは、このプロトタイプを使用して引数名とオフセットが一致するかどうかをチェックします。
*   **`funcdata.h` の擬似命令**: より複雑な状況（ポインタを返す、ローカルスタックフレームを持つ、関数呼び出しを行う場合）では、標準の `funcdata.h` ヘッダーファイルで定義されている擬似命令を使用して明示的なアノテーションが必要です。
    *   **`GO_RESULTS_INITIALIZED`**: 関数が結果としてライブポインタを保持し、かつ関数内で他の関数を呼び出す場合、結果をゼロ初期化した後にこの擬似命令を実行する必要があります。これにより、GCは結果が初期化され、スタック移動やGC中にスキャンされるべきであることを認識します。ただし、標準ライブラリのアセンブリ関数ではこの命令は使用されておらず、アセンブリ関数がポインタを返さないか、関数呼び出しを含まないように設計することが一般的です。
    *   **`NO_LOCAL_POINTERS`**: 関数がローカルスタックフレームを持ち、かつ関数呼び出しを含む場合、ローカルスタックフレームにポインタが含まれていないことを保証するためにこの擬似命令を実行する必要があります。スタックのリサイズによってスタックポインタが変更される可能性があるため、スタックデータへのポインタであってもローカル変数に保持すべきではありません。
*   **引数サイズとフレームサイズのアノテーション**:
    *   引数と結果がない関数は、`TEXT` 命令で `$-0` の引数サイズアノテーションを使用することで、ポインタ情報を省略できます。
    *   ローカルスタックフレームがない関数は、`TEXT` 命令で `$0-` のローカルフレームサイズアノテーションを使用することで、ポインタ情報を省略できます。
    *   関数呼び出しを含まない関数も、ポインタ情報を省略できます。

これらの変更は、GoのアセンブリプログラミングにおけるGCとの連携に関するベストプラクティスを明確にし、開発者がより堅牢でGCフレンドリーなアセンブリコードを書けるようにするための重要なステップです。

## コアとなるコードの変更箇所

このコミットの主要な変更は、`doc/asm.html` ファイルへのドキュメント追加です。

1.  **`doc/asm.html`**:
    *   `SB` 擬似レジスタの説明に、`foo<>(SB)` の形式で名前を付けることで、現在のソースファイル内でのみ可視となる（C言語の `static` 宣言に似た）ローカルシンボルを定義できるという説明が追加されました。
    *   `FP` 擬似レジスタの説明に、32ビットシステムでの64ビット値の `_lo` / `_hi` サフィックスによる区別、および結果が名前付けされていない場合の `ret` という慣習的な名前に関する説明が追加されました。
    *   `TEXT` ディレクティブの引数サイズに関する `go vet` のチェックについての説明が追加されました。
    *   `DATA` および `GLOBL` ディレクティブに関する説明が大幅に拡張され、グローバルデータの定義方法、初期化、`DATA` ディレクティブの形式、`GLOBL` ディレクティブの配置に関する詳細が追加されました。特に、`RODATA` フラグと `NOPTR` フラグの例が示されました。
    *   **新しいセクション `<h3 id="runtime">Runtime Coordination</h3>` が追加されました。** このセクションは、ガベージコレクタとの連携に関する詳細な説明を含んでいます。
        *   グローバルデータにおけるポインタの扱い（`NOPTR`, `RODATA` フラグ、アセンブリでのポインタを含むシンボル定義の制限、Goでの定義推奨）。
        *   関数におけるポインタの扱い（引数、結果、ローカルスタックフレームのポインタ情報、Goプロトタイプ、`GO_RESULTS_INITIALIZED`, `NO_LOCAL_POINTERS` 擬似命令の使用条件と目的）。
        *   スタック移動時のポインタの扱いの注意点。
    *   `runtime·atomicload64` のアセンブリコード例が、新しい `FP` 擬似レジスタの慣習に合わせて更新されました。

2.  **`src/runtime/funcdata.h`**:
    *   `GO_ARGS` マクロに関するコメントが追加され、リンカによって暗黙的に挿入されるため、通常は明示的に記述する必要がないことが説明されました。

## コアとなるコードの解説

このコミットの「コアとなるコード」は、Goアセンブリのドキュメントである `doc/asm.html` に追加された新しいセクションと、既存のセクションへの追記です。

特に重要なのは、`<h3 id="runtime">Runtime Coordination</h3>` セクションです。

```html
<h3 id="runtime">Runtime Coordination</h3>

<p>
For garbage collection to run correctly, the runtime must know the
location of pointers in all global data and in most stack frames.
The Go compiler emits this information when compiling Go source files,
but assembly programs must define it explicitly.
</p>

<p>
A data symbol marked with the <code>NOPTR</code> flag (see above)
is treated as containing no pointers to runtime-allocated data.
A data symbol with the <code>RODATA</code> flag
is allocated in read-only memory and is therefore treated
as implicitly marked <code>NOPTR</code>.
A data symbol with a total size smaller than a pointer
is also treated as implicitly marked <code>NOPTR</code>.
It is not possible to define a symbol containing pointers in an assembly source file;
such a symbol must be defined in a Go source file instead.
Assembly source can still refer to the symbol by name
even without <code>DATA</code> and <code>GLOBL</code> directives.
A good general rule of thumb is to define all non-<code>RODATA</code>
symbols in Go instead of in assembly.
</p>

<p>
Each function also needs annotations giving the location of
live pointers in its arguments, results, and local stack frame.
For an assembly function with no pointer results and
either no local stack frame or no function calls,
the only requirement is to define a Go prototype for the function
in a Go source file in the same package.
For more complex situations, explicit annotation is needed.
These annotations use pseudo-instructions defined in the standard
<code>#include</code> file <code>funcdata.h</code>.
</p>

<p>
If a function has no arguments and no results,
the pointer information can be omitted.
This is indicated by an argument size annotation of <code>$<i>n</i>-0</code>
on the <code>TEXT</code> instruction.
Otherwise, pointer information must be provided by
a Go prototype for the function in a Go source file,
even for assembly functions not called directly from Go.
(The prototype will also let <code>go</code> <code>vet</code> check the argument references.)
At the start of the function, the arguments are assumed
to be initialized but the results are assumed uninitialized.
If the results will hold live pointers during a call instruction,
the function should start by zeroing the results and then 
executing the pseudo-instruction <code>GO_RESULTS_INITIALIZED</code>.
This instruction records that the results are now initialized
and should be scanned during stack movement and garbage collection.
It is typically easier to arrange that assembly functions do not
return pointers or do not contain call instructions;
no assembly functions in the standard library use
<code>GO_RESULTS_INITIALIZED</code>.
</p>

<p>
If a function has no local stack frame,
the pointer information can be omitted.
This is indicated by a local frame size annotation of <code>$0-<i>n</i></code>
on the <code>TEXT</code> instruction.
The pointer information can also be omitted if the
function contains no call instructions.
Otherwise, the local stack frame must not contain pointers,
and the assembly must confirm this fact by executing the 
pseudo-instruction <code>NO_LOCAL_POINTERS</code>.
Because stack resizing is implemented by moving the stack,
the stack pointer may change during any function call:
even pointers to stack data must not be kept in local variables.
</p>
```

このセクションは、GoアセンブリプログラマがGCと協調するために必要な知識を体系的に提供しています。特に、グローバルデータとスタックフレーム内のポインタの扱い、`NOPTR` や `RODATA` といったフラグの重要性、そして `GO_RESULTS_INITIALIZED` や `NO_LOCAL_POINTERS` といった擬似命令の役割と使用条件が詳細に説明されています。これにより、アセンブリコードがGCの正確な動作を妨げないようにするための明確なガイドラインが提供されます。

また、`src/runtime/funcdata.h` への変更は、`GO_ARGS` マクロがリンカによって自動的に挿入されるため、通常は明示的に記述する必要がないという、既存のコードベースの慣習を明確にするためのコメント追加です。これは、ドキュメントの整合性を保ち、開発者の混乱を避けるための小さな改善ですが、全体的な理解を深める上で役立ちます。

## 変更の背景

GoコンパイラのSSAバックエンドにおいて、共通部分式除去 (CSE) は最も時間のかかるコンパイラフェーズの一つであり、しかも複数回実行されていました。特に、CSEの初期パーティション生成プロセスがメモリを大量に消費し、処理速度のボトルネックとなっていました。このコミットは、このパフォーマンス問題を解決し、コンパイル時間を短縮することを目的としています。

また、デバッグやプロファイリングの際に最適化を無効にするための`-N`フラグのサポートも追加されています。これにより、開発者は最適化によるコードの変更に惑わされることなく、元のコードに近い形でデバッグを行うことが可能になります。

## 前提知識の解説

### Goコンパイラ

Goコンパイラは、Go言語で書かれたソースコードを機械語に変換するツールです。Go 1.7以降、コンパイラのバックエンドはSSA (Static Single Assignment) 形式に移行し、より高度な最適化が可能になりました。

### SSA (Static Single Assignment)

SSA形式は、プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。SSA形式では、変数の定義と使用の関係が明確になり、コンパイラはより正確な情報に基づいて最適化を適用できます。

### CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラの最適化手法の一つです。プログラム内で複数回計算される同じ式（共通部分式）を一度だけ計算し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させます。例えば、`a = b * c + d` と `e = b * c + f` というコードがあった場合、`b * c` は共通部分式であり、一度計算すればその結果を両方の代入に利用できます。

CSEは通常、以下のステップで実行されます。
1.  プログラム内のすべての式を識別し、それらを「等価クラス」に分類します。同じ結果を生成する可能性のある式は同じ等価クラスに属します。
2.  各等価クラス内で、支配関係（Dominance Relation）を利用して、ある式の計算結果が別の式の計算に再利用できるかどうかを判断します。
3.  再利用可能な式が見つかった場合、冗長な計算を削除し、既存の計算結果を参照するようにコードを書き換えます。

### 等価クラス (Equivalence Classes)

CSEにおいて、等価クラスとは、同じ値を持つ可能性のある式や値の集合です。初期のCSEでは、オペレーションの種類、オペランド、定数などの属性に基づいて値をグループ化します。その後、データフロー解析を通じて、これらのクラスをより厳密に絞り込み、実際に同じ値を持つことが保証される値のみが同じ等価クラスに残るようにします。

### `-N` フラグ (No optimization flag)

Goコンパイラの`-N`フラグは、コンパイル時の最適化を無効にするためのオプションです。通常、コンパイラは生成されるバイナリのパフォーマンスを向上させるために様々な最適化を適用しますが、これにより生成される機械語が元のソースコードの構造から大きくかけ離れることがあります。デバッグ時に最適化が適用されていると、ステップ実行が期待通りに動作しなかったり、変数の値が最適化によって消滅したりすることがあります。`-N`フラグを使用することで、これらの最適化を無効にし、デバッグしやすいコードを生成できます。

## 技術的詳細

このコミットにおけるCSEの高速化は、主に以下の3つのアプローチによって実現されています。

1.  **初期パーティション生成の改善**:
    *   **変更前**: 初期パーティションの生成に`map[key]eqclass`を使用していました。`key`構造体は、オペレーションコード、型名、補助データ、補助整数、引数の数、Phi変数のブロックID、最初の2つの引数のオペレーションコードなど、多くの属性を含んでいました。このマップベースのアプローチは、キーのハッシュ計算とマップ操作のオーバーヘッドにより、メモリ使用量が多く、速度が遅いという問題がありました。
    *   **変更後**: `map`の代わりにソートベースのアプローチを採用しました。すべての`Value`を一つのスライスに集め、特定の基準（オペレーションコード、AuxInt、引数の数、Phi変数のブロックID、Aux、最初の2つの引数のオペレーションコード、型、Auxフィールド）でソートします。ソートされたスライスでは、同じ属性を持つ`Value`が隣接するため、線形スキャンで等価クラスを効率的に抽出できます。この方法は、マップのオーバーヘッドを回避し、メモリ効率も向上させます。`partitionValues`関数がこの新しいロジックを実装しています。

2.  **サイズ1の等価クラスに対する最適化**:
    *   CSEのイテレーションプロセスにおいて、等価クラスが分割されることがあります。最終的にサイズが1になった等価クラスは、それ以上共通部分式として除去される可能性がないため、それ以降の処理から除外することで無駄な作業を削減します。このコミットでは、`valueEqClass`マップに負のIDを割り当てることで、サイズ1の等価クラスを効率的に識別し、処理をスキップする最適化が導入されています。

3.  **`-N` フラグの実装**:
    *   `src/cmd/compile/internal/ssa/config.go`の`Config`構造体に`optimize`というブール型フィールドが追加されました。これは、コンパイラが最適化を実行するかどうかを制御します。
    *   `NewConfig`関数に`optimize`引数が追加され、`gc/ssa.go`から呼び出される際に、`Debug['N'] == 0`（つまり`-N`フラグが指定されていない場合）に`true`が渡されるようになりました。
    *   `src/cmd/compile/internal/ssa/compile.go`の`Compile`関数内で、各コンパイラパスを実行する前に`f.Config.optimize`と`p.required`をチェックするロジックが追加されました。これにより、`-N`フラグが指定されている場合（`optimize`が`false`）、`required`が`true`のパス（最適化とは関係なく、コード生成のために必須のパス）のみが実行され、それ以外の最適化パスはスキップされます。
    *   `pass`構造体には`required`フィールドが追加され、各パスが最適化に必須かどうかを示します。例えば、`decompose`, `opt`, `lower`, `critical`, `layout`, `schedule`, `flagalloc`, `regalloc`などは`required: true`と設定されています。
    *   `src/cmd/compile/internal/ssa/regalloc.go`では、`-N`フラグが有効な場合に`OpSB`（Stack Base Pointer）が複数導入される可能性があるため、余分な割り当てを無視するロジックが追加されています。これは、最適化が無効な場合にSSAの書き換えルールが複数の`OpSB`を生成し、それらがCSEされないために発生する問題への対応です。

これらの変更により、CSEフェーズの実行速度が向上し、コンパイル時間が短縮されるとともに、デバッグ時の利便性が向上しました。

## 前提知識の解説

### Goコンパイラ

Goコンパイラは、Go言語で書かれたソースコードを機械語に変換するツールです。Go 1.7以降、コンパイラのバックエンドはSSA (Static Single Assignment) 形式に移行し、より高度な最適化が可能になりました。

### SSA (Static Single Assignment)

SSA形式は、プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。SSA形式では、変数の定義と使用の関係が明確になり、コンパイラはより正確な情報に基づいて最適化を適用できます。

### CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラの最適化手法の一つです。プログラム内で複数回計算される同じ式（共通部分式）を一度だけ計算し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させます。例えば、`a = b * c + d` と `e = b * c + f` というコードがあった場合、`b * c` は共通部分式であり、一度計算すればその結果を両方の代入に利用できます。

CSEは通常、以下のステップで実行されます。
1.  プログラム内のすべての式を識別し、それらを「等価クラス」に分類します。同じ結果を生成する可能性のある式は同じ等価クラスに属します。
2.  各等価クラス内で、支配関係（Dominance Relation）を利用して、ある式の計算結果が別の式の計算に再利用できるかどうかを判断します。
3.  再利用可能な式が見つかった場合、冗長な計算を削除し、既存の計算結果を参照するようにコードを書き換えます。

### 等価クラス (Equivalence Classes)

CSEにおいて、等価クラスとは、同じ値を持つ可能性のある式や値の集合です。初期のCSEでは、オペレーションの種類、オペランド、定数などの属性に基づいて値をグループ化します。その後、データフロー解析を通じて、これらのクラスをより厳密に絞り込み、実際に同じ値を持つことが保証される値のみが同じ等価クラスに残るようにします。

### `-N` フラグ (No optimization flag)

Goコンパイラの`-N`フラグは、コンパイル時の最適化を無効にするためのオプションです。通常、コンパイラは生成されるバイナリのパフォーマンスを向上させるために様々な最適化を適用しますが、これにより生成される機械語が元のソースコードの構造から大きくかけ離れることがあります。デバッグ時に最適化が適用されていると、ステップ実行が期待通りに動作しなかったり、変数の値が最適化によって消滅したりすることがあります。`-N`フラグを使用することで、これらの最適化を無効にし、デバッグしやすいコードを生成できます。

## 技術的詳細

このコミットにおけるCSEの高速化は、主に以下の3つのアプローチによって実現されています。

1.  **初期パーティション生成の改善**:
    *   **変更前**: 初期パーティションの生成に`map[key]eqclass`を使用していました。`key`構造体は、オペレーションコード、型名、補助データ、補助整数、引数の数、Phi変数のブロックID、最初の2つの引数のオペレーションコードなど、多くの属性を含んでいました。このマップベースのアプローチは、キーのハッシュ計算とマップ操作のオーバーヘッドにより、メモリ使用量が多く、速度が遅いという問題がありました。

これらの変更により、CSEフェーズの実行速度が向上し、コンパイル時間が短縮されるとともに、デバッグ時の利便性が向上しました。

+		}
+		if j > 1 {
+			partition = append(partition, a[:j])
+		}
+		a = a[j:]
+	}
+
+	return partition
+}
+
+// Sort values to make the initial partition.
+type sortvalues struct {
+	a        []*Value              // array of values
+	typNames map[Type]string       // type -> type ID map
+	auxIDs   map[interface{}]int32 // aux -> aux ID map
+}
+
+func (sv sortvalues) Len() int      { return len(sv.a) }
+func (sv sortvalues) Swap(i, j int) { sv.a[i], sv.a[j] = sv.a[j], sv.a[i] }
+func (sv sortvalues) Less(i, j int) bool {
+	v := sv.a[i]
+	w := sv.a[j]
+	if v.Op != w.Op {
+		return v.Op < w.Op
+	}
+	if v.AuxInt != w.AuxInt {
+		return v.AuxInt < w.AuxInt
+	}
+	if v.Aux == nil && w.Aux != nil { // cheap aux check - expensive one below.
+		return true
+	}
+	if v.Aux != nil && w.Aux == nil {
+		return false
+	}
+	if len(v.Args) != len(w.Args) {
+		return len(v.Args) < len(w.Args)
+	}
+	if v.Op == OpPhi && v.Block.ID != w.Block.ID {
+		return v.Block.ID < w.Block.ID
+	}
+	if len(v.Args) >= 1 {
+		x := v.Args[0].Op
+		y := w.Args[0].Op
+		if x != y {
+			return x < y
+		}
+		if len(v.Args) >= 2 {
+			x = v.Args[1].Op
+			y := w.Args[1].Op
+			if x != y {
+				return x < y
+			}
+		}
+	}
+
+	// Sort by type.  Types are just interfaces, so we can't compare
+	// them with < directly.  Instead, map types to their names and
+	// sort on that.
+	if v.Type != w.Type {
+		x := sv.typNames[v.Type]
+		if x == "" {
+			x = v.Type.String()
+			sv.typNames[v.Type] = x
+		}
+		y := sv.typNames[w.Type]
+		if y == "" {
+			y = w.Type.String()
+			sv.typNames[w.Type] = y
+		}
+		if x != y {
+			return x < y
+		}
+	}
+
+	// Same deal for aux fields.
+	if v.Aux != w.Aux {
+		x := sv.auxIDs[v.Aux]
+		if x == 0 {
+			x = int32(len(sv.auxIDs)) + 1
+			sv.auxIDs[v.Aux] = x
+		}
+		y := sv.auxIDs[w.Aux]
+		if y == 0 {
+			y = int32(len(sv.auxIDs)) + 1
+			sv.auxIDs[w.Aux] = y
+		}
+		if x != y {
+			return x < y
+		}
+	}
+
+	// TODO(khr): is the above really ok to do?  We're building
+	// the aux->auxID map online as sort is asking about it.  If
+	// sort has some internal randomness, then the numbering might
+	// change from run to run.  That will make the ordering of
+	// partitions random.  It won't break the compiler but may
+	// make it nondeterministic.  We could fix this by computing
+	// the aux->auxID map ahead of time, but the hope is here that
+	// we won't need to compute the mapping for many aux fields
+	// because the values they are in are otherwise unique.
+
+	// Sort by value ID last to keep the sort result deterministic.
+	return v.ID < w.ID
+}
```

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/cse.go` の変更

*   **初期パーティション生成のロジック変更**:
    *   以前は`map[key]eqclass`を使用していましたが、これが削除され、代わりにすべての`Value`を`a`というスライスに集めるようになりました。
    *   `partitionValues`という新しい関数が導入され、この関数が`a`スライスをソートし、ソートされた結果から等価クラスを生成します。
    *   `sortvalues`という新しい型が定義され、`sort.Interface`インターフェースを実装しています。この型は、`Value`スライスと、`Type`や`Aux`フィールドを文字列/IDにマッピングするためのマップを含みます。`Less`メソッドは、`Op`、`AuxInt`、引数の数、Phi変数のブロックID、引数のオペレーションコード、型、`Aux`フィールドといった複数の基準に基づいて`Value`を比較します。これにより、同じ属性を持つ`Value`がソート後に隣接するようになります。
    *   `partitionValues`関数は、ソートされた`Value`スライスを線形スキャンし、隣接する同じ属性を持つ`Value`をグループ化して等価クラスを形成します。サイズが1の等価クラスは無視されます。
*   **サイズ1の等価クラスの最適化**:
    *   `valueEqClass`スライスが`ID`型になり、初期化時に各`Value`の`ID`を負の値で設定することで、ユニークな値（サイズ1の等価クラス）を効率的にマークするようになりました。これにより、CSEのイテレーション中にサイズ1になった等価クラスを早期に識別し、それ以降の処理から除外できます。

### `src/cmd/compile/internal/ssa/compile.go` の変更

*   **`pass`構造体の変更**:
    *   `pass`構造体に`required`というブール型フィールドが追加されました。これは、そのパスが最適化の有無にかかわらず常に実行されるべきかどうかを示します。
*   **パス実行ロジックの変更**:
    *   `Compile`関数内のパスループに`if !f.Config.optimize && !p.required { continue }`という条件が追加されました。これにより、`-N`フラグが指定されている場合（`f.Config.optimize`が`false`）、`required`が`false`のパス（つまり、純粋な最適化パス）はスキップされるようになりました。

### `src/cmd/compile/internal/ssa/config.go` の変更

*   **`Config`構造体の変更**:
    *   `Config`構造体に`optimize`というブール型フィールドが追加されました。これは、SSAバックエンドが最適化を実行するかどうかを制御します。
*   **`NewConfig`関数の変更**:
    *   `NewConfig`関数に`optimize`引数が追加され、この値が`Config.optimize`フィールドに設定されるようになりました。これにより、SSAコンフィグレーションの作成時に最適化の有効/無効を外部から制御できるようになります。

### その他の変更

*   `src/cmd/compile/internal/gc/ssa.go`: `ssa.NewConfig`の呼び出しに`Debug['N'] == 0`という条件が追加され、`-N`フラグが指定されていない場合にのみ最適化が有効になるように設定されます。
*   `src/cmd/compile/internal/ssa/regalloc.go`: `-N`フラグが有効な場合、SSA書き換えルールによって複数の`OpSB`が導入される可能性があるため、レジスタ割り当て時に余分な`OpSB`の割り当てを無視するロジックが追加されました。これは、最適化が無効な場合に発生する可能性のあるアサーション失敗を防ぐためのものです。
*   テストファイル (`dom_test.go`, `export_test.go`, `nilcheck_test.go`) も`NewConfig`の呼び出しに`true`を渡すように更新され、デフォルトで最適化が有効になるように変更されています。
*   `test/nilcheck_ssa.go`が削除されました。これは、`-N`フラグの導入により、最適化が有効な場合のnilチェックの除去に関するテストロジックが不要になったか、あるいは他のテストに統合されたためと考えられます。

これらの変更は、GoコンパイラのSSAバックエンドにおけるCSEの効率を大幅に向上させ、コンパイル時間の短縮とデバッグ体験の改善に貢献しています。

# [インデックス 27842] ファイルの概要

このコミットは、Go言語の標準ライブラリ `compress/gzip` パッケージにおける `Reader` のヘッダーCRC (FHCRC) チェックの不具合を修正するものです。具体的には、GZIPヘッダーのCRC16計算がRFC 1952の仕様に厳密に従っていなかった点を修正し、ヘッダー全体（CRC16自体を除く）に対してCRCを計算するように変更されました。これにより、GZIPファイルのヘッダーの整合性チェックがより堅牢になります。

変更されたファイルは以下の通りです。

*   `src/compress/gzip/gunzip.go`: GZIPリーダーのヘッダー読み込みとCRCチェックロジックが修正されました。
*   `src/compress/gzip/gunzip_test.go`: FHCRCチェックの修正を検証するための新しいテストケースが追加されました。
*   `src/compress/gzip/gzip.go`: GZIPライター側で、ヘッダーの書き込み時に`binary.LittleEndian`を使用するように変更され、`put2`および`put4`ヘルパー関数が削除されました。

## コミット

compress/gzip: fix Reader to properly check FHCRC

RFC 1952, section 3.2.3 says:
>>>

immediately before the compressed data. The CRC16 consists of the two
least significant bytes of the CRC32 for all bytes of the

Thus, instead of computing the CRC only over the first 10 bytes

## 変更の背景

この変更の背景には、GZIPファイルフォーマットの仕様であるRFC 1952の解釈と実装の不一致がありました。RFC 1952のセクション3.2.3では、GZIPヘッダーにFHCRC (File Header CRC) フラグが設定されている場合、ヘッダーの整合性を保証するためにCRC16が提供されると規定されています。このCRC16は、圧縮データ直前に配置され、CRC16自体を含まないGZIPヘッダーの全バイトに対するCRC32の最下位2バイトで構成されるべきです。

しかし、Goの `compress/gzip` パッケージの以前の実装では、このCRCがヘッダーの最初の10バイトのみに対して計算されていました。GZIPヘッダーは、フラグに応じて追加のフィールド（Extra Field, File Name, Comment）を持つことがあり、これらのフィールドもFHCRCの計算範囲に含まれるべきです。最初の10バイトのみでCRCを計算すると、これらの追加フィールドが変更された場合にFHCRCチェックをすり抜けてしまう可能性があり、ヘッダーの整合性が正しく検証されないという問題がありました。

この不具合はIssue #15070として報告され、本コミットによって、RFCの規定通りにヘッダー全体（CRC16フィールドを除く）に対してCRCを計算するように修正されました。これにより、GZIPヘッダーの破損や改ざんをより確実に検出できるようになります。

## 前提知識の解説

### GZIPファイルフォーマット

GZIPファイルは、RFC 1952で定義されたファイルフォーマットであり、主にデータの圧縮と解凍に使用されます。GZIPファイルは「メンバー」と呼ばれる複数の圧縮データセットで構成されることがありますが、通常は単一のメンバーで構成されます。各メンバーは以下の主要な部分から構成されます。

1.  **ヘッダー (Header)**: ファイルのメタデータ（マジックナンバー、圧縮方式、フラグ、変更時刻、OSタイプなど）を含みます。
2.  **圧縮データ (Compressed Data)**: DEFLATEアルゴリズムで圧縮された実際のデータ。
3.  **フッター (Footer)**: 圧縮されていないデータのCRC32チェックサムと元のデータサイズを含みます。

### GZIPヘッダーのフラグ (FLG) とFHCRC

GZIPヘッダーの4番目のバイトは「FLG (Flags)」バイトであり、ヘッダーの追加フィールドの有無や動作を制御するビットフラグの集合です。このFLGバイトには以下のビットが含まれます。

*   `FTEXT` (bit 0): 圧縮データがASCIIテキストであるかバイナリであるかを示唆します（ヒントであり、厳密な意味はない）。
*   `FHCRC` (bit 1): ヘッダーCRC (Header CRC) が存在することを示します。このフラグがセットされている場合、ヘッダーの最後にCRC16値が続きます。
*   `FEXTRA` (bit 2): 拡張ヘッダーフィールド (Extra Field) が存在することを示します。
*   `FNAME` (bit 3): オリジナルファイル名 (File Name) が存在することを示します。
*   `FCOMMENT` (bit 4): コメント (Comment) が存在することを示します。

本コミットで修正されたのは、`FHCRC`フラグがセットされている場合のCRC計算ロジックです。

### CRC32とCRC16

CRC (Cyclic Redundancy Check) は、データ転送や保存中に発生したエラーを検出するための一般的なハッシュ関数です。

*   **CRC32**: 32ビットのチェックサムを生成します。GZIPフッターで使用され、圧縮されていない元のデータの整合性を検証します。
*   **CRC16**: 16ビットのチェックサムを生成します。GZIPヘッダーのFHCRCとして使用され、ヘッダー自体の整合性を検証します。RFC 1952では、FHCRCはヘッダーの全バイトに対するCRC32の最下位2バイトとして定義されています。

### エンディアンネス (Endianness)

エンディアンネスは、マルチバイトデータをメモリに格納する際のバイト順序を指します。

*   **リトルエンディアン (Little-Endian)**: 最下位バイトが最も小さいアドレスに格納されます。GZIPファイルフォーマットはリトルエンディアンを使用します。
*   **ビッグエンディアン (Big-Endian)**: 最上位バイトが最も小さいアドレスに格納されます。

Go言語の `encoding/binary` パッケージは、このエンディアンネスを考慮したバイト列と数値の変換機能を提供します。

## 技術的詳細

このコミットの主要な技術的変更点は、GZIPヘッダーのFHCRC計算ロジックをRFC 1952の仕様に合致させることです。

1.  **CRC計算範囲の拡張**: 以前はヘッダーの最初の10バイト（マジックナンバー、圧縮方式、フラグ、変更時刻、OSタイプ）のみでCRCを計算していましたが、RFCの規定に従い、`FEXTRA`、`FNAME`、`FCOMMENT`フラグによって追加される可能性のある全てのヘッダーフィールドを含めてCRCを計算するように変更されました。FHCRC自体はCRC計算の対象外です。
2.  **`z.digest`の逐次更新**: `Reader`構造体の`digest`フィールドは、ヘッダーのCRC計算に使用されるCRC32チェックサムを保持します。このコミットでは、`readHeader`関数内でヘッダーの各部分（初期の10バイト、Extra Field、File Name、Comment）を読み込むたびに、`crc32.Update`関数を使って`z.digest`を逐次更新するように変更されました。これにより、ヘッダー全体に対するCRC32が正しく計算されます。
3.  **`encoding/binary`パッケージの導入**: バイト列から数値への変換（例: `ModTime`、`Extra Field`の長さ、FHCRC値）において、以前は手動でバイトシフトを行っていた`get4`や`read2`といったヘルパー関数が削除されました。代わりに、`encoding/binary`パッケージの`LittleEndian`インターフェース（`le.Uint32`、`le.Uint16`）が導入され、より安全で標準的な方法でリトルエンディアンのバイト列を数値に変換するようになりました。これにより、コードの可読性と保守性が向上します。
4.  **エラーハンドリングの改善**: `io.EOF`が予期せぬ場所で発生した場合に`io.ErrUnexpectedEOF`に変換する`noEOF`ヘルパー関数が導入され、エラーハンドリングが一貫性を持つようになりました。
5.  **`readHeader`関数の変更**: `readHeader`関数は、`save`引数を削除し、`Header`構造体とエラーを返すように変更されました。これにより、ヘッダーのメタデータが`Reader`構造体ではなく、返された`Header`構造体に設定されるようになり、関数の責務が明確化されました。

これらの変更により、`compress/gzip`パッケージはGZIPヘッダーの整合性チェックに関してRFC 1952の仕様に完全に準拠するようになり、不正なGZIPファイルをより確実に検出できるようになりました。

## コアとなるコードの解説

### `src/compress/gzip/gunzip.go` の変更点

1.  **`import "encoding/binary"` の追加**: リトルエンディアン形式のバイト列を数値に変換するために、`encoding/binary`パッケージがインポートされました。
2.  **`var le = binary.LittleEndian` の導入**: `binary.LittleEndian`を`le`という変数に割り当てることで、コード全体でリトルエンディアンのバイト操作を簡潔に行えるようになりました。
3.  **`noEOF` ヘルパー関数の追加**: `io.EOF`が予期せぬ場所で発生した場合に`io.ErrUnexpectedEOF`を返すことで、エラーハンドリングの一貫性を保ちます。
4.  **`readHeader` 関数のシグネチャ変更とロジック修正**:
    *   以前は`func (z *Reader) readHeader(save bool) error`でしたが、`func (z *Reader) readHeader() (hdr Header, err error)`に変更されました。これにより、ヘッダーのメタデータは`Reader`構造体ではなく、返される`Header`構造体に設定されるようになり、関数の責務が明確になりました。
    *   ヘッダーの最初の10バイトを読み込んだ後、`z.digest = crc32.ChecksumIEEE(z.buf[:10])`で初期のCRC32を計算します。
    *   `flagExtra`、`flagName`、`flagComment`の各フラグがセットされている場合、対応するヘッダーフィールドを読み込むたびに、`z.digest = crc32.Update(z.digest, crc32.IEEETable, data)`のように`z.digest`を逐次更新しています。これにより、FHCRCの計算範囲がヘッダー全体に拡張されます。
    *   `flagHdrCrc`がセットされている場合、読み込んだCRC16値（`digest := le.Uint16(z.buf[:2])`）と、これまでに計算された`z.digest`の最下位16ビット（`uint16(z.digest)`）を比較し、一致しない場合は`ErrHeader`を返します。
5.  **`get4` および `read2` ヘルパー関数の削除**: これらの関数は、バイト列から数値への手動変換を行っていましたが、`encoding/binary`の導入により不要となりました。
6.  **`readString` 関数の修正**: `readString`関数も、NUL終端文字列を読み込んだ際に`z.digest`を更新するように変更されました。これは、ファイル名やコメントもFHCRCの計算対象となるためです。
7.  **フッターのCRCチェック**: `Read`関数内のフッターチェック部分でも、`get4`の代わりに`le.Uint32`を使用するように変更されました。

### `src/compress/gzip/gzip.go` の変更点

1.  **`put2` および `put4` ヘルパー関数の削除**: `gunzip.go`と同様に、`gzip.go`でもバイト列への手動書き込みを行うこれらの関数が削除されました。
2.  **`encoding/binary` の使用**: `writeBytes`関数でExtra Fieldの長さを書き込む際や、`Write`関数で`ModTime`を書き込む際、`Close`関数でフッターのCRC32とサイズを書き込む際に、`le.PutUint16`や`le.PutUint32`が使用されるようになりました。これにより、GZIPファイルフォーマットのリトルエンディアン要件が標準的な方法で満たされます。

これらの変更により、GZIPヘッダーの読み書きにおけるバイト順序の扱いが統一され、FHCRCの計算がRFC 1952の仕様に完全に準拠するようになりました。

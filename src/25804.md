# [インデックス 25804] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) がPowerPC (PPC) アーキテクチャにおける `R_PPC_REL32` リロケーションタイプを正しく処理できるようにするための変更です。これにより、`libgcc.a` の `.eh_frame` セクションに含まれるこの種のリロケーションが、Goの内部リンカによって適切に解決されるようになります。

## 変更の背景

Go言語のリンカ (`cmd/link`) は、Goプログラムをコンパイルして実行可能ファイルを生成する際に、Goのオブジェクトファイルだけでなく、C/C++で書かれたライブラリ（例えば `libgcc.a`）もリンクすることがあります。特に、GoがCgoを介してCコードと連携する場合や、特定のシステムライブラリに依存する場合にこの処理が必要となります。

このコミットの背景には、PowerPC (PPC) アーキテクチャ上で `libgcc.a` をリンクする際に発生する問題がありました。`libgcc.a` はGCCのランタイムライブラリであり、例外処理情報を含む `.eh_frame` セクションを持っています。この `.eh_frame` セクション内には、`R_PPC_REL32` という特定のリロケーションタイプが存在します。

Goのリンカがこの `R_PPC_REL32` リロケーションを認識し、適切に解決できない場合、リンクエラーが発生したり、生成された実行可能ファイルが正しく動作しない可能性がありました。このコミットは、この特定のリロケーションタイプをGoリンカが理解し、処理できるようにすることで、PPCアーキテクチャ上でのGoプログラムのビルドと実行の堅牢性を向上させることを目的としています。具体的には、Issue #13375 で報告された問題の解決が図られています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **リンカ (Linker)**:
    コンパイラによって生成された複数のオブジェクトファイル（機械語コードとデータを含む）を結合し、最終的な実行可能ファイルやライブラリを生成するプログラムです。リンカの主な役割の一つは、未解決のシンボル参照（例えば、あるオブジェクトファイルが別のオブジェクトファイルで定義された関数を呼び出す場合）を解決し、適切なアドレスに置き換えることです。

2.  **リロケーション (Relocation)**:
    プログラムがメモリ上のどこにロードされるかに関わらず、コードが正しく実行されるように、アドレス参照を調整するプロセスです。コンパイル時には、多くのアドレスは相対的または仮のものであり、リンカが最終的な絶対アドレスを決定した後に、これらの参照を修正する必要があります。リロケーションエントリは、オブジェクトファイル内に含まれ、リンカに対してどのアドレスをどのように修正すべきかを指示します。

3.  **`R_PPC_REL32`**:
    PowerPC (PPC) アーキテクチャに特有のリロケーションタイプの一つです。`REL32` は「32ビットのPC相対 (Program Counter Relative) リロケーション」を意味します。これは、リロケーションの対象となるアドレスが、現在のプログラムカウンタ（命令ポインタ）からの相対オフセットとして表現されることを示します。つまり、最終的なアドレスは `現在のPCの値 + オフセット` で計算されます。このタイプのリロケーションは、位置独立コード (PIC: Position-Independent Code) の生成によく使用されます。

4.  **`libgcc.a`**:
    GNU Compiler Collection (GCC) のランタイムライブラリです。C/C++プログラムが特定の低レベルな操作（例えば、整数演算のオーバーフローチェック、例外処理のサポート、特定の組み込み関数の実装など）を行う際に必要となる補助関数を提供します。GoプログラムがCgoを介してCコードを呼び出す場合、`libgcc.a` がリンクされることがあります。

5.  **`.eh_frame` セクション**:
    ELF (Executable and Linkable Format) 形式のオブジェクトファイルや実行可能ファイルに含まれるセクションの一つです。主に例外処理 (Exception Handling) のための情報が格納されています。C++の例外やGoのパニックなど、スタックの巻き戻し (stack unwinding) が必要な場合に、このセクションの情報が使用されます。`.eh_frame` 内には、関数呼び出しの際にレジスタがどのように保存・復元されるか、どの命令がどのスタックフレームに対応するかといった情報が含まれており、これらの情報がコード内の特定のアドレスを参照するため、リロケーションが必要となることがあります。

6.  **Goリンカの内部リンク (Internal Link)**:
    Goのリンカ (`cmd/link`) は、通常、Goのオブジェクトファイルを直接処理し、必要に応じてCのオブジェクトファイルやライブラリも取り込みます。この際、外部のCリンカ（例えば `ld`）に依存せず、Goリンカ自身が全てのリロケーション解決やシンボル解決を行うことを「内部リンク」と呼びます。これにより、クロスコンパイルが容易になるなどの利点があります。しかし、外部ライブラリが持つ全てのリロケーションタイプをGoリンカが理解している必要があります。

## 技術的詳細

このコミットの技術的な核心は、GoリンカがPPCアーキテクチャの `R_PPC_REL32` リロケーションを、Goリンカ内部の汎用的なPC相対リロケーションタイプ (`obj.R_PCREL`) にマッピングし、適切に処理することにあります。

Goリンカは、オブジェクトファイルを読み込む際に、その中に含まれるリロケーションエントリを解析します。各リロケーションエントリは、特定のリロケーションタイプ（例: `R_PPC_REL32`）と、そのリロケーションが適用されるオフセット、そして参照先のシンボル情報を含んでいます。リンカはこれらの情報に基づいて、最終的な実行可能ファイル内のアドレスを計算し、コードやデータ内の参照を修正します。

`R_PPC_REL32` は32ビットのPC相対リロケーションであり、その解決には現在の命令ポインタ (PC) の値が基準となります。Goリンカの内部では、このようなPC相対リロケーションは `obj.R_PCREL` というタイプで抽象化されています。このコミットは、外部から読み込んだ `R_PPC_REL32` を `obj.R_PCREL` として扱うようにリンカに指示し、その際に必要なオフセット調整 (`r.Add += 4`) を行います。`r.Add += 4` は、リロケーションが適用される命令の次の命令のアドレスを基準とするため、命令のサイズ（4バイト）を加算して調整している可能性があります。

また、動的インポート (dynamic import) の場合に `R_PPC_REL32` が現れるのは予期しない状況であるため、その場合には診断メッセージ (`ld.Diag`) を出力するようになっています。これは、通常 `R_PPC_REL32` が静的リンクのコンテキストで使われることを示唆しており、動的リンクでは異なるリロケーションタイプが期待されるためです。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/ldelf.go` の変更

`reltype` 関数は、ELFファイルのリロケーションタイプ (`elftype`) をGoリンカ内部のリロケーションタイプに変換し、そのリロケーションが参照するデータのサイズ (`siz`) を設定する役割を担っています。

変更点:
`'9' | R_PPC_REL32<<24:` の行が追加されました。これは、`R_PPC_REL32` リロケーションが検出された場合に、そのリロケーションが32ビット（4バイト）のデータを対象とすることを示しています (`*siz = 4`)。`'9'` は、Goリンカ内部でPPC64アーキテクチャのリロケーションを識別するためのマジックナンバーのようなものです。これにより、リンカは `R_PPC_REL32` を正しく認識し、そのサイズに基づいて処理を進めることができるようになります。

### `src/cmd/link/internal/ppc64/asm.go` の変更

`adddynrel` 関数は、動的リロケーションを追加する際に呼び出される関数ですが、このコンテキストでは、特定のリロケーションタイプに対する最終的な処理を定義する役割も果たしています。

変更点:
`case 256 + ld.R_PPC_REL32:` という新しいケースが追加されました。
*   `r.Type = obj.R_PCREL`: 検出された `R_PPC_REL32` リロケーションを、Goリンカ内部の汎用的なPC相対リロケーションタイプ `obj.R_PCREL` にマッピングします。これにより、GoリンカはPPC固有のリロケーションを、自身が理解できる形式で処理できるようになります。
*   `r.Add += 4`: リロケーションのオフセットに4を加算します。これは、PPCのPC相対リロケーションが、リロケーションが適用される命令の「次の命令」のアドレスを基準としてオフセットを計算することが多いため、命令のサイズ（4バイト）を考慮して調整していると考えられます。
*   `if targ.Type == obj.SDYNIMPORT { ld.Diag("unexpected R_PPC_REL32 for dyn import") }`:
    この条件分岐は、`R_PPC_REL32` が動的インポート (`obj.SDYNIMPORT`) に対して使用された場合に警告を発します。これは、`R_PPC_REL32` が通常、静的リンクのコンテキストで期待されるリロケーションタイプであり、動的リンクでは異なるリロケーションメカニズムが使用されることが一般的であるためです。この診断メッセージは、潜在的な問題を開発者に知らせるためのものです。

これらの変更により、Goリンカは `libgcc.a` の `.eh_frame` セクションに含まれる `R_PPC_REL32` リロケーションを正しく解釈し、GoプログラムとC/C++ライブラリの間のリンクをPPCアーキテクチャ上でより堅牢に行えるようになりました。

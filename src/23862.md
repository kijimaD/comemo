# [インデックス 23862] ファイルの概要

このコミットは、GoランタイムにおけるCGO呼び出しメカニズムの内部的なリファクタリングの一環として、`cgocall` および `asmcgocall` という関数を削除するものです。これは、後続のコミットで `cgocall_errno` と `asmcgocall_errno` をそれぞれ `cgocall` と `asmcgocall` にリネームするための準備作業であり、エラーコードを返すCGO呼び出しが標準となるように設計変更が進められていることを示唆しています。

## 元コミット内容

Goランタイムから `cgocall` および `asmcgocall` 関数を削除します。これは、後続の変更リスト（CL）で `cgocall_errno` を `cgocall` に、`asmcgocall_errno` を `asmcgocall` にリネームするための準備です。この変更は、rsc（おそらくRuss Cox）がCL 9387を2つの部分に分割するよう要求したことに基づいており、本コミットはその最初の部分にあたります。

## 変更の背景

GoプログラムがC言語のコード（またはC言語のABIを持つ他の言語のコード）を呼び出す際、GoランタイムはCGOメカニズムを使用します。このメカニズムは、GoのスケジューラとCのランタイムの間でスタックやレジスタの状態を適切に切り替える役割を担っています。

以前のGoランタイムには、`cgocall` と `cgocall_errno`、そしてそれに対応するアセンブリレベルのラッパーである `asmcgocall` と `asmcgocall_errno` が存在していました。
*   `cgocall` / `asmcgocall`: C関数を呼び出し、戻り値としてエラーコードを考慮しない（または、エラーコードが返されないことを前提とする）ケースで使用されていました。
*   `cgocall_errno` / `asmcgocall_errno`: C関数を呼び出し、Cの `errno` 変数に設定されたエラーコードをGo側で取得する必要があるケースで使用されていました。

このコミットの背景には、CGO呼び出しにおけるエラーハンドリングの一貫性を向上させるという目的があります。Cの関数呼び出しでは、多くの場合、エラーが発生した際に `errno` を設定することが慣例です。GoランタイムがCGOを介してC関数を呼び出す際、`errno` の値を適切に処理することは、堅牢なエラーハンドリングのために不可欠です。

`cgocall_errno` の方を標準的な `cgocall` として採用することで、すべてのCGO呼び出しが `errno` の処理を意識するようになり、潜在的なエラーを見落とすリスクを減らすことができます。このコミットは、そのリネーム作業を安全に行うための前段階として、古い `cgocall` と `asmcgocall` を完全に削除し、既存の呼び出し箇所を `_errno` サフィックスを持つバージョンに切り替えることで、名前の衝突を避け、段階的な移行を可能にしています。

rsc（Russ Cox）によるCL 9387の分割要求は、このような大規模なリファクタリングをより小さく、レビューしやすい単位に分割することで、変更の複雑さを管理し、バグの導入リスクを低減するための一般的なソフトウェア開発プラクティスに従ったものです。

## 前提知識の解説

### GoランタイムとCGO

Go言語は、C言語のコードを呼び出すためのCGO（C Go）というメカニズムを提供しています。これは、Goプログラムから既存のCライブラリを利用したり、OSのシステムコールを直接呼び出したりする際に不可欠です。CGO呼び出しは、通常のGo関数呼び出しとは異なり、GoランタイムのスケジューラとCランタイムの間でコンテキストスイッチを伴います。

*   **Goスケジューラ**: Goの軽量スレッドであるゴルーチンを管理し、OSスレッドにマッピングして実行します。
*   **CGO呼び出しの複雑性**: Goのゴルーチンは非同期的にプリエンプト（横取り）される可能性がありますが、Cコードの実行中はGoランタイムがCコードをプリエンプトすることはできません。そのため、CGO呼び出し中は、GoスケジューラがそのOSスレッドをブロック状態として扱い、他のゴルーチンを別のOSスレッドにスケジュールするなどの調整が必要です。また、スタックの切り替え（GoのスタックからCのスタックへ、またはその逆）も行われます。
*   **`m` と `g`**: Goランタイムの内部では、`m` (machine) はOSスレッドを表し、`g` (goroutine) はゴルーチンを表します。CGO呼び出しは、特定の `m` 上で実行されます。

### `errno` とエラーハンドリング

C言語のプログラミングでは、システムコールやライブラリ関数がエラーを報告する一般的な方法として、グローバル変数 `errno` を使用します。関数が失敗した場合、通常は特定の戻り値（例: -1 や NULL）を返し、`errno` にエラーの種類を示す整数値を設定します。GoがCGOを介してC関数を呼び出す場合、この `errno` の値をGo側で適切に取得し、Goのエラーとして処理する必要があります。

### アセンブリコード (`asm_*.s`)

Goランタイムの低レベルな部分、特にOSとのインタラクションやコンテキストスイッチ、スタック管理などには、アセンブリ言語で書かれたコードが使用されます。`src/runtime/asm_*.s` ファイル群は、各アーキテクチャ（386, amd64, armなど）向けに最適化されたアセンブリコードを含んでいます。`asmcgocall` や `asmcgocall_errno` のような関数は、GoとCの間の呼び出し規約（calling convention）の橋渡しをする役割を担っていました。

### `go:nosplit` ディレクティブ

Go関数に付与される `//go:nosplit` ディレクティブは、その関数がスタックの拡張を必要としないことをコンパイラに指示します。これは、スタックの拡張処理中にデッドロックや競合状態を引き起こす可能性がある、低レベルのランタイム関数でよく使用されます。CGO関連の関数は、ランタイムの非常にデリケートな部分に触れるため、このディレクティブが適用されることがよくあります。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイム内部でCGO呼び出しを処理する `cgocall` および `asmcgocall` の役割を `cgocall_errno` および `asmcgocall_errno` に統一することです。

具体的には、以下のステップが実行されています。

1.  **`cgocall` 関数の削除**: `src/runtime/cgocall.go` から、`cgocall` 関数自体が削除されました。この関数は、内部で `cgocall_errno` を呼び出すだけのラッパーでした。
    ```go
    // 削除前
    //go:nosplit
    func cgocall(fn, arg unsafe.Pointer) {
        cgocall_errno(fn, arg)
    }
    ```
    この削除により、Goコードから直接 `cgocall` を呼び出すことはできなくなります。

2.  **`asmcgocall` アセンブリルーチンの削除**: 各アーキテクチャのアセンブリファイル (`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s` など) から、`TEXT ·asmcgocall(SB)` で定義されていたアセンブリルーチンが削除されました。これらのルーチンは、GoのスタックからCのスタックへの切り替えや、レジスタの保存・復元といった低レベルな処理を担当していました。

3.  **既存の `cgocall` / `asmcgocall` 呼び出し箇所の変更**: Goランタイム内の `cgocall` および `asmcgocall` を使用していたすべての箇所が、対応する `cgocall_errno` および `asmcgocall_errno` に変更されました。これにより、CGO呼び出しを行うすべてのコードパスが、`errno` の処理をサポートするバージョンを使用するようになります。
    *   `src/runtime/cgocall.go`: `cmalloc` や `cfree` といったCのメモリ管理関数を呼び出す箇所が `cgocall_errno` を使用するように変更。
    *   `src/runtime/env_posix.go`: 環境変数を設定・解除する `syscall_setenv_c` や `syscall_unsetenv_c` が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/os1_windows.go`: Windows固有のシステムコールラッパー `stdcall` が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/os3_solaris.go`, `src/runtime/os_solaris.go`, `src/runtime/syscall_solaris.go`: Solaris固有のシステムコールやセマフォ操作、`sysvicall` 関連の関数が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/proc.go`, `src/runtime/proc1.go`: ランタイムの初期化や新しいM（OSスレッド）の作成に関連するCGO呼び出しが `cgocall_errno` または `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/stubs.go`: `asmcgocall` の宣言が削除されました。

この変更は、GoランタイムのCGOインターフェースを簡素化し、`errno` の処理を標準化するための重要なステップです。これにより、将来的にCGO呼び出しのセマンティクスがより明確になり、エラーハンドリングのバグが減少することが期待されます。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがCGO呼び出しを行う際の内部的なインターフェースを `_errno` サフィックスを持つ関数に統一することです。

例えば、`src/runtime/cgocall.go` の `cmalloc` 関数では、Cの `malloc` を呼び出すために `cgocall` を使用していました。

**変更前:**
```go
func cmalloc(n uintptr) unsafe.Pointer {
    // ...
    cgocall(_cgo_malloc, unsafe.Pointer(&args))
    // ...
}
```

**変更後:**
```go
func cmalloc(n uintptr) unsafe.Pointer {
    // ...
    cgocall_errno(_cgo_malloc, unsafe.Pointer(&args))
    // ...
}
```

同様に、アセンブリレベルのラッパーである `asmcgocall` も、各アーキテクチャの `asm_*.s` ファイルから完全に削除されました。これにより、Goランタイム内でCGO呼び出しを行うすべての箇所が、`errno` の処理を組み込んだ `cgocall_errno` または `asmcgocall_errno` を明示的に使用するようになります。

この変更は、単なる名前の変更以上の意味を持ちます。`_errno` バリアントは、C関数呼び出し後に `errno` の値を保存し、Go側で利用できるようにする追加のロジックを含んでいます。この統一により、GoランタイムはCGOを介したC関数呼び出しから返されるエラー情報をより確実に捕捉し、Goのエラーモデルに変換できるようになります。これは、特にOSのシステムコールなど、`errno` を広範に利用するCライブラリとの連携において、Goプログラムの堅牢性と信頼性を向上させる上で重要です。

このコミット自体は `_errno` サフィックスを持つ関数へのリネームは行っていませんが、そのための土台を築いています。古い関数を削除し、すべての呼び出し箇所を `_errno` バージョンに切り替えることで、次のコミットで `_errno` サフィックスを削除しても名前の衝突が発生しないようにしています。

*   **GoからCへの呼び出しフロー**:
    1.  **Cgo生成ラッパー**: Cgoツールは、`runtime.cgocall` を呼び出すGoラッパー関数と、実際のC関数を呼び出すCラッパー関数（例: `_cgo_Cfunc_f`）を生成します。
    2.  **`runtime.cgocall` 呼び出し**: Goラッパーは `runtime.cgocall(_cgo_Cfunc_f, frame)` を呼び出します。ここで `_cgo_Cfunc_f` はCラッパー、`frame` はC関数の引数を含みます。
    3.  **ゴルーチンのロックと `entersyscall`**: `runtime.cgocall` の内部で、現在のゴルーチン（G）はOSスレッド（M）にロックされます。これにより、Cコードの実行中にGoスケジューラがゴルーチンを別のスレッドに移動させるのを防ぎます。次に `entersyscall` が呼び出され、現在のMがGo以外のコードを実行しようとしていることをGoスケジューラに通知します。これにより、スケジューラは新しいMを作成して他のゴルーチンを実行し、C呼び出しがGoプログラム全体をブロックするのを防ぐことができます。
    4.  **スタック切り替え (`runtime.asmcgocall`)**: `runtime.cgocall` は `runtime.asmcgocall` を呼び出します。このアセンブリ関数は、現在のゴルーチンのスタックからM専用の「g0」スタックに実行コンテキストを切り替えます。g0スタックはOSによって割り当てられたスタックであり、従来のCスタックを期待するgccでコンパイルされたCコードを安全に実行できます。
    5.  **C関数の実行**: g0スタック上で、`runtime.asmcgocall` はCラッパー関数（`_cgo_Cfunc_f`）を呼び出し、それが `frame` 構造体から引数を受け取って実際のC関数を呼び出します。結果もこのフレームに記録されます。
    6.  **Goスタックへの復帰**: C関数の完了後、`runtime.asmcgocall` が制御を取り戻し、元のゴルーチンのスタックに戻って `runtime.cgocall` に戻ります。
    7.  **`exitsyscall` とゴルーチンのアンロック**: `runtime.cgocall` は `exitsyscall` を呼び出します。この関数は、Mが `$GOMAXPROCS` の制限に違反することなくGoコードを安全に実行できるようになるまでブロックし、その後ゴルーチンのMからのロックを解除します。
*   **パフォーマンスの考慮事項**: `runtime.cgocall` のオーバーヘッドを含むCgo呼び出しは、ネイティブなGo関数呼び出しよりも大幅に遅いです。このオーバーヘッドは、コンテキスト切り替え、スタック切り替え、スケジューラとの相互作用によるものです。

### `errno` とエラーハンドリング

C言語のプログラミングでは、システムコールやライブラリ関数がエラーを報告する一般的な方法として、グローバル変数 `errno` を使用します。関数が失敗した場合、通常は特定の戻り値（例: -1 や NULL）を返し、`errno` にエラーの種類を示す整数値を設定します。GoがCGOを介してC関数を呼び出す際、この `errno` の値をGo側で適切に取得し、Goのエラーとして処理する必要があります。

*   **Goゴルーチンとの課題**: GoのゴルーチンはGoランタイムによってOSスレッドに多重化されます。これは、1つのゴルーチンが異なるOSスレッドで異なる時間に実行される可能性があることを意味します。GoプログラムがC関数を呼び出し、その後直接 `C.errno` を読み取ろうとすると、ゴルーチンが別のOSスレッドに再スケジュールされている可能性があり、読み取られた `errno` の値がその特定のゴルーチンが行ったC呼び出しに対応しないリスクがあります。これは誤ったエラー報告につながります。
*   **`cgocall_errno` による解決**: スレッドセーフティの問題に対処するため、cgoはC関数呼び出しが完了した直後、ゴルーチンが再スケジュールされる前に `errno` の値を自動的に捕捉します。この捕捉された `errno` の値は、標準のGo `error` 型として返されます。
*   **Goでの使用法**: cgoを介してC関数を呼び出す際、関数の戻り値と `errno` をGo `error` として多値代入で取得できます。例えば、`value, err := C.some_c_function()` のように記述します。`some_c_function` が `errno` を設定した場合、`err` はその `errno` 値をラップした非nilのGoエラーになります。この `err` を `syscall.Errno` (または古いGoバージョンでは `os.Errno`) に型アサートすることで、基になる整数エラーコードを取得できます。
*   **重要な注意点**: C関数は成功時に `errno` をゼロに設定することを常に保証するわけではないという重要な注意点があります。C関数が成功しても、`errno` が *以前の* 操作からの非ゼロ値を保持している場合、cgoは依然として非nilのGoエラーを返します。したがって、実際のC関数がエラーを発生させたかどうかを判断するために、常にC関数の主要な戻り値を確認することが重要です。

要するに、`cgocall_errno` は、Goがマルチスレッド環境でCの `errno` を安全かつ慣用的に処理し、それをGo `error` 型に変換するための内部メカニズムです。

### アセンブリコード (`asm_*.s`)

Goランタイムの低レベルな部分、特にOSとのインタラクションやコンテキストスイッチ、スタック管理などには、アセンブリ言語で書かれたコードが使用されます。`src/runtime/asm_*.s` ファイル群は、各アーキテクチャ（386, amd64, armなど）向けに最適化されたアセンブリコードを含んでいます。`asmcgocall` や `asmcgocall_errno` のような関数は、GoとCの間の呼び出し規約（calling convention）の橋渡しをする役割を担っていました。

### `go:nosplit` ディレクティブ

Go関数に付与される `//go:nosplit` ディレクティブは、その関数がスタックの拡張を必要としないことをコンパイラに指示します。これは、スタックの拡張処理中にデッドロックや競合状態を引き起こす可能性がある、低レベルのランタイム関数でよく使用されます。CGO関連の関数は、ランタイムの非常にデリケートな部分に触れるため、このディレクティブが適用されることがよくあります。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイム内部でCGO呼び出しを処理する `cgocall` および `asmcgocall` の役割を `cgocall_errno` および `asmcgocall_errno` に統一することです。

具体的には、以下のステップが実行されています。

1.  **`cgocall` 関数の削除**: `src/runtime/cgocall.go` から、`cgocall` 関数自体が削除されました。この関数は、内部で `cgocall_errno` を呼び出すだけのラッパーでした。
    ```go
    // 削除前
    //go:nosplit
    func cgocall(fn, arg unsafe.Pointer) {
        cgocall_errno(fn, arg)
    }
    ```
    この削除により、Goコードから直接 `cgocall` を呼び出すことはできなくなります。

2.  **`asmcgocall` アセンブリルーチンの削除**: 各アーキテクチャのアセンブリファイル (`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s` など) から、`TEXT ·asmcgocall(SB)` で定義されていたアセンブリルーチンが削除されました。これらのルーチンは、GoのスタックからCのスタックへの切り替えや、レジスタの保存・復元といった低レベルな処理を担当していました。

3.  **既存の `cgocall` / `asmcgocall` 呼び出し箇所の変更**: Goランタイム内の `cgocall` および `asmcgocall` を使用していたすべての箇所が、対応する `cgocall_errno` および `asmcgocall_errno` に変更されました。これにより、CGO呼び出しを行うすべてのコードパスが、`errno` の処理をサポートするバージョンを使用するようになります。
    *   `src/runtime/cgocall.go`: `cmalloc` や `cfree` といったCのメモリ管理関数を呼び出す箇所が `cgocall_errno` を使用するように変更。
    *   `src/runtime/env_posix.go`: 環境変数を設定・解除する `syscall_setenv_c` や `syscall_unsetenv_c` が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/os1_windows.go`: Windows固有のシステムコールラッパー `stdcall` が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/os3_solaris.go`, `src/runtime/os_solaris.go`, `src/runtime/syscall_solaris.go`: Solaris固有のシステムコールやセマフォ操作、`sysvicall` 関連の関数が `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/proc.go`, `src/runtime/proc1.go`: ランタイムの初期化や新しいM（OSスレッド）の作成に関連するCGO呼び出しが `cgocall_errno` または `asmcgocall_errno` を使用するように変更。
    *   `src/runtime/stubs.go`: `asmcgocall` の宣言が削除されました。

この変更は、GoランタイムのCGOインターフェースを簡素化し、`errno` の処理を標準化するための重要なステップです。これにより、将来的にCGO呼び出しのセマンティクスがより明確になり、エラーハンドリングのバグが減少することが期待されます。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがCGO呼び出しを行う際の内部的なインターフェースを `_errno` サフィックスを持つ関数に統一することです。

例えば、`src/runtime/cgocall.go` の `cmalloc` 関数では、Cの `malloc` を呼び出すために `cgocall` を使用していました。

**変更前:**
```go
func cmalloc(n uintptr) unsafe.Pointer {
    // ...
    cgocall(_cgo_malloc, unsafe.Pointer(&args))
    // ...
}
```

**変更後:**
```go
func cmalloc(n uintptr) unsafe.Pointer {
    // ...
    cgocall_errno(_cgo_malloc, unsafe.Pointer(&args))
    // ...
}
```

同様に、アセンブリレベルのラッパーである `asmcgocall` も、各アーキテクチャの `asm_*.s` ファイルから完全に削除されました。これにより、Goランタイム内でCGO呼び出しを行うすべての箇所が、`errno` の処理を組み込んだ `cgocall_errno` または `asmcgocall_errno` を明示的に使用するようになります。

この変更は、単なる名前の変更以上の意味を持ちます。`_errno` バリアントは、C関数呼び出し後に `errno` の値を保存し、Go側で利用できるようにする追加のロジックを含んでいます。この統一により、GoランタイムはCGOを介したC関数呼び出しから返されるエラー情報をより確実に捕捉し、Goのエラーモデルに変換できるようになります。これは、特にOSのシステムコールなど、`errno` を広範に利用するCライブラリとの連携において、Goプログラムの堅牢性と信頼性を向上させる上で重要です。

このコミット自体は `_errno` サフィックスを持つ関数へのリネームは行っていませんが、そのための土台を築いています。古い関数を削除し、すべての呼び出し箇所を `_errno` バージョンに切り替えることで、次のコミットで `_errno` サフィックスを削除しても名前の衝突が発生しないようにしています。

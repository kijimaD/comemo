## 変更の背景

Go言語の`net`パッケージには、ネットワーク関連の様々な機能が実装されています。`LookupPort`関数は、サービス名（例: "http", "ftp"）とネットワークプロトコル（例: "tcp", "udp"）に基づいてポート番号を検索する機能を提供します。

元々、`TestLookupPort`は`port_test.go`というファイルに存在していました。しかし、`LookupPort`関数自体は、DNSルックアップやサービス名解決といった「ルックアップ」の範疇に属する機能です。Goのテストファイルの命名規則や慣習として、特定の機能に関連するテストは、その機能が属するパッケージ内の適切なテストファイルに配置されることが推奨されます。

このコミットの背景には、テストコードの論理的な配置と保守性の向上が挙げられます。`LookupPort`が`lookup`関連の機能であるため、そのテストも`lookup_test.go`に移動することで、コードベースの整理と可読性の向上が図られました。これにより、将来的に`LookupPort`関数や関連するルックアップ機能に変更が加えられた際に、関連するテストを`lookup_test.go`内で一貫して見つけることができるようになります。

## 前提知識の解説

### Go言語の`net`パッケージ
`net`パッケージは、Go言語でネットワークI/Oを実装するための主要なパッケージです。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルをサポートし、ネットワーク接続の確立、データの送受信、IPアドレスやホスト名の解決などの機能を提供します。

### `LookupPort`関数
`net.LookupPort(network, service string) (port int, err error)`は、指定されたネットワークプロトコル（`network`、例: "tcp", "udp"）とサービス名（`service`、例: "http", "ftp"）に対応するポート番号を検索する関数です。例えば、`LookupPort("tcp", "http")`は通常80を返します。この関数は、`/etc/services`のようなシステム設定ファイルや、DNSのSRVレコードなどを参照してポート情報を解決します。

### Go言語のテスト
Go言語では、テストは非常に重要な開発プロセスの一部です。
- **テストファイルの命名規則**: テストファイルは、テスト対象のソースファイルと同じディレクトリに配置され、ファイル名の末尾に`_test.go`を付けます（例: `lookup.go`に対する`lookup_test.go`）。
- **テスト関数の命名規則**: テスト関数は`Test`で始まり、その後に続く名前の最初の文字は大文字である必要があります（例: `func TestLookupPort(t *testing.T)`）。
- **`*testing.T`**: テスト関数は`*testing.T`型の引数を受け取ります。これを通じて、テストの失敗を報告したり、ログを出力したり、テストをスキップしたりすることができます。
- **テーブルドリブンテスト**: 複数のテストケースを構造体のスライスとして定義し、ループで各テストケースを実行するパターンです。これにより、テストコードの重複を減らし、テストケースの追加・管理を容易にします。このコミットで移動された`lookupPortTests`変数は、このテーブルドリブンテストの典型的な例です。

### `runtime.GOOS`
`runtime.GOOS`は、Goプログラムが実行されているオペレーティングシステムを示す文字列定数です（例: "linux", "windows", "darwin", "nacl"）。テストコード内で特定のOSでのみ実行されるべきでないテストをスキップするために使用されることがあります。このコミットの`TestLookupPort`では、`nacl`（Google Native Client）環境ではテストをスキップするようになっています。これは、`LookupPort`が`nacl`環境でサポートされていないか、異なる振る舞いをする可能性があるためです。

## 技術的詳細

このコミットは、Go言語のテストフレームワークとパッケージ構造に関する理解に基づいています。

1.  **テストの発見と実行**: `go test`コマンドは、カレントディレクトリとそのサブディレクトリ内の`_test.go`ファイルをスキャンし、`Test`で始まる関数をテストとして認識して実行します。テストファイルが移動されても、このメカニズムは変わらないため、テストの実行には影響ありません。
2.  **パッケージの整合性**: `src/net/port_test.go`と`src/net/lookup_test.go`はどちらも`package net`に属しています。Goでは、同じディレクトリ内の`_test.go`ファイルは、テスト対象のパッケージと同じパッケージ名を持つ必要があります。これにより、テストコードはテスト対象のパッケージの内部関数や変数にアクセスできます。この移動は、このパッケージの整合性を維持したまま行われています。
3.  **リファクタリングのメリット**:
    *   **論理的なグループ化**: `LookupPort`関数が`lookup`関連の機能であるため、そのテストを`lookup_test.go`に配置することで、関連するコードとテストが近くにまとまり、コードベースの論理的な構造が強化されます。
    *   **保守性の向上**: 将来的に`LookupPort`関数に修正が加えられた場合、開発者は`lookup.go`と`lookup_test.go`の両方を確認すればよくなり、関連するテストを探す手間が省けます。
    *   **ファイルサイズの管理**: `port_test.go`からテストが削除され、`lookup_test.go`に追加されたことで、各テストファイルの役割がより明確になり、ファイルが肥大化するのを防ぐことができます。

この変更は「No code changes.」と明記されている通り、`LookupPort`関数の振る舞いや`net`パッケージの機能に影響を与えるものではなく、純粋にテストコードの内部的な整理に焦点を当てています。

## コアとなるコードの解説

移動された`TestLookupPort`関数と`lookupPortTests`変数は、`net.LookupPort`関数の正確性を検証するためのテーブルドリブンテストを構成しています。

### `lookupPortTests`変数

```go
var lookupPortTests = []struct {
	network string
	name    string
	port    int
	ok      bool
}{
	// ... (テストケースの定義) ...
}
```

この変数は、`LookupPort`関数に与える入力（`network`と`name`）と、期待される出力（`port`と`ok`）を定義した構造体のスライスです。
- `network`: ネットワークプロトコル（例: "tcp", "udp"）。
- `name`: サービス名またはポート番号の文字列（例: "echo", "80"）。
- `port`: `LookupPort`が成功した場合に期待されるポート番号。
- `ok`: `LookupPort`がエラーなく成功するかどうかを示すブール値。`true`であれば成功、`false`であればエラーが期待されます。

このテーブルには、一般的なサービス名（"echo", "ftp", "http"など）とそれに対応するポート番号、および無効な入力（"--badnet--", "--badport--", "-1", "65536"など）に対するエラーケースが網羅されています。

### `TestLookupPort`関数

```go
func TestLookupPort(t *testing.T) {
	switch runtime.GOOS {
	case "nacl":
		t.Skipf("not supported on %s", runtime.GOOS)
	}

	for _, tt := range lookupPortTests {
		if port, err := LookupPort(tt.network, tt.name); port != tt.port || (err == nil) != tt.ok {
			t.Errorf("LookupPort(%q, %q) = %d, %v; want %d", tt.network, tt.name, port, err, tt.port)
		}
	}
}
```

1.  **OSによるスキップ**:
    ```go
    switch runtime.GOOS {
    case "nacl":
        t.Skipf("not supported on %s", runtime.GOOS)
    }
    ```
    この部分は、テストが`nacl`（Google Native Client）環境で実行されている場合、テスト全体をスキップします。これは、`LookupPort`関数が`nacl`環境でサポートされていないか、その環境での動作が他のOSと異なる可能性があるためです。`t.Skipf`は、テストをスキップし、その理由をフォーマットされた文字列で出力します。

2.  **テーブルドリブンテストの実行**:
    ```go
    for _, tt := range lookupPortTests {
        if port, err := LookupPort(tt.network, tt.name); port != tt.port || (err == nil) != tt.ok {
            t.Errorf("LookupPort(%q, %q) = %d, %v; want %d", tt.network, tt.name, port, err, tt.port)
        }
    }
    ```
    このループは、`lookupPortTests`スライス内の各テストケース（`tt`）を順番に処理します。
    - `LookupPort(tt.network, tt.name)`を呼び出し、実際のポート番号（`port`）とエラー（`err`）を取得します。
    - 取得した`port`が期待される`tt.port`と異なる場合、または、エラーの有無（`err == nil`）が期待される`tt.ok`と異なる場合、テストは失敗と判断されます。
    - `t.Errorf`は、テストが失敗したことを報告し、期待値と実際の結果を詳細に表示します。これにより、どのテストケースでどのような不一致があったのかを明確に把握できます。

このテストは、`LookupPort`関数が様々な入力に対して正しくポート番号を解決し、期待通りにエラーを処理することを確認するために不可欠です。

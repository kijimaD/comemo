# [インデックス 23926] ファイルの概要

このコミットは、Goランタイムのメモリ管理において、`h_spans`という重要なデータ構造への並行アクセスに関するメモリ順序付けの保証について、コード内にドキュメントを追加するものです。特に、弱順序メモリモデルを持つアーキテクチャ上での正しい動作を保証するために、ヒープロックのアンロック操作が提供するメモリバリアの役割を明示しています。

## コミット

runtime: document memory ordering for h_spans

h_spans can be accessed concurrently without synchronization from
other threads, which means it needs the appropriate memory barriers on
weakly ordered machines. It happens to already have the necessary
memory barriers because all accesses to h_spans are currently
protected by the heap lock and the unlocks happen in exactly the
places where release barriers are needed, but it's easy to imagine
that this could change in the future. Document the fact that we're
depending on the barrier implied by the unlock.

Related to issue #9984.

## 変更の背景

Goランタイムのメモリ管理において、`h_spans`というデータ構造は、ヒープ上のメモリ領域（`mspan`）を管理するために使用されます。この`h_spans`は、他のスレッド（特に並行ガベージコレクタ）から同期なしに並行アクセスされる可能性があります。このような並行アクセスがある場合、特にARMやPowerPCのような弱順序メモリモデルを持つプロセッサアーキテクチャでは、コンパイラやプロセッサによる命令の並べ替え（リオーダリング）によって予期せぬ動作が発生する可能性があります。

これまでの実装では、`h_spans`への全てのアクセスがヒープロック（`h.lock`）によって保護されており、このロックのアンロック操作が偶然にも必要なメモリバリア（リリースバリア）を提供していました。しかし、このメモリバリアの存在が明示的にドキュメント化されていなかったため、将来のコード変更でこの暗黙の依存関係が見落とされ、バグが導入されるリスクがありました。

このコミットの目的は、この重要なメモリ順序付けの保証をコードコメントとして明示的に記述し、将来の保守性を高めることにあります。これにより、開発者が`h_spans`に関連するコードを変更する際に、メモリバリアの必要性を認識し、誤って削除したり変更したりするのを防ぐことができます。

## 前提知識の解説

### Goランタイムとメモリ管理

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、スケジューラ、ガベージコレクタ、メモリ管理などが含まれます。Goのメモリ管理は、ヒープと呼ばれる領域からメモリを割り当て、不要になったメモリをガベージコレクタが自動的に解放します。

*   **`mheap`**: Goランタイムのグローバルなヒープを表現する構造体です。システムからメモリを要求し、それを`mspan`に分割して管理します。
*   **`mspan`**: 連続したページ（通常は8KB）の集合を表す構造体です。`mheap`から取得され、オブジェクトの割り当てに使用されます。`mspan`は、その中に割り当てられたオブジェクトのサイズクラス（例えば、8バイト、16バイトなど）に応じて管理されます。
*   **`h_spans`**: `mheap`構造体の一部であり、`mspan`のポインタをページ番号でインデックス付けして保持する配列またはマップのようなデータ構造です。これにより、特定のページアドレスがどの`mspan`に属するかを効率的に検索できます。ガベージコレクタは、オブジェクトのポインタからそのオブジェクトが属する`mspan`を特定するために`h_spans`を参照します。

### メモリ順序付けとメモリバリア

現代のプロセッサは、性能向上のために命令の実行順序を最適化（リオーダリング）することがあります。また、複数のプロセッサコアがそれぞれ独自のキャッシュを持つため、あるコアが行ったメモリへの書き込みが、別のコアからすぐに可視になるとは限りません。このような状況は、並行プログラムにおいてデータ競合や予期せぬ動作を引き起こす可能性があります。

*   **弱順序メモリモデル (Weakly Ordered Memory Model)**: ARMやPowerPCなどの一部のプロセッサアーキテクチャは、メモリ操作の順序について比較的緩い保証しか提供しません。これは、プログラマが明示的にメモリ操作の順序を強制しない限り、コンパイラやハードウェアがメモリ操作を自由に並べ替える可能性があることを意味します。
*   **メモリバリア (Memory Barrier) / メモリフェンス (Memory Fence)**: メモリバリアは、プロセッサやコンパイラに対して、特定のメモリ操作の順序を強制する命令です。メモリバリアを挿入することで、そのバリアより前のメモリ操作が全て完了してから、バリアより後のメモリ操作が開始されることを保証します。
    *   **ストア/ストアバリア (Store/Store Barrier)**: 複数のストア（書き込み）操作の順序を保証します。バリアより前のストアが、バリアより後のストアよりも先に他のプロセッサから見えることを保証します。
    *   **リリースバリア (Release Barrier)**: ロックのアンロック操作などに関連して使用されます。リリースバリアより前の全てのメモリ書き込みが、バリアより後に発生するメモリ書き込みよりも先に他のプロセッサから見えることを保証します。これにより、ロックを解放する前に保護されたデータへの変更が全て完了していることを保証できます。
    *   **データ依存性 (Data Dependency)**: あるメモリ操作の結果が別のメモリ操作の入力として使われる場合、それらの操作の間にはデータ依存性があります。プロセッサは通常、データ依存性のある操作の順序を維持しますが、異なる変数へのアクセスやポインタの読み書きが絡むと、明示的なバリアが必要になることがあります。

### ロックとメモリバリア

ミューテックスなどのロック機構は、通常、内部的にメモリバリアを含んでいます。ロックの取得（acquire）はアキアバリア（acquire barrier）を、ロックの解放（release）はリリースバリア（release barrier）を暗黙的に提供することが多いです。これにより、ロックによって保護されたクリティカルセクション内のメモリ操作が、ロックの取得前や解放後にリオーダリングされることを防ぎ、並行処理の正しさを保証します。

## 技術的詳細

このコミットは、`mHeap_Alloc_m`関数と`mHeap_AllocStack`関数における`h_spans`への書き込みと、それに続く`unlock(&h.lock)`操作の間のメモリ順序付けに焦点を当てています。

`mHeap_Alloc_m`関数は、ヒープから新しい`mspan`を割り当て、その`mspan`に関する情報を`h_spans`に登録します。この`h_spans`への書き込みは、新しいオブジェクトが割り当てられたことを示すポインタが呼び出し元に公開される前に完了している必要があります。なぜなら、ガベージコレクタが別のプロセッサで実行されている場合、公開されたポインタを読み取り、そのポインタが指すオブジェクトが属する`mspan`を`h_spans`から検索しようとする可能性があるからです。

弱順序メモリモデルのシステムでは、`h_spans`への書き込みと、オブジェクトポインタの公開（これは`mHeap_Alloc_m`の戻り値を通じて行われる）の間に、プロセッサが命令を並べ替えてしまう可能性があります。もし`h_spans`への書き込みがオブジェクトポインタの公開よりも後に実行されたり、他のプロセッサから見えるようになるのが遅れたりすると、ガベージコレクタが古い`h_spans`の状態を見てしまい、誤った判断を下す可能性があります。

コミットメッセージと追加されたコメントが説明しているように、`unlock(&h.lock)`操作がこの問題に対する解決策を提供しています。ロックのアンロック操作は、通常、リリースバリアとして機能します。これにより、`unlock`より前の全てのメモリ書き込み（この場合は`h_spans`への書き込み）が、`unlock`より後のメモリ操作（この場合は`mHeap_Alloc_m`から返されたポインタの利用）よりも先に、他のプロセッサから見えることが保証されます。具体的には、`h_spans`への書き込みが完了してから、割り当てられたオブジェクトへのポインタが「公開」される（つまり、他のスレッドからアクセス可能になる）という順序が保証されます。

読み取り側（ガベージコレクタなど）では、オブジェクトポインタ`p`を読み取り、その`p`から`h_spans`内の対応する`mspan`を検索するという「データ依存性」があります。このデータ依存性により、プロセッサは`p`の読み取りと`h_spans`の検索の順序を維持するため、明示的な読み取りバリアは不要とされています。

このコミットは、既存のコードの動作を変更するものではなく、その動作が特定のメモリ順序付けの保証に依存していることを明示的にドキュメント化することで、将来のコード変更における潜在的なバグを防ぐためのものです。

## コアとなるコードの解説

### `mHeap_Alloc_m`関数への追加コメント

`mHeap_Alloc_m`関数に新しく追加されたコメントは、`h_spans`が他のスレッドから同期なしに並行アクセスされる可能性があることを強調しています。そのため、`h_spans`への書き込みが、割り当てられたオブジェクトへのポインタ`p`が呼び出し元に公開される前に完了することを保証するためのストア/ストアバリアが必要であると説明しています。

このバリアが必要な理由は、ガベージコレクタが別のプロセッサで実行されている場合、`p`を読み取り、その`p`から`h_spans`内の対応する`mspan`を検索する可能性があるためです。もし`h_spans`への書き込みが遅延すると、ガベージコレクタが古い情報に基づいて動作してしまう可能性があります。

コメントは、`unlock(&h.lock)`操作がこの必要なバリアとして機能していることを明示しています。`unlock`はリリースバリアとして機能し、それより前の全ての書き込み（`h_spans`への書き込みを含む）が、それより後の操作（`p`の公開）よりも先に他のプロセッサから見えることを保証します。

また、読み取り側では、`p`と`h_spans`内のインデックスとの間の「データ依存性」が読み取り順序を保証するため、明示的な読み取りバリアは不要であることも説明されています。

### `mHeap_AllocStack`関数への追加コメント

`mHeap_AllocStack`関数への追加コメントは簡潔で、「このアンロックはリリースバリアとして機能します。`mHeap_Alloc_m`を参照してください。」と述べています。これは、`mHeap_Alloc_m`で説明されたのと同じメモリ順序付けの原則が、スタック用の`mspan`割り当てにも適用されることを示しています。

これらのコメントは、Goランタイムのメモリ管理における微妙な並行処理の側面を明確にし、将来のコード変更者がこれらの重要な保証を維持できるようにするためのものです。

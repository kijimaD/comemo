# [インデックス 26208] ファイルの概要

このコミットは、Goプログラムがシグナルによって終了させられた際の終了ステータスに関するランタイムの挙動を修正するものです。具体的には、SIGHUP、SIGINT、SIGTERMといったシグナルによってプログラムが終了した場合に、以前は一律にステータス2で終了していた問題を解決し、シグナルによって終了したことを適切に示すステータスを返すように変更されています。これにより、シェルや親プロセスがGoプログラムの終了原因を正確に判断できるようになります。

## 元コミット内容

以前は、SIGHUP、SIGINT、SIGTERMといったシグナルによってプログラムが終了した場合、終了ステータスは2でした。このコミットは、ランタイムがシグナルによってプログラムが終了したことを示すステータスで終了するように修正します。

## 変更の背景

Unix系システムでは、プロセスが終了する際に「終了ステータス（exit status）」を親プロセスに返します。このステータスは通常0から255の範囲の整数で、プログラムの成功/失敗や終了原因を示します。慣例として、0は成功、非ゼロは失敗や異常終了を意味します。

プログラムがシグナルによって終了した場合、その終了ステータスは通常、シグナル番号に128を加えた値（またはそれを示す特定のビットパターン）となります。例えば、SIGTERM（シグナル番号15）で終了した場合、終了ステータスは143（128 + 15）となることが一般的です。これにより、親プロセスやシェルは、プログラムが正常終了したのか、エラーで終了したのか、あるいは外部からのシグナルによって強制終了されたのかを区別できます。

Goランタイムの以前の実装では、SIGHUP、SIGINT、SIGTERMなどの特定のシグナルによってプログラムが終了させられた場合でも、一律に終了ステータス2を返していました。ステータス2は一般的に「コマンドラインの構文エラー」や「ファイルが見つからない」といった、プログラム自身の問題を示すために使われることが多い値です。このため、シグナルによる終了と、プログラム内部のエラーによる終了が区別できず、デバッグや自動化スクリプトでのハンドリングが困難になるという問題がありました。

このコミットは、この不正確な終了ステータスの問題を解決し、Goプログラムがシグナルによって終了した際に、そのシグナルを適切に反映した終了ステータスを返すようにすることで、Unixの慣例に準拠させ、より正確なプロセス管理を可能にすることを目的としています。

## 前提知識の解説

### 終了ステータス (Exit Status)

Unix系OSにおいて、プロセスが終了する際に親プロセスに返す0から255までの整数値です。
- **0**: 成功を示します。
- **1-127**: 一般的にエラーや失敗を示します。具体的な意味はプログラムによって異なります。
- **128-255**: シグナルによる終了を示します。通常、`128 + シグナル番号` の形式で表現されます。例えば、SIGTERM (シグナル番号15) で終了した場合は `128 + 15 = 143` となります。

### シグナル (Signals)

Unix系OSにおけるプロセス間通信（IPC）の一種で、ソフトウェア割り込みのようなものです。特定のイベントが発生した際にOSがプロセスに通知するために使用されます。
- **SIGHUP (Signal Hang Up)**: 端末が切断された際にプロセスに送られるシグナル。デーモンプロセスが設定ファイルを再読み込みするトリガーとしても使われます。
- **SIGINT (Signal Interrupt)**: 通常、Ctrl+Cによって生成され、プロセスを中断するために使われます。
- **SIGTERM (Signal Terminate)**: プロセスを正常に終了させるための要求シグナル。プロセスはこれを受け取ってクリーンアップを行い、終了することが期待されます。
- **SIGKILL (Signal Kill)**: プロセスを強制終了させるシグナル。プロセスはこのシグナルを捕捉、ブロック、無視することはできません。
- **SIGABRT (Signal Abort)**: プログラム自身が異常終了を検出した際に、`abort()`関数を呼び出すことで生成されるシグナル。通常、コアダンプを伴います。
- **SIGPIPE (Signal Pipe)**: パイプの読み込み側が閉じられた状態で、書き込み側がパイプに書き込もうとした際に発生するシグナル。

### `syscall.WaitStatus`

Go言語の`syscall`パッケージに含まれる型で、`wait`システムコールなどによって取得されるプロセスの終了ステータスを解析するためのメソッドを提供します。
- `ws.Signaled()`: プロセスがシグナルによって終了したかどうかを返します。
- `ws.Signal()`: プロセスを終了させたシグナル番号を返します。

### `setsig`, `raise`, `updatesigmask` (Goランタイム内部関数)

これらはGoランタイム内部で使用される、シグナルハンドリングに関連する低レベルな関数です。
- `setsig(sig, handler, restart)`: 指定されたシグナル`sig`のハンドラを設定します。`_SIG_DFL`はデフォルトのハンドラを意味します。
- `raise(sig)`: 指定されたシグナル`sig`を現在のプロセスに送信します。
- `updatesigmask(sigmask)`: プロセスがブロックするシグナルのセット（シグナルマスク）を更新します。

## 技術的詳細

このコミットの核心は、Goランタイムがシグナルによって終了する際に、`exit(2)`を直接呼び出すのではなく、`dieFromSignal`という新しいヘルパー関数を導入し、これを通じてシグナルを再送することで、OSが適切な終了ステータスを設定するようにすることです。

具体的な変更点は以下の通りです。

1.  **`dieFromSignal`関数の導入**:
    `src/runtime/signal1_unix.go`に`dieFromSignal(sig int32)`関数が追加されました。この関数は、致命的なシグナルを受け取った際に、そのシグナルをプロセス自身に再送することで、OSがシグナルによる終了ステータスを生成するようにします。
    -   `setsig(sig, _SIG_DFL, false)`: まず、受け取ったシグナル`sig`のハンドラをデフォルト（OSの標準的な挙動）に戻します。これにより、シグナルが再送された際にGoランタイムのカスタムハンドラが再度呼び出されるのを防ぎ、OSがシグナルを処理するようにします。
    -   `updatesigmask(sigmask{})`: シグナルマスクをクリアし、すべてのシグナルがブロックされない状態にします。これにより、再送されたシグナルが確実にプロセスに到達するようにします。
    -   `raise(sig)`: プロセス自身に`sig`シグナルを再送します。これにより、OSがこのシグナルを捕捉し、プロセスを終了させ、適切なシグナル終了ステータスを設定します。
    -   `exit(2)`: `raise(sig)`が何らかの理由でプロセスを終了させなかった場合のフォールバックとして呼び出されます。これは通常到達しないコードパスです。

2.  **シグナルハンドラからの`dieFromSignal`の呼び出し**:
    -   `src/runtime/signal1_unix.go`内の`sigpipe()`関数や`crash()`関数（SIGABRTを発生させる）が、直接シグナルハンドラを操作して`raise`する代わりに、`dieFromSignal`を呼び出すように変更されました。
    -   各アーキテクチャ固有のシグナルハンドラ（`src/runtime/signal_386.go`, `src/runtime/signal_amd64x.go`など）において、`_SigKill`フラグが設定されている（つまり、プロセスを終了させるべきシグナルが来た）場合に、直接`exit(2)`を呼び出すのではなく、`dieFromSignal(int32(sig))`を呼び出すように変更されました。これにより、これらのシグナルも適切な終了ステータスを返すようになります。

3.  **NaClプラットフォームへの対応**:
    `src/runtime/os_nacl.go`にも`dieFromSignal`関数が追加されていますが、NACL (Native Client) 環境の特性上、ここでは単に`exit(2)`を呼び出す実装となっています。これはNACL環境が一般的なUnixシグナルハンドリングとは異なる制約を持つためと考えられます。

4.  **テストの追加**:
    `src/runtime/crash_unix_test.go`に`TestSignalExitStatus`という新しいテストが追加されました。このテストは、`testprog`というテストプログラムをビルドし、そのプログラムが`syscall.SIGTERM`を自身に送信して終了するシナリオをシミュレートします。そして、`exec.ExitError`から取得できる`syscall.WaitStatus`をチェックし、`Signaled()`が`true`であり、かつ`Signal()`が`syscall.SIGTERM`であることを検証します。これにより、シグナルによる終了が正しくOSに報告され、適切な終了ステータスが返されていることが確認されます。
    また、`src/runtime/testdata/testprog/signal.go`に、自身に`SIGTERM`を送信する`SignalExitStatus`関数を持つテストプログラムが追加され、上記のテストから利用されます。

この変更により、Goプログラムがシグナルによって終了した場合、シェルや他のプロセスは`$?`（bashの場合）などの終了ステータス変数を通じて、そのプログラムがどのシグナルによって終了したかを正確に知ることができるようになります。

## コアとなるコードの解説

### `dieFromSignal` 関数 (`src/runtime/signal1_unix.go`)

この関数は、Goランタイムがシグナルによって終了する際の中心的なロジックを担います。

```go
func dieFromSignal(sig int32) {
	// 1. シグナルハンドラをデフォルトに戻す
	setsig(sig, _SIG_DFL, false)
	// 2. シグナルマスクをクリアし、すべてのシグナルを受け付けるようにする
	updatesigmask(sigmask{})
	// 3. プロセス自身にシグナルを再送する
	raise(sig)
	// 4. 万が一、raise(sig)で終了しなかった場合のフォールバック
	exit(2)
}
```

-   **`setsig(sig, _SIG_DFL, false)`**: Goランタイムは通常、特定のシグナルに対して独自のハンドラを設定しています。しかし、プロセスをシグナルで終了させる場合、OSのデフォルトのシグナル処理に任せるのが最も確実で、かつOSが適切な終了ステータスを生成してくれます。この行は、`sig`で指定されたシグナルのハンドラをデフォルト（`_SIG_DFL`）に戻します。
-   **`updatesigmask(sigmask{})`**: プロセスは、特定のシグナルを一時的にブロック（無視）するようにシグナルマスクを設定できます。`sigmask{}`は空のシグナルマスクを表し、これを設定することで、現在ブロックされているすべてのシグナルを解除し、プロセスがすべてのシグナルを受け付けられる状態にします。これにより、次に`raise(sig)`で送られるシグナルが確実に処理されるようにします。
-   **`raise(sig)`**: この関数は、現在のプロセスに`sig`で指定されたシグナルを送信します。ハンドラがデフォルトに戻され、シグナルマスクがクリアされているため、OSは通常通りこのシグナルを処理し、プロセスを終了させます。この際、OSはシグナルによる終了を示す適切な終了ステータスを生成します。
-   **`exit(2)`**: 理論的には`raise(sig)`がプロセスを終了させるはずですが、万が一、何らかの理由でプロセスが終了しなかった場合の安全策として`exit(2)`が呼び出されます。これはほとんどの場合実行されないコードパスです。

### アーキテクチャ固有のシグナルハンドラ (`src/runtime/signal_amd64x.go`など)

以前は、致命的なシグナル（`flags&_SigKill != 0`）を受け取った際に、直接`exit(2)`を呼び出していましたが、この変更により`dieFromSignal(int32(sig))`を呼び出すようになりました。これにより、各アーキテクチャのシグナルハンドラも、シグナルによる終了ステータスを正しく報告するようになります。

### `TestSignalExitStatus` (`src/runtime/crash_unix_test.go`)

このテストは、変更が正しく機能していることを検証します。

```go
func TestSignalExitStatus(t *testing.T) {
	// テストプログラムをビルド
	exe, err := buildTestProg(t, "testprog")
	// テストプログラムを実行し、自身にSIGTERMを送信させる
	err = testEnv(exec.Command(exe, "SignalExitStatus")).Run()

	// 終了ステータスの検証
	if err == nil {
		t.Error("test program succeeded unexpectedly") // 成功は予期しない
	} else if ee, ok := err.(*exec.ExitError); !ok {
		t.Errorf("error (%v) has type %T; expected exec.ExitError", err, err) // エラーがexec.ExitErrorでない場合はエラー
	} else if ws, ok := ee.Sys().(syscall.WaitStatus); !ok {
		t.Errorf("error.Sys (%v) has type %T; expected syscall.WaitStatus", ee.Sys(), ee.Sys()) // Sys()がsyscall.WaitStatusでない場合はエラー
	} else if !ws.Signaled() || ws.Signal() != syscall.SIGTERM {
		t.Errorf("got %v; expected SIGTERM", ee) // シグナル終了でない、またはSIGTERMでない場合はエラー
	}
}
```

-   `buildTestProg(t, "testprog")`: `src/runtime/testdata/testprog`ディレクトリにあるテストプログラムをビルドします。
-   `exec.Command(exe, "SignalExitStatus").Run()`: ビルドされたテストプログラムを実行します。このプログラムは`SignalExitStatus`というコマンドライン引数を受け取ると、自身に`SIGTERM`シグナルを送信して終了します。
-   `err.(*exec.ExitError)`: プロセスが非ゼロのステータスで終了した場合、`exec.Command.Run()`は`*exec.ExitError`型のエラーを返します。
-   `ee.Sys().(syscall.WaitStatus)`: `exec.ExitError`の`Sys()`メソッドは、プラットフォーム固有の終了ステータス情報（Unix系では`syscall.WaitStatus`）を返します。
-   `!ws.Signaled() || ws.Signal() != syscall.SIGTERM`: `syscall.WaitStatus`の`Signaled()`メソッドでシグナルによって終了したかを確認し、`Signal()`メソッドで終了させたシグナルが`SIGTERM`であるかを確認します。これにより、Goランタイムがシグナルによる終了を正しくOSに報告しているかを検証します。

この一連の変更とテストにより、Goプログラムのシグナルによる終了ステータスがUnixの慣例に沿ったものとなり、より堅牢なプロセス管理が可能になりました。

# [インデックス 27590] ファイルの概要

このコミットは、Goコンパイラにおけるインライン化された関数本体のエクスポート機能を完成させるものです。これにより、コンパイラはパッケージ間でインライン化された関数本体を共有できるようになり、クロスパッケージインライン化によるパフォーマンス向上が期待されます。

## コミット

このコミットは、Goコンパイラのバイナリエクスポートフォーマットを拡張し、インライン化された関数本体をエクスポートおよびインポートする機能を追加します。これにより、コンパイラは他のパッケージからインライン化された関数本体を利用できるようになり、最適化の機会が増加します。

## 変更の背景

Goコンパイラは、プログラムの実行速度を向上させるために、小さな関数を呼び出し元に直接展開する「インライン化」という最適化を行います。しかし、これまでは、異なるパッケージ間で関数をインライン化する際に、その関数の本体（AST: 抽象構文木）をエクスポート・インポートする仕組みが不十分でした。

このコミットの背景には、以下の課題がありました。

1.  **クロスパッケージインライン化の制限:** パッケージ境界を越えて関数をインライン化するためには、インライン化される関数の本体が呼び出し元のパッケージに「見える」必要があります。従来のGoコンパイラのバイナリパッケージエクスポートフォーマットでは、型情報や定数などのAPI情報が主にエクスポートされており、関数本体のASTは含まれていませんでした。このため、コンパイラは同じパッケージ内の関数しかインライン化できませんでした。
2.  **最適化の機会損失:** クロスパッケージインライン化ができないことは、特に標準ライブラリのような頻繁に利用される小さな関数において、パフォーマンス最適化の大きな機会損失となっていました。例えば、`sync.Mutex`のロック/アンロック操作のような非常に短い関数がインライン化できない場合、関数呼び出しのオーバーヘッドが無視できない影響を与える可能性があります。
3.  **新しいバイナリエクスポートフォーマットへの移行:** Goコンパイラは、より効率的で柔軟な新しいバイナリエクスポートフォーマット（`bexport.go`で定義されるもの）への移行を進めていました。この新しいフォーマットは、関数本体のようなより複雑な情報をエクスポートするための基盤を提供することを目的としていました。

このコミットは、これらの課題を解決し、Goプログラムの全体的なパフォーマンスを向上させるために、新しいバイナリエクスポートフォーマットを利用してインライン化された関数本体をエクスポート・インポートする機能を完成させることを目的としています。これにより、コンパイラはより多くの関数をインライン化できるようになり、実行時のオーバーヘッドを削減し、より高速なコードを生成できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラと関連技術に関する前提知識が必要です。

1.  **Goコンパイラの構造:**
    *   **`cmd/compile`**: Go言語の公式コンパイラです。ソースコードを中間表現に変換し、最終的に機械語にコンパイルします。
    *   **AST (Abstract Syntax Tree):** ソースコードの構文構造を木構造で表現したものです。コンパイラはソースコードをパースしてASTを生成し、これに対して様々な解析や最適化を行います。
    *   **`gc` (Go Compiler):** `cmd/compile`の内部パッケージの一つで、コンパイラの主要なロジックを含みます。
    *   **`bexport.go` / `bimport.go`:** Goコンパイラがパッケージ情報をバイナリ形式でエクスポート・インポートするためのロジックを実装しているファイルです。Goのパッケージは、コンパイル時に`.a`（アーカイブ）ファイルとして出力され、その中にバイナリ形式のパッケージ情報が含まれます。他のパッケージがそのパッケージを利用する際には、このバイナリ情報をインポートして型情報などを取得します。
    *   **`go/internal/gcimporter`:** `go/types`パッケージなど、コンパイラ以外のツールがGoのバイナリパッケージ情報を読み込むための内部パッケージです。

2.  **インライン化 (Inlining):**
    *   コンパイラ最適化の一種で、関数呼び出しのオーバーヘッドを削減するために、呼び出される関数の本体を呼び出し元のコードに直接埋め込む（展開する）ことです。
    *   これにより、関数呼び出しのスタックフレームの作成・破棄、引数の渡し、戻り値の受け取りといった処理が不要になり、実行速度が向上します。
    *   しかし、インライン化はコードサイズを増加させる可能性があり、過度なインライン化はキャッシュミスを増やし、かえってパフォーマンスを低下させることもあります。コンパイラはヒューリスティックに基づいてインライン化の判断を行います。
    *   **クロスパッケージインライン化:** 異なるパッケージに定義された関数をインライン化することです。これが可能になると、より広範な最適化が適用できるようになります。

3.  **Goの型システムとシンボル:**
    *   **`*Type`:** Goコンパイラ内部で型を表す構造体です。
    *   **`*Sym` (Symbol):** 変数、関数、型などの識別子（名前）とそれに関連する情報を表す構造体です。
    *   **`*Node`:** ASTの各ノードを表す構造体です。

4.  **バイナリパッケージエクスポートフォーマット:**
    *   Goコンパイラは、パッケージのコンパイル済み情報をバイナリ形式で保存し、他のパッケージがそれを効率的に利用できるようにします。この情報には、エクスポートされた型、定数、変数、関数シグネチャなどが含まれます。
    *   このコミット以前は、関数本体のASTはエクスポートされていませんでした。

これらの知識を前提として、このコミットがどのようにGoコンパイラの機能とパフォーマンスを向上させるのかを深く掘り下げていきます。

## 技術的詳細

このコミットの技術的詳細は、主にGoコンパイラのバイナリパッケージエクスポート/インポートメカニズムの根本的な変更と、インライン化された関数本体のASTを効率的にシリアライズ/デシリアライズする手法にあります。

### 1. バイナリエクスポートフォーマットの再設計

最も重要な変更点は、バイナリエクスポートフォーマットが3つのセクションに分割されたことです。

*   **フェーズ1: プラットフォーム非依存オブジェクト (Platform-independent objects)**
    *   これは、パッケージのAPIを構成する主要な要素（エクスポートされた定数、型、変数、関数シグネチャなど）を含みます。
    *   `go/types`のようなプラットフォーム非依存のツールが型チェックを行うために必要な情報です。
    *   このセクションのオブジェクトは、`exportlist`に現れる順序でエクスポートされます。以前はオブジェクトをグループにソートしようとしていましたが、インライン化された関数本体が参照する追加のオブジェクトを考慮すると、この新しいアプローチの方がシンプルで柔軟性が高いと判断されました。わずかにコンパクトさは失われますが（オブジェクトあたり1バイト増）、複雑さを軽減します。

*   **フェーズ2: インライン化された関数本体によって参照されるオブジェクト (Objects pulled in for export via inlined function bodies)**
    *   このセクションは、インライン化された関数本体が依存する追加のオブジェクト（他の関数、型など）を含みます。
    *   これらのオブジェクトは、コンパイラがインライン化された関数本体を正しく解釈するために必要です。
    *   このデータはコンパイラ固有であり、インライン化の決定や関数本体の表現に依存します。

*   **フェーズ3: インライン化された関数本体 (Inlined function bodies)**
    *   このセクションには、実際にインライン化される関数のASTがバイナリ形式で格納されます。
    *   このフォーマットは完全にコンパイラ固有であり、将来的にエンコーディングをより密に（denser encoding）変更する余地が残されています。

### 2. エクスポート/インポートロジックの変更 (`bexport.go` と `bimport.go`)

*   **`exporter` および `importer` 構造体の導入:**
    *   エクスポートおよびインポート処理の状態を管理するために、それぞれ `exporter` と `importer` という新しい構造体が導入されました。これにより、コードのモジュール性が向上し、状態管理が明確になります。
    *   `exporter` には、エクスポートされるインライン関数本体のリストを保持する `inlined []*Func` フィールドが追加されました。
    *   `importer` には、インポートされたインライン関数本体のリストを保持する `inlined []*Node` フィールドが追加されました。

*   **オブジェクトのエクスポート/インポートの汎用化:**
    *   `exporter.obj(sym *Sym)` および `importer.obj(tag int)` メソッドが導入され、定数、型、変数、関数といった異なる種類のオブジェクトを統一的にエクスポート/インポートできるようになりました。これにより、コードの重複が削減され、拡張性が向上します。
    *   新しいタグ定数 (`constTag`, `typeTag`, `varTag`, `funcTag`, `endTag`) が導入され、バイナリストリーム内でオブジェクトの種類を識別するために使用されます。

*   **インライン関数本体のASTシリアライズ/デシリアライズ:**
    *   `exporter.stmtList()`, `exporter.expr()`, `exporter.stmt()` などのメソッドが追加され、GoのASTノードをバイナリ形式でシリアライズするロジックが実装されました。これは、`fmt.go` がテキスト形式でASTを出力するのと同様のアプローチですが、バイナリ形式で行われます。
    *   同様に、`importer.stmtList()`, `importer.expr()` などのメソッドが追加され、バイナリ形式のASTをデシリアライズしてGoコンパイラ内部のAST構造を再構築するロジックが実装されました。
    *   このASTのバイナリ表現は、コンパイラがインライン化された関数本体を再構築し、それに対して最適化を適用するために不可欠です。

*   **シンボルと名前の処理の改善:**
    *   `exporter.qualifiedName(sym *Sym)` や `exporter.fieldName(sym *Sym, t *Field)` など、シンボル名をエクスポートする際のロジックが調整されました。特に、インライン化された関数本体が他のパッケージのシンボルを参照する場合に、完全修飾名（qualified name）を正しく処理することが重要になります。
    *   パラメータ名についても、インライン化後のコンテキストで正しく解決できるように、`Vargen`（変数生成番号）を含む名前の処理が改善されました。

### 3. `go/internal/gcimporter` の調整

*   `go/internal/gcimporter` は、コンパイラ以外のツール（例: `go/types`）がGoのバイナリパッケージ情報を読み込むためのパッケージです。
*   エクスポートフォーマットの変更（特にフェーズ1のプラットフォーム非依存オブジェクトの構造変更）に伴い、このパッケージも新しいフォーマットを正しく解釈できるように調整されました。これにより、コンパイラとツールの間でパッケージ情報の互換性が維持されます。

### 4. `GO_GCFLAGS=-newexport` フラグ

*   このコミットは、`GO_GCFLAGS=-newexport` フラグを付けてビルドした場合に新しいエクスポートフォーマットが有効になることを示唆しています。これは、新しい機能がデフォルトで有効になる前に、テストと検証を行うためのメカニズムです。`builtin_test.go` の調整が必要であると述べられており、まだ完全にプロダクションレディではないことを示しています。

これらの変更により、Goコンパイラはより高度なクロスパッケージインライン化を実行できるようになり、Goプログラムの実行時パフォーマンスが向上します。

## コアとなるコードの解説

ここでは、`bexport.go` と `bimport.go` の主要な変更点に焦点を当てて解説します。

### `src/cmd/compile/internal/gc/bexport.go` の解説

*   **`exporter` 構造体:**
    ```go
    type exporter struct {
        out      *obj.Biobuf
        pkgIndex map[*Pkg]int
        typIndex map[*Type]int
        inlined  []*Func // インライン化された関数本体を保持するリスト
        // debugging support
        written int // bytes written
        indent  int // for p.trace
        trace   bool
    }
    ```
    `inlined` フィールドは、エクスポートされるインライン関数本体の `*Func` ポインタを収集するために使用されます。

*   **`Export` 関数:**
    この関数は、パッケージのエクスポート処理全体をオーケストレーションします。
    1.  **ヘッダーの書き込み:** フォーマットバージョン、パッケージ名、パス、コンパイラ固有のフラグなどを書き込みます。
    2.  **フェーズ1: プラットフォーム非依存オブジェクトのエクスポート:**
        ```go
        // First, export all exported (package-level) objects; i.e., all objects
        // in the current exportlist. These objects represent all information
        // required to import this package and type-check against it; i.e., this
        // is the platform-independent export data.
        // ...
        for _, n := range exportlist {
            // ...
            p.obj(sym) // obj メソッドを使ってオブジェクトをエクスポート
            objcount++
        }
        p.tag(endTag) // リストの終わりを示すタグ
        p.int(objcount) // 自己検証用のオブジェクト数
        ```
        `exportlist` に含まれるすべてのエクスポート済みオブジェクトを `p.obj(sym)` を呼び出してエクスポートします。このフェーズでは、インライン関数本体の依存関係によって `exportlist` に追加されたオブジェクトは無視されます（`range` ループの特性を利用）。
    3.  **フェーズ2: インライン関数本体の依存オブジェクトのエクスポート:**
        ```go
        // Phase 2: Export objects added to exportlist during phase 1.
        // Don't use range since exportlist may grow during this phase
        // and we want to export all remaining objects.
        for i := numglobals; exportInlined && i < len(exportlist); i++ {
            // ...
            p.obj(sym)
            objcount++
        }
        p.tag(endTag)
        p.int(objcount)
        ```
        `exportInlined` が有効な場合、フェーズ1の処理中に `exportlist` に追加されたオブジェクト（主にインライン関数本体が参照するオブジェクト）をエクスポートします。
    4.  **フェーズ3: インライン関数本体のエクスポート:**
        ```go
        // --- inlined function bodies ---
        p.int(len(p.inlined)) // インライン関数本体の数
        for _, f := range p.inlined {
            p.stmtList(f.Inl) // ASTをバイナリ形式で書き込む
        }
        ```
        `p.inlined` リストに収集された各関数本体のASTを `p.stmtList` メソッドを使ってバイナリ形式でエクスポートします。

*   **`obj(sym *Sym)` メソッド:**
    このメソッドは、`*Sym` が指すオブジェクトの種類（定数、型、変数、関数）に応じて適切なタグを書き込み、そのオブジェクトの具体的な情報をシリアライズします。例えば、関数であればそのシグネチャと、インライン化可能であればそのインデックスを書き込みます。

*   **`stmtList(list Nodes)`、`expr(n *Node)`、`stmt(n *Node)` メソッド:**
    これらのメソッドは、GoのASTノードをバイナリ形式で再帰的にシリアライズする中心的なロジックです。
    *   `op(Op)` メソッドでノードの操作コード（`OADD`, `OCALL` など）を書き込みます。
    *   ノードの種類に応じて、その子ノード、型情報、シンボル、値などを適切な順序で書き込みます。
    *   特に `expr` と `stmt` は、式と文のASTを処理するために、`fmt.go` のテキスト出力ロジックを参考にしつつ、バイナリ形式に変換しています。

### `src/cmd/compile/internal/gc/bimport.go` の解説

*   **`importer` 構造体:**
    ```go
    type importer struct {
        in       *bufio.Reader
        buf      []byte
        bufarray [64]byte
        pkgList  []*Pkg
        typList  []*Type
        inlined  []*Node // インポートされたインライン関数本体を保持するリスト
        // debugging support
        debugFormat bool
        read        int // bytes read
    }
    ```
    `inlined` フィールドは、インポートされたインライン関数本体の `*Node` ポインタを収集するために使用されます。

*   **`Import` 関数:**
    この関数は、エクスポートされたバイナリデータを読み込み、パッケージ情報を再構築します。
    1.  **ヘッダーの読み込み:** エクスポート時と同様に、ヘッダー情報を読み込みます。
    2.  **フェーズ1: プラットフォーム非依存オブジェクトのインポート:**
        ```go
        // Phase 1
        objcount := 0
        for {
            tag := p.tagOrIndex()
            if tag == endTag {
                break
            }
            p.obj(tag) // obj メソッドを使ってオブジェクトをインポート
            objcount++
        }
        // self-verification
        if count := p.int(); count != objcount { /* ... */ }
        ```
        `p.obj(tag)` を呼び出して、バイナリタグに基づいてオブジェクトをデシリアライズし、コンパイラ内部のデータ構造に再構築します。
    3.  **フェーズ2: インライン関数本体の依存オブジェクトのインポート:**
        フェーズ1と同様に、`p.obj(tag)` を使って追加のオブジェクトをインポートします。
    4.  **フェーズ3: インライン関数本体のインポート:**
        ```go
        bcount := p.int() // インライン関数本体の数
        // ...
        for _, f := range p.inlined {
            if f != nil {
                // function body not yet imported - read body and set it
                funchdr(f) // 関数ヘッダーを処理
                f.Func.Inl.Set(p.stmtList()) // ASTをバイナリ形式から読み込み、関数本体に設定
                funcbody(f) // 関数本体を処理
            } else {
                // function already imported - read body but discard declarations
                dclcontext = PDISCARD
                p.stmtList()
                dclcontext = PEXTERN
            }
        }
        ```
        `p.inlined` リストに収集された関数に対応するASTを `p.stmtList` メソッドを使ってバイナリ形式から読み込み、`f.Func.Inl.Set()` で関数本体に設定します。これにより、インライン化された関数本体がコンパイラで利用可能になります。

*   **`obj(tag int)` メソッド:**
    このメソッドは、読み込んだタグに基づいて、定数、型、変数、関数といった異なる種類のオブジェクトをデシリアライズし、対応するコンパイラ内部のデータ構造を構築します。特に、関数をインポートする際には、そのシグネチャを再構築し、インライン化可能であれば `p.inlined` リストに追加します。

*   **`stmtList() []*Node`、`expr() *Node`、`node() *Node` メソッド:**
    これらのメソッドは、バイナリ形式でエンコードされたASTノードを再帰的にデシリアライズし、Goコンパイラ内部の `*Node` 構造体を再構築する中心的なロジックです。
    *   `p.op()` で操作コードを読み込み、それに基づいて新しい `*Node` を作成します。
    *   ノードの種類に応じて、その子ノード、型情報、シンボル、値などを適切な順序で読み込みます。
    *   `ODCL` (宣言) ノードの処理では、変数のクラス（`PPARAM`, `PAUTO` など）を考慮して、正しく宣言を再構築します。

これらのコード変更により、Goコンパイラはインライン化された関数本体をパッケージ間で共有できるようになり、より高度な最適化が可能になります。

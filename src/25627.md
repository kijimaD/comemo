# [インデックス 25627] ファイルの概要

このコミットは、Goランタイムにおけるプロファイリングシグナル（SIGPROF）の処理に関するバグ修正です。具体的には、ゴルーチンのスタックがコピー中である（つまり、不安定な状態にある）場合にSIGPROFがそのスタックをトレースしようとするとパニックを引き起こす可能性があった問題を解決します。

## コミット

commit bbd1a1c706659ae489b174e2a4a707bbc626d5af
Author: Austin Clements <austin@google.com>
Date:   Wed Nov 11 15:34:54 2015 -0500

    runtime: make SIGPROF skip stacks that are being copied
    
    sigprof tracebacks the stack across systemstack switches to make
    profile tracebacks more complete. However, it does this even if the
    user stack is currently being copied, which means it may be in an
    inconsistent state that will cause the traceback to panic.
    
    One specific way this can happen is during stack shrinking. Some
    goroutine blocks for STW, then enters gchelper, which then assists
    with root marking. If that root marking happens to pick the original
    goroutine and its stack needs to be shrunk, it will begin to copy that
    stack. During this copy, the stack is generally inconsistent and, in
    particular, the actual locations of the stack barriers and their
    recorded locations are temporarily out of sync. If a SIGPROF happens
    during this inconsistency, it will walk the stack all the way back to
    the blocked goroutine and panic when it fails to unwind the stack
    barriers.
    
    Fix this by disallowing jumping to the user stack during SIGPROF if
    that user stack is in the process of being copied.
    
    Fixes #12932.

## 元コミット内容

Goランタイムにおいて、SIGPROFシグナルがスタックコピー中のゴルーチンをトレースする際にパニックが発生する問題を修正します。SIGPROFはプロファイルトレースをより完全にするために`systemstack`をまたいでスタックをトレースしますが、ユーザースタックがコピー中である場合、そのスタックは一貫性のない状態にあり、トレースバックがパニックを引き起こす可能性があります。

この問題は、特にスタック縮小中に発生する可能性があります。あるゴルーチンがSTW（Stop The World）のためにブロックされ、その後`gchelper`に入り、ルートマーキングを支援します。もしそのルートマーキングが元のゴルーチンを選択し、そのスタックを縮小する必要がある場合、スタックのコピーが開始されます。このコピー中、スタックは一般的に一貫性がなく、特にスタックバリアの実際の場所と記録された場所が一時的に同期していません。この不整合中にSIGPROFが発生すると、ブロックされたゴルーチンまでスタックを遡り、スタックバリアのアンワインドに失敗してパニックを引き起こします。

この修正は、ユーザースタックがコピー中である場合、SIGPROF中にユーザースタックへのジャンプを許可しないことで問題を解決します。

Fixes #12932.

## 変更の背景

Goランタイムは、ゴルーチンのスタックを動的に拡張・縮小する機能を持っています。これにより、メモリ使用量を効率的に管理できます。しかし、スタックのコピーや移動が行われている最中は、そのスタックは一時的に一貫性のない状態になります。

CPUプロファイリングのためにGoランタイムが使用する`SIGPROF`シグナルは、プログラムの実行中に定期的に発生し、現在の実行スタックをサンプリングして、どの関数がCPU時間を消費しているかを特定します。このスタックトレースの取得は、`gentraceback`という内部関数によって行われます。

問題は、`SIGPROF`がスタックコピー中のゴルーチンをサンプリングした場合に発生しました。`gentraceback`は、`systemstack`（ランタイム内部処理用のスタック）からユーザースタックへジャンプしてトレースを継続する機能を持っています。しかし、スタックコピー中のユーザースタックは、スタックバリア（スタックの境界を示す内部的なマーク）の位置が一時的にずれているなど、内部状態が不安定です。この状態で`gentraceback`がユーザースタックにジャンプしようとすると、不正なメモリアクセスや論理エラーが発生し、ランタイムパニックを引き起こす可能性がありました。

特に、ガベージコレクション（GC）のSTWフェーズ中にスタック縮小が行われるシナリオでこの問題が顕在化しました。GCがルートマーキングを行う際に、スタック縮小が必要なゴルーチンが選ばれると、そのスタックがコピーされます。このコピー中に`SIGPROF`が割り込むと、パニックが発生する可能性があったのです。

このコミットは、このような特定の状況下でのランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

### Goランタイムにおけるスタック管理

Goのゴルーチンは、可変サイズのスタックを持っています。これは、プログラムの実行中に必要に応じてスタックが自動的に拡張または縮小されることを意味します。スタックの拡張や縮小は、新しいスタック領域を確保し、古いスタックの内容を新しい領域にコピーすることで行われます。このコピー処理中は、古いスタックと新しいスタックの両方が存在し、一時的に一貫性のない状態になることがあります。

### Goroutineの状態遷移 (`_Gcopystack`など)

Goランタイムは、ゴルーチンの内部状態を管理するために様々なステータスを使用します。`_Gcopystack`は、ゴルーチンのスタックが現在コピー中であることを示す内部状態です。この状態のゴルーチンは、ユーザーコードを実行しておらず、ランタイムがスタックの移動を管理しています。

### `SIGPROF`シグナルとプロファイリング

`SIGPROF`は、Unix系システムでプロファイリングのために使用されるシグナルです。Goランタイムは、CPUプロファイリングが有効になっている場合、このシグナルを定期的に受け取ります。`SIGPROF`ハンドラは、シグナル発生時のプログラムカウンタ（PC）とスタックポインタ（SP）を記録し、`gentraceback`関数を呼び出してスタックトレースを収集します。これにより、どのコードパスがCPU時間を消費しているかの統計情報を得ることができます。

### `systemstack`とユーザースタック

Goのゴルーチンは、通常のユーザーコードを実行するための「ユーザースタック」と、ランタイムの内部処理（スケジューリング、GC、シグナルハンドリングなど）を実行するための「`systemstack`」を持っています。`systemstack`は、ユーザーコードの実行が中断され、ランタイムが制御を引き継ぐ際に使用されます。`SIGPROF`ハンドラは`systemstack`上で実行されますが、プロファイルのためにはユーザーコードのスタックトレースも必要となるため、`systemstack`からユーザースタックへの切り替え（ジャンプ）が発生することがあります。

### GoのGCにおけるSTW、gchelper、ルートマーキング

*   **STW (Stop The World)**: Goのガベージコレクション（GC）は、ほとんどが並行して実行されますが、一部の重要なフェーズでは、すべてのゴルーチンの実行を一時的に停止させる必要があります。これがSTWフェーズです。STWは、GCの正確性を保証するために、メモリの状態が変化しないようにするために行われます。
*   **gchelper**: GCのSTWフェーズ中、またはGCの並行フェーズ中に、一部のゴルーチンがGCの作業を「手伝う」ことがあります。これは`gchelper`と呼ばれる内部的なメカニズムを通じて行われ、GCの完了を早めるのに役立ちます。
*   **ルートマーキング**: トレース型GCの最初のステップは、プログラムが直接アクセスできるオブジェクト（「ルート」）を特定することです。これには、グローバル変数、現在実行中のゴルーチンのスタック上の変数などが含まれます。これらのルートから到達可能なすべてのオブジェクトが「生きている」とマークされ、それ以外のオブジェクトはガベージとして回収されます。

### `gentraceback`関数の役割とフラグ (`_TraceTrap`, `_TraceJumpStack`)

`gentraceback`は、Goランタイムの内部関数で、スタックトレースを生成する中心的な役割を担います。この関数は、トレースの挙動を制御するための様々なフラグを受け取ります。

*   `_TraceTrap` (値: 2): トレースバックの開始PCとSPがトラップ（例外やシグナルなど）によるものであることを示します。
*   `_TraceJumpStack` (値: 4): `systemstack`上でトレースバックが開始された場合、そこから関連するユーザースタックにジャンプしてトレースを継続すべきであることを示します。このフラグが設定されていると、`gentraceback`は`systemstack`からユーザースタックへの切り替えを試みます。

## 技術的詳細

このコミットが修正しようとしている問題は、`SIGPROF`シグナルが`systemstack`上で処理されている間に、`gentraceback`関数が`_TraceJumpStack`フラグを使用して、現在スタックコピー中であるゴルーチンのユーザースタックにジャンプしようとすることに起因します。

スタックコピー中、ゴルーチンのスタックは`_Gcopystack`状態にあります。この状態では、スタックの内部構造、特にスタックバリア（スタックの境界や成長方向を管理するための内部的なマーク）の位置が一時的に不整合な状態になります。例えば、古いスタックと新しいスタックの間でバリア情報がまだ完全に同期されていない可能性があります。

`gentraceback`が`_TraceJumpStack`フラグに基づいて、この不整合なユーザースタックにジャンプしてトレースを試みると、スタックバリアのアンワインド（スタックフレームを遡る処理）に失敗します。これは、`gentraceback`が期待するスタック構造と実際のスタック構造が異なるためです。結果として、ランタイムはパニックを起こし、プログラムがクラッシュします。

この修正は、`sigprof`関数内で、トレースバックを行う前に現在のゴルーチン（`gp.m.curg`）が`_Gcopystack`状態であるかどうかをチェックします。もし`_Gcopystack`状態であれば、`_TraceJumpStack`フラグをクリアします。これにより、`gentraceback`はユーザースタックへのジャンプを試みなくなり、`systemstack`上でのトレースバックのみを行います。

このアプローチにより、スタックコピー中の不安定なユーザースタックへのアクセスが回避され、ランタイムパニックが防止されます。プロファイルトレースの完全性は若干損なわれる可能性がありますが（ユーザースタックのトレースがスキップされるため）、ランタイムの安定性が優先されます。

## コアとなるコードの解説

変更の中心は、`sigprof`関数内で`gentraceback`を呼び出す際のフラグの計算方法です。

1.  **既存のフラグ設定**: 変更前は、`gentraceback`は常に`_TraceTrap|_TraceJumpStack`というフラグの組み合わせで呼び出されていました。
    *   `_TraceTrap`: シグナルによるトラップからトレースバックを開始することを示します。
    *   `_TraceJumpStack`: `systemstack`からユーザースタックへジャンプしてトレースを継続することを示します。

2.  **新しいフラグ変数 `flags` の導入**: 変更後、まず`flags := uint(_TraceTrap | _TraceJumpStack)`としてデフォルトのフラグを設定します。

3.  **`_Gcopystack`状態のチェック**:
    ```go
    if gp.m.curg != nil && readgstatus(gp.m.curg) == _Gcopystack {
    ```
    この行では、現在のゴルーチン（`gp.m.curg`）が存在し、かつその状態が`_Gcopystack`（スタックコピー中）であるかどうかをチェックしています。`readgstatus`はゴルーチンの状態を読み取るランタイム内部関数です。

4.  **`_TraceJumpStack`フラグのクリア**:
    ```go
    	// We can traceback the system stack, but
    	// don't jump to the potentially inconsistent
    	// user stack.
    	flags &^= _TraceJumpStack
    ```
    もしゴルーチンが`_Gcopystack`状態であれば、`flags &^= _TraceJumpStack`というビット演算によって`_TraceJumpStack`フラグがクリアされます。`&^=`演算子は、左辺から右辺のビットをクリアする（AND NOT）操作です。これにより、`flags`から`_TraceJumpStack`のビットが取り除かれ、`gentraceback`がユーザースタックへのジャンプを試みなくなります。

この変更により、スタックコピー中の不安定なユーザースタックへのアクセスが意図的に回避され、ランタイムパニックが防止されます。`SIGPROF`は`systemstack`上でのトレースバックは引き続き行いますが、ユーザースタックのトレースはスキップされることになります。

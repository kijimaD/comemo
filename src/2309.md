このコミットは、Goコンパイラの`src/cmd/gc/go.h`と`src/cmd/gc/walk.c`ファイルに影響を与えています。主な変更点は以下の通りです。

*   `src/cmd/gc/go.h`: `reorder2`関数の宣言が削除されました。
*   `src/cmd/gc/walk.c`: `reorder2`関数の実装が完全に削除され、`ascompatet`関数内の`reorder2`への呼び出しが削除されました。代わりに、`ascompatet`関数内で関数呼び出しを伴う代入をより堅牢に処理するための新しいロジックが導入され、`fncall`というヘルパー関数が追加されました。

## 変更の背景

このコミットは、Goコンパイラにおける「bug 150」を修正するために行われました。コミットメッセージ自体は簡潔ですが、コードの変更内容から、多値代入や型変換が絡む複雑な式において、関数呼び出しの評価順序が正しく処理されないという問題があったと推測されます。

特に、以前の`reorder2`関数は、代入に含まれる関数呼び出しの評価順序を調整しようとしていましたが、これが不十分であったか、あるいは特定のシナリオで誤動作を引き起こしていた可能性があります。関数呼び出しは副作用を持つことが多く、その評価順序が結果に大きく影響するため、コンパイラはこれを厳密に制御する必要があります。このバグは、関数呼び出しの結果が意図せず上書きされたり、不正な状態になったりするような、予測不能な動作を引き起こしていたと考えられます。

この変更は、コンパイラが代入式を処理する際の堅牢性を高め、特に副作用を持つ式（関数呼び出しなど）の評価が、他の代入操作と競合しないようにするためのものです。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下の概念を把握しておく必要があります。

*   **Goコンパイラ (gc)**: Go言語の公式コンパイラであり、このコミットが変更を加えているのはそのソースコードの一部です。`gc`は、Goソースコードを解析し、最適化を行い、最終的に実行可能なバイナリを生成します。
*   **中間表現 (Node)**: コンパイラは、ソースコードを直接操作するのではなく、それを抽象構文木（AST: Abstract Syntax Tree）などの内部的なデータ構造に変換して処理します。Goコンパイラでは、これらのノードがプログラムの各要素（変数、式、関数呼び出しなど）を表す中間表現として機能します。
*   **Ullman数 (Ullman Number)**: コンパイラ最適化の分野で用いられる概念で、式の評価順序を決定し、レジスタ割り当てを最適化するために使用されます。Ullman数が高い式は、より多くのレジスタや一時変数が必要になる可能性があり、また副作用を持つ可能性が高いと見なされます。`UINF`（Ullman Infinity）は、関数呼び出しのように副作用があり、評価順序が厳密に重要な式に割り当てられる非常に大きなUllman数を指すことが一般的です。
*   **多値代入 (Multiple Assignment)**: Go言語の特徴的な機能の一つで、`a, b = someFunction()`のように、複数の変数を一度に代入できる構文です。関数の複数の戻り値を簡単に受け取ることができます。
*   **関数呼び出しの評価順序 (Function Call Evaluation Order)**: プログラミング言語において、関数呼び出しの引数や、代入の右辺にある式の評価が、左辺の評価に対してどのような順序で行われるかという規則です。特に副作用を持つ関数呼び出しの場合、この順序がプログラムの正確性に直結するため、コンパイラはこれを厳密に管理する必要があります。
*   **型変換 (Type Conversion)**: あるデータ型から別のデータ型へ値を変換する操作です。Goコンパイラは、代入時に必要に応じて暗黙的または明示的な型変換を処理します。

## 技術的詳細

このコミットの核心は、Goコンパイラの`src/cmd/gc/walk.c`ファイル内の`ascompatet`関数の変更にあります。このファイルは、コンパイラの「ウォーカー」フェーズの一部であり、ASTを走査しながら型チェック、最適化、そして最終的なコード生成のための準備を行います。`ascompatet`関数は、特に代入文の右辺と左辺の型互換性を処理し、必要に応じて型変換や式の再配置を行う役割を担っていました。

以前の実装では、`ascompatet`は`reorder2`関数を呼び出して、代入に含まれる関数呼び出しの評価順序を調整しようとしていました。しかし、このアプローチは、特に多値代入や複雑な型変換が絡む場合に、関数呼び出しが意図しないタイミングで評価され、その結果が上書きされたり、不正な状態になったりする問題を引き起こしていました。`reorder2`は、式に含まれる関数呼び出しの数をカウントし、多すぎる場合にエラーを出すようなロジックでしたが、根本的な評価順序の問題を解決できていなかったのです。

新しいアプローチでは、以下の点が改善されました。

1.  **`reorder2`の削除**: 問題の原因となっていた`reorder2`関数が完全に削除されました。
2.  **`fncall`関数の導入**: 新たに`fncall`というヘルパー関数が導入されました。この関数は、与えられた左辺式（`l`）と右辺の型（`rt`）の組み合わせが、関数呼び出しを伴う評価を必要とするかどうかを判断します。特に、`l->ullman >= UINF`のチェックは、`l`が関数呼び出しを含むか、または副作用を持つ複雑な式であることを示唆しており、このような場合に`fncall`は真を返します。
3.  **`ascompatet`内の新しいロジック**:
    *   `fncall(l, r->type)`が真を返した場合、コンパイラは一時変数（`tmp`）を導入します。これは、`l`の評価が関数呼び出しを伴うため、その副作用が他の代入に影響を与えないように、`l`の値を一時的に保持するためです。
    *   `OAS`（代入）ノードが作成され、`l`の値を`tmp`に代入する操作が表現されます。
    *   これらの「遅延された」代入は、`mm`という新しいリストに収集されます。
    *   `ascompatet`のループの最後に、`mm`リストに格納された代入が逆順で処理され、最終的な代入リスト（`nn`）に追加されます。これにより、関数呼び出しの評価が、代入の他の部分が完了した後に、正しい順序で行われることが保証されます。

この変更により、Goコンパイラは、多値代入や型変換が絡む複雑な式において、関数呼び出しの副作用をより堅牢に処理できるようになり、コンパイラの安定性と生成されるコードの正確性が向上しました。

## コアとなるコードの解説

このコミットの主要な変更は、Goコンパイラが代入式、特に多値代入や型変換を伴う代入式を処理する方法の根本的な改善にあります。

1.  **`reorder2`関数の削除**:
    *   `reorder2`は、以前は`ascompatet`関数内で呼び出され、代入の左辺に含まれる式（特に関数呼び出し）の評価順序を管理しようとしていました。しかし、そのロジックは不完全であり、関数呼び出しが多すぎる場合にエラーを出すだけで、副作用を持つ式の評価順序の問題を適切に解決できていませんでした。
    *   この関数の削除は、そのアプローチが不適切であったことを示しており、より堅牢なメカニズムが必要とされたことを意味します。

2.  **`fncall`関数の導入**:
    *   新しく導入された`fncall`関数は、特定の左辺式`l`と右辺の型`rt`の組み合わせが、関数呼び出しを伴う評価を必要とするかどうかを判断します。
    *   `l->ullman >= UINF`という条件は重要です。これは、左辺式`l`が関数呼び出しを含むか、または副作用を持つ非常に複雑な式であることを示します。このような式は、評価順序が厳密に制御される必要があります。
    *   `eqtype(l->type, rt)`は、左辺と右辺の型が同じであれば関数呼び出しは不要であることを示します。それ以外の場合は、型変換が必要であり、それが関数呼び出しを伴う可能性があるため、`fncall`は真を返します。

3.  **`ascompatet`内の新しい評価順序ロジック**:
    *   `ascompatet`関数は、代入の左辺と右辺のペアを順に処理します。
    *   `if(fncall(l, r->type))`のブロックが新しい核心部分です。`fncall`が真を返した場合、つまり左辺の評価が関数呼び出しを伴う可能性がある場合、コンパイラは以下の処理を行います。
        *   `tmp = nod(OXXX, N, N); tempname(tmp, r->type);`: 一時変数`tmp`が作成されます。この一時変数は、関数呼び出しの副作用が他の代入に影響を与えないように、左辺の値を一時的に保持するために使用されます。
        *   `a = nod(OAS, l, tmp); a = convas(a);`: 元の左辺`l`の値をこの一時変数`tmp`に代入する`OAS`（代入）ノードが作成されます。
        *   `mm = list(mm, a);`: この一時変数への代入ノード`a`は、`mm`という新しいリストに追加されます。この`mm`リストは、後で処理されるべき「遅延された」代入を収集します。
        *   `l = tmp;`: 以降の処理では、元の左辺`l`の代わりに、この一時変数`tmp`が使用されます。これにより、関数呼び出しの評価が完了するまで、左辺の評価が事実上遅延されます。
    *   ループの終了条件の直前で、`if(mm != N)`のブロックが追加されました。
        *   `mm = rev(mm);`: `mm`リストは逆順にされます。これは、一時変数への代入が、元の代入の順序とは逆の順序で実行される必要があるためです。
        *   `for(l=listfirst(&savel, &mm); l!=N; l=listnext(&savel)) nn = list(nn, l);`: 逆順になった`mm`リストの各代入ノードが、最終的な代入リスト`nn`に追加されます。これにより、関数呼び出しの評価が、代入の他の部分が完了した後に、正しい順序で行われることが保証されます。

この一連の変更により、Goコンパイラは、多値代入や型変換が絡む複雑な式において、関数呼び出しの副作用をより堅牢に処理できるようになりました。これにより、コンパイラのバグが修正され、生成されるコードの正確性と信頼性が向上しました。

crypto/tls: add support for session ticket key rotation

This change adds a new method to tls.Config, SetSessionTicketKeys, that
changes the key used to encrypt session tickets while the server is
running. Additional keys may be provided that will be used to maintain
continuity while rotating keys. If a ticket encrypted with an old key is
provided by the client, the server will resume the session and provide
the client with a ticket encrypted using the new key.

## 変更の背景

この変更の背景には、TLSセッションチケットのセキュリティと運用の課題がありました。TLSセッションチケットは、クライアントとサーバー間のTLSハンドシェイクのオーバーヘッドを削減し、接続確立を高速化するために使用されます。サーバーはセッション状態を暗号化してチケットとしてクライアントに発行し、クライアントは次回の接続時にそのチケットを提示することで、完全なハンドシェイクを省略してセッションを再開できます。

しかし、従来のGoの `crypto/tls` 実装では、セッションチケットの暗号化に単一のキーしかサポートしていませんでした。これは、セキュリティ上の懸念を引き起こします。暗号化キーは定期的にローテーションされるべきであり、もしキーが漏洩した場合、そのキーで暗号化されたすべてのセッションチケットが危険に晒される可能性があります。単一キーのシステムでは、キーをローテーションする際に、古いキーで暗号化された既存のセッションチケットを処理できなくなるという問題が発生します。これにより、セッションの継続性が損なわれ、ユーザーエクスペリエンスに悪影響を与える可能性がありました。

この問題は、GoのIssue #9994で提起され、サーバーが稼働中にセッションチケットキーを安全にローテーションできるメカニズムの必要性が認識されました。このコミットは、この課題を解決し、TLSサーバーのセキュリティと可用性を向上させることを目的としています。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上での通信のセキュリティを確保するための暗号化プロトコルです。ウェブブラウジング（HTTPS）、電子メール、VoIPなど、様々なアプリケーションで利用されています。TLSは、主に以下の機能を提供します。

1.  **認証**: 通信相手が正当なサーバー（またはクライアント）であることを確認します。通常、サーバー証明書によって行われます。
2.  **機密性**: 通信内容が第三者に傍受されても解読されないように暗号化します。
3.  **完全性**: 通信内容が途中で改ざんされていないことを保証します。

### TLSハンドシェイク

TLS接続を確立する際、クライアントとサーバーは「ハンドシェイク」と呼ばれる一連のメッセージ交換を行います。このハンドシェイクの目的は、安全な通信のための共有秘密鍵を確立し、互いを認証することです。ハンドシェイクには、証明書の交換、鍵交換アルゴリズムのネゴシエーション、暗号スイートの選択などが含まれ、比較的多くの計算リソースとネットワークラウンドトリップを必要とします。

### TLSセッションとセッション再開 (Session Resumption)

TLSセッションは、クライアントとサーバー間で確立された安全な通信の状態を指します。これには、共有秘密鍵、選択された暗号スイート、圧縮方法などが含まれます。

セッション再開は、クライアントが以前に確立したセッションの情報を利用して、新しいTLSハンドシェイクを短縮するメカニズムです。これにより、特に短期間に多数の接続を行うアプリケーション（例：ウェブブラウザが同じサイトの複数のリソースをロードする場合）において、接続確立のレイテンシを削減し、サーバーの負荷を軽減できます。

セッション再開には主に2つの方法があります。

1.  **セッションID (Session ID)**: サーバーがセッションIDを生成し、クライアントに送信します。クライアントは次回の接続時にこのIDを提示し、サーバーは内部キャッシュに保存されたセッション状態を検索して再開します。
2.  **セッションチケット (Session Ticket)**: サーバーがセッション状態全体を暗号化し、「セッションチケット」としてクライアントに送信します。クライアントは次回の接続時にこのチケットを提示し、サーバーはチケットを復号してセッション状態を再構築します。セッションID方式と異なり、サーバー側でセッション状態を保持する必要がないため、スケーラビリティに優れています。

### セッションチケットの暗号化とキーローテーション

セッションチケットは、サーバーが発行する際に特定の暗号化キー（セッションチケットキー）で暗号化されます。クライアントがチケットを提示すると、サーバーは同じキーを使ってチケットを復号し、セッションを再開します。

**キーローテーション**とは、暗号化キーを定期的に変更するセキュリティプラクティスです。これは、キーが漏洩した場合のリスクを軽減するために重要です。キーが長期間使用されると、攻撃者がそのキーを解読する機会が増加します。定期的なローテーションにより、たとえキーが漏洩しても、そのキーで暗号化されたデータが危険に晒される期間を限定できます。

セッションチケットキーのローテーションを適切に行うには、以下の課題を解決する必要があります。

*   **新旧キーの共存**: キーをローテーションする際、新しいキーで新しいチケットを発行し始める一方で、古いキーで暗号化された既存のチケットも引き続き復号できる必要があります。これにより、クライアントが古いチケットを提示してもセッションを中断することなく再開できます。
*   **シームレスな移行**: サーバーのダウンタイムなしにキーを更新できる必要があります。

## 技術的詳細

このコミットは、Goの `crypto/tls` パッケージに `tls.Config` 構造体の新しいメソッド `SetSessionTicketKeys` を導入することで、TLSセッションチケットのキーローテーションを可能にします。

### `SetSessionTicketKeys` メソッド

`SetSessionTicketKeys` は、サーバーが実行中にセッションチケットキーを更新するための主要なインターフェースです。このメソッドは、`[][32]byte` 型のスライスを引数として取ります。このスライス内のキーは、以下のルールで利用されます。

1.  **最初のキー**: スライス内の最初のキー (`keys[0]`) は、**新しく発行されるセッションチケットの暗号化**にのみ使用されます。
2.  **すべてのキー**: スライス内の**すべてのキー**は、クライアントから提示されたセッションチケットの**復号**に試行されます。これにより、キーローテーション中に古いキーで暗号化されたチケットも問題なく処理できます。

この設計により、サーバーは新しいキーを導入しつつ、古いキーで発行されたチケットの有効期限が切れるまで、それらをサポートし続けることができます。クライアントが古いキーで暗号化されたチケットを提示してセッションを再開した場合、サーバーはセッションを再開した後、**新しいキーで暗号化された新しいセッションチケットをクライアントに発行**します。これにより、クライアントは次回以降、最新のキーで暗号化されたチケットを使用するようになります。

`SetSessionTicketKeys` は、サーバーが稼働中に呼び出すことが安全であり、キーの動的な更新を可能にします。ただし、この関数を使用すると、`crypto/tls` パッケージが提供する自動的なセッションチケットキーローテーションメカニズム（もし存在する場合）は無効になります。

### `ticketKey` 構造体とキーの派生

この変更では、セッションチケットキーの内部表現として `ticketKey` 構造体が導入されました。

```go
type ticketKey struct {
	keyName [ticketKeyNameLen]byte // チケットを識別するための不透明なバイト列
	aesKey  [16]byte               // AES暗号化キー
	hmacKey [16]byte               // HMAC認証キー
}
```

`ticketKeyNameLen` は16バイトで、`ticketKey` の `keyName` フィールドの長さを定義します。この `keyName` は、暗号化されたセッションチケットの先頭に平文で付加され、サーバーがチケットを復号する際にどのキーが使用されたかを識別するために利用されます。

`ticketKeyFromBytes` 関数は、外部から提供される32バイトのキー（`[32]byte`）を `ticketKey` 構造体に変換します。この変換プロセスでは、SHA512ハッシュ関数が使用されます。

```go
func ticketKeyFromBytes(b [32]byte) (key ticketKey) {
	hashed := sha512.Sum512(b[:])
	copy(key.keyName[:], hashed[:ticketKeyNameLen])
	copy(key.aesKey[:], hashed[ticketKeyNameLen:ticketKeyNameLen+16])
	copy(key.hmacKey[:], hashed[ticketKeyNameLen+16:ticketKeyNameLen+32])
	return key
}
```

提供された32バイトのキーはSHA512でハッシュされ、そのハッシュ値から `keyName` (16バイト)、`aesKey` (16バイト)、`hmacKey` (16バイト) が派生されます。これにより、単一のシードから必要なすべてのキーマテリアルが生成されます。

### セッションチケットの暗号化と復号の変更

`encryptTicket` 関数と `decryptTicket` 関数は、新しいキーローテーションの仕組みに対応するために変更されました。

*   **`encryptTicket`**: 新しくチケットを暗号化する際、`tls.Config` の `sessionTicketKeys` スライスから最初のキー (`c.config.ticketKeys()[0]`) を取得し、その `keyName` をチケットの先頭に付加します。そして、そのキーの `aesKey` と `hmacKey` を使用してチケットを暗号化およびMAC（Message Authentication Code）計算します。
*   **`decryptTicket`**: チケットを復号する際、まずチケットの先頭から `ticketKeyNameLen` バイトの `keyName` を読み取ります。次に、`tls.Config` の `sessionTicketKeys` スライス内のすべてのキーを順番に試行し、チケットの `keyName` と一致するキーを探します。一致するキーが見つかった場合、そのキーの `aesKey` と `hmacKey` を使用してチケットを復号し、MACを検証します。もし一致するキーが見つからない場合、復号は失敗します。

また、`sessionState` 構造体に `usedOldKey` フィールドが追加されました。これは、復号されたチケットが古いキー（`sessionTicketKeys` スライス内の最初のキーではないキー）で暗号化されていた場合に `true` に設定されます。サーバーはこれを利用して、古いキーで再開されたセッションに対して新しいキーで暗号化されたチケットを再発行するロジックを実装します。

## コアとなるコードの解説

### `src/crypto/tls/common.go` の変更

`tls.Config` 構造体は、TLSサーバーおよびクライアントの設定を保持します。このコミットでは、セッションチケットキーの管理のために以下のフィールドが追加されました。

```go
type Config struct {
	// ... 既存のフィールド ...

	// mutex protects sessionTicketKeys
	mutex sync.RWMutex
	// sessionTicketKeys contains zero or more ticket keys. If the length
	// is zero, SessionTicketsDisabled must be true. The first key is used
	// for new tickets and any subsequent keys can be used to decrypt old
	// tickets.
	sessionTicketKeys []ticketKey
}
```

`sessionTicketKeys` は `ticketKey` 型のスライスであり、サーバーが現在使用しているすべてのセッションチケットキーを保持します。`mutex` は、このスライスへの並行アクセスを保護するための読み書きミューテックスです。

`ticketKey` 構造体は、セッションチケットの暗号化と認証に必要なキーマテリアルをカプセル化します。

```go
// ticketKeyNameLen is the number of bytes of identifier that is prepended to
// an encrypted session ticket in order to identify the key used to encrypt it.
const ticketKeyNameLen = 16

// ticketKey is the internal representation of a session ticket key.
type ticketKey struct {
	// keyName is an opaque byte string that serves to identify the session
	// ticket key. It's exposed as plaintext in every session ticket.
	keyName [ticketKeyNameLen]byte
	aesKey  [16]byte
	hmacKey [16]byte
}
```

`ticketKeyFromBytes` 関数は、外部から提供される32バイトのキーバイト列から、`ticketKey` 構造体を生成します。この関数は、SHA512ハッシュを使用して、キーバイト列から `keyName`、`aesKey`、`hmacKey` を派生させます。これにより、単一のシードから複数の目的（識別、暗号化、認証）のためのキーが安全に生成されます。

`SetSessionTicketKeys` メソッドは、`tls.Config` の `sessionTicketKeys` を更新します。

```go
func (c *Config) SetSessionTicketKeys(keys [][32]byte) {
	if len(keys) == 0 {
		panic("tls: keys must have at least one key")
	}

	newKeys := make([]ticketKey, len(keys))
	for i, bytes := range keys {
		newKeys[i] = ticketKeyFromBytes(bytes)
	}

	c.mutex.Lock()
	c.sessionTicketKeys = newKeys
	c.mutex.Unlock()
}
```

このメソッドは、提供された32バイトのキーのスライスを `ticketKey` のスライスに変換し、`tls.Config` の `sessionTicketKeys` をアトミックに置き換えます。これにより、サーバーは実行中にキーを安全に更新できます。

### `src/crypto/tls/ticket.go` の変更

`sessionState` 構造体は、セッションの状態を保持します。このコミットでは、セッションが古いキーで復号されたかどうかを示す `usedOldKey` フィールドが追加されました。

```go
type sessionState struct {
	// ... 既存のフィールド ...
	// usedOldKey is true if the ticket from which this session came from
	// was encrypted with an older key and thus should be refreshed.
	usedOldKey bool
}
```

`encryptTicket` 関数は、セッション状態をセッションチケットとして暗号化します。変更後、この関数は `tls.Config` の `sessionTicketKeys` スライスから最初のキー（現在のプライマリキー）を取得し、その `keyName` を暗号化されたチケットの先頭に含めるようになりました。

```go
func (c *Conn) encryptTicket(state *sessionState) ([]byte, error) {
	serialized := state.marshal()
	// encrypted のサイズに ticketKeyNameLen を追加
	encrypted := make([]byte, ticketKeyNameLen+aes.BlockSize+len(serialized)+sha256.Size)
	keyName := encrypted[:ticketKeyNameLen]
	iv := encrypted[ticketKeyNameLen : ticketKeyNameLen+aes.BlockSize]
	macBytes := encrypted[len(encrypted)-sha256.Size:]

	if _, err := io.ReadFull(c.config.rand(), iv); err != nil {
		return nil, err
	}
	key := c.config.ticketKeys()[0] // 最初のキーを使用
	copy(keyName, key.keyName[:])   // キー名をチケットにコピー
	block, err := aes.NewCipher(key.aesKey[:])
	if err != nil {
		return nil, errors.New("tls: failed to create cipher while encrypting ticket: " + err.Error())
	}
	// 暗号化のオフセットを調整
	cipher.NewCTR(block, iv).XORKeyStream(encrypted[ticketKeyNameLen+aes.BlockSize:], serialized)

	mac := hmac.New(sha256.New, key.hmacKey[:])
	mac.Write(encrypted[:len(encrypted)-sha256.Size])
	mac.Sum(macBytes[:0])

	return encrypted, nil
}
```

`decryptTicket` 関数は、クライアントから提示されたセッションチケットを復号します。この関数は、チケットの先頭からキー名を抽出し、`tls.Config` の `sessionTicketKeys` スライス内のすべてのキーを順番に試行して、一致するキーを見つけます。

```go
func (c *Conn) decryptTicket(encrypted []byte) (*sessionState, bool) {
	if c.config.SessionTicketsDisabled ||
		len(encrypted) < ticketKeyNameLen+aes.BlockSize+sha256.Size { // サイズチェックを更新
		return nil, false
	}

	keyName := encrypted[:ticketKeyNameLen] // キー名を抽出
	iv := encrypted[ticketKeyNameLen : ticketKeyNameLen+aes.BlockSize]
	macBytes := encrypted[len(encrypted)-sha256.Size:]

	keys := c.config.ticketKeys()
	keyIndex := -1
	for i, candidateKey := range keys {
		if bytes.Equal(keyName, candidateKey.keyName[:]) { // キー名で一致するキーを検索
			keyIndex = i
			break
		}
	}

	if keyIndex == -1 { // 一致するキーが見つからない場合
		return nil, false
	}
	key := &keys[keyIndex] // 見つかったキーを使用

	mac := hmac.New(sha256.New, key.hmacKey[:])
	mac.Write(encrypted[:len(encrypted)-sha256.Size])
	expected := mac.Sum(nil)

	if !hmac.Equal(macBytes, expected) {
		return nil, false
	}

	block, err := aes.NewCipher(key.aesKey[:])
	if err != nil {
		return nil, false
	}
	// 復号のオフセットを調整
	ciphertext := encrypted[ticketKeyNameLen+aes.BlockSize : len(encrypted)-sha256.Size]
	plaintext := ciphertext
	cipher.NewCTR(block, iv).XORKeyStream(plaintext, ciphertext)

	state := &sessionState{usedOldKey: keyIndex > 0} // 古いキーで復号されたかを示すフラグを設定
	ok := state.unmarshal(plaintext)
	return state, ok
}
```

`usedOldKey: keyIndex > 0` の部分は重要です。`sessionTicketKeys` スライスでは、`keys[0]` が現在のプライマリキーです。もし `keyIndex` が0より大きい場合、それは古いキーで復号されたことを意味し、`usedOldKey` が `true` に設定されます。このフラグは、サーバーがセッションを再開した後に新しいチケットをクライアントに発行する必要があるかどうかを判断するために使用されます。

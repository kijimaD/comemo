## 変更の背景

CRC（巡回冗長検査）は、データ転送や保存におけるエラー検出によく用いられる技術です。CRCの計算は、データを多項式として扱い、特定の生成多項式で除算する数学的なプロセスに基づいています。しかし、この生成多項式の表現方法には、MSB-first（最上位ビット優先）とLSB-first（最下位ビット優先、または反転表現）の2つの主要な形式が存在します。

Go言語の `hash/crc32` パッケージは、内部的にLSB-first形式で多項式を扱っていましたが、そのことがドキュメントに明示されていませんでした。この曖昧さは、他のシステムやライブラリとCRC値を比較したり、相互運用したりする際に、開発者にとって混乱の原因となる可能性がありました。特に、異なるシステムが異なる多項式表現を使用している場合、同じ入力データから異なるCRC値が生成されるという問題が発生し得ます。

このコミットは、このような混乱を解消し、`crc32` パッケージの利用者に対して、多項式の表現方法に関する明確な情報を提供することを目的としています。これにより、開発者はGoの `crc32` パッケージがどのように動作するかを正確に理解し、他のCRC実装との互換性を確保するための適切な調整を行うことができるようになります。

## 前提知識の解説

### 巡回冗長検査 (CRC)

CRC（Cyclic Redundancy Check）は、デジタルデータのエラー検出符号の一種です。データブロックの最後に短いチェック値を付加することで、転送中や保存中に発生した偶発的な変更を検出します。CRCは、データをバイナリ多項式として扱い、特定の「生成多項式」で除算し、その剰余をチェック値として使用します。

### 多項式の表現方法

CRCにおける多項式は、通常、バイナリ形式で表現されます。例えば、`x^5 + x^2 + x^0` という多項式は、`x^5` の係数が1、`x^4` の係数が0、`x^3` の係数が0、`x^2` の係数が1、`x^1` の係数が0、`x^0` の係数が1であるため、バイナリで `100101` と表現できます。

しかし、このバイナリ表現をどのようにビット列にマッピングするかには、主に以下の2つの方法があります。

1.  **MSB-first (Most Significant Bit first) / 通常表現**:
    *   最も一般的な表現方法で、多項式の最高次の項の係数がビット列の最上位ビット（左端）に対応します。
    *   例: `x^5 + x^2 + x^0` (バイナリ: `100101`) は、MSB-firstでは `0x25` (16進数) となります。

2.  **LSB-first (Least Significant Bit first) / 反転表現**:
    *   多項式の最低次の項（`x^0`）の係数がビット列の最上位ビット（左端）に対応し、最高次の項の係数が最下位ビット（右端）に対応します。つまり、MSB-first表現のビット列を反転させた形になります。
    *   例: `x^5 + x^2 + x^0` (バイナリ: `100101`) をLSB-firstで表現すると、ビット列を反転させて `101001` となり、これは `0x29` (16進数) に相当します。
    *   コミットメッセージの例では、`x^5 + x^2 + x^0` が5ビットLSB-first形式で `10100` (16進数: `0x14`) となると説明されています。これは、`x^0` の係数が最上位ビット（左端）に来るため、`1` (x^0), `0` (x^1), `1` (x^2), `0` (x^3), `0` (x^4), `1` (x^5) の順に並べた `101001` のうち、5ビット形式なので `10100` となることを示唆しています。

このLSB-first表現は、CRC計算の特定のアルゴリズム（特にビット単位で処理を進める実装）において、計算効率が良い場合があります。しかし、異なる表現方法を使用しているシステム間でCRC値を比較する際には、この違いを考慮しないと誤った結果を招くため、非常に重要な情報となります。

## 技術的詳細

このコミットの技術的な核心は、Goの `hash/crc32` パッケージがCRC多項式をLSB-first形式で扱っていることを、そのパッケージドキュメントに明記した点にあります。

CRC計算では、生成多項式が非常に重要です。例えば、最も一般的なCRC32の標準多項式は、IEEE 802.3で定義されている `x^32 + x^26 + x^23 + x^22 + x^16 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1` です。

*   **MSB-first表現**では、この多項式は `0x04C11DB7` となります。
*   **LSB-first表現**では、この多項式はビットが反転され `0xEDB88320` となります。

Goの `crc32` パッケージは、内部的に `0xEDB88320` を使用してCRC計算を行っています。このコミット以前は、この事実がドキュメントに明示されていなかったため、開発者が他のCRC実装（例えば、MSB-first表現を使用する実装）とGoの `crc32` パッケージを連携させようとした際に、期待通りの結果が得られない可能性がありました。

追加されたドキュメントは、LSB-first表現の定義を具体的に説明しています。
「LSB-first表現は、nビットの16進数であり、最上位ビットはx^0の係数を表し、最下位ビットはx^(n-1)の係数を表します。」
そして、具体的な例を挙げています。
「例えば、x^5 + x^2 + x^0 は、5ビットLSB-first形式では (バイナリ:10100, 16進数:0x14) です。これは、MSB-first（通常）形式の (バイナリ:00101, 16進数:0x05) とは対照的です。」

この説明は、多項式のビット表現がどのように反転されるかを明確に示しており、開発者がGoの `crc32` パッケージの動作を正確に理解し、必要に応じて多項式を適切に変換するための重要な情報を提供します。これにより、CRC計算の相互運用性が向上し、デバッグの手間が削減されます。

## コアとなるコードの解説

追加されたコメントブロックは、`crc32` パッケージのドキュメントに以下の重要な情報を追加しています。

1.  **多項式の表現形式の明示**:
    `Polynomials are represented in LSB-first form also known as reversed representation.`
    （多項式はLSB-first形式、別名反転表現で表現されます。）
    これにより、パッケージが使用する多項式のビット順序が明確になります。

2.  **LSB-first表現の定義**:
    `LSB-first representation is a hexadecimal number with n bits, the most significant bit represents the coefficient of x^0 and the least significant bit represents the coefficient of x^(n-1).`
    （LSB-first表現は、nビットの16進数であり、最上位ビットはx^0の係数を表し、最下位ビットはx^(n-1)の係数を表します。）
    この定義は、LSB-first形式がどのようにビットにマッピングされるかを詳細に説明しています。

3.  **具体的な例による説明**:
    `For example, x^5 + x^2 + x^0 is (binary:10100, hexadecimal:0x14) in 5-bit LSB-first form, as opposed to (binary:00101, hexadecimal:0x05) in MSB-first (normal) form.`
    （例えば、x^5 + x^2 + x^0 は、5ビットLSB-first形式では (バイナリ:10100, 16進数:0x14) です。これは、MSB-first（通常）形式の (バイナリ:00101, 16進数:0x05) とは対照的です。）
    この例は、抽象的な概念を具体的な数値とバイナリ表現で示し、LSB-firstとMSB-firstの違いを直感的に理解できるようにしています。

4.  **関連するWikipedia記事へのリンク**:
    `See http://en.wikipedia.org/wiki/Mathematics_of_cyclic_redundancy_checks#Reversed_representations_and_reciprocal_polynomials for information.`
    （詳細については、http://en.wikipedia.org/wiki/Mathematics_of_cyclic_redundancy_checks#Reversed_representations_and_reciprocal_polynomials を参照してください。）
    これにより、さらに深い理解を求める開発者が追加情報を参照できるようになっています。

これらの変更は、`crc32` パッケージのドキュメントの品質を大幅に向上させ、開発者がCRC計算の微妙な違いを理解し、異なるシステムとの互換性の問題を回避するのに役立ちます。

Issue #8956 を修正します。

## 変更の背景

Go言語の `encoding/binary` パッケージは、Goのデータ構造とバイトシーケンスの間で変換を行うための機能を提供します。このパッケージには、`binary.Read` や `binary.Write` といった関数があり、これらは構造体やプリミティブ型をバイト列に変換したり、その逆を行ったりします。

これらの関数は、パフォーマンスを最適化するために「高速パス（fast path）」と「低速パス（slow path）」の2つの処理経路を持っています。高速パスは、型が事前に既知であり、リフレクション（reflection）を使用せずに処理できる場合に利用されます。これにより、リフレクションのオーバーヘッドを回避し、処理速度を向上させることができます。一方、低速パスは、リフレクションを使用して任意の型を処理する場合に利用されます。

`intDataSize` 関数は、与えられたデータ型が高速パスで処理可能かどうか、そしてそのデータのバイトサイズを決定するために内部的に使用される関数です。このコミット以前の `intDataSize` 関数にはバグがあり、`uint8`, `uint16`, `uint32`, `uint64` といった符号なし整数型を正しく認識していませんでした。その結果、これらの型が `binary.Read` や `binary.Write` に渡された場合でも、`intDataSize` はゼロを返し、高速パスが利用されずに常に低速パス（リフレクションベースの処理）にフォールバックしていました。

この問題は、特に大量の符号なし整数データを扱うアプリケーションにおいて、不必要なパフォーマンスの低下を引き起こしていました。コミットメッセージにある "Fixes #8956" は、このパフォーマンス問題を報告した特定のIssueを指しています。

## 前提知識の解説

### `encoding/binary` パッケージ

`encoding/binary` パッケージは、Goのデータ構造とバイトシーケンスの間で変換を行うための機能を提供します。主に、ネットワークプロトコルやファイルフォーマットなど、特定のバイトオーダー（エンディアン）でデータをやり取りする必要がある場面で利用されます。

*   **`binary.Read(r io.Reader, byteOrder ByteOrder, data interface{}) error`**: `r` からバイナリデータを読み込み、`data` に格納します。`byteOrder` はバイトオーダー（`binary.LittleEndian` または `binary.BigEndian`）を指定します。
*   **`binary.Write(w io.Writer, byteOrder ByteOrder, data interface{}) error`**: `data` をバイナリデータとして `w` に書き込みます。

### 高速パスと低速パス（リフレクション）

Go言語では、プログラム実行時に型の情報を動的に検査・操作する「リフレクション」という機能があります。`encoding/binary` パッケージは、このリフレクションを利用して任意のGoの型をバイナリデータに変換できます。

しかし、リフレクションは実行時のオーバーヘッドが大きいため、パフォーマンスが重要な場面では可能な限り避けるべきです。`encoding/binary` パッケージは、`int8`, `uint8`, `int16`, `uint16` などのプリミティブ型や、それらのポインタ型、あるいはそれらのスライスなど、固定サイズの既知の型については、リフレクションを使わずに直接バイト列を操作する「高速パス」を用意しています。

`intDataSize` 関数は、この高速パスを利用できるかどうかを判断し、その型が占めるバイトサイズを返す役割を担っています。もし `intDataSize` がゼロを返した場合、その型は高速パスでは処理できないと判断され、リフレクションを使った低速パスにフォールバックします。

### 符号付き整数と符号なし整数

*   **符号付き整数 (Signed Integers)**: `int8`, `int16`, `int32`, `int64` など。正の値、負の値、ゼロを表現できます。最上位ビットが符号ビットとして使われます。
*   **符号なし整数 (Unsigned Integers)**: `uint8`, `uint16`, `uint32`, `uint64` など。ゼロと正の値のみを表現できます。すべてのビットが数値の大きさを表現するために使われます。

Go言語では、これらの型は異なる型として扱われます。

## 技術的詳細

このコミットの核心は、`intDataSize` 関数が符号なし整数型を `switch` ステートメントの `case` に含めるように修正された点です。

`intDataSize` 関数は、引数 `data` の型アサーションを行い、その型に基づいてバイトサイズを返します。コミット前のコードでは、`int8`, `*int8`, `*uint8` のように、`uint8` のポインタ型は認識していましたが、`uint8` そのものの型は認識していませんでした。これは `uint16`, `uint32`, `uint64` についても同様でした。

例えば、`uint8` 型の変数が `intDataSize` に渡された場合、どの `case` にもマッチせず、最終的に関数の最後で `0` が返されていました。`intDataSize` が `0` を返すと、`encoding/binary` パッケージは高速パスを利用できないと判断し、リフレクションベースの処理に切り替えます。これにより、本来高速に処理できるはずの符号なし整数型の読み書きが、不必要に遅いパスで実行されていました。

このコミットでは、各サイズの整数型について、符号付き整数型だけでなく、対応する符号なし整数型も明示的に `case` に追加することで、この問題を解決しています。

## コアとなるコードの解説

変更は `src/encoding/binary/binary.go` ファイル内の `intDataSize` 関数に集中しています。

`intDataSize` 関数は、`interface{}` 型の `data` を引数に取り、`switch data := data.(type)` 構文を使って、`data` の実際の型に基づいて処理を分岐しています。

修正前は、各サイズの整数型（例: 1バイト、2バイト、4バイト、8バイト）の `case` 文で、符号付き整数型とそのポインタ型、そして符号なし整数型のポインタ型のみが考慮されていました。

*   **修正前**:
    ```go
    case int8, *int8, *uint8: // uint8 そのものは含まれていない
    ```
*   **修正後**:
    ```go
    case int8, uint8, *int8, *uint8: // uint8 が追加された
    ```

この変更により、`uint8` 型の変数が `intDataSize` に渡された場合、正しくこの `case` にマッチし、`1`（1バイト）が返されるようになりました。同様に、`uint16`, `uint32`, `uint64` もそれぞれの `case` に追加され、正しいバイトサイズが返されるようになりました。

この修正によって、`encoding/binary` パッケージは符号なし整数型に対しても高速パスを利用できるようになり、これらの型のバイナリデータの読み書きパフォーマンスが向上しました。

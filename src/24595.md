# [インデックス 24595] ファイルの概要

このコミットは、Go言語の標準ライブラリ`fmt`パッケージにおけるバグ修正に関するものです。具体的には、`fmt`パッケージが16進数バイトをスキャンする際に、ファイルの終端（EOF）で`UnreadRune`を誤って呼び出すことで発生していた、入力の二重スキャン問題を解決します。この修正により、`fmt`パッケージの堅牢性と正確性が向上します。

## 変更の背景

この変更は、Go 1.5リリースサイクル中に発見された`fmt`パッケージのバグを修正するために行われました。具体的には、`fmt`パッケージが`%x`フォーマット指定子を使用して16進数バイトをスキャンする際、入力ストリームの終端（EOF）に到達した場合に問題が発生していました。

問題の核心は、`hexByte`関数内でEOFを読み取った直後に`s.UnreadRune()`が呼び出されていた点にあります。通常、`UnreadRune`は読み取った文字をストリームに戻すために使用されますが、EOFは実際の文字ではないため、これを「アンリード」しようとすると予期せぬ動作を引き起こします。この場合、EOFをアンリードすることで入力ストリームが論理的に「巻き戻され」、次にバイトをスキャンしようとした際に、既に処理されたはずのバイトが再度スキャンされる「二重スキャン」という現象が発生していました。

コミットメッセージによると、この問題のあるコード行はGo 1.5で導入されたもので、Go 1.4には存在しませんでした。そのため、この変更はGo 1.5におけるリグレッション（回帰バグ）の修正として位置づけられています。このバグは、Go issue #12090として報告されていました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と`fmt`パッケージの動作に関する知識が必要です。

1.  **`fmt`パッケージ**: Go言語の標準ライブラリの一部で、フォーマットされたI/O（入力/出力）を扱います。`Printf`や`Sprintf`のような出力関数だけでなく、`Scanf`や`Sscanf`のような入力スキャン関数も提供します。
2.  **`ScanState`インターフェース**: `fmt`パッケージのスキャン関数（例: `Fscanf`）に渡される入力ソースを表すインターフェースです。このインターフェースは、入力ストリームからルーン（Unicodeコードポイント）を読み取ったり、読み取ったルーンをストリームに戻したりするメソッド（`ReadRune`, `UnreadRune`など）を定義しています。
3.  **`EOF` (End Of File)**: 入力ストリームの終端を示す特別な値です。Goの`io`パッケージでは、通常`-1`または`io.EOF`エラーとして扱われますが、`fmt`パッケージの内部スキャンロジックでは、ルーンとして`eof`定数が使用されることがあります。
4.  **`UnreadRune()`**: `ScanState`インターフェースのメソッドの一つで、直前に`ReadRune()`で読み取ったルーンを入力ストリームに戻します。これにより、次の読み取り操作で同じルーンが再度読み取られるようになります。これは、パーサーが特定のパターンを検出するために先読みし、その文字が現在のトークンの一部ではない場合にストリームに戻す、といったシナリオで有用です。
5.  **16進数スキャン (`%x`)**: `fmt`パッケージのフォーマット指定子`%x`は、入力ストリームから16進数表現の値を読み取るために使用されます。例えば、`"0123"`という文字列から`%x`でスキャンすると、`0x01`や`0x23`といったバイト値に変換されます。
6.  **二重スキャン (Double-scanning)**: 入力ストリームから同じデータが複数回読み取られてしまう現象を指します。これは、入力ポインタの誤った操作や、`UnreadRune`のような操作の不適切な使用によって発生することがあります。

## 技術的詳細

このバグは、`fmt`パッケージの内部関数`hexByte`が16進数バイトをスキャンするロジックに潜んでいました。`hexByte`関数は、入力ストリームから2つの16進数文字（例: '0'〜'9', 'a'〜'f', 'A'〜'F'）を読み取り、それらを1つのバイト値に変換することを目的としています。

問題のコードは以下の部分でした（修正前）：

```go
func (s *ss) hexByte() (b byte, ok bool) {
	rune1 := s.getRune()
	if rune1 == eof {
		s.UnreadRune() // 問題の行
		return
	}
	// ... 後続の処理 ...
}
```

ここで、`s.getRune()`がEOFを返した場合、つまり入力ストリームが終端に達した場合に、`s.UnreadRune()`が呼び出されていました。しかし、EOFは有効なルーンではないため、これを「アンリード」しようとすると、`ScanState`の実装によっては入力ポインタが不正な状態になり、次のスキャン操作で既に処理されたはずのデータが再度読み取られる可能性がありました。コミットメッセージでは、これが「入力が巻き戻され、バイトの二重スキャンを引き起こした」と説明されています。

この修正は、EOFが検出された場合には`UnreadRune()`を呼び出さずに即座にリターンすることで、この問題を解決します。EOFはストリームの終端を示す状態であり、それをストリームに戻すという操作は意味をなしません。この変更により、`fmt`パッケージはEOFを正しく処理し、二重スキャンを防ぐことができます。

また、このコミットでは、このバグを再現し、修正が正しく機能することを確認するための新しいテストケースが`src/fmt/scan_test.go`に追加されています。

## コアとなるコードの解説

### `src/fmt/scan.go` の変更

`hexByte`関数は、`fmt`パッケージの内部で16進数バイトを読み取るために使用されます。この関数は、入力ストリームから最初のルーン`rune1`を`s.getRune()`で取得します。

変更前は、`rune1`が`eof`（ファイルの終端）であった場合、`s.UnreadRune()`が呼び出されていました。この`s.UnreadRune()`の呼び出しが、EOFという特殊な状態に対して行われたため、入力ストリームの内部状態が不正になり、結果として二重スキャンが発生していました。

修正では、この`s.UnreadRune()`の呼び出しが削除されました。これにより、`hexByte`関数はEOFを検出した場合、単に処理を終了し、入力ストリームを不必要に操作することがなくなりました。これは、EOFが読み取られた時点で、それ以上読み取るべきデータがないという正しいセマンティクスに従うものです。

### `src/fmt/scan_test.go` の追加

このコミットでは、`TestHexByte`という新しいテスト関数が追加されています。このテストは、`hexBytes`というカスタム型を定義し、その`Scan`メソッド内で`Fscanf`を使って`%4x`（4つの16進数文字、つまり2バイト）をスキャンします。

テストケースの目的は、`Sscanln("0123\\n", &h)`という入力で、`hexByte`関数が正しく動作することを確認することです。特に、入力の終端近くで16進数スキャンが行われるシナリオをテストしています。

-   `hexBytes`型は`[2]byte`の配列であり、`Scan`メソッドを実装することで`fmt.Scanner`インターフェースを満たします。
-   `Scan`メソッド内では、`Fscanf(ss, "%4x", &b)`を使って入力から4つの16進数文字を読み取り、バイトスライス`b`に格納します。
-   `TestHexByte`関数では、`Sscanln`を使って文字列`"0123\n"`から`hexBytes`型の変数`h`にスキャンします。
-   最終的に、`h[0]`が`0x01`、`h[1]`が`0x23`であることを検証し、16進数スキャンが正しく行われたことを確認します。

このテストは、修正された`hexByte`関数が、入力の終端処理を含め、期待通りに16進数バイトをスキャンできることを保証します。

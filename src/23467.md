# [インデックス 23467] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDNSリゾルバの`resolv.conf`再読み込みメカニズムを根本的に変更します。具体的には、`resolv.conf`の変更を監視するためにバックグラウンドで実行されていたゴルーチンを廃止し、DNSルックアップ処理の一部として`resolv.conf`の再チェックを行うように修正されています。これにより、リソースの効率化、`resolv.conf`変更後の初回ルックアップの成功、および設定ファイルのパースエラー処理の改善が図られています。

## コミット

```
net: redo resolv.conf recheck implementation

The previous implementation spawned an extra goroutine to handle
```

## 変更の背景

この変更の主な背景には、以前の`resolv.conf`再チェック実装が抱えていたいくつかの問題点があります。

1.  **余分なゴルーチンの生成**: 以前の実装では、`resolv.conf`ファイルの変更を定期的に監視するために、専用のバックグラウンドゴルーチンが起動されていました。これはシステムリソースを消費し、不要なオーバーヘッドを生じさせる可能性がありました。特に、GoのIssue #8652 (`net: resolv.conf recheck goroutine never dies`) は、このゴルーチンが適切に終了せず、リソースリークを引き起こす可能性があったことを示唆しています。
2.  **`resolv.conf`変更後の初回ルックアップの失敗**: バックグラウンドゴルーチンによる非同期的な再チェックのため、`resolv.conf`が変更されても、その変更がDNSリゾルバに反映されるまでに時間差が生じることがありました。この時間差の間に実行されたDNSルックアップは、古い設定に基づいて行われるため、失敗する可能性がありました。これはIssue #10576, #10649, #10650, #10845で報告されています。
3.  **`resolv.conf`パースエラー処理の不備**: 以前の実装では、`resolv.conf`のパース中にエラーが発生した場合の挙動が最適ではありませんでした。コミットメッセージは「rechecking logic to ignore resolv.conf parsing errors as it should」と述べており、パースエラーが発生しても、リチェックメカニズム自体は継続し、可能な限り機能するべきであるという意図が読み取れます。

これらの問題を解決し、より堅牢で効率的なDNS解決メカニズムを提供するために、`resolv.conf`の再チェック方法が見直されました。

## 前提知識の解説

このコミットを理解するためには、以下の技術的知識が役立ちます。

*   **`resolv.conf`**: Unix系システムにおけるDNSリゾルバの設定ファイルです。通常`/etc/resolv.conf`に配置され、DNSサーバーのIPアドレス（`nameserver`エントリ）や、ドメイン名解決時に自動的に付加される検索ドメイン（`search`エントリ）などが記述されます。システムがホスト名をIPアドレスに変換する際の挙動を制御します。
*   **Go言語の`net`パッケージ**: Goの標準ライブラリの一部で、ネットワークI/O機能を提供します。DNS解決機能もこのパッケージに含まれており、`LookupIP`などの関数を通じて利用されます。
*   **Goroutine (ゴルーチン)**: Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、Goランタイムによって管理されます。複数のゴルーチンを同時に実行することで、並行処理を容易に記述できます。
*   **DNS解決 (DNS Resolution)**: ドメイン名（例: `www.example.com`）を対応するIPアドレス（例: `93.184.216.34`）に変換するプロセスです。
*   **`sync.Once`**: Goの`sync`パッケージが提供するプリミティブで、特定の関数がプログラムの実行中に一度だけ実行されることを保証します。複数のゴルーチンから同時に呼び出されても、最初の呼び出しのみが実行され、それ以降の呼び出しはブロックされるか、既に実行された結果を待つことになります。
*   **`sync.RWMutex`**: 読み書きロック（Read-Write Mutex）です。共有リソースへのアクセスを制御するために使用されます。複数のリーダーが同時にリソースを読み取ることができますが、書き込みは一度に1つのライターのみが許可され、その間はリーダーもブロックされます。
*   **`os.Stat`**: Goの`os`パッケージが提供する関数で、指定されたファイルまたはディレクトリの情報を取得します。これにはファイルの最終更新時刻（`ModTime`）も含まれます。

## 技術的詳細

このコミットの技術的な核心は、`resolv.conf`の再チェックロジックを、バックグラウンドの常駐ゴルーチンから、DNSルックアップ処理の一部としてオンデマンドで実行されるメカニズムへと変更した点にあります。

1.  **バックグラウンドゴルーチンの廃止**: 以前の`loadConfig`関数は、`resolv.conf`を定期的に再読み込みするための無限ループを持つゴルーチンを起動していました。このコミットでは、このゴルーチンが完全に削除されました。
2.  **オンデマンド再チェックの実装**: `resolv.conf`の再チェックは、`lookup`関数が呼び出されるたびに`loadConfig`関数を通じて行われるようになりました。ただし、毎回ファイルを読み込むのではなく、以下の最適化が施されています。
    *   **`cfg`構造体の変更**:
        *   `ch`フィールドは、以前のゴルーチンへのシグナルチャネルから、`resolv.conf`の再チェック処理を一度に1つのゴルーチンのみに制限するためのセマフォとして再利用されました。
        *   `lastChecked` (`time.Time`) フィールドが追加され、`resolv.conf`が最後にチェックされた時刻を記録します。
        *   `modTime` (`time.Time`) フィールドが追加され、`resolv.conf`ファイルの最終更新時刻を記録します。
    *   **`initCfg`関数の導入**: `sync.Once`によって一度だけ呼び出される`initCfg`関数が新設されました。この関数は、`cfg.dnsConfig`（システム設定または`/etc/resolv.conf`から初期読み込み）、`cfg.modTime`、`cfg.lastChecked`を初期化し、`cfg.ch`セマフォを準備します。これにより、初期設定が確実に一度だけ行われます。
    *   **`loadConfig`ロジックの刷新**:
        *   `onceLoadConfig.Do(initCfg)`により、`cfg`の初期化が保証されます。
        *   `cfg.ch`セマフォを使用して、複数の`lookup`呼び出しが同時に`resolv.conf`の再チェックを試みるのを防ぎます。セマフォを取得できなかった場合（つまり、他のゴルーチンが既に再チェック中または直前に再チェックを完了した場合）、`loadConfig`はすぐにリターンします。
        *   `cfg.lastChecked`と現在の時刻を比較し、前回のチェックから5秒以内であれば再チェックをスキップします。これにより、頻繁なDNSルックアップによる`resolv.conf`の過剰な再チェックを防ぎます。
        *   `os.Stat(resolvConfPath)`でファイルの`ModTime`を取得し、`cfg.modTime`と比較します。`ModTime`が変更されていなければ、再読み込みは不要と判断し、処理を終了します。
        *   `os.Stat`がエラーを返した場合（例: ファイルが存在しない、権限がないなど）、`cfg.modTime`が以前に設定されていた場合は`time.Time{}`にリセットされます。これにより、ファイルの状態変化（例: 削除）が適切に反映されます。
        *   `dnsReadConfig(resolvConfPath)`を呼び出して`resolv.conf`を再パースし、`cfg.mu`（読み書きロック）で保護された`cfg.dnsConfig`を更新します。以前のコードにあった`ncfg.err == nil`のチェックが削除されたため、`dnsReadConfig`がエラーを含む設定を返した場合でも、その設定が`cfg.dnsConfig`に割り当てられるようになりました。これは「resolv.confパースエラーを無視する」というコミットメッセージの意図に合致し、パースエラーが発生してもリゾルバが完全に停止するのではなく、可能な限り動作を継続しようとする挙動を示唆しています。
3.  **`lookup`関数からの呼び出し**: `lookup`関数の冒頭で`loadConfig("/etc/resolv.conf")`が呼び出されるようになりました。これにより、DNSルックアップが実行される直前に、`resolv.conf`が最新の状態であることが保証されます。
4.  **テストコードの変更**: `src/net/dnsclient_unix_test.go`のテストコードも、この新しいメカニズムに合わせて修正されています。特に、`resolvConfTest`構造体からバックグラウンドゴルーチン関連のフィールドが削除され、`SetConf`メソッドは`cfg.lastChecked`をリセットして`loadConfig`を呼び出すことで、テスト中に`resolv.conf`の変更が即座に反映されるようにしています。

この変更により、`resolv.conf`の変更がより迅速かつ確実にDNSルックアップに反映されるようになり、同時に不要なゴルーチンのオーバーヘッドが削減され、リソースリークの問題も解消されました。

## コアとなるコードの解説

### `src/net/dnsclient_unix.go`

*   **`cfg`構造体**: `resolv.conf`の設定を保持するグローバル変数`cfg`が再定義されました。
    *   `ch chan struct{}`: 以前はバックグラウンドゴルーチンとの通信用でしたが、この変更により、`loadConfig`関数が同時に1つしか実行されないようにするためのセマフォとして機能します。
    *   `lastChecked time.Time`: `resolv.conf`が最後にチェックされた時刻を記録します。これにより、頻繁な再チェックを避けることができます。
    *   `modTime time.Time`: `resolv.conf`ファイルの最終更新時刻を記録します。ファイルが変更されたかどうかを効率的に判断するために使用されます。
*   **`initCfg()`関数**: `sync.Once`によって一度だけ実行される初期化関数です。
    *   システム設定または`/etc/resolv.conf`から初期のDNS設定を読み込み、`cfg.dnsConfig`に設定します。
    *   `resolv.conf`の`ModTime`と現在の時刻を`cfg.modTime`および`cfg.lastChecked`に記録します。
    *   `cfg.ch`セマフォを初期化し、最初のトークンをチャネルに送信して、`loadConfig`が実行可能であることを示します。
*   **`loadConfig(resolvConfPath string)`関数**: `resolv.conf`の再読み込みロジックの核心です。
    *   `onceLoadConfig.Do(initCfg)`: `cfg`が確実に一度だけ初期化されることを保証します。
    *   `select { case <-cfg.ch: ... default: return }`: `cfg.ch`をセマフォとして使用し、`loadConfig`の同時実行を1つに制限します。セマフォを取得できた場合のみ処理を続行し、処理完了後に`defer`でセマフォを解放します。
    *   `if cfg.lastChecked.After(now.Add(-5 * time.Second))`: 前回のチェックから5秒以内であれば、再チェックをスキップして早期リターンします。
    *   `os.Stat(resolvConfPath)`と`fi.ModTime().Equal(cfg.modTime)`: ファイルの最終更新時刻をチェックし、変更がなければ再読み込みをスキップします。
    *   `else { ... }`: `os.Stat`がエラーを返した場合（ファイルが存在しないなど）の処理です。`cfg.modTime`が以前に設定されていた場合は`time.Time{}`にリセットし、ファイルの状態変化を反映させます。
    *   `ncfg := dnsReadConfig(resolvConfPath)`: `resolv.conf`をパースします。
    *   `cfg.mu.Lock(); cfg.dnsConfig = ncfg; cfg.mu.Unlock()`: `cfg.dnsConfig`を更新する際に、`sync.RWMutex`で排他制御を行い、データ競合を防ぎます。以前のコードにあった`ncfg.err == nil`のチェックが削除されたため、パースエラーが発生しても新しい設定が適用される可能性があります。
*   **`lookup(name string, qtype uint16)`関数**: DNSルックアップを実行する関数です。
    *   `loadConfig("/etc/resolv.conf")`: ルックアップ処理の冒頭で`loadConfig`を呼び出すことで、常に最新の`resolv.conf`設定が利用されるようにします。
    *   `cfg.mu.RLock(); resolv := cfg.dnsConfig; cfg.mu.RUnlock()`: `cfg.dnsConfig`にアクセスするために読み取りロックを取得し、ルックアップ処理全体でこの設定を使用します。

### `src/net/dnsclient_unix_test.go`

*   **`resolvConfTest`構造体**: テストヘルパー構造体から、バックグラウンドゴルーチンに関連するフィールド（`started`, `quitc`）が削除され、シンプルになりました。
*   **`newResolvConfTest()`関数**: `onceLoadConfig.Do(func(){})`によるデフォルト`loadConfig`の無効化が不要になりました。
*   **`Start()`メソッドの削除**: バックグラウンドゴルーチンがなくなったため、このメソッドは不要となり削除されました。
*   **`SetConf(s string)`メソッド**:
    *   `cfg.lastChecked = time.Time{}`: `resolv.conf`ファイルを更新した後、`lastChecked`をゼロ値にリセットすることで、次の`loadConfig`呼び出しで確実に再チェックが行われるようにします。
    *   `loadConfig(r.path)`: テスト中に`resolv.conf`の変更を即座に反映させるために、明示的に`loadConfig`を呼び出します。
*   **`Close()`メソッド**: バックグラウンドゴルーチンへの終了シグナル送信ロジックが削除され、シンプルになりました。
*   **テスト関数の更新**: `TestReloadResolvConfFail`や`TestReloadResolvConfChange`などのテスト関数から、`r.Start()`の呼び出しが削除されました。
*   **`BenchmarkGoLookupIPWithBrokenNameServer`**: ベンチマーク中に`loadConfig`が実行されないように、`cfg.ch`セマフォを一時的に操作するロジックが追加されました。

これらの変更により、GoのDNSリゾルバはより効率的で予測可能な`resolv.conf`の管理を実現し、特に設定変更時の挙動が改善されました。

# [インデックス 23288] ファイルの概要

このコミットは、Go言語の`text/template`パッケージにおいて、不正なパイプラインがパース時に検出されるように改善するものです。これにより、これまで実行時（特に`html/template`パッケージ使用時）にパニックを引き起こしていた特定の形式のテンプレートエラーが、より早期に、かつ安全に捕捉されるようになります。

## コミット

```
text/template: check for malformed pipelines

Catch some malformed pipelines at parsing time.
The current code accepts pipelines such as:

{{12|.}}\n
{{"hello"|print|false}}\n
{{.|\"blah blah\"}}\n

Such pipelines generate panic in html/template at execution time.

Add an extra check to verify all the commands of the pipeline are executable
(except for the first one).

Fixes #10610
```

## 変更の背景

Goの`text/template`パッケージは、テキストベースのテンプレートを生成するための強力なツールです。このパッケージは、テンプレートの構文解析（パース）と実行（エグゼキューション）の2つの主要なフェーズで動作します。しかし、このコミット以前は、特定の形式の「不正なパイプライン」がパースフェーズを通過し、実行フェーズに至ってしまうという問題がありました。

具体的には、`{{12|.}`や`{{"hello"|print|false}}`のように、パイプラインの途中に数値、文字列、ブーリアン、nil、またはドット（`.`）といった「実行可能ではない」リテラル値が挟まれるケースです。`text/template`自体はこれらの不正なパイプラインをパース時にエラーとして扱わず、実行時に評価しようとします。

この問題が顕在化するのは、特に`html/template`パッケージを使用した場合です。`html/template`は`text/template`の上に構築されており、HTMLのセキュリティを考慮した追加の処理を行います。不正なパイプラインが`html/template`の実行フェーズに到達すると、内部で予期せぬ状態となり、最終的にパニック（プログラムの異常終了）を引き起こしていました。

開発者は、このような実行時パニックは避けるべきであり、テンプレートの構文エラーは可能な限りパース時に検出されるべきだと考えました。これにより、開発者はテンプレートの記述ミスを早期に発見でき、アプリケーションの堅牢性が向上します。このコミットは、この問題を解決し、より安全なテンプレート処理を実現するために導入されました。

## 前提知識の解説

このコミットの理解には、Goのテンプレートシステム、特に`text/template`パッケージにおける以下の概念が重要です。

1.  **`text/template`パッケージ**: Go標準ライブラリの一部で、プレーンテキストの出力生成に特化したテンプレートエンジンです。ユーザーが定義したデータ構造とテンプレート文字列を組み合わせて、動的なテキストを生成します。
2.  **パイプライン (`|`)**: Goテンプレートにおけるパイプラインは、Unixのシェルスクリプトにおけるパイプラインと同様の概念です。あるコマンドの出力（結果）を次のコマンドの入力（引数）として渡すために使用されます。
    *   例: `{{.Name | printf "Hello %s"}}`
        *   `.Name` の値が `printf` 関数の引数として渡されます。
3.  **コマンドと引数**: テンプレート内の`{{...}}`で囲まれた部分は「アクション」と呼ばれ、その中に「コマンド」が含まれます。コマンドは関数呼び出しや変数参照などです。パイプラインでは、複数のコマンドが連結されます。
4.  **実行可能 (Executable) なコマンド**: パイプラインの最初のコマンドは、変数、フィールド、関数呼び出しなど、どのような値でも構いません。しかし、パイプラインの**2番目以降のコマンド**は、その前のコマンドから渡された値を受け取り、何らかの処理を行う「関数」または「メソッド」である必要があります。
    *   例えば、`print`や`html`、`printf`などは関数なので実行可能です。
    *   しかし、数値（`12`）、文字列（`"hello"`）、ブーリアン（`true`/`false`）、nil、またはドット（`.``）のようなリテラル値は、それ自体が関数ではないため、パイプラインの途中で「実行可能」ではありません。これらをパイプラインの途中に置くと、テンプレートエンジンはそれらを関数として呼び出そうとし、エラーやパニックの原因となります。
5.  **`html/template`パッケージ**: `text/template`と同様のAPIを提供しますが、HTML出力に特化しており、クロスサイトスクリプティング（XSS）攻撃などのセキュリティ脆弱性を自動的にエスケープする機能を持っています。`html/template`は内部的に`text/template`を利用しており、より厳格なチェックやエスケープ処理を追加します。このため、`text/template`で許容される一部の構文が、`html/template`では異なる振る舞いをしたり、より厳密なエラーチェックが行われたりすることがあります。

このコミットは、上記4の「実行可能ではないコマンド」がパイプラインの途中に現れるケースを、パース時に検出することで、実行時パニックを防ぐことを目的としています。

## 技術的詳細

このコミットの技術的な核心は、`text/template`パッケージのパース処理に、パイプラインの健全性をチェックする新しいロジックを追加した点にあります。

変更は主に以下のファイルで行われています。

*   `src/text/template/parse/parse.go`: テンプレートの構文解析を行う主要なファイル。
*   `src/text/template/parse/parse_test.go`: 構文解析のテストケースを定義するファイル。

### `parse.go`における変更

1.  **`checkPipeline`関数の追加**:
    `func (t *Tree) checkPipeline(pipe *PipeNode, context string)` という新しい関数が追加されました。この関数は、パースされたパイプラインノード (`*PipeNode`) を受け取り、その中のコマンドが適切であるかを検証します。

2.  **パイプラインの空チェック**:
    `checkPipeline`関数内で、まず `if len(pipe.Cmds) == 0` というチェックが行われます。これは、パイプラインが空である場合に `t.errorf("missing value for %s", context)` を呼び出してエラーを報告します。これは既存のロジックを`checkPipeline`に移動したものです。

3.  **実行可能性のチェック**:
    最も重要な変更は、パイプラインの2番目以降のコマンドに対する実行可能性チェックです。
    ```go
    for i, c := range pipe.Cmds[1:] { // pipe.Cmds[1:] で最初のコマンドをスキップ
        switch c.Args[0].Type() {
        case NodeBool, NodeDot, NodeNil, NodeNumber, NodeString:
            // With A|B|C, pipeline stage 2 is B
            t.errorf("non executable command in pipeline stage %d", i+2)
        }
    }
    ```
    *   `pipe.Cmds[1:]` は、パイプラインの最初のコマンドを除いた残りのコマンドをイテレートします。これは、パイプラインの最初のコマンドはどのような値でも許容されるためです。
    *   各コマンド `c` の最初の引数 (`c.Args[0]`) の型をチェックします。
    *   `NodeBool`, `NodeDot`, `NodeNil`, `NodeNumber`, `NodeString` は、それぞれブーリアン、ドット（`.`）、nil、数値、文字列のリテラルノード型を表します。これらの型は「実行可能ではない」と判断されます。
    *   もしこれらの型のいずれかがパイプラインの2番目以降のステージで検出された場合、`t.errorf` を呼び出して「`non executable command in pipeline stage %d`」（パイプラインのステージ%dに実行不可能なコマンドがあります）というエラーを発生させます。`i+2`は、ループのインデックス`i`が0から始まるため、ユーザーにとって分かりやすいステージ番号（2番目から）を提供します。

4.  **`pipeline`関数からの呼び出し**:
    既存の`pipeline`関数内で、パイプラインのパースが完了した直後（`itemRightDelim`または`itemRightParen`が検出された時）に、新しく追加された`t.checkPipeline(pipe, context)`が呼び出されるようになりました。これにより、パースが完了した時点でパイプラインの健全性チェックが実行されます。

### `parse_test.go`における変更

このコミットでは、新しいチェックロジックが正しく機能することを確認するために、`parse_test.go`に多数の新しいテストケースが追加されています。

*   `wrong pipeline dot`, `wrong pipeline number`, `wrong pipeline string`, `wrong pipeline char`, `wrong pipeline boolean`, `wrong pipeline nil` といったテストケースが追加され、それぞれ`{{12|.}`、`{{.|12|printf}}`、`{{.|print|"error"}}`、`{{12|print|html|'e'}}`、`{{.|true}}`、`{{'c'|nil}}`のような不正なパイプラインがパースエラーを引き起こすことを検証しています。
*   `empty pipeline` テストケースも追加され、`{{printf "%d" ( ) }}` のような空のパイプラインが正しくエラーになることを確認しています。
*   `errorTests`にも`wrongpipeline`と`emptypipeline`が追加され、期待されるエラーメッセージが正確であるかを検証しています。

これらの変更により、`text/template`はより堅牢になり、不正なテンプレートが実行時にパニックを引き起こすリスクが大幅に低減されました。エラーがパース時に捕捉されることで、開発者はより迅速に問題を特定し、修正できるようになります。

## コアとなるコードの解説

### `src/text/template/parse/parse.go`

*   **`pipeline`関数内の変更**:
    `pipeline`関数は、テンプレート内のパイプライン構文を解析する役割を担っています。以前は、パイプラインが閉じられた際（`itemRightDelim`または`itemRightParen`が検出された際）に、パイプラインが空であるかどうかのチェックのみを行っていました。
    このコミットでは、その空チェックのロジックを新しく追加された`checkPipeline`関数に移動し、さらに`checkPipeline`を呼び出すことで、パイプライン全体の健全性チェックを行うように変更されました。これにより、パースが完了した時点で、パイプライン内の各コマンドが実行可能であるかどうかが検証されるようになりました。

*   **`checkPipeline`関数の追加**:
    この関数は、パイプラインの健全性を検証するための中心的なロジックを含んでいます。
    1.  **空のパイプラインの拒否**: `if len(pipe.Cmds) == 0` の部分で、パイプラインにコマンドが一つも含まれていない場合にエラーを発生させます。これは、例えば `{{ ( ) }}` のような構文に対応します。
    2.  **実行可能性の検証**: `for i, c := range pipe.Cmds[1:]` のループが、パイプラインの最初のコマンドを除いたすべての後続コマンドを検査します。
        *   `c.Args[0].Type()` は、現在のコマンドの最初の引数（これはパイプラインの前のステージからの入力、またはコマンド自体の最初の引数）のノード型を取得します。
        *   `switch`文で、そのノード型が`NodeBool`, `NodeDot`, `NodeNil`, `NodeNumber`, `NodeString`のいずれかであるかをチェックします。これらの型はリテラル値を表し、関数やメソッドのように「実行可能」ではありません。
        *   もし実行不可能な型が検出された場合、`t.errorf("non executable command in pipeline stage %d", i+2)` を呼び出してパースエラーを報告します。`i+2`は、ループのインデックス`i`が0から始まるため、パイプラインのステージ番号を正確に（2番目から）示すためのものです。例えば、`{{A|B|C}}`の場合、`B`はステージ2、`C`はステージ3となります。

### `src/text/template/parse/parse_test.go`

*   **新しいテストケースの追加**:
    `parseTests`と`errorTests`の配列に、様々な不正なパイプラインのパターンが追加されました。これには、ドット、数値、文字列、ブーリアン、nilといったリテラル値がパイプラインの途中に現れるケースや、空のパイプラインのケースが含まれます。これらのテストケースは、`checkPipeline`関数が期待通りにパースエラーを発生させることを確認するために使用されます。これにより、将来の変更がこの重要なエラーチェック機能を損なわないことが保証されます。

これらの変更により、Goのテンプレートエンジンは、より早期に、より明確なエラーメッセージで、不正なテンプレート構文を検出できるようになり、開発体験とアプリケーションの堅牢性が向上しました。

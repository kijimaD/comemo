# [インデックス 20764] ファイルの概要

このコミットは、Go 1.4 リリースに向けて、Goランタイムのヒープダンプフォーマットを更新するものです。主な変更点は、ヒープダンプから完全な型情報が削除され、代わりにポインタ/非ポインタマップがダンプされるようになったことです。これにより、グラフの接続性を計算できるようになります。また、Iface/Eface型は引き続きダンプされ、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になる見込みです。

## 元コミット内容

Go 1.4 のヒープダンプフォーマットを更新。
ヒープ内に完全な型情報がなくなったため、それらをダンプすることはできなくなった。代わりに、ポインタ/非ポインタマップをダンプすることで、少なくともグラフの接続性を計算できるようにする。
さらに、Iface/Eface型は引き続きダンプされるため、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になるかもしれない。

## 変更の背景

Goランタイムは継続的に進化しており、特にガベージコレクション（GC）やメモリ管理の最適化は重要なテーマです。Go 1.4では、GCの改善やランタイムの効率化が図られていました。このコミットは、その一環として、ヒープダンプのフォーマットを変更することで、デバッグやプロファイリングのツールがGo 1.4の新しいランタイムの挙動に適応できるようにすることを目的としています。

以前のGoバージョンでは、ヒープダンプにオブジェクトの完全な型情報が含まれていましたが、Go 1.4の変更により、ランタイムがヒープ内で保持する型情報の粒度が変更された可能性があります。これにより、ヒープダンプのサイズ削減や、GCのオーバーヘッド削減に寄与したと考えられます。しかし、その代償として、ヒープダンプから直接完全な型情報を取得することが難しくなりました。

この変更の背景には、以下の点が考えられます。

*   **メモリフットプリントの削減**: ランタイムがヒープ内で保持する型情報の量を減らすことで、Goプログラム全体のメモリ使用量を削減する。
*   **GC効率の向上**: GCがオブジェクトの型情報を参照する頻度や量を減らすことで、GCの実行時間を短縮し、アプリケーションのレイテンシを改善する。
*   **デバッグツールの進化**: 完全な型情報がヒープダンプに含まれなくなったとしても、ポインタ/非ポインタマップやIface/Eface型情報、そしてDWARFデバッグ情報と組み合わせることで、デバッグツールが引き続き有用な情報を提供できるようにする。

このコミットは、Goランタイムの内部構造の変更に合わせた、デバッグおよびプロファイリング機能の適応と進化を示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、システムコールなどが含まれます。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域。Goでは、`make`や`new`で作成されたオブジェクトはヒープに割り当てられます。
*   **ヒープダンプ (Heap Dump)**: 特定の時点でのヒープメモリのスナップショット。デバッグやメモリリークの解析、メモリ使用量のプロファイリングなどに使用されます。Goでは、`GODEBUG=gctrace=1`や`go tool pprof`などのツールと組み合わせて利用されます。
*   **型情報 (Type Information)**: プログラム内の変数やオブジェクトがどのような型であるかを示す情報。Goでは、`reflect`パッケージを通じて実行時に型情報を操作できます。
*   **ポインタ (Pointer)**: メモリ上の特定のアドレスを指し示す変数。Goでは、`*T`のような構文でポインタ型を定義します。
*   **ポインタ/非ポインタマップ (Pointer/Nopointer Maps)**: オブジェクトのメモリレイアウトにおいて、どのオフセットにポインタが含まれているか、どのオフセットに非ポインタ（スカラー値）が含まれているかを示すビットマップまたは同様のデータ構造。ガベージコレクタがヒープをスキャンする際に、どのフィールドがポインタであり、たどるべき参照であるかを判断するために使用されます。
*   **グラフ接続性 (Graph Connectivity)**: ヒープ内のオブジェクトがどのように互いに参照し合っているか、つまりオブジェクト間の参照関係のグラフ構造。ガベージコレクタは、この接続性情報を使用して、到達可能なオブジェクトと到達不可能なオブジェクトを区別します。
*   **Iface/Eface (Interface/Empty Interface)**:
    *   **Iface (Interface)**: Goのインターフェース型。`interface { method1() ... }`のように定義され、型と値のペア（`itab`とデータポインタ）で構成されます。`itab`は、インターフェースが実装する具体的な型とメソッドテーブルへのポインタを含みます。
    *   **Eface (Empty Interface)**: 空のインターフェース型 `interface{}`。任意の型の値を保持できます。これも型と値のペア（`_type`とデータポインタ）で構成されます。
*   **DWARFデバッグ情報 (DWARF Debug Information)**: 実行可能ファイルに埋め込まれる標準的なデバッグ情報フォーマット。変数名、型情報、ソースコードの行番号など、デバッガがプログラムの実行を解析するために必要な情報を提供します。Goのツールチェーンは、コンパイル時にDWARF情報を生成します。
*   **BitVector**: ビットの配列で、特定のプロパティ（この場合はポインタの有無）を効率的に表現するために使用されます。ガベージコレクションにおいて、オブジェクト内のどの部分がポインタであるかをマークするために使われることが多いです。
*   **`runtime·data` / `runtime·bss`**: Goランタイムが管理するデータセグメントとBSSセグメント。
    *   **データセグメント (Data Segment)**: 初期化されたグローバル変数や静的変数が格納されるメモリ領域。
    *   **BSSセグメント (BSS Segment)**: 初期化されていないグローバル変数や静的変数が格納されるメモリ領域。プログラム開始時にゼロで初期化されます。
*   **`MSpan`**: Goのメモリ管理における重要なデータ構造。ヒープメモリの大きなチャンク（ページ）を管理し、そのページがどのオブジェクト型に割り当てられているか、どの部分が使用中かなどの情報を含みます。

これらの概念は、Goランタイムのメモリ管理とデバッグの仕組みを理解する上で不可欠です。

## 技術的詳細

このコミットは、`src/runtime/heapdump.c` ファイルに対する変更であり、Goランタイムのヒープダンプメカニズムの内部実装に深く関わっています。

1.  **ヒープダンプフォーマットのバージョン更新**:
    *   コメント内のヒープダンプフォーマットの参照URLが `http://code.google.com/p/go-wiki/wiki/heapdump13` から `http://code.google.com/p/go-wiki/wiki/heapdump14` に変更されました。これは、Go 1.4でヒープダンプフォーマットに互換性のない変更があったことを明確に示しています。
    *   ヒープダンプのヘッダ文字列も `"go1.3 heap dump\\n"` から `"go1.4 heap dump\\n"` に更新されています。

2.  **`FieldKind` 列挙型の変更**:
    *   `FieldKindString` (2) と `FieldKindSlice` (3) が削除されました。
    *   それに伴い、`FieldKindIface` と `FieldKindEface` の値がそれぞれ `4` と `5` から `2` と `3` に変更されました。
    *   これは、ヒープダンプにおいて、文字列やスライスの内部構造を直接ダンプするのではなく、より抽象的なポインタ情報として扱うようになったことを示唆しています。

3.  **`dumpobj` 関数の変更**:
    *   以前はオブジェクトのダンプ時に `Type*` と `kind` の情報がダンプされていましたが、これらが削除されました (`dumpint(0); // Type*` と `dumpint(0); // kind` の行が削除)。これは、ヒープダンプから完全な型情報が削除されたというコミットメッセージの記述と一致します。
    *   代わりに、`dumpfields(bv);` が追加されました。`bv` は `BitVector` であり、オブジェクト内のポインタの有無を示すマップです。これにより、完全な型情報がなくても、オブジェクト内のどのフィールドがポインタであるかを識別し、ガベージコレクタが参照グラフを構築するために必要な「ポインタ/非ポインタマップ」を提供します。

4.  **`dumpbv` 関数の変更**:
    *   `BitsDead` のケースに `return;` が追加されました。`BitsDead` は、メモリ領域が使用されていない（デッド）ことを示すビットです。この変更は、デッドな領域についてはそれ以上処理を続行する必要がないことを示し、ヒープダンプの効率を向上させる可能性があります。

5.  **`dumproots` 関数の変更**:
    *   データセグメント (`runtime·data`) と BSSセグメント (`runtime·bss`) のダンプにおいて、`dumpbvtypes` の呼び出しが追加されました。これは、これらのグローバルなメモリ領域についても、ポインタ/非ポインタマップをダンプするように変更されたことを意味します。
    *   BSSセグメントの `dumpfields` 呼び出しで、誤って `runtime·gcdatamask` が使用されていた箇所が `runtime·gcbssmask` に修正されました。これは、BSSセグメントにはBSSセグメント用のGCマスクを使用すべきであるという論理的な修正です。

6.  **`itab_callback` 関数の変更**:
    *   この関数は、インターフェーステーブル（`itab`）が発見されたときに呼び出されます。
    *   以前は単に `itab` のアドレスと、その型が直接インターフェースかポインタなし型かを示すブール値がダンプされていました。
    *   変更後、`itab` が指すデータフィールドの型をダンプするように大幅に修正されました。
        *   `KindDirectIface` が0（間接インターフェース）の場合、データスロットは型 `t` へのポインタであるため、`t->ptrto` の型がダンプされます。
        *   `KindNoPointers` が0（ポインタのような型）の場合、データスロットは型 `t` そのものであるため、`t` の型がダンプされます。
        *   それ以外の場合（スカラー型）、`t` の型がダンプされます。
    *   この変更は、インターフェースが参照する具体的な型の情報をヒープダンプに含めることで、デバッグツールがインターフェースの参照先をより正確に特定できるようにすることを目的としています。コミットメッセージにある「Iface/Eface型は引き続きダンプされる」という記述と合致します。

これらの変更は、Go 1.4におけるランタイムのメモリ管理と型情報の扱いの進化を反映しており、ヒープダンプがより効率的かつ目的に合った情報を提供するように調整されたことを示しています。完全な型情報が失われた代わりに、ガベージコレクタが参照グラフを再構築するために必要な最小限のポインタ情報が提供されるようになっています。

## コアとなるコードの解説

このコミットの核心は、Goランタイムのヒープダンプメカニズムが、Go 1.4での内部的な型情報の管理方法の変更に適応するように更新された点にあります。

1.  **型情報の粒度変更と `dumpobj` の修正**:
    *   以前のGoバージョンでは、ヒープ上の各オブジェクトに対して完全な型情報がダンプされていました。これは、`dumpobj` 関数内で `dumpint(0); // Type*` と `dumpint(0); // kind` の行が存在していたことから推測できます（これらの行は、実際にはダミー値として型情報をダンプしていた可能性もありますが、型情報がヒープダンプのコンテキストで考慮されていたことを示します）。
    *   Go 1.4では、ヒープ内に完全な型情報を持たなくなったため、これらの行が削除されました。
    *   代わりに `dumpfields(bv);` が追加されました。`bv` は `BitVector` であり、これはオブジェクト内のどのオフセットにポインタが含まれているかを示すビットマップです。ガベージコレクタは、このポインタ/非ポインタマップを使用して、オブジェクト内の参照を正確に識別し、参照グラフを構築します。これにより、完全な型情報がなくても、ヒープの接続性を正確に表現できるようになります。

2.  **`itab_callback` の強化**:
    *   `itab_callback` は、インターフェーステーブル（`itab`）が発見されたときに呼び出される関数です。`itab` は、Goのインターフェースが具体的な型をどのように実装しているかを示す重要なランタイムデータ構造です。
    *   この関数の変更は、インターフェースが保持するデータフィールドの型情報をヒープダンプに含めることを目的としています。
    *   Goのインターフェースは、内部的に「型」と「値」のペアとして表現されます。
        *   `KindDirectIface == 0` の場合（間接インターフェース）、インターフェースの値はポインタであり、そのポインタが指す先の型が `t->ptrto` で表現されます。この場合、`t->ptrto` の型情報がダンプされます。
        *   `KindNoPointers == 0` の場合（ポインタのような型）、インターフェースの値は直接その型 `t` を保持します。この場合、`t` の型情報がダンプされます。
        *   それ以外の場合（スカラー型）、`t` の型情報がダンプされます。
    *   この詳細な型情報のダンプは、コミットメッセージにある「Iface/Eface型は引き続きダンプされるので、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になるかもしれない」という意図を具体的に実現するものです。これにより、デバッグツールはインターフェースの動的な型をより正確に推論できるようになります。

3.  **グローバルセグメントのポインタマップダンプ**:
    *   `dumproots` 関数における `runtime·data` (データセグメント) と `runtime·bss` (BSSセグメント) のダンプ時に `dumpbvtypes` が追加されました。これは、これらのグローバルなメモリ領域についても、ガベージコレクタが参照を追跡するために必要なポインタ/非ポインタマップがヒープダンプに含まれるようになったことを意味します。これにより、グローバル変数からの参照も正確に追跡できるようになります。

これらの変更は、Go 1.4におけるランタイムのメモリ管理とGCの進化に合わせて、ヒープダンプがより効率的かつ有用な情報を提供するように調整されたことを示しています。完全な型情報がヒープから削除されたとしても、ポインタ/非ポインタマップとインターフェースの型情報を組み合わせることで、デバッグツールは引き続きヒープの状態を深く分析できるようになっています。

## 元コミット内容

Go 1.4 のヒープダンプフォーマットを更新。
ヒープ内に完全な型情報がなくなったため、それらをダンプすることはできなくなった。代わりに、ポインタ/非ポインタマップをダンプすることで、少なくともグラフの接続性を計算できるようにする。
さらに、Iface/Eface型は引き続きダンプされるため、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になるかもしれない。

## 変更の背景

Goランタイムは継続的に進化しており、特にガベージコレクション（GC）やメモリ管理の最適化は重要なテーマです。Go 1.4では、GCの改善やランタイムの効率化が図られていました。このコミットは、その一環として、ヒープダンプのフォーマットを変更することで、デバッグやプロファイリングのツールがGo 1.4の新しいランタイムの挙動に適応できるようにすることを目的としています。

以前のGoバージョンでは、ヒープダンプにオブジェクトの完全な型情報が含まれていましたが、Go 1.4の変更により、ランタイムがヒープ内で保持する型情報の粒度が変更された可能性があります。これにより、ヒープダンプのサイズ削減や、GCのオーバーヘッド削減に寄与したと考えられます。しかし、その代償として、ヒープダンプから直接完全な型情報を取得することが難しくなりました。

この変更の背景には、以下の点が考えられます。

*   **メモリフットプリントの削減**: ランタイムがヒープ内で保持する型情報の量を減らすことで、Goプログラム全体のメモリ使用量を削減する。
*   **GC効率の向上**: GCがオブジェクトの型情報を参照する頻度や量を減らすことで、GCの実行時間を短縮し、アプリケーションのレイテンシを改善する。
*   **デバッグツールの進化**: 完全な型情報がヒープダンプに含まれなくなったとしても、ポインタ/非ポインタマップやIface/Eface型情報、そしてDWARFデバッグ情報と組み合わせることで、デバッグツールが引き続き有用な情報を提供できるようにする。

このコミットは、Goランタイムの内部構造の変更に合わせた、デバッグおよびプロファイリング機能の適応と進化を示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、システムコールなどが含まれます。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域。Goでは、`make`や`new`で作成されたオブジェクトはヒープに割り当てられます。
*   **ヒープダンプ (Heap Dump)**: 特定の時点でのヒープメモリのスナップショット。デバッグやメモリリークの解析、メモリ使用量のプロファイリングなどに使用されます。Goでは、`GODEBUG=gctrace=1`や`go tool pprof`などのツールと組み合わせて利用されます。
*   **型情報 (Type Information)**: プログラム内の変数やオブジェクトがどのような型であるかを示す情報。Goでは、`reflect`パッケージを通じて実行時に型情報を操作できます。
*   **ポインタ (Pointer)**: メモリ上の特定のアドレスを指し示す変数。Goでは、`*T`のような構文でポインタ型を定義します。
*   **ポインタ/非ポインタマップ (Pointer/Nopointer Maps)**: オブジェクトのメモリレイアウトにおいて、どのオフセットにポインタが含まれているか、どのオフセットに非ポインタ（スカラー値）が含まれているかを示すビットマップまたは同様のデータ構造。ガベージコレクタがヒープをスキャンする際に、どのフィールドがポインタであり、たどるべき参照であるかを判断するために使用されます。
*   **グラフ接続性 (Graph Connectivity)**: ヒープ内のオブジェクトがどのように互いに参照し合っているか、つまりオブジェクト間の参照関係のグラフ構造。ガベージコレクタは、この接続性情報を使用して、到達可能なオブジェクトと到達不可能なオブジェクトを区別します。
*   **Iface/Eface (Interface/Empty Interface)**:
    *   **Iface (Interface)**: Goのインターフェース型。`interface { method1() ... }`のように定義され、型と値のペア（`itab`とデータポインタ）で構成されます。`itab`は、インターフェースが実装する具体的な型とメソッドテーブルへのポインタを含みます。
    *   **Eface (Empty Interface)**: 空のインターフェース型 `interface{}`。任意の型の値を保持できます。これも型と値のペア（`_type`とデータポインタ）で構成されます。
*   **DWARFデバッグ情報 (DWARF Debug Information)**: 実行可能ファイルに埋め込まれる標準的なデバッグ情報フォーマット。変数名、型情報、ソースコードの行番号など、デバッガがプログラムの実行を解析するために必要な情報を提供します。Goのツールチェーンは、コンパイル時にDWARF情報を生成します。
*   **BitVector**: ビットの配列で、特定のプロパティ（この場合はポインタの有無）を効率的に表現するために使用されます。ガベージコレクションにおいて、オブジェクト内のどの部分がポインタであるかをマークするために使われることが多いです。
*   **`runtime·data` / `runtime·bss`**: Goランタイムが管理するデータセグメントとBSSセグメント。
    *   **データセグメント (Data Segment)**: 初期化されたグローバル変数や静的変数が格納されるメモリ領域。
    *   **BSSセグメント (BSS Segment)**: 初期化されていないグローバル変数や静的変数が格納されるメモリ領域。プログラム開始時にゼロで初期化されます。
*   **`MSpan`**: Goのメモリ管理における重要なデータ構造。ヒープメモリの大きなチャンク（ページ）を管理し、そのページがどのオブジェクト型に割り当てられているか、どの部分が使用中かなどの情報を含みます。

これらの概念は、Goランタイムのメモリ管理とデバッグの仕組みを理解する上で不可欠です。

## 技術的詳細

このコミットは、`src/runtime/heapdump.c` ファイルに対する変更であり、Goランタイムのヒープダンプメカニズムの内部実装に深く関わっています。

1.  **ヒープダンプフォーマットのバージョン更新**:
    *   コメント内のヒープダンプフォーマットの参照URLが `http://code.google.com/p/go-wiki/wiki/heapdump13` から `http://code.google.com/p/go-wiki/wiki/heapdump14` に変更されました。これは、Go 1.4でヒープダンプフォーマットに互換性のない変更があったことを明確に示しています。
    *   ヒープダンプのヘッダ文字列も `"go1.3 heap dump\\n"` から `"go1.4 heap dump\\n"` に更新されています。

2.  **`FieldKind` 列挙型の変更**:
    *   `FieldKindString` (2) と `FieldKindSlice` (3) が削除されました。
    *   それに伴い、`FieldKindIface` と `FieldKindEface` の値がそれぞれ `4` と `5` から `2` と `3` に変更されました。
    *   これは、ヒープダンプにおいて、文字列やスライスの内部構造を直接ダンプするのではなく、より抽象的なポインタ情報として扱うようになったことを示唆しています。

3.  **`dumpobj` 関数の変更**:
    *   以前はオブジェクトのダンプ時に `Type*` と `kind` の情報がダンプされていましたが、これらが削除されました (`dumpint(0); // Type*` と `dumpint(0); // kind` の行が削除)。これは、ヒープダンプから完全な型情報が削除されたというコミットメッセージの記述と一致します。
    *   代わりに、`dumpfields(bv);` が追加されました。`bv` は `BitVector` であり、オブジェクト内のポインタの有無を示すマップです。これにより、完全な型情報がなくても、オブジェクト内のどのフィールドがポインタであるかを識別し、ガベージコレクタが参照グラフを構築するために必要な「ポインタ/非ポインタマップ」を提供します。

4.  **`dumpbv` 関数の変更**:
    *   `BitsDead` のケースに `return;` が追加されました。`BitsDead` は、メモリ領域が使用されていない（デッド）ことを示すビットです。この変更は、デッドな領域についてはそれ以上処理を続行する必要がないことを示し、ヒープダンプの効率を向上させる可能性があります。

5.  **`dumproots` 関数の変更**:
    *   データセグメント (`runtime·data`) と BSSセグメント (`runtime·bss`) のダンプにおいて、`dumpbvtypes` の呼び出しが追加されました。これは、これらのグローバルなメモリ領域についても、ポインタ/非ポインタマップをダンプするように変更されたことを意味します。
    *   BSSセグメントの `dumpfields` 呼び出しで、誤って `runtime·gcdatamask` が使用されていた箇所が `runtime·gcbssmask` に修正されました。これは、BSSセグメントにはBSSセグメント用のGCマスクを使用すべきであるという論理的な修正です。

6.  **`itab_callback` 関数の変更**:
    *   この関数は、インターフェーステーブル（`itab`）が発見されたときに呼び出されます。
    *   以前は単に `itab` のアドレスと、その型が直接インターフェースかポインタなし型かを示すブール値がダンプされていました。
    *   変更後、`itab` が指すデータフィールドの型をダンプするように大幅に修正されました。
        *   `KindDirectIface` が0（間接インターフェース）の場合、データスロットは型 `t` へのポインタであるため、`t->ptrto` の型がダンプされます。
        *   `KindNoPointers` が0（ポインタのような型）の場合、データスロットは型 `t` そのものであるため、`t` の型がダンプされます。
        *   それ以外の場合（スカラー型）、`t` の型がダンプされます。
    *   この詳細な型情報のダンプは、コミットメッセージにある「Iface/Eface型は引き続きダンプされるので、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になるかもしれない」という意図を具体的に実現するものです。これにより、デバッグツールはインターフェースの動的な型をより正確に推論できるようになります。

これらの変更は、Go 1.4におけるランタイムのメモリ管理と型情報の扱いの進化を反映しており、ヒープダンプがより効率的かつ目的に合った情報を提供するように調整されたことを示しています。完全な型情報が失われた代わりに、ガベージコレクタが参照グラフを再構築するために必要な最小限のポインタ情報が提供されるようになっています。

## コアとなるコードの解説

このコミットの核心は、Goランタイムのヒープダンプメカニズムが、Go 1.4での内部的な型情報の管理方法の変更に適応するように更新された点にあります。

1.  **型情報の粒度変更と `dumpobj` の修正**:
    *   以前のGoバージョンでは、ヒープ上の各オブジェクトに対して完全な型情報がダンプされていました。これは、`dumpobj` 関数内で `dumpint(0); // Type*` と `dumpint(0); // kind` の行が存在していたことから推測できます（これらの行は、実際にはダミー値として型情報をダンプしていた可能性もありますが、型情報がヒープダンプのコンテキストで考慮されていたことを示します）。
    *   Go 1.4では、ヒープ内に完全な型情報を持たなくなったため、これらの行が削除されました。
    *   代わりに `dumpfields(bv);` が追加されました。`bv` は `BitVector` であり、これはオブジェクト内のどのオフセットにポインタが含まれているかを示すビットマップです。ガベージコレクタは、このポインタ/非ポインタマップを使用して、オブジェクト内の参照を正確に識別し、参照グラフを構築します。これにより、完全な型情報がなくても、ヒープの接続性を正確に表現できるようになります。

2.  **`itab_callback` の強化**:
    *   `itab_callback` は、インターフェーステーブル（`itab`）が発見されたときに呼び出される関数です。`itab` は、Goのインターフェースが具体的な型をどのように実装しているかを示す重要なランタイムデータ構造です。
    *   この関数の変更は、インターフェースが保持するデータフィールドの型情報をヒープダンプに含めることを目的としています。
    *   Goのインターフェースは、内部的に「型」と「値」のペアとして表現されます。
        *   `KindDirectIface == 0` の場合（間接インターフェース）、インターフェースの値はポインタであり、そのポインタが指す先の型が `t->ptrto` で表現されます。この場合、`t->ptrto` の型情報がダンプされます。
        *   `KindNoPointers == 0` の場合（ポインタのような型）、インターフェースの値は直接その型 `t` を保持します。この場合、`t` の型情報がダンプされます。
        *   それ以外の場合（スカラー型）、`t` の型情報がダンプされます。
    *   この詳細な型情報のダンプは、コミットメッセージにある「Iface/Eface型は引き続きダンプされるので、DWARF型情報と組み合わせることで、ヒープ内のほとんどの型の再構築が可能になるかもしれない」という意図を具体的に実現するものです。これにより、デバッグツールはインターフェースの動的な型をより正確に推論できるようになります。

3.  **グローバルセグメントのポインタマップダンプ**:
    *   `dumproots` 関数における `runtime·data` (データセグメント) と `runtime·bss` (BSSセグメント) のダンプ時に `dumpbvtypes` が追加されました。これは、これらのグローバルなメモリ領域についても、ガベージコレクタが参照を追跡するために必要なポインタ/非ポインタマップがヒープダンプに含まれるようになったことを意味します。これにより、グローバル変数からの参照も正確に追跡できるようになります。

これらの変更は、Go 1.4におけるランタイムのメモリ管理とGCの進化に合わせて、ヒープダンプがより効率的かつ有用な情報を提供するように調整されたことを示しています。完全な型情報がヒープから削除されたとしても、ポインタ/非ポインタマップとインターフェースの型情報を組み合わせることで、デバッグツールは引き続きヒープの状態を深く分析できるようになっています。

# [インデックス 22089] ファイルの概要

このコミットは、`go install` コマンドがツール（アセンブラやコンパイラなど）をビルド中に、それらのツールが同時に実行されることによって発生する可能性のある問題を解決します。具体的には、ツールのインストールをビルドプロセスの最後に遅延させることで、実行中のツールが上書きされるのを防ぎます。

## 元コミット内容

```
[dev.cc] cmd/go: do not install tools while executing them
```

## 変更の背景

Goのビルドシステムでは、`go install` コマンドがパッケージをビルドし、その結果生成される実行可能ファイルやライブラリをGOPATHのbinディレクトリやpkgディレクトリにインストールします。このプロセスにおいて、Go自身が使用するツール（例えば、アセンブラ、コンパイラ、リンカ、あるいは `cmd/cgo` のような特殊なツール）もGoのソースツリーの一部としてビルド・インストールされることがあります。

問題は、これらのツールがビルドプロセス中に自身を更新しようとする場合に発生します。例えば、`go install` が `cmd/go` 自身をビルドし、同時にそのビルドプロセスで `cmd/go` が実行されているような状況です。この場合、実行中のバイナリが上書きされる可能性があり、予期せぬ動作、ビルドの失敗、あるいは破損したバイナリの生成につながる可能性があります。

このコミットは、このような競合状態を避けるために導入されました。特に、ビルド中に実行される可能性のあるツール（`goTools` マップで定義されるもの）のインストールを、ビルドプロセスの他のステップが完了した後、つまりそれらのツールがもはや実行されていないと安全に仮定できる時点まで遅延させることで、この問題を解決します。

## 前提知識の解説

*   **`go install` コマンド**: Goのソースコードをコンパイルし、生成されたバイナリ（実行可能ファイルやライブラリ）をGOPATHまたはGoモジュールのキャッシュディレクトリにインストールするコマンドです。実行可能ファイルは `$GOPATH/bin` または `$GOBIN` に、パッケージアーカイブは `$GOPATH/pkg` に配置されます。
*   **Goツールチェイン**: Go言語のプログラムをビルド、テスト、実行するために必要な一連のツール群です。これには、`go` コマンド自体、コンパイラ (`cmd/compile`)、アセンブラ (`cmd/asm`)、リンカ (`cmd/link`)、Cgoツール (`cmd/cgo`) などが含まれます。これらのツールはGoのソースコードで書かれており、Goのビルドシステムによってビルドされます。
*   **`cmd/cgo`**: Cgoは、GoプログラムからC言語のコードを呼び出すためのメカニズムを提供します。`cmd/cgo` は、Cgoを使用するGoパッケージをビルドする際にGoツールチェインによって内部的に呼び出されるツールです。その性質上、Goのビルドプロセス中に頻繁に実行される可能性があります。
*   **ビルドグラフとアクション**: Goのビルドシステムは、パッケージ間の依存関係を解決し、ビルドの順序を決定するために内部的にビルドグラフを構築します。各ビルドステップは「アクション」として表現され、依存関係が解決された順に実行されます。
*   **競合状態 (Race Condition)**: 複数のプロセスやスレッドが共有リソース（この場合はファイルシステム上のバイナリファイル）に同時にアクセスしようとしたときに、そのアクセス順序によって結果が非決定的に変わってしまう状態を指します。このコミットの背景にあるのは、実行中のツールが自身を上書きしようとすることによるファイルアクセスの競合です。

## 技術的詳細

この変更は、`src/cmd/go/build.go` ファイル内の `runInstall` 関数に焦点を当てています。`runInstall` は `go install` コマンドの主要なロジックを処理します。

変更の核心は、ビルド対象のパッケージがGoツールであるかどうかを識別し、もしそうであればそのインストールアクションを遅延させるメカニズムを導入した点にあります。

1.  **`goTools` マップの利用**: Goツールとして扱われるパッケージのインポートパスを定義する `goTools` という内部マップが存在します。このマップは、特定のパッケージがGoツールチェインの一部であることを示します。
2.  **ツールの識別と遅延**:
    *   `runInstall` 関数は、インストール対象の各パッケージ `p` に対して `b.action(modeInstall, modeInstall, p)` を呼び出し、インストールアクションを生成します。
    *   新しく追加されたロジックは、`goTools[p.ImportPath] == toTool` という条件で、現在のパッケージ `p` がGoツールであるかどうかをチェックします。
    *   さらに、`p.ImportPath != "cmd/cgo"` という条件が追加されています。これは、`cmd/cgo` が特殊なケースとして扱われることを意味します。`cmd/cgo` は、ビルド中に自身が使用されることが非常に多いため、そのビルドと使用が同じ `go install` コマンド内で安全に行われるように、`b.action` 内で特別に処理されています。したがって、`cmd/cgo` はこの遅延インストールの対象外とされます。
    *   もしパッケージが `cmd/cgo` 以外のGoツールである場合、そのインストールアクション (`action`) はすぐに `a.deps` (メインのアクションの依存関係) に追加されません。代わりに、そのアクションの依存関係 (`action.deps`) がメインのアクション (`a`) の依存関係に追加され、そしてそのツールのアクション自体は `tools` という新しいスライスに一時的に格納されます。
    *   さらに重要なのは、`action.deps = append(action.deps, a)` という行です。これは、ツールのインストールアクションが、メインのビルドアクション `a` に依存するように設定されることを意味します。これにより、メインのビルドが完了するまでツールのインストールが実行されないことが保証されます。
3.  **遅延されたツールの実行**:
    *   すべてのパッケージの処理が完了した後、`if len(tools) > 0` の条件で、遅延されたツールが存在するかどうかがチェックされます。
    *   もし存在する場合、新しい `action` オブジェクトが作成され、その `deps` に遅延されたすべてのツールのアクションが追加されます。これにより、これらのツールはメインのビルドが完了した後にまとめてインストールされることになります。
    *   最終的に、`b.do(a)` が呼び出され、構築されたアクショングラフが実行されます。このグラフには、通常のパッケージのインストールと、遅延されたツールのインストールが含まれます。

このメカニズムにより、Goツールがビルド中に実行される可能性のある他のビルドステップと競合することなく、安全にビルドおよびインストールされるようになります。

## コアとなるコードの解説

変更は `src/cmd/go/build.go` ファイルの `runInstall` 関数内で行われています。

1.  **`var tools []*action` の追加**:
    *   これは、インストールを遅延させる必要のあるGoツールのアクションを一時的に保持するためのスライスです。

2.  **ループ内の条件分岐の追加**:
    *   元のコードでは、各パッケージ `p` のインストールアクション `b.action(...)` が直接 `a.deps` に追加されていました。
    *   変更後、`action := b.action(modeInstall, modeInstall, p)` でまずアクションが生成されます。
    *   `if goTools[p.ImportPath] == toTool && p.ImportPath != "cmd/cgo"`:
        *   この条件は、現在のパッケージ `p` がGoツールであり（`goTools` マップで識別される）、かつ `cmd/cgo` ではない場合に真となります。
        *   `goTools` はGoツールチェインのコンポーネント（例: `cmd/compile`, `cmd/asm`, `cmd/link` など）のインポートパスをキーとして持つマップです。`toTool` はそのマップの値として使用される定数で、そのパッケージがツールであることを示します。
        *   `cmd/cgo` が除外されているのは、前述の通り、`cmd/cgo` はビルド中に頻繁に実行されるため、`b.action` 内で特別に処理され、同じ `go install` コマンド内でビルドと使用が安全に行われるように設計されているためです。
    *   **ツールの場合の処理**:
        *   `a.deps = append(a.deps, action.deps...)`: ツールのインストールアクション自体ではなく、そのツールの依存関係（例えば、ツールのビルドに必要なライブラリなど）がメインのアクション `a` の依存関係に追加されます。これにより、ツールのビルド自体はメインのビルドプロセスの一部として行われます。
        *   `action.deps = append(action.deps, a)`: **これが最も重要な変更点です。** ツールのインストールアクション (`action`) が、メインのビルドアクション `a` に依存するように設定されます。これにより、メインのビルドアクション `a` が完了するまで、ツールのインストールアクションは実行されません。
        *   `tools = append(tools, action)`: ツールのインストールアクション自体は `tools` スライスに格納され、後でまとめて処理されます。
        *   `continue`: 現在のパッケージの処理をスキップし、次のパッケージに移ります。
    *   **ツールではない場合の処理**:
        *   `a.deps = append(a.deps, action)`: パッケージがGoツールではない場合、または `cmd/cgo` である場合は、以前と同様にそのインストールアクションが直接 `a.deps` に追加されます。

3.  **遅延されたツールの最終的な処理**:
    *   `if len(tools) > 0`: すべてのパッケージのループが終了した後、`tools` スライスに要素（遅延されたツールのアクション）が存在するかどうかを確認します。
    *   `a = &action{ deps: tools, }`: もし遅延されたツールが存在する場合、メインのアクション `a` が新しいアクションオブジェクトで上書きされます。この新しいアクションオブジェクトの依存関係は、遅延されたすべてのツールのアクションになります。これにより、これらのツールはメインのビルドが完了した後に、まとめてインストールされることが保証されます。

この変更により、`go install` はGoツールチェインのコンポーネントをビルドする際に、それらが実行中のバイナリを上書きするリスクを回避し、より堅牢なビルドプロセスを実現しています。

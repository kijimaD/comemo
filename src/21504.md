# [インデックス 21504] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/5a`, `cmd/6a`, `cmd/8a`, `cmd/9a`）におけるエラーハンドリングの改善と、`nacl`（Native Client）環境におけるスタックアライメントの問題修正を目的としています。具体的には、アセンブラがエラーを検出した場合に確実に終了コードを返すようにし、また`runtime`パッケージ内の特定の関数でスタックサイズを調整しています。

## コミット

`cmd/5a`, `cmd/6a`, `cmd/8a`, `cmd/9a` の各アセンブラにおいて、終了前にエラーカウンタ `nerrors` を確認し、エラーが存在する場合は `errorexit()` を呼び出すように変更されました。これにより、アセンブラがエラーを検出しても正常終了してしまう問題を修正します。

また、`src/runtime/asm_amd64p32.s` 内の `runtime·memhash_varlen` 関数のスタックサイズが `$20-12` から `$24-12` に変更されました。これは、`nacl`環境で発生していたスタックアライメントの不整合を修正するためのものです。

## 変更の背景

この変更の背景には、主に以下の2つの問題がありました。

1.  **アセンブラのエラーハンドリングの不備**: Goのアセンブラ（`5a`, `6a`, `8a`, `9a` はそれぞれARM、x86-64、x86、PPC64アーキテクチャ向けのアセンブラを指します）が、アセンブル中にエラーを検出しても、そのエラーが適切に終了コードに反映されず、プロセスが正常終了してしまう可能性がありました。これは、ビルドシステムやCI/CDパイプラインにおいて、アセンブルエラーを見落とす原因となり、後続の処理が誤って成功と判断されるリスクをはらんでいました。`nerrors` はコンパイル/アセンブル中に発生したエラーの数を追跡するグローバル変数であり、これが0より大きい場合はエラーが発生していることを意味します。

2.  **NaCl環境でのスタックアライメント問題**: Goのランタイムは、特定のプラットフォーム（この場合はGoogle Native Client, `nacl`）において、スタックのアライメントに関する問題に直面していました。スタックアライメントは、プロセッサがメモリからデータを効率的に読み書きするために、特定のメモリアドレス境界にデータを配置する要件です。不適切なスタックアライメントは、パフォーマンスの低下や、最悪の場合、セグメンテーション違反などのクラッシュを引き起こす可能性があります。このコミットでは、`runtime·memhash_varlen` 関数が`nacl`環境で不適切なスタックサイズを使用しており、それがスタックアライメントの問題を引き起こしていたことが判明しました。

これらの問題は、Goのツールチェインの堅牢性と、特定のプラットフォームでの安定性に影響を与えるため、修正が必要とされました。特に、`Fixes #9539` という記述から、GitHubのIssue #9539で報告された問題に対応していることがわかります。

## 前提知識の解説

### Goのアセンブラ (`cmd/5a`, `cmd/6a`, `cmd/8a`, `cmd/9a`)

Go言語は、そのコンパイラツールチェインの一部として、独自のアセンブラを持っています。これらは、Goのソースコードを最終的な機械語に変換する過程で、アセンブリ言語のコードを処理するために使用されます。
*   `cmd/5a`: ARMアーキテクチャ向けのアセンブラ
*   `cmd/6a`: x86-64アーキテクチャ向けのアセンブラ
*   `cmd/8a`: x86アーキテクチャ向けのアセンブラ
*   `cmd/9a`: PowerPC 64-bitアーキテクチャ向けのアセンブラ

これらのアセンブラは、Goの標準ライブラリやランタイムの一部がアセンブリ言語で書かれているため、Goプログラムのビルドに不可欠です。

### `nerrors` と `errorexit()`

*   `nerrors`: Goのコンパイラやアセンブラのようなツールにおいて、コンパイル/アセンブル中に発生したエラーの数をカウントするためのグローバル変数です。この変数の値が0より大きい場合、何らかのエラーが発生したことを示します。
*   `errorexit()`: エラーが発生した場合にプログラムを終了させるための関数です。通常、非ゼロの終了コードを返して、呼び出し元のプロセス（シェルスクリプトなど）にエラーがあったことを通知します。

### スタックアライメント

スタックアライメントとは、関数呼び出し時にスタックフレームが特定のバイト境界に配置されることを保証するプロセッサの要件です。多くのアーキテクチャ（特にx86-64）では、パフォーマンス上の理由から、スタックポインタが16バイトや8バイトの倍数にアライメントされていることを期待します。これは、SIMD命令（SSEなど）が特定のメモリアライメントを要求するため、または単にメモリアクセスを高速化するためです。

関数が呼び出されると、その関数のローカル変数やレジスタの退避領域などがスタック上に確保されます。このスタックフレームのサイズが適切に計算され、アライメント要件を満たすように配置されないと、以下のような問題が発生します。
*   **パフォーマンスの低下**: アライメントされていないメモリアクセスは、アライメントされているアクセスよりも遅くなることがあります。
*   **クラッシュ**: 一部のプロセッサやオペレーティングシステムでは、アライメントされていないメモリアクセスがハードウェア例外（例: セグメンテーション違反）を引き起こし、プログラムがクラッシュする原因となります。

### Google Native Client (NaCl)

Google Native Client (NaCl) は、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行するためのサンドボックス技術です。Go言語はNaClをターゲットプラットフォームの一つとしてサポートしており、GoプログラムをNaCl環境で実行できるようにコンパイルできます。NaCl環境では、セキュリティと安定性を確保するために、通常のOS環境とは異なる特定の制約や要件（スタックアライメントなど）が存在することがあります。

## 技術的詳細

### アセンブラのエラーハンドリング修正

Goのアセンブラの`main`関数では、アセンブル処理（`assemble(argv[0])`）が完了した後、`Bflush(&bstdout)` で標準出力バッファをフラッシュし、`exits(0)` で正常終了していました。しかし、この時点では`nerrors`変数の値がチェックされていませんでした。

このコミットでは、`Bflush(&bstdout);` の直後に以下のコードが追加されました。

```c
    if(nerrors > 0)
        errorexit();
```

これにより、アセンブル処理中に一つでもエラー（`nerrors > 0`）が発生していた場合、`exits(0)` で正常終了する前に `errorexit()` が呼び出され、アセンブラがエラーを示す終了コードで終了するようになります。これは、ビルドプロセスの信頼性を高め、アセンブルエラーがサイレントに無視されることを防ぎます。

### `runtime·memhash_varlen` のスタックサイズ調整

`src/runtime/asm_amd64p32.s` は、x86-64アーキテクチャで32ビットポインタを使用する環境（amd64p32、主にNaCl環境）向けのランタイムアセンブリコードです。

変更された行は以下の通りです。

```diff
-TEXT runtime·memhash_varlen(SB),NOSPLIT,$20-12
+TEXT runtime·memhash_varlen(SB),NOSPLIT,$24-12
```

ここで、`TEXT`ディレクティブはアセンブリ関数の定義を開始します。
*   `runtime·memhash_varlen(SB)`: 関数名。`SB`はStatic Baseを意味し、シンボルが静的セグメントにあることを示します。
*   `NOSPLIT`: この関数がスタックを分割しないことを示します。
*   `$20-12` または `$24-12`: これはスタックフレームのサイズと引数のサイズを示します。
    *   `$20` または `$24`: 関数が使用するスタックフレームの合計サイズ（ローカル変数、レジスタ退避領域など）。
    *   `-12`: 関数に渡される引数の合計サイズ。

元の `$20-12` は、スタックフレームサイズが20バイトであることを意味します。しかし、x86-64アーキテクチャでは、スタックポインタが16バイト境界にアライメントされていることが一般的です。20バイトは16の倍数ではないため、スタックアライメントの要件を満たしていませんでした。

新しい `$24-12` は、スタックフレームサイズが24バイトであることを意味します。24は16の倍数ではありませんが、関数が呼び出される直前のスタックポインタが16バイトアライメントされている場合、24バイトのスタックフレームを確保しても、次の関数呼び出し時のスタックポインタが再び16バイトアライメントされるように調整されることがあります。

この特定の変更は、`memhash_varlen` 関数が内部で別の関数を呼び出す際に、その呼び出し先の関数のスタックアライメント要件を満たせるように、自身のスタックフレームサイズを調整したものです。コミットメッセージにある「unaligned stack size for nacl that is caught by this change」という記述は、このスタックサイズ変更によって、NaCl環境でのスタックアライメントの問題が修正されたことを示しています。これは、コンパイラやリンカがスタックアライメントのチェックを強化した結果、この不整合が検出され、修正に至った可能性が高いです。

## コアとなるコードの変更箇所

### `src/cmd/5a/lex.c`, `src/cmd/6a/lex.c`, `src/cmd/8a/lex.c`, `src/cmd/9a/lex.c`

これらのファイルでは、`main`関数の最後に以下の行が追加されています。

```diff
--- a/src/cmd/5a/lex.c
+++ b/src/cmd/5a/lex.c
@@ -122,6 +122,8 @@ main(int argc, char *argv[])
 	if(assemble(argv[0]))
 		errorexit();
 	Bflush(&bstdout);
+	if(nerrors > 0)
+		errorexit();
 	exits(0);
 }
```

### `src/runtime/asm_amd64p32.s`

このファイルでは、`runtime·memhash_varlen` 関数のスタックフレームサイズが変更されています。

```diff
--- a/src/runtime/asm_amd64p32.s
+++ b/src/runtime/asm_amd64p32.s
@@ -645,7 +645,7 @@ TEXT runtime·cputicks(SB),NOSPLIT,$0-0
 // memhash_varlen(p unsafe.Pointer, h seed) uintptr
 // redirects to memhash(p, h, size) using the size
 // stored in the closure.
-TEXT runtime·memhash_varlen(SB),NOSPLIT,$20-12
+TEXT runtime·memhash_varlen(SB),NOSPLIT,$24-12
 	GO_ARGS
 	NO_LOCAL_POINTERS
 	MOVL	p+0(FP), AX
```

## コアとなるコードの解説

### アセンブラのエラーハンドリング

各アセンブラの`main`関数に追加された`if(nerrors > 0) errorexit();`は、アセンブル処理が完了した後に、グローバル変数`nerrors`をチェックします。もし`nerrors`が0より大きい（つまり、アセンブル中にエラーが発生した）場合、`errorexit()`関数が呼び出され、プログラムはエラーを示す終了コードで終了します。これにより、アセンブルエラーがビルドシステムに適切に伝達されるようになります。

### `runtime·memhash_varlen` のスタックサイズ変更

`TEXT runtime·memhash_varlen(SB),NOSPLIT,$24-12` の変更は、`runtime·memhash_varlen` 関数が使用するスタックフレームのサイズを20バイトから24バイトに増やしたことを意味します。この調整は、特にNaCl環境のような特定のプラットフォームで、スタックアライメントの要件を満たすために行われました。スタックフレームのサイズを調整することで、関数呼び出し規約やプロセッサの要件に合致させ、ランタイムの安定性と正しい動作を保証します。`memhash_varlen`は、可変長データに対するハッシュ計算に関連する関数であり、その内部で他の関数を呼び出す際にスタックアライメントが重要になる可能性があります。

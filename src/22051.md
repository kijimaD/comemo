# [インデックス 22051] ファイルの概要

このコミットは、Goランタイムにおける`cputicks`関数のx86アーキテクチャ（386およびAMD64）での正確性を向上させるための修正です。具体的には、`RDTSC`（Read Time-Stamp Counter）命令がアウトオブオーダー実行によって不正確な結果を返す可能性がある問題に対し、`LFENCE`または`MFENCE`といったメモリバリア命令を`RDTSC`の前に挿入することで、命令の実行順序を強制し、より正確なCPUティックカウントを取得できるようにします。この修正は、Go issue #9729で報告された問題に対応するものです。

## 変更の背景

この変更の背景には、GoランタイムがCPUのティックカウントを取得するために使用する`RDTSC`命令の特性があります。`RDTSC`命令は、CPUのタイムスタンプカウンタ（TSC）の値を読み取ることで、非常に高精度な時間計測を可能にします。しかし、現代のCPUは性能向上のために「アウトオブオーダー実行（Out-of-Order Execution）」という技術を採用しています。これは、プログラムの記述順序とは異なる順序で命令を実行することで、CPUのパイプラインを効率的に利用するものです。

このアウトオブオーダー実行が`RDTSC`に影響を与え、正確なティックカウントの取得を妨げる可能性がありました。具体的には、`RDTSC`命令が、その前に実行されるべき他の命令が完了する前に実行されてしまうと、期待よりも早い時点のTSC値を読み取ってしまい、結果として「skewed results（歪んだ結果）」、つまり不正確な時間計測値が生成される問題が発生していました。

Go issue #9729では、この`cputicks`関数の不正確さが報告されており、特にベンチマークやプロファイリングなど、正確な時間計測が求められる場面で問題となっていました。このコミットは、この根本的な問題を解決し、`cputicks`が常に信頼性の高い値を提供するようにすることを目的としています。コミットメッセージにもあるように、Linuxカーネルも同様の問題に対処するために`rdtsc_barrier`のようなメカニズムを使用しており、この修正はそのアプローチに倣ったものです。

## 前提知識の解説

### RDTSC (Read Time-Stamp Counter)

`RDTSC`は、x86アーキテクチャのCPU命令で、CPU内部の64ビットのタイムスタンプカウンタ（TSC）の値を読み取ります。TSCはCPUのクロックサイクルごとにインクリメントされるカウンタであり、非常に高分解能な時間計測に利用されます。

### TSC (Time-Stamp Counter)

TSCは、CPUが起動してからのクロックサイクル数をカウントするレジスタです。現代のCPUでは、多くの場合「Invariant TSC」として実装されており、CPUの周波数スケーリング（省電力機能などによる周波数変更）の影響を受けずに一定の速度でインクリメントされます。これにより、TSCは壁時計時間（wall-clock time）の計測にも利用できるようになっています。

### CPUID

`CPUID`は、CPUのベンダー、モデル、サポートする機能（命令セット、キャッシュ情報など）を問い合わせるためのx86命令です。この命令は、特定のレジスタに値を設定して実行することで、CPUに関する様々な情報を取得できます。このコミットでは、CPUのベンダー（IntelかAMDか）を判別するために`CPUID`が使用されています。`CPUID`命令自体は、その前後の命令の実行順序を保証する「シリアライズ命令」としての特性も持っています。

### LFENCE (Load Fence) と MFENCE (Memory Fence)

これらはメモリバリア命令（またはメモリフェンス命令）と呼ばれるもので、CPUのメモリ操作の順序を制御するために使用されます。アウトオブオーダー実行によって命令の順序が入れ替わることを防ぎ、特定の命令が完了するまで次の命令の実行を待機させることができます。

*   **LFENCE (Load Fence)**: ロード操作（メモリからの読み込み）の順序を保証します。`LFENCE`より前のすべてのロード命令が完了するまで、`LFENCE`より後のロード命令や他の命令の実行を開始させません。`RDTSC`の前に`LFENCE`を置くことで、`RDTSC`が実行される前に、その前のすべての命令（特にメモリからのデータ読み込みを伴うもの）が完了していることを保証し、より正確なタイミング測定を可能にします。
*   **MFENCE (Memory Fence)**: ロード操作とストア操作（メモリへの書き込み）の両方の順序を保証する、より強力なメモリバリアです。`MFENCE`より前のすべてのロードおよびストア命令がグローバルに可視化（メモリにコミット）されるまで、`MFENCE`より後のロードおよびストア命令の実行を開始させません。Intel CPUでは`LFENCE`で十分な場合でも、AMD CPUでは`MFENCE`が必要となる場合があります。これは、CPUベンダーによってメモリモデルやアウトオブオーダー実行の挙動が異なるためです。

### x86/AMD64アーキテクチャにおけるRDTSCとメモリバリア

IntelとAMDのCPUでは、`RDTSC`命令とメモリバリア命令の挙動に微妙な違いがあります。特に、`RDTSC`のシリアライズ特性に関して、Intelは`LFENCE`で十分な場合が多いのに対し、AMDはより強力な`MFENCE`を必要とすることが知られています。このコミットでは、このベンダーごとの違いを考慮し、適切なメモリバリアを選択するロジックが導入されています。

## 技術的詳細

このコミットの核心は、`RDTSC`命令がアウトオブオーダー実行によって不正確な結果を返す問題を解決することにあります。現代のCPUは、命令レベルの並列性を高めるために、プログラムの論理的な順序とは異なる順序で命令を実行することがあります。`RDTSC`命令自体は、このようなアウトオブオーダー実行を停止させる「シリアライズ命令」ではありません。そのため、`RDTSC`が実行される前に、本来であれば先に完了しているべき命令がまだ実行中である場合、`RDTSC`は古い、または不正確なTSC値を読み取ってしまう可能性があります。

この問題を解決するために、メモリバリア命令が導入されます。メモリバリア命令は、CPUのパイプラインをフラッシュし、その命令より前のすべての命令が完了するまで、その命令より後の命令の実行を停止させる効果があります。

*   **`LFENCE`の利用**: Intel CPUの場合、`LFENCE`命令を`RDTSC`の直前に挿入することで、`RDTSC`が実行される前に、その前のすべてのロード命令が完了していることを保証します。これにより、`RDTSC`がより正確な時点のTSC値を読み取ることが期待できます。
*   **`MFENCE`の利用**: AMD CPUの場合、`LFENCE`だけでは不十分な場合があるため、より強力な`MFENCE`命令が使用されます。`MFENCE`は、ロードとストアの両方の操作をシリアライズするため、より厳密な順序付けを保証します。

このコミットでは、`CPUID`命令を使用してCPUのベンダーを判別し、それに応じて適切なメモリバリア命令（`LFENCE`または`MFENCE`）を動的に選択するロジックが追加されています。

1.  **CPUベンダーの判別**: `CPUID`命令を実行し、その結果からCPUベンダー文字列（"GenuineIntel"、"AuthenticAMD"など）を判別します。具体的には、`BX`, `DX`, `CX`レジスタに格納されるベンダーID文字列の断片を比較します。
2.  **`lfenceBeforeRdtsc`フラグ**: Intel CPUと判別された場合、`runtime·lfenceBeforeRdtsc`という新しいグローバル変数に`1`（true）を設定します。このフラグは、`cputicks`関数内で`LFENCE`を使用するか`MFENCE`を使用するかの判断に利用されます。
3.  **条件付きメモリバリア挿入**: `runtime·cputicks`関数内で、`lfenceBeforeRdtsc`フラグの値に基づいて、`LFENCE`または`MFENCE`命令が`RDTSC`の直前に挿入されます。
    *   `lfenceBeforeRdtsc`が`1`の場合（Intel CPUと判別された場合）は`LFENCE` (`0x0f 0xae 0xe8`) を挿入します。
    *   それ以外の場合（AMD CPUやその他のベンダーの場合）は`MFENCE` (`0x0f 0xae 0xf0`) を挿入します。
4.  **SSE2のチェック**: 386アーキテクチャのコードでは、`TESTL $0x4000000, runtime·cpuid_edx`という命令でSSE2命令セットが利用可能かどうかのチェックも行われています。これは、`MFENCE`命令がSSE2の一部として導入されたため、SSE2をサポートしない古いCPUでは`MFENCE`が利用できない可能性があるためです。ただし、このコミットの時点では、SSE2がない場合は`JEQ done`でフェンス命令をスキップするようになっています。これは、非常に古いCPUではフェンス命令がサポートされていない可能性を考慮しているものと思われます。

この修正により、`cputicks`関数は、CPUのアーキテクチャ特性を考慮した上で、より正確で信頼性の高いティックカウントを提供するようになります。コミットメッセージにあるように、Linuxカーネルの`rdtsc_barrier`も同様の目的でメモリバリアを使用しており、このGoランタイムの修正もそのベストプラクティスに沿ったものです。

## コアとなるコードの変更箇所

このコミットでは、主に以下の4つのファイルが変更されています。

1.  `src/runtime/asm_386.s`: 32ビットx86アーキテクチャのアセンブリコード。`runtime·rt0_go`関数と`runtime·cputicks`関数が変更されています。
2.  `src/runtime/asm_amd64.s`: 64ビットx86（AMD64）アーキテクチャのアセンブリコード。`runtime·rt0_go`関数と`runtime·cputicks`関数が変更されています。
3.  `src/runtime/runtime1.go`: Goランタイムの初期化に関するGoコード。`cpuid_ecx`と`cpuid_edx`の宣言が削除されています。
4.  `src/runtime/runtime2.go`: Goランタイムの主要なデータ構造とグローバル変数が定義されているGoコード。`cpuid_ecx`と`cpuid_edx`が再宣言され、新たに`lfenceBeforeRdtsc`変数が追加されています。

## コアとなるコードの解説

### `src/runtime/asm_386.s` および `src/runtime/asm_amd64.s`

これらのファイルでは、Goランタイムの初期化ルーチンである`runtime·rt0_go`と、CPUティックカウントを取得する`runtime·cputicks`関数に修正が加えられています。

#### `runtime·rt0_go`関数内の変更

`runtime·rt0_go`は、Goプログラムが起動する際に最初に実行されるアセンブリコードです。この関数内で、CPUのベンダーを判別し、`lfenceBeforeRdtsc`変数を設定するロジックが追加されました。

```assembly
	// Figure out how to serialize RDTSC.
	// On Intel processors LFENCE is enough. AMD requires MFENCE.
	// Don't know about the rest, so let's do MFENCE.
	CMPL	BX, $0x756E6547  // "Genu"
	JNE	notintel
	CMPL	DX, $0x49656E69  // "ineI"
	JNE	notintel
	CMPL	CX, $0x6C65746E  // "ntel"
	JNE	notintel
	MOVB	$1, runtime·lfenceBeforeRdtsc(SB)
notintel:
```

*   このコードブロックは、`CPUID`命令の実行後に配置されます。
*   `CPUID`命令を実行すると、`BX`, `DX`, `CX`レジスタにCPUベンダーID文字列が格納されます。Intel CPUの場合、この文字列は"GenuineIntel"となります。
*   `CMPL`命令と`JNE`命令の組み合わせで、`BX`, `DX`, `CX`レジスタの値が"GenuineIntel"のASCIIコードと一致するかどうかをチェックしています。
    *   `0x756E6547` は "Genu"
    *   `0x49656E69` は "ineI"
    *   `0x6C65746E` は "ntel"
*   もしCPUがIntel製であると判別された場合、`MOVB $1, runtime·lfenceBeforeRdtsc(SB)`によって、グローバル変数`runtime·lfenceBeforeRdtsc`に`1`（真）が設定されます。これは、後続の`cputicks`関数で`LFENCE`を使用すべきであることを示します。
*   Intel製でない場合（`JNE`で`notintel`にジャンプした場合）、`runtime·lfenceBeforeRdtsc`はデフォルト値（`0`または未初期化）のままとなり、`MFENCE`が使用されることになります。

#### `runtime·cputicks`関数内の変更

`runtime·cputicks`関数は、GoプログラムからCPUティックカウントを取得するために呼び出される関数です。この関数に、`RDTSC`命令の前に適切なメモリバリア命令を挿入するロジックが追加されました。

**386アーキテクチャ (`src/runtime/asm_386.s`)**

```assembly
TEXT runtime·cputicks(SB),NOSPLIT,$0-8
	TESTL	$0x4000000, runtime·cpuid_edx(SB) // no sse2, no mfence
	JEQ	done
	CMPB	runtime·lfenceBeforeRdtsc(SB), $1
	JNE	mfence
	BYTE	$0x0f; BYTE $0xae; BYTE $0xe8 // LFENCE
	JMP	done
mfence:
	BYTE	$0x0f; BYTE $0xae; BYTE $0xf0 // MFENCE
done:
	RDTSC
	MOVL	AX, ret_lo+0(FP)
	MOVL	DX, ret_hi+4(FP)
	RET
```

*   `TESTL $0x4000000, runtime·cpuid_edx(SB)`: `cpuid_edx`レジスタのビット26（`0x4000000`）をチェックしています。このビットはSSE2命令セットのサポートを示します。`MFENCE`命令はSSE2の一部として導入されたため、SSE2をサポートしない古いCPUでは`MFENCE`が利用できません。もしSSE2がサポートされていない場合（`JEQ done`）、フェンス命令はスキップされます。
*   `CMPB runtime·lfenceBeforeRdtsc(SB), $1`: `runtime·lfenceBeforeRdtsc`変数の値が`1`（Intel CPU）であるかをチェックします。
*   `JNE mfence`: もし`runtime·lfenceBeforeRdtsc`が`1`でなければ（つまり、Intel CPUでない場合）、`mfence`ラベルにジャンプし、`MFENCE`命令が実行されます。
*   `BYTE $0x0f; BYTE $0xae; BYTE $0xe8 // LFENCE`: `runtime·lfenceBeforeRdtsc`が`1`の場合、`LFENCE`命令のオペコードが直接挿入されます。
*   `JMP done`: `LFENCE`を実行した後、`done`ラベルにジャンプし、`RDTSC`命令の実行に進みます。
*   `mfence:`: `runtime·lfenceBeforeRdtsc`が`1`でない場合、ここにジャンプし、`MFENCE`命令のオペコードが直接挿入されます。
*   `RDTSC`: メモリバリア命令の後に、`RDTSC`命令が実行され、TSCの値が`EDX:EAX`レジスタペアに読み込まれます。
*   `MOVL AX, ret_lo+0(FP)` と `MOVL DX, ret_hi+4(FP)`: 読み込んだTSC値（64ビット）を、関数の戻り値としてスタックフレームに格納します。

**AMD64アーキテクチャ (`src/runtime/asm_amd64.s`)**

```assembly
TEXT runtime·cputicks(SB),NOSPLIT,$0-0
	CMPB	runtime·lfenceBeforeRdtsc(SB), $1
	JNE	mfence
	BYTE	$0x0f; BYTE $0xae; BYTE $0xe8 // LFENCE
	JMP	done
mfence:
	BYTE	$0x0f; BYTE $0xae; BYTE $0xf0 // MFENCE
done:
	RDTSC
	SHLQ	$32, DX
	ADDQ	DX, AX
	RET
```

*   AMD64版の`cputicks`も同様のロジックですが、386版にあったSSE2のチェックがありません。これは、AMD64アーキテクチャではSSE2が必須であるため、常に利用可能であることが前提となっているためです。
*   `RDTSC`命令の後に、`SHLQ $32, DX`と`ADDQ DX, AX`で、`EDX:EAX`レジスタペアに読み込まれた64ビットのTSC値を`RAX`レジスタに結合しています。これは、AMD64では64ビットレジスタを直接扱えるためです。

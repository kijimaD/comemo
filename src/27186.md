# [インデックス 27186] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) における最適化に関するものです。具体的には、プログラムがリフレクションを通じてメソッドを検査しない場合に、不要なメソッド型情報を削除することでバイナリサイズを削減します。

## 元コミット内容

Goのリンカ (`cmd/link`) がメソッドをプルーニング（削除）する際に、関連する `funcType` 情報も同時にプルーニングするように変更します。これにより、リフレクションを使用しないプログラムにおいて、不要なメソッド型情報を削除し、バイナリサイズを大幅に削減できます。例として、`addr2line` ツールで8.8%（310KB）のサイズ削減が報告されています。

将来的には、非エクスポートメソッドの `reflect.Method` の `Type` および `Func` フィールドを `nil` に設定する、より積極的な最適化も検討されていますが、これはAPIの変更と見なされる可能性があるため、このコミットではより安全な変更に留められています。

この変更は、Issue #6853 に関連しています。

## 変更の背景

Goプログラムのバイナリサイズは、特に組み込みシステムやサーバーレス環境など、リソースが限られた環境では重要な考慮事項となります。Goのバイナリには、実行に必要なコードだけでなく、デバッグ情報、シンボルテーブル、そしてリフレクションのための型情報など、様々なメタデータが含まれています。

このコミットの背景には、Goのリンカが不要なコードやデータを削除する「デッドコードエリミネーション（Dead Code Elimination）」のプロセスがあります。しかし、これまでのリンカは、メソッド自体が使用されていない場合でも、そのメソッドに関連する型情報（特に `funcType`）を完全に削除しきれていないケースがありました。

特に、`reflect` パッケージを使用しないプログラムでは、実行時にメソッドの型情報を動的に取得する必要がないため、これらの情報がバイナリに含まれていることは純粋なオーバーヘッドとなります。このコミットは、このオーバーヘッドを削減し、バイナリサイズを最適化することを目的としています。

## 前提知識の解説

1.  **Goのリンカ (`cmd/link`)**: Goコンパイラ (`cmd/compile`) が生成したオブジェクトファイル（`.o`）を結合し、実行可能なバイナリを生成するツールです。デッドコードエリミネーションやシンボル解決、リロケーション処理などを行います。
2.  **リフレクション (`reflect` パッケージ)**: 実行時に型情報を検査したり、値の操作を行ったりする機能を提供します。これにより、プログラムは自身の構造を動的に調べ、変更することができます。例えば、構造体のフィールド名を取得したり、メソッドを動的に呼び出したりする際に使用されます。
3.  **メソッド型情報 (`funcType`)**: Goのメソッドは、特定の型に関連付けられた関数です。リフレクションを通じてメソッドを検査できるようにするため、コンパイラとリンカはメソッドのシグネチャ（引数と戻り値の型）やレシーバの型などの情報をバイナリに埋め込みます。これらの情報が `funcType` として表現されることがあります。
4.  **デッドコードエリミネーション (Dead Code Elimination)**: プログラムの実行に不要なコードやデータを最終的なバイナリから削除する最適化手法です。リンカの主要な役割の一つであり、バイナリサイズの削減や起動時間の短縮に貢献します。
5.  **`reflect.Method` 構造体**: `reflect` パッケージでメソッドを表す構造体です。これにはメソッドの名前、型 (`Type` フィールド)、およびメソッドを呼び出すための関数ポインタ (`Func` フィールド) などが含まれます。
6.  **リロケーション (Relocation)**: リンカがオブジェクトファイルを結合する際に、シンボル参照を実際のメモリアドレスに解決するプロセスです。`R_METHOD` は、メソッドに関連する特定のリロケーションタイプを指します。
7.  **`runtime.uncommontype`**: Goの型システム内部で使用される構造体の一つで、型が持つメソッド情報などを保持します。

## 技術的詳細

このコミットの核心は、リンカのデッドコードエリミネーションプロセスを改善し、リフレクションが使用されない場合にメソッドの `funcType` 情報を積極的に削除することです。

Goのリンカは、プログラム内で到達可能な（使用されている）シンボルを追跡し、到達不可能なシンボルを削除します。メソッドの場合、そのメソッドが直接呼び出されるか、またはリフレクションを通じてアクセスされる可能性がある場合に「到達可能」と見なされます。

以前のリンカでは、メソッド自体が到達不可能と判断されても、そのメソッドに関連する型情報（特に `reflect.Method` 構造体の `Type` や `Func` フィールドが参照する `funcType`）がバイナリに残ってしまうことがありました。これは、これらの型情報が `R_METHOD` リロケーションによって参照されており、リンカがその参照を完全に解決または削除できていなかったためと考えられます。

この変更では、`deadcode.go` 内の `deadcodepass` 構造体と関連するロジックが修正され、`methodref` 構造体が拡張されました。

-   **`methodref` 構造体の変更**: 以前はメソッドの型情報へのリロケーションを2つ (`r0`, `r1`) しか保持していませんでしたが、`reflect.Method` 構造体の4つのフィールド (`mtyp`, `typ`, `ifn`, `tfn`) に対応する4つのリロケーション (`r [4]*Reloc`) を保持するように変更されました。これにより、リンカはメソッドの各部分への参照をより細かく制御できるようになります。
-   **`markMethod` と `markMethodType`**:
    -   `markMethod` は、メソッド全体が到達可能であるとマークし、そのメソッドに関連するすべてのリロケーション (`r[0]` から `r[3]`) を `R_ADDR` タイプに設定します。これは、メソッドが実際に使用される場合に、そのコードと型情報がバイナリに含まれることを保証します。
    -   `markMethodType` は新しく追加された関数で、メソッドの型情報 (`mtyp` と `typ`) のみ到達可能とマークします。これは、リフレクションが使用されるが、メソッドの実行可能なコード自体は不要な場合（例えば、メソッドのシグネチャだけを調べたい場合）に役立ちます。
-   **`deadcode` 関数のロジック変更**:
    -   `reflectSeen` フラグが導入され、プログラムが `reflect` パッケージの `Value.Method` を使用しているかどうかを追跡します。
    -   `DynlinkingGo()` のチェックが追加され、動的リンクの場合には `reflectSeen` を `true` に設定します。これは、動的リンクされたライブラリがエクスポートされたメソッドをリフレクションで呼び出す可能性があるためです。
    -   `reflectSeen` が `true` の場合、エクスポートされたメソッドやインターフェースメソッドは `markMethod` で完全にマークされます。
    -   `reflectSeen` が `true` でない場合、つまりリフレクションが使用されていないプログラムでは、`markMethodType` を使用してメソッドの型情報のみをマークするのではなく、`rem` に追加して削除対象とします。これにより、不要な型情報がバイナリから削除されます。
    -   `cleanupReloc` の呼び出しも、`methodref` の `r` 配列全体をループするように変更され、すべての関連リロケーションが適切に処理されるようになりました。
-   **`dextratypeData` の変更 (`reflect.go`)**: コンパイラ側で `runtime.method` 構造体のフィールドを埋め込む際に、`dsymptr` と `duintptr` を条件分岐で使い分けていた箇所が、常に `dmethodptr` を使用するように簡略化されました。これは、リンカ側でリロケーションの処理がより柔軟になったため、コンパイラ側での複雑な条件分岐が不要になったことを示唆しています。

この変更により、リフレクションを使用しないプログラムでは、メソッドのコードだけでなく、そのメソッドの型情報もリンカによって効果的に削除されるようになり、結果としてバイナリサイズが削減されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go` の変更

`dextratypeData` 関数は、コンパイラが型情報をバイナリに書き込む際に使用されます。特に、`runtime.method` 構造体（Goの内部でメソッドのメタデータを表現するために使われる）のフィールドを埋める役割を担います。

変更前は、`a.isym` と `a.tsym` (インターフェースメソッドと通常メソッドのシンボル) が `nil` かどうかで `dmethodptr` と `duintptr` を使い分けていました。`dsymptr` はシンボルへのポインタを書き込み、`duintptr` はゼロを書き込みます。

変更後は、常に `dmethodptr` を使用するように簡略化されています。これは、リンカ側 (`deadcode.go`) で `methodref` 構造体が4つのリロケーションを保持するように拡張され、各フィールドへの参照をより細かく制御できるようになったため、コンパイラ側で条件分岐によってゼロを埋め込む必要がなくなったことを示しています。リンカが不要な参照を後で削除できるようになるため、コンパイラは常にシンボルへのポインタを生成するだけでよくなりました。

### `src/cmd/link/internal/ld/deadcode.go` の変更

このファイルは、Goリンカのデッドコードエリミネーションロジックを実装しています。

1.  **`methodref` 構造体の変更**:
    -   変更前は `r0` と `r1` という2つの `*Reloc` フィールドを持っていました。これは、メソッドの型情報に関連する2つのリロケーションを指していました。
    -   変更後は `r [4]*Reloc` という配列を持つようになりました。これは、`reflect.Method` 構造体の `mtyp` (メソッドの型シグネチャ)、`typ` (レシーバを含まないメソッドの型)、`ifn` (インターフェースメソッドの関数ポインタ)、`tfn` (通常メソッドの関数ポインタ) の4つのフィールドに対応するリロケーションを保持します。これにより、リンカはメソッドの各部分への参照をより詳細に管理できるようになります。
    -   `mtyp()`, `typ()`, `ifn()`, `tfn()` というヘルパーメソッドが追加され、`r` 配列の各要素にアクセスしやすくなっています。

2.  **`deadcode` 関数の変更**:
    -   `reflectSeen` というブール変数が導入されました。これは、プログラムが `reflect.Value.Method` を使用しているかどうかを示すフラグです。このシンボルが到達可能であれば、リフレクションが使用されていると判断されます。
    -   `DynlinkingGo()` のチェックが追加されました。動的リンクの場合、エクスポートされたメソッドが外部からリフレクションで呼び出される可能性があるため、`reflectSeen` を `true` に設定し、メソッドの型情報を保持するようにします。
    -   メインのループ内で、`d.markableMethods` をイテレートする際に、`reflectSeen` の値に基づいてメソッドの処理が変わります。
        -   `reflectSeen` が `true` で、かつメソッドがエクスポートされているか、インターフェースメソッドである場合、`d.markMethod(m)` が呼び出されます。これはメソッドのコードとすべての型情報をバイナリに含めることを意味します。
        -   `reflectSeen` が `true` で、かつ上記の条件に合致しない場合（非エクスポートメソッドなど）、`d.markMethodType(m)` が呼び出されます。これはメソッドの型情報 (`mtyp` と `typ`) のみをマークし、メソッドの実行可能なコード (`ifn`, `tfn`) は削除対象とします。コミットメッセージにある「uncontroversial change」とはこの部分を指し、Go 1 と同様に `Type` と `Func` フィールドが埋められることを保証します。
        -   `reflectSeen` が `false` の場合、メソッドは `rem` リストに追加され、後で完全に削除されます。
    -   `cleanupReloc` の呼び出しが変更され、`m.r0` と `m.r1` ではなく、`m.r` 配列のすべてのリロケーションに対してループするようになりました。これにより、メソッドに関連するすべてのリロケーションが適切に処理され、不要なものが削除されます。

3.  **`markMethod` および `markMethodType` 関数の追加/変更**:
    -   `markMethod` は、`methodref` の `r` 配列のすべてのシンボルを到達可能とマークし、対応するリロケーションタイプを `obj.R_ADDR` に設定します。
    -   `markMethodType` は新しく追加され、`m.mtyp()` と `m.typ()` (メソッドの型情報) のシンボルのみを到達可能とマークします。これにより、リフレクションで型情報のみが必要な場合に、コード本体は削除しつつ型情報だけを残すことが可能になります。

4.  **`flood` 関数の変更**:
    -   `mpos` という変数が導入され、`runtime.uncommontype` の `R_METHOD` リロケーションを収集する際に、`methodref` の `r` 配列のどの位置にリロケーションを格納するかを追跡します。これにより、4つのリロケーションが正しく `methodref` 構造体に格納されるようになります。
    -   `panic` メッセージ内の `methods[i].r0.Sym.Name` が `methods[i].ifn().Name` に変更されました。これは、メソッド名の一致チェックを `ifn` (インターフェースメソッドの関数ポインタ) のシンボル名に対して行うように修正されたことを示します。

これらの変更により、リンカはリフレクションの使用状況に応じて、メソッドのコードと型情報の両方をよりきめ細かくプルーニングできるようになり、結果としてバイナリサイズの削減を実現しています。

# [インデックス 20225] ファイルの概要

このコミットは、Go言語のリンカである`liblink`において、特にSolaris環境での問題に対処するため、PC相対アドレッシング（Program Counter-relative addressing）を回避するメカニズムを導入するものです。具体的には、Solaris上の`libc.so`からの動的インポートシンボルに対して、PC相対アドレッシングではなく絶対アドレッシングを使用するように変更しています。

## 変更の背景

この変更の背景には、Solarisオペレーティングシステムにおける特定のリンキング（リンク処理）の挙動があります。Goのリンカ`liblink`は、通常、生成するコードにおいてPC相対アドレッシングを多用します。これは、実行可能ファイルがメモリ上のどこにロードされても正しく動作するようにするための、位置独立コード（Position-Independent Code, PIC）を生成する一般的な手法です。

しかし、Solaris環境では、`libc.so`のような共有ライブラリからの動的インポート関数を呼び出す際に、PC相対アドレッシングが問題を引き起こすことが判明しました。コミットメッセージには「For Solaris. Sigh.」とあり、これはこの問題がSolaris特有のものであり、開発者にとって頭の痛い問題であったことを示唆しています。具体的には、Solarisがこれらの関数をシステムコールではなく`.so`（共有オブジェクト）関数として呼び出す際に、Goリンカが生成するPC相対アドレッシングが期待通りに機能しない、あるいは互換性の問題を引き起こす可能性がありました。

この問題は、GoプログラムがSolaris上で正しく動作しない、またはクラッシュする原因となるため、Goのクロスプラットフォーム互換性を維持するために修正が必要でした。コミットコメントには「This is probably working around a Solaris-specific bug that should be fixed differently, but we don't know what that bug is. And this does fix it.」とあり、根本的な原因は不明ながらも、この変更が問題を解決するワークアラウンドとして機能していることが示されています。

## 前提知識の解説

### 1. PC相対アドレッシング (Program Counter-relative Addressing)

PC相対アドレッシングは、命令のオペランドがプログラムカウンタ（PC、または命令ポインタ）の現在の値からのオフセットとして指定されるアドレッシングモードです。

*   **仕組み**: 例えば、「PC + オフセット」という形式でメモリ上のアドレスを計算します。
*   **利点**:
    *   **位置独立コード (PIC)**: 実行可能ファイルがメモリ上の任意のアドレスにロードされても、コード内の参照が正しく解決されます。これは共有ライブラリや動的にロードされるモジュールで特に重要です。
    *   **コードのコンパクトさ**: 絶対アドレスを埋め込むよりも、短いオフセット値で済む場合があります。
*   **用途**: 分岐命令（ジャンプ、コール）や、データへのアクセス（特にグローバル変数や定数）によく使用されます。

### 2. 絶対アドレッシング (Absolute Addressing)

絶対アドレッシングは、命令のオペランドがメモリ上の物理的または仮想的な絶対アドレスを直接指定するアドレッシングモードです。

*   **仕組み**: 「アドレスX」という形式で直接メモリ上の位置を指定します。
*   **利点**: シンプルで直接的です。
*   **欠点**: コードがロードされるメモリ上の位置に依存するため、位置独立コードの生成には不向きです。

### 3. リンカ (Linker)

リンカは、コンパイラによって生成されたオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムや共有ライブラリを作成するツールです。

*   **主な役割**:
    *   **シンボル解決**: 異なるオブジェクトファイル間で参照される関数や変数のアドレスを解決します。
    *   **再配置 (Relocation)**: コード内のアドレス参照を、最終的なメモリ上の位置に合わせて調整します。PC相対アドレッシングや絶対アドレッシングの解決もここで行われます。
    *   **ライブラリの結合**: 静的ライブラリや共有ライブラリをプログラムにリンクします。

### 4. Go言語の`liblink`

`liblink`は、Go言語のツールチェインの一部である内部リンカライブラリです。Goのコンパイラ（`cmd/compile`）が生成したオブジェクトファイルをリンクし、実行可能バイナリを生成する役割を担っています。Goのリンカは、C言語のリンカ（例: GNU `ld`）とは異なり、Go独自の最適化やランタイムの要件に合わせて設計されています。

### 5. シンボルタイプ (`D_EXTERN`, `D_STATIC`)

Goのリンカ内部では、様々なシンボルタイプが定義されています。

*   `D_EXTERN`: 外部シンボル。他のコンパイル単位（通常は別のオブジェクトファイルや共有ライブラリ）で定義されている関数や変数への参照を示します。
*   `D_STATIC`: 静的シンボル。現在のコンパイル単位内で定義されているが、外部からは参照されない（ファイルスコープの）関数や変数を示します。

### 6. 再配置タイプ (`R_ADDR`, `R_PCREL`)

再配置タイプは、リンカがアドレス参照をどのように解決するかを指示します。

*   `R_ADDR`: 絶対アドレス再配置。シンボルが最終的にロードされる絶対アドレスを、指定された場所に書き込みます。
*   `R_PCREL`: PC相対再配置。シンボルが最終的にロードされるアドレスと、再配置が行われる命令のアドレスとの間のオフセットを計算し、そのオフセットを書き込みます。

### 7. Solarisと共有ライブラリ

Solarisは、UNIX系のオペレーティングシステムであり、共有ライブラリ（`.so`ファイル）の扱いに特定の慣習や実装の詳細があります。特に、システムコールや標準Cライブラリ（`libc.so`）の関数呼び出しにおいて、他のOS（Linuxなど）とは異なるリンキングの挙動を示すことがあります。この違いが、Goのリンカが生成するPC相対アドレッシングとSolarisの期待する挙動との間で不整合を引き起こしたと考えられます。

## 技術的詳細

このコミットは、`src/liblink/asm6.c`というファイルに変更を加えています。このファイルは、Goのリンカがx86-64アーキテクチャ（amd64）のコードを生成する際のアセンブラバックエンドの一部です。

変更の核心は、`isextern`という新しい静的関数の導入と、既存の`oclass`および`vaddr`関数の修正です。

### `isextern`関数の導入

```c
// isextern reports whether s describes an external symbol that must avoid pc-relative addressing.
// This happens on systems like Solaris that call .so functions instead of system calls.
// It does not seem to be necessary for any other systems. This is probably working
// around a Solaris-specific bug that should be fixed differently, but we don't know
// what that bug is. And this does fix it.
static int
isextern(LSym *s)
{
	// All the Solaris dynamic imports from libc.so begin with "libc·", which
	// the compiler rewrites to "libc." by the time liblink gets it.
	return strncmp(s->name, "libc.", 5) == 0;
}
```

*   この関数は、与えられたシンボル`s`が、PC相対アドレッシングを回避する必要がある外部シンボルであるかどうかを報告します。
*   コメントにあるように、これはSolarisのようなシステムで発生し、システムコールではなく`.so`関数を呼び出す場合に問題となります。
*   `strncmp(s->name, "libc.", 5) == 0`という条件で、シンボル名が"libc."で始まるかどうかをチェックしています。これは、Solarisの`libc.so`からの動的インポートシンボルが、コンパイラによって`libc·`から`libc.`に書き換えられるというGoツールチェインの内部的な知識に基づいています。つまり、`libc.`で始まるシンボルは、Solarisの`libc.so`からのインポートであると識別しています。

## コアとなるコードの変更箇所

変更は`src/liblink/asm6.c`ファイルに集中しています。

1.  **`isextern`関数の追加**:
    *   `static int isextern(LSym *s)`: シンボル名が "libc." で始まるかどうかをチェックし、Solarisの`libc.so`からのインポートであるかを識別します。

2.  **`oclass`関数の変更**:
    *   `D_EXTERN`または`D_STATIC`シンボルで`isextern`が真の場合、`Yi32`（絶対アドレス）を返すように変更。

3.  **`vaddr`関数の変更**:
    *   `isextern`が真のシンボルに対して、再配置タイプを`R_ADDR`（絶対アドレス再配置）に設定するように変更。

4.  **`asmandsz`関数の変更**:
    *   `D_EXTERN`または`D_STATIC`シンボルで`isextern`が真の場合の処理を追加し、PC相対アドレッシングのロジックから除外。

## コアとなるコードの解説

このコミットの核心は、Goのリンカが特定の外部シンボル（Solarisの`libc.so`からのインポート）を特別扱いし、PC相対アドレッシングではなく絶対アドレッシングでリンクするように強制することです。

*   **`isextern`**: この関数は、問題のあるシンボルを特定するための「フィルター」として機能します。Goのコンパイラが`libc·`を`libc.`に変換するという内部的な知識を利用して、SolarisのCライブラリ関数を正確に識別します。
*   **`oclass`と`vaddr`の連携**: `oclass`がシンボルのアドレッシングモードを決定し、`vaddr`がそのモードに基づいて実際の再配置タイプを設定します。`isextern`によって識別されたシンボルに対して、`oclass`は絶対アドレッシングを示唆する`Yi32`を返し、それに続いて`vaddr`が`R_ADDR`再配置タイプを設定することで、リンカは最終的にこれらのシンボルへの参照を絶対アドレスとして解決します。
*   **`asmandsz`の調整**: `asmandsz`は、アセンブリ命令の生成とオペランドの処理を担当します。ここでの変更は、`isextern`によって識別されたシンボルが、PC相対アドレッシングを前提とした既存のロジックによって誤って処理されないようにするためのガードレールとして機能します。これにより、リンカはこれらのシンボルに対して常に絶対アドレッシングのパスをたどるようになります。

この一連の変更により、GoのリンカはSolarisの特定のリンキング要件に適応し、GoプログラムがSolaris環境で安定して動作するようになりました。これは、Goが多様なプラットフォームで動作するための、低レベルかつプラットフォーム固有の調整の一例です。

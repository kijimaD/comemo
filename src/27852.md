## 変更の背景
このコミットは、Go言語の標準ライブラリに含まれる`hash/adler32`パッケージのパフォーマンスを向上させることを目的としています。Adler-32チェックサムは、データの整合性を迅速に検証するために設計されたアルゴリズムであり、特にデータ転送やストレージシステムにおいて、高速なチェックサム計算が求められる場面で利用されます。

元の実装では、Adler-32の計算がバイト単位でループ処理されていました。しかし、このような逐次的な処理は、ループ制御にかかるオーバーヘッドが大きくなる傾向があります。大量のデータを処理する際に、このオーバーヘッドがボトルネックとなり、全体のパフォーマンスを低下させる可能性があります。

コミットメッセージに示されているベンチマーク結果（`Adler32KB-4`で実行時間が24.49%短縮され、速度が32.41%向上）は、この最適化がAdler-32計算の効率を大幅に改善することを示しています。この性能向上は、Goアプリケーションがより高速にデータを処理できるようになることに貢献します。

## 前提知識の解説

### Adler-32チェックサム
Adler-32は、Mark Adlerによって1995年に開発されたチェックサムアルゴリズムです。CRC32（巡回冗長検査）と比較して、より高速な計算を特徴としますが、エラー検出能力はやや劣ります。主にzlib圧縮ライブラリなどでデータの整合性チェックに利用されています。

Adler-32は、2つの独立した16ビットのチェックサム`s1`と`s2`を計算し、最終的にこれらを組み合わせて32ビットのチェックサムを生成します。
*   `s1`は、入力データのすべてのバイトの合計を65521で割った余り（モジュロ）です。初期値は1です。
*   `s2`は、`s1`の中間値の合計を65521で割った余り（モジュロ）です。初期値は0です。

各入力バイト `D_i` に対して、以下の計算が繰り返されます。
1.  `s1 = (s1 + D_i) mod 65521`
2.  `s2 = (s2 + s1) mod 65521`

ここで使用される65521は、2^16未満の最大の素数であり、これにより特定のバイト差分の組み合わせを検出する能力が向上するとされています。

### ループアンローリング (Loop Unrolling)
ループアンローリングは、プログラムの最適化手法の一つで、ループの実行速度を向上させるために、ループの本体を複数回複製する技術です。これにより、ループの制御構造（カウンタのインクリメント、終了条件のチェック、分岐命令など）にかかるオーバーヘッドを削減します。

**利点:**
*   **ループオーバーヘッドの削減**: ループの反復回数が減るため、ループ制御に関連するCPUサイクルが節約されます。
*   **命令レベル並列性 (Instruction-Level Parallelism, ILP) の向上**: 複数の命令を同時に実行できる最新のCPUにおいて、アンローリングによってより多くの独立した命令が露出され、CPUの並列処理能力を最大限に活用できます。
*   **キャッシュ利用率の向上**: ループ制御命令が減ることで、より多くの「実質的な」計算命令が命令キャッシュに保持されやすくなり、キャッシュミスが減少します。
*   **分岐予測の精度向上**: ループ内の分岐命令の数が減るため、CPUの分岐予測ミスが減り、パイプラインストール（処理の停止）が減少します。

**欠点:**
*   **コードサイズの増加 (Code Bloat)**: ループ本体が複製されるため、生成されるバイナリコードのサイズが大きくなります。これは、命令キャッシュの効率に悪影響を与える可能性があります。
*   **可読性の低下**: 手動でアンローリングを行うと、コードが複雑になり、理解や保守が難しくなることがあります。
*   **レジスタ圧迫**: より多くの変数を同時に保持する必要がある場合、CPUのレジスタが不足し、メモリへの退避（スピル）が発生して性能が低下する可能性があります。

多くのコンパイラは、高い最適化レベルで自動的にループアンローリングを実行しますが、特定のアルゴリズムやハードウェア特性に合わせて手動でアンローリングを行うことで、さらなる性能向上が見込める場合があります。

## 技術的詳細
このコミットでは、Adler-32チェックサム計算の`update`関数において、ループアンローリングが適用されています。元の実装では、入力データ`p`の各バイトを`for _, x := range p`というGo言語のイテレーションループで処理していました。この変更では、このループを最適化し、一度に4バイトを処理する新しいループを追加しています。

具体的には、入力データ`p`の長さが4バイト以上ある間、以下の処理を繰り返します。
1.  `p[0]`、`p[1]`、`p[2]`、`p[3]`の各バイトに対して、Adler-32の`s1`と`s2`の更新計算を順次実行します。
2.  4バイトの処理が完了したら、`p`スライスを4バイト分進め、次の4バイトブロックの処理に移ります。

この4バイト単位での処理により、ループの反復回数が約1/4に削減され、ループ制御にかかるCPUサイクルが大幅に削減されます。Adler-32の計算は各バイトに依存するため、4バイトをまとめて処理する際も、各バイトごとに`s1`と`s2`の更新を順番に行う必要があります。このコミットのコードは、その順序を正しく維持しながらアンローリングを実現しています。

また、`BlockSize()`メソッドの戻り値が`1`から`4`に変更されています。これは、この`digest`型が一度に処理できる推奨ブロックサイズが4バイトになったことを外部に示唆するものです。これにより、`io.Reader`などのインターフェースを通じてデータを読み込む際に、4バイトのバッファサイズを使用することで、より効率的なデータ処理が可能になる可能性があります。

この最適化は、Adler-32計算の特性（各バイトが独立して`s1`に加算され、その結果が`s2`に加算される）と、現代のCPUのパイプライン処理能力を最大限に活用することで、顕著な性能向上を達成しています。

## コアとなるコードの解説

### `BlockSize()` メソッドの変更
`func (d *digest) BlockSize() int { return 4 }`
この変更により、`digest`型の`BlockSize()`メソッドが返す値が`1`から`4`になりました。`BlockSize()`は、ハッシュ関数が一度に処理できる推奨ブロックサイズを返します。この値を`4`に設定することで、このAdler-32実装が4バイト単位でデータを処理する際に最も効率的であることを外部に示します。これにより、このハッシュ関数を利用する側は、例えば`io.CopyBuffer`などで4バイトのバッファサイズを使用することで、より最適なパフォーマンスを引き出すことが期待できます。

### ループアンローリングの実装
```go
		for len(p) >= 4 {
			s1 += uint32(p[0])
			s2 += s1
			s1 += uint32(p[1])
			s2 += s1
			s1 += uint32(p[2])
			s2 += s1
			s1 += uint32(p[3])
			s2 += s1
			p = p[4:]
		}
```
この新しい`for`ループが、ループアンローリングの主要な部分です。
*   `for len(p) >= 4`: 入力データスライス`p`の残りの長さが4バイト以上である限り、このループが実行されます。
*   ループ内部では、`p[0]`、`p[1]`、`p[2]`、`p[3]`の4つのバイトに対して、Adler-32の`s1`と`s2`の更新計算が順次行われます。各バイトが`s1`に加算され、その新しい`s1`の値が`s2`に加算されるというAdler-32のアルゴリズムが、各バイトに対して正確に適用されています。
*   `p = p[4:]`: 4バイトの処理が完了した後、`p`スライスは先頭から4バイト分進められます。これにより、次のループ反復では、まだ処理されていないデータの次の4バイトブロックが対象となります。

このアンローリングされたループは、ループ制御（条件チェックとスライス更新）の回数を大幅に削減し、その結果、CPUの効率的な利用とパフォーマンス向上に繋がります。

### 残りのデータの処理
```go
		for _, x := range p {
			s1 += uint32(x)
			s2 += s1
			if s1 >= NMAX {
				s1 -= NMAX
			}
			if s2 >= NMAX {
				s2 -= NMAX
			}
		}
```
アンローリングされたループが終了した後、`p`スライスには0から3バイトの残りのデータが含まれる可能性があります。この残りのデータは、元の1バイトずつ処理するループ（`for _, x := range p`）によって処理されます。これにより、入力データの長さが4の倍数でなくても、すべてのバイトが正しくAdler-32チェックサム計算に組み込まれることが保証されます。

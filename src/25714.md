## 変更の背景

Go言語の`net/http`パッケージには、HTTPレスポンスの`Content-Type`ヘッダが提供されない場合や、提供されても信頼できない場合に、レスポンスボディの先頭バイトを調べてMIMEタイプを推測する「MIMEスニッフィング」の機能が備わっています。この機能は`http.DetectContentType`関数によって提供されます。

以前の`net/http`パッケージにおけるMP4ファイルのMIMEスニッフィングの実装は、WHATWG (Web Hypertext Application Technology Working Group) が策定するMIME Sniffing Standardの最新仕様に完全に準拠していませんでした。`src/net/http/sniff.go`内のコードには、MP4スニッフィングに関する`TODO`コメントが存在し、「MP4に関する仕様が整理されたら再有効化する」と記されていました。これは、当時のMP4スニッフィングロジックが不完全であるか、あるいは仕様の変更に対応できていなかったことを示唆しています。

このコミットは、この未解決の問題（おそらくIssue #8773で報告されていたもの）に対処し、WHATWG MIME Sniffing StandardのClause 6.2.1「Signature for MP4」に厳密に準拠するようにMP4スニッフィングロジックを更新することで、MP4ファイルの検出の正確性と信頼性を向上させることを目的としています。これにより、GoアプリケーションがHTTP経由でMP4コンテンツを扱う際に、より堅牢なMIMEタイプ検出が可能になります。

## 前提知識の解説

### MIMEスニッフィング (MIME Sniffing)

MIMEスニッフィングとは、データストリーム（特にHTTPレスポンスボディ）の先頭バイトを検査して、そのデータのMIMEタイプ（メディアタイプ）を推測するプロセスです。これは、HTTPレスポンスに`Content-Type`ヘッダが含まれていない場合や、ヘッダが誤っている、あるいは信頼できない場合に、Webブラウザや他のクライアントがコンテンツを正しく解釈・表示するために用いられます。

例えば、サーバーが`Content-Type: application/octet-stream`としてファイルを送信しても、クライアントがそのファイルがHTMLや画像であるとスニッフィングで判断すれば、それに応じた処理（HTMLとしてレンダリング、画像として表示など）を行います。しかし、MIMEスニッフィングはセキュリティ上のリスク（例: 悪意のあるHTMLが画像として偽装され、XSS攻撃に利用される可能性）も伴うため、WHATWGなどの標準化団体によって厳格なルールが定められています。

### Goの`net/http`パッケージにおけるMIMEスニッフィング

Goの標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。このパッケージには、`http.DetectContentType(data []byte)`という関数があり、これは与えられたバイトスライス`data`の先頭512バイトを調べて、そのMIMEタイプを推測します。

`DetectContentType`関数は、内部的に`sniffSignatures`という`[]sniffSig`型のスライスを使用します。`sniffSig`はインターフェースであり、`match(data []byte, firstNonWS int) string`メソッドを定義しています。このインターフェースを実装する具体的な型（例: `exactSig`, `htmlSig`, `mp4Sig`, `textSig`など）が、それぞれ特定のファイルタイプのシグネチャ検出ロジックをカプセル化しています。`DetectContentType`は`sniffSignatures`内の各シグネチャを順番に試行し、最初にマッチしたMIMEタイプを返します。

### MP4ファイルフォーマットの基本的な構造

MP4 (MPEG-4 Part 14) は、ISO Base Media File Format (ISO/IEC 14496-12) に基づくマルチメディアコンテナフォーマットです。このフォーマットの基本的な特徴は、データが「ボックス」（または「アトム」）と呼ばれる構造の階層で構成されている点です。

*   **ボックス (Box / Atom)**: MP4ファイルのすべてのデータはボックス内に格納されます。各ボックスは、そのボックスのサイズを示す4バイトのフィールドと、ボックスのタイプを示す4バイトのフィールド（例: `ftyp`, `moov`, `mdat`など）で始まります。
*   **`ftyp` (File Type Box)**: MP4ファイルの先頭近くに必ず存在する重要なボックスです。このボックスは、ファイルが準拠している仕様（メジャーブランド）と、互換性のある他の仕様（互換ブランド）を定義します。`ftyp`ボックスの構造は以下のようになっています。
    *   `Size` (4バイト): ボックス全体のサイズ。
    *   `Type` (4バイト): `ftyp`というASCII文字列。
    *   `Major Brand` (4バイト): ファイルの主要なブランド（例: `mp42`, `isom`）。
    *   `Minor Version` (4バイト): メジャーブランドのマイナーバージョン。
    *   `Compatible Brands` (4バイトの繰り返し): ファイルが互換性を持つ他のブランドのリスト（例: `mp41`, `mp42`, `isom`, `avc1`など）。

MIMEスニッフィングでは、この`ftyp`ボックスの存在と内容を検査することで、ファイルがMP4であるかどうかを判断します。

### WHATWG MIME Sniffing Standard

WHATWG MIME Sniffing Standardは、WebブラウザがリソースのMIMEタイプを決定するための詳細なアルゴリズムを定義しています。この標準は、異なるブラウザ間でのMIMEタイプ検出の一貫性を確保し、セキュリティリスクを軽減することを目的としています。

特に、Clause 6.2.1「Signature for MP4」は、バイトストリームがMP4ファイルのシグネチャに一致するかどうかを判断するための具体的なステップを規定しています。このコミットは、この仕様に厳密に準拠するようにGoのMP4スニッフィングロジックを調整しています。

## 技術的詳細

このコミットの主要な変更は、`src/net/http/sniff.go`内の`mp4Sig`型の実装と、`src/net/http/sniff_test.go`内の関連するテストケースにあります。

### `sniff.go`の変更点

1.  **`sniffSignatures`スライスへの`mp4Sig`の追加**:
    以前は`// TODO(dsymonds): Re-enable this when the spec is sorted w.r.t. MP4.`というコメントと共に`//mp4Sig(0),`がコメントアウトされていました。このコミットでは、このコメントが削除され、`mp4Sig{}`が`sniffSignatures`スライスに正式に追加されました。これは、MP4スニッフィングが仕様に準拠し、有効化されたことを意味します。
    また、`textSig(0)`も`textSig{}`に変更されています。これは、`mp4Sig`と同様に`textSig`も状態を持たないため、`int`型のダミー引数を渡す必要がなくなり、空の構造体リテラルで十分になったためです。

2.  **`mp4Sig`型の変更**:
    `type mp4Sig int`から`type mp4Sig struct{}`に変更されました。これは、`mp4Sig`がMIMEスニッフィングのロジックを実行する際に、特定のインスタンス状態を必要としないためです。空の構造体はメモリを消費せず、単に`sniffSig`インターフェースを実装するためのプレースホルダーとして機能します。

3.  **`mp4Sig.match`メソッドのロジック更新**:
    これが最も重要な変更点です。WHATWG MIME Sniffing StandardのClause 6.2.1に厳密に準拠するようにロジックが修正されました。

    *   **データ長のチェック**:
        `if len(data) < 8`から`if len(data) < 12`に変更されました。
        WHATWG仕様のClause 6.2.1ステップ3では、「バイトシーケンスの長さが12未満の場合、falseを返す」と規定されています。これは、MP4ファイルの`ftyp`ボックスの`size` (4バイト)、`type` (`ftyp`, 4バイト)、`major_brand` (4バイト) を読み込むために最低12バイトが必要であるためです。以前の8バイトでは`major_brand`までを確実に読み込めませんでした。

    *   **`boxSize`の読み取りと検証**:
        `boxSize := int(binary.BigEndian.Uint32(data[:4]))`で、データの先頭4バイトをビッグエンディアンの符号なし32ビット整数として解釈し、最初のボックスのサイズを取得します。
        その後の`if boxSize < 8 || boxSize > len(data) || boxSize%4 != 0`というチェックは、WHATWG仕様のClause 6.2.1ステップ5に相当します。
        *   `boxSize < 8`: `ftyp`ボックスの最小サイズは8バイト（サイズとタイプのみ）ですが、実際には`major_brand`と`minor_version`を含むため、通常は16バイト以上です。このチェックは不正な`boxSize`を早期に検出します。
        *   `boxSize > len(data)`: 読み込めるデータ量を超えている場合、不正なボックスサイズと判断します。
        *   `boxSize%4 != 0`: MP4のボックスサイズは通常4の倍数であるため、このチェックも不正なデータを検出するのに役立ちます。

    *   **`ftyp`ボックスの検出**:
        `if !bytes.Equal(data[4:8], mp4ftype)`という行で、データの5バイト目から8バイト目（インデックス4から7）が`mp4ftype`（`ftyp`のバイト表現）と一致するかを確認します。これは、最初のボックスが`ftyp`ボックスであることを確認する重要なステップです。

    *   **互換ブランドのチェックの簡素化**:
        以前のコードでは、`ftyp`ボックス内の互換ブランド（`compatible_brands`）をループで走査し、`"mp4"`, `"iso"`, `"M4V"`, `"M4P"`, `"M4B"`などの複数の文字列と照合していました。また、`M4A`, `3gp`, `jp2`などのコメントアウトされたロジックも存在しました。
        このコミットでは、このロジックが大幅に簡素化され、`if bytes.Equal(data[st:st+3], mp4)`という行で、互換ブランドが`mp4`（`mp4`のバイト表現）と一致するかどうかのみをチェックするようになりました。
        これは、WHATWG仕様のClause 6.2.1では、`ftyp`ボックスの`compatible_brands`リストに`mp4`ブランドが含まれていることをMP4シグネチャの条件としているためです。他のブランド（`iso`, `M4V`など）は、MP4のMIMEタイプを決定する上では必須ではなく、また`M4A`, `3gp`, `jp2`などはMP4とは異なるMIMEタイプを持つ可能性があるため、このスニッフィングロジックからは除外されました。これにより、仕様への準拠とコードの簡素化が同時に達成されています。

### `sniff_test.go`の変更点

*   以前は`TODO`コメントと共にコメントアウトされていたMP4関連のテストケースが有効化されました。具体的には、`{"MP4 video", []byte("..."), "video/mp4"}`というテストケースが復活しました。これは、`sniff.go`のMP4スニッフィングロジックが正しく機能することを確認するためのものです。
*   `MP4 audio`に関するテストケースは削除されました。これは、新しい仕様準拠のロジックが`video/mp4`のみを識別し、`audio/mp4`などのより具体的なMP4派生タイプを区別しないためと考えられます。MIMEスニッフィングの目的は、大まかなタイプを正確に識別することであり、詳細なサブタイプは通常、ファイル拡張子やより深い解析に委ねられます。

## 変更の背景

このコミットは、Go言語のコンパイラとリンカの内部実装における改善です。

1.  **複合リテラルの簡潔化 (Destuttering Composite Literals)**:
    Go言語では、構造体や配列、スライスなどを初期化する際に複合リテラルを使用します。初期のGoでは、例えば構造体のスライスを初期化する際に、各要素の構造体型を明示的に記述する必要がありました。これは冗長であり、コードの可読性を損ねる可能性がありました。この「destuttering」は、このような冗長な型記述を省略できるようにすることで、コードをより簡潔に、そして読みやすくすることを目的としています。これはGo言語の進化の一環であり、より洗練された構文を提供するための変更です。

    例:
    変更前: `[]MyStruct{MyStruct{Field: "value"}, MyStruct{Field: "another"}}`
    変更後: `[]MyStruct{{Field: "value"}, {Field: "another"}}`

2.  **DWARF Abbreviation Tableの改善**:
    DWARF (Debugging With Attributed Record Formats) は、コンパイルされたプログラムのデバッグ情報を表現するための標準フォーマットです。デバッガはDWARF情報を使用して、ソースコードレベルでのデバッグ（変数名の表示、ブレークポイントの設定など）を可能にします。
    DWARFでは、デバッグ情報エントリ (DIE: Debugging Information Entry) を効率的に表現するために「Abbreviation Table（省略表）」を使用します。各DIEは、その構造を定義するAbbreviation Tableのエントリを参照します。
    以前の実装では、`DWAbbrev`構造体の`attr`フィールドが`[30]DWAttrForm`という固定長配列で定義されており、属性のリストの終端を示すためにゼロ値の要素（`{0, 0}`）で終端されていました。この固定長配列は、属性の数が30を超える場合に問題となる可能性があり、また、属性の数が少ない場合でもメモリの無駄が生じる可能性がありました。
    この変更は、`attr`フィールドを可変長スライス`[]DWAttrForm`にすることで、より柔軟で効率的な属性の表現を可能にします。これにより、属性の数に上限がなくなり、必要なメモリも動的に割り当てられるようになります。また、スライス自体が長さを保持するため、ゼロ終端の必要がなくなり、コードが簡潔になります。

これらの変更は、Goコンパイラとリンカの内部品質を向上させ、生成されるデバッグ情報の効率性と正確性を高めることに貢献します。

## 前提知識の解説

### Go言語の複合リテラル (Composite Literals)

Go言語において、複合リテラルは、構造体、配列、スライス、マップなどの複合型を初期化するための構文です。

-   **構造体リテラル**: `MyStruct{Field1: value1, Field2: value2}`
-   **配列リテラル**: `[3]int{1, 2, 3}`
-   **スライスリテラル**: `[]string{"a", "b", "c"}`
-   **マップリテラル**: `map[string]int{"key1": 1, "key2": 2}`

このコミットで言及されている「destuttering」は、特に構造体のスライスや配列を初期化する際に、要素の型を省略できるようになった変更を指します。

```go
// 変更前 (冗長な型記述)
var s = []MyStruct{
    MyStruct{Name: "Alice", Age: 30},
    MyStruct{Name: "Bob", Age: 25},
}

// 変更後 (型記述を省略)
var s = []MyStruct{
    {Name: "Alice", Age: 30},
    {Name: "Bob", Age: 25},
}
```

この変更により、コードがより簡潔になり、可読性が向上します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイラが生成する実行可能ファイルに埋め込まれるデバッグ情報の標準フォーマットです。デバッガは、このDWARF情報を解析することで、コンパイル後のバイナリコードと元のソースコードとの間のマッピングを理解し、以下のようなデバッグ機能を提供します。

-   **ソースコードレベルでのデバッグ**: 変数名、関数名、行番号などをソースコードと同じように表示。
-   **変数検査**: プログラム実行中の変数の値や型を表示。
-   **スタックトレース**: 関数呼び出しの履歴を表示。
-   **ブレークポイント**: ソースコードの特定の行で実行を一時停止。

DWARF情報は、主に以下のセクションで構成されます。

-   `.debug_info`: プログラムの構造（コンパイル単位、関数、変数、型など）を記述するDIE (Debugging Information Entry) の集合。
-   `.debug_abbrev`: DIEの構造を定義するAbbreviation Table。これにより、`.debug_info`セクションの冗長性を減らし、サイズを削減します。
-   `.debug_line`: ソースコードの行番号と実行可能コードのアドレスのマッピング。

### DWARF Abbreviation Table (`.debug_abbrev`)

Abbreviation Tableは、DWARFのデバッグ情報において非常に重要な役割を果たします。各DIEは、そのDIEが持つ属性（名前、型、場所など）のリストを定義するAbbreviation Tableのエントリを参照します。これにより、同じ構造を持つ複数のDIEが、その構造を繰り返し記述することなく、単一のAbbreviation Tableエントリを参照するだけで済みます。

-   **DW_TAG**: DIEの種類（例: `DW_TAG_compile_unit` (コンパイル単位), `DW_TAG_subprogram` (関数), `DW_TAG_variable` (変数)）。
-   **DW_CHILDREN**: そのDIEが子DIEを持つかどうか（`DW_CHILDREN_yes` または `DW_CHILDREN_no`）。
-   **属性 (Attributes)**: 各属性は、属性コード（`DW_AT_name`, `DW_AT_type`など）とフォーム（`DW_FORM_string`, `DW_FORM_addr`など、属性値のエンコーディング方法）のペアで構成されます。

このコミットでは、`DWAbbrev`構造体の`attr`フィールドが変更されています。これは、Abbreviation Tableのエントリが持つ属性のリストを表現するための内部データ構造です。

## 技術的詳細

### 複合リテラルの「destuttering」

`src/cmd/5g/peep.go`, `src/cmd/internal/obj/go.go`, `src/cmd/internal/obj/sym.go` の変更は、Goコンパイラのフロントエンドおよび中間コード生成部分における複合リテラルの最適化に関連しています。

これらのファイルでは、以下のようなパターンが見られます。

```go
// 変更前
var predinfo = []struct {
	opcode    int
	notopcode int
	scond     int
	notscond  int
}{
	struct {
		opcode    int
		notopcode int
		scond     int
		notscond  int
	}{arm.ABEQ, arm.ABNE, 0x0, 0x1},
	// ...
}

// 変更後
var predinfo = []struct {
	opcode    int
	notopcode int
	scond     int
	notscond  int
}{
	{arm.ABEQ, arm.ABNE, 0x0, 0x1},
	// ...
}
```

この変更は、Go言語の構文解析器やAST (Abstract Syntax Tree) 変換の段階で、このような冗長な型記述を自動的に省略できるようにするための内部的な調整を反映しています。これにより、コンパイラが生成するコードのサイズや実行時のパフォーマンスに直接的な影響はありませんが、コンパイラ自身のコードベースがよりクリーンで保守しやすくなります。

### DWARF Abbreviation Tableの`DWAbbrev`構造体変更

`src/cmd/internal/ld/dwarf.go` の変更は、GoリンカがDWARFデバッグ情報を生成する際の内部処理に深く関わっています。

**`DWAbbrev`構造体の定義変更**:

```go
// 変更前
type DWAbbrev struct {
	tag      uint8
	children uint8
	attr     [30]DWAttrForm // 固定長配列
}

// 変更後
type DWAbbrev struct {
	tag      uint8
	children uint8
	attr     []DWAttrForm // 可変長スライス
}
```

この変更により、`DWAbbrev`構造体は、そのAbbreviation Tableエントリが持つ属性の数を柔軟に扱うことができるようになります。以前は最大30個の属性しか持てず、それ以上は表現できませんでした。また、属性の数が30未満の場合でも、配列の残りの部分にはゼロ値が埋められ、メモリの無駄が生じていました。スライスに変更することで、必要な数の属性のみを格納できるようになり、メモリ効率が向上します。

**`abbrevs`配列の初期化変更**:

`abbrevs`は、Goリンカが使用するDWARF Abbreviation Tableの定義を保持するグローバルな配列です。この配列の初期化も、`DWAbbrev`構造体の変更に合わせて更新されています。

```go
// 変更前
var abbrevs = [DW_NABRV]struct {
	tag      uint8
	children uint8
	attr     [30]DWAttrForm
}{
	// ...
	struct {
		tag      uint8
		children uint8
		attr     [30]DWAttrForm
	}{
		DW_TAG_compile_unit,
		DW_CHILDREN_yes,
		[30]DWAttrForm{
			DWAttrForm{DW_AT_name, DW_FORM_string},
			DWAttrForm{DW_AT_language, DW_FORM_data1},
			// ...
			DWAttrForm{0, 0}, // ゼロ終端
		},
	},
	// ...
}

// 変更後
var abbrevs = [DW_NABRV]DWAbbrev{
	// ...
	{
		DW_TAG_compile_unit,
		DW_CHILDREN_yes,
		[]DWAttrForm{ // スライスリテラル
			{DW_AT_name, DW_FORM_string},
			{DW_AT_language, DW_FORM_data1},
			// ...
		},
	},
	// ...
}
```

ここでも、複合リテラルの「destuttering」が適用され、各`DWAbbrev`要素の型記述が省略されています。さらに、`attr`フィールドの初期化が固定長配列からスライスリテラルに変更され、ゼロ終端の`DWAttrForm{0, 0}`が不要になっています。

**`writeabbrev`関数の変更**:

`writeabbrev`関数は、DWARF Abbreviation Tableをバイナリ形式で出力する役割を担っています。

```go
// 変更前
func writeabbrev() {
	var j int
	var f *DWAttrForm

	// ...
	for j = 0; j < len(abbrevs[i].attr); j++ {
		f = &abbrevs[i].attr[j]
		uleb128put(int64(f.attr))
		uleb128put(int64(f.form))
		if f.attr == 0 { // ゼロ終端チェック
			break
		}
	}
	// ...
}

// 変更後
func writeabbrev() {
	// ...
	for _, f := range abbrevs[i].attr { // rangeでスライスをイテレート
		uleb128put(int64(f.attr))
		uleb128put(int64(f.form))
	}
	uleb128put(0) // 属性リストの終端マーカー
	uleb128put(0) // 属性リストの終端マーカー
	// ...
}
```

変更前は、固定長配列をループし、`f.attr == 0`でゼロ終端を検出してループを抜けていました。変更後は、スライスを`for ... range`でイテレートするため、スライスの長さが自動的に終端を示します。
しかし、DWARFの仕様では、各Abbreviation Tableエントリの属性リストは、属性コードとフォームのペアがそれぞれゼロ値であるペア（`0, 0`）で終端される必要があります。そのため、スライスを全て書き出した後に、明示的に`uleb128put(0)`を2回呼び出して、この終端マーカーを書き込んでいます。これにより、DWARFの仕様に準拠しつつ、内部実装はスライスによって柔軟性を得ています。

**`putattrs`関数の変更**:

`putattrs`関数は、特定のAbbreviation Tableエントリに対応する属性を書き込む際に使用されます。

```go
// 変更前
func putattrs(abbrev int, attr *DWAttr) {
	var ap *DWAttr

	for af := abbrevs[abbrev].attr[:]; af[0].attr != 0; af = af[1:] {
		for ap = attr; ap != nil; ap = ap.link {
			if ap.atr == af[0].attr {
				putattr(abbrev, int(af[0].form), int(ap.cls), ap.value, ap.data)
				goto done
			}
		}

		putattr(abbrev, int(af[0].form), 0, 0, nil)
	done:
	}
}

// 変更後
func putattrs(abbrev int, attr *DWAttr) {
Outer:
	for _, f := range abbrevs[abbrev].attr { // rangeでスライスをイテレート
		for ap := attr; ap != nil; ap = ap.link {
			if ap.atr == f.attr {
				putattr(abbrev, int(f.form), int(ap.cls), ap.value, ap.data)
				continue Outer // 次の属性へ
			}
		}

		putattr(abbrev, int(f.form), 0, 0, nil)
	}
}
```

ここでも、`abbrevs[abbrev].attr`がスライスになったことに合わせて、ループの記述が`for ... range`に変更されています。`goto done`のようなラベル付きジャンプも`continue Outer`に置き換えられ、コードの構造がより明確になっています。

これらの変更は、Goコンパイラとリンカの内部コードの品質と保守性を向上させるとともに、DWARFデバッグ情報の生成における柔軟性と効率性を高めるものです。

## コアとなるコードの解説

### `src/cmd/5g/peep.go`、`src/cmd/internal/obj/go.go`、`src/cmd/internal/obj/sym.go` の変更

これらのファイルにおける変更は、Go言語の複合リテラルの「destuttering」という構文糖衣（syntactic sugar）の適用です。これは、Goコンパイラがより新しいGo言語の構文規則をサポートするように更新されたことを示しています。

例えば、`src/cmd/5g/peep.go`の`predinfo`の変更は、以下のように解釈できます。

```go
// 変更前: 各要素で明示的に構造体型を記述
var predinfo = []struct { /* ... */ }{
	struct { /* ... */ }{arm.ABEQ, arm.ABNE, 0x0, 0x1},
	struct { /* ... */ }{arm.ABNE, arm.ABEQ, 0x1, 0x0},
	// ...
}

// 変更後: 要素の構造体型を省略
var predinfo = []struct { /* ... */ }{
	{arm.ABEQ, arm.ABNE, 0x0, 0x1},
	{arm.ABNE, arm.ABEQ, 0x1, 0x0},
	// ...
}
```

これは、Go言語の進化に伴い、コンパイラがより簡潔なコードを許容するようになったことを示しており、開発者の記述負担を軽減し、コードの可読性を向上させる効果があります。

### `src/cmd/internal/ld/dwarf.go` の変更

このファイルにおける変更は、Goリンカが生成するDWARFデバッグ情報の内部表現と生成ロジックの改善です。

**`DWAbbrev`構造体の`attr`フィールドの変更**:
`attr [30]DWAttrForm` から `attr []DWAttrForm` への変更は、DWARF Abbreviation Tableのエントリが持つ属性のリストを、固定長配列ではなく動的なスライスで管理するようにしたことを意味します。
-   **固定長配列 (`[30]DWAttrForm`) の問題点**:
    -   属性の数が30を超えるAbbreviation Tableエントリを表現できない。
    -   属性の数が30未満の場合でも、30要素分のメモリが常に確保され、メモリの無駄が生じる。
    -   属性リストの終端を明示的に示すために、ゼロ値の`DWAttrForm{0, 0}`を最後に配置する必要がある。
-   **スライス (`[]DWAttrForm`) の利点**:
    -   属性の数に事実上の上限がなくなり、より複雑なDWARF構造を表現できる。
    -   必要なメモリが動的に割り当てられるため、メモリ効率が向上する。
    -   スライス自体が長さを保持するため、内部的にはゼロ終端の必要がなくなる（ただし、DWARFのバイナリ出力時には仕様に従ってゼロ終端マーカーを書き込む必要がある）。

**`writeabbrev`関数の変更**:
この関数は、`DWAbbrev`構造体の内容をDWARFのバイナリ形式で出力します。

```go
// 変更前 (抜粋): ゼロ終端を検出してループを抜ける
for j = 0; j < len(abbrevs[i].attr); j++ {
    f = &abbrevs[i].attr[j]
    // ...
    if f.attr == 0 {
        break // ゼロ終端でループを抜ける
    }
}

// 変更後 (抜粋): スライスを最後までイテレートし、その後で明示的にゼロ終端マーカーを書き込む
for _, f := range abbrevs[i].attr {
    // ...
}
uleb128put(0) // 属性リストの終端マーカー
uleb128put(0) // 属性リストの終端マーカー
```

この変更は、`attr`がスライスになったことで、Goの`range`ループを使って属性を全て処理できるようになり、コードが簡潔になったことを示しています。しかし、DWARFの仕様では、各Abbreviation Tableエントリの属性リストは、属性コードとフォームのペアがそれぞれゼロ値であるペア（`0, 0`）で終端される必要があります。そのため、スライスを全て書き出した後に、明示的に`uleb128put(0)`を2回呼び出して、この終端マーカーを書き込んでいます。これにより、Goの内部データ構造の柔軟性と、DWARF標準への準拠が両立されています。

**`putattrs`関数の変更**:
この関数も`DWAbbrev.attr`がスライスになったことに合わせて、ループのイテレーション方法が変更されています。`goto`文の使用が`continue Outer`に置き換えられ、コードのフローがより構造化され、理解しやすくなっています。

これらの変更は、Goのツールチェインが生成するデバッグ情報の品質と効率を向上させるための重要なステップであり、デバッガの機能性向上にも寄与します。

## 前提知識の解説

### Go言語の複合リテラル (Composite Literals)

Go言語において、複合リテラルは、構造体、配列、スライス、マップなどの複合型を初期化するための構文です。

-   **構造体リテラル**: `MyStruct{Field1: value1, Field2: value2}`
-   **配列リテラル**: `[3]int{1, 2, 3}`
-   **スライスリテラル**: `[]string{"a", "b", "c"}`
-   **マップリテラル**: `map[string]int{"key1": 1, "key2": 2}`

このコミットで言及されている「destuttering」は、特に構造体のスライスや配列を初期化する際に、要素の型を省略できるようになった変更を指します。

```go
// 変更前 (冗長な型記述)
var s = []MyStruct{
    MyStruct{Name: "Alice", Age: 30},
    MyStruct{Name: "Bob", Age: 25},
}

// 変更後 (型記述を省略)
var s = []MyStruct{
    {Name: "Alice", Age: 30},
    {Name: "Bob", Age: 25},
}
```

この変更により、コードがより簡潔になり、可読性が向上します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイラが生成する実行可能ファイルに埋め込まれるデバッグ情報の標準フォーマットです。デバッガは、このDWARF情報を解析することで、コンパイル後のバイナリコードと元のソースコードとの間のマッピングを理解し、以下のようなデバッグ機能を提供します。

-   **ソースコードレベルでのデバッグ**: 変数名、関数名、行番号などをソースコードと同じように表示。
-   **変数検査**: プログラム実行中の変数の値や型を表示。
-   **スタックトレース**: 関数呼び出しの履歴を表示。
-   **ブレークポイント**: ソースコードの特定の行で実行を一時停止。

DWARF情報は、主に以下のセクションで構成されます。

-   `.debug_info`: プログラムの構造（コンパイル単位、関数、変数、型など）を記述するDIE (Debugging Information Entry) の集合。
-   `.debug_abbrev`: DIEの構造を定義するAbbreviation Table。これにより、`.debug_info`セクションの冗長性を減らし、サイズを削減します。
-   `.debug_line`: ソースコードの行番号と実行可能コードのアドレスのマッピング。

### DWARF Abbreviation Table (`.debug_abbrev`)

Abbreviation Tableは、DWARFのデバッグ情報において非常に重要な役割を果たします。各DIEは、そのDIEが持つ属性（名前、型、場所など）のリストを定義するAbbreviation Tableのエントリを参照します。これにより、同じ構造を持つ複数のDIEが、その構造を繰り返し記述することなく、単一のAbbreviation Tableエントリを参照するだけで済みます。

-   **DW_TAG**: DIEの種類（例: `DW_TAG_compile_unit` (コンパイル単位), `DW_TAG_subprogram` (関数), `DW_TAG_variable` (変数)）。
-   **DW_CHILDREN**: そのDIEが子DIEを持つかどうか（`DW_CHILDREN_yes` または `DW_CHILDREN_no`）。
-   **属性 (Attributes)**: 各属性は、属性コード（`DW_AT_name`, `DW_AT_type`など）とフォーム（`DW_FORM_string`, `DW_FORM_addr`など、属性値のエンコーディング方法）のペアで構成されます。

このコミットでは、`DWAbbrev`構造体の`attr`フィールドが変更されています。これは、Abbreviation Tableのエントリが持つ属性のリストを表現するための内部データ構造です。

この変更は、`attr`がスライスになったことで、Goの`range`ループを使って属性を全て処理できるようになり、コードが簡潔になったことを示しています。しかし、DWARFの仕様では、各Abbreviation Tableエントリの属性リストは、属性コードとフォームのペアがそれぞれゼロ値であるペア（`0, 0`）で終端される必要があります。そのため、スライスを全て書き出した後に、明示的に`uleb128put(0)`を2回呼び出して、この終端マーカーを書き込んでいます。これにより、Goの内部データ構造の柔軟性と、DWARF標準への準拠が両立されています。

**`putattrs`関数の変更**:
この関数も`DWAbbrev.attr`がスライスになったことに合わせて、ループのイテレーション方法が変更されています。`goto`文の使用が`continue Outer`に置き換えられ、コードのフローがより構造化され、理解しやすくなっています。

これらの変更は、Goのツールチェインが生成するデバッグ情報の品質と効率を向上させるための重要なステップであり、デバッガの機能性向上にも寄与します。

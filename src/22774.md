## 前提知識の解説

### Go言語とクロスコンパイル

Go言語は、Googleによって開発された静的型付けのコンパイル型言語です。その特徴の一つに、強力なクロスコンパイル機能があります。これは、あるオペレーティングシステム（OS）やアーキテクチャ上で、別のOSやアーキテクチャ向けの実行ファイルを生成できる能力を指します。例えば、macOS上でLinux/ARM64向けのGoバイナリをビルドすることが可能です。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。これにより、既存のCライブラリをGoプロジェクトで再利用したり、Goでは直接アクセスできないOS固有のAPIやハードウェア機能にアクセスしたりすることが可能になります。Cgoを使用するには、Goのビルドプロセス中にCコンパイラ（通常はGCCやClang）が必要となります。

Cgoを使用する際、GoのツールチェインはGoのコードとCのコードを統合し、最終的な実行ファイルを生成します。この統合の過程で、リンキング（連結）というステップが重要になります。

### リンキング（連結）

リンキングとは、コンパイルされたオブジェクトファイル（機械語コード）と、それらが参照するライブラリのコードを結合して、実行可能なプログラムを生成するプロセスです。リンキングには主に二つの方法があります。

1.  **内部リンキング（Internal Linking / Static Linking）**:
    この方法では、必要なライブラリのコードが最終的な実行ファイルに直接組み込まれます。結果として生成されるバイナリは自己完結型であり、実行時に外部ライブラリを必要としません。これはGoのデフォルトのリンキング方法であり、Goバイナリが単一ファイルで配布しやすいという利点をもたらします。しかし、ライブラリの更新があった場合、実行ファイル全体を再ビルドする必要があります。

2.  **外部リンキング（External Linking / Dynamic Linking）**:
    この方法では、ライブラリのコードは実行ファイルには組み込まれず、実行ファイルは実行時にシステムに存在する共有ライブラリ（例: `.so` ファイル on Linux, `.dll` ファイル on Windows, `.dylib` ファイル on macOS）を参照します。これにより、複数のプログラムが同じライブラリを共有でき、ディスクスペースの節約や、ライブラリの更新が容易になるという利点があります。しかし、実行時に必要な共有ライブラリが存在しない場合、プログラムは実行できません。

### `linux/arm64` アーキテクチャ

`linux/arm64` は、ARMv8-Aアーキテクチャに基づく64ビットLinuxシステムを指します。このアーキテクチャは、低消費電力と高性能を両立できるため、スマートフォン、タブレット、組み込みシステム、そして近年ではデータセンターのサーバー（例: AWS Gravitonプロセッサ）など、幅広いデバイスで採用されています。Goがこのアーキテクチャをサポートすることは、これらのプラットフォームでGoアプリケーションを開発・デプロイする上で非常に重要です。

## 技術的詳細

Go 1.5における`linux/arm64` のCgoサポートが「外部リンキングのみ」に限定されていたという事実は、当時のGoコンパイラとリンカの成熟度、およびARM64アーキテクチャ特有の課題を反映しています。

通常、Goは静的リンキングを強く推奨し、Cgoを使用しないGoプログラムはデフォルトで完全に静的にリンクされます。しかし、Cgoを使用する場合、GoのツールチェインはCコンパイラ/リンカ（GCC/Clang）と連携してCコードをコンパイルし、Goのコードとリンクします。

`linux/arm64` においてCgoが外部リンキングのみをサポートしていたということは、以下の技術的背景が考えられます。

1.  **リンカの複雑性**:
    Goの内部リンカ（`cmd/link`）は、GoのランタイムとCgoで生成されたCコードを統合する役割を担っています。特定のアーキテクチャ（この場合はARM64）において、Cgoが生成するオブジェクトファイルとGoのランタイムを完全に静的にリンクするための複雑なリンカのロジックや、アーキテクチャ固有のリンキング規則の実装が、Go 1.5のリリース時点ではまだ完全ではなかった可能性があります。特に、CgoはC標準ライブラリ（glibcなど）に依存することが多く、これらのライブラリを静的にリンクすることは、ライセンスの問題（LGPLなど）や技術的な複雑さ（再配置、シンボル解決など）を伴うことがあります。

2.  **Goのセルフホスティングへの移行**:
    Go 1.5は、GoコンパイラとランタイムがGo自身で書かれるようになった（セルフホスティング）という大きな変更がありました。この移行は、Goのビルドシステム全体に大きな影響を与え、新しいアーキテクチャへの対応やCgoのような複雑な機能のサポートを安定させるには、段階的なアプローチが必要だったと考えられます。セルフホスティングへの移行期において、すべてのリンキングシナリオを一度に完全にサポートすることは困難だったのかもしれません。

3.  **ABI（Application Binary Interface）の差異**:
    異なるアーキテクチャやOSでは、関数呼び出し規約、データ構造のメモリ配置、システムコールインターフェースなど、ABIが異なります。CgoはGoとCの間のABIブリッジとして機能するため、`linux/arm64` のABIに完全に準拠し、かつ静的リンキングを可能にするためのGoランタイムとリンカの調整には、追加の開発が必要だった可能性があります。外部リンキングは、システムにインストールされている標準のCライブラリとリンカに依存することで、これらのABIの差異の一部を吸収できるため、実装が比較的容易だったと考えられます。

この制約は、`linux/arm64` 上でCgoを使用するGo開発者にとって、ビルド環境に特定の共有ライブラリが存在することを前提とする必要があり、Goの「単一バイナリ」という利点が一部失われることを意味しました。しかし、それでもCgoが利用可能であることは、このアーキテクチャでのGoの採用を促進する上で重要な一歩でした。

## コアとなるコードの解説

この変更は、Go 1.5のリリースノートにおいて、`linux/arm64` ポートに関する重要な情報を追加するものです。

変更前は単に「`linux/arm64`」とだけ記載されており、このポートにおけるCgoのサポート状況については不明瞭でした。Goのユーザーは、Cgoがデフォルトで静的リンキングを試みることを期待するかもしれません。しかし、`linux/arm64` ではその時点では静的リンキングが完全にサポートされていなかったため、この曖昧さは誤解を招く可能性がありました。

変更後の記述「`(cgo is supported, but only with external linking)`」は、以下の点を明確にしています。

1.  **Cgoのサポート**: `linux/arm64` 上でCgoが利用可能であること。これは、Goアプリケーションが既存のCライブラリと連携できることを意味し、このアーキテクチャでのGoの有用性を高めます。
2.  **外部リンキングの制約**: Cgoを使用する際には、外部リンキング（ダイナミックリンキング）が必要であること。これは、Goプログラムが実行時にシステムに存在する共有ライブラリに依存することを意味します。開発者は、ビルド環境とデプロイ環境の両方で必要な共有ライブラリが利用可能であることを確認する必要があります。

この一文の追加は、Go 1.5のリリースにおける`linux/arm64` ポートの成熟度と、Cgoを使用する際の具体的な要件を正確に伝える上で非常に重要です。これにより、開発者は不必要なトラブルシューティングの時間を費やすことなく、`linux/arm64` 上でCgoを適切に利用するための知識を得ることができます。

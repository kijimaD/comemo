## 変更の背景

この変更は、GoランタイムがPlan 9オペレーティングシステム上のx86アーキテクチャで、ヒープメモリ上の不正なアドレスをプログラムカウンタ (PC) として参照してしまった場合に、正確なスタックトレースを生成できないという問題に対処するために導入されました。

元々、この問題は他のシステム（Linux, macOSなど）向けにはRuss CoxによってCL 12026という変更セットで修正されていました。しかし、その際にPlan 9固有の処理が考慮されておらず、Plan 9環境では同様の問題が未解決のままでした。

この問題はGoのIssue #11656として報告されており、「runtime: jump to bad PC missing good traceback」（不正なPCへのジャンプで適切なトレースバックが欠落する）と題されています。特に`SIGILL`（不正命令）シグナルが発生した際に、スタックトレースが途切れてしまい、問題の根本原因を特定するのが困難になることが指摘されていました。このコミットは、Plan 9環境におけるこの特定のバグを修正し、より堅牢なデバッグ体験を提供することを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステムです。ガベージコレクション、スケジューリング、メモリ管理、スタック管理、シグナル処理など、多くの重要な機能を提供します。
*   **スタックトレース (Stack Trace)**: プログラムがエラーやパニックを起こした際に、その時点までの関数呼び出しの履歴を順に表示したものです。これにより、どの関数がどの関数を呼び出し、最終的にどこで問題が発生したのかを追跡できます。デバッグにおいて非常に重要な情報です。
*   **プログラムカウンタ (Program Counter, PC)**: CPUが次に実行する命令のアドレスを保持するレジスタです。スタックトレースでは、各関数呼び出し時点でのPCが記録されます。
*   **スタックポインタ (Stack Pointer, SP)**: 現在のスタックフレームの最上位（または最下位、アーキテクチャによる）のアドレスを指すレジスタです。
*   **ヒープメモリ (Heap Memory)**: プログラム実行中に動的にメモリを確保・解放するために使用される領域です。`new`や`make`で確保されるメモリは通常ヒープに配置されます。
*   **Plan 9**: ベル研究所が開発した分散オペレーティングシステムです。Go言語は当初からPlan 9をサポートしており、Goの設計思想にも影響を与えています。Goランタイムは、各OSの特性に合わせて実装が異なります。
*   **シグナルハンドラ (Signal Handler)**: オペレーティングシステムからプロセスに送られるシグナル（例: セグメンテーション違反、不正命令、タイマー割り込みなど）を捕捉し、処理するための特別な関数です。Goランタイムは、プログラムの異常終了を防ぎ、パニックを適切に処理するためにシグナルハンドラを使用します。
*   **`findfunc`**: Goランタイム内部の関数で、与えられたアドレス（PC）がGoの関数コードの範囲内にあるかどうかを判定します。これにより、PCが有効なGoのコードを指しているか、それとも不正なアドレスを指しているかを判断できます。
*   **`sigpanic`**: Goランタイム内部の関数で、Goプログラムがパニック状態に陥った際に呼び出されます。`sigpanic`はスタックトレースを生成し、プログラムを終了させる役割を担います。
*   **CL (Change List)**: Goプロジェクトにおける変更セットの単位です。GoのコードレビューシステムであるGerritで管理されます。
*   **Issue #11656**: Goプロジェクトのバグトラッカーで報告された問題で、このコミットによって修正されました。

## 技術的詳細

このコミットが修正しようとしている問題は、Plan 9 x86環境で、プログラムが誤ってヒープメモリ上の不正なアドレスをPCとして実行しようとした際に発生します。このような状況では、OSは通常`SIGILL`のようなシグナルをGoランタイムのシグナルハンドラに送ります。

問題は、シグナルハンドラが受け取ったPCが不正なアドレスであるにもかかわらず、それが有効なGoの関数コードではないと判断され、結果としてスタックトレースが途切れてしまうことにありました。特に、PCが`0`でないにもかかわらず`findfunc(pc)`が`nil`を返す（つまり、Goのコードではないと判断される）場合、シグナルハンドラはPCを`0`として扱わず、不完全なスタックトレースを生成していました。

このコミットは、`src/runtime/os3_plan9.go`内の`sighandler`関数に以下のロジックを追加することでこの問題を解決します。

1.  現在のPC (`c.pc()`) とSP (`c.sp()`) を取得します。
2.  以下の条件をチェックします。
    *   PCが`0`ではない (`pc != 0`)。
    *   PCがGoの関数コードではない (`findfunc(pc) == nil`)。
    *   しかし、スタックポインタが指すアドレス（スタックの最上位）がGoの関数コードである (`findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`)。
3.  上記の条件がすべて真である場合、これは「コードではない場所への呼び出し」が発生したが、スタック上には有効な呼び出し元が残っている状況であると判断します。この場合、スタックトレースを適切に生成するために、**PCを強制的に`0`に設定します** (`pc = 0`)。

なぜPCを`0`に設定するのかというと、Goランタイムの`sighandler`内の既存のロジックでは、PCが`0`の場合に`sigpanic`をスタックにプッシュする際に特別な処理を行います。具体的には、PCが`0`であれば、それはおそらく`nil`関数への呼び出しによるパニックであるとみなし、`sigpanic`をスタックにプッシュする際に現在のPCをスタックに保存せず、`sigpanic`自体がスタックトレースの起点となるようにします。これにより、不正なPCがスタックトレースを混乱させることなく、`sigpanic`が呼び出されたコンテキスト（つまり、`nil`関数を呼び出した場所）を適切に表示できるようになります。

この修正により、Plan 9 x86環境でも、ヒープメモリ上の不正なアドレスへの呼び出しによって発生するパニックに対して、より正確で有用なスタックトレースが提供されるようになります。

## コアとなるコードの解説

`src/runtime/os3_plan9.go` の `sighandler` 関数内の変更がこのコミットの核心です。

1.  **PCとSPの取得**:
    ```go
    		pc := uintptr(c.pc())
    		sp := uintptr(c.sp())
    ```
    まず、現在のプログラムカウンタ (PC) とスタックポインタ (SP) の値を`uintptr`型で取得し、それぞれ`pc`と`sp`というローカル変数に格納します。これにより、元の`c.pc()`や`c.sp()`を直接変更することなく、条件付きで`pc`の値を操作できるようになります。

2.  **不正なPCの検出と修正ロジック**:
    ```go
    		// If we don't recognize the PC as code
    		// but we do recognize the top pointer on the stack as code,
    		// then assume this was a call to non-code and treat like
    		// pc == 0, to make unwinding show the context.
    		if pc != 0 && findfunc(pc) == nil && findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil {
    			pc = 0
    		}
    ```
    この`if`文が新しいロジックです。
    *   `pc != 0`: 現在のPCが`0`ではないことを確認します。PCが`0`の場合は、既に`nil`関数呼び出しとして適切に処理されるため、このロジックは不要です。
    *   `findfunc(pc) == nil`: 現在のPCがGoの関数コードの範囲外であることを確認します。これは、PCが不正なアドレス（例えばヒープ上のデータ領域）を指している可能性を示唆します。
    *   `findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`: スタックポインタ`sp`が指すアドレス（つまり、現在の関数を呼び出した呼び出し元のリターンアドレス）が、有効なGoの関数コード内にあることを確認します。これは、不正なPCへのジャンプが発生したものの、その呼び出し元は正当なGoのコードであったことを意味します。

    これら3つの条件がすべて満たされた場合、Goランタイムは「コードではない場所への呼び出し」が発生したと判断します。この状況では、スタックトレースを適切に生成するために、`pc`の値を`0`に強制的に設定します。これにより、後続の`sigpanic`処理が、このイベントを`nil`関数呼び出しによるパニックと同様に扱い、呼び出し元のコンテキストを正しくスタックトレースに含めることができるようになります。

3.  **`sigpanic`のプッシュ処理の変更**:
    ```diff
    -		if c.pc() != 0 {
    +		if pc != 0 {
     			if regSize > ptrSize {
     				sp -= ptrSize
     				*(*uintptr)(unsafe.Pointer(sp)) = 0
     			}
     			sp -= ptrSize
    -			*(*uintptr)(unsafe.Pointer(sp)) = c.pc()
    +			*(*uintptr)(unsafe.Pointer(sp)) = pc
     			c.setsp(sp)
     		}
    ```
    この部分では、`sigpanic`をスタックにプッシュする際に、以前は`c.pc()`を直接使用していましたが、変更後はローカル変数`pc`を使用するように修正されています。これにより、上記のロジックで`pc`が`0`に設定された場合、その`0`がスタックにプッシュされ、`sigpanic`の特別な処理がトリガーされるようになります。

`test/fixedbugs/issue11656.go` の変更は、テストファイルのビルドタグから`!plan9 !386`を削除することで、Plan 9 x86環境でもこのテストが実行されるようにしたものです。これにより、修正が正しく機能していることを確認できるようになりました。

このコミットは、Goランタイムの`src/runtime/signal_386.go`ファイルに対する変更です。このファイルは、Linux/386アーキテクチャにおけるGoプログラムのシグナルハンドリング、特にクラッシュ時のスタックトレース生成に関連するロジックを実装しています。Goランタイムは、オペレーティングシステムからのシグナル（例えば、セグメンテーション違反や不正なメモリアクセスなど）を受け取った際に、プログラムの実行を適切に処理し、デバッグに役立つ情報（スタックトレースなど）を出力する責任を負っています。このファイルは、特に32ビットx86 (i386) アーキテクチャに特化したシグナル処理の実装を含んでいます。

## 変更の背景

Goプログラムがクラッシュした際、デバッグのためにスタックトレースを出力することは非常に重要です。`GOTRACEBACK`環境変数は、このスタックトレースの出力レベルを制御します。特に`GOTRACEBACK=crash`は、プログラムがクラッシュした際に、実行中のすべてのゴルーチン（Goルーチン）のスタックトレースを詳細に出力し、その後プロセスを終了させることを意図しています。

このコミット以前は、`linux/386`アーキテクチャにおいて`GOTRACEBACK=crash`が完全に実装されていませんでした。特に、以下の2つの主要な課題がありました。

1.  **`vdso kernel_vsyscall`のスタックトレースの不正確さ**: Linux/386では、システムコールの一部が`vdso` (Virtual Dynamic Shared Object) と呼ばれるカーネルがユーザー空間にマップする共有ライブラリを通じて行われます。特に`kernel_vsyscall`というルーチンは、システムコールを高速化するために使用されます。しかし、シグナルハンドラが呼び出された際に、プログラムカウンタ（PC）がこの`vdso`領域を指している場合、通常のスタックアンワインドでは正確な呼び出し元を特定できず、スタックトレースが不正確になる問題がありました。
2.  **複数M (OSスレッド) におけるスタックダンプの調整**: Goランタイムは、複数のOSスレッド（M: Machine）を使用してゴルーチン（G: Goroutine）を実行します。`GOTRACEBACK=crash`が設定されている場合、クラッシュ時にすべてのゴルーチンのスタックトレースを出力する必要があります。しかし、シグナルは通常、特定のOSスレッドにのみ配送されるため、他のOSスレッドで実行中のゴルーチンのスタックトレースも取得し、一貫したクラッシュレポートを生成するためのメカニズムが必要でした。

このコミットは、これらの課題に対処し、`linux/386`環境での`GOTRACEBACK=crash`の信頼性と有用性を向上させることを目的としています。

## 前提知識の解説

### `GOTRACEBACK`環境変数

`GOTRACEBACK`はGoプログラムの実行時に設定できる環境変数で、プログラムがパニックまたはクラッシュした際のスタックトレースの出力方法を制御します。

*   **`GOTRACEBACK=0` または `none`**: スタックトレースを出力しません。
*   **`GOTRACEBACK=1` または `single`**: 現在のゴルーチンのスタックトレースのみを出力します。
*   **`GOTRACEBACK=2` または `all`**: すべてのゴルーチンのスタックトレースを出力します。
*   **`GOTRACEBACK=crash`**: `all`と同様にすべてのゴルーチンのスタックトレースを出力しますが、さらにOS固有のクラッシュメカニズム（例: Linuxの`SIGQUIT`）を利用して、他のOSスレッド（M）にもスタックダンプを促し、最終的にプロセスを終了させます。これは、デバッガがアタッチされていない環境で、完全なクラッシュレポートを生成する際に特に有用です。

### Goランタイムのシグナルハンドリング

Goランタイムは、OSからのシグナルを捕捉し、独自のシグナルハンドラ（このコミットで変更されている`sighandler`関数など）で処理します。これにより、GoプログラムはOSのデフォルトの動作（例えば、セグメンテーション違反で即座に終了する）を上書きし、より詳細なデバッグ情報を提供したり、クリーンアップ処理を実行したりすることができます。シグナルハンドラは、シグナル発生時のCPUレジスタの状態やスタックポインタなどのコンテキスト情報を受け取ります。

### `linux/386`アーキテクチャの特性と`vdso`

`linux/386`は、32ビットのx86アーキテクチャを指します。このアーキテクチャでは、システムコール（ユーザープログラムがカーネルの機能を利用するためのインターフェース）の呼び出し方法に特徴があります。

**`vdso` (Virtual Dynamic Shared Object)**:
`vdso`は、Linuxカーネルがユーザー空間にマップする特殊な共有ライブラリです。一部のシステムコール（例: `gettimeofday`, `clock_gettime`, `getcpu`など）は、カーネルモードへの切り替えを伴う通常のシステムコール呼び出しよりも高速に実行するために、`vdso`を通じて直接ユーザー空間で実行されます。これにより、コンテキストスイッチのオーバーヘッドが削減されます。

**`vdso kernel_vsyscall`**:
`linux/386`では、`vdso`内に`kernel_vsyscall`というルーチンが存在し、これがシステムコール呼び出しのゲートウェイとして機能することがあります。シグナルが発生した際に、プログラムカウンタがこの`kernel_vsyscall`ルーチン内を指している場合、スタックトレースを正確に生成するためには、このルーチンの内部的なスタックフレーム構造を理解し、適切な呼び出し元のアドレスを特定する「アンワインド」処理が必要になります。`vdso`のアドレスは動的に変化する可能性があり、またその内部構造もカーネルのバージョンによって異なる可能性があるため、正確なアンワインドは複雑な課題です。

### GoのM (Machine) とG (Goroutine) モデル

Goランタイムは、M (Machine)、P (Processor)、G (Goroutine) という3つの主要な抽象化を使用して並行性を管理します。

*   **G (Goroutine)**: Goの軽量な並行実行単位。数百万個作成することも可能です。
*   **M (Machine)**: OSスレッドに相当します。Goランタイムは、OSスレッドをプールし、その上でゴルーチンを実行します。
*   **P (Processor)**: MとGの間の論理的なプロセッサです。PはMにアタッチされ、Gの実行をスケジュールします。

シグナルはOSスレッド（M）に配送されるため、`GOTRACEBACK=crash`のようにすべてのゴルーチンのスタックトレースが必要な場合、シグナルを受け取ったMだけでなく、他のMで実行中のゴルーチンの情報も収集する必要があります。

### ランタイム関数

*   **`startpanic()`**: パニック処理を開始するGoランタイムの内部関数。
*   **`tracebacktrap()`**: トラップ（シグナル）発生時のスタックトレースを生成する関数。
*   **`tracebackothers()`**: 現在のM以外のMで実行中のゴルーチンのスタックトレースを生成する関数。
*   **`crash()`**: プロセスを強制終了させるGoランタイムの内部関数。
*   **`dumpregs()`**: シグナル発生時のCPUレジスタの値をダンプする関数。
*   **`sigctxt`, `siginfo`**: シグナルハンドラに渡される構造体で、シグナルに関する詳細な情報（シグナル番号、エラーコード、CPUレジスタの状態など）を含みます。

### `raiseproc(_SIGQUIT)`

`raiseproc`は、Goランタイムが内部的に使用する関数で、指定されたシグナルを現在のプロセスに送信します。`_SIGQUIT`は、通常、プログラムを終了させ、コアダンプを生成するために使用されるシグナルです。`GOTRACEBACK=crash`の場合、このシグナルを他のMにリレーすることで、すべてのMがクラッシュ処理に参加し、それぞれのゴルーチンのスタックトレースをダンプするように促します。

## 技術的詳細

このコミットの技術的詳細は、主に`sighandler`関数の変更に集約されます。

1.  **`crashing`変数の導入と条件付き`startpanic()`**:
    *   `var crashing int32`が追加されました。これは、複数のMが同時にクラッシュ処理に入ろうとするのを防ぐためのアトミックなカウンタとして機能します。
    *   `startpanic()`の呼び出しが`if crashing == 0 { startpanic() }`という条件付きになりました。これにより、最初にシグナルを受け取ったMだけが`startpanic()`を呼び出し、パニック処理の初期化を行います。他のMは、既にパニック処理が進行中であることを認識し、重複した初期化を避けます。

2.  **`PC`出力の強化**:
    *   `print("PC=", hex(c.eip()), "\n")`が`print("PC=", hex(c.eip()), " m=", _g_.m.id, "\n")`に変更されました。これにより、クラッシュ時のプログラムカウンタ（PC）だけでなく、どのM（OSスレッド）でシグナルが発生したかを示すMのIDも出力されるようになり、デバッグ情報がより豊富になりました。

3.  **`vdso kernel_vsyscall`のアンワインドロジック**:
    *   `linux/386`に特化した`vdso kernel_vsyscall`のアンワインド処理が追加されました。
    *   `pc := uintptr(c.eip())`と`sp := uintptr(c.esp())`で現在のプログラムカウンタとスタックポインタを取得します。
    *   `if GOOS == "linux" && pc >= 0xf4000000 && gp.stack.lo <= sp && sp+16 <= gp.stack.hi`という条件で、PCが`vdso`領域（`0xf4000000`は一般的な`vdso`の開始アドレス付近）にあり、かつスタックポインタが有効なスタック範囲内にあることを確認します。`sp+16 <= gp.stack.hi`は、スタックポインタを16バイト進めてもスタックの境界を超えないことを保証します。
    *   条件が真の場合、`sp += 16`でスタックポインタを16バイト進めます。これは、`kernel_vsyscall`ルーチンがスタックに保存したいくつかのワード（通常は3ワード）と、初期呼び出しで保存された呼び出し元のPCをスキップするためです。
    *   `pc = *(*uintptr)(unsafe.Pointer(sp - 4))`で、調整されたスタックポインタから4バイト手前（つまり、`kernel_vsyscall`に入る前の呼び出し元のPCが保存されている場所）から、真の呼び出し元PCを読み取ります。
    *   `print("runtime: unwind vdso kernel_vsyscall: pc=", hex(pc), " sp=", hex(sp), "\n")`で、アンワインド処理が行われたことを示すデバッグメッセージを出力します。
    *   この調整された`pc`と`sp`が`tracebacktrap()`に渡され、より正確なスタックトレースが生成されます。

4.  **複数Mでのスタックダンプ連携 (`GOTRACEBACK=crash`時)**:
    *   `docrash`が真（`GOTRACEBACK=crash`が設定されている）の場合の処理が強化されました。
    *   `if GOOS == "linux"`のブロックが追加され、Linux環境でのみこの連携メカニズムが有効になります。
    *   `crashing++`で、現在のMがクラッシュ処理に参加したことを示します。
    *   `if crashing < sched.mcount`の条件は、まだすべてのMがクラッシュ処理に参加していない場合に真となります。`sched.mcount`は、Goランタイムが管理するMの総数です。
    *   `raiseproc(_SIGQUIT)`を呼び出すことで、現在のプロセスに`SIGQUIT`シグナルを送信します。Goランタイムのシグナルハンドリングの仕組みにより、既に`SIGQUIT`を受け取ったMはシグナルマスクで`SIGQUIT`をブロックしているため、このシグナルはまだ`SIGQUIT`を受け取っていない別のMに配送されます。これにより、すべてのMが順次クラッシュ処理に参加し、それぞれのゴルーチンのスタックトレースをダンプする機会を得ます。
    *   `usleep(5 * 1000 * 1000)`（5秒間スリープ）は、シグナルリレーが何らかの理由で失敗した場合のフォールバックメカニズムです。もし他のMが`SIGQUIT`を受け取らず、プロセスが終了しない場合でも、このMは5秒後に自力で`crash()`を呼び出し、プロセスを終了させます。これにより、プロセスがハングアップするのを防ぎます。
    *   最後のMが`SIGQUIT`を受け取ると、`crashing < sched.mcount`の条件が偽となり、`raiseproc`の呼び出しはスキップされ、直接`crash()`が呼び出されてプロセスが終了します。

5.  **`tracebackothers`の条件付き呼び出し**:
    *   `if crashing > 0 && gp != _g_.m.curg && _g_.m.curg != nil && readgstatus(_g_.m.curg)&^_Gscan == _Grunning`という複雑な条件が追加されました。これは、`GOTRACEBACK=crash`が有効で、かつ現在のMが最初にクラッシュ処理を開始したMではない場合に、`tracebackothers`がスキップされたゴルーチンをトレースするためのものです。
    *   `else if crashing == 0`のブロックは、`GOTRACEBACK=crash`ではないか、または最初にクラッシュ処理を開始したMの場合に、通常の`tracebackothers`と改行を出力します。

これらの変更により、`linux/386`環境でのGoプログラムのクラッシュ時に、より正確で包括的なスタックトレースが提供されるようになりました。

## コアとなるコードの解説

### `var crashing int32` の追加

*   `crashing`変数は、複数のOSスレッド（M）が同時にクラッシュ処理を開始しようとするのを調整するために導入されました。`int32`型であり、アトミックな操作が想定されます（Goランタイム内部ではアトミック操作が保証される）。

### `sighandler`関数内の変更

1.  **`startpanic()`の条件付き呼び出し**:
    ```go
    if crashing == 0 {
    	startpanic()
    }
    ```
    シグナルハンドラが呼び出された際、`crashing`が`0`（つまり、まだどのMもクラッシュ処理を開始していない）の場合にのみ`startpanic()`が呼び出されます。これにより、パニック処理の初期化が一度だけ行われることが保証されます。

2.  **`PC`出力の強化**:
    ```go
    print("PC=", hex(c.eip()), " m=", _g_.m.id, "\n")
    ```
    プログラムカウンタ（`c.eip()`）の出力に加えて、現在のMのID（`_g_.m.id`）が追加されました。これにより、どのOSスレッドでクラッシュが発生したかを特定しやすくなります。

3.  **`vdso kernel_vsyscall`のアンワインドロジック**:
    ```go
    pc := uintptr(c.eip())
    sp := uintptr(c.esp())
    if GOOS == "linux" && pc >= 0xf4000000 && gp.stack.lo <= sp && sp+16 <= gp.stack.hi {
    	// Assume in vsyscall page.
    	sp += 16
    	pc = *(*uintptr)(unsafe.Pointer(sp - 4))
    	print("runtime: unwind vdso kernel_vsyscall: pc=", hex(pc), " sp=", hex(sp), "\n")
    }
    tracebacktrap(pc, sp, 0, gp)
    ```
    *   `c.eip()`と`c.esp()`から現在のPCとSPを取得します。
    *   `GOOS == "linux"`かつPCが`0xf4000000`以上の範囲（`vdso`領域の一般的な開始アドレス）にあり、かつスタックポインタが有効なスタック範囲内（`gp.stack.lo <= sp && sp+16 <= gp.stack.hi`）である場合、`vdso kernel_vsyscall`ルーチン内にいると判断します。
    *   `sp += 16`でスタックポインタを16バイト進めます。これは、`kernel_vsyscall`がスタックに保存した内部的な値と、そのルーチンに入る前の呼び出し元のPCをスキップするためです。
    *   `pc = *(*uintptr)(unsafe.Pointer(sp - 4))`で、調整されたスタックポインタから4バイト手前（`uintptr`のサイズ）にある値を読み取り、これを真の呼び出し元PCとします。
    *   デバッグメッセージが出力され、その後、この調整された`pc`と`sp`を使って`tracebacktrap()`が呼び出され、より正確なスタックトレースが生成されます。

    ```go
    }
    ```
    *   `GOTRACEBACK=crash`が有効で、かつ現在のMが最初にクラッシュ処理を開始したMではない場合（`crashing > 0`）、`tracebackothers`がスキップされたゴルーチンをトレースするために、`_g_.m.curg`（現在のMで実行中のゴルーチン）のヘッダを出力し、`traceback`を呼び出します。
    *   `crashing == 0`の場合（`GOTRACEBACK=crash`ではないか、または最初にクラッシュ処理を開始したMの場合）は、通常の`tracebackothers`が呼び出されます。

5.  **複数Mでのスタックダンプ連携 (`docrash`ブロック内)**:
    ```go
    if docrash {
    	if GOOS == "linux" {
    		crashing++
    		if crashing < sched.mcount {
    			// ... (コメント省略) ...
    			print("\n-----\n\n")
    			raiseproc(_SIGQUIT)
    			usleep(5 * 1000 * 1000)
    		}
    	}
    	crash()
    }
    ```
    *   `docrash`が真（`GOTRACEBACK=crash`）の場合、`GOOS == "linux"`の条件でLinux固有の処理が実行されます。
    *   `crashing++`で、現在のMがクラッシュ処理に参加したことを記録します。
    *   `crashing < sched.mcount`の条件が真の場合、まだすべてのMがクラッシュ処理に参加していないことを意味します。
    *   `raiseproc(_SIGQUIT)`を呼び出すことで、プロセス全体に`SIGQUIT`シグナルを送信し、まだシグナルを受け取っていない他のMにクラッシュ処理を促します。
    *   `usleep(5 * 1000 * 1000)`で5秒間スリープします。これは、シグナルリレーが失敗した場合のフォールバックとして、プロセスがハングアップするのを防ぐためのものです。
    *   最終的に、`crash()`が呼び出され、プロセスが終了します。

これらの変更により、`linux/386`環境での`GOTRACEBACK=crash`の動作がより堅牢になり、デバッグ時に役立つ完全なスタックトレースが提供されるようになりました。

# [インデックス 2151] ファイルの概要

このコミットは、Goコンパイラ（`6g`および`gc`）における文字列データの扱いを根本的に変更するものです。具体的には、文字列リテラルを個別のシンボルとして出力するようにし、これによりリンカが未使用の文字列データを破棄（デッドコードエリミネーション）できるように改善しています。さらに、短い文字列については、複数のファイルで同じ文字列が参照されていても、リンカが重複排除を行えるように`DUPOK`属性を持つグローバルシンボルとして生成するようになりました。これにより、最終的なバイナリサイズが削減され、効率が向上します。

## 変更の背景

このコミットが行われた2009年当時、Goコンパイラ（`6g`）は文字列リテラルを単一の大きな文字列プールにまとめていました。この方式にはいくつかの問題がありました。

1.  **デッドコードエリミネーションの妨げ**: 文字列プール全体が単一の大きなデータブロックとして扱われるため、たとえプログラムの実行パスから到達不能な（デッドコードによってのみ参照される）文字列があったとしても、リンカ（`6l`）はその文字列だけを個別に破棄することが困難でした。結果として、最終的なバイナリに不要な文字列データが含まれ、バイナリサイズが増大していました。
2.  **文字列の重複排除の非効率性**: 複数のソースファイルで同じ文字列リテラル（例: `"%s: %s"`）が使用されている場合でも、リンカレベルでの効率的な重複排除が行われていませんでした。これは、コンパイラが文字列を個別のシンボルとして適切に識別していなかったためです。

これらの問題を解決し、バイナリサイズの削減とコンパイル済みコードの効率化を図るために、文字列データの生成方法の見直しが必要とされました。

## 前提知識の解説

このコミットの理解には、以下の概念が重要です。

*   **Goコンパイラ (`6g`, `gc`)**:
    *   `gc` (Go Compiler): Go言語のフロントエンドコンパイラで、Goのソースコードを中間表現に変換し、型チェックや最適化を行います。
    *   `6g`: `gc`のバックエンドの一つで、64ビットアーキテクチャ（AMD64）向けの機械語を生成します。Go 1.5以降は`go tool compile`に統合され、アーキテクチャ固有のコンパイラ名は使われなくなりましたが、このコミット当時は独立したツールでした。
*   **シンボル (Symbol)**: プログラム内の関数、グローバル変数、静的変数、文字列リテラルなどの実体を識別するための名前です。コンパイラはソースコードからシンボルを生成し、リンカはこれらのシンボルを解決して最終的な実行可能ファイルを生成します。
*   **リンカ (Linker)**: コンパイラが生成した複数のオブジェクトファイル（`.o`ファイルなど）を結合し、必要なライブラリとリンクして、実行可能なバイナリファイルを生成するツールです。リンカの主要な役割の一つに、シンボル解決とアドレス割り当てがあります。
*   **デッドコードエリミネーション (Dead Code Elimination, DCE)**: リンカやコンパイラが行う最適化の一種で、プログラムの実行に決して到達しないコードやデータを最終的なバイナリから削除するプロセスです。これにより、バイナリサイズが削減され、起動時間やメモリ使用量が改善されます。
*   **文字列リテラル (String Literals)**: ソースコード中に直接記述された文字列定数（例: `"Hello, World!"`）です。これらは通常、実行可能ファイルのデータセクションに格納されます。
*   **`DUPOK` シンボル属性**: アセンブラやリンカの文脈で使われる概念で、「重複してもOK」を意味します。この属性を持つシンボルは、複数のオブジェクトファイルで同じ名前で定義されていても、リンカがエラーとせず、通常はそれらを単一の実体にマージ（重複排除）します。これにより、同じ定数データがバイナリ内に複数存在することを防ぎ、サイズを削減できます。

## 技術的詳細

このコミットの核心は、Goコンパイラが文字列リテラルを処理し、アセンブリコードとして出力する方法の変更にあります。

1.  **文字列の個別シンボル化**:
    *   以前は、すべての文字列リテラルが`symstringc`という単一の大きなシンボル（文字列プール）にまとめられていました。
    *   変更後、`datastring`関数が文字列ごとにユニークなシンボルを生成するようになりました。短い文字列（長さ100バイト以下）には`pkglookup`関数を使って`D_EXTERN`（外部参照可能）なシンボルを生成し、長い文字列には`lookup`関数を使って`.string.N`のような静的なシンボルを生成します。
    *   `D_EXTERN`シンボルは、リンカが異なるオブジェクトファイル間で同じ名前のシンボルを重複排除する対象となります。これにより、例えば`fmt.Printf`などで使われる共通のフォーマット文字列（`"%s: %s"`など）が、複数のソースファイルで参照されていても、最終バイナリでは1つの実体として扱われるようになります。
    *   `ao.sym->uniq = 1`というフラグが導入され、同じシンボルに対してデータが複数回生成されるのを防ぎます。これにより、コンパイラが同じ文字列を複数回処理しても、アセンブリコード上では一度だけデータが定義されます。

2.  **デッドコードエリミネーションの実現**:
    *   文字列が個別のシンボルとして出力されるようになったことで、リンカ（`6l`）は、その文字列を参照するコードがデッドコードとして削除された場合、対応する文字列シンボルも不要と判断し、最終バイナリから破棄できるようになりました。これは、リンカのデッドコードエリミネーション機能が、関数だけでなくデータにも適用されるようになったことを意味します。

3.  **文字列プール機構の廃止**:
    *   `src/cmd/gc/go.h`、`src/cmd/gc/lex.c`、`src/cmd/gc/obj.c`から、`Pool`構造体、`symstringl`、`symstringc`、`stringpool`、`dumpstrings`といった、従来の文字列プールを管理していたグローバル変数や関数が削除されました。これは、文字列管理の責任が、コンパイラ内の集中プールから、個々の文字列シンボルを生成する新しいメカニズムへと移行したことを明確に示しています。

4.  **データ出力の遅延処理**:
    *   `src/cmd/6g/obj.c`に`data()`、`text()`、`dumpdata()`といった新しい関数が追加されました。これは、文字列データのアセンブリコード生成を一時的にバッファリングし、後でまとめて出力するためのメカニズムです。これにより、コード生成のフローがより整理され、文字列データの出力が他のコード生成と適切に分離されるようになります。

最も重要な変更は`src/cmd/6g/obj.c`の`datastring`関数と`datagostring`関数、そしてそれらをサポートする`data`/`text`フレームワークです。

**`datastring`関数の変更点**:

```c
// 旧: void datastring(char *s, int len)
// 新: void datastring(char *s, int len, Addr *a)

// ... (中略) ...

	// huge strings are made static to avoid long names.
	if(len > 100) {
		snprint(namebuf, sizeof(namebuf), ".string.%d", gen++);
		ao.sym = lookup(namebuf);
		ao.type = D_STATIC; // 静的シンボル
	} else {
		if(len > 0 && s[len-1] == '\0')
			len--;
		tmp.lit.len = len;
		memmove(tmp.lit.s, s, len);
		tmp.lit.s[len] = '\0';
		len++;
		snprint(namebuf, sizeof(namebuf), "\"%Z\"", &tmp.lit);
		ao.sym = pkglookup(namebuf, "string"); // パッケージスコープのシンボル
		ao.type = D_EXTERN; // 外部参照可能（DUPOKの可能性）
	}
	*a = ao;

	// only generate data the first time.
	if(ao.sym->uniq)
		return;
	ao.sym->uniq = 1;

	data(); // データ出力フェーズ開始
	for(w=0; w<len; w+=8) {
		p = pc;
		gins(ADATA, N, N); // データ命令を生成
		p->from = ao;
		p->from.offset = w;
		// ... (データ内容のコピー) ...
	}
	p = pc;
	ggloblsym(ao.sym, len, ao.type == D_EXTERN); // グローバルシンボルとして定義
	if(ao.type == D_STATIC)
		p->from.type = D_STATIC;
	text(); // テキスト出力フェーズに戻る
```

*   `datastring`は、生のバイト列（C文字列）をアセンブリのデータセクションに出力する役割を担います。
*   文字列の長さによって、生成されるシンボルの種類が変わります。
    *   **長い文字列 (len > 100)**: `.string.N`のようなユニークな静的シンボル（`D_STATIC`）として生成されます。これは、リンカがこのシンボルを他のファイルと重複排除しないことを意味します。
    *   **短い文字列**: 文字列の内容を元にした名前（例: `"%s: %s"`）で、パッケージスコープの外部参照可能シンボル（`D_EXTERN`）として生成されます。この`D_EXTERN`は、リンカが同じ内容の文字列を複数のオブジェクトファイルから見つけた場合に、それらを単一の実体にマージ（重複排除）することを可能にします。これは実質的に`DUPOK`属性として機能します。
*   `ao.sym->uniq = 1`は、同じ文字列シンボルに対してデータが複数回生成されるのを防ぐための最適化です。
*   `data()`と`text()`は、コード生成のコンテキストを切り替えるためのヘルパー関数です。`data()`が呼ばれると、生成されるアセンブリ命令はデータセクション向けにバッファリングされ、`text()`が呼ばれると通常のコード生成に戻ります。`dumpdata()`が最終的にバッファリングされたデータを出力します。

**`datagostring`関数の変更点**:

```c
// 旧: void dumpstrings(void)
// 新: void datagostring(Strlit *sval, Addr *a)

// ... (中略) ...

	datastring(sval->s, sval->len, &ap); // 生の文字列データを生成

	if(ap.index == D_STATIC) {
		// huge strings are made static to avoid long names
		snprint(namebuf, sizeof(namebuf), ".gostring.%d", ++gen);
		ao.sym = lookup(namebuf);
		ao.type = D_STATIC;
	} else {
		// small strings get named by their contents,
		// so that multiple modules using the same string
		// can share it.
		snprint(namebuf, sizeof(namebuf), "\"%Z\"", sval);
		ao.sym = pkglookup(namebuf, "go.string");
		ao.type = D_EXTERN;
	}

	*a = ao;
	if(ao.sym->uniq)
		return;
	ao.sym->uniq = 1;

	data();
	// DATA gostring, wp, $cstring (文字列データへのポインタ)
	p = pc;
	gins(ADATA, N, N);
	p->from = ao;
	p->from.scale = wp;
	p->to = ap;

	// DATA gostring+wp, wi, $len (文字列の長さ)
	p = pc;
	gins(ADATA, N, N);
	p->from = ao;
	p->from.offset = wp;
	p->from.scale = wi;
	p->to = ac;
	p->to.offset = sval->len;
	
	p = pc;
	ggloblsym(ao.sym, types[TSTRING]->width, ao.type == D_EXTERN);
	if(ao.type == D_STATIC)
		p->from.type = D_STATIC;
	text();
```

*   `datagostring`は、Go言語の文字列型（長さとデータへのポインタのペア）を表現するデータ構造をアセンブリに出力します。
*   内部で`datastring`を呼び出し、実際の文字列バイト列を生成させます。
*   Goの文字列構造体（ポインタと長さ）を表現するシンボルも、`datastring`と同様に、長さによって`D_STATIC`または`D_EXTERN`として生成されます。これにより、Goの文字列リテラル自体もリンカによる重複排除の恩恵を受けられるようになります。

これらの変更により、Goコンパイラは文字列リテラルをより粒度の高いシンボルとして出力するようになり、リンカがデッドコードエリミネーションと効率的な重複排除を実行するための基盤が整いました。

*   **シンボル (Symbol)**: プログラム内の関数、グローバル変数、静的変数、文字列リテラルなどの実体を識別するための名前です。コンパイラはソースコードからシンボルを生成し、リンカはこれらのシンボルを解決して最終的な実行可能ファイルを生成します。
*   **リンカ (Linker)**: コンパイラが生成した複数のオブジェクトファイル（`.o`ファイルなど）を結合し、必要なライブラリとリンクして、実行可能なバイナリファイルを生成するツールです。リンカの主要な役割の一つに、シンボル解決とアドレス割り当てがあります。
*   **デッドコードエリミネーション (Dead Code Elimination, DCE)**: リンカやコンパイラが行う最適化の一種で、プログラムの実行に決して到達しないコードやデータを最終的なバイナリから削除するプロセスです。これにより、バイナリサイズが削減され、起動時間やメモリ使用量が改善されます。
*   **文字列リテラル (String Literals)**: ソースコード中に直接記述された文字列定数（例: `"Hello, World!"`）です。これらは通常、実行可能ファイルのデータセクションに格納されます。
*   **`DUPOK` シンボル属性**: アセンブラやリンカの文脈で使われる概念で、「重複してもOK」を意味します。この属性を持つシンボルは、複数のオブジェクトファイルで同じ名前で定義されていても、リンカがエラーとせず、通常はそれらを単一の実体にマージ（重複排除）します。これにより、同じ定数データがバイナリ内に複数存在することを防ぎ、サイズを削減できます。

## 技術的詳細

このコミットの核心は、Goコンパイラが文字列リテラルを処理し、アセンブリコードとして出力する方法の変更にあります。

1.  **文字列の個別シンボル化**:
    *   以前は、すべての文字列リテラルが`symstringc`という単一の大きなシンボル（文字列プール）にまとめられていました。
    *   変更後、`datastring`関数が文字列ごとにユニークなシンボルを生成するようになりました。短い文字列（長さ100バイト以下）には`pkglookup`関数を使って`D_EXTERN`（外部参照可能）なシンボルを生成し、長い文字列には`lookup`関数を使って`.string.N`のような静的なシンボルを生成します。
    *   `D_EXTERN`シンボルは、リンカが異なるオブジェクトファイル間で同じ名前のシンボルを重複排除する対象となります。これにより、例えば`fmt.Printf`などで使われる共通のフォーマット文字列（`"%s: %s"`など）が、複数のソースファイルで参照されていても、最終バイナリでは1つの実体として扱われるようになります。
    *   `ao.sym->uniq = 1`というフラグが導入され、同じシンボルに対してデータが複数回生成されるのを防ぎます。これにより、コンパイラが同じ文字列を複数回処理しても、アセンブリコード上では一度だけデータが定義されます。

2.  **デッドコードエリミネーションの実現**:
    *   文字列が個別のシンボルとして出力されるようになったことで、リンカ（`6l`）は、その文字列を参照するコードがデッドコードとして削除された場合、対応する文字列シンボルも不要と判断し、最終バイナリから破棄できるようになりました。これは、リンカのデッドコードエリミネーション機能が、関数だけでなくデータにも適用されるようになったことを意味します。

3.  **文字列プール機構の廃止**:
    *   `src/cmd/gc/go.h`、`src/cmd/gc/lex.c`、`src/cmd/gc/obj.c`から、`Pool`構造体、`symstringl`、`symstringc`、`stringpool`、`dumpstrings`といった、従来の文字列プールを管理していたグローバル変数や関数が削除されました。これは、文字列管理の責任が、コンパイラ内の集中プールから、個々の文字列シンボルを生成する新しいメカニズムへと移行したことを明確に示しています。

4.  **データ出力の遅延処理**:
    *   `src/cmd/6g/obj.c`に`data()`、`text()`、`dumpdata()`といった新しい関数が追加されました。これは、文字列データのアセンブリコード生成を一時的にバッファリングし、後でまとめて出力するためのメカニズムです。これにより、コード生成のフローがより整理され、文字列データの出力が他のコード生成と適切に分離されるようになります。

## コアとなるコードの解説

最も重要な変更は`src/cmd/6g/obj.c`の`datastring`関数と`datagostring`関数、そしてそれらをサポートする`data`/`text`フレームワークです。

**`datastring`関数の変更点**:

```c
// 旧: void datastring(char *s, int len)
// 新: void datastring(char *s, int len, Addr *a)

// ... (中略) ...

	// huge strings are made static to avoid long names.
	if(len > 100) {
		snprint(namebuf, sizeof(namebuf), ".string.%d", gen++);
		ao.sym = lookup(namebuf);
		ao.type = D_STATIC; // 静的シンボル
	} else {
		if(len > 0 && s[len-1] == '\0')
			len--;
		tmp.lit.len = len;
		memmove(tmp.lit.s, s, len);
		tmp.lit.s[len] = '\0';
		len++;
		snprint(namebuf, sizeof(namebuf), "\"%Z\"", &tmp.lit);
		ao.sym = pkglookup(namebuf, "string"); // パッケージスコープのシンボル
		ao.type = D_EXTERN; // 外部参照可能（DUPOKの可能性）
	}
	*a = ao;

	// only generate data the first time.
	if(ao.sym->uniq)
		return;
	ao.sym->uniq = 1;

	data(); // データ出力フェーズ開始
	for(w=0; w<len; w+=8) {
		p = pc;
		gins(ADATA, N, N); // データ命令を生成
		p->from = ao;
		p->from.offset = w;
		// ... (データ内容のコピー) ...
	}
	p = pc;
	ggloblsym(ao.sym, len, ao.type == D_EXTERN); // グローバルシンボルとして定義
	if(ao.type == D_STATIC)
		p->from.type = D_STATIC;
	text(); // テキスト出力フェーズに戻る
```

*   `datastring`は、生のバイト列（C文字列）をアセンブリのデータセクションに出力する役割を担います。
*   文字列の長さによって、生成されるシンボルの種類が変わります。
    *   **長い文字列 (len > 100)**: `.string.N`のようなユニークな静的シンボル（`D_STATIC`）として生成されます。これは、リンカがこのシンボルを他のファイルと重複排除しないことを意味します。
    *   **短い文字列**: 文字列の内容を元にした名前（例: `"%s: %s"`）で、パッケージスコープの外部参照可能シンボル（`D_EXTERN`）として生成されます。この`D_EXTERN`は、リンカが同じ内容の文字列を複数のオブジェクトファイルから見つけた場合に、それらを単一の実体にマージ（重複排除）することを可能にします。これは実質的に`DUPOK`属性として機能します。
*   `ao.sym->uniq = 1`は、同じ文字列シンボルに対してデータが複数回生成されるのを防ぐための最適化です。
*   `data()`と`text()`は、コード生成のコンテキストを切り替えるためのヘルパー関数です。`data()`が呼ばれると、生成されるアセンブリ命令はデータセクション向けにバッファリングされ、`text()`が呼ばれると通常のコード生成に戻ります。`dumpdata()`が最終的にバッファリングされたデータを出力します。

**`datagostring`関数の変更点**:

```c
// 旧: void dumpstrings(void)
// 新: void datagostring(Strlit *sval, Addr *a)

// ... (中略) ...

	datastring(sval->s, sval->len, &ap); // 生の文字列データを生成

	if(ap.index == D_STATIC) {
		// huge strings are made static to avoid long names
		snprint(namebuf, sizeof(namebuf), ".gostring.%d", ++gen);
		ao.sym = lookup(namebuf);
		ao.type = D_STATIC;
	} else {
		// small strings get named by their contents,
		// so that multiple modules using the same string
		// can share it.
		snprint(namebuf, sizeof(namebuf), "\"%Z\"", sval);
		ao.sym = pkglookup(namebuf, "go.string");
		ao.type = D_EXTERN;
	}

	*a = ao;
	if(ao.sym->uniq)
		return;
	ao.sym->uniq = 1;

	data();
	// DATA gostring, wp, $cstring (文字列データへのポインタ)
	p = pc;
	gins(ADATA, N, N);
	p->from = ao;
	p->from.scale = wp;
	p->to = ap;

	// DATA gostring+wp, wi, $len (文字列の長さ)
	p = pc;
	gins(ADATA, N, N);
	p->from = ao;
	p->from.offset = wp;
	p->from.scale = wi;
	p->to = ac;
	p->to.offset = sval->len;
	
	p = pc;
	ggloblsym(ao.sym, types[TSTRING]->width, ao.type == D_EXTERN);
	if(ao.type == D_STATIC)
		p->from.type = D_STATIC;
	text();
```

*   `datagostring`は、Go言語の文字列型（長さとデータへのポインタのペア）を表現するデータ構造をアセンブリに出力します。
*   内部で`datastring`を呼び出し、実際の文字列バイト列を生成させます。
*   Goの文字列構造体（ポインタと長さ）を表現するシンボルも、`datastring`と同様に、長さによって`D_STATIC`または`D_EXTERN`として生成されます。これにより、Goの文字列リテラル自体もリンカによる重複排除の恩恵を受けられるようになります。

これらの変更により、Goコンパイラは文字列リテラルをより粒度の高いシンボルとして出力するようになり、リンカがデッドコードエリミネーションと効率的な重複排除を実行するための基盤が整いました。

## 変更の背景

このコミットの主な背景は、Goプロジェクトの内部的な開発環境である `dev.cc` における386アーキテクチャ（32ビットx86）向けのビルドが失敗していた問題の修正です。具体的には、Goのアセンブラ (`cmd/asm`) が `CALL *x(SB)` という形式の間接呼び出し命令を正しく処理できていませんでした。

Goのランタイムや標準ライブラリの一部は、パフォーマンス最適化や低レベルなハードウェア操作のためにアセンブリ言語で記述されています。これらのアセンブリコードは `cmd/asm` によって機械語に変換されます。`CALL *x(SB)` は、グローバルシンボル `x` のアドレスに格納されている値を呼び出し先のアドレスとして使用する間接呼び出しです。32ビット環境では、ポインタのサイズが32ビットであるため、アドレスの扱いに特有の注意が必要です。

この問題は、`cmd/asm` の `asmJump` 関数が、`obj.TYPE_INDIR` 型のアドレス（間接アドレス）を持つターゲットを適切に扱っていなかったことに起因します。特に、外部シンボルや静的シンボルに対する間接呼び出しが正しく解決されず、ビルドエラーが発生していました。このコミットは、この特定のケースを `cmd/asm` が認識し、正しく処理できるようにすることで、`dev.cc` の386ビルドを修正することを目的としています。

## 前提知識の解説

### Goのアセンブラ (cmd/asm)

`cmd/asm` はGoツールチェーンの一部であり、Goのアセンブリ言語ソースファイル（`.s` 拡張子）をオブジェクトファイル（`.o` 拡張子）に変換する役割を担っています。Goのアセンブリは、一般的なアセンブリ言語とは異なり、Goのリンカと連携して動作する独自の構文を持っています。特に、`FP` (Frame Pointer) や `SB` (Static Base) といった擬似レジスタを使用し、異なるアーキテクチャ間での一貫性を保ちつつ、低レベルな操作を可能にします。

### 386アーキテクチャ

`386` は、32ビットのx86命令セットアーキテクチャを指します。Goのビルドにおいて、`GOARCH=386` を設定することで、32ビットx86プロセッサで実行可能なバイナリを生成できます。Goはクロスコンパイルをサポートしており、異なるOSやアーキテクチャ向けのバイナリを生成することが可能です。32ビット環境では、ポインタのサイズが32ビットに制限されるため、64ビット環境とは異なるアドレス指定やメモリ管理の考慮が必要となる場合があります。

### Goのアセンブリにおけるシンボル参照 (SB)

Goのアセンブリ言語では、`SB` (Static Base) は静的メモリセグメントのベースアドレスを表す擬似レジスタです。すべてのグローバルシンボル（関数やデータ）は、`SB` からのオフセットとしてアドレス指定されます。例えば、`main·morestack(SB)` は、`main` パッケージ内の `morestack` というグローバルシンボルを参照します。

### 間接呼び出し (CALL *x)

`CALL` は、サブルーチンを呼び出すx86命令です。通常、`CALL` 命令は直接アドレスを指定してジャンプしますが、`*` を使用すると間接呼び出しになります。`CALL *x` は、`x` のアドレスに格納されている値を呼び出し先のアドレスとして使用することを意味します。つまり、呼び出しのターゲットアドレスは実行時に決定されます。これは、関数ポインタ、仮想メソッドディスパッチ、または位置独立コードの実装によく使用されます。

### Goのobjパッケージ

`cmd/internal/obj` パッケージは、Goコンパイラとリンカが中間オブジェクトファイル形式を扱うために使用する内部パッケージです。このパッケージは、アセンブリ命令、アドレス、シンボルを表現するための構造体や列挙型を定義しています。

*   **`obj.Addr`**: アセンブリ命令のオペランドのアドレスを表す構造体です。
*   **`obj.TYPE_MEM`**: アドレスオペランドがメモリ位置を参照することを示します。
*   **`obj.TYPE_INDIR`**: アドレスが間接的であることを示します。通常、アドレスはレジスタまたは別のメモリ位置に格納されており、オペランドはその間接アドレスの値を参照します。
*   **`obj.TYPE_BRANCH`**: アドレスオペランドが分岐命令（ジャンプや呼び出しなど）のターゲットであることを示します。
*   **`obj.NAME_EXTERN`**: 外部シンボルを表します。これは、別のコンパイル単位またはパッケージで定義されており、リンカによって解決される必要があるシンボルです。
*   **`obj.NAME_STATIC`**: 静的シンボルを表します。これは通常、内部リンケージを持つグローバルまたはパッケージレベルの変数または関数で、そのコンパイル単位の外にはエクスポートされません。
*   **`obj.Linklookup`**: `cmd/internal/obj` パッケージ内の `Lookup` メソッドを指します。リンカのコンテキスト内でシンボルを名前で検索する役割を担います。

## 技術的詳細

このコミットの技術的な核心は、`cmd/asm` の `asmJump` 関数が `CALL *x(SB)` のような間接呼び出しを正しく処理できるようにすることです。以前の `asmJump` 関数では、`obj.TYPE_MEM` 型のターゲットアドレスが `obj.NAME_EXTERN` または `obj.NAME_STATIC` の名前を持つ場合に、特別な処理を行っていました。この処理は、シンボルをリンカのコンテキストでルックアップし、`obj.TYPE_BRANCH` 型のアドレスとして設定していました。

しかし、`CALL *x(SB)` のような間接呼び出しの場合、ターゲットは単なるメモリ参照 (`TYPE_MEM`) ではなく、そのメモリ位置に格納されている値が実際のアドレスとなる間接参照 (`TYPE_INDIR`) です。以前の実装では、この `TYPE_INDIR` のケースが明示的に処理されていなかったため、386ビルドで問題が発生していました。

このコミットでは、以下の変更が加えられました。

1.  **`obj.TYPE_MEM` の処理の簡素化**: 以前の `obj.TYPE_MEM` かつ `obj.NAME_EXTERN` または `obj.NAME_STATIC` の場合の複雑な `obj.Addr` の構築ロジックが削除され、単に `prog.To = *target` となりました。これは、`obj.TYPE_MEM` のターゲットが直接的なメモリ参照として扱われるべきであることを示唆しています。
2.  **`obj.TYPE_INDIR` の新しいケースの追加**: `target.Type == obj.TYPE_INDIR` かつ `obj.NAME_EXTERN` または `obj.NAME_STATIC` の名前を持つ場合の新しいケースが追加されました。このケースでは、`prog.To = *target` とした上で、`prog.To.Type = obj.TYPE_INDIR` と明示的に設定しています。これにより、アセンブラはターゲットが間接アドレスであることを正しく認識し、リンカが後続の処理で適切に解決できるようになります。

この変更により、`cmd/asm` は `CALL *x(SB)` のような間接呼び出しを、その間接的な性質を保持したまま、リンカに渡すことができるようになりました。これにより、386アーキテクチャにおける間接呼び出しの解決が正しく行われ、`dev.cc` ビルドの問題が解消されました。

## コアとなるコードの解説

変更は `src/cmd/asm/internal/asm/asm.go` ファイルの `asmJump` 関数内で行われています。この関数は、ジャンプ命令（`JMP`, `CALL` など）のターゲットアドレスを処理する役割を担っています。

元のコードでは、`target.Type == obj.TYPE_MEM` かつ `target.Name == obj.NAME_EXTERN` または `obj.NAME_STATIC` の場合に、ターゲットシンボルを `obj.Linklookup` でルックアップし、`obj.TYPE_BRANCH` 型の新しい `obj.Addr` を構築していました。これは、直接的なジャンプ先としてシンボルを解決しようとするロジックでした。

このコミットでは、この部分が以下のように変更されました。

1.  **`obj.TYPE_MEM` のケース**:
    ```go
    case target.Type == obj.TYPE_MEM && (target.Name == obj.NAME_EXTERN || target.Name == obj.NAME_STATIC):
        // JMP main·morestack(SB)
        prog.To = *target
    ```
    以前の複雑な `obj.Addr` の構築ロジックが削除され、単に `prog.To = *target` となりました。これは、`TYPE_MEM` のターゲットは、そのシンボルが指すメモリ位置を直接参照するべきであり、アセンブラがそのアドレスをそのまま `prog.To` に設定すればよいことを意味します。リンカが後でこのメモリ参照を適切に解決します。

2.  **`obj.TYPE_INDIR` の新しいケース**:
    ```go
    case target.Type == obj.TYPE_INDIR && (target.Name == obj.NAME_EXTERN || target.Name == obj.NAME_STATIC):
        // JMP *main·morestack(SB)
        prog.To = *target
        prog.To.Type = obj.TYPE_INDIR
    ```
    この新しいケースは、`target.Type` が `obj.TYPE_INDIR` であり、かつターゲットが外部シンボルまたは静的シンボルである場合を明示的に処理します。`CALL *x(SB)` のような命令がこのケースに該当します。
    ここでも `prog.To = *target` とすることで、元のターゲットアドレスの情報をコピーします。しかし、重要なのはその次の行 `prog.To.Type = obj.TYPE_INDIR` です。これにより、`prog.To` の型が `obj.TYPE_INDIR` であることが明示的に設定されます。これは、このアドレスが直接的なジャンプ先ではなく、そのアドレスに格納されている値が真のジャンプ先であることをリンカに伝えます。

この変更により、`cmd/asm` は `CALL *x(SB)` のような間接呼び出しを、その間接的な性質を正確に表現した `obj.Addr` 構造体として生成できるようになり、リンカがこれを正しく解釈して最終的なバイナリを生成できるようになりました。これにより、386アーキテクチャでのビルド問題が解決されました。

# [インデックス 24048] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージにおけるレース検出器の挙動、特に`OBLOCK`ノードの処理に関する問題を修正するものです。`OBLOCK`ノードは、複数のステートメントをグループ化するためにコンパイラ内部で使用される抽象構文木（AST）ノードの一種です。この修正は、レース検出器が関数呼び出しからの複数の戻り値を正しく処理できるようにすることを目的としています。

## 元コミット内容

このコミットは、Goコンパイラのレース検出器が`OBLOCK`ノードを処理する際のバグを修正します。特に、関数が複数の戻り値を返す場合に、レース検出器が誤ったインストゥルメンテーションを行う可能性がありました。これは、`x, y := f()`のような多値代入がコンパイラ内部で`BLOCK{CALL f, AS x [SP+0], AS y [SP+n]}`のような`OBLOCK`ノードとして表現されることに起因します。レース検出器は、これらのステートメント間にインストゥルメンテーションコードを挿入すべきではありません。なぜなら、それは関数呼び出しの結果を破壊する可能性があるためです。このコミットは、この問題を修正し、`#7561`と`#9137`という2つの関連するバグを解決します。

## 変更の背景

このコミットの背景には、Goのレース検出器が特定のコードパターン、特に複数の戻り値を持つ関数呼び出しとそれらの戻り値の代入を伴う`OBLOCK`ノードを正しく扱えていなかったという問題があります。

*   **Issue #7561**: このイシューは、`x, y := f()`のような多値代入において、レース検出器が誤ったコードを生成し、結果としてプログラムがクラッシュしたり、誤ったレース検出を報告したりする可能性を指摘していました。具体的には、関数呼び出しとその戻り値をスタックからレジスタや変数にコピーする代入操作の間に、レース検出器のインストゥルメンテーションが挿入されることで、スタック上のデータが破壊される可能性がありました。
*   **Issue #9137**: このイシューは、スライス操作における同様の問題を指摘していました。`a[i], a[len(a)-1], a = a[len(a)-1], "", a[:len(a)-1]`のような複雑なスライス代入が、レース検出器によって誤って処理され、データが破損するケースがありました。これは、多値代入と同様に、コンパイラが内部的に`OBLOCK`ノードを生成し、その中の特定の操作がレース検出器によって不適切にインストゥルメントされていたためと考えられます。

これらの問題は、Goのレース検出器の信頼性を損なうものであり、正確なレース検出のためには修正が不可欠でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールチェーンの一部です。コンパイルの過程で、ソースコードは抽象構文木（AST）に変換され、様々な最適化やコード生成が行われます。
*   **抽象構文木 (AST)**: プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラはASTを操作してコードを分析・変換します。
*   **`OBLOCK`ノード**: GoコンパイラのASTにおけるノードタイプの一つで、複数のステートメントをグループ化するために使用されます。例えば、`if`文の本体や、複数の戻り値を持つ関数呼び出しの処理などで生成されます。
*   **レース検出器 (Race Detector)**: Goランタイムに組み込まれているツールで、並行実行されるゴルーチン間でのデータ競合（レースコンディション）を検出します。レース検出器は、メモリへのアクセス（読み書き）を監視し、競合が発生した可能性のある箇所を報告します。
*   **インストゥルメンテーション**: レース検出器が機能するために、コンパイラはプログラムのメモリアクセス命令の周りに特別なコード（インストゥルメンテーションコード）を挿入します。このコードは、メモリアクセスを記録し、競合をチェックします。
*   **多値代入**: Go言語の機能の一つで、複数の変数を一度に代入することができます。例えば、`x, y = f()`のように、関数`f`が複数の値を返し、それらを`x`と`y`に代入するような場合です。コンパイラはこれを内部的に複数の代入操作と関数呼び出しの組み合わせとして扱います。
*   **`OAS` (Assignment)**: ASTにおける代入操作を表すノードタイプ。
*   **`OCALLFUNC`, `OCALLMETH`, `OCALLINTER`**: それぞれ通常の関数呼び出し、メソッド呼び出し、インターフェースメソッド呼び出しを表すASTノードタイプ。
*   **`iscallret(n *Node)`**: `src/cmd/compile/internal/gc/walk.go`に追加されたヘルパー関数で、与えられたノードが関数呼び出しの戻り値をスタックから読み取る操作（`OINDREG`かつ`REGSP`レジスタを使用）であるかどうかを判定します。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/compile/internal/gc/racewalk.go`内の`racewalknode`関数、特に`OBLOCK`ノードの処理ロジックにあります。

以前の実装では、`OBLOCK`ノードが`OCALLFUNC`、`OCALLMETH`、`OCALLINTER`のような関数呼び出しノードを含んでいる場合、その関数呼び出しノード自体は`racewalknode`で処理されていましたが、その後に続く戻り値の代入（`OAS`ノード）は、`racewalklist`によって一括で処理されていました。この際、関数呼び出しと戻り値の代入の間にレース検出器のインストゥルメンテーションが挿入される可能性があり、これが問題を引き起こしていました。

新しい実装では、`OBLOCK`ノード内の各ステートメントを個別に走査し、関数呼び出しノード（`OCALLFUNC`など）を検出した場合、そのノードを処理した後、**それに続く戻り値の代入ノード（`OAS`かつ`iscallret`が真となるノード）をスキップしてインストゥルメンテーションを行わない**ように変更されています。これにより、関数呼び出しの結果がスタックから変数にコピーされる際に、レース検出器のコードが割り込むことを防ぎ、データの破壊を防ぎます。

具体的には、`racewalknode`関数内の`OBLOCK`ケースで、`for l := n.List; l != nil; l = l.Next`ループが導入され、`OBLOCK`内の各ステートメント（`l.N`）が個別に検査されます。
`OCALLFUNC`, `OCALLMETH`, `OCALLINTER`の場合、`racewalknode(&l.N, &out, 0, 0)`で関数呼び出し自体を処理した後、`for l.Next != nil && l.Next.N.Op == OAS && iscallret(l.Next.N.Right)`という条件で、関数呼び出しの戻り値をスタックから読み取る代入ノードを特定し、それらをスキップして`out`リストに追加します。これにより、これらの代入操作にはレース検出器のインストゥルメンテーションが適用されなくなります。

また、`src/cmd/compile/internal/gc/walk.go`には、`iscallret`という新しいヘルパー関数が追加されました。この関数は、与えられたノードがスタックポインタ（`Thearch.REGSP`）からの間接参照（`OINDREG`）であるかどうかをチェックすることで、関数呼び出しの戻り値をスタックから読み取る操作を識別します。

`src/cmd/compile/internal/gc/order.go`の変更は、`OAS2FUNC`（多値関数呼び出し代入）の場合に、一時変数を作成して代入を処理するロジックを追加しています。これは、レース検出器の処理と連携して、多値代入が正しく扱われるようにするためのものです。

テストケースとして、`src/runtime/race/race_test.go`に`TestIssue9137`が追加され、`src/runtime/race/testdata/mop_test.go`には`TestRaceBlockCall1`から`TestRaceBlockCall6`までの複数のテストが追加されています。これらのテストは、多値関数呼び出しとスライス操作がレース検出器によって正しく処理されることを検証します。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラのレース検出器が、関数呼び出しとその戻り値の代入を原子的に扱うように変更された点にあります。

Go言語では、`x, y := f()`のような多値代入は、コンパイラによって以下のような一連の操作に分解されます（簡略化された表現）：

1.  関数`f()`を呼び出す。
2.  `f()`の戻り値をスタックにプッシュする。
3.  スタック上の最初の戻り値を`x`に代入する。
4.  スタック上の2番目の戻り値を`y`に代入する。

これらの操作は、コンパイラのASTでは`OBLOCK`ノード内にネストされた`OCALLFUNC`（または`OCALLMETH`/`OCALLINTER`）ノードと、それに続く複数の`OAS`ノードとして表現されます。

レース検出器は、通常、メモリへのアクセス（読み書き）が発生する各ステートメントの前後でインストゥルメンテーションコードを挿入します。しかし、上記のシナリオで、関数呼び出しと戻り値の代入の間にインストゥルメンテーションが挿入されると、問題が発生します。例えば、`f()`がスタックに値を書き込んだ直後にレース検出器のコードが実行され、そのコードがスタックを一時的に使用したり変更したりすると、その後に続く`x`や`y`への代入が誤ったスタック上の値を読み取ってしまう可能性があります。これが、`#7561`や`#9137`で報告された「結果の破壊」や「データ破損」の原因でした。

このコミットでは、`racewalk.go`の`OBLOCK`処理において、関数呼び出しノード（`OCALLFUNC`など）を検出した場合、その関数呼び出し自体は通常通りインストゥルメントしますが、**それに続く、スタックから戻り値を読み取る代入ノード（`OAS`かつ`iscallret`が真）は、インストゥルメンテーションをスキップする**ように変更されました。これにより、関数呼び出しと戻り値の代入が論理的に一つの原子的な操作として扱われ、レース検出器の介入によって中間データが破壊されることがなくなります。

`iscallret`関数は、この「スタックから戻り値を読み取る代入」を正確に識別するための重要なヘルパーです。`OINDREG`はレジスタの間接参照を表し、`Thearch.REGSP`はスタックポインタレジスタを指します。したがって、`OINDREG && n.Reg == int16(Thearch.REGSP)`という条件は、「スタックポインタが指すメモリ位置から値を読み取る操作」を意味し、これはまさに関数呼び出しの戻り値をスタックから取得する際の典型的なパターンです。

この修正により、Goのレース検出器は、多値代入や複雑なスライス操作を含むコードにおいても、より正確で信頼性の高いデータ競合検出を提供できるようになりました。

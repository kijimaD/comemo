# [インデックス 25274] ファイルの概要

このコミットは、Goプログラムを動的リンクする際に、システムリンカに対して常に遅延PLT (Procedure Linkage Table) 解決を無効にするようにGoリンカ (`cmd/link`) の挙動を変更します。これにより、特に `ppc64le` アーキテクチャ上で発生していた、Goランタイムのスタック管理と遅延PLT解決の間の競合によるスタックオーバーフローの問題が解決されます。

## コミット

Author: Michael Hudson-Doyle <michael.hudson@canonical.com>
Date:   Thu Oct 15 21:48:11 2015 +1300

    cmd/link: always disable lazy PLT resolution when dynamically linking Go
    
    Go cannot allow lazy PLT resolution when calling between Go functions because
    the lazy resolution can use more stack than is available. Lazy resolution is
    disabled by passing -z now to the system linker, but unfortunately was only
    passed when linking to a Go shared library. That sounds fine, but the shared
    library containing the runtime is not linked to any other Go shared library but
    calls main.init and main.main via a PLT, and before this fix this did use lazy
    resolution. (For some reason this never caused a problem on intel, but it
    breaks on ppc64le). Fortunately the fix is very simple: always pass -z now to
    the system linker when dynamically linking Go.

## 元コミット内容

このコミットは、Goプログラムを動的リンクする際に、常に遅延PLT (Procedure Linkage Table) 解決を無効にするように `cmd/link` を変更します。Go関数間で呼び出しを行う際に遅延PLT解決が有効になっていると、利用可能なスタックよりも多くのスタックを使用する可能性があり、これが問題を引き起こすためです。遅延解決はシステムリンカに `-z now` を渡すことで無効にされますが、残念ながら以前はGo共有ライブラリにリンクする場合にのみ渡されていました。これは一見問題ないように思えますが、ランタイムを含む共有ライブラリは他のGo共有ライブラリにはリンクされていませんが、`main.init` や `main.main` をPLT経由で呼び出しており、この修正以前は遅延解決を使用していました。（なぜかIntelでは問題になりませんでしたが、`ppc64le` では壊れていました）。幸いなことに、修正は非常にシンプルで、Goを動的リンクする際に常に `-z now` をシステムリンカに渡すようにするだけです。

## 変更の背景

Goランタイムは、特に動的リンクを使用する場合、シンボル解決のメカニズムとスタック管理に関して特定の要件を持っています。このコミットの背景には、以下の問題がありました。

1.  **Goのスタック管理とPLT解決の競合**: Goは、ゴルーチンごとに比較的小さなスタックを割り当て、必要に応じてスタックを動的に拡張する「可変スタック」メカニズムを採用しています。しかし、遅延PLT解決プロセスは、シンボル解決のために一時的に追加のスタック空間を消費することがあります。Go関数が相互に呼び出す際に、この遅延解決がトリガーされると、Goランタイムが想定するスタックサイズを超過し、スタックオーバーフローを引き起こす可能性がありました。
2.  **`ppc64le` アーキテクチャ固有の問題**: この問題は、特に `ppc64le` (PowerPC 64-bit Little Endian) アーキテクチャで顕著でした。`ppc64le` のABI (Application Binary Interface) やリンカの動作が、Intelアーキテクチャとは異なり、遅延PLT解決時のスタック消費がより大きくなる傾向があったためと考えられます。コミットメッセージにも「For some reason this never caused a problem on intel, but it breaks on ppc64le」と明記されています。
3.  **`-z now` フラグの適用範囲の不備**: 遅延PLT解決を無効にするためには、システムリンカに `-z now` フラグを渡す必要があります。このフラグは、プログラム起動時にすべての動的シンボルを事前に解決するようリンカに指示します。これにより、実行中の遅延解決によるスタック消費を防ぎます。しかし、以前の実装では、このフラグはGo共有ライブラリにリンクする場合にのみ適用されていました。ランタイム自体を含む共有ライブラリが `main.init` や `main.main` のようなエントリポイントをPLT経由で呼び出す場合、それが他のGo共有ライブラリに直接リンクされていなくても、遅延解決が適用されてしまうという見落としがありました。

これらの要因が組み合わさり、`ppc64le` 上で動的リンクされたGoプログラムが、起動時または特定の関数呼び出し時にスタックオーバーフローでクラッシュするという問題が発生していました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

### 1. 動的リンク (Dynamic Linking)

動的リンクは、プログラムが実行時に共有ライブラリ（Linuxでは `.so` ファイル、Windowsでは `.dll` ファイル）のコードにリンクするメカニズムです。これにより、実行ファイルのサイズを小さくし、複数のプログラムで同じライブラリを共有できるため、メモリ使用量を削減し、ライブラリの更新を容易にします。

### 2. PLT (Procedure Linkage Table) と GOT (Global Offset Table)

動的リンクされたプログラムが外部ライブラリの関数を呼び出す際、その関数の正確なメモリアドレスはコンパイル時には不明です。この問題を解決するために、PLTとGOTという2つのテーブルが使用されます。

*   **PLT (Procedure Linkage Table)**: 外部関数の呼び出しを仲介するコードの小さな断片の集まりです。プログラムが外部関数を呼び出すと、まずその関数のPLTエントリにジャンプします。
*   **GOT (Global Offset Table)**: 外部シンボルの実際のアドレスを格納するテーブルです。PLTエントリはGOTを参照して、呼び出すべき関数のアドレスを取得します。

### 3. 遅延シンボル解決 (Lazy Symbol Resolution) と即時シンボル解決 (Eager Symbol Resolution)

シンボル解決とは、外部関数や変数の実際のメモリアドレスを特定するプロセスです。

*   **遅延シンボル解決 (Lazy Resolution)**: デフォルトの動作として、多くの動的リンカは遅延解決を採用しています。これは、外部シンボルのアドレスを、そのシンボルがプログラム内で**初めて参照または呼び出されたとき**にのみ解決するというものです。これにより、プログラムの起動時間を短縮できます。なぜなら、実際に使用されない可能性のあるシンボルをすべて起動時に解決するオーバーヘッドを避けることができるからです。
    *   遅延解決のメカニズム: 初めてPLTエントリが実行されると、GOTエントリはまだ実際の関数アドレスを指していません。代わりに、動的リンカの解決ルーチン（例: `_dl_runtime_resolve`）を指すか、PLT自身に戻るような初期値が設定されています。PLTエントリは、この解決ルーチンに制御を渡し、解決ルーチンが実際の関数アドレスを見つけてGOTエントリを更新し、その後、実際の関数にジャンプします。2回目以降の呼び出しでは、GOTエントリはすでに実際の関数アドレスを指しているため、PLTエントリは直接その関数にジャンプします。
*   **即時シンボル解決 (Eager Resolution)**: リンカフラグ `-z now` を使用すると、動的リンカはプログラムの起動時、`main` 関数が実行される前に、**すべての**動的シンボルを解決します。これにより、実行中の遅延解決によるオーバーヘッドや、セキュリティ上のリスク（PLT書き換え攻撃など）を回避できます。

### 4. Goのスタック管理 (Goroutine Stack Management)

Goランタイムは、ゴルーチンごとに独自のスタックを管理します。初期スタックサイズは比較的小さく（数KB程度）、必要に応じて自動的に拡張されます。この「可変スタック」は、多数のゴルーチンを効率的に実行するために設計されています。スタックの拡張は、特定の関数プロローグでスタックガードページをチェックし、必要であれば新しい、より大きなスタックを割り当てて内容をコピーすることで行われます。

### 5. `ppc64le` アーキテクチャ

PowerPC 64-bit Little Endian (ppc64le) は、IBM Power ISAに基づく64ビットプロセッサアーキテクチャです。このアーキテクチャは、Intel x86-64とは異なるABIを持ち、特に動的リンクやスタックフレームの管理において、異なる規約や実装の詳細が存在します。これが、Intelでは問題にならなかった遅延PLT解決時のスタック消費が `ppc64le` で問題となった一因です。

## 技術的詳細

このコミットが解決しようとしている技術的な問題は、Goのスタック管理と動的リンカの遅延PLT解決メカニズムの間の相互作用にあります。

1.  **遅延PLT解決時のスタック消費**:
    *   遅延PLT解決がトリガーされると、動的リンカはシンボルを解決するために一時的に制御を奪います。この解決プロセス自体が、スタック上にいくつかの情報をプッシュし、レジスタを保存し、場合によっては追加の関数を呼び出すなど、一定量のスタック空間を消費します。
    *   特に `ppc64le` のような一部のアーキテクチャでは、この解決ルーチンが消費するスタック空間が、Goランタイムがゴルーチンに割り当てている初期スタックサイズや、スタック拡張が間に合うと期待される閾値よりも大きくなる可能性がありました。
    *   Goの可変スタックは、Go関数がGo関数を呼び出す際のスタック拡張には対応していますが、動的リンカのような外部のコードがGoのスタック上で動作し、予期せぬスタック消費を引き起こすシナリオには、必ずしも最適化されていませんでした。

2.  **Goランタイムの起動プロセスとPLT**:
    *   Goプログラムが起動する際、ランタイムは `main.init` や `main.main` といったエントリポイントを呼び出します。動的リンクされたGoプログラムの場合、これらのエントリポイントへの呼び出しもPLTを介して行われる可能性があります。
    *   コミットメッセージが指摘しているように、ランタイムを含む共有ライブラリが他のGo共有ライブラリに直接リンクされていなくても、これらの重要なエントリポイントへの呼び出しが遅延PLT解決の対象となることがありました。
    *   もし `main.init` や `main.main` の呼び出しが初めて行われる際に遅延PLT解決がトリガーされ、その解決プロセスが `ppc64le` 上で過剰なスタックを消費すると、Goランタイムがまだ完全に初期化されていない、またはスタック拡張メカニズムが十分に機能する前の段階でスタックオーバーフローが発生し、プログラムがクラッシュしてしまいます。

3.  **`-z now` フラグによる解決**:
    *   この問題に対する解決策は、システムリンカに `-z now` フラグを常に渡すことです。このフラグは、プログラムの実行が開始される前に、すべての動的シンボルを事前に解決するようリンカに指示します。
    *   これにより、Goプログラムの実行中に遅延PLT解決がトリガーされることがなくなり、動的リンカによる予期せぬスタック消費が回避されます。すべてのシンボル解決は、Goランタイムが制御を受け取る前に完了するため、Goのスタック管理メカニズムと競合する可能性がなくなります。
    *   コミットメッセージの変更点 `Linkshared && Iself` から `Iself && DynlinkingGo()` は、この `-z now` フラグを適用する条件をより広範に、かつ正確に修正しています。`DynlinkingGo()` は、Goプログラムが動的リンクされているかどうかを判断する関数であり、`Linkshared` (Go共有ライブラリとしてリンクされているか) よりも適切な条件です。これにより、ランタイム自体が動的リンクされている場合でも、確実に `-z now` が適用されるようになります。

この修正により、Goランタイムは、特に `ppc64le` のような特定のアーキテクチャにおいて、動的リンクされた環境での安定性を向上させました。

## コアとなるコードの解説

変更は `src/cmd/link/internal/ld/lib.go` ファイルの `hostlink` 関数内で行われています。この関数は、Goリンカがシステムリンカ（通常は `gcc` や `clang`）を呼び出す際に使用する引数を構築する役割を担っています。

元のコードでは、`-z now` フラグをシステムリンカに渡す条件が以下のようになっていました。

```go
if Linkshared && Iself {
```

*   `Linkshared`: これは、現在のビルドがGo共有ライブラリとしてリンクされているかどうかを示すフラグです。
*   `Iself`: これは、現在のビルドが実行可能ファイル（self-contained executable）であるかどうかを示すフラグです。

この条件は、「Go共有ライブラリとしてリンクされており、かつそれが実行可能ファイルである場合」に `-z now` を適用するという意味になります。しかし、コミットメッセージが指摘するように、ランタイムを含む共有ライブラリが `main.init` や `main.main` をPLT経由で呼び出す場合、それが他のGo共有ライブラリに直接リンクされていなくても、遅延解決が問題を引き起こす可能性がありました。

新しいコードでは、条件が以下のように変更されました。

```go
if Iself && DynlinkingGo() {
```

*   `Iself`: これは変更されていません。実行可能ファイルであるという条件は引き続き必要です。
*   `DynlinkingGo()`: これは、Goプログラムが動的リンクされているかどうかを判断する新しい（または既存の）関数です。

この変更により、`-z now` フラグがシステムリンカに渡される条件が「実行可能ファイルであり、かつGoプログラムが動的リンクされている場合」に拡張されました。これにより、Goランタイム自体が動的リンクされている場合や、Goプログラムが外部の共有ライブラリに依存している場合など、遅延PLT解決が問題を引き起こす可能性のあるすべてのシナリオで、確実に即時シンボル解決が強制されるようになります。

この修正は、Goのリンカがシステムリンカを呼び出す際の引数生成ロジックを改善し、Goランタイムのスタック管理要件と動的リンクの挙動との間の不整合を解消することで、特に `ppc64le` アーキテクチャにおける安定性を向上させています。

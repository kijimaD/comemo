# [インデックス 23071] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）トリガーコントローラにおける潜在的なゼロ除算バグを修正するものです。具体的には、GCのCPU利用率を計算する際に、経過時間がゼロまたは負の値になるという極めて稀なケースで発生する可能性のあるパニック（ゼロ除算）を防ぎます。`src/runtime/mgc.go` ファイルは、Goランタイムのガベージコレクションの主要なロジック、特にGCのスケジューリングと制御に関連する部分を担っています。

## 元コミット内容

```
runtime: avoid divide-by-zero in GC trigger controller

The trigger controller computes GC CPU utilization by dividing by the
wall-clock time that's passed since concurrent mark began. Since this
delta is nanoseconds it's borderline impossible for it to be zero, but
if it is zero we'll currently divide by zero. Be robust to this
possibility by ignoring the utilization in the error term if no time
has elapsed.

Change-Id: I93dfc9e84735682af3e637f6538d1e7602634f09
Reviewed-on: https://go-review.googlesource.com/9175
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。このGCの効率を最適化するために、「GCトリガーコントローラ」または「GC Pacer」と呼ばれるメカニズムが導入されています。これは、次回のGCサイクルをいつ開始するか、またGCがCPUリソースをどの程度使用すべきかを決定します。

GCトリガーコントローラは、GCが消費しているCPU利用率を計算し、これに基づいて次回のGCの開始タイミングを調整します。このCPU利用率の計算には、コンカレントマークフェーズが開始されてからの経過時間（`duration`）が分母として使用されます。この`duration`はナノ秒単位で計測されるため、通常はゼロになることは「ほとんど不可能」とされています。しかし、システムクロックの異常、非常に短い時間間隔での呼び出し、あるいは特定の環境下でのエッジケースにおいて、`duration`がゼロまたは負の値になる可能性が理論上存在しました。

もし`duration`がゼロになった場合、GC CPU利用率の計算式でゼロ除算が発生し、Goランタイムがパニックを起こしてアプリケーションがクラッシュする原因となります。このコミットは、このような極めて稀な状況でもランタイムが堅牢に動作するように、ゼロ除算を明示的に回避するための修正を導入しました。具体的には、`duration`がゼロまたは負の値である場合に、利用率の計算をスキップし、エラー項における利用率の影響を無視する（デフォルト値を使用する）ことで、システムの安定性を確保しています。

## 前提知識の解説

1.  **Goのガベージコレクション (GC)**:
    *   Goはトレース型GCを採用しており、到達可能なオブジェクトを特定し、それ以外のオブジェクトを解放します。
    *   Go 1.5以降、GCは主に「コンカレントGC」として動作します。これは、GCの大部分のフェーズがアプリケーションのゴルーチンと並行して実行されることを意味します。これにより、GCによるアプリケーションの一時停止（ストップ・ザ・ワールド、STW）時間を最小限に抑え、レイテンシを改善します。
    *   GCは、ヒープの使用量がある閾値（GCトリガー）を超えたときに開始されます。

2.  **GCトリガーコントローラ (GC Pacer)**:
    *   Goランタイムには、GCの実行を制御し、アプリケーションのスループットとレイテンシのバランスを取るための「GCトリガーコントローラ」または「GC Pacer」と呼ばれるコンポーネントがあります。
    *   このコントローラは、GCが消費するCPUリソースを監視し、次回のGCが開始されるべきヒープサイズ（トリガーヒープサイズ）を動的に調整します。目標は、GCがCPU時間の特定の割合（デフォルトでは25%）を超えないようにすることです。
    *   GC Pacerは、GCのCPU利用率、ヒープの成長率、GCの目標（`gcpercent`で設定される）などを考慮して、次回のGCのタイミングを決定します。

3.  **GC CPU利用率の計算**:
    *   GC CPU利用率は、GCが実際にCPUをどれだけ使用しているかを示す指標です。これは、GCに費やされた総CPU時間（`assistTime`, `dedicatedMarkTime`, `fractionalMarkTime` の合計）を、GCがアクティブであった期間の総壁時計時間（`duration`）と利用可能なCPUコア数（`gomaxprocs`）の積で割ることで計算されます。
    *   `utilization = (assistTime + dedicatedMarkTime + fractionalMarkTime) / (duration * gomaxprocs)`
    *   `assistTime`: アプリケーションのゴルーチンがGCを手伝った時間。
    *   `dedicatedMarkTime`: GC専用のゴルーチンがマークフェーズに費やした時間。
    *   `fractionalMarkTime`: GCがバックグラウンドで実行された時間。
    *   `duration`: コンカレントマークフェーズが開始されてからの壁時計時間。
    *   `gomaxprocs`: Goランタイムが使用できる論理CPUコアの数。

4.  **`nanotime()`**:
    *   Goランタイム内部で使用される高精度な時間計測関数です。システム起動時からの経過時間をナノ秒単位で返します。これは壁時計時間であり、CPU時間とは異なります。

5.  **`gcpercent`**:
    *   環境変数または`GOGC`で設定される値で、GCの目標ヒープ成長率をパーセンテージで指定します。例えば、`GOGC=100`は、前回のGCで到達可能だったヒープサイズの100%（つまり2倍）にヒープが成長したら次回のGCを開始するという意味です。

6.  **`memstats.heap_live` と `memstats.heap_marked`**:
    *   `memstats.heap_live`: 現在ライブ（到達可能）なオブジェクトが占めるヒープサイズ。
    *   `memstats.heap_marked`: 前回のGCマークフェーズでマークされたヒープサイズ。
    *   これらはヒープの成長率を計算するために使用されます。

## 技術的詳細

このコミットが修正する問題は、`src/runtime/mgc.go` 内の `gcControllerState.endCycle()` メソッドに存在します。このメソッドは、GCサイクルが終了した際に呼び出され、次回のGCトリガーを調整するための計算を行います。

問題の箇所は、GCのCPU利用率 `utilization` を計算する部分です。

```go
duration := nanotime() - c.bgMarkStartTime
utilization := float64(c.assistTime+c.dedicatedMarkTime+c.fractionalMarkTime) / float64(duration*int64(gomaxprocs))
```

ここで、`duration` は `nanotime()` の現在の値から、コンカレントマークフェーズが開始された時刻 `c.bgMarkStartTime` を引いたものです。理論的には、`nanotime()` は単調増加するはずであり、`c.bgMarkStartTime` は過去の時点を示すため、`duration` は常に正の値になるはずです。しかし、非常に稀なケース（例えば、システムクロックの異常な巻き戻り、あるいは`nanotime()`の呼び出しと`c.bgMarkStartTime`のセットが同じナノ秒内で行われるような極端なタイミング）において、`duration`がゼロまたは負の値になる可能性が考えられます。

もし `duration` が `0` になった場合、`duration * int64(gomaxprocs)` も `0` となり、結果として `utilization` の計算でゼロ除算が発生し、Goランタイムがパニックを起こします。

このコミットでは、このゼロ除算を回避するために、`utilization` の計算の前に `duration` の値をチェックする条件分岐を追加しました。

```go
var utilization float64
if duration <= 0 {
    // Avoid divide-by-zero computing utilization. This
    // has the effect of ignoring the utilization in the
    // error term.
    utilization = gcGoalUtilization
} else {
    utilization = float64(c.assistTime+c.dedicatedMarkTime+c.fractionalMarkTime) / float64(duration*int64(gomaxprocs))
}
```

この変更により、`duration` がゼロまたは負の値である場合、`utilization` は `gcGoalUtilization` という定数（GCの目標利用率、通常は0.25）に設定されます。これにより、ゼロ除算が回避されるだけでなく、`triggerError` の計算において、この異常なケースでの利用率の影響が無視されることになります。

`triggerError` は、次回のGCトリガーを調整するための誤差項であり、`goalGrowthRatio`（目標ヒープ成長率）と `actualGrowthRatio`（実際のヒープ成長率）、そしてGCのCPU利用率 `utilization` を考慮して計算されます。`utilization` が異常な値になる場合に、その影響を排除することで、GCトリガーコントローラのロバスト性を高めています。

## コアとなるコードの解説

変更の中心は、`utilization` 変数の宣言と計算ロジックです。

1.  **`utilization` の宣言の変更**:
    `utilization := ...` から `var utilization float64` に変更され、初期値の代入が条件分岐の内側で行われるようになりました。これは、Goの短い変数宣言 `:=` がスコープ内で一度しか使えないため、条件分岐内で異なる値を代入するために必要な変更です。

2.  **ゼロ除算回避の条件分岐**:
    `if duration <= 0 { ... } else { ... }` という条件分岐が追加されました。
    *   `duration <= 0` の場合:
        `utilization = gcGoalUtilization` と設定されます。`gcGoalUtilization` はGoランタイムで定義されているGCの目標CPU利用率（通常は0.25）を示す定数です。これにより、`duration`がゼロまたは負の値であってもゼロ除算を回避し、`utilization`が有効な値を持つことが保証されます。コメントにもあるように、このケースではエラー項における利用率の影響が実質的に無視されます。
    *   `duration > 0` の場合:
        通常の利用率の計算 `float64(c.assistTime+c.dedicatedMarkTime+c.fractionalMarkTime) / float64(duration*int64(gomaxprocs))` が実行されます。これは、`duration`が正の値であるため、分母がゼロになる心配がないためです。

この修正により、Goランタイムは、極めて稀なエッジケースにおいても安定して動作し、GCトリガーコントローラが予期せぬパニックを引き起こす可能性が排除されました。

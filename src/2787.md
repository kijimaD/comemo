# [インデックス 2787] ファイルの概要

## 変更の背景

Go言語の初期のコンパイラ（`gc`）では、関数本体が空の場合に、コンパイラが暗黙的に`return;`文を挿入する挙動がありました。これは、特に戻り値を宣言している関数において問題を引き起こす可能性がありました。例えば、`func f() int {}` のような関数があった場合、コンパイラはこれを `func f() int { return; }` と解釈し、結果としてゼロ値（この場合は`0`）を返していました。

しかし、これはプログラマの意図しない挙動につながる可能性があり、特に複雑な関数で戻り値の処理を忘れた場合に、コンパイルエラーではなくサイレントなバグとして現れるリスクがありました。Go言語の設計哲学は、エラーを早期に、そして明示的に検出することに重点を置いています。この暗黙的な`return`の挙動は、その哲学に反するものでした。

このコミットは、この暗黙的な`return`の挿入を停止し、空の関数本体は文字通り空であるとコンパイラに認識させることで、戻り値を宣言している関数が明示的な`return`文を持たない場合にコンパイルエラーを発生させるように変更しました。これにより、プログラマは戻り値の処理を忘れなくなり、コードの堅牢性が向上します。

## 前提知識の解説

### Goコンパイラ (`gc`)

`gc`は、Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担っています。コンパイルプロセスは、字句解析、構文解析、抽象構文木（AST）の生成、型チェック、最適化、コード生成など、複数の段階に分かれています。このコミットで変更されている`src/cmd/gc/dcl.c`や`src/cmd/gc/go.y`は、このコンパイルプロセスの初期段階、特に構文解析と宣言処理に関わる部分です。

### 抽象構文木 (AST)

抽象構文木（Abstract Syntax Tree, AST）は、ソースコードの構文構造を木構造で表現したものです。コンパイラはソースコードを直接操作するのではなく、まずASTを生成し、そのASTを走査・変換することで、型チェックやコード生成などの処理を行います。`nod(ORETURN, N, N)`や`nod(OEMPTY, N, N)`といった表記は、Goコンパイラの内部でASTノードを生成するための関数呼び出しであり、それぞれ`return`文と空のステートメントを表すASTノードに対応します。

### Yacc/Bison

`go.y`ファイルは、Yacc（Yet Another Compiler Compiler）またはBison（YaccのGNU版）というツールで利用される文法定義ファイルです。Yacc/Bisonは、BNF（Backus-Naur Form）のような形式で記述された文法定義を読み込み、その文法に従ってソースコードを解析するためのパーサ（構文解析器）を生成します。`go.y`はGo言語の構文規則を定義しており、コンパイラがGoソースコードをASTに変換する際の重要な部分を担っています。

### 暗黙的な`return`と明示的な`return`

プログラミング言語において、関数の戻り値の扱いは言語によって異なります。
*   **暗黙的な`return`**: 関数が戻り値を宣言しているにもかかわらず、明示的な`return`文がない場合に、言語処理系が自動的に何らかの値を返す挙動を指します。Go言語の初期の`gc`では、空の関数本体に対して暗黙的にゼロ値を返す`return`文を挿入していました。
*   **明示的な`return`**: プログラマがコード内で`return`キーワードを用いて、どの値を返すかを明確に指定する挙動を指します。Go言語の現在の仕様では、戻り値を宣言している関数は、すべての実行パスで明示的に値を返す必要があります。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの内部処理におけるASTノードの生成と、Go言語の文法解析の変更にあります。

### `src/cmd/gc/dcl.c` の変更

`src/cmd/gc/dcl.c`は、Goコンパイラの宣言処理（declarations）を担当する部分です。関数リテラル（`funclit1`関数）の処理において、関数本体（`body`）が`nil`（つまり空）である場合に、以前は`list1(nod(ORETURN, N, N))`を挿入していました。これは、空の関数本体を`return;`文を持つものとして扱っていたことを意味します。

### `src/cmd/gc/go.y` の変更

`src/cmd/gc/go.y`は、Go言語の文法定義ファイルであり、構文解析器がGoソースコードを解析する際のルールを記述しています。`fnbody`（関数本体）のルールにおいて、関数本体が空である場合（`$$ == nil`）、以前は`list1(nod(ORETURN, N, N))`を代入していました。これは、構文解析の段階で、空の関数本体が`return;`文として解釈されていたことを示しています。

このコミットでは、ここでも`list1(nod(OEMPTY, N, N))`を代入するように変更されました。これにより、構文解析器は空の関数本体を`OEMPTY`ノードとしてASTに組み込むようになり、`dcl.c`での変更と合わせて、コンパイラ全体で空の関数本体に対する暗黙的な`return`の挿入が排除されます。

### テストファイルの変更

*   `test/fixedbugs/bug043.go` と `test/fixedbugs/bug080.go`: これらの既存のテストファイルでは、空の関数本体を持つ関数に明示的に`return;`を追加する変更が行われています。これは、このコミットによって暗黙的な`return`がなくなったため、これらの関数が以前と同じように動作するためには明示的な`return`が必要になったことを示しています。
*   `test/fixedbugs/bug171.go`: このファイルは新規追加されたテストであり、`func f() int { }` や `func g() (foo int) { }` のように、戻り値を宣言しているにもかかわらず空の関数本体を持つ場合に、コンパイルエラー（`ERROR "return"`）が発生することを検証しています。これは、このコミットの目的である「戻り値を宣言している関数が明示的な`return`を持たない場合にエラーとする」という挙動が正しく実装されたことを確認するための重要なテストです。

これらの変更により、Goコンパイラはより厳格になり、プログラマは戻り値の処理をより意識するようになります。これは、Go言語の堅牢性と明示性を高める上で重要な改善です。

    `funclit1`関数は、関数リテラル（無名関数など）の宣言を処理する際に呼び出されます。ここで`if(body == nil)`という条件は、関数本体が空であることを意味します。以前は、この空の本体に対して`nod(ORETURN, N, N)`、つまり`return`文を表すASTノードを含むリストを生成していました。これは、コンパイラが暗黙的に`return;`を挿入していたことを示します。
    変更後は、`nod(OEMPTY, N, N)`、つまり空のステートメントを表すASTノードを含むリストを生成するように変わりました。これにより、コンパイラは空の関数本体を、特別な意味を持たない「空」として扱うようになります。

*   **`src/cmd/gc/go.y` の変更**:
    `go.y`ファイル内の`fnbody`ルールは、Go言語の関数本体の構文を定義しています。`$$ = $2; if($$ == nil)`という部分は、関数本体が構文解析の結果として空であった場合に実行されます。以前は、この空の本体に対して`nod(ORETURN, N, N)`を代入していました。これは、構文解析の段階で、空の関数本体が`return`文として解釈され、ASTに組み込まれていたことを意味します。
    変更後は、`nod(OEMPTY, N, N)`を代入するように修正されました。これにより、構文解析器は空の関数本体を`OEMPTY`ノードとしてASTに組み込むようになり、コンパイラの宣言処理と一貫した挙動を示すようになります。

これらの変更は、Goコンパイラのフロントエンドにおける基本的な挙動を修正し、Go言語のセマンティクスをより厳格に、そして明示的に定義する上で重要な役割を果たしています。結果として、プログラマは戻り値の扱いについてより注意を払う必要があり、これによりコードの品質と信頼性が向上します。

# [インデックス 27191] ファイルの概要

このコミットは、Go言語の標準ライブラリ `sync` パッケージ内の `Cond` (条件変数) の実装を根本的に変更するものです。主な目的は、既存の実装で発生していた `Broadcast` が全ての待機中のゴルーチンにシグナルを送れない可能性のある問題を解決することです。新しい実装では、「通知リスト (notification list)」と呼ばれるチケットベースのメカニズムを導入し、待機者がロックを解放する前に通知を登録し、シグナルを送る側が待機する必要がなくなりました。

## コミット

## 変更の背景

このコミットの主な背景は、Goの `sync.Cond` の以前の実装における既知のバグ、特に `Broadcast` メソッドが全ての待機中のゴルーチンを確実に起こせない可能性があるという問題に対処することです。この問題は、Issue #14064 で報告されていました。

従来の `sync.Cond` の実装は、セマフォ (`syncSema`) をベースにしており、待機中のゴルーチンの数をカウントする `waiters` フィールドを使用していました。しかし、`Broadcast` が呼び出された際に、シグナルを送る側と待機する側の間の競合状態により、一部のゴルーチンが通知を受け取れない「失われた通知 (lost wakeup)」が発生する可能性がありました。これは、特に `Broadcast` がロックを保持せずに呼び出される場合や、待機中のゴルーチンが `Wait` を呼び出す直前に `Broadcast` が発生した場合に顕著でした。

新しい実装は、この問題を解決するために、より堅牢な「チケットベースの通知リスト」メカニズムを導入しています。これにより、待機中のゴルーチンが通知を登録してからロックを解放し、実際に待機するという手順を踏むことで、通知の取りこぼしを防ぎます。また、シグナルを送る側が待機する必要がなくなるため、実装が簡素化され、効率も向上します。

ベンチマーク結果を見ると、ほとんどのケースでパフォーマンスはわずかに向上または同等であり、機能的な修正がパフォーマンスを大きく損なわないことが示されています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を理解しておく必要があります。

1.  **条件変数 (Condition Variable)**:
    *   並行プログラミングにおいて、特定の条件が満たされるまでゴルーチンを待機させ、条件が満たされたときにそれらのゴルーチンを再開させるための同期プリミティブです。
    *   Go言語では `sync.Cond` として提供されます。
    *   常に `sync.Locker` (通常は `sync.Mutex` または `sync.RWMutex`) と組み合わせて使用されます。条件変数の `Wait` メソッドは、関連するロックを解放し、ゴルーチンをスリープさせ、再開時にロックを再取得します。
    *   `Signal()`: 待機中のゴルーチンのうち、最大1つを再開させます。
    *   `Broadcast()`: 待機中の全てのゴルーチンを再開させます。

2.  **ミューテックス (Mutex)**:
    *   共有リソースへのアクセスを排他的に制御するための同期プリミティブです。Go言語では `sync.Mutex` として提供されます。
    *   `Lock()`: ロックを取得します。既にロックされている場合は、解放されるまで待機します。
    *   `Unlock()`: ロックを解放します。

3.  **ゴルーチン (Goroutine)**:
    *   Goランタイムによって管理される軽量なスレッドです。並行処理の基本単位となります。

4.  **`sudog` 構造体**:
    *   Goランタイム内部で使用される構造体で、待機中のゴルーチンを表します。スケジューラがゴルーチンをブロックしたり、再開したりする際にこの構造体を利用します。
    *   `g`: 待機中のゴルーチンへのポインタ。
    *   `next`, `prev`: 待機リスト内の次の/前の `sudog` へのポインタ。
    *   `releasetime`: ブロックプロファイリングに使用される時間情報。
    *   `nrelease` (旧): 以前の `syncSema` で使用されていた、解放されるべきゴルーチンの数を示すフィールド。
    *   `ticket` (新): このコミットで導入された、通知リストにおけるゴルーチンのチケット番号。

5.  **`gopark` と `goready`**:
    *   `gopark`: 現在のゴルーチンをスリープ状態にし、スケジューラから削除します。特定のイベントが発生するまで待機します。
    *   `goready`: スリープ中のゴルーチンを再開可能な状態にし、スケジューラにキューイングします。

6.  **アトミック操作 (Atomic Operations)**:
    *   複数のゴルーチンから同時にアクセスされても、操作が中断されずに完了することを保証する低レベルの操作です。Go言語では `sync/atomic` パッケージで提供されます。
    *   `atomic.Xadd`: アトミックに値を加算し、加算前の値を返します。
    *   `atomic.Load`: アトミックに値を読み込みます。
    *   `atomic.Store`: アトミックに値を書き込みます。

## 技術的詳細

このコミットの核心は、`sync.Cond` の内部実装を `syncSema` (セマフォ) ベースから、`notifyList` (通知リスト) と呼ばれるチケットベースのメカニズムに移行した点です。

### 以前の実装 (`syncSema` ベース) の問題点

以前の `sync.Cond` は、`syncSema` というランタイム内部のセマフォと、`Cond` 構造体内の `waiters` というカウンタを使用していました。
`Wait` メソッドは `waiters` をインクリメントし、`syncsemacquire` を呼び出してセマフォで待機します。
`Signal` や `Broadcast` は `waiters` をデクリメントし、`syncsemrelease` を呼び出してセマフォを解放することでゴルーチンを再開させます。

この方式では、以下のような競合状態により「失われた通知」が発生する可能性がありました。

1.  ゴルーチンAが `Cond.Wait()` を呼び出す直前。
2.  ゴルーチンBが `Cond.Broadcast()` を呼び出す。
3.  `Broadcast` は `waiters` カウンタを見て、待機中のゴルーチンがいないと判断し、何も通知せずに終了する。
4.  ゴルーチンAが `Cond.Wait()` を呼び出し、`waiters` をインクリメントしてセマフォで待機する。
5.  このゴルーチンAは、既に `Broadcast` が行われたため、永遠に通知を受け取れない可能性がある。

### 新しい実装 (`notifyList` ベース) のメカニズム

新しい実装では、`sync.Cond` は `notifyList` という新しいランタイム内部構造体を使用します。`notifyList` は以下の主要なフィールドを持ちます。

*   `wait` (uint32): 次に待機するゴルーチンに割り当てられるチケット番号。アトミックにインクリメントされます。
*   `notify` (uint32): 次に通知されるべきゴルーチンのチケット番号。
*   `lock` (mutex): `notifyList` 内部の待機リスト (`head`, `tail`) を保護するためのミューテックス。
*   `head`, `tail` (*sudog): 実際に待機しているゴルーチン (`sudog`) のリンクリスト。

動作フローは以下のようになります。

1.  **`Cond.Wait()` の呼び出し**:
    *   `runtime_notifyListAdd(&c.notify)` を呼び出し、`notifyList.wait` をアトミックにインクリメントして、新しいチケット番号 `t` を取得します。この時点で、ゴルーチンはまだロックを保持しています。
    *   `c.L.Unlock()` を呼び出し、関連するミューテックスを解放します。
    *   `runtime_notifyListWait(&c.notify, t)` を呼び出します。
        *   `notifyListWait` はまず `notifyList` のロックを取得します。
        *   取得したチケット番号 `t` が `notifyList.notify` よりも小さい場合 (つまり、既に通知済みである場合)、すぐにロックを解放して戻ります。これにより、失われた通知の問題が解決されます。
        *   まだ通知されていない場合、現在のゴルーチンを表す `sudog` を作成し、その `ticket` フィールドに `t` を設定して、`notifyList` の待機リスト (`head`/`tail`) に追加します。
        *   `goparkunlock` を呼び出して、`notifyList` のロックを解放し、ゴルーチンをスリープさせます。
    *   ゴルーチンが再開されたら、`c.L.Lock()` を呼び出して関連するミューテックスを再取得します。

2.  **`Cond.Signal()` の呼び出し (`runtime_notifyListNotifyOne`)**:
    *   `notifyList.wait` と `notifyList.notify` が同じ場合 (待機中のゴルーチンがいないか、全て通知済みの場合) は、高速パスとして何もせずに戻ります。
    *   `notifyList` のロックを取得します。
    *   `notifyList.notify` をインクリメントし、次に通知すべきチケット番号を更新します。
    *   待機リスト (`head` から `tail` まで) を走査し、インクリメントされた `notifyList.notify` と一致する `ticket` を持つ `sudog` を見つけます。
    *   見つかった `sudog` をリストから削除し、`readyWithTime` (内部で `goready` を呼び出す) を使ってゴルーチンを再開させます。
    *   `notifyList` のロックを解放します。

3.  **`Cond.Broadcast()` の呼び出し (`runtime_notifyListNotifyAll`)**:
    *   `notifyList.wait` と `notifyList.notify` が同じ場合、高速パスとして何もせずに戻ります。
    *   `notifyList` のロックを取得します。
    *   待機リスト (`head` から `tail` まで) をローカル変数に移動し、`notifyList` のリストを空にします。
    *   `notifyList.notify` を `notifyList.wait` の現在の値に設定します。これにより、この `Broadcast` 以降に `Wait` を呼び出すゴルーチンは、既に通知済みと判断されます。
    *   `notifyList` のロックを解放します。
    *   ローカル変数に移動した `sudog` のリストを走査し、全てのゴルーチンを `readyWithTime` を使って再開させます。

このチケットベースのシステムにより、`Wait` を呼び出すゴルーチンは、`notifyListAdd` でチケットを取得した時点で「待機者」として登録され、`Broadcast` はそのチケット番号に基づいて確実に通知を行うことができます。`less` 関数は、`uint32` のラップアラウンドを考慮してチケット番号を比較するために導入されています。

## コアとなるコードの解説

### `src/runtime/sema.go`

このファイルは、新しい `notifyList` ベースの `Cond` 実装の心臓部です。

```go
// notifyList is a ticket-based notification list used to implement sync.Cond.
type notifyList struct {
	wait uint32 // next waiter's ticket number
	notify uint32 // next ticket number to be notified
	lock mutex
	head *sudog
	tail *sudog
}

// less checks if a < b, considering a & b running counts that may overflow the
// 32-bit range, and that their "unwrapped" difference is always less than 2^31.
func less(a, b uint32) bool {
	return int32(a-b) < 0
}

// notifyListAdd adds the caller to a notify list such that it can receive
// notifications. The caller must eventually call notifyListWait to wait for
// such a notification, passing the returned ticket number.
//go:linkname notifyListAdd sync.runtime_notifyListAdd
func notifyListAdd(l *notifyList) uint32 {
	return atomic.Xadd(&l.wait, 1) - 1 // Increment wait and return previous value
}

// notifyListWait waits for a notification.
//go:linkname notifyListWait sync.runtime_notifyListWait
func notifyListWait(l *notifyList, t uint32) {
	lock(&l.lock)
	if less(t, l.notify) { // Already notified?
		unlock(&l.lock)
		return
	}
	// Enqueue itself.
	s := acquireSudog()
	s.g = getg()
	s.ticket = t
	// ... add s to l.head/l.tail list ...
	goparkunlock(&l.lock, "semacquire", traceEvGoBlockCond, 3)
	// ... handle block profiling ...
	releaseSudog(s)
}

// notifyListNotifyAll notifies all entries in the list.
//go:linkname notifyListNotifyAll sync.runtime_notifyListNotifyAll
func notifyListNotifyAll(l *notifyList) {
	// Fast-path: no new waiters since last notification
	if atomic.Load(&l.wait) == atomic.Load(&l.notify) {
		return
	}
	lock(&l.lock)
	s := l.head // Pull list out
	l.head = nil
	l.tail = nil
	atomic.Store(&l.notify, atomic.Load(&l.wait)) // Update notify to current wait
	unlock(&l.lock)
	for s != nil { // Ready all waiters
		next := s.next
		s.next = nil
		readyWithTime(s, 4)
		s = next
	}
}

// notifyListNotifyOne notifies one entry in the list.
//go:linkname notifyListNotifyOne sync.runtime_notifyListNotifyOne
func notifyListNotifyOne(l *notifyList) {
	// Fast-path: no new waiters since last notification
	if atomic.Load(&l.wait) == atomic.Load(&l.notify) {
		return
	}
	lock(&l.lock)
	t := l.notify
	if t == atomic.Load(&l.wait) { // Re-check under lock
		unlock(&l.lock)
		return
	}
	atomic.Store(&l.notify, t+1) // Increment notify ticket
	// Find sudog with ticket 't' in the list and ready it.
	// ... list traversal and removal ...
	unlock(&l.lock)
	readyWithTime(s, 4)
}
```

*   `notifyList` 構造体は、`wait` と `notify` という2つの `uint32` カウンタを導入しています。これらはチケット番号として機能し、ゴルーチンの待機と通知の状態を追跡します。
*   `less(a, b uint32)` 関数は、`uint32` のラップアラウンドを考慮して `a < b` を安全に比較するために使用されます。これは、チケット番号が `uint32` の最大値を超えてゼロに戻る可能性があるため重要です。`int32(a-b) < 0` というトリックは、符号付き整数オーバーフローの動作を利用して、ラップアラウンドを考慮した比較を実現しています。
*   `notifyListAdd` は、`atomic.Xadd(&l.wait, 1)` を使用して `wait` カウンタをアトミックにインクリメントし、ゴルーチンに一意のチケット番号を割り当てます。
*   `notifyListWait` は、ゴルーチンが実際に待機する場所です。チケット番号 `t` を受け取り、`l.notify` と比較して、既に通知されているかどうかをチェックします。通知済みであればすぐに戻り、そうでなければ `sudog` を作成して待機リストに追加し、`goparkunlock` でスリープします。
*   `notifyListNotifyAll` は、待機リスト全体をクリアし、`notify` カウンタを現在の `wait` カウンタに設定することで、全ての待機中のゴルーチンを再開させます。
*   `notifyListNotifyOne` は、`notify` カウンタをインクリメントし、そのチケット番号を持つ `sudog` を待機リストから見つけて再開させます。

### `src/sync/cond.go`

このファイルは、`sync.Cond` の公開APIを新しいランタイム関数にマッピングします。

```go
type Cond struct {
	L Locker
	notify  notifyList // Replaced sema and waiters
	checker copyChecker
}

func (c *Cond) Wait() {
	c.checker.check()
	t := runtime_notifyListAdd(&c.notify) // Get a ticket
	c.L.Unlock()
	runtime_notifyListWait(&c.notify, t) // Wait with the ticket
	c.L.Lock()
}

func (c *Cond) Signal() {
	c.checker.check()
	runtime_notifyListNotifyOne(&c.notify) // Notify one using the new runtime function
}

func (c *Cond) Broadcast() {
	c.checker.check()
	runtime_notifyListNotifyAll(&c.notify) // Notify all using the new runtime function
}
```

*   `Cond` 構造体は、`sema` と `waiters` フィールドの代わりに `notify notifyList` を持つようになりました。
*   `Wait()` メソッドは、まず `runtime_notifyListAdd` を呼び出してチケットを取得し、その後ロックを解放してから `runtime_notifyListWait` で待機します。
*   `Signal()` と `Broadcast()` メソッドは、それぞれ `runtime_notifyListNotifyOne` と `runtime_notifyListNotifyAll` を呼び出すように簡素化されました。これにより、`sync` パッケージ側での複雑なロジックがランタイム側に移譲され、より効率的で堅牢な実装が実現されています。

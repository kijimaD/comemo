# [インデックス 22667] ファイルの概要

このコミットは、Go言語の`go/scanner`パッケージにおける`(*ErrorList).Sort`メソッドの安定化を目的としています。具体的には、同じソースコード上の位置に複数のエラーが存在する場合のソート結果を安定させるため、エラーメッセージ（`Msg`フィールド）もソートの考慮対象に加える変更が行われました。これにより、テストデータやログファイルにおける不要な差分（diff）の発生を防ぎ、より予測可能で安定したエラーリストの出力が保証されます。

## 元コミット内容

`go/scanner`パッケージの`(*ErrorList).Sort`メソッドを安定化する変更です。エラーリストが同じ位置に複数の項目を含む場合、ソート結果を安定させるために、新たに`Msg`フィールドも考慮されるようになりました。

この変更の動機は、リポジトリで追跡されているログにおいて、ソートされた`scanner.ErrorList`の出力に差分が生じるのを避けるためです。例えば、以下のような差分を回避します。

```
-testdata/foo.go:19:44: "bar"
 testdata/foo.go:19:44: "qux"
+testdata/foo.go:19:44: "bar"
```

この変更は提出前に[0]で承認されました。

副次的な影響として、`go/parser/testdata`内の1つのファイルも更新する必要がありました。このファイルでは、パーサーが2つの異なるエラーを生成します。

```
testdata/issue3106.src:22:5: expected ';', found 'if'
testdata/issue3106.src:22:5: expected operand, found 'if'
```

実際の期待されるエラーを比較する前に、前者はソース行ごとに1つのエラーのみを保持するようにフィルタリングされます[1]。新しい`(*ErrorList).Less`では、`RemoveMultiplies`の呼び出し後に保持されるエラーが以前とは異なるものになります。

## 変更の背景

この変更の主な背景は、Go言語のツールチェイン、特に`go/scanner`パッケージが生成するエラーリストの出力の**非決定性**にありました。

Goのソースコードをスキャン（字句解析）する`go/scanner`パッケージは、構文エラーなどを検出した際に`ErrorList`という構造体にエラー情報を蓄積します。この`ErrorList`は、通常、エラーの発生位置（行番号、列番号）に基づいてソートされます。しかし、**同じソースコード上の位置（行と列）で複数の異なるエラーが発生する**場合、従来のソートロジックでは、それらのエラー間の相対的な順序が保証されていませんでした。

この非決定性は、特に以下のような問題を引き起こしていました。

1.  **テストの不安定性**: Goのパーサーやスキャナーのテストでは、特定のエラー出力が期待されます。同じ入力ファイルに対して、テスト実行ごとにエラーリストの順序が変わり、結果としてテストが不安定になったり、CI/CDパイプラインで不必要な差分（diff）が発生したりする原因となっていました。コミットメッセージにある例のように、`testdata/foo.go:19:44`のような同じ位置で異なるメッセージのエラーが複数ある場合、ソート順が非決定的だと、`git diff`で不要な変更として検出されてしまう問題がありました。
2.  **ログのノイズ**: 開発者がエラーログを追跡する際、同じコードベースでもビルド環境や実行タイミングによってエラーの順序が変わると、ログの比較や分析が困難になります。

この問題を解決し、エラーリストのソート結果を**安定化（stabilize）**させることで、テストの信頼性を向上させ、開発者のデバッグ体験を改善することが、このコミットの動機となりました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と`go/scanner`パッケージに関する知識が必要です。

### 1. `go/scanner`パッケージ

`go/scanner`パッケージは、Go言語のソースコードを字句解析（lexical analysis）するためのパッケージです。ソースコードの文字列を入力として受け取り、それをトークン（識別子、キーワード、演算子、リテラルなど）のストリームに変換します。この過程で構文的に不正な部分があれば、エラーを報告します。

### 2. `scanner.Error`と`scanner.ErrorList`

*   **`scanner.Error`**: `go/scanner`パッケージが検出した個々のエラーを表す構造体です。通常、エラーが発生したソースコード上の位置（ファイル名、行番号、列番号）とエラーメッセージ（`Msg`）を含みます。
*   **`scanner.ErrorList`**: 複数の`scanner.Error`オブジェクトを保持するスライス（`[]Error`）であり、エラーのコレクションを表します。この`ErrorList`には、エラーをソートするための`Sort()`メソッドや、重複するエラーを処理するためのメソッドなどが提供されています。

### 3. ソートにおける「安定化（Stabilize）」

ソートアルゴリズムにおける「安定（stable）なソート」とは、ソートキーが同じ要素の相対的な順序が、ソート後も元の順序と変わらないことを保証する特性を指します。

例えば、以下のような要素のリストを考えます。
`[(A, 1), (B, 2), (C, 1)]`

ここで、ソートキーが数値部分だとします。
*   **不安定なソート**: `[(A, 1), (C, 1), (B, 2)]` のように、キーが同じ`A`と`C`の相対順序が入れ替わる可能性があります。
*   **安定なソート**: `[(A, 1), (C, 1), (B, 2)]` のように、キーが同じ`A`と`C`の相対順序が元のリストと同じ`A`が先、`C`が後となることが保証されます。

このコミットでは、`ErrorList`のソートにおいて、エラーの発生位置（行番号と列番号）が同じ場合に、エラーメッセージ（`Msg`）を次のソートキーとして利用することで、ソートの安定性を確保しようとしています。これにより、同じ位置で発生した複数のエラーの相対的な順序が、エラーメッセージの辞書順で決定されるようになり、非決定性が排除されます。

### 4. `go/parser`パッケージとテストデータ

`go/parser`パッケージは、`go/scanner`が生成したトークンストリームを受け取り、Go言語の構文木（AST: Abstract Syntax Tree）を構築する役割を担います。このパッケージのテストでは、意図的にエラーを含むGoのソースコードファイル（`testdata`ディレクトリ内）を使用し、パーサーが期待通りのエラーを報告するかどうかを検証します。

コミットメッセージにある`testdata/issue3106.src`は、このようなテストデータの一つであり、パーサーが複数のエラーを報告するケースを扱っています。

### 5. `RemoveMultiplies`関数

コミットメッセージに言及されている`RemoveMultiplies`関数（`go/parser/error_test.go`内で使用）は、テストの際に、同じソース行で発生した複数のエラーの中から1つだけを保持するようにフィルタリングする目的で使用されます。これは、テストの期待値を簡素化するためによく行われる処理です。このコミットによるソート順の変更が、`RemoveMultiplies`によって最終的に残されるエラーに影響を与える可能性があるため、テストデータの更新が必要となりました。

## 技術的詳細

このコミットの技術的な核心は、`go/scanner`パッケージ内の`ErrorList`型に実装されている`Less`メソッドの変更にあります。`ErrorList`は`sort.Interface`インターフェースを満たすように設計されており、`Sort()`メソッドが呼び出されると、内部的に`sort.Sort()`関数が`Less`メソッドを使用して要素の比較と並べ替えを行います。

変更前の`Less`メソッドは、主にエラーの行番号（`Line`）と列番号（`Column`）に基づいてエラーを比較していました。

```go
// 変更前 (簡略化)
func (p ErrorList) Less(i, j int) bool {
    e := p[i]
    f := p[j]
    if e.Line < f.Line {
        return true
    }
    if e.Line == f.Line {
        return e.Column < f.Column // 行が同じなら列で比較
    }
    return false
}
```

このロジックでは、`e.Line == f.Line` かつ `e.Column == f.Column` の場合、つまり**同じ行と列に複数のエラーが存在する場合**、`Less`メソッドは`false`を返します。これは、`i`番目のエラーが`j`番目のエラーよりも小さいとは判断されないことを意味しますが、同時に`j`番目のエラーが`i`番目のエラーよりも小さいとも判断されないため、ソートアルゴリズムはこれらの要素の相対的な順序を保証しません（不安定なソート）。

このコミットでは、この不安定性を解消するために、`Less`メソッドに以下の変更が加えられました。

1.  **行番号と列番号が同じ場合、エラーメッセージ（`Msg`）で比較するロジックを追加。**
    *   `e.Line == f.Line` かつ `e.Column == f.Column` の場合、`p[i].Msg < p[j].Msg` を評価し、`i`番目のエラーメッセージが`j`番目のエラーメッセージよりも辞書順で小さい場合に`true`を返すようにしました。

これにより、同じ位置で発生したエラーは、そのエラーメッセージの辞書順に基づいて安定してソートされるようになります。

```go
// 変更後 (簡略化)
func (p ErrorList) Less(i, j int) bool {
    e := p[i]
    f := p[j]
    if e.Line < f.Line {
        return true
    }
    if e.Line == f.Line {
        if e.Column < f.Column {
            return true
        }
        if e.Column == f.Column {
            // 行と列が同じ場合、Msgフィールドで比較
            if p[i].Msg < p[j].Msg {
                return true
            }
        }
    }
    return false
}
```

## コアとなるコードの解説

`src/go/scanner/errors.go`内の`ErrorList.Less`メソッドの変更は、Goのソートインターフェース（`sort.Interface`）の要件を満たすためのものです。このメソッドは、`ErrorList`内の2つのエラー要素`p[i]`と`p[j]`を比較し、`p[i]`が`p[j]`よりも「小さい」と判断される場合に`true`を返します。

変更前のロジックでは、まず行番号（`e.Line`と`f.Line`）で比較し、行番号が同じであれば列番号（`e.Column`と`f.Column`）で比較していました。しかし、行番号も列番号も同じ場合（つまり、同じソースコード上の位置で複数のエラーが発生した場合）、それ以上の比較基準がなかったため、`Less`メソッドは`false`を返していました。これは、`sort.Sort`が使用するクイックソートのような不安定なソートアルゴリズムでは、これらの「等しい」要素の相対的な順序が保証されないことを意味します。

変更後の`Less`メソッドでは、この「等しい」ケースをさらに掘り下げています。

```go
		if e.Line == f.Line { // 行番号が同じ場合
			if e.Column < f.Column { // まず列番号で比較
				return true // iの列がjより小さければiが小さい
			}
			if e.Column == f.Column { // 列番号も同じ場合
				if p[i].Msg < p[j].Msg { // エラーメッセージ（Msg）で比較
					return true // iのメッセージがjより辞書順で小さければiが小さい
				}
			}
		}
```

この追加されたロジックにより、行番号と列番号が完全に一致するエラー同士は、そのエラーメッセージの文字列を辞書順で比較することで、明確な順序が与えられるようになりました。例えば、「`expected operand, found 'if'`」と「`expected ';', found 'if'`」という2つのエラーが同じ位置で発生した場合、メッセージの辞書順で「`expected ';', found 'if'`」の方が「`expected operand, found 'if'`」よりも先にくるため、ソート結果が常に一貫するようになります。

この変更は、`go/scanner`や`go/parser`のテストにおいて、エラーリストの出力が非決定的に変化する問題を解決し、テストの安定性と信頼性を向上させる上で非常に重要です。また、開発者がエラーログを分析する際にも、常に同じ順序でエラーが報告されるため、デバッグ作業が容易になります。

`src/go/parser/testdata/issue3106.src`の変更は、この`Less`メソッドの新しい挙動によって、`RemoveMultiplies`関数がフィルタリング後に残すエラーが変わったことを反映しています。これは、ソートロジックの変更が、エラー処理パイプラインの他の部分にどのように影響を与えるかを示す良い例です。

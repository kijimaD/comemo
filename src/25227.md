# [インデックス 25227] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるミューテーターアシストのバランス追跡メカニズムを根本的に変更するものです。以前は、GCサイクル中にミューテーター（ユーザープログラム）が割り当てたバイト数と、GCスキャン作業量を個別に追跡し、その比率からアシストの必要性を判断していました。このコミットでは、このアプローチを改め、GCアシストクレジットを直接バイト単位で追跡する新しい方式を導入しています。これにより、GCアシストの効率性と正確性が向上し、GCサイクル中のパフォーマンスが安定します。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Sun Oct 4 20:16:57 2015 -0700

    runtime: directly track GC assist balance
    
    Currently we track the per-G GC assist balance as two monotonically
    increasing values: the bytes allocated by the G this cycle (gcalloc)
    and the scan work performed by the G this cycle (gcscanwork). The
    assist balance is hence assistRatio*gcalloc - gcscanwork.
    
    This works, but has two important downsides:
    
    1) It requires floating-point math to figure out if a G is in debt or
       not. This makes it inappropriate to check for assist debt in the
       hot path of mallocgc, so we only do this when a G allocates a new
       span. As a result, Gs can operate "in the red", leading to
       under-assist and extended GC cycle length.
    
    2) Revising the assist ratio during a GC cycle can lead to an "assist
       burst". If you think of plotting the scan work performed versus
       heaps size, the assist ratio controls the slope of this line.
       However, in the current system, the target line always passes
       through 0 at the heap size that triggered GC, so if the runtime
       increases the assist ratio, there has to be a potentially large
       assist to jump from the current amount of scan work up to the new
       target scan work for the current heap size.
    
    This commit replaces this approach with directly tracking the GC
    assist balance in terms of allocation credit bytes. Allocating N bytes
    simply decreases this by N and assisting raises it by the amount of
    scan work performed divided by the assist ratio (to get back to
    bytes).
    
    This will make it cheap to figure out if a G is in debt, which will
    let us efficiently check if an assist is necessary *before* performing
    an allocation and hence keep Gs "in the black".
    
    This also fixes assist bursts because the assist ratio is now in terms
    of *remaining* work, rather than work from the beginning of the GC
    cycle. Hence, the plot of scan work versus heap size becomes
    continuous: we can revise the slope, but this slope always starts from
    where we are right now, rather than where we were at the beginning of
    the cycle.

## 元コミット内容

GoランタイムのGCアシストバランスの追跡方法を直接的なものに変更します。

現在、各Goroutine (G) のGCアシストバランスは、GCサイクル中にGが割り当てたバイト数 (`gcalloc`) と、Gが実行したスキャン作業量 (`gcscanwork`) という2つの単調増加する値として追跡されています。アシストバランスは `assistRatio * gcalloc - gcscanwork` として計算されます。

この方法は機能しますが、2つの重要な欠点があります。

1.  **浮動小数点演算のオーバーヘッド**: Gが「負債」状態にあるかどうかを判断するために浮動小数点演算が必要となります。このため、`mallocgc` のホットパスでアシスト負債をチェックするのには不適切であり、Gが新しいスパンを割り当てる際にのみチェックが行われます。結果として、Gは「赤字」状態で動作し続け、アシスト不足やGCサイクル期間の延長につながる可能性があります。
2.  **アシストバースト**: GCサイクル中にアシスト比率を修正すると、「アシストバースト」が発生する可能性があります。スキャン作業量とヒープサイズのグラフを考えると、アシスト比率はその線の傾きを制御します。しかし、現在のシステムでは、ターゲットラインは常にGCをトリガーしたヒープサイズで0を通過するため、ランタイムがアシスト比率を増加させると、現在のヒープサイズに対する新しいターゲットスキャン作業量までジャンプするために、潜在的に大きなアシストが必要となります。

このコミットでは、このアプローチを、割り当てクレジットバイトの観点からGCアシストバランスを直接追跡する方法に置き換えます。Nバイトを割り当てると、この値はNだけ減少し、アシストを行うと、実行されたスキャン作業量をアシスト比率で割った量（バイトに戻すため）だけ増加します。

これにより、Gが負債状態にあるかどうかを安価に判断できるようになり、割り当てを実行する「前」にアシストが必要かどうかを効率的にチェックできるようになります。これにより、Gを「黒字」状態に保つことができます。

また、アシスト比率がGCサイクルの開始時からの作業量ではなく、「残りの」作業量に基づいて計算されるため、アシストバーストも解消されます。したがって、スキャン作業量とヒープサイズのグラフは連続的になります。傾きを修正することはできますが、この傾きは常に現在の状態から始まり、GCサイクルの開始時からの状態ではありません。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作する並行GCです。ミューテーター（ユーザープログラム）がオブジェクトを割り当てる際に、GCの進行を助けるためにGC作業の一部を実行することがあります。これを「ミューテーターアシスト」と呼びます。ミューテーターアシストは、GCがヒープの増加に追いつくようにするために重要です。

このコミット以前のGoランタイムでは、ミューテーターアシストのバランスを追跡するために、各Goroutine (G) がGCサイクル中に割り当てたバイト数 (`gcalloc`) と、Gが実行したスキャン作業量 (`gcscanwork`) を使用していました。そして、`assistRatio * gcalloc - gcscanwork` という式でアシストの「負債」を計算していました。この値が正であれば、GはGC作業を助ける必要があり、負であれば、GC作業を助ける必要がない、あるいはクレジットがある、と判断していました。

しかし、この方式には以下の2つの大きな問題がありました。

1.  **浮動小数点演算によるパフォーマンスオーバーヘッド**: `assistRatio` が `float64` であったため、アシストバランスの計算に浮動小数点演算が必要でした。浮動小数点演算は整数演算に比べてコストが高く、特に `mallocgc` のような頻繁に呼び出されるホットパスで実行するには不適切でした。このため、ランタイムはGが新しいメモリ領域（スパン）を割り当てる際にのみアシスト負債をチェックしていました。結果として、Gは負債状態（「in the red」）であってもGCアシストを行わずに割り当てを続け、GCの進行が遅れる、あるいはGCサイクルが長引く原因となっていました。これは、GCの目標である「低レイテンシ」と「高スループット」に悪影響を与えます。
2.  **アシストバーストの発生**: GCサイクル中にヒープの状態が変化し、GCの目標達成に必要なアシスト比率 (`assistRatio`) が動的に調整されることがあります。しかし、以前のシステムでは、アシスト比率が変更されると、GCサイクル開始時からの累積割り当て量に基づいて計算されるため、突然大量のアシスト作業が必要となる「アシストバースト」が発生する可能性がありました。これは、プログラムの実行が一時的に停止したり、大幅に遅延したりする原因となり、ユーザー体験を損なう可能性がありました。

これらの問題を解決し、より効率的で予測可能なGCアシストメカニズムを実現するために、このコミットではアシストバランスの追跡方法が変更されました。

## 前提知識の解説

このコミットの変更を理解するためには、以下のGoランタイムのGCに関する基本的な概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGC作業を進めます。
*   **ミューテーター (Mutator)**: ユーザープログラムの実行スレッドを指します。ミューテーターはオブジェクトを割り当てたり、既存のオブジェクトを操作したりします。
*   **GCサイクル**: GCが開始されてから終了するまでの一連のプロセスです。これには、マークフェーズ（到達可能なオブジェクトを識別する）、スイープフェーズ（到達不能なオブジェクトが占めていたメモリを解放する）などが含まれます。
*   **ミューテーターアシスト (Mutator Assist)**: GCサイクル中にミューテーターがメモリを割り当てる際に、GC作業の一部を肩代わりして実行することです。これにより、GCがヒープの増加に追いつき、GCの停止時間を短縮することができます。
*   **`gcalloc` (旧)**: 各Goroutineが現在のGCサイクル中に割り当てたバイト数を追跡する変数でした。
*   **`gcscanwork` (旧)**: 各Goroutineが現在のGCサイクル中に実行したスキャン作業量（バイト単位）を追跡する変数でした。
*   **`assistRatio` (旧)**: ミューテーターアシストが実行すべきスキャン作業量と割り当てられたバイト数の比率を示す浮動小数点数でした。
*   **GC負債 (GC Debt)**: ミューテーターがGCアシストを十分に実行せず、GCの進行が遅れている状態を指します。この状態では、ミューテーターは追加のGC作業を実行する必要があります。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域です。
*   **スパン (Span)**: Goのメモリ管理において、連続したページ（通常は8KB）のブロックを指します。オブジェクトはスパン内に割り当てられます。

## 技術的詳細

このコミットの核心は、GCアシストバランスの追跡方法を、割り当てられたバイト数とスキャン作業量から計算する相対的なアプローチから、**割り当てクレジットバイト**を直接追跡する絶対的なアプローチへと変更した点にあります。

新しいアプローチでは、各Goroutine (`g`) は `gcAssistBytes` という単一の `int64` 変数を持つようになります。

*   **`gcAssistBytes` の意味**:
    *   この値が正の場合、Goroutineは `gcAssistBytes` 分のメモリをGCアシストなしで割り当てることができる「クレジット」を持っていることを意味します。
    *   この値が負の場合、GoroutineはGCアシストを実行してこの負債を解消する必要があることを意味します。負債の量は `-gcAssistBytes` となります。

*   **割り当て時の動作**:
    *   Goroutineが `N` バイトを割り当てると、`gcAssistBytes` は `N` だけ減少します。これにより、割り当てが直接クレジットを消費する形になります。

*   **アシスト時の動作**:
    *   GoroutineがGCアシストとして `W` 単位のスキャン作業を実行すると、`gcAssistBytes` は `W / assistWorkPerByte` だけ増加します。ここで `assistWorkPerByte` は、1バイトの割り当てに対してどれだけのスキャン作業が必要かを示す比率です。この逆数である `assistBytesPerWork` も導入され、スキャン作業量からクレジットバイトへの変換を効率的に行います。

この変更により、以下の技術的な利点がもたらされます。

1.  **浮動小数点演算の排除とホットパスの高速化**:
    *   `gcAssistBytes` は `int64` であり、割り当て時の減算やアシスト時の加算はすべて整数演算で行われます。これにより、GC負債のチェックと更新が非常に高速になります。
    *   `mallocgc` のホットパスで `gcAssistBytes` を直接チェックできるようになったため、Goroutineが負債状態になる前にアシストを強制できるようになります。これにより、「in the red」状態での動作が減少し、GCの効率が向上し、GCサイクル期間の延長を防ぎます。

2.  **アシストバーストの解消**:
    *   以前のシステムでは、`assistRatio` がGCサイクル開始時からの累積割り当て量に基づいて計算されていたため、`assistRatio` が変更されると、過去の割り当てに対する未達成のアシスト作業が突然発生し、アシストバーストを引き起こしていました。
    *   新しいシステムでは、`gcAssistBytes` は「残りの」作業量に基づいてクレジットを追跡します。`assistWorkPerByte` は現在のヒープの状態と残りのGC作業に基づいて動的に計算されます。これにより、`assistWorkPerByte` が変更されても、その変更は現在のクレジット残高に連続的に適用されます。スキャン作業量とヒープサイズのグラフは連続的になり、傾き（`assistWorkPerByte`）は現在の状態から調整されるため、突然の大きなアシストは不要になります。

3.  **`gcControllerState` の変更**:
    *   `gcControllerState` 構造体には、`assistRatio` の代わりに `assistWorkPerByte` と `assistBytesPerWork` が導入されました。
        *   `assistWorkPerByte`: 1バイトの割り当てに対してミューテーターアシストが実行すべきスキャン作業量の比率。
        *   `assistBytesPerWork`: `assistWorkPerByte` の逆数で、スキャン作業量からクレジットバイトへの変換に使用されます。
    *   `revise()` 関数は、これらの新しい比率を計算する際に、`memstats.heap_scan` から既に実行されたスキャン作業量 (`c.scanWork`) を差し引くことで、「残りの」スキャン作業量を正確に推定するようになりました。また、`heapDistance` も `memstats.heap_live` を基準に計算されるようになり、より現在のヒープ状態を反映するようになりました。

これらの変更により、GoのGCはよりスムーズに、より予測可能に動作するようになり、プログラムの実行に対するGCの影響がさらに軽減されます。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の `g` 構造体

```go
// Per-G gcController state
// gcalloc    uintptr // bytes allocated during this GC cycle (DELETED)
// gcscanwork int64   // scan work done (or stolen) this GC cycle (DELETED)
gcAssistBytes int64
```
最も根本的な変更は、各Goroutine (`g`) の状態を定義する `g` 構造体から、`gcalloc` と `gcscanwork` という2つのフィールドが削除され、代わりに `gcAssistBytes` という単一の `int64` フィールドが追加されたことです。
*   `gcalloc` と `gcscanwork` は、GCサイクル開始時からの累積値を追跡していました。
*   `gcAssistBytes` は、GoroutineがGCアシストなしで割り当て可能なバイト数のクレジット、またはGCアシストによって解消すべき負債を直接表します。正の値はクレジット、負の値は負債です。これにより、GCアシストの判断が単一の整数値のチェックで可能になり、浮動小数点演算が不要になります。

### `src/runtime/mgc.go` の `gcControllerState` と `revise()`

```go
type gcControllerState struct {
	// ...
	// assistRatio is the ratio of scan work to allocated bytes (DELETED)
	// that should be performed by mutator assists. This is
	// computed at the beginning of each cycle and updated every
	// time heap_scan is updated.
	// assistRatio float64 (DELETED)

	// assistWorkPerByte is the ratio of scan work to allocated
	// bytes that should be performed by mutator assists. This is
	// computed at the beginning of each cycle and updated every
	// time heap_scan is updated.
	assistWorkPerByte float64

	// assistBytesPerWork is 1/assistWorkPerByte.
	assistBytesPerWork float64
	// ...
}

func (c *gcControllerState) revise() {
	// Compute the expected scan work remaining.
	scanWorkExpected := int64(memstats.heap_scan) - c.scanWork
	if scanWorkExpected < 1000 {
		scanWorkExpected = 1000
	}

	// Compute the heap distance remaining.
	heapDistance := int64(c.heapGoal) - int64(memstats.heap_live)
	if heapDistance <= 0 {
		heapDistance = 1
	}

	// Compute the mutator assist ratio so by the time the mutator
	// allocates the remaining heap bytes up to next_gc, it will
	// have done (or stolen) the remaining amount of scan work.
	c.assistWorkPerByte = float64(scanWorkExpected) / float64(heapDistance)
	c.assistBytesPerWork = float64(heapDistance) / float64(scanWorkExpected)
}
```
`gcControllerState` 構造体では、`assistRatio` が `assistWorkPerByte` と `assistBytesPerWork` に置き換えられました。
*   `assistWorkPerByte` は、1バイトの割り当てに対してどれだけのスキャン作業が必要かを示します。
*   `assistBytesPerWork` はその逆数で、スキャン作業量からクレジットバイトへの変換を容易にします。

`revise()` 関数は、GCサイクル中にこれらの比率を再計算します。重要な変更点は、`scanWorkExpected` と `heapDistance` の計算が「残りの」作業量とヒープサイズに基づいて行われるようになったことです。
*   `scanWorkExpected` は、`memstats.heap_scan` (GCサイクル開始時からの総スキャン作業量) から `c.scanWork` (既に実行されたスキャン作業量) を差し引くことで、**残りのスキャン作業量**を推定します。
*   `heapDistance` は、`c.heapGoal` (GCの目標ヒープサイズ) から `memstats.heap_live` (現在のライブヒープサイズ) を差し引くことで、**残りのヒープ割り当て可能量**を推定します。
これにより、アシスト比率の調整が現在の状況に即したものとなり、アシストバーストが解消されます。

### `src/runtime/mgcmark.go` の `gcAssistAlloc()`

```go
func gcAssistAlloc(size uintptr, allowAssist bool) {
	// ...
	// Record allocation.
	gp.gcAssistBytes -= int64(size)

	if !allowAssist || gp.gcAssistBytes >= 0 {
		return
	}

	// ...

	// Compute the amount of scan work we need to do to make the
	// balance positive.
	debtBytes := -gp.gcAssistBytes
	scanWork := int64(gcController.assistWorkPerByte * float64(debtBytes))

	// ... (steal credit and perform scan work logic)

	// Record that we did this much scan work.
	scanWork -= workDone
	// Back out the number of bytes of assist credit that
	// this scan work counts for. The "1+" is a poor man's
	// round-up, to ensure this adds credit even if
	// assistBytesPerWork is very low.
	gp.gcAssistBytes += 1 + int64(gcController.assistBytesPerWork*float64(workDone))
}
```
`gcAssistAlloc` 関数は、Goroutineがメモリを割り当てる際に呼び出されます。
*   割り当てが行われると、`gp.gcAssistBytes -= int64(size)` によって、割り当てられたバイト数分だけクレジットが減少（または負債が増加）します。
*   アシストが必要かどうかのチェックは、`gp.gcAssistBytes >= 0` (クレジットがあるか、負債がないか) で行われます。これにより、浮動小数点演算なしで高速に判断できます。
*   アシストが必要な場合、負債バイト数 (`debtBytes`) を `gcController.assistWorkPerByte` でスキャン作業量に変換し、その作業を実行します。
*   スキャン作業が完了すると、`gp.gcAssistBytes += 1 + int64(gcController.assistBytesPerWork*float64(workDone))` によって、実行されたスキャン作業量に対応するクレジットバイトが `gcAssistBytes` に加算されます。`1+` は、`assistBytesPerWork` が非常に小さい場合でもクレジットが確実に増加するようにするための丸め処理です。

これらの変更により、GoのGCアシストメカニズムは、より効率的で、予測可能で、プログラムの実行に対する影響が少ないものになりました。

## 元コミット内容

GoランタイムのGCアシストバランスの追跡方法を直接的なものに変更します。

現在、各Goroutine (G) のGCアシストバランスは、GCサイクル中にGが割り当てたバイト数 (`gcalloc`) と、Gが実行したスキャン作業量 (`gcscanwork`) という2つの単調増加する値として追跡されています。アシストバランスは `assistRatio * gcalloc - gcscanwork` として計算されます。

この方法は機能しますが、2つの重要な欠点があります。

1.  **浮動小数点演算のオーバーヘッド**: Gが「負債」状態にあるかどうかを判断するために浮動小数点演算が必要となります。このため、`mallocgc` のホットパスでアシスト負債をチェックするのには不適切であり、Gが新しいスパンを割り当てる際にのみチェックが行われます。結果として、Gは「赤字」状態で動作し続け、アシスト不足やGCサイクル期間の延長につながる可能性があります。
2.  **アシストバースト**: GCサイクル中にアシスト比率を修正すると、「アシストバースト」が発生する可能性があります。スキャン作業量とヒープサイズのグラフを考えると、アシスト比率はその線の傾きを制御します。しかし、現在のシステムでは、ターゲットラインは常にGCをトリガーしたヒープサイズで0を通過するため、ランタイムがアシスト比率を増加させると、現在のヒープサイズに対する新しいターゲットスキャン作業量までジャンプするために、潜在的に大きなアシストが必要となります。

このコミットでは、このアプローチを、割り当てクレジットバイトの観点からGCアシストバランスを直接追跡する方法に置き換えます。Nバイトを割り当てると、この値はNだけ減少し、アシストを行うと、実行されたスキャン作業量をアシスト比率で割った量（バイトに戻すため）だけ増加します。

これにより、Gが負債状態にあるかどうかを安価に判断できるようになり、割り当てを実行する「前」にアシストが必要かどうかを効率的にチェックできるようになります。これにより、Gを「黒字」状態に保つことができます。

また、アシスト比率がGCサイクルの開始時からの作業量ではなく、「残りの」作業量に基づいて計算されるため、アシストバーストも解消されます。したがって、スキャン作業量とヒープサイズのグラフは連続的になります。傾きを修正することはできますが、この傾きは常に現在の状態から始まり、GCサイクルの開始時からの状態ではありません。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作する並行GCです。ミューテーター（ユーザープログラム）がオブジェクトを割り当てる際に、GCの進行を助けるためにGC作業の一部を実行することがあります。これを「ミューテーターアシスト」と呼びます。ミューテーターアシストは、GCがヒープの増加に追いつくようにするために重要です。

このコミット以前のGoランタイムでは、ミューテーターアシストのバランスを追跡するために、各Goroutine (G) がGCサイクル中に割り当てたバイト数 (`gcalloc`) と、Gが実行したスキャン作業量 (`gcscanwork`) を使用していました。そして、`assistRatio * gcalloc - gcscanwork` という式でアシストの「負債」を計算していました。この値が正であれば、GはGC作業を助ける必要があり、負であれば、GC作業を助ける必要がない、あるいはクレジットがある、と判断していました。

しかし、この方式には以下の2つの大きな問題がありました。

1.  **浮動小数点演算によるパフォーマンスオーバーヘッド**: `assistRatio` が `float64` であったため、アシストバランスの計算に浮動小数点演算が必要でした。浮動小数点演算は整数演算に比べてコストが高く、特に `mallocgc` のような頻繁に呼び出されるホットパスで実行するには不適切でした。このため、ランタイムはGが新しいメモリ領域（スパン）を割り当てる際にのみアシスト負債をチェックしていました。結果として、Gは負債状態（「in the red」）であってもGCアシストを行わずに割り当てを続け、GCの進行が遅れる、あるいはGCサイクルが長引く原因となっていました。これは、GCの目標である「低レイテンシ」と「高スループット」に悪影響を与えます。
2.  **アシストバーストの発生**: GCサイクル中にヒープの状態が変化し、GCの目標達成に必要なアシスト比率 (`assistRatio`) が動的に調整されることがあります。しかし、以前のシステムでは、アシスト比率が変更されると、GCサイクル開始時からの累積割り当て量に基づいて計算されるため、突然大量のアシスト作業が必要となる「アシストバースト」が発生する可能性がありました。これは、プログラムの実行が一時的に停止したり、大幅に遅延したりする原因となり、ユーザー体験を損なう可能性がありました。

これらの問題を解決し、より効率的で予測可能なGCアシストメカニズムを実現するために、このコミットではアシストバランスの追跡方法が変更されました。

## 前提知識の解説

このコミットの変更を理解するためには、以下のGoランタイムのGCに関する基本的な概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGC作業を進めます。
*   **ミューテーター (Mutator)**: ユーザープログラムの実行スレッドを指します。ミューテーターはオブジェクトを割り当てたり、既存のオブジェクトを操作したりします。
*   **GCサイクル**: GCが開始されてから終了するまでの一連のプロセスです。これには、マークフェーズ（到達可能なオブジェクトを識別する）、スイープフェーズ（到達不能なオブジェクトが占めていたメモリを解放する）などが含まれます。
*   **ミューテーターアシスト (Mutator Assist)**: GCサイクル中にミューテーターがメモリを割り当てる際に、GC作業の一部を肩代わりして実行することです。これにより、GCがヒープの増加に追いつき、GCの停止時間を短縮することができます。
*   **`gcalloc` (旧)**: 各Goroutineが現在のGCサイクル中に割り当てたバイト数を追跡する変数でした。
*   **`gcscanwork` (旧)**: 各Goroutineが現在のGCサイクル中に実行したスキャン作業量（バイト単位）を追跡する変数でした。
*   **`assistRatio` (旧)**: ミューテーターアシストが実行すべきスキャン作業量と割り当てられたバイト数の比率を示す浮動小数点数でした。
*   **GC負債 (GC Debt)**: ミューテーターがGCアシストを十分に実行せず、GCの進行が遅れている状態を指します。この状態では、ミューテーターは追加のGC作業を実行する必要があります。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域です。
*   **スパン (Span)**: Goのメモリ管理において、連続したページ（通常は8KB）のブロックを指します。オブジェクトはスパン内に割り当てられます。

## 技術的詳細

このコミットの核心は、GCアシストバランスの追跡方法を、割り当てられたバイト数とスキャン作業量から計算する相対的なアプローチから、**割り当てクレジットバイト**を直接追跡する絶対的なアプローチへと変更した点にあります。

新しいアプローチでは、各Goroutine (`g`) は `gcAssistBytes` という単一の `int64` 変数を持つようになります。

*   **`gcAssistBytes` の意味**:
    *   この値が正の場合、Goroutineは `gcAssistBytes` 分のメモリをGCアシストなしで割り当てることができる「クレジット」を持っていることを意味します。
    *   この値が負の場合、GoroutineはGCアシストを実行してこの負債を解消する必要があることを意味します。負債の量は `-gcAssistBytes` となります。

*   **割り当て時の動作**:
    *   Goroutineが `N` バイトを割り当てると、`gcAssistBytes` は `N` だけ減少します。これにより、割り当てが直接クレジットを消費する形になります。

*   **アシスト時の動作**:
    *   GoroutineがGCアシストとして `W` 単位のスキャン作業を実行すると、`gcAssistBytes` は `W / assistWorkPerByte` だけ増加します。ここで `assistWorkPerByte` は、1バイトの割り当てに対してどれだけのスキャン作業が必要かを示す比率です。この逆数である `assistBytesPerWork` も導入され、スキャン作業量からクレジットバイトへの変換を効率的に行います。

この変更により、以下の技術的な利点がもたらされます。

1.  **浮動小数点演算の排除とホットパスの高速化**:
    *   `gcAssistBytes` は `int64` であり、割り当て時の減算やアシスト時の加算はすべて整数演算で行われます。これにより、GC負債のチェックと更新が非常に高速になります。
    *   `mallocgc` のホットパスで `gcAssistBytes` を直接チェックできるようになったため、Goroutineが負債状態になる前にアシストを強制できるようになります。これにより、「in the red」状態での動作が減少し、GCの効率が向上し、GCサイクル期間の延長を防ぎます。

2.  **アシストバーストの解消**:
    *   以前のシステムでは、`assistRatio` がGCサイクル開始時からの累積割り当て量に基づいて計算されていたため、`assistRatio` が変更されると、過去の割り当てに対する未達成のアシスト作業が突然発生し、アシストバーストを引き起こしていました。
    *   新しいシステムでは、`gcAssistBytes` は「残りの」作業量に基づいてクレジットを追跡します。`assistWorkPerByte` は現在のヒープの状態と残りのGC作業に基づいて動的に計算されます。これにより、`assistWorkPerByte` が変更されても、その変更は現在のクレジット残高に連続的に適用されます。スキャン作業量とヒープサイズのグラフは連続的になり、傾き（`assistWorkPerByte`）は現在の状態から調整されるため、突然の大きなアシストは不要になります。

3.  **`gcControllerState` の変更**:
    *   `gcControllerState` 構造体には、`assistRatio` の代わりに `assistWorkPerByte` と `assistBytesPerWork` が導入されました。
        *   `assistWorkPerByte`: 1バイトの割り当てに対してミューテーターアシストが実行すべきスキャン作業量の比率。
        *   `assistBytesPerWork`: `assistWorkPerByte` の逆数で、スキャン作業量からクレジットバイトへの変換に使用されます。
    *   `revise()` 関数は、これらの新しい比率を計算する際に、`memstats.heap_scan` から既に実行されたスキャン作業量 (`c.scanWork`) を差し引くことで、「残りの」スキャン作業量を正確に推定するようになりました。また、`heapDistance` も `memstats.heap_live` を基準に計算されるようになり、より現在のヒープ状態を反映するようになりました。

これらの変更により、GoのGCはよりスムーズに、より予測可能に動作するようになり、プログラムの実行に対するGCの影響がさらに軽減されます。

	// ...
	// assistRatio is the ratio of scan work to allocated bytes (DELETED)

	// computed at the beginning of each cycle and updated every
	// time heap_scan is updated.
	// assistRatio float64 (DELETED)

	// assistWorkPerByte is the ratio of scan work to allocated
	// bytes that should be performed by mutator assists. This is
	// computed at the beginning of each cycle and updated every
	// time heap_scan is updated.
	assistWorkPerByte float64

	// assistBytesPerWork is 1/assistWorkPerByte.
	assistBytesPerWork float64
	// ...
}

func (c *gcControllerState) revise() {
	// Compute the expected scan work remaining.
	scanWorkExpected := int64(memstats.heap_scan) - c.scanWork
	if scanWorkExpected < 1000 {
		scanWorkExpected = 1000
	}

	// Compute the heap distance remaining.
	heapDistance := int64(c.heapGoal) - int64(memstats.heap_live)
	if heapDistance <= 0 {
		heapDistance = 1
	}

	// Compute the mutator assist ratio so by the time the mutator
	// allocates the remaining heap bytes up to next_gc, it will
	// have done (or stolen) the remaining amount of scan work.
	c.assistWorkPerByte = float64(scanWorkExpected) / float64(heapDistance)
	c.assistBytesPerWork = float64(heapDistance) / float64(scanWorkExpected)
}
```
`gcControllerState` 構造体では、`assistRatio` が `assistWorkPerByte` と `assistBytesPerWork` に置き換えられました。
*   `assistWorkPerByte` は、1バイトの割り当てに対してどれだけのスキャン作業が必要かを示します。
*   `assistBytesPerWork` はその逆数で、スキャン作業量からクレジットバイトへの変換を容易にします。

`revise()` 関数は、GCサイクル中にこれらの比率を再計算します。重要な変更点は、`scanWorkExpected` と `heapDistance` の計算が「残りの」作業量とヒープサイズに基づいて行われるようになったことです。
*   `scanWorkExpected` は、`memstats.heap_scan` (GCサイクル開始時からの総スキャン作業量) から `c.scanWork` (既に実行されたスキャン作業量) を差し引くことで、**残りのスキャン作業量**を推定します。
*   `heapDistance` は、`c.heapGoal` (GCの目標ヒープサイズ) から `memstats.heap_live` (現在のライブヒープサイズ) を差し引くことで、**残りのヒープ割り当て可能量**を推定します。
これにより、アシスト比率の調整が現在の状況に即したものとなり、アシストバーストが解消されます。

### `src/runtime/mgcmark.go` の `gcAssistAlloc()`

```go
func gcAssistAlloc(size uintptr, allowAssist bool) {
	// ...
	// Record allocation.
	gp.gcAssistBytes -= int64(size)

	if !allowAssist || gp.gcAssistBytes >= 0 {
		return
	}

	// ...

	// Compute the amount of scan work we need to do to make the
	// balance positive.
	debtBytes := -gp.gcAssistBytes
	scanWork := int64(gcController.assistWorkPerByte * float64(debtBytes))

	// ... (steal credit and perform scan work logic)

	// Record that we did this much scan work.
	scanWork -= workDone
	// Back out the number of bytes of assist credit that
	// this scan work counts for. The "1+" is a poor man's
	// round-up, to ensure this adds credit even if
	// assistBytesPerWork is very low.
	gp.gcAssistBytes += 1 + int64(gcController.assistBytesPerWork*float64(workDone))
}
```
`gcAssistAlloc` 関数は、Goroutineがメモリを割り当てる際に呼び出されます。
*   割り当てが行われると、`gp.gcAssistBytes -= int64(size)` によって、割り当てられたバイト数分だけクレジットが減少（または負債が増加）します。
*   アシストが必要かどうかのチェックは、`gp.gcAssistBytes >= 0` (クレジットがあるか、負債がないか) で行われます。これにより、浮動小数点演算なしで高速に判断できます。
*   アシストが必要な場合、負債バイト数 (`debtBytes`) を `gcController.assistWorkPerByte` でスキャン作業量に変換し、その作業を実行します。
*   スキャン作業が完了すると、`gp.gcAssistBytes += 1 + int64(gcController.assistBytesPerWork*float64(workDone))` によって、実行されたスキャン作業量に対応するクレジットバイトが `gcAssistBytes` に加算されます。`1+` は、`assistBytesPerWork` が非常に小さい場合でもクレジットが確実に増加するようにするための丸め処理です。

### `src/runtime/mheap.go` の `mHeap_Alloc_m()`

```go
func mHeap_Alloc_m(h *mheap, npage uintptr, sizeclass int32, large bool) *mspan {
	// ...
	// heap_scan and heap_live were updated.
	if gcBlackenEnabled != 0 {
		gcController.revise()
	}
	// ...
}
```
`mHeap_Alloc_m` は、ヒープから新しいメモリ領域を割り当てる際に呼び出されます。`gcController.revise()` の呼び出し位置が変更され、`heap_scan` と `heap_live` が更新された後に実行されるようになりました。これにより、`revise` 関数が常に最新のヒープ統計に基づいてアシスト比率を計算できるようになり、GCの適応性が向上します。

これらの変更により、GoのGCアシストメカニズムは、より効率的で、予測可能で、プログラムの実行に対する影響が少ないものになりました。

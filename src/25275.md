# [インデックス 25275] ファイルの概要

このコミットは、Goランタイムにおけるスタック管理に関連する定数とロジックの定義を統合することを目的としています。具体的には、これまで `src/runtime/stack1.go` と `src/runtime/stack2.go` の2つのファイルに分散していたスタックレイアウトパラメータやスタックガードに関する定義を、`src/runtime/stack.go` という単一のファイルに集約しています。これにより、Goのgoroutineのスタックサイズ、スタックオーバーフロー検出、スタック拡張メカニズムに関するすべての重要な定数と説明が一箇所で管理されるようになります。

## 変更の背景

この変更の主な背景は、Goランタイムのコードベースの整理と保守性の向上です。スタック管理に関する重要な定数やコメントが `stack1.go` と `stack2.go` という2つの異なるファイルに分かれて存在していました。これは、関連する情報が散在しているため、開発者がスタックの挙動を理解したり、関連する定数を変更したりする際に、複数のファイルを参照する必要があり、非効率的でした。

ファイルを統合することで、スタック管理に関するすべての定義が一箇所に集約され、コードの可読性と発見しやすさが向上します。これは、単一責任の原則（Single Responsibility Principle）にも合致し、特定の機能（この場合はスタック管理の定数定義）に関するコードが単一のモジュールにまとめられることで、将来的な変更やデバッグが容易になります。

Issue #12952で議論された内容も、この統合の動機付けとなった可能性があります。通常、このようなリファクタリングは、コードベースの成長に伴う複雑性の管理や、特定の機能領域の明確化のために行われます。

## 前提知識の解説

### Goランタイムのスタック管理

Go言語のプログラムは、OSのスレッドではなく、Goランタイムが管理する軽量な実行単位である「goroutine」上で動作します。各goroutineは独自のスタックを持ち、このスタックは必要に応じて動的に拡張されます。Goのスタックは「セグメントスタック」ではなく、「連続スタック」として実装されており、スタックが不足しそうになると、より大きな新しいスタックが割り当てられ、古いスタックの内容が新しいスタックにコピーされます。このプロセスは「スタックスプリット（Stack Split）」と呼ばれます。

### スタックガード (Stack Guard)

スタックオーバーフローを検出するための重要なメカニズムです。各goroutineの `g->stackguard` フィールドは、スタックのボトムから一定バイト数上を指すように設定されます。関数が呼び出される際、その関数のスタックフレームサイズが `g->stackguard` の値と比較され、スタックオーバーフローの危険性がないかチェックされます。

### `morestack` 関数

スタックオーバーフローが検出された場合、またはスタックスプリットチェックが必要な場合に呼び出されるランタイム関数です。この関数は、現在のgoroutineのスタックを拡張する役割を担います。新しい、より大きなスタックを割り当て、現在のスタックの内容を新しいスタックにコピーし、実行を継続します。

### `NOSPLIT` 関数

Goの関数には、スタックスプリットチェックを行うものと行わないものがあります。`NOSPLIT` とマークされた関数は、スタックスプリットチェックを行いません。これらの関数は、スタックガード領域内で安全に実行できるだけの十分なスタック空間があることを前提としています。例えば、`morestack` 自体や、`deferproc` のようなランタイムのコア機能の一部は `NOSPLIT` として実装されることがあります。これは、スタック拡張処理中にさらにスタック拡張チェックを行うことによる無限再帰や、パフォーマンスオーバーヘッドを避けるためです。

### スタック関連の主要な定数

コミットで統合されたファイルには、以下のような重要な定数が定義されています。これらはGoランタイムがスタックを管理するために使用する閾値やサイズを決定します。

*   `_StackSystem`: OS固有の目的（シグナルハンドリングなど）のために、通常のガード領域の下に追加されるスタックバイト数。Windows, Plan 9, Darwin/ARMなどで使用されます。
*   `_StackMin`: Goコードが使用する最小スタックサイズ。
*   `_FixedStack`: 割り当てられる最小スタックサイズ。`_StackMin` と `_StackSystem` を基に計算され、2のべき乗に切り上げられます。
*   `_StackBig`: この値よりも大きなフレームを持つ関数は、スタックスプリットチェックに追加の命令を使用します。これは、`SP - framesize` がゼロを下回るオーバーフローを避けるためです。
*   `_StackGuard`: スタックのボトムからこのバイト数上を指すポインタがスタックガードとして設定されます。
*   `_StackSmall`: スタックスプリットチェック後、SPがスタックガードからこのバイト数下まで突き出ることが許容されます。これにより、小さなフレームを持つ関数のチェックシーケンスで命令を節約できます。
*   `_StackLimit`: `NOSPLIT` 関数チェーンが使用できる最大バイト数。`_StackGuard - _StackSystem - _StackSmall` で計算されます。
*   `_StackPreempt`, `_StackFork`: goroutineのプリエンプション要求やフォーク要求を示すために `g->stackguard0` に格納される特殊な値。

## 技術的詳細

このコミットは、Goランタイムのスタック管理ロジック自体を変更するものではなく、その定義の構造を改善するものです。

以前は、`src/runtime/stack1.go` と `src/runtime/stack2.go` という2つのファイルが存在していました。
*   `stack1.go` には、主にスタックレイアウトパラメータに関する詳細なコメントと、`_StackSystem` などの一部の定数が含まれていました。
*   `stack2.go` には、`_StackMin`, `_FixedStack`, `_StackBig`, `_StackGuard`, `_StackSmall`, `_StackLimit` などの残りのスタック関連定数と、`_StackPreempt`, `_StackFork` といった特殊な定数が含まれていました。

このコミットでは、以下の手順で統合が行われました。
1.  `src/runtime/stack1.go` が `src/runtime/stack.go` にリネームされました。これは、`stack.go` がスタック管理の主要な定義ファイルとなることを意味します。
2.  `src/runtime/stack2.go` の内容が、リネームされた `src/runtime/stack.go` の既存の内容（元 `stack1.go` の内容）の先頭に「prepend（前置）」されました。これにより、`stack2.go` の内容が `stack.go` の冒頭に移動し、`stack2.go` は削除されました。

結果として、スタックレイアウトのパラメータ、スタックガードの動作、スタックスプリットチェックのシーケンスに関する詳細な説明コメント、およびすべての関連定数が `src/runtime/stack.go` という単一のファイルに集約されました。

コミットの差分を見ると、`stack1.go` の内容が `stack.go` に移動し、その後に `stack2.go` の内容が追加されていることがわかります。特に、`stack2.go` にあったスタックレイアウトパラメータに関する詳細なコメントブロック（アセンブリレベルでのスタックチェックの挙動を説明している部分）が、新しい `stack.go` の冒頭に移動しています。このコメントは、Goのコンパイラ（6c）とリンカ（gcc）の両方でインクルードされることを意図しており、スタックオーバーフローチェックの最適化されたシーケンス（`CMPQ guard, SP` など）について詳しく説明しています。

この統合は、機能的な変更を伴わない純粋なリファクタリングであり、Goランタイムの内部構造の理解と保守を容易にすることを目的としています。

## コアとなるコードの解説

統合された `src/runtime/stack.go` ファイルの主要な部分は、Goランタイムのスタック管理に関する定数定義と、それらを説明する詳細なコメントブロックです。

ファイル冒頭の大きなコメントブロックは、スタックレイアウトパラメータについて説明しています。
```go
/*
Stack layout parameters.
Included both by runtime (compiled via 6c) and linkers (compiled via gcc).

The per-goroutine g->stackguard is set to point StackGuard bytes
above the bottom of the stack.  Each function compares its stack
pointer against g->stackguard to check for overflow.  To cut one
instruction from the check sequence for functions with tiny frames,
the stack is allowed to protrude StackSmall bytes below the stack
guard.  Functions with large frames don't bother with the check and
always call morestack.  The sequences are (for amd64, others are
similar):

	guard = g->stackguard
	frame = function's stack frame size
	argsize = size of function arguments (call + return)

	stack frame size <= StackSmall:
		CMPQ guard, SP
		JHI 3(PC)
		MOVQ m->morearg, $(argsize << 32)
		CALL morestack(SB)

	stack frame size > StackSmall but < StackBig
		LEAQ (frame-StackSmall)(SP), R0
		CMPQ guard, R0
		JHI 3(PC)
		MOVQ m->morearg, $(argsize << 32)
		CALL morestack(SB)

	stack frame size >= StackBig:
		MOVQ m->morearg, $((argsize << 32) | frame)
		CALL morestack(SB)

The bottom StackGuard - StackSmall bytes are important: there has
to be enough room to execute functions that refuse to check for
stack overflow, either because they need to be adjacent to the
actual caller's frame (deferproc) or because they handle the imminent
stack overflow (morestack).

For example, deferproc might call malloc, which does one of the
above checks (without allocating a full frame), which might trigger
a call to morestack.  This sequence needs to fit in the bottom
section of the stack.  On amd64, morestack's frame is 40 bytes, and
deferproc's frame is 56 bytes.  That fits well within the
StackGuard - StackSmall bytes at the bottom.
The linkers explore all possible call traces involving non-splitting
functions to make sure that this limit cannot be violated.
*/
```
このコメントは、Goランタイムがスタックオーバーフローをどのように検出し、`morestack` を呼び出すかをアセンブリレベルの擬似コードで詳細に説明しています。特に、関数のスタックフレームサイズに応じて異なるチェックシーケンスが使用されること、そして `_StackSmall` や `_StackBig` といった定数がこれらの最適化にどのように関与するかが示されています。また、`NOSPLIT` 関数（`deferproc` や `morestack` など）がスタックガード領域内で安全に実行されるための要件についても強調されています。

その後に続く `const` ブロックでは、前述の「前提知識の解説」で触れた各種スタック関連定数が定義されています。
```go
const (
	_StackSystem = goos_windows*512*ptrSize + goos_plan9*512 + goos_darwin*goarch_arm*1024
	_StackMin = 2048
	_FixedStack0 = _StackMin + _StackSystem
	_FixedStack1 = _FixedStack0 - 1
	_FixedStack2 = _FixedStack1 | (_FixedStack1 >> 1)
	_FixedStack3 = _FixedStack2 | (_FixedStack2 >> 2)
	_FixedStack4 = _FixedStack3 | (_FixedStack3 >> 4)
	_FixedStack5 = _FixedStack4 | (_FixedStack4 >> 8)
	_FixedStack6 = _FixedStack5 | (_FixedStack5 >> 16)
	_FixedStack  = _FixedStack6 + 1
	_StackBig = 4096
	_StackGuard = 640*stackGuardMultiplier + _StackSystem
	_StackSmall = 128
	_StackLimit = _StackGuard - _StackSystem - _StackSmall
)

const (
	_StackPreempt = uintptrMask & -1314
	_StackFork    = uintptrMask & -1234
)
```
これらの定数は、Goランタイムがgoroutineのスタックを初期化し、実行中に管理するために不可欠な数値的パラメータを提供します。例えば、`_FixedStack` はgoroutineに最初に割り当てられるスタックの最小サイズを決定し、`_StackGuard` はスタックオーバーフロー検出の閾値を設定します。`_StackPreempt` や `_StackFork` は、スタックガード領域を一時的に乗っ取ることで、プリエンプションやフォークといった特殊なランタイムイベントをトリガーするために使用されます。

この統合により、Goランタイムのスタック管理の全体像を把握するために必要なすべての情報が、`src/runtime/stack.go` という単一のファイルで利用できるようになりました。

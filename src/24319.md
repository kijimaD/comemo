# [インデックス 24319] ファイルの概要

このコミットは、Go言語の `net` パッケージにおける `Dialer` のタイムアウト処理に関するバグを修正します。具体的には、`Dialer` に `Timeout` が設定されている場合、接続試行中にデッドラインが複数回再計算されることで、ユーザーが指定した総タイムアウト時間を超過してしまう問題を解決します。この修正により、デッドラインは `Dial` 操作の開始時に一度だけ正確に計算され、その値が接続試行全体で一貫して使用されるようになります。

## 元コミット内容

`net: compute the Dialer deadline exactly once.`

相対的な `Timeout` を使用してダイヤルする場合、デッドライン関数は時間のかかる作業を行う前に呼び出される場合にのみ意味があります。

この変更は、`deadline` を一度だけ呼び出し、その結果を `Dial` 操作が完了するまで保存します。`partialDeadline` の実装は、以下のパッチセット3に戻されます:
https://go-review.googlesource.com/#/c/8768/3..4/src/net/dial.go

そうしないと、複数のIPアドレスを持つ名前をダイヤルする場合、またはDNSが遅い場合に、デッドラインが再計算されることで、要求された総 `Timeout` をユーザーが超過してしまいます。

`Fixes #11796`

## 変更の背景

Goの `net.Dialer` は、ネットワーク接続を確立するための機能を提供します。これには、接続試行に時間制限を設けるための `Timeout` と `Deadline` の設定が含まれます。`Timeout` は接続試行の最大許容「期間」を相対的に指定するのに対し、`Deadline` は接続試行が終了すべき「絶対時刻」を指定します。

このコミット以前のGoの `net` パッケージでは、`Dialer` に `Timeout` が設定されている場合、特にDNS解決によって複数のIPアドレスが返されるようなシナリオで問題が発生していました。`Dial` メソッドは、これらのIPアドレスに対して順番に接続を試行することがあります。この際、各接続試行の前に `partialDeadline` 関数が呼び出され、残りのアドレス数に基づいて部分的なデッドラインを計算していました。

しかし、この `partialDeadline` の計算ロジックが、`Dialer` の `deadline` 関数を各試行のたびに呼び出していました。`Dialer.deadline` 関数は、現在の時刻と `Dialer.Timeout` を基に絶対的なデッドラインを計算します。このため、DNS解決や最初の接続試行に時間がかかると、その後の接続試行の前に `deadline` 関数が呼び出された際に、既に経過した時間が考慮されずに新たなデッドラインが計算されてしまうという問題がありました。結果として、ユーザーが `Timeout` で指定した期間よりも長い時間が経過してから接続試行がタイムアウトする、という予期せぬ動作を引き起こしていました。

この問題は、GitHub issue #11796 で報告され、ユーザーが指定したタイムアウトが守られないという形で顕在化しました。このコミットは、この問題を解決し、`Timeout` の意図された動作を保証することを目的としています。

## 前提知識の解説

*   **`net.Dialer`**: Go言語でネットワーク接続を確立するための構造体です。TCP、UDPなどのネットワークタイプとアドレスを指定して接続を試みます。
*   **`net.Dialer.Timeout`**: `time.Duration` 型で、`Dial` 操作が完了するまでの最大許容時間を相対的に指定します。この期間内に接続が確立されない場合、操作は失敗します。
*   **`net.Dialer.Deadline`**: `time.Time` 型で、`Dial` 操作が終了すべき絶対時刻を指定します。`Timeout` と `Deadline` の両方が設定されている場合、先に到達した方が優先されます。
*   **`partialDeadline`**: `net` パッケージ内部で使用される関数で、複数のアドレスに対して接続を試行する際に、各アドレスに対する部分的なデッドラインを計算するために使われます。これは、全体的なタイムアウトを複数の試行に分割して適用するような概念です。
*   **DNS解決と複数のIPアドレス**: ホスト名（例: `google.com`）をIPアドレスに解決する際、単一のIPアドレスだけでなく、複数のIPアドレス（IPv4とIPv6の両方、または複数のIPv4アドレスなど）が返されることがあります。`net.Dialer` はこれらのアドレスに対して順番に接続を試行することが一般的です。
*   **`go-review.googlesource.com/#/c/8768/3..4/src/net/dial.go`**: このリンクは、Goのコードレビューシステムにおける特定の変更セット（パッチセット3から4への変更）を指しています。この変更が、今回のバグの原因となった `partialDeadline` の実装変更を含んでいたことが示唆されています。

## 技術的詳細

このコミットの核心的な問題は、`net.Dialer` の `Dial` メソッドが複数のIPアドレスに対して接続を試行する際に、`Timeout` の計算が非効率的かつ不正確であった点にあります。

以前の実装では、`Dialer.Dial` メソッド内で `resolveAddrList` を呼び出す際に一度 `d.deadline(time.Now())` が呼び出され、これがDNS解決のデッドラインとして使用されていました。しかし、その後の各IPアドレスへの接続試行ループ内で、`partialDeadline` 関数が再度 `ctx.partialDeadline(time.Now(), len(ras)-i)` のように呼び出されていました。ここで `ctx.partialDeadline` は内部的に `d.deadline(time.Now())` を呼び出し、その時点の現在時刻を基準にデッドラインを再計算していました。

この再計算が問題でした。例えば、ユーザーが5秒の `Timeout` を設定し、DNS解決に1秒、最初のIPアドレスへの接続試行に2秒かかったとします。この時点で合計3秒が経過しています。もし `partialDeadline` が再度 `time.Now()` を基にデッドラインを計算すると、残りの2秒ではなく、再び5秒のタイムアウト期間が考慮されてしまう可能性がありました。これにより、各接続試行が独立したタイムアウト期間を持つかのように振る舞い、結果として全体の `Dial` 操作がユーザーが意図した5秒を大幅に超えてしまうことがありました。特に、DNS解決が遅い場合や、複数のIPアドレスへの接続試行が連続して失敗する場合にこの問題は顕著でした。

このコミットでは、この問題を解決するために以下の変更が導入されました。

1.  **`finalDeadline` の導入**: `Dialer.Dial` メソッドの冒頭で `finalDeadline := d.deadline(time.Now())` を呼び出し、`Dial` 操作全体の最終的なデッドラインを一度だけ計算します。この `finalDeadline` は、`dialContext` 構造体の新しいフィールド `finalDeadline` に保存されます。
2.  **`partialDeadline` 関数の変更**: `partialDeadline` 関数は、`*Dialer` のメソッドから独立したパッケージレベルの関数 `partialDeadline(now, deadline time.Time, addrsRemaining int)` に変更されました。これにより、`partialDeadline` は `Dialer` のインスタンスから直接デッドラインを再計算するのではなく、`Dial` 操作の開始時に計算された `finalDeadline` を引数として受け取るようになります。
3.  **`dialContext` の利用**: `dialSerial` 関数（複数のアドレスを順番に試行するロジック）内で `partialDeadline` を呼び出す際に、`ctx.finalDeadline` が渡されるようになります。これにより、各接続試行における部分的なデッドラインの計算は、最初に決定された `finalDeadline` を基準に行われるため、全体のタイムアウトが超過することがなくなります。

この変更により、`Dialer` の `Timeout` は、`Dial` 操作全体に対して一貫した時間制限として機能するようになり、ユーザーの期待通りの動作が保証されます。

## コアとなるコードの解説

このコミットの主要な変更点は、`net.Dialer` の `Dial` メソッドにおけるデッドラインの計算ロジックを根本的に見直したことです。

1.  **デッドラインの一元化**: 以前は `Dial` 処理の途中で `d.deadline(time.Now())` が複数回呼び出され、その都度新しいデッドラインが計算される可能性がありました。この変更により、`Dial` メソッドの冒頭で `finalDeadline := d.deadline(time.Now())` が一度だけ実行され、この `finalDeadline` が `Dial` 操作全体の絶対的な終了時刻として確立されます。これにより、ユーザーが設定した `Timeout` が、接続試行全体に対して一貫して適用されることが保証されます。

2.  **`dialContext` を介したデッドラインの伝達**: 新しく追加された `dialContext.finalDeadline` フィールドは、この一元化されたデッドラインを `Dial` 操作のライフサイクル全体で保持し、必要に応じて下位の関数（特に `dialSerial` 内の `partialDeadline`）に伝達する役割を担います。これにより、デッドラインの再計算を防ぎ、常に最初の `Timeout` 設定に基づいたデッドラインが参照されるようになります。

3.  **`partialDeadline` の独立化**: `partialDeadline` 関数が `*Dialer` のメソッドから独立したことで、この関数が `Dialer` の内部状態（特に `Timeout`）に依存してデッドラインを再計算する機会がなくなりました。代わりに、`Dial` メソッドで計算された `finalDeadline` を明示的に引数として受け取ることで、そのデッドラインを基に部分的なデッドラインを計算するようになります。これにより、各接続試行が全体のタイムアウト期間を尊重しつつ、残りの時間内で完了するように調整されます。

これらの変更により、`net.Dialer` の `Timeout` は、複数のIPアドレスへの接続試行やDNS解決の遅延といったシナリオにおいても、ユーザーが期待する通りに機能するようになり、接続の信頼性と予測可能性が向上しました。

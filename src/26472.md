# [インデックス 26472] ファイルの概要

このコミットは、GoコンパイラのARM64アーキテクチャ向けアセンブラ（`cmd/internal/obj/arm64`）における、リテラルプール（literal pool）のフラッシュタイミングと、スパン依存ジャンプ（span-dependent jump）の拡大に関する調整を目的としています。具体的には、PC相対アドレス指定の最大変位を保守的に設定し、リテラルプールのフラッシュを早めることで、ジャンプ命令のサイズ変更によって発生する可能性のある問題を未然に防ぎます。

## 元コミット内容

このコミットは、GoコンパイラのARM64アセンブラにおいて、リテラルプールのフラッシュロジックを調整するものです。既存のコードは、スパン依存ジャンプが可能な限り短いと仮定して、リテラルプールのフラッシュをギリギリまで遅らせていました。しかし、もし後続のパスでこれらのジャンプが拡大される必要が生じた場合、その「ギリギリのタイミング」では手遅れになる可能性がありました。このコミットは、リテラルプールのフラッシュを少し早めることで、この問題を回避することを目的としています。

この変更は、Issue #13579 を修正します。

## 変更の背景

ARM64のようなRISCアーキテクチャでは、命令セットの制約により、命令に直接埋め込める即値（immediate value）のサイズが限られています。特に、大きな定数やアドレスをロードする場合、直接命令に含めることができません。この問題を解決するために、「リテラルプール」という仕組みが利用されます。リテラルプールは、コードセクションの近くに配置されるデータ領域で、大きな定数やアドレスが格納されます。命令は、PC（プログラムカウンタ）からの相対オフセットを使って、このリテラルプール内のデータにアクセスします。

Goコンパイラのアセンブラは、コード生成の過程で、命令のサイズやジャンプの距離を最適化するために複数回のパス（ラウンド）を実行することがあります。特に、ジャンプ命令（分岐命令）は、そのターゲットまでの距離に応じて異なるエンコーディング（サイズ）を持つことがあります。これを「スパン依存ジャンプ」と呼びます。

元の実装では、リテラルプールをコードの最後に配置することで、PC相対アドレス指定の範囲を最大限に活用しようとしていました。しかし、このアプローチは、ジャンプ命令が最初に短い形式でエンコードされ、その後に距離が長くなったために長い形式に「拡大」される必要がある場合に問題を引き起こす可能性がありました。ジャンプ命令が拡大されると、その命令以降のコードのアドレスがすべてずれてしまい、リテラルプールへのPC相対オフセットも変化します。もしリテラルプールがコードの「最後の瞬間」に配置されていると、このアドレスのずれによってリテラルプールへのアクセスが有効なPC相対範囲外になってしまう可能性がありました。

このコミットは、このような状況、特にジャンプ命令の拡大によってリテラルプールへのアクセスが不可能になることを防ぐために、リテラルプールのフラッシュタイミングを調整し、PC相対アドレス指定の許容範囲をより保守的に設定することで、堅牢性を高めることを目的としています。

## 前提知識の解説

### 1. ARM64アーキテクチャと命令セット

ARM64は、モバイルデバイスやサーバーなど幅広い分野で利用される64ビットRISC（Reduced Instruction Set Computer）アーキテクチャです。命令は固定長（通常32ビット）であり、複雑な操作を単純な命令の組み合わせで実行します。

### 2. PC相対アドレス指定 (PC-relative Addressing)

ARM64では、現在のプログラムカウンタ（PC）の値を基準としてメモリ上のデータやコードにアクセスする「PC相対アドレス指定」が頻繁に用いられます。これは、コードがメモリ上のどこにロードされても正しく動作する「位置独立コード（Position-Independent Code, PIC）」を生成するために重要です。PC相対アドレス指定では、命令にオフセット値が埋め込まれ、`PC + オフセット` の形でアドレスが計算されます。このオフセット値には通常、ビット数の制限があります。

### 3. リテラルプール (Literal Pool)

前述の通り、ARM64命令は即値のサイズに制限があります。例えば、32ビットや64ビットの任意のアドレスや定数を直接命令に埋め込むことはできません。そこで、コンパイラやアセンブラは、これらの大きな値をコードセクション内の特別なデータ領域に配置します。このデータ領域が「リテラルプール」です。命令は、PC相対アドレス指定を使ってリテラルプール内の値にアクセスします。

リテラルプールは、通常、現在の命令から近い場所に配置される必要があります。なぜなら、PC相対オフセットの範囲には制限があるためです。アセンブラは、リテラルプールを適切なタイミングで「フラッシュ」（コードストリームに挿入）し、その後の命令がプール内の値にアクセスできるようにします。

### 4. スパン依存ジャンプ (Span-dependent Jumps)

ジャンプ命令（分岐命令）は、そのターゲットアドレスまでの距離（スパン）に応じて、異なるエンコーディングを持つことがあります。例えば、短い距離のジャンプには短い命令形式が使われ、長い距離のジャンプには長い命令形式が使われることがあります。アセンブラは、最初のパスでジャンプ距離を推定し、最も短い命令形式を選択しようとします。しかし、その後のコード生成や最適化の過程で、命令が追加されたり削除されたりすることで、ジャンプのターゲットまでの距離が変化することがあります。もし距離が長くなり、短い命令形式では到達できなくなった場合、アセンブラはジャンプ命令をより長い形式に「拡大（enlarge）」する必要があります。

### 5. アセンブラの複数パス (Multiple Passes in Assembler)

コンパイラやアセンブラは、最終的なバイナリコードを生成するために複数回のパスを実行することが一般的です。
- **第一パス**: シンボル解決、命令の仮エンコーディング、ジャンプ距離の推定などを行います。
- **第二パス以降**: 第一パスの結果に基づいて、ジャンプ命令のサイズを調整したり、リテラルプールの配置を決定したりします。スパン依存ジャンプの拡大は、この複数パスの過程で発生する可能性があります。

### 6. Goコンパイラの`cmd/internal/obj`パッケージ

`cmd/internal/obj`パッケージは、Goコンパイラのバックエンドの一部であり、特定のアセンブリ言語（この場合はARM64）の命令を生成する役割を担っています。このパッケージは、Goのソースコードから中間表現を経て、最終的な機械語命令を生成するパイプラインの一部です。

## 技術的詳細

このコミットの核心は、ARM64アセンブラにおけるリテラルプールの管理戦略の変更にあります。

### `flushpool`関数の変更

`flushpool`関数は、リテラルプールをコードストリームに挿入するタイミングを決定します。変更前は、現在のPCからリテラルプールの開始位置までの距離が `1024 * 1024` バイト（1MB）未満の場合にリテラルプールをフラッシュしない、というロジックでした。これは、リテラルプールを可能な限り遅く、つまりコードの最後に近い位置に配置しようとする試みでした。

変更後、この閾値は `maxPCDisp` という新しい定数に置き換えられました。

```go
// 変更前
// } else if p.Pc+int64(pool.size)-int64(pool.start) < 1024*1024 {

// 変更後
} else if p.Pc+int64(pool.size)-int64(pool.start) < maxPCDisp {
```

### `maxPCDisp`定数の導入

新しい定数 `maxPCDisp` が導入され、その値は `512 * 1024` バイト（512KB）に設定されました。

```go
// Maximum PC-relative displacement.
// The actual limit is ±2²⁰, but we are conservative
// to avoid needing to recompute the literal pool flush points
// as span-dependent jumps are enlarged.
const maxPCDisp = 512 * 1024
```

このコメントが示すように、ARM64のPC相対変位の実際の最大値は ±2^20 バイト（±1MB）ですが、`maxPCDisp` はその半分である512KBに設定されています。これは、スパン依存ジャンプが拡大された際に、リテラルプールのフラッシュポイントを再計算する必要が生じるのを避けるための「保守的な」アプローチです。ジャンプが拡大されると、その後の命令のアドレスがずれるため、リテラルプールへのオフセットも変化します。この変化が許容範囲を超えないように、最初からより狭い範囲でリテラルプールをフラッシュするようにしています。これにより、リテラルプールがPC相対アドレス指定の範囲外になるリスクを低減します。

### `ispcdisp`関数の変更

`ispcdisp`関数は、与えられた値が有効なPC相対変位であるかどうかをチェックします。変更前は、±0xfffff（約±1MB）の範囲をチェックしていました。

```go
// 変更前
// return v >= -0xfffff && v <= 0xfffff && (v&3) == 0

// 変更後
return -maxPCDisp < v && v < maxPCDisp && v&3 == 0
```

変更後、このチェックも `maxPCDisp` を使用するように更新され、有効なPC相対変位の範囲が ±512KB に制限されました。`v&3 == 0` は、アドレスが4バイトアラインメントされていることを意味します。ARM64の命令は4バイト単位で配置されるため、PC相対オフセットも4の倍数である必要があります。

### `brdist`関数の変更

`brdist`関数は、分岐命令の距離を計算し、その距離が許容範囲を超えていないかをチェックします。もし距離が遠すぎる場合、変更前は診断メッセージを出力するだけでした。

```go
// 変更前
// ctxt.Diag("branch too far\\n%v", p)

// 変更後
ctxt.Diag("branch too far %#x vs %#x [%p]\\n%v\\n%v", v, t, ctxt.Blitrl, p, p.Pcond)
panic("branch too far")
```

変更後、診断メッセージに加えて `panic("branch too far")` が追加されました。これは、分岐が遠すぎるという状況が、回復不可能なエラーであり、アセンブラの処理を続行すべきではないという判断を示しています。これにより、アセンブラが不正なコードを生成するのを防ぎ、早期に問題を検出できるようになります。

## コアとなるコードの変更箇所

`src/cmd/internal/obj/arm64/asm7.go` ファイルが変更されています。

- `flushpool` 関数内のリテラルプールフラッシュの条件式が変更されました。
- `maxPCDisp` という新しい定数が導入されました。
- `ispcdisp` 関数のPC相対変位チェックの範囲が変更されました。
- `brdist` 関数で「branch too far」エラーが発生した場合の処理が、診断メッセージの強化とパニックの発生に変更されました。

## コアとなるコードの解説

### `maxPCDisp` 定数

```go
// Maximum PC-relative displacement.
// The actual limit is ±2²⁰, but we are conservative
// to avoid needing to recompute the literal pool flush points
// as span-dependent jumps are enlarged.
const maxPCDisp = 512 * 1024
```
この定数は、PC相対アドレス指定でアクセスできる最大オフセットを定義します。実際のARM64のハードウェア的な制限は±1MBですが、Goアセンブラはこれを±512KBに制限しています。この保守的な制限は、スパン依存ジャンプが拡大された際に、リテラルプールの位置がPC相対アドレス指定の範囲外になることを防ぐためのものです。ジャンプ命令のサイズが変更されると、その後の命令のアドレスがすべてずれるため、リテラルプールへのオフセットも変化します。この変化を吸収できるだけの「余裕」を持たせるために、意図的に狭い範囲を設定しています。

### `flushpool` 関数内の条件式

```go
} else if p.Pc+int64(pool.size)-int64(pool.start) < maxPCDisp {
	return
}
```
このコードは、リテラルプールをフラッシュするかどうかを決定します。`p.Pc` は現在の命令のプログラムカウンタ、`pool.size` はリテラルプールの現在のサイズ、`pool.start` はリテラルプールの開始アドレスです。この式は、現在の命令からリテラルプールの末尾までの距離が `maxPCDisp` 未満である場合、リテラルプールをフラッシュせずに処理を続行することを示しています。つまり、リテラルプールがまだPC相対アドレス指定の範囲内に収まっている限り、フラッシュを遅らせるという基本的なロジックは維持しつつ、その「範囲」をより保守的に設定しています。これにより、リテラルプールがコードのより早い段階でフラッシュされる可能性が高まります。

### `ispcdisp` 関数

```go
func ispcdisp(v int32) bool {
	return -maxPCDisp < v && v < maxPCDisp && v&3 == 0
}
```
この関数は、与えられたオフセット `v` が有効なPC相対変位であるかをチェックします。
- `-maxPCDisp < v && v < maxPCDisp`: オフセット `v` が `-maxPCDisp` と `maxPCDisp` の間にあることを確認します。これにより、PC相対アドレス指定の範囲が `maxPCDisp` によって制限されます。
- `v&3 == 0`: オフセット `v` が4の倍数であることを確認します。ARM64の命令は4バイトアラインメントされているため、PC相対オフセットも4の倍数である必要があります。

### `brdist` 関数内のパニック

```go
	if v < -t || v >= t {
		ctxt.Diag("branch too far %#x vs %#x [%p]\\n%v\\n%v", v, t, ctxt.Blitrl, p, p.Pcond)
		panic("branch too far")
	}
```
この変更は、分岐命令のターゲットが遠すぎて到達できない場合に、アセンブラがパニックを起こすようにします。以前は診断メッセージを出力するだけでしたが、この変更により、このような状況が致命的なエラーとして扱われ、アセンブラが不正なコードを生成するのを防ぎます。これは、アセンブラの堅牢性を高めるための重要な変更です。

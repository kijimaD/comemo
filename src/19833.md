# [インデックス 19833] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるLinux環境での`epoll`使用時の「偽の接続イベント（spurious on-connect events）」発生を防ぐための修正です。具体的には、非ブロッキングソケットの接続処理において、`connect`システムコールが`EINPROGRESS`を返す前にソケットディスクリプタを`epoll`インスタンスに追加してしまうことで発生する競合状態を解消します。これにより、接続が完了していないにもかかわらず、`epoll`がソケットの書き込み可能イベントを誤って通知してしまう問題を解決します。

## 変更の背景

このコミットは、Go言語のネットワークパッケージがLinux上で非ブロッキングソケットの接続を処理する際に発生していた特定のバグを修正するために導入されました。問題の核心は、`connect`システムコールが非ブロッキングモードで実行され、接続が即座に確立されない場合に`EINPROGRESS`エラーを返すという挙動と、LinuxのI/O多重化メカニズムである`epoll`の利用方法の間の競合状態にありました。

具体的には、Goのランタイムがソケットディスクリプタを`epoll`インスタンスに登録する処理（`fd.init()`を通じて行われることが多い）を、`connect`システムコールがまだ`EINPROGRESS`を返していない段階で実行してしまうことがありました。このタイミングのずれにより、`epoll`はソケットが書き込み可能であると誤って判断し、実際には接続がまだ確立されていないにもかかわらず、`EPOLLOUT`（書き込み可能）や`EPOLLHUP`（ハングアップ）といったイベントをアプリケーションに通知してしまうことがありました。これが「偽の接続イベント（spurious on-connect events）」と呼ばれる現象です。

このような偽のイベントは、アプリケーションが接続が完了したと誤認し、データの送信を試みるなど、予期せぬ動作やエラーを引き起こす可能性がありました。特に、複数のゴルーチンが同時にネットワーク操作を行うような並行性の高い環境では、この競合状態が顕在化しやすくなります。

この問題は、GoのIssueトラッカーで`golang.org/issue/8276`と`golang.org/issue/8426`として報告されていました。特に`issue/8426`は、`epoll_ctl ADD`が`connect`システムコール完了前に呼び出されることによって発生する問題として明確に記述されており、このコミットの直接的な背景となっています。

## 前提知識の解説

### 非ブロッキングソケットと`connect()`

通常の（ブロッキング）ソケットでは、`connect()`システムコールは接続が確立されるまで、またはエラーが発生するまで処理をブロックします。しかし、非ブロッキングソケットの場合、`connect()`は接続が即座に確立できない場合でもブロックせず、`EINPROGRESS`エラーを返してすぐに制御を呼び出し元に戻します。この場合、アプリケーションは後でソケットが接続可能になったことをI/O多重化メカニズム（例: `select`, `poll`, `epoll`）を通じて検知する必要があります。接続が完了すると、ソケットは書き込み可能（`EPOLLOUT`イベントなど）として通知されます。

### `epoll` (Linux)

`epoll`はLinuxカーネルが提供する高性能なI/Oイベント通知メカニズムです。多数のファイルディスクリプタ（ソケットなど）を効率的に監視し、イベントが発生したディスクリプタのみをアプリケーションに通知します。

-   **`epoll_create()`**: `epoll`インスタンスを作成します。
-   **`epoll_ctl()`**: `epoll`インスタンスにファイルディスクリプタを追加（`EPOLL_CTL_ADD`）、変更（`EPOLL_CTL_MOD`）、削除（`EPOLL_CTL_DEL`）します。この際、監視したいイベント（例: `EPOLLIN` (読み込み可能), `EPOLLOUT` (書き込み可能), `EPOLLERR` (エラー), `EPOLLHUP` (ハングアップ)）を指定します。
-   **`epoll_wait()`**: `epoll`インスタンスに登録されたファイルディスクリプタでイベントが発生するまでブロックし、発生したイベントのリストを返します。

`epoll`は、イベント通知の方式として「エッジトリガー（Edge-triggered）」と「レベルトリガー（Level-triggered）」をサポートします。この問題は、主にエッジトリガーモードでの挙動と関連していますが、Goの内部ポーリングメカニズムがどのように`epoll`を利用しているかが重要です。

### Goの`net`パッケージ内部

Goの`net`パッケージは、クロスプラットフォームなネットワークI/Oを提供するために、OS固有のシステムコールを抽象化しています。

-   **`netFD`構造体**: Goの`net`パッケージ内でソケットなどのネットワークファイルディスクリプタを抽象化するために使用される内部構造体です。これには、ソケットのファイルディスクリプタ（`sysfd`）や、I/Oポーリングのための`poll.FD`インスタンスなどが含まれます。
-   **`poll.FD`**: Goのランタイムが提供する内部のポーリングメカニズムです。Linux上では、この`poll.FD`が`epoll`システムコールをラップして、非同期I/Oイベントを処理します。`fd.init()`メソッドは、この`poll.FD`インスタンスを初期化し、必要に応じてソケットディスクリプタをOSのポーリングメカニズム（Linuxでは`epoll`）に登録する役割を担います。
-   **`syscall.Connect`**: Goの`syscall`パッケージを通じて呼び出される、OSネイティブの`connect`システムコールです。
-   **`syscall.EINPROGRESS`**: LinuxなどのUnix系OSで、非ブロッキングソケットに対する`connect()`呼び出しが、接続がまだ完了していないことを示すエラーコードです。

### スプリアスイベント（Spurious Events）

I/Oポーリングの文脈における「スプリアスイベント」とは、実際にはアプリケーションが処理すべきI/Oイベントが発生していないにもかかわらず、ポーリングメカニズムがイベントを通知してしまう現象を指します。これは通常、競合状態やポーリングメカニズムの設計上の特性（例: エッジトリガーモードでのイベントの再通知）によって発生します。このコミットのケースでは、接続が完了していないソケットに対して`EPOLLOUT`が通知されることがスプリアスイベントに該当します。

## 技術的詳細

このコミットの技術的な核心は、Goの`net`パッケージが非ブロッキングソケットの接続処理において、`fd.init()`の呼び出しタイミングを調整することにあります。

修正前は、`fd.init()`（これによりソケットが`epoll`に登録される）が、`syscall.Connect`が`EINPROGRESS`を返す前に呼び出される可能性がありました。`syscall.Connect`が`EINPROGRESS`を返した場合、それは接続がまだ進行中であることを意味します。この時点でソケットが`epoll`に登録されていると、`epoll`はソケットが書き込み可能であると誤って判断し、`EPOLLOUT`イベントを即座に発生させてしまうことがありました。これは、ソケットが非ブロッキングモードであるため、`connect`が完了するのを待たずにすぐに制御を返すためです。

修正後のアプローチは以下の通りです。

1.  **`fd.init()`の呼び出しタイミングの変更**:
    *   `src/pkg/net/fd_unix.go`の`netFD.connect`関数において、`fd.init()`の呼び出しを`syscall.Connect`の戻り値を評価した後、特に`EINPROGRESS`やその他のエラーケースを処理するブロックの後に移動しました。これにより、ソケットが`epoll`に登録されるのは、`connect`が実際に`EINPROGRESS`を返した（つまり、接続が非同期的に進行中であることが確認された）後になります。
    *   接続が即座に成功した場合（`nil`または`EISCONN`）、`fd.init()`は引き続き呼び出されますが、この場合は問題ありません。
2.  **デッドライン（期限）の伝播**:
    *   `netFD.connect`関数に`deadline time.Time`引数が追加されました。これにより、接続操作にタイムアウトを設定できるようになり、接続が指定された時間内に完了しない場合にエラーを返すことができます。これは、偽のイベントとは直接関係ありませんが、接続の堅牢性を高めるための改善です。
3.  **Windows版の調整**:
    *   `src/pkg/net/fd_windows.go`の`netFD.connect`関数も`deadline`引数を受け取るように変更されました。Windowsでは`epoll`の代わりにI/O Completion Ports (IOCP) が使用されるため、Linuxとはポーリングのメカニズムが異なります。Windows版では`fd.init()`の呼び出しは`syscall.Connect`の前に残されていますが、これはIOCPの特性上問題がないためです。IOCPはイベント駆動型であり、非同期操作の完了時にイベントを通知するため、`epoll`のような競合状態は発生しにくいです。
4.  **`sock_posix.go`の整理**:
    *   `netFD.dial`関数から`fd.init()`の呼び出しが削除されました。これは、`fd.init()`の責任が`netFD.connect`関数に一元化されたためです。これにより、コードの重複が避けられ、ロジックがより明確になりました。

この修正により、`epoll`はソケットが実際に接続可能になった（またはエラーが発生した）後にのみイベントを通知するようになり、偽の接続イベントの発生が防止されます。

## コアとなるコードの解説

### `src/pkg/net/fd_unix.go`の変更点

最も重要な変更は、`netFD.connect`関数における`fd.init()`の呼び出し位置の変更です。

-   **`fd.pd.PrepareWrite()`の削除**: 以前は`syscall.Connect`の前に`fd.pd.PrepareWrite()`が呼び出されていましたが、これは削除されました。`fd.pd`は`poll.FD`であり、`PrepareWrite`はポーリングの準備を行うものです。この呼び出しが早すぎたことが問題の一因でした。
-   **`deadline time.Time`引数の追加**: `connect`関数が接続のタイムアウトを管理するための`deadline`引数を受け取るようになりました。
-   **`fd.init()`の移動**:
    -   `syscall.Connect`が`EINPROGRESS`, `EALREADY`, `EINTR`（非ブロッキング接続が進行中または再試行が必要な状態）を返した場合、またはデフォルトのエラーケース（接続が即座に確立されなかった場合）の後に`fd.init()`が呼び出されるようになりました。
    -   これにより、ソケットが`epoll`に登録されるのは、`connect`システムコールが非同期的に進行中であることが確定した後になります。このタイミングの調整が、偽のイベントを防ぐための鍵です。
    -   接続が即座に成功した場合（`nil`または`EISCONN`）、`fd.init()`は引き続き呼び出されますが、この場合は接続が確立済みであるため問題ありません。
-   **デッドライン処理の追加**: `deadline`が設定されている場合、`fd.setWriteDeadline(deadline)`で書き込みデッドラインを設定し、関数終了時に`defer fd.setWriteDeadline(noDeadline)`でデッドラインをリセットするロジックが追加されました。

### `src/pkg/net/fd_windows.go`の変更点

-   **`deadline time.Time`引数の追加**: `fd_unix.go`と同様に、`connect`関数が`deadline`引数を受け取るようになりました。
-   **`fd.init()`の呼び出し**: Windows版では、`fd.init()`は`syscall.Connect`の前に呼び出されます。これは、WindowsのIOCP（I/O Completion Ports）がLinuxの`epoll`とは異なる非同期I/Oモデルを採用しているためです。IOCPでは、ソケットをIOCPに関連付ける処理（`fd.init()`で行われる可能性が高い）は、非同期接続操作の開始前に行っても問題ありません。イベントは操作の完了時に通知されるため、Linuxのような競合状態は発生しません。
-   **デッドライン処理の追加**: `fd_unix.go`と同様に、デッドライン処理が追加されました。

### `src/pkg/net/sock_posix.go`の変更点

-   **`fd.init()`の削除**: `netFD.dial`関数から`fd.init()`の呼び出しが削除されました。これは、`fd.init()`の責任が`netFD.connect`関数に完全に移管されたためです。これにより、`fd.init()`が呼び出されるタイミングが`netFD.connect`内で一元的に管理されるようになり、コードの整合性が向上しました。
-   **`fd.connect`への`deadline`引数の伝播**: `dial`関数から`connect`関数を呼び出す際に、`deadline`引数が正しく渡されるようになりました。

これらの変更により、Linux環境における非ブロッキングソケットの接続処理において、`epoll`へのソケット登録が適切なタイミングで行われるようになり、接続が完了していないにもかかわらず`EPOLLOUT`イベントが誤って通知されるという問題が解決されました。

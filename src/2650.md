## 変更の背景

このコミットの主な背景は、Go言語の`reflect`パッケージに、関数を動的に呼び出す機能（関数リフレクション）を導入することです。Goの初期段階では、リフレクションは主に型情報の取得や構造体フィールドへのアクセスに限定されており、関数そのものを動的に呼び出す機能は未実装でした。

`reflect.FuncValue.Call`メソッドは、インターフェース{}の値から取得した関数を、実行時に与えられた引数で呼び出し、その結果を`[]reflect.Value`として返すことを可能にします。この機能は、以下のような高度なプログラミングパターンを実現するために不可欠です。

*   **汎用的なRPCフレームワークやWebフレームワーク:** ユーザーが定義した関数を、そのシグネチャを知らなくても動的に呼び出すことができます。
*   **テストフレームワーク:** テスト関数を動的に発見し、実行することができます。
*   **コマンドラインパーサー:** コマンド名と引数に基づいて、対応する関数を呼び出すことができます。
*   **データバインディングやORM:** データベースから取得したデータを行構造体やオブジェクトにマッピングする際に、セッターメソッドを動的に呼び出すことができます。

この機能の実装は、Goの型システムとランタイムのスタック管理の深い理解を必要とし、特に異なるアーキテクチャ（386, amd64, arm）でのアセンブリレベルの操作が伴うため、複雑な作業となります。また、チャネルの型チェックの追加や型不一致メッセージの改善は、リフレクションの堅牢性を高め、開発者がより安全にリフレクションを使用できるようにするための付随的な改善です。

## 前提知識の解説

### Goの`reflect`パッケージ

`reflect`パッケージは、Goプログラムが実行時に自身の構造を検査（リフレクト）することを可能にする機能を提供します。これにより、型情報（`reflect.Type`）や値情報（`reflect.Value`）を動的に取得・操作できます。

*   **`reflect.Type`**: Goの型に関する情報（名前、サイズ、メソッドなど）を表現します。`reflect.TypeOf(i interface{})`で取得できます。
*   **`reflect.Value`**: Goの値に関する情報（実際のデータ、設定可能性など）を表現します。`reflect.ValueOf(i interface{})`で取得できます。
*   **`reflect.Kind`**: 型の基本的なカテゴリ（`Int`, `String`, `Struct`, `Func`, `Chan`など）を示します。
*   **`reflect.FuncValue`**: `reflect.Value`の一種で、関数を表します。このコミットで`Call`メソッドが実装されました。

リフレクションは強力ですが、型安全性を損なう可能性があり、パフォーマンスオーバーヘッドも伴うため、必要な場合にのみ慎重に使用すべきです。

### Goのランタイムとスタック管理

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、スケジューラ、メモリ管理、ガベージコレクション、そしてスタック管理が含まれます。

*   **Goroutineスタック**: Goの各goroutineは、動的にサイズが変更されるスタックを持っています。関数呼び出しごとにスタックフレームがプッシュされ、関数からのリターン時にポップされます。
*   **`morestack`と`newstack`**: Goのスタックは必要に応じて自動的に拡張されます。関数呼び出し時にスタックが不足していると判断されると、`morestack`というアセンブリ関数が呼び出されます。`morestack`は、現在のgoroutineの情報を保存し、より大きなスタックセグメントを割り当てる`newstack`関数を呼び出します。`newstack`は新しいスタックセグメントをセットアップし、元の関数呼び出しを新しいスタック上で再開します。
*   **`gobuf`**: goroutineの実行コンテキスト（プログラムカウンタ`PC`、スタックポインタ`SP`など）を保存するための構造体です。スタック切り替え時に使用されます。
*   **`M` (Machine)**: OSのスレッドを表すランタイム構造体です。`M`は現在実行中の`G`（goroutine）や、スケジューリングに必要な情報などを保持します。
*   **`G` (Goroutine)**: Goの軽量スレッドを表すランタイム構造体です。スタック情報、状態、スケジューリング情報などを保持します。

### アセンブリ言語の役割

Goランタイムの低レベルな部分、特にスタック管理、goroutineの切り替え、システムコールなどは、C言語とアセンブリ言語で実装されています。アセンブリ言語は、特定のCPUアーキテクチャのレジスタやメモリを直接操作できるため、パフォーマンスが要求される処理や、C言語では実現が難しい低レベルな操作（例: スタックポインタの直接操作）に用いられます。このコミットでは、リフレクションによる関数呼び出しという特殊なケースで、通常の関数呼び出し規約とは異なるスタックフレームのセットアップが必要となるため、アセンブリ言語が使用されています。

### 型アライメントとパディング

コンピュータのメモリは、特定のバイト境界にデータを配置することで、CPUが効率的にアクセスできるように設計されています。これを「アライメント」と呼びます。例えば、32ビット整数は4バイト境界に、64ビット整数は8バイト境界に配置されるのが一般的です。

構造体や関数の引数をメモリに配置する際、アライメント要件を満たすために、データ間に未使用のバイト（パディング）が挿入されることがあります。このコミットでは、`reflect.FuncValue.Call`が引数と戻り値を動的にメモリに配置するため、各型のサイズとアライメントを正確に計算し、適切なパディングを考慮する必要があります。これは、特に異なるアーキテクチャ間で互換性のある動作を保証するために重要です。

## 技術的詳細

このコミットの核となるのは、`reflect.FuncValue.Call`メソッドが、Goのランタイムとアセンブリ言語の協調によって、どのように任意のGo関数を動的に呼び出すかという点です。

1.  **`reflect.FuncValue.Call`の実装**:
    *   **引数と戻り値の型チェック**: まず、呼び出される関数のシグネチャ（`t.NumIn()`, `t.NumOut()`, `t.In(i)`, `t.Out(i)`)と、`Call`に渡された引数`in`の数と型が一致するかを`typesMustMatch`で厳密にチェックします。
    *   **引数と戻り値のメモリレイアウト計算**: `Call`メソッドは、呼び出される関数の引数と戻り値がスタック上でどのように配置されるかをシミュレートします。各引数と戻り値の`Size()`と`Align()`を考慮し、適切なパディングを挿入しながら、必要なメモリサイズ`size`を計算します。この計算は、Goコンパイラ（6g/8g）の呼び出し規約に依存しており、非常に低レベルな知識が必要です。
    *   **引数フレームの準備**: 計算された`size`に基づいて、`make([]byte, size)`でバイトスライス`args`を割り当てます。これは、呼び出される関数に渡される引数と、関数が返す戻り値を格納するための一時的なメモリ領域（引数フレーム）として機能します。
    *   **入力引数のコピー**: `memmove`関数を使用して、`Call`に渡された`in []Value`の各要素（実際の引数値）を、`args`バイトスライス内の適切なオフセットにコピーします。この際も、各型の`Align()`と`Size()`に基づいてオフセットを計算し、パディングを考慮します。
    *   **ランタイム`call`関数の呼び出し**: 準備された引数フレーム`args`と、呼び出す関数のアドレス`v.addr`、そして引数フレームのサイズ`size`を引数として、`call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size))`を呼び出します。この`call`関数は、Goのソースコード上では`// implemented in ../pkg/runtime/*/asm.s`とコメントされており、実際には各アーキテクチャのアセンブリで実装されています。
    *   **戻り値のコピー**: `call`関数が実行を終え、制御が`reflect.FuncValue.Call`に戻ると、`args`バイトスライスには関数の戻り値が格納されています。`Call`メソッドは、`args`から戻り値を読み出し、`MakeZero`で新しい`reflect.Value`を作成し、`memmove`でデータをコピーして、`[]Value`として返します。

2.  **`reflect·call`アセンブリ関数の役割**:
    *   `reflect·call`は、`src/pkg/runtime/*/asm.s`に各アーキテクチャ（386, amd64, arm）向けに実装されています。
    *   このアセンブリ関数は、Goランタイムのスタック拡張メカニズムである`morestack`を模倣しています。通常の関数呼び出しとは異なり、リフレクションによる呼び出しでは、引数フレームがヒープ上に動的に割り当てられたバイトスライス（`args`）に存在するため、ランタイムがこれを認識し、適切にスタックをセットアップする必要があります。
    *   `reflect·call`は、現在のgoroutineの実行コンテキスト（`PC`, `SP`, `g`など）を`m->morebuf`に保存します。これは、`newstack`が新しいスタック上で関数を実行した後、元の呼び出し元に戻るために必要です。
    *   次に、呼び出す関数`fn`のアドレス、引数フレームのポインタ`arg`、引数フレームのサイズ`argsize`を、`m`構造体の`m->morepc`, `m->morefp`, `m->moreargs`フィールドに設定します。`m->moreframe`は0に設定され、標準サイズのスタックセグメントが割り当てられることを示します。
    *   最後に、`newstack`関数を呼び出します。`newstack`は、`m`構造体に設定された情報（`m->morepc`, `m->morefp`, `m->moreargs`）を使用して、新しいスタックセグメントを割り当て、その上で`fn`を`arg`を引数として実行します。

3.  **`runtime`パッケージの変更**:
    *   `src/pkg/runtime/runtime.h`では、`M`構造体に`void* morefp; // frame pointer for more stack`が追加されました。これは、リフレクション呼び出し時に引数フレームのポインタを保持するために使用されます。
    *   `Stktop`構造体にも`uint8* fp;`が追加されました。これは、スタック切り替え時に古いスタックフレームの引数開始位置を記録するために使用されます。
    *   `src/pkg/runtime/proc.c`の`newstack`関数と`oldstack`関数が、これらの新しい`morefp`および`fp`フィールドを利用するように修正されました。特に`newstack`では、`m->morefp`から引数を新しいスタックにコピーするロジックが追加されています。これにより、リフレクションによって呼び出される関数の引数が、正しく新しいスタックフレームに配置されることが保証されます。

4.  **チャネル送信の型チェック**:
    *   `src/pkg/reflect/value.go`の`ChanValue.send`メソッドに`typesMustMatch(t.Elem(), x.Type());`が追加されました。これにより、チャネルに送信される値の型が、チャネルの要素型と一致するかどうかが実行時にチェックされるようになり、型安全性が向上しました。

これらの変更は、Goのリフレクション機能の強力な拡張であり、Goプログラムがより動的で柔軟な操作を行えるようにするための重要な一歩です。

### `src/pkg/reflect/value.go` の `FuncValue.Call` メソッド

```go
// Call calls the function v with input parameters in.
// It returns the function's output parameters as Values.
func (v *FuncValue) Call(in []Value) []Value {
	var structAlign = Typeof((*tiny)(nil)).(*PtrType).Elem().Size();

	t := v.Type().(*FuncType);
	if len(in) != t.NumIn() {
		panic("FuncValue: wrong argument count");
	}
	nout := t.NumOut();

	// Compute arg size & allocate.
	// This computation is 6g/8g-dependent
	// and probably wrong for gccgo, but so
	// is most of this function.
	size := uintptr(0);
	for i, v := range in {
		tv := v.Type();
		typesMustMatch(t.In(i), tv);
		a := uintptr(tv.Align());
		size = (size + a - 1) &^ (a - 1);
		size += tv.Size();
	}
	size = (size + structAlign - 1) &^ (structAlign - 1);
	for i := 0; i < nout; i++ {
		tv := t.Out(i);
		a := uintptr(tv.Align());
		size = (size + a - 1) &^ (a - 1);
		size += tv.Size();
	}
	
	// size must be > 0 in order for &args[0] to be valid.
	// the argument copying is going to round it up to
	// a multiple of 8 anyway, so make it 8 to begin with.
	if size < 8 {
		size = 8;
	}
	args := make([]byte, size);
	ptr := uintptr(unsafe.Pointer(&args[0]));

	// Copy into args.
	// ... (省略) ...
	off := uintptr(0);
	for i, v := range in {
		tv := v.Type();
		a := uintptr(tv.Align());
		off = (off + a - 1) &^ (a - 1);
		n := tv.Size();
		memmove(addr(ptr+off), v.getAddr(), n);
		off += n;
	}
	off = (off + structAlign - 1) &^ (structAlign - 1);

	// Call
	call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size));

	// Copy return values out of args.
	// ... (省略) ...
	ret := make([]Value, nout);
	for i := 0; i < nout; i++ {
		tv := t.Out(i);
		a := uintptr(tv.Align());
		off = (off + a - 1) &^ (a - 1);
		v := MakeZero(tv);
		n := tv.Size();
		memmove(v.getAddr(), addr(ptr+off), n);
		ret[i] = v;
		off += n;
	}
	return ret;
}
```

### `src/pkg/runtime/amd64/asm.s` の `reflect·call` 関数 (amd64版の例)

```assembly
// Called from reflection library.  Mimics morestack,
// reuses stack growth code to create a frame
// with the desired args running the desired function.
//
// func call(fn *byte, arg *byte, argsize uint32).
TEXT reflect·call(SB), 7, $0
	// Save our caller's state as the PC and SP to
	// restore when returning from f.
	MOVQ	0(SP), AX	// our caller's PC
	MOVQ	AX, (m_morebuf+gobuf_pc)(m)
	LEAQ	8(SP), AX	// our caller's SP
	MOVQ	AX, (m_morebuf+gobuf_sp)(m)
	MOVQ	g, (m_morebuf+gobuf_g)(m)

	// Set up morestack arguments to call f on a new stack.
	// We set f's frame size to zero, meaning
	// allocate a standard sized stack segment.
	// If it turns out that f needs a larger frame than this,
	// f's usual stack growth prolog will allocate
	// a new segment (and recopy the arguments).
	MOVQ	8(SP), AX	// fn
	MOVQ	16(SP), BX	// arg frame
	MOVL	24(SP), CX	// arg size

	MOVQ	AX, m_morepc(m)	// f's PC
	MOVQ	BX, m_morefp(m)	// argument frame pointer
	MOVL	CX, m_moreargs(m)	// f's argument size
	MOVL	$0, m_moreframe(m)	// f's frame size

	// Call newstack on m's scheduling stack.
	MOVQ	m_g0(m), g
	MOVQ	(m_sched+gobuf_sp)(m), SP
	CALL	newstack(SB)
	MOVQ	$0, 0x1103	// crash if newstack returns
	RET
```

## コアとなるコードの解説

### `reflect.FuncValue.Call` メソッド

このメソッドは、Goのリフレクションにおける関数呼び出しのフロントエンドです。

1.  **引数と戻り値のメモリレイアウト計算**: `size`変数の計算ループがその核心です。Goの関数呼び出し規約では、引数と戻り値はスタック上に特定の順序とアライメントで配置されます。`reflect`パッケージは、この規約をエミュレートし、各引数と戻り値の型情報（`tv.Align()`, `tv.Size()`）に基づいて、必要なメモリサイズとオフセットを動的に計算します。`size = (size + a - 1) &^ (a - 1);`というイディオムは、`size`を`a`の倍数に切り上げる（アライメントを調整する）ための一般的なビット演算です。
2.  **`args`バイトスライスの利用**: `args := make([]byte, size)`で作成されるバイトスライスは、呼び出される関数の引数と戻り値が一時的に格納される「引数フレーム」として機能します。これは、通常の関数呼び出しでスタック上に直接配置される引数/戻り値の領域を、ヒープ上に模倣したものです。
3.  **`memmove`によるデータコピー**: `memmove`は、メモリブロックをコピーするための低レベルな関数です。入力引数は`in []Value`から`args`バイトスライスへ、関数実行後の戻り値は`args`バイトスライスから`ret []Value`へと、この`memmove`を使ってコピーされます。これにより、Goの型システムを迂回して、生のバイトデータを効率的に移動させます。
4.  **`call`アセンブリ関数の呼び出し**: `call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size))`が、実際の関数実行をランタイムに委ねる部分です。`v.addr`は呼び出す関数のエントリポイント、`ptr`は`args`バイトスライスの先頭アドレス（引数フレーム）、`size`はそのサイズです。この呼び出しにより、Goの実行フローはGoコードからアセンブリコードへと遷移します。

### `reflect·call` アセンブリ関数

このアセンブリ関数は、Goランタイムのスタック管理メカニズムを再利用して、リフレクションによる関数呼び出しを実現します。

1.  **呼び出し元の状態保存**: `MOVQ 0(SP), AX`などで、`reflect.FuncValue.Call`の呼び出し元のプログラムカウンタ（`PC`）とスタックポインタ（`SP`）をレジスタにロードし、`m->morebuf`構造体に保存します。これは、`reflect·call`が`newstack`を呼び出した後、最終的に`reflect.FuncValue.Call`に戻るための情報です。
2.  **`m`構造体の設定**: `MOVQ AX, m_morepc(m)`などで、呼び出す関数`fn`のアドレスを`m->morepc`に、引数フレームのポインタ`arg`を`m->morefp`に、引数フレームのサイズ`argsize`を`m->moreargs`に設定します。これらのフィールドは、`newstack`関数が新しいスタックフレームを構築する際に参照する情報です。`m_moreframe`を`$0`に設定することで、`newstack`に標準サイズのスタックセグメントを割り当てるように指示します。
3.  **`newstack`の呼び出し**: `CALL newstack(SB)`により、Goランタイムのスタック拡張/切り替えメカニズムがトリガーされます。`newstack`は、`m`構造体に設定された情報に基づいて、新しいスタックセグメントを割り当て、その上で`m->morepc`（つまり、リフレクションで呼び出される関数）を実行します。この際、`m->morefp`が指す引数フレームの内容が、新しいスタックフレームにコピーされ、関数が期待する引数として利用可能になります。

この一連のプロセスにより、Goの型システムとスタック管理の低レベルな詳細を抽象化しつつ、任意のGo関数を動的に呼び出すという強力なリフレクション機能が実現されています。

## 変更の背景

このコミットの主な背景は、Go言語の`reflect`パッケージに、関数を動的に呼び出す機能（関数リフレクション）を導入することです。Goの初期段階では、リフレクションは主に型情報の取得や構造体フィールドへのアクセスに限定されており、関数そのものを動的に呼び出す機能は未実装でした。

`reflect.FuncValue.Call`メソッドは、インターフェース{}の値から取得した関数を、実行時に与えられた引数で呼び出し、その結果を`[]reflect.Value`として返すことを可能にします。この機能は、以下のような高度なプログラミングパターンを実現するために不可欠です。

*   **汎用的なRPCフレームワークやWebフレームワーク:** ユーザーが定義した関数を、そのシグネチャを知らなくても動的に呼び出すことができます。
*   **テストフレームワーク:** テスト関数を動的に発見し、実行することができます。
*   **コマンドラインパーサー:** コマンド名と引数に基づいて、対応する関数を呼び出すことができます。
*   **データバインディングやORM:** データベースから取得したデータを行構造体やオブジェクトにマッピングする際に、セッターメソッドを動的に呼び出すことができます。

この機能の実装は、Goの型システムとランタイムのスタック管理の深い理解を必要とし、特に異なるアーキテクチャ（386, amd64, arm）でのアセンブリレベルの操作が伴うため、複雑な作業となります。また、チャネルの型チェックの追加や型不一致メッセージの改善は、リフレクションの堅牢性を高め、開発者がより安全にリフレクションを使用できるようにするための付随的な改善です。

## 前提知識の解説

### Goの`reflect`パッケージ

`reflect`パッケージは、Goプログラムが実行時に自身の構造を検査（リフレクト）することを可能にする機能を提供します。これにより、型情報（`reflect.Type`）や値情報（`reflect.Value`）を動的に取得・操作できます。

*   **`reflect.Type`**: Goの型に関する情報（名前、サイズ、メソッドなど）を表現します。`reflect.TypeOf(i interface{})`で取得できます。
*   **`reflect.Value`**: Goの値に関する情報（実際のデータ、設定可能性など）を表現します。`reflect.ValueOf(i interface{})`で取得できます。
*   **`reflect.Kind`**: 型の基本的なカテゴリ（`Int`, `String`, `Struct`, `Func`, `Chan`など）を示します。
*   **`reflect.FuncValue`**: `reflect.Value`の一種で、関数を表します。このコミットで`Call`メソッドが実装されました。

リフレクションは強力ですが、型安全性を損なう可能性があり、パフォーマンスオーバーヘッドも伴うため、必要な場合にのみ慎重に使用すべきです。

### Goのランタイムとスタック管理

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、スケジューラ、メモリ管理、ガベージコレクション、そしてスタック管理が含まれます。

*   **Goroutineスタック**: Goの各goroutineは、動的にサイズが変更されるスタックを持っています。関数呼び出しごとにスタックフレームがプッシュされ、関数からのリターン時にポップされます。
*   **`morestack`と`newstack`**: Goのスタックは必要に応じて自動的に拡張されます。関数呼び出し時にスタックが不足していると判断されると、`morestack`というアセンブリ関数が呼び出されます。`morestack`は、現在のgoroutineの情報を保存し、より大きなスタックセグメントを割り当てる`newstack`関数を呼び出します。`newstack`は新しいスタックセグメントをセットアップし、元の関数呼び出しを新しいスタック上で再開します。
*   **`gobuf`**: goroutineの実行コンテキスト（プログラムカウンタ`PC`、スタックポインタ`SP`など）を保存するための構造体です。スタック切り替え時に使用されます。
*   **`M` (Machine)**: OSのスレッドを表すランタイム構造体です。`M`は現在実行中の`G`（goroutine）や、スケジューリングに必要な情報などを保持します。
*   **`G` (Goroutine)**: Goの軽量スレッドを表すランタイム構造体です。スタック情報、状態、スケジューリング情報などを保持します。

### アセンブリ言語の役割

Goランタイムの低レベルな部分、特にスタック管理、goroutineの切り替え、システムコールなどは、C言語とアセンブリ言語で実装されています。アセンブリ言語は、特定のCPUアーキテクチャのレジスタやメモリを直接操作できるため、パフォーマンスが要求される処理や、C言語では実現が難しい低レベルな操作（例: スタックポインタの直接操作）に用いられます。このコミットでは、リフレクションによる関数呼び出しという特殊なケースで、通常の関数呼び出し規約とは異なるスタックフレームのセットアップが必要となるため、アセンブリ言語が使用されています。

### 型アライメントとパディング

コンピュータのメモリは、特定のバイト境界にデータを配置することで、CPUが効率的にアクセスできるように設計されています。これを「アライメント」と呼びます。例えば、32ビット整数は4バイト境界に、64ビット整数は8バイト境界に配置されるのが一般的です。

構造体や関数の引数をメモリに配置する際、アライメント要件を満たすために、データ間に未使用のバイト（パディング）が挿入されることがあります。このコミットでは、`reflect.FuncValue.Call`が引数と戻り値を動的にメモリに配置するため、各型のサイズとアライメントを正確に計算し、適切なパディングを考慮する必要があります。これは、特に異なるアーキテクチャ間で互換性のある動作を保証するために重要です。

## 技術的詳細

このコミットの核となるのは、`reflect.FuncValue.Call`メソッドが、Goのランタイムとアセンブリ言語の協調によって、どのように任意のGo関数を動的に呼び出すかという点です。

1.  **`reflect.FuncValue.Call`の実装**:
    *   **引数と戻り値の型チェック**: まず、呼び出される関数のシグネチャ（`t.NumIn()`, `t.NumOut()`, `t.In(i)`, `t.Out(i)`)と、`Call`に渡された引数`in`の数と型が一致するかを`typesMustMatch`で厳密にチェックします。
    *   **引数と戻り値のメモリレイアウト計算**: `Call`メソッドは、呼び出される関数の引数と戻り値がスタック上でどのように配置されるかをシミュレートします。各引数と戻り値の`Size()`と`Align()`を考慮し、適切なパディングを挿入しながら、必要なメモリサイズ`size`を計算します。この計算は、Goコンパイラ（6g/8g）の呼び出し規約に依存しており、非常に低レベルな知識が必要です。
    *   **引数フレームの準備**: 計算された`size`に基づいて、`make([]byte, size)`でバイトスライス`args`を割り当てます。これは、呼び出される関数に渡される引数と、関数が返す戻り値を格納するための一時的なメモリ領域（引数フレーム）として機能します。
    *   **入力引数のコピー**: `memmove`関数を使用して、`Call`に渡された`in []Value`の各要素（実際の引数値）を、`args`バイトスライス内の適切なオフセットにコピーします。この際も、各型の`Align()`と`Size()`に基づいてオフセットを計算し、パディングを考慮します。
    *   **ランタイム`call`関数の呼び出し**: 準備された引数フレーム`args`と、呼び出す関数のアドレス`v.addr`、そして引数フレームのサイズ`size`を引数として、`call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size))`を呼び出します。この`call`関数は、Goのソースコード上では`// implemented in ../pkg/runtime/*/asm.s`とコメントされており、実際には各アーキテクチャのアセンブリで実装されています。
    *   **戻り値のコピー**: `call`関数が実行を終え、制御が`reflect.FuncValue.Call`に戻ると、`args`バイトスライスには関数の戻り値が格納されています。`Call`メソッドは、`args`から戻り値を読み出し、`MakeZero`で新しい`reflect.Value`を作成し、`memmove`でデータをコピーして、`[]Value`として返します。

2.  **`reflect·call`アセンブリ関数の役割**:
    *   `reflect·call`は、`src/pkg/runtime/*/asm.s`に各アーキテクチャ（386, amd64, arm）向けに実装されています。
    *   このアセンブリ関数は、Goランタイムのスタック拡張メカニズムである`morestack`を模倣しています。通常の関数呼び出しとは異なり、リフレクションによる呼び出しでは、引数フレームがヒープ上に動的に割り当てられたバイトスライス（`args`）に存在するため、ランタイムがこれを認識し、適切にスタックをセットアップする必要があります。
    *   `reflect·call`は、現在のgoroutineの実行コンテキスト（`PC`, `SP`, `g`など）を`m->morebuf`に保存します。これは、`newstack`が新しいスタック上で関数を実行した後、元の呼び出し元に戻るために必要です。
    *   次に、呼び出す関数`fn`のアドレス、引数フレームのポインタ`arg`、引数フレームのサイズ`argsize`を、`m`構造体の`m->morepc`, `m->morefp`, `m->moreargs`フィールドに設定します。`m->moreframe`は0に設定され、標準サイズのスタックセグメントが割り当てられることを示します。
    *   最後に、`newstack`関数を呼び出します。`newstack`は、`m`構造体に設定された情報（`m->morepc`, `m->morefp`, `m->moreargs`）を使用して、新しいスタックセグメントを割り当て、その上で`fn`を`arg`を引数として実行します。

3.  **`runtime`パッケージの変更**:
    *   `src/pkg/runtime/runtime.h`では、`M`構造体に`void* morefp; // frame pointer for more stack`が追加されました。これは、リフレクション呼び出し時に引数フレームのポインタを保持するために使用されます。
    *   `Stktop`構造体にも`uint8* fp;`が追加されました。これは、スタック切り替え時に古いスタックフレームの引数開始位置を記録するために使用されます。
    *   `src/pkg/runtime/proc.c`の`newstack`関数と`oldstack`関数が、これらの新しい`morefp`および`fp`フィールドを利用するように修正されました。特に`newstack`では、`m->morefp`から引数を新しいスタックにコピーするロジックが追加されています。これにより、リフレクションによって呼び出される関数の引数が、正しく新しいスタックフレームに配置されることが保証されます。

4.  **チャネル送信の型チェック**:
    *   `src/pkg/reflect/value.go`の`ChanValue.send`メソッドに`typesMustMatch(t.Elem(), x.Type());`が追加されました。これにより、チャネルに送信される値の型が、チャネルの要素型と一致するかどうかが実行時にチェックされるようになり、型安全性が向上しました。

これらの変更は、Goのリフレクション機能の強力な拡張であり、Goプログラムがより動的で柔軟な操作を行えるようにするための重要な一歩です。

### `src/pkg/reflect/value.go` の `FuncValue.Call` メソッド

```go
// Call calls the function v with input parameters in.
// It returns the function's output parameters as Values.
func (v *FuncValue) Call(in []Value) []Value {
	var structAlign = Typeof((*tiny)(nil)).(*PtrType).Elem().Size();

	t := v.Type().(*FuncType);
	if len(in) != t.NumIn() {
		panic("FuncValue: wrong argument count");
	}
	nout := t.NumOut();

	// Compute arg size & allocate.
	// This computation is 6g/8g-dependent
	// and probably wrong for gccgo, but so
	// is most of this function.
	size := uintptr(0);
	for i, v := range in {
		tv := v.Type();
		typesMustMatch(t.In(i), tv);
		a := uintptr(tv.Align());
		size = (size + a - 1) &^ (a - 1);
		size += tv.Size();
	}
	size = (size + structAlign - 1) &^ (structAlign - 1);
	for i := 0; i < nout; i++ {
		tv := t.Out(i);
		a := uintptr(tv.Align());
		size = (size + a - 1) &^ (a - 1);
		size += tv.Size();
	}
	
	// size must be > 0 in order for &args[0] to be valid.
	// the argument copying is going to round it up to
	// a multiple of 8 anyway, so make it 8 to begin with.
	if size < 8 {
		size = 8;
	}
	args := make([]byte, size);
	ptr := uintptr(unsafe.Pointer(&args[0]));

	// Copy into args.
	// ... (省略) ...
	off := uintptr(0);
	for i, v := range in {
		tv := v.Type();
		a := uintptr(tv.Align());
		off = (off + a - 1) &^ (a - 1);
		n := tv.Size();
		memmove(addr(ptr+off), v.getAddr(), n);
		off += n;
	}
	off = (off + structAlign - 1) &^ (structAlign - 1);

	// Call
	call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size));

	// Copy return values out of args.
	// ... (省略) ...
	ret := make([]Value, nout);
	for i := 0; i < nout; i++ {
		tv := t.Out(i);
		a := uintptr(tv.Align());
		off = (off + a - 1) &^ (a - 1);
		v := MakeZero(tv);
		n := tv.Size();
		memmove(v.getAddr(), addr(ptr+off), n);
		ret[i] = v;
		off += n;
	}
	return ret;
}
```

### `src/pkg/runtime/amd64/asm.s` の `reflect·call` 関数 (amd64版の例)

```assembly
// Called from reflection library.  Mimics morestack,
// reuses stack growth code to create a frame
// with the desired args running the desired function.
//
// func call(fn *byte, arg *byte, argsize uint32).
TEXT reflect·call(SB), 7, $0
	// Save our caller's state as the PC and SP to
	// restore when returning from f.
	MOVQ	0(SP), AX	// our caller's PC
	MOVQ	AX, (m_morebuf+gobuf_pc)(m)
	LEAQ	8(SP), AX	// our caller's SP
	MOVQ	AX, (m_morebuf+gobuf_sp)(m)
	MOVQ	g, (m_morebuf+gobuf_g)(m)

	// Set up morestack arguments to call f on a new stack.
	// We set f's frame size to zero, meaning
	// allocate a standard sized stack segment.
	// If it turns out that f needs a larger frame than this,
	// f's usual stack growth prolog will allocate
	// a new segment (and recopy the arguments).
	MOVQ	8(SP), AX	// fn
	MOVQ	16(SP), BX	// arg frame
	MOVL	24(SP), CX	// arg size

	MOVQ	AX, m_morepc(m)	// f's PC
	MOVQ	BX, m_morefp(m)	// argument frame pointer
	MOVL	CX, m_moreargs(m)	// f's argument size
	MOVL	$0, m_moreframe(m)	// f's frame size

	// Call newstack on m's scheduling stack.
	MOVQ	m_g0(m), g
	MOVQ	(m_sched+gobuf_sp)(m), SP
	CALL	newstack(SB)
	MOVQ	$0, 0x1103	// crash if newstack returns
	RET
```

## コアとなるコードの解説

### `reflect.FuncValue.Call` メソッド

このメソッドは、Goのリフレクションにおける関数呼び出しのフロントエンドです。

1.  **引数と戻り値のメモリレイアウト計算**: `size`変数の計算ループがその核心です。Goの関数呼び出し規約では、引数と戻り値はスタック上に特定の順序とアライメントで配置されます。`reflect`パッケージは、この規約をエミュレートし、各引数と戻り値の型情報（`tv.Align()`, `tv.Size()`）に基づいて、必要なメモリサイズとオフセットを動的に計算します。`size = (size + a - 1) &^ (a - 1);`というイディオムは、`size`を`a`の倍数に切り上げる（アライメントを調整する）ための一般的なビット演算です。
2.  **`args`バイトスライスの利用**: `args := make([]byte, size)`で作成されるバイトスライスは、呼び出される関数の引数と戻り値が一時的に格納される「引数フレーム」として機能します。これは、通常の関数呼び出しでスタック上に直接配置される引数/戻り値の領域を、ヒープ上に模倣したものです。
3.  **`memmove`によるデータコピー**: `memmove`は、メモリブロックをコピーするための低レベルな関数です。入力引数は`in []Value`から`args`バイトスライスへ、関数実行後の戻り値は`args`バイトスライスから`ret []Value`へと、この`memmove`を使ってコピーされます。これにより、Goの型システムを迂回して、生のバイトデータを効率的に移動させます。
4.  **`call`アセンブリ関数の呼び出し**: `call(*(**byte)(v.addr), (*byte)(addr(ptr)), uint32(size))`が、実際の関数実行をランタイムに委ねる部分です。`v.addr`は呼び出す関数のエントリポイント、`ptr`は`args`バイトスライスの先頭アドレス（引数フレーム）、`size`はそのサイズです。この呼び出しにより、Goの実行フローはGoコードからアセンブリコードへと遷移します。

### `reflect·call` アセンブリ関数

このアセンブリ関数は、Goランタイムのスタック管理メカニズムを再利用して、リフレクションによる関数呼び出しを実現します。

1.  **呼び出し元の状態保存**: `MOVQ 0(SP), AX`などで、`reflect.FuncValue.Call`の呼び出し元のプログラムカウンタ（`PC`）とスタックポインタ（`SP`）をレジスタにロードし、`m->morebuf`構造体に保存します。これは、`reflect·call`が`newstack`を呼び出した後、最終的に`reflect.FuncValue.Call`に戻るための情報です。
2.  **`m`構造体の設定**: `MOVQ AX, m_morepc(m)`などで、呼び出す関数`fn`のアドレスを`m->morepc`に、引数フレームのポインタ`arg`を`m->morefp`に、引数フレームのサイズ`argsize`を`m->moreargs`に設定します。これらのフィールドは、`newstack`関数が新しいスタックフレームを構築する際に参照する情報です。`m_moreframe`を`$0`に設定することで、`newstack`に標準サイズのスタックセグメントを割り当てるように指示します。
3.  **`newstack`の呼び出し**: `CALL newstack(SB)`により、Goランタイムのスタック拡張/切り替えメカニズムがトリガーされます。`newstack`は、`m`構造体に設定された情報に基づいて、新しいスタックセグメントを割り当て、その上で`m->morepc`（つまり、リフレクションで呼び出される関数）を実行します。この際、`m->morefp`が指す引数フレームの内容が、新しいスタックフレームにコピーされ、関数が期待する引数として利用可能になります。

この一連のプロセスにより、Goの型システムとスタック管理の低レベルな詳細を抽象化しつつ、任意のGo関数を動的に呼び出すという強力なリフレクション機能が実現されています。

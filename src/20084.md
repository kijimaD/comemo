# [インデックス 20084] ファイルの概要

このコミットは、Go言語のランタイムテストスイートの一部である `test/nosplit.go` ファイルに、PowerPC 64-bit (power64およびpower64le) アーキテクチャのサポートを追加するものです。これにより、Goランタイムの低レベルなスタック管理機能、特に `//go:nosplit` ディレクティブが適用された関数が、Power64環境で正しく動作することを検証するための基盤が強化されます。具体的には、アーキテクチャ固有のポインタサイズとアセンブリマクロの定義が追加され、テストの汎用性が向上しています。

## 変更の背景

Go言語は、様々なアーキテクチャ上での動作をサポートすることを目指しています。PowerPC 64-bit (power64) は、サーバーや高性能コンピューティングで利用される重要なアーキテクチャの一つです。Goランタイムは、ガベージコレクションやスケジューリングなど、低レベルでOSやハードウェアと密接に連携する部分が多く、これらの機能が各アーキテクチャで正しく、かつ効率的に動作することが不可欠です。

`//go:nosplit` ディレクティブは、Goランタイムの非常にクリティカルな部分で使用され、スタックの自動拡張（スタック分割）を無効にします。これは、スタックの成長が予期せぬ中断を引き起こす可能性がある、時間的制約の厳しい操作や、アトミックな操作中にゴルーチンがプリエンプトされることを防ぐために重要です。

このコミットの目的は、`test/nosplit.go` というテストファイルにPower64アーキテクチャのサポートを追加することで、Power64環境においても `//go:nosplit` が適用された関数が期待通りに動作し、スタック管理や関数呼び出しの挙動が正確であることを検証することにあります。これにより、GoランタイムのPower64上での安定性と信頼性が確保されます。

## 前提知識の解説

### Goの`//go:nosplit`ディレクティブ

`//go:nosplit` はGoコンパイラに対する特殊なディレクティブ（指示子）です。このディレクティブが関数に付与されると、その関数が呼び出された際に通常行われるスタックオーバーフローチェックが省略されます。Goのゴルーチンは、必要に応じてスタックを自動的に拡張する「スタック分割」というメカニズムを持っていますが、`//go:nosplit` はこのメカニズムを無効にします。

これは主にGoランタイムの非常に低レベルなコードで使用されます。例えば、ガベージコレクタが実行中であったり、スケジューラがゴルーチンのコンテキストを切り替えている最中など、スタックの拡張やゴルーチンのプリエンプション（一時停止）が不適切または危険な状況で利用されます。誤った使用はスタックオーバーフローやメモリ破損を引き起こす可能性があるため、一般的なアプリケーション開発で利用されることはありません。`test/nosplit.go` は、この `nosplit` の挙動が各アーキテクチャで正しく機能するかを検証するためのテストです。

### PowerPC 64-bit (Power64/ppc64/ppc64le) アーキテクチャ

PowerPCは、IBMが開発したRISC（Reduced Instruction Set Computer）ベースのマイクロプロセッサアーキテクチャです。Power64は、その64ビット版を指し、特にサーバー、スーパーコンピュータ、組み込みシステムなどで広く利用されています。Go言語は、`ppc64`（ビッグエンディアン）と `ppc64le`（リトルエンディアン）の両方のバリアントに対して堅牢なサポートを提供しています。64ビットアーキテクチャであるため、ポインタサイズは8バイトです。

### ポインタサイズ

コンピュータのアーキテクチャにおいて、ポインタ（メモリのアドレスを指す変数）のサイズは、そのアーキテクチャのワードサイズに依存します。64ビットアーキテクチャでは、メモリのアドレスを表現するために64ビット（8バイト）が必要となるため、ポインタのサイズは8バイトとなります。これは、32ビットアーキテクチャのポインタサイズが4バイトであるのと対照的です。

### Goの呼び出し規約

呼び出し規約（Calling Convention）とは、関数が呼び出される際に、引数をどのように渡し、戻り値をどのように受け取り、レジスタをどのように使用するかといった、関数呼び出しに関する一連のルールです。Goランタイムは、パフォーマンスを最適化するために、アーキテクチャごとに異なる、あるいは進化する呼び出し規約を採用しています。近年では、スタックベースの呼び出し規約からレジスタベースの呼び出し規約への移行が進んでおり、これにより関数呼び出しのオーバーヘッドが削減され、全体的なパフォーマンスが向上しています。

### アセンブリ言語の基本

*   **`BL` (Branch with Link)**: PowerPCアーキテクチャにおける関数呼び出し命令の一つです。この命令は、指定されたアドレスに分岐すると同時に、現在のプログラムカウンタ（次の命令のアドレス）をリンクレジスタ（LR）に保存します。これにより、関数が終了した後に呼び出し元に戻ることができます。
*   **`R0` (Register 0)**: PowerPCプロセッサの汎用レジスタの一つです。アセンブリコードでは、特定の目的のためにレジスタが使用されます。
*   **`RETURN`**: これは通常、アセンブリ言語における関数からの戻り命令（例: `blr` on PowerPC）を抽象化したマクロまたは概念を指します。関数が実行を終え、呼び出し元に制御を戻すために使用されます。

## 技術的詳細

このコミットは、`test/nosplit.go` ファイル内のアーキテクチャ固有のコード生成ロジックを拡張し、PowerPC 64-bit (power64およびpower64le) のサポートを導入しています。

`test/nosplit.go` は、Goの `//go:nosplit` ディレクティブが正しく機能するかを検証するためのテストです。このテストは、Goのソースコードからアセンブリコードを生成し、そのアセンブリコードが特定の条件下でスタック分割を行わないことを確認します。そのため、各アーキテクチャの呼び出し規約やレジスタ使用法に合わせたアセンブリマクロを定義する必要があります。

変更の核心は、`goarch`（Goのターゲットアーキテクチャ）に基づいて、ポインタサイズ (`ptrSize`) を設定し、アセンブリコード生成用のマクロを定義する `switch` ステートメントの導入です。

1.  **`ptrSize` の設定**:
    *   `power64` および `power64le` アーキテクチャの場合、`ptrSize` は `8` に設定されます。これは、64ビットアーキテクチャにおけるポインタの標準的なサイズ（8バイト）に合致します。
    *   `amd64` アーキテクチャの場合も、同様に `ptrSize` は `8` に設定されます。
    *   `arm` アーキテクチャの場合、`ptrSize` はデフォルトの `4` のままです（32ビットアーキテクチャのため）。

2.  **アセンブリマクロの定義**:
    *   `power64` および `power64le` の場合、以下のマクロが定義されます。
        *   `#define CALL BL`: 関数呼び出しにPowerPCの `BL` (Branch with Link) 命令を使用することを示します。
        *   `#define REGISTER (R0)`: 汎用レジスタ `R0` を使用することを示します。
        *   `#define RET RETURN`: 関数からの戻りに `RETURN` マクロを使用することを示します。
    *   これらのマクロは、テストが生成するアセンブリコードがPowerPCの呼び出し規約とレジスタ使用法に準拠するようにするために不可欠です。

3.  **汎用的なアライメントチェック**:
    *   以前は `if goarch == "amd64" && size%8 == 4` という条件で `amd64` に特化したアライメントチェックが行われていました。
    *   このコミットにより、条件が `if size%ptrSize == 4` に変更されました。これにより、チェックが特定のアーキテクチャ（`amd64`）に限定されず、現在のアーキテクチャの `ptrSize` に基づいて汎用的に行われるようになります。これは、異なるアーキテクチャでスタックアライメントやデータサイズに関する特定の条件をテストする際に、より正確で柔軟な検証を可能にします。

これらの変更により、`test/nosplit.go` はPower64アーキテクチャ上でも、Goランタイムの低レベルなスタック管理と関数呼び出しの挙動を正確にテストできるようになります。

## コアとなるコードの解説

### `switch goarch` ブロックの追加

このコミットの主要な変更点は、`goarch`（Goのターゲットアーキテクチャ）に基づいて、ポインタサイズ (`ptrSize`) とアセンブリマクロを動的に設定するための `switch` ステートメントが導入されたことです。

*   **`ptrSize := 4`**: まず、`ptrSize` がデフォルトで4バイトに初期化されます。これは32ビットアーキテクチャのポインタサイズに対応します。
*   **`case "power64", "power64le":`**:
    *   `ptrSize = 8`: PowerPC 64-bitアーキテクチャ（ビッグエンディアンの `power64` とリトルエンディアンの `power64le`）の場合、ポインタサイズが8バイトに設定されます。これは64ビットシステムでの標準的なポインタサイズです。
    *   `fmt.Fprintf(&buf, "#define CALL BL\\n#define REGISTER (R0)\\n#define RET RETURN\\n")`: PowerPCの呼び出し規約に合わせたアセンブリマクロが定義されます。
        *   `CALL BL`: 関数呼び出しにはPowerPCの「Branch with Link」命令 (`BL`) を使用します。
        *   `REGISTER (R0)`: 汎用レジスタ `R0` を使用します。
        *   `RET RETURN`: 関数からの戻りには `RETURN` マクロを使用します。
    これらのマクロは、`test/nosplit.go` が生成するアセンブリコードがPowerPC上で正しくコンパイルされ、実行されるために必要です。
*   **`case "arm":`**:
    *   `fmt.Fprintf(&buf, "#define CALL BL\\n#define REGISTER (R0)\\n")`: ARMアーキテクチャの場合、以前の `if` 文と同じマクロが定義されます。`ptrSize` はデフォルトの4のままです。
*   **`case "amd64":`**:
    *   `ptrSize = 8`: AMD64アーキテクチャの場合、ポインタサイズが8バイトに設定されます。
    *   `fmt.Fprintf(&buf, "#define REGISTER AX\\n")`: AMD64の呼び出し規約に合わせたマクロが定義されます。

この `switch` 文の導入により、コードがより構造化され、将来的に新しいアーキテクチャを追加する際の拡張性が向上しています。

### `if size%ptrSize == 4` への変更

以前のコードでは、`if goarch == "amd64" && size%8 == 4` という条件で、`amd64` アーキテクチャに特化したアライメントチェックが行われていました。

このコミットでは、この条件が `if size%ptrSize == 4` に変更されました。

*   **汎用化**: この変更により、アライメントチェックが特定のアーキテクチャ（`amd64`）に限定されず、現在のアーキテクチャの `ptrSize` に依存するようになりました。
*   **正確性の向上**: 例えば、Power64のような他の64ビットアーキテクチャでも、そのポインタサイズ（8バイト）に基づいて同様のアライメント条件をテストできるようになります。これは、異なるアーキテクチャでスタックアライメントやデータサイズに関する特定の条件をテストする際に、より正確で柔軟な検証を可能にします。

これらの変更は、Goランタイムのクロスプラットフォーム対応を強化し、特に低レベルなスタック管理と関数呼び出しの挙動が、様々なアーキテクチャで一貫して正しく機能することを保証するために重要です。

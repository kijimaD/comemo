# [インデックス 23952] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTPリクエストボディの読み込みに関するパフォーマンスとリソース消費の問題を解決するためのものです。具体的には、ハンドラがリクエストボディを完全に読み込まなかった場合でも、`req.Body.Close()`が呼び出された際に、接続の再利用のために残りのボディをすべて読み込もうとする挙動を改善します。これにより、特に巨大なリクエストボディが送信された場合に、不必要なデータ読み込みによるリソースの浪費を防ぎます。

## 変更の背景

この変更の背景には、HTTP/1.1におけるTCPコネクションの再利用の仕組みと、Goの`net/http`パッケージにおけるリクエストボディの処理方法があります。

HTTP/1.1では、パフォーマンス向上のためにKeep-Aliveメカニズムが導入され、一つのTCPコネクション上で複数のHTTPリクエスト/レスポンスをやり取りすることが可能になりました。これにより、コネクションの確立・切断にかかるオーバーヘッドを削減できます。

Goの`net/http`サーバーは、このコネクション再利用を積極的に行います。コネクションを再利用するためには、現在のリクエストのデータが完全に読み込まれ、次のリクエストの開始位置が明確になっている必要があります。特に、リクエストボディが残っている場合、その残りを読み飛ばす必要があります。

しかし、以前の実装では、ハンドラが`req.Body`を完全に読み込まなかった場合（例えば、必要なヘッダだけを処理してボディの残りを無視する場合など）、`req.Body.Close()`が暗黙的または明示的に呼び出された際に、コネクションを再利用するために残りのリクエストボディ全体を読み込もうとしていました。

この挙動は、特にクライアントが非常に大きなリクエストボディ（例: 数GBのファイルアップロード）を送信し、サーバー側がそのボディの一部しか必要としない、あるいは全く必要としない場合に問題となります。サーバーは、不要な大量のデータを読み込むためにCPU時間、メモリ、ネットワーク帯域を消費し、サービス拒否（DoS）攻撃のリスクを高める可能性がありました。

このコミットは、この「不要な大量のデータ読み込み」を制限し、リソースの浪費を防ぐことを目的としています。

## 前提知識の解説

### HTTPリクエストボディと`Content-Length` / `Transfer-Encoding: chunked`

HTTPリクエストには、リクエストボディが含まれることがあります（例: POSTリクエストのデータ）。リクエストボディの長さは、主に以下の2つの方法で示されます。

1.  **`Content-Length`ヘッダ**: ボディのバイト数を明示的に指定します。サーバーはこの値を使って、ボディの終わりを正確に判断できます。
2.  **`Transfer-Encoding: chunked`ヘッダ**: ボディがチャンク（塊）に分割されて送信されることを示します。各チャンクはサイズ情報とデータを含み、最後のチャンクはサイズ0でボディの終わりを示します。この方式は、ボディの全長が事前に分からない場合に便利です。

### `io.Reader`と`io.LimitedReader`

Goの`io.Reader`インターフェースは、データを読み込むための基本的な抽象化です。`net/http`パッケージでは、リクエストボディはこの`io.Reader`として提供されます。

`io.LimitedReader`は、`io.Reader`をラップし、指定されたバイト数までしか読み込まないように制限する構造体です。これは、大量のデータの中から特定の量だけを読み込みたい場合や、読み込み量を制限してリソース消費を抑えたい場合に有用です。

### `req.Body.Close()`の役割

`http.Request`の`Body`フィールドは`io.ReadCloser`インターフェースを満たしており、これは`io.Reader`と`io.Closer`を組み合わせたものです。`Close()`メソッドは、リクエストボディの読み込みを終了し、関連するリソースを解放するために呼び出されます。

`net/http`サーバーの内部では、ハンドラの実行が終了した後、暗黙的に`req.Body.Close()`が呼び出されます。この`Close()`メソッドの重要な役割の一つは、現在のリクエストボディの残りを読み飛ばし、TCPコネクション上で次のリクエストが始まる位置まで進めることです。これにより、コネクションの再利用が可能になります。

### コネクションの再利用（Keep-Alive）

HTTP/1.1では、`Connection: keep-alive`ヘッダがデフォルトで有効であり、サーバーとクライアントは一つのTCPコネクションを複数のリクエスト/レスポンスサイクルで再利用しようとします。これにより、新しいコネクションを確立する際のハンドシェイクのオーバーヘッドが削減され、Webページのロード時間が短縮されます。

コネクションを再利用するためには、サーバーは現在のリクエストのボディを完全に消費し、次のリクエストのヘッダが始まる位置を正確に特定できる必要があります。もしボディが途中で残っていると、次のリクエストのヘッダと混同されてしまい、プロトコルエラーが発生します。

## 技術的詳細

このコミットは、`net/http`パッケージの`body`構造体と、その`Close()`メソッドの挙動を修正することで、前述の問題に対処しています。

### `maxPostHandlerReadBytes`の導入

このコミットでは、`maxPostHandlerReadBytes`という定数が導入されています。これは、ハンドラがリクエストボディを完全に読み込まなかった場合に、コネクション再利用のために読み飛ばす最大バイト数を定義します。この定数は、他の同様のケース（例: フォームデータのパースなど）で使用されている既存の閾値と一致させられています。

### `body`構造体の変更

`src/net/http/transfer.go`内の`body`構造体に以下のフィールドが追加されました。

*   `doEarlyClose bool`: `Close()`メソッドが早期に読み込みを停止すべきかどうかを示すフラグ。`true`の場合、`maxPostHandlerReadBytes`の制限が適用されます。
*   `sawEOF bool`: `Read()`メソッドが既にEOF（End Of File）に到達したかどうかを追跡するフラグ。これにより、`Close()`が不必要に読み込みを試みるのを防ぎます。
*   `earlyClose bool`: `Close()`が`maxPostHandlerReadBytes`の制限により早期に読み込みを停止したかどうかを示すフラグ。このフラグは、コネクションを再利用すべきかどうかを判断するために使用されます。

### `body.Close()`メソッドの挙動変更

`body.Close()`メソッドのロジックが大幅に修正されました。

1.  **`b.sawEOF`の場合**: 既にボディのEOFに到達している場合は、それ以上読み込みを試みずにすぐに終了します。
2.  **`b.hdr == nil && b.closing`の場合**: トレーラーヘッダがなく、かつコネクションが閉じられる予定である場合は、EOFまで読み込む必要がないため、早期に終了します。
3.  **`b.doEarlyClose`の場合**: この新しい条件が追加されました。
    *   もし`b.src`が`io.LimitedReader`であり、かつ残りのバイト数（`lr.N`）が`maxPostHandlerReadBytes`よりも大きい場合、ボディ全体を読み飛ばすのは非効率的であると判断し、`b.earlyClose = true`を設定して読み込みを停止します。この場合、コネクションは再利用されません。
    *   それ以外の場合（`Content-Length`が`maxPostHandlerReadBytes`以下であるか、チャンクエンコーディングの場合）、`io.CopyN`を使って`maxPostHandlerReadBytes`までのデータを`ioutil.Discard`に読み込みます。これにより、ボディの残りの一部（または全部）を消費し、トレーラーヘッダを読み込む機会を与えます。もし`maxPostHandlerReadBytes`に達した場合、`b.earlyClose = true`を設定します。
4.  **デフォルトの場合**: 上記のいずれにも該当しない場合は、以前と同様にボディ全体をEOFまで読み込みます。

### コネクション再利用の判断ロジックの変更

`src/net/http/server.go`内の`(*response).finishRequest()`メソッドが`(*response).shouldReuseConnection()`という新しいメソッドにリファクタリングされました。このメソッドは、TCPコネクションを再利用できるかどうかを判断します。

`shouldReuseConnection()`メソッドは、以下の条件をチェックします。

*   `w.closeAfterReply`が`true`の場合（ハンドラがコネクションを閉じるよう指示した場合など）。
*   `Content-Length`が指定されているにもかかわらず、期待されるバイト数がすべて書き込まれなかった場合。
*   書き込み中にエラーが発生した場合。
*   **新しく追加された条件**: `w.req.Body`が`*body`型であり、かつ`body.didEarlyClose()`が`true`の場合。つまり、`Body.Close()`が`maxPostHandlerReadBytes`の制限により早期に読み込みを停止した場合、コネクションは再利用されません。

この変更により、不要な大量のボディ読み込みを避けた結果、コネクションの再利用を諦めるというトレードオフが明確になりました。

### テストケースの追加

`src/net/http/serve_test.go`に`TestHandlerBodyClose`という新しいテスト関数が追加されました。このテストは、様々なシナリオ（ボディサイズ、チャンクエンコーディングの有無、`Connection: close`ヘッダの有無など）で`Body.Close()`の挙動を検証します。特に、`wantEOFSearch`と`wantNextReq`というフィールドを使って、EOF探索が行われるべきか、そして次のリクエストが同じコネクションで見つかるべきかを期待値として設定し、新しいロジックが正しく機能していることを確認しています。

## コアとなるコードの解説

このコミットの核心は、`src/net/http/transfer.go`内の`body`構造体とその`Close()`メソッドの変更、および`src/net/http/server.go`内のコネクション再利用ロジックの調整にあります。

### `body`構造体と`Close()`メソッド

`body`構造体は、HTTPリクエストボディの読み込みを管理します。`Close()`メソッドは、リクエストボディの読み込みを完了させ、必要に応じてトレーラーヘッダを処理し、コネクションの再利用に備える役割を担います。

変更前は、ハンドラがボディを完全に読み込まなかった場合、`Close()`は常に残りのボディ全体を読み飛ばそうとしました。これが巨大なボディの場合に問題でした。

変更後は、`body`構造体に`doEarlyClose`というフラグが追加され、`(*conn).readRequest()`内でこのフラグが`true`に設定されます。これは、このリクエストボディがハンドラによって完全に読み込まれない可能性があることを示唆します。

`body.Close()`メソッド内で、この`doEarlyClose`フラグが`true`の場合、以下のロジックが適用されます。

1.  **`Content-Length`があり、残りのバイト数が`maxPostHandlerReadBytes`を超える場合**:
    *   `b.earlyClose = true`が設定され、それ以上のボディの読み込みは行われません。
    *   この場合、コネクションは再利用されません。これは、大量のデータを読み飛ばすコストが高すぎるため、コネクションを閉じて新しいコネクションを確立する方が効率的であるという判断です。
2.  **それ以外の場合（`Content-Length`が`maxPostHandlerReadBytes`以下、またはチャンクエンコーディングの場合）**:
    *   `io.CopyN(ioutil.Discard, bodyLocked{b}, maxPostHandlerReadBytes)`を使って、最大`maxPostHandlerReadBytes`バイトまでボディを読み飛ばします。
    *   これにより、チャンクエンコーディングの場合にトレーラーヘッダを読み込む機会を与えつつ、読み飛ばすデータ量に上限を設けます。
    *   もし`maxPostHandlerReadBytes`に達した場合、`b.earlyClose = true`が設定されます。

`sawEOF`フラグは、`body.Read()`が既にEOFを検出したかどうかを追跡し、`Close()`が不必要に読み込みを試みるのを防ぎます。

### コネクション再利用ロジック

`src/net/http/server.go`の`(*response).shouldReuseConnection()`メソッドは、コネクションを再利用すべきかどうかを判断します。このメソッドに、`body.didEarlyClose()`という新しい条件が追加されました。

`body.didEarlyClose()`は、`body.Close()`が`maxPostHandlerReadBytes`の制限により早期に読み込みを停止したかどうかを返します。もし`true`であれば、リクエストボディが完全に消費されていないため、コネクションを再利用すると次のリクエストのパースに問題が生じる可能性があります。したがって、この場合はコネクションは再利用されず、閉じられます。

この一連の変更により、Goの`net/http`サーバーは、巨大なリクエストボディが完全に読み込まれなかった場合でも、不必要なデータ読み込みを避け、リソース消費を抑えることができるようになりました。同時に、コネクション再利用の判断もより賢明になり、プロトコルの一貫性を保ちつつパフォーマンスと堅牢性を向上させています。

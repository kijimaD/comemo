## 変更の背景

Goコンパイラは、コードの最適化をより効果的に行うために、SSA（Static Single Assignment）形式の中間表現を使用しています。SSAは、各変数が一度だけ代入されることを保証する形式であり、データフロー解析や最適化を容易にします。

このコミット以前は、Go言語のスライス操作（例: `a[low:high]` や `a[low:high:max]`）がSSA形式で直接表現されていなかった可能性があります。その結果、コンパイラはこれらの操作に対して限定的な最適化しか適用できず、生成される機械語コードの効率が低下する可能性がありました。

この変更の背景には、スライス操作をSSA形式で明示的に表現することで、以下のようなメリットを享受する目的があります。

1.  **最適化の強化**: スライス操作がSSAオペコードとして表現されることで、コンパイラの最適化パス（例: 共通部分式除去、定数伝播、デッドコード除去など）がこれらの操作に対してより効果的に機能するようになります。
2.  **コード生成の改善**: スライス操作のセマンティクスがSSAレベルで明確になることで、より効率的な機械語コードが生成されるようになります。特に、スライス境界チェックの最適化や、スライスヘッダ（ポインタ、長さ、容量）の構築に関する最適化が期待されます。
3.  **コンパイラの構造化**: Go言語の重要な機能であるスライスをSSA形式で適切に表現することは、コンパイラの内部構造をより整理し、将来的な機能拡張や最適化の基盤を強化することにも繋がります。

特に、`OSLICE3`（`a[low:high:max]`形式の3インデックススライス）のサポートは、スライスの容量（capacity）を明示的に制御するGoの強力な機能であり、これをSSAで正確に表現することは、より高度なメモリ管理最適化に不可欠です。

## 前提知識の解説

### Go言語のスライス

Go言語のスライスは、配列をラップした動的なビューです。スライスは以下の3つの要素から構成される「スライスヘッダ」を持ちます。

*   **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
*   **長さ (Length)**: スライスに含まれる要素の数。`len()`関数で取得。
*   **容量 (Capacity)**: スライスの基底配列の先頭から末尾までの要素の数。`cap()`関数で取得。

スライス操作には以下の形式があります。

*   `a[low:high]`: `low`から`high-1`までの要素を含む新しいスライスを作成します。長さは`high - low`、容量は元のスライスの容量から`low`を引いた値になります。`low`が省略された場合は`0`、`high`が省略された場合は元のスライスの長さがデフォルト値となります。
*   `a[low:high:max]`: `low`から`high-1`までの要素を含む新しいスライスを作成し、その容量を`max - low`に設定します。この形式は、新しいスライスの容量を元のスライスの容量よりも小さく制限したい場合に特に有用です。

スライス操作では、インデックスが基底配列の範囲外である場合や、`low > high`、`high > max`、`low > max`などの不正な関係がある場合にパニック（実行時エラー）が発生します。コンパイラはこれらの境界チェックを挿入する必要があります。

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの中間表現の一種で、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が非常に容易になり、様々な最適化を効率的に適用できます。

Goコンパイラでは、ソースコードがAST（Abstract Syntax Tree）にパースされた後、SSA形式に変換されます。SSA形式では、プログラムは「値 (Value)」と「ブロック (Block)」のグラフとして表現されます。

*   **Value**: 演算の結果や定数など、プログラム中のあらゆる値を表します。各Valueは一意の定義を持ちます。
*   **Block**: 制御フローの基本単位で、一連のValueと、そのブロックの終わりに実行される制御フロー命令（例: 条件分岐、ジャンプ）を含みます。

SSA形式への変換は、コンパイラのバックエンドにおける重要なステップであり、その後の最適化フェーズの基盤となります。

### Goコンパイラの内部構造 (`cmd/compile/internal/gc` と `cmd/compile/internal/ssa`)

*   `src/cmd/compile/internal/gc`: Goコンパイラのフロントエンドと共通部分を扱うパッケージです。ASTの構築、型チェック、一部の最適化、そしてSSA形式への変換の初期段階を担当します。このコミットで変更されている`ssa.go`ファイルは、ASTノードをSSA Valueに変換するロジックを含んでいます。
*   `src/cmd/compile/internal/ssa`: SSA形式の中間表現自体を定義し、それに対する最適化パスを実行するパッケージです。このコミットで変更されている`type.go`ファイルは、SSA内部で利用される型システムに関連する定義を含んでいます。

## 技術的詳細

このコミットの主要な変更点は、Goコンパイラの`gc`パッケージ（具体的には`ssa.go`）において、Go言語のスライス操作をSSA形式のオペコードに変換するロジックが追加されたことです。

### `ssa.go` における変更

以前の`OSLICESTR`の処理は、文字列スライスをSSAに変換する際に、ポインタ、長さ、容量を個別に計算し、境界チェックや条件分岐を明示的に生成していました。これは冗長であり、最適化の機会を逃す可能性がありました。

このコミットでは、`s.slice`という新しいヘルパー関数が導入され、スライス操作の共通ロジックがカプセル化されています。

#### `s.slice` ヘルパー関数

`s.slice(t *Type, v, i, j, k *ssa.Value) (p, l, c *ssa.Value)` 関数は、以下の役割を担います。

1.  **型の判別**: 引数`t`（元のスライスの型）に基づいて、それがスライス、文字列、または配列へのポインタのいずれであるかを判別します。
    *   `t.IsSlice()`: スライスの場合、`OpSlicePtr`, `OpSliceLen`, `OpSliceCap`オペコードを使用して、元のスライスのポインタ、長さ、容量を取得します。
    *   `t.IsString()`: 文字列の場合、`OpStringPtr`, `OpStringLen`オペコードを使用して、元の文字列のポインタと長さを取得します。文字列スライスでは容量は長さと同じと見なされます。
    *   `t.IsPtr()` かつ `t.Type.IsArray()`: 配列へのポインタの場合、ポインタは`v`自体、長さと容量は配列の境界（`t.Type.Bound`）から取得します。
2.  **デフォルト値の設定**: `i`, `j`, `k`（`low`, `high`, `max`インデックス）が`nil`の場合、それぞれ`0`、元の長さ、元の容量のデフォルト値を設定します。
3.  **境界チェック**: `s.sliceBoundsCheck`関数を呼び出して、スライスインデックスが有効な範囲内にあるかどうかのチェックを挿入します。これは、`low <= high`、`high <= max`、`max <= cap`といった条件を検証し、違反した場合はパニックを発生させるためのコードを生成します。
4.  **結果のスライスヘッダの計算**:
    *   新しいスライスの長さ (`rlen`) は `j - i` で計算されます。
    *   新しいスライスの容量 (`rcap`) は `k - i` で計算されます。文字列スライスの場合、`rcap`は`rlen`と同じになります。
5.  **ポインタの調整**: 新しいスライスのポインタ (`p`) は、元のポインタ (`ptr`) に`i * elemSize`を加算することで計算されます。ここで`elemSize`は要素のサイズです。要素サイズが1バイトでない場合は、`OpMulPtr`オペコードで`i`と`elemSize`を乗算します。
6.  **条件付きポインタ更新**: `rcap`が0でない場合（つまり、結果のスライスが空でない場合）、新しいポインタを計算する条件分岐が生成されます。これは、Goのスライスが空の場合でも元の基底配列のポインタを保持できるという特性を考慮したものです。
7.  **結果の返却**: 計算された新しいポインタ (`p`)、長さ (`l`)、容量 (`c`) を返します。

#### 各スライスオペコードの変換

*   `OSLICE`, `OSLICEARR`: `s.slice`関数を呼び出し、返された`p`, `l`, `c`を使って`ssa.OpSliceMake`オペコードを生成します。
*   `OSLICESTR`: `s.slice`関数を呼び出し、返された`p`, `l`を使って`ssa.OpStringMake`オペコードを生成します。文字列スライスは容量の概念が異なるため、`c`は使用されません。
*   `OSLICE3`, `OSLICE3ARR`: `s.slice`関数を呼び出し、返された`p`, `l`, `c`を使って`ssa.OpSliceMake`オペコードを生成します。`OSLICE3`は3インデックススライスに対応します。

### `type.go` および `ssa/type.go` における変更

`src/cmd/compile/internal/gc/type.go`と`src/cmd/compile/internal/ssa/type.go`に、`IsArray()`メソッドが追加されています。これは、型が固定長配列であるかどうかを判定するためのもので、`s.slice`関数内で配列へのポインタを処理する際に利用されます。

*   `gc/type.go`: `t.Etype == TARRAY && t.Bound >= 0` で配列を識別します。Goコンパイラの内部では、スライスは`t.Etype == TARRAY && t.Bound < 0`として表現されるため、これら2つを区別するために`IsArray()`が導入されました。
*   `ssa/type.go`: SSAパッケージの型インターフェースにも`IsArray()`が追加され、`CompilerType`構造体にも対応するフィールドとメソッドが追加されています。

### `ssa_test.go` および `testdata/array_ssa.go` における変更

新しいテストファイル`src/cmd/compile/internal/gc/testdata/array_ssa.go`が追加され、`src/cmd/compile/internal/gc/ssa_test.go`からこのテストが実行されるようになっています。
`array_ssa.go`には、配列からのスライス操作（`a[i:j]`、`a[i:]`、`a[:j]`）の`len`と`cap`の挙動、スライスされた配列要素へのアクセス、要素の変更、そして境界外アクセスによるパニックの発生を検証するテストケースが含まれています。これにより、新しいSSAオペコードの実装がGo言語のセマンティクスに正しく準拠していることが保証されます。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/compile/internal/gc/ssa.go`に追加された`slice`ヘルパー関数と、それを利用して各種スライス操作（`OSLICE`, `OSLICEARR`, `OSLICESTR`, `OSLICE3`, `OSLICE3ARR`）をSSA形式に変換するロジックです。

### `slice` ヘルパー関数

`slice`関数は、Goのスライス操作`v[i:j:k]`のセマンティクスをSSA形式で正確に表現するための中心的なロジックをカプセル化しています。

1.  **入力**:
    *   `t *Type`: 元の式の型（スライス、文字列、配列へのポインタ）。
    *   `v *ssa.Value`: 元の式（スライス、文字列、配列へのポインタ）に対応するSSA Value。
    *   `i, j, k *ssa.Value`: スライスインデックス`low`, `high`, `max`に対応するSSA Value。`nil`の場合、デフォルト値が使用されます。

2.  **出力**:
    *   `p *ssa.Value`: 結果のスライスの基底配列へのポインタ。
    *   `l *ssa.Value`: 結果のスライスの長さ。
    *   `c *ssa.Value`: 結果のスライスの容量。

3.  **処理の概要**:
    *   **型に応じた情報抽出**: `switch`文で`t`の型を判別し、`v`から元のポインタ、長さ、容量を抽出します。
        *   `t.IsSlice()`: `OpSlicePtr`, `OpSliceLen`, `OpSliceCap`を使ってスライスヘッダの各要素を取得します。
        *   `t.IsString()`: `OpStringPtr`, `OpStringLen`を使って文字列のポインタと長さを取得します。文字列の容量は長さと同じと見なされます。
        *   `t.IsPtr()`かつ`t.Type.IsArray()`: 配列へのポインタの場合、ポインタは`v`自体、長さと容量は配列の固定長から取得します。
    *   **デフォルトインデックス**: `i`, `j`, `k`が`nil`の場合、それぞれ`0`、元の長さ、元の容量で初期化されます。
    *   **境界チェック**: `s.sliceBoundsCheck`を呼び出し、`i <= j`, `j <= k`, `k <= cap`といったGoのスライス規則に基づく境界チェックをSSAグラフに挿入します。これにより、実行時に不正なスライス操作が行われた場合にパニックが発生するようになります。
    *   **結果の長さと容量の計算**: `rlen = j - i`、`rcap = k - i`として、新しいスライスの長さと容量を計算します。文字列スライスの場合、`rcap`は`rlen`と同じです。
    *   **ポインタの調整**: 新しいスライスのポインタは、元のポインタ`ptr`に`i * elemSize`を加算して計算されます。`elemSize`は要素のバイトサイズです。`elemtype.Width == 1`（1バイト要素、例: `byte`）の場合は`i`を直接加算し、それ以外の場合は`i`と`elemtype.Width`を`OpMulPtr`で乗算してから加算します。
    *   **条件分岐によるポインタ更新**: `rcap != 0`の場合にのみポインタを調整する条件分岐が生成されます。これは、空のスライスが元の基底配列の先頭を指す場合と、調整されたポインタを指す場合があるためです。この分岐は、コンパイラがより正確なポインタ情報を保持し、後の最適化で利用できるようにするために重要です。
    *   **結果の返却**: 最終的に計算された新しいポインタ、長さ、容量のSSA Valueが返されます。

### 各スライスオペコードの変換ロジック

`expr`関数内の`case OSLICE, OSLICEARR:`、`case OSLICESTR:`、`case OSLICE3, OSLICE3ARR:`ブロックは、それぞれ対応するASTノードを`s.slice`関数呼び出しと`newValue`関数（SSA Valueを生成）に変換します。

*   `OSLICE`, `OSLICEARR`, `OSLICE3`, `OSLICE3ARR`: これらのスライス操作は、`s.slice`から得られたポインタ、長さ、容量の3つの情報を使って`ssa.OpSliceMake`オペコードを生成します。`OSLICE3`は3インデックススライスに対応するため、`k`インデックスも`s.slice`に渡されます。
*   `OSLICESTR`: 文字列スライスは容量の概念が異なるため、`s.slice`から得られたポインタと長さの2つの情報を使って`ssa.OpStringMake`オペコードを生成します。

この変更により、Goコンパイラはスライス操作をSSA形式でより詳細かつ正確に表現できるようになり、結果としてより高度な最適化と効率的なコード生成が可能になります。特に、スライス境界チェックの最適化や、スライスヘッダの構築に関する最適化が期待されます。

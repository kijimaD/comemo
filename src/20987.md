## 変更の背景

Go 1.4では、カスタムインポートパスのサポートが強化されました。カスタムインポートパスとは、Goのパッケージがそのソースコードのリポジトリとは異なるインポートパスを持つことを可能にする機能です。例えば、`import "example.com/repo/pkg"` のように、`example.com` のドメイン配下にあるかのように見せかけつつ、実際にはGitHubなどの別の場所にあるリポジトリから取得される、といったケースがこれに該当します。

この機能の導入に伴い、`go get -u` コマンド（パッケージを更新するコマンド）の挙動に新たなチェックが追加されました。これは、ローカルにダウンロード済みのパッケージのリモートリポジトリが、そのカスタムインポートパスと一致するかどうかを検証するものです。もしリモートリポジトリが初回ダウンロード時から変更されている場合、`go get -u` はエラーとなり、更新が失敗するようになりました。

この変更は、悪意のあるリポジトリへのリダイレクトや、意図しないリポジトリからのコード取得を防ぐためのセキュリティ強化策として導入されました。しかし、正当な理由でリポジトリの場所が変更された場合など、このチェックが更新の妨げとなる可能性がありました。そのため、このチェックを明示的に上書きするための新しいフラグ `-f` が `go get` コマンドに追加されました。

このコミットは、Go 1.4のリリースノートに、この新しいチェックと `-f` フラグの存在を公式に文書化することを目的としています。これにより、ユーザーはGo 1.4での `go get` の挙動変更と、その対処法を理解できるようになります。

## 前提知識の解説

### `go get` コマンド

`go get` は、Go言語のパッケージをリモートリポジトリからダウンロードし、インストールするためのコマンドです。通常、`go get example.com/path/to/package` のように使用され、指定されたパッケージとその依存関係を `$GOPATH` (Go Modulesが導入される前) またはモジュールキャッシュにダウンロードします。

### `go get -u` コマンド

`go get -u` は、指定されたパッケージとその依存関係を「更新」するためのコマンドです。既にローカルに存在するパッケージがある場合、その最新バージョンをリモートリポジトリから取得し、ローカルのコピーを上書きします。

### カスタムインポートパス (Custom Import Paths)

Goのパッケージは通常、そのリポジトリのURLをインポートパスとして使用します（例: `github.com/user/repo/pkg`）。しかし、カスタムインポートパスを使用すると、開発者は独自のドメイン名（例: `example.com/my/package`）をインポートパスとして指定し、そのドメインへのHTTPリクエストを介して、実際のソースコードのリポジトリ（例: `github.com/user/repo`）にリダイレクトさせることができます。これは、`go get` がカスタムインポートパスを解決する際に、指定されたドメインにアクセスし、HTMLメタタグ（`<meta name="go-import" ...>`）から実際のVCS（Version Control System）リポジトリのURLを取得する仕組みによって実現されます。

### Go 1.4における変更点

Go 1.4では、カスタムインポートパスのセキュリティと信頼性を向上させるため、`go get -u` の挙動に重要な変更が加えられました。具体的には、ローカルに存在するカスタムインポートパスを持つパッケージを更新する際、`go get` は以下のチェックを行うようになりました。

1.  **カスタムインポートパスのリモートリポジトリ検証**: `go get` は、パッケージのカスタムインポートパスが指すリモートリポジトリが、ローカルにダウンロードされたパッケージの実際のソースリポジトリと一致するかどうかを確認します。
2.  **不一致時の更新失敗**: もしこのチェックで不一致が検出された場合、`go get -u` はエラーを返し、パッケージの更新を停止します。これは、悪意のあるリダイレクトや、意図しないリポジトリからのコード取得を防ぐための安全策です。

## 技術的詳細

このコミットが文書化している技術的詳細は、Go 1.4で導入された `go get -u` の新しい検証ロジックと、それを制御する `-f` フラグの挙動です。

Go 1.4より前は、`go get -u` はカスタムインポートパスを持つパッケージを更新する際に、そのパッケージが最初にダウンロードされたリポジトリと、現在のカスタムインポートパスが指すリポジトリが異なる場合でも、特に警告なく更新を試みる可能性がありました。これは、カスタムインポートパスの解決メカニズムが悪用され、ユーザーが意図しない悪意のあるリポジトリからコードをダウンロードしてしまうリスクをはらんでいました。

Go 1.4では、このリスクを軽減するために、`go get -u` がパッケージを更新する前に、以下の検証ステップが追加されました。

1.  **ローカルリポジトリ情報の取得**: `go get` は、ローカルに存在するパッケージの `.git` や `.hg` などのVCSメタデータから、そのパッケージが最初にどのリモートリポジトリからクローンされたかという情報を取得します。
2.  **カスタムインポートパスの解決**: 次に、`go get` はパッケージのカスタムインポートパス（例: `example.com/my/package`）を解決し、現在そのパスが指している実際のVCSリポジトリのURL（例: `https://github.com/original-user/original-repo` または `https://github.com/new-user/new-repo`）を取得します。
3.  **リポジトリURLの比較**: 取得したローカルリポジトリのURLと、カスタムインポートパスが現在指しているリポジトリのURLを比較します。
4.  **不一致時の挙動**:
    *   **一致する場合**: 通常通りパッケージの更新を進めます。
    *   **不一致の場合**: `go get -u` コマンドはエラーを発生させ、更新を中断します。このエラーメッセージは、リモートリポジトリが変更されたことをユーザーに通知し、潜在的なセキュリティリスクを示唆します。

この新しいチェックは、カスタムインポートパスの背後にある実際のソースが変更された場合に、ユーザーに明示的な確認を促すことで、サプライチェーン攻撃や意図しないコードの取り込みを防ぐことを目的としています。

### `-f` フラグの導入

この厳格なチェックはセキュリティ上重要ですが、正当な理由でリポジトリの場所が変更された場合（例: プロジェクトが新しい組織に移管された、リポジトリがフォークされ、そのフォークを追跡したい場合など）には、更新の妨げとなります。

そこで、`go get -f` フラグが導入されました。`-f` は "force" を意味し、このフラグを `go get -u` と共に使用すると、上記のリモートリポジトリの一致チェックを「上書き」し、強制的にパッケージの更新を実行します。これにより、ユーザーはリスクを認識した上で、意図的にリポジトリの変更を許可し、更新を進めることができるようになります。

このコミットは、この重要な挙動変更と、それに対応する `-f` フラグの存在をGo 1.4の公式リリースノートに追記することで、ユーザーへの情報提供を確実にするものです。

## コアとなるコードの解説

追加されたHTMLスニペットは、Go 1.4のリリースノートに以下の情報を追記しています。

```html
<p>
To complement this new feature, a check has been added at update time to verify
that the local package's remote repository matches that of its custom import.
The <code>go</code> <code>get</code> <code>-u</code> command will fail to
update a package if its remote repository has changed since it was first
downloaded.
The new <code>-f</code> flag overrides this check.
</p>
```

この段落は、Go 1.4で導入されたカスタムインポートパス関連の新しい機能（おそらく、以前の段落で説明されているカスタムインポートパスの解決に関する改善）を補完するものとして、以下の点を明確に説明しています。

1.  **新しいチェックの導入**: パッケージの更新時（`go get -u`）に、ローカルパッケージのリモートリポジトリがそのカスタムインポートパスと一致するかどうかを検証するチェックが追加されたこと。
2.  **更新失敗の条件**: パッケージが最初にダウンロードされてからリモートリポジトリが変更された場合、`go get -u` コマンドが更新に失敗すること。
3.  **`-f` フラグの役割**: 新しい `-f` フラグがこのチェックを上書きし、強制的に更新を実行できること。

この追加により、Go 1.4のユーザーは、`go get -u` の挙動変更と、それに伴う `-f` フラグの必要性を公式ドキュメントから直接理解できるようになります。これは、Goツールの透明性とユーザーエクスペリエンスを向上させる上で重要なドキュメントの更新です。

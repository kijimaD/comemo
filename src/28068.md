# [インデックス 28068] ファイルの概要

このコミットは、Goランタイムのメモリ管理システム、特に`mspan`（メモリ領域の単位）内で次に利用可能なオブジェクトを見つけるメカニズムを最適化することを目的としています。具体的には、`mspan`構造体に64ビットのキャッシュ（`allocCache`）を導入し、`ctz64`（count trailing zero）命令を利用することで、空きオブジェクトの探索を高速化します。これにより、将来的にハードウェアのCTZ命令を活用したさらなるパフォーマンス向上が期待されます。

## 変更の背景

Goランタイムのメモリ管理において、ガベージコレクタ（GC）やアロケータは、メモリ領域（`mspan`）の中から次に利用可能なオブジェクトを効率的に見つける必要があります。この「次に空いているインデックスを見つける」処理（`nextFreeIndex`）は、頻繁に実行されるため、そのパフォーマンスはランタイム全体の効率に直結します。

従来の`nextFreeIndex`の実装では、`allocBits`というビットマップを直接走査して空きオブジェクトを探していました。これは、特に大きな`mspan`や多くのオブジェクトが割り当てられている場合に、ビット単位またはバイト単位のループ処理が必要となり、CPUサイクルを消費する可能性がありました。

このコミットの目的は、この`nextFreeIndex`の処理を高速化することです。具体的には、CPUが提供する「Count Trailing Zeros (CTZ)」のようなビット操作命令を最大限に活用できるように、データ構造とアルゴリズムを再設計しています。CTZ命令は、数値の最下位ビットから連続するゼロの数を高速に計算できるため、ビットマップから最初の空きスロットを見つけるのに非常に適しています。

コミットメッセージには、現在の`ctz64`の実装がGo言語のループで書かれており、まだ効率的ではないことが明記されています。そのため、この変更自体は一時的にパフォーマンスを悪化させる可能性（ベンチマークで3.1秒 vs 2.8秒）がありますが、これは将来的にCTZのハードウェア命令が利用されるための準備段階と位置づけられています。プロファイリングの結果、Go実装の`ctz64`が全体の1%を占めることが示されており、ハードウェア命令への置き換えによる大きな改善の余地があることを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムのメモリ管理に関する概念とビット操作の知識が必要です。

### Goランタイムのメモリ管理の基本

*   **`mspan`**: Goランタイムのメモリ管理における基本的な単位です。ヒープメモリはページ単位で管理され、連続する複数のページが`mspan`を構成します。各`mspan`は特定のサイズのオブジェクト（`sizeclass`）を格納するために使用されます。
*   **`mcache`**: 各ゴルーチン（P）にローカルなキャッシュで、小さなオブジェクトの割り当てを高速化します。`mcache`は`mspan`のリストを保持し、そこからオブジェクトを割り当てます。
*   **`mcentral`**: `mcache`が`mspan`を使い果たした際に、新しい`mspan`を供給する役割を担います。`mcentral`は、空きオブジェクトを持つ`mspan`と、完全に割り当て済みの`mspan`のリストを管理します。
*   **`mheap`**: 全ての`mspan`を管理するグローバルなヒープです。

### `mspan`内のオブジェクト管理

*   **`allocBits`**: `mspan`構造体内に存在するビットマップです。`mspan`内の各オブジェクトの割り当て状態を追跡します。通常、ビットが`0`であればオブジェクトは空き、`1`であれば割り当て済みを示します。`allocBits`は`[maxObjsPerSpan / 8]uint8`の配列として定義され、バイト単位でアクセスされます。
*   **`freeindex`**: `mspan`内で次に空きオブジェクトが見つかる可能性のある開始インデックスを示します。このインデックスより前のオブジェクトは既に割り当て済みであるか、以前に解放されたオブジェクトです。`freeindex`は、空きオブジェクトの探索範囲を限定し、効率を高めるために使用されます。

### Count Trailing Zeros (CTZ)

*   **CTZ命令**: CPUが提供するビット操作命令の一つで、与えられた数値の最下位ビットから連続するゼロの数を数えます。例えば、バイナリ値 `00010100` (20) の場合、最下位ビットから2つのゼロが連続しているため、CTZは `2` を返します。x86アーキテクチャでは `BSF` (Bit Scan Forward) 命令がこれに相当します。
*   **CTZの利点**: ビットマップから最初の空きビット（またはセットされたビット）を高速に特定するのに非常に有効です。ソフトウェアでループを使ってビットを走査するよりも、はるかに少ないCPUサイクルで結果を得られます。

## 技術的詳細

このコミットの技術的な核心は、`mspan`構造体に`allocCache`という新しいフィールドを導入し、`nextFreeIndex`関数がこのキャッシュと`ctz64`関数を組み合わせて空きオブジェクトを探索する点にあります。

1.  **`mspan.allocCache`の導入**:
    *   `mspan`構造体に`allocCache uint64`というフィールドが追加されました。これは、`allocBits`の一部（64ビット分）をキャッシュするためのものです。
    *   `allocCache`は、`freeindex`に対応するビットが最下位ビットになるようにシフトされます。
    *   重要なのは、`allocCache`は`allocBits`とは逆のセマンティクスを持つ点です。`allocBits`では`0`が空き、`1`が割り当て済みですが、`allocCache`では**`1`が空き**、`0`が割り当て済みを示します。この反転は、`ctz64`が最下位の`1`を効率的に見つけるために行われます。

2.  **`ctz64`関数の実装**:
    *   `src/runtime/mbitmap.go`に`ctz64(markBits uint64) uint64`関数が追加されました。
    *   この関数は、与えられた`uint64`値の最下位ビットから連続するゼロの数を数えます。
    *   現在の実装はGo言語のループによるもので、`markBits == 0`の場合は`64`を返します。これは、64ビットワード内に`1`がない（全て`0`）ことを意味し、`allocCache`のセマンティクスでは「全て割り当て済み」を意味します。
    *   将来的に、この関数はCPUのハードウェアCTZ命令（例: x86の`BSF`）に置き換えられる予定です。

3.  **`refillAllocCache`関数の導入**:
    *   `src/runtime/mbitmap.go`に`refillAllocCache(whichByte uintptr)`関数が追加されました。
    *   この関数は、`mspan.allocBits`の指定された`whichByte`から8バイト（64ビット）を読み込み、それを`uint64`に結合します。
    *   その後、この`uint64`値をビット反転（`^aCache`）し、結果を`s.allocCache`に格納します。これにより、`allocCache`では`1`が空き、`0`が割り当て済みを示すようになります。

4.  **`nextFreeIndex`関数の再設計**:
    *   `src/runtime/mbitmap.go`の`nextFreeIndex`関数が大幅に書き換えられました。
    *   新しい実装では、`s.allocCache`と`ctz64`を組み合わせて空きオブジェクトを探索します。
    *   まず、現在の`s.allocCache`に対して`ctz64`を呼び出し、最初の空きビットのインデックス（`bitIndex`）を取得します。
    *   もし`bitIndex`が`64`（キャッシュ内の全てのビットが`0`、つまり全て割り当て済み）であれば、`s.freeindex`を次の64ビット境界に移動させ、`refillAllocCache`を呼び出して`allocCache`を更新します。このプロセスは空きビットが見つかるか、`mspan`の終端に達するまで繰り返されます。
    *   空きビットが見つかった場合、`s.freeindex`と`bitIndex`を組み合わせて実際の空きオブジェクトのインデックス（`result`）を計算します。
    *   `s.allocCache`は、見つかった空きオブジェクトに対応するビットをクリアするために、`bitIndex + 1`だけ右シフトされます（`s.allocCache >>= bitIndex + 1`）。これにより、次に`nextFreeIndex`が呼び出されたときに、同じオブジェクトが再度選択されるのを防ぎます。
    *   `s.freeindex`が64ビットの境界を越えた場合、`allocCache`を再度`refillAllocCache`で更新し、次の64ビットの範囲をキャッシュするようにします。

これらの変更により、`nextFreeIndex`はビットマップを逐次走査する代わりに、64ビット単位で高速に空きオブジェクトを特定できるようになります。

### `ctz64`関数の実装 (`src/runtime/mbitmap.go`)

```go
func ctz64(markBits uint64) uint64 {
	if markBits == 0 {
		return 64 // bits in 64 bit word, ensures loop terminates
	}
	// tz holds trailing zero count.
	tz := uint64(0)
	for mask := uint64(1); mask&markBits == 0; mask, tz = mask<<1, tz+1 {
	}
	return tz
}
```
この関数は、与えられた`uint64`値`markBits`の最下位ビットから連続するゼロの数を数えます。`markBits`が`0`の場合（つまり、全てのビットが`0`で、`1`が一つも存在しない場合）、`64`を返します。これは、キャッシュされた64ビット全てが割り当て済みであることを意味します。ループは、`mask`が`markBits`の最下位の`1`と一致するまで実行され、その間の`tz`（trailing zero count）をインクリメントします。

### `refillAllocCache`関数の実装 (`src/runtime/mbitmap.go`)

```go

	aCache |= uint64(bytes[2]) << (2 * 8)
	aCache |= uint64(bytes[3]) << (3 * 8)

```
この関数は、`mspan`の`allocBits`配列から8バイト（64ビット分）を読み込み、それを`uint64`型の`aCache`に結合します。その後、`s.allocCache = ^aCache`という行で、`aCache`をビット反転させて`s.allocCache`に格納します。これにより、`allocBits`で`0`が空きだったものが、`allocCache`では`1`が空きとなるように変換されます。

### `nextFreeIndex`関数の新しいロジック (`src/runtime/mbitmap.go`)

```go
func (s *mspan) nextFreeIndex() uintptr {
	// ... (freeindexとnelemsの境界チェック) ...

	aCache := s.allocCache
	bitIndex := ctz64(aCache) // allocCacheから最初の空きビットのインデックスを取得

	for bitIndex == 64 { // キャッシュが全て割り当て済みの場合
		// freeindexを次の64ビット境界に移動
		s.freeindex = (s.freeindex + 64) &^ (64 - 1)
		if s.freeindex >= s.nelems { // mspanの終端に達した場合
			s.freeindex = s.nelems
			return s.freeindex
		}
		whichByte := s.freeindex / 8
		s.refillAllocCache(whichByte) // allocCacheを次の64ビットでリフィル
		aCache = s.allocCache
		bitIndex = ctz64(aCache) // 再度空きビットを探索
	}

	result := s.freeindex + uintptr(bitIndex) // 実際の空きオブジェクトのインデックスを計算
	if result >= s.nelems { // mspanの終端を超えた場合
		s.freeindex = s.nelems
		return s.freeindex
	}
	s.allocCache >>= bitIndex + 1 // 見つかったオブジェクトをキャッシュから「割り当て済み」としてマーク（右シフト）
	s.freeindex = result + 1      // freeindexを更新

	if s.freeindex%64 == 0 && s.freeindex != s.nelems {
		// freeindexが64ビット境界を越えた場合、allocCacheをリフィル
		whichByte := s.freeindex / 8
		s.refillAllocCache(whichByte)
	}
	return result
}
```
この新しい`nextFreeIndex`関数は、以下のステップで動作します。
1.  現在の`s.allocCache`を取得し、`ctz64`を呼び出して、キャッシュ内の最初の空きオブジェクトの相対インデックス（`bitIndex`）を見つけます。
2.  もし`bitIndex`が`64`であれば、現在の64ビットのキャッシュ範囲には空きオブジェクトがないことを意味します。この場合、`s.freeindex`を次の64ビット境界に移動させ、`refillAllocCache`を呼び出して`allocBits`から新しい64ビットを`allocCache`にロードします。この処理は空きが見つかるか、`mspan`の終端に達するまで繰り返されます。
3.  空きオブジェクトが見つかった場合、`s.freeindex`と`bitIndex`を合計して、`mspan`全体における実際の空きオブジェクトのインデックス`result`を計算します。
4.  `s.allocCache >>= bitIndex + 1`という操作により、見つかった空きオブジェクトに対応するビットを`allocCache`から削除（右シフト）します。これにより、次に`nextFreeIndex`が呼び出されたときに、同じオブジェクトが再度選択されるのを防ぎ、キャッシュの整合性を保ちます。
5.  `s.freeindex`を`result + 1`に更新し、次に探索を開始する位置を調整します。
6.  `s.freeindex`が64ビットの境界を越えた場合、`allocCache`を再度`refillAllocCache`で更新し、次の64ビットの範囲をキャッシュするようにします。

このロジックにより、`nextFreeIndex`は`allocBits`をビット単位で走査する代わりに、`ctz64`と`allocCache`を使って64ビット単位で高速に空きオブジェクトを特定できるようになります。

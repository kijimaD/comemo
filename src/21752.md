    cmd/6g, liblink, runtime: support saving base pointers

    This adds a "framepointer" GOEXPERIMENT that that makes the amd64
    toolchain maintain base pointer chains in the same way that gcc
    -fno-omit-frame-pointer does.  Go doesn't use these saved base
    pointers, but this does enable external tools like Linux perf and
    VTune to unwind Go stacks when collecting system-wide profiles.

    This requires support in the compilers to not clobber BP, support in
    liblink for generating the BP-saving function prologue and unwinding
    epilogue, and support in the runtime to save BPs across preemption, to
    skip saved BPs during stack unwinding and, and to adjust saved BPs
    during stack moving.

    As with other GOEXPERIMENTs, everything from the toolchain to the
    runtime must be compiled with this experiment enabled.  To do this,
    run make.bash (or all.bash) with GOEXPERIMENT=framepointer.

## 元コミット内容

このコミットは、Goの`amd64`ツールチェインに「framepointer」という`GOEXPERIMENT`を追加し、GCCの`-fno-omit-frame-pointer`オプションと同様にベースポインタ（BP）チェーンを維持するようにします。Goランタイム自体はこの保存されたベースポインタを使用しませんが、Linux perfやVTuneのような外部ツールがシステム全体のプロファイルを収集する際にGoのスタックをアンワインド（巻き戻し）できるようにします。

この機能を実現するためには、コンパイラがBPレジスタを破壊しないようにするサポート、`liblink`がBPを保存する関数プロローグとアンワインドエピローグを生成するサポート、そしてランタイムがプリエンプション（横取り）時にBPを保存し、スタックアンワインド時に保存されたBPをスキップし、スタック移動時に保存されたBPを調整するサポートが必要です。

他の`GOEXPERIMENT`と同様に、この実験を有効にするには、ツールチェインからランタイムまですべてをこの実験が有効な状態でコンパイルする必要があります。これを行うには、`make.bash`（または`all.bash`）を`GOEXPERIMENT=framepointer`付きで実行します。

## 変更の背景

Go言語のランタイムは、効率的なメモリ管理と並行処理のために独自のスタック管理とガベージコレクションメカニズムを持っています。従来のC/C++プログラムとは異なり、Goの関数呼び出し規約では通常、パフォーマンス最適化のためにベースポインタ（BPレジスタ）を省略します。これにより、BPレジスタを汎用レジスタとして利用でき、レジスタの枯渇を減らし、コード生成を簡素化できます。

しかし、この最適化は、Linux perfやIntel VTuneのようなシステムワイドプロファイリングツールにとって課題となります。これらのツールは、プログラムの実行中に定期的にスタックトレースを収集し、どの関数がCPU時間を消費しているかを特定することでパフォーマンスボトルネックを分析します。スタックトレースを正確に再構築するためには、通常、関数呼び出しフレームの連鎖をたどるためにベースポインタチェーンに依存します。GoがBPを省略すると、これらのツールはGoプログラムのスタックを正確にアンワインドできず、プロファイリングデータが不完全になったり、誤解を招くものになったりする可能性がありました。

このコミットの背景には、Goプログラムのパフォーマンスプロファイリング能力を向上させ、Go開発者がより詳細なシステムレベルの洞察を得られるようにするという明確なニーズがありました。Goランタイムの内部動作を変更することなく、外部ツールとの互換性を提供するために、`GOEXPERIMENT`というオプトインメカニズムを通じてベースポインタの保存をサポートすることが決定されました。これにより、Goのパフォーマンス上の利点を維持しつつ、必要に応じてプロファイリングの深度を増すことが可能になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

1.  **ベースポインタ (Base Pointer - BP / RBP)**:
    *   x86-64アーキテクチャにおいて、`RBP`レジスタは通常、現在の関数呼び出しフレームのベースアドレスを指すために使用されます。関数が呼び出されると、呼び出し元の`RBP`がスタックにプッシュされ、新しい`RBP`が現在のスタックポインタ（`RSP`）に設定されます。これにより、ローカル変数や引数に`RBP`からのオフセットでアクセスできます。
    *   関数が終了すると、保存された`RBP`がスタックからポップされ、`RSP`が元の位置に戻されます。この`RBP`の連鎖は、スタックトレースを生成する際に、各関数呼び出しフレームの境界を特定するために使用されます。
    *   多くのコンパイラ（例: GCC）は、最適化のために`-fomit-frame-pointer`オプションを使用してBPの保存を省略することがあります。これにより、`RBP`レジスタを汎用レジスタとして使用できるようになり、レジスタの利用効率が向上し、コードサイズがわずかに減少する可能性があります。Goのコンパイラも同様の最適化をデフォルトで行っています。

2.  **スタックアンワインド (Stack Unwinding)**:
    *   スタックアンワインドとは、プログラムの実行中に現在の関数呼び出しスタックを逆方向にたどり、呼び出し元の関数情報を取得するプロセスです。これは、デバッガ、プロファイラ、例外処理、ガベージコレクタなどが、現在の実行コンテキストを理解するために使用します。
    *   BPチェーンが利用可能な場合、アンワインドは比較的簡単です。各フレームのBPをたどることで、呼び出し元のBPとリターンアドレスを見つけることができます。BPが省略されている場合、アンワインドはより複雑になり、DWARFデバッグ情報やフレームポインタ以外のメカニズム（例: Goの独自のスタックマップ）に依存する必要があります。

3.  **Goランタイム (Go Runtime)**:
    *   Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、スケジューリング（ゴルーチンの管理）、チャネル通信、スタック管理など、Go言語のコア機能の多くを実装しています。
    *   Goのスタックは、必要に応じて動的に拡大・縮小する「セグメントスタック」または「連続スタック」として実装されています（Go 1.3以降は連続スタック）。これにより、スタックオーバーフローのリスクを減らし、メモリ効率を向上させています。スタックの移動は、ガベージコレクションやスタックの拡大・縮小時に発生します。

4.  **GOEXPERIMENT**:
    *   `GOEXPERIMENT`は、Goツールチェインにおける実験的な機能や変更を有効にするための環境変数です。これにより、開発者はまだ安定版ではない新機能を試したり、特定の動作をカスタマイズしたりできます。`GOEXPERIMENT`で有効化された機能は、ツールチェイン全体（コンパイラ、リンカ、ランタイムなど）で一貫してサポートされる必要があります。

5.  **Linux perf / Intel VTune**:
    *   これらは、システム全体のパフォーマンスをプロファイリングするための強力なツールです。
        *   **Linux perf**: Linuxカーネルに組み込まれたパフォーマンスカウンタを利用して、CPU使用率、キャッシュミス、システムコール、スタックトレースなどの情報を収集します。
        *   **Intel VTune Amplifier**: Intel製のプロファイリングツールで、CPU、メモリ、スレッド、I/Oなどのパフォーマンスデータを詳細に分析し、ボトルネックを特定します。
    *   これらのツールは、多くの場合、スタックアンワインドにBPチェーンに依存するため、Goプログラムのプロファイリングには課題がありました。

## 技術的詳細

このコミットは、Goの`amd64`ツールチェインに`GOEXPERIMENT=framepointer`という新しい実験的フラグを導入することで、外部プロファイリングツールがGoプログラムのスタックをより効果的にアンワインドできるようにします。

主要な技術的変更点は以下の通りです。

1.  **コンパイラ (`cmd/6g`) の変更**:
    *   `src/cmd/6g/gsubr.c`と`src/cmd/6g/reg.c`が変更され、`framepointer_enabled`が有効な場合、`BP`レジスタが予約され、汎用レジスタとして使用されないようにします。これにより、コンパイラが`BP`レジスタを破壊する（clobberする）ことを防ぎます。
    *   具体的には、`ginit`関数で`REG_BP`の参照カウントを増やし、`gclean`関数で減らすことで、`BP`レジスタが使用中であることをコンパイラに伝えます。また、`BtoR`関数では、`framepointer_enabled`の場合に`BP`レジスタがビットマスクから除外されるように変更されています。

2.  **リンカ (`liblink`) の変更**:
    *   `src/liblink/go.c`では、`GOEXPERIMENT`のリストに`"framepointer"`が追加され、`framepointer_enabled`変数がこの実験の状態を追跡するようにします。
    *   `src/liblink/obj6.c`が最も重要な変更箇所です。
        *   **関数プロローグの変更**: `preprocess`関数内で、`framepointer_enabled`が有効な場合、各関数のプロローグにBPを保存するコードが追加されます。
            *   呼び出し元の`BP`をスタックに保存します（`MOVQ BP, (autoffset - bpsize)(SP)`）。
            *   現在のスタックフレームのベースアドレスを新しい`BP`として設定します（`LEAQ (autoffset - bpsize)(SP), BP`）。
            *   これにより、標準的なBPチェーンが確立されます。
        *   **スタックフレームオフセットの調整**: ローカル変数や引数へのアクセスオフセットが、BP保存のために確保されたスペースを考慮して調整されます。
        *   **関数エピローグの変更**: 各関数のエピローグに、保存された`BP`をスタックから復元するコードが追加されます（`MOVQ (autoffset - bpsize)(SP), BP`）。

3.  **Goランタイム (`runtime`) の変更**:
    *   **`gobuf`構造体の拡張**: `src/runtime/runtime2.go`の`gobuf`構造体に`bp uintptr`フィールドが追加されます。`gobuf`はゴルーチンのコンテキスト（スタックポインタ、プログラムカウンタなど）を保存するために使用されます。これにより、プリエンプション時などにBPレジスタの値を保存・復元できるようになります。
    *   **アセンブリコードの変更**: `src/runtime/asm_amd64.s`では、`runtime·gosave`、`runtime·gogo`、`runtime·mcall`、`runtime·morestack`などのアセンブリ関数が変更され、`gobuf`構造体の新しい`bp`フィールドに`BP`レジスタの値を保存・復元するようにします。これは、ゴルーチンの切り替えやスタックの切り替え時にBPのコンテキストが正しく維持されるようにするために不可欠です。
    *   **スタックアンワインドの調整**: `src/runtime/traceback.go`では、スタックトレースを生成する際に、`framepointer_enabled`が有効な場合に保存されたBPのスペースを考慮してスタックフレームのサイズを調整するように変更されます。これにより、Goランタイム自身のスタックアンワインドメカニズムが、BPが保存されている場合でも正しく機能するようになります。
    *   **スタック移動時のBP調整**: `src/runtime/stack1.go`の`adjustframe`関数が変更され、スタックが移動する際に、保存されたBPの値も新しいスタックアドレスに合わせて調整されるようにします。これは、Goの動的なスタック管理において、BPチェーンの整合性を維持するために重要です。
    *   **`framepointer_enabled`のキャッシュ**: `src/runtime/proc1.go`と`src/runtime/stack1.go`で、`framepointer_enabled`というグローバル変数が追加され、`haveexperiment("framepointer")`の結果をキャッシュするようにします。これにより、ランタイムがこの実験が有効かどうかを効率的にチェックできるようになります。
    *   **CGOコールバックの調整**: `src/runtime/cgocall.go`では、CGOコールバックのスタックフレームの計算が、`framepointer_enabled`の場合に保存されたBPのスペースを考慮するように調整されます。

この変更は、Goのツールチェインの複数の層にわたる協調作業を必要とします。コンパイラはBPを予約し、リンカはBPを保存・復元するコードを生成し、ランタイムはBPのコンテキストを管理し、スタック操作時にBPチェーンの整合性を維持します。これにより、Goの内部動作に影響を与えることなく、外部ツールがGoのスタックをより容易に理解できるようになります。

## コアとなるコードの解説

上記の変更箇所は、Goの`amd64`ツールチェインがベースポインタを保存し、外部プロファイリングツールがGoのスタックを正確にアンワインドできるようにするための、多層的なアプローチを示しています。

*   **`src/liblink/obj6.c`の変更**:
    *   これは、Goの関数がどのように機械語に変換されるかの核心部分に触れています。`preprocess`関数は、Goのソースコードから生成された中間表現（`Prog`）を処理し、最終的な機械語命令を生成する前に、スタックフレームのレイアウトやレジスタの使用方法を決定します。
    *   `bpsize`変数の導入と、`autoffset`（自動変数領域のオフセット）への`bpsize`の加算は、各関数呼び出しフレームにベースポインタを保存するための追加のスペースを確保していることを意味します。
    *   `AMOVQ`（Move Quadword）と`ALEAQ`（Load Effective Address Quadword）命令の追加は、標準的な関数プロローグの動作を模倣しています。
        *   `MOVQ BP, (autoffset - bpsize)(SP)`: 呼び出し元の`BP`レジスタの値を、現在のスタックポインタ（`SP`）から`autoffset - bpsize`のオフセットに保存します。これは、新しいスタックフレームの開始位置に、呼び出し元のフレームポインタをプッシュする操作に相当します。
        *   `LEAQ (autoffset - bpsize)(SP), BP`: 現在のスタックポインタから`autoffset - bpsize`のオフセットにあるアドレスを計算し、そのアドレスを新しい`BP`レジスタの値として設定します。これにより、`BP`が現在のスタックフレームのベースを指すようになります。
    *   エピローグでの`MOVQ (autoffset - bpsize)(SP), BP`は、関数がリターンする前に保存された`BP`を復元し、呼び出し元のコンテキストに戻る準備をします。
    *   `deltasp - bpsize`によるオフセットの調整は、ローカル変数や引数へのアクセスが、BP保存のために確保された新しいスタックレイアウトに適合するように行われます。

*   **`src/runtime/asm_amd64.s`の変更**:
    *   Goランタイムは、ゴルーチンのスケジューリングとコンテキスト切り替えをアセンブリレベルで直接管理します。`gobuf`構造体は、ゴルーチンがプリエンプションされたり、別のゴルーチンに切り替わったりする際に、その状態（プログラムカウンタ、スタックポインタなど）を保存するためのものです。
    *   `MOVQ BP, gobuf_bp(AX)`のような命令の追加は、ゴルーチンの状態を保存する際に、`BP`レジスタの現在の値も`gobuf`の新しい`bp`フィールドに保存することを意味します。
    *   同様に、`MOVQ gobuf_bp(BX), BP`は、ゴルーチンが再開される際に、保存された`BP`の値を`BP`レジスタに復元することを意味します。
    *   これらの変更により、`GOEXPERIMENT=framepointer`が有効な場合、ゴルーチンの切り替えを跨いで`BP`チェーンの整合性が維持されるようになります。

*   **`src/runtime/runtime2.go`の変更**:
    *   `gobuf`構造体への`bp uintptr`フィールドの追加は、Goランタイムがベースポインタの値をゴルーチンコンテキストの一部として明示的に管理する必要があることを示しています。`uintptr`型は、ポインタまたはアドレスを保持できる符号なし整数型であり、`BP`レジスタの値を格納するのに適しています。

*   **`src/runtime/stack1.go`の変更**:
    *   Goのスタックは動的に移動する可能性があるため、スタック移動が発生した際に、スタック上のポインタ（ローカル変数や引数だけでなく、保存されたBPも含む）が新しいアドレスに正しく調整される必要があります。
    *   `adjustframe`関数内の変更は、`framepointer_enabled`が有効で、かつBPが保存されていると判断された場合に、その保存されたBPのポインタも`adjustpointer`関数によって調整されることを保証します。これにより、スタック移動後もBPチェーンが有効なままになります。

*   **`src/runtime/traceback.go`の変更**:
    *   Goランタイムは、独自のスタックトレース生成メカニズムを持っています。`gentraceback`関数は、このプロセスの中核です。
    *   `frame.varp -= ptrSize`の追加は、`framepointer_enabled`が有効な場合に、スタックフレームの変数領域の開始位置を計算する際に、保存されたBPのサイズ（`ptrSize`、通常は8バイト）を考慮に入れることを意味します。これにより、Goランタイム自身のスタックアンワインドが、BPが保存されている場合でも、ローカル変数や引数の位置を正確に特定できるようになります。

これらの変更は、Goのコンパイラ、リンカ、ランタイムが連携して、Goのパフォーマンス特性を損なうことなく、外部プロファイリングツールとの互換性を実現するためのものです。`GOEXPERIMENT`というメカニズムを通じて、この機能はオプトインであり、デフォルトではGoの従来の最適化された動作が維持されます。

# [インデックス 19760] ファイルの概要

このコミットは、Goランタイムにおける `runtime.NumGoroutine` 関数のパフォーマンス改善を目的としています。具体的には、既存の実装がすべてのゴルーチンを走査していたために発生していた性能上の課題を解決し、より高速にゴルーチン数を取得できるように変更されました。

## 変更の背景

Go言語の `runtime.NumGoroutine()` 関数は、現在実行中のゴルーチンの総数を返します。この関数は、アプリケーションの監視やデバッグにおいて、並行処理の状況を把握するために利用されます。

このコミット以前の `runtime.NumGoroutine()` の実装は、内部的にすべてのゴルーチンを格納している `allg` というグローバルなリストを走査することでゴルーチンの数を数えていました。ゴルーチンの数がN個ある場合、この走査はO(N)の計算量を持つため、ゴルーチンの数が非常に多くなると、この関数の呼び出し自体が性能ボトルネックになる可能性がありました。特に、この関数が頻繁に呼び出されるようなシナリオでは、その影響は顕著になります。

コミットメッセージにある「Resolves TODO for not walking all goroutines in NumGoroutines.」という記述は、開発者がこの性能課題を認識しており、将来的な改善点としてマークしていたことを示しています。このコミットは、そのTODO項目に対する具体的な解決策を提供し、`runtime.NumGoroutine()` の内部的なパフォーマンスを向上させることを目的としています。

また、この変更は `nacl-amd64p32` ビルド環境で「unaligned stack size」エラーを引き起こすという副作用がありました（Go CL 107290044の議論より）。これは、この変更が既存の潜在的なバグを露呈させた可能性があり、Issue 8379として別途追跡されました。このことは、ランタイムの低レベルな変更が、予期せぬ形で他のシステムに影響を与える可能性があることを示しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**:
    Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数KB程度のスタックサイズで開始し、必要に応じて動的に伸縮します。`go` キーワードを使って関数を呼び出すことで新しいゴルーチンが生成されます。

2.  **Goスケジューラ (GMPモデル)**:
    Goランタイムは、ゴルーチンをOSスレッド上で効率的に実行するために、GMPモデルと呼ばれる独自のスケジューラを使用します。
    *   **G (Goroutine)**: 上述のゴルーチンそのものです。
    *   **M (Machine)**: OSスレッドを表します。Goコードやランタイムコード、システムコールを実行する実際のOSスレッドです。
    *   **P (Processor)**: 論理プロセッサを表します。MがGoコードを実行するために必要なコンテキスト（リソース）であり、ローカルな実行キュー（run queue）を持ち、実行可能なゴルーチンを保持します。`GOMAXPROCS` 環境変数によって数が決まり、通常はCPUコア数に設定されます。MはPと関連付けられて初めてGoコードを実行できます。

3.  **`allg` リスト**:
    Goランタイムが内部的に管理する、これまでに生成されたすべてのゴルーチン（アクティブなもの、終了したもの、フリーリストにあるものなど）を追跡するためのグローバルなリストです。

4.  **フリーリスト (Free List)**:
    Goランタイムは、ゴルーチンの生成と破棄のオーバーヘッドを削減するために、終了したゴルーチンをすぐに解放せず、再利用可能なゴルーチンのプール（フリーリスト）に保持します。新しいゴルーチンが必要になった場合、まずこのフリーリストから取得しようとします。

5.  **`runtime.NumGoroutine()`**:
    Goプログラムから呼び出せる関数で、現在アクティブなゴルーチンの数を返します。

## 技術的詳細

このコミットの核心は、`runtime.NumGoroutine()` がゴルーチン数を計算する方法を、O(N)の全走査から、より効率的な定数時間に近い計算に置き換えることです。

変更前は、`runtime.gcount` 関数（`runtime.NumGoroutine` の内部実装）が `allg` リストをループし、各ゴルーチンのステータス（`Grunnable`, `Grunning`, `Gsyscall`, `Gwaiting` など）をチェックしてアクティブなゴルーチンを数えていました。これは、ゴルーチンの総数が増えるにつれて線形に時間がかかる処理でした。

変更後は、以下の新しいアプローチが採用されました。

1.  **`runtime·sched.ngfree` の導入**:
    `runtime.sched` 構造体（グローバルなスケジューラの状態を管理する）に `ngfree` という新しいフィールドが追加されました。これは、グローバルなフリーリストにあるゴルーチンの総数を追跡します。

2.  **`gfput` と `gfpurge` で `ngfree` をインクリメント**:
    *   `gfput(P *p, G *gp)`: Pのローカルなフリーリストからゴルーチンをグローバルなフリーリストに移動する際に呼び出されます。この関数内で `runtime·sched.ngfree` がインクリメントされ、グローバルなフリーゴルーチン数が増加します。
    *   `gfpurge(P *p)`: Pのローカルなフリーリストをグローバルなフリーリストにパージ（一掃）する際に呼び出されます。この関数内でも `runtime·sched.ngfree` がインクリメントされます。

3.  **`gfree` で `ngfree` をデクリメント**:
    *   `gfree(P *p)`: Pが新しいゴルーチンを必要とし、グローバルなフリーリストからゴルーチンを取得する際に呼び出されます。この関数内で `runtime·sched.ngfree` がデクリメントされ、グローバルなフリーゴルーチン数が減少します。

4.  **`runtime·gcount` の計算ロジックの変更**:
    新しい `runtime·gcount` 関数は、以下の計算式でゴルーチン数を推定します。

    `n = runtime·allglen - runtime·sched.ngfree - sum(p->gfreecnt for all P)`

    *   `runtime·allglen`: これまでに生成されたすべてのゴルーチンの総数（`allg` リストの長さ）。
    *   `runtime·sched.ngfree`: グローバルなフリーリストにあるゴルーチンの数。
    *   `p->gfreecnt`: 各Pのローカルなフリーリストにあるゴルーチンの数。

    この計算は、`allglen` からフリーリストにあるゴルーチン（グローバルとローカルの両方）の数を引くことで、現在アクティブなゴルーチンの数を推定します。これにより、すべてのゴルーチンを走査することなく、ゴルーチン数をほぼ定数時間で取得できるようになります。

    ただし、コミットのコードにもコメントされているように、`allglen`、`ngfree`、`p->gfreecnt` といった変数は並行して変更される可能性があるため、結果は厳密には一貫性がない場合があります。しかし、少なくとも現在のゴルーチンは実行中であるため、結果が1未満になる場合は1に補正されます。これは、正確性よりもパフォーマンスを優先した設計判断です。

## コアとなるコードの解説

1.  **`struct Sched` への `ngfree` の追加**:
    `src/pkg/runtime/proc.c` の `struct Sched` 定義に `int32 ngfree;` が追加されました。これは、Goランタイム全体で管理されるフリーゴルーチンの総数を保持するためのカウンタです。

2.  **`gfput` 関数における `ngfree` のインクリメント**:
    `gfput` は、Pのローカルなフリーリストからゴルーチンをグローバルなフリーリストに移動させる際に呼び出されます。このとき、グローバルなフリーリストにゴルーチンが追加されるため、`runtime·sched.ngfree++` によってカウンタがインクリメントされます。

3.  **`gfree` 関数における `ngfree` のデクリメント**:
    `gfree` は、新しいゴルーチンが必要になった際に、グローバルなフリーリストからゴルーチンを取得する際に呼び出されます。ゴルーチンがフリーリストから取り出されるため、`runtime·sched.ngfree--` によってカウンタがデクリメントされます。

4.  **`gfpurge` 関数における `ngfree` のインクリメント**:
    `gfpurge` は、Pのローカルなフリーリストにあるゴルーチンをすべてグローバルなフリーリストに移動させる際に呼び出されます。この際も、グローバルなフリーリストにゴルーチンが追加されるため、`runtime·sched.ngfree++` によってカウンタがインクリメントされます。

5.  **`runtime·gcount` 関数のロジック変更**:
    この関数は `runtime.NumGoroutine()` の実体です。
    *   変更前は、`runtime·allg` というグローバルな配列をループし、各ゴルーチンのステータスをチェックしてアクティブなゴルーチンを数えていました。これはゴルーチンの総数に比例する時間（O(N)）がかかる処理でした。
    *   変更後は、`n = runtime·allglen - runtime·sched.ngfree;` という計算で、まずこれまでに生成されたゴルーチンの総数 (`runtime·allglen`) から、グローバルなフリーリストにあるゴルーチンの数 (`runtime·sched.ngfree`) を引きます。
    *   さらに、`for(pp=runtime·allp; p=*pp; pp--) n -= p->gfreecnt;` のループで、各P（プロセッサ）が持つローカルなフリーリストにあるゴルーチンの数 (`p->gfreecnt`) を引きます。
    *   これにより、`allglen` から「フリー状態のゴルーチン」の総数を差し引くことで、「アクティブなゴルーチン」の数を効率的に推定します。
    *   最後に `if(n < 1) n = 1;` という行が追加され、計算結果が1未満になった場合でも、少なくとも現在のゴルーチンは実行中であるため、結果を1に補正します。これは、並行処理によるカウンタの不整合を考慮したものです。

この変更により、`runtime.NumGoroutine()` は、すべてのゴルーチンを走査することなく、グローバルおよびローカルのフリーリストのカウンタを利用して、はるかに高速にゴルーチン数を取得できるようになりました。

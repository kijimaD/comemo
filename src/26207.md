# [インデックス 26207] ファイルの概要

このコミットは、Goランタイムにおける`SIGCONT`シグナルのハンドリング方法を変更するものです。具体的には、`SIGCONT`シグナルがデフォルトで`os/signal`パッケージの`signal.Notify`関数を通じて捕捉可能になるように、Goランタイムのシグナルテーブル設定を更新しています。これにより、Goプログラムは`SIGCONT`シグナルをより柔軟に処理できるようになります。

## 変更の背景

この変更以前、Goランタイムは`SIGCONT`シグナルに対して特別なハンドリングを設定していませんでした。これは、多くのUnix系システムにおいて`SIGCONT`がプロセスを停止状態から再開させるためのシグナルであり、通常はアプリケーションレベルで直接処理する必要がないためです。しかし、特定のユースケースでは、Goプログラムが`SIGCONT`シグナルを受け取ったことを検知し、それに応じたカスタムロジックを実行したい場合があります。

Goの`os/signal`パッケージは、`signal.Notify`関数を提供しており、これによりプログラムは特定のシグナルを捕捉し、チャネルを通じて通知を受け取ることができます。しかし、`SIGCONT`がGoランタイムのシグナルテーブルで適切に設定されていない場合、`signal.Notify`を使用しても`SIGCONT`を捕捉することができませんでした。

このコミットは、この制限を解消し、Goプログラムが`signal.Notify`を使って`SIGCONT`を捕捉できるようにすることを目的としています。これにより、例えば、バックグラウンドで動作するGoアプリケーションが`SIGCONT`を受け取った際に、特定の状態をリセットしたり、ログを記録したりといった、より高度なシグナルハンドリングが可能になります。コミットメッセージにある「Fixes #8953」は、この問題がGoのIssueトラッカーで報告されていたことを示唆しています。

## 前提知識の解説

### シグナル (Signals)

Unix系オペレーティングシステムにおいて、シグナルはプロセスに対して非同期にイベントを通知するソフトウェア割り込みの一種です。シグナルは、キーボードからの入力（例: Ctrl+Cによる`SIGINT`）、エラー条件（例: ゼロ除算による`SIGFPE`）、または他のプロセスからの明示的な要求（例: `kill`コマンドによる`SIGTERM`）など、様々な原因によって生成されます。プロセスはシグナルを受け取ると、デフォルトの動作を実行するか、カスタムのシグナルハンドラを呼び出すか、シグナルを無視することができます。

### SIGCONT シグナル

`SIGCONT` (Signal Continue) は、停止状態にあるプロセスを再開させるためのシグナルです。通常、`SIGSTOP`、`SIGTSTP`、`SIGTTIN`、`SIGTTOU`などのシグナルによってプロセスが停止された後に、そのプロセスを再び実行状態に戻すために使用されます。例えば、シェルで`Ctrl+Z`を押してプロセスを停止（`SIGTSTP`）した後、`fg`コマンドや`bg`コマンドでプロセスを再開する際に`SIGCONT`が送られます。`SIGCONT`のデフォルト動作は、プロセスを停止状態から再開させることです。

### Goの `os/signal` パッケージ

Go言語の標準ライブラリである`os/signal`パッケージは、Goプログラムがオペレーティングシステムからのシグナルを処理するための機能を提供します。
- `signal.Notify(c chan<- os.Signal, sig ...os.Signal)`: 指定されたシグナルを捕捉し、それらをチャネル`c`に送信するようにGoランタイムに指示します。これにより、プログラムはシグナルを同期的に処理できます。
- `signal.Stop(c chan<- os.Signal)`: `signal.Notify`によって設定されたシグナルハンドリングを停止します。

### Goランタイムのシグナルハンドリングフラグ (`_SigNotify`, `_SigDefault`)

Goランタイム内部では、各シグナルに対してどのように振る舞うかを定義するシグナルテーブル（`sigtable`）が存在します。このテーブルのエントリは、シグナルの種類と、そのシグナルに対するGoランタイムの動作を制御するフラグの組み合わせで構成されます。

- `_SigNotify`: このフラグが設定されているシグナルは、`os/signal`パッケージの`signal.Notify`関数を通じてGoプログラムが捕捉できるようになります。このフラグがない場合、`signal.Notify`を呼び出してもそのシグナルは捕捉されません。
- `_SigDefault`: このフラグが設定されているシグナルは、Goランタイムが特別なハンドリングを行わない限り、オペレーティングシステムが定義するデフォルトの動作（例: `SIGTERM`ならプロセス終了、`SIGCONT`ならプロセス再開）を実行します。

これらのフラグはビットマスクとして組み合わせて使用され、シグナルの挙動を細かく制御します。例えば、`_SigNotify + _SigDefault`は、「`signal.Notify`で捕捉可能にしつつ、デフォルトのOS動作も維持する」という意味になります。

## 技術的詳細

このコミットの核心は、Goランタイムが内部的に保持するシグナルテーブル（`sigtable`）の`SIGCONT`エントリの変更です。以前は、多くのUnix系OSにおいて`SIGCONT`のエントリは`0`（またはそれに相当する値）に設定されており、これはGoランタイムが`SIGCONT`に対して特別な処理を行わず、`signal.Notify`でも捕捉できないことを意味していました。

変更後、`SIGCONT`のエントリは`_SigNotify + _SigDefault`に設定されます。
- `_SigNotify`が追加されたことで、Goプログラムは`os/signal`パッケージの`signal.Notify`関数を使用して`SIGCONT`シグナルを捕捉し、カスタムの処理ロジックを実行できるようになります。
- `_SigDefault`が維持されているため、`signal.Notify`で`SIGCONT`を捕捉するハンドラが登録されていない場合や、ハンドラがシグナルを処理し終えた後も、`SIGCONT`の本来のデフォルト動作（停止したプロセスの再開）が引き続き機能します。これは、`SIGCONT`の基本的な役割を損なわないための重要な側面です。

この変更は、`darwin` (macOS), `dragonfly`, `freebsd`, `nacl`, `netbsd`, `openbsd`, `solaris`, および`linux` (genericとmips64x) など、複数のオペレーティングシステム向けの`src/runtime/signal_*.go`および`src/runtime/sigtab_linux_*.go`ファイルにわたって適用されています。これは、Goがクロスプラットフォームな言語であるため、各OSのシグナルハンドリングの差異を吸収しつつ、一貫した動作を提供するために必要な対応です。

新しい`TestSIGCONT`テストケースが`src/os/signal/signal_test.go`に追加されており、この変更が正しく機能することを確認しています。このテストでは、`signal.Notify`で`SIGCONT`を登録し、`syscall.Kill`で自身に`SIGCONT`を送信し、チャネルでシグナルが受信されることを検証しています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主にGoランタイムのシグナルテーブル定義ファイルにあります。以下に代表的な変更箇所を示します。

**`src/os/signal/signal_test.go` に追加されたテストケース:**

```go
// Test that SIGCONT works (issue 8953).
func TestSIGCONT(t *testing.T) {
	c := make(chan os.Signal, 1)
	Notify(c, syscall.SIGCONT)
	defer Stop(c)
	syscall.Kill(syscall.Getpid(), syscall.SIGCONT)
	waitSig(t, c, syscall.SIGCONT)
}
```

## コアとなるコードの解説

### `TestSIGCONT` テストケース

このテスト関数は、`SIGCONT`シグナルに対するGoランタイムの新しい動作を検証します。
1.  `c := make(chan os.Signal, 1)`: シグナルを受信するためのバッファ付きチャネルを作成します。バッファサイズが1であるため、シグナルが送信されてもすぐにブロックされません。
2.  `Notify(c, syscall.SIGCONT)`: `os/signal`パッケージの`Notify`関数を呼び出し、`syscall.SIGCONT`シグナルが`c`チャネルに送信されるようにGoランタイムに登録します。
3.  `defer Stop(c)`: テスト関数の終了時に`Stop`を呼び出し、シグナルハンドリングの登録を解除します。これはクリーンアップのために重要です。
4.  `syscall.Kill(syscall.Getpid(), syscall.SIGCONT)`: 現在実行中のプロセス（テスト自身）に対して`SIGCONT`シグナルを送信します。
5.  `waitSig(t, c, syscall.SIGCONT)`: `c`チャネルから`syscall.SIGCONT`が受信されるのを待ちます。もしシグナルが期待通りに受信されなければ、テストは失敗します。

このテストは、`SIGCONT`が`signal.Notify`によって正しく捕捉されるようになったことを明確に示しています。

### `sigtable` の変更

`src/runtime/signal_darwin.go`などのファイルに見られる`sigtable`の変更は、Goランタイムが`SIGCONT`シグナルをどのように扱うかを直接定義しています。
- 変更前: `/* 19 */ {0, "SIGCONT: continue after stop"}`
    - `0`という値は、Goランタイムがこのシグナルに対して特別な処理を行わず、`signal.Notify`でも捕捉できないことを意味していました。OSのデフォルト動作（プロセス再開）は発生しますが、Goプログラムからはその発生を検知できませんでした。
- 変更後: `/* 19 */ {_SigNotify + _SigDefault, "SIGCONT: continue after stop"}`
    - `_SigNotify`フラグが追加されたことで、`signal.Notify`を介してGoプログラムが`SIGCONT`を捕捉できるようになりました。
    - `_SigDefault`フラグが維持されているため、`signal.Notify`でハンドラが登録されていない場合や、ハンドラがシグナルを処理した後も、OSによる`SIGCONT`のデフォルト動作（停止したプロセスの再開）が引き続き適用されます。これにより、`SIGCONT`の本来の意図された機能が損なわれることはありません。

この変更により、Goプログラムは`SIGCONT`シグナルを検知し、それに応じたカスタムロジックを実行する柔軟性を獲得しました。

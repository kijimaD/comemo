# [インデックス 22939] ファイルの概要

このコミットは、Goコンパイラのリンカ部分、特に`cmd/7l`（ARM64アーキテクチャ向けのリンカ）、`cmd/internal/ld`（リンカの内部パッケージ）、および`cmd/internal/obj`（オブジェクトファイルの内部パッケージ）にわたる変更を含んでいます。主な目的は、Darwin/ARM64（macOS/iOSのARM64アーキテクチャ）環境での外部リンキングをサポートすることです。

変更されたファイルは以下の通りです。

-   `src/cmd/7l/asm.go`: ARM64アセンブリとMach-Oリロケーション処理に関する主要な変更が含まれています。
-   `src/cmd/7l/obj.go`: リンカの初期化とDarwin/ARM64固有の設定に関する変更が含まれています。
-   `src/cmd/internal/ld/data.go`: データセクションのリロケーション処理に関する変更が含まれています。
-   `src/cmd/internal/ld/lib.go`: ライブラリのロードとリンキングモードに関する変更が含まれています。
-   `src/cmd/internal/ld/macho.go`: Mach-Oファイルフォーマットの構造と処理に関する変更が含まれています。
-   `src/cmd/internal/ld/sym.go`: シンボル処理とTLSオフセットに関する変更が含まれています。
-   `src/cmd/internal/obj/sym.go`: オブジェクトファイルのシンボル処理とTLSオフセットに関する変更が含まれています。

これらの変更は、GoプログラムがDarwin/ARM64上で外部リンカ（`ld64`など）を使用してビルドされる際の互換性と機能性を向上させることを目的としています。

## 変更の背景

このコミットの主な背景は、Go言語がDarwin/ARM64アーキテクチャ（主にiOSデバイス）上で外部リンキングをサポートする必要があったことです。Goは通常、独自の内部リンカを使用して実行可能ファイルを生成しますが、Cgo（GoとC言語の相互運用機能）を使用する場合や、特定のシステムライブラリにリンクする必要がある場合には、システムの外部リンカ（macOS/iOSでは`ld64`）を使用する必要があります。

コミットメッセージには「ld64 has a bug handling MACHO_ARM64_RELOC_UNSIGNED with !extern relocation」という記述があり、これは`ld64`リンカに特定のバグが存在し、それがDarwin/ARM64上でのGoの外部リンキングを妨げていたことを示唆しています。このバグは、外部リロケーション（`!extern`）を伴う`MACHO_ARM64_RELOC_UNSIGNED`タイプのリロケーションを`ld64`が正しく処理できないというものです。

このコミットは、この`ld64`のバグを回避しつつ、Darwin/ARM64環境での外部リンキングを可能にするための修正を導入しています。これにより、GoプログラムがiOSなどのARM64ベースのAppleプラットフォームでCgoを利用したり、システムライブラリと連携したりする際の互換性が向上します。

## 前提知識の解説

### Goのリンキングモード（内部リンキング vs. 外部リンキング）

Goコンパイラは、通常、独自のリンカ（内部リンカ）を使用して、Goのソースコードから直接実行可能ファイルを生成します。これにより、Goはクロスコンパイルが容易であり、外部のツールチェーンに依存しないという利点があります。

しかし、GoプログラムがC言語で書かれたコード（Cgo経由）や、システムにインストールされている共有ライブラリ（例: macOSのFoundationフレームワーク）を使用する場合、Goの内部リンカだけでは対応できないことがあります。このような場合、Goはシステムのリンカ（macOS/iOSでは`ld64`）を呼び出してリンク処理を行わせます。これを「外部リンキング」と呼びます。

-   **内部リンキング**: Goのリンカがすべてのリンク処理を行う。
-   **外部リンキング**: システムのリンカがリンク処理を行う。Goのリンカは、システムのリンカが処理できるように中間ファイルを生成する。

### Darwin/ARM64アーキテクチャ

DarwinはAppleのオペレーティングシステム（macOS, iOSなど）の基盤となるUNIX系OSの名称です。ARM64は、Apple SiliconチップやiPhone/iPadなどに搭載されている64ビットARMプロセッサアーキテクチャを指します。この組み合わせは、Appleデバイスにおける主要な実行環境です。

### Mach-Oファイルフォーマット

Mach-O（Mach Object）は、macOS、iOS、watchOS、tvOSなどのAppleのオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、共有ライブラリ、およびコアダンプのファイルフォーマットです。ELF（Executable and Linkable Format）がLinuxやUnix系システムで広く使われているのと同様に、Mach-OはAppleプラットフォームの標準です。

Mach-Oファイルは、ヘッダ、ロードコマンド、セグメント、セクション、シンボルテーブル、リロケーション情報などから構成されます。

### リロケーション

リロケーション（Relocation）とは、コンパイル時にアドレスが確定できないシンボル（変数や関数のアドレスなど）について、リンク時に正しいアドレスを埋め込む処理のことです。プログラムがメモリ上のどこにロードされるか、また他のライブラリがどこに配置されるかによって、これらのアドレスは変化するため、リンカが最終的なアドレスを解決する必要があります。

Mach-Oファイルには、様々な種類のリロケーションエントリが存在します。このコミットで言及されているARM64向けのリロケーションタイプには以下のようなものがあります。

-   `MACHO_ARM64_RELOC_UNSIGNED`: 符号なしリロケーション。絶対アドレスを直接埋め込む場合などに使用されます。
-   `MACHO_ARM64_RELOC_BRANCH26`: 26ビットのPC相対オフセットを持つ分岐命令のリロケーション。
-   `MACHO_ARM64_RELOC_PAGE21`: 21ビットのPC相対ページオフセットを持つリロケーション。
-   `MACHO_ARM64_RELOC_PAGEOFF12`: 12ビットのページ内オフセットを持つリロケーション。
-   `MACHO_ARM64_RELOC_ADDEND`: 加算値（アデンド）を伴うリロケーション。

### `ld64`リンカとそのバグ

`ld64`は、Appleが提供するリンカであり、macOSやiOSのアプリケーションビルドプロセスで使用されます。このコミットで言及されているバグは、`ld64`が`MACHO_ARM64_RELOC_UNSIGNED`タイプのリロケーションを、特に外部シンボル（`!extern`）に対して正しく処理できないというものです。これは、Goのリンカが生成するリロケーション情報と`ld64`の期待する形式との間に不整合があったことを示唆しています。

### DWARFデバッグ情報

DWARF（Debugging With Attributed Record Formats）は、ソースレベルデバッガがプログラムの実行をデバッグするために必要な情報（変数名、型情報、ソースコードの行番号と実行可能コードのアドレスのマッピングなど）を格納するための標準フォーマットです。

### Thread-Local Storage (TLS)

TLSは、各スレッドが独自のデータコピーを持つことができるストレージメカニズムです。Goランタイムは、ゴルーチンごとのスタック情報やスケジューラ関連のデータなど、スレッドローカルな情報を格納するためにTLSを使用することがあります。TLSへのアクセス方法は、OSやアーキテクチャによって異なります。

## 技術的詳細

このコミットは、Darwin/ARM64環境での外部リンキングを可能にするために、Goのリンカ（`cmd/7l`および`cmd/internal/ld`）に複数の重要な変更を加えています。

1.  **`ld64`バグの回避策 (`src/cmd/7l/asm.go`の`machoreloc1`関数)**:
    *   `ld64`が`MACHO_ARM64_RELOC_UNSIGNED`と外部リロケーションを組み合わせた場合にバグがあるため、Goのリンカは`R_ADDR`タイプのリロケーションに対して、外部シンボル（`rs.Type == ld.SHOSTOBJ`）の場合に`MACHO_ARM64_RELOC_UNSIGNED`を使用しないように変更されました。代わりに、`rs.Dynid`（ダイナミックシンボルID）を使用して外部リロケーションとしてマークされます。
    *   `R_CALLARM64`（分岐命令）と`R_ADDRARM64`（アドレスリロケーション）についても、Mach-Oの特定のリロケーションタイプ（`MACHO_ARM64_RELOC_BRANCH26`, `MACHO_ARM64_RELOC_PAGE21`, `MACHO_ARM64_RELOC_PAGEOFF12`, `MACHO_ARM64_RELOC_ADDEND`）を適切に生成するように修正されています。特に`R_ADDRARM64`では、ページオフセットとページアドレスのリロケーションを2つのエントリとして生成し、必要に応じてアデンド（加算値）も追加するロジックが導入されています。
    *   `ld64`のバグにより、`BR26`リロケーションに非ゼロのアデンドがあるとリンクが失敗するため、`R_CALLARM64`ではアデンドがゼロであることを確認するチェックが追加されています。

2.  **外部リンキングの強制 (`src/cmd/7l/obj.go`の`archinit`関数)**:
    *   Darwin/ARM64（`ld.HEADTYPE == ld.Hdarwin`）の場合、Goのリンキングモードが強制的に`ld.LinkExternal`に設定されるようになりました。これは、内部リンカではDarwin/ARM64の複雑なリロケーションやシステムライブラリのリンクを完全にサポートするのが困難であるためです。

3.  **`ld64`バグの回避策 (`src/cmd/internal/ld/data.go`の`relocsym`関数)**:
    *   `ld64`がARM64で、シンボルテーブルに存在するアドレス（`dynid >= 0`）またはシンボル内に存在するアドレスを指す場合に、オフセット`o`を2回加算してしまうバグがあるため、`R_ADDR`リロケーションにおいて、`Thearch.Thechar == '7'`（ARM64）かつ`rs.Dynid < 0`（外部シンボルではない）の場合に`Symaddr(rs)`を加算しないように変更されました。これにより、常に外部リロケーションを使用し、`ld64`のバグを回避します。

4.  **Mach-Oセクションの配置 (`src/cmd/internal/ld/macho.go`の`machoshbits`関数)**:
    *   Darwin/ARM64では、`__TEXT`セグメント内の絶対リロケーションが禁止されているため、実行可能ではないセクション（`sect.Rwx&1 == 0`）は`__DATA`セグメントに配置されるように変更されました。これにより、リンカエラーを防ぎます。

5.  **Mach-Oヘッダとスレッド情報 (`src/cmd/internal/ld/macho.go`の`Asmbmacho`関数)**:
    *   Mach-OヘッダのCPUタイプとして`MACHO_CPU_ARM64`と`MACHO_SUBCPU_ARM64_ALL`が追加され、ARM64アーキテクチャが正しく識別されるようになりました。
    *   Unixスレッドのロードコマンドにおいて、ARM64（`Thearch.Thechar == '7'`）向けの新しいスレッドタイプ（`thread type 6`）とワードカウント（`68`）が設定され、開始PC（プログラムカウンタ）が正しく設定されるようになりました。

6.  **TLSオフセットの調整 (`src/cmd/internal/ld/sym.go`と`src/cmd/internal/obj/sym.go`)**:
    *   Darwin/ARM64（`case '7'`）のTLSオフセットが`0`に設定されました。これは、ARM64ではTLSへのアクセス方法が他のアーキテクチャと異なり、ダミー値で十分であるか、または特定のオフセットが不要であることを示唆しています。

7.  **DWARFデバッグ情報の無効化 (`src/cmd/7l/obj.go`の`archinit`関数と`src/cmd/7l/asm.go`の`asmb`関数)**:
    *   一時的にDarwin/ARM64でのDWARFデバッグ情報の生成が無効化されています（`ld.Debug['w'] = 1`）。これは、まだDWARFサポートが完全ではないため、または`ld64`との連携に問題があるためと考えられます。コミットメッセージには「TODO(minux): enable DWARF Support」と記載されており、将来的に有効化される予定であることが示されています。

これらの変更は、GoのリンカがMach-Oファイルフォーマットと`ld64`リンカの特性（特にバグ）を理解し、それらに適応することで、Darwin/ARM64上でのGoプログラムの外部リンキングを安定させることを目的としています。

## コアとなるコードの解説

### `machoreloc1` 関数 (`src/cmd/7l/asm.go`)

この関数は、Mach-O形式のリロケーションエントリを生成するGoリンカの重要な部分です。Darwin/ARM64の外部リンキングをサポートするために、以下の点が変更されました。

1.  **外部リロケーションの扱い**:
    *   以前は、`machoreloc1`は単に`-1`を返していました。これは、Darwin/ARM64のリロケーションが未実装であったことを意味します。
    *   変更後、`rs.Type == ld.SHOSTOBJ`（ホストオブジェクトからのシンボル）または特定のリロケーションタイプ（`R_CALLARM64`, `R_ADDRARM64`, `R_ADDR`）の場合、シンボルが外部リンキングを必要とすると判断されます。
    *   この場合、`rs.Dynid`（ダイナミックシンボルID）がリロケーションエントリのシンボルインデックスとして使用され、`1 << 27`をORすることで「外部リロケーション」フラグが設定されます。これは、`ld64`が外部シンボルを正しく解決するために必要な情報です。
    *   `ld64`のバグ回避のため、`MACHO_ARM64_RELOC_UNSIGNED`を外部リロケーションと共に使用しないという方針が取られています。

2.  **リロケーションタイプごとの処理**:
    *   **`ld.R_ADDR`**: 汎用的なアドレスリロケーション。`MACHO_ARM64_RELOC_UNSIGNED`タイプのリロケーションとしてマークされます。
    *   **`ld.R_CALLARM64`**: ARM64の分岐命令（BR26）のリロケーション。
        *   `r.Xadd != 0`の場合、`ld64`が非ゼロのアデンドを持つ`BR26`リロケーションを許可しないというバグがあるため、エラーを報告します。
        *   PC相対ビット（`1 << 24`）と`MACHO_ARM64_RELOC_BRANCH26`タイプが設定されます。
    *   **`ld.R_ADDRARM64`**: ARM64のページ相対アドレスリロケーション。
        *   このリロケーションは、`MACHO_ARM64_RELOC_PAGEOFF12`と`MACHO_ARM64_RELOC_PAGE21`の2つのリロケーションエントリを生成します。これは、ARM64の命令がアドレスを2つの部分（ページオフセットとページアドレス）に分割してエンコードするためです。
        *   `r.Xadd`（アデンド）が非ゼロの場合、さらに2つの`MACHO_ARM64_RELOC_ADDEND`エントリが生成され、アデンド情報がリンカに渡されます。これにより、リンカは最終的なアドレスを計算する際にこのアデンドを考慮できます。

3.  **リロケーションサイズの設定**:
    *   リロケーションのサイズ（1, 2, 4, 8バイト）に応じて、リロケーションエントリのビット25-26に適切な値が設定されます。

これらの変更により、GoのリンカはDarwin/ARM64上で`ld64`が期待する形式でリロケーション情報を生成できるようになり、外部リンキングが可能になりました。

### `relocsym` 関数 (`src/cmd/internal/ld/data.go`)

この関数は、シンボルに対するリロケーションを処理するGoリンカの汎用的な部分です。Darwin/ARM64の特定の`ld64`バグを回避するために、以下の変更が加えられました。

1.  **`ld64`の二重加算バグの回避**:
    *   コメントに記載されているように、`ld64`のARM64版には、`o`がシンボルテーブルに存在するアドレス（`dynid >= 0`）を指す場合、またはシンボル内に存在するアドレスを指す場合に、`o`をリロケーション値に2回加算してしまうバグがあります。
    *   このバグを回避するため、`HEADTYPE == Hdarwin`（Darwinプラットフォーム）かつ`Thearch.Thechar == '7'`（ARM64アーキテクチャ）の場合に、`rs.Dynid < 0`（外部シンボルではない）であれば、`Symaddr(rs)`（シンボルのアドレス）を`o`に加算しないように変更されました。
    *   これにより、Goのリンカは、`ld64`が二重加算しないように、常に外部リロケーションを使用し、`rs->dynid >= 0`を要求する形に調整されます。
    *   `Thearch.Thechar != '7'`（ARM64以外）の場合は、従来通り`Symaddr(rs)`が加算されます。

この修正は、`ld64`のバグによって発生する不正なアドレス計算を防ぎ、GoプログラムがDarwin/ARM64上で正しくリンクされるようにするために不可欠です。

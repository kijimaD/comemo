# [インデックス 23425] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `Transport` の挙動を改善するものです。具体的には、HTTPリクエストボディがチャンクエンコーディングで送信される際に、`bufio.Writer` によるバッファリングが原因で発生していた、リクエストボディのフラッシュ遅延の問題を解決します。これにより、特にリクエストボディがゆっくりと生成される場合に、サーバーへのデータ送信がより効率的かつタイムリーに行われるようになります。

    net/http: flush request body chunks in Transport
    
    The Transport's writer to the remote server is wrapped in a
    bufio.Writer to suppress many small writes while writing headers and
    trailers. However, when writing the request body, the buffering may get
    in the way if the request body is arriving slowly.
    
    Because the io.Copy from the Request.Body to the writer is already
    buffered, the outer bufio.Writer is unnecessary and prevents small
    Request.Body.Reads from going to the server right away. (and the
    io.Reader contract does say to return when you've got something,
    instead of blocking waiting for more). After the body is finished, the
    Transport's bufio.Writer is still used for any trailers following.
    
    A previous attempted fix for this made the chunk writer always flush
    if the underlying type was a bufio.Writer, but that is not quite
    correct. This CL instead makes it opt-in by using a private sentinel
    type (wrapping a *bufio.Writer) to the chunk writer that requests
    Flushes after each chunk body (the chunk header & chunk body are still
    buffered together into one write).

## 元コミット内容

`net/http`: Transportにおけるリクエストボディチャンクのフラッシュ

`Transport` がリモートサーバーへの書き込みに使用するライターは、ヘッダーやトレーラーの書き込み時に多数の小さな書き込みを抑制するために `bufio.Writer` でラップされています。しかし、リクエストボディの書き込み時には、リクエストボディがゆっくりと到着する場合、このバッファリングが邪魔になる可能性があります。

`Request.Body` からライターへの `io.Copy` は既にバッファリングされているため、外側の `bufio.Writer` は不要であり、小さな `Request.Body.Read` がすぐにサーバーに送信されるのを妨げます（そして `io.Reader` の契約は、さらに多くのデータを待つのではなく、何かデータがあればすぐに返すことを示唆しています）。ボディの書き込みが完了した後も、`Transport` の `bufio.Writer` は、それに続くトレーラーのために引き続き使用されます。

この問題に対する以前の修正試行では、基になる型が `bufio.Writer` であればチャンクライターが常にフラッシュするようにしていましたが、これは完全に正しいわけではありませんでした。このCL（変更リスト）では、代わりにプライベートなセンチネル型（`*bufio.Writer` をラップしたもの）をチャンクライターに渡すことで、各チャンクボディの後にフラッシュを要求するようにオプトイン方式にしています（チャンクヘッダーとチャンクボディは引き続き一緒にバッファリングされて一度に書き込まれます）。

Fixes #6574

## 変更の背景

この変更は、Goの `net/http` パッケージにおける `Transport` の動作、特にHTTPリクエストの送信メカニズムに関するパフォーマンスと応答性の問題に対処するために行われました。

HTTP/1.1では、リクエストボディの長さを事前に知ることができない場合や、ストリーミングでデータを送信したい場合に「チャンク転送エンコーディング (Chunked Transfer Encoding)」が使用されます。この方式では、ボディが複数の「チャンク」に分割され、各チャンクの前にそのサイズが記述され、最後にゼロサイズのチャンクで終了します。

`net/http.Transport` は、HTTPリクエストを実際にネットワーク経由で送信する役割を担っています。この `Transport` は、効率化のために、リモートサーバーへの書き込み操作を `bufio.Writer` でラップしています。`bufio.Writer` は、小さな書き込みを内部バッファに蓄積し、バッファがいっぱいになったときや明示的にフラッシュされたときにまとめて大きな書き込みを行うことで、システムコール（ネットワークI/O）の回数を減らし、パフォーマンスを向上させます。

しかし、この `bufio.Writer` の挙動が、チャンク転送エンコーディングを使用するリクエストボディの送信において問題を引き起こしていました。特に、リクエストボディがアプリケーションによってゆっくりと生成される場合（例：大きなファイルを少しずつ読み込んでアップロードする、リアルタイムでデータを生成してストリーミングする）、`bufio.Writer` がチャンクデータを内部に保持し続けてしまい、すぐにネットワークに送信されないという問題が発生していました。

これは、クライアント側でデータが生成されても、サーバー側ではそのデータがなかなか受信されないという遅延につながり、特に低レイテンシが求められるアプリケーションや、サーバーがクライアントからのデータ到着を待機するようなシナリオで問題となります。コミットメッセージにある `Issue 6574` は、この問題がユーザーによって報告されたことを示しています。

以前の修正試行では、基になるライターが `bufio.Writer` であれば常にフラッシュするというアプローチが取られましたが、これはヘッダーやトレーラーなど、バッファリングが望ましい部分にまで影響を与えてしまう可能性があり、適切ではありませんでした。そのため、リクエストボディのチャンク部分のみを対象に、選択的にフラッシュを行う新しいメカニズムが必要とされていました。

## 前提知識の解説

### 1. `net/http` パッケージと `Transport`
Go言語の `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。
- **`http.Client`**: HTTPリクエストを送信するための高レベルなインターフェースを提供します。
- **`http.Transport`**: `http.Client` の内部で実際にネットワーク接続を管理し、HTTPリクエストの送信やレスポンスの受信といった低レベルな処理を担当します。TCP接続の確立、TLSハンドシェイク、プロキシの利用、接続の再利用（Keep-Alive）などを扱います。

### 2. `io.Reader` と `io.Writer` インターフェース
Go言語におけるI/O操作の基本的な抽象化です。
- **`io.Reader`**: `Read(p []byte) (n int, err error)` メソッドを持つインターフェース。データを読み出す元を表します。
- **`io.Writer`**: `Write(p []byte) (n int, err error)` メソッドを持つインターフェース。データを書き込む先を表します。
これらのインターフェースは、様々なデータソース（ファイル、ネットワーク接続、メモリバッファなど）に対して統一的なI/O操作を可能にします。

### 3. `bufio.Writer`
`bufio` パッケージは、I/O操作をバッファリングすることで効率化するための機能を提供します。
- **`bufio.Writer`**: `io.Writer` をラップし、内部にバッファを持ちます。`Write` メソッドが呼び出されると、データはまずこの内部バッファに書き込まれます。バッファがいっぱいになるか、`Flush()` メソッドが明示的に呼び出されるか、または `Close()` されるまで、基になる `io.Writer` への実際の書き込みは行われません。これにより、多数の小さな書き込みがまとめて一度の大きな書き込みに変換され、システムコールやネットワークI/Oの回数が削減され、パフォーマンスが向上します。

### 4. HTTP チャンク転送エンコーディング (Chunked Transfer Encoding)
HTTP/1.1で導入された転送エンコーディングの一種です。
- **目的**: HTTPメッセージボディの長さを事前に知ることなく、動的に生成されるコンテンツを送信するために使用されます。
- **仕組み**: メッセージボディは、一連の「チャンク」に分割されます。各チャンクは、そのチャンクのサイズ（16進数表記）と、それに続くデータで構成されます。ボディの終わりは、サイズがゼロのチャンクで示されます。
- **ヘッダー**: `Transfer-Encoding: chunked` ヘッダーがメッセージに含まれます。
- **利点**: サーバーがレスポンスボディの全長を計算する前に送信を開始できるため、応答時間を短縮できます。また、クライアントがリクエストボディをストリーミングで送信する際にも利用されます。

### 5. `io.Copy`
`io` パッケージのユーティリティ関数です。
- **`io.Copy(dst io.Writer, src io.Reader) (written int64, err error)`**: `src` からデータを読み込み、それを `dst` に書き込みます。`src` がEOF（End Of File）を返すか、エラーが発生するまで処理を続けます。内部的には、適切なサイズのバッファを使用して効率的にデータを転送します。

## 技術的詳細

このコミットの核心は、`net/http.Transport` がリクエストボディを送信する際の `bufio.Writer` のバッファリング挙動を、チャンク転送エンコーディングを使用する場合にのみ選択的に変更することです。

従来の `Transport` の実装では、HTTPヘッダー、ボディ、トレーラーを含むすべての出力が、パフォーマンス最適化のために `bufio.Writer` を介して行われていました。これは、特にヘッダーのように小さな書き込みが連続する場合には非常に効果的です。しかし、リクエストボディがチャンクエンコーディングで送信され、かつそのボディがゆっくりと生成される（例：`io.Pipe` を使用してストリーミングされる）場合、`bufio.Writer` がチャンクデータを内部バッファに保持し続け、ネットワークへの実際の送信が遅延するという問題がありました。

コミットメッセージによると、`Request.Body` からの `io.Copy` は既に内部でバッファリングを行っているため、外側の `bufio.Writer` による追加のバッファリングは冗長であり、むしろ遅延の原因となっていました。`io.Reader` の契約上、データが利用可能になったらすぐに返すことが期待されるため、`bufio.Writer` がデータを保持し続けることは、この期待に反する挙動と言えます。

この問題を解決するために、コミットは以下の新しいアプローチを導入しました。

1.  **`FlushAfterChunkWriter` センチネル型の導入**:
    `src/net/http/internal/chunked.go` に `FlushAfterChunkWriter` という新しい型が定義されました。これは `*bufio.Writer` を埋め込んだ構造体であり、`io.Writer` インターフェースを満たします。この型自体は特別な `Write` メソッドを持たず、埋め込まれた `*bufio.Writer` のメソッドが使われます。この型の目的は、`NewChunkedWriter` の呼び出し元が、チャンクの書き込み後にフラッシュを要求したいという意図を伝えるための「マーカー（センチネル）」として機能することです。

2.  **`chunkedWriter.Write` での条件付きフラッシュ**:
    `src/net/http/internal/chunked.go` の `chunkedWriter.Write` メソッドが変更されました。チャンクのデータとCRLF (`\r\n`) が書き込まれた後、`cw.Wire` (基になる `io.Writer`) が `*FlushAfterChunkWriter` 型であるかどうかをチェックします。もしそうであれば、`bw.Flush()` を呼び出して、基になる `bufio.Writer` のバッファを強制的にフラッシュします。これにより、各チャンクボディが書き込まれた直後にネットワークに送信されるようになります。

3.  **`transferWriter.WriteBody` での `FlushAfterChunkWriter` の適用**:
    `src/net/http/transfer.go` の `transferWriter.WriteBody` メソッドが変更されました。ここで、リクエストボディがチャンクエンコーディングで送信される場合 (`chunked(t.TransferEncoding)`)、かつ書き込み先 (`w`) が `*bufio.Writer` であり、かつそれがレスポンスではない (`!t.IsResponse`) 場合に、`w` を `&internal.FlushAfterChunkWriter{bw}` でラップして `internal.NewChunkedWriter` に渡すようにしました。
    -   `!t.IsResponse` の条件は重要です。このフラッシュ挙動はリクエストボディにのみ適用され、レスポンスボディには適用されません。レスポンスボディの場合、サーバー側でのバッファリングは依然として望ましい場合があります。
    -   これにより、`internal.NewChunkedWriter` は、チャンク書き込み後にフラッシュが必要であることを示す `FlushAfterChunkWriter` 型のライターを受け取ることになります。

この変更により、HTTPリクエストボディがチャンクエンコーディングで送信される際に、各チャンクが書き込まれるたびに `bufio.Writer` のバッファがフラッシュされ、データがより迅速にネットワークに送信されるようになります。ヘッダーやトレーラーの書き込み時には引き続き `bufio.Writer` によるバッファリングの恩恵を受けられるため、全体的な効率を損なうことなく、特定の問題を解決しています。

## コアとなるコードの解説

### `src/net/http/internal/chunked.go` の変更

1.  **`FlushAfterChunkWriter` 型の追加**:
    ```go
    type FlushAfterChunkWriter struct {
    	*bufio.Writer
    }
    ```
    この構造体は、`*bufio.Writer` を埋め込んでいます。これにより、`FlushAfterChunkWriter` は `bufio.Writer` のすべてのメソッド（`Write`, `Flush` など）を自動的に継承します。この型の主な目的は、`chunkedWriter` に対して「このライターはチャンクの後にフラッシュされるべきだ」というシグナルを送るためのマーカーとして機能することです。

2.  **`chunkedWriter.Write` メソッドの変更**:
    ```go
    func (cw *chunkedWriter) Write(data []byte) (n int, err error) {
        // ... チャンクサイズとデータ、CRLFの書き込み ...

        if _, err = io.WriteString(cw.Wire, "\r\n"); err != nil {
            return
        }
        if bw, ok := cw.Wire.(*FlushAfterChunkWriter); ok {
            err = bw.Flush()
        }
        return
    }
    ```
    `chunkedWriter` は、チャンクデータとそれに続くCRLF (`\r\n`) を `cw.Wire` (基になる `io.Writer`) に書き込んだ後、追加のロジックを実行します。
    -   `if bw, ok := cw.Wire.(*FlushAfterChunkWriter); ok`: ここで型アサーションが行われます。`cw.Wire` が `*FlushAfterChunkWriter` 型にキャストできるかどうかをチェックします。`ok` が `true` の場合、それは `transferWriter` がこの特別なフラッシュ挙動を要求していることを意味します。
    -   `err = bw.Flush()`: `FlushAfterChunkWriter` 型であることが確認された場合、埋め込まれた `*bufio.Writer` の `Flush()` メソッドが呼び出されます。これにより、`bufio.Writer` の内部バッファに蓄積されていたデータが、基になるネットワーク接続に強制的に書き出されます。

### `src/net/http/transfer.go` の変更

1.  **`transferWriter` 構造体への `IsResponse` フィールド追加**:
    ```go
    type transferWriter struct {
        // ... 既存のフィールド ...
        IsResponse       bool
    }
    ```
    このフィールドは、`transferWriter` がリクエストを処理しているのか、それともレスポンスを処理しているのかを区別するために追加されました。リクエストボディのフラッシュ挙動は、リクエストにのみ適用されるべきであるため、この情報が必要になります。

2.  **`newTransferWriter` 関数での `IsResponse` の設定**:
    ```go
    func newTransferWriter(r interface{}) (t *transferWriter, err error) {
        // ... 既存のコード ...
        case *Response:
            t.IsResponse = true
            // ...
    }
    ```
    `newTransferWriter` が `*Response` 型の引数を受け取った場合、`t.IsResponse` を `true` に設定します。これにより、後続の処理でこれがレスポンスであることが識別されます。

3.  **`transferWriter.WriteBody` メソッドの変更**:
    ```go
    func (t *transferWriter) WriteBody(w io.Writer) error {
        // ... 既存のコード ...

    この部分が、`FlushAfterChunkWriter` を実際に適用する場所です。
    -   `if chunked(t.TransferEncoding)`: まず、転送エンコーディングがチャンク形式であるかを確認します。
    -   `if bw, ok := w.(*bufio.Writer); ok && !t.IsResponse`: 次に、基になるライター `w` が `*bufio.Writer` 型であり、かつ現在処理しているのがレスポンスではない（つまりリクエストである）ことを確認します。
    -   `w = &internal.FlushAfterChunkWriter{bw}`: 上記の条件がすべて満たされた場合、元の `*bufio.Writer` (`bw`) を `internal.FlushAfterChunkWriter` でラップし、その新しいラッパーを `w` に再代入します。この `w` が `internal.NewChunkedWriter` に渡されます。
    -   これにより、`internal.NewChunkedWriter` は、チャンク書き込み後にフラッシュが必要なことを認識し、`chunkedWriter.Write` メソッド内で `Flush()` を呼び出すようになります。

### `src/net/http/transport_test.go` の変更

-   **`logWritesConn` 型の追加**:

-   **`TestTransportFlushesBodyChunks` テストケースの追加**:
    このテストは、`io.Pipe` を使用してゆっくりとリクエストボディを生成し、`Transport` が `FlushAfterChunkWriter` を正しく使用して各チャンクをフラッシュしていることを検証します。
    -   `logWritesConn` を `Transport` の `Dial` 関数に注入し、ネットワークへの書き込みを傍受します。
    -   `io.Pipe` を使ってリクエストボディを生成し、数バイトずつゆっくりと書き込みます。
    -   `http.NewRequest` で `POST` リクエストを作成し、`Transfer-Encoding: chunked` が適用されるようにします。
    -   `tr.RoundTrip(req)` を呼び出してリクエストを送信します。
    -   `logWritesConn` に記録された書き込み (`lw.writes`) が、期待されるチャンクごとのフラッシュパターンと一致するかどうかを `reflect.DeepEqual` で比較します。特に、ヘッダーと最初の数バイトが一緒に送信され、その後各チャンクが個別にフラッシュされていることを確認します。

これらの変更により、`net/http.Transport` は、リクエストボディがチャンクエンコーディングで送信される場合に、より応答性の高いデータストリーミング挙動を実現できるようになりました。

`net/http`: Transportにおけるリクエストボディチャンクのフラッシュ

`Transport` がリモートサーバーへの書き込みに使用するライターは、ヘッダーやトレーラーの書き込み時に多数の小さな書き込みを抑制するために `bufio.Writer` でラップされています。しかし、リクエストボディの書き込み時には、リクエストボディがゆっくりと到着する場合、このバッファリングが邪魔になる可能性があります。

`Request.Body` からライターへの `io.Copy` は既にバッファリングされているため、外側の `bufio.Writer` は不要であり、小さな `Request.Body.Read` がすぐにサーバーに送信されるのを妨げます（そして `io.Reader` の契約は、さらに多くのデータを待つのではなく、何かデータがあればすぐに返すことを示唆しています）。ボディの書き込みが完了した後も、`Transport` の `bufio.Writer` は、それに続くトレーラーのために引き続き使用されます。

この問題に対する以前の修正試行では、基になる型が `bufio.Writer` であればチャンクライターが常にフラッシュするようにしていましたが、これは完全に正しいわけではありませんでした。このCL（変更リスト）では、代わりにプライベートなセンチネル型（`*bufio.Writer` をラップしたもの）をチャンクライターに渡すことで、各チャンクボディの後にフラッシュを要求するようにオプトイン方式にしています（チャンクヘッダーとチャンクボディは引き続き一緒にバッファリングされて一度に書き込まれます）。

Fixes #6574

## 変更の背景

この変更は、Goの `net/http` パッケージにおける `Transport` の動作、特にHTTPリクエストの送信メカニズムに関するパフォーマンスと応答性の問題に対処するために行われました。

HTTP/1.1では、リクエストボディの長さを事前に知ることができない場合や、ストリーミングでデータを送信したい場合に「チャンク転送エンコーディング (Chunked Transfer Encoding)」が使用されます。この方式では、ボディが複数の「チャンク」に分割され、各チャンクの前にそのサイズが記述され、最後にゼロサイズのチャンクで終了します。

`net/http.Transport` は、HTTPリクエストを実際にネットワーク経由で送信する役割を担っています。この `Transport` は、効率化のために、リモートサーバーへの書き込み操作を `bufio.Writer` でラップしています。`bufio.Writer` は、小さな書き込みを内部バッファに蓄積し、バッファがいっぱいになったときや明示的にフラッシュされたときにまとめて大きな書き込みを行うことで、システムコール（ネットワークI/O）の回数を減らし、パフォーマンスを向上させます。

しかし、この `bufio.Writer` の挙動が、チャンク転送エンコーディングを使用するリクエストボディの送信において問題を引き起こしていました。特に、リクエストボディがアプリケーションによってゆっくりと生成される場合（例：大きなファイルを少しずつ読み込んでアップロードする、リアルタイムでデータを生成してストリーミングする）、`bufio.Writer` がチャンクデータを内部に保持し続けてしまい、すぐにネットワークに送信されないという問題が発生していました。

これは、クライアント側でデータが生成されても、サーバー側ではそのデータがなかなか受信されないという遅延につながり、特に低レイテンシが求められるアプリケーションや、サーバーがクライアントからのデータ到着を待機するようなシナリオで問題となります。コミットメッセージにある `Issue 6574` は、この問題がユーザーによって報告されたことを示しています。

以前の修正試行では、基になるライターが `bufio.Writer` であれば常にフラッシュするというアプローチが取られましたが、これはヘッダーやトレーラーなど、バッファリングが望ましい部分にまで影響を与えてしまう可能性があり、適切ではありませんでした。そのため、リクエストボディのチャンク部分のみを対象に、選択的にフラッシュを行う新しいメカニズムが必要とされていました。

## 前提知識の解説

### 1. `net/http` パッケージと `Transport`
Go言語の `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。
- **`http.Client`**: HTTPリクエストを送信するための高レベルなインターフェースを提供します。
- **`http.Transport`**: `http.Client` の内部で実際にネットワーク接続を管理し、HTTPリクエストの送信やレスポンスの受信といった低レベルな処理を担当します。TCP接続の確立、TLSハンドシェイク、プロキシの利用、接続の再利用（Keep-Alive）などを扱います。

### 2. `io.Reader` と `io.Writer` インターフェース
Go言語におけるI/O操作の基本的な抽象化です。
- **`io.Reader`**: `Read(p []byte) (n int, err error)` メソッドを持つインターフェース。データを読み出す元を表します。
- **`io.Writer`**: `Write(p []byte) (n int, err error)` メソッドを持つインターフェース。データを書き込む先を表します。
これらのインターフェースは、様々なデータソース（ファイル、ネットワーク接続、メモリバッファなど）に対して統一的なI/O操作を可能にします。

### 3. `bufio.Writer`
`bufio` パッケージは、I/O操作をバッファリングすることで効率化するための機能を提供します。
- **`bufio.Writer`**: `io.Writer` をラップし、内部にバッファを持ちます。`Write` メソッドが呼び出されると、データはまずこの内部バッファに書き込まれます。バッファがいっぱいになるか、`Flush()` メソッドが明示的に呼び出されるか、または `Close()` されるまで、基になる `io.Writer` への実際の書き込みは行われません。これにより、多数の小さな書き込みがまとめて一度の大きな書き込みに変換され、システムコールやネットワークI/Oの回数が削減され、パフォーマンスが向上します。

### 4. HTTP チャンク転送エンコーディング (Chunked Transfer Encoding)
HTTP/1.1で導入された転送エンコーディングの一種です。
- **目的**: HTTPメッセージボディの長さを事前に知ることなく、動的に生成されるコンテンツを送信するために使用されます。
- **仕組み**: メッセージボディは、一連の「チャンク」に分割されます。各チャンクは、そのチャンクのサイズ（16進数表記）と、それに続くデータで構成されます。ボディの終わりは、サイズがゼロのチャンクで示されます。
- **ヘッダー**: `Transfer-Encoding: chunked` ヘッダーがメッセージに含まれます。
- **利点**: サーバーがレスポンスボディの全長を計算する前に送信を開始できるため、応答時間を短縮できます。また、クライアントがリクエストボディをストリーミングで送信する際にも利用されます。

### 5. `io.Copy`
`io` パッケージのユーティリティ関数です。
- **`io.Copy(dst io.Writer, src io.Reader) (written int64, err error)`**: `src` からデータを読み込み、それを `dst` に書き込みます。`src` がEOF（End Of File）を返すか、エラーが発生するまで処理を続けます。内部的には、適切なサイズのバッファを使用して効率的にデータを転送します。

## 技術的詳細

このコミットの核心は、`net/http.Transport` がリクエストボディを送信する際の `bufio.Writer` のバッファリング挙動を、チャンク転送エンコーディングを使用する場合にのみ選択的に変更することです。

従来の `Transport` の実装では、HTTPヘッダー、ボディ、トレーラーを含むすべての出力が、パフォーマンス最適化のために `bufio.Writer` を介して行われていました。これは、特にヘッダーのように小さな書き込みが連続する場合には非常に効果的です。しかし、リクエストボディがチャンクエンコーディングで送信され、かつそのボディがゆっくりと生成される（例：`io.Pipe` を使用してストリーミングされる）場合、`bufio.Writer` がチャンクデータを内部バッファに保持し続け、ネットワークへの実際の送信が遅延するという問題がありました。

コミットメッセージによると、`Request.Body` からの `io.Copy` は既に内部でバッファリングを行っているため、外側の `bufio.Writer` による追加のバッファリングは冗長であり、むしろ遅延の原因となっていました。`io.Reader` の契約上、データが利用可能になったらすぐに返すことが期待されるため、`bufio.Writer` がデータを保持し続けることは、この期待に反する挙動と言えます。

この問題を解決するために、コミットは以下の新しいアプローチを導入しました。

1.  **`FlushAfterChunkWriter` センチネル型の導入**:
    `src/net/http/internal/chunked.go` に `FlushAfterChunkWriter` という新しい型が定義されました。これは `*bufio.Writer` を埋め込んだ構造体であり、`io.Writer` インターフェースを満たします。この型の目的は、`NewChunkedWriter` の呼び出し元が、チャンクの書き込み後にフラッシュを要求したいという意図を伝えるための「マーカー（センチネル）」として機能することです。

2.  **`chunkedWriter.Write` での条件付きフラッシュ**:
    `src/net/http/internal/chunked.go` の `chunkedWriter.Write` メソッドが変更されました。チャンクのデータとCRLF (`\r\n`) が書き込まれた後、`cw.Wire` (基になる `io.Writer`) が `*FlushAfterChunkWriter` 型であるかどうかをチェックします。もしそうであれば、`bw.Flush()` を呼び出して、基になる `bufio.Writer` のバッファを強制的にフラッシュします。これにより、各チャンクボディが書き込まれた直後にネットワークに送信されるようになります。

3.  **`transferWriter.WriteBody` での `FlushAfterChunkWriter` の適用**:
    `src/net/http/transfer.go` の `transferWriter.WriteBody` メソッドが変更されました。ここで、リクエストボディがチャンクエンコーディングで送信される場合 (`chunked(t.TransferEncoding)`)、かつ書き込み先 (`w`) が `*bufio.Writer` であり、かつそれがレスポンスではない (`!t.IsResponse`) 場合に、`w` を `&internal.FlushAfterChunkWriter{bw}` でラップして `internal.NewChunkedWriter` に渡すようにしました。
    -   `!t.IsResponse` の条件は重要です。このフラッシュ挙動はリクエストボディにのみ適用され、レスポンスボディには適用されません。レスポンスボディの場合、サーバー側でのバッファリングは依然として望ましい場合があります。
    -   これにより、`internal.NewChunkedWriter` は、チャンク書き込み後にフラッシュが必要であることを示す `FlushAfterChunkWriter` 型のライターを受け取ることになります。

この変更により、HTTPリクエストボディがチャンクエンコーディングで送信される際に、各チャンクが書き込まれるたびに `bufio.Writer` のバッファがフラッシュされ、データがより迅速にネットワークに送信されるようになります。ヘッダーやトレーラーの書き込み時には引き続き `bufio.Writer` によるバッファリングの恩恵を受けられるため、全体的な効率を損なうことなく、特定の問題を解決しています。

                if bw, ok := w.(*bufio.Writer); ok && !t.IsResponse {
                    w = &internal.FlushAfterChunkWriter{bw}
                }
                cw := internal.NewChunkedWriter(w)
                _, err = io.Copy(cw, t.Body)
                // ...
            }
        }
        // ...
    }
    ```
    この部分が、`FlushAfterChunkWriter` を実際に適用する場所です。
    -   `if chunked(t.TransferEncoding)`: まず、転送エンコーディングがチャンク形式であるかを確認します。
    -   `if bw, ok := w.(*bufio.Writer); ok && !t.IsResponse`: 次に、基になるライター `w` が `*bufio.Writer` 型であり、かつ現在処理しているのがレスポンスではない（つまりリクエストである）ことを確認します。
    -   `w = &internal.FlushAfterChunkWriter{bw}`: 上記の条件がすべて満たされた場合、元の `*bufio.Writer` (`bw`) を `internal.FlushAfterChunkWriter` でラップし、その新しいラッパーを `w` に再代入します。この `w` が `internal.NewChunkedWriter` に渡されます。
    -   これにより、`internal.NewChunkedWriter` は、チャンク書き込み後にフラッシュが必要なことを認識し、`chunkedWriter.Write` メソッド内で `Flush()` を呼び出すようになります。

### `src/net/http/transport_test.go` の変更

-   **`logWritesConn` 型の追加**:
    これはテスト専用の `net.Conn` 実装で、`Write` メソッドが呼び出されるたびに、書き込まれたデータを内部のスライス (`writes`) に記録します。これにより、テストコードはネットワークに実際にどのようなデータが、どのような順序で、どのようなチャンクで書き込まれたかを詳細に検証できます。

-   **`TestTransportFlushesBodyChunks` テストケースの追加**:
    このテストは、`io.Pipe` を使用してゆっくりとリクエストボディを生成し、`Transport` が `FlushAfterChunkWriter` を正しく使用して各チャンクをフラッシュしていることを検証します。
    -   `logWritesConn` を `Transport` の `Dial` 関数に注入し、ネットワークへの書き込みを傍受します。
    -   `io.Pipe` を使ってリクエストボディを生成し、数バイトずつゆっくりと書き込みます。
    -   `http.NewRequest` で `POST` リクエストを作成し、`Transfer-Encoding: chunked` が適用されるようにします。
    -   `tr.RoundTrip(req)` を呼び出してリクエストを送信します。
    -   `logWritesConn` に記録された書き込み (`lw.writes`) が、期待されるチャンクごとのフラッシュパターンと一致するかどうかを `reflect.DeepEqual` で比較します。特に、ヘッダーと最初の数バイトが一緒に送信され、その後各チャンクが個別にフラッシュされていることを確認します。

これらの変更により、`net/http.Transport` は、リクエストボディがチャンクエンコーディングで送信される場合に、より応答性の高いデータストリーミング挙動を実現できるようになりました。

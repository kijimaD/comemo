# [インデックス 25144] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/tar` パッケージ内の `sparseFileReader` に存在する複数のバグを修正するものです。具体的には、悪意のあるtarファイルによって引き起こされる可能性のあるサービス拒否（DoS）攻撃（無限ループや任意のパニック）を防ぐための堅牢性強化が目的です。`reader.go` では `sparseFileReader` のロジックが修正され、`reader_test.go` ではこれらの脆弱性に対処するための広範な単体テストが追加されています。

## 元コミット内容

`archive/tar` パッケージの `sparseFileReader` に存在するバグを修正し、サービス拒否攻撃（無限ループ、任意のパニック）を防ぐ。これは不十分なエラーチェックとハンドリングに起因しており、この変更リスト（CL）で修正される。同時に、悪意のある入力の可能性をテストするための多数の単体テストが追加される。

## 変更の背景

このコミットの背景には、`archive/tar` パッケージが、特にスパースファイル（sparse file）の処理において、悪意のある入力に対して脆弱であったという問題があります。スパースファイルは、ファイル内の連続するゼロブロックをディスク上に物理的に保存せず、メタデータとして記録することでディスクスペースを節約する特殊なファイル形式です。tarアーカイブは、このようなスパースファイルを効率的に格納するためのメカニズムを提供します。

しかし、`sparseFileReader` の実装において、以下の2つの主要な脆弱性が発見されました。

1.  **無限ループ (Infinite Loop)**: 悪意を持って細工されたtarファイルが、`sparseFileReader` の内部状態を不正なものにし、ファイル読み取り処理が終了せずに無限にループする可能性がありました。これにより、システムリソースが枯渇し、サービス拒否状態に陥る可能性があります。
2.  **任意のパニック (Arbitrary Panics)**: 不適切なエラーハンドリングや境界チェックの欠如により、特定の不正な入力が `sparseFileReader` の処理中にGoランタイムのパニックを引き起こす可能性がありました。パニックは通常、プログラムの異常終了を意味し、これもまたサービス拒否の一形態となります。

これらの脆弱性は、`archive/tar` パッケージを利用するアプリケーションが、信頼できないソースから提供されたtarファイルを処理する際に、セキュリティ上のリスクを抱えることを意味します。このコミットは、これらの既知の脆弱性に対処し、パッケージの堅牢性とセキュリティを向上させることを目的としています。

## 前提知識の解説

### `archive/tar` パッケージ

Go言語の標準ライブラリ `archive/tar` は、tarアーカイブ（テープアーカイブ）の読み書きをサポートするパッケージです。tarファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式であり、Unix系システムで広く利用されています。このパッケージは、tarファイルのヘッダ情報の解析、ファイルデータの読み書き、および特殊なファイルタイプ（シンボリックリンク、ハードリンク、デバイスファイル、そしてスパースファイルなど）の処理を扱います。

### スパースファイル (Sparse File)

スパースファイルは、ファイルシステムが、ファイル内の連続するゼロバイトのブロックを実際にディスク上に割り当てずに、その存在だけを記録する特殊なファイルです。これにより、特に大きなファイルで大部分がゼロで埋められている場合に、ディスクスペースを大幅に節約できます。例えば、1GBのファイルのうち、先頭と末尾の1KBだけがデータで、残りがゼロの場合、スパースファイルとして保存すれば、ディスク上では2KB程度のスペースしか消費しません。

tarアーカイブは、スパースファイルを効率的に格納するために、ファイル内のデータブロックと「穴」（ゼロブロック）の位置とサイズを記述するメタデータ（スパースマップ）を使用します。`sparseFileReader` は、このスパースマップを解釈し、実際のデータとゼロ埋めされた穴を組み合わせて、元のスパースファイルを再構築する役割を担います。

### サービス拒否 (Denial of Service, DoS) 攻撃

DoS攻撃は、正当なユーザーがサービスを利用できないようにすることを目的としたサイバー攻撃です。この文脈では、悪意のあるtarファイルが、`archive/tar` パッケージの処理を妨害し、アプリケーションやシステム全体を機能不全に陥れることを指します。

*   **無限ループ**: プログラムが特定の処理から抜け出せなくなり、CPUリソースを消費し続ける状態です。これにより、他のタスクが実行できなくなり、サービスが停止します。
*   **パニック**: Go言語におけるパニックは、回復不能なエラーが発生した際にプログラムが異常終了するメカニズムです。ファイル解析中にパニックが発生すると、そのファイルを処理していたアプリケーションプロセスがクラッシュし、サービスが中断されます。

### `sparseEntry` 構造体

`sparseEntry` は、スパースファイル内のデータフラグメント（実際のデータが格納されている部分）のオフセットとサイズを定義する構造体です。

```go
type sparseEntry struct {
	offset   int64 // Starting position of the fragment
	numBytes int64 // Length of the fragment
}
```

`offset` はファイル先頭からのバイトオフセット、`numBytes` はそのフラグメントのバイト長を示します。スパースファイルは、これらの `sparseEntry` のリストと、それらの間に存在する「穴」（ゼロで埋められる部分）によって構成されます。

## 技術的詳細

このコミットの技術的詳細の核心は、`sparseFileReader` の堅牢性を高めるための入力検証とエラーハンドリングの改善にあります。

### 脆弱性の原因

以前の `sparseFileReader` は、`sparseEntry` のリスト（スパースマップ）が不正な形式であったり、矛盾する情報を含んでいたりする場合に、それを適切に処理できませんでした。具体的には、以下のようなケースが問題を引き起こしていました。

*   **不正な `sparseEntry`**: `offset` や `numBytes` が負の値である、または非常に大きな値である場合。
*   **オーバーラップするフラグメント**: スパースマップ内の複数の `sparseEntry` が、ファイル内の同じ領域を指している場合。
*   **順序の誤り**: `sparseEntry` がオフセット順に並んでいない場合。
*   **ファイルサイズを超えるフラグメント**: `sparseEntry` が示すデータ領域が、ヘッダで宣言されたファイルの合計サイズを超えている場合。
*   **`io.EOF` の不適切な処理**: `rfr.Read(b)` が `io.EOF` を返した際に、`sparseFileReader` がまだ読み取るべきデータがあると誤解し、無限ループに陥る可能性がありました。

これらの問題は、`sparseFileReader` がスパースマップの整合性を十分に検証せずに処理を進めていたために発生しました。

### 修正内容

このコミットでは、主に以下の技術的詳細が修正されています。

1.  **`newSparseFileReader` 関数の導入**:
    `sparseFileReader` を直接作成する代わりに、`newSparseFileReader` というファクトリ関数が導入されました。この関数は、`sparseFileReader` を初期化する前に、渡された `sparseEntry` のリスト（スパースマップ）と `total` サイズ（ファイルの合計サイズ）を徹底的に検証します。

    ```go
    func newSparseFileReader(rfr numBytesReader, sp []sparseEntry, total int64) (*sparseFileReader, error) {
        if total < 0 {
            return nil, ErrHeader // Total size cannot be negative
        }

        // Validate all sparse entries. These are the same checks as performed by
        // the BSD tar utility.
        for i, s := range sp {
            switch {
            case s.offset < 0 || s.numBytes < 0:
                return nil, ErrHeader // Negative values are never okay
            case s.offset > math.MaxInt64-s.numBytes:
                return nil, ErrHeader // Integer overflow with large length
            case s.offset+s.numBytes > total:
                return nil, ErrHeader // Region extends beyond the "real" size
            case i > 0 && sp[i-1].offset+sp[i-1].numBytes > s.offset:
                return nil, ErrHeader // Regions can't overlap and must be in order
            }
        }
        return &sparseFileReader{rfr: rfr, sp: sp, total: total}, nil
    }
    ```
    この関数内で、以下の重要な検証が行われます。
    *   `total` (ファイルの合計サイズ) が負でないこと。
    *   各 `sparseEntry` の `offset` および `numBytes` が負でないこと。
    *   `offset + numBytes` が `math.MaxInt64` を超えて整数オーバーフローを起こさないこと。
    *   `offset + numBytes` が `total` を超えていないこと（データフラグメントがファイルの論理サイズを超えないこと）。
    *   `sparseEntry` がオフセット順に並んでおり、かつ互いにオーバーラップしていないこと。これは `sp[i-1].offset+sp[i-1].numBytes > s.offset` のチェックで行われます。

    これらのチェックは、BSD tarユーティリティが行う検証と同じであり、不正なスパースマップを早期に検出して `ErrHeader` を返すことで、後続の処理でのパニックや無限ループを防ぎます。

2.  **`sparseFileReader.Read` メソッドのロジック改善**:
    `Read` メソッドは、スパースファイルの実データを読み取る主要なロジックを含んでいます。このメソッドは、以下の点で改善されました。
    *   **空のフラグメントのスキップ**: `sfr.sp` リストの先頭にある `numBytes == 0` の空のフラグメントをスキップするロジックが追加されました。これにより、無意味な処理を減らし、潜在的な無限ループの経路を塞ぎます。
    *   **最後の穴の処理**: `sfr.sp` が空になった後、`sfr.pos < sfr.total` であれば、残りの部分を最後の穴として適切に処理し、ゼロを埋めるようになりました。以前は、この部分で `io.ErrUnexpectedEOF` が発生したり、無限ループに陥る可能性がありました。
    *   **`io.EOF` の適切な伝播**: `sfr.rfr.Read(b)` が `io.EOF` を返した場合の処理がより正確になりました。期待されるデータ量に達していない場合は `io.ErrUnexpectedEOF` を返し、そうでない場合は `nil` を返すことで、呼び出し元が正しいエラー状態を判断できるようにします。
    *   **`endPos` の計算**: フラグメントの終了位置 `endPos` の計算が `sfr.sp[0].offset + sfr.sp[0].numBytes` と明確化され、オーバーフローフリーであることがコメントで明記されました。

3.  **`sparseFileReader.readHole` メソッドの改善**:
    `readHole` メソッドは、スパースファイル内の「穴」（ゼロで埋められる部分）を読み取る役割を担います。`toOffset` パラメータが `endOffset` に変更され、より明確になりました。

4.  **テストケースの拡充**:
    `reader_test.go` には、`TestSparseFileReader` 関数内で、様々な悪意のある入力やエッジケースを網羅する多数のテストベクトルが追加されました。これには、負のサイズ、オーバーラップするフラグメント、順序が不正なフラグメント、ファイルサイズを超えるフラグメントなどが含まれます。これらのテストは、`newSparseFileReader` が期待通りに `ErrHeader` を返すこと、または `Read` メソッドが正しいデータとエラーを返すことを検証します。

これらの変更により、`archive/tar` パッケージは、不正なスパースファイルに対してもより堅牢になり、サービス拒否攻撃のリスクが大幅に低減されました。

## コアとなるコードの解説

### `newSparseFileReader` 関数

この関数は、スパースファイルのセキュリティと堅牢性を確保するための最も重要な変更点です。

```go
func newSparseFileReader(rfr numBytesReader, sp []sparseEntry, total int64) (*sparseFileReader, error) {
	if total < 0 {
		return nil, ErrHeader // Total size cannot be negative
	}

	// Validate all sparse entries. These are the same checks as performed by
	// the BSD tar utility.
	for i, s := range sp {
		switch {
		case s.offset < 0 || s.numBytes < 0:
			return nil, ErrHeader // Negative values are never okay
		case s.offset > math.MaxInt64-s.numBytes:
			return nil, ErrHeader // Integer overflow with large length
		case s.offset+s.numBytes > total:
			return nil, ErrHeader // Region extends beyond the "real" size
		case i > 0 && sp[i-1].offset+sp[i-1].numBytes > s.offset:
			return nil, ErrHeader // Regions can't overlap and must be in order
		}
	}
	return &sparseFileReader{rfr: rfr, sp: sp, total: total}, nil
}
```

この関数は、`sparseFileReader` を構築する前に、スパースマップ `sp` とファイルの論理的な合計サイズ `total` の整合性を厳密にチェックします。

*   `total < 0`: ファイルサイズが負であることはありえないため、即座にエラーを返します。
*   `s.offset < 0 || s.numBytes < 0`: スパースエントリのオフセットやサイズが負であることは不正です。
*   `s.offset > math.MaxInt64-s.numBytes`: `offset` と `numBytes` の合計が `int64` の最大値を超えてオーバーフローする可能性をチェックします。これにより、不正な大きな値によるメモリ割り当てエラーやパニックを防ぎます。
*   `s.offset+s.numBytes > total`: スパースエントリが示すデータ領域が、ファイルの宣言された合計サイズを超えていないことを確認します。これにより、ファイル境界外へのアクセスを防ぎます。
*   `i > 0 && sp[i-1].offset+sp[i-1].numBytes > s.offset`: 複数のスパースエントリが互いにオーバーラップしていないこと、およびオフセット順に並んでいることを確認します。オーバーラップは、ファイルの内容が矛盾する原因となり、不正な読み取り動作につながる可能性があります。

これらの検証により、`sparseFileReader` が常に有効で安全なスパースマップで動作することが保証され、サービス拒否攻撃の主要な経路が遮断されます。

### `sparseFileReader.Read` メソッド

`Read` メソッドは、スパースファイルの論理的な内容をバイトスライス `b` に読み込む役割を担います。

```go
func (sfr *sparseFileReader) Read(b []byte) (n int, err error) {
	// Skip past all empty fragments.
	for len(sfr.sp) > 0 && sfr.sp[0].numBytes == 0 {
		sfr.sp = sfr.sp[1:]
	}

	// If there are no more fragments, then it is possible that there
	// is one last sparse hole.
	if len(sfr.sp) == 0 {
		// This behavior matches the BSD tar utility.
		// However, GNU tar stops returning data even if sfr.total is unmet.
		if sfr.pos < sfr.total {
			return sfr.readHole(b, sfr.total), nil
		}
		return 0, io.EOF
	}

	// In front of a data fragment, so read a hole.
	if sfr.pos < sfr.sp[0].offset {
		return sfr.readHole(b, sfr.sp[0].offset), nil
	}

	// In a data fragment, so read from it.
	// This math is overflow free since we verify that offset and numBytes can
	// be safely added when creating the sparseFileReader.
	endPos := sfr.sp[0].offset + sfr.sp[0].numBytes // End offset of fragment
	bytesLeft := endPos - sfr.pos                   // Bytes left in fragment
	if int64(len(b)) > bytesLeft {
		b = b[:bytesLeft]
	}

	n, err = sfr.rfr.Read(b)
	sfr.pos += int64(n)

	if err == io.EOF {
		if sfr.pos < endPos {
			err = io.ErrUnexpectedEOF // There was supposed to be more data
		} else if sfr.pos < sfr.total {
			err = nil // There is still an implicit sparse hole at the end
		}
	}

	if sfr.pos == endPos {
		sfr.sp = sfr.sp[1:] // We are done with this fragment, so pop it
	}
	return n, err
}
```

この修正された `Read` メソッドは、以下の点で以前のバージョンよりも堅牢です。

*   **空のフラグメントのスキップ**: `for len(sfr.sp) > 0 && sfr.sp[0].numBytes == 0` ループは、`numBytes` がゼロのスパースエントリを効率的にスキップします。これにより、無駄な処理や、これらのエントリが原因で発生する可能性のあるロジックエラーを防ぎます。
*   **最後の穴の処理**: `if len(sfr.sp) == 0` ブロックは、すべてのデータフラグメントが処理された後に、ファイルの論理的な終端まで残っている可能性のある「穴」を適切に処理します。`sfr.pos < sfr.total` であれば、`readHole` を呼び出してゼロを埋め、そうでなければ `io.EOF` を返します。これにより、ファイル終端処理の正確性が向上し、無限ループを防ぎます。
*   **データフラグメントの読み取り**: `endPos` と `bytesLeft` の計算が明確になり、`newSparseFileReader` での検証によりオーバーフローがないことが保証されます。`b = b[:bytesLeft]` は、読み取るバイト数が現在のフラグメントの残りのバイト数を超えないようにスライスを調整します。
*   **`io.EOF` のハンドリング**: `sfr.rfr.Read(b)` が `io.EOF` を返した場合の条件分岐が改善されました。
    *   `sfr.pos < endPos`: まだ現在のフラグメントの終端に達していないのに `io.EOF` が返された場合、それは予期せぬファイルの終端であり、`io.ErrUnexpectedEOF` を返します。
    *   `sfr.pos < sfr.total`: 現在のフラグメントは読み終えたが、ファイルの論理的な終端には達していない場合（つまり、後続に穴がある場合）、エラーは `nil` にリセットされます。これにより、`io.EOF` が早すぎるタイミングで返されることを防ぎます。
*   **フラグメントのポップ**: `if sfr.pos == endPos` は、現在のフラグメントの読み取りが完了したことを正確に判断し、`sfr.sp = sfr.sp[1:]` で次のフラグメントに移動します。

これらの変更は、`sparseFileReader` が不正な入力に対してより堅牢に動作し、予期せぬパニックや無限ループを防ぐ上で不可欠です。

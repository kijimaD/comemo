## 変更の背景

このコミットの主な目的は、`TestNumGoroutine` というテストの「flakiness（不安定性）」を解消することです。Flakyテストとは、コードの変更がないにもかかわらず、実行するたびに成功したり失敗したりするテストを指します。このようなテストは、通常、並行処理におけるタイミングの問題や、テスト環境の非決定的な要素によって引き起こされます。

`TestNumGoroutine` は、`runtime.NumGoroutine()` 関数が報告するGoroutineの数と、`runtime.Stack()` 関数がダンプするスタックトレース内のGoroutineの数が一致するかどうかを検証していました。しかし、Goランタイムの性質上、Goroutineは非同期に生成・終了するため、`runtime.NumGoroutine()` が呼び出された直後にGoroutineが終了したり、新しいGoroutineが生成されたりすると、その後の `runtime.Stack()` の結果と一致しなくなる可能性がありました。これがテストのflakinessの原因でした。

コミットメッセージにある `Fixes #14107` は、この変更がGoのIssue 14107を解決することを示しています。Issue 14107では、まさにこの `TestNumGoroutine` が不安定であるという報告がされており、その原因が `runtime.NumGoroutine()` と `runtime.Stack()` の間のレースコンディションにあることが指摘されていました。

## 前提知識の解説

### GoのGoroutine

GoroutineはGo言語における軽量な並行処理の単位です。OSのスレッドよりもはるかに軽量で、数千、数万のGoroutineを同時に実行することが可能です。GoランタイムのスケジューラがこれらのGoroutineをOSスレッドにマッピングし、効率的に実行を切り替えます。

### `runtime.NumGoroutine()`

この関数は、現在実行中または実行可能状態にあるGoroutineの総数を返します。これは、Goプログラムの並行処理の状況を把握するための重要な指標となります。

### `runtime.Stack()`

この関数は、現在のすべてのGoroutineのスタックトレースをバイトスライスとしてダンプします。引数 `all` が `true` の場合、すべてのGoroutineのスタックトレースが含まれます。この情報は、デバッグやプロファイリングの際に、どのGoroutineがどこで何をしているかを特定するために非常に役立ちます。

### テストのFlakiness (Flaky Test)

Flakyテストは、ソフトウェア開発において大きな問題となります。CI/CDパイプラインでテストがランダムに失敗すると、開発者はその失敗が実際のバグによるものなのか、それともテスト自体の不安定性によるものなのかを判断するのに時間を費やすことになります。これにより、開発の速度が低下し、テストへの信頼が損なわれます。Flakyテストの原因は多岐にわたりますが、並行処理のタイミング依存性、外部リソースへの依存、環境の非決定性などが一般的です。

### レースコンディション (Race Condition)

レースコンディションは、複数のGoroutine（またはスレッド）が共有リソース（メモリ、ファイルなど）に同時にアクセスし、そのアクセス順序によってプログラムの最終的な結果が変わってしまう状況を指します。このコミットのケースでは、`runtime.NumGoroutine()` と `runtime.Stack()` の呼び出しの間にGoroutineの状態が変化することで、期待される結果が得られないというレースコンディションが発生していました。

### `runtime.Gosched()`

`runtime.Gosched()` は、現在のGoroutineの実行を一時停止し、Goスケジューラに他のGoroutineを実行する機会を与える関数です。これは、明示的にGoroutineの実行順序を制御するものではなく、あくまでスケジューラにヒントを与えるものです。これにより、他のGoroutineが処理を進める時間を確保し、特定のGoroutineがCPUを占有し続けることを防ぐことができます。このコミットでは、Goroutineの状態が安定するのを待つために利用されています。

## 技術的詳細

変更前の `TestNumGoroutine` は、`runtime.NumGoroutine()` を呼び出してGoroutineの数を取得し、その直後に `runtime.Stack()` を呼び出してスタックトレースをダンプし、ダンプされた文字列内の "goroutine " の出現回数を数えていました。そして、この2つの値が一致することを期待していました。

しかし、Goランタイムは並行処理を積極的に利用しており、Goroutineの生成や終了は非常に高速かつ非同期に行われます。そのため、`runtime.NumGoroutine()` が呼び出された時点と、`runtime.Stack()` がすべてのGoroutineの情報を収集し終える時点との間に、Goroutineの数が変動する可能性がありました。例えば、`runtime.NumGoroutine()` が5を返した後、すぐに1つのGoroutineが終了し、`runtime.Stack()` が4つのGoroutineしか見つけられない、といった状況です。これがテストの不安定性の根本原因でした。

このコミットでは、このレースコンディションを緩和するために、リトライメカニズムが導入されました。具体的には、`runtime.NumGoroutine()` と `runtime.Stack()` の結果が一致するまで、最大10回まで試行を繰り返すように変更されました。各試行の間には `runtime.Gosched()` が呼び出され、他のGoroutineに実行機会を与えることで、システムの状態がより安定するのを待つようにしています。これにより、一時的なGoroutine数の不一致がテスト失敗に直結するのを防ぎ、テストの信頼性を向上させています。

コミットメッセージにもあるように、これは「根本的にレースコンディションのあるチェック」であり、完全にレースコンディションを排除するものではありませんが、テストのflakinessを大幅に減少させる効果があります。

## コアとなるコードの解説

変更の核心は、`runtime.NumGoroutine()` と `runtime.Stack()` の呼び出しをリトライループで囲んだ点にあります。

1.  **`for i := 0; ; i++`**:
    この無限ループは、Goroutine数のチェックを最大10回まで繰り返すためのものです。ループカウンタ `i` が10に達すると、テストは失敗します。

2.  **`runtime.Gosched()`**:
    ループの各イテレーションの最初に `runtime.Gosched()` が呼び出されます。これにより、現在のGoroutineはCPUをGoスケジューラに譲り、他のGoroutine（特に終了しようとしているGoroutine）が処理を完了する機会を得ます。これは、`runtime.NumGoroutine()` と `runtime.Stack()` がより安定したGoroutineの状態を観測できるようにするための重要なステップです。

3.  **`n := runtime.NumGoroutine()` と `buf = buf[:runtime.Stack(buf, true)]`**:
    `runtime.Gosched()` の後、現在のGoroutine数 `n` を取得し、その直後にすべてのGoroutineのスタックトレースを `buf` にダンプします。この2つの操作をできるだけ近接して実行することで、Goroutine数の変動による不一致の可能性を最小限に抑えようとしています。

4.  **`nstk := strings.Count(string(buf), "goroutine ")`**:
    ダンプされたスタックトレース文字列 `buf` 内に含まれる "goroutine " という文字列の出現回数を数えます。これは、スタックトレースに現れるGoroutineの数を間接的にカウントする方法です。

5.  **`if n == nstk { break }`**:
    `runtime.NumGoroutine()` が返した数 `n` と、スタックトレースからカウントした数 `nstk` が一致した場合、テストは成功とみなし、ループを抜けます。

6.  **`if i >= 10 { t.Fatalf(...) }`**:
    もしループが10回繰り返されても `n` と `nstk` が一致しなかった場合、テストは失敗と判断され、`t.Fatalf` を呼び出してエラーメッセージを出力します。これは、一時的なレースコンディションではなく、Goroutine数の報告に根本的な問題がある可能性を示唆します。

この変更により、テストは一時的なタイミングのずれによる失敗を許容し、より堅牢になりました。

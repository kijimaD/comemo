# [インデックス 21882] ファイルの概要

このコミットは、Go言語のツールチェイン、特にアセンブラ (`cmd/asm`) とビルドツール (`cmd/dist`) における複数の修正を統合したものです。主な目的は、Goランタイムの正確なアセンブリを保証し、アセンブラの堅牢性を向上させることにあります。具体的には、アセンブラの命令エンコーディングの修正、マクロ再帰検出の改善、そしてビルドプロセスの調整が含まれています。

## 変更の背景

このコミットは、Go言語のランタイム（Goプログラムの実行をサポートする低レベルコード）がGoアセンブラによって正しくアセンブルされることを保証するための「最終的な修正」として位置づけられています。Goランタイムは、ガベージコレクション、スケジューリング、システムコールなどの重要な機能を提供するため、そのアセンブリの正確性はGoプログラム全体の安定性とパフォーマンスに直結します。

変更の背景には、以下のような具体的な問題があったと考えられます。

1.  **アセンブラの命令エンコーディングの不正確さ**: 特に、複雑なメモリアドレッシングモード（例: `(R)(R*scale)` や `sym(R)(R*8)`）のエンコーディングにバグがあった可能性があります。これらのモードは、ベースレジスタ、インデックスレジスタ、スケールファクタ、オフセット（シンボル）を組み合わせてメモリ位置を計算するために使用されます。不正確なエンコーディングは、生成される機械語コードが意図したものではなくなり、ランタイムの誤動作やクラッシュを引き起こす可能性があります。
2.  **マクロ再帰検出の不備**: アセンブラのマクロ処理において、無限再帰に陥る可能性があったか、または再帰の深さのチェックが不十分であった可能性があります。これにより、アセンブラがハングアップしたり、リソースを過剰に消費したりする問題が発生します。
3.  **JMP命令のコンテキスト設定の欠落**: `obj`パッケージ（Goのオブジェクトファイル生成を担当するライブラリ）が生成する`JMP`（ジャンプ）命令において、適切なコンテキスト情報が設定されていなかった可能性があります。コンテキスト情報は、デバッグやプロファイリングにおいて重要であり、欠落しているとツールの機能が損なわれる可能性があります。
4.  **ビルドプロセスの不整合**: `cmd/asm/internal/`のような内部パッケージが、Goのビルドシステムによって適切にパッケージとして認識されていなかった可能性があります。これにより、ビルドが失敗したり、依存関係の解決に問題が生じたりすることが考えられます。

これらの問題は、Goランタイムのような低レベルでクリティカルなコードの正確なコンパイルとリンクを妨げるため、Go言語の安定性と信頼性を確保するために修正が不可欠でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のツールチェインとアセンブリに関する知識が必要です。

1.  **Goアセンブラ (`cmd/asm`)**:
    *   Go言語は、Goソースコードを機械語に変換するコンパイラだけでなく、Goスタイルのアセンブリ言語を機械語に変換する独自のアセンブラを持っています。これは、C言語のGCCアセンブラやIntel/AT&T構文のアセンブラとは異なる独自の構文（Plan 9アセンブラに由来）を使用します。
    *   Goアセンブラは、主にGoランタイムや特定のパフォーマンスクリティカルなライブラリ（例: 暗号化、数値計算）で、Go言語では実現が難しい低レベルの最適化やハードウェアとの直接的なインタラクションを行うために使用されます。
    *   `cmd/asm/internal/asm` はアセンブラのパース（構文解析）を担当する部分であり、アセンブリコードのオペランド（引数）やアドレッシングモードを解釈します。
    *   `cmd/asm/internal/lex` はアセンブラの字句解析（トークン化）を担当する部分であり、マクロの展開などもここで行われます。

2.  **Goのオブジェクトファイル生成 (`cmd/internal/obj`)**:
    *   Goコンパイラやアセンブラが生成する中間表現は、最終的に機械語コードを含むオブジェクトファイルに変換されます。この変換は、`cmd/internal/obj` パッケージ群が担当します。
    *   `cmd/internal/obj/x86` は、x86アーキテクチャ（Intel/AMDプロセッサ）向けの機械語コード生成とオブジェクトファイルフォーマットに関するロジックを含んでいます。
    *   `obj.Addr` は、Goアセンブラが扱うアドレス（メモリ位置、レジスタなど）を表現するための構造体です。`Type`、`Reg`（ベースレジスタ）、`Index`（インデックスレジスタ）、`Scale`（スケールファクタ）、`Offset`（オフセット値）などのフィールドを持ちます。
    *   `obj.TYPE_MEM` はメモリアドレス指定、`obj.TYPE_ADDR` はアドレスそのものを表します。
    *   `obj.Ctxt` は、オブジェクト生成のコンテキスト（シンボルテーブル、エラーハンドリングなど）を保持します。

3.  **メモリアドレッシングモード**:
    *   アセンブリ言語では、CPUがメモリ上のデータにアクセスする方法を「アドレッシングモード」と呼びます。
    *   **ベースレジスタ + インデックスレジスタ * スケールファクタ + オフセット**: `sym(R1)(R2*scale)` のような形式は、`R1`（ベースレジスタ）、`R2`（インデックスレジスタ）、`scale`（スケールファクタ、通常1, 2, 4, 8）、`sym`（シンボルまたはオフセット）を組み合わせて実効アドレスを計算します。例えば、`AX(BX*8)` は `AX + BX * 8` のアドレスを指します。
    *   `sym(R)(R*8)` は、シンボルオフセットにレジスタと8倍のスケールファクタを持つインデックスレジスタを加算するアドレッシングモードです。これは、配列の要素にアクセスする際によく使用されます（例: `array_base + index * element_size`）。
    *   `(R)(R*scale)` は、ベースレジスタとインデックスレジスタにスケールファクタを適用したアドレッシングモードです。

4.  **Goのビルドシステム (`cmd/dist`)**:
    *   `cmd/dist` は、GoのソースコードからGoツールチェイン自体（コンパイラ、アセンブラ、リンカなど）をビルドするためのブートストラップツールです。
    *   `bootstrapDirs` は、ブートストラップビルドプロセス中にコンパイルされる必要のあるパッケージのリストです。
    *   `install` 関数は、Goパッケージをビルドしてインストールするロジックを含みます。`ispkg` は、特定のディレクトリがGoパッケージとして扱われるべきかどうかを判断するフラグです。

5.  **マクロと再帰**:
    *   アセンブラのマクロは、繰り返し使用されるコードパターンを抽象化し、コードの可読性と再利用性を高めるための機能です。
    *   マクロが自分自身を呼び出す、または他のマクロを介して間接的に自分自身を呼び出すことを「マクロ再帰」と呼びます。無限再帰は、プログラムのクラッシュやハングアップを引き起こすため、検出と防止が必要です。

## 技術的詳細

このコミットは、Goアセンブラとビルドプロセスの複数の側面を改善しています。

### 1. アセンブラのパースロジックの改善 (`src/cmd/asm/internal/asm/parse.go`)

最も重要な変更は、アセンブラがメモリアドレッシングモードをパースする方法の改善です。
*   以前は、`operand` 関数内でレジスタ間接アドレッシングモードのパースロジックが直接記述されていましたが、これが `registerIndirect` という新しいヘルパー関数に抽出されました。
*   `registerIndirect` 関数は、`(R1)`、`(R2*scale)`、または `(R1)(R2*scale)` のような一般的なレジスタ間接アドレッシングモードを解析します。
*   特に、`sym(R)(R*8)` のような形式が正しく解釈されるように修正されました。これは、シンボルオフセットに加えて、ベースレジスタと8倍のスケールファクタを持つインデックスレジスタを組み合わせたアドレッシングモードです。以前は「見落とし」とされていたため、この修正により、より複雑なメモリアクセスパターンがGoアセンブラで正確に表現できるようになりました。
*   `a.Type = obj.TYPE_MEM` と `a.Type = obj.TYPE_ADDR` の設定は、オペランドがメモリ参照なのか、それともアドレス値そのものなのかを区別するために重要です。
*   `a.Reg`、`a.Index`、`a.Scale` の設定は、`obj.Addr` 構造体に必要な情報を正確に格納し、後続のコード生成フェーズで正しい機械語命令が生成されるようにします。

### 2. マクロ再帰検出の修正 (`src/cmd/asm/internal/lex/input.go`)

アセンブラの字句解析器におけるマクロ再帰の検出ロジックが修正されました。
*   以前は、`for i := 0; i < 100; i++` のように、単にループカウンタ `i` を使用してトークン生成の試行回数を制限していました。
*   修正後は、`for nesting := 0; nesting < 100;` のように `nesting` という変数を導入し、マクロが呼び出されるたびに `nesting++` しています。
*   これにより、トークン生成の試行回数ではなく、マクロの「ネストの深さ」を正確に100に制限するようになりました。これは、無限再帰をより効果的に防ぎ、アセンブラの堅牢性を高めます。元のコメントが「100 tries」から「100 macro invocations」に修正されていることからも、この意図が明確です。

### 3. ビルドプロセスの調整 (`src/cmd/dist/build.go`, `src/cmd/dist/buildtool.go`)

Goのビルドシステム (`cmd/dist`) に関連する修正も行われました。
*   `src/cmd/dist/build.go` では、`ispkg` の判定ロジックが変更され、`cmd/asm/internal/` ディレクトリもGoパッケージとして扱われるようになりました。これにより、アセンブラの内部パッケージがGoの標準的なビルドプロセスに正しく組み込まれ、依存関係の解決がスムーズになります。
*   `src/cmd/dist/buildtool.go` では、ブートストラップビルド時にコンパイルされるディレクトリのリスト `bootstrapDirs` に、`asm`、`asm/internal/arch`、`asm/internal/asm`、`asm/internal/flags`、`asm/internal/lex` といったアセンブラ関連のディレクトリが追加されました。これは、Goツールチェイン自体をビルドする際に、アセンブラのコンポーネントが適切にブートストラップされることを保証します。
*   また、`bootstrapFixImports` 関数において、`"cmd/"` で始まるインポートパスが `"bootstrap/"` に置換されるようになりました。これは、ブートストラップビルドの際に、一時的なブートストラップ環境でコンパイルされたパッケージが、通常の `cmd` パッケージとは異なるパスで参照されることを可能にします。

### 4. JMP命令のコンテキスト設定 (`src/cmd/internal/obj/x86/obj6.go`)

x86アーキテクチャ向けのオブジェクトコード生成において、`JMP` 命令のコンテキスト設定が追加されました。
*   `q.Ctxt = p.Ctxt` という行が追加され、生成されるジャンプ命令 (`q`) に、元の命令 (`p`) のコンテキスト (`Ctxt`) が引き継がれるようになりました。
*   `Ctxt` は、シンボルテーブルやその他のメタデータを含むオブジェクト生成のコンテキストです。この設定により、生成されたジャンプ命令が、その命令が属するコードブロックや関数に関する正しいコンテキスト情報を保持するようになります。これは、デバッグ情報やシンボル解決の正確性を保証するために重要です。

これらの修正は、Goアセンブラの機能と堅牢性を向上させ、Goランタイムのような低レベルのコードがGoツールチェインによって正確に処理されることを保証します。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/parse.go` の変更

*   **`operand` 関数の簡素化と `registerIndirect` の導入**:
    *   元の `operand` 関数内にあったレジスタ間接アドレッシングモードの複雑なパースロジックが、新しく追加された `registerIndirect` 関数に完全に移動されました。これにより、`operand` 関数の可読性が向上し、関心事の分離が図られています。
    *   `p.peek() == '('` のチェックが追加され、シンボル参照の直後に括弧がある場合（例: `sym(R)` や `sym(R)(R*8)` のような形式）に `registerIndirect` が呼び出されるようになりました。これは、`sym(R)(R*8)` のようなアドレッシングモードを正しく処理するための重要な変更です。
*   **`registerIndirect` 関数の詳細**:
    *   この関数は、Goアセンブラの構文におけるレジスタ間接アドレッシングモードの多様な形式（`(R1)`、`(R2*scale)`、`(R1)(R2*scale)`）を統一的に処理します。
    *   `p.next()` と `p.register()` を使用して、括弧内のレジスタとスケールファクタを抽出します。
    *   `a.Type = obj.TYPE_MEM` または `a.Type = obj.TYPE_ADDR` を設定することで、オペランドがメモリ位置を参照しているのか、それともアドレス値そのものなのかを正確に区別します。これは、アセンブラが生成する機械語命令のオペランドタイプに直接影響します。
    *   `a.Reg`、`a.Index`、`a.Scale` フィールドに抽出したレジスタとスケールファクタを割り当てます。これにより、`obj.Addr` 構造体が、複雑なアドレッシングモードを正確に表現できるようになります。
    *   特に重要なのは、`else if scale != 0` のブロックです。これは、`(R*scale)` の形式で、ベースレジスタが明示されていない場合に、`a.Reg = 0` と設定し、`a.Index` と `a.Scale` を使用してアドレスを計算するロジックです。これにより、`sym(R*8)` のような形式も正しく解釈できるようになります。

### `src/cmd/asm/internal/lex/input.go` の変更

*   **マクロ再帰検出の改善**:
    *   `for i := 0; i < 100; i++` が `for nesting := 0; nesting < 100;` に変更され、ループ変数の名前が `i` から `nesting` に変更されました。これは、コードの意図をより明確にするためのリファクタリングです。
    *   最も重要な変更は、`if macro != nil { nesting++ ... }` の行です。以前は、トークンを生成する試行回数をカウントしていましたが、この変更により、マクロが実際に呼び出される（`in.invokeMacro(macro)`）たびに `nesting` カウンタが増加するようになりました。
    *   これにより、アセンブラはマクロの「ネストの深さ」を正確に追跡し、100レベルを超えるマクロ再帰を検出して停止するようになります。これは、無限マクロ展開によるアセンブラのハングアップやクラッシュを防ぐための堅牢性向上策です。

### `src/cmd/internal/obj/x86/obj6.go` の変更

*   **JMP命令のコンテキスト伝播**:
    *   `q.Ctxt = p.Ctxt` の一行が追加されました。
    *   `obj6.go` は、x86アーキテクチャ向けのオブジェクトコード生成を担当するファイルです。この特定のコードブロックは、ジャンプ命令（`JMP`）を生成するループの一部です。
    *   `p` は元の命令（`obj.Prog`）、`q` は新しく生成されるジャンプ命令を表します。
    *   `Ctxt` フィールドは、命令が属するコンテキスト（例えば、シンボルテーブルやデバッグ情報など）を保持します。この修正により、生成されたジャンプ命令が、元の命令と同じコンテキスト情報を引き継ぐことが保証されます。
    *   これは、特にデバッグやプロファイリングツールが、生成されたジャンプ命令を正しく解釈し、元のソースコードやシンボルにマッピングするために重要です。コンテキストが欠落していると、デバッグ時にジャンプ先の情報が不明になったり、シンボル解決が失敗したりする可能性があります。

これらの変更は、Goアセンブラの正確性、堅牢性、そしてGoツールチェイン全体の整合性を向上させるために不可欠なものです。

# [インデックス 21722] ファイルの概要

このコミットは、Go言語のツールチェイン（アセンブラ、コンパイラ、リンカ）における内部データ構造である`Prog`（プログラム命令）と`Addr`（オペランド/アドレス）の表現方法を大幅にリファクタリングするものです。主な目的は、これらの構造体のフィールドが持つ意味をより明確にし、コードの可読性、保守性、そして将来的な移植性を向上させることにあります。具体的には、以前は多義的に使用されていた`D_`プレフィックスを持つ定数を、`TYPE_`（オペランドの種類）、`REG_`（レジスタ）、`NAME_`（シンボル名）といった、よりセマンティックなプレフィックスを持つ定数に置き換えることで、内部表現の構造化を進めています。

## 変更の背景

Go言語のコンパイラ、アセンブラ、リンカといったツールチェインは、ソースコードを最終的な実行可能バイナリに変換する過程で、様々な中間表現（IR）を使用します。このコミットが行われる以前は、`Prog`（プログラム命令）や`Addr`（オペランド）といった主要な内部データ構造において、そのフィールド（特に`type`フィールド）が、オペランドの種類、レジスタ、シンボル名など、複数の異なる意味を`D_`という単一のプレフィックスで表していました。

この多義的な表現は、コードの理解を困難にし、新しいアーキテクチャへの対応や機能追加の際に、意図しない副作用やバグを引き起こす可能性がありました。例えば、`D_SP`がレジスタとしてのスタックポインタを指す場合と、アドレス指定モードの一部として使われる場合で、その文脈をコードから読み解く必要がありました。

このコミットの背景には、このような内部表現の曖昧さを解消し、より明確で構造化された表現を導入することで、ツールチェイン全体の可読性、保守性、そして将来的な拡張性（特に異なるCPUアーキテクチャへの移植性）を向上させるという目的があります。これにより、コンパイラ開発者は、より安全かつ効率的にコードを変更・拡張できるようになります。

## 前提知識の解説

### Goツールチェインの構成要素

*   **`cmd/8a` (アセンブラ)**: Goのアセンブリ言語（Plan 9アセンブリ構文）を機械語に変換するツールです。`8`は386アーキテクチャ（x86 32-bit）を指します。
*   **`cmd/8g` (コンパイラ)**: Goのソースコードを、アセンブリ言語（`8a`が処理できる形式）に変換するツールです。
*   **`cmd/8l` (リンカ)**: アセンブラによって生成されたオブジェクトファイルを結合し、実行可能バイナリを生成するツールです。
*   **`liblink` (リンキングライブラリ)**: リンカが内部的に使用する共通のライブラリで、オブジェクトファイルの解析やシンボル解決などの機能を提供します。

### `Prog`と`Addr`データ構造

Goのツールチェインにおいて、`Prog`と`Addr`は非常に重要な内部データ構造です。

*   **`Prog`**: アセンブリ言語の単一の命令を表す構造体です。命令の種類（例: `MOV`、`ADD`）、ソースオペランド、デスティネーションオペランドなどの情報を含みます。
*   **`Addr`**: `Prog`構造体内で使用され、命令のオペランド（引数）を表す構造体です。オペランドは、レジスタ、メモリのアドレス、即値定数、シンボルなど、様々な種類があります。

これらの構造体は、コンパイラがGoのソースコードを解析し、中間表現を生成し、最終的に機械語に近いアセンブリ命令を構築する過程で頻繁に利用されます。

### 内部表現の重要性

コンパイラは、ソースコードを直接機械語に変換するのではなく、複数の段階的な中間表現（IR）を経由します。これにより、コンパイラの各フェーズ（構文解析、意味解析、最適化、コード生成など）を独立して開発・テストでき、コンパイラ全体の複雑性を管理しやすくなります。また、異なるアーキテクチャに対応する際も、共通のIRを維持しつつ、バックエンドのコード生成部分のみを変更するといった柔軟性が得られます。

### `D_`プレフィックスの定数

このコミット以前のGoツールチェインでは、`D_NONE`, `D_AUTO`, `D_PARAM`, `D_EXTERN`, `D_STATIC`, `D_CONST`, `D_INDIR`, `D_ADDR`, `D_BRANCH`, `D_SCONST`, `D_FCONST`, `D_CONST2`, `D_SP`といった定数が、`Addr`構造体の`type`フィールドなどで使用されていました。これらの定数は、オペランドの種類（定数、アドレス、間接参照など）や、レジスタ（`D_SP`など）、さらにはシンボルの種類（`D_AUTO`、`D_EXTERN`など）といった、複数の異なるセマンティクスを表現するためにオーバーロードされていました。

## 技術的詳細

このコミットの核心は、`Prog`と`Addr`構造体におけるオペランドの表現を、よりセマンティックに分離し、明確化することです。具体的には、以前の`D_`プレフィックスを持つ定数を、以下の新しいプレフィックスを持つ定数に置き換えています。

1.  **`TYPE_`**: オペランドの**種類**（例: 定数、メモリ、アドレス、分岐先など）を表します。
    *   `D_NONE` → `TYPE_NONE`
    *   `D_CONST` → `TYPE_CONST`
    *   `D_INDIR` → `TYPE_MEM` (メモリ参照を明示)
    *   `D_ADDR` → `TYPE_ADDR`
    *   `D_BRANCH` → `TYPE_BRANCH`
    *   `D_SCONST` → `TYPE_SCONST` (文字列定数)
    *   `D_FCONST` → `TYPE_FCONST` (浮動小数点定数)
    *   `D_CONST2` → `TYPE_TEXTSIZE` (テキストセクションのサイズなど、特殊な定数)

2.  **`REG_`**: CPUの**レジスタ**を明示的に識別します。
    *   `D_SP` → `REG_SP` (スタックポインタレジスタ)
    *   `D_AX` → `REG_AX` (AXレジスタ)
    *   `D_CX` → `REG_CX` (CXレジスタ)
    *   `D_DX` → `REG_DX` (DXレジスタ)
    *   `D_DI` → `REG_DI` (DIレジスタ)
    *   `D_SI` → `REG_SI` (SIレジスタ)
    *   `D_F0` → `REG_F0` (浮動小数点レジスタ)
    *   その他、`D_AL`, `D_AH`, `D_BL`, `D_BH`, `D_CL`, `D_CH`, `D_DL`, `D_DH`, `D_BP`, `D_BX`, `D_CS`, `D_ES`, `D_FS`, `D_GS`, `D_SS`, `D_TLS`, `D_X0`, `D_CR`, `D_DR`, `D_GDTR`, `D_IDTR`, `D_LDTR`, `D_MSW`, `D_TASK`, `D_TR` など、すべてのレジスタ関連の定数が`REG_`プレフィックスに統一されています。

3.  **`NAME_`**: シンボルやメモリ領域の**種類**（名前）を表します。
    *   `D_AUTO` → `NAME_AUTO` (自動変数)
    *   `D_PARAM` → `NAME_PARAM` (関数パラメータ)
    *   `D_EXTERN` → `NAME_EXTERN` (外部シンボル)
    *   `D_STATIC` → `NAME_STATIC` (静的シンボル)

この変更により、`Addr`構造体は、`type`フィールドでオペランドの一般的な種類を示し、`reg`フィールドでレジスタを、`name`フィールドでシンボル名を、それぞれ独立して表現できるようになります。例えば、以前は`D_INDIR+D_SP`のように`type`フィールドにレジスタ情報が埋め込まれていたものが、`type = TYPE_MEM`, `reg = REG_SP`のように明確に分離されます。

このリファクタリングは、主に以下のファイル群に影響を与えています。

*   **アセンブラ (`src/cmd/8a/`)**: `a.y` (Yacc文法定義), `lex.c` (Lexer定義), `y.tab.c` (Yacc生成コード) など。アセンブリ命令のパースと内部表現への変換ロジックが更新されています。
*   **コンパイラ (`src/cmd/8g/`)**: `cgen.c`, `cgen64.c` (コード生成), `ggen.c` (汎用コード生成), `gobj.c` (オブジェクトファイル生成), `gsubr.c` (サブルーチン関連) など。コンパイラのバックエンドにおける命令生成とオペランド処理のロジックが変更されています。
*   **リンキングライブラリ (`src/liblink/`)**: `asm8.c`, `list8.c`, `obj8.c` など。リンカがオブジェクトファイルを扱う際の内部表現が更新されています。

## コアとなるコードの解説

これらの変更は、Goツールチェインの内部表現のセマンティックな明確さを劇的に向上させます。

*   **`D_INDIR+D_ADDR` から `TYPE_INDIR`**: 以前は`D_INDIR`と`D_ADDR`を組み合わせて間接アドレス指定を表していましたが、これは`Addr`構造体の`type`フィールドが複数の意味を兼ねていたためです。`TYPE_INDIR`への変更は、オペランドが間接参照であることを明確に示し、その詳細（どのレジスタを基点とするかなど）は`Addr`構造体の他のフィールド（例: `reg`）で表現されるようになります。
*   **`$$.type = $1;` から `$$.type = TYPE_REG; $$.reg = $1;`**: レジスタの定義において、以前はレジスタの識別子（例: `D_AL`, `D_AX`）が直接`type`フィールドに代入されていました。これは、`type`フィールドがオペランドの種類とレジスタの両方を表すという曖昧さがありました。新しいコードでは、`type`フィールドを`TYPE_REG`に固定し、実際のレジスタ識別子を`reg`フィールドに格納することで、役割が明確に分離されます。これにより、`Addr`構造体を見ただけで、それがレジスタオペランドであり、どのレジスタであるかが一目でわかるようになります。
*   **`D_CONST` から `TYPE_CONST`**: 定数オペランドについても同様に、`type`フィールドが`TYPE_CONST`となり、定数の値は`offset`フィールドに格納されることで、セマンティクスが明確になります。
*   **`D_INDIR+D_NONE` や `D_INDIR+$3` から `TYPE_MEM` と `REG_NONE`/`REG_SP`/`$3`**: メモリ参照の表現が大幅に改善されています。以前は`D_INDIR`とレジスタの`D_`定数を組み合わせていましたが、これは非常に読みにくく、エラーの温床でした。新しい表現では、`type`フィールドが`TYPE_MEM`となり、メモリ参照であることを明確に示します。そして、基点となるレジスタは`reg`フィールドに、オフセットは`offset`フィールドに格納されます。これにより、`Addr`構造体がメモリ参照をどのように表現しているかが、より直感的になります。
*   **`D_AUTO` / `D_EXTERN` / `D_PARAM` / `D_STATIC` から `NAME_AUTO` / `NAME_EXTERN` / `NAME_PARAM` / `NAME_STATIC`**: シンボルの種類を示す定数も、`NAME_`プレフィックスに統一されました。これにより、`Addr`構造体の`name`フィールドがシンボル名に関連する情報を持つことが明確になります。

`appendpp`関数のシグネチャ変更も重要です。以前は`ftype`と`ttype`という単一の引数でソースとデスティネーションの型を扱っていましたが、新しいシグネチャでは`ftype`, `freg`, `ttype`, `treg`のように、型とレジスタが分離された引数を持つようになりました。これにより、命令を生成する際に、オペランドの型とレジスタをより明示的に指定できるようになり、コードの正確性と安全性が向上します。

全体として、このコミットは、Goツールチェインの内部表現を、より厳密で、自己記述的で、将来の変更に強いものにするための重要な基盤を築いています。これは、コンパイラ開発におけるベストプラクティスの一つであり、大規模なソフトウェアプロジェクトの長期的な健全性を保つ上で不可欠な改善です。

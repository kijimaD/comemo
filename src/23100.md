# [インデックス 23100] ファイルの概要

## 変更の背景

Go言語は通常、静的リンクを優先し、必要なすべてのコードとライブラリを最終的な実行可能ファイルに直接埋め込みます。これにより、バイナリの移植性が高まります。しかし、`cgo`を使用する場合や、Go 1.8で導入された`plugin`パッケージのように、Goバイナリが動的にリンクされるシナリオも存在します。

動的リンクされたプログラムでは、外部ライブラリのシンボル（関数やデータ）にアクセスする際に、Global Offset Table (GOT)やProcedure Linkage Table (PLT)といったメカニズムが使用されることが一般的です。これらのテーブルは、実行時にシンボルのアドレスを解決するために必要ですが、アクセスにオーバーヘッドを伴うことがあります。

このコミットの背景には、Goプログラム内で定義された文字列定数であっても、動的リンクが有効な場合にGOTを介してアクセスされることで発生するパフォーマンス上の問題がありました。特に、`fannkuch`ベンチマークのような計算負荷の高いプログラムでは、このオーバーヘッドが顕著になる可能性がありました。

この変更の目的は、Goコンパイラとリンカが、外部に公開する必要のない内部的なシンボル（特に文字列定数）を「ローカルシンボル」として識別し、GOTを介さずに直接アクセスできるようにすることで、動的リンク時のパフォーマンスを改善することです。これにより、静的リンク時と同等のレジスタ使用効率を動的リンク時にも実現し、全体的な実行効率を高めることを目指しています。

## 前提知識の解説

### 1. 動的リンクと静的リンク

*   **静的リンク**: プログラムが必要とするすべてのライブラリコードが、コンパイル時に最終的な実行可能ファイルに直接組み込まれる方式です。これにより、実行可能ファイルは自己完結型となり、他のシステムに配布する際に依存関係の問題が発生しにくくなります。Go言語のデフォルトのビルド挙動です。
*   **動的リンク**: プログラムが必要とするライブラリが、実行時にロードされる共有ライブラリ（例: Linuxの`.so`ファイル、Windowsの`.dll`ファイル）として提供される方式です。これにより、複数のプログラムが同じライブラリを共有でき、ディスクスペースとメモリ使用量を節約できます。しかし、ライブラリのバージョン管理や、実行環境に特定のライブラリが存在することへの依存といった課題があります。Goでは`cgo`や`plugin`パッケージを使用する際に動的リンクが関わってきます。

### 2. Global Offset Table (GOT) と Procedure Linkage Table (PLT)

ELF (Executable and Linkable Format) バイナリ（Linuxなどで一般的）における動的リンクの主要なメカニズムです。

*   **Global Offset Table (GOT)**: 共有ライブラリ内のグローバル変数や関数のアドレスを格納するテーブルです。プログラムが共有ライブラリ内のシンボルにアクセスしようとすると、まずGOTを参照します。初回アクセス時には、動的リンカが実際のシンボルアドレスを解決し、そのアドレスをGOTに書き込みます。2回目以降のアクセスでは、GOTにキャッシュされたアドレスを直接使用します。
*   **Procedure Linkage Table (PLT)**: 共有ライブラリ内の関数を呼び出すための「踏み台」となるテーブルです。関数呼び出しはまずPLTのエントリを介して行われます。PLTエントリはGOTを参照し、必要に応じて動的リンカを呼び出して関数のアドレスを解決します。

GOTとPLTは、プログラムと共有ライブラリ間の位置独立コード（PIC: Position-Independent Code）を実現するために不可欠です。PICは、メモリ上のどこにロードされても正しく実行できるコードであり、共有ライブラリで広く使用されます。

### 3. シンボルの可視性（グローバル vs ローカル）

動的リンクの文脈では、シンボルには「グローバル」と「ローカル」の可視性があります。

*   **グローバルシンボル**: 実行可能ファイルや共有ライブラリの外部から参照可能なシンボルです。他の共有ライブラリや実行可能ファイルからアクセスされる可能性があります。GOTを介したアクセスが必要になることが多いです。
*   **ローカルシンボル**: 実行可能ファイルや共有ライブラリの内部でのみ参照可能なシンボルです。外部からはアクセスされません。これらのシンボルへのアクセスは、GOTを介さずに、より直接的な（例: PC相対アドレッシング）方法で行うことができます。

このコミットで導入される「ローカルシンボル」は、Go言語のパッケージレベルの可視性（大文字で始まる識別子がエクスポートされるなど）とは異なり、**動的リンカの観点からのシンボルの可視性**を指します。

これらの変更により、Goコンパイラは、Goプログラム内部で完結する文字列定数などのシンボルを、動的リンカの観点から「ローカル」であると明示的にマークできるようになります。リンカとコードジェネレータは、この「ローカル」フラグを利用して、これらのシンボルへのアクセスにGOTを使用しない最適化された命令を生成します。結果として、動的リンクが有効な場合でも、文字列定数へのアクセスが効率化され、`fannkuch`ベンチマークのようなシナリオでレジスタ使用効率が向上し、静的リンク時とほぼ同等のパフォーマンスが期待できるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、Goのコンパイラ、リンカ、およびアセンブラが連携して、特定のシンボルを「ローカル」として扱い、動的リンク時のGOTアクセスを回避するようにすることです。

1.  **`LSym`構造体の`Local`フィールド**:
    このブール値のフィールドは、シンボルが現在のモジュール（実行可能ファイルまたは共有ライブラリ）の外部に公開されるべきではないことを示します。Goの内部的な文字列定数や、特定の型情報などは、通常、外部から直接参照される必要がないため、このフラグが`true`に設定されます。

2.  **`obj.LOCAL`フラグ**:
    これは、コンパイラが`ggloblsym`関数（グローバルシンボルを生成する関数）を呼び出す際に、そのシンボルをローカルとしてマークするための指示として使用されます。例えば、`stringsym`関数（文字列定数のシンボルを生成）では、このフラグが渡されるようになり、生成される文字列シンボルがローカルとして扱われるようになります。

3.  **`ggloblsym`関数の変更**:
    この関数は、`obj.LOCAL`フラグを受け取ると、生成する`LSym`オブジェクトの`Local`フィールドを`true`に設定します。これにより、コンパイラが意図したシンボルの可視性がリンカに正確に伝達されます。

4.  **`progedit`関数（`obj/x86/obj6.go`）の変更**:
    この関数は、アセンブラが生成する命令を編集し、リンカが後で処理できるように準備します。特に、動的リンクが有効な場合（`ctxt.Flag_dynlink`が`true`）、`ALEAQ`や`AMOVQ`といった命令が外部シンボルを参照する際に、`!p.From.Sym.Local`という条件が追加されました。
    *   `p.From.Name == obj.NAME_EXTERN`: これは、参照が外部シンボル（Goのパッケージ外、またはCライブラリなど）に対するものであることを示します。
    *   `!p.From.Sym.Local`: この新しい条件は、その外部シンボルが「ローカル」としてマークされていない場合にのみ、GOTを介したアクセスが必要であることを意味します。もしシンボルがローカルであれば、GOTを介さずに直接アクセスできるため、この最適化が適用されます。

これらの変更により、Goのツールチェーンは、動的リンクされたバイナリにおいて、内部的な文字列定数などのアクセスを最適化し、GOTを介した間接参照のオーバーヘッドを削減します。これは、特に多くの文字列定数を持つプログラムや、動的リンクがパフォーマンスに影響を与えるシナリオにおいて、実行効率の向上に寄与します。

## 変更の背景

Go言語は通常、静的リンクを優先し、必要なすべてのコードとライブラリを最終的な実行可能ファイルに直接埋め込みます。これにより、実行可能ファイルの移植性が高まります。しかし、`cgo`を使用する場合や、Go 1.8で導入された`plugin`パッケージのように、Goバイナリが動的にリンクされるシナリオも存在します。

動的リンクされたプログラムでは、外部ライブラリのシンボル（関数やデータ）にアクセスする際に、Global Offset Table (GOT)やProcedure Linkage Table (PLT)といったメカニズムが使用されることが一般的です。これらのテーブルは、実行時にシンボルのアドレスを解決するために必要ですが、アクセスにオーバーヘッドを伴うことがあります。

このコミットの背景には、Goプログラム内で定義された文字列定数であっても、動的リンクが有効な場合にGOTを介してアクセスされることで発生するパフォーマンス上の問題がありました。特に、`fannkuch`ベンチマークのような計算負荷の高いプログラムでは、このオーバーヘッドが顕著になる可能性がありました。

この変更の目的は、Goコンパイラとリンカが、外部に公開する必要のない内部的なシンボル（特に文字列定数）を「ローカルシンボル」として識別し、GOTを介さずに直接アクセスできるようにすることで、動的リンク時のパフォーマンスを改善することです。これにより、静的リンク時と同等のレジスタ使用効率を動的リンク時にも実現し、全体的な実行効率を高めることを目指しています。

## 前提知識の解説

### 1. 動的リンクと静的リンク

*   **静的リンク**: プログラムが必要とするすべてのライブラリコードが、コンパイル時に最終的な実行可能ファイルに直接組み込まれる方式です。これにより、実行可能ファイルは自己完結型となり、他のシステムに配布する際に依存関係の問題が発生しにくくなります。Go言語のデフォルトのビルド挙動です。
*   **動的リンク**: プログラムが必要とするライブラリが、実行時にロードされる共有ライブラリ（例: Linuxの`.so`ファイル、Windowsの`.dll`ファイル）として提供される方式です。これにより、複数のプログラムが同じライブラリを共有でき、ディスクスペースとメモリ使用量を節約できます。しかし、ライブラリのバージョン管理や、実行環境に特定のライブラリが存在することへの依存といった課題があります。Goでは`cgo`や`plugin`パッケージを使用する際に動的リンクが関わってきます。

### 2. Global Offset Table (GOT) と Procedure Linkage Table (PLT)

ELF (Executable and Linkable Format) バイナリ（Linuxなどで一般的）における動的リンクの主要なメカニズムです。

*   **Global Offset Table (GOT)**: 共有ライブラリ内のグローバル変数や関数のアドレスを格納するテーブルです。プログラムが共有ライブラリ内のシンボルにアクセスしようとすると、まずGOTを参照します。初回アクセス時には、動的リンカが実際のシンボルアドレスを解決し、そのアドレスをGOTに書き込みます。2回目以降のアクセスでは、GOTにキャッシュされたアドレスを直接使用します。
*   **Procedure Linkage Table (PLT)**: 共有ライブラリ内の関数を呼び出すための「踏み台」となるテーブルです。関数呼び出しはまずPLTのエントリを介して行われます。PLTエントリはGOTを参照し、必要に応じて動的リンカを呼び出して関数のアドレスを解決します。

GOTとPLTは、プログラムと共有ライブラリ間の位置独立コード（PIC: Position-Independent Code）を実現するために不可欠です。PICは、メモリ上のどこにロードされても正しく実行できるコードであり、共有ライブラリで広く使用されます。

### 3. シンボルの可視性（グローバル vs ローカル）

動的リンクの文脈では、シンボルには「グローバル」と「ローカル」の可視性があります。

*   **グローバルシンボル**: 実行可能ファイルや共有ライブラリの外部から参照可能なシンボルです。他の共有ライブラリや実行可能ファイルからアクセスされる可能性があります。GOTを介したアクセスが必要になることが多いです。
*   **ローカルシンボル**: 実行可能ファイルや共有ライブラリの内部でのみ参照可能なシンボルです。外部からはアクセスされません。これらのシンボルへのアクセスは、GOTを介さずに、より直接的な（例: PC相対アドレッシング）方法で行うことができます。

このコミットで導入される「ローカルシンボル」は、Go言語のパッケージレベルの可視性（大文字で始まる識別子がエクスポートされるなど）とは異なり、**動的リンカの観点からのシンボルの可視性**を指します。

## 技術的詳細

このコミットの核心は、Goコンパイラとリンカが、Goプログラム内部で定義されたシンボル（特に文字列定数）を、動的リンカの観点から「ローカル」として明示的にマークする機能を追加することです。これにより、これらのシンボルへのアクセスパスが最適化され、GOTを介した間接参照が不要になります。

具体的な変更点は以下の通りです。

1.  **`LSym`構造体への`Local`フィールドの追加**:
    `src/cmd/internal/obj/link.go` に定義されている`LSym`構造体（リンカが扱うシンボルを表す）に、`Local bool`フィールドが追加されました。このフィールドは、そのシンボルが動的リンカの観点からローカルであるかどうかを示します。コメントには「動的リンカの意味でのローカル、つまり、その定義を含むモジュール（共有ライブラリまたは実行可能ファイル）の外部からは見えない」と明記されています。

2.  **`obj.LOCAL`フラグの導入**:
    `src/cmd/internal/obj/textflag.go` に新しい定数`LOCAL = 128`が追加されました。これは、`ggloblsym`関数に渡される際に、作成される`LSym`の`Local`フィールドを`true`に設定するためのフラグとして使用されます。

3.  **コンパイラ（`gc`）でのローカルシンボルマーク**:
    `src/cmd/internal/gc/gsubr.go` の`ggloblsym`関数が変更され、`obj.LOCAL`フラグを受け取って`LSym.Local`を設定できるようになりました。
    `src/cmd/internal/gc/obj.go` や `src/cmd/internal/gc/pgen.go`, `src/cmd/internal/gc/reflect.go` では、文字列定数や型情報など、Goプログラム内部で完結するシンボルを生成する際に、`obj.LOCAL`フラグを`ggloblsym`に渡すように変更されています。これにより、これらのシンボルがリンカによってローカルとして扱われるようになります。

4.  **リンカ（`ld`）でのローカルシンボル処理**:
    `src/cmd/internal/ld/objfile.go` では、オブジェクトファイルからシンボルを読み込む際に、新しいフラグ（`flags & 2`）をチェックして`LSym.Local`フィールドを設定するロジックが追加されました。
    `src/cmd/internal/ld/symtab.go` では、以前はシンボル名に基づいて（例: `..gostring.`を含むシンボル）ローカルとしてマークしていたロジックが削除され、コンパイラから渡される`LSym.Local`フラグを信頼するようになりました。

5.  **アセンブラ/コード生成（`obj/x86`）でのGOT回避**:
    `src/cmd/internal/obj/x86/obj6.go` では、x86アーキテクチャ向けのコード生成ロジックが変更されました。特に、`ALEAQ` (Load Effective Address Quadword) や `AMOVQ` (Move Quadword) といった命令で、外部シンボルへの参照を処理する際に、そのシンボルが`LSym.Local`であるかどうかをチェックするようになりました。`!p.From.Sym.Local`の条件が追加されたことで、ローカルシンボルに対してはGOTを介した間接参照を避け、より直接的なアドレス指定を行うようになります。

これらの変更により、Goコンパイラは、Goプログラム内部で完結する文字列定数などのシンボルを、動的リンカの観点から「ローカル」であると明示的にマークできるようになります。リンカとコードジェネレータは、この「ローカル」フラグを利用して、これらのシンボルへのアクセスにGOTを使用しない最適化された命令を生成します。結果として、動的リンクが有効な場合でも、文字列定数へのアクセスが効率化され、`fannkuch`ベンチマークのようなシナリオでレジスタ使用効率が向上し、静的リンク時とほぼ同等のパフォーマンスが期待できるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、Goのコンパイラ、リンカ、およびアセンブラが連携して、特定のシンボルを「ローカル」として扱い、動的リンク時のGOTアクセスを回避するようにすることです。

1.  **`LSym`構造体の`Local`フィールド**:
    このブール値のフィールドは、シンボルが現在のモジュール（実行可能ファイルまたは共有ライブラリ）の外部に公開されるべきではないことを示します。Goの内部的な文字列定数や、特定の型情報などは、通常、外部から直接参照される必要がないため、このフラグが`true`に設定されます。

2.  **`obj.LOCAL`フラグ**:
    これは、コンパイラが`ggloblsym`関数（グローバルシンボルを生成する関数）を呼び出す際に、そのシンボルをローカルとしてマークするための指示として使用されます。例えば、`stringsym`関数（文字列定数のシンボルを生成）では、このフラグが渡されるようになり、生成される文字列シンボルがローカルとして扱われるようになります。

3.  **`ggloblsym`関数の変更**:
    この関数は、`obj.LOCAL`フラグを受け取ると、生成する`LSym`オブジェクトの`Local`フィールドを`true`に設定します。これにより、コンパイラが意図したシンボルの可視性がリンカに正確に伝達されます。

4.  **`progedit`関数（`obj/x86/obj6.go`）の変更**:
    この関数は、アセンブラが生成する命令を編集し、リンカが後で処理できるように準備します。特に、動的リンクが有効な場合（`ctxt.Flag_dynlink`が`true`）、`ALEAQ`や`AMOVQ`といった命令が外部シンボルを参照する際に、`!p.From.Sym.Local`という条件が追加されました。
    *   `p.From.Name == obj.NAME_EXTERN`: これは、参照が外部シンボル（Goのパッケージ外、またはCライブラリなど）に対するものであることを示します。
    *   `!p.From.Sym.Local`: この新しい条件は、その外部シンボルが「ローカル」としてマークされていない場合にのみ、GOTを介したアクセスが必要であることを意味します。もしシンボルがローカルであれば、GOTを介さずに直接アクセスできるため、この最適化が適用されます。

これらの変更により、Goのツールチェーンは、動的リンクされたバイナリにおいて、内部的な文字列定数などのアクセスを最適化し、GOTを介した間接参照のオーバーヘッドを削減します。これは、特に多くの文字列定数を持つプログラムや、動的リンクがパフォーマンスに影響を与えるシナリオにおいて、実行効率の向上に寄与します。

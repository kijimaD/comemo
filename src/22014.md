## 変更の背景

Go言語のツールチェーンにおいて、アセンブラが生成するバイナリに含まれる行番号情報は、デバッグ、スタックトレースの生成、プロファイリング、エラー報告といった様々な開発プロセスにおいて極めて重要です。

*   **デバッグ**: デバッガ（例: Delve）は、実行中のプログラムのどのソースコード行にいるかを開発者に示すために、正確な行番号情報に依存します。行番号が不正確だと、ブレークポイントが意図しない場所でヒットしたり、表示されるソースコードが実際の実行位置とずれたりして、デバッグ作業が著しく困難になります。
*   **スタックトレース**: プログラムがパニックを起こしたり、ランタイムエラーに遭遇したりした場合、Goランタイムはスタックトレースを生成します。このトレースは、エラー発生に至るまでの関数呼び出しのシーケンスを、それぞれの呼び出しが発生したファイル名と行番号とともに示します。行番号が間違っていると、エラーの根本原因を特定し、ソースコード内の正確な位置を特定することが不可能になります。
*   **プロファイリング**: CPU使用率やメモリ使用量などのパフォーマンスデータを収集するプロファイリングツールは、そのデータをソースコードの特定の行に関連付けて表示することがよくあります。正確な行番号は、パフォーマンスのボトルネックがコードのどの部分にあるかを正確に特定するために不可欠です。
*   **エラー報告**: コンパイラや静的解析ツールは、エラーや警告を報告する際に、開発者が問題のあるコードに直接アクセスできるよう、行番号を使用します。

このコミットは、`cmd/9a` および `cmd/new9a` というGoのアセンブラが、これらの重要な行番号情報を誤って処理していた問題を修正することを目的としています。これにより、Goプログラムのデバッグ、エラー報告、およびプロファイリングの信頼性と精度が向上します。コミットメッセージには、2010年のCL 2297042で他のアセンブラに対して同様の修正が行われたことが示されており、この問題がGoツールチェーン全体で段階的に修正されてきた経緯が伺えます。

## 前提知識の解説

*   **アセンブラ (Assembler)**: アセンブラは、アセンブリ言語で書かれたプログラムを、コンピュータが直接実行できる機械語（バイナリコード）に変換するプログラムです。Go言語のビルドプロセスでは、Goのソースコードはまず中間表現に変換され、最終的に各アーキテクチャ向けのアセンブリコードを経て機械語に変換されます。
*   **`cmd/9a` と `cmd/new9a`**: これらはGo言語のツールチェーンに含まれるアセンブラです。
    *   `cmd/9a` は、Plan 9オペレーティングシステムに由来するGoの初期のアセンブラ群の一部でした。`9a` は `amd64` アーキテクチャ（および `386`、`arm` など、`9` はアーキテクチャのプレースホルダー）用のアセンブラを指すことが多かったです。
    *   `cmd/new9a` は、より新しい、統合されたアセンブラであり、現代のGoでは `go tool asm` として利用されています。これは、以前のアーキテクチャ固有のアセンブラを置き換える形で開発されました。
    これらのツールは、Goのコンパイラによって生成されたアセンブリコードを、実行可能なバイナリに変換する役割を担っています。
*   **行番号情報**: ソースコードの各行が、コンパイルされたバイナリ内のどの機械語命令に対応するかを示すメタデータです。この情報は、デバッグシンボルとしてバイナリに埋め込まれるか、別途デバッグ情報ファイルとして提供されます。
*   **Yacc/Bison (`.y` ファイル)**: `a.y` ファイルは、Yacc（Yet Another Compiler Compiler）またはそのGNU版であるBisonによって生成されるパーサの定義ファイルです。Yacc/Bisonは、文法規則に基づいてソースコードを解析し、構文木を構築するためのC言語（またはGo言語）のコードを生成します。
*   **Lex/Flex (`.c` または `.go` ファイル)**: `lex.c` や `lex.go` ファイルは、Lex（Lexical Analyzer Generator）またはそのGNU版であるFlexによって生成される字句解析器（レクサー）の定義ファイルです。字句解析器は、ソースコードを読み込み、トークン（キーワード、識別子、演算子など）のストリームに分割します。
*   **`lineno` と `stmtline`**:
    *   `lineno` は、字句解析器が現在処理しているソースコードの行番号を指す変数であることが一般的です。これは、入力ストリームの現在の位置を追跡するために使用されます。
    *   `stmtline` は、このコミットで導入された新しい概念で、おそらく現在解析中の「ステートメント」の開始行番号を保持するために使用されます。Yacc/Bisonのようなパーサジェネレータでは、複数の字句（トークン）が結合されて一つの文法規則（ステートメント）を形成することがあります。この場合、`lineno` はトークンごとに更新されますが、`stmtline` はステートメント全体の開始行を正確に記録するために導入されたと考えられます。

## 技術的詳細

このコミットの核心は、アセンブラが生成する `Prog` (プログラム命令) 構造体の `lineno` フィールドに設定される値の変更にあります。以前は、字句解析器が提供する現在の行番号 `lineno` が直接使用されていました。しかし、これは特定の文法規則の解析中に、`lineno` が複数のトークンを処理する過程で更新され、結果として `Prog` に設定される行番号が、その命令が属するステートメントの開始行ではなく、ステートメントの途中の行や終了行になってしまう可能性がありました。

この問題を解決するため、以下の変更が導入されました。

1.  **`stmtline` 変数の導入**: `src/cmd/9a/a.h` および `src/cmd/new9a/a.h` に `EXTERN int32 stmtline;` が追加されました。これは、ステートメントの開始行番号を保持するためのグローバル変数です。
2.  **パーサにおける `stmtline` の更新**: `src/cmd/9a/a.y` および `src/cmd/new9a/a.y` のYacc/Bison定義ファイルにおいて、`prog` 規則（プログラム全体の解析を開始する最上位の規則）が変更されました。具体的には、各 `line` (アセンブリの1行の命令やディレクティブ) の解析が始まる直前に、`stmtline = lineno;` というアクションが追加されました。これにより、新しいステートメントの処理が開始されるたびに、`stmtline` がその時点の `lineno` (つまり、ステートメントの開始行) で更新されるようになります。
3.  **`Prog` 構造体への `stmtline` の適用**: `src/cmd/9a/lex.c` および `src/cmd/new9a/lex.go` の字句解析器の出力関数 (`outcode`, `outgcode`) において、`Prog` 構造体の `lineno` フィールドに `lineno` の代わりに `stmtline` が設定されるように変更されました。
    *   C言語版 (`src/cmd/9a/lex.c`): `p->lineno = lineno;` が `p->lineno = stmtline;` に変更。
    *   Go言語版 (`src/cmd/new9a/lex.go`): `p.Lineno = lineno` が `p.Lineno = stmtline` に変更。

この変更により、アセンブラが生成する機械語命令には、その命令が属するアセンブリ言語のステートメントの正確な開始行番号が関連付けられるようになります。これにより、デバッグ情報、スタックトレース、プロファイリングデータにおける行番号の精度が大幅に向上し、開発者がGoプログラムの問題をより正確に特定できるようになります。

また、`a.y` ファイル内の `YYLAST`, `YYNNTS`, `YYNRULES`, `YYNSTATES` といったBisonが生成する定数の値が変更されているのは、文法規則の追加や変更（特に `prog` 規則の変更）によって、パーサの内部構造が再生成された結果です。これは、行番号修正のための文法変更がパーサに影響を与えたことを示しています。

## コアとなるコードの解説

変更の核心は、アセンブラが生成する `Prog` (プログラム命令) オブジェクトに付与される行番号のソースを `lineno` から `stmtline` へと切り替えた点にあります。

*   **`src/cmd/9a/a.h` / `src/cmd/new9a/a.h`**:
    `EXTERN int32 stmtline;`
    この行は、`stmtline` という32ビット整数型のグローバル変数を宣言しています。`EXTERN` キーワードは、この変数が他のファイルで定義されていることを示唆しており、複数のファイル間で共有されることを意味します。この変数が、現在処理中のアセンブリステートメントの開始行番号を保持します。

*   **`src/cmd/9a/a.y` / `src/cmd/new9a/a.y`**:
    ```diff
    --- a/src/cmd/9a/a.y
    +++ b/src/cmd/9a/a.y
    @@ -64,7 +64,11 @@
     %type	<addr>	imm ximm fimm rel psr lcr cbit fpscr msr mask
     %%
     prog:
    -|	prog line
    +|	prog
    +	{
    +		stmtline = lineno;
    +	}
    +	line
     ```
     このYacc/Bisonの文法定義の変更は非常に重要です。`prog` 規則は、アセンブリプログラム全体を解析する際の最上位の規則です。その中で、`line` (アセンブリの1行の命令やディレクティブ) を処理する直前に、`{ stmtline = lineno; }` というアクションが追加されています。
     これは、新しいアセンブリステートメントの解析が始まるたびに、その時点での字句解析器の現在の行番号 (`lineno`) を `stmtline` にコピーすることを意味します。これにより、`stmtline` は常に現在のステートメントの「開始行」を正確に指すようになります。

*   **`src/cmd/9a/lex.c` / `src/cmd/new9a/lex.go`**:
    ```diff
    --- a/src/cmd/9a/lex.c
    +++ b/src/cmd/9a/lex.c
    @@ -672,7 +672,7 @@ outcode(int a, Addr *g1, int reg, Addr *g2)

     	p = emallocz(sizeof(Prog));
     	p->as = a;
    -	p->lineno = lineno;
    +	p->lineno = stmtline;
     	if(nosched)
     		p->mark |= NOSCHED;
     	p->from = *g1;
    ```
    `outcode` および `outgcode` 関数は、アセンブリ命令を `Prog` 構造体として出力する役割を担っています。この変更により、`Prog` 構造体の `lineno` フィールドに、字句解析器の現在の行番号 (`lineno`) ではなく、パーサによって設定されたステートメントの開始行番号 (`stmtline`) が代入されるようになりました。
    これにより、生成される機械語命令には、その命令が属するアセンブリ言語のステートメントの正確な開始行番号が関連付けられ、デバッグ情報やスタックトレースの精度が向上します。

これらの変更は、アセンブラがソースコードの行番号情報をどのように解釈し、バイナリに埋め込むかという根本的なロジックを修正するものであり、Go言語のツールチェーンの信頼性を高める上で重要な役割を果たします。

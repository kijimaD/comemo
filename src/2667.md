## 変更の背景

このコミットの背景には、Goの `gob` パッケージの効率的なデータエンコーディング戦略があります。`gob` は、データをバイナリ形式でシリアライズする際に、エンコードされる値の型情報を一緒に送信します。しかし、同じ型の値が複数回エンコードされる場合、毎回型情報を送信するのは冗長であり、ネットワーク帯域やストレージを無駄にします。

`gob` パッケージは、この非効率性を避けるために、一度送信された型情報については、その後の同じ型の値のエンコード時には型情報を再送信しないように設計されています。代わりに、既に送信済みの型を参照するための「型ID」のみを送信します。

このコミットは、この重要な最適化が正しく機能していることを保証するためのテストケースを追加するものです。具体的には、同じ型の値を2回エンコードした際に、2回目のエンコードでは型情報が送信されず、型IDのみが送信されることを検証しています。これにより、`gob` の設計意図通りの動作が保証され、将来の変更によってこの挙動が意図せず壊れることを防ぎます。

## 前提知識の解説

### Goの `gob` パッケージ

`gob` は、Goプログラム間でGoのデータ構造をエンコードおよびデコードするためのGo固有のバイナリ形式です。主な特徴は以下の通りです。

-   **自己記述型**: `gob` ストリームは、エンコードされたデータの型情報を自身で含んでいます。これにより、デコード側は事前に型定義を知らなくてもデータを正しく解釈できます。
-   **効率性**: 型情報は一度だけ送信され、その後は型IDで参照されます。これにより、同じ型のデータが繰り返し送信される場合に効率的です。
-   **Go固有**: Goの型システム（構造体、インターフェース、マップ、スライスなど）に特化しており、リフレクションを活用して動作します。
-   **ストリーム指向**: 連続するデータのストリームをエンコード・デコードするのに適しています。

### `gob` の型情報と型ID

`gob` エンコーダは、新しい型に遭遇すると、その型の完全な記述（フィールド名、型など）をエンコードストリームに書き込み、その型に一意の「型ID」を割り当てます。この型IDは負の整数で表現されます。

一度型情報が送信されると、エンコーダはその型IDを記憶します。同じ型の値が次にエンコードされる際には、完全な型情報の代わりに、その型ID（負の整数）のみが送信されます。デコーダは、この型IDを受け取ると、以前に受信した型情報と照合してデータを正しくデコードします。

このメカニズムにより、特にネットワーク経由で大量の構造化データを送信する場合や、永続化する際に、データサイズを大幅に削減できます。

### `gob` のエンコード/デコードの流れ（簡略版）

1.  **エンコード**:
    *   `gob.NewEncoder(writer)` でエンコーダを作成。
    *   `encoder.Encode(value)` を呼び出す。
    *   エンコーダは `value` の型をチェック。
    *   もしその型が初めてエンコードされる場合、型情報をストリームに書き込み、型IDを割り当てる。
    *   その後、値自体をバイナリ形式でストリームに書き込む。
    *   もしその型が既にエンコードされている場合、型IDのみをストリームに書き込み、その後値自体を書き込む。
2.  **デコード**:
    *   `gob.NewDecoder(reader)` でデコーダを作成。
    *   `decoder.Decode(pointerToValue)` を呼び出す。
    *   デコーダはストリームから次の要素を読み込む。
    *   もし型情報が読み込まれた場合、それを内部に登録し、対応する型IDを記憶する。
    *   もし型IDが読み込まれた場合、既に登録されている型情報と照合する。
    *   その後、バイナリデータを読み込み、提供されたポインタ先の変数にデコードする。

## 技術的詳細

このコミットで追加されたテストは、`gob` エンコーダが型情報を一度だけ送信し、その後は型IDのみを送信するという挙動を厳密に検証しています。

テストのロジックは以下のステップで構成されています。

1.  **最初のエンコード**:
    *   `ET1` という構造体のインスタンス `et1` を作成し、`gob` エンコーダでエンコードします。
    *   この際、`gob` は `ET1` の型情報をストリームに書き込み、それに割り当てられた型ID（負の整数）を送信します。
    *   その後、`et1` の値がエンコードされます。
    *   デコード側では、この型情報と値が正しくデコードされることを確認します。

2.  **2回目のエンコード（本コミットの焦点）**:
    *   同じ `et1` インスタンス（または同じ型の別のインスタンス）を再度エンコードします。
    *   `gob` エンコーダは、`ET1` 型が既にエンコードされたことがあると認識しているため、今回は**型情報を送信せず**、以前に割り当てられた型ID（負の整数）のみを送信します。
    *   その後、`et1` の値がエンコードされます。
    *   テストでは、この2回目のエンコードで、ストリームから読み取られる最初の要素が、期待される型ID（負の整数）であることを確認します。もし型情報が誤って再送信されていれば、このチェックは失敗します。
    *   最後に、デコードされた値が元の値と完全に一致すること（`reflect.DeepEqual` を使用）を確認し、データの整合性を保証します。

このテストは、`gob` の内部状態管理、特に型情報のキャッシュと再利用のメカニズムが正しく機能していることを保証するために不可欠です。これにより、`gob` ストリームの効率性が維持されます。

	// Now do it again. This time we should see only the type id and value.
	b.Reset();
	enc.Encode(et1);
	if enc.state.err != nil {
		t.Error("2nd round: encoder fail:", enc.state.err)

	// 5a) The type id for the et1 value
	newId1 = DecodeInt(state);

	if !reflect.DeepEqual(et1, newEt1) {
		t.Fatalf("2nd round: invalid data for et1: expected %+v; got %+v\n", *et1, *newEt1);
	}
	// 7a) EOF
	if b.Len() != 0 {
		t.Error("2nd round: not at eof;", b.Len(), "bytes left")

## コアとなるコードの解説

追加されたコードは、`TestBasicEncoder` 関数内で、最初のエンコードとデコードが成功した後、同じ `et1` 変数を再度エンコードし、その結果を検証するものです。

1.  `b.Reset()`: `bytes.Buffer` `b` をリセットし、以前のエンコードデータ（最初のエンコード結果）をクリアします。これにより、2回目のエンコード結果のみを独立して検証できます。
2.  `enc.Encode(et1)`: `et1` (型 `ET1` の構造体インスタンス) を再度エンコードします。`gob` エンコーダは、`ET1` 型が既に登録されていることを認識しているため、この時点では型情報ではなく、型IDのみをストリームに書き込むはずです。
3.  `if enc.state.err != nil`: エンコード中にエラーが発生しなかったことを確認します。
4.  `newId1 = DecodeInt(state)`: エンコードされたストリームから最初の整数（型ID）をデコードします。`state` は、エンコードされたバイナリデータを読み取るためのヘルパーオブジェクトです。
5.  `if newId1 != -id1`: ここがこのテストの核心です。
    *   `id1` は最初のエンコード時に `ET1` 型に割り当てられた型IDです。`gob` の慣例により、型IDは負の整数で表現されます。
    *   2回目のエンコードでは、型情報ではなく、この負の型IDが送信されることを期待しています。
    *   したがって、デコードされた `newId1` が `-id1` と等しいことを検証します。もし等しくなければ、型情報が誤って再送信されたか、型IDが正しく送信されなかったことを意味し、テストは失敗します。
6.  `newEt1 = new(ET1)`: デコード結果を格納するための新しい `ET1` 型のポインタを作成します。
7.  `err = Decode(b, newEt1)`: ストリームに残っているデータ（`et1` の値）を `newEt1` にデコードします。
8.  `if err != nil`: デコード中にエラーが発生しなかったことを確認します。
9.  `if !reflect.DeepEqual(et1, newEt1)`: デコードされた `newEt1` の値が、元の `et1` の値と完全に一致することを確認します。これは、型情報が正しく処理され、データが破損なく転送されたことを保証します。
10. `if b.Len() != 0`: ストリームの終端に到達し、余分なデータが残っていないことを確認します。

この一連のステップにより、`gob` エンコーダが同じ型の値を複数回エンコードする際に、型情報の冗長な送信を適切に抑制し、かつデータの整合性を保っていることが厳密に検証されます。

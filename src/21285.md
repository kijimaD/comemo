# [インデックス 21285] ファイルの概要

このコミットは、Goコンパイラのリンカである`liblink`がPPC64アーキテクチャ向けに`MOVD`命令を生成する際のバグを修正するものです。具体的には、レジスタからのオフセットを持つ負の定数（例: `$-n(Rm)`）が誤って処理され、レジスタ情報が失われる問題を解決します。

## 元コミット内容

PPC64アーキテクチャにおいて、`liblink`が32ビットを超える定数に対する`MOVD`命令を、定数をメモリに配置し、そのメモリアドレスからロードするように書き換える際に、条件判定に2つのバグがありました。

a) 誤った符号拡張により、すべての負の定数に対してこの書き換えがトリガーされていました。
b) レジスタからの定数オフセット（アセンブリにおける`$n(Rm)`形式のアドレス）に対してもトリガーされる可能性がありました。

これらのバグが組み合わさることで、`MOVD $-n(Rm), x`のような形式の命令が、`-n`をメモリに配置し、その定数をメモリからロードするように書き換えられ、結果としてレジスタ`Rm`の情報が完全に失われていました。このコミットはこれらの問題を修正します。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、アセンブリコードを生成し、それをリンカが最終的な実行可能ファイルに結合します。PPC64アーキテクチャでは、特定の命令（`MOVD`など）が大きな定数を直接オペランドとして扱えない場合があります。このような場合、コンパイラやリンカは、その定数をメモリ上のどこかに配置し、そこからロードするような命令シーケンスに変換（書き換え）します。

このコミットの背景には、PPC64アーキテクチャにおける定数処理の最適化と、それに伴うバグがありました。特に、32ビットを超える定数（またはそのように誤認された定数）を扱う際に、`liblink`が不適切な書き換えを行ってしまう問題です。

問題の核心は、`MOVD $-n(Rm), x`のような命令、つまり「レジスタ`Rm`から`-n`のオフセットにあるメモリ位置から値`x`をロードする」という意図の命令が、誤って「`-n`という定数をメモリに配置し、そこから`x`にロードする」という命令に変換されてしまうことでした。これにより、本来オフセットの基準となるべきレジスタ`Rm`が無視され、プログラムの動作が不正になる可能性がありました。

このバグは、特に負の定数とレジスタオフセットの組み合わせで顕在化し、GoプログラムがPPC64上で正しく動作しない原因となっていました。

## 前提知識の解説

### Goコンパイラと`liblink`

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。このツールチェーンには、フロントエンド（Goソースコードの解析）、バックエンド（アセンブリコードの生成）、そしてリンカが含まれます。

`liblink`は、Goコンパイラツールチェーンにおけるリンカの役割を担うライブラリです。アセンブリコード（Goのアセンブリ言語はPlan 9アセンブリに似ています）を解析し、オブジェクトファイルや共有ライブラリ、最終的な実行可能ファイルを生成します。この過程で、アセンブリ命令のオペランドの解決、アドレスの再配置、そして特定の命令の最適化や書き換え（このコミットで扱われているような定数処理の書き換えなど）を行います。

### PPC64アーキテクチャ

PPC64（PowerPC 64-bit）は、IBMが開発したPowerPC命令セットアーキテクチャの64ビット版です。RISC（Reduced Instruction Set Computer）アーキテクチャであり、固定長の命令、多数の汎用レジスタ、ロード/ストアアーキテクチャ（メモリへのアクセスはロード命令とストア命令のみで行われる）などの特徴を持ちます。

PPC64の命令セットには、メモリからのロードやメモリへのストアを行うための命令が含まれます。これらの命令は、ベースレジスタとオフセットを組み合わせてメモリアドレスを指定することが一般的です。例えば、`n(Rm)`という形式は、「レジスタ`Rm`の値に`n`を加えたアドレス」を意味します。

### `MOVD`命令 (PPC64における)

PPC64における`MOVD`命令は、一般的にデータを移動（Move Doubleword）させるために使用されます。これは、64ビットのデータをレジスタ間で移動させたり、メモリとレジスタ間で移動させたりする際に使われます。

このコミットの文脈では、`MOVD`は「メモリからレジスタへデータをロードする」または「レジスタからメモリへデータをストアする」操作を指します。特に、`MOVD $constant, Reg`のような形式は、「`constant`という値を`Reg`レジスタにロードする」ことを意味します。また、`MOVD offset(Reg), Reg2`のような形式は、「`Reg`レジスタの値に`offset`を加えたメモリアドレスからデータを`Reg2`レジスタにロードする」ことを意味します。

### 定数とアドレス指定

アセンブリ言語では、定数は命令のオペランドとして直接指定されることがあります。しかし、命令のビット幅には限りがあるため、非常に大きな定数や、特定の命令が直接扱えない形式の定数は、メモリに配置されてからロードされるという間接的な方法が取られます。

PPC64では、メモリへのアクセスは通常、ベースレジスタとオフセットの組み合わせで行われます。`$n(Rm)`という表記は、Goのアセンブリ言語（Plan 9アセンブリ）におけるアドレス指定モードの一つで、「レジスタ`Rm`の値に定数`n`を加えたアドレス」を意味します。ここで`n`はオフセット値です。

### 符号拡張 (Sign Extension)

符号拡張とは、より小さいビット幅の数値（例えば32ビット整数）を、より大きいビット幅の数値（例えば64ビット整数）に変換する際に、元の数値の符号を保持するために、上位ビットを符号ビットで埋める操作です。

例えば、8ビットの符号付き整数で`-1`は`11111111`と表現されます。これを16ビットに符号拡張すると、`1111111111111111`となります。もし符号拡張が正しく行われず、単にゼロで埋められた場合（ゼロ拡張）、`-1`は大きな正の数として扱われてしまい、計算結果が狂います。

このコミットでは、負の定数を扱う際に誤った符号拡張が行われ、本来32ビットの範囲に収まる負の定数も、32ビットを超える定数として誤認され、不必要なメモリへの書き換えがトリガーされる原因となっていました。

## 技術的詳細

このコミットが修正する問題は、`liblink`がPPC64アーキテクチャ向けに`MOVD`命令を処理する際の、定数オペランドの誤った認識に起因します。

`liblink`は、`MOVD`命令のソースオペランドが32ビットを超える定数であると判断した場合、その定数をデータセクション（またはリテラルプール）に配置し、そのメモリ位置から値をロードする命令に書き換える最適化（または必要処理）を行います。これは、PPC64の命令が直接扱える定数のサイズに制限があるためです。

しかし、この書き換えをトリガーする条件判定に2つのバグがありました。

1.  **誤った符号拡張**:
    元のコードでは、`p->from.offset`（オペランドのオフセット値）が`int64`型にキャストされる際に、`uint32`に一度キャストされてから`int64`にキャストされていました。
    ` (int64)(uint32)p->from.offset != p->from.offset`
    この` (uint32)p->from.offset`という中間キャストが問題でした。例えば、`p->from.offset`が`-1`のような負の32ビット整数であった場合、`uint32`にキャストされると、そのビットパターンは大きな正の数として解釈されます（例: `0xFFFFFFFF`）。その後、`int64`にキャストされても、その大きな正の数値がそのまま`int64`として扱われるため、元の負の数とは異なる値となり、結果として「32ビットを超える定数」であると誤って判断されていました。これにより、本来メモリに配置する必要のない負の定数まで、不必要にメモリに配置されることになっていました。

2.  **レジスタオフセットの誤認識**:
    元の条件判定では、`p->from.type == D_CONST`（定数オペランドであること）と`p->from.name == D_NONE`（名前がないこと）のみをチェックしていました。しかし、`$n(Rm)`のような形式のアドレスは、`D_CONST`タイプを持ち、`p->from.offset`に`n`が、`p->from.reg`に`Rm`が設定されます。元の条件では`p->from.reg`がチェックされていなかったため、レジスタからのオフセットを持つアドレスも、単なる大きな定数として誤認される可能性がありました。

これらのバグが組み合わさることで、`MOVD $-n(Rm), x`のような命令が特に問題となりました。
- `-n`という負のオフセットが、誤った符号拡張により「32ビットを超える定数」と判断される。
- `Rm`というレジスタ情報が、条件判定で考慮されないため無視される。

結果として、`liblink`は`-n`をメモリに配置し、そこからロードする命令に書き換えてしまい、本来の意図である「`Rm`からのオフセット」という情報が完全に失われ、プログラムの動作が不正になるという深刻な問題を引き起こしていました。

## コアとなるコードの解説

変更の核心は、`src/liblink/obj9.c`の`progedit`関数内の`AMOVD`命令を処理する`case`文にあります。

元のコード:
```c
if(p->from.type == D_CONST && p->from.name == D_NONE && (int64)(uint32)p->from.offset != p->from.offset) {
```

修正後のコード:
```c
// Put >32-bit constants in memory and load them
if(p->from.type == D_CONST && p->from.name == D_NONE && p->from.reg == NREG && (int32)p->from.offset != p->from.offset) {
```

この変更により、条件判定がより正確になりました。

1.  **`p->from.reg == NREG`の追加**:
    これは、オペランドがレジスタからのオフセット（例: `$n(Rm)`）ではないことを明示的にチェックする条件です。`NREG`は「レジスタなし」を意味する定数です。
    この条件が追加されたことで、`$n(Rm)`のような形式のアドレスが、単なる大きな定数として誤って扱われることがなくなりました。これにより、レジスタ`Rm`の情報が不必要に失われることが防がれます。

2.  **`(int32)p->from.offset != p->from.offset`への変更**:
    元の`(int64)(uint32)p->from.offset != p->from.offset`という条件は、負の32ビット定数が誤って32ビットを超える定数として認識される原因でした。
    新しい条件`(int32)p->from.offset != p->from.offset`は、`p->from.offset`が`int32`の範囲に収まるかどうかを正確にチェックします。
    -   もし`p->from.offset`が`int32`の範囲に収まる場合（例えば、`-1`や`100`）、`(int32)p->from.offset`は`p->from.offset`と同じ値になります。この場合、条件は`false`となり、定数はメモリに配置されません。
    -   もし`p->from.offset`が`int32`の範囲を超える場合（例えば、`2^31`を超える正の数や、`-2^31`を下回る負の数）、`(int32)p->from.offset`は`p->from.offset`とは異なる値になります（オーバーフローによる切り捨てや符号の変化）。この場合、条件は`true`となり、定数はメモリに配置されます。
    この変更により、負の定数に対する誤った符号拡張の問題が解決され、本当に32ビットを超える定数のみがメモリに配置されるようになりました。

これらの修正により、`liblink`はPPC64アーキテクチャにおいて、`MOVD`命令の定数オペランドをより正確に処理できるようになり、特にレジスタからのオフセットを持つ負の定数に対するコード生成のバグが解消されました。

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。このツールチェーンには、フロントエンド（Goソースコードの解析）、バックエンド（アセンブリコードの生成）、そしてリンカが含まれます。

`liblink`は、Goコンパイラツールチェーンにおけるリンカの役割を担うライブラリです。Goのツールチェーンにおいて`liblink`は、独立した実行ファイルとして存在するわけではなく、Goコンパイラやアセンブラ、リンカといった様々なコンポーネントが共通して利用する内部ライブラリやパッケージを指します。その主な役割は、Goのオブジェクトファイル形式を定義し、コンパイラやアセンブラが生成する中間コードの構造やメタデータを規定することにあります。これにより、ツールチェーン内の各段階が互換性を保ち、最終的な実行可能ファイルを正しく組み立てることが可能になります。

### PPC64アーキテクチャ

PPC64（PowerPC 64-bit）は、IBMが開発したPowerPC命令セットアーキテクチャの64ビット版です。RISC（Reduced Instruction Set Computer）アーキテクチャであり、固定長の命令、多数の汎用レジスタ、ロード/ストアアーキテクチャ（メモリへのアクセスはロード命令とストア命令のみで行われる）などの特徴を持ちます。

PPC64の命令セットには、メモリからのロードやメモリへのストアを行うための命令が含まれます。これらの命令は、ベースレジスタとオフセットを組み合わせてメモリアドレスを指定することが一般的です。例えば、`n(Rm)`という形式は、「レジスタ`Rm`の値に`n`を加えたアドレス」を意味します。

### `MOVD`命令 (PPC64における)

PPC64における`MOVD`命令は、一般的にデータを移動（Move Doubleword）させるために使用されます。これは、64ビットのデータをレジスタ間で移動させたり、メモリとレジスタ間で移動させたりする際に使われます。Goのアセンブリ言語では、`MOVD`は通常、ネイティブのPowerPC `ld` (load doubleword) 命令に対応します。

Goアセンブリにおける`MOVD`の一般的な構文は、`MOVD source, destination`の形式で、最後のオペランドが常にデスティネーションとなります。例えば、`MOVD (R3), R4`は、レジスタ`R3`が指すメモリアドレスから64ビットの値をロードし、それをレジスタ`R4`に格納します。これはネイティブPPC64アセンブリの`ld r4, 0(r3)`に相当します。

### 定数とアドレス指定

アセンブリ言語では、定数は命令のオペランドとして直接指定されることがあります。しかし、命令のビット幅には限りがあるため、非常に大きな定数や、特定の命令が直接扱えない形式の定数は、メモリに配置されてからロードされるという間接的な方法が取られます。

PPC64では、メモリへのアクセスは通常、ベースレジスタとオフセットの組み合わせで行われます。`$n(Rm)`という表記は、Goのアセンブリ言語（Plan 9アセンブリ）におけるアドレス指定モードの一つで、「レジスタ`Rm`の値に定数`n`を加えたアドレス」を意味します。ここで`n`はオフセット値です。

### `D_CONST` (Goアセンブリ内部表現)

`D_CONST`は、Goのアセンブラ（`cmd/asm`）が定数値を内部的に表現するために使用するフラグまたはタイプです。Goのアセンブリコードで定数を扱う際、例えば`const myConst = 100`のようなGoコードの定数をアセンブリから参照する場合、Goビルドシステムは`go_asm.h`のようなヘッダを生成し、アセンブリコードが`const_myConst`のような形式でこれらの定数を参照できるようにします。`D_CONST`は、アセンブラがこれらの定数参照を処理し、解決する際に、そのオペランドが定数であることを示すために利用されます。これは、開発者が直接アセンブリファイルに記述するようなユーザー向けのタイプではありません。

### 符号拡張 (Sign Extension)

符号拡張とは、コンピュータの算術演算において、バイナリ数値のビット数を増やしながら、その符号（正または負）と数値自体を保持する操作です。これは、より小さいビット表現の数値をより大きいビット表現に変換する際に不可欠です。

2の補数表現で符号付き整数を扱う場合、符号拡張は以下のように機能します。
-   **正の数**: 最上位ビット（MSB、正の数の場合は0）が、追加されるビットを埋めるために左側に複製されます。
-   **負の数**: 最上位ビット（MSB、負の数の場合は1）が、追加されるビットを埋めるために左側に複製されます。

符号拡張の主な目的は、ビット表現が拡張されても数値が変化しないことを保証することです。これに対し、ゼロ拡張は符号なし数値に用いられ、単に数値の左側をゼロで埋めます。

このコミットでは、負の定数を扱う際に誤った符号拡張が行われ、本来32ビットの範囲に収まる負の定数も、32ビットを超える定数として誤認され、不必要なメモリへの書き換えがトリガーされる原因となっていました。

## 技術的詳細

このコミットが修正する問題は、`liblink`がPPC64アーキテクチャ向けに`MOVD`命令を処理する際の、定数オペランドの誤った認識に起因します。

`liblink`は、`MOVD`命令のソースオペランドが32ビットを超える定数であると判断した場合、その定数をデータセクション（またはリテラルプール）に配置し、そのメモリ位置から値をロードする命令に書き換える最適化（または必要処理）を行います。これは、PPC64の命令が直接扱える定数のサイズに制限があるためです。

しかし、この書き換えをトリガーする条件判定に2つのバグがありました。

1.  **誤った符号拡張**:
    元のコードでは、`p->from.offset`（オペランドのオフセット値）が`int64`型にキャストされる際に、`uint32`に一度キャストされてから`int64`にキャストされていました。
    ` (int64)(uint32)p->from.offset != p->from.offset`
    この` (uint32)p->from.offset`という中間キャストが問題でした。例えば、`p->from.offset`が`-1`のような負の32ビット整数であった場合、`uint32`にキャストされると、そのビットパターンは大きな正の数として解釈されます（例: `0xFFFFFFFF`）。その後、`int64`にキャストされても、その大きな正の数値がそのまま`int64`として扱われるため、元の負の数とは異なる値となり、結果として「32ビットを超える定数」であると誤って判断されていました。これにより、本来メモリに配置する必要のない負の定数まで、不必要にメモリに配置されることになっていました。

2.  **レジスタオフセットの誤認識**:
    元の条件判定では、`p->from.type == D_CONST`（定数オペランドであること）と`p->from.name == D_NONE`（名前がないこと）のみをチェックしていました。しかし、`$n(Rm)`のような形式のアドレスは、`D_CONST`タイプを持ち、`p->from.offset`に`n`が、`p->from.reg`に`Rm`が設定されます。元の条件では`p->from.reg`がチェックされていなかったため、レジスタからのオフセットを持つアドレスも、単なる大きな定数として誤認される可能性がありました。

これらのバグが組み合わさることで、`MOVD $-n(Rm), x`のような命令が特に問題となりました。
- `-n`という負のオフセットが、誤った符号拡張により「32ビットを超える定数」と判断される。
- `Rm`というレジスタ情報が、条件判定で考慮されないため無視される。

結果として、`liblink`は`-n`をメモリに配置し、そこからロードする命令に書き換えてしまい、本来の意図である「`Rm`からのオフセット」という情報が完全に失われ、プログラムの動作が不正になるという深刻な問題を引き起こしていました。

## コアとなるコードの解説

変更の核心は、`src/liblink/obj9.c`の`progedit`関数内の`AMOVD`命令を処理する`case`文にあります。

元のコード:
```c
if(p->from.type == D_CONST && p->from.name == D_NONE && (int64)(uint32)p->from.offset != p->from.offset) {
```

修正後のコード:
```c
// Put >32-bit constants in memory and load them
if(p->from.type == D_CONST && p->from.name == D_NONE && p->from.reg == NREG && (int32)p->from.offset != p->from.offset) {
```

この変更により、条件判定がより正確になりました。

1.  **`p->from.reg == NREG`の追加**:
    これは、オペランドがレジスタからのオフセット（例: `$n(Rm)`）ではないことを明示的にチェックする条件です。`NREG`は「レジスタなし」を意味する定数です。
    この条件が追加されたことで、`$n(Rm)`のような形式のアドレスが、単なる大きな定数として誤って扱われることがなくなりました。これにより、レジスタ`Rm`の情報が不必要に失われることが防がれます。

2.  **`(int32)p->from.offset != p->from.offset`への変更**:
    元の`(int64)(uint32)p->from.offset != p->from.offset`という条件は、負の32ビット定数が誤って32ビットを超える定数として認識される原因でした。
    新しい条件`(int32)p->from.offset != p->from.offset`は、`p->from.offset`が`int32`の範囲に収まるかどうかを正確にチェックします。
    -   もし`p->from.offset`が`int32`の範囲に収まる場合（例えば、`-1`や`100`）、`(int32)p->from.offset`は`p->from.offset`と同じ値になります。この場合、条件は`false`となり、定数はメモリに配置されません。
    -   もし`p->from.offset`が`int32`の範囲を超える場合（例えば、`2^31`を超える正の数や、`-2^31`を下回る負の数）、`(int32)p->from.offset`は`p->from.offset`とは異なる値になります（オーバーフローによる切り捨てや符号の変化）。この場合、条件は`true`となり、定数はメモリに配置されます。
    この変更により、負の定数に対する誤った符号拡張の問題が解決され、本当に32ビットを超える定数のみがメモリに配置されるようになりました。

これらの修正により、`liblink`はPPC64アーキテクチャにおいて、`MOVD`命令の定数オペランドをより正確に処理できるようになり、特にレジスタからのオフセットを持つ負の定数に対するコード生成のバグが解消されました。

## 元コミット内容

このコミットは、Goランタイムにおけるメモリ割り当てのサイズに関する問題を修正します。具体的には、`malloc`関数に渡されるサイズが、実際に必要とされるサイズと異なる場合があるという問題に対処しています。

コミットメッセージによると、以下の2つのケースで問題が発生していました。

1.  **パニック時 (panic.c):** パニック処理中にメモリを要求する際、実際に使用するメモリよりも少ないサイズを`malloc`に伝えていました。
2.  **スライス拡張時 (slice.goc):** スライスを拡張する際、実際に使用するメモリよりも多いサイズを`malloc`に伝えていました。特に、要素の「端数」を要求する可能性があり、これが問題を引き起こしていました。

これらの不正確なサイズ指定が「新しいGC (New GC)」を壊す原因となっていたと述べられています。

## 変更の背景

このコミットの背景には、Goランタイムにおける新しいガベージコレクション (GC) の導入があります。Go 1.5 (2015年8月リリース) では、ストップ・ザ・ワールド (STW) 時間を大幅に短縮する新しいGCが導入されました。この新しいGCは、メモリの割り当てと解放のパターンに対してより厳密な要件を持っていました。

従来のGCでは許容されていた、`malloc`への不正確なサイズ指定が、新しいGCの内部動作と整合性が取れなくなり、GCの誤動作やクラッシュを引き起こす可能性がありました。特に、メモリ割り当てのサイズが実際のオブジェクトサイズと異なる場合、GCがオブジェクトの境界を正しく認識できなかったり、ポインタのスキャン範囲を誤ったりするリスクがありました。

このコミットは、新しいGCが正しく機能するために、ランタイムが`malloc`に常に正確なメモリサイズを伝えるようにするための修正です。これにより、GCがメモリレイアウトを正確に理解し、効率的かつ安全に動作できるようになります。

## 前提知識の解説

*   **Goランタイム (Go Runtime):** Goプログラムの実行を管理する低レベルのシステムです。ガベージコレクタ、スケジューラ、メモリ割り当てなどが含まれます。Goプログラムは、OSの機能に直接アクセスするのではなく、ランタイムを介してこれらの機能を利用します。
*   **ガベージコレクション (Garbage Collection, GC):** プログラムが動的に割り当てたメモリのうち、もはや使用されていない（参照されていない）領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、Go 1.5以降はSTW時間を最小限に抑えるように設計されています。
*   **`malloc`:** C言語の標準ライブラリ関数で、指定されたサイズのメモリブロックをヒープから割り当てます。Goランタイムも内部的にメモリ割り当てのために同様の低レベル関数を使用します。
*   **`runtime·roundupsize`:** Goランタイム内部で使用される関数で、指定されたサイズを、メモリ割り当てに適したアラインメント（通常はページサイズやオブジェクトの最小アラインメント）に切り上げるために使用されます。これにより、メモリの効率的な利用とGCの効率的な動作が保証されます。
*   **`runtime·mallocgc`:** Goランタイム内部のメモリ割り当て関数で、ガベージコレクタによって管理されるメモリを割り当てます。この関数は、割り当てるメモリのサイズだけでなく、そのメモリにポインタが含まれるかどうか（GCがスキャンする必要があるか）などの情報もGCに伝えます。
*   **スライス (Slice):** Goの組み込み型で、配列の一部を参照する動的なビューです。スライスは、基になる配列の容量を超えて要素を追加しようとすると、より大きな新しい配列を割り当ててデータをコピーすることで「拡張 (grow)」されます。
*   **パニック (Panic):** Goにおける回復不可能なエラー状態です。パニックが発生すると、通常のプログラムフローは中断され、遅延関数が実行された後、プログラムが終了します。パニック処理中にも、エラー情報を記録したり、スタックトレースを生成したりするためにメモリ割り当てが行われることがあります。

## 技術的詳細

このコミットは、Goランタイムがメモリ割り当てを行う際に、`malloc`（またはそれに相当する内部関数）に渡すサイズが、実際に割り当てられるオブジェクトの正確なサイズと一致するように修正しています。

問題の核心は、`malloc`が要求されたサイズに基づいてメモリブロックを割り当てる際、そのブロックのメタデータ（サイズ情報など）を内部的に管理している点にあります。新しいGCは、このメタデータや、割り当てられたメモリブロックの実際のサイズ情報を利用して、オブジェクトの境界を特定し、ポインタをスキャンします。もし`malloc`に伝えられたサイズが実際のオブジェクトサイズと異なると、GCは誤った情報を基に動作し、メモリの破損やGCのクラッシュを引き起こす可能性がありました。

具体的には、以下の2つのファイルで修正が行われています。

1.  **`src/pkg/runtime/panic.c`:**
    *   `newdefer`関数内で、`defer`構造体を割り当てる際に使用されるサイズ計算に問題がありました。
    *   以前は`TOTALSIZE(siz)`を直接`malloc`に渡していましたが、これはアラインメントを考慮していないため、実際に割り当てられるサイズと異なる可能性がありました。
    *   修正後は、`runtime·roundupsize(TOTALSIZE(siz))` を使用して、`malloc`に渡す前にサイズを適切に切り上げています。これにより、`malloc`が実際に割り当てるサイズと、ランタイムが期待するサイズが一致するようになります。

2.  **`src/pkg/runtime/slice.goc`:**
    *   `growslice1`関数内で、スライスを拡張する際に新しい容量のメモリを割り当てる部分に問題がありました。
    *   以前は`capmem = runtime·roundupsize(newcap1*typ->size)`でメモリサイズを計算していましたが、その後の`ret->cap = capmem/typ->size`で容量を計算する際に、`capmem`が`typ->size`の正確な倍数でない場合（つまり、`roundupsize`によって切り上げられた結果、要素の「端数」が生じる場合）、`ret->cap`が実際の要素数と一致しない可能性がありました。
    *   この「端数」の問題は、GCがスライス内の要素をスキャンする際に、誤った境界を認識する原因となります。
    *   修正では、`capmem`を`roundupsize`で切り上げた後、`newcap1 = capmem/typ->size`で実際の要素数を再計算し、さらに`capmem = newcap1*typ->size`として、`capmem`が`typ->size`の正確な倍数になるように調整しています。
    *   これにより、`mallocgc`に渡される`capmem`が常に正確な要素数に対応するサイズとなり、`ret->cap`も正確な容量を反映するようになります。GCは、この正確な情報に基づいてスライス内のポインタを安全にスキャンできるようになります。

この修正は、Goランタイムのメモリ管理とGCの間の契約を強化し、新しいGCの堅牢性と正確性を保証するために不可欠でした。

## コアとなるコードの解説

### `src/pkg/runtime/panic.c` の変更

*   **変更前:** `total = TOTALSIZE(siz);`
*   **変更後:** `total = runtime·roundupsize(TOTALSIZE(siz));`

この変更は、`newdefer`関数内で`defer`構造体を割り当てる際に、`malloc`に渡すメモリサイズを修正しています。`TOTALSIZE(siz)`は、`defer`構造体の基本サイズと、それに続く可変長データ（`siz`）の合計サイズを計算しますが、これは必ずしもメモリ割り当てのアラインメント要件を満たすとは限りません。`runtime·roundupsize`関数は、この`total`サイズを、システムがメモリを割り当てる際の最小単位（例えば、ページサイズやキャッシュラインサイズ）に切り上げます。これにより、`malloc`が実際に割り当てるメモリブロックのサイズと、ランタイムがそのブロックを使用する際の期待されるサイズが正確に一致するようになり、GCがメモリレイアウトを正しく解釈できるようになります。

### `src/pkg/runtime/slice.goc` の変更

*   **変更前 (`growslice1`関数内):**
    ```go
    capmem = runtime·roundupsize(newcap1*typ->size);
    // ...
    ret->cap = capmem/typ->size;
    ```
*   **変更後 (`growslice1`関数内):**
    ```go
    // Try to use all memory that malloc will give us...
    capmem = runtime·roundupsize(newcap1*typ->size);
    // ...but don't ask for fractional number of elements (that can confuse GC).
    newcap1 = capmem/typ->size;
    capmem = newcap1*typ->size;
    // ...
    ret->cap = newcap1;
    ```

この変更は、スライスを拡張する際のメモリ割り当てロジックを改善しています。

1.  `capmem = runtime·roundupsize(newcap1*typ->size);`
    これは、新しい容量`newcap1`と要素のサイズ`typ->size`から必要なバイト数を計算し、それを`runtime·roundupsize`で切り上げて、`malloc`に渡す適切なメモリサイズ`capmem`を決定します。

2.  `newcap1 = capmem/typ->size;`
    ここで重要な変更が行われています。`runtime·roundupsize`によって`capmem`が切り上げられた結果、`capmem`が`typ->size`の正確な倍数でなくなる可能性があります。例えば、要素サイズが8バイトで、`roundupsize`が16バイト単位で切り上げる場合、10バイトが必要なときに16バイトが割り当てられることがあります。この場合、`capmem/typ->size`は16/8=2となりますが、元の`newcap1`は10/8=1.25のような「端数」を含んでいたかもしれません。この行では、実際に割り当てられた`capmem`に基づいて、そのメモリに収まる正確な要素数`newcap1`を再計算しています。これにより、`newcap1`は常に整数値となり、割り当てられたメモリブロックに正確に収まる要素の数を表します。

3.  `capmem = newcap1*typ->size;`
    さらに、再計算された`newcap1`（正確な要素数）を使用して、`capmem`を再度計算し直しています。これにより、`capmem`は常に`typ->size`の正確な倍数となり、GCがスライス内の要素をスキャンする際に、要素の境界を正確に認識できるようになります。

4.  `ret->cap = newcap1;`
    最後に、スライスの実際の容量`ret->cap`を、再計算された正確な要素数`newcap1`に設定しています。

これらの変更により、`mallocgc`に渡されるメモリサイズと、スライスが実際に保持できる要素数が常に整合性が取れるようになり、新しいGCがスライスを正しく処理できるようになります。特に、ポインタを含むスライスの場合、GCは各要素をスキャンしてポインタを見つける必要があるため、要素の境界が正確であることは極めて重要です。

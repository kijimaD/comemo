## 変更の背景

このコミットの主な背景は、Goコンパイラ（`cmd/compile`）のメモリ効率の改善にあります。コミットメッセージに記載されている`$ sizeof -p cmd/compile/internal/gc Node Node 272`という出力は、`Node`構造体が272バイトのメモリを消費していることを示しています。`Node`構造体は、Goコンパイラがソースコードを解析して生成する抽象構文木（AST）の各ノードを表す中心的なデータ構造であり、コンパイルプロセス中に大量に生成されます。

このような頻繁に使用されるデータ構造のサイズが大きいと、以下のような問題が発生します。

1.  **メモリ使用量の増加**: 大規模なGoプログラムをコンパイルする際に、ASTが大量のメモリを消費し、システム全体のメモリ使用量が増大します。
2.  **キャッシュ効率の低下**: `Node`構造体が大きすぎると、CPUのキャッシュラインに収まる`Node`の数が減り、キャッシュミスが増加します。これにより、メモリへのアクセスが遅くなり、コンパイル速度が低下します。
3.  **ガベージコレクションの負荷**: メモリ使用量が増えると、ガベージコレクタがより頻繁に、より長い時間実行される必要があり、コンパイル時間がさらに長くなる可能性があります。

これらの問題を解決するため、Goコンパイラの開発チームは、`Node`構造体のメモリフットプリントを削減するための最適化を継続的に行っています。このコミットは、その一環として、`Ntest`と`Stkdelta`という2つのフィールドが冗長であるか、より効率的な方法で管理できると判断された結果として行われました。`Ntest`は既存の`Left`フィールドで代用可能であり、`Stkdelta`はすべての`Node`で必要とされるわけではない一時的な情報であるため、グローバルマップに移行することでメモリを節約できると考えられました。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは、`cmd/compile`というパッケージに実装されています。これは、Goのソースコードを解析し、中間表現を経て、最終的に実行可能なバイナリコード（機械語）に変換する役割を担います。コンパイラは複数のフェーズ（字句解析、構文解析、型チェック、最適化、コード生成など）で構成されており、各フェーズでコードの異なる側面を処理します。

### AST (Abstract Syntax Tree)

抽象構文木（AST）は、ソースコードの構文構造を木構造で表現したものです。コンパイラは字句解析と構文解析のフェーズでソースコードをASTに変換し、その後の型チェック、最適化、コード生成などのすべてのフェーズでこのASTを操作します。ASTの各ノードは、プログラムの要素（変数、式、文、関数定義など）に対応します。

### `Node`構造体

`Node`構造体は、Goコンパイラ内部の`cmd/compile/internal/gc`パッケージで定義されており、ASTの各ノードを表す中心的なデータ構造です。この構造体には、ノードの種類（`Op`）、関連する型情報（`Type`）、シンボル情報（`Sym`）、子ノードへのポインタ（`Left`, `Right`, `List`, `Nbody`など）、およびその他のメタデータ（`Xoffset`, `Lineno`など）が含まれます。`Node`構造体の設計は、コンパイラのメモリ使用量とパフォーマンスに直接的な影響を与えます。

### `Node.Ntest`フィールド (削除前)

`Node.Ntest`は、主に制御フロー文（`if`、`for`、`switch`など）の条件式を保持するために使用されていたフィールドです。例えば、`if condition { ... }`という文では、`condition`の部分が`Ntest`に格納されていました。

### `Node.Stkdelta`フィールド (削除前)

`Node.Stkdelta`は、スタックフレームの最適化に関連するオフセット情報、具体的にはスタックフレームのコンパクト化フェーズで追加されるスタックオフセットの差分を記録するために使用されていたフィールドです。Goコンパイラは、関数呼び出しのスタックフレームを効率的に管理するために、未使用のスタックスロットを削除するなどの最適化を行います。`Stkdelta`はこの最適化プロセスで一時的に必要となる情報でした。

### メモリフットプリントの削減

メモリフットプリントの削減とは、プログラムが実行中に使用するメモリの総量を減らすことです。コンパイラのような複雑なソフトウェアでは、大量のデータ構造をメモリ上に保持するため、データ構造のサイズを少しでも削減することが、全体のメモリ使用量とパフォーマンスに大きな影響を与えます。特に、ASTのようなコアデータ構造のサイズ削減は、キャッシュヒット率の向上、ガベージコレクションの頻度と時間の削減、そして最終的なコンパイル時間の短縮に繋がります。

## 技術的詳細

このコミットは、`Node`構造体から`Ntest`と`Stkdelta`という2つのフィールドを削除し、それらの機能を既存のフィールドまたは新しいメカニズムに移行することで、`Node`構造体のメモリフットプリントを削減します。

1.  **`Node.Ntest`の削除と`Node.Left`への統合**:
    *   以前は、`if`文、`for`文、`switch`文などの条件式は`Node.Ntest`フィールドに格納されていました。
    *   このコミットでは、`Ntest`フィールドが`Node`構造体から完全に削除されました。
    *   その代わりに、これらの条件式は既存の`Node.Left`フィールドに格納されるように変更されました。`Node.Left`は、ASTノードの左側の子ノードを指す汎用的なフィールドです。
    *   この変更により、`Node`構造体から`*Node`型のポインタフィールドが1つ削減され、`Node`インスタンスあたりのメモリ使用量がポインタサイズ分（64ビットシステムでは8バイト）削減されます。
    *   コンパイラの様々なフェーズ（エスケープ解析、コード生成、型チェック、ウォーク処理など）で`n.Ntest`を参照していた箇所が、`n.Left`を参照するように一括して変更されました。

2.  **`Node.Stkdelta`の削除と`stkdelta`マップへの移行**:
    *   `Node.Stkdelta`は、スタックフレームのコンパクト化フェーズでスタックオフセットの差分を記録するために使用されていました。
    *   このコミットでは、`Stkdelta`フィールドが`Node`構造体から削除されました。
    *   代わりに、`src/cmd/compile/internal/gc/pgen.go`に`stkdelta`というグローバルな`map[*Node]int64`が導入されました。
    *   このマップは、スタックフレームのコンパクト化が必要な特定の`Node`インスタンスに対してのみ、そのスタックオフセットの差分を記録します。
    *   `Stkdelta`が`Node`構造体の一部であった場合、すべての`Node`インスタンスがこの`int64`フィールド（8バイト）を保持する必要がありましたが、マップに移行することで、実際に`Stkdelta`情報が必要なノードのみがメモリを消費するようになります。これにより、全体的なメモリ使用量が削減されます。
    *   スタックフレームの最適化が完了した後、`stkdelta`マップから対応するエントリが削除され、メモリが解放されます。

これらの変更は、Goコンパイラの内部データ構造の最適化であり、コンパイラのメモリ効率とパフォーマンスの向上に直接貢献します。特に、ASTノードのサイズ削減は、コンパイル時間の短縮やメモリ使用量の削減に大きな影響を与えます。

## コアとなるコードの解説

### `Node.Ntest`の削除と`Node.Left`への統合

`Node`構造体から`Ntest`フィールドが削除されたことで、条件式（`if`、`for`、`switch`）のテスト部分は、既存の`Left`フィールドがその役割を兼ねるようになりました。これは、ASTノードの設計において、フィールドの多重利用やより汎用的な構造への集約が行われたことを示唆します。

例えば、以前は`if n.Ntest { ... }`のように書かれていたコードは、`if n.Left { ... }`のように変更されます。この変更は、ASTの構造をよりシンプルにし、メモリ使用量を削減する効果があります。多くのプログラミング言語のASTでは、二項演算子や単項演算子、制御フロー文の条件など、様々な要素が「左の子」「右の子」といった汎用的なフィールドで表現されることが一般的です。Goコンパイラもこのパターンに沿って、`Ntest`という特定の用途のフィールドを廃止し、`Left`フィールドにその役割を統合したと考えられます。

### `Node.Stkdelta`の削除と`stkdelta`マップへの移行

`Stkdelta`フィールドは、スタックフレームの最適化（未使用のスタックスロットの削除）に関連するオフセット情報を持っていました。これが`Node`構造体から削除され、`stkdelta`というグローバルな`map[*Node]int64`に移行されました。

この変更の背景には、`Stkdelta`情報がすべての`Node`インスタンスで常に必要とされるわけではなく、特定の最適化フェーズでのみ一時的に必要とされる情報であるという認識があります。`Node`構造体自体に`Stkdelta`を持たせるのは、その情報が不要な`Node`インスタンスに対してもメモリを割り当てることになるため、非効率です。

`map[*Node]int64`を使用することで、`Stkdelta`情報が必要な`Node`インスタンスに対してのみ、その情報をマップに格納し、メモリを節約できます。スタックフレームの最適化フェーズが終了すれば、マップから対応するエントリを削除することで、そのメモリを解放できます。これにより、コンパイラのメモリ使用量が動的に管理され、全体的なメモリ効率が向上します。

これらの変更は、Goコンパイラの内部構造の洗練と最適化の一環であり、コンパイラのメモリ効率とパフォーマンスの向上に貢献します。特に、`Node`のような頻繁にインスタンス化されるデータ構造のサイズ削減は、コンパイル時間の短縮やメモリ使用量の削減に大きな影響を与えます。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは、`cmd/compile`というパッケージに実装されています。これは、Goのソースコードを解析し、中間表現を経て、最終的に実行可能なバイナリコード（機械語）に変換する役割を担います。コンパイラは複数のフェーズ（字句解析、構文解析、型チェック、最適化、コード生成など）で構成されており、各フェーズでコードの異なる側面を処理します。

### AST (Abstract Syntax Tree)

抽象構文木（AST）は、ソースコードの構文構造を木構造で表現したものです。コンパイラは字句解析と構文解析のフェーズでソースコードをASTに変換し、その後の型チェック、最適化、コード生成などのすべてのフェーズでこのASTを操作します。ASTの各ノードは、プログラムの要素（変数、式、文、関数定義など）に対応します。

### `Node`構造体

`Node`構造体は、Goコンパイラ内部の`cmd/compile/internal/gc`パッケージで定義されており、ASTの各ノードを表す中心的なデータ構造です。この構造体には、ノードの種類（`Op`）、関連する型情報（`Type`）、シンボル情報（`Sym`）、子ノードへのポインタ（`Left`, `Right`, `List`, `Nbody`など）、およびその他のメタデータ（`Xoffset`, `Lineno`など）が含まれます。`Node`構造体の設計は、コンパイラのメモリ使用量とパフォーマンスに直接的な影響を与えます。

### `Node.Ntest`フィールド (削除前)

`Node.Ntest`は、主に制御フロー文（`if`文、`for`文、`switch`文など）の条件式を保持するために使用されていたフィールドです。例えば、`if condition { ... }`という文では、`condition`の部分が`Ntest`に格納されていました。

### `Node.Stkdelta`フィールド (削除前)

`Node.Stkdelta`は、スタックフレームの最適化に関連するオフセット情報、具体的にはスタックフレームのコンパクト化フェーズで追加されるスタックオフセットの差分を記録するために使用されていたフィールドです。Goコンパイラは、関数呼び出しのスタックフレームを効率的に管理するために、未使用のスタックスロットを削除するなどの最適化を行います。`Stkdelta`はこの最適化プロセスで一時的に必要となる情報でした。

### メモリフットプリントの削減

メモリフットプリントの削減とは、プログラムが実行中に使用するメモリの総量を減らすことです。コンパイラのような複雑なソフトウェアでは、大量のデータ構造をメモリ上に保持するため、データ構造のサイズを少しでも削減することが、全体のメモリ使用量とパフォーマンスに大きな影響を与えます。特に、ASTのようなコアデータ構造のサイズ削減は、キャッシュヒット率の向上、ガベージコレクションの頻度と時間の削減、そして最終的なコンパイル時間の短縮に繋がります。

## 技術的詳細

このコミットは、`Node`構造体から`Ntest`と`Stkdelta`という2つのフィールドを削除し、それらの機能を既存のフィールドまたは新しいメカニズムに移行することで、`Node`構造体のメモリフットプリントを削減します。

1.  **`Node.Ntest`の削除と`Node.Left`への統合**:
    *   以前は、`if`文、`for`文、`switch`文などの条件式は`Node.Ntest`フィールドに格納されていました。
    *   このコミットでは、`Ntest`フィールドが`Node`構造体から完全に削除されました。
    *   その代わりに、これらの条件式は既存の`Node.Left`フィールドに格納されるように変更されました。`Node.Left`は、ASTノードの左側の子ノードを指す汎用的なフィールドです。
    *   この変更により、`Node`構造体から`*Node`型のポインタフィールドが1つ削減され、`Node`インスタンスあたりのメモリ使用量がポインタサイズ分（64ビットシステムでは8バイト）削減されます。
    *   コンパイラの様々なフェーズ（エスケープ解析、コード生成、型チェック、ウォーク処理など）で`n.Ntest`を参照していた箇所が、`n.Left`を参照するように一括して変更されました。

2.  **`Node.Stkdelta`の削除と`stkdelta`マップへの移行**:
    *   `Node.Stkdelta`は、スタックフレームのコンパクト化フェーズでスタックオフセットの差分を記録するために使用されていました。
    *   このコミットでは、`Stkdelta`フィールドが`Node`構造体から削除されました。
    *   代わりに、`src/cmd/compile/internal/gc/pgen.go`に`stkdelta`というグローバルな`map[*Node]int64`が導入されました。
    *   このマップは、スタックフレームのコンパクト化が必要な特定の`Node`インスタンスに対してのみ、そのスタックオフセットの差分を記録します。
    *   `Stkdelta`が`Node`構造体の一部であった場合、すべての`Node`インスタンスがこの`int64`フィールド（8バイト）を保持する必要がありましたが、マップに移行することで、実際に`Stkdelta`情報が必要なノードのみがメモリを消費するようになります。これにより、全体的なメモリ使用量が削減されます。
    *   スタックフレームの最適化が完了した後、`stkdelta`マップから対応するエントリが削除され、メモリが解放されます。

これらの変更は、Goコンパイラの内部データ構造の最適化であり、コンパイラのメモリ効率とパフォーマンスの向上に直接貢献します。特に、ASTノードのサイズ削減は、コンパイル時間の短縮やメモリ使用量の削減に大きな影響を与えます。

## コアとなるコードの解説

### `Node.Ntest`の削除と`Node.Left`への統合

`Node`構造体から`Ntest`フィールドが削除されたことで、条件式（`if`、`for`、`switch`）のテスト部分は、既存の`Left`フィールドがその役割を兼ねるようになりました。これは、ASTノードの設計において、フィールドの多重利用やより汎用的な構造への集約が行われたことを示唆します。

例えば、以前は`if n.Ntest { ... }`のように書かれていたコードは、`if n.Left { ... }`のように変更されます。この変更は、ASTの構造をよりシンプルにし、メモリ使用量を削減する効果があります。多くのプログラミング言語のASTでは、二項演算子や単項演算子、制御フロー文の条件など、様々な要素が「左の子」「右の子」といった汎用的なフィールドで表現されることが一般的です。Goコンパイラもこのパターンに沿って、`Ntest`という特定の用途のフィールドを廃止し、`Left`フィールドにその役割を統合したと考えられます。

### `Node.Stkdelta`の削除と`stkdelta`マップへの移行

`Stkdelta`フィールドは、スタックフレームの最適化（未使用のスタックスロットの削除）に関連するオフセット情報を持っていました。これが`Node`構造体から削除され、`stkdelta`というグローバルな`map[*Node]int64`に移行されました。

この変更の背景には、`Stkdelta`情報がすべての`Node`インスタンスで常に必要とされるわけではなく、特定の最適化フェーズでのみ一時的に必要とされる情報であるという認識があります。`Node`構造体自体に`Stkdelta`を持たせるのは、その情報が不要な`Node`インスタンスに対してもメモリを割り当てることになるため、非効率です。

`map[*Node]int64`を使用することで、`Stkdelta`情報が必要な`Node`インスタンスに対してのみ、その情報をマップに格納し、メモリを節約できます。スタックフレームの最適化フェーズが終了すれば、マップから対応するエントリが削除されることで、そのメモリを解放できます。これにより、コンパイラのメモリ使用量が動的に管理され、全体的なメモリ効率が向上します。

これらの変更は、Goコンパイラの内部構造の洗練と最適化の一環であり、コンパイラのメモリ効率とパフォーマンスの向上に貢献します。特に、`Node`のような頻繁にインスタンス化されるデータ構造のサイズ削減は、コンパイル時間の短縮やメモリ使用量の削減に大きな影響を与えます。

## 元コミット内容

このコミットの目的は、GoコンパイラにおけるSSA（Static Single Assignment）形式の処理中に発生するガベージ（一時的なメモリ割り当て）を削減することです。コミットメッセージには、`compilebench`ツールを用いたベンチマーク結果が詳細に記載されており、特にメモリ割り当て量（`alloc/op`）の大幅な削減が示されています。

ベンチマーク結果の概要：

*   **`time/op` (操作あたりの時間)**: CPU時間の測定では、一部のベンチマークでわずかな増加が見られるものの、全体的には大きな変化はありません。`GoTypes`と`Compiler`ではわずかに改善しています。
*   **`alloc/op` (操作あたりのメモリ割り当て量)**:
    *   `Template`: 63.3MB → 59.1MB (-6.72%)
    *   `Unicode`: 43.1MB → 42.9MB (-0.47%)
    *   `GoTypes`: 220MB → 200MB (-9.00%)
    *   `Compiler`: 1.00GB → 0.89GB (-10.09%)
    これらの数値は、コンパイルプロセス中のメモリフットプリントが大幅に削減されたことを明確に示しています。
*   **`allocs/op` (操作あたりの割り当て回数)**: 割り当て回数自体はわずかな減少に留まっていますが、これは主に個々の割り当てサイズが小さくなったこと、または一部の割り当てが完全に回避されたことを示唆しています。

この結果から、この変更がコンパイラの実行速度に大きな影響を与えることなく、メモリ効率を大幅に向上させたことがわかります。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な中間表現（IR）を使用します。その中でもSSA形式は、最適化の機会を増やすために重要な役割を果たします。SSA形式の処理中には、多くのデータ構造が一時的に生成され、これらがガベージコレクタ（GC）の対象となります。コンパイラのようなパフォーマンスが重視されるツールにおいて、コンパイル時間の短縮は非常に重要であり、GCによる一時停止（STW: Stop The World）時間はその主要なボトルネックの一つとなり得ます。

このコミットの背景には、GoコンパイラのSSAバックエンドにおけるメモリ割り当てのオーバーヘッドを削減し、コンパイル時のGC負荷を軽減するという明確な目的があります。特に、`stackalloc`（スタックアロケーション）フェーズは、関数内のローカル変数をスタック上にどのように配置するかを決定する重要なステップであり、この過程で多くの補助的なデータ構造が使用されます。これらのデータ構造を効率的に管理し、可能な限り再利用することで、新たなメモリ割り当ての回数と量を減らし、結果としてGCの頻度と時間を削減することが期待されます。

ベンチマーク結果が示すように、特に`Compiler`ベンチマークで10%以上の`alloc/op`削減が達成されており、これは大規模なGoプロジェクトのコンパイル時間短縮に寄与する可能性があります。

## 前提知識の解説

### Goコンパイラ (Go Compiler)

Goコンパイラは、Go言語で書かれたソースコードを、特定のCPUアーキテクチャ（例: x86-64, ARM）で実行可能な機械語に変換するプログラムです。Goコンパイラは、フロントエンド、ミドルエンド、バックエンドの3つの主要なフェーズに分かれています。

*   **フロントエンド**: 字句解析、構文解析、意味解析を行い、抽象構文木（AST）を生成します。
*   **ミドルエンド**: ASTをさらに最適化された中間表現（IR）に変換します。Go 1.7以降、この中間表現としてSSA形式が導入されました。
*   **バックエンド**: 中間表現をターゲットアーキテクチャの機械語に変換し、最終的な実行可能ファイルを生成します。

### SSA (Static Single Assignment) 形式

SSA（Static Single Assignment）形式は、コンパイラ最適化において広く用いられる中間表現の一種です。SSA形式の主な特徴は以下の通りです。

*   **単一割り当て**: 各変数は、プログラム内でただ一度だけ値が割り当てられます。もし変数が複数回値を変更する場合、SSA形式ではそのたびに新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。
*   **データフロー解析の容易さ**: 単一割り当ての特性により、変数の定義と使用の関係が明確になり、データフロー解析や最適化が非常に容易になります。
*   **最適化の機会**: 共通部分式の削除、定数伝播、デッドコード削除など、多くの強力な最適化がSSA形式上で効率的に実行できます。

Goコンパイラでは、Go 1.7でSSAバックエンドが導入され、コンパイル速度の向上と生成されるコードの品質改善に大きく貢献しました。

### スタックアロケーション (Stack Allocation)

スタックアロケーションは、プログラムの実行中にローカル変数や関数の引数などのデータをスタックメモリ領域に割り当てるプロセスです。

*   **スタックメモリ**: プログラムの実行中に一時的に使用されるメモリ領域で、LIFO（Last-In, First-Out）の原則に従って管理されます。関数が呼び出されると、その関数のローカル変数や引数などがスタックフレームとしてスタックにプッシュされ、関数が終了するとポップされます。
*   **コンパイラの役割**: コンパイラは、どの変数をスタックに割り当てるか（エスケープ解析の結果に基づいて）、そしてスタックフレーム内でそれらをどのように配置するかを決定します。スタックアロケーションは、ヒープアロケーション（ガベージコレクタが管理するメモリ領域への割り当て）と比較して非常に高速です。
*   **`stackalloc`フェーズ**: GoコンパイラのSSAバックエンドには、`stackalloc`というフェーズがあり、これはSSA形式の値を分析し、スタック上に割り当てるべき値を特定し、それらのスタック上のオフセットを決定します。

### ガベージコレクション (Garbage Collection)

ガベージコレクション（GC）は、プログラムが動的に割り当てたメモリのうち、もはや使用されていない（到達不能な）領域を自動的に解放するプロセスです。Go言語は、並行マーク＆スイープ方式のGCを採用しており、低レイテンシを特徴としています。

*   **GCの目的**: プログラマが手動でメモリを管理する手間を省き、メモリリークなどのバグを防ぎます。
*   **GCのコスト**: GCは、実行時にメモリ使用量を監視し、不要なオブジェクトを特定して解放するためにCPU時間とメモリ帯域幅を消費します。特に、ヒープへの頻繁な小さなオブジェクトの割り当ては、GCの頻度を増加させ、プログラムの実行を一時的に停止させる（STW）原因となり、パフォーマンスに悪影響を与える可能性があります。
*   **メモリ割り当ての削減**: このコミットのように、コンパイル時であってもメモリ割り当ての回数や量を減らすことは、GCの負担を軽減し、全体的なパフォーマンスを向上させる上で非常に効果的です。

### ベンチマーク (Benchmarks)

ベンチマークは、ソフトウェアの性能を測定するためのテストです。Go言語には、標準ライブラリにベンチマーク機能が組み込まれており、`go test -bench=.`コマンドで実行できます。

*   **`time/op`**: 1回の操作にかかる平均時間を示します。プログラムの実行速度を測る指標です。
*   **`alloc/op`**: 1回の操作で割り当てられるメモリの総量を示します。ヒープ割り当ての量を測る指標であり、GCの負荷に直結します。
*   **`allocs/op`**: 1回の操作で発生するメモリ割り当ての回数を示します。これもGCの負荷に影響しますが、`alloc/op`の方がより直接的にGCの作業量を示します。

これらの指標を比較することで、コード変更がパフォーマンス（特にメモリ効率）に与える影響を定量的に評価できます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける`stackalloc`フェーズで一時的に使用される`stackAllocState`構造体とその内部のスライスを再利用するメカニズムの導入です。これにより、コンパイルプロセス中のメモリ割り当て（ガベージ）を大幅に削減しています。

1.  **`Config`構造体への`stackAllocState`の追加**:
    `src/cmd/compile/internal/ssa/config.go`内の`Config`構造体に、`*stackAllocState`型のフィールド`stackAllocState`が追加されました。この`Config`構造体は、SSAバックエンド全体で共有される設定やスクラッチスペースを管理するためのものです。ここに`stackAllocState`へのポインタを持たせることで、`stackAllocState`オブジェクトをプールし、再利用するためのフックが提供されます。

    ```go
    type Config struct {
        // ... 既存のフィールド ...
        // Reusable stackAllocState.
        // See stackalloc.go's {new,put}StackAllocState.
        stackAllocState *stackAllocState
        // ... その他のフィールド ...
    }
    ```

2.  **`stackAllocState`の再利用メカニズム (`newStackAllocState`, `putStackAllocState`)**:
    `src/cmd/compile/internal/ssa/stackalloc.go`に、`stackAllocState`オブジェクトをプールから取得し、プールに戻すための2つの新しい関数が追加されました。

    *   `newStackAllocState(f *Func) *stackAllocState`:
        この関数は、`f.Config.stackAllocState`に以前使用された`stackAllocState`オブジェクトが格納されていれば、それを再利用します。もし`nil`であれば、新しい`stackAllocState`を割り当てます。再利用する際には、以前の`Func`への参照が残っていないかチェックし、エラーを防ぎます。

    *   `putStackAllocState(s *stackAllocState)`:
        この関数は、`stackAllocState`オブジェクトをプールに戻す役割を担います。オブジェクト内のスライス（`values`, `interfere`, `names`, `slots`, `used`）の要素をゼロ値でクリアし、`f`フィールドを`nil`に設定してから、`s.f.Config.stackAllocState`に自身を格納します。これにより、次の`stackalloc`呼び出しでこのオブジェクトが再利用される準備が整います。

3.  **`stackalloc`関数での`defer`による管理**:
    `stackalloc`関数は、`newStackAllocState`で`stackAllocState`を取得し、`defer putStackAllocState(s)`を使って関数終了時に必ずプールに戻すように変更されました。これにより、リソースのリークを防ぎ、確実に再利用サイクルに乗せることができます。

    ```go
    func stackalloc(f *Func, spillLive [][]ID) [][]ID {
        // ...
        s := newStackAllocState(f)
        s.init(f, spillLive)
        defer putStackAllocState(s) // 関数終了時に必ずプールに戻す
        // ...
    }
    ```

4.  **スライス内部の要素の再利用**:
    `stackAllocState.init`関数や`stackAllocState.stackalloc`関数内で使用される複数のスライス（`s.values`, `s.names`, `s.slots`, `s.used`, `s.interfere`）について、常に`make`で新しいスライスを割り当てるのではなく、既存のスライスの容量が十分であれば、それを再スライス（`s.values = s.values[:n]`）して再利用するように変更されました。これにより、スライスの基盤となる配列の再割り当てを回避し、ヒープ割り当てを削減します。

    例: `s.values`の初期化

    ```go
    // 変更前: 常に新しいスライスを割り当てる
    // s.values = make([]stackValState, f.NumValues())

    // 変更後: 容量が十分なら再利用、そうでなければ新規割り当て
    if n := f.NumValues(); cap(s.values) >= n {
        s.values = s.values[:n]
    } else {
        s.values = make([]stackValState, n)
    }
    ```
    このパターンは、`s.names`, `s.slots`, `s.used`, `s.interfere`といった他のスライスにも適用されています。

これらの変更により、`stackalloc`フェーズが複数回実行される場合（例えば、複数の関数をコンパイルする際）、`stackAllocState`オブジェクトとその内部のスライスが繰り返し割り当てられることを防ぎ、コンパイラ全体のメモリフットプリントとGC負荷を大幅に削減することに成功しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/config.go` の変更

*   **`stackAllocState *stackAllocState` フィールドの追加**:
    `Config`構造体は、GoコンパイラのSSAバックエンドにおけるグローバルな設定やリソースを管理します。この変更により、`Config`が`stackAllocState`オブジェクトへのポインタを保持できるようになりました。これは、`stackAllocState`オブジェクトをコンパイルプロセス全体で再利用するための「プール」として機能させるための基盤となります。これにより、各関数が`stackalloc`フェーズを実行するたびに新しい`stackAllocState`を割り当てるのではなく、既存のオブジェクトを再利用できるようになります。

### `src/cmd/compile/internal/ssa/stackalloc.go` の変更

*   **`stackAllocState` 構造体のフィールド追加**:
    `stackAllocState`構造体自体に、`live`, `names`, `slots`, `used`といったスライスが追加されました。これらは以前は`stackalloc`関数内でローカル変数として宣言され、毎回新しく割り当てられていましたが、`stackAllocState`の一部とすることで、オブジェクトの再利用時にこれらのスライスも再利用の対象となります。

*   **`newStackAllocState(f *Func) *stackAllocState` 関数の追加**:
    この関数は、`stackAllocState`オブジェクトの取得を担当します。
    1.  `f.Config.stackAllocState`をチェックし、以前にプールに戻された`stackAllocState`オブジェクトがあれば、それを返します。
    2.  もしプールが空（`nil`）であれば、新しい`stackAllocState`オブジェクトを割り当てて返します。
    3.  `s.f != nil`のチェックは、`newStackAllocState`が呼ばれたにもかかわらず、以前の`stackAllocState`が`putStackAllocState`によって適切にクリアされていない（つまり、まだ`f`への参照が残っている）場合にパニックを発生させ、バグを早期に検出するための防御的なコードです。

*   **`putStackAllocState(s *stackAllocState)` 関数の追加**:
    この関数は、`stackAllocState`オブジェクトをプールに戻す役割を担います。
    1.  `s.values`, `s.interfere`, `s.names`, `s.slots`, `s.used`といった内部スライスの要素をゼロ値でクリアします。これは、以前のコンパイルセッションのデータが残らないようにするためと、GCが不要な参照を早期に解放できるようにするためです。
    2.  `s.f = nil`とすることで、`stackAllocState`オブジェクトが`Func`オブジェクトへの参照を持たないようにします。これにより、`Func`オブジェクトがGCされるのを妨げないようにします。
    3.  `s.f.Config.stackAllocState = s`によって、現在の`stackAllocState`オブジェクトを`Config`のプールに格納し、次の利用に備えます。

*   **`stackalloc` 関数での `newStackAllocState` と `defer putStackAllocState(s)` の使用**:
    `stackalloc`関数の冒頭で`s := newStackAllocState(f)`を呼び出して`stackAllocState`オブジェクトを取得し、`defer putStackAllocState(s)`を使って関数が終了する際に必ず`putStackAllocState`が実行されるようにしています。これにより、オブジェクトの取得と解放のペアが保証され、リソース管理が簡素化されます。

*   **スライスの再利用ロジックの導入 (`init`, `stackalloc`, `buildInterferenceGraph` 内)**:
    `init`, `stackalloc`, `buildInterferenceGraph`といった関数内で、`make([]Type, size)`を使って新しいスライスを割り当てる代わりに、以下のパターンが導入されました。

    ```go
    if n := f.NumValues(); cap(s.values) >= n {
        s.values = s.values[:n] // 既存の容量が十分なら再スライス
    } else {
        s.values = make([]stackValState, n) // 容量が足りなければ新規割り当て
    }
    ```
    このパターンは、`s.values`, `s.names`, `s.slots`, `s.used`, `s.interfere`といった複数のスライスに適用されています。これにより、スライスの基盤となる配列が一度確保されれば、その後の呼び出しでは再割り当てをせずに既存のメモリ領域を再利用できるため、ヒープ割り当ての回数と量を大幅に削減できます。これは、Goにおけるメモリ最適化の一般的なイディオムであり、特に一時的なデータ構造が頻繁に生成・破棄される場合に効果的です。

これらの変更の組み合わせにより、GoコンパイラのSSAバックエンドは、コンパイル時のメモリ使用量を劇的に削減し、GCの負担を軽減することで、全体的なコンパイルパフォーマンスを向上させています。

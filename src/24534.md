# [インデックス 24534] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるプロポーショナルスイープのメカニズムを改善するものです。具体的には、スイープの進行度をオブジェクトの割り当てバイト数ではなく、スパン（メモリブロック）の割り当てバイト数に比例させるように変更し、GCサイクル開始時のスイープ負債（sweep debt）を解消することを目的としています。これにより、GCの開始が遅延する問題を解決し、全体的なGC性能を向上させます。

## コミット

```
runtime: make sweep proportional to spans bytes allocated

Proportional concurrent sweep is currently based on a ratio of spans
to be swept per bytes of object allocation. However, proportional
sweeping is performed during span allocation, not object allocation,
in ordered to minimize contention and overhead. Since objects are
allocated from spans after those spans are allocated, the system tends
to operate in debt, which means when the next GC cycle starts, there
is often sweep debt remaining, so GC has to finish the sweep, which
delays the start of the cycle and delays enabling mutator assists.

For example, it's quite likely that many Ps will simultaneously refill
their span caches immediately after a GC cycle (because GC flushes the
span caches), but at this point, there has been very little object
allocation since the end of GC, so very little sweeping is done. The
Ps then allocate objects from these cached spans, which drives up the
bytes of object allocation, but since these allocations are coming
from cached spans, nothing considers whether more sweeping has to
happen. If the sweep ratio is high enough (which can happen if the
next GC trigger is very close to the retained heap size), this can
easily represent a sweep debt of thousands of pages.

Fix this by making proportional sweep proportional to the number of
bytes of spans allocated, rather than the number of bytes of objects
allocated. Prior to allocating a span, both the small object path and
the large object path ensure credit for allocating that span, so the
system operates in the black, rather than in the red.

Combined with the previous commit, this should eliminate all sweeping
from GC start up. On the stress test in issue #11911, this reduces the
time spent sweeping during GC (and delaying start up) by several
orders of magnitude:

                mean    99%ile     max
    pre fix      1 ms    11 ms   144 ms
    post fix   270 ns   735 ns   916 ns

Updates #11911.
```

## 変更の背景

Goのガベージコレクタは、並行（concurrent）かつプロポーショナル（proportional）なスイープを採用しています。プロポーショナルスイープとは、GCサイクル中にミューテータ（ユーザープログラム）がメモリを割り当てる際に、その割り当て量に応じて少しずつスイープ作業を進めることで、GCの一時停止時間を短縮し、アプリケーションのスループットを向上させる仕組みです。

しかし、このコミット以前のGoランタイムでは、プロポーショナルスイープの「負債」が発生するという問題がありました。具体的には、スイープの進行度は「オブジェクトの割り当てバイト数」に基づいて計算されていましたが、実際のスイープ作業は「スパンの割り当て時」に行われていました。

このミスマッチが問題を引き起こしていました。オブジェクトは、まずスパンが割り当てられ、そのスパンの中から割り当てられます。GCサイクル終了後、多くのP（プロセッサ）が同時にスパンキャッシュを補充する可能性があります。この時点では、GC終了後間もないため、オブジェクトの割り当てはほとんど行われておらず、結果としてスイープ作業もほとんど進みません。しかし、その後Pはキャッシュされたスパンからオブジェクトを割り当て始め、オブジェクトの割り当てバイト数は増加します。この際、キャッシュされたスパンからの割り当てであるため、追加のスイープが必要であるという考慮がなされず、スイープ負債が蓄積されていきました。

このスイープ負債が残った状態で次のGCサイクルが開始されると、GCはまず残っているスイープ負債を解消しなければならず、その結果、GCサイクルの開始が遅延し、ミューテータアシスト（GCがミューテータのメモリ割り当てを助ける仕組み）の有効化も遅れていました。特に、次のGCトリガーがヒープの保持サイズに非常に近い場合、この負債は何千ページにも及ぶ可能性がありました。

この遅延は、特にレイテンシに敏感なアプリケーションにおいてパフォーマンスの低下を招くため、重要な改善点とされていました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: 不要になったメモリを自動的に解放する仕組み。GoのGCは、並行マーク＆スイープ方式を採用しています。
    *   **マークフェーズ**: どのオブジェクトがまだ使用されているかを識別します。
    *   **スイープフェーズ**: マークされなかった（使用されていない）オブジェクトが占めていたメモリを解放し、再利用可能にします。
*   **並行GC (Concurrent GC)**: GC作業の一部をユーザープログラム（ミューテータ）と並行して実行することで、GCによるアプリケーションの一時停止時間を最小限に抑えます。
*   **プロポーショナルスイープ (Proportional Sweep)**: 並行スイープの一種で、ミューテータがメモリを割り当てる際に、その割り当て量に比例してスイープ作業を進めます。これにより、GCサイクル全体でスイープ作業が分散され、GCの一時停止が短縮されます。
*   **mheap**: Goランタイムのグローバルなヒープを表すデータ構造。メモリの割り当てと解放を管理します。
*   **mspan**: `mheap`から割り当てられる連続したメモリページのブロック。オブジェクトは`mspan`から割り当てられます。`mspan`は特定のサイズクラス（small, largeなど）のオブジェクトを格納するために使用されます。
*   **mcentral**: 特定のサイズクラスの`mspan`を管理するデータ構造。`mcache`（各Pにローカルなキャッシュ）に`mspan`を提供します。
*   **mcache**: 各P（プロセッサ）にローカルな`mspan`のキャッシュ。ミューテータは通常、`mcache`から直接メモリを割り当てることで、ロックの競合を減らし、高速な割り当てを実現します。`mcache`が空になると、`mcentral`から新しい`mspan`を取得します。
*   **P (Processor)**: Goスケジューラにおける論理プロセッサ。Goルーチンを実行するコンテキストを提供します。
*   **Sweep Debt**: GCサイクル中に十分にスイープ作業が進まず、次のGCサイクル開始時に未処理のスイープが残ってしまう状態。

## 技術的詳細

このコミットの核心は、プロポーショナルスイープの「負債」問題を解決するために、スイープの進行度を追跡する指標を変更した点にあります。

1.  **スイープ指標の変更**:
    *   変更前: プロポーショナルスイープは、`memstats.heap_live` (ライブヒープサイズ) と `memstats.heap_marked` (マークされたヒープサイズ) の差、つまり「オブジェクトの割り当てバイト数」に基づいてスイープすべきページ数を計算していました。
    *   変更後: スイープは「スパンの割り当てバイト数」に比例するように変更されました。新しいフィールド `mheap_.spanBytesAlloc` が導入され、GCサイクル中に割り当てられたスパンの合計バイト数を追跡します。

2.  **`deductSweepCredit` 関数の導入**:
    *   この新しい関数は、スパンが割り当てられる「前」に呼び出されます。
    *   `spanBytesAlloc` を更新し、現在のスイープ負債（`pagesOwed`）を計算します。`pagesOwed` は `mheap_.sweepPagesPerByte * float64(spanBytesAlloc)` で計算されます。
    *   もしスイープ負債が残っている場合（`pagesOwed - mheap_.pagesSwept > callerSweepPages`）、`gosweepone()` を呼び出して、負債が解消されるまでスイープ作業を実行します。`callerSweepPages` は、呼び出し元が既にスイープする予定のページ数（例えば、大きな割り当ての場合）を考慮するためのものです。
    *   これにより、システムは常に「黒字」（スイープ負債がない状態）で動作し、スパンが割り当てられる時点で必要なスイープが実行されるようになります。

3.  **`mcentral_CacheSpan` の変更**:
    *   `mcentral_CacheSpan` は、`mcache`にスパンを供給する際に呼び出されます。
    *   変更前は、ここで複雑なスイープ負債の計算と `gosweepone()` の呼び出しが行われていました。
    *   変更後、このロジックは `deductSweepCredit` の呼び出しに置き換えられ、よりシンプルかつ正確になりました。

4.  **`largeAlloc` の変更**:
    *   大きなオブジェクトの割り当てパスである `largeAlloc` も、スパンを割り当てる前に `deductSweepCredit` を呼び出すようになりました。これにより、大きな割り当てにおいてもスイープ負債が発生しないようにします。

5.  **`gcSweep` の変更**:
    *   GCスイープの開始時に、`mheap_.spanBytesAlloc` が `0` にリセットされるようになりました。これは、新しいGCサイクルが始まるたびに、スパン割り当てバイト数のカウントを最初からやり直すためです。

この変更により、スパンが割り当てられるたびに、そのスパンのサイズに応じたスイープクレジットが差し引かれ、必要に応じてスイープが実行されます。これにより、GCサイクル開始時に大量のスイープ負債が残る状況が回避され、GCの開始遅延が大幅に削減されました。

コミットメッセージに記載されている性能改善は顕著で、ストレステストにおいてスイープにかかる時間がミリ秒単位からナノ秒単位へと数桁改善されています。これは、GCの一時停止時間の削減に直結し、Goアプリケーションの応答性とスループットの向上に大きく貢献します。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下のファイルに集中しています。

*   **`src/runtime/malloc.go`**:
    *   `largeAlloc` 関数内で、`mHeap_Alloc` を呼び出す前に `deductSweepCredit` が呼び出されるようになりました。
        ```go
        // Deduct credit for this span allocation and sweep if
        // necessary. mHeap_Alloc will also sweep npages, so this only
        // pays the debt down to npage pages.
        deductSweepCredit(npages*_PageSize, npages)
        ```

*   **`src/runtime/mcentral.go`**:
    *   `mCentral_CacheSpan` 関数内の既存のスイープ負債処理ロジックが削除され、`deductSweepCredit` の呼び出しに置き換えられました。
        ```go
        // Deduct credit for this span allocation and sweep if necessary.
        deductSweepCredit(uintptr(class_to_size[c.sizeclass]), 0)
        ```

*   **`src/runtime/mgc.go`**:
    *   `gcSweep` 関数内で、GCスイープの開始時に `mheap_.spanBytesAlloc` が `0` に初期化されるようになりました。
        ```go
        mheap_.spanBytesAlloc = 0
        ```

*   **`src/runtime/mgcsweep.go`**:
    *   新しい関数 `deductSweepCredit` が追加されました。
        ```go
        // deductSweepCredit deducts sweep credit for allocating a span of
        // size spanBytes. This must be performed *before* the span is
        // allocated to ensure the system has enough credit. If necessary, it
        // performs sweeping to prevent going in to debt. If the caller will
        // also sweep pages (e.g., for a large allocation), it can pass a
        // non-zero callerSweepPages to leave that many pages unswept.
        //
        // deductSweepCredit is the core of the "proportional sweep" system.
        // It uses statistics gathered by the garbage collector to perform
        // enough sweeping so that all pages are swept during the concurrent
        // sweep phase between GC cycles.
        //
        // mheap_ must NOT be locked.
        func deductSweepCredit(spanBytes uintptr, callerSweepPages uintptr) {
            if mheap_.sweepPagesPerByte == 0 {
                // Proportional sweep is done or disabled.
                return
            }

            // Account for this span allocation.
            spanBytesAlloc := xadd64(&mheap_.spanBytesAlloc, int64(spanBytes))

            // Fix debt if necessary.
            pagesOwed := int64(mheap_.sweepPagesPerByte * float64(spanBytesAlloc))
            for pagesOwed-int64(atomicload64(&mheap_.pagesSwept)) > int64(callerSweepPages) {
                if gosweepone() == ^uintptr(0) {
                    mheap_.sweepPagesPerByte = 0
                    break
                }
            }
        }
        ```

*   **`src/runtime/mheap.go`**:
    *   `mheap` 構造体に新しいフィールド `spanBytesAlloc` が追加されました。
        ```go
        spanBytesAlloc    uint64  // bytes of spans allocated this cycle; updated atomically
        ```

## コアとなるコードの解説

このコミットの核となる変更は、`deductSweepCredit` 関数の導入と、それがメモリ割り当てパスに統合されたことです。

1.  **`mheap` 構造体への `spanBytesAlloc` の追加**:
    *   `mheap` はGoランタイムのグローバルヒープを表す構造体です。
    *   `spanBytesAlloc` は `uint64` 型で、現在のGCサイクル中に割り当てられたスパンの合計バイト数を原子的に（atomically）追跡します。これは、スイープの進行度を計算するための新しい指標となります。

2.  **`deductSweepCredit` 関数の動作**:
    *   この関数は、`spanBytes`（割り当てられるスパンのサイズ）と `callerSweepPages`（呼び出し元が既にスイープする予定のページ数）を引数に取ります。
    *   まず、`mheap_.sweepPagesPerByte` が `0` であれば、プロポーショナルスイープが無効か完了しているため、すぐにリターンします。
    *   `xadd64(&mheap_.spanBytesAlloc, int64(spanBytes))` を使用して、`spanBytesAlloc` に現在のスパンのサイズを加算します。`xadd64` はアトミックな加算操作であり、複数のPからの同時アクセスに対して安全です。
    *   `pagesOwed` は、`mheap_.sweepPagesPerByte` と更新された `spanBytesAlloc` を基に、現在スイープすべき総ページ数を計算します。`sweepPagesPerByte` は、GCサイクル開始時に設定される、バイトあたりのスイープページ数の比率です。
    *   `for` ループ内で、`pagesOwed` から `mheap_.pagesSwept`（既にスイープされたページ数）と `callerSweepPages` を引いた値が `0` より大きい場合、つまりスイープ負債が残っている場合に `gosweepone()` を呼び出します。
    *   `gosweepone()` は、ヒープから未スイープのスパンを一つ見つけてスイープする関数です。これにより、負債が解消されるまでスイープ作業が強制的に実行されます。
    *   `gosweepone()` が `^uintptr(0)` を返した場合（スイープすべきスパンがもうない場合）、`mheap_.sweepPagesPerByte` を `0` に設定してスイープを停止します。

3.  **`mCentral_CacheSpan` と `largeAlloc` からの呼び出し**:
    *   `mCentral_CacheSpan` は、`mcache`が空になり、`mcentral`から新しいスパンを取得する際に呼び出されます。この時点で `deductSweepCredit` が呼び出されることで、スパンがユーザープログラムに渡される前に、そのスパンの割り当てに対するスイープクレジットが処理されます。
    *   `largeAlloc` は、大きなオブジェクト（ページサイズを超えるオブジェクト）を直接`mheap`から割り当てる際に呼び出されます。ここでも同様に、スパンが割り当てられる前に `deductSweepCredit` が呼び出され、スイープ負債の発生を防ぎます。

これらの変更により、Goランタイムはスパンの割り当て時にリアルタイムでスイープ負債を管理できるようになり、GCサイクル開始時の不要な遅延が解消されました。

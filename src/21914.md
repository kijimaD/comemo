# [インデックス 21914] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9固有のメモリ管理に関するバグ修正です。具体的には、Plan 9の`sysFree`システムコールがメモリを解放する際に、Goランタイムが期待する「ゼロ初期化されたメモリ」の保証が破られることによって発生するデータ破損の問題を解決します。

Author: Austin Clements <austin@google.com>
Date:   Thu Feb 12 10:37:01 2015 -0500

    runtime: on Plan 9, zero memory returned to the brk by sysFree
    
    Plan 9's sysFree has an optimization where if the object being freed
    is the last object allocated, it will roll back the brk to allow the
    memory to be reused by sysAlloc.  However, it does not zero this
    "returned" memory, so as a result, sysAlloc can return non-zeroed
    memory after a sysFree.  This leads to corruption because the runtime
    assumes sysAlloc returns zeroed memory.
    
    Fix this by zeroing the memory returned by sysFree.
    
    Fixes #9846.

## 元コミット内容

このコミットは、Plan 9オペレーティングシステム上でGoランタイムがメモリを管理する際のバグを修正します。

Plan 9の`sysFree`関数には、解放されるオブジェクトが最後に割り当てられたオブジェクトである場合に、`brk`（プログラムのデータセグメントの終端）を巻き戻して、そのメモリを`sysAlloc`が再利用できるようにする最適化があります。しかし、この「返された」メモリはゼロクリアされません。その結果、`sysFree`の後に`sysAlloc`がゼロクリアされていないメモリを返す可能性があり、Goランタイムが`sysAlloc`がゼロクリアされたメモリを返すと仮定しているため、データ破損につながります。

この問題は、`sysFree`によって返されるメモリをゼロクリアすることで修正されます。

この修正は、Issue #9846を解決します。

## 変更の背景

Goランタイムは、新しく割り当てられたメモリが常にゼロ初期化されているという重要な仮定（「ゼロ初期化メモリの仮定」）に基づいて設計されています。これは、Goの変数型がデフォルトでゼロ値を持つという言語仕様と密接に関連しており、プログラマが明示的に初期化しなくても、新しく確保されたメモリが予測可能な状態であることを保証します。例えば、`new(int)`で確保された整数は0に、`new(bool)`で確保されたブール値は`false`に、ポインタは`nil`に初期化されます。この仮定は、Goのメモリ安全性とプログラミングの簡潔さに大きく貢献しています。

しかし、Plan 9オペレーティングシステムにおけるメモリ管理の特定の挙動が、このGoランタイムのゼロ初期化メモリの仮定を破る原因となっていました。Plan 9では、`brk`システムコールを通じてプログラムのデータセグメントの終端を操作することでメモリを管理します。Goランタイムは、`sysAlloc`関数を通じてOSからメモリを要求し、`sysFree`関数を通じてメモリを解放します。

問題は、Plan 9の`sysFree`に存在する特定の最適化にありました。通常、`sbrk`（`brk`の一般的な形式）ベースのメモリ管理では、一度確保されたメモリをOSに返すことは困難であり、Goランタイムは内部的なフリーリストで管理します。しかし、Plan 9の`sysFree`は、解放されるメモリブロックがデータセグメントの最上位（`brk`の直下）にある場合、`brk`ポインタを巻き戻すことで、そのメモリをOSに「返す」ような挙動をします。この最適化自体は効率的ですが、`sysFree`がこの巻き戻されたメモリ領域をゼロクリアしないという問題がありました。

その結果、`sysFree`によって`brk`が巻き戻された後、その領域が`sysAlloc`によって再利用されると、以前のデータが残ったままの非ゼロ初期化メモリがGoランタイムに渡されてしまいます。これはGoランタイムのゼロ初期化メモリの仮定に違反し、予期せぬデータ破損やプログラムの誤動作を引き起こす可能性がありました。このコミットは、この特定のPlan 9の`sysFree`の挙動によって引き起こされるGoランタイムのメモリ破損バグを修正するために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **Goランタイムのゼロ初期化メモリの仮定 (Zeroed Memory Assumption)**:
    Go言語では、`new`キーワードやスライス、マップの作成などによって新しく確保されるメモリ領域は、自動的にゼロ値で初期化されることが保証されています。例えば、`var i int`と宣言された整数型変数`i`は自動的に`0`に初期化されますし、`make([]byte, 10)`で作成されたバイトスライスは、その要素がすべて`0`に初期化されます。この特性は、プログラマが明示的にメモリを初期化する手間を省き、未初期化メモリによるバグ（セキュリティ脆弱性を含む）を防ぐ上で非常に重要です。Goランタイムのメモリ管理システムは、このゼロ初期化の保証を維持するように設計されています。

2.  **`brk`システムコールとメモリ管理**:
    Unix系OS（およびPlan 9）では、プログラムが動的にメモリを確保する際の一つの方法として、`brk`（または`sbrk`）システムコールを使用することがあります。`brk`は、プロセスのデータセグメントの終端（「プログラムブレイク」または「ヒープブレイク」と呼ばれる）の位置を変更します。
    *   `brk`ポインタを上位アドレスに移動させることで、プログラムはより多くのメモリを確保できます。
    *   `brk`ポインタを下位アドレスに移動させることで、メモリをOSに解放することができます。ただし、これは通常、データセグメントの最上位にあるメモリブロックに対してのみ効率的に行われます。中間にあるメモリブロックを解放しても、`brk`ポインタを動かせないため、OSには返されず、プロセスのアドレス空間内に残ります。

3.  **Goランタイムのメモリ管理の抽象化**:
    Goランタイムは、OSの提供する低レベルなメモリ管理機能（`brk`や`mmap`など）を抽象化し、独自のメモリ管理システム（アリーナ、スパン、mcacheなど）を構築しています。`sysAlloc`はGoランタイムがOSから生のメモリブロックを取得するための関数であり、`sysFree`はGoランタイムがOSにメモリブロックを返すための関数です。これらの関数はOSに依存し、その実装はOSごとに異なります（例: Linuxでは`mmap`、Plan 9では`brk`ベース）。

4.  **Plan 9のメモリ管理の特性**:
    Plan 9は、Unixとは異なる設計思想を持つOSであり、そのメモリ管理も独自の特性を持っています。このコミットで問題となったのは、Plan 9の`sysFree`が、解放されるメモリが`brk`の直下にある場合に`brk`を巻き戻すという「最適化」を行う点です。この最適化は、メモリの再利用を効率化するためのものですが、Goランタイムのゼロ初期化の仮定と衝突しました。

## 技術的詳細

このバグは、Goランタイムのゼロ初期化メモリの仮定と、Plan 9の`sysFree`システムコールの特定の最適化との間の不整合によって引き起こされました。

1.  **Goランタイムのゼロ初期化の期待**: Goランタイムは、`sysAlloc`を通じてOSから取得したメモリ領域が、常にビットパターンとしてゼロ（すべてのビットが0）で初期化されていることを期待します。これは、Go言語の型システムにおけるゼロ値の概念と密接に結びついており、新しく割り当てられた変数が予測可能な初期状態を持つことを保証します。この仮定が破られると、未初期化のメモリが使用され、古いデータが残っていたり、ガベージコレクションが誤動作したりする原因となり、結果としてデータ破損やクラッシュにつながります。

2.  **Plan 9の`sysFree`の最適化**: Plan 9のメモリ管理において、`sysFree`関数は、解放されるメモリブロックが現在の`brk`ポインタの直下にある場合（つまり、最後に割り当てられたメモリブロックである場合）、`brk`ポインタをそのブロックの開始位置まで巻き戻すという最適化を行います。これにより、巻き戻された領域はOSに「返された」とみなされ、後続の`sysAlloc`呼び出しによって再利用される可能性があります。これは、メモリの断片化を減らし、効率的なメモリ再利用を促進するための一般的な最適化手法です。

3.  **問題の発生**: しかし、このPlan 9の`sysFree`の最適化は、巻き戻されたメモリ領域をゼロクリアしませんでした。つまり、`sysFree`が`brk`を巻き戻してメモリを「解放」した後も、その領域には以前のデータがそのまま残っていました。その後、Goランタイムが`sysAlloc`を呼び出して新しいメモリを要求し、たまたまこの巻き戻された領域が再利用されると、Goランタイムはゼロ初期化されていないメモリを受け取ることになります。これはGoランタイムのゼロ初期化メモリの仮定に違反し、Goプログラム内で未初期化データが使用されることになり、データ破損や予測不能な動作を引き起こしました。

4.  **修正**: このコミットは、`src/runtime/mem_plan9.go`内の`sysFree`関数に、`brk`を巻き戻す直前に`memclr`関数を呼び出す行を追加することで、この問題を解決します。`memclr`は指定されたメモリ領域をゼロクリアするGoランタイムの内部関数です。
    具体的には、`sysFree`が`bloc`（Goランタイムが管理する`brk`に相当するポインタ）を巻き戻す前に、巻き戻される領域（`bloc`から`n`バイト分）を`memclr`でゼロクリアします。これにより、`sysFree`によって「返された」メモリが常にゼロ初期化された状態になり、`sysAlloc`がその領域を再利用する際にGoランタイムのゼロ初期化メモリの仮定が満たされるようになります。

この修正は、Plan 9という特定のOS環境におけるメモリ管理の挙動と、Goランタイムの普遍的なメモリ管理の仮定との間のギャップを埋めるものであり、Goプログラムの堅牢性と移植性を向上させます。

## コアとなるコードの解説

変更は`src/runtime/mem_plan9.go`ファイルの`sysFree`関数内の一箇所です。

`sysFree`関数は、GoランタイムがOSにメモリを解放する際に呼び出されます。
*   `v unsafe.Pointer`: 解放されるメモリブロックの開始アドレス。
*   `n uintptr`: 解放されるメモリブロックのサイズ。

関数内部では、まず`n`が`memRound(n)`によってメモリのアライメントに合わせて丸められます。

重要なのは以下の`if`文のブロックです。
```go
	if bloc == uintptr(v)+n {
		bloc -= n
		memclr(unsafe.Pointer(bloc), n) // 追加された行
	}
```

*   `bloc`: これはGoランタイムが内部的に管理している、Plan 9における`brk`ポインタに相当するものです。GoランタイムがOSから確保しているメモリ領域の現在の終端を示します。
*   `uintptr(v)+n`: これは、現在解放しようとしているメモリブロックの終端アドレスです。

`if bloc == uintptr(v)+n`という条件は、「解放しようとしているメモリブロックが、GoランタイムがOSから確保しているメモリ領域の現在の終端（`bloc`）にぴったりと一致しているか」をチェックしています。つまり、このブロックが最後に割り当てられたメモリであり、かつ、その直後に他の割り当てがないため、`brk`ポインタを巻き戻すことが可能であることを意味します。

この条件が真である場合、以下の処理が行われます。
1.  `bloc -= n`: `bloc`ポインタが`n`バイト分だけ下位アドレスに移動されます。これは、`brk`ポインタを巻き戻すことに相当し、`n`バイト分のメモリがGoランタイムの管理下から解放され、OSに「返された」状態になります。
2.  `memclr(unsafe.Pointer(bloc), n)`: **この行がこのコミットで追加された修正です。**
    *   `unsafe.Pointer(bloc)`: 巻き戻された`bloc`の新しい位置（つまり、解放されたメモリ領域の開始アドレス）を`unsafe.Pointer`にキャストしています。
    *   `n`: ゼロクリアするメモリのサイズです。
    `memclr`関数は、指定されたアドレスから指定されたサイズのメモリ領域をすべてゼロ（0x00）で埋めます。

この追加された一行により、`sysFree`が`brk`を巻き戻してメモリを解放する際に、その解放された領域が確実にゼロクリアされるようになります。これにより、後続の`sysAlloc`呼び出しがこの領域を再利用した場合でも、Goランタイムのゼロ初期化メモリの仮定が満たされ、データ破損が防止されます。

# [インデックス 19348] ファイルの概要

このコミットは、Go言語の正規表現エンジンにおけるパフォーマンス最適化に関するものです。特に、非常に複雑な正規表現に対してワンパスアルゴリズムの適用可能性をチェックする際の過度な計算コストを削減することを目的としています。

Author: Rob Pike <r@golang.org>
Date:   Tue May 13 12:17:49 2014 -0700

    regexp/syntax: don't waste time checking for one pass algorithm
    The code recurs very deeply in cases like (?:x{1,1000}){1,1000}
    Since if much time is spent checking whether one pass is possible, it's not
    worth doing at all, a simple fix is proposed: Stop if the check takes too long.
    To do this, we simply avoid machines with >1000 instructions.
    
    Benchmarks show a percent or less change either way, effectively zero.
    
    Fixes #7608.

## 元コミット内容

正規表現の構文解析において、ワンパスアルゴリズムの適用可能性をチェックする際に時間を無駄にしないようにする変更です。`(?:x{1,1000}){1,1000}`のような非常に深い再帰を伴う正規表現の場合、ワンパスチェックのコードが非常に深く再帰し、スタックオーバーフローやパフォーマンス低下を引き起こす可能性がありました。ワンパスが可能かどうかをチェックするのに多くの時間が費やされるのであれば、そのチェック自体を行う価値がないという考えに基づき、チェックに時間がかかりすぎる場合は停止するという単純な修正が提案されました。具体的には、1000以上の命令を持つ正規表現マシンに対しては、ワンパスチェックを行わないようにします。ベンチマークでは、この変更によるパフォーマンスへの影響は実質的にゼロであることが示されています。この変更はIssue #7608を修正します。

## 変更の背景

Go言語の`regexp`パッケージは、GoogleのRE2エンジンをベースにしており、線形時間でのマッチングを保証する高性能な正規表現エンジンです。このエンジンは、入力文字列を一度走査するだけでマッチングを完了できる「ワンパスアルゴリズム」を適用できるかどうかを内部的にチェックし、可能な場合はその最適化されたパスを使用します。

しかし、一部の非常に複雑な正規表現、特に`(?:x{1,1000}){1,1000}`のようにネストされた量指定子を持つパターンでは、このワンパスアルゴリズムの適用可能性を判断するための内部的なチェック処理が、非常に深い再帰呼び出しを発生させることがありました。この深い再帰は、Goランタイムのスタックサイズを圧迫し、最悪の場合スタックオーバーフローを引き起こす可能性がありました。また、ワンパスチェック自体に時間がかかりすぎると、その最適化の恩恵よりもチェックのコストが上回ってしまうという問題も発生していました。

このコミットは、このような特定のケースにおいて、ワンパスアルゴリズムのチェックが非効率になる問題を解決するために導入されました。

## 前提知識の解説

### 正規表現 (Regular Expression)

正規表現は、文字列のパターンを記述するための強力なツールです。テキスト検索、置換、検証など、様々な場面で利用されます。例えば、`a+b`は「aが1回以上続き、その後にbが続く」というパターンを表します。

### Go言語の`regexp`パッケージ

Go言語の標準ライブラリには、正規表現を扱うための`regexp`パッケージが用意されています。このパッケージは、GoogleのRE2ライブラリをベースにしており、線形時間でのマッチングを保証するという特徴があります。これは、入力文字列の長さに比例してマッチング時間が延びることを意味し、一般的な正規表現エンジンで問題となる「最悪計算量問題」（バックトラッキングによる指数関数的な時間増加）を回避します。ただし、この線形時間保証のため、後方参照（backreferences）など一部の高度な正規表現機能はサポートしていません。

### 正規表現エンジンの種類

正規表現エンジンは大きく分けて2つのタイプがあります。

1.  **DFA (Deterministic Finite Automaton) ベース**: 入力文字列を左から右へ一度だけ走査し、現在の状態と次の文字に基づいて次の状態を決定します。常に線形時間で動作し、マッチングの有無を高速に判断できますが、部分マッチの取得や後方参照などの機能は苦手です。RE2やGoの`regexp`パッケージはDFA的な特性を持ちます。
2.  **NFA (Nondeterministic Finite Automaton) ベース**: バックトラッキング（試行錯誤的にパターンを探索する）を用いてマッチングを行います。より柔軟なパターン表現が可能で、後方参照などもサポートしますが、特定のパターンと入力の組み合わせで指数関数的な時間がかかる「最悪計算量問題」（カタストロフィックバックトラッキング）を引き起こす可能性があります。Perl、Python、Javaなどの多くの言語の正規表現エンジンはNFAベースです。

Goの`regexp`パッケージは、内部的にはNFAを構築しますが、それをDFAに変換して実行することで、DFAの線形時間特性とNFAの表現力を両立させています。

### One-Pass Algorithm (ワンパスアルゴリズム)

正規表現マッチングにおける最適化手法の一つです。特定の正規表現パターンと入力文字列の組み合わせにおいて、入力文字列を最初から最後まで一度だけ走査する（ワンパス）ことで、マッチングを完了できる場合に適用されます。これにより、マッチング処理の効率が大幅に向上します。Goの`regexp`パッケージは、このワンパスアルゴリズムを適用できるかどうかを正規表現のコンパイル時に判断しようとします。

### スタックオーバーフロー (Stack Overflow)

プログラムが関数呼び出しを行う際、その関数のローカル変数や引数などの情報は「スタック」と呼ばれるメモリ領域に積まれます。関数が別の関数を呼び出すと、さらにその情報がスタックに積まれていきます。再帰呼び出し（関数が自分自身を呼び出すこと）が非常に深く繰り返されると、スタック領域が使い果たされ、これ以上情報を積むことができなくなります。この状態をスタックオーバーフローと呼び、通常はプログラムのクラッシュにつながります。

## 技術的詳細

このコミットの技術的な核心は、Goの`regexp/syntax`パッケージ内の`Prog`構造体と`makeOnePass`メソッドにあります。

*   **`regexp/syntax`パッケージ**: このパッケージは、正規表現の構文解析を行い、正規表現を内部的な命令列（プログラム）に変換する役割を担っています。この命令列が、正規表現エンジンの実行単位となります。
*   **`Prog`構造体**: 正規表現の内部表現である命令列を保持する構造体です。`p.Inst`は、この命令列のスライス（配列）を指します。
*   **`makeOnePass`メソッド**: `Prog`構造体のメソッドであり、この正規表現がワンパスアルゴリズムで処理可能かどうかを判断し、可能であればそのための最適化された`Prog`を返します。このメソッドは、正規表現の複雑さに応じて再帰的に呼び出されることがあります。

変更前は、`makeOnePass`メソッドが、`(?:x{1,1000}){1,1000}`のような非常に深いネストを持つ正規表現に対して、ワンパスチェックのために非常に深く再帰していました。この再帰の深さが、スタックオーバーフローのリスクや、チェック自体のパフォーマンスコスト増大につながっていました。

今回の修正では、`makeOnePass`メソッドの冒頭に以下のチェックが追加されました。

```go
// If the machine is very long, it's not worth the time to check if we can use one pass.
if len(p.Inst) >= 1000 {
	return NotOnePass
}
```

このコードは、正規表現の内部命令列の長さ（`len(p.Inst)`）が1000以上の場合、ワンパスアルゴリズムのチェックを即座に諦め、`NotOnePass`（ワンパス不可能であることを示す特別な`Prog`）を返すようにします。

この閾値（1000命令）は、経験的に「ワンパスチェックに時間がかかりすぎる」と判断される正規表現の複雑さの目安として設定されています。命令数が1000を超えるような非常に長い正規表現は、ワンパス最適化の恩恵を受ける可能性が低いか、そのチェックコストが最適化のメリットを上回る可能性が高いと判断されたためです。

コミットメッセージにある「Benchmarks show a percent or less change either way, effectively zero.」という記述は、この変更が正規表現エンジンの全体的なパフォーマンスに与える影響が非常に小さいことを示しています。これは、この最適化チェックが問題となるのはごく一部の非常に特殊なケースに限られるためであり、一般的な正規表現の処理速度には影響がないことを意味します。

## コアとなるコードの解説

### `src/pkg/regexp/syntax/prog.go` の変更

`makeOnePass`関数の冒頭に、正規表現の命令列の長さ（`len(p.Inst)`）が1000以上であるかをチェックする条件が追加されました。

```go
// If the machine is very long, it's not worth the time to check if we can use one pass.
if len(p.Inst) >= 1000 {
	return NotOnePass
}
```

*   `p.Inst`は、正規表現を内部的に表現する命令のシーケンスです。このスライスの長さは、正規表現の複雑さに比例します。
*   この`if`文は、「正規表現マシン（命令列）が非常に長い場合、ワンパスアルゴリズムが適用可能かどうかをチェックするのに時間を費やす価値はない」という判断に基づいています。
*   `NotOnePass`は、この正規表現がワンパスアルゴリズムでは処理できないことを示す特別な`*Prog`値です。これにより、深い再帰を伴うワンパスチェックの処理がスキップされ、スタックオーバーフローのリスクが回避されます。

この変更により、非常に複雑な正規表現（特に深いネストを持つもの）のコンパイル時に発生しうるパフォーマンス問題やスタックオーバーフローが防止されます。

### `src/pkg/regexp/all_test.go` の変更

新しいテストケース`TestOnePassCutoff`が追加されました。

```go
// This ran out of stack before issue 7608 was fixed.
func TestOnePassCutoff(t *testing.T) {
	MustCompile(`^(?:x{1,1000}){1,1000}$`)
}
```

*   このテストは、コミットメッセージで問題の例として挙げられている正規表現`^(?:x{1,1000}){1,1000}$`をコンパイルします。
*   コメントにあるように、この正規表現はIssue #7608が修正される前はスタックオーバーフローを引き起こしていました。
*   このテストの目的は、修正が正しく機能し、この種の複雑な正規表現のコンパイルがスタックオーバーフローなしに完了することを確認することです。テストが成功すれば、修正が有効であることが証明されます。

# [インデックス 20387] ファイルの概要

このコミットは、Goランタイムにおけるゴルーチンのステータス管理に関する重要な変更を導入しています。具体的には、ゴルーチンのステータス値と、そのステータスを読み取る関数 `readgstatus` の実装を、Go言語側からC言語側へ移行することで、GoとCのランタイム間の連携を強化し、コードの重複を排除することを目的としています。

## 変更の背景

このコミットが行われた背景には、Goランタイムの進化があります。初期のGoランタイムでは、Go言語で書かれた部分とC言語で書かれた部分（特に低レベルなOSとのインタラクションやスケジューリングの一部）との間で、共通のデータ構造や関数を効率的に共有するメカニズムが十分に成熟していませんでした。

コミットメッセージにある「When this code was written, there was no way for Go to reuse the C function and enum values. Now there is.」という記述は、この状況を明確に示しています。つまり、以前はゴルーチンのステータス値やその読み取りロジックをGo側とC側でそれぞれ定義・実装する必要があり、コードの重複や潜在的な不整合のリスクがありました。

しかし、Go言語とランタイムの開発が進むにつれて、Cgo（GoとCの相互運用機能）や内部的なリンケージメカニズムが改善され、C言語で定義された関数や列挙型（enum）の値をGo言語側から直接利用できるようになりました。この改善により、ゴルーチンのステータス管理のような、GoとCのランタイム間で密接に連携する必要がある部分において、C言語側の「真実の情報源」を直接参照することが可能になったため、この変更が導入されました。これにより、コードの簡素化、保守性の向上、そしてランタイム全体の整合性強化が図られています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する非常に重要なコンポーネントです。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理（ガベージコレクション）、チャネルによる通信、システムコールとの連携など、多岐にわたる機能が含まれます。Goプログラムは、OSのネイティブスレッド上で動作しますが、Goランタイムがその上で多数のゴルーチンを効率的に多重化して実行します。ランタイムの一部はGoで書かれていますが、パフォーマンスが要求される低レベルな部分やOSとのインタラクションはC（またはアセンブリ）で書かれています。

### ゴルーチン (Goroutine)

ゴルーチンはGo言語の並行処理の基本単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行することも可能です。ゴルーチンはGoランタイムによってスケジューリングされ、OSスレッドにマッピングされます。ゴルーチンは、実行中に様々な状態（ステータス）を取ります。

### ゴルーチンのステータス (Goroutine Status)

ゴルーチンは、そのライフサイクルにおいて様々な状態を遷移します。主要なステータスには以下のようなものがあります。

*   **Runnable**: 実行可能だが、現在CPU上で実行されていない状態。スケジューラによって実行されるのを待っている。
*   **Running**: 現在CPU上で実行されている状態。
*   **Syscall**: システムコールを実行中で、OSカーネル内でブロックされている状態。
*   **Waiting**: チャネル操作、ロックの取得、タイマーの待機など、特定のイベントを待っている状態。
*   **Dead**: 実行が終了した状態。
*   **Scan**: ガベージコレクション中に、スタックがスキャンされている状態。これは他のステータスと組み合わされることがあります（例: `ScanRunning`）。

これらのステータスは、ランタイムがゴルーチンをどのように管理し、スケジューリングするかを決定するために不可欠な情報です。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリを利用したり、Goでは実装が難しい低レベルな処理をCで記述したりすることが可能になります。Cgoは、GoとCの間のデータ変換や関数呼び出しのメカニズムを提供します。

### `proc.c` と `proc.go`

Goランタイムのソースコードにおいて、`proc.c` と `proc.go` は、主にプロセッサ（P）、OSスレッド（M）、ゴルーチン（G）の管理、スケジューリング、およびコンテキストスイッチに関連する低レベルなロジックを扱います。

*   `proc.c`: C言語で書かれた部分で、OSとの直接的なインタラクション、低レベルなスケジューリングプリミティブ、アセンブリコードとの連携などが含まれることが多いです。
*   `proc.go`: Go言語で書かれた部分で、高レベルなスケジューリングロジック、ゴルーチンの作成・破棄、状態管理などが含まれます。

これら二つのファイルは密接に連携し、Goの並行処理モデルを支えています。

### `#pragma textflag NOSPLIT`

これはCコンパイラ（またはGoのツールチェーンが使用するコンパイラ）に対するディレクティブ（指示子）です。`NOSPLIT` は、続く関数が複数のコードセクションに分割されないように指示します。これは、特に低レベルなランタイムコードやアセンブリコードから呼び出される関数において重要になることがあります。関数が分割されると、スタックフレームのセットアップやレジスタの保存・復元など、通常の関数呼び出し規約が適用され、オーバーヘッドが発生したり、特定の最適化が妨げられたりする可能性があります。`NOSPLIT` を使用することで、コンパイラは関数全体を単一の連続したコードブロックとして扱い、より効率的なコード生成や、特定の低レベルな操作（例えば、スタックポインタの直接操作）を可能にします。

### `_Grunning`, `_Gscanrunning`

これらは、GoランタイムのC言語側で定義されているゴルーチンのステータスを表す定数です。GoランタイムのCコードでは、ゴルーチンの状態を数値で表現するためにこれらの定数を使用しています。このコミット以前は、Go側でも同様の定数が定義されていましたが、この変更によりC側の定義を直接利用するようになりました。

## 技術的詳細

このコミットの核心は、Goランタイムにおけるゴルーチンのステータス管理を、Go言語側からC言語側へ一元化することにあります。

1.  **ゴルーチンステータス定数のC側への移行**:
    *   変更前は、`src/pkg/runtime/proc.go` 内に `gStatusidle` から `gStatusScanEnqueue` までのゴルーチンステータスを表す定数ブロックがGo言語で定義されていました。これらの定数は、C言語側のランタイムでも同様の目的で使用される値と重複していました。
    *   このコミットでは、`proc.go` からこのGo言語側の定数ブロックが完全に削除されました。これにより、GoコードはC言語側で定義されている対応する定数（例: `_Grunning`, `_Gscanrunning`）を直接参照するようになります。これは、GoツールチェーンがCヘッダーファイルを解析し、Cの定数をGoのコードで利用可能にする機能が成熟したことを示唆しています。この変更により、ステータス値の定義がC側に集約され、GoとCの間での不整合のリスクがなくなります。

2.  **`readgstatus` 関数のC側への移行と最適化**:
    *   変更前は、`src/pkg/runtime/proc.go` に `func readgStatus(gp *g) uint32` というGo言語で書かれた関数が存在し、ゴルーチン `gp` のアトミックステータスを読み取っていました。
    *   このコミットでは、このGo言語の `readgStatus` 関数が削除されました。代わりに、`src/pkg/runtime/proc.c` にC言語で実装された `runtime·readgstatus` 関数が使用されるようになりました。
    *   `proc.c` の `runtime·readgstatus` 関数の定義の直前に `#pragma textflag NOSPLIT` が追加されています。これは、この関数がコンパイラによって分割されないように指示するもので、低レベルなランタイムのコンテキストにおいて、関数呼び出しのオーバーヘッドを最小限に抑えたり、特定の最適化を可能にしたりするために重要です。`readgstatus` はゴルーチンの最も基本的な状態を読み取る関数であるため、その実行効率はランタイム全体のパフォーマンスに直結します。`NOSPLIT` を適用することで、この関数の呼び出しがより効率的になり、スタックフレームの管理などが簡素化される可能性があります。

3.  **`gopark` 関数における変更**:
    *   `src/pkg/runtime/proc.go` 内の `gopark` 関数は、ゴルーチンを待機状態にする際にその現在のステータスをチェックします。
    *   変更前は `status := readgStatus(gp)` とGo言語の関数を呼び出し、`if status != gStatusRunning && status != gStatusScanRunning` とGo言語の定数と比較していました。
    *   変更後は `status := readgstatus(gp)` とC言語の関数を呼び出し、`if status != _Grunning && status != _Gscanrunning` とC言語の定数と比較するように修正されました。これにより、`gopark` 関数もC言語側の統一されたステータス管理ロジックと定数を利用するようになりました。

これらの変更は、GoランタイムのC言語部分とGo言語部分の間の境界をより明確にし、共通の概念（ゴルーチンステータス）を単一の情報源（C言語側）で管理することで、ランタイムの堅牢性と保守性を向上させるものです。また、`readgstatus` のような頻繁に呼び出される可能性のある低レベル関数に `NOSPLIT` を適用することで、パフォーマンスの最適化も図られています。

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリを利用したり、Goでは実装が難しい低レベルな処理をCで記述したりすることが可能です。Cgoは、GoとCの間のデータ変換や関数呼び出しのメカニズムを提供します。

### `proc.c` と `proc.go`

Goランタイムのソースコードにおいて、`proc.c` と `proc.go` は、主にプロセッサ（P）、OSスレッド（M）、ゴルーチン（G）の管理、スケジューリング、およびコンテキストスイッチに関連する低レベルなロジックを扱います。

*   `proc.c`: C言語で書かれた部分で、OSとの直接的なインタラクション、低レベルなスケジューリングプリミティブ、アセンブリコードとの連携などが含まれることが多いです。
*   `proc.go`: Go言語で書かれた部分で、高レベルなスケジューリングロジック、ゴルーチンの作成・破棄、状態管理などが含まれます。

これら二つのファイルは密接に連携し、Goの並行処理モデルを支えています。

### `#pragma textflag NOSPLIT`

これはCコンパイラ（またはGoのツールチェーンが使用するコンパイラ）に対するディレクティブ（指示子）です。`NOSPLIT` は、続く関数が複数のコードセクションに分割されないように指示します。これは、特に低レベルなランタイムコードやアセンブリコードから呼び出される関数において重要になることがあります。関数が分割されると、スタックフレームのセットアップやレジスタの保存・復元など、通常の関数呼び出し規約が適用され、オーバーヘッドが発生したり、特定の最適化が妨げられたりする可能性があります。`NOSPLIT` を使用することで、コンパイラは関数全体を単一の連続したコードブロックとして扱い、より効率的なコード生成や、特定の低レベルな操作（例えば、スタックポインタの直接操作）を可能にします。

### `_Grunning`, `_Gscanrunning`

これらは、GoランタイムのC言語側で定義されているゴルーチンのステータスを表す定数です。GoランタイムのCコードでは、ゴルーチンの状態を数値で表現するためにこれらの定数を使用しています。このコミット以前は、Go側でも同様の定数が定義されていましたが、この変更によりC側の定義を直接利用するようになりました。

## 技術的詳細

このコミットの核心は、Goランタイムにおけるゴルーチンのステータス管理を、Go言語側からC言語側へ一元化することにあります。

1.  **ゴルーチンステータス定数のC側への移行**:
    *   変更前は、`src/pkg/runtime/proc.go` 内に `gStatusidle` から `gStatusScanEnqueue` までのゴルーチンステータスを表す定数ブロックがGo言語で定義されていました。これらの定数は、C言語側のランタイムでも同様の目的で使用される値と重複していました。
    *   このコミットでは、`proc.go` からこのGo言語側の定数ブロックが完全に削除されました。これにより、GoコードはC言語側で定義されている対応する定数（例: `_Grunning`, `_Gscanrunning`）を直接参照するようになります。これは、GoツールチェーンがCヘッダーファイルを解析し、Cの定数をGoのコードで利用可能にする機能が成熟したことを示唆しています。この変更により、ステータス値の定義がC側に集約され、GoとCの間での不整合のリスクがなくなります。

2.  **`readgstatus` 関数のC側への移行と最適化**:
    *   変更前は、`src/pkg/runtime/proc.go` に `func readgStatus(gp *g) uint32` というGo言語で書かれた関数が存在し、ゴルーチン `gp` のアトミックステータスを読み取っていました。
    *   このコミットでは、このGo言語の `readgStatus` 関数が削除されました。代わりに、`src/pkg/runtime/proc.c` にC言語で実装された `runtime·readgstatus` 関数が使用されるようになりました。
    *   `proc.c` の `runtime·readgstatus` 関数の定義の直前に `#pragma textflag NOSPLIT` が追加されています。これは、この関数がコンパイラによって分割されないように指示するもので、低レベルなランタイムのコンテキストにおいて、関数呼び出しのオーバーヘッドを最小限に抑えたり、特定の最適化を可能にしたりするために重要です。`readgstatus` はゴルーチンの最も基本的な状態を読み取る関数であるため、その実行効率はランタイム全体のパフォーマンスに直結します。`NOSPLIT` を適用することで、この関数の呼び出しがより効率的になり、スタックフレームの管理などが簡素化される可能性があります。

3.  **`gopark` 関数における変更**:
    *   `src/pkg/runtime/proc.go` 内の `gopark` 関数は、ゴルーチンを待機状態にする際にその現在のステータスをチェックします。
    *   変更前は `status := readgStatus(gp)` とGo言語の関数を呼び出し、`if status != gStatusRunning && status != gStatusScanRunning` とGo言語の定数と比較していました。
    *   変更後は `status := readgstatus(gp)` とC言語の関数を呼び出し、`if status != _Grunning && status != _Gscanrunning` とC言語の定数と比較するように修正されました。これにより、`gopark` 関数もC言語側の統一されたステータス管理ロジックと定数を利用するようになりました。

これらの変更は、GoランタイムのC言語部分とGo言語部分の間の境界をより明確にし、共通の概念（ゴルーチンステータス）を単一の情報源（C言語側）で管理することで、ランタイムの堅牢性と保守性を向上させるものです。また、`readgstatus` のような頻繁に呼び出される可能性のある低レベル関数に `NOSPLIT` を適用することで、パフォーマンスの最適化も図られています。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の変更

*   `#pragma textflag NOSPLIT` の追加:
    *   これは、`runtime·readgstatus` 関数がコンパイラによって分割されないように指示するディレクティブです。`runtime·readgstatus` はゴルーチンの現在のステータスを読み取る低レベルな関数であり、その実行効率はランタイムのパフォーマンスに直結します。`NOSPLIT` を適用することで、関数呼び出しのオーバーヘッドを削減し、より効率的なコード生成を可能にしています。これは、GoランタイムがC言語のコードと密接に連携し、パフォーマンスがクリティカルな部分で細かな最適化を行っていることを示しています。

### `src/pkg/runtime/proc.go` の変更

1.  **ゴルーチンステータス定数ブロックの削除**:
    *   以前はGo言語で定義されていた `gStatusidle` から `gStatusScanEnqueue` までの定数ブロックが削除されました。これは、これらのステータス値がC言語側のランタイムで既に定義されており、Go言語側からそのC言語の定義を直接利用できるようになったためです。これにより、コードの重複が解消され、GoとCのランタイム間でステータス値の定義が常に同期されるようになり、潜在的な不整合のリスクが排除されます。

2.  **`readgStatus` 関数の削除**:
    *   Go言語で実装されていた `func readgStatus(gp *g) uint32` 関数が削除されました。この関数は、ゴルーチン `gp` のアトミックステータスを読み取る役割を担っていました。この削除は、ステータス読み取りのロジックがC言語側の `runtime·readgstatus` 関数に一元化されたことを意味します。これにより、ステータス読み取りの処理がC言語の低レベルな最適化の恩恵を受けられるようになります。

3.  **`gopark` 関数内の変更**:
    *   `gopark` 関数は、ゴルーチンを待機状態にする際にその現在のステータスをチェックする重要な関数です。
    *   `status := readgStatus(gp)` が `status := readgstatus(gp)` に変更されました。これは、Go言語の `readgStatus` 関数ではなく、C言語の `runtime·readgstatus` 関数を呼び出すようになったことを示しています。
    *   `if status != gStatusRunning && status != gStatusScanRunning` が `if status != _Grunning && status != _Gscanrunning` に変更されました。これは、Go言語で定義されていた `gStatusRunning` や `gStatusScanRunning` といった定数ではなく、C言語側で定義されている `_Grunning` や `_Gscanrunning` といった定数と比較するようになったことを意味します。

これらの変更は、GoランタイムがC言語の低レベルな機能とより密接に連携し、ゴルーチンのステータス管理をより効率的かつ一貫性のある方法で行うための重要なステップです。これにより、ランタイムのパフォーマンスと保守性が向上します。

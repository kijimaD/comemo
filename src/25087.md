# [インデックス 25087] ファイルの概要

このコミットは、Go言語の `compress/gzip` パッケージにおける `gzip.Reader` が、ストリームの途中でデータが途切れている（truncated）場合に、その状態を正しく検出できない問題を修正します。具体的には、`io.ReadFull` の呼び出しが `io.EOF` エラーを適切に処理せず、予期せぬストリームの終了を `io.ErrUnexpectedEOF` として報告するように変更されています。

## 元コミット内容

`compress/gzip`: 切り詰められたストリームを検出する

`io.ReadFull` の呼び出しが `io.EOF` エラーをチェックしないため、リーダーは切り詰められたストリームを検出できませんでした。

`io.EOF` エラーの場合に `io.ErrUnexpectedEOF` を返すように変更します。

## 変更の背景

Go言語の `compress/gzip` パッケージは、gzip形式で圧縮されたデータを読み書きするための機能を提供します。`gzip.Reader` は、圧縮されたgzipストリームを読み込み、解凍して元のデータを提供します。

このコミット以前の `gzip.Reader` の実装では、`io.ReadFull` 関数を使用して固定長のバイト数を読み込む際に、ストリームが途中で終了した場合（つまり、期待されるバイト数よりも少ないバイト数で `io.EOF` が発生した場合）に、そのエラーを `io.EOF` としてそのまま返していました。

しかし、`io.ReadFull` のセマンティクスでは、期待されるバイト数を読み込む前にストリームが終了した場合、それは「予期せぬEOF」として `io.ErrUnexpectedEOF` を返すのが適切です。`io.EOF` は、ストリームの終端に達し、それ以上読み込むデータがないことを意味しますが、`io.ReadFull` が期待するバイト数を読み込めなかった場合は、データが「切り詰められた」状態であり、これは通常、エラーとして扱われるべきです。

この不整合により、`gzip.Reader` は、不完全なgzipファイルや破損したgzipファイルを読み込んだ際に、単に `io.EOF` を返すだけで、データが途中で切り詰められたというより具体的なエラー情報を利用者に伝えることができませんでした。これにより、アプリケーション側で問題の原因を特定するのが困難になる可能性がありました。

## 前提知識の解説

### `io.Reader` インターフェース

Go言語における `io.Reader` は、データを読み込むための基本的なインターフェースです。
```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```
`Read` メソッドは、`p` に最大 `len(p)` バイトのデータを読み込み、読み込んだバイト数 `n` とエラー `err` を返します。データがもうない場合は `io.EOF` を返します。

### `io.ReadFull` 関数

`io.ReadFull` は、`io.Reader` から正確に指定されたバイト数を読み込むためのユーティリティ関数です。
```go
func ReadFull(r Reader, buf []byte) (n int, err error)
```
この関数は、`len(buf)` バイトを `r` から `buf` に読み込もうとします。
- 成功した場合: `n == len(buf)` かつ `err == nil`。
- `len(buf)` バイトを読み込む前に `io.EOF` に達した場合: `n < len(buf)` かつ `err == io.ErrUnexpectedEOF`。
- 読み込みを開始する前に `io.EOF` に達した場合（つまり、`n == 0`）: `err == io.EOF`。

### `io.EOF` と `io.ErrUnexpectedEOF`

- **`io.EOF`**: End Of File。ストリームの終端に達し、それ以上読み込むデータがないことを示します。これは通常、エラーではなく、正常な終了条件として扱われます。`io.ReadFull` の文脈では、読み込みを試みる前にストリームが空であった場合に返されます。
- **`io.ErrUnexpectedEOF`**: Unexpected End Of File。期待されるデータ量の一部しか読み込めなかった場合に発生するエラーです。これは、データが途中で切り詰められたり、破損していることを示唆します。`io.ReadFull` の文脈では、`len(buf)` バイトを読み込む前にストリームが終了した場合に返されます。

### GZIP ファイルフォーマットの概要

GZIPファイルは、RFC 1952 で定義されている圧縮ファイル形式です。基本的な構造は以下のようになります。
- **ヘッダ (Header)**: マジックナンバー、圧縮方式、フラグ、タイムスタンプ、OS情報などを含む。
- **圧縮データ (Compressed data)**: DEFLATEアルゴリズムで圧縮されたデータ。
- **フッタ (Footer)**: CRC32チェックサムと元のデータのサイズ（ISIZE）を含む。

`gzip.Reader` は、これらのセクションを順に読み込み、ヘッダの解析、データの解凍、フッタの検証を行います。各セクションの読み込みには、固定長のバイト数を読み込む必要があるため、`io.ReadFull` が頻繁に使用されます。

## 技術的詳細

このコミットの核心は、`gzip.Reader` 内で `io.ReadFull` を使用して固定長のデータを読み込む際に、`io.EOF` が返された場合の処理を修正することです。

元のコードでは、`io.ReadFull` が `io.EOF` を返した場合、そのエラーをそのまま `gzip.Reader` の呼び出し元に伝播させていました。しかし、`gzip` ヘッダやフッタ、または特定のフィールドは固定長であるため、これらの部分を読み込む途中で `io.EOF` が発生するということは、ストリームが期待される長さよりも短いことを意味します。これは `io.EOF` ではなく、`io.ErrUnexpectedEOF` として報告されるべき「異常な」状態です。

修正では、`io.ReadFull` の結果として `io.EOF` が返された場合に、それを `io.ErrUnexpectedEOF` にラップして返すように変更されています。これにより、`gzip.Reader` の利用者は、ストリームが途中で切れていることを明確に区別できるようになります。

ただし、`readHeader` メソッドの冒頭でヘッダの最初の10バイトを読み込む部分については、例外的な処理が追加されています。RFC 1952 のセクション 2.2 では、gzipファイルが「一連のメンバー（圧縮データセット）」で構成されると述べていますが、「一連」が「1つ以上」を意味するのか「0個以上」を意味するのかが不明確です。Goの実装では「0個以上」と解釈し、空のストリーム（つまり、gzipヘッダすら存在しないストリーム）を `io.EOF` として正常に処理することを許容しています。このため、`readHeader` の最初の `io.ReadFull` で `io.EOF` が発生した場合は、そのまま `io.EOF` を返すようにしています。これは、複数のgzipメンバーが連結されたファイルにおいて、最後のメンバーの後にデータがない場合に `io.EOF` を返すという、より一般的な `io.Reader` の振る舞いに合致させるためです。

## コアとなるコードの変更箇所

変更は主に `src/compress/gzip/gunzip.go` に集中しており、テストファイル `src/compress/gzip/gunzip_test.go` に新しいテストケースが追加されています。

### `src/compress/gzip/gunzip.go` の変更点

1.  **`read2()` メソッド**:
    ```diff
    func (z *Reader) read2() (uint32, error) {
    	_, err := io.ReadFull(z.r, z.buf[0:2])
    	if err != nil {
    +		if err == io.EOF {
    +			err = io.ErrUnexpectedEOF
    +		}
    		return 0, err
    	}
    	return uint32(z.buf[0]) | uint32(z.buf[1])<<8, nil
    }
    ```
    2バイトを読み込む `read2` 関数で、`io.ReadFull` が `io.EOF` を返した場合に `io.ErrUnexpectedEOF` に変換しています。

2.  **`readHeader()` メソッド**:
    ```diff
    func (z *Reader) readHeader(save bool) error {
    	_, err := io.ReadFull(z.r, z.buf[0:10])
    	if err != nil {
    +		// RFC1952 section 2.2 says the following:
    +		//	A gzip file consists of a series of "members" (compressed data sets).
    +		//
    +		// Other than this, the specification does not clarify whether a
    +		// "series" is defined as "one or more" or "zero or more". To err on the
    +		// side of caution, Go interprets this to mean "zero or more".
    +		// Thus, it is okay to return io.EOF here.
    		return err
    	}
    	if z.buf[0] != gzipID1 || z.buf[1] != gzipID2 || z.buf[2] != gzipDeflate {
    		// ...
    	}
    	// ...
    	if flags&_FNAME != 0 {
    		// ...
    		data := make([]byte, n)
    		if _, err = io.ReadFull(z.r, data); err != nil {
    +			if err == io.EOF {
    +				err = io.ErrUnexpectedEOF
    +			}
    			return err
    		}
    		// ...
    	}
    	// ...
    }
    ```
    ヘッダの最初の10バイトを読み込む部分では、`io.EOF` をそのまま返します（コメントで理由が説明されています）。しかし、ファイル名などの可変長フィールドの長さを読み込んだ後にそのデータを読み込む `io.ReadFull` では、`io.EOF` を `io.ErrUnexpectedEOF` に変換しています。

3.  **`Read()` メソッド**:
    ```diff
    func (z *Reader) Read(p []byte) (n int, err error) {
    	// ...
    	// Finished file; check checksum + size.
    	if _, err := io.ReadFull(z.r, z.buf[0:8]); err != nil {
    +		if err == io.EOF {
    +			err = io.ErrUnexpectedEOF
    +		}
    		z.err = err
    		return 0, err
    	}
    	// ...
    }
    ```
    `Read` メソッドの最後で、CRC32チェックサムと元のデータサイズ（ISIZE）を含むフッタの8バイトを読み込む際にも、`io.EOF` を `io.ErrUnexpectedEOF` に変換しています。

### `src/compress/gzip/gunzip_test.go` の変更点

1.  **`TestNilStream()`**:
    空のストリームを `gzip.Reader` に渡した場合のテストです。GoがRFC1952の「一連のメンバー」を「0個以上」と解釈しているため、`NewReader(bytes.NewReader(nil))` は `io.EOF` を返すことが期待されます。

2.  **`TestTruncatedStreams()`**:
    意図的に途中で切り詰められたgzipデータストリームを生成し、様々な長さで `gzip.Reader` に渡してテストします。このテストでは、`io.ErrUnexpectedEOF` が適切に返されることを検証しています。特に、`flate.ReadError` のような下位レイヤーのエラーも `io.ErrUnexpectedEOF` に変換されることを確認しています。

## コアとなるコードの解説

このコミットの主要な変更は、`gzip.Reader` の内部で `io.ReadFull` が使用されている複数の箇所で、返されたエラーが `io.EOF` であった場合に、それを `io.ErrUnexpectedEOF` に変換するロジックを追加したことです。

- **`read2()`**: GZIPヘッダ内の特定のフィールド（例えば `XFL` や `OS` フィールドの一部、または `XLEN`）は2バイト固定長です。これらを読み込む際に `io.ReadFull` が `io.EOF` を返した場合、それは2バイトを読み込む前にストリームが終了したことを意味するため、`io.ErrUnexpectedEOF` が適切です。

- **`readHeader()`**: GZIPヘッダの最初の10バイトを読み込む部分では、空のストリームを許容するというGoの解釈に基づき、`io.EOF` はそのまま返されます。しかし、ヘッダ内のフラグによって存在する可能性のある可変長フィールド（例えばファイル名 `FNAME`）の長さを読み込んだ後、そのデータ自体を読み込む際には、そのデータが期待される長さよりも短い場合は `io.ErrUnexpectedEOF` を返すように修正されています。これは、ファイル名が途中で切れているという異常な状態を正確に報告するためです。

- **`Read()`**: GZIPファイルのフッタには、CRC32チェックサムと元のデータサイズ（ISIZE）がそれぞれ4バイトずつ、合計8バイト含まれています。`Read` メソッドの終盤でこれらの8バイトを読み込む際に `io.ReadFull` が `io.EOF` を返した場合、それはフッタが不完全であることを意味するため、`io.ErrUnexpectedEOF` に変換されます。

これらの変更により、`gzip.Reader` は、不完全なgzipストリームに対してより正確なエラー情報を提供するようになり、利用者は `io.ErrUnexpectedEOF` を捕捉することで、データが途中で切り詰められたことを明確に認識し、適切なエラーハンドリングを行うことができるようになります。

追加されたテストケースは、この新しいエラーハンドリングの振る舞いを検証するために重要です。`TestNilStream` は、空の入力に対する `gzip.Reader` の期待される振る舞い（`io.EOF`）を確認し、`TestTruncatedStreams` は、様々な長さで切り詰められた入力に対して `io.ErrUnexpectedEOF` が適切に返されることを網羅的にテストしています。

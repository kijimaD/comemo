# [インデックス 28028] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における数値リテラルの文字列表現の初期化方法を最適化するものです。具体的には、エラーメッセージでリテラルが必要になる場合に備えて、すべてのレキシングされた数値に対して「literal 2.01」のような文字列を事前に生成するのではなく、構文エラーが発生した場合にのみこの文字列を遅延初期化するように変更しています。これにより、不要なメモリ割り当てと処理時間を削減し、コンパイラのパフォーマンスを向上させています。

## 変更の背景

Goコンパイラは、ソースコードを解析する過程で、数値リテラル（例: `123`, `3.14`, `0xFF`）を識別します。以前の実装では、これらのリテラルがレキシング（字句解析）されるたびに、その文字列表現（例: `"literal 123"`, `"literal 3.14"`）を`litbuf`というバッファに格納していました。これは、将来的に構文エラーが発生し、そのエラーメッセージに特定のリテラルの情報を含める必要がある場合に備えての処理でした。

しかし、実際にはほとんどのリテラルはエラーメッセージで参照されることなく、コンパイルが正常に完了します。そのため、すべてのリテラルに対して無条件に文字列表現の文字列を生成し、メモリを割り当てることは、多くのケースで無駄な処理となっていました。この不要な文字列生成とメモリ割り当ては、コンパイラの実行速度とメモリ使用量に悪影響を与えていました。

このコミットは、この非効率性を解消するために導入されました。コミットメッセージに含まれるベンチマーク結果（`allocs/op`の`delta`が負の値）は、この変更が実際にメモリ割り当てを削減し、コンパイラのパフォーマンスを向上させたことを示しています。

## 前提知識の解説

### Goコンパイラの字句解析（Lexing）と構文解析（Parsing）

*   **字句解析（Lexing/Scanning）**: ソースコードを最小単位の「トークン」に分割するプロセスです。例えば、`var x = 10;`というコードは、`var`（キーワード）、`x`（識別子）、`=`（演算子）、`10`（数値リテラル）、`;`（区切り文字）といったトークンに分割されます。このコミットでは、`src/cmd/compile/internal/gc/lex.go`が字句解析器（レキサー）の一部を担当しています。
*   **構文解析（Parsing）**: 字句解析器によって生成されたトークンのストリームを受け取り、Go言語の文法規則に従って、それらが有効な構造を形成しているかを確認し、抽象構文木（AST）を構築するプロセスです。このコミットでは、`src/cmd/compile/internal/gc/parser.go`が構文解析器（パーサー）の一部を担当しています。
*   **`litbuf`**: "literal buffer"の略で、レキサーが識別したリテラル（数値、文字列など）の文字列表現を一時的に保持するために使用されるグローバル変数（またはパッケージレベル変数）です。エラーメッセージなどでリテラルの詳細が必要な場合に参照されます。

### 遅延初期化（Lazy Initialization）

遅延初期化とは、オブジェクトの生成、値の計算、リソースの割り当てなどの処理を、それが実際に必要になるまで遅らせる最適化手法です。このコミットでは、`litbuf`にリテラルの文字列表現を格納する処理を、構文エラーが発生してその情報が実際にエラーメッセージで必要になるまで遅らせています。これにより、エラーが発生しない通常のコンパイルパスでは、この文字列生成のコストが完全に回避されます。

### メモリ割り当て（Memory Allocation）

プログラムが実行時にメモリを要求し、オペレーティングシステムやランタイムからメモリブロックを受け取るプロセスです。文字列の生成は、多くの場合、新しいメモリ領域の割り当てを伴います。不要な文字列生成を避けることで、メモリ割り当ての回数と量が減少し、ガベージコレクションの負荷が軽減され、結果としてプログラムのパフォーマンスが向上します。コミットメッセージの`allocs/op`は、1操作あたりのメモリ割り当て回数を示しており、この値が減少することはメモリ効率の改善を意味します。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの字句解析フェーズと構文解析フェーズ間の`litbuf`変数の利用方法を変更することにあります。

以前の実装では、`lex.go`内の`number`関数（数値リテラルを処理する部分）が、数値リテラルを識別した直後に、その文字列表現（例: `"literal 123"`）を`litbuf`に格納していました。これは、`LLITERAL`トークンが生成された際に、そのリテラルの詳細が`litbuf`を通じて利用可能であることを保証するためでした。

変更後、`lex.go`の`number`関数は、数値リテラルを識別しても`litbuf`を初期化せず、単に空文字列`""`を代入するだけになりました。リテラルの実際の文字列表現は、`lexbuf.String()`（レキサーが現在処理しているトークンの生文字列を返す関数と推測される）から取得できますが、この処理は行われません。

代わりに、`parser.go`内の`syntax_error`関数（構文エラーが発生した際に呼び出される関数）が変更されました。この関数は、エラーが発生したトークンが`LLITERAL`（リテラル）である場合、`litbuf`が空文字列であるかどうかをチェックします。もし`litbuf`が空であれば、その時点で初めて`lexbuf.String()`を使用してリテラルの文字列表現を取得し、`"literal " + lexbuf.String()`という形式で`litbuf`を初期化します。

このアプローチにより、構文エラーが発生しない限り、数値リテラルの文字列表現を生成するための文字列結合とメモリ割り当てが完全にスキップされます。エラーが発生した場合にのみ、そのコストが支払われるため、平均的なコンパイル時間とメモリ使用量が改善されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/lex.go` の変更

`func (l *lexer) number(c rune)` は、レキサーが数値リテラルを処理する際の主要な関数です。
変更前:
`litbuf = "literal " + str`
この行では、数値リテラル（`str`変数に格納されている）が識別されるとすぐに、その文字列表現に`"literal "`というプレフィックスを付けて`litbuf`に代入していました。これは、エラーが発生するかどうかにかかわらず、常に文字列の結合と新しい文字列のメモリ割り当てを行っていました。

変更後:
`litbuf = "" // lazily initialized in (*parser).syntax_error`
この行では、`litbuf`に空文字列`""`を代入するだけになりました。これにより、数値リテラルがレキシングされた時点では、不要な文字列生成とメモリ割り当ては行われません。コメント`// lazily initialized in (*parser).syntax_error`は、この変数が`parser.go`の`syntax_error`関数で遅延初期化されることを明示しています。

### `src/cmd/compile/internal/gc/parser.go` の変更

`func (p *parser) syntax_error(msg string)` は、構文エラーが発生した際に呼び出される関数です。
`case LLITERAL:` のブロックは、エラーが発生したトークンがリテラルである場合の処理を定義しています。
変更前:
このブロックでは、`litbuf`が既にリテラルの文字列表現を含んでいることを前提として、それを`tok`変数に代入していました。

変更後:
```go
		if litbuf == "" {
			litbuf = "literal " + lexbuf.String()
		}
		tok = litbuf
```
`if litbuf == ""` という条件が追加されました。これは、`litbuf`がまだ初期化されていない（つまり、`lex.go`で空文字列が代入されたままの状態）場合にのみ、以下の処理を実行することを意味します。
`litbuf = "literal " + lexbuf.String()`: ここで初めて、`lexbuf.String()`（現在のトークンの生文字列）からリテラルの文字列表現を取得し、`"literal "`プレフィックスを付けて`litbuf`に代入します。この処理は、エラーが発生し、かつそのエラーメッセージでリテラルの詳細が必要な場合にのみ実行されます。
その後、`tok = litbuf`によって、初期化された（または既に初期化されていた）`litbuf`の値が`tok`変数に代入され、エラーメッセージの生成に使用されます。

この二つの変更により、`litbuf`の初期化が「必要になった時（構文エラー発生時）」に「一度だけ」行われるようになり、コンパイラの全体的な効率が向上しました。

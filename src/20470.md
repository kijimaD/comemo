# [インデックス 20470] ファイルの概要

このコミットは、Goランタイムにおけるマップ（`map`）のイテレーション順序のランダム性を改善するためのものです。具体的には、マップのイテレータがバケット内の要素を走査する際に、常にバケット内でのランダムな開始オフセットを使用するように変更することで、イテレーション順序の予測可能性をさらに低減し、意図しない順序依存性によるバグを防ぐことを目的としています。

## 変更の背景

Go言語のマップ（`map`）は、その設計上、イテレーション（要素の走査）の順序が保証されていません。これは、開発者がマップの順序に依存するコードを書くことを防ぎ、将来のGoのバージョンでマップの実装が変更されても、既存のコードが壊れないようにするための重要な特性です。もしイテレーション順序が予測可能であると、開発者はその順序に依存するコードを書いてしまい、Goのバージョンアップ時に予期せぬバグが発生する可能性があります。

このコミットの背景には、Go issue #8688 があります。このissueでは、特定の条件下でマップのイテレーション順序が予測可能になってしまうケースが報告されていました。特に、マップのバケット（ハッシュテーブルの内部構造）が小さい場合や、特定の要素の追加・削除パターンにおいて、イテレーションの開始オフセットが常に同じになってしまう可能性がありました。これにより、マップのイテレーション順序が「ランダムではない」と認識され、開発者が誤って順序に依存してしまうリスクがありました。

このコミットは、このような予測可能性を排除し、マップのイテレーション順序が常に十分にランダムであることを保証するために導入されました。これにより、Goのマップの「順序は保証されない」という特性がより堅牢になり、開発者が安全にマップを使用できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとデータ構造に関する知識が必要です。

*   **Goのマップ（`map`）の内部構造**: Goのマップはハッシュテーブルとして実装されています。内部的には、キーのハッシュ値に基づいて要素が「バケット」と呼ばれる領域に格納されます。各バケットは複数のキー/値ペアを保持できます。マップのサイズが大きくなると、バケットの数が増えたり、既存のバケットが分割されたり（成長）します。
*   **マップのイテレーション順序のランダム化**: Goのマップは、イテレーションのたびに異なる順序で要素を返すように設計されています。これは、イテレータが開始するバケットと、そのバケット内の開始オフセットをランダムに選択することで実現されます。これにより、開発者がマップの順序に依存するコードを書くことを防ぎます。
*   **`fastrand1()`**: Goランタイム内部で使用される高速な擬似乱数生成関数です。これは暗号学的に安全である必要はなく、単にイテレーション順序のランダム化など、予測可能性を低減するために使用されます。
*   **`bucketCnt`**: マップの各バケットが保持できるキー/値ペアの最大数を示す定数です。このコミット以前は単に `8` と定義されていましたが、このコミットで `bucketCntBits` を用いたビットシフト演算 `1 << bucketCntBits` で定義されるようになりました。
*   **`hmap` 構造体**: Goのマップのランタイム表現です。マップのバケットの数（`B`フィールド）や、オーバーフローバケットへのポインタなどを保持します。
*   **`hiter` 構造体**: マップのイテレータのランタイム表現です。イテレーションの開始バケット（`startBucket`）や、バケット内の開始オフセット（`offset`）などの状態を保持します。

## 技術的詳細

このコミットの主要な変更点は、`src/runtime/hashmap.go` 内の `mapiterinit` 関数におけるイテレータの開始位置（`startBucket` と `offset`）の決定ロジックです。

変更前は、`h.B` (バケット数の対数、つまり `2^h.B` がバケット数) の値に応じて、`startBucket` と `offset` の決定方法が異なっていました。

*   `h.B == 0` の場合（マップが非常に小さい、または空の場合）：
    *   `startBucket` は `0` に固定。
    *   `offset` は `fastrand1()` の下位ビットを使ってランダムに決定。
*   `h.B <= 31` の場合：
    *   `startBucket` は `fastrand1()` を使ってランダムに決定。
    *   `offset` は `0` に固定。
*   `h.B > 31` の場合：
    *   `startBucket` は2つの `fastrand1()` の結果を組み合わせてランダムに決定。
    *   `offset` は `0` に固定。

このロジックの問題点は、`offset` が `0` に固定されるケースがあったことです。特に、`h.B > 0` の場合、バケット内の開始オフセットが常に `0` になってしまい、バケット内の要素の順序が予測可能になる可能性がありました。Goのマップは、バケット内の要素の順序も保証されないため、この挙動は意図しない順序依存性を生む可能性がありました。

このコミットでは、この問題を解決するために、`mapiterinit` 関数内の開始位置決定ロジックを統一し、常にバケット内でのランダムなオフセットを使用するように変更しました。

新しいロジックでは、単一の乱数 `r` を生成し、その乱数から `startBucket` と `offset` の両方を導出します。

1.  `r := uintptr(fastrand1())` で最初の乱数を生成します。
2.  もし `h.B` が `31 - bucketCntBits` より大きい場合（つまり、バケット数が非常に多く、`startBucket` を表現するために32ビット以上の乱数が必要な場合）、`r` に `uintptr(fastrand1()) << 31` を加算して、より多くのビットを持つ乱数を生成します。これは、`startBucket` の範囲が広すぎる場合に、より広い範囲でランダム性を確保するためです。
3.  `it.startBucket = r & (uintptr(1)<<h.B - 1)`: 生成された乱数 `r` の下位 `h.B` ビットを使って `startBucket` を決定します。これにより、`0` から `2^h.B - 1` の範囲でランダムなバケットが選択されます。
4.  `it.offset = uint8(r >> h.B & (bucketCnt - 1))`: 生成された乱数 `r` の上位ビット（`h.B` ビット目から）を使って `offset` を決定します。`bucketCnt - 1` とのビットAND演算により、`0` から `bucketCnt - 1` の範囲でランダムなバケット内オフセットが選択されます。

この変更により、`startBucket` と `offset` の両方が常にランダムな値から導出されるようになり、マップのイテレーション順序の予測可能性がさらに低減されました。

また、`bucketCnt` の定義が `const bucketCnt = 8` から `const (bucketCntBits = 3; bucketCnt = 1 << bucketCntBits)` に変更されました。これは、`bucketCnt` が `2^N` の形式であることを明示し、`offset` の計算でビットシフトを使用する際に、より意図が明確になるようにするためです。`1 << bucketCntBits` は `2^3 = 8` となり、値自体は変わりません。

`src/runtime/map_test.go` では、マップのイテレーション順序がランダムであることを確認するためのテストが強化されました。特に、`TestMapIterOrder` 関数内で、マップの要素数 `n` ごとにイテレーションを `1000` 回繰り返すループが追加され、各イテレーションで異なる順序が得られることをより厳密にチェックするようになりました。これにより、変更が意図通りに機能し、イテレーション順序の予測可能性が排除されたことを検証しています。

## コアとなるコードの解説

### `src/runtime/hashmap.go` の変更

1.  **`bucketCnt` の定義変更**:
    ```go
    -	bucketCnt = 8
    +	bucketCntBits = 3
    +	bucketCnt     = 1 << bucketCntBits
    ```
    `bucketCnt` は引き続き `8` ですが、`bucketCntBits` を導入し、`1 << bucketCntBits` とすることで、`bucketCnt` が2のべき乗であることを明示し、ビット演算との親和性を高めています。これは、`offset` の計算でビットシフトを使用する際に、コードの意図をより明確にするための変更です。

2.  **`hiter` 構造体の `i` フィールドのインデント修正**:
    ```go
    -	i	    uint8
    +	i           uint8
    ```
    これは機能的な変更ではなく、単なるコードフォーマットの修正です。

3.  **`mapiterinit` 関数の開始位置決定ロジックの変更**:
    この部分がこのコミットの最も重要な変更点です。
    変更前は `switch` 文を使って `h.B` の値に応じて異なるロジックを適用していましたが、変更後は単一の統一されたロジックになりました。

    ```go
    -	switch {
    -	case h.B == 0:
    -		it.startBucket = 0
    -		it.offset = uint8(fastrand1()) & (bucketCnt - 1)
    -	case h.B <= 31:
    -		it.startBucket = uintptr(fastrand1()) & (uintptr(1)<<h.B-1)
    -		it.offset = 0
    -	default:
    -		it.startBucket = (uintptr(fastrand1()) + uintptr(fastrand1())<<31) & (uintptr(1)<<h.B-1)
    -		it.offset = 0
    -	}
    +	r := uintptr(fastrand1())
    +	if h.B > 31-bucketCntBits {
    +		r += uintptr(fastrand1()) << 31
    +	}
    +	it.startBucket = r & (uintptr(1)<<h.B - 1)
    +	it.offset = uint8(r >> h.B & (bucketCnt - 1))
    ```
    *   **乱数 `r` の生成**: まず `r := uintptr(fastrand1())` で最初の乱数を取得します。
    *   **広範囲の乱数生成（必要に応じて）**: `if h.B > 31-bucketCntBits` の条件は、マップのバケット数が非常に多く、`startBucket` を表現するために32ビット以上の乱数が必要な場合に真となります。この場合、`r += uintptr(fastrand1()) << 31` を実行し、さらに別の乱数を31ビット左シフトして `r` に加算することで、`r` のビット数を増やし、より広範囲の乱数を生成します。これにより、非常に大きなマップでも `startBucket` のランダム性が十分に確保されます。
    *   **`startBucket` の決定**: `it.startBucket = r & (uintptr(1)<<h.B - 1)`
        `uintptr(1)<<h.B - 1` は、`h.B` ビットがすべて1であるマスクを生成します（例: `h.B=3` なら `0b111`）。`r` とこのマスクのビットAND演算を行うことで、`r` の下位 `h.B` ビットのみが `startBucket` として使用されます。これにより、`0` から `2^h.B - 1` の範囲でランダムな開始バケットが選択されます。
    *   **`offset` の決定**: `it.offset = uint8(r >> h.B & (bucketCnt - 1))`
        `r >> h.B` は、`r` を `h.B` ビット右シフトします。これにより、`startBucket` の決定に使用されたビットの次のビットからが `offset` の決定に使用されます。
        `(bucketCnt - 1)` は、`bucketCnt` が `8` の場合 `7` (`0b111`) となります。このマスクとのビットAND演算により、右シフトされた `r` の下位 `bucketCntBits` ビット（この場合は3ビット）のみが `offset` として使用されます。これにより、`0` から `bucketCnt - 1` の範囲でランダムなバケット内オフセットが選択されます。

    この新しいロジックにより、`startBucket` と `offset` の両方が単一または複数のランダムな値から導出され、常にランダムな開始位置が保証されるようになりました。これにより、マップのイテレーション順序の予測可能性が完全に排除されます。

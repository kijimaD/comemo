# [インデックス 24783] ファイルの概要

このコミットは、Goランタイムのアセンブリコードファイル `src/runtime/asm_amd64.s` に変更を加えるものです。このファイルは、amd64アーキテクチャにおけるGoランタイムの低レベルな処理、特にスタック管理やゴルーチン切り替え、システムコールなどのアセンブリ実装を含んでいます。具体的には、スタックバリアに関連する処理が修正されています。

## コミット

Goランタイムにおいて、スタックバリアのアンワインド処理が正しく同期していることを確認するためのチェックを追加します。これにより、スタックバリア配列の位置と実際のスタック上の位置がずれることによる、デバッグが困難なクラッシュを防ぎます。

## 変更の背景

Goのガベージコレクション（GC）は、実行中のプログラムのスタックをスキャンし、ポインタを更新する際に「スタックバリア」というメカニズムを利用します。スタックバリアは、GCがスタックを安全に操作できるように、特定の関数呼び出しの前後で実行を一時停止させるためのフックのようなものです。

コミット前の実装では、スタックバリアのスタブ（アセンブリコードで書かれた短い関数）が、ゴルーチン（G）のスタックバリア配列から次のスタックバリア情報を盲目的にアンワインドしていました。ここで問題となるのは、スタックバリア配列内の位置が、実際のスタック上の位置と何らかのバグによって同期が取れなくなった場合です。

もし同期が失われると、スタックバリアスタブは誤ったリターンアドレス（PC: Program Counter）にジャンプしてしまう可能性があります。これにより、プログラムは予期せぬ場所に制御を移し、非常にデバッグが困難なクラッシュを引き起こすことになります。このようなクラッシュは、スタックの状態が壊れているため、通常のデバッグツールでは原因特定が極めて困難です。このコミットは、この潜在的な問題を検出し、早期にパニックさせることで、デバッグを容易にすることを目的としています。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する低レベルなシステムです。ガベージコレクション、ゴルーチン管理、スケジューリング、メモリ割り当て、システムコールインターフェースなど、Go言語の並行処理とメモリ安全性を実現するための多くの重要な機能を提供します。アセンブリコードは、これらの機能の中でも特にパフォーマンスが要求される部分や、OSとの直接的なインターフェース部分で利用されます。

### スタックバリア (Stack Barrier)

Goのガベージコレクションは、並行GC（Concurrent GC）を採用しており、プログラムの実行と並行してGCが動作します。この際、GCがスタックをスキャンしてポインタを更新するタイミングで、プログラムがスタックを書き換えてしまうと、GCが不正なポインタを読み込んだり、誤った場所にポインタを更新したりする可能性があります。

スタックバリアは、このような競合状態を防ぐためのメカニズムです。特定の関数呼び出しのプロローグ（関数開始時）やエピローグ（関数終了時）にスタックバリアが挿入され、GCがスタックをスキャンする際に、これらのバリアを検出して安全に処理を進めます。具体的には、GCがスタックをスキャンしている間、スタックバリアに到達したゴルーチンは一時停止し、GCが安全にスタックを操作できるようにします。

各ゴルーチン（G）は、自身のスタックバリアの状態を管理するための `g_stkbar` という配列と、現在のスタックバリアの位置を示す `g_stkbarPos` というインデックスを持っています。

### スタックアンワインド (Stack Unwind)

スタックアンワインドとは、関数呼び出しの連鎖を逆方向にたどり、スタックフレームを解放していく処理のことです。関数がリターンする際、その関数のスタックフレームが解放され、実行は呼び出し元のアドレス（リターンアドレス）に戻ります。例外処理やパニック発生時にも、特定のスタックフレームまで遡るためにスタックアンワインドが行われます。

### G (Goroutine)

GはGoランタイムにおけるゴルーチンの内部表現です。各ゴルーチンは軽量な実行スレッドであり、独自のスタックを持っています。Goランタイムは、これらのGをOSのスレッド（M: Machine）に多重化して実行します。

### saved LR (Link Register)

LR（Link Register）は、ARMアーキテクチャなどで関数呼び出し元のアドレス（リターンアドレス）を保持するために使われるレジスタです。amd64アーキテクチャでは、通常、リターンアドレスは関数呼び出し時にスタックにプッシュされます。このコミットメッセージにおける `saved LR` は、スタックバリアが介入する前の、本来のリターンアドレスが保存されているスタック上の位置を指します。スタックバリアは、本来のリターンアドレスを一時的に保存し、自身の処理が完了した後にそのアドレスにジャンプすることで、関数の実行を継続させます。

## 技術的詳細

このコミットは、Goランタイムのスタックバリア処理における堅牢性を向上させるものです。

GoのGCがスタックをスキャンする際、スタックバリアはゴルーチンのスタック上に配置され、GCが安全にポインタを更新できるようにします。スタックバリアがヒットすると、`runtime·stackBarrier` というアセンブリ関数が実行されます。この関数は、ゴルーチン構造体 `g` 内の `g_stkbar` 配列と `g_stkbarPos` を利用して、次にアンワインドすべきスタックバリアの情報を取得します。

コミット前の問題は、`runtime·stackBarrier` が `g_stkbarPos` に基づいて `g_stkbar` から情報を取得する際に、その情報が現在のスタックの状態と一致しているかを検証していなかった点にあります。もし何らかのランタイムバグにより `g_stkbarPos` が誤った値を指していた場合、`runtime·stackBarrier` は誤った `saved LR` を取得し、そのアドレスにジャンプしてしまう可能性がありました。これは、プログラムが全く関係のないメモリ領域に飛び、予測不能なクラッシュを引き起こす原因となります。

このコミットでは、この問題を解決するために、`runtime·stackBarrier` のアセンブリコードに以下のチェックを追加します。

1.  `g_stkbar` 配列から、現在処理中のスタックバリアに対応する `stkbar_savedLRPtr` の値（本来のリターンアドレスが保存されているスタック上のアドレス）を読み込みます。
2.  読み込んだ `stkbar_savedLRPtr` の値と、現在のスタックポインタ `SP` の値を比較します。
3.  もし両者が一致しない場合、それはスタックバリア配列の位置と実際のスタック上の位置が同期していないことを意味します。この場合、`JNE 2(PC)` 命令によって2バイト先にジャンプし、その後の `MOVL $0, 0` 命令を実行します。`MOVL $0, 0` は無効なメモリアドレスへの書き込みを試みるため、セグメンテーション違反（Segmentation Fault）を引き起こし、プログラムをパニックさせます。

この変更により、スタックバリアの同期が失われた場合に、デバッグが困難なランダムなクラッシュではなく、明確なパニック（セグメンテーション違反）が発生するようになります。これにより、開発者は問題の根本原因をより迅速に特定し、修正することが可能になります。

## コアとなるコードの変更箇所

`src/runtime/asm_amd64.s` ファイルの `runtime·stackBarrier` 関数に以下の変更が加えられました。

```diff
--- a/src/runtime/asm_amd64.s
+++ b/src/runtime/asm_amd64.s
@@ -346,7 +346,12 @@ TEXT runtime·stackBarrier(SB),NOSPLIT,$0
 	MOVQ	(g_stkbar+slice_array)(CX), DX
 	MOVQ	g_stkbarPos(CX), BX
 	IMULQ	$stkbar__size, BX	// Too big for SIB.
+	MOVQ	stkbar_savedLRPtr(DX)(BX*1), R8
 	MOVQ	stkbar_savedLRVal(DX)(BX*1), BX
+	// Assert that we're popping the right saved LR.
+	CMPQ	R8, SP
+	JNE	2(PC)
+	MOVL	$0, 0
 	// Record that this stack barrier was hit.
 	ADDQ	$1, g_stkbarPos(CX)
 	// Jump to the original return PC.
```

## コアとなるコードの解説

変更されたアセンブリコードの各行を詳細に解説します。

```assembly
	MOVQ	(g_stkbar+slice_array)(CX), DX
	MOVQ	g_stkbarPos(CX), BX
	IMULQ	$stkbar__size, BX	// Too big for SIB.
```
これらの行は、現在のゴルーチン `g` (レジスタ `CX` に格納されている) からスタックバリア配列 `g_stkbar` のベースアドレスを `DX` に、現在のスタックバリアのインデックス `g_stkbarPos` を `BX` にロードし、`BX` をスタックバリア構造体のサイズ `stkbar__size` で乗算してオフセットを計算しています。これにより、`DX` と `BX` を使って `g_stkbar` 配列内の特定のスタックバリアエントリにアクセスできるようになります。

```assembly
	MOVQ	stkbar_savedLRPtr(DX)(BX*1), R8
```
この行が追加された主要な変更点の一つです。
`stkbar_savedLRPtr` は、スタックバリア構造体内のフィールドで、本来のリターンアドレスがスタック上のどこに保存されているかを示すポインタ（アドレス）を保持しています。
`stkbar_savedLRPtr(DX)(BX*1)` は、`DX` (g_stkbarのベースアドレス) と `BX` (計算されたオフセット) を使って、現在のスタックバリアエントリから `stkbar_savedLRPtr` の値を読み込み、それをレジスタ `R8` に格納します。`R8` には、スタックバリアが介入する前の、本来のリターンアドレスがスタックに積まれていた場所のアドレスが格納されます。

```assembly
	MOVQ	stkbar_savedLRVal(DX)(BX*1), BX
```
この行は以前から存在しており、`stkbar_savedLRVal` (スタックバリア構造体内のフィールドで、本来のリターンアドレスそのもの) の値を読み込み、レジスタ `BX` に格納します。この `BX` の値が、スタックバリア処理の最後にジャンプするアドレスとなります。

```assembly
	// Assert that we're popping the right saved LR.
	CMPQ	R8, SP
	JNE	2(PC)
	MOVL	$0, 0
```
ここが今回のコミットの核心部分です。
- `CMPQ R8, SP`: レジスタ `R8` に格納されている `stkbar_savedLRPtr` の値（本来のリターンアドレスが保存されているスタック上のアドレス）と、現在のスタックポインタ `SP` の値を比較します。
    - `SP` は、現在のスタックのトップを指しています。スタックバリアが正しく機能している場合、`stkbar_savedLRPtr` が指すアドレスは、スタックバリアが処理される直前の `SP` の値と一致するか、非常に近い値であるはずです。この比較は、スタックバリアがスタック上の正しい位置でアンワインドされているかを確認するためのものです。
- `JNE 2(PC)`: もし `R8` と `SP` が一致しない場合（`JNE` は "Jump if Not Equal"）、プログラムカウンタ（PC）を現在の命令から2バイト先にジャンプさせます。
- `MOVL $0, 0`: `JNE` が実行された場合、この命令が実行されます。これは、アドレス `0` に値 `0` を書き込もうとする命令です。アドレス `0` は通常、オペレーティングシステムによって保護されたメモリ領域であり、ユーザープログラムがアクセスすることはできません。したがって、この命令はセグメンテーション違反（Segmentation Fault）を引き起こし、Goランタイムはパニックしてクラッシュします。

このチェックにより、スタックバリアのアンワインド処理がスタック上の正しい位置で行われていることを保証し、もし同期が失われている場合は、早期に明確なエラー（パニック）を発生させることで、デバッグの困難なランダムなクラッシュを防ぎます。

```assembly
	// Record that this stack barrier was hit.
	ADDQ	$1, g_stkbarPos(CX)
	// Jump to the original return PC.
```
これらの行は以前から存在しており、スタックバリアがヒットしたことを記録するために `g_stkbarPos` をインクリメントし、最後に `BX` に格納されている本来のリターンアドレスにジャンプして、関数の実行を継続させます。

このコミットは、Goランタイムのスタックバリア処理における堅牢性を向上させるものです。

GoのGCがスタックをスキャンする際、スタックバリアはゴルーチンのスタック上に配置され、GCが安全にポインタを更新できるようにします。スタックバリアがヒットすると、`runtime·stackBarrier` というアセンブリ関数が実行されます。この関数は、ゴルーチン構造体 `g` 内の `g_stkbar` 配列と `g_stkbarPos` を利用して、次にアンワインドすべきスタックバリアの情報を取得します。

コミット前の問題は、`runtime·stackBarrier` が `g_stkbarPos` に基づいて `g_stkbar` から情報を取得する際に、その情報が現在のスタックの状態と一致しているかを検証していなかった点にあります。もし何らかのランタイムバグにより `g_stkbarPos` が誤った値を指していた場合、`runtime·stackBarrier` は誤った `saved LR` を取得し、そのアドレスにジャンプしてしまう可能性がありました。これは、プログラムが全く関係のないメモリ領域に飛び、予測不能なクラッシュを引き起こす原因となります。

このコミットでは、この問題を解決するために、`runtime·stackBarrier` のアセンブリコードに以下のチェックを追加します。

1.  `g_stkbar` 配列から、現在処理中のスタックバリアに対応する `stkbar_savedLRPtr` の値（本来のリターンアドレスが保存されているスタック上のアドレス）を読み込みます。
2.  読み込んだ `stkbar_savedLRPtr` の値と、現在のスタックポインタ `SP` の値を比較します。
3.  もし両者が一致しない場合、それはスタックバリア配列の位置と実際のスタック上の位置が同期していないことを意味します。この場合、`JNE 2(PC)` 命令によって2バイト先にジャンプし、その後の `MOVL $0, 0` 命令を実行します。`MOVL $0, 0` は無効なメモリアドレスへの書き込みを試みるため、セグメンテーション違反（Segmentation Fault）を引き起こし、プログラムをパニックさせます。

この変更により、スタックバリアの同期が失われた場合に、デバッグが困難なランダムなクラッシュではなく、明確なパニック（セグメンテーション違反）が発生するようになります。これにより、開発者は問題の根本原因をより迅速に特定し、修正することが可能になります。

## コアとなるコードの変更箇所

`src/runtime/asm_amd64.s` ファイルの `runtime·stackBarrier` 関数に以下の変更が加えられました。

```diff
--- a/src/runtime/asm_amd64.s
+++ b/src/runtime/asm_amd64.s
@@ -346,7 +346,12 @@ TEXT runtime·stackBarrier(SB),NOSPLIT,$0
 	MOVQ	(g_stkbar+slice_array)(CX), DX
 	MOVQ	g_stkbarPos(CX), BX
 	IMULQ	$stkbar__size, BX	// Too big for SIB.
+	MOVQ	stkbar_savedLRPtr(DX)(BX*1), R8
 	MOVQ	stkbar_savedLRVal(DX)(BX*1), BX
+	// Assert that we're popping the right saved LR.
+	CMPQ	R8, SP
+	JNE	2(PC)
+	MOVL	$0, 0
 	// Record that this stack barrier was hit.
 	ADDQ	$1, g_stkbarPos(CX)
 	// Jump to the original return PC.
```

## コアとなるコードの解説

変更されたアセンブリコードの各行を詳細に解説します。

```assembly
	MOVQ	(g_stkbar+slice_array)(CX), DX
	MOVQ	g_stkbarPos(CX), BX
	IMULQ	$stkbar__size, BX	// Too big for SIB.
```
これらの行は、現在のゴルーチン `g` (レジスタ `CX` に格納されている) からスタックバリア配列 `g_stkbar` のベースアドレスを `DX` に、現在のスタックバリアのインデックス `g_stkbarPos` を `BX` にロードし、`BX` をスタックバリア構造体のサイズ `stkbar__size` で乗算してオフセットを計算しています。これにより、`DX` と `BX` を使って `g_stkbar` 配列内の特定のスタックバリアエントリにアクセスできるようになります。

```assembly
	MOVQ	stkbar_savedLRPtr(DX)(BX*1), R8
```
この行が追加された主要な変更点の一つです。
`stkbar_savedLRPtr` は、スタックバリア構造体内のフィールドで、本来のリターンアドレスがスタック上のどこに保存されているかを示すポインタ（アドレス）を保持しています。
`stkbar_savedLRPtr(DX)(BX*1)` は、`DX` (g_stkbarのベースアドレス) と `BX` (計算されたオフセット) を使って、現在のスタックバリアエントリから `stkbar_savedLRPtr` の値を読み込み、それをレジスタ `R8` に格納します。`R8` には、スタックバリアが介入する前の、本来のリターンアドレスがスタックに積まれていた場所のアドレスが格納されます。

```assembly
	MOVQ	stkbar_savedLRVal(DX)(BX*1), BX
```
この行は以前から存在しており、`stkbar_savedLRVal` (スタックバリア構造体内のフィールドで、本来のリターンアドレスそのもの) の値を読み込み、レジスタ `BX` に格納します。この `BX` の値が、スタックバリア処理の最後にジャンプするアドレスとなります。

```assembly
	// Assert that we're popping the right saved LR.
	CMPQ	R8, SP
	JNE	2(PC)
	MOVL	$0, 0
```
ここが今回のコミットの核心部分です。
- `CMPQ R8, SP`: レジスタ `R8` に格納されている `stkbar_savedLRPtr` の値（本来のリターンアドレスが保存されているスタック上のアドレス）と、現在のスタックポインタ `SP` の値を比較します。
    - `SP` は、現在のスタックのトップを指しています。スタックバリアが正しく機能している場合、`stkbar_savedLRPtr` が指すアドレスは、スタックバリアが処理される直前の `SP` の値と一致するか、非常に近い値であるはずです。この比較は、スタックバリアがスタック上の正しい位置でアンワインドされているかを確認するためのものです。
- `JNE 2(PC)`: もし `R8` と `SP` が一致しない場合（`JNE` は "Jump if Not Equal"）、プログラムカウンタ（PC）を現在の命令から2バイト先にジャンプさせます。
- `MOVL $0, 0`: `JNE` が実行された場合、この命令が実行されます。これは、アドレス `0` に値 `0` を書き込もうとする命令です。アドレス `0` は通常、オペレーティングシステムによって保護されたメモリ領域であり、ユーザープログラムがアクセスすることはできません。したがって、この命令はセグメンテーション違反（Segmentation Fault）を引き起こし、Goランタイムはパニックしてクラッシュします。

このチェックにより、スタックバリアのアンワインド処理がスタック上の正しい位置で行われていることを保証し、もし同期が失われている場合は、早期に明確なエラー（パニック）を発生させることで、デバッグの困難なランダムなクラッシュを防ぎます。

```assembly
	// Record that this stack barrier was hit.
	ADDQ	$1, g_stkbarPos(CX)
	// Jump to the original return PC.
```
これらの行は以前から存在しており、スタックバリアがヒットしたことを記録するために `g_stkbarPos` をインクリメントし、最後に `BX` に格納されている本来のリターンアドレスにジャンプして、関数の実行を継続させます。

# [インデックス 27764] ファイルの概要

このコミットは、Goコンパイラの内部コードジェネレータ（`cmd/compile/internal/gc`）にIBM System/390x (s390x) アーキテクチャのサポートを追加するものです。特に、レジスタ最適化（`regopt`）において、`From3`フィールドを持つ命令が定数を表す場合に利用できるように変更されています。これは、s390xのストレージ間命令がデータの長さを`From3`フィールドに格納するというアーキテクチャ特性に対応するために必要です。

## 元コミット内容

`cmd/compile/internal/gc: s390xサポートの追加`

`regopt`において、`From3`フィールドを持つ命令が定数を表す限り使用できるようにします。これは、s390xのストレージ間命令がデータの長さを`From3`に配置するため必要です。

## 変更の背景

この変更の背景には、Go言語がより多くのアーキテクチャをサポートするための継続的な取り組みがあります。s390xはIBMのメインフレームコンピュータで使用される64ビット命令セットアーキテクチャであり、エンタープライズ環境で広く利用されています。Goコンパイラがs390xをサポートすることで、Goアプリケーションをメインフレーム環境でネイティブに実行できるようになり、その利用範囲が拡大します。

特に、s390xアーキテクチャの特定の命令セット特性、すなわち「ストレージ間命令（storage-to-storage instructions）」がデータの長さを命令の`From3`フィールドにエンコードするという点が、既存のGoコンパイラのレジスタ最適化（`regopt`）ロジックと衝突していました。`regopt`は通常、`From3`フィールドが使用されている命令を処理しないように設計されていましたが、s390xのこの特性に対応するためには、`From3`が定数である場合に限り、`regopt`がその命令を処理できるようにする必要がありました。これにより、s390x固有の命令を効率的に利用しつつ、コンパイラの最適化パスを適切に機能させることが可能になります。

## 前提知識の解説

### Goコンパイラ (`cmd/compile/internal/gc`)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。`cmd/compile/internal/gc`は、その主要な部分であり、フロントエンド（構文解析、型チェック）からバックエンド（コード生成、最適化）までを担当します。

*   **`gc` (Go Compiler)**: Go言語の公式コンパイラ。
*   **`cgen.go`**: コード生成（Code Generation）に関連する処理を扱うファイル。特定のGoの操作をターゲットアーキテクチャの機械語命令に変換するロジックが含まれます。
*   **`gsubr.go`**: Goのサブルーチン（Subroutines）や共通のユーティリティ関数に関連する処理を扱うファイル。アーキテクチャ固有の挙動を抽象化するヘルパー関数などが含まれます。
*   **`pgen.go`**: プログラム生成（Program Generation）に関連する処理を扱うファイル。スタックフレームの管理や自動変数の割り当てなど、実行可能コードの構造を構築する部分です。
*   **`reg.go`**: レジスタ割り当て（Register Allocation）と最適化（Optimization）に関連する処理を扱うファイル。`regopt`関数は、生成された中間コードに対してレジスタの使用を最適化し、効率的な機械語を生成します。
*   **`walk.go`**: 抽象構文木（AST）の走査（Walk）と変換を行うファイル。Goのソースコードから生成されたASTを、コード生成に適した形に変換する様々なパスが含まれます。

### s390xアーキテクチャ

s390xは、IBM Zシリーズのメインフレームコンピュータで使用される64ビット命令セットアーキテクチャです。その特徴として以下が挙げられます。

*   **メインフレーム環境**: 高い信頼性、可用性、保守性（RAS）が求められるエンタープライズシステムで利用されます。
*   **ストレージ間命令 (Storage-to-Storage Instructions)**: s390xには、メモリ上の2つのオペランド間で直接データを操作する命令が多数存在します。これらの命令は、データのコピーや比較などを行う際に、レジスタを介さずに効率的に処理できるという利点があります。
*   **`From3`フィールド**: s390xの特定の命令フォーマットでは、命令のオペランドの一部として`From3`というフィールドが使用されます。コミットメッセージにあるように、ストレージ間命令ではこの`From3`フィールドが操作するデータの「長さ」を示す定数として使われることがあります。

### `obj.Prog`と`From3Type()`

Goコンパイラのバックエンドでは、`obj.Prog`という構造体がアセンブリ命令を表します。この構造体には、命令の種類（`As`）、オペランド（`From`, `To`, `From3`など）が含まれます。

*   **`obj.TYPE_NONE`**: オペランドが存在しないことを示すタイプ。
*   **`obj.TYPE_CONST`**: オペランドが定数であることを示すタイプ。
*   **`p.From3Type()`**: `obj.Prog`オブジェクトの`From3`フィールドのタイプを返すメソッド。

### レジスタ最適化 (`regopt`)

`regopt`は、Goコンパイラの重要な最適化パスの一つです。このパスは、中間表現（IR）を走査し、レジスタの使用を最適化することで、より高速で効率的な機械語コードを生成します。具体的には、頻繁にアクセスされる値をレジスタに保持したり、不要なメモリロード/ストアを排除したりします。

## 技術的詳細

このコミットの主要な技術的変更点は、s390xアーキテクチャの特性をGoコンパイラのレジスタ最適化パスに統合することです。

1.  **`regopt`の変更**:
    *   既存の`regopt`関数は、`From3`フィールドを持つ命令に対しては最適化を行わないように設計されていました。これは、`From3`が複雑なアドレス指定やレジスタを参照する場合に、レジスタ最適化のロジックが複雑になるのを避けるためです。
    *   しかし、s390xのストレージ間命令では、`From3`がデータの長さを表す「定数」として使用されます。この場合、`From3`はレジスタ割り当てや複雑なアドレス計算に影響を与えないため、`regopt`がこれらの命令を安全に処理できるようになります。
    *   コミットでは、`regopt`内のチェックを`p.From3Type() != obj.TYPE_NONE`から`p.From3Type() != obj.TYPE_NONE && p.From3Type() != obj.TYPE_CONST`に変更することで、`From3`が定数である命令は`regopt`の対象とすることを許可しています。これにより、s390xのストレージ間命令もレジスタ最適化の恩恵を受けられるようになります。

2.  **s390xのアーキテクチャファミリーへの追加**:
    *   Goコンパイラの多くの部分では、特定のアーキテクチャファミリー（例: `sys.AMD64`, `sys.ARM`, `sys.PPC64`など）に共通のコード生成ロジックや最適化を適用しています。
    *   このコミットでは、`cgen.go`, `gsubr.go`, `pgen.go`, `walk.go`内の複数の箇所で、`Ctxt.Arch.InFamily`や`Thearch.LinkArch.InFamily`といった関数呼び出しに`sys.S390X`が追加されています。これは、s390xがAMD64やPPC64などと同様に、PC相対アドレッシングを使用したり、特定のスタックアライメント要件を持ったり、`math.Sqrt`のような組み込み関数の最適化パスを共有したりすることを示しています。
    *   例えば、`gsubr.go`の`Ismem`関数では、AMD64やPPC64と同様にs390xもPC相対アドレッシングを使用するため、`OADDR`ノードがメモリ参照として扱われるように変更されています。

3.  **s390x固有の制約の追加**:
    *   `walk.go`の`walkrotate`関数には、s390x固有の回転命令の制約が追加されています。`if Thearch.LinkArch.Family == sys.S390X && w != 32 && w != 64 { return n }`というコードは、s390xが32ビットおよび64ビットの回転操作のみをサポートすることを示しており、それ以外のビット幅の回転はコンパイラが処理できないため、そのままノードを返す（最適化しない）ようにしています。

これらの変更により、Goコンパイラはs390xアーキテクチャの特性を正しく理解し、効率的な機械語コードを生成できるようになります。

## コアとなるコードの解説

### `reg.go`の変更

`regopt`関数は、アセンブリ命令（`obj.Prog`）を走査し、レジスタ割り当てを最適化します。変更前のコードでは、`p.From3Type() != obj.TYPE_NONE`という条件で、`From3`フィールドを持つ命令は一律に最適化の対象外とされていました。これは、`From3`がレジスタや複雑なメモリオペランドを参照する場合に、`regopt`のロジックが正しく機能しない可能性があったためです。

しかし、s390xアーキテクチャのストレージ間命令では、`From3`フィールドがデータの「長さ」を表す定数として使用されます。この定数はレジスタ割り当てには影響しないため、このような命令も最適化の対象とすることが可能です。

変更後の`if p.From3Type() != obj.TYPE_NONE && p.From3Type() != obj.TYPE_CONST`という条件は、「`From3`フィールドが存在し、かつそれが定数ではない場合」にのみ最適化をスキップするように修正されています。これにより、`From3`が定数であるs390xの命令は`regopt`によって適切に処理され、より効率的なコードが生成されるようになります。

### その他のファイルの変更

*   **`cgen.go` (`cgen_wb`, `bgenx`)**:
    *   `cgen_wb`はライトバリア（write barrier）のコード生成に関連し、`bgenx`はブール値のコード生成に関連します。これらの関数で`sys.S390X`が`InFamily`チェックに追加されたことで、s390xもAMD64やARMなどの他のアーキテクチャと同様に、特定の最適化されたコード生成パスを利用できるようになります。
*   **`gsubr.go` (`Ismem`, `Gbranch`, `Naddr`)**:
    *   `Ismem`関数では、`OADDR`ノード（アドレス参照）がメモリ参照として扱われるアーキテクチャに`sys.S390X`が追加されました。これは、s390xがAMD64と同様にPC相対アドレッシングを使用するため、アドレスが直接メモリを指す場合に効率的な処理が可能になることを意味します。
    *   `Gbranch`関数では、分岐命令の最適化に関連する`InFamily`チェックに`sys.S390X`が追加され、特定のアーキテクチャファミリーに共通の分岐最適化が適用されるようになりました。
    *   `Naddr`関数では、アドレスノードの処理において、特定のアーキテクチャファミリーに共通の幅（width）設定ロジックに`sys.S390X`が追加されました。
*   **`pgen.go` (`allocauto`)**:
    *   `allocauto`関数は自動変数（スタック上の変数）のメモリ割り当てに関連します。`sys.S390X`が`InFamily`チェックに追加されたことで、s390xもMIPS64やARMなどと同様に、スタックアライメントの要件を満たすようにスタックサイズが調整されるようになります。
*   **`walk.go` (`math.Sqrt`最適化, `walkrotate`)**:
    *   `math.Sqrt`の最適化パスに`sys.S390X`が追加されたことで、s390xでも`math.Sqrt`関数が組み込みの平方根命令に置き換えられ、パフォーマンスが向上する可能性があります。
    *   `walkrotate`関数には、s390x固有の回転命令の制約が追加されました。s390xは32ビットと64ビットの回転のみをサポートするため、それ以外のビット幅の回転操作はコンパイラが直接処理せず、より汎用的なコード生成パスにフォールバックするようにしています。

これらの変更は、s390xアーキテクチャの特性をGoコンパイラの各ステージ（コード生成、最適化、AST変換など）に適切に組み込むことで、s390x上でのGoプログラムの正確性と効率性を確保するために行われています。

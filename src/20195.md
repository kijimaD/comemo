# [インデックス 20195] ファイルの概要

このコミットは、Goコンパイラの`cmd/5g`（ARMアーキテクチャ向け）と`cmd/8g`（x86 32-bitアーキテクチャ向け）において、小さな構造体（struct）と配列（array）の「レジスタ化（registerize）」を実装するものです。これは、既に`cmd/6g`（AMD64アーキテクチャ向け）では長らく行われていた最適化であり、パフォーマンス向上を目的としています。

## 元コミット内容

`cmd/5g`および`cmd/8g`コンパイラにおいて、小さな構造体と配列をレジスタ化する変更が加えられました。これは、`cmd/6g`では以前から実装されていた最適化です。
`5g`においては、`[3]uintptr`のような型のローカル変数`t`に対して`t[0]`のようにアドレスを取得しようとすると、`t`自体のメモリアドレスが取得されてしまうという問題（Issue 8125）が依然として存在します。
このコミットはIssue 8123を修正します。

## 変更の背景

Goコンパイラは、異なるCPUアーキテクチャ向けにコードを生成するために、それぞれ専用のバックエンドを持っています。このコミットが対象としている`cmd/5g`はARMアーキテクチャ向け、`cmd/8g`はx86 32-bitアーキテクチャ向けのコンパイラです。一方、`cmd/6g`はAMD64（x86-64）アーキテクチャ向けのコンパイラです。

コンパイラ最適化の一つに「レジスタ割り当て（Register Allocation）」、またはこのコミットで言及されている「レジスタ化（Registerization）」があります。これは、プログラムの変数や一時的な値を、CPUの高速なレジスタに割り当てることで、メモリへのアクセス回数を減らし、プログラムの実行速度を向上させる重要な最適化です。メモリへのアクセスはCPUレジスタへのアクセスに比べて非常に遅いため、可能な限りレジスタを活用することがパフォーマンス向上に直結します。

`cmd/6g`では既にこの最適化が適用されており、小さな構造体や配列がレジスタに割り当てられることで効率的なコードが生成されていました。しかし、`cmd/5g`と`cmd/8g`ではこの最適化が不足しており、同等のパフォーマンス改善が期待されていました。このコミットは、これらのコンパイラにも同様のレジスタ化の恩恵をもたらすことを目的としています。

コミットメッセージで言及されているIssue 8123は、このレジスタ化の不足に関連する問題であり、このコミットによって修正されます。また、Issue 8125は、`5g`コンパイラにおける配列のアドレッシングに関する既存の問題であり、このコミットでは解決されないものの、レジスタ化の文脈でその複雑性が指摘されています。

## 前提知識の解説

### 1. Goコンパイラのアーキテクチャ別バックエンド (`5g`, `8g`, `6g`)

Go言語の初期のコンパイラは、ターゲットとするCPUアーキテクチャごとに異なる名前を持っていました。これらはGoコンパイラ（`gc`）ツールチェーンの一部でした。

*   **`5g`**: ARMアーキテクチャ（例: ARMv5, ARMv6, ARMv7）向けのGoコンパイラ。
*   **`8g`**: Intel 386（x86 32-bit）アーキテクチャ向けのGoコンパイラ。
*   **`6g`**: AMD64（x86-64）アーキテクチャ向けのGoコンパイラ。

これらのコンパイラは、Go 1.5以降でGo自身で再実装され、現在では`go build`コマンドを通じて透過的に利用されます。しかし、このコミットが作成された2014年当時は、これらのC言語で書かれたバックエンドが活発に開発されていました。

### 2. レジスタ割り当て（Register Allocation / Registerization）

レジスタ割り当ては、コンパイラ最適化の最も重要な側面の一つです。CPUには、非常に高速にアクセスできる少数のレジスタがあります。これに対し、メインメモリ（RAM）へのアクセスははるかに遅いです。レジスタ割り当ての目的は、プログラムの実行中に頻繁にアクセスされる変数や中間結果を、可能な限りレジスタに保持することです。

*   **利点**:
    *   **高速化**: メモリアクセスを減らすことで、命令の実行速度が大幅に向上します。
    *   **コードサイズの削減**: メモリへのロード/ストア命令が減ることで、生成される機械語コードのサイズが小さくなる場合があります。
*   **課題**:
    *   **レジスタ数の制限**: CPUのレジスタ数は限られているため、すべての変数をレジスタに保持することはできません。
    *   **スピル（Spilling）**: レジスタが不足した場合、一部の変数を一時的にメモリに退避させる必要があります。これをスピルと呼び、パフォーマンスが低下する要因となります。
*   **「小さな構造体と配列のレジスタ化」**: 通常、構造体や配列は複数の要素から構成され、メモリ上に連続して配置されます。しかし、サイズが非常に小さい（例えば、数個の要素しかない）構造体や配列の場合、それらを丸ごとレジスタに収めることが可能になる場合があります。これにより、個々の要素にアクセスするたびにメモリを参照するのではなく、レジスタ内で直接操作できるようになり、効率が向上します。

### 3. `cgen.c` ファイル

`src/cmd/5g/cgen.c` および `src/cmd/8g/cgen.c` は、Goコンパイラのバックエンドにおけるコード生成（code generation）を担当するC言語のソースファイルです。`cgen`は「code generation」の略であり、抽象構文木（AST）や中間表現（IR）から、ターゲットアーキテクチャの機械語命令を生成するロジックが含まれています。このファイル内の`componentgen`関数は、複合型（構造体や配列など）のコンポーネント（個々のフィールドや要素）を処理する際に呼び出される重要な関数です。

## 技術的詳細

このコミットの核心は、`componentgen`関数における構造体と配列の処理ロジックの変更です。

### 変更点概要

1.  **`TARRAY` (配列) の処理**:
    *   スライス（`isslice(t)`）はこれまで通り処理されます。
    *   新たに、サイズが小さく（`t->bound > 0 && t->bound <= 3`、つまり要素数が1〜3個）、かつ「fat type」ではない（`!isfat(t->type)`）配列がレジスタ化の対象となります。
        *   「fat type」とは、ポインタと長さなど、複数のワードで構成される型（例: スライス、文字列、インターフェース）を指します。これらの型はレジスタに直接収めるのが難しいため、レジスタ化の対象外とされます。
    *   レジスタ化の対象となる配列の場合、`componentgen`は`goto yes`に分岐し、配列の各要素を個別に処理してレジスタに割り当てようとします。具体的には、`nodl.xoffset`と`nodr.xoffset`を`t->type->width`（要素のサイズ）ずつインクリメントしながら、`gmove`（汎用的な移動命令）や`clearslim`（ゼロクリア命令）を使って要素をレジスタ間で移動またはクリアします。

2.  **`TSTRUCT` (構造体) の処理**:
    *   新たに、小さな構造体で、かつ「fat type」ではないフィールドのみを持つ構造体がレジスタ化の対象となります。
    *   構造体のフィールド数をカウントし（`fldcount`）、フィールド数が0より大きく4以下（`fldcount == 0 || fldcount > 4` の条件で`goto no`に分岐しない）の場合にレジスタ化の対象となります。
    *   各フィールドが「fat type」でないことも確認されます（`isfat(t->type)`）。
    *   レジスタ化の対象となる構造体の場合、`componentgen`は`goto yes`に分岐し、構造体の各フィールドを個別に処理してレジスタに割り当てようとします。配列と同様に、`nodl.xoffset`と`nodr.xoffset`を`t->width`（フィールドのサイズ）ずつインクリメントしながら、`gmove`や`clearslim`を使ってフィールドをレジスタ間で移動またはクリアします。
    *   `funarg`（関数引数）として渡される構造体の場合、オフセットの調整が行われます。

### `isfat`関数の役割

`isfat`関数は、型が「fat type」であるかどうかを判定します。Go言語におけるfat typeの例としては、スライス（ポインタと長さ）、文字列（ポインタと長さ）、インターフェース（型情報とデータポインタ）などがあります。これらの型は単一のレジスタに収まらないため、レジスタ化の対象から除外されます。このコミットでは、レジスタ化の対象を「fat type」ではない小さな構造体や配列に限定することで、レジスタ割り当ての複雑性を管理しつつ、パフォーマンス向上を図っています。

### Issue 8125との関連

コミットメッセージで言及されているIssue 8125は、`5g`コンパイラにおける配列のアドレッシングに関する問題です。具体的には、`[3]uintptr`のような固定サイズの配列`t`に対して`t[0]`のように要素にアクセスしようとすると、コンパイラが配列の先頭要素のアドレスではなく、配列`t`自体のメモリアドレスを取得してしまうという問題です。これは、配列のレジスタ化をさらに複雑にする要因であり、このコミットでは解決されていませんが、その存在が認識されていることを示しています。レジスタ化された配列の場合、要素へのアクセスはレジスタ内で行われるため、この問題の影響は軽減される可能性がありますが、完全に解消されるわけではありません。

## コアとなるコードの解説

`componentgen`関数は、コンパイラが複合型（構造体や配列）の要素をどのように扱うかを決定する中心的なロジックを含んでいます。この関数は、左辺値（`nl`）と右辺値（`nr`）のノードを受け取り、それらの型に基づいて適切なコード生成を行います。

### `TARRAY` (配列) の処理

変更前は、スライスではない配列は一律で`goto no`に分岐し、レジスタ化の対象外とされていました。
変更後は、以下の条件が追加されました。

```c
		t = nl->type;

		// Slices are ok.
		if(isslice(t))
			break;
		// Small arrays are ok.
		if(t->bound > 0 && t->bound <= 3 && !isfat(t->type))
			break;

		goto no;
```

*   `isslice(t)`: 型がスライスであるかをチェックします。スライスはポインタと長さを持つため、レジスタ化の対象外ですが、既存の処理フローを維持します。
*   `t->bound > 0 && t->bound <= 3`: 配列の要素数が1から3個であることをチェックします。これは「小さな配列」の定義です。
*   `!isfat(t->type)`: 配列の要素の型が「fat type」ではないことをチェックします。これにより、要素自体がレジスタに収まる単純な型であることを保証します。

これらの条件を満たす小さな配列の場合、`break`によって`goto no`への分岐が回避され、後続のレジスタ化ロジックに進みます。

レジスタ化ロジックは以下の部分です。

```c
		t = nl->type;
		if(!isslice(t)) { // スライスではない配列の場合
			nodl.type = t->type; // 左辺値ノードの型を配列の要素型に設定
			nodr.type = nodl.type; // 右辺値ノードの型も同様に設定
			for(fldcount=0; fldcount < t->bound; fldcount++) { // 配列の各要素をループ
				if(nr == N) // 右辺値がない（クリア操作など）場合
					clearslim(&nodl); // 左辺値ノードをクリア
				else // 右辺値がある場合
					gmove(&nodr, &nodl); // 右辺値ノードから左辺値ノードへ移動
				nodl.xoffset += t->type->width; // 次の要素へオフセットを進める
				nodr.xoffset += t->type->width; // 次の要素へオフセットを進める
			}
			goto yes; // 処理完了
		}
```
このコードは、配列の各要素を個別に処理し、レジスタ間でデータを移動またはクリアすることで、配列全体をレジスタに「展開」するような動作をします。

### `TSTRUCT` (構造体) の処理

変更前は、構造体は`componentgen`の初期段階で`goto no`に分岐し、レジスタ化の対象外とされていました。
変更後は、以下の条件が追加されました。

```c
	case TSTRUCT:
		// Small structs with non-fat types are ok.
		// Zero-sized structs are treated separately elsewhere.
		fldcount = 0;
		for(t=nl->type->type; t; t=t->down) {
			if(isfat(t->type))
				goto no;
			if(t->etype != TFIELD)
				fatal("componentgen: not a TFIELD: %lT", t);
			fldcount++;
		}
		if(fldcount == 0 || fldcount > 4)
			goto no;

		break;
```

*   `fldcount = 0; for(t=nl->type->type; t; t=t->down) { ... fldcount++; }`: 構造体のフィールド数をカウントします。
*   `if(isfat(t->type)) goto no;`: 各フィールドの型が「fat type」ではないことをチェックします。一つでもfat typeのフィールドがあれば、構造体全体はレジスタ化の対象外となります。
*   `if(fldcount == 0 || fldcount > 4) goto no;`: フィールド数が0個（ゼロサイズ構造体は別途処理されるため）または4個を超える構造体はレジスタ化の対象外とします。これは「小さな構造体」の定義です。

これらの条件を満たす小さな構造体の場合、`break`によって`goto no`への分岐が回避され、後続のレジスタ化ロジックに進みます。

レジスタ化ロジックは以下の部分です。

```c
	case TSTRUCT:
		if(nl->op == ONAME)
			gvardef(nl); // 変数定義を生成
		loffset = nodl.xoffset; // 左辺値ノードのオフセットを保存
		roffset = nodr.xoffset; // 右辺値ノードのオフセットを保存
		// funarg structs may not begin at offset zero.
		if(nl->type->etype == TSTRUCT && nl->type->funarg && nl->type->type)
			loffset -= nl->type->type->width; // 関数引数構造体のオフセット調整
		if(nr != N && nr->type->etype == TSTRUCT && nr->type->funarg && nr->type->type)
			roffset -= nr->type->type->width; // 関数引数構造体のオフセット調整

		for(t=nl->type->type; t; t=t->down) { // 構造体の各フィールドをループ
			nodl.xoffset = loffset + t->width; // 左辺値ノードのオフセットをフィールドの幅だけ進める
			nodl.type = t->type; // 左辺値ノードの型をフィールドの型に設定

			if(nr == N) // 右辺値がない（クリア操作など）場合
				clearslim(&nodl); // 左辺値ノードをクリア
			else { // 右辺値がある場合
				nodr.xoffset = roffset + t->width; // 右辺値ノードのオフセットをフィールドの幅だけ進める
				nodr.type = nodl.type; // 右辺値ノードの型を左辺値ノードの型に設定
				gmove(&nodr, &nodl); // 右辺値ノードから左辺値ノードへ移動
			}
		}
		goto yes; // 処理完了
```
このコードは、構造体の各フィールドを個別に処理し、レジスタ間でデータを移動またはクリアすることで、構造体全体をレジスタに「展開」するような動作をします。関数引数として渡される構造体の場合、オフセットの調整が必要になることがあります。

これらの変更により、`cmd/5g`と`cmd/8g`は、`cmd/6g`と同様に、小さな構造体や配列をより効率的にレジスタに割り当て、結果として生成されるコードのパフォーマンスを向上させることが可能になりました。

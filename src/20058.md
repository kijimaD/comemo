# [インデックス 20058] ファイルの概要

このコミットは、Go言語のリンカーである`liblink`における、Power64アーキテクチャ向けのコード生成の修正に関するものです。具体的には、特定の`MOVD`アセンブリ命令のパターンを`ADD`命令に書き換えることで、スタック分割プロローグの不具合を修正しています。これにより、Power64上でのGoプログラムのスタック管理の正確性と効率性が向上します。

## 変更の背景

このコミットは、Go言語がPower64アーキテクチャへの対応を進める中で発見された、コード生成の不具合を修正するために行われました。特に、Goのランタイムが関数呼び出し時にスタックを管理するために使用する「スタック分割プロローグ」において、`MOVD $con(Ra), Rb`という形式のアセンブリ命令が正しく機能しない、または非効率であるという問題がありました。

PowerPC（Power64）アーキテクチャにおいて、`MOVD`は一般的なデータ移動命令ではありません。`$con(Ra)`という形式は、レジスタ`Ra`に定数`$con`を加算したアドレスからデータをロードする、あるいはそのアドレスを計算するという意図で使われることがあります。しかし、この特定の文脈（スタックポインタの計算など）では、直接`ADD`命令を使用して`$con`と`Ra`を加算し、結果を`Rb`に格納する方が、より適切かつ効率的なアセンブリコードとなります。

この不具合は、Goの軽量なゴルーチンが動的にスタックを拡張・縮小するメカニズム（スタック分割）に影響を与え、Power64環境でのプログラムの安定性やパフォーマンスに問題を引き起こす可能性がありました。そのため、リンカー（`liblink`）が生成するアセンブリコードを修正し、この問題を解決する必要がありました。

## 前提知識の解説

### 1. Go言語の`liblink`

`liblink`は、Go言語のツールチェインの内部コンポーネントであり、主にリンカーに関連する機能を提供します。Goのコンパイラ、アセンブラ、リンカーが共通して使用する内部フラグやデータオブジェクト構造を定義しています。これはGoのビルドシステムの中核をなす部分であり、Goプログラムが実行可能なバイナリに変換される過程で重要な役割を果たします。一般のGo開発者が直接操作するライブラリではありません。

### 2. Go言語のスタック管理とスタック分割（Stack Split）

Go言語のゴルーチンは非常に軽量であり、数百万ものゴルーチンを同時に実行できる設計になっています。これを可能にする重要なメカニズムの一つが、動的なスタック管理です。

*   **スタックの動的拡張・縮小**: ゴルーチンは非常に小さなスタック（初期値は数KB）で開始し、関数呼び出しによってスタックが必要になると、自動的にスタックを拡張します。不要になったスタック領域は縮小されることもあります。
*   **セグメントスタック（Go 1.4以前）**: このコミットが作成された2014年時点では、Goは「セグメントスタック」という方式を採用していました。これは、スタックが不足すると新しいスタックセグメントを割り当て、それを既存のスタックに連結するというものでした。これにより、スタックは複数の不連続なメモリ領域にまたがることがありました。
*   **スタック分割プロローグ**: 各Go関数の冒頭には、スタックの残量をチェックし、必要に応じてスタックを拡張するためのコード（プロローグ）が挿入されます。この処理が「スタック分割プロローグ」と呼ばれます。スタックが不足している場合、ランタイムは新しいスタックセグメントを割り当て、現在のスタックの内容を新しいセグメントにコピーし、スタックポインタを更新します。このプロセスは、Goの効率的な並行処理を支える基盤技術です。

Go 1.4以降では、セグメントスタックの「ホットスプリット問題」（頻繁なスタック分割による性能劣化）を解決するため、「連続スタック」とスタックコピー方式に移行しましたが、このコミットはそれ以前の、または移行期のPower64アーキテクチャにおけるスタック管理の課題を扱っています。

### 3. PowerPC/Power64アーキテクチャとアセンブリ命令

PowerPCはIBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。Power64はその64ビット版です。

*   **レジスタ**: PowerPCアーキテクチャは、汎用レジスタ（GPRs）を多数持ち、これらを使用して演算やアドレス計算を行います。
*   **`MOVD`**: PowerPCアセンブリにおいて、`MOVD`という直接的な命令は標準ではありません。データ移動には`mr`（Move Register）や`li`（Load Immediate）などが使われます。`$con(Ra)`のような形式は、通常、`Ra`レジスタの値にオフセット`$con`を加算したメモリアドレスからのロード（`lwz`, `ld`など）や、そのアドレスを計算する際に用いられるアドレッシングモードを示唆します。
*   **`ADD`**: `ADD`命令は、2つのオペランドを加算し、結果をデスティネーションレジスタに格納する基本的な算術命令です。例えば、`add rD, rA, rB`は`rD = rA + rB`を意味し、`addi rD, rA, value`は`rD = rA + value`（即値加算）を意味します。

このコミットの文脈では、`MOVD $con(Ra), Rb`が、実際には`Ra`に`$con`を加算して`Rb`に格納する、つまりアドレス計算を行う意図で使われていたが、Power64の`liblink`がこれを適切に処理できていなかった、あるいは`ADD`命令の方がより直接的で効率的な表現である、という状況が考えられます。

## 技術的詳細

このコミットの核心は、`liblink`がPower64アーキテクチャ向けに生成するアセンブリコードの最適化と修正にあります。

問題となっていたのは、`MOVD $con(Ra), Rb`という形式の命令です。これは、`Ra`レジスタの値に定数`$con`を加算した結果を`Rb`レジスタに移動（または格納）するという意図で使われていました。しかし、PowerPCのアセンブリ命令セットにおいて、このような形式の`MOVD`は直接的な命令として存在しないか、あるいはリンカーがこれを特定の文脈で誤って解釈していました。特に、スタックポインタの計算など、アドレスのオフセットを扱う場面でこの問題が発生していました。

コミットは、この`MOVD $con(Ra), Rb`のパターンを、より直接的でPowerPCアーキテクチャに適合した`ADD $con, Ra, Rb`という命令に書き換えることで解決を図っています。

*   **`MOVD $con(Ra), Rb`**: これは、`Ra`レジスタの内容に`$con`（定数オフセット）を加算し、その結果を`Rb`レジスタに格納するという、実質的なアドレス計算の操作を意図していたと考えられます。しかし、PowerPCの命令セットでは、このような「レジスタ+オフセット」のアドレッシングモードを伴う`MOVD`は一般的ではなく、リンカーがこれを適切にアセンブリ命令に変換する際に問題が生じていた可能性があります。
*   **`ADD $con, Ra, Rb`**: これは、`Ra`レジスタの内容に即値`$con`を加算し、その結果を`Rb`レジスタに格納する、標準的な即値加算命令です。この命令は、まさに`Ra`に`$con`を加算して`Rb`に格納するという操作を直接的に表現しており、PowerPCアーキテクチャにおいて効率的に実行されます。

この書き換えにより、`liblink`はPower64上でスタック分割プロローグを生成する際に、より正確で効率的なアセンブリ命令を使用できるようになります。これにより、スタックポインタの計算が正しく行われ、ゴルーチンのスタック管理が安定し、結果としてGoプログラム全体の信頼性とパフォーマンスが向上します。

また、スタック分割プロローグ内の`CMP R4, R31`が`CMPU R31, R4`に変更されている点も重要です。
*   `CMP`は符号付き比較、`CMPU`は符号なし比較です。スタックサイズやアドレスは通常、符号なしの値として扱われるため、`CMPU`を使用することでより正確な比較が可能になります。
*   オペランドの順序が`R4, R31`から`R31, R4`に変更されているのは、PowerPCの比較命令のセマンティクスや、後続の条件分岐命令（`BLT`など）との整合性を考慮した変更である可能性があります。

さらに、`stacksplit`関数内の引数サイズチェックが`if(arg&3)`から`if(arg&7)`に変更されています。これは、スタックアライメントの要件が変更されたか、またはPower64アーキテクチャにおけるメモリ境界の制約が8バイト（64ビット）に厳しくなったことを示唆しています。これにより、スタックフレームのサイズが適切にアライメントされているかどうかのチェックが強化され、潜在的なアライメント違反によるクラッシュやパフォーマンス低下を防ぎます。

## コアとなるコードの解説

### 1. `progedit` 関数内の命令書き換えロジック

```c
+	if(p->from.type == D_CONST && p->from.reg != NREG) {
+		if(p->as == AMOVD && p->to.type == D_REG) {
+			p->as = AADD;
+			p->reg = p->from.reg;
+			p->from.reg = NREG;
+		} else
+			ctxt->diag("invalid instruction: %P", p);
+	}
```
このコードブロックは、`progedit`関数（プログラム命令を編集するリンカーの内部関数）に追加されました。
*   `p->from.type == D_CONST && p->from.reg != NREG`: これは、命令のソースオペランドが定数（`D_CONST`）であり、かつレジスタが指定されている（`NREG`ではない）場合をチェックしています。これは、`$con(Ra)`のような形式、つまり「レジスタ`Ra`に定数`$con`を加算した値」を意味するパターンを検出しています。
*   `p->as == AMOVD && p->to.type == D_REG`: 検出された命令が`MOVD`命令であり、かつデスティネーションオペランドがレジスタ（`D_REG`）である場合、つまり`MOVD $con(Ra), Rb`のパターンに合致する場合に処理を行います。
*   `p->as = AADD;`: `MOVD`命令を`ADD`命令（`AADD`）に書き換えます。
*   `p->reg = p->from.reg;`: `ADD`命令の第2オペランド（加算されるレジスタ）として、元の`MOVD`命令のソースオペランドのレジスタ（`Ra`）を設定します。
*   `p->from.reg = NREG;`: 元のソースオペランドのレジスタ指定を無効化します。これにより、`ADD $con, Ra, Rb`という形式が生成されます。
*   `ctxt->diag("invalid instruction: %P", p);`: 上記の条件に合致しないが、`D_CONST`と`NREG`の組み合わせを持つ不正な命令が検出された場合、診断メッセージを出力します。

このロジックにより、リンカーはPower64向けに`MOVD $con(Ra), Rb`と意図された命令を、より適切な`ADD $con, Ra, Rb`に自動的に変換するようになります。

### 2. `stacksplit` 関数内の変更

`stacksplit`関数は、Goのスタック分割ロジックの中核を担う部分です。

*   **不要なTODOコメントとリターン文の削除**:
    ```diff
    -	// TODO(minux)
    -	return p;
    ```
    これは開発中のコードで一時的に追加されていたもので、実際のスタック分割ロジックが実装されたため削除されました。

*   **比較命令の変更**:
    ```diff
    -		//	CMP	R4, R31
    +		//	CMPU	R31, R4
    		p = appendp(ctxt, p);\
    		p->as = ACMP;\
    		p->from.type = D_REG;\
    -		p->from.reg = 4;\
    +		p->from.reg = REGTMP;\
    		p->to.type = D_REG;\
    -		p->to.reg = REGTMP;\
    +		p->to.reg = 4;\
    ```
    コメント行の`CMP`が`CMPU`に変わっているのは、実際の命令もそれに合わせて変更されることを示唆しています。
    *   `p->as = ACMP;` の行は、元のコードでは`ACMP`（符号付き比較）が使われていましたが、コメントが`CMPU`に変わっていることから、この部分も最終的には`ACMPU`（符号なし比較）に修正されるべき意図があったか、あるいはPower64の特定のコンテキストでは`ACMP`が符号なしとして扱われるか、または後続の変更で修正されることを示唆しています。
    *   `p->from.reg = 4;` から `p->from.reg = REGTMP;` へ、そして `p->to.reg = REGTMP;` から `p->to.reg = 4;` への変更は、比較命令のオペランドの順序と使用するレジスタが入れ替わっていることを示しています。これは、PowerPCの比較命令のセマンティクスや、スタックガードの比較ロジックの正確性を確保するための調整です。`REGTMP`は一時レジスタを指します。

*   **スタックアライメントチェックの変更**:
    ```diff
    -	if(arg&3) // ????
    +	if(arg&7)
    		ctxt->diag("misaligned argument size in stack split: %d", arg);\
    ```
    `arg&3`は4バイトアライメント（下位2ビットが0であること）をチェックしていますが、`arg&7`は8バイトアライメント（下位3ビットが0であること）をチェックしています。これは、Power64アーキテクチャにおいて、スタックフレームのサイズが8バイト境界にアライメントされている必要があるという要件を反映しています。これにより、スタックの不適切なアライメントによる問題を防ぎます。

これらの変更は、Power64アーキテクチャ上でのGoランタイムのスタック管理をより堅牢かつ正確にするための重要な修正です。

## 変更の背景

このコミットは、Goコンパイラおよびリンカの初期開発段階における内部的なコードの整理と最適化の一環として行われました。特に、ARMアーキテクチャ向けのコード生成において、データ構造の冗長性を排除し、アドレスの表現方法をよりセマンティクスに合致させる必要がありました。

具体的には、`Addr`構造体と`Prog`構造体の間で「幅（width）」や「スケール（scale）」といった情報が重複して保持されていたため、これを`Prog`構造体の`reg`フィールドに一元化することで、コードの保守性と理解度を向上させることが目的です。

また、`ADATA`（データ定義）命令において、`D_ADDR`というアドレスタイプが使用されていましたが、これが実際には定数値を指す場合が多く、`D_CONST`で表現する方が適切であるという判断がなされました。`5l`リンカ側でも`D_ADDR`の特別なハンドリングが不要になったため、その処理を元に戻すことで、ツールチェーン全体の整合性を保ち、不必要な複雑さを排除しています。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイラおよびリンカの基本的な内部構造と、アセンブリ言語におけるアドレス指定モードに関する知識が必要です。

*   **Goツールチェーン**:
    *   **`5g`**: Go言語のARMアーキテクチャ向けコンパイラです。ソースコードをARMアセンブリコード（または中間表現）に変換する役割を担います。Goの初期のツールチェーンでは、各アーキテクチャ（例: `8g` for x86, `6g` for x86-64, `5g` for ARM）ごとにコンパイラが分かれていました。
    *   **`5l`**: Go言語のARMアーキテクチャ向けリンカです。`5g`によって生成されたオブジェクトファイルを結合し、実行可能なバイナリを生成します。
*   **`Prog`構造体**: Goコンパイラのバックエンドで、アセンブリ命令を抽象的に表現するための主要なデータ構造です。各`Prog`インスタンスは、オペコード（`as`）、ソースアドレス（`from`）、デスティネーションアドレス（`to`）、次の命令へのリンク（`link`）などの情報を含みます。
*   **`Addr`構造体**: `Prog`構造体内で、命令のオペランド（ソースやデスティネーション）のアドレスを表現するために使用されるデータ構造です。アドレスタイプ（`type`）、レジスタ（`reg`）、オフセット（`offset`）などの情報を含みます。
*   **アドレス指定モード (Addressing Modes)**: CPUがメモリ上のデータにアクセスする方法を定義します。
    *   **`D_ADDR`**: この文脈では、おそらく直接的なメモリアドレスを指すために使われていたタイプです。
    *   **`D_CONST`**: 定数値を表すアドレスタイプです。
    *   **`D_REG`**: レジスタを指すアドレスタイプです。
    *   **`D_OREG`**: オフセット付きレジスタ（例: `[R0 + offset]`）を指すアドレスタイプです。
*   **`ADATA`命令**: アセンブリ言語において、データセクションに定数データや初期化済みデータを定義するために使用される擬似命令です。

## 技術的詳細

このコミットの技術的な変更は、主に以下の2点に集約されます。

1.  **`Addr.scale`フィールドの廃止と`Prog.reg`フィールドへの機能統合**:
    *   以前の`Addr`構造体には`uchar scale; /* doubles as width in DATA op */`というフィールドが存在し、これが`ADATA`命令におけるデータの幅（サイズ）を表現するために使われていました。
    *   このコミットでは、`Addr.scale`フィールドが削除され、代わりに`Prog`構造体の既存の`char reg;`フィールドが「`// doubles as width in DATA op`」というコメントと共に、この幅情報を保持するように変更されました。
    *   これにより、命令のオペランドのアドレス情報（`Addr`）と、命令自体の属性（`Prog`）であるデータ幅情報がより適切に分離され、`Prog`構造体で命令全体に関する情報を一元的に管理できるようになりました。この変更は、`src/cmd/5g/cgen.c`, `src/cmd/5g/galign.c`, `src/cmd/5g/gg.h`, `src/cmd/5g/ggen.c`, `src/cmd/5g/gobj.c`, `src/cmd/5g/gsubr.c`, `src/cmd/5g/list.c` の広範囲にわたる`p->from.scale`から`p->reg`への置換として現れています。

2.  **`ADATA`命令における`D_ADDR`から`D_CONST`への変更と`5l`での`D_ADDR`ハンドリングの削除**:
    *   `src/cmd/5g/ggen.c`や`src/cmd/5g/gobj.c`内のデータ生成ロジックにおいて、`ADATA`命令の`to.type`フィールドが`D_ADDR`に設定されている箇所が複数ありました。これは、データセクションに配置される値がアドレスであるという意図だったと考えられます。
    *   しかし、このコミットではこれらの`p->to.type = D_ADDR;`が`p->to.type = D_CONST;`に置き換えられています。これは、`ADATA`命令で定義される値が、リンカによって解決されるべきアドレスではなく、単なる定数値として扱われるべきであるというセマンティクスの修正を示唆しています。
    *   この変更に伴い、`src/cmd/5g/gobj.c`と`src/cmd/5l/obj.c`の両方で、`zaddr`関数内の`D_ADDR`ケースが削除されています。これは、`D_ADDR`が特別なアドレス指定モードとして扱われる必要がなくなったことを意味し、`5l`リンカが`D_ADDR`を特別に処理するロジックも不要になったため、そのハンドリングが「revert（元に戻された）」というコミットメッセージの記述と一致します。
    *   この修正により、コンパイラとリンカの間でのアドレス表現に関する認識の齟齬が解消され、より正確なコード生成とリンクが可能になります。

これらの変更は、Goコンパイラの内部データ表現をより効率的かつ正確にし、将来的な機能拡張や最適化のための基盤を強化するものです。

## コアとなるコードの変更箇所

*   **`src/cmd/5g/gg.h`**: `Addr`構造体から`scale`フィールドが削除され、`Prog`構造体の`reg`フィールドのコメントが更新され、`DATA`オペレーションにおける幅を兼ねることを明示。
*   **`src/cmd/5g/cgen.c`, `src/cmd/5g/ggen.c`, `src/cmd/5g/gobj.c`, `src/cmd/5g/gsubr.c`, `src/cmd/5g/list.c`**: `p->from.scale`を使用していた箇所が`p->reg`に置き換えられ、`ADATA`命令の`p->to.type`が`D_ADDR`から`D_CONST`に変更。
*   **`src/cmd/5g/galign.c`**: `zprog.from.scale = 0;`の初期化が削除。
*   **`src/cmd/5g/gobj.c`, `src/cmd/5l/obj.c`**: `zaddr`関数内の`D_ADDR`を処理する`case`文が削除。
*   **`src/cmd/5g/cgen.c`**: `sgen`関数の引数名が`ns`から`res`にリファクタリングされ、関数内部の`ns`の参照も`res`に更新。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラとリンカがアセンブリ命令とオペランドをどのように内部的に表現するかという点にあります。

`Addr`構造体は命令のオペランド（ソースやデスティネーション）の詳細を保持し、`Prog`構造体は個々のアセンブリ命令全体を表現します。以前は、`Addr`構造体の`scale`フィールドが`ADATA`命令におけるデータのサイズ（幅）を格納していましたが、これは命令自体の属性と見なすこともできます。このコミットでは、この`scale`の役割を`Prog`構造体の`reg`フィールドに統合することで、命令のメタデータが`Prog`構造体により一元的に集約されるようになりました。これにより、`Addr`構造体は純粋にオペランドのアドレス指定に関する情報のみを保持するようになり、データ構造の責務が明確化されました。

また、`ADATA`命令でアドレスを定義する際に`D_ADDR`タイプを使用していた箇所が`D_CONST`に変更されたことは、コンパイラが生成するオブジェクトコードのセマンティクスに関する重要な修正です。これは、特定のデータ定義が、実行時に解決されるべきアドレス参照ではなく、コンパイル時に確定する定数値として扱われるべきであることを示しています。この変更は、リンカ側での`D_ADDR`の特別な処理を不要にし、ツールチェーン全体のシンプル化と正確性の向上に貢献しています。

`sgen`関数の引数名のリファクタリング（`ns`から`res`へ）は、機能的な変更ではありませんが、コードの可読性と意図の明確化に寄与しています。`sgen`はメモリブロックコピーを生成する関数であり、`res`（resultの略）という名前はコピー先をより明確に示します。

これらの変更は、Goコンパイラの初期段階における内部設計の洗練と、より堅牢なコード生成メカニズムの構築に向けた一歩と言えます。

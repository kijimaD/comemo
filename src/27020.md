# [インデックス 27020] ファイルの概要

このコミットは、Go言語の `hash/crc32` パッケージにおけるCRC32計算のパフォーマンス改善に関するものです。特に、アセンブラ最適化が利用できないシステム（AMD64以外）において、Castagnoli多項式および比較的小さいデータサイズでのCRC32計算速度を向上させることを目的としています。具体的には、「スライス・バイ・8 (slicing by 8)」と呼ばれる最適化手法をCastagnoli多項式に適用し、この最適化を適用するデータサイズの閾値を調整しています。

## コミット

`hash/crc32: use slicing by 8 for Castagnoli and smaller sizes`

このコミットは、Castagnoli多項式を使用するCRC32計算において、「スライス・バイ・8」最適化を導入し、アセンブラが利用できないシステムでのパフォーマンスを向上させます。また、この最適化が有効になるデータサイズの閾値を16バイトに調整しました。これにより、以前よりも小さいデータサイズでも「スライス・バイ・8」が適用され、全体的なスループットが大幅に改善されています。

## 変更の背景

CRC32（巡回冗長検査）は、データ転送や保存におけるエラー検出によく用いられるアルゴリズムです。その計算速度は、特に大量のデータを扱うアプリケーションにおいて重要な性能指標となります。Go言語の `hash/crc32` パッケージは、このCRC32計算を提供していますが、特定の条件下でのパフォーマンスに改善の余地がありました。

既存の実装では、AMD64アーキテクチャのような一部のシステムでは、SSE4.2命令セットなどのハードウェアアクセラレーションを利用してCRC32計算を高速化していました。しかし、これらのアセンブラ最適化が利用できないシステム（例えばARMアーキテクチャなど）では、純粋なソフトウェア実装に頼る必要があり、その性能はハードウェアアクセラレーションを利用できるシステムに比べて劣っていました。

特に、Castagnoli多項式（CRC-32C）を使用する場合や、比較的小さいデータサイズ（数KB以下）のペイロードを処理する場合に、ソフトウェア実装の効率が課題となっていました。このコミットは、これらの「アセンブラなし」の環境と「小さいデータサイズ」のシナリオにおけるCRC32計算のボトルネックを解消し、全体的なスループットを向上させることを目的としています。

## 前提知識の解説

### CRC32 (Cyclic Redundancy Check)

CRC32は、データの破損を検出するために広く使用されるエラー検出コードです。データブロックのチェックサムを生成し、そのチェックサムをデータと共に送信または保存します。受信側または読み出し側で同じアルゴリズムを用いてチェックサムを再計算し、元のチェックサムと比較することで、データが破損していないかを確認します。CRCは、ビットエラーの検出に非常に効果的であり、特に通信プロトコルやストレージシステムで利用されます。

### 多項式 (Polynomials)

CRC計算は、有限体上の多項式除算に基づいています。CRC32では、32ビットの生成多項式が使用されます。最も一般的な多項式には以下の2種類があります。

*   **IEEE 802.3 (Ethernet) 多項式**: `0xEDB88320` (反転表現) または `0x04C11DB7` (非反転表現)。これは最も広く使われているCRC32多項式です。
*   **Castagnoli (CRC-32C) 多項式**: `0x82F63B78`。これはiSCSIやSCTPなどのプロトコルで使用され、IEEE多項式よりもランダムなエラーパターンに対して優れた検出能力を持つことが知られています。

### スライス・バイ・X (Slicing-by-X) アルゴリズム

CRC計算の基本的な方法は、データを1バイトずつ処理していくものですが、これは効率的ではありません。スライス・バイ・Xアルゴリズムは、この処理を高速化するための手法です。これは、事前に計算されたルックアップテーブルを使用して、一度に複数のバイト（Xバイト）を処理します。

例えば、「スライス・バイ・8」では、8つのルックアップテーブル（それぞれ256エントリ）を使用し、入力データの8バイトを同時に処理します。これにより、ループの反復回数が大幅に減少し、計算効率が向上します。この手法は、特にソフトウェア実装において、ハードウェアアクセラレーションがない場合に有効な最適化です。

### アセンブラ最適化とハードウェアアクセラレーション

一部のCPUアーキテクチャ（例: Intel/AMDのSSE4.2命令セット）には、CRC32計算をハードウェアレベルで高速化するための専用命令が搭載されています。これらの命令は非常に高速であり、Go言語の `hash/crc32` パッケージも、利用可能な場合はこれらの命令を自動的に使用するように実装されています。しかし、これらの命令がないシステム（例: ARMベースのプロセッサや古いx86プロセッサ）では、純粋なソフトウェア実装に頼るしかありません。このコミットは、まさにこの「アセンブラ最適化がない」シナリオでのパフォーマンス改善に焦点を当てています。

## 技術的詳細

このコミットの核心は、アセンブラ最適化が利用できない環境（特にAMD64以外のアーキテクチャ）でのCRC32計算、特にCastagnoli多項式を使用する場合のパフォーマンスを向上させることです。

1.  **Castagnoli多項式への「スライス・バイ・8」の適用**:
    以前は、IEEE多項式に対しては「スライス・バイ・8」最適化が適用されていましたが、Castagnoli多項式には適用されていませんでした。このコミットでは、Castagnoli多項式に対しても `slicing8Table` を生成し、`updateSlicingBy8` 関数を利用するように変更されました。これにより、Castagnoliのソフトウェア計算が大幅に高速化されます。

2.  **`sliceBy8Cutoff` 閾値の調整**:
    「スライス・バイ・8」のようなテーブルベースの最適化は、セットアップコスト（テーブルの初期化など）や、小さいデータサイズに対するオーバーヘッドが存在します。そのため、ある程度のデータサイズを超えた場合にのみこの最適化を適用し、それより小さいデータサイズではよりシンプルなバイトごとの処理（`update` 関数）にフォールバックするのが一般的です。
    このコミットでは、`sliceBy8Cutoff` という定数を導入し、この閾値を `16` バイトに設定しました。以前のIEEE多項式の実装では、この閾値が `4KB` (4096バイト) と非常に大きく設定されていました。コミットメッセージのテスト結果から、16バイト程度の小さいデータサイズでも「スライス・バイ・8」が従来のバイトごとの処理よりも高速であることが判明したため、この閾値が大幅に引き下げられました。これにより、より多くのシナリオで高速な「スライス・バイ・8」が利用されるようになります。

3.  **ベンチマークによる性能検証**:
    コミットメッセージには、変更前後のベンチマーク結果が詳細に記載されています。
    *   **Castagnoli, アセンブラなし, 40バイトペイロード**: 161 ns/op から 100 ns/op へと **37.89%** の高速化 (1.61倍)。
    *   **Castagnoli, アセンブラなし, 32KBペイロード**: 115426 ns/op から 45171 ns/op へと **60.87%** の高速化 (2.56倍)。
    *   **IEEE, アセンブラなし, 1KBペイロード**: 3604 ns/op から 1463 ns/op へと **59.41%** の高速化 (2.46倍)。

    これらの結果は、特にアセンブラ最適化が利用できない環境において、CastagnoliおよびIEEEの両多項式で、小さいデータサイズから大きいデータサイズまで、大幅な性能向上が達成されたことを明確に示しています。

## コアとなるコードの変更箇所

### `src/hash/crc32/crc32.go`

*   `sliceBy8Cutoff` 定数 (`const sliceBy8Cutoff = 16`) が追加され、スライス・バイ・8を適用する最小データサイズを定義。
*   `castagnoliTable8 *slicing8Table` が追加され、Castagnoli多項式用のスライス・バイ・8テーブルを保持。
*   `castagnoliInit()` 関数内で `castagnoliTable8 = makeTable8(Castagnoli)` が呼び出され、Castagnoli用のスライス・バイ・8テーブルが初期化されるように変更。
*   `updateSlicingBy8` 関数内で、入力 `p` の長さが0の場合に早期リターンする `if len(p) == 0 { return crc }` が追加され、エッジケースを適切に処理。
*   `ChecksumIEEE` 関数が `updateIEEE(0, data)` を呼び出すように変更され、内部で最適な更新ロジックが選択されるように抽象化。

### `src/hash/crc32/crc32_amd64.go`, `src/hash/crc32/crc32_amd64p32.go`, `src/hash/crc32/crc32_generic.go`

これらのファイルは、異なるアーキテクチャやコンパイルオプションに応じたCRC32計算の具体的な実装を含んでいます。

*   `updateCastagnoli` 関数と `updateIEEE` 関数において、`len(p) >= sliceBy8Cutoff` の条件が追加されました。これにより、入力データのサイズが `sliceBy8Cutoff` (16バイト) 以上の場合に `updateSlicingBy8` 関数が呼び出され、スライス・バイ・8最適化が適用されるようになります。
*   特に `updateIEEE` では、以前の `len(p) >= 4096` という条件が `len(p) >= sliceBy8Cutoff` に変更され、IEEE多項式に対してもより小さいデータサイズからスライス・バイ・8が適用されるようになりました。
*   `crc32_generic.go` では、`updateCastagnoli` が直接 `sliceBy8Cutoff` をチェックし、`updateSlicingBy8` を呼び出すように変更され、汎用的なソフトウェア実装でもこの最適化が利用されるようになりました。

### `src/hash/crc32/crc32_test.go`

*   新しいベンチマーク関数が追加されました。
    *   `BenchmarkIEEECrc40B`
    *   `BenchmarkCastagnoliCrc40B`
    *   `BenchmarkCastagnoliCrc32KB`
*   既存のベンチマーク関数も、新しい `benchmark` ヘルパー関数を使用するようにリファクタリングされました。
*   `benchmark` ヘルパー関数は、`hash.Hash32` インターフェースとデータサイズ `n` を受け取り、共通のベンチマークロジックを提供します。これにより、ベンチマークコードの重複が削減され、可読性が向上しています。
*   ベンチマークの前に `Warm up` ステップが追加され、JITコンパイルやキャッシュの影響を最小限に抑え、より安定した測定結果を得るようにしています。

## コアとなるコードの解説

このコミットの主要な変更は、CRC32計算のディスパッチロジックと、スライス・バイ・8最適化の適用範囲の拡大にあります。

1.  **`sliceBy8Cutoff` の役割**:
    `const sliceBy8Cutoff = 16` は、CRC32計算において「スライス・バイ・8」アルゴリズムを使用するか、よりシンプルなバイトごとの処理にフォールバックするかの閾値を定義します。入力データが16バイト未満の場合、スライス・バイ・8のセットアップコストがパフォーマンス上の利益を上回る可能性があるため、従来の処理が選択されます。16バイト以上の場合には、スライス・バイ・8が適用され、高速な計算が期待されます。

2.  **`castagnoliTable8` の導入**:
    `var castagnoliTable8 *slicing8Table` は、Castagnoli多項式専用のスライス・バイ・8ルックアップテーブルへのポインタです。`makeTable8(Castagnoli)` によってこのテーブルが生成され、`castagnoliInit()` で初期化されます。このテーブルは、`updateSlicingBy8` 関数が8バイトを一度に処理するために必要な事前計算された値を含んでいます。

3.  **`updateCastagnoli` および `updateIEEE` のディスパッチロジック**:
    `updateCastagnoli` と `updateIEEE` は、CRC32計算の主要なエントリポイントです。これらの関数は、以下の優先順位で最適な計算方法を選択します。
    *   **AMD64の場合**: まずSSE4.2命令セットが利用可能かチェックします。利用可能であれば、最も高速なハードウェアアクセラレーションが使用されます。
    *   **アセンブラなし、またはSSE4.2が利用できない場合**: 次に、入力データの長さ `len(p)` が `sliceBy8Cutoff` (16バイト) 以上であるかを確認します。
        *   もし `len(p) >= sliceBy8Cutoff` であれば、`updateSlicingBy8` 関数が呼び出され、スライス・バイ・8最適化が適用されます。
        *   そうでなければ、`update` 関数が呼び出され、バイトごとの基本的なCRC計算が実行されます。

    このディスパッチロジックにより、システム環境（ハードウェアアクセラレーションの有無）と入力データのサイズに応じて、常に最適なCRC32計算方法が動的に選択されるようになります。

4.  **`updateSlicingBy8` の改善**:
    `updateSlicingBy8` 関数は、入力データの先頭から8バイトずつ処理を進めます。`if len(p) == 0 { return crc }` の追加により、空のバイトスライスが渡された場合でも安全に処理を終えることができるようになりました。これは堅牢性の向上に寄与します。

これらの変更により、Goの `hash/crc32` パッケージは、より幅広い環境とデータサイズにおいて、効率的かつ高速なCRC32計算を提供できるようになりました。

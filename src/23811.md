# [インデックス 23811] ファイルの概要

このコミットは、Goコマンドラインツール（`cmd/go`）のビルドシステムにおける重要な改善を導入しています。具体的には、GoのビルドIDにGoツールチェーンのバージョン情報を含めるように変更することで、異なるGoバージョン間で`GOPATH`を共有している場合に、適切な再ビルドが自動的に行われるようにします。これにより、開発者がGoのバージョンを切り替える際に発生する可能性のある、古いバイナリが使用されてしまう問題を解決します。

## 元コミット内容

`cmd/go`: ビルドIDにGoツールチェーン情報を含める

これにより、Go 1.5でビルドされたパッケージやバイナリはGo 1.6に対して古く見え、その逆も同様になります。これにより、異なるGoバージョン間で同じ`GOPATH`を維持しながら切り替える際に、切り替えごとに適切な再ビルドが行われるようになります。

Go 1.4のバイナリもGo 1.5に対して古く見えますが、Go 1.5のバイナリはGo 1.4に対して古く見えません（Go 1.4にはこのような機能がないため）。Go 1.4とGo 1.5を切り替える人々は、Go 1.4に切り替えるたびに`go install -a`を使用する必要がありますが、Go 1.5に戻す際には必要ありません。

Fixes #6534.
Fixes #10702.

## 変更の背景

Goの開発において、複数のGoバージョンを切り替えて使用するシナリオは珍しくありません。特に、新しいGoバージョンがリリースされた際や、異なるプロジェクトで異なるGoバージョンを使用する必要がある場合に発生します。このとき、多くの開発者は`GOPATH`環境変数を共有して使用しています。

従来のGoビルドシステムでは、パッケージのビルドIDは主にソースファイルのハッシュに基づいて生成されていました。このため、Goのバージョンが変更されても、ソースファイル自体に変更がなければ、ビルドIDは同じままでした。その結果、開発者がGo 1.5でビルドしたバイナリをGo 1.6に切り替えた後も、`go build`や`go install`コマンドが「既に最新である」と判断し、再ビルドを行わないことがありました。これは、Goの内部的な変更（例えば、ランタイムの最適化や標準ライブラリの変更）がバイナリに影響を与えるにもかかわらず、古いバージョンのGoでビルドされたバイナリがそのまま使用されてしまうという問題を引き起こしました。

この問題は、特にGo 1.5で導入された大きな変更（例えば、コンパイラのGo言語への移行）によって顕著になりました。古いGoバージョンでビルドされたバイナリが新しいGoバージョンで予期せぬ動作をしたり、パフォーマンスの問題を引き起こしたりする可能性がありました。

このコミットは、この問題を解決するために、ビルドIDの生成ロジックにGoツールチェーンのバージョン情報を組み込むことで、異なるGoバージョンでビルドされたパッケージが確実に再ビルドされるようにすることを目的としています。

## 前提知識の解説

### GOPATH

`GOPATH`は、Go言語のワークスペースのルートディレクトリを指定する環境変数です。Go 1.11でGo Modulesが導入されるまでは、Goのソースコード、コンパイル済みパッケージ、および実行可能バイナリが配置される場所を定義する上で非常に重要な役割を果たしていました。

*   **`src`**: ソースコードが配置されるディレクトリ。`github.com/user/repo`のようなパス構造で管理されます。
*   **`pkg`**: コンパイル済みのパッケージアーカイブ（`.a`ファイル）が配置されるディレクトリ。Goコマンドは、依存関係を解決する際にこのディレクトリ内のパッケージを検索し、再ビルドの必要がない場合はここから利用します。
*   **`bin`**: `go install`コマンドで生成された実行可能バイナリが配置されるディレクトリ。

`GOPATH`を共有している場合、異なるGoバージョンでビルドされたパッケージが同じ`pkg`ディレクトリに保存されるため、ビルドIDが適切に管理されていないと問題が発生します。

### Go ビルドID (Build ID)

GoのビルドIDは、コンパイルされたパッケージやバイナリの「フィンガープリント」のようなものです。Goコマンドは、パッケージをビルドする際に、そのパッケージのソースコード、コンパイルオプション、および依存するパッケージのビルドIDなどに基づいて一意のハッシュ値を生成し、これをビルドIDとして使用します。

ビルドIDの主な目的は以下の通りです。

1.  **キャッシュの利用**: `go build`や`go install`コマンドは、ビルドIDを使用して、パッケージが変更されていないかどうかを判断します。ビルドIDが変更されていなければ、再コンパイルをスキップし、キャッシュされたコンパイル済みパッケージ（`pkg`ディレクトリ内の`.a`ファイル）を再利用することで、ビルド時間を短縮します。
2.  **依存関係の追跡**: あるパッケージが依存するパッケージのビルドIDも、そのパッケージ自身のビルドIDの計算に含まれます。これにより、依存パッケージが変更された場合でも、その変更が上位のパッケージのビルドIDに反映され、適切な再ビルドがトリガーされます。

### `go install` と `go build`

*   **`go build`**: 指定されたパッケージとその依存関係をコンパイルし、実行可能バイナリを生成します。デフォルトでは、現在のディレクトリにバイナリを配置します。
*   **`go install`**: `go build`と同様にコンパイルを行いますが、生成された実行可能バイナリを`GOPATH/bin`に、コンパイル済みパッケージアーカイブを`GOPATH/pkg`に配置します。これにより、他のプロジェクトからそのパッケージを依存関係として利用できるようになります。
*   **`go install -a`**: 全てのパッケージ（標準ライブラリを含む）を強制的に再ビルドします。これは、Goバージョンを切り替えた際に、古いバージョンのGoでビルドされた標準ライブラリが残っている場合に、クリーンな状態からビルドを開始するために使用されることがあります。

### `runtime/zversion.go`

`runtime/zversion.go`は、Goのソースツリー内の`src/runtime`ディレクトリに存在する特殊なファイルです。このファイルは、Goのビルドプロセス中に自動生成され、現在のGoツールチェーンのバージョン情報（例: `go1.5`）を文字列定数として保持しています。このファイルの内容は、Goのランタイムパッケージに埋め込まれ、実行時にGoのバージョンを識別するために使用されます。

このコミットでは、この`zversion.go`ファイルの内容をビルドIDの計算に含めることで、Goツールチェーンのバージョンが変更されたことをビルドシステムに認識させるための鍵となります。

## 技術的詳細

このコミットの核心は、GoコマンドがパッケージのビルドIDを計算するロジックを`src/cmd/go/pkg.go`内の`(*Package).load`メソッドで変更することにあります。具体的には、ビルドIDのハッシュ計算に以下の2つの要素を追加します。

1.  **`runtime`パッケージの`zversion.go`の内容**:
    *   `runtime`パッケージはGoの全てのプログラムが暗黙的に依存する最も基本的なパッケージです。
    *   `runtime`パッケージのビルドIDを計算する際に、そのパッケージ内の`zversion.go`ファイルの内容をハッシュに含めます。
    *   `zversion.go`はGoツールチェーンのバージョン情報を含むため、Goのバージョンが変わると`zversion.go`の内容も変わり、結果として`runtime`パッケージのビルドIDも変わります。
    *   これにより、Go 1.5でビルドされた`runtime`パッケージとGo 1.6でビルドされた`runtime`パッケージは異なるビルドIDを持つことになります。

2.  **依存パッケージのビルドID**:
    *   任意のパッケージのビルドIDを計算する際に、そのパッケージが直接依存する全てのパッケージのビルドIDもハッシュに含めます。
    *   この変更は、`runtime`パッケージのビルドIDの変更を他の全てのパッケージに伝播させるために重要です。
    *   例えば、`fmt`パッケージが`runtime`パッケージに依存している場合、`runtime`パッケージのビルドIDがGoのバージョン変更によって変わると、`fmt`パッケージのビルドIDも自動的に変わります。さらに、`fmt`に依存する他のパッケージもその影響を受け、最終的にアプリケーション全体のビルドIDがGoのバージョン変更を反映するように変わります。

この2つのメカニズムを組み合わせることで、Goのバージョンが変更された場合、`runtime`パッケージのビルドIDが変わり、それが依存関係を通じて全てのパッケージのビルドIDに伝播します。その結果、`go build`や`go install`コマンドは、`GOPATH`を共有していても、異なるGoバージョンでビルドされたパッケージを「古い」と判断し、自動的に再ビルドを実行するようになります。

コミットメッセージにあるGo 1.4とGo 1.5の間の挙動の違いは、この機能がGo 1.5で導入されたためです。Go 1.4にはこのビルドIDの仕組みがないため、Go 1.5でビルドされたバイナリはGo 1.4からは「新しい」と認識されません。しかし、Go 1.4でビルドされたバイナリは、Go 1.5からは`runtime/zversion.go`や依存関係のビルドID情報が欠けているため、「古い」と認識され、再ビルドが促されます。

## コアとなるコードの変更箇所

変更は`src/cmd/go/pkg.go`ファイルの`(*Package).load`関数内で行われています。この関数は、パッケージのビルドIDを計算する主要なロジックを含んでいます。

```diff
--- a/src/cmd/go/pkg.go
+++ b/src/cmd/go/pkg.go
@@ -724,6 +724,27 @@ func (p *Package) load(stk *importStack, bp *build.Package, err error) *Package
 	for _, file := range inputFiles {
 		fmt.Fprintf(h, "%s\\n", file)
 	}
+
+	// Include the content of runtime/zversion.go in the hash
+	// for package runtime. This will give package runtime a
+	// different build ID in each Go release.
+	if p.Standard && p.ImportPath == "runtime" {
+		data, _ := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
+		fmt.Fprintf(h, "zversion %q\\n", string(data))
+	}
+
+	// Include the build IDs of any dependencies in the hash.
+	// This, combined with the runtime/zversion content,
+	// will cause packages to have different build IDs when
+	// compiled with different Go releases.
+	// This helps the go command know to recompile when
+	// people use the same GOPATH but switch between
+	// different Go releases. See golang.org/issue/10702.
+	for _, dep := range p.Deps {
+		p1 := deps[dep]
+		fmt.Fprintf(h, "dep %s %s\\n", p1.ImportPath, p1.buildID)
+	}
+
 	p.buildID = fmt.Sprintf("%x", h.Sum(nil))
 
 	return p
```

## コアとなるコードの解説

変更されたコードブロックは、パッケージのビルドIDを計算するために使用されるハッシュ`h`に、追加の情報を書き込んでいます。

1.  **`runtime/zversion.go`の内容の組み込み**:
    ```go
    	// Include the content of runtime/zversion.go in the hash
    	// for package runtime. This will give package runtime a
    	// different build ID in each Go release.
    	if p.Standard && p.ImportPath == "runtime" {
    		data, _ := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
    		fmt.Fprintf(h, "zversion %q\\n", string(data))
    	}
    ```
    *   この`if`文は、現在処理しているパッケージが標準ライブラリの一部（`p.Standard`）であり、かつ`runtime`パッケージである場合にのみ実行されます。
    *   `ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))`は、`runtime`パッケージのディレクトリ内にある`zversion.go`ファイルの内容を読み込みます。
    *   `fmt.Fprintf(h, "zversion %q\\n", string(data))`は、読み込んだ`zversion.go`の内容を文字列としてハッシュ`h`に書き込みます。`%q`フォーマットは、文字列を引用符で囲んで出力するため、内容が正確にハッシュに反映されます。
    *   これにより、Goのバージョンが変わって`zversion.go`の内容が変わると、`runtime`パッケージのビルドIDも確実に変更されます。

2.  **依存パッケージのビルドIDの組み込み**:
    ```go
    	// Include the build IDs of any dependencies in the hash.
    	// This, combined with the runtime/zversion content,
    	// will cause packages to have different build IDs when
    	// compiled with different Go releases.
    	// This helps the go command know to recompile when
    	// people use the same GOPATH but switch between
    	// different Go releases. See golang.org/issue/10702.
    	for _, dep := range p.Deps {
    		p1 := deps[dep]
    		fmt.Fprintf(h, "dep %s %s\\n", p1.ImportPath, p1.buildID)
    	}
    ```
    *   この`for`ループは、現在のパッケージ`p`が直接依存する全てのパッケージ（`p.Deps`）を反復処理します。
    *   `p1 := deps[dep]`は、依存パッケージの情報を取得します。
    *   `fmt.Fprintf(h, "dep %s %s\\n", p1.ImportPath, p1.buildID)`は、各依存パッケージのインポートパスと、その依存パッケージ自身のビルドIDをハッシュ`h`に書き込みます。
    *   このステップが重要です。`runtime`パッケージのビルドIDが変更されると、`runtime`に依存する全てのパッケージ（例えば`fmt`）は、このループによってその変更を自身のビルドID計算に含めることになります。これにより、Goバージョン変更によるビルドIDの変更が、依存関係ツリー全体に伝播し、適切な再ビルドが促されます。

最終的に、これらの追加情報がハッシュ`h`に書き込まれた後、`p.buildID = fmt.Sprintf("%x", h.Sum(nil))`によって最終的なビルドIDが生成されます。

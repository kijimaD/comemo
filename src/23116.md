# [インデックス 23116] ファイルの概要

このコミットは、Go言語の`crypto/tls`パッケージにCertificate Transparency (CT) のサポートを追加するものです。具体的には、RFC 6962で定義されているSigned Certificate Timestamps (SCTs) の送受信機能が実装されました。これにより、TLSサーバーは証明書にSCTを含めて提供できるようになり、TLSクライアントはSCTを要求し、受信したSCTを`ConnectionState`構造体で公開できるようになります。

## 元コミット内容

この変更は、RFC 6962で記述されているSigned Certificate Timestamps (SCTs) の提供と受信のサポートを追加します。

サーバーは、`Certificate`構造体にリストされているSCTを提供できるようになりました。クライアントはSCTを要求し、受信したSCTは`ConnectionState`構造体で公開されます。

## 変更の背景

このコミットの背景には、TLS/SSL証明書エコシステムのセキュリティと信頼性を向上させるというCertificate Transparency (CT) の目標があります。従来の証明書発行プロセスでは、認証局 (CA) が誤って、あるいは悪意を持って不正な証明書を発行した場合、それを検出することが困難でした。これにより、攻撃者が不正な証明書を使用してウェブサイトになりすますリスクがありました。

Certificate Transparencyは、この問題を解決するために導入されました。CTは、公開された、追記専用のログにすべてのTLS証明書（または発行前のプレ証明書）を記録することを義務付けるフレームワークです。CAが証明書をCTログに提出すると、ログはSCT (Signed Certificate Timestamp) を返します。このSCTは、証明書が公開ログに記録されたことを証明する暗号的に署名されたアサーションです。

主要なブラウザ（Google Chromeなど）は、新しく発行される証明書に対してCTの要件を課し始めており、CAは発行するすべての証明書をログに記録することが実質的に義務付けられています。クライアント（ブラウザなど）は、TLSハンドシェイク中にサーバーからSCTを受け取り、そのSCTを検証することで、証明書が正当であり、公開記録されていることを確認します。

このコミットは、Goの`crypto/tls`パッケージがこのCTエコシステムに参加できるようにするための基盤を構築するものであり、サーバーとクライアントの両方がSCTを適切に処理できるようにすることで、Goアプリケーションのセキュリティと信頼性を向上させます。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブブラウザとウェブサーバー間のHTTPS通信などで広く利用されています。TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行われる一連のステップです。このハンドシェイク中に、サーバーは自身の身元を証明するためにX.509証明書をクライアントに提示します。

### X.509 証明書

X.509証明書は、公開鍵暗号方式において、公開鍵の所有者を証明するためのデジタル証明書です。認証局 (CA) によって発行され、ウェブサイトのドメイン名、公開鍵、CAの署名などが含まれています。クライアントは、CAの公開鍵を使用して証明書の署名を検証することで、その証明書が信頼できるCAによって発行されたものであることを確認します。

### Certificate Transparency (CT)

Certificate Transparency (CT) は、TLS証明書の発行プロセスに透明性をもたらすための公開監査システムです。その主な目的は以下の通りです。

*   **不正な証明書の検出**: CAが誤って、または悪意を持って不正な証明書を発行した場合でも、それを迅速に検出できるようにします。
*   **CAの活動の監視**: すべての証明書発行が公開ログに記録されるため、CAの活動を誰もが監査できるようになります。
*   **セキュリティの向上**: 不正な証明書の使用を防ぐことで、フィッシングや中間者攻撃などのリスクを低減します。

CTは、以下の主要なコンポーネントで構成されます。

*   **CTログ (CT Logs)**: 公開された、追記専用のデータベースで、CAが発行したすべての証明書（またはプレ証明書）が記録されます。ログは、Merkle Treeと呼ばれるデータ構造を使用して、追加されたすべてのエントリの整合性を保証します。
*   **Signed Certificate Timestamps (SCTs)**: CTログが証明書を受け取ると、その証明書がログに記録されたことを証明するSCTを発行します。SCTは、ログのID、タイムスタンプ、ログの署名などを含みます。
*   **CTモニター (CT Monitors)**: CTログを監視し、特定のドメイン名に関連する証明書が発行された場合にアラートを発するサービスです。これにより、ドメイン所有者は、自身が知らないうちに発行された証明書を検出できます。
*   **CTオーディター (CT Auditors)**: CTログの整合性を検証し、ログが正しく運用されていることを確認するエンティティです。

### Merkle Tree (マークルツリー)

Merkle Tree（ハッシュツリーとも呼ばれる）は、データの整合性を効率的に検証するために使用されるツリー構造のデータ構造です。各リーフノードはデータブロックのハッシュを含み、各非リーフノードは子ノードのハッシュの連結のハッシュを含みます。ルートノードのハッシュ（Merkle Root）は、ツリー内のすべてのデータの整合性を要約します。CTログでは、このMerkle Treeを使用して、ログに記録されたすべての証明書の整合性を保証し、特定の証明書がログに含まれていることを効率的に証明します。

## 技術的詳細

このコミットは、Goの`crypto/tls`パッケージにCertificate Transparency (CT) のサポートを導入するために、TLSプロトコルレベルでのSCTの送受信メカニズムを実装しています。これは、主に以下の技術的要素によって実現されます。

1.  **SCT拡張の定義**:
    TLSプロトコルでは、クライアントとサーバー間で追加情報を交換するために「拡張 (Extension)」メカニズムが使用されます。このコミットでは、SCTを伝送するための新しいTLS拡張タイプ`extensionSCT`が定義されました。RFC 6962のセクション6で定義されているように、この拡張のタイプコードは`18`です。

    *   `src/crypto/tls/common.go`に`extensionSCT uint16 = 18`が追加されました。

2.  **`Certificate`構造体へのSCTの追加**:
    TLSサーバーがクライアントに提供する証明書には、SCTを含めることができるようになりました。これは、`Certificate`構造体に`SignedCertificateTimestamps`フィールドを追加することで実現されます。このフィールドは、複数のSCTを格納できる`[][]byte`型です。

    *   `src/crypto/tls/common.go`の`Certificate`構造体に`SignedCertificateTimestamps [][]byte`が追加されました。

3.  **`ConnectionState`構造体へのSCTの追加**:
    TLSクライアントがサーバーから受信したSCTは、接続の状態を示す`ConnectionState`構造体を通じてアプリケーションに公開されます。これにより、アプリケーションは受信したSCTを検証したり、監査目的で利用したりすることができます。

    *   `src/crypto/tls/common.go`の`ConnectionState`構造体に`SignedCertificateTimestamps [][]byte`が追加されました。

4.  **TLSハンドシェイクメッセージの変更**:
    SCTの送受信は、TLSハンドシェイクの`ClientHello`および`ServerHello`メッセージを通じて行われます。

    *   **`ClientHello`メッセージ**: クライアントは、SCTをサポートしていることを示すために、`ClientHello`メッセージにSCT拡張を含めます。この拡張自体はデータを持たず、存在すること自体がSCTのサポートを示します。
        *   `src/crypto/tls/handshake_messages.go`の`clientHelloMsg`構造体に`scts bool`フィールドが追加され、`marshal()`および`unmarshal()`メソッドでSCT拡張の処理が追加されました。
        *   `src/crypto/tls/handshake_client.go`で、クライアントハンドシェイク時に`clientHelloMsg.scts`が`true`に設定されるようになりました。

    *   **`ServerHello`メッセージ**: サーバーは、クライアントがSCTを要求し、かつサーバーがSCTを提供できる場合、`ServerHello`メッセージにSCT拡張を含めてSCTを送信します。SCT拡張のデータ部分には、実際のSCTデータが格納されます。SCTは、複数のSCTが連結された形式で送信され、各SCTの前にその長さを示す2バイトのフィールドが付加されます。
        *   `src/crypto/tls/handshake_messages.go`の`serverHelloMsg`構造体に`scts [][]byte`フィールドが追加され、`marshal()`および`unmarshal()`メソッドでSCT拡張の処理が追加されました。
        *   `src/crypto/tls/handshake_server.go`で、サーバーハンドシェイク時にクライアントがSCTを要求した場合、サーバーの証明書にSCTが含まれていれば、それが`serverHelloMsg.scts`に設定されるようになりました。

5.  **テストケースの追加**:
    SCT機能の正確な動作を保証するために、新しいテストケースが追加されました。これには、SCTを含むハンドシェイクのテストや、SCTのエンコード/デコードのテストが含まれます。

    *   `src/crypto/tls/handshake_client_test.go`に`TestHandshakClientSCTs`が追加され、`openssl`コマンドで取得したSCTデータを使用したテストが行われています。
    *   `src/crypto/tls/handshake_server_test.go`に`TestSCTHandshake`が追加され、サーバーがSCTを提供し、クライアントがそれを受信できることを確認しています。
    *   既存のテストデータファイル（`src/crypto/tls/testdata/Client-TLSvXX-ClientCert-*-*`など）も、SCT拡張の追加に合わせて更新されています。

これらの変更により、Goの`crypto/tls`パッケージは、Certificate Transparencyの重要な要素であるSCTの送受信をTLSプロトコルレベルでサポートするようになり、より透明で信頼性の高いTLS通信が可能になりました。

## コアとなるコードの解説

このコミットのコアとなるコードの変更は、主にTLSハンドシェイクメッセージの構造と処理、およびSCTを格納するためのデータ構造の拡張に集中しています。

### `src/crypto/tls/common.go` の変更

*   **`extensionSCT` 定義**:
    ```go
    const (
        // ... 既存の拡張タイプ
        extensionSCT                 uint16 = 18 // https://tools.ietf.org/html/rfc6962#section-6
        // ...
    )
    ```
    これは、Certificate TransparencyのSCT拡張を識別するための定数です。TLSプロトコルでは、各拡張に一意の数値IDが割り当てられています。

*   **`ConnectionState` 構造体の拡張**:
    ```go
    type ConnectionState struct {
        // ... 既存のフィールド
        SignedCertificateTimestamps [][]byte // SCTs from the server, if any
    }
    ```
    クライアント側で、サーバーから受信したSCTをアプリケーションがアクセスできるようにするためのフィールドです。`[][]byte`型であるため、複数のSCTを格納できます。各`[]byte`が1つのSCTを表します。

*   **`Certificate` 構造体の拡張**:
    ```go
    type Certificate struct {
        // ... 既存のフィールド
        SignedCertificateTimestamps [][]byte // Signed Certificate Timestamps which will be served to clients that request it.
        // ...
    }
    ```
    サーバー側で、提供する証明書に関連付けられたSCTを格納するためのフィールドです。サーバーは、このフィールドにSCTを設定することで、TLSハンドシェイク中にクライアントにSCTを送信できるようになります。

### `src/crypto/tls/handshake_messages.go` の変更

このファイルは、TLSハンドシェイクメッセージのエンコード（`marshal`）とデコード（`unmarshal`）ロジックを定義しています。SCTサポートのために、`clientHelloMsg`と`serverHelloMsg`が変更されました。

*   **`clientHelloMsg` の変更**:
    ```go
    type clientHelloMsg struct {
        // ...
        scts                bool // クライアントがSCTを要求するかどうか
        // ...
    }

    func (m *clientHelloMsg) marshal() []byte {
        // ...
        if m.scts {
            // SCT拡張を追加。データ部分はゼロ長。
            z[0] = byte(extensionSCT >> 8)
            z[1] = byte(extensionSCT)
            z[2] = 0 // length high byte
            z[3] = 0 // length low byte
            z = z[4:]
        }
        // ...
    }

    func (m *clientHelloMsg) unmarshal(data []byte) bool {
        // ...
        case extensionSCT:
            m.scts = true
            if length != 0 { // SCT拡張のデータ部分はゼロ長でなければならない
                return false
            }
        // ...
    }
    ```
    クライアントは、`scts`フィールドを`true`に設定することで、`ClientHello`メッセージにSCT拡張を含めます。この拡張は、SCTのサポートを示すだけで、データは含みません（長さが0）。

*   **`serverHelloMsg` の変更**:
    ```go
    type serverHelloMsg struct {
        // ...
        scts                [][]byte // サーバーが提供するSCTのリスト
        // ...
    }

    func (m *serverHelloMsg) marshal() []byte {
        // ...
        sctLen := 0
        if len(m.scts) > 0 {
            for _, sct := range m.scts {
                sctLen += len(sct) + 2 // 各SCTの長さ + 2バイトの長さフィールド
            }
            extensionsLength += 2 + sctLen // 拡張タイプと長さフィールドの2バイト + SCTリストの長さ
            numExtensions++
        }
        // ...
        if sctLen > 0 {
            z[0] = byte(extensionSCT >> 8)
            z[1] = byte(extensionSCT)
            l := sctLen + 2 // SCTリスト全体の長さ + SCTリストの長さを示す2バイト
            z[2] = byte(l >> 8)
            z[3] = byte(l)
            z[4] = byte(sctLen >> 8) // SCTリスト全体の長さ
            z[5] = byte(sctLen)
            z = z[6:]
            for _, sct := range m.scts {
                z[0] = byte(len(sct) >> 8) // 各SCTの長さ
                z[1] = byte(len(sct))
                copy(z[2:], sct)
                z = z[len(sct)+2:]
            }
        }
        // ...
    }

    func (m *serverHelloMsg) unmarshal(data []byte) bool {
        // ...
        case extensionSCT:
            d := data[:length]
            if len(d) < 2 {
                return false
            }
            l := int(d[0])<<8 | int(d[1]) // SCTリスト全体の長さ
            d = d[2:]
            if len(d) != l {
                return false
            }
            if l == 0 {
                continue
            }

            m.scts = make([][]byte, 0, 3) // 複数のSCTを格納
            for len(d) != 0 {
                if len(d) < 2 {
                    return false
                }
                sctLen := int(d[0])<<8 | int(d[1]) // 各SCTの長さ
                d = d[2:]
                if len(d) < sctLen {
                    return false
                }
                m.scts = append(m.scts, d[:sctLen]) // SCTを抽出
                d = d[sctLen:]
            }
        // ...
    }
    ```
    サーバーは、`scts`フィールドにSCTのリストを設定することで、`ServerHello`メッセージにSCT拡張を含めます。SCTのエンコードとデコードは、RFC 6962の規定に従い、各SCTの前にその長さを示す2バイトのフィールドが付加される形式で行われます。

### `src/crypto/tls/handshake_server.go` の変更

*   **サーバーハンドシェイクロジック**:
    ```go
    func (hs *serverHandshakeState) handshake() (bool, error) {
        // ...
        if hs.clientHello.scts { // クライアントがSCTを要求した場合
            hs.hello.scts = hs.cert.SignedCertificateTimestamps // サーバーの証明書からSCTを設定
        }
        // ...
    }
    ```
    サーバーは、クライアントが`ClientHello`でSCT拡張を送信した場合（`hs.clientHello.scts`が`true`）、自身の証明書（`hs.cert`）にSCTが設定されていれば、それを`ServerHello`メッセージ（`hs.hello.scts`）に含めてクライアントに返します。

これらの変更により、Goの`crypto/tls`パッケージは、TLSハンドシェイク中にSCTを効果的に送受信できるようになり、Certificate Transparencyの要件を満たすための重要な機能が追加されました。

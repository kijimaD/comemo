# [インデックス 27455] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）とGoランタイム（`src/runtime`）から、使用されなくなったライトバリアヘルパー関数群を削除するものです。具体的には、`writebarrierstring`、`writebarrierslice`、`writebarrieriface`、そして様々な`writebarrierfat`関数とその生成スクリプトが対象となります。これらのヘルパーは、以前の変更（CL 10316）によって不要になったとされています。この変更により、コードベースの簡素化と、コンパイルおよびランタイムの効率化が期待されます。

## 変更の背景

このコミットの主な背景は、Goランタイムとコンパイラにおいて、特定のライトバリアヘルパー関数がもはや使用されていないという事実です。コミットメッセージには「These have been unused since CL 10316.」と明記されており、CL 10316という以前の変更（Change List）によって、これらのヘルパーが冗長になったことが示唆されています。

Goのガベージコレクション（GC）は、オブジェクトがヒープ上で移動する際に、ポインタの整合性を保つためにライトバリアを使用します。ライトバリアは、GCがオブジェクトを移動している最中に、プログラムがそのオブジェクトへのポインタを書き換えることを検出し、適切な処理（例えば、古いポインタを新しいポインタに更新する）を行うためのメカニズムです。

以前は、`string`、`slice`、`interface`型、そして様々なサイズの構造体（`fat`ヘルパー）に対する特定のライトバリアヘルパーが存在していました。これらは、異なるデータ型やメモリレイアウトに対して、効率的かつ正確にライトバリアを適用するために設計されていたと考えられます。しかし、GoのGCメカニズムやコンパイラの最適化が進むにつれて、これらの特定のヘルパーが不要になった、あるいはより汎用的なメカニズムに置き換えられた可能性があります。

不要なコードを削除することは、コードベースの保守性を向上させ、コンパイラの複雑さを軽減し、最終的には生成されるバイナリのサイズを削減し、コンパイル時間を短縮することに貢献します。

## 前提知識の解説

### ガベージコレクション (Garbage Collection, GC) とライトバリア (Write Barrier)

Go言語は、自動メモリ管理のためにガベージコレクションを採用しています。GCの主な目的は、プログラムがもはや参照しないメモリ領域（ガベージ）を自動的に解放し、メモリリークを防ぎ、開発者が手動でメモリを管理する負担を軽減することです。

GoのGCは、並行（concurrent）かつインクリメンタル（incremental）なマーク＆スイープ方式をベースにしています。これは、GCがプログラムの実行と並行して動作し、GCサイクル全体を一度に実行するのではなく、小さなステップで実行することを意味します。

ライトバリアは、並行GCにおいて非常に重要な技術です。GCがヒープ上のオブジェクトを移動（コンパクション）したり、オブジェクトの到達可能性をマークしたりしている最中に、アプリケーションコードがポインタを書き換える可能性があります。この書き換えによって、GCが誤った情報を基に動作したり、オブジェクトを見失ったりする「ポインタの消失」問題が発生する可能性があります。

ライトバリアは、プログラムがヒープ上のポインタを書き込む際に自動的に挿入される小さなコードスニペットです。このコードは、書き込み操作が行われる前に、GCに対して「このポインタが変更されようとしている」という通知を行います。これにより、GCはポインタの変更を検出し、必要に応じて追加の処理（例えば、変更前のポインタが指していたオブジェクトをマークする、あるいは新しいポインタが指すオブジェクトをマークする）を実行して、ポインタの整合性を維持します。

### `cmd/compile` と `src/runtime`

*   **`cmd/compile`**: Go言語のコンパイラです。Goのソースコードを機械語に変換する役割を担います。ライトバリアは、コンパイラによって適切なポインタ書き込み箇所に自動的に挿入されます。このコミットでは、コンパイラが認識していたライトバリアヘルパーの定義が削除されています。
*   **`src/runtime`**: Go言語のランタイムシステムです。ガベージコレクタ、スケジューラ、メモリ割り当て、プリミティブな同期メカニズムなど、Goプログラムの実行をサポートする低レベルな機能を提供します。ライトバリアヘルパーの実装は、このランタイムパッケージ内に存在していました。

### `writebarrierfat` ヘルパー

`writebarrierfat`という命名は、「fat」（太い、大きい）という言葉が示唆するように、複数のポインタを含む可能性のある、より大きなデータ構造（例えば、構造体や配列）に対するライトバリア処理を指していたと考えられます。`writebarrierfat01`、`writebarrierfat10`、`writebarrierfat001`などの命名規則は、対象となるデータ構造内のどのワードがポインタであり、どのワードが非ポインタ（スカラー値）であるかを示すビットマップのようなものと推測されます。例えば、`writebarrierfat01`は2ワードのデータ構造で、最初のワードがスカラー、2番目のワードがポインタであることを示唆しているかもしれません。これらのヘルパーは、異なるポインタレイアウトを持つ複合型に対して、効率的にライトバリアを適用するために、コンパイラによって選択的に呼び出されていたと考えられます。

## 技術的詳細

このコミットは、Goのガベージコレクションにおけるライトバリアの実装が進化し、特定の最適化や特殊ケース処理が不要になったことを示しています。

以前のGoのGCでは、`string`、`slice`、`interface`といった組み込み型や、複数のポインタを含む可能性のある複合型（`writebarrierfat`ヘルパーが対象としていたもの）に対して、それぞれ専用のライトバリアヘルパー関数が用意されていました。これらのヘルパーは、それぞれの型のメモリレイアウトやポインタの有無に応じて、最適なライトバリア処理を提供することを目的としていました。

しかし、GoのGCは継続的に改善されており、特にGo 1.5以降の三色マーク＆スイープGCの導入とそれに伴うライトバリアの変更（DijkstraスタイルのライトバリアからYuasaスタイルのハイブリッドライトバリアへの移行など）は、ライトバリアの実装に大きな影響を与えました。

コミットメッセージにある「CL 10316」が具体的にどのような変更であったかは不明ですが、推測されるのは以下のいずれか、または複数の組み合わせです。

1.  **より汎用的なライトバリアメカニズムの導入**: 特定の型に特化したヘルパーではなく、ポインタのビットマップ情報に基づいて任意の複合型を処理できる、より汎用的なライトバリア関数が導入された可能性があります。これにより、個別の`writebarrierfat`ヘルパーが不要になったと考えられます。
2.  **コンパイラの最適化**: コンパイラが、特定の型のライトバリアをインライン化したり、より効率的なコードを直接生成したりするようになった可能性があります。これにより、ランタイム側のヘルパー関数を呼び出す必要がなくなったのかもしれません。
3.  **GCアルゴリズムの変更**: GCアルゴリズム自体の変更により、特定のポインタ書き込みパターンに対するライトバリアの要件が緩和されたか、あるいは処理方法が変更され、これらのヘルパーが不要になった可能性も考えられます。

このコミットでは、`src/cmd/compile/internal/gc/builtin.go` および `src/cmd/compile/internal/gc/builtin/runtime.go` から、これらのライトバリアヘルパーのコンパイラ側の宣言が削除されています。これは、コンパイラがこれらの関数をもう認識せず、生成するコード内でこれらを呼び出さないことを意味します。

また、`src/runtime/mbarrier.go` からも、`writebarrierstring`、`writebarrierslice`、`writebarrieriface` の実装が削除されています。さらに、`src/runtime/wbfat.go` と `src/runtime/wbfat_gen.go` ファイル自体が削除されています。`wbfat_gen.go` は、`writebarrierfat`ヘルパー関数群を自動生成するためのスクリプトであったため、これらのヘルパーが不要になったことで、生成スクリプトも不要になったわけです。

`src/cmd/compile/internal/gc/order.go` の変更は興味深い点です。ここでは、`ordermapassign`関数内で`writebarrierfat`に関するコメントが追加されています。`// TODO(mdempsky): writebarrierfat doesn't exist anymore, but removing that // logic causes net/http's tests to become flaky; see CL 21242.` このコメントは、`writebarrierfat`がもはや存在しないにもかかわらず、関連するロジックを完全に削除すると`net/http`のテストが不安定になるという一時的な状況を示唆しています。これは、ライトバリアの変更がシステム全体に与える影響の複雑さと、慎重な移行が必要であることを物語っています。ただし、このコミット自体は、`writebarrierfat`ヘルパーの削除を目的としており、このコメントは将来的なクリーンアップのメモとして追加されたものです。

全体として、この変更はGoのGCとコンパイラの成熟度を示すものであり、より洗練された、あるいは汎用的なライトバリアメカニズムへの移行を反映していると考えられます。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルからコードが削除されています。

*   **`src/cmd/compile/internal/gc/builtin.go`**:
    *   `writebarrierstring`、`writebarrierslice`、`writebarrieriface`、および多数の`writebarrierfatXX`関数の宣言が削除されました。これらはコンパイラがランタイムのライトバリアヘルパーを認識するための組み込み関数宣言でした。
*   **`src/cmd/compile/internal/gc/builtin/runtime.go`**:
    *   上記と同様に、`writebarrierstring`、`writebarrierslice`、`writebarrieriface`、および多数の`writebarrierfatXX`関数の宣言が削除されました。
*   **`src/runtime/mbarrier.go`**:
    *   `writebarrierstring`、`writebarrierslice`、`writebarrieriface`関数の実装が削除されました。
*   **`src/runtime/wbfat.go`**:
    *   ファイル全体が削除されました。このファイルには、様々な`writebarrierfatXX`ヘルパー関数の実装が含まれていました。
*   **`src/runtime/wbfat_gen.go`**:
    *   ファイル全体が削除されました。このファイルは、`wbfat.go`内の`writebarrierfatXX`ヘルパー関数を自動生成するためのGoプログラムでした。
*   **`src/cmd/compile/internal/gc/order.go`**:
    *   `ordermapassign`関数内に、`writebarrierfat`がもはや存在しないこと、しかし関連ロジックの削除が`net/http`テストを不安定にするという`TODO`コメントが追加されました。これは、削除されたヘルパーに関連する古いロジックがまだ残っている可能性を示唆しています。

## コアとなるコードの解説

削除されたコードは、Goのガベージコレクションにおけるライトバリアの特定の側面を処理するためのものでした。

### `builtin.go` および `builtin/runtime.go` の変更

これらのファイルは、Goコンパイラがランタイムの特定の関数を「組み込み関数」として認識し、特別な処理を行うための宣言を含んでいます。これらのファイルからライトバリアヘルパーの宣言が削除されたことは、コンパイラがこれらの関数を直接呼び出す必要がなくなったことを意味します。これは、コンパイラがより汎用的なライトバリアメカニズムを使用するか、あるいはライトバリアコードを直接インライン化するようになったためと考えられます。

### `mbarrier.go` の変更

`mbarrier.go`は、Goランタイムにおけるメモリバリア（ライトバリアを含む）の主要な実装が含まれるファイルです。ここから`writebarrierstring`、`writebarrierslice`、`writebarrieriface`が削除されたことは、これらの特定の型に対するライトバリア処理が、より抽象化された、あるいは汎用的な`writebarrierptr`などの関数によって処理されるようになったことを示唆しています。例えば、`string`や`slice`は内部的にポインタと長さ/容量を持つ構造体として表現されるため、これらの構造体内のポインタフィールドに対するライトバリアは、汎用的なポインタライトバリアで十分になったのかもしれません。

### `wbfat.go` および `wbfat_gen.go` の削除

`wbfat.go`は、`writebarrierfat01`などの関数を多数含んでいました。これらの関数は、複数のポインタとスカラー値が混在するデータ構造に対して、ポインタ部分のみにライトバリアを適用するためのものでした。`wbfat_gen.go`はそのような関数を自動生成するスクリプトでした。これらのファイルが完全に削除されたことは、GoのGCが、複合型内のポインタを識別し、ライトバリアを適用するメカニズムを根本的に変更したことを強く示唆しています。

考えられる変更点としては、以下のようなものが挙げられます。

*   **型情報の活用**: ランタイムが、各型の詳細なポインタビットマップ情報（どのオフセットにポインタがあるかを示す情報）をより効率的に利用するようになった。これにより、コンパイラが特定の`writebarrierfat`ヘルパーを呼び出すのではなく、汎用的な`typedmemmove`や`memmove`のような関数が型情報に基づいてポインタを処理し、必要なライトバリアを適用できるようになった。
*   **コンパイラのインライン化**: コンパイラが、複合型への書き込み時に、必要なライトバリアロジックを直接インライン化するようになった。これにより、ランタイムのヘルパー関数を呼び出すオーバーヘッドが削減され、特定のヘルパー関数が不要になった。

### `order.go` の `TODO` コメント

`order.go`に追加された`TODO`コメントは、この変更が完全にスムーズではなかったことを示しています。`writebarrierfat`が削除されたにもかかわらず、`ordermapassign`内の関連ロジックを削除するとテストが不安定になるということは、古いライトバリアの仮定に基づいたコードパスがまだ存在するか、あるいは新しいライトバリアメカニズムへの完全な移行がまだ進行中であったことを示唆しています。これは、大規模なシステムにおける低レベルな変更の複雑さと、段階的な移行の必要性を浮き彫りにしています。

# [インデックス 20460] ファイルの概要

このコミットは、Goランタイムにおけるメモリ割り当て関数 `mallocgc` と `gomallocgc` を統合することを目的としています。これにより、コードの重複を排除し、特にガベージコレクション（GC）におけるポインタスキャンの挙動に関する混乱を解消します。

## 変更の背景

このコミットの背景には、Goランタイムにおけるメモリ割り当て関数の設計と、C言語との相互運用（cgo）における特定のメモリブロックのガベージコレクション（GC）処理に関する課題がありました。

コミットメッセージによると、作者であるRuss Coxは、`mallocgc` と `gomallocgc` という二つのメモリ割り当て関数が本質的に同じものであると誤解していました。この誤解は、`cgocallback.go` のコードを記述する際に顕在化しました。`cgocallback.go` は、C言語からGo言語へのコールバックを処理する部分であり、C言語のコードがGoのメモリ割り当て関数を呼び出す必要がありました。

問題は、`gomallocgc` が `nil` 型（割り当てるオブジェクトの型情報がないことを示す）かつ `FlagNoScan` フラグが設定されていない場合に、どのように振る舞うべきか不明確であった点です。Russ Coxは、C言語のコードから翻訳された `cgocallback.go` 内の呼び出しが、C言語版と同様に、割り当てられたメモリブロックを「保守的に（conservatively）」扱うことを意図していました。しかし、`gomallocgc` の既存の挙動では、この特定の組み合わせ（`nil` 型かつ `FlagNoScan` なし）が意図した保守的なスキャンを保証していませんでした。

この混乱と、特定のシナリオでのGC挙動の不確実性を解消するため、`mallocgc` と `gomallocgc` を統合し、`nil` 型かつ `FlagNoScan` なしのケースでもメモリブロックが正しく保守的に扱われるように変更されました。

## 前提知識の解説

### Goのメモリ管理とガベージコレクション (GC)

Go言語は、自動メモリ管理（ガベージコレクション）を採用しています。開発者は手動でメモリを解放する必要がなく、GCが不要になったメモリを自動的に回収します。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。

*   **マークフェーズ**: GCは、プログラムがアクセス可能なすべてのオブジェクト（ルートセットから到達可能なオブジェクト）を「マーク」します。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能で不要なオブジェクト）をメモリから解放します。

GoのGCは、初期のバージョンでは「Stop-the-World (STW)」方式を採用していました。これは、GCが実行されている間、プログラムの実行が完全に停止することを意味します。このコミットが作成された2014年9月時点では、GoのGCはまだSTWが主要な方式でした。Go 1.5（2015年8月リリース）で、より低レイテンシな並行GCが導入されることになります。

### `mallocgc` と `gomallocgc`

Goランタイムには、ヒープメモリを割り当てるための関数がいくつか存在します。
*   `mallocgc`: これはGoランタイムの主要なメモリ割り当て関数であり、ガベージコレクタと連携して動作します。割り当てられたメモリはGCの対象となります。
*   `gomallocgc`: このコミット以前に存在した関数で、`mallocgc` と同様にGoのヒープメモリを割り当てますが、その具体的な役割や `mallocgc` との厳密な違いが不明確でした。コミットメッセージから、作者自身もその違いに混乱していたことが伺えます。このコミットによって、`gomallocgc` は `mallocgc` に統合され、単一の統一されたメモリ割り当て関数が使用されることになります。

### `FlagNoScan`

`FlagNoScan` は、メモリ割り当て時に指定できるフラグの一つです。このフラグが設定されたメモリブロックは、GCがポインタスキャンを行わないことを示します。つまり、そのメモリブロック内にはGCが追跡すべきポインタが含まれていない、あるいは含まれていてもGCがそれらを無視してよい、とランタイムに伝えます。これは、例えば、純粋なデータ（数値、バイト列など）のみを格納するメモリブロックや、GCの対象外となるC言語のメモリなどを割り当てる際に使用されます。

### ポインタスキャンと保守的スキャン (Conservative Scanning)

*   **ポインタスキャン（Precise Scanning）**: GCがメモリブロック内のどこにポインタがあるかを正確に知っている場合に行われるスキャンです。型情報に基づいて、どのメモリワードがポインタであり、どのメモリワードが単なる整数や他のデータであるかを識別し、ポインタが指す先を追跡します。GoのGCは、基本的にこの正確なポインタスキャンを目指しています。
*   **保守的スキャン（Conservative Scanning）**: GCがメモリブロック内のどこにポインタがあるかを正確に識別できない場合に行われるスキャンです。この場合、GCはメモリブロック内のすべてのワードを調べ、それが有効なポインタのように見える値であれば、それをポインタとして扱います。つまり、「ポインタかもしれないものはすべてポインタとして扱う」という保守的なアプローチを取ります。これにより、誤ってポインタをデータとして解釈してしまい、到達可能なオブジェクトを回収してしまう（誤った回収）リスクを回避できますが、実際にはポインタではない値をポインタとして扱うことで、不要なメモリを保持し続ける（メモリリーク）可能性があります。C言語との相互運用など、型情報がGoランタイムに完全に透過的でない場合に用いられることがあります。

## 技術的詳細

このコミットの核心は、`mallocgc` と `gomallocgc` の統合、そして `nil` 型と `FlagNoScan` の組み合わせにおけるGCの挙動の明確化です。

1.  **関数の統合**:
    *   `src/runtime/malloc.c` にあったC言語実装の `runtime·mallocgc` 関数が削除されました。このC言語の `runtime·mallocgc` は、内部的にGo言語実装の `gomallocgc` を呼び出す「トランポリン」のような役割を果たしていました。
    *   `src/runtime/malloc.go` にあったGo言語実装の `gomallocgc` 関数が `mallocgc` にリネームされました。これにより、Goランタイムのメモリ割り当ての主要なエントリポイントが `mallocgc` に統一されました。
    *   `src/runtime/malloc.go` にあった `cmallocgc` 関数（CからGoの `mallocgc` を呼び出すためのラッパー）も削除されました。

2.  **`nil` 型と `FlagNoScan` の問題解決**:
    *   コミットメッセージで言及されているように、`gomallocgc` が `nil` 型（型情報なし）で、かつ `FlagNoScan` フラグが設定されていない場合に、GCがどのように振る舞うべきか不明確でした。通常、型情報がない場合はGCはポインタスキャンを行いませんが、`FlagNoScan` がないということは、ポインタが含まれる可能性があることを示唆します。
    *   この曖昧さを解消するため、新しい `mallocgc` 関数（旧 `gomallocgc`）の内部に以下のチェックが追加されました。
        ```go
        if flags&flagNoScan == 0 && typ == nil {
            gothrow("malloc missing type")
        }
        ```
        この変更により、`FlagNoScan` がなく、かつ型情報も `nil` であるという矛盾した状態での `mallocgc` の呼び出しは、ランタイムパニックを引き起こすようになりました。これは、このような状況ではGCが正確なスキャンを行うべきか、保守的なスキャンを行うべきか判断できないため、プログラマに明確な型情報を提供するか、`FlagNoScan` を明示的に指定するよう強制するものです。

3.  **`cgocallback.go` の修正と保守的スキャン**:
    *   `src/runtime/cgocallback.go` 内の `_cgo_allocate_internal` 関数では、以前は `gomallocgc(len, nil, 0)` と呼び出されていました。これは、型情報が `nil` で、`FlagNoScan` も指定されていない状態でした。
    *   このコミットにより、この呼び出しは `mallocgc(len, conservative, 0)` に変更されました。ここで `conservative` は、`runtime·conservative` という特別な型（`Type*`）を指します。この型は、GCに対して「このメモリブロックはポインタを含む可能性があるため、保守的にスキャンせよ」と指示します。これにより、C言語からGoに渡されたメモリブロックが、GoのGCによって適切に扱われることが保証されます。

この変更は、Goランタイムのメモリ割り当てとGCの挙動をより予測可能で堅牢なものにし、特にC言語との相互運用における潜在的なバグを防ぐ上で重要です。

## コアとなるコードの変更箇所

主要な変更は以下のファイルに集中しています。

*   `src/runtime/cgocallback.go`: `gomallocgc` の呼び出しが `mallocgc` に変更され、`conservative` 型が明示的に渡されるようになりました。
*   `src/runtime/chan.go`: `gomallocgc` の呼び出しが `mallocgc` に変更されました。
*   `src/runtime/malloc.c`: C言語実装の `runtime·mallocgc` および `cmallocgc` 関数が削除されました。
*   `src/runtime/malloc.go`:
    *   `gomallocgc` 関数が `mallocgc` にリネームされました。
    *   `mallocgc` 関数内に、`flags&flagNoScan == 0 && typ == nil` の場合にパニックを起こすチェックが追加されました。
    *   `cmallocgc` 関数が削除されました。
    *   `newobject`, `newarray`, `rawmem`, `runfinq` などの関数内の `gomallocgc` 呼び出しが `mallocgc` に変更されました。
*   `src/runtime/mgc0.c`: `runtime·mallocgc` の呼び出しで `FlagNoScan` が追加されました。
*   `src/runtime/os_plan9.c`, `src/runtime/os_windows.c`, `src/runtime/panic.go`, `src/runtime/parfor.c`, `src/runtime/proc.c`, `src/runtime/runtime.c`, `src/runtime/select.go`, `src/runtime/string.go`: これらのファイル内の `gomallocgc` 呼び出しが `mallocgc` に変更され、一部では `runtime·conservative` 型が明示的に渡されるようになりました。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

```go
// 旧: func gomallocgc(size uintptr, typ *_type, flags int) unsafe.Pointer {
func mallocgc(size uintptr, typ *_type, flags int) unsafe.Pointer {
	if size == 0 {
		return unsafe.Pointer(&zeroObject)
	}
	size0 := size

	// 追加されたチェック
	if flags&flagNoScan == 0 && typ == nil {
		gothrow("malloc missing type")
	}

	// ... (既存のメモリ割り当てロジック) ...
}

// cmallocgc は削除された
// 旧: func cmallocgc(size uintptr, typ *_type, flags int, ret *unsafe.Pointer) {
// 旧: 	*ret = gomallocgc(size, typ, flags)
// 旧: }

// newobject, newarray, rawmem, runfinq などの関数内の呼び出しが gomallocgc から mallocgc に変更
// 例:
// 旧: return gomallocgc(uintptr(typ.size), typ, flags)
// 新: return mallocgc(uintptr(typ.size), typ, flags)
```

*   `gomallocgc` が `mallocgc` にリネームされたことで、Goランタイムのヒープ割り当ての単一の窓口が確立されました。
*   追加された `if flags&flagNoScan == 0 && typ == nil` チェックは非常に重要です。これは、GCがポインタスキャンを行うべき（`FlagNoScan` がない）にもかかわらず、割り当てられるオブジェクトの型情報（`typ`）が `nil` であるという矛盾した状態を検出します。このような状況では、GCは正確なスキャンを行うことができないため、ランタイムパニック `malloc missing type` を発生させ、プログラマに問題の修正を促します。これにより、GCの挙動の曖昧さが解消されます。

### `src/runtime/cgocallback.go` の変更

```go
// 旧: ret := gomallocgc(len, nil, 0)
ret := mallocgc(len, conservative, 0)
```

*   `_cgo_allocate_internal` 関数は、C言語からGoにコールバックする際にメモリを割り当てるために使用されます。
*   以前は `gomallocgc(len, nil, 0)` と呼び出されていましたが、これは型情報が `nil` で、`FlagNoScan` も指定されていない状態でした。
*   変更後、`mallocgc(len, conservative, 0)` となりました。ここで `conservative` は `runtime·conservative` という特別な型を指します。この型は、GCに対して、割り当てられたメモリブロックを「保守的にスキャンする」ように指示します。これにより、C言語との相互運用で割り当てられたメモリブロック内のポインタが、GoのGCによって確実に追跡されるようになります。

### `src/runtime/malloc.c` の変更

```c
// 削除された関数
// void*
// runtime·mallocgc(uintptr size, Type *typ, uint32 flag)
// {
// 	void *ret;
//
// 	// Call into the Go version of mallocgc.
// 	// TODO: maybe someday we can get rid of this.  It is
// 	// probably the only location where we run Go code on the M stack.
// 	if((flag&FlagNoScan) == 0 && typ == nil)
// 		typ = runtime·conservative;
// 	runtime·cmallocgc(size, typ, flag, &ret);
// 	return ret;
// }

// cmallocgc の宣言も削除された
// void runtime·cmallocgc(uintptr size, Type *typ, uint32 flag, void **ret);
```

*   C言語で実装されていた `runtime·mallocgc` 関数が完全に削除されました。この関数は、Go言語で実装された `gomallocgc`（現在の `mallocgc`）への単なるラッパーでした。この削除により、メモリ割り当てのロジックがGo言語側に一元化され、C言語とGo言語間の不必要な呼び出しオーバーヘッドが削減されます。
*   `cmallocgc` の宣言と実装も削除されました。これは、C言語からGoの `mallocgc` を呼び出すための「トランポリン」関数でしたが、`mallocgc` がGo言語側で直接処理されるようになったため不要になりました。

これらの変更により、Goランタイムのメモリ割り当てサブシステムはよりシンプルになり、GCの挙動がより明確かつ堅牢になりました。

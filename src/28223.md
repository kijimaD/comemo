# [インデックス 28223] ファイルの概要

このコミットは、Go言語の `archive/tar` パッケージにおけるtarヘッダーフォーマットの扱いを大幅に改善するものです。これまでコードベース全体に散らばっていたtarヘッダーフィールドのオフセットと長さに関するハードコードされた定数を一元化し、`format.go` という新しいファイルに集約しました。これにより、コードの可読性、保守性、および正確性の検証が向上しています。特に、`encoding/binary` パッケージを使用した場合に発生する可能性のあるアロケーションを避けつつ、効率的なバイト配列操作によってヘッダー情報を扱う新しいメカニズムを導入しています。

## コミット

archive/tar: tarヘッダーフォーマットに関する全ての情報を一元化

ReaderとWriterには、tarフォーマットの特定のフィールドのオフセットと長さに関するハードコードされた定数が散在していました。これにより、レビュー担当者がコード全体を検索する必要があるため、オフセットが正しいことを検証することが困難になっていました。代わりに、ヘッダー構造のレイアウトに関するすべての情報を単一のファイルに一元化すべきです。これは、一元化されるだけでなく、ヘッダー構造フォーマットに関するドキュメントの形式としても機能するという利点があります。

この方法は、`encoding/binary` を使用した場合、`binary.Read` が呼び出されるたびにヘッダー構造のアロケーションが発生するため、その方法よりも選択されました。この方法はアロケーションをゼロにし、そのロジックは構造体が宣言された場合よりも長くありません。

+// GetFormat checks that the block is a valid tar header based on the checksum.
+// It then attempts to guess the specific format based on magic values.
+// If the checksum fails, then formatUnknown is returned.
+func (b *block) GetFormat() (format int) {
+	// Verify checksum.
+	var p parser
+	value := p.parseOctal(b.V7().Chksum())
+	chksum1, chksum2 := b.ComputeChecksum()
+	if p.err != nil || (value != chksum1 && value != chksum2) {
+		return formatUnknown
+	}
+
+	// Guess the magic values.
+	magic := string(b.USTAR().Magic())
+	version := string(b.USTAR().Version())
+	trailer := string(b.STAR().Trailer())
+	switch {
+	case magic == magicUSTAR && trailer == trailerSTAR:
+		return formatSTAR
+	case magic == magicUSTAR:
+		return formatUSTAR
+	case magic == magicGNU && version == versionGNU:
+		return formatGNU
+	default:
+		return formatV7
+	}
+}

+// SetFormat writes the magic values necessary for specified format
+// and then updates the checksum accordingly.
+func (b *block) SetFormat(format int) {
+	// Set the magic values.
+	switch format {
+	case formatV7:
+		// Do nothing.
+	case formatGNU:
+		copy(b.GNU().Magic(), magicGNU)
+		copy(b.GNU().Version(), versionGNU)
+	case formatSTAR:
+		copy(b.STAR().Magic(), magicUSTAR)
+		copy(b.STAR().Version(), versionUSTAR)
+		copy(b.STAR().Trailer(), trailerSTAR)
+	case formatUSTAR, formatPAX:
+		copy(b.USTAR().Magic(), magicUSTAR)
+		copy(b.USTAR().Version(), versionUSTAR)
+	default:
+		panic("invalid format")
+	}
+
+	// Update checksum.
+	// This field is special in that it is terminated by a NULL then space.
+	var f formatter
+	field := b.V7().Chksum()
+	chksum, _ := b.ComputeChecksum() // Possible values are 256..128776
+	f.formatOctal(field[:7], chksum) // Never fails since 128776 < 262143
+	field[7] = ' '
+}

+// ComputeChecksum computes the checksum for the header block.
+// POSIX specifies a sum of the unsigned byte values, but the Sun tar used
+// signed byte values.
+// We compute and return both.
+func (b *block) ComputeChecksum() (unsigned, signed int64) {
+	for i, c := range b {
+		if 148 <= i && i < 156 {
+			c = ' ' // Treat the checksum field itself as all spaces.
+		}
+		unsigned += int64(uint8(c))
+		signed += int64(int8(c))
+	}
+	return unsigned, signed
+}

## 変更の背景

このコミットの主な背景は、Go言語の `archive/tar` パッケージがtarアーカイブヘッダーのフィールドオフセットと長さを扱う方法における、既存の課題を解決することにありました。

1.  **散在するハードコードされた定数:** 以前の実装では、tarヘッダー内の各フィールド（ファイル名、モード、UID、GID、サイズなど）の開始オフセットとバイト長が、`Reader` および `Writer` のコード全体にハードコードされた定数として散らばっていました。これは、コードの可読性を著しく低下させ、特定のフィールドの定義を変更する必要がある場合に、複数の場所を更新しなければならないという保守性の問題を引き起こしていました。
2.  **検証の困難さ:** 定数が散在しているため、コードレビュー担当者が各オフセットと長さがtar仕様に正確に準拠しているかを検証することが非常に困難でした。コード全体を検索し、各使用箇所を個別に確認する必要があったため、エラーの見落としや不正確な実装のリスクがありました。
3.  **ドキュメントとしての機能不足:** ヘッダーの構造に関する情報がコード内に明示的に定義されていなかったため、コード自体がヘッダーフォーマットのドキュメントとして機能していませんでした。新しい開発者やレビュー担当者がtarヘッダーのレイアウトを理解するためには、外部の仕様書を参照するか、コードを丹念に追う必要がありました。
4.  **`encoding/binary` の非効率性:** コミットメッセージでは、`encoding/binary` パッケージを使用する代替案が検討されたものの、その方法では `binary.Read` が呼び出されるたびにヘッダー構造のアロケーションが発生するため、パフォーマンス上のオーバーヘッドがあることが指摘されています。`archive/tar` のような低レベルのI/Oパッケージでは、アロケーションを最小限に抑えることが重要です。

これらの課題に対処するため、tarヘッダーフォーマットに関するすべての情報を一元化し、より構造化された方法でアクセスできるようにすることが目的とされました。これにより、コードの保守性と正確性が向上し、パフォーマンスへの影響も最小限に抑えられます。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### 1. Tarアーカイブフォーマット

`tar` (tape archive) は、複数のファイルを一つのアーカイブファイルにまとめるためのファイルフォーマットです。主にUnix系システムで利用され、ファイルのメタデータ（パーミッション、所有者、タイムスタンプなど）とファイルデータが連続して格納されます。tarフォーマットには歴史的にいくつかのバリエーションが存在し、それぞれヘッダーの構造やサポートする機能が異なります。

*   **V7 Tar (Old-Style Tar):** 最も古い形式で、ファイル名やファイルサイズに厳しい制限があります。マジックナンバーを持たないため、自動判別が難しい場合があります。
*   **USTAR (POSIX 1003.1-1988):** POSIX標準で定義された形式で、V7の制限を緩和し、`prefix` フィールドの導入により長いファイル名をサポートします。`ustar` というマジックナンバーを持ちます。
*   **GNU Tar Format:** USTARの拡張で、さらに長いファイル名やスパースファイル、追加のタイムスタンプなどをサポートします。特定のヘッダータイプ（`L` や `K`）を使用して、ファイル名やリンクパスの長さを無制限にします。
*   **PAX (POSIX 1003.1-2001):** 最新のPOSIX標準で、USTARを拡張したものです。拡張ヘッダーレコード（`x` および `g` タイプ）を導入し、任意の長さのパス、無制限のファイルサイズ、ナノ秒単位のタイムスタンプなど、より柔軟なメタデータ表現を可能にします。後方互換性があります。
*   **STAR:** Sunによって実装されたPOSIX.1-2001拡張ヘッダータイプのベンダー固有のバリアントです。

各tarアーカイブは、通常512バイトの「ヘッダーブロック」で始まり、その後にファイルデータが続きます。ヘッダーブロックには、ファイル名、サイズ、パーミッション、所有者、タイムスタンプ、チェックサムなどのメタデータが格納されます。

### 2. Go言語の `archive/tar` パッケージ

`archive/tar` パッケージは、Goプログラムでtarアーカイブの読み書きを行うための標準ライブラリです。`Reader` と `Writer` という主要な型を提供し、それぞれtarアーカイブからの読み込みとtarアーカイブへの書き込みを抽象化します。このパッケージは、異なるtarフォーマット（V7, USTAR, GNU, PAXなど）を透過的に扱うことを目指しています。

### 3. Go言語におけるメモリ管理とアロケーション

Go言語はガベージコレクションを備えていますが、不要なメモリ割り当て（アロケーション）はパフォーマンスに影響を与える可能性があります。特に、頻繁に呼び出されるI/O処理や低レベルのデータ処理では、アロケーションを最小限に抑えることが重要です。`encoding/binary` パッケージは、構造体とバイト列の間の変換に便利ですが、その過程で一時的な構造体のアロケーションが発生することがあります。このコミットでは、このアロケーションを避けるために、バイト配列を直接操作するアプローチが採用されています。

### 4. バイト配列とスライス操作

Go言語では、`[]byte` 型のスライスを使ってバイト列を効率的に操作できます。このコミットでは、`[512]byte` の固定長配列を基盤とし、そのスライスを返すメソッドを定義することで、メモリコピーやアロケーションなしにヘッダーの各フィールドにアクセスする手法が用いられています。

## 技術的詳細

このコミットの技術的な核心は、tarヘッダーの構造をGoの型システムとバイト配列操作を組み合わせて表現し、一元化することにあります。

### 1. `format.go` の導入と `block` 型

*   新しいファイル `src/archive/tar/format.go` が導入されました。このファイルは、tarヘッダーフォーマットに関するすべての定数、型、およびヘルパー関数をカプセル化します。
*   `type block [blockSize]byte` という型が定義されました。`blockSize` は512バイトで、これはtarヘッダーブロックの標準サイズです。この `block` 型は、512バイトの生データを保持する固定長配列として機能します。

### 2. ヘッダーフォーマット固有のビュー

`format.go` では、異なるtarフォーマット（V7, GNU, STAR, USTAR）に対応する複数の構造体（例: `headerV7`, `headerGNU`, `headerSTAR`, `headerUSTAR`）が定義されています。これらの構造体は、実際には `[blockSize]byte` のエイリアスであり、基盤となる `block` 型のデータに対する「ビュー」を提供します。

例:
```go
type headerV7 [blockSize]byte

func (h *headerV7) Name() []byte     { return h[000:][:100] }
func (h *headerV7) Mode() []byte     { return h[100:][:8] }
func (h *headerV7) Chksum() []byte   { return h[148:][:8] }
// ... 他のフィールドも同様
```
これらのメソッドは、`headerV7` 型のインスタンス（実体は `block` 型のバイト配列）に対して、特定のオフセットと長さを持つバイトスライスを返します。重要なのは、これらのメソッドが**新しいメモリを割り当てない**ことです。常に基盤となる `block` 配列の特定の部分へのスライスを返します。これにより、`encoding/binary` を使用した場合に発生するアロケーションが回避されます。

`block` 型には、これらのビューを取得するためのヘルパーメソッドも追加されました。
```go
func (b *block) V7() *headerV7       { return (*headerV7)(b) }
func (b *block) GNU() *headerGNU     { return (*headerGNU)(b) }
// ... 他のフォーマットも同様
```
これにより、`tr.blk.V7().Name()` のように、現在のブロックを特定のフォーマットのヘッダーとして解釈し、そのフィールドにアクセスすることが可能になります。

### 3. フォーマットの自動判別と設定

*   `block` 型には `GetFormat()` メソッドが追加されました。このメソッドは、ヘッダーブロックのチェックサムを検証し、さらにマジック値（`magicUSTAR`, `magicGNU`, `trailerSTAR` など）に基づいて、ヘッダーがどのtarフォーマット（`formatV7`, `formatUSTAR`, `formatGNU`, `formatSTAR`, `formatPAX`）に属するかを判別します。
*   `SetFormat(format int)` メソッドは、指定されたフォーマットに応じてマジック値をヘッダーブロックに書き込み、チェックサムを更新します。これにより、`Writer` が正しいフォーマットのヘッダーを生成できるようになります。

### 4. チェックサム計算の一元化

`ComputeChecksum()` メソッドも `block` 型に移動され、チェックサムの計算ロジックが一元化されました。これにより、`common.go` から `checksum` 関数が削除され、関連するロジックが `format.go` に集約されました。

### 5. `Reader` と `Writer` の変更

`Reader` と `Writer` の実装は、新しい `block` 型とヘッダービューを活用するように変更されました。
*   `Reader` は `hdrBuff [blockSize]byte` の代わりに `blk block` フィールドを持つようになりました。
*   ヘッダーの読み込み (`readHeader`) や書き込み (`writeHeader`) のロジックは、直接バイトオフセットを操作する代わりに、`tr.blk.V7().Name()` のようなメソッド呼び出しを通じて行われるようになりました。これにより、コードがより抽象的で読みやすくなりました。
*   `writer_test.go` では、`fileNameSize` や `fileNamePrefixSize` といった古い定数が、新しい `nameSize` や `prefixSize` に置き換えられています。

このアプローチにより、tarヘッダーの構造が `format.go` に明確に定義され、各フィールドへのアクセスが型安全かつアロケーションフリーで行えるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/archive/tar/format.go` で導入された `block` 型と、それに関連するヘッダービューのメカニズムです。

### `block` 型とヘッダービュー

```go
// src/archive/tar/format.go
type block [blockSize]byte // blockSizeは512

type headerV7 [blockSize]byte
func (h *headerV7) Name() []byte     { return h[000:][:100] }
func (h *headerV7) Mode() []byte     { return h[100:][:8] }
// ...

func (b *block) V7() *headerV7       { return (*headerV7)(b) }
func (b *block) GNU() *headerGNU     { return (*headerGNU)(b) }
// ...
```

*   `block` は、tarヘッダーの生データを格納するための512バイトの固定長配列です。
*   `headerV7` などの型も `[blockSize]byte` のエイリアスとして定義されています。これは、`block` 型と同じ基盤となるメモリレイアウトを持つことを意味します。
*   `V7()` メソッドのように、`block` 型から `*headerV7` への型変換は、**ポインタの型キャスト**であり、新しいメモリ割り当ては発生しません。これは、`block` の生データが `headerV7` の構造と互換性があるため可能です。
*   `headerV7` の `Name()` メソッドは `h[000:][:100]` のように、基盤となるバイト配列の特定の部分への**スライス**を返します。スライスは元の配列への参照であり、ここでも新しいメモリ割り当ては発生しません。

この設計により、`Reader` や `Writer` は、`tr.blk` という単一の `block` インスタンスを保持するだけで、そのデータを異なるtarフォーマットのヘッダーとして解釈し、各フィールドに効率的にアクセスできるようになります。例えば、`tr.blk.V7().Name()` は、`tr.blk` の最初の100バイトをファイル名フィールドとして取得します。これは、以前の `header[0:100]` と同等の操作ですが、`V7()` メソッドを介することで、どのフォーマットのどのフィールドにアクセスしているかがコード上でより明確になります。

### フォーマット判別ロジック

```go
// src/archive/tar/format.go
func (b *block) GetFormat() (format int) {
	// チェックサム検証
	// ...

	// マジック値によるフォーマット判別
	magic := string(b.USTAR().Magic())
	version := string(b.USTAR().Version())
	trailer := string(b.STAR().Trailer())
	switch {
	case magic == magicUSTAR && trailer == trailerSTAR:
		return formatSTAR
	case magic == magicUSTAR:
		return formatUSTAR
	case magic == magicGNU && version == versionGNU:
		return formatGNU
	default:
		return formatV7
	}
}
```
`GetFormat()` メソッドは、まずヘッダーのチェックサムを計算して検証します。その後、`b.USTAR().Magic()` や `b.STAR().Trailer()` のように、異なるフォーマットのヘッダービューを使ってマジックフィールドにアクセスし、その値に基づいて現在のヘッダーがどのtarフォーマットに属するかを判別します。これにより、`Reader` は読み込んだヘッダーブロックのフォーマットを正確に特定し、それに応じた解析ロジックを適用できるようになります。

### `Reader` と `Writer` の簡素化

以前は `reader.go` や `writer.go` の中で、`header[148:156]` のようにマジックナンバーやチェックサムフィールドに直接アクセスするコードが散在していました。このコミットにより、これらのアクセスは `tr.blk.V7().Chksum()` や `tr.blk.USTAR().Magic()` のような、より意味的で型安全なメソッド呼び出しに置き換えられました。これにより、コードの意図が明確になり、ヘッダーフォーマットの変更があった場合でも、`format.go` の定義を更新するだけで済むため、保守性が大幅に向上しました。

# [インデックス 2433] ファイルの概要

このコミットは、Go言語のランタイムにおけるシステムコール生成ツール `mksyscall` が、64-bitシステム上で64-bit引数を正しく扱えていなかった問題を修正するものです。特に `Seek` システムコールにおけるオフセット値の処理が改善されました。

変更されたファイルは以下の通りです。

*   `src/lib/os/os_test.go`: `Seek` システムコールの動作を検証するための新しいテストケース `TestSeek` が追加されました。
*   `src/lib/syscall/mksyscall`: システムコールラッパーを生成するスクリプトの内部変数の初期化が変更されました。
*   `src/lib/syscall/zsyscall_darwin_amd64.go`: Darwin (macOS) のAMD64アーキテクチャ向けシステムコールラッパーが修正されました。`lseek`, `ftruncate`, `pread`, `pwrite`, `truncate` などの関数で、64-bit引数の渡し方が変更されています。また、`getfsstat64` の削除と `Getfsstat` の追加、`gettimeofday` の移動が行われています。
*   `src/lib/syscall/zsyscall_linux_amd64.go`: Linux のAMD64アーキテクチャ向けシステムコールラッパーが修正されました。`Fallocate`, `Ftruncate`, `Pread`, `Pwrite`, `Seek`, `SyncFileRange`, `Truncate` などの関数で、64-bit引数の渡し方が変更されています。また、ソケット関連の関数群の移動が行われています。

## 変更の背景

このコミットの背景には、Go言語の初期段階におけるシステムコール呼び出しの抽象化レイヤーの不完全さがありました。具体的には、`mksyscall` というツールが、64-bitアーキテクチャ上で動作しているにもかかわらず、システムコールに渡されるべき64-bitの引数（特にファイル操作におけるオフセット値など）を32-bitとして扱ってしまうバグが存在していました。

これにより、例えば `Seek` システムコールで非常に大きなファイルオフセットを指定した場合、そのオフセット値が正しくOSに伝達されず、予期せぬ動作やエラーが発生する可能性がありました。64-bitシステムでは、ファイルサイズやオフセットが32-bitの範囲をはるかに超えることが一般的であるため、この問題はファイルI/Oの信頼性と正確性に直接影響を与える重要なものでした。

この修正は、Goランタイムが64-bitシステムのリソースを完全に活用し、大規模なファイル操作を正確に実行できるようにするために不可欠でした。

## 前提知識の解説

### Goの`syscall`パッケージとシステムコール

Go言語の`syscall`パッケージは、Goプログラムからオペレーティングシステム（OS）のシステムコールを直接呼び出すための低レベルなインターフェースを提供します。システムコールは、ファイルI/O、ネットワーク通信、プロセス管理など、OSカーネルが提供する基本的なサービスを利用するための唯一の手段です。

### `mksyscall`ツール

`mksyscall`は、Goの`syscall`パッケージ内で使用されるGoコードを自動生成するためのツールです。OSのC言語ヘッダファイルやシステムコール定義を解析し、それに対応するGo言語のシステムコールラッパー関数（例: `zsyscall_darwin_amd64.go`, `zsyscall_linux_amd64.go` など）を生成します。これにより、開発者は各OSやアーキテクチャのシステムコール呼び出しの詳細を直接記述することなく、Goの抽象化されたインターフェースを通じてシステムコールを利用できます。

### 64-bitシステムと32-bit引数の扱い

64-bitアーキテクチャのシステムでは、CPUレジスタやメモリアドレス、一部のデータ型（例: `long`、`size_t`）が64-bit幅を持ちます。しかし、システムコールインターフェース（ABI: Application Binary Interface）は、歴史的経緯や互換性のために、64-bit値を2つの32-bit引数として渡すことを要求する場合があります。特に、初期の64-bitシステムや特定のOSでは、このような「分割渡し」の慣習が見られました。

*   **`uintptr`**: Go言語における`uintptr`型は、ポインタを保持できる符号なし整数型です。システムコールに引数を渡す際によく使用され、そのサイズは実行環境のポインタサイズ（32-bitシステムでは32-bit、64-bitシステムでは64-bit）に依存します。
*   **`offset >> 32`**: 64-bitの整数値 `offset` がある場合、`offset >> 32` はその値の上位32ビットを取り出すビットシフト演算です。例えば、`offset` が `0x123456789ABCDEF0` であれば、`offset >> 32` は `0x12345678` となります。この操作は、64-bit値を2つの32-bit引数としてシステムコールに渡す必要がある場合に用いられます。

### `Seek`システムコール

`Seek`（または`lseek`）システムコールは、オープンされたファイルの読み書き位置（ファイルポインタ）を変更するために使用されます。このシステムコールは通常、以下の3つの引数を取ります。

1.  ファイルディスクリプタ (file descriptor)
2.  オフセット (offset): ファイルポインタを移動させるバイト数。これは64-bit値であることが多いです。
3.  `whence`: オフセットの基準位置（ファイルの先頭、現在の位置、ファイルの末尾）。

このコミットの問題は、2番目のオフセット引数が64-bitシステム上で正しくOSに伝達されていなかった点にありました。

## 技術的詳細

このコミットの核心は、`mksyscall`ツールが64-bitシステム上で64-bit引数を正しく処理するように修正された点にあります。

### `mksyscall`の変更

`src/lib/syscall/mksyscall`ファイルでは、`$_32bit`という変数の初期化が変更されています。

```diff
--- a/src/lib/syscall/mksyscall
+++ b/src/lib/syscall/mksyscall
@@ -15,7 +15,7 @@

 $errors = 0;

+$_32bit = "";

 	$_32bit = "big-endian";
```

以前は `$_32bit = 0;` と初期化されていましたが、これが `$_32bit = "";` に変更されました。Perlスクリプトである`mksyscall`において、`0`は数値としてのゼロですが、`""`は空文字列です。この変更は、`mksyscall`が32-bit固有の処理を適用するかどうかを判断するロジックに影響を与えます。おそらく、以前の`0`という値が、意図せず32-bitモードを有効にするか、あるいは64-bitシステムであっても32-bit引数処理のロジックをトリガーする原因となっていたと考えられます。`""`にすることで、明示的に32-bitモードではないことを示し、64-bitシステムでは64-bit引数をそのまま扱うように`mksyscall`が生成するコードの挙動が変わったと推測されます。

### `zsyscall_darwin_amd64.go`と`zsyscall_linux_amd64.go`の変更

この`mksyscall`の変更の結果、`zsyscall_darwin_amd64.go`と`zsyscall_linux_amd64.go`で生成されるシステムコールラッパーのコードが大きく変更されました。

最も顕著な変更は、`lseek`, `ftruncate`, `pread`, `pwrite`, `truncate`, `Seek`, `SyncFileRange`, `Fallocate` などの関数において、64-bitオフセット引数を渡す際に使用されていた `uintptr(offset >> 32)` という部分が削除されたことです。

**変更前（例: `lseek`）:**
```go
func lseek(fd int, offset int64, whence int) (newoffset uintptr, errno int) {
	r0, r1, e1 := Syscall6(SYS_LSEEK, uintptr(fd), uintptr(offset), uintptr(offset >> 32), uintptr(whence), 0, 0);
	newoffset = uintptr(r0);
	errno = int(e1);
	return;
}
```
ここでは、`offset` (64-bit) が `uintptr(offset)` と `uintptr(offset >> 32)` の2つの引数に分割されて `Syscall6` に渡されています。これは、64-bit値を2つの32-bitレジスタまたはスタックスロットに分割して渡すことを想定したABIに対応するためのコードです。

**変更後（例: `lseek`）:**
```go
func lseek(fd int, offset int64, whence int) (newoffset uintptr, errno int) {
	r0, r1, e1 := Syscall(SYS_LSEEK, uintptr(fd), uintptr(offset), uintptr(whence));
	newoffset = uintptr(r0);
	errno = int(e1);
	return;
}
```
変更後では、`uintptr(offset >> 32)` が削除され、`offset` が単一の `uintptr(offset)` として渡されています。また、`Syscall6` から `Syscall` に変更されている点も重要です。`Syscall` は最大3つの引数を取るのに対し、`Syscall6` は最大6つの引数を取ります。この変更は、Goランタイムが64-bitアーキテクチャ上で、64-bitのオフセット値を単一の64-bitレジスタまたはスタックスロットとしてOSに渡せるようになったことを意味します。これは、OSのABIが64-bit引数を直接サポートしていることを前提としています。

同様の変更が、`Ftruncate`, `Pread`, `Pwrite`, `Truncate`, `Seek`, `SyncFileRange`, `Fallocate` など、64-bitオフセットや長さを引数として取る多くのシステムコールラッパーに適用されています。

### `TestSeek`の追加

`src/lib/os/os_test.go` に追加された `TestSeek` 関数は、この修正が正しく機能することを検証するための重要なテストです。特に、`1<<40` のような非常に大きなオフセット値（これは32-bit整数の最大値 `2^32-1` をはるかに超える）をテストケースに含めることで、64-bitオフセットが正確に処理されることを確認しています。

```go
	var tests = []test {
		// ... 既存のテストケース ...
		test{ 1<<40, 0, 1<<40 },
		test{ 1<<40, 2, 1<<40 + int64(len(data)) }
	};
```
これらのテストケースは、`Seek`関数が `1<<40` という大きなオフセットを正しく解釈し、ファイルポインタを期待される位置に移動できることを保証します。

## 前提知識の解説

### Goの`syscall`パッケージとシステムコール

Go言語の`syscall`パッケージは、Goプログラムからオペレーティングシステム（OS）のシステムコールを直接呼び出すための低レベルなインターフェースを提供します。システムコールは、ファイルI/O、ネットワーク通信、プロセス管理など、OSカーネルが提供する基本的なサービスを利用するための唯一の手段です。

### `mksyscall`ツール

`mksyscall`は、Goの`syscall`パッケージ内で使用されるGoコードを自動生成するためのツールです。OSのC言語ヘッダファイルやシステムコール定義を解析し、それに対応するGo言語のシステムコールラッパー関数（例: `zsyscall_darwin_amd64.go`, `zsyscall_linux_amd64.go` など）を生成します。これにより、開発者は各OSやアーキテクチャのシステムコール呼び出しの詳細を直接記述することなく、Goの抽象化されたインターフェースを通じてシステムコールを利用できます。

### 64-bitシステムと32-bit引数の扱い

64-bitアーキテクチャのシステムでは、CPUレジスタやメモリアドレス、一部のデータ型（例: `long`、`size_t`）が64-bit幅を持ちます。しかし、システムコールインターフェース（ABI: Application Binary Interface）は、歴史的経緯や互換性のために、64-bit値を2つの32-bit引数として渡すことを要求する場合があります。特に、初期の64-bitシステムや特定のOSでは、このような「分割渡し」の慣習が見られました。

*   **`uintptr`**: Go言語における`uintptr`型は、ポインタを保持できる符号なし整数型です。システムコールに引数を渡す際によく使用され、そのサイズは実行環境のポインタサイズ（32-bitシステムでは32-bit、64-bitシステムでは64-bit）に依存します。
*   **`offset >> 32`**: 64-bitの整数値 `offset` がある場合、`offset >> 32` はその値の上位32ビットを取り出すビットシフト演算です。例えば、`offset` が `0x123456789ABCDEF0` であれば、`offset >> 32` は `0x12345678` となります。この操作は、64-bit値を2つの32-bit引数としてシステムコールに渡す必要がある場合に用いられます。

### `Seek`システムコール

`Seek`（または`lseek`）システムコールは、オープンされたファイルの読み書き位置（ファイルポインタ）を変更するために使用されます。このシステムコールは通常、以下の3つの引数を取ります。

1.  ファイルディスクリプタ (file descriptor)
2.  オフセット (offset): ファイルポインタを移動させるバイト数。これは64-bit値であることが多いです。
3.  `whence`: オフセットの基準位置（ファイルの先頭、現在の位置、ファイルの末尾）。

このコミットの問題は、2番目のオフセット引数が64-bitシステム上で正しくOSに伝達されていなかった点にありました。

### `zsyscall_darwin_amd64.go`と`zsyscall_linux_amd64.go`の変更

この`mksyscall`の変更の結果、`zsyscall_darwin_amd64.go`と`zsyscall_linux_amd64.go`で生成されるシステムコールラッパーのコードが大きく変更されました。

**変更前（例: `lseek`）:**
```go

**変更後（例: `lseek`）:**

同様の変更が、`Ftruncate`, `Pread`, `Pwrite`, `Truncate`, `Seek`, `SyncFileRange`, `Fallocate` など、64-bitオフセットや長さを引数として取る多くのシステムコールラッパーに適用されています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`mksyscall`ツールが生成するシステムコールラッパーの引数処理の改善です。

1.  **`mksyscall`の`$_32bit`変数の変更**:
    `mksyscall`スクリプト内の`$_32bit`変数の初期値が`0`から空文字列`""`に変更されました。この変更は、`mksyscall`がシステムコールラッパーを生成する際に、64-bitシステム上で64-bit引数を32-bitとして扱うべきではないことを正しく認識させるためのものです。これにより、生成されるGoコードが、64-bit引数を分割せずに単一の`uintptr`として渡すように変わりました。

2.  **`zsyscall_darwin_amd64.go`および`zsyscall_linux_amd64.go`におけるシステムコール引数の簡素化**:
    `mksyscall`の変更により、`lseek`, `ftruncate`, `pread`, `pwrite`, `truncate`, `Seek`, `SyncFileRange`, `Fallocate`などのシステムコールラッパー関数において、64-bitオフセット引数（`int64`型）を渡す際に、以前は`uintptr(offset)`と`uintptr(offset >> 32)`のように上位32ビットと下位32ビットに分割して渡していた箇所が、`uintptr(offset)`のみを渡す形に修正されました。
    これは、64-bitアーキテクチャのOSが、システムコール引数として64-bit値を直接受け取れるABIを持っていることをGoランタイムが正しく利用できるようになったことを意味します。引数の数が減ったことで、`Syscall6`（6引数まで対応）から`Syscall`（3引数まで対応）への変更も行われています。これにより、システムコール呼び出しのオーバーヘッドがわずかに減少し、コードの可読性も向上します。

3.  **`TestSeek`による64-bitオフセットの検証**:
    `src/lib/os/os_test.go`に追加された`TestSeek`関数は、`os.File`の`Seek`メソッドが、特に`1<<40`のような非常に大きな64-bitオフセット値を正しく処理できることを確認します。このテストは、ファイルポインタが期待される位置に移動するかどうかを検証し、`mksyscall`の修正がファイルI/Oの正確性に貢献していることを保証します。

これらの変更により、Go言語のランタイムは64-bitシステム上で64-bit引数をより効率的かつ正確に扱うことができるようになり、大規模なファイル操作の信頼性が向上しました。

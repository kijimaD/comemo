# [インデックス 23812] ファイルの概要

このコミットは、Goコマンドのビルドロジックを司る`src/cmd/go/pkg.go`ファイルと、その挙動を検証するテストファイル`src/cmd/go/go_test.go`に影響を与えています。主要な変更は、`go`コマンドの`-a`フラグの挙動をGo 1.3以前のセマンティクスに戻し、ビルドIDに基づく再ビルド判定メカニズムを強化することにあります。

## 変更の背景

このコミットは、Goコマンドのビルドシステムにおける`-a`フラグの挙動を、Go 1.3以前の「すべてを再ビルドする」というシンプルな意味合いに戻すことを目的としています。Go 1.4で導入された`-a`フラグの例外的な挙動（標準ライブラリには適用しない）が、特定のユースケースで問題を引き起こしていました。

具体的には、以下の問題が挙げられます。

1.  **`go install -a ./...` の問題**: Go 1.4では、このコマンドが標準ライブラリを再ビルドしなかったため、異なるGoバージョン間でGOPATHを共有する際に問題が発生していました（コミットメッセージで #3036, #6534, #8290, #10702 を修正すると記載）。特に、Go 1.4でビルドされたパッケージがGo 1.5で再利用されると、ツールチェーンの不一致によりリンクエラーが発生する可能性がありました。
2.  **`go build -tags netgo -a myprog` の問題**: `netgo`タグは、`net`パッケージがCgoを使用するかどうかを制御します。Go 1.4の`-a`フラグの挙動では、標準ライブラリが再ビルドされないため、`netgo`タグ付きでビルドしようとしても、既存の非`netgo`バージョンの`net`パッケージが再利用されてしまい、意図した動作になりませんでした（コミットメッセージで #9369 を修正すると記載）。ユーザーはこれを回避するために`-installsuffix`という非直感的なフラグを使用する必要がありました。

これらの問題は、Goコマンドのビルド判定ロジックである`isStale`関数が、ファイルの更新時刻（mtime）のみに依存していたことに起因していました。mtimeベースの判定は、ファイルが削除された場合や、異なるツールチェーンでビルドされた場合など、多くのシナリオで不正確な結果を返すことがありました。

このコミットは、新たに導入された「ビルドID」メカニズムによって、これらの問題が`-a`フラグなしでも解決されるようになったため、`-a`フラグの特別な挙動を廃止し、より予測可能で理解しやすい挙動に戻すものです。ビルドIDは、ビルドの入力（ソースファイルリスト、依存関係のビルドID、ツールチェーンバージョンなど）のハッシュに基づいており、mtimeの限界を克服します。

## 前提知識の解説

### Goコマンドのビルドシステム

Go言語のビルドシステムは、`go build`や`go install`といったコマンドを通じて利用されます。これらのコマンドは、ソースコードをコンパイルし、実行可能ファイルやパッケージアーカイブ（`.a`ファイル）を生成します。効率的なビルドのために、Goコマンドは依存関係を分析し、変更されていないパッケージは再ビルドしないように最適化されています。

### パッケージの再ビルド判定 (`isStale`)

Goコマンドがパッケージを再ビルドする必要があるかどうかを判断するロジックは、内部的には`isStale`関数によって行われます。この関数は、インストール済みのパッケージやバイナリが、現在のソースコードやビルド環境に対して「古い」（stale）かどうかを判定します。

歴史的に、`isStale`は主にファイルの最終更新時刻（mtime）に基づいていました。しかし、mtimeベースの判定には以下のような多くの問題がありました。

*   **ファイルの削除**: パッケージ内のソースファイルが削除されても、残りのファイルのmtimeは変わらないため、`isStale`は変更を検出できませんでした。
*   **ファイルシステムによるmtimeの不正確さ**: 1秒単位のmtime粒度を持つファイルシステムでは、入力ファイルと出力ファイルのmtimeが同じになることがあり、再ビルドが必要なのにスキップされることがありました。
*   **バイナリ配布時のmtime**: バイナリ配布では、すべてのファイルのmtimeが同じに設定されることがあり、不必要な再ビルドや、書き込み権限がない場合のビルドエラーを引き起こす可能性がありました。
*   **ツールチェーンの変更**: 異なるGoバージョン間でGOPATHを共有する場合、ツールチェーンが変更されてもmtimeだけでは変更を検出できず、互換性のないオブジェクトファイルが再利用される問題がありました。

### ビルドID (Build IDs)

ビルドIDは、Go 1.5で導入された、パッケージのビルド入力のハッシュに基づいた識別子です。これはmtimeベースの判定の限界を克服するために考案されました。ビルドIDは、以下の要素をハッシュ化して生成されます。

*   **コンパイルされるソースファイルの一覧**: ファイルが追加または削除されたことを検出します。
*   **`runtime/zversion.go` の内容**: `runtime`パッケージのビルドIDにGoのバージョン情報を含めることで、ツールチェーンの変更を検出します。
*   **依存パッケージのビルドID**: 依存するパッケージのいずれかが変更された場合、その変更が現在のパッケージのビルドIDに反映され、再ビルドがトリガーされます。

これにより、Goコマンドは、ソースファイルの変更、依存関係の変更、さらにはGoツールチェーン自体の変更を正確に検出できるようになり、より信頼性の高い再ビルド判定が可能になりました。

### `-a` フラグ

`go`コマンドの`-a`フラグは、「強制的にすべてのパッケージを再ビルドする」という指示です。これは、`isStale`の判定が誤っていると思われる場合に、ユーザーが手動で再ビルドを強制するための「最後の手段」として使われてきました。

*   **Go 1.3まで**: `-a`は標準ライブラリを含むすべてのパッケージに適用され、文字通り「すべてを再ビルド」しました。
*   **Go 1.4**: `go install -a ./...` のようなコマンドで標準ライブラリが再ビルドされると、書き込み権限の問題が発生することがあったため、`-a`フラグは標準ライブラリには適用されないように変更されました。
*   **Go 1.5以降（このコミット）**: ビルドIDの導入により、`-a`フラグなしでも多くの問題が解決されたため、Go 1.3の挙動に戻され、再び標準ライブラリを含む「すべてを再ビルド」する意味を持つようになりました。

### `netgo` ビルドタグ

`netgo`はGoのビルドタグの一つで、`net`パッケージのビルド時にCgo（C言語との連携）を使用しないことを指示します。これにより、Cライブラリに依存しない完全に静的なバイナリを生成できます。`netgo`タグが指定されない場合、`net`パッケージはシステムにインストールされているCライブラリ（例: `libc`）を利用して名前解決などを行います。

## 技術的詳細

このコミットの核となる変更は、`src/cmd/go/pkg.go`ファイル内の`isStale`関数と`computeBuildID`関数のロジックにあります。

### `isStale`関数の変更

`isStale`関数は、パッケージが再ビルドを必要とするかどうかを判断する主要なロジックを含んでいます。このコミットにより、`isStale`の冒頭で`-a`フラグの処理が変更されました。

変更前（Go 1.4の挙動）は、標準ライブラリの場合に`-a`フラグを無視するロジックが含まれていました。
変更後（このコミット）は、`buildA`（`-a`フラグが指定されたかを示すグローバル変数）が`true`であれば、標準ライブラリであるかどうかにかかわらず、即座に`true`（再ビルドが必要）を返します。これにより、`-a`フラグはGo 1.3と同様に「すべてを再ビルドする」というシンプルな意味合いに戻りました。

また、ビルドIDに基づく再ビルド判定がmtimeベースの判定よりも優先されるようにロジックが再構成されました。

1.  **`-a`フラグによる強制再ビルド**: `buildA`が`true`の場合、無条件で`true`を返す。
2.  **ビルドIDの不一致**: インストール済みパッケージのビルドIDと、現在の入力から計算されたビルドIDが異なる場合、再ビルドが必要と判断する。これは、ソースファイルの削除、ビルドタグの変更、ツールチェーンの変更などを検出します。
3.  **依存パッケージの古さ**: 依存するパッケージのいずれかが`Stale`（古い）とマークされている場合、現在のパッケージも再ビルドが必要。
4.  **標準ライブラリの特別な扱い**: リリース版のGoを使用している場合、標準ライブラリについてはmtimeベースの判定をスキップし、ビルドIDベースの判定のみを適用します。これは、リリース版のGoのインストールプロセスがmtimeを適切に設定しない可能性があるためです。
5.  **mtimeベースの判定**: 上記のチェックを通過した後、最終的にmtimeに基づいて入力ファイル（ソースファイル、依存パッケージのターゲットファイル、コンパイラなど）がインストール済みパッケージよりも新しいかどうかをチェックします。

### `computeBuildID`関数の導入と役割

このコミットでは、`computeBuildID`関数が新たに導入され、`*Package`構造体の`buildID`フィールドを計算する責任を負います。以前は、`load`関数内で直接ビルドIDが計算されていましたが、これを独立した関数に切り出すことで、コードの可読性と保守性が向上しました。

`computeBuildID`は、以下の情報をSHA1ハッシュとして結合し、パッケージのビルドIDを生成します。

*   **`file %s\n`**: パッケージを構成するすべてのソースファイル（Goファイル、Cgoファイル、Cファイルなど）のファイル名リスト。これにより、ファイルの追加や削除が検出されます。
*   **`zversion %q\n`**: `runtime`パッケージの場合、`runtime/zversion.go`の内容を含めます。これはGoのバージョン情報を含んでおり、ツールチェーンの変更を検出するために使用されます。
*   **`dep %s %s\n`**: 依存する各パッケージのインポートパスと、その依存パッケージのビルドID。これにより、依存関係の変更が現在のパッケージのビルドIDに伝播し、連鎖的な再ビルドが可能になります。

このビルドIDメカニズムは、mtimeベースの判定が抱えていた多くの問題を解決し、Goコマンドのビルド判定をより堅牢で正確なものにしました。特に、異なるGoバージョン間でのGOPATHの共有や、`netgo`のようなビルドタグの利用が、`-a`フラグなしで正しく機能するようになりました。

## コアとなるコードの解説

### `src/cmd/go/pkg.go` の変更点

#### `load` 関数からのビルドID計算の分離

変更前:
```go
// Compute build ID for this package.
// ... (SHA1ハッシュ計算ロジック) ...
p.buildID = fmt.Sprintf("%x", h.Sum(nil))
return p
```

変更後:
```go
computeBuildID(p)
return p
```
この変更により、ビルドIDの計算ロジックが`load`関数から`computeBuildID`という独立した関数に切り出されました。これにより、`load`関数の責務が明確になり、コードのモジュール性が向上しました。

#### `isStale` 関数の変更

`isStale`関数は、パッケージが古いかどうかを判断するGoコマンドの核心部分です。このコミットで最も重要な変更がここにあります。

変更前（抜粋）:
```go
func isStale(p *Package) bool {
    // ...
    if p.Standard && (p.ImportPath == "unsafe" || buildContext.Compiler == "gccgo") {
        return false
    }
    // ...
    // If we are running a release copy of Go, do not rebuild the standard packages.
    // ...
    if isGoRelease && p.Standard {
        return false
    }

    // If the -a flag is given, rebuild everything (except standard packages; see above).
    if buildA {
        return true
    }
    // ...
}
```

変更後（抜粋）:
```go
func isStale(p *Package) bool {
    // ...
    if p.Standard && (p.ImportPath == "unsafe" || buildContext.Compiler == "gccgo") {
        return false
    }

    // If the -a flag is given, rebuild everything.
    if buildA {
        return true
    }

    // ... (ビルドIDに基づく判定がここに追加) ...
    targetBuildID, err := readBuildID(p)
    if err == nil && targetBuildID != p.buildID {
        return true
    }

    // ... (依存パッケージの古さ判定) ...

    // If we are running a release copy of Go and didn't find a content-based
    // reason to rebuild the standard packages, do not rebuild them.
    // ...
    if isGoRelease && p.Standard {
        return false
    }

    // Time-based staleness.
    built := fi.ModTime()
    // ... (mtimeに基づく判定) ...
}
```

主要な変更点は以下の通りです。

*   **`-a`フラグの挙動変更**: 変更後のコードでは、`buildA`が`true`の場合、`p.Standard`（標準ライブラリかどうか）のチェックをスキップして即座に`true`を返します。これにより、Go 1.4で導入された「標準ライブラリは`-a`の対象外」という例外が撤廃され、Go 1.3以前の「すべてを再ビルド」という挙動に戻りました。
*   **ビルドIDによる判定の優先**: `os.Stat(p.target)`でファイルの存在とmtimeをチェックする前に、`readBuildID(p)`で既存のビルドIDを読み込み、`p.buildID`（現在の入力から計算されたビルドID）と比較するロジックが追加されました。ビルドIDが一致しない場合、mtimeに関わらず再ビルドがトリガーされます。これは、mtimeベースの判定の弱点を補うための重要な変更です。
*   **標準ライブラリのmtime判定スキップ**: `isGoRelease && p.Standard`の条件が、ビルドIDによる判定の後に移動しました。これは、リリース版のGoでは標準ライブラリのmtimeが信頼できないため、ビルドIDによるコンテンツベースの判定が優先され、mtimeベースの判定はスキップされるべきであることを意味します。

#### `computeBuildID` 関数の新規定義

```go
// computeBuildID computes the build ID for p, leaving it in p.buildID.
// Build ID is a hash of the information we want to detect changes in.
// See the long comment in isStale for details.
func computeBuildID(p *Package) {
    h := sha1.New()

    // Include the list of files compiled as part of the package.
    // This lets us detect removed files. See issue 3895.
    inputFiles := stringList(
        p.GoFiles,
        p.CgoFiles,
        p.CFiles,
        p.CXXFiles,
        p.MFiles,
        p.HFiles,
        p.SFiles,
        p.SysoFiles,
        p.SwigFiles,
        p.SwigCXXFiles,
    )
    for _, file := range inputFiles {
        fmt.Fprintf(h, "file %s\n", file)
    }

    // Include the content of runtime/zversion.go in the hash
    // for package runtime. This will give package runtime a
    // different build ID in each Go release.
    if p.Standard && p.ImportPath == "runtime" {
        data, _ := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
        fmt.Fprintf(h, "zversion %q\n", string(data))
    }

    // Include the build IDs of any dependencies in the hash.
    // This, combined with the runtime/zversion content,
    // will cause packages to have different build IDs when
    // compiled with different Go releases.
    // This helps the go command know to recompile when
    // people use the same GOPATH but switch between
    // different Go releases. See issue 10702.
    // This is also a better fix for issue 8290.
    for _, p1 := range p.deps {
        fmt.Fprintf(h, "dep %s %s\n", p1.ImportPath, p1.buildID)
    }

    p.buildID = fmt.Sprintf("%x", h.Sum(nil))
}
```
この関数は、パッケージ`p`のビルドIDを計算し、`p.buildID`に設定します。SHA1ハッシュを使用して、以下の要素を結合しています。

*   **`inputFiles`**: パッケージを構成するすべてのソースファイルの名前をリスト化し、ハッシュに含めます。これにより、ソースファイルの追加や削除がビルドIDに影響を与え、再ビルドがトリガーされるようになります。これはIssue #3895（ファイルの削除が検出されない問題）への対応です。
*   **`runtime/zversion.go`**: `runtime`パッケージの場合、`runtime/zversion.go`ファイルの内容をハッシュに含めます。このファイルにはGoのバージョン情報が含まれており、Goのリリースバージョンが変わると`runtime`パッケージのビルドIDも変わるため、ツールチェーンの変更を検出できます。
*   **依存パッケージのビルドID**: パッケージ`p`が依存するすべてのパッケージ`p1`について、そのインポートパスと`p1.buildID`をハッシュに含めます。これにより、依存関係の変更が現在のパッケージのビルドIDに伝播し、連鎖的な再ビルドが可能になります。これはIssue #10702（異なるGoバージョン間でのGOPATH共有問題）およびIssue #8290（ツールチェーン変更時の再ビルド問題）への対応です。

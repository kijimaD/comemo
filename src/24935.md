# [インデックス 24935] ファイルの概要

このコミットは、Go言語の `encoding/xml` パッケージにおけるXMLデコーダの挙動を修正するものです。具体的には、ルート要素が適切に閉じられていない、あるいはその子孫要素が閉じられていないXML入力に対して、`xml.Decoder` の `Token` メソッドが `io.EOF` を返して成功とみなしてしまう問題を修正し、`SyntaxError` を返すように変更しています。

## 元コミット内容

`encoding/xml: Return SyntaxError for unmatched root start elements.`

現在、`xml.Decoder` の `Token` ルーチンは、ルート開始要素（および閉じられていない子孫要素）が適切に閉じられていないXML入力に対しても、成功裏に処理を終えていました。例えば、以下の全ての入力：

```xml
<root>
<root><foo>
<root><foo></foo>
```

は、`Token` が `nil` と `io.EOF` を返し、パースが成功したことを示していました。

この変更はそれを修正します。`RawToken` のセマンティクスはそのまま維持されます。

Fixes #11405

## 変更の背景

Go言語の `encoding/xml` パッケージは、XMLデータのエンコードとデコードを提供します。XMLは厳格な構造を持つマークアップ言語であり、開始タグと終了タグのペアが正しく対応している必要があります。しかし、このコミット以前の `xml.Decoder` の `Token` メソッドは、不完全なXML入力、特にルート要素やその子孫要素が閉じられていない場合に、エラーを報告せずに `io.EOF` を返していました。これは、XMLの構文規則に違反しているにもかかわらず、デコード処理が「成功」したと誤認される可能性があり、アプリケーションが不正なXMLを正常なものとして処理してしまうバグにつながる恐れがありました。

この問題は、`Fixes #11405` で示されているように、GoのIssueトラッカーで報告されたものです。開発者は、不完全なXML入力に対しては明確な構文エラーを返すことで、より堅牢なXML処理を期待していました。この変更は、このような不正なXML入力に対するデコーダの挙動を改善し、XMLの構文規則に厳密に従うようにすることで、開発者がXML処理の健全性をより確実に検証できるようにすることを目的としています。

## 前提知識の解説

*   **XML (Extensible Markup Language)**: 構造化されたデータを表現するためのマークアップ言語。開始タグと終了タグのペアで要素を定義し、階層構造を形成します。すべての開始タグには対応する終了タグが必要です。
*   **Go言語の `encoding/xml` パッケージ**: Go標準ライブラリの一部で、Goの構造体とXMLデータの間の変換（エンコード/デコード）を提供します。
*   **`xml.Decoder`**: XMLストリームを読み込み、トークン（開始要素、終了要素、文字データなど）に分割するための型です。
*   **`Decoder.Token()` メソッド**: `xml.Decoder` の主要なメソッドの一つで、XMLストリームから次のトークンを読み込みます。通常、有効なトークンと `nil` エラー、または `nil` トークンとエラー（`io.EOF` を含む）を返します。
*   **`io.EOF` (End Of File)**: 入力ストリームの終端に達したことを示すエラーです。通常、ストリームの正常な終了を示します。
*   **`SyntaxError`**: 構文解析中に発生したエラーを示す型です。XMLの構文規則に違反する入力があった場合に返されるべきエラーです。
*   **スタック (Stack)**: この文脈では、XMLデコーダが現在開いている要素の階層を追跡するために使用するデータ構造を指します。開始タグを読み込むたびにスタックに要素がプッシュされ、終了タグを読み込むたびにポップされます。スタックが空でない状態で `io.EOF` に達した場合、それは閉じられていない要素が存在することを示唆します。

## 技術的詳細

このコミットの核心は、`xml.Decoder` の `Token` メソッドにおけるエラー処理の改善です。以前のバージョンでは、XML入力が途中で終了し、まだ閉じられていない開始要素が存在する場合でも、`Token` メソッドは `io.EOF` を返して正常終了とみなしていました。これは、XMLの構文規則（すべての開始タグには対応する終了タグが必要）に反する挙動でした。

変更後のコードでは、`d.rawToken()` から `io.EOF` が返された際に、以下の条件をチェックします。

1.  `err == io.EOF`: `rawToken` がファイルの終端に達したことを報告している。
2.  `d.stk != nil`: デコーダの内部スタック `d.stk` が `nil` でない、つまり、まだ開いている要素が存在する可能性がある。
3.  `d.stk.kind != stkEOF`: スタックの最上位要素の種類が `stkEOF` でない。`stkEOF` はスタックが空であることを示す内部的な状態であり、これが `stkEOF` でないということは、スタックに未処理の開始要素が残っていることを意味します。

これらの条件がすべて真である場合、つまり、ファイルの終端に達したにもかかわらず、まだ閉じられていないXML要素がスタックに残っている場合、デコーダは `d.syntaxError("unexpected EOF")` を呼び出して `SyntaxError` を生成し、それを返します。これにより、不完全なXML入力が明確な構文エラーとして扱われるようになります。

`RawToken` メソッドのセマンティクスは変更されていません。`RawToken` はより低レベルなトークンを返し、構文の厳密なチェックは `Token` メソッドで行われるという役割分担が維持されています。

## コアとなるコードの解説

### `src/encoding/xml/xml.go` の変更点

`Decoder.Token()` メソッド内の変更は、`d.rawToken()` がエラーを返した場合の処理を強化しています。

```go
	} else if t, err = d.rawToken(); err != nil {
		if err == io.EOF && d.stk != nil && d.stk.kind != stkEOF {
			err = d.syntaxError("unexpected EOF")
		}
		return
	}
```

*   `else if t, err = d.rawToken(); err != nil { ... }`: `d.rawToken()` がトークンを正常に読み込めず、エラーを返した場合にこのブロックに入ります。
*   `if err == io.EOF && d.stk != nil && d.stk.kind != stkEOF { ... }`: ここが追加された条件分岐です。
    *   `err == io.EOF`: `rawToken` が入力の終わりに達したことを示しています。
    *   `d.stk != nil`: デコーダの内部スタック `d.stk` が初期化されており、要素を追跡している状態であることを確認します。
    *   `d.stk.kind != stkEOF`: スタックの最上位要素の種類が `stkEOF` でないことを確認します。`stkEOF` はスタックが空であることを示す内部的なマーカーです。これが `stkEOF` でないということは、まだ閉じられていない開始要素がスタックに残っていることを意味します。
*   `err = d.syntaxError("unexpected EOF")`: 上記の条件がすべて満たされた場合、つまり、XML入力が途中で終了し、閉じられていない要素が残っている場合に、`"unexpected EOF"` というメッセージを持つ `SyntaxError` を生成し、それを `err` 変数に代入します。
*   `return`: 最終的に、この `SyntaxError` が `Token` メソッドの呼び出し元に返されます。

この変更により、不完全なXML入力は `io.EOF` ではなく `SyntaxError` として報告されるようになり、アプリケーションはXMLの構文エラーを適切に検出できるようになります。

### `src/encoding/xml/xml_test.go` の変更点

`TestIssue11405` という新しいテスト関数が追加されました。

```go
func TestIssue11405(t *testing.T) {
	testCases := []string{
		"<root>",
		"<root><foo>",
		"<root><foo></foo>",
	}
	for _, tc := range testCases {
		d := NewDecoder(strings.NewReader(tc))
		var err error
		for {
			_, err = d.Token()
			if err != nil {
				break
			}
		}
		if _, ok := err.(*SyntaxError); !ok {
			t.Errorf("%s: Token: Got error %v, want SyntaxError", tc, err)
		}
	}
}
```

*   `testCases := []string{...}`: 閉じられていないルート要素や子要素を含む、不正なXML入力の文字列スライスを定義しています。これらは以前は `io.EOF` を返していましたが、修正後は `SyntaxError` を返すことが期待されます。
*   `for _, tc := range testCases { ... }`: 各テストケースに対してループ処理を行います。
*   `d := NewDecoder(strings.NewReader(tc))`: 各テストケース文字列から新しい `xml.Decoder` を作成します。
*   `for { _, err = d.Token(); if err != nil { break } }`: `Token()` メソッドをエラーが返されるまで繰り返し呼び出します。
*   `if _, ok := err.(*SyntaxError); !ok { ... }`: ここがテストの核心部分です。
    *   `err.(*SyntaxError)`: 返されたエラーが `*SyntaxError` 型に型アサーションできるか試みます。
    *   `!ok`: 型アサーションが失敗した場合（つまり、返されたエラーが `SyntaxError` でなかった場合）に真となります。
    *   `t.Errorf(...)`: 期待される `SyntaxError` ではなく、別のエラー（例えば `io.EOF`）が返された場合にテストを失敗させます。

このテストケースは、コミットによって導入された新しいエラー処理ロジックが、意図した通りに機能していることを検証します。

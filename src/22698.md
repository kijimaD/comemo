# [インデックス 22698] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net`パッケージのテストファイルである`src/net/dial_test.go`に対する変更です。具体的には、ネットワーク接続のタイムアウト時にファイルディスクリプタ（FD）が適切に閉じられることを検証する`TestDialTimeoutFDLeak`テストの信頼性を向上させることを目的としています。

## 変更の背景

`TestDialTimeoutFDLeak`テストは、`DialTimeout`関数がタイムアウトした場合に、使用されたファイルディスクリプタが適切にクリーンアップされ、リークしないことを検証するためのものです。しかし、このテストは特定のプラットフォーム（特にLinux以外）で不安定（flaky）であり、テストが成功したり失敗したりする状況が発生していました。

元の実装では、システム上のファイルディスクリプタの数を`numFD()`関数（Linuxでは`/proc/self/fd`を読み取る）で直接カウントしていました。この方法は、テスト環境の外部要因（他のプロセスやOSの挙動）に影響されやすく、またLinuxに特化していたため、他のOSではテストがスキップされるか、実装されていませんでした。

このコミットの目的は、テストの信頼性を高め、より多くのサポートされているプラットフォームで実行できるようにすることです。これにより、`DialTimeout`のFDリークに関する回帰バグが、より広範な環境で早期に検出できるようになります。コミットメッセージにある`Updates #4384`は、このテストの不安定性に関する既存の課題（issue）に対応していることを示唆しています。

## 前提知識の解説

### ファイルディスクリプタ (File Descriptor, FD)

ファイルディスクリプタは、Unix系オペレーティングシステムにおいて、プロセスが開いているファイルやソケット、パイプなどのI/Oリソースを識別するためにカーネルが割り当てる非負の整数値です。プログラムがファイルを開いたり、ネットワーク接続を確立したりするたびに、新しいFDが割り当てられます。FDは有限のリソースであり、適切に閉じられないと、利用可能なFDを使い果たしてしまい、新たなI/O操作ができなくなる「ファイルディスクリプタリーク（FD Leak）」という問題を引き起こす可能性があります。

### `DialTimeout`関数

Go言語の`net`パッケージには、ネットワーク接続を確立するための`Dial`関数群があります。その中でも`DialTimeout`は、指定されたネットワークアドレスへの接続を試み、設定されたタイムアウト期間内に接続が確立できない場合にエラーを返す関数です。この関数は、ネットワークの遅延や到達不能なホストへの接続試行など、様々な状況でタイムアウトが発生する可能性があります。タイムアウト時に、内部的に使用されたソケットや関連リソースが適切に閉じられ、FDがリークしないことが重要です。

### テストのFlakiness (不安定性)

ソフトウェアテストにおける「flakiness」とは、テストが同じコードベースに対して、実行するたびに成功と失敗を繰り返す現象を指します。これは、テストが外部環境（ネットワークの状態、OSのスケジューリング、他のプロセスの影響など）に依存していたり、非決定的な要素（並行処理のタイミング、乱数など）を含んでいたりする場合によく発生します。flakyなテストは、開発者がコードの変更が原因ではないにもかかわらずテストが失敗するため、信頼性が低く、開発効率を低下させます。

### `net/internal/socktest`パッケージ

`net/internal/socktest`は、Goの`net`パッケージ内部で使用されるテストユーティリティパッケージです。このパッケージは、実際のネットワーク操作を行わずに、ソケットのライフサイクルや挙動をシミュレート・制御するための機能を提供します。これにより、ネットワークの状態に依存しない、より安定したテストを作成することが可能になります。特に、ソケットの作成、接続、読み書き、クローズなどの各段階で、テストコードが介入し、エラーを注入したり、遅延をシミュレートしたりすることができます。

## 技術的詳細

このコミットの主要な技術的変更点は、`TestDialTimeoutFDLeak`テストが、プラットフォーム依存のFDカウントから、`net/internal/socktest`パッケージを用いたソケット操作のシミュレーションへと移行したことです。

1.  **`numFD()`関数の削除とプラットフォーム非依存化**:
    元のテストでは、`numFD()`というヘルパー関数を使用して、現在のプロセスが開いているファイルディスクリプタの数を取得していました。この関数はLinuxでは`/proc/self/fd`を読み取ることで実装されていましたが、他のOSでは実装されておらず、テストがスキップされる原因となっていました。このコミットでは`numFD()`関数が完全に削除され、テストはFDの実際の数に依存しない形に変更されました。

2.  **`net/internal/socktest`の導入**:
    テストは`net/internal/socktest`パッケージをインポートし、その機能を利用するようになりました。このパッケージは、ソケットのライフサイクルにおける特定のイベント（例: `FilterConnect`）でカスタムの動作を挿入できるフックを提供します。

3.  **`socktest.FilterConnect`による接続タイムアウトのシミュレーション**:
    新しいテストでは、`socktest.Set(socktest.FilterConnect, ...)`を使用して、ソケットの接続フェーズにフィルターを設定しています。このフィルターは、接続試行時に常に`errTimeout`を返し、かつ`time.Sleep(2 * T)`（`T`は100ミリ秒）で意図的な遅延を導入します。これにより、実際のネットワーク接続を試みることなく、`DialTimeout`関数が確実にタイムアウトエラーを返す状況をシミュレートします。この方法は、ネットワークの不安定性や外部要因に左右されずに、タイムアウト時のFDリークを検証できるため、テストの信頼性が大幅に向上します。

4.  **`testHookDialChannel`の利用（Plan 9/Windows向け）**:
    Plan 9やWindowsのような特定のOSでは、`socktest`が完全にサポートされていないか、挙動が異なる場合があります。これらのプラットフォーム向けに、`testHookDialChannel`というテストフックが使用されています。これは、`DialTimeout`が内部的にチャネルを介して接続試行を待機する際に、意図的に遅延を挿入するためのものです。これにより、これらのプラットフォームでもタイムアウトの状況をシミュレートし、テストの適用範囲を広げています。

5.  **FDリークの検証方法の変更**:
    元のテストでは、`DialTimeout`を多数回実行した後、`numFD()`でFDの総数をチェックし、リークがないことを確認していました。新しいテストでは、`socktest.Sockets()`を使用して、`socktest`が追跡しているソケットの数を、テスト実行前と実行後で比較します。これにより、テストによって開かれたソケットがすべて閉じられていることを、より正確かつプラットフォーム非依存な方法で検証します。

これらの変更により、`TestDialTimeoutFDLeak`は、実際のネットワーク状態やOSのFD管理に依存することなく、`DialTimeout`のタイムアウト処理におけるFDリークの有無を、より安定して、かつ広範なプラットフォームで検証できるようになりました。

## コアとなるコードの変更箇所

`src/net/dial_test.go`ファイルにおいて、主に以下の変更が行われています。

*   **インポートの変更**:
    *   `"io"`のインポートが削除されました。
    *   `"net/internal/socktest"`が新しくインポートされました。
*   **`TestDialTimeoutFDLeak`関数の大幅な書き換え**:
    *   `runtime.GOOS != "linux"`によるスキップロジックが削除され、`switch runtime.GOOS`によるプラットフォームごとの特殊な処理（Plan 9のスキップ、Plan 9/Windows向けの`testHookDialChannel`設定）が導入されました。
    *   `newLocalListener`による実際のリスナーの作成が削除されました。
    *   `DialTimeout`の呼び出しが、実際のネットワークアドレスではなく、ダミーの`"127.0.0.1:0"`に対して行われるようになりました。
    *   `socktest.Set(socktest.FilterConnect, ...)`によるソケットフィルターの設定が追加されました。
    *   `numFD()`の呼び出しと、それに基づくFD数の検証ロジックが削除されました。
    *   `socktest.Sockets()`を用いたソケット数の比較によるFDリークの検証ロジックが追加されました。
*   **`numFD()`関数の削除**:
    ファイルの末尾にあった`numFD()`関数が完全に削除されました。

## コアとなるコードの解説

変更後の`TestDialTimeoutFDLeak`のコア部分は以下のようになります。

```go
func TestDialTimeoutFDLeak(t *testing.T) {
	switch runtime.GOOS {
	case "plan9":
		t.Skipf("%s does not have full support of socktest", runtime.GOOS)
	}

	const T = 100 * time.Millisecond

	switch runtime.GOOS {
	case "plan9", "windows":
		origTestHookDialChannel := testHookDialChannel
		testHookDialChannel = func() { time.Sleep(2 * T) }
		defer func() { testHookDialChannel = origTestHookDialChannel }()
		if runtime.GOOS == "plan9" {
			break
		}
		fallthrough
	default:
		// socktest.FilterConnectを設定し、接続試行時にタイムアウトエラーを返すようにする
		sw.Set(socktest.FilterConnect, func(so *socktest.Status) (socktest.AfterFilter, error) {
			time.Sleep(2 * T) // 意図的な遅延を挿入
			return nil, errTimeout // タイムアウトエラーを返す
		})
		defer sw.Set(socktest.FilterConnect, nil) // テスト終了後にフィルターを解除
	}

	before := sw.Sockets() // テスト開始前のソケット数を取得
	const N = 100
	var wg sync.WaitGroup
	wg.Add(N)
	for i := 0; i < N; i++ {
		go func() {
			defer wg.Done()
			// このDialは、上記のソケットフィルターとテストフックにより、
			// SYNセグメントを送信し始めることはない。
			c, err := DialTimeout("tcp", "127.0.0.1:0", T) // ダミーアドレスへの接続を試行
			if err == nil {
				t.Errorf("unexpectedly established: tcp:%s->%s", c.LocalAddr(), c.RemoteAddr())
				c.Close()
			}
		}()
	}
	wg.Wait() // 全てのgoroutineの完了を待つ
	after := sw.Sockets() // テスト終了後のソケット数を取得
	if len(after) != len(before) {
		t.Errorf("got %d; want %d", len(after), len(before)) // ソケット数が変化していないことを検証
	}
}
```

このコードは、以下の点でFDリークテストの信頼性を向上させています。

*   **仮想的なタイムアウト**: `socktest.FilterConnect`を使用することで、実際のネットワーク接続を確立することなく、`DialTimeout`がタイムアウトする状況を強制的に作り出します。これにより、ネットワークの遅延や外部要因に左右されずに、タイムアウト処理のロジックを正確にテストできます。
*   **プラットフォーム非依存**: `numFD()`のようなOS固有のFDカウントメカニズムに依存せず、`socktest`が内部的に追跡するソケットの状態を比較することで、テストがより多くのプラットフォームで実行可能になりました。
*   **クリーンな状態の保証**: `defer sw.Set(socktest.FilterConnect, nil)`により、テスト終了後に設定したソケットフィルターが確実に解除され、他のテストに影響を与えないようにしています。
*   **正確なFDリーク検出**: `before := sw.Sockets()`と`after := sw.Sockets()`でテスト前後のソケット数を比較することで、テスト中に一時的に開かれたソケットがすべて閉じられていることを厳密に検証します。`len(after) != len(before)`が真であれば、それはFDリークが発生したことを意味します。

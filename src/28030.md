# [インデックス 28030] ファイルの概要

このコミットは、GoランタイムにおけるフリーなGoroutine（G）の管理方法を最適化するものです。具体的には、これまで単一のリストで管理されていたフリーなGを、「スタックを持つG」と「スタックを持たないG」の2つのリストに分割します。これにより、スタックを再利用できるGを優先的に割り当てることが可能になり、将来的なスタックの並行解放に向けた基盤を構築します。

## 元コミット内容

```
runtime: split gfree list into with-stacks and without-stacks

Currently all free Gs are added to one list. Split this into two
lists: one for free Gs with cached stacks and one for Gs without
cached stacks.

This lets us preferentially allocate Gs that already have a stack, but
more importantly, it sets us up to free cached G stacks concurrently.
```

## 変更の背景

Goランタイムでは、Goroutine（G）の生成と破棄が頻繁に行われます。Goroutineが終了すると、そのリソースはすぐに解放されるのではなく、将来の再利用のためにフリーリストに保持されることがあります。これにより、新しいGoroutineを生成する際のオーバーヘッド（メモリ割り当てなど）を削減し、パフォーマンスを向上させます。

このコミット以前は、すべてのフリーなGoroutineが単一の`gfree`リストで管理されていました。しかし、Goroutineにはスタックメモリが割り当てられており、Goroutineがフリーリストに戻される際にスタックが解放される場合と、キャッシュとして保持される場合があります。単一のリストでは、スタックを持つGoroutineと持たないGoroutineが混在するため、以下のような課題がありました。

1.  **スタック再利用の非効率性**: 新しいGoroutineが必要になった際、フリーリストから取得したGoroutineがスタックを持たない場合、新たにスタックを割り当てる必要がありました。これは、スタックが既に割り当てられているGoroutineを再利用するよりもコストがかかります。
2.  **スタック解放の複雑性**: スタックメモリの解放は、特に並行処理環境下では複雑な問題です。単一のリストでは、スタックを持つGoroutineと持たないGoroutineを区別してスタックを並行して解放するメカニズムを導入するのが困難でした。

この変更は、これらの課題に対処し、Goroutineのライフサイクル管理をより効率的かつ柔軟にするために導入されました。特に、スタックを持つGoroutineを優先的に再利用することで、メモリ割り当てのオーバーヘッドを削減し、Goroutineの起動レイテンシを改善することを目的としています。さらに、スタックの並行解放という将来的な最適化への道を開く重要なステップでもあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

### Goroutine (G)

Goにおける軽量な実行スレッドです。数KB程度の小さなスタックから始まり、必要に応じてスタックサイズを動的に増減させます。Goプログラムの並行処理の基本単位であり、Goランタイムのスケジューラによって管理されます。

### スタック

Goroutineが関数呼び出しの情報を格納するために使用するメモリ領域です。Goのスタックは動的に伸縮可能であり、Go 1.4以降は連続したメモリ領域を使用する「連続スタック（contiguous stack）」が採用されています。これにより、スタックの成長や縮小がより効率的に行われます。

### スケジューラ (Scheduler)

Goランタイムのスケジューラは、GoroutineをOSスレッド（M: Machine）にマッピングし、実行を管理します。P（Processor）と呼ばれる論理プロセッサを介して、Goroutineの実行、停止、再開、およびMへの割り当てを調整します。

### `gfree` リスト

Goランタイムが終了したGoroutineを再利用のために保持しておくフリーリストです。新しいGoroutineが必要になった際に、このリストから既存のGoroutineを再利用することで、メモリ割り当てのコストを削減します。

### `g` 構造体

Goroutineの状態を表すランタイム内部の構造体です。スタック情報（`stack.lo`, `stack.hi`）、スケジューリング関連のリンク（`schedlink`）、現在の状態などが含まれます。

### `p` 構造体

論理プロセッサを表す構造体で、ローカルなGoroutineキューやフリーなGoroutineのキャッシュ（`_p_.gfree`）などを持ちます。

### `schedt` 構造体

グローバルなスケジューラの状態を保持する構造体です。グローバルなフリーGoroutineリスト（このコミット以前は`sched.gfree`）やロック（`sched.gflock`）などが含まれます。

## 技術的詳細

このコミットの核心は、GoランタイムがフリーなGoroutineを管理する方法の変更にあります。以前は、`schedt`構造体内の`gfree`という単一のリストが、スタックを持つGoroutineと持たないGoroutineの両方を保持していました。この変更により、`gfree`は以下の2つのリストに分割されます。

1.  **`sched.gfreeStack`**: スタックメモリがまだ割り当てられているフリーなGoroutineを格納するリスト。
2.  **`sched.gfreeNoStack`**: スタックメモリが既に解放されているフリーなGoroutineを格納するリスト。

この分割によって、GoランタイムはGoroutineの再利用戦略をより洗練させることができます。

### Goroutineの解放 (`gfput`)

Goroutineが終了し、フリーリストに戻される際（`gfput`関数）、そのGoroutineがスタックを持っているかどうか（`gp.stack.lo == 0`で判断）に基づいて、適切なリスト（`sched.gfreeStack`または`sched.gfreeNoStack`）に追加されるようになります。これにより、リストに格納される時点でGoroutineのスタック状態が明確に区別されます。

### Goroutineの取得 (`gfget`)

新しいGoroutineが必要になった際（`gfget`関数）、ランタイムはまず`_p_.gfree`（Pローカルなフリーリスト）を確認します。Pローカルなリストが空の場合、グローバルなフリーリストからGoroutineを取得しようとします。この際、**`sched.gfreeStack`から優先的にGoroutineを取得する**ようになります。これは、スタックが既に割り当てられているGoroutineを再利用する方が、新しいスタックを割り当てるよりも効率的であるためです。`sched.gfreeStack`が空の場合にのみ、`sched.gfreeNoStack`からGoroutineを取得します。`sched.gfreeNoStack`から取得したGoroutineには、実行前に新しいスタックを割り当てる必要があります。

### スタックの並行解放への準備

この変更のもう一つの重要な側面は、**スタックの並行解放**に向けた基盤を構築することです。スタックを持つGoroutineと持たないGoroutineが明確に分離されたことで、ランタイムは将来的に、`sched.gfreeStack`にあるGoroutineのスタックを、Goroutine自体の再利用とは独立して、並行して解放するメカニズムを導入できるようになります。これにより、メモリ使用量の最適化と、ガベージコレクションの効率化が期待されます。

### 性能への影響

*   **Goroutine起動の高速化**: スタックを持つGoroutineを優先的に再利用することで、スタック割り当てのオーバーヘッドが削減され、Goroutineの起動レイテンシが改善されます。これは、特にGoroutineの生成と破棄が頻繁に行われるアプリケーションにおいて顕著な性能向上をもたらす可能性があります。
*   **メモリ効率の向上**: スタックの並行解放が可能になることで、不要になったスタックメモリをより迅速にシステムに返却できるようになり、全体的なメモリ効率が向上します。

このコミットは、GoランタイムのGoroutine管理における重要な最適化であり、Goプログラムのパフォーマンスと効率性をさらに高めるための基盤を強化するものです。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  `src/runtime/proc.go`: Goroutineのライフサイクル管理（解放と取得）を行う関数が含まれています。
2.  `src/runtime/runtime2.go`: ランタイムの主要なデータ構造（`schedt`など）が定義されています。

具体的な変更箇所は以下の通りです。

*   `src/runtime/proc.go`内の`gfput`関数: フリーなGoroutineをリストに追加するロジックが変更されました。
*   `src/runtime/proc.go`内の`gfget`関数: フリーなGoroutineをリストから取得するロジックが変更されました。
*   `src/runtime/proc.go`内の`gfpurge`関数: PローカルなフリーリストからグローバルなフリーリストへGoroutineを移動させるロジックが変更されました。
*   `src/runtime/runtime2.go`内の`schedt`構造体: グローバルなフリーGoroutineリストの定義が変更されました。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の変更

`schedt`構造体は、Goスケジューラのグローバルな状態を保持します。このコミットにより、`gfree`という単一のポインタが、`gfreeStack`と`gfreeNoStack`の2つのポインタに置き換えられました。

```go
// Old:
// gflock mutex
// gfree  *g
// ngfree int32

// New:
gflock       mutex
gfreeStack   *g    // スタックを持つフリーなGのリスト
gfreeNoStack *g    // スタックを持たないフリーなGのリスト
ngfree       int32 // フリーなGの総数 (変更なし)
```

この変更により、ランタイムはGoroutineのスタック状態に基づいて、異なるフリーリストを管理できるようになります。

### `src/runtime/proc.go` の変更

#### `gfput(_p_ *p, gp *g)` 関数

この関数は、Goroutine `gp` をフリーリストに戻す際に呼び出されます。変更前は、単に`sched.gfree`リストに追加していました。変更後は、`gp.stack.lo == 0`（スタックを持たないことを意味する）かどうかをチェックし、`sched.gfreeNoStack`または`sched.gfreeStack`のいずれかにGoroutineを追加します。

```go
// 変更前 (簡略化)
// gp.schedlink.set(sched.gfree)
// sched.gfree = gp

// 変更後
if gp.stack.lo == 0 { // スタックを持たない場合
    gp.schedlink.set(sched.gfreeNoStack)
    sched.gfreeNoStack = gp
} else { // スタックを持つ場合
    gp.schedlink.set(sched.gfreeStack)
    sched.gfreeStack = gp
}
```

#### `gfget(_p_ *p) *g` 関数

この関数は、フリーリストからGoroutineを取得する際に呼び出されます。変更前は、`sched.gfree`からGoroutineを取得していました。変更後は、まず`sched.gfreeStack`からGoroutineを取得しようと試み、それが空の場合に`sched.gfreeNoStack`から取得します。

```go
// 変更前 (簡略化)
// if gp == nil && sched.gfree != nil {
//     // sched.gfree から Goroutine を取得
// }

// 変更後
if gp == nil && (sched.gfreeStack != nil || sched.gfreeNoStack != nil) {
    lock(&sched.gflock)
    for _p_.gfreecnt < 32 { // Pローカルなキャッシュを埋めるループ
        if sched.gfreeStack != nil {
            // スタックを持つGを優先的に取得
            gp = sched.gfreeStack
            sched.gfreeStack = gp.schedlink.ptr()
        } else if sched.gfreeNoStack != nil {
            // スタックを持つGがない場合、スタックを持たないGを取得
            gp = sched.gfreeNoStack
            sched.gfreeNoStack = gp.schedlink.ptr()
        } else {
            break // 両方のリストが空の場合
        }
        // 取得したGをPローカルなフリーリストに追加
        _p_.gfreecnt++
        sched.ngfree--
        gp.schedlink.set(_p_.gfree)
        _p_.gfree = gp
    }
    unlock(&sched.gflock)
    goto retry
}
```
このロジックにより、スタックを持つGoroutineが優先的に再利用され、スタック割り当てのコストが削減されます。

#### `gfpurge(_p_ *p)` 関数

この関数は、PローカルなフリーリストからGoroutineをグローバルなフリーリストに移動させる際に呼び出されます。`gfput`と同様に、Goroutineのスタック状態に基づいて、`sched.gfreeNoStack`または`sched.gfreeStack`のいずれかにGoroutineを追加します。

```go
// 変更前 (簡略化)
// gp.schedlink.set(sched.gfree)
// sched.gfree = gp

// 変更後
if gp.stack.lo == 0 { // スタックを持たない場合
    gp.schedlink.set(sched.gfreeNoStack)
    sched.gfreeNoStack = gp
} else { // スタックを持つ場合
    gp.schedlink.set(sched.gfreeStack)
    sched.gfreeStack = gp
}
```

これらの変更により、GoランタイムはフリーなGoroutineをより効率的に管理し、スタックの再利用を最適化できるようになりました。

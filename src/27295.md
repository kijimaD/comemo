# [インデックス 27295] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるメソッドの重複チェックロジックのバグを修正します。具体的には、レシーバの型が同じであれば、レシーバ名が異なっていてもメソッドが重複していると誤って判断しないように、`addmethod`関数でのチェックを調整します。この問題は、`Eqtype`のセマンティクス変更と、`GO_GCFLAGS=-newexport`を使用したコンパイラのブートストラッププロセス中に、古いエクスポートデータと新しいエクスポートデータが混在する状況で顕在化しました。

## 変更の背景

この変更は、Goコンパイラにおけるメソッドの重複チェックに関する意図しない回帰バグを修正するために行われました。

問題の根本原因は、以前のコミットである`golang.org/cl/20602`にあります。このコミットでは、Goコンパイラの型等価性チェックを行う`Eqtype`関数のセマンティクスが変更されました。具体的には、`Eqtype`がレシーバパラメータの型等価性をチェックするのをやめ、その責任を`addmethod`関数（`Eqtype`の呼び出し元で唯一レシーバパラメータを気にする関数）に移行しました。

しかし、この変更の際に、`addmethod`でのチェックが意図せず厳しくなり、レシーバ名が完全に一致することを要求するようになってしまいました。通常、エクスポートデータ内のレシーバ名は元のソースと常に一致するため、これは問題になりません。

この問題が顕在化したのは、`GO_GCFLAGS=-newexport ./all.bash`を実行した際でした。このコマンドは、Goコンパイラのブートストラッププロセスの一部であり、`newexport`形式のエクスポートデータを使用するようにコンパイラをビルドする際に用いられます。このプロセス中に、`sync`パッケージに対して古い形式と新しい形式のエクスポートデータの両方をロードしようとすると、レシーバ名の不一致が原因でメソッドの重複エラーが発生しました。これは`golang.org/issue/14877`として報告された問題です。

このコミットは、`addmethod`がレシーバ名ではなく、レシーバの**型**のみを比較するように修正することで、この回帰バグを解決します。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するプログラムです。`src/cmd/compile`ディレクトリにそのソースコードがあります。コンパイラは、字句解析、構文解析、型チェック、最適化、コード生成など、複数のフェーズを経て動作します。

### `Eqtype`関数

`Eqtype`はGoコンパイラ内部で使用される関数で、2つの型が等しいかどうかを判断します。Go言語では、型の等価性は厳密に定義されており、例えば構造体のフィールドの型や順序、関数の引数と戻り値の型などが一致する必要があります。メソッドの型等価性をチェックする際にも、レシーバの型が重要な要素となります。

### `addmethod`関数

`addmethod`は、Goコンパイラが型にメソッドを追加する際に使用される内部関数です。Goの型システムでは、メソッドは特定の型に関連付けられます。`addmethod`は、新しいメソッドを型に追加する前に、そのメソッドが既に存在しないか（つまり重複していないか）をチェックする責任も持ちます。この重複チェックの際に、レシーバの型や名前が考慮されます。

### レシーバパラメータ

Go言語のメソッドは、特別な引数である「レシーバ」を持ちます。例えば、`func (r MyType) MyMethod()`というメソッド定義では、`r MyType`がレシーバパラメータです。`r`はレシーバ変数名、`MyType`はレシーバの型です。レシーバは、メソッドがどの型の値に対して呼び出されるかを指定します。

### エクスポートデータ (Export Data)

Goコンパイラは、コンパイル済みのパッケージの公開（エクスポート）された宣言（型、関数、変数、メソッドなど）に関する情報を「エクスポートデータ」として生成します。このデータは、他のパッケージがそのパッケージをインポートする際に、型チェックやコード生成のために利用されます。これにより、コンパイラはインポートされたパッケージのソースコードを再解析することなく、そのAPI情報を効率的に取得できます。

### `newexport`形式

`newexport`は、Goコンパイラのエクスポートデータの新しい形式を指します。Goコンパイラは、ビルド速度の向上などの目的で、エクスポートデータの形式を改良することがあります。`newexport`形式は、特にインデックス構造を導入することで、大規模なパッケージをインポートする際の効率的なアクセスを可能にしました。

### `GO_GCFLAGS=-newexport ./all.bash`

`GO_GCFLAGS=-newexport`は、Goコンパイラに`newexport`形式のエクスポートデータを使用するように指示するフラグです。`./all.bash`は、Goのソースツリー全体をビルドし、テストを実行するためのスクリプトです。このコマンドを組み合わせることで、Goコンパイラ自体を`newexport`形式でビルドし、その新しいコンパイラで他のパッケージをコンパイルする、いわゆる「ブートストラップ」プロセスが実行されます。このプロセス中に、古いコンパイラが生成したエクスポートデータと新しいコンパイラが生成したエクスポートデータが混在する状況が発生し、今回の問題が顕在化しました。

## 技術的詳細

このコミットが修正する問題は、`src/cmd/compile/internal/gc/dcl.go`ファイル内の`addmethod`関数に存在しました。

`addmethod`関数は、新しいメソッドを型に追加する際に、同じ名前とシグネチャを持つメソッドが既に存在しないかを確認します。以前の`golang.org/cl/20602`の変更により、`Eqtype`関数はレシーバパラメータ全体の型等価性チェックを行わなくなり、その責任が`addmethod`に移されました。

`addmethod`内の関連するコードスニペットは以下のようになります（変更前）：

```go
		// Eqtype only checks that incoming and result parameters match,
		// so explicitly check that the receiver parameters match too.
		if !Eqtype(t, f.Type) || !Eqtype(t.Recvs(), f.Type.Recvs()) {
			Yyerror("method redeclared: %v.%v\n\t%v\n\t%v", pa, msym, f.Type, t)
		}
```

ここで、`t`は現在追加しようとしているメソッドの型、`f.Type`は既に存在するメソッドの型を表します。
`!Eqtype(t, f.Type)`は、メソッドのシグネチャ（引数と戻り値の型）が異なる場合に真となります。
問題は`!Eqtype(t.Recvs(), f.Type.Recvs())`の部分でした。`t.Recvs()`はレシーバパラメータのリストを返します。このリストには、レシーバの型だけでなく、レシーバ名も含まれる可能性があります。`Eqtype`がこのレシーバパラメータのリスト全体を比較する際、レシーバ名が異なると、たとえレシーバの型が同じであっても、異なるレシーバパラメータと判断してしまいました。

この厳しすぎるチェックが、`GO_GCFLAGS=-newexport`のブートストラッププロセス中に問題を引き起こしました。古いエクスポートデータと新しいエクスポートデータの間で、レシーバ名に関する微妙な違いがあった場合、コンパイラは同じメソッドを異なるものと誤解し、「メソッドの再宣言」エラーを報告してしまったのです。

Go言語のセマンティクスでは、メソッドの重複はレシーバの**型**とメソッド名、そしてシグネチャによって判断されるべきであり、レシーバ名自体はメソッドの識別には影響しません（レシーバ名はメソッド内で使用されるローカル変数名のようなものです）。

## コアとなるコードの解説

変更は`src/cmd/compile/internal/gc/dcl.go`ファイルの`addmethod`関数内の1行です。

変更前:
```go
		if !Eqtype(t, f.Type) || !Eqtype(t.Recvs(), f.Type.Recvs()) {
```

変更後:
```go
		if !Eqtype(t, f.Type) || !Eqtype(t.Recv().Type, f.Type.Recv().Type) {
```

この変更の核心は、`t.Recvs()`と`f.Type.Recvs()`の比較を、`t.Recv().Type`と`f.Type.Recv().Type`の比較に置き換えた点です。

*   `t.Recvs()`: これはメソッドのレシーバパラメータのリスト全体を返します。これにはレシーバ名も含まれる可能性があります。
*   `t.Recv()`: これはメソッドの単一のレシーバパラメータを返します。
*   `t.Recv().Type`: これはレシーバパラメータの**型**のみを返します。

したがって、変更後のコードでは、`addmethod`はメソッドのシグネチャ（`!Eqtype(t, f.Type)`）が異なるか、またはレシーバの**型**（`!Eqtype(t.Recv().Type, f.Type.Recv().Type)`）が異なる場合にのみ、メソッドが重複していると判断します。これにより、レシーバ名が異なっていてもレシーバの型が同じであれば、正しく同じメソッドとして扱われるようになり、意図しない「メソッドの再宣言」エラーが解消されました。

この修正は、Go言語のメソッドの重複に関するセマンティクスに合致しており、コンパイラの堅牢性を向上させます。

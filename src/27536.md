# [インデックス 27536] ファイルの概要

このコミットは、GoコンパイラのAMD64アーキテクチャ向けSSA（Static Single Assignment）バックエンドにおける最適化を導入しています。具体的には、メモリのロード（読み込み）およびストア（書き込み）操作の前にインデックスを計算するために使用される左シフト（`SHLQ`）命令を、ロード/ストア命令自体に統合することで、生成される機械語コードの効率を向上させています。これにより、命令数の削減とバイナリサイズの縮小が実現されます。

## 変更の背景

Goコンパイラは、生成されるバイナリのサイズと実行速度の両方を最適化することを目指しています。このコミットの背景には、AMD64アーキテクチャにおいて、配列のインデックス計算で頻繁に発生する特定のパターンを効率化したいという意図があります。

具体的には、Goのプログラムが配列やスライスにアクセスする際、インデックス `i` と要素のサイズ `S` を用いてメモリアドレス `base + i * S` を計算する必要があります。この `i * S` の計算は、多くの場合、`i << log2(S)` のような左シフト命令として表現されます（例: `S=4` なら `i << 2`）。

従来のコンパイラでは、このシフト操作が独立した命令として生成され、その後にロード/ストア命令が続くことがありました。しかし、AMD64アーキテクチャには、ベースアドレス、インデックスレジスタ、スケールファクタ（1, 2, 4, 8）を直接指定できる「スケール付きインデックスアドレッシングモード」が存在します。このアドレッシングモードを利用すれば、シフト命令を別途発行することなく、ロード/ストア命令内でインデックスのスケーリングを同時に実行できます。

コミットメッセージにある「Very common, cuts about 70k from pkg/tools/linux_amd64/* binaries.」という記述は、この最適化パターンが非常に頻繁に現れること、そしてその最適化が`pkg/tools/linux_amd64/*`バイナリから約70KBものサイズ削減をもたらすことを示しています。これは、命令数の削減がバイナリサイズに直接影響し、結果として実行時のパフォーマンス向上にも寄与することを示唆しています。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現（IR）に変換します。Go 1.7以降、主要な最適化フェーズではSSA（Static Single Assignment）形式が採用されています。SSA形式では、各変数が一度だけ代入されるという特性があり、データフロー解析や様々な最適化（定数伝播、デッドコード削除、共通部分式除去など）を効率的に行うことができます。SSAバックエンドは、このSSA形式のIRを特定のCPUアーキテクチャ（例: AMD64）の機械語命令に変換する役割を担います。

### AMD64アドレッシングモード

AMD64（x86-64）アーキテクチャは、メモリにアクセスするための多様なアドレッシングモードを提供します。その中でも特に重要なのが「ベース＋インデックス＋スケール＋ディスプレイスメント」形式のアドレッシングモードです。
`[base + index*scale + displacement]`
- `base`: ベースアドレスを保持するレジスタ。
- `index`: インデックスを保持するレジスタ。
- `scale`: インデックスに掛けられる定数（1, 2, 4, 8のいずれか）。これは配列の要素サイズに対応します。
- `displacement`: 定数オフセット。
このアドレッシングモードは、配列の要素にアクセスする際に非常に効率的であり、`base`が配列の先頭アドレス、`index`が配列の添字、`scale`が要素のサイズに対応します。

### SHLQ命令

`SHLQ`は"Shift Left Quadword"の略で、AMD64アーキテクチャにおける64ビット値を左にシフトする命令です。例えば、`SHLQ $2, %rax` は`%rax`レジスタの値を2ビット左にシフトします。これは、`%rax`の値を4倍することに相当します。配列のインデックス計算で、要素サイズが2の冪乗である場合に、乗算の代わりにシフトが用いられるのは一般的な最適化手法です。

### コンパイラ最適化ルール

GoコンパイラのSSAバックエンドでは、`*.rules`ファイルに記述されたルールに基づいて、SSA形式のIRをより効率的なIRに変換したり、最終的な機械語命令に近づけたりする最適化が行われます。これらのルールは、特定のSSA操作のパターンを検出し、それを別のより効率的なSSA操作のパターンに書き換えるものです。`rewriteAMD64.go`のようなファイルは、これらのルールをGoコードとして実装し、SSAグラフのノードを走査してパターンマッチングと書き換えを実行します。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるパターンマッチングと書き換えの強化です。具体的には、以下のSSA操作の組み合わせを検出し、より効率的な単一の操作に変換します。

1.  **`SHLQconst` 操作の検出**:
    `SHLQconst [N] idx` は、インデックス `idx` を定数 `N` ビットだけ左シフトする操作を表します。`N`が1, 2, 3の場合、それぞれ2倍、4倍、8倍に相当し、これはGoの`int16` (2バイト), `int32` (4バイト), `int64`/ポインタ (8バイト) の要素サイズに対応します。

2.  **`loadidx1` / `storeidx1` 操作との結合**:
    `MOVWloadidx1`, `MOVLloadidx1`, `MOVQloadidx1` (ロード操作) や `MOVWstoreidx1`, `MOVLstoreidx1`, `MOVQstoreidx1`, `MOVWstoreconstidx1`, `MOVLstoreconstidx1`, `MOVQstoreconstidx1` (ストア操作) は、インデックス付きアドレッシングモードを使用するメモリ操作を表します。`idx1`というサフィックスは、インデックスがまだスケーリングされていない状態、またはデフォルトのスケール1で扱われている状態を示唆します。

このコミットは、`SHLQconst`でスケーリングされたインデックスが、直後に`loadidx1`または`storeidx1`操作で使用されるパターンを認識します。そして、この2つの操作を、AMD64のスケール付きインデックスアドレッシングモードを直接利用する新しい`loadidxN`または`storeidxN`操作に変換します。ここで`N`はスケールファクタ（2, 4, 8）を表します。

例えば、32ビット値（`MOVL`）をロードする際に、インデックスが2ビット左シフト（4倍）されている場合、
`(MOVLloadidx1 [c] {sym} ptr (SHLQconst [2] idx) mem)`
というSSAパターンは、
`(MOVLloadidx4 [c] {sym} ptr idx mem)`
というパターンに書き換えられます。

この書き換えにより、`SHLQconst`命令が独立して生成されることがなくなり、ロード/ストア命令がインデックスのスケーリングを内部的に処理するようになります。結果として、生成されるアセンブリコードから不要なシフト命令が削除され、命令数が減少し、バイナリサイズが小さくなります。これは、コンパイラの「peephole optimization」（局所的な最適化）の一種であり、特定の命令シーケンスをより効率的なシーケンスに置き換えるものです。

## コアとなるコードの変更箇所

このコミットは主に以下の2つのファイルに影響を与えています。

1.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`**:
    このファイルには、AMD64アーキテクチャ向けのSSA書き換えルールが定義されています。コミットでは、`SHLQconst`と`loadidx1`/`storeidx1`の組み合わせを検出して、対応する`loadidxN`/`storeidxN`に変換する新しいルールが追加されています。

    追加されたルールの例:
    ```
    // combine SHLQ into indexed loads and stores
    (MOVWloadidx1 [c] {sym} ptr (SHLQconst [1] idx) mem) -> (MOVWloadidx2 [c] {sym} ptr idx mem)
    (MOVLloadidx1 [c] {sym} ptr (SHLQconst [2] idx) mem) -> (MOVLloadidx4 [c] {sym} ptr idx mem)
    (MOVQloadidx1 [c] {sym} ptr (SHLQconst [3] idx) mem) -> (MOVQloadidx8 [c] {sym} ptr idx mem)
    (MOVWstoreidx1 [c] {sym} ptr (SHLQconst [1] idx) val mem) -> (MOVWstoreidx2 [c] {sym} ptr idx val mem)
    (MOVLstoreidx1 [c] {sym} ptr (SHLQconst [2] idx) val mem) -> (MOVLstoreidx4 [c] {sym} ptr idx val mem)
    (MOVQstoreidx1 [c] {sym} ptr (SHLQconst [3] idx) val mem) -> (MOVQstoreidx8 [c] {sym} ptr idx val mem)
    (MOVWstoreconstidx1 [c] {sym} ptr (SHLQconst [1] idx) mem) -> (MOVWstoreconstidx2 [c] {sym} ptr idx mem)
    (MOVLstoreconstidx1 [c] {sym} ptr (SHLQconst [2] idx) mem) -> (MOVLstoreconstidx4 [c] {sym} ptr idx mem)
    (MOVQstoreconstidx1 [c] {sym} ptr (SHLQconst [3] idx) mem) -> (MOVQstoreconstidx8 [c] {sym} ptr idx mem)
    ```
    これらのルールは、それぞれ16ビット（`MOVW`）、32ビット（`MOVL`）、64ビット（`MOVQ`）のデータ型に対するロード/ストア操作と、対応するシフト量（1, 2, 3ビット）を結合するものです。

2.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`**:
    このファイルは、`AMD64.rules`ファイルで定義されたルールに基づいて自動生成されるか、手動で実装されるSSA書き換えロジックを含んでいます。コミットでは、`MOVLloadidx1`, `MOVLstoreconstidx1`, `MOVLstoreidx1`, `MOVQloadidx1`, `MOVQstoreconstidx1`, `MOVQstoreidx1`, `MOVWloadidx1`, `MOVWstoreconstidx1`, `MOVWstoreidx1`といった既存のSSA操作の書き換え関数内に、`SHLQconst`パターンを検出して新しい`loadidxN`/`storeidxN`操作に変換する新しい`match`ブロックが追加されています。

    例として、`rewriteValueAMD64_OpAMD64MOVLloadidx1`関数内の変更は以下のようになります。
    ```go
    // match: (MOVLloadidx1 [c] {sym} ptr (SHLQconst [2] idx) mem)
    // cond:
    // result: (MOVLloadidx4 [c] {sym} ptr idx mem)
    for {
        c := v.AuxInt
        sym := v.Aux
        ptr := v.Args[0]
        v_1 := v.Args[1]
        if v_1.Op != OpAMD64SHLQconst {
            break
        }
        if v_1.AuxInt != 2 {
            break
        }
        idx := v_1.Args[0]
        mem := v.Args[2]
        v.reset(OpAMD64MOVLloadidx4) // 新しい操作にリセット
        v.AuxInt = c
        v.Aux = sym
        v.AddArg(ptr)
        v.AddArg(idx)
        v.AddArg(mem)
        return true
    }
    ```
    このコードは、SSA値`v`が`MOVLloadidx1`操作であり、その第2引数（インデックス）が`SHLQconst [2]`操作である場合に、`v`を`MOVLloadidx4`操作に書き換えるロジックを実装しています。

## コアとなるコードの解説

`AMD64.rules`ファイルは、コンパイラがSSA形式のコードを最適化するための「レシピ」を提供します。追加されたルールは、特定の構造を持つSSAグラフのサブグラフ（`SHLQconst`の後に`loadidx1`または`storeidx1`が続く）を、より簡潔で効率的なサブグラフ（`loadidxN`または`storeidxN`）に置き換えることを宣言しています。

`rewriteAMD64.go`ファイル内の変更は、これらのルールを実際に適用するためのGoコードです。各`rewriteValueAMD64_Op...`関数は、特定のSSA操作（`Op...`）を処理する際に呼び出されます。追加された`for`ループ内の`match`ブロックは、SSAグラフを走査しながら、定義されたパターンに合致するノードシーケンスを探します。

パターンが一致すると、`v.reset(...)`を呼び出して現在のSSA操作を新しい、最適化された操作（例: `OpAMD64MOVLloadidx4`）に置き換え、関連する引数（`ptr`, `idx`, `mem`, `val`など）と補助情報（`AuxInt`, `Aux`）を適切に設定します。これにより、中間表現の段階で命令が結合され、最終的に生成される機械語コードから冗長なシフト命令が排除されます。

この最適化は、GoコンパイラがAMD64プロセッサのハードウェア機能を最大限に活用し、配列アクセスのような一般的な操作をより効率的に実行できるようにするための重要なステップです。結果として、Goプログラムの実行速度向上とバイナリサイズの削減に貢献します。

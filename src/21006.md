# [インデックス 21006] ファイルの概要

Goの`bufio`パッケージにおける`Scanner`が、ユーザー定義の`SplitFunc`が連続して空のトークンを生成し、入力が進まない場合に無限ループに陥るのを防ぐための修正です。このコミットは、このような状況を検出し、`panic`を発生させることで、プログラムのハングアップを防ぎ、デバッグを容易にします。

## 元コミット内容

`bufio`: 空のトークンを生成するループを防ぐ

分割関数の新しいルールにより、EOFで無限ループする一般的なバグに晒されることになりました。連続してあまりにも多くの空のトークンが配信された場合、スキャナーをシャットダウンすることでこれらを取り除きます。

Fixes #9020.

## 変更の背景

Go言語の`bufio.Scanner`は、`io.Reader`からデータを読み込み、ユーザーが提供する`SplitFunc`（分割関数）に基づいてデータをトークンに分割する強力なユーティリティです。この`SplitFunc`は、入力のどの部分をトークンとして抽出し、次にどこから読み取りを再開するかを`Scanner`に指示します。

このコミットが導入された背景には、`SplitFunc`の設計と使用における特定の落とし穴がありました。特に、Go 1.4で導入された`SplitFunc`の新しいルール（またはその解釈）により、`SplitFunc`がファイルの終端（EOF）に達した際に、入力ストリームを全く進めずに（`advance`値が0のまま）連続して空のトークンを返し続けるようなバグのある実装が、`Scanner`を無限ループに陥らせる可能性が浮上しました。

このような無限ループは、プログラムがハングアップしたり、CPUリソースを際限なく消費したりする原因となります。開発者が意図しない`SplitFunc`の実装をしてしまった場合、デバッグが困難になることも予想されます。

このコミットは、このような「EOFでの無限ループ」という一般的なバグパターンを特定し、それに対する堅牢な防御策を`bufio.Scanner`自体に組み込むことを目的としています。具体的には、`SplitFunc`が100回連続して空のトークンを返した場合に`panic`を発生させることで、無限ループを早期に検出し、プログラムを異常終了させるように変更されました。これにより、問題の発生を明確にし、開発者がバグを特定しやすくなります。

なお、コミットメッセージには`Fixes #9020`とありますが、Goの公式Issueトラッカーでこの番号のIssueを直接見つけることはできませんでした。しかし、コミットメッセージとコードの変更内容から、解決しようとしている問題（`SplitFunc`による無限ループ）は明確です。

## 前提知識の解説

### `bufio.Scanner`

`bufio.Scanner`は、Go言語の標準ライブラリ`bufio`パッケージの一部で、`io.Reader`インターフェースを実装する任意のデータソース（ファイル、ネットワーク接続など）からデータを読み込み、それをトークン（単語、行、カスタム区切り文字で区切られたデータなど）に分割するための高レベルなインターフェースを提供します。

主な特徴は以下の通りです。
*   **柔軟なトークン化**: ユーザーが`SplitFunc`を定義することで、任意のロジックでデータをトークンに分割できます。
*   **効率的なバッファリング**: 内部でバッファリングを行うため、小さな読み取り操作が多数発生するのを防ぎ、I/O効率を高めます。
*   **エラーハンドリング**: スキャン中に発生したエラーを`Err()`メソッドで取得できます。

### `SplitFunc`

`SplitFunc`は`bufio.Scanner`の心臓部とも言える機能で、以下のようなシグネチャを持つ関数です。

```go
type SplitFunc func(data []byte, atEOF bool) (advance int, token []byte, err error)
```

*   `data []byte`: 現在処理可能な入力データのスライス。
*   `atEOF bool`: `true`の場合、`data`が入力の終端（EOF）で利用可能な最後のデータであることを示します。
*   `advance int`: `Scanner`が次に読み取りを開始する位置まで、`data`スライスを何バイト進めるべきかを示します。
*   `token []byte`: 抽出されたトークン。
*   `err error`: トークン化中に発生したエラー。

`SplitFunc`の役割は、`data`スライスから次のトークンを見つけ、そのトークンと、次に`Scanner`が読み取りを開始すべき位置（`advance`）を返すことです。

### トークンの生成と入力の進行

`SplitFunc`がトークンを返す際、`advance`の値は非常に重要です。
*   `advance > 0`: `Scanner`は`data`スライスを`advance`バイトだけ進め、次のスキャン操作はその新しい位置から開始されます。これは、入力が実際に消費され、進行したことを意味します。
*   `advance == 0`: `Scanner`は`data`スライスを全く進めません。これは、現在の`data`スライスから有効なトークンを抽出できなかった場合（例: トークンがまだ完全にバッファに読み込まれていない場合）や、エラーが発生した場合などに使用されます。

### 無限ループのシナリオ

問題となる無限ループは、`SplitFunc`が以下のような状況で発生します。
1.  `Scanner`がEOFに近づくか、EOFに達する。
2.  `SplitFunc`が、`data`スライスを全く進めずに（`advance`が0）、かつ空のトークン（`token`が`nil`または`len(token) == 0`）を返し続ける。
3.  `Scanner`は入力が進まないため、同じ`data`スライスに対して繰り返し`SplitFunc`を呼び出し、無限ループに陥る。

これは、特に`SplitFunc`がEOF処理を誤って実装した場合に発生しやすいバグです。例えば、EOFで残りのデータを処理しようとしたが、有効なトークンを形成できず、かつ`advance`を0のままにしてしまうようなケースです。

## 技術的詳細

このコミットは、`bufio.Scanner`が`SplitFunc`によって引き起こされる無限ループを検出するためのメカニズムを導入しています。

1.  **`Scanner`構造体への`empties`フィールドの追加**:
    `Scanner`構造体に`empties int`という新しいフィールドが追加されました。このフィールドは、`SplitFunc`が連続して空のトークン（`len(token) == 0`）を生成し、かつ入力が進行しなかった回数をカウントするために使用されます。

    ```go
    type Scanner struct {
        // ... 既存のフィールド
        empties      int       // Count of successive empty tokens.
    }
    ```

2.  **`Scan()`メソッド内のロジック変更**:
    `Scanner`の`Scan()`メソッドは、次のトークンを見つけるための主要なループを含んでいます。このループ内で、`SplitFunc`がトークンを返した後の処理が以下のように変更されました。

    *   **非空トークンが生成された場合**:
        `SplitFunc`が`len(token) > 0`である非空のトークンを返した場合、`s.empties`カウンタは`0`にリセットされます。これは、入力が正常に進み、有効なトークンが抽出されたことを意味します。

        ```go
        if len(token) > 0 {
            s.empties = 0
        }
        ```

    *   **空トークンが生成された場合**:
        `SplitFunc`が`len(token) == 0`である空のトークンを返した場合、`s.empties`カウンタがインクリメントされます。これは、トークンは生成されたものの、それが空であり、入力が実質的に進んでいない可能性を示唆します。

        ```go
        else { // len(token) == 0 の場合
            s.empties++
            if s.empties > 100 {
                panic("bufio.Scan: 100 empty tokens without progressing")
            }
        }
        ```
        ここで、`s.empties`が`100`を超えた場合、`panic`が発生します。この`panic`メッセージは、`Scanner`が入力の進行なしに100回連続して空のトークンを受け取ったことを明確に示しており、これは無限ループの兆候と見なされます。`100`という閾値は、通常の`SplitFunc`の動作でこれほど多くの連続した空トークンが生成されることは稀であるという経験則に基づいていると考えられます。

    *   **バッファへの新しいデータ読み込み時**:
        `Scan()`メソッドは、必要に応じて基になる`io.Reader`から新しいデータを内部バッファに読み込みます。新しいデータがバッファに正常に読み込まれた場合（`n > 0`）、これも入力の進行と見なされるため、`s.empties`カウンタは`0`にリセットされます。

        ```go
        if n > 0 {
            s.empties = 0
            break // 新しいデータが読み込まれたので、ループを抜けて再試行
        }
        ```

これらの変更により、`bufio.Scanner`は、悪意のある、またはバグのある`SplitFunc`が引き起こす無限ループから自身を保護するようになりました。`panic`を発生させることで、プログラムがハングアップする代わりに、問題の根本原因を特定しやすい形で異常終了します。

## コアとなるコードの解説

### `src/bufio/scan.go`の変更点

1.  **`Scanner`構造体への`empties`フィールドの追加**:
    `Scanner`型に`empties int`という新しいフィールドが追加されました。このフィールドは、`SplitFunc`が連続して空のトークンを返した回数を記録します。

2.  **`Scan()`メソッド内のトークン処理ロジックの変更**:
    `Scan()`メソッドの内部ループで、`SplitFunc`がトークンを返した後の処理が変更されました。
    *   `if token != nil`ブロック内で、`SplitFunc`が返した`token`の長さがチェックされます。
    *   `if len(token) > 0`の場合、つまり非空のトークンが生成された場合、`s.empties`は`0`にリセットされます。これは、入力が正常に進んだことを示します。
    *   `else`ブロック（`len(token) == 0`の場合）、つまり空のトークンが生成された場合、`s.empties`がインクリメントされます。
    *   その後、`if s.empties > 100`という条件がチェックされます。もし`empties`カウンタが`100`を超えた場合、`panic("bufio.Scan: 100 empty tokens without progressing")`が発生します。これは、`SplitFunc`が入力の進行なしに100回連続で空のトークンを返したことを意味し、無限ループの兆候と見なされます。

3.  **バッファへの新しいデータ読み込み時の`empties`リセット**:
    `Scan()`メソッドの後半、`io.Reader`から新しいデータが内部バッファに読み込まれた際（`if n > 0`の条件が真の場合）にも、`s.empties = 0`が追加されました。これは、新しいデータが読み込まれたことで入力が進行したと見なし、空トークンカウンタをリセットするためです。

これらの変更により、`Scanner`は、`SplitFunc`が無限に空のトークンを生成し続けるようなバグから自身を保護し、プログラムの安定性を向上させます。

### `src/bufio/scan_test.go`の変更点

1.  **`loopAtEOFSplit`関数**:
    この関数は、EOFに達すると`advance`が0で空のトークンを返し続ける、意図的に無限ループを引き起こす`SplitFunc`の例です。`len(data) > 0`の間は1バイトずつ進んでトークンを返しますが、`data`が空になると`advance`を0、`token`も空のまま返します。

2.  **`TestDontLoopForever`テスト**:
    *   `NewScanner`で`"abc"`という短い文字列を読み込む`Scanner`を作成し、`loopAtEOFSplit`を`SplitFunc`として設定します。
    *   `defer`と`recover()`を使用して、このテストが`panic`を捕捉するように設定されています。これは、`Scanner`が期待通り`panic`を発生させることを検証するためです。
    *   `for count := 0; s.Scan(); count++`ループで`Scanner`をスキャンします。`count > 1000`で`t.Fatal("looping")`というチェックがありますが、これは`panic`が期待通り発生すれば到達しないはずです。
    *   `panic`が捕捉された後、そのメッセージが`"empty tokens"`を含むことを確認し、修正が正しく機能していることを検証します。

3.  **`countdown`型と`split`メソッド**:
    *   `countdown`型は、`SplitFunc`が空のトークンを返すものの、実際には入力が進行している（`advance`が1）ケースをシミュレートするためのヘルパーです。`*c > 0`の間は1バイトずつ進んでトークンを返しますが、`*c`が0になると`advance`も`token`も空を返します。

4.  **`TestEmptyLinesOK`テスト**:
    *   このテストは、`countdown`の`split`メソッドを使用し、`strings.Repeat("\n", 10000)`という10000個の改行文字からなる文字列をスキャンします。
    *   このシナリオでは、`SplitFunc`は多くの空のトークン（改行間の空行）を生成しますが、`advance`は常に1であるため、入力は進行しています。
    *   このテストの目的は、`Scanner`が空のトークンが多数生成されても、入力が進行している限り`panic`が発生しないことを確認することです。これにより、この修正が正しく「入力が進まない」無限ループのみを対象としていることが保証されます。

これらのテストは、`empties`カウンタと`panic`ロジックが、意図しない無限ループを効果的に検出し、かつ正当な空トークンの生成を妨げないことを確認するために重要です。

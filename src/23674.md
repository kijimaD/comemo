# [インデックス 23674] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャの関数プロローグを改善することを目的としています。特に、スタック拡張が不要な一般的なケースにおいて、条件付き命令の数を減らし、単一の条件付き分岐命令で処理することで、実行速度の向上を図っています。この変更は、各関数に4バイトのオーバーヘッドを追加しますが、一般的な実行パスでのパフォーマンス改善が期待されます。

## 変更の背景

Go言語のランタイムは、関数呼び出し時にスタックのサイズが足りるかどうかをチェックし、必要であればスタックを拡張する「スタック分割 (stack split)」というメカニズムを持っています。このコミット以前のARMアーキテクチャにおける関数プロローグ（関数の冒頭部分）では、スタック拡張が必要ない場合でも、複数の条件付き命令（`MOVW.LS`, `BL.LS`, `B.LS`）を実行していました。

しかし、ほとんどの関数呼び出しではスタック拡張は不要であり、この余分な命令の実行はオーバーヘッドとなっていました。このコミットの目的は、この一般的なケースでのオーバーヘッドを削減し、パフォーマンスを向上させることです。具体的には、スタック拡張が不要な場合に実行される条件付き命令の数を3つから1つの条件付き分岐命令に減らすことで、命令キャッシュの効率化やパイプラインの詰まりの軽減を目指しています。

この変更は、Go issue #10587 に関連しており、ARMプラットフォームでのGoプログラムの実行効率を改善するための取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **ARMアーキテクチャ**: ARM (Advanced RISC Machine) は、モバイルデバイスや組み込みシステムで広く使用されているRISC (Reduced Instruction Set Computer) プロセッサアーキテクチャです。命令セットは固定長で、条件付き実行やロード/ストア命令が特徴です。
*   **関数プロローグ (Function Prologue)**: 関数が呼び出された際に、その関数の実行開始前に行われる一連の処理のことです。これには、スタックフレームのセットアップ、レジスタの保存、スタックサイズチェックなどが含まれます。
*   **スタック分割 (Stack Split)**: Goランタイムの重要な機能の一つで、関数が呼び出される際に必要なスタックサイズをチェックし、現在のスタックが不足している場合に新しい、より大きなスタックセグメントを割り当てて切り替えるメカニズムです。これにより、Goルーチンは小さなスタックで開始し、必要に応じて動的に拡張できるため、メモリ効率が向上します。
*   **`morestack` / `morestack_noctxt` / `morestackc`**: Goランタイム内でスタック拡張処理を行うための関数群です。`morestack_noctxt` はコンテキスト情報なしでスタック拡張を処理する場合に、`morestackc` はC言語との相互運用時に使用されます。
*   **条件付き実行 (Conditional Execution)**: ARM命令セットの特徴の一つで、ほとんどの命令に条件コードを付加することで、特定の条件が満たされた場合にのみ命令を実行させることができます。例えば、`.LS` は "Lower or Same" (より小さいか等しい) という条件を表します。
*   **条件付き分岐 (Conditional Branch)**: 特定の条件が満たされた場合に、プログラムの実行フローを別の場所へジャンプさせる命令です。
*   **レジスタ**: CPU内部にある高速な記憶領域です。ARMアーキテクチャでは、`R0`から`R15`までの汎用レジスタや、リンクレジスタ (`LR`, `R14`)、スタックポインタ (`SP`, `R13`) などがあります。
    *   `R10`: Goランタイムでは、現在のGoroutineのG構造体へのポインタを保持することがあります。
    *   `R13` (SP): スタックポインタ。スタックの現在のトップを指します。
    *   `R14` (LR): リンクレジスタ。関数呼び出し時に戻りアドレスを保存するために使用されます。
    *   `R15` (PC): プログラムカウンタ。次に実行される命令のアドレスを指します。
*   **`TEXT` ディレクティブ**: Goアセンブリ言語における関数の定義を示すディレクティブです。
*   **`MOVW`**: ARMアセンブリにおけるワード（32ビット）の移動命令です。
*   **`ADD`**: 加算命令です。
*   **`CMP`**: 比較命令です。
*   **`BL`**: Branch with Link。関数呼び出しに使用され、戻りアドレスをLRレジスタに保存してから分岐します。
*   **`B`**: Branch。無条件分岐命令です。
*   **`BLS`**: Branch if Lower or Same。条件付き分岐命令です。

## 技術的詳細

このコミットの主要な変更点は、ARMアーキテクチャにおけるGo関数のプロローグで、スタック拡張が必要ない場合の処理を最適化することです。

**変更前のアプローチ:**
スタックサイズチェック後、スタック拡張が必要ない（条件が`LS`、つまり「より小さいか等しい」が偽）場合でも、以下の3つの条件付き命令が実行されていました。

1.  `MOVW.LS R14, R3`: リンクレジスタR14の値をR3に移動（条件付き）
2.  `BL.LS runtime.morestack_noctxt(SB)`: `morestack_noctxt`関数を呼び出し（条件付き）
3.  `B.LS main.f(SB)`: 現在の関数に分岐（条件付き）

これらの命令は、スタック拡張が必要な場合にのみ意味を持ちますが、条件付き実行であるため、スタック拡張が不要な場合でも命令フェッチやデコードのパイプラインを通過していました。

**変更後のアプローチ:**
このコミットでは、スタックサイズチェック後、スタック拡張が不要な場合には、単一の条件付き分岐命令 `B.LS` を使用して、スタック拡張ロジックをスキップするように変更されました。

具体的には、以下のようになります。

1.  スタックサイズチェック (`CMP R1, R2`) の結果、スタック拡張が不要な場合 (`LS` 条件が偽の場合)、`B.LS` 命令が実行され、スタック拡張のためのコードブロック全体をスキップして、関数の本体の処理に進みます。
2.  スタック拡張が必要な場合 (`LS` 条件が真の場合)、`B.LS` 命令は実行されず、その後のスタック拡張のためのコードブロック（`MOVW R14, R3`, `BL runtime.morestack_noctxt(SB)`, `B main.f(SB)`）が実行されます。

この変更により、スタック拡張が不要な一般的なケースでは、3つの条件付き命令の代わりに1つの条件付き分岐命令のみが実行されるため、命令実行の効率が向上します。ただし、この最適化のために、スタック拡張ロジックが関数の本体の後に配置される形になり、各関数のバイナリサイズが4バイト増加します。これは、分岐命令のターゲットアドレスを指すための追加の命令が必要になるためです。

コミットメッセージには、iPhone 6とRaspberry Pi (rpi) でのベンチマーク結果が示されており、多くの`sort`パッケージのベンチマークでわずかながら改善が見られます。特に、rpiでの`StableInt1K`や`StableInt64K`、`Stable1e4`、`Stable1e6`などで顕著な改善が見られます。一方で、`SearchWrappers`のようにパフォーマンスが低下するケースも一部存在します。これは、コードサイズの増加や、特定のワークロードにおけるキャッシュの振る舞いの変化によるものと考えられます。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm/obj5.go` の変更

`stacksplit` 関数は、Goコンパイラが各Go関数のプロローグにスタックチェックコードを挿入する際に使用されます。

**変更前:**

```go
	// MOVW.LS	R14, R3
	p = obj.Appendp(ctxt, p)
	p.As = AMOVW
	p.Scond = C_SCOND_LS
	p.From.Type = obj.TYPE_REG
	p.From.Reg = REGLINK
	p.To.Type = obj.TYPE_REG
	p.To.Reg = REG_R3

	// BL.LS		runtime.morestack(SB) // modifies LR, returns with LO still asserted
	p = obj.Appendp(ctxt, p)
	p.As = ABL
	p.Scond = C_SCOND_LS
	p.To.Type = obj.TYPE_BRANCH
	// ... morestack variant selection ...

	// BLS	start
	p = obj.Appendp(ctxt, p)
	p.As = ABLS
	p.To.Type = obj.TYPE_BRANCH
	p.Pcond = ctxt.Cursym.Text.Link // Branch to the start of the function body
```

このコードは、スタックチェックの結果が「Lower or Same (LS)」の場合（つまりスタックが足りない可能性がある場合）に、`R14`を`R3`に移動し、`morestack`を呼び出し、そして関数の先頭に戻るという一連の命令を生成していました。スタックが足りている場合でも、これらの条件付き命令はフェッチ・デコードされていました。

**変更後:**

```go
	// BLS call-to-morestack
	bls := obj.Appendp(ctxt, p)
	bls.As = ABLS
	bls.To.Type = obj.TYPE_BRANCH

	var last *obj.Prog
	for last = ctxt.Cursym.Text; last.Link != nil; last = last.Link {
	}

	// MOVW	LR, R3
	movw := obj.Appendp(ctxt, last)
	movw.As = AMOVW
	movw.From.Type = obj.TYPE_REG
	movw.From.Reg = REGLINK
	movw.To.Type = obj.TYPE_REG
	movw.To.Reg = REG_R3

	bls.Pcond = movw // If LS condition is true, branch to movw (start of morestack logic)

	// BL runtime.morestack
	call := obj.Appendp(ctxt, movw)
	call.As = obj.ACALL
	call.To.Type = obj.TYPE_BRANCH
	// ... morestack variant selection ...
	call.To.Sym = obj.Linklookup(ctxt, morestack, 0)

	// B start
	b := obj.Appendp(ctxt, call)
	b.As = obj.AJMP
	b.To.Type = obj.TYPE_BRANCH
	b.Pcond = ctxt.Cursym.Text.Link // Unconditional branch back to the function body start

	return bls // Return the first instruction of the new prologue
```

変更後では、まず `BLS` (Branch if Lower or Same) 命令を生成します。この命令は、スタックチェックの結果が `LS` (スタックが足りない) であれば、`movw` 命令（スタック拡張ロジックの開始点）に分岐します。スタックが足りている場合は、この `BLS` 命令はスキップされ、関数の本体のコードが直接実行されます。

スタック拡張ロジック自体は、関数の本体の後に配置されます。このロジックは、`MOVW LR, R3` (リンクレジスタをR3に保存)、`BL runtime.morestack` (スタック拡張関数呼び出し)、そして `B start` (元の関数の先頭に戻る無条件分岐) で構成されます。

この再構成により、スタック拡張が不要な一般的なケースでは、`CMP` 命令の後に1つの `BLS` 命令が実行されるだけで済み、以前の3つの条件付き命令の実行を回避できます。

### `src/runtime/sys_arm.go` の変更

`rewindmorestack` 関数は、スタック拡張後にプログラムカウンタ (PC) を正しい位置に巻き戻すために使用されます。

**変更前:**

```go
	if inst>>24 == 0x9a { // Check for BL.LS instruction
		buf.pc += uintptr(int32(inst<<8)>>6) + 8
		return
	}
```

以前は、`BL.LS` 命令のオペコード (`0x9a`) のみをチェックしていました。

**変更後:**

```go
	if inst>>24 == 0x9a || inst>>24 == 0xea { // Check for BL.LS or B (unconditional branch) instruction
		buf.pc += uintptr(int32(inst<<8)>>6) + 8
		return
	}
```

新しいプロローグでは、スタック拡張ロジックの最後に無条件分岐命令 `B` (オペコード `0xea`) が使用される可能性があるため、`rewindmorestack` はこの新しい命令も認識してPCを正しく調整できるように更新されました。これにより、スタック拡張後の戻りアドレスの計算が正確に行われます。

## 変更の背景

Go言語の`struct`型定義において、複数のフィールドを記述する際には、各フィールド宣言の後にセミコロン（`;`）を置くか、改行によってセミコロンを省略する規則があります。しかし、他の言語（例えばC++やJavaなど）の習慣から、誤ってフィールドの区切りにコンマ（`,`）を使用してしまう開発者がいました。

このコミット以前は、`struct { x int, y float }` のようにコンマを使った場合、パーサーは「`;`が期待される」という一般的なエラーを出すかもしれませんが、コンマがなぜ問題なのか、あるいはコンマがどこで期待されるのかについて、具体的な情報を提供していませんでした。`Fixes #12437`という記述から、この問題がユーザーによって報告され、より明確なエラーメッセージが求められていたことが伺えます。この変更は、このような一般的な構文エラーに対して、より具体的で役立つエラーメッセージを提供することで、開発者のデバッグ体験を向上させることを目的としています。

## 前提知識の解説

### Go言語の構文におけるセミコロンとコンマ

*   **セミコロン (`;`)**: Go言語では、ステートメントの区切り文字としてセミコロンが使用されます。しかし、ほとんどの場合、改行によって自動的に挿入されるため、明示的に記述する必要はありません。`struct`型定義のフィールド宣言では、各フィールドの後にセミコロンが必要です（ただし、改行があれば省略可能）。
    ```go
    type MyStruct struct {
        Field1 int; // 明示的なセミコロン
        Field2 string // 改行によるセミコロン省略
    }
    ```
*   **コンマ (`,`)**: コンマは、主にリスト、引数、戻り値、マップのキーと値のペアなどを区切るために使用されます。`struct`のフィールド宣言の区切りには通常使用されません。

### Goパーサーの役割

Goコンパイラのフロントエンドの一部であるパーサーは、Goのソースコードを読み込み、その構文がGo言語の仕様に準拠しているかを検証し、抽象構文木（AST: Abstract Syntax Tree）と呼ばれる内部表現に変換する役割を担います。このプロセスは大きく分けて以下のステップを含みます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子、リテラルなど）のストリームに分解します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームをGo言語の文法規則に従って解析し、ASTを構築します。この段階で構文エラーが検出されます。

パーサーが構文エラーを検出した際、開発者にとって理解しやすく、問題の解決に役立つエラーメッセージを提供することは非常に重要です。

### `go/parser` パッケージ

`go/parser`パッケージは、Go言語の標準ライブラリの一部であり、Goのソースコードを解析するための機能を提供します。このパッケージは、Goツールチェインのコンパイラやその他のツール（`go vet`、`gofmt`など）で内部的に使用されています。開発者がGoコードをプログラム的に解析する必要がある場合にも利用されます。

## 技術的詳細

このコミットの核心は、`go/parser`パッケージ内の`parser`構造体の`expectSemi`メソッドの変更にあります。

`expectSemi`メソッドは、パーサーが現在の位置でセミコロン（または改行によるセミコロンの自動挿入）を期待しているときに呼び出されます。例えば、`struct`のフィールド宣言の終わりや、`var`、`const`、`func`などの宣言の終わりなどです。

変更前の`expectSemi`のロジックは以下のようでした。

1.  現在のトークンが閉じ括弧（`token.RPAREN`）や閉じ波括弧（`token.RBRACE`）でない場合、セミコロンが期待される。
2.  現在のトークンが`token.SEMICOLON`であれば、それを消費して次に進む。
3.  そうでなければ、エラーを報告し、ステートメントの同期を試みる。

このロジックでは、`struct { x int, }` のようにコンマがあった場合、`token.SEMICOLON`ではないため、単に「`;`が期待される」という一般的なエラーが出力されていました。

変更後の`expectSemi`のロジックは、`switch`ステートメントを導入し、`token.COMMA`を特別に処理します。

1.  現在のトークンが閉じ括弧（`token.RPAREN`）や閉じ波括弧（`token.RBRACE`）でない場合、セミコロンが期待される。
2.  `switch p.tok` で現在のトークンを評価する。
    *   `case token.COMMA`:
        *   「`;`が期待される」というエラーを報告するが、このエラーメッセージはコンマが検出されたことを示唆するようになります。
        *   `fallthrough`キーワードにより、次の`case token.SEMICOLON`の処理に移行します。これは、コンマをセミコロンの代わりとして「許容」し、パーサーがそのコンマを消費して解析を続行できるようにするためです。これにより、エラーを報告しつつも、パーサーが完全に停止するのを防ぎ、後続の構文エラーも検出できる可能性が高まります（エラー回復）。
    *   `case token.SEMICOLON`:
        *   現在のトークン（セミコロンまたは`fallthrough`で渡されたコンマ）を消費して次に進む。
    *   `default`:
        *   それ以外のトークンであれば、一般的な「`;`が期待される」エラーを報告し、ステートメントの同期を試みる。

この変更により、`struct`型定義でコンマが誤って使用された場合に、パーサーは「`;`が期待されるが、`,`が見つかった」といった、より具体的で分かりやすいエラーメッセージを出力できるようになります。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更

`expectSemi`関数は、Goの構文解析においてセミコロンが期待される場所で呼び出されます。この変更の目的は、`struct`型定義内でフィールドの区切りに誤ってコンマが使われた場合に、より適切なエラーメッセージを生成することです。

変更前は、現在のトークンが`token.SEMICOLON`でなければ、一律に「`;`が期待される」というエラーを出力していました。
変更後は、`switch`文を導入し、現在のトークンが`token.COMMA`である場合を特別に扱います。

```go
		switch p.tok {
		case token.COMMA:
			// permit a ',' instead of a ';' but complain
			p.errorExpected(p.pos, "';'")
			fallthrough
		case token.SEMICOLON:
			p.next()
		default:
			p.errorExpected(p.pos, "';'")
			syncStmt(p)
		}
```

*   `case token.COMMA:`: ここが新しいロジックの肝です。
    *   `p.errorExpected(p.pos, "';'")`: この行は、パーサーが現在の位置でセミコロンを期待していることを示すエラーメッセージを生成します。しかし、この変更により、内部的にはコンマが検出されたという情報も含まれるようになり、最終的なエラーメッセージは「expected ';', found ','」のようになることが期待されます。
    *   `fallthrough`: このキーワードは、現在の`case`ブロックの実行後、次の`case`ブロック（`case token.SEMICOLON`）に制御を移します。これは、コンマを検出してエラーを報告した後も、パーサーがそのコンマを「セミコロンの代わり」として消費し、解析を続行できるようにするためのエラー回復メカニズムです。これにより、単一の構文エラーで解析が完全に停止するのではなく、後続の構文エラーも検出できる可能性が高まります。
*   `case token.SEMICOLON:`: `fallthrough`によってここに到達した場合、または現在のトークンが実際にセミコロンであった場合、`p.next()`が呼び出され、現在のトークン（コンマまたはセミコロン）が消費され、パーサーは次のトークンに進みます。
*   `default:`: `token.COMMA`でも`token.SEMICOLON`でもない、予期しないトークンが来た場合は、以前と同様に一般的な「`;`が期待される」エラーを報告し、`syncStmt(p)`でステートメントの同期を試みます。

この変更により、`struct { x int, }`のようなコードに対して、より具体的で分かりやすいエラーメッセージ「expected ';', found ','」が出力されるようになります。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更

`expectSemi`関数は、Goの構文解析においてセミコロンが期待される場所で呼び出されます。この変更の目的は、`struct`型定義内でフィールドの区切りに誤ってコンマが使われた場合に、より適切なエラーメッセージを生成することです。

変更前は、現在のトークンが`token.SEMICOLON`でなければ、一律に「`;`が期待される」というエラーを出力していました。
変更後は、`switch`文を導入し、現在のトークンが`token.COMMA`である場合を特別に扱います。

```go
		switch p.tok {
		case token.COMMA:
			// permit a ',' instead of a ';' but complain
			p.errorExpected(p.pos, "';'")
			fallthrough
		case token.SEMICOLON:
			p.next()
		default:
			p.errorExpected(p.pos, "';'")
			syncStmt(p)
		}
```

*   `case token.COMMA:`: ここが新しいロジックの肝です。
    *   `p.errorExpected(p.pos, "';'")`: この行は、パーサーが現在の位置でセミコロンを期待していることを示すエラーメッセージを生成します。しかし、この変更により、内部的にはコンマが検出されたという情報も含まれるようになり、最終的なエラーメッセージは「expected ';', found ','」のようになることが期待されます。
    *   `fallthrough`: このキーワードは、現在の`case`ブロックの実行後、次の`case`ブロック（`case token.SEMICOLON`）に制御を移します。これは、コンマを検出してエラーを報告した後も、パーサーがそのコンマを「セミコロンの代わり」として消費し、解析を続行できるようにするためのエラー回復メカニズムです。これにより、単一の構文エラーで解析が完全に停止するのではなく、後続の構文エラーも検出できる可能性が高まります。
*   `case token.SEMICOLON:`: `fallthrough`によってここに到達した場合、または現在のトークンが実際にセミコロンであった場合、`p.next()`が呼び出され、現在のトークン（コンマまたはセミコロン）が消費され、パーサーは次のトークンに進みます。
*   `default:`: `token.COMMA`でも`token.SEMICOLON`でもない、予期しないトークンが来た場合は、以前と同様に一般的な「`;`が期待される」エラーを報告し、`syncStmt(p)`でステートメントの同期を試みます。

この変更により、`struct { x int, }`のようなコードに対して、より具体的で分かりやすいエラーメッセージ「expected ';', found ','」が出力されるようになります。

### `src/go/parser/short_test.go` の変更

`short_test.go`ファイルは、Goパーサーの様々な無効な構文に対するテストケースを定義しています。`invalids`変数には、エラーを発生させるべきコードスニペットとその期待されるエラーメッセージが記述されています。

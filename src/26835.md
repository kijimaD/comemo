## 変更の背景

この変更の主な背景は、`crypto/tls` パッケージのテストスイートの可読性と保守性の向上です。以前のコードでは、TLSプロトコルバージョン（例: `0x0301`）や圧縮メソッド（例: `0`）を直接数値リテラルとして記述していました。これらの数値は、その意味を知らない開発者にとっては「マジックナンバー」となり、コードの意図を理解するために追加の知識や調査が必要でした。

このような不透明なリテラルを `VersionTLS10` や `compressionNone` といった意味が明確な名前付き定数に置き換えることで、テストコードが自己文書化され、以下のような利点が得られます。

1.  **可読性の向上**: コードを読んだ際に、その値が何を意味するのかがすぐに理解できるようになります。
2.  **保守性の向上**: 将来的にこれらの値が変更された場合でも、定数の定義箇所を修正するだけで済み、コード全体を検索してリテラル値を置き換える手間が省けます。また、誤って異なる意味を持つ同じ数値リテラルを変更してしまうリスクも低減されます。
3.  **エラーの削減**: マジックナンバーは入力ミスや誤解によるバグの原因となることがありますが、名前付き定数を使用することでこれらのリスクを減らすことができます。

このコミットは、Go言語の標準ライブラリが重視するコード品質と保守性の高さを維持するための、典型的なリファクタリングの一例と言えます。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下の概念について知っておく必要があります。

*   **TLS (Transport Layer Security)**:
    インターネット上で安全な通信を確立するための暗号化プロトコルです。ウェブサイトのHTTPS接続などで広く利用されており、データの盗聴、改ざん、なりすましを防ぎます。TLS通信の開始時には、クライアントとサーバー間で「ハンドシェイク」と呼ばれる一連のメッセージ交換が行われ、互いの能力を交渉し、暗号化パラメータを確立します。

*   **TLSハンドシェイク (TLS Handshake)**:
    TLSプロトコルにおいて、クライアントとサーバーが安全な通信セッションを確立するために実行するプロセスです。このプロセスには、プロトコルバージョンのネゴシエーション、暗号スイートの選択、サーバー認証（およびオプションでクライアント認証）、共有秘密鍵の生成などが含まれます。

*   **ClientHelloメッセージ**:
    TLSハンドシェイクの最初のステップで、クライアントがサーバーに送信するメッセージです。このメッセージには、クライアントがサポートするTLSプロトコルバージョン、利用可能な暗号スイートのリスト、サポートする圧縮メソッド、セッションID、ランダムなバイト列などの情報が含まれます。サーバーはこの情報に基づいて、通信に使用するプロトコルバージョンや暗号スイートなどを決定します。

*   **TLSプロトコルバージョン**:
    TLSプロトコルには、TLS 1.0、TLS 1.1、TLS 1.2、TLS 1.3など、複数のバージョンが存在します。これらのバージョンは、セキュリティ機能やパフォーマンスが異なります。プロトコルバージョンは通常、2バイトの数値で表現され、例えばTLS 1.0は `0x0301` (メジャーバージョン3、マイナーバージョン1) となります。

*   **圧縮メソッド (Compression Method)**:
    TLSハンドシェイク中に、クライアントとサーバーが通信データの圧縮方法について合意するために使用されるパラメータです。歴史的にはデータ圧縮がサポートされていましたが、CRIME/BREACH攻撃などの脆弱性が発見されたため、現代のTLS実装では通常、圧縮は無効化されています。`0` は「圧縮なし (null compression)」を意味する一般的な値です。

*   **マジックナンバー (Magic Number)**:
    プログラミングにおいて、コード中に直接埋め込まれた、その意味が不明瞭な数値や文字列リテラルのことを指します。マジックナンバーはコードの可読性を低下させ、誤解を招きやすく、変更が必要になった際に複数の箇所を修正する必要があるため、保守性を損なう原因となります。

*   **名前付き定数 (Named Constants)**:
    マジックナンバーの問題を解決するために、その値が表す意味を明確に示す名前を付けた定数を使用するプログラミングのプラクティスです。例えば、`0x0301` の代わりに `VersionTLS10` を使用することで、コードの意図が明確になり、可読性、保守性、および正確性が向上します。

## 技術的詳細

このコミットは、`src/crypto/tls/handshake_server_test.go` ファイル内のテストコードに焦点を当てています。このファイルは、Go言語の `crypto/tls` パッケージがTLSサーバーハンドシェイクを正しく処理するかどうかを検証するための単体テストを含んでいます。

変更の核心は、`clientHelloMsg` 構造体のインスタンスを生成する際に、特定のフィールドに直接ハードコードされていた数値リテラルを、対応する名前付き定数に置き換えることです。

具体的には、以下の2つの置き換えが行われています。

1.  **`vers: 0x0301` を `vers: VersionTLS10` へ**:
    *   `clientHelloMsg` 構造体の `vers` フィールドは、クライアントが提案するTLSプロトコルバージョンを示します。以前は `0x0301` という16進数リテラルが直接使用されていました。これはTLS 1.0を意味しますが、この数値を見ただけではその意味を即座に理解することは困難です。
    *   変更後、`VersionTLS10` という名前付き定数が使用されています。この定数は `crypto/tls` パッケージ内で `const VersionTLS10 = 0x0301` のように定義されていると推測され、その名前自体が「TLS 1.0バージョン」であることを明確に示しています。これにより、テストコードの意図が非常に分かりやすくなります。

2.  **`compressionMethods: []uint8{0}` を `compressionMethods: []uint8{compressionNone}` へ**:
    *   `clientHelloMsg` 構造体の `compressionMethods` フィールドは、クライアントがサポートする圧縮メソッドのリストを示します。以前は `[]uint8{0}` という形で、圧縮メソッドが「0」であることを直接指定していました。この「0」が「圧縮なし」を意味することは、TLSプロトコルの仕様を知っている開発者でなければ理解しにくいものです。
    *   変更後、`compressionNone` という名前付き定数が使用されています。この定数も `crypto/tls` パッケージ内で `const compressionNone = 0` のように定義されていると推測され、その名前が「圧縮なし」であることを明確に示しています。

これらの変更は、テストのロジックや振る舞いを一切変更するものではありません。テストは引き続き同じ条件で実行され、同じ結果を生成します。しかし、コードの意図がより明確になるため、将来的にテストコードを読み解いたり、デバッグしたり、あるいは新しいテストケースを追加したりする際の開発者の負担が大幅に軽減されます。これは、大規模なオープンソースプロジェクトにおいて、コードベースの健全性を維持するために非常に重要な側面です。

## コアとなるコードの解説

上記の差分は、`handshake_server_test.go` 内の複数のテストケースで `clientHelloMsg` 構造体を初期化する際に、`vers` フィールドと `compressionMethods` フィールドに割り当てられる値が変更されたことを示しています。

例えば、`TestNoSuiteOverlap` 関数内の以下の部分が変更されています。

```go
 	clientHello := &clientHelloMsg{
-		vers:               0x0301,
+		vers:               VersionTLS10,
 		cipherSuites:       []uint16{0xff00},
-		compressionMethods: []uint8{0},
+		compressionMethods: []uint8{compressionNone},
 	}
```

*   **`clientHello := &clientHelloMsg{...}`**: これは、`clientHelloMsg` 型の新しいインスタンスを作成し、そのポインタを `clientHello` 変数に割り当てています。`clientHelloMsg` は、TLSクライアントがサーバーに送信するClientHelloメッセージの内容をシミュレートするためにテストで使用される構造体です。
*   **`vers: VersionTLS10`**: `vers` フィールドは、クライアントがサポートするTLSプロトコルバージョンを示します。以前は `0x0301` という16進数リテラルが直接使われていましたが、これはTLS 1.0を意味します。変更後は `VersionTLS10` という名前付き定数が使われており、コードの意図が明確になります。この定数は `crypto/tls` パッケージ内で定義されているはずです。
*   **`compressionMethods: []uint8{compressionNone}`**: `compressionMethods` フィールドは、クライアントがサポートする圧縮メソッドのリストを示します。以前は `[]uint8{0}` という数値リテラルが使われていましたが、これは「圧縮なし」を意味します。変更後は `compressionNone` という名前付き定数が使われており、同様にコードの意図が明確になります。この定数も `crypto/tls` パッケージ内で定義されているはずです。

これらの変更は、テストコードのセマンティクス（意味）には影響を与えません。テストは以前と同じTLS 1.0バージョンと圧縮なしのClientHelloメッセージをシミュレートし続けます。しかし、コードの可読性が大幅に向上し、開発者がこれらの値の目的を理解するために追加の調査を行う必要がなくなります。これは、コードベース全体の品質と保守性を高めるための、小さくとも重要な改善です。

# [インデックス 2335] ファイルの概要

このコミットは、Goコンパイラ（`gc`）とランタイムにおいて、パッケージの再帰的な初期化を検出するメカニズムを導入するものです。Go言語のパッケージ初期化は厳密な順序で行われますが、複雑な依存関係の中で意図しない再帰呼び出しが発生する可能性があります。この変更は、そのような再帰を早期に検出し、ランタイムパニックを引き起こすことで、プログラムの異常終了を防ぎ、開発者に問題の存在を通知することを目的としています。

## 変更の背景

Go言語では、プログラムの実行開始前に各パッケージが初期化される仕組みがあります。これには、パッケージレベルの変数宣言の評価や、`init`関数の実行が含まれます。この初期化プロセスは、パッケージの依存関係グラフに基づいて順序付けられ、各パッケージは一度だけ初期化されることが保証されています。

しかし、初期化中に別のパッケージの初期化がトリガーされ、それが元のパッケージの初期化を再度トリガーするような循環的な依存関係が存在する場合、無限ループに陥る可能性があります。例えば、パッケージAがパッケージBに依存し、パッケージBがパッケージAに依存している場合、Aの初期化中にBの初期化が始まり、Bの初期化中にAの初期化が再び始まってしまう、といった状況です。

このコミット以前は、このような再帰的な初期化は検出されず、プログラムがスタックオーバーフローやデッドロックなどの未定義の動作を引き起こす可能性がありました。Go言語の設計思想として、このような潜在的な問題を早期に検出し、明確なエラーメッセージで開発者に通知することが重要であるため、この「再帰的な初期化の検出」機能が導入されました。

## 前提知識の解説

### Go言語のパッケージ初期化

Go言語では、プログラムの実行は`main`パッケージの`main`関数から始まります。しかし、`main`関数が呼び出される前に、プログラムが依存するすべてのパッケージが初期化されます。この初期化プロセスは以下のルールに従います。

1.  **依存関係の解決**: 各パッケージは、そのパッケージがインポートするすべてのパッケージが初期化された後に初期化されます。これにより、依存関係グラフが構築され、初期化の順序が決定されます。
2.  **変数初期化**: パッケージレベルで宣言された変数は、その初期化式が評価され、値が割り当てられます。
3.  **`init`関数の実行**: 各パッケージは、`init`という名前の引数なし、戻り値なしの関数を複数持つことができます。これらの`init`関数は、パッケージ内の変数初期化が完了した後に、宣言された順序で実行されます。
4.  **一度だけ実行**: 各パッケージの初期化は、プログラムの実行中に一度だけ行われます。

この初期化プロセスは、コンパイラによって生成される隠れた初期化関数（このコミットでは`Init·<file>()`として言及されているもの）によって管理されます。

### コンパイラの役割

Goコンパイラ（`gc`）は、ソースコードを機械語に変換するだけでなく、パッケージの初期化ロジックも生成します。具体的には、各Goソースファイル（またはパッケージ全体）に対して、その初期化状態を管理するためのコードを自動的に挿入します。これには、初期化が完了したかどうかを追跡するフラグや、依存するパッケージの初期化関数を呼び出すコードが含まれます。

### 再帰的な初期化の問題

再帰的な初期化は、主に以下のシナリオで発生します。

*   **循環インポート**: パッケージAがBをインポートし、BがAをインポートしている場合。Goコンパイラは通常、循環インポートをエラーとして検出しますが、初期化式の評価順序によっては、より複雑な形で再帰が発生する可能性があります。
*   **初期化式内の依存関係**: あるパッケージレベル変数の初期化式が、まだ完全に初期化されていない別のパッケージレベル変数や`init`関数に依存している場合。

このような状況では、初期化関数が自分自身を呼び出すか、または初期化中の別の初期化関数を呼び出すことになり、無限ループに陥る可能性があります。

## 技術的詳細

このコミットの核心は、Goコンパイラが生成するパッケージ初期化コードに、再帰検出のための状態管理メカニズムを組み込むことです。

### 状態変数の導入

以前は、各パッケージの初期化状態は`bool`型の`initdone·<file>`変数（例: `initdone·mypackage.go`）で管理されていました。これは、初期化が完了したかどうかを示す単純なフラグでした。

このコミットでは、`initdone·<file>`変数の型が`bool`から`uint8`に変更されます。この`uint8`変数は、初期化の進行状況をより詳細に追跡するための状態マシンとして機能します。

*   **`0`**: 初期化がまだ開始されていない状態。
*   **`1`**: 初期化が進行中である状態（依存パッケージの初期化やパッケージ自身の初期化式評価中）。
*   **`2`**: 初期化が完全に完了した状態。

### 初期化コードの変更

コンパイラが生成する各パッケージの初期化関数（`Init·<file>()`）は、以下のようなロジックを持つように変更されます。

1.  **初期化状態のチェック**: `Init·<file>()`が呼び出された際、まず`initdone·<file>`の値がチェックされます。
    *   もし`initdone·<file> == 2`であれば、そのパッケージは既に完全に初期化されているため、すぐに`return`します。これは通常の初期化完了ケースです。
    *   もし`initdone·<file> == 1`であれば、そのパッケージは現在初期化中であるにもかかわらず、再度初期化が試みられたことを意味します。これは再帰的な初期化の兆候であるため、`sys.throwinit()`を呼び出してパニックを引き起こします。
2.  **初期化開始のマーク**: `initdone·<file>`が`0`（未開始）の場合、`initdone·<file>`を`1`にインクリメントします。これにより、このパッケージが初期化中であることをマークします。
3.  **依存パッケージの初期化**: インポートしている他のパッケージの初期化関数を呼び出します。
4.  **パッケージ固有の初期化**: パッケージレベルの変数初期化式や`init`関数を実行します。
5.  **初期化完了のマーク**: パッケージ固有の初期化がすべて完了した後、`initdone·<file>`を再度インクリメントし、`2`にします。これにより、パッケージが完全に初期化されたことをマークします。
6.  **リターン**: 初期化関数から`return`します。

### `sys.throwinit`の導入

この変更では、ランタイムに新しいシステム関数`sys.throwinit`が追加されます。この関数は、再帰的な初期化が検出された際に呼び出され、`"recursive call during initialization"`というメッセージと共にパニックを発生させます。これにより、開発者は再帰初期化の問題を明確に特定できます。

## コアとなるコードの変更箇所

主要な変更は以下のファイルに集中しています。

1.  **`src/cmd/gc/builtin.c.boot`**:
    *   `sys.throwinit`という新しい組み込み関数がシステムインポートリストに追加されます。これは、コンパイラがランタイムの`throwinit`関数を呼び出せるようにするための宣言です。
2.  **`src/cmd/gc/dcl.c`**:
    *   `fninit`関数（パッケージ初期化コードを生成する部分）が大幅に修正されています。
    *   `initdone·<file>`変数の型が`TBOOL`（bool）から`TUINT8`（uint8）に変更されます。
    *   生成される初期化コードのロジックが、`uint8`の状態変数に基づいて再帰を検出するように変更されます。具体的には、`initdone·<file> == 1`の場合に`sys.throwinit()`を呼び出す条件分岐が追加されています。
    *   `initdone·<file>`変数のインクリメント（`++`）操作が導入され、状態遷移を管理します。
3.  **`src/cmd/gc/sinit.c`**:
    *   `initlin`関数内の`OLIST`ケースで、`goto loop`が導入されています。これは、初期化リストの処理方法に関する微調整であり、初期化コード生成のコンテキストでリストを効率的に処理するための変更と考えられます。直接的な再帰検出ロジックではありませんが、初期化コードの構造に関連しています。
4.  **`src/cmd/gc/sys.go`**:
    *   `func throwinit()`の宣言が追加されます。これはGoコンパイラが使用する内部的なシステム関数で、`builtin.c.boot`で宣言されたものに対応します。
5.  **`src/runtime/runtime.c`**:
    *   `sys·throwinit`関数の実装が追加されます。この関数は、`throw("recursive call during initialization")`を呼び出し、指定されたエラーメッセージでGoランタイムパニックを引き起こします。

## コアとなるコードの解説

`src/cmd/gc/dcl.c`の`fninit`関数における変更が最も重要です。

変更前の擬似コード:
```
var initdone·<file> bool
func Init·<file>() {
    if initdone·<file> { return } // 既に初期化済みなら終了
    initdone·<file> = true       // 初期化開始をマーク
    // 依存パッケージの初期化
    // パッケージ固有の初期化ステートメント
    // init関数があれば実行
    return
}
```

変更後の擬似コード（コメント内の番号はコミットのdiffに対応）:
```
var initdone·<file> uint8 // (1) boolからuint8に変更
func Init·<file>() {      // (2)
    if initdone·<file> != 0 { // (3) 初期化が開始されているかチェック
        if initdone·<file> == 2 { // (4) 完全に初期化済みなら終了
            return
        }
        // (5) initdone·<file> == 1 の場合、再帰初期化なのでパニック
        sys.throwinit() 
    }
    initdone·<file>++ // (6) 0 -> 1: 初期化中をマーク
    // (7) 依存パッケージの初期化
    // (8) パッケージ固有の初期化ステートメント
    // (9) init関数があれば実行
    initdone·<file>++ // (10) 1 -> 2: 初期化完了をマーク
    return            // (11)
}
```

この変更により、`initdone·<file>`が`1`の状態で再度`Init·<file>()`が呼び出された場合、それは再帰的な初期化サイクルが発生していることを意味するため、`sys.throwinit()`が呼び出され、プログラムはパニックで終了します。これにより、Goプログラムは再帰初期化による未定義の動作に陥ることなく、問題を早期に開発者に通知できるようになります。

`src/runtime/runtime.c`に追加された`sys·throwinit`関数は、このパニックメッセージを具体的に提供する役割を担います。

# [インデックス 25875] ファイルの概要

このコミットは、Go言語の標準ライブラリ `mime` パッケージ内の `mediatype.go` ファイルに対する変更です。`mime` パッケージは、MIME（Multipurpose Internet Mail Extensions）メディアタイプ（Content-Typeヘッダなどで使用される）の解析とフォーマットを扱うための機能を提供します。具体的には、`FormatMediaType` 関数が、スラッシュを含まないメディアタイプ（例: `Content-Disposition` ヘッダの値）も適切にフォーマットできるように修正されました。

## コミット

mime: let FormatMediaType format slash-less media types, to mirror ParseMediaType.

A Content-Type always has a slash (type/subtype)
A Content-Disposition does not (e.g. "attachment" or "line").
A "media type" is either one of those, plus optional parameters afterwards.

Our ParseMediaType and FormatMediaType weren't consistent in whether
they permitted Content-Dispositions. Now they both do.

Fixes #11289

## 元コミット内容

mime: let FormatMediaType format slash-less media types, to mirror ParseMediaType.

A Content-Type always has a slash (type/subtype)
A Content-Disposition does not (e.g. "attachment" or "line").
A "media type" is either one of those, plus optional parameters afterwards.

Our ParseMediaType and FormatMediaType weren't consistent in whether
they permitted Content-Dispositions. Now they both do.

Fixes #11289

## 変更の背景

この変更の背景には、`mime` パッケージ内の `ParseMediaType` 関数と `FormatMediaType` 関数の間に存在していた一貫性の欠如があります。

*   **`ParseMediaType`**: この関数は、`Content-Type` ヘッダのような「`type/subtype`」形式のメディアタイプだけでなく、`Content-Disposition` ヘッダの値のように「`attachment`」や「`inline`」といったスラッシュを含まない形式も解析できました。
*   **`FormatMediaType`**: 一方、この関数は、メディアタイプをフォーマットする際に、入力文字列が必ずスラッシュ（`/`）を含む「`type/subtype`」形式であることを前提としていました。スラッシュが含まれない文字列が入力された場合、空文字列を返していました。

この不一致により、`ParseMediaType` で正常に解析できたスラッシュなしのメディアタイプを、`FormatMediaType` で再フォーマットしようとすると失敗するという問題が発生していました。特に、`Content-Disposition` ヘッダの値はスラッシュを含まないことが一般的であり、このヘッダを扱う際に不便が生じていました。

この問題は、GitHub Issue #11289 で報告されており、このコミットはその問題を解決するために行われました。目的は、両関数がスラッシュの有無に関わらずメディアタイプ（またはそれに準ずる文字列）を一貫して扱えるようにすることです。

## 前提知識の解説

### MIMEメディアタイプ (Content-Type)

MIME（Multipurpose Internet Mail Extensions）メディアタイプは、インターネット上で転送されるデータの種類を識別するための標準的な方法です。主にHTTPヘッダの `Content-Type` や電子メールの添付ファイルなどで使用されます。

*   **構造**: 基本的に「`type/subtype`」の形式を取ります（例: `text/html`, `image/jpeg`, `application/json`）。
    *   `type`: 大分類を示します（例: `text`, `image`, `application`）。
    *   `subtype`: 小分類を示します（例: `html`, `jpeg`, `json`）。
*   **パラメータ**: メディアタイプには、セミコロン（`;`）で区切られたオプションのパラメータを含めることができます（例: `text/html; charset=utf-8`）。
*   **RFC**: MIMEメディアタイプは、RFC 2045（MIMEの基本構造）およびRFC 6838（メディアタイプ登録手続き）などで定義されています。

### Content-Disposition ヘッダ

`Content-Disposition` ヘッダは、HTTPレスポンスや電子メールのMIMEパートにおいて、そのコンテンツがどのように表示または処理されるべきかを示すために使用されます。

*   **目的**: 主に、ブラウザがファイルを表示するのか（`inline`）、それともダウンロードを促すのか（`attachment`）を制御するために使われます。
*   **値の形式**: `Content-Type` とは異なり、`Content-Disposition` の値は必ずしも「`type/subtype`」の形式を取りません。例えば、「`attachment`」や「`inline`」といった単一のトークンが使われることがあります。また、`filename` などのパラメータを含むこともあります（例: `attachment; filename="report.pdf"`）。
*   **RFC**: `Content-Disposition` ヘッダは、RFC 2183（電子メールにおけるContent-Disposition）およびRFC 6266（HTTPにおけるContent-Disposition）などで定義されています。

### `isToken` 関数

Goの `mime` パッケージにおける `isToken` 関数は、RFCで定義されている「トークン」の規則に従って文字列が有効なトークンであるかをチェックするユーティリティ関数です。トークンは、特定の文字セット（英数字と一部の記号）のみで構成される文字列であり、空白や特殊文字を含まないことが保証されます。これは、ヘッダ名や一部のヘッダ値の構成要素として重要です。

## 技術的詳細

このコミットの技術的な核心は、`FormatMediaType` 関数が入力されたメディアタイプ文字列 `t` にスラッシュが含まれているかどうかを条件分岐で判断し、それぞれ異なる処理を行うように変更された点です。

変更前は、`FormatMediaType` は常に `strings.Index(t, "/")` を呼び出し、スラッシュが見つからない場合は即座に空文字列を返していました。これは、`Content-Type` のような「`type/subtype`」形式のみを想定していたためです。

変更後は、以下のロジックが導入されました。

1.  `slash := strings.Index(t, "/")` でスラッシュの位置を検索します。
2.  `if slash == -1` の条件で、スラッシュが見つからなかった場合（つまり、`Content-Disposition` の値のようなスラッシュなしの形式の場合）の処理が追加されました。
    *   この場合、入力文字列 `t` 全体が有効なトークンであるか `isToken(t)` でチェックされます。
    *   有効なトークンであれば、その文字列全体を小文字に変換してバッファに書き込みます。
3.  スラッシュが見つかった場合（従来の `Content-Type` のような形式の場合）は、以前と同様に `major` と `sub` に分割し、それぞれが有効なトークンであるか `isToken` でチェックした後、小文字に変換して「`major/sub`」の形式でバッファに書き込みます。

この変更により、`FormatMediaType` は `ParseMediaType` と同様に、スラッシュの有無にかかわらずメディアタイプ（またはそれに準ずる文字列）を適切に処理できるようになり、両関数間の一貫性が保たれました。

## コアとなるコードの解説

### `src/mime/mediatype.go` の変更

変更の核心は `FormatMediaType` 関数の冒頭部分です。

1.  **旧コード**:
    ```go
    	slash := strings.Index(t, "/")
    	if slash == -1 {
    		return ""
    	}
    	major, sub := t[:slash], t[slash+1:]
    	if !isToken(major) || !isToken(sub) {
    		return ""
    	}
    	var b bytes.Buffer
    	b.WriteString(strings.ToLower(major))
    	b.WriteByte('/')
    	b.WriteString(strings.ToLower(sub))
    ```
    このコードは、入力 `t` にスラッシュが含まれていない場合（`slash == -1`）、即座に空文字列を返していました。これは、`Content-Disposition` のようなスラッシュなしの値を処理できないことを意味します。

2.  **新コード**:
    ```go
    	var b bytes.Buffer
    	if slash := strings.Index(t, "/"); slash == -1 {
    		if !isToken(t) {
    			return ""
    		}
    		b.WriteString(strings.ToLower(t))
    	} else {
    		major, sub := t[:slash], t[slash+1:]
    		if !isToken(major) || !isToken(sub) {
    			return ""
    		}
    		b.WriteString(strings.ToLower(major))
    		b.WriteByte('/')
    		b.WriteString(strings.ToLower(sub))
    	}
    ```
    新しいコードでは、まず `strings.Index(t, "/")` でスラッシュの位置を検索します。
    *   **`slash == -1` の場合（スラッシュなし）**:
        *   入力文字列 `t` 全体が `isToken(t)` によって有効なトークンであるかチェックされます。
        *   有効であれば、`t` を小文字に変換して `bytes.Buffer` に直接書き込みます。これにより、「`attachment`」のようなスラッシュなしのメディアタイプが正しくフォーマットされます。
    *   **`slash != -1` の場合（スラッシュあり）**:
        *   従来のロジックが実行されます。`t` を `major` と `sub` に分割し、それぞれが `isToken` でチェックされた後、「`major/sub`」の形式でバッファに書き込まれます。

この変更により、`FormatMediaType` は `Content-Type` と `Content-Disposition` の両方のユースケースに対応できるようになりました。

### `src/mime/mediatype_test.go` の変更

テストファイルでは、`formatTests` スライス内のテストケースが一つ変更されています。

*   **旧テストケース**:
    ```go
    {"noslash", nil, ""},
    ```
    これは、「`noslash`」という入力に対して、期待される出力が空文字列であることを示していました。つまり、スラッシュがない場合はフォーマットに失敗するという旧来の動作をテストしていました。

*   **新テストケース**:
    ```go
    {"noslash", map[string]string{"X": "Y"}, "noslash; x=Y"}, // e.g. Content-Disposition values (RFC 2183); issue 11289
    ```
    新しいテストケースでは、「`noslash`」という入力とパラメータ `{"X": "Y"}` に対して、期待される出力が「`noslash; x=Y`」となっています。これは、スラッシュを含まないメディアタイプがパラメータと共に正しくフォーマットされることを検証しています。コメントには `Content-Disposition` の値の例（RFC 2183）と関連するIssue番号が明記されており、この変更の意図が明確に示されています。

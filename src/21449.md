# [インデックス 21449] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおけるTLS再ネゴシエーション拡張の処理に関するバグを修正するものです。具体的には、`ClientHello` メッセージのパース時に、再ネゴシエーション情報拡張 (Renegotiation Info Extension) のタイプを誤って比較していた「+ 1」というデバッグコードの残存を修正し、関連するテストを追加しています。このバグは、Firefoxブラウザで `security.ssl.require_safe_negotiation` 設定が有効になっている場合に、TLS接続の確立を妨げる可能性がありました。

## 元コミット内容

Go言語の `crypto/tls` パッケージにおいて、TLS再ネゴシエーション拡張の処理に存在するバグを修正します。このバグは、デバッグコードの残存により、`ClientHello` メッセージのパース時に再ネゴシエーション情報拡張のタイプを誤って比較していたことに起因します。この修正により、特にFirefoxブラウザの特定のセキュリティ設定下での接続問題を解決し、関連するテストを追加します。

## 変更の背景

この変更の背景には、TLS (Transport Layer Security) プロトコルにおける「再ネゴシエーション」の脆弱性と、それを解決するために導入された「セキュアな再ネゴシエーション」の仕組みがあります。

2009年に、TLSの再ネゴシエーション機能に重大な脆弱性 (CVE-2009-3555) が発見されました。この脆弱性は、攻撃者が既存のTLSセッションに自身のデータを挿入し、あたかも正規のクライアントから送信されたかのように見せかけることを可能にするものでした。これにより、セッションハイジャックや不正なリクエストの挿入といった攻撃が可能になります。

この脆弱性に対処するため、RFC 5746「Transport Layer Security (TLS) Renegotiation Indication Extension」が策定されました。このRFCは、再ネゴシエーションを既存のTLS接続に暗号学的に紐付けるメカニズムを定義しています。これにより、攻撃者が再ネゴシエーションプロセス中にデータを挿入したり、クライアントになりすましたりすることを防ぎます。セキュアな再ネゴシエーションは、主に2つの方法でクライアントによって通知されます。一つは特別な暗号スイート値 (`TLS_EMPTY_RENEGOTIATION_INFO_SCSV`) を使用する方法、もう一つはTLS拡張 (`renegotiation_info` 拡張) を使用する方法です。

Go言語の `crypto/tls` パッケージは、TLSプロトコルを実装しており、セキュアな再ネゴシエーションのサポートも含まれています。しかし、このコミットが示すように、`renegotiation_info` 拡張の処理において、デバッグコードが誤って残存していました。具体的には、`ClientHello` メッセージをパースする際に、`extensionRenegotiationInfo` の値に「+ 1」を加算して比較していたため、正しい拡張を認識できませんでした。

この小さなバグは、通常は大きな問題を引き起こしませんでしたが、Firefoxブラウザの `about:config` 設定にある `security.ssl.require_safe_negotiation` が有効になっている場合に顕在化しました。この設定は、Firefoxがセキュアな再ネゴシエーションを厳密に要求することを意味します。GoのTLS実装がこの拡張を正しく処理できないため、Firefoxはセキュアな再ネゴシエーションがサポートされていないと判断し、接続を拒否していました。

このコミットは、このデバッグコードの残存を修正し、GoのTLS実装が `renegotiation_info` 拡張を正しく認識できるようにすることで、Firefoxとの互換性の問題を解決することを目的としています。また、この種のバグを将来的に防ぐためのテストも追加されています。

## 前提知識の解説

### TLS/SSL (Transport Layer Security / Secure Sockets Layer)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。SSLの後継として開発され、現在ではTLSが広く利用されています。ウェブブラウジング（HTTPS）、電子メール、VoIPなど、様々なアプリケーションでデータの機密性、完全性、認証を保証するために使用されます。

**TLSハンドシェイク**: TLS接続が確立される際に、クライアントとサーバーの間で行われる一連のメッセージ交換です。このプロセスで、プロトコルバージョン、暗号スイート、鍵交換アルゴリズム、デジタル証明書などがネゴシエートされ、セッション鍵が生成されます。

### TLS 拡張 (TLS Extensions)

TLS拡張は、TLSプロトコルのコア機能を拡張するためのメカニズムです。`ClientHello` や `ServerHello` などのハンドシェイクメッセージに含めることができ、新しい機能やプロトコルの改善を既存のTLSバージョンに導入するために使用されます。各拡張には一意のタイプコードが割り当てられています。

### セキュアな再ネゴシエーション (Secure Renegotiation) と RFC 5746

前述の通り、TLSの再ネゴシエーション機能には脆弱性 (CVE-2009-3555) が存在しました。これを解決するために、RFC 5746「Transport Layer Security (TLS) Renegotiation Indication Extension」が策定されました。

RFC 5746は、以下の2つの主要なメカニズムを導入しています。

1.  **`TLS_EMPTY_RENEGOTIATION_INFO_SCSV` (Signaling Cipher Suite Value)**: これは、クライアントがセキュアな再ネゴシエーションをサポートしていることをサーバーに通知するための特別な暗号スイート値です。
2.  **`renegotiation_info` 拡張**: これは、ハンドシェイクメッセージに含まれるTLS拡張であり、再ネゴシエーションが既存のセッションに暗号学的に紐付けられていることを示すための情報を含みます。この拡張は、クライアントとサーバーの両方がセキュアな再ネゴシエーションをサポートしている場合に利用されます。拡張のタイプコードは `0xff01` (65281) です。

このコミットで問題となっていたのは、この `renegotiation_info` 拡張の処理でした。

### Go言語の `crypto/tls` パッケージ

Go言語の標準ライブラリには、TLSプロトコルを実装した `crypto/tls` パッケージが含まれています。このパッケージは、Goアプリケーションで安全なネットワーク通信を実装するための基盤を提供します。クライアントとサーバーの両方の機能を提供し、証明書の検証、鍵交換、暗号化、復号化などを扱います。

### Firefoxの `security.ssl.require_safe_negotiation`

Firefoxブラウザには、`about:config` ページからアクセスできる詳細設定があります。その中の一つに `security.ssl.require_safe_negotiation` があります。

*   **`true` に設定されている場合**: Firefoxは、セキュアな再ネゴシエーションを厳密に要求します。サーバーがRFC 5746に準拠したセキュアな再ネゴシエーションをサポートしていない場合、またはその拡張を正しく処理できない場合、Firefoxは接続を拒否し、エラー (`SSL_ERROR_UNSAFE_NEGOTIATION` など) を表示します。
*   **`false` に設定されている場合 (デフォルト)**: Firefoxは、セキュアな再ネゴシエーションを要求しません。これにより、古いサーバーやセキュアな再ネゴシエーションをサポートしていないサーバーとも接続できますが、潜在的な脆弱性に対しては保護されません。

このコミットのバグは、Goの `crypto/tls` が `renegotiation_info` 拡張を正しく処理できなかったため、`security.ssl.require_safe_negotiation` が `true` のFirefoxとの接続が失敗するという形で現れました。

## 技術的詳細

このコミットの核心的な問題は、`src/crypto/tls/handshake_messages.go` ファイル内の `clientHelloMsg` の `unmarshal` メソッドにありました。このメソッドは、受信した `ClientHello` メッセージのバイト列をGoのデータ構造に変換（アンマーシャル）する役割を担っています。

`ClientHello` メッセージには、クライアントがサポートする様々なTLS拡張が含まれることがあります。`unmarshal` メソッドは、これらの拡張をループで処理し、それぞれの拡張タイプに基づいて適切な処理を行います。問題の箇所は、`renegotiation_info` 拡張を処理する `switch` ステートメントの `case` 文にありました。

元のコードでは、`extensionRenegotiationInfo` という定数（これは `renegotiation_info` 拡張の正しいタイプコード、すなわち `0xff01` を表す）に対して、誤って「`+ 1`」が追加されていました。

```go
// src/crypto/tls/handshake_messages.go (修正前)
case extensionRenegotiationInfo + 1: // <-- ここが問題
    if length != 1 || data[0] != 0 {
        return false
    }
```

これは、`extensionRenegotiationInfo` の実際の値が `0xff01` であるにもかかわらず、コードが `0xff01 + 1`、つまり `0xff02` の拡張タイプを探していたことを意味します。結果として、GoのTLSサーバーは、クライアントから送信された正しい `renegotiation_info` 拡張を認識できず、あたかもその拡張が提供されていないかのように振る舞っていました。

この「+ 1」は、コミットメッセージにもあるように、おそらくデバッグ中に誤って残されたコードであると考えられます。開発者が一時的に別の拡張タイプをテストしたり、オフセットを試したりした際に、その変更が元に戻されずにコミットされてしまった可能性があります。

このバグがFirefoxの `security.ssl.require_safe_negotiation` 設定に影響を与えたのは、Firefoxがこの設定が有効な場合、サーバーが `renegotiation_info` 拡張を正しく処理し、セキュアな再ネゴシエーションをサポートしていることを厳密に期待するためです。Goのサーバーがこの拡張を認識できないと、Firefoxはサーバーがセキュアな再ネゴシエーションをサポートしていないと判断し、セキュリティポリシーに反するため接続を拒否していました。

修正は非常に単純で、この誤った「+ 1」を取り除くことによって、GoのTLS実装が `renegotiation_info` 拡張の正しいタイプコード `0xff01` を認識できるようにします。

また、このコミットでは、このバグを検出するための新しいテストケースが `src/crypto/tls/handshake_server_test.go` に追加されています。このテストは、`net.Pipe()` を使用してクライアントとサーバー間の通信をシミュレートし、クライアントが `secureRenegotiation` フラグをセットした `ClientHello` を送信した際に、サーバーが `ServerHello` で `secureRenegotiation` 拡張を正しくエコーバックするかどうかを検証します。これにより、GoのTLS実装がセキュアな再ネゴシエーション拡張を正しく処理していることを保証します。

## コアとなるコードの解説

### `src/crypto/tls/handshake_messages.go` の変更

このファイルでは、`clientHelloMsg` 構造体の `unmarshal` メソッドが修正されています。このメソッドは、クライアントから受信した `ClientHello` メッセージのバイト列をGoの内部表現に変換する際に、含まれるTLS拡張を解析します。

変更点:

```go
-		case extensionRenegotiationInfo + 1:
+		case extensionRenegotiationInfo:
```

この1行の変更が、このコミットの最も重要な修正点です。
*   `extensionRenegotiationInfo` は、TLSの `renegotiation_info` 拡張のタイプコード（`0xff01`）を表す定数です。
*   修正前は、この定数に誤って `+ 1` が加算されていました。これは、`ClientHello` メッセージ内の拡張タイプが `0xff01` であるにもかかわらず、コードが `0xff02` を探していたことを意味します。
*   この修正により、`switch` ステートメントは正しい `extensionRenegotiationInfo` のタイプコードにマッチするようになり、GoのTLSサーバーはクライアントが送信した `renegotiation_info` 拡張を正しく認識できるようになりました。
*   その結果、サーバーはセキュアな再ネゴシエーションをサポートしていることをクライアントに適切に通知できるようになり、Firefoxの `security.ssl.require_safe_negotiation` 設定が有効な場合でも接続が成功するようになります。

### `src/crypto/tls/handshake_server_test.go` の変更

このファイルには、`TestRenegotiationExtension` という新しいテスト関数が追加されています。このテストは、GoのTLSサーバーが `renegotiation_info` 拡張を正しく処理できることを検証するために設計されています。

テストの主な流れ:

1.  **`clientHelloMsg` の準備**:
    *   `clientHello` オブジェクトが作成され、`VersionTLS12` (TLS 1.2) を使用し、`secureRenegotiation` フラグが `true` に設定されています。これは、クライアントがセキュアな再ネゴシエーションをサポートしていることを示す `ClientHello` メッセージをシミュレートします。
2.  **パイプのセットアップ**:
    *   `net.Pipe()` を使用して、インメモリのネットワーク接続（パイプ）を作成します。これにより、実際のネットワークソケットを使用せずに、クライアントとサーバー間の通信をシミュレートできます。`c` はクライアント側、`s` はサーバー側の接続を表します。
3.  **クライアントのシミュレーション**:
    *   ゴルーチン内でクライアント側の処理が実行されます。
    *   `Client(c, testConfig)` でクライアントのTLS接続が初期化されます。
    *   `cli.writeRecord(recordTypeHandshake, clientHello.marshal())` を呼び出して、準備した `ClientHello` メッセージをサーバーに送信します。
    *   サーバーからの応答（`ServerHello`）を読み取り、`c.Close()` で接続を閉じます。
4.  **サーバーの処理**:
    *   メインゴルーチンでサーバー側の処理が実行されます。
    *   `Server(s, testConfig).Handshake()` を呼び出して、サーバーがクライアントからの `ClientHello` を受け取り、TLSハンドシェイクを実行するようにします。
5.  **応答の検証**:
    *   サーバーが送信した `ServerHello` メッセージ（`buf` に格納されている）をパースします。
    *   `serverHello.unmarshal()` を使用して、`ServerHello` メッセージのバイト列を `serverHelloMsg` 構造体に変換します。
    *   最後に、`if !serverHello.secureRenegotiation` のチェックを行います。これは、サーバーがクライアントの `secureRenegotiation` フラグを正しく認識し、自身の `ServerHello` メッセージでそれをエコーバックしているかどうかを検証します。もしエコーバックされていなければ、テストは失敗し、バグが存在することを示します。

このテストは、`net.Pipe()` を使用することで、実際のネットワーク環境に依存せずに、TLSハンドシェイクの特定の側面（この場合は再ネゴシエーション拡張の処理）を分離してテストできるため、非常に効果的です。

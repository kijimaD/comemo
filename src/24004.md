# [インデックス 24004] ファイルの概要

このコミットは、Go言語の `encoding/asn1` パッケージにおける日付・時刻のパース処理の厳格化に関するものです。具体的には、`UTCTime` および `GeneralizedTime` のパースにおいて、Goの `time` パッケージが持つ「無効な日付の正規化」という挙動によって、本来拒否されるべき不正な時刻文字列が受け入れられてしまう問題を修正しています。この修正により、パースされた時刻が元の文字列と正確にラウンドトリップするかどうかを検証することで、より厳格な入力チェックが実現されました。

変更されたファイルは以下の通りです。

*   `src/encoding/asn1/asn1.go`: `parseUTCTime` および `parseGeneralizedTime` 関数に、パース後の再シリアライズと元の入力との比較ロジックが追加されました。
*   `src/encoding/asn1/asn1_test.go`: 不正な時刻文字列が `time` パッケージによって正規化されるケースを捕捉するための新しいテストケースが追加されました。

## コミット

```
encoding/asn1: be stricter by reserialising parsed times.

The time package does normalisation of times: for example day zero is
converted to the last day of the previous month and the 31st of February
is moved into March etc. This makes the ASN.1 parsing a little
worryingly lax.

This change causes the parser to reserialise parsed times to ensure that
they round-trip correctly and thus were not normalised.

Fixes #11134.
```

`encoding/asn1`: パースされた時刻を再シリアライズすることで、より厳格にする。

`time` パッケージは時刻の正規化を行う。例えば、0日目は前月の最終日に変換され、2月31日は3月に移動されるなどである。これにより、ASN.1のパースが少し心配になるほど緩くなっていた。

この変更は、パースされた時刻が正しくラウンドトリップし、したがって正規化されなかったことを保証するために、パース後に時刻を再シリアライズするようにする。

## 変更の背景

この変更の背景には、Go言語の標準ライブラリである `encoding/asn1` パッケージが、抽象構文記法1 (ASN.1) で定義された日付・時刻形式（特に `UTCTime` と `GeneralizedTime`）をパースする際のセキュリティと堅牢性の問題がありました。

Goの `time` パッケージの `time.Parse` 関数は、非常に柔軟なパース機能を提供しますが、その柔軟性ゆえに、一部の「無効な」日付や時刻の表現を自動的に「有効な」日付に正規化してしまうという挙動を持っています。例えば、「2月31日」のような存在しない日付をパースしようとすると、`time.Parse` はエラーを返さずに「3月2日」として解釈してしまうことがあります。同様に、「0日目」を前月の最終日として扱うなどの正規化が行われます。

ASN.1は、X.509証明書やCRLs（証明書失効リスト）など、セキュリティ上重要なプロトコルで広く利用されています。これらの文脈において、日付・時刻のフィールドは厳密な形式と値の範囲が求められます。もし `encoding/asn1` が `time.Parse` の正規化挙動をそのまま受け入れてしまうと、以下のような問題が発生する可能性がありました。

1.  **セキュリティ脆弱性**: 攻撃者が意図的に不正な日付を含む証明書を作成し、それが正規化されて有効な日付として扱われた場合、証明書の有効期限チェックなどが誤動作し、システムが不正な証明書を受け入れてしまう可能性があります。これは、認証や認可のメカニズムを迂回する手段となり得ます。
2.  **相互運用性の問題**: 他のシステムがより厳格なASN.1日付パースロジックを持っている場合、Goで生成またはパースされたデータが、他のシステムでは不正と見なされる可能性があります。これは、異なるシステム間でのデータ交換やプロトコル通信において問題を引き起こします。
3.  **予期せぬ動作**: 開発者が意図しない日付の解釈が行われることで、アプリケーションのロジックが期待通りに動作しない可能性があります。

このコミットは、このような「緩い」パース挙動を修正し、ASN.1の仕様に厳密に従った日付・時刻の検証を行うことを目的としています。

## 前提知識の解説

### ASN.1 (Abstract Syntax Notation One)

ASN.1は、データ構造を記述するための国際標準です。異なるコンピュータシステム間でデータを交換する際に、データの表現形式を明確に定義するために使用されます。特に、通信プロトコル、暗号化、デジタル証明書（X.509）などの分野で広く利用されています。ASN.1は、データの型（整数、文字列、シーケンスなど）とエンコーディングルール（BER, DER, PERなど）を定義します。

### UTCTime と GeneralizedTime

ASN.1では、日付と時刻を表現するための特定の型が定義されています。

*   **UTCTime**:
    *   形式: `YYMMDDhhmmssZ` または `YYMMDDhhmmss+hhmm` / `YYMMDDhhmmss-hhmm`
    *   特徴: 年が2桁で表現されます。通常、1950年から2049年までの日付を扱います。RFC 5280などの標準では、2050年以降の日付は `GeneralizedTime` を使用すべきとされています。
    *   例: `991231235959Z` (1999年12月31日 23:59:59 UTC)
*   **GeneralizedTime**:
    *   形式: `YYYYMMDDhhmmssZ` または `YYYYMMDDhhmmss.fffZ` など、より柔軟な形式。
    *   特徴: 年が4桁で表現され、より広い範囲の日付を扱えます。ミリ秒以下の精度も表現可能です。
    *   例: `20230101120000Z` (2023年1月1月 12:00:00 UTC)

これらの時刻形式は、デジタル証明書の有効期間 (`validity` フィールド) など、セキュリティ上重要な情報で利用されます。

### Goの `time` パッケージの正規化挙動

Goの `time` パッケージの `time.Parse` 関数は、指定されたレイアウト文字列に基づいて時刻文字列を `time.Time` オブジェクトに変換します。この関数は、ユーザーフレンドリーな設計思想から、一部の「論理的に無効な」日付表現を自動的に「有効な」日付に調整（正規化）する挙動を持っています。

例:
*   `time.Parse("20060102", "20230231")` は、2023年2月31日という存在しない日付を、自動的に2023年3月3日としてパースします。
*   `time.Parse("20060102", "20230100")` は、2023年1月0日という存在しない日付を、自動的に2022年12月31日としてパースします。

この正規化は、一般的なアプリケーションでは便利ですが、ASN.1のように厳密な仕様が求められる文脈では、不正な入力を誤って受け入れてしまう原因となります。

### ラウンドトリップテスト

ラウンドトリップテストとは、データをある形式から別の形式に変換し、その結果を再度元の形式に戻したときに、元のデータと変換後のデータが完全に一致するかどうかを確認するテスト手法です。

このコミットの文脈では、以下のステップでラウンドトリップテストが行われます。
1.  入力された時刻文字列（例: `s`）を `time.Parse` で `time.Time` オブジェクトにパースする（例: `ret`）。
2.  パースされた `time.Time` オブジェクト（`ret`）を、**元のパースに使用したのと同じフォーマット文字列**で再度文字列にフォーマットする（例: `serialized`）。
3.  元の入力文字列 `s` と再フォーマットされた文字列 `serialized` を比較する。

もし `s != serialized` であれば、`time.Parse` が元の時刻文字列を正規化したことを意味します。これは、元の時刻文字列がASN.1の厳密な要件を満たさない不正な形式であったことを示唆するため、エラーとして処理されるべきです。

## 技術的詳細

このコミットの核心は、`encoding/asn1` パッケージ内の `parseUTCTime` および `parseGeneralizedTime` 関数における、Goの `time` パッケージの正規化挙動への対処です。

従来の `encoding/asn1` の実装では、入力されたバイト列を直接 `string` に変換し、それを `time.Parse` に渡していました。`time.Parse` は、前述の通り、無効な日付（例: 2月31日）を自動的に有効な日付に調整する機能を持っています。この挙動は、ASN.1の厳格な日付フォーマット要件とは相容れませんでした。ASN.1では、日付文字列は特定の形式に厳密に従う必要があり、仕様外の表現はエラーとして拒否されるべきです。

この問題を解決するため、コミットでは「パース後の再シリアライズによる検証」という手法が導入されました。

1.  **時刻文字列のパース**:
    まず、入力されたバイト列（ASN.1の時刻データ）は `string(bytes)` で文字列に変換され、`time.Parse` 関数に渡されます。`parseUTCTime` では、`0601021504Z0700` (YYMMDDhhmmZ) と `060102150405Z0700` (YYMMDDhhmmssZ) の2つのフォーマットを試行します。`parseGeneralizedTime` では `20060102150405Z0700` (YYYYMMDDhhmmssZ) を使用します。

2.  **パース結果の再シリアライズ**:
    `time.Parse` によって `time.Time` オブジェクト（`ret`）が正常に生成された後、この `ret` オブジェクトを、**元のパースに使用したのと同じフォーマット文字列** (`formatStr`) を用いて再度文字列にフォーマットします。この結果は `serialized` という変数に格納されます。

3.  **元の入力との比較**:
    再シリアライズされた文字列 `serialized` と、元の入力文字列 `s` を比較します。
    `if serialized := ret.Format(formatStr); serialized != s { ... }`

    *   もし `serialized == s` であれば、`time.Parse` は元の入力文字列を一切変更せずに `time.Time` オブジェクトに変換できたことを意味します。これは、入力が有効なASN.1時刻文字列であったことを示します。
    *   もし `serialized != s` であれば、`time.Parse` が入力文字列を正規化したことを意味します。例えば、「2月31日」が「3月2日」に変換された場合、再シリアライズすると「3月2日」の文字列が生成され、元の「2月31日」とは一致しません。この不一致は、元の入力がASN.1の厳密な要件を満たさない不正な形式であったことを明確に示します。

4.  **エラー処理**:
    `serialized != s` の場合、`fmt.Errorf("asn1: time did not serialize back to the original value and may be invalid: given %q, but serialized as %q", s, serialized)` というエラーを返してパースを拒否します。これにより、不正なASN.1時刻文字列がシステムに受け入れられることを防ぎます。

このアプローチは、`time.Parse` の柔軟性を利用しつつ、その副作用である正規化を検出し、ASN.1の厳格な検証要件を満たすための効果的な手段です。テストファイル `asn1_test.go` には、この正規化挙動によって以前は受け入れられていたが、本来は不正であるべき時刻文字列のテストケースが多数追加されており、この修正が意図通りに機能することを確認しています。

## コアとなるコードの解説

このコミットの主要な変更は、`parseUTCTime` と `parseGeneralizedTime` 関数に導入された以下のパターンです。

```go
	// 時刻文字列をパース
	ret, err = time.Parse(formatStr, s)
	if err != nil {
		return // パースエラーがあれば即座に終了
	}

	// パースされた時刻を元のフォーマットで再シリアライズ
	if serialized := ret.Format(formatStr); serialized != s {
		// 再シリアライズ結果が元の文字列と異なる場合、正規化が行われたと判断しエラーを返す
		err = fmt.Errorf("asn1: time did not serialize back to the original value and may be invalid: given %q, but serialized as %q", s, serialized)
		return
	}
```

1.  **`s := string(bytes)`**: 入力されたバイト列をGoの文字列 `s` に変換します。これが元の入力となります。
2.  **`ret, err = time.Parse(formatStr, s)`**: `time.Parse` を使用して、`s` を `time.Time` オブジェクト `ret` にパースします。`formatStr` は、`UTCTime` または `GeneralizedTime` の標準的なフォーマット文字列です。
3.  **`if err != nil { return }`**: `time.Parse` 自体がパースに失敗した場合（例: フォーマットが全く異なる場合）は、通常のエラー処理として関数を終了します。
4.  **`if serialized := ret.Format(formatStr); serialized != s { ... }`**: ここがこの変更の肝となる部分です。
    *   `ret.Format(formatStr)`: パースして得られた `time.Time` オブジェクト `ret` を、**元のパースに使用したのと同じ `formatStr` を使って**再び文字列に変換します。この結果が `serialized` です。
    *   `serialized != s`: `serialized` と元の入力文字列 `s` を比較します。
        *   もし両者が一致しない場合、それは `time.Parse` が `s` をパースする際に、何らかの正規化（例: 2月31日を3月3日に変更）を行ったことを意味します。ASN.1の厳格な要件では、このような正規化は許容されず、元の入力が不正であると見なされるべきです。
        *   このため、`fmt.Errorf(...)` を使って、元の入力と再シリアライズ結果の不一致を詳細に含むエラーメッセージを生成し、パースを拒否します。

このロジックにより、`time.Parse` の柔軟な正規化挙動を逆手に取り、ASN.1の厳密な日付・時刻形式に合致しない入力を確実に検出して拒否することが可能になりました。これにより、`encoding/asn1` パッケージの堅牢性とセキュリティが向上しています。

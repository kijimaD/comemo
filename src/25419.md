## 変更の背景

Thread-Local Storage (TLS) は、各スレッドが独自のデータコピーを持つことを可能にするメカニズムです。これは、グローバル変数や静的変数がスレッド間で共有されるのではなく、スレッドごとに独立した状態を保持する必要がある場合に特に重要です。例えば、エラーコード、乱数ジェネレータの状態、または特定のライブラリのコンテキスト情報などがTLSに格納されることがあります。

ARM64アーキテクチャにおいて、TLS変数へのアクセス方法にはいくつかのモデルが存在します。Goのツールチェーンは、これまで主に「local-exec」モデルをサポートしていたと考えられます。しかし、より複雑なリンケージシナリオや、特に共有ライブラリ（ダイナミックリンクライブラリ）を使用する場合において、「initial-exec」モデルのサポートが求められることがあります。

「initial-exec」モデルは、プログラムの起動時にすべてのTLS変数のオフセットが決定され、その後は固定のアドレス計算でアクセスできるため、実行時のパフォーマンスが向上する可能性があります。このコミットは、GoがARM64上でより効率的かつ柔軟にTLSを扱えるようにするための基盤を強化することを目的としています。

## 前提知識の解説

### Thread-Local Storage (TLS)

TLSは、マルチスレッドプログラミングにおいて、各スレッドがグローバル変数や静的変数の独自のコピーを持つことを可能にする記憶域クラスです。これにより、スレッド間のデータ競合を避けることができ、スレッドセーフなコードをより簡単に記述できます。C/C++では`__thread`キーワードや`pthread_getspecific`/`pthread_setspecific`などのAPIを通じて利用されます。Go言語では、ランタイムが内部的にTLSを利用することがありますが、ユーザーが直接TLSを操作するような言語機能は提供されていません。しかし、Goのランタイム自体が特定のプラットフォーム固有の機能（例えば、スケジューラやガベージコレクタの内部状態）を管理するためにTLSを利用することがあります。

### TLSアクセスモデル

ELF (Executable and Linkable Format) 形式のバイナリでは、TLS変数へのアクセス方法に関していくつかのモデルが定義されています。主なものとして「local-exec」と「initial-exec」があります。

1.  **Local-exec (ローカル実行) モデル**:
    *   このモデルは、実行可能ファイル自体がTLS変数を定義し、共有ライブラリがTLS変数を定義しない場合に最も効率的です。
    *   TLS変数のオフセットは、スレッドのTLSブロックの先頭からの相対オフセットとして、コンパイル時またはリンク時に完全に解決されます。
    *   実行時には、スレッドのTLSブロックのベースアドレス（通常は特定のレジスタに保持される）に直接オフセットを加算することでTLS変数にアクセスできます。
    *   このモデルは、単一の実行可能ファイル内で完結するTLSアクセスに適しています。

2.  **Initial-exec (初期実行) モデル**:
    *   このモデルは、実行可能ファイルと、それにリンクされるすべての共有ライブラリが、TLS変数を定義する可能性がある場合に適しています。
    *   プログラムの起動時（初期化時）に、すべてのTLS変数のオフセットが動的リンカによって決定され、グローバルオフセットテーブル (GOT) やプロシージャリンケージテーブル (PLT) のようなデータ構造に格納されます。
    *   TLS変数へのアクセスは、まずGOTからその変数のオフセットをロードし、そのオフセットをスレッドのTLSブロックのベースアドレスに加算することで行われます。
    *   Local-execモデルよりも間接的なアクセスになるため、わずかにオーバーヘッドがありますが、共有ライブラリを介したTLSアクセスを可能にします。

### ARM64アーキテクチャ

ARM64 (AArch64) は、ARMv8-A命令セットアーキテクチャに基づく64ビットプロセッサアーキテクチャです。モバイルデバイスからサーバーまで幅広い分野で採用されています。TLSへのアクセスは、通常、`TPIDR_EL0`レジスタ（または同等のレジスタ）に格納されたスレッドポインタを基点として行われます。TLS変数のオフセットを計算し、このスレッドポインタに加算することで、各スレッド固有のデータにアクセスします。

### Goツールチェーンの構成要素

*   **`cmd/internal/obj`**: Goのアセンブラとオブジェクトファイル生成を担当するパッケージです。Goのソースコード（またはGoのアセンブリコード）が機械語に変換される過程で、シンボル、リロケーション情報、および命令が生成されます。TLS変数への参照もここで適切な形式に変換されます。
*   **`cmd/link`**: Goのリンカです。オブジェクトファイルを結合して実行可能ファイルや共有ライブラリを生成します。この過程で、リロケーションエントリが解決され、TLS変数へのアクセスコードが最終的なアドレスに解決されます。特に、ELFバイナリのリロケーションタイプを理解し、適切に処理する役割を担います。

## 技術的詳細

このコミットは、ARM64アーキテクチャにおけるTLSの「initial-exec」モデルをサポートするために、Goのコンパイラバックエンドとリンカに複数の変更を導入しています。

1.  **新しいTLSクラスの導入 (`a.out.go`, `anames7.go`)**:
    *   `src/cmd/internal/obj/arm64/a.out.go` に、TLS変数の新しい分類として `C_TLS_LE` (Local-exec TLS) と `C_TLS_IE` (Initial-exec TLS) が追加されました。これまでの `C_TLS` は `C_TLS_LE` に相当するものとして扱われるようになります。
    *   `C_TLS_LE` は、スレッドローカルベースからの定数オフセットとしてリンカによって最終的に選択されるTLS変数を表します。
    *   `C_TLS_IE` は、動的リンカがスレッドローカルベースからのオフセットで埋めるメモリアドレス（リンカによって選択される）となるTLS変数を表します。これは、GOTを介した間接アクセスを示唆しています。
    *   `src/cmd/internal/obj/arm64/anames7.go` では、これらの新しいクラス名が文字列として定義され、デバッグや診断メッセージで利用できるようになっています。

2.  **アセンブラの変更 (`asm7.go`)**:
    *   `src/cmd/internal/obj/arm64/asm7.go` の `aclass` 関数が変更され、`obj.STLSBSS` (TLS BSSセクションのシンボル) タイプを持つシンボルが、リンカの共有ライブラリフラグ (`ctxt.Flag_shared`) に応じて `C_TLS_IE` または `C_TLS_LE` のいずれかに分類されるようになりました。`ctxt.Flag_shared != 0` の場合、つまり共有ライブラリとしてビルドされる場合は `C_TLS_IE` が選択されます。
    *   `asmout` 関数では、`C_TLS_LE` と `C_TLS_IE` のそれぞれに対応する命令シーケンスが生成されるようになりました。
        *   `C_TLS_LE` の場合は、従来の `movz reg, 0 + reloc` (リロケーション付きのゼロ値移動命令) に対応するケース69が引き続き使用されます。これは、TLS変数のオフセットを直接レジスタにロードする効率的な方法です。
        *   `C_TLS_IE` の場合は、新しいケース70が追加され、`adrp` (アドレスページ相対) と `ldr` (ロード) 命令のシーケンスが生成されます。これは、GOTからTLS変数のオフセットをロードするための典型的なパターンです。具体的には、`ADRP` 命令でGOTエントリのページアドレスを計算し、`LDR` 命令でそのページ内のオフセットから実際のTLSオフセットをロードします。

3.  **リンカのリロケーションタイプの追加 (`link.go`, `asm.go`, `elf.go`)**:
    *   `src/cmd/internal/obj/link.go` に、新しいリロケーションタイプ `R_ARM64_TLS_IE` が追加されました。これは、`ADRP; LD64` 命令シーケンスをリロケートし、参照されるTLSシンボルによって定義されるスレッドローカル変数とスレッドローカルベース間のオフセットをGOTからロードするために使用されます。
    *   `src/cmd/link/internal/arm64/asm.go` では、`elfreloc1` 関数が `R_ARM64_TLS_IE` リロケーションタイプを処理するように更新されました。これには、ELFの特定のリロケーションタイプ (`R_AARCH64_TLSIE_ADR_GOTTPREL_PAGE21` と `R_AARCH64_TLSIE_LD64_GOTTPREL_LO12_NC`) を生成するロジックが含まれています。
    *   `src/cmd/link/internal/ld/elf.go` では、ELFのリロケーション定数として `R_AARCH64_TLSIE_ADR_GOTTPREL_PAGE21` と `R_AARCH64_TLSIE_LD64_GOTTPREL_LO12_NC` が追加されました。これらは、ARM64のinitial-exec TLSモデルでGOTを介してTLSオフセットをロードするために必要なELFリロケーションタイプです。

これらの変更により、Goのツールチェーンは、ARM64上で共有ライブラリを生成する際や、より複雑なリンケージシナリオにおいて、initial-exec TLSモデルを適切に利用できるようになります。これにより、GoプログラムがシステムレベルのTLS機能とよりシームレスに連携できるようになり、特にC/C++ライブラリとの相互運用性や、特定のOS機能の利用において重要となります。

## コアとなるコードの解説

このコミットの核心は、ARM64アーキテクチャにおけるTLS変数へのアクセス方法を、ビルド時のリンケージタイプ（共有ライブラリか否か）に応じて動的に切り替える能力をGoツールチェーンに与えることです。

1.  **`a.out.go` におけるTLSクラスの分離**:
    *   以前は `C_TLS` という単一の抽象化でTLS変数を扱っていましたが、このコミットで `C_TLS_LE` と `C_TLS_IE` に明確に分離されました。これにより、アセンブラとリンカは、それぞれのTLSアクセスモデルに特化したコード生成とリロケーション処理を行うための明確な指示を得ることができます。
    *   `C_TLS_LE` は「local-exec」モデルに対応し、TLSブロックのベースからの直接オフセットとして解決されます。これは、実行可能ファイル自体がTLS変数を定義し、共有ライブラリを介さない場合に最も効率的です。
    *   `C_TLS_IE` は「initial-exec」モデルに対応し、動的リンカによって実行時にオフセットが決定されるメモリ位置を指します。これは、共有ライブラリがTLS変数にアクセスする場合や、より柔軟なリンケージが必要な場合に用いられます。

2.  **`asm7.go` における条件付きコード生成**:
    *   `aclass` 関数は、シンボルが `obj.STLSBSS` (TLS BSSセクションのシンボル) である場合、リンカの `ctxt.Flag_shared` フラグをチェックするようになりました。このフラグは、現在ビルドされているバイナリが共有ライブラリであるか、または共有ライブラリにリンクされる実行可能ファイルであるかを示します。
        *   `ctxt.Flag_shared != 0` (共有ライブラリが関与する場合) であれば、`C_TLS_IE` が返され、initial-execモデルが選択されます。
        *   そうでなければ、`C_TLS_LE` が返され、local-execモデルが選択されます。
    *   `asmout` 関数は、この `C_TLS_IE` クラスに対応する新しい命令シーケンス (ケース70) を生成します。このシーケンスは、ARM64の `ADRP` (Address Page Relative) と `LDR` (Load Register) 命令を組み合わせて、GOT (Global Offset Table) を介してTLS変数のオフセットをロードします。これは、initial-execモデルでTLS変数にアクセスするための標準的な方法です。`ADRP` はページベースアドレスを計算し、`LDR` はそのページ内のオフセットから実際の値をロードします。

3.  **リンカにおける新しいリロケーションタイプの定義と処理**:
    *   `link.go` で `R_ARM64_TLS_IE` という新しいGo内部リロケーションタイプが定義されました。これは、`ADRP; LD64` 命令シーケンスをリロケートするためのものです。
    *   `arm64/asm.go` の `elfreloc1` 関数は、この `R_ARM64_TLS_IE` リロケーションタイプを受け取り、対応するELFリロケーションタイプ (`R_AARCH64_TLSIE_ADR_GOTTPREL_PAGE21` と `R_AARCH64_TLSIE_LD64_GOTTPREL_LO12_NC`) を生成するように拡張されました。これらのELFリロケーションは、動的リンカが実行時にTLS変数のオフセットをGOTに適切に配置し、プログラムがそれをロードできるようにするために不可欠です。
    *   `elf.go` には、これらの新しいARM64固有のELFリロケーション定数が追加され、リンカがELFバイナリを生成する際にこれらを認識し、正しく処理できるようになりました。

これらの変更により、Goのツールチェーンは、ARM64上でビルドされるプログラムが、そのリンケージ要件に応じて最適なTLSアクセスモデルを選択し、効率的かつ正確にTLS変数にアクセスできるようになります。特に、共有ライブラリを使用するGoプログラムや、Goランタイム自体がシステムレベルのTLS機能を利用するシナリオにおいて、この機能は重要です。

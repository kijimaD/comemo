# [インデックス 22477] ファイルの概要

このコミットは、GoランタイムがiOS (darwin/arm) 環境でlldbデバッガ下で実行される際に発生する、`SIGSEGV` (Segmentation Fault) のハンドリングに関する問題を解決するためのものです。具体的には、lldbが`SIGSEGV`をインターセプトし、Goランタイムに適切に渡さないために、Goのパニック機構が機能しないという課題に対処しています。Mach例外機構を活用し、スレッドレベルの例外ハンドラを登録することで、lldbよりも先に`EXC_BAD_ACCESS`例外を捕捉し、Goのパニックに変換することで、この問題を回避しています。

## 元コミット内容

GoのiOS向けプログラム（特に`gomobile`などでビルドされたもの）は、開発サイクルにおいて`lldb`デバッガの下で実行されることが一般的です。しかし、`lldb`は`SIGSEGV`シグナルをインターセプトし、それをプログラムに返さないという問題がありました。これにより、Goプログラム内でセグメンテーション違反が発生しても、Goランタイムのパニック機構が正常に動作せず、デバッグやエラーハンドリングが困難になるという課題が生じていました。この問題は、LLVMのバグトラッカーでも報告されていました（[https://llvm.org/bugs/show_bug.cgi?id=22868](https://llvm.org/bugs/show_bug.cgi?id=22868)）。

このコミットは、`lldb`が`SIGSEGV`を捕捉する前に、Goランタイムが`EXC_BAD_ACCESS`例外を捕捉し、それをGoのパニックに変換することで、この問題を回避することを目的としています。

## 変更の背景

GoプログラムがiOS上でクラッシュした場合、通常は`SIGSEGV`シグナルがGoランタイムに送られ、Goのパニック機構が起動してスタックトレースを出力し、プログラムを終了させます。これにより、開発者は問題の原因を特定しやすくなります。しかし、`lldb`のようなデバッガがアタッチされている場合、`lldb`はデバッグ対象プロセスに送られるシグナルを監視し、必要に応じてインターセプトします。

macOSやiOSなどのDarwin系OSでは、UnixシグナルはMach例外の上にエミュレートされています。`SIGSEGV`は、Mach例外の`EXC_BAD_ACCESS`に対応します。`lldb`のようなデバッガは、通常、タスクレベル（プロセス全体）のMach例外ハンドラを登録します。このハンドラが`EXC_BAD_ACCESS`を捕捉すると、`lldb`はデバッグセッションを中断し、開発者がプログラムの状態を調査できるようにします。

問題は、`lldb`が`SIGSEGV`をインターセプトした後、Goランタイムにそのシグナルを適切に「パスバック」しない、あるいはGoランタイムがそれを期待通りに処理できないという点にありました。これにより、Goのパニック機構が発動せず、デバッグが困難になるという状況が発生していました。このコミットは、この`lldb`の挙動を回避し、Goランタイムが自律的に`SIGSEGV`相当のイベントを処理できるようにするためのものです。

## 前提知識の解説

### Mach例外 (Mach Exceptions)

Mach例外は、macOSやiOSのカーネルであるMachカーネルが提供する低レベルの例外処理メカニズムです。Unixシグナル（`SIGSEGV`など）は、このMach例外の上に構築されています。プログラムが不正なメモリアクセスを行った場合、カーネルは`EXC_BAD_ACCESS`というMach例外を生成します。

Mach例外ハンドラは、以下の3つのレベルで登録できます。

1.  **スレッドレベル (Thread-level):** 特定のスレッドに紐付けられた例外ハンドラです。最も優先順位が高く、例外が発生したスレッドに登録されている場合、最初にこのハンドラが例外を処理する機会を得ます。
2.  **タスクレベル (Task-level):** プロセス全体（Machの用語では「タスク」）に紐付けられた例外ハンドラです。スレッドレベルのハンドラが存在しないか、例外を処理しなかった場合に、このハンドラが処理する機会を得ます。デバッガ（`lldb`など）は通常、このレベルで例外ハンドラを登録します。
3.  **ホストレベル (Host-level):** システム全体に紐付けられた例外ハンドラです。タスクレベルのハンドラも例外を処理しなかった場合の最終的なフォールバックです。

例外が発生すると、カーネルはまずスレッドレベルのハンドラに例外メッセージを送信しようとします。もしスレッドレベルのハンドラが例外を処理し、`KERN_SUCCESS`を返した場合、その例外はそこで「消費」され、それ以上のレベルのハンドラには伝播しません。これが、このコミットが`lldb`のタスクレベルハンドラをバイパスするために利用するメカニズムです。

### `SIGSEGV` (Segmentation Fault)

`SIGSEGV`は、プログラムが不正なメモリアクセス（例えば、存在しないアドレスへの書き込み、読み取り専用領域への書き込みなど）を試みた際にOSからプロセスに送られるシグナルです。Goランタイムでは、このシグナルを捕捉してパニックを発生させ、スタックトレースを出力することで、デバッグを容易にします。

### `lldb`

`lldb`は、LLVMプロジェクトの一部として開発されているオープンソースのデバッガです。XcodeのデフォルトデバッガとしてmacOSやiOSの開発で広く利用されています。`lldb`は、デバッグ対象のプロセスにアタッチし、ブレークポイントの設定、ステップ実行、変数の検査、シグナルのインターセプトなど、様々なデバッグ機能を提供します。

## 技術的詳細

このコミットの核心は、Mach例外の優先順位を利用して`lldb`の`SIGSEGV`インターセプトを回避することにあります。

1.  **スレッドレベル例外ハンドラの登録:**
    Goランタイムは、各Goルーチンが実行されるOSスレッドに対して、`EXC_BAD_ACCESS`例外を捕捉するためのスレッドレベルのMach例外ハンドラを登録します。これは、`darwin_arm_init_thread_exception_port()` 関数によって行われます。この関数は、新しいMachポートを割り当て、現在のスレッドの`EXC_MASK_BAD_ACCESS`例外をそのポートにリダイレクトするように設定します。

2.  **Mach例外サーバーの起動:**
    プロセス起動時に、`darwin_arm_init_mach_exception_handler()` 関数が呼び出されます。この関数は、`mach_exception_handler_port_set`というMachポートセットを初期化し、新しいスレッドを生成して、そのポートセット上でMachメッセージサーバー（`mach_msg_server`）を実行します。このサーバーは、登録されたスレッドから送られてくる`EXC_BAD_ACCESS`例外メッセージを待ち受けます。

3.  **例外の捕捉とGoパニックへの変換:**
    `mach_exception_handler`スレッドが`EXC_BAD_ACCESS`例外メッセージを受信すると、`catch_exception_raise`関数が呼び出されます。
    *   この関数は、例外の種類が`EXC_BAD_ACCESS`であるかを確認します。そうでなければ`KERN_FAILURE`を返し、例外を次のハンドラ（`lldb`のタスクレベルハンドラなど）に渡します。
    *   `EXC_BAD_ACCESS`の場合、例外が発生したスレッドのCPUレジスタの状態（特にプログラムカウンタ `PC` とリンクレジスタ `LR`）を取得します。
    *   Goランタイムの`sigpanic`関数（Goのパニックを処理する内部関数）を呼び出すために、レジスタの状態を操作します。具体的には、`PC`を`x_cgo_panicmem`（`panicmem`アセンブリ関数のアドレス）に設定し、`LR`と`PC`の元の値を`R1`と`R2`レジスタに保存します。これにより、`panicmem`が呼び出された際に、あたかも元の障害発生箇所から`sigpanic`が直接呼び出されたかのように見せかけます。
    *   レジスタの状態を更新した後、`KERN_SUCCESS`を返します。これにより、例外はGoランタイムによって処理されたとみなされ、`lldb`のタスクレベルハンドラには伝播しません。

4.  **`panicmem`アセンブリ関数:**
    `src/runtime/cgo/signal_darwin_arm.s` に追加された `panicmem` 関数は、`EXC_BAD_ACCESS`例外からGoのパニック機構への橋渡しをします。この関数は、Cコード（外部コード）でセグメンテーション違反が発生した場合でも、Goの`g`レジスタ（現在のGoルーチンを示すポインタ）をロードし、Goルーチン上で発生したパニックとして`runtime.setsigsegv`と`runtime.sigpanic`を呼び出すように設計されています。これにより、Goのスタックトレースが適切に生成されます。

5.  **`setsigsegv`関数の追加:**
    `src/runtime/sigpanic_unix.go` に追加された `setsigsegv` 関数は、Goルーチンの`g`オブジェクトに`_SIGSEGV`シグナル情報と障害発生時のプログラムカウンタ（`pc`）を設定します。これは、`sigpanic`がGoのパニックを生成する際に必要な情報を提供します。

6.  **`lldb`ビルドタグの導入:**
    `src/runtime/cgo/gcc_signal_darwin_lldb.c` は、`lldb`ビルドタグが有効な場合にコンパイルされるファイルです。このファイルでは、上記のMach例外ハンドラの初期化関数（`darwin_arm_init_thread_exception_port`と`darwin_arm_init_mach_exception_handler`）が空の関数として定義されています。これは、`lldb`でデバッグする際に、GoランタイムがMach例外をインターセプトする挙動を無効にし、`lldb`がシグナルを捕捉できるようにするためのものです。これにより、開発者は必要に応じて`lldb`の通常のデバッグフローを利用できます。

## コアとなるコードの解説

### `src/runtime/cgo/gcc_signal_darwin_armx.c` の `catch_exception_raise` 関数

```c
kern_return_t
catch_exception_raise(
	mach_port_t exception_port,
	mach_port_t thread,
	mach_port_t task,
	exception_type_t exception,
	exception_data_t code_vector,
	mach_msg_type_number_t code_count)
{
	// ... (省略) ...

	if (exception != EXC_BAD_ACCESS) {
		return KERN_FAILURE; // EXC_BAD_ACCESS以外は処理せず、次のハンドラに渡す
	}

	// スレッドの状態（レジスタ）を取得
	ret = thread_get_state(thread, ARM_UNIFIED_THREAD_STATE, (thread_state_t)&thread_state, &state_count);
	// ... (エラーハンドリング) ...

	// sigpanicへの呼び出しを偽装するためにレジスタを操作
	thread_state.ts_32.__r[1] = thread_state.ts_32.__lr; // LRをR1に保存
	thread_state.ts_32.__r[2] = thread_state.ts_32.__pc; // PCをR2に保存
	thread_state.ts_32.__pc = x_cgo_panicmem;           // PCをpanicmemのアドレスに設定

	// スレッドの状態を更新
	ret = thread_set_state(thread, ARM_UNIFIED_THREAD_STATE, (thread_state_t)&thread_state, state_count);
	// ... (エラーハンドリング) ...

	return KERN_SUCCESS; // 例外を処理済みとしてマークし、他のハンドラには渡さない
}
```
この関数は、`EXC_BAD_ACCESS`例外が発生した際にMach例外サーバーによって呼び出されます。重要なのは、例外が発生したスレッドのレジスタ状態を読み取り、`PC`（プログラムカウンタ）をGoランタイムの`panicmem`アセンブリ関数のアドレスに書き換える点です。これにより、例外ハンドラから戻った際に、元の障害発生箇所ではなく`panicmem`が実行されるようになります。元の`PC`と`LR`（リンクレジスタ）は、`panicmem`がGoの`sigpanic`に渡すために、一時的にレジスタに保存されます。`KERN_SUCCESS`を返すことで、この例外が完全に処理されたことをカーネルに伝え、`lldb`のようなタスクレベルのデバッガがこの例外を捕捉するのを防ぎます。

### `src/runtime/cgo/signal_darwin_arm.s` の `panicmem` 関数

```assembly
TEXT ·panicmem(SB),NOSPLIT,$-4
	// If in external C code, we need to load the g register.
	BL  runtime·load_g(SB) // gレジスタをロード
	CMP $0, g
	BNE ongothread         // Goルーチン上であればongothreadへ

	// On a foreign thread. We call badsignal, which will, if all
	// goes according to plan, not return.
	// ... (Goルーチン外での処理、ここでは省略) ...

ongothread:
	// Trigger a SIGSEGV panic.
	//
	// The goal is to arrange the stack so it looks like the runtime
	// function sigpanic was called from the PC that faulted. It has
	// to be sigpanic, as the stack unwinding code in traceback.go
	// looks explicitly for it.
	//
	// To do this we call into runtime·setsigsegv, which sets the
	// appropriate state inside the g object. We give it the faulting
	// PC on the stack, then put it in the LR before calling sigpanic.
	MOVM.DB.W [R1,R2], (R13) // R1(LR), R2(PC)をスタックに保存
	BL runtime·setsigsegv(SB) // setsigsegvを呼び出し、gオブジェクトにSIGSEGV情報を設定
	MOVM.IA.W (R13), [R1,R2] // スタックからR1, R2を復元

	SUB $4, R13
	MOVW R1, 0(R13)
	MOVW R2, R14
	B runtime·sigpanic(SB) // sigpanicへジャンプ
```
`panicmem`は、`catch_exception_raise`によって制御が移された後に実行されるアセンブリ関数です。この関数の主な目的は、セグメンテーション違反が発生したコンテキスト（Goルーチン内か、Cgoを介したCコード内か）を判断し、Goのパニック機構に適切に引き渡すことです。

Goルーチン上で発生した場合（`ongothread`ラベル以降）、`runtime.setsigsegv`を呼び出して現在のGoルーチン（`g`オブジェクト）に`SIGSEGV`が発生したことを記録します。その後、スタックとレジスタを操作して、あたかも元の障害発生箇所から`runtime.sigpanic`が直接呼び出されたかのように見せかけ、最終的に`runtime.sigpanic`へジャンプします。これにより、Goのランタイムが通常のパニック処理フローに入り、正確なスタックトレースを生成できるようになります。

### `src/runtime/sigpanic_unix.go` の `setsigsegv` 関数

```go
// setsigsegv is used on darwin/arm{,64} to fake a segmentation fault.
//go:nosplit
func setsigsegv(pc uintptr) {
	g := getg()
	g.sig = _SIGSEGV
	g.sigpc = pc
	g.sigcode0 = _SEGV_MAPERR
	g.sigcode1 = 0 // TODO: emulate si_addr
}
```
このGo関数は、`panicmem`アセンブリ関数から呼び出されます。現在のGoルーチン（`g`）を取得し、その`g`オブジェクトのフィールドに`SIGSEGV`が発生したことを示す情報を設定します。具体的には、`g.sig`に`_SIGSEGV`を設定し、`g.sigpc`に障害発生時のプログラムカウンタ（`pc`）を設定します。これにより、後続の`sigpanic`関数が、この情報に基づいて適切なパニックメッセージとスタックトレースを生成できるようになります。

## 元コミット内容

GoのiOS向けプログラム（特に`gomobile`などでビルドされたもの）は、開発サイクルにおいて`lldb`デバッガの下で実行されることが一般的です。しかし、`lldb`は`SIGSEGV`シグナルをインターセプトし、それをプログラムに返さないという問題がありました。これにより、Goプログラム内でセグメンテーション違反が発生しても、Goランタイムのパニック機構が正常に動作せず、デバッグやエラーハンドリングが困難になるという課題が生じていました。この問題は、LLVMのバグトラッカーでも報告されていました（[https://llvm.org/bugs/show_bug.cgi?id=22868](https://llvm.org/bugs/show_bug.cgi?id=22868)）。

このコミットは、`lldb`が`SIGSEGV`を捕捉する前に、Goランタイムが`EXC_BAD_ACCESS`例外を捕捉し、それをGoのパニックに変換することで、この問題を回避することを目的としています。

## 変更の背景

GoプログラムがiOS上でクラッシュした場合、通常は`SIGSEGV`シグナルがGoランタイムに送られ、Goのパニック機構が起動してスタックトレースを出力し、プログラムを終了させます。これにより、開発者は問題の原因を特定しやすくなります。しかし、`lldb`のようなデバッガがアタッチされている場合、`lldb`はデバッグ対象プロセスに送られるシグナルを監視し、必要に応じてインターセプトします。

macOSやiOSなどのDarwin系OSでは、UnixシグナルはMach例外の上にエミュレートされています。`SIGSEGV`は、Mach例外の`EXC_BAD_ACCESS`に対応します。`lldb`のようなデバッガは、通常、タスクレベル（プロセス全体）のMach例外ハンドラを登録します。このハンドラが`EXC_BAD_ACCESS`を捕捉すると、`lldb`はデバッグセッションを中断し、開発者がプログラムの状態を調査できるようにします。

問題は、`lldb`が`SIGSEGV`をインターセプトした後、Goランタイムにそのシグナルを適切に「パスバック」しない、あるいはGoランタイムがそれを期待通りに処理できないという点にありました。これにより、Goのパニック機構が発動せず、デバッグが困難になるという状況が発生していました。このコミットは、この`lldb`の挙動を回避し、Goランタイムが自律的に`SIGSEGV`相当のイベントを処理できるようにするためのものです。

## 前提知識の解説

### Mach例外 (Mach Exceptions)

Mach例外は、macOSやiOSのカーネルであるMachカーネルが提供する低レベルの例外処理メカニズムです。Unixシグナル（`SIGSEGV`など）は、このMach例外の上に構築されています。プログラムが不正なメモリアクセスを行った場合、カーネルは`EXC_BAD_ACCESS`というMach例外を生成します。

Mach例外ハンドラは、以下の3つのレベルで登録できます。

1.  **スレッドレベル (Thread-level):** 特定のスレッドに紐付けられた例外ハンドラです。最も優先順位が高く、例外が発生したスレッドに登録されている場合、最初にこのハンドラが例外を処理する機会を得ます。
2.  **タスクレベル (Task-level):** プロセス全体（Machの用語では「タスク」）に紐付けられた例外ハンドラです。スレッドレベルのハンドラが存在しないか、例外を処理しなかった場合に、このハンドラが処理する機会を得ます。デバッガ（`lldb`など）は通常、このレベルで例外ハンドラを登録します。
3.  **ホストレベル (Host-level):** システム全体に紐付けられた例外ハンドラです。タスクレベルのハンドラも例外を処理しなかった場合の最終的なフォールバックです。

例外が発生すると、カーネルはまずスレッドレベルのハンドラに例外メッセージを送信しようとします。もしスレッドレベルのハンドラが例外を処理し、`KERN_SUCCESS`を返した場合、その例外はそこで「消費」され、それ以上のレベルのハンドラには伝播しません。これが、このコミットが`lldb`のタスクレベルハンドラをバイパスするために利用するメカニズムです。

### `SIGSEGV` (Segmentation Fault)

`SIGSEGV`は、プログラムが不正なメモリアクセス（例えば、存在しないアドレスへの書き込み、読み取り専用領域への書き込みなど）を試みた際にOSからプロセスに送られるシグナルです。Goランタイムでは、このシグナルを捕捉してパニックを発生させ、スタックトレースを出力することで、デバッグを容易にします。

### `lldb`

`lldb`は、LLVMプロジェクトの一部として開発されているオープンソースのデバッガです。XcodeのデフォルトデバッガとしてmacOSやiOSの開発で広く利用されています。`lldb`は、デバッグ対象のプロセスにアタッチし、ブレークポイントの設定、ステップ実行、変数の検査、シグナルのインターセプトなど、様々なデバッグ機能を提供します。

## 技術的詳細

このコミットの核心は、Mach例外の優先順位を利用して`lldb`の`SIGSEGV`インターセプトを回避することにあります。

1.  **スレッドレベル例外ハンドラの登録:**
    Goランタイムは、各Goルーチンが実行されるOSスレッドに対して、`EXC_BAD_ACCESS`例外を捕捉するためのスレッドレベルのMach例外ハンドラを登録します。これは、`darwin_arm_init_thread_exception_port()` 関数によって行われます。この関数は、新しいMachポートを割り当て、現在のスレッドの`EXC_MASK_BAD_ACCESS`例外をそのポートにリダイレクトするように設定します。

2.  **Mach例外サーバーの起動:**
    プロセス起動時に、`darwin_arm_init_mach_exception_handler()` 関数が呼び出されます。この関数は、`mach_exception_handler_port_set`というMachポートセットを初期化し、新しいスレッドを生成して、そのポートセット上でMachメッセージサーバー（`mach_msg_server`）を実行します。このサーバーは、登録されたスレッドから送られてくる`EXC_BAD_ACCESS`例外メッセージを待ち受けます。

3.  **例外の捕捉とGoパニックへの変換:**
    `mach_exception_handler`スレッドが`EXC_BAD_ACCESS`例外メッセージを受信すると、`catch_exception_raise`関数が呼び出されます。
    *   この関数は、例外の種類が`EXC_BAD_ACCESS`であるかを確認します。そうでなければ`KERN_FAILURE`を返し、例外を次のハンドラ（`lldb`のタスクレベルハンドラなど）に渡します。
    *   `EXC_BAD_ACCESS`の場合、例外が発生したスレッドのCPUレジスタの状態（特にプログラムカウンタ `PC` とリンクレジスタ `LR`）を取得します。
    *   Goランタイムの`sigpanic`関数（Goのパニックを処理する内部関数）を呼び出すために、レジスタの状態を操作します。具体的には、`PC`を`x_cgo_panicmem`（`panicmem`アセンブリ関数のアドレス）に設定し、`LR`と`PC`の元の値を`R1`と`R2`レジスタに保存します。これにより、`panicmem`が呼び出された際に、あたかも元の障害発生箇所から`sigpanic`が直接呼び出されたかのように見せかけます。
    *   レジスタの状態を更新した後、`KERN_SUCCESS`を返します。これにより、例外はGoランタイムによって処理されたとみなされ、`lldb`のタスクレベルハンドラには伝播しません。

4.  **`panicmem`アセンブリ関数:**
    `src/runtime/cgo/signal_darwin_arm.s` に追加された `panicmem` 関数は、`EXC_BAD_ACCESS`例外からGoのパニック機構への橋渡しをします。この関数は、Cコード（外部コード）でセグメンテーション違反が発生した場合でも、Goの`g`レジスタ（現在のGoルーチンを示すポインタ）をロードし、Goルーチン上で発生したパニックとして`runtime.setsigsegv`と`runtime.sigpanic`を呼び出すように設計されています。これにより、Goのスタックトレースが適切に生成されます。

5.  **`setsigsegv`関数の追加:**
    `src/runtime/sigpanic_unix.go` に追加された `setsigsegv` 関数は、Goルーチンの`g`オブジェクトに`_SIGSEGV`シグナル情報と障害発生時のプログラムカウンタ（`pc`）を設定します。これは、`sigpanic`がGoのパニックを生成する際に必要な情報を提供します。

6.  **`lldb`ビルドタグの導入:**
    `src/runtime/cgo/gcc_signal_darwin_lldb.c` は、`lldb`ビルドタグが有効な場合にコンパイルされるファイルです。このファイルでは、上記のMach例外ハンドラの初期化関数（`darwin_arm_init_thread_exception_port`と`darwin_arm_init_mach_exception_handler`）が空の関数として定義されています。これは、`lldb`でデバッグする際に、GoランタイムがMach例外をインターセプトする挙動を無効にし、`lldb`がシグナルを捕捉できるようにするためのものです。これにより、開発者は必要に応じて`lldb`の通常のデバッグフローを利用できます。

## コアとなるコードの解説

### `src/runtime/cgo/gcc_signal_darwin_armx.c` の `catch_exception_raise` 関数

```c
kern_return_t
catch_exception_raise(
	mach_port_t exception_port,
	mach_port_t thread,
	mach_port_t task,
	exception_type_t exception,
	exception_data_t code_vector,
	mach_msg_type_number_t code_count)
{
	// ... (省略) ...

	if (exception != EXC_BAD_ACCESS) {
		return KERN_FAILURE; // EXC_BAD_ACCESS以外は処理せず、次のハンドラに渡す
	}

	// スレッドの状態（レジスタ）を取得
	ret = thread_get_state(thread, ARM_UNIFIED_THREAD_STATE, (thread_state_t)&thread_state, &state_count);
	// ... (エラーハンドリング) ...

	// sigpanicへの呼び出しを偽装するためにレジスタを操作
	thread_state.ts_32.__r[1] = thread_state.ts_32.__lr; // LRをR1に保存
	thread_state.ts_32.__r[2] = thread_state.ts_32.__pc; // PCをR2に保存
	thread_state.ts_32.__pc = x_cgo_panicmem;           // PCをpanicmemのアドレスに設定

	// スレッドの状態を更新
	ret = thread_set_state(thread, ARM_UNIFIED_THREAD_STATE, (thread_state_t)&thread_state, state_count);
	// ... (エラーハンドリング) ...

	return KERN_SUCCESS; // 例外を処理済みとしてマークし、他のハンドラには渡さない
}
```
この関数は、`EXC_BAD_ACCESS`例外が発生した際にMach例外サーバーによって呼び出されます。重要なのは、例外が発生したスレッドのレジスタ状態を読み取り、`PC`（プログラムカウンタ）をGoランタイムの`panicmem`アセンブリ関数のアドレスに書き換える点です。これにより、例外ハンドラから戻った際に、元の障害発生箇所ではなく`panicmem`が実行されるようになります。元の`PC`と`LR`（リンクレジスタ）は、`panicmem`がGoの`sigpanic`に渡すために、一時的にレジスタに保存されます。`KERN_SUCCESS`を返すことで、この例外が完全に処理されたことをカーネルに伝え、`lldb`のようなタスクレベルのデバッガがこの例外を捕捉するのを防ぎます。

### `src/runtime/cgo/signal_darwin_arm.s` の `panicmem` 関数

```assembly
TEXT ·panicmem(SB),NOSPLIT,$-4
	// If in external C code, we need to load the g register.
	BL  runtime·load_g(SB) // gレジスタをロード
	CMP $0, g
	BNE ongothread         // Goルーチン上であればongothreadへ

	// On a foreign thread. We call badsignal, which will, if all
	// goes according to plan, not return.
	// ... (Goルーチン外での処理、ここでは省略) ...

ongothread:
	// Trigger a SIGSEGV panic.
	//
	// The goal is to arrange the stack so it looks like the runtime
	// function sigpanic was called from the PC that faulted. It has
	// to be sigpanic, as the stack unwinding code in traceback.go
	// looks explicitly for it.
	//
	// To do this we call into runtime·setsigsegv, which sets the
	// appropriate state inside the g object. We give it the faulting
	// PC on the stack, then put it in the LR before calling sigpanic.
	MOVM.DB.W [R1,R2], (R13) // R1(LR), R2(PC)をスタックに保存
	BL runtime·setsigsegv(SB) // setsigsegvを呼び出し、gオブジェクトにSIGSEGV情報を設定
	MOVM.IA.W (R13), [R1,R2] // スタックからR1, R2を復元

	SUB $4, R13
	MOVW R1, 0(R13)
	MOVW R2, R14
	B runtime·sigpanic(SB) // sigpanicへジャンプ
```
`panicmem`は、`catch_exception_raise`によって制御が移された後に実行されるアセンブリ関数です。この関数の主な目的は、セグメンテーション違反が発生したコンテキスト（Goルーチン内か、Cgoを介したCコード内か）を判断し、Goのパニック機構に適切に引き渡すことです。

Goルーチン上で発生した場合（`ongothread`ラベル以降）、`runtime.setsigsegv`を呼び出して現在のGoルーチン（`g`オブジェクト）に`SIGSEGV`が発生したことを記録します。その後、スタックとレジスタを操作して、あたかも元の障害発生箇所から`runtime.sigpanic`が直接呼び出されたかのように見せかけ、最終的に`runtime.sigpanic`へジャンプします。これにより、Goのランタイムが通常のパニック処理フローに入り、正確なスタックトレースを生成できるようになります。

### `src/runtime/sigpanic_unix.go` の `setsigsegv` 関数

```go
// setsigsegv is used on darwin/arm{,64} to fake a segmentation fault.
//go:nosplit
func setsigsegv(pc uintptr) {
	g := getg()
	g.sig = _SIGSEGV
	g.sigpc = pc
	g.sigcode0 = _SEGV_MAPERR
	g.sigcode1 = 0 // TODO: emulate si_addr
}
```
このGo関数は、`panicmem`アセンブリ関数から呼び出されます。現在のGoルーチン（`g`）を取得し、その`g`オブジェクトのフィールドに`SIGSEGV`が発生したことを示す情報を設定します。具体的には、`g.sig`に`_SIGSEGV`を設定し、`g.sigpc`に障害発生時のプログラムカウンタ（`pc`）を設定します。これにより、後続の`sigpanic`関数が、この情報に基づいて適切なパニックメッセージとスタックトレースを生成できるようになります。

## 変更の背景

Go言語は、その設計思想として幅広いプラットフォームとアーキテクチャをサポートすることを目指しています。このコミットは、その目標の一環として、MIPS64およびMIPS64LEアーキテクチャ上でのGoの実行を可能にするために行われました。MIPSアーキテクチャは、組み込みシステムやネットワーク機器などで広く利用されており、これらのプラットフォームでGoアプリケーションを実行できるようにすることは、Goのエコシステムを拡大する上で重要です。

Goランタイムは、OSやアーキテクチャに依存する低レベルの処理（メモリ管理、スケジューリング、シグナルハンドリングなど）を抽象化して提供しています。新しいアーキテクチャをサポートするためには、そのアーキテクチャ固有のレジスタセット、システムコールインターフェース、メモリモデル、シグナル処理メカニズムなどに合わせてランタイムコードを調整する必要があります。このコミットは、MIPS64アーキテクチャに特化したこれらの調整を導入するものです。

## 前提知識の解説

### MIPS64アーキテクチャ

MIPS (Microprocessor without Interlocked Pipeline Stages) は、RISC (Reduced Instruction Set Computer) アーキテクチャの一種です。MIPS64は、64ビットのMIPSプロセッサを指し、64ビット幅のレジスタとアドレス空間を持ちます。MIPS64LEは、リトルエンディアン形式のMIPS64を意味します（LEはLittle Endianの略）。エンディアンネスは、メモリ上でのバイトの順序付けを指し、Goランタイムはこれらを区別して適切に処理する必要があります。

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェース、シグナルハンドリングなどが含まれます。Goプログラムは、OSやハードウェアと直接対話するのではなく、ランタイムを介してこれらの低レベルの操作を行います。そのため、新しいアーキテクチャをサポートするには、ランタイムの各コンポーネントをそのアーキテクチャに合わせて実装する必要があります。

### シグナルハンドリング

シグナルは、オペレーティングシステムがプロセスに非同期イベントを通知するメカニズムです。例えば、プログラムのエラー（セグメンテーション違反、浮動小数点例外）、外部からの割り込み（Ctrl+C）、タイマーイベントなどがあります。Goランタイムは、これらのシグナルを捕捉し、適切に処理することで、プログラムのクラッシュを防いだり、デバッグ情報を提供したり、プロファイリングを可能にしたりします。シグナルハンドリングは、CPUのレジスタ状態（コンテキスト）を保存・復元するOS固有のメカニズムに深く依存します。

### ロックフリーデータ構造 (Lock-Free Data Structures)

ロックフリーデータ構造は、複数のスレッド（Goではゴルーチン）が同時にアクセスしても、ロックを使用せずに正しく動作するように設計されたデータ構造です。これにより、ロックの競合によるパフォーマンスの低下を避け、高い並行性を実現できます。ロックフリースタックは、その一例であり、アトミック操作（Compare-And-Swapなど）を利用して、プッシュやポップ操作を安全に行います。`lfstackPack`と`lfstackUnpack`は、ポインタとカウンタを単一の64ビット値にパック/アンパックすることで、アトミック操作を容易にするための一般的なテクニックです。

### `ucontext` および `sigcontext`

Linuxシステムでは、シグナルハンドラが呼び出された際に、シグナル発生時のプロセスのコンテキスト情報（CPUレジスタの値、スタックポインタ、プログラムカウンタなど）が`ucontext_t`構造体を通じて提供されます。この`ucontext_t`内部には、CPU固有のレジスタ情報を含む`mcontext_t`（MIPS64の場合は`sigcontext`に相当）が含まれています。シグナルハンドラはこれらの構造体を利用して、シグナル発生時のプログラムの状態を分析したり、必要に応じてレジスタ値を変更して実行フローを制御したりします。

## 技術的詳細

このコミットで追加されたファイルは、MIPS64アーキテクチャにおけるGoランタイムの動作を定義する上で不可欠な要素を含んでいます。

1.  **`src/runtime/defs_linux_mips64x.go`**:
    *   **システムコール定数**: `_EINTR`, `_EAGAIN`, `_ENOMEM` などのエラーコード、`_PROT_NONE`, `_PROT_READ`, `_PROT_WRITE`, `_PROT_EXEC` などのメモリ保護フラグ、`_MAP_ANON`, `_MAP_PRIVATE`, `_MAP_FIXED` などのメモリマッピングフラグ、`_MADV_DONTNEED` などの `madvise` フラグが定義されています。これらは、GoランタイムがLinuxカーネルと対話する際に使用する低レベルの定数です。
    *   **シグナル関連定数**: `_SA_RESTART`, `_SA_ONSTACK`, `_SA_SIGINFO` などの `sigaction` フラグ、`_SIGHUP` から `_SIGXFSZ` までの標準的なシグナル番号、`_FPE_INTDIV` などの浮動小数点例外コード、`_BUS_ADRALN` などのバスエラーコード、`_SEGV_MAPERR` などのセグメンテーション違反コードが定義されています。これらはシグナルハンドリングの挙動を制御するために使用されます。
    *   **データ構造**: `timespec`, `timeval`, `sigactiont`, `siginfo`, `itimerval`, `epollevent`, `sigaltstackt`, `sigcontext`, `ucontext` といったC言語の構造体に対応するGoの構造体が定義されています。これらは、OSとのインターフェース（特にシグナルハンドリングや時間関連のシステムコール）でデータの受け渡しに使用されます。特に `sigcontext` と `ucontext` は、シグナル発生時のCPU状態を保持するために重要です。

2.  **`src/runtime/lfstack_linux_mips64x.go`**:
    *   **アドレス空間の考慮**: コメントに「On mips64, Linux limits the user address space to 40 bits (see TASK_SIZE64 in the Linux kernel). This has grown over time, so here we allow 48 bit addresses.」とあるように、MIPS64 Linuxカーネルの `TASK_SIZE64` がユーザーアドレス空間を40ビットに制限していることに対し、Goランタイムでは48ビットのアドレスを許容するように設計されています。これは、より大きなメモリ空間を効率的に利用するための工夫です。
    *   **`lfstackPack` と `lfstackUnpack`**: ロックフリースタックのノードポインタとカウンタを単一の `uint64` 値にパック/アンパックする関数です。`addrBits` (48ビット) と `cntBits` (64 - 48 + 3 = 19ビット) を使用して、ポインタとカウンタを効率的に格納します。ポインタは3バイトアラインメントされているため、下位3ビットをカウンタに利用できる点が特徴です。これにより、アトミックなCAS (Compare-And-Swap) 操作でスタックのヘッドを更新する際に、ポインタとカウンタを同時に更新できます。

3.  **`src/runtime/os_linux_mips64x.go`**:
    *   **`cputicks()`**: CPUのティック数を返す関数です。プロファイラや乱数生成器のシードとして使用されます。MIPS64では、`nanotime()`（ナノ秒単位のシステム時間）と `randomNumber` を組み合わせてティック数を近似しています。これは、MIPS64アーキテクチャで高精度なCPUティックカウンタに直接アクセスするのが難しい場合の一般的なアプローチです。

4.  **`src/runtime/signal_linux_mips64x.go`**:
    *   **`sigctxt` 構造体**: シグナルハンドラに渡される `siginfo` と `ucontext` ポインタをラップする構造体です。
    *   **レジスタアクセスメソッド**: `sigctxt` のメソッドとして、MIPS64の各汎用レジスタ (`r0` から `r31`)、スタックポインタ (`sp`)、プログラムカウンタ (`pc`)、リンクレジスタ (`link`)、`lo` レジスタ、`hi` レジスタにアクセスするためのヘルパー関数が提供されています。これらは、シグナル発生時のCPU状態を読み取ったり、変更したりするために使用されます。

5.  **`src/runtime/signal_mips64x.go`**:
    *   **`dumpregs()`**: シグナル発生時にMIPS64の全レジスタの内容をダンプする関数です。デバッグやクラッシュレポートの際に非常に役立ちます。
    *   **`sighandler()`**: MIPS64 LinuxにおけるGoランタイムの主要なシグナルハンドラです。
        *   `_SIGPROF` (プロファイリングシグナル) の処理: プロファイリング情報を収集するために `sigprof` 関数を呼び出します。
        *   パニックシグナルの処理: `_SigPanic` フラグが設定されたシグナル（例: `SIGSEGV`）を受信した場合、Goのパニックメカニズムをトリガーします。この際、スタックフレームを調整し、`sigpanic` 関数が呼び出されたかのように見せかけます。特に、リンクレジスタ (`c.link()`) をスタックに保存し、プログラムカウンタ (`c.pc()`) を `sigpanic` 関数のアドレスに設定することで、Goのスタックトレースが正しく生成されるようにします。
        *   `_SigNotify` フラグが設定されたシグナルの処理: `sigsend` を呼び出して、Goのシグナル通知メカニズムをトリガーします。
        *   `_SigKill` フラグが設定されたシグナルの処理: プロセスを終了します。
        *   クラッシュ処理: `_SigThrow` フラグが設定されたシグナル（通常は致命的なエラー）の場合、スタックトレースを生成し、レジスタをダンプします。複数のM (OSスレッド) が存在する場合、`SIGQUIT` を他のMにリレーして、すべてのゴルーチンのスタックトレースを収集しようとします。最終的に `crash()` 関数を呼び出してプロセスを終了します。

これらのファイルは、MIPS64アーキテクチャの特性（レジスタセット、メモリモデル、シグナルコンテキストなど）をGoランタイムにマッピングし、Goの並行処理モデル、メモリ管理、エラーハンドリングがこの新しいプラットフォームでシームレスに機能するようにするための基盤を提供します。

このコミットは、既存のファイルを変更するのではなく、MIPS64およびMIPS64LEアーキテクチャをサポートするための新しいGoファイルを `src/runtime/` ディレクトリに追加しています。

具体的には、以下の5つのファイルが新規追加されています。

1.  `src/runtime/defs_linux_mips64x.go`:

## コアとなるコードの解説

### `src/runtime/defs_linux_mips64x.go` の `sigcontext` および `ucontext`

```go
type sigcontext struct {
	sc_regs      [32]uint64
	sc_fpregs    [32]uint64
	sc_mdhi      uint64
	sc_hi1       uint64
	sc_hi2       uint64
	sc_hi3       uint64
	sc_mdlo      uint64
	sc_lo1       uint64
	sc_lo2       uint64
	sc_lo3       uint64
	sc_pc        uint64
	sc_fpc_csr   uint32
	sc_used_math uint32
	sc_dsp       uint32
	sc_reserved  uint32
}

type ucontext struct {
	uc_flags    uint64
	uc_link     *ucontext
	uc_stack    sigaltstackt
	uc_mcontext sigcontext
	uc_sigmask  uint64
}
```
これらの構造体は、Linuxカーネルがシグナルハンドラに渡すコンテキスト情報 (`ucontext_t`) をGoで表現したものです。
*   `sigcontext`: MIPS64 CPUのレジスタセットを直接マッピングしています。`sc_regs` は汎用レジスタ、`sc_fpregs` は浮動小数点レジスタ、`sc_pc` はプログラムカウンタ、`sc_mdhi`/`sc_mdlo` などはMIPS固有の特殊レジスタです。シグナル発生時のCPUの状態を正確に把握するために不可欠です。
*   `ucontext`: シグナルスタック情報 (`uc_stack`) やシグナルマスク (`uc_sigmask`) など、より広範なコンテキスト情報を含みます。特に `uc_mcontext sigcontext` フィールドを通じて、CPUレジスタ情報にアクセスします。

### `src/runtime/lfstack_linux_mips64x.go` の `lfstackPack` と `lfstackUnpack`

```go
const (
	addrBits = 48
	cntBits  = 64 - addrBits + 3 // 64 - 48 + 3 = 19
)

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
}

func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr) {
	node = (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
	cnt = uintptr(val & (1<<cntBits - 1))
	return
}
```
これらの関数は、ロックフリースタックの実装で重要な役割を果たします。
*   `addrBits = 48`: MIPS64 Linuxのユーザーアドレス空間が実質的に48ビットに制限されていることを反映しています。これにより、64ビットの `uint64` のうち、上位48ビットをポインタに、残りのビットをカウンタに割り当てることができます。
*   `cntBits = 19`: カウンタに割り当てられるビット数です。`64 - addrBits` で残りのビットが16ビットですが、`node` がポインタアラインされている（通常は8バイトアラインメント、つまり下位3ビットが常に0）ため、その3ビットをカウンタに再利用することで、カウンタの範囲を広げています。
*   `lfstackPack`: `node` ポインタを上位ビットに、`cnt` カウンタを下位ビットにパックします。ポインタは `(64-addrBits)` ビットだけ左シフトされ、カウンタはマスク (`1<<cntBits-1`) されてからOR演算で結合されます。
*   `lfstackUnpack`: パックされた `uint64` 値から `node` ポインタと `cnt` カウンタを復元します。ポインタは右シフト (`>> cntBits`) された後、左シフト (`<< 3`) されてアラインメントが復元されます。カウンタはマスク (`&(1<<cntBits-1)`) することで抽出されます。
このテクニックは、ポインタとカウンタを単一のアトミックな64ビット操作で更新することを可能にし、ABA問題（ロックフリーアルゴリズムで発生しうる問題）の検出や、単にカウンタをインクリメントする目的で利用されます。

### `src/runtime/signal_mips64x.go` の `sighandler` 関数

```go
//go:nowritebarrier
func sighandler(sig uint32, info *siginfo, ctxt unsafe.Pointer, gp *g) {
	// ... (省略) ...

	if c.sigcode() != _SI_USER && flags&_SigPanic != 0 {
		// Make it look like a call to the signal func.
		// Have to pass arguments out of band since
		// augmenting the stack frame would break
		// the unwinding code.
		gp.sig = sig
		gp.sigcode0 = uintptr(c.sigcode())
		gp.sigcode1 = uintptr(c.sigaddr())
		gp.sigpc = uintptr(c.pc())

		// We arrange link, and pc to pretend the panicking
		// function calls sigpanic directly.
		// Always save LINK to stack so that panics in leaf
		// functions are correctly handled. This smashes
		// the stack frame but we're not going back there
		// anyway.
		sp := c.sp() - ptrSize
		c.set_sp(sp)
		*(*uint64)(unsafe.Pointer(uintptr(sp))) = c.link()

		pc := uintptr(gp.sigpc)

		// If we don't recognize the PC as code
		// but we do recognize the link register as code,
		// then assume this was a call to non-code and treat like
		// pc == 0, to make unwinding show the context.
		if pc != 0 && findfunc(pc) == nil && findfunc(uintptr(c.link())) != nil {
			pc = 0
		}

		// Don't bother saving PC if it's zero, which is
		// probably a call to a nil func: the old link register
		// is more useful in the stack trace.
		if pc != 0 {
			c.set_link(uint64(pc))
		}

		// In case we are panicking from external C code
		c.set_r30(uint64(uintptr(unsafe.Pointer(gp))))
		c.set_pc(uint64(funcPC(sigpanic)))
		return
	}
	// ... (省略) ...
}
```
`sighandler` 関数は、Goランタイムのシグナル処理の中核です。特に、`_SigPanic` フラグが設定されたシグナル（例: `SIGSEGV`）を受信した際の処理は、Goのパニックメカニズムと密接に関連しています。
*   **コンテキストの保存**: シグナル発生時のプログラムカウンタ (`c.pc()`)、スタックポインタ (`c.sp()`)、リンクレジスタ (`c.link()`) などの情報が `gp` (現在のゴルーチン) に保存されます。
*   **スタックフレームの調整**: パニックをトリガーするために、シグナルハンドラはスタックフレームを「偽装」します。具体的には、現在のスタックポインタを `ptrSize` だけ減らし、その位置に元のリンクレジスタの値を書き込みます。これにより、スタックトレースが `sigpanic` 関数を呼び出したかのように見えます。
*   **プログラムカウンタとリンクレジスタの変更**: `c.set_pc(uint64(funcPC(sigpanic)))` によって、プログラムカウンタが `sigpanic` 関数の開始アドレスに設定されます。これにより、シグナルハンドラから戻ると、`sigpanic` 関数が実行され、Goのパニック処理が開始されます。また、元のプログラムカウンタが有効なGoコードを指していない場合（例: Cコードからのパニック）、リンクレジスタを調整して、より有用なスタックトレース情報を提供しようとします。
この複雑な処理は、OSレベルのシグナルからGoランタイムのパニックメカニズムへの橋渡しを行い、Goプログラムが予期せぬエラーから回復したり、詳細なデバッグ情報を出力したりすることを可能にします。

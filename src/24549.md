# [インデックス 24549] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャ上でのcgo呼び出し時のスタックポインタのアライメントに関するバグ修正です。特にFreeBSD/ARM環境でcgoを使用する際に発生していたクラッシュを解決します。`runtime·_initcgo`関数のスタックフレームサイズを調整することで、ARM ABIで要求される8バイトアライメントを保証します。

This is what is causing freebsd/arm to crash mysteriously when using cgo.
The bug was introduced in golang.org/cl/4030, which moved this code out
of rt0_go and into its own function. The ARM ABI says that calls must
be made with the stack pointer at an 8-byte boundary, but only FreeBSD

## 変更の背景

この変更は、FreeBSD/ARM環境でcgo（GoからC言語のコードを呼び出す機能）を使用する際に発生していた原因不明のクラッシュを修正するために行われました。問題の根本原因は、以前のコミット（`golang.org/cl/4030`）によって`initcgo`関連のコードが`rt0_go`（Goランタイムの初期化エントリポイント）から独立した関数に移動された際に導入されました。

ARMアーキテクチャのABI（Application Binary Interface）では、関数呼び出しを行う際にスタックポインタ（SP）が8バイト境界にアライメントされている必要があります。しかし、この変更によって`initcgo`関数がC言語の関数を呼び出す際に、スタックポインタが8バイトアライメントされていない状態になっていました。興味深いことに、このABI違反に対してはFreeBSDのみがクラッシュするという挙動を示していました。他のシステムでは同様の違反があっても問題が顕在化しなかったようです。

この問題はGo issue #10119として報告されており、このコミットはその問題を解決することを目的としています。

## 前提知識の解説

### cgo (GoとCの相互運用)
cgoは、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリをGoプロジェクトで再利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。cgoを使用すると、GoのランタイムとCのランタイムの間でスタックやレジスタの状態を適切に切り替える必要があり、ABIの規則に従うことが非常に重要になります。

### ARM ABI (Application Binary Interface)
ABIは、オペレーティングシステムとプログラム、またはプログラムの異なるコンポーネント間で、データ構造のレイアウト、関数呼び出し規約、レジスタの使用方法などを定義する一連の規則です。ARMアーキテクチャのABIには、関数呼び出し時のスタックポインタのアライメントに関する特定の要件が含まれています。一般的に、スタックポインタは特定のバイト境界（例えば4バイトまたは8バイト）にアライメントされている必要があります。これは、プロセッサがメモリからデータを効率的に読み書きするため、または特定の命令がアライメントされたアドレスを要求するために重要です。アライメントが守られない場合、パフォーマンスの低下、未定義の動作、あるいは本件のようにプログラムのクラッシュを引き起こす可能性があります。

### スタックポインタ (SP) とスタックフレーム
スタックは、関数呼び出し時にローカル変数、引数、戻りアドレスなどを格納するために使用されるメモリ領域です。スタックポインタ（SP）は、スタックの現在のトップ（またはボトム、アーキテクチャによる）を指すレジスタです。関数が呼び出されると、新しいスタックフレームが作成され、SPが移動します。スタックフレームには、関数のローカルデータや、呼び出し元の関数に戻るためのアドレス（リターンアドレス、ARMでは通常Link Register: LRに格納され、スタックにプッシュされる）などが含まれます。

### `rt0_go`
`rt0_go`は、Goプログラムが起動する際のエントリポイントとなるランタイムの初期化関数です。オペレーティングシステムによってGoプログラムがロードされた後、最初に実行されるGoのコードであり、Goランタイムの初期化、スケジューラの起動、最初のgoroutineの作成など、Goプログラムが動作するために必要な基本的な設定を行います。

### `TEXT` ディレクティブ (Goアセンブリ)
Goのアセンブリ言語では、`TEXT`ディレクティブを使用して関数を定義します。その書式は通常 `TEXT symbol(SB), flags, args_size` のようになります。
*   `symbol(SB)`: 関数のシンボル名。`SB`はStatic Baseを意味し、グローバルシンボルであることを示します。
*   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`はスタックの拡張を許可しないことを示す）。
*   `args_size`: 関数の引数と戻り値の合計サイズ（バイト単位）。これはスタックフレームのサイズ計算に影響を与えます。このコミットでは、この`args_size`が`$0`から`$4`に変更されています。

## 技術的詳細

このバグは、`runtime·_initcgo`関数がC言語の関数（`_cgo_init`）を呼び出す際に、スタックポインタがARM ABIの要求する8バイト境界にアライメントされていないために発生していました。

Goのランタイムは、`rt0_go`から起動し、システムスタック上で動作します。`runtime·_initcgo`は`rt0_go`から呼び出される関数であり、その中でC言語の初期化関数`_cgo_init`を呼び出します。

問題は、`runtime·_initcgo`が呼び出された時点ではスタックポインタが8バイトアライメントされていても、`runtime·_initcgo`自身のスタックフレームの構築方法によって、C関数を呼び出す直前でアライメントが崩れてしまうことにありました。具体的には、Goのアセンブリ関数では、`TEXT`ディレクティブで指定されたスタックフレームサイズに加えて、リターンアドレス（LRレジスタの内容）をスタックにプッシュすることが一般的です。

元のコードでは、`TEXT runtime·_initcgo(SB),NOSPLIT,$0`と定義されており、これはこの関数自体がスタック上にローカル変数や引数用の領域を0バイトしか確保しないことを意味します。しかし、関数呼び出し規約により、`BL`命令（Branch with Link、関数呼び出し）を実行する前に、`LR`レジスタの内容がスタックにプッシュされます。`LR`は4バイトのレジスタであるため、スタックにプッシュされるとスタックポインタが4バイト減少し、結果として8バイトアライメントが崩れて4バイトアライメントになってしまいます。

FreeBSD/ARMのCライブラリは、この8バイトアライメントの違反に対して厳格であり、アライメントされていないスタックポインタでのC関数呼び出しを許容せず、クラッシュを引き起こしていました。

このコミットの解決策は、`runtime·_initcgo`関数の`TEXT`ディレクティブにおけるスタックフレームサイズを`$0`から`$4`に変更することです。これにより、`runtime·_initcgo`関数は自身のスタックフレームとして4バイトを確保します。この4バイトの確保と、`LR`レジスタがスタックにプッシュされる4バイトとを合わせると、合計8バイトがスタックにプッシュされることになります。これにより、C関数を呼び出す直前のスタックポインタが、呼び出し元から引き継いだ8バイトアライメントを維持したまま、再び8バイトアライメントされることが保証されます。

コメントにもあるように、`TEXT runtime·_initcgo(SB),NOSPLIT,$4`とすることで、ダミーの4バイトを確保し、`LR`のプッシュと合わせて合計8バイトのスタックフレームとなり、スタックポインタが8バイトアライメントを維持するようにしています。

## コアとなるコードの変更箇所

変更は`src/runtime/tls_arm.s`ファイルにあります。

```diff
--- a/src/runtime/tls_arm.s
+++ b/src/runtime/tls_arm.s
@@ -77,7 +77,17 @@ TEXT runtime·load_g(SB),NOSPLIT,$0
 	MOVW	0(R0), g
 	RET
 
-TEXT runtime·_initcgo(SB),NOSPLIT,$0
+// This is called from rt0_go, which runs on the system stack
+// using the initial stack allocated by the OS.
+// It calls back into standard C using the BL (R4) below.
+// To do that, the stack pointer must be 8-byte-aligned
+// on some systems, notably FreeBSD.
+// The ARM ABI says the stack pointer must be 8-byte-aligned
+// on entry to any function, but only FreeBSD's C library seems to care.
+// The caller was 8-byte aligned, but we push an LR.
+// Declare a dummy word ($4, not $0) to make sure the
+// frame is 8 bytes and stays 8-byte-aligned.
+TEXT runtime·_initcgo(SB),NOSPLIT,$4
 #ifndef GOOS_nacl
 	// if there is an _cgo_init, call it.
 	MOVW	_cgo_init(SB), R4
```

## コアとなるコードの解説

変更の中心は、`src/runtime/tls_arm.s`ファイル内の`runtime·_initcgo`関数の定義行です。

*   **変更前**: `TEXT runtime·_initcgo(SB),NOSPLIT,$0`
*   **変更後**: `TEXT runtime·_initcgo(SB),NOSPLIT,$4`

この変更は、`runtime·_initcgo`関数のスタックフレームサイズを`$0`（0バイト）から`$4`（4バイト）に増やしています。

Goのアセンブリ関数では、`TEXT`ディレクティブの最後の引数（`$0`や`$4`）は、その関数がスタック上に確保するローカル変数や引数用の領域のサイズを示します。このサイズは、関数が呼び出される際にスタックポインタが調整される量に影響します。

`runtime·_initcgo`関数は、C言語の関数`_cgo_init`を呼び出す前に、Goの呼び出し規約に従ってリターンアドレス（LRレジスタの内容）をスタックにプッシュします。LRは4バイトのレジスタです。

1.  **変更前 (`$0`)**: 関数自体が0バイトのスタック領域を確保します。しかし、LRがスタックにプッシュされると、スタックポインタは4バイト減少します。もし呼び出し元が8バイトアライメントを保証していても、この4バイトのプッシュによってスタックポインタは4バイトアライメントにずれてしまいます。
2.  **変更後 (`$4`)**: 関数自体が4バイトのスタック領域を確保します。これにLRがスタックにプッシュされる4バイトを加えると、合計で8バイトがスタックにプッシュされることになります。これにより、呼び出し元から引き継いだ8バイトアライメントが、C関数呼び出し直前でも維持されるようになります。

この修正により、`_cgo_init`が呼び出される際には、スタックポインタが常に8バイト境界にアライメントされていることが保証され、FreeBSD/ARM環境でのクラッシュが解消されます。コメントで「Declare a dummy word ($4, not $0) to make sure the frame is 8 bytes and stays 8-byte-aligned.」とあるように、この4バイトは実質的にダミーの領域として機能し、アライメントを調整するために使われています。

# [インデックス 20981] ファイルの概要

このコミットは、Goランタイムにおける`fastrand1`という擬似乱数生成器が、PowerPC 64ビットアーキテクチャ（`power64x`）上で正しく動作しない問題を修正するものです。具体的には、乱数生成の状態をテストする際の符号ビットの扱いに関するバグが修正されています。

## コミット

```
commit 40a5b3ecb1578a68b0423b8ef4eaebd5fb4c7869
Author: Austin Clements <austin@google.com>
Date:   Fri Oct 31 13:39:36 2014 -0400

    [dev.power64] runtime: fix fastrand1 on power64x
    
    fastrand1 depends on testing the high bit of its uint32 state.
    For efficiency, all of the architectures implement this as a
    sign bit test.  However, on power64, fastrand1 was using a
    64-bit sign test on the zero-extended 32-bit state.  This
    always failed, causing fastrand1 to have very short periods
    and often decay to 0 and get stuck.
    
    Fix this by using a 32-bit signed compare instead of a 64-bit
    compare.  This fixes various tests for the randomization of
    select of map iteration.
    
    LGTM=rsc
    R=rsc, dave
    CC=golang-codereviews
    https://golang.org/cl/166990043
```

## 元コミット内容

`[dev.power64] runtime: fix fastrand1 on power64x`

`fastrand1`は、その`uint32`状態の最上位ビットをテストすることに依存しています。効率のために、すべてのアーキテクチャでこれは符号ビットテストとして実装されています。しかし、`power64`では、`fastrand1`はゼロ拡張された32ビットの状態に対して64ビットの符号テストを使用していました。これは常に失敗し、`fastrand1`が非常に短い周期を持ち、しばしば0に減衰して停止する原因となっていました。

この問題を修正するために、64ビット比較の代わりに32ビット符号付き比較を使用します。これにより、`select`のランダム化やマップイテレーションに関する様々なテストが修正されます。

## 変更の背景

Goランタイムには、内部的に使用される擬似乱数生成器である`fastrand1`が存在します。これは、`select`文のランダムなケース選択や、マップのイテレーション順序のランダム化など、様々な場面で利用されます。これらの機能は、プログラムの予測可能性を低減し、デッドロックやライブロックなどの問題を回避するために重要です。

`fastrand1`の実装は、その内部状態（`uint32`）の最上位ビットを効率的にテストすることに依存しています。多くのアーキテクチャでは、この最上位ビットのテストは、数値の符号ビットをテストする命令（符号付き比較など）を利用することで効率的に行われます。

しかし、PowerPC 64ビットアーキテクチャ（`power64x`）において、`fastrand1`の実装にバグがありました。32ビットの乱数状態を扱う際に、64ビットレジスタにロードされた際にゼロ拡張され、そのゼロ拡張された64ビット値に対して符号テストが行われていました。これにより、本来32ビット値の最上位ビットをテストすべきところが、常に64ビット値の符号ビット（常に0）をテストしてしまうという問題が発生していました。

この誤った符号テストの結果、`fastrand1`は期待されるランダムなシーケンスを生成できず、非常に短い周期で同じ値を繰り返したり、最終的には0に固定されてしまったりする現象が発生していました。これは、`select`やマップイテレーションのランダム性が失われることを意味し、Goプログラムの動作に予期せぬ影響を与える可能性がありました。

## 前提知識の解説

*   **擬似乱数生成器 (PRNG: Pseudo-Random Number Generator)**: 完全にランダムではないが、統計的にランダムに見える数列を生成するアルゴリズムです。初期シード値から決定論的に次の値を生成します。Goランタイムの`fastrand1`もその一種です。
*   **符号ビット (Sign Bit)**: 2の補数表現において、数値が正か負かを示す最上位ビットです。通常、最上位ビットが0であれば正、1であれば負を示します。
*   **ゼロ拡張 (Zero Extension)**: 小さいビット幅の数値を大きいビット幅のレジスタにロードする際に、上位ビットを0で埋める操作です。例えば、32ビットの符号なし整数を64ビットレジスタにロードする場合、上位32ビットは0で埋められます。
*   **PowerPC 64ビットアーキテクチャ (`power64x`)**: IBMが開発したRISCプロセッサアーキテクチャであるPowerPCの64ビット版です。Go言語は様々なアーキテクチャをサポートしており、`power64x`もその一つです。
*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、そして`fastrand1`のような内部ユーティリティ機能を提供します。
*   **`select`文**: Go言語の`select`文は、複数の通信操作（チャネルの送受信）の中から準備ができたものをランダムに選択して実行します。このランダム性は、デッドロックを回避し、公平性を保つために重要です。
*   **マップイテレーション (Map Iteration)**: Go言語のマップ（ハッシュテーブル）は、イテレーション（要素の走査）の順序が意図的にランダム化されています。これは、プログラマがマップの順序に依存するコードを書くことを防ぎ、より堅牢なプログラムを促進するためです。このランダム化にも`fastrand1`が利用されます。
*   **アセンブリ言語 (Assembly Language)**: プロセッサが直接実行できる機械語命令を人間が読める形式で記述した低レベル言語です。Goランタイムの一部、特にパフォーマンスが重要な部分やハードウェアに密接に関わる部分はアセンブリ言語で記述されています。このコミットで変更されている`src/runtime/asm_power64x.s`は、PowerPC 64ビットアーキテクチャ向けのアセンブリコードファイルです。
*   **`CMP`命令と`CMPW`命令**: PowerPCアセンブリにおける比較命令です。
    *   `CMP R3, $0`: R3レジスタの値を64ビットとして0と比較します。
    *   `CMPW R3, $0`: R3レジスタの値を32ビットとして0と比較します。この`W`サフィックスは「Word」（32ビット）を意味します。

## 技術的詳細

`fastrand1`は、その内部状態である`uint32`値の最上位ビット（MSB: Most Significant Bit）をチェックすることで、次の乱数生成のロジックを決定します。このMSBがセットされているかどうかを効率的に判断するために、多くのアーキテクチャでは符号ビットのテストを利用します。32ビットの符号付き整数において、MSBは符号ビットとして機能するため、このビットが1であれば数値は負、0であれば正（またはゼロ）と解釈されます。

PowerPC 64ビットアーキテクチャでは、32ビットの値を64ビットレジスタにロードする際、通常はゼロ拡張が行われます。つまり、元の32ビット値はレジスタの下位32ビットに配置され、上位32ビットはすべて0で埋められます。

問題は、`fastrand1`がこのゼロ拡張された64ビット値に対して、64ビットの符号テスト（`CMP R3, $0`）を実行していた点にありました。32ビットの`uint32`状態がゼロ拡張されて64ビットレジスタに格納されると、その上位32ビットは常に0になります。したがって、たとえ元の32ビット値の最上位ビットが1（つまり、32ビット値として負）であったとしても、64ビット値としては常に正（またはゼロ）と判断されてしまいます。これは、64ビット値の符号ビットが常に0であるためです。

この誤った符号テストにより、`fastrand1`の内部ロジックが期待通りに分岐せず、擬似乱数生成のアルゴリズムが破綻していました。結果として、生成される乱数列の周期が極端に短くなり、最終的には乱数生成器が0に固定されてしまうという致命的な問題を引き起こしていました。

修正は、この誤った64ビット比較を、32ビットの符号付き比較（`CMPW R3, $0`）に置き換えることで行われました。`CMPW`命令は、レジスタの下位32ビットのみを対象として比較を行うため、ゼロ拡張された64ビット値であっても、元の32ビット値の符号ビットを正しくテストすることができます。これにより、`fastrand1`はPowerPC 64ビットアーキテクチャ上でも他のアーキテクチャと同様に正しく動作し、`select`やマップイテレーションのランダム性が回復しました。

## コアとなるコードの変更箇所

変更は、`src/runtime/asm_power64x.s`というPowerPC 64ビットアーキテクチャ向けのアセンブリコードファイル内で行われています。

```diff
--- a/src/runtime/asm_power64x.s
+++ b/src/runtime/asm_power64x.s
@@ -965,7 +965,7 @@ TEXT runtime·fastrand1(SB), NOSPLIT, $0-4
  	MOVD	g_m(g), R4
  	MOVWZ	m_fastrand(R4), R3
  	ADD	R3, R3
-	CMP	R3, $0
+	CMPW	R3, $0
  	BGE	2(PC)
  	XOR	$0x88888eef, R3
  	MOVW	R3, m_fastrand(R4)
```

## コアとなるコードの解説

上記のコードスニペットは、`runtime·fastrand1`関数のアセンブリ実装の一部です。

*   `MOVD g_m(g), R4`: 現在のgoroutineの`m`構造体（マシン記述子）へのポインタを`R4`レジスタにロードします。`m`構造体には、`fastrand1`の状態が格納されています。
*   `MOVWZ m_fastrand(R4), R3`: `m`構造体から`m_fastrand`フィールド（これが`fastrand1`の32ビット状態）を読み込み、`R3`レジスタにゼロ拡張してロードします。ここで、32ビット値が64ビットレジスタ`R3`にロードされ、上位32ビットは0で埋められます。
*   `ADD R3, R3`: `R3`レジスタの値を2倍します（左シフト1ビットに相当）。これは擬似乱数生成アルゴリズムの一部です。
*   `-	CMP	R3, $0`: **変更前の行**。`R3`レジスタの値を64ビットとして0と比較します。この命令が問題の原因でした。`R3`はゼロ拡張された32ビット値を含んでいるため、その64ビットとしての符号ビットは常に0であり、この比較は常に「正またはゼロ」と評価されていました。
*   `+	CMPW	R3, $0`: **変更後の行**。`R3`レジスタの値を32ビットとして0と比較します。`CMPW`命令は、`R3`レジスタの下位32ビットのみを対象として比較を行うため、元の32ビット値の符号ビットを正しくテストできます。これにより、`fastrand1`のロジックが意図通りに動作するようになります。
*   `BGE 2(PC)`: 比較結果に基づいて条件分岐します。`BGE`は「Greater than or Equal」（以上）の場合に分岐します。この分岐は、`fastrand1`のアルゴリズムにおける重要なステップであり、符号ビットのテスト結果に依存します。
*   `XOR $0x88888eef, R3`: 特定の定数と`R3`の値をXORします。これも擬似乱数生成アルゴリズムの一部です。
*   `MOVW R3, m_fastrand(R4)`: 更新された`R3`の値を`m_fastrand`フィールドに書き戻します。

この変更により、PowerPC 64ビットアーキテクチャ上での`fastrand1`の動作が修正され、Goプログラムのランダムな挙動が保証されるようになりました。

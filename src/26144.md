# [インデックス 26144] ファイルの概要

このコミットは、Goコマンド（`go build`, `go install`, `go list`など）がワイルドカードマッチング（例: `./...`）を行う際に、構文エラーを含むディレクトリを誤ってスキップしてしまう問題を修正します。Go 1.5以前のバージョンでは、無効なGoソースファイルを含むディレクトリがサイレントに無視されることがあり、ユーザーが重大なエラーを見落とす原因となっていました。この変更により、構文エラーのあるディレクトリも適切に処理され、エラーが明示的に報告されるようになります。

## コミット

`cmd/go`: ワイルドカードマッチング（例: `./...`）において、構文エラーのあるディレクトリをスキップしないようにする。

Fixes #11407.

## 変更の背景

Go 1.5およびそれ以前のバージョンでは、`go list`などのGoコマンドがパッケージを探索する際に、ディレクトリ内に構文エラーのあるGoソースファイルが存在すると、そのディレクトリ全体をサイレントにスキップしてしまうという問題がありました。これは、`./...`のようなワイルドカードパターンを使用して複数のパッケージを対象とする場合に特に顕著でした。

具体的には、`go/build`パッケージの`ImportDir`関数が、ディレクトリ内の最初の構文エラーに遭遇した時点で処理を中断し、エラーを返していました。このエラーが`cmd/go`のパッケージマッチングロジックで適切に処理されず、エラーのあるディレクトリがパターンに一致しないものとして扱われ、結果的に無視されていました。

この挙動は、開発者がコードベース内の重大な構文エラーに気づきにくくするという問題を引き起こしていました。例えば、`go build ./...`を実行しても、一部のパッケージに構文エラーがあってもビルドが成功したかのように見え、実際にはエラーのあるパッケージがビルド対象から外れてしまっていたのです。Issue #11407は、このサイレントスキップの問題を報告し、修正を求めたものです。

このコミットは、この問題を解決し、構文エラーのあるディレクトリもワイルドカードマッチングの対象として含め、エラーを明示的に報告するように変更することで、開発者がより早く問題に気づけるようにすることを目的としています。

## 前提知識の解説

### Goコマンドとパッケージ探索

Go言語には、コードのビルド、テスト、インストール、情報表示などを行うための様々なコマンド（`go build`, `go test`, `go install`, `go list`など）があります。これらのコマンドの多くは、ユーザーが指定したパッケージパスに基づいて、対象となるGoパッケージを探索します。

### ワイルドカードマッチング (`./...`)

Goコマンドでは、パッケージパスの指定にワイルドカードパターンを使用できます。特に `./...` は、現在のディレクトリとそのすべてのサブディレクトリにあるすべてのパッケージを対象とすることを示します。これは、プロジェクト全体をビルドしたり、テストを実行したりする際によく使われます。

### `go/build` パッケージ

`go/build`パッケージは、Goソースコードの構造を解析し、パッケージの依存関係を解決するための低レベルな機能を提供します。Goコマンドの内部で広く利用されており、Goソースファイルからパッケージ情報を抽出する中心的な役割を担っています。

*   **`build.Context`**: ビルド環境に関する情報（GOPATH、GOOS、GOARCHなど）を保持します。
*   **`build.Package`**: Goパッケージに関する詳細情報（パッケージ名、インポートパス、ソースファイルリスト、依存関係など）を格納する構造体です。
*   **`build.ImportDir(dir string, mode build.ImportMode)`**: 指定されたディレクトリ（`dir`）からGoパッケージ情報をインポートしようと試みます。成功すれば`*build.Package`構造体を返し、失敗すればエラーを返します。`mode`引数によって、インポートの挙動を制御できます（例: `build.ImportOnly`でインポートパスのみを解析）。

### Goのソースファイル解析とエラーハンドリング

Goコンパイラやツールは、Goソースファイルを解析する際に、構文エラー、パッケージ名の不一致、不正なインポートコメントなど、様々な問題に遭遇することがあります。これらの問題は通常、エラーとして報告され、プログラムのコンパイルや実行を妨げます。

## 技術的詳細

このコミットの技術的な核心は、`go/build`パッケージの`ImportDir`関数と、`cmd/go`のパッケージマッチングロジックの連携を変更することにあります。

### `src/go/build/build.go` の変更

1.  **`Package` 構造体への `InvalidGoFiles` フィールドの追加**:
    `build.Package` 構造体に `InvalidGoFiles []string` という新しいフィールドが追加されました。このフィールドは、パッケージのビルド中に構文エラー、パッケージ名の不一致、不正なインポートコメントなどの問題が検出されたGoソースファイルのリストを保持します。これにより、問題のあるファイルを記録しつつ、パッケージの解析を可能な限り継続できるようになります。

    ```go
    type Package struct {
        // ... 既存のフィールド ...
        InvalidGoFiles []string // .go source files with detected problems (parse error, wrong package name, and so on)
        // ... 既存のフィールド ...
    }
    ```

2.  **`ImportDir` 関数内のエラー処理の変更**:
    `ImportDir` 関数は、ディレクトリ内のGoソースファイルを走査し、パッケージ情報を構築します。以前は、構文エラーやその他の問題に遭遇すると、即座にエラーを返して処理を中断していました。この変更では、エラーが発生した場合でも、そのファイル名を`InvalidGoFiles`に追加し、`badFile`というヘルパー関数を通じて`badGoError`変数に最初のエラーを記録しつつ、可能な限り他のファイルの解析を継続するように修正されました。

    *   **`badFile` ヘルパー関数の導入**:
        ```go
        var badGoError error
        // ...
        badFile := func(err error) {
            if badGoError == nil {
                badGoError = err
            }
            p.InvalidGoFiles = append(p.InvalidGoFiles, name)
        }
        ```
        この関数は、最初のエラーのみを`badGoError`に保持し、問題のあるファイル名を`p.InvalidGoFiles`に追加します。

    *   **エラー発生時の挙動変更**:
        `parser.ParseFile`での構文エラー、`MultiplePackageError`（同じディレクトリ内で異なるパッケージ名が検出された場合）、不正なインポートコメント、Cgoの不正な使用など、様々なエラーケースで`return p, err`の代わりに`badFile(err)`を呼び出し、`continue`で次のファイルの処理に進むようになりました。

    *   **最終的なエラー返却ロジック**:
        ファイルの走査が完了した後、`badGoError`が`nil`でない場合（つまり、何らかの問題が検出された場合）にのみ、`return p, badGoError`としてエラーを返します。これにより、`ImportDir`は、問題のあるファイルの情報（`InvalidGoFiles`）を含む`Package`構造体を返しつつ、最初のエラーを報告できるようになります。

### `src/cmd/go/main.go` の変更

1.  **`matchPackagesInFS` 関数内の条件式の変更**:
    `matchPackagesInFS` 関数は、ワイルドカードパターンに一致するパッケージをファイルシステムから探索します。この関数内で`buildContext.ImportDir`を呼び出し、その結果に基づいてディレクトリをスキップするかどうかを判断していました。

    変更前は、`ImportDir`がエラーを返すと、そのディレクトリはパターンに一致しないものとして扱われ、スキップされていました。
    変更後、条件式が以下のように修正されました。

    ```go
    if p, err := buildContext.ImportDir(path, 0); err != nil && (p == nil || len(p.InvalidGoFiles) == 0) {
        // ... エラー処理 ...
    }
    ```
    この新しい条件式は、「`ImportDir`がエラーを返したが、それが無効なGoファイルによるものではない場合（つまり、`p`が`nil`であるか、`p.InvalidGoFiles`が空である場合）」にのみ、そのディレクトリをスキップする（またはエラーをログに記録する）ことを意味します。
    逆に言えば、`ImportDir`がエラーを返しても、`p`が`nil`ではなく、かつ`p.InvalidGoFiles`にファイルが記録されている場合（つまり、構文エラーなどの問題があるGoファイルが検出された場合）は、そのディレクトリをスキップせず、後続のビルドやリスト処理の対象として含めるようになります。これにより、エラーが明示的に報告される機会が生まれます。

### `src/cmd/go/go_test.go` の変更

1.  **`TestWildcardMatchesSyntaxErrorDirs` テストの追加**:
    このコミットの意図を検証するために、新しいテストケースが追加されました。このテストは、意図的に構文エラーを含むGoファイル（`pkg mypackage`という不正なパッケージ宣言）を持つディレクトリを作成し、`go list ./...`、`go build ./...`、`go install ./...`といったコマンドが、そのエラーをサイレントにスキップせずに、適切に失敗することを確認します。

    ```go
    func TestWildcardMatchesSyntaxErrorDirs(t *testing.T) {
        tg := testgo(t)
        defer tg.cleanup()
        tg.tempFile("src/mypkg/x.go", `package mypkg`)
        tg.tempFile("src/mypkg/y.go", `pkg mypackage`) // 構文エラー
        tg.setenv("GOPATH", tg.path("."))
        tg.cd(tg.path("src/mypkg"))
        tg.runFail("list", "./...") // 失敗することを期待
        tg.runFail("build", "./...") // 失敗することを期待
        tg.runFail("install", "./...") // 失敗することを期待
    }
    ```
    このテストは、変更が正しく機能し、構文エラーのあるディレクトリがもはやサイレントにスキップされないことを保証します。

## コアとなるコードの解説

このコミットの主要な変更は、Goのビルドシステムがエラーをどのように扱うか、特にパッケージの探索と解析の段階でどのように扱うかという点にあります。

1.  **エラーの「収集」と「遅延報告」**:
    `src/go/build/build.go`の`ImportDir`関数は、以前は「最初のエラーで即座に停止」するモデルでした。しかし、この変更により、「エラーを収集し、可能な限り解析を継続し、最終的に最初のエラーを報告する」モデルに移行しました。
    `InvalidGoFiles`フィールドと`badGoError`変数の導入は、この新しいモデルを支えています。`ImportDir`は、構文エラーやその他の問題に遭遇しても、すぐに処理を中断せず、問題のあるファイル名を`InvalidGoFiles`に記録し、最初のエラーを`badGoError`に保持します。これにより、ディレクトリ内の他の有効なGoファイルに関する情報を引き続き収集できます。

2.  **`cmd/go` と `go/build` の連携強化**:
    `src/cmd/go/main.go`の`matchPackagesInFS`関数における条件式の変更は、`cmd/go`が`go/build`パッケージから返される情報をより詳細に解釈するようにしたものです。
    以前は、`ImportDir`がエラーを返すと、`matchPackagesInFS`はそのディレクトリを無条件にスキップしていました。しかし、新しい条件`err != nil && (p == nil || len(p.InvalidGoFiles) == 0)`は、`ImportDir`がエラーを返した場合でも、それが`InvalidGoFiles`に記録されるような「無効なGoファイル」によるエラーであれば、そのディレクトリをスキップしないように指示します。
    これは、`ImportDir`がエラーを返しても、`p`（`*build.Package`）が`nil`ではなく、`p.InvalidGoFiles`に何らかのファイルがリストされている場合、そのディレクトリは「Goパッケージとして認識できるが、内部に問題のあるファイルがある」と判断されるためです。このようなディレクトリは、ワイルドカードマッチングの対象から外すべきではなく、後続のビルドプロセスでエラーとして報告されるべきである、という設計思想に基づいています。

3.  **ユーザーエクスペリエンスの向上**:
    この一連の変更により、`go build ./...`のようなコマンドを実行した際に、構文エラーのあるパッケージがサイレントに無視されることがなくなります。代わりに、Goコマンドはエラーを明示的に報告し、開発者が問題に迅速に対処できるようになります。これは、Goツールの堅牢性とユーザーフレンドリーさを向上させる重要な改善です。

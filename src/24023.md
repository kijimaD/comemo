## 変更の背景

Goコンパイラは、ソースコードを解析し、エラーが発生した場合にはそのエラーが発生した正確な行番号を報告する必要があります。しかし、以前のコンパイラでは、特定の状況下、特に「無名定数」（unnamed constants）が関与する場合に、エラーメッセージの行番号が正しく報告されない問題がありました。

この問題は、`#8836` として報告されており、開発者がコンパイルエラーに遭遇した際に、誤った行番号が示されることでデバッグが困難になるという実用的な課題を引き起こしていました。例えば、関数呼び出しの引数リスト内で無名定数を使用し、その引数に型不一致などのエラーがあった場合、コンパイラが報告する行番号が実際の定数の位置ではなく、関数呼び出しの開始行など、より一般的な位置を指してしまうことがありました。

このコミットは、`setlineno` 関数がノードのタイプに応じて行番号を設定するロジックを改善し、無名定数に対しても適切な行番号が設定されるようにすることで、この問題を解決することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

*   **`cmd/compile`**: Go言語の公式コンパイラです。ソースコードを解析し、中間表現を生成し、最終的に実行可能なバイナリを生成する役割を担います。
*   **抽象構文木 (AST)**: コンパイラがソースコードを解析した結果として生成するツリー構造のデータ表現です。ソースコードの各要素（変数、関数、定数など）はASTの「ノード」（`Node`）として表現されます。
*   **`Node`**: ASTの基本的な構成要素です。各`Node`は、それが表すソースコードの要素の種類を示す `Op` (Operation) フィールドや、ソースコード上の位置を示す `Lineno` (Line Number) フィールドなどを持っています。
*   **`lineno`**: コンパイラが現在処理しているソースコードの行番号を追跡するためのグローバル変数（またはそれに準ずるメカニズム）です。
*   **`setlineno(n *Node)`**: コンパイラ内部で使用される関数で、現在の処理行番号を、引数として渡されたASTノード `n` の行番号に更新する役割を担います。これにより、エラーメッセージなどが正確なソースコードの位置を指すようになります。
*   **`n.Op`**: `Node`の操作タイプを示すフィールドです。このコミットでは以下の`Op`が重要です。
    *   **`ONAME`**: 変数名や関数名などの識別子を表すノード。
    *   **`OTYPE`**: 型を表すノード。
    *   **`OPACK`**: パッケージを表すノード。
    *   **`OLITERAL`**: リテラル（定数）を表すノード。例えば、`10`、`"hello"`、`true` など。
*   **`n.Sym`**: `Node`がシンボル（名前）に関連付けられている場合に、そのシンボルへのポインタを保持するフィールドです。例えば、`ONAME`ノードは通常`Sym`を持ちますが、無名定数（例: `0` や `42` といった直接記述された数値）の`OLITERAL`ノードは`Sym`を持たないことがあります。
*   **`fallthrough`**: Go言語の `switch` ステートメントで使用されるキーワードで、一致した `case` ブロックの実行後、次の `case` ブロックの実行を継続させます。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/subr.go` 内の `setlineno` 関数のロジック変更にあります。

`setlineno` 関数は、コンパイラがASTをトラバースする際に、現在の処理コンテキストの行番号を更新するために呼び出されます。これにより、コンパイルエラーが発生した際に、エラーメッセージがソースコードの正しい位置を指すことが保証されます。

変更前の `setlineno` 関数では、`ONAME`, `OTYPE`, `OPACK`, `OLITERAL` の各ノードタイプに対しては、行番号の更新を行わない `break` 処理が記述されていました。これは、これらのノードが通常、それ自体で新しい行番号を持つというよりも、より大きな式やステートメントの一部として扱われるため、その親ノードやコンテキストが行番号を決定するという設計思想に基づいていた可能性があります。

しかし、このアプローチは「無名定数」である `OLITERAL` ノードにおいて問題を引き起こしました。特に、`n.Sym` が `nil` である `OLITERAL` ノード（つまり、名前を持たない直接記述された定数）の場合、そのノード自体がエラーの原因となるにもかかわらず、`setlineno` が行番号を更新しないため、エラーメッセージが不正確な行番号を報告してしまう事態が発生していました。

このコミットでは、`OLITERAL` ノードの処理が変更されました。具体的には、`OLITERAL` ノードであっても、もし `n.Sym` が `nil` であれば（つまり無名定数であれば）、`fallthrough` を使用して `default` ケースの処理に移行するように修正されました。`default` ケースでは、ノード `n` の `Lineno` フィールドを使用して `lineno` を更新するロジックが含まれています。これにより、無名定数に対してもそのノード自身の `Lineno` が正しく反映されるようになり、エラーメッセージの精度が向上しました。

`test/fixedbugs/issue8836.go` は、この修正が正しく機能することを確認するためのテストケースです。このテストケースでは、`foobar` 関数への引数として無名定数 `42` を渡し、意図的に型エラーを発生させています。コメント `// ERROR ".*"` は、この行でコンパイルエラーが発生し、そのエラーメッセージが何らかの文字列を含むことを期待していることを示しています。このテストは、修正が適用されたコンパイラが `42` の行で正確なエラーを報告することを確認します。

## コアとなるコードの解説

変更の核心は、`setlineno` 関数内の `switch n.Op` ステートメントにおける `OLITERAL` ケースの扱いです。

**変更前:**

```go
		switch n.Op {
		case ONAME, OTYPE, OPACK, OLITERAL:
			break // OLITERALを含むこれらのノードでは行番号を更新しない
```

このコードでは、`OLITERAL` ノードが検出された場合、`break` によって `setlineno` 関数は現在の `lineno` を更新せずに終了していました。これにより、無名定数（`OLITERAL` ノードで `n.Sym == nil` のもの）がエラーの原因となった場合でも、そのノード自身の正確な行番号が `lineno` に反映されず、結果として不正確なエラー報告につながっていました。

**変更後:**

```go
		switch n.Op {
		case ONAME, OTYPE, OPACK:
			break // これらのノードでは引き続き行番号を更新しない

		case OLITERAL:
			if n.Sym != nil {
				break // 名前付き定数（n.Sym != nil）の場合は行番号を更新しない
			}
			fallthrough // 無名定数（n.Sym == nil）の場合はdefaultケースへ進む

		default:
			lineno = n.Lineno // ノードの行番号でlinenoを更新
			if lineno == 0 {
				// ...
			}
```

この修正では、`OLITERAL` ケースが独立して扱われるようになりました。
1.  まず、`n.Sym != nil` のチェックが行われます。これは、定数が名前を持っているかどうか（例: `const MyConst = 42` の `MyConst`）を判断します。名前付き定数の場合、その定数の宣言箇所が行番号のコンテキストとして適切であるため、ここでは `break` して行番号の更新を行いません。
2.  しかし、`n.Sym == nil` の場合、つまり「無名定数」（例: `foobar(&a, 0, 0, 42)` の `0` や `42`）である場合は、`fallthrough` キーワードが使用されます。
3.  `fallthrough` により、実行は次の `default` ケースへと継続されます。
4.  `default` ケースでは、`lineno = n.Lineno` という行があり、ここで現在の処理行番号 `lineno` が、問題の `OLITERAL` ノード自身の `Lineno` フィールドの値で更新されます。これにより、無名定数が関与するエラーに対しても、その定数がソースコード上で記述されている正確な行番号がコンパイラによって認識され、エラーメッセージに反映されるようになります。

この変更は、Goコンパイラが生成するエラーメッセージの品質を向上させ、開発者がより効率的に問題を特定し修正できるようにするための重要な改善です。

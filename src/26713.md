## 変更の背景

Goコンパイラは、長らく「gc」と呼ばれる独自のコンパイラを使用してきました。このコンパイラは、最適化の機会を増やすために、プログラムの内部表現をより抽象的で分析しやすい形式に変換する新しいバックエンドを必要としていました。その解決策として導入されたのがSSA (Static Single Assignment) 形式です。

SSAバックエンドの開発は、Go 1.7リリースに向けての主要な取り組みの一つでした。SSA形式は、各変数が一度だけ代入されるようにプログラムを変換するもので、これによりデータフロー解析や最適化が大幅に容易になります。このコミットが行われた2016年2月は、Go 1.7のリリースサイクルが本格化する前の段階であり、SSAバックエンドの統合と安定化が活発に進められていた時期に当たります。

`dev.ssa` ブランチは、このSSAバックエンドの開発と実験のために設けられたものであり、このマージコミットは、`master` ブランチで進行していた他の開発と `dev.ssa` ブランチでのSSA作業を同期させるための定期的な操作の一環です。特に、`ssa.go` ファイルの導入は、AST (Abstract Syntax Tree) からSSA形式への変換ロジックがこの時点で大きく進展していたことを示しています。

## 前提知識の解説

### 1. コンパイラのバックエンドと中間表現 (IR)

コンパイラは通常、ソースコードを解析して抽象構文木 (AST) を生成する「フロントエンド」、ASTを最適化に適した中間表現 (IR) に変換し、様々な最適化を行う「ミドルエンド」、そしてIRをターゲットマシンコードに変換する「バックエンド」に分かれます。GoコンパイラにおけるSSAバックエンドは、このミドルエンドとバックエンドの間に位置し、最適化の基盤となるIRとしてSSA形式を採用しています。

### 2. 静的単一代入 (Static Single Assignment, SSA) 形式

SSA形式は、プログラム中の各変数がただ一度だけ代入されるようにする中間表現です。例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

これをSSA形式に変換すると、以下のようになります。

```go
x0 = 1
x1 = x0 + 2
y0 = x1 * 3
```

各代入ごとに新しいバージョン (添字付き) の変数が導入されるため、変数の定義と使用の関係が明確になります。これにより、以下のようなコンパイラ最適化が容易になります。

*   **デッドコード削除 (Dead Code Elimination)**: 使用されていない代入を簡単に特定し削除できます。
*   **共通部分式除去 (Common Subexpression Elimination)**: 同じ計算が複数回行われている場合、一度だけ計算して結果を再利用できます。
*   **定数伝播 (Constant Propagation)**: 定数値をプログラム全体に伝播させ、計算をコンパイル時に実行できます。
*   **レジスタ割り当て (Register Allocation)**: 変数のライフタイムが明確になるため、効率的なレジスタ割り当てが可能になります。

### 3. GoコンパイラのASTとSSA

Goコンパイラのフロントエンドは、Goのソースコードを解析してAST (`Node`構造体で表現される) を構築します。従来のバックエンドはASTを直接操作してコード生成を行っていましたが、SSAバックエンドではASTをSSA形式に変換し、そのSSA形式に対して最適化を適用してから最終的なマシンコードを生成します。

### 4. `cmd/compile/internal/ssa` パッケージ

GoコンパイラのSSAバックエンドは、`cmd/compile/internal/ssa` パッケージに実装されています。このパッケージは、SSA形式の関数 (`ssa.Func`)、ブロック (`ssa.Block`)、値 (`ssa.Value`) などのデータ構造と、それらを操作するためのAPIを提供します。`ssa.go` は、GoコンパイラのAST (`gc`パッケージ) からこの `ssa` パッケージのデータ構造を構築する役割を担います。

## 技術的詳細

このコミットの主要な技術的詳細は、GoコンパイラのASTからSSA形式への変換ロジックを実装する `src/cmd/compile/internal/gc/ssa.go` ファイルに集約されています。

### `ssa.go` の役割

`ssa.go` は、Goコンパイラのフロントエンドが生成したAST (`gc`パッケージの`Node`構造体) を受け取り、`cmd/compile/internal/ssa` パッケージが定義するSSA形式のデータ構造 (`ssa.Func`, `ssa.Block`, `ssa.Value`) に変換する役割を担います。これは、ASTベースのIRとSSAベースのIRの間の「橋渡し」となる部分です。

### `state` 構造体

SSA変換プロセスは、`state` 構造体によって管理されます。この構造体は、SSA関数 (`*ssa.Func`)、現在のSSAブロック (`*ssa.Block`)、変数とSSA値のマッピング (`vars`、`decladdrs`、`varsyms`)、ラベル情報 (`labels`、`labeledNodes`)、ラインナンバーのスタック (`line`) など、SSA生成に必要なすべてのコンテキストを保持します。

### `buildssa` 関数

`buildssa(fn *Node)` 関数は、特定のGo関数 (`fn` はその関数のASTノード) のSSA形式を構築するためのエントリポイントです。この関数は、`state` 構造体を初期化し、関数のエントリブロックと初期値を設定します。その後、関数のAST (`fn.Func.Enter` と `fn.Nbody`) を走査し、各ステートメントと式をSSA形式に変換します。

### ASTからSSAへの変換

`state.stmt(n *Node)` と `state.expr(n *Node)` 関数が、ASTノードをSSA形式に変換する中心的なロジックを実装しています。

*   **ステートメントの変換 (`stmt`)**: `OAS` (代入)、`OIF` (if文)、`OFOR` (forループ)、`OGOTO` (goto文)、`OLABEL` (ラベル)、`ORETURN` (return文) など、様々なASTステートメントを対応するSSAブロックと値に変換します。特に、制御フロー構造 (if, for, goto) は、SSAのブロック構造 (`ssa.BlockPlain`, `ssa.BlockIf`, `ssa.BlockLoop` など) にマッピングされます。
*   **式の変換 (`expr`)**: `OLITERAL` (リテラル)、`ONAME` (変数参照)、`OCONV` (型変換)、`OADD` (加算) など、様々なAST式をSSA値に変換します。例えば、`OLITERAL` は `ssa.OpConstInt64` などの定数SSA値に、`OADD` は `ssa.OpAdd64` などの演算SSA値に変換されます。

### 演算子のマッピング

`opToSSA`、`fpConvOpToSSA`、`shiftOpToSSA` といったマップが定義されており、GoのAST演算子 (`Op`) と型 (`EType`) の組み合わせを、対応するSSA演算子 (`ssa.Op`) に変換します。これにより、Goの言語レベルの操作が、SSAバックエンドが理解できる低レベルの操作に変換されます。

### `shouldssa` 関数

`shouldssa(fn *Node)` 関数は、特定の関数をSSAバックエンドでコンパイルするかどうかを決定します。これは、環境変数 (`GOSSAFUNC`, `GOSSAHASH`, `GOSSAPKG`) を利用して、SSAコンパイルを制御するためのデバッグ/開発機能です。これにより、開発者は特定の関数やパッケージのみをSSAでコンパイルし、問題の特定やデバッグを容易に行うことができます。

### `order.go` の変更

`src/cmd/compile/internal/gc/order.go` の `cleantempnopop` 関数における変更は、一時変数の管理方法がSSAの導入に合わせて変更されたことを示しています。従来の `*NodeList` を使用したリンクリストベースの管理から、`[]*Node` を使用したスライスベースの管理に移行しており、これはSSA形式での変数管理の効率化や整合性向上に寄与します。特に、`l.N.Name.Keepalive = false` と `l.N.Addrtaken = true` の設定は、SSAが変数のライフタイムを正確に追跡し、不要な変数を削除したり、必要な変数を保持したりするためのヒントを提供します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go`

このファイルは、GoコンパイラのSSAバックエンドへの入り口であり、ASTからSSAへの変換をオーケストレーションします。

*   **`shouldssa` 関数**:
    この関数は、特定の関数をSSAでコンパイルするかどうかを決定します。環境変数 `GOSSAFUNC`、`GOSSAPKG`、`GOSSAHASH` をチェックすることで、開発者がSSAコンパイルの適用範囲を細かく制御できるようにします。これは、SSAバックエンドがまだ開発段階であった時期に、特定のバグをデバッグしたり、パフォーマンスを比較したりするために非常に重要な機能でした。例えば、`GOSSAFUNC=MyFunction` と設定すると、`MyFunction` のみがSSAでコンパイルされ、そのSSA IRが `ssa.html` に出力される可能性があります。

*   **`buildssa` 関数**:
    Go関数のAST (`*Node`) を受け取り、対応するSSA形式の関数 (`*ssa.Func`) を構築します。
    1.  `state` 構造体を初期化し、SSA変換のコンテキストを設定します。
    2.  関数のエントリブロック (`s.f.Entry`) を作成し、メモリ (`s.startmem`)、スタックポインタ (`s.sp`)、グローバルポインタ (`s.sb`) などの初期SSA値を生成します。
    3.  関数のローカル変数 (`PPARAM`, `PAUTO`) のアドレスを `decladdrs` マップに記録します。これは、変数のロード/ストア操作をSSAで表現するために必要です。
    4.  `s.stmtList(fn.Func.Enter)` と `s.stmtList(fn.Nbody)` を呼び出し、関数のASTを走査してSSA形式に変換します。
    5.  変換後、`ssa.Compile(s.f)` を呼び出して、SSAパッケージに実際の最適化とコード生成を委ねます。

*   **`state` 構造体**:
    SSA変換中の状態を保持する中心的なデータ構造です。
    -   `config *ssa.Config`: SSAバックエンドの設定情報。
    -   `f *ssa.Func`: 現在構築中のSSA関数。
    -   `labels map[string]*ssaLabel`: ラベル定義と使用を追跡するためのマップ。
    -   `curBlock *ssa.Block`: 現在コードを生成しているSSAブロック。
    -   `vars map[*Node]*ssa.Value`: 現在のブロックにおける変数 (`*Node`) とそのSSA値 (`*ssa.Value`) のマッピング。
    -   `decladdrs map[*Node]*ssa.Value`: ローカル変数のアドレスを保持。
    -   `startmem`, `sp`, `sb`: メモリ、スタックポインタ、スタティックベースポインタを表すSSA値。

*   **`stmt` および `expr` メソッド**:
    ASTノードをSSA形式に変換する再帰的な処理を行います。
    -   `stmt` は主に制御フローや代入などのステートメントを処理し、SSAブロックの分岐や結合を管理します。
    -   `expr` は主に式を処理し、その式の計算結果を表すSSA値を生成します。
    -   例えば、`OAS` (代入) の場合、右辺の式を `s.expr` でSSA値に変換し、その値を左辺の変数に代入するSSA操作 (`ssa.OpStore` など) を生成します。
    -   `OIF` (if文) の場合、条件式を評価し、結果に基づいて `ssa.BlockIf` を生成し、thenブロックとelseブロックへのエッジを追加します。

*   **演算子マッピング (`opToSSA`, `fpConvOpToSSA`, `shiftOpToSSA`)**:
    GoのASTで定義されている様々な演算子 (例: `OADD`, `ODIV`, `OLSH`) と型 (`TINT8`, `TFLOAT64` など) の組み合わせを、SSAバックエンドが理解できる具体的なSSA操作 (例: `ssa.OpAdd8`, `ssa.OpDiv64F`, `ssa.OpLsh64x64`) に変換するためのテーブルです。これにより、抽象的なGoの操作が、ターゲットアーキテクチャに依存しないSSAの低レベル操作に変換されます。

### `src/cmd/compile/internal/gc/order.go`

`cleantempnopop` 関数の変更は、SSAバックエンドへの移行に伴う一時変数管理の改善を示しています。

*   **`cleantempnopop` 関数の変更点**:
    この関数は、一時変数のスタックから特定のマークより上の変数を「kill」（無効化）する役割を担います。
    -   以前は `*NodeList` (リンクリスト) で一時変数を管理していましたが、変更後は `[]*Node` (スライス) を使用するようになりました。これにより、インデックスベースのアクセスが可能になり、より効率的な処理が期待できます。
    -   `l.N.Name.Keepalive = false` と `l.N.Addrtaken = true` の設定は、SSAコンパイラに対して、これらの変数がもはや「生きていない」（`Keepalive=false`）が、そのアドレスは「取られている」（`Addrtaken=true`）可能性があることを伝えます。これは、ガベージコレクションや最適化において、変数の正確なライフタイム情報をSSAが利用できるようにするための重要なヒントです。特に、`Addrtaken=true` は、変数がポインタとして扱われる可能性があることを示し、SSAがその変数をメモリ上に保持する必要があることを示唆します。

これらの変更は、GoコンパイラがASTベースの処理からSSAベースの処理へと移行する過程で、変数のライフタイム管理やメモリ割り当ての決定をSSAバックエンドに委ねるための重要なステップです。

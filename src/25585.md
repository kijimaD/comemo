## 元コミット内容

```
cmd/go: handle linking against a shared library that implicitly includes a package

If you say "go install -buildmode=shared a b" and package a depends on another
package c, package c is implicitly included in the resulting shared library (as
specified by "Go Execution Modes"). But if c depends on b, linking against this
shared library hangs, because the go tool doesn't know when computing c's
dependencies that c is part of the same shared library as c.

Fix this by tracking the shared library a package *is* in separately from the
shared library a package has been explicitly linked into.

Fixes #13044
```

## 変更の背景

このコミットは、Goの共有ライブラリビルドモード (`-buildmode=shared`) における特定の依存関係解決の問題を修正するために導入されました。

問題のシナリオは以下の通りです。
1.  `go install -buildmode=shared a b` のように、複数のパッケージを共有ライブラリとしてビルドしようとします。
2.  パッケージ `a` がパッケージ `c` に依存している場合、Goのビルドシステムは「Go Execution Modes」の仕様に従い、パッケージ `c` を結果の共有ライブラリに**暗黙的に**含めます。
3.  ここで、パッケージ `c` が、共有ライブラリに**明示的に**リンクされているパッケージ `b` にも依存しているとします。
4.  この状況で、`go tool` が `c` の依存関係を計算する際、`c` 自身が `b` と同じ共有ライブラリの一部であるという事実を認識できませんでした。
5.  この認識不足が原因で、共有ライブラリへのリンク処理がハングアップするという問題が発生していました。

つまり、`go tool` は、あるパッケージが「どの共有ライブラリに属しているか」と「どの共有ライブラリにリンクされているか」を区別できていなかったため、循環参照のような依存関係の誤解釈が生じていたのです。この修正は、この区別を明確にすることで、ビルドプロセスのハングアップを防ぐことを目的としています。

## 前提知識の解説

### Goのビルドモード (`-buildmode`)

Goコンパイラ (`go build` や `go install`) は、`-buildmode` フラグを使用して様々なビルドモードをサポートしています。
*   **`exe` (デフォルト)**: 実行可能ファイルをビルドします。
*   **`archive`**: 静的ライブラリ (`.a` ファイル) をビルドします。
*   **`shared`**: 共有ライブラリ (`.so` や `.dll` など) をビルドします。複数のGoパッケージを一つの共有ライブラリにまとめ、他のGoプログラムやC/C++プログラムから利用できるようにします。
*   **`c-archive`**: C言語の静的ライブラリをビルドします。
*   **`c-shared`**: C言語の共有ライブラリをビルドします。

このコミットは、特に `shared` モードに関連する問題に対処しています。

### 共有ライブラリ (Shared Libraries) の概念

共有ライブラリは、複数のプログラムで共有されるコードの集合体です。これにより、ディスクスペースの節約、メモリ使用量の削減、およびプログラムのモジュール化が促進されます。Goでは、`-buildmode=shared` を使用してGoパッケージを共有ライブラリとしてビルドできます。これにより、Goのランタイムと複数のGoパッケージが単一の共有ライブラリにまとめられ、他のGoプログラムがそのライブラリにリンクして利用できるようになります。

### Goのパッケージ依存関係の解決

Goのビルドシステムは、`import` ステートメントに基づいてパッケージ間の依存関係を解決します。ビルドプロセス中、`go tool` はこれらの依存関係を解析し、正しい順序でパッケージをコンパイルおよびリンクするためのビルドグラフを構築します。このグラフは、どのパッケージがどのパッケージに依存しているか、そしてそれらをどのようにビルドすべきかを決定します。

### `cmd/go` ツールの役割

`cmd/go` は、Go言語のビルド、テスト、インストール、フォーマットなど、様々な操作を管理する主要なコマンドラインツールです。Goのソースコードを解析し、コンパイラやリンカを呼び出して最終的なバイナリを生成する役割を担っています。`src/cmd/go/build.go` は、このツールのビルド関連のコアロジックを含んでいます。

### `action` および `action1` 関数の役割

`src/cmd/go/build.go` 内の `action` および `action1` 関数は、Goのビルドプロセスにおいて非常に重要です。これらは、特定のパッケージに対して実行すべき「アクション」（コンパイル、インストールなど）を定義し、そのアクションが依存する他のアクション（依存パッケージのビルドなど）を再帰的に決定することで、ビルドグラフを構築します。

*   `action`: パッケージのビルドアクションを決定するエントリポイントの一つ。
*   `action1`: `action` の内部で呼び出され、より詳細なロジック（共有ライブラリの考慮など）を処理します。この関数は、パッケージのビルドモード、依存関係のビルドモード、および共有ライブラリを検索するかどうか (`lookshared`) を引数として取ります。

### `p.Shlib` の意味

`Package` 構造体内の `Shlib` フィールドは、そのパッケージが属する共有ライブラリの名前を保持します。これは、パッケージが共有ライブラリの一部としてビルドされる場合に設定されます。

## 技術的詳細

このコミットの核心的な問題は、`go tool` がパッケージの依存関係を解決する際に、あるパッケージが「どの共有ライブラリに属しているか」という情報と、「どの共有ライブラリにリンクされているか」という情報を混同していた点にあります。

具体的には、`go install -buildmode=shared a b` の例で、`a` が `c` に依存し、`c` が `b` に依存する場合を考えます。
*   `a` と `b` は明示的に共有ライブラリに含められます。
*   `c` は `a` の依存関係として**暗黙的に**同じ共有ライブラリに含められます。
*   `c` が `b` に依存しているため、`go tool` は `c` の依存関係を解決しようとします。
*   このとき、`go tool` は `c` が `b` と同じ共有ライブラリの一部であることを認識できず、`b` を外部の共有ライブラリとして扱おうとするため、依存関係の解決がループしたり、ハングアップしたりしていました。

この問題を解決するために、`action1` 関数に新しい引数 `forShlib string` が追加されました。
*   `forShlib` は、現在処理中のパッケージ `p` が「どの共有ライブラリの一部になる予定か」を示す文字列です。これは、パッケージが明示的に共有ライブラリに含められる場合だけでなく、暗黙的に含められる場合にも設定されます。
*   これにより、`action1` は、パッケージ `p` の依存関係 `p1` を処理する際に、`p1` が `p` と同じ共有ライブラリの一部であるかどうかを正確に判断できるようになります。

新しいロジックでは、以下のケースが考慮されます。
1.  **現在のパッケージ `p` が共有ライブラリの一部である場合 (`forShlib != ""`)**:
    *   依存パッケージ `p1` が明示的に**異なる**共有ライブラリの一部である場合 (`p1.Shlib != "" && p1.Shlib != forShlib`)、`p1` はその異なる共有ライブラリのアクションとして依存関係に追加されます。
    *   それ以外の場合（`p1` が同じ共有ライブラリの一部であるか、まだどの共有ライブラリにも属していない場合）、`p1` は現在の共有ライブラリの一部としてビルドされるアクションとして依存関係に追加されます。この際、`lookshared` は `false` に設定され、`p1` が外部の共有ライブラリとして検索されるのを防ぎます。
2.  **現在のパッケージ `p` が共有ライブラリの一部ではない場合 (`forShlib == ""`)**:
    *   依存パッケージ `p1` が共有ライブラリの一部である場合 (`p1.Shlib != ""`)、`p1` はその共有ライブラリのアクションとして依存関係に追加されます。
    *   それ以外の場合、`p1` は通常のパッケージとしてビルドされるアクションとして依存関係に追加されます。

この変更により、`go tool` はパッケージが「どの共有ライブラリに属しているか」というコンテキストを正確に保持し、依存関係の解決時に誤った外部リンクを試みることを防ぎます。結果として、共有ライブラリビルドモードでのハングアップが解消されます。

## コアとなるコードの解説

このコミットの主要な変更は、`action1` 関数に `forShlib string` 引数を導入し、それに基づいて依存関係の解決ロジックを調整した点にあります。

### `forShlib` 引数の役割

`forShlib` 引数は、現在処理中のパッケージ `p` が、最終的にどの共有ライブラリに属することになるのかを示すコンテキストを提供します。
*   `forShlib == ""` の場合、`p` は共有ライブラリの一部としてビルドされていないことを意味します。
*   `forShlib != ""` の場合、`p` は `forShlib` で指定された共有ライブラリの一部としてビルドされていることを意味します。

この情報は、`p` がインポートするパッケージ `p1` のビルドアクションを決定する際に非常に重要になります。

### `action1` 内の新しい依存関係解決ロジック

```go

    			// a.deps, otherwise put the action for p1 into a.deps.

このコードブロックは、`p` がインポートする各パッケージ `p1` に対して、適切なビルドアクションを `a.deps` (現在のパッケージ `p` のアクションが依存するアクションのリスト) に追加します。

1.  **`if forShlib != ""` (現在のパッケージ `p` が共有ライブラリの一部である場合)**:
    *   これは、`p` が共有ライブラリ (`forShlib` で指定されたもの) のコンテキストでビルドされていることを意味します。
    *   **`if p1.Shlib != "" && p1.Shlib != forShlib` (依存パッケージ `p1` が明示的に異なる共有ライブラリの一部である場合)**:
        *   `p1` は、`p` が属する共有ライブラリとは別の共有ライブラリに属しています。この場合、`p1` はその外部共有ライブラリとしてリンクされる必要があります。
        *   `b.action1(depMode, depMode, p1, true, p1.Shlib)`: `lookshared` を `true` に設定し、`p1.Shlib` を `forShlib` として渡すことで、`p1` が外部の共有ライブラリとして正しく扱われるようにします。
    *   **`else` (依存パッケージ `p1` が現在の共有ライブラリの一部であるか、まだどの共有ライブラリにも属していない場合)**:
        *   `p1` は、`p` と同じ共有ライブラリの一部としてビルドされるべきです（暗黙的または明示的に）。
        *   `b.action1(depMode, depMode, p1, false, forShlib)`: `lookshared` を `false` に設定することで、`p1` が外部の共有ライブラリとして検索されるのを防ぎます。`forShlib` をそのまま渡すことで、`p1` が現在の共有ライブラリのコンテキストで処理されることを保証します。

2.  **`else` (現在のパッケージ `p` が共有ライブラリの一部ではない場合)**:
    *   これは、`p` が通常の実行可能ファイルなどのコンテキストでビルドされていることを意味します。
    *   `b.action1(depMode, depMode, p1, buildLinkshared, p1.Shlib)`:
        *   `buildLinkshared` は、グローバルな設定に基づいて共有ライブラリへのリンクを許可するかどうかを決定します。
        *   `p1.Shlib` を `forShlib` として渡すことで、`p1` がもし共有ライブラリの一部であれば、そのコンテキストで処理されるようにします。

この新しいロジックにより、`go tool` は、パッケージが「どの共有ライブラリに属しているか」という情報を正確に追跡し、依存関係の解決時に、同じ共有ライブラリ内のパッケージを外部の共有ライブラリとして誤って扱ってしまう問題を回避できるようになりました。これにより、共有ライブラリビルド時のハングアップが解消され、より堅牢なビルドシステムが実現されました。

## 変更の背景

このコミットは、Goの共有ライブラリビルドモード (`-buildmode=shared`) における特定の依存関係解決の問題を修正するために導入されました。

問題のシナリオは以下の通りです。
1.  `go install -buildmode=shared a b` のように、複数のパッケージを共有ライブラリとしてビルドしようとします。
2.  パッケージ `a` がパッケージ `c` に依存している場合、Goのビルドシステムは「Go Execution Modes」の仕様に従い、パッケージ `c` を結果の共有ライブラリに**暗黙的に**含めます。
3.  ここで、パッケージ `c` が、共有ライブラリに**明示的に**リンクされているパッケージ `b` にも依存しているとします。
4.  この状況で、`go tool` が `c` の依存関係を計算する際、`c` 自身が `b` と同じ共有ライブラリの一部であるという事実を認識できませんでした。
5.  この認識不足が原因で、共有ライブラリへのリンク処理がハングアップするという問題が発生していました。

つまり、`go tool` は、あるパッケージが「どの共有ライブラリに属しているか」と「どの共有ライブラリにリンクされているか」を区別できていなかったため、循環参照のような依存関係の誤解釈が生じていたのです。この修正は、この区別を明確にすることで、ビルドプロセスのハングアップを防ぐことを目的としています。

## 前提知識の解説

### Goのビルドモード (`-buildmode`)

Goコンパイラ (`go build` や `go install`) は、`-buildmode` フラグを使用して様々なビルドモードをサポートしています。
*   **`exe` (デフォルト)**: 実行可能ファイルをビルドします。
*   **`archive`**: 静的ライブラリ (`.a` ファイル) をビルドします。
*   **`shared`**: 共有ライブラリ (`.so` や `.dll` など) をビルドします。複数のGoパッケージを一つの共有ライブラリにまとめ、他のGoプログラムやC/C++プログラムから利用できるようにします。
*   **`c-archive`**: C言語の静的ライブラリをビルドします。
*   **`c-shared`**: C言語の共有ライブラリをビルドします。

このコミットは、特に `shared` モードに関連する問題に対処しています。

### 共有ライブラリ (Shared Libraries) の概念

共有ライブラリは、複数のプログラムで共有されるコードの集合体です。これにより、ディスクスペースの節約、メモリ使用量の削減、およびプログラムのモジュール化が促進されます。Goでは、`-buildmode=shared` を使用してGoパッケージを共有ライブラリとしてビルドできます。これにより、Goのランタイムと複数のGoパッケージが単一の共有ライブラリにまとめられ、他のGoプログラムがそのライブラリにリンクして利用できるようになります。

### Goのパッケージ依存関係の解決

Goのビルドシステムは、`import` ステートメントに基づいてパッケージ間の依存関係を解決します。ビルドプロセス中、`go tool` はこれらの依存関係を解析し、正しい順序でパッケージをコンパイルおよびリンクするためのビルドグラフを構築します。このグラフは、どのパッケージがどのパッケージに依存しているか、そしてそれらをどのようにビルドすべきかを決定します。

### `cmd/go` ツールの役割

`cmd/go` は、Go言語のビルド、テスト、インストール、フォーマットなど、様々な操作を管理する主要なコマンドラインツールです。Goのソースコードを解析し、コンパイラやリンカを呼び出して最終的なバイナリを生成する役割を担っています。`src/cmd/go/build.go` は、このツールのビルド関連のコアロジックを含んでいます。

### `action` および `action1` 関数の役割

`src/cmd/go/build.go` 内の `action` および `action1` 関数は、Goのビルドプロセスにおいて非常に重要です。これらは、特定のパッケージに対して実行すべき「アクション」（コンパイル、インストールなど）を定義し、そのアクションが依存する他のアクション（依存パッケージのビルドなど）を再帰的に決定することで、ビルドグラフを構築します。

*   `action`: パッケージのビルドアクションを決定するエントリポイントの一つ。
*   `action1`: `action` の内部で呼び出され、より詳細なロジック（共有ライブラリの考慮など）を処理します。この関数は、パッケージのビルドモード、依存関係のビルドモード、および共有ライブラリを検索するかどうか (`lookshared`) を引数として取ります。

### `p.Shlib` の意味

`Package` 構造体内の `Shlib` フィールドは、そのパッケージが属する共有ライブラリの名前を保持します。これは、パッケージが共有ライブラリの一部としてビルドされる場合に設定されます。

## 技術的詳細

このコミットの核心的な問題は、`go tool` がパッケージの依存関係を解決する際に、あるパッケージが「どの共有ライブラリに属しているか」という情報と、「どの共有ライブラリにリンクされているか」という情報を混同していた点にあります。

具体的には、`go install -buildmode=shared a b` の例で、`a` が `c` に依存し、`c` が `b` に依存する場合を考えます。
*   `a` と `b` は明示的に共有ライブラリに含められます。
*   `c` は `a` の依存関係として**暗黙的に**同じ共有ライブラリに含められます。
*   `c` が `b` に依存しているため、`go tool` は `c` の依存関係を解決しようとします。
*   このとき、`go tool` は `c` が `b` と同じ共有ライブラリの一部であることを認識できず、`b` を外部の共有ライブラリとして扱おうとするため、依存関係の解決がループしたり、ハングアップしたりしていました。

この問題を解決するために、`action1` 関数に新しい引数 `forShlib string` が追加されました。
*   `forShlib` は、現在処理中のパッケージ `p` が「どの共有ライブラリの一部になる予定か」を示す文字列です。これは、パッケージが明示的に共有ライブラリに含められる場合だけでなく、暗黙的に含められる場合にも設定されます。
*   これにより、`action1` は、パッケージ `p` の依存関係 `p1` を処理する際に、`p1` が `p` と同じ共有ライブラリの一部であるかどうかを正確に判断できるようになります。

新しいロジックでは、以下のケースが考慮されます。
1.  **現在のパッケージ `p` が共有ライブラリの一部である場合 (`forShlib != ""`)**:
    *   依存パッケージ `p1` が明示的に**異なる**共有ライブラリの一部である場合 (`p1.Shlib != "" && p1.Shlib != forShlib`)、`p1` はその異なる共有ライブラリのアクションとして依存関係に追加されます。
    *   それ以外の場合（`p1` が同じ共有ライブラリの一部であるか、まだどの共有ライブラリにも属していない場合）、`p1` は現在の共有ライブラリの一部としてビルドされるアクションとして依存関係に追加されます。この際、`lookshared` は `false` に設定され、`p1` が外部の共有ライブラリとして検索されるのを防ぎます。
2.  **現在のパッケージ `p` が共有ライブラリの一部ではない場合 (`forShlib == ""`)**:
    *   依存パッケージ `p1` が共有ライブラリの一部である場合 (`p1.Shlib != ""`)、`p1` はその共有ライブラリのアクションとして依存関係に追加されます。
    *   それ以外の場合、`p1` は通常のパッケージとしてビルドされるアクションとして依存関係に追加されます。

この変更により、`go tool` はパッケージが「どの共有ライブラリに属しているか」というコンテキストを正確に保持し、依存関係の解決時に誤った外部リンクを試みることを防ぎます。結果として、共有ライブラリビルドモードでのハングアップが解消されます。

    *   **`else` (依存パッケージ `p1` が現在の共有ライブラリの一部であるか、まだどの共有ライブラリにも属していない場合)**:
        *   `p1` は、`p` と同じ共有ライブラリの一部としてビルドされるべきです（暗黙的または明示的に）。
        *   `b.action1(depMode, depMode, p1, false, forShlib)`: `lookshared` を `false` に設定することで、`p1` が外部の共有ライブラリとして検索されるのを防ぎます。`forShlib` をそのまま渡すことで、`p1` が現在の共有ライブラリのコンテキストで処理されることを保証します。

2.  **`else` (現在のパッケージ `p` が共有ライブラリの一部ではない場合)**:
    *   これは、`p` が通常の実行可能ファイルなどのコンテキストでビルドされていることを意味します。
    *   `b.action1(depMode, depMode, p1, buildLinkshared, p1.Shlib)`:
        *   `buildLinkshared` は、グローバルな設定に基づいて共有ライブラリへのリンクを許可するかどうかを決定します。
        *   `p1.Shlib` を `forShlib` として渡すことで、`p1` がもし共有ライブラリの一部であれば、そのコンテキストで処理されるようにします。

この新しいロジックにより、`go tool` は、パッケージが「どの共有ライブラリに属しているか」という情報を正確に追跡し、依存関係の解決時に、同じ共有ライブラリ内のパッケージを外部の共有ライブラリとして誤って扱ってしまう問題を回避できるようになりました。これにより、共有ライブラリビルド時のハングアップが解消され、より堅牢なビルドシステムが実現されました。

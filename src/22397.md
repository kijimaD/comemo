## 元コミット内容

`cmd/internal/obj/x86: implement -shared computation of TLS base`

このコミットは、Goコンパイラのx86アセンブラにおいて、共有ライブラリ（`-shared`）が有効な場合のTLS（Thread Local Storage）ベースアドレスの計算を実装します。以前のコミットでAMD64における共有ライブラリの再有効化パッチの一部がリベース時に失われたため、それを復元し、必要なオフセット値（addend）を`-4`に修正します。また、Gitが新しいケースを誤ったswitch文に配置しないように更新されています。

## 変更の背景

Go言語は、バージョン1.4から実験的に共有ライブラリのサポートを開始しました。特に、GoプログラムをC/C++などの他の言語とリンクして単一の実行ファイルを生成する際に、共有ライブラリとしてGoコードをビルドする機能は重要です。このコミットは、その共有ライブラリサポート、特にAMD64アーキテクチャにおけるTLS（Thread Local Storage）の取り扱いに関するものです。

TLSは、各スレッドが独自のデータを持つことを可能にするメカニズムです。Goランタイムでは、`g`（goroutine構造体）や`m`（machine構造体）といった重要なランタイムデータがTLSを通じてアクセスされることがあります。共有ライブラリとしてビルドされたGoコードがこれらのTLS変数に正しくアクセスするためには、TLSベースアドレスの計算と、それに関連するリロケーション（再配置）処理が正確に行われる必要があります。

コミットメッセージによると、以前の「AMD64で`-shared`を再有効化する」パッチの一部が、リベース作業中に誤って失われていたとのことです。この失われた部分が、Linux環境におけるTLSベースアドレスの計算ロジックであり、このコミットはその失われた部分を復元し、さらにオフセット値（addend）の修正も行っています。オフセット値の修正は、TLS変数へのアクセスが正しく行われるために不可欠な調整です。

## 前提知識の解説

### 1. Goコンパイラとアセンブラ (`cmd/internal/obj/x86`)

Goコンパイラは、Goのソースコードを機械語に変換するツールチェーンの一部です。`cmd/internal/obj`パッケージは、Goのツールチェーン内部で使用されるオブジェクトファイル生成のための共通コードを提供します。その中の`x86`サブパッケージは、x86およびx86-64アーキテクチャ向けのアセンブラコード生成を担当します。Goのコンパイラは、最終的な機械語を生成する前に、中間表現からアセンブリコードを生成し、それをオブジェクトファイルに変換します。このプロセスにおいて、TLSのような特殊なメモリ領域へのアクセスは、アーキテクチャ固有の命令とリロケーション情報としてエンコードされます。

### 2. 共有ライブラリ (`-shared`フラグ)

共有ライブラリ（Shared Libraries、またはDynamic Link Libraries: DLLs on Windows, .so files on Linux, .dylib files on macOS）は、複数のプログラムで共有されるコードとデータを含むファイルです。これにより、ディスクスペースの節約、メモリ使用量の削減、プログラムのモジュール化が可能になります。Goコンパイラで`-shared`フラグを使用してビルドすると、Goパッケージが共有ライブラリとしてコンパイルされ、他のプログラムからリンクできるようになります。

### 3. TLS (Thread Local Storage)

TLSは、マルチスレッドプログラミングにおいて、各スレッドが自分専用のグローバル変数を持つためのメカニズムです。通常、グローバル変数はすべてのスレッドで共有されますが、TLS変数は各スレッドが独立したコピーを持ちます。Goランタイムでは、現在のgoroutineの状態やスタックポインタなどの情報がTLSに格納されることがあります。これにより、高速なアクセスが可能になります。

### 4. リロケーション (Relocation)

リロケーションとは、コンパイル時にアドレスが確定できないシンボル（変数や関数など）について、リンケージ時に実際のアドレスを解決し、機械語コード内の参照を修正するプロセスです。共有ライブラリでは、コードがメモリ上のどこにロードされるか実行時まで分からないため、特に重要になります。

### 5. `R_TLS_IE` リロケーションタイプ

`R_TLS_IE` (Thread Local Storage Initial Executable) は、ELF (Executable and Linkable Format) 形式の実行ファイルや共有ライブラリで使用されるリロケーションタイプの一つです。これは、TLS変数が初期実行可能ファイル（メインプログラム）の一部として定義されている場合に、共有ライブラリからそのTLS変数にアクセスするために使用されます。このリロケーションタイプは、TLS変数のアドレスを間接的に取得するためのコードパターン（通常はGOT/PLTを介したアクセス）を生成するようにリンカに指示します。

### 6. `g@gottpoff(%rip)`

これは、x86-64アーキテクチャにおけるアセンブリの記法です。
- `g`: アクセスしようとしているTLS変数（Goランタイムの`g`構造体）。
- `gottpoff`: GOT (Global Offset Table) を介してTLS変数のオフセットを取得することを示します。GOTは、共有ライブラリが外部シンボルにアクセスするためのアドレスを格納するテーブルです。
- `(%rip)`: RIP (Instruction Pointer) 相対アドレッシングを示します。x86-64では、命令ポインタからの相対オフセットでメモリにアクセスすることが一般的です。

この命令は、`g`のTLSオフセットをGOTから取得し、それを`%rip`からの相対アドレスとして使用して、最終的にTLSベースアドレスからの`g`のアドレスを計算します。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/x86/asm6.go`内の`doasm`関数におけるTLSベースアドレスの計算ロジックの追加です。具体的には、`obj.Hlinux`（Linuxヘッダタイプ）かつ`ctxt.Flag_shared == 1`（共有ライブラリビルド）の場合の処理が追加されています。

Goのコンパイラは、`MOV TLS, R_to`のような擬似命令を生成することがあります。これは、TLSベースアドレスをレジスタ`R_to`にロードするという意味です。しかし、共有ライブラリ環境では、TLSベースアドレスは直接ロードできるものではなく、リロケーションメカニズムを介して間接的に取得する必要があります。

追加されたコードは、この`MOV TLS, R_to`命令を、共有ライブラリ環境で正しく機能するx86-64の機械語命令に変換します。

1.  **`ctxt.Rexflag = Pw | (regrex[p.To.Reg] & Rxr)`**: REXプレフィックスを設定します。REXプレフィックスは、x86-64アーキテクチャで8ビット以上のレジスタや新しいアドレッシングモードを使用するために必要です。`Pw`は64ビットオペランドサイズ、`R_to`レジスタに応じた`Rxr`ビットを設定します。
2.  **`ctxt.Andptr[0] = 0x8B`**: `MOV`命令のオペコードの最初のバイトを設定します。`0x8B`は、レジスタにメモリの内容を移動する命令のオペコードの一部です。
3.  **`ctxt.Andptr[0] = byte(0x05 | (reg[p.To.Reg] << 3))`**: `MOV`命令のModR/Mバイトを設定します。`0x05`はRIP相対アドレッシングを示し、`reg[p.To.Reg] << 3`はターゲットレジスタ（`R_to`）を指定します。これにより、`movq 0(%rip), R_to`という形式の命令が生成されます。
4.  **`r = obj.Addrel(ctxt.Cursym)`**: リロケーションエントリを現在のシンボルに追加します。
5.  **`r.Off = int32(p.Pc + int64(-cap(ctxt.Andptr)+cap(ctxt.And[:])))`**: リロケーションのオフセットを設定します。これは、リロケーションが必要な命令内の正確な位置を示します。
6.  **`r.Type = obj.R_TLS_IE`**: リロケーションタイプを`R_TLS_IE`に設定します。これはリンカに対し、このオフセットがTLS初期実行可能モデルのリロケーションであることを伝えます。
7.  **`r.Siz = 4`**: リロケーションのサイズを4バイトに設定します。これは、リロケーションが適用されるオフセット値が4バイトであることを意味します。
8.  **`r.Add = -4`**: リロケーションの加算値（addend）を`-4`に設定します。この値は、リロケーションの計算時に最終アドレスに加算されるオフセットです。コミットメッセージで「fixes the addend to be the necessary -4」とあるのはこの部分です。この`-4`という値は、`movq 0(%rip), R_to`命令のオペランドが命令の終わりから4バイト手前にあるため、RIP相対アドレッシングで正しいオフセットを指すために必要となります。
9.  **`put4(ctxt, 0)`**: 命令のオペランドとして0を書き込みます。この0は、リンカによって`R_TLS_IE`リロケーションに基づいて実際のオフセットに置き換えられます。

この一連の処理により、Goの共有ライブラリがLinux/AMD64環境でTLS変数（特に`g`）にアクセスする際に、正しい機械語命令とリロケーション情報が生成されるようになります。これにより、Goの共有ライブラリが他の言語のコードと連携してTLS変数にアクセスする際の互換性と正確性が向上します。

## コアとなるコードの解説

追加された`case obj.Hlinux:`ブロックは、GoコンパイラがLinux上で共有ライブラリをビルドする際に、TLSベースアドレスを扱うための特殊な処理を定義しています。

1.  **`if ctxt.Flag_shared == 0 { ... }`**:
    このチェックは、`-shared`フラグが有効でない（つまり、共有ライブラリとしてビルドされていない）にもかかわらず、Linux環境でTLSベースアドレスの計算が要求された場合にエラーを発生させます。これは、この特定のTLSベースアドレス計算ロジックが共有ライブラリビルドに特化しているためです。

2.  **コメントブロック**:
    このコメントは、このコードが他のケース（例えば、静的リンクされたバイナリ）とは異なる命令を生成することを示しています。
    -   通常の`MOV TLS, R_to`という擬似命令が、共有ライブラリでは`movq g@gottpoff(%rip), R_to`という形式の命令に変換されることを説明しています。
    -   この命令はさらに、`movq 0(%rip), R_to`という機械語命令と、`R_TLS_IE`というリロケーション情報としてエンコードされます。
    -   この処理は、アクセスされるTLS変数が`g`（goroutine構造体）であることを前提としていますが、そのチェックはここでは行われず、後続のアセンブル段階で行われることが示唆されています。

3.  **`ctxt.Rexflag = Pw | (regrex[p.To.Reg] & Rxr)`**:
    x86-64アーキテクチャの命令に必要なREXプレフィックスを設定します。`Pw`は64ビットオペランドサイズを示し、`regrex[p.To.Reg] & Rxr`はターゲットレジスタ（`p.To.Reg`）に応じてREX.Rビットを設定し、レジスタの拡張アドレッシングを可能にします。

4.  **`ctxt.Andptr[0] = 0x8B`** と **`ctxt.Andptr[0] = byte(0x05 | (reg[p.To.Reg] << 3))`**:
    これらは、`movq 0(%rip), R_to`命令のオペコードとModR/Mバイトを生成します。
    -   `0x8B`は`MOV`命令のオペコードの一部です。
    -   `0x05`はModR/Mバイトの一部で、RIP相対アドレッシングを示します。
    -   `reg[p.To.Reg] << 3`は、ターゲットレジスタ（`R_to`）をModR/Mバイトのレジスタフィールドにエンコードします。
    `ctxt.Andptr`は、生成される機械語命令のバイト列を格納するためのバッファです。`ctxt.Andptr = ctxt.Andptr[1:]`は、バイトを書き込んだ後にポインタを進める操作です。

5.  **`r := obj.Addrel(ctxt.Cursym)`**:
    現在のシンボル（関数やデータなど）に関連付けられたリロケーションエントリを新しく作成します。

6.  **`r.Off = int32(p.Pc + int64(-cap(ctxt.Andptr)+cap(ctxt.And[:])))`**:
    リロケーションが適用される命令内のオフセットを設定します。`p.Pc`は現在のプログラムカウンタ（命令のアドレス）です。`-cap(ctxt.Andptr)+cap(ctxt.And[:])`は、`ctxt.Andptr`バッファの現在の位置から、命令のオペランドが始まる位置までの相対オフセットを計算します。

7.  **`r.Type = obj.R_TLS_IE`**:
    リロケーションタイプを`R_TLS_IE`に設定します。これは、リンカに対して、このリロケーションがTLS初期実行可能モデル（Initial Executable model）に従って解決されるべきであることを伝えます。このモデルでは、TLS変数はメイン実行ファイルの一部として定義され、共有ライブラリからアクセスされます。

8.  **`r.Siz = 4`**:
    リロケーションのサイズを4バイトに設定します。これは、リロケーションが修正するアドレス値が4バイトであることを意味します。

9.  **`r.Add = -4`**:
    リロケーションの加算値（addend）を`-4`に設定します。これは、リンカがリロケーションを解決する際に、計算されたアドレスにこの値を加算することを意味します。`movq 0(%rip), R_to`命令において、`0(%rip)`の`0`は命令の終わりから4バイト手前に位置するため、RIP相対アドレッシングで正しいオフセットを指すためには`-4`の加算が必要になります。

10. **`put4(ctxt, 0)`**:
    命令のオペランドとして4バイトの`0`を書き込みます。この`0`はプレースホルダーであり、リンカが`R_TLS_IE`リロケーションを解決する際に、実際のTLSオフセットに置き換えられます。

このコードブロック全体で、Goコンパイラは、共有ライブラリとしてビルドされたGoプログラムがLinux/AMD64環境でTLS変数に効率的かつ正確にアクセスできるように、必要な機械語命令とリロケーション情報を生成しています。

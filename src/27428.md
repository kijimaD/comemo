## 変更の背景

Goのベンチマークツール (`go test -bench`) は、`-cpu` フラグを使用して複数の `GOMAXPROCS` 値でベンチマークを実行する機能を提供します。この際、各ベンチマークの実行結果は、そのベンチマーク名に `GOMAXPROCS` の値（例: `BenchmarkFoo-8` は8コアで実行されたことを示す）を付加して報告されます。

しかし、このコミットが修正しようとしている問題は、ベンチマーク関数内で `b.Run` を使用してサブベンチマークを定義した場合に発生していました。親ベンチマークが既に `GOMAXPROCS` のサフィックスを持つ名前で実行されているにもかかわらず、そのサブベンチマークが自身の名前を構築する際に、親ベンチマークの名前を誤って継承し、さらに `GOMAXPROCS` サフィックスを再度追加してしまうことがありました。これにより、`BenchmarkParent-8-8` のように `proc-count` が重複してベンチマーク名に現れ、結果の解析を困難にし、混乱を招いていました。

この問題は、Go issue #14964 で報告されており、このコミットはその問題を解決するために作成されました。

## 前提知識の解説

このコミットの理解には、以下のGo言語のベンチマークに関する知識が役立ちます。

*   **Goのベンチマーク (`go test -bench`)**: Goには標準でベンチマーク機能が組み込まれており、`go test -bench=.` のように実行することで、パッケージ内のベンチマーク関数（`BenchmarkXxx` という形式の関数）を実行し、パフォーマンスを測定できます。
*   **`testing` パッケージ**: Goの標準ライブラリ `testing` パッケージは、テストとベンチマークの機能を提供します。ベンチマーク関数は `*testing.B` 型の引数を受け取ります。
*   **`*testing.B`**: ベンチマークのコンテキストを提供する構造体です。`b.N` を使ってループ回数を制御したり、`b.ResetTimer()` でタイマーをリセットしたり、`b.Run()` でサブベンチマークを実行したりします。
*   **`b.Run(name string, f func(b *B))`**: このメソッドを使用すると、ベンチマーク関数内でさらに細かい単位でベンチマークを実行できます。これは「サブベンチマーク」と呼ばれ、テストのサブテストと同様に、階層的なベンチマーク構造を構築するのに役立ちます。
*   **`GOMAXPROCS`**: Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数です。デフォルトでは論理CPUの数に設定されます。`go test -bench -cpu=N` フラグを使用すると、ベンチマークを特定の `GOMAXPROCS` 値で実行し、並行処理のパフォーマンス特性を評価できます。
*   **ベンチマーク名の構造**: `go test -bench` の出力では、ベンチマーク名に `GOMAXPROCS` の値がハイフンで区切られて付加されます（例: `BenchmarkMyFunc-4`）。

## 技術的詳細

問題の核心は、`src/testing/benchmark.go` 内の `processBench` 関数にありました。この関数は、ベンチマークの実行を処理し、特に `b.Run` を介してサブベンチマークが作成される際に、新しい `*testing.B` インスタンスを初期化します。

以前の実装では、新しい `*testing.B` インスタンスの `name` フィールドを初期化する際に、`benchName` という変数が使用されていました。この `benchName` は、親ベンチマークの名前を基に構築されており、既に `GOMAXPROCS` のサフィックスが含まれている可能性がありました。

例えば、`BenchmarkParent` が `GOMAXPROCS=8` で実行されると、`benchName` は `BenchmarkParent-8` のようになることがありました。この `BenchmarkParent-8` のコンテキスト内で `b.Run("SubBenchmark", ...)` が呼び出されると、新しいサブベンチマークの `name` が `benchName` から初期化され、さらに `GOMAXPROCS` サフィックスが追加されることで、`BenchmarkParent-8-SubBenchmark-8` のように `proc-count` が重複してしまっていたのです。

このコミットでは、`name: benchName,` を `name: b.name,` に変更することで、この問題を解決しています。`b.name` は、現在の `*testing.B` インスタンスが保持している、`GOMAXPROCS` サフィックスがまだ付加されていない「純粋な」ベンチマーク名を指します。これにより、サブベンチマークが作成される際に、親ベンチマークの `GOMAXPROCS` サフィックスが誤って継承されることがなくなり、各ベンチマーク名には適切な `GOMAXPROCS` サフィックスが一度だけ付加されるようになります。

## コアとなるコードの解説

変更前のコードでは、新しいベンチマーク（サブベンチマーク）の `name` フィールドを `benchName` という変数で初期化していました。この `benchName` は、`processBench` 関数のスコープ内で、親ベンチマークの名前から派生したものであり、既に `GOMAXPROCS` の情報が含まれている可能性がありました。

変更後のコードでは、`name: b.name,` となっています。ここで `b` は `processBench` 関数に渡された現在の `*testing.B` インスタンスを指します。`b.name` は、その `*testing.B` インスタンスが表すベンチマークの「基本名」であり、`GOMAXPROCS` のサフィックスが付加される前の状態の名前です。

この変更により、サブベンチマークが作成される際に、親ベンチマークの `GOMAXPROCS` サフィックスが誤って新しいベンチマーク名にコピーされることがなくなります。結果として、各ベンチマーク名には、そのベンチマークが実行された `GOMAXPROCS` の値が一度だけ、正しく付加されるようになります。これにより、ベンチマーク結果の出力がより正確で理解しやすくなります。

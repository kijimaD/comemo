## 変更の背景

Goコンパイラの内部では、アセンブリ命令を抽象的に表現するために `Prog` という構造体が使用されています。この `Prog` 構造体には、命令のオペランド（引数）を表す `From`、`To`、そして `From3` といったフィールドが含まれています。

以前のバージョンでは、`From3` はおそらく値型（`Addr` 構造体など）として定義されており、常に有効な `Addr` 構造体が存在することを前提としていました。しかし、何らかの理由（例えば、一部の命令には3番目のオペランドが存在しない場合があり、その表現をより効率的または正確にするため）で `From3` がポインタ型（`*Addr`）に変更されました。

ポインタ型になったことで、`From3` は `nil` 値を取る可能性が生じました。`nil` ポインタのフィールドにアクセスしようとすると、Goランタイムはパニック（実行時エラー）を引き起こします。この変更後、`From3` が `nil` である可能性があるにもかかわらず、既存のコードが `p.From3.Type` や `p.From3.Offset` のように直接フィールドにアクセスしていたため、ビルドが失敗したり、実行時にパニックが発生したりするようになりました。

このコミットは、この「`From3` をポインタにした」という先行する変更によって引き起こされたビルドの破損を修正するために作成されました。

## 前提知識の解説

### Goコンパイラと `cmd/internal/obj` パッケージ

Go言語のコンパイラは、ソースコードを機械語に変換する複雑なプロセスを実行します。このプロセスの一部として、Goコンパイラは中間表現（IR: Intermediate Representation）を使用します。`cmd/internal/obj` パッケージは、この中間表現の一つであり、アセンブリ命令を抽象化した `Prog` 構造体や、そのオペランドを表す `Addr` 構造体などを定義しています。これはGoコンパイラのバックエンドに近い部分で、特定のアセンブリ命令セット（x86、ARM64、PPC64など）に依存しない汎用的な命令表現を提供します。

### `Prog` 構造体

`Prog` 構造体は、単一のアセンブリ命令または擬似命令を表します。主要なフィールドには以下のようなものがあります。

*   `As`: 命令の種類（例: `MOV`, `ADD`, `CALL` など）。
*   `From`, `To`: 命令の主要なオペランド。通常、`From` はソース、`To` はデスティネーションを表します。
*   `From3`: 一部の命令で使用される3番目のオペランド。例えば、3項演算（`ADD R1, R2, R3` のように `R1 = R2 + R3` を意味する）などで使用されることがあります。

### `Addr` 構造体

`Addr` 構造体は、`Prog` 構造体のオペランド（`From`, `To`, `From3`）の詳細を記述します。これには以下のようなフィールドが含まれます。

*   `Type`: オペランドの種類（例: レジスタ、メモリ、即値、シンボルなど）。
*   `Class`: オペランドの分類。
*   `Offset`: メモリ参照の場合のオフセット値や、即値の場合の定数値など。

### ポインタと `nil`

Go言語において、ポインタは変数のメモリアドレスを保持する型です。ポインタは、何も指していない状態を表す `nil` 値を取ることができます。ポインタ型のフィールドにアクセスする前に `nil` チェックを行わないと、プログラムはランタイムパニック（`nil` ポインタ参照）でクラッシュします。

このコミットの背景にある問題は、`From3` が値型からポインタ型に変更されたことで、`nil` の可能性が導入されたにもかかわらず、既存のコードがその変更に対応していなかったことにあります。

## 技術的詳細

このコミットの技術的な解決策は、主に以下の2点に集約されます。

1.  **`nil` チェックの導入**: `Prog` 構造体の `From3` フィールドにアクセスする前に、そのポインタが `nil` でないことを確認する `nil` チェックを追加します。
2.  **ヘルパーメソッドの導入**: `From3` の `Type` や `Offset` といったフィールドに安全にアクセスするためのヘルパーメソッド (`From3Type()`, `From3Offset()`) を `Prog` 構造体に追加します。これらのメソッドは内部で `nil` チェックを行い、`From3` が `nil` の場合は適切なデフォルト値（`obj.TYPE_NONE` や `0`）を返します。これにより、呼び出し元は `nil` チェックを意識することなく `From3` の情報を取得できるようになります。

このアプローチにより、コードの堅牢性が向上し、`From3` が `nil` である場合でもプログラムがクラッシュすることなく、期待される動作（例えば、3番目のオペランドがないことを示す）を継続できるようになります。

`src/cmd/internal/obj/arm64/asm7.go`, `src/cmd/internal/obj/objfile.go`, `src/cmd/internal/obj/ppc64/asm9.go`, `src/cmd/internal/obj/x86/obj6.go` の各ファイルでは、`p.From3.Type` や `p.From3.Offset` のような直接アクセスが、新しく追加されたヘルパーメソッド `p.From3Type()` や `p.From3Offset()` に置き換えられています。

例えば、`src/cmd/internal/obj/arm64/asm7.go` では:
```go
// 変更前
// if p.From3.Type != obj.TYPE_NONE {

// 変更後
if p.From3Type() != obj.TYPE_NONE {
```
このように、直接フィールドにアクセスする代わりに、`nil` 安全なヘルパーメソッドを使用することで、ビルドの破損が修正されています。これは、Goコンパイラの内部コード全体で一貫性のある安全なアクセスパターンを確立するための重要な変更です。

## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおける最適化の継続的な取り組みがあります。Goコンパイラは、ソースコードをSSA形式に変換した後、様々な最適化パスを適用して、より効率的な機械語コードを生成します。論理演算の冗長性を排除することは、これらの最適化の中でも特に重要です。

具体的には、`Fixes #14363` という記述から、この変更がGoのIssue 14363を解決するために行われたことがわかります。このIssueでは、コンパイラが `x & (x & y)` のような自明な論理演算の恒等式を認識し、より単純な形式に書き換えるべきであるという提案がなされていました。このような冗長な演算は、プログラマが意図せず記述してしまう場合や、他の最適化パスの結果として生成される場合があります。これらをコンパイラが自動的に簡略化することで、開発者が意識することなく、より高速なコードが生成されるようになります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（定数伝播、共通部分式除去、デッドコード削除など）を効率的に適用できるようになります。Goコンパイラも、フロントエンドで生成されたAST（Abstract Syntax Tree）をSSA形式に変換し、その上で最適化を行います。

### 2. コンパイラの最適化ルール

コンパイラは、プログラムのセマンティクス（意味）を変えることなく、その性能を向上させるために様々な最適化を行います。これらの最適化は、多くの場合、特定のパターンをより効率的なパターンに「書き換える」というルールベースで行われます。GoコンパイラのSSAバックエンドでは、`*.rules` ファイルにこれらの書き換えルールが記述されており、`go generate` コマンドによって対応するGoコード（`rewrite*.go`）が生成されます。

### 3. 論理演算の恒等式

論理演算には、数学と同様に様々な恒等式が存在します。このコミットで扱われるのは、特に以下の吸収律（Absorption Law）に関連するものです。

*   **AND演算の吸収律**: `A & (A & B) = A & B`
*   **OR演算の吸収律**: `A | (A | B) = A | B`
*   **XOR演算の特性**: `A ^ (A ^ B) = B` (XORは結合法則と交換法則を満たし、`A ^ A = 0` であるため)

これらの恒等式をコンパイラが認識し、適用することで、冗長な演算を削減できます。

### `generic.rules` ファイル

`src/cmd/compile/internal/ssa/gen/generic.rules` は、GoコンパイラのSSA最適化のための書き換えルールを定義するファイルです。このファイルは、特定のSSAオペレーションのパターンを検出し、それをより最適化された形式に変換する方法を記述します。

追加されたルールは、主に以下の形式に従っています。

```
(OpType x (OpType x y)) -> (OpType x y)
```

ここで `OpType` は `And64`, `Or32`, `Xor8` などの論理演算の種類を表し、`x` と `y` はオペランド（変数や式）を表します。

具体的には、以下のパターンが追加されています。

*   **AND演算**:
    *   `(And64 x (And64 x y)) -> (And64 x y)`
    *   `(And64 x (And64 y x)) -> (And64 x y)`
    *   `(And64 (And64 x y) x) -> (And64 x y)`
    *   `(And64 (And64 x y) y) -> (And64 x y)`
    これらは、`x & (x & y)` や `(x & y) & x` のような形式を `x & y` に簡略化するルールです。各ビット幅（8, 16, 32, 64）に対して同様のルールが追加されています。

*   **OR演算**:
    *   `(Or64 x (Or64 x y)) -> (Or64 x y)`
    *   `(Or64 x (Or64 y x)) -> (Or64 x y)`
    *   `(Or64 (Or64 x y) x) -> (Or64 x y)`
    *   `(Or64 (Or64 x y) y) -> (Or64 x y)`
    これらは、`x | (x | y)` や `(x | y) | x` のような形式を `x | y` に簡略化するルールです。各ビット幅に対して同様のルールが追加されています。

*   **XOR演算**:
    *   `(Xor64 x (Xor64 x y)) -> y`
    *   `(Xor64 x (Xor64 y x)) -> y`
    *   `(Xor64 (Xor64 x y) x) -> y`
    *   `(Xor64 (Xor64 x y) y) -> x`
    これらは、`x ^ (x ^ y)` を `y` に、`(x ^ y) ^ y` を `x` に簡略化するルールです。各ビット幅に対して同様のルールが追加されています。

これらのルールは、論理演算の結合法則、交換法則、吸収律といった数学的特性に基づいています。

### `rewritegeneric.go` ファイル

`src/cmd/compile/internal/ssa/rewritegeneric.go` は、`generic.rules` ファイルから `go generate` コマンドによって自動生成されるGoのソースコードです。このファイルには、`generic.rules` で定義された各書き換えルールを実際に適用するための関数が含まれています。

例えば、`And16` のルールに対応するGoコードは、`rewriteValuegeneric_OpAnd16` 関数内に生成されます。この関数は、SSA値 `v` が `And16` オペレーションである場合に、そのオペランドを検査し、ルールに合致すれば `v` をより単純な形式に書き換えます。

生成されるコードは、以下のような構造を持っています。

```go
// match: (And16 x (And16 x y))
// cond:
// result: (And16 x y)
for {
    x := v.Args[0]
    v_1 := v.Args[1]
    if v_1.Op != OpAnd16 {
        break
    }
    if x != v_1.Args[0] {
        break
    }
    y := v_1.Args[1]
    v.reset(OpAnd16)
    v.AddArg(x)
    v.AddArg(y)
    return true
}
```

このコードは、SSAツリーを走査し、`And16` オペレーションの第2引数が別の `And16` オペレーションであり、かつその第1引数が外側の `And16` の第1引数と同じである（つまり `x & (x & y)` のパターン）場合に、`v` を `x & y` に書き換える処理を行っています。

## コアとなるコードの解説

### `generic.rules` の追加ルール

追加されたルールは、論理演算の特性を利用して、冗長な計算を排除することを目的としています。

*   **AND/ORの吸収律**:
    `x & (x & y)` は、`x` と `y` の両方が真である場合にのみ真となります。これは `x & y` と全く同じ意味です。同様に、`x | (x | y)` は `x | y` と同じ意味です。これらのルールは、SSA形式のグラフにおいて、より少ないノードで同じ意味を表現できるようにします。

*   **XORの特性**:
    `x ^ (x ^ y)` は、`x` と `y` のビットを比較し、異なる場合に1を立てる演算です。`x ^ y` の結果と `x` を再度XORすると、`y` が得られます。これは、`A ^ B ^ A = B` というXORの特性に基づいています。このルールは、特に暗号化やハッシュ計算などでXORが多用される場合に、コンパイラがより効率的なコードを生成するのに役立ちます。

これらのルールが適用されることで、コンパイラは以下のような最適化を実現します。

1.  **命令数の削減**: 冗長な論理演算が削除されるため、生成される機械語命令の数が減少します。
2.  **レジスタ使用量の最適化**: 中間結果を保持するためのレジスタが不要になる場合があり、レジスタの競合が減少し、より効率的なレジスタ割り当てが可能になります。
3.  **キャッシュ効率の向上**: コードサイズが小さくなることで、CPUの命令キャッシュの効率が向上する可能性があります。

### `rewritegeneric.go` の生成コード

`rewritegeneric.go` に生成されたコードは、`generic.rules` で定義されたパターンマッチングと書き換えロジックをGo言語で実装したものです。各 `rewriteValuegeneric_Op*` 関数は、特定のSSAオペレーション（例: `OpAnd16`）を処理します。

関数内では、まず現在のSSA値 `v` のオペランド（`v.Args[0]`, `v.Args[1]` など）を検査し、`generic.rules` で定義された「match」パターンに合致するかどうかを確認します。例えば、`x & (x & y)` のパターンを検出するために、`v.Args[1]` が `OpAnd16` であるか、そしてそのオペランドが適切に `x` と `y` に対応しているかを確認します。

パターンに合致した場合、`v.reset(OpType)` を呼び出して現在のSSA値のオペレーションを新しい、より単純なオペレーションに設定し、`v.AddArg()` を使って新しいオペランドを追加します。これにより、SSAグラフが書き換えられ、最適化が適用されます。

この自動生成の仕組みにより、コンパイラの開発者は高レベルなルール記述言語で最適化ルールを定義でき、手動で複雑なGoコードを書く手間を省くことができます。

    if v_1.Op != OpAnd16 {
        break
    }
    if x != v_1.Args[0] {
        break
    }
    y := v_1.Args[1]
    v.reset(OpAnd16)
    v.AddArg(x)
    v.AddArg(y)
    return true
}
```

このコードは、SSAツリーを走査し、`And16` オペレーションの第2引数が別の `And16` オペレーションであり、かつその第1引数が外側の `And16` の第1引数と同じである（つまり `x & (x & y)` のパターン）場合に、`v` を `x & y` に書き換える処理を行っています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、以下の2つのファイルにわたります。

1.  **`src/cmd/compile/internal/ssa/gen/generic.rules`**:
    *   AND, OR, XORの各ビット幅（8, 16, 32, 64）に対する論理演算の恒等式に基づく書き換えルールが多数追加されています。
    *   例えば、`And64 x (And64 x y)` を `And64 x y` に簡略化するルールや、`Xor64 x (Xor64 x y)` を `y` に簡略化するルールなどが追加されています。

2.  **`src/cmd/compile/internal/ssa/rewritegeneric.go`**:
    *   `generic.rules` の変更に対応して、`rewriteValuegeneric_OpAnd16`, `rewriteValuegeneric_OpAnd32`, `rewriteValuegeneric_OpAnd64`, `rewriteValuegeneric_OpAnd8` などの関数内に、新しい書き換えロジックが追加されています。
    *   同様に、`rewriteValuegeneric_OpOr16` から `rewriteValuegeneric_OpOr8`、`rewriteValuegeneric_OpXor16` から `rewriteValuegeneric_OpXor8` までの関数にも、対応する書き換えロジックが追加されています。
    *   これらの変更は、`generic.rules` ファイルの変更に基づいて自動生成されたものです。

## コアとなるコードの解説

### `generic.rules` の追加ルール

追加されたルールは、論理演算の特性を利用して、冗長な計算を排除することを目的としています。

*   **AND/ORの吸収律**:
    `x & (x & y)` は、`x` と `y` の両方が真である場合にのみ真となります。これは `x & y` と全く同じ意味です。同様に、`x | (x | y)` は `x | y` と同じ意味です。これらのルールは、SSA形式のグラフにおいて、より少ないノードで同じ意味を表現できるようにします。

*   **XORの特性**:
    `x ^ (x ^ y)` は、`x` と `y` のビットを比較し、異なる場合に1を立てる演算です。`x ^ y` の結果と `x` を再度XORすると、`y` が得られます。これは、`A ^ B ^ A = B` というXORの特性に基づいています。このルールは、特に暗号化やハッシュ計算などでXORが多用される場合に、コンパイラがより効率的なコードを生成するのに役立ちます。

これらのルールが適用されることで、コンパイラは以下のような最適化を実現します。

1.  **命令数の削減**: 冗長な論理演算が削除されるため、生成される機械語命令の数が減少します。
2.  **レジスタ使用量の最適化**: 中間結果を保持するためのレジスタが不要になる場合があり、レジスタの競合が減少し、より効率的なレジスタ割り当てが可能になります。
3.  **キャッシュ効率の向上**: コードサイズが小さくなることで、CPUの命令キャッシュの効率が向上する可能性があります。

### `rewritegeneric.go` の生成コード

`rewritegeneric.go` に生成されたコードは、`generic.rules` で定義されたパターンマッチングと書き換えロジックをGo言語で実装したものです。各 `rewriteValuegeneric_Op*` 関数は、特定のSSAオペレーション（例: `OpAnd16`）を処理します。

関数内では、まず現在のSSA値 `v` のオペランド（`v.Args[0]`, `v.Args[1]` など）を検査し、`generic.rules` で定義された「match」パターンに合致するかどうかを確認します。例えば、`x & (x & y)` のパターンを検出するために、`v.Args[1]` が `OpAnd16` であるか、そしてそのオペランドが適切に `x` と `y` に対応しているかを確認します。

パターンに合致した場合、`v.reset(OpType)` を呼び出して現在のSSA値のオペレーションを新しい、より単純なオペレーションに設定し、`v.AddArg()` を使って新しいオペランドを追加します。これにより、SSAグラフが書き換えられ、最適化が適用されます。

この自動生成の仕組みにより、コンパイラの開発者は高レベルなルール記述言語で最適化ルールを定義でき、手動で複雑なGoコードを書く手間を省くことができます。

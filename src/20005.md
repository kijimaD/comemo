# [インデックス 20005] ファイルの概要

このコミットは、Go言語の `debug/elf` パッケージにPowerPC 64ビット (PPC64) アーキテクチャのサポートを追加するものです。具体的には、ELF (Executable and Linkable Format) ファイルにおけるPPC64固有のリロケーションタイプを定義し、それらのリロケーションを適用するためのロジックを実装しています。これにより、GoのツールチェインがPPC64アーキテクチャ上で生成されたELFバイナリをより正確に解析・処理できるようになります。

## 変更の背景

Go言語は、様々なアーキテクチャとオペレーティングシステムをサポートすることを目指しています。このコミットが行われた2014年当時、Goはx86、ARMなどの主要なアーキテクチャをサポートしていましたが、PowerPC 64ビットアーキテクチャへの対応はまだ発展途上でした。特に、Goのツールチェインが外部のCライブラリやシステムコールと連携するためには、ELFバイナリの正確な解析とリロケーションの適用が不可欠です。

ELFファイルは、実行可能ファイル、共有ライブラリ、オブジェクトファイルなどの形式を定義する標準的なファイルフォーマットです。これらのファイルには、プログラムが実行時に正しくメモリにロードされ、他のモジュールとリンクされるために必要な「リロケーション」情報が含まれています。リロケーションとは、プログラム内のシンボル参照（変数や関数のアドレスなど）を、ロード時の実際のメモリ位置に合わせて調整するプロセスです。

PPC64アーキテクチャは、その命令セットアーキテクチャ (ISA) とメモリモデルの特性上、x86などとは異なる独自のリロケーションタイプを持っています。Goの `debug/elf` パッケージは、ELFファイルを読み込み、その構造を解析するためのライブラリであり、デバッガやリンカ、その他のツールがELFファイルを扱う際に利用されます。PPC64のELFバイナリを正しく処理するためには、このパッケージがPPC64固有のリロケーションタイプを認識し、適切に処理できる必要がありました。

このコミットは、GoがPPC64アーキテクチャを完全にサポートするための重要なステップの一つとして、`debug/elf` パッケージにPPC64のリロケーション処理能力を追加することを目的としています。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。プログラムのコード、データ、シンボル、リロケーション情報などが構造化されて格納されています。

### リロケーション (Relocation)

リロケーションとは、コンパイル時に未解決だったシンボル参照（例えば、別のファイルで定義された関数やグローバル変数のアドレス）を、プログラムがメモリにロードされる際に実際のメモリ位置に解決するプロセスです。リンカやダイナミックローダがこの処理を行います。ELFファイルには、どの位置のどのシンボル参照を、どのような計算で解決すべきかを示すリロケーションエントリが含まれています。

### PowerPC 64ビット (PPC64) アーキテクチャ

PowerPCはIBMが開発したRISC (Reduced Instruction Set Computer) アーキテクチャです。PPC64は64ビット版のPowerPCであり、サーバーや組み込みシステムなどで利用されています。PPC64は、その命令セットやレジスタの使い方、メモリへのアクセス方法などにおいて、x86やARMとは異なる特性を持っています。これにより、ELFファイルのリロケーションタイプもPPC64固有のものが多数存在します。

### `debug/elf` パッケージ

Go言語の標準ライブラリに含まれる `debug/elf` パッケージは、ELFファイルを解析するためのGo言語のAPIを提供します。このパッケージは、ELFヘッダ、セクションヘッダ、プログラムヘッダ、シンボルテーブル、リロケーションテーブルなどを読み込み、Goの構造体として表現します。デバッガやプロファイラ、リンカなどのツールがELFファイルを扱う際にこのパッケージを利用します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッグを可能にするためのデバッグ情報フォーマットです。ELFファイル内にデバッグ情報セクションとして格納されることが多く、変数名、型情報、ソースコードの行番号と実行可能コードのアドレスのマッピングなどが含まれます。デバッガはDWARF情報を用いて、実行中のプログラムの状態をソースコードレベルで表示したり、ブレークポイントを設定したりします。

## 技術的詳細

このコミットの主要な技術的変更点は、PPC64アーキテクチャにおけるELFリロケーションのサポートです。

1.  **PPC64リロケーションタイプの定義**:
    `src/pkg/debug/elf/elf.go` に `R_PPC64` という新しい型が追加され、PPC64アーキテクチャで利用される多数のリロケーションタイプが定数として定義されています。これには、アドレス関連 (`R_PPC64_ADDR32`, `R_PPC64_ADDR64` など)、相対アドレス関連 (`R_PPC64_REL24`, `R_PPC64_REL64` など)、GOT (Global Offset Table) 関連 (`R_PPC64_GOT16` など)、TOC (Table Of Contents) 関連 (`R_PPC64_TOC16` など)、TLS (Thread Local Storage) 関連 (`R_PPC64_TPREL16` など) など、PPC64特有の様々なリロケーションが含まれます。これらの定義は、ELF仕様書におけるPPC64リロケーションの標準に準拠しています。

2.  **PPC64リロケーション適用ロジックの実装**:
    `src/pkg/debug/elf/file.go` に `applyRelocationsPPC64` という新しい関数が追加されました。この関数は、PPC64のELFバイナリから読み込んだリロケーションエントリ (`Rela64` 構造体) を解析し、指定されたメモリ領域 (`dst` バイトスライス) にリロケーションを適用します。
    現在の実装では、`R_PPC64_ADDR64` と `R_PPC64_ADDR32` の2つのリロケーションタイプのみが処理されています。これらはそれぞれ、64ビットおよび32ビットのアドレスを直接書き込むリロケーションです。他のリロケーションタイプについては、コメントで「We don't handle non-section relocations for now.」とあり、今後の拡張が示唆されています。これは、GoのツールチェインがPPC64上で生成するバイナリや、Goが解析する必要があるPPC64バイナリの初期段階での要件を満たすための最小限の実装と考えられます。

3.  **DWARFリロケーションのPPC64対応**:
    `src/pkg/debug/elf/file.go` の `DWARF()` メソッド内で、`.rela.debug_info` セクションのリロケーションを処理する際に、既存の `EM_X86_64` に加えて `f.Machine == EM_PPC64` が条件に追加されました。これは、PPC64のELFファイルにおいても、デバッグ情報セクションがリロケーションを必要とする場合に、そのリロケーションが正しく適用されるようにするための変更です。これにより、PPC64環境でのデバッグ情報の正確な解釈が可能になります。

4.  **テストケースの追加**:
    `src/pkg/debug/elf/file_test.go` に、新しいテストデータファイル `testdata/go-relocation-test-gcc482-ppc64le.obj` を使用するリロケーションテストが追加されました。このテストは、PPC64LE (Little Endian) 環境でGCC 4.8.2によってコンパイルされたオブジェクトファイルのリロケーションが正しく処理されることを検証します。具体的には、DWARFデバッグ情報内の `CompileUnit` エントリの `AttrProducer` や `AttrName` などのフィールドが期待通りに読み取れるかを確認しています。これは、PPC64のリロケーション処理が、デバッグ情報の読み込みに影響を与えないことを保証するためにも重要です。

		return f.applyRelocationsPPC64(dst, rels)

func (f *File) applyRelocationsPPC64(dst []byte, rels []byte) error {
	// 24 is the size of Rela64.
	if len(rels)%24 != 0 {
		return errors.New("length of relocation section is not a multiple of 24")
	}

	symbols, _, err := f.getSymbols(SHT_SYMTAB)
	if err != nil {
		return err
	}

	b := bytes.NewReader(rels)
	var rela Rela64

	for b.Len() > 0 {
		binary.Read(b, f.ByteOrder, &rela)
		symNo := rela.Info >> 32
		t := R_PPC64(rela.Info & 0xffff)

		if symNo == 0 || symNo > uint64(len(symbols)) {
			continue
		}
		sym := &symbols[symNo-1]
		if SymType(sym.Info&0xf) != STT_SECTION {
			// We don't handle non-section relocations for now.
			continue
		}

		switch t {
		case R_PPC64_ADDR64:
			if rela.Off+8 >= uint64(len(dst)) || rela.Addend < 0 {
				continue
			}
			f.ByteOrder.PutUint64(dst[rela.Off:rela.Off+8], uint64(rela.Addend))
		case R_PPC64_ADDR32:
			if rela.Off+4 >= uint64(len(dst)) || rela.Addend < 0 {
				continue
			}
			f.ByteOrder.PutUint32(dst[rela.Off:rela.Off+4], uint32(rela.Addend))
		}
	}

	return nil
}

func (f *File) DWARF() (*dwarf.Data, error) {

	if rela != nil && rela.Type == SHT_RELA && (f.Machine == EM_X86_64 || f.Machine == EM_PPC64) {

	}

## コアとなるコードの解説

### `src/pkg/debug/elf/elf.go` の変更

このファイルでは、PPC64アーキテクチャに特化したリロケーションタイプが `R_PPC64` という新しい列挙型として定義されています。各定数は、PPC64のELF仕様で定められた特定のリロケーション操作に対応する数値を持っています。例えば、`R_PPC64_ADDR32` は32ビットアドレスのリロケーション、`R_PPC64_ADDR64` は64ビットアドレスのリロケーションを示します。
`rppc64Strings` は、これらの数値と対応する文字列名をマッピングするためのテーブルであり、`String()` メソッドと `GoString()` メソッドは、リロケーションタイプを人間が読める形式で表現するために使用されます。これにより、デバッグやエラーメッセージの出力時にリロケーションタイプを識別しやすくなります。

### `src/pkg/debug/elf/file.go` の変更

1.  **`applyRelocations` 関数の拡張**:
    `applyRelocations` 関数は、ELFファイルのクラス (32ビットまたは64ビット) とマシンアーキテクチャに基づいて、適切なリロケーション適用関数を呼び出すディスパッチャの役割を担っています。このコミットでは、`f.Class == ELFCLASS64 && f.Machine == EM_PPC64` という条件が追加され、PPC64の64ビットELFファイルの場合に新しく追加された `applyRelocationsPPC64` 関数が呼び出されるようになりました。

2.  **`applyRelocationsPPC64` 関数の新規追加**:
    この関数は、PPC64のELFファイルにおけるリロケーションを実際に適用するロジックを含んでいます。
    *   まず、リロケーションセクションのバイト列 (`rels`) の長さが `Rela64` 構造体のサイズ (24バイト) の倍数であることを確認します。これは、リロケーションエントリが固定長であることを前提としたチェックです。
    *   次に、ELFファイルのシンボルテーブルを取得します。リロケーションは通常、シンボルを参照して行われるため、シンボル情報が必要です。
    *   `rels` バイト列を `bytes.NewReader` でラップし、`binary.Read` を使って `Rela64` 構造体を一つずつ読み込みます。`Rela64` 構造体には、リロケーションを適用するオフセット (`Off`)、リロケーションタイプとシンボルインデックスを含む情報 (`Info`)、および加算値 (`Addend`) が含まれます。
    *   `rela.Info` からシンボル番号 (`symNo`) とリロケーションタイプ (`t`) を抽出します。
    *   現在の実装では、シンボルがセクションタイプ (`STT_SECTION`) であるリロケーションのみを処理します。これは、セクション内のオフセットに対するリロケーションを対象としていることを意味します。
    *   `switch t` 文でリロケーションタイプを判定し、対応する処理を行います。現時点では `R_PPC64_ADDR64` と `R_PPC64_ADDR32` のみが実装されており、それぞれ `dst` バイトスライス内の指定されたオフセットに `rela.Addend` の値を64ビットまたは32ビットの整数として書き込みます。これは、絶対アドレスを直接埋め込むタイプのリロケーションです。

3.  **`DWARF()` 関数の変更**:
    `DWARF()` 関数は、ELFファイルからDWARFデバッグ情報を読み込む際に、`.rela.debug_info` セクションのリロケーションを処理します。このコミットでは、`f.Machine == EM_PPC64` が条件に追加されたことで、PPC64のELFファイルでもデバッグ情報のリロケーションが正しく適用されるようになり、デバッガがPPC64バイナリのデバッグ情報を正確に解釈できるようになります。

### `src/pkg/debug/elf/file_test.go` の変更

このファイルには、PPC64LE環境でGCCによってコンパイルされたオブジェクトファイル (`testdata/go-relocation-test-gcc482-ppc64le.obj`) を用いた新しいテストケースが追加されました。このテストは、`debug/elf` パッケージがPPC64のELFファイルを正しく解析し、特にDWARFデバッグ情報が期待通りに読み取れることを検証します。これにより、PPC64サポートの正確性と信頼性が保証されます。

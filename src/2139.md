## 変更の背景

Go言語のリンカー（当時は`6l`として知られ、現在は`cmd/ld`の一部）は、コンパイルされたGoパッケージとその依存関係を単一の実行可能バイナリに結合する役割を担っています。このプロセスにおいて、バイナリのサイズを最適化するために「デッドコード削除（Dead Code Elimination, DCE）」が行われます。デッドコードとは、プログラムの実行中に決して到達しない、または使用されないコードのことです。

このコミット以前のリンカーには、デッドコード削除のメカニズムに不完全な点がありました。具体的には、リンカーは到達不能なコードの「シンボル」（名前や参照）をバイナリから削除していましたが、そのシンボルが指す実際の「コード本体」はバイナリ内に残ったままでした。これは、リンカーが内部的にコードのリストを管理する方法に起因していました。`firstp`というリストを編集しても、`follow`という別の処理が`textp`という別のリストからコードの情報を再構築してしまうため、`firstp`への変更が最終的なバイナリに反映されなかったのです。結果として、バイナリサイズが不必要に大きくなるという問題がありました。

この問題は、特に小さなプログラム、例えば`fmt.Printf("hello, world\n")`のような単純なプログラムでも顕著に現れ、バイナリサイズが最適化されていない状態でした。開発者は、この非効率性を解消し、生成されるGoバイナリのフットプリントを削減する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goリンカー (`6l`/`cmd/ld`)**: Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。Goのリンカーは、C/C++のリンカーとは異なり、ガベージコレクションやランタイムのサポートなど、Go特有の機能も組み込みます。`6l`は、x86-64アーキテクチャ向けのリンカーを指す古い名称です。
*   **デッドコード削除 (Dead Code Elimination, DCE)**: コンパイラやリンカーが行う最適化の一種で、プログラムの実行に影響を与えないコード（到達不能なコードや未使用の変数など）を特定し、最終的なバイナリから削除するプロセスです。これにより、バイナリサイズが削減され、ロード時間やメモリ使用量が改善されます。
*   **シンボル (Symbol)**: プログラム内の関数、変数、型などの名前と、それらがメモリ上でどこに配置されているかを示す情報（アドレスなど）を関連付けるものです。リンカーはシンボルテーブルを使用して、異なるオブジェクトファイル間の参照を解決します。
*   **`Prog` (Program Instruction)**: Goリンカーの内部表現における、個々の機械語命令や擬似命令を表す構造体です。リンカーはプログラム全体を`Prog`のリストとして扱います。
*   **`Sym` (Symbol Structure)**: リンカーが扱うシンボルに関する情報を保持する内部構造体です。これにはシンボルの名前、型、アドレスなどが含まれます。
*   **`textp`**: リンカーの内部で、実行可能コード（テキストセグメント）を構成する`Prog`（命令）のリストを管理するためのポインタまたはリストのヘッドです。これは、プログラム内のすべての関数やコードブロックの命令を含みます。
*   **`firstp`**: `textp`と同様に`Prog`のリストを指すポインタですが、コミットメッセージによると、`follow`という処理によって`textp`から再構築される性質を持っていました。これは、リンカーの異なるフェーズでコードのリストを表現するための異なるビューであった可能性があります。
*   **`datap`**: 初期化されたデータセグメントを構成する`Prog`のリストを管理するためのポインタです。
*   **`sweeplist`**: リンカーの内部関数で、デッドコード削除の「スイープ」フェーズを担当します。この関数は、到達不能とマークされた`Prog`や`Sym`をリストから削除する役割を担います。
*   **`deadcode`**: デッドコード削除の全体的なプロセスを調整する関数です。`sweeplist`を呼び出して、実際にデッドコードを削除します。
*   **`ATEXT`**: `Prog`構造体内の`as`フィールドが取りうる値の一つで、その`Prog`が関数の開始点（テキストセグメントの命令）であることを示します。

## 技術的詳細

このコミットの核心は、Goリンカーがデッドコードを処理する方法の根本的な変更にあります。以前のリンカーは、到達不能なコードのシンボルを`Sxxx`（デッド）とマークすることで削除しようとしていました。しかし、実際のコード命令（`Prog`構造体で表現される）のリストである`textp`が適切に再構築されていなかったため、シンボルが削除されても、そのコード本体はバイナリに残ってしまっていました。

問題の根源は、リンカーの内部処理における`firstp`と`textp`の関係にありました。コミットメッセージが示唆するように、`firstp`リストを直接編集しても、`follow`という処理が`textp`リストを基に`firstp`を再構築してしまうため、デッドコードの削除が永続化されませんでした。つまり、`textp`がコードの真のソースであり、ここからデッドコードを物理的に削除する必要があったのです。

このコミットでは、以下の主要な変更が導入されました。

1.  **`sweeplist`関数の強化**: `sweeplist`は、デッドとマークされた`Prog`をリストから削除するだけでなく、生き残った`ATEXT`（関数）の`Prog`を新しい`textp`リストに再リンクするロジックが追加されました。これにより、`textp`は実際に生きているコードのみを含むように再構築されます。
2.  **`deadcode`関数における`textp`の初期化**: `deadcode`関数内で、`sweeplist`を呼び出す前に`textp`と`etextp`（`textp`リストの末尾を指すポインタ）が明示的に`P`（NULLに相当）に初期化されます。これにより、`sweeplist`が`textp`をゼロから再構築することが保証され、以前のデッドコードの残骸がリストに残ることを防ぎます。
3.  **`ldpkg`関数におけるデータ終端の追加**: `ldpkg`関数でパッケージデータを読み込む際に、`mal(len+1)`で1バイト余分にメモリを確保し、`data[len] = '\0'`でヌル終端文字を追加しています。これは、C言語の文字列としてデータを扱う際の安全性を高めるための一般的なプラクティスであり、直接的なデッドコード削除とは関係ありませんが、このコミットに含まれるクリーンアップの一部です。

これらの変更により、リンカーはデッドコードのシンボルだけでなく、そのコード本体もバイナリから物理的に削除できるようになりました。結果として、生成される実行可能ファイルのサイズが大幅に削減され、コミットメッセージにあるように`fmt.Printf("hello, world\n")`のバイナリサイズが143945バイトから128650バイトへと減少しました。これは、Goプログラムの配布と実行における効率性を大きく向上させる改善です。

## コアとなるコードの解説

### `sweeplist`関数の変更

`sweeplist`関数は、リンカーがプログラム内の`Prog`（命令）のリストを走査し、デッドとマークされた要素を削除する役割を担います。このコミット以前は、`sweeplist`は主にシンボルを`Sxxx`（デッド）とマークすることに焦点を当てていました。しかし、実際のコード命令のリストである`textp`が適切に更新されていなかったため、コード本体が残存していました。

追加されたコードブロック:
```c
if(p->as == ATEXT) {
    // keeping this function; link into textp list
    if(etextp == P)
        textp = p;
    else
        etextp->pcond = p;
    etextp = p;
    etextp->pcond = P;
}
```
このブロックは、`sweeplist`が処理している現在の`Prog` `p`が`ATEXT`（関数の開始点）であり、かつその関数がデッドコードとして削除されない場合に実行されます。
*   `if(etextp == P)`: `textp`リストがまだ空の場合（最初の生きている関数が見つかった場合）、`textp`のヘッドを現在の`p`に設定します。
*   `else etextp->pcond = p;`: `textp`リストが既に存在する場合、現在の`etextp`（リストの末尾）の`pcond`フィールド（次の`Prog`へのポインタ）を現在の`p`に設定し、リストに`p`を追加します。
*   `etextp = p;`: `etextp`を現在の`p`に更新し、リストの新しい末尾とします。
*   `etextp->pcond = P;`: 新しいリストの末尾である`etextp`の次のポインタを`P`（NULL）に設定し、リストの終端を示します。

このロジックにより、`sweeplist`は生きている関数（`ATEXT`）の`Prog`のみを抽出し、それらで新しい`textp`リストを再構築します。これにより、デッドコードの命令が`textp`リストから物理的に削除されることが保証されます。

### `deadcode`関数の変更

`deadcode`関数は、デッドコード削除プロセス全体をオーケストレーションします。以前は、`sweeplist`を呼び出して`firstp`リストを処理していましたが、`textp`リストの再構築が不十分でした。

追加されたコード:
```c
// remove dead code.
// sweeplist will rebuild the list of functions at textp
textp = P;
etextp = P;

// follow is going to redo the firstp, lastp list
// but update it anyway just to keep things consistent.
sweeplist(&firstp, &lastp);
```
*   `textp = P; etextp = P;`: `sweeplist`を呼び出す前に、`textp`と`etextp`を明示的にNULLに初期化します。これは非常に重要です。これにより、`sweeplist`が`textp`リストをゼロから構築し始めることが保証され、以前のデッドコードの残骸がリストに残ることを防ぎます。
*   `sweeplist(&firstp, &lastp);`: `firstp`と`lastp`（`firstp`リストの末尾）に対して`sweeplist`を呼び出します。この呼び出しの中で、上述の`sweeplist`内の変更が適用され、生きている`ATEXT`の`Prog`が新しい`textp`リストにリンクされます。

この変更により、`deadcode`関数は`textp`リストがデッドコードを含まないように適切に再構築されることを保証し、結果として最終的なバイナリからデッドコードが物理的に削除されるようになります。

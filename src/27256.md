# [インデックス 27256] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるシンボル参照の重複排除に関するものです。具体的には、オブジェクトファイルへのシンボル参照の書き込み時に、既に書き込まれたシンボル参照を再利用することで、生成されるアーカイブファイルのサイズを削減し、リンク時間のわずかな改善を実現します。

## 変更の背景

Goコンパイラは、ソースコードをコンパイルしてオブジェクトファイルを生成し、その後リンカがこれらのオブジェクトファイルを結合して実行可能ファイルを生成します。このプロセスにおいて、プログラム内で参照される様々な要素（関数、変数など）は「シンボル」として扱われます。これらのシンボルへの参照は、オブジェクトファイル内に記録されます。

以前の実装では、同じシンボルが複数回参照される場合、その都度シンボル参照情報がオブジェクトファイルに書き込まれていました。これにより、特に大規模なプロジェクトや多くのパッケージを使用するGoプログラムでは、生成されるアーカイブファイル（`.a`ファイルなど、複数のオブジェクトファイルをまとめたもの）のサイズが不必要に大きくなる傾向がありました。アーカイブファイルのサイズが大きいと、ディスク容量を消費するだけでなく、リンカがファイルを読み込み、処理する時間も増加し、結果としてビルド全体のリンク時間が長くなるという問題がありました。

このコミットは、この非効率性を解消し、アーカイブファイルのサイズを削減し、リンク時間を改善することを目的としています。コミットメッセージに記載されているように、`pkg/linux_amd64`のアーカイブサイズを1.4MB（3.2%）削減し、`LinkCmdGo`のベンチマークで0.65%のリンク時間改善が見られました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **Goコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)**: Goのビルドツールチェーンの主要なコンポーネントです。コンパイラはGoのソースコードを機械語に変換し、オブジェクトファイルを生成します。リンカはこれらのオブジェクトファイルを結合し、必要なライブラリとリンクして実行可能ファイルを生成します。
*   **シンボル (Symbol)**: プログラム内の関数、グローバル変数、型、定数など、名前を持つエンティティを識別するためのものです。コンパイラはこれらのエンティティをシンボルとして管理します。
*   **シンボル参照 (Symbol Reference)**: あるシンボルが別の場所で使われる際に、そのシンボルを指し示す情報です。例えば、関数Aが関数Bを呼び出す場合、関数Aのオブジェクトファイルには関数Bへのシンボル参照が含まれます。
*   **オブジェクトファイル (.o)**: コンパイラによって生成される中間ファイルで、機械語コード、データ、シンボルテーブル、リロケーション情報などが含まれます。
*   **アーカイブファイル (.a)**: 複数のオブジェクトファイルをまとめたライブラリファイルです。Goでは、パッケージをコンパイルすると通常アーカイブファイルが生成されます。
*   **`src/cmd/internal/obj/objfile.go`**: Goコンパイラ内部で使用される、オブジェクトファイルの書き込みに関連するユーティリティ関数が定義されているファイルです。このファイルは、Goのカスタムオブジェクトファイルフォーマットを扱うための低レベルな処理を含んでいます。
*   **`LSym` (Linker Symbol)**: リンカが内部的にシンボルを表現するために使用する構造体です。シンボルの名前、バージョン、タイプ、サイズ、参照インデックス（`RefIdx`）などの情報を含みます。
*   **`RefIdx`**: シンボル参照の一意なインデックスです。このインデックスは、オブジェクトファイル内でシンボル参照を効率的に識別するために使用されます。
*   **`Version`**: Goのシンボルにはバージョン情報が付与されることがあります。これは、異なるGoバージョン間での互換性や、特定の最適化のために使用されることがあります。このコミットでは、バージョン0（非バージョン付き）とバージョン1（バージョン付き）のシンボルを区別して扱っています。
*   **`Biobuf`**: Goコンパイラ内部で使用されるバッファリングされたI/Oライターです。オブジェクトファイルへの書き込みを効率的に行います。
*   **重複排除 (Deduplication)**: 同じデータが複数回出現する場合に、そのデータを一度だけ保存し、他の出現箇所からはその保存されたデータへの参照を用いることで、データ量を削減する技術です。このコミットでは、シンボル参照に対してこの技術を適用しています。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/objfile.go`内の`wrref`関数にシンボル参照の重複排除ロジックを導入した点にあります。`wrref`関数は、`LSym`構造体で表されるシンボルへの参照をオブジェクトファイルに書き込む役割を担っています。

変更前は、`wrref`が呼び出されるたびに、シンボル参照がオブジェクトファイルに書き込まれ、新しい`RefIdx`が割り当てられていました。これにより、同じシンボルが複数回参照されると、その都度新しい参照エントリが作成され、ファイルサイズが増大していました。

変更後は、以下のメカニズムで重複排除が行われます。

1.  **マップの導入**:
    *   `refIdx = make(map[string]int)`: バージョン0（非バージョン付き）のシンボル名とその`RefIdx`をマッピングするためのグローバルマップが導入されました。
    *   `vrefIdx = make(map[string]int)`: バージョン1（バージョン付き）のシンボル名とその`RefIdx`をマッピングするためのグローバルマップが導入されました。
    *   これらのマップは、既に書き込まれたシンボル参照を追跡し、そのインデックスを再利用するために使用されます。

2.  **シンボルバージョンの考慮**:
    *   `wrref`関数内で、書き込もうとしているシンボル`s`の`s.Version`に基づいて、使用するマップ（`refIdx`または`vrefIdx`）が選択されます。これにより、バージョンが異なる同じ名前のシンボルが正しく区別されます。

3.  **既存参照のチェック**:
    *   シンボル`s`の名前をキーとして、選択されたマップから既存の`RefIdx`を検索します。
    *   `idx := m[s.Name]`
    *   もし`idx`が0でなければ（つまり、そのシンボル名に対応する`RefIdx`が既にマップに存在すれば）、その既存の`RefIdx`を現在のシンボル`s`の`s.RefIdx`に設定し、関数を終了します。これにより、重複するシンボル参照の書き込みがスキップされます。
    *   `if idx != 0 { s.RefIdx = idx; return }`

4.  **新規参照の書き込みと記録**:
    *   マップに既存の`RefIdx`が見つからなかった場合、シンボル参照は通常通りオブジェクトファイルに書き込まれます。
    *   `ctxt.RefsWritten++`で新しい`RefIdx`がインクリメントされ、`s.RefIdx`に設定されます。
    *   そして、この新しい`RefIdx`が、シンボル`s`の名前をキーとして対応するマップに記録されます。
    *   `m[s.Name] = ctxt.RefsWritten`

この変更により、同じシンボルへの参照はオブジェクトファイル内で一度だけ物理的に書き込まれ、それ以降の参照は既存の`RefIdx`を再利用する形になります。これにより、オブジェクトファイルの冗長性が排除され、ファイルサイズが削減されます。

## コアとなるコードの解説

変更の中心は`wrref`関数です。

1.  **グローバルマップの宣言**:
    ```go
    var refIdx = make(map[string]int)
    var vrefIdx = make(map[string]int)
    ```
    `wrref`関数の外で、`refIdx`と`vrefIdx`という2つのマップが初期化されています。これらはそれぞれ、バージョン0とバージョン1のシンボル名と、それに対応する`RefIdx`（シンボル参照インデックス）を記憶するために使用されます。これにより、関数呼び出し間で状態を保持し、重複を検出できるようになります。

2.  **シンボルバージョンに基づくマップの選択**:
    ```go
    	var m map[string]int
    	switch s.Version {
    	case 0:
    		m = refIdx
    	case 1:
    		m = vrefIdx
    	default:
    		log.Fatalf("%s: invalid version number %d", s.Name, s.Version)
    	}
    ```
    `wrref`関数が呼び出されると、まず引数として渡された`LSym`構造体`s`の`Version`フィールドをチェックします。`Version`が0であれば`refIdx`マップを、1であれば`vrefIdx`マップを、現在の処理で使用するマップ`m`として選択します。これにより、バージョンが異なる同じ名前のシンボルが混同されることを防ぎます。

3.  **重複のチェックと再利用**:
    ```go
    	idx := m[s.Name]
    	if idx != 0 {
    		s.RefIdx = idx
    		return
    	}
    ```
    選択されたマップ`m`から、現在のシンボル`s`の名前（`s.Name`）をキーとして`RefIdx`を検索します。もし`idx`が0以外の値であれば、それはこのシンボルが既に一度書き込まれており、その`RefIdx`がマップに記録されていることを意味します。この場合、`s.RefIdx`を既存の`idx`に設定し、それ以上オブジェクトファイルにシンボル参照を書き込むことなく関数を終了します。これが重複排除のメカニズムです。

4.  **新規シンボル参照の書き込みとマップへの記録**:
    ```go
    	// ... (既存のシンボル参照書き込みロジック) ...
    	ctxt.RefsWritten++
    	s.RefIdx = ctxt.RefsWritten
    	m[s.Name] = ctxt.RefsWritten
    ```
    もしマップに既存の`RefIdx`が見つからなかった場合（つまり、`idx`が0の場合）、シンボル参照は通常通りオブジェクトファイルに書き込まれます。`ctxt.RefsWritten`は書き込まれた参照の総数を追跡するカウンターで、これがインクリメントされて新しい`RefIdx`が生成されます。この新しい`RefIdx`は`s.RefIdx`に設定されるだけでなく、`m[s.Name] = ctxt.RefsWritten`という行によって、将来の重複チェックのために対応するマップに記録されます。

この一連の変更により、Goコンパイラはオブジェクトファイルにシンボル参照を書き込む際に、既に同じシンボルが書き込まれていないかを効率的にチェックし、重複を避けることができるようになりました。

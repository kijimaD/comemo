# [インデックス 2717] ファイルの概要

このコミットは、Go言語のRPC (Remote Procedure Call) におけるHTTPアクセス方法の改善を目的としています。具体的には、RPC接続にHTTPの`CONNECT`メソッドを使用するように変更し、接続確立前にHTTPレスポンスを待機することで、より堅牢なエラー報告とプロトコルハンドリングを実現しています。これにより、以前発生していたテストのハングアップ問題の解決にも寄与しています。

## 変更の背景

このコミットが行われた背景には、Go言語の初期のRPC実装におけるいくつかの課題がありました。

1.  **HTTP `GET`メソッドの不適切な利用**: 以前のRPC実装では、HTTPの`GET`メソッドを使用してRPC接続を確立しようとしていました。しかし、`GET`メソッドはリソースの取得を目的としたものであり、永続的なトンネル接続を確立するRPCのセマンティクスとは合致しませんでした。特に、RPCサービスへの接続は、特定のパス（例: `/_goRPC_`）へのトンネルを確立するものであり、これはHTTPプロキシが使用する`CONNECT`メソッドの意図と完全に一致します。
2.  **接続確立の信頼性不足**: 以前の実装では、HTTPリクエストを送信した後、すぐにRPCプロトコルが開始されると仮定していました。このため、HTTPレイヤーでのエラーや予期せぬレスポンスが適切に処理されず、RPC接続が不安定になる可能性がありました。特に、HTTPリクエストリーダーのバッファリングが、意図せずRPCプロトコルのバイトを「食べてしまう」ことで、プロトコル同期の問題を引き起こす懸念がありました。
3.  **テストのハングアップ問題**: コミットメッセージに「`gotest sometimes hangs, but not in HTTP.`」や「`gotest -match=Unknown hangs every few runs even in a clean client.`」とあるように、Goのテストスイート（`gotest`）が時折ハングアップする問題が発生していました。このハングアップは直接HTTPに関連するものではないとされていますが、RPC接続の不安定性が間接的に影響を与えていた可能性があります。RPC接続の堅牢性を高めることで、このような不安定な挙動を排除し、システムの全体的な信頼性を向上させることが求められていました。

これらの問題を解決し、GoのRPCメカニズムをより堅牢で標準に準拠したものにするために、この変更が導入されました。

## 前提知識の解説

### 1. HTTP `CONNECT`メソッド

HTTP `CONNECT`メソッドは、主にHTTPプロキシサーバーを介してSSL/TLS接続を確立するために設計されたHTTPリクエストメソッドです。クライアントはプロキシに対して`CONNECT host:port HTTP/1.1`のようなリクエストを送信し、プロキシは指定された`host:port`へのTCP接続を確立します。接続が成功すると、プロキシは`HTTP/1.1 200 Connection Established`のようなレスポンスを返します。このレスポンスを受け取った後、クライアントとサーバー間の通信はプロキシを介して直接トンネルされ、プロキシは以降のデータを変更せずに転送します。

このコミットでは、RPC接続をHTTPプロキシ経由のSSL/TLS接続と同様に、永続的なバイナリデータストリームのトンネルとして扱うために`CONNECT`メソッドのセマンティクスを借用しています。これにより、HTTPレイヤーを介してRPCプロトコルを確立する際の意図が明確になります。

### 2. Go言語のRPC (Remote Procedure Call)

Go言語の標準ライブラリには、`net/rpc`パッケージを通じてRPC機能が提供されています。これは、異なるアドレス空間にあるプログラムが、あたかもローカルな手続きであるかのように、互いの手続き（関数やメソッド）を呼び出すためのメカニズムです。GoのRPCは、エンコーディングに`gob`形式を使用し、TCPやHTTPなどのトランスポート層上で動作します。

初期のGo RPCは、HTTPをトランスポートとして利用する際に、特定のパス（例: `/_goRPC_`）へのHTTPリクエストを送信し、その接続上でRPCプロトコルを多重化する方式を採用していました。このコミットは、そのHTTPトランスポート層のハンドシェイク部分を改善するものです。

### 3. HTTPリクエスト/レスポンスのパース

HTTPプロトコルは、ヘッダーとボディから構成されるテキストベースのメッセージ交換です。クライアントはリクエストを送信し、サーバーはレスポンスを返します。これらのメッセージは、ステータスライン（リクエストの場合はリクエストライン）、ヘッダーフィールド、そしてオプションのメッセージボディから構成されます。

このコミットでは、HTTPレスポンスを正確にパースし、そのステータスコードを確認してからRPCプロトコルに移行するという変更が含まれています。これにより、HTTPレイヤーでのエラー（例: 405 Method Not Allowed）をRPCプロトコルが開始される前に捕捉できるようになります。

## 技術的詳細

このコミットの技術的な変更点は、主に以下の3つのファイルにわたります。

### `src/pkg/http/client.go` の変更

*   **`ReadResponse` 関数の抽出**: 以前は`send`関数内に直接記述されていたHTTPレスポンスのパースロジックが、`ReadResponse`という独立した関数として抽出されました。これにより、コードの再利用性が向上し、`rpc/client.go`からHTTPレスポンスを読み取る際にこの関数を利用できるようになります。
*   **エラーハンドリングの改善**: `send`関数内でHTTPリクエストの書き込みに失敗した場合、`conn.Close()`が明示的に呼び出されるようになりました。また、`ReadResponse`の呼び出しでエラーが発生した場合も同様に接続が閉じられます。これにより、エラー発生時にリソースが適切に解放されるようになります。
*   **`defer`による`conn.Close()`の削除**: 以前は`send`関数の冒頭に`defer func() { if conn != nil { conn.Close() } }()`という記述がありましたが、これは削除されました。代わりに、エラー発生時に明示的に`conn.Close()`を呼び出す形に変更されています。これにより、接続が正常に確立された場合には`conn`が閉じられないことが保証され、RPCプロトコルがその接続を継続して使用できるようになります。

### `src/pkg/rpc/client.go` の変更

*   **`GET`から`CONNECT`への変更**: `DialHTTP`関数内で、RPCサーバーへの接続確立時に送信するHTTPリクエストメソッドが`GET`から`CONNECT`に変更されました。これにより、RPC接続の意図がHTTPプロトコルに沿ったものになります。
    ```go
    // 変更前
    // io.WriteString(conn, "GET " + rpcPath + " HTTP/1.0\\n\\n");
    // 変更後
    io.WriteString(conn, "CONNECT " + rpcPath + " HTTP/1.0\\n\\n");
    ```
*   **HTTPレスポンスの待機と検証**: `CONNECT`リクエストを送信した後、`http.ReadResponse`を呼び出してHTTPレスポンスを読み取り、そのステータスが`"200 Connected to Go RPC"`であることを確認するようになりました。
    ```go
    resp, err := http.ReadResponse(bufio.NewReader(conn));
    if err == nil && resp.Status == connected {
        return NewClient(conn), nil;
    }
    ```
    これにより、RPCプロトコルが開始される前にHTTPレイヤーでのハンドシェイクが成功したことを確認でき、エラー発生時にはRPCクライアントに適切なエラーが返されるようになります。
*   **エラー報告の改善**: 予期せぬHTTPレスポンスが返された場合、`os.ErrorString("unexpected HTTP response: " + resp.Status)`という具体的なエラーメッセージが生成され、`net.OpError`として返されるようになりました。

### `src/pkg/rpc/server.go` の変更

*   **`bufRWC`構造体の削除**: 以前は`serveHTTP`関数内で`bufRWC`というヘルパーストラクトを使用していましたが、これは削除されました。この構造体は`io.Reader`, `io.Writer`, `io.Closer`をラップしていましたが、`Hijack`された`net.Conn`が直接`io.ReadWriteCloser`インターフェースを満たすため、不要になりました。
*   **`rpcPath`と`connected`定数の定義**: RPCパスと成功時のHTTPステータス文字列がグローバル変数として定義されました。
    ```go
    var rpcPath string = "/_goRPC_"
    var connected = "200 Connected to Go RPC"
    ```
*   **`serveHTTP`関数のロジック変更**:
    *   受信したHTTPリクエストのメソッドが`CONNECT`でない場合、`405 Method Not Allowed`レスポンスを返すようになりました。これにより、不正なメソッドでのRPC接続試行を適切に拒否できます。
    *   `c.Hijack()`で取得した`conn`に対して、成功時のHTTPレスポンス`HTTP/1.0 200 Connected to Go RPC\n\n`を明示的に書き込むようになりました。これにより、クライアント側がRPCプロトコルを開始する前に、サーバー側がHTTPハンドシェイクを完了したことを通知します。
    *   その後、`server.serve(conn)`を呼び出し、ハイジャックされた接続上で直接RPCプロトコルを処理するようになります。

これらの変更により、GoのRPCにおけるHTTPトランスポートは、より標準的なHTTPプロキシの`CONNECT`メソッドのセマンティクスに準拠し、接続確立の信頼性とエラー報告の精度が大幅に向上しました。

## コアとなるコードの変更箇所

### `src/pkg/http/client.go`

*   `ReadResponse`関数が新規追加され、HTTPレスポンスのパースロジックがカプセル化されました。

*   エラー発生時の`conn.Close()`の呼び出しが明示的になり、`defer`によるクローズ処理が削除されました。

### `src/pkg/rpc/client.go`

*   `http.ReadResponse`を呼び出してHTTPレスポンスを読み取り、`"200 Connected to Go RPC"`ステータスを検証するロジックが追加されました。
*   エラー発生時の`net.OpError`による詳細なエラー報告が導入されました。

### `src/pkg/rpc/server.go`

*   `bufRWC`構造体が削除されました。
*   `rpcPath`と`connected`グローバル変数が定義されました。
*   `serveHTTP`関数内で、`CONNECT`メソッド以外のリクエストを`405 Method Not Allowed`で拒否するロジックが追加されました。
*   `c.Hijack()`後に、クライアントに`"HTTP/1.0 200 Connected to Go RPC\n\n"`レスポンスを書き込む処理が追加されました。
*   `server.serve`に直接ハイジャックされた`net.Conn`を渡すようになりました。

## コアとなるコードの解説

このコミットの核心は、Go RPCがHTTPをトランスポートとして利用する際のハンドシェイクプロトコルを、より堅牢で標準的なものに再定義した点にあります。

1.  **`CONNECT`メソッドの採用**:
    *   クライアント側 (`rpc/client.go`) は、RPCサービスへの接続要求を`GET /_goRPC_ HTTP/1.0`ではなく、`CONNECT /_goRPC_ HTTP/1.0`として送信します。これは、HTTPプロキシがトンネル接続を確立する際に使用する`CONNECT`メソッドのセマンティクスを借用したものです。これにより、HTTPレイヤーを介して永続的なバイナリストリームを確立するという意図が明確になります。
    *   サーバー側 (`rpc/server.go`) は、`CONNECT`メソッド以外のリクエストを`405 Method Not Allowed`で拒否することで、RPCエンドポイントへの不正なアクセスを防ぎ、プロトコルの厳密性を保証します。

2.  **HTTPレスポンスの明示的な待機と検証**:
    *   クライアント側は`CONNECT`リクエストを送信した後、サーバーからのHTTPレスポンスを明示的に待ち、それが`"200 Connected to Go RPC"`であることを確認します。このステップは、RPCプロトコルが開始される前にHTTPレイヤーでのハンドシェイクが成功したことを保証します。これにより、ネットワークエラー、サーバー側の設定ミス、または不正なリクエストなどによる問題をRPCプロトコルが開始される前に捕捉し、より適切なエラー報告が可能になります。
    *   サーバー側は、`CONNECT`リクエストを受け入れ、接続をハイジャックした後、クライアントに`"HTTP/1.0 200 Connected to Go RPC\n\n"`という成功レスポンスを書き込みます。これは、クライアントがRPCプロトコルを開始しても良いという明確なシグナルとなります。

3.  **プロトコル同期の改善**:
    *   コミットメッセージにある「`keeps the protocol alternating between speakers, so that the buffering in the HTTP request reader cannot accidentally eat some RPC bytes too.`」という記述は、この変更の重要な利点を示しています。以前の実装では、HTTPリクエストのバッファリングがRPCプロトコルの最初のバイトを誤って消費してしまう可能性があり、これがプロトコル同期の問題やハングアップの原因となることがありました。
    *   新しいアプローチでは、HTTPハンドシェイクが完全に完了し、サーバーから`200 Connected`レスポンスが返されるまで、RPCプロトコルは開始されません。これにより、HTTPレイヤーとRPCレイヤーの間の明確な境界が確立され、バッファリングによる意図しないバイト消費が防止され、プロトコルの同期がより信頼性の高いものになります。

これらの変更は、GoのRPCメカニズムの堅牢性、信頼性、およびHTTPプロトコルとの整合性を大幅に向上させるものでした。

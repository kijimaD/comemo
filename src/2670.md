# [インデックス 2670] ファイルの概要

このコミットは、Goコンパイラのコード生成フェーズにおける重要なリファクタリングであり、特に式の評価とステートメントの処理方法を改善しています。主な変更点は、副作用の管理方法をより明示的にするために、グローバル変数 `addtop` および `addtotop` を `Node **init` 引数に置き換えたことです。また、Go言語から削除された古い機能（switch mapとinterface conversion cases）に関連するコードも削除されています。

## 元コミット内容

このコミットは、Goコンパイラの内部処理を整理し、新しいスコープ規則への準備を進めるためのものです。具体的には、以下の変更が含まれます。

*   `walkstate` 関数が `walkstmt` に、`walktype` 関数が `walkexpr` にそれぞれ名称変更されました。また、ステートメント関連の処理が `walkstmt` に集約されました。
*   `walkexpr` および関連する関数に `Node **init` という最終引数が追加されました。これにより、式の評価中に発生する副作用（初期化ステートメントなど）を明示的に `init` リストに追加できるようになり、以前使用されていたグローバル変数 `addtop` および `addtotop` が廃止されました。
*   Go言語から数ヶ月前に削除された `switch map` および `interface conversion cases` に関連するコードが削除されました。

## 変更の背景

このコミットの背景には、Go言語の進化とコンパイラの設計思想の改善があります。

1.  **新しいスコープ規則への準備**: Go言語は開発初期段階であり、言語仕様が活発に進化していました。この「新しいスコープ」とは、おそらく言語のセマンティクスにおける変数や定数の可視性、ライフタイムに関する変更を指しており、コンパイラがこれらの新しい規則を正確に処理できるように内部構造を調整する必要がありました。
2.  **副作用の明示的な管理**: コンパイラがコードを処理する際、式の評価や型チェックの過程で、一時変数の宣言や初期化といった「副作用」が発生することがあります。以前は `addtop` や `addtotop` といったグローバル変数を通じてこれらの副作用が管理されていましたが、これはコードの追跡を困難にし、予期せぬ相互作用を引き起こす可能性がありました。`Node **init` 引数を導入することで、副作用がどのコンテキストで、どの式やステートメントに関連して発生するのかが明確になり、コンパイラの堅牢性と保守性が向上します。これは、コンパイラの設計において、状態の変更を局所化し、明示的に扱うという一般的なベストプラクティスに沿ったものです。
3.  **言語機能の削除とコードベースのクリーンアップ**: Go言語の初期開発では、様々な実験的な機能が試され、その後言語仕様から削除されることがありました。`switch map` と `interface conversion cases` は、おそらくそのような実験的な機能の一部であり、言語から削除された後もコンパイラコードベースに残っていたものをクリーンアップしたものです。これにより、コンパイラは現在の言語仕様のみをサポートするようになり、不要な複雑さが排除されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念とGo言語の初期の特性に関する知識が必要です。

*   **Goコンパイラのフェーズ**: Goコンパイラ（特に `gc`、当時の主要なコンパイラ）は、ソースコードを機械語に変換するために複数のフェーズを経ます。
    *   **構文解析 (Parsing)**: ソースコードを抽象構文木 (AST) に変換します。
    *   **型チェック (Type Checking)**: ASTの各ノードの型を解決し、型の一貫性を検証します。
    *   **中間表現 (IR) への変換**: ASTを、より低レベルで最適化しやすい中間表現に変換します。
    *   **コード生成 (Code Generation)**: IRから最終的な機械語を生成します。
    このコミットは主に型チェックと中間表現への変換フェーズ、特に「walk」と呼ばれるASTトラバーサル処理に関連しています。
*   **AST (Abstract Syntax Tree)**: ソースコードの構造を木構造で表現したものです。コンパイラはASTを走査（walk）しながら、様々な処理を行います。
*   **`Node` 構造体**: Goコンパイラ内部でASTの各要素（式、ステートメント、型など）を表すデータ構造です。`Node` には、その種類 (`op`)、関連する型 (`type`)、子ノード (`left`, `right`, `ninit`, `nbody` など) といった情報が含まれます。
*   **`walk` 関数群**: Goコンパイラでは、ASTを走査して型チェック、最適化、中間コード生成などの処理を行う関数群が「walk」というプレフィックスで命名されていました。
    *   `walkstate` (旧名): ステートメント（文）を処理する関数。
    *   `walktype` (旧名): 式の型を解決し、評価する関数。
*   **副作用 (Side Effects)**: プログラムの実行中に、変数の値の変更、I/O操作、一時オブジェクトの生成など、関数の戻り値以外にプログラムの状態に影響を与える操作を指します。コンパイラの文脈では、式の評価中に発生する一時変数の宣言や初期化などがこれに該当します。
*   **`addtop` / `addtotop` (旧グローバル変数)**: このコミット以前に、Goコンパイラが式の評価中に生成された初期化ステートメントなどの副作用を一時的に保持するために使用していたグローバルなリスト（`Node` のリンクリスト）です。
*   **`Node **init` 引数**: 新しく導入された引数で、副作用として生成された `Node` のリストへのポインタのポインタです。これにより、関数内で生成された副作用を呼び出し元に明示的に「返却」し、呼び出し元がその副作用リストを自身の `ninit` フィールドなどに結合できるようになります。
*   **`switch map` と `interface conversion cases`**: Go言語の初期には、`switch` ステートメントで `map` 型を直接使用したり、インターフェース型を別のインターフェース型に変換する際に特別な `case` 構文があったりした可能性があります。これらは後の言語仕様の変更で削除された機能です。

## 技術的詳細

このコミットの技術的詳細の中心は、GoコンパイラのAST走査ロジックにおける副作用管理のパラダイムシフトです。

以前のコンパイラでは、`walktype` (現在の `walkexpr`) のような式を処理する関数が、式の評価中に発生する初期化ステートメント（例えば、複合リテラルや関数呼び出しの引数評価で一時変数が生成される場合）を、`addtop` というグローバルな `Node` リストに暗黙的に追加していました。その後、`addtotop` 関数がこのグローバルリストの内容を、現在処理中の `Node` の `ninit` フィールドに移動させていました。

このアプローチの問題点は以下の通りです。
1.  **非局所性**: `addtop` がグローバル変数であるため、どの `walk` 関数がいつ `addtop` を変更するのか、またその内容がいつ `ninit` に結合されるのかがコードを追うだけでは分かりにくい。
2.  **推論の困難さ**: 式の評価が副作用を持つかどうか、またその副作用がどこに影響するかを静的に推論するのが難しい。
3.  **エラーの可能性**: グローバル状態の管理は、特に並行処理や複雑なAST変換において、意図しない競合や状態の不整合を引き起こすリスクがあります。

このコミットでは、この問題を解決するために `Node **init` 引数を導入しました。
*   `walkexpr` (旧 `walktype`) や `dodclvar` (変数宣言処理) など、副作用を生成する可能性のある関数は、この `init` 引数を通じて、生成された副作用ノードを呼び出し元に渡します。
*   `init` は `Node` ポインタへのポインタ (`Node **`) であるため、関数内で `*init = list(*init, new_side_effect_node);` のようにすることで、呼び出し元の `Node` リストに直接副作用ノードを追加できます。
*   これにより、副作用の発生源とそれが結合される場所が明確になり、コンパイラのコードパスがより理解しやすくなります。

また、`walkstate` が `walkstmt` に、`walktype` が `walkexpr` に改名されたのは、それぞれの関数が処理する対象（ステートメントと式）をより正確に反映するためです。ステートメントは副作用を持つことが多く、式は値を生成しますが、その評価過程で副作用を持つこともあります。この区別を明確にすることで、コンパイラの構造がより論理的になりました。

`switch map` と `interface conversion cases` の削除は、Go言語の仕様変更に伴うコンパイラの同期です。これらの機能は言語から削除されたため、コンパイラもそれらをサポートする必要がなくなり、関連するコードを削除することでコードベースが簡素化されました。これは、コンパイラが常に最新の言語仕様に準拠していることを保証するための定期的なクリーンアップ作業の一部です。

## コアとなるコードの解説

最も重要な変更は `src/cmd/gc/walk.c` に集中しています。

**`walkexpr(Node *n, int top, Node **init)` 関数**:
この関数は、GoコンパイラのAST走査において、式を評価し、型を解決し、コンパイル時定数を評価する役割を担います。以前の `walktype` との最大の違いは、`Node **init` 引数を受け取るようになった点です。

*   `init` 引数は、この `walkexpr` の呼び出し中に生成された初期化ステートメントなどの副作用ノードを連結するためのリストの先頭へのポインタを指します。
*   関数内で副作用ノード（例: 一時変数の宣言や初期化）が生成されると、`*init = list(*init, new_side_effect_node);` のようにして、このリストにノードが追加されます。
*   これにより、`walkexpr` の呼び出し元は、返された式の `Node` だけでなく、その評価中に発生したすべての副作用も `init` 引数を通じて受け取ることができます。呼び出し元は、これらの副作用を自身の `ninit` フィールドに結合するなどして、適切な位置に挿入します。

**`walkstmt(Node *n)` 関数**:
この関数は、ステートメント（文）を処理します。以前の `walkstate` に相当します。ステートメント自体が副作用を持つことが多いため、`walkstmt` は内部で `walkexpr` を呼び出す際に `Node **init` を利用し、その結果得られた副作用を自身の `ninit` フィールドに結合します。例えば、`OCALL` (関数呼び出し) や `OSEND` (チャネル送信) のようなステートメントは、それ自体が副作用を持つ式であり、その評価中にさらに副作用が発生する可能性があります。

**`addtop` / `addtotop` の削除**:
これらのグローバル変数は、`walkexpr` が副作用を生成するたびにその副作用ノードを一時的に保持するために使用されていました。`Node **init` 引数の導入により、このグローバルな状態が不要になり、削除されました。これにより、コンパイラのコードはより関数型プログラミングに近い、副作用を明示的に扱うスタイルに移行しました。

**例: `dodclvar(Node *n, Type *t, Node **init)`**:
この関数は変数を宣言します。以前は `addtop = list(addtop, nod(ODCL, n, N));` のようにグローバルな `addtop` に宣言ノードを追加していましたが、変更後は `*init = list(*init, nod(ODCL, n, N));` となり、呼び出し元が提供する `init` リストに直接追加するようになりました。

これらの変更により、コンパイラのAST走査ロジックは、副作用の管理に関してよりモジュール化され、予測可能で、デバッグしやすいものになりました。

*   **Goコンパイラのフェーズ**: Goコンパイラ（特に `gc`、当時の主要なコンパイラ）は、ソースコードを機械語に変換するために複数のフェーズを経ます。
    *   **構文解析 (Parsing)**: ソースコードを抽象構文木 (AST) に変換します。
    *   **型チェック (Type Checking)**: ASTの各ノードの型を解決し、型の一貫性を検証します。
    *   **中間表現 (IR) への変換**: ASTを、より低レベルで最適化しやすい中間表現に変換します。
    *   **コード生成 (Code Generation)**: IRから最終的な機械語を生成します。
    このコミットは主に型チェックと中間表現への変換フェーズ、特に「walk」と呼ばれるASTトラバーサル処理に関連しています。
*   **AST (Abstract Syntax Tree)**: ソースコードの構造を木構造で表現したものです。コンパイラはASTを走査（walk）しながら、様々な処理を行います。
*   **`Node` 構造体**: Goコンパイラ内部でASTの各要素（式、ステートメント、型など）を表すデータ構造です。`Node` には、その種類 (`op`)、関連する型 (`type`)、子ノード (`left`, `right`, `ninit`, `nbody` など) といった情報が含まれます。
*   **`walk` 関数群**: Goコンパイラでは、ASTを走査して型チェック、最適化、中間コード生成などの処理を行う関数群が「walk」というプレフィックスで命名されていました。
    *   `walkstate` (旧名): ステートメント（文）を処理する関数。
    *   `walktype` (旧名): 式の型を解決し、評価する関数。
*   **副作用 (Side Effects)**: プログラムの実行中に、変数の値の変更、I/O操作、一時オブジェクトの生成など、関数の戻り値以外にプログラムの状態に影響を与える操作を指します。コンパイラの文脈では、式の評価中に発生する一時変数の宣言や初期化などがこれに該当します。
*   **`addtop` / `addtotop` (旧グローバル変数)**: このコミット以前に、Goコンパイラが式の評価中に生成された初期化ステートメントなどの副作用を一時的に保持するために使用していたグローバルなリスト（`Node` のリンクリスト）です。
*   **`Node **init` 引数**: 新しく導入された引数で、副作用として生成された `Node` のリストへのポインタのポインタです。これにより、関数内で生成された副作用を呼び出し元に明示的に「返却」し、呼び出し元がその副作用リストを自身の `ninit` フィールドなどに結合できるようになります。
*   **`switch map` と `interface conversion cases`**: Go言語の初期には、`switch` ステートメントで `map` 型を直接使用したり、インターフェース型を別のインターフェース型に変換する際に特別な `case` 構文があったりした可能性があります。これらは後の言語仕様の変更で削除された機能です。

## 技術的詳細

このコミットの技術的詳細の中心は、GoコンパイラのAST走査ロジックにおける副作用管理のパラダイムシフトです。

以前のコンパイラでは、`walktype` (現在の `walkexpr`) のような式を処理する関数が、式の評価中に発生する初期化ステートメント（例えば、複合リテラルや関数呼び出しの引数評価で一時変数が生成される場合）を、`addtop` というグローバルな `Node` リストに暗黙的に追加していました。その後、`addtotop` 関数がこのグローバルリストの内容を、現在処理中の `Node` の `ninit` フィールドに移動させていました。

このアプローチの問題点は以下の通りです。
1.  **非局所性**: `addtop` がグローバル変数であるため、どの `walk` 関数がいつ `addtop` を変更するのか、またその内容がいつ `ninit` に結合されるのかがコードを追うだけでは分かりにくい。
2.  **推論の困難さ**: 式の評価が副作用を持つかどうか、またその副作用がどこに影響するかを静的に推論するのが難しい。
3.  **エラーの可能性**: グローバル状態の管理は、特に並行処理や複雑なAST変換において、意図しない競合や状態の不整合を引き起こすリスクがあります。

このコミットでは、この問題を解決するために `Node **init` 引数を導入しました。
*   `init` 引数は `Node` ポインタへのポインタ (`Node **`) であるため、関数内で `*init = list(*init, new_side_effect_node);` のようにすることで、呼び出し元の `Node` リストに直接副作用ノードを追加できます。
*   これにより、`walkexpr` (旧 `walktype`) や `dodclvar` (変数宣言処理) など、副作用を生成する可能性のある関数は、この `init` 引数を通じて、生成された副作用ノードを呼び出し元に渡します。
*   副作用の発生源とそれが結合される場所が明確になり、コンパイラのコードパスがより理解しやすくなります。

また、`walkstate` が `walkstmt` に、`walktype` が `walkexpr` に改名されたのは、それぞれの関数が処理する対象（ステートメントと式）をより正確に反映するためです。ステートメントは副作用を持つことが多く、式は値を生成しますが、その評価過程で副作用を持つこともあります。この区別を明確にすることで、コンパイラの構造がより論理的になりました。

`switch map` と `interface conversion cases` の削除は、Go言語の仕様変更に伴うコンパイラの同期です。これらの機能は言語から削除されたため、コンパイラもそれらをサポートする必要がなくなり、関連するコードを削除することでコードベースが簡素化されました。これは、コンパイラが常に最新の言語仕様に準拠していることを保証するための定期的なクリーンアップ作業の一部です。

    *   `walkexpr` 関数に `Node **init` 引数が追加され、式の評価中に発生する副作用がこの引数を通じて管理されるようになりました。

## コアとなるコードの解説

最も重要な変更は `src/cmd/gc/walk.c` に集中しています。

**`walkexpr(Node *n, int top, Node **init)` 関数**:
この関数は、GoコンパイラのAST走査において、式を評価し、型を解決し、コンパイル時定数を評価する役割を担います。以前の `walktype` との最大の違いは、`Node **init` 引数を受け取るようになった点です。

*   `init` 引数は、この `walkexpr` の呼び出し中に生成された初期化ステートメントなどの副作用ノードを連結するためのリストの先頭へのポインタを指します。
*   関数内で副作用ノード（例: 一時変数の宣言や初期化）が生成されると、`*init = list(*init, new_side_effect_node);` のようにして、このリストにノードが追加されます。
*   これにより、`walkexpr` の呼び出し元は、返された式の `Node` だけでなく、その評価中に発生したすべての副作用も `init` 引数を通じて受け取ることができます。呼び出し元は、これらの副作用を自身の `ninit` フィールドに結合するなどして、適切な位置に挿入します。

**`walkstmt(Node *n)` 関数**:
この関数は、ステートメント（文）を処理します。以前の `walkstate` に相当します。ステートメント自体が副作用を持つことが多いため、`walkstmt` は内部で `walkexpr` を呼び出す際に `Node **init` を利用し、その結果得られた副作用を自身の `ninit` フィールドに結合します。例えば、`OCALL` (関数呼び出し) や `OSEND` (チャネル送信) のようなステートメントは、それ自体が副作用を持つ式であり、その評価中にさらに副作用が発生する可能性があります。

**`addtop` / `addtotop` の削除**:
これらのグローバル変数は、`walkexpr` が副作用を生成するたびにその副作用ノードを一時的に保持するために使用されていました。`Node **init` 引数の導入により、このグローバルな状態が不要になり、削除されました。これにより、コンパイラのコードはより関数型プログラミングに近い、副作用を明示的に扱うスタイルに移行しました。

**例: `dodclvar(Node *n, Type *t, Node **init)`**:
この関数は変数を宣言します。以前は `addtop = list(addtop, nod(ODCL, n, N));` のようにグローバルな `addtop` に宣言ノードを追加していましたが、変更後は `*init = list(*init, nod(ODCL, n, N));` となり、呼び出し元が提供する `init` リストに直接追加するようになりました。

これらの変更により、コンパイラのAST走査ロジックは、副作用の管理に関してよりモジュール化され、予測可能で、デバッグしやすいものになりました。

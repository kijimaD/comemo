# [インデックス 23897] ファイルの概要

このコミットは、Go 1.5におけるベンダーディレクトリの予備的なサポートを追加するものです。具体的には、`GO15VENDOREXPERIMENT=1` 環境変数が設定されている場合に、Go 1.5のベンダー提案に従ってインポートパスの解決方法を変更します。これにより、外部パッケージをソースツリーにベンダー（コピー）する際に、コードの変更なしで利用できるようになります。

## コミット

```
cmd/go: add preliminary support for vendor directories

When GO15VENDOREXPERIMENT=1 is in the environment,
this CL changes the resolution of import paths according to
the Go 1.5 vendor proposal:

        If there is a source directory d/vendor, then,
        when compiling a source file within the subtree rooted at d,
        import "p" is interpreted as import "d/vendor/p" if that exists.

        When there are multiple possible resolutions,
        the most specific (longest) path wins.

        The short form must always be used: no import path can
        contain “/vendor/” explicitly.

        Import comments are ignored in vendored packages.

The goal of these changes is to allow authors to vendor (copy) external
packages into their source trees without any modifications to the code.
This functionality has been archived in tools like godep, nut and gb by
requiring GOPATH manipulation. This alternate directory-based approach
eliminates the need for GOPATH manipulation and in keeping with the
go command's use of directory layout-based configuration.

The flag allows experimentation with these vendoring semantics once
Go 1.5 is released, without forcing them on by default. If the experiment
is deemed a success, the flag will default to true in Go 1.6 and then be
removed in Go 1.7.

For more details, see the original proposal by Keith Rarick at
https://groups.google.com/d/msg/golang-dev/74zjMON9glU/dGhnoi2IMzsJ.

Change-Id: I2c6527e777d14ac6dc43c53e4b3ff24f3279216e
Reviewed-on: https://go-review.googlesource.com/10923
Reviewed-by: Andrew Gerrand <adg@golang.org>
```

## 元コミット内容

`cmd/go: add preliminary support for vendor directories`

このコミットは、Go 1.5におけるベンダーディレクトリの予備的なサポートを追加するものです。`GO15VENDOREXPERIMENT=1` 環境変数が設定されている場合、Go 1.5のベンダー提案に従ってインポートパスの解決方法が変更されます。

主な変更点は以下の通りです。

*   ソースディレクトリ `d` 内に `d/vendor` ディレクトリが存在する場合、`d` のサブツリー内のソースファイルをコンパイルする際、`import "p"` は `d/vendor/p` が存在すればそのように解釈されます。
*   複数の解決策がある場合、最も具体的な（最も長い）パスが優先されます。
*   常に短い形式を使用する必要があり、インポートパスに明示的に `/vendor/` を含めることはできません。
*   ベンダーパッケージ内のインポートコメントは無視されます。

これらの変更の目的は、コードの変更なしに外部パッケージをソースツリーにベンダー（コピー）できるようにすることです。これは `godep`、`nut`、`gb` といったツールが `GOPATH` 操作を必要としていた機能ですが、この代替のディレクトリベースのアプローチは `GOPATH` 操作の必要性を排除し、`go` コマンドのディレクトリレイアウトベースの構成の使用と一致しています。

このフラグは、Go 1.5リリース後にこれらのベンダーセマンティクスを実験的に試すことを可能にし、デフォルトで強制することはありません。実験が成功と見なされた場合、Go 1.6でこのフラグはデフォルトで `true` になり、Go 1.7で削除される予定です。

詳細については、Keith Rarickによる元の提案（[https://groups.google.com/d/msg/golang-dev/74zjMON9glU/dGhnoi2IMzsJ](https://groups.google.com/d/msg/golang-dev/74zjMON9glU/dGhnoi2IMzsJ)）を参照してください。

## 変更の背景

Go言語の初期のバージョンでは、プロジェクトの依存関係管理は主に`GOPATH`に依存していました。これはシンプルである一方で、プロジェクトごとに異なるバージョンのライブラリを使用したい場合や、特定の依存関係をプロジェクト内に固定したい（ベンダーしたい）場合に課題がありました。`GOPATH`の操作は複雑になりがちで、ビルドの再現性やプロジェクトのポータビリティを損なう可能性がありました。

この問題に対処するため、`godep`、`nut`、`gb`といったコミュニティツールが登場し、`GOPATH`を操作することでベンダー依存関係を管理していました。しかし、これらはGoツールチェーンのネイティブな機能ではなく、それぞれ独自のアプローチを取っていました。

このコミットは、Go 1.5のリリースに向けて、Goツールチェーン自体にベンダー依存関係のサポートを組み込むための第一歩です。`vendor`ディレクトリという標準的なメカニズムを導入することで、`GOPATH`の複雑な操作なしに、プロジェクト内で依存関係を自己完結させ、ビルドの再現性と信頼性を向上させることを目指しています。`GO15VENDOREXPERIMENT`という環境変数による実験的な導入は、コミュニティからのフィードバックを収集し、機能の安定性を確保するための慎重なアプローチでした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と背景知識が必要です。

1.  **GOPATH**: Go言語のワークスペースのルートディレクトリを指定する環境変数です。Goのソースコード、コンパイル済みパッケージ、実行可能ファイルがこのディレクトリ構造内に配置されます。Go 1.11以前では、依存関係の解決において非常に重要な役割を果たしていました。
2.  **パッケージ管理と依存関係**: Go言語では、`import`文を使用して他のパッケージをコードに取り込みます。Goのビルドシステムは、`GOPATH`や`GOROOT`（Goのインストールディレクトリ）内のパスを検索して、これらのパッケージを見つけます。
3.  **ベンダー（Vendoring）**: ソフトウェア開発において、プロジェクトが依存する外部ライブラリやパッケージのコピーを、プロジェクト自身のソースコードリポジトリ内に含めるプラクティスを指します。これにより、外部の変更に影響されずに、プロジェクトが特定のバージョンの依存関係でビルドされることを保証し、ビルドの再現性と安定性を高めます。
4.  **Go 1.5**: このバージョンはGo言語にとって重要なリリースであり、ガベージコレクタの改善や、このコミットで導入されたベンダー実験など、多くの変更が含まれていました。
5.  **`go/build` パッケージ**: Goの標準ライブラリの一部で、Goソースコードパッケージの構造を解析し、ビルドプロセスに必要な情報を提供する機能を持っています。このコミットでは、`go/build`パッケージの機能を利用して、`vendor`ディレクトリ内のパッケージを解決しています。

## 技術的詳細

このコミットは、`cmd/go`（`go`コマンドの実装）にベンダーディレクトリのサポートを導入します。その核心は、インポートパスの解決ロジックを変更し、`vendor`ディレクトリを優先的に検索するようにすることです。

1.  **`GO15VENDOREXPERIMENT` フラグ**:
    *   `src/cmd/go/pkg.go` に `go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") == "1"` というグローバル変数が追加されています。この変数が `true` の場合にベンダー機能が有効になります。
    *   これは、Go 1.5ではデフォルトで無効であり、ユーザーが明示的にオプトインすることで実験的に利用できることを意味します。

2.  **インポートパス解決の変更 (`vendoredImportPath` 関数)**:
    *   `src/cmd/go/pkg.go` に `vendoredImportPath` という新しい関数が追加されました。この関数は、親パッケージのディレクトリとインポートパスを受け取り、`vendor`ディレクトリ内の対応するパスを検索します。
    *   検索ロジックは、現在のパッケージのディレクトリから`GOPATH`のルートに向かって階層的に`vendor`ディレクトリを探します。例えば、`d/a/b/c`というディレクトリで`import "p"`が解決される場合、`d/a/b/c/vendor/p`、`d/a/b/vendor/p`、`d/a/vendor/p`、`d/vendor/p`の順に検索されます。
    *   最も具体的な（最も深い階層にある）`vendor`ディレクトリ内のパッケージが優先されます。
    *   `isDir`関数は、ディレクトリの存在をキャッシュしてパフォーマンスを向上させています。

3.  **インポートパスの書き換えとエラー処理**:
    *   `loadImport`関数が変更され、`vendoredImportPath`を呼び出して実際のインポートパスを決定するようになりました。
    *   `go/build`パッケージがパッケージを見つけられなかった場合のエラーメッセージに、検索された`vendor`ディレクトリのパスを追加するロジックが導入されています。これにより、デバッグ時にどの`vendor`ディレクトリが検索されたかをユーザーが把握しやすくなります。
    *   `disallowVendor`および`disallowVendorVisibility`関数が追加され、`vendor`ディレクトリの使用に関する特定の制約（例: インポートパスに明示的に`/vendor/`を含めることの禁止、`vendor`ディレクトリ外からのベンダーパッケージへのアクセス制限）を強制します。

4.  **コンパイラへの `importmap` の伝達**:
    *   `src/cmd/go/build.go` の `gc` 関数（Goコンパイラを呼び出す部分）が変更され、ベンダーされたインポートパスをコンパイラに伝えるために `-importmap` フラグを使用するようになりました。
    *   例えば、`import "p"` が `d/vendor/p` に解決された場合、コンパイラには `-importmap p=d/vendor/p` のように渡され、コンパイラが正しいパッケージを見つけられるようにします。

5.  **テストの追加**:
    *   `src/cmd/go/vendor_test.go` には、ベンダー機能の動作を検証するための広範なテストが追加されています。これには、`go list`、`go run`、`go test` コマンドがベンダーパッケージを正しく処理することを確認するテストや、意図的に不正なインポートパスを使用した場合のエラー処理を検証するテストが含まれます。
    *   `src/cmd/go/testdata/src/vend/` 以下に、ベンダー機能のテストケースとして使用されるサンプルコードが多数追加されています。

この変更により、Goのビルドシステムは、プロジェクトのディレクトリ構造に基づいて依存関係を自動的に解決できるようになり、外部ツールや`GOPATH`の複雑な設定なしにベンダー依存関係を管理する道が開かれました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に`src/cmd/go/pkg.go`ファイルに集中しています。

1.  **`go15VendorExperiment` 変数の追加**:
    ```go
    // The Go 1.5 vendoring experiment is enabled by setting GO15VENDOREXPERIMENT=1.
    // The variable is obnoxiously long so that years from now when people find it in
    // their profiles and wonder what it does, there is some chance that a web search
    // might answer the question.
    var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") == "1"
    ```
    この変数は、ベンダー機能が有効かどうかを制御します。

2.  **`loadImport` 関数のシグネチャ変更とベンダーパス解決の組み込み**:
    ```go
    // 変更前:
    // func loadImport(path string, srcDir string, stk *importStack, importPos []token.Position) *Package {
    // 変更後:
    func loadImport(path, srcDir string, parent *Package, stk *importStack, importPos []token.Position) *Package {
        // ...
        if isLocal {
            importPath = dirToImportPath(filepath.Join(srcDir, path))
        } else {
            path, vendorSearch = vendoredImportPath(parent, path) // ここでベンダーパス解決が呼び出される
            importPath = path

        // ...

    `parent *Package` 引数が追加され、`vendoredImportPath`関数が呼び出されるようになりました。

    func vendoredImportPath(parent *Package, path string) (found string, searched []string) {
        if parent == nil || !go15VendorExperiment {

        // ... 最も具体的なvendor/pathを見つけるロジック ...

    この関数がベンダーパス解決の主要なロジックを実装しています。

    }

    func disallowVendorVisibility(srcDir string, p *Package, stk *importStack) *Package {
        // ... ベンダーパッケージの可視性ルールをチェック ...
    }
    ```
    これらの関数は、ベンダー機能の制約を強制します。

5.  **`src/cmd/go/build.go` における `importmap` の追加**:
    ```go
    for _, path := range p.Imports {
        if i := strings.LastIndex(path, "/vendor/"); i >= 0 {
            gcargs = append(gcargs, "-importmap", path[i+len("/vendor/"):]+"="+path)
        } else if strings.HasPrefix(path, "vendor/") {

        }

    ```
    コンパイラにベンダーパスをマッピングするための引数を追加しています。

## コアとなるコードの解説

このコミットの核心は、Goのビルドシステムがインポートパスを解決する際に、プロジェクト内の`vendor`ディレクトリを自動的に検索し、優先的に使用するメカニズムを導入した点にあります。

*   **`go15VendorExperiment`**: これは、この新機能がGo 1.5では実験的なものであり、ユーザーが明示的に有効にする必要があることを示しています。これにより、既存のプロジェクトへの影響を最小限に抑えつつ、コミュニティからのフィードバックを収集する機会が提供されました。
*   **`vendoredImportPath`**: この関数は、Goのインポート解決ロジックの中心的な拡張です。従来の`GOPATH`ベースの検索に加えて、現在のパッケージのディレクトリから上位のディレクトリに向かって`vendor`ディレクトリを探索します。これにより、プロジェクトのサブディレクトリにベンダーされた依存関係を、通常のインポートパス（例: `import "github.com/foo/bar"`)で参照できるようになります。この階層的な検索と「最も具体的なパスが勝つ」というルールは、複雑なプロジェクト構造やネストされたベンダーディレクトリを持つ場合に、正しい依存関係が解決されることを保証します。
*   **`disallowVendor` と `disallowVendorVisibility`**: これらの関数は、ベンダー機能の健全性を保つためのガードレールとして機能します。
    *   `disallowVendor` は、ユーザーがインポートパスに明示的に`/vendor/`を含めることを禁止します。これは、ベンダー機能が透過的に動作し、ユーザーがベンダーディレクトリの内部構造を意識せずに済むようにするためです。
    *   `disallowVendorVisibility` は、ベンダーパッケージの可視性ルールを強制します。これにより、ベンダーされたパッケージが、そのベンダーディレクトリを含むプロジェクトのサブツリー内でのみ使用されるように制限されます。これは、ベンダーされた依存関係がプロジェクトの外部に漏洩したり、意図しない方法で使用されたりするのを防ぐための重要なセキュリティおよび整合性メカニズムです。
*   **`-importmap` フラグ**: `go`コマンドがGoコンパイラ（`gc`）を呼び出す際に、ベンダーされたインポートパスを元のインポートパスにマッピングする`-importmap`フラグを渡すことで、コンパイラが正しいパッケージを見つけてリンクできるようにします。これにより、コンパイル時にベンダーされたパッケージが正しく参照され、ビルドが成功します。

これらの変更は、Go言語の依存関係管理において大きな転換点となり、プロジェクトの自己完結性とビルドの再現性を大幅に向上させる基盤を築きました。

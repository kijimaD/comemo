## 元コミット内容

`cmd/internal/obj, runtime: implement IE model TLS on ppc64le`

このコミットは、PPC64LEアーキテクチャにおけるTLSアクセスコードを、ABIドキュメントに記載されているパターンに一致するように変更することを目的としています。これにより、システムリンカがTLSアクセスを不適切に最適化するのを防ぎます。この変更により、`-buildmode=pie` オプションが機能するようになります。

## 変更の背景

Go言語のプログラムは、特に共有ライブラリとしてビルドされる場合や、アドレス空間配置のランダム化 (ASLR) を利用するPosition-Independent Executables (PIE) としてビルドされる場合に、スレッドローカルストレージ (TLS) へのアクセス方法が重要になります。PPC64LEアーキテクチャでは、TLSへのアクセス方法が特定のABI (Application Binary Interface) に従って実装されている必要があります。

以前の実装では、PPC64LEにおけるTLSアクセスがABIの要件を完全に満たしていなかったため、`-buildmode=pie` を使用してPIEをビルドすることができませんでした。PIEは、セキュリティ上の理由から現代のオペレーティングシステムで広く採用されており、実行可能ファイルのベースアドレスをランダム化することで、バッファオーバーフロー攻撃などの特定の種類の攻撃を軽減します。

このコミットの主な目的は、PPC64LE上でGoプログラムがPIEとして正しくビルドされ、実行できるように、TLSアクセスコードをPPC64LEのABIに準拠させることでした。特に、TLSの「Initial Exec (IE)」モデルを実装することで、共有ライブラリやPIE環境でのTLS変数の効率的かつ正確なアクセスを保証します。

## 前提知識の解説

### Thread-Local Storage (TLS)

TLSは、各スレッドが独自のデータコピーを持つことを可能にするストレージメカニズムです。グローバル変数や静的変数はプロセス内のすべてのスレッドで共有されますが、TLS変数はスレッドごとに独立した値を持ちます。これは、スレッドセーフなプログラミングや、スレッド固有のコンテキストを管理する際に非常に重要です。Goランタイムでは、現在のゴルーチン (g) ポインタなどの重要な情報がTLSに格納されることがあります。

### TLSアクセスモデル

TLSへのアクセスにはいくつかのモデルがあり、それぞれ異なるパフォーマンス特性と柔軟性を提供します。

1.  **Local Exec (LE) モデル**: 最も効率的なモデルです。TLS変数が現在の実行可能ファイル内で定義されており、かつ実行可能ファイルが共有ライブラリではない場合にのみ使用できます。TLS変数のスレッドポインタからのオフセットはリンク時に既知です。
2.  **Initial Exec (IE) モデル**: TLS変数が現在の実行可能ファイルまたは常に実行可能ファイルと共にロードされる共有ライブラリで定義されている場合に使用されます。TLS変数のアドレスはロード時に解決されます。LEモデルよりは遅いですが、General Dynamic (GD) モデルよりは効率的です。
3.  **General Dynamic (GD) モデル**: 最も柔軟なモデルで、TLS変数がどの共有ライブラリで定義されているかに関わらず使用できます。しかし、最もオーバーヘッドが大きいです。

このコミットは、PPC64LEにおけるIEモデルの実装に焦点を当てています。

### Position-Independent Executables (PIE)

PIEは、メモリ内の任意のアドレスにロードできる実行可能ファイルです。これは、アドレス空間配置のランダム化 (ASLR) と組み合わせて使用され、セキュリティを向上させます。PIEは、共有ライブラリと同様に、コードが絶対アドレスではなく相対アドレスを使用するようにコンパイルおよびリンクされる必要があります。

### PPC64LE ABI

PPC64LE (PowerPC 64-bit Little-Endian) は、IBM Powerアーキテクチャの64ビットリトルエンディアン版です。このアーキテクチャには、レジスタの使用方法、関数呼び出し規約、メモリレイアウト、そしてTLSへのアクセス方法などを定義する特定のABIがあります。ABIに準拠しないコードは、システムリンカによって正しく処理されなかったり、実行時にクラッシュしたりする可能性があります。

PPC64LEのABIでは、TLS変数は通常、スレッドポインタレジスタ (R13) を基準としたオフセットでアクセスされます。IEモデルの場合、Global Offset Table (GOT) と Table of Contents (TOC) レジスタ (R2) を介して間接的にアクセスするパターンが一般的です。

### リロケーション (Relocation)

リロケーションは、コンパイル時にアドレスが確定できないシンボル（例えば、共有ライブラリ内の関数や変数）のアドレスを、リンク時またはロード時に解決するプロセスです。リンカは、オブジェクトファイル内のリロケーションエントリを読み取り、実行可能ファイルや共有ライブラリがメモリにロードされる際のアドレスに基づいて、コード内の参照を修正します。TLSアクセスも、特定のリロケーションタイプを使用してリンカにその意図を伝えます。

## 技術的詳細

このコミットは、PPC64LEアーキテクチャにおけるTLSのIEモデルをサポートするために、Goのツールチェーン（アセンブラ、リンカ）とランタイムにわたる複数の変更を導入しています。

1.  **新しいリロケーションタイプの導入**:
    *   `src/cmd/internal/obj/link.go` に `R_POWER_TLS_IE` と `R_POWER_TLS` という新しいリロケーションタイプが追加されました。
        *   `R_POWER_TLS_IE`: IEモデルのTLSアクセスを実装するために使用されます。これは、D-formまたはDS-form命令シーケンスをリロケートします。具体的には、TOC (R2) からスレッドローカルシンボルのGOTスロットへのオフセットを挿入します。このGOTスロットは、動的リンカによってスレッドポインタ (R13) からのスレッドローカルシンボルのオフセットで埋められます。
        *   `R_POWER_TLS`: `MOVD 0(R13)(R31*1), g` のようなX-form命令が特定のスレッドローカルシンボルにアクセスしていることをマークします。これはコード生成には影響しませんが、システムリンカがIEモデルのコードをLEモデルのコードに緩和 (relax) する際に使用されます。
    *   `src/cmd/link/internal/ld/elf.go` には、PPC64LEのELF ABIに特化した複数の新しいリロケーションタイプ (`R_PPC64_GOT16_HA`, `R_PPC64_GOT16_LO_DS`, `R_PPC64_TLS`, `R_PPC64_GOT_TPREL16_LO_DS`, `R_PPC64_GOT_TPREL16_HA` など) が追加されました。これらは、IEモデルのTLSアクセスに必要な複雑なリロケーションシーケンスをサポートするために不可欠です。

2.  **アセンブラの変更 (`cmd/internal/obj/ppc64/asm9.go`)**:
    *   `aclass` 関数が変更され、共有ライブラリ/PIEビルド (`ctxt.Flag_shared != 0`) の場合に、スレッドローカルBSSセクション (`obj.STLSBSS`) のシンボルに対して `C_TLS_IE` を返すようになりました。これにより、アセンブラはIEモデルのTLSアクセスコードを生成するようになります。
    *   `asmout` 関数では、`C_TLS_IE` に対応する新しい命令シーケンスが追加されました。これは、`OP_ADDIS` (Add Immediate Shifted) と `opload(AMOVD)` 命令を生成し、`R_POWER_TLS_IE` リロケーションを付加します。このシーケンスは、PPC64LEのABIでIEモデルのTLSアクセスに推奨されるパターンです。
    *   また、`REG_R13` (スレッドポインタ) へのアクセスがある場合、`Flag_shared` が設定されていれば `R_POWER_TLS` リロケーションが生成されるようになりました。これは、リンカがTLSアクセスを識別し、必要に応じて最適化（緩和）できるようにするためのヒントです。

3.  **リンカの変更 (`cmd/link/internal/ppc64/asm.go`)**:
    *   `elfreloc1` 関数が拡張され、`obj.R_POWER_TLS` と `obj.R_POWER_TLS_IE` リロケーションを処理するようになりました。
        *   `obj.R_POWER_TLS` は `ld.R_PPC64_TLS` にマッピングされます。
        *   `obj.R_POWER_TLS_IE` は、`ld.R_PPC64_GOT_TPREL16_HA` と `ld.R_PPC64_GOT_TPREL16_LO_DS` という2つのELFリロケーションに展開されます。これらは、IEモデルのTLSアクセスに必要なGOTエントリの解決と、TOCからのオフセット計算をリンカに指示します。

4.  **ランタイムの変更 (`src/runtime/tls_ppc64x.s`)**:
    *   `runtime·save_g` と `runtime·load_g` 関数内の `g` (ゴルーチンポインタ) をTLSからロード/ストアするアセンブリ命令が変更されました。
    *   以前の `ADD R13, R31; MOVD g, 0(R31)` から、`MOVD g, 0(R13)(R31*1)` に変更されています。この新しい命令は、PPC64LEのABIに準拠したTLSアクセスパターンであり、スレッドポインタ (R13) と別のレジスタ (R31) を組み合わせたインデックス付きアドレッシングモードを使用しています。これにより、リンカがTLSアクセスを正しく認識し、最適化できるようになります。

これらの変更により、GoコンパイラとリンカはPPC64LE上でIEモデルのTLSアクセスコードを生成し、システムリンカがそれを正しく処理できるようになります。結果として、`-buildmode=pie` を使用したPIEのビルドが可能になり、Goプログラムのセキュリティと互換性が向上します。

## コアとなるコードの解説

### `src/cmd/internal/obj/link.go` の変更

このファイルでは、Goのアセンブラとリンカが内部的に使用するリロケーションタイプが定義されています。`R_POWER_TLS_IE` と `R_POWER_TLS` の追加は、PPC64LEにおけるIEモデルのTLSアクセスを正確に表現するために不可欠です。

*   `R_POWER_TLS_IE` のコメントは、このリロケーションがD-form/DS-form命令シーケンスをリロケートし、TOC (Table of Contents) からスレッドローカルシンボルのGOT (Global Offset Table) スロットへのオフセットを挿入することを明確にしています。動的リンカがこのGOTスロットを、スレッドポインタ (R13) からのスレッドローカルシンボルのオフセットで埋めるという、PPC64LE ABIのIEモデルの動作を反映しています。
*   `R_POWER_TLS` のコメントは、これがX-form命令（例: `MOVD 0(R13)(R31*1), g`）が特定のスレッドローカルシンボルにアクセスしていることをマークするために使用されることを説明しています。これはコード生成には直接影響しませんが、システムリンカがIEモデルのコードをLEモデルのコードに緩和する際に重要なヒントとなります。

### `src/cmd/internal/obj/ppc64/asm9.go` の変更

このファイルは、PPC64LEアーキテクチャのアセンブラのバックエンドロジックを含んでいます。

*   `aclass` 関数の変更は、TLSアクセスモデルの選択ロジックの核心です。`ctxt.Flag_shared != 0` は、共有ライブラリまたはPIEとしてビルドされているかどうかを示します。このフラグがセットされている場合、スレッドローカルBSSセクション (`obj.STLSBSS`) のシンボルに対して `C_TLS_IE` が返されるようになります。これにより、アセンブラはIEモデルに特化した命令シーケンスを生成する準備をします。そうでなければ、より効率的なLEモデル (`C_TLS_LE`) が使用されます。
*   `asmout` 関数内の変更は、実際にIEモデルのTLSアクセス命令を生成する部分です。
    *   `case 80:` の追加は、`C_TLS_IE` に対応する命令生成ロジックです。`OP_ADDIS` と `opload(AMOVD)` を使用して、TOC (R2) を基準にGOTスロットのアドレスを計算し、そこからTLS変数のオフセットをロードするPPC64LE ABIのIEモデルパターンを実装しています。`R_POWER_TLS_IE` リロケーションがここで付加され、リンカにこの命令シーケンスの意図を伝えます。
    *   `REG_R13` (スレッドポインタ) へのアクセスがある場合に `R_POWER_TLS` リロケーションを生成するロジックは、リンカがTLSアクセスを識別し、必要に応じて最適化（例えば、IEモデルからLEモデルへの緩和）を行うためのメタデータを提供します。

### `src/cmd/link/internal/ppc64/asm.go` の変更

このファイルは、PPC64LEアーキテクチャのリンカのバックエンドロジックを含んでいます。

*   `elfreloc1` 関数の変更は、アセンブラによって生成されたGo独自のリロケーションタイプを、PPC64LEのELF ABIに準拠したシステムリンカが理解できるELFリロケーションタイプに変換する役割を担います。
    *   `obj.R_POWER_TLS` が `ld.R_PPC64_TLS` にマッピングされることで、システムリンカはこれがTLSアクセスであることを認識します。
    *   `obj.R_POWER_TLS_IE` が `ld.R_PPC64_GOT_TPREL16_HA` と `ld.R_PPC64_GOT_TPREL16_LO_DS` の2つのELFリロケーションに展開されるのは非常に重要です。これらは、IEモデルのTLSアクセスに必要なGOTエントリの解決と、TOCからのオフセット計算をシステムリンカに指示するためのPPC64LE ABI固有のリロケーションです。

### `src/runtime/tls_ppc64x.s` の変更

このファイルは、PPC64LEアーキテクチャのGoランタイムのアセンブリコードを含んでいます。

*   `runtime·save_g` と `runtime·load_g` 関数内の変更は、`g` (現在のゴルーチンポインタ) をTLSからロード/ストアする方法をPPC64LEのABIに準拠させるものです。
    *   以前の `ADD R13, R31; MOVD g, 0(R31)` は、スレッドポインタ (R13) にオフセットを加算してからメモリアクセスを行うものでした。
    *   新しい `MOVD g, 0(R13)(R31*1)` は、PPC64LEのインデックス付きアドレッシングモードを使用しており、R13をベースレジスタ、R31をインデックスレジスタとして、スレッドポインタからのオフセットを計算してTLS変数にアクセスします。この形式は、システムリンカがTLSアクセスを正しく認識し、IEモデルのコンテキストで適切に処理するために必要なパターンです。

これらの変更は、GoのツールチェーンがPPC64LE上でPIEをサポートし、TLSを効率的かつABI準拠の方法で利用するための基盤を確立します。

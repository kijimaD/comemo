このコミットは、Goランタイムにおけるゴルーチンの状態管理、特にスタックコピー操作中の挙動を改善し、並行GC（Garbage Collection）との連携を強化することを目的としています。`dev.cc`ブランチ（並行GC開発に関連）の変更を`dev.garbage`ブランチにマージする一環として行われました。主な変更点は、`casgstatus`関数の挙動の調整と、スタックコピー専用の新しい状態遷移関数`casgcopystack`の導入です。これにより、スタックの拡張・縮小処理がより堅牢になり、GCとの競合状態が適切に処理されるようになります。

## 変更の背景

Go言語の初期のバージョンでは、ガベージコレクション（GC）が実行される際に、プログラム全体の実行が一時停止する「ストップ・ザ・ワールド（STW）」方式が採用されていました。これにより、特に大規模なアプリケーションやリアルタイム性が求められるシステムでは、GCによる長い一時停止が問題となることがありました。

Goチームは、このSTWによる一時停止を最小限に抑えるため、Go 1.5に向けて並行GCの開発を進めていました。並行GCでは、GCの大部分の処理をアプリケーションの実行と並行して行うことで、ユーザーコードの実行を妨げずにメモリ管理を行うことを目指します。

並行GCを実装する上で、ゴルーチンのスタック管理は重要な課題の一つでした。Goのゴルーチンは、必要に応じてスタックを動的に拡張・縮小する「スタックコピー」というメカニズムを採用しています。GCが実行中にゴルーチンのスタックが拡張・縮小されると、GCが参照しているオブジェクトのポインタが無効になるなどの競合状態が発生する可能性があります。

このコミットは、並行GCの開発ブランチである`dev.cc`の変更を`dev.garbage`にマージする過程で、特にゴルーチンのスタックコピーとGCの並行処理における同期と堅牢性を向上させるために行われました。具体的には、スタックコピー中にゴルーチンの状態が不整合にならないように、状態遷移のロジックをより厳密にし、GCとの協調を適切に行うための変更が導入されています。以前の`preemptscan`に関連するロジックがコメントアウトされていることから、GCの動作とスタック管理の連携方法が見直されたことが伺えます。

## 前提知識の解説

### ゴルーチン (Goroutine) とその状態

Goにおけるゴルーチンは、軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。Goランタイムのスケジューラがゴルーチンの実行を管理し、OSスレッドにマッピングします。

ゴルーチンは内部的に様々な状態を持ち、Goランタイムはこれらの状態を管理することで並行処理を実現しています。本コミットに関連する主なゴルーチン状態は以下の通りです。

*   **`_Gwaiting`**: ゴルーチンが何らかのイベント（チャネル操作、ネットワークI/O、タイマーなど）を待機している状態です。
*   **`_Grunnable`**: ゴルーチンが実行可能であり、スケジューラの実行キューでOSスレッドに割り当てられるのを待っている状態です。
*   **`_Gcopystack`**: ゴルーチンのスタックが現在、新しいより大きなスタックにコピーされている最中であることを示す状態です。スタックが不足した場合に、ランタイムがスタックを拡張するためにこの状態に遷移します。
*   **`_Gscan`**: このフラグは他のゴルーチン状態（例: `_Gwaiting|_Gscan`）と組み合わせて使用され、そのゴルーチンのスタックが現在ガベージコレクタによってスキャンされていることを示します。

### `casgstatus` と `readgstatus`

これらはGoランタイム内部で使用される関数で、ゴルーチン（`g`オブジェクト）の状態を原子的に（アトミックに）管理・読み取るために使われます。

*   **`readgstatus(gp *g) uint32`**: 指定されたゴルーチン`gp`の現在の状態を読み取ります。
*   **`casgstatus(gp *g, oldval, newval uint32)`**: ゴルーチン`gp`の現在の状態が`oldval`である場合にのみ、その状態を`newval`に原子的に変更しようとします。これはCompare-And-Swap (CAS) 操作であり、複数の並行処理が同時にゴルーチンの状態を変更しようとした際に、競合状態を防ぎ、安全な状態遷移を保証します。

### `systemstack`

`systemstack`は、Goランタイムの特定の重要な操作を実行するための特別なスタックです。通常のゴルーチンスタックとは異なり、`systemstack`上で実行されるコードはプリエンプション（横取り）されません。これは、スタックの拡張・縮小、ガベージコレクションのルーチン、スケジューラの一部操作など、中断されてはならない処理に使用されます。`systemstack`上で実行されるコードは、ユーザーゴルーチンのスタックを成長させる必要がなく、GCも`systemstack`をスキャンしません。

### `gothrow`

`gothrow`は、Goランタイム内部で回復不能な致命的なエラーが発生した場合に呼び出される関数です。ユーザーレベルの`panic`とは異なり、`gothrow`が呼び出されると通常はプログラムが終了します。これは、ランタイムの内部的な整合性チェックが失敗した場合など、非常に深刻な問題が発生したことを示します。

### スタックコピー (Stack Copying)

Goのゴルーチンは、最初は比較的小さなスタック（Go 1.4以降は2KB程度）で開始し、必要に応じてスタックを動的に拡張・縮小します。Go 1.4以降では、「スタックコピー」というメカニズムが採用されています。これは、ゴルーチンのスタックが不足した場合に、ランタイムが新しいより大きな連続したスタック領域を割り当て、古いスタックの内容を新しいスタックにコピーするというものです。これにより、スタックの動的なサイズ変更が効率的に行われます。スタックコピー時には、スタック内のポインタも新しいメモリ位置を指すように更新されます。

### 並行ガベージコレクション (Concurrent Garbage Collection)

GoのGCは、並行性、三色マーキング、マーク＆スイープアルゴリズムを特徴としています。

*   **並行性**: GCの大部分の作業はアプリケーションと並行して実行され、STW（Stop-The-World）による一時停止時間を最小限に抑えます。
*   **三色マーキング**: オブジェクトを白（未訪問、潜在的なゴミ）、灰色（訪問済みだが参照先未スキャン）、黒（訪問済みで参照先もスキャン済み）の三色で分類し、到達可能なオブジェクトを特定します。
*   **マーク＆スイープ**:
    *   **マークフェーズ**: ルートオブジェクト（ゴルーチンスタック、グローバル変数などから到達可能なオブジェクト）から開始し、到達可能なすべてのオブジェクトをマークします。
    *   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なゴミ）のメモリを解放します。

GCはヒープ上のメモリを管理し、ゴルーチンスタックも到達可能なオブジェクトを特定するためにスキャンされます。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムにおけるゴルーチンの状態遷移、特にスタックコピー操作と並行GCとの連携の堅牢性を高めることにあります。

### `src/runtime/proc1.go` の変更点

`casgstatus`関数は、ゴルーチンの状態を原子的に変更するための中心的な関数です。このコミットでは、`casgstatus`の内部ループに新しいチェックが追加されました。

```go
		if oldval == _Gwaiting && gp.atomicstatus == _Grunnable {
			systemstack(func() {
				gothrow("casgstatus: waiting for Gwaiting but is Grunnable")
			})
		}
```
このコードは、`casgstatus`が`_Gwaiting`状態からの遷移を試みているにもかかわらず、ゴルーチンがすでに`_Grunnable`状態になっているという予期せぬ状況を検出します。これは、`netpoll`などの非同期ウェイクアップによってゴルーチンが`_Gwaiting`から`_Grunnable`に遷移した際に発生する可能性のある競合状態を示唆しています。このような不整合を検出した場合、`gothrow`を呼び出してプログラムを終了させ、ランタイムのバグとして扱います。これは、ランタイムの内部状態の整合性を厳密に保つための防御的なプログラミングです。

また、以前の`preemptscan`に関連するGCヘルプのロジックがコメントアウトされました。
```go
-		if gp.preemptscan && !gp.gcworkdone && (oldval == _Grunning || oldval == _Gsyscall) {
-			gp.preemptscan = false
-			systemstack(func() {
-				gcphasework(gp)
-			})
-		}
```
これは、並行GCの進化に伴い、GCがゴルーチンのプリエンプションスキャンに依存するのではなく、より洗練された方法でGC作業を調整するようになったことを示唆しています。

さらに、`casgcopystack`という新しい関数が導入されました。
```go
// casgstatus(gp, oldstatus, Gcopystack), assuming oldstatus is Gwaiting or Grunnable.
// Returns old status. Cannot call casgstatus directly, because we are racing with an
// async wakeup that might come in from netpoll. If we see Gwaiting from the readgstatus,
// it might have become Grunnable by the time we get to the cas. If we called casgstatus,
// it would loop waiting for the status to go back to Gwaiting, which it never will.
//go:nosplit
func casgcopystack(gp *g) uint32 {
	for {
		oldstatus := readgstatus(gp) &^ _Gscan
		if oldstatus != _Gwaiting && oldstatus != _Grunnable {
			gothrow("copystack: bad status, not Gwaiting or Grunnable")
		}
		if cas(&gp.atomicstatus, oldstatus, _Gcopystack) {
			return oldstatus
		}
	}
}
```
この関数は、ゴルーチンの状態を`_Gcopystack`に遷移させることに特化しています。`casgstatus`を直接呼び出すのではなく、`casgcopystack`を使用する理由は、`netpoll`などの非同期ウェイクアップとの競合を考慮しているためです。ゴルーチンが`_Gwaiting`状態から`_Gcopystack`への遷移を試みる際に、非同期ウェイクアップによってすでに`_Grunnable`に遷移している可能性があります。`casgstatus`を直接使うと、`_Gwaiting`に戻るのを無限に待つループに陥る可能性がありますが、`casgcopystack`は`_Gwaiting`または`_Grunnable`のいずれかの状態から`_Gcopystack`への遷移を試み、成功した場合は元の状態を返します。これにより、スタックコピー操作の開始がより堅牢になります。`go:nosplit`ディレクティブは、この関数がスタックを拡張しないことを保証し、ランタイムの低レベルな操作に適しています。

### `src/runtime/stack1.go` の変更点

`newstack`関数は、ゴルーチンのスタックがオーバーフローした際に新しいスタックを割り当て、古いスタックの内容をコピーする処理を行います。

変更前は、`readgstatus`で現在の状態を読み取り、`_Gscan`フラグを除去してから`casgstatus`を呼び出して`_Gcopystack`に遷移させていました。
```go
-	oldstatus := readgstatus(gp)
-	oldstatus &^= _Gscan
-	casgstatus(gp, oldstatus, _Gcopystack) // oldstatus is Gwaiting or Grunnable
-	// Note that the concurrent GC might be scanning the stack as we try to replace it.
-	// copystack takes care of the appropriate coordination with the stack scanner.
```
変更後では、`casgstatus(gp, _Gwaiting, _Gcopystack)`と直接呼び出す形に変更されました。
```go
+	casgstatus(gp, _Gwaiting, _Gcopystack)
+
+	// The concurrent GC will not scan the stack while we are doing the copy since
+	// the gp is in a Gcopystack status.
```
これは、`newstack`が呼び出される時点ではゴルーチンが`_Gwaiting`状態にあることが期待されるため、より直接的な状態遷移を試みるようになったことを示唆しています。また、`_Gcopystack`状態にある間は並行GCがスタックをスキャンしないというコメントが追加され、GCとの協調が明確化されています。

`shrinkstack`関数は、ゴルーチンのスタックが過剰に大きい場合に、そのサイズを縮小する処理を行います。

変更前は、`newstack`と同様に`readgstatus`で状態を読み取り、`_Gscan`フラグを除去してから`casgstatus`を呼び出して`_Gcopystack`に遷移させていました。また、GCによって開始された場合は`_Gscan`状態で行われるため`_Gcopystack`への遷移は不要であるというコメントがありました。
```go
-	// This is being done in a Gscan state and was initiated by the GC so no need to move to
-	// the Gcopystate.
-	// The world is stopped, so the goroutine must be Gwaiting or Grunnable,
-	// and what it is is not changing underfoot.
-	oldstatus := readgstatus(gp) &^ _Gscan
-	if oldstatus != _Gwaiting && oldstatus != _Grunnable {
-		gothrow("status is not Gwaiting or Grunnable")
-	}
-	casgstatus(gp, oldstatus, _Gcopystack)
```
変更後では、新しく導入された`casgcopystack`関数を使用するように変更されました。
```go
+	oldstatus := casgcopystack(gp)
 	copystack(gp, newsize)
+	casgstatus(gp, _Gcopystack, oldstatus)
```
`shrinkstack`では、まず`casgcopystack(gp)`を呼び出してゴルーチンを`_Gcopystack`状態に遷移させ、元の状態（`_Gwaiting`または`_Grunnable`）を`oldstatus`として取得します。スタックコピーが完了した後、`casgstatus(gp, _Gcopystack, oldstatus)`を呼び出して、ゴルーチンを元の状態に戻します。これにより、スタック縮小操作中の状態管理がより明確かつ堅牢になりました。

これらの変更は、Goランタイムが並行GCの導入に向けて、ゴルーチンのスタック管理とGCの協調をより精密に制御しようとしていた時期の重要なステップを示しています。特に、競合状態の検出と、スタックコピーのようなクリティカルな操作における状態遷移の厳密な管理が重視されています。

## コアとなるコードの解説

### `src/runtime/proc1.go` の解説

1.  **`casgstatus`関数の変更**:
    *   追加されたコードブロック:
        ```go
        		if oldval == _Gwaiting && gp.atomicstatus == _Grunnable {
        			systemstack(func() {
        				gothrow("casgstatus: waiting for Gwaiting but is Grunnable")
        			})
        		}
        ```
        このコードは、`casgstatus`が`oldval`として`_Gwaiting`を期待しているにもかかわらず、ゴルーチン`gp`の実際のアトミックな状態（`gp.atomicstatus`）がすでに`_Grunnable`になっている場合に、ランタイムエラーを発生させます。これは、`casgstatus`がループ内で状態遷移を試みている間に、`netpoll`などの非同期イベントによってゴルーチンが`_Gwaiting`から`_Grunnable`に遷移してしまったという、予期せぬ競合状態を検出するためのものです。`systemstack`内で`gothrow`を呼び出すことで、この致命的な不整合を即座に報告し、プログラムを終了させます。
    *   コメントアウトされたGCヘルプのロジック:
        ```go
        -		if gp.preemptscan && !gp.gcworkdone && (oldval == _Grunning || oldval == _Gsyscall) {
        -			gp.preemptscan = false
        -			systemstack(func() {
        -				gcphasework(gp)
        -			})
        -		}
        ```
        以前は、ゴルーチンが`_Grunning`または`_Gsyscall`状態であり、かつGCのプリエンプションスキャンが必要な場合に、GC作業を助けるためのロジックがありました。この部分がコメントアウトされたのは、並行GCの設計変更により、GCがゴルーチンの状態遷移に直接介入するのではなく、より独立したメカニズムでGC作業を調整するようになったためと考えられます。

2.  **`casgcopystack`関数の新規追加**:
    ```go
    // casgstatus(gp, oldstatus, Gcopystack), assuming oldstatus is Gwaiting or Grunnable.
    // Returns old status. Cannot call casgstatus directly, because we are racing with an
    // async wakeup that might come in from netpoll. If we see Gwaiting from the readgstatus,
    // it might have become Grunnable by the time we get to the cas. If we called casgstatus,
    // it would loop waiting for the status to go back to Gwaiting, which it never will.
    //go:nosplit
    func casgcopystack(gp *g) uint32 {
    	for {
    		oldstatus := readgstatus(gp) &^ _Gscan
    		if oldstatus != _Gwaiting && oldstatus != _Grunnable {
    			gothrow("copystack: bad status, not Gwaiting or Grunnable")
    		}
    		if cas(&gp.atomicstatus, oldstatus, _Gcopystack) {
    			return oldstatus
    		}
    	}
    }
    ```
    この関数は、ゴルーチンの状態を`_Gcopystack`に原子的に遷移させるための専用ヘルパーです。
    *   コメントが示すように、この関数は`oldstatus`が`_Gwaiting`または`_Grunnable`であることを前提としています。
    *   `casgstatus`を直接呼び出せない理由として、`netpoll`などの非同期ウェイクアップとの競合が挙げられています。もしゴルーチンが`_Gwaiting`から`_Gcopystack`への遷移を試みる際に、すでに`_Grunnable`に遷移していた場合、`casgstatus`は`_Gwaiting`に戻るのを無限に待つことになります。
    *   `for`ループ内で、まず`readgstatus`で現在の状態を読み取り、`_Gscan`フラグを除去します。
    *   読み取った`oldstatus`が`_Gwaiting`でも`_Grunnable`でもない場合、`gothrow`でエラーを発生させます。これは、スタックコピーを開始するゴルーチンはこれらのいずれかの状態であるべきという前提が崩れたことを意味します。
    *   `cas(&gp.atomicstatus, oldstatus, _Gcopystack)`で、現在の状態が`oldstatus`であれば`_Gcopystack`に原子的に変更を試みます。成功すれば、元の`oldstatus`を返してループを抜けます。失敗した場合はループを続行し、再試行します。
    *   `go:nosplit`ディレクティブは、この関数がスタックを拡張しないことをコンパイラに指示します。これは、ランタイムの低レベルな操作でスタックのオーバーフローを防ぐために重要です。

### `src/runtime/stack1.go` の解説

1.  **`newstack`関数の変更**:
    *   変更前:
        ```go
        -	oldstatus := readgstatus(gp)
        -	oldstatus &^= _Gscan
        -	casgstatus(gp, oldstatus, _Gcopystack) // oldstatus is Gwaiting or Grunnable
        -	// Note that the concurrent GC might be scanning the stack as we try to replace it.
        ```

        以前は、`readgstatus`で現在の状態を読み取り、`_Gscan`フラグを除去してから`casgstatus`を呼び出して`_Gcopystack`に遷移させていました。
    *   変更後:
        ```go

        +

        +	// the gp is in a Gcopystack status.
        ```

        `newstack`が呼び出される時点では、ゴルーチンは通常`_Gwaiting`状態にあることが期待されるため、より直接的に`casgstatus(gp, _Gwaiting, _Gcopystack)`を呼び出す形に変更されました。これにより、スタック拡張の開始時にゴルーチンが`_Gwaiting`から`_Gcopystack`へ遷移します。
        新しいコメントは、ゴルーチンが`_Gcopystack`状態にある間は、並行GCがそのスタックをスキャンしないことを明示しています。これは、スタックコピー中にGCが不整合な状態のスタックをスキャンするのを防ぐための重要な協調メカニズムです。

2.  **`shrinkstack`関数の変更**:
    *   変更前:
        ```go
        -	// This is being done in a Gscan state and was initiated by the GC so no need to move to
        -	// the Gcopystate.
        -	// The world is stopped, so the goroutine must be Gwaiting or Grunnable,
        -	// and what it is is not changing underfoot.
        -	oldstatus := readgstatus(gp) &^ _Gscan
        -	if oldstatus != _Gwaiting && oldstatus != _Grunnable {
        -		gothrow("status is not Gwaiting or Grunnable")
        -	}
        -	casgstatus(gp, oldstatus, _Gcopystack)
        ```
        以前は、`newstack`と同様に`readgstatus`で状態を読み取り、`_Gscan`フラグを除去してから`casgstatus`を呼び出して`_Gcopystack`に遷移させていました。また、GCによって開始されたスタック縮小は`_Gscan`状態で行われるため、`_Gcopystack`への遷移は不要であるというコメントがありました。
    *   変更後:
        ```go
        +	oldstatus := casgcopystack(gp)
         	copystack(gp, newsize)
        +	casgstatus(gp, _Gcopystack, oldstatus)
        ```
        `shrinkstack`では、新しく導入された`casgcopystack`関数を使用するように変更されました。
        1.  `oldstatus := casgcopystack(gp)`: まず、`casgcopystack`を呼び出してゴルーチンを`_Gcopystack`状態に遷移させ、その際に元の状態（`_Gwaiting`または`_Grunnable`）を`oldstatus`として取得します。これにより、スタック縮小操作が安全に開始されます。
        2.  `copystack(gp, newsize)`: 実際のスタック縮小（コピー）処理が実行されます。
        3.  `casgstatus(gp, _Gcopystack, oldstatus)`: スタックコピーが完了した後、ゴルーチンを`_Gcopystack`状態から、スタック縮小開始前の元の状態（`oldstatus`）に戻します。

これらの変更は、Goランタイムが並行GCの導入に向けて、ゴルーチンのスタック管理とGCの協調をより精密に制御しようとしていた時期の重要なステップを示しています。特に、競合状態の検出と、スタックコピーのようなクリティカルな操作における状態遷移の厳密な管理が重視されています。

## 変更の背景

このコミットは、以前のコミット`da4abda2a1718c74b39134764ae6f694041a25e4`をRevertするものです。元のコミットは、「`REG_R0`を32に変更した後」に発生した`liblink`と`cmd/5a`におけるレジスタリストのパースと表示の問題を修正しようとしました。

ここでいう「`REG_R0`を32に変更」とは、ARMアーキテクチャにおけるレジスタ`R0`の扱い、またはレジスタのビット表現に関する何らかの変更があったことを示唆しています。この変更が、レジスタリスト（複数のレジスタをビットマスクで表現する形式）の処理に不具合を引き起こしたため、元のコミットでその修正が試みられました。

しかし、今回のRevertコミットは、その「修正」自体がさらなる問題を引き起こしたか、あるいは根本的な解決策ではなかったことを意味します。Revertによって、元の「修正」が導入した変更（例えば、`int64`から`int32`への型変更や、ビットシフト演算の変更）が元に戻され、以前の安定した状態に戻されています。これは、元の修正が意図しない副作用をもたらしたか、または問題の根本原因が別の場所にあったため、その修正が適切でなかったと判断されたためと考えられます。

## 前提知識の解説

*   **Go言語のツールチェイン**: Go言語のプログラムをビルド、テスト、実行するために必要な一連のツール群です。これには、コンパイラ、アセンブラ、リンカなどが含まれます。
*   **`cmd/5a`**: Go言語のツールチェインにおけるARMアーキテクチャ（32ビット）用のアセンブラです。アセンブラは、アセンブリ言語で書かれたコードを機械語に変換する役割を担います。Goのアセンブリは、一般的なGNUアセンブラとは異なる独自の構文を持っています。
*   **`liblink`**: Go言語のリンカが使用するライブラリです。リンカは、コンパイルされたオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成する役割を担います。`liblink`は、このリンカのコア機能を提供します。
*   **レジスタリスト (Register List)**: ARMアーキテクチャでは、複数のレジスタを一度に操作する命令（例: `LDM` (Load Multiple), `STM` (Store Multiple)）が存在します。これらの命令では、どのレジスタを操作するかをビットマスクで指定することが一般的です。例えば、レジスタ`R0`から`R3`までを含むリストは、対応するビットを立てた整数値で表現されます。
*   **`REG_R0`**: ARMアーキテクチャのレジスタ`R0`を指します。`R0`は、関数呼び出しにおける引数の受け渡しや戻り値の格納など、汎用的に使用されるレジスタです。この文脈では、`REG_R0`がレジスタリストのビットマスクにおける`R0`の位置、あるいは`R0`に関連するオフセット値として使われていた可能性があります。
*   **`int32` vs `int64`**: 整数型で、それぞれ32ビットと64ビットの幅を持ちます。レジスタリストを表現する際に、32ビットで十分な場合と、より多くのレジスタを表現するために64ビットが必要な場合があります。この変更は、レジスタリストの表現に必要なビット幅の認識に関するものです。
*   **ビットシフト演算 (`<<`, `>>`)**: 整数値のビットを左右に移動させる演算です。レジスタリストのビットマスクを生成する際や、特定のレジスタの情報を抽出する際に使用されます。`1ULL << i`は、`1`を`unsigned long long`型として扱い、`i`ビット左にシフトすることを意味し、結果は64ビットになります。`1 << i`は、`1`を`int`型として扱い、`i`ビット左にシフトすることを意味し、結果は通常32ビットになります。

## 技術的詳細

このRevertコミットは、元のコミットが導入した以下の主要な変更を元に戻しています。

1.  **`lval` 型の変更**:
    *   `src/cmd/5a/a.y` および `src/cmd/5a/y.tab.c`、`src/cmd/5a/y.tab.h` において、パーサのセマンティック値（`YYSTYPE`ユニオン内の`lval`フィールド）の型が`int64`から`int32`に戻されています。これは、レジスタリストのビットマスクを表現する際に、32ビットで十分であるという元の設計に戻ったことを意味します。元のコミットが`int64`に変更したのは、`REG_R0`の変更に伴い、レジスタリストの表現が64ビットを必要とするようになったと誤解したか、あるいは将来的な拡張を見越したものであったが、現状では不要であったためと考えられます。
2.  **ビットシフト演算の変更**:
    *   `src/cmd/5a/a.y` および `src/cmd/5a/y.tab.c` において、レジスタリストを生成する際のビットシフト演算が`1ULL << i`から`1 << i`に戻されています。これは、レジスタリストのビットマスクが32ビットの整数で表現されるべきであり、64ビットの`unsigned long long`を使用する必要がないことを明確にしています。元のコミットが`1ULL`を使用した理由は、`REG_R0`の変更がレジスタのビット位置を64ビット空間で扱うことを示唆していると解釈されたためかもしれません。
3.  **`REG_R0`関連のビットシフトの削除**:
    *   `src/liblink/asm5.c` において、`p->from.offset >> REG_R0` や `p->to.offset >> REG_R0` といった`REG_R0`によるビットシフトが削除され、`p->from.offset` や `p->to.offset` が直接使用されるようになっています。これは、`REG_R0`がレジスタリストのオフセット計算においてビットシフトとして機能していたが、その役割が不要になったか、あるいは誤っていたことを示しています。元のコミットは、`REG_R0`の変更がこのオフセット計算に影響を与えると判断し、修正を試みたものの、それが正しくなかったためRevertされました。
4.  **`vlong` 型の変更**:
    *   `src/liblink/list5.c` において、レジスタリストを処理する変数`v`の型が`vlong`（通常は64ビット整数）から`int`（通常は32ビット整数）に戻されています。これも、レジスタリストの表現が32ビットで十分であるという認識に戻ったことを裏付けています。

これらの変更は、GoのARMアセンブラとリンカが、レジスタリストを32ビットのビットマスクとして扱うという元の設計に回帰したことを示しています。元のコミットが導入した変更は、`REG_R0`の変更に関する誤解、またはレジスタリストの表現に関する誤った仮定に基づいていた可能性が高いです。

## コアとなるコードの解説

このRevertコミットの核心は、GoのARMアセンブラとリンカがレジスタリストをどのように表現し、処理するかという点にあります。

*   **型の一貫性**: `a.y`、`y.tab.c`、`y.tab.h`における`lval`の型を`int64`から`int32`に戻すことで、レジスタリストのビットマスクが32ビット整数で表現されるという前提を再確立しています。これは、ARMのレジスタセットが通常32個以下であり、32ビットで十分なビットマスクを表現できるためです。元のコミットが`int64`に変更したのは、おそらく`REG_R0`の変更を誤って解釈し、より大きなビット幅が必要だと判断したためでしょう。
*   **正確なビットシフト演算**: `1ULL << i`から`1 << i`への変更は、レジスタリストのビットマスク生成において、32ビットの整数演算を使用することを保証します。`1ULL`は`unsigned long long`型（64ビット）のリテラルであり、これを使用すると結果も64ビットになります。レジスタリストが32ビットで表現されるべきであるならば、この64ビット演算は不要であり、潜在的に誤った結果や非効率性をもたらす可能性があります。
*   **`REG_R0`の役割の修正**: `asm5.c`と`list5.c`における`REG_R0`によるビットシフトの削除は、`REG_R0`がレジスタリストのオフセット計算において、特定のビット位置を示すためのシフト量として機能していたが、その役割が誤っていたか、あるいは不要になったことを示しています。元のコミットは、`REG_R0`の変更がこのオフセット計算に影響を与えると判断し、修正を試みたものの、それが正しくなかったためRevertされました。これにより、レジスタリストのオフセットは直接`a->offset`として扱われるようになり、`REG_R0`による余分なシフトがなくなりました。
*   **`vlong`から`int`への変更**: `list5.c`における`vlong v`から`int v`への変更も、レジスタリストのビットマスクが32ビット整数で十分であるという前提を強化します。

これらの変更は、GoのARMツールチェインがレジスタリストを扱う際の内部表現とロジックを、より正確で効率的な32ビットベースの処理に戻すことを目的としています。元のコミットが導入した変更は、`REG_R0`の変更に関する誤解や、レジスタリストの表現に関する誤った仮定に基づいていたため、Revertが必要になったと考えられます。

*   **`int32` vs `int64`**: 整数型で、それぞれ32ビットと64ビットの幅を持ちます。レジスタリストを表現する際に、32ビットで十分な場合と、より多くのレジスタを表現するために64ビットが必要な場合があります。この変更は、レジスタリストの表現に必要なビット幅の認識に関するものです。
*   **ビットシフト演算 (`<<`, `>>`)**: 整数値のビットを左右に移動させる演算です。レジスタリストのビットマスクを生成する際や、特定のレジスタの情報を抽出する際に使用されます。`1ULL << i`は、`1`を`unsigned long long`型として扱い、`i`ビット左にシフトすることを意味し、結果は64ビットになります。`1 << i`は、`1`を`int`型として扱い、`i`ビット左にシフトすることを意味し、結果は通常32ビットになります。

## 技術的詳細

このRevertコミットは、元のコミットが導入した以下の主要な変更を元に戻しています。

1.  **`lval` 型の変更**:
    *   `src/cmd/5a/a.y` および `src/cmd/5a/y.tab.c`、`src/cmd/5a/y.tab.h` において、パーサのセマンティック値（`YYSTYPE`ユニオン内の`lval`フィールド）の型が`int64`から`int32`に戻されています。これは、レジスタリストのビットマスクを表現する際に、32ビットで十分であるという元の設計に戻ったことを意味します。元のコミットが`int64`に変更したのは、`REG_R0`の変更に伴い、レジスタリストの表現が64ビットを必要とするようになったと誤解したか、あるいは将来的な拡張を見越したものであったが、現状では不要であったためと考えられます。
2.  **ビットシフト演算の変更**:
    *   `src/cmd/5a/a.y` および `src/cmd/5a/y.tab.c` において、レジスタリストを生成する際のビットシフト演算が`1ULL << i`から`1 << i`に戻されています。これは、レジスタリストのビットマスクが32ビットの整数で表現されるべきであり、64ビットの`unsigned long long`を使用する必要がないことを明確にしています。元のコミットが`1ULL`を使用した理由は、`REG_R0`の変更がレジスタのビット位置を64ビット空間で扱うことを示唆していると解釈されたためかもしれません。
3.  **`REG_R0`関連のビットシフトの削除**:
    *   `src/liblink/asm5.c` において、`p->from.offset >> REG_R0` や `p->to.offset >> REG_R0` といった`REG_R0`によるビットシフトが削除され、`p->from.offset` や `p->to.offset` が直接使用されるようになっています。これは、`REG_R0`がレジスタリストのオフセット計算においてビットシフトとして機能していたが、その役割が不要になったか、あるいは誤っていたことを示しています。元のコミットは、`REG_R0`の変更がこのオフセット計算に影響を与えると判断し、修正を試みたものの、それが正しくなかったためRevertされました。
4.  **`vlong` 型の変更**:
    *   `src/liblink/list5.c` において、レジスタリストを処理する変数`v`の型が`vlong`（通常は64ビット整数）から`int`（通常は32ビット整数）に戻されています。これも、レジスタリストの表現が32ビットで十分であるという認識を裏付けています。

これらの変更は、GoのARMアセンブラとリンカが、レジスタリストを32ビットのビットマスクとして扱うという元の設計に回帰したことを示しています。元のコミットが導入した変更は、`REG_R0`の変更に関する誤解や、レジスタリストの表現に関する誤った仮定に基づいていた可能性が高いです。

## コアとなるコードの解説

このRevertコミットの核心は、GoのARMアセンブラとリンカがレジスタリストをどのように表現し、処理するかという点にあります。

*   **型の一貫性**: `a.y`、`y.tab.c`、`y.tab.h`における`lval`の型を`int64`から`int32`に戻すことで、レジスタリストのビットマスクが32ビット整数で表現されるという前提を再確立しています。これは、ARMのレジスタセットが通常32個以下であり、32ビットで十分なビットマスクを表現できるためです。元のコミットが`int64`に変更したのは、おそらく`REG_R0`の変更を誤って解釈し、より大きなビット幅が必要だと判断したためでしょう。
*   **正確なビットシフト演算**: `1ULL << i`から`1 << i`への変更は、レジスタリストのビットマスク生成において、32ビットの整数演算を使用することを保証します。`1ULL`は`unsigned long long`型（64ビット）のリテラルであり、これを使用すると結果も64ビットになります。レジスタリストが32ビットで表現されるべきであるならば、この64ビット演算は不要であり、潜在的に誤った結果や非効率性をもたらす可能性があります。
*   **`REG_R0`の役割の修正**: `asm5.c`と`list5.c`における`REG_R0`によるビットシフトの削除は、`REG_R0`がレジスタリストのオフセット計算において、特定のビット位置を示すためのシフト量として機能していたが、その役割が不要になったか、あるいは誤っていたことを示しています。元のコミットは、`REG_R0`の変更がこのオフセット計算に影響を与えると判断し、修正を試みたものの、それが正しくなかったためRevertされました。これにより、レジスタリストのオフセットは直接`a->offset`として扱われるようになり、`REG_R0`による余分なシフトがなくなりました。
*   **`vlong`から`int`への変更**: `list5.c`における`vlong v`から`int v`への変更も、レジスタリストのビットマスクが32ビット整数で十分であるという前提を強化します。

これらの変更は、GoのARMツールチェインがレジスタリストを扱う際の内部表現とロジックを、より正確で効率的な32ビットベースの処理に戻すことを目的としています。元のコミットが導入した変更は、`REG_R0`の変更に関する誤解や、レジスタリストの表現に関する誤った仮定に基づいていたため、Revertが必要になったと考えられます。

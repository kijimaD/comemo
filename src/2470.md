## 元コミット内容

このコミットは、Goランタイムの386アーキテクチャ向けコードを、より新しい設計に適合させるための広範な変更を導入しています。主な目的は、ゴルーチン（`g`）とOSスレッド（`m`）のコンテキスト管理、スタックの動的な伸縮、およびスレッドローカルストレージ（TLS）のアクセス方法を改善することです。具体的には、`g`と`m`構造体へのアクセスを`FS`セグメントレジスタのオフセットから直接シンボル参照へと変更し、`Gobuf`構造体を用いたコンテキストスイッチメカニズムを導入し、スタックの成長と縮小を処理する`sys·morestack`と`sys·lessstack`関数を再構築しています。また、OSスレッドの作成（`clone`）時におけるTLSのセットアップも強化されています。

## 変更の背景

Go言語は、軽量な並行処理の単位であるゴルーチンを効率的に管理するために、独自のランタイムシステムを持っています。初期のGoランタイムは、ゴルーチンのスケジューリング、スタック管理、OSスレッドとの連携において、様々な試行錯誤を繰り返していました。このコミットが行われた2009年頃は、Go言語がまだ開発の初期段階にあり、ランタイムのコア部分が活発に設計・実装されていた時期です。

この「新しいランタイム」への更新は、以下の課題に対処することを目的としています。

1.  **`g`と`m`構造体へのアクセスの一貫性:** 以前は`FS`セグメントレジスタのオフセットを介して`g`（現在のゴルーチン）と`m`（現在のOSスレッド）にアクセスしていましたが、これはアセンブリコードの可読性を損ない、将来的なアーキテクチャ変更への対応を難しくしていました。より直接的でシンボリックなアクセス方法への移行が求められていました。
2.  **堅牢なコンテキストスイッチ:** ゴルーチンの切り替えは、プログラムカウンタ（PC）とスタックポインタ（SP）を含むCPUレジスタの状態を正確に保存・復元する必要があります。このプロセスを`Gobuf`という専用の構造体でカプセル化することで、より安全で明確なコンテキストスイッチを実現しようとしていました。
3.  **効率的なスタック管理:** Goのゴルーチンは、必要に応じてスタックを動的に成長・縮小させます。このメカニズムは、スタックオーバーフローを防ぎつつ、メモリ使用量を最適化するために不可欠です。`morestack`と`lessstack`の再設計は、この動的なスタック管理をより効率的かつ正確に行うためのものでした。
4.  **OSスレッド作成時のTLSの正確な設定:** 新しいOSスレッドが作成される際、そのスレッドが自身の`m`と`g`構造体に正しくアクセスできるように、スレッドローカルストレージ（TLS）を適切に設定する必要があります。特に386アーキテクチャでは、Local Descriptor Table (LDT) を用いたTLSのセットアップが重要でした。

これらの変更は、Goランタイムの安定性、パフォーマンス、および将来的な拡張性を向上させるための基盤を築くものでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

*   **Goランタイム (Go Runtime):** Goプログラムの実行を管理するシステム。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、スタック管理、システムコールインターフェースなどを担当します。
*   **ゴルーチン (Goroutine):** Go言語における軽量な並行処理の単位。OSスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。GoランタイムがゴルーチンをOSスレッドにマッピングし、スケジューリングを行います。
*   **M (Machine/Thread):** Goランタイムが抽象化するOSスレッド。`m`構造体は、OSスレッド固有の情報（スタック、レジスタ、現在のゴルーチンなど）を保持します。
*   **G (Goroutine):** Goランタイムが抽象化するゴルーチン。`g`構造体は、ゴルーチン固有の情報（スタック、レジスタ、状態など）を保持します。
*   **P (Processor):** Goランタイムのスケジューラが使用する論理プロセッサ。`P`は`M`にアタッチされ、`M`が`G`を実行するためのコンテキストを提供します。
*   **スケジューラ (Scheduler):** Goランタイムの主要なコンポーネントで、ゴルーチンを`M`に割り当て、実行を管理します。
*   **コンテキストスイッチ (Context Switch):** CPUが現在実行中のタスク（ゴルーチンやスレッド）から別のタスクに切り替えるプロセス。この際、現在のタスクのCPUレジスタの状態を保存し、新しいタスクのレジスタ状態を復元します。
*   **スタック (Stack):** 関数呼び出しの際にローカル変数やリターンアドレスなどが格納されるメモリ領域。Goのゴルーチンスタックは動的に伸縮します。
*   **スタックガード (Stack Guard):** スタックオーバーフローを検出するためのメカニズム。スタックの末尾にガードページを設けることで、スタックがその領域に侵入しようとするとトラップが発生し、ランタイムがスタックを拡張します。
*   **スレッドローカルストレージ (TLS: Thread Local Storage):** 各OSスレッドがそれぞれ独立したデータを保持するためのメカニズム。Goランタイムでは、現在の`g`と`m`へのポインタをTLSに格納することで、アセンブリコードから高速にアクセスできるようにしています。
*   **Local Descriptor Table (LDT):** 386アーキテクチャにおけるセグメンテーションメカニズムの一部。特定のセグメントレジスタ（例: `FS`、`GS`）が指すメモリ領域を定義するために使用されます。TLSの実装に利用されることがあります。
*   **`8l` (Go Linker for 386):** Go言語のツールチェーンの一部で、386アーキテクチャ向けのオブジェクトファイルをリンクして実行可能ファイルを生成するリンカ。
*   **`asm.s` ファイル:** Goランタイムのコア部分で、アセンブリ言語で書かれたコードが含まれます。コンテキストスイッチ、システムコール、スタック管理など、パフォーマンスが要求される低レベルな処理が実装されています。
*   **`Gobuf` 構造体:** ゴルーチンのコンテキスト（スタックポインタ、プログラムカウンタ、現在のゴルーチンへのポインタなど）を保存するための構造体。`setjmp`/`longjmp`のような機能を提供します。
*   **`clone` システムコール:** Linuxにおいて、新しいプロセスやスレッドを作成するためのシステムコール。Goランタイムはこれを利用してOSスレッドを生成します。
*   **`futex` システムコール:** Linuxにおいて、ユーザー空間での高速な同期プリミティブ（ミューテックス、セマフォなど）を実装するためのシステムコール。

## 技術的詳細

このコミットの技術的詳細は、主に386アーキテクチャのアセンブリコードと、GoランタイムのCコードにおける`g`と`m`の管理、スタックの動的な伸縮、およびOSスレッドのライフサイクル管理に焦点を当てています。

### `g`と`m`へのアクセス方法の変更

以前のGoランタイムでは、現在のゴルーチン`g`とOSスレッド`m`へのポインタは、`FS`セグメントレジスタのオフセットを介してアクセスされていました（例: `0(FS)`が`g`、`4(FS)`が`m`）。これは、386アーキテクチャのセグメンテーション機能を利用したTLSの実装方法でした。

このコミットでは、このアクセス方法が変更され、`g`と`m`が直接シンボルとして参照されるようになりました（例: `MOVL CX, g`, `MOVL AX, m`）。これは、`g`と`m`がグローバル変数、またはTLSを介してより抽象的にアクセスされるようになったことを示唆しています。この変更により、アセンブリコードの可読性が向上し、セグメントレジスタの直接操作に依存しない、よりポータブルなランタイム設計への一歩となりました。

### `Gobuf` を用いたコンテキストスイッチ

ゴルーチンのコンテキストスイッチは、`gosave`、`gogo`、`gogocall`といった関数によって管理されます。

*   **`gosave(Gobuf*)`**: 現在のゴルーチンの状態（SP, PC, `g`へのポインタ）を`Gobuf`構造体に保存します。これはC言語の`setjmp`に相当する機能を提供し、後で`gogo`によってこの状態に復帰できるようにします。
    *   `gobuf_sp(AX)`: スタックポインタを保存。
    *   `gobuf_pc(AX)`: プログラムカウンタ（リターンアドレス）を保存。
    *   `gobuf_g(AX)`: 現在のゴルーチン`g`へのポインタを保存。
*   **`gogo(Gobuf*, uintptr)`**: `Gobuf`構造体に保存された状態を復元し、そのゴルーチンに実行を切り替えます。これはC言語の`longjmp`に相当します。
    *   `gobuf_g(BX)`から`g`を復元し、`g`レジスタ（またはTLS経由の`g`シンボル）に設定。
    *   `gobuf_sp(BX)`からSPを復元。
    *   `gobuf_pc(BX)`からPCを復元し、そのアドレスにジャンプ。
*   **`gogocall(Gobuf*, void (*fn)(void))`**: `Gobuf`に保存された状態を復元した後、指定された関数`fn`を呼び出します。これは、特定の関数を実行するためにゴルーチンを起動する際に使用されます。

これらの関数は、ゴルーチンの状態管理を`Gobuf`という明確なデータ構造に集約することで、コンテキストスイッチのロジックをより構造化し、エラーの可能性を減らしています。

### 動的なスタック管理 (`sys·morestack`, `sys·lessstack`)

Goのゴルーチンスタックは、必要に応じて自動的に成長・縮小します。このメカニズムは、`sys·morestack`と`sys·lessstack`というアセンブリ関数によって実現されます。

*   **`sys·morestack`**: 関数プロローグでスタックガードに到達した場合に呼び出されます。
    *   現在のゴルーチンがスケジューラゴルーチン（`m->g0`）でないことを確認。スケジューラゴルーチンはスタックを成長させることはできません。
    *   現在の関数のフレームサイズと引数サイズを`m`構造体（`m_moreframe`, `m_moreargs`）に保存。
    *   現在のゴルーチンのコンテキスト（呼び出し元のPC, SP, `g`）を`m->morebuf`に保存。
    *   現在の関数のPCを`m->morepc`に保存。
    *   スケジューラゴルーチン（`m->g0`）に切り替え、`newstack`関数を呼び出してスタックを拡張します。
*   **`sys·lessstack`**: スタックが縮小可能になった場合（通常は関数からのリターン時）に呼び出されます。
    *   関数の戻り値を`m->cret`に保存。
    *   スケジューラゴルーチン（`m->g0`）に切り替え、`oldstack`関数を呼び出してスタックを縮小します。

これらの関数は、ゴルーチンが自身のスタックを使い果たそうとしたとき、またはスタックが過剰に大きい場合に、ランタイムが介入してスタックを動的に調整するための重要なフックを提供します。

### OSスレッド作成時のTLSとLDTのセットアップ

`newosproc`関数（`darwin/thread.c`, `linux/thread.c`）は、新しいOSスレッドを作成する際に`clone`システムコール（Linux）または`bsdthread_create`（Darwin）を呼び出します。このコミットでは、新しいOSスレッドが起動した後の初期化プロセスが強化されています。

特にLinuxの`clone`アセンブリコードでは、子スレッドが起動した後に以下の処理が行われます。

1.  **`m`, `g`, `fn` の復元:** 親スレッドから渡された`m`（OSスレッド情報）、`g`（ゴルーチン情報）、および`fn`（新しいスレッドで実行する関数）へのポインタをスタックから復元します。
2.  **`m->procid` の設定:** `gettid`システムコール（または同等の機能）を呼び出して現在のスレッドIDを取得し、`m->procid`に保存します。これはデバッガなどでのスレッド識別に使用されます。
3.  **LDTとTLSのセットアップ:**
    *   `m->tls`に格納されたスレッドローカルストレージ情報に基づいて、`setldt`関数を呼び出し、Local Descriptor Table (LDT) エントリを設定します。
    *   設定されたLDTエントリに対応するセグメントセレクタを`FS`レジスタにロードします。これにより、`FS`レジスタを介してスレッドローカルなデータ（特に`g`と`m`へのポインタ）にアクセスできるようになります。
4.  **`g`と`m`の初期化:** `FS`レジスタが設定された後、新しいスレッドの`g`と`m`シンボルが、復元されたポインタで初期化されます。
5.  **スタックチェックと関数呼び出し:** `emptyfunc`を呼び出してスタックが正しく設定されているかを確認した後、新しいスレッドで実行すべき関数`fn`を呼び出します。

この詳細なTLSとLDTのセットアップは、386アーキテクチャにおいて、各OSスレッドが自身の`g`と`m`構造体に効率的かつ安全にアクセスするための基盤となります。

### リンカ (`8l`) の変更

`src/cmd/8l/pass.c`の`dostkoff`関数における変更は、リンカがスタックフレームのオフセットを計算し、ランタイムが使用するスタックガードや引数サイズなどの情報をどのように扱うかに関連しています。新しいランタイムのスタック管理メカニズムに合わせて、リンカもこれらの値を正しく設定するように調整されています。特に、`newproc`に渡される引数サイズが`8`から`0`に変更されたことは、ゴルーチン起動時のABI（Application Binary Interface）の変更を示唆しています。

### システムコールABIの変更

`src/pkg/runtime/linux/os.h`および関連するアセンブリファイルでは、`futex`と`clone`システムコールの戻り値の型が`int64`から`int32`に変更されています。これは、これらのシステムコールが返す値の範囲が`int32`で十分であると判断されたか、または特定のLinuxカーネルバージョンとの互換性、あるいは386アーキテクチャにおけるレジスタの利用方法の最適化によるものと考えられます。

## コアとなるコードの解説

### `src/pkg/runtime/386/asm.s` の変更点

このファイルは、386アーキテクチャにおけるGoランタイムの心臓部であり、ゴルーチンのスケジューリングとスタック管理の低レベルな詳細を扱います。

*   **`g`と`m`の直接参照:**
    ```assembly
    // 旧
    // MOVL CX, 0(FS)
    // MOVL AX, 4(FS)
    // 新
    MOVL CX, g
    MOVL AX, m
    ```
    これは、現在のゴルーチン`g`とOSスレッド`m`へのポインタを、`FS`セグメントレジスタのオフセットではなく、直接`g`と`m`というシンボル（グローバル変数またはTLSを介してアクセスされる変数）として扱うようになったことを示しています。これにより、コードの意図がより明確になります。

*   **`gosave`と`gogo`の再実装:**
    ```assembly
    // uintptr gosave(Gobuf*)
    TEXT gosave(SB), 7, $0
        MOVL    4(SP), AX       // gobuf
        LEAL    4(SP), BX       // caller's SP
        MOVL    BX, gobuf_sp(AX)
        MOVL    0(SP), BX       // caller's PC
        MOVL    BX, gobuf_pc(AX)
        MOVL    g, BX
        MOVL    BX, gobuf_g(AX)
        MOVL    $0, AX          // return 0
        RET

    // void gogo(Gobuf*, uintptr)
    TEXT gogo(SB), 7, $0
        MOVL    8(SP), AX       // return 2nd arg
        MOVL    4(SP), BX       // gobuf
        MOVL    gobuf_g(BX), DX
        MOVL    0(DX), CX       // make sure g != nil
        MOVL    DX, g
        MOVL    gobuf_sp(BX), SP    // restore SP
        MOVL    gobuf_pc(BX), BX
        JMP BX
    ```
    `gosave`は現在のSP、PC、`g`を`Gobuf`構造体のフィールド（`gobuf_sp`, `gobuf_pc`, `gobuf_g`）に保存します。`gogo`はこれらのフィールドから値を復元し、`g`レジスタ（またはシンボル）を更新し、SPを復元し、保存されたPCにジャンプして実行を再開します。これにより、ゴルーチンのコンテキストスイッチがより明示的かつ構造化されます。

*   **`sys·morestack`と`sys·lessstack`の導入:**
    ```assembly
    // Called during function prolog when more stack is needed.
    TEXT sys·morestack(SB),7,$0
        // Cannot grow scheduler stack (m->g0).
        MOVL    m, BX
        MOVL    m_g0(BX), SI
        CMPL    g, SI
        JNE     2(PC)
        INT     $3 // crash

        // ... (frame size, arg size, caller PC/SP/g, current PCの保存) ...

        // Call newstack on m's scheduling stack.
        MOVL    m_g0(BX), BP
        MOVL    BP, g
        MOVL    (m_sched+gobuf_sp)(BX), SP
        CALL    newstack(SB)
        MOVL    $0, 0x1003 // crash if newstack returns
        RET

    // Return point when leaving stack.
    TEXT sys·lessstack(SB), 7, $0
        // Save return value in m->cret
        MOVL    m, BX
        MOVL    AX, m_cret(BX)

        // Call oldstack on m's scheduling stack.
        MOVL    m_g0(BX), DX
        MOVL    DX, g
        MOVL    (m_sched+gobuf_sp)(BX), SP
        CALL    oldstack(SB)
        MOVL    $0, 0x1004 // crash if oldstack returns
        RET
    ```
    `sys·morestack`は、スタックが不足した際にランタイムがスタックを拡張するために呼び出されます。現在のゴルーチンの状態を保存し、スケジューラゴルーチンに切り替えて`newstack`を呼び出します。`sys·lessstack`は、スタックが過剰に大きい場合に縮小するために呼び出され、同様にスケジューラゴルーチンに切り替えて`oldstack`を呼び出します。これらの関数は、Goの動的なスタック管理の核心をなします。

### `src/pkg/runtime/linux/386/sys.s` の `clone` システムコール変更点

`clone`システムコールは、新しいOSスレッドを作成するために使用されます。このコミットでは、子スレッドが起動した後の初期化ロジックが大幅に拡張されています。

```assembly
TEXT clone(SB),7,$0
    // ... (親スレッドでの処理) ...

    // In child on new stack.  Reload registers (paranoia).
    MOVL    0(SP), BX       // m
    MOVL    4(SP), DX       // g
    MOVL    8(SP), CX       // fn

    MOVL    AX, m_procid(BX)    // save tid as m->procid

    // set up ldt 7+id to point at m->tls.
    // m->tls is at m+40.  newosproc left the id in tls[0].
    LEAL    m_tls(BX), BP
    MOVL    0(BP), DI
    ADDL    $7, DI      // m0 is LDT#7. count up.
    // setldt(tls#, &tls, sizeof tls)
    PUSHAL      // save registers
    PUSHL   $32     // sizeof tls
    PUSHL   BP      // &tls
    PUSHL   DI      // tls #
    CALL    setldt(SB)
    POPL    AX
    POPL    AX
    POPL    AX
    POPAL
    SHLL    $3, DI      // segment# is ldt*8 + 7 (different 7 than above)
    ADDL    $7, DI
    MOVW    DI, FS

    // Now segment is established.  Initialize m, g.
    MOVL    DX, g
    MOVL    BX, m

    // ... (スタックチェックとfn()呼び出し) ...
```
子スレッドのコンテキストでは、まず親から渡された`m`, `g`, `fn`をスタックから取得します。次に、`gettid`システムコールで取得したスレッドIDを`m->procid`に保存します。最も重要なのは、`setldt`を呼び出してLDTエントリを設定し、そのセレクタを`FS`レジスタにロードすることで、新しいスレッドのTLSを確立している点です。これにより、`g`と`m`へのアクセスが正しく設定され、その後の`g`と`m`の初期化が確実に行われます。

これらの変更は、Goランタイムが386アーキテクチャ上でゴルーチンとOSスレッドをどのように管理し、コンテキストスイッチとスタック管理をどのように実行するかという、Goの並行処理モデルの根幹に関わるものです。

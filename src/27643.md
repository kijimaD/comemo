## 元コミット内容

`cmd/vet: do not treat declaration as asignment in atomic check`

このコミットは、`cmd/vet` ツールが `atomic` チェックを行う際に、変数の宣言を代入として扱わないようにする修正です。これにより、`sync/atomic` パッケージの誤用に関する誤った警告が解消されます。

## 変更の背景

Go言語には、並行処理における共有メモリへの安全なアクセスを保証するための `sync/atomic` パッケージが存在します。このパッケージは、アトミック操作（不可分操作）を提供し、複数のゴルーチンが同時に同じメモリ位置にアクセスしてもデータ競合が発生しないようにします。

`go vet` ツールは、Goコードの静的解析を行い、潜在的なバグや疑わしい構造を検出します。その機能の一つに `atomic` チェックがあり、`sync/atomic` パッケージの誤用、特にアトミックな値への直接代入を検出することを目的としています。アトミックな値への直接代入は、アトミック操作の保証を破り、データ競合を引き起こす可能性があるため、`vet` はこれを警告します。

しかし、このコミット以前の `cmd/vet` の `atomic` チェックにはバグがありました。Go言語では、`x := atomic.AddUint64(&x, 1)` のように、短い変数宣言 (`:=`) を使用して新しい変数を宣言し、同時に `sync/atomic` パッケージの関数呼び出しの結果で初期化する場合があります。この場合、`vet` はこれを「アトミックな値への直接代入」と誤認し、不適切な警告を発していました。これは、既存の変数への代入と新しい変数の宣言を区別できていなかったためです。

この誤検出は、開発者が正しく記述されたコードに対しても警告を受け取る原因となり、`vet` ツールの信頼性を損ねる可能性がありました。そのため、この問題を解決し、`vet` がより正確な解析を行うようにするための修正が必要とされました。Issue #15118 はこの問題が報告されたものです。

## 前提知識の解説

### `go vet` と `cmd/vet`

`go vet` はGo言語に標準で付属する静的解析ツールです。コンパイラでは検出できないが、潜在的なバグや非慣用的なコードパターンを検出します。例えば、到達不能なコード、フォーマット文字列の不一致、ロックの誤用、そしてこのコミットで扱われるアトミック操作の誤用などが挙げられます。`cmd/vet` は `go vet` の実装本体です。

### `sync/atomic` パッケージ

`sync/atomic` パッケージは、Go言語で低レベルのアトミック操作を提供します。これは、ミューテックス（`sync.Mutex`）のような高レベルな同期プリミティブを使用せずに、単一のCPU命令で実行される不可分な操作を可能にします。これにより、複数のゴルーチンが同時に共有変数にアクセスする際のデータ競合を防ぎ、パフォーマンスを向上させることができます。
主な関数には `AddUint64`, `LoadUint64`, `StoreUint64`, `CompareAndSwapUint64` などがあり、これらは特定の型（`int32`, `int64`, `uint32`, `uint64`, `uintptr`, `unsafe.Pointer`）に対してアトミックな読み書き、加算、比較交換操作を提供します。

### アトミック操作の重要性

並行プログラミングにおいて、複数のゴルーチンが共有変数に同時にアクセスし、その値を変更しようとすると、データ競合（data race）が発生する可能性があります。データ競合は予測不能な結果やプログラムのクラッシュを引き起こすため、厳密に避ける必要があります。アトミック操作は、このようなデータ競合を防ぐための基本的なメカニズムの一つです。

### Goにおける変数宣言と代入

Go言語では、変数の宣言と初期化にはいくつかの方法があります。
- `var x int = 0`: 明示的な型指定と初期化。
- `var x = 0`: 型推論による宣言と初期化。
- `x := 0`: 短い変数宣言（Short variable declaration）。これは、新しい変数を宣言し、同時に初期化する際に使用されます。この構文は、同じスコープ内で既に宣言されている変数に対しては代入として機能しますが、少なくとも1つの新しい変数が宣言される必要があります。

### 変数シャドーイング (Variable Shadowing)

変数シャドーイングとは、内側のスコープで宣言された変数が、外側のスコープで同じ名前の変数を「隠す」現象を指します。このコミットのテストケースにも示されているように、`x := atomic.AddUint64(&x, 1)` のようなコードは、外側のスコープの `x` をシャドーイングする新しい `x` を宣言する可能性があります。`cmd/vet` は、このようなシャドーイングも検出して警告することがあります。

## 技術的詳細

`cmd/vet` の `atomic` チェックは、Goの抽象構文木（AST: Abstract Syntax Tree）を走査し、代入文（`ast.AssignStmt`）を分析することで機能します。以前の実装では、`ast.AssignStmt` の `Tok` フィールドが `token.ASSIGN`（通常の代入 `=`）または `token.DEFINE`（短い変数宣言 `:=`）のどちらであるかに関わらず、左辺（`Lhs`）の式が `sync/atomic` パッケージによって管理される値である場合に警告を発していました。

問題は、`token.DEFINE` を伴う `ast.AssignStmt` が、新しい変数の宣言と初期化を意味するにもかかわらず、既存の変数への「代入」として扱われていた点にありました。例えば、`x := atomic.AddUint64(&y, 1)` のようなコードは、`x` という新しい変数を宣言しているだけであり、`y` はアトミックに更新されています。しかし、`vet` は `x` がアトミックな値であるかのように誤解し、警告を発していました。

このコミットでは、`checkAtomicAssignment` 関数に以下の条件が追加されました。

```go
	if len(n.Lhs) == 1 && n.Tok == token.DEFINE {
		return
	}
```

このコードは、代入文の左辺が1つだけであり（つまり、単一の変数宣言）、かつそれが短い変数宣言 (`:=`) である場合に、`atomic` チェックをスキップするように指示します。これにより、新しい変数の宣言と初期化が、既存のアトミック値への直接代入と誤認されることがなくなりました。

この修正は、`ast.AssignStmt` の `Lhs` の長さが1であることと、トークンが `token.DEFINE` であることを確認することで、新しい変数の宣言と既存の変数への代入を明確に区別します。これにより、`vet` は正しくないアトミック操作のみを警告し、正当なコードに対しては沈黙するようになります。

## コアとなるコードの解説

### `src/cmd/vet/atomic.go` の変更

`checkAtomicAssignment` 関数は、`ast.AssignStmt` 型のノード（代入文）を受け取り、その中でアトミック操作の誤用がないかをチェックします。
追加された以下の3行がこのコミットの核心です。

```go
	if len(n.Lhs) == 1 && n.Tok == token.DEFINE {
		return
	}
```

- `n.Lhs` は代入文の左辺の式（例: `x` や `x, y`）のリストです。
- `len(n.Lhs) == 1` は、左辺に単一の式があることを意味します。
- `n.Tok == token.DEFINE` は、その代入文が短い変数宣言 (`:=`) であることを意味します。

この条件が真である場合、つまり「単一の新しい変数が短い変数宣言によって宣言されている」場合、`vet` はこの代入文をアトミックチェックの対象外とします。これにより、`x := atomic.AddUint64(&y, 1)` のような正当な宣言が誤って警告されることがなくなります。

### `src/cmd/vet/testdata/atomic.go` の変更

テストデータファイル `atomic.go` には、この修正が正しく機能することを確認するための新しいテストケースが追加されています。

```go
	{
		// A variable declaration creates a new variable in the current scope.
		x := atomic.AddUint64(&x, 1) // ERROR "declaration of .x. shadows declaration at testdata/atomic.go:16"

		// Re-declaration assigns a new value.
		x, w := atomic.AddUint64(&x, 1), 10 // ERROR "direct assignment to atomic value"
		_ = w
	}
```

このテストケースは、以下の2つのシナリオを検証しています。

1.  `x := atomic.AddUint64(&x, 1)`:
    - これは、外側のスコープの `x` をシャドーイングする新しい `x` を宣言しています。
    - `vet` は、この `x` が外側の `x` をシャドーイングしていることを正しく検出し、「declaration of .x. shadows declaration at testdata/atomic.go:16」という警告を発します。
    - **重要な点**: この行は、今回の修正によって「アトミック値への直接代入」としては警告されなくなります。なぜなら、`len(n.Lhs) == 1 && n.Tok == token.DEFINE` の条件に合致するため、`checkAtomicAssignment` 関数が早期リターンするからです。

2.  `x, w := atomic.AddUint64(&x, 1), 10`:
    - この行は、複数の変数を短い変数宣言で宣言しています。
    - `len(n.Lhs)` は `2` となるため、上記の早期リターン条件には合致しません。
    - `vet` は、`x` への `atomic.AddUint64(&x, 1)` の結果の代入を「direct assignment to atomic value」として正しく警告します。これは、`x` が既に存在し、その値がアトミック操作なしで直接変更されていると解釈されるためです。このケースは、`sync/atomic` の誤用として適切にフラグ付けされるべきです。

これらのテストケースは、`vet` が宣言と代入を正しく区別し、適切な警告のみを発するように修正されたことを確認するために不可欠です。

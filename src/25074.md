# [インデックス 25074] ファイルの概要

このコミットは、Go言語の `image/png` パッケージにおける、PNGデコード時の整数アンダーフローの脆弱性に対処するものです。特に32ビットシステムで発生する可能性のある、未知のチャンクの長さ処理に関する問題を修正し、悪意のあるPNGファイルによるサービス拒否攻撃を防ぎます。

## 元コミット内容

このコミットは、Go言語の `image/png` パッケージにおいて、PNG画像をデコードする際に発生する可能性のある整数アンダーフローのバグを修正します。この問題は、特に32ビットシステムで顕著であり、未知のチャンクの長さが非常に大きい値（例: `0xffffffff`）に設定された場合に発生します。この不正な長さが符号なし整数として扱われると、非常に大きな値として解釈され、メモリ割り当てや読み込みループで問題を引き起こす可能性があります。修正は、未知のチャンクの長さを `0x7fffffff` (2^31 - 1) に制限することで、このアンダーフローを防ぎます。これはPNG仕様で推奨されるチャンクの最大サイズと一致しており、正当なPNG画像には影響を与えません。

## 変更の背景

この変更は、Go issue #12687 ([https://github.com/golang/go/issues/12687](https://github.com/golang/go/issues/12687)) で報告されたバグに対応するものです。報告された問題は、悪意を持って細工されたPNGファイルが、Goの `image/png` パッケージのデコーダで整数アンダーフローを引き起こし、結果としてサービス拒否（DoS）攻撃につながる可能性を示唆していました。

具体的には、PNGファイルには「チャンク」と呼ばれるデータブロックが含まれており、それぞれがタイプと長さを持ちます。デコーダが未知のチャンクに遭遇した場合、そのチャンクの長さを読み取り、その分のデータをスキップして次のチャンクに進む必要があります。しかし、32ビットシステムで `length` 変数が符号付き整数として扱われる場合、`0xffffffff` のような値は `-1` として解釈される可能性があります。この負の値が、例えば `make([]byte, length)` のようなメモリ割り当て関数や、データを読み込むループの条件式に渡されると、予期せぬ動作（非常に大きなメモリ割り当て要求、無限ループ、クラッシュなど）を引き起こす可能性があります。

この脆弱性は、GoプログラムがPNG画像を処理する際に、悪意のある入力によって不安定になるリスクを排除するために修正が必要でした。

## 前提知識の解説

### PNG (Portable Network Graphics) 形式

PNGは、可逆圧縮を特徴とするラスターグラフィックファイル形式です。ウェブ上で広く利用されており、透明度（アルファチャンネル）をサポートします。PNGファイルは、複数の「チャンク」と呼ばれるデータブロックで構成されています。

### PNGチャンク

PNGファイルは、以下の構造を持っています。

1.  **8バイトのシグネチャ**: PNGファイルであることを識別するための固定値。
2.  **チャンク**: 複数のチャンクが連続して配置されます。各チャンクは以下の構造を持ちます。
    *   **Length (4バイト)**: チャンクのデータ部分の長さをバイト単位で示します。符号なし32ビット整数です。
    *   **Chunk Type (4バイト)**: チャンクのタイプを示すASCII文字（例: `IHDR`, `IDAT`, `IEND`）。
    *   **Chunk Data (Lengthバイト)**: チャンクの実際のデータ。
    *   **CRC (4バイト)**: チャンクタイプとチャンクデータに対するCRC-32チェックサム。

PNG仕様では、チャンクの `Length` フィールドは符号なし32ビット整数であり、その最大値は `2^31 - 1` (0x7fffffff) であることが推奨されています。これは、多くのシステムで符号付き32ビット整数として扱われる際に正の値として扱える最大値と一致します。

### 整数アンダーフロー (Integer Underflow)

整数アンダーフローは、数値演算の結果が、そのデータ型で表現できる最小値よりも小さくなる場合に発生します。特に符号なし整数では、`0` からさらに減算しようとすると、最大値にラップアラウンドすることがあります（例: `0 - 1` が `0xffffffff` になる）。

このコミットのケースでは、`length` が符号なし32ビット整数として読み込まれた後、それが符号付き整数として扱われるコンテキスト（例えば、Goの `int` 型が32ビットシステムで符号付き32ビットである場合）で利用されると問題が発生します。`0xffffffff` は符号なしでは最大値ですが、符号付き32ビット整数では `-1` と解釈されます。この負の値が、配列のサイズやループ回数として使われると、予期せぬ動作を引き起こします。

### サービス拒否 (Denial of Service, DoS)

サービス拒否攻撃は、システムやネットワークリソースを過負荷にしたり、クラッシュさせたりすることで、正当なユーザーがサービスを利用できないようにする攻撃です。このバグの場合、悪意のあるPNGファイルを処理させると、デコーダがクラッシュしたり、大量のメモリを消費したりして、アプリケーション全体の応答性を低下させる可能性があります。

## 技術的詳細

Goの `image/png` パッケージは、PNGファイルをデコードするための実装を提供します。デコード処理中に、`decoder` 構造体の `parseChunk` メソッドが各チャンクを解析します。このメソッドは、チャンクの `Length` フィールドを読み取り、その値に基づいてチャンクデータを処理します。

問題は、`length` 変数がGoの `int` 型として宣言されている場合に発生します。Goの `int` 型は、システムアーキテクチャ（32ビットまたは64ビット）に応じてサイズが異なります。32ビットシステムでは `int` は32ビットの符号付き整数として扱われます。

悪意のあるPNGファイルが、未知のチャンクに対して `Length` フィールドに `0xffffffff` (4,294,967,295) を設定した場合、32ビットシステムではこの値が符号付き `int` に変換されると `-1` として解釈されます。

`parseChunk` メソッド内で、未知のチャンクのデータをスキップするために、`length` の値を使ってループが実行されます。

```go
	// Ignore this chunk (of a known length).
	var ignored [4096]byte
	for length > 0 {
		// ...
	}
```

もし `length` が `-1` であれば、`length > 0` の条件は常に偽となり、ループは実行されません。しかし、その前に `length` の値が `io.ReadFull` や `make` などの関数に渡されると、問題が発生します。特に、`io.ReadFull` は読み込むバイト数として負の値を受け取るとエラーを返すか、予期せぬ動作をする可能性があります。また、`make([]byte, length)` のように負の長さでスライスを作成しようとすると、パニックを引き起こす可能性があります。

このコミットでは、`parseChunk` メソッドに `length` の値が `0x7fffffff` (2^31 - 1) を超える場合にエラーを返すチェックを追加することで、この問題を解決しています。`0x7fffffff` は、符号付き32ビット整数で表現できる最大正の値です。PNG仕様の推奨に従うことで、正当なPNGファイルがこのチェックによって拒否されることはありません。

## コアとなるコードの解説

### `src/image/png/reader.go` の変更

`func (d *decoder) parseChunk() error` メソッドは、PNGファイルの各チャンクを解析する主要なロジックを含んでいます。このメソッドは、チャンクタイプを識別し、それに応じて適切なパーサーを呼び出します。

追加されたコード `if length > 0x7fffffff` は、チャンクの `length` フィールドが `0x7fffffff` (2,147,483,647) を超える場合に、`FormatError` を返してデコード処理を中断します。

*   `0x7fffffff` は、符号付き32ビット整数で表現できる最大値です。
*   このチェックにより、`length` が `0xffffffff` のような値（32ビットシステムで符号付き `int` として `-1` と解釈される可能性がある値）になることを防ぎます。
*   PNG仕様では、チャンクの長さは `2^31 - 1` を超えないことが推奨されているため、この制限は仕様に準拠しており、正当なPNGファイルには影響を与えません。
*   `FormatError` を返すことで、不正なPNGファイルが検出されたことを明確に示し、それ以上の処理を停止させ、潜在的な脆弱性の悪用を防ぎます。

### `src/image/png/reader_test.go` の変更

`TestUnknownChunkLengthUnderflow` という新しいテスト関数が追加されました。

*   このテストは、悪意を持って細工されたPNGデータ (`data` 変数に定義されているバイト列) を作成します。このデータには、未知のチャンクの長さとして `0xffffffff` が含まれています。
*   `Decode(bytes.NewReader(data))` を呼び出して、この不正なデータをデコードしようとします。
*   `if err == nil` の条件は、デコードがエラーなしで成功した場合に真となります。
*   `t.Errorf("Didn't fail reading an unknown chunk with length 0xffffffff")` は、デコードがエラーを返さなかった場合にテストを失敗させます。これは、修正が正しく機能し、不正な長さのチャンクがエラーとして検出されることを期待しているためです。

このテストケースは、修正が意図した通りに機能し、整数アンダーフローの脆弱性が適切に処理されることを保証します。

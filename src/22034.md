## 変更の背景

このコミットは、Go 1.5リリースで導入された画期的なガベージコレクタ（GC）の改善に関連しています。Go 1.5では、従来の「Stop-the-World (STW)」方式から、並行マーク・アンド・スイープ方式へと移行し、GCによるアプリケーションの一時停止時間を大幅に削減することを目指しました。

コミットメッセージにある「reorganization CL」とは、GoランタイムのGC関連コードの大規模な再編成を指しています。このような大規模な変更作業中に、特定の修正が見落とされたり、誤って削除されたりすることは珍しくありません。このコミットは、Russ Cox氏が自身の変更リスト（CL）を準備する際に、Austin Clements氏による重要な変更を誤って削除してしまったことに対する修正です。コミットメッセージの「I blame Git.」というユーモラスな表現は、このような複雑なコードベースの管理における課題を示唆しています。

この修正は、並行GCのマークフェーズが正しく機能し、GC作業が効率的に処理され、リソースが適切に解放されることを保証するために不可欠でした。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション、特にGo 1.5で導入された並行GCの概念を理解する必要があります。

*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリ領域を自動的に解放するプロセスです。GoのGCは、開発者が手動でメモリを管理する手間を省き、メモリリークのリスクを低減します。
*   **並行マーク・アンド・スイープGC**: Go 1.5で導入されたGCアルゴリズムです。
    *   **並行 (Concurrent)**: GCの大部分の作業（特にマークフェーズ）が、ユーザープログラムの実行と並行して行われます。これにより、アプリケーションの一時停止時間（STW）が大幅に短縮されます。
    *   **マークフェーズ (Mark Phase)**: GCがヒープ上のオブジェクトを走査し、到達可能な（使用中の）オブジェクトを「マーク」する段階です。到達不可能なオブジェクトは「マークされない」ままになります。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクトが占めるメモリ領域を解放する段階です。
*   **トライカラーマーキング (Tri-color Marking)**: 並行GCでオブジェクトの状態を管理するために使用される概念です。
    *   **白 (White)**: まだGCによって走査されていないオブジェクト、または到達不可能と見なされるオブジェクト。最終的に解放される候補です。
    *   **灰 (Gray)**: 到達可能とマークされたが、その参照先がまだ走査されていないオブジェクト。
    *   **黒 (Black)**: 到達可能とマークされ、その参照先もすべて走査されたオブジェクト。
*   **ライトバリア (Write Barrier)**: 並行マークフェーズ中にユーザープログラムがポインタを変更する際に、GCがメモリグラフの一貫性を維持するためのメカニズムです。これにより、GCがオブジェクトをマークしている間に、ユーザープログラムがオブジェクトの参照を変更しても、GCが誤って到達可能なオブジェクトを解放してしまうことを防ぎます。
*   **`gcDrain`**: Goランタイム内部の関数で、GCのマーク作業を処理するために使用されます。これは、GCワーカーがマークキューからオブジェクトを取り出し、その参照を走査してマークするプロセスを管理します。
*   **`gcWork`**: GC作業のバッファと状態を管理するための構造体です。GCワーカーは`gcWork`インスタンスを使用して、マークすべきオブジェクトのキューを管理し、作業のバランスを取ります。`gcWork`は、GCワーカー間で作業を効率的に共有するためのメカニズムを提供します。`dispose()`メソッドは、`gcWork`インスタンスが使用していたリソース（例えば、内部バッファ）を解放するために呼び出されます。

## 技術的詳細

このコミットの技術的な核心は、`gcmark_m`関数における`gcDrain`の呼び出し方法の変更にあります。

Go 1.5の並行GCでは、`gcmark_m`関数は並行マークフェーズの主要なエントリポイントの一つです。このフェーズでは、複数のGCワーカーゴルーチンが協調してヒープを走査し、到達可能なオブジェクトをマークします。

変更前のコードでは、`gcDrain(nil)`が呼び出されていました。これは、`gcDrain`関数に`nil`（ヌル）の`gcWork`ポインタを渡すことを意味します。この場合、`gcDrain`は内部的に一時的な`gcWork`インスタンスを作成して使用しますが、そのインスタンスが明示的に破棄されることはありませんでした。これは、リソースリークや、GC作業の完了状態の不正確な追跡につながる可能性がありました。

変更後のコードでは、以下のようになっています。

```go
    var gcw gcWork
    gcDrain(&gcw)
    gcw.dispose()
```

この変更により、以下の点が改善されます。

1.  **明示的な`gcWork`インスタンスの利用**: `gcw`という`gcWork`型の変数を明示的に宣言し、そのアドレスを`gcDrain`に渡しています。これにより、`gcDrain`は特定の`gcWork`インスタンスを使用してGC作業を実行します。
2.  **リソースの適切な解放**: `gcDrain(&gcw)`の呼び出し後、`gcw.dispose()`が呼び出されます。`dispose()`メソッドは、`gcWork`インスタンスが内部的に保持していたリソース（例えば、マーク作業用のバッファ）を適切に解放します。これは、GCの効率性と安定性を確保するために非常に重要です。リソースが解放されないと、メモリ使用量が増加したり、GCの次のサイクルで問題が発生したりする可能性があります。

この修正は、並行GCのマークフェーズが終了した際に、使用された`gcWork`バッファが確実にクリーンアップされるようにするために不可欠でした。これにより、GCの健全性が保たれ、潜在的なメモリリークやGCの動作不良が防止されます。

## コアとなるコードの解説

変更されたコードは、`src/runtime/mgc.go`内の`gcmark_m`関数です。この関数は、Goランタイムの並行マークフェーズを実行する主要な部分です。

*   **変更前**:
    ```go
    func gcmark_m() {
    	gcDrain(nil)
    ```
    ここでは、`gcDrain`関数が`nil`引数で呼び出されていました。これは、`gcDrain`が内部で一時的な`gcWork`オブジェクトを生成して使用することを意味します。しかし、この一時オブジェクトが使用後に適切にクリーンアップされる保証がありませんでした。

*   **変更後**:
    ```go
    func gcmark_m() {
    	var gcw gcWork
    	gcDrain(&gcw)
    	gcw.dispose()
    ```
    1.  `var gcw gcWork`: `gcWork`型のローカル変数`gcw`を宣言します。これにより、GC作業を管理するための専用のワークキューインスタンスが作成されます。
    2.  `gcDrain(&gcw)`: `gcDrain`関数に、新しく作成した`gcw`インスタンスへのポインタを渡します。`gcDrain`はこの`gcw`インスタンスを使用して、マーク作業（オブジェクトの走査とマーク）を実行します。
    3.  `gcw.dispose()`: `gcDrain`の呼び出しが完了した後、`gcw`インスタンスの`dispose()`メソッドを呼び出します。このメソッドは、`gcw`が内部的に保持していたすべてのリソース（例えば、マーク作業中に使用されたバッファなど）を解放し、クリーンアップします。これにより、リソースリークを防ぎ、GCの次のサイクルに向けてシステムをクリーンな状態に保ちます。

この変更は、GCのマークフェーズが終了した際に、使用された`gcWork`バッファが確実にクリーンアップされるようにするために不可欠でした。これにより、GCの健全性が保たれ、潜在的なメモリリークやGCの動作不良が防止されます。

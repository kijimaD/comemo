## 変更の背景

このコミットは、主に以下の2つの問題意識から生まれました。

1.  **Issue #14409の解決**:
    Goの脱出解析は、変数がスタックに割り当てられるかヒープに割り当てられるかを決定する重要な最適化です。スタック割り当てはヒープ割り当てよりも高速であるため、正確な脱出解析はプログラムのパフォーマンスに直結します。Issue #14409では、クロージャがキャプチャした変数の一部が、コンパイラによってスタックに留まると誤って判断され、実際にはヒープにエスケープしてしまうケースが報告されました。これにより、不必要なヒープアロケーションが発生し、ガベージコレクションの負荷が増大する可能性がありました。このコミットは、この特定のケースを修正し、脱出解析の精度を向上させることを目的としています。

2.  **Windowsランタイムの堅牢性と保守性の向上**:
    Windows環境におけるGoランタイムは、OSのAPIを呼び出すために`kernel32.dll`などのシステムライブラリをロードします。このロード処理は、ランタイムの初期化において非常に重要です。以前の実装では、`kernel32.dll`のロードに失敗した場合のハンドリングが不十分であったり、特定のポインタ操作が「技術的なエスケープ」として認識され、コードの意図が不明瞭になる可能性がありました。このコミットは、これらの問題を解決し、Windowsランタイムの堅牢性を高め、コードの保守性を向上させることを目指しています。

## 前提知識の解説

### 1. Goの脱出解析 (Escape Analysis)

Goコンパイラの重要な最適化の一つに「脱出解析（Escape Analysis）」があります。これは、変数がプログラムの実行中にどこに割り当てられるべきかを決定するプロセスです。

*   **スタック割り当て**: 関数内で宣言され、その関数の実行が終了すると不要になる変数は、通常、スタックに割り当てられます。スタック割り当ては非常に高速で、ガベージコレクションの対象外です。
*   **ヒープ割り当て**: 変数が関数のスコープを超えて存続する必要がある場合（例: ポインタが関数から返される、グローバル変数に代入されるなど）、その変数はヒープに割り当てられます。ヒープ割り当てはスタック割り当てよりも遅く、ガベージコレクションの対象となります。

脱出解析は、変数が「エスケープする」（関数のスコープを超えて存続する必要がある）かどうかを判断し、適切なメモリ領域に割り当てます。不正確な脱出解析は、不必要なヒープ割り当てを引き起こし、ガベージコレクションの頻度を増やし、プログラムのパフォーマンスを低下させる可能性があります。

### 2. Goのクロージャ (Closures)

Goのクロージャは、関数が自身の外側のスコープにある変数を参照できる機能です。クロージャがキャプチャした変数は、クロージャが実行される間、そのライフタイムが延長されます。このため、クロージャがキャプチャした変数がヒープにエスケープするかどうかは、脱出解析にとって複雑な問題となります。

### 3. `OCALLFUNC`と`indirect`な呼び出し

Goコンパイラの内部では、関数の呼び出しは様々な種類に分類されます。
*   `OCALLFUNC`: 関数呼び出しを表すノードタイプの一つです。
*   `indirect`: 間接的な関数呼び出しを指します。これは、関数ポインタやインターフェースメソッドを通じて関数が呼び出される場合などです。

このコミットで問題となったのは、`OCALLFUNC`かつ`indirect`なクロージャ呼び出しの特定の組み合わせでした。

### 4. Windows APIと`kernel32.dll`

Windowsオペレーティングシステムでは、多くのシステム機能がダイナミックリンクライブラリ（DLL）として提供されています。`kernel32.dll`は、メモリ管理、プロセスとスレッドの管理、ファイルI/Oなど、Windowsのコア機能を提供する非常に重要なDLLです。Goのランタイムは、Windows上で動作するために、この`kernel32.dll`から必要な関数（例: `LoadLibraryA`, `GetProcAddress`など）をロードして使用します。

### 5. `unsafe.Pointer`と技術的なエスケープ

Goの`unsafe.Pointer`は、任意の型のポインタを保持できる特殊な型で、型安全性をバイパスしてメモリを直接操作することを可能にします。これは、C言語との相互運用や、特定の低レベルな最適化に必要ですが、誤用するとメモリ安全性の問題を引き起こす可能性があります。
「技術的なエスケープ」とは、`unsafe.Pointer`などの低レベルな操作によって、コンパイラが追跡できない形でポインタが移動し、結果的にヒープにエスケープしてしまうような状況を指します。これは、コードの意図を不明瞭にし、将来的な最適化を妨げる可能性があります。

## 技術的詳細

### 1. `cmd/compile/internal/gc/esc.go`における脱出解析の修正

このコミットの主要な変更点の一つは、Goコンパイラの脱出解析ロジック、特に`src/cmd/compile/internal/gc/esc.go`ファイル内の`esccall`関数に対する修正です。

`esccall`関数は、関数呼び出しの引数や戻り値がエスケープするかどうかを分析します。以前の実装では、`OCALLFUNC`（関数呼び出し）かつ`indirect`（間接呼び出し、例えば関数ポインタを介した呼び出し）であるクロージャ呼び出しにおいて、キャプチャされた変数の一部がヒープにエスケープするケースが適切に処理されていませんでした。

具体的には、以下のコードが追加されました。

```go
		} else { // indirect and OCALLFUNC = could be captured variables, too. (#14409)
			ll := e.nodeEscState(n).Escretval.Slice()
			for _, llN := range ll {
				escassignDereference(e, llN, fn, e.stepAssign(nil, llN, fn, "captured by called closure"))
			}
		}
```

このコードブロックは、間接的なクロージャ呼び出しの場合に実行されます。
*   `e.nodeEscState(n).Escretval.Slice()`: 呼び出し`n`の戻り値のエスケープ状態から、関連するノードのリストを取得します。
*   `for _, llN := range ll`: 取得した各ノード`llN`についてループします。
*   `escassignDereference(e, llN, fn, e.stepAssign(nil, llN, fn, "captured by called closure"))`: `escassignDereference`関数を呼び出し、`llN`が参照外しによってエスケープする可能性があることをコンパイラに通知します。`e.stepAssign`は、`llN`が`fn`（呼び出されたクロージャ）によって「キャプチャされた」ことによるエスケープステップを生成します。

この修正により、コンパイラは間接的なクロージャ呼び出しでキャプチャされた変数の部分的なエスケープを正しく認識し、必要に応じてヒープに割り当てるようになります。これにより、Issue #14409で報告されたような、不正確な脱出解析によるバグやパフォーマンス低下が防止されます。

### 2. `src/runtime/os1_windows.go`におけるWindowsランタイムの改善

もう一つの変更は、Windows固有のランタイムコードである`src/runtime/os1_windows.go`における改善です。

以前の実装では、`kernel32.dll`をロードし、そこから必要な関数ポインタを取得する際に、一時的なバイト配列`buf`と`strtoptr`ヘルパー関数を使用していました。

```go
// 変更前
var buf [50]byte // large enough for longest string
strtoptr := func(s string) uintptr {
    buf[copy(buf[:], s)] = 0 // nil-terminated for OS
    return uintptr(noescape(unsafe.Pointer(&buf[0])))
}
l := stdcall1(_LoadLibraryA, strtoptr("kernel32.dll"))
// ...
```

このアプローチは、文字列を`uintptr`に変換するために一時的なバッファを使用しており、`noescape`や`unsafe.Pointer`が関与するため、コードの意図が不明瞭になりがちでした。また、`kernel32.dll`のロードに失敗した場合の処理も改善の余地がありました。

このコミットでは、以下の変更が行われました。

*   **バイトスライスによる文字列定義**:
    `kernel32.dll`やAPI関数名を表す文字列を、`[]byte`スライスとして直接定義するようになりました。これにより、一時的なバッファ`buf`が不要になり、文字列の扱いがより明確になります。

    ```go
    // 変更後
    var (
        kernel32dll                 = []byte("kernel32.dll\x00")
        addVectoredContinueHandler  = []byte("AddVectoredContinueHandler\x00")
        // ...
    )
    ```
    `\x00`はCスタイルのヌル終端文字列を表現するために追加されています。

*   **`windowsFindfunc`ヘルパー関数の導入**:
    `GetProcAddress`を呼び出すロジックを`windowsFindfunc`という新しいヘルパー関数にカプセル化しました。これにより、コードの重複が減り、可読性が向上します。

    ```go
    func windowsFindfunc(name []byte, lib uintptr) stdFunction {
        f := stdcall2(_GetProcAddress, lib, uintptr(unsafe.Pointer(&name[0])))
        return stdFunction(unsafe.Pointer(f))
    }
    ```

*   **`kernel32.dll`ロード失敗時の厳密なエラーハンドリング**:
    `kernel32.dll`のロードに失敗した場合（`k32 == 0`）、以前は単に`if l != 0`で処理をスキップしていましたが、このコミットでは`throw("kernel32.dll not found")`を呼び出してランタイムパニックを発生させるようになりました。`kernel32.dll`はGoランタイムにとって必須のDLLであるため、そのロード失敗は回復不能なエラーと見なされ、早期にプログラムを終了させることで、より堅牢な動作を保証します。

    ```go
    k32 := stdcall1(_LoadLibraryA, uintptr(unsafe.Pointer(&kernel32dll[0])))
    if k32 == 0 {
        throw("kernel32.dll not found")
    }
    ```

これらの変更により、Windowsランタイムの初期化コードはよりクリーンになり、`unsafe.Pointer`の使用がより意図的で明確なものとなり、`kernel32.dll`のロード失敗に対するエラーハンドリングが強化されました。

## コアとなるコードの解説

### 1. `src/cmd/compile/internal/gc/esc.go`の変更

この変更は、Goコンパイラの脱出解析器が、特定のクロージャ呼び出しパターンでキャプチャされた変数のエスケープを正しく検出できるようにするためのものです。

*   **`OCALLFUNC && indirect`のケース**: `esccall`関数は、関数呼び出しノード`n`を分析します。`n.Op == OCALLFUNC`は関数呼び出しであることを示し、`n.Func.Op == OINDREG`または`n.Func.Op == OIND`は間接呼び出し（レジスタまたはメモリを介した関数ポインタによる呼び出し）であることを示します。この組み合わせは、クロージャが関数ポインタとして渡され、間接的に呼び出されるシナリオをカバーします。
*   **`Escretval`と`escassignDereference`**: `e.nodeEscState(n).Escretval`は、呼び出し`n`の戻り値のエスケープ状態を表します。`Slice()`メソッドは、この状態から関連するノードのリストを取得します。`escassignDereference`関数は、ポインタの参照外し操作がエスケープを引き起こす可能性があることを脱出解析器に伝えます。
*   **`"captured by called closure"`**: `e.stepAssign`で生成されるエスケープステップの理由として「captured by called closure」（呼び出されたクロージャによってキャプチャされた）が明示されています。これは、このエスケープがクロージャのキャプチャメカニズムに起因することを明確に示しています。

この修正により、コンパイラは、クロージャが間接的に呼び出される際に、そのクロージャがキャプチャした変数の一部がヒープにエスケープする可能性を正確に認識し、適切なメモリ割り当てを行うことができるようになります。これにより、不必要なヒープアロケーションが削減され、ガベージコレクションの効率が向上し、結果としてプログラムのパフォーマンスが改善されます。

### 2. `src/runtime/os1_windows.go`の変更

この変更は、Windows環境におけるGoランタイムの初期化処理、特にシステムDLLのロードに関する堅牢性とコードの明確性を向上させるものです。

*   **文字列リテラルのバイトスライス化**: 以前は`strtoptr`というヘルパー関数と一時的な`buf`配列を使用して、Goの文字列をCスタイルのヌル終端バイト配列に変換していました。新しいコードでは、`kernel32dll`などの文字列を直接`[]byte`スライスとして定義し、末尾に`\x00`（ヌル文字）を追加することで、Cスタイルの文字列として扱えるようにしています。これにより、`strtoptr`関数と`buf`配列が不要になり、コードが簡潔かつ明確になりました。
*   **`windowsFindfunc`の導入**: `_GetProcAddress`を呼び出してDLLから関数ポインタを取得するロジックが`windowsFindfunc`という専用のヘルパー関数にまとめられました。これにより、コードの重複が排除され、`loadOptionalSyscalls`関数の可読性が向上しています。
*   **`kernel32.dll`ロード失敗時の`throw`**: `_LoadLibraryA`を呼び出して`kernel32.dll`をロードする際に、戻り値`k32`が`0`（ロード失敗）の場合、以前は単に処理をスキップしていましたが、新しいコードでは`throw("kernel32.dll not found")`を呼び出しています。`throw`はGoランタイムの内部関数で、回復不能なエラーが発生した場合にパニックを引き起こします。`kernel32.dll`はWindows上でGoランタイムが動作するために不可欠なDLLであるため、そのロード失敗は致命的なエラーと見なされ、プログラムを即座に終了させることで、未定義の動作を防ぎ、デバッグを容易にします。

これらの変更は、Windowsランタイムの初期化コードをより堅牢にし、エラーハンドリングを改善し、`unsafe.Pointer`などの低レベルな操作の意図をより明確にすることで、コードの保守性を高めています。

### 3. `test/escape_closure.go`の変更

このファイルには、脱出解析の修正を検証するための新しいテストケースが追加されています。`ClosureLeak1`, `ClosureLeak1a`, `ClosureLeak2`, `ClosureLeak2a`, `ClosureLeak2b`といった関数が追加され、クロージャがキャプチャした変数がどのようにエスケープするかをテストしています。

*   `// ERROR "..."`コメントは、コンパイラが特定の変数や式がヒープにエスケープすると正しく診断することを期待していることを示します。
*   特に`ClosureLeak1a`と`ClosureLeak2a`では、可変長引数（`...string`）として渡されたスライスの一部がクロージャによってキャプチャされ、それが最終的に関数の戻り値として「リーク」する（エスケープする）ケースを検証しています。これは、Issue #14409で指摘された問題の具体的なシナリオを再現し、修正が正しく機能していることを確認するためのものです。

これらのテストケースは、コンパイラの脱出解析がクロージャとキャプチャされた変数に関する複雑なシナリオを正確に処理できるようになったことを保証します。

# [インデックス 28093] ファイルの概要

このコミットは、Goコンパイラのエクスポートデータにおける位置情報（ファイル名と行番号）のエンコーディング方法を最適化するものです。特にファイル名のエンコーディングにデルタエンコーディングを導入することで、エクスポートデータの全体サイズを削減し、コンパイル時のパフォーマンス向上に寄与します。

## 元コミット内容

Goコンパイラ（`cmd/compile`）において、エクスポートデータ内の位置情報（ファイル名）にデルタエンコーディングを適用する変更です。これにより、特にファイルパスが長い場合や多数のファイルが関与するパッケージにおいて、エクスポートデータのサイズが大幅に削減されます（一部のパッケージで15%〜25%、平均で約2%）。

## 変更の背景

Goコンパイラは、パッケージのコンパイル結果を他のパッケージが利用できるように「エクスポートデータ」として出力します。このエクスポートデータには、型情報、関数シグネチャ、変数定義などのメタデータに加え、それらがソースコードのどの位置（ファイル名と行番号）で定義されているかを示す位置情報が含まれます。

従来のエクスポートデータにおけるファイル名のエンコーディングは、ファイルパス全体をそのまま記録する方式でした。しかし、現代のソフトウェア開発では、プロジェクトのディレクトリ構造が深く、ファイルパスが長くなる傾向があります。また、大規模なパッケージでは多くのファイルが関与するため、エクスポートデータ内のファイル名情報が肥大化し、結果としてエクスポートデータ全体のサイズが増大するという問題がありました。

エクスポートデータのサイズ増大は、以下のような悪影響を及ぼします。

1.  **コンパイル時間の増加:** エクスポートデータの読み書きに時間がかかり、コンパイル速度が低下する可能性があります。
2.  **ディスク使用量の増加:** ビルドキャッシュや中間ファイルとして保存されるエクスポートデータがディスクスペースを消費します。
3.  **ネットワーク転送量の増加:** 分散ビルドシステムやCI/CD環境において、エクスポートデータの転送に時間がかかり、帯域幅を消費します。

このコミットは、これらの問題を解決するために、ファイル名のエンコーディングをより効率的なデルタエンコーディングに切り替えることで、エクスポートデータのサイズを削減し、コンパイラの全体的な効率を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラであり、Goのソースコードを機械語に変換する役割を担います。コンパイルプロセス中に、各パッケージの公開された（エクスポートされた）要素に関するメタデータを生成し、これを「エクスポートデータ」として出力します。他のパッケージがこのパッケージを利用する際には、このエクスポートデータを読み込んで型チェックやシンボル解決を行います。

### エクスポートデータ (Export Data)

Goコンパイラが生成するバイナリ形式のメタデータです。Goのパッケージシステムにおいて、あるパッケージが別のパッケージの公開された型、関数、変数などを参照する際に必要となります。エクスポートデータには、以下のような情報が含まれます。

*   パッケージ名
*   エクスポートされた型定義（構造体、インターフェースなど）
*   エクスポートされた関数やメソッドのシグネチャ
*   エクスポートされた変数や定数の定義
*   これら各要素がソースコードのどこで定義されているかを示す「位置情報」（ファイル名と行番号）

このデータは、通常、コンパイル済みパッケージの `.a` ファイル（アーカイブファイル）内に埋め込まれるか、中間ファイルとして生成されます。

### 位置情報 (Position Information)

ソースコード内の特定の構文要素（変数、関数、型など）が、どのソースファイル（ファイル名）のどの行番号で定義されているかを示す情報です。この情報は、主に以下の目的で利用されます。

*   **エラー報告:** コンパイルエラーや実行時エラーが発生した際に、正確なエラー発生箇所をユーザーに伝えるため。
*   **デバッグ:** デバッガがソースコードと実行中のプログラムの状態を関連付けるため。
*   **ツールサポート:** IDEやコードエディタが、定義へのジャンプ、リファクタリング、コード補完などの機能を提供するため。

位置情報は、Goコンパイラのエクスポートデータに不可欠な要素ですが、その表現形式が効率的でない場合、エクスポートデータ全体のサイズに大きな影響を与えます。

### デルタエンコーディング (Delta Encoding)

データ圧縮技術の一つで、連続するデータ要素間の「差分」（デルタ）を記録することで、データ量を削減します。特に、データが連続して出現し、かつ隣接する要素間で大きな変化がない場合に非常に効果的です。

例えば、ファイルパスの場合、同じディレクトリ内の複数のファイルは共通のプレフィックス（ディレクトリパス）を持つことがよくあります。
`"/home/user/project/src/package/file1.go"`
`"/home/user/project/src/package/file2.go"`
これらのパスをそれぞれ完全に記録する代わりに、最初のパスを記録し、2番目のパスについては「最初のパスと共通のプレフィックスがここまであり、残りの部分が `file2.go` である」という差分情報だけを記録することで、大幅なデータ削減が期待できます。

### `bexport.go` と `bimport.go`

これらはGoコンパイラ (`cmd/compile`) の内部パッケージにあるファイルで、それぞれバイナリ形式のエクスポートデータ生成（`bexport.go`）と、その読み込み（`bimport.go`）を司っています。
`bexport.go` は、Goのソースコードを解析して得られたAST（抽象構文木）や型情報から、バイナリ形式のエクスポートデータをシリアライズするロジックを含みます。
`bimport.go` は、そのバイナリ形式のエクスポートデータを読み込み、Goコンパイラが利用できる内部データ構造にデシリアライズするロジックを含みます。
このコミットでは、位置情報のエンコーディング/デコーディングロジックがこれらのファイルで変更されています。また、`src/go/internal/gcimporter/bimport.go` も同様に、エクスポートデータのインポート処理に関連する変更を受けています。

## 技術的詳細

このコミットの核心は、エクスポートデータに書き込まれるファイル名の冗長性を排除するために、デルタエンコーディングを導入した点にあります。

### 従来のエンコーディングの問題点

以前は、位置情報としてファイル名と行番号を記録する際、ファイル名が変更されるたびにその完全なパス文字列をエクスポートデータに書き込んでいました。Goのソースファイルは通常、同じディレクトリ内に複数存在し、その結果、多くのファイルが共通のディレクトリパスプレフィックスを持つことになります。例えば、`src/cmd/compile/internal/amd64/` ディレクトリ内の複数のファイルの位置情報を記録する場合、毎回 `src/cmd/compile/internal/amd64/` という共通のプレフィックスが繰り返し書き込まれていました。これは特に、深いディレクトリ構造を持つプロジェクトや、多数のソースファイルからなるパッケージにおいて、エクスポートデータのサイズを不必要に増大させていました。

### デルタエンコーディングによる解決策

このコミットでは、ファイル名のエンコーディングに以下のロジックを適用します。

1.  **行番号のみの変更:** 現在処理している位置情報が、直前の位置情報と同じファイル名であり、行番号のみが変更されている場合、行番号の差分（デルタ）のみを記録します。これは最も頻繁に発生するケースであり、非常に効率的です。
2.  **ファイル名の変更:** 現在処理している位置情報が、直前の位置情報と異なるファイル名を持つ場合、以下の手順でエンコードします。
    *   直前のファイル名と現在のファイル名との間で、共通するプレフィックスの長さを計算します（例: `commonPrefixLen` 関数）。
    *   この共通プレフィックスの長さ `n` を整数として記録します。
    *   現在のファイル名から共通プレフィックスを除いた残りのサフィックス部分のみを文字列として記録します。
    *   これにより、ファイルパス全体を記録する代わりに、共通部分の長さと、変化したわずかなサフィックス部分のみを記録すればよくなります。
    *   エンコード後、現在のファイル名を `p.prevFile` として保存し、次の比較に備えます。

### 具体的な効果

コミットメッセージに示されているように、この変更によりエクスポートデータのサイズが大幅に削減されました。

*   `cmd/compile/internal/amd64` のような一部のパッケージでは、最大27%もの削減が見られます。これは、これらのパッケージが多くのファイルを含み、かつファイルパスが比較的長い場合に特に効果を発揮したことを示唆しています。
*   全体的なパッケージでは平均2%の削減ですが、これは「ほとんど増加なし」という条件で達成されており、非常に効率的な最適化と言えます。

この最適化は、Goコンパイラの内部処理の効率化に貢献し、結果としてGoプログラムのビルド時間を短縮する効果が期待できます。

## コアとなるコードの変更箇所

このコミットで主に変更されたファイルは以下の通りです。

*   `src/cmd/compile/internal/gc/bexport.go`: エクスポートデータを生成する側のロジック。ファイル名のデルタエンコーディングの実装が含まれます。
*   `src/cmd/compile/internal/gc/bimport.go`: エクスポートデータを読み込む側のロジック。ファイル名のデルタデコーディングの実装が含まれます。
*   `src/go/internal/gcimporter/bimport.go`: `go/importer` パッケージが `gc` 形式のエクスポートデータを読み込むためのロジック。こちらもデコーディングの変更が反映されています。

特に重要な変更は、`bexport.go` の `(*exporter).pos` メソッドと、新しく追加されたヘルパー関数 `commonPrefixLen` です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/bexport.go` の変更

`(*exporter).pos(n *Node)` メソッドは、ASTノード `n` の位置情報（ファイル名と行番号）をエクスポートデータに書き込む役割を担います。

変更前は、ファイル名が異なる場合、常に新しいファイル名全体を書き込んでいました。
変更後は、以下のロジックが導入されました。

```go
func (p *exporter) pos(n *Node) {
	// ... (省略) ...

	file, line := fileLine(n) // 現在のファイル名と行番号を取得
	if file == p.prevFile {
		// 共通ケース: ファイル名が同じ場合、行番号の差分のみを書き込む
		delta := line - p.prevLine
		p.int(delta) // 差分をエンコード
		if delta == 0 {
			p.int(-1) // 行番号も同じ場合は、ファイル変更なしを示す特殊な-1を書き込む
		}
	} else {
		// ファイル名が異なる場合
		p.int(0) // ファイル名が変更されたことを示す0を書き込む
		// 直前のファイル名と現在のファイル名の共通プレフィックス長を計算
		n := commonPrefixLen(p.prevFile, file)
		p.int(n)           // 共通プレフィックス長をエンコード
		p.string(file[n:]) // 共通プレフィックスを除いたサフィックス部分をエンコード
		p.prevFile = file  // 現在のファイル名を次の比較のために保存
		p.int(line)        // 行番号をエンコード
	}
	p.prevLine = line // 現在の行番号を次の比較のために保存
}

// commonPrefixLen は2つの文字列の共通プレフィックスの長さを返すヘルパー関数
func commonPrefixLen(a, b string) int {
	if len(a) > len(b) {
		a, b = b, a
	}
	// len(a) <= len(b)
	i := 0
	for i < len(a) && a[i] == b[i] {
		i++
	}
	return i
}
```

この変更により、ファイル名が同じ場合は行番号のデルタのみ、ファイル名が異なる場合でも共通プレフィックスの長さとサフィックスのみを記録することで、データ量を大幅に削減しています。

### `src/cmd/compile/internal/gc/bimport.go` および `src/go/internal/gcimporter/bimport.go` の変更

`(*importer).pos()` メソッドは、エクスポートデータから位置情報を読み込む役割を担います。エンコーディングの変更に合わせて、デコーディングロジックも更新されています。

```go
func (p *importer) pos() {
	file := p.prevFile
	line := p.prevLine

	if delta := p.int(); delta != 0 {
		// 行番号が変更されたケース
		line += delta
	} else if n := p.int(); n >= 0 {
		// ファイル名が変更されたケース
		// 共通プレフィックス長 n とサフィックスを読み込み、ファイル名を再構築
		file = p.prevFile[:n] + p.string()
		p.prevFile = file // 次のデコードのために現在のファイル名を保存
		line = p.int()    // 行番号を読み込む
	}
	p.prevLine = line // 次のデコードのために現在の行番号を保存
}
```

デコーディングロジックは、エンコーディングロジックと対称的です。まず整数値を読み込み、それが0でなければ行番号のデルタとして扱います。0であればファイル名が変更されたと判断し、次に読み込んだ整数値 `n` を共通プレフィックス長として利用し、その後に続く文字列（サフィックス）と組み合わせて元のファイル名を復元します。

これらの変更により、エクスポートデータのサイズ削減という目標が達成され、Goコンパイラの効率が向上しました。

# [インデックス 20497] ファイルの概要

このコミットは、Goコンパイラ（`cmd/cc`, `cmd/gc`）が`argsize` PCDATA（Program Counter Data）の生成を停止し、関連するランタイムコードを削除するものです。`argsize` PCDATAは、かつてガベージコレクタが関数呼び出しの引数サイズを特定するために使用していましたが、Goランタイムの進化によりその必要がなくなりました。

## コミット

Author: Russ Cox <rsc@golang.org>
Date:   Fri Sep 12 07:51:00 2014 -0400

    cmd/cc, cmd/gc: stop generating 'argsize' PCDATA
    
    The argsize PCDATA was specifying the number of
    bytes passed to a function call, so that if the function
    did not specify its argument count, the garbage collector
    could use the call site information to scan those bytes
    conservatively. We don't do that anymore, so stop
    generating the information.

## 元コミット内容

`cmd/cc`, `cmd/gc`: 'argsize' PCDATAの生成を停止

`argsize` PCDATAは、関数呼び出しに渡されるバイト数を指定していました。これは、関数が引数の数を指定しない場合に、ガベージコレクタが呼び出しサイトの情報を使用してそれらのバイトを保守的にスキャンできるようにするためでした。私たちはもはやそのようにしないため、この情報の生成を停止します。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）戦略の進化があります。初期のGoバージョン（例: Go 1.0）では、特にゴルーチンのスタックをスキャンする際に「保守的（conservative）」なGCアプローチが採用されていました。保守的なGCでは、スタック上のすべての値をポインタの可能性があるものとして扱います。これにより、非ポインタ値が有効なメモリアドレスに似ている場合に「不要な保持（unwanted retention）」、つまりメモリリークが発生する可能性がありました。

`PCDATA_ArgSize`は、このような保守的なスキャンを支援するためのメタデータでした。関数が引数の数を明示的に指定しない場合、GCは`PCDATA_ArgSize`が提供する呼び出しサイトの情報を利用して、引数領域を保守的にスキャンし、ポインタを特定しようとしました。

しかし、GoのGCはGo 1.1で「ほぼ正確（mostly precise）」になり、Go 1.3/1.4以降では「完全に正確（fully precise）」へと進化しました。完全に正確なGCは、ポインタと非ポインタを正確に区別できるため、偶発的なメモリ保持を防ぐことができます。この進化に伴い、コンパイラとランタイムは、関数引数のサイズをより正確に、かつ保守的なスキャンに依存せずに決定できるようになりました。その結果、`PCDATA_ArgSize`の必要性がなくなり、その生成を停止し、関連コードを削除することが決定されました。これは、GCの精度向上とランタイムの簡素化を目的とした変更です。

## 前提知識の解説

*   **ガベージコレクション (GC)**: プログラムが動的に割り当てたメモリのうち、もはや使用されていない（到達不能な）領域を自動的に解放する仕組みです。GoのGCは、並行マーク＆スイープ方式を採用しています。
*   **保守的GC (Conservative GC)**: メモリ領域内の値がポインタであるか非ポインタであるかを完全に区別できない場合に、その値をポインタであると仮定してスキャンするGC方式です。これにより、誤ってポインタでない値をポインタと解釈し、到達不能なオブジェクトを誤って到達可能と判断して保持してしまう（メモリリーク）可能性があります。
*   **正確なGC (Precise GC)**: メモリ領域内の値がポインタであるか非ポインタであるかを正確に区別できるGC方式です。これにより、不要なメモリ保持を防ぎ、効率的なメモリ管理が可能になります。GoのGCは、スタックやヒープ上のポインタを正確に識別するために、コンパイラが生成するメタデータを利用します。
*   **PCDATA (Program Counter Data)**: Goコンパイラが生成するバイナリに埋め込まれるメタデータの一種です。プログラムカウンタ（PC）の特定の位置（命令）に関連付けられた情報を提供します。GCがスタックをスキャンする際などに、このPCDATAを利用して、どのメモリ領域がポインタを含んでいるか、あるいはスタックフレームのレイアウトがどうなっているかなどを判断します。
*   **`PCDATA_ArgSize`**: このコミットで削除されるPCDATAの一種で、関数呼び出し命令における引数のサイズを示していました。これは、特に可変引数関数や、コンパイラが引数サイズを静的に決定できない場合に、GCがスタック上の引数領域を保守的にスキャンするために使用されていました。
*   **`funcdata.h`**: Goランタイムの内部ヘッダファイルで、GCやスタックトレースなどのランタイム機能が利用する関数関連のメタデータ（FUNCDATAやPCDATAの定数など）が定義されています。

## 技術的詳細

このコミットは、Goコンパイラのバックエンド（`cmd/5c`, `cmd/5g`, `cmd/6c`, `cmd/6g`, `cmd/8c`, `cmd/8g`）とランタイム（`src/runtime/funcdata.h`）にわたる変更です。

具体的には、以下の処理が削除されています。

1.  **`PCDATA_ArgSize`の定義の削除**: `src/runtime/funcdata.h`から`PCDATA_ArgSize`マクロと関連するコメントが削除され、`PCDATA_StackMapIndex`が0に再割り当てされました。これは、`PCDATA_ArgSize`がもはや使用されないことを明確に示しています。
    ```c
    // 変更前
    #define PCDATA_ArgSize 0 /* argument size at CALL instruction */
    #define PCDATA_StackMapIndex 1

    // 変更後
    #define PCDATA_StackMapIndex 0
    ```
2.  **`gargsize`関数の削除**: 各アーキテクチャ（5g, 6g, 8g）のジェネレータ（`ggen.c`）およびサブルーチン（`gsubr.c`）から、`PCDATA_ArgSize`を生成するための`gargsize`関数が削除されました。この関数は、`PCDATA_ArgSize`と引数サイズを引数として`APCDATA`命令を生成していました。
3.  **`ginscall`関数からの`gargsize`呼び出しの削除**: 関数呼び出し命令を生成する`ginscall`関数内で、`PCDATA_ArgSize`を生成するための`gargsize`の呼び出しが削除されました。以前は、特定の条件（例: 可変引数関数、リフレクションによって生成された関数）で引数サイズを`PCDATA_ArgSize`として記録していました。
4.  **`cgen`関数からの`gpcdata`呼び出しの削除**: Cコンパイラ（`cmd/5c`, `cmd/6c`, `cmd/8c`）のコードジェネレータ（`cgen.c`）から、`PCDATA_ArgSize`に関連する`gpcdata`の呼び出しが削除されました。

これらの変更は、GoのGCがスタック上の引数領域をスキャンする際に、もはや`PCDATA_ArgSize`に依存しないことを意味します。これは、コンパイラがより正確なスタックマップ情報を生成できるようになり、GCがポインタを正確に識別できるようになったためです。これにより、ランタイムの複雑さが軽減され、GCの効率と精度がさらに向上します。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイル群で変更が行われています。

*   `src/cmd/{5c,6c,8c}/cgen.c`: Cコンパイラのコード生成部分。`gpcdata(PCDATA_ArgSize, ...)`の呼び出しが削除されています。
*   `src/cmd/{5g,6g,8g}/gg.h`: 各アーキテクチャのGoコンパイラのヘッダファイル。`gargsize`関数のプロトタイプ宣言が削除されています。
*   `src/cmd/{5g,6g,8g}/ggen.c`: 各アーキテクチャのGoコンパイラのコード生成部分。`ginscall`関数内での`gargsize`の呼び出しと、`arg`変数の計算ロジックが削除されています。
*   `src/cmd/{5g,6g,8g}/gsubr.c`: 各アーキテクチャのGoコンパイラのサブルーチン。`gargsize`関数の実装が完全に削除されています。
*   `src/runtime/funcdata.h`: ランタイムの関数データ定義。`PCDATA_ArgSize`の定義が削除され、`PCDATA_StackMapIndex`の定数値が変更されています。

これらの変更は、`PCDATA_ArgSize`の生成と利用に関するコードパスを、コンパイラからランタイムまで完全に削除することを目指しています。

## コアとなるコードの解説

変更の核心は、`PCDATA_ArgSize`という特定のメタデータがGoランタイムのガベージコレクタにとって不要になったという点です。

1.  **`src/runtime/funcdata.h`**:
    *   `#define PCDATA_ArgSize 0` の行が削除されました。これは、`PCDATA_ArgSize`という概念自体がGoランタイムから取り除かれたことを意味します。
    *   それに伴い、`#define PCDATA_StackMapIndex 1` が `#define PCDATA_StackMapIndex 0` に変更され、定数の再割り当てが行われました。これは、`PCDATA_ArgSize`が占めていたPCDATAのインデックスが解放され、他のPCDATAがその位置を再利用できるようになったことを示します。

2.  **`src/cmd/{5g,6g,8g}/ggen.c` (例: `src/cmd/5g/ggen.c`)**:
    *   `ginscall` 関数は、関数呼び出しの命令を生成する役割を担っています。この関数内には、以前は`arg`という変数を計算し、その値を使って`gargsize(arg)`を呼び出すロジックがありました。
    *   このコミットでは、`arg`変数の宣言と、その計算ロジック、そして`gargsize(arg)`の呼び出しがすべて削除されました。これにより、コンパイラは関数呼び出し時に`PCDATA_ArgSize`を生成しなくなりました。
    *   コメントアウトされていた部分（`// Most functions have a fixed-size argument block...`）も削除され、この機能が完全に廃止されたことが明確になっています。

3.  **`src/cmd/{5g,6g,8g}/gsubr.c` (例: `src/cmd/5g/gsubr.c`)**:
    *   `gargsize` 関数自体が完全に削除されました。この関数は、`PCDATA_ArgSize`と引数サイズを受け取り、`APCDATA`命令（PCDATAをアセンブリコードに埋め込む命令）を生成する役割を担っていました。この関数の削除は、`PCDATA_ArgSize`の生成パスが完全に断たれたことを意味します。

4.  **`src/cmd/{5c,6c,8c}/cgen.c` (例: `src/cmd/5c/cgen.c`)**:
    *   `_cgen` や `cgen` 関数内で、`gpcdata(PCDATA_ArgSize, curarg)` や `gpcdata(PCDATA_ArgSize, -1)` といった`PCDATA_ArgSize`に関連する`gpcdata`の呼び出しが削除されました。これは、Cコンパイラ側でも`PCDATA_ArgSize`の生成が停止されたことを示します。

これらの変更は、GoのGCがスタック上の引数領域をスキャンする際に、もはや`PCDATA_ArgSize`に依存しないという、より洗練されたGCメカニズムへの移行を反映しています。これは、コンパイラがより正確な型情報とスタックマップを生成できるようになり、GCがポインタを正確に識別できるようになったため、保守的なスキャンが不要になったことを意味します。結果として、ランタイムのコードベースが簡素化され、GCのパフォーマンスと信頼性が向上します。

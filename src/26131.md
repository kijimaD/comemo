## 変更の背景

このコミットの主な背景は、Goの`net/http`パッケージにおけるHTTPハンドラの記述に関する既存のドキュメントが、特に並行処理の側面において不明瞭であった点にあります。

1.  **ドキュメントの明確化**: 以前の`Handler`インターフェースのドキュメントは、「object」という用語を多用しており、また`ServeMux`に特化しすぎた記述となっていました。これにより、`Handler`のより一般的な利用方法や、`ResponseWriter`との相互作用における並行処理のセマンティクスが十分に伝わっていませんでした。開発者がHTTPハンドラを記述する際に、`ResponseWriter`への書き込みと`Request.Body`からの読み込みを並行して行う場合の挙動や、`ServeHTTP`メソッドが返された後のこれらのインターフェースの使用に関する明確なガイドラインが不足していました。
2.  **並行処理の安全性**: HTTPリクエストの処理は本質的に並行して行われるため、`ResponseWriter`と`Request.Body`へのアクセスがスレッドセーフであるか、あるいは特定の制約があるかについて、開発者が正確に理解していることが重要です。特に、`ServeHTTP`が完了した後に`ResponseWriter`を使用したり、`Request.Body`を読み込んだりする行為は未定義の動作を引き起こす可能性があり、これを明示的に警告する必要がありました。
3.  **テストカバレッジの向上**: ドキュメントの明確化と合わせて、並行処理下でのリクエストボディの読み込みとレスポンスライターへの書き込みの挙動を検証するためのテストケースが不足していました。このコミットでは、このギャップを埋めるためのテストが追加されています。
4.  **既存の問題への対応**: コミットメッセージには`Fixes #13050`と`Updates #13659`と記載されています。これらのIssueは、おそらく上記のドキュメントの不明瞭さや並行処理に関する問題提起に関連していると考えられます。特に`#13659`は、HTTP/2のテスト作成中に発見された新しい問題として言及されており、このコミットが単なるドキュメント修正に留まらず、実際の挙動の検証を通じて新たな課題を浮き彫りにしたことを示唆しています。

これらの背景から、このコミットは`net/http`パッケージの堅牢性と使いやすさを向上させるための重要な一歩と言えます。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下のGo言語および`net/http`パッケージに関する前提知識が必要です。

1.  **Goの`net/http`パッケージ**:
    *   Go言語でHTTPサーバーおよびクライアントを構築するための標準ライブラリです。
    *   **`http.Handler`インターフェース**: HTTPリクエストを処理するためのインターフェースで、`ServeHTTP(ResponseWriter, *Request)`メソッドを一つ持ちます。このメソッドが実際のリクエスト処理ロジックを実装します。
    *   **`http.ResponseWriter`インターフェース**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。`Header() Header`、`Write([]byte) (int, error)`、`WriteHeader(statusCode int)`の3つのメソッドを持ちます。
    *   **`http.Request`構造体**: クライアントからのHTTPリクエストを表す構造体です。リクエストメソッド、URL、ヘッダー、ボディ（`Body io.ReadCloser`）などの情報を含みます。
    *   **HTTPリクエスト/レスポンスサイクル**: クライアントからのリクエストを受け取り、`Handler`がそれを処理し、`ResponseWriter`を通じてレスポンスを返す一連の流れ。

2.  **Goの並行処理**:
    *   **Goroutine**: Goランタイムによって管理される軽量なスレッドです。`go`キーワードを使って関数呼び出しの前に置くことで、その関数を新しいgoroutineで実行できます。HTTPサーバーは通常、各リクエストを個別のgoroutineで処理します。
    *   **Channel**: goroutine間で値を安全に送受信するための通信メカニズムです。並行処理における同期やデータ共有に利用されます。
    *   **`sync.WaitGroup`**: 複数のgoroutineの完了を待つための同期プリミティブです。`Add(delta int)`でカウンタを増やし、`Done()`で減らし、`Wait()`でカウンタがゼロになるまでブロックします。

3.  **HTTPプロトコルの基礎**:
    *   **リクエストボディとレスポンスボディ**: HTTPリクエストにはクライアントからサーバーへ送られるデータ（リクエストボディ）が含まれることがあり、HTTPレスポンスにはサーバーからクライアントへ送られるデータ（レスポンスボディ）が含まれます。
    *   **HTTP/1.x と HTTP/2**: HTTPプロトコルのバージョン。HTTP/2は多重化（multiplexing）をサポートし、単一のTCP接続上で複数のリクエストとレスポンスを並行して送受信できます。これにより、HTTP/1.xとは異なる並行処理の特性を持つことがあります。

これらの知識を前提として、コミットが`ResponseWriter`と`Handler`のドキュメントに加えた並行処理に関する警告や、新しいテストケースがどのように並行アクセスをシミュレートしているかを理解することができます。

## 技術的詳細

このコミットは、主に`net/http`パッケージのドキュメントの更新と、並行処理の挙動を検証する新しいテストケースの追加という二つの側面から技術的な詳細を掘り下げることができます。

### 1. `net/http/server.go` におけるドキュメントの変更

`Handler`と`ResponseWriter`インターフェースのコメントが大幅に修正され、特に並行処理に関する重要な警告が追加されました。

#### `Handler`インターフェースのドキュメント変更点:

*   **旧ドキュメントの課題**: 以前のドキュメントは「object」という用語を多用し、`ServeMux`に特化しすぎた記述でした。これは、`Handler`がより汎用的なHTTPリクエストハンドリングのメカニズムであることを不明瞭にしていました。
*   **新しい記述**:
    *   `ServeHTTP`メソッドが`ResponseWriter`にヘッダーとデータを書き込み、その後returnすべきであるという基本的な役割は変わりません。
    *   **重要な警告の追加**: 「`ServeHTTP`呼び出しの完了後、またはそれと並行して`ResponseWriter`を使用したり、`Request.Body`を読み込んだりすることは有効ではありません。」という文言が追加されました。これは、`ServeHTTP`メソッドの実行スコープ外でのこれらのインターフェースへのアクセスが未定義の動作を引き起こす可能性を明確に警告しています。
    *   **`Request.Body`の読み込みに関する推奨**: 「HTTPクライアントソフトウェア、HTTPプロトコルバージョン、およびクライアントとGoサーバー間の仲介者によっては、`ResponseWriter`に書き込んだ後に`Request.Body`から読み込むことができない場合があります。慎重なハンドラは、まず`Request.Body`を読み込み、その後応答すべきです。」という推奨事項が追加されました。これは、特にストリーミングリクエストボディの場合や、プロキシなどの仲介者がリクエストボディの読み込みに影響を与える可能性がある場合に、予期せぬ挙動を避けるためのベストプラクティスを示しています。

#### `ResponseWriter`インターフェースのドキュメント変更点:

*   **重要な警告の追加**: 「`Handler.ServeHTTP`メソッドが返された後、`ResponseWriter`を使用してはなりません。」という明確な警告が追加されました。これは、`ResponseWriter`が`ServeHTTP`メソッドのライフサイクルに厳密に紐付けられていることを強調し、メソッドが終了した後の`ResponseWriter`へのアクセスが安全ではないことを示しています。

これらのドキュメント変更は、GoのHTTPサーバーを扱う開発者が、並行処理のコンテキストで`ResponseWriter`と`Request.Body`を安全かつ正しく使用するための明確な契約とガイドラインを提供します。

### 2. `net/http/clientserver_test.go` におけるテストの追加

`testConcurrentReadWriteReqBody`という新しいテスト関数が追加され、HTTPリクエストのボディを読み込みながら、同時にHTTPレスポンスを書き込むという並行処理のシナリオを検証します。

*   **テストの目的**: HTTPハンドラ内で、リクエストボディの読み込みとレスポンスボディの書き込みを異なるgoroutineで並行して実行した場合の挙動をテストします。
*   **テストの実装**:
    *   `newClientServerTest`を使用して、HTTP/1.xとHTTP/2の両方でテストを実行できるクライアント/サーバー環境をセットアップします。
    *   `HandlerFunc`内で、`sync.WaitGroup`と`didRead`チャネルを使用して、リクエストボディの読み込みとレスポンスボディの書き込みを並行して行う2つのgoroutineを起動します。
    *   **リクエストボディの読み込みgoroutine**: `ioutil.ReadAll(r.Body)`を使ってリクエストボディを読み込み、期待される内容と一致するか検証します。読み込みが完了したら`didRead`チャネルに`true`を送信します。
    *   **レスポンスボディの書き込みgoroutine**: `io.WriteString(w, resBody)`を使ってレスポンスボディを書き込みます。
    *   **HTTP/1.xの特殊な挙動**: HTTP/1.xの場合、`ResponseWriter`への書き込み中に`Request.Body`を読み込むことは意図的に許可されていません（「doesn't permit writes during read (mostly due to it being undefined)」）。そのため、HTTP/1.xのテストでは、書き込みgoroutineが`didRead`チャネルからの受信を待つことで、リクエストボディの読み込みが完了するまで書き込みをブロックします。これは、HTTP/1.xのストリーミングモデルにおける制約を反映しています。
    *   **HTTP/2のスキップ**: `TestConcurrentReadWriteReqBody_h2`テストは`t.Skip("known failing; golang.org/issue/13659")`によってスキップされています。これは、このコミットの作成時点ではHTTP/2においてこの並行処理シナリオが失敗することが既知の問題（Issue #13659）であったことを示しています。これは、HTTP/2の多重化の特性がHTTP/1.xとは異なるため、並行処理のセマンティクスも異なる可能性があることを示唆しています。
*   **クライアント側の検証**: クライアントは`Expect: 100-continue`ヘッダーを含むリクエストを送信し、サーバーからのレスポンスボディが期待される内容と一致するかを検証します。

このテストは、Goの`net/http`ハンドラが並行処理のコンテキストでどのように動作するかを具体的に示し、特にHTTP/1.xとHTTP/2の間で挙動が異なる可能性があることを浮き彫りにしています。ドキュメントの更新と合わせて、開発者がより堅牢なHTTPサービスを構築するための理解を深めるのに役立ちます。

## コアとなるコードの解説

### `src/net/http/clientserver_test.go` の変更点

*   **`TestConcurrentReadWriteReqBody_h1` と `TestConcurrentReadWriteReqBody_h2` の追加**:
    *   これらの関数は、`testConcurrentReadWriteReqBody`という共通のテストヘルパー関数を呼び出します。`_h1`はHTTP/1.xモードで、`_h2`はHTTP/2モードでテストを実行します。
    *   `TestConcurrentReadWriteReqBody_h2`には`t.Skip("known failing; golang.org/issue/13659")`という行が追加されています。これは、このテストがHTTP/2環境下では既知の問題（Issue #13659）により失敗するため、一時的にスキップされることを示しています。これは、HTTP/2の多重化の特性がHTTP/1.xとは異なり、並行処理のセマンティクスに影響を与える可能性があることを示唆しています。

*   **`testConcurrentReadWriteReqBody` 関数の追加**:
    *   このテスト関数は、HTTPハンドラ内でリクエストボディの読み込みとレスポンスボディの書き込みを並行して行うシナリオをシミュレートします。
    *   **`newClientServerTest`**: テスト用のHTTPサーバーとクライアントをセットアップします。ハンドラとして`HandlerFunc`が渡されます。
    *   **ハンドラ内の並行処理**:
        *   `sync.WaitGroup` (`wg`) を使用して、2つのgoroutine（リクエストボディ読み込みとレスポンスボディ書き込み）の完了を待ちます。
        *   `didRead`チャネル (`make(chan bool, 1)`) は、リクエストボディの読み込みが完了したことを通知するために使用されます。
        *   **リクエストボディ読み込みgoroutine**: `ioutil.ReadAll(r.Body)`を呼び出してリクエストボディを読み込みます。読み込みが完了したら`didRead <- true`で通知します。
        *   **レスポンスボディ書き込みgoroutine**: `io.WriteString(w, resBody)`を呼び出してレスポンスボディを書き込みます。
        *   **HTTP/1.x の同期**: `if !h2 { <-didRead }` のブロックは、HTTP/1.xの場合にのみ適用されます。HTTP/1.xの実装では、リクエストボディの読み込み中にレスポンスを書き込むことが意図的に許可されていません。そのため、このブロックはリクエストボディの読み込みが完了するまでレスポンス書き込みgoroutineをブロックし、HTTP/1.xのセマンティクスに準拠させます。
    *   **クライアント側の検証**:
        *   `NewRequest`で`POST`リクエストを作成し、リクエストボディを含めます。
        *   `req.Header.Add("Expect", "100-continue")` は、リクエストをより複雑にするために追加されています。
        *   `cst.c.Do(req)` でリクエストを実行し、`ioutil.ReadAll(res.Body)` でレスポンスボディを読み込み、期待される内容と一致するかを検証します。

    *   **新しい段落の追加**: `// Depending on the HTTP client software, HTTP protocol version, and // any intermediaries between the client and the Go server, it may not // be possible to read from the Request.Body after writing to the // ResponseWriter. Cautious handlers should read the Request.Body // first, and then reply.`
        *   `ResponseWriter`への書き込み後に`Request.Body`を読み込むことができない可能性があることを警告し、安全なハンドラはまず`Request.Body`を読み込むべきであるというベストプラクティスを推奨しています。

*   **`ResponseWriter`インターフェースのドキュメント更新**:
    *   **新しい行の追加**: `// A ResponseWriter may not be used after the Handler.ServeHTTP method // has returned.`
        *   `Handler.ServeHTTP`メソッドが返された後、`ResponseWriter`を使用してはならないという明確な警告が追加されました。これは、`ResponseWriter`のライフサイクルが`ServeHTTP`メソッドの実行期間に限定されることを強調しています。

*   **`HandlerFunc`のドキュメント更新**:
    *   旧: `// Handler object that calls f.`
    *   新: `// Handler that calls f.`
        *   ここでも「object」という用語が削除され、より簡潔な表現に変更されました。

これらの変更は、GoのHTTPハンドラを記述する際の並行処理に関する潜在的な落とし穴を開発者に警告し、より堅牢で予測可能なコードを書くための明確なガイドラインを提供することを目的としています。特に、`ServeHTTP`メソッドのライフサイクルと、その中で`ResponseWriter`および`Request.Body`をどのように扱うべきかについての理解を深める上で非常に重要です。

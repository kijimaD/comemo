# [インデックス 27102] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるレジスタ割り当ての最適化に関するものです。特に、x86アーキテクチャの「2アドレス命令」に対して、出力レジスタを入力レジスタのいずれかと一致させることで、生成されるアセンブリコードの効率を向上させます。これにより、`golang.org/x/crypto/sha3`のパフォーマンスが10%向上するなど、顕著な改善が見られました。

    cmd/compile: regalloc of two address instructions

    x86 has a lot of instructions that require the output to be in the same
    register as one of the inputs.  When allocating the output register,
    allocate the same register as the input if it is available.

## 元コミット内容

Goコンパイラにおいて、2アドレス命令のレジスタ割り当てを改善する。
x86アーキテクチャには、出力が入力のいずれかのレジスタと同じである必要がある命令が多く存在する。出力レジスタを割り当てる際、利用可能であれば入力と同じレジスタを割り当てるようにする。
これにより、`golang.org/x/crypto/sha3`のパフォーマンスが10%向上した（Go 1.6より6%遅かったものが、4%速くなった）。
Issue #14745 を修正。

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムを中間表現であるSSA形式に変換し、そこからターゲットアーキテクチャの機械語を生成します。この過程で、レジスタ割り当ては生成されるコードの効率に大きく影響します。

x86アーキテクチャの命令セットには、いわゆる「2アドレス命令」が多数存在します。これは、演算結果がオペランドの一つに上書きされる形式の命令です。例えば、`ADD R1, R2`という命令は、`R1 = R1 + R2`という操作を行い、結果を`R1`に格納します。もしコンパイラが`R1`と異なるレジスタに結果を割り当てようとすると、余分な`MOV`命令（レジスタ間コピー）が必要となり、コードサイズが増加し、実行速度が低下します。

このコミット以前は、Goコンパイラのレジスタ割り当て器が、このようなx86の特性を十分に考慮していなかった可能性があります。その結果、不必要なレジスタ間コピーが発生し、特に計算量の多いコード（例: 暗号化ライブラリ）でパフォーマンスが低下していました。`golang.org/x/crypto/sha3`の例では、Go 1.6と比較して6%も遅いという問題が報告されており、この最適化の必要性が浮き彫りになっていました。

この変更の目的は、レジスタ割り当て器が2アドレス命令の特性を認識し、可能な限り入力レジスタを再利用することで、生成されるコードの品質と実行速度を向上させることにあります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化で用いられる中間表現の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（定数伝播、共通部分式除去など）が効率的に行えます。Goコンパイラは、ソースコードをSSA形式に変換した後、レジスタ割り当てや命令スケジューリングなどのバックエンド処理を行います。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要なフェーズの一つです。プログラム中の変数を、CPUの高速なレジスタに割り当てることで、メモリへのアクセスを減らし、実行速度を向上させます。レジスタの数は限られているため、どの変数をどのレジスタに割り当てるか、いつメモリに退避（スピル）させるかなどを決定する必要があります。

### 3. x86アーキテクチャの2アドレス命令

x86（およびx64）アーキテクチャの多くの算術・論理命令は、2つのオペランドを取り、そのうちの1つに結果を格納します。
例:
- `ADD dest, src` : `dest = dest + src`
- `SUB dest, src` : `dest = dest - src`
- `MUL dest, src` : `dest = dest * src`
- `AND dest, src` : `dest = dest & src`
これらの命令は、`dest`レジスタが入力としても出力としても使われるため、「2アドレス命令」と呼ばれます。もし`dest`と異なるレジスタに結果を格納したい場合、`MOV`命令で`dest`の内容を別のレジスタにコピーしてから演算を行うか、演算後に結果を別のレジスタにコピーする必要があります。

### 4. 可換性 (Commutativity)

演算が可換であるとは、オペランドの順序を入れ替えても結果が変わらない性質を指します。例えば、加算（`A + B = B + A`）や乗算（`A * B = B * A`）、ビットごとのAND、OR、XORは可換演算です。減算（`A - B ≠ B - A`）や除算は可換ではありません。レジスタ割り当てにおいて、可換演算であるという情報は、どちらの入力レジスタを結果の格納先として再利用しても良いかという柔軟性を提供します。

### 5. `resultInArg0` フラグ

このコミットで導入された `resultInArg0` フラグは、特定の命令において、その結果が最初の引数（`arg0`）と同じレジスタに格納されることをコンパイラに伝えるためのメタデータです。x86の2アドレス命令の多くは、この特性を持っています。このフラグを利用することで、レジスタ割り当て器は、`arg0`が結果を保持するのに最適なレジスタであることを認識し、優先的にそのレジスタを割り当てようとします。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるレジスタ割り当て器が、x86の2アドレス命令の特性をより効果的に利用できるようにすることです。具体的には、以下の変更が行われました。

1.  **命令メタデータの拡張**:
    *   `src/cmd/compile/internal/ssa/gen/main.go` および `src/cmd/compile/internal/ssa/op.go` に、`opData` および `opInfo` 構造体に新しいフィールド `resultInArg0 bool` が追加されました。このフィールドは、命令の出力が最初の引数と同じレジスタに格納されるべきであることを示します。
    *   既存の `commutative bool` フィールドも、レジスタ割り当てのヒントとして活用されます。

2.  **x86命令定義の更新**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go` において、AMD64アーキテクチャの多くの命令（加算、減算、乗算、論理演算、シフト、単項演算など）に対して、`commutative: true` および `resultInArg0: true` が設定されました。
        *   例えば、`ADDQ` (64ビット加算) は可換であり、結果は`arg0`に格納されるため、両方のフラグが`true`に設定されます。
        *   `SUBQ` (64ビット減算) は可換ではないため、`commutative: false`ですが、結果は`arg0`に格納されるため、`resultInArg0: true`が設定されます。
        *   シフト命令 (`SHLQ`, `SHRQ`, `SARQ`など) や単項演算 (`NEGQ`, `NOTQ`など) も、結果が`arg0`に格納されるため、`resultInArg0: true`が設定されます。

3.  **レジスタ割り当てロジックの変更**:
    *   `src/cmd/compile/internal/ssa/regalloc.go` の `regalloc` 関数内で、出力レジスタを選択するロジックが変更されました。
    *   新しいロジックでは、もし命令が `resultInArg0` フラグを持つ場合、レジスタ割り当て器はまず、最初の引数 (`args[0]`) が割り当てられているレジスタを、出力レジスタとして利用可能かどうかをチェックします。
    *   さらに、もし命令が `commutative` でもある場合、2番目の引数 (`args[1]`) が割り当てられているレジスタも、出力レジスタとして利用可能であれば優先的に選択肢に加えます。
    *   これにより、レジスタ割り当て器は、x86の2アドレス命令の特性を考慮し、不必要なレジスタ間コピーを避けるように、より賢明なレジスタ選択を行うことができます。具体的には、`mask` 変数を使って利用可能なレジスタのビットマスクを生成し、`resultInArg0` や `commutative` の情報に基づいて、`arg0` や `arg1` のレジスタを優先的に選択するように `mask` を調整しています。

この最適化は、コンパイラが生成するアセンブリコードの品質を直接的に向上させ、特にCPUレジスタを頻繁に利用する数値計算や暗号処理などのワークロードにおいて、顕著なパフォーマンス改善をもたらします。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go`

これらのファイルでは、AMD64アーキテクチャの各SSA命令の定義に、`commutative` と `resultInArg0` のフラグが追加されています。

```go
// 変更前 (例: ADDSS)
// {name: "ADDSS", argLength: 2, reg: fp21, asm: "ADDSS"},

// 変更後 (例: ADDSS)
{name: "ADDSS", argLength: 2, reg: fp21, asm: "ADDSS", commutative: true, resultInArg0: true},
```

多くの算術・論理・シフト・単項演算に対して、同様の変更が適用されています。

### `src/cmd/compile/internal/ssa/gen/main.go` および `src/cmd/compile/internal/ssa/op.go`

`opData` および `opInfo` 構造体に `resultInArg0` フィールドが追加されています。

```go
// src/cmd/compile/internal/ssa/gen/main.go
type opData struct {
	// ...
	commutative       bool  // this operation is commutative (e.g. addition)
	resultInArg0      bool  // prefer v and v.Args[0] to be allocated to the same register
}

// src/cmd/compile/internal/ssa/op.go
type opInfo struct {
	// ...
	commutative       bool // this operation is commutative (e.g. addition)
	resultInArg0      bool // prefer v and v.Args[0] to be allocated to the same register
}
```

### `src/cmd/compile/internal/ssa/regalloc.go`

レジスタ割り当ての主要なロジックが変更されています。特に、出力レジスタの選択部分です。

```go
// 変更前
// var mask regMask
// if s.values[v.ID].needReg {
//     mask = regspec.outputs[0] &^ s.reserved()
//     // ...
// }
// if mask != 0 {
//     r := s.allocReg(v, mask)
//     s.assignReg(r, v, v)
// }

// 変更後
// Pick register for output.
var mask regMask
if s.values[v.ID].needReg {
    mask = regspec.outputs[0] &^ s.reserved()
    if mask>>33&1 != 0 {
        s.f.Fatalf("bad mask %s\n", v.LongString())
    }
    if opcodeTable[v.Op].resultInArg0 { // resultInArg0がtrueの場合
        r := register(s.f.getHome(args[0].ID).(*Register).Num) // arg0のレジスタを取得
        if (mask&^s.used)>>r&1 != 0 { // arg0のレジスタが利用可能であれば
            mask = regMask(1) << r // そのレジスタを優先
        }
        if opcodeTable[v.Op].commutative { // さらに可換であれば
            r := register(s.f.getHome(args[1].ID).(*Register).Num) // arg1のレジスタも取得
            if (mask&^s.used)>>r&1 != 0 { // arg1のレジスタが利用可能であれば
                mask = regMask(1) << r // そのレジスタも優先
            }
        }
        // TODO: enforce resultInArg0 always, instead of treating it
        // as a hint. Then we don't need the special cases adding
        // moves all throughout ssa.go:genValue.
    }
}
if mask != 0 {
    r := s.allocReg(v, mask)
    s.assignReg(r, v, v)
}
```

## コアとなるコードの解説

`regalloc.go`の変更は、レジスタ割り当て器が命令の特性に基づいて出力レジスタを賢く選択するためのものです。

1.  **`mask = regspec.outputs[0] &^ s.reserved()`**:
    まず、命令の出力が可能なレジスタの集合 (`regspec.outputs[0]`) から、予約済みレジスタ (`s.reserved()`) を除外して、実際に割り当て可能なレジスタのビットマスク `mask` を生成します。

2.  **`if opcodeTable[v.Op].resultInArg0`**:
    現在の命令 `v` が `resultInArg0` フラグを持つ場合、つまり、結果が最初の引数と同じレジスタに格納されることが望ましい命令である場合に、以下の最適化ロジックが適用されます。

3.  **`r := register(s.f.getHome(args[0].ID).(*Register).Num)`**:
    最初の引数 `args[0]` が現在割り当てられているレジスタ `r` を取得します。`getHome` は、SSA値が割り当てられているレジスタ（またはメモリ位置）を返す関数です。

4.  **`if (mask&^s.used)>>r&1 != 0`**:
    取得した `r` レジスタが、`mask` で示される割り当て可能なレジスタの集合に含まれており、かつ現在使用中でない (`s.used` に含まれない) 場合、つまり `r` が出力レジスタとして利用可能である場合をチェックします。

5.  **`mask = regMask(1) << r`**:
    もし `r` が利用可能であれば、`mask` を更新して、`r` レジスタのみを割り当て可能なレジスタとして設定します。これにより、レジスタ割り当て器は `r` を最優先で選択するようになります。これは、x86の2アドレス命令の特性を最大限に活かすための重要なステップです。

6.  **`if opcodeTable[v.Op].commutative`**:
    さらに、命令が `commutative` (可換) である場合、2番目の引数 `args[1]` のレジスタも同様にチェックし、利用可能であれば優先候補に加えます。可換演算では `arg0` と `arg1` のどちらに結果を格納しても意味的に問題がないため、より柔軟な選択が可能になります。

この変更により、コンパイラは、`ADD R1, R2` のような命令を処理する際に、`R1` が利用可能であれば、結果を `R1` に直接書き込むようにレジスタを割り当てます。これにより、`MOV R_temp, R1; ADD R_temp, R2; MOV R1, R_temp` のような冗長な命令シーケンスが回避され、より効率的な `ADD R1, R2` という単一の命令に変換される可能性が高まります。

コメントにある `// TODO: enforce resultInArg0 always, instead of treating it as a hint.` は、将来的には `resultInArg0` を単なるヒントではなく、常に強制するようなロジックにすることで、さらに最適化を進める余地があることを示唆しています。これにより、`ssa.go:genValue` 内の特殊なケースで `MOV` 命令を追加する必要がなくなる可能性があります。

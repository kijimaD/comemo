# [インデックス 28204] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける制御フローグラフ (CFG) の編集性能を大幅に改善することを目的としています。具体的には、CFGの先行ブロック (Preds) および後続ブロック (Succs) の配列にインデックス情報を付加することで、エッジの追加・削除操作を定数時間 (O(1)) で行えるように変更しました。これにより、特に`deadcode` (到達不能コード削除) および`fuse` (ブロック結合) といった最適化パスにおける最悪ケースの計算量がO(n^2)から大幅に削減され、コンパイル時間の短縮に貢献しています。

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムの最適化のために制御フローグラフ (CFG) を頻繁に操作します。特に、到達不能コード削除 (`deadcode`) やブロック結合 (`fuse`) といったパスでは、CFGのエッジ（ブロック間の接続）を削除したり追加したりする操作が繰り返し行われます。

従来のCFG表現では、各ブロックは先行ブロック (`Preds`) と後続ブロック (`Succs`) を単なるブロックポインタの配列 (`[]*Block`) として保持していました。この構造では、配列から特定のエッジ（ブロックポインタ）を削除する際に、そのエッジを見つけるために配列全体を走査する必要があり、さらに要素を削除した後に後続の要素をシフトする必要がありました。この操作は配列の長さに比例する線形時間 (O(N)) のコストがかかります。

もし、CFGが密で、これらの操作が多数のブロックに対して行われる場合、最悪ケースでは全体の計算量がブロック数の二乗 (O(N^2)) になってしまう可能性がありました。コミットメッセージに示されているベンチマーク結果は、この問題が実際に大規模なコードベースで顕著なパフォーマンス低下を引き起こしていたことを明確に示しています。特に`BenchmarkFuse10000`や`BenchmarkDeadCode200000`では、95%以上の実行時間削減が達成されており、この変更がコンパイラの性能に与える影響の大きさが伺えます。

この非効率性を解消し、コンパイル時間を短縮するために、CFGのエッジ編集操作を定数時間で行えるような新しいデータ構造とアルゴリズムの導入が不可欠でした。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現に変換する際に、SSA (Static Single Assignment) 形式を利用します。SSA形式は、各変数が一度だけ定義されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。SSA形式のプログラムは、以下の主要な要素で構成されます。

*   **ブロック (Block)**: 制御フローグラフのノードに相当し、一連の命令（値）を含みます。ブロックは常に単一のエントリポイントと単一のエグジットポイントを持ちます。
*   **値 (Value)**: SSA形式における命令やオペランドを表します。各値は一度だけ定義され、その定義はプログラム内で一意です。
*   **オペレーション (Operation)**: 値が実行する具体的な処理（例: 加算、ロード、ストア、比較など）。

### 2. 制御フローグラフ (CFG)

制御フローグラフ (Control Flow Graph, CFG) は、プログラムの可能な実行パスを抽象的に表現したグラフ構造です。

*   **ノード (Node)**: プログラムの基本的な実行単位（この文脈では「ブロック」）を表します。
*   **エッジ (Edge)**: ノード間の制御の移転（ジャンプ、呼び出し、フォールスルーなど）を表します。例えば、`if`文は条件分岐に応じて2つのエッジを持つブロックを生成します。

CFGは、コンパイラがプログラムの構造を理解し、最適化を適用するための基盤となります。

### 3. Preds (Predecessors) と Succs (Successors)

CFGにおいて、各ブロックは他のブロックとの関係を保持します。

*   **Preds (Predecessors)**: あるブロックに制御を移すことができる先行ブロックのリストです。
*   **Succs (Successors)**: あるブロックから制御が移る可能性のある後続ブロックのリストです。

これらのリストは、CFGの構造を定義し、データフロー解析や最適化アルゴリズムで頻繁に参照されます。

### 4. クリティカルエッジ (Critical Edges)

クリティカルエッジとは、複数の先行ブロックを持つブロック（マージポイント）に接続する、複数の後続ブロックを持つブロック（分岐点）からのエッジのことです。

例:
```
  A
 / \
B   C
 \ /
  D
```
ここで、Aが複数の後続（BとC）を持ち、Dが複数の先行（BとC）を持つ場合、B->DとC->Dのエッジはクリティカルエッジになり得ます。SSA形式の最適化では、クリティカルエッジが存在するとPhi関数の配置や最適化が複雑になるため、通常は間に空のブロックを挿入してクリティカルエッジを分割します。

### 5. Phi関数

SSA形式の重要な要素の一つがPhi (Φ) 関数です。Phi関数は、複数の制御フローパスが合流するブロック（マージポイント）において、異なるパスで定義された同じ論理的な変数に単一の定義を与えるために使用されます。例えば、`if`文の`then`ブランチと`else`ブランチでそれぞれ`x`が定義され、その後に合流するブロックで`x`が使用される場合、Phi関数が導入され、どちらの`x`の値が使われるかを決定します。

### 6. O(n^2) の問題

計算量の表記であるO(N^2)は、アルゴリズムの実行時間が入力サイズNの二乗に比例することを示します。配列から要素を削除する操作は、その要素を見つけるために平均してN/2の要素を走査し、その後N/2の要素をシフトする必要があるため、O(N)の時間がかかります。このO(N)の操作が、例えばN個のブロックそれぞれに対して行われる場合、全体の計算量はO(N * N) = O(N^2)となってしまいます。これは、Nが大きくなるにつれて実行時間が劇的に増加することを意味し、大規模なプログラムのコンパイルにおいて深刻な性能問題を引き起こします。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/ssa/block.go`内の`Block`構造体と、新たに導入された`Edge`構造体の変更にあります。

### `Block`構造体の変更

従来の`Block`構造体では、先行ブロックと後続ブロックはそれぞれ`[]*Block`型のスライスとして定義されていました。

```go
type Block struct {
    // ...
    Succs []*Block
    Preds []*Block
    // ...
}
```

このコミットにより、`Succs`と`Preds`の型が`[]Edge`に変更されました。

```go
type Block struct {
    // ...
    Succs []Edge
    Preds []Edge
    // ...
}
```

### `Edge`構造体の導入

`Edge`は、CFGのエッジを表す新しい構造体です。

```go
type Edge struct {
    // block edge goes to (in a Succs list) or from (in a Preds list)
    b *Block
    // index of reverse edge.  Invariant:
    //   e := x.Succs[idx]
    //   e.b.Preds[e.i] = Edge{x,idx}
    // and similarly for predecessors.
    i int
}
```

この`Edge`構造体は以下の2つのフィールドを持ちます。

*   `b *Block`: エッジが指す（またはエッジが来る元の）ブロックへのポインタ。
*   `i int`: **逆エッジのインデックス**。これがこの変更の鍵となる部分です。例えば、ブロック`X`からブロック`Y`へのエッジ`e`が`X.Succs[idx_X]`にあるとします。このとき、`e.b`は`Y`を指し、`e.i`は`Y.Preds`内の`X`からのエッジのインデックス`idx_Y`を保持します。つまり、`Y.Preds[idx_Y]`は`Edge{X, idx_X}`となります。

この双方向のインデックス情報を持つことで、CFGのエッジを削除する際に、対応する逆方向のエッジを直接、定数時間で特定し、更新することが可能になります。

### 定数時間CFG編集のメカニズム

1.  **エッジの追加 (`AddEdgeTo`)**:
    `b.AddEdgeTo(c)`が呼び出されると、`b.Succs`に`Edge{c, len(c.Preds)}`を追加し、同時に`c.Preds`に`Edge{b, len(b.Succs)-1}`を追加します。`len()`は定数時間で取得できるため、追加操作は定数時間で行われます。

2.  **エッジの削除 (`removePred`, `removeSucc`)**:
    例えば、ブロック`b`の`i`番目の後続エッジを削除する場合、`b.removeSucc(i)`が呼び出されます。
    *   まず、削除対象のエッジ`e = b.Succs[i]`を取得します。
    *   このエッジが指すブロック`c = e.b`と、そのブロック`c`の`Preds`リスト内での逆エッジのインデックス`j = e.i`を取得します。
    *   `b.Succs`から`i`番目の要素を削除します。これは、配列の最後の要素を`i`番目に移動させ、配列の長さを1つ減らすことで行われます。この際、移動された要素の逆エッジのインデックスも更新されます。
    *   同様に、`c.Preds`から`j`番目の要素を削除します。ここでも、配列の最後の要素を`j`番目に移動させ、移動された要素の逆エッジのインデックスを更新します。
    この一連の操作は、配列の末尾からの要素移動とインデックス更新により、定数時間で実行されます。

3.  **後続ブロックの入れ替え (`swapSuccessors`)**:
    `b.swapSuccessors()`は、2つの後続ブロックを持つブロックの`Succs[0]`と`Succs[1]`を入れ替えます。この際、それぞれの後続ブロックの`Preds`リスト内の逆エッジのインデックスも適切に更新されます。これも定数時間操作です。

### パフォーマンス改善

この変更により、`deadcode`や`fuse`といった最適化パスで頻繁に行われるCFGのエッジ削除操作が、O(N)からO(1)に改善されました。これにより、これらのパス全体の計算量が最悪ケースでO(N^2)だったものが、O(N)またはO(N log N)といったより効率的な計算量に削減され、特に大規模な関数や複雑な制御フローを持つプログラムのコンパイル時間が大幅に短縮されました。ベンチマーク結果は、この理論的な改善が実測値として現れていることを明確に示しています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、`src/cmd/compile/internal/ssa/block.go`に集中しています。

1.  **`Block`構造体の定義変更**:
    ```go
    // 変更前
    // Succs []*Block
    // Preds []*Block

    // 変更後
    Succs []Edge
    Preds []Edge
    ```
    `Succs`と`Preds`が`*Block`のスライスから`Edge`構造体のスライスに変更されました。

2.  **`Edge`構造体の新規追加**:
    ```go
    type Edge struct {
        b *Block // block edge goes to (in a Succs list) or from (in a Preds list)
        i int    // index of reverse edge.
    }

    func (e Edge) Block() *Block {
        return e.b
    }
    ```
    `Edge`構造体が導入され、ブロックポインタ`b`と逆エッジのインデックス`i`を保持します。また、`Block()`ヘルパーメソッドが追加され、`Edge`から`*Block`を取得する際に使用されます。

3.  **CFG編集ヘルパーメソッドの追加/変更**:
    *   `AddEdgeTo(c *Block)`: ブロック`b`から`c`へのエッジを追加する際に、両方のブロックの`Succs`と`Preds`を`Edge`構造体を使って適切に更新します。
    *   `removePred(i int)`: `b`の`i`番目の先行エッジを削除します。対応する後続エッジも更新されます。
    *   `removeSucc(i int)`: `b`の`i`番目の後続エッジを削除します。対応する先行エッジも更新されます。
    *   `swapSuccessors()`: 2つの後続ブロックを持つブロックの`Succs`を入れ替え、対応する逆エッジのインデックスも更新します。

これらの変更に伴い、`src/cmd/compile/internal/ssa/`以下の多数のファイル（例: `amd64/ssa.go`, `arm/ssa.go`, `gc/ssa.go`, `check.go`, `critical.go`, `deadcode.go`, `dom.go`, `flagalloc.go`, `func.go`, `fuse.go`, `html.go`, `layout.go`, `likelyadjust.go`, `loopbce.go`, `nilcheck.go`, `phiopt.go`, `print.go`, `prove.go`, `regalloc.go`, `rewrite*.go`, `shortcircuit.go`, `trim.go`など）で、`b.Succs[i]`や`b.Preds[i]`といった直接的なブロックポインタへのアクセスが、`b.Succs[i].b`や`b.Preds[i].b`のように`Edge`構造体の`b`フィールドを介したアクセスに変更されています。

また、`deadcode_test.go`と`fuse_test.go`には、この変更による性能改善を測定するためのベンチマークが追加されています。

## コアとなるコードの解説

### `Edge`構造体による定数時間操作

このコミットの最も重要な側面は、`Edge`構造体の`i int`フィールドです。これは「逆エッジのインデックス」を意味します。

具体的に、ブロック`X`からブロック`Y`へのエッジを考えます。
*   `X.Succs`リストの`k`番目の要素が`Edge{Y, j}`であるとします。これは「`X`の後続ブロックの`k`番目は`Y`であり、`Y`の先行ブロックリストにおける`X`からのエッジは`j`番目にある」ことを意味します。
*   同時に、`Y.Preds`リストの`j`番目の要素は`Edge{X, k}`となります。これは「`Y`の先行ブロックの`j`番目は`X`であり、`X`の後続ブロックリストにおける`Y`へのエッジは`k`番目にある」ことを意味します。

この双方向のインデックス情報が常に整合性を保つように設計されています。

#### エッジ削除の例 (`removeSucc`と`removePred`)

例えば、`b.removeSucc(i)`が呼び出され、ブロック`b`の`i`番目の後続エッジを削除する場合を考えます。
1.  `e := b.Succs[i]`：削除対象のエッジ`e`を取得します。`e.b`は後続ブロック`c`、`e.i`は`c.Preds`における逆エッジのインデックス`j`です。
2.  `b.removeSucc(i)`の内部では、`b.Succs`リストから`i`番目の要素を削除します。Goのスライスでは、要素を削除する一般的な方法は、最後の要素を削除位置に移動させ、スライスを短縮することです。
    *   `n := len(b.Succs) - 1`
    *   `if i != n { b.Succs[i] = b.Succs[n] }`
    *   `b.Succs = b.Succs[:n]`
    *   **重要なのは、`b.Succs[n]`が`i`に移動した場合、その移動されたエッジの逆エッジのインデックスも更新する必要があることです。`b.Succs[i].b.Preds[b.Succs[i].i].i = i`のように更新されます。**
3.  次に、対応する逆エッジを削除するために、`c.removePred(j)`が呼び出されます。ここでも同様に、`c.Preds`リストから`j`番目の要素を削除し、移動された要素の逆エッジのインデックスを更新します。

このように、エッジの削除は、削除対象のエッジとその逆エッジを直接特定し、スライスの末尾要素を移動させることで、配列のシフトを伴わずに定数時間で完了します。これにより、従来のO(N)の操作がO(1)に改善され、`deadcode`や`fuse`のようなCFGを頻繁に編集する最適化パスのパフォーマンスが劇的に向上しました。

### `Block().Values`への変更

多くの箇所で`b.Succs[0]`のような直接的なブロックポインタへのアクセスが`b.Succs[0].Block()`に変更されています。これは、`Succs`が`[]*Block`から`[]Edge`に変わったため、`Edge`構造体の`b`フィールドを介して実際のブロックポインタにアクセスする必要があるからです。`Edge`構造体に`Block() *Block`メソッドが追加されたことで、この変更はコードの可読性を保ちつつ行われています。

### ベンチマークの重要性

コミットメッセージに含まれるベンチマーク結果は、この変更の有効性を定量的に示しています。特に、入力サイズが大きくなるにつれて、`BenchmarkFuse`と`BenchmarkDeadCode`の実行時間が劇的に短縮されていることがわかります。これは、O(N^2)のアルゴリズムがO(N)またはそれに近いアルゴリズムに改善されたことの典型的な証拠であり、コンパイラの性能向上に大きく貢献しています。

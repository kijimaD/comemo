# [インデックス 18589] ファイルの概要

このコミットは、GoランタイムにおけるC言語で書かれた関数（Goから呼び出されるもの）の生成方法を改善し、`goc2c`ツールをより広範に適用することを目的としています。これにより、アーキテクチャ固有のアライメント問題や、スタック情報出力のための手動での`#pragma`記述の必要性を排除し、ランタイムコードの移植性と保守性を向上させています。

    ```
    runtime: use goc2c as much as possible

    Package runtime's C functions written to be called from Go
    started out written in C using carefully constructed argument
    lists and the FLUSH macro to write a result back to memory.

    For some functions, the appropriate parameter list ended up
    being architecture-dependent due to differences in alignment,
    so we added 'goc2c', which takes a .goc file containing Go func
    declarations but C bodies, rewrites the Go func declaration to
    equivalent C declarations for the target architecture, adds the
    needed FLUSH statements, and writes out an equivalent C file.
    That C file is compiled as part of package runtime.

    Native Client's x86-64 support introduces the most complex
    alignment rules yet, breaking many functions that could until
    now be portably written in C. Using goc2c for those avoids the
    breakage.

    Separately, Keith's work on emitting stack information from
    the C compiler would require the hand-written functions
    to add #pragmas specifying how many arguments are result
    parameters. Using goc2c for those avoids maintaining #pragmas.

    For both reasons, use goc2c for as many Go-called C functions
    as possible.

    This CL is a replay of the bulk of CL 15400047 and CL 15790043,
    both of which were reviewed as part of the NaCl port and are
    checked in to the NaCl branch. This CL is part of bringing the
    NaCl code into the main tree.

    No new code here, just reformatting and occasional movement
    into .h files.
    ```

## 変更の背景

Goランタイムは、パフォーマンスが重要な部分でC言語で書かれた関数をGoから呼び出す仕組みを持っています。当初、これらのC関数は手動で引数リストを構築し、`FLUSH`マクロを使用して結果をメモリに書き戻していました。しかし、このアプローチにはいくつかの課題がありました。

1.  **アーキテクチャ依存のアライメント問題**: 特定のアーキテクチャ（特にNative Clientのx86-64サポート）では、データのアライメントに関する複雑なルールが存在します。これにより、Cで手書きされた関数が異なるアーキテクチャ間で移植性を失い、正しく動作しない問題が発生していました。`goc2c`は、Goの関数宣言からターゲットアーキテクチャに合わせたCの宣言を生成することで、この問題を解決します。
2.  **スタック情報出力のための`#pragma`の維持**: Cコンパイラがスタック情報を正確に出力するためには、手書きのC関数に引数の数や結果パラメータの指定に関する`#pragma`ディレクティブを追加する必要がありました。これは手動でのメンテナンスが煩雑であり、エラーの原因となる可能性がありました。`goc2c`を使用することで、これらの`#pragma`の記述と維持が不要になります。
3.  **Native Client (NaCl) ポートの統合**: この変更は、GoのNative Clientポート（Google ChromeでGoコードを実行するための技術）の一部として開発されたもので、NaClブランチで既にレビューされ、チェックインされていました。このコミットは、そのNaClコードをメインのGoツリーに統合するプロセスの一環です。

これらの理由から、Goから呼び出されるC関数の多くで`goc2c`の使用を拡大することが決定されました。

## 前提知識の解説

*   **Goランタイム**: Goプログラムの実行を管理する低レベルのコンポーネントです。ガベージコレクション、スケジューリング、チャネル、マップなどの組み込み機能の実装を含みます。パフォーマンスが重要な部分では、C言語やアセンブリ言語で書かれたコードが使用されることがあります。
*   **`goc2c`ツール**: Goランタイムのビルドプロセスで使用される内部ツールです。`.goc`拡張子を持つファイルを入力として受け取ります。`.goc`ファイルは、Goの関数宣言とC言語の関数本体を組み合わせた形式で記述されます。`goc2c`は、この`.goc`ファイルを解析し、ターゲットアーキテクチャに特化したC言語のソースコードを生成します。この生成されたCコードは、Goの呼び出し規約に適合するように引数リストを調整し、必要に応じて`FLUSH`マクロを挿入します。
*   **`FLUSH`マクロ**: GoランタイムのCコードで使用されるマクロです。Goの関数がC関数を呼び出し、C関数がGoの変数に結果を書き込む際に、コンパイラがその書き込みを最適化によって削除しないようにするために使用されます。特に、レジスタに格納された値をメモリに強制的に書き出すことで、Go側からその値が正しく参照できるようにします。
*   **Native Client (NaCl)**: Googleが開発したサンドボックス技術で、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行できるようにするものです。Go言語もNaClをターゲットとしてサポートしていました。NaCl環境では、セキュリティとパフォーマンスのために厳格なメモリレイアウトとアライメントのルールが適用され、これが通常のCコードの移植性を損なう原因となることがありました。
*   **アライメント (Alignment)**: メモリ上のデータの配置に関するルールです。特定のデータ型（例: 64ビット整数）は、そのサイズ（例: 8バイト）の倍数のアドレスに配置される必要があります。異なるアーキテクチャでは、このアライメント要件が異なる場合があり、これが移植性の問題を引き起こすことがあります。
*   **`#pragma`ディレクティブ**: C/C++コンパイラに対する特別な指示です。コンパイラの動作を制御するために使用されます。このコミットの文脈では、スタック情報の出力に関連するメタデータをコンパイラに伝えるために使用されていました。

## 技術的詳細

このコミットの核心は、GoランタイムのC言語部分におけるコード生成と管理のパラダイムシフトにあります。

従来のGoランタイムでは、Goから呼び出されるC関数は手動でC言語で記述されていました。これらの関数は、Goの呼び出し規約に合うように引数リストを慎重に設計し、結果をGoのメモリに書き戻すために`FLUSH`マクロを明示的に使用する必要がありました。この手動アプローチは、特に以下のような問題に直面していました。

1.  **アーキテクチャ間の差異への対応**: 異なるCPUアーキテクチャ（例: x86-64、ARM）では、データのメモリ上のアライメント要件や、関数呼び出し時の引数の渡し方（レジスタの使用方法など）が異なります。手動でCコードを書く場合、これらのアーキテクチャ固有の差異をすべて考慮し、条件付きコンパイル（`#ifdef`など）で対応する必要がありました。Native Clientのx86-64サポートは、特に複雑なアライメントルールを導入し、この問題を顕著にしました。`goc2c`は、Goの型情報に基づいて、ターゲットアーキテクチャに最適なCの関数シグネチャとアライメントを自動的に生成することで、この問題を解決します。
2.  **スタック情報の正確な伝達**: Goのガベージコレクタやデバッガは、正確なスタック情報を必要とします。Cコンパイラがこの情報を正しく生成するためには、C関数がGoの呼び出し規約に従っていること、特に引数と戻り値のメモリレイアウトに関する情報が必要です。Keithによるスタック情報出力の改善作業では、手書きのC関数に対して、これらの情報を`#pragma`ディレクティブで明示的に指定することが求められました。これは、コードの可読性を損ない、メンテナンスの負担を増大させます。`goc2c`は、Goの関数宣言から必要なスタック情報メタデータを自動的に生成することで、手動での`#pragma`記述を不要にします。

このコミットでは、これらの問題を解決するために、より多くのGoから呼び出されるC関数を`.goc`ファイル形式に変換し、`goc2c`ツールによって自動生成されるようにしました。これにより、開発者はGoの型システムとGoの関数宣言のセマンティクスに集中でき、低レベルのC言語の呼び出し規約やアーキテクチャ固有のアライメント、スタック情報に関する詳細を`goc2c`に任せることができます。

変更の具体的な影響としては、多くのランタイムのCソースファイル（例: `alg.c`, `chan.c`, `hashmap.c`, `iface.c`など）が`.goc`拡張子に変更され、Goの関数宣言とCの関数本体を組み合わせた形式で記述されるようになりました。また、これらのファイルから抽出された構造体定義などが、対応する`.h`ファイルに移動され、CコードとGoコードの間で共有される定義の一貫性が保たれています。

`goc2c`ツール自体も、新しい型（`Complex128`, `Float32`, `Float64`）のアライメントとサイズを正確に処理できるように更新され、より堅牢になっています。特に、`type_table`に`rnd`（アライメント）フィールドが追加され、`type_size`関数がアライメント情報を返すように変更されています。これにより、`goc2c`が生成するCコードが、Goの型のアライメント要件をより正確に満たすことができるようになりました。

この変更は、Goランタイムの低レベル部分の保守性を大幅に向上させ、将来的なアーキテクチャサポートやデバッグ機能の拡張を容易にする基盤を築きました。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   **`src/cmd/dist/goc2c.c`**: `goc2c`ツールの実装ファイル。Goの型とCの型のアライメントとサイズのマッピングを改善し、より多くのGoの型を正確に処理できるように変更されています。特に、`type_table`に`rnd`（アライメント）フィールドが追加され、`type_size`関数がアライメント情報を返すように修正されています。また、`FLUSH`マクロの生成ロジックも調整されています。
*   **`src/pkg/runtime/*.c` から `src/pkg/runtime/*.goc` へのリネーム**: 多くのGoランタイムのCソースファイルが、`goc2c`で処理される`.goc`ファイルにリネームされています。これには、`alg.c`, `chan.c`, `complex.c`, `cpuprof.c`, `hashmap.c`, `iface.c`, `lfstack.c`, `slice.c`, `string.c`, `symtab.c`などが含まれます。
*   **`src/pkg/runtime/*.h` ファイルの追加/更新**: `.goc`ファイルから抽出された構造体定義やマクロ定義が、対応する`.h`ファイル（例: `chan.h`, `hashmap.h`）に移動または追加されています。これにより、CコードとGoコードの間で共有される定義の一貫性が保たれます。
*   **`src/pkg/runtime/export_test.c` から `src/pkg/runtime/defs.c` へのリネームと内容変更**: テスト関連の定義ファイルがリネームされ、デバッグ情報取得のためのヘッダーファイルインクルードが追加されています。
*   **`src/pkg/runtime/export_test.go` の変更**: `goc2c`への移行に伴い、Go側からC関数を呼び出すためのテスト用エクスポート関数名が変更されています（例: `lfstackpush`が`lfstackpush_go`に）。
*   **`FLUSH`マクロの削除**: `.goc`ファイルに変換された関数では、`goc2c`が自動的に`FLUSH`マクロを挿入するため、手動で記述されていた`FLUSH`マクロが削除されています。

## コアとなるコードの解説

このコミットの主要な変更は、`goc2c`ツールの機能拡張と、GoランタイムのCコードを`.goc`形式に移行した点にあります。

**`src/cmd/dist/goc2c.c` の変更点**:

*   **`type_table`の拡張とアライメント情報の追加**:
    ```c
    static struct {
    	char *name;
    	int size;
    	int rnd; // alignment
    } type_table[] = {
    	// ...
    	{"Complex128", 16, 0}, // 新しい型とアライメントの初期値
    	// ...
    };
    ```
    `type_table`に`rnd`フィールドが追加され、各Goの型に対応するCの型のアライメント情報が保持されるようになりました。これにより、`goc2c`はアーキテクチャ固有のアライメント要件をより正確に考慮してCコードを生成できます。
*   **`type_size`関数の変更**:
    ```c
    static int
    type_size(char *p, int *rnd)
    {
    	// ...
    	if(streq(type_table[i].name, p)) {
    		*rnd = type_table[i].rnd; // アライメント情報を返す
    		return type_table[i].size;
    	}
    	// ...
    }
    ```
    `type_size`関数が、型のサイズだけでなく、その型のアライメント情報もポインタ`rnd`を介して返すようになりました。これは、引数リストのオフセット計算において正確なアライメントを確保するために重要です。
*   **`read_params`関数の変更**:
    ```c
    // ...
    			p->type = read_type();
    			rnd = 0;
    			size = type_size(p->type, &rnd);
    			if(rnd > structround)
    				rnd = structround;
    			if(offset%rnd)
    				offset += rnd - offset%rnd;
    			offset += size;
    // ...
    ```
    `read_params`関数内で、各パラメータのサイズとアライメントに基づいてオフセットを計算するロジックが強化されました。これにより、アーキテクチャ固有のアライメント要件を満たすように引数リストのメモリレイアウトが調整されます。
*   **`write_6g_func_trailer`での`FLUSH`マクロの自動挿入**:
    ```c
    // ...
    	for (p = rets; p != nil; p = p->next)
    		if(!streq(p->name, "...")) // 可変引数でない場合にFLUSHを挿入
    			bwritef(output, "\tFLUSH(&%s);\\n", p->name);
    // ...
    ```
    `goc2c`が生成するCコードの関数トレーラー部分で、戻り値に対して自動的に`FLUSH`マクロが挿入されるようになりました。これにより、手動での`FLUSH`記述が不要になります。

**`.goc`ファイルへの移行**:

多くのランタイムのCファイルが`.goc`にリネームされ、Goの関数宣言とCの関数本体を組み合わせた形式で記述されるようになりました。例えば、`src/pkg/runtime/chan.c`が`src/pkg/runtime/chan.goc`に変わり、その中の関数は以下のような形式になっています。

```go
// func makechan(t *ChanType, size uint64) (c *Hchan) {
//    c = makechan(t, size);
// }
// 上記はGoの関数宣言のコメント形式。goc2cがこれを解析する。
// 実際のCの関数本体は以下に続く。
func makechan(t *ChanType, size int64) (c *Hchan) {
    c = makechan(t, size);
}
```

この変更により、GoランタイムのCコードは、Goの型システムとより密接に連携し、アーキテクチャ固有の複雑な詳細を`goc2c`ツールに委ねることで、保守性と移植性が大幅に向上しました。

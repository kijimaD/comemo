# [インデックス 21124] ファイルの概要

このコミットは、Go言語のツールチェイン内部で使用される`debug/goobj`パッケージを`cmd/internal/goobj`へ移動するものです。この変更は、`debug/goobj`がまだ公開準備ができていないにもかかわらず、バイナリ読み取り関連のコマンドで必要とされているという状況に対応するために行われました。`cmd/internal`ディレクトリへの移動は、そのパッケージがGoツールチェインの内部でのみ使用されることを明確にし、外部からの不適切な依存を防ぐための標準的な慣習です。

## 変更の背景

このコミットの背景には、`debug/goobj`パッケージの特殊な状況があります。このパッケージはGoのオブジェクトファイル（`.o`ファイル）を読み取るための機能を提供しますが、そのAPIはまだ安定しておらず、公開（パブリックAPIとして提供）する準備ができていませんでした。しかし、Goツールチェイン内のいくつかのバイナリ読み取り関連コマンド（特にリンカである`cmd/link`）がこのパッケージに依存していました。

Go 1.3のリリースブランチでは、このパッケージが削除された経緯がありますが、その後の開発でコマンドの依存関係により削除が不可能になりました。このような状況で、未公開の不安定なAPIを持つパッケージが外部からアクセスされることを防ぎつつ、内部のツールチェインが必要とする機能を提供し続ける必要がありました。

Go言語では、`internal`ディレクトリの慣習（Go 1.4で導入）があり、このディレクトリ内のパッケージは、その`internal`ディレクトリの親ディレクトリツリー内にあるコードからのみインポートできます。これにより、パッケージの可視性を制限し、意図しない外部依存を防ぐことができます。このコミットは、この`internal`パッケージの慣習が正式に導入される前の段階で、同様の目的を達成するために`cmd/internal`というパスに移動することで、`debug/goobj`がGoツールチェインの内部でのみ使用されることを明確にしました。

## 前提知識の解説

*   **Goのパッケージとモジュール**: Go言語では、コードはパッケージにまとめられ、パッケージはディレクトリ構造によって整理されます。他のパッケージのコードを使用するには、`import`ステートメントでそのパッケージをインポートします。
*   **Goのオブジェクトファイル (`.o`ファイル)**: Goコンパイラがソースコードをコンパイルする際に生成される中間ファイルです。これには、コンパイルされたコードやデータ、シンボル情報などが含まれます。
*   **Goツールチェイン**: Go言語のコンパイラ、リンカ、アセンブラ、デバッガなどの開発ツール群の総称です。これらのツールはGoプログラムのビルド、実行、デバッグに不可欠です。
*   **`cmd/internal`ディレクトリの慣習**: Go言語では、`cmd/internal`のようなパスに配置されたパッケージは、Goツールチェインの内部でのみ使用されることを意図しています。これは、Go 1.4で導入された`internal`パッケージの慣習の先駆けとなるもので、特定のパッケージが外部からインポートされることを防ぎ、ツールチェインの内部実装の詳細を隠蔽するために用いられます。これにより、内部APIの変更が外部のユーザーに影響を与えることを心配せずに、ツールチェインの開発を進めることができます。
*   **リンカ (`cmd/link`)**: Goツールチェインの一部であり、コンパイルされたオブジェクトファイルやライブラリを結合して実行可能なバイナリを生成する役割を担います。リンカは、プログラム内の関数や変数の参照を解決し、最終的な実行ファイルを構築します。

## 技術的詳細

このコミットの技術的な核心は、`debug/goobj`パッケージのインポートパスを`cmd/internal/goobj`に変更することです。これは単なるディレクトリの移動以上の意味を持ちます。

1.  **可視性の制限**: `debug/goobj`が`cmd/internal/goobj`に移動することで、このパッケージはGoツールチェインの内部でのみインポート可能になります。これは、Go 1.4で導入された`internal`パッケージのルールと同様の効果を持ちます。つまり、Goの標準ライブラリや外部のGoプロジェクトから直接`cmd/internal/goobj`をインポートしようとすると、コンパイルエラーが発生するようになります。これにより、まだ安定していない、あるいは公開を意図していないAPIが誤って使用されることを防ぎます。
2.  **依存関係の管理**: `cmd/link`などのGoツールチェイン内のコマンドは、Goのオブジェクトファイルを読み取るために`goobj`パッケージに依存していました。この移動により、これらの内部ツールは引き続き`goobj`の機能を利用できますが、その依存関係はGoツールチェインの内部に閉じ込められます。
3.  **APIの未成熟性への対応**: コミットメッセージにある「The API is still not vetted nor terribly well designed.」という記述は、このパッケージのAPIがまだ設計段階であり、将来的に変更される可能性が高いことを示唆しています。`internal`パスへの移動は、このような不安定なAPIが外部に漏れることを防ぎ、開発者が自由にAPIを改善できる柔軟性を提供します。
4.  **ファイルシステム上の変更**: 物理的には、`src/debug/goobj`ディレクトリが`src/cmd/internal/goobj`にリネームされ、そのディレクトリ内のファイル（`read.go`と`read_test.go`）も移動されます。これに伴い、`debug/goobj`をインポートしていたすべてのファイル（主に`src/cmd/internal/objfile/goobj.go`と`src/cmd/link`以下の複数のファイル）でインポートパスが`cmd/internal/goobj`に更新されます。

この変更は、Goツールチェインの内部構造を整理し、将来のAPIの安定化と公開に向けた準備を進める上で重要なステップでした。

## コアとなるコードの変更箇所

このコミットのコアとなるコードの変更は、主に以下の2点です。

1.  **ディレクトリのリネーム**:
    *   `src/debug/goobj/read.go` が `src/cmd/internal/goobj/read.go` にリネーム。
    *   `src/debug/goobj/read_test.go` が `src/cmd/internal/goobj/read_test.go` にリネーム。

2.  **インポートパスの変更**:
    `debug/goobj`をインポートしていた以下のファイルで、インポートパスが`cmd/internal/goobj`に変更されています。

    *   `src/cmd/link/auto.go`

    *   `src/cmd/link/link_test.go`

## コアとなるコードの解説

変更された各ファイルでは、`import`ステートメント内のパッケージパスが`"debug/goobj"`から`"cmd/internal/goobj"`に修正されています。

例えば、`src/cmd/internal/objfile/goobj.go`の変更は以下のようになっています。

```diff
--- a/src/cmd/internal/objfile/goobj.go
+++ b/src/cmd/internal/objfile/goobj.go
@@ -7,7 +7,7 @@
 package objfile
 
 import (
-	"debug/goobj"
+	"cmd/internal/goobj"
 	"fmt"
 	"os"
 )
```

これは、`objfile`パッケージがGoのオブジェクトファイルを扱うために`goobj`パッケージの機能を利用していることを示しています。インポートパスの変更により、`objfile`パッケージは新しい内部パスから`goobj`パッケージを参照するようになります。

同様に、`src/cmd/link`以下のファイル群（`auto.go`, `dead.go`, `pclntab.go`など）も、リンカの処理においてGoオブジェクトファイルの情報を利用するために`debug/goobj`をインポートしていました。これらのファイルもすべて、新しい`cmd/internal/goobj`パスを参照するように更新されています。

この一連の変更は、`goobj`パッケージがGoツールチェインの内部コンポーネントとして明確に位置づけられ、そのAPIが外部に公開されないようにするためのものです。これにより、Goツールチェインの内部構造の整合性が保たれ、将来的な開発の柔軟性が確保されます。

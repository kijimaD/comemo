# [インデックス 28108] ファイルの概要

このコミットは、Go言語の`debug/pe`パッケージにおける重要な修正を導入しています。具体的には、PE (Portable Executable) ファイルフォーマット内の`.bss`セクションが、リンカによってゼロ初期化されるという暗黙の前提を、`debug/pe`パッケージが正しく反映するように変更しました。これにより、`.bss`セクションのデータを読み取る際に、常にゼロが返されるようになります。

## 元コミット内容

`debug/pe: .bss section must contain only zeros`

`.bss`セクションはPEファイル内にデータが格納されていません。しかし、リンカが`.bss`セクションのデータを使用する際には、そのすべてのバイトがゼロに設定されていると仮定されます。現在の`(*Section).Data`はゴミデータを返します。`(*Section).Data`がゼロで埋められたスライスを返すように変更します。

Issue #15345 を更新します。

## 変更の背景

この変更の背景には、PE (Portable Executable) ファイルフォーマットの`.bss`セクションの特性と、それがプログラムの実行時にどのように扱われるかという根本的な理解があります。

`.bss` (Block Started by Symbol) セクションは、初期化されていないグローバル変数や静的変数を格納するために使用されるデータセクションです。これらの変数は、プログラムの実行開始時にゼロで初期化されることがC/C++などの言語仕様で保証されています。しかし、PEファイル自体には、これらの変数の初期値（すべてゼロ）を格納するための領域は通常割り当てられません。これは、ファイルサイズを削減するための最適化であり、リンカやOSのローダーがプログラムをメモリにロードする際に、`.bss`セクションに対応するメモリ領域をゼロで埋める責任を負います。

Go言語の`debug/pe`パッケージは、PEファイルを解析し、その構造やセクションのデータにアクセスするための機能を提供します。このパッケージの以前の実装では、`.bss`セクションのデータにアクセスしようとした場合、ファイル内の対応するオフセットからデータを読み取ろうとしていました。しかし、`.bss`セクションはファイル内に実際のデータを持たないため、この操作は未定義の、いわゆる「ゴミデータ」を返していました。

この挙動は、PEファイルを解析してデバッグ情報などを扱う際に問題となります。特に、`.bss`セクションの内容がゼロであるという前提に依存するツールや解析ロジックにとっては、誤ったデータが返されることはバグの原因となります。Issue #15345 はこの問題点を指摘しており、このコミットはその解決を目的としています。

## 前提知識の解説

### PE (Portable Executable) ファイルフォーマット

PEは、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLL (Dynamic Link Library) などのファイルフォーマットです。COFF (Common Object File Format) をベースにしており、以下のような主要な構造を持ちます。

*   **DOS Header**: 互換性のために存在する古いDOS実行可能ファイルのヘッダ。
*   **PE Signature**: "PE\0\0"というシグネチャ。
*   **COFF File Header**: マシンタイプ、セクション数、タイムスタンプなどの基本的な情報。
*   **Optional Header**: 実行可能ファイルのロードアドレス、エントリポイント、セクションアライメントなどの詳細情報。
*   **Section Table**: ファイル内の各セクション（コード、データなど）に関する情報（名前、仮想アドレス、サイズ、ファイル内のオフセットなど）の配列。
*   **Sections**: 実際のコードやデータが格納されている領域。

### `.bss`セクション

`.bss`セクションは、PEファイルを含む多くの実行可能ファイルフォーマット（ELF、Mach-Oなど）に存在する標準的なセクションです。

*   **目的**: 初期化されていないグローバル変数および静的変数を格納します。
*   **特徴**:
    *   **ファイルサイズ**: 通常、ファイル内には実際のデータが格納されません。これにより、実行可能ファイルのサイズを小さく保つことができます。
    *   **メモリ初期化**: プログラムがメモリにロードされる際、OSのローダーまたはリンカによって、このセクションに対応するメモリ領域はすべてゼロで初期化されます。これは、C言語などの仕様で保証されている動作です。
    *   **`PointerToRawData`**: PEファイルのセクションヘッダには`PointerToRawData`というフィールドがあり、これはセクションのデータがファイル内でどこから始まるかを示します。`.bss`セクションの場合、このフィールドは通常`0`になります。これは、ファイル内にデータが存在しないことを示唆しています。

### `io.ReaderAt`と`io.SectionReader`

Go言語の標準ライブラリ`io`パッケージは、I/O操作のための強力なインターフェースを提供します。

*   **`io.ReaderAt`**:
    ```go
    type ReaderAt interface {
        ReadAt(p []byte, off int64) (n int, err error)
    }
    ```
    このインターフェースは、任意のオフセットからデータを読み取る機能を提供します。ファイルやメモリマップされたデータなど、ランダムアクセスが可能なデータソースに適しています。`ReadAt`は、`p`スライスに`off`で指定されたオフセットからデータを読み込み、読み込んだバイト数とエラーを返します。

*   **`io.SectionReader`**:
    `io.SectionReader`は、既存の`io.ReaderAt`から特定のセクション（範囲）を読み取るための構造体です。これは、大きなデータソースの一部をあたかも独立した`io.ReaderAt`であるかのように扱うことを可能にします。`io.SectionReader`は、元の`io.ReaderAt`と、読み取るセクションの開始オフセット、およびそのセクションの長さを指定して作成されます。

### Goの`debug/pe`パッケージ

`debug/pe`パッケージは、GoプログラムがWindowsのPEファイルを解析するための機能を提供します。このパッケージを使用することで、PEファイルのヘッダ情報、セクションテーブル、各セクションのデータなどにアクセスできます。デバッガ、リンカ、またはPEファイルを検査するツールを作成する際に利用されます。

## 技術的詳細

このコミットの技術的な核心は、`debug/pe`パッケージがPEファイルのセクションデータを扱う方法、特に`.bss`セクションの処理を改善することにあります。

`debug/pe`パッケージの`NewFile`関数は、PEファイルを解析し、そのセクション情報を`File`構造体に格納します。各セクションは`Section`構造体で表現され、その中に`io.SectionReader` (`s.sr`) を保持しています。この`io.SectionReader`は、元のPEファイルを表す`io.ReaderAt`から、セクションのデータが格納されている範囲を読み取るために使用されます。

問題は、`.bss`セクションのようにファイル内に実際のデータを持たないセクションの場合、`SectionHeader.PointerToRawData`フィールドが`0`になることです。以前の実装では、この`PointerToRawData`が`0`であっても、元の`io.ReaderAt` (`r`) をそのまま`io.NewSectionReader`に渡していました。その結果、`(*Section).Data`メソッドが呼び出された際に、ファイル内の無関係なオフセットからデータが読み取られ、ゴミデータが返されていました。

このコミットでは、この挙動を修正するために以下の変更が加えられました。

1.  **`zeroReaderAt`構造体の導入**:
    `zeroReaderAt`という新しい型が定義されました。これは`io.ReaderAt`インターフェースを実装しており、その`ReadAt`メソッドは、要求されたバイト数だけゼロを書き込んだスライスを返します。これにより、ファイル内の実際のデータに依存せず、常にゼロを供給する`io.ReaderAt`が提供されます。

    ```go
    type zeroReaderAt struct{}

    func (w zeroReaderAt) ReadAt(p []byte, off int64) (n int, err error) {
        for i := range p {
            p[i] = 0
        }
        return len(p), nil
    }
    ```

2.  **`NewFile`関数での条件付き`ReaderAt`選択**:
    `NewFile`関数内でセクションを処理するループにおいて、各セクションの`SectionHeader.PointerToRawData`が`0`であるかどうかがチェックされます。
    *   もし`PointerToRawData`が`0`であれば（これは通常`.bss`セクションに該当します）、`zeroReaderAt{}`のインスタンスが`io.NewSectionReader`に渡されます。これにより、このセクションからデータを読み取ろうとすると、`zeroReaderAt`が常にゼロを返すようになります。
    *   `PointerToRawData`が`0`でなければ、元のPEファイルを表す`io.ReaderAt` (`r`) がそのまま使用されます。

    ```go
    // 変更前
    // s.sr = io.NewSectionReader(r, int64(s.SectionHeader.Offset), int64(s.SectionHeader.Size))

    // 変更後
    r2 := r
    if sh.PointerToRawData == 0 { // .bss must have all 0s
        r2 = zeroReaderAt{}
    }
    s.sr = io.NewSectionReader(r2, int64(s.SectionHeader.Offset), int64(s.SectionHeader.Size))
    ```

この修正により、`debug/pe`パッケージは、PEファイルの`.bss`セクションのデータを読み取る際に、リンカやローダーが提供するのと同じように、常にゼロ初期化されたデータを提供するようになりました。これは、PEファイル解析の正確性を向上させ、`.bss`セクションのゼロ初期化に依存するツールとの互換性を確保します。

## コアとなるコードの解説

### `src/debug/pe/file.go` の変更

1.  **`zeroReaderAt` 型の追加**:
    この新しい型は、`io.ReaderAt`インターフェースを満たすように設計されています。その`ReadAt`メソッドは、呼び出されると、渡されたバイトスライス`p`のすべての要素を`0`で埋めます。これにより、ファイル内の実際のデータに依存せず、常にゼロを返すデータソースとして機能します。これは、`.bss`セクションがメモリ上でゼロ初期化されるという特性をエミュレートするために不可欠です。

2.  **`NewFile` 関数内のロジック変更**:
    `NewFile`関数はPEファイルを解析し、各セクションの`Section`オブジェクトを作成します。この修正の中心は、各セクションの`io.SectionReader` (`s.sr`) を初期化する部分です。
    *   `sh.PointerToRawData == 0`という条件が追加されました。`PointerToRawData`は、セクションのデータがPEファイル内でどこから始まるかを示すオフセットです。この値が`0`である場合、そのセクションはファイル内に実際のデータを持たないことを意味し、通常は`.bss`セクションに該当します。
    *   この条件が真の場合、`r2`変数には`zeroReaderAt{}`のインスタンスが代入されます。これにより、このセクションの`io.SectionReader`は、`zeroReaderAt`からデータを読み取るようになります。
    *   条件が偽の場合（つまり、セクションがファイル内にデータを持つ場合）、`r2`は元のPEファイルを表す`io.ReaderAt` (`r`) のままとなり、通常のファイル読み取りが行われます。

この変更により、`debug/pe`パッケージは、`.bss`セクションのデータアクセスに対して、そのセマンティクス（ゼロ初期化）を正しく反映するようになりました。

### `src/debug/pe/file_test.go` の変更

`TestBSSHasZeros`という新しいテスト関数が追加されました。このテストは、修正が正しく機能することを確認するためのものです。

1.  **環境チェック**:
    *   `testenv.MustHaveExec(t)`: 外部コマンドの実行が可能であることを確認します。
    *   `runtime.GOOS != "windows"`: このテストはWindows固有のPEファイルフォーマットに依存するため、Windows環境でのみ実行されます。
    *   `exec.LookPath("gcc")`: Cコンパイラ`gcc`がシステムに存在することを確認します。これは、`.bss`セクションを持つPEオブジェクトファイルを生成するために必要です。

2.  **テストファイルの生成**:
    *   一時ディレクトリが作成されます。
    *   `a.c`というCソースファイルが作成されます。このファイルには、`int zero = 0;`という初期化されていないグローバル変数が含まれています。C言語の仕様により、これは`.bss`セクションに配置され、実行時にゼロ初期化されることが保証されます。

3.  **オブジェクトファイルのコンパイル**:
    *   `gcc -c a.c -o a.obj`コマンドを使用して、`a.c`をオブジェクトファイル`a.obj`にコンパイルします。この`a.obj`が、テスト対象のPEファイルとなります。

4.  **PEファイルの解析と`.bss`セクションの検証**:
    *   `pe.Open(objpath)`: 生成された`a.obj`ファイルを`debug/pe`パッケージで開きます。
    *   セクションのリストをイテレートし、名前が`.bss`であるセクションを探します。
    *   `.bss`セクションが見つかったら、`bss.Data()`を呼び出してその内容を読み取ります。
    *   読み取られたデータスライスの長さが`0`でないことを確認します（`.bss`セクションは通常、変数のサイズ分の領域を確保するため空ではない）。
    *   最後に、データスライスのすべてのバイトが`0`であることを確認します。もし`0`以外のバイトが見つかった場合、テストは失敗し、修正が正しく機能していないことを示します。

このテストは、実際のPEファイルを生成し、その`.bss`セクションの内容を`debug/pe`パッケージを通じて検証することで、修正の正確性と堅牢性を保証しています。

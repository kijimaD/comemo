# [インデックス 24533] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおける重要な改善を導入しています。具体的には、次回のGCサイクルが開始されるトリガーヒープサイズ（`next_gc`）が、現在の割り当て済みヒープサイズ（`heap_live`）よりも小さくなる可能性があった問題を修正し、コンカレントスイープが適切に実行されるための十分なヒープ距離を確保することを目的としています。これにより、GCの起動遅延やミューテーターアシストの増加を防ぎ、全体的なGCの効率とアプリケーションのパフォーマンスを向上させます。

## 変更の背景

Go 1.5で導入されたコンカレントGCは、アプリケーションの実行と並行してガベージコレクションの大部分を実行することで、"Stop-The-World" (STW) ポーズ時間を大幅に短縮しました。このコンカレントGCの重要な要素の一つに「コンカレントスイープ」があります。これは、GCサイクル間で、アプリケーションがメモリを割り当てている間に、バックグラウンドで不要なメモリ領域を解放する処理です。

しかし、このコミット以前のGoランタイムでは、次回のGCサイクルをトリガーするヒープサイズである `next_gc` の計算に問題がありました。特定の条件下（特に `gcpercent` の値が低い場合や、到達可能なヒープの推定値が実際のライブヒープサイズよりも小さい場合）において、`next_gc` が現在のライブヒープサイズ `heap_live` よりも小さく設定されてしまう可能性がありました。

このような状況が発生すると、GCサイクルが終了した直後に、次のGCサイクルが即座にトリガーされてしまいます。これにより、コンカレントスイープが実行されるための「ヒープの成長期間」が事実上なくなり、スイープ処理の完了責任が次のGCサイクル自体に押し付けられることになります。結果として、GCの起動が遅延し、アプリケーションの実行を一時停止させてGCを手伝わせる「ミューテーターアシスト」の発生頻度が増加し、アプリケーションのレイテンシやスループットに悪影響を及ぼしていました。

このコミットは、この問題を解決し、コンカレントスイープが常に実行されるための十分な時間とヒープ領域を確保することを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語のガベージコレクションは、主に**マーク＆スイープ**アルゴリズムをベースにしています。Go 1.5以降、このGCは**コンカレント（並行）**に動作するように設計されており、アプリケーションの実行（ミューテーター）とGC処理が同時に進行します。

*   **マークフェーズ**: プログラムが使用しているオブジェクト（ライブオブジェクト）を特定し、マークする段階です。Go 1.5以降では、このフェーズの大部分がミューテーターと並行して実行されます。
*   **スイープフェーズ**: マークされなかったオブジェクト（不要なオブジェクト）が占めていたメモリ領域を解放し、再利用可能にする段階です。

### コンカレントGCとコンカレントスイープ

Go 1.5で導入されたコンカレントGCは、GCポーズ時間をミリ秒以下に抑えることを目標としています。そのために、マークフェーズとスイープフェーズの大部分をアプリケーションの実行と並行して行います。

*   **コンカレントスイープ**: GCサイクルが完了した後、次のGCサイクルが開始されるまでの間に、バックグラウンドでメモリの解放（スイープ）を行う処理です。これにより、アプリケーションがメモリを割り当てている間に、GCがメモリをクリーンアップし続けることができます。コンカレントスイープは、ヒープが成長するにつれて徐々に実行され、次のGCが始まるまでに完了することが理想とされます。

### `next_gc` と `gcpercent`

Goランタイムは、次回のGCサイクルをいつ開始するかを決定するためにいくつかの内部変数と設定を使用します。

*   **`next_gc`**: 次のGCサイクルがトリガーされる目標ヒープサイズ（バイト単位）を示す内部変数です。現在のヒープサイズが `next_gc` に達すると、GCが開始されます。
*   **`gcpercent` (GOGC)**: ガベージコレクタの積極性を制御する重要な設定値です。環境変数 `GOGC` または `runtime/debug.SetGCPercent` で設定できます。デフォルト値は100です。
    *   `gcpercent` は、前回のGC後に残ったライブヒープサイズ（`heap_live`）に対して、ヒープがどれだけ成長したら次のGCを開始するかをパーセンテージで指定します。例えば、`GOGC=100` の場合、ライブヒープサイズが前回の2倍（100%成長）になったときに次のGCがトリガーされます。
    *   `next_gc` は通常、`heap_live * (1 + gcpercent / 100)` のような式で計算されます。

### `heap_live`

*   **`heap_live`**: 前回のGCサイクルが完了した時点で、プログラムによってまだ使用されている（到達可能な）オブジェクトが占めるヒープメモリの量（バイト単位）です。これは、GCが次の `next_gc` を計算する際の基準となります。

### ミューテーターアシスト

GCがアプリケーションのメモリ割り当て速度に追いつけない場合、アプリケーションの実行スレッド（ミューテーター）がGCを手伝うことがあります。これを**ミューテーターアシスト**と呼びます。ミューテーターアシストが発生すると、アプリケーションの実行が一時的に停止し、GC処理に時間を費やすため、アプリケーションのパフォーマンスが低下します。コンカレントGCの目標は、ミューテーターアシストを最小限に抑えることです。

## 技術的詳細

このコミットが解決しようとしている問題は、`next_gc` の計算が不適切であると、コンカレントスイープが機能不全に陥る可能性があるという点です。

1.  **問題の発生**:
    *   GCサイクルが完了した後、ランタイムは次の `next_gc` 値を計算します。この計算は、前回のGCでマークされたライブオブジェクトの量 (`heap_live`) と `gcpercent` に基づいて行われます。
    *   しかし、何らかの理由（例えば、`gcpercent` が非常に低い値に設定されている場合や、GCがライブヒープサイズを過小評価した場合）で、計算された `next_gc` が、現在の `heap_live` よりも小さくなってしまうことがありました。
    *   このような状況では、GCサイクルが終了した瞬間に、現在のヒープサイズが既に `next_gc` を超えているため、次のGCサイクルが即座にトリガーされてしまいます。

2.  **コンカレントスイープへの影響**:
    *   コンカレントスイープは、GCサイクルと次のGCサイクルの間の「ヒープが成長する期間」を利用して、バックグラウンドでメモリを解放します。
    *   `next_gc` が `heap_live` よりも小さい場合、この「ヒープが成長する期間」が存在しないため、コンカレントスイープが実行される機会が失われます。
    *   結果として、スイープ処理の完了が次のGCサイクルに持ち越され、GCの起動が遅延したり、ミューテーターアシストが増加したりする原因となります。

3.  **解決策**:
    *   このコミットは、`next_gc` が常に現在のライブヒープサイズ `heap_live` よりも「少しだけ」大きくなるように保証することで、この問題を解決します。
    *   具体的には、`sweepMinHeapDistance` という新しい定数を導入し、`next_gc` が `heap_live + sweepMinHeapDistance * gcpercent / 100` で計算される最小値よりも小さくならないように調整します。
    *   これにより、たとえ通常の `next_gc` の計算結果が低くても、コンカレントスイープが実行されるための最低限のヒープ成長距離が確保され、次のGCが即座にトリガーされることを防ぎます。

この変更により、GoランタイムはGCサイクル間のコンカレントスイープをより確実に実行できるようになり、GCの効率が向上し、アプリケーションのSTWポーズ時間の短縮に貢献します。

## コアとなるコードの解説

### `sweepMinHeapDistance` 定数の追加

```go
	// sweepMinHeapDistance is a lower bound on the heap distance
	// (in bytes) reserved for concurrent sweeping between GC
	// cycles. This will be scaled by gcpercent/100.
	sweepMinHeapDistance = 1024 * 1024
```

*   `sweepMinHeapDistance` は、コンカレントスイープのために確保されるべき最小のヒープ成長距離をバイト単位で定義しています。ここでは `1024 * 1024`、つまり1MBに設定されています。
*   この値は、`gcpercent/100` でスケーリングされることがコメントで示されており、`gcpercent` の設定に応じて動的に調整されることを意味します。これにより、`gcpercent` が低い場合でも、コンカレントスイープのための絶対的な最小ヒープ距離が保証されます。

### `gcMark` 関数内の `next_gc` 調整ロジック

`gcMark` 関数は、GCのマークフェーズが完了した後に呼び出され、次のGCサイクルに向けた準備を行います。この関数内で、`next_gc` の値が調整されます。

```go
	minNextGC := memstats.heap_live + sweepMinHeapDistance*uint64(gcpercent)/100
	if memstats.next_gc < minNextGC {
		// The allocated heap is already past the trigger.
		// This can happen if the triggerRatio is very low and
		// the reachable heap estimate is less than the live
		// heap size.
		//
		// Concurrent sweep happens in the heap growth from
		// heap_live to next_gc, so bump next_gc up to ensure
		// that concurrent sweep has some heap growth in which
		// to perform sweeping before we start the next GC
		// cycle.
		memstats.next_gc = minNextGC
	}
```

1.  **`minNextGC` の計算**:
    *   `minNextGC` は、次のGCがトリガーされるべき最小のヒープサイズを計算します。
    *   計算式は `memstats.heap_live + sweepMinHeapDistance*uint64(gcpercent)/100` です。
    *   これは、現在のライブヒープサイズ (`memstats.heap_live`) に、`sweepMinHeapDistance` を `gcpercent` でスケーリングした値を加算したものです。
    *   例えば、`gcpercent` が100（デフォルト）の場合、`minNextGC` は `memstats.heap_live + 1MB` となります。これにより、ライブヒープサイズから少なくとも1MBのヒープ成長が許容されることになります。

2.  **`next_gc` の調整**:
    *   `if memstats.next_gc < minNextGC` の条件は、既存の `next_gc` の値が、計算された `minNextGC` よりも小さい場合に真となります。
    *   これは、通常の `next_gc` の計算結果が、コンカレントスイープに必要な最小限のヒープ成長距離を確保できていない状況を意味します。
    *   この条件が真の場合、`memstats.next_gc = minNextGC` によって、`next_gc` の値が `minNextGC` に引き上げられます。
    *   この調整により、次のGCサイクルが開始されるまでに、少なくとも `sweepMinHeapDistance * gcpercent / 100` 分のヒープ成長が保証され、その期間中にコンカレントスイープが実行されるための十分な時間が確保されます。

この変更は、GoランタイムのGCスケジューリングの堅牢性を高め、コンカレントスイープの効率的な動作を保証することで、アプリケーションの安定したパフォーマンスに貢献します。

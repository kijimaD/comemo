# [インデックス 26446] ファイルの概要

このコミットは、GoランタイムがNetBSDおよびDragonFly BSDシステム上でシグナルスタックを処理する方法に関する重要な変更を導入しています。具体的には、`pthread_create`によって作成されたCスレッドが、Goスレッドからシグナルスタックを継承してしまう問題に対処するため、Goランタイムが常に新しいシグナルスタックをインストールするように修正されています。これにより、複数のシグナルが同時に発生した場合に起こりうる「カオス」を回避し、GoとCの相互運用性における安定性を向上させています。

## 変更の背景

この変更は、NetBSDおよびDragonFly BSDシステムにおけるGoランタイムのシグナル処理のバグを修正するために導入されました。主な問題は以下の通りです。

1.  **シグナルスタックの継承**: NetBSDおよびDragonFlyでは、`pthread_create`によって新しいスレッドが作成されると、そのスレッドは親スレッドのシグナルスタックを継承します。
2.  **Cgoプログラムでの問題**: GoプログラムがCgoを介してCコードと連携する場合、Goランタイムが管理するGoスレッドがCスレッドを作成することがあります。このとき、作成されたCスレッドはGoスレッドのシグナルスタックを継承してしまいます。
3.  **同時シグナルによる「カオス」**: 複数のスレッドが同じシグナルスタックを共有している状態で、同時にシグナルが発生すると、スタックの破損や予期せぬ動作（「カオス」と表現されています）を引き起こす可能性がありました。これは、シグナルハンドラが実行される際に、そのスタック領域が他のスレッドによって使用されている可能性があるためです。
4.  **Go 1.5の動作との整合性**: コミットメッセージには「Still, this is the 1.5 behavior.」とあり、Go 1.5の動作との整合性を保ちつつ、この問題に対処する必要があったことが示唆されています。Go 1.5では、Goランタイムがスレッドの管理方法を大きく変更し、OSスレッドとGoのgoroutineの対応関係がより密接になりました。この変更は、その新しいモデルにおけるシグナル処理の堅牢性を高めるものです。
5.  **関連するIssueの修正**: このコミットは、以下のGo issueを修正します。
    *   **Issue #14051**: NetBSDでのシグナルスタックの問題に関連する可能性があります。
    *   **Issue #14052**: DragonFly BSDでのシグナルスタックの問題に関連する可能性があります。
    *   **Issue #14067**: 一般的なシグナル処理の堅牢性に関連する可能性があります。

これらの問題は、特にCgoを使用してGoとCのコードを混在させるアプリケーションにおいて、不安定性やクラッシュの原因となる可能性がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

*   **シグナル (Signals)**: オペレーティングシステムがプロセスやスレッドに非同期的にイベントを通知するメカニズムです。例えば、Ctrl+Cによる割り込み（SIGINT）、不正なメモリアクセス（SIGSEGV）、タイマーの期限切れ（SIGALRM）などがあります。シグナルを受け取ったプロセスは、デフォルトの動作を実行するか、登録されたシグナルハンドラ関数を実行します。
*   **シグナルスタック (Signal Stack)**: 通常、シグナルハンドラは通常の実行スタック上で実行されます。しかし、スタックオーバーフローが発生している状況でシグナルが届いた場合、シグナルハンドラが実行されるための十分なスタック領域がない可能性があります。これを避けるために、OSは代替のシグナルスタック（またはシグナルスタックフレーム）を提供します。`sigaltstack`システムコールを使用して、プロセスはシグナルハンドラが実行されるための専用のスタック領域を設定できます。これにより、通常のスタックが破損している場合でも、シグナルハンドラが安全に実行できるようになります。
*   **`pthread_create`**: POSIXスレッド（pthreads）ライブラリの一部であり、新しいスレッドを作成するためのC言語の関数です。この関数によって作成されたスレッドは、親スレッドから様々な属性（シグナルマスク、スケジューリングポリシーなど）を継承することがあります。NetBSDおよびDragonFly BSDでは、シグナルスタックも継承されるというOS固有の動作があります。
*   **Cgo**: Go言語の機能の一つで、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGo言語のコードを呼び出したりすることを可能にします。Cgoを使用すると、GoのランタイムとCのランタイムが同じプロセス空間内で共存するため、両者の間の相互作用、特にスレッドやシグナル処理に関する調整が重要になります。
*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（goroutineの管理）、メモリ管理、そしてシグナル処理などが含まれます。Goランタイムは、OSスレッドを抽象化し、その上で多数の軽量なgoroutineを効率的に実行します。
*   **`minit()` 関数**: Goランタイムの初期化プロセスの一部として、各OSスレッド（M: Machine）が起動する際に呼び出される関数です。この関数は、スレッド固有の初期化、例えばシグナルハンドリングの設定などを行います。
*   **`_g_.m.gsignal.stack`**: Goランタイム内部のデータ構造で、現在のGoスケジューラM（OSスレッド）に関連付けられたシグナルスタックの情報を保持します。
*   **`_g_.m.newSigstack`**: Goランタイム内部のフラグで、現在のMが新しいシグナルスタックを割り当てたかどうかを示します。

## 技術的詳細

このコミットの技術的な核心は、NetBSDおよびDragonFly BSDにおけるシグナルスタックの継承問題への対処です。

**問題点**:
NetBSDとDragonFlyでは、`pthread_create`で新しいスレッドが生成されると、そのスレッドは親スレッドのシグナルスタックを継承します。Cgoプログラムにおいて、Goランタイムが管理するGoスレッドがCスレッドを生成した場合、そのCスレッドはGoスレッドのシグナルスタックを継承してしまいます。これにより、GoスレッドとCスレッドが同じシグナルスタックを共有することになり、同時にシグナルが発生した場合にスタックの破損や競合状態が発生し、「カオス」と呼ばれる不安定な状態を引き起こす可能性がありました。

**Go 1.5以前の動作 (変更前)**:
変更前のコードでは、`minit()`関数内で`sigaltstack(nil, &st)`を呼び出し、既存のシグナルスタックがあるかどうかを確認していました。
*   もし既存のシグナルスタックが無効（`_SS_DISABLE`フラグが立っている）であれば、`signalstack(&_g_.m.gsignal.stack)`を呼び出して新しいシグナルスタックをインストールし、`_g_.m.newSigstack = true`を設定していました。
*   既存のシグナルスタックが存在する場合は、そのスタック情報を`_g_.m.gsignal.stack`にコピーし、`_g_.m.newSigstack = false`を設定して、既存のスタックを再利用していました。

この「既存のシグナルスタックを再利用する」というロジックが、NetBSDとDragonFlyのシグナルスタック継承の特性と組み合わさることで問題を引き起こしていました。CスレッドがGoスレッドのシグナルスタックを継承し、Goランタイムがそれを「既存のスタック」として認識して再利用しようとすると、複数のスレッドが同じスタックを共有する状況が生まれてしまいます。

**このコミットによる変更 (変更後)**:
このコミットでは、`src/runtime/os1_dragonfly.go`と`src/runtime/os1_netbsd.go`の`minit()`関数から、既存のシグナルスタックをチェックして再利用するロジックが完全に削除されました。代わりに、以下のコードが常に実行されるようになりました。

```go
	signalstack(&_g_.m.gsignal.stack)
	_g_.m.newSigstack = true
```

これにより、NetBSDおよびDragonFly BSDシステムでは、Goランタイムが管理する各OSスレッド（M）が起動する際に、**常に新しい専用のシグナルスタックをインストールする**ようになります。

**トレードオフと限界**:
コミットメッセージには、この変更がもたらすトレードオフについても言及されています。

> This breaks the case of a C thread that calls sigaltstack and then calls a Go function, because we will drop the C thread's alternate signal stack as we return from Go. Still, this is the 1.5 behavior. And what else can we do?

これは、Cスレッドが`sigaltstack`を呼び出して独自の代替シグナルスタックを設定した後、Go関数を呼び出すようなシナリオで問題が発生する可能性を示しています。Go関数からCに戻る際に、GoランタイムがCスレッドの代替シグナルスタックの追跡を失い、それを破棄してしまうためです。しかし、コミットメッセージは、これがGo 1.5の動作であり、「他に何ができるのか？」と問いかけており、この状況下での最善の解決策であることを示唆しています。GoランタイムがCのシグナルスタック管理に深く介入することは難しく、Goのメモリモデルとシグナル処理の整合性を優先した結果と言えます。

要するに、この変更は、GoランタイムがCgoを介してCスレッドと連携する際のシグナル処理の堅牢性を高めるために、特定のOS（NetBSD, DragonFly）におけるシグナルスタックの継承問題を回避するものです。これにより、Goプログラムの安定性が向上しますが、Cコード側で`sigaltstack`を積極的に使用する特定のケースでは、Goとの相互運用に注意が必要になる可能性があります。

## コアとなるコードの変更箇所

変更は主に以下の2つのファイルにあります。

*   `src/runtime/os1_dragonfly.go`
*   `src/runtime/os1_netbsd.go`

それぞれのファイルの`minit()`関数内で、シグナルスタックの初期化ロジックが変更されています。

**変更前 (例: `src/runtime/os1_dragonfly.go`)**:

```go
func minit() {
	// ...
	// Initialize signal handling
	var st sigaltstackt
	sigaltstack(nil, &st)
	if st.ss_flags&_SS_DISABLE != 0 {
		signalstack(&_g_.m.gsignal.stack)
		_g_.m.newSigstack = true
	} else {
		// Use existing signal stack.
		stsp := uintptr(unsafe.Pointer(st.ss_sp))
		_g_.m.gsignal.stack.lo = stsp
		_g_.m.gsignal.stack.hi = stsp + st.ss_size
		_g_.m.gsignal.stackguard0 = stsp + _StackGuard
		_g_.m.gsignal.stackguard1 = stsp + _StackGuard
		_g_.m.gsignal.stackAlloc = st.ss_size
		_g_.m.newSigstack = false
	}
	// ...
}
```

**変更後 (例: `src/runtime/os1_dragonfly.go`)**:

```go
func minit() {
	// ...
	// Initialize signal handling.

	// On DragonFly a thread created by pthread_create inherits
	// the signal stack of the creating thread.  We always create
	// a new signal stack here, to avoid having two Go threads
	// using the same signal stack.  This breaks the case of a
	// thread created in C that calls sigaltstack and then calls a
	// Go function, because we will lose track of the C code's
	// sigaltstack, but it's the best we can do.
	signalstack(&_g_.m.gsignal.stack)
	_g_.m.newSigstack = true
	// ...
}
```

両方のファイルで、`sigaltstack`を呼び出して既存のシグナルスタックをチェックし、それを再利用する条件分岐が削除され、常に`signalstack(&_g_.m.gsignal.stack)`と`_g_.m.newSigstack = true`が実行されるようになっています。

## コアとなるコードの解説

変更されたコードの核心は、Goランタイムが各OSスレッド（M）に対して、シグナル処理のために**常に新しい専用のシグナルスタックを割り当てる**ようにした点です。

1.  **`minit()` 関数**:
    この関数は、Goランタイムが新しいOSスレッド（M）を初期化する際に呼び出されます。Goのスケジューラは、必要に応じてOSスレッドを起動し、そのスレッド上でgoroutineを実行します。`minit()`は、そのOSスレッドがGoの実行環境で適切に機能するために必要な初期設定を行います。

2.  **削除されたロジック**:
    変更前は、`sigaltstack(nil, &st)`を呼び出して、現在のスレッドに既に代替シグナルスタックが設定されているかどうかを確認していました。
    *   `st.ss_flags&_SS_DISABLE != 0` は、代替シグナルスタックが無効化されているか、設定されていない状態をチェックします。この場合、Goランタイムは新しいシグナルスタックを割り当てていました。
    *   `else` ブロックでは、既存のシグナルスタックが存在する場合、その情報をGoランタイムの内部構造体`_g_.m.gsignal.stack`にコピーし、そのスタックを再利用していました。この部分が、NetBSDやDragonFlyでCスレッドがGoスレッドのシグナルスタックを継承する問題を引き起こしていました。

3.  **新しいロジック**:
    変更後は、上記の条件分岐が完全に削除され、以下の2行が常に実行されるようになりました。

    ```go
    signalstack(&_g_.m.gsignal.stack)
    _g_.m.newSigstack = true
    ```

    *   `signalstack(&_g_.m.gsignal.stack)`: この関数は、Goランタイムが管理する`_g_.m.gsignal.stack`構造体で指定された情報に基づいて、OSに対して新しい代替シグナルスタックを設定する役割を担います。これにより、現在のOSスレッドは、他のスレッドと共有されていない、自身専用のシグナルスタックを持つことが保証されます。
    *   `_g_.m.newSigstack = true`: このフラグは、現在のM（OSスレッド）が新しいシグナルスタックを割り当てたことをGoランタイムに通知します。これは、シグナルハンドラが実行される際に、正しいスタックが使用されることを保証するための内部的な状態管理に利用されます。

この変更により、NetBSDおよびDragonFly BSD上でのCgoプログラムにおいて、Goランタイムが管理するスレッドとCライブラリが生成するスレッドの間でシグナルスタックが意図せず共有されることによる競合状態や不安定性が解消されます。各Goスレッドが独自のシグナルスタックを持つことで、シグナル処理の分離と堅牢性が向上します。

2.  **Cgoプログラムでの問題**: GoプログラムがCgoを介してCコードと連携する場合、Goランタイムが管理するGoスレッドがCスレッドを作成することがあります。このとき、作成されたCスレッドはGoスレッドのシグナルスタックを継承してしまいます。
3.  **同時シグナルによる「カオス」**: 複数のスレッドが同じシグナルスタックを共有している状態で、同時にシグナルが発生すると、スタックの破損や予期せぬ動作（「カオス」と表現されています）を引き起こす可能性がありました。これは、シグナルハンドラが実行される際に、そのスタック領域が他のスレッドによって使用されている可能性があるためです。
4.  **Go 1.5の動作との整合性**: コミットメッセージには「Still, this is the 1.5 behavior.」とあり、Go 1.5の動作との整合性を保ちつつ、この問題に対処する必要があったことが示唆されています。Go 1.5では、Goランタイムがスレッドの管理方法を大きく変更し、OSスレッドとGoのgoroutineの対応関係がより密接になりました。この変更は、その新しいモデルにおけるシグナル処理の堅牢性を高めるものです。
5.  **関連するIssueの修正**: このコミットは、以下のGo issueを修正します。
    *   **Issue #14051**: NetBSDでのシグナルスタックの問題に関連する可能性があります。
    *   **Issue #14052**: DragonFly BSDでのシグナルスタックの問題に関連する可能性があります。
    *   **Issue #14067**: 一般的なシグナル処理の堅牢性に関連する可能性があります。

これらの問題は、特にCgoを使用してGoとCのコードを混在させるアプリケーションにおいて、不安定性やクラッシュの原因となる可能性がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

*   **シグナル (Signals)**: オペレーティングシステムがプロセスやスレッドに非同期的にイベントを通知するメカニズムです。例えば、Ctrl+Cによる割り込み（SIGINT）、不正なメモリアクセス（SIGSEGV）、タイマーの期限切れ（SIGALRM）などがあります。シグナルを受け取ったプロセスは、デフォルトの動作を実行するか、登録されたシグナルハンドラ関数を実行します。
*   **シグナルスタック (Signal Stack)**: 通常、シグナルハンドラは通常の実行スタック上で実行されます。しかし、スタックオーバーフローが発生している状況でシグナルが届いた場合、シグナルハンドラが実行されるための十分なスタック領域がない可能性があります。これを避けるために、OSは代替のシグナルスタック（またはシグナルスタックフレーム）を提供します。`sigaltstack`システムコールを使用して、プロセスはシグナルハンドラが実行されるための専用のスタック領域を設定できます。これにより、通常のスタックが破損している場合でも、シグナルハンドラが安全に実行できるようになります。
*   **`pthread_create`**: POSIXスレッド（pthreads）ライブラリの一部であり、新しいスレッドを作成するためのC言語の関数です。この関数によって作成されたスレッドは、親スレッドから様々な属性（シグナルマスク、スケジューリングポリシーなど）を継承することがあります。NetBSDおよびDragonFly BSDでは、シグナルスタックも継承されるというOS固有の動作があります。
*   **Cgo**: Go言語の機能の一つで、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGo言語のコードを呼び出したりすることを可能にします。Cgoを使用すると、GoのランタイムとCのランタイムが同じプロセス空間内で共存するため、両者の間の相互作用、特にスレッドやシグナル処理に関する調整が重要になります。
*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（goroutineの管理）、メモリ管理、そしてシグナル処理などが含まれます。Goランタイムは、OSスレッドを抽象化し、その上で多数の軽量なgoroutineを効率的に実行します。
*   **`minit()` 関数**: Goランタイムの初期化プロセスの一部として、各OSスレッド（M: Machine）が起動する際に呼び出される関数です。この関数は、スレッド固有の初期化、例えばシグナルハンドリングの設定などを行います。
*   **`_g_.m.gsignal.stack`**: Goランタイム内部のデータ構造で、現在のGoスケジューラM（OSスレッド）に関連付けられたシグナルスタックの情報を保持します。
*   **`_g_.m.newSigstack`**: Goランタイム内部のフラグで、現在のMが新しいシグナルスタックを割り当てたかどうかを示します。

## 技術的詳細

このコミットの技術的な核心は、NetBSDおよびDragonFly BSDにおけるシグナルスタックの継承問題への対処です。

**問題点**:
NetBSDとDragonFlyでは、`pthread_create`で新しいスレッドが生成されると、そのスレッドは親スレッドのシグナルスタックを継承します。Cgoプログラムにおいて、Goランタイムが管理するGoスレッドがCスレッドを生成した場合、そのCスレッドはGoスレッドのシグナルスタックを継承してしまいます。これにより、GoスレッドとCスレッドが同じシグナルスタックを共有することになり、同時にシグナルが発生した場合にスタックの破損や競合状態が発生し、「カオス」と呼ばれる不安定な状態を引き起こす可能性がありました。

**Go 1.5以前の動作 (変更前)**:
変更前のコードでは、`minit()`関数内で`sigaltstack(nil, &st)`を呼び出し、既存のシグナルスタックがあるかどうかを確認していました。
*   もし既存のシグナルスタックが無効（`_SS_DISABLE`フラグが立っている）であれば、`signalstack(&_g_.m.gsignal.stack)`を呼び出して新しいシグナルスタックをインストールし、`_g_.m.newSigstack = true`を設定していました。
*   既存のシグナルスタックが存在する場合は、そのスタック情報を`_g_.m.gsignal.stack`にコピーし、`_g_.m.newSigstack = false`を設定して、既存のスタックを再利用していました。

この「既存のシグナルスタックを再利用する」というロジックが、NetBSDとDragonFlyのシグナルスタック継承の特性と組み合わさることで問題を引き起こしていました。CスレッドがGoスレッドのシグナルスタックを継承し、Goランタイムがそれを「既存のスタック」として認識して再利用しようとすると、複数のスレッドが同じスタックを共有する状況が生まれてしまいます。

**このコミットによる変更 (変更後)**:
このコミットでは、`src/runtime/os1_dragonfly.go`と`src/runtime/os1_netbsd.go`の`minit()`関数から、既存のシグナルスタックをチェックして再利用するロジックが完全に削除されました。代わりに、以下のコードが常に実行されるようになりました。

```go
	signalstack(&_g_.m.gsignal.stack)
	_g_.m.newSigstack = true
```

これにより、NetBSDおよびDragonFly BSDシステムでは、Goランタイムが管理する各OSスレッド（M）が起動する際に、**常に新しい専用のシグナルスタックをインストールする**ようになります。

**トレードオフと限界**:
コミットメッセージには、この変更がもたらすトレードオフについても言及されています。

> This breaks the case of a C thread that calls sigaltstack and then calls a Go function, because we will drop the C thread's alternate signal stack as we return from Go. Still, this is the 1.5 behavior. And what else can we do?

これは、Cスレッドが`sigaltstack`を呼び出して独自の代替シグナルスタックを設定した後、Go関数を呼び出すようなシナリオで問題が発生する可能性を示しています。Go関数からCに戻る際に、GoランタイムがCスレッドの代替シグナルスタックの追跡を失い、それを破棄してしまうためです。しかし、コミットメッセージは、これがGo 1.5の動作であり、「他に何ができるのか？」と問いかけており、この状況下での最善の解決策であることを示唆しています。GoランタイムがCのシグナルスタック管理に深く介入することは難しく、Goのメモリモデルとシグナル処理の整合性を優先した結果と言えます。

要するに、この変更は、GoランタイムがCgoを介してCスレッドと連携する際のシグナル処理の堅牢性を高めるために、特定のOS（NetBSD, DragonFly）におけるシグナルスタックの継承問題を回避するものです。これにより、Goプログラムの安定性が向上しますが、Cコード側で`sigaltstack`を積極的に使用する特定のケースでは、Goとの相互運用に注意が必要になる可能性があります。

## コアとなるコードの変更箇所

変更は主に以下の2つのファイルにあります。

*   `src/runtime/os1_dragonfly.go`
*   `src/runtime/os1_netbsd.go`

それぞれのファイルの`minit()`関数内で、シグナルスタックの初期化ロジックが変更されています。

**変更前 (例: `src/runtime/os1_dragonfly.go`)**:

```go
func minit() {
	// ...
	// Initialize signal handling
	var st sigaltstackt
	sigaltstack(nil, &st)
	if st.ss_flags&_SS_DISABLE != 0 {
		signalstack(&_g_.m.gsignal.stack)
		_g_.m.newSigstack = true
	} else {
		// Use existing signal stack.
		stsp := uintptr(unsafe.Pointer(st.ss_sp))
		_g_.m.gsignal.stack.lo = stsp
		_g_.m.gsignal.stack.hi = stsp + st.ss_size
		_g_.m.gsignal.stackguard0 = stsp + _StackGuard
		_g_.m.gsignal.stackguard1 = stsp + _StackGuard
		_g_.m.gsignal.stackAlloc = st.ss_size
		_g_.m.newSigstack = false
	}
	// ...
}
```

**変更後 (例: `src/runtime/os1_dragonfly.go`)**:

```go
func minit() {
	// ...
	// Initialize signal handling.

	// On DragonFly a thread created by pthread_create inherits
	// the signal stack of the creating thread.  We always create
	// a new signal stack here, to avoid having two Go threads
	// using the same signal stack.  This breaks the case of a
	// thread created in C that calls sigaltstack and then calls a
	// Go function, because we will lose track of the C code's
	// sigaltstack, but it's the best we can do.
	signalstack(&_g_.m.gsignal.stack)
	_g_.m.newSigstack = true
	// ...
}
```

両方のファイルで、`sigaltstack`を呼び出して既存のシグナルスタックをチェックし、それを再利用する条件分岐が削除され、常に`signalstack(&_g_.m.gsignal.stack)`と`_g_.m.newSigstack = true`が実行されるようになっています。

## コアとなるコードの解説

変更されたコードの核心は、Goランタイムが各OSスレッド（M）に対して、シグナル処理のために**常に新しい専用のシグナルスタックを割り当てる**ようにした点です。

1.  **`minit()` 関数**:
    この関数は、Goランタイムが新しいOSスレッド（M）を初期化する際に呼び出されます。Goのスケジューラは、必要に応じてOSスレッドを起動し、そのスレッド上でgoroutineを実行します。`minit()`は、そのOSスレッドがGoの実行環境で適切に機能するために必要な初期設定を行います。

2.  **削除されたロジック**:
    変更前は、`sigaltstack(nil, &st)`を呼び出して、現在のスレッドに既に代替シグナルスタックが設定されているかどうかを確認していました。
    *   `st.ss_flags&_SS_DISABLE != 0` は、代替シグナルスタックが無効化されているか、設定されていない状態をチェックします。この場合、Goランタイムは新しいシグナルスタックを割り当てていました。
    *   `else` ブロックでは、既存のシグナルスタックが存在する場合、その情報をGoランタイムの内部構造体`_g_.m.gsignal.stack`にコピーし、そのスタックを再利用していました。この部分が、NetBSDやDragonFlyでCスレッドがGoスレッドのシグナルスタックを継承する問題を引き起こしていました。

3.  **新しいロジック**:
    変更後は、上記の条件分岐が完全に削除され、以下の2行が常に実行されるようになりました。

    ```go
    signalstack(&_g_.m.gsignal.stack)
    _g_.m.newSigstack = true
    ```

    *   `signalstack(&_g_.m.gsignal.stack)`: この関数は、Goランタイムが管理する`_g_.m.gsignal.stack`構造体で指定された情報に基づいて、OSに対して新しい代替シグナルスタックを設定する役割を担います。これにより、現在のOSスレッドは、他のスレッドと共有されていない、自身専用のシグナルスタックを持つことが保証されます。
    *   `_g_.m.newSigstack = true`: このフラグは、現在のM（OSスレッド）が新しいシグナルスタックを割り当てたことをGoランタイムに通知します。これは、シグナルハンドラが実行される際に、正しいスタックが使用されることを保証するための内部的な状態管理に利用されます。

この変更により、NetBSDおよびDragonFly BSD上でのCgoプログラムにおいて、Goランタイムが管理するスレッドとCライブラリが生成するスレッドの間でシグナルスタックが意図せず共有されることによる競合状態や不安定性が解消されます。各Goスレッドが独自のシグナルスタックを持つことで、シグナル処理の分離と堅牢性が向上します。

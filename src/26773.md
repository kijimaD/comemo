# [インデックス 26773] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における`gcWork`の利用方法を統一し、簡素化することを目的としています。具体的には、これまでスタックベースで`gcWork`を使用していた2つの箇所を、P（プロセッサ）ごとに割り当てられた`gcWork`を使用するように変更しています。これにより、GCのワーク管理が一貫性を持ち、コードの理解と保守が容易になります。

## コミット

```
runtime: use only per-P gcWork

Currently most uses of gcWork use the per-P gcWork, but there are two
places that still use a stack-based gcWork. Simplify things by making
these instead use the per-P gcWork.
```

## 元コミット内容

現在のGoランタイムでは、`gcWork`のほとんどの利用箇所でP（プロセッサ）ごとの`gcWork`が使われていますが、2箇所だけスタックベースの`gcWork`が残っていました。このコミットは、これらの残っていた箇所もPごとの`gcWork`を使用するように変更することで、`gcWork`の利用方法を簡素化します。

## 変更の背景

Goのガベージコレクタ（GC）は、アプリケーションの実行と並行して動作するコンカレントなマーク＆スイープ方式を採用しています。このGCのマークフェーズでは、到達可能なオブジェクトを識別し、それらを「グレイオブジェクト」として`gcWork`バッファに追加します。その後、GCゴルーチンやアプリケーションゴルーチン（マークアシスト）がこれらのバッファからオブジェクトを取り出し、そのポインタをスキャンして、新たに発見された到達可能なオブジェクトを再び`gcWork`バッファに戻すという作業を繰り返します。

`gcWork`は、このGC作業を効率的に分散・管理するための重要なデータ構造です。Go 1.5以降、GCのコンカレンシーが強化され、ほとんどのGC作業は各P（論理プロセッサ）に紐付けられた`gcWork`インスタンスを通じて行われるようになりました。これにより、GC作業がCPUコア間で効率的に分散され、Stop-The-World（STW）ポーズの時間を最小限に抑えることができます。

しかし、このコミット以前は、一部のGC処理において、Pに紐付けられた`gcWork`ではなく、関数内で一時的にスタック上に確保される`gcWork`（スタックベースの`gcWork`）が使用されていました。このような混在は、コードの複雑性を増し、GCのワークフローの一貫性を損なう可能性がありました。このコミットの背景には、GCワーク管理のロジックを統一し、より予測可能で効率的なシステムを構築するという意図があります。スタックベースの`gcWork`を廃止し、すべてをPごとの`gcWork`に集約することで、GCの動作がよりシンプルになり、将来的な改善やデバッグが容易になることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とガベージコレクションの仕組みについて理解しておく必要があります。

1.  **M-P-Gモデル**:
    *   **G (Goroutine)**: Goランタイムによって管理される軽量なスレッドのようなものです。数KBの小さなスタックで開始し、必要に応じて動的に伸縮します。
    *   **P (Processor)**: 論理プロカルプロセッサであり、Goコードを実行するためのコンテキストを提供します。通常、CPUコアの数に設定され、実行可能なゴルーチンのローカルキューを持っています。
    *   **M (Machine)**: OSスレッドであり、Goコードを実行します。MはGを実行するためにPを獲得する必要があります。
    Goランタイムは、複数のGをPにスケジュールし、PはMによって実行されます。このモデルにより、Goは複数のコアでゴルーチンを効率的に並行実行できます。

2.  **Goのガベージコレクション (GC)**:
    GoのGCは、コンカレントなトライカラー（三色）マーク＆スイープアルゴリズムです。
    *   **トライカラーマーキング**:
        *   **白 (White)**: まだ到達可能かどうかわからないオブジェクト。GCの開始時にはすべてのオブジェクトが白です。
        *   **灰 (Gray)**: 到達可能であることがわかったが、そのポインタがまだスキャンされていないオブジェクト。
        *   **黒 (Black)**: 到達可能であり、そのポインタがすべてスキャンされたオブジェクト。
    *   **マークフェーズ**: GCの主要なフェーズで、ルートオブジェクト（グローバル変数、ゴルーチンのスタックなど）から開始してオブジェクトグラフを辿り、到達可能なオブジェクトを識別します。このフェーズの大部分はアプリケーションの実行と並行して行われます。
    *   **`gcWork`**: GCのマークフェーズにおいて、グレイオブジェクトのポインタをスキャンする作業を管理するための内部データ構造です。到達可能なオブジェクトが発見されると、`gcWork`バッファに追加され、GCワーカー（GCゴルーチンやマークアシストを行うアプリケーションゴルーチン）によって処理されます。

3.  **`gcWork`の種類**:
    *   **Per-P `gcWork`**: 各P（論理プロセッサ）に紐付けられた`gcWork`インスタンスです。GCのコンカレントな性質を最大限に活かすために、ほとんどのGC作業はこのPごとの`gcWork`を通じて行われます。これにより、GC作業がCPUコア間で効率的に分散され、並行処理のオーバーヘッドが削減されます。
    *   **スタックベースの `gcWork`**: 関数内で一時的にスタック上に確保される`gcWork`インスタンスです。これは、特定のGC処理がPに依存しない、あるいはPのコンテキスト外で実行される場合に用いられることがありました。しかし、Pごとの`gcWork`が主流となる中で、その利用は限定的になっていました。

4.  **`_GCmarktermination`**:
    GCのマークフェーズの終了段階を示すフェーズです。このフェーズでは、マーク作業の最終的な調整や、STWポーズ中に実行される必要のある処理が行われます。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのガベージコレクションにおけるワークキュー管理の一貫性を向上させることにあります。GoのGCは、並行性を最大限に高めるために、各論理プロセッサ（P）に専用の`gcWork`バッファを持たせています。これにより、複数のPが同時にGC作業（オブジェクトのスキャンとマーク）を進めることができ、Stop-The-World（STW）ポーズの時間を短縮しています。

コミット以前は、`src/runtime/mgc.go`内の`gcMark`関数と`gchelper`関数（特に`_GCmarktermination`フェーズ）の2箇所で、Pに紐付けられた`gcWork`ではなく、関数内でローカル変数として宣言されるスタックベースの`gcWork`が使用されていました。

*   **スタックベースの`gcWork`の問題点**:
    *   **一貫性の欠如**: GCワークフロー全体でPごとの`gcWork`が推奨される中、一部でスタックベースの`gcWork`が残っていると、GCのワーク管理ロジックが複雑になり、理解しにくくなります。
    *   **最適化の機会損失**: Pごとの`gcWork`は、Pのローカルキャッシュやスケジューラの特性を活かして効率的に設計されています。スタックベースの`gcWork`は、これらの最適化の恩恵を十分に受けられない可能性があります。
    *   **デバッグの複雑化**: 異なる種類の`gcWork`が混在していると、GC関連のバグが発生した際に、問題の特定とデバッグがより困難になります。

このコミットでは、これらの問題を解決するために、スタックベースの`gcWork`の宣言を削除し、代わりに現在のゴルーチン（G）が実行されているM（OSスレッド）に紐付けられたPの`gcWork`インスタンスへのポインタを取得するように変更しています。

具体的には、以下の変更が行われました。

*   `var gcw gcWork` (スタック上に`gcWork`を宣言)
    ↓
    `gcw := &getg().m.p.ptr().gcw` (現在のPの`gcWork`へのポインタを取得)

ここで、`getg()`は現在のゴルーチン（G）を取得し、`m`はそのGを実行しているM（OSスレッド）、`p`はそのMが現在使用しているP（論理プロセッサ）を指します。`ptr()`はポインタのデリファレンスを行い、最終的にPに紐付けられた`gcw`フィールド（`gcWork`インスタンス）へのポインタを取得しています。

この変更により、GCのワーク管理が完全にPごとの`gcWork`に統一され、GCの内部動作の一貫性と効率が向上します。また、`src/runtime/mgcwork.go`からは、スタックベースの`gcWork`の使用方法に関するコメントが削除され、コードベース全体でPごとの`gcWork`が標準的なアプローチであることが明確に示されています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

`src/runtime/mgc.go`は、Goランタイムのガベージコレクションの主要なロジックを実装しているファイルです。このファイル内の`gcMark`関数と`gchelper`関数が変更されました。

*   **`gcMark`関数内の変更**:
    `gcMark`関数は、GCのマークフェーズを開始する主要な関数の一つです。以前は、この関数内で`var gcw gcWork`という行があり、スタック上に一時的な`gcWork`インスタンスを宣言していました。このコミットでは、この行が`gcw := &getg().m.p.ptr().gcw`に置き換えられました。
    *   `getg()`: 現在実行中のゴルーチン（G）の構造体へのポインタを返します。
    *   `.m`: そのゴルーチンを実行しているOSスレッド（M）の構造体へのポインタです。
    *   `.p`: そのMが現在使用している論理プロセッサ（P）の構造体へのポインタです。
    *   `.ptr()`: ポインタのデリファレンスを行い、Pの実際の構造体を取得します。
    *   `.gcw`: Pの構造体内に定義されている、Pごとの`gcWork`インスタンスです。
    この変更により、`gcMark`関数はスタック上のローカルな`gcWork`ではなく、現在のPに紐付けられたグローバルな`gcWork`インスタンスを使用するようになりました。

*   **`gchelper`関数内の変更**:
    `gchelper`関数は、GCのヘルパーゴルーチンが実行する関数で、GCの様々なフェーズで補助的な役割を果たします。特に`_GCmarktermination`フェーズ（マークフェーズの終了処理）において、以前は`var gcw gcWork`を使用していました。これも同様に`gcw := &_g_.m.p.ptr().gcw`に置き換えられました。`_g_`は現在のゴルーチンを指すグローバル変数です。この変更も、`gcMark`関数と同様に、スタックベースの`gcWork`からPごとの`gcWork`への切り替えを意味します。

これらの変更により、`gcDrain`関数（`gcWork`バッファからオブジェクトをドレインする関数）に渡される`gcWork`インスタンスが、常にPごとの`gcWork`のポインタとなり、GCワークフロー全体で一貫したワーク管理が実現されます。

### `src/runtime/mgcwork.go` の変更

`src/runtime/mgcwork.go`は、`gcWork`データ構造とその操作（`put`、`get`、`dispose`など）を定義しているファイルです。このファイルでは、コードのロジック自体は変更されていませんが、コメントが削除されています。

*   **コメントの削除**:
    以前は、`gcWork`をスタック上で使用する方法に関するコメントブロックが存在しました。
    ```
    //     var gcw gcWork
    //     disable preemption
    //     .. call gcw.put() to produce and gcw.get() to consume ..
    //     gcw.dispose()
    //     enable preemption
    ```
    このコメントは、スタックベースの`gcWork`の利用方法を説明していましたが、今回のコミットでスタックベースの`gcWork`が廃止されたため、不要となり削除されました。これにより、`mgcwork.go`のドキュメントは、Pごとの`gcWork`の使用方法のみを反映するようになり、コードベースの意図がより明確になりました。

これらの変更は、GoランタイムのGCワーク管理を簡素化し、一貫性を高めることで、GCの効率性と保守性を向上させるための重要なステップです。

# [インデックス 25180] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける`append`組み込み関数の処理に関する最適化とバグ修正を目的としています。特に、大きな型の要素をスライスに追加する際の評価順序を調整することで、コンパイラの「lowering pass」が混乱する問題を解決しています。

## コミット

```
commit 9aba7e76f605f7c4fad49886e710152730c34b69
Author: Keith Randall <khr@golang.org>
Date:   Mon Oct 5 13:48:40 2015 -0700

    [dev.ssa] cmd/compile: Eval append args after growslice

    For appending large types, we want to evaluate the
    values being appended after the growslice call, not before.
    Evaluating them before leads to phi operations on large types
    which confuses the lowering pass.

    The order pass has already removed any side-effects from the
    values being appended, so it doesn't matter if we do this
    last eval before or after the growslice call.

    This change fixes a bunch (but not all) of our failed lowerings.
```

## 元コミット内容

このコミットの元のメッセージは以下の通りです。

「[dev.ssa] cmd/compile: growsliceの後にappend引数を評価する

大きな型をappendする場合、appendされる値をgrowslice呼び出しの後に評価したい。growslice呼び出しの前に評価すると、大きな型に対するphi演算が発生し、lowering passが混乱する。

order passは、appendされる値からすべての副作用をすでに削除しているため、この最後の評価をgrowslice呼び出しの前に行うか後に行うかは問題ではない。

この変更により、多くの（すべてではないが）loweringの失敗が修正される。」

## 変更の背景

Goコンパイラは、プログラムをSSA (Static Single Assignment) 形式という中間表現に変換し、様々な最適化を適用してから最終的な機械語を生成します。`append`組み込み関数は、スライスに要素を追加するために使用されますが、スライスの容量が不足している場合は、より大きな新しい基盤配列を割り当てるために`growslice`というランタイム関数が呼び出されます。

このコミット以前は、`append`される引数（追加される値）が`growslice`の呼び出しよりも前に評価されていました。特に、構造体や大きな配列のような「大きな型」を`append`する場合、この評価順序が問題を引き起こしていました。

問題の核心は、`growslice`の前に引数を評価すると、SSA形式において「大きな型」に対するPhi演算（Phiノード）が生成されることにありました。Phi演算は、複数の制御フローパスが合流する点で変数の値を結合するために使用されます。しかし、Goコンパイラのlowering pass（SSAを機械語に近い形に変換するフェーズ）は、大きな型に対する複雑なPhi演算を適切に処理できず、コンパイルの失敗（"failed lowerings"）につながっていました。

この変更の背景には、コンパイラがより堅牢に、そして効率的に`append`操作、特に大きな型を扱う能力を向上させる必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念とSSA形式に関する知識が必要です。

1.  **GoコンパイラとSSA (Static Single Assignment) 形式**:
    *   Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、SSA形式という中間表現に変換します。
    *   SSA形式では、すべての変数が一度だけ定義されます。これにより、データフロー解析や最適化が容易になります。
    *   SSAは「値」と「ブロック」で構成されます。値は演算子、型、引数を持つ基本的な構成要素であり、ブロックは制御フローを表します。

2.  **`append`関数と`growslice`**:
    *   Goの組み込み関数`append`は、スライスに要素を追加します。
    *   スライスの基盤配列の容量が不足している場合、`append`はGoランタイムの`growslice`関数を呼び出します。
    *   `growslice`は、新しいより大きな配列を割り当て、既存の要素を新しい配列にコピーし、追加される要素のためのスペースを確保します。

3.  **大きな型 (Large Types)**:
    *   Goコンパイラの文脈では、大きな型とは、多くのフィールドを持つ構造体や大きな配列など、メモリ上でかなりのサイズを占める型を指します。
    *   これらの型は、レジスタに収まらないことが多く、スタックやヒープに割り当てられるため、コンパイラが最適化を行う上で特別な考慮が必要になることがあります。

4.  **Phi演算 (Phi Operations / Phi Nodes)**:
    *   Phi演算はSSA形式の重要な要素であり、複数の制御フローパスが合流する地点で変数の値を結合するために使用されます。
    *   例えば、`if-else`文の後に、`if`ブロックと`else`ブロックの両方で定義された変数の値は、Phiノードによって結合され、その後のコードで使用される単一のSSA値が生成されます。
    *   Phiノードは、異なるパスから来る「メモリ」の状態をマージするためにも使用されます。

5.  **Lowering Pass**:
    *   Lowering passは、GoコンパイラのSSAバックエンドにおける特殊なフェーズです。
    *   このパスの主な役割は、機械に依存しないSSA表現を、機械に依存する形式に変換することです。
    *   抽象的で汎用的なSSA演算子を、特定のアーキテクチャの具体的な命令に置き換えることで、中間表現を最終的な機械語に近づけます。
    *   このパスは、SSA IR上で実行される一連の最適化パスの一部であり、コード生成された書き換えルールを使用して実装されることもあります。

6.  **Order Pass**:
    *   Goコンパイラのフロントエンドの一部であり、式の評価順序を決定し、副作用を持つ操作を適切に配置する役割を担います。このパスが副作用を削除しているため、`append`される値の評価順序を`growslice`の前後に変更しても、プログラムのセマンティクスは変わらないという前提が成り立ちます。

## 技術的詳細

このコミットの技術的な核心は、`append`操作における引数の評価タイミングの変更です。

以前の実装では、`append`される要素（`n.List.Next`で表される）は、`growslice`の呼び出し（新しいスライスが割り当てられる可能性のある操作）の**前に**評価されていました。この評価が、特に大きな型の場合に問題を引き起こしました。

具体的には、`growslice`の前に大きな型の引数を評価すると、SSA形式においてこれらの大きな型に対するPhi演算が生成されることがありました。Phi演算は、複数の制御フローパスが合流する点で変数の値を結合するために必要ですが、Goコンパイラのlowering passは、大きな型に対する複雑なPhi演算を効率的かつ正確に機械語に変換するのに苦労していました。これにより、コンパイルエラーや非効率なコード生成が発生していました。

このコミットでは、`append`される引数の評価を`growslice`の呼び出し**後**に移動させます。

1.  まず、スライス自体（`n.List.N`）を評価して`slice`というSSA値を取得します。
2.  次に、`growslice`が必要かどうかを判断し、必要であれば`growslice`を呼び出すためのロジックが実行されます。この段階では、`append`される引数はまだ評価されていません。
3.  `growslice`の呼び出しが完了し、新しいスライス（または既存のスライス）のポインタと容量が確定した後で、`append`される引数（`n.List.Next`）が評価され、`args`スライスに格納されます。
4.  最後に、これらの評価された引数がスロットに割り当てられます。

この変更により、`growslice`の呼び出しによって生じる可能性のある制御フローの分岐（容量が足りる場合と足りない場合）の後に、大きな型の引数が評価されるようになります。これにより、大きな型に対するPhi演算の生成が回避されるか、少なくともlowering passが処理しやすい形になります。

コミットメッセージにあるように、「order passは、appendされる値からすべての副作用をすでに削除しているため、この最後の評価をgrowslice呼び出しの前に行うか後に行うかは問題ではない」という点が重要です。副作用がないため、評価順序を変更してもプログラムのセマンティクスは維持されます。

結果として、この変更はGoコンパイラのlowering passが大きな型を伴う`append`操作をより堅牢に処理できるようにし、多くのコンパイル失敗を修正しました。

## コアとなるコードの解説

変更の中心は、`append`される引数を評価するコードブロックの移動です。

**変更前:**

```go
		// Evaluate slice
		slice := s.expr(n.List.N)

		// Evaluate args  <-- ここで引数が評価されていた
		nargs := int64(count(n.List) - 1)
		args := make([]*ssa.Value, 0, nargs)
		for l := n.List.Next; l != nil; l = l.Next {
			args = append(args, s.expr(l.N))
		}

		// Allocate new blocks
		grow := s.f.NewBlock(ssa.BlockPlain)
		assign := s.f.NewBlock(ssa.BlockPlain)

		// Decide if we need to grow
		// ... growsliceの呼び出しロジック ...
```

このコードでは、`growslice`の呼び出しが必要かどうかを判断し、実際に`growslice`が呼び出される前に、`append`される引数（`n.List.Next`）が`s.expr(l.N)`によって評価され、`args`スライスに格納されていました。この早期評価が、大きな型に対するPhi演算の問題を引き起こしていました。

**変更後:**

```go
		// Evaluate slice
		slice := s.expr(n.List.N)

		// Allocate new blocks
		grow := s.f.NewBlock(ssa.BlockPlain)
		assign := s.f.NewBlock(ssa.BlockPlain)

		// Decide if we need to grow
		nargs := int64(count(n.List) - 1) // nargsの計算はgrowsliceの判断に必要なので残る
		// ... growsliceの呼び出しロジック ...

		// assign new elements to slots
		s.startBlock(assign)

		// Evaluate args  <-- ここに引数の評価が移動した
		args := make([]*ssa.Value, 0, nargs)
		for l := n.List.Next; l != nil; l = l.Next {
			args = append(args, s.expr(l.N))
		}

		p = s.variable(&ptrVar, pt)          // generates phi for ptr
		c = s.variable(&capVar, Types[TINT]) // generates phi for cap
		p2 := s.newValue2(ssa.OpPtrIndex, pt, p, l)
```

変更後では、`append`される引数の評価ロジックが、`growslice`の呼び出しを含む「Decide if we need to grow」ブロックと「assign new elements to slots」ブロックの間に移動しています。具体的には、`s.startBlock(assign)`の後に引数が評価されるようになりました。

これにより、`growslice`の呼び出しによって導入される可能性のある制御フローの分岐（スライスが成長するかどうか）が解決された後に、`append`される引数が評価されることになります。この評価順序の変更が、大きな型に対するPhi演算の生成を抑制し、lowering passがよりスムーズに処理できるようになるという効果をもたらします。

`nargs`の計算は、`growslice`が必要かどうかを判断するために、`growslice`の呼び出しロジックの前に残されています。これは、追加される要素の数に基づいて新しい容量を計算する必要があるためです。

# [インデックス 22182] ファイルの概要

このコミットは、Go言語のLinuxシステムコール実装において、従来のシステムコールを`*at`サフィックスを持つ新しいシステムコール（例: `open` を `openat` へ）に置き換えるものです。これは、特にARM64アーキテクチャでレガシーなシステムコールが削除されたことへの対応であり、Goのシステムコールインターフェースの堅牢性と将来性を向上させることを目的としています。

## 開発者の意図

このコミットの主な目的は、Linuxカーネルにおけるシステムコールの進化に対応し、Go言語の`syscall`パッケージを最新の状態に保つことです。特に、ARM64アーキテクチャが従来の（レガシーな）システムコールを廃止し、`*at`サフィックスを持つ新しいシステムコールのみをサポートするようになったことが、この変更の直接的な動機となっています。

従来のシステムコール（例: `open`, `link`, `chmod`）は、パス名を直接引数として受け取ります。これに対し、`*at`システムコール（例: `openat`, `linkat`, `fchmodat`）は、追加の引数としてディレクトリディスクリプタ（`dirfd`）を受け取ります。これにより、パス解決の基準となるディレクトリを明示的に指定できるようになります。

この変更は、Goが将来のLinuxカーネルバージョンや新しいアーキテクチャ（特にARM64）との互換性を維持するために不可欠でした。また、`*at`システムコールは、従来のシステムコールが抱えていたセキュリティ上の問題（特にシンボリックリンク攻撃などの競合状態）を解決し、より堅牢なファイルシステム操作を可能にします。

## 変更の背景

Linuxカーネルでは、ファイルシステム関連の多くのシステムコールに、従来の形式と`*at`サフィックスを持つ新しい形式が存在します。例えば、ファイルを開くためのシステムコールには`open`と`openat`があります。`*at`システムコールは、Linuxカーネル2.6.16で導入され、従来のシステムコールが持ついくつかの問題点を解決するために設計されました。

このコミットが行われた2015年当時、ARM64アーキテクチャは、従来のシステムコールを完全に削除し、`*at`形式のシステムコールのみをサポートする最初のLinuxアーキテクチャとして登場しました。これは、Go言語がARM64をサポートする上で、従来のシステムコールに依存している部分を`*at`システムコールに移行する必要があることを意味しました。

Goの`syscall`パッケージは、Goプログラムから直接Linuxカーネルのシステムコールを呼び出すための低レベルなインターフェースを提供しています。このパッケージが従来のシステムコールに依存し続けると、ARM64のような新しいアーキテクチャでGoプログラムが正しく動作しなくなる可能性がありました。そのため、Goのランタイムチームは、既存のGoプログラムの互換性を維持しつつ、内部的に`*at`システムコールを利用するように`syscall`パッケージを再実装することを決定しました。

この変更は、Goのクロスプラットフォーム対応と、将来のLinuxカーネルの進化への適応能力を向上させる上で重要なステップでした。

## 前提知識の解説

### システムコール (Syscalls)

システムコールは、オペレーティングシステム（OS）のカーネルが提供するサービスに、ユーザー空間のプログラムがアクセスするためのインターフェースです。ファイル操作（ファイルの読み書き、作成、削除）、プロセス管理（プロセスの生成、終了）、ネットワーク通信など、OSの基本的な機能のほとんどはシステムコールを通じて行われます。Go言語のような高レベル言語も、最終的にはこれらのシステムコールを呼び出すことでOSと対話します。

### レガシーシステムコール (Legacy Syscalls)

ここでいう「レガシーシステムコール」とは、`open`, `link`, `chmod`, `chown`, `mkdir`, `mknod`, `readlink`, `rename`, `rmdir`, `symlink`, `unlink` のように、パス名を直接引数として受け取る従来のシステムコールを指します。これらのシステムコールは、指定されたパス名を現在の作業ディレクトリ（カレントディレクトリ）からの相対パスとして解釈するか、絶対パスとして解釈します。

### `*at` システムコール (e.g., `openat`, `fchmodat`, `unlinkat`)

`*at`サフィックスを持つシステムコールは、従来のシステムコールに加えて、追加の引数として「ディレクトリディスクリプタ（`dirfd`）」を受け取ります。この`dirfd`は、パス解決の基準となるディレクトリを示すファイルディスクリプタです。

*   **`dirfd` の役割**:
    *   `dirfd`が有効なディレクトリのファイルディスクリプタである場合、`path`引数はそのディレクトリからの相対パスとして解釈されます。
    *   `dirfd`が特別な値である `_AT_FDCWD` の場合、`path`引数は現在の作業ディレクトリからの相対パスとして解釈されます。これは従来のシステムコールと同じ動作になります。
    *   `path`引数が絶対パスである場合、`dirfd`は無視されます。

### `_AT_FDCWD`

`_AT_FDCWD`は、Linuxカーネルが定義する特別な定数で、`*at`システムコールにおいて「現在の作業ディレクトリ（Current Working Directory）」を意味します。これにより、従来のシステムコールと同じセマンティクスを`*at`システムコールで実現できます。

### なぜ `*at` が必要か？ (Why `*at` is needed)

`*at`システムコールが導入された主な理由は、従来のシステムコールが抱えていた以下の問題点を解決するためです。

1.  **競合状態 (Race Condition) の回避**:
    従来のシステムコールでは、パス名を解決する際に、プログラムがパス名を指定してからカーネルがそのパスを実際に操作するまでの間に、外部からパス名が変更される（例: シンボリックリンクが別のファイルに置き換えられる）可能性があります。これは「シンボリックリンク攻撃」などのセキュリティ脆弱性につながることがありました。
    `*at`システムコールでは、`dirfd`によって操作対象のディレクトリを固定できるため、このような競合状態を大幅に軽減できます。例えば、`openat(dirfd, "file.txt", ...)`とすることで、`dirfd`が指すディレクトリ内の`file.txt`を確実に操作できます。

2.  **堅牢性 (Robustness) の向上**:
    パス解決の基準を明示的に指定できるため、プログラムの動作がより予測可能になります。カレントディレクトリの変更に依存しない操作が可能になり、マルチスレッド環境や複雑なファイルシステム操作を行うプログラムの堅牢性が向上します。

3.  **コンテナ/サンドボックス環境での利用**:
    コンテナ技術やサンドボックス環境では、特定のプロセスがアクセスできるファイルシステム領域を制限することが重要です。`*at`システムコールは、`dirfd`を通じて操作のスコープを限定できるため、このような環境でのセキュリティと隔離性を高めるのに役立ちます。

4.  **新しいアーキテクチャの要件**:
    ARM64のように、一部の新しいアーキテクチャでは、設計の簡素化やセキュリティの強化のために、従来のシステムコールが完全に削除され、`*at`形式のシステムコールのみが提供される場合があります。Goのような言語がこれらの新しいアーキテクチャをサポートするためには、`*at`システムコールへの移行が必須となります。

このコミットは、Goがこれらの利点を享受し、将来のLinux環境に適合するための重要な基盤を築くものです。

## 技術的詳細

このコミットは、Go言語の`syscall`パッケージにおけるLinuxシステムコールの実装を根本的に変更します。Goの`syscall`パッケージは、各アーキテクチャ（386, amd64, arm, ppc64, ppc64leなど）ごとに異なるシステムコール番号や呼び出し規約に対応するために、一部のファイルが自動生成されています（例: `zsyscall_linux_386.go`）。

変更の核心は以下の2点です。

1.  **`syscall_linux.go` におけるラッパー関数の再実装**:
    このファイルでは、Goのユーザーが通常利用する`syscall`パッケージの関数（例: `syscall.Open`, `syscall.Link`）が定義されています。このコミットでは、これらの関数が、対応する`*at`システムコール（例: `syscall.Openat`, `syscall.Linkat`）を内部的に呼び出すように変更されました。
    従来のシステムコールがパス名を直接受け取るのに対し、`*at`システムコールは`dirfd`を必要とします。この`dirfd`には、現在の作業ディレクトリを示す特別な値である`_AT_FDCWD`が渡されます。これにより、Goのユーザーから見たAPIの変更なしに、内部的なシステムコール呼び出しが`*at`バージョンに切り替わります。

2.  **`zsyscall_linux_*.go` ファイルの更新**:
    これらのファイルは、`mksyscall.pl`などのツールによって自動生成される、各システムコールに対応する低レベルなGo関数を含んでいます。このコミットでは、従来のシステムコール（例: `SYS_OPEN`, `SYS_LINK`）に対応する定義が削除され、代わりに`*at`システムコール（例: `SYS_OPENAT`, `SYS_LINKAT`）に対応する定義が追加されました。
    これにより、Goのランタイムが直接呼び出すシステムコールが、従来のバージョンから`*at`バージョンへと切り替わります。

このアプローチにより、Goの既存のコードベースは、`syscall.Open`などの従来の関数名をそのまま使用できますが、その背後ではより現代的で堅牢な`*at`システムコールが利用されるようになります。これは、APIの互換性を保ちつつ、内部実装を最新のLinuxカーネルのベストプラクティスに合わせるための巧妙な方法です。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/syscall/syscall_linux.go`:
    *   `Access`, `Chmod`, `Chown`, `Creat`, `Link`, `Mkdir`, `Mknod`, `Readlink`, `Rename`, `Rmdir`, `Symlink`, `Unlink`, `Unlinkat` といった従来のシステムコールに対応するGoの関数が、それぞれ対応する`*at`システムコール（`Faccessat`, `Fchmodat`, `Fchownat`, `Openat`, `linkat`, `Mkdirat`, `Mknodat`, `readlinkat`, `Renameat`, `unlinkat`, `symlinkat`, `unlinkat`）を呼び出すように変更されています。

    *   `Open`関数も、内部的に`openat(_AT_FDCWD, ...)`を呼び出すように変更されています。
    *   従来のシステムコールに対応する`//sys`ディレクティブ（Goのツールがシステムコールラッパーを生成するために使用）が削除されています。

    *   代わりに、`linkat`, `readlinkat`, `symlinkat`, `unlinkat` といった`*at`システムコールに対応する低レベルなGo関数定義が追加されています。これらの関数は、対応するLinuxシステムコール番号（例: `SYS_LINKAT`, `SYS_READLINKAT`）を直接呼び出します。

これらの変更により、Goの`syscall`パッケージは、従来のAPIを維持しつつ、内部的にはより新しい`*at`システムコールを利用する構造に移行しました。

## コアとなるコードの解説

### `src/syscall/syscall_linux.go` の変更

このファイルは、Goのユーザーが直接利用する高レベルなシステムコール関数を提供します。変更のポイントは、これらの関数が従来のシステムコールを直接呼び出すのではなく、`*at`システムコールを呼び出すように変更された点です。

例えば、`Access`関数の変更を見てみましょう。

**変更前:**
```go
//sys	Access(path string, mode uint32) (err error)
```
これは、Goのツールが`SYS_ACCESS`システムコールを直接呼び出す`Access`関数を生成することを示していました。

**変更後:**
```go
func Access(path string, mode uint32) (err error) {
	return Faccessat(_AT_FDCWD, path, mode, 0)
}
```
変更後、`Access`関数は、`Faccessat`という`*at`システムコールを呼び出すようになりました。ここで重要なのは、`_AT_FDCWD`が最初の引数として渡されている点です。これは、「現在の作業ディレクトリを基準として`path`を解決する」ことを意味し、従来の`Access`システムコールと同じセマンティクスを維持します。

同様に、`Open`関数も以下のように変更されています。

**変更前:**
```go
func Open(path string, mode int, perm uint32) (fd int, err error) {
	return open(path, mode|O_LARGEFILE, perm)
}
```
**変更後:**
```go
func Open(path string, mode int, perm uint32) (fd int, err error) {
	return openat(_AT_FDCWD, path, mode|O_LARGEFILE, perm)
}
```
`open`システムコールが`openat`システムコールに置き換えられ、ここでも`_AT_FDCWD`が使用されています。

これらの変更により、Goのプログラムは引き続き`syscall.Access`や`syscall.Open`を呼び出すことができますが、その裏側ではLinuxカーネルの`faccessat`や`openat`といった`*at`システムコールが利用されることになります。これにより、GoのAPIの互換性を保ちつつ、基盤となるシステムコール実装を最新化し、ARM64のような新しいアーキテクチャへの対応を可能にしています。

### `src/syscall/zsyscall_linux_*.go` の変更

これらのファイルは、Goのビルドプロセス中に自動生成される、各システムコールに対応する低レベルなGo関数を含んでいます。このコミットでは、従来のシステムコールに対応する関数定義が削除され、`*at`システムコールに対応する関数定義が追加されました。

例えば、`zsyscall_linux_amd64.go`における`open`関数の変更を見てみましょう。

**変更前 (抜粋):**
```go
func open(path string, mode int, perm uint32) (fd int, err error) {
	var _p0 *byte
	_p0, err = BytePtrFromString(path)
	if err != nil {
		return
	}
	r0, _, e1 := Syscall(SYS_OPEN, uintptr(unsafe.Pointer(_p0)), uintptr(mode), uintptr(perm))
	use(unsafe.Pointer(_p0))
	fd = int(r0)
	if e1 != 0 {
		err = e1
	}
	return
}
```
これは、`SYS_OPEN`システムコールを直接呼び出す関数でした。

**変更後 (抜粋):**
`open`関数自体は`syscall_linux.go`で`openat`を呼び出すように変更されたため、`zsyscall_linux_amd64.go`からは削除されています。代わりに、`linkat`, `readlinkat`, `symlinkat`, `unlinkat`などの`*at`システムコールに対応する関数が追加されています。

例えば、`linkat`関数の追加は以下のようになります。
```go
func linkat(olddirfd int, oldpath string, newdirfd int, newpath string, flags int) (err error) {
	var _p0 *byte
	_p0, err = BytePtrFromString(oldpath)
	if err != nil {
		return
	}
	var _p1 *byte
	_p1, err = BytePtrFromString(newpath)
	if err != nil {
		return
	}
	_, _, e1 := Syscall6(SYS_LINKAT, uintptr(olddirfd), uintptr(unsafe.Pointer(_p0)), uintptr(newdirfd), uintptr(unsafe.Pointer(_p1)), uintptr(flags), 0)
	use(unsafe.Pointer(_p0))
	use(unsafe.Pointer(_p1))
	if e1 != 0 {
		err = e1
	}
	return
}
```
この`linkat`関数は、`SYS_LINKAT`システムコールを直接呼び出しており、`olddirfd`, `oldpath`, `newdirfd`, `newpath`, `flags`といった`*at`システムコール特有の引数を受け取っています。

これらの`zsyscall_linux_*.go`ファイルの変更は、Goのシステムコール呼び出しの「最下層」を更新するものであり、GoランタイムがLinuxカーネルと直接対話する方法を現代化しています。これにより、GoはARM64のような新しいアーキテクチャの要件を満たし、将来のLinuxカーネルの変更にも対応できるようになります。

## 開発者の意図

このコミットの主な目的は、Linuxカーネルにおけるシステムコールの進化に対応し、Go言語の`syscall`パッケージを最新の状態に保つことです。特に、ARM64アーキテクチャが従来の（レガシーな）システムコールを廃止し、`*at`サフィックスを持つ新しいシステムコールのみをサポートするようになったことが、この変更の直接的な動機となっています。

従来のシステムコール（例: `open`, `link`, `chmod`）は、パス名を直接引数として受け取ります。これに対し、`*at`システムコール（例: `openat`, `linkat`, `fchmodat`）は、追加の引数としてディレクトリディスクリプタ（`dirfd`）を受け取ります。これにより、パス解決の基準となるディレクトリを明示的に指定できるようになります。

この変更は、Goが将来のLinuxカーネルバージョンや新しいアーキテクチャ（特にARM64）との互換性を維持するために不可欠でした。また、`*at`システムコールは、従来のシステムコールが抱えていたセキュリティ上の問題（特にシンボリックリンク攻撃などの競合状態）を解決し、より堅牢なファイルシステム操作を可能にします。

## 変更の背景

Linuxカーネルでは、ファイルシステム関連の多くのシステムコールに、従来の形式と`*at`サフィックスを持つ新しい形式が存在します。例えば、ファイルを開くためのシステムコールには`open`と`openat`があります。`*at`システムコールは、Linuxカーネル2.6.16で導入され、従来のシステムコールが持ついくつかの問題点を解決するために設計されました。

このコミットが行われた2015年当時、ARM64アーキテクチャは、従来のシステムコールを完全に削除し、`*at`形式のシステムコールのみをサポートする最初のLinuxアーキテクチャとして登場しました。これは、Go言語がARM64をサポートする上で、従来のシステムコールに依存している部分を`*at`システムコールに移行する必要があることを意味しました。

Goの`syscall`パッケージは、Goプログラムから直接Linuxカーネルのシステムコールを呼び出すための低レベルなインターフェースを提供しています。このパッケージが従来のシステムコールに依存し続けると、ARM64のような新しいアーキテクチャでGoプログラムが正しく動作しなくなる可能性がありました。そのため、Goのランタイムチームは、既存のGoプログラムの互換性を維持しつつ、内部的に`*at`システムコールを利用するように`syscall`パッケージを再実装することを決定しました。

この変更は、Goのクロスプラットフォーム対応と、将来のLinuxカーネルの進化への適応能力を向上させる上で重要なステップでした。

## 前提知識の解説

### システムコール (Syscalls)

システムコールは、オペレーティングシステム（OS）のカーネルが提供するサービスに、ユーザー空間のプログラムがアクセスするためのインターフェースです。ファイル操作（ファイルの読み書き、作成、削除）、プロセス管理（プロセスの生成、終了）、ネットワーク通信など、OSの基本的な機能のほとんどはシステムコールを通じて行われます。Go言語のような高レベル言語も、最終的にはこれらのシステムコールを呼び出すことでOSと対話します。

### レガシーシステムコール (Legacy Syscalls)

ここでいう「レガシーシステムコール」とは、`open`, `link`, `chmod`, `chown`, `mkdir`, `mknod`, `readlink`, `rename`, `rmdir`, `symlink`, `unlink` のように、パス名を直接引数として受け取る従来のシステムコールを指します。これらのシステムコールは、指定されたパス名を現在の作業ディレクトリ（カレントディレクトリ）からの相対パスとして解釈するか、絶対パスとして解釈します。

### `*at` システムコール (e.g., `openat`, `fchmodat`, `unlinkat`)

`*at`サフィックスを持つシステムコールは、従来のシステムコールに加えて、追加の引数として「ディレクトリディスクリプタ（`dirfd`）」を受け取ります。この`dirfd`は、パス解決の基準となるディレクトリを示すファイルディスクリプタです。

*   **`dirfd` の役割**:
    *   `dirfd`が有効なディレクトリのファイルディスクリプタである場合、`path`引数はそのディレクトリからの相対パスとして解釈されます。
    *   `dirfd`が特別な値である `_AT_FDCWD` の場合、`path`引数は現在の作業ディレクトリからの相対パスとして解釈されます。これは従来のシステムコールと同じ動作になります。
    *   `path`引数が絶対パスである場合、`dirfd`は無視されます。

### `_AT_FDCWD`

`_AT_FDCWD`は、Linuxカーネルが定義する特別な定数で、`*at`システムコールにおいて「現在の作業ディレクトリ（Current Working Directory）」を意味します。これにより、従来のシステムコールと同じセマンティクスを`*at`システムコールで実現できます。

### なぜ `*at` が必要か？ (Why `*at` is needed)

`*at`システムコールが導入された主な理由は、従来のシステムコールが抱えていた以下の問題点を解決するためです。

1.  **競合状態 (Race Condition) の回避**:
    従来のシステムコールでは、パス名を解決する際に、プログラムがパス名を指定してからカーネルがそのパスを実際に操作するまでの間に、外部からパス名が変更される（例: シンボリックリンクが別のファイルに置き換えられる）可能性があります。これは「シンボリックリンク攻撃」などのセキュリティ脆弱性につながることがありました。
    `*at`システムコールでは、`dirfd`によって操作対象のディレクトリを固定できるため、このような競合状態を大幅に軽減できます。例えば、`openat(dirfd, "file.txt", ...)`とすることで、`dirfd`が指すディレクトリ内の`file.txt`を確実に操作できます。

2.  **堅牢性 (Robustness) の向上**:
    パス解決の基準を明示的に指定できるため、プログラムの動作がより予測可能になります。カレントディレクトリの変更に依存しない操作が可能になり、マルチスレッド環境や複雑なファイルシステム操作を行うプログラムの堅牢性が向上します。

3.  **コンテナ/サンドボックス環境での利用**:
    コンテナ技術やサンドボックス環境では、特定のプロセスがアクセスできるファイルシステム領域を制限することが重要です。`*at`システムコールは、`dirfd`を通じて操作のスコープを限定できるため、このような環境でのセキュリティと隔離性を高めるのに役立ちます。

4.  **新しいアーキテクチャの要件**:
    ARM64のように、一部の新しいアーキテクチャでは、設計の簡素化やセキュリティの強化のために、従来のシステムコールが完全に削除され、`*at`形式のシステムコールのみが提供される場合があります。Goのような言語がこれらの新しいアーキテクチャをサポートするためには、`*at`システムコールへの移行が必須となります。

このコミットは、Goがこれらの利点を享受し、将来のLinux環境に適合するための重要な基盤を築くものです。

## 技術的詳細

このコミットは、Go言語の`syscall`パッケージにおけるLinuxシステムコールの実装を根本的に変更します。Goの`syscall`パッケージは、各アーキテクチャ（386, amd64, arm, ppc64, ppc64leなど）ごとに異なるシステムコール番号や呼び出し規約に対応するために、一部のファイルが自動生成されています（例: `zsyscall_linux_386.go`）。

変更の核心は以下の2点です。

1.  **`syscall_linux.go` におけるラッパー関数の再実装**:
    このファイルでは、Goのユーザーが通常利用する`syscall`パッケージの関数（例: `syscall.Open`, `syscall.Link`）が定義されています。このコミットでは、これらの関数が、対応する`*at`システムコール（例: `syscall.Openat`, `syscall.Linkat`）を内部的に呼び出すように変更されました。
    従来のシステムコールがパス名を直接受け取るのに対し、`*at`システムコールは`dirfd`を必要とします。この`dirfd`には、現在の作業ディレクトリを示す特別な値である`_AT_FDCWD`が渡されます。これにより、Goのユーザーから見たAPIの変更なしに、内部的なシステムコール呼び出しが`*at`バージョンに切り替わります。

2.  **`zsyscall_linux_*.go` ファイルの更新**:
    これらのファイルは、`mksyscall.pl`などのツールによって自動生成される、各システムコールに対応する低レベルなGo関数を含んでいます。このコミットでは、従来のシステムコール（例: `SYS_OPEN`, `SYS_LINK`）に対応する定義が削除され、代わりに`*at`システムコール（例: `SYS_OPENAT`, `SYS_LINKAT`）に対応する定義が追加されました。
    これにより、Goのランタイムが直接呼び出すシステムコールが、従来のバージョンから`*at`バージョンへと切り替わります。

このアプローチにより、Goの既存のコードベースは、`syscall.Open`などの従来の関数名をそのまま使用できますが、その背後ではより現代的で堅牢な`*at`システムコールが利用されるようになります。これは、APIの互換性を保ちつつ、内部実装を最新のLinuxカーネルのベストプラクティスに合わせるための巧妙な方法です。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/syscall/syscall_linux.go`:
    *   `Access`, `Chmod`, `Chown`, `Creat`, `Link`, `Mkdir`, `Mknod`, `Readlink`, `Rename`, `Rmdir`, `Symlink`, `Unlink`, `Unlinkat` といった従来のシステムコールに対応するGoの関数が、それぞれ対応する`*at`システムコール（`Faccessat`, `Fchmodat`, `Fchownat`, `Openat`, `linkat`, `Mkdirat`, `Mknodat`, `readlinkat`, `Renameat`, `unlinkat`, `symlinkat`, `unlinkat`）を呼び出すように変更されています。
    *   これらのラッパー関数では、`_AT_FDCWD`が`dirfd`引数として渡され、現在の作業ディレクトリを基準としたパス解決が行われるようにしています。
    *   `Open`関数も、内部的に`openat(_AT_FDCWD, ...)`を呼び出すように変更されています。
    *   従来のシステムコールに対応する`//sys`ディレクティブ（Goのツールがシステムコールラッパーを生成するために使用）が削除されています。

*   `src/syscall/zsyscall_linux_386.go`, `src/syscall/zsyscall_linux_amd64.go`, `src/syscall/zsyscall_linux_arm.go`, `src/syscall/zsyscall_linux_ppc64.go`, `src/syscall/zsyscall_linux_ppc64le.go`:
    *   これらの自動生成されるファイルから、従来のシステムコール（例: `open`, `access`, `chmod`, `creat`, `link`, `mkdir`, `mknod`, `readlink`, `rename`, `rmdir`, `symlink`, `unlink`, `unlinkat`）に対応する低レベルなGo関数定義が削除されています。
    *   代わりに、`linkat`, `readlinkat`, `symlinkat`, `unlinkat` といった`*at`システムコールに対応する低レベルなGo関数定義が追加されています。これらの関数は、対応するLinuxシステムコール番号（例: `SYS_LINKAT`, `SYS_READLINKAT`）を直接呼び出します。

これらの変更により、Goの`syscall`パッケージは、従来のAPIを維持しつつ、内部的にはより新しい`*at`システムコールを利用する構造に移行しました。

## コアとなるコードの解説

### `src/syscall/syscall_linux.go` の変更

このファイルは、Goのユーザーが直接利用する高レベルなシステムコール関数を提供します。変更のポイントは、これらの関数が従来のシステムコールを直接呼び出すのではなく、`*at`システムコールを呼び出すように変更された点です。

例えば、`Access`関数の変更を見てみましょう。

**変更前:**
```go
//sys	Access(path string, mode uint32) (err error)
```
これは、Goのツールが`SYS_ACCESS`システムコールを直接呼び出す`Access`関数を生成することを示していました。

**変更後:**
```go
func Access(path string, mode uint32) (err error) {
	return Faccessat(_AT_FDCWD, path, mode, 0)
}
```
変更後、`Access`関数は、`Faccessat`という`*at`システムコールを呼び出すようになりました。ここで重要なのは、`_AT_FDCWD`が最初の引数として渡されている点です。これは、「現在の作業ディレクトリを基準として`path`を解決する」ことを意味し、従来の`Access`システムコールと同じセマンティクスを維持します。

同様に、`Open`関数も以下のように変更されています。

**変更前:**
```go
func Open(path string, mode int, perm uint32) (fd int, err error) {
	return open(path, mode|O_LARGEFILE, perm)
}
```
**変更後:**
```go
func Open(path string, mode int, perm uint32) (fd int, err error) {
	return openat(_AT_FDCWD, path, mode|O_LARGEFILE, perm)
}
```
`open`システムコールが`openat`システムコールに置き換えられ、ここでも`_AT_FDCWD`が使用されています。

これらの変更により、Goのプログラムは引き続き`syscall.Access`や`syscall.Open`を呼び出すことができますが、その裏側ではLinuxカーネルの`faccessat`や`openat`といった`*at`システムコールが利用されることになります。これにより、GoのAPIの互換性を保ちつつ、基盤となるシステムコール実装を最新化し、ARM64のような新しいアーキテクチャへの対応を可能にしています。

### `src/syscall/zsyscall_linux_*.go` の変更

これらのファイルは、Goのビルドプロセス中に自動生成される、各システムコールに対応する低レベルなGo関数を含んでいます。このコミットでは、従来のシステムコールに対応する関数定義が削除され、`*at`システムコールに対応する関数定義が追加されました。

例えば、`zsyscall_linux_amd64.go`における`open`関数の変更を見てみましょう。

**変更前 (抜粋):**
```go
func open(path string, mode int, perm uint32) (fd int, err error) {
	var _p0 *byte
	_p0, err = BytePtrFromString(path)
	if err != nil {
		return
	}
	r0, _, e1 := Syscall(SYS_OPEN, uintptr(unsafe.Pointer(_p0)), uintptr(mode), uintptr(perm))
	use(unsafe.Pointer(_p0))
	fd = int(r0)
	if e1 != 0 {
		err = e1
	}
	return
}
```
これは、`SYS_OPEN`システムコールを直接呼び出す関数でした。

**変更後 (抜粋):**
`open`関数自体は`syscall_linux.go`で`openat`を呼び出すように変更されたため、`zsyscall_linux_amd64.go`からは削除されています。代わりに、`linkat`, `readlinkat`, `symlinkat`, `unlinkat`などの`*at`システムコールに対応する関数が追加されています。

例えば、`linkat`関数の追加は以下のようになります。
```go
func linkat(olddirfd int, oldpath string, newdirfd int, newpath string, flags int) (err error) {
	var _p0 *byte
	_p0, err = BytePtrFromString(oldpath)
	if err != nil {
		return
	}
	var _p1 *byte
	_p1, err = BytePtrFromString(newpath)
	if err != nil {
		return
	}
	_, _, e1 := Syscall6(SYS_LINKAT, uintptr(olddirfd), uintptr(unsafe.Pointer(_p0)), uintptr(newdirfd), uintptr(unsafe.Pointer(_p1)), uintptr(flags), 0)
	use(unsafe.Pointer(_p0))
	use(unsafe.Pointer(_p1))
	if e1 != 0 {
		err = e1
	}
	return
}
```
この`linkat`関数は、`SYS_LINKAT`システムコールを直接呼び出しており、`olddirfd`, `oldpath`, `newdirfd`, `newpath`, `flags`といった`*at`システムコール特有の引数を受け取っています。

これらの`zsyscall_linux_*.go`ファイルの変更は、Goのシステムコール呼び出しの「最下層」を更新するものであり、GoランタイムがLinuxカーネルと直接対話する方法を現代化しています。これにより、GoはARM64のような新しいアーキテクチャの要件を満たし、将来のLinuxカーネルの変更にも対応できるようになります。

## 元コミット内容

so get rid of it. But because arithmetic is done with uint64s, to simplify
dealing with large constants, complain about right shift and divide with
huge numbers to avoid ambiguity about signed shifts.

## 変更の背景

このコミットには主に二つの背景があります。

1.  **オーバーフローチェックの問題点**: `cmd/asm`における定数評価時のオーバーフローチェックは、意図しない問題や複雑性を引き起こしていました。コミットメッセージには「overflow checking was causing more problems than it was avoiding」と明記されており、この機能がアセンブラの安定性や開発効率を阻害していたことが示唆されます。Go言語の設計思想として、パフォーマンスのためにデフォルトで整数オーバーフローチェックを行わず、ラップアラウンド挙動を採用している点も、この変更の背景にあると考えられます。アセンブラレベルでの厳密なオーバーフローチェックは、Goの哲学と合致せず、むしろ不必要な制約となっていた可能性があります。

2.  **ラベルのスコープの明確化**: 以前の`cmd/asm`では、ラベルのスコープが曖昧であったか、あるいはグローバルに近いスコープを持っていた可能性があります。アセンブリ言語において、ラベルはコード内の特定の位置を示すために使用されますが、そのスコープが明確でないと、異なる関数内で同じ名前のラベルが衝突したり、意図しないジャンプが発生したりするリスクがあります。ラベルを関数スコープにすることで、コードのモジュール性が向上し、大規模なアセンブリコードの管理が容易になります。

3.  **`uint64`演算の曖昧さの解消**: `cmd/asm`は定数を`uint64`（符号なし64ビット整数）として扱います。`uint64`は非常に大きな値を表現できますが、特に右シフト (`>>`) や除算 (`/`) のような演算において、最上位ビット (MSB) がセットされている（つまり、符号付き整数として解釈すると負の値になる）ような「巨大な数」を扱う際に、その挙動が曖昧になることがあります。これは、アセンブラが最終的に生成する機械語が、符号付き/符号なしの区別を厳密に行うCPUの命令にマッピングされるため、アセンブラの段階でこの曖昧さを排除する必要があったためです。このコミットは、このような状況でエラーを発生させることで、プログラマに意図しない挙動を警告し、より堅牢なアセンブリコードの記述を促します。

## 前提知識の解説

### Goの`cmd/asm`とは

`cmd/asm`は、Go言語のツールチェインに含まれるアセンブラです。Goプログラムは通常Go言語で記述されますが、パフォーマンスが非常に重要な部分や、特定のハードウェア機能にアクセスする必要がある場合などには、Goアセンブリ言語（Plan 9アセンブリの派生）で記述されたコードを使用することがあります。`cmd/asm`は、このGoアセンブリ言語のソースコードを機械語に変換する役割を担っています。Goアセンブリは、一般的なアセンブリ言語とは異なる独特の構文とセマンティクスを持っています。

### アセンブリ言語におけるラベルのスコープ

アセンブリ言語において、ラベルはプログラム内の特定の命令やデータのアドレスを示すシンボルです。例えば、ジャンプ命令のターゲットや、データの参照点として使用されます。ラベルにはスコープがあり、そのラベルがどの範囲で参照可能であるかを定義します。

*   **グローバルスコープ**: プログラム全体から参照可能なラベル。異なるファイルや関数からでもアクセスできます。
*   **ローカルスコープ**: 特定のブロックや関数内でのみ参照可能なラベル。同じ名前のラベルが異なる関数内に存在しても衝突しません。

一般的に、ローカルスコープのラベルは、コードのモジュール性を高め、名前の衝突を避けるために推奨されます。

### 符号なし整数 (`uint64`) の算術演算と最上位ビット (MSB)

`uint64`は、0から約1.8 x 10^19までの値を表現できる符号なし64ビット整数です。符号なし整数は常に非負の値を取ります。

*   **最上位ビット (MSB)**: 64ビットの数値において、最も左側のビット（63番目のビット、0から数えて）を指します。符号付き整数では、このビットが数値の符号（0なら正、1なら負）を示しますが、符号なし整数では単に数値の一部として扱われます。
*   **右シフト (`>>`)**: 数値のビットを右に移動させる演算です。符号なし整数では、左側から0が埋められます。
*   **除算 (`/`)**: 通常の算術除算です。

問題となるのは、`uint64`で表現される非常に大きな値が、もし符号付き整数として解釈された場合に負の値となるようなケースです。例えば、`1<<63`（最上位ビットのみが1）という`uint64`の値は、符号なしでは非常に大きな正の数ですが、符号付き64ビット整数（`int64`）として解釈すると最小の負の数になります。このような値に対して右シフトや除算を行うと、アセンブラが意図しない挙動をしたり、生成される機械語が期待と異なる結果を生む可能性があります。このコミットは、このような曖昧さを避けるために、MSBがセットされた`uint64`値に対する特定の演算でエラーを出すように変更しました。

### Goにおける整数オーバーフローの一般的な挙動

Go言語では、CやC++と同様に、整数型での算術演算がオーバーフローした場合、エラーを発生させずに「ラップアラウンド」します。例えば、`uint8`型の最大値に1を加えると、0に戻ります。これはパフォーマンスを重視した設計判断であり、Goのランタイムやコンパイラは通常、明示的なオーバーフローチェックを行いません。このコミットで`cmd/asm`からオーバーフローチェックが削除されたのは、このGo言語全体の哲学と整合性を取るためとも考えられます。

## 技術的詳細

### オーバーフローチェックの削除

このコミットの最も大きな変更点の一つは、`src/cmd/asm/internal/asm/overflow.go`ファイルが完全に削除されたことです。このファイルには、`addOverflows`, `subOverflows`, `mulOverflows`, `shiftOverflows`といった、`uint64`の算術演算におけるオーバーフローを検出するための関数が含まれていました。これらの関数は、`parse.go`内の定数式評価ロジックで使用されていました。

オーバーフローチェックの削除は、以下の理由が考えられます。

*   **複雑性の軽減**: オーバーフローチェックのロジックは、特にエッジケースを考慮すると複雑になりがちです。この複雑性がアセンブラ自体のバグやメンテナンスコストの原因となっていた可能性があります。
*   **誤検出（False Positives）**: 厳密なオーバーフローチェックが、実際には問題ない状況でエラーを報告し、アセンブリコードの記述を不必要に困難にしていた可能性があります。
*   **性能オーバーヘッド**: チェックの実行にはわずかながらも性能コストがかかります。アセンブラは高速であることが求められるため、このオーバーヘッドが問題視された可能性があります。
*   **Goの哲学との整合性**: Go言語自体が整数オーバーフローをラップアラウンドとして扱うため、アセンブラがそれとは異なる厳密なチェックを行うのは一貫性に欠けるという判断があったかもしれません。

`parse.go`からは、`addOverflows`, `mulOverflows`, `shiftOverflows`の呼び出しが削除され、単純な算術演算に置き換えられています。

### ラベルの関数スコープ化

この変更は、`src/cmd/asm/internal/asm/asm.go`の`asmText`関数に導入されました。`asmText`関数は、Goアセンブリの`TEXT`命令（Go関数を定義する命令）を処理する際に呼び出されます。

変更前は、ラベルの管理が関数間で共有されていた可能性があり、異なる`TEXT`ブロック（Go関数）で同じ名前のラベルを使用すると衝突が発生する可能性がありました。このコミットでは、`TEXT`命令が解析されるたびに、既存のラベル参照をパッチし（`p.patch()`）、新しい空のラベルマップを作成する（`p.labels = make(map[string]*obj.Prog)`）ことで、ラベルのスコープを現在の`TEXT`ブロック（関数）に限定しています。これにより、各関数内で独立したラベル空間が確保され、名前の衝突が回避されます。

### `uint64`演算における新しいチェック

オーバーフローチェックが削除された一方で、`src/cmd/asm/internal/asm/parse.go`の`expr`および`term`関数には、`uint64`値に対する右シフトと除算に関する新しいチェックが追加されました。

*   **除算 (`/`)**: `value&(1<<63) != 0`というチェックが追加されました。これは、`value`の最上位ビット（MSB）がセットされているかどうかを確認しています。MSBがセットされた`uint64`値は非常に大きな正の数ですが、もしこれが符号付き整数として扱われると負の数になります。このような値に対する除算は、アセンブラが生成する機械語の挙動において曖昧さや予期せぬ結果を生む可能性があるため、エラーとして扱われます。
*   **右シフト (`>>`)**: `shift > 0 && value&(1<<63) != 0`というチェックが追加されました。これも同様に、シフト量が正であり、かつ`value`のMSBがセットされている場合にエラーを発生させます。符号なし右シフトは通常、左から0を埋めますが、MSBがセットされた大きな値に対する右シフトは、特にその結果が後で符号付きの文脈で使われる場合に混乱を招く可能性があるため、明示的に禁止されます。

これらのチェックは、以前の包括的なオーバーフローチェックとは異なり、特定の「曖昧さ」や「誤解を招く可能性のある挙動」に焦点を当てています。`uint64`の算術演算が、最終的にCPUの符号付き/符号なしのレジスタや命令にマッピングされる際に、プログラマの意図と異なる解釈がされないようにするためのガードレールとして機能します。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/asm.go`の変更

*   **ラベルの関数スコープ化**:
    `asmText`関数内で、`TEXT`命令が解析される直前に以下の2行が追加されました。
    ```go
    p.patch()
    p.labels = make(map[string]*obj.Prog)
    ```
    `p.patch()`は、それまでに定義されたラベルへの参照を解決（パッチ適用）する役割を担います。これにより、以前の`TEXT`ブロックで定義された未解決のラベル参照が、そのブロック内で適切に解決されます。
    `p.labels = make(map[string]*obj.Prog)`は、新しい空のマップを`p.labels`に割り当てることで、現在の`TEXT`ブロック（関数）専用の新しいラベル空間を作成します。これにより、この関数内で定義されるラベルは、他の関数内のラベルと名前が衝突しても問題なく扱えるようになります。

*   **`p.toPatch`のリセット**:
    `patch()`関数内で、`p.toPatch = p.toPatch[:0]`が追加されました。これは、パッチ適用が完了した後、`toPatch`スライスをクリアし、次のパッチ適用サイクルに備えるためのものです。これにより、以前のパッチ情報が誤って再利用されることを防ぎます。

### `src/cmd/asm/internal/asm/overflow.go`の削除

このファイルは、`addOverflows`, `subOverflows`, `mulOverflows`, `shiftOverflows`といった、`uint64`の算術演算におけるオーバーフローを検出する関数群を含んでいました。このファイルの削除は、`cmd/asm`がこれらの一般的なオーバーフローチェックを完全に廃止したことを意味します。これにより、アセンブラのコードベースが簡素化され、Goの整数演算のラップアラウンド挙動との整合性が高まります。

### `src/cmd/asm/internal/asm/parse.go`の変更

*   **一般的なオーバーフローチェックの削除**:
    `expr`関数内の加算 (`+`) と`term`関数内の乗算 (`*`) および左シフト (`<<`) の箇所から、それぞれ`addOverflows`, `mulOverflows`, `shiftOverflows`の呼び出しと、それに関連するエラー報告ロジックが削除されました。これにより、これらの演算における一般的なオーバーフローは、Goの通常の整数演算と同様にラップアラウンドする挙動となります。

*   **`uint64`の最上位ビットに関する新しいチェック**:
    *   **除算 (`/`)**:
        ```go
        if value&(1<<63) != 0 {
            p.errorf("divide with high bit set")
        }
        ```
        このコードは、除算のオペランド`value`の最上位ビット（63番目のビット）が1であるかどうかをチェックします。`1<<63`は`uint64`で表現できる最大の正の数（符号付き`int64`では最小の負の数）です。このような値に対する除算は、アセンブラが生成する機械語の挙動において、符号付き/符号なしの解釈の違いから曖昧さや予期せぬ結果を生む可能性があるため、明示的にエラーとします。
    *   **右シフト (`>>`)**:
        ```go
        if shift > 0 && value&(1<<63) != 0 {
            p.errorf("right shift with high bit set")
        }
        ```
        このコードは、右シフトのオペランド`value`の最上位ビットが1であり、かつシフト量`shift`が0より大きい場合にエラーを発生させます。符号なし右シフトは左から0を埋めますが、MSBがセットされた大きな値に対する右シフトは、特にその結果が後で符号付きの文脈で使われる場合に混乱を招く可能性があるため、明示的に禁止されます。

これらの新しいチェックは、一般的なオーバーフロー検出ではなく、`uint64`の特性（特にMSBがセットされた値）と、それがアセンブラが生成する機械語のセマンティクスに与える影響に特化したものです。これにより、アセンブラはより堅牢になり、プログラマは意図しない挙動を避けることができます。

## 変更の背景

Goランタイムは、初期の段階ではパフォーマンスや低レベルな操作のためにC言語で書かれた部分が多く存在しました。しかし、Go 1.4以降、ランタイムの大部分をC言語からGo言語へ書き換える大規模なプロジェクトが進行しました。この移行の主要な動機の一つは、ガベージコレクタ（GC）がゴルーチン（G）スタックを正確にスキャンできるようにするためでした。

GoのGCは、スタック上のどの値がポインタであり、どれがそうでないかを正確に識別する「正確なスタックマップ」を必要とします。GoコンパイラはGoコードに対してこの正確なスタックマップを生成できますが、CコードはGoのGCが直接利用できる形式でこの情報を提供しません。このため、「Gスタック上のすべてのコードはGoで書かれている必要がある」という原則が確立されました。

`badreflectcall`関数は、`reflect.Call`の引数サイズが1GBを超える場合にパニックを引き起こすためのランタイム関数です。この関数がC言語で実装されており、かつGスタック上で実行される場合、GCがスタックを正確にスキャンできない可能性がありました。これは、GCが誤ったポインタを認識したり、重要なポインタを見落としたりする原因となり、ランタイムの不安定性やメモリリークにつながる恐れがありました。このコミットは、この問題を解決するために`badreflectcall`をGo言語に移行することを目的としています。

## 前提知識の解説

*   **Goランタイム**: Goプログラムの実行を管理する低レベルな部分です。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信などを担当します。
*   **ゴルーチン (Goroutine)**: Goにおける軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
*   **Gスタック (Goroutine Stack)**: 各ゴルーチンが持つ独自のスタック領域です。Goのスタックは動的に伸縮し、必要に応じて自動的にサイズが調整されます。
*   **ガベージコレクタ (GC)**: プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは、実行中のプログラムを一時停止させることなく、並行的に動作するように設計されています。
*   **正確なスタックマップ (Exact Stack Maps)**: GCがスタックをスキャンする際に、スタック上のどの位置にポインタが存在するかを正確に識別するための情報です。これにより、GCはポインタを追跡し、到達可能なオブジェクトをマークすることができます。
*   **`reflect`パッケージ**: Goの標準ライブラリの一部で、実行時に型情報や値にアクセスし、操作するための機能を提供します。`reflect.Call()`は、動的に関数を呼び出すために使用されます。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。GoとCの間のインターフェースを提供します。

## 技術的詳細

このコミットの核心は、GoランタイムのC言語部分をGo言語に移行するという、より大きな戦略の一部です。特に、`badreflectcall`関数がC言語で実装されていたことが問題でした。

`reflect.Call()`は、Goの強力な機能の一つですが、その実装は低レベルであり、ランタイムのスタック管理と密接に関連しています。`reflect.Call()`が非常に大きな引数を扱う場合（このケースでは1GB以上）、ランタイムはエラーを検出し、`badreflectcall`を呼び出してパニックを発生させます。

問題は、この`badreflectcall`がC言語で書かれており、かつゴルーチンのスタック（Gスタック）上で実行される可能性があったことです。前述の通り、C言語で書かれたコードはGoのGCが必要とする正確なスタックマップ情報を提供しません。もし`badreflectcall`がC言語のままGスタック上で実行され、そのスタックフレーム内にポインタが含まれていた場合、GCはそのポインタを正しく認識できず、メモリリークやクラッシュの原因となる可能性がありました。

このコミットでは、`badreflectcall`関数をC言語の`src/pkg/runtime/proc.c`からGo言語の`src/pkg/runtime/proc.go`へ移動し、Go言語で再実装することでこの問題を解決しています。Go言語で実装された関数は、Goコンパイラによって正確なスタックマップが生成されるため、GCはGスタックを安全かつ正確にスキャンできるようになります。これにより、`reflect.Call`に関連する潜在的なランタイムの不安定性が解消されます。

## コアとなるコードの変更箇所

このコミットでは、以下の2つのファイルが変更されています。

1.  **`src/pkg/runtime/proc.c`**:
    *   `runtime·badreflectcall`関数のC言語実装が削除されています。
    *   具体的には、以下のコードが削除されました。
        ```c
        void
        runtime·badreflectcall(void) // called from assembly
        {
        	runtime·panicstring("runtime: arg size to reflect.call more than 1GB");
        }
        ```

2.  **`src/pkg/runtime/proc.go`**:
    *   `badreflectcall`関数のGo言語実装が追加されています。
    *   具体的には、以下のコードが追加されました。
        ```go
        func badreflectcall() {
        	panic("runtime: arg size to reflect.call more than 1GB")
        }
        ```

## コアとなるコードの解説

変更の核心は、`runtime·badreflectcall`というC言語の関数が、Go言語の`badreflectcall`関数に置き換えられた点です。

*   **C言語版 (`runtime·badreflectcall`)**:
    *   この関数はC言語で書かれており、`runtime·panicstring`を呼び出してパニックを発生させていました。
    *   C言語で書かれているため、この関数がGスタック上で実行される際に、GoのGCが必要とする正確なスタックマップ情報を提供できませんでした。これは、GCがスタック上のポインタを正しく識別できないという潜在的な問題を引き起こしていました。

*   **Go言語版 (`badreflectcall`)**:
    *   この関数はGo言語で書かれており、Goの組み込み関数である`panic`を呼び出してパニックを発生させています。
    *   Go言語で書かれているため、Goコンパイラは`badreflectcall`のスタックフレームに対して正確なスタックマップを生成できます。これにより、GCはGスタックを安全にスキャンし、スタック上のポインタを正確に追跡できるようになります。

この変更により、`reflect.Call`が不正な引数サイズで呼び出された際に発生するパニック処理が、GoのGCと完全に互換性のある形で実行されるようになり、ランタイムの堅牢性が向上しました。

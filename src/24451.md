## 変更の背景

このコミットは、GoコンパイラのARM64バックエンドにおけるビルド時の問題を修正するために導入されました。Goの関数呼び出し規約やスタックフレームの管理において、特定のアーキテクチャ（この場合はARM64）ではスタックアライメントの要件が存在します。特に、ARM64ではスタックポインタが16バイト境界にアラインされている必要があります。

`src/cmd/internal/obj/arm64/obj7.go`内の`preprocess`関数は、Goの関数が使用するスタックフレームのサイズを計算し、必要に応じて調整する役割を担っています。この調整プロセス中に、スタックアライメントの要件を満たすためにフレームサイズが8バイト追加されるケースがありました。しかし、この追加された8バイトが、現在の関数のローカル変数サイズではなく、リンカーコンテキスト全体のローカル変数サイズに誤って加算されていました。

この誤った加算は、特定の条件下でビルドエラーや不正なコード生成を引き起こす可能性がありました。コミットメッセージの「fix build」という簡潔な表現は、この問題がビルドプロセスに直接的な影響を与えていたことを示唆しています。

## 前提知識の解説

*   **Goコンパイラとバックエンド**: Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。このプロセスは、フロントエンド（構文解析、型チェックなど）とバックエンド（コード生成、最適化など）に分かれています。ARM64は、GoがサポートするCPUアーキテクチャの一つであり、`cmd/internal/obj/arm64`はそのARM64アーキテクチャ向けのコード生成を担当するバックエンドの一部です。
*   **オブジェクトファイル (`obj`)**: コンパイラが生成する中間ファイルで、機械語コードやデータ、シンボル情報などが含まれます。Goコンパイラでは、`cmd/internal/obj`パッケージがこれらのオブジェクトファイルの構造や操作を定義しています。
*   **スタックフレーム**: 関数が呼び出されるたびに、その関数が使用するローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保されるメモリ領域です。
*   **スタックアライメント**: 特定のCPUアーキテクチャ（ARM64など）では、パフォーマンス上の理由やハードウェアの制約により、スタックポインタが特定のバイト数（例: 16バイト）の倍数にアラインされている必要があります。これにより、メモリへのアクセスが効率的になり、一部の命令が正しく動作するようになります。
*   **`obj.Link` (リンカーコンテキスト)**: Goコンパイラのリンカーが使用するグローバルなコンテキストオブジェクトです。リンカーは、複数のオブジェクトファイルを結合して実行可能ファイルを生成する役割を担います。`ctxt.Autosize`や`ctxt.Locals`のようなフィールドは、リンカー全体または現在のコンパイルユニット全体に関する情報を保持することがあります。
*   **`obj.LSym` (ローカルシンボル)**: 個々の関数やグローバル変数など、プログラム内のシンボル（名前付きエンティティ）を表す構造体です。関数ごとに独自のローカル変数サイズ (`cursym.Locals`) を持っています。
*   **`preprocess`関数**: Goコンパイラのバックエンドにおいて、コード生成の最終段階でシンボル（関数など）を処理し、スタックフレームのサイズ調整やアライメントの保証などを行う関数です。

## 技術的詳細

GoコンパイラのARM64バックエンドでは、関数が使用するスタックフレームのサイズを決定する際に、スタックアライメントの制約を考慮する必要があります。ARM64では、スタックポインタは16バイト境界にアラインされている必要があります。

`src/cmd/internal/obj/arm64/obj7.go`内の`preprocess`関数は、各関数のシンボル (`cursym`) を処理する際に、その関数のスタックフレームサイズ (`ctxt.Autosize`) をチェックします。

問題のコードブロックは以下の部分です。

```go
				// that the frame size is 8 mod 16.
				if ctxt.Autosize == 8 {
					ctxt.Autosize += 8
					ctxt.Locals += 8 // ← 修正前
				} else {
					ctxt.Diag("%v: unaligned frame size %d - must be 8 mod 16 (or 0)", p, ctxt.Autosize-8)
				}
```

ここで、`ctxt.Autosize == 8`という条件は、現在の関数のスタックフレームサイズが8バイトであり、16バイトアライメントを満たすためにさらに8バイト追加する必要がある状況を示しています。この場合、`ctxt.Autosize += 8`によってフレームサイズが16バイトに調整されます。

しかし、その次の行の`ctxt.Locals += 8`が問題でした。`ctxt.Locals`はリンカーコンテキスト (`obj.Link`) に属するフィールドであり、これは現在の関数 (`cursym`) のローカル変数サイズではなく、より広範なコンテキストにおけるローカル変数サイズの合計や、あるいは一時的な作業変数として使われる可能性のあるフィールドです。

本来、この8バイトの追加は、現在の関数 (`cursym`) のローカル変数サイズに反映されるべきでした。なぜなら、この8バイトは現在の関数のスタックフレームの一部として確保されるため、その関数のローカル変数領域のサイズに影響を与えるからです。

このコミットは、この誤りを修正し、`ctxt.Locals += 8`を`cursym.Locals += 8`に変更することで、現在の関数のローカル変数サイズを正しく更新するようにしました。これにより、各関数のスタックフレームサイズが正確に計算され、ARM64のスタックアライメント要件が満たされるとともに、ビルド時の問題が解消されます。

## コアとなるコードの変更箇所

変更は`src/cmd/internal/obj/arm64/obj7.go`ファイルの一箇所のみです。

```diff
--- a/src/cmd/internal/obj/arm64/obj7.go
+++ b/src/cmd/internal/obj/arm64/obj7.go
@@ -576,7 +576,7 @@ func preprocess(ctxt *obj.Link, cursym *obj.LSym) {
```

## コアとなるコードの解説

変更された行は以下の通りです。

-   **修正前**: `ctxt.Locals += 8`
-   **修正後**: `cursym.Locals += 8`

この変更の核心は、`Locals`フィールドを更新する対象を`ctxt`（リンカーコンテキスト）から`cursym`（現在のローカルシンボル、つまり現在の関数）へ変更した点にあります。

*   `ctxt.Autosize`: これは現在の関数のスタックフレームの自動サイズ調整部分を示しています。`ctxt.Autosize == 8`の場合、フレームサイズが8バイトであることを意味し、ARM64の16バイトアライメント要件を満たすために追加の8バイトが必要です。
*   `ctxt.Autosize += 8`: この行は、現在の関数のスタックフレームサイズを8バイト増やし、合計16バイトにしてアライメント要件を満たします。
*   `cursym.Locals`: これは、現在処理中の関数シンボル (`cursym`) に関連付けられたローカル変数の合計サイズを保持するフィールドです。スタックフレームに追加される8バイトは、実質的にこの関数のローカル変数領域の一部として扱われるため、このフィールドを更新するのが正しい挙動です。

この修正により、各関数のローカル変数サイズが正確に記録され、結果として生成される機械語コードのスタックフレーム管理が正しく行われるようになります。これにより、ARM64アーキテクチャ上でのGoプログラムの安定性と正確性が向上します。

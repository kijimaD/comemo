# [インデックス 27179] ファイルの概要

このコミットは、Goのオブジェクトファイルにおけるシンボル参照の格納方法を最適化するものです。具体的には、オブジェクトファイル内でシンボルが互いを参照する際に、シンボル名とバージョンを直接記述する代わりに、一意なシンボル参照のリストを作成し、そのリストへのインデックスを使用するように変更します。これにより、オブジェクトファイルのサイズが削減され、リンカのパフォーマンスが向上します。

## 変更の背景

Goのコンパイラとリンカは、プログラムをビルドする際にオブジェクトファイルを生成します。これらのオブジェクトファイルには、関数、変数、型などのシンボルに関する情報が含まれており、シンボルは互いを参照することが頻繁にあります。

このコミット以前は、オブジェクトファイル内のシンボル参照は、参照先のシンボルの「名前」と「バージョン」を直接記述する形式でした。しかし、同じシンボルがオブジェクトファイル内で何度も参照される場合、その都度シンボル名とバージョンが重複して書き込まれることになり、以下の問題が生じていました。

1.  **ファイルサイズの増大**: 重複するシンボル名とバージョンの文字列がオブジェクトファイルに何度も格納されるため、ファイルサイズが不必要に大きくなっていました。
2.  **リンカのパフォーマンス低下**: リンカがオブジェクトファイルを処理する際、これらのシンボル参照を解決するために、重複するシンボル名に対して繰り返しマップルックアップ（ハッシュテーブル検索）を行う必要があり、これがリンカの処理速度を低下させる要因となっていました。

この問題を解決するため、一意なシンボル参照のリストをオブジェクトファイルに導入し、各シンボル参照をそのリストへのインデックスで表現することで、ファイルサイズの削減とリンカの効率化を図るのがこの変更の背景です。コミットメッセージにあるように、`pkg/linux_amd64`のサイズが30%削減され、リンカのベンチマークも大幅に改善されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムと内部構造に関する知識が必要です。

### 1. Goのビルドプロセス

Goのプログラムは、ソースコードから実行可能ファイルが生成されるまでに、主に以下のステップを経ます。

*   **コンパイル (Compile)**: `go build`コマンドが呼び出されると、まずGoコンパイラ（`cmd/compile`）が各Goソースファイル（`.go`）を対応するオブジェクトファイル（`.o`）にコンパイルします。オブジェクトファイルには、機械語コード、データ、そしてシンボル情報（関数名、変数名、型情報など）が含まれます。
*   **リンク (Link)**: 次に、Goリンカ（`cmd/link`）が、生成された複数のオブジェクトファイルと、標準ライブラリなどの既存のオブジェクトファイルを結合して、最終的な実行可能ファイルを作成します。この過程で、異なるオブジェクトファイル間で参照されているシンボル（例えば、あるファイルで定義された関数を別のファイルから呼び出す場合）が解決されます。

### 2. オブジェクトファイルフォーマット

Goのオブジェクトファイルは、独自のバイナリフォーマットを持っています。このフォーマットは、シンボル、リロケーション、PC-Lineテーブル（プログラムカウンタとソースコードの行番号のマッピング）、関数データなどの情報を効率的に格納するように設計されています。

*   **シンボル (Symbol)**: プログラム内の名前付きエンティティ（関数、グローバル変数、型など）を表します。各シンボルは、名前、バージョン、型、サイズ、データ、リロケーション情報などを持っています。
*   **リロケーション (Relocation)**: オブジェクトファイル内のコードやデータが、最終的な実行可能ファイル内のどこに配置されるかによってアドレスが変動する場合に、そのアドレスを修正するための情報です。例えば、ある関数が別の関数を呼び出す際、呼び出し先の関数のアドレスはリンク時に決定されるため、リロケーション情報が必要になります。リロケーションエントリは、参照先のシンボルを指し示します。
*   **シンボルバージョン (Symbol Version)**: Goのリンカは、異なるパッケージやコンパイル単位で同じ名前のシンボルが存在する場合に、それらを区別するためにバージョン情報を使用することがあります。特に、内部シンボルや特定のコンテキストに限定されたシンボルに対して用いられます。

### 3. `LSym`構造体

`src/cmd/internal/obj/link.go`に定義されている`LSym`構造体は、リンカが内部的にシンボルを表現するために使用する主要なデータ構造です。この構造体には、シンボルの名前、型、サイズ、データ、リロケーション、関連する型情報（`Gotype`）など、シンボルに関するあらゆる情報が含まれています。

### 4. `goobj`パッケージ

`src/cmd/internal/goobj`パッケージは、Goのオブジェクトファイルの読み書きに関する低レベルな機能を提供します。コンパイラがオブジェクトファイルを生成する際や、リンカがオブジェクトファイルを読み込む際にこのパッケージが利用されます。

## 技術的詳細

このコミットの技術的な核心は、Goのオブジェクトファイルフォーマットを変更し、シンボル参照の表現方法を最適化することにあります。

### 変更前: 直接参照

変更前は、オブジェクトファイル内のシンボルが他のシンボルを参照する際（例: リロケーションエントリが参照するシンボル、関数の型情報が参照する型シンボルなど）、その参照は直接、参照先のシンボルの「名前」と「バージョン」のペアとして記述されていました。

例えば、`func A()`が`func B()`を呼び出す場合、`A`のオブジェクトファイル内のリロケーションエントリは、`B`のシンボル名（例: `"main.B"`)とバージョン（例: `0`）を直接含んでいました。もし`func C()`も`func B()`を呼び出す場合、`C`のオブジェクトファイルにも同様に`"main.B"`と`0`が記述されていました。

### 変更後: インデックス参照

このコミットでは、以下の新しいメカニズムが導入されました。

1.  **シンボル参照リストの導入**: オブジェクトファイルのヘッダ部分に、そのオブジェクトファイル内で参照されるすべての一意なシンボル（名前とバージョンのペア）のリストが追加されます。このリストは`SymRefs`と呼ばれ、各エントリには0から始まるインデックスが割り当てられます。インデックス0は、`nil`シンボル（参照がないことを示す）のために予約されます。
2.  **インデックスによる参照**: オブジェクトファイル内のシンボルが他のシンボルを参照する際には、もはやシンボル名とバージョンを直接記述するのではなく、`SymRefs`リスト内の対応するシンボルエントリの「インデックス」を記述するようになります。

例えば、`func A()`と`func C()`が両方とも`func B()`を参照する場合、`SymRefs`リストには`"main.B"`と`0`のペアが一度だけ格納され、例えばインデックス`5`が割り当てられます。`A`と`C`のリロケーションエントリは、それぞれ`5`というインデックスを記述するだけでよくなります。

type Package struct {
	ImportPath string   // import path denoting this package
	Imports    []string // packages imported by this package
	SymRefs    []SymID  // list of symbol names and versions refered to by this pack
	Syms       []*Sym   // symbols defined by this package
	MaxVersion int      // maximum Version in any SymID in Syms
}

// readSymID reads a SymID from the input file.
func (r *objReader) readSymID() SymID {
	i := r.readInt()
	return r.p.SymRefs[i]
}

func (r *objReader) readRef() {
	name, vers := r.readString(), r.readInt()

	// In a symbol name in an object file, "". denotes the
	// current package, but in a SymID, "" denotes a nil symbol.
	// Translate "". to r.p.ImportPath.
	if name == "" {
		name = r.p.ImportPath
	}
	if vers != 0 {
		vers = r.p.MaxVersion
	}
	r.p.SymRefs = append(r.p.SymRefs, SymID{name, vers})
}

// A symbol points to other symbols using an index into the symbol
// reference sequence. Index 0 corresponds to a nil LSym* pointer.
// In the symbol layout described below "symref index" stands for this
// index.

// Each symbol is laid out as the following fields (taken from LSym*):
//
//	- byte 0xfe (sanity check for synchronization)
//	- type [int]
//	- name & version [symref index] // 変更点
//	- flags [int]
//	- size [int]
//	- gotype [symref index] // 変更点
//	- p [data block]
//	- nr [int]
//	- r [nr relocations, sorted by off]
//	  - type [int]
//	  - add [int]
//	  - xadd [int]
//	  - sym [symref index] // 変更点
//	  - xsym [symref index] // 変更点
//
// Each local has the encoding:
//
//	- asym [symref index] // 変更点
//	- offset [int]
//	- type [int]
//	- gotype [symref index] // 変更点
//
// The pcln table has the encoding:
//
//	- nfuncdata [int]
//	- funcdata [nfuncdata symref index] // 変更点
//	- funcdatasym [nfuncdata ints]
//	- nfile [int]
//	- file [nfile symref index] // 変更点

func Writeobjfile(ctxt *Link, b *Biobuf) {
	// ... (既存のコード) ...

	// Emit symbol references.
	for s := ctxt.Text; s != nil; s = s.Next {
		writerefs(ctxt, b, s)
	}
	for s := ctxt.Data; s != nil; s = s.Next {
		writerefs(ctxt, b, s)
	}
	Bputc(b, 0xff) // シンボル参照リストの終端マーカー

	// Emit symbols.
	// ... (既存のコード) ...
}

func wrref(ctxt *Link, b *Biobuf, s *LSym, isPath bool) {
	if s == nil || s.RefIdx != 0 { // すでに登録済みかnilならスキップ
		return
	}
	Bputc(b, 0xfe)
	if isPath {
		wrstring(b, filepath.ToSlash(s.Name))
	} else {
		wrstring(b, s.Name)
	}
	wrint(b, int64(s.Version))
	ctxt.RefsWritten++
	s.RefIdx = ctxt.RefsWritten // インデックスを割り当て
}

func writerefs(ctxt *Link, b *Biobuf, s *LSym) {
	wrref(ctxt, b, s, false)
	wrref(ctxt, b, s.Gotype, false)
	for i := range s.R {
		wrref(ctxt, b, s.R[i].Sym, false)
	}

	if s.Type == STEXT {
		for a := s.Autom; a != nil; a = a.Link {
			wrref(ctxt, b, a.Asym, false)
			wrref(ctxt, b, a.Gotype, false)
		}
		pc := s.Pcln
		for _, d := range pc.Funcdata {
			wrref(ctxt, b, d, false)
		}
		for _, f := range pc.File {
			wrref(ctxt, b, f, true)
		}
	}
}

func writesym(ctxt *Link, b *Biobuf, s *LSym) {
	// ... (既存のコード) ...
	Bputc(b, 0xfe)
	wrint(b, int64(s.Type))
	wrsym(b, s) // シンボル名とバージョンではなく、RefIdxを書き込む
	// ... (既存のコード) ...
}

func wrsym(b *Biobuf, s *LSym) {
	if s == nil {
		wrint(b, 0) // nilシンボルはインデックス0
		return
	}
	if s.RefIdx == 0 {
		log.Fatalln("writing an unreferenced symbol", s.Name)
	}
	wrint(b, int64(s.RefIdx)) // 割り当てられたインデックスを書き込む
}

func readref(ctxt *Link, f *obj.Biobuf, pkg string, pn string) {
	if obj.Bgetc(f) != 0xfe {
		log.Fatalf("readsym out of sync")
	}
	name := rdsymName(f, pkg)
	v := rdint(f)
	if v != 0 && v != 1 {
		log.Fatalf("invalid symbol version %d", v)
	}
	if v == 1 {
		v = ctxt.Version
	}
	lsym := Linklookup(ctxt, name, v)
	ctxt.CurRefs = append(ctxt.CurRefs, lsym) // 読み込んだシンボル参照をCurRefsに追加
}

func rdsym(ctxt *Link, f *obj.Biobuf, pkg string) *LSym {
	i := rdint(f) // インデックスを読み込む
	if i == 0 {
		return nil

## 変更の背景

Goのコンパイラとリンカは、プログラムをビルドする際にオブジェクトファイルを生成します。これらのオブジェクトファイルには、関数、変数、型などのシンボルに関する情報が含まれており、シンボルは互いを参照することが頻繁にあります。

このコミット以前は、オブジェクトファイル内のシンボル参照は、参照先のシンボルの「名前」と「バージョン」を直接記述する形式でした。しかし、同じシンボルがオブジェクトファイル内で何度も参照される場合、その都度シンボル名とバージョンが重複して書き込まれることになり、以下の問題が生じていました。

1.  **ファイルサイズの増大**: 重複するシンボル名とバージョンの文字列がオブジェクトファイルに何度も格納されるため、ファイルサイズが不必要に大きくなっていました。
2.  **リンカのパフォーマンス低下**: リンカがオブジェクトファイルを処理する際、これらのシンボル参照を解決するために、重複するシンボル名に対して繰り返しマップルックアップ（ハッシュテーブル検索）を行う必要があり、これがリンカの処理速度を低下させる要因となっていました。

この問題を解決するため、一意なシンボル参照のリストをオブジェクトファイルに導入し、各シンボル参照をそのリストへのインデックスで表現することで、ファイルサイズの削減とリンカの効率化を図るのがこの変更の背景です。コミットメッセージにあるように、`pkg/linux_amd64`のサイズが30%削減され、リンカのベンチマークも大幅に改善されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムと内部構造に関する知識が必要です。

### 1. Goのビルドプロセス

Goのプログラムは、ソースコードから実行可能ファイルが生成されるまでに、主に以下のステップを経ます。

*   **コンパイル (Compile)**: `go build`コマンドが呼び出されると、まずGoコンパイラ（`cmd/compile`）が各Goソースファイル（`.go`）を対応するオブジェクトファイル（`.o`）にコンパイルします。オブジェクトファイルには、機械語コード、データ、そしてシンボル情報（関数名、変数名、型情報など）が含まれます。
*   **リンク (Link)**: 次に、Goリンカ（`cmd/link`）が、生成された複数のオブジェクトファイルと、標準ライブラリなどの既存のオブジェクトファイルを結合して、最終的な実行可能ファイルを作成します。この過程で、異なるオブジェクトファイル間で参照されているシンボル（例えば、あるファイルで定義された関数を別のファイルから呼び出す場合）が解決されます。

### 2. オブジェクトファイルフォーマット

Goのオブジェクトファイルは、独自のバイナリフォーマットを持っています。このフォーマットは、シンボル、リロケーション、PC-Lineテーブル（プログラムカウンタとソースコードの行番号のマッピング）、関数データなどの情報を効率的に格納するように設計されています。

*   **シンボル (Symbol)**: プログラム内の名前付きエンティティ（関数、グローバル変数、型など）を表します。各シンボルは、名前、バージョン、型、サイズ、データ、リロケーション情報などを持っています。
*   **リロケーション (Relocation)**: オブジェクトファイル内のコードやデータが、最終的な実行可能ファイル内のどこに配置されるかによってアドレスが変動する場合に、そのアドレスを修正するための情報です。例えば、ある関数が別の関数を呼び出す際、呼び出し先の関数のアドレスはリンク時に決定されるため、リロケーション情報が必要になります。リロケーションエントリは、参照先のシンボルを指し示します。
*   **シンボルバージョン (Symbol Version)**: Goのリンカは、異なるパッケージやコンパイル単位で同じ名前のシンボルが存在する場合に、それらを区別するためにバージョン情報を使用することがあります。特に、内部シンボルや特定のコンテキストに限定されたシンボルに対して用いられます。

### 3. `LSym`構造体

`src/cmd/internal/obj/link.go`に定義されている`LSym`構造体は、リンカが内部的にシンボルを表現するために使用する主要なデータ構造です。この構造体には、シンボルの名前、型、サイズ、データ、リロケーション、関連する型情報（`Gotype`）など、シンボルに関するあらゆる情報が含まれています。

### 4. `goobj`パッケージ

`src/cmd/internal/goobj`パッケージは、Goのオブジェクトファイルの読み書きに関する低レベルな機能を提供します。コンパイラがオブジェクトファイルを生成する際や、リンカがオブジェクトファイルを読み込む際にこのパッケージが利用されます。

## 技術的詳細

このコミットの技術的な核心は、Goのオブジェクトファイルフォーマットを変更し、シンボル参照の表現方法を最適化することにあります。

### 変更前: 直接参照

変更前は、オブジェクトファイル内のシンボルが他のシンボルを参照する際（例: リロケーションエントリが参照するシンボル、関数の型情報が参照する型シンボルなど）、その参照は直接、参照先のシンボルの「名前」と「バージョン」のペアとして記述されていました。

例えば、`func A()`が`func B()`を呼び出す場合、`A`のオブジェクトファイル内のリロケーションエントリは、`B`のシンボル名（例: `"main.B"`)とバージョン（例: `0`）を直接含んでいました。もし`func C()`も`func B()`を呼び出す場合、`C`のオブジェクトファイルにも同様に`"main.B"`と`0`が記述されていました。

### 変更後: インデックス参照

このコミットでは、以下の新しいメカニズムが導入されました。

1.  **シンボル参照リストの導入**: オブジェクトファイルのヘッダ部分に、そのオブジェクトファイル内で参照されるすべての一意なシンボル（名前とバージョンのペア）のリストが追加されます。このリストは`SymRefs`と呼ばれ、各エントリには0から始まるインデックスが割り当てられます。インデックス0は、`nil`シンボル（参照がないことを示す）のために予約されます。
2.  **インデックスによる参照**: オブジェクトファイル内のシンボルが他のシンボルを参照する際には、もはやシンボル名とバージョンを直接記述するのではなく、`SymRefs`リスト内の対応するシンボルエントリの「インデックス」を記述するようになります。

例えば、`func A()`と`func C()`が両方とも`func B()`を参照する場合、`SymRefs`リストには`"main.B"`と`0`のペアが一度だけ格納され、例えばインデックス`5`が割り当てられます。`A`と`C`のリロケーションエントリは、それぞれ`5`というインデックスを記述するだけでよくなります。

	ImportPath string   // import path denoting this package
	Imports    []string // packages imported by this package
	SymRefs    []SymID  // list of symbol names and versions refered to by this pack

func (r *objReader) readSymID() SymID {
	i := r.readInt()

func (r *objReader) readRef() {
	name, vers := r.readString(), r.readInt()

	// In a symbol name in an object file, "". denotes the
	// current package, but in a SymID, "" denotes a nil symbol.
	// Translate "". to r.p.ImportPath.

		name = r.p.ImportPath
	}
	if vers != 0 {
		vers = r.p.MaxVersion
	}
	r.p.SymRefs = append(r.p.SymRefs, SymID{name, vers})
}

//	  - xadd [int]

func Writeobjfile(ctxt *Link, b *Biobuf) {
	// ... (既存のコード) ...

	// Emit symbol references.
	for s := ctxt.Text; s != nil; s = s.Next {
		writerefs(ctxt, b, s)
	}
	for s := ctxt.Data; s != nil; s = s.Next {
		writerefs(ctxt, b, s)
	}
	Bputc(b, 0xff) // シンボル参照リストの終端マーカー

	// Emit symbols.
	// ... (既存のコード) ...
}

func wrref(ctxt *Link, b *Biobuf, s *LSym, isPath bool) {
	if s == nil || s.RefIdx != 0 { // すでに登録済みかnilならスキップ
		return
	}
	Bputc(b, 0xfe)
	if isPath {
		wrstring(b, filepath.ToSlash(s.Name))
	} else {
		wrstring(b, s.Name)
	}
	wrint(b, int64(s.Version))
	ctxt.RefsWritten++
	s.RefIdx = ctxt.RefsWritten // インデックスを割り当て
}

func writerefs(ctxt *Link, b *Biobuf, s *LSym) {
	wrref(ctxt, b, s, false)
	wrref(ctxt, b, s.Gotype, false)
	for i := range s.R {
		wrref(ctxt, b, s.R[i].Sym, false)
	}

	if s.Type == STEXT {
		for a := s.Autom; a != nil; a = a.Link {
			wrref(ctxt, b, a.Asym, false)
			wrref(ctxt, b, a.Gotype, false)
		}
		pc := s.Pcln
		for _, d := range pc.Funcdata {
			wrref(ctxt, b, d, false)
		}
		for _, f := range pc.File {
			wrref(ctxt, b, f, true)
		}
	}
}

func writesym(ctxt *Link, b *Biobuf, s *LSym) {
	// ... (既存のコード) ...
	Bputc(b, 0xfe)
	wrint(b, int64(s.Type))
	wrsym(b, s) // シンボル名とバージョンではなく、RefIdxを書き込む
	// ... (既存のコード) ...
}

func wrsym(b *Biobuf, s *LSym) {
	if s == nil {
		wrint(b, 0) // nilシンボルはインデックス0
		return
	}
	if s.RefIdx == 0 {
		log.Fatalln("writing an unreferenced symbol", s.Name)
	}
	wrint(b, int64(s.RefIdx)) // 割り当てられたインデックスを書き込む
}

## コアとなるコードの解説

### `src/cmd/internal/goobj/read.go`

*   **`Package`構造体への`SymRefs`追加**:
    *   `SymRefs []SymID`が追加され、オブジェクトファイルから読み込まれる一意なシンボル参照のリストを保持します。`SymID`はシンボル名とバージョンをペアにした構造体です。
*   **`readSymID()`の変更**:
    *   以前はシンボル名とバージョンを直接読み込んで`SymID`を構築していましたが、変更後は`r.readInt()`でインデックス`i`を読み込み、`r.p.SymRefs[i]`として、既に読み込まれている`SymRefs`リストから対応する`SymID`を返します。これにより、オブジェクトファイル内のシンボル参照がインデックスベースになったことを示します。
*   **`readRef()`の追加**:
    *   この新しい関数は、オブジェクトファイルからシンボル名とバージョンを読み込み、現在のパッケージの`ImportPath`に基づいて名前を調整し、`SymID`を作成して`r.p.SymRefs`スライスに追加します。これは、オブジェクトファイルのヘッダ部分にあるシンボル参照リストを構築するために使用されます。
*   **`parseObject()`の変更**:
    *   シンボル本体を読み込むループの前に、`r.p.SymRefs = []SymID{{"", 0}}`でインデックス0を`nil`シンボルとして初期化し、`for`ループで`readRef()`を繰り返し呼び出して、オブジェクトファイル内のシンボル参照リスト全体を読み込みます。`0xff`バイトがリストの終端を示します。

### `src/cmd/internal/obj/link.go`

*   **`LSym`構造体への`RefIdx`追加**:
    *   `RefIdx int`フィールドが追加されました。これは、リンカがオブジェクトファイルを書き出す際に、この`LSym`が`SymRefs`リスト内で何番目のインデックスに割り当てられたかを記録するためのものです。初期値は0で、これは`nil`シンボルを意味します。
*   **`Link`構造体への`RefsWritten`追加**:
    *   `RefsWritten int`フィールドが追加されました。これは、オブジェクトファイルに書き込まれた一意なシンボル参照の総数を追跡し、新しい`RefIdx`を割り当てる際に使用されます。

### `src/cmd/internal/obj/objfile.go`

*   **オブジェクトファイルフォーマットの更新**:
    *   コメントが更新され、シンボルが「シンボル参照インデックス」を使用して他のシンボルを参照するようになったことが明確に記述されています。
*   **`Writeobjfile()`の変更**:
    *   シンボル本体を書き出す前に、`ctxt.Text`と`ctxt.Data`の各シンボルに対して`writerefs()`を呼び出すループが追加されました。これにより、オブジェクトファイルにシンボル参照リストが先行して書き込まれます。リストの終端は`0xff`でマークされます。
*   **`wrref()`の追加**:
    *   この関数は、与えられた`LSym`がまだ`SymRefs`リストに登録されていない場合（`s.RefIdx == 0`）、そのシンボル名とバージョンをオブジェクトファイルに書き込み、`ctxt.RefsWritten`をインクリメントし、その値を`s.RefIdx`に割り当てます。これにより、各一意なシンボル参照にインデックスが割り当てられます。
*   **`writerefs()`の追加**:
    *   この関数は、与えられた`LSym`自体だけでなく、その`Gotype`、リロケーション先のシンボル、関数データ、ファイルシンボルなど、その`LSym`が参照する可能性のあるすべてのシンボルに対して`wrref()`を再帰的に呼び出します。これにより、オブジェクトファイル内のすべてのシンボル参照が`SymRefs`リストに確実に登録されます。
*   **`writesym()`の変更**:
    *   シンボル名とバージョンを直接書き込む代わりに、`wrsym(b, s)`を呼び出すように変更されました。
*   **`wrsym()`の変更**:
    *   以前はシンボル名とバージョンを書き込んでいましたが、変更後は`s == nil`の場合はインデックス`0`を、それ以外の場合は`s.RefIdx`（割り当てられたインデックス）を書き込みます。`s.RefIdx`が`0`の場合はエラーを発生させ、未参照のシンボルが書き込まれるのを防ぎます。

### `src/cmd/link/internal/ld/objfile.go`

*   **オブジェクトファイルフォーマットの更新**:
    *   `src/cmd/internal/obj/objfile.go`と同様に、オブジェクトファイルのフォーマット記述が更新されています。
*   **`ldobjfile()`の変更**:
    *   シンボル本体を読み込むループの前に、`ctxt.CurRefs = []*LSym{nil}`でインデックス0を`nil`シンボルとして初期化し、`for`ループで`readref()`を繰り返し呼び出して、オブジェクトファイル内のシンボル参照リスト全体を読み込み、`ctxt.CurRefs`に格納します。
*   **`readsym()`の変更**:
    *   以前はシンボル名とバージョンを直接読み込んで`LSym`を検索していましたが、変更後は`rdsym(ctxt, f, pkg)`を呼び出して`LSym`を取得するように変更されました。

    *   この新しい関数は、オブジェクトファイルからシンボル名とバージョンを読み込み、`Linklookup()`で対応する`LSym`を取得し、それを`ctxt.CurRefs`スライスに追加します。これは、リンカがオブジェクトファイルのシンボル参照リストを構築するために使用されます。

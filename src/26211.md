# [インデックス 26211] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `Transport.roundTrip` と `persistConn.readLoop` 間のプロトコルをさらに厳密化し、信頼性を向上させるための変更です。特に、HTTPクライアントのコネクション管理、アイドルコネクションの再利用、そして競合状態におけるチャネル通信の堅牢性に関する問題に対処しています。

    change to tighten and simplify the communication protocol between
    Transport.roundTrip and persistConn.readLoop in
    https://golang.org/cl/17890 wasn't complete.
    
    This change simplifies it further: the buffered-vs-unbuffered
    complexity goes away, and we no longer need to re-try channel reads in
    the select case. It was trying to prioritize channels in the case that
    two were readable in the select. (it was only failing in the race builder
    because the race builds randomize select scheduling)
    
    The problem was that in the bodyless response case we had to return
    the idle connection before replying to roundTrip. But putIdleConn
    previously both added it to the free list (which we wanted), but also
    closed the connection, which made the caller goroutine
    (Transport.roundTrip) have two readable cases: pc.closech, and the
    response. We guarded against similar conditions in the caller's select
    for two readable channels, but such a fix wasn't possible here, and would
    be overly complicated.
    
    Instead, switch to unbuffered channels. The unbuffered channels were only
    to prevent goroutine leaks, so address that differently: add a "callerGone"
    channel closed by the caller on exit, and select on that during any unbuffered
    sends.
    
    As part of the fix, split putIdleConn into two halves: a part that
    just returns to the freelist, and a part that also closes. Update the
    four callers to the variants each wanted.
    
    Incidentally, the connections were closing on return to the pool due
    to MaxIdleConnsPerHost (somewhat related: #13801), but this bug
    could've manifested for plenty of other reasons.

## 元コミット内容

このコミットは、以前の変更 (https://golang.org/cl/17890) が不完全であったことを受けて、`net/http` パッケージ内の `Transport.roundTrip` と `persistConn.readLoop` 間の通信プロトコルをさらに厳密化し、簡素化することを目的としています。

主な変更点は以下の通りです。

1.  **バッファリングされたチャネルとアンバッファリングされたチャネルの複雑さの解消**: 以前の設計では、チャネルのバッファリング状態によって挙動が異なり、複雑さが増していました。このコミットでは、この複雑さを排除します。
2.  **`select` 文でのチャネル読み取りのリトライの廃止**: 以前は、`select` 文で複数のチャネルが読み取り可能になった場合に、チャネルの優先順位付けを試みるためにリトライロジックが必要でした。これは特にレースビルド環境で `select` のスケジューリングがランダム化されるために問題を引き起こしていました。
3.  **ボディレスレスポンスのケースにおける問題の解決**: ボディを持たないレスポンスの場合、アイドルコネクションを `roundTrip` に応答する前に返却する必要がありました。しかし、`putIdleConn` はコネクションをフリーリストに追加すると同時に閉じてしまうため、呼び出し元のゴルーチン (`Transport.roundTrip`) が `pc.closech` とレスポンスという2つの読み取り可能なチャネルを持つことになり、問題が発生していました。
4.  **アンバッファリングチャネルへの切り替えとゴルーチンリーク対策**: 上記の問題を解決するため、アンバッファリングチャネルに切り替えます。アンバッファリングチャネルはゴルーチンリークを防ぐ目的で使われていましたが、このコミットでは「`callerGone`」チャネルを導入し、呼び出し元が終了時にこのチャネルを閉じることで、アンバッファリング送信中のゴルーチンリークを防ぎます。
5.  **`putIdleConn` の分割**: `putIdleConn` 関数を、フリーリストにコネクションを戻すだけの部分 (`tryPutIdleConn`) と、コネクションを閉じる部分 (`putOrCloseIdleConn`) の2つに分割します。これにより、呼び出し元は必要な機能だけを利用できるようになります。

この変更は、`#13825` で報告された不安定なテストのデバッグ中に発見された問題に対処し、`#13801` に関連する `MaxIdleConnsPerHost` によるコネクションクローズの問題にも間接的に関連しています。

## 変更の背景

このコミットの背景には、Goの `net/http` クライアントにおけるコネクション管理の堅牢性と信頼性の向上が挙げられます。特に、以下の問題が顕在化していました。

1.  **不安定なテスト (`#13825`)**: `net/http` パッケージのテストスイートにおいて、特定の条件下でテストが不安定になる問題が報告されていました。これは、並行処理におけるチャネル通信のタイミングや競合状態に起因するもので、特に `race builder` (競合検出機能が有効なビルド) で顕著でした。`race builder` は `select` 文のスケジューリングをランダム化するため、通常のビルドでは表面化しない競合状態を露呈させることがあります。
2.  **`Transport.roundTrip` と `persistConn.readLoop` 間のプロトコル不備**: HTTPクライアントの `Transport` は、HTTPリクエストを送信し、レスポンスを受信する役割を担います。この際、永続的なコネクション (`persistConn`) を利用して複数のリクエスト/レスポンスを処理します。`roundTrip` はリクエストの送信とレスポンスの受信を調整し、`readLoop` は実際のネットワークからの読み取りを担当します。これら二つのゴルーチン間の通信プロトコルが十分に厳密でなかったため、特定のシナリオ（特にボディレスレスポンスの場合）で競合状態が発生し、コネクションが意図せず閉じられたり、アイドルコネクションプールへの返却が正しく行われなかったりする可能性がありました。
3.  **`putIdleConn` の二重の役割**: 以前の `putIdleConn` 関数は、アイドルコネクションをプールに戻すだけでなく、特定の条件下でコネクションを閉じる役割も持っていました。この二重の役割が、ボディレスレスポンスのケースで `roundTrip` ゴルーチンが `pc.closech` とレスポンスチャネルの両方から読み取り可能になるという競合状態を引き起こしていました。
4.  **ゴルーチンリークの懸念**: アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、ゴルーチンリークのリスクがあります。以前の設計では、このリスクを軽減するためのメカニズムが不十分でした。

これらの問題は、HTTPクライアントの信頼性に直接影響し、アプリケーションのパフォーマンスや安定性を損なう可能性がありました。このコミットは、これらの根本原因に対処し、より堅牢で予測可能なコネクション管理を実現することを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびHTTPプロトコルに関する前提知識が必要です。

1.  **Goの並行処理とチャネル**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量なスレッドのようなもので、並行処理の基本単位です。`go` キーワードを使って関数を呼び出すことで起動します。
    *   **チャネル (Channel)**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルにはバッファリングされたものとアンバッファリングされたものがあります。
        *   **アンバッファリングチャネル**: バッファサイズが0のチャネルです。送信操作は受信操作が準備できるまでブロックされ、受信操作は送信操作が準備できるまでブロックされます。これにより、送信側と受信側の同期が保証されます。
        *   **バッファリングチャネル**: バッファサイズが1以上のチャネルです。バッファが満杯でない限り、送信操作はブロックされません。バッファが空でない限り、受信操作はブロックされません。
    *   **`select` 文**: 複数のチャネル操作を待機し、準備ができた最初のチャネル操作を実行します。`select` 文は、どのケースが実行されるかをランダムに選択することがあります（特に複数のチャネルが同時に準備できた場合）。これが「race builds randomize select scheduling」というコミットメッセージの記述に関連します。
    *   **ゴルーチンリーク**: 終了すべきゴルーチンが何らかの理由で終了せず、リソースを消費し続ける状態を指します。チャネル操作がブロックされたままになり、対応する受信側や送信側が存在しない場合に発生しやすいです。

2.  **HTTP/1.1 Keep-Alive とコネクション再利用**:
    *   **Keep-Alive**: HTTP/1.1 の機能で、単一のTCPコネクション上で複数のHTTPリクエスト/レスポンスをやり取りすることを可能にします。これにより、コネクション確立のオーバーヘッド（TCPハンドシェイク、TLSハンドシェイクなど）を削減し、パフォーマンスを向上させます。
    *   **アイドルコネクションプール**: HTTPクライアントは、Keep-Aliveが有効なコネクションを使い終わった後、すぐに閉じずにプールに保持します。同じホストへの次のリクエストが来た際に、このプールから既存のコネクションを再利用することで、効率を高めます。
    *   **`MaxIdleConnsPerHost`**: `net/http.Transport` の設定項目で、ホストごとに保持するアイドルコネクションの最大数を指定します。この制限を超えると、古いアイドルコネクションは閉じられます。

3.  **`net/http.Transport` の内部構造**:
    *   **`Transport`**: HTTPクライアントの低レベルな実装を担う構造体で、コネクションの確立、プール、リクエストの送信、レスポンスの受信などを管理します。
    *   **`roundTrip` メソッド**: `Transport` の主要なメソッドで、単一のHTTPリクエスト/レスポンスサイクルを処理します。
    *   **`persistConn` 構造体**: 永続的なTCPコネクション（Keep-Aliveコネクション）を表す構造体です。この構造体には、コネクションの状態（閉じられているか、壊れているかなど）や、リクエスト/レスポンスを処理するためのチャネルなどが含まれます。
    *   **`readLoop` ゴルーチン**: `persistConn` に関連付けられたゴルーチンで、ネットワークからデータを継続的に読み取り、受信したHTTPレスポンスを解析し、適切なチャネルを通じて `roundTrip` ゴルーチンに渡します。
    *   **`writeLoop` ゴルーチン**: `persistConn` に関連付けられたゴルーチンで、リクエストボディをネットワークに書き込みます。

これらの概念を理解することで、コミットが解決しようとしている問題と、その解決策の技術的な詳細をより深く把握することができます。

## 技術的詳細

このコミットの技術的詳細は、主に `net/http.Transport` の内部における `roundTrip` と `readLoop` ゴルーチン間の通信プロトコルの変更に集約されます。

1.  **`persistConn.closed` フィールドの変更**:
    *   以前は `bool` 型 (`closed bool`) で、コネクションが閉じられたかどうかを示すフラグでした。
    *   変更後、`error` 型 (`closed error`) になりました。これにより、コネクションが閉じられた理由（エラー）を記録できるようになり、デバッグ情報が豊富になります。`nil` でない場合は閉じられていることを意味します。

2.  **`putIdleConn` 関数の分割とエラーハンドリングの強化**:
    *   以前の `putIdleConn` は、アイドルコネクションをプールに戻すか、または閉じるかの両方のロジックを含んでいました。また、成功/失敗を `bool` で返していました。
    *   このコミットでは、`putIdleConn` を `tryPutIdleConn` と `putOrCloseIdleConn` の2つに分割しました。
        *   `tryPutIdleConn(*persistConn) error`: コネクションをアイドルプールに登録しようと試み、成功すれば `nil` を、失敗すればその理由を示す `error` を返します。この関数はコネクションを閉じません。
        *   `putOrCloseIdleConn(*persistConn)`: `tryPutIdleConn` を呼び出し、エラーが返された場合に `pconn.close(err)` を呼び出してコネクションを閉じます。
    *   これにより、コネクションをプールに戻すロジックと閉じるロジックが明確に分離され、呼び出し元は自身の意図に応じて適切な関数を選択できるようになりました。
    *   また、`errKeepAlivesDisabled`, `errConnBroken`, `errWantIdle`, `errTooManyIdle` などの新しいエラー変数が導入され、`tryPutIdleConn` がコネクションをプールに登録できなかった具体的な理由を詳細に伝えることができるようになりました。

3.  **アンバッファリングチャネルへの切り替えと `callerGone` チャネルの導入**:
    *   コミットメッセージにあるように、以前はバッファリングされたチャネルとアンバッファリングされたチャネルが混在しており、特にボディレスレスポンスのケースで `select` 文の競合状態を引き起こしていました。
    *   この変更では、`requestAndChan.ch` (リクエストとレスポンスをやり取りするチャネル) をアンバッファリングチャネルに変更しました (`ch chan responseAndError` から `ch chan responseAndError // unbuffered; always send in select on callerGone`)。
    *   アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、ゴルーチンリークのリスクがあります。これを防ぐために、`requestAndChan` 構造体に `callerGone <-chan struct{}` という新しいフィールドが追加されました。
    *   `callerGone` チャネルは、`roundTrip` ゴルーチンが終了する際に閉じられます。`readLoop` ゴルーチンは、アンバッファリングチャネルへの送信を行う `select` 文の中で `<-rc.callerGone` も監視します。これにより、`roundTrip` が先に終了した場合でも `readLoop` がブロックされずに終了できるようになり、ゴルーチンリークが防止されます。

4.  **`readLoop` と `roundTrip` の `select` ロジックの簡素化**:
    *   `readLoop` 内でレスポンスを `rc.ch` に送信する際、以前はバッファリングされたチャネルとアンバッファリングされたチャネルの挙動の違いを考慮した複雑なロジックがありました。
    *   新しい実装では、`select` 文を使って `rc.ch <- responseAndError{res: resp}` または `<-rc.callerGone` のいずれかを待機する形に統一され、簡素化されました。これにより、チャネルの優先順位付けやリトライの必要がなくなりました。
    *   `roundTrip` 内の `WaitResponse` ループも簡素化され、`writeErrCh` からのエラー処理が直接的になり、以前のような `select` 内でのタイムアウトを伴うリトライロジックが削除されました。

5.  **`responseAndError` 構造体の簡素化**:
    *   以前の `responseAndError` は、`ch chan *Response` と `r *Response` の両方を持っており、`res()` メソッドでどちらを使うかを判断していました。
    *   変更後、`res *Response` のみを持つようになり、`ch` フィールドが削除されました。これは、`requestAndChan.ch` が直接 `responseAndError` を送受信するようになったため、`responseAndError` 内部でさらにチャネルを持つ必要がなくなったためです。これにより、構造体が簡素化され、意図が明確になりました。

これらの変更により、`net/http` クライアントのコネクション管理における並行処理のロジックがより明確になり、競合状態が減少し、全体的な堅牢性が向上しています。特に、`select` 文のランダムなスケジューリングに依存しない、より予測可能な挙動が実現されました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は、主に `src/net/http/transport.go` に集中しています。

1.  **`persistConn` 構造体の変更**:
    ```go

    // After

    `closed` フィールドが `bool` から `error` に変更され、コネクションが閉じられた理由を保持できるようになりました。

2.  **`putIdleConn` 関数の分割と新しいエラー定義**:
    ```go

    	errKeepAlivesDisabled = errors.New("http: putIdleConn: keep alives disabled")

    	}
    }

    // Renamed and modified putIdleConn to tryPutIdleConn
    // func (t *Transport) putIdleConn(pconn *persistConn) bool { // Before
    func (t *Transport) tryPutIdleConn(pconn *persistConn) error { // After
    	// ... logic to check conditions and return specific errors ...
    	// Instead of `return false` or `return true`, it now returns `error` or `nil`.
    }
    ```
    `putIdleConn` が `tryPutIdleConn` にリネーム・変更され、`putOrCloseIdleConn` が新設されました。また、コネクションをプールに登録できない具体的な理由を示すエラーが複数定義されました。

3.  **`persistConn.readLoop` 内の変更**:
    ```go

    // After
    closeErr := errReadLoopExiting // default value, if not changed below
    defer func() { pc.close(closeErr) }()

    tryPutIdleConn := func() bool {
    	if err := pc.t.tryPutIdleConn(pc); err != nil {
    		closeErr = err
    		return false
    	}
    	return true
    }

    // ... inside the loop, where responses are sent ...
    // Before (example for bodyless response)
    // resc := make(chan *Response)        // unbuffered matters; see below
    // rc.ch <- responseAndError{ch: resc} // buffered send
    // ...
    // alive = alive && ... && pc.t.putIdleConn(pc)
    // resc <- resp // unbuffered send

    // After (example for bodyless response and other response sends)
    // Replaced with:
    select {
    case rc.ch <- responseAndError{res: resp}:
    case <-rc.callerGone:
    	return
    }
    // ...
    // alive = alive && ... && tryPutIdleConn()
    ```
    `readLoop` の `defer` 処理が変更され、`closeErr` を記録するようになりました。また、`tryPutIdleConn` のローカル関数が定義され、レスポンス送信時のチャネル操作が `select` と `callerGone` を使用する形に統一・簡素化されました。

4.  **`requestAndChan` 構造体の変更**:
    ```go

    // ch  chan responseAndError
    // After
    ch  chan responseAndError // unbuffered; always send in select on callerGone
    // New field
    callerGone <-chan struct{} // closed when roundTrip caller has returned
    ```
    `ch` フィールドがアンバッファリングチャネルとして明示され、`callerGone` チャネルが追加されました。

    // After
    // case <-pc.closech:
    //   ... err = beforeRespHeaderError{fmt.Errorf("net/http: HTTP/1 transport connection broken: %v", pc.closed)} ...
    ```
    `roundTrip` メソッド内で `callerGone` チャネルが作成され、`requestAndChan` に渡されるようになりました。また、`WaitResponse` ループ内のエラーハンドリングとチャネル待機ロジックが簡素化されました。

6.  **`persistConn.close` および `closeLocked` の変更**:
    ```go
    // Before
    // func (pc *persistConn) close() { ... pc.closeLocked() ... }
    // func (pc *persistConn) closeLocked() { ... if !pc.closed { pc.conn.Close(); pc.closed = true; close(pc.closech) } ... }
    // After
    func (pc *persistConn) close(err error) { // Now takes an error argument
    	pc.lk.Lock()
    	defer pc.lk.Unlock()
    	pc.closeLocked(err)
    }

    func (pc *persistConn) closeLocked(err error) { // Now takes an error argument
    	if err == nil {
    		panic("nil error") // Ensure an error is always provided
    	}
    	pc.broken = true
    	if pc.closed == nil { // Check if closed error is nil
    		pc.conn.Close()
    		pc.closed = err // Store the error
    		close(pc.closech)
    	}
    	// ...
    }
    ```
    `close` および `closeLocked` メソッドが `error` 引数を受け取るようになり、コネクションが閉じられた理由を `pc.closed` に記録するようになりました。

これらの変更は、`net/http` クライアントの内部的な堅牢性を高め、特に並行処理における競合状態やデッドロックのリスクを軽減することを目的としています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`net/http` パッケージにおけるHTTPクライアントのコネクション管理、特に `Transport.roundTrip` と `persistConn.readLoop` という2つの主要なゴルーチン間の通信プロトコルを改善することにあります。

**問題点**:
以前の実装では、特にボディを持たないHTTPレスポンス（例: `HEAD` リクエストのレスポンス）を処理する際に問題が発生していました。`persistConn.readLoop` はレスポンスを読み取った後、コネクションをアイドルプールに戻すために `putIdleConn` を呼び出していました。しかし、`putIdleConn` はコネクションをプールに戻すと同時に、特定の条件下でコネクションを閉じてしまう可能性がありました。
このとき、`Transport.roundTrip` ゴルーチンは、レスポンスを受け取るためのチャネルと、コネクションが閉じられたことを通知する `pc.closech` の両方から読み取り可能になる可能性がありました。Goの `select` 文は、複数のチャネルが同時に準備できた場合、どのチャネルを選択するかをランダムに決定することがあります（特に `race builder` 環境で顕著）。このランダム性により、`roundTrip` が意図しないチャネル（例えば `pc.closech`）を先に選択してしまい、レスポンスの処理が正しく行われない、あるいはデッドロックに陥るなどの不安定な挙動を引き起こしていました。

**解決策**:

1.  **`putIdleConn` の分割**:
    *   `putIdleConn` の役割が曖昧であったため、これを `tryPutIdleConn` と `putOrCloseIdleConn` に分割しました。
    *   `tryPutIdleConn` は、コネクションをアイドルプールに登録できるかどうかを試み、成功すれば `nil` を、失敗すれば具体的なエラーを返します。この関数はコネクションを閉じません。
    *   `putOrCloseIdleConn` は `tryPutIdleConn` を呼び出し、もしプールへの登録に失敗した場合は、そのエラーを理由としてコネクションを閉じます。
    *   これにより、コネクションをプールに戻すことと、コネクションを閉じることのロジックが明確に分離され、各呼び出し元は自身の意図に合った関数を呼び出すことができるようになりました。特に `readLoop` は、コネクションをプールに戻すことだけを試み、その結果に基づいて閉じるかどうかを判断できるようになります。

2.  **アンバッファリングチャネルと `callerGone` の導入**:
    *   `roundTrip` と `readLoop` 間の主要な通信チャネル (`requestAndChan.ch`) をアンバッファリングチャネルに変更しました。アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、より厳密な同期を保証します。
    *   しかし、アンバッファリングチャネルはゴルーチンリークのリスクも伴います。例えば、`readLoop` がレスポンスを送信しようとしている間に `roundTrip` が何らかの理由で先に終了してしまった場合、`readLoop` はチャネル送信で永遠にブロックされ、リークしてしまいます。
    *   この問題を解決するために、`requestAndChan` に `callerGone <-chan struct{}` という新しいチャネルが追加されました。
    *   `roundTrip` ゴルーチンは、自身の開始時にこの `callerGone` チャネルを作成し、終了時にこれを閉じます。
    *   `readLoop` ゴルーチンは、アンバッファリングチャネルへの送信を行う `select` 文の中で、`rc.ch <- ...` と同時に `<-rc.callerGone` も監視します。
    *   これにより、`roundTrip` が先に終了して `callerGone` が閉じられた場合、`readLoop` はチャネル送信を諦めて安全に終了できるようになり、ゴルーチンリークが防止されます。

3.  **`persistConn.closed` の `error` 型への変更**:
    *   コネクションが閉じられた理由を `bool` ではなく `error` として記録することで、デバッグ時の情報が格段に増えました。これにより、なぜコネクションが閉じられたのか、その根本原因を特定しやすくなります。

これらの変更により、`net/http` クライアントは、特に高負荷時や競合状態が発生しやすいシナリオにおいて、より安定して動作するようになりました。`select` 文のランダムなスケジューリングに起因する不安定性が解消され、コネクションのライフサイクル管理がより予測可能で堅牢なものになっています。

## 元コミット内容

このコミットは、以前の変更 (https://golang.org/cl/17890) が不完全であったことを受けて、`net/http` パッケージ内の `Transport.roundTrip` と `persistConn.readLoop` 間の通信プロトコルをさらに厳密化し、簡素化することを目的としています。

主な変更点は以下の通りです。

1.  **バッファリングされたチャネルとアンバッファリングされたチャネルの複雑さの解消**: 以前の設計では、チャネルのバッファリング状態によって挙動が異なり、複雑さが増していました。このコミットでは、この複雑さを排除します。
2.  **`select` 文でのチャネル読み取りのリトライの廃止**: 以前は、`select` 文で複数のチャネルが読み取り可能になった場合に、チャネルの優先順位付けを試みるためにリトライロジックが必要でした。これは特にレースビルド環境で `select` のスケジューリングがランダム化されるために問題を引き起こしていました。
3.  **ボディレスレスポンスのケースにおける問題の解決**: ボディを持たないレスポンスの場合、アイドルコネクションを `roundTrip` に応答する前に返却する必要がありました。しかし、`putIdleConn` はコネクションをフリーリストに追加すると同時に閉じてしまうため、呼び出し元のゴルーチン (`Transport.roundTrip`) が `pc.closech` とレスポンスという2つの読み取り可能なチャネルを持つことになり、問題が発生していました。
4.  **アンバッファリングチャネルへの切り替えとゴルーチンリーク対策**: 上記の問題を解決するため、アンバッファリングチャネルに切り替えます。アンバッファリングチャネルはゴルーチンリークを防ぐ目的で使われていましたが、このコミットでは「`callerGone`」チャネルを導入し、呼び出し元が終了時にこのチャネルを閉じることで、アンバッファリング送信中のゴルーチンリークを防ぎます。
5.  **`putIdleConn` の分割**: `putIdleConn` 関数を、フリーリストにコネクションを戻すだけの部分 (`tryPutIdleConn`) と、コネクションを閉じる部分 (`putOrCloseIdleConn`) の2つに分割します。これにより、呼び出し元は必要な機能だけを利用できるようになります。

この変更は、`#13825` で報告された不安定なテストのデバッグ中に発見された問題に対処し、`#13801` に関連する `MaxIdleConnsPerHost` によるコネクションクローズの問題にも間接的に関連しています。

## 変更の背景

このコミットの背景には、Goの `net/http` クライアントにおけるコネクション管理の堅牢性と信頼性の向上が挙げられます。特に、以下の問題が顕在化していました。

1.  **不安定なテスト (`#13825`)**: `net/http` パッケージのテストスイートにおいて、特定の条件下でテストが不安定になる問題が報告されていました。これは、並行処理におけるチャネル通信のタイミングや競合状態に起因するもので、特に `race builder` (競合検出機能が有効なビルド) で顕著でした。`race builder` は `select` 文のスケジューリングをランダム化するため、通常のビルドでは表面化しない競合状態を露呈させることがあります。
2.  **`Transport.roundTrip` と `persistConn.readLoop` 間のプロトコル不備**: HTTPクライアントの `Transport` は、HTTPリクエストを送信し、レスポンスを受信する役割を担います。この際、永続的なコネクション (`persistConn`) を利用して複数のリクエスト/レスポンスを処理します。`roundTrip` はリクエストの送信とレスポンスの受信を調整し、`readLoop` は実際のネットワークからの読み取りを担当します。これら二つのゴルーチン間の通信プロトコルが十分に厳密でなかったため、特定のシナリオ（特にボディレスレスポンスの場合）で競合状態が発生し、コネクションが意図せず閉じられたり、アイドルコネクションプールへの返却が正しく行われなかったりする可能性がありました。
3.  **`putIdleConn` の二重の役割**: 以前の `putIdleConn` 関数は、アイドルコネクションをプールに戻すだけでなく、特定の条件下でコネクションを閉じる役割も持っていました。この二重の役割が、ボディレスレスポンスのケースで `roundTrip` ゴルーチンが `pc.closech` とレスポンスチャネルの両方から読み取り可能になるという競合状態を引き起こしていました。
4.  **ゴルーチンリークの懸念**: アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、ゴルーチンリークのリスクがあります。以前の設計では、このリスクを軽減するためのメカニズムが不十分でした。

これらの問題は、HTTPクライアントの信頼性に直接影響し、アプリケーションのパフォーマンスや安定性を損なう可能性がありました。このコミットは、これらの根本原因に対処し、より堅牢で予測可能なコネクション管理を実現することを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびHTTPプロトコルに関する前提知識が必要です。

1.  **Goの並行処理とチャネル**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量なスレッドのようなもので、並行処理の基本単位です。`go` キーワードを使って関数を呼び出すことで起動します。
    *   **チャネル (Channel)**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルにはバッファリングされたものとアンバッファリングされたものがあります。
        *   **アンバッファリングチャネル**: バッファサイズが0のチャネルです。送信操作は受信操作が準備できるまでブロックされ、受信操作は送信操作が準備できるまでブロックされます。これにより、送信側と受信側の同期が保証されます。
        *   **バッファリングチャネル**: バッファサイズが1以上のチャネルです。バッファが満杯でない限り、送信操作はブロックされません。バッファが空でない限り、受信操作はブロックされません。
    *   **`select` 文**: 複数のチャネル操作を待機し、準備ができた最初のチャネル操作を実行します。`select` 文は、複数のチャネルが同時に準備できた場合、どのケースが実行されるかをランダムに選択することがあります。これが「race builds randomize select scheduling」というコミットメッセージの記述に関連します。
    *   **ゴルーチンリーク**: 終了すべきゴルーチンが何らかの理由で終了せず、リソースを消費し続ける状態を指します。チャネル操作がブロックされたままになり、対応する受信側や送信側が存在しない場合に発生しやすいです。

2.  **HTTP/1.1 Keep-Alive とコネクション再利用**:
    *   **Keep-Alive**: HTTP/1.1 の機能で、単一のTCPコネクション上で複数のHTTPリクエスト/レスポンスをやり取りすることを可能にします。これにより、コネクション確立のオーバーヘッド（TCPハンドシェイク、TLSハンドシェイクなど）を削減し、パフォーマンスを向上させます。
    *   **アイドルコネクションプール**: HTTPクライアントは、Keep-Aliveが有効なコネクションを使い終わった後、すぐに閉じずにプールに保持します。同じホストへの次のリクエストが来た際に、このプールから既存のコネクションを再利用することで、効率を高めます。
    *   **`MaxIdleConnsPerHost`**: `net/http.Transport` の設定項目で、ホストごとに保持するアイドルコネクションの最大数を指定します。この制限を超えると、古いアイドルコネクションは閉じられます。

3.  **`net/http.Transport` の内部構造**:
    *   **`Transport`**: HTTPクライアントの低レベルな実装を担う構造体で、コネクションの確立、プール、リクエストの送信、レスポンスの受信などを管理します。
    *   **`roundTrip` メソッド**: `Transport` の主要なメソッドで、単一のHTTPリクエスト/レスポンスサイクルを処理します。
    *   **`persistConn` 構造体**: 永続的なTCPコネクション（Keep-Aliveコネクション）を表す構造体です。この構造体には、コネクションの状態（閉じられているか、壊れているかなど）や、リクエスト/レスポンスを処理するためのチャネルなどが含まれます。
    *   **`readLoop` ゴルーチン**: `persistConn` に関連付けられたゴルーチンで、ネットワークからデータを継続的に読み取り、受信したHTTPレスポンスを解析し、適切なチャネルを通じて `roundTrip` ゴルーチンに渡します。
    *   **`writeLoop` ゴルーチン**: `persistConn` に関連付けられたゴルーチンで、リクエストボディをネットワークに書き込みます。

これらの概念を理解することで、コミットが解決しようとしている問題と、その解決策の技術的な詳細をより深く把握することができます。

## 技術的詳細

このコミットの技術的詳細は、主に `net/http.Transport` の内部における `roundTrip` と `readLoop` ゴルーチン間の通信プロトコルの変更に集約されます。

1.  **`persistConn.closed` フィールドの変更**:
    *   以前は `bool` 型 (`closed bool`) で、コネクションが閉じられたかどうかを示すフラグでした。
    *   変更後、`error` 型 (`closed error`) になりました。これにより、コネクションが閉じられた理由（エラー）を記録できるようになり、デバッグ情報が豊富になります。`nil` でない場合は閉じられていることを意味します。

2.  **`putIdleConn` 関数の分割とエラーハンドリングの強化**:
    *   以前の `putIdleConn` は、アイドルコネクションをプールに戻すか、または閉じるかの両方のロジックを含んでいました。また、成功/失敗を `bool` で返していました。
    *   このコミットでは、`putIdleConn` を `tryPutIdleConn` と `putOrCloseIdleConn` の2つに分割しました。
        *   `tryPutIdleConn(*persistConn) error`: コネクションをアイドルプールに登録しようと試み、成功すれば `nil` を、失敗すればその理由を示す `error` を返します。この関数はコネクションを閉じません。
        *   `putOrCloseIdleConn(*persistConn)`: `tryPutIdleConn` を呼び出し、エラーが返された場合に `pconn.close(err)` を呼び出してコネクションを閉じます。
    *   これにより、コネクションをプールに戻すロジックと閉じるロジックが明確に分離され、呼び出し元は自身の意図に応じて適切な関数を選択できるようになりました。
    *   また、`errKeepAlivesDisabled`, `errConnBroken`, `errWantIdle`, `errTooManyIdle` などの新しいエラー変数が導入され、`tryPutIdleConn` がコネクションをプールに登録できなかった具体的な理由を詳細に伝えることができるようになりました。

3.  **アンバッファリングチャネルへの切り替えと `callerGone` チャネルの導入**:
    *   コミットメッセージにあるように、以前はバッファリングされたチャネルとアンバッファリングされたチャネルが混在しており、特にボディレスレスポンスのケースで `select` 文の競合状態を引き起こしていました。
    *   この変更では、`requestAndChan.ch` (リクエストとレスポンスをやり取りするチャネル) をアンバッファリングチャネルに変更しました (`ch chan responseAndError` から `ch chan responseAndError // unbuffered; always send in select on callerGone`)。
    *   アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、ゴルーチンリークのリスクがあります。これを防ぐために、`requestAndChan` 構造体に `callerGone <-chan struct{}` という新しいフィールドが追加されました。
    *   `callerGone` チャネルは、`roundTrip` ゴルーチンが終了する際に閉じられます。`readLoop` ゴルーチンは、アンバッファリングチャネルへの送信を行う `select` 文の中で `<-rc.callerGone` も監視します。これにより、`roundTrip` が先に終了した場合でも `readLoop` がブロックされずに終了できるようになり、ゴルーチンリークが防止されます。

4.  **`readLoop` と `roundTrip` の `select` ロジックの簡素化**:
    *   `readLoop` 内でレスポンスを `rc.ch` に送信する際、以前はバッファリングされたチャネルとアンバッファリングされたチャネルの挙動の違いを考慮した複雑なロジックがありました。
    *   新しい実装では、`select` 文を使って `rc.ch <- responseAndError{res: resp}` または `<-rc.callerGone` のいずれかを待機する形に統一され、簡素化されました。これにより、チャネルの優先順位付けやリトライの必要がなくなりました。
    *   `roundTrip` 内の `WaitResponse` ループも簡素化され、`writeErrCh` からのエラー処理が直接的になり、以前のような `select` 内でのタイムアウトを伴うリトライロジックが削除されました。

5.  **`responseAndError` 構造体の簡素化**:
    *   以前の `responseAndError` は、`ch chan *Response` と `r *Response` の両方を持っており、`res()` メソッドでどちらを使うかを判断していました。
    *   変更後、`res *Response` のみを持つようになり、`ch` フィールドが削除されました。これは、`requestAndChan.ch` が直接 `responseAndError` を送受信するようになったため、`responseAndError` 内部でさらにチャネルを持つ必要がなくなったためです。これにより、構造体が簡素化され、意図が明確になりました。

これらの変更により、`net/http` クライアントのコネクション管理における並行処理のロジックがより明確になり、競合状態が減少し、全体的な堅牢性が向上しています。特に、`select` 文のランダムなスケジューリングに依存しない、より予測可能な挙動が実現されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`net/http` パッケージにおけるHTTPクライアントのコネクション管理、特に `Transport.roundTrip` と `persistConn.readLoop` という2つの主要なゴルーチン間の通信プロトコルを改善することにあります。

**問題点**:
以前の実装では、特にボディを持たないHTTPレスポンス（例: `HEAD` リクエストのレスポンス）を処理する際に問題が発生していました。`persistConn.readLoop` はレスポンスを読み取った後、コネクションをアイドルプールに戻すために `putIdleConn` を呼び出していました。しかし、`putIdleConn` はコネクションをプールに戻すと同時に、特定の条件下でコネクションを閉じてしまう可能性がありました。
このとき、`Transport.roundTrip` ゴルーチンは、レスポンスを受け取るためのチャネルと、コネクションが閉じられたことを通知する `pc.closech` の両方から読み取り可能になる可能性がありました。Goの `select` 文は、複数のチャネルが同時に準備できた場合、どのチャネルを選択するかをランダムに決定することがあります（特に `race builder` 環境で顕著）。このランダム性により、`roundTrip` が意図しないチャネル（例えば `pc.closech`）を先に選択してしまい、レスポンスの処理が正しく行われない、あるいはデッドロックに陥るなどの不安定な挙動を引き起こしていました。

**解決策**:

1.  **`putIdleConn` の分割**:
    *   `putIdleConn` の役割が曖昧であったため、これを `tryPutIdleConn` と `putOrCloseIdleConn` に分割しました。
    *   `tryPutIdleConn` は、コネクションをアイドルプールに登録できるかどうかを試み、成功すれば `nil` を、失敗すれば具体的なエラーを返します。この関数はコネクションを閉じません。
    *   `putOrCloseIdleConn` は `tryPutIdleConn` を呼び出し、もしプールへの登録に失敗した場合は、そのエラーを理由としてコネクションを閉じます。
    *   これにより、コネクションをプールに戻すことと、コネクションを閉じることのロジックが明確に分離され、各呼び出し元は自身の意図に合った関数を呼び出すことができるようになりました。特に `readLoop` は、コネクションをプールに戻すことだけを試み、その結果に基づいて閉じるかどうかを判断できるようになります。

2.  **アンバッファリングチャネルと `callerGone` の導入**:
    *   `roundTrip` と `readLoop` 間の主要な通信チャネル (`requestAndChan.ch`) をアンバッファリングチャネルに変更しました。アンバッファリングチャネルは、送信側と受信側が同時に準備できていないとブロックされるため、より厳密な同期を保証します。
    *   しかし、アンバッファリングチャネルはゴルーチンリークのリスクも伴います。例えば、`readLoop` がレスポンスを送信しようとしている間に `roundTrip` が何らかの理由で先に終了してしまった場合、`readLoop` はチャネル送信で永遠にブロックされ、リークしてしまいます。
    *   この問題を解決するために、`requestAndChan` に `callerGone <-chan struct{}` という新しいチャネルが追加されました。
    *   `roundTrip` ゴルーチンは、自身の開始時にこの `callerGone` チャネルを作成し、終了時にこれを閉じます。
    *   `readLoop` ゴルーチンは、アンバッファリングチャネルへの送信を行う `select` 文の中で、`rc.ch <- ...` と同時に `<-rc.callerGone` も監視します。
    *   これにより、`roundTrip` が先に終了して `callerGone` が閉じられた場合、`readLoop` はチャネル送信を諦めて安全に終了できるようになり、ゴルーチンリークが防止されます。

3.  **`persistConn.closed` の `error` 型への変更**:
    *   コネクションが閉じられた理由を `bool` ではなく `error` として記録することで、デバッグ時の情報が格段に増えました。これにより、なぜコネクションが閉じられたのか、その根本原因を特定しやすくなります。

これらの変更により、`net/http` クライアントは、特に高負荷時や競合状態が発生しやすいシナリオにおいて、より安定して動作するようになりました。`select` 文のランダムなスケジューリングに起因する不安定性が解消され、コネクションのライフサイクル管理がより予測可能で堅牢なものになっています。

## 元コミット内容

Goランタイムにおいて、`buildmode=c-shared` でビルドされた際に `main` 関数が実行されないようにする変更です。

## 変更の背景

Go言語は、`go build` コマンドの `-buildmode` オプションを使用することで、様々な形式のバイナリを生成できます。その中でも `c-archive` と `c-shared` は、GoのコードをC言語など他の言語から利用可能なライブラリとしてビルドするためのモードです。

*   **`buildmode=c-archive`**: 静的ライブラリ（.aファイル）を生成します。このライブラリは、C/C++プロジェクトにリンクされ、Goの関数を呼び出すことができます。
*   **`buildmode=c-shared`**: 共有ライブラリ（.soファイルや.dylibファイルなど）を生成します。これは動的にロードされ、Goの関数をエクスポートして他の言語から利用できるようにします。

通常のGoプログラムでは、`main` パッケージの `main` 関数がプログラムのエントリポイントとして実行されます。しかし、Goのコードがライブラリとして利用される場合、そのライブラリをロードする側のC/C++プログラムなどが独自のエントリポイントを持つため、Go側の `main` 関数が自動的に実行されることは望ましくありません。Goの `main` 関数が実行されてしまうと、予期せぬ初期化処理や、プログラムの終了処理が行われ、ライブラリとして利用する側のアプリケーションの動作に悪影響を与える可能性があります。

このコミット以前は、`buildmode=c-archive` の場合は `main` 関数が実行されないように制御されていましたが、`buildmode=c-shared` の場合はその制御が不十分でした。そのため、`c-shared` でビルドされたGoライブラリがロードされた際に、Goランタイムの `main` 関数が意図せず実行されてしまう可能性がありました。この変更は、`c-shared` ビルドモードにおいても `main` 関数が実行されないようにすることで、Goライブラリがより安全かつ予測可能な形で他の言語から利用できるようにすることを目的としています。

## 前提知識の解説

### Goのビルドモード (`-buildmode`)

`go build` コマンドには `-buildmode` というオプションがあり、Goプログラムのビルド方法を制御します。主要なビルドモードには以下のようなものがあります。

*   **`exe` (デフォルト)**: 実行可能バイナリを生成します。通常のGoアプリケーションはこのモードでビルドされます。
*   **`archive`**: 静的ライブラリ（.a）を生成します。Goパッケージを他のGoプログラムからリンクして利用する場合に用いられます。
*   **`c-archive`**: C言語の静的ライブラリ（.a）を生成します。Goの関数をC/C++プログラムから呼び出すために使用されます。Goのランタイムと必要なGoコードがすべて含まれます。
*   **`c-shared`**: C言語の共有ライブラリ（.so, .dylib, .dll）を生成します。Goの関数をC/C++プログラムから動的にロードして呼び出すために使用されます。
*   **`shared`**: Goの共有ライブラリを生成します。他のGoプログラムから動的にロードして利用する場合に用いられます。

### Goランタイムの `main` 関数 (`runtime.main`)

Goプログラムのエントリポイントは、ユーザーが記述する `main` パッケージの `main` 関数ですが、その裏側ではGoランタイムが提供する `runtime.main` 関数が実際のプログラムの起動処理を担っています。`runtime.main` は、Goランタイムの初期化、ガベージコレクションの有効化、スケジューラの起動、そして最終的にユーザーの `main` 関数（`main.main`）の呼び出しなど、Goプログラムが実行されるために必要な様々な準備を行います。

### `systemstack` と `newextram`

Goランタイムは、ユーザーコードが実行されるゴルーチンのスタックとは別に、ランタイム内部の重要な処理を実行するための特別なスタック（システムスタック）を持っています。`systemstack` は、現在のゴルーチンの実行を一時停止し、指定された関数をシステムスタック上で実行するためのGoランタイム関数です。

`newextram` は、Goランタイムが新しいOSスレッド（M: Machine）を作成し、そのスレッド上でGoスケジューラがゴルーチンを実行できるようにするための関数です。Goランタイムは、必要に応じてOSスレッドを動的に作成・破棄することで、ゴルーチンの並行実行を効率的に管理します。

コミット前のコードでは、`islibrary` (Goコードがライブラリとしてビルドされている場合) に `main_main()` が永遠にブロックすることを想定して `newextram` を呼び出し、新しいMを割り当てる処理がありました。これは、ライブラリとして利用されるGoプログラムが、自身の `main` 関数でブロックするような設計になっている場合に、他のGoルーチンが実行できるようにするための考慮だったと考えられます。しかし、`c-shared` の場合は `main` 関数自体が実行されるべきではないため、この処理は不要かつ問題となる可能性がありました。

### `isarchive` と `islibrary`

Goランタイム内部では、現在のビルドモードや実行環境に応じて、特定のフラグが設定されます。
*   `isarchive`: プログラムが `c-archive` モードでビルドされた場合に真となるフラグです。
*   `islibrary`: プログラムがライブラリとしてビルドされた場合に真となるフラグです。これは `c-archive` や `c-shared` の場合に真となります。

これらのフラグは、ランタイムが自身の動作を調整するために使用されます。

## 技術的詳細

Goランタイムの `src/runtime/proc.go` ファイルには、Goプログラムの起動と終了に関するコアロジックが含まれています。特に `func main()` は、Goランタイムが初期化された後に最初に実行されるGo関数であり、ユーザーが記述する `main.main()` 関数を呼び出す責任を負っています。

このコミットの核心は、`c-shared` ビルドモードにおける `runtime.main` の挙動の修正です。
従来のGoランタイムでは、`buildmode=c-archive` でビルドされたGoプログラムは、その `main` 関数が実行されないように明示的に制御されていました。これは、`c-archive` が静的ライブラリであり、Goの `main` 関数が実行されると、ライブラリをリンクする側のC/C++アプリケーションの制御フローを妨げる可能性があるためです。

しかし、`buildmode=c-shared` の場合、Goのコードは動的にロードされる共有ライブラリとなります。この場合も、ライブラリをロードする側のアプリケーションが独自のエントリポイントを持つため、Goの `main` 関数が自動的に実行されることは望ましくありません。もし `c-shared` ライブラリがロードされた際に `runtime.main` が実行されてしまうと、Goランタイムが自身のスケジューラを起動したり、ガベージコレクションを開始したり、さらにはユーザーが定義した `main.main` 関数を呼び出そうとしたりする可能性があります。これは、ライブラリとして利用されるGoコードの意図しない副作用を引き起こし、ホストアプリケーションのクラッシュや予期せぬ動作につながる恐れがあります。

このコミットでは、`c-shared` ビルドモードの場合も `c-archive` と同様に `runtime.main` がユーザーの `main.main` を呼び出さないように変更されました。具体的には、`isarchive` フラグだけでなく、`islibrary` フラグ（`c-shared` の場合も真となる）も考慮して、`main_main()` の呼び出しをスキップするように修正されています。

また、コミット前のコードには、`islibrary` の場合に `main_main()` が永遠にブロックすることを想定して `systemstack(newextram)` を呼び出す部分がありました。これは、ライブラリとして利用されるGoプログラムが、自身の `main` 関数でブロックするような設計になっている場合に、他のGoルーチンが実行できるようにするための考慮だったと考えられます。しかし、`c-shared` の場合は `main` 関数自体が実行されるべきではないため、この処理は不要であり、削除されました。これにより、`c-shared` ライブラリのロード時に不要なOSスレッドの作成やランタイムの初期化が抑制され、よりクリーンなライブラリとしての挙動が実現されます。

## コアとなるコードの解説

このコミットでは、`src/runtime/proc.go` ファイル内の `func main()` 関数が変更されています。

1.  **`systemstack(newextram)` の削除**:
    変更前のコードでは、以下の部分がありました。
    ```go
    if islibrary {
        // Allocate new M as main_main() is expected to block forever.
        systemstack(newextram)
    }
    ```
    このコードは、Goプログラムがライブラリとしてビルドされ (`islibrary` が真)、かつ `main_main()` が無限にブロックする（つまり、Goランタイムが常にアクティブな状態を維持する必要がある）と想定される場合に、新しいOSスレッド（M）を割り当てていました。しかし、`c-shared` のような共有ライブラリの場合、Goの `main` 関数自体が実行されるべきではないため、この `newextram` の呼び出しは不要であり、むしろ意図しないリソースの消費や挙動を引き起こす可能性がありました。このコミットでは、このブロックが完全に削除されました。これにより、`c-shared` ライブラリがロードされた際に、Goランタイムが不要なOSスレッドを起動するのを防ぎます。

2.  **`isarchive` 条件の拡張**:
    変更前のコードでは、`main_main()` の呼び出しをスキップする条件が `isarchive` のみでした。
    ```go
    if isarchive {
        // A program compiled with -buildmode=c-archive has a main,
        // but it is not executed.
        return
    }
    main_main()
    ```
    このコミットでは、この条件が `isarchive || islibrary` に拡張されました。
    ```go
    if isarchive || islibrary {
        // A program compiled with -buildmode=c-archive or c-shared
        // has a main, but it is not executed.
        return
    }
    main_main()
    ```
    `islibrary` フラグは、Goプログラムが `c-archive` または `c-shared` のいずれかのモードでライブラリとしてビルドされた場合に真となります。この変更により、`c-shared` でビルドされたGoライブラリがロードされた際にも、`runtime.main` 関数がユーザーの `main.main()` 関数を呼び出すことなく、すぐに `return` するようになります。これにより、Goライブラリが他の言語から利用される際に、Go側の `main` 関数が意図せず実行されることによる問題を回避できます。コメントも「`c-archive` または `c-shared` でコンパイルされたプログラムは `main` を持つが、それは実行されない」と更新され、変更の意図が明確に示されています。

これらの変更により、Goの共有ライブラリがより適切に他の言語のアプリケーションに組み込まれ、Goランタイムの挙動が予測可能になります。

しかし、`buildmode=c-shared` の場合、Goのコードは動的にロードされる共有ライブラリとなります。この場合も、ライブラリをロードする側のアプリケーションが独自のエントリポイントを持つため、Goの `main` 関数が自動的に実行されることは望ましくありません。もし `c-shared` ライブラリがロードされた際に `runtime.main` が実行されてしまうと、Goランタイムが自身のスケジューラを起動したり、ガベージコレクションを開始したり、さらにはユーザーが定義した `main.main` 関数を呼び出そうとしたりする可能性があります。これは、ライブラリとして利用されるGoコードの意図しない副作用を引き起こし、ホストアプリケーションのクラッシュや予期せぬ動作につながる恐れがあります。

このコミットでは、`c-shared` ビルドモードの場合も `c-archive` と同様に `runtime.main` がユーザーの `main.main` を呼び出さないように変更されました。具体的には、`isarchive` フラグだけでなく、`islibrary` フラグ（`c-shared` の場合も真となる）も考慮して、`main_main()` の呼び出しをスキップするように修正されています。

また、コミット前のコードには、`islibrary` の場合に `main_main()` が永遠にブロックすることを想定して `systemstack(newextram)` を呼び出す部分がありました。これは、ライブラリとして利用されるGoプログラムが、自身の `main` 関数でブロックするような設計になっている場合に、他のGoルーチンが実行できるようにするための考慮だったと考えられます。しかし、`c-shared` の場合は `main` 関数自体が実行されるべきではないため、この処理は不要であり、削除されました。これにより、`c-shared` ライブラリのロード時に不要なOSスレッドの作成やランタイムの初期化が抑制され、よりクリーンなライブラリとしての挙動が実現されます。

## コアとなるコードの解説

このコミットでは、`src/runtime/proc.go` ファイル内の `func main()` 関数が変更されています。

1.  **`systemstack(newextram)` の削除**:
    変更前のコードでは、以下の部分がありました。
    ```go
    if islibrary {
        // Allocate new M as main_main() is expected to block forever.
        systemstack(newextram)
    }
    ```
    このコードは、Goプログラムがライブラリとしてビルドされ (`islibrary` が真)、かつ `main_main()` が無限にブロックする（つまり、Goランタイムが常にアクティブな状態を維持する必要がある）と想定される場合に、新しいOSスレッド（M）を割り当てていました。しかし、`c-shared` のような共有ライブラリの場合、Goの `main` 関数自体が実行されるべきではないため、この `newextram` の呼び出しは不要であり、むしろ意図しないリソースの消費や挙動を引き起こす可能性がありました。このコミットでは、このブロックが完全に削除されました。これにより、`c-shared` ライブラリがロードされた際に、Goランタイムが不要なOSスレッドを起動するのを防ぎます。

2.  **`isarchive` 条件の拡張**:
    変更前のコードでは、`main_main()` の呼び出しをスキップする条件が `isarchive` のみでした。
    ```go
    if isarchive {
        // A program compiled with -buildmode=c-archive has a main,
        // but it is not executed.
        return
    }
    main_main()
    ```
    このコミットでは、この条件が `isarchive || islibrary` に拡張されました。
    ```go
    if isarchive || islibrary {
        // A program compiled with -buildmode=c-archive or c-shared
        // has a main, but it is not executed.
        return
    }
    main_main()
    ```
    `islibrary` フラグは、Goプログラムが `c-archive` または `c-shared` のいずれかのモードでライブラリとしてビルドされた場合に真となります。この変更により、`c-shared` でビルドされたGoライブラリがロードされた際にも、`runtime.main` 関数がユーザーの `main.main()` 関数を呼び出すことなく、すぐに `return` するようになります。これにより、Goライブラリが他の言語から利用される際に、Go側の `main` 関数が意図せず実行されることによる問題を回避できます。コメントも「`c-archive` または `c-shared` でコンパイルされたプログラムは `main` を持つが、それは実行されない」と更新され、変更の意図が明確に示されています。

これらの変更により、Goの共有ライブラリがより適切に他の言語のアプリケーションに組み込まれ、Goランタイムの挙動が予測可能になります。

# [インデックス 20858] ファイルの概要

このコミットは、Go言語の標準ライブラリである `regexp` パッケージ内のテストファイル `src/regexp/all_test.go` における `TestOnePassCutoff` 関数の修正に関するものです。以前のバージョンでは、特定の複雑な正規表現がスタックオーバーフローを引き起こす可能性があり、その問題（issue 7608）が修正された後も、正規表現エンジンが「複雑すぎる」パターンを適切に拒否することを確認するためのテストの調整が行われました。この変更は、正規表現のコンパイルが単一パスで処理できない場合に、その正規表現が正しく「単一パスではない」と識別されることを検証することを目的としています。

## 元コミット内容

このコミットの元々の内容は、`regexp` パッケージの `TestOnePassCutoff` テストを修正することです。以前は、このテストはスタックオーバーフローの問題（issue 7608）が修正される前に発生していたスタックオーバーフローを検証していましたが、その問題が解決されたため、テストの目的を変更しました。新しいテストは、複雑すぎる正規表現が正しく拒否されることを検証します。これは、以前の変更セット (CL 162770043) の代替として行われました。

## 変更の背景

この変更の背景には、Go言語の `regexp` パッケージが抱えていた正規表現の「破滅的バックトラッキング（catastrophic backtracking）」問題への対処があります。一般的な正規表現エンジン、特にNFA（非決定性有限オートマトン）ベースの実装では、`a+a+b` のようなパターンに `aaaaab` のような文字列をマッチさせようとすると、指数関数的な時間でバックトラッキングが発生し、処理が極端に遅くなったり、スタックオーバーフローを引き起こしたりする可能性があります。

Goの `regexp` パッケージは、GoogleのRE2ライブラリにインスパイアされており、DFA（決定性有限オートマトン）ベースのアプローチを採用しています。DFAベースのエンジンは、線形時間でマッチングを行うため、破滅的バックトラッキングの問題を根本的に回避できます。しかし、一部の正規表現パターン（特に、繰り返しとオプションの組み合わせが複雑なもの）は、DFAにコンパイルする際に非常に大きな状態空間を生成する可能性があり、コンパイル自体が困難になることがあります。

`TestOnePassCutoff` テストは、元々、issue 7608で報告されたスタックオーバーフローの問題が修正される前に、その問題が発生することを確認するために存在していました。この問題は、特定の正規表現のコンパイルがGoランタイムのスタックを使い果たしてしまうというものでした。コミットメッセージにあるように、この「スタックの吹き飛び（stack blowout）」はもはや発生しないようになりました。これは、Goの正規表現エンジンが、コンパイル時に過度に複雑な正規表現を検出し、それを「単一パスで処理できない」と判断して拒否するメカニズムを導入したためと考えられます。

このコミットは、その新しいメカニズムが正しく機能し、複雑な正規表現が適切に「拒否」されることを検証するために、テストのロジックを更新しています。つまり、スタックオーバーフローが起きなくなった今、テストは「複雑な正規表現が、期待通りに単一パスで処理できないと判断されるか」という点に焦点を移したのです。

## 前提知識の解説

### Go言語の `regexp` パッケージ

Go言語の `regexp` パッケージは、正規表現を扱うための標準ライブラリです。このパッケージは、GoogleのRE2ライブラリに基づいています。RE2は、従来の正規表現エンジンが抱える「破滅的バックトラッキング」の問題を解決するために設計されており、すべての正規表現マッチングを文字列の長さに線形な時間で実行することを保証します。これは、NFA（非決定性有限オートマトン）ベースのバックトラッキングエンジンとは異なり、DFA（決定性有限オートマトン）ベースのアプローチを採用しているためです。

### 正規表現のバックトラッキングと破滅的バックトラッキング

*   **バックトラッキング**: 多くの正規表現エンジン（特にPerl、Python、Javaなどで使われるNFAベースのもの）は、パターンマッチングの際に、ある部分がマッチしなかった場合に、以前にマッチした部分を「巻き戻して」別の可能性を試す「バックトラッキング」というメカニズムを使用します。
*   **破滅的バックトラッキング (Catastrophic Backtracking)**: 特定の正規表現パターン（例: `(a+)+b` や `(a|aa)+b`）と特定の入力文字列（例: `aaaaaaaaab`）の組み合わせにおいて、バックトラッキングの組み合わせが指数関数的に増加し、マッチング処理に膨大な時間がかかったり、スタックオーバーフローを引き起こしたりする現象を指します。これは、正規表現の脆弱性の一つとして知られています（ReDoS: Regular Expression Denial of Service）。

### `regexp/syntax` パッケージ

`regexp/syntax` パッケージは、`regexp` パッケージの内部で使われる低レベルの正規表現構文解析およびコンパイルのためのパッケージです。正規表現文字列を抽象構文木（AST）にパースし、それを正規表現の内部表現（プログラム）にコンパイルする機能を提供します。このパッケージは、正規表現の構文解析と最適化の段階を担っており、`regexp` パッケージがDFAベースのマッチングを効率的に行えるようにするための基盤を提供します。

### `TestOnePassCutoff` の目的

`TestOnePassCutoff` は、正規表現エンジンが特定の複雑なパターンを「単一パス（one-pass）」で処理できるかどうかをテストするためのものです。Goの `regexp` パッケージは、可能な限り効率的なマッチングを行うために、正規表現を「単一パス」で処理できるかどうかを判断しようとします。単一パスで処理できる正規表現は、入力文字列を一度スキャンするだけでマッチングが完了するため、非常に高速です。しかし、すべての正規表現が単一パスで処理できるわけではありません。特に、後方参照（backreferences）や一部の複雑な繰り返しパターンは、単一パスでの処理が困難または不可能です。このテストは、エンジンが単一パスで処理できない正規表現を正しく識別できることを確認します。

## 技術的詳細

このコミットは、`src/regexp/all_test.go` 内の `TestOnePassCutoff` 関数を変更しています。

**変更前のコード:**

```go
// This ran out of stack before issue 7608 was fixed.
func TestOnePassCutoff(t *testing.T) {
	if testing.Short() {
		t.Skip("Skipping in short mode")
	}
	MustCompile(`^(?:x{1,1000}){1,1000}$`)
}
```

変更前は、`MustCompile` 関数を使って `^(?:x{1,1000}){1,1000}$` という正規表現をコンパイルしていました。この正規表現は、`x` が1回から1000回繰り返されるグループが、さらに1回から1000回繰り返されるという非常に複雑なパターンです。コメントにあるように、issue 7608が修正される前は、この正規表現のコンパイルがスタックオーバーフローを引き起こしていました。`MustCompile` は、コンパイルに失敗するとパニックを起こすため、テストはスタックオーバーフローが発生しないことを暗黙的に期待していました。

**変更後のコード:**

```go
// Check that one-pass cutoff does trigger.
func TestOnePassCutoff(t *testing.T) {
	re, err := syntax.Parse(`^x{1,1000}y{1,1000}$`, syntax.Perl)
	if err != nil {
		t.Fatalf("parse: %v", err)
	}
	p, err := syntax.Compile(re.Simplify())
	if err != nil {
		t.Fatalf("compile: %v", err)
	}
	if compileOnePass(p) != notOnePass {
		t.Fatalf("makeOnePass succeeded; wanted notOnePass")
	}
}
```

変更後のテストは、`regexp/syntax` パッケージを直接使用して、より詳細な検証を行っています。

1.  `re, err := syntax.Parse(`^x{1,1000}y{1,1000}$`, syntax.Perl)`:
    *   `syntax.Parse` 関数は、正規表現文字列を解析し、`*syntax.Regexp` 型の抽象構文木（AST）を返します。
    *   パターンは `^x{1,1000}y{1,1000}$` です。これは、`x` が1回から1000回、その後に `y` が1回から1000回続くというパターンです。このパターンは、以前のテストで使用されていた `^(?:x{1,1000}){1,1000}$` よりも単純に見えますが、`regexp` エンジンが単一パスで処理するには依然として複雑なケースとなり得ます。
    *   `syntax.Perl` フラグは、Perl互換の正規表現構文を使用することを指定します。

2.  `p, err := syntax.Compile(re.Simplify())`:
    *   `re.Simplify()` は、正規表現のASTを簡素化し、最適化を行います。これにより、コンパイルがより効率的になります。
    *   `syntax.Compile` 関数は、簡素化されたASTを正規表現の内部表現（プログラム）にコンパイルし、`*syntax.Prog` 型のオブジェクトを返します。このプログラムは、DFAベースのマッチングエンジンが実行する命令のシーケンスです。

3.  `if compileOnePass(p) != notOnePass { ... }`:
    *   `compileOnePass(p)` は、コンパイルされた正規表現プログラム `p` が単一パスで処理可能かどうかを内部的に判断する関数です。この関数は、正規表現の特性に基づいて、単一パスで処理できる場合は対応する内部表現を返し、できない場合は `notOnePass` という特別な値を返します。
    *   `notOnePass` は、正規表現が単一パスで処理できないことを示す定数です。
    *   このテストは、`^x{1,1000}y{1,1000}$` という正規表現が、Goの `regexp` エンジンによって「単一パスではない」と正しく判断されることを検証しています。もし `compileOnePass` が `notOnePass` 以外の値を返した場合（つまり、単一パスで処理できると誤って判断した場合）、テストは失敗します。

この変更により、テストはスタックオーバーフローの発生有無ではなく、正規表現エンジンが複雑なパターンを適切に「単一パスではない」と識別する能力を直接的に検証するようになりました。これは、正規表現の安全性とパフォーマンスを維持するための重要な側面です。

## コアとなるコードの解説

変更後の `TestOnePassCutoff` 関数のコアとなるコードは以下の通りです。

```go
	re, err := syntax.Parse(`^x{1,1000}y{1,1000}$`, syntax.Perl)
	if err != nil {
		t.Fatalf("parse: %v", err)
	}
	p, err := syntax.Compile(re.Simplify())
	if err != nil {
		t.Fatalf("compile: %v", err)
	}
	if compileOnePass(p) != notOnePass {
		t.Fatalf("makeOnePass succeeded; wanted notOnePass")
	}
```

1.  `re, err := syntax.Parse(`^x{1,1000}y{1,1000}$`, syntax.Perl)`:
    *   この行は、正規表現文字列 `^x{1,1000}y{1,1000}$` を解析します。
    *   `syntax.Parse` は、正規表現の文字列表現を、Goの `regexp` パッケージが内部で扱う抽象構文木（AST）である `*syntax.Regexp` 型のオブジェクトに変換します。
    *   `syntax.Perl` は、Perl互換の正規表現構文規則（例: `\d` が数字にマッチするなど）を適用するようにパーサーに指示するフラグです。
    *   エラーが発生した場合（例: 不正な正規表現構文）、`t.Fatalf` を呼び出してテストを失敗させます。

2.  `p, err := syntax.Compile(re.Simplify())`:
    *   `re.Simplify()` は、パースされた正規表現ASTを簡素化し、最適化します。これにより、冗長な部分が削除されたり、より効率的な表現に変換されたりすることがあります。
    *   `syntax.Compile` は、簡素化されたASTを、正規表現エンジンが実行可能な内部プログラム（`*syntax.Prog` 型）にコンパイルします。このプログラムは、DFAベースのマッチングロジックを表現する命令のシーケンスです。
    *   ここでも、コンパイル中にエラーが発生した場合はテストを失敗させます。

3.  `if compileOnePass(p) != notOnePass { t.Fatalf("makeOnePass succeeded; wanted notOnePass") }`:
    *   この行がテストの核心です。
    *   `compileOnePass(p)` は、コンパイルされた正規表現プログラム `p` が「単一パス」でマッチング可能かどうかを判断する内部関数です。単一パスでマッチングできる正規表現は、入力文字列を一度スキャンするだけで結果が得られるため、非常に効率的です。
    *   `notOnePass` は、正規表現が単一パスで処理できない場合に `compileOnePass` が返す特別な値です。
    *   このテストは、`^x{1,1000}y{1,1000}$` という正規表現が、Goの正規表現エンジンによって「単一パスではない」と正しく判断されることを期待しています。もし `compileOnePass` が `notOnePass` 以外の値を返した場合（つまり、単一パスで処理できると誤って判断した場合）、それはエンジンの判断ロジックに問題があることを意味するため、テストは失敗します。

この一連の処理により、Goの `regexp` パッケージが、特定の複雑な正規表現パターンに対して、スタックオーバーフローを引き起こすことなく、かつ、その複雑性を正しく認識して「単一パスではない」と判断できることを検証しています。

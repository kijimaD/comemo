## 元コミット内容

`cmd/internal/ld, cmd/6l: external linking for windows/amd64`

このコミットは、GoのリンカがWindowsのAMD64アーキテクチャで外部リンキングを行う際の挙動を修正・改善することを目的としています。

## 変更の背景

Go言語は、その初期からクロスコンパイルと自己完結型バイナリの生成に強みを持っていました。しかし、Cgo（GoからCコードを呼び出す機能）を使用する場合や、既存のC/C++ライブラリ（特にWindowsのDLL）とリンクする必要がある場合、Goの内部リンカだけでは対応しきれない複雑なリンキング要件が発生します。このような場合、Goは外部のCリンカ（WindowsではMicrosoft Visual C++リンカやMinGWの`ld`など）を呼び出して最終的な実行ファイルを生成する「外部リンキング」を行います。

2015年頃のGoのWindowsサポートは成熟しつつありましたが、特にAMD64アーキテクチャにおける外部リンキングは、Windows特有のPE/COFF（Portable Executable/Common Object File Format）形式のバイナリ構造とリロケーションメカニズムに対応する必要がありました。このコミットは、`R_CALL`や`R_PCREL`といったリロケーションタイプがWindows環境で正しく処理されるように、Goのリンカの挙動を調整することを目的としています。具体的には、WindowsのPE/COFF形式におけるリロケーションの計算方法や、外部シンボルの命名規則（例：`_`プレフィックスや`@argsize`デコレーション）の違いに対応するための修正が含まれています。これにより、Cgoを利用したGoプログラムがWindows/AMD64環境でより安定して外部ライブラリとリンクできるようになります。

## 前提知識の解説

*   **外部リンキング (External Linking)**: Goプログラムが、Goのツールチェインに含まれる内部リンカではなく、システムにインストールされているC/C++リンカ（例: `gcc`や`link.exe`）を使用して最終的な実行ファイルを生成するプロセス。Cgoを使用する場合や、特定のシステムライブラリとリンクする場合に必要となります。
*   **PE/COFF (Portable Executable/Common Object File Format)**: Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトファイル、DLL（ダイナミックリンクライブラリ）の標準ファイル形式。LinuxのELFやmacOSのMach-Oに相当します。
*   **リロケーション (Relocation)**: リンカがプログラム内のアドレス参照を修正するプロセス。コンパイル時には最終的なメモリ上のアドレスが不明なため、相対アドレスやシンボル名で参照が記述され、リンカがロード時のアドレスに基づいてこれらの参照を実際の絶対アドレスに「再配置」します。
*   **リロケーションタイプ (Relocation Types)**: リロケーションの具体的な種類を示す定数。
    *   `ld.R_CALL`: 関数呼び出しのリロケーション。
    *   `ld.R_PCREL`: プログラムカウンタ相対のリロケーション。命令ポインタからの相対オフセットでアドレスを指定します。WindowsのPE/COFFでは、`IMAGE_REL_AMD64_REL32`などがこれに該当し、リロケーション対象のアドレスの「次」の命令からの相対オフセットで計算されるという特性があります。
    *   `ld.R_ADDR`: 絶対アドレスのリロケーション。
*   **PLT (Procedure Linkage Table)**: 動的リンクされた共有ライブラリ内の関数を呼び出す際に使用されるテーブル。通常、ELF（Linux）やMach-O（macOS）で使われますが、Windowsのインポートアドレステーブル（IAT）も同様の役割を果たします。このコミットでは、Windows環境ではPLTの処理が不要になるケースが示唆されています。
*   **Goリンカ (`cmd/ld`, `cmd/6l`)**: Goのビルドツールチェインの一部で、Goのソースコードから生成されたオブジェクトファイルを結合し、実行可能ファイルを生成するプログラム。`cmd/6l`はAMD64アーキテクチャ向けのリンカです。`cmd/internal/ld`はリンカの共通ロジックを定義する内部パッケージです。
*   **Windows/AMD64**: Windowsオペレーティングシステム上で動作するAMD64（x86-64）アーキテクチャ。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのGoの機能。Cgoを使用すると、GoのビルドプロセスはCコンパイラとリンカを呼び出す必要があり、外部リンキングが頻繁に利用されます。
*   **シンボルデコレーション (Symbol Decoration)**: WindowsのC/C++コンパイラやリンカが、関数名や変数名に特定のプレフィックスやサフィックス（例: `_`や`@argsize`）を追加する慣習。これは、呼び出し規約（calling convention）や名前の衝突を避けるために行われます。

## 技術的詳細

このコミットの主要な技術的変更点は、GoのリンカがWindows/AMD64環境でPE/COFF形式のリロケーションを正確に処理するためのロジックを追加・修正したことです。

1.  **`pereloc1`関数の導入**:
    *   `src/cmd/6l/asm.go`に`pereloc1`という新しい関数が追加されました。この関数は、PE/COFF形式のリロケーションエントリを生成する役割を担います。
    *   `pereloc1`は、リロケーションの対象となるシンボル（`rs.Dynid`）と、リロケーションのオフセット（`sectoff`）を受け取ります。
    *   `r.Type`（リロケーションタイプ）に応じて、Windows特有のリロケーションタイプ（例: `ld.IMAGE_REL_AMD64_ADDR64`, `ld.IMAGE_REL_AMD64_ADDR32`, `ld.IMAGE_REL_AMD64_REL32`）を決定し、PE/COFFのリロケーションテーブルに書き込みます。
    *   特に`R_CALL`や`R_PCREL`の場合、`IMAGE_REL_AMD64_REL32`が使用されます。これは、AMD64アーキテクチャにおける32ビット相対アドレスのリロケーションです。

2.  **`adddynrel`のWindows対応**:
    *   `src/cmd/6l/asm.go`の`adddynrel`関数は、動的リロケーションを追加する役割を担っています。
    *   以前は`R_CALL`や`R_PCREL`タイプのリロケーションに対しては、ELFやMach-O向けにPLT（Procedure Linkage Table）シンボルを追加していましたが、このコミットにより`ld.HEADTYPE == ld.Hwindows`の場合には特別な処理を行わないようになりました。これは、WindowsのPE/COFF形式ではリロケーションが`pereloc1`で直接処理されるため、PLTのような中間テーブルが不要になることを意味します。

3.  **`relocsym`におけるPCRELのWindows/AMD64対応**:
    *   `src/cmd/internal/ld/data.go`の`relocsym`関数は、シンボルに対するリロケーションを処理します。
    *   `R_PCREL`タイプのリロケーションについて、`HEADTYPE == Hwindows && Thearch.Thechar == '6'`（Windows/AMD64）の場合に特別なオフセット調整が導入されました。
    *   PE/COFFのPC32リロケーションは、リロケーション対象のバイトの「後」のアドレスをベースとして使用します。そのため、`r.Siz`（リロケーションのサイズ）をオフセットに加算して補償します。
    *   さらに、GNU `ld`が`.text`セクションの`VirtualAddress`をリロケーションアドレスに常に加算するという挙動を補償するために、`s.Sect.(*Section).Vaddr - PEBASE`を減算する調整も行われています。これにより、Goのリンカが計算するアドレスと外部リンカが期待するアドレスの間の不一致が解消されます。

4.  **PE/COFFシンボル命名規則の調整**:
    *   `src/cmd/internal/ld/pe.go`では、Windows特有のシンボル命名規則に対応するための変更が行われました。
    *   `initdynimport`関数において、`Thearch.Thechar == '8'`（Windows/386）の場合にのみ、`@argsize`デコレーション（例: `_func@4`）を動的インポートシンボル名に追加するようになりました。これは、Windows/386の`stdcall`呼び出し規約に特有のものです。
    *   `addpesym`関数においても、`Thearch.Thechar == '8'`（Windows/386）の場合にのみ、外部リンキングされたシンボル（`Linkmode == LinkExternal`）に対して`_`プレフィックスを追加するようになりました。これは、WindowsのC/C++コンパイラがシンボルに`_`を付加する慣習に対応するためです。
    *   また、`SDATA`タイプのシンボル（通常は`.data`セクションに属する）が、`LinkExternal`モードで`.bss`セクションに誤って配置されないように、`s.Type != SDATA`という条件が追加されました。これにより、`runtime.edata`のようなシンボルが正しく`.data`セクションにマッピングされるようになります。

これらの変更により、GoのリンカはWindows/AMD64環境で外部リンキングを行う際に、PE/COFF形式のバイナリ仕様と外部リンカの挙動により正確に適合するようになり、Cgoを利用したプログラムの互換性と安定性が向上しました。

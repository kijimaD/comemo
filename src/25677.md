# [インデックス 25677] ファイルの概要

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal/gc` における構文解析器（パーサー）の挙動を改善するものです。具体的には、構文エラーが発生した際に、パーサーが少なくとも1つのトークンを消費するように修正することで、無限ループに陥る可能性があったバグ（Issue 13248）を解決します。これにより、エラー発生時のパーサーの堅牢性が向上し、より安定したコンパイル処理が実現されます。

## 変更の背景

この変更は、Goコンパイラの構文解析器が特定の構文エラーに遭遇した際に、無限ループに陥る可能性があったバグ（Go Issue 13248）を修正するために導入されました。

従来の `advance` 関数は、エラー発生時に指定された「停止リスト」内のトークンが見つかるまでトークンを消費し続ける設計でした。しかし、もし停止リストが空であるか、あるいは現在のトークンが既に停止リスト内のトークンと一致している場合、`advance` 関数はトークンを消費せずにすぐにリターンしてしまう可能性がありました。

この挙動は、特に `operand` 関数のような場所で問題を引き起こしました。`operand` 関数は、予期しないトークンに遭遇した場合に `syntax_error` を呼び出し、その後 `p.advance(';', '}')` を呼び出してエラー回復を試みます。しかし、もし `p.advance()` がトークンを消費せずに戻ってきてしまうと、パーサーは同じ不正なトークンを繰り返し処理しようとし、結果として無限ループに陥る可能性がありました。

Issue 13248は、このような状況下でコンパイラがハングアップする具体的なケースを報告しており、このコミットはその問題を根本的に解決することを目的としています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile/internal/gc`)

Go言語の公式コンパイラは、`go tool compile` コマンドを通じて利用されます。その内部実装は、`src/cmd/compile/internal/gc` パッケージに存在します。`gc` は "Go Compiler" の略であり、Go言語のソースコードを機械語に変換する主要な役割を担っています。このパッケージには、字句解析器（lexer）、構文解析器（parser）、型チェッカー（type checker）、中間表現（IR）の生成、最適化、コード生成など、コンパイラの主要なコンポーネントが含まれています。

### 構文解析器（Parser）

構文解析器は、字句解析器によって生成されたトークンのストリームを受け取り、Go言語の文法規則に従ってそれらが正しい構造を形成しているかを確認します。正しい場合は抽象構文木（AST）を構築し、不正な場合は構文エラーを報告します。Goコンパイラのパーサーは、再帰下降型パーサー（recursive-descent parser）の形式を採用しています。これは、文法の各非終端記号に対応する関数を持ち、それらの関数が再帰的に呼び出されることで入力トークンを解析していく方式です。

### `parser.go`

`src/cmd/compile/internal/gc/parser.go` は、Goコンパイラの構文解析器の実装が含まれるファイルです。このファイルには、Go言語の文法規則に対応する多くの解析関数（例: `parseFile`, `declaration`, `statement`, `expression` など）や、トークンを操作するためのヘルパー関数（例: `next`, `advance`）が定義されています。

### トークンと字句解析

ソースコードはまず字句解析器によって、意味を持つ最小単位である「トークン」に分割されます。例えば、`var x = 10` というコードは、`var` (キーワード)、`x` (識別子)、`=` (演算子)、`10` (整数リテラル) といったトークンに分解されます。パーサーはこれらのトークンを順に読み進めながら構文を解析します。

### `p.next()` と `p.tok`

Goコンパイラのパーサー (`parser` 構造体) は、現在のトークンを `p.tok` フィールドに保持しています。`p.next()` メソッドは、字句解析器から次のトークンを読み込み、`p.tok` を更新する役割を担います。これにより、パーサーは入力ストリームを前方に進めることができます。

### `EOF` (End Of File)

`EOF` は、入力ストリームの終端を示す特別なトークンです。パーサーが `EOF` に遭遇した場合、それ以上読み込むべきトークンがないことを意味します。

### `Yyerror()`

`Yyerror()` は、Goコンパイラが構文エラーを報告するために使用する関数です。エラーメッセージを受け取り、それを適切な形式で出力します。

### エラー回復 (Error Recovery)

構文エラーが発生した場合、パーサーは通常、それ以上解析を続けることができません。しかし、コンパイラはユーザーにできるだけ多くのエラーを報告するために、エラーが発生した場所から回復し、解析を続行しようと試みます。このプロセスをエラー回復と呼びます。`advance` 関数は、このエラー回復メカニズムの一部として機能します。特定の「停止リスト」内のトークン（例: セミコロンや閉じ括弧など、文の区切りとなるトークン）まで読み飛ばすことで、パーサーが同期を取り戻し、後続のコードの解析を試みることを可能にします。

## 技術的詳細

このコミットの核心は、`parser.go` 内の `advance` 関数と `operand` 関数の変更にあります。

### `advance` 関数の変更

**変更前:**

```go
// Advance consumes tokens until it finds one in the stoplist.
// If the stoplist is empty, the next token is consumed.
func (p *parser) advance(stoplist ...int32) {
	if len(stoplist) == 0 {
		p.next()
		return
	}

	for p.tok != EOF {
		for _, stop := range stoplist {
			if p.tok == stop {
				return // stop token found, return without consuming it
			}
		}
		p.next() // consume current token and move to next
	}
}
```

変更前の `advance` 関数には、以下の問題がありました。

1.  `stoplist` が空の場合、`p.next()` を一度だけ呼び出してすぐにリターンします。これは問題ありません。
2.  `stoplist` が空でない場合、`p.tok` が `EOF` でない限りループします。
3.  ループ内で、`p.tok` が `stoplist` 内のいずれかのトークンと一致した場合、**そのトークンを消費せずに** `return` します。

この「消費せずにリターンする」挙動が、特定のシナリオで無限ループの原因となっていました。もし `p.tok` が既に停止リスト内のトークンであり、かつそのトークンがエラー回復の文脈で消費されるべきであった場合、`advance` は何もせずに戻ってしまい、呼び出し元は同じ不正な状態のトークンを再度処理しようとします。

**変更後:**

```go
// Advance consumes tokens until it finds a token of the stoplist.
// If the stoplist is empty or no advance was necessary, the next
// token is consumed.
func (p *parser) advance(stoplist ...int32) {
	if len(stoplist) == 0 {
		p.next()
		return
	}

	for n := 0; p.tok != EOF; n++ { // n: number of tokens consumed so far
		for _, stop := range stoplist {
			if p.tok == stop {
				if n == 0 { // If no tokens were consumed before finding a stop token
					p.next() // consume at least one token
				}
				return
			}
		}
		p.next() // consume current token and move to next
	}
}
```

変更後の `advance` 関数では、`n` というカウンターが導入されています。このカウンターは、`advance` 関数が呼び出されてから何個のトークンを消費したかを追跡します。

最も重要な変更は、`p.tok == stop` となったブロック内に追加された `if n == 0 { p.next() }` です。
これにより、以下の挙動が保証されます。

*   **少なくとも1つのトークンを消費する**: `advance` 関数が呼び出された時点で `p.tok` が既に `stoplist` 内のトークンと一致していた場合（つまり `n == 0`）、`p.next()` が一度呼び出され、現在のトークンが消費されます。これにより、パーサーは必ず入力ストリームを前方に進めることが保証され、無限ループが回避されます。
*   `n > 0` の場合（つまり、既にいくつかのトークンを読み飛ばした後に停止トークンが見つかった場合）は、以前と同様に停止トークンを消費せずにリターンします。これは、停止トークンが次の有効な構文の開始点である可能性が高いため、そのトークンを次の解析ステップで利用できるようにするためです。

この変更により、`advance` 関数は、エラー回復の際に常にパーサーの状態を前進させることが保証され、無限ループの発生を防ぎます。

### `operand` 関数の変更

**変更前:**

```go
	default:
		p.syntax_error("in operand")
		p.advance(';', '}') // Try to recover by advancing to ';' or '}'
		return nil
```

`operand` 関数は、式の一部であるオペランドを解析する際に使用されます。`default` ケースは、予期しないトークンに遭遇した場合、つまり構文エラーが発生した場合に実行されます。
変更前は、`p.advance(';', '}')` を呼び出して、セミコロンまたは閉じ波括弧まで読み飛ばすことでエラー回復を試みていました。しかし、前述の `advance` 関数の問題により、この呼び出しがトークンを消費せずに戻ってきてしまうと、`operand` 関数は無限に同じエラーを報告し続ける可能性がありました。

**変更後:**

```go
	default:
		p.syntax_error("expecting expression") // More specific error message
		p.advance() // Advance without a stoplist, guaranteeing consumption of one token
		return nil
```

変更後では、以下の2点が変更されています。

1.  **エラーメッセージの変更**: `"in operand"` から `"expecting expression"` へと、より具体的なエラーメッセージに変更されています。これはユーザーにとってエラーの原因を理解しやすくするための改善です。
2.  **`p.advance()` の呼び出し**: `p.advance(';', '}')` から `p.advance()` に変更されています。引数なしで `advance` を呼び出すと、`advance` 関数の最初の `if len(stoplist) == 0` ブロックが実行され、**必ず1つのトークンが消費されます** (`p.next()` が呼び出されるため)。これにより、`operand` 関数が構文エラーに遭遇した場合でも、パーサーが確実に前進し、無限ループを回避できるようになります。

この `operand` 関数の変更は、`advance` 関数の修正と相まって、エラー回復時のパーサーの堅牢性を高めるための重要な修正です。

## コアとなるコードの解説

### `advance` 関数の変更点

1.  **コメントの更新**:
    `// Advance consumes tokens until it finds one in the stoplist.`
    `// If the stoplist is empty, the next token is consumed.`
    から
    `// Advance consumes tokens until it finds a token of the stoplist.`
    `// If the stoplist is empty or no advance was necessary, the next`
    `// token is consumed.`
    に変更されました。これは、新しい挙動、特に「停止リストが空の場合、またはトークンを消費する必要がなかった場合でも、次のトークンが消費される」という点を明確にしています。

2.  **`n` カウンターの導入**:
    `for p.tok != EOF {`
    が
    `for n := 0; p.tok != EOF; n++ {`
    に変更されました。`n` は `advance` 関数が呼び出されてから消費されたトークンの数を追跡します。

3.  **「少なくとも1つのトークンを消費する」ロジックの追加**:
    `if p.tok == stop {` ブロック内に
    `if n == 0 { p.next() }`
    が追加されました。これは、`advance` が呼び出された時点で既に `p.tok` が停止リスト内のトークンと一致していた場合（つまり、`advance` が何もトークンを消費せずに停止トークンを見つけた場合）、`p.next()` を呼び出してその停止トークンを消費することを保証します。これにより、パーサーが同じトークンで無限ループに陥ることを防ぎます。

### `operand` 関数の変更点

1.  **エラーメッセージの変更**:
    `p.syntax_error("in operand")`
    が
    `p.syntax_error("expecting expression")`
    に変更されました。これにより、エラーメッセージがより具体的になり、ユーザーが問題の原因を特定しやすくなります。

2.  **`advance` の呼び出し方法の変更**:
    `p.advance(';', '}')`
    が
    `p.advance()`
    に変更されました。引数なしで `advance` を呼び出すことで、`advance` 関数は停止リストが空であると判断し、必ず `p.next()` を一度呼び出して現在のトークンを消費します。これにより、`operand` 関数内で構文エラーが発生した場合でも、パーサーが確実に前進し、無限ループを回避できるようになります。

これらの変更は、Goコンパイラの構文解析器におけるエラー回復メカニズムの堅牢性を高め、特定の不正な入力に対する無限ループの脆弱性を解消することを目的としています。

# [インデックス 21944] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/ld`）のアーキテクチャを根本的に変更し、`cmd/ld`を独立したライブラリとして機能させることを目的としています。これにより、各アーキテクチャ固有のリンカ（`cmd/5l`, `cmd/6l`, `cmd/8l`, `cmd/9l`など）が`cmd/ld`を呼び出す形に統一され、リンカ全体の構造が整理されます。特に、`cmd/ld`がアーキテクチャ固有のリンカで定義されたシンボルを参照する「逆シンボル参照」が解消される点が重要です。この変更は、将来的にリンカ全体をGo言語で自動変換または再実装するための重要なステップと位置づけられています。

## 変更の背景

Go言語のリンカは、当初C言語で実装されており、各アーキテクチャ（ARM, x86, x86-64, PowerPCなど）ごとに独立したリンカ（例: `cmd/5l` for ARM, `cmd/6l` for x86-64, `cmd/8l` for x86, `cmd/9l` for PowerPC）が存在していました。これらのリンカは共通のロジックを`cmd/ld`ディレクトリ内のファイルと共有していましたが、完全なライブラリとして分離されていませんでした。

この設計にはいくつかの課題がありました。
1.  **依存関係の複雑さ**: `cmd/ld`内の共通コードが、各アーキテクチャ固有のリンカ（`cmd/5l`など）で定義されたシンボルに依存する「逆シンボル参照」が存在していました。これは、共通部分が特定の実装詳細に結合していることを意味し、コードの再利用性や保守性を低下させていました。
2.  **Go言語への移行の障壁**: Go言語のツールチェイン全体をGo言語で記述するという長期的な目標がありました。リンカのC言語実装は、この目標達成の大きな障壁となっていました。特に、複雑な相互依存関係は、自動変換や段階的なGo言語への移行を困難にしていました。
3.  **コードの重複と一貫性の欠如**: 各アーキテクチャ固有のリンカが共通ロジックを部分的にしか共有していないため、コードの重複が生じやすく、異なるアーキテクチャ間でリンカの動作に微妙な不一致が生じる可能性がありました。

このコミットは、これらの課題を解決し、リンカのアーキテクチャをよりクリーンでモジュール化されたものにするための重要な一歩です。`cmd/ld`を真のライブラリとして確立することで、リンカの共通部分とアーキテクチャ固有の部分を明確に分離し、将来的なGo言語への移行を容易にすることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **リンカ (Linker)**:
    *   コンパイラによって生成されたオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するツールです。
    *   主な役割は、シンボル解決（未解決の参照を、定義されたシンボルに結びつける）と再配置（コードやデータのメモリアドレスを調整する）です。
    *   Go言語では、デフォルトで静的リンクが行われるため、生成されるバイナリには必要なすべてのライブラリと依存関係が組み込まれます。

2.  **Go言語のリンカの歴史と構造**:
    *   Go言語の初期のリンカは、Plan 9というオペレーティングシステムのツールチェインに由来しており、C言語で書かれていました。
    *   各CPUアーキテクチャ（例: ARM, x86, x86-64, PowerPC）ごとに、`5l`, `6l`, `8l`, `9l`といったリンカが存在しました。これらの数字は、Plan 9の慣習でアーキテクチャを表すものです（例: `5` for ARM, `6` for x86-64, `8` for x86, `9` for PowerPC）。
    *   `cmd/ld`ディレクトリは、これらのアーキテクチャ固有のリンカが共有する共通のリンキングロジックを含んでいました。しかし、これは厳密なライブラリではなく、各リンカが`cmd/ld`内の関数を直接呼び出すような構造でした。

3.  **シンボル (Symbol)**:
    *   プログラム内の関数、変数、定数などの名前付きエンティティを指します。
    *   リンカは、これらのシンボル間の参照を解決し、最終的な実行ファイル内で正しいメモリアドレスにマッピングします。

4.  **逆シンボル参照 (Reverse Symbol References)**:
    *   通常、共通ライブラリは、そのライブラリを利用する上位モジュール（この場合はアーキテクチャ固有のリンカ）に依存しません。しかし、このコミット以前のGoリンカでは、`cmd/ld`内の共通コードが、`cmd/5l`などのアーキテクチャ固有のリンカで定義された特定のシンボルを参照していました。
    *   これは、共通部分が特定の実装に「逆方向」に依存している状態であり、モジュール性の観点からは望ましくありません。この依存関係は、`cmd/ld`を独立したライブラリとして再利用することを困難にしていました。

5.  **`cmd/link`**:
    *   Go 1.4以降、Go言語のリンカは`cmd/link`という単一のコマンドに統合されました。このコミットは、その統合と、リンカ全体をGo言語で再実装する長期的な目標に向けた初期のステップです。

6.  **`thearch` 構造体**:
    *   Goリンカの内部では、`thearch`というグローバルな構造体が、現在のターゲットアーキテクチャに特化した関数ポインタや設定（例: ポインタサイズ、エンディアン、リロケーション処理関数など）を保持しています。これにより、共通のリンキングロジックが、実行時に適切なアーキテクチャ固有の処理を呼び出すことができます。このコミットでは、この`thearch`構造体を活用して、アーキテクチャ固有の処理を`cmd/ld`から分離し、`cmd/ld`がより汎用的なライブラリとなるように変更されています。

## 技術的詳細

このコミットの核心は、Goリンカの共通部分である`cmd/ld`を、各アーキテクチャ固有のリンカ（`cmd/5l`, `cmd/6l`, `cmd/8l`, `cmd/9l`）から独立した「真のライブラリ」として再構築することです。

具体的な変更点は以下の通りです。

1.  **`cmd/ld`のライブラリ化**:
    *   以前は、各アーキテクチャ固有のリンカ（例: `src/cmd/5l/obj.c`）が`main`関数を持ち、リンカの処理を開始していました。このコミットでは、各アーキテクチャ固有のリンカの`main`関数が、`cmd/ld`内の共通エントリポイントである`ldmain`関数を呼び出すように変更されています。
    *   これにより、リンカの起動ロジックが`cmd/ld`に集約され、各アーキテクチャ固有のリンカは`cmd/ld`が提供するAPIを利用するクライアントのような役割になります。

2.  **逆シンボル参照の解消**:
    *   最も重要な変更点の一つは、`cmd/ld`が各アーキテクチャ固有のリンカで定義されていたシンボル（例: `LPUT`, `WPUT`, `VPUT`などのバイト書き込み関数や、`linuxdynld`などの動的リンカパス）に直接依存しなくなったことです。
    *   これらのアーキテクチャ固有の機能は、`thearch`というグローバルな構造体を介して提供されるようになりました。`thearch`構造体は、現在のターゲットアーキテクチャに応じた関数ポインタやデータ（例: `thearch.lput`, `thearch.linuxdynld`）を保持します。
    *   各アーキテクチャ固有のリンカ（例: `src/cmd/5l/obj.c`）の`linkarchinit`関数内で、そのアーキテクチャに対応する`thearch`構造体のフィールドが初期化されます。これにより、`cmd/ld`内の共通コードは、`thearch`を介して抽象化されたインターフェースを使用し、特定のアーキテクチャの実装詳細に依存しなくなります。

3.  **コードの整理と削除**:
    *   各アーキテクチャ固有のリンカのソースファイル（例: `src/cmd/5l/asm.c`, `src/cmd/5l/l.h`, `src/cmd/5l/list.c`など）から、`cmd/ld`に移動されたり、`thearch`構造体を介してアクセスされるようになったりした冗長な定義や関数が削除されています。
    *   例えば、`rnd`関数や`Iconv`関数、`LPUT`/`WPUT`/`VPUT`マクロなどが削除され、`thearch`構造体内の対応する関数ポインタに置き換えられています。
    *   また、各リンカのヘッダファイル（例: `src/cmd/5l/l.h`）から、`5.out.h`などのアーキテクチャ固有の出力形式に関するインクルードが削除され、`cmd/ld`内の共通ヘッダファイル（`lib.h`, `elf.h`, `macho.h`, `pe.h`など）が直接インクルードされるようになっています。

4.  **ビルドシステムの変更**:
    *   `src/cmd/dist/build.go`内のビルド設定が更新され、`cmd/ld`が独立したライブラリとしてビルドされるように変更されています。具体的には、`cmd/ld`が`libld.a`としてビルドされ、各アーキテクチャ固有のリンカがこのライブラリにリンクされるようになります。
    *   また、ビルド順序も調整され、`cmd/ld`が各アーキテクチャ固有のリンカ（`cmd/%sl`）よりも前にビルドされるように設定されています。

これらの変更により、リンカのコードベースはよりモジュール化され、`cmd/ld`はアーキテクチャに依存しない共通のリンキングロジックを提供するクリーンなライブラリとして機能するようになります。これは、将来的にリンカ全体をGo言語で再実装する際の基盤となります。

## コアとなるコードの変更箇所

このコミットでは、Goリンカの複数のファイルにわたる広範な変更が行われています。特に重要な変更は、各アーキテクチャ固有のリンカ（`src/cmd/5l`, `src/cmd/6l`, `src/cmd/8l`, `src/cmd/9l`）と、共通リンカライブラリである`src/cmd/ld`の間の依存関係の反転と抽象化です。

具体的な変更箇所は以下のファイル群に集中しています。

1.  **`src/cmd/{5l,6l,8l,9l}/obj.c`**:
    *   これらのファイルは、各アーキテクチャ固有のリンカのエントリポイントでした。変更後、これらの`main`関数は、`cmd/ld`内の共通の`ldmain`関数を呼び出すようになります。
    *   また、`linkarchinit`関数が追加または大幅に修正され、そのアーキテクチャ固有の関数ポインタやデータ（例: `lput`, `wput`, `vput`, `linuxdynld`など）を`thearch`グローバル構造体に設定する役割を担います。

    例: `src/cmd/5l/obj.c`の変更点
    ```c
    // 変更前: main関数がリンカの処理を直接開始
    // 変更後: main関数がlinkarchinitを呼び出し、その後ldmainを呼び出す
    void
    main(int argc, char **argv)
    {
        linkarchinit(); // アーキテクチャ固有の初期化
        ldmain(argc, argv); // cmd/ldの共通リンカエントリポイントを呼び出す
    }

    void
    linkarchinit(void)
    {
        thestring = "arm";
        thelinkarch = &linkarm;
        // thearch構造体のフィールドを初期化
        thearch.thechar = thechar;
        thearch.ptrsize = thelinkarch->ptrsize;
        // ... その他のアーキテクチャ固有の関数ポインタやデータを設定
        thearch.lput = lputl; // バイト書き込み関数
        thearch.linuxdynld = "/lib/ld-linux.so.3"; // 動的リンカパス
    }
    ```

2.  **`src/cmd/{5l,6l,8l,9l}/asm.c`**:
    *   各アーキテクチャ固有の動的リンカパス（例: `linuxdynld`, `freebsddynld`など）の定義が削除され、これらは`thearch`構造体を通じてアクセスされるようになります。
    *   リロケーション処理関数（例: `elfreloc1`, `machoreloc1`）内で、以前は直接呼び出されていた`LPUT`, `VPUT`などのバイト書き込みマクロが、`thearch.lput`, `thearch.vput`などの`thearch`構造体を介した呼び出しに置き換えられています。

    例: `src/cmd/5l/asm.c`の変更点
    ```c
    // 変更前: グローバル変数として定義されていた動的リンカパス
    // char linuxdynld[] = "/lib/ld-linux.so.3";
    // 変更後: 削除され、thearch.linuxdynld を使用

    // 変更前: 直接呼び出されていたバイト書き込みマクロ
    // LPUT(sectoff);
    // 変更後: thearch構造体を介した呼び出し
    thearch.lput(sectoff);
    ```

3.  **`src/cmd/{5l,6l,8l,9l}/l.h`**:
    *   各リンカ固有のヘッダファイルから、`5.out.h`などのアーキテクチャ固有の出力形式に関するインクルードが削除されます。
    *   以前はグローバル変数として定義されていたリンカの状態変数（例: `PtrSize`, `IntSize`, `RegSize`, `lcsize`, `symsize`など）や、`P`, `S`などのマクロ、`LPUT`, `WPUT`, `VPUT`などのバイト書き込みマクロの定義が削除されます。これらは`cmd/ld`内の共通定義や`thearch`構造体を通じてアクセスされるようになります。
    *   `rnd`関数や`Iconv`関数などのプロトタイプ宣言も削除されます。

4.  **`src/cmd/{5l,6l,8l,9l}/list.c`**:
    *   `Iconv`関数など、各リンカ固有のリスト表示関連の関数が削除されます。

5.  **`src/cmd/ld/data.c`**:
    *   リロケーション処理を行う`relocsym`関数内で、以前は直接参照されていた`thechar`や`PtrSize`などのグローバル変数が、`thearch.thechar`や`thearch.ptrsize`などの`thearch`構造体メンバーに置き換えられています。
    *   `archreloc`や`archrelocvariant`といったアーキテクチャ固有のリロケーション処理関数も、`thearch.archreloc`や`thearch.archrelocvariant`を介して呼び出されるようになります。
    *   シンボルを走査するループの条件が`s!=S`から`s!=nil`に変更されています。これは、`S`マクロが削除されたためです。

6.  **`src/cmd/ld/decodesym.c`**:
    *   シンボルから型情報をデコードする関数群（例: `decodetype_kind`, `decodetype_size`など）内で、`PtrSize`や`IntSize`が`thearch.ptrsize`や`thearch.intsize`に置き換えられています。

7.  **`src/cmd/ld/dwarf.c`**:
    *   DWARFデバッグ情報関連の処理において、`PtrSize`が`thearch.ptrsize`に、`LPUT`, `VPUT`, `WPUT`などのバイト書き込みマクロが`thearch.lput`, `thearch.vput`, `thearch.wput`に置き換えられています。
    *   `linesec == S`のようなシンボル参照が`linesec == nil`に変更されています。

8.  **`src/cmd/dist/build.go`**:
    *   ビルドスクリプトが更新され、`cmd/ld`が独立したライブラリとしてビルドされ、他のリンカがそれに依存するように変更されています。
    *   `islib`変数の定義に`|| dir == "cmd/ld"`が追加され、`cmd/ld`がライブラリとして扱われるようになります。
    *   `buildorder`に`"cmd/ld"`が追加され、`cmd/ld`が各アーキテクチャ固有のリンカ（`cmd/%sl`）よりも前にビルドされるように順序が調整されています。

9.  **`src/cmd/ld/Makefile`**:
    *   `src/cmd/ld`ディレクトリに新しいMakefileが追加され、`cmd/ld`が独立したライブラリとしてビルドされるための設定が記述されています。

これらの変更は、リンカのコードベース全体にわたる大規模なリファクタリングであり、`cmd/ld`を共通のリンキングロジックを提供する抽象化されたライブラリとして確立するためのものです。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goリンカのアーキテクチャを、各アーキテクチャ固有のリンカ（`5l`, `6l`, `8l`, `9l`）が共通の`cmd/ld`ライブラリを呼び出す形に再構築した点にあります。

以前のリンカは、各アーキテクチャ固有のリンカがそれぞれ独自の`main`関数を持ち、共通のリンキングロジックを`cmd/ld`ディレクトリ内のCファイルから直接インクルードしたり、グローバル変数やマクロを通じて共有したりしていました。この方式では、`cmd/ld`内の共通コードが、各アーキテクチャ固有のリンカで定義されたシンボル（例えば、特定のアーキテクチャでのバイト書き込み関数や、OSごとの動的リンカのパスなど）に依存する「逆シンボル参照」が発生していました。これは、共通部分が特定の実装に結合しているため、モジュール性が低く、将来的な変更やGo言語への移行を困難にしていました。

このコミットでは、この問題を解決するために、以下の主要なメカニズムが導入・強化されています。

1.  **`thearch` 構造体による抽象化**:
    *   Goリンカの内部には、`LinkArch`という構造体があり、これは各アーキテクチャ固有のリンキング設定（ポインタサイズ、レジスタサイズなど）を定義しています。
    *   このコミットでは、`thearch`というグローバルな`LinkArch`型の構造体が導入（またはその役割が強化）され、各アーキテクチャ固有のリンカが起動時に、自身のアーキテクチャに特化した関数ポインタやデータをこの`thearch`構造体に設定するように変更されました。
    *   例えば、バイトを書き込むための関数（`lput`, `wput`, `vput`）や、OSごとの動的リンカのパス（`linuxdynld`など）は、以前は各アーキテクチャ固有のリンカのファイル内で直接定義されていたり、マクロとして提供されていましたが、これらは`thearch`構造体のメンバーとして抽象化され、関数ポインタや文字列として保持されるようになりました。
    *   これにより、`cmd/ld`内の共通リンキングロジックは、特定のアーキテクチャの実装詳細を直接知る必要がなくなり、`thearch.lput(...)`のように抽象化されたインターフェースを通じてアーキテクチャ固有の処理を呼び出すことができるようになりました。

2.  **`ldmain` 関数へのエントリポイントの統一**:
    *   各アーキテクチャ固有のリンカ（`src/cmd/5l/obj.c`など）の`main`関数は、リンカの処理を直接開始するのではなく、まず`linkarchinit()`を呼び出して`thearch`構造体を初期化し、その後`cmd/ld`内の共通エントリポイントである`ldmain(argc, argv)`を呼び出すように変更されました。
    *   この変更により、リンカの起動ロジックが`cmd/ld`に集約され、各アーキテクチャ固有のリンカは、`cmd/ld`が提供する共通のリンキングフレームワークを利用する「クライアント」のような役割になります。

3.  **シンボル参照の整理**:
    *   以前は、`S`というマクロが`((LSym*)0)`として定義され、シンボルリストの終端を示すために使われていましたが、このコミットではこのマクロが削除され、代わりに`nil`（C言語の`NULL`に相当）が直接使われるようになりました。これは、リンカのコードベース全体でシンボル参照の一貫性を高めるための変更です。

これらの変更により、`cmd/ld`はアーキテクチャに依存しない、より汎用的なリンキングライブラリとして機能するようになります。これにより、リンカのコードベースはよりクリーンで保守しやすくなり、将来的にGo言語でリンカ全体を再実装する際の基盤が強化されました。特に、リンカの共通部分とアーキテクチャ固有の部分が明確に分離されたことで、Go言語への自動変換や段階的な移行が技術的に実現可能になった点が、このコミットの最大の意義と言えます。

# [インデックス 27220] ファイルの概要

このコミットは、Goランタイムのスタック管理に関連する `src/runtime/stack.go` ファイルに対する変更です。`stack.go` は、Goのゴルーチンのスタックの割り当て、拡張、縮小といったライフサイクルを管理する重要な部分を担っています。特に、ゴルーチンがスタックを使い果たした際に新しいスタックを割り当てる `newstack` 関数や、スタックの縮小処理などが含まれます。

## コミット

このコミットは、`newstack` 関数における一時的な `_Gwaiting` 状態の不具合を修正することを目的としています。並行スタック縮小処理中にゴルーチンが `_Gwaiting` 状態に遷移するタイミングが原因で発生する競合状態を解消し、ゴルーチンの状態遷移をより堅牢にすることで、ランタイムの安定性を向上させます。

## 変更の背景

Goランタイムでは、ゴルーチンのスタックは必要に応じて動的に拡張・縮小されます。特に、Go 1.5以降に導入された並行スタック縮小 (Concurrent Stack Shrinking) は、ガベージコレクション (GC) と並行してスタックを縮小することで、メモリ使用量を最適化し、GCのポーズタイムを短縮することを目的としています。

しかし、この並行スタック縮小のメカニズムには、ゴルーチンの状態遷移とスタックの移動が競合する可能性がありました。具体的には、ゴルーチンが一時的に `_Gwaiting` 状態に遷移した直後にスタックが移動されると、GCがそのゴルーチンをスキャンする際に、古いスタックポインタを参照してしまうなどの不整合が発生する可能性がありました。これは、GCがゴルーチンのスタックをスキャンする際に、そのゴルーチンが安全な状態（例えば、実行中でない状態）であることを前提としているためです。

この問題は、Go issue #12967 (関連する議論は `golang/go` issue #14406で言及されています) で報告されており、特にGCのポーズタイムが増加する原因となることが指摘されていました。以前の修正では `gopark` 関数における同様の問題が対処されましたが、`newstack` 関数にも同様の脆弱性が残っていたため、このコミットで `newstack` の修正が行われました。

## 前提知識の解説

### Goランタイムのゴルーチン状態

Goランタイムは、ゴルーチンの実行状態を管理するためにいくつかの内部状態を定義しています。このコミットに関連する主な状態は以下の通りです。

*   `_Grunning`: ゴルーチンが現在実行中である状態。
*   `_Gwaiting`: ゴルーチンが何らかのイベント（チャネル操作、タイマー、システムコールなど）を待機している状態。この状態のゴルーチンはスケジューラによって実行されません。
*   `_Gscanrunning`: GCがゴルーチンのスタックをスキャンしている間、ゴルーチンが実行中である状態。
*   `_Gscanwaiting`: GCがゴルーチンのスタックをスキャンしている間、ゴルーチンが待機中である状態。
*   `_Gcopystack`: ゴルーチンのスタックが現在コピー中である状態。スタックの拡張や縮小の際に一時的にこの状態になります。

### `newstack` と `gopark` の役割

*   `newstack`: ゴルーチンが現在のスタックを使い果たし、より大きなスタックが必要になったときに呼び出されるランタイム関数です。この関数は、新しい（より大きな）スタックを割り当て、古いスタックの内容を新しいスタックにコピーし、ゴルーチンのスタックポインタを更新します。
*   `gopark`: ゴルーチンを一時的に停止させ、`_Gwaiting` 状態に遷移させるランタイム関数です。例えば、チャネルからの受信を待つ際や、ミューテックスのロック取得を待つ際などに使用されます。

### `casgstatus` (Compare And Swap G status) の機能

`casgstatus(gp, oldval, newval)` は、ゴルーチン `gp` の状態をアトミックに更新するための関数です。現在の状態が `oldval` であれば `newval` に変更し、成功した場合は `true` を返します。これは、複数のM (Machine) やP (Processor) が同時にゴルーチンの状態を変更しようとした場合に、競合状態を防ぐために使用されます。

### 並行スタック縮小 (Concurrent Stack Shrinking)

Go 1.5で導入された機能で、ガベージコレクタが実行中に、使用されていないスタック領域を解放し、ゴルーチンのスタックをより小さなサイズに縮小するプロセスです。これにより、メモリフットプリントが削減され、GCの効率が向上します。この処理は、ゴルーチンが実行中でない（例えば `_Gwaiting` 状態にある）ときに安全に行われる必要があります。

### Goのガベージコレクション (GC) とSTW (Stop-The-World)

GoのGCは、並行かつ世代別GCを採用しており、ほとんどの処理をアプリケーションの実行と並行して行います。しかし、GCの特定のフェーズ（特にマークフェーズの開始と終了、およびマーク終了後のスイープフェーズの一部）では、アプリケーションの実行を一時的に停止させる「Stop-The-World (STW)」フェーズが発生します。STWは短時間ですが、アプリケーションの応答性に影響を与えるため、GoランタイムはSTWの時間を最小限に抑えるように設計されています。並行スタック縮小は、STW時間を短縮するための取り組みの一つです。

## 技術的詳細

このコミットが修正しようとしている問題は、`newstack` 関数内でゴルーチンが一時的に `_Gwaiting` 状態に遷移するタイミングと、並行スタック縮小処理がゴルーチンのスタックを移動させるタイミングとの間の競合です。

以前の `newstack` の実装では、スタックのコピーが始まる前に、ゴルーチンを `_Grunning` から `_Gwaiting` に遷移させ、`gp.waitreason = "stack growth"` を設定していました。この `_Gwaiting` 状態は、スタックのコピーが完了するまでの間の一時的なものでした。

問題は、この一時的な `_Gwaiting` 状態の間に、並行スタック縮小処理が介入し、ゴルーチンのスタックを移動させてしまう可能性があったことです。GCは `_Gwaiting` 状態のゴルーチンを安全にスキャンできると期待しますが、もしスタックが移動してしまっていた場合、GCが古いスタックポインタを参照してしまい、メモリの破損やクラッシュにつながる可能性がありました。

このコミットの目的は、`newstack` 内での `_Gwaiting` 状態への遷移を排除するか、その期間を極めて短くすることで、このような競合状態を回避することです。具体的には、スタックコピーの準備が整うまでゴルーチンを `_Grunning` 状態に保ち、スタックコピーが開始される直前に直接 `_Gcopystack` 状態に遷移させることで、不整合な状態でのGCスキャンを防ぎます。

## コアとなるコードの解説

このコミットの主要な変更点は、`newstack` 関数内でのゴルーチンの状態遷移ロジックの再構築です。

1.  **`_Gwaiting` への初期遷移の削除**:
    変更前は、`newstack` の冒頭でゴルーチンを `_Grunning` から `_Gwaiting` に遷移させ、`gp.waitreason = "stack growth"` を設定していました。この一時的な `_Gwaiting` 状態が、並行スタック縮小との競合の原因となっていました。
    ```diff
    -	casgstatus(gp, _Grunning, _Gwaiting)
    -	gp.waitreason = "stack growth"
    ```
    この部分が削除されたことで、ゴルーチンはスタックコピーの準備が整うまで `_Grunning` 状態を維持します。これにより、不整合な `_Gwaiting` 状態の期間がなくなります。

2.  **`_Grunning` から `_Gcopystack` への直接遷移**:
    変更前は、スタックコピーの直前に `_Gwaiting` から `_Gcopystack` へ遷移していました。
    ```diff
    -	casgstatus(gp, _Gwaiting, _Gcopystack)
    ```
    変更後は、ゴルーチンが `_Grunning` 状態から直接 `_Gcopystack` 状態に遷移するように修正されました。
    ```diff
    +	casgstatus(gp, _Grunning, _Gcopystack)
    ```
    これにより、ゴルーチンはスタックコピーが始まる直前まで `_Grunning` であり、スタックコピー中は `_Gcopystack` であるという、より明確で安全な状態遷移パスが確立されます。`_Gcopystack` 状態のゴルーチンはGCによってスキャンされないため、スタックコピー中の安全性が保証されます。

3.  **`scang` との同期のための `_Gwaiting` 遷移の追加**:
    新しいコードでは、`gp.preemptscan` が `true` の場合にのみ、`_Grunning` から `_Gwaiting` への遷移が追加されています。
    ```go
    +		// Synchronize with scang.
    +		casgstatus(gp, _Grunning, _Gwaiting)
    ```
    これは、GCがゴルーチンをスキャンする (`scang`) 際に、ゴルーチンが安全な状態であることを保証するためのものです。`gp.preemptscan` は、GCがこのゴルーチンをスキャンする必要があることを示唆しており、この場合にのみ一時的に `_Gwaiting` に遷移させることで、GCとの同期を図っています。この遷移は、以前の無条件の `_Gwaiting` 遷移とは異なり、特定の条件下でのみ発生し、その後の `castogscanstatus` によって `_Gscanwaiting` に遷移する可能性があるため、より制御された安全な状態遷移となっています。

これらの変更により、`newstack` 関数におけるゴルーチンの状態遷移が簡素化され、特に並行スタック縮小処理との間の競合が解消されました。これにより、Goランタイムの安定性とGCの正確性が向上します。

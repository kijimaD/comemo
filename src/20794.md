# [インデックス 20794] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/ld`) におけるPE (Portable Executable) ファイルのシンボル解析ロジックの修正に関するものです。具体的には、PEファイル内のシンボルがセクションを表すかどうかを判断する際の誤った仮定を修正し、GCC 4.9.1によって生成される特定のシンボルが正しく処理されるように変更されました。これにより、Windows環境でのGoプログラムのリンク時に発生する可能性のある問題を解決しています。

## 変更の背景

この変更の背景には、Go言語のリンカ (`cmd/ld`) がPE (Portable Executable) ファイルを処理する際の既存の仮定が、特定のコンパイラバージョン（具体的にはGCC 4.9.1）によって生成されるオブジェクトファイルと互換性がなくなったという問題があります。

これまでのGoリンカのPEオブジェクトリーダーは、「`.`（ドット）」で始まるシンボル名はすべてセクションを表すという単純な仮定に基づいていました。この仮定は、それまでのGCCの挙動においては概ね正しかったようです。しかし、GCC 4.9.1がリリースされた際、このバージョンが生成するオブジェクトファイルには、セクションではないにもかかわらず「`.`」で始まるシンボルが含まれるようになりました。

この新しい挙動により、Goリンカがこれらのオブジェクトファイルを処理する際に、本来セクションではないシンボルを誤ってセクションとして解釈してしまう問題が発生しました。この誤った解釈は、リンカの内部処理、特にリロケーション（再配置）やシンボルテーブルの構築に影響を与え、最終的にリンクエラーや不正な実行可能ファイルの生成につながる可能性がありました。

コミットメッセージに記載されている `Fixes #8811` と `Fixes #8856` は、この問題に関連する具体的なバグ報告を示しています。これらのバグは、GoプログラムがCgo（GoとC/C++の相互運用機能）を介してGCC 4.9.1でコンパイルされたC/C++コードとリンクされる際に顕在化したと考えられます。

このため、Goリンカは、シンボル名が「`.`」で始まるかどうかだけでなく、シンボルの他の属性（シンボルクラスやタイプなど）も考慮して、それが本当にセクションシンボルであるかをより厳密に判断する必要が生じました。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

### 1. PE (Portable Executable) フォーマット

PEフォーマットは、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトファイル、DLL (Dynamic Link Library) などの標準ファイルフォーマットです。PEファイルは、以下のような主要な構造で構成されています。

*   **DOSヘッダ**: 互換性のための古いDOS実行可能ファイルヘッダ。
*   **PEヘッダ**: ファイルがPEファイルであることを示すシグネチャと、ファイルタイプ、マシンアーキテクチャなどの情報を含む。
*   **COFF (Common Object File Format) ヘッダ**: PEヘッダの一部で、セクションの数、シンボルテーブルのオフセットとサイズなどの情報を含む。
*   **オプションヘッダ**: 実行可能ファイルのロードに関する追加情報（エントリポイント、イメージベースアドレスなど）。
*   **セクションテーブル**: ファイル内の各セクションに関する情報（セクション名、仮想アドレス、サイズ、ファイル内のオフセットなど）の配列。
*   **セクション**: 実際のコード、初期化済みデータ、未初期化データ、リソースなどが格納される論理的なブロック。例えば、`.text` はコード、`.data` は初期化済みデータ、`.bss` は未初期化データなど。
*   **シンボルテーブル**: プログラム内の関数、変数、セクションなどの名前とアドレス情報を含むエントリのリスト。リンカが異なるオブジェクトファイルを結合する際に、これらのシンボル情報を使用して参照を解決します。
*   **リロケーションテーブル**: プログラムがメモリにロードされる際に、アドレスを修正する必要がある箇所を示す情報。

### 2. Goリンカ (cmd/ld)

`cmd/ld` は、Go言語のツールチェインの一部であり、Goのソースコードからコンパイルされたオブジェクトファイルを結合して、最終的な実行可能ファイルやライブラリを生成するリンカです。Goのリンカは、クロスコンパイルをサポートしており、異なるOSやアーキテクチャ向けの実行ファイルを生成できます。Windows向けにビルドする場合、`cmd/ld` はPEフォーマットのファイルを生成・解析する能力を持っています。

### 3. シンボル (Symbol)

プログラミングにおいて、シンボルとは、プログラム内の特定のエンティティ（関数、変数、セクションなど）を識別するための名前です。コンパイラはソースコードをコンパイルする際に、これらのエンティティに対応するシンボルを生成し、オブジェクトファイル内のシンボルテーブルに記録します。リンカは、これらのシンボルを使用して、異なるオブジェクトファイル間の参照を解決し、最終的な実行可能ファイルを構築します。

PEフォーマットにおけるシンボルは、名前だけでなく、そのシンボルが何を表すか（関数、変数、セクションなど）、そのスコープ（グローバル、ローカル、スタティックなど）、データ型などの属性も持ちます。

### 4. セクション (Section)

実行可能ファイルやオブジェクトファイルは、異なる種類のデータやコードを論理的に分離するためにセクションに分割されます。各セクションは特定の目的を持ち、例えば実行可能なコードは `.text` セクションに、初期化されたデータは `.data` セクションに、未初期化データは `.bss` セクションに格納されます。PEファイルでは、セクションはセクションテーブルに記述され、それぞれがファイル内の特定のオフセットとメモリ内の仮想アドレスに対応します。

### 5. GCC (GNU Compiler Collection)

GCCは、GNUプロジェクトによって開発された、C、C++、Objective-C、Fortran、Ada、Goなどの多くのプログラミング言語をサポートするコンパイラの集合です。Go言語自体は独自のコンパイラ（`gc`）を持っていますが、Cgoを通じてC/C++コードをGoプログラムに組み込む場合、そのC/C++コードのコンパイルにはGCCが使用されることがあります。

このコミットで言及されている「GCC 4.9.1」は、特定のバージョンのGCCを指しており、このバージョンでシンボル生成の挙動に変化があったことが問題の根本原因となっています。

### 6. シンボルクラス (Symbol Class) とタイプ (Type)

PEフォーマットのシンボルテーブルエントリには、シンボルの「ストレージクラス (Storage Class)」と「タイプ (Type)」というフィールドが含まれます。これらはシンボルの性質を詳細に記述するために使用されます。

*   **ストレージクラス (Storage Class)**: シンボルのスコープやリンカによる扱い方を示します。例えば、`IMAGE_SYM_CLASS_EXTERNAL` は外部リンケージを持つシンボル（他のファイルから参照可能）、`IMAGE_SYM_CLASS_STATIC` はファイルスコープの静的シンボル（現在のファイル内でのみ参照可能）などを意味します。
*   **タイプ (Type)**: シンボルが何を表すかを示します。例えば、関数、配列、ポインタなどです。セクションシンボルは通常、特定のタイプ値を持つか、タイプがゼロ（基本タイプ）である場合があります。

これらのフィールドを組み合わせることで、リンカはシンボルがセクションを表すものなのか、それとも通常の変数や関数なのかを正確に区別することができます。

## 技術的詳細

このコミットの技術的な核心は、GoリンカのPEファイル処理部分 (`src/cmd/ld/ldpe.c`) におけるシンボル解釈の厳密化です。

### 以前のロジックの問題点

GoリンカのPEオブジェクトリーダーは、シンボルがセクションを表すかどうかを判断する際に、非常に単純なヒューリスティックを使用していました。それは、シンボル名が単に「`.`」で始まるかどうかをチェックするというものでした。

```c
// 以前のロジックの例 (擬似コード)
if (obj->pesym[symindex].name[0] == '.') {
    // このシンボルはセクションであると仮定
    rp->add += obj->pesym[symindex].value;
}
```

この仮定は、ほとんどのケースで機能していましたが、GCC 4.9.1が生成するオブジェクトファイルでは、セクションではない通常のデータシンボルや関数シンボルが「`.`」で始まる名前を持つことがありました。例えば、デバッグ情報に関連するシンボルや、特定の最適化によって生成される内部シンボルなどがこれに該当する可能性があります。

リンカがこれらの非セクションシンボルを誤ってセクションとして扱ってしまうと、以下のような問題が発生します。

1.  **リロケーションの誤った適用**: セクションシンボルは、そのセクションのベースアドレスに関連するリロケーションの計算に使用されることがあります。非セクションシンボルをセクションとして扱うと、リロケーションのオフセット計算が狂い、不正なアドレスが参照される可能性があります。
2.  **シンボルテーブルの破損**: リンカが内部的に管理するシンボルテーブルに、誤った種類のシンボルが登録されることで、後続のシンボル解決処理でエラーが発生したり、予期せぬ動作を引き起こしたりする可能性があります。
3.  **リンクエラー**: 最悪の場合、リンカは矛盾を検出して処理を中断し、リンクエラーを報告します。

### 新しい `issect` 関数の導入とロジック

この問題を解決するために、コミットでは `issect` という新しい静的関数が導入されました。この関数は、与えられたPEシンボルが本当にセクションシンボルであるかどうかを、より厳密な基準で判断します。

`issect` 関数の定義は以下の通りです。

```c
static int
issect(PeSym *s)
{
	return s->sclass == IMAGE_SYM_CLASS_STATIC && s->type == 0 && s->name[0] == '.';
}
```

この関数は、以下の3つの条件がすべて真である場合にのみ、シンボルがセクションであると判断します。

1.  `s->sclass == IMAGE_SYM_CLASS_STATIC`: シンボルのストレージクラスが `IMAGE_SYM_CLASS_STATIC` であること。
    *   `IMAGE_SYM_CLASS_STATIC` は、シンボルがファイルスコープの静的シンボルであることを示します。セクションシンボルは通常、そのオブジェクトファイル内で静的に定義されるため、このクラスに分類されます。これにより、外部リンケージを持つ通常の関数や変数シンボルを除外できます。
2.  `s->type == 0`: シンボルのタイプが `0` であること。
    *   PEフォーマットでは、シンボルのタイプフィールドは、そのシンボルが関数、配列、ポインタなど、どのようなエンティティを表すかを示します。タイプ `0` は通常、基本タイプ（またはタイプが指定されていない）を意味し、セクションシンボルによく見られる特徴です。これにより、関数や配列などの特定のタイプを持つシンボルを除外できます。
3.  `s->name[0] == '.'`: シンボル名が「`.`」で始まること。
    *   これは以前の唯一の条件でしたが、他の2つの条件と組み合わせることで、より正確なフィルタリングが可能になります。PEファイルにおける標準的なセクション名（例: `.text`, `.data`, `.rdata`）はすべて「`.`」で始まります。

これらの条件を組み合わせることで、リンカは「`.`」で始まるシンボルであっても、それがセクションシンボルとしての適切な属性（静的クラスと基本タイプ）を持たない限り、セクションとして誤って解釈することを防ぎます。

### リンカのシンボル解決への影響

この変更は、`cmd/ld` がPEオブジェクトファイルからシンボルを読み取り、処理する複数の箇所に適用されています。

*   **リロケーション処理**: `ldpe` 関数内で、リロケーションの追加オフセットを計算する際に、シンボルがセクションであるかどうかの判断に `issect` が使用されるようになりました。これにより、リロケーションが正しいセクションベースアドレスに対して適用されるようになります。
*   **サブシンボルの処理**: シンボルテーブルを走査し、サブシンボル（例えば、セクションシンボルに関連付けられた通常のシンボル）を処理する際にも、`issect` を使用してセクションシンボルをスキップするロジックが変更されました。これにより、セクションシンボルが通常のシンボルとして誤って扱われることを防ぎます。
*   **シンボル名の解決**: `readsym` 関数内で、シンボル名を取得する際に、シンボルがセクションであるかどうかの判断に `issect` が使用されています。セクションシンボルの場合、そのセクション名がシンボル名として使用されるため、この判断が重要になります。

この修正により、GoリンカはGCC 4.9.1のような新しいコンパイラバージョンによって生成されるPEオブジェクトファイルに対しても、堅牢かつ正確なシンボル解決とリンク処理を実行できるようになりました。

## コアとなるコードの解説

### `issect` 関数の役割

`issect` 関数は、PEシンボルがセクションシンボルであるか否かを判定するための中心的なロジックをカプセル化しています。この関数が導入される前は、シンボル名が `.` で始まるかどうかという単一の条件で判断されていましたが、これは不十分でした。

`issect` は以下の3つの条件をAND結合で評価します。

1.  `s->sclass == IMAGE_SYM_CLASS_STATIC`:
    *   `s->sclass` はシンボルのストレージクラスを示します。`IMAGE_SYM_CLASS_STATIC` は、シンボルが現在のオブジェクトファイル内で静的に定義されていることを意味します。セクションシンボルは通常、このクラスに分類されます。これにより、外部から参照可能なグローバルシンボル（例えば、通常の関数やグローバル変数）が誤ってセクションとして扱われることを防ぎます。
2.  `s->type == 0`:
    *   `s->type` はシンボルのタイプを示します。PEフォーマットでは、タイプはシンボルが関数、配列、ポインタなど、どのようなエンティティを表すかを指定します。タイプ `0` は「基本タイプ」または「タイプが指定されていない」ことを意味し、セクションシンボルによく見られる特徴です。これにより、特定のデータ型を持つシンボルがセクションとして誤認されるのを防ぎます。
3.  `s->name[0] == '.'`:
    *   これは以前から存在した条件で、シンボル名が `.` で始まることを確認します。PEファイルにおけるセクション名（例: `.text`, `.data`, `.rdata`）は慣習的に `.` で始まります。

これらの条件を組み合わせることで、リンカはより正確にセクションシンボルを識別し、それ以外の `.` で始まるシンボル（例えば、GCC 4.9.1が生成する特定のデバッグシンボルなど）を適切に無視または異なる方法で処理できるようになります。

### `ldpe` 関数内での `issect` の利用

`ldpe` 関数は、PEオブジェクトファイルを読み込み、その内容をGoリンカの内部表現に変換する主要な関数です。この関数内で、シンボルがセクションであるかどうかの判断が必要な複数の箇所で `issect` が呼び出されています。

*   **リロケーションのオフセット計算**:
    PEファイルのリロケーションエントリには、シンボルへの参照が含まれることがあります。特に、セクションシンボルへの参照は、そのセクションのベースアドレスを基準としたオフセット計算に影響を与えます。以前は `obj->pesym[symindex].name[0] == '.'` で判断していましたが、これが `issect(&obj->pesym[symindex])` に置き換えられました。これにより、リロケーションの計算が、真のセクションシンボルに対してのみ正しく適用されるようになります。

*   **サブシンボルのスキップ**:
    PEシンボルテーブルには、セクションシンボルとそのセクション内の通常のシンボル（サブシンボル）が混在していることがあります。リンカが通常のシンボルを処理する際、セクションシンボル自体はスキップする必要があります。以前は `obj->pesym[i].name[0] == '.'` でセクションシンボルをスキップしていましたが、これも `issect(&obj->pesym[i])` に変更されました。これにより、セクションシンボルではない `.` 始まりのシンボルが誤ってスキップされることを防ぎ、リンカがそれらを適切に処理できるようになります。

### `readsym` 関数内での `issect` の利用

`readsym` 関数は、PEシンボルテーブルから個々のシンボルを読み取り、その名前を解決する役割を担っています。セクションシンボルの場合、そのシンボル名として、関連するセクションの名前が使用されることがあります。

*   **シンボル名の解決**:
    `if(sym->name[0] == '.')` という条件が `if(issect(sym))` に変更されました。これにより、`readsym` は、真のセクションシンボルに対してのみ、そのセクション名を取得するロジックを適用し、それ以外の `.` 始まりのシンボルに対しては通常のシンボル名解決ロジックを適用するようになります。

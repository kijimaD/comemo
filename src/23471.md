# [インデックス 23471] ファイルの概要

このコミットは、Goリンカにおける動的ライブラリの追加処理 (`adddynlib` 関数) の実装を統合するものです。これまで各アーキテクチャ固有のリンカ (`5l`, `6l`, `7l`, `8l`, `9l`) に個別に存在していたほぼ同一のコードを、共通の内部リンカパッケージ (`cmd/internal/ld`) に集約し、コードの重複を排除しています。

## 変更の背景

このコミットが行われた2015年5月は、Go 1.5のリリース（同年8月）に向けて、Goの動的リンク機能が大きく強化されていた時期にあたります。それ以前のGoでは、動的リンクのサポートは限定的であり、特に標準の `go build` ツールでは一般的ではありませんでした。しかし、Go 1.5では、Goプログラムを共有ライブラリとしてビルドしたり、C言語の共有ライブラリとリンクしたりする機能が導入されました。

このような動的リンク機能の強化に伴い、リンカ内部での動的ライブラリの扱いに関するコードの整理と共通化が求められました。コミットメッセージにあるように、Goの各アーキテクチャ固有のリンカ (`5l`, `6l`, `7l`, `8l`, `9l` など) には、動的ライブラリを追加するための `adddynlib` 関数がそれぞれ実装されていましたが、これらの実装は本質的に同じ内容でした。

この重複するコードは、保守性の低下や将来的な機能拡張の妨げとなるため、共通のロジックを中央集権的な場所 (`cmd/internal/ld` パッケージ) に移動し、一元的に管理することが決定されました。これにより、コードベースの簡素化、バグの削減、および今後の動的リンク関連機能の開発効率向上が期待されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goリンカ (cmd/ld)**: Go言語のビルドツールチェーンの一部であり、コンパイルされたオブジェクトファイルやアーカイブファイルを結合して、実行可能ファイルや共有ライブラリを生成する役割を担います。Goのリンカは、伝統的なC/C++のリンカとは異なり、Goランタイムや標準ライブラリの多くを静的にリンクする傾向があります。
*   **動的リンク (Dynamic Linking)**: プログラムの実行時に必要なライブラリをロードするリンク方式です。これにより、複数のプログラムが同じライブラリのコピーを共有できるため、ディスクスペースの節約やメモリ使用量の削減、ライブラリの更新が容易になるなどの利点があります。対照的に、静的リンクでは必要なライブラリコードが実行可能ファイルに直接組み込まれます。
*   **共有ライブラリ (Shared Libraries)**: 動的リンクで使用されるライブラリの形式です。Linuxでは `.so` (shared object)、macOSでは `.dylib` (dynamic library)、Windowsでは `.dll` (dynamic link library) といった拡張子を持ちます。
*   **アーキテクチャ固有のリンカ**: Goのツールチェーンは、異なるCPUアーキテクチャ（例: x86, ARM, ARM64, PowerPC）に対応するために、それぞれに特化したリンカを持っていました。
    *   `5l`: ARM (32-bit)
    *   `6l`: x86-64 (AMD64)
    *   `7l`: ARM64
    *   `8l`: x86 (32-bit)
    *   `9l`: PowerPC (PPC64)
    これらのリンカは、それぞれのアーキテクチャの特性に合わせたコード生成やバイナリフォーマットの処理を行っていました。
*   **`cmd/internal/ld` パッケージ**: Goのリンカの共通ロジックをカプセル化するために導入された内部パッケージです。アーキテクチャに依存しないリンカの機能やデータ構造がここに集約されています。
*   **ELF (Executable and Linkable Format)**: LinuxやUnix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準バイナリフォーマットです。
    *   **`DT_NEEDED`**: ELF形式の動的セクション (`.dynamic`) に含まれるエントリの一つで、このバイナリが依存する共有ライブラリの名前を指定します。
*   **Mach-O**: macOS (Darwin) で使用される実行可能ファイル、オブジェクトファイル、共有ライブラリのバイナリフォーマットです。
    *   **`Machoadddynlib`**: Mach-O形式のバイナリに動的ライブラリの依存関係を追加するためのリンカ内部関数。

## 技術的詳細

このコミットの主要な目的は、Goリンカにおける動的ライブラリの追加ロジックの共通化です。具体的には、以下の変更が行われました。

1.  **`needlib` 関数の削除**:
    *   各アーキテクチャ固有のリンカ (`src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/7l/asm.go`, `src/cmd/8l/asm.go`, `src/cmd/9l/asm.go`) から、`needlib` 関数が削除されました。
    *   `needlib` は、特定の動的ライブラリが既にリンカによって処理されたかどうかを判断するためのヘルパー関数でした。これは、シンボルテーブル内に特定の名前 (`.dynlib.libname` や `.elfload.libname`) のエントリが存在するかどうかを確認することで実現されていました。
2.  **`adddynlib` 関数の削除と共通化**:
    *   同様に、各アーキテクチャ固有のリンカの `asm.go` ファイルから `adddynlib` 関数が削除されました。
    *   これらの `adddynlib` 関数は、ELF形式 (`DT_NEEDED` エントリの追加) とMach-O形式 (`Machoadddynlib` の呼び出し) の両方に対応していましたが、そのロジックはほぼ同一でした。
    *   削除された `adddynlib` の機能は、`src/cmd/internal/ld/go.go` に新しく追加された共通の `adddynlib` 関数に集約されました。
3.  **`ld.Thearch.Adddynlib` の削除**:
    *   各アーキテクチャの `obj.go` ファイル (`src/cmd/5l/obj.go`, `src/cmd/6l/obj.go`, `src/cmd/7l/obj.go`, `src/cmd/8l/obj.go`, `src/cmd/9l/obj.go`) から、`ld.Thearch.Adddynlib = adddynlib` という行が削除されました。
    *   これは、`ld.Thearch` 構造体（現在のアーキテクチャ固有のリンカ設定を保持）から `Adddynlib` フィールドが削除されたことに伴う変更です。`src/cmd/internal/ld/lib.go` の `Arch` 構造体定義からも `Adddynlib func(string)` が削除されています。これにより、動的ライブラリ追加のロジックがアーキテクチャ固有のインターフェースから切り離されました。
4.  **新しい共通 `adddynlib` の導入**:
    *   `src/cmd/internal/ld/go.go` に、新しい `adddynlib(lib string)` 関数が追加されました。
    *   この新しい関数は、`Seenlib` という `map[string]bool` 型のグローバル変数を使用して、既に処理された動的ライブラリを追跡します。これにより、`needlib` 関数が担っていた重複追加防止の役割が、よりシンプルかつ効率的な方法で実現されています。
    *   `adddynlib` の内部ロジックは、`ld.Iself` (ELF形式の場合) と `ld.HEADTYPE == obj.Hdarwin` (Mach-O形式の場合) に応じて、適切なバイナリフォーマット固有の処理を呼び出します。それ以外のフォーマットの場合はエラーを報告します。
5.  **`loadcgo` 関数の更新**:
    *   `src/cmd/internal/ld/go.go` 内の `loadcgo` 関数が、アーキテクチャ固有の `Thearch.Adddynlib(lib)` の呼び出しを、新しく導入された共通の `adddynlib(lib)` に変更しました。これにより、Cgoによって動的ライブラリが要求される際に、共通のロジックが使用されるようになります。

この変更により、Goリンカの動的ライブラリ処理は、アーキテクチャ固有の差異を吸収しつつ、より一貫性のある、保守しやすい形に進化しました。

## コアとなるコードの解説

### 削除された `needlib` 関数 (例: `src/cmd/5l/asm.go` から)

```go
func needlib(name string) int {
	if name[0] == '\x00' {
		return 0
	}

	/* reuse hash code in symbol table */
	p := fmt.Sprintf(".dynlib.%s", name)

	s := ld.Linklookup(ld.Ctxt, p, 0)

	if s.Type == 0 {
		s.Type = 100 // avoid SDATA, etc.
		return 1
	}

	return 0
}
```
この関数は、特定のライブラリ名 (`name`) が既にリンカによって処理され、動的ライブラリとして追加される必要があるかどうかをチェックしていました。シンボルテーブル内に `.dynlib.name` (または `.elfload.name` for `6l`) というシンボルが存在するかどうかで判断していました。存在しない場合は、新しいライブラリとしてマークし、`1` を返していました。

### 削除された `adddynlib` 関数 (例: `src/cmd/5l/asm.go` から)

```go
func adddynlib(lib string) {
	if needlib(lib) == 0 {
		return
	}

	if ld.Iself {
		s := ld.Linklookup(ld.Ctxt, ".dynstr", 0)
		if s.Size == 0 {
			ld.Addstring(s, "")
		}
		ld.Elfwritedynent(ld.Linklookup(ld.Ctxt, ".dynamic", 0), ld.DT_NEEDED, uint64(ld.Addstring(s, lib)))
	} else if ld.HEADTYPE == obj.Hdarwin {
		ld.Machoadddynlib(lib)
	} else {
		ld.Diag("adddynlib: unsupported binary format")
	}
}
```
この関数は、`needlib` を呼び出してライブラリがまだ追加されていないことを確認した後、実際の動的ライブラリの追加処理を行っていました。
*   `ld.Iself` が真の場合（ELF形式のバイナリを生成する場合）、`.dynstr` セクションにライブラリ名を追加し、`.dynamic` セクションに `DT_NEEDED` エントリを追加して、このバイナリが `lib` に依存することを記録していました。
*   `ld.HEADTYPE == obj.Hdarwin` が真の場合（Mach-O形式のバイナリを生成する場合）、`ld.Machoadddynlib` を呼び出してMach-O固有の処理を行っていました。
*   それ以外のバイナリフォーマットの場合は、サポートされていないという診断メッセージを出力していました。

### 新しく追加された共通 `adddynlib` 関数 (`src/cmd/internal/ld/go.go` に)

```go
var Seenlib = make(map[string]bool)

func adddynlib(lib string) {
	if Seenlib[lib] {
		return
	}
	Seenlib[lib] = true

	if Iself {
		s := Linklookup(Ctxt, ".dynstr", 0)
		if s.Size == 0 {
			Addstring(s, "")
		}
		Elfwritedynent(Linklookup(Ctxt, ".dynamic", 0), DT_NEEDED, uint64(Addstring(s, lib)))
	} else if HEADTYPE == obj.Hdarwin {
		Machoadddynlib(lib)
	} else {
		Diag("adddynlib: unsupported binary format")
	}
}
```
新しい共通の `adddynlib` 関数は、以前の各アーキテクチャ固有の実装とほぼ同じロジックを持っていますが、いくつかの重要な違いがあります。
*   **`Seenlib` マップによる重複防止**: `needlib` 関数の代わりに、`Seenlib` というグローバルマップを使用しています。これにより、既に処理されたライブラリはマップに記録され、同じライブラリが複数回追加されるのを防ぎます。これは、`needlib` がシンボルテーブルを検索していたよりも、より直接的で効率的な方法です。
*   **共通パッケージへの移動**: この関数が `cmd/internal/ld` パッケージに移動されたことで、Goリンカのすべての部分から一貫した方法で動的ライブラリを追加できるようになりました。これにより、コードの重複が解消され、将来的なメンテナンスや機能拡張が容易になります。
*   **`loadcgo` からの呼び出し**: `src/cmd/internal/ld/go.go` 内の `loadcgo` 関数は、Cgoによって動的ライブラリが必要とされる場合に、この新しい共通の `adddynlib` を呼び出すように変更されました。

この変更は、Goリンカの内部構造を整理し、動的リンク機能の基盤を強化する上で重要なステップでした。

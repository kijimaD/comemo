# [インデックス 28216] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおけるPlan 9オペレーティングシステム向けの`StartProcess`関数において、子プロセスに渡すべきではない余分なファイルディスクリプタ（FD）を閉じるメカニズムを簡素化し、レースコンディションの発生を抑制することを目的としています。具体的には、親プロセスがフォーク前に開いているFDのリストを作成するのではなく、子プロセス自身がオープンされているFDのリストを読み取り、明示的に要求されていないFDを閉じるように変更されています。これにより、コードの複雑性が軽減され、将来的に`ForkLock`の削除が可能になります。

## 元コミット内容

このコミットは、Goの`syscall`パッケージにおけるPlan 9実装の`StartProcess`関数において、子プロセスが継承すべきではないファイルディスクリプタを閉じる処理を改善します。以前の`@ality`による作業（`https://golang.org/cl/57890043`）を再活性化し、レースコンディションを減らすことを目指しています。具体的には、親プロセスがフォーク前にオープンなFDのリストを作成するのではなく、子プロセスが自身でオープンなFDを列挙し、明示的に保持するよう指定されていないものを閉じる方式に変更されます。これにより、親プロセスが起動時に継承した余分なFDを保持し続けるという複雑な問題も解消されます。この変更は、Plan 9における`ForkLock`を不要にし、その後のコミットで削除される予定です。GoのIssue #5605を修正します。

## 変更の背景

Goプログラムが子プロセスを起動する際、親プロセスが持つファイルディスクリプタ（FD）の一部が子プロセスに継承されることがあります。しかし、多くの場合、子プロセスは親プロセスが持つ全てのFDを必要とせず、むしろセキュリティやリソース管理の観点から、不要なFDは閉じるべきです。特にUnix系システムでは、`exec`システムコールが実行される際に`FD_CLOEXEC`フラグが設定されたFDは自動的に閉じられますが、Plan 9のような一部のシステムではこの挙動が異なります。

このコミットの背景には、Plan 9環境における`syscall.StartProcess`のFDクローズ処理が抱えていた以下の問題がありました。

1.  **レースコンディションの可能性**: 従来の方式では、親プロセスがフォーク前にオープンなFDのリストを収集し、子プロセスに閉じるべきFDのリストを渡していました。この「リスト収集」と「フォーク」の間に、別のゴルーチンが新しいFDを開いてしまうと、そのFDはリストに含まれず、子プロセスに意図せず継承されてしまう可能性がありました。これはレースコンディションの一種であり、予期せぬ動作やリソースリークにつながる恐れがありました。
2.  **複雑な継承FDの管理**: 親プロセス自身が起動時に継承したFD（例えば、シェルから起動された際に標準入出力以外のFD）を、子プロセスに渡すべきかどうかを判断するロジックが複雑でした。
3.  **`ForkLock`の必要性**: 上記のレースコンディションを防ぐため、Goのランタイムは`ForkLock`というグローバルロックを使用していました。これは、`StartProcess`が実行される間、他のゴルーチンがFDを操作するのを防ぐためのものでしたが、並行性を阻害し、パフォーマンスのボトルネックとなる可能性がありました。

これらの問題を解決し、より堅牢でシンプルなFD管理を実現するために、このコミットが導入されました。特に、Plan 9の「全てがファイル」という哲学と、FDの管理方法がUnix系とは異なる点を考慮した設計が求められました。

## 前提知識の解説

### Plan 9オペレーティングシステム

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。その最も特徴的な設計思想は「**全てがファイル** (Everything is a file)」です。これは、プロセス、ネットワーク接続、グラフィックス、デバイスなど、システム内のあらゆるリソースがファイルとして表現され、標準的なファイルシステムインターフェース（`open`, `read`, `write`, `close`など）を通じてアクセスされることを意味します。

*   **ファイルディスクリプタ (Fid)**: Plan 9では、Unixのファイルディスクリプタに相当するものを「Fid (File Identifier)」と呼びます。これらは32ビットの整数で、オープンされたファイルだけでなく、ディレクトリのトラバースや属性の問い合わせ（`stat`）など、サーバー上のあらゆる「現在のファイル」を識別します。
*   **9Pプロトコル**: Plan 9の「全てがファイル」の哲学は、9P (Plan 9 File Protocol) と呼ばれるプロトコルによって実現されています。これは、クライアントとサーバー間の全ての通信を規定するシンプルでメッセージ指向のプロトコルであり、ローカルなカーネルモジュール、リモートファイルサーバー、ユーザー空間プロセスなど、あらゆる種類のサーバーとの間でファイル操作を行います。
*   **制御ファイル**: Plan 9では、システムリソースを管理するために「制御ファイル」が用いられます。これらは通常`/dev`や`/proc`のようなディレクトリに存在し、制御ファイルを開くと、そのリソースのインスタンスを表す新しいFidが返されます。このFidへの`write`操作を通じて、リソースにコマンドを送信できます。
*   **プロセスごとの名前空間**: 各プロセスは独自のファイルシステム階層（名前空間）を持つことができます。これは`bind`や`mount`操作によって動的に変更可能で、柔軟なリソース管理と分散システムでの利用を可能にします。

### ファイルディスクリプタの継承とクローズ

Unix系システムでは、`fork`システムコールで子プロセスが生成されると、親プロセスの全てのFDが子プロセスに複製されます。その後、`exec`システムコールで新しいプログラムが実行される際、`FD_CLOEXEC`フラグが設定されているFDは自動的に閉じられます。Goの`syscall.StartProcess`は、このメカニズムを利用して不要なFDを閉じます。

しかし、Plan 9では`FD_CLOEXEC`のようなフラグが存在しないため、子プロセスが不要なFDを明示的に閉じる必要があります。この処理を安全かつ効率的に行うことが、このコミットの主要な課題でした。

### `ForkLock`

Goのランタイムでは、`fork`/`exec`のようなプロセス生成操作において、親プロセスと子プロセスの間でFDの状態に関するレースコンディションを防ぐために`ForkLock`というグローバルなミューテックスが使用されることがあります。これは、`fork`が実行される直前にロックを取得し、`exec`が実行されるまで（または子プロセスが不要なFDを閉じるまで）保持することで、その間に他のゴルーチンがFDを操作して予期せぬ状態変化を引き起こすのを防ぎます。しかし、これは並行性を制限するため、可能な限り排除することが望ましいとされています。

## 技術的詳細

このコミットの核心は、子プロセスが不要なファイルディスクリプタを閉じるロジックを、親プロセスから子プロセスへ移行し、その方法をPlan 9のシステム特性に合わせて最適化した点にあります。

### 変更前のアプローチ（親プロセス主導）

変更前は、`forkExec`関数内で`ForkLock`を取得した後、親プロセスが`readdupdevice()`を呼び出して現在オープンされている全てのFDのリストを取得していました。このリストから、標準入出力や`attr.Files`で明示的に指定されたFD、および起動時に継承されたFDを除外し、残りを`fdsToClose`リストとして作成していました。この`fdsToClose`リストが`forkAndExecInChild`関数に渡され、子プロセスはそのリストに基づいてFDを閉じていました。

このアプローチの問題点は、`readdupdevice()`でリストを取得してから`fork`が実際に実行されるまでの間に、他のゴルーチンが新しいFDを開く可能性があり、そのFDが`fdsToClose`リストに含まれないため、子プロセスに意図せず継承されてしまうレースコンディションが存在したことです。

### 変更後のアプローチ（子プロセス主導）

新しいアプローチでは、`forkAndExecInChild`関数が`fdsToClose`引数を受け取らなくなりました。代わりに、子プロセスが`fork`後に自身でオープンなFDを列挙し、閉じるべきものを判断します。

1.  **`#d`ディレクトリの利用**: Plan 9では、オープンなファイルディスクリプタに関する情報が仮想ファイルシステム上の`#d`ディレクトリ（`dupdev`変数で表現）を通じて提供されます。このディレクトリには、各FDに対応するエントリが含まれています。
2.  **`SYS_OPEN`で`#d`を開く**: 子プロセスは`fork`後、まず`SYS_OPEN`システムコールを使って`#d`ディレクトリを読み取り専用で開きます。これにより、`dupdevfd`というFDが取得されます。
3.  **`SYS_PREAD`でディレクトリを読み取る**: 次に、`SYS_PREAD`システムコールをループで呼び出し、`dupdevfd`からディレクトリの内容（FDに関する情報）を`statbuf`に読み込みます。
4.  **`gdirname`と`atoi`でFD番号を抽出**: 読み込んだディレクトリデータは、Plan 9のディレクトリエントリ形式（`STATFIXLEN`や`nameOffset`などの定数で定義される構造）に従っています。新しく追加されたヘルパー関数`gstringb`と`gdirname`は、このバイナリデータからファイル名（FD番号）を抽出するために使用されます。抽出されたファイル名（文字列）は、`atoi`関数によって整数（FD番号）に変換されます。
5.  **`closeFdExcept`で不要なFDを閉じる**: 抽出された各FD番号に対して、新しく追加された`closeFdExcept`関数が呼び出されます。この関数は、引数として渡された`fd1`（子プロセスとの通信パイプの書き込み側）、`fd2`（`#d`ディレクトリを開いたFD）、および`fds`（`attr.Files`で明示的に子プロセスに渡すよう指定されたFDのリスト）に含まれないFDのみを`SYS_CLOSE`システムコールで閉じます。これにより、子プロセスが必要とするFDだけがオープンなまま維持されます。
6.  **`dupdevfd`を閉じる**: 全てのFDの処理が終わった後、`#d`ディレクトリを開いた`dupdevfd`も閉じられます。

この変更により、FDのリスト収集と`fork`の間のレースコンディションが解消されます。子プロセスは`fork`後に自身のコンテキストでオープンなFDを直接列挙するため、親プロセスの状態に依存する問題がなくなります。

### 新しいヘルパー関数

*   **`gstringb(b []byte) []byte`**: バイトスライス`b`から、16ビットの長さプレフィックスを持つ文字列を読み取ります。Plan 9のディレクトリエントリからファイル名を抽出する際に使用されます。
*   **`gdirname(buf []byte) (name []byte, rest []byte)`**: ディレクトリエントリのバッファから最初のファイル名を抽出し、残りのバッファを返します。
*   **`closeFdExcept(n int, fd1 int, fd2 int, fds []int)`**: 指定されたFD番号`n`が、`fd1`, `fd2`, または`fds`リストのいずれにも含まれない場合に、そのFDを閉じます。

### `ForkLock`の冗長化

この新しいアプローチでは、親プロセスが`fork`前にオープンなFDのリストを正確に把握する必要がなくなったため、`ForkLock`が不要になります。コミットメッセージにもあるように、このコミットに続いて`ForkLock`を削除するコミットが予定されています。

## コアとなるコードの変更箇所

主な変更は`src/syscall/exec_plan9.go`ファイルに集中しています。

*   `gstringb`, `gdirname`, `closeFdExcept`の3つの新しいヘルパー関数が追加されました。
*   `forkAndExecInChild`関数のシグネチャが変更され、`fdsToClose []int`引数が削除されました。
*   `forkAndExecInChild`関数内で、`#d`ディレクトリを読み取り、オープンなFDを列挙し、`closeFdExcept`を使って不要なFDを閉じる新しいロジックが追加されました。
*   `forkExec`関数から、親プロセスが`readdupdevice()`を呼び出して`fdsToClose`リストを作成するロジックが削除されました。また、`forkAndExecInChild`の呼び出しも新しいシグネチャに合わせて変更されました。
*   `src/syscall/syscall_plan9.go`には、`atoi`関数に`//go:nosplit`ディレクティブが追加されています。

```go
// gstringb reads a non-empty string from b, prefixed with a 16-bit length in little-endian order.
// It returns the string as a byte slice, or nil if b is too short to contain the length or
// the full string.
//go:nosplit
func gstringb(b []byte) []byte {
	if len(b) < 2 {
		return nil
	}
	n, b := gbit16(b) // gbit16は16ビットの長さを読み取り、残りのスライスを返す（既存関数）
	if int(n) > len(b) {
		return nil
	}
	return b[:n]
}

// Offset of the name field in a 9P directory entry - see UnmarshalDir() in dir_plan9.go
const nameOffset = 39

// gdirname returns the first filename from a buffer of directory entries,
// and a slice containing the remaining directory entries.
// If the buffer doesn't start with a valid directory entry, the returned name is nil.
//go:nosplit
func gdirname(buf []byte) (name []byte, rest []byte) {
	if len(buf) < 2 {
		return
	}
	size, buf := gbit16(buf) // ディレクトリエントリ全体のサイズを読み取る
	if size < STATFIXLEN || int(size) > len(buf) { // STATFIXLENは固定部分の最小サイズ
		return
	}
	name = gstringb(buf[nameOffset:size]) // nameOffsetからsizeまでの範囲でファイル名を抽出
	rest = buf[size:] // 残りのバッファ
	return
}

// close the numbered file descriptor, unless it is fd1, fd2, or a member of fds.
//go:nosplit
func closeFdExcept(n int, fd1 int, fd2 int, fds []int) {
	if n == fd1 || n == fd2 { // fd1 (パイプ) または fd2 (#dディレクトリ) は閉じない
		return
	}
	for _, fd := range fds { // attr.Filesで指定されたFDは閉じない
		if n == fd {
			return
		}
	}
	RawSyscall(SYS_CLOSE, uintptr(n), 0, 0) // それ以外は閉じる
}
```

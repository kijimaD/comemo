# [インデックス 27134] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/link`）におけるシンボル管理の最適化に関するものです。具体的には、シンボルを検索する際のデータ構造を変更し、単一バージョンを持つシンボルに対しては文字列キーのマップを使用することで、リンク時間を約3%削減しています。

## 変更の背景

Go言語のリンカは、プログラムを構成する様々なオブジェクトファイルやライブラリからシンボル（関数、変数など）を解決し、最終的な実行可能ファイルを生成する重要な役割を担っています。このプロセスにおいて、リンカは大量のシンボル情報を効率的に管理し、検索する必要があります。

従来のリンカでは、シンボル名とそのバージョンを組み合わせた`symVer`構造体をキーとする単一のマップ（`Hash map[symVer]*LSym`）を使用してシンボルを管理していました。しかし、多くのシンボルは実際には単一のバージョンしか持たないため、`symVer`構造体全体をキーとして使用することは、不要なオーバーヘッドを生じさせる可能性がありました。

このコミットの背景には、リンカのパフォーマンスを向上させたいという目的があります。特に、大規模なGoプログラムのビルド時間において、リンカの処理速度は全体のビルド時間に大きく影響します。シンボル検索の効率化は、このビルド時間を短縮するための重要な手段の一つです。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラによって生成された複数のオブジェクトファイル（機械語コードとシンボル情報を含む）やライブラリを結合し、実行可能なプログラムを生成するツールです。主な役割は以下の通りです。
*   **シンボル解決**: あるオブジェクトファイルで定義された関数や変数を、別のオブジェクトファイルから参照できるように、それらのアドレスを解決します。
*   **再配置**: オブジェクトファイル内のアドレスが、最終的な実行可能ファイル内のどこに配置されるかに応じて調整されます。
*   **ライブラリの結合**: 静的ライブラリや動的ライブラリをプログラムに結合します。

### シンボル (Symbol)
プログラミングにおいて、シンボルとは関数名、変数名、ラベルなど、プログラム内の特定のエンティティを識別するための名前です。リンカはこれらのシンボルとそのアドレス情報を管理し、参照を解決します。

### シンボルバージョン (Symbol Version)
Go言語のリンカでは、同じ名前のシンボルが異なるバージョンを持つことがあります。これは、例えば異なるコンパイルオプションやGoのバージョンによって、同じ関数名でも内部的な実装が異なる場合に発生する可能性があります。リンカは、正しいバージョンのシンボルを選択するために、シンボル名だけでなくバージョン情報も考慮する必要があります。

### マップ (Map) / ハッシュテーブル (Hash Table)
マップ（Go言語では`map`型）は、キーと値のペアを格納するデータ構造で、キーを使って高速に値を取得できます。内部的にはハッシュテーブルとして実装されていることが多く、キーのハッシュ値を計算してメモリ上の位置を特定します。キーの比較コストは、マップのパフォーマンスに直接影響します。文字列をキーとするマップは、構造体をキーとするマップよりも一般的に比較コストが低い傾向があります。

### `symVer`構造体
このコミット以前のGoリンカでは、シンボル名（`string`）とバージョン（`int`）を組み合わせた`symVer`という構造体をマップのキーとして使用していました。

```go
type symVer struct {
    symb string
    v    int
}
```
この構造体をキーとして使用すると、マップのルックアップ時に毎回`symb`と`v`の両方を比較する必要があり、特に`symb`が長い文字列の場合、比較コストが高くなる可能性があります。

## 技術的詳細

このコミットの核心は、リンカがシンボルを検索する際のデータ構造を最適化し、シンボル検索の平均的なケースを高速化することにあります。

従来のリンカでは、`Link`構造体内に`Hash map[symVer]*LSym`という単一のマップを持っていました。これは、シンボル名とバージョンを組み合わせた`symVer`構造体をキーとして、`LSym`（リンカシンボル）へのポインタを値として保持していました。

変更後、`Link`構造体は以下の2つのマップを持つようになりました。

1.  `HashName map[string]*LSym`: シンボル名をキーとするマップ。ほとんどのシンボルは単一バージョンであるという仮定に基づき、まずこのマップで検索を行います。文字列キーは`symVer`構造体キーよりも比較コストが低いため、高速なルックアップが期待できます。
2.  `HashVersion map[symVer]*LSym`: `symVer`構造体をキーとするマップ。これは、同じ名前で複数のバージョンを持つシンボル（衝突が発生した場合）を格納するための「スピルオーバー（spill over）」マップとして機能します。

シンボルを検索する`_lookup`関数は、以下のように動作が変更されました。

*   まず、`HashName`マップをシンボル名（`symb string`）で検索します。
*   もし`HashName`にエントリが見つかった場合、そのシンボルのバージョン（`s.Version`）が要求されたバージョン（`v`）と一致するかを確認します。
    *   一致すれば、そのシンボルを返します。
    *   一致しない場合（つまり、同じ名前だが異なるバージョンのシンボルが存在する場合）、`HashVersion`マップを`symVer{symb, v}`をキーとして検索します。
*   `HashName`にエントリが見つからなかった場合、または`HashVersion`でシンボルが見つからなかった場合、そして`creat`フラグが設定されていれば、新しいシンボルを作成します。
    *   新しいシンボルを作成する際、もし`HashName`に同じ名前のシンボルが既に存在していた場合（`exist`がtrueの場合）、新しいシンボルは`HashVersion`に追加されます。
    *   そうでなければ（`HashName`に同じ名前のシンボルがまだ存在しない場合）、新しいシンボルは`HashName`に追加されます。

このアプローチにより、「ほとんどのシンボルは単一バージョンである」という経験則を活用し、より高速な文字列キーによる検索を優先することで、リンカ全体のパフォーマンスが向上します。複数のバージョンを持つ稀なケースは、追加の`HashVersion`マップで処理されますが、これは頻繁にアクセスされないため、全体的なオーバーヘッドは最小限に抑えられます。

## コアとなるコードの解説

このコミットの主要な変更は、`Link`構造体内のシンボル管理方法と、それに伴う`_lookup`関数の実装です。

### `Link`構造体の変更

- **`Hash map[symVer]*LSym` の削除**: 従来の単一マップが廃止されました。このマップは`symVer`構造体（シンボル名とバージョン）をキーとしていたため、キーの比較コストが高くなる可能性がありました。
- **`HashName map[string]*LSym` の追加**: シンボル名（`string`）のみをキーとする新しいマップです。Goのリンカが扱うシンボルの大部分はバージョンが1つしかないという前提に基づいています。文字列キーは`symVer`構造体キーよりもハッシュ計算や比較が高速であるため、このマップでの検索は効率的です。
- **`HashVersion map[symVer]*LSym` の追加**: `symVer`構造体をキーとするマップで、`HashName`で名前の衝突が発生した場合（つまり、同じ名前で異なるバージョンを持つシンボルが存在する場合）の「スピルオーバー」領域として機能します。これにより、稀なケースである複数バージョンシンボルの管理も引き続き行えます。

### `_lookup`関数の変更

`_lookup`関数は、指定されたシンボル名とバージョンに対応する`LSym`（リンカシンボル）を検索または作成する役割を担います。

1.  **一次検索 (`HashName`)**:
    ```go
    s, exist := ctxt.HashName[symb]
    ```
    まず、シンボル名`symb`を使って`HashName`マップを検索します。`exist`は、その名前のシンボルが`HashName`に存在したかどうかを示します。

2.  **バージョンチェックと二次検索 (`HashVersion`)**:
    ```go
    if s != nil {
        if int(s.Version) == v {
            return s
        }
        s = ctxt.HashVersion[symVer{symb, v}]
        if s != nil {
            return s
        }
    }
    ```
    `HashName`でシンボル`s`が見つかった場合、そのシンボルのバージョン`s.Version`が要求されたバージョン`v`と一致するかを確認します。
    -   一致すれば、それが目的のシンボルなので、すぐに返します。
    -   一致しない場合、これは同じ名前で異なるバージョンのシンボルが存在するケースです。この場合、`HashVersion`マップを`symVer{symb, v}`をキーとして検索し、目的のシンボルを探します。見つかればそれを返します。

3.  **シンボルの新規作成**:
    ```go
    s = linknewsym(ctxt, symb, v)
    s.Extname = s.Name
    if exist {
        ctxt.HashVersion[symVer{symb, v}] = s
    } else {
        ctxt.HashName[symb] = s
    }
    return s
    ```
    もし既存のマップでシンボルが見つからず、かつ`creat`フラグが設定されている場合、新しいシンボル`s`が作成されます。
    -   `exist`が`true`の場合（つまり、`HashName`に同じ名前のシンボルが既に存在していたが、バージョンが異なっていた場合）、新しいシンボルは`HashVersion`に追加されます。
    -   `exist`が`false`の場合（つまり、`HashName`に同じ名前のシンボルがまだ存在しなかった場合）、新しいシンボルは`HashName`に追加されます。

このロジックにより、ほとんどのシンボル検索は`HashName`での高速なルックアップで完結し、リンカの全体的なパフォーマンスが向上します。

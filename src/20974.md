## 変更の背景

このコミットは、GoランタイムのPowerPC 64-bitアーキテクチャ向けアセンブリコード `src/runtime/asm_power64x.s` に誤って混入した構文エラーを修正するものです。コミットメッセージによると、このエラーは、コミットの作者が別の問題（CL 169790043で提出された変更）の修正に集中していた際に、不注意で発生した「スリップイン」したものであり、意図的な変更ではなかったことが示唆されています。

Go言語のランタイムは、ガベージコレクション、スケジューリング、プリエンプションなど、言語の低レベルな動作を管理する重要な部分です。これらの機能の一部は、特定のアーキテクチャの特性を最大限に活用するため、アセンブリ言語で記述されています。PowerPC 64-bitアーキテクチャは、IBMが開発したRISCプロセッサアーキテクチャであり、サーバー、組み込みシステム、ゲーム機など、幅広い分野で使用されています。GoランタイムがPowerPC 64-bitをサポートするためには、このアーキテクチャに特化したアセンブリコードが必要となります。

このような低レベルのアセンブリコードにおける構文エラーは、コンパイルエラーを引き起こし、GoプログラムがPowerPC 64-bit環境で正しくビルドまたは実行できない原因となります。そのため、この修正は、GoランタイムのPowerPC 64-bitサポートの安定性と正確性を確保するために不可欠でした。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する一連のライブラリとシステムです。これには、ガベージコレクタ、ゴルーチン（軽量スレッド）スケジューラ、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、コンパイル時にランタイムとリンクされ、自己完結型のバイナリを生成します。ランタイムの一部は、パフォーマンスや特定のハードウェア機能へのアクセスを最適化するために、C言語やアセンブリ言語で記述されています。

### アセンブリ言語

アセンブリ言語は、特定のコンピュータアーキテクチャの機械語命令と1対1で対応する低レベルのプログラミング言語です。人間が読めるニーモニック（例: `MOVB`, `CMP`, `BEQ`）を使用して命令を表現し、レジスタやメモリへの直接的なアクセスを可能にします。アセンブリ言語は、オペレーティングシステムカーネル、デバイスドライバ、高性能なライブラリなど、ハードウェアに密接に連携する必要がある場面や、極限のパフォーマンスが求められる場面で利用されます。Goランタイムも、特定のアーキテクチャに依存する部分（例: コンテキストスイッチ、スタック管理）でアセンブリ言語を使用します。

### PowerPC 64-bitアーキテクチャ

PowerPC (Performance Optimization With Enhanced RISC – Performance Computing) は、IBM、Apple、Motorolaによって開発されたRISC (Reduced Instruction Set Computer) プロセッサアーキテクチャです。64-bit版は、より大きなメモリアドレス空間とデータ処理能力を提供します。PowerPCアーキテクチャは、汎用レジスタ、ロード/ストアアーキテクチャ、固定長命令などの特徴を持ちます。

### Goのアセンブリ構文

Go言語は、独自の（Plan 9アセンブラに由来する）アセンブリ構文を使用します。これは、一般的なGAS (GNU Assembler) 構文やIntel構文とは異なります。Goのアセンブリ構文では、レジスタは `R0`, `R1` のように表記され、メモリ参照は `offset(base_register)` の形式を取ります。また、即値（リテラル値）は `$` 記号を前置して表現されます（例: `$0`）。

### フレームポインタ (FP)

フレームポインタ (FP) は、関数呼び出しスタックフレームの基点を指すレジスタです。関数が呼び出されると、その関数のローカル変数、引数、およびその他のコンテキスト情報がスタック上にプッシュされ、スタックフレームが形成されます。FPレジスタは、このスタックフレーム内の特定のデータ（例えば、引数や戻り値）にアクセスするための基準点として使用されます。`ret+24(FP)` のような表記は、FPレジスタが指すアドレスから24バイトオフセットした位置にあるメモリを指し、これは通常、関数の戻り値が格納される場所や、特定の引数にアクセスする際に使用されます。

## 技術的詳細

このコミットの技術的詳細は、PowerPC 64-bitアセンブリにおける `MOVB` 命令の正しい使用法に集約されます。

元のコード行は以下の通りでした。
`MOVB $0, ret+24(FP)`

ここで、`MOVB` は「Move Byte」命令であり、1バイトのデータを移動するために使用されます。
*   `$0` は即値 `0` を表します。
*   `ret+24(FP)` は、フレームポインタ (FP) から24バイトオフセットしたメモリ位置を指します。

この命令は、即値 `0` を直接メモリ位置 `ret+24(FP)` に1バイトとして書き込もうとしています。しかし、PowerPCアーキテクチャのアセンブリ命令セット、特にGoのアセンブラが解釈する構文では、`MOVB` 命令のソースオペランドとして即値を直接メモリに書き込む形式はサポートされていないか、構文的に誤りである可能性が高いです。多くのRISCアーキテクチャでは、即値をメモリに書き込む場合、まず即値をレジスタにロードし、そのレジスタの内容をメモリにストアするという2段階の操作が必要になります。

修正後のコード行は以下の通りです。
`MOVB R0, ret+24(FP)`

ここで、`R0` はPowerPC 64-bitアーキテクチャの汎用レジスタの一つです。PowerPCアーキテクチャでは、レジスタ `R0` は特別な意味を持つことがあり、多くの場合、その値は常に `0` であると保証されています（ゼロレジスタとして機能する場合）。もし `R0` がゼロレジスタとして機能する場合、この命令はレジスタ `R0` の内容（つまり `0`）をメモリ位置 `ret+24(FP)` に1バイトとして書き込むことになります。

この修正は、論理的な動作（メモリ位置に `0` を書き込む）を変えることなく、GoアセンブラがPowerPC 64-bit向けに期待する正しい構文に準拠するように変更したものです。つまり、即値 `0` を直接メモリに移動する代わりに、`0` の値を持つことが保証されているレジスタ `R0` を介してメモリに移動することで、構文エラーを解消しています。これは、アセンブリ言語の命令セットアーキテクチャ (ISA) の制約と、Goアセンブラの特定の構文規則に合わせた典型的な修正パターンです。

## コアとなるコードの変更箇所

変更は `src/runtime/asm_power64x.s` ファイルの1箇所のみです。

```diff
--- a/src/runtime/asm_power64x.s
+++ b/src/runtime/asm_power64x.s
@@ -711,7 +711,7 @@ test:
 	CMP	R6, R7
 	BEQ	loop
 
-\tMOVB\t$0, ret+24(FP)\n+\tMOVB\tR0, ret+24(FP)
 	RETURN
 
 // eqstring tests whether two strings are equal.
```

具体的には、712行目の `MOVB` 命令のソースオペランドが `$0` (即値0) から `R0` (レジスタR0) に変更されています。

## コアとなるコードの解説

変更された行は、`test:` というラベルで始まるアセンブリコードブロック内にあります。このブロックは、おそらく何らかのテストまたは条件分岐のロジックの一部であり、`CMP` (Compare) および `BEQ` (Branch if Equal) 命令に続いて実行されます。

元のコード `MOVB $0, ret+24(FP)` は、`test` ブロックの実行パスにおいて、フレームポインタ (FP) から24バイトオフセットしたメモリ位置にバイト値 `0` を書き込もうとしていました。このメモリ位置は、関数の戻り値や特定のローカル変数に関連している可能性が高いです。

しかし、GoアセンブラのPowerPC 64-bit向け構文では、即値を直接メモリに移動する `MOVB` 命令の形式は許可されていませんでした。このため、コンパイル時に構文エラーが発生していました。

修正後のコード `MOVB R0, ret+24(FP)` は、この構文エラーを解消します。PowerPCアーキテクチャにおいて、レジスタ `R0` は通常、値 `0` を保持する特別なレジスタとして扱われます。したがって、`R0` の内容をメモリに移動することは、結果的に `0` をメモリに書き込むことと同じ論理的効果を持ちます。この変更により、Goアセンブラは命令を正しく解釈し、コンパイルが成功するようになります。

この修正は、GoランタイムのPowerPC 64-bitポートにおける低レベルなアセンブリコードの正確性を保証し、コンパイルプロセスを安定させる上で重要です。

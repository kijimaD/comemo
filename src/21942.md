# [インデックス 21942] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるC言語からGo言語への翻訳作業を円滑に進めるための、様々なマイナーな調整とクリーンアップを目的としています。具体的には、C言語特有のイディオムをGo言語のコードベースに適合させるための変更や、未使用コードの削除、型の一貫性の確保などが行われています。これらの変更は、Go 1.5でのコンパイラのセルフホスト化（C言語で書かれたコンパイラをGo言語で書き直すこと）に向けた準備の一環です。

## 元コミット内容

このコミットは、GoコンパイラのC言語ソースコードをGo言語に翻訳するプロセスを容易にするための、一連の小規模ながら重要な調整を含んでいます。主な変更点は以下の通りです。

*   **三項演算子 `? :` の削除**: C言語特有の三項演算子を、Go言語の条件分岐に書き換えています。
*   **変数名 `len` のリネーム**: Go言語の組み込み関数 `len` との衝突を避けるため、変数名を変更しています。
*   **`goto` 文の書き換え**: C言語の `goto` 文を、Go言語でより自然なネストされた `switch` 文に変換しています。また、`goto` のターゲットがGo言語のスコープ規則に適合するように移動されています。
*   **`anyregalloc` の戻り値の型の一貫性**: `anyregalloc` 関数の戻り値の型が `int` と `int32` で混在していたのを `int` に統一しています。
*   **未使用変数 `nr` の削除**: `agen` 関数内の未使用変数 `nr` を削除しています。
*   **生成された `builtin1.c` への適切なヘッダーの追加**: `builtin1.c` ファイルに不足していたヘッダーファイル (`u.h`, `libc.h`, `go.h`) を追加しています。
*   **`%E` フォーマットの調整**: `printf` 系関数で使用される `%E` フォーマットにおいて、`%-6E` や `%2E` のような奇妙なサイズ指定を避けるように変更しています。
*   **`gengcmask` 引数の変更**: `gengcmask` 関数の `uint8[16]` 型の引数を `uint8*` に変更しています。これは `c2go` ツールによって診断されたもので、実際の意味では配列ではなかったためです。
*   **`#ifdef XXX` のコメントブロック化**: `5g/peep.c` 内の `#ifdef XXX` ディレクティブをコメントブロックに置き換えています。
*   **`FAIL` マクロの展開と削除**: `5g` コンパイラで使用されていた `FAIL` マクロを、その実体である `if(debug['P']) print(...)` と `return 0;` に展開し、マクロ自体を削除しています。
*   **`noimpl` マクロの展開と削除**: `9g` コンパイラで使用されていた `noimpl` マクロを、その実体である `fatal` 関数呼び出しに展開し、マクロ自体を削除しています。
*   **`regalloc` エラー出力の変更**: `8g` コンパイラにおける `regalloc` エラーの出力を、`fprint(2, ...)` (標準エラー出力) から `print(...)` (標準出力) に変更しています。これは、コンパイラ全体で `fprint(2, ...)` の唯一の使用箇所であったため、統一性を図るものです。

これらの変更は、最終的な出力バイナリに影響を与えず、ビット単位で同一の出力を維持していることが確認されています。

## 変更の背景

このコミットの主要な背景は、Go言語のコンパイラおよびツールチェインをC言語からGo言語自身で書き直す「セルフホスト化」プロジェクト、通称「C to Go translation」です。Go言語の初期バージョンでは、コンパイラやランタイムの一部がC言語で書かれていました。しかし、Go言語の成熟に伴い、ツールチェイン全体をGo言語で記述することで、開発の効率化、保守性の向上、そしてGo言語の機能（例えば、ガベージコレクション）をコンパイラ開発自体にも適用できるといったメリットが期待されました。

このセルフホスト化はGo 1.5で実現されましたが、その準備として、C言語で書かれた既存のコードベースをGo言語に変換しやすい形に整形する必要がありました。このコミットで行われている変更は、まさにそのためのものです。

*   **C言語特有のイディオムの排除**: 三項演算子 (`? :`) や `goto` 文はC言語では一般的ですが、Go言語では推奨されません。これらをGo言語の構造（`if/else` や `switch`）に書き換えることで、自動翻訳ツール（`c2go` など）が処理しやすくなり、また手動での変換作業も簡素化されます。
*   **マクロの展開**: C言語のプリプロセッサマクロは強力ですが、Go言語には同等の機能がありません。マクロをその実体コードに展開することで、Go言語への変換時にマクロの解釈という複雑なステップを回避できます。
*   **型の一貫性**: `anyregalloc` の戻り値の型のように、C言語では許容される暗黙的な型変換や型の不一致が、Go言語では厳密にチェックされます。事前に型を統一することで、翻訳後のGoコードでの型エラーを防ぎます。
*   **未使用コードのクリーンアップ**: 未使用の変数や `#ifdef` で囲まれたデッドコードを削除することで、翻訳対象のコード量を減らし、複雑性を低減します。

このコミットは、Go 1.5のリリース（2015年8月）に先立つ2015年2月に行われており、セルフホスト化に向けた重要な中間ステップであったことが伺えます。

## 前提知識の解説

*   **Goコンパイラ (`gc`)**: Go言語の公式コンパイラです。元々はC言語で書かれていましたが、Go 1.5でGo言語自身で書き直されました。
*   **`5g`, `6g`, `8g`, `9g`**: Go 1.5以前のGoコンパイラは、ターゲットアーキテクチャごとに異なるバイナリを持っていました。
    *   `5g`: ARMアーキテクチャ向け
    *   `6g`: `amd64` (x86-64) アーキテクチャ向け
    *   `8g`: `386` (x86-32) アーキテクチャ向け
    *   `9g`: このコミットでは言及されていますが、`5g`, `6g`, `8g` のような明確なアーキテクチャ固有のコンパイラ名としては一般的ではありません。しかし、Goコンパイラのソースコード内では、特定のアーキテクチャに関連するファイル名やディレクトリ名として `9g` が使われることがありました。
    Go 1.5以降は、これらのコンパイラは単一の `compile` ツールに統合され、`go tool compile` コマンドで任意のアーキテクチャ向けにコンパイルできるようになりました。
*   **`peep.c`**: コンパイラの「peephole optimizer（ピーフホール最適化）」に関連するファイルです。ピーフホール最適化は、生成されたアセンブリコードの小さな連続した命令列（ピーフホール）を調べて、より効率的な命令列に置き換える最適化手法です。
*   **`agen`, `bgen`, `cgen`**: Goコンパイラのコード生成フェーズに関連する関数群です。
    *   `agen`: アドレス生成 (Address Generation)
    *   `bgen`: 論理式生成 (Boolean Generation)
    *   `cgen`: コード生成 (Code Generation)
*   **`goto` 文**: C言語における無条件ジャンプ命令です。コードの可読性を損なう可能性があるため、現代のプログラミングでは使用が推奨されないことが多いですが、コンパイラのような低レベルなコードでは効率のために使われることがあります。Go言語でも `goto` は存在しますが、その使用には厳密な制限があります（例えば、同じ関数内のラベルにしかジャンプできない、変数のスコープを飛び越えられないなど）。
*   **三項演算子 (`? :`)**: C言語における `条件 ? 真の場合の値 : 偽の場合の値` という形式の条件演算子です。Go言語には同等の構文はありません。
*   **マクロ (`#define`)**: C言語のプリプロセッサ機能で、コンパイル前にテキスト置換を行います。`FAIL` や `noimpl` のようなマクロは、共通のコードパターンを簡潔に記述するために使われます。
*   **`fprint(2, ...)`**: C言語の `fprintf` 関数で、ファイルディスクリプタ `2` (標準エラー出力 `stderr`) に出力します。`print(...)` は通常、標準出力 `stdout` に出力します。

## 技術的詳細

このコミットで行われた各変更は、C言語のコードをGo言語のコードに変換する際の課題を解決するための具体的なアプローチを示しています。

1.  **`? :` の削除**:
    *   C言語の三項演算子は簡潔ですが、Go言語には直接的な同等物がないため、`if/else` 文に展開する必要があります。
    *   例: `x = cond ? a : b;` は `if cond { x = a } else { x = b }` に変換されます。
    *   これにより、翻訳ツールがGo言語の構文に沿ったコードを生成しやすくなります。

2.  **変数名 `len` のリネーム**:
    *   Go言語には `len` という組み込み関数があり、スライス、配列、文字列、マップ、チャネルの長さを返すために広く使われます。
    *   C言語のコードで `len` という名前の変数が使われていると、Go言語に翻訳した際に組み込み関数 `len` と名前が衝突し、コンパイルエラーや意図しない動作を引き起こす可能性があります。
    *   これを避けるため、変数名を `n` など、他の名前に変更しています。

3.  **`goto` 文の書き換えとターゲットの移動**:
    *   C言語の `goto` は柔軟性が高く、任意のラベルにジャンプできます。しかし、Go言語の `goto` は、ジャンプ先のラベルが現在のブロックまたは外側のブロックに存在し、かつジャンプによって変数の初期化をスキップしないという制約があります。
    *   このコミットでは、`goto` をネストされた `switch` 文に書き換えることで、制御フローをより構造化された形にし、Go言語の `goto` の制約に適合させています。
    *   `goto` ターゲットの移動は、Go言語のスコープ規則に合わせるためのものです。例えば、`goto` のターゲットが、ジャンプ元から到達できないスコープ内にあった場合、Go言語ではエラーになります。これを修正するために、ターゲットを適切なスコープに移動しています。

4.  **`anyregalloc` の戻り値の型の一貫性**:
    *   `anyregalloc` はレジスタ割り当てに関連する関数で、C言語では `int` と `int32` が混在して使われていました。C言語では `int` のサイズが環境によって異なることがありますが、Go言語では `int` は通常32ビットまたは64ビットのプラットフォーム依存の整数型であり、`int32` は常に32ビットです。
    *   Go言語への翻訳時に型の不一致による警告やエラーを避けるため、戻り値の型を `int` に統一しています。これは、Go言語の型システムがC言語よりも厳格であるため、翻訳前にこのような不整合を解消しておくことが重要だからです。

5.  **未使用変数 `nr` の削除**:
    *   `agen` 関数内で `nr` という変数が宣言されていましたが、コード中で使用されていませんでした。
    *   未使用の変数を削除することで、コードの冗長性を減らし、翻訳対象のコード量を削減します。これは、自動翻訳ツールの処理を簡素化し、生成されるGoコードの品質を向上させるのに役立ちます。

6.  **`builtin1.c` への適切なヘッダーの追加**:
    *   `builtin1.c` は、Goの組み込み関数や型に関する情報を含む自動生成されるCファイルです。
    *   このファイルが依存する `u.h`, `libc.h`, `go.h` といったヘッダーファイルが不足していたため、コンパイルエラーが発生する可能性がありました。
    *   これらを追加することで、生成されるCコードが正しくコンパイルされるようになり、Go言語への翻訳プロセスもスムーズになります。

7.  **`%E` フォーマットの調整**:
    *   `printf` 系関数における `%E` フォーマットは浮動小数点数を指数表記で出力するためのものですが、`%-6E` や `%2E` のような奇妙な幅指定は、C言語の特定のコンパイラや環境で予期せぬ動作を引き起こす可能性があります。
    *   Go言語の `fmt` パッケージにはC言語の `printf` とは異なるフォーマット指定子があり、このような特殊な指定はGo言語の `fmt` に直接変換できない場合があります。
    *   事前にCコード側で一般的なフォーマットに修正しておくことで、Go言語への翻訳時の複雑性を軽減します。

8.  **`gengcmask` 引数の変更**:
    *   `gengcmask` 関数はガベージコレクションのビットマスクを生成するためのものです。元のCコードでは `uint8[16]` (サイズ16の `uint8` 配列) として引数が渡されていましたが、コメントには「(diagnosed by c2go; not an array in any real sense)」とあり、これは実際には固定サイズの配列としてではなく、ポインタとして扱われるべきであったことを示唆しています。
    *   C言語では配列を関数に渡すと、実質的にその先頭要素へのポインタとして扱われます。`uint8*` に変更することで、この関数の意図と実際の使用方法をより明確にし、Go言語のポインタやスライスへの変換を容易にしています。

9.  **`#ifdef XXX` のコメントブロック化**:
    *   C言語の `#ifdef` プリプロセッサディレクティブは、条件付きコンパイルに使用されます。`#ifdef XXX` は、`XXX` が定義されている場合にのみコードブロックをコンパイルします。
    *   このコミットでは、`#ifdef NOTDEF` のような、おそらくデバッグや一時的な目的で使われ、現在は無効化されているコードブロックを、C言語のコメントブロック (`/* ... */`) に置き換えています。
    *   これにより、プリプロセッサの処理をGo言語への翻訳前に完了させ、Go言語のコードにプリプロセッサディレクティブが残らないようにしています。Go言語にはプリプロセッサがないため、これは翻訳の前提条件となります。

10. **`FAIL` および `noimpl` マクロの展開と削除**:
    *   `FAIL` と `noimpl` は、それぞれエラー発生時や未実装機能の呼び出し時に使用されるマクロでした。
    *   これらのマクロを、その実体である `if(debug['P']) print(...)` や `fatal(...)` の呼び出しに直接展開することで、マクロの抽象化レイヤーを排除しています。
    *   これにより、Go言語への翻訳時にマクロの定義を解析する必要がなくなり、コードがより直接的で理解しやすくなります。

11. **`regalloc` エラー出力の変更**:
    *   `8g` コンパイラにおける `regalloc` (レジスタ割り当て) エラーの出力が `fprint(2, ...)` (標準エラー出力) を使用していました。コミットメッセージには「(only use of fprint(2, ...) in all compilers)」とあり、これがGoコンパイラ全体で `fprint(2, ...)` の唯一の使用箇所であったことを示しています。
    *   これを `print(...)` (標準出力) に変更することで、コンパイラ全体でのエラー出力方法の一貫性を高めています。Go言語の `fmt` パッケージは通常、標準出力に書き込むため、この変更はGo言語への翻訳後のコードの動作をより予測可能にします。

これらの変更は、GoコンパイラのC言語コードベースを、Go言語のセマンティクスと構文により適合させるための「前処理」として機能しています。これにより、自動翻訳ツールや手動でのリファクタリングがより効率的かつ正確に行えるようになり、Go 1.5でのセルフホスト化の成功に貢献しました。

## コアとなるコードの変更箇所

このコミットでは多数のファイルが変更されていますが、特にC言語特有のイディオムをGo言語に適合させるための変更が顕著です。

### 1. `goto` 文の書き換えとネストされた `switch` への変換 (例: `src/cmd/5g/cgen.c`)

元のコードでは `goto caseor;` や `goto caseand;` といった `goto` が使われていました。

```c
// src/cmd/5g/cgen.c (変更前)
 	case OANDAND:
 		if(!true)
 			goto caseor;

 	caseand:
 		p1 = gbranch(AB, T, 0);
 		p2 = gbranch(AB, T, 0);
 		patch(p1, pc);
 		bgen(n->left, !true, -likely, p2);
 		bgen(n->right, !true, -likely, p2);
 		p1 = gbranch(AB, T, 0);
 		patch(p1, to);
 		patch(p2, pc);
 		goto ret;

 	case OOROR:
 		if(!true)
 			goto caseand;

 	caseor:
 		bgen(n->left, true, likely, to);
 		bgen(n->right, true, likely, to);
 		goto ret;
```

変更後、`goto` は削除され、`if` とネストされた `switch` に置き換えられています。

```c
// src/cmd/5g/cgen.c (変更後)
 	case OANDAND:
 	case OOROR:
 		if((n->op == OANDAND) == true) {
 			p1 = gbranch(AJMP, T, 0);
 			p2 = gbranch(AJMP, T, 0);
 			patch(p1, pc);
 			bgen(n->left, !true, -likely, p2);
 			bgen(n->right, !true, -likely, p2);
 			p1 = gbranch(AJMP, T, 0);
 			patch(p1, to);
 			patch(p2, pc);
 		} else {
 			bgen(n->left, true, likely, to);
 			bgen(n->right, true, likely, to);
 		}
 		goto ret;
```

### 2. `anyregalloc` の戻り値の型の一貫性 (例: `src/cmd/5g/gsubr.c`)

`anyregalloc` 関数の戻り値の型が `int32` から `int` に変更されています。

```c
// src/cmd/5g/gsubr.c (変更前)
int32
anyregalloc(void)
{
	int i, j;
```

```c
// src/cmd/5g/gsubr.c (変更後)
int
anyregalloc(void)
{
	int i, j;
```

### 3. `FAIL` マクロの展開と削除 (例: `src/cmd/5g/peep.c`)

`FAIL` マクロの定義が削除され、その使用箇所が直接的な `if` 文と `print`、`return 0;` に置き換えられています。

```c
// src/cmd/5g/peep.c (変更前)
#define FAIL(msg) { if(debug['P']) print("	%s; FAILURE\n", msg); return 0; }
/*c2go void FAIL(char*); */

int
shiftprop(Flow *r)
{
	...
	if(p->to.type != TYPE_REG)
		FAIL("BOTCH: result not reg");
	...
```

```c
// src/cmd/5g/peep.c (変更後)
int
shiftprop(Flow *r)
{
	...
	if(p->to.type != TYPE_REG) {
		if(debug['P'])
			print("	BOTCH: result not reg; FAILURE\n");
		return 0;
	}
	...
```

### 4. `noimpl` マクロの展開と削除 (例: `src/cmd/9g/gsubr.c`)

`noimpl` マクロの定義が削除され、その使用箇所が `fatal` 関数呼び出しに置き換えられています。

```c
// src/cmd/9g/gg.h (変更前)
// TODO(minux): Remove when no longer used.
#define noimpl sysfatal("%s not implemented (%s:%d).", __func__, __FILE__, __LINE__)

// src/cmd/9g/gsubr.c (変更前)
	if(n->xoffset != (int32)n->xoffset) {
		// TODO(minux): offset too large, move into R31 and add to R31 instead.
		// this is used only in test/fixedbugs/issue6036.go.
		print("offset too large: %N\n", n);
		noimpl;
		a = *n;
		a.op = OREGISTER;
		a.type = types[tptr];
```


## コアとなるコードの解説

### 1. `goto` 文の書き換えとネストされた `switch` への変換

`src/cmd/5g/cgen.c` の変更は、C言語の `goto` 文をGo言語の構造に適合させる典型的な例です。元のコードでは、`OANDAND` (論理AND) と `OOROR` (論理OR) の処理において、共通のロジックにジャンプするために `goto caseor;` や `goto caseand;` が使われていました。これはC言語では一般的なパターンですが、Go言語の `goto` はより制限的であり、このような自由なジャンプは許されません。

変更後のコードでは、`OANDAND` と `OOROR` の両方の `case` が結合され、内部で `if((n->op == OANDAND) == true)` という条件分岐が導入されています。これにより、元の `goto` が実現していたロジックが、Go言語で自然な `if/else` 構造に変換されています。このリファクタリングは、コードの可読性を向上させるだけでなく、自動翻訳ツールがC言語の `goto` の複雑な制御フローをGo言語の構造にマッピングする際の課題を軽減します。

### 2. `anyregalloc` の戻り値の型の一貫性

`src/cmd/5g/gsubr.c` における `anyregalloc` 関数の戻り値の型変更は、Go言語の厳格な型システムへの適応を示しています。C言語では `int` と `int32` の間で暗黙的な型変換が許容されることが多く、特に `int` のサイズがプラットフォームによって異なるため、このような混在は問題を引き起こす可能性があります。Go言語では、`int` はプラットフォームのネイティブな整数型（通常32ビットまたは64ビット）であり、`int32` は常に32ビットの整数型です。

この変更により、`anyregalloc` が常に `int` を返すことが保証され、Go言語への翻訳時に型不一致によるコンパイルエラーや予期せぬ動作を防ぎます。これは、Go言語のコードがより堅牢で予測可能になるための重要なステップです。

### 3. `FAIL` および `noimpl` マクロの展開と削除

`src/cmd/5g/peep.c` の `FAIL` マクロと `src/cmd/9g/gsubr.c` の `noimpl` マクロの変更は、C言語のプリプロセッサマクロをGo言語の直接的な関数呼び出しに置き換えるプロセスを示しています。C言語のマクロはコンパイル前にテキスト置換されるため、デバッガでステップ実行するのが難しかったり、予期せぬ副作用を引き起こしたりすることがあります。Go言語にはプリプロセッサがないため、マクロはGo言語の関数やコードブロックに変換する必要があります。

`FAIL` マクロは、デバッグモードでのみメッセージを出力し、その後関数から `return 0;` するというロジックを持っていました。これを直接 `if` 文と `print`、`return 0;` に展開することで、マクロの抽象化が取り除かれ、コードの動作がより明確になります。

同様に、`noimpl` マクロは未実装のコードパスに到達した場合に `sysfatal` (システムエラーで終了) を呼び出すものでした。これを直接 `fatal` 関数呼び出しに置き換えることで、Go言語への翻訳時にマクロの解釈というステップが不要になります。

これらの変更は、C言語のプリプロセッサに依存するコードをGo言語のセマンティクスに適合させ、翻訳後のコードの可読性と保守性を向上させる上で不可欠です。

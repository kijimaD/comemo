# [インデックス 24114] ファイルの概要

このコミットは、GoランタイムがC言語と共有ライブラリ（c-shared）または静的アーカイブ（c-archive）としてビルドされた際に、致命的なエラーやパニックが発生した場合の挙動を変更するものです。具体的には、プロセス全体を突然終了させる（exit）のではなく、より明確な異常終了シグナルである`abort`を呼び出すように修正されています。これにより、Goコードが外部のC/C++アプリケーションに組み込まれている場合のクラッシュレポートの信頼性が向上します。

    runtime: abort on fatal errors and panics in c-shared and c-archive modes
    
    The default behaviour for fatal errors and runtime panics is to dump
    the goroutine stack traces and exit with code 2. However, when the process is
    owned by foreign code, it is suprising and inappropriate to suddenly exit
    the whole process, even on fatal errors. Instead, re-use the crash behaviour
    from GOTRACEBACK=crash and abort.
    
    The motivating use case is issue #11382, where an Android crash reporter
    is confused by an exiting process, but I believe the aborting behaviour
    is appropriate for all cases where Go does not own the process.
    
    The change is simple and contained and will enable reliable crash reporting
    for Android apps in Go 1.5, but I'll leave it to others to judge whether it
    is too late for Go 1.5.

## 元コミット内容

Goランタイムが致命的なエラーやパニックに遭遇した場合、デフォルトではゴルーチンのスタックトレースをダンプし、終了コード2でプロセスを終了します。しかし、GoコードがC言語の共有ライブラリ（c-shared）や静的アーカイブ（c-archive）としてビルドされ、外部のC/C++コードによってプロセスが所有されている場合、Goランタイムが突然プロセス全体を終了させることは、予期せぬ挙動であり不適切です。このコミットは、このような状況下で、`GOTRACEBACK=crash`が設定された場合と同様のクラッシュ挙動、すなわち`abort`を呼び出すように変更します。

この変更の主な動機は、Issue #11382で報告されたAndroidのクラッシュレポーターが、Goプロセスが終了する際に混乱するという問題に対処するためです。Goがプロセスを所有していないすべてのケースにおいて、`abort`による挙動が適切であると判断されました。

この変更はシンプルで限定的であり、Go 1.5でのAndroidアプリケーションにおける信頼性の高いクラッシュレポートを可能にするでしょう。

## 変更の背景

Go言語は、その強力な並行処理モデルと効率性から、スタンドアロンアプリケーションだけでなく、既存のシステムに組み込むライブラリとしても利用されることがあります。特に、`c-shared`や`c-archive`といったビルドモードを使用することで、GoコードをC言語のインターフェースを持つライブラリとしてエクスポートし、C、C++、Java（JNI経由でAndroidなど）といった他の言語から利用することが可能になります。

しかし、Goランタイム内で致命的なエラー（例：メモリ破壊、不正なポインタアクセス）や捕捉されないパニックが発生した場合、Goのデフォルトの挙動は、スタックトレースを出力した後に`exit(2)`を呼び出してプロセスを終了させることです。この挙動は、Goがプロセス全体を制御しているスタンドアロンアプリケーションでは問題ありません。

問題となるのは、Goコードが外部のアプリケーションにライブラリとして組み込まれているケースです。この場合、プロセス全体のライフサイクルはGoではなく、ホストアプリケーション（例えばAndroidアプリのJavaコード）が管理しています。Goライブラリが内部で`exit()`を呼び出すと、ホストアプリケーションは予期せず終了することになり、そのクラッシュレポートメカニズムが適切に機能しない可能性があります。ホストアプリケーションは、Goライブラリが「正常に」終了したのか、それとも致命的なエラーで「クラッシュ」したのかを区別できず、デバッグが困難になります。

このコミットは、このような状況下でのGoランタイムの挙動を改善し、ホストアプリケーションがGoライブラリの致命的な問題をより適切に検出・報告できるようにすることを目的としています。

## 前提知識の解説

### Goのビルドモード: `c-shared`と`c-archive`

Goは、`go build -buildmode`オプションを通じて、様々な形式でバイナリを生成できます。このコミットに関連するのは以下の2つです。

*   **`c-shared`**: GoパッケージをC言語から呼び出し可能な共有ライブラリ（例: Linuxでは`.so`、macOSでは`.dylib`、Windowsでは`.dll`）としてコンパイルします。このモードでビルドされたライブラリは、実行時にホストアプリケーションによって動的にロードされます。Goコードは`package main`である必要があり、Cからエクスポートしたい関数には`//export FunctionName`というディレクティブを付与します。
*   **`c-archive`**: GoパッケージをC言語からリンク可能な静的アーカイブ（例: `.a`ファイル）としてコンパイルします。このアーカイブは、ホストアプリケーションのコンパイル時に直接リンクされ、最終的な実行可能ファイルの一部となります。`c-shared`と同様に、`package main`と`//export`ディレクティブが必要です。

これらのモードは、Goの強力な機能を既存のC/C++ベースのシステムや、Android/iOSのようなモバイルプラットフォームに統合する際に不可欠です。

### `panic`と`recover`

Goには、プログラムの異常な状態を示すための組み込み関数`panic`があります。`panic`が呼び出されると、現在の関数の実行が停止し、遅延関数（`defer`）が実行され、呼び出し元の関数へとパニックが伝播していきます。最終的に、`main`関数までパニックが到達し、`recover`によって捕捉されない場合、プログラムはスタックトレースを出力して終了します。

`recover`は、`defer`関数内で呼び出すことで、パニックからの回復を試みることができます。これにより、プログラムの異常終了を防ぎ、エラーハンドリングを行うことが可能です。しかし、致命的なランタイムエラー（例: nilポインタ参照）や、意図的に捕捉されないパニックは、最終的にプログラムの終了につながります。

### `exit()`と`abort()`

C言語の標準ライブラリには、プログラムを終了させるための関数がいくつかあります。

*   **`exit(int status)`**: プログラムを正常または異常終了させます。`status`引数は、プログラムの終了ステータスを示します（通常、`0`は成功、非`0`はエラー）。`exit()`は、終了前にバッファのフラッシュや登録された終了ハンドラの実行など、いくつかのクリーンアップ処理を行います。
*   **`abort()`**: プログラムを異常終了させます。通常、`SIGABRT`シグナルを発生させ、コアダンプを生成します。`abort()`は、`exit()`のようなクリーンアップ処理を行わず、即座にプログラムを終了させることが多いです。コアダンプは、プログラムがクラッシュした時点のメモリ状態を記録したものであり、デバッグツール（GDBなど）を使用してクラッシュの原因を詳細に分析するために非常に有用です。

### `GOTRACEBACK`環境変数

Goランタイムは、`GOTRACEBACK`環境変数の設定に応じて、パニック発生時のスタックトレースの出力レベルを制御します。

*   **`GOTRACEBACK=0`**: スタックトレースを出力しません。
*   **`GOTRACEBACK=1` (デフォルト)**: 現在のゴルーチンのスタックトレースを出力します。
*   **`GOTRACEBACK=2`**: すべてのゴルーチンのスタックトレースを出力します。
*   **`GOTRACEBACK=crash`**: スタックトレースを出力し、さらにプログラムを`abort`させてコアダンプを生成します。これは、特にCGoを介したCコードとの連携で発生する複雑なクラッシュのデバッグに役立ちます。

### Androidのクラッシュレポート

Androidアプリケーションでは、Java/Kotlinコードがメインの実行環境であり、GoライブラリはJNI（Java Native Interface）を介して呼び出されます。Androidシステムは、アプリケーションがクラッシュした場合に、そのクラッシュレポート（スタックトレース、デバイス情報など）を収集し、開発者やクラッシュレポートサービスに送信するメカニズムを持っています。Goライブラリが`exit()`を呼び出してプロセスを終了させると、Androidのクラッシュレポートシステムは、それが通常の終了なのか、それとも致命的なエラーによるクラッシュなのかを正確に判断できない場合があります。`abort()`による終了は、より明確な「異常終了」のシグナルとして認識されやすく、Androidのクラッシュレポートシステムが適切に反応し、有用なデバッグ情報を生成するのに役立ちます。

## 技術的詳細

このコミットの核心は、Goランタイムがプロセスを所有していない状況（`c-shared`または`c-archive`モード）において、致命的なエラーやパニック発生時の終了挙動を`exit`から`abort`に変更することです。

Goランタイムの内部では、`parsedebugvars`という関数がデバッグ関連の環境変数を解析し、ランタイムの挙動を設定します。この関数内で、`GOTRACEBACK`環境変数の値に基づいて`traceback_cache`という内部変数が設定されます。`GOTRACEBACK=crash`が設定されている場合、`traceback_cache`の特定のビットがセットされ、ランタイムが`abort`を呼び出すように指示されます。

このコミットでは、`parsedebugvars`関数に新たなロジックが追加されます。具体的には、Goランタイムが`c-shared`（`isarchive`がfalseで`islibrary`がtrue）または`c-archive`（`isarchive`がtrue）モードでビルドされているかどうかをチェックします。これらのモードのいずれかである場合、`traceback_cache`の最下位ビット（`1`）を強制的にセットします。このビットは、`GOTRACEBACK=crash`が設定された場合と同じ効果を持ち、ランタイムに`abort`を呼び出すように指示します。

これにより、Goコードが外部のC/C++アプリケーションに組み込まれている場合、たとえ`GOTRACEBACK=crash`が明示的に設定されていなくても、致命的なエラーやパニックが発生した際には`abort`が呼び出されるようになります。`abort`は通常、`SIGABRT`シグナルを発生させ、オペレーティングシステムレベルでコアダンプを生成します。このコアダンプは、クラッシュ時の詳細なメモリ状態やスタックトレースを含んでおり、GDBのようなデバッガで分析することで、クラッシュの根本原因を特定するのに役立ちます。

この変更は、Goランタイムがプロセス全体の制御権を持たない状況において、より予測可能でデバッグしやすいクラッシュ挙動を提供することで、Goと他の言語との相互運用性を向上させます。特に、AndroidのようなモバイルプラットフォームでGoライブラリを使用する際のクラッシュレポートの信頼性向上に貢献します。

## コアとなるコードの解説

追加されたコードブロックは以下の通りです。

```go
	// when C owns the process, simply exit'ing the process on fatal errors
	// and panics is surprising. Be louder and abort instead.
	if islibrary || isarchive {
		traceback_cache |= 1
	}
```

*   **`islibrary`**: このブール変数は、Goランタイムが`c-shared`モードでビルドされている場合に`true`になります。つまり、Goコードが動的にロードされる共有ライブラリとして機能していることを示します。
*   **`isarchive`**: このブール変数は、Goランタイムが`c-archive`モードでビルドされている場合に`true`になります。つまり、Goコードが静的リンクされるアーカイブライブラリとして機能していることを示します。
*   **`islibrary || isarchive`**: この条件式は、GoランタイムがC言語から利用されるライブラリとしてビルドされているかどうかを判断します。
*   **`traceback_cache |= 1`**: この行が変更の核心です。`traceback_cache`は、`GOTRACEBACK`環境変数の設定を内部的に保持する`uint32`型の変数です。`|= 1`という操作は、`traceback_cache`の最下位ビット（0番目のビット）をセットします。この最下位ビットがセットされている場合、Goランタイムは致命的なエラーやパニックが発生した際に、`exit`ではなく`abort`を呼び出すように動作します。これは、`GOTRACEBACK=crash`が設定された場合と同じ効果をもたらします。

この変更により、Goランタイムが外部コードによって所有されている状況下で、致命的な問題が発生した場合に、より明確なクラッシュシグナル（`abort`）を発するように強制されます。これにより、ホストアプリケーションのクラッシュレポートシステムが、Goライブラリの異常終了を正確に検出し、適切なデバッグ情報を収集できるようになります。

# [インデックス 20444] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおいて、システムコール呼び出し中にGoのガベージコレクタ（GC）がポインタが指すメモリを誤って解放してしまう問題を修正するものです。特に、`syscall.Syscall`が`uintptr`型の引数を受け取る際に、その`uintptr`がGoのメモリを指している場合、GCがそのメモリを追跡できず、システムコールが完了する前にメモリが解放されてしまう「use-after-free」の脆弱性が発生する可能性がありました。この問題は、特にSolaris環境で`open(2)`システムコールにおいて顕著に現れていました。

    syscall: keep allocated C string live across call to Syscall
    
    Given:
    
            p := alloc()
            fn_taking_ptr(p)
    
    p is NOT recorded as live at the call to fn_taking_ptr:
    it's not needed by the code following the call.
    p was passed to fn_taking_ptr, and fn_taking_ptr must keep
    it alive as long as it needs it.
    In practice, fn_taking_ptr will keep its own arguments live
    for as long as the function is executing.
    
    But if instead you have:
    
            p := alloc()
            i := uintptr(unsafe.Pointer(p))
            fn_taking_int(i)
    
    p is STILL NOT recorded as live at the call to fn_taking_int:
    it's not needed by the code following the call.
    fn_taking_int is responsible for keeping its own arguments
    live, but fn_taking_int is written to take an integer, so even
    though fn_taking_int does keep its argument live, that argument
    does not keep the allocated memory live, because the garbage
    collector does not dereference integers.
    
    The shorter form:
    
            p := alloc()
            fn_taking_int(uintptr(unsafe.Pointer(p)))
    
    and the even shorter form:
    
            fn_taking_int(uintptr(unsafe.Pointer(alloc())))
    
    are both the same as the 3-line form above.
    
    syscall.Syscall is like fn_taking_int: it is written to take a list
    of integers, and yet those integers are sometimes pointers.
    If there is no other copy of those pointers being kept live,
    the memory they point at may be garbage collected during
    the call to syscall.Syscall.
    
    This is happening on Solaris: for whatever reason, the timing
    is such that the garbage collector manages to free the string
    argument to the open(2) system call before the system call
    has been invoked.
    
    Change the system call wrappers to insert explicit references
    that will keep the allocations alive in the original frame
    (and therefore preserve the memory) until after syscall.Syscall
    has returned.
    
    Should fix Solaris flakiness.
    
    This is not a problem for cgo, because cgo wrappers have
    correctly typed arguments.

## 変更の背景

Go言語のガベージコレクタ（GC）は、プログラムが使用しなくなったメモリを自動的に解放することで、メモリ管理の複雑さを軽減します。しかし、Goの型システムを迂回して低レベルの操作を行う場合、GCの動作と予期せぬ相互作用が発生することがあります。

このコミットの背景にある問題は、Goプログラムがオペレーティングシステムのシステムコールを呼び出す際に発生しました。特に、`syscall`パッケージを通じてシステムコールを呼び出す際、Goの文字列やバイトスライスなどのGoが管理するメモリ領域へのポインタを、システムコールが期待する`uintptr`型（符号なし整数型でメモリアドレスを表す）に変換して渡すことがあります。

GoのGCは、`uintptr`型の値をポインタとして追跡しません。GCが追跡するのは、Goのポインタ型（`*T`や`unsafe.Pointer`）のみです。このため、Goのメモリを指す`uintptr`がシステムコールに渡され、かつそのGoのメモリに対して他にGoが追跡しているポインタが存在しない場合、GCはシステムコールが完了する前にそのメモリを「到達不可能」と判断し、解放してしまう可能性がありました。

この「use-after-free」問題は、特にSolaris環境で顕著に現れました。Solaris上での`open(2)`システムコール呼び出しにおいて、ファイルパスを表す文字列がシステムコールに渡された直後にGCによって解放され、システムコールがその解放されたメモリにアクセスしようとしてクラッシュや予期せぬ動作を引き起こすという、再現性の低い（flakiness）バグとして報告されていました。

この問題は、Goのメモリ安全性の原則に反するため、システムコール呼び出し中にGoが管理するメモリが確実に生存するようにするための修正が必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とシステムプログラミングの知識が不可欠です。

1.  **Goのガベージコレクタ (GC)**:
    *   Goはトレース型GCを採用しており、プログラムが到達可能なオブジェクトをマークし、到達不可能なオブジェクトを解放します。
    *   GCはGoのポインタ型（`*T`）を追跡し、それらが指すメモリが使用中であることを認識します。
    *   GCはオブジェクトをメモリ内で移動させることがあります（moving collector）。これにより、メモリの断片化を減らし、キャッシュ効率を向上させることができます。

2.  **`unsafe.Pointer`**:
    *   `unsafe`パッケージは、Goの型安全性を意図的にバイパスするための機能を提供します。
    *   `unsafe.Pointer`は、任意の型のポインタを保持できる特殊なポインタ型です。これはC言語の`void*`に似ています。
    *   `unsafe.Pointer`はGCによって追跡されます。つまり、`unsafe.Pointer`がGoのメモリを指している限り、GCはそのメモリを解放しません。
    *   `*T`と`uintptr`の間で変換を行う際の中間ステップとして使用されます。

3.  **`uintptr`**:
    *   `uintptr`は、ポインタのビットパターンを保持するのに十分な大きさの符号なし整数型です。
    *   これは純粋な数値であり、Goのポインタ型ではありません。
    *   **重要**: `uintptr`はGCによって追跡されません。`uintptr`がGoのメモリのアドレスを保持していても、そのメモリへの他のGoポインタが存在しない場合、GCはそのメモリを解放する可能性があります。
    *   GCがオブジェクトを移動させた場合、`uintptr`が保持するアドレスは古くなり、無効なメモリを指す可能性があります。

4.  **`syscall`パッケージ**:
    *   Goプログラムからオペレーティングシステムのシステムコールを直接呼び出すための低レベルなインターフェースを提供します。
    *   多くのシステムコールは、ファイルパスやバッファなどの引数を生のメモリアドレスとして受け取ります。Goでは、これらのアドレスを`uintptr`型に変換して渡すことが一般的です。
    *   `syscall.Syscall`関数は、可変個の`uintptr`引数を受け取ります。これは、システムコールが様々な型の引数を取るためです。

5.  **「use-after-free」問題**:
    *   プログラムが既に解放されたメモリ領域にアクセスしようとするときに発生するバグです。
    *   解放されたメモリは、別の目的で再利用される可能性があり、その結果、データ破損、クラッシュ、またはセキュリティ脆弱性につながることがあります。

6.  **`runtime.KeepAlive`**:
    *   Go 1.4で導入された関数で、特定の変数がその関数呼び出しの時点までGCによって解放されないことを保証します。
    *   コンパイラ組み込み関数であり、GCが変数の「生存期間」を誤って短く見積もることを防ぎます。
    *   このコミットで導入される`use`関数は、`runtime.KeepAlive`と同様の目的で、`syscall`パッケージ内部で利用されるものです。

## 技術的詳細

このコミットの技術的解決策は、システムコールに渡されるGoが管理するメモリ（特に文字列やバイトスライス）が、システムコールが完了するまでGCによって解放されないように、明示的な「生存期間の延長」メカニズムを導入することです。

具体的には、以下の変更が行われました。

1.  **`use`関数の導入**:
    *   `src/syscall/syscall.go`に`use(p unsafe.Pointer)`という新しい関数が追加されました。
    *   この関数は実質的には何もしない（`RET`命令のみ）ノーオペレーション（no-op）関数ですが、コンパイラに対しては引数`p`がこの関数呼び出しの時点まで「生きている」（GCによって解放されない）ことを保証するヒントとして機能します。
    *   `//go:noescape`ディレクティブが付与されており、この関数が引数をヒープにエスケープさせないことを示しています。これにより、スタック上のメモリが不必要にヒープに移動するのを防ぎます。

    ```go
    // src/syscall/syscall.go
    // ...
    import "unsafe"
    // ...
    // use is a no-op, but the compiler cannot see that it is.
    // Calling use(p) ensures that p is kept live until that point.
    //go:noescape
    func use(p unsafe.Pointer)
    ```

2.  **`mksyscall.pl`および関連スクリプトの変更**:
    *   `src/syscall/mksyscall.pl`（システムコールラッパーコードを自動生成するPerlスクリプト）が変更されました。
    *   このスクリプトは、Goの文字列やバイトスライスが`uintptr(unsafe.Pointer(...))`としてシステムコールに渡される際に、その直後に`use(unsafe.Pointer(_pN))`のような呼び出しを挿入するように修正されました。ここで`_pN`は、システムコールに渡されるGoのメモリを指す一時変数です。
    *   これにより、システムコールが実行されている間、GoのGCはそのメモリがまだ使用中であると認識し、解放を控えるようになります。
    *   `mksyscall_solaris.pl`など、各OS固有のシステムコール生成スクリプトも同様に更新されました。

3.  **既存のシステムコールラッパーへの`use`の追加**:
    *   自動生成されるコードだけでなく、手動で記述された一部のシステムコールラッパー（例: `src/syscall/dll_windows.go`, `src/syscall/so_solaris.go`, `src/syscall/syscall_linux.go`など）にも、明示的に`use(unsafe.Pointer(...))`呼び出しが追加されました。
    *   これにより、システムコールに渡されるポインタが、システムコールが戻るまで確実に生存することが保証されます。

この修正は、GoのGCが`uintptr`を追跡しないという性質と、システムコールがポインタを`uintptr`として受け取るという事実の間のギャップを埋めるものです。`use`関数は、GCに対して「このポインタが指すメモリはまだ必要だ」というシグナルを送り、システムコールが安全に完了できるようにします。

## コアとなるコードの解説

このコミットの核心は、Goのガベージコレクタが`uintptr`型の値をポインタとして認識しないという特性を考慮し、システムコールに渡されるGoのメモリがGCによって誤って解放されないようにするための`use`関数の導入とその適用です。

1.  **`func use(p unsafe.Pointer)`**:
    *   この関数は`src/syscall/syscall.go`に定義されています。
    *   `unsafe.Pointer`を引数に取ります。`unsafe.Pointer`はGCによって追跡されるため、この関数に渡されたポインタが指すメモリは、`use`関数が呼び出された時点までGCによって「生きている」と見なされます。
    *   `//go:noescape`ディレクティブは、コンパイラに対して、この関数が引数`p`をヒープにエスケープさせないことを保証します。これにより、不要なヒープ割り当てやGCのオーバーヘッドを防ぎます。
    *   関数本体は`RET`（リターン）命令のみで、実際には何も処理を行いません。これは、コンパイラにGCのヒントを与えるためだけの関数であることを示しています。

2.  **`mksyscall.pl`による自動生成コードへの`use`の挿入**:
    *   `mksyscall.pl`スクリプトは、Goのシステムコールラッパーを生成する際に、文字列（`string`）やバイトスライス（`[]byte`）などのGoが管理するデータがシステムコールに渡される直後に、`use(unsafe.Pointer(_pN))`という行を挿入するように変更されました。
    *   例えば、`BytePtrFromString`でGoの文字列からCスタイルのバイトポインタ（`*byte`）が生成され、それが`uintptr(unsafe.Pointer(_pN))`としてシステムコールに渡されます。この直後に`use(unsafe.Pointer(_pN))`が追加されることで、システムコールが実行されている間、元のGoの文字列が指すメモリがGCによって解放されるのを防ぎます。
    *   このメカニズムにより、システムコールがそのメモリを安全に読み書きできるようになります。システムコールが戻った後、`use`呼び出しのスコープを抜ければ、GCはそのメモリを再び解放の対象とすることができます。

この修正は、GoのランタイムとOSの低レベルなインターフェースとの間の重要な同期メカニズムを提供し、特にGCのタイミングに依存する稀なバグ（Solarisでのflakinessなど）を解決するために不可欠でした。

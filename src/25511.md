# [インデックス 25511] ファイルの概要

このコミットはGoランタイムのガベージコレクション（GC）に関連する`src/runtime/mgc.go`ファイルに対する変更です。`mgc.go`はGoの並行マーク＆スイープ型ガベージコレクタの主要なロジックを実装しており、GCの各フェーズ（マーク、スイープなど）の管理、GCワーカーのスケジューリング、およびGCの状態遷移を制御します。

## コミット

runtime: eliminate mark completion in scheduler

Currently, findRunnableGCWorker will perform mark completion if there
is no remaining work and no running workers. This used to be necessary
to resolve a race in the transition from mark 1 to mark 2 where we
would enter mark 2 with no mark work (and no dedicated workers), so no
workers would run, so no worker would signal mark completion.

However, we're about to make mark completion also perform the entire
follow-on process, which includes mark termination. We really don't
want to do that in the scheduler if it happens to detect completion.

Conveniently, this hack is no longer necessary because we always
enqueue root scanning work at the beginning of both mark 1 and mark 2,
so a mark worker will always run. Hence, we can simply eliminate it.

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）におけるマークフェーズの完了処理の改善と、それに伴う不要なコードの削除があります。

以前のGoランタイムでは、GCのマークフェーズ（特にマーク1からマーク2への移行時）において、`findRunnableGCWorker`関数がGCワーカーが実行されていない、かつ残りの作業がない場合にマーク完了処理を実行する「ハック」が存在していました。これは、マーク2フェーズに突入した際に、初期のマーク作業がキューにないためにGCワーカーが起動せず、結果としてマーク完了がシグナルされないという競合状態（レースコンディション）を回避するために必要でした。

しかし、このコミットが作成された時点では、マーク完了処理がマーク終了（mark termination）を含む後続のプロセス全体を実行するように変更される予定でした。もしスケジューラがGCワーカーの検出時にマーク完了処理を実行してしまうと、意図せずマーク終了プロセス全体がスケジューラ内で実行されてしまうことになり、これは望ましくありませんでした。

幸いなことに、GoランタイムのGCは、マーク1とマーク2の両フェーズの開始時に常にルートスキャン作業をキューに入れるように変更されていました。これにより、GCワーカーは常に実行されることが保証され、マーク完了をシグナルするワーカーが常に存在することになります。この変更により、以前の「ハック」は不要となり、削除することが可能になりました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと、特にマークフェーズに関する知識が必要です。

1.  **Goのガベージコレクション (GC)**: Goは並行マーク＆スイープ型のGCを採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（STW: Stop The World）時間を最小限に抑えることを目指しています。
2.  **GCのフェーズ**: GoのGCは複数のフェーズに分かれています。
    *   **Marking (マークフェーズ)**: このフェーズでは、到達可能なオブジェクト（プログラムから参照されているオブジェクト）を特定します。これはさらに「マーク1」と「マーク2」に分けられることがあります。
        *   **Mark 1**: 初期マークフェーズ。STWを伴い、ルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークします。
        *   **Mark 2**: 並行マークフェーズ。STWを解除し、GCワーカーがバックグラウンドでヒープ全体をスキャンし、到達可能なオブジェクトをマークします。このフェーズ中にアプリケーションがオブジェクトグラフを変更する可能性があるため、ライトバリア（write barrier）が使用されます。
    *   **Mark Termination (マーク終了)**: マークフェーズの最終段階で、STWを伴い、マーク作業の最終処理と次のフェーズへの移行準備を行います。
    *   **Sweeping (スイープフェーズ)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、メモリを再利用可能にします。これも並行して行われます。
3.  **GCワーカー**: GCのマークフェーズ中に、実際のマーク作業を行うゴルーチンです。これらは通常のアプリケーションゴルーチンと並行して実行され、ヒープをスキャンして到達可能なオブジェクトを特定します。
4.  **スケジューラ (`findRunnableGCWorker`)**: Goランタイムのスケジューラは、実行可能なゴルーチンを見つけてCPUコア（P: Processor）に割り当てます。`findRunnableGCWorker`は、GCワーカーが必要な場合に、実行可能なGCワーカーゴルーチンを見つける役割を担います。
5.  **ルートスキャン**: GCのマークフェーズの開始時に、プログラムの実行ルート（スタック、グローバル変数、レジスタなど）から到達可能なオブジェクトをスキャンし、マーク作業の初期キューに投入するプロセスです。

このコミットは、特にマークフェーズにおけるGCワーカーのスケジューリングと、マーク完了のシグナル方法に関する最適化とクリーンアップを目的としています。

## 技術的詳細

このコミットは、`src/runtime/mgc.go`内の`gcControllerState`構造体の`findRunnableGCWorker`メソッドと、`gc`関数の変更を含んでいます。

### `findRunnableGCWorker`メソッドの変更

以前の`findRunnableGCWorker`メソッドには、GCワーカーが実行されていない、かつ残りの作業がない場合にマーク完了処理を強制的に実行するロジックが含まれていました。このロジックは、`work.nwait == work.nproc`（全てのプロセッサがGCワーカーの作業を待機している状態、つまりGCワーカーが実行されておらず、かつ作業がない状態）という条件で発動していました。

このブロックでは、`gcBlackenPromptly`というフラグの状態に応じて`work.bgMark1.complete()`または`work.bgMark2.complete()`を呼び出し、マークフェーズの完了をシグナルしていました。`complete()`メソッドが`true`を返した場合（つまり、完了処理が実際に何かを「readied」した、例えば次のGCフェーズへの移行を準備した）、`resetspinning()`を呼び出してスケジューラにその状態を通知していました。

このコミットでは、この約20行にわたるコードブロック全体が削除されました。

### `gc`関数の変更

`gc`関数はGCのメインエントリポイントであり、GCの各フェーズをオーケストレーションします。このコミットでは、`gc`関数内のマークフェーズの開始部分にコメントが追加されました。

具体的には、マーク1フェーズとマーク2フェーズの開始時にルートスキャン作業をキューに入れる部分に、以下のコメントが追加されています。

```go
// This also ensures there will be queued mark
// work, which ensures some mark worker will
// run and signal mark 2 completion.
```

このコメントは、ルートスキャン作業が常にキューに入れられるようになったことで、GCワーカーが必ず起動し、マーク完了を適切にシグナルするようになるため、`findRunnableGCWorker`内の特別な完了処理が不要になったことを明確に示しています。

### 変更の論理的つながり

この変更の核心は、GCのマークフェーズの開始時に「常に」ルートスキャン作業がキューに入れられるようになったという前提にあります。

1.  **以前の問題**: マーク1からマーク2への移行時など、特定の状況下で初期のマーク作業がキューにない場合がありました。この場合、`findRunnableGCWorker`は実行可能なGCワーカーを見つけられず、かつ作業もないと判断し、誰もマーク完了をシグナルしないというデッドロックのような状態に陥る可能性がありました。これを回避するために、`findRunnableGCWorker`が「もしや完了しているのでは？」と判断して、自らマーク完了処理をトリガーする「ハック」が必要でした。
2.  **新しい前提**: GCの設計変更により、マーク1とマーク2の開始時には必ずルートスキャン作業がキューに入れられるようになりました。これにより、GCワーカーは常に何らかの作業を見つけて実行を開始し、その作業の完了時にマークフェーズの完了を適切にシグナルするようになります。
3.  **ハックの不要化**: 上記の新しい前提により、`findRunnableGCWorker`が自らマーク完了をトリガーする必要がなくなりました。GCワーカーが常に作業を見つけて実行するため、マーク完了は常にワーカーによって適切に処理されることが保証されます。
4.  **将来の変更への対応**: さらに、コミットメッセージが示唆するように、マーク完了処理が将来的にマーク終了プロセス全体を含むように拡張される予定でした。もし`findRunnableGCWorker`がこの拡張されたマーク完了処理を呼び出してしまった場合、スケジューラ内でマーク終了まで実行されてしまい、GCのフェーズ管理が複雑化し、意図しない副作用が生じる可能性がありました。この観点からも、不要なハックを削除することは重要でした。

このコミットは、GCの堅牢性を高め、将来の拡張性を確保するためのクリーンアップ作業の一環と言えます。

## コアとなるコードの解説

### 削除されたコードブロックの解説

削除されたコードブロックは、`gcControllerState`の`findRunnableGCWorker`メソッド内に存在していました。このブロックは、GCワーカーが全て待機状態（`work.nwait == work.nproc`）であり、かつ他に実行可能なGC作業がない場合に、GCマークフェーズの完了を強制的にシグナルする役割を担っていました。

具体的には、`gcBlackenPromptly`というフラグの状態に応じて、`work.bgMark1.complete()`または`work.bgMark2.complete()`を呼び出していました。これらの`complete()`メソッドは、それぞれのマークフェーズ（マーク1またはマーク2）の完了処理を実行し、必要に応じて次のGCフェーズへの移行を準備します。もし`complete()`が`true`を返した場合（つまり、何らかの状態遷移が発生した場合）、`resetspinning()`を呼び出してスケジューラにその変更を通知していました。

この「ハック」は、マークフェーズの移行時に初期作業がキューにない場合に、GCワーカーが起動せず、結果としてマーク完了がシグナルされないという競合状態を回避するために導入されていました。しかし、このコミットの背景で述べたように、GCの設計変更によりこのハックは不要となりました。

### 追加されたコメントの解説

`gc`関数内の追加されたコメントは、GCのマークフェーズ（マーク1とマーク2）の開始時にルートスキャン作業が常にキューに入れられるようになったことを強調しています。

```go
// This also ensures there will be queued mark
// work, which ensures some mark worker will
// run and signal mark 2 completion.
```

このコメントは、ルートスキャン作業がキューに入れられることで、GCワーカーが常に実行可能な作業を見つけられるようになり、その結果、GCワーカー自身がマークフェーズの完了を適切にシグナルするようになることを説明しています。これにより、`findRunnableGCWorker`内の冗長なマーク完了処理が不要になったという論理的なつながりを示しています。

要するに、GCの初期化段階でマーク作業が確実にスケジュールされるようになったため、スケジューラが「もしや完了しているのでは？」と推測して完了処理を呼び出す必要がなくなった、ということです。これはGCのロジックを簡素化し、より堅牢にするための重要な変更です。

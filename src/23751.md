# [インデックス 23751] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/zip` パッケージにおける `zip.Writer.CreateHeader` メソッドの挙動に関する重要な修正と明確化を行います。具体的には、`CreateHeader` に渡された `FileHeader` オブジェクトが、メソッド呼び出し後に変更されることによって発生する可能性のある問題を解決し、APIの利用規約を明確にすることを目的としています。

## 元コミット内容

`archive/zip`: `CreateHeader` が `FileHeader` の所有権を持つことを明確化する。
`Fixes #11144`

## 変更の背景

このコミットは、Go issue #11144 で報告された問題に対処するために行われました。この問題は、`archive/zip` パッケージを使用してZIPアーカイブを作成する際に、特定の状況下で「unexpected EOF」というパニックが発生するというものでした。

根本的な原因は、`zip.Writer.CreateHeader` メソッドに `*zip.FileHeader` オブジェクトを渡した後、ユーザーコードがその `FileHeader` オブジェクトを再利用または変更してしまうことにありました。`CreateHeader` は渡された `FileHeader` の内容を内部的に利用してZIPエントリのヘッダを構築しますが、その `FileHeader` オブジェクトへのポインタを内部のディレクトリ構造に保持します。もし同じ `FileHeader` オブジェクトが複数のエントリの作成に再利用されたり、`CreateHeader` 呼び出し後に変更されたりすると、ZIPアーカイブのメタデータが破損し、結果として「unexpected EOF」のような予期せぬエラーやパニックを引き起こす可能性がありました。

このコミットは、このような誤用を防ぎ、APIの意図を明確にするために、ドキュメントの追加と、不正な `FileHeader` の再利用を検出するランタイムチェックを導入しています。

## 前提知識の解説

### `archive/zip` パッケージ

`archive/zip` パッケージは、ZIPアーカイブの読み書きをサポートするGo言語の標準ライブラリです。このパッケージを使用することで、プログラム内でZIPファイルの作成、既存のZIPファイルの解凍、およびZIPアーカイブ内の個々のファイルへのアクセスが可能になります。

### `zip.Writer` と `zip.FileHeader`

*   **`zip.Writer`**: ZIPアーカイブへの書き込み操作を管理する構造体です。`Create` や `CreateHeader` などのメソッドを通じて、新しいファイルをアーカイブに追加します。
*   **`zip.FileHeader`**: ZIPアーカイブ内の個々のファイルに関するメタデータ（ファイル名、圧縮方法、最終更新日時、パーミッションなど）を保持する構造体です。`CreateHeader` メソッドは、この `FileHeader` を引数として受け取り、その情報に基づいてZIPエントリのヘッダを書き込みます。

### ポインタとオブジェクトの「所有権」

Go言語では、関数やメソッドに構造体をポインタ (`*Struct`) で渡すことがよくあります。ポインタを渡すことで、呼び出し元と呼び出し先が同じメモリ上のオブジェクトを共有し、呼び出し先がそのオブジェクトの内容を変更できるようになります。

この文脈での「所有権 (ownership)」とは、特定のオブジェクトが一度ある関数やメソッドに渡された後、そのオブジェクトのライフサイクルや変更責任が、呼び出し元から呼び出し先に移るという概念を指します。`CreateHeader` の場合、`FileHeader` オブジェクトを渡した後は、`zip.Writer` がその `FileHeader` の内容に依存し、内部的に参照を保持するため、呼び出し元はもはやその `FileHeader` を変更したり、他のエントリのために再利用したりすべきではない、という規約を意味します。これを破ると、データ競合や不正な状態を引き起こす可能性があります。

### データディスクリプタ (`fh.Flags |= 0x8`)

ZIPファイルフォーマットには、ファイルデータに続いてCRC-32チェックサム、圧縮サイズ、非圧縮サイズを記述する「データディスクリプタ」というオプションの構造があります。`fh.Flags |= 0x8` は、`FileHeader` のフラグフィールドに特定のビット（0x8）をセットすることで、このデータディスクリプタを使用することをZIPライターに指示しています。これにより、ファイルの内容を書き込む前にこれらのサイズが不明な場合でも、ZIPエントリを作成できるようになります。

## 技術的詳細

このコミットの技術的詳細は、主に以下の2点に集約されます。

1.  **`FileHeader` の所有権の明確化**: `zip.Writer.CreateHeader` のドキュメントに、`FileHeader` オブジェクトがメソッド呼び出し後に変更されてはならないという明確な指示が追加されました。これは、`zip.Writer` が内部的に `FileHeader` へのポインタを保持し、後続の処理でその内容に依存するためです。変更されると、ZIPアーカイブの整合性が損なわれる可能性があります。

2.  **不正な `FileHeader` 再利用の検出**: 以前の `FileHeader` と同じ `FileHeader` オブジェクトが `CreateHeader` に再度渡された場合に、エラーを返す新しいチェックが追加されました。これは、ユーザーが誤って同じ `FileHeader` インスタンスを複数のZIPエントリの作成に再利用しようとする一般的な間違いを防ぐためのものです。このチェックは、`w.dir` (ZIPアーカイブのディレクトリ構造を保持する内部スライス) の最後の要素が、現在渡された `fh` と同じ `FileHeader` を参照しているかどうかを確認することで行われます。もし同じであれば、それは不正な再利用と判断され、`"archive/zip: invalid duplicate FileHeader"` というエラーが返されます。

この変更により、開発者は `CreateHeader` の正しい使用方法をより明確に理解できるようになり、また、ランタイムでの早期エラー検出によって、デバッグが困難なZIPアーカイブ破損の問題を未然に防ぐことができます。

## コアとなるコードの解説

### ドキュメントの変更

`CreateHeader` 関数のコメントに以下の行が追加されました。

```go
// The provided FileHeader fh
// must not be modified after a call to CreateHeader.
```

これは、`CreateHeader` に `FileHeader` を渡した後は、その `FileHeader` オブジェクトを変更してはならないという、APIの新しい利用規約を明確に示しています。これにより、開発者は `FileHeader` の「所有権」が `zip.Writer` に移ることを理解し、誤った使用を避けることができます。

### 重複 `FileHeader` チェックの追加

以下のコードブロックが `CreateHeader` 関数の冒頭に追加されました。

```go
	if len(w.dir) > 0 && w.dir[len(w.dir)-1].FileHeader == fh {
		// See https://golang.org/issue/11144 confusion.
		return nil, errors.New("archive/zip: invalid duplicate FileHeader")
	}
```

このコードは、以下の条件をチェックします。

*   `len(w.dir) > 0`: 既にZIPアーカイブに少なくとも1つのエントリが追加されていることを確認します。最初のファイルを追加する際にはこのチェックはスキップされます。
*   `w.dir[len(w.dir)-1].FileHeader == fh`: `w.dir` は `zip.Writer` が内部的に管理する、追加されたファイルエントリのリストです。この条件は、直前に追加されたファイルエントリが参照している `FileHeader` オブジェクトと、現在 `CreateHeader` に渡された `fh` オブジェクトが**同じメモリ上のインスタンス**であるかどうかを比較しています。

もしこれらの条件が両方とも真であれば、それはユーザーが同じ `FileHeader` オブジェクトを複数のファイルエントリの作成に再利用しようとしていることを意味します。これは不正な操作であり、`"archive/zip: invalid duplicate FileHeader"` というエラーを返して処理を中断します。これにより、ZIPアーカイブの破損を防ぎ、開発者に問題の早期発見を促します。コメント `// See https://golang.org/issue/11144 confusion.` は、このチェックが issue #11144 で報告された混乱と問題に対処するためのものであることを示しています。

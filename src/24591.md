# [インデックス 24591] ファイルの概要

このコミットは、GoランタイムがARMアーキテクチャ上で動作する際の、特にGOARMバージョンとマルチプロセッサシステム（SMP）に関する互換性と安定性の改善を目的としています。具体的には、GOARM=5およびGOARM=6のFreeBSD/ARM単一プロセッサシステムでのGoの実行を可能にしつつ、GOARMが7未満の非Linux SMP ARMシステムでは、適切な同期メカニズムがないために早期にクラッシュさせることで、未定義の動作を防ぐように変更されています。

## コミット

このコミットは、GoランタイムがARMアーキテクチャの異なるバージョン（GOARM=5, GOARM=6, GOARM=7）および異なるオペレーティングシステム（FreeBSD, Darwin, NetBSD, OpenBSD, NaCl, Linux）上で、単一プロセッサ（UP）および対称型マルチプロセッサ（SMP）環境でどのように動作するかを調整します。特に、GOARMが7未満のシステムでSMPを安全にサポートするための同期プリミティブが不足している問題に対処し、Go 1.5リリースサイクルにおける現実的な解決策を提供します。

## 変更の背景

Go言語は、様々なアーキテクチャとオペレーティングシステムをサポートすることを目指しています。ARMアーキテクチャは、組み込みシステムからモバイルデバイス、サーバーまで幅広く利用されており、Goランタイムがこれらの環境で効率的かつ正確に動作することが重要です。

このコミットの背景には、以下の課題がありました。

1.  **GOARMバージョンの違いによる同期プリミティブのサポート状況**: ARMアーキテクチャには複数のバージョン（ARMv5, ARMv6, ARMv7など）があり、それぞれが異なる命令セットと機能を提供します。特に、マルチプロセッサシステムでデータの一貫性を保証するために不可欠なメモリバリアやアトミック操作といった同期プリミティブのサポート状況がバージョンによって異なります。GOARM=7（ARMv7）以降では強力な同期命令が利用可能ですが、GOARM=5（ARMv5）やGOARM=6（ARMv6）ではそれらが限定的であるか、全く存在しない場合があります。
2.  **非Linuxシステムでの同期の課題**: Linuxカーネルは、システムコールを通じて、特定のARMバージョンに適した同期ルーチンやメモリバリアをGoランタイムに提供できます。これにより、GoランタイムはLinux上であれば、異なるGOARMバージョンでも比較的容易にSMPをサポートできます。しかし、FreeBSD、Darwin（macOS）、NetBSD、OpenBSDなどの非Linuxシステムでは、Goランタイム自身がこれらの同期メカニズムを実装するか、OSが提供する低レベルのプリミティブを利用する必要があります。このコミットの時点では、GOARMが7未満の非LinuxシステムでSMPを安全に動作させるための適切な同期実装が不足していました。
3.  **Go 1.5リリースサイクル**: Go 1.5は、Go言語にとって重要なリリースであり、セルフホスト化（GoコンパイラがGo自身で書かれる）が達成されたバージョンです。このリリースサイクル中に、既存のコードベースに大きな変更を加えることはリスクが高く、時間的な制約もありました。そのため、GOARM=6での異なる同期実装の可能性は認識されつつも、このサイクルでの導入は見送られました。
4.  **バグ修正 (#12067)**: このコミットは、特定の環境でのGoランタイムの不安定性やクラッシュを引き起こしていた問題（Issue #12067）を修正するものです。この問題は、主にGOARMが7未満のSMPシステムで、適切な同期なしにGoランタイムが動作しようとすることに起因していました。

これらの背景から、開発チームは、GOARM=5およびGOARM=6の単一プロセッサFreeBSD/ARMシステムでの動作を可能にしつつ、GOARMが7未満の非Linux SMPシステムでは、未定義の動作やデータ破損を防ぐために早期にクラッシュさせるという、実用的かつ安全なアプローチを選択しました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

1.  **ARMアーキテクチャとGOARM**:
    *   **ARM (Advanced RISC Machine)**: モバイルデバイス、組み込みシステム、IoTデバイスなどで広く使用されているRISCベースのプロセッサアーキテクチャです。
    *   **GOARM**: GoコンパイラがARMターゲット向けに生成するコードのバージョンを指定する環境変数またはビルドタグです。
        *   **GOARM=5 (ARMv5)**: ARMv5TE命令セットを指し、主に古い組み込みシステムで使用されます。アトミック操作やメモリバリアのサポートが限定的です。
        *   **GOARM=6 (ARMv6)**: ARMv6命令セットを指し、Raspberry Pi 1などで使用されました。ARMv5よりは改善されていますが、強力なメモリバリア命令はまだ限定的です。
        *   **GOARM=7 (ARMv7)**: ARMv7-A命令セットを指し、多くのスマートフォンやタブレット、Raspberry Pi 2/3などで使用されました。`DMB` (Data Memory Barrier) や `DSB` (Data Synchronization Barrier) といった強力なメモリバリア命令、およびアトミック操作をサポートしています。
2.  **SMP (Symmetric Multiprocessing)**: 複数のCPUコアが同じメモリを共有し、並行してタスクを実行するシステムアーキテクチャです。SMP環境では、複数のコアが同時に共有データにアクセスするため、データの一貫性を保つために厳密な同期メカニズムが必要です。
3.  **メモリバリア (Memory Barrier) / フェンス (Fence)**:
    *   プロセッサは、パフォーマンス向上のために命令の実行順序を入れ替えたり（アウトオブオーダー実行）、メモリへの書き込みをバッファリングしたりします。
    *   マルチプロセッサシステムでは、このような最適化が原因で、あるCPUコアから見たメモリの変更順序が、別のCPUコアから見た順序と異なる場合があります。
    *   メモリバリアは、コンパイラやプロセッサに対して、特定のメモリ操作の順序を強制する命令です。これにより、共有データへのアクセスが正しく同期され、データの一貫性が保証されます。
    *   ARMv7以降では、`DMB` (Data Memory Barrier) や `DSB` (Data Synchronization Barrier) といった命令が提供されます。`DMB ST` はストア操作の順序を保証するバリアです。
4.  **アトミック操作 (Atomic Operations)**: 複数のCPUコアから同時にアクセスされても、その操作全体が不可分（アトミック）に実行されることを保証する操作です。例えば、共有変数のインクリメントは、読み込み、インクリメント、書き込みの3つのステップから成り、これらがアトミックでないと競合状態が発生する可能性があります。アトミック操作は、これらのステップを単一の不可分な操作として実行します。
5.  **Goランタイムの同期**: Goランタイムは、ゴルーチン（goroutine）のスケジューリング、ガベージコレクション、チャネル操作など、内部で多くの並行処理を行います。これらの処理は、共有データ構造にアクセスするため、正確な同期メカニズムに依存しています。Goランタイムは、プラットフォーム固有の低レベルなアトミック操作やメモリバリアを利用して、これらの同期を実現しています。
6.  **`sysctl`**: Unix系システムでカーネルのパラメータを読み書きするためのシステムコールです。このコミットでは、`hw.ncpu` パラメータを読み取ることで、システムのCPUコア数を取得するために使用されています。

## 技術的詳細

このコミットの核心は、ARMアーキテクチャのバージョン（GOARM）とOSの種類に応じて、GoランタイムのSMPサポートを適切に制御することにあります。

1.  **`armPublicationBarrier` の条件付き実行**:
    *   `src/runtime/asm_arm.s` にある `runtime·armPublicationBarrier` は、Goランタイムが内部的に使用するメモリバリアです。これは、あるゴルーチンが共有データ構造を更新した後、その変更が他のゴルーチンから見えるようにするために使用されます。
    *   変更前は、このバリアはARMv7+でのみ有効で、それ以前のバージョンではno-op（何もしない）でした。
    *   このコミットでは、`MOVB runtime·goarm(SB), R11` で現在のGOARMバージョンを取得し、`CMP $7, R11` で7と比較します。
    *   `BLT 2(PC)` (Branch if Less Than) 命令により、GOARMが7未満の場合（つまりGOARM=5またはGOARM=6の場合）、`DMB ST` 命令をスキップして `RET` に直接ジャンプします。これにより、GOARMが7未満のシステムでは、`armPublicationBarrier` が引き続きno-opとして機能します。
    *   コミットメッセージにある「This will not work on SMP ARMv6 machines, if any are in use.」というコメントは、GOARM=6では`DMB ST`のような強力なバリア命令が利用できないため、SMP環境でこのバリアがno-opであるとデータの一貫性が保証されないことを明確に示しています。
2.  **非Linux SMP ARMシステムでの早期クラッシュ**:
    *   `src/runtime/os_darwin_arm.go`, `src/runtime/os_freebsd_arm.go`, `src/runtime/os_netbsd_arm.go`, `src/runtime/os_openbsd_arm.go` の各ファイルで、`checkgoarm()` 関数が変更されています。
    *   これらのOSでは、`getncpu()` 関数を呼び出してシステムのCPUコア数を取得します。
    *   `if getncpu() > 1 && goarm < 7` という条件が追加されました。これは、「システムがマルチCPUであり、かつGOARMバージョンが7未満である」場合に真となります。
    *   この条件が真の場合、Goランタイムはエラーメッセージを出力し、`exit(1)` でプログラムを終了させます。エラーメッセージは、「runtime: this system has multiple CPUs and must use atomic synchronization instructions. Recompile using GOARM=7.」と、ユーザーにGOARM=7で再コンパイルするよう促します。
    *   この早期クラッシュのメカニズムは、適切な同期プリミティブがないSMP環境でGoランタイムが動作し続けることによる、より深刻なデータ破損や未定義の動作を防ぐための「フェイルファスト」戦略です。
3.  **`getncpu()` 関数の導入と `osinit()` の変更**:
    *   `src/runtime/os1_darwin.go` では、`osinit()` 関数からCPU数取得ロジックが `getncpu()` という新しい関数に分離されました。
    *   `getncpu()` は `sysctl` システムコールを使用して `hw.ncpu` を取得します。取得に失敗した場合やCPU数が0以下の場合、デフォルトで1を返します。これは、単一プロセッサシステムとして扱われることを意味します。
    *   この変更により、`checkgoarm()` 関数が `osinit()` よりも前に呼び出される場合でも、正確なCPU数を取得できるようになりました。
4.  **`goarm` 変数の定義場所の変更**:
    *   `src/runtime/os_linux_arm.go` から `goarm` 変数の定義が削除され、`src/runtime/runtime2.go` に移動されました。
    *   `runtime2.go` はGoランタイムのコア部分であり、`goarm` 変数を一元的に管理することで、異なるOS固有のファイルからアクセスしやすくなります。この変数は、`cmd/link`（Goリンカ）によって設定されます。
5.  **NaCl/ARM の要件**:
    *   `src/runtime/os_nacl_arm.go` では、NaCl (Native Client) 環境がARMv7のみをサポートするという制約に基づき、`goarm != 7` の場合にエラーを出力して終了するチェックが追加されました。これは、NaCl環境の厳格な要件に合わせたものです。

これらの変更により、GoランタイムはARMアーキテクチャの多様な環境において、より堅牢で予測可能な動作をするようになりました。特に、同期プリミティブのサポートが不十分な古いARMバージョンでのSMP動作を明示的に禁止することで、潜在的なバグを未然に防いでいます。

## コアとなるコードの解説

このコミットの主要な変更は、GoランタイムがARMアーキテクチャ上で、特にマルチプロセッサ環境でどのようにメモリ同期を扱うかという点にあります。

1.  **`runtime·armPublicationBarrier` の条件付き実行 (`src/runtime/asm_arm.s`)**:
    *   `armPublicationBarrier` は、Goランタイムが共有データ構造の変更を他のプロセッサコアに「公開」する際に使用するメモリバリアです。これは、あるゴルーチンがデータを書き込んだ後、そのデータが他のゴルーチンから正しく読み取れるように、プロセッサのキャッシュやストアバッファの順序を強制するために重要です。
    *   ARMv7以降のアーキテクチャでは、`DMB ST` (Data Memory Barrier, Store) 命令が利用可能であり、これはストア操作の順序を保証します。
    *   しかし、GOARM=5やGOARM=6のような古いARMバージョンでは、この種の強力なメモリバリア命令が利用できないか、その効果が限定的です。
    *   この変更では、`runtime·goarm` 変数（Goリンカによって設定される現在のGOARMバージョン）をチェックし、GOARMが7未満であれば `DMB ST` 命令をスキップします。これにより、古いARMバージョンでは `armPublicationBarrier` が実質的に何もしない（no-op）となります。
    *   この設計は、古いARMバージョンではSMP環境での安全な同期が不可能であることを認識し、後述の早期クラッシュメカニズムと組み合わせて、未定義の動作を防ぐためのものです。

2.  **非Linux SMP ARMシステムでの早期クラッシュ (`src/runtime/os_darwin_arm.go` など)**:
    *   `checkgoarm()` 関数は、Goランタイムの初期化段階で呼び出され、現在のARM環境がGoの実行要件を満たしているかを確認します。
    *   `getncpu()` はシステムのCPUコア数を取得します。`sysctl` を使用して `hw.ncpu` を読み取ることで、物理的なコア数を把握します。
    *   `if getncpu() > 1 && goarm < 7` という条件は、システムが複数のCPUコアを持ち（SMP環境）、かつGOARMバージョンが7未満である場合にトリガーされます。
    *   この条件が真の場合、Goランタイムはエラーメッセージを出力し、プログラムを強制終了します。これは、GOARMが7未満のSMPシステムでは、`armPublicationBarrier` がno-opであるため、Goランタイムが内部的に必要とするメモリ同期が保証されず、データ競合やクラッシュが発生する可能性が非常に高いためです。
    *   Linuxシステムでは、カーネルが適切な同期ルーチンを提供するため、この早期クラッシュの対象外とされています。しかし、FreeBSD、Darwin、NetBSD、OpenBSDなどの非Linuxシステムでは、Goランタイム自身が同期を管理する必要があり、GOARMが7未満ではそれが困難であるため、この制限が設けられました。
    *   この「フェイルファスト」アプローチは、不安定な動作を許容するよりも、問題のある設定で早期に失敗することで、開発者やユーザーに問題を明確に伝え、GOARM=7での再コンパイルを促すことを目的としています。

3.  **`goarm` 変数の一元管理 (`src/runtime/runtime2.go`)**:

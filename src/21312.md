# [インデックス 21312] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおけるHTTP Rangeヘッダー処理のオフバイワンエラーを修正するものです。具体的には、ファイルサイズ `N` のファイルに対して `Range: bytes=N-*` のようなリクエストが来た際に、RFC 7233の仕様に従って `416 Range Not Satisfiable` を返すように変更し、不正な `Content-Range` ヘッダーが生成される問題を解決しています。

## 元コミット内容

`net/http`: Rangeヘッダーのオフバイワンエラーを修正

ファイルサイズが `N` の場合、`Range: bytes=N-*` のリクエストは `416 (Range Not Satisfiable)` を返すべきである（RFC 7233 [1]）。しかし、現状では `206 (Partial Content)` と0バイトのボディを返し、不正な `Content-Range` ヘッダー（`bytes N-(N-1)/N`）を生成していた（RFC 7233 [2]）。

このコミットは、この問題を修正する。

関連するIssue: #8988

## 変更の背景

この変更の背景には、HTTPのRangeリクエストの仕様、特にRFC 7233に準拠するための必要性があります。Goの `net/http` パッケージは、ファイルサービングにおいてRangeヘッダーを処理する機能を提供していますが、特定のケースで仕様に合致しない挙動を示していました。

具体的には、ファイルサイズが `N` バイトである場合、有効なバイト範囲は `0` から `N-1` までです。しかし、`Range: bytes=N-*` のように、開始位置が `N` である範囲をリクエストした場合、これはファイルの範囲外であり、サーバーは `416 Range Not Satisfiable` ステータスコードを返す必要があります。

しかし、修正前の `net/http` パッケージでは、このような無効なRangeリクエストに対して `206 Partial Content` を返していました。さらに問題なのは、この `206` レスポンスには0バイトのボディが含まれ、`Content-Range` ヘッダーが `bytes N-(N-1)/N` のように不正な値になっていました。RFC 7233のセクション4.2では、`last-byte-pos` が `first-byte-pos` より小さい `byte-range-resp` を含む `Content-Range` フィールドは無効であると明記されています。

この不正確な挙動は、クライアント側でのRangeリクエストの処理に混乱を招く可能性があり、HTTPプロトコルの厳密な解釈と実装の観点から修正が必要とされました。

## 前提知識の解説

### HTTP Rangeヘッダー

HTTP Rangeヘッダーは、クライアントがサーバーに対して、リソース全体ではなく、その一部（バイト範囲）のみを要求するために使用されます。これは、大きなファイルのダウンロードを中断した後に再開したり、動画や音声のストリーミングで特定の部分にシークしたりする際に特に有用です。

Rangeヘッダーの一般的な形式は以下の通りです。

*   `Range: bytes=start-end`: 指定された開始位置から終了位置までのバイト範囲を要求します。
*   `Range: bytes=start-`: 指定された開始位置からリソースの最後までを要求します。
*   `Range: bytes=-suffix`: リソースの最後から指定されたバイト数だけを要求します。

サーバーがRangeリクエストを正常に処理できる場合、`206 Partial Content` ステータスコードを返し、`Content-Range` ヘッダーで返されるバイト範囲を示します。

### HTTPステータスコード

*   **`206 Partial Content`**: クライアントのRangeリクエストが成功し、リソースの一部が返されたことを示します。
*   **`416 Range Not Satisfiable`**: クライアントが要求したバイト範囲が、リソースの現在のサイズに対して無効または満たせない場合に返されます。例えば、要求された開始位置がリソースのサイズを超えている場合などです。この場合、サーバーは `Content-Range` ヘッダーにリソースの現在のサイズを含めて返すべきです（例: `Content-Range: bytes */1234`）。

### RFC 7233: Hypertext Transfer Protocol (HTTP/1.1): Range Requests

このRFCは、HTTP/1.1におけるRangeリクエストのセマンティクスを定義しています。このコミットの背景で特に重要となるのは以下のセクションです。

*   **セクション2.1 (Byte Ranges)**: バイト範囲の定義と、バイト範囲セットが「満たせる (satisfiable)」かどうかの条件を記述しています。`first-byte-pos` がリソースの現在の長さより小さいバイト範囲指定が含まれる場合、または `suffix-byte-range-spec` が非ゼロの `suffix-length` を持ち、リソースの長さが非ゼロである場合に満たせるとされます。
*   **セクション3.1 (Range)**: `Range` ヘッダーフィールドの動作について説明しています。サーバーが `Range` ヘッダーフィールドをサポートし、指定された範囲が有効かつ満たせる場合、`206 (Partial Content)` レスポンスを送信すべきであると述べています。また、範囲が無効または満たせない場合、サーバーは `416 (Range Not Satisfiable)` レスポンスを送信すべきであると明記しています。
*   **セクション4.2 (Content-Range)**: `Content-Range` ヘッダーフィールドの形式と使用法を定義しています。`last-byte-pos` の値が `first-byte-pos` の値より小さい `byte-range-resp` を含む `Content-Range` フィールドは無効であると規定しています。

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントとサーバーを構築するための標準ライブラリです。このパッケージには、静的ファイルをサーブする機能も含まれており、その中でHTTP Rangeヘッダーの処理が行われます。`fs.go` ファイルは、ファイルシステムからのコンテンツサービングに関連するロジックを含んでいます。

## 技術的詳細

このコミットの技術的な核心は、`src/net/http/fs.go` 内の `parseRange` 関数における単一の条件式変更にあります。

修正前:
`if err != nil || i > size || i < 0 {`

修正後:
`if err != nil || i >= size || i < 0 {`

この変更は、Rangeリクエストの開始位置 `i` がファイルのサイズ `size` と等しい場合を、無効な範囲として扱うようにします。

ファイルのバイトは通常0から始まるインデックスで扱われます。したがって、サイズが `N` のファイルの場合、有効なバイトインデックスは `0` から `N-1` までです。インデックス `N` はファイルの範囲外となります。

修正前は `i > size` であったため、`i` が `size` と等しい場合は有効な開始位置と見なされていました。これにより、例えばファイルサイズが10バイトの場合、`Range: bytes=10-*` のようなリクエストが来た際に、`parseRange` 関数はこれを有効な範囲として処理しようとしていました。しかし、これは論理的に誤りであり、RFC 7233の規定に反します。

`i >= size` に変更することで、開始位置 `i` がファイルのサイズ `size` 以上である場合に、その範囲を無効と判断し、エラーを返すようになります。これにより、`Range: bytes=N-*` のようなリクエストに対して、`parseRange` 関数がエラーを返し、結果として `416 Range Not Satisfiable` ステータスコードがクライアントに返されるようになります。

また、`src/net/http/fs_test.go` に追加されたテストケースは、この修正が意図通りに機能することを確認しています。特に、ファイルサイズを超える範囲指定（例: `bytes=11-` や `bytes=100-`、`testFileLen` が11の場合）が `StatusRequestedRangeNotSatisfiable` (416) を返すことを検証しています。これにより、以前のオフバイワンエラーによって発生していた不正な `206` レスポンスと `Content-Range` ヘッダーの問題が解決されます。

## コアとなるコードの解説

上記の差分は、`src/net/http/fs.go` ファイル内の `parseRange` 関数における変更を示しています。この関数は、HTTPリクエストの `Range` ヘッダーを解析し、要求されたバイト範囲を処理する役割を担っています。

変更された行は以下の通りです。

```go
// 修正前
if err != nil || i > size || i < 0 {

// 修正後
if err != nil || i >= size || i < 0 {
```

ここで、`i` はRangeリクエストで指定された開始バイト位置（`first-byte-pos`）を表し、`size` は対象となるファイルの合計サイズ（バイト単位）を表します。

*   `err != nil`: `strconv.ParseInt` で文字列から整数への変換に失敗した場合。
*   `i < 0`: 開始位置が負の値である場合。

これらは以前から不正な範囲として扱われていました。このコミットで修正されたのは `i > size` の部分です。

*   **修正前 (`i > size`)**: この条件では、開始位置 `i` がファイルのサイズ `size` を「超えている」場合にのみ、その範囲を無効と判断していました。つまり、`i` が `size` と「等しい」場合は、有効な開始位置として扱われていました。しかし、ファイルが0から始まるインデックスを持つことを考えると、サイズ `N` のファイルの有効なインデックスは `0` から `N-1` までです。したがって、インデックス `N` はファイルの範囲外であり、`N` から始まる範囲は無効であるべきです。
*   **修正後 (`i >= size`)**: この条件では、開始位置 `i` がファイルのサイズ `size` を「以上」である場合に、その範囲を無効と判断します。これにより、`i` が `size` と等しい場合も適切に無効な範囲として扱われるようになります。例えば、ファイルサイズが10バイトの場合、`Range: bytes=10-*` のリクエストは、開始位置が `10` であり、これは `size` と等しいため、この条件によって無効な範囲と判断され、エラーが返されます。

この小さな変更により、`net/http` パッケージはHTTP RangeリクエストのRFC 7233の仕様に厳密に準拠するようになり、ファイルサイズを超える範囲指定に対して正しく `416 Range Not Satisfiable` を返すようになりました。

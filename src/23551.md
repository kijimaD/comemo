# [インデックス 23551] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDragonFly BSD上でのデュアルスタック（IPv4/IPv6両対応）ソケットの挙動調整に関するものです。特に、DragonFly BSDがIPv6のIPv4-mappedアドレスのサポートを廃止したこと、および一部のカーネルバージョンでそのサポートが不正確であったことに対処しています。

## 変更の背景

この変更の背景には、DragonFly BSDオペレーティングシステムにおけるネットワークスタックの進化があります。具体的には、DragonFly BSDがIPv6のIPv4-mappedアドレスのサポートを段階的に廃止しているという事実が挙げられます。

IPv4-mappedアドレスとは、IPv6アドレス空間内にIPv4アドレスを埋め込む形式（例: `::ffff:192.0.2.1`）で、IPv6ソケットがIPv4通信も処理できるようにするために使用されます。これにより、アプリケーションは単一のIPv6ソケットでIPv4とIPv6の両方の接続を受け入れることができ、デュアルスタックアプリケーションの実装が簡素化されます。

しかし、DragonFly BSDのカーネルは、このIPv4-mappedアドレスのサポートを廃止する方向へと進んでいました。さらに問題だったのは、一部のリリースバージョンではカーネルがこの機能をサポートしているかのように振る舞うものの、実際には正しく機能しない（または`sysctl`を介してカーネルの状態を調整しない限り機能しない）という予測不能な挙動が見られたことです。

このような状況は、Goの`net`パッケージが提供するネットワーク機能、特にデュアルスタックソケットの信頼性に悪影響を及ぼす可能性がありました。予測不能な挙動を避けるため、Goの`net`パッケージは、すべてのDragonFly BSDカーネルがIPv6のIPv4-mappedアドレスをサポートしないと仮定するよう変更されました。これにより、DragonFly BSD上でのGoアプリケーションのネットワーク挙動が安定し、予測可能になります。

また、コミットメッセージには`Fixes #10764`とありますが、このIssueは公開されているGoのIssueトラッカーでは見つかりませんでした。これは内部的なIssueであるか、あるいは別のプラットフォームでの議論を指している可能性があります。

## 前提知識の解説

このコミットを理解するためには、以下のネットワーク関連の概念とGoの`net`パッケージの挙動に関する知識が必要です。

1.  **IPv4とIPv6**:
    *   **IPv4 (Internet Protocol version 4)**: 現在広く使われているインターネットプロトコルで、32ビットのアドレスを使用します。アドレス枯渇問題が深刻化しています。
    *   **IPv6 (Internet Protocol version 6)**: IPv4の後継として設計されたプロトコルで、128ビットのアドレスを使用し、より広大なアドレス空間を提供します。
2.  **デュアルスタックソケット**:
    *   単一のソケットでIPv4とIPv6の両方の通信を処理できるソケットのことです。これにより、アプリケーション開発者は両方のプロトコルに対応するために2つの異なるソケットを管理する必要がなくなります。
    *   通常、IPv6ソケットを作成し、`IPV6_V6ONLY`ソケットオプションを`0`に設定することで、IPv4-mappedアドレスを介してIPv4通信も受け入れることができます。
3.  **IPv4-mapped IPv6アドレス**:
    *   IPv6アドレス形式でIPv4アドレスを表現する方法です。`::ffff:C.D.E.F` の形式を取り、IPv6ソケットがIPv4パケットを処理する際に使用されます。
4.  **`IPV6_V6ONLY`ソケットオプション**:
    *   IPv6ソケットがIPv6通信のみを処理するか（`1`に設定）、IPv4-mappedアドレスを介してIPv4通信も処理するか（`0`に設定）を制御するソケットオプションです。
    *   多くのUnix系OSでは、デフォルトで`0`に設定されているか、または設定可能です。しかし、OpenBSDやDragonFly BSDのように、セキュリティや設計上の理由からこのオプションをサポートせず、常にIPv6通信のみを許可するシステムもあります。
5.  **Goの`net`パッケージ**:
    *   Go言語の標準ライブラリの一部で、ネットワークI/O機能を提供します。TCP/UDP接続、IPアドレスの解決、ソケットの作成など、低レベルから高レベルまでのネットワーク操作を抽象化して提供します。
    *   内部的には、OSのシステムコール（`socket`, `bind`, `listen`など）を呼び出してネットワーク操作を行います。
6.  **DragonFly BSDとOpenBSD**:
    *   両者ともBSD系のオペレーティングシステムです。
    *   **DragonFly BSD**: FreeBSD 4.xからフォークしたOSで、独自のカーネル設計（特にメッセージパッシングと軽量カーネルスレッド）に特徴があります。
    *   **OpenBSD**: セキュリティを最優先するOSとして知られ、多くのセキュリティ機能がデフォルトで有効になっています。このセキュリティポリシーの一環として、IPv6ソケットでのIPv4-mappedアドレスのサポートを意図的に無効にしていることがよくあります。これは、IPv6ソケットが意図せずIPv4トラフィックを処理することを防ぐためです。

## 技術的詳細

このコミットの技術的詳細の中心は、Goの`net`パッケージがDragonFly BSDおよびOpenBSD上でデュアルスタックソケットの挙動をどのように調整するかという点にあります。

Goの`net`パッケージは、`probeIPv6Stack()`関数を使用して、システムがIPv6をサポートしているか、そしてIPv4-mappedアドレスを介したIPv4通信をサポートしているかを検出します。この関数は、IPv6ソケットを作成し、`IPV6_V6ONLY=0`を設定しようと試みることで、システムの機能をプローブします。

しかし、DragonFly BSDでは、カーネルがIPv4-mappedアドレスのサポートを廃止しているにもかかわらず、一部のバージョンでは`IPV6_V6ONLY=0`の設定を「受け入れたかのように」振る舞うことがありました。これは、`setsockopt`がエラーを返さないにもかかわらず、実際にはソケットがIPv6通信のみを処理するという、矛盾した状態を引き起こします。このような予測不能な挙動は、Goアプリケーションがデュアルスタックソケットを期待して動作した場合に問題を引き起こす可能性があります。

OpenBSDも同様にIPv4-mappedアドレスをサポートしていませんが、こちらは`IPV6_V6ONLY=0`の設定を試みると明確にエラーを返すため、Goの`net`パッケージはOpenBSDの挙動をより正確に検出できます。

このコミットでは、この問題に対処するため、`probeIPv6Stack()`関数内で`runtime.GOOS`（Goが動作しているOS）をチェックし、`"dragonfly"`または`"openbsd"`の場合には、IPv4-mappedアドレスのサポートをプローブする部分をスキップするように変更しています。具体的には、`probes`スライスからIPv4-mappedアドレスのプローブ項目を削除し、これらのOSでは`supportsIPv4map`が常に`false`となるようにします。

これにより、Goの`net`パッケージは、DragonFly BSDおよびOpenBSD上ではIPv6ソケットがIPv4-mappedアドレスを介したIPv4通信を処理しないことを明示的に認識し、デュアルスタックソケットの挙動を適切に調整します。結果として、これらのOS上でIPv4とIPv6の両方に対応するアプリケーションを開発する場合、Goの`net`パッケージは内部的に2つの異なるソケット（IPv4用とIPv6用）を作成して管理するようになります。これは、これらのOSのネットワークスタックの設計に合致する挙動であり、予測不能な問題を回避します。

また、`setDefaultSockopts`関数でも`supportsIPv4map`のチェックが追加され、IPv4-mappedアドレスがサポートされていないシステムでは`IPV6_V6ONLY=0`を設定しようとしないようになっています。これにより、無効なソケットオプション設定によるエラーや無駄な処理を避けることができます。

テストコードも、この変更に合わせて調整されています。特に、`TestDualStackTCPListener`や`TestDualStackUDPListener`では、`supportsIPv4map`変数の値に基づいてテストの挙動が変更され、DragonFly BSDやOpenBSDのようなシステムでIPv4-mappedアドレスがサポートされない場合のテストロジックが適切に反映されるようになっています。

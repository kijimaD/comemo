## 元コミット内容

`database/sql`: 全ての接続がビジーな場合にステートメントの再準備を回避する

以前は、全ての接続がビジーな場合、プールから割り当てられた接続上で常にステートメントを再準備していました。これは、ほとんどの時間全ての接続がビジーである場合、各接続に対する準備済みステートメントの数が時間とともに増加し続けることを意味していました。

代わりに、空いている接続を取得した後、その接続上でステートメントが既に準備されているかどうかを確認し、もしそうであればステートメントハンドルを再利用します。

## 変更の背景

Goの `database/sql` パッケージは、データベース操作のための汎用的なインターフェースを提供します。このパッケージは、データベース接続のプールを管理し、アプリケーションが効率的にデータベースと対話できるようにします。

このコミット以前の挙動では、`database/sql` パッケージが管理する接続プールにおいて、全てのデータベース接続が一時的にビジー（使用中）になった場合、新しいクエリを実行するために接続が解放されるのを待つか、あるいは新しい接続が確立される必要がありました。問題は、接続が解放されて再利用される際に、その接続上で以前に準備されたステートメント（プリペアドステートメント）が適切に再利用されず、同じステートメントが繰り返し再準備されてしまう点にありました。

具体的には、`Stmt` オブジェクト（準備済みステートメントを表す）が `connStmt()` メソッドを通じてデータベース接続を取得する際、もし利用可能な接続が全てビジーであった場合、接続プールから新しい接続が取得されるか、既存の接続が解放されるのを待つことになります。この時、取得された接続が以前に同じステートメントを準備していたとしても、その準備済みステートメントハンドルが再利用されず、常に新しいステートメントとして再準備されていました。

この「常に再準備する」という挙動は、特に高負荷なシステムで全ての接続が頻繁にビジーになるような状況下で、以下のような問題を引き起こしました。

1.  **リソースの浪費**: データベースサーバー側で、同じSQLステートメントに対して複数の準備済みステートメントオブジェクトが作成され、メモリやその他のリソースを不必要に消費していました。
2.  **パフォーマンスの低下**: ステートメントの準備は、SQLのパース、最適化、実行計画の生成など、データベースサーバーにとってコストのかかる操作です。これが頻繁に繰り返されることで、全体的なクエリ実行パフォーマンスが低下していました。
3.  **スケーラビリティの阻害**: 準備済みステートメントの数が増加し続けることで、データベースサーバーのリソースが枯渇しやすくなり、アプリケーションのスケーラビリティが阻害される可能性がありました。

このコミットは、これらの問題を解決し、`database/sql` パッケージがより効率的に準備済みステートメントを管理し、データベースリソースを最適に利用できるようにすることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の概念が重要です。

1.  **`database/sql` パッケージ**: Go言語の標準ライブラリの一部で、SQLデータベースと対話するための汎用的なインターフェースを提供します。特定のデータベースドライバー（例: MySQL, PostgreSQL, SQLite）に依存しない抽象化レイヤーを提供し、アプリケーションコードがデータベースの種類に縛られずに記述できるようにします。
2.  **プリペアドステートメント (Prepared Statement)**: データベース操作の効率化とセキュリティ向上（SQLインジェクション対策）のために使用される技術です。SQLステートメントを一度データベースに送信して「準備」させ、その後に異なるパラメータをバインドして複数回実行することができます。データベースはステートメントを一度だけパース、コンパイル、最適化するため、繰り返し実行するクエリのパフォーマンスが向上します。
    -   `db.Prepare(query string)`: SQLクエリを準備し、`*sql.Stmt` オブジェクトを返します。
    -   `stmt.Exec(args ...interface{})`: 準備済みステートメントを実行します。
    -   `stmt.Query(args ...interface{})`: 準備済みステートメントを実行し、結果セットを返します。
3.  **データベース接続プール (Connection Pool)**: データベースへの接続はコストのかかる操作（ネットワークオーバーヘッド、認証など）です。接続プールは、事前に確立されたデータベース接続のセットを管理し、必要に応じてアプリケーションに提供します。これにより、接続の確立と切断のオーバーヘッドを削減し、アプリケーションのパフォーマンスを向上させます。接続が不要になった場合、プールに返却され、他のリクエストで再利用されます。
4.  **`driver.Stmt` インターフェース**: `database/sql` パッケージは、データベースドライバーが実装すべきインターフェースを定義しています。`driver.Stmt` は、準備済みステートメントを表すインターフェースで、データベースドライバーはこのインターフェースを実装して、実際のデータベース固有の準備済みステートメントハンドルを管理します。
5.  **`connStmt` 構造体**: `database/sql` パッケージ内部で、特定のデータベース接続 (`*driverConn`) とその接続上で準備された `driver.Stmt` (`si`) のペアを管理するために使用される内部構造体です。`Stmt` オブジェクトは、複数の `connStmt` をリストとして保持し、異なる接続上で同じSQLステートメントが準備された場合の情報を追跡します。

## 技術的詳細

このコミットの核心は、`database/sql` パッケージの `(*Stmt).connStmt()` メソッドのロジック変更にあります。このメソッドは、`Stmt` オブジェクト（準備済みステートメント）が実行される際に、そのステートメントを実行するための適切なデータベース接続と、その接続上で既に準備されている `driver.Stmt` ハンドルを取得する役割を担っています。

**変更前の挙動**:
変更前は、`connStmt()` メソッド内で、`s.css` (準備済みステートメントが準備されている接続とステートメントハンドルのリスト) をイテレートし、利用可能な接続 (`v.dc`) があるかを確認していました。
もし利用可能な接続が見つかった場合、その接続と既存の `driver.Stmt` ハンドル (`v.si`) をすぐに返していました。
しかし、もし `s.css` 内の全ての接続がビジーであった場合、`match` フラグは `false` のままでした。この場合、`s.db.conn()` を呼び出して新しい接続を取得するか、既存の接続が解放されるのを待っていました。
問題は、この新しく取得された（または解放された）接続に対して、**常に** `dc.prepareLocked(s.query)` を呼び出してステートメントを再準備していた点です。たとえその接続が以前に同じステートメントを準備していたとしても、その情報が利用されず、新しい `connStmt` エントリとして `s.css` に追加されていました。
この結果、特に接続プールが枯渇しやすい状況では、同じSQLステートメントが異なる接続上で何度も再準備され、`s.css` リストが不必要に肥大化し、データベースサーバー側のリソースも浪費されていました。

**変更後の挙動**:
変更後の `connStmt()` メソッドは、この問題を解決するためにロジックを改善しました。

1.  まず、`s.css` リストをイテレートし、利用可能な接続 (`v.dc`) があるかを確認します。もし利用可能な接続が見つかった場合、以前と同様にその接続と既存の `driver.Stmt` ハンドルを返します。ここまでは同じです。
2.  `s.css` 内の全ての接続がビジーであった場合、`s.db.conn()` を呼び出して、接続プールから利用可能な接続を取得するか、新しい接続を確立します。この時点では、この接続上でステートメントが既に準備されているかどうかはまだ確認していません。
3.  **重要な変更点**: 新しく取得された `dc` (データベース接続) に対して、`s.css` リストを**再度**イテレートします。この2回目のパスの目的は、**今取得した `dc` が、既に `s.css` リスト内のいずれかの `connStmt` エントリと一致するかどうか**、つまり、この接続上で既にこのステートメントが準備されているかどうかを確認することです。
4.  もし `v.dc == dc` となる `connStmt` エントリが見つかった場合、それはこの接続上でステートメントが既に準備されていることを意味します。この場合、新しいステートメントを準備する代わりに、既存の `v.si` (準備済みステートメントハンドル) を再利用して返します。
5.  もし2回目のパスでも一致するエントリが見つからなかった場合（つまり、新しく取得した接続上でこのステートメントがまだ準備されていない場合）、その時初めて `dc.prepareLocked(s.query)` を呼び出してステートメントを準備し、新しい `connStmt` エントリとして `s.css` に追加します。

この変更により、全ての接続がビジーな状況でも、接続が解放されて再利用される際に、その接続上で既に準備されているステートメントが適切に再利用されるようになります。これにより、不必要なステートメントの再準備が回避され、データベースリソースの効率的な利用とパフォーマンスの向上が図られます。

### `src/pkg/database/sql/sql.go` の `(*Stmt).connStmt()` メソッド

```go
func (s *Stmt) connStmt() (ci *driverConn, releaseConn func(error), si driver.Stmt, err error) {
	// ... (トランザクション関連の初期チェックは省略)

	// 最初のパス: 既存の準備済みステートメントを持つ利用可能な接続を探す
	for i := 0; i < len(s.css); i++ {
		v := s.css[i]
		_, err := s.db.connIfFree(v.dc) // 接続が利用可能かチェック
		if err == nil {
			// 利用可能な接続が見つかった場合、その接続と既存のステートメントを返す
			s.mu.Unlock() // ロックを解除
			return v.dc, v.dc.releaseConn, v.si, nil
		}
		if err == errConnClosed {
			// 無効な接続はリストから削除 (遅延削除)
			s.css = append(s.css[:i], s.css[i+1:]...)
			i--
		}
	}
	s.mu.Unlock() // ここで一度ロックを解除

	// 全ての接続がビジーな場合、新しい接続を取得するか、既存の接続が解放されるのを待つ
	dc, err := s.db.conn()
	if err != nil {
		return nil, nil, nil, err
	}

	// 2回目のパス: 新しく取得した接続が、既にこのステートメントを準備しているか確認
	s.mu.Lock() // 再度ロック
	for _, v := range s.css {
		if v.dc == dc {
			// 取得した接続が既にリストに存在し、ステートメントが準備済みの場合、それを再利用
			s.mu.Unlock() // ロックを解除
			return dc, dc.releaseConn, v.si, nil
		}
	}
	s.mu.Unlock() // ロックを解除

	// 既存の準備済みステートメントが見つからなかった場合、この接続上でステートメントを準備
	dc.Lock() // 接続のロック
	si, err = dc.prepareLocked(s.query) // ステートメントを準備
	dc.Unlock() // 接続のロック解除
	if err != nil {
		s.db.putConn(dc, err) // エラー時は接続をプールに戻す
		return nil, nil, nil, err
	}

	// 新しく準備したステートメントを `s.css` リストに追加
	s.mu.Lock() // 再度ロック
	cs := connStmt{dc, si}
	s.css = append(s.css, cs)
	s.mu.Unlock() // ロックを解除

	return dc, dc.releaseConn, si, nil // 準備されたステートメントを返す
}
```

この変更の肝は、`s.db.conn()` で接続を取得した後に、`s.css` リストを再度チェックする新しい `for` ループが追加された点です。これにより、接続プールから取得した接続が、以前に同じ `Stmt` オブジェクトのSQLクエリを準備したことがあるかどうかを確認し、もしそうであれば不必要な再準備を回避して既存の `driver.Stmt` ハンドルを再利用します。

Goの `database/sql` パッケージは、データベース操作のための汎用的なインターフェースを提供します。このパッケージは、データベース接続のプールを管理し、アプリケーションが効率的にデータベースと対話できるようにします。

このコミット以前の挙動では、`database/sql` パッケージが管理する接続プールにおいて、全てのデータベース接続が一時的にビジー（使用中）になった場合、新しいクエリを実行するために接続が解放されるのを待つか、あるいは新しい接続が確立される必要がありました。問題は、接続が解放されて再利用される際に、その接続上で以前に準備されたステートメント（プリペアドステートメント）が適切に再利用されず、同じステートメントが繰り返し再準備されてしまう点にありました。

具体的には、`Stmt` オブジェクト（準備済みステートメントを表す）が `connStmt()` メソッドを通じてデータベース接続を取得する際、もし利用可能な接続が全てビジーであった場合、接続プールから新しい接続が取得されるか、既存の接続が解放されるのを待つことになります。この時、取得された接続が以前に同じステートメントを準備していたとしても、その準備済みステートメントハンドルが再利用されず、常に新しいステートメントとして再準備されていました。

この「常に再準備する」という挙動は、特に高負荷なシステムで全ての接続が頻繁にビジーになるような状況下で、以下のような問題を引き起こしました。

1.  **リソースの浪費**: データベースサーバー側で、同じSQLステートメントに対して複数の準備済みステートメントオブジェクトが作成され、メモリやその他のリソースを不必要に消費していました。
2.  **パフォーマンスの低下**: ステートメントの準備は、SQLのパース、最適化、実行計画の生成など、データベースサーバーにとってコストのかかる操作です。これが頻繁に繰り返されることで、全体的なクエリ実行パフォーマンスが低下していました。
3.  **スケーラビリティの阻害**: 準備済みステートメントの数が増加し続けることで、データベースサーバーのリソースが枯渇しやすくなり、アプリケーションのスケーラビリティが阻害される可能性がありました。

このコミットは、これらの問題を解決し、`database/sql` パッケージがより効率的に準備済みステートメントを管理し、データベースリソースを最適に利用できるようにすることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の概念が重要です。

1.  **`database/sql` パッケージ**: Go言語の標準ライブラリの一部で、SQLデータベースと対話するための汎用的なインターフェースを提供します。特定のデータベースドライバー（例: MySQL, PostgreSQL, SQLite）に依存しない抽象化レイヤーを提供し、アプリケーションコードがデータベースの種類に縛られずに記述できるようにします。
2.  **プリペアドステートメント (Prepared Statement)**: データベース操作の効率化とセキュリティ向上（SQLインジェクション対策）のために使用される技術です。SQLステートメントを一度データベースに送信して「準備」させ、その後に異なるパラメータをバインドして複数回実行することができます。データベースはステートメントを一度だけパース、コンパイル、最適化するため、繰り返し実行するクエリのパフォーマンスが向上します。
    -   `db.Prepare(query string)`: SQLクエリを準備し、`*sql.Stmt` オブジェクトを返します。
    -   `stmt.Exec(args ...interface{})`: 準備済みステートメントを実行します。
    -   `stmt.Query(args ...interface{})`: 準備済みステートメントを実行し、結果セットを返します。
3.  **データベース接続プール (Connection Pool)**: データベースへの接続はコストのかかる操作（ネットワークオーバーヘッド、認証など）です。接続プールは、事前に確立されたデータベース接続のセットを管理し、必要に応じてアプリケーションに提供します。これにより、接続の確立と切断のオーバーヘッドを削減し、アプリケーションのパフォーマンスを向上させます。接続が不要になった場合、プールに返却され、他のリクエストで再利用されます。
4.  **`driver.Stmt` インターフェース**: `database/sql` パッケージは、データベースドライバーが実装すべきインターフェースを定義しています。`driver.Stmt` は、準備済みステートメントを表すインターフェースで、データベースドライバーはこのインターフェースを実装して、実際のデータベース固有の準備済みステートメントハンドルを管理します。
5.  **`connStmt` 構造体**: `database/sql` パッケージ内部で、特定のデータベース接続 (`*driverConn`) とその接続上で準備された `driver.Stmt` (`si`) のペアを管理するために使用される内部構造体です。`Stmt` オブジェクトは、複数の `connStmt` をリストとして保持し、異なる接続上で同じSQLステートメントが準備された場合の情報を追跡します。

## 技術的詳細

このコミットの核心は、`database/sql` パッケージの `(*Stmt).connStmt()` メソッドのロジック変更にあります。このメソッドは、`Stmt` オブジェクト（準備済みステートメント）が実行される際に、そのステートメントを実行するための適切なデータベース接続と、その接続上で既に準備されている `driver.Stmt` ハンドルを取得する役割を担っています。

**変更前の挙動**:
変更前は、`connStmt()` メソッド内で、`s.css` (準備済みステートメントが準備されている接続とステートメントハンドルのリスト) をイテレートし、利用可能な接続 (`v.dc`) があるかを確認していました。
もし利用可能な接続が見つかった場合、その接続と既存の `driver.Stmt` ハンドル (`v.si`) をすぐに返していました。
しかし、もし `s.css` 内の全ての接続がビジーであった場合、`match` フラグは `false` のままでした。この場合、`s.db.conn()` を呼び出して新しい接続を取得するか、既存の接続が解放されるのを待っていました。
問題は、この新しく取得された（または解放された）接続に対して、**常に** `dc.prepareLocked(s.query)` を呼び出してステートメントを再準備していた点です。たとえその接続が以前に同じステートメントを準備していたとしても、その情報が利用されず、新しい `connStmt` エントリとして `s.css` に追加されていました。
この結果、特に高負荷なシステムで全ての接続が頻繁にビジーになるような状況では、同じSQLステートメントが異なる接続上で何度も再準備され、`s.css` リストが不必要に肥大化し、データベースサーバー側のリソースも浪費されていました。

**変更後の挙動**:
変更後の `connStmt()` メソッドは、この問題を解決するためにロジックを改善しました。

1.  まず、`s.css` リストをイテレートし、利用可能な接続 (`v.dc`) があるかを確認します。もし利用可能な接続が見つかった場合、以前と同様にその接続と既存の `driver.Stmt` ハンドルを返します。ここまでは同じです。
2.  `s.css` 内の全ての接続がビジーであった場合、`s.db.conn()` を呼び出して、接続プールから利用可能な接続を取得するか、新しい接続を確立します。この時点では、この接続上でステートメントが既に準備されているかどうかはまだ確認していません。
3.  **重要な変更点**: 新しく取得された `dc` (データベース接続) に対して、`s.css` リストを**再度**イテレートします。この2回目のパスの目的は、**今取得した `dc` が、既に `s.css` リスト内のいずれかの `connStmt` エントリと一致するかどうか**、つまり、この接続上で既にこのステートメントが準備されているかどうかを確認することです。
4.  もし `v.dc == dc` となる `connStmt` エントリが見つかった場合、それはこの接続上でステートメントが既に準備されていることを意味します。この場合、新しいステートメントを準備する代わりに、既存の `v.si` (準備済みステートメントハンドル) を再利用して返します。
5.  もし2回目のパスでも一致するエントリが見つからなかった場合（つまり、新しく取得した接続上でこのステートメントがまだ準備されていない場合）、その時初めて `dc.prepareLocked(s.query)` を呼び出してステートメントを準備し、新しい `connStmt` エントリとして `s.css` に追加します。

この変更により、全ての接続がビジーな状況でも、接続が解放されて再利用される際に、その接続上で既に準備されているステートメントが適切に再利用されるようになります。これにより、不必要なステートメントの再準備が回避され、データベースリソースの効率的な利用とパフォーマンスの向上が図られます。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、`src/pkg/database/sql/sql.go` ファイルの `(*Stmt).connStmt()` メソッドと、`src/pkg/database/sql/sql_test.go` ファイルのテストコードにあります。

**`src/pkg/database/sql/sql.go` の変更点**:

-   `connStmt()` メソッド内のロジックが大幅に変更されています。
-   以前の `match` フラグと `cs` 変数の初期化が削除されました。
-   最初の `for` ループ内で、利用可能な接続が見つかった場合に即座に `return` するロジックが追加されました。
-   全ての接続がビジーであった場合の処理フローが変更され、まず `s.db.conn()` で接続を取得した後、その接続が `s.css` リストに既に存在するかどうかを再確認する新しい `for` ループが導入されました。
-   この2回目のチェックで既存の `connStmt` が見つかった場合、その `driver.Stmt` を再利用するようになりました。
-   見つからなかった場合にのみ、`dc.prepareLocked(s.query)` を呼び出してステートメントを新しく準備するようになりました。

**`src/pkg/database/sql/sql_test.go` の変更点**:

-   `TestErrBadConnReconnect` テスト関数に `forcePrepare` というヘルパー関数が追加されました。この関数は、`Stmt` オブジェクトの `css` フィールドを `nil` に設定することで、次の実行時にステートメントが強制的に再準備されるようにします。
-   既存のテストコードで、`stmt.css` を直接操作して接続をビジー状態にする代わりに、新しく追加された `forcePrepare` 関数を使用するように変更されました。これにより、テストの意図がより明確になり、新しいロジックのテストカバレッジが向上します。

## コアとなるコードの解説

### `src/pkg/database/sql/sql.go` の `(*Stmt).connStmt()` メソッド

```go
func (s *Stmt) connStmt() (ci *driverConn, releaseConn func(error), si driver.Stmt, err error) {
	// ... (トランザクション関連の初期チェックは省略)

	// 最初のパス: 既存の準備済みステートメントを持つ利用可能な接続を探す
	for i := 0; i < len(s.css); i++ {
		v := s.css[i]
		_, err := s.db.connIfFree(v.dc) // 接続が利用可能かチェック
		if err == nil {
			// 利用可能な接続が見つかった場合、その接続と既存のステートメントを返す
			s.mu.Unlock() // ロックを解除
			return v.dc, v.dc.releaseConn, v.si, nil
		}
		if err == errConnClosed {
			// 無効な接続はリストから削除 (遅延削除)
			s.css = append(s.css[:i], s.css[i+1:]...)
			i--
		}
	}
	s.mu.Unlock() // ここで一度ロックを解除

	// 全ての接続がビジーな場合、新しい接続を取得するか、既存の接続が解放されるのを待つ
	dc, err := s.db.conn()
	if err != nil {
		return nil, nil, nil, err
	}

	// 2回目のパス: 新しく取得した接続が、既にこのステートメントを準備しているか確認
	s.mu.Lock() // 再度ロック
	for _, v := range s.css {
		if v.dc == dc {
			// 取得した接続が既にリストに存在し、ステートメントが準備済みの場合、それを再利用
			s.mu.Unlock() // ロックを解除
			return dc, dc.releaseConn, v.si, nil
		}
	}
	s.mu.Unlock() // ロックを解除

	// 既存の準備済みステートメントが見つからなかった場合、この接続上でステートメントを準備
	dc.Lock() // 接続のロック
	si, err = dc.prepareLocked(s.query) // ステートメントを準備
	dc.Unlock() // 接続のロック解除
	if err != nil {
		s.db.putConn(dc, err) // エラー時は接続をプールに戻す
		return nil, nil, nil, err
	}

	// 新しく準備したステートメントを `s.css` リストに追加
	s.mu.Lock() // 再度ロック
	cs := connStmt{dc, si}
	s.css = append(s.css, cs)
	s.mu.Unlock() // ロックを解除

	return dc, dc.releaseConn, si, nil // 準備されたステートメントを返す
}
```

この変更の肝は、`s.db.conn()` で接続を取得した後に、`s.css` リストを再度チェックする新しい `for` ループが追加された点です。これにより、接続プールから取得した接続が、以前に同じ `Stmt` オブジェクトのSQLクエリを準備したことがあるかどうかを確認し、もしそうであれば不必要な再準備を回避して既存の `driver.Stmt` ハンドルを再利用します。

### `src/pkg/database/sql/sql_test.go` の変更点

```go
// Provide a way to force a re-prepare of a statement on next execution
forcePrepare := func(stmt *Stmt) {
	stmt.css = nil
}

// ... (TestErrBadConnReconnect 関数内)

// stmt1 のテスト
// make sure we must prepare the stmt first
// 以前のコード:
// for _, cs := range stmt1.css {
// 	cs.dc.inUse = true
// }
forcePrepare(stmt1) // 新しいヘルパー関数を使用

// stmt2 のテスト
// make sure we must prepare the stmt first
// 以前のコード:
// for _, cs := range stmt2.css {
// 	cs.dc.inUse = true
// }
forcePrepare(stmt2) // 新しいヘルパー関数を使用
```

`forcePrepare` ヘルパー関数は、テストの可読性と保守性を向上させます。`stmt.css = nil` とすることで、`Stmt` オブジェクトが保持している準備済みステートメントのキャッシュをクリアし、次の実行時に必ずステートメントが再準備される状況をシミュレートします。これは、このコミットが解決しようとしている「再準備の回避」ロジックが正しく機能するかどうかを検証するために重要です。

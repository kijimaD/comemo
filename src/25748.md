# [インデックス 25748] ファイルの概要

このコミットは、Goの`net/http`パッケージにおける`Transport`の挙動に関する回帰バグを修正するものです。具体的には、HTTPリクエストのメソッドが空文字列である場合に、それが「GET」として扱われるというGoの`net/http`パッケージのドキュメントに記載された振る舞いが、以前のコミットによって意図せず無効化されてしまった問題を解決します。

## 元コミット内容

このコミットは、`net/http`パッケージの`Transport`が空のメソッドを受け入れるように再度修正するものです。以前のコミット`https://golang.org/cl/16829`によって導入された「`NewRequest`および`Transport.RoundTrip`で有効なメソッドを要求する」という変更が原因で発生した回帰バグを修正します。Goのドキュメントによれば、空文字列は有効なメソッドであり、「GET」を意味します。このコミットはIssue #13311を修正します。

## 変更の背景

この変更の背景には、Goの`net/http`パッケージにおけるHTTPメソッドの取り扱いに関する設計上の考慮と、その後の実装における回帰バグの発生があります。

元々、Goの`net/http`パッケージのクライアント側（特に`http.Request`構造体）では、`Method`フィールドが空文字列の場合にHTTPの「GET」メソッドとして解釈されるという仕様がありました。これは、利便性のため、またはHTTP/1.1のデフォルトメソッドがGETであることに起因する慣習的な振る舞いとしてドキュメントに明記されていました。

しかし、`https://golang.org/cl/16829`（コミットハッシュ`0b314e1`）という以前のコミットで、「`NewRequest`および`Transport.RoundTrip`で有効なメソッドを要求する」という変更が導入されました。この変更の目的は、HTTPメソッド文字列の堅牢性を高め、例えば「` GET`」のような不正な形式のメソッドが使用されることを防ぐことにありました。これにより、異なるHTTPサーバー間での挙動の不整合を防ぎ、より予測可能なHTTPリクエストの生成を保証しようとしました。

この堅牢性向上のための変更が、意図せずGoの`net/http`パッケージが持つ「空文字列メソッドはGETを意味する」という既存のドキュメント化された振る舞いを壊してしまいました。結果として、空文字列メソッドを持つリクエストが`Transport.RoundTrip`によって無効と判断され、エラーとなる回帰バグが発生しました。これがIssue #13311として報告され、本コミットによって修正されることになりました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **HTTPメソッド**: HTTP（Hypertext Transfer Protocol）において、クライアントがサーバーにどのような操作を要求するかを示すものです。代表的なものにGET（リソースの取得）、POST（データの送信）、PUT（リソースの更新）、DELETE（リソースの削除）などがあります。HTTP/1.1の仕様では、メソッドはトークンとして定義され、空白文字などを含まない特定の形式である必要があります。
2.  **Goの`net/http`パッケージ**: Go言語の標準ライブラリの一部で、HTTPクライアントおよびサーバーの実装を提供します。Webアプリケーションの構築やHTTPリクエストの送信に広く利用されます。
3.  **`http.Request`構造体**: `net/http`パッケージでHTTPリクエストを表す構造体です。この構造体には、リクエストメソッド（`Method`フィールド）、URL（`URL`フィールド）、ヘッダー（`Header`フィールド）、ボディ（`Body`フィールド）などが含まれます。
4.  **`http.Transport`**: `net/http`パッケージにおいて、HTTPリクエストを実際に送信し、レスポンスを受信する低レベルのメカニズムを提供する構造体です。コネクションの管理、プロキシの利用、TLSハンドシェイクなどを担当します。`http.Client`は内部的に`http.Transport`を利用してリクエストを処理します。
5.  **`RoundTrip`メソッド**: `http.Transport`インターフェースの主要なメソッドで、単一のHTTPリクエストを送信し、そのレスポンスを受け取る役割を担います。
6.  **回帰バグ (Regression Bug)**: 以前は正しく動作していた機能が、新しい変更（コードの追加、修正など）によって再び動作しなくなる、または誤動作するようになるバグのことです。
7.  **Goのドキュメントと慣習**: Go言語の標準ライブラリは、そのドキュメントが非常に重要です。ドキュメントに記載された振る舞いは、Goプログラマーにとって信頼できる契約となります。特に`net/http`パッケージのように広く使われるライブラリでは、ドキュメントと実際の挙動の一貫性が極めて重要です。

## 技術的詳細

本コミットは、`net/http`パッケージの`Transport.RoundTrip`メソッドにおけるHTTPメソッドの検証ロジックを修正することで、回帰バグを解決しています。

以前のコミット`0b314e1`では、`validMethod(req.Method)`という関数呼び出しによって、リクエストメソッドが有効であるかを厳密にチェックしていました。この`validMethod`関数は、HTTPメソッドがRFCに準拠した形式であるか（例えば、空白文字を含まないか、予約文字を使用していないかなど）を確認するものです。この厳密なチェックは、不正なメソッド文字列による潜在的な問題を回避するために導入されました。

しかし、Goの`net/http`パッケージのドキュメントでは、`http.Request`の`Method`フィールドが空文字列の場合、クライアントリクエストでは「GET」を意味すると明記されていました。`validMethod`関数は空文字列を有効なHTTPメソッドとして認識しないため、このドキュメント化された振る舞いが壊れてしまいました。

本コミットでは、この問題を解決するために、`Transport.RoundTrip`内のメソッド検証ロジックを以下のように変更しています。

```diff
-	if !validMethod(req.Method) {
+	if req.Method != "" && !validMethod(req.Method) {
		return nil, fmt.Errorf("net/http: invalid method %q", req.Method)
	}
```

この変更により、`req.Method`が空文字列である場合には`validMethod`関数が呼び出されなくなります。つまり、空文字列のメソッドは特別なケースとして扱われ、`validMethod`による検証をスキップします。これにより、Goのドキュメントに記載されている「空文字列メソッドはGETを意味する」という振る舞いが再び有効になります。

この修正は、`net/http`パッケージの内部的な整合性と、ユーザーが期待するドキュメント化された振る舞いの両方を維持するために重要です。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更点

-   **変更前**: `if !validMethod(req.Method)`
    -   これは、`req.Method`が空文字列であっても、常に`validMethod`関数を呼び出してその有効性をチェックしていました。`validMethod`は空文字列を有効なHTTPメソッドとして認識しないため、ここでエラーが発生していました。
-   **変更後**: `if req.Method != "" && !validMethod(req.Method)`
    -   この変更により、`validMethod`関数が呼び出される前に`req.Method != ""`という条件が追加されました。
    -   もし`req.Method`が空文字列であれば、`req.Method != ""`は`false`となり、`&&`演算子の短絡評価により`!validMethod(req.Method)`の部分は評価されません。結果として、空文字列のメソッドはエラーにならず、`Transport`はGoのドキュメントに従ってそれを「GET」として処理できるようになります。
    -   `req.Method`が空文字列でない場合は、引き続き`validMethod`が呼び出され、不正な形式のメソッド文字列が検出されます。これにより、堅牢性向上の目的も維持されます。

### `src/net/http/transport_test.go` の変更点

-   **`TestTransportNoHost`の修正**:
    -   以前は`Request`の初期化時に`Method: "GET"`が明示的に指定されていましたが、この行が削除されました。これは、テストの意図（ホストがない場合の挙動）とは直接関係ないメソッド指定を削除し、より簡潔にするため、または新しい`TestTransportEmptyMethod`との整合性を取るためと考えられます。
-   **`TestTransportEmptyMethod`の追加**:
    -   この新しいテストケースは、Issue #13311で報告された問題を直接検証するために追加されました。
    -   `NewRequest("GET", "http://foo.com/", nil)`でリクエストを作成した後、`req.Method = ""`と明示的に空文字列を設定しています。
    -   `httputil.DumpRequestOut(req, false)`を使用して、`Transport`が内部的にどのようにリクエストを処理するかをダンプします。`httputil.DumpRequestOut`は内部で`Transport`を使用するため、`Transport`の挙動をテストするのに適しています。
    -   ダンプされたリクエスト文字列に「`GET `」という部分文字列が含まれているかを`strings.Contains`で確認しています。これにより、空文字列のメソッドが正しく「GET」として解釈され、HTTPリクエストラインが「GET / HTTP/1.1」のような形式で生成されていることを検証しています。
    -   このテストの追加により、将来的に同様の回帰バグが発生することを防ぐための安全網が提供されます。

これらの変更により、Goの`net/http`パッケージは、ドキュメントに記載された「空文字列メソッドはGETを意味する」という振る舞いを維持しつつ、不正な形式のHTTPメソッドに対する堅牢性も確保できるようになりました。

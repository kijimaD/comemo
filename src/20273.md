# [インデックス 20273] ファイルの概要

このコミットは、GoランタイムにおけるOpenBSD/386アーキテクチャ向けの`tfork`システムコール実装のバグ修正と、`tfork`の戻り値の型をOpenBSDの`pid_t`の実際のサイズに合わせるための変更を含んでいます。

変更されたファイルは以下の通りです。

*   `src/pkg/runtime/os_openbsd.c`: OpenBSD固有のC言語ランタイムファイル。`runtime·tfork`関数のC言語でのプロトタイプ宣言が含まれています。
*   `src/pkg/runtime/os_openbsd.go`: OpenBSD固有のGo言語ランタイムファイル。`tfork`関数のGo言語での宣言が含まれています。
*   `src/pkg/runtime/sys_openbsd_386.s`: OpenBSD/386アーキテクチャ向けのGoアセンブリコード。`runtime·tfork`の具体的な実装が含まれています。
*   `src/pkg/runtime/sys_openbsd_amd64.s`: OpenBSD/AMD64アーキテクチャ向けのGoアセンブリコード。`runtime·tfork`の具体的な実装が含まれています。

## 元コミット内容

このコミットは、GoランタイムのOpenBSD/386アーキテクチャにおける`tfork`システムコールの実装に関する2つの問題を修正します。

1.  以前のリビジョン`05c3fee13eb3`において、OpenBSD/386の`tfork`実装で、誤って`"params"`パラメータを使用すべき箇所で`"psize"`パラメータが使用されていました。これにより、`tfork`システムコールへの引数が正しく渡されず、スレッド作成に問題が生じる可能性がありました。
2.  OpenBSDの`__tfork`システムコールは、`pid_t`型の値を返しますが、これは全てのOpenBSDアーキテクチャで`int32`として定義されています。しかし、Goランタイムの`runtime.tfork`関数は誤って`int64`を返すように宣言されていました。このコミットでは、`runtime.tfork`の戻り値を`int64`から`int32`に変更し、それに合わせてアセンブリ実装も更新しています。

## 変更の背景

このコミットの背景には、GoランタイムがOpenBSD上で新しいスレッド（GoにおけるM/GモデルのM、つまりOSスレッド）を作成する際の正確性と互換性の確保があります。

Goランタイムは、Goルーチンを効率的に実行するために、必要に応じてOSスレッドを生成・管理します。OpenBSDのようなUNIX系OSでは、新しいスレッドを作成するために特定のシステムコールを使用します。OpenBSDでは、この目的のために`__tfork`システムコールが提供されています。

変更の具体的な背景は以下の2点です。

1.  **誤ったパラメータの使用**: 以前のコミットで、OpenBSD/386のアセンブリコードにおいて、`tfork`システムコールに渡す引数のオフセットが誤っていました。これにより、本来渡すべき`param`（新しいスレッドのパラメータ構造体へのポインタ）ではなく、`psize`（パラメータ構造体のサイズ）が誤って参照されていました。これは、スレッドの初期化に必要な情報が正しく渡されないため、ランタイムの不安定性やクラッシュを引き起こす可能性のある重大なバグでした。
2.  **戻り値の型不一致**: OpenBSDのシステムコールは、通常、成功時にはプロセスID（`pid_t`）を返し、失敗時にはエラーコードを返します。OpenBSDでは、`pid_t`は32ビット整数として定義されています。しかし、Goランタイムの`tfork`のGo言語およびC言語の宣言では、戻り値が64ビット整数（`int64`）とされていました。これは、実際のOSのAPIとの不一致であり、特に32ビットアーキテクチャである386では、戻り値の解釈に問題が生じる可能性がありました。この修正は、GoランタイムがOSのAPIと正確に連携するための整合性確保を目的としています。

これらの問題は、GoランタイムがOpenBSD上で安定して動作し、正しくスレッドを管理するために不可欠な修正でした。

## 前提知識の解説

### OpenBSDの`tfork`システムコール

`tfork`（具体的には`__tfork()`）は、OpenBSDに特有の低レベルなシステムコールで、既存のプロセス内で新しいカーネルスレッドを作成するために使用されます。Linuxの`clone()`システムコールに似ていますが、OpenBSDではプロセス作成のための`vfork()`とは区別されています。

*   **目的**: 新しいスレッドを作成し、呼び出し元プロセスのアドレス空間を共有します。
*   **OpenBSD固有**: このシステムコールはOpenBSDに特有であり、移植性のあるアプリケーション向けではありません。
*   **低レベル**: 通常、ユーザー空間のアプリケーションは直接`__tfork()`を呼び出すのではなく、より高レベルなラッパー関数（例: `__tfork_thread()`）を使用します。Goランタイムのような低レベルな部分では、直接システムコールを呼び出すためにアセンブリコードを使用することがあります。
*   **戻り値**: 成功した場合、新しいスレッドのID（`pid_t`）を返します。

### `pid_t`型

`pid_t`は、プロセスID（Process ID）やスレッドID（Thread ID）を表すために使用されるデータ型です。UNIX系OSで広く使われています。

*   **サイズ**: OpenBSDでは、`pid_t`は全てのアーキテクチャにおいて32ビット符号付き整数（`int32`）として定義されています。

### Goアセンブリの基本

Go言語は、Goアセンブリと呼ばれる独自の擬似アセンブリ言語を使用します。これは、基盤となるハードウェアの機械語命令に直接1対1でマッピングされるのではなく、より抽象的な表現を提供します。この抽象化により、Goは異なるアーキテクチャ間での移植性を高めています。

*   **命令の形式**: Goアセンブリの命令は、通常、`OPCODE source, destination`の形式を取ります。ソースが左、デスティネーションが右です。

#### 主要な命令と擬似レジスタ

*   **`MOVL` (Move Long)**:
    *   4バイト（32ビット）の値を移動する命令です。
    *   例: `MOVL $123, AX` は、値123を`AX`レジスタに移動します。
*   **`MOVQ` (Move Quad)**:
    *   8バイト（64ビット）の値を移動する命令です。
    *   例: `MOVQ $123, AX` は、値123を`AX`レジスタに移動します。
    *   32ビットアーキテクチャ（386）では、64ビット値を扱う場合、上位32ビットと下位32ビットを別々に扱う必要があります。
*   **`FP` (Frame Pointer)**:
    *   これは実際のハードウェアレジスタではなく、**擬似レジスタ**です。
    *   関数引数やスタック上の戻り値を参照するために使用されます。
    *   Goコンパイラがこの仮想フレームポインタを管理し、引数は`FP`からの正のオフセットでアクセスされます。
    *   例: `param+0(FP)` は、関数の最初の引数`param`を参照します。`psize+4(FP)`は、`psize`引数を参照し、そのオフセットが4バイトであることを示します（32ビットシステムで2番目の引数など）。
*   **`SB` (Static Base Pointer)**:
    *   これも**擬似レジスタ**で、グローバルシンボルテーブル、またはメモリの原点を表します。
    *   主にグローバル関数やデータの宣言と参照に使用されます。
    *   例: `runtime·tfork(SB)` は、グローバルシンボル`runtime·tfork`のアドレスを参照します。

## 技術的詳細

このコミットは、OpenBSD/386におけるGoランタイムの`tfork`実装の2つの主要な技術的課題に対処しています。

### 1. `param`と`psize`の誤用修正

Goランタイムの`tfork`関数は、新しいスレッドの初期化に必要なパラメータを含む構造体へのポインタ（`param`）と、その構造体のサイズ（`psize`）を受け取ります。

元のバグは、リビジョン`05c3fee13eb3`で導入されました。`src/pkg/runtime/sys_openbsd_386.s`内の`runtime·tfork`アセンブリ実装において、`tfork`システムコールに渡す引数を準備する際に、誤って`psize`引数のオフセット（`psize+4(FP)`）から値を読み取ってしまい、本来読み取るべき`param`引数のオフセット（`param+0(FP)`）から読み取っていませんでした。

具体的には、以下の行が問題でした。
`- MOVL psize+4(FP), AX`
これは、`psize`引数のアドレスから4バイトオフセットした場所の値を`AX`レジスタに移動していました。しかし、Goの関数呼び出し規約では、`param`は最初の引数であり、`param+0(FP)`でアクセスされるべきでした。

修正後は以下のようになります。
`+ MOVL param+0(FP), AX`
これにより、`param`引数（新しいスレッドのパラメータ構造体へのポインタ）が正しく`AX`レジスタにロードされ、`tfork`システムコールに正しい情報が渡されるようになります。これは、新しいスレッドが正しく初期化されるために不可欠な修正です。

### 2. `tfork`戻り値の型を`int64`から`int32`へ変更

OpenBSDの`__tfork`システムコールは、成功時に`pid_t`型の値を返します。OpenBSDの定義では、`pid_t`は32ビット符号付き整数（`int32`）です。

しかし、Goランタイムの`runtime.tfork`関数は、Go言語 (`src/pkg/runtime/os_openbsd.go`) とC言語 (`src/pkg/runtime/os_openbsd.c`) の両方で`int64`を返すように宣言されていました。

この不一致は、特に32ビットアーキテクチャである386では問題を引き起こす可能性があります。システムコールが32ビット値を返すにもかかわらず、Goランタイムが64ビット値として解釈しようとすると、上位32ビットが不定になったり、誤った値として扱われたりする可能性があります。

このコミットでは、以下の変更が行われました。

*   **Go言語とC言語の宣言の変更**:
    *   `src/pkg/runtime/os_openbsd.c`と`src/pkg/runtime/os_openbsd.go`で、`tfork`の戻り値の型が`int64`から`int32`に変更されました。
*   **アセンブリ実装の変更**:
    *   `src/pkg/runtime/sys_openbsd_386.s`では、`tfork`システムコールの戻り値（`AX`レジスタに格納される）をGoの戻り値スロットに格納する際に、`MOVL`命令を使用するように変更されました。以前は`MOVL`と`$-1`または`$0`を組み合わせて64ビット値を構築しようとしていましたが、これは不要になり、`MOVL`で32ビット値を直接格納するようになりました。
    *   `src/pkg/runtime/sys_openbsd_amd64.s`でも同様に、`MOVQ`命令が`MOVL`命令に変更されました。AMD64ではレジスタは64ビットですが、`pid_t`が32ビットであるため、上位ビットをゼロクリアする意味合いで`MOVL`を使用することで、正しい32ビット値として扱われるようにします。

これらの変更により、GoランタイムはOpenBSDの`__tfork`システムコールから返される`pid_t`値を正確に解釈し、Goの型システムと整合性を保つことができるようになります。

## コアとなるコードの解説

### `src/pkg/runtime/os_openbsd.c` および `src/pkg/runtime/os_openbsd.go`

これらのファイルでは、`runtime·tfork`（C言語）および`tfork`（Go言語）の関数シグネチャが変更されています。

*   **変更前**: `int64 runtime·tfork(...)` / `func tfork(...) int64`
*   **変更後**: `int32 runtime·tfork(...)` / `func tfork(...) int32`

これは、OpenBSDの`__tfork`システムコールが返す`pid_t`が32ビット整数であるという事実に基づいています。GoランタイムがOSのAPIと正確に連携するために、Go側での戻り値の型も32ビットに合わせるように修正されました。

### `src/pkg/runtime/sys_openbsd_386.s` (32ビットアーキテクチャ)

このファイルは、OpenBSD/386における`tfork`システムコールのGoアセンブリ実装です。

1.  **`param`と`psize`の誤用修正**:
    *   **変更前**: `MOVL psize+4(FP), AX`
        *   これは、`psize`引数のスタック上のオフセット`+4`から値を読み込み、`AX`レジスタに格納していました。しかし、これは誤りでした。
    *   **変更後**: `MOVL param+0(FP), AX`
        *   これは、`param`引数（関数の最初の引数）のスタック上のオフセット`+0`から値を読み込み、`AX`レジスタに格納しています。これにより、`tfork`システムコールに渡されるべき正しいパラメータ構造体へのポインタが`AX`にセットされるようになります。

2.  **戻り値の処理の変更**:
    *   `tfork`システムコールが失敗した場合（`JCC`命令の後のブロック）と、親プロセスで成功した場合（`CMPL AX, $0`の後のブロック）の両方で、戻り値の処理が簡素化されました。
    *   **変更前**:
        ```assembly
        MOVL	AX, ret_lo+20(FP)
        MOVL	$-1, ret_hi+24(FP) // または $0
        ```
        *   これは、32ビットの`AX`レジスタの値を`ret_lo`（戻り値の下位32ビット）に格納し、`ret_hi`（戻り値の上位32ビット）に`-1`または`0`を明示的に格納することで、64ビットの戻り値を構築しようとしていました。
    *   **変更後**:
        ```assembly
        MOVL	AX, ret+20(FP)
        ```
        *   `tfork`の戻り値の型が`int32`に変更されたため、`AX`レジスタの32ビット値を直接`ret`（戻り値）のスタック上の位置に格納するだけでよくなりました。これにより、コードが簡潔になり、32ビットの戻り値が正しく扱われるようになります。

### `src/pkg/runtime/sys_openbsd_amd64.s` (64ビットアーキテクチャ)

このファイルは、OpenBSD/AMD64における`tfork`システムコールのGoアセンブリ実装です。

*   **関数シグネチャのコメント変更**:
    *   `// int64 tfork(...)` から `// int32 tfork(...)` へとコメントが変更され、戻り値の型が`int32`になったことが示されています。

*   **戻り値の処理の変更**:
    *   `tfork`システムコールが失敗した場合と、親プロセスで成功した場合の両方で、戻り値の処理が変更されました。
    *   **変更前**: `MOVQ AX, ret+40(FP)`
        *   これは、`AX`レジスタ（64ビット）の値を`ret`（戻り値）のスタック上の位置に格納していました。
    *   **変更後**: `MOVL AX, ret+40(FP)`
        *   `tfork`の戻り値の型が`int32`に変更されたため、`MOVL`命令を使用するように変更されました。AMD64では`AX`レジスタは64ビットですが、`MOVL`を使用することで、`AX`の下位32ビットのみが`ret`に格納され、上位ビットはゼロクリアされます。これにより、`pid_t`が32ビット値として正しく扱われるようになります。

これらの変更は、GoランタイムがOpenBSDの`tfork`システムコールと正確にインターフェースし、特に32ビットアーキテクチャでのデータ整合性を確保するために重要です。

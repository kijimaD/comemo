# [インデックス 24916] ファイルの概要

このコミットは、Go言語の `text/template` パッケージにおいて、テンプレートのアクション間の空白（スペース、タブ、改行）をトリミングする機能を追加するものです。これにより、テンプレートの可読性を損なうことなく、生成される出力の不要な空白を制御できるようになります。特に、HTMLやXMLなどの構造化されたテキストを生成する際に、余分な空白が問題となるケースに対応しています。

## コミット

Date:   Tue Sep 8 14:58:12 2015 -0700

    text/template: provide a way to trim leading and trailing space between actions
    
    Borrowing a suggestion from the issue listed below, we modify the lexer to
    trim spaces at the beginning (end) of a block of text if the action immediately
    before (after) is marked with a minus sign. To avoid parsing/lexing ambiguity,
    we require an ASCII space between the minus sign and the rest of the action.
    Thus:
    
            {{23 -}}
            <
            {{- 45}}
    
    produces the output
            23<45
    
    All the work is done in the lexer. The modification is invisible to the parser
    or any outside package (except I guess for noticing some gaps in the input
    if one tracks error positions). Thus it slips in without worry in text/template
    and html/template both.
    
    Fixes long-requested issue #9969.

## 元コミット内容

このコミットは、`text/template` パッケージに、テンプレートアクションの前後にある空白をトリミングする機能を追加します。これは、アクションの区切り文字（`{{` または `}}`）の直後にマイナス記号（`-`）とASCIIスペースを配置することで実現されます。

具体的には、
- `{{- ` のように左区切り文字の直後に `- ` がある場合、そのアクションの直前のテキストの末尾にある空白がすべてトリミングされます。
- ` -}}` のように右区切り文字の直前に ` -` がある場合、そのアクションの直後のテキストの先頭にある空白がすべてトリミングされます。

この変更は、テンプレートの字句解析器（lexer）で完結しており、構文解析器（parser）や外部パッケージからは透過的です。これにより、`text/template` および `html/template` の両方で安全にこの機能が利用可能になります。

この機能は、長らく要望されていた [Issue #9969](https://github.com/golang/go/issues/9969) を解決するものです。

## 変更の背景

Goの `text/template` パッケージは、強力なテキスト生成機能を提供しますが、テンプレートの記述スタイルと生成される出力の間の空白の扱いに課題がありました。特に、テンプレートの可読性を高めるために改行やインデントを多用すると、それがそのまま出力に反映され、意図しない余分な空白が生成されることがありました。

この問題は、特に以下のようなシナリオで顕著でした。
1.  **HTML/XML生成**: HTMLやXMLでは、要素間の余分な空白がレンダリングに影響を与えたり、ファイルサイズを不必要に増加させたりすることがあります。
2.  **JSON/YAML生成**: 機械可読なデータ形式では、厳密なフォーマットが求められるため、意図しない空白はパースエラーの原因となる可能性があります。
3.  **コード生成**: ソースコードを生成する際に、インデントや改行の制御が難しく、生成されたコードが不格好になることがありました。

[Issue #9969](https://github.com/golang/go/issues/9969) は、このようなテンプレートにおける空白制御の難しさを指摘し、より柔軟なトリミング機構の導入を求めるものでした。開発者は、テンプレートのソースコードをきれいに保ちつつ、出力から不要な空白を削除する方法を求めていました。

## 前提知識の解説

このコミットを理解するためには、Go言語の `text/template` パッケージの基本的な動作原理と、コンパイラ/インタプリタの一般的な構造に関する知識が役立ちます。

### Go `text/template` パッケージ
`text/template` は、Go言語に組み込まれているテンプレートエンジンです。プレースホルダーや制御構造（条件分岐、ループなど）を含むテキストテンプレートを定義し、データ構造を適用して最終的なテキスト出力を生成します。
主な構成要素は以下の通りです。
-   **テンプレートソース**: ユーザーが記述する、プレースホルダーやアクションを含むテキスト。
-   **アクション**: `{{...}}` で囲まれた部分で、変数、関数呼び出し、制御構造などが記述されます。
-   **字句解析器 (Lexer)**: テンプレートソースを読み込み、意味のある最小単位（トークン、例: `{{`, `}}`, 識別子、文字列、数値など）に分割します。
-   **構文解析器 (Parser)**: 字句解析器が生成したトークンのストリームを受け取り、それらを構文規則に従って抽象構文木（AST: Abstract Syntax Tree）に構築します。
-   **実行エンジン (Executor)**: 抽象構文木と提供されたデータを基に、最終的なテキスト出力を生成します。

### 字句解析 (Lexing) と構文解析 (Parsing)
コンパイラやインタプリタのフロントエンドは、通常、字句解析と構文解析の2つのフェーズに分かれます。
-   **字句解析 (Lexical Analysis)**: ソースコードを文字のストリームとして読み込み、正規表現などのパターンマッチングを用いて、予約語、識別子、演算子、リテラルなどの「トークン」に分割します。この段階では、個々のトークンの意味は考慮されますが、それらのトークンがどのように組み合わさって文を構成するかは考慮されません。空白やコメントは通常、この段階で破棄されるか、特別なトークンとして扱われます。
-   **構文解析 (Syntactic Analysis)**: 字句解析器が生成したトークンのストリームを受け取り、言語の文法規則（BNFなど）に従って、トークンが正しい順序と構造で並んでいるかを検証し、抽象構文木（AST）を構築します。この段階で、プログラムの構造が明確になります。

このコミットの重要な点は、「すべての作業は字句解析器で行われる」という点です。これは、空白トリミングのロジックが、トークンを生成する前の段階で適用されることを意味します。構文解析器は、トリミングされた後のトークンストリームを受け取るため、この変更の影響を受けません。これにより、既存の構文解析ロジックを複雑にすることなく、新しい機能が導入されています。

## 技術的詳細

このコミットの技術的詳細の核心は、`text/template` の字句解析器 (`src/text/template/parse/lex.go`) に、新しい空白トリミングのルールを組み込んだ点にあります。

### 新しいトリミングマーカー
導入されたトリミングマーカーは以下の通りです。
-   `leftTrimMarker = "- "` (左区切り文字 `{{` の直後に続く場合)
-   `rightTrimMarker = " -"` (右区切り文字 `}}` の直前に続く場合)

これらのマーカーは、マイナス記号とASCIIスペースの組み合わせで構成されます。ASCIIスペースが必須である理由は、`{{-3}}` のような負の数を表す式との曖昧さを避けるためです。これにより、`{{- 3}}` はトリミングマーカーとして解釈され、`{{-3}}` は `-3` という数値として解釈されます。

### 字句解析器の変更点
字句解析器は、テンプレートソースをスキャンし、`{{` や `}}` といったアクションの区切り文字を検出する際に、これらのトリミングマーカーの存在をチェックするように変更されました。

1.  **`lexText` 関数**:
    -   この関数は、アクションの区切り文字 `{{` が現れるまで通常のテキストをスキャンします。
    -   `l.atLeftDelim()` という新しいヘルパー関数が導入され、現在の位置が左区切り文字 `{{` であるかどうか、そしてその直後に `leftTrimMarker` (`- `) が続くかどうかを判定します。
    -   もし `{{- ` が検出された場合、そのアクションの直前のテキストブロック (`l.input[l.start:l.pos]`) の末尾にある空白文字（スペース、タブ、キャリッジリターン、改行）の長さを `rightTrimLength` 関数で計算します。
    -   計算された長さ分だけ `l.pos` を戻し、`itemText` トークンを発行します。これにより、末尾の空白がトークンに含まれなくなります。
    -   その後、`l.pos` を元の位置に戻し、`l.ignore()` を呼び出して `{{- ` マーカー自体を破棄します。

2.  **`lexLeftDelim` 関数**:
    -   左区切り文字 `{{` をスキャンする関数です。
    -   ここでも `leftTrimMarker` の存在がチェックされ、もし存在すれば、そのマーカーの長さ分だけ `l.pos` を進め、`l.ignore()` でマーカーを破棄します。これにより、`{{- ` 全体が1つの左区切りトークンとして扱われ、`- ` 部分は出力されません。

3.  **`lexRightDelim` 関数**:
    -   右区切り文字 `}}` をスキャンする関数です。
    -   `rightTrimMarker` (` -`) の存在がチェックされ、もし存在すれば、そのマーカーの長さ分だけ `l.pos` を進め、`l.ignore()` でマーカーを破棄します。
    -   さらに、`leftTrimLength` 関数が導入され、` -}}` の直後にあるテキストの先頭の空白文字の長さを計算し、その分だけ `l.pos` を進めて `l.ignore()` で破棄します。これにより、アクションの直後の先頭空白がトリミングされます。

### 字句解析器での完結
このアプローチの利点は、字句解析器の段階で空白のトリミングが処理されるため、構文解析器はトリミングされた後のトークンストリームを受け取る点です。これにより、構文解析器のロジックを変更する必要がなく、既存のテンプレート構文に影響を与えることなく新しい機能が追加されました。これは、Goのテンプレートエンジンが持つ堅牢性と後方互換性を維持する上で重要な設計判断です。

### 空白文字の定義
トリミングの対象となる空白文字は、Go言語自体で定義されているものと同じです。
-   スペース (` `)
-   水平タブ (`\t`)
-   キャリッジリターン (`\r`)
-   改行 (`\n`)

## コアとなるコードの変更箇所

この機能の核心的な変更は `src/text/template/parse/lex.go` に集中しています。

```go
// Trimming spaces.
// If the action begins "{- " rather than "{", then all space/tab/newlines
// preceding the action are trimmed; conversely if it ends " -}" the
// leading spaces are trimmed. This is done entirely in the lexer; the
// parser never sees it happen. We require an ASCII space to be
// present to avoid ambiguity with things like "{-3}". It reads
// better with the space present anyway. For simplicity, only ASCII
// space does the job.
const (
	spaceChars      = " \t\r\n" // These are the space characters defined by Go itself.
	leftTrimMarker  = "- "      // Attached to left delimiter, trims trailing spaces from preceding text.
	rightTrimMarker = " -"      // Attached to right delimiter, trims leading spaces from following text.
	trimMarkerLen   = Pos(len(leftTrimMarker))
)

// lexText scans until an opening action delimiter, "{{".
func lexText(l *lexer) stateFn {
	for {
		delim, trimSpace := l.atLeftDelim()
		if delim {
			trimLength := Pos(0)
			if trimSpace {
				trimLength = rightTrimLength(l.input[l.start:l.pos])
			}
			if l.pos > l.start {
				l.emit(itemText)
			}
			l.pos += trimLength // Adjust pos to skip trimmed spaces
			l.ignore()          // Ignore the left delimiter and potential trim marker
			return lexLeftDelim
		}
		// ... (rest of lexText)
	}
}

// atLeftDelim reports whether the lexer is at a left delimiter, possibly followed by a trim marker.
func (l *lexer) atLeftDelim() (delim, trimSpaces bool) {
	if !strings.HasPrefix(l.input[l.pos:], l.leftDelim) {
		return false, false
	}
	// The left delim might have the marker afterwards.
	trimSpaces = strings.HasPrefix(l.input[l.pos+Pos(len(l.leftDelim)):], leftTrimMarker)
	return true, trimSpaces
}

// rightTrimLength returns the length of the spaces at the end of the string.
func rightTrimLength(s string) Pos {
	return Pos(len(s) - len(strings.TrimRight(s, spaceChars)))
}

// atRightDelim reports whether the lexer is at a right delimiter, possibly preceded by a trim marker.
func (l *lexer) atRightDelim() (delim, trimSpaces bool) {
	if strings.HasPrefix(l.input[l.pos:], l.rightDelim) {
		return true, false
	}
	// The right delim might have the marker before.
	if strings.HasPrefix(l.input[l.pos:], rightTrimMarker) {
		if strings.HasPrefix(l.input[l.pos+trimMarkerLen:], l.rightDelim) {
			return true, true
		}
	}
	return false, false
}

// leftTrimLength returns the length of the spaces at the beginning of the string.
func leftTrimLength(s string) Pos {
	return Pos(len(s) - len(strings.TrimLeft(s, spaceChars)))
}

// lexLeftDelim scans the left delimiter, which is known to be present, possibly with a trim marker.
func lexLeftDelim(l *lexer) stateFn {
	l.pos += Pos(len(l.leftDelim))
	trimSpace := strings.HasPrefix(l.input[l.pos:], leftTrimMarker)
	afterMarker := Pos(0)
	if trimSpace {
		afterMarker = trimMarkerLen
	}
	// ... (comment handling)
	l.emit(itemLeftDelim)
	l.pos += afterMarker // Advance past the trim marker
	l.ignore()           // Ignore the trim marker
	l.parenDepth = 0
	return lexInsideAction
}

// lexRightDelim scans the right delimiter, which is known to be present, possibly with a trim marker.
func lexRightDelim(l *lexer) stateFn {
	trimSpace := strings.HasPrefix(l.input[l.pos:], rightTrimMarker)
	if trimSpace {
		l.pos += trimMarkerLen // Advance past the trim marker
		l.ignore()             // Ignore the trim marker
	}
	l.pos += Pos(len(l.rightDelim))
	l.emit(itemRightDelim)
	if trimSpace {
		l.pos += leftTrimLength(l.input[l.pos:]) // Advance past leading spaces after the right delimiter
		l.ignore()                               // Ignore those leading spaces
	}
	return lexText
}

// lexInsideAction scans the elements inside action delimiters.
func lexInsideAction(l *lexer) stateFn {
	// ...
	delim, _ := l.atRightDelim()
	if delim {
		if l.parenDepth == 0 {
			return lexRightDelim
		}
	}
	// ...
}
```

## コアとなるコードの解説

上記のコード変更は、`text/template` の字句解析器 (`lex.go`) に、テンプレートアクションの前後にある空白を条件付きで削除するロジックを導入しています。

1.  **定数 `spaceChars`, `leftTrimMarker`, `rightTrimMarker`, `trimMarkerLen` の定義**:
    -   `spaceChars`: Goの空白文字（スペース、タブ、CR、LF）を定義しています。これらがトリミングの対象となります。
    -   `leftTrimMarker` (`"- "`): 左区切り文字 `{{` の直後に続くことで、先行するテキストの末尾空白をトリミングするマーカーです。
    -   `rightTrimMarker` (`" -" `): 右区切り文字 `}}` の直前に続くことで、後続するテキストの先頭空白をトリミングするマーカーです。
    -   `trimMarkerLen`: マーカーの長さを定義し、コード内で一貫して使用します。

2.  **`lexText` 関数の変更**:
    -   `lexText` は、通常のテキストをスキャンし、アクションの開始 (`{{`) を検出する主要な関数です。
    -   `l.atLeftDelim()` を呼び出して、現在の位置が `{{` であり、かつ `{{- ` の形式であるかをチェックします。
    -   `trimSpace` が `true` の場合（つまり `{{- ` が見つかった場合）、`rightTrimLength(l.input[l.start:l.pos])` を使って、`{{- ` の直前のテキストの末尾にある空白の長さを計算します。
    -   `l.pos -= trimLength` で字句解析器の現在位置を戻し、`l.emit(itemText)` で空白がトリミングされたテキスト部分をトークンとして発行します。
    -   その後、`l.pos += trimLength` で位置を元に戻し、`l.ignore()` で `{{- ` マーカー自体を無視します。これにより、このマーカーは最終的な出力には含まれません。

3.  **`atLeftDelim`, `rightTrimLength`, `atRightDelim`, `leftTrimLength` ヘルパー関数の追加**:
    -   これらの関数は、トリミングマーカーの検出と、文字列の左右の空白の長さを計算するために導入されました。
    -   `atLeftDelim` と `atRightDelim` は、区切り文字とそれに続く/先行するトリミングマーカーの存在を効率的にチェックします。
    -   `rightTrimLength` は文字列の末尾の空白の長さを、`leftTrimLength` は文字列の先頭の空白の長さを返します。これらは `strings.TrimRight` および `strings.TrimLeft` を利用して実装されています。

4.  **`lexLeftDelim` 関数の変更**:
    -   `{{` を処理する際に、`{{- ` の形式であれば、`- ` 部分を `l.ignore()` で無視するように変更されました。

5.  **`lexRightDelim` 関数の変更**:
    -   `}}` を処理する際に、` -}}` の形式であれば、`- ` 部分を `l.ignore()` で無視します。
    -   さらに、` -}}` の直後にあるテキストの先頭空白を `leftTrimLength` で計算し、その部分も `l.ignore()` で無視するように変更されました。

これらの変更により、字句解析器はテンプレートソースをトークン化する際に、指定されたトリミングマーカーに基づいて自動的に空白を削除します。この処理は字句解析の段階で完結するため、構文解析器やテンプレートの実行ロジックは、空白がすでにトリミングされた状態のトークンストリームを受け取ることになり、既存のコードベースへの影響を最小限に抑えつつ、強力な空白制御機能が実現されています。

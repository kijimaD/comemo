## 変更の背景

Go言語は、メモリ安全性を保証するために、配列やスライスへのアクセス時に常に境界チェックを行います。これは、インデックスが有効な範囲内にあることを確認するためのもので、不正なメモリアクセスを防ぐ上で非常に重要です。しかし、ループ内でインデックスが常に有効な範囲内にあることがコンパイル時に静的に証明できる場合でも、これらのチェックが実行されると、不要なオーバーヘッドとなり、プログラムの実行速度を低下させる可能性があります。

このコミットの背景には、このような冗長な境界チェックを特定し、削除することで、Goプログラムの実行効率を向上させるという目的があります。特に、`for i := 0; i < len(s); i++`のような典型的なループパターンでは、インデックス`i`が常に`0`から`len(s)-1`の範囲内にあることが明らかです。このようなケースで境界チェックを省略できれば、パフォーマンスの向上が期待できます。

Goコンパイラは、以前から様々な最適化を行ってきましたが、SSA (Static Single Assignment) 形式への変換後に行われる最適化パスにおいて、誘導変数に特化した境界チェック除去が不足していました。このコミットは、そのギャップを埋めるものです。

## 前提知識の解説

### 1. 静的単一割り当て (Static Single Assignment, SSA)

SSAは、コンパイラ最適化で用いられる中間表現の一種です。SSA形式では、各変数が一度だけ定義されるという特性を持ちます。これにより、データフロー解析が容易になり、コンパイラがより効果的な最適化（例えば、デッドコード除去、共通部分式除去、レジスタ割り当てなど）を実行できるようになります。Goコンパイラも、最適化の段階でコードをSSA形式に変換します。

### 2. 誘導変数 (Induction Variable)

誘導変数とは、ループの各反復でその値が一定の規則（通常は定数による加算または減算）に従って変化する変数のことです。最も一般的なのは、`for i := 0; i < N; i++` の`i`のようなループカウンタです。誘導変数は、配列のインデックスとして頻繁に使用されます。

### 3. 境界チェック除去 (Bounds Check Elimination, BCE)

BCEは、コンパイラ最適化の一種で、配列やスライスへのアクセス時に行われる実行時境界チェックの一部または全てを削除する技術です。コンパイラが、特定のアクセスが必ず有効な範囲内で行われることを静的に証明できる場合、そのチェックは冗長であると判断され、削除されます。これにより、実行時のオーバーヘッドが減少し、プログラムの速度が向上します。

### 4. 支配関係 (Dominance) と疎支配木 (Sparse Dominator Tree, SDOM)

コンパイラのデータフロー解析において、支配関係は重要な概念です。
*   **支配 (Dominance):** プログラムの制御フローグラフにおいて、ブロックAがブロックBを支配するとは、AからBへのすべてのパスがAを通過することを意味します。
*   **疎支配木 (Sparse Dominator Tree, SDOM):** 支配関係を効率的に表現するためのデータ構造です。SDOMは、特定のブロックが他のブロックを支配するかどうかを高速に判定するために使用されます。このコミットでは、ループの条件が満たされた場合にのみ誘導変数が更新されることを証明するために、SDOMが利用されています。

### 5. GoコンパイラのSSAオペレーション

GoコンパイラのSSAバックエンドでは、様々な操作が`Op`（オペレーション）として表現されます。このコミットで特に重要なのは以下のものです。
*   `OpPhi`: SSA形式におけるΦ関数。複数の制御フローパスが合流する点で、異なるパスから来る同じ変数の値を結合するために使用されます。ループの誘導変数は通常、`Phi`関数として表現されます。
*   `OpIsInBounds`, `OpIsSliceInBounds`: 境界チェックを表すオペレーション。これらのオペレーションが除去の対象となります。
*   `OpAdd64`, `OpConst64`: 64ビット整数加算と64ビット定数を表すオペレーション。誘導変数の増分を特定するのに使われます。
*   `OpLess64`, `OpGreater64`: 64ビット整数比較（より小さい、より大きい）を表すオペレーション。ループの終了条件を特定するのに使われます。
*   `OpStringLen`, `OpSliceLen`, `OpSliceCap`: 文字列の長さ、スライスの長さ、スライスの容量を取得するオペレーション。これらは境界チェックの上限値として使われます。

## 技術的詳細

このコミットは、GoコンパイラのSSAパスに`loopbce`という新しい最適化パスを追加します。このパスは、主に以下の2つのステップで構成されます。

1.  **誘導変数の特定 (`findIndVar`関数):**
    *   コンパイラは、関数内のすべてのブロックを走査し、ループのヘッダーブロック（ループの入り口となるブロック）を特定します。
    *   ループヘッダーブロックの制御フロー（`b.Control`）が`OpLess64`または`OpGreater64`である場合、つまりループが`i < max`または`max > i`のような条件で制御されている場合に注目します。
    *   ループ変数が`OpPhi`オペレーションであり、かつその`Phi`関数が自身（ループ変数）と、定数による加算（`OpAdd64`）の結果に依存している場合、それを誘導変数として識別します。例えば、`i = Phi(min, nxt)`で、`nxt = i + inc`のようなパターンです。
    *   増分値（`inc`）が正の定数であることも確認します。現在の実装では、負の増分はサポートしていません。
    *   さらに、ループの入り口ブロックが単一の先行ブロックを持つこと、および誘導変数の更新が行われるブロックがループの入り口ブロックによって支配されていること（`sdom.isAncestorEq`）を確認し、誘導変数が安全にインクリメントされることを保証します。
    *   `max`値が`c + SliceLen`の形式で`c <= 0`の場合、`c`を削除して`SliceLen`のみを`max`として扱うことで、`SliceLen == 0`の場合のオーバーフローを防ぎます。
    *   増分が1でない場合でも、`min`と`max`が定数であり、`max.AuxInt > min.AuxInt`かつ`max.AuxInt % inc.AuxInt == min.AuxInt % inc.AuxInt`という条件を満たせば、誘導変数として認識します。これは、例えば`for i := 0; i < 10; i += 2`のようなケースで、`i`が常に偶数であり、`max`が`min`と同じ剰余を持つ場合に、境界チェックを安全に除去できることを意味します。

2.  **境界チェックの除去 (`removeBoundsChecks`関数):**
    *   特定された誘導変数と、それらが支配するループの範囲情報を利用して、既存の境界チェック（`OpIsInBounds`および`OpIsSliceInBounds`）を削除します。
    *   `removeBoundsChecks`関数は、`OpIsInBounds`または`OpIsSliceInBounds`オペレーションを持つブロックを走査します。
    *   境界チェックの対象となるインデックスが、`findIndVar`で特定された誘導変数であるかを確認します。
    *   誘導変数の最小値（`iv.min`）が非負（`isNonNegative(iv.min)`）であり、かつ境界チェックの上限値が誘導変数の最大値（`iv.max`）と一致する場合、その境界チェックは冗長であると判断し、削除します。
    *   特に`OpIsSliceInBounds`の場合、`v.Args[1].Op == OpSliceCap && iv.max.Op == OpSliceLen`という条件も考慮されます。これは、`a[:i+1]`のようなスライス操作で、`len`が`cap`に昇格されるケース（スライスの長さが容量を超えないことが保証される場合）に対応します。
    *   冗長と判断された境界チェックは、そのブロックの`Kind`を`BlockFirst`に変更し、`Control`オペレーションを`nil`に設定することで削除されます。これにより、コンパイラは当該ブロックを無条件に通過するようになり、実行時のチェックがスキップされます。

この最適化は、GoコンパイラのSSAパスの後半に追加され、既存の`nilcheckelim`や`prove`パスの後に実行されます。これにより、他の最適化によってSSA形式が安定した後に、誘導変数に特化したBCEが適用されることになります。

## コアとなるコードの解説

### `findIndVar`関数

この関数の核心は、ループの構造を解析し、ループ変数が「誘導変数」の定義に合致するかどうかを厳密にチェックすることにあります。

1.  **ループヘッダーの特定**: `for _, b := range f.Blocks`で全てのブロックを走査し、`b.Kind != BlockIf || len(b.Preds) != 2`でループの条件分岐（`if`ブロック）かつ2つの先行ブロックを持つもの（ループヘッダーの典型的な形）をフィルタリングします。
2.  **ループ条件の解析**: `b.Control.Op`が`OpLess64`または`OpGreater64`であるかを調べ、ループの終了条件（`ind < max`または`max > ind`）を特定します。ここで`ind`が誘導変数候補、`max`が上限値候補です。
3.  **誘導変数の`Phi`関数としての識別**: `ind.Op != OpPhi`であれば、それは誘導変数ではありません。誘導変数はループの入り口で初期値を取り、ループ内で更新された値が次の反復で使われるため、`Phi`関数として表現されます。
4.  **増分値の特定**: `ind.Args[0]`または`ind.Args[1]`が`OpAdd64`であり、かつその`Add64`オペレーションの引数の一つが`ind`自身である場合、`ind`がループ内でインクリメントされていると判断します。例えば、`nxt = ind + inc`のような形です。ここから`min`（初期値）と`nxt`（次の値）、そして`inc`（増分）を抽出します。
5.  **増分値の検証**: `inc.Op != OpConst64 || inc.AuxInt <= 0`で、増分が正の定数であることを確認します。負の増分や非定数の増分は現在のところサポートされていません。
6.  **支配関係による安全性の確認**:
    *   `len(b.Succs[entry].Preds) != 1`: ループの入り口ブロックが単一の先行ブロックを持つことを確認します。これにより、ループが常に期待されるパスで進入されることを保証します。
    *   `!sdom.isAncestorEq(b.Succs[entry], nxt.Block)`: `nxt`（誘導変数の更新）が、ループの入り口ブロックによって支配されていることを確認します。これは、誘導変数の更新がループ条件が真である場合にのみ実行されることを保証し、境界チェック除去の安全性を確保します。
7.  **特殊なケースの処理**: `max`が`c + SliceLen`の形式で`c <= 0`の場合、`max`を`SliceLen`に簡略化します。これは、`len(a)`が0の場合に`c + len(a)`がオーバーフローする可能性を考慮したものです。
8.  **増分が1でない場合の処理**: `inc.AuxInt != 1`の場合、`min`と`max`が定数であり、`max.AuxInt > min.AuxInt`かつ`max.AuxInt % inc.AuxInt == min.AuxInt % inc.AuxInt`という条件を満たす場合にのみ、誘導変数として受け入れます。これにより、`for i := 0; i < 10; i += 2`のようなステップが2のループでもBCEが可能になります。

### `removeBoundsChecks`関数

この関数は、`findIndVar`で特定された誘導変数情報を使って、実際に境界チェックを削除します。

1.  **境界チェックの特定**: `for _, b := range f.Blocks`で全てのブロックを走査し、`b.Control`が`OpIsInBounds`または`OpIsSliceInBounds`であるブロックを対象とします。
2.  **誘導変数との関連付け**: 境界チェックの対象となるインデックス（`v.Args[0]`）が、`dropAdd64`関数で定数オフセットを分離した後、`findIndVar`で特定された誘導変数（`ind.Op == OpPhi`）であるかを確認します。
3.  **安全性の確認**:
    *   `sdom.isAncestorEq(iv.entry, b)`: 境界チェックが行われるブロック`b`が、誘導変数のループ入り口ブロック`iv.entry`によって支配されていることを確認します。これにより、誘導変数が有効な範囲内にあることが保証されるコンテキストでチェックが行われていることを確認します。
    *   `isNonNegative(iv.min)`: 誘導変数の最小値が非負であることを確認します。これは、配列やスライスのインデックスが負にならないことを保証するために重要です。
4.  **上限値の一致**: 境界チェックの上限値（`v.Args[1]`）が、誘導変数の最大値（`iv.max`）と一致するかを確認します。
5.  **スライス容量の考慮**: `OpIsSliceInBounds`の場合、上限値が`OpSliceCap`であり、誘導変数の最大値が`OpSliceLen`であるケースも考慮します。これは、`a[:i+1]`のようなスライス操作で、スライスの長さが容量を超えないことが保証される場合に、`len`が`cap`に昇格される最適化に対応するためです。
6.  **境界チェックの削除**: 上記の全ての条件が満たされた場合、その境界チェックは冗長であると判断し、ブロック`b`の`Kind`を`BlockFirst`に、`Control`を`nil`に設定することで、コンパイラがそのチェックをスキップするように変更します。

これらの変更により、Goコンパイラはループ内の一般的な誘導変数パターンを認識し、安全かつ効果的に不要な境界チェックを除去できるようになり、結果として生成されるバイナリの実行効率が向上します。

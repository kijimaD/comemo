## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用します。このSSA形式の構築と変換の過程で、`Block`（基本ブロック）や`Value`（値）といったデータ構造が頻繁に生成、変更、破棄されます。特に、`Block`構造体に含まれる`Preds`（先行ブロックのリスト）、`Succs`（後続ブロックのリスト）、`Values`（ブロック内の命令/値のリスト）は、スライスとして実装されており、要素の追加や削除のたびにメモリの再割り当てが発生する可能性があります。

頻繁なメモリ割り当てと解放は、ガベージコレクションの負荷を増やし、コンパイル時間のボトルネックとなることがあります。このコミットの目的は、これらのスライスが使用するメモリ割り当てを最適化し、コンパイル速度を向上させることにあります。具体的には、`Block`構造体内に固定サイズのバッキングストア（配列）を事前に確保することで、小さなスライス操作においてはヒープ割り当てを回避し、スタック上に近い場所でデータを管理できるようにします。これにより、メモリ割り当てのオーバーヘッドを削減し、コンパイル全体のパフォーマンスを改善します。コミットメッセージにある「Speeds up compilation by 6%」という記述は、この最適化がもたらす具体的な効果を示しています。

## 前提知識の解説

### GoコンパイラのSSA（Static Single Assignment）形式

Goコンパイラは、ソースコードを機械語に変換する過程で、複数の段階の中間表現（IR）を使用します。SSA形式は、その中でも特に重要な最適化段階で用いられるIRの一つです。SSA形式の主な特徴は以下の通りです。

*   **静的単一代入 (Static Single Assignment):** 各変数が一度だけ代入されることを保証します。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。
*   **基本ブロック (Basic Block):** プログラムの制御フローは、基本ブロックの集合として表現されます。基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令シーケンスです。
*   **値 (Value):** SSA形式では、各命令の結果や定数、変数の値などが`Value`として表現されます。`Value`は、その操作の種類（Op）、型（Type）、所属するブロック（Block）、引数（Args）、結果を使用する他の`Value`（Uses）などの情報を含みます。

### `Block`構造体

GoコンパイラのSSAパッケージにおける`Block`構造体は、プログラムの基本ブロックを表します。主要なフィールドは以下の通りです。

*   `ID`: ブロックの一意な識別子。
*   `Kind`: ブロックの種類（例: `BlockPlain`, `BlockIf`, `BlockDefer`など）。
*   `Control`: ブロックの制御フローを決定する`Value`（例: `if`文の条件式）。
*   `Preds`: このブロックに制御が移る可能性のある先行ブロックのリスト（スライス）。
*   `Succs`: このブロックから制御が移る可能性のある後続ブロックのリスト（スライス）。
*   `Values`: このブロック内で定義される`Value`のリスト（スライス）。

これらの`Preds`, `Succs`, `Values`は、プログラムの制御フローグラフやデータフローグラフを構築・操作する際に頻繁にアクセスされ、変更されます。

### スライスとメモリ割り当て

Go言語のスライスは、可変長配列のようなデータ構造です。内部的には、要素へのポインタ、長さ（len）、容量（cap）を持ちます。スライスに要素を追加する際（`append`関数など）、現在の容量が不足している場合は、より大きな容量を持つ新しい基底配列が割り当てられ、既存の要素が新しい配列にコピーされます。この再割り当ては、特に頻繁に発生する場合、パフォーマンスに大きな影響を与えます。

## 技術的詳細

このコミットの核心は、`Block`構造体内の`Preds`, `Succs`, `Values`スライスに対して、固定サイズの「バッキングストアバッファ」を導入することです。

変更前は、`Block`構造体の`Preds`, `Succs`, `Values`フィールドは直接スライスとして宣言されていました。これらのスライスが初期化される際や、要素が追加されて容量が不足する際には、ヒープ上に新しい基底配列が割り当てられていました。

変更後は、`Block`構造体に以下のフィールドが追加されました。

```go
type Block struct {
    // ... 既存のフィールド ...

    // Storage for Succs, Preds, and Values
    succstorage [2]*Block
    predstorage [4]*Block
    valstorage  [8]*Value
}
```

*   `succstorage [2]*Block`: 2つの`*Block`を格納できる配列。`Succs`スライスのバッキングストアとして使用されます。
*   `predstorage [4]*Block`: 4つの`*Block`を格納できる配列。`Preds`スライスのバッキングストアとして使用されます。
*   `valstorage [8]*Value`: 8つの`*Value`を格納できる配列。`Values`スライスのバッキングストアとして使用されます。

これらの配列は`Block`構造体の一部として、構造体自体が割り当てられる際に一緒にメモリが確保されます。これにより、`Block`が生成される際に、`Preds`, `Succs`, `Values`スライスがこれらの内部配列を指すように初期化されることで、小さなスライス操作（例えば、先行ブロックが2つ以下、後続ブロックが2つ以下、ブロック内の値が8つ以下の場合）では、追加のヒープ割り当てが不要になります。

具体的には、`NewBlock`関数内で新しい`Block`が作成される際に、以下のようにスライスが初期化されます。

```go
b.Preds = b.predstorage[:0]
b.Succs = b.succstorage[:0]
b.Values = b.valstorage[:0]
```

これにより、スライスは容量がそれぞれ`len(b.predstorage)`、`len(b.succstorage)`、`len(b.valstorage)`（つまり4, 2, 8）に設定され、基底配列は`Block`構造体内の`predstorage`, `succstorage`, `valstorage`を指すようになります。

この最適化のメリットは以下の通りです。

1.  **メモリ割り当ての削減:** 多くの基本ブロックは、少数の先行/後続ブロックや値しか持たないため、これらの小さなスライス操作でヒープ割り当てが不要になります。
2.  **ガベージコレクション負荷の軽減:** ヒープ割り当てが減ることで、ガベージコレクタが追跡・処理する必要のあるオブジェクトの数が減り、GCの実行頻度や時間が短縮されます。
3.  **キャッシュ効率の向上:** `Block`構造体と、それに密接に関連する`Preds`, `Succs`, `Values`のデータがメモリ上で近接して配置されるため、CPUキャッシュのヒット率が向上し、メモリアクセスが高速化されます。

ただし、スライスの要素数がバッキングストアの容量（2, 4, 8）を超える場合は、通常通りヒープ上に新しい基底配列が割り当てられます。この最適化は、一般的なケース（少数の要素）でパフォーマンスを向上させることを目的としています。

また、`deadcode.go`や`func.go`では、`f.freeBlocks`リストのリンクリストのポインタとして、以前は`b.Aux.(*Block)`を使用していた箇所が`b.succstorage[0]`に変更されています。これは、`succstorage`が`Block`構造体内に常に存在するため、`Aux`フィールドを汎用的なポインタとして使用するよりも型安全で、かつメモリレイアウトの予測可能性を高めるためと考えられます。`Aux`フィールドは他の目的にも使用される可能性があるため、専用のストレージを使用することで、よりクリーンな設計になります。

`fuse.go`の変更では、ブロックの融合（fuse）処理において、`c.Preds`を`b.Preds`で置き換える際に、`predstorage`を優先的に利用するロジックが追加されています。

```go
c.predstorage[0] = nil // 既存のデータをクリア
if len(b.Preds) > len(b.predstorage) {
    c.Preds = b.Preds // バッキングストアより大きい場合は通常のスライス割り当て
} else {
    c.Preds = append(c.predstorage[:0], b.Preds...) // バッキングストアにコピー
}
```

これは、`b.Preds`の要素数が`predstorage`の容量内に収まる場合は、`predstorage`を再利用してコピーすることで、新たなヒープ割り当てを避けるための工夫です。

## コアとなるコードの解説

このコミットの主要な変更は、`Block`構造体への`succstorage`, `predstorage`, `valstorage`という3つの配列の追加です。これらは、それぞれ`Block.Succs`、`Block.Preds`、`Block.Values`というスライスが、ヒープ割り当てなしで利用できる「内部バッファ」を提供します。

例えば、`Block`が新しく作成される際、`func.go`の`NewBlock`関数内で以下のように初期化されます。

```go
b.Preds = b.predstorage[:0]
b.Succs = b.succstorage[:0]
b.Values = b.valstorage[:0]
```

このコードは、`b.Preds`スライスが`b.predstorage`配列の先頭を指し、長さが0、容量が`len(b.predstorage)`（この場合は4）となるように設定します。これにより、最大4つの先行ブロックが追加されるまでは、`append`操作によって新しい基底配列がヒープに割り当てられることはありません。同様に、`Succs`は2つまで、`Values`は8つまでヒープ割り当てなしで要素を追加できます。

このアプローチは、GoコンパイラのSSA中間表現において、多くの基本ブロックが比較的少数の先行/後続ブロックや命令しか持たないという経験則に基づいています。このような「ホットパス」での小さなスライス操作におけるメモリ割り当てを削減することで、全体的なコンパイル時間を短縮します。

また、`func.go`や`check.go`で`f.freeBlocks`のリンクリストのポインタとして`b.Aux.(*Block)`の代わりに`b.succstorage[0]`を使用する変更は、`Block`構造体内の専用フィールドを再利用することで、型アサーションのオーバーヘッドをなくし、コードの意図をより明確にする効果もあります。`Aux`フィールドは汎用的な補助データとして使われることがありますが、`succstorage[0]`をフリーリストのリンキングに使うことで、その目的を固定し、より効率的なメモリ管理を実現しています。

`fuse.go`における`c.Preds`の置き換えロジックは、このバッキングストアの利用をさらに最適化するものです。`b.Preds`の要素数が`predstorage`の容量内に収まる場合、`append(c.predstorage[:0], b.Preds...)`というイディオムを使って、`c.predstorage`の既存のメモリを再利用しつつ、`b.Preds`の内容をコピーしています。これにより、不要なヒープ割り当てをさらに抑制しています。

これらの変更は、GoコンパイラのSSAバックエンドにおけるメモリ効率と実行速度を向上させるための、典型的なマイクロ最適化の例と言えます。

## 変更の背景

このコミットは、Go言語の初期段階（2009年5月）に行われたもので、`container/vector`パッケージの設計と効率性の改善が背景にあります。

1.  **`IntVector`の冗長性排除**: 当時のGo言語における構造体の埋め込み（embedding）の挙動に関連しています。`IntVector`は`vector.Vector`を埋め込んでおり、`Vector`が持つ汎用的なメソッド（`Set`, `Insert`, `Delete`, `Push`など）を`IntVector`がそのまま利用できるにもかかわらず、`IntVector`側でそれらのメソッドをラップして再定義していました。これはコードの冗長性を生み、メンテナンス性を低下させていました。このコミットは、埋め込みによって「正しい型で継承される」メソッドを削除し、コードベースを簡潔にすることを目指しました。
2.  **`vector.Delete`のパフォーマンスとAPI改善**: `vector.Delete`メソッドは、要素を削除した後にその要素を返していました。しかし、要素の削除と同時にその値を返すことは、特に大きなデータ構造の場合に不要なオーバーヘッドを生む可能性があります。また、削除された要素の値が必要な場合は、削除前に`At(i)`メソッドで取得できるため、`Delete`メソッドが値を返す必要はないという判断がなされました。これにより、`Delete`メソッドのシグネチャを簡素化し、潜在的なパフォーマンス向上を図っています。
3.  **`vector.Pop`の最適化**: `Pop`メソッドは、以前は`Delete`メソッドを内部的に呼び出していましたが、このコミットでは`Pop`が直接配列操作を行うように変更されました。これは、`Pop`が常に末尾の要素を削除するという特定の操作であるため、より効率的な直接操作に切り替えることでパフォーマンスを向上させる意図があったと考えられます。また、GC（ガベージコレクション）をサポートするために、削除された要素の参照を`nil`に設定する処理が明示的に追加されています。

これらの変更は、Go言語の標準ライブラリが成熟していく過程で、よりクリーンで効率的なAPI設計を目指す初期の取り組みの一環と言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の初期の概念とデータ構造に関する知識が必要です。

1.  **`container/vector`パッケージ**:
    *   Go言語の初期の標準ライブラリには、動的配列（ベクター）を実装するための`container/vector`パッケージが存在しました。これは、現在のGoにおける組み込みスライス（`[]T`）が提供する機能の一部を補完するものでした。
    *   `vector.Vector`は、任意の型の要素（`Element`インターフェース）を格納できる汎用的なベクターでした。
    *   `intvector.IntVector`は、`vector.Vector`を埋め込むことで、`int`型に特化したベクターとして機能していました。これは、Goのジェネリクスがまだ存在しない時代において、特定の型に特化したコレクションを提供するための一般的なパターンでした。

2.  **構造体の埋め込み (Embedding)**:
    *   Go言語の構造体埋め込みは、他の構造体やインターフェースを匿名フィールドとして構造体内に含める機能です。これにより、埋め込まれた型のメソッドが、埋め込み元の構造体のメソッドとして「昇格（promoted）」されます。
    *   例えば、`IntVector`が`vector.Vector`を埋め込んでいる場合、`IntVector`のインスタンスは`vector.Vector`のメソッドを直接呼び出すことができます。
    *   このコミットの背景にあるのは、`IntVector`が`vector.Vector`のメソッドをラップして再定義していたことです。埋め込みの機能により、これらのラッパーメソッドは不要となり、直接`IntVector.Vector.Method()`のようにアクセスするか、あるいは単に`IntVector.Method()`として呼び出すことが可能になります。このコミットは、後者の「昇格」されたメソッドを直接利用する方針に切り替えることで、冗長なコードを削除しています。

3.  **スライス (Slices)**:
    *   Go言語の組み込み型であるスライスは、配列の一部を参照する動的なビューです。`container/vector`パッケージは、スライスがGo言語の主要な動的配列メカニズムとして確立される前の過渡期に存在していました。
    *   `vector.Vector`の内部実装は、最終的にGoのスライスを基盤としていました。`Delete`メソッドにおける`copy`関数やスライスの再スライス（`p.a = a[0 : n-1]`）は、スライスの基本的な操作です。

4.  **ガベージコレクション (GC) と`nil`化**:
    *   Goはガベージコレクタを持つ言語です。不要になったメモリはGCによって自動的に解放されます。
    *   コレクションから要素を削除する際、その要素への参照が残っていると、GCがそのメモリを解放できず、メモリリークや不要なメモリ保持につながる可能性があります。
    *   このコミットでは、`Delete`および`Pop`メソッドで削除された要素の参照を`nil`に設定する（`a[n-1] = nil;` や `p.a[i] = nil;`）ことで、GCがその要素を適切に回収できるようにしています。これは、メモリ効率を向上させるための重要なプラクティスです。

## 技術的詳細

このコミットの技術的詳細は、主に`container/vector`パッケージ内の`intvector.go`と`vector.go`の変更に集約されます。

### `src/lib/container/vector/intvector.go`の変更

*   **冗長なメソッドの削除**:
    *   `Set(i int, x int)`
    *   `Insert(i int, x int)`
    *   `Delete(i int) int`
    *   `Push(x int)`
    これらのメソッドは、`IntVector`が埋め込んでいる`vector.Vector`の同名のメソッドを単に呼び出すだけのラッパーでした。Goの構造体埋め込みの機能により、`IntVector`のインスタンスから直接`p.Vector.Set(i, x)`のようにアクセスするか、あるいは`p.Set(i, x)`のように「昇格された」メソッドとして呼び出すことが可能です。このコミットは、冗長なラッパーを削除し、コードベースを簡潔に保つことを選択しました。
*   **`TODO`コメントの削除**: `// TODO do not export field`というコメントが削除されています。これは、`Vector`フィールドが匿名で埋め込まれることで、実質的にエクスポートされない形になるため、この`TODO`が不要になったことを示唆しています。

### `src/lib/container/vector/vector.go`の変更

*   **`Delete(i int) Element` から `Delete(i int)` への変更**:
    *   変更前: `func (p *Vector) Delete(i int) Element` は削除された要素を返していました。
    *   変更後: `func (p *Vector) Delete(i int)` は何も返さなくなりました。
    *   内部実装では、削除された要素`x := a[i]`の取得行が削除され、`return x`も削除されています。
    *   この変更の理由は、コミットメッセージにある通り「Faster vector.Delete, removed result value (easy to get via At(i))」です。削除された要素が必要な場合は、削除前に`At(i)`で取得するというパターンを推奨することで、`Delete`メソッド自体のオーバーヘッドを減らし、より高速な操作を可能にしています。
*   **`Pop() Element` の実装変更**:
    *   変更前: `Pop`は内部的に`return p.Delete(len(p.a) - 1)`を呼び出していました。
    *   変更後: `Pop`は`Delete`を呼び出す代わりに、直接スライス操作を行うようになりました。
        ```go
        i := len(p.a) - 1;
        x := p.a[i];
        p.a[i] = nil;  // support GC, nil out entry
        p.a = p.a[0 : i];
        return x;
        ```
    *   この変更により、`Pop`は末尾要素の取得、GCのための`nil`化、そしてスライスの再スライスを直接行います。これは、`Pop`が常に末尾の要素を扱うという特性を活かした最適化であり、汎用的な`Delete`メソッドを呼び出すよりも効率的です。特に、`Delete`メソッドが返り値をなくしたため、`Pop`が以前のように`Delete`の返り値を利用できなくなったことも、この変更の理由の一つと考えられます。

### `src/lib/container/vector/vector_test.go`の変更

*   `TestInsertDeleteClear`関数内のテストロジックが、`Delete`メソッドのシグネチャ変更に合わせて修正されています。
    *   変更前: `if a.Delete(0).(int) != val(i) { t.Error("D") }`
    *   変更後: `if a.At(0).(int) != val(i) { t.Error("D") }` の後に `a.Delete(0);`
    *   これは、`Delete`が値を返さなくなったため、削除前の要素の値は`At(0)`で事前に取得する必要があることを反映しています。

これらの変更は、Go言語の初期におけるパフォーマンスとAPI設計の洗練に向けた継続的な努力を示しています。

## コアとなるコードの解説

### `src/lib/container/vector/intvector.go`の変更

*   **削除されたメソッド群**: `Set`, `Insert`, `Delete`, `Push`メソッドが`IntVector`から削除されました。これらのメソッドは、`IntVector`が`vector.Vector`を匿名フィールドとして埋め込んでいるため、`IntVector`のインスタンスから直接`vector.Vector`のメソッドを呼び出すことが可能です。例えば、以前は`p.Set(i, x)`が`p.Vector.Set(i, x)`を呼び出すラッパーでしたが、この変更後は`p.Set(i, x)`という呼び出しは、Goの言語仕様によって`p.Vector.Set(i, x)`に自動的に解決されるため、明示的なラッパーは不要になります。これにより、コードの重複が排除され、`IntVector`の定義がより簡潔になりました。

### `src/lib/container/vector/vector.go`の変更

*   **`Delete(i int)`メソッドの変更**:
    *   **返り値の削除**: 以前は`Element`型の値を返していましたが、この変更により返り値がなくなりました。これは、削除された要素の値が必要な場合は、削除操作を行う前に`At(i)`メソッドで明示的に取得するという設計思想に基づいています。これにより、`Delete`メソッドのシグネチャが簡素化され、メソッドの目的が「要素を削除する」ことに特化されました。
    *   **パフォーマンス**: 返り値の生成と返却に伴うオーバーヘッドがなくなることで、理論的には`Delete`操作がわずかに高速化される可能性があります。
*   **`Pop() Element`メソッドの変更**:
    *   以前は`Delete(len(p.a) - 1)`を呼び出すことで末尾要素の削除と取得を行っていましたが、この変更により`Pop`は直接配列操作を行うようになりました。
    *   `i := len(p.a) - 1;`: 末尾要素のインデックスを取得します。
    *   `x := p.a[i];`: 末尾要素の値を`x`に保存します。
    *   `p.a[i] = nil;`: **重要な変更点**。削除される要素への参照を`nil`に設定します。これにより、ガベージコレクタがこの要素が不要になったことを認識し、メモリを適切に解放できるようになります。これはメモリリークを防ぎ、メモリ効率を向上させるためのプラクティスです。
    *   `p.a = p.a[0 : i];`: スライスを再スライスし、末尾要素を論理的に削除します。
    *   `return x;`: 削除された末尾要素の値を返します。
    *   この変更は、`Pop`が常に末尾要素を扱うという特性を活かした最適化であり、汎用的な`Delete`メソッドを呼び出すよりも効率的です。また、`Delete`メソッドが返り値を返さなくなったため、`Pop`が以前のように`Delete`の返り値を利用できなくなったことも、この変更の直接的な理由の一つです。

### `src/lib/container/vector/vector_test.go`の変更

*   `TestInsertDeleteClear`内のテストコードが、`Delete`メソッドの返り値がなくなったことに合わせて修正されました。
    *   以前は`a.Delete(0).(int)`の返り値を直接検証していましたが、変更後はまず`a.At(0).(int)`で削除前の要素の値を取得し、その後に`a.Delete(0)`を呼び出す形に変更されています。これは、`Delete`メソッドの新しいAPI契約に準拠したテストの書き方です。

1.  **`IntVector`の冗長性排除**: 当時のGo言語における構造体の埋め込み（embedding）の挙動に関連しています。`IntVector`は`vector.Vector`を埋め込んでおり、`Vector`が持つ汎用的なメソッド（`Set`, `Insert`, `Delete`, `Push`など）を`IntVector`がそのまま利用できるにもかかわらず、`IntVector`側でそれらのメソッドをラップして再定義していました。これはコードの冗長性を生み、メンテナンス性を低下させていました。このコミットは、埋め込みによって「正しい型で継承される」メソッドを削除し、コードベースを簡潔にすることを目指しました。
2.  **`vector.Delete`のパフォーマンスとAPI改善**: `vector.Delete`メソッドは、要素を削除した後にその要素を返していました。しかし、要素の削除と同時にその値を返すことは、特に大きなデータ構造の場合に不要なオーバーヘッドを生む可能性があります。また、削除された要素の値が必要な場合は、削除前に`At(i)`メソッドで取得できるため、`Delete`メソッドが値を返す必要はないという判断がなされました。これにより、`Delete`メソッドのシグネチャを簡素化し、潜在的なパフォーマンス向上を図っています。
3.  **`vector.Pop`の最適化**: `Pop`メソッドは、以前は`Delete`メソッドを内部的に呼び出していましたが、このコミットでは`Pop`が直接配列操作を行うように変更されました。これは、`Pop`が常に末尾の要素を削除するという特定の操作であるため、より効率的な直接操作に切り替えることでパフォーマンスを向上させる意図があったと考えられます。また、GC（ガベージコレクション）をサポートするために、削除された要素の参照を`nil`に設定する処理が明示的に追加されています。

これらの変更は、Go言語の標準ライブラリが成熟していく過程で、よりクリーンで効率的なAPI設計を目指す初期の取り組みの一環と言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の初期の概念とデータ構造に関する知識が必要です。

1.  **`container/vector`パッケージ**:
    *   Go言語の初期の標準ライブラリには、動的配列（ベクター）を実装するための`container/vector`パッケージが存在しました。これは、現在のGoにおける組み込みスライス（`[]T`）が提供する機能の一部を補完するものでした。
    *   `vector.Vector`は、任意の型の要素（`Element`インターフェース）を格納できる汎用的なベクターでした。
    *   `intvector.IntVector`は、`vector.Vector`を埋め込むことで、`int`型に特化したベクターとして機能していました。これは、Goのジェネリクスがまだ存在しない時代において、特定の型に特化したコレクションを提供するための一般的なパターンでした。

2.  **構造体の埋め込み (Embedding)**:
    *   Go言語の構造体埋め込みは、他の構造体やインターフェースを匿名フィールドとして構造体内に含める機能です。これにより、埋め込まれた型のメソッドが、埋め込み元の構造体のメソッドとして「昇格（promoted）」されます。
    *   例えば、`IntVector`が`vector.Vector`を埋め込んでいる場合、`IntVector`のインスタンスは`vector.Vector`のメソッドを直接呼び出すことができます。
    *   このコミットの背景にあるのは、`IntVector`が`vector.Vector`のメソッドをラップして再定義していたことです。埋め込みの機能により、これらのラッパーメソッドは不要となり、直接`IntVector.Vector.Method()`のようにアクセスするか、あるいは単に`IntVector.Method()`として呼び出すことが可能になります。このコミットは、後者の「昇格」されたメソッドを直接利用する方針に切り替えることで、冗長なコードを削除しています。

3.  **スライス (Slices)**:
    *   Go言語の組み込み型であるスライスは、配列の一部を参照する動的なビューです。`container/vector`パッケージは、スライスがGo言語の主要な動的配列メカニズムとして確立される前の過渡期に存在していました。
    *   `vector.Vector`の内部実装は、最終的にGoのスライスを基盤としていました。`Delete`メソッドにおける`copy`関数やスライスの再スライス（`p.a = a[0 : n-1]`）は、スライスの基本的な操作です。

4.  **ガベージコレクション (GC) と`nil`化**:
    *   Goはガベージコレクタを持つ言語です。不要になったメモリはGCによって自動的に解放されます。
    *   コレクションから要素を削除する際、その要素への参照が残っていると、GCがそのメモリを解放できず、メモリリークや不要なメモリ保持につながる可能性があります。
    *   このコミットでは、`Delete`および`Pop`メソッドで削除された要素の参照を`nil`に設定する（`a[n-1] = nil;` や `p.a[i] = nil;`）ことで、GCがその要素を適切に回収できるようにしています。これは、メモリ効率を向上させるための重要なプラクティスです。

## 技術的詳細

このコミットの技術的詳細は、主に`container/vector`パッケージ内の`intvector.go`と`vector.go`の変更に集約されます。

### `src/lib/container/vector/intvector.go`の変更

*   **冗長なメソッドの削除**:
    *   `Set(i int, x int)`
    *   `Insert(i int, x int)`
    *   `Delete(i int) int`
    *   `Push(x int)`
    これらのメソッドは、`IntVector`が埋め込んでいる`vector.Vector`の同名のメソッドを単に呼び出すだけのラッパーでした。Goの構造体埋め込みの機能により、`IntVector`のインスタンスから直接`p.Vector.Set(i, x)`のようにアクセスするか、あるいは`p.Set(i, x)`のように「昇格された」メソッドとして呼び出すことが可能です。このコミットは、冗長なラッパーを削除し、コードベースを簡潔に保つことを選択しました。
*   **`TODO`コメントの削除**: `// TODO do not export field`というコメントが削除されています。これは、`Vector`フィールドが匿名で埋め込まれることで、実質的にエクスポートされない形になるため、この`TODO`が不要になったことを示唆しています。

### `src/lib/container/vector/vector.go`の変更

*   **`Delete(i int) Element` から `Delete(i int)` への変更**:
    *   変更前: `func (p *Vector) Delete(i int) Element` は削除された要素を返していました。
    *   変更後: `func (p *Vector) Delete(i int)` は何も返さなくなりました。
    *   内部実装では、削除された要素`x := a[i]`の取得行が削除され、`return x`も削除されています。
    *   この変更の理由は、コミットメッセージにある通り「Faster vector.Delete, removed result value (easy to get via At(i))」です。削除された要素が必要な場合は、削除前に`At(i)`で取得するというパターンを推奨することで、`Delete`メソッド自体のオーバーヘッドを減らし、より高速な操作を可能にしています。
*   **`Pop() Element` の実装変更**:
    *   変更前: `Pop`は内部的に`return p.Delete(len(p.a) - 1)`を呼び出していました。
    *   変更後: `Pop`は`Delete`を呼び出す代わりに、直接スライス操作を行うようになりました。
        ```go
        i := len(p.a) - 1;
        x := p.a[i];
        p.a[i] = nil;  // support GC, nil out entry
        p.a = p.a[0 : i];
        return x;
        ```
    *   この変更により、`Pop`は末尾要素の取得、GCのための`nil`化、そしてスライスの再スライスを直接行います。これは、`Pop`が常に末尾の要素を扱うという特性を活かした最適化であり、汎用的な`Delete`メソッドを呼び出すよりも効率的です。特に、`Delete`メソッドが返り値をなくしたため、`Pop`が以前のように`Delete`の返り値を利用できなくなったことも、この変更の理由の一つと考えられます。

### `src/lib/container/vector/vector_test.go`の変更

*   `TestInsertDeleteClear`関数内のテストロジックが、`Delete`メソッドのシグネチャ変更に合わせて修正されています。
    *   変更前: `if a.Delete(0).(int) != val(i) { t.Error("D") }`
    *   変更後: `if a.At(0).(int) != val(i) { t.Error("D") }` の後に `a.Delete(0);`
    *   これは、`Delete`が値を返さなくなったため、削除前の要素の値は`At(0)`で事前に取得する必要があることを反映しています。

これらの変更は、Go言語の初期におけるパフォーマンスとAPI設計の洗練に向けた継続的な努力を示しています。

## コアとなるコードの解説

### `src/lib/container/vector/intvector.go`の変更

*   **削除されたメソッド群**: `Set`, `Insert`, `Delete`, `Push`メソッドが`IntVector`から削除されました。これらのメソッドは、`IntVector`が`vector.Vector`を匿名フィールドとして埋め込んでいるため、`IntVector`のインスタンスから直接`vector.Vector`のメソッドを呼び出すことが可能です。例えば、以前は`p.Set(i, x)`が`p.Vector.Set(i, x)`を呼び出すラッパーでしたが、この変更後は`p.Set(i, x)`という呼び出しは、Goの言語仕様によって`p.Vector.Set(i, x)`に自動的に解決されるため、明示的なラッパーは不要になります。これにより、コードの重複が排除され、`IntVector`の定義がより簡潔になりました。

### `src/lib/container/vector/vector.go`の変更

*   **`Delete(i int)`メソッドの変更**:
    *   **返り値の削除**: 以前は`Element`型の値を返していましたが、この変更により返り値がなくなりました。これは、削除された要素の値が必要な場合は、削除操作を行う前に`At(i)`メソッドで明示的に取得するという設計思想に基づいています。これにより、`Delete`メソッドのシグネチャが簡素化され、メソッドの目的が「要素を削除する」ことに特化されました。
    *   **パフォーマンス**: 返り値の生成と返却に伴うオーバーヘッドがなくなることで、理論的には`Delete`操作がわずかに高速化される可能性があります。
*   **`Pop() Element`メソッドの変更**:
    *   以前は`Delete(len(p.a) - 1)`を呼び出すことで末尾要素の削除と取得を行っていましたが、この変更により`Pop`は直接配列操作を行うようになりました。
    *   `i := len(p.a) - 1;`: 末尾要素のインデックスを取得します。
    *   `x := p.a[i];`: 末尾要素の値を`x`に保存します。
    *   `p.a[i] = nil;`: **重要な変更点**。削除される要素への参照を`nil`に設定します。これにより、ガベージコレクタがこの要素が不要になったことを認識し、メモリを適切に解放できるようになります。これはメモリリークを防ぎ、メモリ効率を向上させるためのプラクティスです。
    *   `p.a = p.a[0 : i];`: スライスを再スライスし、末尾要素を論理的に削除します。
    *   `return x;`: 削除された末尾要素の値を返します。
    *   この変更は、`Pop`が常に末尾要素を扱うという特性を活かした最適化であり、汎用的な`Delete`メソッドを呼び出すよりも効率的です。また、`Delete`メソッドが返り値を返さなくなったため、`Pop`が以前のように`Delete`の返り値を利用できなくなったことも、この変更の直接的な理由の一つです。

### `src/lib/container/vector/vector_test.go`の変更

*   `TestInsertDeleteClear`内のテストコードが、`Delete`メソッドの返り値がなくなったことに合わせて修正されました。
    *   以前は`a.Delete(0).(int)`の返り値を直接検証していましたが、変更後はまず`a.At(0).(int)`で削除前の要素の値を取得し、その後に`a.Delete(0)`を呼び出す形に変更されています。これは、`Delete`メソッドの新しいAPI契約に準拠したテストの書き方です。

これらの変更は、Go言語の初期におけるAPIの洗練、パフォーマンスの最適化、そしてメモリ管理のベストプラクティスへの移行を示すものです。

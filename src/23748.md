# [インデックス 23748] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/link`）がWindows環境で`-s`フラグ（シンボル情報を除去するフラグ）と共に使用された際に発生していたクラッシュを修正するものです。具体的には、PE（Portable Executable）ファイル形式のシンボルテーブル生成ロジックにおいて、`-s`フラグが指定されている場合や外部リンカを使用している場合に、不要なシンボル処理をスキップすることで問題を解決しています。

## 変更の背景

Go言語のリンカは、実行ファイルを生成する際に様々な最適化を行います。その一つに、デバッグ情報やシンボルテーブルを除去する機能があり、これは`go build`コマンドに`-s`フラグを渡すことで有効になります。このフラグを使用すると、生成されるバイナリのサイズが小さくなり、配布に適した形になります。

しかし、Windows環境において、この`-s`フラグを有効にしてGoプログラムをリンクすると、リンカ自体がクラッシュするという問題（Issue #10254）が報告されていました。このクラッシュは、特にPE（Portable Executable）ファイル形式のシンボルテーブルを処理する部分で発生していました。

PEファイルはWindowsの実行ファイル形式であり、その内部にはシンボルテーブルが含まれます。シンボルテーブルは、関数名やグローバル変数名などの情報を格納し、デバッグや動的リンクに利用されます。`-s`フラグが指定された場合、これらのシンボル情報は不要となるか、あるいは最小限に抑えられるべきです。

このコミットは、`-s`フラグが指定されているにもかかわらず、リンカがシンボルテーブルのエントリを不適切に処理しようとすることで発生していたクラッシュを修正することを目的としています。特に、動的インポート（DLLの利用など）に関連するシンボル処理と、外部リンカ（`LinkExternal`）を使用する場合の挙動が問題の原因となっていたようです。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Go言語のリンカ (`cmd/link`)**:
    Go言語のビルドプロセスにおいて、コンパイルされたオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能バイナリを生成するツールです。Goは独自のリンカを持っており、多くの場合、C/C++のような外部リンカに依存しません。

2.  **`-s` フラグ**:
    `go build`コマンドや`go link`コマンドに渡されるオプションの一つで、生成されるバイナリからシンボルテーブルとデバッグ情報を除去するようリンカに指示します。これにより、バイナリサイズが削減されますが、デバッグが困難になります。

3.  **Windows PE (Portable Executable) フォーマット**:
    Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLLなどのファイル形式です。PEファイルは、ヘッダ、セクション、シンボルテーブルなど、プログラムの実行に必要な様々な情報を含んでいます。

4.  **シンボルテーブル**:
    実行可能ファイルやオブジェクトファイル内に含まれるデータ構造で、プログラム内のシンボル（関数名、グローバル変数名など）とそのアドレスや型などの情報が格納されています。デバッガはこれを利用して、ソースコードレベルでのデバッグを可能にします。

5.  **動的インポート (Dynamic Import)**:
    Windowsにおいて、プログラムが実行時にDLL（Dynamic Link Library）から関数やデータを取り込む仕組みです。PEファイルには、どのDLLからどのシンボルをインポートするかを示す情報が含まれます。

6.  **外部リンカ (`LinkExternal`)**:
    Goのリンカは通常、内部リンカを使用しますが、CGO（GoとCの相互運用）を使用する場合や、特定のプラットフォーム要件がある場合には、`gcc`などの外部リンカを使用するように設定できます。`Linkmode == LinkExternal`は、この外部リンカモードが有効であることを示します。

7.  **COFF (Common Object File Format)**:
    PEファイル形式の基盤となっているオブジェクトファイル形式の一つです。PEファイル内のシンボルテーブルはCOFFシンボル形式で記述されることがあります。`ncoffsym`はCOFFシンボルの数を管理するカウンタと推測されます。

## 技術的詳細

このコミットの技術的詳細は、主に`src/cmd/link/internal/ld/pe.go`ファイル内のシンボルテーブル生成ロジックの変更にあります。

問題の核心は、`-s`フラグが指定されている（つまりシンボル情報が不要な）場合や、外部リンカが使用されている場合に、Goの内部リンカがPEシンボルテーブルに関連する処理を不適切に実行しようとしていた点にあります。特に、動的インポートに関連するシンボル（`initdynimport`関数内で処理されるもの）や、一般的なアセンブリシンボル（`genasmsym`関数で処理されるもの）の扱いが問題でした。

変更前は、`initdynimport`関数内で動的インポートシンボルに対して`ncoffsym++`が実行され、シンボルテーブルエントリが事前に割り当てられていました。しかし、`-s`フラグが有効な場合はこれらのエントリは最終的に不要になるため、この事前割り当てが問題を引き起こす可能性がありました。

また、`addpesymtable`関数では、`Debug['s'] == 0`（`-s`フラグが指定されていない場合）にのみ`genasmsym(addpesym)`が呼び出され、PEシンボルテーブルにアセンブリシンボルが追加されていました。しかし、`LinkExternal`モードの場合の動的インポートシンボルの処理が、この条件分岐の外側で、かつ重複して行われていました。この重複と条件の不整合が、`-s`フラグと`LinkExternal`モードの組み合わせでクラッシュを引き起こす原因となっていたと考えられます。

このコミットでは、以下の主要な変更が導入されています。

1.  **`initdynimport`からの`ncoffsym`インクリメントの削除**:
    動的インポートシンボルに対する`ncoffsym`の事前インクリメントが削除されました。これにより、`-s`フラグが指定されている場合に不要なシンボルエントリの割り当てを試みることを防ぎます。

2.  **新しいヘルパー関数`pegenasmsym`の導入**:
    `pegenasmsym`という新しい関数が導入されました。この関数は、`genasmsym`のラッパーとして機能し、`LinkExternal`モードの場合に動的インポートシンボルを`addpesym`に渡すロジックをカプセル化しています。これにより、シンボル生成ロジックが一箇所に集約され、重複が排除されます。

3.  **`addpesymtable`のロジックの簡素化と修正**:
    `addpesymtable`関数内の条件分岐が`if Debug['s'] == 0 || Linkmode == LinkExternal`に変更されました。これは、`-s`フラグが指定されていない場合、または外部リンカを使用している場合にシンボルテーブルを生成することを示します。
    さらに、`ncoffsym`の初期化（`ncoffsym = 0`）と、新しい`pegenasmsym`関数を呼び出すことで、シンボルテーブルの生成ロジックが整理され、`-s`フラグや`LinkExternal`モードの有無に応じた適切なシンボル処理が保証されるようになりました。特に、`LinkExternal`モードの場合でも、`pegenasmsym`を通じて動的インポートシンボルが適切に処理されるようになっています。

これらの変更により、リンカは`-s`フラグが指定された場合や外部リンカを使用している場合に、PEシンボルテーブルの不必要な処理を回避し、クラッシュを防ぐことができるようになりました。

## コアとなるコードの解説

1.  **`initdynimport`からの変更**:
    以前は、動的インポートシンボルが処理される際に、`ncoffsym`（COFFシンボルカウンタ）がインクリメントされ、`dynSym.Dynid`にその値が割り当てられていました。これは、シンボルテーブルにエントリを「予約」するような動作でした。しかし、`-s`フラグが指定されている場合、これらのシンボル情報は最終的に破棄されるため、この事前割り当ては無駄であり、場合によってはリンカの内部状態を不正にし、クラッシュの原因となっていた可能性があります。このコミットでは、この不要な事前割り当てを削除することで、リンカの挙動をより堅牢にしています。

2.  **`pegenasmsym`の導入**:
    この新しい関数は、PEファイル形式に特化したアセンブリシンボル生成のヘルパーです。
    *   `Linkmode == LinkExternal`の場合、動的インポートに関連するシンボル（`d.ms`リストを走査して取得される`Xsym`）を`put`関数（この場合は`addpesym`）に渡して追加します。これは、外部リンカを使用する場合でも、Goの内部リンカが動的インポートシンボルを適切に認識し、処理する必要があるためです。
    *   その後、`genasmsym(put)`を呼び出し、一般的なアセンブリシンボルを`put`関数に渡します。
    この関数を導入することで、動的インポートシンボルの処理と一般的なアセンブリシンボルの処理を一つの統一されたパスで管理できるようになり、`addpesymtable`内のロジックが簡素化されました。

3.  **`addpesymtable`の変更**:
    この関数は、最終的なPEシンボルテーブルを構築する役割を担っています。
    *   変更前の`if Debug['s'] == 0`という条件は、`-s`フラグが指定されていない場合にのみシンボルテーブルを生成するというものでした。しかし、`LinkExternal`モードの場合の動的インポートシンボルの処理がこの条件の外側で重複して行われており、これが問題でした。
    *   変更後の条件`if Debug['s'] == 0 || Linkmode == LinkExternal`は、`-s`フラグが指定されていない場合、**または**外部リンカを使用している場合にシンボルテーブルを生成することを示します。外部リンカを使用する場合、Goのリンカはシンボルテーブルを生成し、それを外部リンカに渡す必要があるため、この条件は理にかなっています。
    *   内部では、`ncoffsym = 0`でカウンタをリセットした後、新しく導入された`pegenasmsym(addpesym)`を呼び出しています。これにより、`LinkExternal`モードの動的インポートシンボルと、一般的なアセンブリシンボルが、重複なく、かつ適切な条件で`addpesym`を通じて`coffsym`（COFFシンボル配列）に追加されるようになります。
    *   この修正により、`-s`フラグが指定されている場合はシンボルテーブルの生成が完全にスキップされ、クラッシュが回避されます。一方、外部リンカを使用している場合は、必要なシンボル情報が正しく収集されるようになります。

これらの変更は、GoリンカのPEファイル生成ロジックにおける、シンボルテーブルの生成と`-s`フラグ、および外部リンカの相互作用に関するバグを修正し、堅牢性を向上させています。

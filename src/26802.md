## 元コミット内容

`cmd/compile`: `Func.{Dcl,Inldcl}` を `NodeList` から `slice` に変更。

`slice` は `NodeList` よりもメモリ使用量が少なく、リストを走査する際のメモリ局所性が向上します。

この変更により、クロージャに関連するトリッキーなケースが明らかになりました。エスケープ解析パスがクロージャに対して実行される際、`ODCLFUNC` ではなく `OCLOSURE` の `Dcl` リストに要素を追加していました。これは、両者が同じ `NodeList` を共有していたため、偶然にも機能していました。この問題は `addrescapes` の変更と、再発を防ぐための `Tempname` のチェックによって修正されました。

このコミットにより、`listsort` 関数のテスト以外の最後の使用箇所が削除されました。この関数を完全に削除するための別の変更リスト (CL) が後で送られる予定です。

残念ながら、この変更はすべてのテストをパスしますが、`toolstash -cmp` はパスしません。問題は、`cmpstackvarlt` がソート順を完全に決定しないため、`listsort` から `sort.Sort` への変更（一般的には望ましい変更）が異なる順序を生成することにあります。`cmpstackvarlt` を完全に決定論的にすることで段階的にこの問題を解決することも可能ですが、いずれにせよ `toolstash -cmp` はどこかの時点で壊れるでしょう。

筆者の非公式なテストでは、コンパイラの速度が2.2%向上しました。

Issue #14473 を更新します。

## 変更の背景

このコミットの主な背景は、Goコンパイラのパフォーマンス最適化とメモリ効率の改善です。具体的には、コンパイラ内部で関数内の宣言（`Dcl`）やインライン化された宣言（`Inldcl`）を管理するために使用されていたデータ構造を、`NodeList`（リンクリスト）からGoの組み込み型である`slice`（動的配列）に切り替えることを目的としています。

リンクリストは要素がメモリ上に分散して配置されるため、リストを走査する際にキャッシュミスが頻繁に発生し、メモリ局所性が低いという問題があります。一方、スライスは要素がメモリ上に連続して配置されるため、CPUのキャッシュ効率が良く、高速なアクセスが可能です。コンパイラが頻繁にこれらの宣言リストを走査することを考えると、この変更は全体的なコンパイル時間の短縮に大きく貢献すると期待されます。

また、このデータ構造の変更は、既存のコードベースに潜在していたバグを露呈させました。特に、クロージャのエスケープ解析における`Dcl`リストへの追加処理の誤りが発見され、その修正もこのコミットに含まれています。これは、データ構造の変更がコードの健全性を検証する副次的な効果をもたらした良い例と言えます。

さらに、`listsort`関数の使用を廃止し、Go標準ライブラリの`sort.Sort`に移行することで、コードの保守性を高め、より最適化されたソートアルゴリズムを利用するという意図も含まれています。

## 前提知識の解説

### Goコンパイラの内部構造

Goコンパイラ（`cmd/compile`）は、Go言語のソースコードを機械語に変換する複雑なプロセスを実行します。このプロセスには、字句解析、構文解析、型チェック、中間表現（IR）の生成、最適化、コード生成などが含まれます。

*   **AST (Abstract Syntax Tree)**: ソースコードの構文構造を木構造で表現したものです。コンパイラはASTを操作して様々な解析や変換を行います。
*   **`Node`**: ASTの各ノードを表すGoコンパイラ内部のデータ構造です。変数、関数、式、文など、プログラムのあらゆる要素が`Node`として表現されます。
*   **`Func`**: 関数を表す`Node`に付随する構造体で、その関数に関する様々な情報（宣言された変数、引数、戻り値、ボディなど）を保持します。
*   **`Dcl` (Declarations)**: 関数内で宣言されたローカル変数、引数、戻り値などを指します。コンパイラはこれらの宣言をリストとして管理します。
*   **`Inldcl` (Inlined Declarations)**: インライン化された関数内の宣言を指します。インライン化は、関数呼び出しのオーバーヘッドを削減するために、呼び出し元のコードに呼び出される関数の本体を直接埋め込む最適化手法です。

### `NodeList` と `slice`

*   **`NodeList`**: このコミット以前にGoコンパイラで使用されていた、`Node`オブジェクトのリンクリスト実装です。リンクリストは、各要素が次の要素へのポインタを持つ構造で、要素の追加や削除は効率的ですが、特定の要素へのアクセスやリストの走査は、メモリが連続していないためにキャッシュミスが多く発生し、パフォーマンスが低下する可能性があります。
*   **`slice`**: Go言語の組み込み型であるスライスは、動的配列のようなものです。内部的には、要素が連続したメモリブロックに格納された配列へのポインタ、長さ、容量から構成されます。スライスはメモリ局所性が高く、シーケンシャルなアクセスや走査が非常に高速です。要素の追加によって容量を超えた場合は、より大きな新しい配列が割り当てられ、既存の要素がコピーされます。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、Goコンパイラが行う重要な最適化の一つです。変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを決定します。

*   **スタック (Stack)**: 関数呼び出しごとに割り当てられるメモリ領域で、関数の実行が終了すると自動的に解放されます。スタックに割り当てられた変数は、その関数内でのみ有効です。
*   **ヒープ (Heap)**: プログラム全体で共有されるメモリ領域で、ガベージコレクタによって管理されます。ヒープに割り当てられた変数は、その変数を参照するポインタが存在する限り有効です。
*   **エスケープ (Escape)**: ある関数内で宣言された変数が、その関数のスコープ外（例えば、別の関数にポインタとして渡される、グローバル変数に代入される、クロージャによってキャプチャされるなど）から参照され続ける可能性がある場合、その変数は「エスケープする」と表現されます。エスケープする変数は、関数の終了後も存在し続ける必要があるため、ヒープに割り当てられる必要があります。
*   **`addrescapes`**: エスケープ解析の過程で、変数がヒープに割り当てられるべきかどうかを判断し、必要な処理を行うコンパイラ内部の関数です。

### クロージャ (Closures)

クロージャは、関数が自身の外側のスコープにある変数を参照できる機能です。Goでは、匿名関数が外側の変数をキャプチャするとクロージャになります。

*   **`OCLOSURE`**: Goコンパイラ内部でクロージャ（匿名関数）を表すASTノードの種類です。
*   **`ODCLFUNC`**: Goコンパイラ内部で通常の宣言された関数を表すASTノードの種類です。

クロージャが外側の変数をキャプチャする場合、その変数はクロージャが実行される間、存続する必要があります。そのため、エスケープ解析によってヒープに割り当てられることがよくあります。

### `toolstash -cmp`

`toolstash -cmp`は、Goコンパイラの開発者が変更がコンパイル結果に与える影響を比較するために使用するツールです。これは、変更前と変更後のコンパイラで同じソースコードをコンパイルし、生成されたオブジェクトファイルやアセンブリコードの差分を検出します。これにより、意図しないコード生成の変更やパフォーマンスの回帰を早期に発見できます。

*   **`cmpstackvarlt`**: スタック変数のソート順を比較するための関数です。`toolstash -cmp`が異なるソート順を検出する原因となった、決定論的でない比較ロジックを持つ可能性が示唆されています。

## 技術的詳細

このコミットの技術的詳細の核心は、Goコンパイラの`Func`構造体内の`Dcl`（宣言リスト）と`Inldcl`（インライン宣言リスト）の型を、カスタムのリンクリスト実装である`NodeList`から、Goの組み込みスライス型`[]*Node`に変更した点にあります。

### `NodeList`から`[]*Node`への変更の利点

1.  **メモリ効率の向上**:
    *   `NodeList`は各`Node`が次の`Node`へのポインタを持つため、各要素にポインタ分のオーバーヘッドがあります。また、個々の`Node`がヒープ上に分散して割り当てられる傾向があります。
    *   `[]*Node`は、`*Node`へのポインタの連続した配列であり、オーバーヘッドが少なく、メモリ使用量が削減されます。
2.  **メモリ局所性の改善**:
    *   リンクリストは要素がメモリ上で連続している保証がないため、リストを走査する際にCPUキャッシュのヒット率が低くなり、パフォーマンスが低下します（キャッシュミス）。
    *   スライスは要素が連続したメモリブロックに格納されるため、CPUがデータをプリフェッチしやすくなり、キャッシュヒット率が向上します。これにより、リストの走査が高速化されます。コンパイラは宣言リストを頻繁に走査するため、この改善はコンパイル時間短縮に直接寄与します。
3.  **コードの簡素化と標準化**:
    *   カスタムのリンクリスト実装をGoの標準スライスに置き換えることで、コードがよりGoのイディオムに沿ったものになり、理解しやすくなります。
    *   `listsort`のようなカスタムソート関数が不要になり、標準ライブラリの`sort.Sort`を利用できるようになります。

### クロージャのエスケープ解析に関するバグとその修正

この変更によって、クロージャのエスケープ解析における既存のバグが露呈しました。

*   **バグの内容**: エスケープ解析パスがクロージャ（`OCLOSURE`）に対して実行される際、そのクロージャ内で宣言された変数（`Dcl`リスト）を、本来そのクロージャ自身が持つべき`Dcl`リストではなく、そのクロージャを囲む関数（`ODCLFUNC`）の`Dcl`リストに追加していました。
*   **なぜ今まで問題にならなかったか**: `OCLOSURE`と`ODCLFUNC`が同じ`NodeList`インスタンスを共有していたため、誤ったリストに追加しても、結果的に同じメモリ領域に書き込まれていたため、偶然にも機能していました。
*   **`NodeList`から`slice`への変更で露呈した理由**: `NodeList`が`slice`に置き換えられたことで、`OCLOSURE`と`ODCLFUNC`がそれぞれ独立した`slice`を持つようになり、この共有関係が解消されました。その結果、誤った`slice`に要素が追加されると、期待される動作と異なる結果が生じるようになり、バグが顕在化しました。
*   **修正方法**:
    *   `addrescapes`関数に修正が加えられました。具体的には、エスケープ解析中に現在の関数が`OCLOSURE`であり、かつその`Closure`フィールドが設定されている場合、`Curfn`（現在の関数ノード）をその`Closure`フィールドが指すノードに切り替えるロジックが追加されました。これにより、エスケープ解析がクロージャ自身の`Dcl`リストを正しく操作するようになります。
    *   `Tempname`関数にもチェックが追加されました。この関数は一時変数を生成し、現在の関数の`Dcl`リストに追加しますが、ここでも`OCLOSURE`の`Dcl`リストに誤って追加しようとした場合に`Fatalf`（致命的なエラー）を発生させることで、同様の再発を防ぐためのガードが設けられました。

### `listsort`の廃止と`toolstash -cmp`の問題

*   **`listsort`の廃止**: `NodeList`が`slice`に置き換えられたことで、カスタムのリンクリストソート関数である`listsort`の必要性がなくなりました。コミットメッセージでは、テスト以外の最後の使用箇所が削除されたと述べられており、将来的にはこの関数自体が削除される予定です。これは、Go標準ライブラリの`sort`パッケージを利用することで、より堅牢で最適化されたソート機能に依存できるという利点があります。
*   **`toolstash -cmp`の問題**: `listsort`から標準ライブラリの`sort.Sort`への移行は望ましい変更ですが、`toolstash -cmp`がコンパイル結果の差分を検出する際に問題を引き起こしました。これは、`cmpstackvarlt`という比較関数がスタック変数のソート順を完全に決定論的に定義していなかったためです。結果として、`sort.Sort`が`listsort`とは異なる（しかし、どちらも有効な）ソート順を生成し、`toolstash -cmp`が差分を報告する原因となりました。コミットメッセージでは、`cmpstackvarlt`を完全に決定論的にすることでこの問題を段階的に解決できる可能性に言及していますが、`toolstash -cmp`がどこかの時点で差分を報告するのは避けられないという認識も示されています。これは、コンパイラの内部的なデータ構造や処理順序の変更が、最終的なコード生成に影響を与え、比較ツールがそれを検出するという、コンパイラ開発における一般的な課題を浮き彫りにしています。

### パフォーマンス向上

筆者の非公式なテストでは、この変更によりコンパイラの速度が2.2%向上したと報告されています。これは、`NodeList`から`slice`への移行によるメモリ局所性の改善が、コンパイル時間短縮に実際に寄与したことを示しています。

## コアとなるコードの解説

このコミットのコード変更は、Goコンパイラの内部で関数スコープの宣言（ローカル変数、引数、戻り値など）を管理する方法を、従来のリンクリストからGoのスライスへと移行させるものです。これにより、メモリ効率とパフォーマンスが向上し、同時に既存のバグが修正されました。

### `Func`構造体の変更 (`src/cmd/compile/internal/gc/syntax.go`)

最も根本的な変更は、`Func`構造体内の`Dcl`と`Inldcl`フィールドの型定義です。

```go
type Func struct {
	// ...
	Dcl        []*Node   // autodcl for this func/closure
	Inldcl     []*Node   // copy of dcl for use in inlining
	// ...
}
```

*   **`Dcl`**: 関数内で宣言されたすべての変数（自動変数、引数、戻り値など）のリストを保持します。以前は`*NodeList`（リンクリストのヘッドへのポインタ）でしたが、`[]*Node`（`Node`ポインタのスライス）に変更されました。
*   **`Inldcl`**: インライン化された関数内の宣言のコピーを保持します。これも同様に`*NodeList`から`[]*Node`に変更されました。

この変更により、これらの宣言リストへのアクセスや操作は、リンクリストのポインタを辿るのではなく、スライスのインデックスアクセスやスライス操作（`append`など）で行われるようになります。

### リンクリスト走査からスライス走査への移行 (多数のファイル)

`Func.Dcl`や`Func.Inldcl`を使用していたGoコンパイラの多くの箇所で、リストの走査ロジックが変更されています。

**変更前（リンクリスト）の典型的なパターン:**

```go
for l := gc.Curfn.Func.Dcl; l != nil; l = l.Next {
	n := l.N
	// ... n を使用した処理 ...
}
```
このパターンでは、`l`が`NodeList`の要素（`Node`へのポインタと次の`NodeList`要素へのポインタを持つ構造体）であり、`l.Next`で次の要素に進みます。

**変更後（スライス）の典型的なパターン:**

```go
for _, n := range gc.Curfn.Func.Dcl {
	// ... n を使用した処理 ...
}
```
このパターンでは、Goのスライスの`range`ループを使用しており、`n`はスライス内の`*Node`要素を直接参照します。これにより、コードが簡潔になり、メモリ局所性が向上します。

### クロージャのエスケープ解析の修正 (`src/cmd/compile/internal/gc/gen.go`)

このコミットの重要な修正点の一つは、クロージャのエスケープ解析におけるバグの修正です。

**`addrescapes`関数の修正:**

```go
func addrescapes(n *Node) {
	// ...
	oldfn := Curfn
	Curfn = n.Name.Curfn
	if Curfn.Func.Closure != nil && Curfn.Op == OCLOSURE {
		Curfn = Curfn.Func.Closure
	}
	// ...
}
```
`addrescapes`は、変数がヒープにエスケープするかどうかを判断する関数です。クロージャの場合、`n.Name.Curfn`はクロージャを囲む関数を指すことがありますが、エスケープ解析はクロージャ自身のコンテキストで行われるべきです。この修正では、もし現在の関数（`Curfn`）が`OCLOSURE`（クロージャを表すノード）であり、かつその`Closure`フィールドが設定されている場合、`Curfn`をその`Closure`フィールドが指すノード（つまり、クロージャ自身の関数ノード）に再設定します。これにより、エスケープ解析がクロージャの`Dcl`リストを正しく操作するようになります。

**`Tempname`関数の修正:**

```go
func Tempname(nn *Node, t *Type) {
	// ...
	if Curfn.Func.Closure != nil && Curfn.Op == OCLOSURE {
		Dump("Tempname", Curfn)
		Fatalf("adding tempname to wrong closure function")
	}
	// ...
	Curfn.Func.Dcl = append(Curfn.Func.Dcl, n)
	// ...
}
```
`Tempname`は一時変数を生成し、現在の関数の`Dcl`リストに追加します。この修正では、`addrescapes`と同様に、もし`Curfn`が`OCLOSURE`であるにもかかわらず、その`Dcl`リストに一時変数を追加しようとした場合に、致命的なエラー（`Fatalf`）を発生させます。これは、クロージャの`Dcl`リストが誤って操作されることを防ぐためのガードであり、エスケープ解析の修正と合わせて、クロージャの変数管理の正確性を保証します。

### スタック変数ソートの変更 (`src/cmd/compile/internal/gc/pgen.go`)

`allocauto`関数内で、スタック変数のソートにGo標準ライブラリの`sort.Sort`が使用されるようになりました。

```go
// byStackVar implements sort.Interface for []*Node using cmpstackvarlt.
type byStackVar []*Node

func (s byStackVar) Len() int           { return len(s) }
func (s byStackVar) Less(i, j int) bool { return cmpstackvarlt(s[i], s[j]) }
func (s byStackVar) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }

// ...

func allocauto(ptxt *obj.Prog) {
	// ...
	sort.Sort(byStackVar(Curfn.Func.Dcl))
	// ...
}
```
`byStackVar`という新しい型が定義され、`sort.Interface`（`Len`, `Less`, `Swap`メソッド）を実装しています。これにより、`Curfn.Func.Dcl`（`[]*Node`型）を`byStackVar`型にキャストして`sort.Sort`に渡すことで、`cmpstackvarlt`関数で定義されたロジックに基づいてソートできるようになります。これは、カスタムの`listsort`関数を廃止し、標準ライブラリのソート機能に移行する一環です。

これらの変更は、Goコンパイラの内部的な堅牢性、効率性、および保守性を向上させるための重要なステップです。

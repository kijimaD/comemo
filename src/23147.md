## 変更の背景

この変更の背景には、Go言語の`defer`ステートメントの実行タイミングと、テストにおけるリソース管理の堅牢性に関する考慮があります。

Goの`defer`ステートメントは、それが含まれる関数がリターンする直前に実行されるようにスケジュールされます。しかし、`defer`が宣言された時点での変数の値がキャプチャされるわけではなく、`defer`が実行される時点での変数の値が使用されます。このコミットのケースでは、`defer`関数内で参照されるスライス`lss`は、`defer`が実行されるまで要素が追加され続けます。

元のコードでは、`defer`ステートメントがサーバーインスタンスを生成するループの**後**に配置されていました。これは、ループ内で複数の`localServer`インスタンスを作成し、それらを`lss`スライスに追加する処理が行われることを前提としています。

問題は、もしループの途中で`newLocalServer()`の呼び出しがエラーを返し、テストが早期に終了（`t.Fatal()`などで）した場合に発生します。この場合、`defer`ステートメントが宣言された行に到達する前にテスト関数が終了してしまうため、`defer`されたクリーンアップ関数が一度もスケジュールされず、結果として既に作成されていた`localServer`インスタンスが適切にティアダウンされない可能性がありました。これにより、テスト実行後にポートが解放されなかったり、リソースリークが発生したりするなどの問題が引き起こされる可能性があります。

このコミットは、このようなシナリオでも確実にリソースが解放されるように、`defer`ステートメントの配置を修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とテストに関する知識が必要です。

1.  **`defer`ステートメント**:
    Go言語の`defer`ステートメントは、関数がリターンする直前に実行される関数呼び出しをスケジュールするために使用されます。これは、リソースの解放（ファイルクローズ、ロック解除、ネットワーク接続クローズなど）を確実に行うための非常に便利な機能です。`defer`された関数は、`defer`ステートメントが実行された順序とは逆の順序で実行されます（LIFO: Last-In, First-Out）。重要なのは、`defer`された関数は、`defer`ステートメントが**実行された時点**でスケジュールされるという点です。つまり、`defer`ステートメントが実行されなければ、その関数はスケジュールされません。

2.  **Goのテストフレームワーク (`testing`パッケージ)**:
    Goには標準で`testing`パッケージが提供されており、これを使ってユニットテストやベンチマークテストを記述します。
    *   `func TestXxx(t *testing.T)`: テスト関数は`Test`で始まり、`*testing.T`型の引数を取ります。
    *   `t.Fatal()` / `t.Fatalf()`: これらのメソッドは、テストを失敗としてマークし、現在のテスト関数の実行を即座に停止します。これにより、テストの残りの部分が実行されなくなります。

3.  **リソース管理とクリーンアップ**:
    ネットワークサーバーのテストでは、テストのために一時的にサーバーを起動し、テストが完了したらそのサーバーを停止し、使用したポートなどのリソースを解放する必要があります。これを怠ると、テストの実行ごとにリソースが消費され続け、最終的にはリソース不足でテストが実行できなくなるなどの問題が発生します。`teardown()`のような関数は、このクリーンアップ処理を担当します。

## 技術的詳細

このコミットの技術的な核心は、`defer`ステートメントの実行タイミングと、それが参照する変数のライフサイクルにあります。

元のコードでは、`TestTCPServer`と`TestUnixAndUnixpacketServer`の両方のテスト関数内で、以下のような構造になっていました。

```go
// ...
var lss []*localServer
var tpchs []chan error
for i := 0; i < N; i++ {
    ls, err := (&streamListener{Listener: ln}).newLocalServer()
    if err != nil {
        t.Fatal(err) // ここでエラーが発生し、テストが終了する可能性がある
    }
    lss = append(lss, ls)
    tpchs = append(tpchs, make(chan error, 1))
}
defer func() { // このdeferはループの後に宣言されている
    for _, ls := range lss {
        ls.teardown()
    }
}()
// ...
```

このコードでは、`defer`ステートメントが`for`ループの**後**に記述されています。もし`for`ループ内で`newLocalServer()`がエラーを返し、`t.Fatal(err)`が呼び出された場合、テスト関数はそこで終了します。このとき、`defer`ステートメントが記述されている行に到達しないため、`defer`された無名関数は**一度もスケジュールされません**。結果として、その時点までに`lss`スライスに追加されていた`localServer`インスタンスの`teardown()`メソッドが呼び出されず、リソースが解放されない状態になります。

変更後のコードでは、`defer`ステートメントが`for`ループの**前**に移動されています。

```go
// ...
var lss []*localServer
var tpchs []chan error
defer func() { // このdeferはループの前に宣言されている
    for _, ls := range lss {
        ls.teardown()
    }
}()
for i := 0; i < N; i++ {
    ls, err := (&streamListener{Listener: ln}).newLocalServer()
    if err != nil {
        t.Fatal(err) // ここでエラーが発生しても、deferは既にスケジュールされている
    }
    lss = append(lss, ls)
    tpchs = append(tpchs, make(chan error, 1))
}
// ...
```

この配置により、`defer`ステートメントは`for`ループが開始される前に必ず実行され、無名関数がスケジュールされます。この無名関数は、テスト関数がリターンする直前に実行されます。`defer`された関数が実行される際、`lss`スライスは、その時点までにループで追加されたすべての`localServer`インスタンスを含んでいます。したがって、たとえループの途中でエラーが発生し、`t.Fatal()`によってテストが早期に終了したとしても、`defer`されたクリーンアップ関数は既にスケジュールされているため、`lss`に含まれるすべての`localServer`インスタンスに対して`teardown()`が確実に呼び出され、リソースが適切に解放されるようになります。

これは、Goの`defer`が「関数が終了する際に実行される」という性質と、「`defer`が宣言された時点でスケジュールされる」という性質を巧みに利用した、堅牢なリソース管理の典型的なパターンです。

## コアとなるコードの変更箇所

変更は`src/net/server_test.go`ファイル内の2つのテスト関数、`TestTCPServer`と`TestUnixAndUnixpacketServer`にあります。

具体的には、以下の`defer`ブロックの移動です。

```diff
-		defer func() {
-			for _, ls := range lss {
-				ls.teardown()
-			}
-		}()
```
が削除され、

```diff
+		defer func() {
+			for _, ls := range lss {
+				ls.teardown()
+			}
+		}()
```
が、`lss`と`tpchs`の変数宣言の直後、かつサーバーインスタンスを生成する`for`ループの直前に挿入されています。

## コアとなるコードの解説

変更されたコードは、Goの`defer`ステートメントのセマンティクスを最大限に活用しています。

```go
var lss []*localServer // localServerインスタンスを格納するスライス
var tpchs []chan error // エラーチャネルを格納するスライス

// deferステートメントをここに移動
// この無名関数は、TestTCPServer関数が終了する直前に実行されるようにスケジュールされる
// lssスライスは、このdeferが実行される時点ではなく、無名関数が実行される時点での内容が参照される
defer func() {
    for _, ls := range lss { // lssスライス内のすべてのlocalServerに対してteardown()を呼び出す
        ls.teardown()
    }
}()

for i := 0; i < N; i++ {
    // 新しいlocalServerインスタンスを作成
    ls, err := (&streamListener{Listener: ln}).newLocalServer()
    if err != nil {
        t.Fatal(err) // エラーが発生した場合、ここでテストが終了する
    }
    lss = append(lss, ls) // 成功した場合、lssスライスにインスタンスを追加
    tpchs = append(tpchs, make(chan error, 1))
}
```

この変更のポイントは、`defer`ブロックが`for`ループの**前**に配置されたことです。これにより、`TestTCPServer`関数が実行を開始すると、まず`lss`と`tpchs`が宣言され、その直後に`defer`ブロックが実行され、無名関数が「この関数が終了する際に実行されるべき」タスクとしてスケジュールされます。

たとえ`for`ループ内で`newLocalServer()`がエラーを返し、`t.Fatal(err)`が呼び出されてテストが即座に終了したとしても、`defer`された無名関数は既にスケジュールされているため、テスト関数が終了する直前に必ず実行されます。その際、`lss`スライスには、エラーが発生するまでに正常に作成されたすべての`localServer`インスタンスが含まれており、それらすべてに対して`ls.teardown()`が呼び出され、リソースが適切にクリーンアップされます。

これは、テストの堅牢性を高め、リソースリークを防ぐための重要な修正であり、Goにおける`defer`の適切な使用例を示しています。

# [インデックス 27889] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile`) とリンカ (`cmd/link`) における `typelink` シンボルのソート方法を改善するものです。具体的には、`typelink` シンボル名に冗長な型情報を埋め込む代わりに、リンカがシンボルの内容（実際の型文字列）に基づいてソートするように変更することで、シンボル名のサイズを削減し、バイナリサイズを最適化します。

## コミット

`cmd/link`, `cmd/compile`: リンカにおける `typelink` ソートの改善

このコミットは、`typelink` シンボル名を短縮し、リンカがその内容に基づいてソートできるようにすることで、Goバイナリのサイズを削減します。

## 変更の背景

Goのコンパイラとリンカは、リフレクションやデバッグ情報のために、プログラム内の型に関するメタデータ（`rtype`構造体）を生成し、これらを `typelink` シンボルとして参照します。以前の実装では、これらの `typelink` シンボルをリンカが効率的にソートできるように、シンボル名自体に型の詳細な文字列表現をほぼ二重に含めていました。具体的には、曖昧なパッケージ名を含む型名と、完全で曖昧さのない型名をタブ区切りで連結していました。

このアプローチは、特に複雑な型や長い型名を持つ場合に、`typelink` シンボル名が非常に長くなるという問題を引き起こしていました。コミットメッセージで言及されているように、`#15104` の問題では、シンボル名が6KBにも達するケースがあり、これはバイナリサイズの肥大化に繋がっていました。シンボル名が長くなると、リンカの処理効率にも影響を与える可能性がありました。

この変更の背景には、シンボル名の冗長性を排除し、バイナリサイズを削減しつつ、リンカのソート処理の効率を維持または向上させるという目的があります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Goのソースコードをオブジェクトファイルに変換するツールです。型情報などのメタデータもこの段階で生成されます。
*   **Goリンカ (`cmd/link`)**: コンパイラが生成した複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成するツールです。この過程でシンボルの解決や配置、ソートが行われます。
*   **`typelink` シンボル**: Goランタイムがリフレクション機能を提供するために使用する特殊なシンボルです。これらは、プログラム内の特定の型 (`reflect.Type` 構造体など) とその文字列表現を関連付けます。リンカはこれらのシンボルを特定の順序で配置する必要があります。
*   **`LSym` (Linker Symbol)**: リンカが内部的にシンボルを表現するためのデータ構造です。シンボル名、サイズ、データ、リロケーション情報などが含まれます。
*   **`rtype` (Runtime Type)**: Goの `reflect` パッケージが利用する、ランタイムにおける型の内部表現です。この構造体には、型の名前やフィールド、メソッドなどの情報が含まれており、その中には型の文字列表現も含まれます。
*   **リロケーション (Relocation)**: オブジェクトファイル内の情報で、リンカが複数のオブジェクトファイルを結合する際に、コードやデータの特定の部分をどのように修正すべきかを指示します。例えば、あるシンボルへの参照が、最終的なバイナリ内のどこを指すべきかを解決するために使用されます。
*   **`bytes.Compare`**: Go標準ライブラリ `bytes` パッケージの関数で、2つのバイトスライスを辞書順に比較します。ソート処理で文字列の比較に用いられます。

## 技術的詳細

このコミットの核心は、`typelink` シンボルのソートロジックをシンボル名からシンボルの内容（実際の型文字列）へと移行させる点にあります。

1.  **コンパイラ側の変更 (`src/cmd/compile/internal/gc/reflect.go`)**:
    *   `typelinkLSym` 関数は、`go.typelink` シンボルの名前を生成する役割を担っています。
    *   変更前は、シンボル名に `Tconv(t, FmtLeft|FmtUnsigned)` (曖昧なパッケージ名を含む型名) と `Tconv(t, FmtLeft)` (完全で曖昧さのない型名) の両方を含め、タブ文字で区切っていました。これは、リンカがシンボル名に基づいてソートする際に、型の文字列表現がソートキーとして機能するようにするためでした。
    *   変更後は、シンボル名が `go.typelink.` に `Tconv(t, FmtLeft)` (完全で曖昧さのない型名) のみを追加する形に簡素化されました。これにより、シンボル名自体の冗長性が排除され、大幅に短縮されます。

2.  **リンカ側の変更 (`src/cmd/link/internal/ld/data.go`)**:
    *   `dataSlice.Less` メソッドは、リンカがデータシンボルをソートする際の比較ロジックを定義しています。
    *   このメソッドに、`go.typelink.` で始まるシンボルを特別に処理するロジックが追加されました。
    *   `decodetype_string` という新しいヘルパー関数を使用して、`typelink` シンボルが参照する `rtype` 構造体から、実際の型文字列のバイトスライスを抽出します。
    *   抽出された型文字列 (`s1n` と `s2n`) を `bytes.Compare` で比較し、その結果に基づいてソート順を決定します。これにより、シンボル名ではなく、シンボルが指す実際の型情報に基づいてソートが行われるようになります。

3.  **シンボルデコードヘルパーの追加 (`src/cmd/link/internal/ld/decodesym.go`)**:
    *   `decodetype_string(s *LSym) []byte` という新しい関数が追加されました。
    *   この関数は、与えられた `LSym` (リンカシンボル) から、そのシンボルが表す `rtype` 構造体の文字列フィールドの内容を抽出します。
    *   `rtype` 構造体のメモリレイアウトを考慮し、`4*SysArch.PtrSize + 8` というオフセットを計算して、文字列データへのポインタと長さを取得します。このオフセットは、`rtype` 構造体内の `string` フィールドの位置に対応します。
    *   `decode_reloc` を使用してリロケーション情報を解決し、実際の文字列バイトスライスを `r.Sym.P[r.Add : r.Add+strlen]` から読み出します。

これらの変更により、`typelink` シンボル名は短縮され、リンカはシンボル名からではなく、シンボルが指す実際の型情報に基づいてソートを行うことができるようになりました。これにより、バイナリサイズの削減と、よりクリーンなシンボル管理が実現されます。コミットメッセージにあるように、この変更はリンカのソート作業全体の増加には繋がらないとされています。

## コアとなるコードの解説

*   **`src/cmd/compile/internal/gc/reflect.go` の変更**:
    *   `typelinkLSym` 関数は、`go.typelink` シンボルの名前を生成する際に、`Tconv(t, FmtLeft|FmtUnsigned)` と `Tconv(t, FmtLeft)` を連結していた部分を、後者の `Tconv(t, FmtLeft)` のみを使用するように変更しました。これにより、シンボル名から冗長なソート情報が削除され、シンボル名が短縮されます。

*   **`src/cmd/link/internal/ld/data.go` の変更**:
    *   `dataSlice.Less` メソッドは、リンカがシンボルをソートする際の比較ロジックを定義しています。
    *   `strings.HasPrefix(s1.Name, "go.typelink.")` を用いて、比較対象のシンボルが `typelink` シンボルであるかを判定します。
    *   `typelink` シンボルである場合、新しく追加された `decodetype_string` 関数を呼び出し、各シンボルが参照する `rtype` 構造体から実際の型文字列を抽出します。
    *   抽出された2つの型文字列 (`s1n`, `s2n`) を `bytes.Compare` で比較し、その結果をソート順として返します。これにより、シンボル名ではなく、シンボルが指す型情報に基づいてソートが行われるようになります。

*   **`src/cmd/link/internal/ld/decodesym.go` の追加**:
    *   `decodetype_string` 関数は、`LSym` から `rtype` 構造体の文字列フィールドの内容を安全に抽出するためのユーティリティです。
    *   `off := 4*SysArch.PtrSize + 8` は、`rtype` 構造体内の文字列フィールドのオフセットを計算しています。`SysArch.PtrSize` はポインタのサイズ（32bitまたは64bitシステムで異なる）を表し、`rtype` 構造体の先頭から文字列データへのポインタと文字列長が格納されている位置を特定します。
    *   `strlen := int64(decode_inuxi(s.P[off+SysArch.PtrSize:], SysArch.IntSize))` は、文字列の長さを読み取ります。
    *   `r := decode_reloc(s, int32(off))` は、文字列データが別のシンボルにリロケートされている可能性があるため、そのリロケーション情報を取得します。
    *   最終的に `r.Sym.P[r.Add : r.Add+strlen]` を通じて、リロケートされたシンボルのデータから実際の文字列バイトスライスを抽出して返します。

これらの変更により、コンパイラはより短いシンボル名を生成し、リンカはその短いシンボル名から必要な型情報をデコードしてソートを行うという、役割分担が明確化され、効率的な処理が実現されています。

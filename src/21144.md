# [インデックス 21144] ファイルの概要

このコミットは、Goランタイムのロックフリースタック（`lfstack`）の実装において、Power64アーキテクチャ上でのユーザー空間アドレスビット数の取り扱いを修正し、より多くのビットをサポートするように拡張するものです。これにより、Power64環境でのポインタ切り捨ての問題が解消され、`lfstack`の堅牢性が向上しました。

## コミット

このコミットは、Goランタイムの`lfstack`（ロックフリースタック）がPower64アーキテクチャ上でポインタを誤って切り捨てていたバグを修正します。以前は、Power64 Linuxのユーザー空間アドレスが43ビットに制限されているという古い情報に基づいていましたが、実際には46ビットまで拡張されていました。この変更では、アドレスビットの制限を48ビットに引き上げ、将来性を持たせるとともに、ポインタのパッキングとアンパッキングの整合性を検証する自己テストを追加しています。

## 変更の背景

Goランタイムの`lfstack`（ロックフリースタック）は、ポインタとカウンタを単一の`uint64`値にパックして格納する最適化を行っています。これは、アトミック操作を効率的に行うため、特にABA問題の解決に役立ちます。この最適化は、ポインタが使用するアドレスビット数とカウンタが使用するビット数を適切に分割することで実現されます。

Power64アーキテクチャにおいて、Goランタイムは以前、Linuxのユーザー空間アドレスが43ビットに制限されているという2001年の論文に基づく古い仮定を持っていました。この仮定に基づき、`lfstack`はポインタのアドレス情報を43ビットに収まるように設計されていました。しかし、時間の経過とともにPower64 Linuxカーネルの進化により、ユーザー空間アドレスの制限は46ビットに拡張されていました（Linuxカーネルの`TASK_SIZE_USER64`定数に関連）。

この古い仮定が原因で、Goランタイムの`lfstack`は、43ビットを超えるアドレスを持つポインタを扱う際に、ポインタの最上位ビットを切り捨ててしまい、不正なアドレスを参照する可能性がありました。この問題は、特にPower64LE（Little Endian）環境で`all.bash`テストスイートが失敗する原因となっていました。このコミットは、このポインタ切り捨ての問題を解決し、`lfstack`がPower64アーキテクチャ上で正しく機能するようにするために行われました。

## 前提知識の解説

### ロックフリースタック (Lock-Free Stack) と `lfstack`

ロックフリーデータ構造は、ミューテックスなどのロック機構を使用せずに、複数のスレッドが同時にアクセスしても正しく動作するように設計されたデータ構造です。これにより、ロックの競合によるパフォーマンスの低下やデッドロックのリスクを回避できます。

Goランタイムの`lfstack`は、このようなロックフリースタックの一種です。これは、ガベージコレクタ（GC）の補助的なデータ構造や、特定のランタイム内部処理で利用されます。ロックフリースタックの実装には、通常、アトミック操作（例: `CompareAndSwap`）が不可欠です。

### ABA問題

ロックフリーデータ構造、特にスタックやキューのような線形データ構造を実装する際に直面する一般的な問題がABA問題です。これは、あるスレッドがメモリ位置から値Aを読み取り、その後、別のスレッドがそのメモリ位置の値をAからBに変更し、さらにAに戻すという一連の操作を行った場合に発生します。最初のスレッドが再度そのメモリ位置を読み取ると、値がAであるため、変更がなかったと誤解し、不正な操作を行う可能性があります。

`lfstack`のようなロックフリースタックでは、スタックのヘッドポインタを更新する際にABA問題が発生する可能性があります。これを解決するために、ポインタにカウンタ（またはバージョン番号）を付加する「ポインタタグ付け（Pointer Tagging）」という手法がよく用いられます。ポインタとカウンタを組み合わせた値をアトミックに更新することで、値がAに戻ったとしても、カウンタが異なるため、ABA問題を検出して回避できます。

### ポインタタグ付けとアドレスビット/カウンタビットの分割

ポインタタグ付けでは、ポインタのアドレス情報とカウンタ情報を単一のワード（例: `uint64`）にパックします。64ビットシステムでは、通常、ポインタは64ビット幅ですが、実際のユーザー空間アドレスは64ビットすべてを使用するわけではありません。例えば、多くのシステムでは48ビットや57ビットのアドレス空間しか使用しません。この未使用のビット空間をカウンタのために利用します。

`lfstackPack`関数は、`lfnode`ポインタと`cnt`（カウンタ）を`uint64`にパックします。
`lfstackUnpack`関数は、パックされた`uint64`から`lfnode`ポインタと`cnt`を復元します。

このパック/アンパックの処理において、ポインタが使用するアドレスビット数とカウンタが使用するビット数を適切に分割する必要があります。もしポインタが使用するビット数よりも少ないビット数でアドレスを格納しようとすると、ポインタ情報が切り捨てられ、不正なアドレスが生成される原因となります。

### Linuxカーネルのユーザー空間アドレス制限 (`TASK_SIZE_USER64`)

Linuxカーネルは、各アーキテクチャ（x86-64, PowerPC64など）において、ユーザー空間プロセスがアクセスできる仮想メモリ空間の上限を定義しています。これは通常、`TASK_SIZE`または`TASK_SIZE_USER64`といった定数で表現されます。この制限は、カーネルがユーザー空間とカーネル空間を分離するために重要であり、セキュリティやメモリ管理の効率に影響します。

PowerPC64アーキテクチャでは、このユーザー空間アドレスの制限が時間の経過とともに変化してきました。古い情報では43ビットとされていましたが、カーネルの進化により46ビット、さらには64KBページサイズなどの特定の構成では48ビット（4PB）まで拡張されています。Goランタイムは、このカーネルの進化に合わせて、`lfstack`がポインタを正しく扱えるように調整する必要がありました。

## 技術的詳細

このコミットの主要な変更点は、Power64アーキテクチャにおける`lfstack`のポインタパッキングロジックの更新です。

1.  **アドレスビットの仮定の更新**:
    *   以前の`lfstack_linux_power64x.go`では、Power64 Linuxのユーザー空間アドレスが43ビットに制限されているという仮定に基づいていました。これは2001年の論文に基づく古い情報でした。
    *   新しいコードでは、この制限が46ビットに拡張されていることを認識し、さらに将来性を見越して48ビットのアドレスをサポートするように変更されました。これは、AMD64アーキテクチャでのアドレスビット数と一致させる意図もあります。
    *   これに伴い、`lfstackPack`と`lfstackUnpack`関数で使用されるビットシフト量が変更されました。

2.  **新しい定数 `addrBits` と `cntBits` の導入**:
    *   以前は、ビットシフト量がハードコードされていましたが、新しいコミットでは`addrBits`と`cntBits`という定数が導入されました。
    *   `addrBits`はポインタのアドレスが使用するビット数（48ビット）。
    *   `cntBits`はカウンタが使用するビット数。これは`64 - addrBits + 3`として計算されます。ここで`+3`は、ポインタが8バイトアラインメント（3ビット）であることを利用して、下位3ビットをカウンタに利用できることを示しています。
        *   `64 - addrBits`は、アドレスが使用しない上位ビット数。
        *   `+3`は、ポインタアラインメントにより下位3ビットもカウンタに使えるため。
        *   これにより、`cntBits`は`64 - 48 + 3 = 19`ビットとなります。つまり、カウンタは19ビット（`1<<19 - 1`まで）の値を保持できます。

3.  **`lfstackPack` と `lfstackUnpack` のロジック変更**:
    *   `lfstackPack`関数では、`uint64(uintptr(unsafe.Pointer(node))) << (64 - addrBits)`という形で、ポインタのアドレスを上位ビットにシフトして格納します。これにより、アドレスが`addrBits`の範囲で正しく保持されます。
    *   `lfstackUnpack`関数では、`uintptr(val >> cntBits << 3)`という形で、パックされた値からポインタを復元します。`>> cntBits`でカウンタ部分を削除し、`<< 3`でポインタアラインメントによって失われた下位3ビットを復元します。

4.  **自己テストの追加**:
    *   `src/runtime/lfstack.go`の`lfstackpush`関数に、ポインタのパッキングとアンパッキングの整合性を検証する自己テストが追加されました。
    *   `if node1, _ := lfstackUnpack(new); node1 != node`というチェックが追加され、`pack(unpack(x)) == x`が常に成り立つことを保証します。もしこの条件が満たされない場合（つまり、パッキング/アンパッキングで情報が失われた場合）、ランタイムパニック（`gothrow("lfstackpush")`）が発生し、問題が早期に検出されるようになります。これは、将来的にアドレスビットの仮定が再び古くなった場合などに、有用なデバッグ情報を提供します。

これらの変更により、Power64アーキテクチャ上での`lfstack`のポインタ切り捨て問題が解決され、より広いアドレス空間を安全に利用できるようになりました。

## コアとなるコードの解説

### `src/runtime/lfstack.go` の変更

*   **自己テストの追加**:
    `lfstackpush`関数内で、`new := lfstackPack(node, node.pushcnt)`によってポインタとカウンタがパックされた後、すぐに`lfstackUnpack(new)`でアンパックし、元の`node`ポインタと一致するかどうかを検証しています。
    `if node1, _ := lfstackUnpack(new); node1 != node`
    もし一致しない場合、それはパッキング/アンパッキングのロジックに問題があり、ポインタ情報が失われたことを意味します。この場合、詳細なデバッグ情報を出力し、`gothrow("lfstackpush")`を呼び出してランタイムパニックを発生させます。これにより、将来的にアドレス空間の仮定が再び古くなった場合や、他のアーキテクチャで同様の問題が発生した場合に、早期に問題を検出できるようになります。

### `src/runtime/lfstack_linux_power64x.go` の変更

*   **コメントの更新**:
    Power64 Linuxのユーザー空間アドレス制限に関するコメントが更新されました。古い43ビットの仮定が削除され、現在の46ビットの制限と、将来を見越した48ビットのサポートが明記されています。また、`TASK_SIZE_USER64`への言及も追加され、より正確な情報源が示されています。

*   **定数 `addrBits` と `cntBits` の導入**:
    ```go
    const (
    	addrBits = 48
    	cntBits  = 64 - addrBits + 3
    )
    ```
    `addrBits`は、ポインタのアドレスが使用するビット数を48ビットと定義しています。これは、Power64の現在の46ビット制限をカバーし、AMD64との整合性も考慮した将来性のある値です。
    `cntBits`は、カウンタが使用できるビット数を計算しています。`64 - addrBits`は、64ビットワードのうちアドレスが使用しない上位ビット数です。`+ 3`は、ポインタが8バイトアラインメント（つまり、アドレスの下位3ビットが常に0）であることを利用して、これらの3ビットもカウンタとして利用できることを示しています。これにより、カウンタは合計19ビット（`1<<19 - 1`まで）の値を保持できます。

*   **`lfstackPack` 関数の変更**:
    ```go
    func lfstackPack(node *lfnode, cnt uintptr) uint64 {
    	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
    }
    ```
    以前は`<<21`というハードコードされたシフト量を使用していましたが、これは43ビットのアドレスを仮定していました。新しいコードでは、`<<(64-addrBits)`を使用しています。`64-addrBits`は`64-48=16`となり、ポインタのアドレスを16ビット左にシフトして`uint64`の上位に配置します。これにより、ポインタは48ビットのアドレス空間を正しく利用できるようになります。カウンタ部分は`cnt&(1<<cntBits-1)`で、`cntBits`で定義されたビット数にマスクされます。

*   **`lfstackUnpack` 関数の変更**:
    ```go
    func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr) {
    	node = (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
    	cnt = uintptr(val & (1<<cntBits - 1))
    	return
    }
    ```
    以前は`val >> 24 << 3`というハードコードされたシフト量を使用していましたが、これは古いビット分割に基づいています。新しいコードでは、`val >> cntBits << 3`を使用しています。`>> cntBits`でカウンタ部分を削除し、残ったアドレス部分を抽出します。その後、`<< 3`で、ポインタアラインメントによって`lfstackPack`時に利用された下位3ビットを復元し、正しいポインタアドレスを再構築します。カウンタ部分は`val & (1<<cntBits - 1)`で、パックされた値の下位`cntBits`をマスクして抽出します。

これらの変更により、Power64アーキテクチャにおける`lfstack`のポインタパッキングとアンパッキングのロジックが、現在のLinuxカーネルのユーザー空間アドレス制限と将来の拡張に対応できるようになり、ポインタの切り捨て問題が根本的に解決されました。

# [インデックス 21345] ファイルの概要

このコミットは、Goランタイムがglibcの内部シグナルハンドラ（特に`SIGSETXID`と`SIGCANCEL`）を、Goのスタックオーバーフローを防ぐために、代替シグナルスタック上で実行されるように修正するものです。

## コミット

```
commit 675eb72c285cd0dd44a5f280bb3fa456ddf6de16
Author: Austin Clements <austin@google.com>
Date:   Fri Dec 19 16:16:17 2014 -0500

    runtime: run libc SIGSETXID and SIGCANCEL handlers on signal stack
    
    These signals are used by glibc to broadcast setuid/setgid to all
    threads and to send pthread cancellations.  Unlike other signals, the
    Go runtime does not intercept these because they must invoke the libc
    handlers (see issues #3871 and #6997).  However, because 1) these
    signals may be issued asynchronously by a thread running C code to
    another thread running Go code and 2) glibc does not set SA_ONSTACK
    for its handlers, glibc's signal handler may be run on a Go stack.
    Signal frames range from 1.5K on amd64 to many kilobytes on ppc64, so
    this may overflow the Go stack and corrupt heap (or other stack) data.
    
    Fix this by ensuring that these signal handlers have the SA_ONSTACK
    flag (but not otherwise taking over the handler).
    
    This has been a problem since Go 1.1, but it's likely that people
    haven't encountered it because it only affects setuid/setgid and
    pthread_cancel.
    
    Fixes #9600.
    
    Change-Id: I6cf5f5c2d3aa48998d632f61f1ddc2778dcfd300
    Reviewed-on: https://go-review.googlesource.com/1887
    Reviewed-by: Ian Lance Taylor <iant@golang.org>
```

## 元コミット内容

Goランタイムは、`SIGSETXID`と`SIGCANCEL`というglibcが使用するシグナルハンドラを、シグナルスタック上で実行するように変更します。これらのシグナルは、それぞれ`setuid`/`setgid`のブロードキャストと`pthread_cancel`のためにglibcによって使用されます。Goランタイムはこれらのシグナルをインターセプトせず、glibcのハンドラを呼び出す必要があります（Issue #3871と#6997を参照）。しかし、これらのシグナルがCコードを実行しているスレッドからGoコードを実行している別のスレッドに非同期に発行される可能性があり、かつglibcがそのハンドラに対して`SA_ONSTACK`フラグを設定しないため、glibcのシグナルハンドラがGoのスタック上で実行される可能性がありました。シグナルフレームはamd64で1.5KB、ppc64では数KBにもなるため、これがGoのスタックをオーバーフローさせ、ヒープや他のスタックデータを破壊する可能性がありました。このコミットは、これらのシグナルハンドラに`SA_ONSTACK`フラグが設定されるようにすることで、この問題を修正します。この問題はGo 1.1から存在していましたが、`setuid`/`setgid`や`pthread_cancel`にしか影響しないため、あまり表面化していませんでした。このコミットはIssue #9600を修正します。

## 変更の背景

Goランタイムは、独自の軽量なゴルーチンスタック管理システムを持っています。一方、LinuxなどのUnix系システムでは、シグナルハンドラは通常、シグナルが配送された時点のスレッドのスタック上で実行されます。glibc（GNU C Library）は、C言語で書かれたアプリケーションがシステムコールやライブラリ関数を呼び出す際に利用される標準ライブラリであり、内部的に特定のシグナルを使用してスレッド間の通信や状態変更をブロードキャストすることがあります。

このコミットが対処している問題は、GoプログラムがCgo（C言語との相互運用機能）を介してCコードと連携する際に発生する可能性がありました。具体的には、glibcが内部的に使用する`SIGSETXID`と`SIGCANCEL`という2つのシグナルが関係しています。

*   **`SIGSETXID`**: このシグナルは、glibcが`setuid()`や`setgid()`といった特権変更操作を、プロセス内の他のスレッドにブロードキャストするために使用するとされています。これにより、プロセス内のすべてのスレッドが新しいユーザーIDやグループIDを認識し、適切な権限で動作できるようになります。
*   **`SIGCANCEL`**: このシグナルは、glibcがPOSIXスレッドのキャンセル（`pthread_cancel()`）を実装するために内部的に使用するものです。あるスレッドが別のスレッドの実行をキャンセルしようとした際に、ターゲットスレッドにこのシグナルが送られ、キャンセル処理がトリガーされます。

Goランタイムは、これらのglibc内部シグナルを直接インターセプトせず、glibc自身のハンドラが実行されることを許可しています。これは、これらのシグナルがglibcの内部状態管理に不可欠であり、Goランタイムがそれらを横取りすると、glibcの機能が正しく動作しなくなるためです（コミットメッセージで参照されているIssue #3871と#6997がこの背景にあると考えられます）。

しかし、問題はglibcのシグナルハンドラが`SA_ONSTACK`フラグを設定せずに登録されている点にありました。`SA_ONSTACK`フラグが設定されていない場合、シグナルハンドラはシグナルが配送された時点のスレッドの現在のスタック上で実行されます。Goのゴルーチンスタックは非常に小さく（初期サイズは数KB）、必要に応じて動的に拡張されますが、シグナルハンドラが要求するスタックサイズは、特に`ppc64`のようなアーキテクチャでは数KBにも達することがあります。

もしglibcのシグナルハンドラが、Goの小さなゴルーチンスタック上で実行された場合、スタックオーバーフローが発生する可能性がありました。スタックオーバーフローは、スタック領域が不足し、隣接するメモリ領域（ヒープや他のスタック）を上書きしてしまう深刻な問題です。これにより、プログラムのクラッシュ、データの破損、予期せぬ動作など、様々な問題が引き起こされる可能性があります。

このコミットは、この潜在的なスタックオーバーフローとそれに伴うデータ破損のリスクを解消するために導入されました。

## 前提知識の解説

### 1. シグナルとシグナルハンドラ

Unix系OSにおいて、シグナルはプロセスに対して非同期にイベントを通知するメカニズムです。例えば、Ctrl+Cを押すと`SIGINT`シグナルが、不正なメモリアクセスがあると`SIGSEGV`シグナルがプロセスに送られます。プロセスは、特定のシグナルを受信した際に実行する関数（シグナルハンドラ）を登録できます。

### 2. `sigaction()`と`SA_ONSTACK`フラグ

`sigaction()`は、シグナルハンドラを設定するためのシステムコールです。この関数は、シグナルハンドラのアドレスだけでなく、シグナルの動作を制御するための様々なフラグを含む`sigaction`構造体を受け取ります。

`SA_ONSTACK`フラグは、`sigaction`構造体の`sa_flags`フィールドに設定できる重要なフラグの一つです。このフラグが設定されている場合、シグナルハンドラは、プロセスが事前に設定した代替シグナルスタック（alternate signal stack）上で実行されます。

*   **代替シグナルスタックの必要性**: 通常、シグナルハンドラはシグナルが配送された時点のプロセスの現在のスタック上で実行されます。しかし、もしシグナルがスタックオーバーフローなどのスタック関連の問題によって発生した場合、またはシグナルハンドラ自体が大量のスタック空間を必要とする場合、現在のスタックが破損しているか、または不足している可能性があります。このような状況でシグナルハンドラが現在のスタック上で実行されると、さらなるクラッシュや未定義の動作を引き起こす可能性があります。
*   **`sigaltstack()`**: 代替シグナルスタックは、`sigaltstack()`システムコールを使って事前に設定されます。これにより、OSはシグナルハンドラのために安全で独立したスタック領域を確保できます。

### 3. Goランタイムのスタック管理

Go言語のゴルーチンは、非常に軽量な並行処理の単位であり、それぞれが独自のスタックを持っています。Goランタイムは、これらのゴルーチンスタックを効率的に管理し、必要に応じて動的に拡張・縮小します。初期のゴルーチンスタックは比較的小さく、これは数百万のゴルーチンを同時に実行できるようにするための設計上の選択です。

### 4. Cgoとglibc

Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cgoを使用すると、GoとCのコードが同じプロセス空間内で共存し、相互に呼び出しを行うことができます。この際、Cコードがglibcのような標準Cライブラリの関数を呼び出すと、glibcの内部的な動作がGoランタイムの挙動に影響を与える可能性があります。

### 5. `setuid`/`setgid`と`pthread_cancel`

*   **`setuid`/`setgid`**: これらはUnix系OSにおけるシステムコールで、プロセスの実効ユーザーID（UID）や実効グループID（GID）を変更するために使用されます。これにより、プログラムは一時的に異なるユーザーやグループの権限で動作できます。セキュリティ上重要な操作です。
*   **`pthread_cancel()`**: POSIXスレッド（pthreads）ライブラリの関数で、別のスレッドの実行をキャンセル（終了）する要求を送信します。ターゲットスレッドは、キャンセルポイントに到達した際に終了します。

### 6. 関連するGoのIssue (コミットメッセージより)

*   **Issue #3871**: 詳細不明ですが、コミットメッセージの文脈から、Goランタイムが特定のglibcシグナルをインターセプトしない理由、つまりglibcのハンドラに処理を委ねる必要があることに関連していると考えられます。
*   **Issue #6997**: 同様に詳細不明ですが、`SIGCANCEL`シグナルとGoランタイムの相互作用、特にglibcの`pthread_cancel`ハンドラを尊重する必要性に関連していると推測されます。
*   **Issue #9600**: このコミットが直接修正する問題です。具体的な内容は不明ですが、glibcのシグナルハンドラがGoスタック上で実行されることによるスタックオーバーフローとデータ破損の問題を指していると考えられます。

## 技術的詳細

このコミットの技術的な解決策は、Goランタイムが特定のglibcシグナル（`SIGSETXID`と`SIGCANCEL`）のハンドラに対して、`SA_ONSTACK`フラグを明示的に設定することです。

Goランタイムは、システム起動時にシグナルハンドラを初期化する`initsig()`関数を持っています。この関数は、Goが処理すべきシグナルと、glibcに任せるべきシグナルを区別しています。`SIGSETXID`と`SIGCANCEL`は、Goが直接処理しないシグナルとして認識されており、そのハンドラはglibcによって管理されます。

このコミットでは、`src/runtime/signal_linux.go`の`sigtable`に、`SIGCANCEL`（シグナル32）と`SIGSETXID`（シグナル33）に対して新しいフラグ`_SigSetStack`を追加しています。

```go
// src/runtime/signal_linux.go
var sigtable = [...]sigTabT{
	// ...
	/* 32 */ {_SigSetStack, "signal 32"}, /* SIGCANCEL; see issue 6997 */
	/* 33 */ {_SigSetStack, "signal 33"}, /* SIGSETXID; see issue 3871, 9400 */
	// ...
}
```

そして、`src/runtime/runtime2.go`で`_SigSetStack`という新しい定数を定義しています。

```go
// src/runtime/runtime2.go
const (
	// ...
	_SigSetStack = 1 << 8 // add SA_ONSTACK to libc handler
)
```

`src/runtime/signal1_unix.go`の`initsig()`関数内で、この`_SigSetStack`フラグがチェックされるようになりました。

```go
// src/runtime/signal1_unix.go
func initsig() {
	for i := int32(0); i < _NSIG; i++ {
		t := &sigtable[i]
		// ...
		if t.flags&_SigSetStack != 0 {
			setsigstack(i)
			continue
		}
		// ...
	}
}
```

もしシグナルのフラグに`_SigSetStack`が含まれていれば、`setsigstack(i)`関数が呼び出されます。

`setsigstack()`関数（`src/runtime/os1_linux.go`に実装）は、指定されたシグナル番号`i`に対して、現在のシグナルハンドラの設定を取得し、もしそのハンドラがデフォルト動作（`_SIG_DFL`）でも無視（`_SIG_IGN`）でもなく、かつ`SA_ONSTACK`フラグが設定されていない場合に、`SA_ONSTACK`フラグを追加してシグナルハンドラを再設定します。

```go
// src/runtime/os1_linux.go
func setsigstack(i int32) {
	var sa sigactiont
	// 現在のシグナルハンドラ設定を取得
	if rt_sigaction(uintptr(i), nil, &sa, unsafe.Sizeof(sa.sa_mask)) != 0 {
		gothrow("rt_sigaction failure")
	}
	// ハンドラがデフォルトでも無視でもなく、SA_ONSTACKが設定されていない場合のみ処理
	if sa.sa_handler == 0 || sa.sa_handler == _SIG_DFL || sa.sa_handler == _SIG_IGN || sa.sa_flags&_SA_ONSTACK != 0 {
		return
	}
	// SA_ONSTACKフラグを追加
	sa.sa_flags |= _SA_ONSTACK
	// シグナルハンドラを再設定
	if rt_sigaction(uintptr(i), &sa, nil, unsafe.Sizeof(sa.sa_mask)) != 0 {
		gothrow("rt_sigaction failure")
	}
}
```

これにより、glibcの`SIGSETXID`および`SIGCANCEL`ハンドラが、Goのゴルーチンスタックではなく、代替シグナルスタック上で実行されることが保証されます。これにより、Goの小さなスタックがこれらのシグナルハンドラの実行によってオーバーフローするリスクが排除され、Goプログラムの安定性と堅牢性が向上します。

また、このコミットには、`issue9400`という新しいテストケースが追加されています。このテストは、意図的にGoのスタックを巻き戻し（スタックポインタを一時的に大きく進めることで、スタックの末尾に近い領域を「使用済み」にする）、その状態で`setgid(0)`を呼び出して`SIGSETXID`シグナルをトリガーし、シグナルハンドラがGoのスタックを破壊しないことを検証します。テストでは、スタックに特定のパターンを書き込み、シグナルハンドラ実行後にそのパターンが破壊されていないことを確認することで、スタックオーバーフローが発生していないことを保証しています。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

```go
const (
	// ...
	_SigSetStack = 1 << 8 // add SA_ONSTACK to libc handler
)
```
`_SigSetStack`は、シグナルハンドラが代替シグナルスタック上で実行されるべきであることを示す新しいビットフラグです。これは、`sigaction`システムコールに渡される`sa_flags`の一部として使用されます。

### `src/runtime/signal_linux.go`

```go
var sigtable = [...]sigTabT{
	// ...
	/* 32 */ {_SigSetStack, "signal 32"}, /* SIGCANCEL; see issue 6997 */
	/* 33 */ {_SigSetStack, "signal 33"}, /* SIGSETXID; see issue 3871, 9400 */
	// ...
}
```
`sigtable`は、Goランタイムが認識する各シグナルの特性を定義するテーブルです。ここで、シグナル32（`SIGCANCEL`）とシグナル33（`SIGSETXID`）に対して`_SigSetStack`フラグが設定されています。これにより、Goランタイムはこれらのシグナルが特別なスタック処理を必要とすることを認識します。

### `src/runtime/signal1_unix.go`

```go
func initsig() {
	for i := int32(0); i < _NSIG; i++ {
		t := &sigtable[i]
		// ...
		if t.flags&_SigSetStack != 0 {
			setsigstack(i)
			continue
		}
		// ...
	}
}
```
`initsig()`は、Goランタイムが起動時にシグナルハンドラを初期化する主要な関数です。この変更により、各シグナルについて`sigtable`のフラグをチェックし、もし`_SigSetStack`フラグが設定されていれば、そのシグナルに対して`setsigstack()`関数を呼び出すようになりました。これにより、特定のシグナルハンドラが代替スタック上で実行されるように設定されます。

### `src/runtime/os1_linux.go`

```go
func setsigstack(i int32) {
	var sa sigactiont
	// 既存のシグナルハンドラ設定を取得
	if rt_sigaction(uintptr(i), nil, &sa, unsafe.Sizeof(sa.sa_mask)) != 0 {
		gothrow("rt_sigaction failure")
	}
	// ハンドラがデフォルト、無視、または既にSA_ONSTACKが設定されている場合は何もしない
	if sa.sa_handler == 0 || sa.sa_handler == _SIG_DFL || sa.sa_handler == _SIG_IGN || sa.sa_flags&_SA_ONSTACK != 0 {
		return
	}
	// SA_ONSTACKフラグを設定
	sa.sa_flags |= _SA_ONSTACK
	// 更新された設定でシグナルハンドラを再設定
	if rt_sigaction(uintptr(i), &sa, nil, unsafe.Sizeof(sa.sa_mask)) != 0 {
		gothrow("rt_sigaction failure")
	}
}
```
この関数は、Linux固有のシグナル処理ロジックをカプセル化しています。`rt_sigaction`システムコールを使用して、指定されたシグナルの現在のハンドラ設定を読み取ります。もしハンドラが有効で、かつまだ`SA_ONSTACK`フラグが設定されていない場合、このフラグを追加し、その新しい設定でハンドラを再登録します。これにより、glibcのハンドラがGoのスタックではなく、安全な代替シグナルスタック上で実行されるようになります。

### `misc/cgo/test/issue9400_linux.go`

```go
func test9400(t *testing.T) {
	// ...
	// Grow the stack and put down a test pattern
	const pattern = 0x123456789abcdef
	var big [1024]uint64 // len must match assmebly
	for i := range big {
		big[i] = pattern
	}

	// Temporarily rewind the stack and trigger SIGSETXID
	issue9400.RewindAndSetgid()

	// Check test pattern
	for i := range big {
		if big[i] != pattern {
			t.Fatalf("entry %d of test pattern is wrong; %#x != %#x", i, big[i], pattern)
		}
	}
}
```
このテストは、修正の有効性を検証するために非常に重要です。`big`配列を使ってGoのスタックを意図的に大きく消費させ、その領域に特定のパターンを書き込みます。次に、アセンブリコードで実装された`RewindAndSetgid()`を呼び出します。この関数は、スタックポインタを一時的に巻き戻し（スタックの「使用済み」領域を増やすことで、スタックオーバーフローを誘発しやすくする）、その後`setgid(0)`を呼び出して`SIGSETXID`シグナルをトリガーします。シグナルハンドラが実行された後、`big`配列のパターンが変更されていないことを確認することで、シグナルハンドラがGoのスタックを破壊しなかったことを検証します。

## 元コミット内容

Goランタイムにおいて、`Sigaltstack`という名前の型が、同名のシステムコールまたはライブラリ関数である`sigaltstack`と名前の衝突を起こしていました。このコミットは、型の名前を`SigaltstackT`に変更することで、この衝突を解消することを目的としています。

## 変更の背景

Go言語のランタイムは、オペレーティングシステム（OS）の低レベルな機能と密接に連携して動作します。特に、シグナルハンドリングは、プログラムの堅牢性と安定性を確保するために非常に重要です。Goランタイムは、シグナルハンドラが実行される際に、通常のゴルーチンのスタックとは異なる代替スタック（alternate signal stack）を使用するように設定します。これは、ゴルーチンのスタックサイズが限られているため、シグナル発生時にスタックオーバーフローを防ぐための重要なメカニズムです。

この代替スタックの設定には、POSIX標準で定義されている`sigaltstack`というシステムコールが使用されます。このシステムコールは、代替シグナルスタックの情報を設定・取得するための関数です。

Goランタイムの内部では、この`sigaltstack`システムコールに関連するデータ構造を表現するために、`Sigaltstack`という名前の型が定義されていました。しかし、C言語のヘッダファイルやOSのAPI定義において、既に`sigaltstack`という名前の関数が存在するため、Goの内部で定義された型名とOSの関数名が衝突する可能性がありました。このような名前の衝突は、特にCGO（GoとC言語の相互運用機能）を使用する場合や、GoランタイムがOSのネイティブAPIを直接呼び出す際に、コンパイルエラーや予期せぬ動作を引き起こす原因となります。

このコミットは、このような名前の衝突を明示的に回避し、コードの可読性と保守性を向上させるために、型の名前をより明確な`SigaltstackT`（`T`はTypeを意味すると考えられる）に変更しました。

## 前提知識の解説

### シグナルとシグナルハンドリング

シグナルは、UNIX系OSにおいてプロセスに非同期的にイベントを通知するメカニズムです。例えば、Ctrl+Cを押すと`SIGINT`シグナルが、無効なメモリアドレスにアクセスすると`SIGSEGV`（セグメンテーション違反）シグナルがプロセスに送信されます。プロセスはこれらのシグナルを受け取ると、デフォルトの動作（例えば、プロセス終了）を実行するか、事前に登録されたシグナルハンドラ関数を実行します。

### 代替シグナルスタック（Alternate Signal Stack）

シグナルハンドラは、シグナルが発生した時点のプロセスの状態（スタックを含む）に依存せずに安全に実行される必要があります。特に、スタックオーバーフローなどの問題でシグナルが発生した場合、通常のスタックではシグナルハンドラ自体が実行できない可能性があります。これを避けるため、OSは代替シグナルスタックという仕組みを提供しています。

`sigaltstack`システムコールは、この代替シグナルスタックを設定するために使用されます。シグナルハンドラが`SA_ONSTACK`フラグ付きで登録されている場合、シグナル発生時にOSは自動的にこの代替スタックに切り替えてハンドラを実行します。これにより、シグナルハンドラは安全かつ独立した環境で動作できます。

### `struct sigaltstack`

`sigaltstack`システムコールは、通常、`stack_t`または`struct sigaltstack`という構造体を使用して、代替スタックのアドレス、サイズ、および状態（有効/無効など）を定義します。この構造体はOSによって定義されており、GoランタイムがOSのAPIと連携する際には、この構造体の定義をGoの型にマッピングする必要があります。

### CGOとGoランタイムの相互運用

Go言語はCGOを通じてC言語のコードと相互運用できます。Goランタイムは、C言語のライブラリやシステムコールを直接呼び出す際に、OSのAPI定義とGoの内部表現との間で整合性を保つ必要があります。名前の衝突は、このような相互運用において特に問題となりやすい点です。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがOSの低レベルな構造体や関数をGoのコード内でどのように表現し、管理しているかという点にあります。

Goランタイムは、各OSおよびアーキテクチャ（例: Linux/amd64, FreeBSD/386, Solaris/amd64など）に特化した定義ファイル（`defs*.go`および`defs*.h`）を持っています。これらのファイルは、C言語の構造体や定数をGoの型や定数にマッピングするために使用されます。

元のコードでは、`C.struct_sigaltstack`というC言語の構造体をGoの`Sigaltstack`という型にエイリアスしていました。

```go
type Sigaltstack C.struct_sigaltstack
```

しかし、OSのAPIには`sigaltstack`という名前の関数が存在するため、Goのコード内で`Sigaltstack`という型名を使用すると、コンパイラが型と関数のどちらを参照すべきか判断できなくなり、名前の衝突が発生していました。

このコミットでは、この型の名前を`SigaltstackT`に変更することで、この曖昧さを解消しました。

```go
type SigaltstackT C.struct_sigaltstack
```

これにより、Goのコードは`SigaltstackT`という型名を使用して代替シグナルスタックの構造体を明確に参照できるようになり、OSの`sigaltstack`関数との名前の衝突がなくなりました。

この変更は、GoランタイムがサポートするすべてのOSおよびアーキテクチャの定義ファイルにわたって一貫して適用されています。これは、Goがクロスプラットフォーム対応を重視しており、各プラットフォームの特性を吸収しつつ、共通のランタイムロジックを維持していることを示しています。

## コアとなるコードの解説

上記の変更箇所は、GoランタイムがOSのシグナルスタック管理機能とどのように連携しているかを示しています。

-   **`type Sigaltstack C.struct_sigaltstack` から `type SigaltstackT C.struct_sigaltstack` への変更**:
    これは、Goの型定義における名前の衝突を直接的に解決するものです。`C.struct_sigaltstack`は、C言語のヘッダファイルで定義されている`struct sigaltstack`構造体をGoのコードから参照するためのCGOの構文です。この構造体は、代替シグナルスタックのポインタ（`ss_sp`）、サイズ（`ss_size`）、およびフラグ（`ss_flags`）を保持します。Goランタイムは、この構造体を使ってOSに代替スタックの情報を渡したり、OSから情報を取得したりします。型名を変更することで、GoのコンパイラがOSの`sigaltstack`関数とGoの`SigaltstackT`型を明確に区別できるようになります。

-   **`typedef struct Sigaltstack Sigaltstack;` から `typedef struct SigaltstackT SigaltstackT;` および `struct Sigaltstack { ... }` から `struct SigaltstackT { ... }` への変更 (Cヘッダファイル)**:
    Goランタイムは、CGOを介してC言語のコードを生成する際に、これらのCヘッダファイルを使用します。Cヘッダファイル内でも、Goの型名に合わせて構造体の名前や`typedef`名を変更することで、CGOが生成するコードとGoのコードとの間の整合性を保ち、コンパイル時のエラーを防ぎます。これは、GoランタイムがC言語のコードと密接に連携していることの証拠であり、両者の間のインターフェースが厳密に管理されていることを示しています。

-   **`Sigaltstack st;` から `SigaltstackT st;` への変更 (OS固有のCファイル)**:
    これは、GoランタイムのC言語で書かれた部分（例えば、`os_linux.c`）で、実際に`sigaltstack`システムコールを呼び出す際に使用されるローカル変数の型も変更されたことを示しています。これにより、Goの型定義の変更がC言語のコードにも適切に反映され、ランタイム全体での一貫性が保たれます。

この変更は、機能的な振る舞いを変更するものではなく、主にコードの健全性、可読性、およびコンパイル時の名前解決の明確化を目的としています。Goランタイムのような低レベルなシステムプログラミングにおいては、このような名前の衝突はデバッグが困難な問題を引き起こす可能性があるため、早期に解決することが重要です。

## 元コミット内容

このコミットは、Goコンパイラが大規模な文字列 `switch` ステートメントを処理する際のパフォーマンスを向上させることを目的としています。具体的には、定数文字列の長いリストに対する `switch` ステートメントが二分探索（バイナリサーチ）を使用する際に、文字列の比較コストが高いという問題に対処しています。解決策として、文字列の比較を「まず長さを比較し、次に文字列自体を比較する」という二段階のアプローチに変更することで、全体的な比較コストを削減し、パフォーマンスを大幅に改善しています。

## 変更の背景

Go言語のコンパイラは、定数式が多数存在する `switch` ステートメントに対して、効率的なコードを生成するために二分探索アルゴリズムを適用します。これは、特に多くの `case` 句を持つ `switch` ステートメントにおいて、線形探索よりも高速に目的の `case` に到達できるため、一般的な最適化手法です。

しかし、文字列を比較する場合、整数などのプリミティブ型と比較して、そのコストは格段に高くなります。文字列の比較は、文字ごとに順次比較を行う必要があり、文字列が長くなるほど、また共通のプレフィックスが長くなるほど、比較に要する時間が増大します。

このコミットの背景には、大規模な文字列 `switch` ステートメントがアプリケーションのパフォーマンスボトルネックとなるケースが存在したことが考えられます。コミットメッセージに記載されているベンチマーク結果は、この最適化が特に `BenchmarkSwitch` シリーズにおいて、最大で55%以上の実行時間短縮をもたらしていることを示しており、この問題の重要性を裏付けています。`Fixes #10000` と記載されていることから、GoのIssueトラッカーにこのパフォーマンス問題が報告され、その解決のためにこの変更が導入されたと推測されます（ただし、Web検索では該当するIssueの直接的な内容は確認できませんでした）。

## 前提知識の解説

### Go言語の `switch` ステートメント

Go言語の `switch` ステートメントは、他の言語と同様に、与えられた式と複数の `case` 句の値を比較し、一致する `case` のコードブロックを実行します。Goの `switch` は非常に柔軟で、式を省略して `switch true` のように振る舞わせることもできます。

### コンパイラによる `switch` の最適化

コンパイラは、`switch` ステートメントを効率的に実行するために様々な最適化を行います。
*   **線形探索**: `case` 句の数が少ない場合（通常は3つ以下）、コンパイラは単純な `if-else if-else` の連鎖に変換し、線形に比較を行います。
*   **二分探索 (Binary Search)**: `case` 句の数が多い場合、特に定数値を比較する `switch` では、コンパイラは二分探索ツリーのような構造を生成することがあります。これにより、比較回数を大幅に減らし、高速な分岐を実現します。例えば、100個の `case` がある場合、線形探索では最大100回の比較が必要ですが、二分探索では最大7回程度の比較で済みます。
*   **ジャンプテーブル**: 連続した整数値の `case` 句の場合、コンパイラはジャンプテーブルを生成することがあります。これは、式の値に基づいて直接対応するコードブロックにジャンプする非常に高速なメカニズムです。

### 文字列の比較コスト

文字列の比較は、その内部表現と長さによってコストが変動します。Goでは文字列は不変のバイトスライスとして扱われます。2つの文字列を比較する際、Goランタイムはまずそれらの長さが等しいかを確認し、次に各バイトを順に比較していきます。このプロセスは、文字列が長くなるほど、また最初の不一致が見つかるまでの共通プレフィックスが長くなるほど、CPUサイクルを多く消費します。

## 技術的詳細

このコミットの核心は、Goコンパイラが文字列 `switch` ステートメントの二分探索を構築する際に使用する比較ロジックを最適化することです。

従来の二分探索では、文字列の比較に直接 `OLE` (Less Than or Equal) 演算子を使用していました。これは、文字列の辞書順比較を意味し、前述の通りコストが高い操作です。

新しいアプローチでは、文字列の比較を以下の二段階で行います。

1.  **文字列の長さを比較**: まず、比較対象の文字列の長さを比較します。長さの比較は、整数の比較であるため、非常に高速です。
    *   もし `s.exprname` (比較対象の文字列) の長さが `mid` (二分探索の中間点にある文字列) の長さより小さい場合、`s.exprname` は `mid` より小さいと判断されます。
    *   もし `s.exprname` の長さが `mid` の長さより大きい場合、`s.exprname` は `mid` より大きいと判断されます。
2.  **文字列の値を比較**: 長さが等しい場合にのみ、文字列自体の辞書順比較を行います。

この最適化の理由は以下の通りです。

*   **早期終了**: 多くのケースで、文字列の長さが異なるだけで比較結果が確定します。これにより、コストの高い文字列値の比較を回避できます。
*   **一貫性のあるソート順**: `exprcmp` 関数（`case` 句のソートに使用される）と `exprSwitch.walkCases` 関数（二分探索ツリーの構築に使用される）の両方で、この「長さ優先、次に値」というソート順を適用することで、二分探索のロジックと `case` 句の順序に一貫性を持たせています。これにより、正しい `case` への分岐が保証されます。

この変更により、特に多数の `case` 句を持つ文字列 `switch` ステートメントにおいて、二分探索の各ステップでの比較コストが大幅に削減され、結果として全体の実行速度が向上します。ベンチマーク結果が示すように、`BenchmarkSwitch` のパフォーマンスが劇的に改善されているのはこのためです。

## コアとなるコードの変更箇所

変更は `src/cmd/internal/gc/swt.go` ファイルに集中しています。

1.  **`func (s *exprSwitch) walkCases(cc []*caseClause) *Node` 内の変更**:
    `switch` ステートメントの二分探索ツリーを構築する `walkCases` 関数において、`a.Ntest` (条件ノード) の生成ロジックが変更されています。

    ```diff
    --- a/src/cmd/internal/gc/swt.go
    +++ b/src/cmd/internal/gc/swt.go
    @@ -314,7 +314,16 @@ func (s *exprSwitch) walkCases(cc []*caseClause) *Node {\n    // find the middle and recur\n    half := len(cc) / 2\n    a := Nod(OIF, nil, nil)\n-   a.Ntest = Nod(OLE, s.exprname, cc[half-1].node.Left)\n+   mid := cc[half-1].node.Left\n+   le := Nod(OLE, s.exprname, mid)\n+   if Isconst(mid, CTSTR) {\n+       // Search by length and then by value; see exprcmp.\n+       lenlt := Nod(OLT, Nod(OLEN, s.exprname, nil), Nod(OLEN, mid, nil))\n+       leneq := Nod(OEQ, Nod(OLEN, s.exprname, nil), Nod(OLEN, mid, nil))\n+       a.Ntest = Nod(OOROR, lenlt, Nod(OANDAND, leneq, le))\n+   } else {\n+       a.Ntest = le\n+   }\n    typecheck(&a.Ntest, Erv)\n    a.Nbody = list1(s.walkCases(cc[:half]))\n    a.Nelse = list1(s.walkCases(cc[half:]))\
    ```
    *   `Isconst(mid, CTSTR)` で、中間点の `case` が文字列定数であるかを確認します。
    *   文字列定数である場合、`a.Ntest` は `(len(s.exprname) < len(mid)) || (len(s.exprname) == len(mid) && s.exprname <= mid)` という論理式に変換されます。
        *   `lenlt`: `s.exprname` の長さが `mid` の長さより小さいか (`OLT` - Less Than)。
        *   `leneq`: `s.exprname` の長さが `mid` の長さと等しいか (`OEQ` - Equal)。
        *   `le`: `s.exprname` が `mid` 以下か (`OLE` - Less Than or Equal)。
        *   `OOROR` (OR) と `OANDAND` (AND) を用いて、長さによる比較を優先し、長さが等しい場合にのみ値による比較を行う複合条件を構築しています。
    *   文字列定数でない場合は、従来の `OLE` 比較がそのまま使用されます。

2.  **`func exprcmp(c1, c2 *caseClause) int` 内の変更**:
    `case` 句をソートするために使用される `exprcmp` 関数において、文字列の比較ロジックが変更されています。

    ```diff
    --- a/src/cmd/internal/gc/swt.go
    +++ b/src/cmd/internal/gc/swt.go
    @@ -750,7 +759,19 @@ func exprcmp(c1, c2 *caseClause) int {\n    case CTINT, CTRUNE:\n        return Mpcmpfixfix(n1.Val.U.Xval, n2.Val.U.Xval)\n    case CTSTR:\n-\t\treturn cmpslit(n1, n2)\n+\t\t// Sort strings by length and then by value.\n+\t\t// It is much cheaper to compare lengths than values,\n+\t\t// and all we need here is consistency.\n+\t\t// We respect this sorting in exprSwitch.walkCases.\n+\t\ta := n1.Val.U.Sval\n+\t\tb := n2.Val.U.Sval\n+\t\tif len(a) < len(b) {\n+\t\t\treturn -1\n+\t\t}\n+\t\tif len(a) > len(b) {\n+\t\t\treturn +1\n+\t\t}\n+\t\treturn stringsCompare(a, b)\n    }\n    \n    return 0\
    ```

    *   `CTSTR` (文字列定数) の `case` において、`cmpslit(n1, n2)` の直接呼び出しから、長さによる比較を優先するロジックに変更されています。

    *   長さが等しい場合にのみ、`stringsCompare(a, b)` を呼び出して文字列の辞書順比較を行います。

## コアとなるコードの解説

このコミットは、Goコンパイラのバックエンドの一部である `cmd/internal/gc` パッケージ内の `swt.go` ファイルを修正しています。このファイルは、`switch` ステートメントの最適化、特に定数式を伴う `switch` ステートメントのコード生成を担当しています。

### `exprSwitch.walkCases` の変更

`exprSwitch.walkCases` 関数は、`switch` ステートメントの `case` 句のリストを受け取り、それらを効率的に評価するための抽象構文木 (AST) ノードを生成します。大規模な定数 `switch` の場合、この関数は二分探索ツリーを構築します。

変更前は、文字列の比較に単純な `OLE` (Less Than or Equal) 演算子を使用していました。これは、Goの文字列比較のセマンティクスに従い、辞書順で比較を行います。しかし、この比較は文字列の長さに比例してコストがかかります。

変更後は、`mid` (二分探索の中間点にある `case` の値) が文字列定数である場合に、比較ロジックを最適化しています。
`a.Ntest = Nod(OOROR, lenlt, Nod(OANDAND, leneq, le))`
この行は、以下のような論理式をASTとして表現しています。
`if (len(s.exprname) < len(mid)) || (len(s.exprname) == len(mid) && s.exprname <= mid)`

これは、比較対象の文字列 `s.exprname` が `mid` よりも小さいかどうかを判断する際に、まず長さを比較し、長さが等しい場合にのみ文字列の内容を比較するという戦略をコンパイラに指示します。これにより、多くの比較で高コストな文字列内容の比較をスキップできるようになります。

### `exprcmp` の変更

`exprcmp` 関数は、`case` 句の値を比較し、それらをソートするために使用されます。このソート順は、`walkCases` 関数が二分探索ツリーを正しく構築するために非常に重要です。二分探索は、ソートされたデータに対してのみ正しく機能するためです。

変更前は、文字列の比較に `cmpslit` 関数を使用していました。これもまた、標準的な辞書順比較を行います。

変更後は、`exprcmp` 関数も `walkCases` と同様に「長さ優先、次に値」の比較ロジックを採用しています。
1.  `len(a) < len(b)` であれば `-1` を返す（`a` が `b` より小さい）。
2.  `len(a) > len(b)` であれば `+1` を返す（`a` が `b` より大きい）。
3.  長さが等しい場合のみ `stringsCompare(a, b)` を呼び出し、文字列の内容を辞書順で比較した結果を返す。

この `exprcmp` の変更は、`walkCases` で導入された新しい比較戦略と完全に整合しています。これにより、`case` 句が新しい比較順序でソートされ、`walkCases` が生成する二分探索ツリーがこの新しい順序に基づいて正しく機能することが保証されます。

これらの変更は、Goコンパイラが生成するコードの効率を向上させ、特に文字列を多数の `case` 句で `switch` するようなシナリオにおいて、アプリケーションの実行時パフォーマンスを大幅に改善します。

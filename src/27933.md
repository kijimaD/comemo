## 元コミット内容

このコミットの主な目的は、Goリンカ (`cmd/link`) がシンボルを管理するために使用していたリンクリスト構造を、より効率的なスライス構造に置き換えることです。これは、リンカのパフォーマンスを向上させるための最初にして最大のステップと位置づけられています。

具体的な変更点として、セクションのソート処理が独立して並行して実行されるようになりました。この改善により、`jujud` プロジェクトの `linux/amd64` 環境でのリンク時間が約4%短縮されたと報告されています。この変更は、GoのIssue #15374 に関連しています。

## 変更の背景

Goリンカ (`cmd/link`) は、Goプログラムのビルドプロセスにおいて非常に重要な役割を担っています。大規模なアプリケーションや多数の依存関係を持つプロジェクトでは、リンク処理に時間がかかることがあり、開発者の生産性に影響を与える可能性があります。

従来のリンカの実装では、シンボル（関数、変数、セクションなど）をリンクリストで管理していました。リンクリストは要素の挿入や削除が容易であるという利点がありますが、特定の要素へのアクセスにはリストの先頭から順にたどる必要があり、O(N) の時間計算量がかかります。また、メモリ上の配置が連続的ではないため、CPUのキャッシュ効率が悪く、パフォーマンスのボトルネックとなることが知られています。

このコミットは、リンカのパフォーマンスを改善するために、このリンクリストベースのシンボル管理を、Goのイディオムであり、より高性能なデータ構造であるスライスに置き換えることを目的としています。スライスはメモリ上で連続した領域にデータを格納するため、CPUキャッシュの利用効率が高く、インデックスによる要素アクセスがO(1)で非常に高速です。

特に、データシンボルの処理はリンカの重要なフェーズであり、この部分をスライス化し、さらにソート処理を並行化することで、全体的なリンク時間の短縮が期待されました。実際に、`jujud` という具体的なプロジェクトでのベンチマークで約4%のリンク時間短縮が確認され、この変更の有効性が示されています。

## 前提知識の解説

### Goにおけるリンカ (cmd/link)

`cmd/link` は、Goツールチェーンの一部であり、Goコンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合して、実行可能なバイナリファイルや共有ライブラリを生成するプログラムです。その主な役割は以下の通りです。

*   **シンボル解決 (Symbol Resolution):** 異なるオブジェクトファイルで定義された関数や変数の参照を、最終的なメモリアドレスに解決します。
*   **セクション配置 (Section Placement):** コード、初期化済みデータ、未初期化データ (BSS)、読み取り専用データなどの異なる種類の情報を、実行可能ファイル内の適切なセクションに配置します。
*   **再配置処理 (Relocation Processing):** コンパイル時にアドレスが確定できないシンボル参照（例: 外部関数呼び出し、グローバル変数へのアクセス）を、リンク時に実際のメモリアドレスに基づいて修正します。
*   **デバッグ情報の生成:** デバッガがソースコードと実行可能コードをマッピングできるように、デバッグ情報（DWARFなど）を生成します。

### シンボル (LSym)

Goリンカにおける「シンボル」は、プログラム内の様々なエンティティ（関数、グローバル変数、型情報、文字列リテラルなど）を表す内部データ構造です。`LSym` (Linker Symbol) は、これらのエンティティの名前、型、サイズ、値（アドレス）、関連する再配置情報などを保持します。リンカはこれらの `LSym` オブジェクトを操作して、最終的なバイナリを構築します。

### リンクリストとスライス

Go言語におけるリンクリストとスライスは、どちらもデータのコレクションを扱うためのデータ構造ですが、その特性は大きく異なります。

*   **リンクリスト (Linked List):**
    *   各要素（ノード）がデータと次の要素へのポインタ（または前の要素へのポインタも含む）を持つ構造です。
    *   **利点:** リストの途中への要素の挿入や削除が、ポインタの付け替えだけで済むため、O(1) の時間計算量で高速に行えます（ただし、挿入/削除位置を見つけるまでの探索時間は別途かかります）。
    *   **欠点:** 特定のインデックスの要素にアクセスするには、リストの先頭から順にたどる必要があり、O(N) の時間計算量がかかります。また、メモリ上に連続して配置されないため、CPUのキャッシュミスが発生しやすく、データアクセスが遅くなる傾向があります。各ノードがポインタを保持するため、メモリオーバーヘッドも大きくなります。

*   **スライス (Slice):**
    *   Goの組み込み型であり、基盤となる配列への「ビュー」を提供します。スライス自体は、基盤配列へのポインタ、長さ、容量の3つの要素から構成されます。
    *   **利点:** メモリ上で連続した領域にデータが格納されるため、CPUのキャッシュ効率が非常に高いです。インデックスによる要素アクセスはO(1)で非常に高速です。Goのイディオムであり、多くの標準ライブラリ関数がスライスを効率的に扱います。
    *   **欠点:** 容量を超えて要素を追加する場合、より大きな新しい配列が割り当てられ、既存の要素がコピーされるため、一時的にコストがかかることがあります。しかし、多くの場合、このコストはリンクリストのランダムアクセスやキャッシュミスのコストよりも小さく、全体的なパフォーマンスはスライスの方が優れています。

リンカのようなツールでは、シンボル情報のソート、検索、セクションへの配置など、様々な操作でデータ構造を頻繁に走査します。このようなシナリオでは、スライスの持つ連続したメモリ配置と高速なランダムアクセスが、リンクリストよりもはるかに有利に働きます。

### 再配置 (Relocation)

再配置とは、リンカがオブジェクトファイル内のシンボル参照を、最終的な実行可能ファイル内の実際のメモリアドレスに解決するプロセスです。コンパイル時、コンパイラは関数呼び出しやグローバル変数へのアクセスなどの命令に対して、まだ確定していないアドレスのプレースホルダーを埋め込みます。リンカは、すべてのオブジェクトファイルを結合し、各シンボルの最終的なアドレスが決定された後、これらのプレースホルダーを実際のメモリアドレスに置き換えます。

### セクション (Section)

実行可能ファイルは、異なる種類の情報（コード、データ、BSSなど）を格納するために、複数の論理的なセクションに分割されています。

*   `.text` セクション: 実行可能な機械語コードを格納します。
*   `.data` セクション: 初期化されたグローバル変数や静的変数を格納します。
*   `.rodata` セクション: 読み取り専用のデータ（文字列リテラル、定数など）を格納します。
*   `.bss` セクション: 初期化されていないグローバル変数や静的変数を格納します。プログラム開始時にゼロで初期化されます。
*   `.got` (Global Offset Table) / `.plt` (Procedure Linkage Table): 動的リンクで使用されるテーブル。

リンカは、これらのセクションにシンボルを適切に配置し、各セクションのサイズとアドレスを決定します。

## 技術的詳細

このコミットの核となる技術的変更は、Goリンカ (`cmd/link`) がデータシンボルを管理する方法を、リンクリストからスライスベースの構造へと移行した点にあります。これにより、シンボルの収集、ソート、セクションへの割り当ての各フェーズで、パフォーマンスと効率が向上しています。

1.  **データ構造の変更:**
    *   以前は、データシンボルは `*LSym` 型のリンクリスト `datap` として管理されていました。
    *   このコミットでは、`datap` は `[]*LSym` 型のスライスに変更されました。
    *   さらに、`dodata` 関数内で、シンボルタイプごとにシンボルを分類するための `var data [obj.SXREF][]*LSym` というスライスの配列が導入されました。`obj.SXREF` はシンボルタイプの最大値を示し、これにより各シンボルタイプに対応するスライスが用意されます。

2.  **並行処理の導入:**
    *   `dodata` 関数内で、各シンボルタイプ (`data[symn]`) に属するシンボルのソート処理が並行して実行されるようになりました。
    *   これは `sync.WaitGroup` と `go func() { ... }()` を使用して実現されています。リンカは複数のシンボルタイプを同時にソートできるため、マルチコアプロセッサの恩恵を最大限に活用し、リンク時間を短縮します。

3.  **ソートロジックの改善:**
    *   `dataSortKey` という新しい構造体が導入されました。この構造体は、ソートに必要な `size`、`name`、および元の `*LSym` へのポインタ (`lsym`) を保持します。ソートキーをインラインに保持することで、ソート中のキャッシュ効率が向上します。
    *   `bySizeAndName` という `dataSortKey` のスライス型が定義され、`sort.Sort` インターフェース (`Len`, `Swap`, `Less`) を実装しています。
    *   `Less` メソッドでは、まず `size` で比較し、次に `name` で比較するというロジックが採用されています。
    *   特定のシンボルタイプ (`obj.SELFGOT`, `obj.STYPELINK`) に対しては、カスタムのソートロジックが適用されます。
        *   `obj.SELFGOT` (Global Offset Table) の場合、`ppc64` アーキテクチャでは `.got` と `.toc` セクションをインターリーブする必要があるため、サイズ比較をスキップし、名前 (`.got` が `.toc` より前にソートされるように) で比較します。
        *   `obj.STYPELINK` の場合、`reflect` パッケージが型リンクをバイナリサーチできるように、`rtype.string` フィールドでソートされます。これにより、型情報の検索効率が向上します。

4.  **セクション割り当ての変更:**
    *   以前は、リンクリスト `datap` を順次走査し、シンボルタイプに基づいてセクションを割り当てていました。
    *   新しい実装では、`data [obj.SXREF][]*LSym` の配列をループし、各シンボルタイプに属するスライスからシンボルを取り出してセクションに割り当てます。これにより、より構造化された方法でセクション割り当てが行われます。
    *   `maxalign` 関数も、リンクリストのヘッドシンボルを受け取る代わりに、シンボルのスライスを受け取るように変更され、スライス全体から最大アラインメントを計算するようになりました。

5.  **再配置処理関数の更新:**
    *   `reloc` および `dynreloc` 関数内の `datap` のイテレーションが、リンクリスト (`for s := datap; s != nil; s = s.Next`) からスライス (`for _, sym := range datap`) に変更されました。
    *   `dynreloc` 関数は、引数として `*[obj.SXREF][]*LSym` を受け取るように変更され、シンボルタイプごとのスライスをイテレートして再配置処理を行うようになりました。
    *   `elf.go`, `macho.go`, `pe.go` 内の `elfrelocsect`, `machorelocsect`, `perelocsect` といった再配置関連関数も、リンクリストのヘッドシンボルではなく、シンボルのスライスを受け取るように変更され、内部の処理がスライスベースに適合されました。

6.  **`blkSlice` 関数の導入:**
    *   `blkSlice` は、リンクリストを処理していた `blk` 関数のスライス版として導入されました。これは、将来的に `blk` を完全に置き換えることを意図しています。
    *   `Datblk` 関数は、データブロックの書き込みに `blkSlice` を呼び出すように変更されました。

これらの変更により、リンカはシンボルデータをより効率的に管理し、特にソート処理において並行性を活用することで、全体的なリンク時間の短縮を実現しています。

    type dataSortKey struct {
        size int64
        name string
        lsym *LSym
    }

    type bySizeAndName []dataSortKey

    func (d bySizeAndName) Len() int      { return len(d) }
    func (d bySizeAndName) Swap(i, j int) { d[i], d[j] = d[j], d[i] }
    func (d bySizeAndName) Less(i, j int) bool {
        s1, s2 := d[i], d[j]
        if s1.size != s2.size {
            return s1.size < s2.size
        }
        return s1.name < s2.name
    }

## コアとなるコードの解説

このコミットの核心は、リンカがシンボルを扱う際のデータ構造を、柔軟性よりもパフォーマンスを重視したスライスへと全面的に移行した点にあります。

*   **`var datap []*LSym`:**
    これは、リンカが最終的にアドレス順に並べられたデータシンボルを保持するグローバル変数です。以前はリンクリストのヘッドポインタでしたが、スライスに変更されたことで、リンカの他の部分がこのシンボルリストをより効率的に走査できるようになります。

*   **`var data [obj.SXREF][]*LSym`:**
    `dodata` 関数内で一時的に使用されるこの構造は、シンボルをそのタイプ (`obj.STYPE`, `obj.SNOPTRDATA` など) ごとに分類して保持するためのものです。`obj.SXREF` はシンボルタイプの列挙の最大値であり、これにより各シンボルタイプに対応する `[]*LSym` のスライスが用意されます。この分類により、同じタイプのシンボルをまとめて処理したり、並行してソートしたりすることが容易になります。

*   **並行ソートのメカニズム:**
    ```go
    var wg sync.WaitGroup
    for symn := range data {
        symn := symn // クロージャ内で正しい symn をキャプチャ
        wg.Add(1)
        go func() {
            data[symn] = dodataSect(symn, data[symn])
            wg.Done()
        }()
    }
    wg.Wait()
    ```
    このコードブロックは、Goの並行処理の強力な機能を示しています。`data` 配列の各要素（つまり、各シンボルタイプに対応するシンボルのスライス）に対して、個別のGoroutineを起動して `dodataSect` 関数を呼び出し、ソート処理を実行します。`sync.WaitGroup` は、すべてのGoroutineが完了するまでメインのGoroutine（`dodata` 関数）の実行を待機させるために使用されます。これにより、複数のCPUコアを持つシステムでは、ソート処理が大幅に高速化されます。

*   **`dodataSect` 関数とカスタムソート:**
    この関数は、特定のシンボルタイプに特化したソートロジックをカプセル化しています。`dataSortKey` 構造体は、ソートに必要な最小限の情報（サイズ、名前、元のシンボルへのポインタ）を保持することで、ソート中のメモリアクセスを局所化し、キャッシュ効率を向上させます。
    特に注目すべきは、`obj.SELFGOT` や `obj.STYPELINK` のような特定のシンボルタイプに対して、ソートキーを動的に変更している点です。これは、リンカが特定のアーキテクチャやGoランタイムの要件に合わせて、シンボルの並び順を厳密に制御する必要があるためです。例えば、`obj.STYPELINK` のソートキーを `rtype.string` にすることで、Goの `reflect` パッケージが型情報を効率的に検索できるようになります。

*   **`reloc` および `dynreloc` の変更:**
    これらの関数は、再配置処理を行う際にシンボルリストを走査します。リンクリストからスライスへの変更により、`for s := datap; s != nil; s = s.Next` のようなポインタをたどるイテレーションが、`for _, sym := range datap` のようなスライスを直接イテレートする形式に置き換えられました。これにより、コードが簡潔になるだけでなく、スライスの連続したメモリ配置によるキャッシュ効率の恩恵を受け、走査速度が向上します。

*   **`blkSlice` の導入:**
    `blkSlice` 関数は、データブロックを書き込む際に、リンクリストではなくスライスを処理するように設計されています。これは、リンカのデータ処理パイプライン全体がスライスベースに移行していることの一例です。`Datblk` 関数がこの新しい `blkSlice` を呼び出すようになったことで、データセクションの書き込みもスライスの利点を享受できるようになります。

これらの変更は、Goリンカの内部アーキテクチャを現代のハードウェアに最適化し、大規模なGoアプリケーションのビルド時間を短縮するための重要な一歩と言えます。

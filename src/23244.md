## 変更の背景

このコミットは、Goの `net/http` パッケージ内の特定のテストが不安定（flaky）であるという問題に対処するために行われました。不安定なテストとは、コードの変更がないにもかかわらず、実行するたびに成功したり失敗したりするテストのことです。このようなテストは、CI/CDパイプラインの信頼性を損ない、開発者が実際のバグとテストの不安定性を区別することを困難にします。

コミットメッセージによると、この不安定性の原因は「スケジューリングの競合状態（scheduling race）」でした。テストは、特定のゴルーチンがすでにスケジュールされ、実行されていることを前提として何かを測定していました。しかし、Goランタイムのゴルーチンスケジューラは非決定論的であるため、テストが期待する順序でゴルーチンが実行される保証はありませんでした。結果として、テストがゴルーチンの完了を待たずにアサーションを実行してしまい、誤って失敗することがありました。

具体的には、`TestIdleConnChannelLeak` というテストが、`Transport.readLoop` ゴルーチンがアイドル接続をプールに戻すのを待たずに、アイドル接続マップのサイズをチェックしていました。通常は `readLoop` が迅速に処理を終えるため問題になりませんでしたが、特定のスケジューリング条件下では `readLoop` が遅延し、テストが誤った状態を検出してしまう可能性がありました。この問題は `Fixes #10427` として報告されていました。

## 前提知識の解説

### Goのゴルーチンとスケジューリング

Go言語は、軽量な並行処理の単位として「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数千、数万のゴルーチンを同時に実行することが可能です。Goランタイムには、これらのゴルーチンをOSスレッドにマッピングし、実行を管理するスケジューラが組み込まれています。

Goのスケジューラはプリエンプティブ（preemptive）ですが、完全にプリエンプティブではありません。Go 1.14以前は、関数呼び出しやチャネル操作などの特定のポイントでしかゴルーチンをプリエンプトできませんでした。Go 1.14以降は非同期プリエンプションが導入され、より積極的にゴルーチンを中断できるようになりましたが、それでもスケジューリングの順序は非決定論的です。つまり、複数のゴルーチンが同時に実行される場合、それらがどの順序で実行されるか、いつ中断され、いつ再開されるかは、実行ごとに異なる可能性があります。

### 競合状態（Race Condition）

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソースにアクセスする際に、そのアクセス順序によってプログラムの最終結果が変化してしまう状況を指します。Goのテストにおける競合状態は、テストが特定のゴルーチンの完了や状態変化を前提としているにもかかわらず、スケジューリングの非決定性によりその前提が崩れることで発生します。これにより、テストが「不安定」になり、同じコードベースでも実行ごとに結果が変わるという問題が生じます。

### `sync.Mutex` と同期プリミティブ

Goの `sync` パッケージは、並行処理における同期のためのプリミティブを提供します。`sync.Mutex` は相互排他ロックであり、共有リソースへのアクセスを一度に一つのゴルーチンに制限するために使用されます。`Lock()` メソッドでロックを取得し、`Unlock()` メソッドでロックを解放します。これにより、競合状態を防ぎ、共有リソースへのアクセスを安全に制御できます。

### `export_test.go` ファイル

Goのパッケージでは、通常、外部からアクセスできない（エクスポートされていない）内部の関数や変数があります。しかし、テストの目的でこれらの内部要素にアクセスしたい場合があります。Goでは、`_test.go` で終わるファイルにテストコードを記述しますが、同じパッケージ内の `export_test.go` というファイルを作成することで、テスト専用に内部要素をエクスポートすることができます。これにより、通常のアプリケーションコードには影響を与えずに、テストの柔軟性を高めることができます。

## 技術的詳細

このコミットの技術的解決策は、テストコードが `net/http` パッケージの内部的なゴルーチン（特に `persistConn.readLoop`）の実行タイミングを制御できるように、テスト専用のフック（hook）と同期メカニズムを導入することです。

1.  **`testHookMu` の導入**:
    *   `sync.Locker` インターフェースを満たす `testHookMu` という変数が `src/net/http/transport.go` に追加されました。
    *   このミューテックスは、テスト専用のフック変数 `testHookReadLoopBeforeNextRead` へのアクセスを保護するために使用されます。
    *   本番環境でのオーバーヘッドを避けるため、`testHookMu` はデフォルトで何もしない `fakeLocker` 型のインスタンスに初期化されます。
    *   `src/net/http/export_test.go` の `init()` 関数内で、テスト実行時のみ `testHookMu` が実際の `sync.Mutex` のインスタンスに置き換えられます。これにより、テスト時のみ同期のコストを支払うようになります。

2.  **`testHookReadLoopBeforeNextRead` フックの追加**:
    *   `src/net/http/transport.go` に `testHookReadLoopBeforeNextRead func()` という関数型の変数が追加されました。これは、`persistConn.readLoop` ゴルーチンが次の読み取り操作を行う直前に呼び出されるフックです。
    *   `readLoop` の開始時に、`testHookMu` をロックしてこのフックの現在の値をローカル変数にコピーします。これにより、ループ中にフックが変更されても一貫性が保たれます。
    *   `readLoop` のループ内で、次の読み取りを行う直前に、このフックが `nil` でなければ呼び出されます。

3.  **`SetReadLoopBeforeNextReadHook` 関数のエクスポート**:
    *   `src/net/http/export_test.go` に `SetReadLoopBeforeNextReadHook(f func())` という関数が追加されました。
    *   この関数は、テストコードが `testHookReadLoopBeforeNextRead` の値を設定できるようにします。内部で `testHookMu` を使用して安全にフックを設定します。

4.  **`TestIdleConnChannelLeak` テストの修正**:
    *   `src/net/http/transport_test.go` の `TestIdleConnChannelLeak` テストが修正されました。
    *   `nReqs` (リクエスト数) と同じサイズの `didRead` というチャネルが作成されます。
    *   `SetReadLoopBeforeNextReadHook` を使用して、`didRead <- true` をチャネルに送信する匿名関数をフックとして設定します。
    *   テストは `nReqs` 回のHTTP GETリクエストを実行した後、`for i := 0; i < nReqs; i++ { <-didRead }` というループを追加します。これにより、各 `readLoop` ゴルーチンが `testHookReadLoopBeforeNextRead` フックを呼び出し、`didRead` チャネルに値を送信するまでテストの実行がブロックされます。
    *   この同期メカニズムにより、テストはすべての `readLoop` ゴルーチンがアイドル接続をプールに戻す処理を完了したことを確認してから、`IdleConnChMapSizeForTesting()` を呼び出してアイドル接続マップのサイズをチェックできるようになります。これにより、競合状態が解消され、テストが安定します。

```go
func TestIdleConnChannelLeak(t *testing.T) {
	// ... 既存コード ...

	const nReqs = 5
	didRead := make(chan bool, nReqs) // nReqs個のバッファを持つチャネルを作成
	SetReadLoopBeforeNextReadHook(func() { didRead <- true }) // フックを設定: チャネルにtrueを送信
	defer SetReadLoopBeforeNextReadHook(nil) // テスト終了時にフックを解除

	// ... 既存コード ...

	for _, disableKeep := range []bool{true, false} {
		tr.DisableKeepAlives = disableKeep
		for i := 0; i < nReqs; i++ {
			_, err := c.Get(fmt.Sprintf("http://foo-host-%d.tld/", i))
			if err != nil {
				t.Fatal(err)
			}
			// Note: no res.Body.Close is needed here, since the
			// response Content-Length is zero. Perhaps the test
			// should be more explicit and use a HEAD, but tests
			// elsewhere guarantee that zero byte responses generate
			// a "Content-Length: 0" instead of chunking.
		}

		// At this point, each of the 5 Transport.readLoop goroutines
		// are scheduling noting that there are no response bodies (see
		// earlier comment), and are then calling putIdleConn, which
		// decrements this count. Usually that happens quickly, which is
		// why this test has seemed to work for ages. But it's still
		// racey: we have wait for them to finish first. See Issue 10427
		for i := 0; i < nReqs; i++ {
			<-didRead // 各readLoopゴルーチンからの通知を待機
		}

		if got := tr.IdleConnChMapSizeForTesting(); got != 0 {
			t.Fatalf("ForDisableKeepAlives = %v, map size = %d; want 0", disableKeep, got)
		}
	}
}
```
このテストの修正は、競合状態を解消するための核心部分です。`didRead` チャネルと `SetReadLoopBeforeNextReadHook` を組み合わせることで、テストは `readLoop` ゴルーチンが次の読み取り操作の準備ができたことを明示的に通知するまで待機します。これにより、`putIdleConn` が呼び出され、アイドル接続マップのサイズが正しく更新されることが保証され、テストが非決定的に失敗する問題が解決されます。

## 変更の背景

このコミットは、Goの `net/http` パッケージ内の特定のテストが不安定（flaky）であるという問題に対処するために行われました。不安定なテストとは、コードの変更がないにもかかわらず、実行するたびに成功したり失敗したりするテストのことです。このようなテストは、CI/CDパイプラインの信頼性を損ない、開発者が実際のバグとテストの不安定性を区別することを困難にします。

コミットメッセージによると、この不安定性の原因は「スケジューリングの競合状態（scheduling race）」でした。テストは、特定のゴルーチンがすでにスケジュールされ、実行されていることを前提として何かを測定していました。しかし、Goランタイムのゴルーチンスケジューラは非決定論的であるため、テストが期待する順序でゴルーチンが実行される保証はありませんでした。結果として、テストがゴルーチンの完了を待たずにアサーションを実行してしまい、誤って失敗することがありました。

具体的には、`TestIdleConnChannelLeak` というテストが、`Transport.readLoop` ゴルーチンがアイドル接続をプールに戻すのを待たずに、アイドル接続マップのサイズをチェックしていました。通常は `readLoop` が迅速に処理を終えるため問題になりませんでしたが、特定のスケジューリング条件下では `readLoop` が遅延し、テストが誤った状態を検出してしまう可能性がありました。この問題は `Fixes #10427` として報告されていました。

## 前提知識の解説

### Goのゴルーチンとスケジューリング

Go言語は、軽量な並行処理の単位として「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数千、数万のゴルーチンを同時に実行することが可能です。Goランタイムには、これらのゴルーチンをOSスレッドにマッピングし、実行を管理するスケジューラが組み込まれています。

Goのスケジューラはプリエンプティブ（preemptive）ですが、完全にプリエンプティブではありません。Go 1.14以前は、関数呼び出しやチャネル操作などの特定のポイントでしかゴルーチンをプリエンプトできませんでした。Go 1.14以降は非同期プリエンプションが導入され、より積極的にゴルーチンを中断できるようになりましたが、それでもスケジューリングの順序は非決定論的です。つまり、複数のゴルーチンが同時に実行される場合、それらがどの順序で実行されるか、いつ中断され、いつ再開されるかは、実行ごとに異なる可能性があります。

### 競合状態（Race Condition）

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソースにアクセスする際に、そのアクセス順序によってプログラムの最終結果が変化してしまう状況を指します。Goのテストにおける競合状態は、テストが特定のゴルーチンの完了や状態変化を前提としているにもかかわらず、スケジューリングの非決定性によりその前提が崩れることで発生します。これにより、テストが「不安定」になり、同じコードベースでも実行ごとに結果が変わるという問題が生じます。

### `sync.Mutex` と同期プリミティブ

Goの `sync` パッケージは、並行処理における同期のためのプリミティブを提供します。`sync.Mutex` は相互排他ロックであり、共有リソースへのアクセスを一度に一つのゴルーチンに制限するために使用されます。`Lock()` メソッドでロックを取得し、`Unlock()` メソッドでロックを解放します。これにより、競合状態を防ぎ、共有リソースへのアクセスを安全に制御できます。

### `export_test.go` ファイル

Goのパッケージでは、通常、外部からアクセスできない（エクスポートされていない）内部の関数や変数があります。しかし、テストの目的でこれらの内部要素にアクセスしたい場合があります。Goでは、`_test.go` で終わるファイルにテストコードを記述しますが、同じパッケージ内の `export_test.go` というファイルを作成することで、テスト専用に内部要素をエクスポートすることができます。これにより、通常のアプリケーションコードには影響を与えずに、テストの柔軟性を高めることができます。

## 技術的詳細

このコミットの技術的解決策は、テストコードが `net/http` パッケージの内部的なゴルーチン（特に `persistConn.readLoop`）の実行タイミングを制御できるように、テスト専用のフック（hook）と同期メカニズムを導入することです。

1.  **`testHookMu` の導入**:
    *   `sync.Locker` インターフェースを満たす `testHookMu` という変数が `src/net/http/transport.go` に追加されました。
    *   このミューテックスは、テスト専用のフック変数 `testHookReadLoopBeforeNextRead` へのアクセスを保護するために使用されます。
    *   本番環境でのオーバーヘッドを避けるため、`testHookMu` はデフォルトで何もしない `fakeLocker` 型のインスタンスに初期化されます。
    *   `src/net/http/export_test.go` の `init()` 関数内で、テスト実行時のみ `testHookMu` が実際の `sync.Mutex` のインスタンスに置き換えられます。これにより、テスト時のみ同期のコストを支払うようになります。

2.  **`testHookReadLoopBeforeNextRead` フックの追加**:
    *   `src/net/http/transport.go` に `testHookReadLoopBeforeNextRead func()` という関数型の変数が追加されました。これは、`persistConn.readLoop` ゴルーチンが次の読み取り操作を行う直前に呼び出されるフックです。
    *   `readLoop` の開始時に、`testHookMu` をロックしてこのフックの現在の値をローカル変数にコピーします。これにより、ループ中にフックが変更されても一貫性が保たれます。
    *   `readLoop` のループ内で、次の読み取りを行う直前に、このフックが `nil` でなければ呼び出されます。

3.  **`SetReadLoopBeforeNextReadHook` 関数のエクスポート**:
    *   `src/net/http/export_test.go` に `SetReadLoopBeforeNextReadHook(f func())` という関数が追加されました。
    *   この関数は、テストコードが `testHookReadLoopBeforeNextRead` の値を設定できるようにします。内部で `testHookMu` を使用して安全にフックを設定します。

4.  **`TestIdleConnChannelLeak` テストの修正**:
    *   `src/net/http/transport_test.go` の `TestIdleConnChannelLeak` テストが修正されました。
    *   `nReqs` (リクエスト数) と同じサイズの `didRead` というチャネルが作成されます。
    *   `SetReadLoopBeforeNextReadHook` を使用して、`didRead <- true` をチャネルに送信する匿名関数をフックとして設定します。
    *   テストは `nReqs` 回のHTTP GETリクエストを実行した後、`for i := 0; i < nReqs; i++ { <-didRead }` というループを追加します。これにより、各 `readLoop` ゴルーチンが `testHookReadLoopBeforeNextRead` フックを呼び出し、`didRead` チャネルに値を送信するまでテストの実行がブロックされます。
    *   この同期メカニズムにより、テストはすべての `readLoop` ゴルーチンがアイドル接続をプールに戻す処理を完了したことを確認してから、`IdleConnChMapSizeForTesting()` を呼び出してアイドル接続マップのサイズをチェックできるようになります。これにより、競合状態が解消され、テストが安定します。

`init()` 関数はパッケージが初期化される際に自動的に実行されます。この変更により、テストが実行される環境（`_test.go` ファイルが存在し、テストビルドが行われる場合）でのみ、`testHookMu` が実際の `sync.Mutex` インスタンスに置き換えられます。これにより、本番環境のバイナリには同期のオーバーヘッドが導入されません。`SetReadLoopBeforeNextReadHook` は、テストコードが `readLoop` の特定のポイントで実行されるコールバック関数を登録するためのエクスポートされた関数です。

### `src/net/http/transport_test.go` の変更

```go
func TestIdleConnChannelLeak(t *testing.T) {
	// ... 既存コード ...

	const nReqs = 5
	didRead := make(chan bool, nReqs) // nReqs個のバッファを持つチャネルを作成
	SetReadLoopBeforeNextReadHook(func() { didRead <- true }) // フックを設定: チャネルにtrueを送信
	defer SetReadLoopBeforeNextReadHook(nil) // テスト終了時にフックを解除

	// ... 既存コード ...

	for _, disableKeep := range []bool{true, false} {
		tr.DisableKeepAlives = disableKeep
		for i := 0; i < nReqs; i++ {
			_, err := c.Get(fmt.Sprintf("http://foo-host-%d.tld/", i))
			if err != nil {
				t.Fatal(err)
			}
			// Note: no res.Body.Close is needed here, since the
			// response Content-Length is zero. Perhaps the test
			// should be more explicit and use a HEAD, but tests
			// elsewhere guarantee that zero byte responses generate
			// a "Content-Length: 0" instead of chunking.
		}

		// At this point, each of the 5 Transport.readLoop goroutines
		// are scheduling noting that there are no response bodies (see
		// earlier comment), and are then calling putIdleConn, which
		// decrements this count. Usually that happens quickly, which is
		// why this test has seemed to work for ages. But it's still
		// racey: we have wait for them to finish first. See Issue 10427
		for i := 0; i < nReqs; i++ {
			<-didRead // 各readLoopゴルーチンからの通知を待機
		}

		if got := tr.IdleConnChMapSizeForTesting(); got != 0 {
			t.Fatalf("ForDisableKeepAlives = %v, map size = %d; want 0", disableKeep, got)
		}
	}
}
```
このテストの修正は、競合状態を解消するための核心部分です。`didRead` チャネルと `SetReadLoopBeforeNextReadHook` を組み合わせることで、テストは `readLoop` ゴルーチンが次の読み取り操作の準備ができたことを明示的に通知するまで待機します。これにより、`putIdleConn` が呼び出され、アイドル接続マップのサイズが正しく更新されることが保証され、テストが非決定的に失敗する問題が解決されます。

## 元コミット内容

このコミットの主な目的は、GoコンパイラのSSAバックエンドにおけるドミネータ計算のメモリ割り当てフットプリントを削減することです。具体的には、ドミネータ計算で使用されるポインタのスライスを、ポインタのインデックスのスライスに変換しています。これにより、64ビットマシン上ではメモリ使用量が半分になり、これらのスライスがアクティブな間にGCが発生しても、トレースすべきポインタがなくなるため、GCのオーバーヘッドが軽減されます。

また、レジスタ割り当て（regalloc）における割り当て回数を削減するマイナーな最適化と、`compile.go`における`Sprintf`呼び出しを削減するマイナーな最適化も含まれています。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式を使用します。SSA形式では、ドミネータツリー（Dominator Tree）の計算が重要なステップとなります。ドミネータツリーは、プログラムの制御フローグラフ（CFG）において、あるブロックに到達するすべてのパスが必ず通過するブロック（ドミネータ）の関係を表します。この計算は、デッドコード削除、レジスタ割り当て、ループ最適化など、多くの最適化パスの基盤となります。

しかし、ドミネータツリーの計算は、特に大規模な関数において、多くのメモリを消費する可能性があります。特に、グラフのノード（ここでは`Block`）へのポインタを多数含むスライスを使用すると、以下の問題が発生します。

1.  **メモリ使用量の増大**: ポインタ自体がメモリを消費し、多数のポインタスライスは大きなメモリフットプリントとなります。
2.  **GCオーバーヘッド**: ポインタはガベージコレクタがヒープをスキャンする際に追跡する必要があるため、GCの作業量が増加し、プログラムの実行が一時停止する（ストップ・ザ・ワールド）時間が長くなる可能性があります。

このコミットは、これらの問題を解決するために、ポインタのスライスをインデックスのスライスに置き換えることで、メモリ使用量を削減し、GCの効率を向上させることを目的としています。これにより、コンパイル時間の短縮とコンパイラ自体のメモリ消費量の削減が期待されます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く使用される中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が簡素化され、多くの最適化が容易になります。Goコンパイラも、最適化パスの多くでSSA形式を利用しています。

### 2. 制御フローグラフ (CFG)

CFGは、プログラムの実行可能なすべてのパスを抽象的に表現したグラフです。ノードは基本ブロック（Basic Block、連続した命令のシーケンスで、入り口は一つ、出口は一つ）を表し、エッジはブロック間の制御フローの遷移を表します。

### 3. ドミネータ (Dominator) とドミネータツリー (Dominator Tree)

-   **ドミネータ**: 制御フローグラフにおいて、ノード `A` がノード `B` のドミネータであるとは、`entry` ノードから `B` へのすべてのパスが `A` を通過する場合を言います。
-   **即時ドミネータ (Immediate Dominator, IDom)**: ノード `B` の即時ドミネータ `IDom(B)` は、`B` をドミネートするすべてのノードの中で、`B` に最も近いノードです。
-   **ドミネータツリー**: 各ノードとその即時ドミネータとの間にエッジを張ることで形成されるツリー構造です。このツリーの根は `entry` ノードです。ドミネータツリーは、プログラムの構造を理解し、最適化を行う上で非常に有用です。

### 4. Lengauer-Tarjan アルゴリズム

ドミネータツリーを効率的に計算するためのアルゴリズムとして、Lengauer-Tarjanアルゴリズムが広く知られています。このアルゴリズムは、深さ優先探索（DFS）とセグメントツリーのようなデータ構造を組み合わせて、ほぼ線形時間でドミネータツリーを構築します。このコミットで変更されている`dom.go`ファイルは、このアルゴリズムの実装に関連しています。

### 5. ガベージコレクション (GC)

Go言語はガベージコレクタを備えており、開発者が手動でメモリを管理する必要がありません。GCは、プログラムが使用しなくなったメモリ領域を自動的に解放します。しかし、GCの実行には時間がかかり、特に大量のポインタを追跡する必要がある場合、そのオーバーヘッドは無視できません。ポインタの数を減らすことは、GCの効率を向上させる上で有効な手段です。

### 6. Goの型 `ID` と `*Block`

-   `*Block`: `Block`構造体へのポインタです。64ビットシステムでは8バイトを占め、GCの対象となります。
-   `ID`: GoコンパイラのSSAバックエンドで、`Block`や`Value`などのエンティティを一意に識別するために使用される整数型のIDです。通常、`int32`や`int`が使われます。これは4バイトを占め、ポインタではないためGCの追跡対象ではありません。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/compile/internal/ssa/dom.go`ファイルに集中しています。このファイルは、Lengauer-Tarjanアルゴリズムに基づいてドミネータツリーを計算するロジックを含んでいます。

変更の核心は、ドミネータ計算中に使用される一時的なデータ構造（スライス）が、`*Block`（`Block`へのポインタ）の代わりに`ID`（`Block`のインデックス）を格納するように変更された点です。

具体的には、以下のスライスの型が変更されています。

-   `dfnum`: `[]int` から `[]int32` へ
-   `order`: `[]*Block` から `[]ID` へ
-   `parent`: `[]*Block` から `[]ID` へ
-   `semi`: `[]*Block` から `[]ID` へ
-   `samedom`: `[]*Block` から `[]ID` へ
-   `ancestor`: `[]*Block` から `[]ID` へ
-   `best`: `[]*Block` から `[]ID` へ
-   `bucket`: `[]*Block` から `[]ID` へ

これらのスライスは、ドミネータ計算の各ステップで大量の`Block`参照を保持するために使用されます。ポインタの代わりにインデックスを使用することで、以下のメリットが得られます。

1.  **メモリ使用量の削減**: 64ビットシステムでは、ポインタは8バイトですが、`ID`（`int32`）は4バイトです。これにより、これらのスライスのメモリフットプリントが約半分になります。
2.  **GCオーバーヘッドの削減**: `ID`は整数型であるため、ガベージコレクタがヒープをスキャンする際に追跡する必要がありません。これにより、GCの作業量が減少し、コンパイル中のGC一時停止時間が短縮される可能性があります。
3.  **キャッシュ効率の向上**: メモリフットプリントが小さくなることで、CPUのキャッシュに収まるデータ量が増え、メモリアクセスの局所性が向上し、全体的なパフォーマンスが向上する可能性があります。

また、`dfs`関数（深さ優先探索）の戻り値に`fromID []*Block`が追加されています。これは、`ID`から実際の`*Block`へのマッピングを提供するためのものです。インデックスベースの操作を行う際に、必要に応じて実際の`Block`オブジェクトにアクセスできるようにするための補助的なデータ構造です。

`src/cmd/compile/internal/ssa/compile.go`では、コンパイルパスのログ出力に関するマイナーな最適化が行われています。具体的には、`Sprintf`の呼び出しが、`f.Log() || f.Config.HTML != nil`という条件の内側に移動されています。これにより、ログやHTML出力が不要な場合には`Sprintf`の呼び出しがスキップされ、不要な文字列割り当てとフォーマット処理が削減されます。

`src/cmd/compile/internal/ssa/regalloc.go`では、レジスタ割り当ての`computeLive`関数内で、`live`スライスの容量が0の場合に新しいスライスを割り当てる際の最適化が行われています。`cap(l) == 0`の場合に`make([]liveInfo, 0, len(t.contents()))`で適切な容量を持つスライスを事前に割り当てることで、動的なスライス拡張による再割り当ての回数を減らし、割り当て回数を削減しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/dom.go` の変更

このファイルにおける変更は、ドミネータ計算のLengauer-Tarjanアルゴリズムの実装において、`Block`オブジェクトへのポインタを直接扱う代わりに、`Block`のユニークな識別子である`ID`（整数）を扱うようにしたことが最も重要です。

例えば、`dfs`関数は深さ優先探索を行い、各ブロックの深さ優先番号（`dfnum`）、探索順序（`order`）、親ブロック（`parent`）を計算します。変更前はこれらが`*Block`のスライスとして保持されていましたが、変更後は`ID`のスライスとして保持されます。

```go
// 変更前 (抜粋)
func dfs(entries []*Block, succFn linkedBlocks) (dfnum []int, order []*Block, parent []*Block) {
    // ...
    dfnum = make([]int, maxBlockID)
    order = make([]*Block, maxBlockID)
    parent = make([]*Block, maxBlockID)
    // ...
    parent[entry.ID] = entry // ポインタを格納
    // ...
    order[n] = node // ポインタを格納
}

// 変更後 (抜粋)
func dfs(entries []*Block, succFn linkedBlocks) (fromID []*Block, dfnum []int32, order []ID, parent []ID) {
    // ...
    dfnum = make([]int32, maxBlockID)
    order = make([]ID, maxBlockID)
    parent = make([]ID, maxBlockID)
    fromID = make([]*Block, maxBlockID) // IDからBlockへのマッピング
    // ...
    parent[entry.ID] = entry.ID // IDを格納
    // ...
    order[n] = node.ID // IDを格納
}
```

`fromID []*Block`スライスは、`Block`のIDをインデックスとして、対応する`*Block`ポインタを格納するルックアップテーブルとして機能します。これにより、ドミネータ計算のロジック自体はIDベースで効率的に行いつつ、必要に応じて実際の`Block`オブジェクトにアクセスできるようになります。

`dominatorsLT`関数や`eval`関数でも同様に、`*Block`の代わりに`ID`を引数や戻り値、スライスの要素として使用するように変更されています。これにより、メモリ使用量が削減され、GCの負担が軽減されます。

### `src/cmd/compile/internal/ssa/compile.go` の変更

この変更は、コンパイルパスの実行時間とメモリ統計のログ出力に関するものです。

```go
// 変更前 (抜粋)
    tEnd := time.Now()
    time := tEnd.Sub(tStart).Nanoseconds()
    var stats string
    if logMemStats {
        // ... Sprintf呼び出し ...
    } else {
        stats = fmt.Sprintf("[%d ns]", time) // 無条件でSprintf
    }
    if f.Log() {
        f.Logf("  pass %s end %s\\n", p.name, stats)
    }
    printFunc(f)
    if f.Config.HTML != nil {
        f.Config.HTML.WriteFunc(fmt.Sprintf("after %s <span class=\"stats\">%s</span>", phaseName, stats), f)
    }

// 変更後 (抜粋)
    if f.Log() || f.Config.HTML != nil { // 条件が追加された
        tEnd := time.Now()
        time := tEnd.Sub(tStart).Nanoseconds()
        var stats string
        if logMemStats {
            // ... Sprintf呼び出し ...
        } else {
            stats = fmt.Sprintf("[%d ns]", time) // 条件付きでSprintf
        }
        f.Logf("  pass %s end %s\\n", p.name, stats)
        printFunc(f)
        f.Config.HTML.WriteFunc(fmt.Sprintf("after %s <span class=\"stats\">%s</span>", phaseName, stats), f)
    }
```

変更後では、`f.Log()`または`f.Config.HTML != nil`のいずれかが真である場合にのみ、時間計測、メモリ統計の収集、および`Sprintf`による文字列フォーマットが行われます。これにより、ログやHTML出力が不要なコンパイル時には、これらの処理が完全にスキップされ、不要なCPUサイクルとメモリ割り当てが削減されます。

### `src/cmd/compile/internal/ssa/regalloc.go` の変更

この変更は、レジスタ割り当てのライブネス解析（`computeLive`関数）におけるスライスの再割り当てに関する最適化です。

```go
// 変更前 (抜粋)
                l := s.live[p.ID][:0] // スライスをクリア

// 変更後 (抜粋)
                l := s.live[p.ID][:0]
                if cap(l) == 0 { // 容量が0の場合
                    l = make([]liveInfo, 0, len(t.contents())) // 適切な容量で再割り当て
                }
```

`s.live[p.ID][:0]`はスライスの長さを0にリセットしますが、基底配列の容量は保持されます。しかし、もしスライスの容量が元々0であった場合（例えば、初めて使用される場合や、以前に非常に小さなスライスが割り当てられていた場合）、その後の`append`操作で何度も基底配列の再割り当てが発生し、効率が悪くなります。

変更後では、`cap(l) == 0`の場合に、`len(t.contents())`という、そのスライスが最終的に必要とするであろう要素数に基づいて、適切な容量を持つ新しいスライスを`make`で割り当てています。これにより、不要な再割り当てが削減され、メモリ割り当ての回数が減少し、パフォーマンスが向上します。

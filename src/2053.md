# [インデックス 2053] ファイルの概要

このコミットは、Go言語の標準ライブラリにおけるI/O操作の基本的な関数名のリファクタリングに関するものです。具体的には、`io.Readn` という関数が `io.FullRead` に名称変更され、それに伴い関連するコードベース全体でこの変更が適用されています。この変更は、Go言語がまだ公開される前の初期開発段階で行われたものであり、API設計における明確性と一貫性へのこだわりを示しています。

## 元コミット内容

`Readn is a silly name when there's no n. Change to FullRead.`

このコミットメッセージは非常に簡潔ですが、変更の意図を明確に伝えています。「`n` がないのに `Readn` という名前は馬鹿げている。`FullRead` に変更する。」という内容です。これは、関数名がその機能と一致していないという問題意識から、より適切な名前に変更するというリファクタリングであることを示しています。

## 変更の背景

このコミットは、Go言語が一般に公開される2009年11月よりも前の、2009年4月に行われました。この時期は、Go言語のコアライブラリとAPIが活発に設計・開発・洗練されていた段階です。

当時の `io` パッケージには `Readn` という関数が存在していました。しかし、その実装は、指定されたバイト数 `n` を読み込むのではなく、提供されたバッファが満たされるまで、またはEOF（ファイルの終端）やエラーが発生するまでデータを読み込むものでした。つまり、関数名 `Readn` が示唆する「`n` バイトを読み込む」という動作と、実際の動作が乖離していました。

Go言語の設計哲学の一つに、APIの明確性と直感的な命名があります。`Readn` のような誤解を招く名前は、この哲学に反していました。Go言語の共同開発者の一人であるRob Pikeは、このような命名の不整合を早期に修正することの重要性を認識しており、このコミットはそのような改善の一環として行われました。関数名を `FullRead` に変更することで、その関数が「バッファを完全に満たすまで読み込む」という実際の動作をより正確に表現するようになりました。これは、後のGo標準ライブラリにおける `io.ReadFull` の振る舞いに通じるものです。

## 前提知識の解説

*   **Go言語のI/Oインターフェース**: Go言語のI/O操作の基盤は、`io.Reader` と `io.Writer` というシンプルなインターフェースによって提供されます。
    *   `io.Reader` インターフェースは `Read(p []byte) (n int, err error)` メソッドを定義します。このメソッドは、データを `p` に読み込み、読み込んだバイト数 `n` とエラーを返します。`Read` メソッドは、要求されたバイト数 (`len(p)`) よりも少ないバイト数を読み込むことがありますが、これはエラーではありません（例えば、データがまだ利用可能でない場合や、ファイルの終端に達した場合など）。
*   **`io.ReadFull` (現代のGo)**: 現代のGo言語の `io` パッケージには `io.ReadFull(r Reader, buf []byte) (n int, err error)` という関数があります。この関数は、`buf` の長さと全く同じバイト数を `r` から読み込むことを保証します。もし `len(buf)` バイトを読み込む前にEOFに達した場合、`io.ErrUnexpectedEOF` を返します。この `io.ReadFull` の動作は、このコミットで `io.FullRead` と命名された関数の意図と非常に似ています。
*   **Go言語の初期開発**: Go言語は2007年にGoogleで開発が始まり、2009年11月にオープンソースとして公開されました。このコミットは公開前の2009年4月のものであり、言語仕様や標準ライブラリのAPIがまだ流動的で、活発な議論と変更が行われていた時期にあたります。Rob Pike、Ken Thompson、Robert Griesemerといった主要な開発者が、言語の基盤を築いていました。

## 技術的詳細

このコミットの技術的な核心は、`io` パッケージ内の `Readn` 関数の名称変更と、それに伴うコードベース全体での参照の更新です。

元の `io.Readn` 関数のシグネチャは以下のようであったと推測されます（コミットの差分から）：

```go
func Readn(r Read, buf []byte) (n int, err os.Error)
```

この関数は `buf` スライスを引数に取り、そのバッファが満たされるまでデータを読み込もうとします。しかし、関数名 `Readn` は、通常「`n` バイトを読み込む」というセマンティクスを連想させます。しかし、この関数には `n` を指定する引数がなく、また `n` バイトの読み込みを保証するものでもありませんでした（バッファが満たされるか、EOF/エラーまで読み込む）。

Rob Pikeは、この命名が誤解を招くものであり、Go言語のAPI設計原則である「明確性」に反すると判断しました。そこで、関数名を `FullRead` に変更することで、その実際の動作、すなわち「バッファを完全に満たすまで読み込む」という意図をより正確に表現するようにしました。

この変更は、単なる名前の変更に留まらず、Go言語の初期の設計段階において、APIのセマンティクスと命名の一貫性を非常に重視していたことを示しています。このような細かなリファクタリングが積み重なることで、Go言語の標準ライブラリは、その後の開発者にとって直感的で使いやすいものとなっていきました。

## コアとなるコードの解説

このコミットの核心は、`src/lib/io/io.go` 内の `Readn` 関数の定義と、それを使用する箇所を `FullRead` に変更した点にあります。

元の `Readn` 関数は、`io.Reader` インターフェースを実装する `r` からデータを読み込み、`buf` スライスに格納していました。ループを使って `buf` が完全に満たされるまで、または `r.Read` がエラー（EOFを含む）を返すまで読み込みを試みていました。

```go
// Readn reads r until the buffer buf is full, or until EOF or error.
func Readn(r Read, buf []byte) (n int, err os.Error) {
	n = 0;
	for n < len(buf) {
		nn, e := r.Read(buf[n:len(buf)]);
		if nn > 0 {
			n += nn;
		}
		if e != nil {
			err = e;
			break;
		}
	}
	return n, err
}
```

この実装は、現代の `io.ReadFull` と同様に、バッファを「完全に」満たすことを意図しています。しかし、関数名 `Readn` は、引数として `n` を取らないにもかかわらず、特定のバイト数 `n` を読み込むかのような印象を与えていました。この命名の不整合が、Rob Pikeによって「silly name」と評され、`FullRead` というより適切な名前に変更されました。

この変更は、Go言語のAPI設計における以下の重要な原則を強調しています。

1.  **明確な命名**: 関数名はその機能とセマンティクスを正確に反映すべきであるという原則。これにより、開発者は関数の動作を推測しやすくなり、誤用を防ぐことができます。
2.  **一貫性**: ライブラリ全体で一貫した命名規則とセマンティクスを維持することの重要性。これにより、コードベース全体の理解と保守が容易になります。
3.  **早期のリファクタリング**: 言語の初期段階でこのような基本的なAPIの不整合を修正することは、将来的な大規模な変更や後方互換性の問題を避ける上で非常に重要です。

このコミットは、Go言語がその設計段階から、開発者の使いやすさとコードの品質を重視していたことの証拠と言えるでしょう。

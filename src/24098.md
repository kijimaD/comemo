## 変更の背景

この変更の背景には、Goのアセンブラが持つ独特な性質と、それに対するユーザーの理解を深める必要性があります。Goのアセンブラは、一般的なアセンブラとは異なり、Goコンパイラとリンカのパイプラインの一部として機能します。コンパイラは「半抽象的な命令セット」を生成し、リンカが最終的な機械語命令を選択するというプロセスを取ります。このため、アセンブラで記述された `MOV` のような命令が、必ずしも対応する機械語の `MOV` 命令に直接変換されるわけではありません。

`Update #10096` は、Goのアセンブラドキュメントの改善に関するIssueであり、このコミットはそのIssueに対応するものです。ユーザーがGoのアセンブラをより正確に理解し、効果的に使用できるように、特に以下の点について明確化が求められていました。

1.  **定数評価の規則**: Goのアセンブラにおける定数式の評価方法が、C言語のような従来の規則とは異なるため、その違いを明確にする必要がありました。
2.  **擬似レジスタの役割**: `FP`, `PC`, `SB`, `SP` といった擬似レジスタが、ハードウェアレジスタとは異なる抽象的な概念としてどのように機能するかを詳細に説明する必要がありました。特に、`FP` と `SP` の使用法における慣習や、ハードウェア `SP` との区別は混乱を招きやすいため、その明確化が重要でした。
3.  **命令セットの抽象性**: Goのアセンブラが扱う命令が、最終的な機械語命令とどのように異なるのか、その「半抽象的」な性質をより正確に記述する必要がありました。
4.  **新しいTEXTフラグ**: クロージャ関数に関連する新しい `TEXT` フラグ `NEEDCTXT` の導入に伴い、その説明を追加する必要がありました。

これらの背景から、このコミットはGoのアセンブラのドキュメントをより包括的で正確なものにし、開発者がGoの低レベルプログラミングをより効果的に行えるようにするための重要な一歩と言えます。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識があると役立ちます。

1.  **Go言語のアセンブラ**: Go言語は、特定のパフォーマンスが要求される場面や、Goランタイムのコア部分（スケジューラ、ガベージコレクタなど）でアセンブリ言語を使用します。Goのアセンブラは、一般的なアセンブラ（例: GAS, NASM）とは異なる独自の構文とセマンティクスを持っています。これは、Plan 9オペレーティングシステムのアセンブラに強く影響を受けています。
2.  **Plan 9アセンブラ**: Plan 9はベル研究所で開発されたオペレーティングシステムで、そのツールチェインはGo言語のツールチェインに大きな影響を与えました。Plan 9アセンブラは、命令が抽象的であり、特定のCPUアーキテクチャに直接マッピングされない場合があります。リンカが最終的な命令選択を行うという特徴があります。
3.  **Goコンパイラとリンカのパイプライン**: Goのビルドプロセスでは、ソースコードがコンパイラによって中間表現に変換され、その後リンカによって実行可能ファイルが生成されます。Goのアセンブラは、このパイプラインにおいて、コンパイラが生成する「半抽象的な命令セット」を記述するための言語として機能します。リンカは、この半抽象的な命令をターゲットアーキテクチャの具体的な機械語命令に変換する役割を担います。
4.  **擬似レジスタ (Pseudo-registers)**: Goのアセンブラには、ハードウェアレジスタとは別に、コンパイラとリンカによって管理される仮想的なレジスタが存在します。これらは「擬似レジスタ」と呼ばれ、`FP` (Frame Pointer), `PC` (Program Counter), `SB` (Static Base), `SP` (Stack Pointer) があります。これらは、関数引数、ローカル変数、グローバルシンボル、スタックトップへの参照を抽象化するために使用されます。
    *   `SB` (Static Base): グローバルシンボル（関数やグローバル変数）の基準点。`foo(SB)` はグローバルな `foo` シンボルを参照します。
    *   `FP` (Frame Pointer): 関数引数とローカル変数の基準点。`0(FP)` は最初の引数を参照します。
    *   `SP` (Stack Pointer): 現在のスタックフレームのトップを指します。ローカル変数へのアクセスには負のオフセットが使われます。
    *   `PC` (Program Counter): プログラムカウンタ。ジャンプや分岐命令のターゲットとして使用されます。
5.  **`TEXT` ディレクティブとフラグ**: Goのアセンブラでは、`TEXT` ディレクティブを使って関数を定義します。このディレクティブには、関数の特性を示すためのフラグ（例: `NOSPLIT`, `WRAPPER`）を付与できます。

## 技術的詳細

このコミットは `doc/asm.html` ドキュメントに以下の重要な技術的詳細を追加・修正しています。

1.  **定数評価の変更**:
    *   **演算子優先順位**: Goのアセンブラにおける定数式は、Go言語自身の演算子優先順位に従って解析されるようになりました。これは、従来のC言語のような優先順位とは異なります。例として `3&1<<2` は、C言語では `3&(1<<2)` と解析され `0` になりますが、Goアセンブラでは `(3&1)<<2` と解析され `4` になります。
    *   **64ビット符号なし整数**: 定数は常に64ビットの符号なし整数として評価されます。これにより、`-2` のような負の定数は、符号なしの64ビット整数として表現されます。
    *   **曖昧さの排除**: 曖昧さを避けるため、右オペランドの最上位ビットがセットされている場合の除算や右シフトは拒否されます。

2.  **擬似レジスタの詳細な説明**:
    *   **一般的なレジスタ**: `R1` や `LR` のようなレジスタは事前に定義されており、その正確なセットはアーキテクチャに依存することが明記されました。
    *   **4つの擬似レジスタ**: `FP`, `PC`, `SB`, `SP` の4つの擬似レジスタが、すべてのアーキテクチャで共通して存在することが強調され、それぞれの役割が明確にリストアップされました。
        *   `FP`: フレームポインタ。引数とローカル変数。
        *   `PC`: プログラムカウンタ。ジャンプと分岐。
        *   `SB`: 静的ベースポインタ。グローバルシンボル。
        *   `SP`: スタックポインタ。スタックのトップ。
    *   **シンボル参照**: ユーザー定義シンボルは、`FP` (引数とローカル変数) および `SB` (グローバル変数) へのオフセットとして記述されます。
    *   **`SB` のオフセット**: `a+4(SB)` のように、シンボルアドレスからのオフセットで参照できることが示されました。
    *   **`FP` の引数命名規則**: 関数引数を参照する際には、`first_arg+0(FP)` のように名前を付与する慣習が必須となり、`0(FP)` のような名前なしの参照はアセンブラによって拒否されるようになりました。これは、オフセットの意味（フレームポインタからのオフセット）を `SB` との混同を避けるためでもあります。`FP` は常に擬似レジスタであり、ハードウェアレジスタではないことが強調されています。
    *   **`SP` の区別**: ハードウェアレジスタに `SP` という名前が存在するアーキテクチャでは、仮想スタックポインタ (`x-8(SP)`) とハードウェア `SP` (`-8(SP)`) を区別するために名前のプレフィックスが使用されます。
    *   **`SP` と `PC` の特殊性**: `SP` と `PC` が物理的な番号付きレジスタのエイリアスであるマシン（例: ARM）でも、Goアセンブラでは `SP` と `PC` は特別に扱われます。`SP` への参照には `FP` と同様にシンボルが必要です。実際のハードウェアレジスタにアクセスするには、`R13` や `R15` のような真の `R` 名を使用します。

3.  **分岐とジャンプ**:
    *   分岐と直接ジャンプは、常に `PC` へのオフセット、またはラベルへのジャンプとして記述されます。
    *   ラベルは定義された関数内でのみ可視であり、複数の関数で同じラベル名を使用することが許可されます。
    *   直接ジャンプと呼び出し命令は、`name(SB)` のようなテキストシンボルをターゲットにできますが、`name+4(SB)` のようなシンボルからのオフセットはターゲットにできません。

4.  **`TEXT` フラグ `NEEDCTXT` の追加**:
    *   `TEXT` アイテムに対して `NEEDCTXT = 64` フラグが追加されました。これは、関数がクロージャであり、そのインカミングコンテキストレジスタを使用することを示します。

これらの変更は、Goのアセンブラの動作と構文に関する理解を深め、特にGoの低レベルコードを書く開発者にとってのドキュメントの正確性と有用性を大幅に向上させます。

## コアとなるコードの解説

このコミットは、Goのアセンブラのドキュメント `doc/asm.html` を大幅に改善し、特に機械に依存しない側面について、より正確で詳細な情報を提供しています。

主な変更点は以下の通りです。

1.  **導入部分の明確化**:
    *   Plan 9アセンブラへの参照が「elsewhere」（他の場所）とより一般化され、現在のドキュメントがPlan 9ドキュメントとの「違い」を説明するものであることが強調されました。
    *   Goコンパイラが「半抽象的な命令セット」で動作し、命令選択がコード生成後に部分的に行われるという、Goアセンブラの独特な性質がより明確に記述されました。これにより、`MOV` のような命令が必ずしも直接的な機械語命令にマッピングされないという点が理解しやすくなりました。

2.  **`go tool compile -S` の例の改善**:
    *   `GOOS=linux GOARCH=amd64` が追加され、特定のOSとアーキテクチャでのアセンブリ出力の確認方法がより具体的になりました。

3.  **「Constants」（定数）セクションの追加**:
    *   Goアセンブラにおける定数式の評価が、Go言語の演算子優先順位に従うことが明記されました。これにより、C言語の優先順位との違いによる混乱が解消されます。
    *   定数が常に64ビットの符号なし整数として評価されること、および曖昧さを避けるための特定の演算の拒否が説明されました。これは、負の数の表現やビット演算の挙動を理解する上で重要です。

4.  **「Symbols」（シンボル）セクションの拡張と明確化**:
    *   `R1` や `LR` のような一般的なレジスタがアーキテクチャに依存することが示されました。
    *   `FP`, `PC`, `SB`, `SP` の4つの擬似レジスタがすべてのアーキテクチャで共通して存在し、それぞれが何を表すかが明確にリストアップされました。
    *   `SB` を使ったオフセット参照 (`a+4(SB)`) の例が追加され、グローバルシンボルへのアクセス方法がより詳細になりました。
    *   `FP` を使った関数引数参照において、`first_arg+0(FP)` のように名前を付与する慣習が必須となり、名前なしの参照が拒否されることが明記されました。これは、ドキュメントの正確性を高め、ユーザーが正しい慣習に従うことを促します。
    *   仮想 `SP` (`x-8(SP)`) とハードウェア `SP` (`-8(SP)`) の違いが明確に説明され、スタック操作の理解が深まります。
    *   `SP` と `PC` が物理レジスタのエイリアスであるアーキテクチャ（例: ARM）での特殊な扱いが説明され、ハードウェアレジスタへのアクセス方法が示されました。
    *   **分岐とジャンプに関する新しい説明**: ラベルのスコープ（関数内のみ）や、直接ジャンプがテキストシンボルをターゲットにできるが、オフセット付きシンボルはターゲットにできないという重要な制約が追加されました。

5.  **`TEXT` フラグ `NEEDCTXT` の追加**:
    *   クロージャ関数がインカミングコンテキストレジスタを使用することを示す `NEEDCTXT = 64` フラグが追加されました。これは、Goのランタイムとアセンブリコードの連携を理解する上で新しい情報です。

これらの変更は、Goのアセンブラのドキュメントをより網羅的で、正確で、理解しやすいものにすることで、Goの低レベルプログラミングに関わる開発者にとって非常に価値のあるものとなっています。特に、Goアセンブラの独特なセマンティクスや擬似レジスタの挙動に関する詳細な説明は、一般的なアセンブラの知識を持つ開発者がGoアセンブラに移行する際の障壁を低減するのに役立ちます。

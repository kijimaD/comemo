このコミットは、Goコンパイラの内部パッケージである `cmd/internal/gc` 内の `swt.go` ファイルに対する変更です。`swt.go` は、Go言語の `switch` ステートメントの処理、特に抽象構文木（AST）の走査（walking）と型チェック（typechecking）を担当するコードが含まれています。このファイルは、コンパイラがソースコードの `switch` 文をどのように解釈し、中間表現に変換するかを定義する、コンパイラの重要な部分です。

機能的な変更はありません。標準ライブラリで `toolstash -cmp` を使用して確認済みです。

## 変更の背景

このコミットの主な目的は、Goコンパイラ内の `switch` ステートメントを処理するコードの品質と保守性を向上させることです。具体的な背景は以下の通りです。

1.  **コードのイディオマティック化**: 既存のコードは、Go言語の慣習（イディオム）に必ずしも従っていませんでした。特に、グローバル変数の多用や、関連するロジックが散在している点が挙げられます。この変更は、Goらしい構造（例えば、関連するデータと振る舞いを構造体にまとめるなど）に近づけることを目指しています。
2.  **ドキュメントの追加**: コードの理解を深めるために、より詳細なコメントやドキュメントを追加することが目的でした。これにより、将来のメンテナンスや新しい開発者がコードベースを理解する際の障壁が低減されます。
3.  **グローバル変数の削減**: 以前の実装では、`switch` 文の処理に複数のグローバル変数が使用されていました。グローバル変数は、コードの依存関係を不明瞭にし、並行処理の際に競合状態を引き起こす可能性があり、テストを困難にするなど、多くの問題を引き起こす可能性があります。このコミットは、これらのグローバル変数を可能な限り削減し、関連するデータを構造体内にカプセル化することで、コードの健全性を高めています。
4.  **機能変更なしのクリーンアップ**: この変更は、既存の `switch` 文の動作に影響を与えない、純粋なリファクタリングです。`toolstash -cmp` コマンド（Goのツールで、変更前後のコンパイラが生成するバイナリを比較し、機能的な差異がないことを確認するために使用されます）を用いて、標準ライブラリに対するコンパイル結果に違いがないことが確認されています。これは、コードの改善が既存の機能に悪影響を与えないことを保証するための重要なステップです。

これらの変更は、Goコンパイラ全体の品質向上と、長期的な保守性の確保に貢献しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の前提知識があると役立ちます。

### Goコンパイラ (`gc`)

Go言語の公式コンパイラは、通常 `gc` (Go Compiler) と呼ばれます。これはGoツールチェーンの一部であり、Goのソースコードを機械語に変換する役割を担っています。`gc` は複数のステージを経てコンパイルを行います。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Parsing)**: トークンのストリームを解析し、抽象構文木（AST）を構築します。ASTはプログラムの構造を階層的に表現したものです。
3.  **型チェック (Type Checking)**: ASTを走査し、プログラムがGoの型システム規則に準拠しているかを確認します。型の一致、型の互換性、未定義の変数などをチェックします。
4.  **中間表現 (IR) 生成**: ASTを、より低レベルの中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用し、生成されるコードの効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間表現から、ターゲットアーキテクチャの機械語コードを生成します。

このコミットが関連する `swt.go` ファイルは、主に構文解析後のAST走査と型チェックの段階で `switch` 文を処理する部分に属します。

### 抽象構文木 (AST: Abstract Syntax Tree)

ASTは、ソースコードの構造を木構造で表現したデータ構造です。コンパイラはソースコードを直接操作するのではなく、ASTを操作することで、型チェック、最適化、コード生成などの処理を行います。`switch` 文もAST上では特定のノードとして表現され、そのノードの子ノードが `case` 句や `default` 句を表します。

### Goの `switch` ステートメント

Goには主に2種類の `switch` ステートメントがあります。

1.  **式スイッチ (Expression Switch)**:
    `switch` キーワードの後に式が続く形式です。この式の結果が各 `case` の値と比較されます。
    ```go
    switch x {
    case 1:
        // ...
    case 2, 3:
        // ...
    default:
        // ...
    }
    ```
    `switch` の後に式がない場合（`switch {}` または `switch true {}` と同等）は、各 `case` の条件式が評価され、最初に `true` になった `case` が実行されます。

2.  **型スイッチ (Type Switch)**:
    `switch` キーワードの後に型アサーション（`.(type)`）が続く形式です。これはインターフェース変数の動的な型をチェックするために使用されます。
    ```go
    switch v := i.(type) {
    case int:
        // v は int 型
    case string:
        // v は string 型
    case nil:
        // i は nil
    default:
        // v は i の動的な型
    }
    ```
    型スイッチでは、`case` 句に具体的な型やインターフェース型を指定できます。

コンパイラは、これらの `switch` 文を効率的に実行可能なコード（例えば、一連の `if-else if` 文や、定数が多い場合はジャンプテーブル）に変換する必要があります。

### グローバル変数

グローバル変数は、プログラムのどこからでもアクセス可能な変数です。利便性がある一方で、以下のような問題を引き起こす可能性があります。

*   **状態管理の複雑化**: どの関数がいつグローバル変数を変更するのか追跡が難しくなります。
*   **テストの困難さ**: テストの際にグローバル変数の状態をリセットする必要があり、テストの独立性が損なわれる可能性があります。
*   **並行処理の問題**: 複数のゴルーチンが同時にグローバル変数にアクセスすると、競合状態（race condition）が発生し、予期せぬ動作を引き起こす可能性があります。
*   **コードの再利用性の低下**: グローバル変数に依存するコードは、そのグローバル変数が存在しない環境では再利用が困難になります。

このコミットは、これらの問題を軽減するためにグローバル変数を構造体のフィールドとしてカプセル化し、関連するロジックをメソッドとして定義することで、よりクリーンで保守性の高いコードを目指しています。

### イディオマティックなGoコード

「イディオマティックなGoコード」とは、Go言語の設計思想や慣習に沿ったコードのことです。これには以下のような特徴が含まれます。

*   **明示的なエラーハンドリング**: エラーを無視せず、`if err != nil` で明示的に処理します。
*   **シンプルな構造体とインターフェース**: 複雑な継承よりも、シンプルな構造体と小さなインターフェースを組み合わせて使用します。
*   **グローバル状態の最小化**: 可能な限り、関数やメソッドの引数としてデータを渡し、グローバル変数の使用を避けます。
*   **並行処理のGoらしいアプローチ**: ゴルーチンとチャネルを効果的に使用します。
*   **明確な命名**: 変数、関数、構造体などの名前は、その目的を明確に示します。

このコミットは、特に「グローバル状態の最小化」と「シンプルな構造体とインターフェース」の原則に沿って、`switch` 処理コードを改善しています。

## 技術的詳細

このコミットは、Goコンパイラの `switch` 文処理ロジックを大幅にリファクタリングし、より構造化されたオブジェクト指向的なアプローチを導入しています。

### 旧実装の問題点

変更前の `swt.go` は、以下のような課題を抱えていました。

1.  **グローバル変数の多用**:
    *   `var C *Case`: `Case` 構造体のリンクリストの先頭を指すグローバル変数。
    *   `var newlabel_swt_label int`: スイッチ文内で生成されるラベルのカウンタ。
    *   `var exprname *Node`: 式スイッチの対象となる式のノード。
    *   `var hashname *Node`, `var facename *Node`, `var boolname *Node`: 型スイッチの処理に関連する一時変数。
    これらのグローバル変数は、`switch` 文の処理状態を暗黙的に共有しており、コードの理解を困難にし、将来的な並行処理の導入やテストの際に問題を引き起こす可能性がありました。

2.  **`Case` 構造体の限界**:
    `Case` 構造体は、`switch` 文の各 `case` 句を表していましたが、そのフィールド（`type_`、`hash`、`ordinal`）は、式スイッチと型スイッチの両方の情報を混在させていました。また、リンクリストとして管理されており、ソートなどの操作が手動で行われていました。

3.  **手続き型で散在したロジック**:
    `exprswitch` と `typeswitch` という2つの主要な関数が、それぞれ式スイッチと型スイッチの処理を担当していましたが、内部で多くのヘルパー関数（`mkcaselist`, `exprbsw`, `typeone`, `typebsw` など）を呼び出し、グローバル変数に依存していました。これにより、関連するロジックがファイル全体に散在し、全体像を把握しにくくなっていました。ソートロジックも `csort` という汎用的なリンクリストソート関数と、`exprcmp`, `typecmp`, `ordlcmp` といった比較関数を組み合わせて手動で実装されていました。

### 新実装の改善点

このコミットは、上記の課題を解決するために以下の主要な改善を導入しています。

1.  **専用の構造体の導入とカプセル化**:
    *   `exprSwitch` 構造体: 式スイッチの処理に必要な状態（`exprname`、`kind`）をカプセル化します。
    *   `typeSwitch` 構造体: 型スイッチの処理に必要な状態（`hashname`、`facename`、`okname`）をカプセル化します。
    *   `caseClause` 構造体: `Case` 構造体を置き換え、各 `case` 句の情報をより明確に（`node`、`ordinal`、`hash`、`typ`）保持します。`typ` フィールドは `caseKindDefault`, `caseKindExprConst`, `caseKindExprVar`, `caseKindTypeNil`, `caseKindTypeConst`, `caseKindTypeVar` といった新しい定数で、ケースの種類を明確に区別します。
    これにより、グローバル変数のほとんどがこれらの構造体のフィールドに移行され、関連するデータとロジックが密接に結びつけられました。

2.  **メソッドの導入**:
    `exprSwitch` と `typeSwitch` にそれぞれ `walk` メソッドが追加されました。これにより、`switch` 文の走査ロジックがそれぞれの構造体に属するようになり、コードがよりオブジェクト指向的で理解しやすくなりました。例えば、`walkswitch` 関数は、`switch` の種類に応じて `s.walk(sw)` を呼び出すだけになり、ディスパッチの役割に徹します。

3.  **標準ライブラリ `sort` パッケージの活用**:
    以前は手動でリンクリストをソートする `csort` 関数が使用されていましたが、新しい実装では `sort.Sort` インターフェース（`Len()`, `Swap()`, `Less()` メソッドを持つ）を実装した新しい型が導入されました。
    *   `caseClauseByOrd`: `caseClause` を元の出現順序（`ordinal`）でソートします。`default` と `nil` ケースを特別扱いします。
    *   `caseClauseByExpr`: 式スイッチの `caseClause` を、定数値に基づいてソートします。
    *   `caseClauseByType`: 型スイッチの `caseClause` を、型ハッシュと元の出現順序に基づいてソートします。
    これにより、ソートロジックが標準的で効率的な `sort.Sort` に委ねられ、コードの複雑性が軽減されました。

4.  **定数の整理と明確化**:
    旧来の `Snorm`, `Strue`, `Sfalse`, `Stype`, `Tdefault`, `Texprconst`, `Texprvar`, `Ttypenil`, `Ttypeconst`, `Ttypevar` といった定数が、`switchKind*` と `caseKind*` というより明確な命名規則を持つ定数に置き換えられました。これにより、コードの意図がより分かりやすくなりました。

5.  **コードの可読性と保守性の向上**:
    これらの変更により、`switch` 文の処理ロジックがモジュール化され、各部分の役割が明確になりました。グローバル変数の削減と構造体へのカプセル化は、コードの依存関係を減らし、将来的な変更やデバッグを容易にします。

### `toolstash -cmp` について

コミットメッセージにある `toolstash -cmp on the stdlib` は、Go開発における重要な検証ステップです。
`toolstash` は、Goのツールチェーンの変更をテストするためのユーティリティです。
`toolstash -cmp` は、変更前のコンパイラ（またはツール）と変更後のコンパイラ（またはツール）を使用して、同じソースコード（この場合はGoの標準ライブラリ全体）をコンパイルし、生成されたバイナリコードを比較します。
この比較は、バイナリレベルでの同一性を保証するもので、コンパイラの内部的なリファクタリングが、外部から見える動作（生成される実行ファイルの機能やパフォーマンス）に影響を与えていないことを確認するために使用されます。
このコミットが「機能的な変更はない」と明言しているのは、この `toolstash -cmp` による検証が成功したためです。

## コアとなるコードの解説

このコミットのコアとなる変更は、`switch` 文の処理ロジックを、グローバル変数に依存する手続き型のアプローチから、構造体とメソッドを用いたオブジェクト指向的なアプローチへと移行した点にあります。

### `exprSwitch` と `typeSwitch` 構造体

これらの構造体は、それぞれ式スイッチと型スイッチの処理に必要なすべての状態をカプセル化します。

*   **`exprSwitch`**:
    ```go
    type exprSwitch struct {
        exprname *Node // node for the expression being switched on
        kind     int   // kind of switch statement (switchKind*)
    }
    ```
    `exprname` は `switch` の対象となる式（例: `switch x` の `x`）のASTノードを保持します。`kind` は、`switch` が `switch a {...}` のような通常の式スイッチなのか、`switch true {...}` のようなブール値スイッチなのかを区別します。

*   **`typeSwitch`**:
    ```go
    type typeSwitch struct {
        hashname *Node // node for the hash of the type of the variable being switched on
        facename *Node // node for the concrete type of the variable being switched on
        okname   *Node // boolean node used for comma-ok type assertions
    }
    ```
    `hashname` は、型スイッチの対象となるインターフェース変数の動的な型のハッシュ値を保持するノードです。`facename` は、インターフェースの具象型（concrete type）を保持するノードで、`okname` は型アサーション（`v, ok := i.(type)`）の `ok` 部分を保持するノードです。これらのノードは、コンパイラが内部的に生成する一時変数に対応します。

### `walk` メソッド

`exprSwitch` と `typeSwitch` の両方に `walk(sw *Node)` メソッドが追加されました。このメソッドは、それぞれの種類の `switch` 文のASTを走査し、最終的な中間表現（一連の `if-goto` ステートメントなど）を生成する主要なロジックを含んでいます。

例えば、`exprSwitch.walk` は以下の処理を行います。
1.  `switch` 文の対象式を評価し、必要に応じて一時変数に格納します。
2.  `caseClauses` 関数を呼び出して、`switch` 文の各 `case` 句を `caseClause` のスライスとして取得します。
3.  `default` ケースを分離します。
4.  各 `case` 句を処理します。定数式の場合は、効率的なバイナリサーチを可能にするためにソートし、`walkCases` メソッドで `if-goto` のツリーを生成します。非定数式の場合は、線形に処理します。
5.  最終的に生成されたASTノードを `sw.Nbody` に設定します。

`typeSwitch.walk` も同様に、型スイッチに特化したロジックでASTを走査します。

### `caseClause` 構造体とソートロジック

`caseClause` 構造体は、`switch` 文の各 `case` 句の情報を統一的に表現します。

```go
type caseClause struct {
    node    *Node  // points at case statement
    ordinal int    // position in switch
    hash    uint32 // hash of a type switch
    typ     uint8  // type of case
}
```
*   `node`: `case` ステートメント自体のASTノードを指します。
*   `ordinal`: `switch` 文内での `case` 句の元の出現順序を保持します。これは、重複チェック後の最終的なコード生成順序を保証するために重要です。
*   `hash`: 型スイッチの場合に、型のハッシュ値を保持します。これにより、型の一致を効率的にチェックできます。
*   `typ`: `case` 句の種類（`default`, `exprConst`, `exprVar`, `typeNil`, `typeConst`, `typeVar`）を明確に区別します。

ソートロジックは、Goの標準ライブラリ `sort.Sort` インターフェースを利用して実装されました。
*   `caseClauseByOrd`: `ordinal` フィールドに基づいて `caseClause` をソートします。`default` ケースと `nil` ケースは特別に先頭に配置されます。これは、最終的なコード生成の順序を決定するために使用されます。
*   `caseClauseByExpr`: 式スイッチの定数ケースをソートするために使用されます。`exprcmp` ヘルパー関数を用いて、定数値（浮動小数点数、整数、文字列など）に基づいて比較を行います。これにより、コンパイラは定数ケースに対して効率的なバイナリサーチツリーを構築できます。
*   `caseClauseByType`: 型スイッチの具象型ケースをソートするために使用されます。型のハッシュ値と `ordinal` に基づいて比較を行います。

これらのソートロジックにより、コンパイラは `switch` 文の `case` 句を効率的に整理し、線形探索（`if-goto` の連鎖）またはバイナリサーチ（定数が多い場合）のいずれかの最適なコードパスを生成できるようになります。

### `walkCases` メソッド

`exprSwitch` と `typeSwitch` の両方に存在する `walkCases` メソッドは、`caseClause` のスライスを受け取り、それらのケースに対応するASTノード（`if-goto` ステートメントのツリー）を生成します。
*   ケースの数が少ない場合（`binarySearchMin` 未満、デフォルトは4）は、シンプルな線形探索（一連の `if-else if`）を生成します。
*   ケースの数が多い場合は、バイナリサーチツリーを再帰的に生成します。これにより、特に多数の定数ケースを持つ `switch` 文の実行時パフォーマンスが向上します。

これらの変更により、`swt.go` のコードはより構造化され、各部分の役割が明確になり、保守性と拡張性が向上しました。

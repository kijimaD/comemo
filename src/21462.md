# [インデックス 21462] ファイルの概要

このコミットは、Goランタイムのスタック管理に関する変更です。具体的には、スタックキャッシュの「オーダー数」を増やし、より多様なサイズのスタックを効率的に再利用できるようにしています。これにより、スタックの割り当てと解放のオーバーヘッドを削減し、全体的なパフォーマンスを向上させることを目的としています。

## コミット

```
commit 5aae246f1e1c59511a82398d88128e9fc9357107
Author: Keith Randall <khr@golang.org>
Date:   Fri Dec 26 18:10:59 2014 -0800

    runtime: increase number of stack orders to 4

    Cache 2KB, 4KB, 8KB, and 16KB stacks. Larger stacks
    will be allocated directly. There is no point in cacheing
    32KB+ stacks as we ask for and return 32KB at a time
    from the allocator.

    Note that the minimum stack is 8K on windows/64bit and 4K on
    windows/32bit and plan9. For these os/arch combinations,
    the number of stack orders is less so that we have the same
    maximum cached size.

    Fixes #9045
```

## 元コミット内容

Goランタイムにおいて、スタックのキャッシュオーダー数を3から4に増やします。これにより、2KB、4KB、8KB、16KBのスタックをキャッシュできるようになります。これより大きなスタックは直接アロケータから割り当てられます。32KB以上のスタックをキャッシュする意味はありません。なぜなら、アロケータからは一度に32KB単位で要求および返却されるためです。

また、Windows 64bit環境では最小スタックサイズが8KB、Windows 32bitおよびPlan9環境では4KBであることに注意が必要です。これらのOS/アーキテクチャの組み合わせでは、キャッシュされる最大サイズを同じに保つために、スタックオーダー数が少なく設定されます。

この変更はIssue #9045を修正します。

## 変更の背景

Goのランタイムは、ゴルーチン（goroutine）ごとにスタックを割り当てて管理します。スタックは関数呼び出しやローカル変数の保存に使用されるメモリ領域であり、ゴルーチンの実行中に動的にサイズが変更される可能性があります（スタックの伸縮）。スタックの割り当てと解放は、頻繁に発生する操作であり、その効率はGoプログラム全体のパフォーマンスに大きく影響します。

以前のGoランタイムでは、スタックのキャッシュサイズが限定されており、特定のサイズのスタックしか効率的に再利用できませんでした。これにより、キャッシュミスが発生した場合、よりコストのかかる直接的なメモリ割り当てが必要となり、パフォーマンスのボトルネックとなる可能性がありました。

このコミットの背景には、より多様なサイズのスタックを効率的にキャッシュし、再利用することで、スタックの割り当てと解放にかかるオーバーヘッドを削減し、特に多数のゴルーチンが頻繁に生成・消滅するようなワークロードにおいて、Goプログラムの実行効率を向上させるという目的があります。Issue #9045は、このスタックキャッシュの効率性に関する具体的な問題点を指摘していたと考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

1.  **ゴルーチンとスタック**:
    *   **ゴルーチン**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。
    *   **スタック**: 各ゴルーチンは自身のスタックを持っています。スタックは、関数呼び出しの引数、ローカル変数、リターンアドレスなどを格納するために使用されるメモリ領域です。Goのスタックは、必要に応じて自動的に伸縮します（スタックの動的拡張・縮小）。

2.  **スタックの割り当てと解放**:
    *   ゴルーチンが新しく作成される際、初期スタックが割り当てられます。
    *   関数呼び出しが深くなったり、大きなローカル変数が使用されたりすると、スタックが拡張されることがあります。
    *   関数から戻ったり、ゴルーチンが終了したりすると、スタックは解放されるか、再利用のためにキャッシュされます。

3.  **スタックキャッシュ**:
    *   Goランタイムは、頻繁に割り当て・解放されるスタックの効率を上げるために、使用済みのスタックをすぐにOSに返却せず、内部的にキャッシュして再利用します。これにより、OSへのシステムコールを減らし、メモリ割り当てのオーバーヘッドを削減します。
    *   キャッシュされるスタックのサイズは、通常、特定の「オーダー」に基づいて管理されます。例えば、オーダー0は最小サイズ、オーダー1はその2倍、オーダー2はそのさらに2倍、といった具合に、2のべき乗でサイズが増えていくのが一般的です。

4.  **`FixedStack`**:
    *   Goランタイムがゴルーチンに最初に割り当てる最小スタックサイズです。このサイズは、OSやアーキテクチャによって異なる場合があります。例えば、Linux/macOSでは2KB、Windows 64bitでは8KBなどです。この最小サイズが、スタックキャッシュの「オーダー0」の基準となります。

5.  **`ptrSize` と `goos_windows` / `goos_plan9`**:
    *   `ptrSize`: ポインタのサイズ（バイト単位）を表すGoランタイムの定数です。32bitシステムでは4、64bitシステムでは8となります。
    *   `goos_windows`, `goos_plan9`: ビルド時のOSを示すGoランタイムの定数です。Windowsでビルドされた場合は`goos_windows`が1となり、それ以外は0となります。Plan9も同様です。これらは条件付きコンパイルや、OS固有の挙動を調整するために使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムがスタックをキャッシュする際の「オーダー数」を調整することにあります。

以前は、`_NumStackOrders` が `3` に固定されていました。これは、`FixedStack`（最小スタックサイズ）を基準として、`FixedStack * 2^0`, `FixedStack * 2^1`, `FixedStack * 2^2` の3種類のサイズのスタックをキャッシュしていたことを意味します。

このコミットでは、`_NumStackOrders` の値を `4` に変更し、さらにOSとアーキテクチャに応じて動的に調整するロジックが導入されました。

新しい `_NumStackOrders` の計算式は以下の通りです。
`_NumStackOrders = 4 - ptrSize/4*goos_windows - 1*goos_plan9`

この式を各OS/アーキテクチャに適用すると、以下のようになります。

*   **Linux/macOS/BSD (64bit)**:
    *   `FixedStack` = 2KB
    *   `ptrSize` = 8
    *   `goos_windows` = 0, `goos_plan9` = 0
    *   `_NumStackOrders` = `4 - 8/4*0 - 1*0` = `4`
    *   キャッシュされるスタックサイズ: 2KB, 4KB, 8KB, 16KB

*   **Windows (32bit)**:
    *   `FixedStack` = 4KB
    *   `ptrSize` = 4
    *   `goos_windows` = 1, `goos_plan9` = 0
    *   `_NumStackOrders` = `4 - 4/4*1 - 1*0` = `4 - 1*1 - 0` = `3`
    *   キャッシュされるスタックサイズ: 4KB, 8KB, 16KB

*   **Windows (64bit)**:
    *   `FixedStack` = 8KB
    *   `ptrSize` = 8
    *   `goos_windows` = 1, `goos_plan9` = 0
    *   `_NumStackOrders` = `4 - 8/4*1 - 1*0` = `4 - 2*1 - 0` = `2`
    *   キャッシュされるスタックサイズ: 8KB, 16KB

*   **Plan9**:
    *   `FixedStack` = 4KB
    *   `ptrSize` はアーキテクチャによるが、ここでは32bitを想定（4）
    *   `goos_windows` = 0, `goos_plan9` = 1
    *   `_NumStackOrders` = `4 - ptrSize/4*0 - 1*1` = `4 - 0 - 1` = `3`
    *   キャッシュされるスタックサイズ: 4KB, 8KB, 16KB

この調整の目的は、どのOS/アーキテクチャにおいても、キャッシュされるスタックの最大サイズを16KBに統一することです。例えば、Windows 64bitでは`FixedStack`が8KBと大きいため、オーダー数を2に減らすことで、キャッシュされる最大サイズが`8KB * 2^1 = 16KB`となり、他のシステムと整合性が保たれます。

コミットメッセージにあるように、32KB以上のスタックをキャッシュする意味がないのは、Goのアロケータが32KB単位でメモリを管理しているためです。つまり、32KB以上のスタックは、キャッシュするよりも直接アロケータから取得・返却する方が効率的であるという判断です。

## コアとなるコードの変更箇所

`src/runtime/malloc2.go` ファイルの `_NumStackOrders` 定義が変更されています。

```diff
--- a/src/runtime/malloc2.go
+++ b/src/runtime/malloc2.go
@@ -117,7 +117,17 @@ const (

 	// Number of orders that get caching.  Order 0 is FixedStack
 	// and each successive order is twice as large.
-	_NumStackOrders = 3
+	// We want to cache 2KB, 4KB, 8KB, and 16KB stacks.  Larger stacks
+	// will be allocated directly.
+	// Since FixedStack is different on different systems, we
+	// must vary NumStackOrders to keep the same maximum cached size.
+	//   OS               | FixedStack | NumStackOrders
+	//   -----------------+------------+---------------
+	//   linux/darwin/bsd | 2KB        | 4
+	//   windows/32       | 4KB        | 3
+	//   windows/64       | 8KB        | 2
+	//   plan9            | 4KB        | 3
+	_NumStackOrders = 4 - ptrSize/4*goos_windows - 1*goos_plan9
```

## コアとなるコードの解説

変更された行は以下の通りです。

```go
_NumStackOrders = 4 - ptrSize/4*goos_windows - 1*goos_plan9
```

この行は、Goのビルドシステムが提供する定数 `ptrSize`、`goos_windows`、`goos_plan9` を利用して、`_NumStackOrders` の値をコンパイル時に決定します。

*   `ptrSize`: システムのポインタサイズ（バイト単位）。32bitシステムでは4、64bitシステムでは8。
*   `goos_windows`: Windows OSでビルドされている場合は1、それ以外は0。
*   `goos_plan9`: Plan9 OSでビルドされている場合は1、それ以外は0。

この計算式により、各OS/アーキテクチャの `FixedStack` サイズに合わせて `_NumStackOrders` が調整され、結果としてキャッシュされるスタックの最大サイズが16KBに統一されます。

例えば、Windows 64bit環境では `ptrSize` が8、`goos_windows` が1となるため、
`_NumStackOrders = 4 - 8/4*1 - 1*0 = 4 - 2*1 - 0 = 2` と計算されます。
これにより、Windows 64bit環境ではスタックオーダーが2となり、`FixedStack` (8KB) を基準に `8KB * 2^0 = 8KB` と `8KB * 2^1 = 16KB` のスタックがキャッシュされます。

この変更は、Goランタイムが異なるプラットフォームで一貫したスタックキャッシュ戦略を維持しつつ、各プラットフォームの特性（特に最小スタックサイズ）に適応できるようにするための重要な改善です。

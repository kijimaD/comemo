## 変更の背景

Goコンパイラ（`cmd/compile/internal/gc`）の内部では、Go言語の様々な型（構造体、関数、チャネルなど）を表現するために`*Type`構造体が使用されています。この`*Type`構造体には、`Etype`（要素型、`TINT`や`TSTRUCT`などの列挙型）や`Type`（別の`*Type`へのポインタ、例えばスライスやチャネルの要素型、または定義された型の基底型を指す）といったフィールドがあります。

しかし、コンパイラ内部には、Go言語のユーザーが直接扱う型とは異なる、特定の目的のために使われる「擬似型」が存在します。このコミットで言及されている`TCHANARGS`、`TFUNCARGS`、`TDDDFIELD`などがそれにあたります。

*   `TCHANARGS`: チャネル操作（送受信）の引数型を内部的に表現するために使われます。
*   `TFUNCARGS`: 関数型の引数と戻り値を内部的に表現し、例えばそれらの幅（メモリサイズ）を計算するために使われます。
*   `TDDDFIELD`: 可変長引数（`...T`）を内部的に表現するために使われます。

これらの擬似型は、`*Type`構造体の`Type`フィールドを、それが「ラップしている」実際の型を指すために利用していました。しかし、`t.Type`という一般的なフィールド名でアクセスすると、その`Type`フィールドが擬似型によって特別な意味を持つことがコードの読み手には分かりにくいという問題がありました。また、擬似型ではない通常の型に対して`t.Type`をアクセスするのと、擬似型に対してアクセスするのとで、その意図が混同される可能性がありました。

このコミットは、このような擬似型の生成と、それがラップしている型へのアクセスを明示的な専用の関数とメソッドにカプセル化することで、コードの意図を明確にし、型システムの堅牢性を高めることを目的としています。

## 前提知識の解説

### Goコンパイラの型システム (`cmd/compile/internal/gc/type.go`)

Goコンパイラの`gc`パッケージは、Go言語のソースコードを解析し、中間表現を経て最終的な機械語コードを生成する役割を担っています。その中核となるのが型システムであり、`src/cmd/compile/internal/gc/type.go`で定義されている`Type`構造体が、Go言語のあらゆる型を表現します。

`Type`構造体の主要なフィールドは以下の通りです。

*   `Etype EType`: 型の種類（例: `TINT`、`TSTRUCT`、`TFUNC`、`TCHAN`）。`EType`は列挙型で、Go言語のプリミティブ型から複合型まで多岐にわたる種類を定義しています。
*   `Type *Type`: 多くの複合型において、その「要素」となる型を指します。例えば、`[]int`のスライス型であれば、`Type`フィールドは`int`型を指します。`*chan int`のチャネル型であれば、`Type`フィールドは`int`型を指します。

### 擬似型 (Pseudo-types)

Goコンパイラ内部には、Go言語の仕様には直接現れないが、コンパイラの処理を効率的かつ構造的に行うために導入された「擬似型」と呼ばれる特殊な`Etype`が存在します。これらは主に、特定の複合型の内部構造や、コンパイラが一時的に必要とする型情報を表現するために使われます。

*   `TCHANARGS`: チャネルの送受信操作に関連する型情報を一時的に保持するために使用されます。例えば、チャネルの要素型のサイズを計算する際などに利用されます。
*   `TFUNCARGS`: 関数の引数と戻り値のリストを一つの型として扱うために使用されます。これにより、関数のシグネチャ全体のメモリレイアウトやアラインメントの計算が容易になります。
*   `TDDDFIELD`: 可変長引数（`...T`）を持つ関数の引数を表現するために使用されます。Goの可変長引数は、内部的にはスライスとして扱われますが、コンパイラがその特殊性を認識するためにこの擬似型が使われます。

これらの擬似型は、`Type`構造体の`Type`フィールドを「ラップされた型」として利用することで、その擬似型が参照する実際の型を保持していました。

## 技術的詳細

このコミットの核心は、擬似型（`TCHANARGS`, `TFUNCARGS`, `TDDDFIELD`）の取り扱いを改善することにあります。

### `typWrapper`関数の導入

以前は、擬似型を生成する際に、まず`typ(EType)`で基本的な`Type`構造体を作成し、その後`t.Type = wrappedType`のように手動でラップする型を割り当てていました。

**変更前:**
```go
t1 := typ(TCHANARGS)
t1.Type = t
```

このアプローチは、`Type`フィールドが擬似型にとって特別な意味を持つことをコードの読み手に伝えにくく、また誤って他の目的で`Type`フィールドが使われる可能性がありました。

**変更後:**
```go
t1 := typWrapper(TCHANARGS, t)
```

新しく導入された`typWrapper`関数は、擬似型（`TCHANARGS`, `TFUNCARGS`, `TDDDFIELD`）専用のコンストラクタとして機能します。この関数は、指定された`EType`とラップする`*Type`を受け取り、適切な`Type`構造体を生成して返します。`typWrapper`は、引数として受け取った`EType`が擬似型であることを厳密にチェックし、それ以外の`EType`が渡された場合には`Fatalf`でパニックを起こします。これにより、擬似型の生成が意図された方法でのみ行われることが保証され、型安全性が向上します。

### `Type.Wrapped()`メソッドの導入

同様に、擬似型がラップしている型にアクセスする際も、以前は`t.Type`を直接参照していました。

**変更前:**
```go
t1 := t.Type
```

**変更後:**
```go
t1 := t.Wrapped()
```

`Type.Wrapped()`メソッドは、`*Type`構造体が擬似型である場合に、それがラップしている型を返す専用のアクセサです。このメソッドもまた、レシーバの`Etype`が`TCHANARGS`, `TFUNCARGS`, `TDDDFIELD`のいずれかであることをチェックし、そうでなければ`Fatalf`でパニックを起こします。これにより、擬似型がラップしている型へのアクセスが明示的になり、コードの意図が明確になります。また、擬似型ではない通常の型に対して誤って`Wrapped()`メソッドが呼び出されることを防ぎます。

### 変更のメリット

1.  **意図の明確化:** `typWrapper`と`Type.Wrapped()`を使用することで、コードの読み手は、その型が特定の擬似型であり、別の型をラップしているという意図をすぐに理解できます。
2.  **型安全性の向上:** 専用のコンストラクタとアクセサが導入されたことで、擬似型が誤った方法で生成されたり、その内部の`Type`フィールドが誤って解釈されたりするリスクが減少します。`Fatalf`による厳密なチェックは、開発段階でのバグの早期発見に貢献します。
3.  **保守性の向上:** 擬似型の生成とアクセスに関するロジックが一箇所に集約されるため、将来的にこれらの擬似型の挙動を変更する必要が生じた場合でも、影響範囲が限定され、変更が容易になります。
4.  **コードの一貫性:** コンパイラ内部の型システム全体で、擬似型の取り扱いに関する一貫したパターンが確立されます。

## コアとなるコードの解説

### `typWrapper`関数

```go
// typWrapper returns a new wrapper psuedo-type.
func typWrapper(et EType, wrapped *Type) *Type {
	switch et {
	case TCHANARGS, TFUNCARGS, TDDDFIELD:
	default:
		Fatalf("typWrapper bad etype %s", et)
	}
	t := typ(et)
	t.Type = wrapped
	return t
}
```

*   **目的**: 指定された`EType`（擬似型）と、それがラップする`*Type`を受け取り、新しい擬似型`*Type`を生成して返します。
*   **引数**:
    *   `et EType`: 生成する擬似型の種類（例: `TCHANARGS`）。
    *   `wrapped *Type`: 擬似型がラップする実際の型。
*   **処理**:
    1.  `switch et`: `et`が`TCHANARGS`, `TFUNCARGS`, `TDDDFIELD`のいずれかであることを確認します。これら以外の`EType`が渡された場合、`Fatalf`を呼び出してプログラムを終了させます。これにより、`typWrapper`が意図された擬似型のみを生成することが保証されます。
    2.  `t := typ(et)`: 基本的な`Type`構造体を`et`で初期化して作成します。この時点では`t.Type`フィールドはまだ設定されていません。
    3.  `t.Type = wrapped`: 作成した`Type`構造体の`Type`フィールドに、引数で渡された`wrapped`型を割り当てます。これが、擬似型がラップする型となります。
    4.  `return t`: 生成された擬似型を返します。

### `Type.Wrapped()`メソッド

```go
// Wrapped returns the type that pseudo-type t wraps.
func (t *Type) Wrapped() *Type {
	switch t.Etype {
	case TCHANARGS, TFUNCARGS, TDDDFIELD:
	default:
		Fatalf("Type.Wrapped %s", t.Etype)
	}
	return t.Type
}
```

*   **目的**: レシーバである`*Type`が擬似型である場合に、それがラップしている型を返します。
*   **レシーバ**: `t *Type`: ラップされた型を取得したい擬似型。
*   **処理**:
    1.  `switch t.Etype`: レシーバ`t`の`Etype`が`TCHANARGS`, `TFUNCARGS`, `TDDDFIELD`のいずれかであることを確認します。これら以外の`EType`を持つ型に対して`Wrapped()`が呼び出された場合、`Fatalf`を呼び出してプログラムを終了させます。これにより、`Wrapped()`メソッドが擬似型に対してのみ呼び出されることが保証されます。
    2.  `return t.Type`: レシーバ`t`の`Type`フィールドの値を返します。この値が、擬似型がラップしている実際の型です。

これらの変更により、Goコンパイラの内部型システムにおける擬似型の取り扱いがより堅牢で、意図が明確なものになりました。

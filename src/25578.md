    runtime: replace traceBuf slice with index
    
    Currently traceBuf keeps track of where it is in the trace buffer by
    also maintaining a slice that points in to this buffer with an initial
    length of 0 and a cap of the length of the array. All writes to this
    buffer are done by appending to the slice (as long as the bounds
    checks are right, it will never overflow and the append won't allocate
    a new slice).
    
    Each of these appends generates a write barrier. As long as we never
    overflow the buffer, this write barrier won't fire, but this wreaks
    havoc with eliminating write barriers from the tracing code. If we
    were to overflow the buffer, this would both allocate and invoke a
    write barrier, both things that are dicey at best to do in many of the
    contexts tracing happens. It also wastes space in the traceBuf and
    leads to more complex code and more complex generated code.
    
    Replace this slice trick with keeping track of a simple array
    position.

## 変更の背景
Goランタイムのトレーシング機能は、プログラムの実行状況を詳細に記録するために使用されます。このトレーシングは、パフォーマンス分析やデバッグにおいて非常に重要です。しかし、トレーシングコード自体がパフォーマンスに影響を与えては本末転倒です。

このコミット以前の`traceBuf`の実装では、トレースデータをバッファに書き込む際にGoのスライス（`[]byte`）を使用していました。具体的には、固定サイズの`arr`というバイト配列を基盤とし、その配列を指すスライス`buf`を`traceBufHeader`構造体内に保持していました。データ書き込みは、この`buf`スライスへの`append`操作によって行われていました。

問題は、Goの`append`操作が潜在的にライトバリア（Write Barrier）を発生させる点にありました。ライトバリアは、ガベージコレクタが正確に動作するために、ヒープ上のポインタの変更を追跡するメカニズムです。`append`は、スライスの容量が不足した場合に新しい基盤配列を割り当て、古い配列から要素をコピーするという動作をします。この新しい配列の割り当てやポインタの更新は、ガベージコレクタにとって重要なイベントであり、ライトバリアをトリガーする可能性があります。

トレーシングコードは、ガベージコレクション（GC）の動作を監視したり、GC中に実行されたりすることがあります。このようなクリティカルなコンテキストでライトバリアが発生すると、GCの動作を妨げたり、デッドロックを引き起こしたり、予期せぬパフォーマンスの低下を招いたりするリスクがありました。特に、トレースバッファが予期せずオーバーフローして新しいスライスが割り当てられるような状況では、ライトバリアとメモリ割り当ての両方が発生し、トレーシングの信頼性と効率に深刻な影響を与える可能性がありました。

また、スライスを保持する「トリック」は、コードを複雑にし、`traceBuf`構造体内で余分なスペースを消費していました。このコミットは、これらの問題を解決し、トレーシングコードをよりシンプルで効率的、かつライトバリアフリーにすることを目指しています。

## 前提知識の解説

### Goのスライス (Slice)
Goのスライスは、配列をラップした動的なビューです。スライスは、基盤となる配列、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。
-   **基盤配列**: スライスが参照する実際のデータが格納されている配列。
-   **長さ (len)**: スライスに含まれる要素の数。
-   **容量 (cap)**: スライスの基盤配列が保持できる要素の最大数。

`append`関数は、スライスに要素を追加するために使用されます。`append`は、現在のスライスの容量が十分であれば、基盤配列の既存のスペースに要素を追加し、スライスの長さを更新します。容量が不足している場合、`append`はより大きな新しい基盤配列を割り当て、既存の要素を新しい配列にコピーし、新しいスライスを返します。

### Goのガベージコレクション (Garbage Collection) とライトバリア (Write Barrier)
Goは、自動メモリ管理のためにガベージコレクタ（GC）を使用します。GCは、プログラムが不要になったメモリを自動的に解放し、メモリリークを防ぎます。GoのGCは、並行（concurrent）かつ低遅延（low-latency）で動作するように設計されています。

ライトバリアは、ガベージコレクタが正確に動作するために使用される技術の一つです。これは、ヒープ上のポインタが変更されるたびに実行される小さなコードスニペットです。ライトバリアの主な目的は、GCがオブジェクトグラフを走査している最中に、プログラムがポインタを変更することでGCが見落とす可能性のあるオブジェクトを追跡することです。

GoのGCは、三色マーク・アンド・スイープ（Tri-color mark-and-sweep）アルゴリズムの変種を使用しています。このアルゴリズムでは、オブジェクトは白、灰色、黒のいずれかの色でマークされます。
-   **白**: まだGCによって到達可能かどうかが判断されていないオブジェクト（最終的に回収される可能性がある）。
-   **灰色**: 到達可能であることがわかっているが、その参照先がまだ走査されていないオブジェクト。
-   **黒**: 到達可能であることがわかっており、その参照先もすべて走査済みのオブジェクト。

ライトバリアは、黒のオブジェクトから白のオブジェクトへのポインタの変更を検出するために使用されます。このような変更が発生した場合、ライトバリアは白のオブジェクトを灰色にマークし、GCがそのオブジェクトを見落とさないようにします。

ライトバリアはGCの正確性を保証するために不可欠ですが、その実行にはオーバーヘッドが伴います。そのため、GCのパフォーマンスを向上させるためには、ライトバリアの発生回数を減らすことが望ましいとされています。

### Goランタイムのトレーシング (Tracing)
Goランタイムのトレーシング機能は、Goプログラムの実行中に発生する様々なイベント（GCの開始/終了、ゴルーチンのスケジューリング、システムコールなど）を記録するメカニズムです。これらのイベントはトレースバッファに書き込まれ、後で`go tool trace`コマンドなどを使って可視化・分析することができます。トレーシングは、Goプログラムのパフォーマンス特性を理解し、ボトルネックを特定するために非常に強力なツールです。

トレーシングコードは、ランタイムの非常に低レベルな部分で動作し、GCの内部動作にも深く関わっています。そのため、トレーシングコード自体がGCに悪影響を与えないように、特に注意深く設計される必要があります。

## 技術的詳細
このコミットの核心は、`traceBufHeader`構造体の`buf []byte`フィールドを`pos int`フィールドに置き換えることです。

**変更前:**
`traceBufHeader`構造体は、トレースデータを格納するための固定サイズのバイト配列`arr`と、その`arr`を指すスライス`buf`を持っていました。
```go
type traceBufHeader struct {
    // ...
    buf       []byte                  // trace data, always points to traceBuf.arr
    // ...
}
```
データは`buf`スライスに対して`append`操作を使って書き込まれていました。コミットメッセージによると、この`buf`スライスは`arr`の先頭を指し、初期の長さは0、容量は`arr`の長さと同じに設定されていました。これにより、`append`操作が新しい基盤配列を割り当てることなく、`arr`の既存のスペースにデータを書き込むことが期待されていました。

しかし、`append`関数は、たとえ新しいメモリ割り当てが発生しない場合でも、その内部ロジックによってライトバリアを生成する可能性があります。これは、`append`がスライスの基盤配列や長さを変更する際に、ポインタの変更を伴う可能性があるためです。トレーシングコードはGCの動作を監視するようなクリティカルなコンテキストで実行されるため、このようなライトバリアの発生は望ましくありませんでした。特に、バッファが予期せずオーバーフローした場合、新しいメモリ割り当てとそれに伴うライトバリアが確実に発生し、ランタイムの安定性やパフォーマンスに悪影響を与える可能性がありました。

**変更後:**
`buf []byte`フィールドは`pos int`フィールドに置き換えられました。
```go
type traceBufHeader struct {
    // ...
    pos       int                     // next write offset in arr
    // ...
}
```
`pos`は、`arr`配列内の次に書き込むべき位置（オフセット）を示す単純な整数インデックスです。データ書き込みは、`arr[pos] = value; pos++`のような直接的な配列アクセスとインデックスのインクリメントによって行われるようになりました。

この変更により、以下の利点が得られます。
1.  **ライトバリアの排除**: `append`操作が完全に排除されたため、それに伴うライトバリアの発生がなくなりました。これにより、トレーシングコードがGCの動作に与える影響が最小限に抑えられ、より予測可能で効率的な動作が保証されます。
2.  **コードの簡素化**: スライスを「トリック」として使用する複雑さがなくなり、単純なインデックス管理に置き換えられたことで、コードがより理解しやすくなりました。
3.  **スペースの節約**: `traceBufHeader`構造体内でスライスヘッダ（基盤配列へのポインタ、長さ、容量）を保持する必要がなくなり、わずかながらメモリ使用量が削減されます。
4.  **オーバーフロー検出の明確化**: `len(buf.arr)-buf.pos < maxSize`のような明確な条件でバッファの空き容量をチェックできるようになり、オーバーフローの検出とハンドリングがより直接的になりました。

この変更は、Goランタイムのトレーシングメカニズムの堅牢性とパフォーマンスを向上させるための重要な改善です。

## コアとなるコードの解説

このコミットの主要な変更は、`traceBufHeader`構造体内の`buf []byte`スライスを`pos int`インデックスに置き換えることで、トレースバッファへのデータ書き込み方法を根本的に変更した点にあります。

-   **`traceBufHeader`構造体**:
    -   以前は`buf []byte`がトレースデータの現在のビューを保持していました。これは`traceBuf.arr`という固定サイズの配列を基盤とするスライスでした。
    -   変更後は`pos int`が導入され、これは`traceBuf.arr`配列内の次に書き込むべきバイトのオフセットを示します。これにより、スライスヘッダを維持する必要がなくなり、メモリ効率が向上し、コードが簡素化されます。

-   **データ書き込みロジックの変更**:
    -   以前は、`traceEvent`関数や`traceStackTable.dump`関数内で、`data = append(data, ...)` の形式でデータがバッファに書き込まれていました。この`append`操作がライトバリアを発生させる可能性がありました。
    -   変更後は、`traceBuf`型に新しく追加された`varint`メソッドと`byte`メソッドが使用されます。
        -   `func (buf *traceBuf) varint(v uint64)`: `v`を可変長整数として`buf.arr`に書き込み、`buf.pos`を更新します。可変長整数エンコーディングは、小さな数値を効率的に表現するために使用され、トレースデータのサイズを削減するのに役立ちます。
        -   `func (buf *traceBuf) byte(v byte)`: 単一のバイト`v`を`buf.arr[buf.pos]`に書き込み、`buf.pos`をインクリメントします。
    -   これらのメソッドは、直接`buf.arr`配列と`buf.pos`インデックスを操作するため、Goの`append`関数が持つライトバリアのオーバーヘッドを完全に回避できます。これにより、トレーシングコードがGCの動作に与える影響が最小限に抑えられます。

-   **バッファの空き容量チェック**:
    -   以前は`cap(buf.buf)-len(buf.buf) < maxSize`というスライスベースのチェックが行われていました。
    -   変更後は`len(buf.arr)-buf.pos < maxSize`という、より直接的な配列の長さと現在の書き込み位置に基づくチェックに変わりました。これは、`arr`が固定サイズの配列であるため、その長さは`len(buf.arr)`で取得でき、`pos`が現在の書き込み位置を示すため、残りの空き容量を正確に計算できます。

-   **バッファのリセット**:
    -   `traceFlush`関数では、バッファを再利用する際に、以前は`bufp.buf = bufp.arr[:0]`としてスライスの長さを0にリセットしていました。
    -   変更後は`bufp.pos = 0`とすることで、インデックスを0にリセットするだけで済み、よりシンプルかつ効率的です。

このコミットは、Goランタイムのトレーシングメカニズムにおいて、パフォーマンスと信頼性を向上させるための重要な最適化です。ライトバリアの排除は、特にGCと密接に関連するランタイムコードにおいて、デッドロックや予期せぬ遅延を防ぐ上で非常に価値があります。

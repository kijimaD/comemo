# [インデックス 22027] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における作業ポインタの管理を抽象化するための、高レベルなプロデューサー/コンシューマー抽象化を導入します。これにより、GCコードの複雑性が軽減され、将来的なGCワークバッファの利用方法の変更が容易になります。

## 変更の背景

Goのガベージコレクタ（GC）は、メモリ管理の効率性と低レイテンシを追求するために継続的に進化しています。このコミット以前は、GCの内部で「ワークバッファ」と呼ばれる、GCがスキャンすべきオブジェクトへのポインタを格納するバッファの操作が、低レベルかつ明示的に行われていました。これは、GCコードの複雑性を増大させ、将来的なGCアルゴリズムの改善や最適化を困難にする可能性がありました。

この変更の主な背景は以下の通りです。

1.  **GCコードの簡素化**: ワークバッファの充填、排出、シャッフルといった詳細な操作を抽象化することで、GCコード全体の可読性と保守性を向上させること。
2.  **GCワークバッファ利用の柔軟性向上**: ワークバッファの利用方法を変更する際の障壁を取り除くこと。具体的には、`work.partial`キューの利用方法の改善、FIFO（先入れ先出し）ルックアヘッドキャッシュの再導入、プリフェッチ機能の追加、デュアルバッファの使用による「フラッピング」（バッファの頻繁な切り替え）の回避などが挙げられています。
3.  **将来のGC改善への道筋**: この抽象化層を導入することで、今後のGCアルゴリズムの進化やパフォーマンス最適化のための基盤を構築すること。

このコミット自体は既存のコードの動作を変更するものではなく、次のコミットで実際のGCがこの新しい抽象化を利用するように切り替わるための準備段階として位置づけられています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクタの基本的な概念と、並行GCにおける「ワークバッファ」の役割について理解しておく必要があります。

### Goのガベージコレクタ（GC）

GoのGCは、主に以下の特徴を持つ「並行トライカラーマーク＆スイープ」方式を採用しています。

*   **トライカラーマーキング (Tri-color Marking)**: オブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって到達可能かどうかが判断されていないオブジェクト。GCサイクルの開始時にはすべてのオブジェクトが白です。
    *   **灰 (Grey)**: 到達可能であることが判明したが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。ワークキューに置かれます。
    *   **黒 (Black)**: 到達可能であり、かつそのオブジェクトが参照するすべてのオブジェクトがスキャン済みであるオブジェクト。
*   **マークフェーズ (Mark Phase)**: ルート（グローバル変数、スタック上のポインタなど）から到達可能なオブジェクトを特定するフェーズです。このフェーズはアプリケーションのゴルーチンと並行して実行されます（並行マーク）。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（白のままの）オブジェクトを解放し、メモリを再利用するフェーズです。
*   **ライトバリア (Write Barrier)**: 並行マーク中にアプリケーションがポインタを変更した場合に、GCの正確性を保つためのメカニズムです。オブジェクトへのポインタが変更される際に、GCがその変更を検知し、必要に応じてオブジェクトの色を調整します。これにより、GCがオブジェクトグラフをスキャンしている最中に、アプリケーションがオブジェクトの参照関係を変更しても、GCが誤って到達可能なオブジェクトを解放してしまうことを防ぎます。

### GCワークバッファとプロデューサー/コンシューマーモデル

Goの並行GCでは、マークフェーズ中にスキャンすべきオブジェクト（灰色のオブジェクト）を効率的に処理するために「ワークバッファ」が使用されます。

*   **プロデューサー (Producer)**: GCのマークフェーズにおいて、ルートスキャン、スタックスキャン、オブジェクトスキャン、ライトバリアなどによって、新たに到達可能であることが判明したオブジェクト（灰色になったオブジェクト）をワークバッファに追加する役割を担います。
*   **コンシューマー (Consumer)**: ワークバッファから灰色オブジェクトを取り出し、そのオブジェクトをスキャンして参照先のオブジェクトを特定し、それらを灰色にする（ワークバッファに追加する）役割を担います。スキャンが完了したオブジェクトは黒になります。

このプロデューサー/コンシューマーモデルにより、複数のGCワーカーゴルーチンが並行してワークバッファからオブジェクトを取得し、処理を進めることができます。ワークバッファは、GCワーカー間の作業の分散と負荷分散を可能にする重要なデータ構造です。

従来のGCワークバッファの操作は、低レベルなポインタ操作やバッファの充填/排出ロジックがGCコードの様々な場所に散らばっており、これが複雑性の原因となっていました。

## 技術的詳細

このコミットは、GCワークバッファの操作を抽象化するために、`gcWorkProducer`と`gcWork`という2つの新しいGo構造体を導入します。これらは、GCがスキャンすべきオブジェクトへのポインタ（灰色オブジェクト）を扱うための高レベルなインターフェースを提供します。

### `wbufptr` 型

`wbufptr`は`uintptr`のエイリアスであり、`*workbuf`へのポインタを保持します。この型が導入された主な理由は、`workbuf`がヒープ上に存在しない（GCの対象外である）ため、`workbuf`へのポインタに対するライトバリアが不要であり、かつGC中にライトバリアが危険である可能性があるためです。`wbufptrOf`関数と`ptr`メソッドは、`wbufptr`と`*workbuf`間の変換を安全に行うためのヘルパーです。

```go
// A wbufptr holds a workbuf*, but protects it from write barriers.
// workbufs never live on the heap, so write barriers are unnecessary.
// Write barriers on workbuf pointers may also be dangerous in the GC.
type wbufptr uintptr

func wbufptrOf(w *workbuf) wbufptr {
	return wbufptr(unsafe.Pointer(w))
}

func (wp wbufptr) ptr() *workbuf {
	return (*workbuf)(unsafe.Pointer(wp))
}
```

### `gcWorkProducer` 構造体

`gcWorkProducer`は、GCに作業（スキャンすべきオブジェクトへのポインタ）を「生産」するためのインターフェースを提供します。

```go
type gcWorkProducer struct {
	// Invariant: wbuf is never full or empty
	wbuf wbufptr
}
```

主なメソッドは以下の通りです。

*   `initFromCache()`: このM（論理プロセッサ）の`currentwbuf`キャッシュからワークを取得して初期化します。
*   `put(obj uintptr)`: GCがトレースすべきポインタ（`obj`）をキューに入れます。内部的には、現在のワークバッファ（`wbuf`）にオブジェクトを追加し、ワークバッファが満杯になった場合はグローバルキューに`putfull`し、新しいワークバッファを取得します。
*   `dispose()`: キャッシュされているポインタをグローバルキューに返します。部分的に満たされたワークバッファは`putpartial`で返されます。
*   `disposeToCache()`: キャッシュされているポインタをこのMの`currentwbuf`に返します。`currentwbuf`が既に非nilの場合はパニックします。

### `gcWork` 構造体

`gcWork`は、GCに作業を「生産」するだけでなく、「消費」するためのインターフェースも提供します。`gcWorkProducer`を埋め込んでいるため、`gcWorkProducer`のすべてのメソッドも利用できます。

```go
type gcWork struct {
	gcWorkProducer
}
```

主なメソッドは以下の通りです。

*   `tryGet() uintptr`: GCがトレースすべきポインタをキューから取り出そうとします。この`gcWork`インスタンスまたはグローバルキューにポインタが残っていない場合、0を返します。他の`gcWork`インスタンスやキャッシュにはポインタが残っている可能性があります。
*   `get() uintptr`: GCがトレースすべきポインタをキューから取り出します。必要であればブロックし、すべてのキューとキャッシュからすべてのポインタが取得されたことを確認します。ポインタが残っていない場合は0を返します。
*   `dispose()`: キャッシュされているポインタをグローバルキューに返します。`gcWorkProducer`の`dispose`とは異なり、`putfull`を使用してワークバッファをグローバルキューに戻します。これは、コンシューマーのキューに残しておくべきであるという意図があるためです。
*   `balance()`: この`gcWork`にキャッシュされている一部の作業をグローバルキューに戻します。これにより、ワークの偏りを解消し、他のGCワーカーが作業を見つけやすくします。

### 内部動作の抽象化

これらの構造体とメソッドは、GCワークバッファの以下の内部詳細を抽象化します。

*   **バッファの充填と排出**: `put`メソッドは、ワークバッファが満杯になったときに自動的にグローバルキューに渡し、新しいバッファを取得します。`tryGet`や`get`メソッドは、ワークバッファが空になったときに自動的にグローバルキューから新しいバッファを取得します。
*   **バッファのシャッフル**: `balance`メソッドは、ローカルにキャッシュされたワークバッファの一部をグローバルキューに戻すことで、ワークの分散を助けます。
*   **部分的なキューの管理**: `work.partial`キューの利用方法を改善する基盤となります。
*   **キャッシュの利用**: 各M（論理プロセッサ）がローカルにワークバッファをキャッシュすることで、グローバルな競合を減らします。

この抽象化により、GCのコードはワークバッファの低レベルな管理から解放され、より高レベルなGCロジックに集中できるようになります。

### `src/runtime/mgcwork.go` の新規追加

このファイルは完全に新規に追加されたもので、GCワーク抽象化の核心となる`wbufptr`、`gcWorkProducer`、`gcWork`の各型とそれらのメソッドが定義されています。

```go
// Garbage collector work pool abstraction.
//
// This implements a producer/consumer model for pointers to grey
// objects.  A grey object is one that is marked and on a work
// queue.  A black object is marked and not on a work queue.
//
// Write barriers, root discovery, stack scanning, and object scanning
// produce pointers to grey objects.  Scanning consumes pointers to
// grey objects, thus blackening them, and then scans them,
// potentially producing new pointers to grey objects.

// A wbufptr holds a workbuf*, but protects it from write barriers.
// workbufs never live on the heap, so write barriers are unnecessary.
// Write barriers on workbuf pointers may also be dangerous in the GC.
type wbufptr uintptr

func wbufptrOf(w *workbuf) wbufptr {
	return wbufptr(unsafe.Pointer(w))
}

func (wp wbufptr) ptr() *workbuf {
	return (*workbuf)(unsafe.Pointer(wp))
}

// A gcWorkProducer provides the interface to produce work for the
// garbage collector.
//
// The usual pattern for using gcWorkProducer is:
//
//     var gcw gcWorkProducer
//     .. call gcw.put() ..
//     gcw.dispose()
type gcWorkProducer struct {
	// Invariant: wbuf is never full or empty
	wbuf wbufptr
}

// A gcWork provides the interface to both produce and consume work
// for the garbage collector.
//
// The pattern for using gcWork is the same as gcWorkProducer.
type gcWork struct {
	gcWorkProducer
}

// Note that there is no need for a gcWorkConsumer because everything
// that consumes pointers also produces them.

// initFromCache fetches work from this M's currentwbuf cache.
//go:nowritebarrier
func (w *gcWorkProducer) initFromCache() {
	// TODO: Instead of making gcWorkProducer pull from the
	// currentwbuf cache, use a gcWorkProducer as the cache and
	// make shade pass around that gcWorkProducer.
	if w.wbuf == 0 {
		w.wbuf = wbufptr(xchguintptr(&getg().m.currentwbuf, 0))
	}
}

// put enqueues a pointer for the garbage collector to trace.
//go:nowritebarrier
func (ww *gcWorkProducer) put(obj uintptr) {
	w := (*gcWorkProducer)(noescape(unsafe.Pointer(ww))) // TODO: remove when escape analysis is fixed

	wbuf := w.wbuf.ptr()
	if wbuf == nil {
		wbuf = getpartialorempty(42)
		w.wbuf = wbufptrOf(wbuf)
	}

	wbuf.obj[wbuf.nobj] = obj
	wbuf.nobj++

	if wbuf.nobj == uintptr(len(wbuf.obj)) {
		putfull(wbuf, 50)
		w.wbuf = 0
	}
}

// dispose returns any cached pointers to the global queue.
//go:nowritebarrier
func (w *gcWorkProducer) dispose() {
	if wbuf := w.wbuf; wbuf != 0 {
		putpartial(wbuf.ptr(), 58)
		w.wbuf = 0
	}
}

// disposeToCache returns any cached pointers to this M's currentwbuf.
// It calls throw if currentwbuf is non-nil.
//go:nowritebarrier
func (w *gcWorkProducer) disposeToCache() {
	if wbuf := w.wbuf; wbuf != 0 {
		wbuf = wbufptr(xchguintptr(&getg().m.currentwbuf, uintptr(wbuf)))
		if wbuf != 0 {
			throw("m.currentwbuf non-nil in disposeToCache")
		}
		w.wbuf = 0
	}
}

// tryGet dequeues a pointer for the garbage collector to trace.
//
// If there are no pointers remaining in this gcWork or in the global
// queue, tryGet returns 0.  Note that there may still be pointers in
// other gcWork instances or other caches.
//go:nowritebarrier
func (ww *gcWork) tryGet() uintptr {
	w := (*gcWork)(noescape(unsafe.Pointer(ww))) // TODO: remove when escape analysis is fixed

	wbuf := w.wbuf.ptr()
	if wbuf == nil {
		wbuf = trygetfull(74)
		if wbuf == nil {
			return 0
		}
		w.wbuf = wbufptrOf(wbuf)
	}

	wbuf.nobj--
	obj := wbuf.obj[wbuf.nobj]

	if wbuf.nobj == 0 {
		putempty(wbuf, 86)
		w.wbuf = 0
	}

	return obj
}

// get dequeues a pointer for the garbage collector to trace, blocking
// if necessary to ensure all pointers from all queues and caches have
// been retrieved.  get returns 0 if there are no pointers remaining.
//go:nowritebarrier
func (ww *gcWork) get() uintptr {
	w := (*gcWork)(noescape(unsafe.Pointer(ww))) // TODO: remove when escape analysis is fixed

	wbuf := w.wbuf.ptr()
	if wbuf == nil {
		wbuf = getfull(103)
		if wbuf == nil {
			return 0
		}
		wbuf.checknonempty()
		w.wbuf = wbufptrOf(wbuf)
	}

	// TODO: This might be a good place to add prefetch code

	wbuf.nobj--
	obj := wbuf.obj[wbuf.nobj]

	if wbuf.nobj == 0 {
		putempty(wbuf, 115)
		w.wbuf = 0
	}

	return obj
}

// dispose returns any cached pointers to the global queue.
//go:nowritebarrier
func (w *gcWork) dispose() {
	if wbuf := w.wbuf; wbuf != 0 {
		// Even though wbuf may only be partially full, we
		// want to keep it on the consumer's queues rather
		// than putting it back on the producer's queues.
		// Hence, we use putfull here.
		putfull(wbuf.ptr(), 133)
		w.wbuf = 0
	}
}

// balance moves some work that's cached in this gcWork back on the
// global queue.
//go:nowritebarrier
func (w *gcWork) balance() {
	if wbuf := w.wbuf; wbuf != 0 && wbuf.ptr().nobj > 4 {
		w.wbuf = wbufptrOf(handoff(wbuf.ptr()))
	}
}

// The gcWork interface caches a work buffer until full (or empty) to
// avoid contending on the global work buffer lists.
```

## コアとなるコードの解説

`src/runtime/mgcwork.go`で導入された新しい型とメソッドは、GoのGCがオブジェクトをスキャンする際のワークバッファ管理を大幅に簡素化し、効率化することを目的としています。

### `wbufptr`

`wbufptr`は、`*workbuf`（ワークバッファへのポインタ）を`uintptr`としてラップしたものです。これは、`workbuf`がヒープ上に割り当てられないため、Goのライトバリアの対象外とすることで、GCのパフォーマンスへの影響を最小限に抑え、GC中の安全性を確保するための工夫です。`unsafe.Pointer`を使って`uintptr`と`*workbuf`の間で変換を行います。

### `gcWorkProducer`

この構造体は、GCのマークフェーズ中に新しい灰色オブジェクトを発見し、それをGCシステムに「投入」する役割を担います。

*   **`wbuf wbufptr`**: 現在使用しているワークバッファへのポインタを保持します。このバッファは、新しい灰色オブジェクトを一時的に格納するために使用されます。
*   **`put(obj uintptr)`**: 最も重要なメソッドで、`obj`で示されるオブジェクトへのポインタをワークキューに追加します。
    *   もし現在の`wbuf`が`nil`であれば、`getpartialorempty`を呼び出して新しいワークバッファを取得します。これは、部分的に使用されているバッファか、完全に空のバッファを取得することを意味します。
    *   `wbuf.obj[wbuf.nobj] = obj`でオブジェクトをバッファに追加し、`wbuf.nobj++`でオブジェクト数をインクリメントします。
    *   もし`wbuf`が満杯になった場合（`wbuf.nobj == uintptr(len(wbuf.obj))`）、`putfull`を呼び出して満杯のバッファをグローバルキューに返し、`w.wbuf = 0`として現在のバッファをクリアします。これにより、プロデューサーは次の`put`呼び出しで新しいバッファを取得する準備ができます。
*   **`dispose()`**: `gcWorkProducer`が使い終わったときに呼び出され、現在キャッシュしているワークバッファをグローバルキューに返します。`putpartial`を使用することで、部分的に満たされたバッファも適切に処理されます。
*   **`initFromCache()` と `disposeToCache()`**: これらは、各M（論理プロセッサ）が持つローカルキャッシュ（`getg().m.currentwbuf`）との間でワークバッファをやり取りするためのメソッドです。これにより、グローバルなワークキューへのアクセス頻度を減らし、競合を緩和します。

### `gcWork`

`gcWork`は`gcWorkProducer`を埋め込んでいるため、オブジェクトを「生産」する機能も持ちますが、主な役割はGCがスキャンすべきオブジェクトを「消費」することです。

*   **`tryGet() uintptr`**: ワークキューからオブジェクトを非ブロックで取得しようとします。
    *   もし現在の`wbuf`が`nil`であれば、`trygetfull`を呼び出してグローバルキューから満杯のワークバッファを取得しようとします。
    *   オブジェクトが取得できれば、`wbuf.obj[wbuf.nobj]`からオブジェクトを取り出し、`wbuf.nobj--`でオブジェクト数をデクリメントします。
    *   もし`wbuf`が空になった場合（`wbuf.nobj == 0`）、`putempty`を呼び出して空のバッファをグローバルキューに返し、`w.wbuf = 0`として現在のバッファをクリアします。
*   **`get() uintptr`**: `tryGet`と似ていますが、ワークキューからオブジェクトを取得できるまでブロックする可能性があります。これは、すべてのポインタが処理されるまで待機する必要がある場合に利用されます。
*   **`dispose()`**: `gcWork`が使い終わったときに呼び出され、現在キャッシュしているワークバッファをグローバルキューに返します。`gcWorkProducer`の`dispose`とは異なり、`putfull`を使用します。これは、コンシューマーが使用していたバッファは、たとえ部分的にしか使われていなくても、満杯のバッファとして扱われ、コンシューマー側のキューに戻されるべきであるという意図があるためです。
*   **`balance()`**: この`gcWork`インスタンスがローカルに多くのワークを抱え込んでいる場合に、その一部をグローバルキューに戻すことで、他のGCワーカーがワークを見つけやすくし、ワークの偏りを解消します。

これらの抽象化により、GCの各コンポーネントは、ワークバッファの低レベルな詳細（バッファの割り当て、解放、満杯/空のチェック、グローバルキューとのやり取りなど）を意識することなく、`put`や`get`といったシンプルなインターフェースを通じてGCワークを扱うことができるようになります。これにより、GCコードのモジュール性が向上し、将来的なGCアルゴリズムの変更や最適化が容易になります。

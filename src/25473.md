# [インデックス 25473] ファイルの概要

このコミットは、Goランタイムのガベージコレクション (GC) における「GCアシスト」のメカニズムを改善するものです。以前は、GCアシストがすぐに満たされない場合に、ミューテーター（ユーザープログラム）のゴルーチンが短い時間（100マイクロ秒）スリープし、CPUを浪費していました。この変更により、スリープループを廃止し、代わりに適切なスケジューリングキューと`park`/`ready`メカニズムを導入することで、CPUの無駄遣いをなくし、より効率的なGCアシストの処理を実現しています。

## 変更の背景

Goのガベージコレクション (GC) は、プログラムの実行と並行して動作する「並行GC」を採用しています。このGCサイクル中に、ユーザープログラム（ミューテーター）が新しいオブジェクトを大量に割り当てると、GCの進行が追いつかなくなる可能性があります。これを防ぐために導入されているのが「GCアシスト」というメカニズムです。

GCアシストは、ミューテーターが一定量以上のメモリを割り当てた際に、GC作業の一部を肩代わりさせることで、GCの進行を助けるものです。しかし、このコミット以前の実装では、GCアシストが必要な作業をすぐに完了できない場合、ミューテーターのゴルーチンは100マイクロ秒の短い間隔でスリープし、GC作業が完了するのを待つという「ビジーループ（busy-loop）」に近い状態になっていました。

このビジーループにはいくつかの問題がありました。

1.  **CPUの無駄遣い**: 短いスリープと再試行を繰り返すため、GC作業が完了するまでの間、CPUサイクルが無駄に消費されていました。これは特に、GC作業が長時間かかる場合に顕著でした。
2.  **ミューテーター実行の遅延**: スリープと再試行のオーバーヘッドにより、ミューテーターの実行が不必要に遅延していました。
3.  **再帰的なアロケーションの問題**: ゴルーチンをスリープさせる処理自体がメモリ割り当てを必要とする場合があり、GCアシスト中にさらにメモリを割り当てるという再帰的な問題を引き起こす可能性がありました。これを回避するために、特別な処理が必要となっていました。

これらの問題を解決し、GCアシストの効率とミューテーターのパフォーマンスを向上させるために、このコミットによる変更が導入されました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにした並行GCです。GCサイクルは以下のフェーズで構成されます。

*   **マークフェーズ**:
    *   **マーク準備 (Mark Setup / STW)**: 短いSTW (Stop The World) が発生し、GCが開始される準備をします。
    *   **並行マーク (Concurrent Mark)**: GCワーカーがバックグラウンドで到達可能なオブジェクトをマークします。この間もミューテーターは実行されます。
    *   **マーク終結 (Mark Termination / STW)**: 短いSTWが発生し、マークフェーズを終了させます。
*   **スイープフェーズ**:
    *   **並行スイープ (Concurrent Sweep)**: マークされなかったオブジェクト（到達不能なオブジェクト）が解放されます。これも並行して行われます。

### GCアシスト (GC Assist)

並行マークフェーズ中に、ミューテーターが新しいオブジェクトを割り当てる際、GCの進行度合いに応じて「GCアシスト」がトリガーされることがあります。これは、ミューテーターがGC作業の一部（例えば、オブジェクトのスキャン）を肩代わりすることで、GCがメモリ割り当てに追いつけるようにするための仕組みです。各ゴルーチンには「アシスト債務 (assist debt)」が割り当てられ、この債務を返済するためにGCアシスト作業を行います。

### クレジット (Credit)

GCアシストの文脈では、「クレジット」という概念が使われます。これは、GC作業の進行度合いを示す仮想的な単位です。
*   **バックグラウンドスキャンクレジット (Background Scan Credit)**: バックグラウンドでGCワーカーが行ったスキャン作業量。
*   **アシストクレジット (Assist Credit)**: ミューテーターがGCアシストとして行ったスキャン作業量。

ミューテーターがメモリを割り当てる際、その割り当て量に応じてアシスト債務が発生します。この債務は、バックグラウンドスキャンクレジットを「盗む」か、ミューテーター自身がGCアシスト作業を行うことで返済されます。

### `gopark` と `goready`

Goランタイムにおけるゴルーチンのスケジューリングプリミティブです。
*   `gopark(lock, reason, traceEv, traceskip)`: 現在のゴルーチンを停止（パーク）させ、スケジューラーから外します。`lock`はゴルーチンがパークされる前に解放されるべきミューテックス、`reason`はパークの理由、`traceEv`はトレースイベントの種類、`traceskip`はスタックトレースをスキップするフレーム数です。
*   `goready(gp, traceskip)`: パークされているゴルーチン`gp`を再開可能（レディ）状態にし、スケジューラーの実行キューに戻します。

これらは、ゴルーチンが特定の条件が満たされるまで待機し、条件が満たされたときに効率的に再開されるためのメカニズムを提供します。

### `timeSleep`

指定された時間だけ現在のゴルーチンをスリープさせる関数です。このコミット以前は、GCアシストが満たされない場合に`timeSleep(100 * 1000)`（100マイクロ秒）が使われていました。

### `atomicload` と `xaddint64`

Goランタイムで使われるアトミック操作です。
*   `atomicload(&var)`: 変数の値をアトミックに読み込みます。
*   `xaddint64(&var, delta)`: 変数に`delta`をアトミックに加算し、加算前の値を返します。

これらは複数のゴルーチンが共有するデータに安全にアクセスするために使用されます。

## 技術的詳細

このコミットの核心は、GCアシストがすぐに満たされない場合の「ビジーループ」を、`gopark`/`goready`を用いた効率的な待機・再開メカニズムに置き換えることです。

新しいメカニズムは以下の要素で構成されます。

1.  **`assistQueue`の導入**:
    *   `runtime.work`構造体に`assistQueue`という新しいキューが追加されました。これは、GCアシストが満たされずにブロックされたゴルーチン（G）を格納するためのリンクリストです。
    *   `assistQueue`は`lock`（ミューテックス）、`head`（キューの先頭）、`tail`（キューの末尾）で構成されます。

2.  **GCアシストの待機 (`gcAssistAlloc`内)**:
    *   `gcAssistAlloc`関数内で、GCアシストがクレジットを盗むか、十分な作業を行うことで債務を返済できない場合、以前は`timeSleep`と`goto retry`でビジーループに入っていました。
    *   この変更により、ゴルーチンは`assistQueue`に追加され、`goparkunlock(&work.assistQueue.lock, "GC assist", traceEvGoBlock, 2)`を呼び出してパークされます。これにより、CPUを消費せずに待機状態に入ります。
    *   パークされる前に、GCサイクルが終了しているかどうかのチェックが行われます。GCが終了していれば、アシスト債務は無視され、ゴルーチンはすぐに復帰します。
    *   また、キューに追加された直後にバックグラウンドスキャンクレジットが利用可能になった場合、ゴルーチンはキューから外され、すぐに`retry`ラベルにジャンプしてアシストを再試行します。これは、キューイングとパークの間にクレジットが利用可能になるという競合状態を避けるためです。

3.  **ブロックされたアシストの再開 (`gcFlushBgCredit`と`gcWakeAllAssists`)**:
    *   **`gcFlushBgCredit`**: バックグラウンドスキャンクレジットがフラッシュされる（つまり、GCワーカーが作業を完了し、クレジットが利用可能になる）たびに呼び出されます。
        *   この関数はまず`assistQueue`をチェックし、ブロックされているアシストゴルーチンが存在するかどうかを確認します。
        *   キュー内の各ゴルーチンに対して、利用可能なクレジットを割り当て、そのアシスト債務を返済します。
        *   債務が完全に返済されたゴルーチンは`goready`によって再開されます。
        *   債務が部分的にしか返済されなかったゴルーチンは、キューの末尾に移動されることがあります。これは、大きなアシスト債務を持つゴルーチンがキューを占有し、小さな債務を持つゴルーチンの再開を遅らせるのを防ぐためのヒューリスティックです。
        *   残ったクレジットは、グローバルなバックグラウンドクレジットプールにフラッシュされます。
    *   **`gcWakeAllAssists`**: GCサイクルが終了する際に呼び出されます。
        *   `assistQueue`にブロックされているすべてのゴルーチンを`goready`によって再開します。これは、GCサイクルが終了すれば、すべてのアシスト債務は無効になるためです。

この新しいメカニズムにより、GCアシストが満たされない場合にゴルーチンは効率的に待機し、GCワーカーが作業を完了してクレジットが利用可能になったときにのみ再開されるようになります。これにより、CPUの無駄遣いがなくなり、ミューテーターの実行遅延が最小限に抑えられます。また、ゴルーチンのスリープに伴う再帰的なメモリ割り当ての問題も解消されます。

## コアとなるコードの解説

### `work.assistQueue`

このキューは、GCアシストがすぐに満たされなかったために一時的に実行を停止したゴルーチンを保持します。`head`と`tail`はキューの先頭と末尾のゴルーチンを指し、`lock`はキューへのアクセスを保護します。

### `gcAssistAlloc`内の`goparkunlock`

```go
		// Park for real.
		goparkunlock(&work.assistQueue.lock, "GC assist", traceEvGoBlock, 2)
```
GCアシストが債務を返済できない場合、この行で現在のゴルーチンがパークされます。`work.assistQueue.lock`はパークされる直前に解放され、ゴルーチンが再開されるときに再度取得されることはありません（`goparkunlock`の動作による）。`"GC assist"`はパークの理由を示し、トレース情報に利用されます。

### `gcWakeAllAssists()`

```go
func gcWakeAllAssists() {
	lock(&work.assistQueue.lock)
	injectglist(work.assistQueue.head.ptr())
	work.assistQueue.head.set(nil)
	work.assistQueue.tail.set(nil)
	unlock(&work.assistQueue.lock)
}
```
この関数は、GCサイクルが終了したときに呼び出されます。`assistQueue`にロックをかけ、キューの先頭からすべてのゴルーチンを`injectglist`を使ってスケジューラーの実行キューに戻します。その後、キューを空にします。これにより、GCサイクル終了時にはすべてのアシストゴルーチンが再開され、通常のプログラム実行に戻ることができます。

### `gcFlushBgCredit(scanWork int64)`

```go
func gcFlushBgCredit(scanWork int64) {
	// ... (fast path for empty queue) ...

	lock(&work.assistQueue.lock)
	gp := work.assistQueue.head.ptr()
	for gp != nil && scanBytes > 0 {
		// ... (satisfy assist debt and ready goroutine) ...
	}
	// ... (update queue head/tail, flush remaining credit) ...
	unlock(&work.assistQueue.lock)
}
```
この関数は、バックグラウンドGCワーカーが一定量のスキャン作業を完了し、`scanWork`としてクレジットが利用可能になったときに呼び出されます。
1.  まず、`assistQueue`が空でないかチェックします。空であれば、クレジットは直接グローバルなバックグラウンドクレジットプールに追加されます。
2.  キューにゴルーチンがある場合、`assistQueue.lock`を取得し、キューの先頭からゴルーチンを順に処理します。
3.  各ゴルーチン`gp`のアシスト債務`gp.gcAssistBytes`（負の値）を、利用可能な`scanBytes`で返済しようとします。
4.  債務が完全に返済された場合（`scanBytes + gp.gcAssistBytes >= 0`）、そのゴルーチンは`ready(xgp, 0)`によって再開され、キューから削除されます。
5.  債務が部分的にしか返済されなかった場合、残りの`scanBytes`はそのゴルーチンの債務に充当され、`scanBytes`は0になります。このゴルーチンはキューの末尾に移動され、他のゴルーチンが先にクレジットを受け取れるようにします（ヒューリスティック）。
6.  すべてのブロックされたアシストを処理し終えるか、`scanBytes`が0になった後、残りのクレジットはグローバルなバックグラウンドクレジットプールにフラッシュされます。

このメカニズムにより、バックグラウンドGCの進行と同期して、ブロックされたミューテーターが効率的に再開されるようになります。

## 元コミット内容

このコミットは、`gobuild` ツール内のバグを修正します。主な変更点は、`exec.LookPath` の呼び出しにおけるエラー変数のスコープの問題と、`run` 関数内で発生したエラーが標準エラー出力に表示されない問題の解決です。これにより、`gobuild` の堅牢性とデバッグのしやすさが向上します。

## 変更の背景

Go言語の初期段階では、`gobuild` はプロジェクトのビルドを管理するための主要なツールの一つでした。このツールは、Goプログラムのコンパイルに必要なバイナリのパスを検索したり、外部コマンドを実行したりする役割を担っていました。

このコミットが行われた2009年6月は、Go言語がまだ一般に公開される前の開発初期段階にあたります。この時期は、言語仕様や標準ライブラリ、ツールチェインが活発に開発・改善されていた時期であり、このような基本的なツールのバグ修正は日常的に行われていました。

具体的な背景としては、`exec.LookPath` の戻り値である `err` 変数が `if` ステートメント内で `:=` を使って宣言されていたため、その `err` が `if` ブロックのローカル変数となり、外側のスコープの `err` 変数をシャドーイング（隠蔽）してしまう問題がありました。これにより、`exec.LookPath` がエラーを返しても、外側のスコープでそのエラーが正しく捕捉されない可能性がありました。

また、`run` 関数内で `os.StartProcess` や `os.Wait` がエラーを返した場合、そのエラーメッセージがユーザーに表示されず、単に `false` が返されるだけだったため、何が問題だったのかを特定するのが困難でした。このコミットは、これらの問題を解決し、`gobuild` の信頼性とデバッグの容易さを向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念と初期のGo言語の特性について知っておく必要があります。

1.  **`exec.LookPath`**:
    *   `os/exec` パッケージの一部で、指定された実行可能ファイルがシステムの `PATH` 環境変数内のどこにあるかを検索する関数です。
    *   成功した場合は実行可能ファイルの絶対パスを返し、見つからない場合はエラーを返します。
    *   このコミットの時点では、`os/exec` パッケージはまだ `exec` パッケージとして存在していた可能性があります（Goの進化の過程でパッケージ名や構造は変化しています）。

2.  **`os.Error`**:
    *   Go言語の非常に初期のバージョンで使用されていたエラーインターフェースです。
    *   現在のGo言語では、`error` という組み込みインターフェースが使用されており、`os.Error` は廃止されています。`error` インターフェースは `Error() string` メソッドを持つ任意の型として定義されます。
    *   このコミットでは `var err os.Error;` と宣言されており、当時のエラーハンドリングの慣習を示しています。

3.  **`:=` と `=` による変数宣言と代入**:
    *   `:=` (ショート変数宣言) は、変数の宣言と初期化を同時に行うGoの構文です。この構文は、新しい変数を宣言し、その型を初期値から推論します。
    *   `=` は、既に宣言されている変数に値を代入する際に使用します。
    *   このコミットの修正の中心は、`if s, err := exec.LookPath(v); err != nil {` のように `if` ステートメント内で `:=` を使用すると、`err` が `if` ブロックのローカル変数として再宣言されてしまい、外側のスコープの `err` とは別の変数になってしまう「シャドーイング」の問題を解決することです。修正後は `var err os.Error;` で `err` を外側で宣言し、`s, err = exec.LookPath(v)` で既存の `err` 変数に代入することで、この問題を回避しています。

4.  **`os.StartProcess` と `os.Wait`**:
    *   `os.StartProcess` は、新しいプロセスを開始するための関数です。実行するプログラムのパス、引数、およびプロセス属性を受け取ります。
    *   `os.Wait` は、指定されたプロセスが終了するのを待ち、その終了ステータスに関する情報（`waitmsg`）を返します。
    *   これらの関数は、`gobuild` が外部コマンド（コンパイラなど）を実行し、その完了を待つために使用されていました。

5.  **`fmt.Fprintln(os.Stderr, err)`**:
    *   `fmt` パッケージは、フォーマットされたI/Oを実装します。
    *   `Fprintln` は、指定された `io.Writer` (この場合は `os.Stderr`、標準エラー出力) に引数をスペースで区切り、改行を追加して出力します。
    *   `os.Stderr` は、プログラムの標準エラー出力ストリームを表す `*os.File` です。エラーメッセージは通常、標準エラー出力に書き込まれます。

6.  **`gobuild` ツール**:
    *   Go言語の非常に初期のビルドツールです。現在の `go build` コマンドの前身にあたります。
    *   Go言語の進化とともに、より洗練された `go` コマンドに統合され、`gobuild` 自体は使われなくなりました。このツールは、Go言語の初期のツールチェインの歴史の一部です。

## 技術的詳細

このコミットは、Go言語の初期のツール開発における一般的な落とし穴と、堅牢なエラーハンドリングの重要性を示しています。

### エラー変数のシャドーイング問題の解決

最も重要な変更は、`src/cmd/gobuild/util.go` の `init` 関数内での `exec.LookPath` の呼び出し方です。

```go
// 変更前
if s, err := exec.LookPath(v); err != nil {
    fatal("cannot find binary %s", v);
}

// 変更後
var err os.Error; // errを外側のスコープで宣言
if s, err = exec.LookPath(v); err != nil { // 既存のerrに代入
    fatal("cannot find binary %s", v);
}
```

変更前では、`if` ステートメントの条件部で `s, err := exec.LookPath(v)` と書かれていました。Go言語では、`:=` を使用すると新しい変数が宣言されます。この場合、`err` は `if` ブロックのローカル変数として宣言され、`init` 関数内のより広いスコープに存在する可能性のある同名の `err` 変数をシャドーイングしていました。

もし `exec.LookPath` がエラーを返した場合、そのエラーは `if` ブロック内のローカルな `err` に格納され、`fatal` 関数が呼び出されます。しかし、もし `fatal` 関数がプログラムを終了させなかった場合（例えば、テスト環境で `fatal` がモックされていた場合など）、`if` ブブロックを抜けた後、外側のスコープの `err` 変数は更新されず、`exec.LookPath` が返した実際のエラー情報が失われる可能性がありました。

変更後では、`if` ステートメントの前に `var err os.Error;` と明示的に `err` 変数を宣言しています。そして、`if` ステートメント内では `s, err = exec.LookPath(v)` と `=` を使用して、既に宣言されている `err` 変数に値を代入しています。これにより、`exec.LookPath` が返すエラーが正しく外側のスコープの `err` 変数に反映され、シャドーイングの問題が解消されます。これは、Go言語で `:=` を使う際の一般的な注意点の一つであり、特にエラーハンドリングにおいて重要な側面です。

### エラーメッセージの出力によるデバッグの改善

`run` 関数内の2箇所で、エラー発生時に `fmt.Fprintln(os.Stderr, err)` を追加しています。

```go
// 変更前 (例: os.StartProcess後のエラーハンドリング)
if err != nil {
    return false;
}

// 変更後
if err != nil {
    fmt.Fprintln(os.Stderr, err); // エラーメッセージを標準エラー出力に表示
    return false;
}
```

この変更により、`os.StartProcess` や `os.Wait` の呼び出しでエラーが発生した場合、そのエラーメッセージが標準エラー出力に表示されるようになります。これにより、`gobuild` の実行中に何らかの問題が発生した際に、ユーザーや開発者が具体的なエラー内容を把握しやすくなり、デバッグが大幅に容易になります。以前は単に `false` が返されるだけで、エラーの原因を特定するのが困難でした。これは、ユーザーフレンドリーなツール開発における基本的なプラクティスです。

## コアとなるコードの解説

### `init` 関数内の変更

`init` 関数はGoプログラムの起動時に自動的に実行される特殊な関数です。ここでは、`gobuild` が使用する外部バイナリ（コンパイラなど）のパスを検索し、`bin` マップに格納しています。

```go
		var s string;
		var err os.Error; // ここでerr変数を宣言
		if s, err = exec.LookPath(v); err != nil { // 既存のerr変数に代入
			fatal("cannot find binary %s", v);
		}
		bin[v] = s;
```

この部分では、`exec.LookPath(v)` を呼び出して、`v` で指定されたバイナリのパスを検索しています。
- 変更前は `if s, err := exec.LookPath(v);` となっており、`err` が `if` ブロック内で新しく宣言されていました。
- 変更後は、`if` ブロックの前に `var err os.Error;` と宣言し、`if` ブロック内では `s, err = exec.LookPath(v);` と `=` を使って既存の `err` 変数に代入しています。これにより、`exec.LookPath` がエラーを返した場合、そのエラーが `init` 関数スコープの `err` 変数に正しく格納されるようになります。

### `run` 関数内の変更

`run` 関数は、指定されたコマンドを実行し、その結果を処理する役割を担っています。

```go
	// ... (os.StartProcessの呼び出しなど)
	if err != nil {
		fmt.Fprintln(os.Stderr, err); // エラーメッセージを標準エラー出力に表示
		return false;
	}
```
この箇所は、`os.StartProcess` の呼び出し後にエラーが発生した場合の処理です。以前はエラーメッセージが出力されませんでしたが、`fmt.Fprintln(os.Stderr, err)` が追加されたことで、エラーの詳細が標準エラー出力に表示されるようになりました。これにより、プロセス起動失敗の原因を特定しやすくなります。

```go
	// ... (os.Waitの呼び出しなど)
	if err != nil {
		fmt.Fprintln(os.Stderr, err); // エラーメッセージを標準エラー出力に表示
		return false;
	}
	return waitmsg.Exited() && waitmsg.ExitStatus() == 0;
```
同様に、この箇所は `os.Wait` の呼び出し後にエラーが発生した場合の処理です。プロセスが正常に終了しなかったり、`os.Wait` 自体がシステムコールエラーを返したりした場合に、そのエラーメッセージが標準エラー出力に表示されるようになり、プロセスの終了に関する問題のデバッグが容易になります。

これらの変更は、Go言語の初期のツール開発において、エラーハンドリングのベストプラクティスが確立されていく過程を示しており、堅牢性とデバッグの容易さを向上させる上で非常に重要でした。

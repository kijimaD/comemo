# [インデックス 26201] ファイルの概要

このコミットでは、Goコンパイラの内部パッケージである`cmd/internal/obj`内の、ARM、ARM64、およびx86アーキテクチャ向けのアセンブラコード生成ロジックが変更されています。具体的には、以下の3つのファイルが修正されました。

*   `src/cmd/internal/obj/arm/obj5.go`
*   `src/cmd/internal/obj/arm64/obj7.go`
*   `src/cmd/internal/obj/x86/obj6.go`

## コミット

`cmd/internal/obj`: `runtime.morestack`呼び出しにおけるPCSPテーブルの修正

このコミットは、`runtime.morestack`が呼び出される際のPCSP (Program Counter to Stack Pointer) テーブルの不正確さを修正します。これにより、スタックの正確なアンワインド（巻き戻し）が可能になり、デバッグやプロファイリングの精度が向上します。

## 変更の背景

Goプログラムが実行される際、各関数はスタック上に自身のスタックフレームを確保します。このスタックフレームのサイズが不足した場合、Goランタイムは自動的にスタックを拡張するメカニズムを持っています。このメカニズムの中心となるのが`runtime.morestack`関数です。

問題は、`runtime.morestack`が呼び出される時点でのPCSP (Program Counter to Stack Pointer) テーブルの正確性でした。PCSPテーブルは、特定のプログラムカウンタ（命令アドレス）において、スタックポインタがどれだけ調整されているか（つまり、現在のスタックフレームのサイズ）を示すメタデータです。この情報は、ガベージコレクションがスタック上のポインタをスキャンする際や、デバッガがスタックトレースを生成する際に不可欠です。

以前の実装では、`runtime.morestack`が呼び出される直前の命令のPCSP情報が、既にスタックフレームが設定され、スタックポインタが調整された後の状態を正確に反映していませんでした。これにより、`runtime.morestack`への呼び出しが行われるプログラムカウンタにおいて、ランタイムがスタックの状態を誤って解釈する可能性がありました。結果として、スタックトレースが不正確になったり、ガベージコレクションが誤動作したりするリスクがありました。

このコミットは、Issue #13346で報告されたこの問題を解決することを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime):** Goプログラムの実行を管理する低レベルのシステムです。スケジューラ、ガベージコレクタ、スタック管理などが含まれます。
*   **スタックフレーム (Stack Frame):** 関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保されるメモリ領域です。
*   **スタックポインタ (Stack Pointer, SP):** 現在のスタックの最上位（または最下位、アーキテクチャによる）を指すレジスタです。関数がスタックフレームを確保すると、SPは調整されます。
*   **プログラムカウンタ (Program Counter, PC):** 次に実行される命令のアドレスを保持するレジスタです。
*   **PCSPテーブル (Program Counter to Stack Pointer table):** Goのバイナリに埋め込まれるメタデータの一つで、特定のPC値に対応するSPのオフセット情報を提供します。これにより、ランタイムは任意のPCにおけるスタックの状態（どの変数がどこにあるかなど）を把握できます。これは、ガベージコレクションがスタック上のポインタを正確に識別するため、およびデバッガが正確なスタックトレースを生成するために非常に重要です。
*   **`runtime.morestack`:** Goランタイムの内部関数で、現在のゴルーチンのスタックが不足した場合に、より大きなスタックを割り当てて切り替える処理を行います。これは、Goの「スタックの自動拡張」機能の根幹をなすものです。
*   **`cmd/internal/obj`パッケージ:** Goコンパイラのバックエンドの一部であり、Goの抽象構文木から特定アーキテクチャ（ARM, ARM64, x86など）のアセンブリコードを生成する役割を担います。このパッケージは、命令の生成だけでなく、PCSPテーブルのようなランタイムメタデータの生成も行います。
*   **`obj.Prog`:** アセンブリ命令を表す構造体です。
*   **`obj.ANOP` (No-Operation):** 何も操作を行わないアセンブリ命令です。しかし、Goのアセンブラでは、この命令にメタデータ（例: `Spadj`）を付加することで、実行には影響を与えずにPCSPテーブルの情報を更新するマーカーとして利用されることがあります。
*   **`Spadj` (Stack Adjustment):** `obj.Prog`構造体のフィールドで、その命令が実行された際にスタックポインタがどれだけ調整されるか（または、その命令のPCにおけるスタックポインタの論理的な調整量）を示します。

## 技術的詳細

このコミットの核心は、`runtime.morestack`が呼び出される直前のPCSPテーブルのエントリを正確にすることです。

Goの関数が呼び出され、スタックフレームが設定されると、スタックポインタはフレームサイズ分だけ減少します（多くのアーキテクチャでスタックはアドレスの低い方に伸びるため）。`runtime.morestack`が呼び出されるのは、このスタックフレームが既に設定された後です。したがって、`runtime.morestack`への呼び出し命令のPCに対応するPCSPテーブルのエントリは、その関数のスタックフレームが既に確保されている状態を反映している必要があります。

このコミットでは、以下の変更が導入されました。

1.  **`ANOP`命令の挿入:**
    `runtime.morestack`への呼び出し（または、その呼び出しを準備する命令）の直前に、`obj.ANOP`（No-Operation）命令が挿入されます。この`ANOP`命令自体はCPUによって何も実行されませんが、Goのアセンブラにとっては重要な意味を持ちます。
2.  **`Spadj`値の設定:**
    挿入された`ANOP`命令の`Spadj`フィールドに、現在の関数のスタックフレームサイズ（`-framesize`）が設定されます。これにより、この`ANOP`命令のPCにおいて、PCSPテーブルはスタックポインタが`framesize`分だけ減少した状態（つまり、スタックフレームが確保された状態）であると記録されます。
3.  **ジャンプ命令の`Spadj`修正:**
    `runtime.morestack`から元の関数に戻るためのジャンプ命令（`AJMP`や`AB`）にも、`Spadj`フィールドが`+framesize`に設定されます。これは、`morestack`呼び出しによって一時的に変更されたスタックポインタの状態を、元の関数のコンテキストに戻すための論理的な調整を示します。

この修正により、`runtime.morestack`が呼び出されるPCにおいて、PCSPテーブルがスタックポインタの正しいオフセットを報告するようになります。これにより、ガベージコレクタやデバッガがスタックを正確にスキャン・アンワインドできるようになり、Goプログラムの信頼性とデバッグ可能性が向上します。

この変更は、ARM、ARM64、およびx86の3つの主要なアーキテクチャのアセンブラコード生成ロジックに適用されており、Goのスタック分割（stack splitting）メカニズムにおける一般的な問題の解決策であることを示しています。

## コアとなるコードの解説

1.  **`spfix`の挿入:**
    ```go
    	spfix := obj.Appendp(ctxt, last)
    	spfix.As = obj.ANOP
    	spfix.Spadj = -framesize
    ```
    `obj.Appendp(ctxt, last)`は、現在の命令リストの最後に新しい命令を追加します。ここで追加されるのは`ANOP`命令です。
    `spfix.As = obj.ANOP`は、この命令が何もしない命令であることを示します。
    `spfix.Spadj = -framesize`がこの変更の肝です。これは、この`ANOP`命令のPCにおいて、スタックポインタが`framesize`分だけ減少している（つまり、現在の関数のスタックフレームが既に確保されている）というメタデータ情報をPCSPテーブルに記録するよう指示します。これにより、`runtime.morestack`が呼び出される直前のスタックの状態が正確に表現されます。

2.  **後続命令のリンク修正:**
    ```go
    	// MOVW	LR, R3
    -	movw := obj.Appendp(ctxt, last)
    +	movw := obj.Appendp(ctxt, spfix)
    ```
    以前は`last`（元の命令リストの最後）に直接追加されていた`movw`命令（戻りアドレスを保存する命令）が、新しく挿入された`spfix`命令の後にリンクされるように変更されています。これにより、`spfix`命令が命令シーケンスに正しく組み込まれます。

3.  **ジャンプ命令の`Spadj`修正:**
    ```go
    	b.As = obj.AJMP
    	b.To.Type = obj.TYPE_BRANCH
    	b.Pcond = ctxt.Cursym.Text.Link
    +	b.Spadj = +framesize
    ```
    `runtime.morestack`から元の関数に戻るためのジャンプ命令（`b`）に対して、`b.Spadj = +framesize`が追加されています。これは、このジャンプ命令のPCにおいて、スタックポインタが`framesize`分だけ増加している（つまり、`morestack`呼び出しによって行われたスタック調整が元に戻された）というメタデータ情報をPCSPテーブルに記録するよう指示します。これにより、スタックのアンワインドが正確に行われます。

これらの変更により、Goコンパイラは、`runtime.morestack`が関与するスタック分割のシナリオにおいて、より正確なPCSPテーブルを生成するようになり、ランタイムのスタック管理の堅牢性が向上しました。

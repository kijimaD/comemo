# [インデックス 27222] ファイルの概要

このコミットは、Goランタイムにおけるゴルーチン（G）の状態ロックとチャネルロック間のロック順序を明確にし、`closechan`関数がこの新しい順序を尊重するように修正するものです。特に、将来のスタック縮小の並行化を見据えた変更であり、デッドロックの可能性を排除することを目的としています。

## 変更の背景

このコミットの主な背景は、Goランタイムにおけるゴルーチンのスタック管理の進化、特に**スタック縮小の並行化**の計画にあります。

現状では、ゴルーチンのスタックをロックする操作（ゴルーチンのステータスを`_Gcopystack`や`_Gscan`に設定するなど）と、チャネルロックの取得の間には、明確なロック順序が定義されていませんでした。これは、これらの操作が互いに独立して行われることが多かったため、問題にはなりませんでした。

しかし、将来的にスタック縮小処理を並行化する際、スタック縮小を行うゴルーチンは、まず対象のゴルーチンをロックし、その後、そのゴルーチンがブロックされている可能性のあるチャネルのロックを取得する必要が生じます。この新しいシナリオでは、ゴルーチンロックとチャネルロックの間に特定の順序（ゴルーチンロック -> チャネルロック）が強制されることになります。

もし、チャネル操作側がチャネルロックを保持したままゴルーチンをロックしようとすると、スタック縮小側とデッドロックが発生する可能性があります。このコミットは、このような将来的なデッドロックを防ぐために、ロック順序を明確に定義し、既存のコードがその順序を尊重するように修正することを目的としています。特に、`closechan`関数がこの順序に違反する可能性があったため、修正の対象となりました。

この変更は、Goランタイムのパフォーマンスとスケーラビリティを向上させるための、より大規模なスタック管理の改善の一環として行われています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine, G)**:
    Goにおける軽量な実行スレッドです。Goプログラムの並行性の基本単位であり、Goランタイムによってスケジューリングされます。各ゴルーチンは独自のスタックを持ちます。

2.  **ゴルーチンのステータス**:
    ゴルーチンは様々な内部ステータスを持ちます。このコミットで言及されているのは以下のものです。
    *   `_Gcopystack`: ゴルーチンのスタックがコピー中であることを示すステータス。スタックの拡張や縮小の際に一時的に設定されます。
    *   `_Gscan`: ゴルーチンのスタックがGCによってスキャン中であることを示すステータス。
    これらのステータスを設定することは、実質的にそのゴルーチンのスタックをロックする行為と見なされます。

3.  **チャネル (Channel)**:
    ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは内部的にキューを持ち、複数のゴルーチンが同時にチャネルにアクセスする可能性があるため、内部状態を保護するためにロック（ミューテックス）を使用します。

4.  **`hchan`構造体**:
    Goランタイム内部でチャネルを表現する構造体です。この構造体には`lock mutex`フィールドが含まれており、チャネルの内部状態（送受信キュー、クローズ状態など）を保護するために使用されます。

5.  **`closechan`関数**:
    チャネルをクローズするためのランタイム関数です。チャネルがクローズされると、そのチャネルでブロックされているすべての送受信ゴルーチンが解放されます。この解放処理中に、ブロックされていたゴルーチンのステータスを変更する（`goready`を呼び出す）必要があります。

6.  **`goready`関数**:
    指定されたゴルーチンを「実行可能」状態にし、スケジューラキューに戻すランタイム関数です。これにより、ゴルーチンは再び実行される機会を得ます。

7.  **ロック順序 (Lock Ordering)**:
    複数のロック（ミューテックス）を使用するシステムにおいて、デッドロックを防ぐために、ロックを取得する順序を事前に定義し、常にその順序に従うという規則です。例えば、「ロックAを取得してからロックBを取得する」という順序を定めた場合、決して「ロックBを取得してからロックAを取得する」という操作を行ってはいけません。

8.  **スタック縮小の並行化**:
    Goのゴルーチンスタックは、必要に応じて自動的に拡張されます。しかし、使用されなくなった大きなスタックを解放し、メモリ効率を向上させるために、スタックを縮小する機能も存在します。この縮小処理を、他のランタイム操作と並行して安全に行えるようにするための改善が計画されていました。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムにおける**ロック順序の違反によるデッドロックの可能性**を排除することにあります。

既存のGoランタイムでは、チャネルのロック（`hchan.lock`）を保持したまま、チャネルでブロックされているゴルーチンを`goready`によって実行可能状態に戻すことが行われていました。`goready`はゴルーチンのステータスを変更する操作であり、これはゴルーチンのスタックをロックする行為と見なすことができます。

将来的にスタック縮小が並行化されると、スタック縮小処理は以下の順序でロックを取得する可能性があります。
1.  対象ゴルーチンのスタックをロック（ゴルーチンのステータス変更）
2.  そのゴルーチンがブロックされているチャネルのロックを取得

もし`closechan`のようなチャネル操作が、チャネルロックを保持したままゴルーチンのステータスを変更（つまりゴルーチンをロック）しようとすると、以下のデッドロックシナリオが発生する可能性があります。

*   **シナリオA (スタック縮小側)**: ゴルーチンG1のスタックをロック -> チャネルCのロックを取得しようとして待機
*   **シナリオB (チャネルクローズ側)**: チャネルCのロックを保持 -> ゴルーチンG1のスタックをロックしようとして待機

この状況では、G1のスタックロックとチャネルCのロックが互いに相手のロック解除を待つ形になり、デッドロックが発生します。

このコミットは、この問題を解決するために、`hchan`構造体の`lock`フィールドのコメントを更新し、**「このロックを保持している間は、他のGのステータスを変更してはならない（特にGをready状態にしてはならない）。これはスタック縮小とデッドロックする可能性があるためである。」**という明確なロック順序の制約を導入しました。

そして、`closechan`関数がこの新しい制約を遵守するように修正されました。具体的には、チャネルロックを保持している間は`goready`を直接呼び出すのを避け、代わりに解放すべきゴルーチンを一時的なリスト（`glist`）に集め、チャネルロックを解放した後にまとめて`goready`を呼び出すように変更されました。これにより、ゴルーチンのステータス変更（ロック）がチャネルロックの解放後に行われるため、ロック順序の違反が解消されます。

## コアとなるコードの解説

このコミットの主要な変更は、`closechan`関数におけるゴルーチンの`goready`呼び出しのタイミングを調整することです。

1.  **`hchan.lock`コメントの追加**:
    これは、Goランタイム開発者向けの重要なドキュメント変更です。`hchan`のミューテックスを保持している間は、他のゴルーチンのステータスを変更する操作（特に`goready`）を行ってはならないという、新しいロック順序の制約を明示しています。これにより、将来のコード変更で誤ってデッドロックを引き起こすことを防ぎます。

2.  **`glist`変数の導入と`goready`の遅延**:
    `closechan`関数は、クローズされるチャネルでブロックされていたすべての読み取りゴルーチンと書き込みゴルーチンを解放する必要があります。以前は、これらのゴルーチンをデキューするたびに`goready`を直接呼び出していました。
    しかし、新しいロック順序の制約に従うため、このコミットでは以下の変更が行われました。
    *   `var glist *g`：解放すべきゴルーチンを一時的に連結リストとして保持するためのポインタが導入されました。
    *   `gp.schedlink.set(glist)`と`glist = gp`：チャネルからデキューされたゴルーチン`gp`は、すぐに`goready`されるのではなく、`glist`の先頭に連結されます。`schedlink`はゴルーチン構造体内のフィールドで、スケジューラがゴルーチンをリンクするために使用するものです。ここでは、一時的な連結リストを構築するために再利用されています。
    *   `unlock(&c.lock)`：すべてのブロックされていたゴルーチンが`glist`に集められた後、チャネルのロックが解放されます。
    *   `for glist != nil { ... goready(gp, 3) }`：チャネルロックが解放された後、`glist`に集められたすべてのゴルーチンがループで順次`goready`されます。これにより、ゴルーチンのステータス変更（ロック）がチャネルロックを保持していない状態で行われることが保証され、デッドロックの可能性が排除されます。

この変更により、Goランタイムは、将来のスタック縮小の並行化が導入された際にも、安定して動作し続けるための基盤が強化されました。

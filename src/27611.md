# [インデックス 27611] ファイルの概要

このコミットはGoランタイムの`src/runtime/proc.go`ファイルに対する変更です。`proc.go`はGoランタイムの中核をなすファイルの一つで、ゴルーチン（goroutine）のスケジューリング、状態管理、およびガベージコレクション（GC）に関連する処理など、低レベルのプロセス管理機能が実装されています。具体的には、ゴルーチンの生成、破棄、状態遷移、そしてGC中のゴルーチンスタックのスキャンといった重要な操作が含まれています。

## 変更の背景

このコミットの背景には、Goランタイムにおけるガベージコレクション（GC）関連の処理、特に`scang`と`casgstatus`という2つの関数が、CPUを無駄に消費する「アクティブスピンループ（busy-waiting）」を使用していた問題があります。

アクティブスピンループとは、ある条件が満たされるまでCPUを解放せずに繰り返しチェックし続ける待機方法です。ユーザー空間のアプリケーションにおいて、このようなアクティブスピンは一般的に推奨されません。なぜなら、待機している間に他の有用な処理が実行される機会を奪い、CPUリソースを浪費するからです。

コミットメッセージによると、`scang`関数におけるアクティブスピンは、4コアマシンでの`go install -a std`プロファイルにおいて、CPU時間の11%を占めていました。これは、GCがゴルーチンのスタックをスキャンする際に、ゴルーチンの状態が変化するのを待つためにCPUを使い続けていたことを示しています。また、`casgstatus`関数も同様にアクティブスピンを使用していましたが、こちらはゴルーチンの状態をアトミックに変更する際に使用されます。

これらのアクティブスピンは、特にシステムがわずかに過負荷状態（oversubscription）になった場合に、テールレイテンシ（処理時間の長いリクエストのレイテンシ）を増加させる原因となっていました。GC関連のゴルーチンが、ユーザーコードを実行する代わりに、ループ内でCPUクォンタム全体を消費してしまうためです。`scang`の待機時間は数ミリ秒、`casgstatus`の待機時間は数百マイクロ秒に及ぶことがあり、このような長い時間アクティブスピンすることは非効率的でした。

理想的には、GCの待機メカニズムを非同期ステートマシンに切り替えることが考えられますが、このコミットでは、より即効性のある改善策として、合理的な待機時間の後にOSスケジューラに制御を譲る（yieldする）ことで、CPUの無駄な消費を削減することを目指しました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と一般的な並行処理の知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステムです。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル通信、システムコールインターフェースなどを担当します。
*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。OSスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。Goランタイムのスケジューラによって管理されます。
*   **ゴルーチンの状態 (Goroutine States)**: ゴルーチンはライフサイクルを通じて様々な状態を遷移します。このコミットで言及されている主な状態は以下の通りです。
    *   `_Gwaiting`: イベントを待機している状態。
    *   `_Grunnable`: 実行可能だが、まだスケジューラによって実行されていない状態。
    *   `_Gscanwaiting`: GCスキャンを待機している状態。
    *   `_Gscanrunning`: GCスキャンが実行されている状態。
    *   `_Gdead`: 終了した状態。
    *   `_Gcopystack`: スタックコピー中。
*   **ガベージコレクション (Garbage Collection, GC)**: Goの自動メモリ管理機能です。不要になったメモリを自動的に解放し、メモリリークを防ぎます。GoのGCは並行（concurrent）かつ低遅延（low-latency）を目指して設計されており、一部のフェーズでは「Stop-The-World (STW)」と呼ばれる、すべてのゴルーチンの実行を一時停止する期間が発生することもありますが、多くの処理はユーザープログラムと並行して実行されます。GC中には、ゴルーチンのスタックをスキャンして参照されているオブジェクトを特定する処理が行われます。
*   **`scang`関数**: Goランタイム内部のGC関連関数で、特定のゴルーチン（`gp`）のスタックをスキャンする役割を担います。GCが正確に動作するためには、ゴルーチンのスタックがGCによってスキャン可能な状態である必要があります。
*   **`casgstatus`関数**: Goランタイム内部の関数で、ゴルーチンの状態をアトミックに（不可分に）変更するために使用されます。`atomic.Cas`（Compare-and-Swap）操作を用いて、現在の状態が期待する`oldval`である場合にのみ`newval`に更新します。
*   **アクティブスピン (Active Spinning) / ビジーループ (Busy-waiting)**: ある条件が満たされるまで、CPUを消費しながら繰り返しループ内で条件をチェックし続ける待機方法です。CPUリソースを無駄に消費し、他のタスクの実行を妨げるため、一般的には避けるべきとされています。
*   **`atomic.Cas` (Compare-and-Swap)**: アトミック操作の一種で、メモリ位置の現在の値が指定された期待値と等しい場合にのみ、そのメモリ位置を新しい値に更新します。この操作は不可分であり、複数のスレッドが同時にアクセスしても競合状態が発生しません。
*   **`nanotime()`**: Goランタイムが提供する高分解能タイマーで、ナノ秒単位の時間を返します。OSのシステムクロックとは異なり、単調増加が保証されており、経過時間の計測に適しています。
*   **`procyield()`**: プロセッサにヒントを与え、現在のスレッドがCPUを一時的に解放して他のスレッドに実行を譲ることを促す関数です。OSスケジューラを介さずに、CPUレベルでのコンテキストスイッチを試みます。非常に短い待機に適しています。
*   **`osyield()`**: OSスケジューラに明示的に制御を譲り、現在のスレッドを一時的に実行可能キューから外し、他のスレッドが実行される機会を与えます。`procyield()`よりもコストは高いですが、より確実にCPUを解放します。比較的長い待機に適しています。
*   **テールレイテンシ (Tail Latency)**: サービスリクエストの応答時間において、特に長い応答時間を示す上位数パーセント（例: 99パーセンタイル、99.9パーセンタイル）のレイテンシを指します。システムのパフォーマンス指標として平均レイテンシだけでなく、テールレイテンシを改善することは、ユーザー体験の向上に非常に重要です。
*   **過負荷状態 (Oversubscription)**: システムのCPUコア数よりも多くの実行可能なタスク（この場合はゴルーチン）が存在し、CPUリソースが不足している状態を指します。この状態では、スケジューラが頻繁にコンテキストスイッチを行う必要があり、パフォーマンスが低下しやすくなります。

## 技術的詳細

このコミットの主要な目的は、Goランタイム内のGC関連関数である`scang`と`casgstatus`におけるアクティブスピンループを改善し、CPUの無駄な消費を削減することです。

**問題の特定:**
コミットメッセージによると、`go install -a std`のプロファイル結果から、`scang`関数がCPU時間の11%をアクティブスピンに費やしていることが判明しました。これは、GCがゴルーチンのスタックをスキャンする際に、ゴルーチンの状態が変化するのを待つために、CPUを継続的にポーリングしていたためです。`casgstatus`も同様の問題を抱えていました。これらの関数での待機時間は、`scang`で数ミリ秒、`casgstatus`で数百マイクロ秒に及ぶことがあり、この間CPUを占有し続けることは非効率的でした。特に、システムがわずかに過負荷状態になると、GCゴルーチンがユーザーコードの実行機会を奪い、テールレイテンシが増加するという悪影響がありました。

**解決策の導入:**
このコミットでは、アクティブスピンループを完全に排除する代わりに、合理的な待機時間の後にOSスケジューラに制御を譲る（yieldする）メカニズムを導入しました。これにより、CPUを無駄に消費し続けることを防ぎつつ、必要な条件が満たされるのを待つことができます。

具体的には、以下のロジックが導入されました。
1.  **`yieldDelay`の導入**: `scang`と`casgstatus`のループ内に、それぞれ`yieldDelay`という定数を定義しました。`scang`には10マイクロ秒（10 * 1000ナノ秒）、`casgstatus`には5マイクロ秒（5 * 1000ナノ秒）が設定されました。
2.  **`nextYield`の追跡**: ループの初回実行時に、`nanotime()`を使用して次にOSにyieldすべき時刻`nextYield`を計算します（現在の時刻 + `yieldDelay`）。
3.  **条件付きyield**:
    *   ループ内で`nanotime()`が`nextYield`よりも小さい間は、`procyield()`を呼び出します。`procyield()`はCPUに短いヒントを与え、他の実行可能なスレッドがあればCPUを譲ることを促しますが、OSスケジューラを介さないためオーバーヘッドが小さいです。`casgstatus`では1回、`scang`では10回`procyield()`を呼び出すことで、より短い期間でのポーリングを試みます。
    *   `nanotime()`が`nextYield`以上になった場合（つまり、`yieldDelay`が経過した場合）、`osyield()`を呼び出してOSスケジューラに明示的に制御を譲ります。これにより、現在のゴルーチンは実行可能キューから外され、他のゴルーチンやOSスレッドが実行される機会を得ます。`osyield()`の後、`nextYield`は`yieldDelay/2`だけ延長され、次のOSへのyieldまでの期間が調整されます。

**`yieldDelay`のパラメータ選択:**
`yieldDelay`の最適な値を見つけるために、`golang.org/x/benchmarks/http`ベンチマークを使用して、様々な`yieldDelay`設定とシステム負荷（過負荷レベル）の下でのテールレイテンシが測定されました。

*   **過負荷なしの場合**: `scang`と`casgstatus`の`yieldDelay`を様々に変更してベンチマークを実行。結果として、`scang` 10000ナノ秒（10µs）、`casgstatus` 5000ナノ秒（5µs）の組み合わせが、Latency-999（99.9パーセンタイルレイテンシ）で5〜8%の改善を示しました。
*   **わずかな過負荷の場合**: バックグラウンドで別のHTTPベンチマークを`GOMAXPROCS`を減らして実行し、わずかな過負荷状態をシミュレート。このシナリオでも、同様の`yieldDelay`設定でLatency-999が6〜8%改善されました。
*   **顕著な過負荷の場合**: バックグラウンドで別のHTTPベンチマークを`GOMAXPROCS`をフルで使用して実行し、顕著な過負荷状態をシミュレート。この最も厳しいシナリオでは、Latency-999が8〜10%改善され、この変更が過負荷状況下で特に効果的であることが示されました。

これらのベンチマーク結果から、`scang`に10µs、`casgstatus`に5µsの`yieldDelay`が、テールレイテンシを5〜10%削減する合理的な妥協点として選択されました。

**全体的なパフォーマンスへの影響:**
`go install -a std`ベンチマークの結果は、この変更が全体的なシステムパフォーマンスに良い影響を与えたことを示しています（4コアマシンでの結果）。
*   `Time` (総実行時間): 5.34%削減
*   `UserTime` (ユーザーCPU時間): 6.76%削減
*   `SysTime` (システムCPU時間): 7.00%増加 (OSへのyieldが増えたため、システムコールが増加したことを示唆)
*   `CpuLoad` (CPU使用率): 0.59%削減
*   `MaxRSS` (最大常駐セットサイズ): ほぼ変化なし

`SysTime`の増加は、`osyield()`の呼び出しが増えたことによるOSスケジューラへのコンテキストスイッチの増加を反映していますが、`UserTime`と`Time`の全体的な削減は、CPUの無駄な消費が減り、より効率的にタスクが完了したことを示しています。

## コアとなるコードの解説

### `casgstatus`関数

`casgstatus`関数は、ゴルーチン`gp`の`atomicstatus`を`oldval`から`newval`へアトミックに更新しようとします。この関数は、GC中にゴルーチンの状態を安全に遷移させるために使用されます。

変更点：
1.  **`yieldDelay`と`nextYield`の導入**:
    ```go
    const yieldDelay = 5 * 1000 // 5マイクロ秒
    var nextYield int64
    ```
    `yieldDelay`は、OSに制御を譲るまでの最大アクティブスピン時間（5マイクロ秒）を定義します。`nextYield`は、次にOSにyieldすべき`nanotime()`の値を保持します。
2.  **ループカウンタ`i`の導入**:
    ```go
    for i := 0; !atomic.Cas(&gp.atomicstatus, oldval, newval); i++ {
    ```
    ループが何回繰り返されたかを追跡するために`i`が導入されました。
3.  **条件付きyieldロジック**:
    ```go
    if i == 0 {
        nextYield = nanotime() + yieldDelay
    }
    if nanotime() < nextYield {
        for x := 0; x < 10 && gp.atomicstatus != oldval; x++ {
            procyield(1)
        }
    } else {
        osyield()
        nextYield = nanotime() + yieldDelay/2
    }
    ```
    *   ループの初回（`i == 0`）で、`nextYield`が現在の`nanotime()`に`yieldDelay`を加算して初期化されます。
    *   現在の`nanotime()`が`nextYield`よりも小さい場合（つまり、まだ`yieldDelay`が経過していない場合）、内部ループで最大10回`procyield(1)`を呼び出します。これは、CPUに短いヒントを与えて他のスレッドに実行を譲ることを促しますが、OSスケジューラを介さないため、オーバーヘッドが低く、短い待機に適しています。
    *   `yieldDelay`が経過した場合（`nanotime() >= nextYield`）、`osyield()`を呼び出してOSスケジューラに明示的に制御を譲ります。これにより、現在のゴルーチンは実行可能キューから外され、他のタスクが実行される機会を得ます。`osyield()`の後、`nextYield`は`yieldDelay`の半分だけ延長され、次のOSへのyieldまでの期間が調整されます。これは、OSへのyieldが比較的コストの高い操作であるため、頻繁に呼び出しすぎないようにするためと考えられます。

### `scang`関数

`scang`関数は、GC中に特定のゴルーチン`gp`のスタックをスキャンする役割を担います。ゴルーチンがスキャン可能な状態になるまで待機する必要があるため、ここでもアクティブスピンループが使用されていました。

変更点：
1.  **`yieldDelay`と`nextYield`の導入**:
    ```go
    const yieldDelay = 10 * 1000 // 10マイクロ秒
    var nextYield int64
    ```
    `casgstatus`と同様に、`yieldDelay`（ここでは10マイクロ秒）と`nextYield`が導入されます。
2.  **ループラベル`loop`とカウンタ`i`の導入**:
    ```go
    loop:
    for i := 0; !gp.gcscandone; i++ {
    ```
    `break loop`で外側のループを抜けるためにラベル`loop`が追加され、`casgstatus`と同様にループカウンタ`i`が導入されました。
3.  **`break loop`の追加**:
    ゴルーチンが`_Gdead`状態になった場合や、GCスキャンが完了して`gp.gcscandone`が`true`になった場合に、`break loop`でループを即座に終了するように変更されました。これにより、不要な待機をさらに削減します。
4.  **条件付きyieldロジック**:
    ```go
    if i == 0 {
        nextYield = nanotime() + yieldDelay
    }
    if nanotime() < nextYield {
        procyield(10)
    } else {
        osyield()
        nextYield = nanotime() + yieldDelay/2
    }
    ```
    `casgstatus`と同様のロジックが適用されますが、`procyield`の呼び出し回数が10回に固定されています。`scang`の`yieldDelay`が`casgstatus`よりも長いのは、`scang`の待機時間がより長い傾向にあるためです。

これらの変更により、GoランタイムはGC関連の待機中にCPUを無駄に消費するアクティブスピンを減らし、代わりにOSスケジューラに制御を譲ることで、システムリソースをより効率的に利用できるようになりました。結果として、特に過負荷状態でのテールレイテンシが改善され、全体的なパフォーマンスが向上しました。

# [インデックス 26142] ファイルの概要

このコミットは、Goランタイムのプロファイリングにおける競合状態を修正するものです。具体的には、`src/runtime/proc.go` ファイルが変更されています。このファイルは、Goランタイムのプロセス管理、スケジューリング、およびシグナル処理に関連する重要な機能を含んでいます。

## コミット

Goランタイムにおいて、`sigprof`（プロファイリングシグナル）がCgo呼び出し中またはライブラリ呼び出し中のGoroutineのスタックトレースを生成する際に発生する可能性のある競合状態を修正します。この修正は、スタックバリアロックが保持されている間は、Cgoおよびライブラリ呼び出しのスタックトレースを許可しないようにすることで、"missed stack barrier"パニックを防ぎます。

## 元コミット内容

```
runtime: require the stack barrier lock to traceback cgo and libcalls

Currently, if sigprof determines that the G is in user code (not cgo
or libcall code), it will only traceback the G stack if it can acquire
the stack barrier lock. However, it has no such restriction if the G
is in cgo or libcall code. Because cgo calls count as syscalls, stack
scanning and stack barrier installation can occur during a cgo call,
which means sigprof could attempt to traceback a G in a cgo call while
scanstack is installing stack barriers in that G's stack. As a result,
the following sequence of events can cause the sigprof traceback to
panic with "missed stack barrier":

1. M1: G1 performs a Cgo call (which, on Windows, is any system call,
   which could explain why this is easier to reproduce on Windows).

2. M1: The Cgo call puts G1 into _Gsyscall state.

3. M2: GC starts a scan of G1's stack. It puts G1 in to _Gscansyscall
   and acquires the stack barrier lock.

4. M3: A profiling signal comes in. On Windows this is a global
   (though I don't think this matters), so the runtime stops M1 and
   calls sigprof for G1.

5. M3: sigprof fails to acquire the stack barrier lock (because the
   GC's stack scan holds it).

6. M3: sigprof observes that G1 is in a Cgo call, so it calls
   gentraceback on G1 with its Cgo transition point.

7. M3: gentraceback on G1 grabs the currently empty g.stkbar slice.

8. M2: GC finishes scanning G1's stack and installing stack barriers.

9. M3: gentraceback encounters one of the just-installed stack
   barriers and panics.

This commit fixes this by only allowing cgo tracebacks if sigprof can
acquire the stack barrier lock, just like in the regular user
traceback case.

For good measure, we put the same constraint on libcall tracebacks.
This case is probably already safe because, unlike cgo calls, libcalls
leave the G in _Grunning and prevent reaching a safe point, so
scanstack cannot run during a libcall. However, this also means that
sigprof will always acquire the stack barrier lock without contention,
so there's no cost to adding this constraint to libcall tracebacks.

Fixes #12528. For 1.5.3 (will require some backporting).
```

## 変更の背景

このコミットは、Goランタイムにおけるプロファイリングの際に発生する特定の競合状態を解決するために導入されました。以前のGoランタイムでは、`sigprof`（プロファイリングシグナル）がGoroutineのスタックトレースを生成する際、そのGoroutineが通常のGoコードを実行している場合はスタックバリアロックの取得を試みていました。しかし、Cgo（GoからC言語のコードを呼び出すメカニズム）呼び出し中やライブラリ呼び出し中のGoroutineに対しては、このロック取得の制限がありませんでした。

この制限の欠如が、ガベージコレクション（GC）によるスタックのスキャンとスタックバリアの設置がCgo呼び出し中のGoroutineのスタックに対して行われている最中に、`sigprof`がそのGoroutineのスタックトレースを試みるという競合状態を引き起こしました。特にWindows環境では、すべてのシステムコールがCgo呼び出しとして扱われるため、この問題が再現しやすかったとされています。

この競合状態の結果、`sigprof`がスタックトレースを生成する際に、GCがちょうど設置したばかりのスタックバリアに遭遇し、「missed stack barrier」というパニックを引き起こす可能性がありました。これは、プロファイリング中にランタイムがクラッシュするという深刻な問題であり、システムの安定性とプロファイリングの信頼性を損なうものでした。このコミットは、この不安定性を排除し、プロファイリングの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を把握しておく必要があります。

*   **Goroutine (G)**: Goランタイムが管理する軽量なスレッドのような実行単位です。
*   **M (Machine)**: オペレーティングシステムのスレッドを表します。GoroutineはM上で実行されます。
*   **P (Processor)**: Mに割り当てられ、Goroutineの実行をスケジュールする論理プロセッサです。
*   **Cgo**: GoプログラムからC言語の関数を呼び出すためのメカニズムです。Cgo呼び出し中は、GoランタイムのスケジューラがGoroutineを管理できない状態になることがあります。
*   **Libcall (Library Call)**: 特にWindowsにおいて、GoランタイムがOSのライブラリ関数を直接呼び出す際に使用される概念です。これもCgoと同様に、Goランタイムの通常の管理下から一時的に外れることがあります。
*   **`sigprof` (Profiling Signal)**: プロファイリングのために定期的にGoランタイムに送信されるシグナルです。このシグナルを受け取ると、ランタイムは現在実行中のGoroutineのスタックトレースを収集し、プロファイリングデータとして記録します。
*   **スタックバリア (Stack Barrier)**: Goのガベージコレクション（GC）は、スタックをスキャンして参照されているオブジェクトを特定します。このスキャン中にスタックの内容が変更されると問題が発生するため、GCはスタックバリアと呼ばれるメカニズムを使用して、スタックのスキャンと同時にスタックが変更されることを防ぎます。スタックバリアロックは、このスタックバリアの設置やスキャンを保護するための排他ロックです。
*   **`gentraceback`**: Goランタイム内部の関数で、指定されたGoroutineのスタックトレースを生成します。
*   **Goroutineの状態**: Goroutineは様々な状態を持ちます。
    *   `_Grunning`: 通常のGoコードを実行中。
    *   `_Gsyscall`: システムコール（Cgo呼び出しを含む）を実行中。この状態のGoroutineは、Goスケジューラから一時的に切り離されます。
    *   `_Gscansyscall`: システムコール中にあり、かつGCによってスタックがスキャンされている状態。
*   **`g.stkbar`**: Goroutineのスタックバリア情報を保持するスライスです。GCがスタックバリアを設置する際にこのスライスが更新されます。

## 技術的詳細

このコミットが修正する問題は、以下の具体的なステップで発生します。

1.  **M1: G1がCgo呼び出しを実行**: Goroutine G1がCgo関数を呼び出します。Windowsでは、これは任意のシステムコールに該当する場合があります。
2.  **M1: G1が`_Gsyscall`状態に移行**: Cgo呼び出しにより、G1は`_Gsyscall`状態になります。これは、GoスケジューラがG1の実行を一時的に中断し、OSがCコードの実行を管理していることを意味します。
3.  **M2: GCがG1のスタックをスキャン開始**: 別のM（M2）上で、ガベージコレクタがG1のスタックのスキャンを開始します。この際、G1は`_Gscansyscall`状態に移行し、GCはスタックバリアロックを取得します。これにより、他のGoroutineがG1のスタックにアクセスして変更することを防ぎます。
4.  **M3: プロファイリングシグナルが到着**: 別のM（M3）上で、プロファイリングシグナル（`sigprof`）が到着します。このシグナルはM1を停止させ、G1のプロファイリングを開始します。
5.  **M3: `sigprof`がスタックバリアロックの取得に失敗**: `sigprof`はスタックバリアロックの取得を試みますが、M2上のGCが既にロックを保持しているため、取得に失敗します。
6.  **M3: `sigprof`がCgo呼び出し中のG1を検知**: `sigprof`はG1がCgo呼び出し中であることを検知します。従来のロジックでは、Cgo呼び出し中のGoroutineに対してはスタックバリアロックの取得が必須ではなかったため、ロックが取得できなくてもスタックトレースを続行します。
7.  **M3: `gentraceback`が`g.stkbar`スライスを取得**: `sigprof`は`gentraceback`を呼び出し、G1のCgo遷移点からスタックトレースを開始します。`gentraceback`は、その時点では空であるG1の`g.stkbar`スライスを取得します。
8.  **M2: GCがスタックバリアの設置を完了**: M2上のGCはG1のスタックのスキャンとスタックバリアの設置を完了します。これにより、`g.stkbar`スライスが更新されます。
9.  **M3: `gentraceback`がパニック**: M3上の`gentraceback`は、GCがちょうど設置したばかりのスタックバリアに遭遇します。しかし、`gentraceback`が最初に`g.stkbar`スライスを取得した時点では空であったため、このバリアの存在を予期しておらず、「missed stack barrier」というパニックを引き起こします。

このコミットは、この問題に対処するために、Cgo呼び出し中およびライブラリ呼び出し中のGoroutineのスタックトレースを行う際にも、通常のGoコードのスタックトレースと同様に、`sigprof`がスタックバリアロックを正常に取得できることを必須とします。これにより、GCがスタックバリアを設置している最中に`gentraceback`が実行されることを防ぎ、競合状態によるパニックを回避します。

具体的には、`tracebackUser`というフラグが導入され、これが真（スタックバリアロックが取得できた場合）の場合にのみ、Cgoおよびlibcallのスタックトレースが許可されるようになります。libcallの場合、Goroutineは通常`_Grunning`状態に留まり、セーフポイントに到達できないため、`scanstack`が実行されることはありません。そのため、libcallのケースではスタックバリアロックの競合は発生しにくいですが、一貫性と将来的な安全性のために同様の制約が追加されています。これにより、プロファイリングの堅牢性が向上し、ランタイムの安定性が確保されます。

## コアとなるコードの解説

変更は`src/runtime/proc.go`ファイルの`sigprof`関数内で行われています。この関数は、プロファイリングシグナルが到着した際に呼び出され、スタックトレースを収集する役割を担います。

変更点は以下の2つの`if`文に`&& tracebackUser`という条件が追加されたことです。

1.  **Cgo呼び出しのスタックトレース条件**:
    ```diff
    -	if mp.ncgo > 0 && mp.curg != nil && mp.curg.syscallpc != 0 && mp.curg.syscallsp != 0 {
    +	if mp.ncgo > 0 && mp.curg != nil && mp.curg.syscallpc != 0 && mp.curg.syscallsp != 0 && tracebackUser {
    ```
    この`if`文は、現在のM（`mp`）がCgo呼び出し中であり、かつ現在のGoroutine（`mp.curg`）がシステムコールを実行している状態（`syscallpc`と`syscallsp`が非ゼロ）である場合に、Cgo呼び出しのスタックトレースを試みるためのものです。
    追加された`&& tracebackUser`は、`sigprof`関数内でスタックバリアロックの取得が成功した場合に設定されるフラグです。これにより、Cgo呼び出し中のGoroutineのスタックトレースは、スタックバリアロックが安全に取得できた場合にのみ実行されるようになります。これは、GCがスタックバリアを設置している最中にスタックトレースが実行されることを防ぎ、前述のパニックを回避します。

2.  **Libcall（Windows上のシステムコール）のスタックトレース条件**:
    ```diff
    -		if GOOS == "windows" && n == 0 && mp.libcallg != 0 && mp.libcallpc != 0 && mp.libcallsp != 0 {
    +		if GOOS == "windows" && n == 0 && mp.libcallg != 0 && mp.libcallpc != 0 && mp.libcallsp != 0 && tracebackUser {
    ```
    この`if`文は、OSがWindowsであり、かつ現在のMがライブラリ呼び出し（`libcall`）を実行している状態である場合に、そのライブラリ呼び出しのスタックトレースを試みるためのものです。
    ここにも`&& tracebackUser`が追加されています。コミットメッセージにもあるように、libcallの場合はCgoほど競合のリスクは高くないとされていますが、一貫性と将来的な安全性のために同様の制約が適用されました。これにより、libcallのスタックトレースもスタックバリアロックの保護下で行われることが保証されます。

これらの変更により、`sigprof`がスタックトレースを生成する際に、GCによるスタックバリアの設置と競合する可能性のある状況が排除され、Goランタイムの安定性とプロファイリングの信頼性が向上しました。

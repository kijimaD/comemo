## 元コミット内容

このコミットは、GoコンパイラのSSA（Static Single Assignment）ステージにおいて、スタックにスピルされる値（レジスタに割り当てられなかった値）のために使用されるスタック領域の再利用を実装するものです。具体的には、各型ごとにスピル用のスタックスロットのリストを管理し、互いに干渉しないスピルに対してこれらのスタックスロットを再利用します。これにより、関数のスタックフレームサイズが削減されます。例として、`runtime.mSpan_Sweep` 関数のスタックフレームサイズは584バイトから392バイトに、`heapBitsSetType` 関数は576バイトから152バイトに削減されたと報告されています。

## 変更の背景

コンパイラがプログラムを機械語に変換する際、変数は通常CPUのレジスタに割り当てられます。しかし、利用可能なレジスタの数には限りがあるため、全ての変数をレジスタに割り当てることはできません。レジスタに割り当てられなかった変数は「スピル（spill）」され、メモリ（通常は関数のスタックフレーム）に一時的に保存されます。

以前のGoコンパイラでは、スピルされた値に対してスタックスロットを割り当てる際に、効率的な再利用が行われていませんでした。これは、異なるライフタイムを持つ変数であっても、それぞれに独立したスタックスロットが割り当てられる傾向があったため、スタックフレームが不必要に大きくなる原因となっていました。スタックフレームが大きいと、メモリ使用量が増加し、関数呼び出しのオーバーヘッドが増える可能性があります。

このコミットの目的は、この非効率性を解消し、スタックスロットの再利用を促進することで、スタックフレームサイズを削減し、結果としてプログラムの実行効率とメモリ効率を向上させることにあります。特に、Goランタイムのようなパフォーマンスが重視されるコードでは、このような最適化が大きな影響を与えます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化の中間表現（IR）の一種です。SSA形式では、各変数が一度だけ定義されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（デッドコード削除、定数伝播、共通部分式除去など）を効率的に適用できるようになります。

例:
```
// 非SSA形式
x = 1
x = x + 1
y = x * 2

// SSA形式
x1 = 1
x2 = x1 + 1
y1 = x2 * 2
```
SSA形式では、変数の各定義に新しいバージョン番号が割り当てられます。複数の制御フローパスが合流する点（例: if文の終わりやループの終わり）では、異なるパスで定義された同じ変数のバージョンを結合するために「Φ（ファイ）関数」が導入されます。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要な最適化フェーズです。目的は、プログラム中の変数をCPUの高速なレジスタに割り当てることです。レジスタはメモリよりもはるかに高速にアクセスできるため、レジスタ割り当ての効率はプログラムの実行速度に直結します。

レジスタ割り当ては通常、以下のステップで行われます。
*   **ライブネス解析 (Liveness Analysis)**: 各プログラムポイントでどの変数が「ライブ」（将来的に使用される可能性がある）であるかを特定します。
*   **干渉グラフの構築 (Interference Graph Construction)**: ライブネス解析の結果に基づき、干渉グラフを構築します。このグラフでは、ノードが変数を表し、エッジは2つの変数が同時にライブであり、したがって同じレジスタを共有できないことを示します。
*   **グラフ彩色 (Graph Coloring)**: 干渉グラフを彩色します。利用可能なレジスタの数を色として、隣接するノードが異なる色を持つようにグラフを彩色します。彩色に成功すれば、各変数をレジスタに割り当てることができます。

### 3. スピル (Spilling)

干渉グラフの彩色に失敗した場合（つまり、利用可能なレジスタの数よりも多くの変数が同時にライブである場合）、一部の変数はレジスタに割り当てることができません。これらの変数は「スピル」され、メモリ（通常はスタックフレーム）に保存されます。スピルされた値は、使用される直前にメモリからレジスタにロードされ、変更された場合はメモリにストアし直されます。このロード/ストア操作はオーバーヘッドとなるため、スピルの回数を減らし、スピルされた値が使用するメモリ領域を効率的に管理することが重要です。

### 4. スタックスロット (Stack Slots)

スピルされた値や、関数呼び出しの引数、ローカル変数などを格納するために、関数のスタックフレーム内に確保されるメモリ領域をスタックスロットと呼びます。

### 5. Φ（ファイ）関数 (Phi Functions) とスタックPhi

SSA形式におけるΦ関数は、複数の制御フローパスが合流する点で、異なるパスで定義された同じ変数のバージョンを結合するために使用されます。レジスタ割り当ての文脈では、Φ関数は特別な扱いを必要とします。もしΦ関数の引数と結果が異なるレジスタに割り当てられた場合、合流点で値を移動させるための追加の命令（ムーブ命令）が必要になります。

このコミットでは、特に「スタックPhi」という概念が導入されています。これは、レジスタに割り当てられずスタックにスピルされるΦ関数とその引数を指します。スタックPhiとその引数は、同じスタックスロットを共有する必要があります。

### 6. ライブ変数解析 (Live Variable Analysis)

あるプログラムポイントにおいて、変数が「ライブ」であるとは、その変数の現在の値が将来のどこかの時点で読み取られる可能性があることを意味します。ライブネス解析は、コンパイラがレジスタ割り当てやデッドコード削除などの最適化を行う上で不可欠な情報を提供します。このコミットでは、スピルされた値のスタックスロットを再利用するために、これらの値のライブ範囲を正確に把握することが重要になります。

## 技術的詳細

このコミットの主要な技術的改善点は、GoコンパイラのSSAバックエンドにおけるスタックスロットの割り当て戦略にあります。以前は、スピルされた値に対してスタックスロットが比較的単純に割り当てられていましたが、この変更により、レジスタ割り当てと同様の干渉グラフベースのアプローチをスタックスロットの再利用に適用しています。

### 1. 型ごとのスタックスロット管理

新しいアプローチでは、コンパイラは各データ型（`v.Type`）ごとに、その型を持つスピルされた値のために割り当てられたスタックスロットのリスト（`locations` マップ）を管理します。これにより、同じ型の値が同じサイズのスタックスロットを共有しやすくなります。

### 2. スピル値の干渉グラフ構築

レジスタ割り当てと同様に、スタックスロットの再利用のためにも「干渉」の概念が導入されます。2つのスピルされた値が同時にライブである場合、それらは同じスタックスロットを共有できません。このコミットでは、`StoreReg` オペレーション（レジスタからスタックへのスピル）と「スタックPhi」オペレーション（スタックにスピルされるΦ関数）の間で干渉グラフを構築します。

*   **`liveSpills()` 関数**: この新しい関数は、各ブロックの各サクセッサエッジ（後続ブロックへの遷移）でライブである`StoreReg`およびスタックPhiの値のIDのリストを計算します。これは、レジスタ割り当てにおけるライブネス解析に似ていますが、スピルされた値に特化しています。
    *   `liveSpills`は、ブロックのポストオーダー順（逆順）にイテレートすることで、ライブネス情報が後方へ伝播する性質を利用し、安定化を早めます。
    *   各ブロック内で、値のリストを逆順に処理し、`OpStoreReg`で値が「デッド」になり、`OpLoadReg`で値が「ライブ」になるというロジックでライブセットを更新します。
    *   Φ関数については、その引数も考慮してライブセットを更新します。
*   **`interfere` 配列**: `liveSpills`の結果を利用して、`stackalloc`関数内で`interfere`配列が構築されます。これは、`v.ID`をインデックスとして、`v`と同時にライブである他の値のIDのリストを格納します。これにより、どの値がどの値とスタックスロットを共有できないかが明確になります。

### 3. スタックPhiの特別な扱い

Φ関数はSSA形式の特性上、特別な考慮が必要です。スタックにスピルされるΦ関数（`v.isStackPhi()`で判定）とその引数（`v.Args`）は、同じスタックスロットを使用しなければなりません。このため、`phiArg`というブール配列が導入され、`StoreReg`オペレーションがΦ関数の引数であるかどうかを追跡します。Φ関数の引数である`StoreReg`には、個別にスタックスロットを割り当てず、対応するΦ関数と同じスロットを割り当てます。

### 4. スタックスロットの割り当てと再利用ロジック

`stackalloc`関数内の主要なループで、各`StoreReg`およびスタックPhiオペレーションに対してスタックスロットが割り当てられます。

*   **`locations[v.Type]`**: 現在処理している値`v`の型に対応する既存のスタックスロットのリストを取得します。
*   **`used` 配列**: `interfere[v.ID]`にリストされている、`v`と干渉する値が現在どのスタックスロットを使用しているかをマークするために使用されます。
*   **空きスロットの検索**: `locations[v.Type]`の中から、`used`配列でマークされていない（つまり、`v`と干渉しない）最初のスタックスロットを探します。
*   **新規スロットの割り当て**: もし利用可能な空きスロットが見つからなければ、`f.Config.fe.Auto(v.Type)`を呼び出して新しいスタックスロットを割り当て、`locations[v.Type]`に追加します。
*   **スロットの割り当て**: 見つかった（または新しく割り当てられた）スタックスロットを`v`に割り当てます（`f.setHome(v, loc)`）。`slots[v.ID]`には、`locations[v.Type]`内でのそのスロットのインデックスが記録されます。
*   **Phi関数の引数への伝播**: もし`v`がスタックPhiであれば、その全ての引数（`v.Args`）にも同じスタックスロットが割り当てられます。

この洗練されたアプローチにより、コンパイラはスタックフレーム内のメモリをより効率的に利用し、全体的なパフォーマンスを向上させることができます。

## コアとなるコードの解説

### `stackalloc(f *Func)` 関数

この関数は、レジスタに割り当てられなかった全てのSSA値（`Value`）に対して、スタックフレーム内のストレージを割り当てます。

1.  **`types := make([]Type, f.NumValues())`**: `f.NumValues()`はSSA値の総数です。各SSA値の型をIDでキャッシュするためのスライスを初期化します。
2.  **`live := f.liveSpills()`**: 新しく追加された`liveSpills`関数を呼び出し、各ブロックの各サクセッサエッジでライブであるスピル値のIDリストを取得します。
3.  **`interfere := make([][]ID, f.NumValues())`**: スピル値間の干渉グラフを表現するためのスライスを初期化します。`interfere[v.ID]`は、`v`と同時にライブである他のスピル値のIDのリストを格納します。
4.  **干渉グラフの構築**:
    *   各ブロックを逆順にイテレートし、`liveSpills`と同様のライブネス解析ロジック（`s.clear()`, `s.addAll()`, `s.remove()`, `s.add()`）を使用して、ブロック内の各値`v`について、その値が`OpStoreReg`または`isStackPhi()`である場合に、同時にライブである他の値との干渉関係を`interfere`配列に記録します。
    *   `v.Type == types[id]`のチェックにより、同じ型の値のみが干渉関係として考慮されます。これは、異なる型の値は異なるサイズのスタックスロットを必要とするため、通常は同じスロットを共有できないためです。
5.  **`phiArg := make([]bool, f.NumValues())`**: Φ関数の引数である`StoreReg`オペレーションをマークするためのブールスライスを初期化します。
6.  **Φ関数の引数の特定**: 各ブロックの各値について、それがスタックPhiである場合、その引数（`v.Args`）のIDを`phiArg`に`true`とマークします。これにより、これらの引数には個別のスタックスロットが割り当てられず、対応するPhi関数と同じスロットが割り当てられるようになります。
7.  **`locations := map[Type][]*LocalSlot{}`**: 各型ごとに、その型のために割り当てられた`LocalSlot`（スタックスロット）のポインタのスライスを管理するマップを初期化します。
8.  **`slots := make([]int, f.NumValues())`**: 各SSA値が`locations[v.Type]`内のどのインデックスのスタックスロットを使用しているかを記録するためのスライスを初期化します。初期値は`-1`（未割り当て）です。
9.  **スタックスロットの割り当てループ**:
    *   各ブロックの各値`v`をイテレートします。
    *   `v`が`OpStoreReg`または`isStackPhi()`であり、かつ`phiArg[v.ID]`が`false`（つまり、Φ関数の引数ではない）の場合に処理を進めます。
    *   **`locs := locations[v.Type]`**: `v`の型に対応する既存のスタックスロットのリストを取得します。
    *   **`used := make([]bool, f.NumValues())`**: `locs`内の各スタックスロットが、`v`と干渉する他の値によって使用されているかどうかをマークするための一時的なブールスライスです。
    *   **干渉するスロットのマーク**: `interfere[v.ID]`にリストされている各値`xid`について、`slots[xid]`が示すスタックスロット（`locs`内のインデックス）を`used[slot] = true`とマークします。
    *   **Phi関数の引数の干渉も考慮**: `v`が`OpPhi`の場合、その引数`a`についても同様に干渉するスロットをマークします。これは、Phiとその引数が同じスロットを共有するため、Phiが干渉するものはその引数も干渉すると見なされるためです。
    *   **空きスロットの検索**: `locs`をイテレートし、`used[i]`が`false`である最初のインデックス`i`（つまり、`v`と干渉しない空きスロット）を探します。
    *   **新規スロットの割り当て**: もし空きスロットが見つからなければ（`i == len(locs)`）、`f.Config.fe.Auto(v.Type)`を呼び出して新しい`LocalSlot`を割り当て、`locs`に追加します。
    *   **スロットの割り当て**: 見つかった（または新しく割り当てられた）スタックスロット`loc`を`v`に割り当てます（`f.setHome(v, loc)`）。`slots[v.ID] = i`で、`v`が使用するスロットのインデックスを記録します。
    *   **Phi関数の引数への伝播**: `v`が`OpPhi`の場合、その全ての引数`a`にも同じ`loc`を割り当て、`slots[a.ID] = i`と記録します。

### `liveSpills() (f *Func) [][][]ID` 関数

この関数は、各ブロックの各サクセッサエッジでライブである`StoreReg`およびスタックPhi値のIDのリストを計算します。

1.  **`live := make([][][]ID, f.NumBlocks())`**: 結果を格納するための3次元スライスを初期化します。`live[b.ID][i]`は、ブロック`b`からその`i`番目のサクセッサへのエッジでライブな値のIDリストです。
2.  **`po := postorder(f)`**: 関数のブロックをポストオーダー順（深さ優先探索の逆順）で取得します。ライブネス解析は後方フロー解析であるため、この順序で処理することで収束が早まります。
3.  **反復計算ループ**: `changed`フラグが`false`になるまでループを繰り返します。
    *   **各ブロック`b`をポストオーダー順に処理**:
        *   **`s.clear()`**: 現在のブロックの終端でライブな値のセット`s`をクリアします。
        *   **サクセッサからのライブネス伝播**: `b`の各サクセッサエッジから`live`情報を`s`にマージします。
        *   **ブロック内での後方伝播**: `b`の値を逆順にイテレートします。
            *   `OpStoreReg`の場合、その値はスタックにストアされたので、それ以降はライブではなくなります（`s.remove(v.ID)`）。
            *   `OpLoadReg`の場合、その引数（元の値）がロードされたので、その引数はライブになります（`s.add(v.Args[0].ID)`）。
            *   `isStackPhi()`の場合、その値はPhi関数として処理されるので、それ以降はライブではなくなります（`s.remove(v.ID)`）。また、Phi関数は後で処理するために`phis`スライスに保存されます。
        *   **プリデセッサへのライブネス伝播**: `b`の各プリデセッサ`p`について、`p`から`b`へのエッジでライブな値のセットを更新します。
            *   `t.clear()`: プリデセッサ`p`のライブセット`t`をクリアします。
            *   `t.addAll(live[p.ID][j])`: 既存のライブ情報を追加します。
            *   `t.addAll(s.contents())`: 現在のブロックの開始点でライブな値（`s`）を追加します。
            *   `for _, v := range phis { t.add(v.Args[i].ID) }`: Phi関数の引数もライブセットに追加します。
            *   もし`t`のサイズが変更された場合、`changed = true`を設定し、`live[p.ID][j]`を更新します。
4.  **`return live`**: 最終的に計算されたライブネス情報を返します。

### `(v *Value) isStackPhi() bool` メソッド

このメソッドは、`Value`がスタックにスピルされるΦ関数であるかどうかを判定します。

*   `v.Op != OpPhi`であれば、Phi関数ではないので`false`。
*   `v.Type == TypeMem`であれば、メモリ型なので`false`（メモリ操作は通常、レジスタ割り当ての対象外）。
*   `v.ID`が`f.RegAlloc`の範囲外であるか、または`f.RegAlloc[v.ID]`が`nil`である場合、その値はレジスタに割り当てられていないため、スタックPhiであると判断されます。

これらの変更により、Goコンパイラはスタックフレームのサイズを大幅に削減し、より効率的なコードを生成できるようになりました。

## 元コミット内容

このコミットは、GoコンパイラのSSA（Static Single Assignment）ステージにおいて、スタックにスピルされる値（レジスタに割り当てられなかった値）のために使用されるスタック領域の再利用を実装するものです。具体的には、各型ごとにスピル用のスタックスロットのリストを管理し、互いに干渉しないスピルに対してこれらのスタックスロットを再利用します。これにより、関数のスタックフレームサイズが削減されます。例として、`runtime.mSpan_Sweep` 関数のスタックフレームサイズは584バイトから392バイトに、`heapBitsSetType` 関数は576バイトから152バイトに削減されたと報告されています。

## 変更の背景

コンパイラがプログラムを機械語に変換する際、変数は通常CPUのレジスタに割り当てられます。しかし、利用可能なレジスタの数には限りがあるため、全ての変数をレジスタに割り当てることはできません。レジスタに割り当てられなかった変数は「スピル（spill）」され、メモリ（通常は関数のスタックフレーム）に一時的に保存されます。

以前のGoコンパイラでは、スピルされた値に対してスタックスロットを割り当てる際に、効率的な再利用が行われていませんでした。これは、異なるライフタイムを持つ変数であっても、それぞれに独立したスタックスロットが割り当てられる傾向があったため、スタックフレームが不必要に大きくなる原因となっていました。スタックフレームが大きいと、メモリ使用量が増加し、関数呼び出しのオーバーヘッドが増える可能性があります。

このコミットの目的は、この非効率性を解消し、スタックスロットの再利用を促進することで、スタックフレームサイズを削減し、結果としてプログラムの実行効率とメモリ効率を向上させることにあります。特に、Goランタイムのようなパフォーマンスが重視されるコードでは、このような最適化が大きな影響を与えます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化の中間表現（IR）の一種です。SSA形式では、各変数が一度だけ定義されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（デッドコード削除、定数伝播、共通部分式除去など）を効率的に適用できるようになります。

例:
```
// 非SSA形式
x = 1
x = x + 1
y = x * 2

// SSA形式
x1 = 1
x2 = x1 + 1
y1 = x2 * 2
```
SSA形式では、変数の各定義に新しいバージョン番号が割り当てられます。複数の制御フローパスが合流する点（例: if文の終わりやループの終わり）では、異なるパスで定義された同じ変数のバージョンを結合するために「Φ（ファイ）関数」が導入されます。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要な最適化フェーズです。目的は、プログラム中の変数をCPUの高速なレジスタに割り当てることです。レジスタはメモリよりもはるかに高速にアクセスできるため、レジスタ割り当ての効率はプログラムの実行速度に直結します。

レジスタ割り当ては通常、以下のステップで行われます。
*   **ライブネス解析 (Liveness Analysis)**: 各プログラムポイントでどの変数が「ライブ」（将来的に使用される可能性がある）であるかを特定します。
*   **干渉グラフの構築 (Interference Graph Construction)**: ライブネス解析の結果に基づき、干渉グラフを構築します。このグラフでは、ノードが変数を表し、エッジは2つの変数が同時にライブであり、したがって同じレジスタを共有できないことを示します。
*   **グラフ彩色 (Graph Coloring)**: 干渉グラフを彩色します。利用可能なレジスタの数を色として、隣接するノードが異なる色を持つようにグラフを彩色します。彩色に成功すれば、各変数をレジスタに割り当てることができます。

### 3. スピル (Spilling)

干渉グラフの彩色に失敗した場合（つまり、利用可能なレジスタの数よりも多くの変数が同時にライブである場合）、一部の変数はレジスタに割り当てることができません。これらの変数は「スピル」され、メモリ（通常はスタックフレーム）に保存されます。スピルされた値は、使用される直前にメモリからレジスタにロードされ、変更された場合はメモリにストアし直されます。このロード/ストア操作はオーバーヘッドとなるため、スピルの回数を減らし、スピルされた値が使用するメモリ領域を効率的に管理することが重要です。

### 4. スタックスロット (Stack Slots)

スピルされた値や、関数呼び出しの引数、ローカル変数などを格納するために、関数のスタックフレーム内に確保されるメモリ領域をスタックスロットと呼びます。

### 5. Φ（ファイ）関数 (Phi Functions) とスタックPhi

SSA形式におけるΦ関数は、複数の制御フローパスが合流する点で、異なるパスで定義された同じ変数のバージョンを結合するために使用されます。レジスタ割り当ての文脈では、Φ関数は特別な扱いを必要とします。もしΦ関数の引数と結果が異なるレジスタに割り当てられた場合、合流点で値を移動させるための追加の命令（ムーブ命令）が必要になります。

このコミットでは、特に「スタックPhi」という概念が導入されています。これは、レジスタに割り当てられずスタックにスピルされるΦ関数とその引数を指します。スタックPhiとその引数は、同じスタックスロットを共有する必要があります。

### 6. ライブ変数解析 (Live Variable Analysis)

あるプログラムポイントにおいて、変数が「ライブ」であるとは、その変数の現在の値が将来のどこかの時点で読み取られる可能性があることを意味します。ライブネス解析は、コンパイラがレジスタ割り当てやデッドコード削除などの最適化を行う上で不可欠な情報を提供します。このコミットでは、スピルされた値のスタックスロットを再利用するために、これらの値のライブ範囲を正確に把握することが重要になります。

## 技術的詳細

このコミットの主要な技術的改善点は、GoコンパイラのSSAバックエンドにおけるスタックスロットの割り当て戦略にあります。以前は、スピルされた値に対してスタックスロットが比較的単純に割り当てられていましたが、この変更により、レジスタ割り当てと同様の干渉グラフベースのアプローチをスタックスロットの再利用に適用しています。

### 1. 型ごとのスタックスロット管理

新しいアプローチでは、コンパイラは各データ型（`v.Type`）ごとに、その型を持つスピルされた値のために割り当てられたスタックスロットのリスト（`locations` マップ）を管理します。これにより、同じ型の値が同じサイズのスタックスロットを共有しやすくなります。

### 2. スピル値の干渉グラフ構築

レジスタ割り当てと同様に、スタックスロットの再利用のためにも「干渉」の概念が導入されます。2つのスピルされた値が同時にライブである場合、それらは同じスタックスロットを共有できません。このコミットでは、`StoreReg` オペレーション（レジスタからスタックへのスピル）と「スタックPhi」オペレーション（スタックにスピルされるΦ関数）の間で干渉グラフを構築します。

*   **`liveSpills()` 関数**: この新しい関数は、各ブロックの各サクセッサエッジ（後続ブロックへの遷移）でライブである`StoreReg`およびスタックPhiの値のIDのリストを計算します。これは、レジスタ割り当てにおけるライブネス解析に似ていますが、スピルされた値に特化しています。
    *   `liveSpills`は、ブロックのポストオーダー順（逆順）にイテレートすることで、ライブネス情報が後方へ伝播する性質を利用し、安定化を早めます。
    *   各ブロック内で、値のリストを逆順に処理し、`OpStoreReg`で値が「デッド」になり、`OpLoadReg`で値が「ライブ」になるというロジックでライブセットを更新します。
    *   Φ関数については、その引数も考慮してライブセットを更新します。
*   **`interfere` 配列**: `liveSpills`の結果を利用して、`stackalloc`関数内で`interfere`配列が構築されます。これは、`v.ID`をインデックスとして、`v`と同時にライブである他の値のIDのリストを格納します。これにより、どの値がどの値とスタックスロットを共有できないかが明確になります。

### 3. スタックPhiの特別な扱い

Φ関数はSSA形式の特性上、特別な考慮が必要です。スタックにスピルされるΦ関数（`v.isStackPhi()`で判定）とその引数（`v.Args`）は、同じスタックスロットを使用しなければなりません。このため、`phiArg`というブール配列が導入され、`StoreReg`オペレーションがΦ関数の引数であるかどうかを追跡します。Φ関数の引数である`StoreReg`には、個別にスタックスロットを割り当てず、対応するΦ関数と同じスロットを割り当てます。

### 4. スタックスロットの割り当てと再利用ロジック

`stackalloc`関数内の主要なループで、各`StoreReg`およびスタックPhiオペレーションに対してスタックスロットが割り当てられます。

*   **`locations[v.Type]`**: 現在処理している値`v`の型に対応する既存のスタックスロットのリストを取得します。
*   **`used` 配列**: `interfere[v.ID]`にリストされている、`v`と干渉する他の値が現在どのスタックスロットを使用しているかをマークするために使用されます。
*   **空きスロットの検索**: `locations[v.Type]`の中から、`used`配列でマークされていない（つまり、`v`と干渉しない）最初のスタックスロットを探します。
*   **新規スロットの割り当て**: もし利用可能な空きスロットが見つからなければ（`i == len(locs)`）、`f.Config.fe.Auto(v.Type)`を呼び出して新しいスタックスロットを割り当て、`locs`に追加します。
*   **スロットの割り当て**: 見つかった（または新しく割り当てられた）スタックスロット`loc`を`v`に割り当てます（`f.setHome(v, loc)`）。`slots[v.ID]`には、`locations[v.Type]`内でのそのスロットのインデックスが記録されます。
*   **Phi関数の引数への伝播**: `v`が`OpPhi`の場合、その全ての引数（`v.Args`）にも同じ`loc`を割り当て、`slots[a.ID] = i`と記録します。

この洗練されたアプローチにより、Goコンパイラはスタックフレームのサイズを大幅に削減し、より効率的なコードを生成できるようになりました。

## コアとなるコードの解説

### `stackalloc(f *Func)` 関数

この関数は、レジスタに割り当てられなかった全てのSSA値（`Value`）に対して、スタックフレーム内のストレージを割り当てます。

1.  **`types := make([]Type, f.NumValues())`**: `f.NumValues()`はSSA値の総数です。各SSA値の型をIDでキャッシュするためのスライスを初期化します。
2.  **`live := f.liveSpills()`**: 新しく追加された`liveSpills`関数を呼び出し、各ブロックの各サクセッサエッジでライブであるスピル値のIDリストを取得します。
3.  **`interfere := make([][]ID, f.NumValues())`**: スピル値間の干渉グラフを表現するためのスライスを初期化します。`interfere[v.ID]`は、`v`と同時にライブである他のスピル値のIDのリストを格納します。
4.  **干渉グラフの構築**:
    *   各ブロックを逆順にイテレートし、`liveSpills`と同様のライブネス解析ロジック（`s.clear()`, `s.addAll()`, `s.remove()`, `s.add()`）を使用して、ブロック内の各値`v`について、その値が`OpStoreReg`または`isStackPhi()`である場合に、同時にライブである他の値との干渉関係を`interfere`配列に記録します。
    *   `v.Type == types[id]`のチェックにより、同じ型の値のみが干渉関係として考慮されます。これは、異なる型の値は異なるサイズのスタックスロットを必要とするため、通常は同じスロットを共有できないためです。
5.  **`phiArg := make([]bool, f.NumValues())`**: Φ関数の引数である`StoreReg`オペレーションをマークするためのブールスライスを初期化します。
6.  **Φ関数の引数の特定**: 各ブロックの各値について、それがスタックPhiである場合、その引数（`v.Args`）のIDを`phiArg`に`true`とマークします。これにより、これらの引数には個別のスタックスロットが割り当てられず、対応するPhi関数と同じスロットが割り当てられるようになります。
7.  **`locations := map[Type][]*LocalSlot{}`**: 各型ごとに、その型のために割り当てられた`LocalSlot`（スタックスロット）のポインタのスライスを管理するマップを初期化します。
8.  **`slots := make([]int, f.NumValues())`**: 各SSA値が`locations[v.Type]`内のどのインデックスのスタックスロットを使用しているかを記録するためのスライスを初期化します。初期値は`-1`（未割り当て）です。
9.  **スタックスロットの割り当てループ**:
    *   各ブロックの各値`v`をイテレートします。
    *   `v`が`OpStoreReg`または`isStackPhi()`であり、かつ`phiArg[v.ID]`が`false`（つまり、Φ関数の引数ではない）の場合に処理を進めます。
    *   **`locs := locations[v.Type]`**: `v`の型に対応する既存のスタックスロットのリストを取得します。
    *   **`used` 配列**: `interfere[v.ID]`にリストされている、`v`と干渉する他の値が現在どのスタックスロットを使用しているかをマークするための一時的なブールスライスです。
    *   **干渉するスロットのマーク**: `interfere[v.ID]`にリストされている各値`xid`について、`slots[xid]`が示すスタックスロット（`locs`内のインデックス）を`used[slot] = true`とマークします。
    *   **Phi関数の引数の干渉も考慮**: `v`が`OpPhi`の場合、その引数`a`についても同様に干渉するスロットをマークします。これは、Phiとその引数が同じスロットを共有するため、Phiが干渉するものはその引数も干渉すると見なされるためです。
    *   **空きスロットの検索**: `locs`をイテレートし、`used[i]`が`false`である最初のインデックス`i`（つまり、`v`と干渉しない空きスロット）を探します。
    *   **新規スロットの割り当て**: もし空きスロットが見つからなければ（`i == len(locs)`）、`f.Config.fe.Auto(v.Type)`を呼び出して新しい`LocalSlot`を割り当て、`locs`に追加します。
    *   **スロットの割り当て**: 見つかった（または新しく割り当てられた）スタックスロット`loc`を`v`に割り当てます（`f.setHome(v, loc)`）。`slots[v.ID] = i`で、`v`が使用するスロットのインデックスを記録します。
    *   **Phi関数の引数への伝播**: `v`が`OpPhi`の場合、その全ての引数`a`にも同じ`loc`を割り当て、`slots[a.ID] = i`と記録します。

### `liveSpills() (f *Func) [][][]ID` 関数

この関数は、各ブロックの各サクセッサエッジでライブである`StoreReg`およびスタックPhi値のIDのリストを計算します。

1.  **`live := make([][][]ID, f.NumBlocks())`**: 結果を格納するための3次元スライスを初期化します。`live[b.ID][i]`は、ブロック`b`からその`i`番目のサクセッサへのエッジでライブな値のIDリストです。
2.  **`po := postorder(f)`**: 関数のブロックをポストオーダー順（深さ優先探索の逆順）で取得します。ライブネス解析は後方フロー解析であるため、この順序で処理することで収束が早まります。
3.  **反復計算ループ**: `changed`フラグが`false`になるまでループを繰り返します。
    *   **各ブロック`b`をポストオーダー順に処理**:
        *   **`s.clear()`**: 現在のブロックの終端でライブな値のセット`s`をクリアします。
        *   **サクセッサからのライブネス伝播**: `b`の各サクセッサエッジから`live`情報を`s`にマージします。
        *   **ブロック内での後方伝播**: `b`の値を逆順にイテレートします。
            *   `OpStoreReg`の場合、その値はスタックにストアされたので、それ以降はライブではなくなります（`s.remove(v.ID)`）。
            *   `OpLoadReg`の場合、その引数（元の値）がロードされたので、その引数はライブになります（`s.add(v.Args[0].ID)`）。
            *   `isStackPhi()`の場合、その値はPhi関数として処理されるので、それ以降はライブではなくなります（`s.remove(v.ID)`）。また、Phi関数は後で処理するために`phis`スライスに保存されます。
        *   **プリデセッサへのライブネス伝播**: `b`の各プリデセッサ`p`について、`p`から`b`へのエッジでライブな値のセットを更新します。
            *   `t.clear()`: プリデセッサ`p`のライブセット`t`をクリアします。
            *   `t.addAll(live[p.ID][j])`: 既存のライブ情報を追加します。
            *   `t.addAll(s.contents())`: 現在のブロックの開始点でライブな値（`s`）を追加します。
            *   `for _, v := range phis { t.add(v.Args[i].ID) }`: Phi関数の引数もライブセットに追加します。
            *   もし`t`のサイズが変更された場合、`changed = true`を設定し、`live[p.ID][j]`を更新します。
4.  **`return live`**: 最終的に計算されたライブネス情報を返します。

### `(v *Value) isStackPhi() bool` メソッド

このメソッドは、`Value`がスタックにスピルされるΦ関数であるかどうかを判定します。

*   `v.Op != OpPhi`であれば、Phi関数ではないので`false`。
*   `v.Type == TypeMem`であれば、メモリ型なので`false`（メモリ操作は通常、レジスタ割り当ての対象外）。
*   `v.ID`が`f.RegAlloc`の範囲外であるか、または`f.RegAlloc[v.ID]`が`nil`である場合、その値はレジスタに割り当てられていないため、スタックPhiであると判断されます。

これらの変更により、Goコンパイラはスタックフレームのサイズを大幅に削減し、より効率的なコードを生成できるようになりました。

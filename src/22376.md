# [インデックス 22376] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるライトバリアの動作調整と、GC中のメモリ割り当てに関するチェックの追加を目的としています。特に、GCのマークフェーズ開始からマーク終了フェーズ終了までの間、ライトバリアが継続的に有効であることを保証し、GC中に新たなメモリ割り当てが発生しないようにするための変更が含まれています。また、メモリプールをGCサイクルの早期にクリアすることで、メモリの再利用を効率化しています。

## 元コミット内容

Goランタイムにおいて、ライトバリアがアクティブであるべきタイミングを調整します。
ワールドが停止している間であっても、GCはポインタの書き込みを行う可能性があり、それらの書き込みはライトバリアによって保護される必要があります。
これは、マークフェーズの開始からマーク終了フェーズの終了まで、ライトバリアが継続的にオンになっている必要があることを意味します。

メモリプールをクリアするロジックをGCの開始時に移動させ、そのGCサイクル中にメモリが再利用されるようにしました。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。コンカレントGCでは、GCがヒープをスキャンしている最中にも、アプリケーションのゴルーチンがメモリを書き換える可能性があります。この「並行性」がGCの正確性を損なわないようにするために、「ライトバリア（Write Barrier）」という仕組みが導入されています。

ライトバリアは、ポインタの書き込み操作をインターセプトし、GCがオブジェクトグラフを正確に追跡できるようにするためのメカニズムです。具体的には、GCがオブジェクトをマークしている最中に、アプリケーションがそのオブジェクトへのポインタを書き換えた場合、GCはその変更を検知し、必要に応じて新しい参照先のオブジェクトもマーク対象に含める必要があります。

このコミット以前のGoランタイムでは、GCの特定のフェーズ、特に「ワールドが停止している（Stop-The-World: STW）」期間中であっても、GC自身がポインタの書き込みを行う可能性があり、これらの書き込みがライトバリアによって適切に保護されていないケースが存在したと考えられます。STWは、GCがヒープの一貫したスナップショットを取得したり、特定の重要な処理を行うために、全てのアプリケーションゴルーチンの実行を一時的に停止させる期間です。しかし、STW中であっても、GC内部の処理でポインタが書き換えられることがあり、これがGCの正確性や効率に影響を与える可能性がありました。

また、GCの実行中に新たなメモリ割り当てが発生することは、GCのロジックを複雑にし、予期せぬ問題を引き起こす可能性があります。GCの目的は、不要なメモリを解放し、再利用可能にすることであり、その最中に新たなメモリが割り当てられると、GCの対象範囲や処理の整合性が損なわれる恐れがあります。

これらの問題を解決するため、このコミットでは以下の点が改善されました。
1.  **ライトバリアの有効期間の延長**: GCのマークフェーズ開始からマーク終了フェーズ終了まで、ライトバリアが継続的にアクティブであることを保証する。これにより、GC自身が行うポインタ書き込みも保護されるようになります。
2.  **GC中のメモリ割り当ての禁止**: GCの特定のフェーズ（特にマーク終了フェーズ）中に`mallocgc`（メモリ割り当て関数）が呼び出された場合にパニックを発生させるチェックを追加し、GC中の不適切な割り当てを防ぐ。
3.  **メモリプールクリアの早期化**: メモリプール（`mcache`など）をクリアする処理をGCサイクルのより早い段階に移動させることで、解放されたメモリが現在のGCサイクル中に再利用されるようにし、メモリ効率を向上させる。

これらの変更は、GoのGCの堅牢性、正確性、および効率をさらに向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な概念と、それに付随するメカニズムについて理解しておく必要があります。

### 1. ガベージコレクション (GC) の基本

Goは自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、主に「三色マーク＆スイープ（Tri-color Mark-and-Sweep）」アルゴリズムをベースにしたコンカレントGCです。

*   **マークフェーズ (Mark Phase)**: GCがヒープ上の到達可能なオブジェクト（プログラムから参照されているオブジェクト）を特定し、マークするフェーズです。GoのGCは、このフェーズの一部をアプリケーションの実行と並行して行います（コンカレントマーク）。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト、つまり不要なメモリ）を解放し、再利用可能にするフェーズです。
*   **Stop-The-World (STW)**: GCの特定の重要な処理（例えば、初期マークやマーク終了、あるいはヒープの一貫したスナップショットの取得など）を行う際に、全てのアプリケーションゴルーチンの実行を一時的に停止させる期間です。STW期間中は、アプリケーションの実行が完全に停止するため、この期間をいかに短くするかがGCのパフォーマンスにおいて重要になります。

### 2. ライトバリア (Write Barrier)

コンカレントGCにおいて最も重要なメカニズムの一つがライトバリアです。
アプリケーションが実行中にヒープ上のポインタを書き換える（例えば、あるオブジェクトのフィールドに別のオブジェクトへの参照を代入する）際、その操作をGCが検知できるようにする仕組みです。

*   **なぜ必要か？**: コンカレントマーク中にアプリケーションがポインタを書き換えると、GCが既にスキャンした部分のオブジェクトグラフが変更され、本来マークされるべきオブジェクトがマークされずに回収されてしまう（「オブジェクトの取りこぼし」または「浮遊ゴミ」）可能性があります。これを防ぐためにライトバリアが導入されています。
*   **動作**: ライトバリアは、ポインタの書き込み操作が行われる直前または直後にフックされ、GCが必要な処理（例えば、書き換えられたポインタの古い参照先と新しい参照先の両方をマークする）を実行します。これにより、GCは常に正確なオブジェクトグラフを追跡できます。

### 3. `gcphase`

Goランタイム内部では、GCの現在の状態を示すために`gcphase`というグローバル変数が使用されます。これはGCのライフサイクルにおける様々なフェーズを表現する列挙型のようなものです。このコミットで言及されている主なフェーズは以下の通りです。

*   `_GCoff`: GCがアクティブではない状態。
*   `_GCmark`: GCがマークフェーズを実行中である状態。
*   `_GCmarktermination`: GCのマーク終了フェーズ。このフェーズはSTW期間中に実行され、マークフェーズの最終処理やクリーンアップが行われます。

### 4. メモリプール (`clearpools`)

Goランタイムは、メモリ割り当ての効率を向上させるために、様々なサイズのオブジェクトをキャッシュする「メモリプール」を持っています。例えば、`mcache`は各P（プロセッサ、Goスケジューラにおける論理CPU）に紐付けられたローカルキャッシュで、小さなオブジェクトの割り当てを高速化します。

`clearpools`関数は、これらのメモリプールをクリアし、キャッシュされているメモリをヒープに返却する役割を担います。これにより、GCがこれらのメモリをスキャンし、不要であれば解放できるようになります。この処理を適切なタイミングで行うことで、メモリの再利用効率が向上します。

### 5. `systemstack` と `stoptheworld` / `starttheworld`

*   `systemstack`: 現在のゴルーチンをシステムスタックに切り替えて関数を実行します。これは、GCのようなランタイムの低レベルな処理を行う際に使用されます。
*   `stoptheworld` / `starttheworld`: 全てのアプリケーションゴルーチンの実行を停止/再開する関数です。前述のSTW期間の開始と終了を制御します。

これらの概念を理解することで、コミットの変更点がGoランタイムの全体的な動作にどのように影響するかを深く把握できます。

## 技術的詳細

このコミットの技術的詳細は、Goのガベージコレクション（GC）の正確性と効率を向上させるための、ライトバリアの活性期間の調整と、GC中のメモリ割り当ての厳格な制御に集約されます。

### 1. ライトバリアの活性期間の調整

従来のGo GCでは、STW期間中、特にマーク終了フェーズ（`_GCmarktermination`）において、GC自身がポインタの書き込みを行う場合でも、ライトバリアが常にアクティブであるとは限りませんでした。コミットメッセージにあるように、「ワールドが停止している間であっても、GCはライトバリアによって保護される必要のあるポインタの書き込みを行う可能性がある」という問題がありました。

この問題は、GCがオブジェクトグラフを最終的に確定させるマーク終了フェーズにおいて、GC内部の処理がヒープ上のポインタを書き換える際に、その変更がライトバリアによって捕捉されないと、GCの正確性が損なわれる可能性を意味します。例えば、GCが内部的にオブジェクトのメタデータを更新したり、特定のデータ構造を再構築したりする際にポインタを書き換えることが考えられます。

このコミットでは、この問題を解決するために、ライトバリアがアクティブであるべき期間を厳密に定義し、それをコードに反映させています。具体的には、GCのマークフェーズが開始されてから、マーク終了フェーズが完全に終了するまでの間、ライトバリアが継続的にオンになっていることを保証します。

*   **`gcphase`の遷移の調整**: `src/runtime/mgc.go`において、`gcphase`の遷移ロジックが変更されました。特に、STW中に`_GCmarktermination`フェーズに移行する際に、ライトバリアが有効になるように調整されています。これにより、GC自身が行うポインタ書き込みもライトバリアの保護下に置かれることになります。
*   **`gcMark`と`gcSweep`における`gcphase`のチェック**: `gcMark`関数と`gcSweep`関数において、それぞれの処理が実行される際の`gcphase`が期待される値であるかどうかのチェック（`throw`）が追加されました。これは、GCの各フェーズが正しい順序と状態で実行されていることを保証するための防御的なプログラミングであり、予期せぬ`gcphase`の遷移やライトバリアの非活性化を防ぎます。

### 2. GC中のメモリ割り当ての禁止

GCの実行中に新たなメモリ割り当てが行われることは、GCのロジックを複雑にし、潜在的なバグの原因となる可能性があります。GCの主な目的は、既存の不要なメモリを特定し、解放することであり、その最中にヒープの状態が動的に変化することは望ましくありません。

このコミットでは、特に`_GCmarktermination`フェーズ中に`mallocgc`（Goのメモリ割り当ての根幹をなす関数）が呼び出された場合に、ランタイムパニック（`throw`）を発生させるチェックが`src/runtime/malloc.go`に追加されました。

*   **`mallocgc`の変更**: `mallocgc`関数の冒頭に`if gcphase == _GCmarktermination { throw("mallocgc called with gcphase == _GCmarktermination") }`というチェックが追加されました。これは、GCのマーク終了フェーズというクリティカルな期間中に、アプリケーションやランタイムの他の部分が誤ってメモリ割り当てを行わないようにするための厳格な制約です。このチェックにより、GCの整合性が保たれ、デバッグが容易になります。

### 3. メモリプールクリアの早期化

Goランタイムは、メモリ割り当てのパフォーマンスを最適化するために、`mcache`のようなメモリプールを使用しています。これらのプールには、再利用可能な小さなオブジェクトがキャッシュされています。GCが実行される際、これらのプールにキャッシュされているメモリもGCの対象となり、不要であれば解放されるべきです。

このコミットでは、`clearpools()`関数の呼び出し位置が`src/runtime/mgc.go`内で変更されました。以前はGCサイクルの後半で呼び出されていたものが、GCの開始時、具体的には`stoptheworld`と`finishsweep_m`の直後に移動されました。

*   **`clearpools()`の移動**: `clearpools()`をGCの開始時に移動させることで、メモリプール内のメモリがより早くヒープに返却され、現在のGCサイクル中にこれらのメモリがスキャンされ、不要であれば解放される可能性が高まります。これにより、メモリの再利用が効率化され、GCの全体的なパフォーマンスが向上する可能性があります。コミットメッセージにあるように、「メモリが次のGCサイクルまで再利用されない」という問題を解決します。

これらの変更は、GoのGCがより予測可能で、堅牢で、効率的になるように、ランタイムの低レベルな動作を微調整するものです。特に、コンカレントGCの複雑な相互作用の中で、メモリの整合性を保つための重要な改善と言えます。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer {
	if gcphase == _GCmarktermination {
		throw("mallocgc called with gcphase == _GCmarktermination")
	}
	// ...
}
```
この変更は、GCのマーク終了フェーズ（`_GCmarktermination`）中に`mallocgc`関数が呼び出されることを厳しく禁止するためのものです。`_GCmarktermination`フェーズは、GCがオブジェクトグラフの最終的な確定とクリーンアップを行う非常にデリケートな期間です。この期間中に新たなメモリ割り当てが行われると、GCの内部状態が予期せず変更され、GCの正確性や整合性が損なわれる可能性があります。`throw`はGoランタイム内部のパニック機構であり、この条件が満たされた場合はプログラムが異常終了します。これにより、GCの堅牢性が向上し、デバッグが容易になります。

```go
	systemstack(finishsweep_m) // finish sweep before we start concurrent scan.
	// clearpools before we start the GC. If we wait they memory will not be
	// reclaimed until the next GC cycle.
	clearpools()
	// ...
}
```
`clearpools()`の呼び出しが、GCの開始時、具体的には`stoptheworld`と`finishsweep_m`の直後に移動されました。以前はGCサイクルの後半で呼び出されていました。この変更の意図は、メモリプール（`mcache`など）にキャッシュされているメモリをGCサイクルのより早い段階でヒープに返却することです。これにより、これらのメモリが現在のGCサイクル中にスキャンされ、不要であれば解放される可能性が高まります。結果として、メモリの再利用が効率化され、GCの全体的なパフォーマンスが向上します。コメントにもあるように、この変更がなければ、メモリは次のGCサイクルまで再利用されない可能性がありました。

#### `gcphase` の遷移とライトバリアの活性化

```go
// ... (inside gc function, after stoptheworld in concurrent mode)
			// The gcphase is _GCmark, it will transition to _GCmarktermination
			// below. The important thing is that the wb remains active until
			// all marking is complete. This includes writes made by the GC.
// ...
// World is stopped.
// Start marktermination which includes enabling the write barrier.
gcphase = _GCmarktermination
// ...
```
この部分の変更は、ライトバリアがアクティブであるべき期間を明確に定義し、それを強制するためのものです。以前は、コンカレントGCモードで`stoptheworld`が呼び出された後、`gcphase`が直接`_GCoff`に設定される可能性がありました。しかし、コミットメッセージが示唆するように、STW中であってもGC自身がポインタの書き込みを行う可能性があり、これらの書き込みはライトバリアによって保護される必要があります。

新しいロジックでは、STW中に`gcphase`が明示的に`_GCmarktermination`に設定されます。このフェーズでは、ライトバリアが有効になっていることが期待されます。これにより、GCのマークフェーズ開始からマーク終了フェーズ終了までの間、ライトバリアが継続的にアクティブであることが保証され、GCの正確性が維持されます。

#### `gcMark` と `gcSweep` における `gcphase` のチェック

```go
// Inside gcMark:
if gcphase != _GCmarktermination {
	throw("in gcMark expecting to see gcphase as _GCmarktermination")
}
// ...
// Inside gcSweep:
if gcphase != _GCoff {
	throw("gcSweep being done but phase is not GCoff")
}
```
これらの`throw`チェックは、GCの各フェーズが正しい`gcphase`の状態で行われていることを保証するための防御的なメカニズムです。
- `gcMark`が呼び出される際には、`gcphase`が`_GCmarktermination`であるべきだと主張しています。これは、`gcMark`がマーク終了フェーズの一部として実行され、このフェーズ中にライトバリアがアクティブである必要があるためです。
- `gcSweep`が呼び出される際には、`gcphase`が`_GCoff`であるべきだと主張しています。これは、スイープフェーズはマークフェーズとは異なり、ライトバリアが不要な期間であるためです。

これらのチェックは、GCの複雑な状態遷移における潜在的なバグを早期に発見し、ランタイムの安定性を高めるのに役立ちます。

#### `gc` 関数の終了時の `gcphase` チェック

```go
// ... (at the end of gc function)
if gcphase != _GCoff {
	throw("gc done but gcphase != _GCoff")
}
// ...
```
`gc`関数が終了する際に、`gcphase`が必ず`_GCoff`（GCが非アクティブな状態）に戻っていることを確認するためのチェックです。これは、GCサイクルが正常に完了し、ランタイムが通常の実行状態に戻ったことを保証するための最終的な整合性チェックです。もしGCが終了したにもかかわらず`gcphase`が`_GCoff`でなければ、GCの状態管理に問題があることを示唆します。

これらの変更は、GoのGCがより堅牢で、予測可能で、効率的になるように、ランタイムの低レベルな動作を微調整するものです。特に、コンカレントGCの複雑な相互作用の中で、メモリの整合性を保つための重要な改善と言えます。

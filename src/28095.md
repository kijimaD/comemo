# [インデックス 28095] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージに、HTTPクライアントリクエストのトレーシング機能を追加するものです。具体的には、`net/http/httptrace` という新しいパッケージを導入し、HTTPリクエストのライフサイクルにおける様々なイベント（DNSルックアップ、TCP接続、TLSハンドシェイク、リクエスト/レスポンスの書き込みなど）をフックするメカニズムを提供します。これにより、開発者はHTTPクライアントの動作を詳細に監視し、パフォーマンスの問題を特定したり、ネットワーク関連のデバッグを容易にしたりできるようになります。

## 元コミット内容

`net/http` および `net/http/httptrace` パッケージに、HTTPクライアントリクエストをトレースするための新しいパッケージを追加します。
これは Issue #12580 に対応するものです。

## 変更の背景

Go言語の `net/http` クライアントは、そのシンプルさと効率性から広く利用されています。しかし、複雑なネットワーク環境やマイクロサービスアーキテクチャにおいて、HTTPリクエストがどのように処理されているかを詳細に把握することは、デバッグやパフォーマンスチューニングにおいて非常に重要です。特に、DNS解決の遅延、TCP接続の確立時間、TLSハンドシェイクのオーバーヘッド、アイドル接続の再利用状況、リクエストやレスポンスの書き込みタイミングなど、HTTPリクエストの各フェーズで何が起こっているかを可視化する手段が求められていました。

このコミットは、これらの要求に応えるために `httptrace` パッケージを導入しました。これにより、開発者はHTTPクライアントの内部動作にフックを仕掛け、各イベントの発生時にカスタムロジックを実行できるようになります。これは、分散トレーシングシステムとの統合、カスタムメトリクスの収集、ネットワーク診断ツールの構築などに役立ちます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とネットワークの基礎知識が必要です。

1.  **`context.Context`**: Go 1.7で導入された `context` パッケージは、API境界を越えてデッドライン、キャンセルシグナル、およびリクエストスコープの値を伝播するためのメカニズムを提供します。`httptrace` はこの `context.Context` を利用して、トレーシングフックをHTTPリクエストのライフサイクル全体にわたって伝播させます。これにより、リクエストに関連するトレーシング情報を一元的に管理し、必要に応じて下流の関数に渡すことができます。

2.  **HTTPクライアントのライフサイクル**: HTTPクライアントがリクエストを送信し、レスポンスを受信するまでには、以下のような複数のフェーズがあります。
    *   **DNS解決**: ホスト名からIPアドレスへの変換。
    *   **TCP接続確立**: サーバーとのTCPハンドシェイク。
    *   **TLSハンドシェイク**: HTTPSの場合、暗号化された通信路の確立。
    *   **接続の再利用**: Keep-Alive接続が有効な場合、既存のアイドル接続が再利用されることがあります。
    *   **リクエストヘッダ/ボディの書き込み**: クライアントからサーバーへのデータ送信。
    *   **レスポンスヘッダ/ボディの読み込み**: サーバーからクライアントへのデータ受信。

3.  **フック (Hooks)**: プログラムの特定のポイントで実行されるように登録された関数やコールバックのことです。`httptrace` は、HTTPクライアントのライフサイクルの各フェーズに対応するフックを提供し、開発者がこれらのフックに独自の関数を登録できるようにします。

4.  **`internal` パッケージ**: Go言語では、`internal` ディレクトリ内のパッケージは、その親ディレクトリのパッケージからのみインポート可能です。このコミットでは `internal/nettrace` というパッケージが導入されており、これは `net` パッケージの内部トレーシングメカニズムを提供し、`httptrace` から利用されます。これにより、`net` パッケージの低レベルな動作を `httptrace` が安全にフックできるようになっています。

## 技術的詳細

このコミットの主要な技術的詳細は以下の通りです。

1.  **`net/http/httptrace` パッケージの導入**:
    *   `ClientTrace` 構造体が定義され、HTTPクライアントリクエストの様々なイベントに対応するフック（関数フィールド）を保持します。例えば、`DNSStart`, `DNSDone`, `ConnectStart`, `ConnectDone`, `GetConn`, `GotConn`, `PutIdleConn`, `GotFirstResponseByte`, `WroteHeaders`, `Wait100Continue`, `WroteRequest` などがあります。
    *   `WithClientTrace(ctx context.Context, trace *ClientTrace) context.Context` 関数が提供されます。これは、既存の `context.Context` に `ClientTrace` インスタンスを関連付け、新しいコンテキストを返します。HTTPクライアントは、この新しいコンテキストを使用してリクエストを送信することで、登録されたトレーシングフックが呼び出されるようになります。
    *   `ClientTrace` の `compose` メソッドは、複数の `ClientTrace` インスタンスを合成する機能を提供します。これにより、複数のトレーシングロジックを組み合わせることが可能になります。例えば、ある `ClientTrace` がDNS解決をトレースし、別の `ClientTrace` が接続確立をトレースする場合、これらを合成して両方のイベントを監視できます。合成されたフックは、新しいフックが先に実行され、その後古いフックが実行されるように設計されています。

2.  **`internal/nettrace` パッケージの導入**:
    *   `net` パッケージの内部で利用されるトレーシングフックを定義します。`httptrace` は、この `internal/nettrace` を介して `net` パッケージの低レベルなイベント（DNS解決や接続確立）にアクセスします。
    *   `nettrace.Trace` 構造体は、`DNSStart`, `DNSDone`, `ConnectStart`, `ConnectDone` といったフックを持ちます。
    *   `nettrace.TraceKey` は `context.Context` のキーとして使用され、`net` パッケージ内で `nettrace.Trace` インスタンスを伝播するために利用されます。

3.  **`net` パッケージへのトレーシングフックの統合**:
    *   `src/net/dial.go` の `dialSingle` 関数に `nettrace.TraceKey` を介して `ConnectStart` と `ConnectDone` フックが追加されました。これにより、TCP接続の確立前後にトレーシングが可能になります。
    *   `src/net/lookup.go` の `lookupIPContext` 関数に `nettrace.TraceKey` を介して `DNSStart` と `DNSDone` フックが追加されました。これにより、DNSルックアップの開始時と完了時にトレーシングが可能になります。

4.  **`net/http` パッケージへのトレーシングフックの統合**:
    *   `src/net/http/request.go` の `write` メソッドに `httptrace.ContextClientTrace` を介して `WroteHeaders`, `Wait100Continue`, `WroteRequest` フックが追加されました。これにより、リクエストヘッダの書き込み後、100-continue待機時、およびリクエスト全体の書き込み完了時にトレーシングが可能になります。
    *   `src/net/http/transport.go` の `RoundTrip` メソッドおよび `getConn` メソッドに `httptrace.ContextClientTrace` を介して `GetConn`, `GotConn`, `PutIdleConn` フックが追加されました。これにより、接続の取得前、接続取得後（新規接続またはアイドル接続の再利用）、およびアイドルプールへの接続返却時にトレーシングが可能になります。
    *   `persistConn` 構造体に `idleAt` フィールドが追加され、接続がアイドル状態になった時刻を記録することで、`GotConnInfo` で `IdleTime` を正確に報告できるようになりました。

これらの変更により、GoのHTTPクライアントは、リクエストの各段階で詳細な情報を取得し、外部の監視システムやデバッグツールと連携するための強力な基盤を手に入れました。

## コアとなるコードの解説

このコミットの核心は、`context.Context` を利用してHTTPリクエストのライフサイクル全体にわたってトレーシングフックを伝播させるメカニズムを構築した点にあります。

1.  **`ClientTrace` と `WithClientTrace`**:
    `httptrace.ClientTrace` は、開発者が関心のあるイベント（DNS解決、接続確立、リクエスト/レスポンスの送受信など）に対応するコールバック関数を登録するための中心的な構造体です。
    `httptrace.WithClientTrace` 関数は、この `ClientTrace` インスタンスを `context.Context` に埋め込みます。これにより、`http.Client` がリクエストを処理する際に、このコンテキストから `ClientTrace` を取り出し、適切なタイミングで登録されたフックを呼び出すことが可能になります。
    特に注目すべきは、`WithClientTrace` が `ClientTrace` の `hasNetHooks()` メソッドをチェックし、`net` パッケージに関連するフックが登録されている場合に、`internal/nettrace.Trace` インスタンスを作成して `nettrace.TraceKey` を介してコンテキストに埋め込んでいる点です。これにより、`net` パッケージの低レベルな動作も `httptrace` から制御できるようになります。

2.  **フックの合成 (`compose` メソッド)**:
    `ClientTrace` の `compose` メソッドは、複数のトレーシングロジックを組み合わせるための洗練されたメカニズムを提供します。これはリフレクション (`reflect` パッケージ) を使用して実装されており、既存の `ClientTrace` インスタンス (`old`) と新しい `ClientTrace` インスタンス (`t`) のフックを結合します。もし `t` にフックが設定されていればそれが先に呼ばれ、その後 `old` のフックが呼ばれるように新しい関数が生成されます。これにより、複数のミドルウェアやライブラリがそれぞれ独自のトレーシングフックを提供しても、それらが衝突することなく協調して動作できるようになります。

3.  **`net` パッケージとの連携 (`internal/nettrace`)**:
    `net` パッケージはGoの低レベルなネットワーク操作を担っており、`net/http` の基盤となっています。`httptrace` が `net` パッケージのイベント（DNS解決、接続確立）をトレースできるようにするため、`internal/nettrace` パッケージが導入されました。`httptrace.WithClientTrace` は、`ClientTrace` のDNSおよびConnectフックを `internal/nettrace.Trace` の対応するフックに変換し、`nettrace.TraceKey` を使って `net` パッケージに伝播させます。`net` パッケージ内の `dial.go` や `lookup.go` は、この `nettrace.TraceKey` をコンテキストから取得し、フックが登録されていれば呼び出すように変更されています。これにより、HTTPクライアントのより低レベルなネットワーク動作も詳細にトレースできるようになります。

4.  **`net/http/transport` と `request` への統合**:
    `http.Transport` はHTTPクライアントの実際のネットワーク通信を処理する部分であり、`http.Request` はリクエストの構造を定義します。
    このコミットでは、`http.Transport` の `RoundTrip` メソッドが `httptrace.ContextClientTrace` を呼び出して `ClientTrace` を取得し、それを `transportRequest` 構造体に格納して下流に伝播させます。
    `getConn` メソッドでは、接続の取得（新規作成、またはアイドル接続の再利用）の前後で `GetConn` と `GotConn` フックが呼び出されます。特に、アイドル接続が再利用された場合には、`GotConnInfo` に `Reused` や `WasIdle`、`IdleTime` といった詳細情報が提供されます。
    `persistConn` の `readLoop` や `readResponse` メソッドでは、レスポンスの最初のバイトが読み込まれた時 (`GotFirstResponseByte`) や、100-continueレスポンスを受信した時 (`Got100Continue`) にフックが呼び出されます。
    `http.Request` の `write` メソッドでは、リクエストヘッダの書き込み後 (`WroteHeaders`)、100-continue待機時 (`Wait100Continue`)、およびリクエスト全体の書き込み完了時 (`WroteRequest`) にフックが呼び出されます。

これらの変更により、GoのHTTPクライアントは、リクエストの開始から終了までのほぼ全ての重要なイベントをフックできるようになり、非常に詳細なトレーシングと監視が可能になりました。

## 変更の背景

Go言語の `net/http` クライアントは、そのシンプルさと効率性から広く利用されています。しかし、複雑なネットワーク環境やマイクロサービスアーキテクチャにおいて、HTTPリクエストがどのように処理されているかを詳細に把握することは、デバッグやパフォーマンスチューニングにおいて非常に重要です。特に、DNS解決の遅延、TCP接続の確立時間、TLSハンドシェイクのオーバーヘッド、アイドル接続の再利用状況、リクエストやレスポンスの書き込みタイミングなど、HTTPリクエストの各フェーズで何が起こっているかを可視化する手段が求められていました。

このコミットは、これらの要求に応えるために `httptrace` パッケージを導入しました。これにより、開発者はHTTPクライアントの内部動作にフックを仕掛け、各イベントの発生時にカスタムロジックを実行できるようになります。これは、分散トレーシングシステムとの統合、カスタムメトリクスの収集、ネットワーク診断ツールの構築などに役立ちます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とネットワークの基礎知識が必要です。

1.  **`context.Context`**: Go 1.7で導入された `context` パッケージは、API境界を越えてデッドライン、キャンセルシグナル、およびリクエストスコープの値を伝播するためのメカニズムを提供します。`httptrace` はこの `context.Context` を利用して、トレーシングフックをHTTPリクエストのライフサイクル全体にわたって伝播させます。これにより、リクエストに関連するトレーシング情報を一元的に管理し、必要に応じて下流の関数に渡すことができます。

2.  **HTTPクライアントのライフサイクル**: HTTPクライアントがリクエストを送信し、レスポンスを受信するまでには、以下のような複数のフェーズがあります。
    *   **DNS解決**: ホスト名からIPアドレスへの変換。
    *   **TCP接続確立**: サーバーとのTCPハンドシェイク。
    *   **TLSハンドシェイク**: HTTPSの場合、暗号化された通信路の確立。
    *   **接続の再利用**: Keep-Alive接続が有効な場合、既存のアイドル接続が再利用されることがあります。
    *   **リクエストヘッダ/ボディの書き込み**: クライアントからサーバーへのデータ送信。
    *   **レスポンスヘッダ/ボディの読み込み**: サーバーからクライアントへのデータ受信。

3.  **フック (Hooks)**: プログラムの特定のポイントで実行されるように登録された関数やコールバックのことです。`httptrace` は、HTTPクライアントのライフサイクルの各フェーズに対応するフックを提供し、開発者がこれらのフックに独自の関数を登録できるようにします。

4.  **`internal` パッケージ**: Go言語では、`internal` ディレクトリ内のパッケージは、その親ディレクトリのパッケージからのみインポート可能です。このコミットでは `internal/nettrace` というパッケージが導入されており、これは `net` パッケージの内部トレーシングメカニズムを提供し、`httptrace` から利用されます。これにより、`net` パッケージの低レベルな動作を `httptrace` が安全にフックできるようになっています。

## 技術的詳細

このコミットの主要な技術的詳細は以下の通りです。

1.  **`net/http/httptrace` パッケージの導入**:
    *   `ClientTrace` 構造体が定義され、HTTPクライアントリクエストの様々なイベントに対応するフック（関数フィールド）を保持します。例えば、`DNSStart`, `DNSDone`, `ConnectStart`, `ConnectDone`, `GetConn`, `GotConn`, `PutIdleConn`, `GotFirstResponseByte`, `WroteHeaders`, `Wait100Continue`, `WroteRequest` などがあります。
    *   `WithClientTrace(ctx context.Context, trace *ClientTrace) context.Context` 関数が提供されます。これは、既存の `context.Context` に `ClientTrace` インスタンスを関連付け、新しいコンテキストを返します。HTTPクライアントは、この新しいコンテキストを使用してリクエストを送信することで、登録されたトレーシングフックが呼び出されるようになります。
    *   `ClientTrace` の `compose` メソッドは、複数の `ClientTrace` インスタンスを合成する機能を提供します。これにより、複数のトレーシングロジックを組み合わせることが可能になります。例えば、ある `ClientTrace` がDNS解決をトレースし、別の `ClientTrace` が接続確立をトレースする場合、これらを合成して両方のイベントを監視できます。合成されたフックは、新しいフックが先に実行され、その後古いフックが実行されるように設計されています。

2.  **`internal/nettrace` パッケージの導入**:
    *   `net` パッケージの内部で利用されるトレーシングフックを定義します。`httptrace` は、この `internal/nettrace` を介して `net` パッケージの低レベルなイベント（DNS解決や接続確立）にアクセスします。
    *   `nettrace.Trace` 構造体は、`DNSStart`, `DNSDone`, `ConnectStart`, `ConnectDone` といったフックを持ちます。
    *   `nettrace.TraceKey` は `context.Context` のキーとして使用され、`net` パッケージ内で `nettrace.Trace` インスタンスを伝播するために利用されます。

3.  **`net` パッケージへのトレーシングフックの統合**:
    *   `src/net/dial.go` の `dialSingle` 関数に `nettrace.TraceKey` を介して `ConnectStart` と `ConnectDone` フックが追加されました。これにより、TCP接続の確立前後にトレーシングが可能になります。
    *   `src/net/lookup.go` の `lookupIPContext` 関数に `nettrace.TraceKey` を介して `DNSStart` と `DNSDone` フックが追加されました。これにより、DNSルックアップの開始時と完了時にトレーシングが可能になります。

4.  **`net/http` パッケージへのトレーシングフックの統合**:
    *   `src/net/http/request.go` の `write` メソッドに `httptrace.ContextClientTrace` を介して `WroteHeaders`, `Wait100Continue`, `WroteRequest` フックが追加されました。これにより、リクエストヘッダの書き込み後、100-continue待機時、およびリクエスト全体の書き込み完了時にトレーシングが可能になります。
    *   `src/net/http/transport.go` の `RoundTrip` メソッドおよび `getConn` メソッドに `httptrace.ContextClientTrace` を介して `GetConn`, `GotConn`, `PutIdleConn` フックが追加されました。これにより、接続の取得前、接続取得後（新規接続またはアイドル接続の再利用）、およびアイドルプールへの接続返却時にトレーシングが可能になります。
    *   `persistConn` 構造体に `idleAt` フィールドが追加され、接続がアイドル状態になった時刻を記録することで、`GotConnInfo` で `IdleTime` を正確に報告できるようになりました。

これらの変更により、GoのHTTPクライアントは、リクエストの各段階で詳細な情報を取得し、外部の監視システムやデバッグツールと連携するための強力な基盤を手に入れました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下の3つのファイルに集約されます。

1.  **`src/net/http/httptrace/trace.go` (新規ファイル)**:
    *   `ClientTrace` 構造体の定義: HTTPクライアントのトレーシングフックの集合。
    *   `WithClientTrace` 関数: `context.Context` に `ClientTrace` を関連付けるための主要なAPI。
    *   `compose` メソッド: 複数の `ClientTrace` インスタンスを合成するロジック。

    ```go
    // src/net/http/httptrace/trace.go
    type ClientTrace struct {
        // ... 各種フックの定義 ...
        DNSStart func(DNSStartInfo)
        DNSDone  func(DNSDoneInfo)
        ConnectStart func(network, addr string)
        ConnectDone func(network, addr string, err error)
        // ...
    }

    func WithClientTrace(ctx context.Context, trace *ClientTrace) context.Context {
        // ... 既存のトレースと合成し、nettrace.TraceKeyも設定 ...
        if trace.hasNetHooks() {
            nt := &nettrace.Trace{
                ConnectStart: trace.ConnectStart,
                ConnectDone:  trace.ConnectDone,
            }
            // ... DNSStart/DNSDoneの変換と設定 ...
            ctx = context.WithValue(ctx, nettrace.TraceKey{}, nt)
        }
        return ctx
    }

    func (t *ClientTrace) compose(old *ClientTrace) {
        // ... リフレクションを使ってフックを合成するロジック ...
    }
    ```

2.  **`src/internal/nettrace/nettrace.go` (新規ファイル)**:
    *   `Trace` 構造体の定義: `net` パッケージ内部のトレーシングフックの集合。
    *   `TraceKey` 構造体: `context.Context` で `nettrace.Trace` を伝播するためのキー。

    ```go
    // src/internal/nettrace/nettrace.go
    type TraceKey struct{}

    type Trace struct {
        DNSStart func(name string)
        DNSDone  func(netIPs []interface{}, coalesced bool, err error)
        ConnectStart func(network, addr string)
        ConnectDone func(network, addr string, err error)
    }
    ```

3.  **`src/net/http/transport.go`**:
    *   `transportRequest` 構造体に `trace *httptrace.ClientTrace` フィールドが追加され、リクエストごとにトレーシング情報が伝播されるようになりました。
    *   `RoundTrip` メソッド内で `httptrace.ContextClientTrace(ctx)` を呼び出し、コンテキストから `ClientTrace` を取得しています。
    *   `getConn` メソッド内で `trace.GetConn` と `trace.GotConn` が呼び出され、接続の取得イベントをトレースしています。
    *   `tryPutIdleConn` メソッド内で `trace.PutIdleConn` が呼び出され、アイドル接続のプールへの返却イベントをトレースしています。
    *   `persistConn` 構造体に `idleAt time.Time` フィールドが追加され、アイドル時間の計測に利用されます。

    ```go
    // src/net/http/transport.go
    type transportRequest struct {
        *Request
        extra    Header
        trace    *httptrace.ClientTrace // 追加
    }

    func (t *Transport) RoundTrip(req *Request) (*Response, error) {
        // ...
        ctx := req.Context()
        trace := httptrace.ContextClientTrace(ctx) // ClientTraceの取得
        // ...
        treq := &transportRequest{Request: req, trace: trace} // traceをtransportRequestに設定
        // ...
    }

    func (t *Transport) getConn(treq *transportRequest, cm connectMethod) (*persistConn, error) {
        req := treq.Request
        trace := treq.trace // traceの利用
        if trace != nil {
            trace.GetConn(cm.addr())
        }
        if pc, idleSince := t.getIdleConn(cm); pc != nil {
            if trace != nil {
                trace.GotConn(pc.gotIdleConnTrace(idleSince))
            }
            // ...
        }
        // ...
    }

    type persistConn struct {
        // ...
        idleAt time.Time // 追加
        // ...
    }
    ```

## コアとなるコードの解説

このコミットの核心は、`context.Context` を利用してHTTPリクエストのライフサイクル全体にわたってトレーシングフックを伝播させるメカニズムを構築した点にあります。

1.  **`ClientTrace` と `WithClientTrace`**:
    `httptrace.ClientTrace` は、開発者が関心のあるイベント（DNS解決、接続確立、リクエスト/レスポンスの送受信など）に対応するコールバック関数を登録するための中心的な構造体です。
    `httptrace.WithClientTrace` 関数は、この `ClientTrace` インスタンスを `context.Context` に埋め込みます。これにより、`http.Client` がリクエストを処理する際に、このコンテキストから `ClientTrace` を取り出し、適切なタイミングで登録されたフックを呼び出すことが可能になります。
    特に注目すべきは、`WithClientTrace` が `ClientTrace` の `hasNetHooks()` メソッドをチェックし、`net` パッケージに関連するフックが登録されている場合に、`internal/nettrace.Trace` インスタンスを作成して `nettrace.TraceKey` を介してコンテキストに埋め込んでいる点です。これにより、`net` パッケージの低レベルな動作も `httptrace` から制御できるようになります。

2.  **フックの合成 (`compose` メソッド)**:
    `ClientTrace` の `compose` メソッドは、複数のトレーシングロジックを組み合わせるための洗練されたメカニズムを提供します。これはリフレクション (`reflect` パッケージ) を使用して実装されており、既存の `ClientTrace` インスタンス (`old`) と新しい `ClientTrace` インスタンス (`t`) のフックを結合します。もし `t` にフックが設定されていればそれが先に呼ばれ、その後 `old` のフックが呼ばれるように新しい関数が生成されます。これにより、複数のミドルウェアやライブラリがそれぞれ独自のトレーシングフックを提供しても、それらが衝突することなく協調して動作できるようになります。

3.  **`net` パッケージとの連携 (`internal/nettrace`)**:
    `net` パッケージはGoの低レベルなネットワーク操作を担っており、`net/http` の基盤となっています。`httptrace` が `net` パッケージのイベント（DNS解決、接続確立）をトレースできるようにするため、`internal/nettrace` パッケージが導入されました。`httptrace.WithClientTrace` は、`ClientTrace` のDNSおよびConnectフックを `internal/nettrace.Trace` の対応するフックに変換し、`nettrace.TraceKey` を使って `net` パッケージに伝播させます。`net` パッケージ内の `dial.go` や `lookup.go` は、この `nettrace.TraceKey` をコンテキストから取得し、フックが登録されていれば呼び出すように変更されています。これにより、HTTPクライアントのより低レベルなネットワーク動作も詳細にトレースできるようになります。

4.  **`net/http/transport` と `request` への統合**:
    `http.Transport` はHTTPクライアントの実際のネットワーク通信を処理する部分であり、`http.Request` はリクエストの構造を定義します。
    このコミットでは、`http.Transport` の `RoundTrip` メソッドが `httptrace.ContextClientTrace` を呼び出して `ClientTrace` を取得し、それを `transportRequest` 構造体に格納して下流に伝播させます。
    `getConn` メソッドでは、接続の取得（新規作成、またはアイドル接続の再利用）の前後で `GetConn` と `GotConn` フックが呼び出されます。特に、アイドル接続が再利用された場合には、`GotConnInfo` に `Reused` や `WasIdle`、`IdleTime` といった詳細情報が提供されます。
    `persistConn` の `readLoop` や `readResponse` メソッドでは、レスポンスの最初のバイトが読み込まれた時 (`GotFirstResponseByte`) や、100-continueレスポンスを受信した時 (`Got100Continue`) にフックが呼び出されます。
    `http.Request` の `write` メソッドでは、リクエストヘッダの書き込み後 (`WroteHeaders`)、100-continue待機時 (`Wait100Continue`)、およびリクエスト全体の書き込み完了時 (`WroteRequest`) にフックが呼び出されます。

これらの変更により、GoのHTTPクライアントは、リクエストの開始から終了までのほぼ全ての重要なイベントをフックできるようになり、非常に詳細なトレーシングと監視が可能になりました。

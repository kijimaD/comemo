## 変更の背景

Go言語の`goto`文には、特定の制限があります。特に重要なのは、「`goto`は変数の宣言を飛び越えてはならない」というルールです。これは、未初期化の変数にアクセスする可能性を防ぎ、プログラムの安全性を保つためのものです。

しかし、Goコンパイラの以前の実装では、この`goto`の検証ロジックが型宣言（`type MyType int`のようなもの）も変数の宣言と同様に扱ってしまうというバグがありました。これにより、`goto`のジャンプ先に型宣言が存在する場合、実際には問題がないにもかかわらず、コンパイラが「変数の宣言を飛び越えている」と誤って判断し、不必要なエラーを報告していました。

このコミットは、この誤った挙動を修正し、型宣言が`goto`の検証において無視されるようにすることで、Go言語の仕様に沿った正しいコンパイルを可能にすることを目的としています。コミットメッセージにある`Fixes #8042`は、この問題がGoのイシュートラッカーで報告されていたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの概念を理解しておく必要があります。

1.  **`goto`文の制限**: Go言語の`goto`文は、C言語などと比較して厳しく制限されています。特に、`goto`は変数の宣言を飛び越えて、その変数のスコープ内に入ることはできません。これは、未初期化の変数へのアクセスを防ぐためです。
    ```go
    func main() {
        goto L1
        x := 10 // goto L1 はこの宣言を飛び越えるためエラー
    L1:
        fmt.Println("Hello")
    }
    ```
    しかし、型宣言や定数宣言は、実行時にメモリを割り当てる変数とは異なり、この制限の対象外です。

2.  **Goコンパイラのシンボルテーブルとスコープ管理**: Goコンパイラ（特に`cmd/internal/gc`）は、プログラムのコンパイル中にシンボルテーブルを使用して、変数、関数、型などの識別子（シンボル）を管理します。シンボルは、そのスコープ（有効範囲）と共に管理され、新しいブロックに入るたびに新しいスコープが作成され、シンボルがプッシュ（追加）されます。ブロックを抜ける際には、そのスコープ内のシンボルがポップ（削除）されます。

3.  **`dclstack` (Declaration Stack)**: Goコンパイラ内部では、宣言されたシンボルを追跡するために「宣言スタック」のようなものが使用されます。これは、現在のスコープ内でどのシンボルが宣言されているかを把握し、特に`goto`の検証時に、ジャンプ元とジャンプ先の間でどのシンボルが宣言されたかを確認するために重要です。

4.  **`Node.Op`と`Sym.whyPushed`**: GoコンパイラのAST（抽象構文木）では、各ノードが`Op`フィールドを持ち、そのノードが表す操作の種類（例: `ONAME`は変数、`OTYPE`は型）を示します。このコミットでは、`Sym`構造体に`whyPushed`というフィールドが追加され、シンボルが宣言スタックにプッシュされた理由（つまり、それが変数宣言なのか、型宣言なのかなど）を記録するようになりました。

## 技術的詳細

このコミットの技術的な核心は、`goto`文の検証ロジック（`checkgoto`関数）が、宣言スタック上のシンボルを評価する際に、それが型宣言であるかどうかを区別するようになった点です。

以前の`checkgoto`関数は、`goto`のジャンプ元とジャンプ先の間のスコープで宣言されたシンボルをすべて一律に「宣言」として扱い、変数の宣言を飛び越えることによるエラーを検出していました。しかし、型宣言は実行時の状態に影響を与えないため、`goto`がこれを飛び越えても問題ありません。

この修正では、以下の変更が導入されました。

1.  **`Sym.whyPushed`フィールドの追加**: `src/cmd/internal/gc/go.go`の`Sym`構造体に`whyPushed uint8`フィールドが追加されました。このフィールドは、シンボルが宣言スタックにプッシュされた理由（`Node.Op`と同じ値）を格納します。これにより、シンボルが変数（`ONAME`）なのか、型（`OTYPE`）なのかなどを区別できるようになります。

2.  **`popdcl`関数での`whyPushed`の設定**: `src/cmd/internal/gc/dcl.go`の`popdcl`関数（宣言スタックからシンボルをポップする際に、そのシンボルの情報を更新する関数）で、`s.Def.Op`の値が`s.whyPushed`にコピーされるようになりました。`s.Def`はシンボルの定義ノードを指し、その`Op`フィールドがシンボルの種類を示します。

3.  **`checkgoto`関数での型宣言の無視**: `src/cmd/internal/gc/gen.go`の`checkgoto`関数が修正され、`goto`のジャンプ元とジャンプ先の間の宣言スタックを走査する際に、`whyPushed`フィールドをチェックするようになりました。
    *   新しいコードでは、`ntt > nf`のループ内で、`ts.whyPushed != OTYPE`である場合にのみ`break`します。これは、ジャンプ元とジャンプ先の間に型宣言のみが存在する場合は、エラーとせずに`return`（検証をスキップ）することを意味します。
    *   また、`dcl`（宣言されたシンボル）を特定するループ内で、`ts.whyPushed != OTYPE`の条件が追加されました。これにより、型宣言は`dcl`として扱われなくなり、`goto`の制限対象から除外されます。

これらの変更により、`checkgoto`関数は型宣言を正しく識別し、それらを`goto`の検証対象から除外することで、誤ったエラー報告を防ぎます。

1.  **`Sym`構造体への`whyPushed`の追加**:
    `Sym`構造体は、コンパイラが識別子（変数名、型名など）に関する情報を格納するために使用するものです。`whyPushed`フィールドが追加されたことで、各シンボルが宣言スタックに積まれた際に、それがどのような種類の宣言（例えば、`OTYPE`は型、`ONAME`は変数）であったかを記録できるようになりました。これは、`goto`の検証ロジックがシンボルの種類に基づいて異なる挙動をするための前提となります。

2.  **`popdcl`での`whyPushed`の設定**:

3.  **`checkgoto`での型宣言の無視**:
    `checkgoto`関数は、`goto`文がGo言語のルール（特に「変数の宣言を飛び越えてはならない」）に違反していないかを検証する主要な関数です。
    *   修正前は、`goto`のジャンプ元とジャンプ先の間に存在するすべての宣言を等しく扱っていました。
    *   修正後は、`whyPushed`フィールドを利用して、宣言スタック上のシンボルが`OTYPE`（型宣言）であるかどうかをチェックします。もし、ジャンプ元とジャンプ先の間に型宣言のみが存在する場合、新しいロジックはそれを問題ないと判断し、エラーを報告せずに処理を続行します。
    *   また、変数宣言を検出する既存のロジックにも`ts.whyPushed != OTYPE`という条件が追加され、型宣言が変数宣言として誤って扱われることを防ぎます。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラが`goto`文の有効性をチェックする際に、シンボルが「型宣言」であるか「変数宣言」であるかを正確に区別するようになった点にあります。

1.  **`Sym`構造体への`whyPushed`の追加**:
    `Sym`構造体は、コンパイラが識別子（変数名、型名など）に関する情報を格納するために使用するものです。`whyPushed`フィールドが追加されたことで、各シンボルが宣言スタックに積まれた際に、それがどのような種類の宣言（例えば、`OTYPE`は型、`ONAME`は変数）であったかを記録できるようになりました。これは、`goto`の検証ロジックがシンボルの種類に基づいて異なる挙動をするための前提となります。

2.  **`popdcl`での`whyPushed`の設定**:
    `popdcl`関数は、スコープからシンボルが外れる際に呼び出される関数です。ここで`s.Def.Op`の値を`d.whyPushed`にコピーすることで、シンボルが宣言スタックにプッシュされた時点でのそのシンボルの種類を正確に保持します。これにより、後で`checkgoto`関数がこの情報を使って判断を下せるようになります。

3.  **`checkgoto`での型宣言の無視**:
    `checkgoto`関数は、`goto`文がGo言語のルール（特に「変数の宣言を飛び越えてはならない」）に違反していないかを検証する主要な関数です。
    *   修正前は、`goto`のジャンプ元とジャンプ先の間に存在するすべての宣言を等しく扱っていました。
    *   修正後は、`whyPushed`フィールドを利用して、宣言スタック上のシンボルが`OTYPE`（型宣言）であるかどうかをチェックします。もし、ジャンプ元とジャンプ先の間に型宣言のみが存在する場合、新しいロジックはそれを問題ないと判断し、エラーを報告せずに処理を続行します。
    *   また、変数宣言を検出する既存のロジックにも`ts.whyPushed != OTYPE`という条件が追加され、型宣言が変数宣言として誤って扱われることを防ぎます。

これらの変更により、Goコンパイラは`goto`文の検証において、型宣言と変数宣言を正しく区別し、Go言語の仕様に厳密に準拠した挙動を実現しています。これにより、開発者は型宣言を含むコードで`goto`をより柔軟に使用できるようになり、不必要なコンパイルエラーに悩まされることがなくなります。

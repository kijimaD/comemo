## 変更の背景

このコミットの主な背景は、Goのビルドシステムが共有ライブラリ（shared objects）を扱う際に、それらが古くなっている（stale）状態を適切に検出し、再構築するメカニズムが不十分であった点にあります。

Go 1.5で導入された`buildmode=shared`オプションは、複数のGoプログラムが共通のGoパッケージセットを共有ライブラリとしてリンクすることを可能にし、バイナリサイズの削減や起動時間の短縮といった利点をもたらしました。しかし、この機能が導入された当初は、共有ライブラリ自体のソースコードが変更されていない場合でも、その共有ライブラリが依存するパッケージのアーカイブファイル（`.a`ファイル）が更新された際に、共有ライブラリが自動的に再構築されないという問題がありました。

具体的には、以下のようなシナリオで問題が発生する可能性がありました。

1.  `libdep.so`という共有ライブラリが`dep.a`というアーカイブファイルに依存している。
2.  `dep.a`のソースコードが変更され、`dep.a`が再構築される。
3.  しかし、`libdep.so`のソースコード自体は変更されていないため、`go install`コマンドは`libdep.so`が最新であると判断し、再構築を行わない。
4.  結果として、`libdep.so`にリンクする実行可能ファイルは、古いバージョンの`dep.a`を含む`libdep.so`にリンクしてしまう。

この問題は、ビルドの整合性を損ない、予期せぬバグや動作を引き起こす可能性がありました。このコミットは、このような「staleな共有ライブラリ」の問題を解決し、共有ライブラリが依存するパッケージの変更を検出し、必要に応じて共有ライブラリ自体も再構築するように、ビルドシステムのアクショングラフとstaleness検出ロジックを強化することを目的としています。

コミットメッセージにある「This changes the action graph when shared libraries are involved to always have an action for the shared library (which does nothing when the shared library is up to date)」という記述は、共有ライブラリが最新である場合でも、その共有ライブラリをビルドするアクションが常にアクショングラフに存在するように変更されたことを示しています。これにより、共有ライブラリのstalenessチェックが常に実行され、必要に応じて再構築がトリガーされるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムと関連技術に関する知識が必要です。

### Goのビルドモードと共有ライブラリ (`-buildmode=shared`)

Go 1.5から導入された`go build -buildmode=shared`オプションは、Goパッケージを共有ライブラリ（`.so`ファイル、Windowsでは`.dll`、macOSでは`.dylib`）としてビルドする機能を提供します。これにより、複数のGo実行可能ファイルが同じ共有ライブラリにリンクできるようになり、ディスク使用量の削減や、特に大規模なモノレポ環境でのビルド時間の短縮に貢献します。

-   **`go install -buildmode=shared <packages>`**: 指定されたパッケージとその依存関係を共有ライブラリとしてビルドし、インストールします。
-   **`go install -linkshared <executable>`**: 共有ライブラリにリンクするように実行可能ファイルをビルドします。

### `cmd/go`とビルドアクショングラフ

`go`コマンドは、Goのソースコードを管理し、ビルド、テスト、インストールを行うための主要なツールです。内部的には、ビルドプロセスを効率的に管理するために「アクショングラフ」を構築します。

-   **アクション (Action)**: `go`コマンドが実行する個々のタスク（例: パッケージのコンパイル、アーカイブの作成、実行可能ファイルのリンク、共有ライブラリのインストールなど）を表す内部構造体です。
-   **アクショングラフ (Action Graph)**: 各アクション間の依存関係を表現する有向非巡回グラフ（DAG）です。`go`コマンドはこのグラフを辿ることで、正しい順序でビルドステップを実行し、必要なものだけを再ビルドすることでインクリメンタルビルドを実現します。
-   **`builder`構造体**: `src/cmd/go/build.go`に定義されており、ビルドプロセス全体を管理し、アクショングラフを構築・実行する役割を担います。

### `cgo`

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoの機能です。`cgo`を使用すると、GoのビルドプロセスはCコンパイラやリンカと連携する必要があり、共有ライブラリのビルドがより複雑になります。特に、`runtime/cgo`パッケージは`cgo`のランタイムサポートを提供し、外部リンカの使用を強制することが多いため、共有ライブラリのビルドにおいて特別な考慮が必要です。

### `staleness`検出

ビルドシステムにおける`staleness`とは、ビルド成果物（例: 実行可能ファイル、ライブラリ）が、その入力ファイル（ソースコード、依存ライブラリなど）よりも古い状態であることを指します。`go`コマンドは、ファイルの最終更新時刻（modification time）などを比較することで`staleness`を検出し、必要なものだけを再ビルドすることでビルド時間を短縮します。

### ELFファイルとノートセクション

-   **ELF (Executable and Linkable Format)**: Unix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリなどの標準ファイルフォーマットです。
-   **ノートセクション (`SHT_NOTE`)**: ELFファイルには、プログラムの実行には直接関係しないが、ツールやデバッガにとって有用な情報を格納するための「ノートセクション」を含めることができます。このコミットでは、共有ライブラリが含むGoパッケージのリストをこのノートセクションに格納し、後で読み出すことで、共有ライブラリの内容を動的に把握するために利用しています。

### `shlibname`ファイル

このコミットで導入された概念で、Goパッケージがどの共有ライブラリに属しているかを記録するためのファイルです。例えば、`mypackage.a`というアーカイブファイルが`libshared.so`という共有ライブラリに含まれる場合、`mypackage.shlibname`というファイルが作成され、その中に`libshared.so`という文字列が書き込まれます。これにより、`go`コマンドは特定のパッケージが共有ライブラリの一部であるかどうか、そしてどの共有ライブラリに属しているかを効率的に判断できるようになります。

### `ldd`コマンド

`ldd`はLinuxシステムで利用されるコマンドラインユーティリティで、指定された実行可能ファイルや共有ライブラリが依存している共有ライブラリの一覧を表示します。このコミットのテストスクリプトでは、ビルドされた実行可能ファイルが意図した共有ライブラリに正しくリンクされているかを確認するために使用されています。

## 技術的詳細

このコミットの技術的詳細は、主に`go`コマンドのビルドロジック、特に共有ライブラリの取り扱いとstaleness検出メカニズムの変更に集約されます。

### 1. アクショングラフの変更と`cacheKey`の拡張

以前の`go`コマンドは、共有ライブラリが最新であると判断された場合、その共有ライブラリをビルドするアクションをアクショングラフに含めないことがありました。このコミットでは、共有ライブラリが関与する場合、常に共有ライブラリに対するアクションがアクショングラフに存在するように変更されました。これにより、共有ライブラリのstalenessチェックが常に実行されるようになります。

この変更をサポートするために、`builder`構造体内の`actionCache`のキーとして使用される`cacheKey`構造体が拡張されました。

```go
type cacheKey struct {
	mode  buildMode
	p     *Package
	shlib string // 新しく追加されたフィールド
}
```

`shlib`フィールドが追加されたことで、`actionCache`はパッケージ、ビルドモードに加えて、そのパッケージが属する共有ライブラリの名前も考慮してアクションをキャッシュするようになりました。これにより、共有ライブラリのコンテキストに応じた正確なアクションの管理が可能になります。

### 2. `action1`関数の導入と共有ライブラリのstaleness検出ロジック

`builder.action`関数は`builder.action1`関数に置き換えられ、`lookshared`という新しいブール引数が追加されました。この引数は、共有ライブラリ内でパッケージを探すかどうかを制御します。

`action1`関数内では、`lookshared`が`true`の場合、パッケージが属する共有ライブラリ（`p.Shlib`）が考慮されます。もしその共有ライブラリに対するアクションが既にキャッシュされていればそれを再利用し、そうでなければ`readpkglist`関数を使って共有ライブラリに含まれるパッケージリストを読み込み、`libaction`を呼び出して共有ライブラリをビルドするアクションを生成します。

最も重要な変更は、`libaction`関数内で共有ライブラリのstalenessを検出するロジックが追加されたことです。

```go
// src/cmd/go/build.go の libaction 関数内
// ...
		stale := false
		var built time.Time
		if fi, err := os.Stat(a.target); err == nil {
			built = fi.ModTime()
		}
		for _, p := range pkgs {
			if p.target == "" {
				continue
			}
			stale = stale || p.Stale // パッケージ自体がstaleか
			lstat, err := os.Stat(p.target)
			if err != nil || lstat.ModTime().After(built) { // パッケージのターゲットファイルが共有ライブラリより新しいか
				stale = true
			}
			a.deps = append(a.deps, b.action(depMode, depMode, p))
		}

		if stale {
			// 共有ライブラリがstaleであれば、ビルドアクションを生成
			a.f = (*builder).install
			buildAction := b.libaction(libname, pkgs, modeBuild, depMode)
			a.deps = []*action{buildAction}
			// ... shlibnameファイルのインストールアクションも追加 ...
		}
// ...
```

このロジックは、共有ライブラリを構成する個々のパッケージ（`.a`ファイル）のstaleness、またはパッケージのターゲットファイル（`.a`ファイル）の更新時刻が共有ライブラリ（`.so`ファイル）の更新時刻よりも新しい場合に、共有ライブラリ全体を`stale`と判断します。`stale`と判断された場合、共有ライブラリを再構築するための`buildAction`が生成され、アクショングラフに追加されます。これにより、共有ライブラリが常に最新の依存関係に基づいてビルドされることが保証されます。

### 3. `readnote`関数の導入とELFノートセクションからのパッケージリスト読み込み

`src/cmd/go/note.go`に新しく追加された`readnote`関数は、ELFファイルから特定の名前とタイプのノートセクションを読み取るための汎用的なユーティリティです。この関数は`debug/elf`パッケージを利用してELFファイルを解析し、ノートセクション内の情報を抽出します。

`src/cmd/go/build.go`の`readpkglist`関数は、この`readnote`関数を使用して共有ライブラリファイル（`.so`）から「GO\x00\x00」という名前のノートセクションを読み込みます。このノートセクションには、その共有ライブラリに含まれるGoパッケージのインポートパスのリストが格納されており、`readpkglist`はこのリストを解析して`*Package`のリストを返します。これにより、`go`コマンドは共有ライブラリの内容を動的に把握し、ビルドプロセスに組み込むことができます。

### 4. `Package`構造体への`Shlib`フィールド追加と`shlibname`ファイルの利用

`src/cmd/go/pkg.go`の`Package`構造体に`Shlib`という新しいフィールドが追加されました。このフィールドは、パッケージが共有ライブラリにリンクされている場合に、その共有ライブラリの名前を格納します。

```go
type Package struct {
	// ... 既存のフィールド ...
	Shlib         string `json:",omitempty"` // the shared library that contains this package (only set when -linkshared)
	// ... 既存のフィールド ...
}
```

`Package.load`関数内で、`buildLinkshared`が有効な場合、パッケージのターゲットファイル（`.a`ファイル）に対応する`.shlibname`ファイルを読み込みます。この`.shlibname`ファイルには、そのパッケージが属する共有ライブラリの名前が記述されており、読み込んだ値が`p.Shlib`に設定されます。これにより、各パッケージがどの共有ライブラリに属しているかをビルドシステムが追跡できるようになります。

### 5. `runtime/cgo`の扱い

`src/cmd/go/build.go`と`src/cmd/internal/ld/lib.go`では、`runtime/cgo`パッケージの扱いに関する変更も行われています。`buildmode=shared`を使用する場合、`runtime/cgo`は常に外部リンカを強制するため、共有ライブラリのビルドにおいて特別な考慮が必要です。このコミットでは、`runtime/cgo`が共有ライブラリに含まれるべきかどうか、そしてそれが既に別の共有ライブラリに含まれていないかを確認するロジックが追加され、重複や不整合を防ぐようになっています。

### 6. テストスクリプトの強化

`misc/cgo/testshared/test.bash`スクリプトは、共有ライブラリの再構築ロジックを検証するための新しいテストケースで大幅に強化されました。

-   `dep`パッケージと`exe`パッケージという新しいテスト用Goパッケージが追加されました。`dep`は共有ライブラリとしてビルドされ、`exe`は`dep`にリンクします。
-   `ensure_ldd`関数が導入され、`ldd`コマンドを使用して実行可能ファイルが意図した共有ライブラリにリンクされていることを確認します。
-   `will_check_rebuilt`, `assert_rebuilt`, `assert_not_rebuilt`というヘルパー関数が導入され、ファイルの更新時刻を比較することで、特定のファイルが再構築されたかどうかを検証します。
-   `dep.go`のソースファイルを`touch`して更新し、`exe`を再インストールすることで、`libdep.so`と`dep.a`が再構築されることを検証するテストケースが追加されました。
-   `dep.a`ファイルを`touch`して更新し、`exe`を再インストールすることで、`libdep.so`のみが再構築され、`dep.a`は再構築されないことを検証するテストケースも追加されました。これは、共有ライブラリのstaleness検出がより粒度高く行われるようになったことを示しています。

これらのテストケースは、共有ライブラリのstaleness検出と再構築のメカニズムが期待通りに機能することを保証します。

    // libaction 関数内 (簡略化)
    // ...
    		stale := false
    		var built time.Time
    		if fi, err := os.Stat(a.target); err == nil {
    			built = fi.ModTime() // 共有ライブラリの最終更新時刻
    		}
    		for _, p := range pkgs {
    			// ...
    			stale = stale || p.Stale // 構成パッケージ自体がstaleか
    			lstat, err := os.Stat(p.target)
    			if err != nil || lstat.ModTime().After(built) { // 構成パッケージのアーカイブファイルが共有ライブラリより新しいか
    				stale = true
    			}
    			// ...
    		}

    		if stale {
    			// 共有ライブラリがstaleであれば、ビルドアクションを生成し、依存関係として追加
    			a.f = (*builder).install
    			buildAction := b.libaction(libname, pkgs, modeBuild, depMode)
    			a.deps = []*action{buildAction}
    			// ... shlibnameファイルのインストールアクションも追加 ...
    		}
    // ...
    ```
    このコードは、共有ライブラリを構成する個々のパッケージ（`.a`ファイル）のいずれかがstaleであるか、またはそのアーカイブファイルの更新時刻が共有ライブラリ（`.so`ファイル）の更新時刻よりも新しい場合に、共有ライブラリ全体をstaleとマークします。`stale`と判断された場合、`go`コマンドは共有ライブラリを再構築するための新しいビルドアクションを生成し、それを現在のアクションの依存関係として追加します。これにより、共有ライブラリが常に最新の依存関係に基づいて再ビルドされることが保証されます。

-   **`allArchiveActions`関数**:
    ```go

    	// ...
    	// rootアクションから辿れるすべてのアーカイブ(.a)アクションを収集
    	// 共有ライブラリ(.so)アクションを介して依存するアーカイブも含む

## 変更の背景

このコミットの主な背景は、Goのビルドシステムが共有ライブラリ（shared objects）を扱う際に、それらが古くなっている（stale）状態を適切に検出し、再構築するメカニズムが不十分であった点にあります。

Go 1.5で導入された`buildmode=shared`オプションは、複数のGoプログラムが共通のGoパッケージセットを共有ライブラリとしてリンクすることを可能にし、バイナリサイズの削減や起動時間の短縮といった利点をもたらしました。しかし、この機能が導入された当初は、共有ライブラリ自体のソースコードが変更されていない場合でも、その共有ライブラリが依存するパッケージのアーカイブファイル（`.a`ファイル）が更新された際に、共有ライブラリが自動的に再構築されないという問題がありました。

具体的には、以下のようなシナリオで問題が発生する可能性がありました。

1.  `libdep.so`という共有ライブラリが`dep.a`というアーカイブファイルに依存している。
2.  `dep.a`のソースコードが変更され、`dep.a`が再構築される。
3.  しかし、`libdep.so`のソースコード自体は変更されていないため、`go install`コマンドは`libdep.so`が最新であると判断し、再構築を行わない。
4.  結果として、`libdep.so`にリンクする実行可能ファイルは、古いバージョンの`dep.a`を含む`libdep.so`にリンクしてしまう。

この問題は、ビルドの整合性を損ない、予期せぬバグや動作を引き起こす可能性がありました。このコミットは、このような「staleな共有ライブラリ」の問題を解決し、共有ライブラリが依存するパッケージの変更を検出し、必要に応じて共有ライブラリ自体も再構築するように、ビルドシステムのアクショングラフとstaleness検出ロジックを強化することを目的としています。

コミットメッセージにある「This changes the action graph when shared libraries are involved to always have an action for the shared library (which does nothing when the shared library is up to date)」という記述は、共有ライブラリが最新である場合でも、その共有ライブラリをビルドするアクションが常にアクショングラフに存在するように変更されたことを示しています。これにより、共有ライブラリのstalenessチェックが常に実行され、必要に応じて再構築がトリガーされるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムと関連技術に関する知識が必要です。

### Goのビルドモードと共有ライブラリ (`-buildmode=shared`)

Go 1.5から導入された`go build -buildmode=shared`オプションは、Goパッケージを共有ライブラリ（`.so`ファイル、Windowsでは`.dll`、macOSでは`.dylib`）としてビルドする機能を提供します。これにより、複数のGo実行可能ファイルが同じ共有ライブラリにリンクできるようになり、ディスク使用量の削減や、特に大規模なモノレポ環境でのビルド時間の短縮に貢献します。

-   **`go install -buildmode=shared <packages>`**: 指定されたパッケージとその依存関係を共有ライブラリとしてビルドし、インストールします。
-   **`go install -linkshared <executable>`**: 共有ライブラリにリンクするように実行可能ファイルをビルドします。

### `cmd/go`とビルドアクショングラフ

`go`コマンドは、Goのソースコードを管理し、ビルド、テスト、インストールを行うための主要なツールです。内部的には、ビルドプロセスを効率的に管理するために「アクショングラフ」を構築します。

-   **アクション (Action)**: `go`コマンドが実行する個々のタスク（例: パッケージのコンパイル、アーカイブの作成、実行可能ファイルのリンク、共有ライブラリのインストールなど）を表す内部構造体です。
-   **アクショングラフ (Action Graph)**: 各アクション間の依存関係を表現する有向非巡回グラフ（DAG）です。`go`コマンドはこのグラフを辿ることで、正しい順序でビルドステップを実行し、必要なものだけを再ビルドすることでインクリメンタルビルドを実現します。
-   **`builder`構造体**: `src/cmd/go/build.go`に定義されており、ビルドプロセス全体を管理し、アクショングラフを構築・実行する役割を担います。

### `cgo`

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoの機能です。`cgo`を使用すると、GoのビルドプロセスはCコンパイラやリンカと連携する必要があり、共有ライブラリのビルドがより複雑になります。特に、`runtime/cgo`パッケージは`cgo`のランタイムサポートを提供し、外部リンカの使用を強制することが多いため、共有ライブラリのビルドにおいて特別な考慮が必要です。

### `staleness`検出

ビルドシステムにおける`staleness`とは、ビルド成果物（例: 実行可能ファイル、ライブラリ）が、その入力ファイル（ソースコード、依存ライブラリなど）よりも古い状態であることを指します。`go`コマンドは、ファイルの最終更新時刻（modification time）などを比較することで`staleness`を検出し、必要なものだけを再ビルドすることでビルド時間を短縮します。

### ELFファイルとノートセクション

-   **ELF (Executable and Linkable Format)**: Unix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリなどの標準ファイルフォーマットです。
-   **ノートセクション (`SHT_NOTE`)**: ELFファイルには、プログラムの実行には直接関係しないが、ツールやデバッガにとって有用な情報を格納するための「ノートセクション」を含めることができます。このコミットでは、共有ライブラリが含むGoパッケージのリストをこのノートセクションに格納し、後で読み出すことで、共有ライブラリの内容を動的に把握するために利用しています。

### `shlibname`ファイル

このコミットで導入された概念で、Goパッケージがどの共有ライブラリに属しているかを記録するためのファイルです。例えば、`mypackage.a`というアーカイブファイルが`libshared.so`という共有ライブラリに含まれる場合、`mypackage.shlibname`というファイルが作成され、その中に`libshared.so`という文字列が書き込まれます。これにより、`go`コマンドは特定のパッケージが共有ライブラリの一部であるかどうか、そしてどの共有ライブラリに属しているかを効率的に判断できるようになります。

### `ldd`コマンド

`ldd`はLinuxシステムで利用されるコマンドラインユーティリティで、指定された実行可能ファイルや共有ライブラリが依存している共有ライブラリの一覧を表示します。このコミットのテストスクリプトでは、ビルドされた実行可能ファイルが意図した共有ライブラリに正しくリンクされているかを確認するために使用されています。

## 技術的詳細

このコミットの技術的詳細は、主に`go`コマンドのビルドロジック、特に共有ライブラリの取り扱いとstaleness検出メカニズムの変更に集約されます。

### 1. アクショングラフの変更と`cacheKey`の拡張

以前の`go`コマンドは、共有ライブラリが最新であると判断された場合、その共有ライブラリをビルドするアクションをアクショングラフに含めないことがありました。このコミットでは、共有ライブラリが関与する場合、常に共有ライブラリに対するアクションがアクショングラフに存在するように変更されました。これにより、共有ライブラリのstalenessチェックが常に実行されるようになります。

この変更をサポートするために、`builder`構造体内の`actionCache`のキーとして使用される`cacheKey`構造体が拡張されました。

```go
type cacheKey struct {
	mode  buildMode
	p     *Package
	shlib string // 新しく追加されたフィールド
}
```

`shlib`フィールドが追加されたことで、`actionCache`はパッケージ、ビルドモードに加えて、そのパッケージが属する共有ライブラリの名前も考慮してアクションをキャッシュするようになりました。これにより、共有ライブラリのコンテキストに応じた正確なアクションの管理が可能になります。

### 2. `action1`関数の導入と共有ライブラリのstaleness検出ロジック

`builder.action`関数は`builder.action1`関数に置き換えられ、`lookshared`という新しいブール引数が追加されました。この引数は、共有ライブラリ内でパッケージを探すかどうかを制御します。

`action1`関数内では、`lookshared`が`true`の場合、パッケージが属する共有ライブラリ（`p.Shlib`）が考慮されます。もしその共有ライブラリに対するアクションが既にキャッシュされていればそれを再利用し、そうでなければ`readpkglist`関数を使って共有ライブラリに含まれるパッケージリストを読み込み、`libaction`を呼び出して共有ライブラリをビルドするアクションを生成します。

最も重要な変更は、`libaction`関数内で共有ライブラリのstalenessを検出するロジックが追加されたことです。

```go
// src/cmd/go/build.go の libaction 関数内
// ...
		stale := false
		var built time.Time
		if fi, err := os.Stat(a.target); err == nil {
			built = fi.ModTime()
		}
		for _, p := range pkgs {
			if p.target == "" {
				continue
			}
			stale = stale || p.Stale // パッケージ自体がstaleか
			lstat, err := os.Stat(p.target)
			if err != nil || lstat.ModTime().After(built) { // パッケージのターゲットファイルが共有ライブラリより新しいか
				stale = true
			}
			a.deps = append(a.deps, b.action(depMode, depMode, p))
		}

		if stale {
			// 共有ライブラリがstaleであれば、ビルドアクションを生成
			a.f = (*builder).install
			buildAction := b.libaction(libname, pkgs, modeBuild, depMode)
			a.deps = []*action{buildAction}
			// ... shlibnameファイルのインストールアクションも追加 ...
		}
// ...
```

このロジックは、共有ライブラリを構成する個々のパッケージ（`.a`ファイル）のstaleness、またはパッケージのターゲットファイル（`.a`ファイル）の更新時刻が共有ライブラリ（`.so`ファイル）の更新時刻よりも新しい場合に、共有ライブラリ全体を`stale`と判断します。`stale`と判断された場合、共有ライブラリを再構築するための`buildAction`が生成され、アクショングラフに追加されます。これにより、共有ライブラリが常に最新の依存関係に基づいてビルドされることが保証されます。

### 3. `readnote`関数の導入とELFノートセクションからのパッケージリスト読み込み

`src/cmd/go/note.go`に新しく追加された`readnote`関数は、ELFファイルから特定の名前とタイプのノートセクションを読み取るための汎用的なユーティリティです。この関数は`debug/elf`パッケージを利用してELFファイルを解析し、ノートセクション内の情報を抽出します。

`src/cmd/go/build.go`の`readpkglist`関数は、この`readnote`関数を使用して共有ライブラリファイル（`.so`）から「GO\x00\x00」という名前のノートセクションを読み込みます。このノートセクションには、その共有ライブラリに含まれるGoパッケージのインポートパスのリストが格納されており、`readpkglist`はこのリストを解析して`*Package`のリストを返します。これにより、`go`コマンドは共有ライブラリの内容を動的に把握し、ビルドプロセスに組み込むことができます。

### 4. `Package`構造体への`Shlib`フィールド追加と`shlibname`ファイルの利用

`src/cmd/go/pkg.go`の`Package`構造体に`Shlib`という新しいフィールドが追加されました。このフィールドは、パッケージが共有ライブラリにリンクされている場合に、その共有ライブラリの名前を格納します。

```go
type Package struct {
	// ... 既存のフィールド ...
	Shlib         string `json:",omitempty"` // the shared library that contains this package (only set when -linkshared)
	// ... 既存のフィールド ...
}
```

`Package.load`関数内で、`buildLinkshared`が有効な場合、パッケージのターゲットファイル（`.a`ファイル）に対応する`.shlibname`ファイルを読み込みます。この`.shlibname`ファイルには、そのパッケージが属する共有ライブラリの名前が記述されており、読み込んだ値が`p.Shlib`に設定されます。これにより、各パッケージがどの共有ライブラリに属しているかをビルドシステムが追跡できるようになります。

### 5. `runtime/cgo`の扱い

`src/cmd/go/build.go`と`src/cmd/internal/ld/lib.go`では、`runtime/cgo`パッケージの扱いに関する変更も行われています。`buildmode=shared`を使用する場合、`runtime/cgo`は常に外部リンカを強制するため、共有ライブラリのビルドにおいて特別な考慮が必要です。このコミットでは、`runtime/cgo`が共有ライブラリに含まれるべきかどうか、そしてそれが既に別の共有ライブラリに含まれていないかを確認するロジックが追加され、重複や不整合を防ぐようになっています。

### 6. テストスクリプトの強化

`misc/cgo/testshared/test.bash`スクリプトは、共有ライブラリの再構築ロジックを検証するための新しいテストケースで大幅に強化されました。

-   `dep`パッケージと`exe`パッケージという新しいテスト用Goパッケージが追加されました。`dep`は共有ライブラリとしてビルドされ、`exe`は`dep`にリンクします。
-   `ensure_ldd`関数が導入され、`ldd`コマンドを使用して実行可能ファイルが意図した共有ライブラリにリンクされていることを確認します。
-   `will_check_rebuilt`, `assert_rebuilt`, `assert_not_rebuilt`というヘルパー関数が導入され、ファイルの更新時刻を比較することで、特定のファイルが再構築されたかどうかを検証します。
-   `dep.go`のソースファイルを`touch`して更新し、`exe`を再インストールすることで、`libdep.so`と`dep.a`が再構築されることを検証するテストケースが追加されました。
-   `dep.a`ファイルを`touch`して更新し、`exe`を再インストールすることで、`libdep.so`のみが再構築され、`dep.a`は再構築されないことを検証するテストケースも追加されました。これは、共有ライブラリのstaleness検出がより粒度高く行われるようになったことを示しています。

これらのテストケースは、共有ライブラリのstaleness検出と再構築のメカニズムが期待通りに機能することを保証します。

## コアとなるコードの解説

### `src/cmd/go/build.go`における変更

-   **`cacheKey`の拡張**:
    ```go
    type cacheKey struct {
    	mode  buildMode
    	p     *Package
    	shlib string // 共有ライブラリの名前を識別子として追加
    }
    ```
    この変更により、`go`コマンドの内部キャッシュは、同じパッケージであっても異なる共有ライブラリに属する場合や、共有ライブラリにリンクしない場合とで、異なるビルドアクションを区別できるようになりました。これは、共有ライブラリのコンテキストに応じた正確なビルド管理の基盤となります。

-   **`action1`と`libaction`におけるstaleness検出と再構築ロジック**:
    `action1`関数は、パッケージが共有ライブラリに属している場合、その共有ライブラリに対するアクションを生成または取得します。ここで重要なのは、`libaction`関数内で実装されたstaleness検出ロジックです。
    ```go
    // libaction 関数内 (簡略化)
    // ...
    		stale := false
    		var built time.Time
    		if fi, err := os.Stat(a.target); err == nil {
    			built = fi.ModTime() // 共有ライブラリの最終更新時刻
    		}
    		for _, p := range pkgs {
    			// ...
    			stale = stale || p.Stale // 構成パッケージ自体がstaleか
    			lstat, err := os.Stat(p.target)
    			if err != nil || lstat.ModTime().After(built) { // 構成パッケージのアーカイブファイルが共有ライブラリより新しいか
    				stale = true
    			}
    			// ...
    		}

    		if stale {
    			// 共有ライブラリがstaleであれば、ビルドアクションを生成し、依存関係として追加
    			a.f = (*builder).install
    			buildAction := b.libaction(libname, pkgs, modeBuild, depMode)
    			a.deps = []*action{buildAction}
    			// ... shlibnameファイルのインストールアクションも追加 ...
    		}
    // ...
    ```
    このコードは、共有ライブラリを構成する個々のパッケージ（`.a`ファイル）のいずれかがstaleであるか、またはそのアーカイブファイルの更新時刻が共有ライブラリ（`.so`ファイル）の更新時刻よりも新しい場合に、共有ライブラリ全体をstaleとマークします。`stale`と判断された場合、`go`コマンドは共有ライブラリを再構築するための新しいビルドアクションを生成し、それを現在のアクションの依存関係として追加します。これにより、共有ライブラリが常に最新の依存関係に基づいて再ビルドされることが保証されます。

-   **`allArchiveActions`関数**:
    ```go
    func allArchiveActions(root *action) []*action {
    	// ...
    	// rootアクションから辿れるすべてのアーカイブ(.a)アクションを収集
    	// 共有ライブラリ(.so)アクションを介して依存するアーカイブも含む
    	// ...
    }
    ```
    この新しいヘルパー関数は、特定のアクション（通常は実行可能ファイルのリンクアクション）が依存するすべてのアーカイブファイル（`.a`）のビルドアクションを再帰的に収集します。これは、共有ライブラリにリンクする場合、直接の依存関係だけでなく、共有ライブラリが内部的に依存するアーカイブファイルも考慮する必要があるため重要です。`go build`コマンドがコンパイル時に`-I`フラグでインクルードパスを指定する際に、この関数が収集したアーカイブアクションのパスが使用されます。

### `src/cmd/go/note.go`における`readnote`関数

// src/cmd/go/note.go
func readnote(filename, name string, typ int32) ([]byte, error) {
	f, err := elf.Open(filename)
	if err != nil {
		return nil, err
	}
	// ... ELFファイルのノートセクションを走査し、指定された名前とタイプのノートを読み込むロジック ...
}
```
この関数は、ELF形式の共有ライブラリファイルから、特定の名前（例: "GO\x00\x00"）とタイプを持つノートセクションのデータを読み取ります。Goのビルドシステムは、共有ライブラリにその共有ライブラリに含まれるGoパッケージのリストをこのノートセクションに書き込みます。`readnote`関数は、この埋め込まれたパッケージリストを後で読み出すために使用されます。これにより、`go`コマンドは共有ライブラリの内容を動的に検査し、ビルドの依存関係を正確に解決できるようになります。

### `src/cmd/go/pkg.go`における`Shlib`フィールドと`.shlibname`ファイルの利用

```go
// src/cmd/go/pkg.go の Package 構造体
type Package struct {
	// ...
	Shlib         string `json:",omitempty"` // このパッケージを含む共有ライブラリの名前
	// ...
}

// Package.load 関数内 (簡略化)
// ...
	if buildLinkshared {
		shlibnamefile := p.target[:len(p.target)-2] + ".shlibname" // .a ファイル名から .shlibname ファイル名を生成
		shlib, err := ioutil.ReadFile(shlibnamefile)
		if err == nil {
			p.Shlib = strings.TrimSpace(string(shlib)) // 読み込んだ共有ライブラリ名を Shlib フィールドに設定
		} else if !os.IsNotExist(err) {
			fatalf("unexpected error reading %s: %v", shlibnamefile, err)
		}
	}
// ...
```
`Package`構造体に`Shlib`フィールドが追加されたことで、各Goパッケージがどの共有ライブラリに属しているかという情報が、ビルドシステム内で明示的に管理されるようになりました。`Package.load`関数は、パッケージのアーカイブファイル（`.a`）がビルドされた際に生成される可能性のある`.shlibname`ファイルを読み込み、その内容（共有ライブラリ名）を`p.Shlib`に設定します。この情報は、`action1`関数が共有ライブラリのアクションを決定する際に利用され、パッケージが共有ライブラリの一部である場合のビルドパスを適切に処理するために不可欠です。

これらの変更により、Goのビルドシステムは共有ライブラリのstalenessをより正確に検出し、必要に応じて再構築をトリガーすることで、共有ライブラリを使用する際のビルドの信頼性と整合性を大幅に向上させています。

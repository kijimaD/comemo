# [インデックス 20105] ファイルの概要

このコミットは、Go言語のビルドシステムの一部である `cmd/dist` に関連する変更を含んでいます。具体的には、以下の3つのファイルが変更されています。

- `src/cmd/dist/a.h`: ヘッダーファイルの変更
- `src/cmd/dist/build.c`: ビルドプロセスを管理するC言語ソースファイルの変更
- `src/cmd/dist/goc2c.c`: `.goc` ファイルをC言語ソースファイルに変換するツールの変更

## 変更の背景

このコミットは、Go言語のビルドプロセスにおけるデバッグ情報の不整合を修正するために行われました。Go言語のソースコードからツールチェインをビルドする際、`GOROOT_FINAL` 環境変数を設定することで、ビルドが行われる場所（ビルドロケーション）とは異なる最終的なインストール場所（インストールロケーション）を指定できます。

しかし、`goc2c` というツールが `.goc` ファイル（GoとCの混合コード）をC言語のソースファイルに変換する際に、生成されるCソースファイルに埋め込まれる行番号情報が、ビルドロケーションを参照していました。この問題自体は、直接的な実行には影響しませんが、Goのリンカが `runtime/string.goc` の場所を使用して、結果として生成されるバイナリにGDB（GNU Debugger）スクリプトを埋め込む際に問題を引き起こしました。

具体的には、リンカが埋め込むGDBスクリプトにはビルドロケーションのパスが含まれているにもかかわらず、デバッガはインストールロケーションを期待するため、デバッガが「スクリプトがロードパスの外にある」と不平を言う結果となっていました。これにより、デバッグ体験が損なわれ、開発者がGoプログラムを効果的にデバッグすることが困難になっていました。この問題は、Go issue 8524として報告されていました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

1.  **Go言語のビルドシステム (`cmd/dist`)**: Go言語のツールチェイン自体をビルドするためのシステムです。Goのコンパイラ、リンカ、その他のツールはGo言語で書かれていますが、それらを最初にビルドするためには特別なブートストラッププロセスが必要です。`cmd/dist` はこのブートストラップと、GoのソースコードからGoのバイナリを生成する全体のビルドプロセスを管理します。

2.  **`GOROOT_FINAL`**: Goツールチェインをソースからビルドする際に使用される環境変数です。これは、ビルドされたGoツリーがコンパイル後に移動される場合に、Goのバイナリやスクリプトが想定する最終的なインストールパスを指定するために使用されます。例えば、`/usr/local/go` にインストールされることを想定してビルドするが、実際のビルドは一時的なディレクトリで行う場合などに設定されます。

3.  **`goc2c`**: Goのビルドプロセス内で使用される内部ツールの一つです。Goのランタイムには、GoとC言語のコードが混在している `.goc` ファイルが存在します。`goc2c` は、これらの `.goc` ファイルをC言語のソースファイルに変換する役割を担っています。この変換プロセス中に、元の `.goc` ファイルの行番号情報が、生成されるCソースファイルに `#line` ディレクティブとして埋め込まれます。これにより、Cコンパイラがエラーや警告を報告する際に、元の `.goc` ファイルの正確な行番号を示すことができます。

4.  **GDBスクリプトの埋め込みとデバッグ情報のパス**: Goのリンカは、生成される実行可能バイナリにデバッグ情報を埋め込みます。これには、ソースファイルのパスや行番号情報が含まれます。特に、Goのランタイムの一部である `runtime/string.goc` のようなファイルは、デバッガがGoプログラムの実行状態を正確に解釈するために必要なGDBスクリプトの生成に関連しています。デバッガは、これらのスクリプトやソースファイルのパスが、実際にファイルが存在する場所と一致することを期待します。不一致があると、デバッガはソースコードの表示やブレークポイントの設定などで問題を起こす可能性があります。

## 技術的詳細

問題の核心は、`goc2c` が生成するCソースファイルに埋め込む `#line` ディレクティブのパスが、`GOROOT_FINAL` で指定された最終的なインストールパスではなく、ビルド時のパスを参照していた点にあります。

Goのビルドプロセスでは、`runtime/string.goc` のようなファイルが `goc2c` によってCソースに変換され、その後Cコンパイラによってコンパイルされます。このCソースには、元の `.goc` ファイルのパスと行番号を示す `#line` ディレクティブが含まれています。

```c
#line <line_number> "<file_path>"
```

この `<file_path>` の部分が、`GOROOT_FINAL` が設定されているにもかかわらず、ビルドが行われた一時的なディレクトリのパスになっていました。

Goのリンカは、最終的なバイナリを生成する際に、デバッグ情報の一部として、これらのソースファイルのパスを埋め込みます。特に、`runtime/string.goc` に関連するデバッグ情報は、GDBがGoプログラムをデバッグする際に使用するスクリプトのパスに影響を与えます。

デバッガ（GDBなど）がGoの実行可能ファイルをロードし、デバッグを開始しようとすると、埋め込まれたデバッグ情報に基づいてソースファイルやスクリプトを探します。もし、デバッグ情報に記録されているパスがビルドロケーション（例: `/tmp/go-build-12345/src/runtime/string.goc`）であり、Goが実際にインストールされている場所がインストールロケーション（例: `/usr/local/go/src/runtime/string.goc`）である場合、デバッガは指定されたパスにファイルを見つけることができず、「スクリプトがロードパスの外にある」といったエラーを報告します。

このコミットの修正は、`goc2c` が `#line` ディレクティブに埋め込むパスを、ビルドロケーションではなく、`GOROOT_FINAL` で指定されたインストールロケーションのパスに修正することで、この不整合を解消します。これにより、デバッガが正しいパスでソースファイルやGDBスクリプトを見つけられるようになり、デバッグ体験が改善されます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/dist/a.h`**:
    *   `goc2c` 関数のプロトタイプが変更され、新しい引数 `goc_final` が追加されました。
        ```diff
        -void	goc2c(char*, char*);
        +void	goc2c(char*, char*, char*);
        ```

2.  **`src/cmd/dist/build.c`**:
    *   `install` 関数内で、`goc2c` を呼び出す際に、`GOROOT_FINAL` に基づく最終的なパスを渡すように変更されました。
    *   新しい `Buf` 型の変数 `final_path` と `final_name` が追加されました。
    *   `final_path` は `GOROOT_FINAL` と現在のディレクトリパスを結合して構築されます。
    *   `goc2c` の呼び出しで、元の `.goc` ファイルのパス (`p`)、最終的な `.goc` ファイルのパス (`bstr(&final_name)`)、および生成されるCソースファイルのパス (`bstr(&b)`) の3つの引数を渡すように変更されました。
        ```diff
        -	Buf b, b1, path;
        +	Buf b, b1, path, final_path, final_name;
        // ...
        +	binit(&final_path);
        +	binit(&final_name);
        // ...
        +	bpathf(&final_path, "%s/src/%s", goroot_final, dir);
        // ...
        -		bprintf(&b, "%s%sz%s", bstr(&path), slash, lastelem(p));
        +		bprintf(&b, "%s%sz%s", bstr(&path), slash, lastelem(p));
        +		bprintf(&final_name, "%s%s%s", bstr(&final_path), slash, lastelem(p));
        // ...
        -		goc2c(p, bstr(&b));
        +		goc2c(p, bstr(&final_name), bstr(&b));
        ```

3.  **`src/cmd/dist/goc2c.c`**:
    *   `goc2c` 関数が新しい引数 `goc_final` を受け取るように変更されました。
    *   `final_file` という新しい静的変数が追加され、`goc_final` の値が格納されます。
    *   `#line` ディレクティブを生成する箇所で、元の `file` 変数ではなく、新しく追加された `final_file` 変数を使用するように変更されました。
        ```diff
        static const char *file;
        +static const char *final_file;
        static unsigned int lineno;
        // ...
        -			bwritef(output, "\n#line %d \"%s\"\n", lineno, file);
        +			bwritef(output, "\n#line %d \"%s\"\n", lineno, final_file);
        // ...
        -	bwritef(output, "#line %d \"%s\"\n", lineno, file);
        +	bwritef(output, "#line %d \"%s\"\n", lineno, final_file);
        // ...
        void
        -goc2c(char *goc, char *c)
        +goc2c(char *goc, char *goc_final, char *c)
        {
        // ...
        	file = goc;
        +	final_file = goc_final;
        ```

## コアとなるコードの解説

この変更の核心は、`goc2c` ツールが生成するCソースファイル内の `#line` ディレクティブに埋め込まれるファイルパスを、ビルド時のパスから最終的なインストールパス（`GOROOT_FINAL` に基づくパス）に切り替えることです。

1.  **`goc2c` 関数の引数追加**: `src/cmd/dist/a.h` と `src/cmd/dist/goc2c.c` で `goc2c` 関数に `goc_final` という新しい `char*` 引数が追加されました。この引数は、`GOROOT_FINAL` を考慮した最終的な `.goc` ファイルのパスを `goc2c` に渡すために使用されます。

2.  **`build.c` でのパスの計算と引き渡し**: `src/cmd/dist/build.c` の `install` 関数は、Goのパッケージをビルドおよびインストールする主要なロジックを含んでいます。
    *   `final_path` という新しい `Buf` 変数が導入され、`goroot_final` (これは `GOROOT_FINAL` 環境変数の値に対応します) と現在のソースディレクトリを結合して、最終的なインストールパスを構築します。
    *   `goc2c` を呼び出す際、以前はビルド時のパス (`bstr(&b)`) のみを渡していましたが、変更後は `bstr(&final_name)` を追加で渡すようになりました。`final_name` は `final_path` に基づいて構築され、`GOROOT_FINAL` を考慮した `.goc` ファイルの最終的なパスを表します。

3.  **`goc2c.c` での `#line` ディレクティブの修正**: `src/cmd/dist/goc2c.c` は、実際に `.goc` ファイルをCソースに変換するロジックを含んでいます。
    *   `goc2c` 関数内で、新しく受け取った `goc_final` 引数の値が `final_file` という静的変数に格納されます。
    *   Cソースファイルに `#line` ディレクティブを書き込むすべての箇所で、以前はビルド時のパスを保持していた `file` 変数を使用していたのを、新しく最終的なパスを保持する `final_file` 変数を使用するように変更されました。

この一連の変更により、`goc2c` が生成するCソースファイル内のデバッグ情報（特にファイルパス）が、Goが最終的にインストールされる場所と一致するようになります。これにより、GDBのようなデバッガがGoのバイナリをデバッグする際に、正しいソースファイルのパスを解決できるようになり、デバッグ時の「スクリプトがロードパスの外にある」というエラーが解消されます。これは、Goのビルドシステムとデバッグツールの間の整合性を高め、開発者のデバッグ体験を向上させる重要な修正です。

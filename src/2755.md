# [インデックス 2755] ファイルの概要

このコミットは、Go言語のリンカである`6l`におけるELF64（Executable and Linkable Format for 64-bit systems）関連の定数（いわゆる「マジックナンバー」）の整理と移動を目的としています。具体的には、ELF64ヘッダのサイズや構造に関する定数が、リンカの主要なアセンブラ部分（`src/cmd/6l/asm.c`）から、ELF64フォーマットを専門に扱う`src/cmd/ld/elf64.c`および`src/cmd/ld/elf64.h`へと集約されました。これにより、コードの保守性と可読性が向上し、ELF64関連のロジックが一元管理されるようになります。

## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ初期開発段階にありました。Goのツールチェイン、特にリンカ（`6l`はamd64アーキテクチャ向けのリンカ）は、様々なプラットフォーム向けの実行ファイルを生成する必要がありました。ELF64はLinuxなどのUnix系システムで広く使われる64ビット実行ファイルフォーマットであり、Goのバイナリ生成において重要な役割を担っていました。

初期のコードベースでは、ELF64ヘッダのサイズやオフセットといった定数（「マジックナンバー」と呼ばれることもあります）が、リンカの異なる部分に散在していることがありました。これは、コードの可読性を低下させ、将来的な変更やバグ修正を困難にする要因となります。例えば、ELF64の仕様が変更された場合、複数のファイルを修正する必要が生じ、一貫性のない挙動を引き起こす可能性がありました。

このコミットの背景には、このような散在する定数を一箇所に集約し、ELF64関連のロジックをモジュール化して、コードベース全体の品質と保守性を向上させるという、一般的なソフトウェアエンジニアリングのベストプラクティスがあります。特に、リンカのような低レベルで複雑なツールにおいては、このような整理は非常に重要です。

## 前提知識の解説

### 1. ELF64 (Executable and Linkable Format for 64-bit systems)

ELFは、Unix系オペレーティングシステム（Linux、FreeBSDなど）で実行ファイル、共有ライブラリ、オブジェクトファイルを表現するための標準的なファイルフォーマットです。ELF64は、64ビットアーキテクチャ（x86-64など）向けに拡張されたバージョンです。

ELFファイルは主に以下のセクションで構成されます。
*   **ELFヘッダ (ELF Header):** ファイルの先頭に位置し、ファイルのタイプ（実行ファイル、ライブラリなど）、ターゲットアーキテクチャ、エントリポイントアドレスなど、ファイル全体の基本的な情報を含みます。
*   **プログラムヘッダテーブル (Program Header Table):** 実行時にメモリにロードされるセグメント（コード、データなど）の配置情報を含みます。各エントリはプログラムヘッダ (Program Header, PHDR) と呼ばれます。
*   **セクションヘッダテーブル (Section Header Table):** リンク時に使用されるファイルの論理的な構造（.text, .data, .bssなどのセクション）に関する情報を含みます。各エントリはセクションヘッダ (Section Header, SHDR) と呼ばれます。
*   **セクション (Sections):** 実際のコードやデータが格納される領域です。

ELFヘッダ、プログラムヘッダ、セクションヘッダには、それぞれ固定のサイズがあります。これらのサイズはELF仕様によって定義されており、リンカが実行ファイルを正しく構築するために不可欠な「マジックナンバー」となります。

### 2. Go言語のリンカ (`6l`)

Go言語のツールチェインには、各アーキテクチャに対応するアセンブラとリンカが含まれています。`6l`は、x86-64（amd64）アーキテクチャ向けのGoプログラムをリンクするためのツールです。リンカの主な役割は、コンパイルされたオブジェクトファイル（`.o`ファイル）とライブラリを結合し、実行可能なバイナリファイルを生成することです。このプロセスには、シンボルの解決、アドレスの再配置、そしてELFなどの特定のファイルフォーマットに準拠したヘッダやセクションの構築が含まれます。

### 3. マジックナンバー (Magic Numbers)

プログラミングにおける「マジックナンバー」とは、コード中に直接埋め込まれた、意味不明な数値定数のことを指します。このコミットの文脈では、ELF64ヘッダのサイズ（例: 64バイト）、プログラムヘッダのエントリサイズ（例: 56バイト）、セクションヘッダのエントリサイズ（例: 64バイト）といった、ELFフォーマットの構造を定義する数値定数を指します。これらは本来、ELF仕様に基づいた明確な意味を持つ値ですが、コード中にリテラル値として散在していると、その意味が分かりにくくなり、変更が必要になった際に探し出すのが困難になります。そのため、通常は名前付き定数として定義し、一箇所に集約することが推奨されます。

## 技術的詳細

このコミットの核心は、ELF64バイナリの構造を定義するいくつかの重要な定数を、より適切な場所へ移動し、名前付き定数として定義し直すことです。

具体的には、以下の定数が対象となります。
*   **ELFヘッダのサイズ**: `ehsize`
*   **プログラムヘッダのエントリサイズ**: `phentsize`
*   **セクションヘッダのエントリサイズ**: `shentsize`
*   **ELF64ヘッダ全体の予約サイズ**: `HEADR` (これはELF64ヘッダ、プログラムヘッダ、セクションヘッダの合計サイズを考慮した、ファイル先頭に予約される領域のサイズ)

以前のコードでは、これらの値が`src/cmd/6l/asm.c`内でリテラル値として直接使用されていました。例えば、`eh->phoff = 64L;` や `eh->ehsize = 64;` といった記述です。これは、ELF64の構造に関する知識が`asm.c`に漏れ出している状態であり、`ld/elf64.c`や`ld/elf64.h`というELF64専用のファイルが存在するにもかかわらず、情報が分散していました。

この変更により、これらの定数は`src/cmd/ld/elf64.h`に`#define`ディレクティブを使って定義され、`ELF64HDRSIZE` (64), `ELF64PHDRSIZE` (56), `ELF64SHDRSIZE` (64) といった明確な名前が与えられました。さらに、`elf64init()`という新しい関数が`src/cmd/ld/elf64.c`に導入され、これらの定数を使ってELF64ヘッダの初期値を設定するようになりました。

また、`src/cmd/6l/obj.c`では、`HEADR`というリンカがファイル先頭に予約する領域のサイズが、以前は`elf64headr()`という関数で計算されていましたが、このコミットで`ELF64FULLHDRSIZE`という新しい定数に置き換えられました。`ELF64FULLHDRSIZE`は、ELF64ヘッダ、プログラムヘッダ、セクションヘッダの合計サイズを考慮した、ファイル先頭に予約される領域のサイズを定義するもので、`elf64.h`で2048バイトと定義されています。これは、将来的な拡張やアライメントの要件に対応するために、ある程度の余裕を持たせた値です。

この変更は、単に定数を移動するだけでなく、リンカの初期化ロジックにも影響を与えています。`asm.c`の`asmb()`関数内で`elf64init()`が呼び出されるようになり、ELF64ヘッダの初期化が`ld/elf64.c`に委譲されるようになりました。これにより、`asm.c`はELF64の内部構造の詳細を知る必要がなくなり、より高レベルなアセンブル処理に集中できるようになります。

## コアとなるコードの変更箇所

### `src/cmd/6l/asm.c`
*   `asmb()`関数内で`elf64init()`の呼び出しが追加されました。
*   ELF64ヘッダのフィールド（`phoff`, `shoff`, `ehsize`, `phentsize`, `shentsize`）への直接的なリテラル値の代入が削除されました。
*   `elf64writehdr()`, `elf64writephdrs()`, `elf64writeshdrs()`の呼び出しが、それぞれの戻り値（書き込まれたバイト数）を合計して`ELF64FULLHDRSIZE`と比較する形に変更されました。これは、ヘッダサイズが想定内に収まっているかを確認するためのチェックです。

### `src/cmd/6l/obj.c`
*   `main()`関数内で、ELF64実行ファイルの場合の`HEADR`の初期化が、`elf64headr()`関数の呼び出しから`ELF64FULLHDRSIZE`定数への直接代入に変更されました。

### `src/cmd/ld/elf64.c`
*   `elf64init()`関数が新しく追加され、ELF64ヘッダのオフセットやサイズに関するフィールド（`hdr.phoff`, `hdr.shoff`, `hdr.ehsize`, `hdr.phentsize`, `hdr.shentsize`）を、`elf64.h`で定義された定数を使って初期化するようになりました。
*   `elf64headr()`関数が削除されました。
*   `elf64writeshdrs()`、`elf64writephdrs()`、`elf64writehdr()`関数が、`void`から`uint32`を返すように変更され、それぞれが書き込んだヘッダの合計サイズを返すようになりました。
*   文字列テーブル関連の変数名が`nume64str`から`numstr`に変更されました。

### `src/cmd/ld/elf64.h`
*   ELF64ヘッダ、プログラムヘッダ、セクションヘッダのサイズを定義する新しい定数`ELF64HDRSIZE` (64), `ELF64PHDRSIZE` (56), `ELF64SHDRSIZE` (64) が追加されました。
*   ファイル先頭に予約される領域の合計サイズを定義する`ELF64FULLHDRSIZE` (2048) が追加されました。
*   `elf64init()`関数のプロトタイプ宣言が追加されました。
*   `elf64headr()`関数のプロトタイプ宣言が削除されました。
*   `elf64writehdr()`, `elf64writephdrs()`, `elf64writeshdrs()`関数の戻り値の型が`void`から`uint32`に変更されました。

## コアとなるコードの解説

このコミットの主要な目的は、ELF64フォーマットに関する「マジックナンバー」を中央集権化し、コードのモジュール性と保守性を高めることです。

1.  **定数の一元化**: `src/cmd/ld/elf64.h`に`ELF64HDRSIZE`, `ELF64PHDRSIZE`, `ELF64SHDRSIZE`, `ELF64FULLHDRSIZE`といった名前付き定数を導入することで、ELF64の構造に関する数値がコード全体に散らばることを防ぎます。これにより、ELF64の仕様変更があった場合でも、`elf64.h`の1箇所を修正するだけで済み、エラーのリスクを低減できます。

2.  **初期化ロジックの分離**: `src/cmd/ld/elf64.c`に`elf64init()`関数を導入し、ELF64ヘッダの初期化ロジックを`asm.c`から分離しました。`asm.c`はリンカの全体的なアセンブルフローを管理する役割に徹し、ELF64固有の詳細な初期化は`elf64.c`に任せることで、関心の分離（Separation of Concerns）が実現されています。これは、コードの理解を容易にし、各ファイルの責任範囲を明確にします。

3.  **ヘッダサイズ計算の改善**: 以前は`elf64headr()`関数がヘッダサイズを「TODO: calculate these byte counts properly」というコメント付きで概算していましたが、この関数は削除され、代わりに`ELF64FULLHDRSIZE`という固定値が導入されました。これは、初期開発段階での暫定的な計算から、より堅牢で余裕を持った固定サイズへの移行を示唆しています。また、`asm.c`で`elf64writehdr()`などの戻り値を合計して`ELF64FULLHDRSIZE`と比較するチェックが追加されたことで、実際に書き込まれたヘッダのサイズが予約された領域を超えていないかを確認できるようになり、潜在的なバッファオーバーフローやファイル破損を防ぐための安全策が講じられています。

4.  **型安全性の向上**: `elf64writeshdrs()`などの関数が`void`から`uint32`を返すように変更されたことで、これらの関数が実際に書き込んだバイト数を呼び出し元に伝えることができるようになりました。これにより、リンカはファイル構造の整合性をより厳密にチェックできるようになります。

これらの変更は、Goリンカのコードベースが成熟し、より堅牢で保守しやすい設計へと進化していく過程の一部を示しています。低レベルなシステムプログラミングにおいては、このような定数の管理とモジュール化が、長期的なプロジェクトの成功に不可欠です。

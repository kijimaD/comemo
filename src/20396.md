# [インデックス 20396] ファイルの概要

このコミットは、Goランタイムにおけるスタックトレースの生成方法に関する改善です。特に、`onM`関数が呼び出された際のスタックトレースが途中で途切れてしまう問題を解決し、より完全なトレース情報を提供することを目的としています。これにより、プログラムがクラッシュした際に、`onM`の呼び出し元を正確に特定できるようになります。

## コミット

Author: Russ Cox <rsc@golang.org>
Date:   Thu Sep 4 22:48:08 2014 -0400

    runtime: do not stop traceback at onM
    
    Behavior before this CL:
    
    1. If onM is called on a g0 stack, it just calls the given function.
    
    2. If onM is called on a gsignal stack, it calls badonm.
    
    3. If onM is called on a curg stack, it switches to the g0 stack
    and then calls the function.
    
    In cases 1 and 2, if the program then crashes (and badonm always does),
    we want to see what called onM, but the traceback stops at onM.
    In case 3, the traceback must stop at onM, because the g0
    stack we are renting really does stop at onM.
    
    The current code stops the traceback at onM to handle 3,
    at the cost of making 1 and 2 crash with incomplete traces.
    
    Change traceback to scan past onM but in case 3 make it look
    like on the rented g0 stack, onM was called from mstart.
    The traceback already knows that mstart is a top-of-stack function.
    
    Alternate fix at CL 132610043 but I think this one is cleaner.
    This CL makes 3 the exception, while that CL makes 1 and 2 the exception.
    
    Submitting TBR to try to get better stack traces out of the
    freebsd/amd64 builder, but happy to make changes in a
    followup CL.

## 変更の背景

Goランタイムでは、特定の低レベルな処理を実行するために、通常のゴルーチンスタックとは異なる特殊なスタック（`g0`スタックや`gsignal`スタック）を使用することがあります。`onM`関数は、これらの特殊なコンテキストで関数を実行するためのメカニズムを提供します。

このコミットが導入される前は、`onM`関数がスタックトレースの生成において問題を引き起こしていました。具体的には、`onM`が呼び出された時点でスタックトレースが途切れてしまい、`onM`のさらに上位の呼び出し元（つまり、`onM`を呼び出した実際のコード）がトレースに含まれないという問題がありました。

この問題は、特にプログラムがクラッシュした際に深刻でした。クラッシュの原因を特定するためには、完全なスタックトレースが不可欠ですが、`onM`でトレースが途切れることで、デバッグ情報が不完全になっていました。

コミットメッセージでは、`onM`の呼び出しパターンを以下の3つのケースに分類しています。

1.  **`g0`スタックからの呼び出し**: `onM`は与えられた関数を直接呼び出します。
2.  **`gsignal`スタックからの呼び出し**: `onM`は`badonm`関数を呼び出します。`badonm`は常にクラッシュを引き起こします。
3.  **現在のゴルーチン（`curg`）スタックからの呼び出し**: `onM`は`g0`スタックに切り替えてから関数を呼び出します。

問題は、ケース1と2でクラッシュが発生した場合、`onM`の呼び出し元を知りたいにもかかわらず、トレースが`onM`で止まってしまうことでした。ケース3では、`g0`スタックを「借りて」いるため、トレースが`onM`で止まるのが正しい振る舞いとされていました。

以前のコードは、ケース3の振る舞いに合わせて`onM`でトレースを停止させていましたが、その代償としてケース1と2で不完全なトレースが生成されていました。このコミットは、この不整合を解消し、ケース1と2で完全なトレースを提供しつつ、ケース3の特殊な要件も満たすことを目指しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念について理解しておく必要があります。

*   **Goroutine (G)**: Goにおける軽量な実行スレッドです。Goプログラムの並行性の基本単位となります。
*   **Machine (M)**: オペレーティングシステムのスレッドに相当します。Goランタイムは、M上でGを実行します。
*   **Processor (P)**: MとGを仲介する論理プロセッサです。Pは実行可能なGのキューを保持し、MにGをディスパッチします。
*   **スタック (Stack)**: 関数呼び出しの情報を格納するメモリ領域です。Goでは、ゴルーチンごとに独自のスタックを持ちます。
    *   **Goroutine Stack**: 通常のGoコードが実行される際に使用されるスタックです。動的にサイズが変更されます。
    *   **`g0` Stack**: ランタイム内部の低レベルな処理（スケジューリング、GC、システムコールなど）を実行するために使用される特別なスタックです。各Mに紐付けられ、固定サイズです。
    *   **`gsignal` Stack**: シグナルハンドラが実行される際に使用される特別なスタックです。シグナル処理中に通常のスタックが破損するのを防ぐために使用されます。
*   **`onM` 関数**: Goランタイム内部で使用される関数で、現在のM（OSスレッド）上で特定の関数を実行するために使用されます。これは、現在のゴルーチンスタックから`g0`スタックに切り替える必要がある場合や、シグナルハンドラのような特殊なコンテキストでコードを実行する必要がある場合などに利用されます。
*   **スタックトレース (Stack Trace)**: プログラムの実行中に、ある時点での関数呼び出しの連鎖（コールスタック）を示すリストです。デバッグやエラー解析において非常に重要な情報となります。Goランタイムは、プログラムがパニックを起こしたり、デバッガがアタッチされたりした際にスタックトレースを生成します。
*   **`mstart` 関数**: GoランタイムがM（OSスレッド）を起動する際に最初に実行される関数です。これはMのライフサイクルにおけるエントリポイントであり、スタックトレースにおいては通常、スタックの最上位（またはそれに近い位置）に現れる関数として認識されます。

## 技術的詳細

このコミットの核心は、Goランタイムのスタックトレース生成ロジックと、`onM`関数の振る舞いの間の不整合を解消することにあります。

従来のスタックトレース生成メカニズムでは、`onM`関数がスタックトレースの「トップ」と見なされ、それより上位の呼び出し元がトレースに含まれませんでした。これは、`onM`が`curg`スタックから`g0`スタックに切り替えるケース（ケース3）を考慮した設計でした。この場合、`onM`が`g0`スタックを「借りて」実行されるため、`g0`スタック上では`onM`がスタックの最上位にあると見なすのが適切でした。

しかし、この設計は、`onM`が`g0`スタックや`gsignal`スタックから直接呼び出されるケース（ケース1と2）において問題を引き起こしました。これらのケースでは、`onM`の呼び出し元はデバッグ上非常に重要であり、トレースが`onM`で途切れることはデバッグを困難にしていました。特に、`gsignal`スタックから`badonm`が呼び出されてクラッシュする場合、`badonm`を呼び出した`onM`、そして`onM`を呼び出したシグナルハンドラやその他のランタイムコードのコンテキストが失われることは大きな問題でした。

このコミットの解決策は、スタックトレースのロジックを変更し、`onM`を「スタックのトップ」と見なさないようにすることです。これにより、ケース1と2では`onM`の呼び出し元もトレースに含まれるようになります。

一方で、ケース3の特殊な要件（`curg`スタックから`g0`スタックに切り替える場合）を維持するために、アセンブリコードに巧妙な変更が加えられています。具体的には、`curg`スタックから`g0`スタックに切り替える際に、`g0`スタックの最上位に`mstart`関数が`onM`を呼び出したかのように見せかけるための偽の戻りアドレスをプッシュします。スタックトレースのロジックは`mstart`をスタックのトップ関数として認識しているため、これにより、ケース3では`onM`が`mstart`から呼び出されたように見え、それより上位の`curg`スタックのトレースは表示されなくなります。これは、`g0`スタックを「借りて」いるという状況をスタックトレースに正しく反映させるための工夫です。

この変更により、ケース1と2では完全なスタックトレースが得られ、ケース3では以前と同様に`onM`より上位の`curg`スタックのトレースは表示されないという、それぞれのケースに最適な振る舞いが実現されます。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/pkg/runtime/asm_386.s` (32-bit x86 アセンブリ)
*   `src/pkg/runtime/asm_amd64.s` (64-bit x86 アセンブリ)
*   `src/pkg/runtime/asm_arm.s` (ARM アセンブリ)
*   `src/pkg/runtime/traceback.go` (Goソースコード)

**`src/pkg/runtime/asm_*.s` ファイルの変更点:**

これらのアセンブリファイルでは、`oncurg`というラベルの付いたセクションが変更されています。`oncurg`は、`onM`が現在のゴルーチン（`curg`）スタックから呼び出された際に、`g0`スタックに切り替える処理を担当する部分です。

変更前:
```assembly
    // switch to g0
    MOVL    DX, g(CX)
    MOVL    (g_sched+gobuf_sp)(DX), SP
```
（amd64では`MOVQ`、armでは`MOVW`）

変更後:
```assembly
    // switch to g0
    MOVL    DX, g(CX)
    MOVL    (g_sched+gobuf_sp)(DX), BX // SPをBXにロード
    // make it look like mstart called onM on g0, to stop traceback
    SUBL    $4, BX // スタックポインタを4バイト（32bitの場合）減らす
    MOVL    $runtime·mstart(SB), DX // mstart関数のアドレスをDXにロード
    MOVL    DX, 0(BX) // 減らしたスタックポインタの位置にmstartのアドレスをプッシュ
    MOVL    BX, SP // SPを更新
```
（amd64では`MOVQ`、`SUBQ $8`、armでは`MOVW`、`SUB $4`）

この変更は、`g0`スタックに切り替える際に、`mstart`関数のアドレスをスタックに偽の戻りアドレスとしてプッシュすることで、スタックトレースが`mstart`で停止するように見せかけるためのものです。

**`src/pkg/runtime/traceback.go` ファイルの変更点:**

このファイルでは、スタックトレースのトップと見なされる関数を定義している部分が変更されています。

変更前:
```go
var (
    mstartPC    = funcPC(mstart)
    newprocPC   = funcPC(newproc)
    newstackPC  = funcPC(newstack)
    onMPC       = funcPC(onM) // onMがトップと見なされていた
    rt0_goPC    = funcPC(rt0_go)
    sigpanicPC  = funcPC(sigpanic)
)

func topofstack(f *_func) bool {
    return pc == goexitPC ||
        pc == mstartPC ||
        pc == mcallPC ||
        pc == onMPC || // ここでonMがトップと判定されていた
        pc == morestackPC ||
        pc == lessstackPC ||
        pc == rt0_goPC ||
        pc == sigpanicPC ||
        pc == newprocPC ||
        pc == newstackPC
}
```

変更後:
```go
var (
    mstartPC    = funcPC(mstart)
    newprocPC   = funcPC(newproc)
    newstackPC  = funcPC(newstack)
    // onMPC       = funcPC(onM) // onMの定義が削除された
    rt0_goPC    = funcPC(rt0_go)
    sigpanicPC  = funcPC(sigpanic)
)

func topofstack(f *_func) bool {
    return pc == goexitPC ||
        pc == mstartPC ||
        pc == mcallPC ||
        // pc == onMPC || // onMのチェックが削除された
        pc == morestackPC ||
        pc == lessstackPC ||
        pc == rt0_goPC ||
        pc == sigpanicPC ||
        pc == newprocPC ||
        pc == newstackPC
}
```

`onMPC`変数の定義と、`topofstack`関数内の`onMPC`によるチェックが削除されています。これにより、スタックトレースのロジックは`onM`をスタックのトップ関数として自動的に停止させなくなります。

## コアとなるコードの解説

このコミットの変更は、Goランタイムのスタックトレース生成における正確性とデバッグ可能性を大幅に向上させます。

1.  **`traceback.go`の変更**:
    `traceback.go`から`onM`をスタックのトップ関数として扱うロジックが削除されたことで、スタックトレースはデフォルトで`onM`を通過して、その呼び出し元を辿るようになります。これは、`g0`スタックや`gsignal`スタックから`onM`が呼び出されたケース（ケース1と2）において、完全なスタックトレースを得るために不可欠です。これにより、クラッシュ発生時に`onM`を呼び出した実際のランタイムコードやシグナルハンドラのコンテキストが明らかになり、デバッグが容易になります。

2.  **アセンブリファイルの変更 (`asm_*.s`)**:
    `oncurg`セクションにおけるアセンブリコードの変更は、`curg`スタックから`g0`スタックに切り替える特殊なケース（ケース3）に対応するためのものです。
    *   `SUBL $4, BX` (または`SUBQ $8`, `SUB $4`): これはスタックポインタ（`BX`レジスタに格納されている）を、戻りアドレスを格納するのに十分なバイト数だけ減らしています。これにより、スタック上に新しいエントリのためのスペースが確保されます。
    *   `MOVL $runtime·mstart(SB), DX` と `MOVL DX, 0(BX)`: ここで、`runtime·mstart`関数のアドレスがスタックの新しいトップにプッシュされます。これは、`onM`が`mstart`から呼び出されたかのように見せかけるための「偽の戻りアドレス」です。
    *   `MOVL BX, SP`: 更新されたスタックポインタを実際の`SP`レジスタに設定します。

    このアセンブリレベルの操作により、`curg`スタックから`g0`スタックに切り替わった後、スタックトレースが生成される際には、`onM`の呼び出し元が`mstart`であると認識されます。`mstart`はランタイムによってスタックのトップ関数として認識されているため、結果として、このケースでは`onM`より上位の`curg`スタックのトレースは表示されず、以前と同様の振る舞いが維持されます。

この二重のアプローチにより、Goランタイムは、`onM`の呼び出しコンテキストに応じて、スタックトレースの正確性と有用性を最適化しています。デバッグ情報の改善は、ランタイムの安定性と開発者の生産性にとって非常に重要です。

# [インデックス 19961] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、PowerPC 64-bit (ppc64) アーキテクチャ向けのリンカ機能 (`9l`) を、共通のリンカライブラリである `liblink` へ統合する大規模なリファクタリングを目的としています。具体的には、`9l` のアセンブラおよびリンカのコア機能が `liblink` 内の `asm9.c`、`list9.c`、`obj9.c` ファイルに移植され、共通のリンカコンテキスト (`Link *ctxt`) を使用するように変更されています。これにより、Goのツールチェインにおけるアーキテクチャ固有のコードの重複を減らし、保守性を向上させることが期待されます。

## 変更の背景

Go言語の初期のツールチェインは、Plan 9オペレーティングシステムから派生した設計思想に基づいていました。各アーキテクチャ（例: x86、ARM、PowerPC）には、それぞれ独立したアセンブラ (`5a`, `6a`, `8a`, `9a` など) とリンカ (`5l`, `6l`, `8l`, `9l` など) が存在していました。これは、各アーキテクチャの特性に特化した最適化や処理を容易にする一方で、共通のリンカロジックが各リンカで重複して実装されるという問題を引き起こしていました。

このコミットが行われた2014年頃は、Go言語がより多くのアーキテクチャをサポートし、ツールチェインの保守性と拡張性を向上させる必要性が高まっていました。特に、PowerPC 64-bit (ppc64) アーキテクチャは、エンタープライズシステムや高性能計算分野で利用されており、Goのサポートを強化する上で重要なターゲットでした。

`liblink` は、Goのリンカの共通部分を抽象化し、各アーキテクチャ固有の処理をプラグインのように組み込むためのライブラリとして設計されました。このコミットの目的は、`9l` リンカのPowerPC 64-bit固有のコード生成、命令レイアウト、リロケーション処理などを `liblink` のフレームワークに適合させ、共通化されたインターフェースを通じて利用できるようにすることでした。これにより、コードの重複を排除し、将来的な機能追加やバグ修正が容易になるというメリットがあります。

## 前提知識の解説

### Go Toolchainの概要

Go言語のビルドプロセスは、主に以下のツールによって構成されます。

*   **`go tool compile`**: Goのソースコードをアセンブリコード（Plan 9形式）にコンパイルします。
*   **`go tool as`**: アセンブリコードをオブジェクトファイルにアセンブルします。
*   **`go tool link`**: オブジェクトファイルをリンクして実行可能ファイルを生成します。

`liblink` は、この `go tool link` の中核をなすライブラリであり、シンボル解決、リロケーション処理、コード生成、実行可能ファイルフォーマットの出力など、リンカの主要な機能を提供します。

### Plan 9 Assemblers/Linkers (9l, 5l, 6l, 8l)

Go言語のツールチェインは、Bell LabsのPlan 9オペレーティングシステムのツールチェインに強く影響を受けています。Plan 9では、各CPUアーキテクチャに特化したアセンブラとリンカが提供されており、Goもその命名規則を踏襲していました。

*   **`5l`**: ARMアーキテクチャ向けリンカ
*   **`6l`**: AMD64 (x86-64) アーキテクチャ向けリンカ
*   **`8l`**: 386 (x86-32) アーキテクチャ向けリンカ
*   **`9l`**: PowerPC 64-bit (ppc64) アーキテクチャ向けリンカ

これらのリンカは、それぞれがアーキテクチャ固有の命令セット、レジスタ、アドレッシングモード、リロケーションタイプなどを処理するロジックを持っていました。このコミットは、`9l` のこれらの固有ロジックを `liblink` に取り込む作業です。

### PowerPC 64-bit (ppc64) アーキテクチャ

PowerPCは、IBMが開発したRISC (Reduced Instruction Set Computer) アーキテクチャです。ppc64は64ビット版であり、以下の特徴がリンカの処理に影響を与えます。

*   **固定長命令**: 全ての命令が4バイト（32ビット）固定長です。
*   **ロード/ストアアーキテクチャ**: メモリ操作はロード命令とストア命令に限定され、演算はレジスタ間で行われます。
*   **複雑なアドレッシングモード**: ベースレジスタとオフセットを組み合わせたアドレッシングが一般的です。特に、32ビットの即値やアドレスを扱う際に、複数の命令（例: `addis` と `addi`）を組み合わせて64ビットレジスタにロードするシーケンスが必要になることがあります。
*   **リロケーションの複雑さ**: 実行時にアドレスが確定するシンボル（関数やグローバル変数）への参照は、リンカによって適切なアドレスに修正される必要があります。PowerPCでは、特に大きなオフセットを持つアドレスや関数呼び出しに対して、複数の命令を修正する必要があるため、特定のリロケーションタイプが定義されています。

### リロケーション

リロケーションとは、コンパイル時にアドレスが確定しないシンボル（関数、グローバル変数など）への参照を、リンカが最終的な実行可能ファイル内で正しいメモリアドレスに修正するプロセスです。オブジェクトファイルには、未解決の参照と、それらを解決するために必要な情報（リロケーションエントリ）が含まれています。リンカはこれらのエントリを読み取り、シンボルの最終アドレスに基づいて命令内のオフセットやアドレス値を書き換えます。

PowerPCでは、例えば32ビットの即値フィールドに64ビットアドレスをロードするために、上位16ビットをロードする `addis` (Add Immediate Shifted) 命令と、下位16ビットをロードする `addi` (Add Immediate) 命令を組み合わせる場合があります。このような場合、リロケーションはこれら2つの命令の両方を修正する必要があります。

### `include/link.h`

このヘッダファイルは、Goリンカの内部で使用される共通のデータ構造や定数を定義しています。`Prog` (プログラム命令を表す構造体) や `Addr` (アドレスを表す構造体) など、リンカが扱う基本的な要素がここで定義されています。アーキテクチャ固有のリンカを `liblink` に統合する際、これらの共通構造体にアーキテクチャ固有のフィールドを追加したり、新しいリロケーションタイプを定義したりする必要があります。

### `src/liblink/asm9.c`, `src/liblink/list9.c`, `src/liblink/obj9.c`

これらのファイルは、元々 `9l` リンカのPowerPC 64-bit固有の機能を提供していました。

*   **`asm9.c`**: PowerPC 64-bit命令のバイナリコード生成ロジックを含みます。`span` 関数（命令のレイアウトとPCアドレスの割り当て）や `asmout` 関数（実際の機械語の出力）などが含まれます。
*   **`list9.c`**: PowerPC 64-bitのアセンブリ命令やアドレスを人間が読める形式で表示するためのフォーマットロジックを含みます。デバッグやリスト出力に利用されます。
*   **`obj9.c`**: PowerPC 64-bitのオブジェクトファイル形式（Plan 9 `a.out` 形式）の読み書きやシンボルテーブルの処理など、オブジェクトファイルレベルの操作を扱います。

このコミットでは、これらのファイル内の関数が `liblink` の共通コンテキスト (`Link *ctxt`) を受け取るように変更され、`liblink` の一部として機能するように再構築されています。

## 技術的詳細

このコミットの主要な変更点は、PowerPC 64-bitアーキテクチャ固有のリンカロジックを `liblink` の共通フレームワークに統合することです。

### `include/link.h` の変更

*   **`Addr` 構造体の拡張**:
    ```diff
    -	int8	reg;	// for 5l
    -	int8	name; // for 5l
    -	int8	class;	// for 5l
    +	int8	reg;	// for 5l, 9l
    +	int8	name; // for 5l, 9l
    +	int8	class;	// for 5l, 9l
    ```
    `reg`, `name`, `class` フィールドが `9l` でも使用されることを明示しています。これは、アドレスのタイプ分類やレジスタ指定が共通化されることを示唆します。
*   **`Prog` 構造体の拡張**:
    ```diff
    -	uchar	reg; // arm only
    +	uchar	reg; // arm, power64 only
    	uchar	scond; // arm only
    	Addr	from;
    +	Addr	from3; // power64 only, fma and rlwm
    	Addr	to;
    	
    	// ...
    	
    -	uchar	mark;
    +	uint16	mark;
    +	uint16	optab;	// 5l, 9l
    	uchar	back;	// 6l, 8l
    	uchar	ft;	/* 6l, 8l oclass cache */
    	uchar	tt;	// 6l, 8l
    -	uint16	optab;	// 5l
    	uchar	isize;	// 6l, 8l
    ```
    `reg` フィールドが `power64` でも使用されるようになり、`from3` という新しい `Addr` フィールドが追加されています。これは、PowerPCの特定の命令（例: FMA (Fused Multiply-Add) や `rlwm` (Rotate Left Word Masked)）が3つのオペランドを持つ場合に対応するためです。`mark` と `optab` の型が変更され、`optab` が `9l` でも使用されることが明示されています。
*   **新しいリロケーションタイプの追加**:
    ```diff
    enum
    {
    	R_ADDR = 1,
    +	R_ADDRPOWER, // relocation for loading 31-bit address using addis and addi/ld/st for Power
    	R_SIZE,
    	R_CALL, // relocation for direct PC-relative call
    	R_CALLARM, // relocation for ARM direct call
    	R_CALLIND, // marker for indirect call (no actual relocating necessary)
    +	R_CALLPOWER, // relocation for Power direct call
    	R_CONST,
    	R_PCREL,
    	R_TLS,
    ```
    `R_ADDRPOWER` と `R_CALLPOWER` というPowerPC固有のリロケーションタイプが追加されました。
    *   `R_ADDRPOWER`: `addis` と `addi`/`ld`/`st` 命令を組み合わせて31ビットアドレスをロードする際のリロケーションを扱います。これは、PowerPCが32ビットの即値しか扱えないため、64ビットアドレスをレジスタにロードする際に2つの命令が必要になることに対応します。
    *   `R_CALLPOWER`: PowerPCの直接呼び出し（ブランチ命令）のリロケーションを扱います。
*   **新しい関数のプロトタイプ宣言**: `span9`, `listinit9` など、`9l` 固有の処理を行う関数のプロトタイプが追加されています。
*   **`LinkArch` 構造体の追加**: `linkpower64` と `linkpower64le` (little-endian) という `LinkArch` 構造体の外部宣言が追加され、PowerPC 64-bitアーキテクチャのリンカ設定が `liblink` に統合されることを示しています。

### `src/liblink/asm9.c` の変更

このファイルは、PowerPC 64-bit命令のコード生成の核心部分です。

*   **`Link *ctxt` の導入**: ほとんどの関数が `Link *ctxt` ポインタを引数として受け取るように変更されています。これは、リンカのグローバルな状態（現在のシンボル、診断メッセージの出力先、デバッグフラグなど）を `ctxt` 構造体を通じて明示的に渡すことで、コードのモジュール化と再入可能性を高めるための重要な変更です。これにより、`asm9.c` の関数が `liblink` の共通フレームワーク内でより安全かつ柔軟に利用できるようになります。
*   **`Optab` 構造体と命令テーブルの更新**:
    *   `Optab` 構造体が定義され、各命令のアセンブリ命令 (`as`)、オペランドのクラス (`a1`〜`a4`)、命令のタイプ (`type`)、サイズ (`size`)、パラメータ (`param`) を保持します。
    *   `optab` 配列に、`ASYSCALL` の新しい形式（レジスタや即値を伴うもの）、`ADWORD` の新しい形式（データ定数を伴うもの）、`ADUFFZERO`, `ADUFFCOPY`, `AUNDEF`, `AUSEFIELD`, `APCDATA`, `AFUNCDATA` といった特殊な命令や擬似命令が追加されています。これらは、Goランタイムの内部処理や最適化、スタックフレーム情報の記録などに利用されます。
*   **`span9` 関数の導入**: 元々 `span` という名前だった関数が `span9` にリネームされ、`Link *ctxt` を引数として受け取るようになりました。この関数は、Goのプログラム命令 (`Prog` 構造体) を走査し、各命令のPCアドレスを割り当て、命令のサイズを計算します。また、ブランチ命令のターゲットアドレスが遠すぎる場合に、追加のブランチ命令を挿入してジャンプ範囲を調整するロジック（`bflag` を使用したループ）も含まれています。
*   **`asmout` 関数の大幅な変更**:
    *   `asmout` 関数も `Link *ctxt` を引数として受け取るようになりました。
    *   この関数は、`Prog` 構造体で表されるGoの命令を、実際のPowerPC 64-bitの機械語命令に変換し、`out` 配列に書き込みます。
    *   各命令タイプ (`o->type`) に応じて、適切なPowerPC命令のオペコードとオペランドを計算し、生成します。
    *   **リロケーション処理の強化**:
        *   `addaddrreloc` という新しいヘルパー関数が導入され、`R_ADDRPOWER` リロケーションを生成します。これは、`addis` と `addi` (または `ld`/`st`) の2つの命令を修正する必要があるPowerPC固有のアドレスロードに対応します。
        *   `R_CALLPOWER` リロケーションも `asmout` 内で処理され、ブランチ命令のターゲットアドレスを修正します。
        *   以前の `dlm` (dynamic linking) に関連する `reloc` 関数呼び出しの多くがコメントアウトまたは削除されており、静的リンクに焦点を当てた変更か、動的リンクの処理が別の場所に移されたことを示唆しています。
*   **ヘルパー関数の変更**: `aclass`, `oplook`, `oprrr`, `opirr`, `opload`, `opstore`, `oploadx`, `opstorex`, `vregoff`, `regoff`, `getmask`, `maskgen`, `getmask64`, `maskgen64` など、多くのヘルパー関数が `static` になり、`Link *ctxt` を引数として受け取るように変更されています。これにより、これらの関数がリンカのコンテキスト内で動作し、グローバル変数への依存を減らすことができます。
*   **診断メッセージの変更**: `diag` 関数呼び出しが `ctxt->diag` に変更され、診断メッセージの出力も `Link *ctxt` を通じて行われるようになりました。

### `src/liblink/list9.c` の変更

*   **`listinit9` 関数の導入**: `listinit` が `listinit9` にリネームされ、`fmtinstall` を使用してPowerPC 64-bit固有の命令やアドレスのフォーマット関数を登録します。
*   **新しいフォーマット指定子の追加**: `%^` (C_* クラス用) や `%$` (文字列定数アドレス用)、`%M` (アドレス用) といった内部使用のフォーマット指定子が追加されています。

### `src/liblink/obj9.c` の変更 (コミット差分には含まれていないが、関連する変更)

このコミットの性質上、`obj9.c` も同様に `Link *ctxt` を受け取るように変更され、オブジェクトファイルの読み込み、シンボルテーブルの処理、セクションの解析など、PowerPC 64-bit固有のオブジェクトファイル形式に関するロジックが `liblink` のフレームワークに統合されたと考えられます。

### 変更の意義

このコミットは、Goのツールチェインが特定のアーキテクチャに特化したコードから、より汎用的な `liblink` ライブラリへと移行する重要なステップを示しています。

*   **コードの再利用と保守性**: `9l` のコアロジックを `liblink` に統合することで、PowerPC 64-bitリンカのコードが他のアーキテクチャのリンカと共通の基盤で管理されるようになります。これにより、コードの重複が減り、バグ修正や機能追加がより効率的に行えるようになります。
*   **アーキテクチャ抽象化の向上**: `Link *ctxt` の導入は、リンカの内部状態を明示的に管理し、アーキテクチャ固有の処理を共通のインターフェースを通じて呼び出すことを可能にします。これは、将来的に新しいアーキテクチャのサポートを追加する際の柔軟性を高めます。
*   **PowerPC 64-bitサポートの成熟**: このリファクタリングは、PowerPC 64-bitアーキテクチャにおけるGoのサポートがより堅牢で、ツールチェインの他の部分と密接に統合されることを意味します。特に、複雑なリロケーションタイプの追加は、PowerPCの命令セットの特性に合わせた正確なコード生成を保証します。

## コアとなるコードの解説

### `span9` 関数

`span9` 関数は、Goのリンカにおける「命令のレイアウト」を担当します。これは、アセンブリ命令のリストを走査し、各命令が最終的な実行可能ファイル内で占めるバイト数を計算し、それぞれの命令にPC (Program Counter) アドレスを割り当てる役割を担います。

変更点としては、`span9` が `Link *ctxt` を引数として受け取るようになったことで、リンカの現在のコンテキスト（例えば、現在のシンボル `cursym` やデバッグフラグ `ctxt->debugvlog` など）にアクセスできるようになりました。これにより、関数がより自己完結的になり、グローバル変数への依存が減ります。

また、`span9` は、ブランチ命令のターゲットが現在の命令から遠すぎる場合に、追加のジャンプ命令（トランポリン）を挿入して、ブランチの範囲制限を回避するロジックを含んでいます。これは、PowerPCのブランチ命令が相対アドレスの範囲に制限があるため、大きなプログラムでは必要となる処理です。

### `asmout` 関数

`asmout` 関数は、`span9` によってPCアドレスが割り当てられた各 `Prog` 命令を、実際のPowerPC 64-bitの機械語命令（バイナリコード）に変換して出力する役割を担います。この関数は、`Optab` テーブルを参照して命令のタイプとオペランドのクラスを判断し、それに基づいて適切なPowerPC命令のビットパターンを生成します。

このコミットにおける `asmout` の最も重要な変更は、PowerPC 64-bit固有のリロケーション処理の強化です。特に、`R_ADDRPOWER` リロケーションを処理するために `addaddrreloc` ヘルパー関数が導入されました。これは、64ビットアドレスをレジスタにロードするために `addis` と `addi` (または `ld`/`st`) の2つの命令が必要となるPowerPCの特性に対応するものです。`addaddrreloc` は、これらの2つの命令のオペランドを修正するためのリロケーションエントリを生成します。

例えば、`case 19` (`mov $lcon,r`) や `case 74`, `case 75`, `case 76` (リロケーションを伴うロード/ストア) の処理では、`addis` と `addi` を組み合わせてアドレスをロードし、その際に `addaddrreloc` を呼び出してリロケーション情報を記録しています。これにより、リンカは最終的なリンク時に、これらの命令の即値フィールドを正しいアドレス値で埋めることができます。

### `aclass`, `oplook`, `oprrr`, `opirr`, `opload`, `opstore`, `oploadx`, `opstorex` 関数群

これらのヘルパー関数は、`asmout` 関数が機械語を生成する際に利用されます。

*   **`aclass(Link *ctxt, Addr *a)`**: `Addr` 構造体で表されるオペランドの「クラス」を決定します。このクラスは、オペランドがレジスタ、即値、メモリ参照（オフセット付き）、シンボル参照など、どのタイプに属するかを示します。`Link *ctxt` を受け取ることで、リンカの現在の状態（例: `ctxt->autosize`、`ctxt->instoffset`）に基づいて正確なクラスを判断できるようになりました。
*   **`oplook(Link *ctxt, Prog *p)`**: `Prog` 命令とオペランドのクラスに基づいて、対応する `Optab` エントリ（命令の形式とサイズ情報）を検索します。
*   **`oprrr`, `opirr`, `opload`, `opstore`, `oploadx`, `opstorex`**: これらは、PowerPCの命令フォーマットに基づいて、特定の命令（レジスタ-レジスタ演算、即値-レジスタ演算、ロード、ストア、インデックス付きロード、インデックス付きストアなど）のオペコードや機能コードを返す関数です。これらも `Link *ctxt` を受け取るようになり、よりコンテキストに依存した正確なオペコード選択が可能になりました。

これらの関数が `Link *ctxt` を引数として受け取るように変更されたことは、Goリンカの内部設計が、グローバル変数に依存する古いPlan 9スタイルから、より現代的な「コンテキストを明示的に渡す」スタイルへと移行していることを示しています。これにより、コードの可読性、テスト容易性、および並行処理の安全性が向上します。

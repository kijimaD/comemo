## 変更の背景

このコミットは、Goコンパイラがラベルとパッケージ名を誤って解釈するバグを修正するために行われました。具体的には、Goプログラム内でインポートされたパッケージと同じ名前のラベルを定義した場合、コンパイラがそのラベルを正しく認識できず、構文エラーを報告するか、意図しない動作を引き起こす可能性がありました。

コミットメッセージにある「partially resolving symbols too early (シンボルを部分的に早期解決しすぎていることによる、もう一つの（歴史的な）アーティファクト)」という記述は、コンパイラのパーシング段階で、識別子（この場合は`math`）がラベルとして使われるべきか、それともパッケージ名として使われるべきかを判断する際に、誤った優先順位付けや早期の型解決が行われていたことを示唆しています。

この問題は、Go言語のIssue #13539として報告されており、このコミットはその問題を解決することを目的としています。

## 前提知識の解説

このコミットの理解には、以下のGo言語およびGoコンパイラの内部構造に関する知識が役立ちます。

1.  **Goコンパイラの`cmd/compile/internal/gc`パッケージ**:
    *   `cmd/compile`はGo言語の公式コンパイラです。その中でも`internal/gc`は、コンパイラの主要なロジック（字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成など）を担う部分です。
    *   `parser.go`ファイルは、ソースコードを解析して抽象構文木（AST）を構築する構文解析器（パーサー）の一部です。

2.  **Goにおけるラベル（`label:`）**:
    *   Go言語では、`for`、`switch`、`select`ステートメントにラベルを付けることができます。
    *   `break label`や`continue label`構文を使用することで、ネストされたループやスイッチから特定のラベルが付いたステートメントを脱出したり、次のイテレーションに進んだりすることができます。
    *   例:
        ```go
        func main() {
        outerLoop:
            for i := 0; i < 5; i++ {
                for j := 0; j < 5; j++ {
                    if i*j > 6 {
                        break outerLoop // outerLoopを抜ける
                    }
                    fmt.Println(i, j)
                }
            }
        }
        ```

3.  **Goのパッケージインポートと名前解決**:
    *   Goでは`import "packageName"`構文で外部パッケージをインポートします。インポートされたパッケージは、そのパッケージ名（例: `math.Sin`の`math`）を使ってアクセスされます。
    *   コンパイラは、ソースコード中の識別子が変数名、関数名、型名、パッケージ名、あるいはラベル名など、どのエンティティを指すのかを解決（名前解決）する必要があります。

4.  **Goコンパイラ内部のノードタイプ (`ONAME`, `ONONAME`, `OTYPE`, `OPACK`)**:
    *   Goコンパイラは、ソースコードを解析する際に、内部的に抽象構文木（AST）を構築します。このASTの各ノードは、コードの異なる要素を表すために特定の「オペレーションコード」（`Op`）を持ちます。
    *   **`ONAME`**: 一般的な名前付きエンティティ（変数、関数、型など）を表します。
    *   **`ONONAME`**: 名前がまだ解決されていない、または名前を持たない内部的なエンティティを表す可能性があります。
    *   **`OTYPE`**: 型を表します。
    *   **`OPACK`**: パッケージを表します。例えば、`import "math"`とすると、`math`という識別子は内部的に`OPACK`ノードとして扱われることがあります。

## 技術的詳細

このバグは、Goコンパイラのパーサーが`simple_stmt`関数内でラベルを処理する際に発生していました。`simple_stmt`関数は、Goの文法における単純なステートメント（例: `var x int`、`x = 1`、`label:`など）を解析する役割を担っています。

問題の核心は、パーサーが`lhs`（左辺）のオペレーションコードをチェックして、それがラベルとして有効な名前であるかどうかを判断するロジックにありました。以前のコードでは、`lhs.Op`が`ONAME`（一般的な名前）、`ONONAME`（未解決の名前）、または`OTYPE`（型名）のいずれかである場合にのみ、それをラベルとして認識していました。

しかし、もしプログラムが`import "math"`のようにパッケージをインポートし、かつ`math:`のようにそのパッケージ名と同じ名前のラベルを定義した場合、パーサーは`math`という識別子を`OPACK`ノードとして早期に解釈してしまうことがありました。この`OPACK`ノードは、以前のラベル認識ロジックの`if lhs.Op == ONAME || lhs.Op == ONONAME || lhs.Op == OTYPE`という条件に合致しなかったため、パーサーは`math:`を有効なラベルとして扱えず、構文エラーを報告するか、あるいは`math`パッケージが使用されていないという誤った警告（`imported and not used`）を報告しないという問題を引き起こしていました。

この「シンボルを部分的に早期解決しすぎている」という問題は、コンパイラの異なるフェーズ（字句解析、構文解析、名前解決、型チェックなど）がどのように連携し、どの段階でどの情報を利用可能にするかという設計上の課題に起因します。このケースでは、構文解析の段階で、識別子がラベルとして使われる可能性を考慮する前に、それがパッケージ名であるという情報が強すぎたために発生しました。

## コアとなるコードの解説

変更の核心は、`lhs.Op`のチェック方法が`if`文から`switch`文に変わり、`OPACK`が有効なラベル名として認識されるようになった点です。

*   **変更前**:
    ```go
    if lhs.Op == ONAME || lhs.Op == ONONAME || lhs.Op == OTYPE {
        lhs = newname(lhs.Sym)
    } else {
        p.syntax_error("expecting semicolon or newline or }")
        // ...
    }
    ```
    このコードでは、`lhs`（左辺、ここではラベル名として解釈される可能性のある識別子）のオペレーションコードが`ONAME`、`ONONAME`、`OTYPE`のいずれかである場合にのみ、それを新しい名前ノード（`newname(lhs.Sym)`）に変換していました。`OPACK`であった場合、`else`ブロックに入り、構文エラーが報告されていました。

*   **変更後**:
    ```go
    switch lhs.Op {
    case ONAME, ONONAME, OTYPE, OPACK:
        lhs = newname(lhs.Sym)
    default:
        p.syntax_error("expecting semicolon or newline or }")
        // ...
    }
    ```
    新しいコードでは、`switch`文を使用して`lhs.Op`をチェックしています。重要な変更点は、`case`リストに`OPACK`が追加されたことです。これにより、`lhs`が`OPACK`ノードとして識別された場合でも、それがラベル名として有効であると判断され、`newname(lhs.Sym)`によって新しい名前ノードに変換されます。
    `newname(lhs.Sym)`は、既存のシンボル（`lhs.Sym`）から新しい名前ノードを作成する関数です。これにより、`math`という識別子がパッケージ名として早期に認識されていても、ラベルとして使用される文脈では、そのシンボル情報を使って適切なラベルノードに「再解釈」されるようになります。

この修正により、コンパイラは`import "math"`と`math:`ラベルが共存するコードを正しく解析できるようになります。`math`パッケージが実際にコード内で使用されていない場合は、`imported and not used`という警告が正しく発行されるようになります。

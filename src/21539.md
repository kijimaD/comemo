## 元コミット内容

Goランタイムにおいて、`GODEBUG=crash`が設定されている場合、LinuxおよびOS X環境で全てのGoスレッドのスタックトレースをログに出力するように変更されました。

通常、パニックやスローが発生した場合、現在のスレッドと一時停止中のゴルーチンのスレッドスタックのみが表示されます。他のスレッドで実行中のゴルーチンや、システムスタック上で実行中の他のスレッドは不透明でした。この変更により、`GODEBUG=crash`が設定されている場合に、`SIGQUIT`シグナルを全てのGoスレッドにリレーすることで、この制限が解消されます。

もしこの機能が十分に機能するようであれば、将来的にはアイドル状態のM（OSスレッド）を省略しつつ、この`SIGQUIT`リレーメカニズムを標準のパニック/スロー時の動作の一部とすることも検討されています。

## 変更の背景

Goプログラムがクラッシュする際、デバッグの目的でスタックトレースが出力されます。しかし、従来のGoランタイムでは、クラッシュを引き起こしたゴルーチンが実行されていたOSスレッド（M）のスタックトレースと、現在一時停止している他のゴルーチンのスタックトレースしか表示されませんでした。

これは、以下のような状況で問題となります。

1.  **デッドロックやハングアップの診断**: プログラムがデッドロック状態に陥ったり、応答しなくなったりした場合、どのゴルーチンがどのOSスレッドで実行されており、どのような状態にあるのかを包括的に把握することが困難でした。特に、Cgo呼び出しなどGoランタイムの管理外で実行されている可能性のあるOSスレッドの状態は全く見えませんでした。
2.  **複雑な並行処理のデバッグ**: 複数のゴルーチンが同時に動作し、それぞれが異なるOSスレッドにマッピングされているような複雑な並行処理において、特定のクラッシュがどのスレッドの状態と関連しているのかを特定するのが難しくなります。
3.  **`GODEBUG=crash`の目的の強化**: `GODEBUG=crash`は、Goプログラムがクラッシュした際に詳細なデバッグ情報を出力するための環境変数です。しかし、全てのOSスレッドの状態が把握できないと、そのデバッグ情報の完全性が損なわれていました。

このコミットは、これらの課題に対処し、クラッシュ時のデバッグ情報をより包括的にすることで、Goプログラムのデバッグ効率を向上させることを目的としています。特に、`SIGQUIT`シグナルをOSスレッド間でリレーするというアプローチは、各スレッドが自身のスタックトレースを安全にダンプできるようにするための巧妙なメカニズムです。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念とOSのシグナルに関する知識が不可欠です。

### Goランタイムのスケジューラ (Goroutine, M, P)

Go言語は、独自の軽量な並行処理モデルである「ゴルーチン（Goroutine）」を採用しています。ゴルーチンはOSスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムには、これらのゴルーチンをOSスレッドにマッピングし、実行を管理するスケジューラが組み込まれています。

-   **G (Goroutine)**: Go言語における軽量な実行単位です。関数呼び出しの前に`go`キーワードを付けることで生成されます。
-   **M (Machine)**: OSスレッドを表します。Goランタイムは、ゴルーチンを実行するためにOSスレッドを使用します。Mは、Goコードを実行するだけでなく、Cgo呼び出しやシステムコールなど、OSレベルの処理も担当します。
-   **P (Processor)**: 論理プロセッサを表します。PはMとGの間のコンテキストとして機能し、MがGを実行するために必要なリソース（スケジューラのキューなど）を提供します。通常、Pの数はCPUのコア数に設定されます。

Goスケジューラは、GをPに割り当て、PがMに割り当てられることで、GがM上で実行されます。Mは、Goコードを実行していない間（例えば、ネットワークI/Oでブロックされている間）は、Pを解放して他のMがPを使用できるようにすることができます。

### シグナル

シグナルは、Unix系OSにおいてプロセスに非同期的にイベントを通知するメカニズムです。特定のイベント（例: 割り込み、エラー、終了要求）が発生すると、カーネルはプロセスにシグナルを送信します。プロセスは、シグナルを受信すると、そのシグナルに対応するシグナルハンドラを実行したり、デフォルトの動作（プロセス終了など）を実行したりします。

このコミットで関連するシグナルは以下の通りです。

-   **`SIGQUIT` (Signal Quit)**: プロセスに終了を要求するシグナルです。通常、コアダンプを生成してプロセスを終了させます。キーボードからは`Ctrl+\`で送信されることが多いです。このコミットでは、このシグナルをスタックトレース収集のトリガーとして利用しています。
-   **`SIGSEGV` (Signal Segmentation Violation)**: プロセスが不正なメモリアクセスを行った場合に発生するシグナルです。通常、プロセスを終了させ、コアダンプを生成します。Goプログラムでは、パニックの一般的な原因の一つです。
-   **`SIGPROF` (Signal Profiling Timer Expired)**: プロファイリングタイマーが期限切れになった場合に発生するシグナルです。CPUプロファイリングなどで使用されます。

### `GODEBUG=crash`環境変数

`GODEBUG`環境変数は、Goランタイムのデバッグオプションを設定するために使用されます。`GODEBUG=crash=1`のように設定すると、Goプログラムがクラッシュした際に、通常よりも詳細なデバッグ情報を出力するようになります。このコミットは、この`crash`オプションの機能を拡張するものです。

### スタックトレース

スタックトレース（またはバックトレース）は、プログラムの実行中に特定の時点（通常はエラーやクラッシュ発生時）で、現在実行中の関数から呼び出し元の関数へと遡って、関数呼び出しの履歴をリストアップしたものです。これにより、プログラムがどのようにしてその状態に至ったのかを理解し、問題の原因を特定するのに役立ちます。Goでは、ゴルーチンごとにスタックトレースが生成されます。

## 技術的詳細

このコミットの核心は、`GODEBUG=crash`が設定された状態でパニックが発生した際に、Goプロセス内の**全てのOSスレッド（M）**のスタックトレースを収集するメカニズムにあります。これは、`SIGQUIT`シグナルをOSスレッド間でリレーすることで実現されます。

### `SIGQUIT`リレーメカニズム

1.  **最初のパニック/クラッシュ**: Goプログラムでパニックやクラッシュ（例: `SIGSEGV`）が発生すると、そのシグナルを受信したOSスレッド（M）の`sighandler`関数が呼び出されます。
2.  **`GODEBUG=crash`のチェック**: `sighandler`内で`GODEBUG=crash`が有効かどうかがチェックされます。有効な場合、`crashing`というグローバル変数がインクリメントされます。
3.  **`SIGQUIT`の送信**: `crashing`変数が`sched.mcount`（Goランタイムが管理するOSスレッドの総数）よりも小さい場合、つまりまだ全てのMがスタックトレースをダンプしていない場合、現在のMは`raiseproc(_SIGQUIT)`を呼び出して、プロセス全体に`SIGQUIT`シグナルを送信します。
4.  **シグナルのリレー**: `SIGQUIT`シグナルは、まだ`SIGQUIT`を受信していない別のMに配送されます。Goランタイムは、既に`SIGQUIT`を受信したMがシグナルマスクを設定して、それ以上シグナルを受信しないようにすることで、シグナルがまだ処理されていないMに確実に届くようにします。
5.  **スタックトレースのダンプ**: `SIGQUIT`を受信した各Mは、自身の`sighandler`を呼び出し、自身のスタックトレースをダンプします。この際、`crashing`変数がインクリメントされ、次のMに`SIGQUIT`がリレーされます。
6.  **最後のM**: 最後のMが`SIGQUIT`を受信し、自身のスタックトレースをダンプすると、`crashing`変数が`sched.mcount`に達するため、それ以上`SIGQUIT`はリレーされず、最終的に`crash()`関数が呼び出されてプロセスが終了します。
7.  **タイムアウトとフォールバック**: 万が一シグナルのリレーがうまくいかなかった場合でも、各Mは`raiseproc(_SIGQUIT)`を呼び出した後に`sleep`（`usleep(5 * 1000 * 1000)`、つまり5秒間）します。これは、リレーが途中で途切れても、最終的には各Mがタイムアウト後に自身で`crash()`を呼び出して終了するためのフォールバックメカニズムです。ただし、通常は最後のMがすぐに`crash()`を呼び出すため、このスリープが完了する前にプロセスは終了します。

### `raiseproc`関数の導入

このメカニズムをサポートするために、`raiseproc`という新しい関数が導入されました。これは、現在のプロセスに指定されたシグナルを送信するためのGoランタイム内部関数です。OS固有の実装（アセンブリコード）が提供されており、`getpid`システムコールで現在のプロセスのPIDを取得し、`kill`システムコールでそのPIDにシグナルを送信します。

### `_SIGQUIT`定数の追加

各OSの`defs_*.go`ファイルに、`_SIGQUIT`という定数が追加され、その値がUnix系OSでは`3`（`SIGQUIT`の標準的な値）に設定されています。WindowsやPlan9など、`SIGQUIT`の概念がないOSではダミーの値（`0`）が設定されています。

## コアとなるコードの変更箇所

### `src/runtime/signal_amd64x.go`

このファイルは、AMD64アーキテクチャにおけるシグナルハンドリングのロジックを定義しています。主要な変更点は以下の通りです。

-   `crashing`変数の追加: `var crashing int32`
    -   これは、現在クラッシュ処理中であり、何個のMが既にスタックトレースをダンプしたかを追跡するためのカウンタです。
-   `sighandler`関数の変更:
    -   `startpanic()`の呼び出しが`if crashing == 0 { startpanic() }`で囲まれました。これにより、最初のパニック時のみ`startpanic()`が実行され、`SIGQUIT`リレーによる後続の`sighandler`呼び出しではスキップされます。
    -   スタックトレース出力時に`PC=`の後に`m=`と`_g_.m.id`（MのID）が出力されるようになりました。
    -   `tracebackothers(gp)`の呼び出しが条件付きになりました。`crashing > 0`かつ現在のMが`curg`（現在のゴルーチン）ではない場合、`tracebackothers`はスキップされ、代わりに`traceback`が直接呼び出されるロジックが追加されました。これは、`SIGQUIT`リレー中に既にダンプされたMのスタックトレースを重複して出力しないようにするためです。
    -   `docrash`がtrueの場合の処理に、`SIGQUIT`リレーのロジックが追加されました。
        ```go
        if docrash {
            // TODO(rsc): Implement raiseproc on other systems
            // and then add to this switch.
            switch GOOS {
            case "darwin", "linux":
                crashing++
                if crashing < sched.mcount {
                    // There are other m's that need to dump their stacks.
                    // Relay SIGQUIT to the next m by sending it to the current process.
                    // All m's that have already received SIGQUIT have signal masks blocking
                    // receipt of any signals, so the SIGQUIT will go to an m that hasn't seen it yet.
                    // When the last m receives the SIGQUIT, it will fall through to the call to
                    // crash below. Just in case the relaying gets botched, each m involved in
                    // the relay sleeps for 5 seconds and then does the crash/exit itself.
                    // In expected operation, the last m has received the SIGQUIT and run
                    // crash/exit and the process is gone, all long before any of the
                    // 5-second sleeps have finished.
                    print("\n-----\n\n")
                    raiseproc(_SIGQUIT)
                    usleep(5 * 1000 * 1000)
                }
            }
            crash()
        }
        ```
        このブロックは、`crashing`カウンタをインクリメントし、まだ全てのMが処理されていない場合に`raiseproc(_SIGQUIT)`を呼び出して`SIGQUIT`をリレーします。また、リレーが失敗した場合のフォールバックとして`usleep`が追加されています。

### `src/runtime/defs_*.go` (例: `src/runtime/defs_nacl_386.go`)

-   `_SIGQUIT = 3` の追加:

### `src/runtime/os_*.go` (例: `src/runtime/os_darwin.go`, `src/runtime/os_linux.go`)

### `src/runtime/sys_*.s` (例: `src/runtime/sys_darwin_386.s`, `src/runtime/sys_linux_amd64.s`)

-   `runtime·raiseproc`関数の実装が追加されました。
    -   これらのアセンブリファイルでは、`getpid`システムコールで現在のプロセスのPIDを取得し、`kill`システムコールでそのPIDに指定されたシグナル（`_SIGQUIT`）を送信するロジックが記述されています。
    -   例 (`sys_linux_amd64.s`):
        ```assembly
        TEXT runtime·raiseproc(SB),NOSPLIT,$0
            MOVL    $39, AX    // syscall - getpid
            SYSCALL
            MOVL    AX, DI    // arg 1 pid
            MOVL    sig+0(FP), SI    // arg 2
            MOVL    $62, AX    // syscall - kill
            SYSCALL
            RET
        ```
        このコードは、Linux AMD64環境で`getpid`（システムコール番号39）と`kill`（システムコール番号62）を呼び出して、プロセスにシグナルを送信します。

## コアとなるコードの解説

### `crashing`変数と`startpanic()`の制御

`signal_amd64x.go`の`crashing`変数は、`GODEBUG=crash`が有効な場合に、クラッシュ処理が進行中であることを示すフラグ兼カウンタとして機能します。
`if crashing == 0 { startpanic() }`という条件は重要です。`startpanic()`は、Goランタイムがパニック状態に入った際に一度だけ実行されるべき初期化処理（例えば、デバッグ情報の準備など）を行います。`SIGQUIT`リレーによって複数のMが`sighandler`を呼び出すことになりますが、`startpanic()`は最初のMによってのみ実行されるように制御されています。これにより、重複した初期化を防ぎ、クラッシュ処理の整合性を保ちます。

### `tracebackothers`の条件付き実行と`traceback`の直接呼び出し

通常のパニック時には、`tracebackothers(gp)`が呼び出され、現在のゴルーチン以外の全てのゴルーチンのスタックトレースが出力されます。しかし、`SIGQUIT`リレーのシナリオでは、各Mが自身のスタックトレースをダンプするため、`tracebackothers`をそのまま使用すると重複が発生する可能性があります。

このコミットでは、`crashing > 0`（つまり、既に`SIGQUIT`リレーが開始されている）かつ、現在のMが`curg`（現在のゴルーチン）ではない場合に、`tracebackothers`をスキップし、代わりに`traceback(^uintptr(0), ^uintptr(0), 0, gp)`を直接呼び出すロジックが追加されています。これは、`SIGQUIT`を受信したMが、自身のスタックトレースのみをダンプし、他のMが既にダンプした可能性のあるゴルーチンのスタックトレースを再度ダンプしないようにするための最適化です。

### `SIGQUIT`リレーのロジック

`sighandler`内の`if docrash { ... }`ブロックが、`SIGQUIT`リレーの核心です。

1.  `crashing++`: 現在のMがスタックトレースをダンプしたことを示すために、`crashing`カウンタをインクリメントします。
2.  `if crashing < sched.mcount`: `crashing`の値がGoランタイムが管理するOSスレッドの総数（`sched.mcount`）よりも小さい場合、まだ全てのMがスタックトレースをダンプしていないことを意味します。
3.  `raiseproc(_SIGQUIT)`: この行が、プロセス全体に`SIGQUIT`シグナルを送信し、まだスタックトレースをダンプしていない別のMにシグナルをリレーする役割を担います。
4.  `usleep(5 * 1000 * 1000)`: これは、リレーが失敗した場合のフォールバックメカニズムです。もし何らかの理由で`SIGQUIT`が他のMに配送されなかったり、最後のMが`crash()`を呼び出す前にプロセスが終了しなかったりした場合でも、このスリープ後に現在のMが最終的に`crash()`を呼び出してプロセスを終了させます。しかし、通常は最後のMがすぐに`crash()`を呼び出すため、このスリープが完了する前にプロセスは終了します。

### `raiseproc`関数の実装

`raiseproc`関数は、GoランタイムがOSスレッドにシグナルを送信するための抽象化レイヤーです。各OS/アーキテクチャのアセンブリファイル（例: `sys_linux_amd64.s`）で具体的に実装されています。

-   **`getpid`システムコール**: まず、`getpid`システムコールを呼び出して、現在のプロセスのプロセスID（PID）を取得します。シグナルはプロセス全体に送信されるため、このPIDが必要です。
-   **`kill`システムコール**: 次に、`kill`システムコールを呼び出します。`kill`システムコールは、指定されたPIDのプロセスに指定されたシグナルを送信します。ここでは、取得したPIDと`_SIGQUIT`シグナルを引数として渡します。

このアセンブリレベルの実装により、GoランタイムはOSの低レベルなシグナルメカニズムを直接操作し、全てのOSスレッドに`SIGQUIT`を効率的に配送することができます。

## 元コミット内容

Goランタイムにおいて、`GODEBUG=crash`が設定されている場合、LinuxおよびOS X環境で全てのGoスレッドのスタックトレースをログに出力するように変更されました。

通常、パニックやスローが発生した場合、現在のスレッドと一時停止中のゴルーチンのスレッドスタックのみが表示されます。他のスレッドで実行中のゴルーチンや、システムスタック上で実行中の他のスレッドは不透明でした。この変更により、`GODEBUG=crash`が設定されている場合に、`SIGQUIT`シグナルを全てのGoスレッドにリレーすることで、この制限が解消されます。

もしこの機能が十分に機能するようであれば、将来的にはアイドル状態のM（OSスレッド）を省略しつつ、この`SIGQUIT`リレーメカニズムを標準のパニック/スロー時の動作の一部とすることも検討されています。

## 変更の背景

Goプログラムがクラッシュする際、デバッグの目的でスタックトレースが出力されます。しかし、従来のGoランタイムでは、クラッシュを引き起こしたゴルーチンが実行されていたOSスレッド（M）のスタックトレースと、現在一時停止している他のゴルーチンのスタックトレースしか表示されませんでした。

これは、以下のような状況で問題となります。

1.  **デッドロックやハングアップの診断**: プログラムがデッドロック状態に陥ったり、応答しなくなったりした場合、どのゴルーチンがどのOSスレッドで実行されており、どのような状態にあるのかを包括的に把握することが困難でした。特に、Cgo呼び出しなどGoランタイムの管理外で実行されている可能性のあるOSスレッドの状態は全く見えませんでした。
2.  **複雑な並行処理のデバッグ**: 複数のゴルーチンが同時に動作し、それぞれが異なるOSスレッドにマッピングされているような複雑な並行処理において、特定のクラッシュがどのスレッドの状態と関連しているのかを特定するのが難しくなります。
3.  **`GODEBUG=crash`の目的の強化**: `GODEBUG=crash`は、Goプログラムがクラッシュした際に詳細なデバッグ情報を出力するための環境変数です。しかし、全てのOSスレッドの状態が把握できないと、そのデバッグ情報の完全性が損なわれていました。

このコミットは、これらの課題に対処し、クラッシュ時のデバッグ情報をより包括的にすることで、Goプログラムのデバッグ効率を向上させることを目的としています。特に、`SIGQUIT`シグナルをOSスレッド間でリレーするというアプローチは、各スレッドが自身のスタックトレースを安全にダンプできるようにするための巧妙なメカニズムです。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念とOSのシグナルに関する知識が不可欠です。

### Goランタイムのスケジューラ (Goroutine, M, P)

Go言語は、独自の軽量な並行処理モデルである「ゴルーチン（Goroutine）」を採用しています。ゴルーチンはOSスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムには、これらのゴルーチンをOSスレッドにマッピングし、実行を管理するスケジューラが組み込まれています。

-   **G (Goroutine)**: Go言語における軽量な実行単位です。関数呼び出しの前に`go`キーワードを付けることで生成されます。
-   **M (Machine)**: OSスレッドを表します。Goランタイムは、ゴルーチンを実行するためにOSスレッドを使用します。Mは、Goコードを実行するだけでなく、Cgo呼び出しやシステムコールなど、OSレベルの処理も担当します。
-   **P (Processor)**: 論理プロセッサを表します。PはMとGの間のコンテキストとして機能し、MがGを実行するために必要なリソース（スケジューラのキューなど）を提供します。通常、Pの数はCPUのコア数に設定されます。

Goスケジューラは、GをPに割り当て、PがMに割り当てられることで、GがM上で実行されます。Mは、Goコードを実行していない間（例えば、ネットワークI/Oでブロックされている間）は、Pを解放して他のMがPを使用できるようにすることができます。

### シグナル

シグナルは、Unix系OSにおいてプロセスに非同期的にイベントを通知するメカニズムです。特定のイベント（例: 割り込み、エラー、終了要求）が発生すると、カーネルはプロセスにシグナルを送信します。プロセスは、シグナルを受信すると、そのシグナルに対応するシグナルハンドラを実行したり、デフォルトの動作（プロセス終了など）を実行したりします。

このコミットで関連するシグナルは以下の通りです。

-   **`SIGQUIT` (Signal Quit)**: プロセスに終了を要求するシグナルです。通常、コアダンプを生成してプロセスを終了させます。キーボードからは`Ctrl+\`で送信されることが多いです。このコミットでは、このシグナルをスタックトレース収集のトリガーとして利用しています。
-   **`SIGSEGV` (Signal Segmentation Violation)**: プロセスが不正なメモリアクセスを行った場合に発生するシグナルです。通常、プロセスを終了させ、コアダンプを生成します。Goプログラムでは、パニックの一般的な原因の一つです。
-   **`SIGPROF` (Signal Profiling Timer Expired)**: プロファイリングタイマーが期限切れになった場合に発生するシグナルです。CPUプロファイリングなどで使用されます。

### `GODEBUG=crash`環境変数

`GODEBUG`環境変数は、Goランタイムのデバッグオプションを設定するために使用されます。`GODEBUG=crash=1`のように設定すると、Goプログラムがクラッシュした際に、通常よりも詳細なデバッグ情報を出力するようになります。このコミットは、この`crash`オプションの機能を拡張するものです。

### スタックトレース

スタックトレース（またはバックトレース）は、プログラムの実行中に特定の時点（通常はエラーやクラッシュ発生時）で、現在実行中の関数から呼び出し元の関数へと遡って、関数呼び出しの履歴をリストアップしたものです。これにより、プログラムがどのようにしてその状態に至ったのかを理解し、問題の原因を特定するのに役立ちます。Goでは、ゴルーチンごとにスタックトレースが生成されます。

## 技術的詳細

このコミットの核心は、`GODEBUG=crash`が設定された状態でパニックが発生した際に、Goプロセス内の**全てのOSスレッド（M）**のスタックトレースを収集するメカニズムにあります。これは、`SIGQUIT`シグナルをOSスレッド間でリレーすることで実現されます。

### `SIGQUIT`リレーメカニズム

1.  **最初のパニック/クラッシュ**: Goプログラムでパニックやクラッシュ（例: `SIGSEGV`）が発生すると、そのシグナルを受信したOSスレッド（M）の`sighandler`関数が呼び出されます。
2.  **`GODEBUG=crash`のチェック**: `sighandler`内で`GODEBUG=crash`が有効かどうかがチェックされます。有効な場合、`crashing`というグローバル変数がインクリメントされます。
3.  **`SIGQUIT`の送信**: `crashing`変数が`sched.mcount`（Goランタイムが管理するOSスレッドの総数）よりも小さい場合、つまりまだ全てのMがスタックトレースをダンプしていない場合、現在のMは`raiseproc(_SIGQUIT)`を呼び出して、プロセス全体に`SIGQUIT`シグナルを送信します。
4.  **シグナルのリレー**: `SIGQUIT`シグナルは、まだ`SIGQUIT`を受信していない別のMに配送されます。Goランタイムは、既に`SIGQUIT`を受信したMがシグナルマスクを設定して、それ以上シグナルを受信しないようにすることで、シグナルがまだ処理されていないMに確実に届くようにします。
5.  **スタックトレースのダンプ**: `SIGQUIT`を受信した各Mは、自身の`sighandler`を呼び出し、自身のスタックトレースをダンプします。この際、`crashing`変数がインクリメントされ、次のMに`SIGQUIT`がリレーされます。
6.  **最後のM**: 最後のMが`SIGQUIT`を受信し、自身のスタックトレースをダンプすると、`crashing`変数が`sched.mcount`に達するため、それ以上`SIGQUIT`はリレーされず、最終的に`crash()`関数が呼び出されてプロセスが終了します。
7.  **タイムアウトとフォールバック**: 万が一シグナルのリレーがうまくいかなかった場合でも、各Mは`raiseproc(_SIGQUIT)`を呼び出した後に`sleep`（`usleep(5 * 1000 * 1000)`、つまり5秒間）します。これは、リレーが途中で途切れても、最終的には各Mがタイムアウト後に自身で`crash()`を呼び出して終了するためのフォールバックメカニズムです。ただし、通常は最後のMがすぐに`crash()`を呼び出すため、このスリープが完了する前にプロセスは終了します。

### `raiseproc`関数の導入

このメカニズムをサポートするために、`raiseproc`という新しい関数が導入されました。これは、現在のプロセスに指定されたシグナルを送信するためのGoランタイム内部関数です。OS固有の実装（アセンブリコード）が提供されており、`getpid`システムコールで現在のプロセスのPIDを取得し、`kill`システムコールでそのPIDにシグナルを送信します。

### `_SIGQUIT`定数の追加

各OSの`defs_*.go`ファイルに、`_SIGQUIT`という定数が追加され、その値がUnix系OSでは`3`（`SIGQUIT`の標準的な値）に設定されています。WindowsやPlan9など、`SIGQUIT`の概念がないOSではダミーの値（`0`）が設定されています。

## コアとなるコードの変更箇所

### `src/runtime/signal_amd64x.go`

このファイルは、AMD64アーキテクチャにおけるシグナルハンドリングのロジックを定義しています。主要な変更点は以下の通りです。

-   `crashing`変数の追加: `var crashing int32`
    -   これは、現在クラッシュ処理中であり、何個のMが既にスタックトレースをダンプしたかを追跡するためのカウンタです。
-   `sighandler`関数の変更:
    -   `startpanic()`の呼び出しが`if crashing == 0 { startpanic() }`で囲まれました。これにより、最初のパニック時のみ`startpanic()`が実行され、`SIGQUIT`リレーによる後続の`sighandler`呼び出しではスキップされます。
    -   スタックトレース出力時に`PC=`の後に`m=`と`_g_.m.id`（MのID）が出力されるようになりました。
    -   `tracebackothers(gp)`の呼び出しが条件付きになりました。`crashing > 0`かつ現在のMが`curg`（現在のゴルーチン）ではない場合、`tracebackothers`はスキップされ、代わりに`traceback`が直接呼び出されるロジックが追加されました。これは、`SIGQUIT`リレー中に既にダンプされたMのスタックトレースを重複して出力しないようにするためです。
    -   `docrash`がtrueの場合の処理に、`SIGQUIT`リレーのロジックが追加されました。
        ```go
        if docrash {
            // TODO(rsc): Implement raiseproc on other systems
            // and then add to this switch.
            switch GOOS {
            case "darwin", "linux":
                crashing++
                if crashing < sched.mcount {
                    // There are other m's that need to dump their stacks.
                    // Relay SIGQUIT to the next m by sending it to the current process.
                    // All m's that have already received SIGQUIT have signal masks blocking
                    // receipt of any signals, so the SIGQUIT will go to an m that hasn't seen it yet.
                    // When the last m receives the SIGQUIT, it will fall through to the call to
                    // crash below. Just in case the relaying gets botched, each m involved in
                    // the relay sleeps for 5 seconds and then does the crash/exit itself.
                    // In expected operation, the last m has received the SIGQUIT and run
                    // crash/exit and the process is gone, all long before any of the
                    // 5-second sleeps have finished.
                    print("\n-----\n\n")
                    raiseproc(_SIGQUIT)
                    usleep(5 * 1000 * 1000)
                }
            }
            crash()
        }
        ```
        このブロックは、`crashing`カウンタをインクリメントし、まだ全てのMが処理されていない場合に`raiseproc(_SIGQUIT)`を呼び出して`SIGQUIT`をリレーします。また、リレーが失敗した場合のフォールバックとして`usleep`が追加されています。

## コアとなるコードの解説

### `crashing`変数と`startpanic()`の制御

`signal_amd64x.go`の`crashing`変数は、`GODEBUG=crash`が有効な場合に、クラッシュ処理が進行中であることを示すフラグ兼カウンタとして機能します。
`if crashing == 0 { startpanic() }`という条件は重要です。`startpanic()`は、Goランタイムがパニック状態に入った際に一度だけ実行されるべき初期化処理（例えば、デバッグ情報の準備など）を行います。`SIGQUIT`リレーによって複数のMが`sighandler`を呼び出すことになりますが、`startpanic()`は最初のMによってのみ実行されるように制御されています。これにより、重複した初期化を防ぎ、クラッシュ処理の整合性を保ちます。

### `tracebackothers`の条件付き実行と`traceback`の直接呼び出し

通常のパニック時には、`tracebackothers(gp)`が呼び出され、現在のゴルーチン以外の全てのゴルーチンのスタックトレースが出力されます。しかし、`SIGQUIT`リレーのシナリオでは、各Mが自身のスタックトレースをダンプするため、`tracebackothers`をそのまま使用すると重複が発生する可能性があります。

このコミットでは、`crashing > 0`（つまり、既に`SIGQUIT`リレーが開始されている）かつ、現在のMが`curg`（現在のゴルーチン）ではない場合に、`tracebackothers`をスキップし、代わりに`traceback(^uintptr(0), ^uintptr(0), 0, gp)`を直接呼び出すロジックが追加されています。これは、`SIGQUIT`を受信したMが、自身のスタックトレースのみをダンプし、他のMが既にダンプした可能性のあるゴルーチンのスタックトレースを再度ダンプしないようにするための最適化です。

### `SIGQUIT`リレーのロジック

`sighandler`内の`if docrash { ... }`ブロックが、`SIGQUIT`リレーの核心です。

1.  `crashing++`: 現在のMがスタックトレースをダンプしたことを示すために、`crashing`カウンタをインクリメントします。
2.  `if crashing < sched.mcount`: `crashing`の値がGoランタイムが管理するOSスレッドの総数（`sched.mcount`）よりも小さい場合、まだ全てのMがスタックトレースをダンプしていないことを意味します。
3.  `raiseproc(_SIGQUIT)`: この行が、プロセス全体に`SIGQUIT`シグナルを送信し、まだスタックトレースをダンプしていない別のMにシグナルをリレーする役割を担います。
4.  `usleep(5 * 1000 * 1000)`: これは、リレーが失敗した場合のフォールバックメカニズムです。もし何らかの理由で`SIGQUIT`が他のMに配送されなかったり、最後のMが`crash()`を呼び出す前にプロセスが終了しなかったりした場合でも、このスリープ後に現在のMが最終的に`crash()`を呼び出してプロセスを終了させます。しかし、通常は最後のMがすぐに`crash()`を呼び出すため、このスリープが完了する前にプロセスは終了します。

### `raiseproc`関数の実装

`raiseproc`関数は、GoランタイムがOSスレッドにシグナルを送信するための抽象化レイヤーです。各OS/アーキテクチャのアセンブリファイル（例: `sys_linux_amd64.s`）で具体的に実装されています。

-   **`getpid`システムコール**: まず、`getpid`システムコールを呼び出して、現在のプロセスのプロセスID（PID）を取得します。シグナルはプロセス全体に送信されるため、このPIDが必要です。
-   **`kill`システムコール**: 次に、`kill`システムコールを呼び出します。`kill`システムコールは、指定されたPIDのプロセスに指定されたシグナルを送信します。ここでは、取得したPIDと`_SIGQUIT`シグナルを引数として渡します。

このアセンブリレベルの実装により、GoランタイムはOSの低レベルなシグナルメカニズムを直接操作し、全てのOSスレッドに`SIGQUIT`を効率的に配送することができます。

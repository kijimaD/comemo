## 元コミット内容

`fmt: refactor pointer formatting and improve tests`

このコミットは、`fmt` パッケージにおけるポインタのフォーマット処理をリファクタリングし、テストを改善します。

主な変更点は以下の通りです。
*   `fmt` パッケージ内の他の型における動詞処理と同様に、フォーマット関数の直接選択のために `switch` ステートメントを使用します。
*   `%v` でフォーマットされた `nil` ポインタにもパディングを適用します。
*   ポインタのテスト結果が、ポインタが表示されるべきインデックス `i` よりも短いフォーマット済み文字列 `s` になった場合に、`TestSprintf` で発生する "slice bounds out of range" パニックを防ぐためのガードを追加します。
*   テストの追加と再編成を行います。
*   Issue #14712 と #14714 を修正します。

## 変更の背景

このコミットは、Go言語の `fmt` パッケージにおけるポインタのフォーマット処理に関するいくつかの既存の問題と不整合を解決するために行われました。具体的には、以下の2つのIssueが修正されています。

1.  **Issue #14712: `fmt: %v of nil pointer should respect width`**
    このIssueは、`fmt.Sprintf` や `fmt.Printf` で `nil` ポインタを `%v` フォーマット動詞で出力する際に、幅指定（例: `%8v`）が無視されるというバグを報告していました。例えば、`fmt.Sprintf("%8v", (*int)(nil))` は `"<nil>"` と出力され、期待される `   <nil>` のようにパディングが適用されませんでした。これは、他の型の値が幅指定に従ってパディングされるのと比較して、一貫性のない挙動でした。

2.  **Issue #14714: `fmt: TestSprintf panics with "slice bounds out of range"`**
    このIssueは、`fmt` パッケージのテストスイートである `TestSprintf` が、特定の条件下で "slice bounds out of range" パニックを引き起こす可能性があることを報告していました。これは、テストケースで期待される出力文字列に `PTR` というプレースホルダーが含まれている場合、テストコードがこの `PTR` を実際のポインタアドレスに置き換える処理を行う際に、生成された文字列の長さが期待されるインデックスよりも短い場合に発生していました。特に、ポインタアドレスが非常に短い形式で出力される場合（例: `0x0`）に問題が生じやすかったと考えられます。

これらの問題を解決し、`fmt` パッケージのポインタフォーマット処理の一貫性と堅牢性を向上させることが、このコミットの主な動機となっています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と `fmt` パッケージの動作に関する知識が必要です。

1.  **`fmt` パッケージとフォーマット動詞:**
    `fmt` パッケージは、Go言語におけるフォーマットI/Oを実装しています。`fmt.Printf` や `fmt.Sprintf` などの関数は、フォーマット文字列と引数を受け取り、指定された形式で文字列を生成します。フォーマット文字列には、`%v` (デフォルトフォーマット)、`%p` (ポインタアドレス)、`%d` (10進数)、`%x` (16進数) などの「フォーマット動詞」が含まれます。

2.  **`%v` と `%#v`:**
    *   `%v`: 値のデフォルトフォーマット。ポインタの場合、通常は `0x` プレフィックス付きの16進数アドレスとして表示されます。`nil` ポインタの場合は `"<nil>"` と表示されます。
    *   `%#v`: Go構文で表現可能な値を出力します。ポインタの場合、型情報を含む `(*Type)(0xADDRESS)` の形式で表示されます。`nil` ポインタの場合は `(*Type)(nil)` と表示されます。

3.  **`%p`:**
    ポインタの値を `0x` プレフィックス付きの16進数として表示します。`nil` ポインタの場合は `0x0` と表示されます。

4.  **幅指定とパディング:**
    フォーマット動詞には、出力の幅を指定するオプションがあります。例えば、`%8v` は、出力が少なくとも8文字の幅になるようにパディング（通常はスペース）を追加します。左寄せの場合は `%-8v` を使用します。

5.  **`reflect` パッケージ:**
    `reflect` パッケージは、実行時にGoの型、値、構造を検査および操作するための機能を提供します。`fmt` パッケージは、引数の型を動的に判断し、適切なフォーマット処理を行うために `reflect` パッケージを内部的に使用しています。
    *   `reflect.Value`: Goの値の実行時表現。
    *   `reflect.Kind()`: `reflect.Value` の基底型（例: `reflect.Ptr`, `reflect.Chan`, `reflect.Func`）。
    *   `reflect.Value.Pointer()`: ポインタが指すアドレスを `uintptr` として返します。

6.  **`uintptr`:**
    `uintptr` は、ポインタを整数として表現できるGoの型です。これは、ポインタ演算や、ポインタアドレスを数値として扱う必要がある場合に使用されます。

7.  **`pp` 構造体と `fmt` 構造体:**
    `fmt` パッケージの内部では、`pp` (printer) 構造体が実際のフォーマット処理を担当します。`pp` は `fmt` 構造体（フォーマットフラグ、幅、精度などを保持）を埋め込んでおり、これらを使って出力形式を決定します。
    *   `p.fmt.sharpV`: `%#v` が指定されているかどうかを示すフラグ。
    *   `p.fmt.sharp`: `#` フラグが指定されているかどうかを示すフラグ（`%#p` など）。
    *   `p.fmt.padString()`: 文字列をパディングして出力する内部ヘルパー関数。
    *   `p.fmt0x64()`: `0x` プレフィックス付きの16進数として `uint64` をフォーマットする内部ヘルパー関数。
    *   `p.fmtUint64()`: 指定された動詞（`b`, `o`, `d`, `x`, `X`）に従って `uint64` をフォーマットする内部ヘルパー関数。

## 技術的詳細

このコミットの技術的な詳細を、`src/fmt/print.go` と `src/fmt/fmt_test.go` の変更点に焦点を当てて解説します。

### `src/fmt/print.go` の変更点

`fmt` パッケージの `print.go` ファイルには、`pp` 構造体の `fmtPointer` メソッドが定義されており、これがポインタのフォーマット処理を担当します。

**変更前:**
変更前の `fmtPointer` メソッドは、最初に `use0x64` というブール変数を使って、`0x` プレフィックス付きの16進数フォーマット (`fmt0x64`) を使用するか、それとも基数指定のフォーマット (`fmtUint64`) を使用するかを決定していました。このロジックは、`verb` (フォーマット動詞) に応じて `use0x64` を設定する `switch` ステートメントと、その後の `if/else if/else` ブロックで構成されていました。

特に問題だったのは、`verb == 'v' && u == 0` (つまり `%v` で `nil` ポインタ) の場合に `p.buf.WriteString(nilAngleString)` を直接呼び出しており、この際に幅指定によるパディングが適用されていなかった点です。

**変更後:**
変更後の `fmtPointer` メソッドは、フォーマット動詞 `verb` に基づいて処理を直接分岐させる、より明確な `switch` ステートメントを採用しています。

```go
func (p *pp) fmtPointer(value reflect.Value, verb rune) {
	// ... (uintptr u の取得部分は変更なし) ...

	switch verb {
	case 'v':
		if p.fmt.sharpV { // %#v の場合
			p.buf.WriteByte('(')
			p.buf.WriteString(value.Type().String())
			p.buf.WriteString(")(")
			if u == 0 {
				p.buf.WriteString(nilString)
			} else {
				p.fmt0x64(uint64(u), true)
			}
			p.buf.WriteByte(')')
		} else { // %v の場合
			if u == 0 { // nil ポインタの場合
				p.fmt.padString(nilAngleString) // ここでパディングが適用されるように変更
			} else {
				p.fmt0x64(uint64(u), !p.fmt.sharp)
			}
		}
	case 'p': // %p の場合
		p.fmt0x64(uint64(u), !p.fmt.sharp)
	case 'b', 'o', 'd', 'x', 'X': // 基数指定の動詞の場合
		p.fmtUint64(uint64(u), verb)
	default:
		p.badVerb(verb)
	}
}
```

この変更のポイントは以下の通りです。
1.  **`switch verb` の導入:** 以前の `use0x64` フラグと複雑な `if/else` 構造を廃止し、`verb` に基づく `switch` ステートメントで処理を明確に分岐させることで、コードの可読性と保守性が向上しました。これはコミットメッセージにある「Uses a switch statement for direct format function selection similar to other types verb handling in fmt.」に該当します。
2.  **`nil` ポインタのパディング修正 (Issue #14712 修正):**
    `case 'v'` のブロック内で、`u == 0` (nil ポインタ) の場合に `p.fmt.padString(nilAngleString)` を呼び出すように変更されました。これにより、`"<nil>"` 文字列が `pp` 構造体の持つ幅指定に従って適切にパディングされるようになり、Issue #14712 が修正されました。
3.  **`%#p` の挙動の明確化:** `%#p` は `0x` プレフィックスなしでアドレスを出力するべきですが、以前のロジックでは `!p.fmt.sharp` の扱いが曖昧でした。新しい `switch` 構造では、`case 'p'` の中で `p.fmt0x64(uint64(u), !p.fmt.sharp)` が直接呼び出され、`#` フラグの有無に応じて `0x` プレフィックスの有無が適切に制御されるようになりました。

### `src/fmt/fmt_test.go` の変更点

テストファイル `fmt_test.go` では、主に以下の変更が行われました。

1.  **`TestSprintf` のパニック防止 (Issue #14714 修正):**
    `TestSprintf` 関数内の `PTR` プレースホルダー置換ロジックが修正されました。以前は、`strings.Index(tt.out, "PTR")` で `PTR` の位置 `i` を見つけた後、`s[j:]` のスライス操作を行う際に、`s` (実際の出力文字列) の長さが `i` よりも短い場合に "slice bounds out of range" パニックが発生する可能性がありました。
    新しいコードでは、`if i >= 0 && i < len(s)` というガード条件が追加され、`i` が有効なインデックス範囲内にあることを確認してからスライス操作を行うようになりました。これにより、Issue #14714 が修正されました。

    ```go
    // 変更前:
    // if i := strings.Index(tt.out, "PTR"); i >= 0 {
    //     // ...
    //     s = s[0:i] + pattern + s[j:]
    // }

    // 変更後:
    i := strings.Index(tt.out, "PTR")
    if i >= 0 && i < len(s) { // ここにガード条件が追加
        // ...
        // s = p (p は適切に構築された文字列)
    }
    ```

2.  **ポインタフォーマットのテストケース拡充:**
    `fmtTests` スライスに、ポインタのフォーマットに関する新しいテストケースが多数追加されました。
    *   `nil` ポインタの `%p`, `%#p`, `%v`, `%#v` フォーマット。
    *   `nil` ポインタに対する幅指定 (`%8.2p`, `%8.2v`) のテスト。これにより、Issue #14712 の修正が正しく機能するか検証されます。
    *   非ポインタ型に対する `%p` のテスト (`%!p(int=27)`)。
    *   `nil` 自体に対する `%p` のテスト (`%!p(<nil>)`)。
    *   ポインタに対する基数指定 (`%b`, `%d`, `%o`, `%x`, `%X`) のテスト。
    *   `String()` メソッドを持つポインタの挙動 (`%s` と `%p` の違い)。
    *   無効な動詞 (`%☠`) とポインタの組み合わせテスト。

3.  **テストデータの整理:**
    `const` と `var` の宣言が整理され、関連する定数や変数がグループ化されました。

これらの変更により、ポインタのフォーマット処理がより堅牢になり、予期せぬパニックが防止され、`fmt` パッケージの動作の一貫性が向上しました。

## コアとなるコードの解説

### `src/fmt/print.go` の `fmtPointer` メソッド

このメソッドは、`reflect.Value` 型のポインタ値とフォーマット動詞 `verb` を受け取り、そのポインタを `pp` 構造体のバッファにフォーマットして書き込みます。

*   **変更前:**
    *   `use0x64` というフラグを使って、`%p` や `%v` の場合は `0x` プレフィックス付きの16進数フォーマットを、`%b`, `%d`, `%o`, `%x`, `%X` の場合は基数指定のフォーマットを使用するかを決定していました。
    *   `if p.fmt.sharpV` (つまり `%#v`) のブロックと、`else if verb == 'v' && u == 0` (つまり `%v` で `nil` ポインタ) のブロック、そしてそれ以外の `else` ブロックという複雑な条件分岐がありました。
    *   特に `verb == 'v' && u == 0` の場合、`p.buf.WriteString(nilAngleString)` を直接呼び出していたため、`fmt` 構造体に設定された幅指定が無視され、パディングが適用されませんでした。

*   **変更後:**
    *   `switch verb` ステートメントが導入され、フォーマット動詞に基づいて処理が直接分岐されるようになりました。これにより、コードの構造がより明確になり、各動詞の処理が独立して理解しやすくなりました。
    *   `case 'v'` のブロック内で、`nil` ポインタ (`u == 0`) の処理が `p.fmt.padString(nilAngleString)` を呼び出すように変更されました。`p.fmt.padString` は `fmt` 構造体の幅指定を考慮して文字列をパディングするため、Issue #14712 で報告された `%v` での `nil` ポインタのパディング問題が解決されました。
    *   `case 'p'` では `p.fmt0x64(uint64(u), !p.fmt.sharp)` が直接呼び出され、`#` フラグの有無に応じて `0x` プレフィックスの有無が適切に制御されます。
    *   `case 'b', 'o', 'd', 'x', 'X'` では `p.fmtUint64(uint64(u), verb)` が呼び出され、基数指定のフォーマットが適用されます。

このリファクタリングにより、`fmtPointer` のロジックが簡素化され、`fmt` パッケージ全体でのフォーマット動詞の処理の一貫性が向上しました。

### `src/fmt/fmt_test.go` の `TestSprintf` 関数

このテスト関数は、`fmtTests` スライスに定義された多数のフォーマットテストケースをループ処理し、`fmt.Sprintf` の出力が期待される結果と一致するかを検証します。

*   **変更前:**
    *   テスト結果の文字列 `s` と期待される出力 `tt.out` を比較する前に、`tt.out` に含まれる `PTR` プレースホルダーを実際のポインタアドレスに置き換える処理を行っていました。
    *   この置換ロジックは、`strings.Index(tt.out, "PTR")` で `PTR` の開始位置 `i` を見つけ、その後のループでポインタアドレスの文字を特定し、`s[0:i] + pattern + s[j:]` のように文字列を再構築していました。
    *   しかし、`s` の長さが `i` よりも短い場合、`s[j:]` のようなスライス操作が "slice bounds out of range" パニックを引き起こす可能性がありました。これは、特に `0x0` のように短いポインタアドレスが生成される場合に顕著でした。

*   **変更後:**
    *   `i := strings.Index(tt.out, "PTR")` の後に、`if i >= 0 && i < len(s)` というガード条件が追加されました。これにより、`PTR` が見つかり、かつそのインデックス `i` が実際の出力文字列 `s` の有効な範囲内にある場合にのみ、ポインタアドレスの置換処理が実行されるようになりました。
    *   このガード条件の追加により、Issue #14714 で報告された "slice bounds out of range" パニックが効果的に防止されます。
    *   また、`PTR` の置換ロジック自体も、`PTR_b`, `PTR_o`, `PTR_d`, `PTR_x`, `PTR_X` といった基数指定のプレースホルダーに対応するように拡張され、それぞれの基数に応じた有効な文字セット (`chars`) を使用してアドレス部分を特定するようになりました。これにより、テストの柔軟性と正確性が向上しています。

これらのテストの改善は、`fmtPointer` メソッドのリファクタリングと密接に関連しており、変更が正しく機能し、新たな問題を引き起こさないことを保証するために不可欠です。

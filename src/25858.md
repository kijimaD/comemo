# [インデックス 25858] ファイルの概要

## 元コミット内容

`cmd/compile: use correct line number for := (LCOLAS)`

このコミットは、Goコンパイラが`:=`（短い変数宣言）演算子に関連するエラーを報告する際に、正しい行番号を使用するように修正します。

主な変更点は以下の通りです。
- `LCOLAS`（`:=`を表すトークン）の行番号を扱う際に、一貫して`lno`というローカル変数名を使用するように変更。
- レキサー（字句解析器）において、`yylval.i`に行番号を割り当てる不要な処理を削除。

この修正は`mdempsky`氏の提案に基づいています。
Issue #13415を修正します。

## 変更の背景

Goコンパイラは、コードの構文エラーやセマンティックエラーを検出した際に、そのエラーが発生した正確な行番号をユーザーに報告する必要があります。これにより、開発者は問題の箇所を迅速に特定し、修正することができます。

このコミットが修正する問題（Issue #13415）は、`:=`演算子に関連する特定のエラー（例: `x, x := ...` のように左辺で変数が重複して宣言されるケース）が発生した際に、コンパイラが報告する行番号が不正確であるというものでした。具体的には、エラーが実際に発生した行ではなく、その後の行や関連性の低い行を指してしまうことがありました。

このような不正確なエラー報告は、デバッグを困難にし、開発者の生産性を低下させます。そのため、コンパイラが常に正確な行番号情報を提供することは非常に重要です。このコミットは、`:=`演算子の処理における行番号の管理方法を見直し、この問題を解決することを目的としています。

## 前提知識の解説

このコミットの理解には、以下のGoコンパイラの内部構造と概念に関する知識が役立ちます。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するプログラムです。複数のフェーズ（字句解析、構文解析、型チェック、最適化、コード生成など）で構成されます。
2.  **字句解析 (Lexing/Scanning)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割するプロセスです。例えば、`var x = 10`というコードは、`var`（キーワード）、`x`（識別子）、`=`（代入演算子）、`10`（整数リテラル）といったトークンに分割されます。
    *   `src/cmd/compile/internal/gc/lex.go`: Goコンパイラの字句解析器の実装が含まれています。
    *   **`LCOLAS`**: 字句解析器が`:=`という文字列を認識したときに生成するトークンの一種です。
3.  **構文解析 (Parsing)**: 字句解析器が生成したトークンのストリームを受け取り、Go言語の文法規則に従って、プログラムの構造を抽象構文木（AST: Abstract Syntax Tree）として構築するプロセスです。
    *   `src/cmd/compile/internal/gc/parser.go`: Goコンパイラの構文解析器の実装が含まれています。
    *   **`lineno`**: 構文解析器が現在処理しているソースコードの行番号を追跡するための変数です。
    *   **`yylval`**: `yacc`や`bison`のようなパーサジェネレータでよく使われる構造体で、字句解析器から構文解析器へトークンの「意味的な値」（例: 識別子の名前、リテラルの値、そしてこのケースでは行番号など）を渡すために使用されます。`yylval.i`はその中の整数値を格納するフィールドです。
4.  **`:=` (短い変数宣言)**: Go言語特有の構文で、変数の宣言と初期化を同時に行うことができます。例えば、`x := 10`は`var x int = 10`とほぼ同等ですが、型推論が行われます。
5.  **エラー報告**: コンパイラは、コードに問題がある場合、エラーメッセージとともに行番号やファイル名を報告します。この情報が正確であることは、開発体験において非常に重要です。

このコミットは、字句解析器と構文解析器の間で行番号情報がどのようにやり取りされ、`:=`演算子のASTノードにどのように関連付けられるかという、コンパイラの内部的な詳細に焦点を当てています。

## 技術的詳細

このコミットの技術的な核心は、`:=`演算子（`LCOLAS`トークン）に関連する行番号の管理を、レキサーからパーサーへと移管し、パーサー内で一貫した方法で処理することにあります。

1.  **レキサーからの行番号情報の削除**:
    *   以前の`src/cmd/compile/internal/gc/lex.go`では、`:=`トークン（`LCOLAS`）を検出した際に、`yylval.i = int(lexlineno)`という行がありました。これは、レキサーが認識した現在の行番号（`lexlineno`）を`yylval.i`という共有変数に格納し、パーサーに渡そうとしていたことを示唆しています。
    *   このコミットでは、この行が削除されました。これは、`yylval.i`を介した行番号の伝達が、`:=`のケースでは不要であるか、あるいは誤った行番号をパーサーに提供する原因となっていたことを意味します。パーサーは自身の`lineno`変数を持っており、これがより信頼性の高い情報源であると判断されたと考えられます。

2.  **パーサー内での行番号の一貫した取得と利用**:
    *   `src/cmd/compile/internal/gc/parser.go`では、`simple_stmt`関数と`case_`関数（それぞれ通常の短い変数宣言と`select`文の`case`節内の短い変数宣言を処理）が`LCOLAS`トークンを扱います。
    *   これらの関数内で、以前は`line := lineno`という形で現在の行番号を取得していましたが、これを`lno := lineno`に変更しました。これは単なる変数名の変更ですが、`lno`という一貫した名前を使用することで、コードの可読性と保守性が向上します。
    *   最も重要な変更は、`colas`関数（`:=`演算子に対応するASTノードを構築する関数）を呼び出す際に、この`lno`変数を明示的に行番号として渡すようになった点です。
        *   `return colas(lhs, rhs, int32(line))` が `return colas(lhs, rhs, int32(lno))` に変更。
        *   `stmt.List = list1(colas(cases, list1(rhs), int32(p.op)))` が `stmt.List = list1(colas(cases, list1(rhs), int32(lno)))` に変更。
    *   これにより、`colas`関数がASTノードを作成する際に、パーサーが`LCOLAS`トークンを処理した時点での正確な行番号が確実に渡されるようになります。

この修正の全体的な効果は、`:=`演算子に関連するASTノードが、その宣言がソースコード内で実際に発生した行番号と正確に結びつけられるようになることです。これにより、コンパイラがそのノードに関連するエラーを報告する際に、常に正しい行番号を指すことが保証されます。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラの字句解析と構文解析の連携において、`:=`演算子（`LCOLAS`トークン）の行番号情報を正確に伝達し、ASTノードに紐付ける方法を改善した点にあります。

1.  **`lex.go`の変更**:
    *   `yylval.i = int(lexlineno)`の削除は、レキサーが`:=`トークンを検出した際に、その行番号を`yylval.i`という汎用的なフィールドに格納してパーサーに渡すという従来のメカニズムが、この特定のケースでは問題を引き起こしていたことを示しています。おそらく、`yylval.i`が他の目的で上書きされたり、パーサーが期待するタイミングで読み取られなかったりしたため、不正確な行番号が伝播していた可能性があります。この変更により、`:=`の行番号の責任は完全にパーサーに移管されます。

2.  **`parser.go`の変更**:
    *   `simple_stmt`関数と`case_`関数は、Goの文法において`:=`演算子が出現する主要な場所を処理します。
    *   `lno := lineno`という行は、パーサーが`LCOLAS`トークンを消費した直後に、パーサー自身の持つ現在の正確な行番号（`lineno`）を`lno`というローカル変数に保存することを意味します。これにより、その後の処理で`lineno`が更新されても、`:=`演算子自体の行番号は`lno`に保持されます。
    *   `colas(lhs, rhs, int32(lno))`への変更は、`colas`関数が`:=`演算子に対応するASTノードを構築する際に、この正確にキャプチャされた`lno`を行番号として使用することを保証します。`colas`関数は、左辺（`lhs`）、右辺（`rhs`）、そして行番号を受け取り、新しい短い変数宣言のASTノードを作成します。この修正により、作成されるASTノードには常に正しいソースコード上の位置情報が埋め込まれることになります。
    *   特に`case_`関数における`int32(p.op)`から`int32(lno)`への変更は重要です。`p.op`はパーサーの現在の演算子を表す可能性があり、これが必ずしも`LCOLAS`の正確な行番号を指すとは限りませんでした。`lno`を明示的に使用することで、この曖昧さが解消され、正確な行番号が保証されます。

3.  **`test/fixedbugs/issue13415.go`の追加**:
    *   このテストは、修正が意図通りに機能することを確認するためのものです。`select`文の`case`節内で`x, x := ...`という不正な短い変数宣言を記述し、コンパイラが`ERROR "x repeated on left side of :="`というメッセージを、この`case`行の正確な位置で報告するかどうかを検証します。このようなテストケースは、コンパイラのエラー報告の正確性を保証するために不可欠です。

これらの変更により、Goコンパイラは`:=`演算子に関連するエラーを、より正確な行番号で報告できるようになり、開発者のデバッグ体験が向上します。

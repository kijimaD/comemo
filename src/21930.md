## 変更の背景

この変更の背景には、Goランタイムのガベージコレクタ（GC）の進化があります。GoのGCは、並行マーク＆スイープ方式を採用しており、アプリケーションの実行と並行してGC処理を進めることで、Stop-The-World（STW）ポーズの時間を最小限に抑えることを目指しています。

`drainworkbuf` 関数は、GCのマークフェーズにおいて、"work buffer"（ワークバッファ）と呼ばれる一時的なデータ構造に格納されたオブジェクトを処理する役割を担っています。ワークバッファには、GCによって到達可能と判断されたものの、まだその内部のポインタがスキャンされていない「グレーオブジェクト」が格納されます。`drainworkbuf` はこれらのグレーオブジェクトをスキャンし、さらに到達可能なオブジェクトを発見してマークする処理を行います。

元々、`drainworkbuf` 関数には `drainallwbufs` というブーリアン引数がありました。これは、関数がすべてのワークバッファをドレインすべきか、それとも部分的にドレインすべきかを制御するためのものでした。しかし、時間の経過とともに、`drainworkbuf` が呼び出されるすべての箇所で、この `drainallwbufs` 引数には常に `true` が渡されるようになりました。これは、GCの設計上、部分的なドレインが不要になったか、あるいはそのように動作させることが非効率的になったことを示唆しています。

このコミットは、実際の使用状況に合わせてコードを簡素化し、冗長な引数を削除することを目的としています。これにより、コードの可読性が向上し、`drainworkbuf` の役割が「常にすべてのワークバッファをドレインする」という明確なものになります。また、コミットメッセージにある「1つのwbufをドレインする状況はもはや存在しない」という記述は、GCのワーク処理の粒度が変化し、より大きな単位での処理が主流になったことを示しています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクタ（GC）の基本的な仕組みと、特に並行マーク＆スイープGCにおける「ワークバッファ」の概念を理解する必要があります。

### Goのガベージコレクタ（GC）の概要

GoのGCは、主に以下のフェーズで動作します。

1.  **マークフェーズ (Mark Phase)**:
    *   GCのルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトを特定し、マークします。
    *   GoのGCは並行マークを採用しており、アプリケーションのゴルーチンと並行してオブジェクトのスキャンとマークを行います。
    *   このフェーズで、到達可能だがまだスキャンされていないオブジェクトは「グレーオブジェクト」と呼ばれ、後述するワークバッファに格納されます。
    *   マークフェーズの最後には、すべての到達可能なオブジェクトがマークされ、到達不可能なオブジェクトはマークされません。

2.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクト（到達不可能なオブジェクト）が占めていたメモリ領域を解放し、再利用可能にします。
    *   スイープも並行して行われることがありますが、一部の処理はSTWポーズ中に行われることもあります。

### ワークバッファ (Work Buffer) とグレーオブジェクト (Grey Object)

Goの並行GCでは、マークフェーズ中に複数のゴルーチンが並行してオブジェクトをスキャンします。この並行処理を効率的に行うために、「ワークバッファ」という仕組みが導入されています。

*   **グレーオブジェクト**: GCのマークフェーズにおいて、到達可能であると識別されたものの、そのオブジェクトが参照している他のオブジェクト（ポインタ）がまだスキャンされていない状態のオブジェクトを指します。これらのオブジェクトは、GCが次にスキャンすべき「作業リスト」のようなものです。
*   **ワークバッファ (Work Buffer)**: グレーオブジェクトを一時的に格納するためのバッファです。各P（プロセッサ、Goランタイムのスケジューラが管理する論理CPU）は、自身のローカルなワークバッファを持ち、GCワーカーゴルーチンがこのバッファからグレーオブジェクトを取り出してスキャンします。ワークバッファが満杯になったり、空になったりすると、グローバルなワークキューとの間でやり取りが行われます。
*   **ドレイン (Drain)**: ワークバッファに格納されたグレーオブジェクトをすべて処理し、バッファを空にするプロセスを指します。この処理には、グレーオブジェクトから参照される新しいオブジェクトをマークし、必要に応じてそれらをワークバッファに追加する作業が含まれます。すべてのワークバッファがドレインされると、GCはすべての到達可能なオブジェクトを特定し終えたことになります。

### `go:nowritebarrier` ディレクティブ

`go:nowritebarrier` はGoコンパイラに対するディレクティブ（指示）で、その関数内でポインタの書き込みバリア（write barrier）を生成しないように指示します。書き込みバリアは、GCがオブジェクトグラフを正確に追跡するために、ポインタの書き込み時に特定の処理（例えば、新しいオブジェクトが参照されたことをGCに通知する）を行う仕組みです。GCの内部処理、特にGC自体がメモリを操作するような低レベルな部分では、書き込みバリアが不要または邪魔になる場合があり、その際にこのディレクティブが使用されます。`drainworkbuf` のようなGCのコア関数にこのディレクティブが付いているのは、GCの整合性を保ちつつパフォーマンスを最適化するためです。

## 技術的詳細

このコミットは、`src/runtime/mgc.go` ファイル内の `drainworkbuf` 関数のシグネチャと、その呼び出し箇所を変更しています。

### `drainworkbuf` 関数の役割

`drainworkbuf` 関数は、GoのGCにおけるマークフェーズの重要な部分を担っています。その主な役割は以下の通りです。

1.  **ワークバッファの処理**: 引数として渡された `wbuf`（ワークバッファ）から開始し、そこに格納されているグレーオブジェクトをスキャンします。
2.  **グレーオブジェクトのスキャン**: 各グレーオブジェクトのポインタをたどり、それが参照するオブジェクトをマークします。もし新しい到達可能なオブジェクトが見つかれば、それらをグレーオブジェクトとしてワークバッファに追加します。
3.  **ワークバッファの補充と排出**: ローカルのワークバッファが空になった場合、グローバルなワークキューから新しいワークバッファを取得して処理を続けます。ワークバッファが完全に処理されたら、それを空のバッファとしてキューに戻します。
4.  **すべてのワークのドレイン**: この関数は、最終的にすべてのワークバッファが空になるまで、つまりGCが処理すべきグレーオブジェクトがなくなるまで、このプロセスを繰り返します。

### 変更点と技術的意味合い

元の `drainworkbuf` 関数は、`func drainworkbuf(wbuf *workbuf, drainallwbufs bool)` というシグネチャを持っていました。ここで `drainallwbufs` は、すべてのワークバッファをドレインするかどうかを制御するブーリアン引数でした。

このコミットでは、以下の変更が行われました。

1.  **`drainallwbufs` 引数の削除**:
    ```diff
    -func drainworkbuf(wbuf *workbuf, drainallwbufs bool) {
    +func drainworkbuf(wbuf *workbuf) {
    ```
    この変更により、`drainworkbuf` は常にすべてのワークバッファをドレインするようになりました。コミットメッセージが示唆するように、この引数は常に `true` で呼び出されていたため、実質的に冗長でした。引数を削除することで、関数の意図がより明確になり、コードの簡潔性が向上します。

2.  **`drainallwbufs` に基づく条件分岐の削除**:
    ```diff
    -		if !drainallwbufs {
    -			break
    -		}
    ```
    `drainallwbufs` 引数が削除されたため、この条件分岐も不要になりました。これにより、ワークバッファが空になった際に、常にグローバルキューから新しいワークバッファを補充しようとする動作が保証されます。これは、`drainworkbuf` が「すべてのワークをドレインする」という単一の目的を持つことを強調しています。

3.  **呼び出し箇所の更新**:
    `drainworkbuf` が呼び出されているすべての箇所で、`drainallwbufs` 引数が削除されました。
    *   `src/runtime/mgc.go` の `gchelper` 関数内:
        ```diff
        -		drainworkbuf(nil, true) // blocks in getfull
        +		drainworkbuf(nil) // blocks in getfull
        ```
    *   `src/runtime/mgc.go` の `gcmark_m` 関数内:
        ```diff
        -	drainworkbuf(nil, true)
        +	drainworkbuf(nil)
        ```
    *   `src/runtime/mgc.go` の `gc` 関数内:
        ```diff
        -	drainworkbuf(nil, true)
        +	drainworkbuf(nil)
        ```
    これらの変更は、`drainworkbuf` が常に完全なドレイン操作を行うという新しいセマンティクスに合わせて、既存の呼び出しを更新したものです。

### 技術的意味合い

*   **GCの動作の明確化**: `drainworkbuf` が常にすべてのワークバッファをドレインするという動作がコードレベルで明確になりました。これにより、GCのマークフェーズにおけるワーク処理の挙動がより予測可能になります。
*   **コードの簡素化と保守性**: 冗長な引数とそれに基づく条件分岐が削除されたことで、コードベースが簡素化され、将来的な保守が容易になります。
*   **パフォーマンスへの影響**: この変更自体が直接的なパフォーマンスの向上をもたらすわけではありませんが、GCの内部ロジックがより効率的で意図通りに動作していることを示しています。`drainallwbufs` が常に `true` であったという事実は、GCが常にすべてのワークを処理する必要があったことを意味しており、この変更はその実態をコードに反映したものです。
*   **GC設計の成熟**: このような変更は、GoのGCが初期段階から成熟し、その内部動作がより洗練されてきたことを示しています。不要な柔軟性やオプションが削除され、最も効率的で安定したパスが採用されています。

## コアとなるコードの解説

### `drainworkbuf` 関数の変更

*   **シグネチャの変更**:
    `func drainworkbuf(wbuf *workbuf, drainallwbufs bool)` から `func drainworkbuf(wbuf *workbuf)` へと変更されました。これにより、`drainallwbufs` 引数が削除され、関数が常にすべてのワークバッファをドレインする単一の動作を持つことが明確になりました。

*   **内部ロジックの変更**:
    `drainallwbufs` 引数に依存していた条件分岐 `if !drainallwbufs { break }` が削除されました。これにより、`wbuf.nobj == 0`（現在のワークバッファが空になった）場合、常に `putempty` で空のバッファをキューに戻し、その後 `getfull` でグローバルキューから新しいワークバッファを取得しようとします。これは、GCが処理すべきワークがなくなるまでループを継続することを保証します。

*   **コメントの更新**:
    関数のコメントも更新され、`drainallwbufs` 引数に関する記述が削除され、`drainworkbuf` が「すべてのワークバッファをドレインする」という新しい役割を反映しています。

### 呼び出し箇所の変更

`gchelper`, `gcmark_m`, `gc` の各関数内で `drainworkbuf` が呼び出されている箇所も、新しいシグネチャに合わせて `drainworkbuf(nil, true)` から `drainworkbuf(nil)` へと変更されました。これは、これらの関数がGCの特定のフェーズ（ヘルパーゴルーチンの起動、マークフェーズ、GCのメイン処理）でワークバッファの完全なドレインを必要とすることを示しています。`nil` を渡すことで、`drainworkbuf` は必要に応じて新しいワークバッファを取得して処理を開始します。

これらの変更は、GoのGCがより効率的で、特定のシナリオで常に完全なワークバッファのドレインが必要とされるようになったことを反映しています。冗長な引数を削除することで、コードの意図が明確になり、保守性が向上します。

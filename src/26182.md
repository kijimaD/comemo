# [インデックス 26182] ファイルの概要

このコミットは、Goランタイムのテストインフラストラクチャを大幅に改善し、テスト実行時間の短縮を目的としています。具体的には、多数の個別のテストプログラムを少数の統合されたプログラムに集約し、テスト実行時にこれらのプログラムのコンパイル結果を再利用するメカニズムを導入しています。

## 元コミット内容

Goランタイムのテストプログラムをソースコードから分離し、統合しました。

これにより、コンパイルするプログラムが多数からわずか3つになり、繰り返しのテストで再ビルドする代わりにコンパイル結果を再利用できるようになりました。

これらの変更を合わせると、私のラップトップでの `all.bash` 実行中のランタイムテストにかかる時間が約60秒から約30秒に短縮されました。（`all.bash` 自体は5分半で実行されます。）

Issue #10571に対応。

## 変更の背景

Goのランタイムテストは、多くの小さなテストプログラムを個別にコンパイルし、実行する形式でした。このアプローチは、各テストが独立しているという利点がある一方で、テストスイート全体の実行時間を著しく長くするという問題がありました。特に、`all.bash` のような包括的なテストスクリプトを実行する際には、コンパイルオーバーヘッドが無視できないレベルに達していました。

このコミットの主な動機は、テスト実行時間の短縮です。開発者がより迅速にフィードバックを得られるようにし、CI/CDパイプラインの効率を向上させることを目的としています。Issue #10571で議論されたこの問題に対し、Russ Cox氏が解決策を提案しました。

## 前提知識の解説

*   **Goのテストフレームワーク**: Go言語には標準で `testing` パッケージが提供されており、`go test` コマンドを通じてテストを実行します。テストファイルは通常 `_test.go` というサフィックスを持ち、`TestXxx` という形式の関数を定義します。
*   **`go build` コマンド**: Goのソースコードをコンパイルして実行可能ファイルを生成するコマンドです。テストプログラムも最終的には実行可能ファイルとしてビルドされます。
*   **`all.bash`**: Goプロジェクトのルートディレクトリにあるシェルスクリプトで、Goツールチェイン全体のビルド、インストール、およびテストを実行する際に使用されます。これはGo開発における主要なテスト実行メカニズムの一つです。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用するテストは、通常のGoテストとは異なるコンパイル・リンクプロセスを必要とすることがあります。
*   **テストの分離と結合**: 従来のGoランタイムテストでは、各テストケースが独自のソースコードを持ち、個別の実行可能ファイルとしてビルドされていました。このコミットでは、関連するテストケースを一つの大きな実行可能ファイルにまとめることで、コンパイル回数を減らしています。
*   **`runtime.LockOSThread()`**: Goのランタイム関数で、現在のGoルーチンを特定のOSスレッドにロックします。これは、CgoコールバックやOSスレッドに依存する低レベルな操作を行う際に重要となります。

## 技術的詳細

このコミットの核心は、Goランタイムのテスト方法論の変更にあります。以前は、各 `_test.go` ファイル内でテスト対象のコード（例えばクラッシュテストのソースコード）が文字列リテラルとして定義され、`executeTest` のようなヘルパー関数がその文字列を一時ファイルに書き出し、個別に `go build` して実行していました。この方式は、テストごとにコンパイルが走るため、テストケースが増えるにつれてコンパイル時間が累積し、テストスイート全体の実行時間が長くなるという問題がありました。

新しいアプローチでは、以下の変更が導入されました。

1.  **テストプログラムの集約**:
    *   `src/runtime/testdata/` ディレクトリの下に、`testprog`、`testprogcgo`、`testprognet` という新しいディレクトリが作成されました。
    *   これらのディレクトリには、それぞれ関連するテストケースの実際のソースコード（例: `crash.go`, `deadlock.go`, `gc.go` など）が配置されています。
    *   各テストプログラム（例: `testprog/main.go`）は、`register(name string, f func())` 関数を通じて、テスト関数を名前で登録するメカニズムを持っています。これにより、一つの実行可能ファイルが複数のテストロジックを内包できるようになります。
    *   `main` 関数では、コマンドライン引数としてテスト名を読み取り、対応する登録済みテスト関数を実行します。

2.  **コンパイル結果の再利用**:
    *   `src/runtime/crash_test.go` などのテストファイルでは、`executeTest` 関数が `runTestProg` 関数に置き換えられました。
    *   `runTestProg` 関数は、`buildTestProg` を呼び出して、`testprog`、`testprogcgo`、`testprognet` のいずれかの実行可能ファイルをビルドします。
    *   `buildTestProg` 関数は、`sync.Mutex` と `map[string]buildexe` を使用して、一度ビルドされた実行可能ファイルのパスとビルド結果をキャッシュします。これにより、同じテストプログラムが複数回必要とされても、再コンパイルすることなく、既存のビルド済み実行可能ファイルを再利用できます。
    *   `TestMain` 関数が導入され、テストスイートの開始時に一時ディレクトリを作成し、終了時にクリーンアップするロジックが追加されました。

3.  **ソースコードの分離**:
    *   以前は `_test.go` ファイル内に文字列リテラルとして埋め込まれていたテスト対象のソースコード（例: `cgoSignalDeadlockSource`）が削除され、対応する `testdata` ディレクトリ内のファイルに移動されました。これにより、`_test.go` ファイルはテストの実行ロジックに集中し、テスト対象のコードは独立したファイルとして管理されるようになりました。

これらの変更により、`all.bash` 実行時のランタイムテストにかかる時間が大幅に短縮され、開発効率が向上しました。特に、Cgo関連のテストはコンパイルに時間がかかる傾向があるため、`testprogcgo` のような集約されたプログラムの導入は大きな効果をもたらします。

## コアとなるコードの解説

変更の核心は、`executeTest` 関数が `runTestProg` 関数に置き換えられたことです。

1.  **`executeTest` (変更前)**:
    *   この関数は、テスト対象のGoソースコードを文字列テンプレートとして受け取り、それを一時ファイルに書き出していました。
    *   その後、`go build` コマンドを使ってその一時ファイルを個別にコンパイルし、実行可能ファイルを生成していました。
    *   最後に、生成された実行可能ファイルを実行し、その出力を返していました。
    *   このプロセスはテストごとに繰り返されるため、コンパイルオーバーヘッドが大きかったのです。

2.  **`runTestProg` (変更後)**:
    *   この関数は、`binary` (例: "testprog", "testprogcgo") と `name` (テスト関数名、例: "CgoSignalDeadlock") を引数に取ります。
    *   内部で `buildTestProg` を呼び出し、指定された `binary` に対応する実行可能ファイルのパスを取得します。
    *   `buildTestProg` は、`testprog` などの集約されたテストプログラムを一度だけビルドし、その結果をキャッシュします。これにより、同じ `binary` が再度要求されても再コンパイルは行われません。
    *   `runTestProg` は、ビルドされた実行可能ファイル (`exe`) を、引数として `name` (テスト関数名) を渡して実行します。
    *   実行可能ファイル (`testprog/main.go` など) は、渡された `name` に基づいて、登録されている適切なテスト関数を呼び出します。

3.  **`testprog/main.go` (新規)**:
    *   このファイルは、`testdata/testprog` ディレクトリ内のすべてのテスト関数を登録するためのエントリポイントです。
    *   `register(name string, f func())` 関数は、テスト関数を文字列名と対応する関数ポインタのマップに格納します。
    *   `main` 関数は、コマンドライン引数からテスト名を取得し、マップから対応する関数を見つけて実行します。これにより、一つの実行可能ファイルが複数の異なるテストロジックを実行できるようになります。

この新しい構造により、Goランタイムのテストは、コンパイル回数を劇的に減らし、テスト実行時間を大幅に短縮することに成功しました。

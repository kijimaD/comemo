# [インデックス 26930] ファイルの概要

このコミットは、Goリンカにおいて、すべての文字列データを単一のシンボルに結合する最適化を導入します。これにより、生成されるバイナリのサイズが削減され、特に`go.string."..."`形式の文字列シンボルの重複排除が可能になります。

## 元コミット内容

この変更は、Goリンカに`mergestrings`という新しいパスを導入します。このパスは、到達可能性解析（reachability analysis）の後に実行され、到達可能なすべての`go.string."..."`形式の文字データシンボルを単一のシンボルに結合します。この最適化により、`juju`バイナリのサイズが1.2MB（1.5%）削減され、DWARF情報なしでビルドされた`cmd/go`のサイズが0.5%削減されるなど、バイナリサイズの縮小効果が確認されています。リンカの速度には顕著な影響はありません。

## 変更の背景

Goプログラムがコンパイルされリンクされる際、文字列リテラルは通常、個別の読み取り専用データセクションに配置され、それぞれが`go.string."..."`のような名前を持つシンボルとして表現されます。プログラム内で多数の異なる文字列リテラルが使用される場合、これらの個々のシンボルがバイナリ内に分散して存在することになります。

このアプローチにはいくつかの問題がありました。

1.  **バイナリサイズの増大**: 各文字列が独自のシンボルとして扱われるため、シンボルごとのオーバーヘッド（ヘッダ情報、アライメントなど）が発生し、全体としてバイナリサイズが不必要に大きくなる可能性がありました。特に、短い文字列が多数存在する場合にこの影響は顕著です。
2.  **重複排除の困難さ**: 異なる場所で同じ文字列リテラルが使用されていても、リンカがそれらを効率的に重複排除することが難しい場合があります。個別のシンボルとして扱われるため、リンカはそれらが同じデータを持つことを認識しにくいのです。
3.  **メモリ効率の低下**: 実行時にこれらの文字列がメモリにロードされる際、断片化されたデータとして扱われることで、キャッシュ効率の低下やメモリ使用量の増大につながる可能性がありました。

このコミットは、これらの問題を解決するために、すべての文字列データを一つの大きなシンボルに集約することで、バイナリサイズの削減と効率的なデータ管理を目指しています。特に、`juju`のような大規模なGoアプリケーションで顕著なサイズ削減効果が見られたことから、この最適化の重要性が伺えます。

## 前提知識の解説

このコミットの理解には、以下のGoリンカの概念と用語に関する知識が必要です。

*   **Goリンカ (`cmd/link`)**: Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリやライブラリを生成するツールです。シンボルの解決、メモリレイアウトの決定、リロケーションの適用など、多くの重要なタスクを実行します。
*   **シンボル (`LSym`)**: プログラム内の名前付きエンティティ（関数、グローバル変数、文字列リテラルなど）を表すリンカ内部のデータ構造です。各シンボルは、その名前、型、サイズ、データ、およびリロケーション情報などを持っています。
*   **リロケーション (`Reloc`)**: リンカがシンボルを最終的なメモリ位置に配置する際に、コードやデータ内の参照を修正するための情報です。例えば、ある関数が別のグローバル変数を参照している場合、その参照はリロケーションとして記録され、リンカがグローバル変数の最終アドレスを決定した後に修正されます。
*   **`go.string."..."`シンボル**: Goリンカが文字列リテラルを表現するために内部的に使用するシンボル名です。例えば、`"hello"`という文字列リテラルは`go.string."hello"`のようなシンボルとして扱われます。これらのシンボルは、文字列の実際のバイトデータを含んでいます。
*   **到達可能性解析 (Reachability Analysis)**: リンカの重要なフェーズの一つで、プログラムの実行に必要なコードとデータ（シンボル）を特定します。到達可能なシンボルのみが最終的なバイナリに含まれ、到達不可能なシンボルは破棄されます。これにより、不要なコードやデータがバイナリに含まれるのを防ぎます。
*   **`AttrReachable`**: シンボルが到達可能であるかどうかを示す属性です。リンカは、この属性が設定されているシンボルのみを処理対象とします。
*   **`obj.SGOSTRING`**: Goリンカ内部で定義されているシンボルタイプの一つで、Goの文字列データであることを示します。
*   **`BuildmodeShared`**: Goのビルドモードの一つで、共有ライブラリ（`.so`や`.dylib`）を生成する際に使用されます。共有ライブラリでは、シンボルの扱いが通常の実行可能バイナリとは異なる場合があるため、特定の最適化が適用されないことがあります。

## 技術的詳細

このコミットで導入された`mergestrings`関数は、Goリンカの処理パイプラインにおいて、到達可能性解析の後に実行されます。その主な目的は、プログラム内で使用されるすべての文字列リテラルデータを効率的に集約し、バイナリサイズを削減することです。

具体的な処理フローは以下の通りです。

1.  **共有ライブラリビルドモードのスキップ**:
    `if Buildmode == BuildmodeShared { return }`
    共有ライブラリ（`BuildmodeShared`）をビルドしている場合は、この最適化をスキップします。共有ライブラリでは、文字列データの扱いが異なる可能性があり、この最適化が適切でないか、あるいは別の最適化パスが存在するためと考えられます。

2.  **データ構造の初期化**:
    *   `strs := make([]*LSym, 0, 256)`: 収集された文字列シンボル（`go.string."..."`）を格納するためのスライス。
    *   `seenStr := make(map[string]bool, 256)`: 既に`strs`スライスに追加された文字列シンボルの名前を追跡するためのマップ。重複追加を防ぎます。
    *   `relocsToStrs := make(map[*LSym][]*Reloc, 256)`: 各文字列シンボルを参照するリロケーションを格納するためのマップ。後でリロケーションのターゲットを更新するために使用されます。
    *   `size := 0`: すべての文字列データの合計バイトサイズを追跡します。

3.  **文字列シンボルとリロケーションの収集**:
    リンカが認識するすべてのシンボル（`Ctxt.Allsym`）をイテレートします。
    *   `if !s.Attr.Reachable() || s.Attr.Special() { continue }`: 到達可能でないシンボルや特殊なシンボルはスキップします。これは、到達可能性解析の後にこのパスが実行されるため、不要なシンボルを処理しないようにするためです。
    *   各シンボル`s`のリロケーション`r`を調べます。
    *   `if r.Sym == nil { continue }`: リロケーションがシンボルを参照していない場合はスキップします。
    *   `if !seenStr[r.Sym.Name]`: リロケーションが参照するシンボルがまだ処理されていない場合。
        *   `if !strings.HasPrefix(r.Sym.Name, "go.string.") { continue }`: シンボル名が`go.string.`で始まらない場合はスキップします。これは文字列リテラルシンボルを特定するためです。
        *   `if strings.HasPrefix(r.Sym.Name, "go.string.hdr") { continue }`: `go.string.hdr`で始まるシンボルはスキップします。これらは文字列データ自体ではなく、文字列ヘッダ（ポインタと長さ）を表すシンボルであり、結合の対象外です。
        *   `strs = append(strs, r.Sym)`: 該当する文字列シンボルを`strs`スライスに追加します。
        *   `seenStr[r.Sym.Name] = true`: シンボル名を`seenStr`マップに記録します。
        *   `size += len(r.Sym.P)`: シンボルのデータ長を合計サイズ`size`に加算します。
    *   `relocsToStrs[r.Sym] = append(relocsToStrs[r.Sym], r)`: 現在のリロケーション`r`を、それが参照する文字列シンボル`r.Sym`に関連付けて`relocsToStrs`マップに格納します。

4.  **すべての文字列データを単一シンボルに結合し、リロケーションを更新**:
    *   `alldata := Linklookup(Ctxt, "go.string.alldata", 0)`: `go.string.alldata`という新しいシンボルを作成または検索します。これがすべての文字列データを格納する単一のシンボルになります。
    *   `alldata.Type = obj.SGOSTRING`: 新しいシンボルのタイプを`SGOSTRING`に設定します。
    *   `alldata.Attr |= AttrReachable`: 新しいシンボルを到達可能としてマークします。
    *   `alldata.Size = int64(size)`: 新しいシンボルのサイズを、収集したすべての文字列データの合計サイズに設定します。
    *   `alldata.P = make([]byte, 0, size)`: 新しいシンボルのデータスライスを初期化します。

    収集された各文字列シンボル`str`について以下の処理を行います。
    *   `off := len(alldata.P)`: 現在の`alldata.P`の長さ（オフセット）を取得します。これは、現在の文字列データが`alldata`シンボル内でどこから始まるかを示します。
    *   `alldata.P = append(alldata.P, str.P...)`: 現在の文字列シンボル`str`のデータ`str.P`を、`alldata`シンボルのデータスライス`alldata.P`の末尾に追加します。
    *   `str.Attr.Set(AttrReachable, false)`: 元の文字列シンボル`str`を到達不可能としてマークします。これにより、リンカは最終的なバイナリにこの個別の文字列シンボルを含めなくなります。
    *   `for _, r := range relocsToStrs[str]`: 現在の文字列シンボル`str`を参照していたすべてのリロケーション`r`をイテレートします。
        *   `r.Add += int64(off)`: リロケーションのオフセット`r.Add`に、`alldata`シンボル内での現在の文字列データの開始オフセット`off`を加算します。これにより、リロケーションが`alldata`シンボル内の正しい位置を指すようになります。
        *   `r.Sym = alldata`: リロケーションが参照するシンボルを、元の個別の文字列シンボルから新しい結合されたシンボル`alldata`に更新します。

この一連の処理により、個々の文字列シンボルは`go.string.alldata`という単一の大きなシンボルに統合され、それらを参照していたすべてのリロケーションも新しいシンボル内の正しいオフセットを指すように修正されます。結果として、バイナリサイズが削減され、文字列データの管理が効率化されます。

## コアとなるコードの解説

`mergestrings`関数の実装は、Goリンカの内部構造とシンボル管理のメカニズムを深く利用しています。

1.  **シンボルとリロケーションの走査**:
    `Ctxt.Allsym`を走査することで、リンカが認識するすべてのシンボルにアクセスします。これは、Goリンカがプログラム全体のシンボル情報をどのように管理しているかを示しています。
    各シンボルの`s.R`（リロケーションのスライス）を調べることで、他のシンボルへの参照を特定します。これは、リンカがコードやデータ間の依存関係をどのように追跡しているかを示します。

2.  **文字列シンボルの識別**:
    `strings.HasPrefix(r.Sym.Name, "go.string.")`というチェックは、Goコンパイラが文字列リテラルに対して特定の命名規則（`go.string.`プレフィックス）を使用していることを前提としています。これにより、リンカは文字列データと他の種類のデータを区別できます。
    `strings.HasPrefix(r.Sym.Name, "go.string.hdr")`の除外は、文字列データ自体ではなく、文字列のランタイム表現（ポインタと長さ）を扱うシンボルが存在することを示唆しています。これらのシンボルは、文字列データが結合された後も、結合されたシンボル内の正しいオフセットを指すように更新される必要がありますが、データ結合の対象ではありません。

3.  **新しい結合シンボルの作成**:
    `Linklookup(Ctxt, "go.string.alldata", 0)`は、リンカのコンテキスト（`Ctxt`）を使用して、新しいシンボルを作成または既存のシンボルを検索する標準的な方法です。`"go.string.alldata"`という名前は、このシンボルがすべての文字列データを集約する目的であることを明確に示しています。
    `alldata.Type = obj.SGOSTRING`は、この新しいシンボルがGoの文字列データを含むことをリンカに伝えます。これにより、リンカは適切な処理（例えば、読み取り専用データセクションへの配置）を行うことができます。

4.  **データ結合とリロケーションの更新**:
    `alldata.P = append(alldata.P, str.P...)`は、Goのスライス操作を利用して、個々の文字列データを効率的に一つのバイトスライスに結合しています。
    `r.Add += int64(off)`と`r.Sym = alldata`は、リロケーションの核心的な更新です。元のリロケーションは個別の文字列シンボルを指していましたが、この変更により、結合された`alldata`シンボル内の正しいオフセットを指すように修正されます。これは、リンカがバイナリ内の参照をどのように解決し、修正するかを示す典型的な例です。
    `str.Attr.Set(AttrReachable, false)`は、元の個別の文字列シンボルが不要になったことをリンカに通知し、最終バイナリから除外されるようにします。

このコードは、Goリンカがバイナリサイズを最適化するために、シンボルレベルでどのようにデータを再編成し、参照を修正するかを示す優れた例です。

# [インデックス 26877] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) 形式変換フェーズにおいて、静的な分岐予測の調整ロジックを導入するものです。具体的には、ループ、異常終了（パニック）、関数呼び出し、およびリターンといったコードパターンに基づいて、分岐の「起こりやすさ」（likeliness）を予測し、それに応じてブロックの順序付けを最適化します。これにより、CPUの分岐予測器の効率を高め、結果としてプログラムの実行性能を向上させることを目指します。

## 変更の背景

この変更の背景には、現代のCPUアーキテクチャにおける「分岐予測」の重要性があります。CPUは、プログラムの実行フローが分岐する際に、次に実行されるであろう命令を事前に予測し、パイプラインにロードすることで性能を向上させます。しかし、予測が外れると、パイプラインがフラッシュされ、ペナルティが発生し、性能が大幅に低下します。

Goコンパイラは、プログラムをSSA形式に変換し、様々な最適化パスを適用します。このコミット以前は、分岐の起こりやすさに関する静的な情報が不足しており、コンパイラが生成するコードのブロック順序が、CPUの分岐予測器にとって最適でない可能性がありました。特に、ループの継続、関数からの異常終了（パニック）、関数呼び出し、および関数のリターンといった一般的なパターンには、経験則に基づいた予測が可能です。

このコミットは、これらのパターンを識別し、コンパイラがより賢明なブロック順序付けを行うためのヒント（分岐予測情報）を生成することを目的としています。コミットメッセージにもあるように、この変更はIssue #11451を修正するものです。Issue #11451は、Goコンパイラが分岐予測のヒントを生成しないことによる性能上の懸念を提起していました。

当初のバージョンでは、この最適化が実際のコードの性能に大きな影響を与えないことが判明しましたが、コンパイラ出力の正規化や、将来的なレジスタ割り当ての改善のための情報源として、このパスを維持する価値があると判断されました。そのため、このパスのオーバーヘッドを最小限に抑えるように調整されています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において中間表現として広く用いられるプログラム表現形式です。この形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラも、ソースコードをSSA形式に変換した後、様々な最適化パスを適用します。

### 2. 分岐予測 (Branch Prediction)

CPUの分岐予測器は、条件分岐（`if`文、`for`ループなど）が発生した際に、次に実行されるコードパスを推測するハードウェアコンポーネントです。正確な予測はパイプラインの効率を最大化し、誤った予測は性能低下を招きます。コンパイラは、コードの静的な分析に基づいて、分岐予測器がより正確な予測を行えるように、コードブロックの配置順序を調整したり、分岐予測のヒント（例: `__builtin_expect`のようなコンパイラ組み込み関数）を埋め込んだりすることがあります。

### 3. 基本ブロック (Basic Block)

基本ブロックは、プログラムの制御フローグラフ (Control Flow Graph, CFG) における連続した命令のシーケンスで、入り口は一つ、出口は一つという特性を持ちます。分岐予測は、これらの基本ブロック間の遷移において行われます。

### 4. ループネスト解析 (Loop Nest Analysis)

コンパイラは、プログラム内のループ構造を識別し、そのネスト関係（どのループがどのループの内側にあるか）を解析します。この情報は、ループ最適化や、今回の分岐予測のように、ループの挙動に関するヒューリスティックを適用する際に非常に重要です。

### 5. ポストオーダー順序 (Postorder Traversal)

グラフ（この場合は制御フローグラフ）のノードを訪問する順序の一つです。ポストオーダー順序では、ノードを訪問する前にその全ての子ノードを訪問します。このコミットでは、`likelyadjust`パスがポストオーダー順序でブロックを処理していることが示唆されています。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドに`likelyadjust`という新しい最適化パスを追加します。このパスの目的は、プログラムの制御フローグラフ（CFG）内の各基本ブロックに対して、その分岐が「起こりやすい」か「起こりにくい」かという静的な予測情報を付与することです。この情報は、後続のブロックレイアウトパス（`layout`パス）が、CPUの分岐予測器にとって最適なコードブロックの物理的な配置を決定する際に利用されます。

`likelyadjust`パスは、以下のヒューリスティックに基づいて分岐予測を行います。

1.  **ループの継続 (loop/not-loop):**
    *   ループの内部に留まる分岐は「起こりやすい (likely)」と予測されます。
    *   ループから脱出する分岐は「起こりにくい (unlikely)」と予測されます。
    *   これは、`loopnestfor`関数によって構築されるループネスト情報 (`b2l`配列) を利用して判断されます。

2.  **異常終了 (abnormal-exit/not):**
    *   `BlockExit`（パニックなどによる異常終了）に至るパスは「非常に起こりにくい (very unlikely)」と予測されます。これは`blEXIT`という高い「unlikeliness」値で表現されます。

3.  **関数呼び出し (call/not-call):**
    *   関数呼び出しを含む分岐は、呼び出しを含まない分岐よりも「起こりにくい (unlikely)」と予測されます。これは`blCALL`という値で表現されます。

4.  **リターン (ret/default):**
    *   関数からのリターン (`BlockRet`, `BlockRetJmp`) は「起こりにくい (unlikely)」と予測されます。これは`blRET`という値で表現されます。

このパスは、`certain`と`local`という2つの配列を使用して、各ブロックの「unlikeliness」スコアを計算します。
*   `certain[b.ID]`：ブロック`b`から到達可能なすべてのパスで発生する可能性のある、最も高い（最も起こりにくい）unlikelinessスコア。
*   `local[b.ID]`：ブロック`b`自体の特性に基づくunlikelinessスコア。

これらのスコアは、ポストオーダー順序でブロックを走査しながら計算されます。これにより、後続のブロックのunlikelinessが現在のブロックのunlikelinessに伝播されます。

2つの後続ブロックを持つ分岐の場合、`likelyadjust`は以下の優先順位で予測を適用します。
1.  **ループ構造に基づく予測:** どちらかの後続ブロックがループの外側にある場合、ループ内に留まる方を`BranchLikely`とします。
2.  **`certain`スコアに基づく予測:** `certain`スコアが高い（起こりにくい）方の後続ブロックを`BranchUnlikely`とします。
3.  **`local`スコアに基づく予測:** `local`スコアが高い（起こりにくい）方の後続ブロックを`BranchUnlikely`とします。

既存の分岐予測情報 (`b.Likely`) が既に存在する場合、このパスはそれを尊重し、`BranchUnknown`の場合にのみ新しい予測を適用します。また、デバッグフラグ (`-d=ssa/likelyadjust/debug`) を使用することで、予測の動作を詳細にログ出力できるようになっています。

コミットメッセージにあるように、このパスは`make.bash`のコンパイル時間に対して約0.75秒のオーバーヘッドを追加しますが、これは全体の200秒に対して非常に小さい値です。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/likelyadjust.go`

このファイルは、GoコンパイラのSSAバックエンドにおける分岐予測調整の心臓部です。

#### `loop` および `loopnest` 構造体

*   `loop`構造体は、ループのヘッダーブロック、外側のループへの参照、ループ内のブロック数、および内側ループであるかどうかのフラグを保持します。
*   `loopnest`構造体は、関数全体のループネスト情報をカプセル化し、各ブロックが属するループ (`b2l`)、ポストオーダー順序のブロックリスト (`po`)、支配木 (`sdom`)、および検出されたすべてのループのリスト (`loops`) を含みます。

#### `likelyadjust` 関数

この関数が、分岐予測の主要なロジックを実装しています。

1.  **`certain` と `local` 配列の初期化:**
    *   `certain`配列は、あるブロックから到達可能なすべてのパスで発生する可能性のある、最も「起こりにくい」イベントのスコアを追跡します。
    *   `local`配列は、そのブロック自体が持つ「起こりにくい」イベントのスコアを追跡します。
    *   これらのスコアは`int8`型で、`blDEFAULT` (0) から`blEXIT` (3) までのランク付けされた値を使用します。値が大きいほど「起こりにくい」ことを意味します。

2.  **ループネスト情報の取得:**
    *   `loopnestfor(f)`を呼び出して、現在の関数`f`のループネスト情報を取得します。

3.  **ポストオーダー順序でのブロック走査:**
    *   `for _, b := range po` ループにより、関数内の基本ブロックをポストオーダー順序（子孫ブロックが先に処理される）で走査します。これにより、後続ブロックの`certain`および`local`スコアが計算済みであることを利用できます。

4.  **ブロックの種類に基づく `local` および `certain` スコアの更新:**
    *   `switch b.Kind` ステートメントで、ブロックの種類に応じて`local`および`certain`スコアを更新します。
        *   `BlockExit`: パニックなどの異常終了を表すため、`local`と`certain`を`blEXIT`（最も起こりにくい）に設定します。
        *   `BlockRet`, `BlockRetJmp`: 関数からのリターンを表すため、`local`と`certain`を`blRET`に設定します。
        *   `BlockCall`: 関数呼び出しを含むため、`local`を`blCALL`に設定します。`certain`は、後続ブロックの`certain`スコアと`blCALL`の最大値を取ります。これは、呼び出しを含むパスは少なくとも`blCALL`のunlikelinessを持つことを意味します。
        *   `default`ケース（通常の分岐や単一後続ブロック）:
            *   単一後続ブロックの場合、`certain`は後続ブロックの`certain`を継承します。
            *   二つの後続ブロックを持つ場合、`certain`は両後続ブロックの`certain`スコアの最小値を取ります。これは、最も「起こりにくい」イベントを回避するパスが存在する可能性があるためです。

5.  **分岐予測の適用:**
    *   二つの後続ブロックを持つブロックの場合、`b.Likely`フィールドに分岐予測を設定します。
    *   **ループヒューリスティック:**
        *   現在のブロック`b`とその後続ブロックが属するループ (`l`, `l0`, `l1`) を比較します。
        *   ループから外に出る分岐 (`l0 == nil` または `l1 == nil`) は`BranchUnlikely`、ループ内に留まる分岐 (`l == l0` または `l == l1`) は`BranchLikely`と予測します。
    *   **`certain` および `local` スコアに基づくヒューリスティック:**
        *   ループヒューリスティックが適用できない場合、`certain`スコアが高い方（より起こりにくい方）を`BranchUnlikely`とします。
        *   `certain`スコアが同じ場合、`local`スコアが高い方（より起こりにくい方）を`BranchUnlikely`とします。
    *   **既存の予測の尊重:** `b.Likely`が`BranchUnknown`の場合にのみ、新しい予測を適用します。既存の予測は上書きしません。

#### `loopnestfor` 関数

この関数は、制御フローグラフからループネスト構造を構築します。

1.  **ポストオーダー順序と支配木の取得:**
    *   `postorder(f)`でブロックのポストオーダー順序を取得します。
    *   `dominators(f)`と`newSparseTree(f, dom)`で支配木を構築します。

2.  **ループの識別:**
    *   ポストオーダー順序で各ブロック`b`を走査します。
    *   `b`の後続ブロック`bb`が`b`を支配する場合 (`sdom.isAncestorEq(bb, b)`)、`bb`はループヘッダーであると判断されます。
    *   各ブロックが属する最も内側のループを`b2l`配列に記録します。
    *   `sdom.outerinner`関数を使用して、ループ間の内側/外側関係を構築します。

### `test/opt_branchlikely.go`

このテストファイルは、`likelyadjust`パスが意図通りに動作し、適切な分岐予測ヒントを生成することを確認します。
`// ERROR "Branch prediction rule ..."`というコメントは、`errorcheck`ツールがコンパイラのデバッグ出力 (`-d=ssa/likelyadjust/debug=1`) を解析し、指定された文字列（分岐予測ルール）がログに出力されることを期待していることを示します。
例えば、`for i := 0; i < x; i++ { // ERROR "Branch prediction rule stay in loop"` は、このループの継続分岐が「ループ内に留まる」と予測されることをテストしています。
また、`if y == 0 { // ERROR "Branch prediction rule default < call"` は、関数呼び出しを含む分岐が、呼び出しを含まない分岐よりも「起こりにくい」と予測されることをテストしています。

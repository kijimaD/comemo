## 元コミット内容

このコミットは、Goランタイムのメモリ統計（`memstats`）の修正を目的としています。

主な問題点は以下の通りです。
1.  **新しく割り当てられたメモリの`inuse`からの減算**: 新しくメモリが割り当てられた際、そのメモリは`inuse`（使用中メモリ）に一度も加算されていないにもかかわらず、`inuse`から減算されていました。これは論理的な矛盾であり、`inuse`の値を不正確にしていました。
2.  **スパンの残り（leftovers）の`inuse`および`idle`からの減算**: メモリブロック（スパン）の一部が使用され、残りが「残り」として扱われる場合、その残りが`inuse`と`idle`（アイドル状態のメモリ）の両方から減算されていました。しかし、これらの「残り」は元々`inuse`や`idle`に加算されていなかったため、これもまた不正確な統計値の原因となっていました。

このコミットは、これらの問題を修正し、Goランタイムのメモリ統計の正確性を向上させます。関連するIssueとして、#8544と#8430が挙げられています。

## 変更の背景

Goランタイムは、プログラムのメモリ使用状況を追跡し、`runtime.MemStats`構造体を通じてその統計情報を提供します。この情報は、Goプログラムのパフォーマンスチューニング、メモリリークの検出、およびシステムリソースの監視において非常に重要です。

しかし、このコミットが修正しようとしている問題は、`MemStats`の計算ロジックに潜むバグでした。具体的には、メモリの割り当てと解放の際に、`heap_inuse`（ヒープで使用中のメモリ）と`heap_idle`（ヒープでアイドル状態のメモリ）という重要な統計値が正しく更新されていませんでした。

-   **`heap_inuse`の不正確さ**: 新しいメモリがヒープに割り当てられた際、そのメモリは実際に使用中になるにもかかわらず、`heap_inuse`に正しく加算されていませんでした。さらに、一部のシナリオでは、まだ`heap_inuse`に計上されていないメモリが誤って減算されるという逆の操作が行われていました。
-   **`heap_idle`の不正確さ**: 同様に、メモリブロックが解放され、アイドル状態になった際に、`heap_idle`に正しく加算されない、または誤って減算されるケースがありました。特に、スパンの「残り」部分の処理において、この問題が顕著でした。

これらの不正確な計算は、`runtime.ReadMemStats`関数を通じて取得されるメモリ統計値が現実のメモリ使用状況と乖離する原因となっていました。これにより、開発者はGoプログラムのメモリプロファイルを正確に把握することが困難になり、デバッグや最適化の妨げとなっていました。

このコミットは、これらの根本的な計算ミスを特定し、`MHeap_FreeSpanLocked`関数の呼び出し箇所と内部ロジックを修正することで、`memstats`の正確性を回復させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理に関するいくつかの基本的な概念を理解しておく必要があります。

1.  **Goのメモリ管理（GC）**: Goはガベージコレクション（GC）によってメモリを自動的に管理します。開発者は手動でメモリを解放する必要がありません。GoのGCは、ヒープメモリを効率的に管理し、不要になったオブジェクトを回収します。

2.  **`runtime.MemStats`**: これはGoプログラムのメモリ使用状況に関する詳細な統計情報を提供する構造体です。`runtime.ReadMemStats`関数を呼び出すことで、この構造体のインスタンスを取得できます。主要なフィールドには以下のようなものがあります。
    *   `Alloc`: 現在ヒープに割り当てられているオブジェクトによって使用されているバイト数。
    *   `TotalAlloc`: プログラムの開始以降に割り当てられた合計バイト数。
    *   `Sys`: オペレーティングシステムから取得された合計バイト数。
    *   `HeapAlloc`: ヒープに割り当てられているオブジェクトによって使用されているバイト数（`Alloc`と同じ）。
    *   `HeapSys`: ヒープのためにOSから取得されたバイト数。
    *   `HeapIdle`: ヒープ内でアイドル状態（未使用でOSに解放されていない）のバイト数。
    *   `HeapInuse`: ヒープ内で使用中（オブジェクトが割り当てられている）のバイト数。
    *   `HeapReleased`: OSに解放されたヒープメモリのバイト数。
    *   `StackInuse`: スタックで使用中のバイト数。
    *   `StackSys`: スタックのためにOSから取得されたバイト数。
    *   `MSpanInuse`, `MSpanSys`: メモリスパン管理構造体で使用中のバイト数。
    *   `MCacheInuse`, `MCacheSys`: メモリキャッシュ管理構造体で使用中のバイト数。
    *   `GCSys`: GCメタデータのためにOSから取得されたバイト数。
    *   `OtherSys`: その他のシステム割り当て。

3.  **ヒープとスパン（Heap and MSpan）**:
    *   Goのヒープは、`MHeap`という構造体によって管理されます。
    *   ヒープメモリは、`MSpan`と呼ばれる連続したページブロックに分割されます。`MSpan`は、特定のサイズのオブジェクトを格納するために使用されるか、またはアイドル状態のメモリとして管理されます。
    *   `PageShift`: ページサイズを表すビットシフト値です。`1 << PageShift`で実際のページサイズ（通常は8KB）が得られます。メモリのサイズは通常、ページ単位で計算されます。

4.  **`MHeap_FreeSpanLocked`関数**: この関数は、指定された`MSpan`をヒープに解放（返却）するために使用されます。この関数が呼び出されると、スパンの状態が`MSpanFree`に設定され、必要に応じて隣接するフリーなスパンと結合されます。このコミットの核心は、この関数が`memstats`を更新する方法の変更にあります。

5.  **`scavenge`関数**: これは、アイドル状態のヒープメモリをOSに解放（リリース）する役割を持つ関数です。`memstats.heap_released`などの統計値は、このスカベンジングプロセスによって更新されます。

これらの概念は、Goランタイムがどのようにメモリを管理し、その統計を報告するかを理解する上で不可欠です。このコミットは、これらの統計が正確に反映されるように、内部のメモリ管理ロジックを調整しています。

## 技術的詳細

このコミットの技術的な核心は、`MHeap_FreeSpanLocked`関数のシグネチャ変更と、それに伴う`memstats`の更新ロジックの修正にあります。

**変更前（問題点）**:
`MHeap_FreeSpanLocked`関数は、スパンを解放する際に常に`mstats.heap_inuse`からスパンのサイズを減算し、`mstats.heap_idle`に加算していました。しかし、この関数が呼び出される文脈によっては、解放されるスパンが元々`heap_inuse`に計上されていなかったり、`heap_idle`に加算されるべきでなかったりするケースがありました。

具体的には、コミットメッセージに記載されている2つの問題がこれに該当します。
1.  **新しく割り当てられたメモリ**: `MHeap_Grow`関数内で新しいスパンが作成され、すぐに`MHeap_FreeSpanLocked`に渡される場合がありました。このスパンはまだ`heap_inuse`に加算されていないにもかかわらず、`MHeap_FreeSpanLocked`内で`heap_inuse`から減算されていました。
2.  **スパンの残り（leftovers）**: `MHeap_AllocSpanLocked`が大きなスパンから一部を割り当て、残りを`MHeap_FreeSpanLocked`に返す場合、その残りは`heap_inuse`にも`heap_idle`にも計上されていないにもかかわらず、両方から減算されていました。

これらの誤った操作により、`heap_inuse`と`heap_idle`の値が不正確になり、結果として`MemStats`全体が信頼できないものになっていました。

**変更後（修正内容）**:
このコミットでは、`MHeap_FreeSpanLocked`関数のシグネチャに2つの新しいブール型引数が追加されました。
```c
static void MHeap_FreeSpanLocked(MHeap *h, MSpan *s, bool acctinuse, bool acctidle)
```
*   `acctinuse`: このスパンの解放が`heap_inuse`の減算に影響を与えるべきかどうかを示すフラグ。`true`の場合のみ`heap_inuse`から減算されます。
*   `acctidle`: このスパンの解放が`heap_idle`の加算に影響を与えるべきかどうかを示すフラグ。`true`の場合のみ`heap_idle`に加算されます。

これにより、`MHeap_FreeSpanLocked`の呼び出し元が、その文脈に応じて`heap_inuse`と`heap_idle`の更新を制御できるようになりました。

**具体的な修正箇所と意図**:

1.  **`MHeap_AllocSpanLocked`内の呼び出し**:
    *   `MHeap_AllocSpanLocked`が大きなスパンから一部を切り出し、残りを`t`として`MHeap_FreeSpanLocked`に渡す箇所では、`acctinuse`と`acctidle`の両方を`false`に設定しています。
        ```c
        MHeap_FreeSpanLocked(h, t, false, false);
        ```
        これは、`t`（残り部分）が元々`heap_inuse`にも`heap_idle`にも計上されていないため、解放時にこれらの統計値を変更すべきではないという意図です。

2.  **`MHeap_Grow`内の呼び出し**:
    *   `MHeap_Grow`が新しいスパン`s`をOSから取得し、それをヒープに解放する箇所では、`acctinuse`を`false`、`acctidle`を`true`に設定しています。
        ```c
        MHeap_FreeSpanLocked(h, s, false, true);
        ```
        これは、新しく取得したメモリはまだ`heap_inuse`には計上されていないが、アイドル状態のメモリとして`heap_idle`に加算されるべきであるという意図です。

3.  **`mheap_free`内の呼び出し**:
    *   `mheap_free`が使用中のスパン`s`を解放する箇所では、`acctinuse`と`acctidle`の両方を`true`に設定しています。
        ```c
        MHeap_FreeSpanLocked(h, s, true, true);
        ```
        これは、`s`が元々`heap_inuse`に計上されており、解放後はアイドル状態になるため、両方の統計値を更新すべきであるという意図です。

4.  **`runtime.MHeap_FreeStack`内の呼び出し**:
    *   スタックメモリのスパンを解放する箇所でも、`acctinuse`と`acctidle`の両方を`true`に設定しています。
        ```c
        MHeap_FreeSpanLocked(h, s, true, true);
        ```
        これは、スタックメモリも同様に`inuse`から`idle`へ状態が遷移するためです。

5.  **`scavenge`関数内の`MemStats`表示**:
    *   `scavenge`関数内でメモリ統計を表示する際に、直接`mstats`グローバル変数を使用するのではなく、`runtime.ReadMemStats(&stats)`を呼び出して最新の統計情報を取得するように変更されています。
        ```c
        runtime·ReadMemStats(&stats);
        // ...
        runtime·printf("scvg%d: inuse: %D, idle: %D, sys: %D, released: %D, consumed: %D (MB)\\n",
            k, stats.heap_inuse>>20, stats.heap_idle>>20, stats.heap_sys>>20,
            stats.heap_released>>20, (stats.heap_sys - stats.heap_released)>>20);
        ```
        これにより、表示される統計値が常に最新かつ正確なものとなることが保証されます。

これらの変更により、`heap_inuse`と`heap_idle`の計算が、メモリのライフサイクルにおける各段階でより正確に行われるようになり、`runtime.MemStats`の信頼性が大幅に向上しました。

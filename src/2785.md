## 変更の背景

このコミットは、Goランタイムのガベージコレクション (GC) プロセスにおける深刻なバグを修正するために行われました。具体的には、`make smoketest`というテストスイートが`cmd/gofmt`の実行中にクラッシュするという問題が発生していました。

この問題の根本原因は、GCがスタックをスキャンする際に使用するスタックポインタ (SP) の値が、実際に使用される時点までに古くなってしまうことにありました。GoのGCは、プログラムが使用しているメモリを特定するために、実行中のGoroutineのスタックを走査し、そこから参照されているオブジェクトをマークします。このスタック走査は`scanstack`関数によって行われます。

以前の実装では、GCの開始時に`gosave`関数を呼び出して現在のGoroutineのスタックポインタを`g->sched.sp`に保存していました。しかし、この`gosave`の呼び出しから、実際に`scanstack`関数がその保存された`g->sched.sp`を使用するまでの間に、ランタイム内部の処理（例えば、`stoptheworld()`や`starttheworld()`といったGoroutineのスケジューリングに関連する操作）によってスタックの状態が変化し、スタックポインタがずれてしまうことがありました。

結果として、`scanstack`は不正なスタック領域をスキャンしようとし、これがGCの誤動作やプログラムのクラッシュ（`make smoketest`の失敗）を引き起こしていました。このバグは、特に`cmd/gofmt`のようなツールが多くのGoroutineを生成し、GCが頻繁に実行されるような状況で顕在化したと考えられます。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoランタイムの概念について解説します。

*   **Goのガベージコレクション (GC)**:
    Go言語は自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。2009年当時のGoのGCは、現在の並行・低遅延GCとは異なり、よりシンプルな「ストップ・ザ・ワールド (Stop-The-World)」方式のマーク・アンド・スイープコレクタが主流でした。この方式では、GCが実行される間、全てのGoroutineの実行が一時停止されます。GCの主要なフェーズの一つに「マークフェーズ」があり、このフェーズでルートセット（グローバル変数、レジスタ、そして**Goroutineのスタック**）から到達可能なオブジェクトを特定します。

*   **スタックポインタ (SP)**:
    スタックポインタ (Stack Pointer, SP) は、CPUのレジスタの一つで、現在の関数呼び出しのスタックフレームの最上位（または最下位、アーキテクチャによる）を指します。関数が呼び出されると、引数、ローカル変数、リターンアドレスなどがスタックに積まれ、SPが更新されます。GCがスタックをスキャンする際には、このSPからスタックの基底アドレスまでを走査し、スタック上に存在するポインタ値を読み取って、それがヒープ上のオブジェクトを指しているかどうかを判断します。

*   **Goroutine (G)**:
    GoroutineはGo言語の軽量な実行単位であり、OSのスレッドよりもはるかに少ないリソースで生成・管理されます。各Goroutineは独自のスタックを持ち、このスタックは必要に応じて動的に拡張・縮小されます（セグメントスタック方式）。

*   **`g->sched.sp`**:
    `G`構造体はGoroutineの状態を保持しており、`sched`フィールドはそのGoroutineのスケジューリング情報を格納します。`g->sched.sp`は、Goroutineが実行を中断（プリエンプトされたり、システムコールに入ったり）した際に、その時点のスタックポインタを保存するために使用されます。これにより、Goroutineが再開される際に、中断した時点から正確に実行を再開できます。

*   **`scanstack`関数**:
    GoランタイムのGCにおいて、特定のGoroutineのスタックをスキャンする役割を担う関数です。この関数は、スタックの開始アドレスと終了アドレスを受け取り、その範囲内のメモリを走査して、ヒープ上のオブジェクトへのポインタを見つけ出し、それらをマークします。

*   **`gosave`関数**:
    `gosave`は、現在のGoroutineの実行コンテキスト（プログラムカウンタ `PC`、スタックポインタ `SP`、その他のレジスタ値など）を、指定された`gobuf`構造体（通常は`g->sched`）に保存するランタイム内部関数です。これは、Goroutineの切り替え（コンテキストスイッチ）や、GCのようにスタックの状態を一時的に保存する必要がある場面で利用されます。C言語の`setjmp`に似た機能を提供します。

*   **`Stktop`構造体**:
    Goの初期のランタイムでは、スタックは固定サイズではなく、必要に応じて小さなブロック（セグメント）を連結して拡張する「セグメントスタック」方式を採用していました。`Stktop`構造体は、これらのスタックセグメントの連結リストを管理するためのもので、各セグメントの基底アドレスや、前のスタックセグメントへのポインタ（`stk->stackbase`）などが含まれていました。`stk->gobuf.sp`は、スタックセグメントが切り替わる際に、前のセグメントの`gobuf`に保存されたスタックポインタを指します。

## 技術的詳細

このコミットの技術的な詳細な変更点は以下の通りです。

1.  **`gc`関数からの`gosave`呼び出しの削除**:
    `src/pkg/runtime/mgc0.c`内の`gc`関数から、`gosave(&g->sched);`という呼び出しが2箇所削除されました。

    ```diff
    +++ b/src/pkg/runtime/mgc0.c

     		throw("mheap locked during gc");
    @@ -230,7 +232,6 @@ gc(int32 force)
     		mstats.next_gc = mstats.inuse_pages+mstats.inuse_pages*gcpercent/100;
     	}
     	starttheworld();
    -	gosave(&g->sched);	// update g's stack pointer for debugging
     	semrelease(&gcsema);
     	m->gcing = 0;
     }
    ```
    この`gosave`は、GCがスタックをスキャンする前に現在のGoroutineのスタックポインタを`g->sched`に保存することを意図していました。しかし、`gosave`が呼び出された後、`stoptheworld()`や`starttheworld()`といったGoroutineのスケジューリング操作が挟まることで、スタックの状態が変化し、`g->sched.sp`に保存された値が古くなってしまう問題がありました。この削除により、GCが現在のGoroutineのスタックをスキャンする際に、`g->sched.sp`に依存するのではなく、よりリアルタイムなスタックポインタを使用する道が開かれました。

2.  **`scanstack`関数の引数とスタックポインタ取得ロジックの変更**:
    `src/pkg/runtime/mgc0.c`内の`scanstack`関数のシグネチャが`scanstack(G *g)`から`scanstack(G *gp)`に変更され、より汎用的な引数名になりました。そして、関数内部でのスタックポインタ`sp`の取得ロジックが大きく変更されました。
    ```diff
    --- a/src/pkg/runtime/mgc0.c
    +++ b/src/pkg/runtime/mgc0.c
    @@ -61,13 +61,16 @@ scanblock(int32 depth, byte *b, int64 n)
     }

     static void
    -scanstack(G *g)
    +scanstack(G *gp)
     {
     	Stktop *stk;
     	byte *sp;

    -	sp = g->sched.sp;
    -	stk = (Stktop*)g->stackbase;
    +	if(gp == g)
    +		sp = (byte*)&gp;
    +	else
    +		sp = gp->sched.sp;
    +	stk = (Stktop*)gp->stackbase;
     	while(stk) {
     		scanblock(0, sp, (byte*)stk - sp);
     		sp = stk->gobuf.sp;
    ```
    *   **`if(gp == g)`の追加**: これは、`scanstack`関数が現在実行中のGoroutine（`g`）のスタックをスキャンしているかどうかを判断する重要な分岐です。
        *   もし`gp == g`（つまり、現在実行中のGoroutineのスタックをスキャンしている）の場合、`sp = (byte*)&gp;`と設定されます。これは、`scanstack`関数自身のスタックフレーム内に存在する引数`gp`のアドレスをスタックポインタの開始点として使用することを意味します。現在実行中のGoroutineのスタックは常に最新の状態であるため、`g->sched.sp`のような過去に保存された値ではなく、現在のスタックポインタに近い値からスキャンを開始することで、スタックの不整合を回避します。
        *   `else`（つまり、他のGoroutine `gp`のスタックをスキャンしている）の場合、`sp = gp->sched.sp;`と設定されます。この場合、`gp`は現在実行中でないGoroutineであるため、そのGoroutineが最後に実行を中断した際に`g->sched.sp`に保存されたスタックポインタが正確な開始点となります。
    *   `stk = (Stktop*)gp->stackbase;`は、スキャン対象のGoroutineのスタック基底から`Stktop`構造体を取得し、スタックセグメントの連結リストを辿るために使用されます。

この修正により、`scanstack`関数は、スキャン対象のGoroutineが現在実行中であるか停止中であるかに応じて、常に最も正確なスタックポインタからスキャンを開始できるようになりました。これにより、スタックポインタのずれによるGCの誤動作が解消され、`make smoketest`のクラッシュが修正されました。

## コアとなるコードの解説

このコミットの核となる変更は、`src/pkg/runtime/mgc0.c`ファイル内の`gc`関数と`scanstack`関数に集中しています。

1.  **`gc`関数からの`gosave(&g->sched)`の削除**:
    `gc`関数はGoのガベージコレクションのメインエントリポイントです。以前のコードでは、GCの開始時と終了時に`gosave(&g->sched)`が呼び出されていました。これは、GC中に現在のGoroutineのスタックポインタを`g->sched.sp`に明示的に保存することを目的としていました。しかし、この`gosave`の呼び出しと、実際に`scanstack`がその保存された`sp`を使用するまでの間に、`stoptheworld()`や`starttheworld()`といったGoroutineのスケジューリング操作が実行され、スタックの状態が変化する可能性がありました。これにより、`g->sched.sp`に保存された値が古くなり、`scanstack`が不正なスタック領域をスキャンする原因となっていました。このコミットでは、これらの冗長で問題を引き起こす`gosave`の呼び出しを削除することで、この問題を根本的に解決しています。

2.  **`scanstack`関数のスタックポインタ取得ロジックの改善**:
    `scanstack`関数は、GCがGoroutineのスタックを走査してルートオブジェクトを特定する上で非常に重要な役割を担います。
    *   **引数の変更**: `scanstack(G *g)`から`scanstack(G *gp)`へと引数名が変更されました。これは機能的な変更というよりは、引数が現在のGoroutine `g`だけでなく、任意のGoroutine `gp`を指すことを明確にするためのものです。
    *   **条件分岐による`sp`の決定**: 最も重要な変更は、`sp`（スタックポインタ）の初期値を決定するための条件分岐が導入されたことです。
        ```c
        if(gp == g)
            sp = (byte*)&gp;
        else
            sp = gp->sched.sp;
        ```
        *   `if(gp == g)`: この条件は、`scanstack`が現在実行中のGoroutine（つまり、`scanstack`自身が実行されているGoroutine）のスタックをスキャンしている場合に真となります。この場合、`sp`は`gp`引数のアドレス（`&gp`）に設定されます。`gp`引数は`scanstack`関数のスタックフレーム上に存在するため、そのアドレスは現在のスタックポインタに非常に近い値となります。これにより、現在実行中のGoroutineのスタックをスキャンする際には、`gosave`で保存された可能性のある古い`g->sched.sp`ではなく、リアルタイムの正確なスタックポインタからスキャンを開始できるようになります。
        *   `else`: この条件は、`scanstack`が現在実行中でない他のGoroutine `gp`のスタックをスキャンしている場合に真となります。この場合、`sp`は`gp->sched.sp`に設定されます。他のGoroutineは実行を中断しているため、`gp->sched.sp`にはそのGoroutineが中断した時点の正確なスタックポインタが保存されており、これがスタック走査の開始点として適切です。

これらの変更により、`scanstack`は常にスキャン対象のGoroutineの状態に応じて最適なスタックポインタの開始点を選択できるようになり、GCがスタックを正確にスキャンできるようになりました。これにより、スタックポインタの不整合によるGCのバグが解消され、`make smoketest`のクラッシュが修正されました。

`src/pkg/runtime/amd64/traceback.c`の変更は、`printf`のコメントアウトされた行の追加であり、これはデバッグ目的で一時的に追加されたものと考えられ、このコミットの主要な修正とは直接関係ありません。

## 変更の背景

このコミットは、GoコンパイラがSSA (Static Single Assignment) フォームを導入した際に生じた、特定のベンチマークにおけるパフォーマンスの乖離を解消することを目的としています。特に`AppendInPlace`ベンチマークにおいて、SSAが有効な場合とそうでない場合で、以前は20%もの性能低下が見られました。これは、SSAが導入される前のコンパイラ（非SSA）と比較して、SSAが複合リテラル（`struct`や`array`などの初期化）の扱いにおいて、より保守的なアプローチを取っていたためと考えられます。

具体的には、SSAは最適化を適用する際に、式が副作用を持つかどうかを厳密に評価します。複合リテラルが「静的」である（つまり、その構成要素がすべて定数であり、実行時に副作用を伴う操作を含まない）場合でも、SSAはこれを副作用を持つ可能性があると見なし、最適化を妨げていた可能性があります。このコミットは、静的な複合リテラルが本質的に副作用を持たないことをコンパイラに明示することで、SSAバックエンドがより積極的な最適化（例えば、スタック割り当ての促進や不要なコード生成の削減）を行えるようにし、パフォーマンスの改善を図っています。

この変更は、以前の関連する変更（CL 22192）を拡張するものであり、`AppendInPlace`ベンチマークにおける性能低下を解消し、非SSAコンパイラと同等かそれ以上の性能を達成することを目指しています。提示されたベンチマーク結果は、この変更によって約4%から7%の性能向上が見られ、以前の20%の性能低下が解消されたことを示しています。

## 前提知識の解説

### Goコンパイラ (cmd/compile)

`cmd/compile`はGo言語の公式コンパイラであり、Goのソースコードを機械語に変換する役割を担っています。コンパイルプロセスは、字句解析、構文解析、型チェック、中間表現 (IR) の生成、最適化、コード生成といった複数のフェーズに分かれています。このコミットが関連するのは、主に中間表現の最適化フェーズです。

### SSA (Static Single Assignment) フォーム

SSA (Static Single Assignment) フォームは、コンパイラの最適化において広く用いられる中間表現の一種です。SSAでは、プログラム中の全ての変数が一度だけ代入されるという特性を持ちます。これにより、データの流れが明確になり、コンパイラは以下のような高度な最適化をより容易に適用できるようになります。

*   **データフロー解析の簡素化**: 変数の定義と使用の関係が明確になるため、コンパイラは値がどこで生成され、どこで使われているかを効率的に追跡できます。
*   **最適化の促進**: 定数伝播、共通部分式除去、デッドコード除去、エスケープ解析などの最適化がSSA形式上で効果的に行われます。
*   **レジスタ割り当ての改善**: 変数のライフタイムが明確になるため、レジスタ割り当ての効率が向上します。

Goコンパイラは、バージョン1.7からSSAバックエンドを導入し、多くの最適化をSSA形式上で行うようになりました。

### 複合リテラル (Composite Literals)

Goにおける複合リテラルは、`struct`、`array`、`slice`、`map`といった複合型の値を簡潔に初期化するための構文です。例えば、`Point{X: 1, Y: 2}` (構造体リテラル) や `[]int{1, 2, 3}` (スライスリテラル) などがあります。これらは、新しい型のインスタンスを作成し、指定された値で初期化します。

### 静的複合リテラル (Static Composite Literals)

静的複合リテラルとは、その構成要素がすべてコンパイル時に決定される定数であり、実行時に副作用を伴う操作（例えば、関数呼び出し、チャネル操作、マップへの書き込みなど）を含まない複合リテラルのことを指します。このようなリテラルは、その値がプログラムの実行中に変化することがなく、またその生成自体がプログラムの状態に影響を与えないため、「副作用がない」と見なすことができます。

### 副作用 (Side Effects)

プログラミングにおける副作用とは、関数や式がその戻り値以外に、プログラムの外部の状態（グローバル変数、ヒープメモリ、I/O操作など）を変更する効果のことを指します。例えば、変数の値を変更する、ファイルに書き込む、ネットワークリクエストを送信するなどが副作用にあたります。コンパイラ最適化の文脈では、副作用のない式は、その結果が使われない場合に除去されたり、複数回評価されても問題ないため、より積極的に最適化の対象となります。

### `safeexpr` 関数

`safeexpr`関数は、Goコンパイラの内部関数であり、与えられた式が「安全」であるかどうか、特に副作用がないかどうかを判断する役割を担っていると推測されます。この関数は、コンパイラが特定の最適化を適用する前に、その式がプログラムのセマンティクスを変更することなく移動、複製、または除去できるかを評価するために使用されます。副作用がないと判断された式は、より積極的な最適化の対象となります。

## 技術的詳細

GoコンパイラがSSAバックエンドを導入した際、一部のコードパターン、特に複合リテラルを含む`append`操作において、非SSAコンパイラと比較して性能が低下するケースが報告されました。これは、SSAが複合リテラルの評価を、潜在的に副作用を持つものとして扱っていたためと考えられます。

具体的には、`append`関数はスライスに要素を追加する際に、必要に応じて新しいバッキング配列を割り当てます。`AppendInPlace`ベンチマークは、この再割り当てが発生しないように、十分な容量を持つスライスに対して`append`を呼び出すシナリオを測定します。このような状況では、`append`のオーバーヘッドは主に要素のコピーと、追加される要素の評価にあります。

もし複合リテラルが副作用を持つと見なされると、コンパイラはそれを安易に最適化（例えば、スタック割り当てへの変換や、不要な一時オブジェクトの除去）することができません。これにより、ヒープ割り当てが増加したり、余分なコードが生成されたりして、性能が低下する可能性があります。

このコミットの目的は、`safeexpr`関数において、静的な複合リテラル（`OSTRUCTLIT`や`OARRAYLIT`）が副作用を持たないことを明示的にコンパイラに伝えることです。`isStaticCompositeLiteral(n)`という内部関数（コミットの差分には含まれていませんが、その存在が示唆されています）が、複合リテラルが静的であるかどうかを判断します。静的であると判断された場合、`safeexpr`は元のノード`n`をそのまま返すことで、その式が副作用を持たず、安全に最適化できることをコンパイラのSSAバックエンドに伝えます。

これにより、SSAバックエンドは、`AppendInPlace`ベンチマークのようなシナリオで、静的な複合リテラルをより効率的に処理できるようになります。例えば、これらのリテラルがヒープではなくスタックに割り当てられるようになり、ガベージコレクションのオーバーヘッドが削減され、全体的な実行速度が向上します。結果として、非SSAコンパイラとの性能差が解消され、むしろSSAの利点を活かした性能向上が実現されました。

## コアとなるコードの解説

この変更は、Goコンパイラの`src/cmd/compile/internal/gc/subr.go`ファイル内の`safeexpr`関数にあります。`safeexpr`関数は、コンパイラが式を評価する際に、その式が副作用を持つかどうかを判断するために使用されます。

追加されたコードブロックは以下の通りです。

```go
	case OSTRUCTLIT, OARRAYLIT:
		if isStaticCompositeLiteral(n) {
			return n
		}
```

1.  **`case OSTRUCTLIT, OARRAYLIT:`**: この行は、現在処理しているノード`n`が構造体リテラル (`OSTRUCTLIT`) または配列リテラル (`OARRAYLIT`) である場合に、この`case`ブロックのコードを実行することを示しています。これらはGoにおける複合リテラルの主要な形式です。
2.  **`if isStaticCompositeLiteral(n)`**: ここで、`isStaticCompositeLiteral`という関数が呼び出され、現在の複合リテラル`n`が「静的」であるかどうかをチェックします。この関数は、リテラルの全ての要素が定数であり、実行時に副作用を伴う操作を含まないことを検証すると考えられます。このコミットの差分には`isStaticCompositeLiteral`関数の実装は含まれていませんが、その名前から役割は明らかです。
3.  **`return n`**: もし`isStaticCompositeLiteral(n)`が`true`を返した場合、つまり複合リテラルが静的で副作用がないと判断された場合、`safeexpr`関数は元のノード`n`をそのまま返します。これは、この複合リテラルが副作用を持たないため、特別な処理や変換を必要とせず、コンパイラのSSAバックエンドがこれを安全に最適化できることを示唆しています。

この変更の意義は、コンパイラが静的な複合リテラルをより正確に認識し、それらが副作用を持たないことを保証することで、SSAバックエンドがより積極的な最適化を適用できるようになる点にあります。これにより、不要なメモリ割り当て（特にヒープ割り当て）が削減され、コード生成が効率化され、結果として`AppendInPlace`ベンチマークのようなシナリオでの性能が向上します。

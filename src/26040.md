# [インデックス 26040] ファイルの概要

このコミットは、Goランタイムにおけるスタックメモリ管理の改善に関するものです。特に、大きなスタックスパン（スタックに割り当てられるメモリ領域）の再利用メカニズムを導入することで、特定の条件下でのメモリ使用量の増大を防ぎます。ガベージコレクション（GC）中の競合を避けつつ、大きなスタックスパンを効率的に再利用するための新しいキャッシュ構造とロジックが`src/runtime/stack.go`に実装されています。

## コミット

```
commit 0cbf8d13a791ab5212c53dbcd58d0fdd622023b1
Author: Austin Clements <austin@google.com>
Date:   Mon Dec 14 14:30:25 2015 -0500

    runtime: recycle large stack spans

    To prevent races with the garbage collector, stack spans cannot be
    reused as heap spans during a GC. We deal with this by caching stack
    spans during GC and releasing them at the end of mark termination.
    However, while our cache lets us reuse small stack spans, currently
    large stack spans are *not* reused. This can cause significant memory
    growth in programs that allocate large stacks rapidly, but grow the
    heap slowly (such as in issue #13552).

    Fix this by adding logic to reuse large stack spans for other stacks.

    Fixes #11466.

    Fixes #13552. Without this change, the program in this issue creeps to
    over 1GB of memory over the course of a few hours. With this change,
    it stays rock solid at around 30MB.
```

## 元コミット内容

Goランタイムにおいて、大きなスタックスパンの再利用に関する問題に対処するコミットです。ガベージコレクタとの競合を避けるため、GC中はスタックスパンをヒープスパンとして再利用できません。このため、GC中にスタックスパンをキャッシュし、マーク終了時に解放する仕組みが導入されていました。しかし、このキャッシュは小さなスタックスパンの再利用には機能するものの、大きなスタックスパンは再利用されませんでした。この結果、大きなスタックを頻繁に割り当てるがヒープの成長が遅いプログラム（issue #13552で報告されたようなケース）で、メモリ使用量が著しく増大する問題が発生していました。

このコミットは、他のスタックのために大きなスタックスパンを再利用するロジックを追加することで、この問題を解決します。これにより、issue #11466と#13552が修正されます。特に#13552のプログラムでは、この変更がない場合、数時間で1GBを超えるメモリを消費していましたが、変更後は約30MBで安定するようになりました。

## 変更の背景

Goランタイムは、ゴルーチンごとにスタックを割り当て、必要に応じてスタックを拡張・縮小します。スタックはメモリの「スパン」として管理され、使用されなくなったスタックスパンは解放されるか、再利用のためにキャッシュされます。

このコミットが導入される以前は、Goのガベージコレクタ（GC）の動作とスタックのメモリ管理には特定の制約がありました。GCが実行されている間、スタックとして使用されていたメモリ領域（スタックスパン）を、ヒープメモリとして再利用することはできませんでした。これは、GCがメモリをスキャンしている最中にそのメモリ領域の役割が変わると、GCの正確性や安全性に問題が生じる可能性があるためです。

この制約に対処するため、GoランタイムはGC中に解放されたスタックスパンを一時的にキャッシュし、GCのマークフェーズが終了した後にまとめて解放する仕組みを持っていました。しかし、このキャッシュメカニズムは主に「小さな」スタックスパンの再利用に焦点を当てており、「大きな」スタックスパンは再利用されずに、GC終了時に単に解放されるだけでした。

この設計上のギャップが、特定のワークロードで問題を引き起こしました。具体的には、非常に大きなスタックを頻繁に割り当てるが、ヒープ全体のメモリ使用量はそれほど増えないようなプログラムです。このようなプログラムでは、大きなスタックスパンが次々と割り当てられ、使用されなくなっても再利用されずに解放されるため、システム全体のメモリ使用量が継続的に増加（「メモリクリープ」）し、最終的には過剰なメモリを消費する事態が発生していました。コミットメッセージで言及されているissue #13552は、この問題の典型例であり、数時間で1GBを超えるメモリを消費するプログラムが、この変更によって30MB程度に安定するという劇的な改善が見られました。

このコミットの目的は、この「大きなスタックスパンの再利用不足」という問題を解決し、Goプログラムのメモリ効率を向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチンとスタック**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行することが一般的です。
    *   **スタック (Stack)**: 各ゴルーチンは独自のスタックを持ち、関数呼び出しの引数、ローカル変数、リターンアドレスなどが格納されます。Goのスタックは動的に伸縮可能であり、必要に応じて自動的に拡張・縮小されます。
    *   **スタックスパン (Stack Span)**: Goランタイムは、メモリを`mspan`と呼ばれる連続したページ（通常は8KB）のブロックで管理します。スタックに割り当てられるこれらの`mspan`がスタックスパンです。

2.  **メモリ管理とガベージコレクション (GC)**:
    *   **mheap**: Goランタイムのヒープマネージャで、`mspan`を管理します。`mheap`は、メモリを`mspan`単位で割り当てたり解放したりします。
    *   **ガベージコレクション (GC)**: Goは自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムがもはや到達できないメモリ領域を自動的に解放し、再利用可能にします。
    *   **GCのフェーズ**: GoのGCは、主に「マークフェーズ」と「スイープフェーズ」に分かれます。
        *   **マークフェーズ**: ライブオブジェクト（到達可能なオブジェクト）を識別します。この間、プログラムの実行は一時停止（Stop-The-World）するか、並行して実行されますが、メモリの状態はGCにとって一貫している必要があります。
        *   **マーク終了 (Mark Termination)**: マークフェーズの終了を意味します。この時点で、どのオブジェクトがライブであるかが確定します。
        *   **スイープフェーズ**: マークされなかった（デッドな）オブジェクトが占めていたメモリを解放し、再利用可能にします。

3.  **GC中のメモリ再利用の制約**:
    *   GCがアクティブな間、特にマークフェーズ中は、スタックスパンとして使用されていたメモリをヒープスパンとして再利用することはできません。これは、GCがスタックをスキャンしてライブオブジェクトを識別している最中に、そのメモリ領域がヒープの一部として扱われると、GCが誤った判断を下す可能性があるためです。
    *   このため、GC中に解放されたスタックスパンは、すぐに`mheap`に戻されるのではなく、一時的にキャッシュされ、GCのマーク終了後に`mheap`に解放されるか、他のスタックのために再利用される必要があります。

4.  **メモリクリープ (Memory Creep)**:
    *   プログラムの実行中に、メモリ使用量が徐々に、しかし継続的に増加していく現象を指します。これは、メモリリークが原因であることもありますが、このコミットのケースのように、メモリが適切に解放されているにもかかわらず、再利用されずにシステムに保持され続けることによっても発生します。

このコミットは、これらの概念、特にGC中のメモリ再利用の制約と、大きなスタックスパンの再利用不足によるメモリクリープの問題に対処しています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムが大きなスタックスパンを再利用するための専用のキャッシュメカニズムを導入した点にあります。

以前のGoランタイムでは、GC中に解放されたスタックスパンは`stackFreeQueue`という単一のリストに一時的に格納されていました。GCのマーク終了時に、このキュー内のすべてのスパンが`mheap_.freeStack`を通じて`mheap`に返却されていました。このアプローチは、小さなスタックスパンの再利用にはある程度機能しましたが、大きなスタックスパンに対しては効率的ではありませんでした。なぜなら、`stackFreeQueue`はスパンのサイズを考慮せずに一元的に管理していたため、特定のサイズの大きなスタックスパンが必要になったときに、適切なサイズのスパンを効率的に見つけて再利用することが困難だったからです。結果として、大きなスタックスパンはほとんど再利用されず、GC終了時に`mheap`に返却されても、すぐに別の大きなスタックの割り当てに利用されるとは限らず、メモリ使用量の増大につながっていました。

このコミットでは、以下の変更が導入されました。

1.  **`stackLarge`構造体の導入**:
    *   `stackLarge`という新しいグローバル構造体が導入されました。これは、大きなスタックスパンを管理するための専用のキャッシュです。
    *   `stackLarge`は、`lock`（ミューテックス）と`free`という配列を持ちます。
    *   `free`配列は、`_MHeapMap_Bits`のサイズを持ち、各要素は`mSpanList`です。この配列は、スタックスパンのページ数（`s.npages`）の対数（log_2）に基づいて、異なるサイズのスタックスパンを分類して格納するためのフリーリストとして機能します。これにより、特定のサイズのスタックスパンが必要になったときに、そのサイズに合ったスパンを効率的に検索・取得できるようになります。

2.  **`stacklog2`関数の追加**:
    *   `stacklog2(n uintptr) int`というヘルパー関数が追加されました。これは、与えられた数値`n`の2を底とする対数の整数部分（`⌊log_2(n)⌋`）を計算します。この関数は、スタックスパンのページ数に基づいて`stackLarge.free`配列の適切なインデックスを決定するために使用されます。

3.  **`stackalloc`における大きなスタックスパンの再利用ロジック**:
    *   `stackalloc`関数（スタックを割り当てる関数）が変更され、新しいスタックを割り当てる際に、まず`stackLarge`キャッシュから適切なサイズの大きなスタックスパンを探すようになりました。
    *   具体的には、必要なページ数`npage`を計算し、`stacklog2(npage)`を使って`stackLarge.free`配列の対応するフリーリストをロックし、そこからスパンを取得しようとします。
    *   もし`stackLarge`キャッシュに適切なスパンがあれば、それを再利用します。なければ、以前と同様に`mheap_.allocStack`を呼び出して新しいスパンをヒープから割り当てます。

4.  **`stackfree`における大きなスタックスパンのキャッシュロジック**:
    *   `stackfree`関数（スタックを解放する関数）が変更され、GCが実行中の場合、解放されたスタックスパンを`stackLarge`キャッシュに追加するようになりました。
    *   以前は、GC中はすべての解放されたスタックスパンが`stackFreeQueue`に追加されていました。この変更により、大きなスタックスパンは`stackLarge.free`の適切なサイズ別リストに挿入されるようになります。
    *   これにより、GC終了時に`mheap`に返却されるのを待つだけでなく、GC中であっても他のスタックのために再利用される可能性が生まれます。

5.  **`freeStackSpans`における`stackLarge`キャッシュの解放**:
    *   `freeStackSpans`関数（GCのマーク終了時にスタックスパンを解放する関数）が変更され、`stackFreeQueue`の解放に加えて、`stackLarge`キャッシュ内のすべてのスパンも`mheap_.freeStack`を通じて`mheap`に返却されるようになりました。
    *   これにより、`stackLarge`キャッシュに一時的に保持されていた大きなスタックスパンも、GCサイクルが完了した後に適切にシステムに返却されます。

これらの変更により、Goランタイムは大きなスタックスパンをサイズ別に効率的にキャッシュし、再利用できるようになりました。これにより、大きなスタックを頻繁に割り当てるプログラムにおけるメモリクリープの問題が大幅に軽減されます。

    ```go
    	free [_MHeapMap_Bits]mSpanList // free lists by log_2(s.npages)
    }
    ```
    `stackFreeQueue` の代わりに、大きなスタックスパンをサイズ別に管理するための新しい構造体が導入されました。

    ```go
    // stacklog2 returns ⌊log_2(n)⌋.
    func stacklog2(n uintptr) int {
    	log2 := 0
    	for n > 1 {
    		n >>= 1
    		log2++
    	}
    	return log2
    }
    ```

## コアとなるコードの解説

このコミットの核心は、Goランタイムが大きなスタックスパンを効率的に再利用するための新しいデータ構造とロジックを導入したことにあります。

1.  **`stackLarge` 構造体**:
    *   `stackLarge`は、`mSpanList`の配列`free`を持ちます。この配列のインデックスは、スタックスパンのページ数（`s.npages`）の2を底とする対数（`log_2(s.npages)`）に対応しています。これにより、異なるサイズの大きなスタックスパンを効率的に分類し、管理することができます。
    *   例えば、ページ数が8（2^3）のスパンは`free[3]`に、ページ数が16（2^4）のスパンは`free[4]`に格納されます。これにより、特定のサイズのスタックが必要になったときに、そのサイズに最も適したスパンを直接探すことが可能になります。
    *   `lock`ミューテックスは、`stackLarge`構造体へのアクセスを保護し、複数のゴルーチンからの同時アクセスによるデータ競合を防ぎます。

2.  **`stacklog2` 関数**:
    *   この関数は、与えられたページ数`n`に対して、`stackLarge.free`配列の適切なインデックスを計算するために使用されます。例えば、`stacklog2(1)`は0、`stacklog2(2)`は1、`stacklog2(3)`は1、`stacklog2(4)`は2を返します。これは、スパンのサイズを対数スケールで分類するのに役立ちます。

3.  **`stackalloc` の変更**:
    *   スタックを割り当てる際、まず必要なページ数`npage`を計算し、`stacklog2(npage)`を使って`stackLarge.free`から適切なスパンを探します。
    *   もし`stackLarge`キャッシュに利用可能なスパンがあれば、それを`remove`して再利用します。これにより、新しいメモリ割り当てのオーバーヘッドを回避し、メモリ使用量を削減します。
    *   キャッシュに適切なスパンがない場合のみ、`mheap_.allocStack`を呼び出して新しいスパンをヒープから割り当てます。

4.  **`stackfree` の変更**:
    *   スタックを解放する際、GCが実行中である場合は、解放されたスタックスパンを`stackLarge`キャッシュに追加します。
    *   `log2npage := stacklog2(s.npages)`でスパンのサイズに応じたインデックスを計算し、`stackLarge.free[log2npage].insert(s)`で適切なフリーリストにスパンを挿入します。
    *   これにより、GCが終了するまで待つことなく、解放された大きなスタックスパンが他のスタックのためにすぐに再利用される可能性が高まります。

5.  **`freeStackSpans` の変更**:
    *   GCのマーク終了時に呼び出される`freeStackSpans`関数は、`stackFreeQueue`に加えて`stackLarge`キャッシュ内のすべてのスパンも解放するようになりました。
    *   `for i := range stackLarge.free`ループとネストされた`for s := stackLarge.free[i].first; s != nil;`ループにより、`stackLarge`内のすべてのサイズ別フリーリストを走査し、各スパンを`mheap_.freeStack(s)`で`mheap`に返却します。
    *   これにより、キャッシュに一時的に保持されていたスパンが、GCサイクルが完了した後に適切にシステムに返却され、メモリリークを防ぎます。

これらの変更は、Goランタイムが大きなスタックスパンをより賢く管理し、再利用することで、メモリ効率を大幅に向上させ、特定のメモリクリープ問題を解決する上で重要な役割を果たしています。

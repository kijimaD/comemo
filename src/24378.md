## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおけるレジスタ割り当ての不正確さがありました。特に、AMD64アーキテクチャの特定の「インプレース命令」が正しく処理されていませんでした。インプレース命令とは、オペランドの一つが演算結果の格納先としても機能する命令のことです。例えば、`XORQ AX, 1` という命令は、`AX` レジスタの内容と定数 `1` の排他的論理和を計算し、その結果を再び `AX` レジスタに格納します。

問題は、GoコンパイラのSSAバックエンドがこのようなインプレース命令を機械語に変換する際に、ソースレジスタとデスティネーションレジスタが異なる場合に、不適切なレジスタ操作を行っていたことにあります。これにより、`GOGC=off GOSSAPKG=mime go test -a mime` のような特定のテストケースでコンパイルされたコードが誤動作し、テストが失敗していました。

このコミットは、この問題を修正し、テストがパスするようにするための暫定的な措置です。コミットメッセージにもあるように、より根本的な解決策は、レジスタアロケータがインプレース命令の特性を直接理解し、より効率的なコードを生成するように改善することです。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA (Static Single Assignment) 形式を使用します。SSA形式は、各変数が一度だけ代入されるという特性を持つため、データフロー解析や最適化を容易にします。

1.  **フロントエンド**: Goのソースコードを解析し、抽象構文木 (AST) を生成します。
2.  **ミドルエンド (SSAジェネレータ)**: ASTをSSA形式に変換します。この段階で、Goの型システムやセマンティクスが適用され、多くの最適化が行われます。SSA形式では、プログラム内の各値が `ssa.Value` オブジェクトとして表現されます。
3.  **バックエンド (機械語ジェネレータ)**: SSA形式の値をターゲットアーキテクチャ（この場合はAMD64）の機械語命令に変換します。この過程で、SSA値は物理レジスタに割り当てられます。

### SSA値とレジスタ割り当て

SSA形式では、プログラム中の各計算結果は一意の `ssa.Value` として表現されます。これらの `ssa.Value` は、最終的にCPUの物理レジスタ（またはメモリ上のスタック）に割り当てられる必要があります。この割り当てを行うのがレジスタアロケータです。

### インプレース命令 (In-place instructions)

インプレース命令とは、演算のソースオペランドの一つが、同時に演算結果のデスティネーションオペランドとしても機能する機械語命令です。
例:
*   `ADD AX, BX` (Intel構文): `AX = AX + BX`
*   `XORQ AX, 1` (Intel構文): `AX = AX ^ 1` (AXと1の排他的論理和をAXに格納)

これらの命令は、結果を格納するために新しいレジスタを必要としないため、レジスタの使用効率を高めることができます。しかし、コンパイラがSSA形式から機械語を生成する際に、SSA値のソースとデスティネーションが異なる場合に、インプレース命令の特性を考慮せずにコードを生成すると、不必要な `MOV` 命令が挿入されたり、レジスタの衝突が発生したりする可能性があります。

### AMD64アーキテクチャの命令

*   **`SHLQ` (Shift Left Quadword)**: 64ビット値を左シフトします。
*   **`SHRQ` (Shift Right Quadword)**: 64ビット値を右シフトします。
*   **`SARQ` (Shift Arithmetic Right Quadword)**: 64ビット値を算術右シフトします（符号を保持）。
*   **`XORQ` (Exclusive OR Quadword)**: 64ビット値のビット単位の排他的論理和を計算します。

これらの命令は、定数オペランドを持つバリアント（例: `SHLQconst`, `XORQconst`）も存在し、特定のレジスタ（シフト命令の場合は `CL` レジスタ）を暗黙的に使用する場合や、オペランドがインプレースで更新される場合があります。

### `src/cmd/compile/internal/gc/ssa.go` と `genValue` 関数

`src/cmd/compile/internal/gc/ssa.go` は、Goコンパイラのバックエンドの一部であり、SSA形式の値をターゲットアーキテクチャの機械語命令に変換する処理を担っています。
`genValue` 関数は、個々の `ssa.Value` オブジェクトを受け取り、それに対応するアセンブリ命令 (`obj.Prog`) を生成する主要な関数の一つです。この関数内で、各SSA操作 (`ssa.Op`) に応じて適切な機械語命令が選択され、レジスタ割り当ての考慮も行われます。

## 技術的詳細

このコミットの技術的な核心は、`genValue` 関数における `ssa.OpAMD64XORQconst` の処理方法の変更にあります。

以前のコードでは、`ssa.OpAMD64XORQconst` は独立した `case` ブロックで処理されていました。このブロックは、`AXORQ` 命令を生成し、定数オペランドを `From` フィールドに、ターゲットレジスタを `To` フィールドに設定していました。しかし、この処理では、SSA値のソースレジスタと結果を格納するレジスタが異なる場合に、レジスタの整合性を適切に保つためのロジックが不足していました。

具体的には、SSA形式では `v = XORQconst(x, const)` のように表現され、`x` と `v` は異なるSSA値である可能性があります。しかし、AMD64の `XORQ` 命令は通常、`XORQ Reg1, Reg2` のように `Reg1 = Reg1 ^ Reg2` の形式で動作します。もし `x` が `R1` に割り当てられ、`v` が `R2` に割り当てられる場合、単純に `XORQ R2, const` を生成すると、`R1` の値が考慮されず、誤った結果になります。この場合、`MOVQ R1, R2` の後に `XORQ R2, const` のように、`x` の値を `v` のレジスタにコピーする中間命令が必要になります。

このコミットでは、`ssa.OpAMD64XORQconst` の処理を、既に同様のレジスタ整合性ロジックを持つ `SHLQconst`, `SHRQconst`, `SARQconst` の `case` ブロックに統合しました。この共通ブロックは以下のロジックを含んでいます。

1.  SSA値 `v` のソースオペランド `v.Args[0]` に割り当てられたレジスタ `x` を取得します。
2.  SSA値 `v` 自体（結果）に割り当てられたレジスタ `r` を取得します。
3.  もし `x` と `r` が異なるレジスタである場合 (`if x != r`)、`MOVQ` 命令を生成して `x` の内容を `r` にコピーします。これにより、インプレース命令が `r` に対して正しく動作するための準備が整います。

この変更により、`XORQconst` がインプレース命令として扱われる際に、ソースとデスティネーションのレジスタが異なる場合のレジスタの整合性が保証され、コンパイルされたコードの正確性が向上しました。

また、`src/cmd/compile/internal/ssa/TODO` ファイルに新しい項目が追加され、この修正が一時的なものであることが明記されました。長期的な目標は、レジスタアロケータが `XORQ AX, 1` のようなインプレース命令を直接、かつ効率的に生成できるようにすることです。現在の修正は、`MOVQ AX, BX; XORQ BX, 1` のような、一時的なレジスタコピーを伴う可能性のあるコードを生成する可能性がありますが、これによりバグは修正されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

1.  **`ssa.OpAMD64XORQconst` の統合**:
    `case ssa.OpAMD64SHLQconst, ssa.OpAMD64SHRQconst, ssa.OpAMD64SARQconst:` の行に `, ssa.OpAMD64XORQconst` が追加されました。これにより、`XORQconst` の処理が、シフト命令の定数オペランド版と同じロジックで扱われるようになりました。
    このブロック内のロジックは以下の通りです。
    ```go
    x := regnum(v.Args[0]) // ソースオペランドのレジスタ番号を取得
    r := regnum(v)         // 結果のSSA値に割り当てられたレジスタ番号を取得
    if x != r {
        // ソースレジスタと結果レジスタが異なる場合、MOVQ命令を生成して値をコピー
        p := Prog(x86.AMOVQ)
        p.From.Type = obj.TYPE_REG
        p.From.Reg = x
        p.To.Type = obj.TYPE_REG
        p.To.Reg = r
    }
    ```
    この `if x != r` のチェックと `MOVQ` 命令の挿入により、`XORQconst` のようなインプレース命令が、ソースとデスティネーションのSSA値が異なるレジスタに割り当てられた場合でも、正しく動作するようになります。つまり、`XORQ` 命令が実行される前に、正しい値が結果レジスタにコピーされることが保証されます。

2.  **古い `ssa.OpAMD64XORQconst` 処理の削除**:
    以前存在した以下の `case` ブロックが削除されました。
    ```go
    case ssa.OpAMD64XORQconst:
        p := Prog(x86.AXORQ)
        p.From.Type = obj.TYPE_CONST
        p.From.Offset = v.AuxInt
        p.To.Type = obj.TYPE_REG
        p.To.Reg = regnum(v.Args[0])
    ```
    この古い実装では、`XORQ` 命令のデスティネーションレジスタとして `v.Args[0]` のレジスタ（つまりソースレジスタ）が直接使用されていました。これは、SSA値 `v` が `v.Args[0]` と同じレジスタに割り当てられている場合には問題ありませんが、異なるレジスタに割り当てられている場合には、`v.Args[0]` の値が `v` のレジスタにコピーされていないため、誤った結果を生じる可能性がありました。新しい共通ロジックに統合されたことで、この問題が解決されました。

### `src/cmd/compile/internal/ssa/TODO` の変更

新しいTODO項目が追加されました。
```
 - Handle in-place instructions (like XORQconst) directly:
   Use XORQ AX, 1 rather than MOVQ AX, BX; XORQ BX, 1.
```
これは、現在の修正がレジスタの整合性を確保するための暫定的なものであることを示しています。理想的には、レジスタアロケータがインプレース命令のセマンティクスをより深く理解し、SSA値のソースとデスティネーションが同じ物理レジスタに割り当てられるようにすることで、`MOVQ` 命令のような余分なコピー命令を生成することなく、`XORQ AX, 1` のようなより効率的なコードを直接生成できるようになるべきだという長期的な目標を提示しています。

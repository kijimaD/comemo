# [インデックス 23473] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/internal/ld`) における動的シンボルおよび動的ライブラリの取り扱いに関する変更です。具体的には、外部リンキング（external linking）を使用する際に、不必要に `.dynamic` および `.dynsym` シンボルが作成されるのを防ぐことを目的としています。これにより、リンカの動作がより正確になり、`data.go` に存在していた一時的な回避策（fudge）が削除されました。

変更が加えられたファイルは以下の通りです。

*   `src/cmd/internal/ld/data.go`: リンカがシンボル情報を処理する際に、特定のシンボル（`.dynamic` や `.dynsym`）を誤ってグローバルシンボルとして扱わないようにするロジックが修正されました。
*   `src/cmd/internal/ld/go.go`: Cgo関連の処理において、動的ライブラリの追加方法が変更され、外部リンキングの有無やOSの種類（Darwinかそれ以外か）に応じて `adddynlib` の呼び出しが調整されました。
*   `src/cmd/internal/ld/lib.go`: 動的ライブラリのリストを保持するための新しいグローバル変数 `dynlib` が追加され、`adddynlib` および `Adddynsym` 関数が外部リンキング時に動的シンボルやライブラリの追加を抑制するように修正されました。

## 変更の背景

Go言語のリンカは、Goプログラムを最終的な実行可能ファイルに変換する重要な役割を担っています。このプロセスには、Go独自のランタイムと、Cgoを介してリンクされる可能性のあるC/C++ライブラリの両方を考慮する必要があります。

このコミットの主な背景には、以下の問題がありました。

1.  **`.dynamic` および `.dynsym` シンボルの不適切な生成**: 外部リンキング（`LinkExternal` モード）を使用する場合、Goリンカは最終的なバイナリの生成を外部のCリンカ（例: `gcc`）に委ねます。この際、Goリンカが内部的に `.dynamic` や `.dynsym` といったELF形式（Linuxなどで使用される実行可能ファイルフォーマット）の動的セクションに関連するシンボルを生成してしまうことがありました。これらのシンボルは外部リンカによって適切に処理されるべきものであり、Goリンカがこれらを生成すると、重複や不整合が生じる可能性がありました。特に、`data.go` にはこれらのシンボルが誤ってグローバルシンボルとして扱われるのを防ぐための「fudge」（一時的な回避策、ごまかし）が存在していました。これは、シンボル名が `.` で始まるものを除外するという、やや場当たり的な方法でした。
2.  **`adddynlib` 呼び出しのタイミング問題**: 動的ライブラリを追加する `adddynlib` 関数は、リンキングモード（内部か外部か）が決定される前に呼び出されることがありました。特にDarwin（macOS）以外のシステム（主にELFベースのシステム）では、外部リンキングの場合には動的ライブラリの処理を外部リンカに任せるべきであり、Goリンカが独自に `DT_NEEDED` エントリ（ELFバイナリが依存する共有ライブラリを示す）を追加するのは不適切でした。このタイミングのずれが、リンカの複雑性を増し、バグの原因となる可能性がありました。

このコミットは、これらの問題を解決し、リンカの動作をより堅牢で正確にすることを目的としています。特に、外部リンキング時にGoリンカが動的シンボルやライブラリの情報を不必要に生成・処理しないようにすることで、`data.go` の「fudge」を削除し、コードのクリーンアップと保守性の向上を図っています。

## 前提知識の解説

### Goリンカ (`cmd/internal/ld`)

Go言語のコンパイラツールチェーンの一部であり、Goソースコードから実行可能バイナリを生成する最終段階を担います。Goリンカは、Goのオブジェクトファイル、アーカイブ、およびCgoによって生成されたC/C++オブジェクトファイルを結合し、実行可能な形式に変換します。Goランタイムの初期化、ガベージコレクション、スケジューラなどのGo固有の機能も、リンカによって最終バイナリに組み込まれます。

### 内部リンキングと外部リンキング

Goリンカには、主に2つのリンキングモードがあります。

*   **内部リンキング (Internal Linking)**: Goリンカがすべてのリンク処理を単独で行います。Goのオブジェクトファイルと、Cgoによって生成されたC/C++オブジェクトファイルを直接リンクし、単一の静的バイナリを生成します。このモードでは、外部のCリンカ（例: `gcc`）は使用されません。Goのクロスコンパイル能力を最大限に活用できるため、Goプログラムのデプロイが容易になります。
*   **外部リンキング (External Linking)**: Goリンカは、GoのオブジェクトファイルとCgoによって生成されたC/C++オブジェクトファイルを結合し、中間的なオブジェクトファイルを生成します。その後、この中間オブジェクトファイルを外部のCリンカ（例: `gcc`）に渡し、最終的な実行可能バイナリの生成を外部リンカに委ねます。このモードは、Cgoを使用しており、特に複雑なC/C++ライブラリに依存している場合や、特定のリンカフラグが必要な場合によく使用されます。例えば、`net` パッケージがシステムDNSリゾルバを使用する場合や、`os/user` パッケージがシステムユーザーデータベースにアクセスする場合など、Cgoを介してシステムライブラリにリンクする必要がある場合に利用されます。

このコミットは、特に外部リンキング時の動作に焦点を当てています。

### 動的リンクと静的リンク

*   **静的リンク**: プログラムが必要とするすべてのライブラリコードが、コンパイル時に最終的な実行可能ファイルに直接組み込まれます。結果として生成されるバイナリは自己完結型であり、実行時に外部ライブラリを必要としません。しかし、バイナリサイズが大きくなり、ライブラリの更新があった場合にプログラム全体を再コンパイルする必要があります。
*   **動的リンク**: プログラムが必要とするライブラリコードは、実行可能ファイルには組み込まれず、共有ライブラリ（WindowsではDLL、Linuxでは.so、macOSでは.dylib）として別途存在します。プログラムは実行時にこれらの共有ライブラリをロードして使用します。これにより、バイナリサイズが小さくなり、複数のプログラムで同じライブラリを共有できるためメモリ効率が向上します。また、ライブラリの更新があっても、プログラムを再コンパイルせずに新しいライブラリを使用できます。しかし、実行時にライブラリが見つからないとプログラムが起動しない（DLL Hellなど）という問題が発生する可能性があります。

Goの外部リンキングは、C/C++ライブラリとの動的リンクを可能にするために使用されることがあります。

### `.dynamic` と `.dynsym` (ELF形式)

ELF (Executable and Linkable Format) は、Linuxや多くのUnix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットとして使用されています。

*   **`.dynamic` セクション**: ELFバイナリの動的リンク情報を格納するセクションです。このセクションには、プログラムが実行時に必要とする共有ライブラリのリスト（`DT_NEEDED` エントリ）、動的リンカのパス、初期化/終了関数へのポインタなど、動的リンカがプログラムをロードして実行するために必要な情報が含まれています。
*   **`.dynsym` セクション**: 動的シンボルテーブルを格納するセクションです。これは、プログラムが実行時に解決する必要があるシンボル（共有ライブラリからインポートされる関数や変数、または共有ライブラリによってエクスポートされるシンボル）のリストを含みます。

これらのセクションは、動的リンクされたプログラムが正しく動作するために不可欠です。

### Mach-O と ELF

*   **Mach-O (Mach Object)**: AppleのmacOSやiOSなどのDarwin系オペレーティングシステムで使用される実行可能ファイルフォーマットです。ELFと同様に、実行可能ファイル、オブジェクトファイル、共有ライブラリ（ダイナミックライブラリ）の構造を定義します。Mach-Oも動的リンクをサポートしており、独自のセクションや構造を持っています。
*   **ELF (Executable and Linkable Format)**: 前述の通り、LinuxやUnix系システムで広く使用されています。

Goリンカは、ターゲットOSに応じてこれらの異なるフォーマットを生成する必要があります。このコミットでは、特にDarwinとそれ以外のシステム（主にELF）での `adddynlib` の処理の違いが言及されています。

### `adddynlib` と `Adddynsym`

Goリンカ内部の関数で、動的リンクに関連する情報を処理します。

*   `adddynlib(lib string)`: 指定されたライブラリ名 `lib` を、最終的なバイナリが依存する動的ライブラリのリストに追加する役割を持ちます。ELF形式の場合、これは `.dynamic` セクションに `DT_NEEDED` エントリを追加することに対応します。Mach-O形式の場合は `Machoadddynlib` を呼び出します。
*   `Adddynsym(ctxt *Link, s *LSym)`: 指定されたシンボル `s` を動的シンボルとしてマークし、動的シンボルテーブル（ELFの `.dynsym` など）に追加する役割を持ちます。これは、シンボルが実行時に動的に解決される必要があることをリンカに伝えます。

## 技術的詳細

このコミットの技術的な核心は、Goリンカが外部リンキングモード (`Linkmode == LinkExternal`) で動作している場合に、動的リンクに関連する内部処理を抑制することにあります。

1.  **`data.go` の「fudge」の削除**:
    以前の `data.go` の `proggenaddsym` 関数には、シンボル名が `.` で始まるものを除外することで、`.dynamic` や `.dynsym` といったELFの動的セクションシンボルが誤ってGoのグローバルシンボルとして扱われるのを防ぐための条件 `s.Name[0] != '.'` がありました。これは、これらのシンボルが `SELFSECT`（自己セクション、つまり特定のセクションに属し、グローバルシンボルではない）として正しくマークされていない場合に発生する問題を回避するためのものでした。
    このコミットでは、外部リンキング時にこれらのシンボルがそもそも生成されないようにすることで、この場当たり的な条件を削除することが可能になりました。これにより、リンカのロジックがよりクリーンで意図に沿ったものになります。

2.  **`adddynlib` 呼び出しの遅延と条件付き実行**:
    `src/cmd/internal/ld/go.go` の `loadcgo` 関数内で、Cgoによって指定された動的ライブラリ (`lib`) を処理する部分が変更されました。
    以前は、Darwin（macOS）以外のシステムでも `adddynlib(lib)` が直接呼び出されていました。しかし、外部リンキングの場合、これらのライブラリの依存関係は外部リンカが処理すべきです。
    変更後、Darwinシステム (`HEADTYPE == obj.Hdarwin`) の場合は引き続き `Machoadddynlib(lib)` が直接呼び出されます。これは、Mach-O形式の動的ライブラリ処理がELFとは異なるためです。
    一方、Darwin以外のシステムでは、`adddynlib(lib)` を直接呼び出す代わりに、ライブラリ名が新しいグローバル変数 `dynlib` （`src/cmd/internal/ld/lib.go` で定義）に追加されるようになりました。
    この `dynlib` リストは、リンキングモードが最終的に決定された後、`addexport` 関数内でまとめて処理されます。これにより、外部リンキングが選択された場合には、`adddynlib` が `LinkExternal` モードを認識し、動的ライブラリの追加を抑制できるようになります。

3.  **`adddynlib` および `Adddynsym` の外部リンキング抑制**:
    `src/cmd/internal/ld/lib.go` 内の `adddynlib` 関数と `Adddynsym` 関数に、`Linkmode == LinkExternal` という条件が追加されました。
    *   `adddynlib`: 以前は `seenlib[lib]` で重複チェックを行っていましたが、これに加えて `Linkmode == LinkExternal` の場合も早期リターンするようになりました。これにより、外部リンキング時にはGoリンカがELFの `DT_NEEDED` エントリを生成するのを防ぎます。
    *   `Adddynsym`: 以前は `s.Dynid >= 0` （既に動的シンボルとしてマークされているか）でチェックしていましたが、これに加えて `Linkmode == LinkExternal` の場合も早期リターンするようになりました。これにより、外部リンキング時にはGoリンカが動的シンボルテーブルにエントリを追加するのを防ぎます。

これらの変更により、Goリンカは外部リンキング時に動的リンクに関する内部処理を適切に抑制し、外部のCリンカにその役割を完全に委ねるようになります。これにより、リンカの動作がより一貫性のあるものとなり、不必要なシンボルやセクションの生成が回避されます。

この関数は、シンボルを動的シンボルテーブルに追加する役割を持っています。外部リンキングモードの場合、動的シンボルは外部のCリンカが処理すべきであるため、Goリンカが `.dynsym` エントリを生成するのを抑制する必要があります。この条件により、外部リンキング時には `Adddynsym` が早期にリターンし、不必要な処理を行わなくなります。

```go
 	for _, exp := range dynexp {
 		Adddynsym(Ctxt, exp)
 	}
 	for _, lib := range dynlib {
 		adddynlib(lib)
 	}
```

`addexport` 関数内のこの変更は、動的シンボルと動的ライブラリの処理を分離し、`dynlib` リストの処理を追加しています。
以前は `dynexp` （エクスポートされる動的シンボル）のみをループして `Adddynsym` を呼び出していましたが、変更後は `dynlib` リストもループして `adddynlib` を呼び出すようになりました。
この `addexport` 関数は、リンキングモードが最終的に決定された後に呼び出されるため、`dynlib` に追加されたライブラリが `adddynlib` 関数内で `Linkmode == LinkExternal` のチェックを受けることが保証されます。これにより、非Darwinシステムでの `adddynlib` 呼び出しのタイミング問題が解決されます。

### `src/cmd/internal/ld/lib.go` の変更

```go
 	dynexp             []*LSym
+	dynlib             []string
 	ldflag             []string
```

新しいグローバル変数 `dynlib` が `[]string` 型で追加されました。
このスライスは、非Darwinシステムにおいて、リンキングモードが決定される前に `loadcgo` 関数によって収集された動的ライブラリ名を一時的に保持するために使用されます。その後、`addexport` 関数内でこのリストが処理され、`adddynlib` が適切なタイミングで呼び出されるようになります。

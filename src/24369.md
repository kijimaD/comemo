# [インデックス 24369] ファイルの概要

このコミットは、Go言語の `net` パッケージにおける `TestDialTimeout` および `TestDialTimeoutFDLeak` というテストが、TCP同時オープン（TCP simultaneous open）のシナリオで不安定（flaky）になる問題を修正するものです。具体的には、`socktest` パッケージのソケットクローズフィルタの挙動を調整し、テストの信頼性を向上させています。

## 変更の背景

このコミットは、Goの `net` パッケージ内の `TestDialTimeout` と `TestDialTimeoutFDLeak` というテストが、特定の条件下で不安定（flaky）になる問題を解決するために導入されました。具体的には、TCP同時オープン（TCP simultaneous open）という稀なネットワークシナリオが発生した際に、テストが非決定的に失敗することがありました。

テストのflakinessは、開発プロセスにおいて大きな問題となります。テストが時々失敗し、時々成功する場合、その失敗が実際のバグによるものなのか、それともテスト環境やタイミングの問題によるものなのかを判断するのが困難になるためです。このコミットは、このような非決定的なテストの失敗を排除し、テストスイートの信頼性を向上させることを目的としています。

特に `TestDialTimeoutFDLeak` はファイルディスクリプタ（FD）のリークを検出するためのテストであり、ソケットのオープンとクローズのタイミングが非常に重要です。TCP同時オープンという特殊な状況下で、ソケットのライフサイクル管理が複雑になり、`socktest` パッケージがソケットの状態を正確に追跡できなくなることが、テストの不安定さの原因となっていました。

## 前提知識の解説

### Goの `net` パッケージ

Go言語の `net` パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。TCP/IP、UDP、Unixドメインソケットなど、様々なネットワークプロトコルを扱うための機能が含まれています。`Dial` や `Listen` といった関数を通じて、ネットワーク接続の確立やデータの送受信を行うことができます。

### `socktest` パッケージ

`socktest` パッケージは、Goの `net` パッケージのテストのために特別に設計された内部パッケージです。これは、ソケットのライフサイクル（オープン、クローズ、接続など）における特定のイベントをフックし、その挙動をシミュレートしたり、ソケットの状態を監視したりする機能を提供します。これにより、ネットワークエラーや特定のネットワークシナリオ（例えば、接続拒否、タイムアウトなど）をテスト内で再現し、`net` パッケージの堅牢性を検証することが可能になります。`socktest.FilterConnect` や `socktest.FilterClose` のようなフィルタは、それぞれ接続時やクローズ時に特定の処理を挿入するために使用されます。

### TCP同時オープン (TCP Simultaneous Open)

通常のTCP接続確立（3ウェイハンドシェイク）では、クライアントが `SYN` を送信し、サーバーが `SYN-ACK` で応答し、クライアントが `ACK` を返すという手順を踏みます。しかし、TCP同時オープンは、非常に稀なケースで発生する特殊な接続確立シナリオです。これは、2つのホストが同時に互いに接続を試み、それぞれが `SYN` セグメントを相手に送信した場合に起こります。

この場合、両方のホストが `SYN` を送信し、同時に相手から `SYN` を受信します。その後、それぞれが `SYN-ACK` を送信し、相手から `SYN-ACK` を受信します。最終的に、両方のホストが `ESTABLISHED` 状態に移行します。このプロセスは通常の3ウェイハンドシェイクとは異なり、両方のエンドポイントがアクティブなオープン要求を開始するため、ソケットの状態遷移がより複雑になります。特に、ソケットのオープンとクローズのタイミングが通常の接続よりも予測しにくくなることがあります。

### ファイルディスクリプタ (File Descriptor, FD)

ファイルディスクリプタ（FD）は、Unix系オペレーティングシステムにおいて、プロセスがファイルやソケットなどのI/Oリソースにアクセスするために使用する抽象的な識別子です。FDは非負の整数で表され、各プロセスはオープンしているファイルやソケットごとに一意のFDを持ちます。ソケットがオープンされるとFDが割り当てられ、クローズされると解放されます。FDリークは、ソケットが適切にクローズされずにFDが解放されない状態を指し、システムリソースの枯渇やパフォーマンス低下の原因となります。

### テストのflakiness

テストのflakinessとは、テストが同じコードベース、同じ環境で実行されたにもかかわらず、成功したり失敗したりする非決定的な挙動を指します。これは、並行処理のタイミング問題、外部リソースの可用性、システムクロックの精度、またはネットワークの不安定性など、様々な要因によって引き起こされる可能性があります。flakyなテストは、開発者が実際のバグとテストの不安定さを区別することを困難にし、開発効率を低下させます。

## 技術的詳細

このコミットの技術的な核心は、`socktest` パッケージの `FilterClose` フックの利用方法を変更し、TCP同時オープン時のソケットのオープン/クローズの「ジッターバグ」を回避することにあります。

従来のテストでは、`socktest.Switch` を使用してソケットのオープン数を追跡し、テストの前後でFDの数が一致するかどうかを確認していました。しかし、TCP同時オープンが発生すると、`netFD` とソケット間のオープン/クローズのタイミングが複雑になり、`socktest.Switch` がソケットの状態を正確に追跡できなくなることがありました。これは、`tcpsock_posix.go` 内の `selfConnect` のような自己接続シナリオで特に顕著になります。

このコミットでは、`TestDialTimeoutFDLeak` と `TestDialTimeout` の両方で、`socktest.FilterClose` を設定し、ソケットがクローズされる際に常に `errTimedout` を返すように変更しています。これにより、ソケットのクローズ処理が意図的に失敗させられ、ソケットが閉じられない状態をシミュレートします。

`TestDialTimeoutFDLeak` では、この変更により、`Dial` 呼び出しがタイムアウトするたびに `socktest.FilterClose` が呼び出され、`attempts` カウンタが増加します。テストの最後で、`attempts` が `N`（試行回数）以上であることを確認することで、FDリークが発生していないことを間接的に検証します。以前のように `sw.Sockets()` の数を比較するのではなく、`FilterClose` が期待通りに呼び出された回数を数えることで、TCP同時オープンによるソケット状態追跡の不確実性を回避しています。

また、`defer func() { sw.Set(socktest.FilterClose, nil); forceCloseSockets() }()` という遅延関数が追加されています。これは、テストの終了時に `FilterClose` を無効にし、`forceCloseSockets()` を呼び出すことで、テスト中に開かれた可能性のあるすべてのソケットを強制的にクローズし、テスト間の状態のクリーンアップを確実にします。これにより、テスト間の相互作用によるflakinessも防止されます。

`TestDialTimeout` でも同様に `socktest.FilterClose` を設定し、`errTimedout` を返すようにすることで、タイムアウトテストの信頼性を向上させています。

## コアとなるコードの解説

### `src/net/dial_test.go` の変更点

1.  **`before := sw.Sockets()` の削除**: 以前はテスト開始前のソケット数を記録していましたが、TCP同時オープン時の `socktest.Switch` の追跡の不確実性を避けるため、この行が削除されました。
2.  **`defer` 関数によるクリーンアップの強化**:
    ```go
    defer func() {
        sw.Set(socktest.FilterClose, nil)
        forceCloseSockets()
    }()
    ```
    この `defer` 関数は、テストが終了する際に必ず実行されます。
    *   `sw.Set(socktest.FilterClose, nil)`: テスト中に設定された `FilterClose` フックを解除し、ソケットクローズの挙動をデフォルトに戻します。
    *   `forceCloseSockets()`: テスト中に開かれた可能性のあるすべてのソケットを強制的にクローズします。これにより、テスト間の状態のリークを防ぎ、テストの独立性と信頼性を高めます。
3.  **`attempts` カウンタと `socktest.FilterClose` の導入**:
    ```go
    var mu sync.Mutex
    var attempts int
    sw.Set(socktest.FilterClose, func(so *socktest.Status) (socktest.AfterFilter, error) {
        mu.Lock()
        attempts++
        mu.Unlock()
        return nil, errTimedout
    })
    ```
    *   `attempts` は、`socktest.FilterClose` が呼び出された回数をカウントするための変数です。
    *   `mu sync.Mutex` は、`attempts` 変数への並行アクセスを安全にするためのミューテックスです。`TestDialTimeoutFDLeak` は複数のゴルーチンで `Dial` を呼び出すため、カウンタの更新は同期される必要があります。
    *   `sw.Set(socktest.FilterClose, ...)`: ソケットがクローズされようとするときに呼び出されるフックを設定します。このフックは `nil, errTimedout` を返します。これは、ソケットのクローズ操作をタイムアウトエラーとして処理し、ソケットが実際には閉じられないようにシミュレートします。これにより、`Dial` 呼び出しがタイムアウトするたびにこのフックが呼び出され、`attempts` がインクリメントされます。
4.  **テスト結果の検証方法の変更**:
    ```go
    if attempts < N {
        t.Errorf("got %d; want >= %d", attempts, N)
    }
    ```
    以前は `len(after) != len(before)` でFDリークをチェックしていましたが、この変更により、`attempts` カウンタが `N`（`Dial` の試行回数）以上であることを確認するようになりました。これは、`Dial` 呼び出しが `errTimedout` で失敗し、`FilterClose` が期待通りに呼び出されたことを検証するものです。これにより、TCP同時オープン時のソケット状態追跡の不確実性を回避し、テストの信頼性を向上させています。

### `src/net/timeout_test.go` の変更点

`TestDialTimeout` でも同様に、TCP同時オープン時のソケットのオープン/クローズのジッターバグを回避するために、以下の変更が加えられています。

1.  **`defer` 関数によるクリーンアップの強化**: `dial_test.go` と同様に、テスト終了時に `FilterClose` を解除し、`forceCloseSockets()` を呼び出す `defer` 関数が追加されています。
2.  **`socktest.FilterClose` の設定**:
    ```go
    sw.Set(socktest.FilterClose, func(so *socktest.Status) (socktest.AfterFilter, error) {
        return nil, errTimedout
    })
    ```
    `TestDialTimeoutFDLeak` と同様に、ソケットクローズ時に `errTimedout` を返す `FilterClose` フックが設定されます。これにより、タイムアウトテストのシナリオにおいて、ソケットのクローズ挙動をより制御しやすくし、テストの安定性を向上させています。

これらの変更により、TCP同時オープンという特殊なネットワークシナリオにおいても、`socktest` がソケットの状態をより確実にシミュレート・監視できるようになり、テストのflakinessが解消されました。

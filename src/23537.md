# [インデックス 23537] ファイルの概要

このコミットは、Goコンパイラの内部（`cmd/internal/gc`）におけるエスケープ解析の挙動を改善するものです。具体的には、スタックに割り当てるには大きすぎる型（配列など）をヒープに移動させるチェックを、エスケープ解析のフェーズに統合しました。これにより、大きな型がヒープに移動する際に、その中に含まれるポインタが正しくエスケープしていると認識され、スタックポインタのヒープへのリークという潜在的なバグを防ぎます。

## コミット

```
cmd/internal/gc: move check for large-hence-heap-allocated types into escape analysis

Before this change, the check for too-large arrays (and other large
types) occurred after escape analysis.  If the data moved off stack
and onto the heap contained any pointers, it would therefore escape,
but because the too-large check occurred after escape analysis this
would not be recorded and a stack pointer would leak to the heap
(see the modified escape_array.go for an example).

Some of these appear to remain, in calls to typecheck from within walk.

Also corrected a few comments in escape_array.go about "BAD"
analysis that is now done correctly.

Enhanced to move aditional EscNone-but-large-so-heap checks into esc.c.
```

## 変更の背景

Goコンパイラは、プログラムの実行効率を最大化するために、変数をスタックとヒープのどちらに割り当てるかを決定する「エスケープ解析」を行います。スタックは高速ですがサイズに限りがあり、ヒープは柔軟ですがガベージコレクションのオーバーヘッドがあります。

このコミット以前は、Goコンパイラは「スタックに割り当てるには大きすぎる型（例えば、非常に大きな配列）」をヒープに移動させる処理を、エスケープ解析が完了した「後」に行っていました。この順序には問題がありました。もし、スタックに割り当てられるはずだった大きな型が、その中にポインタを含んでおり、かつそのポインタが関数のスコープ外に「エスケープしない」とエスケープ解析で判断されていた場合、その大きな型が後からヒープに移動されると、その中のポインタは実際にはヒープ上に存在することになります。しかし、エスケープ解析の段階ではそのポインタはスタックポインタとして扱われていたため、ヒープ上にスタックポインタが「リーク」するという不整合が生じ、ランタイムエラーやクラッシュの原因となる可能性がありました。

この変更の目的は、この不整合を解消し、コンパイラの健全性を向上させることです。

## 前提知識の解説

### Goのメモリ管理（スタックとヒープ）

*   **スタック (Stack)**: 関数呼び出しやローカル変数の格納に使われるメモリ領域です。LIFO (Last-In, First-Out) 構造で、非常に高速にアクセスできます。Goでは、変数が関数のスコープ内で完結し、そのアドレスが関数の外に渡されない（エスケープしない）場合にスタックに割り当てられます。スタックは通常、サイズが限られています。
*   **ヒープ (Heap)**: プログラム実行中に動的にメモリを確保する領域です。スタックよりもアクセスは遅いですが、より大きなデータを柔軟に扱うことができます。Goでは、変数が関数のスコープ外にエスケープする場合や、コンパイラがスタックに割り当てられないと判断した場合にヒープに割り当てられます。ヒープに割り当てられたメモリは、Goのガベージコレクタによって管理されます。

### エスケープ解析 (Escape Analysis)

Goコンパイラの重要な最適化の一つで、変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを決定する静的解析です。

*   **エスケープする (Escape)**: 変数の寿命が、それを宣言した関数のスコープを超えて続く可能性がある場合、その変数は「エスケープする」と判断されます。例えば、関数の戻り値としてポインタを返す場合や、グローバル変数にポインタを代入する場合などです。エスケープする変数はヒープに割り当てられます。
*   **エスケープしない (Not Escape)**: 変数の寿命が、それを宣言した関数のスコープ内で完結する場合、その変数は「エスケープしない」と判断されます。このような変数はスタックに割り当てられます。

エスケープ解析は、ガベージコレクションの負荷を減らし、プログラムのパフォーマンスを向上させるために非常に重要です。

### 大きな型 (Large Types) の扱い

Goコンパイラには、スタックオーバーフローを防ぐため、特定のサイズ（`MaxStackVarSize`）を超える大きな型（特に大きな配列や構造体）は、たとえエスケープ解析でエスケープしないと判断されても、強制的にヒープに割り当てるというポリシーがあります。これは、スタックのサイズが限られているため、非常に大きなデータをスタックに置くとすぐにスタックを使い果たしてしまう可能性があるためです。

## 技術的詳細

このコミットの核心は、Goコンパイラの`cmd/compile/internal/gc`パッケージにおけるエスケープ解析のロジックの再構築です。

1.  **大きな型のヒープ割り当てチェックの統合**:
    *   以前は、`movelarge`という独立したフェーズで、`MaxStackVarSize`を超える大きな型をヒープに移動させていました。
    *   この変更により、このチェックが`esc.go`内のエスケープ解析（`esc`関数）の内部に移動されました。
    *   具体的には、`esc`関数内でノード`n`が`EscHeap`（ヒープにエスケープ）とマークされていない場合でも、以下の条件のいずれかを満たすと強制的に`EscHeap`に設定されるようになりました。
        *   `n.Type.Width > MaxStackVarSize`: 型のサイズが`MaxStackVarSize`を超える場合。
        *   `n.Op == ONEW && n.Type.Type.Width >= 1<<16`: `new`演算子で作成される型が特定のサイズ（65536バイト）を超える場合。
        *   `n.Op == OMAKESLICE && !isSmallMakeSlice(n)`: `make`で作成されるスライスが`isSmallMakeSlice`関数で「小さい」と判断されない場合。`isSmallMakeSlice`は、スライスの要素数と要素のサイズに基づいて、スライスがスタックに割り当てられるほど小さいかどうかを判断する新しいヘルパー関数です。
    *   この統合により、大きな型がヒープに移動する決定がエスケープ解析の過程で行われるため、その型に含まれるポインタも同時に正しくエスケープしているとマークされるようになります。これにより、スタックポインタのヒープへのリークが防止されます。

2.  **`movelarge`関数の削除**:
    *   `src/cmd/compile/internal/gc/pgen.go`から、以前大きな型をヒープに移動させていた`movelarge`関数とその関連ロジックが完全に削除されました。これは、その機能が`esc.go`に統合されたためです。

3.  **`walk.go`からの関連チェックの削除**:
    *   `src/cmd/compile/internal/gc/walk.go`内の`walkexpr`関数から、`ONEW`および`OMAKESLICE`に関する大きな型のチェックロジックが削除されました。これらのチェックも`esc.go`に集約されました。
    *   `isSmallMakeSlice`ヘルパー関数が`walk.go`に追加され、`OMAKESLICE`のサイズチェックを抽象化しています。

4.  **コメントの修正とテストケースの更新**:
    *   `src/cmd/compile/internal/gc/lex.go`のコメントが更新され、大きな値がエスケープ解析中にスタックから移動されることの重要性が強調されました。
    *   `test/escape_array.go`と`test/escape5.go`のテストファイルが更新され、新しいエスケープ解析の挙動、特に大きな配列や`new`、`make`で作成される大きなスライスが正しくヒープに割り当てられ、ポインタがエスケープするとマークされることを検証するようになりました。`escape_array.go`の「BAD」というコメントが修正され、解析の改善が示唆されています。

## コアとなるコードの解説

### `esc.go`の変更

`esc.go`に追加されたコードブロックは、エスケープ解析の主要なループ内で実行されます。`n.Esc != EscHeap`という条件は、まだヒープにエスケープするとマークされていないノードに対してのみ、以下のチェックを適用することを示しています。

*   `n.Type.Width > MaxStackVarSize`: これは、変数の型がGoコンパイラがスタックに割り当てると判断する最大サイズ（`MaxStackVarSize`）を超えているかどうかをチェックします。超えている場合、その変数は強制的にヒープに割り当てられます。
*   `n.Op == ONEW && n.Type.Type.Width >= 1<<16`: `new`キーワードを使って作成されるオブジェクトが、65536バイト（`1<<16`）以上のサイズであるかをチェックします。これも、大きすぎるオブジェクトをヒープに強制的に割り当てるための条件です。
*   `n.Op == OMAKESLICE && !isSmallMakeSlice(n)`: `make`キーワードで作成されるスライスが、`isSmallMakeSlice`関数によって「小さい」と判断されない場合、つまり大きすぎると判断された場合にヒープに割り当てられます。

これらの条件のいずれかを満たす場合、ノード`n`の`Esc`フィールドは`EscHeap`に設定され、`addrescapes(n)`と`escassign(e, &e.theSink, n)`が呼び出されます。これにより、このノードがヒープにエスケープすると明示的にマークされ、そのアドレスがエスケープしていると記録されます。この変更により、大きな型がヒープに移動する際に、その中のポインタも正しくエスケープしていると認識されるようになり、スタックポインタのリークが防止されます。

### `pgen.go`の変更

`movelarge`関数は、以前は`MaxStackVarSize`を超えるローカル変数をヒープに移動させる役割を担っていました。この関数が完全に削除されたのは、その機能が`esc.go`内のエスケープ解析に統合されたためです。これにより、コンパイラのコードパスが簡素化され、大きな型の処理が一元化されました。

### `walk.go`の変更

`walk.go`からは、`ONEW`と`OMAKESLICE`に関する大きな型のチェックロジックが削除されました。これは、これらのチェックが`esc.go`に移動されたためです。代わりに、`isSmallMakeSlice`という新しいヘルパー関数が追加されました。この関数は、`make`で作成されるスライスがスタックに割り当てられるほど小さいかどうかを判断するためのロジックをカプセル化しています。この変更により、`walk.go`のコードがクリーンになり、エスケープ解析のロジックが`esc.go`に集中するようになりました。

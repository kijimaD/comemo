## 変更の背景

Go言語では、配列の長さはコンパイル時に決定される定数である必要があります。これは、配列が固定サイズのメモリブロックとして割り当てられるためです。もし配列の長さが実行時まで決定できない場合、コンパイラはメモリを適切に割り当てることができません。

以前のGoコンパイラでは、非定数な式が配列の境界として指定された場合、一律に「invalid array bound」（無効な配列境界）という一般的なエラーメッセージを出力していました。このメッセージは、配列の境界が無効であることは示しますが、具体的に「なぜ無効なのか」、つまり「定数ではないから」という理由を明確に伝えていませんでした。これにより、開発者はエラーの原因を特定し、修正するまでに余分な時間を要する可能性がありました。

このコミットは、ユーザーがより迅速に問題の原因を特定できるよう、エラーメッセージの具体性を向上させることを目的としています。特に、配列の境界が整数型であり、かつリテラル（定数）ではない場合に、「non-constant array bound」（非定数な配列境界）という、より詳細で分かりやすいメッセージを出すように変更されました。これにより、開発者はコードのどこを修正すべきか、より明確なヒントを得ることができます。

関連するIssue #8196は、このエラーメッセージの曖昧さについて報告しており、このコミットはその問題を解決するために作成されました。

## 前提知識の解説

### Go言語における配列

Go言語の配列は、同じ型の要素を固定数だけ格納できるデータ構造です。配列の長さは型の一部であり、コンパイル時に既知の定数である必要があります。
例: `var a [10]int` は長さ10の整数配列を宣言します。この `10` は定数でなければなりません。配列の長さがコンパイル時に決定されることで、Goランタイムは効率的なメモリ割り当てとアクセスを提供できます。

### コンパイル時定数 (Compile-time Constants)

Go言語では、変数の値がコンパイル時に決定される「定数」であるかどうかが重要です。配列の長さ、`case`文のラベル、`iota`など、多くのGoの機能はコンパイル時定数を要求します。これは、コンパイラがコードを最適化したり、メモリレイアウトを決定したりするために必要です。コンパイル時定数でない値（例えば、関数呼び出しの結果や実行時に決定される変数など）を配列の長さに使用しようとすると、コンパイルエラーが発生します。

### Goコンパイラ (`cmd/gc`)

`cmd/gc`は、Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っています。コンパイルの過程で、構文解析、型チェック、最適化、コード生成など、様々なフェーズがあります。このコミットが変更を加えている`typecheck.c`は、ソースコードの型がGo言語の型システムルールに適合しているかを検証する型チェックフェーズの一部です。

### 型チェック (Type Checking)

型チェックは、プログラムが型システムの一貫性ルールに従っていることを検証するコンパイルフェーズです。これにより、型に関するエラー（例えば、整数型を期待する場所に文字列型を渡すなど）を早期に発見し、実行時エラーを防ぎます。配列の境界が定数であるかどうかの検証も、この型チェックの一部として行われます。型チェックは、プログラムの安全性と信頼性を高める上で非常に重要な役割を果たします。

### `yyerror` 関数

`yyerror`は、`yacc`や`bison`のようなパーサジェネレータによって生成されるパーサ内で、構文エラーやセマンティックエラーを報告するために使用される一般的な関数名です。Goコンパイラの`cmd/gc`も、内部的にパーサジェネレータを使用しているため、エラー報告に`yyerror`のような関数が使われています。この関数は、指定されたフォーマット文字列と引数に基づいてエラーメッセージを標準エラー出力に出力し、コンパイルプロセスを停止させることが一般的です。

### `toint` 関数

Goコンパイラの内部関数で、与えられたノード（式）を整数値に変換しようとします。配列の境界が定数であるかを評価する際に、その値を取得するために使用されます。この関数は、変換が成功した場合は整数値を返し、失敗した場合はエラーを報告する役割を担います。

### `isint` と `T` (型システム)

`isint`は、Goコンパイラ内部で、特定の型が整数型であるかを判定するためのフラグ配列または関数を指します。`l->type->etype`は、ノード`l`の基底型（element type）を示しており、`isint[l->type->etype]`はその基底型が整数型であるかをチェックしています。
`T`は、Goコンパイラの型システムにおける特定の型を表す内部的な定数または変数であると考えられます。`l->type != T`という条件は、`l`（配列の境界を表すノード）の型が特定の内部型`T`ではないことをチェックしており、これはコンパイラが内部的に使用する特殊な型を除外するためのものです。

### `OLITERAL`

`OLITERAL`は、Goコンパイラ内部で、ノードがリテラル（定数）であることを示すオペレーションコードまたはフラグです。コンパイラは、ソースコードの各要素を内部的なノードとして表現し、それぞれのノードにオペレーションコードを割り当てます。`l->op != OLITERAL`という条件は、ノード`l`がリテラルではないことをチェックしています。これにより、コンパイル時に値が確定しない式を識別します。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/gc/typecheck.c`ファイル内の`reswitch`ラベルの直下にある配列境界チェックロジックにあります。この部分は、Goコンパイラが配列の長さを評価し、それが有効な定数であるかを検証する役割を担っています。

変更前は、配列の境界が定数として評価できない場合、またはその他の理由で無効な場合に、一律に以下のエラーメッセージを出力していました。

```c
yyerror("invalid array bound %N", l);
```
ここで`%N`は、エラーが発生したノード（式）の情報を出力するためのフォーマット指定子です。

変更後は、このエラー報告のロジックがより詳細になりました。新しい`if`文が導入され、特定の条件を満たす場合にのみ、より具体的なエラーメッセージを出力するように分岐しています。

```c
if(l->type != T && isint[l->type->etype] && l->op != OLITERAL)
    yyerror("non-constant array bound %N", l);
else
    yyerror("invalid array bound %N", l);
```

この`if`文の条件は以下の3つの部分から構成されており、これらがすべて真である場合に「non-constant array bound」エラーが出力されます。

1.  **`l->type != T`**: 配列の境界を表すノード`l`の型が、コンパイラ内部で特殊な目的で使用される型`T`ではないことを確認します。これは、通常のユーザーが記述するコードにおける型を対象とするためのフィルタリングです。
2.  **`isint[l->type->etype]`**: ノード`l`の基底型（`etype`）が整数型であることを確認します。配列の長さは整数でなければならないため、このチェックは必須です。`isint`は、各型が整数型であるかを示すブール値の配列であると推測されます。
3.  **`l->op != OLITERAL`**: ノード`l`がリテラル（定数）ではないことを確認します。`OLITERAL`はコンパイラ内部でリテラルを表すオペレーションコードです。この条件が真であるということは、式がコンパイル時に定数として評価できないことを意味します。

これらの条件がすべて真である場合、つまり「配列の境界が整数型であり、かつリテラル（定数）ではない」という状況であれば、より具体的なエラーメッセージ「non-constant array bound %N」が出力されます。それ以外の場合（例えば、配列の境界に文字列や浮動小数点数、nilなど、そもそも配列の境界として不適切な型が指定された場合）は、引き続き一般的な「invalid array bound %N」が出力されます。

この変更により、コンパイラはエラーの原因をより正確に診断し、開発者に「配列の長さが定数ではない」という具体的なフィードバックを提供できるようになります。これにより、開発者は問題の根本原因を迅速に理解し、修正に取り掛かることができます。

また、`test/fixedbugs/bug255.go`ファイルも更新され、新しいエラーメッセージの動作を検証するテストケースが追加されました。

変更前は、`var f [e]int`のような非定数な配列境界のケースでは、`ERROR "invalid array bound|not constant"`というエラーを期待していました。

変更後には、以下の新しいテストケースが追加されました。

```go
var h [len(a)]int  // ok
```
この行では、`len(a)`が使用されています。`a`は`var a [10]int`として定義された固定長の配列であるため、`len(a)`はコンパイル時に定数`10`として評価されます。したがって、この行は問題なくコンパイルされ、エラーは発生しません。これは、`len`関数が定数引数に対しては定数結果を返すことを示しています。

```go
func ff() string

var i [len([1]string{ff()})]int // ERROR "non-constant array bound|not constant"
```
この行では、`len([1]string{ff()})`が配列の境界として使用されています。`ff()`は関数呼び出しであり、その結果はコンパイル時には不明です。したがって、`[1]string{ff()}`という配列リテラル自体は定数ではありません。その結果、`len`関数の引数も非定数となり、`len([1]string{ff()})`全体も非定数式となります。このため、新しいエラーメッセージ「non-constant array bound」が期待されるようになりました。このテストケースの追加により、このコミットで導入された新しいエラーメッセージが正しく機能することを確認しています。

## コアとなるコードの解説

### `src/cmd/gc/typecheck.c` の変更

この変更は、Goコンパイラの型チェックフェーズにおいて、配列の境界が評価される部分にあります。
`reswitch`ラベルは、コンパイラが様々な種類のノード（ここでは配列の境界を表すノード`l`）を処理するための分岐点です。
`default`ケースは、`l`がリテラルとして直接評価できない場合に実行されます。
変更前は、この`default`ケースで一律に「invalid array bound」エラーを出していました。

変更後は、`if`文が追加され、より具体的な条件に基づいてエラーメッセージを分岐させています。
-   **`l->type != T`**: ノード`l`の型が、コンパイラ内部の特定の型`T`ではないことを確認します。これは、通常のユーザーコードにおける型を対象とするための条件です。
-   **`isint[l->type->etype]`**: ノード`l`の基底型（`etype`）が整数型であるかをチェックします。`isint`は、各型が整数型であるかを示すブール値の配列であると推測されます。
-   **`l->op != OLITERAL`**: ノード`l`がリテラル（定数）ではないことをチェックします。`OLITERAL`は、コンパイラがノードをリテラルとして認識するための内部的なオペレーションコードです。

これらの条件がすべて真である場合、つまり「整数型だが定数ではない」という状況であれば、`yyerror("non-constant array bound %N", l);`が実行され、より具体的なエラーメッセージが出力されます。それ以外の場合（例えば、配列の境界に文字列や浮動小数点数、nilなどが指定された場合）は、引き続き`yyerror("invalid array bound %N", l);`が実行されます。
この修正により、コンパイラはエラーの原因をより正確に特定し、開発者に対してより有用な情報を提供できるようになります。

### `test/fixedbugs/bug255.go` の変更

このテストファイルは、Goコンパイラの配列境界チェックの挙動を検証するためのものです。
追加された`var h [len(a)]int`は、`len(a)`がコンパイル時に定数として評価できるため、エラーにならないことを示しています。これは、`a`が固定長の配列であり、その長さはコンパイル時に既知だからです。このテストケースは、`len`関数が定数引数に対しては定数結果を返すというGoの仕様を反映しています。

追加された`var i [len([1]string{ff()})]int`は、`ff()`という関数呼び出しが含まれているため、`len`関数の引数がコンパイル時に定数として評価できません。関数呼び出しの結果は実行時まで確定しないため、この式全体が非定数となります。このため、新しいエラーメッセージ「non-constant array bound」が期待されるようになりました。このテストケースの追加により、`cmd/gc`の変更が意図通りに機能し、適切なエラーメッセージが出力されることが保証されます。

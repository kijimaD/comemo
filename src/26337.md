# [インデックス 26337] ファイルの概要

このコミットは、Goの標準ライブラリ`net/http`パッケージ内の`http.Redirect`関数が、スキームを持たないURL（例: `//example.com/path`）を正しく処理できるようにするための変更です。これにより、ブラウザの挙動やHTTP/1.1のドラフト仕様に準拠し、より柔軟なリダイレクトが可能になります。

## 変更の背景

HTTPリダイレクトにおいて、`Location`ヘッダーに指定されるURLの形式は、HTTP/1.1の仕様の変遷とともに進化してきました。初期のRFC 2616では、`Location`ヘッダーには完全な絶対URIが必須とされていました。しかし、その後のRFC 7231やRFC 9110といった新しい仕様では、相対URLの使用が明示的に許可されるようになりました。

スキームレスURL（プロトコル相対URLとも呼ばれ、`//example.com/path`のように`http:`や`https:`といったスキーム部分を省略したもの）は、この相対URLの一種です。多くのモダンブラウザは、`Location`ヘッダー内のスキームレスURLを既にサポートしており、現在のHTTP/1.1仕様でも有効な形式とされています。

しかし、このコミットが作成された時点のGo標準ライブラリの`net/http.Redirect`関数は、スキームレスURLを適切に処理できていませんでした。具体的には、スキームがないURLを常に相対パスとして解釈してしまう可能性があり、`//example.com/path`のようなURLが意図しないリダイレクトを引き起こす原因となっていました。このコミットは、このギャップを埋め、Goの`http.Redirect`がブラウザや最新のHTTP仕様に沿った挙動をするようにするために導入されました。

## 前提知識の解説

### HTTPリダイレクトとLocationヘッダー

HTTPリダイレクトは、ウェブサーバーがクライアント（ブラウザなど）に対して、要求されたリソースが別のURLに移動したことを伝えるメカニズムです。これには、`3xx`系のHTTPステータスコード（例: `301 Moved Permanently`, `302 Found`, `307 Temporary Redirect`）が使用されます。リダイレクト先のURLは、HTTPレスポンスヘッダーの`Location`フィールドに指定されます。

### URLスキームとスキームレスURL（プロトコル相対URL）

*   **URLスキーム**: URLの先頭にある`http://`や`https://`、`ftp://`などの部分を指します。これは、リソースにアクセスするためのプロトコルを示します。
*   **スキームレスURL（プロトコル相対URL）**: `//`で始まり、スキーム部分が省略されたURLです（例: `//example.com/path`）。この形式のURLは、現在のページのスキーム（`http`または`https`）を継承して解釈されます。例えば、`https://current-site.com`から`//example.com/path`にリダイレクトされる場合、ブラウザは`https://example.com/path`としてアクセスします。これは、HTTPとHTTPSの両方で機能するリソース（画像、スクリプト、リダイレクト先など）を埋め込む際に便利です。

### Goの`net/url.Parse`の動作

Goの`net/url`パッケージの`Parse`関数は、URL文字列を解析し、`url.URL`構造体に変換します。この構造体には、スキーム、ホスト、パスなどのURLの各要素が格納されます。`url.Parse`はRFC 3986に基づいてURLを解析しますが、スキームがないURLの解釈には注意が必要です。

例えば、`url.Parse("example.com/path")`のようなスキームのない文字列を解析した場合、`Host`フィールドが空で`Path`フィールドに`/example.com/path`が格納されるなど、意図しない相対パスとして解釈されることがあります。しかし、`url.Parse("//example.com/path")`のように`//`で始まるスキームレスURLの場合、`Host`フィールドに`example.com`が、`Path`フィールドに`/path`が正しく格納されます。これは、`//`がネットワークパス参照を示すためです。

### Goの`net/http.Redirect`の基本的な機能

Goの`net/http.Redirect`関数は、指定された`ResponseWriter`、`Request`、リダイレクト先URL文字列、およびHTTPステータスコードを使用して、HTTPリダイレクトレスポンスを生成し、クライアントに送信します。この関数は、リダイレクト先のURLが絶対URLであるか相対URLであるかを判断し、必要に応じて現在のリクエストのURLを基に絶対URLを構築します。

## 技術的詳細

このコミットの核心は、`http.Redirect`関数がリダイレクト先のURLを絶対URLとして扱うべきか、それとも現在のリクエストに対する相対URLとして扱うべきかを判断するロジックの改善にあります。

変更前は、`http.Redirect`関数内で`url.Parse`によって解析されたURLオブジェクト`u`に対して、`u.Scheme == ""`という条件のみでスキームの有無を判断していました。この条件が真の場合、Goの標準ライブラリは、そのURLを現在のリクエストに対する相対パスとして扱おうとしました。

しかし、`//foobar.com/baz`のようなスキームレスURLは、`url.Parse`によって解析されると`u.Scheme`は空ですが、`u.Host`には`foobar.com`が設定されます。変更前のロジックでは、`u.Scheme == ""`が真となるため、このURLも相対パスとして扱われ、例えば`http://example.com/qux/`からのリダイレクトで`Location`ヘッダーが`/qux//foobar.com/baz`のようになるなど、誤ったリダイレクトが発生する可能性がありました。

このコミットでは、この問題を解決するために、絶対/相対URLのチェック条件に`u.Host == ""`を追加しました。新しい条件は`u.Scheme == "" && u.Host == ""`となります。

*   `u.Scheme == "" && u.Host == ""`が真の場合: これは、スキームもホストも持たない純粋な相対パス（例: `/foo/bar`や`../baz`）であることを意味します。この場合、`http.Redirect`は現在のリクエストのURLを基に絶対URLを構築します。
*   `u.Scheme == ""`が真だが`u.Host != ""`の場合: これは、`//foobar.com/baz`のようなスキームレスURLであることを意味します。この場合、`u.Host`が存在するため、`http.Redirect`はこれを絶対URL（プロトコル相対URL）として扱い、そのまま`Location`ヘッダーに設定します。これにより、ブラウザが現在のページのスキームを継承してリダイレクトを処理できるようになります。

この変更により、`http.Redirect`はスキームレスURLを正しく認識し、意図した通りのリダイレクト動作を実現できるようになりました。

また、`oldpath`変数の初期化が、その変数が実際に使用されるコードブロックの内部に移動されました。これは、変数のスコープを最小限に抑え、コードの可読性と保守性を向上させるための一般的なプログラミングプラクティスです。

## コアとなるコードの解説

### `src/net/http/server.go`の`Redirect`関数

変更の核心は、`Redirect`関数内の条件分岐です。

```go
-		oldpath := r.URL.Path
-		if oldpath == "" { // should not happen, but avoid a crash if it does
-			oldpath = "/"
-		}
-		if u.Scheme == "" {
+		if u.Scheme == "" && u.Host == "" {
+			oldpath := r.URL.Path
+			if oldpath == "" { // should not happen, but avoid a crash if it does
+				oldpath = "/"
+			}
+
 			// no leading http://server
 			if urlStr == "" || urlStr[0] != '/' {
 				// make relative path absolute
```

*   **変更前**: `if u.Scheme == ""`という条件のみで、リダイレクト先のURL `u`がスキームを持たない場合に、それを相対パスとして扱っていました。この場合、`r.URL.Path`（現在のリクエストのパス）を基に絶対パスを構築しようとします。
*   **変更後**: 条件が`if u.Scheme == "" && u.Host == ""`に変更されました。
    *   この新しい条件が真となるのは、URL `u`がスキームもホストも持たない場合、つまり純粋な相対パス（例: `/foo/bar`）である場合のみです。このとき、以前と同様に`r.URL.Path`を基にした絶対パスの構築が行われます。
    *   もし`u.Scheme == ""`だが`u.Host != ""`の場合（例: `//foobar.com/baz`のようなスキームレスURL）、この`if`ブロックには入らず、`u`はそのまま`Location`ヘッダーに設定されます。これにより、スキームレスURLが正しくプロトコル相対URLとして扱われ、ブラウザが現在のスキームを継承してリダイレクトを実行できるようになります。
*   **`oldpath`変数の移動**: `oldpath`変数の宣言と初期化が、それが使用される`if u.Scheme == "" && u.Host == ""`ブロックの内部に移動されました。これにより、変数のスコープが限定され、コードの局所性が高まり、保守性が向上します。

### `src/net/http/serve_test.go`の`TestRedirectURLFormat`関数

このコミットでは、`TestRedirectURLFormat`という新しいテスト関数が追加されました。このテストは、`http.Redirect`関数が様々な形式のURL（特にスキームレスURL）をどのように処理するかを検証することを目的としています。

*   **テストケース**: `tests`スライスには、以下のような多様な入力URL (`in`) と期待される`Location`ヘッダーの値 (`want`) のペアが含まれています。
    *   通常のHTTP/HTTPS URL (`http://foobar.com/baz`, `https://foobar.com/baz`)
    *   カスタムスキームURL (`test://foobar.com/baz`)
    *   **スキームレスURL (`//foobar.com/baz`)**: このテストケースが、今回の変更の主要な検証ポイントです。期待される出力も`//foobar.com/baz`であり、`http.Redirect`がこれをそのまま`Location`ヘッダーに設定することを検証します。
    *   ルート相対パス (`/foobar.com/baz`)
    *   カレントパス相対パス (`foobar.com/baz`)
    *   上位ディレクトリ相対パス (`../quux/foobar.com/baz`)
    *   スラッシュの数が誤っているURL (`///foobar.com/baz`)
*   **テストロジック**: 各テストケースについて、`httptest.NewRecorder()`でレスポンスレコーダーを作成し、`Redirect`関数を呼び出します。その後、レコーダーの`Header().Get("Location")`で取得した`Location`ヘッダーの値が、期待される`want`値と一致するかを検証します。

このテストの追加により、スキームレスURLのサポートが正しく実装されたこと、および他のURL形式に対する既存の挙動が維持されていることが保証されます。

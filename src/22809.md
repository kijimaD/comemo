## 元コミット内容

このコミットの主な内容は、Go言語のランタイムにおいて、ARM64アーキテクチャ向けに`runtime.cmpstring`関数と`bytes.Compare`関数のアセンブリ実装を追加することです。これにより、これらの比較操作のパフォーマンスが大幅に改善されました。コミットメッセージには、様々なベンチマーク結果が示されており、特に大きなバイトスライスの比較において、実行時間が最大で約80%削減され、スループットが5倍以上向上していることが明確に示されています。

## 変更の背景

Go言語は、その高いパフォーマンスと並行処理能力で知られていますが、その基盤を支えるランタイムの最適化は常に重要な課題です。文字列やバイトスライスの比較は、プログラムの様々な場所で頻繁に行われる基本的な操作です。これらの操作が効率的であればあるほど、アプリケーション全体のパフォーマンスに大きな影響を与えます。

ARM64アーキテクチャは、スマートフォン、タブレット、サーバーなど、幅広いデバイスで採用が進んでおり、Go言語がこれらのプラットフォームで最高のパフォーマンスを発揮するためには、各アーキテクチャに特化した最適化が不可欠です。

このコミットは、ARM64環境における`runtime.cmpstring`（Goランタイム内部で文字列比較に使用される）と`bytes.Compare`（`bytes`パッケージでバイトスライス比較に使用される）の性能ボトルネックを解消することを目的としています。アセンブリ言語でこれらの関数を実装することで、Goコンパイラが生成するコードでは実現できない、より低レベルでCPUの特性を最大限に活かした最適化が可能になります。具体的には、レジスタの効率的な利用、特定のCPU命令の活用、分岐予測の最適化などが挙げられます。

## 前提知識の解説

### Go言語の`bytes.Compare`と`strings.Compare`

*   **`bytes.Compare(a, b []byte) int`**:
    この関数は、2つのバイトスライス`a`と`b`を辞書順に比較します。戻り値は以下のいずれかです。
    *   `0`: `a`と`b`が等しい場合。
    *   `-1`: `a`が`b`より辞書順で小さい場合。
    *   `+1`: `a`が`b`より辞書順で大きい場合。
    `bytes.Compare`は、バイトスライスの順序を決定する必要がある場合に有用です。ただし、単に等しいかどうかをチェックするだけであれば、`bytes.Equal(a, b []byte) bool`を使用することが推奨されます。`bytes.Equal`は、長さが異なる場合に早期に`false`を返すなど、等値性チェックに特化した最適化が施されているため、多くの場合でより高速です。

*   **`strings.Compare(a, b string) int`**:
    この関数は、2つの文字列`a`と`b`を辞書順に比較します。戻り値は`bytes.Compare`と同様に-1, 0, 1です。
    Go言語では、文字列の等値性チェックには通常`==`演算子を使用します。これはコンパイラによって最適化され、多くの場合で`strings.Compare`よりも高速です。`strings.Compare`は、主に`bytes.Compare`との一貫性を提供するために存在し、文字列の順序を決定する必要がある場合に使用されます。

### `runtime.cmpstring`

`runtime.cmpstring`は、Goランタイムの内部で使用される文字列比較関数です。これはGo言語のユーザーが直接呼び出すことを意図したものではなく、コンパイラが文字列比較演算子（例: `==`, `<`, `>`)を処理する際や、他のランタイム内部関数から利用されます。ランタイムの根幹をなす部分であるため、そのパフォーマンスはGoプログラム全体の実行速度に直結します。この関数は、特定のアーキテクチャ向けにアセンブリ言語で実装されることで、最大限の効率が追求されます。

### アセンブリ言語による最適化

Go言語のランタイムや標準ライブラリの一部では、C言語やGo言語ではなく、アセンブリ言語で記述されたコードが使用されることがあります。これは、以下のような理由によります。

*   **低レベルな制御**: CPUのレジスタ、キャッシュ、特定の命令セット（SIMD命令など）を直接制御することで、Go言語やC言語では不可能なレベルの最適化を実現できます。
*   **パフォーマンスの限界突破**: 非常に頻繁に実行されるクリティカルなパス（例: メモリコピー、文字列比較、コンテキストスイッチなど）において、わずかな命令数の削減やパイプラインの最適化が、全体として大きな性能向上につながります。
*   **アーキテクチャ固有の最適化**: 各CPUアーキテクチャ（x86-64, ARM64, PowerPCなど）には独自の特性と命令セットがあります。アセンブリ言語を使用することで、そのアーキテクチャに特化した最適なコードを記述できます。

### ARM64アーキテクチャ

ARM64（AArch64）は、ARMv8-Aアーキテクチャ以降で導入された64ビット命令セットアーキテクチャです。モバイルデバイスからサーバー、組み込みシステムまで幅広く利用されています。

*   **レジスタ**: 31個の汎用64ビットレジスタ（X0-X30）と、ゼロレジスタ（XZR）を持ちます。関数呼び出し規約により、これらのレジスタは引数渡し、戻り値、一時的な値の保持などに効率的に利用されます。
*   **命令セット**: 固定長32ビットの命令を持ち、ロード/ストア命令、データ処理命令、分岐命令などが含まれます。条件付き実行命令（`CSEL`など）は、分岐予測ミスによるペナルティを避けるために重要です。
*   **メモリモデル**: ロード/ストア命令を使用してメモリとレジスタ間でデータを転送します。効率的なメモリアクセスはパフォーマンスに直結します。

### ベンチマークの読み方

コミットメッセージに記載されているベンチマーク結果は、コード変更による性能変化を定量的に示すものです。

*   **`ns/op` (nanoseconds per operation)**: 1回の操作にかかる平均時間（ナノ秒）。この値が小さいほど高速です。
*   **`MB/s` (megabytes per second)**: 1秒あたりに処理できるデータ量（メガバイト）。この値が大きいほど高速です。主にデータ処理スループットを示す際に用いられます。
*   **`delta`**: 変更前（old）と変更後（new）の`ns/op`の差分をパーセンテージで示したもの。負の値は高速化を意味します。
*   **`speedup`**: 変更後の速度が変更前の何倍になったかを示すもの。`new MB/s / old MB/s`で計算されます。

このコミットのベンチマークでは、特に`BenchmarkCompareBytesBig`のような大規模なバイトスライスの比較において、`ns/op`が大幅に減少し、`MB/s`が劇的に増加していることがわかります。これは、アセンブリ実装が大規模データ処理において非常に効果的であることを示しています。

## 技術的詳細

このコミットの核心は、`src/runtime/asm_arm64.s`に追加された`runtime.cmpbody`というアセンブリ関数です。この関数は、`runtime.cmpstring`と`bytes.Compare`の両方から呼び出される共通の比較ロジックを提供します。これにより、コードの重複を避けつつ、比較処理の最適化を一元的に行うことができます。

### `runtime.cmpbody`関数の詳細

`runtime.cmpbody`は、2つのメモリ領域（バイトスライスまたは文字列の基底アドレス）を比較し、その結果を-1、0、または+1で返します。

**エントリ時のレジスタの状態:**

*   `R0`: 1つ目のシーケンス（s1）の長さ
*   `R1`: 2つ目のシーケンス（s2）の長さ
*   `R2`: 1つ目のシーケンス（s1）の開始アドレス
*   `R3`: 2つ目のシーケンス（s2）の開始アドレス

**終了時のレジスタの状態:**

*   `R8`: 比較結果 (-1, 0, または +1)
*   `R4`, `R5`, `R6`: 内部で使用され、値が変更される（clobbered）

**比較ロジックのフロー:**

1.  **長さの比較と最小長の決定**:
    ```armasm
    CMP R0, R1
    CSEL    LT, R1, R0, R6 // R6 is min(R0, R1)
    ```
    まず、`CMP R0, R1`で2つのシーケンスの長さを比較します。
    `CSEL LT, R1, R0, R6`は条件付き選択命令です。もし`R0 < R1`（LT: Less Than）であれば`R1`（s2の長さ）を`R6`に格納し、そうでなければ`R0`（s1の長さ）を`R6`に格納します。これにより、`R6`には2つのシーケンスの短い方の長さが設定されます。これは、比較ループが短い方のシーケンスの終端を超えてアクセスしないようにするために重要です。

2.  **比較終了アドレスの計算**:
    ```armasm
    ADD R2, R6    // R2 is current byte in s1, R6 is last byte in s1 to compare
    ```
    `R2`（s1の開始アドレス）に`R6`（最小長さ）を加算することで、`R2`は比較すべきs1の最後のバイトの次のアドレス（または比較終了アドレス）を指すようになります。ループ内で`R2`がこのアドレスに達したら、バイトごとの比較は終了です。

3.  **バイトごとの比較ループ (`loop`ラベル)**:
    ```armasm
    loop:
        CMP R2, R6
        BEQ samebytes // all compared bytes were the same; compare lengths
        MOVBU.P 1(R2), R4
        MOVBU.P 1(R3), R5
        CMP R4, R5
        BEQ loop
    ```
    *   `CMP R2, R6`: 現在のs1のポインタ`R2`が、計算された比較終了アドレス`R6`に達したかをチェックします。
    *   `BEQ samebytes`: もし`R2`が`R6`に等しければ、これは短い方のシーケンスの全てのバイトが一致したことを意味します。この場合、バイトごとの比較は終了し、`samebytes`ラベルにジャンプして最終的な長さの比較を行います。
    *   `MOVBU.P 1(R2), R4`: `R2`が指すメモリから1バイトを符号なしで`R4`にロードし、その後`R2`を1バイト分インクリメントします（ポストインクリメント）。これはs1の現在のバイトを取得し、次のバイトへポインタを進める効率的な方法です。
    *   `MOVBU.P 1(R3), R5`: 同様に、`R3`が指すメモリから1バイトを符号なしで`R5`にロードし、`R3`を1バイト分インクリメントします。
    *   `CMP R4, R5`: ロードした2つのバイトを比較します。
    *   `BEQ loop`: もし2つのバイトが等しければ、ループの先頭に戻り、次のバイトの比較を続けます。

4.  **バイトが不一致の場合**:
    ```armasm
    // bytes differed
    MOVD    $1, R8
    CSNEG   LT, R8, R8, R8
    RET
    ```
    ループ内で`CMP R4, R5`の結果が不一致（`BEQ loop`が実行されない）の場合、バイトが異なることが判明します。
    *   `MOVD $1, R8`: まず、結果レジスタ`R8`に`1`を設定します。
    *   `CSNEG LT, R8, R8, R8`: 条件付き否定命令です。もし`R4 < R5`（LT: Less Than）であれば、`R8`の値を否定します（`1`が`-1`に）。これにより、s1のバイトがs2のバイトより小さければ`-1`、大きければ`1`が`R8`に設定されます。
    *   `RET`: 関数から戻ります。

5.  **全バイト一致後の長さ比較 (`samebytes`ラベル)**:
    ```armasm
    samebytes:
        MOVD    $1, R8
        CMP R0, R1
        CSNEG   LT, R8, R8, R8
        CSEL    EQ, ZR, R8, R8
        RET
    ```
    短い方のシーケンスの全てのバイトが一致した場合、このセクションに到達します。この時点で、どちらかのシーケンスがもう一方のプレフィックス（接頭辞）であるか、あるいは両者が完全に等しいかのどちらかです。
    *   `MOVD $1, R8`: まず、結果レジスタ`R8`に`1`を設定します。
    *   `CMP R0, R1`: 元の長さ`R0`（s1の長さ）と`R1`（s2の長さ）を比較します。
    *   `CSNEG LT, R8, R8, R8`: もし`R0 < R1`（s1がs2より短い）であれば、`R8`の値を否定します（`1`が`-1`に）。これにより、s1がs2のプレフィックスであれば`-1`が設定されます。
    *   `CSEL EQ, ZR, R8, R8`: 条件付き選択命令です。もし`R0 == R1`（EQ: Equal）であれば、ゼロレジスタ`ZR`（値は常に0）を`R8`に格納します。そうでなければ、現在の`R8`の値（`-1`または`1`）をそのまま`R8`に保持します。これにより、両者の長さが等しければ`0`が、s1がs2より長ければ`1`が設定されます。
    *   `RET`: 関数から戻ります。

### ARM64命令の役割

*   **`MOVD`**: 64ビットの値をレジスタ間で、または即値からレジスタへ移動します。
*   **`CMP`**: 2つのオペランドを比較し、結果に応じてプロセッサの状態フラグを設定します。
*   **`CSEL` (Conditional Select)**: 条件に基づいて2つのソースレジスタのいずれかの値をターゲットレジスタに選択的にコピーします。これにより、条件分岐を伴う命令シーケンスを、分岐予測ミスによるペナルティなしに実行できるため、パイプラインの効率が向上します。
*   **`ADD`**: 加算を行います。
*   **`BEQ` (Branch if Equal)**: 比較結果が等しい場合に指定されたラベルに分岐します。
*   **`MOVBU.P` (Move Byte Unsigned, Post-indexed)**: メモリから1バイトを符号なしでロードし、同時にベースレジスタ（この場合は`R2`や`R3`）をオフセット値（この場合は`1`）だけインクリメントします。これは、配列やスライスを順次処理するループにおいて非常に効率的です。

このアセンブリ実装は、Go言語の比較関数が頻繁に呼び出される環境において、ARM64プロセッサの特性を最大限に活用し、大幅なパフォーマンス向上を実現しています。特に、`MOVBU.P`による効率的なメモリロードとポインタ更新、そして`CSEL`による分岐の削減が、高速化の主要な要因となっています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の2つのファイルに集中しています。

1.  **`src/runtime/asm_arm64.s`**:
    *   このファイルに、`runtime.cmpstring`、`bytes.Compare`、そしてそれらが共通して利用する`runtime.cmpbody`のアセンブリ実装が追加されました。
    *   具体的には、`runtime.cmpstring`と`bytes.Compare`は、それぞれ引数（文字列やバイトスライスの基底アドレスと長さ）を適切なレジスタにロードした後、`runtime.cmpbody`を呼び出しています。
    *   `runtime.cmpbody`は、前述の技術的詳細で解説したバイトごとの比較ロジックと長さの比較ロジックを含んでいます。

2.  **`src/runtime/noasm.go`**:
    *   このファイルは、特定のアセンブリ実装が存在しないアーキテクチャ向けに、Go言語で書かれたフォールバックルーチンを提供します。
    *   変更前は、`+build arm64 ppc64 ppc64le`というビルドタグが含まれており、ARM64アーキテクチャでもこのファイルがビルドされていました。
    *   このコミットにより、`+build arm64`タグが削除され、`+build ppc64 ppc64le`のみが残りました。これは、ARM64向けにアセンブリ実装が提供されたため、もはや`noasm.go`の汎用Goコードを使用する必要がなくなったことを意味します。

#### `TEXT runtime·cmpstring(SB),NOSPLIT,$0-40`

```armasm
TEXT runtime·cmpstring(SB),NOSPLIT,$0-40
    MOVD    s1_base+0(FP), R2
    MOVD    s1_len+8(FP), R0
    MOVD    s2_base+16(FP), R3
    MOVD    s2_len+24(FP), R1
    BL  runtime·cmpbody(SB)
    MOVD    R8, ret+32(FP)
    RET
```
*   `s1_base+0(FP)`: フレームポインタ(FP)からのオフセットで、最初の文字列の基底アドレスを取得し、`R2`に格納します。
*   `s1_len+8(FP)`: 最初の文字列の長さを取得し、`R0`に格納します。
*   `s2_base+16(FP)`: 2番目の文字列の基底アドレスを取得し、`R3`に格納します。
*   `s2_len+24(FP)`: 2番目の文字列の長さを取得し、`R1`に格納します。
*   `BL runtime·cmpbody(SB)`: `runtime.cmpbody`関数を呼び出します。`BL`はBranch with Linkで、呼び出し元に戻るためのアドレスをリンクレジスタ(LR)に保存します。
*   `MOVD R8, ret+32(FP)`: `runtime.cmpbody`の戻り値である`R8`を、呼び出し元のスタックフレーム上の戻り値領域に格納します。
*   `RET`: 関数から戻ります。

#### `TEXT bytes·Compare(SB),NOSPLIT,$0-56`

```armasm
TEXT bytes·Compare(SB),NOSPLIT,$0-56
    MOVD    s1+0(FP), R2
    MOVD    s1+8(FP), R0
    MOVD    s2+24(FP), R3
    MOVD    s2+32(FP), R1
    BL  runtime·cmpbody(SB)
    MOVD    R8, ret+48(FP)
    RET
```
*   `bytes.Compare`も同様に、引数であるバイトスライスの基底アドレスと長さを適切なレジスタ（`R2`, `R0`, `R3`, `R1`）にロードします。バイトスライスは内部的にポインタと長さの構造体として扱われるため、オフセットが異なります。
*   その後、`runtime.cmpbody`を呼び出し、結果を`R8`から戻り値領域に格納して戻ります。

#### `TEXT runtime·cmpbody<>(SB),NOSPLIT,$-4-0`

この関数は、前述の「技術的詳細」セクションで詳しく解説した共通の比較ロジックを実装しています。ARM64の命令セットを最大限に活用し、バイトごとの比較を効率的に行い、長さの比較も適切に処理することで、高速な比較を実現しています。特に、`MOVBU.P`命令によるロードとポインタの自動インクリメント、そして`CSEL`命令による条件分岐の削減が、パフォーマンス向上に大きく貢献しています。

## 変更の背景

Go言語は、その高いパフォーマンスと並行処理能力で知られていますが、その基盤を支えるランタイムの最適化は常に重要な課題です。文字列やバイトスライスの比較は、プログラムの様々な場所で頻繁に行われる基本的な操作です。これらの操作が効率的であればあるほど、アプリケーション全体のパフォーマンスに大きな影響を与えます。

ARM64アーキテクチャは、スマートフォン、タブレット、サーバーなど、幅広いデバイスで採用が進んでおり、Go言語がこれらのプラットフォームで最高のパフォーマンスを発揮するためには、各アーキテクチャに特化した最適化が不可欠です。

このコミットは、ARM64環境における`runtime.cmpstring`（Goランタイム内部で文字列比較に使用される）と`bytes.Compare`（`bytes`パッケージでバイトスライス比較に使用される）の性能ボトルネックを解消することを目的としています。アセンブリ言語でこれらの関数を実装することで、Goコンパイラが生成するコードでは実現できない、より低レベルでCPUの特性を最大限に活かした最適化が可能になります。具体的には、レジスタの効率的な利用、特定のCPU命令の活用、分岐予測の最適化などが挙げられます。

## 前提知識の解説

### Go言語の`bytes.Compare`と`strings.Compare`

*   **`bytes.Compare(a, b []byte) int`**:
    この関数は、2つのバイトスライス`a`と`b`を辞書順に比較します。戻り値は以下のいずれかです。
    *   `0`: `a`と`b`が等しい場合。
    *   `-1`: `a`が`b`より辞書順で小さい場合。
    *   `+1`: `a`が`b`より辞書順で大きい場合。
    `bytes.Compare`は、バイトスライスの順序を決定する必要がある場合に有用です。ただし、単に等しいかどうかをチェックするだけであれば、`bytes.Equal(a, b []byte) bool`を使用することが推奨されます。`bytes.Equal`は、長さが異なる場合に早期に`false`を返すなど、等値性チェックに特化した最適化が施されているため、多くの場合でより高速です。

*   **`strings.Compare(a, b string) int`**:
    この関数は、2つの文字列`a`と`b`を辞書順に比較します。戻り値は`bytes.Compare`と同様に-1, 0, 1です。
    Go言語では、文字列の等値性チェックには通常`==`演算子を使用します。これはコンパイラによって最適化され、多くの場合で`strings.Compare`よりも高速です。`strings.Compare`は、主に`bytes.Compare`との一貫性を提供するために存在し、文字列の順序を決定する必要がある場合に使用されます。

### `runtime.cmpstring`

`runtime.cmpstring`は、Goランタイムの内部で使用される文字列比較関数です。これはGo言語のユーザーが直接呼び出すことを意図したものではなく、コンパイラが文字列比較演算子（例: `==`, `<`, `>`)を処理する際や、他のランタイム内部関数から利用されます。ランタイムの根幹をなす部分であるため、そのパフォーマンスはGoプログラム全体の実行速度に直結します。この関数は、特定のアーキテクチャ向けにアセンブリ言語で実装されることで、最大限の効率が追求されます。

### アセンブリ言語による最適化

Go言語のランタイムや標準ライブラリの一部では、C言語やGo言語ではなく、アセンブリ言語で記述されたコードが使用されることがあります。これは、以下のような理由によります。

*   **低レベルな制御**: CPUのレジスタ、キャッシュ、特定の命令セット（SIMD命令など）を直接制御することで、Go言語やC言語では不可能なレベルの最適化を実現できます。
*   **パフォーマンスの限界突破**: 非常に頻繁に実行されるクリティカルなパス（例: メモリコピー、文字列比較、コンテキストスイッチなど）において、わずかな命令数の削減やパイプラインの最適化が、全体として大きな性能向上につながります。
*   **アーキテクチャ固有の最適化**: 各CPUアーキテクチャ（x86-64, ARM64, PowerPCなど）には独自の特性と命令セットがあります。アセンブリ言語を使用することで、そのアーキテクチャに特化した最適なコードを記述できます。

### ARM64アーキテクチャ

ARM64（AArch64）は、ARMv8-Aアーキテクチャ以降で導入された64ビット命令セットアーキテクチャです。モバイルデバイスからサーバー、組み込みシステムまで幅広く利用されています。

*   **レジスタ**: 31個の汎用64ビットレジスタ（X0-X30）と、ゼロレジスタ（XZR）を持ちます。関数呼び出し規約により、これらのレジスタは引数渡し、戻り値、一時的な値の保持などに効率的に利用されます。
*   **命令セット**: 固定長32ビットの命令を持ち、ロード/ストア命令、データ処理命令、分岐命令などが含まれます。条件付き実行命令（`CSEL`など）は、分岐予測ミスによるペナルティを避けるために重要です。
*   **メモリモデル**: ロード/ストア命令を使用してメモリとレジスタ間でデータを転送します。効率的なメモリアクセスはパフォーマンスに直結します。

### ベンチマークの読み方

コミットメッセージに記載されているベンチマーク結果は、コード変更による性能変化を定量的に示すものです。

*   **`ns/op` (nanoseconds per operation)**: 1回の操作にかかる平均時間（ナノ秒）。この値が小さいほど高速です。
*   **`MB/s` (megabytes per second)**: 1秒あたりに処理できるデータ量（メガバイト）。この値が大きいほど高速です。主にデータ処理スループットを示す際に用いられます。
*   **`delta`**: 変更前（old）と変更後（new）の`ns/op`の差分をパーセンテージで示したもの。負の値は高速化を意味します。
*   **`speedup`**: 変更後の速度が変更前の何倍になったかを示すもの。`new MB/s / old MB/s`で計算されます。

このコミットのベンチマークでは、特に`BenchmarkCompareBytesBig`のような大規模なバイトスライスの比較において、`ns/op`が大幅に減少し、`MB/s`が劇的に増加していることがわかります。これは、アセンブリ実装が大規模データ処理において非常に効果的であることを示しています。

## 技術的詳細

このコミットの核心は、`src/runtime/asm_arm64.s`に追加された`runtime.cmpbody`というアセンブリ関数です。この関数は、`runtime.cmpstring`と`bytes.Compare`の両方から呼び出される共通の比較ロジックを提供します。これにより、コードの重複を避けつつ、比較処理の最適化を一元的に行うことができます。

### `runtime.cmpbody`関数の詳細

`runtime.cmpbody`は、2つのメモリ領域（バイトスライスまたは文字列の基底アドレス）を比較し、その結果を-1、0、または+1で返します。

**エントリ時のレジスタの状態:**

*   `R0`: 1つ目のシーケンス（s1）の長さ
*   `R1`: 2つ目のシーケンス（s2）の長さ
*   `R2`: 1つ目のシーケンス（s1）の開始アドレス
*   `R3`: 2つ目のシーケンス（s2）の開始アドレス

**終了時のレジスタの状態:**

*   `R8`: 比較結果 (-1, 0, または +1)
*   `R4`, `R5`, `R6`: 内部で使用され、値が変更される（clobbered）

**比較ロジックのフロー:**

1.  **長さの比較と最小長の決定**:
    ```armasm
    CMP R0, R1
    CSEL    LT, R1, R0, R6 // R6 is min(R0, R1)
    ```
    まず、`CMP R0, R1`で2つのシーケンスの長さを比較します。
    `CSEL LT, R1, R0, R6`は条件付き選択命令です。もし`R0 < R1`（LT: Less Than）であれば`R1`（s2の長さ）を`R6`に格納し、そうでなければ`R0`（s1の長さ）を`R6`に格納します。これにより、`R6`には2つのシーケンスの短い方の長さが設定されます。これは、比較ループが短い方のシーケンスの終端を超えてアクセスしないようにするために重要です。

2.  **比較終了アドレスの計算**:
    ```armasm
    ADD R2, R6    // R2 is current byte in s1, R6 is last byte in s1 to compare
    ```
    `R2`（s1の開始アドレス）に`R6`（最小長さ）を加算することで、`R2`は比較すべきs1の最後のバイトの次のアドレス（または比較終了アドレス）を指すようになります。ループ内で`R2`がこのアドレスに達したら、バイトごとの比較は終了です。

3.  **バイトごとの比較ループ (`loop`ラベル)**:
    ```armasm
    loop:
        CMP R2, R6
        BEQ samebytes // all compared bytes were the same; compare lengths
        MOVBU.P 1(R2), R4
        MOVBU.P 1(R3), R5
        CMP R4, R5
        BEQ loop
    ```
    *   `CMP R2, R6`: 現在のs1のポインタ`R2`が、計算された比較終了アドレス`R6`に達したかをチェックします。
    *   `BEQ samebytes`: もし`R2`が`R6`に等しければ、これは短い方のシーケンスの全てのバイトが一致したことを意味します。この場合、バイトごとの比較は終了し、`samebytes`ラベルにジャンプして最終的な長さの比較を行います。
    *   `MOVBU.P 1(R2), R4`: `R2`が指すメモリから1バイトを符号なしで`R4`にロードし、その後`R2`を1バイト分インクリメントします（ポストインクリメント）。これはs1の現在のバイトを取得し、次のバイトへポインタを進める効率的な方法です。
    *   `MOVBU.P 1(R3), R5`: 同様に、`R3`が指すメモリから1バイトを符号なしで`R5`にロードし、`R3`を1バイト分インクリメントします。
    *   `CMP R4, R5`: ロードした2つのバイトを比較します。
    *   `BEQ loop`: もし2つのバイトが等しければ、ループの先頭に戻り、次のバイトの比較を続けます。

4.  **バイトが不一致の場合**:
    ```armasm
    // bytes differed
    MOVD    $1, R8
    CSNEG   LT, R8, R8, R8
    RET
    ```
    ループ内で`CMP R4, R5`の結果が不一致（`BEQ loop`が実行されない）の場合、バイトが異なることが判明します。
    *   `MOVD $1, R8`: まず、結果レジスタ`R8`に`1`を設定します。
    *   `CSNEG LT, R8, R8, R8`: 条件付き否定命令です。もし`R4 < R5`（LT: Less Than）であれば、`R8`の値を否定します（`1`が`-1`に）。これにより、s1のバイトがs2のバイトより小さければ`-1`、大きければ`1`が`R8`に設定されます。
    *   `RET`: 関数から戻ります。

5.  **全バイト一致後の長さ比較 (`samebytes`ラベル)**:
    ```armasm
    samebytes:
        MOVD    $1, R8
        CMP R0, R1
        CSNEG   LT, R8, R8, R8
        CSEL    EQ, ZR, R8, R8
        RET
    ```
    短い方のシーケンスの全てのバイトが一致した場合、このセクションに到達します。この時点で、どちらかのシーケンスがもう一方のプレフィックス（接頭辞）であるか、あるいは両者が完全に等しいかのどちらかです。
    *   `MOVD $1, R8`: まず、結果レジスタ`R8`に`1`を設定します。
    *   `CMP R0, R1`: 元の長さ`R0`（s1の長さ）と`R1`（s2の長さ）を比較します。
    *   `CSNEG LT, R8, R8, R8`: もし`R0 < R1`（s1がs2より短い）であれば、`R8`の値を否定します（`1`が`-1`に）。これにより、s1がs2のプレフィックスであれば`-1`が設定されます。
    *   `CSEL EQ, ZR, R8, R8`: 条件付き選択命令です。もし`R0 == R1`（EQ: Equal）であれば、ゼロレジスタ`ZR`（値は常に0）を`R8`に格納します。そうでなければ、現在の`R8`の値（`-1`または`1`）をそのまま`R8`に保持します。これにより、両者の長さが等しければ`0`が、s1がs2より長ければ`1`が設定されます。
    *   `RET`: 関数から戻ります。

### ARM64命令の役割

*   **`MOVD`**: 64ビットの値をレジスタ間で、または即値からレジスタへ移動します。
*   **`CMP`**: 2つのオペランドを比較し、結果に応じてプロセッサの状態フラグを設定します。
*   **`CSEL` (Conditional Select)**: 条件に基づいて2つのソースレジスタのいずれかの値をターゲットレジスタに選択的にコピーします。これにより、条件分岐を伴う命令シーケンスを、分岐予測ミスによるペナルティなしに実行できるため、パイプラインの効率が向上します。
*   **`ADD`**: 加算を行います。
*   **`BEQ` (Branch if Equal)**: 比較結果が等しい場合に指定されたラベルに分岐します。
*   **`MOVBU.P` (Move Byte Unsigned, Post-indexed)**: メモリから1バイトを符号なしでロードし、同時にベースレジスタ（この場合は`R2`や`R3`）をオフセット値（この場合は`1`）だけインクリメントします。これは、配列やスライスを順次処理するループにおいて非常に効率的です。

このアセンブリ実装は、Go言語の比較関数が頻繁に呼び出される環境において、ARM64プロセッサの特性を最大限に活用し、大幅なパフォーマンス向上を実現しています。特に、`MOVBU.P`による効率的なメモリロードとポインタの自動インクリメント、そして`CSEL`による分岐の削減が、パフォーマンス向上に大きく貢献しています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の2つのファイルに集中しています。

1.  **`src/runtime/asm_arm64.s`**:
    *   このファイルに、`runtime.cmpstring`、`bytes.Compare`、そしてそれらが共通して利用する`runtime.cmpbody`のアセンブリ実装が追加されました。
    *   具体的には、`runtime.cmpstring`と`bytes.Compare`は、それぞれ引数（文字列やバイトスライスの基底アドレスと長さ）を適切なレジスタにロードした後、`runtime.cmpbody`を呼び出しています。
    *   `runtime.cmpbody`は、前述の技術的詳細で解説したバイトごとの比較ロジックと長さの比較ロジックを含んでいます。

2.  **`src/runtime/noasm.go`**:
    *   このファイルは、特定のアセンブリ実装が存在しないアーキテクチャ向けに、Go言語で書かれたフォールバックルーチンを提供します。
    *   変更前は、`+build arm64 ppc64 ppc64le`というビルドタグが含まれており、ARM64アーキテクチャでもこのファイルがビルドされていました。
    *   このコミットにより、`+build arm64`タグが削除され、`+build ppc64 ppc64le`のみが残りました。これは、ARM64向けにアセンブリ実装が提供されたため、もはや`noasm.go`の汎用Goコードを使用する必要がなくなったことを意味します。

## コアとなるコードの解説

### `src/runtime/asm_arm64.s`

このファイルに追加されたアセンブリコードは、Goの関数呼び出し規約に従い、引数をレジスタから取得し、結果をレジスタに格納します。

#### `TEXT runtime·cmpstring(SB),NOSPLIT,$0-40`

```armasm
TEXT runtime·cmpstring(SB),NOSPLIT,$0-40
    MOVD    s1_base+0(FP), R2
    MOVD    s1_len+8(FP), R0
    MOVD    s2_base+16(FP), R3
    MOVD    s2_len+24(FP), R1
    BL  runtime·cmpbody(SB)
    MOVD    R8, ret+32(FP)
    RET
```
*   `s1_base+0(FP)`: フレームポインタ(FP)からのオフセットで、最初の文字列の基底アドレスを取得し、`R2`に格納します。
*   `s1_len+8(FP)`: 最初の文字列の長さを取得し、`R0`に格納します。
*   `s2_base+16(FP)`: 2番目の文字列の基底アドレスを取得し、`R3`に格納します。
*   `s2_len+24(FP)`: 2番目の文字列の長さを取得し、`R1`に格納します。
*   `BL runtime·cmpbody(SB)`: `runtime.cmpbody`関数を呼び出します。`BL`はBranch with Linkで、呼び出し元に戻るためのアドレスをリンクレジスタ(LR)に保存します。
*   `MOVD R8, ret+32(FP)`: `runtime.cmpbody`の戻り値である`R8`を、呼び出し元のスタックフレーム上の戻り値領域に格納します。
*   `RET`: 関数から戻ります。

#### `TEXT bytes·Compare(SB),NOSPLIT,$0-56`

```armasm
TEXT bytes·Compare(SB),NOSPLIT,$0-56
    MOVD    s1+0(FP), R2
    MOVD    s1+8(FP), R0
    MOVD    s2+24(FP), R3
    MOVD    s2+32(FP), R1
    BL  runtime·cmpbody(SB)
    MOVD    R8, ret+48(FP)
    RET
```
*   `bytes.Compare`も同様に、引数であるバイトスライスの基底アドレスと長さを適切なレジスタ（`R2`, `R0`, `R3`, `R1`）にロードします。バイトスライスは内部的にポインタと長さの構造体として扱われるため、オフセットが異なります。
*   その後、`runtime.cmpbody`を呼び出し、結果を`R8`から戻り値領域に格納して戻ります。

#### `TEXT runtime·cmpbody<>(SB),NOSPLIT,$-4-0`

この関数は、前述の「技術的詳細」セクションで詳しく解説した共通の比較ロジックを実装しています。ARM64の命令セットを最大限に活用し、バイトごとの比較を効率的に行い、長さの比較も適切に処理することで、高速な比較を実現しています。特に、`MOVBU.P`命令によるロードとポインタの自動インクリメント、そして`CSEL`命令による条件分岐の削減が、パフォーマンス向上に大きく貢献しています。

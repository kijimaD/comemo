## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA (Static Single Assignment) 形式を使用します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。`Value` はSSAグラフのノードを表し、その操作や結果をカプセル化します。

`Value` オブジェクトは、その操作の種類 (Op)、型 (Type)、引数 (Args)、そして補助値 (Auxiliary Value, `Aux`) を持ちます。`Aux` は、定数、シンボル、メモリオフセットなど、特定の操作に付随する追加情報を提供します。例えば、メモリロード/ストア操作では、`Aux` はアクセスするシンボルやオフセットを保持することがあります。

Common Subexpression Elimination (CSE) は、コンパイラ最適化の一種で、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することでパフォーマンスを向上させます。CSEのような最適化パスをデバッグする際、`Value` オブジェクトがどのような補助値を持っているかを正確に把握することは極めて重要です。

このコミット以前は、`Value` が `auxSym` 型の補助値を持つ場合、その `Aux` の内容が `LongString()` メソッドの出力に含まれていませんでした。これにより、デバッガがSSAグラフを検査する際に、`Value` が参照している具体的なシンボル情報が欠落し、CSEの挙動を追跡したり、バグを特定したりすることが困難でした。この変更は、この情報不足を解消し、コンパイラ開発者がより効率的にデバッグを行えるようにすることを目的としています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現 (IR) の一種です。SSA形式の主要な特性は、「各変数がプログラム内で一度だけ代入される」という点にあります。これにより、データフロー解析が大幅に簡素化され、以下のような様々な最適化を効率的に適用できるようになります。

*   **Common Subexpression Elimination (CSE)**: 共通部分式の除去。
*   **Dead Code Elimination (DCE)**: 到達不能コードの除去。
*   **Constant Propagation**: 定数伝播。
*   **Register Allocation**: レジスタ割り当て。

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、SSA形式に変換し、このSSA形式上で多くの最適化を行います。`src/cmd/compile/internal/ssa` パッケージは、このSSA形式の構築と最適化を担当するGoコンパイラのバックエンドの一部です。

### ValueとAuxiliary Value (Aux)

SSA形式において、`Value` は計算結果やオペランドを表す基本的な構成要素です。各 `Value` は、その操作 (Op)、結果の型 (Type)、入力となる他の `Value` (Args)、そして補助情報 (Auxiliary Value, `Aux`) を持ちます。

`Aux` は、`Value` の操作を具体化するための追加データです。例えば：

*   **定数**: `OpConst` の `Value` は、`Aux` に実際の定数値 (整数、浮動小数点数など) を保持します。
*   **シンボル**: メモリ操作 (ロード、ストア) や関数呼び出しに関連する `Value` は、`Aux` にグローバル変数、関数、または構造体のフィールドなどのシンボル情報を保持することがあります。
*   **オフセット**: メモリアドレス計算に関連する `Value` は、`Aux` にベースアドレスからのオフセットを保持することがあります。

`Aux` の型は `auxInt` (整数)、`auxFloat` (浮動小数点数)、`auxString` (文字列)、`auxSym` (シンボル)、`auxSymOff` (シンボルとオフセット) など、多岐にわたります。これらの補助値は、SSAグラフの各ノードが表す操作のセマンティクスを完全に定義するために不可欠です。

### Common Subexpression Elimination (CSE)

Common Subexpression Elimination (CSE) は、コンパイラ最適化の最も基本的な手法の一つです。プログラム内で同じ式が複数回評価され、かつその間に式の値に影響を与えるような変更がない場合、CSEはその式を一度だけ計算し、その結果を再利用するようにコードを変換します。

例：
```go
a = x + y
b = z + (x + y)
```
CSEを適用すると、`x + y` の計算は一度だけ行われ、その結果が `a` と `b` の両方に使用されます。

```go
temp = x + y
a = temp
b = z + temp
```
これにより、冗長な計算が削減され、プログラムの実行速度が向上します。GoコンパイラのSSAバックエンドでは、SSA形式の特性を活かしてCSEを効率的に実行します。

### デバッグの重要性

コンパイラの最適化パスは複雑であり、意図しないバグや非効率なコード生成を引き起こす可能性があります。そのため、コンパイラ開発者は、最適化の各段階で中間表現 (SSAグラフなど) を検査し、期待通りの変換が行われているかを確認する必要があります。

`Value` オブジェクトの `LongString()` メソッドは、SSAグラフのノードを人間が読める形式で出力するためのデバッグユーティリティです。この出力に `Aux` の情報が含まれていないと、特にシンボル情報が重要なCSEのような最適化のデバッグにおいて、`Value` が具体的に何を操作しているのかを判断するのが困難になります。例えば、`LOAD` 操作の `Value` がどのグローバル変数からロードしているのかが `Aux` なしでは分かりません。このコミットは、このデバッグ情報の欠落を補うものです。

変更前は、`auxSym` の `Value` に対しては `v.Aux` の内容が `LongString()` の出力に含まれていませんでした。これは、`v.Aux` が `nil` でない場合でも、シンボル情報がデバッグ出力から欠落することを意味していました。

このコミットでは、`auxSym` のケースに以下のコードが追加されました。

```go
case auxSym:
    if v.Aux != nil {
        s += fmt.Sprintf(" {%s}", v.Aux)
    }
```

このコードは、`Value` の `Aux` が `auxSym` 型であり、かつ `v.Aux` 自体が `nil` でない場合に、`v.Aux` の文字列表現を `"{シンボル名}"` の形式で `LongString()` の出力に追加します。`v.Aux` は `ssa.Aux` 型であり、これは通常、`*obj.LSym` (リンカシンボル) などのシンボル情報を保持するインターフェース型です。`fmt.Sprintf(" {%s}", v.Aux)` は、`v.Aux` の `String()` メソッドを呼び出してその文字列表現を取得し、出力に埋め込みます。

これにより、例えば `LOAD` 操作の `Value` が特定のグローバル変数 `myVar` を参照している場合、その `LongString()` 出力には ` {myVar}` のような情報が含まれるようになり、デバッガはどのシンボルが操作されているかを一目で確認できるようになります。これは、特にCSEのような最適化が正しくシンボルを扱っているか、あるいは予期せぬシンボルが共通部分式として扱われていないかなどを検証する際に非常に役立ちます。

## コアとなるコードの解説

変更は `src/cmd/compile/internal/ssa/value.go` ファイル内の `(*Value).LongString()` メソッドにあります。このメソッドは、`Value` オブジェクトのデバッグ用の文字列表現を生成します。

追加されたコードは、`switch v.AuxType` ステートメント内の `case auxSym:` ブロックです。

```go
	case auxSym:
		if v.Aux != nil {
			s += fmt.Sprintf(" {%s}", v.Aux)
		}
```

*   `case auxSym:`: これは、`Value` の補助値の型が `auxSym` である場合にこのブロックのコードが実行されることを意味します。`auxSym` は、`Value` がシンボル（例: グローバル変数、関数、型など）に関連付けられていることを示します。
*   `if v.Aux != nil`: `v.Aux` が `nil` でないことを確認します。`v.Aux` はインターフェース型であり、シンボル情報が実際に設定されている場合にのみ処理を行います。
*   `s += fmt.Sprintf(" {%s}", v.Aux)`: `v.Aux` の文字列表現を `"{シンボル名}"` の形式で既存の文字列 `s` に追加します。`fmt.Sprintf` は `v.Aux` の `String()` メソッドを暗黙的に呼び出し、その結果をフォーマットします。これにより、デバッグ出力に具体的なシンボル名が含まれるようになります。

この変更により、`auxSym` を持つ `Value` の `LongString()` 出力は、例えば `v1 = LOAD <int> {main.myGlobalVar}` のようになり、`myGlobalVar` というシンボルがこの `LOAD` 操作に関連付けられていることが明確に示されます。これは、コンパイラの最適化、特にCSEがシンボルを正しく扱っているかを検証する上で非常に価値のある情報となります。

## 元コミット内容

`net/http/cgi`: CGIリクエストに対して`REMOTE_PORT`の値を正しく渡すように修正。

現在、CGIまたはFCGIリクエストを受け取った際、クライアントのリモートポートはゼロにハードコードされている。これは、ほとんどのウェブサーバーが`REMOTE_PORT`変数を渡しているにもかかわらず発生していた。

この問題は、CGI RFC (rfc3875) がクライアントのリモートポートについて何も言及していないため、元々除外されていた可能性が高い。しかし、テストされたすべてのウェブサーバー（Apache 2.2、Apache 2.4、nginx、lighttpdを含む）は`REMOTE_PORT`を渡している。

Fixes #8351

## 変更の背景

このコミットの背景には、Go言語の`net/http/cgi`パッケージがCGI（Common Gateway Interface）またはFCGI（FastCGI）リクエストを処理する際に、クライアントのリモートポート情報を正確に取得できていなかったという問題があります。

従来のGoのCGIハンドリングでは、`http.Request`構造体の`RemoteAddr`フィールドのポート部分が常に「0」にハードコードされていました。これは、CGIの公式仕様であるRFC 3875が`REMOTE_PORT`という環境変数について明示的に定義していないことに起因していると考えられます。しかし、実際にはApache、Nginx、Lighttpdといった主要なウェブサーバーのほとんどが、CGIスクリプトに対してクライアントのリモートポートを示す`REMOTE_PORT`環境変数を提供していました。

この不一致により、GoのCGIアプリケーションは、クライアントの正確なリモートアドレス（特にポート番号）を把握できず、ログ記録、アクセス制御、セッション管理など、クライアントの完全なアドレス情報が必要なシナリオで問題が生じていました。このコミットは、この実用上のギャップを埋め、ウェブサーバーが提供する`REMOTE_PORT`情報を活用することで、より正確なクライアント情報を提供するように修正することを目的としています。

## 前提知識の解説

### CGI (Common Gateway Interface)

CGIは、ウェブサーバーが外部プログラム（CGIスクリプト）と連携するための標準的なプロトコルです。ウェブサーバーはクライアントからのリクエストを受け取ると、そのリクエストに関する情報（HTTPヘッダー、クエリ文字列、クライアントIPアドレスなど）を環境変数としてCGIスクリプトに渡し、スクリプトの標準入力にリクエストボディを渡します。CGIスクリプトは処理結果を標準出力に出力し、ウェブサーバーがそれを受け取ってクライアントに返します。

### FCGI (FastCGI)

FastCGIはCGIの拡張であり、CGIのプロセス起動オーバーヘッドを削減するために設計されました。CGIがリクエストごとに新しいプロセスを起動するのに対し、FastCGIは永続的なプロセスを維持し、複数のリクエストを処理できます。これにより、パフォーマンスが向上します。Goの`net/http/cgi`パッケージは、CGIとFastCGIの両方のリクエストを処理する能力を持っています。

### 環境変数 (Environment Variables)

CGIにおいて、ウェブサーバーはクライアントのリクエストに関する様々なメタデータを環境変数としてCGIスクリプトに渡します。例えば、`REMOTE_ADDR`はクライアントのIPアドレス、`REQUEST_METHOD`はHTTPメソッド（GET, POSTなど）を示します。`REMOTE_PORT`もその一つで、クライアントが接続に使用したポート番号を伝達するためにウェブサーバーによって設定されることがあります。

### `http.Request`構造体と`RemoteAddr`フィールド

Go言語の`net/http`パッケージにおける`http.Request`構造体は、HTTPリクエストのすべての側面を表します。この構造体には`RemoteAddr`というフィールドがあり、これはリクエストを送信したクライアントのネットワークアドレス（IPアドレスとポート番号）を文字列形式（例: "192.168.1.1:12345"）で保持します。Goの標準HTTPサーバーは、基盤となるTCP接続のリモートアドレスからこのフィールドを自動的に設定します。

### `net.JoinHostPort`関数

Go言語の`net`パッケージにある`JoinHostPort`関数は、ホスト名（またはIPアドレス）とポート番号を結合して、"host:port"形式のネットワークアドレス文字列を生成します。これは、`http.Request.RemoteAddr`のようなフィールドに値を設定する際に便利です。

### `strconv.Atoi`関数

Go言語の`strconv`パッケージにある`Atoi`関数は、文字列を整数に変換します。このコミットでは、`REMOTE_PORT`環境変数から取得したポート番号の文字列を整数に変換するために使用されています。変換に失敗した場合（例えば、文字列が有効な数値でない場合）、この関数はゼロとエラーを返します。このコミットではエラーは無視され、ゼロがデフォルト値として使用されます。

## 技術的詳細

このコミットの核心は、Goの`net/http/cgi`パッケージがCGIリクエストから`http.Request.RemoteAddr`を構築する際のポート情報の扱いを改善することにあります。

変更前は、`child.go`内の`RequestFromMap`関数において、`http.Request`の`RemoteAddr`フィールドは、`REMOTE_ADDR`環境変数から取得したIPアドレスと、ハードコードされたポート番号「0」を結合して設定されていました。これは、CGI RFC 3875が`REMOTE_PORT`を標準としていないため、安全策として取られていた可能性があります。

しかし、現実のウェブサーバーの実装では、`REMOTE_PORT`環境変数が広く利用されており、クライアントの正確なポート情報を提供していました。このコミットは、この実情に合わせて、`REMOTE_PORT`環境変数の値が存在し、有効な数値であれば、その値を`RemoteAddr`のポートとして使用するように変更しました。

具体的には、`params["REMOTE_PORT"]`から文字列としてポート番号を取得し、`strconv.Atoi`関数を使って整数に変換します。`Atoi`関数は、変換に失敗した場合（例えば、`REMOTE_PORT`が設定されていない、または無効な値である場合）にゼロを返すため、この変更は後方互換性を保ちつつ、より正確な情報を提供できるようになっています。変換された整数値は、`strconv.Itoa`で再度文字列に変換され、`net.JoinHostPort`によって`REMOTE_ADDR`と結合されます。

テストコード（`child_test.go`）も更新され、`REMOTE_PORT`が設定されている場合の正しい動作と、設定されていない場合のデフォルトの「0」が使用される動作の両方が検証されています。これにより、変更が意図通りに機能し、既存の動作を損なわないことが保証されます。

## コアとなるコードの解説

### `src/net/http/cgi/child.go` の変更点

`RequestFromMap`関数は、CGI環境変数（`params`マップ）から`http.Request`オブジェクトを構築する役割を担っています。

変更前:
```go
r.RemoteAddr = net.JoinHostPort(params["REMOTE_ADDR"], "0")
```
ここでは、`REMOTE_ADDR`環境変数の値（クライアントのIPアドレス）と、ハードコードされた文字列"0"を`net.JoinHostPort`で結合し、`r.RemoteAddr`に設定していました。これにより、クライアントのポート情報は常に「0」として扱われていました。

変更後:
```go
remotePort, _ := strconv.Atoi(params["REMOTE_PORT"]) // zero if unset or invalid
r.RemoteAddr = net.JoinHostPort(params["REMOTE_ADDR"], strconv.Itoa(remotePort))
```
この変更では、まず`params["REMOTE_PORT"]`から`REMOTE_PORT`環境変数の値を取得します。
`strconv.Atoi`関数を使って、この文字列を整数`remotePort`に変換します。もし`REMOTE_PORT`が設定されていない、または有効な数値でない場合、`Atoi`は`0`とエラーを返しますが、ここではエラーは`_`で無視され、`remotePort`は`0`になります。
次に、この整数`remotePort`を`strconv.Itoa`で再び文字列に変換し、`net.JoinHostPort`を使って`REMOTE_ADDR`と結合します。
これにより、ウェブサーバーが`REMOTE_PORT`を提供している場合はその値が正確に反映され、提供していない場合や無効な値の場合は従来通り「0」が使用されるという、より柔軟で正確な動作が実現されます。

### `src/net/http/cgi/child_test.go` の変更点

テストファイルには、この変更の動作を検証するための2つの重要なテストケースが追加・修正されています。

1.  **`TestRequest`関数の修正**:
    既存の`TestRequest`関数では、`REMOTE_ADDR`が"5.6.7.8"の場合に`RemoteAddr`が"5.6.7.8:0"になることを期待していました。
    変更後、テスト環境変数に`"REMOTE_PORT": "54321"`が追加され、期待される`RemoteAddr`の値も`"5.6.7.8:54321"`に修正されました。これにより、`REMOTE_PORT`が正しくパースされ、`RemoteAddr`に反映されることが検証されます。

2.  **`TestRequestWithoutRemotePort`関数の追加**:
    この新しいテスト関数は、`REMOTE_PORT`環境変数が設定されていないシナリオをテストします。
    `env`マップには`REMOTE_PORT`が含まれていません。この場合、`RequestFromMap`関数は`REMOTE_PORT`を`0`として処理するため、期待される`RemoteAddr`は`"5.6.7.8:0"`となります。
    このテストの追加により、`REMOTE_PORT`が存在しない場合でも、`RemoteAddr`が適切にデフォルト値（ポート0）に設定されることが保証され、後方互換性が維持されていることが確認できます。

これらのコード変更とテストの追加により、GoのCGIハンドリングは、より現実世界のウェブサーバーの挙動に即した形で、クライアントのリモートポート情報を正確に取得・反映できるようになりました。

## 変更の背景

このコミットは、Goコンパイラが特定の状況下で誤解を招くエラーメッセージを出力していた問題を修正するために行われました。具体的には、可変長引数（variadic arguments）を取る関数に `nil` を渡した場合に、コンパイラが「`fatal error: dowidth: unknown type: E-34`」という、問題の本質とはかけ離れた内部的なエラーメッセージを報告していました。

開発者にとって、このような内部的なエラーメッセージは問題の特定と解決を困難にします。このコミットの目的は、より正確で分かりやすいエラーメッセージ（この場合は「`nil`」）を生成するようにコンパイラの動作を改善し、開発者のデバッグ体験を向上させることにあります。

## 前提知識の解説

### Go言語の可変長引数 (Variadic Functions)

Go言語では、関数が任意の数の引数を受け入れることができる「可変長引数」という機能があります。これは、関数の最後のパラメータの型名の前に `...` を付けることで定義されます。

例: `func f(args ...T)`

この `args` は関数内で `[]T` 型のスライスとして扱われます。つまり、`f(1, 2, 3)` と呼び出すと、`args` は `[]T{1, 2, 3}` となります。`f()` と引数なしで呼び出すと、`args` は空のスライス `[]T{}` となります。

### `nil` の扱い

Go言語における `nil` は、ポインタ、チャネル、関数、インターフェース、マップ、スライスといった参照型の「ゼロ値」を表します。`nil` は型情報を持たないため、コンテキストによってその具体的な型が決定されます。例えば、`var s []int = nil` は `int` 型のスライスが `nil` であることを示しますが、単に `nil` とだけ書かれた場合、コンパイラはそれがどの型の `nil` なのかを判断する必要があります。

### Goコンパイラの役割

Goコンパイラは、Goのソースコードを機械語に変換するプログラムです。その過程で、構文解析、意味解析、型チェックなどの様々な段階を経て、コードがGo言語の仕様に準拠しているかを確認します。もしコードに問題があれば、コンパイラはエラーメッセージを生成して開発者に報告します。エラーメッセージの質は、開発者が問題を迅速に特定し修正するために非常に重要です。

### `errchk` ディレクティブ

Goのテストスイートでは、`// errchk $G $D/$F.go` のようなディレクティブが使われることがあります。これは、特定のGoソースファイル（`$D/$F.go`）をコンパイルする際に、`$G`（Goコンパイラ）が特定の行で特定のエラーメッセージを出力することを期待するテストです。テストが成功するためには、指定された行で正確に期待されるエラーメッセージが出力される必要があります。

## 技術的詳細

このコミットで追加された `test/bugs/bug153.go` は、可変長引数を持つ関数 `f` に `nil` を直接渡すという、非常に具体的なケースをテストしています。

```go
package main

func f(args ...) {
}

func main() {
	f(nil);  // ERROR "nil"
}
```

ここで `func f(args ...)` は、`args` が `[]interface{}` 型のスライスとして扱われることを意味します。`main` 関数内で `f(nil)` と呼び出すと、コンパイラは `nil` を `[]interface{}` 型のスライスに変換しようとします。

Go言語では、`nil` は型情報を持たないため、コンパイラは `nil` がどの型のスライスとして解釈されるべきかを判断する必要があります。通常、`nil` は `[]T` 型のスライスに代入可能ですが、可変長引数に直接 `nil` を渡す場合、コンパイラがその `nil` を `[]interface{}` 型のスライスとして適切に処理できない場合に問題が発生します。

元のコンパイラは、この状況で「`fatal error: dowidth: unknown type: E-34`」というエラーを出力していました。これは、コンパイラの内部で型情報の「幅」（メモリサイズなど）を計算する `dowidth` という処理が、`nil` の型が不明であるために予期しない型（`E-34` はおそらく内部的なエラーコードやプレースホルダー）に遭遇し、処理を継続できなかったことを示唆しています。これは、コンパイラの型システムが `nil` と可変長引数の組み合わせを適切に扱えていなかったことを意味します。

このコミットによる修正（具体的なコンパイラコードの変更は示されていませんが、テストの追加から推測されます）は、コンパイラがこの特定のケースを認識し、`nil` が可変長引数に直接渡された場合に、より意味のあるエラーメッセージ「`nil`」を生成するように改善されたことを示しています。これにより、開発者は「`nil` を可変長引数に直接渡すことはできない（または意図しない挙動になる）」という問題点を明確に理解できるようになります。

## 変更の背景

CRC64（Cyclic Redundancy Check 64-bit）は、データ転送や保存におけるエラー検出によく用いられるチェックサムアルゴリズムです。CRC64には複数の標準があり、それぞれ異なる「ポリノミアル」（生成多項式）を使用します。Go言語の `hash/crc64` パッケージは、これらの異なるポリノミアルをサポートしていますが、このコミット以前は、テストスイートがISOポリノミアルにのみ焦点を当てていました。

ECMAポリノミアルは、ISOポリノミアルと同様に広く使用されているCRC64の標準の一つです。異なるポリノミアルを使用するということは、同じ入力データに対しても異なるCRC64値が生成されることを意味します。したがって、ライブラリがECMAポリノミアルを正しく実装していることを保証するためには、そのための専用のテストケースが必要でした。

この変更の背景には、`hash/crc64` パッケージの網羅性と信頼性を向上させ、異なるCRC64標準を使用するシステムとの互換性を保証するという目的があります。特に、IntelのIlya Tocar氏によるコミットであることから、特定のハードウェアやシステムでECMAポリノミアルが要求されるシナリオに対応する必要があった可能性も考えられます。

## 前提知識の解説

### CRC (Cyclic Redundancy Check)

CRC（巡回冗長検査）は、デジタルデータのエラー検出によく用いられる手法です。データを送信または保存する際に、特定のアルゴリズムに基づいて短い固定長のチェックサム（CRC値）を計算し、データと共に付加します。データを受信または読み出す際に、同じアルゴリズムで再度チェックサムを計算し、元のチェックサムと比較することで、データが破損していないかを確認します。

### CRCの仕組みとポリノミアル（生成多項式）

CRCの計算は、バイナリデータを多項式として扱い、特定の「生成多項式（Generator Polynomial）」で除算する操作に似ています。この除算の「余り」がCRC値となります。生成多項式はCRCアルゴリズムの心臓部であり、その選択によってエラー検出能力や生成されるCRC値が異なります。

### CRC64

CRC64は、64ビットのCRC値を生成するアルゴリズムです。64ビットという長いチェックサムは、非常に高い確率でデータのエラーを検出できます。CRC64にはいくつかの標準があり、それぞれ異なる生成多項式を使用します。

### ISOポリノミアルとECMAポリノミアル

CRC64で広く使われる代表的な生成多項式には、以下の2つがあります。

1.  **ISOポリノミアル (ISO 3309)**:
    *   多項式表現: `x^64 + x^4 + x^3 + x + 1`
    *   16進数表現: `0xD800000000000000` (または `0x42F0E1EBA9EA3693` を反転させたものなど、実装によって表現が異なる場合がある)
    *   国際標準化機構 (ISO) によって定義されたもので、通信プロトコルなどで広く利用されます。

2.  **ECMAポリノミアル (ECMA-182)**:
    *   多項式表現: `x^64 + x^62 + x^57 + x^55 + x^54 + x^53 + x^52 + x^47 + x^46 + x^45 + x^40 + x^39 + x^38 + x^37 + x^35 + x^33 + x^32 + x^31 + x^29 + x^28 + x^26 + x^20 + x^19 + x^17 + x^16 + x^14 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^3 + x + 1`
    *   16進数表現: `0xC96C5795D78707F0`
    *   ECMA（European Computer Manufacturers Association）によって定義されたもので、特にストレージシステムやファイルシステムなどで利用されることがあります。

これら2つのポリノミアルは異なるため、同じ入力データに対して異なるCRC64値を生成します。Goの `hash/crc64` パッケージは、`crc64.ISO` と `crc64.ECMA` という定数でこれらのポリノミアルを提供しており、ユーザーはどちらかを選択してCRC64計算を行うことができます。

## 技術的詳細

このコミットは、`crc64_test.go` ファイル内のテストロジックを拡張することで、ECMAポリノミアルの正確性を検証しています。

1.  **テストデータ構造の変更**:
    元の `test` 構造体は `out uint64` フィールドのみを持ち、単一の期待CRC64値を格納していました。これを `outISO uint64` と `outECMA uint64` に分割することで、各入力文字列に対してISOとECMA両方のポリノミアルに対応する期待値を保持できるようになりました。これは、異なるポリノミアルが異なる結果を生成するというCRCの性質を直接反映した変更です。

2.  **ゴールデンテストデータの拡張**:
    `golden` 配列は、既知の入力文字列とその期待されるCRC64値のペアを定義する「ゴールデンテストデータ」です。この配列が拡張され、各エントリにISOとECMA両方の期待値が追加されました。これらの期待値は、通常、信頼できる別のCRC64実装や計算ツールを用いて事前に算出されたものです。

3.  **`TestGolden` 関数のロジック変更**:
    `TestGolden` 関数は、`golden` 配列の各エントリをループ処理し、実際のCRC64計算結果と期待値を比較します。
    *   変更前は、`New(tab)` でISOポリノミアル用のテーブルを生成し、その結果を `g.out` と比較していました。
    *   変更後は、まず `tabISO := MakeTable(ISO)` でISOポリノミアル用のテーブルを生成し、`New(tabISO)` でCRC64ハッシュオブジェクトを作成、計算結果を `g.outISO` と比較します。
    *   次に、`tabECMA := MakeTable(ECMA)` でECMAポリノミアル用のテーブルを生成し、`New(tabECMA)` で別のCRC64ハッシュオブジェクトを作成、計算結果を `g.outECMA` と比較します。
    *   いずれかの比較で不一致があった場合、`t.Errorf` でエラーを報告し、`t.FailNow()` でテストを即座に終了させます。これにより、ECMAポリノミアルの実装に問題があれば、すぐに検出できるようになります。

4.  **ベンチマーク関数の明確化**:
    `BenchmarkCrc64KB` は `BenchmarkISOCrc64KB` にリネームされ、`h := New(MakeTable(ISO))` と明示的にISOポリノミアルを使用するように変更されました。これにより、ベンチマークがどのポリノミアルの性能を測定しているのかが明確になります。

これらの変更により、`hash/crc64` パッケージは、ISOとECMA両方の主要なCRC64ポリノミアルに対して、その正確性が自動テストによって保証されるようになりました。

## コアとなるコードの解説

### `type test struct` の変更

```go
type test struct {
	outISO  uint64
	outECMA uint64
	in      string
}
```
この変更は、テストケースの構造を根本的に変えています。以前は単一の `out` フィールドでCRC64の期待値を保持していましたが、ISOとECMAという異なるポリノミアルに対応するため、それぞれ `outISO` と `outECMA` という専用のフィールドが追加されました。これにより、一つのテストエントリで両方のポリノミアルに対する検証が可能になります。

### `var golden = []test{...}` の変更

`golden` 配列は、CRC64計算の「正解」となる値（ゴールデンデータ）を定義しています。各要素は `test` 構造体のインスタンスであり、入力文字列 `in` と、それに対応するISOおよびECMAポリノミアルでの期待CRC64値 `outISO`, `outECMA` を含んでいます。

例:
```go
	{0x0, 0x0, ""}, // 空文字列の場合、ISOもECMAもCRCは0
	{0x3420000000000000, 0x330284772e652b05, "a"}, // "a" の場合、ISOとECMAで異なるCRC値
```
このように、各入力文字列に対して、ISOとECMAそれぞれの正しいCRC64値がハードコードされています。これらの値は、他の信頼できるCRC64実装と比較して検証されたものです。

### `func TestGolden(t *testing.T)` の変更

```go
func TestGolden(t *testing.T) {
	tabISO := MakeTable(ISO)
	tabECMA := MakeTable(ECMA)
	for i := 0; i < len(golden); i++ {
		g := golden[i]
		// ISOポリノミアルのテスト
		c := New(tabISO)
		io.WriteString(c, g.in)
		s := c.Sum64()
		if s != g.outISO {
			t.Errorf("ISO crc64(%s) = 0x%x want 0x%x", g.in, s, g.outISO)
			t.FailNow()
		}
		// ECMAポリノミアルのテスト
		c = New(tabECMA)
		io.WriteString(c, g.in)
		s = c.Sum64()
		if s != g.outECMA {
			t.Errorf("ECMA crc64(%s) = 0x%x want 0x%x", g.in, s, g.outECMA)
			t.FailNow()
		}
	}
}
```
この関数は、CRC64の正確性を検証する主要なテストです。
1.  `MakeTable(ISO)` と `MakeTable(ECMA)` を呼び出して、それぞれISOとECMAポリノミアルに対応するCRC計算テーブルを生成します。`MakeTable` 関数は、指定されたポリノミアルに基づいてCRC計算に必要なルックアップテーブルを事前に構築します。これにより、実際のCRC計算が高速に行われます。
2.  `golden` 配列の各テストエントリ `g` に対してループ処理を行います。
3.  **ISOポリノミアルの検証**:
    *   `New(tabISO)` を使ってISOポリノミアル用の `crc64.Hash` インターフェースを実装したオブジェクトを作成します。
    *   `io.WriteString(c, g.in)` で入力文字列 `g.in` をハッシュオブジェクトに書き込みます。
    *   `s := c.Sum64()` で計算されたCRC64値を取得します。
    *   `if s != g.outISO` で、計算結果 `s` が `golden` データに定義されたISOの期待値 `g.outISO` と一致するかを検証します。一致しない場合はエラーを報告し、テストを終了します。
4.  **ECMAポリノミアルの検証**:
    *   同様に、`New(tabECMA)` を使ってECMAポリノミアル用のハッシュオブジェクトを作成します。
    *   入力文字列を書き込み、CRC64値を計算します。
    *   `if s != g.outECMA` で、計算結果 `s` が `golden` データに定義されたECMAの期待値 `g.outECMA` と一致するかを検証します。一致しない場合はエラーを報告し、テストを終了します。

この二重の検証により、Goの `hash/crc64` パッケージがISOとECMA両方の標準に正確に準拠していることが保証されます。

## 変更の背景

CRC64（Cyclic Redundancy Check 64-bit）は、データ転送や保存におけるエラー検出によく用いられるチェックサムアルゴリズムです。CRC64には複数の標準があり、それぞれ異なる「ポリノミアル」（生成多項式）を使用します。Go言語の `hash/crc64` パッケージは、これらの異なるポリノミアルをサポートしていますが、このコミット以前は、テストスイートがISOポリノミアルにのみ焦点を当てていました。

ECMAポリノミアルは、ISOポリノミアルと同様に広く使用されているCRC64の標準の一つです。異なるポリノミアルを使用するということは、同じ入力データに対しても異なるCRC64値が生成されることを意味します。したがって、ライブラリがECMAポリノミアルを正しく実装していることを保証するためには、そのための専用のテストケースが必要でした。

この変更の背景には、`hash/crc64` パッケージの網羅性と信頼性を向上させ、異なるCRC64標準を使用するシステムとの互換性を保証するという目的があります。特に、IntelのIlya Tocar氏によるコミットであることから、特定のハードウェアやシステムでECMAポリノミアルが要求されるシナリオに対応する必要があった可能性も考えられます。

## 前提知識の解説

### CRC (Cyclic Redundancy Check)

CRC（巡回冗長検査）は、デジタルデータのエラー検出によく用いられる手法です。データを送信または保存する際に、特定のアルゴリズムに基づいて短い固定長のチェックサム（CRC値）を計算し、データと共に付加します。データを受信または読み出す際に、同じアルゴリズムで再度チェックサムを計算し、元のチェックサムと比較することで、データが破損していないかを確認します。

### CRCの仕組みとポリノミアル（生成多項式）

CRCの計算は、バイナリデータを多項式として扱い、特定の「生成多項式（Generator Polynomial）」で除算する操作に似ています。この除算の「余り」がCRC値となります。生成多項式はCRCアルゴリズムの心臓部であり、その選択によってエラー検出能力や生成されるCRC値が異なります。

### CRC64

CRC64は、64ビットのCRC値を生成するアルゴリズムです。64ビットという長いチェックサムは、非常に高い確率でデータのエラーを検出できます。CRC64にはいくつかの標準があり、それぞれ異なる生成多項式を使用します。

### ISOポリノミアルとECMAポリノミアル

CRC64で広く使われる代表的な生成多項式には、以下の2つがあります。

1.  **ISOポリノミアル (ISO 3309)**:
    *   多項式表現: `x^64 + x^4 + x^3 + x + 1`
    *   16進数表現: `0xD800000000000000` (または `0x42F0E1EBA9EA3693` を反転させたものなど、実装によって表現が異なる場合がある)
    *   国際標準化機構 (ISO) によって定義されたもので、通信プロトコルなどで広く利用されます。

2.  **ECMAポリノミアル (ECMA-182)**:
    *   多項式表現: `x^64 + x^62 + x^57 + x^55 + x^54 + x^53 + x^52 + x^47 + x^46 + x^45 + x^40 + x^39 + x^38 + x^37 + x^35 + x^33 + x^32 + x^31 + x^29 + x^28 + x^26 + x^20 + x^19 + x^17 + x^16 + x^14 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^3 + x + 1`
    *   16進数表現: `0xC96C5795D78707F0`
    *   ECMA（European Computer Manufacturers Association）によって定義されたもので、特にストレージシステムやファイルシステムなどで利用されることがあります。

これら2つのポリノミアルは異なるため、同じ入力データに対して異なるCRC64値を生成します。Goの `hash/crc64` パッケージは、`crc64.ISO` と `crc64.ECMA` という定数でこれらのポリノミアルを提供しており、ユーザーはどちらかを選択してCRC64計算を行うことができます。

## 技術的詳細

このコミットは、`crc64_test.go` ファイル内のテストロジックを拡張することで、ECMAポリノミアルの正確性を検証しています。

1.  **テストデータ構造の変更**:
    元の `test` 構造体は `out uint64` フィールドのみを持ち、単一の期待CRC64値を格納していました。これを `outISO uint64` と `outECMA uint64` に分割することで、各入力文字列に対してISOとECMA両方のポリノミアルに対応する期待値を保持できるようになりました。これは、異なるポリノミアルが異なる結果を生成するというCRCの性質を直接反映した変更です。

2.  **ゴールデンテストデータの拡張**:
    `golden` 配列は、既知の入力文字列とその期待されるCRC64値のペアを定義する「ゴールデンテストデータ」です。この配列が拡張され、各エントリにISOとECMA両方の期待値が追加されました。これらの期待値は、通常、信頼できる別のCRC64実装や計算ツールを用いて事前に算出されたものです。

3.  **`TestGolden` 関数のロジック変更**:
    `TestGolden` 関数は、`golden` 配列の各エントリをループ処理し、実際のCRC64計算結果と期待値を比較します。
    *   変更前は、`New(tab)` でISOポリノミアル用のテーブルを生成し、その結果を `g.out` と比較していました。

これらの変更により、`hash/crc64` パッケージは、ISOとECMA両方の主要なCRC64ポリノミアルに対して、その正確性が自動テストによって保証されるようになりました。

```
この関数は、CRC64の正確性を検証する主要なテストです。
1.  `MakeTable(ISO)` と `MakeTable(ECMA)` を呼び出して、それぞれISOとECMAポリノミアルに対応するCRC計算テーブルを生成します。`MakeTable` 関数は、指定されたポリノミアルに基づいてCRC計算に必要なルックアップテーブルを事前に構築します。これにより、実際のCRC計算が高速に行われます。
2.  `golden` 配列の各テストエントリ `g` に対してループ処理を行います。
3.  **ISOポリノミアルの検証**:
    *   `New(tabISO)` を使ってISOポリノミアル用の `crc64.Hash` インターフェースを実装したオブジェクトを作成します。
    *   `io.WriteString(c, g.in)` で入力文字列 `g.in` をハッシュオブジェクトに書き込みます。
    *   `s := c.Sum64()` で計算されたCRC64値を取得します。
    *   `if s != g.outISO` で、計算結果 `s` が `golden` データに定義されたISOの期待値 `g.outISO` と一致するかを検証します。一致しない場合はエラーを報告し、テストを終了します。
4.  **ECMAポリノミアルの検証**:
    *   同様に、`New(tabECMA)` を使ってECMAポリノミアル用のハッシュオブジェクトを作成します。
    *   入力文字列を書き込み、CRC64値を計算します。
    *   `s := c.Sum64()` で計算されたCRC64値を取得します。
    *   `if s != g.outECMA` で、計算結果 `s` が `golden` データに定義されたECMAの期待値 `g.outECMA` と一致するかを検証します。一致しない場合はエラーを報告し、テストを終了します。

この二重の検証により、Goの `hash/crc64` パッケージがISOとECMA両方の標準に正確に準拠していることが保証されます。

# [インデックス 17807] ファイルの概要

このコミットは、Go言語の仕様書（`doc/go_spec.html`）におけるスライス操作、特に`append`関数の振る舞いに関する記述を明確化するものです。`append`関数が、既存のスライスの基底配列に十分な容量がある場合に、その基底配列を再利用するという動作を仕様として明記しています。これは、当時の実装が既にそのように動作していたものの、仕様として明文化することで、言語の振る舞いをより厳密に定義し、開発者の理解を深めることを目的としています。

## 変更の背景

Go言語のスライスは、その柔軟性と効率性から非常に強力なデータ構造ですが、その内部的な振る舞い、特に基底配列の再利用に関する理解は、開発者にとって時に混乱を招くことがありました。`append`関数はスライスに要素を追加するための主要な手段ですが、その際に新しい基底配列が割り当てられるのか、それとも既存の基底配列が再利用されるのかは、パフォーマンスやメモリ使用量に大きな影響を与えます。

このコミットの背景には、Goコミュニティ内での議論、特に「多数派の意見（majority sentiment）」があったことが示唆されています。当時の`append`関数の実装は、既に十分な容量がある場合に基底配列を再利用するようになっていましたが、この振る舞いが仕様として明記されていなかったため、開発者は実装の詳細に依存するか、あるいはその振る舞いを推測する必要がありました。

このコミットは、この暗黙の振る舞いをGo言語の公式仕様に組み込むことで、言語の定義をより厳密にし、開発者が`append`関数の動作をより正確に予測できるようにすることを目的としています。これにより、Goプログラムの予測可能性と信頼性が向上し、開発者はより効率的なコードを書くことができるようになります。

また、コミットメッセージには`Fixes #5818.`と`Fixes #5180.`という記述がありますが、公開されているGoのIssueトラッカーでこれらの番号に直接関連する情報を見つけることは困難でした。これは、当時の内部的なIssue番号であるか、あるいは非常に古いIssueである可能性が考えられます。しかし、これらのIssueが、`append`関数の基底配列再利用に関する仕様の不明確さや、それによって引き起こされる可能性のある問題に関連していたことは推測できます。

## 前提知識の解説

### Go言語のスライス (Slices)

Go言語のスライスは、配列のセグメント（部分）を記述するデータ構造です。スライスは、基底となる配列への参照、長さ（`len`）、そして容量（`cap`）の3つの要素で構成されます。

-   **基底配列 (Underlying Array)**: スライスが参照する実際のデータが格納されている配列です。スライスは、この基底配列の一部または全体を「ビュー」として提供します。
-   **長さ (Length)**: スライスに含まれる要素の数です。`len(s)`で取得できます。
-   **容量 (Capacity)**: スライスの基底配列の先頭から、スライスが拡張できる最大要素数です。`cap(s)`で取得できます。容量は、基底配列の残りの部分のサイズを示します。

スライスは動的なサイズ変更が可能であるかのように見えますが、実際には、基底配列の容量が不足した場合に新しい基底配列が割り当てられ、既存の要素がコピーされることでサイズが変更されます。

### `make`関数によるスライスの作成

`make`関数は、スライス、マップ、チャネルを初期化するために使用されます。スライスの場合、`make([]T, length, capacity)`のように使用し、指定された長さと容量を持つ新しい基底配列を割り当て、その配列を参照するスライスを返します。

### `append`関数

`append`関数は、スライスに要素を追加するために使用されます。その振る舞いは、スライスの現在の容量に依存します。

1.  **容量が十分な場合**: 追加する要素を格納するのに十分な容量が既存の基底配列にある場合、`append`は既存の基底配列を再利用し、新しい要素をその配列の末尾に追加します。この場合、新しいメモリ割り当ては発生しません。スライスの長さは増加しますが、基底配列は同じままです。
2.  **容量が不足する場合**: 追加する要素を格納するのに十分な容量が既存の基底配列にない場合、`append`はより大きな新しい基底配列を割り当てます。既存の要素は新しい配列にコピーされ、その後、新しい要素が追加されます。この再割り当ては、メモリ割り当てとデータコピーのオーバーヘッドを伴うため、パフォーマンスに影響を与える可能性があります。新しい基底配列のサイズは、Goのランタイムによって決定され、通常は現在の容量の2倍（小規模なスライスの場合）または1.25倍（大規模なスライスの場合）に増加します。

`append`関数は常に更新されたスライスを返すため、`s = append(s, element)`のように、その戻り値を元のスライス変数に再代入することが重要です。これは、基底配列が変更された可能性があるためです。

### スライス式 (Slice Expressions)

スライス式（例: `a[low:high]`）は、既存の配列やスライスから新しいスライスを作成します。この新しいスライスは、元の配列やスライスと同じ基底配列を共有します。このため、一方のスライスを変更すると、もう一方のスライスからもその変更が見える可能性があります。

## 技術的詳細

このコミットの技術的な核心は、Go言語の仕様書における`append`関数の振る舞いの「再利用」に関する記述の明確化です。以前の仕様では、`append`が容量不足の場合に新しい基底配列を割り当てることについては言及されていましたが、容量が十分な場合に既存の基底配列を「再利用する」という点が明示されていませんでした。

この変更は、単なるドキュメントの修正以上の意味を持ちます。Go言語の仕様は、言語の振る舞いを定義する公式なドキュメントであり、コンパイラの実装者やGoプログラムの動作を理解しようとする開発者にとっての最終的な権威です。この明確化により、以下の点が保証されます。

1.  **予測可能性の向上**: 開発者は、`append`がいつ新しいメモリを割り当て、いつ既存のメモリを再利用するかを正確に予測できるようになります。これは、メモリ使用量やパフォーマンスを最適化する上で非常に重要です。
2.  **実装の一貫性**: 将来のGoコンパイラやランタイムの実装が、この仕様に厳密に従うことが保証されます。これにより、異なるGoバージョン間での`append`の振る舞いの一貫性が保たれます。
3.  **教育と理解の促進**: Go言語を学習する人々や、その内部動作を深く理解したい人々にとって、この仕様の明確化は、スライスの概念と`append`の動作をより正確に把握するための助けとなります。特に、スライスが「動的な配列」のように見えても、その背後には基底配列の再利用と再割り当てというメカニズムがあることを理解する上で不可欠です。
4.  **「言語変更」としての位置づけ**: コミットメッセージには「This is technically a language change」とありますが、これは既存の実装の振る舞いを仕様に合わせるものであり、実際の動作が変わるわけではないため、後方互換性を損なうものではありません。しかし、言語の「定義」が変わるという意味では「言語変更」と見なされます。

また、`make`関数に関する記述も修正されており、`make`が常に新しい隠れた配列を割り当てることを明確にしています。これは、`make`とスライス式によるスライス作成の違いをより明確にするものです。スライス式が既存の基底配列を共有するのに対し、`make`は常に独立した基底配列を作成するという重要な違いがあります。

さらに、スライス式が`nil`スライスに対して適用された場合の振る舞いについても明確化されています。`nil`スライスに対するスライス操作の結果は`nil`スライスになること、そしてそれ以外の場合には結果のスライスがオペランドと基底配列を共有することが明記されています。これは、スライスの共有セマンティクスを理解する上で重要な詳細です。

これらの変更は、Go言語の設計哲学である「シンプルさ」と「明確さ」を反映しており、言語の基盤となるデータ構造の振る舞いをより堅牢に定義することに貢献しています。

## コアとなるコードの解説

変更は主にGo言語の仕様書（`doc/go_spec.html`）の以下のセクションに集中しています。

1.  **ドキュメントのバージョン日付の更新**:
    ```diff
    -	"Subtitle": "Version of Oct 7, 2013",
    +	"Subtitle": "Version of Oct 16, 2013",
    ```
    これは単に仕様書の更新日を反映したものです。

2.  **スライスの定義の明確化**:
    ```diff
    -A slice is a descriptor for a contiguous segment of an array and
    +A slice is a descriptor for a contiguous segment of an <i>underlying array</i> and
     provides access to a numbered sequence of elements from that array.
    ```
    「an array」が「an *underlying array*」に変更され、スライスが「基底配列」のセグメントであることをより明確に強調しています。これにより、スライスの背後にある配列の概念がより明確になります。

3.  **`make`関数によるスライス作成の記述の修正**:
    ```diff
    -and parameters specifying the length and optionally the capacity:
    -</p>
    -
    -<pre>
    -make([]T, length)
    -make([]T, length, capacity)
    -</pre>
    -
    -<p>
    -A call to <code>make</code> allocates a new, hidden array to which the returned
    -slice value refers. That is, executing
    -</p>
    -
    -<pre>
    -make([]T, length, capacity)
    -</pre>
    -
    -<p>
    -produces the same slice as allocating an array and slicing it, so these two examples
    -result in the same slice:
    +and parameters specifying the length and optionally the capacity.
    +A slice created with <code>make</code> always allocates a new, hidden array

    +</p>

    +</pre>

    ```
    `make([]T, length)`の形式が削除され、`make([]T, length, capacity)`の形式に統一されました。これは、`make`が常に新しい隠れた配列を割り当てることを明確にするためのものです。また、`make`が配列を割り当ててスライスするのと同等であるという説明が、より簡潔に「allocating an array and slicing it」という表現に修正され、スライス式へのリンクが追加されました。これにより、`make`が新しい独立した基底配列を作成するという点が強調されます。

4.  **スライスのスライス（または配列のスライス）に関する記述の修正**:
    ```diff
    -however with slices of slices (or arrays of slices), the lengths may vary dynamically.
    -Moreover, the inner slices must be allocated individually (with <code>make</code>).
    +however with slices of slices (or arrays of slices), the inner lengths may vary dynamically.
    +Moreover, the inner slices must be initialized individually.
    ```
    「allocated individually (with `make`)」が「initialized individually」に変更されました。これは、内部スライスが必ずしも`make`で割り当てられるとは限らず、他の方法（例えば、既存のスライスからのスライス式）で初期化される可能性もあるため、より一般的な表現に修正されたものです。

5.  **スライス式の結果に関する明確化**:
    ```diff
    -is a <code>nil</code> slice.
    +is a <code>nil</code> slice. Otherwise, the result shares its underlying array with the
    +operand.
    ```
    スライス式が`nil`スライスに対して適用された場合の結果が`nil`スライスであることに加えて、それ以外の場合には結果のスライスがオペランドと基底配列を共有することが明記されました。これは、スライスの共有セマンティクスを理解する上で重要な情報です。

6.  **`append`関数の基底配列再利用に関する明確化（最も重要な変更）**:
    ```diff
    -If the capacity of <code>s</code> is not large enough to fit the additional
    -values, <code>append</code> allocates a new, sufficiently large slice that fits
    -both the existing slice elements and the additional values. Thus, the returned
    -slice may refer to a different underlying array.
    +If the capacity of <code>s</code> is not large enough to fit the additional
    +values, <code>append</code> allocates a new, sufficiently large underlying
    +array that fits both the existing slice elements and the additional values.
    +Otherwise, <code>append</code> re-uses the underlying array.
    ```
    この部分がこのコミットの核心です。以前の記述では、容量が不足した場合に新しいスライス（新しい基底配列を指す）が割り当てられることのみが述べられていました。この変更により、以下の重要な文が追加されました。

    `Otherwise, append re-uses the underlying array.`

    これは、「それ以外の場合（つまり、容量が十分な場合）、`append`は基底配列を再利用する」という振る舞いを明確に仕様として定義したものです。これにより、`append`の動作が完全に記述され、開発者はその振る舞いを正確に予測できるようになります。

これらの変更は、Go言語の仕様をより正確で包括的なものにし、スライスという重要なデータ構造の振る舞いに関する曖昧さを解消することを目的としています。

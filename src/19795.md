# [インデックス 19795] ファイルの概要

このコミットは、Go言語の標準ライブラリ `crypto/subtle` パッケージ内の `ConstantTimeCompare` 関数の挙動を変更するものです。具体的には、比較対象のバイトスライス `x` と `y` の長さが異なる場合に、以前はパニック（panic）を引き起こしていた動作を、`0` を返すように修正しています。これにより、関数の堅牢性が向上し、呼び出し側での事前チェックの必要性が減り、潜在的な「潜水艦クラッシャー」（予期せぬパニックによるクラッシュ）のリスクが低減されます。また、この変更は、定数時間比較のセキュリティ上の意図を損なうことなく、より実用的な挙動を提供します。

## 元コミット内容

`crypto/subtle: make ConstantTimeCompare return zero for args of different length.`

これは、`ConstantTimeCompare` 関数が異なる長さの引数に対してゼロを返すようにする変更です。

パニックを引き起こすよりも、この方がより有用です。なぜなら、そうでなければすべての呼び出し元が呼び出し前に長さのチェックを行う必要があり、一部のプログラマはそれを忘れ、結果として潜在的な「潜水艦クラッシャー」を発生させる可能性があるからです。この機能の他の実装も長さのチェックを行っています。

この変更は後方互換性があります。ただし、異なる長さの引数でパニックが発生することに依存するコードが書かれている場合は除きます。しかし、Go 1.3以前もそのようなケースはありませんでした。

Go issue #7304 を更新します。

## 変更の背景

`crypto/subtle` パッケージは、暗号学的な操作においてサイドチャネル攻撃、特にタイミング攻撃を防ぐための関数を提供します。`ConstantTimeCompare` 関数は、2つのバイトスライスの内容を比較する際に、比較にかかる時間が入力データの値に依存しないように設計されています。これにより、攻撃者が比較時間から秘密情報（例えば、パスワードや暗号鍵の一部）を推測することを防ぎます。

このコミット以前の `ConstantTimeCompare` 関数は、比較対象の2つのバイトスライスの長さが異なる場合、`panic` を発生させていました。これは、セキュリティ上の観点からは、異なる長さの入力が与えられた場合に、その事実を即座に、かつ安全に通知するという意図があったのかもしれません。しかし、コミットメッセージが指摘するように、この挙動にはいくつかの問題がありました。

1.  **呼び出し側の負担**: `panic` を避けるためには、`ConstantTimeCompare` を呼び出す前に、常に引数の長さが等しいことを確認するコードを記述する必要がありました。これは冗長であり、プログラマがこのチェックを忘れると、予期せぬ `panic` が発生し、アプリケーションがクラッシュする「潜水艦クラッシャー」となる可能性がありました。
2.  **他の実装との乖離**: 他のプログラミング言語やライブラリにおける同様の定数時間比較関数は、通常、長さが異なる場合に `false`（またはそれに相当する値）を返すことで、この問題をより穏やかに処理していました。Goの以前の挙動は、この一般的な慣習から外れていました。
3.  **実用性の向上**: 長さが異なることが判明した場合に `0` を返すことは、その比較が失敗したことを明確に示し、かつプログラムの実行を中断しないため、より実用的なエラーハンドリングを可能にします。暗号学的ハッシュや秘密の長さは、通常、機密情報とは見なされないため、長さが異なることを `0` を返すことで示すことは、セキュリティ上のリスクを増大させません。

この変更は、`ConstantTimeCompare` のセキュリティ特性を維持しつつ、その使いやすさと堅牢性を向上させることを目的としています。

## 前提知識の解説

### 定数時間比較 (Constant-Time Comparison)

定数時間比較とは、比較操作にかかる時間が、比較されるデータの値や、データがどこで異なるかに関わらず、常に一定であるか、または入力データの長さにのみ依存するように設計された比較アルゴリズムのことです。

通常の比較関数（例: C言語の `memcmp` や多くの言語の文字列比較）は、効率を重視して、データが異なる最初のバイトを見つけた時点で比較を終了します。例えば、`"password"` と `"pissword"` を比較する場合、2文字目で違いが見つかるため、すぐに比較を終了します。これに対し、`"password"` と `"passworb"` を比較する場合は、7文字目まで比較が進みます。このように、比較にかかる時間が入力データの内容によって変動します。

暗号学的な文脈では、このような時間変動は「タイミング攻撃」と呼ばれるサイドチャネル攻撃の脆弱性につながる可能性があります。定数時間比較は、このタイミング攻撃を防ぐために不可欠です。

### サイドチャネル攻撃 (Side-Channel Attacks)

サイドチャネル攻撃とは、暗号システムやセキュアなシステムの実装から意図せず漏洩する物理的な情報（サイドチャネル）を分析することで、秘密情報（例: 暗号鍵）を推測しようとする攻撃手法です。これは、暗号アルゴリズム自体の数学的な脆弱性を直接攻撃するのではなく、その実装の物理的な特性を悪用します。

主なサイドチャネル攻撃の種類には以下のようなものがあります。

*   **タイミング攻撃 (Timing Attacks)**:
    *   システムが特定の操作（例: 暗号化、復号、比較）を実行するのにかかる時間を測定し、その時間差から秘密情報を推測します。
    *   例えば、パスワードの検証において、正しい文字が入力されると処理時間がわずかに長くなるような実装の場合、攻撃者は総当たり攻撃よりもはるかに効率的にパスワードを特定できる可能性があります。
    *   定数時間比較は、このタイミング攻撃に対する主要な対策の一つです。
*   **電力解析攻撃 (Power Analysis Attacks)**:
    *   デバイスの電力消費量を測定し、その変動パターンから内部の計算や秘密情報を推測します。
*   **電磁波解析攻撃 (Electromagnetic (EM) Attacks)**:
    *   デバイスから放射される電磁波を測定し、そこに含まれる情報から秘密を抽出します。
*   **キャッシュ攻撃 (Cache Attacks)**:
    *   共有システム（例: 仮想化環境、クラウドサービス）において、キャッシュメモリのヒット/ミスパターンを監視することで、秘密情報に関連するメモリアクセスパターンを推測します。

定数時間プログラミングは、これらのサイドチャネル攻撃、特にタイミング攻撃に対する重要な防御策であり、機密性の高い操作の実行時間が秘密入力値に依存しないようにすることを目的としています。

## 技術的詳細

このコミットの技術的な核心は、`crypto/subtle` パッケージの `ConstantTimeCompare` 関数における、入力スライスの長さが異なる場合の挙動の変更です。

変更前は、`ConstantTimeCompare(x, y []byte)` 関数内で `if len(x) != len(y)` の条件が真になった場合、以下の `panic` ステートメントが実行されていました。

```go
panic("subtle: slices have different lengths")
```

この `panic` は、プログラムの実行を即座に中断させ、クラッシュを引き起こします。暗号学的な文脈では、このような予期せぬ中断は、サービス拒否攻撃のベクトルとなる可能性や、適切なエラーハンドリングを複雑にする原因となります。

変更後は、この `panic` が `return 0` に置き換えられました。

```go
return 0
```

`ConstantTimeCompare` 関数は、2つのバイトスライスの内容が等しい場合に `1` を返し、そうでない場合に `0` を返すように設計されています。したがって、長さが異なる場合に `0` を返すことは、内容が等しくないという結果と一貫しており、関数のセマンティクスを維持します。

この変更の利点は以下の通りです。

1.  **堅牢性の向上**: 長さの不一致が `panic` ではなく `0` の返却値として扱われるため、呼び出し側は `panic` を捕捉するための複雑な `defer`/`recover` ロジックを記述する必要がなくなります。これにより、コードがよりシンプルになり、エラーハンドリングが容易になります。
2.  **プログラマの負担軽減**: 呼び出し側で `ConstantTimeCompare` を呼び出す前に `len(x) == len(y)` のチェックを明示的に行う必要がなくなります。これにより、コードの記述量が減り、ヒューマンエラー（チェックの忘れ）による潜在的なクラッシュを防ぎます。
3.  **セキュリティの維持**: 長さが異なることを `0` を返すことで示すことは、タイミング攻撃に対する脆弱性を導入しません。なぜなら、比較対象のデータの長さ自体は、通常、秘密情報とは見なされないため、その情報が漏洩してもセキュリティ上の問題は発生しないからです。重要なのは、比較にかかる時間がデータの「内容」に依存しないことです。この変更後も、長さが等しい場合の比較ロジックは定数時間で実行されます。
4.  **テストの追加**: この変更の意図を明確にするため、`ConstantTimeCompare` のテストケースに、長さが異なるスライスを比較した場合に `0` が返されることを確認するテストが追加されました。これにより、将来の変更でこの挙動が意図せず変更されることを防ぎます。

このコミットは、Go言語の `crypto/subtle` パッケージが、セキュリティと実用性のバランスを考慮して進化していることを示しています。

## コアとなるコードの解説

### `src/pkg/crypto/subtle/constant_time.go`

*   **`ConstantTimeCompare` 関数の変更**:
    *   変更前: `if len(x) != len(y)` の条件が真（つまり、2つのスライスの長さが異なる）の場合、`panic("subtle: slices have different lengths")` が実行され、プログラムがクラッシュしていました。
    *   変更後: 同じ条件で `return 0` が実行されるようになりました。これにより、長さが異なる場合は `ConstantTimeCompare` が `0` を返し、呼び出し元は `panic` を処理することなく、比較が失敗したことを認識できます。これは、関数のセマンティクス（一致しない場合は `0` を返す）と一貫しており、より穏やかで堅牢なエラーハンドリングを可能にします。
*   **コメントの更新**:
    *   `ConstantTimeCompare` のドキュメンテーションコメントが `"returns 1 iff the two equal length slices, x"` から `"returns 1 iff the two slices, x"` に変更されました。これは、関数がもはや「等しい長さのスライス」のみを前提とせず、異なる長さのスライスも処理し、その結果として `0` を返すようになったことを反映しています。
*   **`ConstantTimeCopy` からの `return` の削除**:
    *   `ConstantTimeCopy` 関数内の最後の `return` ステートメントが削除されています。これは、Goでは関数の最後に到達すると暗黙的に `return` が行われるため、冗長な記述を削除したクリーンアップであり、このコミットの主要な変更（`ConstantTimeCompare` の挙動変更）とは直接的な関連はありませんが、コードの可読性とGoの慣習に合わせたものです。

### `src/pkg/crypto/subtle/constant_time_test.go`

*   **テストケースの追加**:
    *   `testConstantTimeCompareData` スライスに、`ConstantTimeCompare` の新しい挙動を検証するための2つのテストケースが追加されました。
        *   `{[]byte{0x11}, []byte{0x11, 0x12}, 0},`
        *   `{[]byte{0x11, 0x12}, []byte{0x11}, 0},`
    *   これらのテストケースは、長さが異なるバイトスライスを `ConstantTimeCompare` に渡した場合に、期待通り `0` が返されることを確認します。これにより、変更された挙動が正しく実装され、将来の回帰が防止されます。

これらの変更により、`ConstantTimeCompare` はより使いやすく、かつセキュリティ上の目的（タイミング攻撃の防止）を損なうことなく、堅牢な関数となりました。

# [インデックス 27588] ファイルの概要

このコミットは、Go言語の標準ライブラリ`testing`パッケージ内のベンチマークテスト`TestBRun`の不安定性（flakiness）を解消することを目的としています。具体的には、ベンチマーク中に発生するメモリ割り当ての計測において、`runtime.MemStats`が報告する値がベンチマーク対象のコードが直接行った割り当てよりも多くなることがあるため、テストのアサーションを厳密な一致から下限値のチェックへと変更しています。これにより、テストがランタイムの内部的な変動に影響されずに、期待される最小限のメモリ割り当てを正しく検証できるようになります。

## 変更の背景

Goの`testing`パッケージには、コードのパフォーマンスを測定するためのベンチマーク機能が含まれています。ベンチマークテストでは、実行時間だけでなく、メモリ割り当ての回数（`MemAllocs`）や割り当てられたバイト数（`MemBytes`）も計測できます。`TestBRun`というテストは、このメモリ割り当ての計測機能が正しく動作するかを検証するためのものです。

しかし、この`TestBRun`が時折失敗するという問題が発生していました。コミットメッセージとコード内のコメントによると、この不安定性の原因は、Goランタイムの`runtime.MemStats`が報告するメモリ割り当ての統計が、ベンチマーク対象のコードが直接行った割り当てだけでなく、Goランタイム自身の内部的な割り当て（ガベージコレクション、スケジューラ、内部データ構造の管理など）も含む場合があるためでした。

これにより、ベンチマーク対象のコードが期待通り2回のメモリ割り当てを行ったとしても、`runtime.MemStats`はそれ以上の値を報告することがあり、厳密な等価性（`==`）をチェックするテストが誤って失敗していました。テストの本来の目的は「結果が過少報告されていないこと」を確認することであるため、過剰な報告による失敗は不適切でした。この不安定なテスト（flaky test）は開発プロセスを妨げるため、修正が必要とされました。

## 前提知識の解説

### Goのベンチマークテスト (`testing`パッケージ)

Go言語には、標準ライブラリとして`testing`パッケージが提供されており、ユニットテスト、例（Example）テスト、そしてベンチマークテストを記述できます。
*   **`*testing.B`**: ベンチマーク関数は`func BenchmarkXxx(b *testing.B)`というシグネチャを持ちます。`*testing.B`型は、ベンチマークの実行回数や時間、メモリ割り当てなどの情報を提供します。
*   **`b.Run()`**: サブベンチマークを定義するために使用されます。これにより、一つのベンチマーク関数内で複数の異なるシナリオをテストできます。
*   **`b.ReportAllocs()`**: このメソッドを呼び出すことで、ベンチマーク中に発生したメモリ割り当ての回数とバイト数を計測し、結果に含めるよう指示します。
*   **`b.result.MemAllocs`**: ベンチマーク中に発生したメモリ割り当ての総回数。
*   **`b.result.MemBytes`**: ベンチマーク中に割り当てられたメモリの総バイト数。

### `runtime.MemStats`

`runtime`パッケージは、Goランタイムとの相互作用を可能にする低レベルな機能を提供します。`runtime.MemStats`構造体は、Goプログラムのメモリ使用状況に関する詳細な統計情報を含んでいます。これには、ヒープのサイズ、ガベージコレクションの統計、そしてメモリ割り当ての総回数などが含まれます。`MemStats`は、プログラム全体のメモリ使用状況を反映するため、ベンチマーク対象のコードだけでなく、Goランタイム自体の動作によって発生するメモリ割り当ても集計する可能性があります。

### Flaky Test (不安定なテスト)

Flaky Testとは、同じコードに対して同じ条件で実行しても、成功したり失敗したりするテストのことです。これは、テストが外部要因（例: 実行環境、時間、並行処理のタイミング、リソースの可用性など）に依存している場合に発生しやすく、開発者がコードの変更が原因ではないにもかかわらずテストが失敗するため、信頼性が低く、開発効率を低下させる原因となります。Flaky Testは、CI/CDパイプラインにおいて特に問題となり、誤ったアラートや無駄な再実行を引き起こします。

## 技術的詳細

このコミットの核心的な問題は、Goのベンチマークシステムがメモリ割り当てを計測する際に、`runtime.MemStats`を利用している点にあります。`runtime.MemStats`は、Goプログラム全体のメモリ使用状況を追跡するため、ベンチマーク対象の関数が明示的に行ったメモリ割り当てだけでなく、Goランタイムが内部的に行う様々な処理によるメモリ割り当ても捕捉してしまいます。

具体的には、以下のような要因が`MemAllocs`や`MemBytes`の報告値を変動させる可能性があります。

1.  **ガベージコレクション (GC)**: GCは、不要になったメモリを解放するプロセスですが、その過程で一時的なデータ構造を割り当てることがあります。GCの実行タイミングや頻度は、プログラムの実行状況やヒープの使用量によって変動するため、ベンチマークの実行ごとに異なるメモリ割り当てとして計上される可能性があります。
2.  **スケジューラ**: Goのランタイムスケジューラは、ゴルーチンを効率的に実行するために内部的なデータ構造を管理し、必要に応じてメモリを割り当てることがあります。
3.  **内部データ構造の成長**: Goランタイムの内部的なマップ、スライス、チャネルなどのデータ構造は、要素が追加される際に容量を拡張するために再割り当てを行うことがあります。これらの割り当ても`MemStats`に計上されます。
4.  **並行処理のオーバーヘッド**: 複数のゴルーチンが同時に動作している場合、同期プリミティブやチャネル操作など、並行処理に関連するランタイムのオーバーヘッドがメモリ割り当てとして現れることがあります。

`TestBRun`の以前の実装では、ベンチマーク対象のコードが2回のメモリ割り当てを行うことを期待し、`b.result.MemAllocs == 2`という厳密な等価性チェックを行っていました。しかし、上記のランタイムの内部的な要因により、`MemAllocs`が2よりも大きな値（例えば3や4）を報告することがあり、これがテストの失敗につながっていました。

このコミットでは、テストの目的が「メモリ割り当てが過少報告されていないこと」を確認することであるという本質に立ち返り、厳密な等価性チェックを「下限値のチェック」に変更しました。つまり、`MemAllocs`が少なくとも2回以上であることを確認すれば、ベンチマーク対象のコードが正しく動作していると判断できる、という考え方です。これにより、ランタイムの内部的な変動による余分な割り当てを許容しつつ、テストの信頼性を向上させています。

## コアとなるコードの解説

変更は`src/testing/sub_test.go`ファイル内の`TestBRun`関数に集中しています。このテスト関数は、`b.Run`を使ってサブベンチマークを実行し、その結果として得られるメモリ割り当ての統計（`MemAllocs`と`MemBytes`）を検証しています。

元のコードでは、以下の2つのアサーションがありました。

1.  `if got := b.result.MemAllocs; got != 2 { ... }`
    *   これは、メモリ割り当ての回数`MemAllocs`が厳密に2回であることを期待していました。
2.  `if got := b.result.MemBytes; got != 2*bufSize { ... }`
    *   これは、割り当てられたメモリの総バイト数`MemBytes`が厳密に`2*bufSize`（`bufSize`は事前に定義されたバッファサイズ）であることを期待していました。

このコミットでは、これらのアサーションが以下のように変更されました。

1.  `if got := b.result.MemAllocs; got < 2 { ... }`
    *   `!= 2`が` < 2`に変更されました。これにより、`MemAllocs`が2回未満の場合にのみエラーが報告されるようになります。つまり、2回以上の割り当てが報告されてもテストは成功します。
2.  `if got := b.result.MemBytes; got < 2*bufSize { ... }`
    *   `!= 2*bufSize`が` < 2*bufSize`に変更されました。これにより、`MemBytes`が`2*bufSize`未満の場合にのみエラーが報告されるようになります。つまり、`2*bufSize`以上のバイト数が報告されてもテストは成功します。

この変更の意図は、コード内のコメントで明確に説明されています。
`// runtime.MemStats sometimes reports more allocations than the`
`// benchmark is responsible for. Luckily the point of this test is`
`// to ensure that the results are not underreported, so we can`
`// simply verify the lower bound.`

このコメントは、「`runtime.MemStats`はベンチマークが担当するよりも多くの割り当てを報告することがある。幸いなことに、このテストの目的は結果が過少報告されていないことを確認することなので、単に下限を検証すればよい」と述べています。

したがって、この変更は、ベンチマーク対象のコードが意図した最小限のメモリ割り当てを確実に行っていることを検証しつつ、Goランタイムの内部的な動作によって発生する可能性のある余分な割り当てを許容することで、`TestBRun`の不安定性を解消し、テストの信頼性を向上させています。

## コアとなるコードの解説

変更は`src/testing/sub_test.go`ファイル内の`TestBRun`関数に集中しています。このテスト関数は、`b.Run`を使ってサブベンチマークを実行し、その結果として得られるメモリ割り当ての統計（`MemAllocs`と`MemBytes`）を検証しています。

元のコードでは、以下の2つのアサーションがありました。

1.  `if got := b.result.MemAllocs; got != 2 { ... }`
    *   これは、メモリ割り当ての回数`MemAllocs`が厳密に2回であることを期待していました。
2.  `if got := b.result.MemBytes; got != 2*bufSize { ... }`
    *   これは、割り当てられたメモリの総バイト数`MemBytes`が厳密に`2*bufSize`（`bufSize`は事前に定義されたバッファサイズ）であることを期待していました。

このコミットでは、これらのアサーションが以下のように変更されました。

1.  `if got := b.result.MemAllocs; got < 2 { ... }`
    *   `!= 2`が` < 2`に変更されました。これにより、`MemAllocs`が2回未満の場合にのみエラーが報告されるようになります。つまり、2回以上の割り当てが報告されてもテストは成功します。
2.  `if got := b.result.MemBytes; got < 2*bufSize { ... }`
    *   `!= 2*bufSize`が` < 2*bufSize`に変更されました。これにより、`MemBytes`が`2*bufSize`未満の場合にのみエラーが報告されるようになります。つまり、`2*bufSize`以上のバイト数が報告されてもテストは成功します。

この変更の意図は、コード内のコメントで明確に説明されています。
`// runtime.MemStats sometimes reports more allocations than the`
`// benchmark is responsible for. Luckily the point of this test is`
`// to ensure that the results are not underreported, so we can`
`// simply verify the lower bound.`

このコメントは、「`runtime.MemStats`はベンチマークが担当するよりも多くの割り当てを報告することがある。幸いなことに、このテストの目的は結果が過少報告されていないことを確認することなので、単に下限を検証すればよい」と述べています。

したがって、この変更は、ベンチマーク対象のコードが意図した最小限のメモリ割り当てを確実に行っていることを検証しつつ、Goランタイムの内部的な動作によって発生する可能性のある余分な割り当てを許容することで、`TestBRun`の不安定性を解消し、テストの信頼性を向上させています。

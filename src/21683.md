## 変更の背景

Go言語のコンパイラには、プログラムのパフォーマンスを最適化するための「エスケープ解析（Escape Analysis）」という重要な機能があります。エスケープ解析は、変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定します。スタック割り当ては高速ですが、関数呼び出しの終了とともにメモリが解放されます。一方、ヒープ割り当ては低速ですが、ガベージコレクションによって管理され、関数呼び出しのスコープを超えてもデータが存続できます。

このコミット以前のGoコンパイラでは、`&T{...}`のようなポインタリテラル（`PTRLIT`）の要素初期化子（例: `&Lit{&i}`における`&i`）が、無条件にヒープにエスケープすると判断されていました。これは、たとえその要素が関数のスコープ外に公開されない場合でも発生していました。このような不必要なヒープ割り当ては、ガベージコレクションの負荷を増やし、プログラムの実行速度を低下させる原因となります。

コミットメッセージにある「There is no reason for that.」という記述は、この挙動が最適ではなく、改善の余地があることを示しています。この変更の目的は、`PTRLIT`の要素初期化子に対するエスケープ解析の精度を高め、本当にヒープにエスケープする必要がある場合にのみヒープ割り当てが行われるようにすることです。これにより、Goプログラムの実行時パフォーマンスが向上します。

## 前提知識の解説

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、プログラム内の変数がその宣言されたスコープ（通常は関数）を「エスケープ」するかどうかを決定します。

*   **スタック割り当て**: 変数が関数内で完結し、関数の実行が終了すると不要になる場合、その変数はスタックに割り当てられます。スタックは高速なメモリ領域であり、割り当てと解放が非常に効率的です。
*   **ヒープ割り当て**: 変数が関数のスコープを超えて参照される可能性がある場合（例: グローバル変数に代入される、チャネルを通じて他のゴルーチンに渡される、関数の戻り値となるなど）、その変数はヒープに割り当てられます。ヒープはより柔軟なメモリ領域ですが、割り当てと解放にはオーバーヘッドがあり、ガベージコレクションの対象となります。

エスケープ解析の目的は、可能な限り多くの変数をスタックに割り当てることで、ガベージコレクションの頻度と負荷を減らし、プログラムのパフォーマンスを向上させることです。

### GoコンパイラのASTノード: `STRUCTLIT`と`PTRLIT`

Goコンパイラは、ソースコードを解析して抽象構文木（AST: Abstract Syntax Tree）を構築します。このASTの各ノードは、コードの特定の構造を表します。

*   **`STRUCTLIT` (Struct Literal)**: 構造体リテラルを表すASTノードです。例えば、`Vertex{X: 1, Y: 2}`のようなコードがこれに該当します。これは新しい構造体の値を直接初期化する際に使用されます。
*   **`PTRLIT` (Pointer Literal)**: ポインタリテラルを表すASTノードです。これは、構造体リテラルのアドレスを取る場合、例えば`&Vertex{X: 1, Y: 2}`のようなコードに該当します。この構文は、新しい`Vertex`構造体をヒープに割り当て、そのポインタを返すことを意味します（ただし、エスケープ解析の結果によってはスタックに割り当てられることもあります）。

このコミットの変更は、特に`&T{...}`形式の`PTRLIT`における、内部の要素（例: `&Lit{&i}`における`&i`）のエスケープ解析の挙動に焦点を当てています。

### `esc.c`と`escassign`関数

`src/cmd/gc/esc.c`は、Goコンパイラのエスケープ解析ロジックが実装されているファイルです。このファイルには、ASTノードを走査し、各変数のエスケープ挙動を分析するための関数群が含まれています。

`escassign`関数は、ある値が別の場所（変数、シンクなど）に代入される際のエスケープ挙動を分析する中心的な役割を担っています。`dst`（代入先）と`src`（代入元）のノードを受け取り、`src`が`dst`に代入されることでエスケープするかどうかを判断します。

## 技術的詳細

このコミットの核心は、`src/cmd/gc/esc.c`ファイル内の`esc`関数と`escassign`関数の挙動変更にあります。

変更前は、`OPTRLIT`（`PTRLIT`に対応する内部表現）のケースにおいて、その要素初期化子（`n->left`）が`e->theSink`という特別な「シンク」に代入されるかのように扱われていました。`e->theSink`は、コンパイラが追跡できない外部のメモリ領域を抽象的に表すもので、ここに代入されると、その値は無条件にヒープにエスケープすると判断されます。

```c
// 変更前 (抜粋)
case OPTRLIT:
    n->esc = EscNone;  // until proven otherwise
    e->noesc = list(e->noesc, n);
    n->escloopdepth = e->loopdepth;
    // Contents make it to memory, lose track.
    escassign(e, &e->theSink, n->left); // ここが問題
    break;
```

この挙動により、`&T{...}`のようなポインタリテラル内の要素（例: `&Lit{&i}`の`&i`）は、たとえそのポインタリテラル自体がスタックに割り当てられるべき場合でも、常にヒープにエスケープすると誤って判断されていました。

このコミットでは、`OPTRLIT`の処理が以下のように変更されました。

1.  `escassign(e, &e->theSink, n->left);` の行が `escassign(e, n, n->left);` に変更されました。
    *   これは、`OPTRLIT`の要素初期化子（`n->left`）が、もはや無条件に「シンク」に代入されるのではなく、`OPTRLIT`ノード自体（`n`）にリンクされることを意味します。
    *   これにより、`OPTRLIT`ノードのエスケープ挙動が、その要素初期化子のエスケープ挙動を決定するようになりました。つまり、`OPTRLIT`自体がヒープにエスケープする場合にのみ、その要素もヒープにエスケープすると判断されるようになります。
2.  `escassign`関数の`switch`文の`case`に`OPTRLIT`が追加されました。
    *   これは、`OPTRLIT`ノードが代入元（`src`）として`escassign`に渡された際に、特別な処理を必要としないことを明示しています。`OCONVNOP`, `OMAPLIT`, `OSTRUCTLIT`, `OCALLPART`と同様に、これらのノード自体がエスケープ挙動を持つわけではなく、その内部要素や結果がエスケープ解析の対象となるため、`break`で処理を終えます。

この変更により、`STRUCTLIT`の要素初期化子が既に`STRUCTLIT`自体にリンクされているのと同様に、`PTRLIT`の要素初期化子も`PTRLIT`自体にリンクされるようになりました。結果として、`PTRLIT`がエスケープする場合にのみ、その要素初期化子もエスケープするという、より正確なエスケープ解析が可能になります。

`test/escape2.go`と`test/escape2n.go`のテストケースが追加され、この新しいエスケープ解析の挙動が検証されています。特に、`ptrlitNoescape()`, `ptrlitNoEscape2()`, `ptrlitEscape()`の各関数は、`&Lit{&i}`のような構造体ポインタリテラルとその内部ポインタが、それぞれどのようにエスケープ解析されるべきかを示しています。

*   `ptrlitNoescape()`: リテラルも要素もエスケープしないケース。
*   `ptrlitNoEscape2()`: リテラルはエスケープしないが、要素はエスケープするケース（`sink = *x`により、`*x`が参照する`i`がヒープに移動）。
*   `ptrlitEscape()`: リテラルも要素もエスケープするケース（`sink = x`により、`x`が参照する`Lit`と`i`がヒープに移動）。

これらのテストケースは、変更が意図通りに機能し、不要なヒープ割り当てが削減されることを確認しています。

## コアとなるコードの解説

### `esc`関数内の`OPTRLIT`ケースの変更

```c
-		escassign(e, &e->theSink, n->left);
+		escassign(e, n, n->left);
```

この変更が最も重要です。
*   **変更前 (`escassign(e, &e->theSink, n->left);`)**: `OPTRLIT`ノードの左の子（`n->left`、これは通常、`&T{...}`の`T{...}`部分、つまり`OSTRUCTLIT`ノードを指します）が、無条件に`e->theSink`（コンパイラが追跡できない外部メモリ）にエスケープするとマークされていました。これにより、`&T{...}`の内部要素は常にヒープに割り当てられると判断されていました。
*   **変更後 (`escassign(e, n, n->left);`)**: `OPTRLIT`ノードの左の子（`n->left`）が、`OPTRLIT`ノード自体（`n`）にリンクされるようになりました。これは、「もし`OPTRLIT`ノード自体がエスケープするなら、その内部要素もエスケープする」という論理を導入します。これにより、`OPTRLIT`ノードがスタックに割り当てられるべき場合、その内部要素もスタックに割り当てられる可能性が生まれます。

コメントも「Contents make it to memory, lose track.」から「Link OSTRUCTLIT to OPTRLIT; if OPTRLIT escapes, OSTRUCTLIT elements do too.」に変更され、この新しい挙動を正確に反映しています。

### `escassign`関数内の`switch`文への`OPTRLIT`の追加

```c
 	case OCONVNOP:
 	case OMAPLIT:
 	case OSTRUCTLIT:
+	case OPTRLIT:
 	case OCALLPART:
 		break;
```

`escassign`関数は、`src`（代入元）のノードの種類に基づいてエスケープ解析のロジックを適用します。`OPTRLIT`がこの`switch`文の`case`に追加されたことで、`OPTRLIT`ノードが`src`として渡された場合、特別なエスケープ処理は行われず、`break`で処理が終了します。これは、`OPTRLIT`自体がエスケープ挙動を持つのではなく、その内部要素のエスケープ挙動が、`OPTRLIT`ノード自体のエスケープ挙動に依存するという新しいモデルと一致しています。つまり、`OPTRLIT`ノードが代入される際に、その内部要素が自動的にエスケープするわけではないことを示しています。

これらの変更により、Goコンパイラのエスケープ解析はより賢くなり、`&T{...}`形式のポインタリテラルとその要素に対して、より正確なスタック割り当ての判断を下せるようになりました。これは、ガベージコレクションの負荷軽減と全体的なパフォーマンス向上に貢献します。

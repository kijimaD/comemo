# [インデックス 25646] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、`linux/ppc64le`アーキテクチャでの`-buildmode=shared`オプションのサポートを有効にするものです。これにより、PowerPC 64-bit Little Endian (ppc64le) 環境でGoプログラムを共有ライブラリとしてビルドし、他のプログラムから利用できるようになります。具体的には、`go`コマンドと`link`コマンドの内部ロジックが更新され、ppc64leプラットフォームが共有ライブラリビルドの対象として認識されるようになります。

## 変更の背景

この変更の背景には、Go言語のアプリケーションがより多様なシステム環境で利用されるようになるという流れがあります。特に、IBM Power SystemsなどのPowerPCアーキテクチャは、エンタープライズ分野や高性能計算（HPC）で利用されており、これらの環境でGoプログラムを共有ライブラリとして提供できることは、Goの採用を促進する上で重要です。

Go 1.5で導入された`-buildmode=shared`は、Goパッケージを共有ライブラリ（`.so`ファイル）としてビルドし、他のGoプログラムやC/C++プログラムからリンクして利用できるようにする機能です。これにより、複数のGoプログラムが同じGoランタイムの共有ライブラリを共有できるようになり、ディスク使用量の削減や起動時間の短縮、さらにはC/C++アプリケーションとの連携が容易になるというメリットがあります。

このコミット以前は、`linux/ppc64le`プラットフォームでは`-buildmode=shared`がサポートされていませんでした。この変更は、`ppc64le`環境でのGoの共有ライブラリ機能の利用を可能にし、Goエコシステムのプラットフォームサポートを拡大することを目的としています。

## 前提知識の解説

*   **`ppc64le` (PowerPC 64-bit Little Endian)**: IBMが開発したPowerPCアーキテクチャの64ビット版で、リトルエンディアン方式を採用しています。主にサーバーや高性能計算システムで利用されます。Go言語は、様々なCPUアーキテクチャとOSの組み合わせ（プラットフォーム）をサポートしており、`linux/ppc64le`はその一つです。
*   **`cmd/go`**: Go言語の公式コマンドラインツールです。ソースコードのコンパイル、パッケージの管理、テストの実行など、Go開発における主要なタスクを担います。`go build`コマンドはこのツールの一部です。
*   **`cmd/link`**: Go言語のリンカです。コンパイラによって生成されたオブジェクトファイルを結合し、実行可能ファイルや共有ライブラリを生成します。
*   **`-buildmode=shared`**: `go build`コマンドのオプションの一つで、Goパッケージを共有ライブラリ（Linuxでは`.so`ファイル）としてビルドします。これにより、複数のGoプログラムが同じGoランタイムを共有したり、C/C++プログラムからGoの関数を呼び出したりすることが可能になります。
*   **`-linkshared`**: `go build`コマンドのオプションの一つで、Goプログラムをビルドする際に、Goランタイムや標準ライブラリを共有ライブラリとしてリンクするように指示します。
*   **PIC (Position-Independent Code)**: 位置独立コード。共有ライブラリのコードは、メモリ上のどこにロードされても正しく実行できるように、位置独立である必要があります。これは、共有ライブラリが複数のプロセスによって異なるアドレス空間にロードされる可能性があるためです。Goの`-buildmode=shared`では、内部的にPICを生成するようコンパイラに指示します。
*   **ELF (Executable and Linkable Format)**: LinuxなどのUnix系システムで広く使われている、実行可能ファイル、共有ライブラリ、オブジェクトファイルの標準フォーマットです。シンボルテーブル、セクション、ヘッダなどの情報を含みます。
*   **`STV_HIDDEN`**: ELFシンボル可視性の一つで、シンボルが共有ライブラリの外部からは見えないように（隠蔽されるように）指定します。これは、ライブラリの内部実装の詳細を隠蔽し、APIの安定性を保つために使用されます。
*   **`LinkExternal`**: Goリンカが、Go独自のリンカではなく、システムの外部リンカ（例: `gcc`）を使用して最終的なリンク処理を行うことを意味します。共有ライブラリの生成やC/C++コードとの連携には、外部リンカの機能が必要となることが多いです。

## 技術的詳細

このコミットは、`linux/ppc64le`プラットフォームでGoの共有ライブラリ機能（`-buildmode=shared`）を有効にするために、Goツールチェインの複数のコンポーネントにわたる変更を加えています。

1.  **`src/cmd/go/build.go`の変更**:
    *   `go build`コマンドが`-buildmode=shared`オプションを受け付け、`linux/ppc64le`をサポート対象プラットフォームとして認識するように更新されます。これにより、`go build -buildmode=shared -o libfoo.so foo.go`のようなコマンドがppc64le上で実行可能になります。
    *   `codegenArg = "-fPIC"`が設定されることで、コンパイラが位置独立コード（PIC）を生成するように指示されます。これは共有ライブラリの要件です。
    *   `-linkshared`オプションに関するエラーメッセージが修正され、より正確な情報を提供するようになります。

2.  **`src/cmd/link/internal/ld/lib.go`の変更**:
    *   Goリンカの内部で、`BuildmodeShared`（共有ライブラリビルドモード）が有効な場合に、`ppc64le`アーキテクチャがサポート対象として明示的に追加されます。これにより、リンカはppc64le上で共有ライブラリを生成する際の特定の処理を適切に実行できるようになります。

3.  **`src/cmd/link/internal/ld/symtab.go`の変更**:
    *   `putelfsym`関数は、ELFシンボルテーブルにエントリを書き込む役割を担います。この関数内の条件式が変更され、`STV_HIDDEN`シンボル可視性の設定ロジックが更新されます。
    *   具体的には、`BuildmodePIE`（位置独立実行可能ファイル）だけでなく、`DynlinkingGo()`（Goが共有ライブラリに動的にリンクされている状態）の場合も考慮されるようになります。これは、共有ライブラリとしてビルドされたGoコードが、その内部シンボルを外部に公開しないようにするために重要です。`runtime.duffzero`や`runtime.duffcopy`といった特定のランタイム関数は、特殊な最適化が施されているため、このルールから除外されます。

4.  **`src/cmd/link/internal/ppc64/obj.go`の変更**:
    *   `ppc64`アーキテクチャ固有のオブジェクトファイル処理を行う`archinit`関数が変更されます。
    *   `ld.BuildmodePIE`だけでなく、`ld.BuildmodeShared`の場合にも`ld.Linkmode = ld.LinkExternal`が設定されるようになります。これは、共有ライブラリをビルドする際に、Goリンカがシステムの外部リンカ（例: `ld`または`gcc`）を利用して最終的なリンク処理を行うことを意味します。外部リンカは、共有ライブラリの生成に必要な複雑な処理（例: ダイナミックリンキング情報の埋め込み）を適切に処理できます。
    *   また、`ld.Linkshared`が有効な場合にも`ld.Linkmode = ld.LinkExternal`が設定される新しいブロックが追加されています。これは、Goプログラムが共有ライブラリにリンクされる場合にも外部リンカを使用することを保証します。

これらの変更により、`linux/ppc64le`プラットフォーム上でGoの共有ライブラリが正しくビルドされ、実行時に必要なシンボル解決や動的リンクが適切に行われるようになります。

## コアとなるコードの解説

### `src/cmd/go/build.go`

*   **`case "linux/386", ..., "linux/ppc64le":`**:
    *   `buildModeInit`関数内で、`-buildmode=shared`が指定された際に、`platform`変数の値（例: `linux/ppc64le`）をチェックしています。この変更により、`linux/ppc64le`が共有ライブラリビルドをサポートするプラットフォームのリストに追加されました。これにより、`go build`コマンドはppc64le上で共有ライブラリを生成する際にエラーを発生させなくなります。
    *   `codegenArg = "-fPIC"`は、コンパイラに対して位置独立コード（PIC）を生成するよう指示するフラグです。共有ライブラリはメモリ上の任意のアドレスにロードされるため、PICである必要があります。
*   **`fatalf("-linkshared not supported on %s\n", platform)`**:
    *   以前は`-buildmode=shared`に関するエラーメッセージでしたが、`-linkshared`に関するエラーメッセージに修正されました。これは、エラーメッセージの正確性を向上させるための変更です。

### `src/cmd/link/internal/ld/lib.go`

*   **`if goos != "linux" || (goarch != "386" && ... && goarch != "ppc64le")`**:
    *   `BuildMode`の`Set`メソッド内で、ビルドモードが`"shared"`に設定された際のプラットフォームチェックが行われています。この条件式に`&& goarch != "ppc64le"`が追加されたことで、`linux`オペレーティングシステムと`ppc64le`アーキテクチャの組み合わせが、共有ライブラリビルドモードの有効なターゲットとして認識されるようになりました。これにより、リンカはppc64le上で共有ライブラリをビルドする際に`badmode()`エラーを返さなくなります。

### `src/cmd/link/internal/ld/symtab.go`

*   **`if (Buildmode == BuildmodePIE || DynlinkingGo()) && Thearch.Thechar == '9' ...`**:
    *   `putelfsym`関数は、ELFシンボルテーブルのエントリを処理します。この変更は、`ppc64`アーキテクチャ（`Thearch.Thechar == '9'`）において、特定の関数シンボル（`STT_FUNC`）の可視性（`STV_HIDDEN`）を決定するロジックを更新しています。
    *   以前は`BuildmodePIE`の場合のみ考慮されていましたが、`DynlinkingGo()`（Goが共有ライブラリに動的にリンクされている状態、つまり`-linkshared`が使われている場合）も条件に追加されました。これは、共有ライブラリとしてビルドされたGoコードが、その内部シンボルを外部に公開しないようにするために重要です。`runtime.duffzero`や`runtime.duffcopy`といった特定のランタイム関数は、特殊な最適化が施されているため、このルールから除外されます。

### `src/cmd/link/internal/ppc64/obj.go`

*   **`case ld.BuildmodePIE, ld.BuildmodeShared:`**:
    *   `ppc64`アーキテクチャ固有の初期化関数`archinit`内の`switch`文に`ld.BuildmodeShared`が追加されました。これにより、ビルドモードが`BuildmodePIE`または`BuildmodeShared`のいずれかである場合に、`ld.Linkmode = ld.LinkExternal`が設定されます。
    *   `ld.LinkExternal`は、Goリンカがシステムの外部リンカ（例: `ld`または`gcc`）を使用して最終的なリンク処理を行うことを意味します。共有ライブラリの生成には、外部リンカが提供する高度な機能が必要となるため、この設定は重要です。
*   **`if ld.Linkshared { ld.Linkmode = ld.LinkExternal }`**:
    *   新しく追加されたこのブロックは、`ld.Linkshared`（Goプログラムが共有ライブラリにリンクされるモード）が有効な場合にも、明示的に`ld.Linkmode = ld.LinkExternal`を設定します。これにより、共有ライブラリにリンクする際にも外部リンカが確実に使用され、正しい動的リンクが行われるようになります。

これらの変更は、`linux/ppc64le`プラットフォームにおけるGoの共有ライブラリ機能の完全なサポートを確立するために不可欠なものです。

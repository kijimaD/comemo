# [インデックス 21661] ファイルの概要

このコミットは、Goランタイムにおけるマップのガベージコレクション（GC）性能を大幅に改善するものです。特に、キーと値がポインタを含まない（例: `map[int]int`）大規模なマップにおいて、GCがマップ全体をスキャンするのを回避することで、GCポーズ時間を劇的に削減します。

## コミット

このコミットは、Goランタイムのマップ実装において、キーと値がポインタを含まない場合にガベージコレクタがマップの内容をスキャンしないように最適化を導入します。これにより、大規模なマップ（例えば `map[int]int`）のGCスキャン時間が、以前の数秒から無視できるレベルにまで短縮されます。この最適化は、オーバーフローバケットのポインタを保持するための独立したメカニズムを導入し、GCがマップのデータ構造全体を走査する必要をなくすことで実現されます。

    runtime: do not scan maps when k/v do not contain pointers
    
    Currently we scan maps even if k/v does not contain pointers.
    This is required because overflow buckets are hanging off the main table.
    This change introduces a separate array that contains pointers to all
    overflow buckets and keeps them alive. Buckets themselves are marked
    as containing no pointers and are not scanned by GC (if k/v does not
    contain pointers).
    
    This brings maps in line with slices and chans -- GC does not scan
    their contents if elements do not contain pointers.
    
    Currently scanning of a map[int]int with 2e8 entries (~8GB heap)
    takes ~8 seconds. With this change scanning takes negligible time.

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムが使用しなくなったメモリを自動的に解放する役割を担っています。しかし、このGCプロセスがアプリケーションの実行を一時的に停止させる「GCポーズ」は、特にリアルタイム性が求められるアプリケーションにおいて性能上のボトルネックとなることがあります。

このコミットが対処している問題は、Goのマップ（`map`）の実装に起因するGC性能の課題です。以前のGoランタイムでは、マップのキーと値がポインタを含まない型（例: `int`, `string`, `float64`などのプリミティブ型や、ポインタを含まない構造体）であっても、GCはマップの内部構造全体をスキャンしていました。これは、マップが内部的に「バケット」と呼ばれるデータ構造を使用し、バケットが満杯になった際には「オーバーフローバケット」をリンクして拡張するためです。これらのオーバーフローバケットは、メインのバケットからポインタで参照されており、GCはこれらのポインタを辿って、マップのすべての部分が到達可能であり、誤って解放されないことを確認する必要がありました。

このGCの挙動は、特にエントリ数が非常に多い大規模なマップ（例: 2億エントリを持つ`map[int]int`が約8GBのヒープを消費するケース）において、深刻なGCポーズを引き起こしていました。コミットメッセージに記載されているように、このようなマップのスキャンには約8秒もの時間がかかり、アプリケーションの応答性に大きな影響を与えていました。

この問題は、GoのIssue #9477「runtime: Large maps cause significant GC pauses」として報告されており、このコミットはその解決策として導入されました。目標は、スライスやチャネルと同様に、要素がポインタを含まない場合にはGCがその内容をスキャンしないように、マップのGC動作を改善することでした。

## 前提知識の解説

このコミットの変更を理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **Goのガベージコレクション (GC)**:
    *   Goは並行マーク＆スイープ方式のGCを採用しています。これは、GCがアプリケーションの実行と並行して動作し、GCポーズを最小限に抑えることを目指しています。
    *   GCは、ヒープ上のオブジェクトが「ライブ」（プログラムから到達可能）であるか「デッド」（到達不可能で解放可能）であるかを判断するために、ポインタを辿ってオブジェクトグラフを走査します。
    *   GCがスキャンする必要があるのは、ポインタを含むデータのみです。`int`や`float64`のようなプリミティブ型はポインタを含まないため、それ自体をスキャンする必要はありません。

2.  **Goのマップ (map) の内部構造**:
    *   Goのマップはハッシュテーブルとして実装されています。
    *   **バケット (Bucket)**: マップのデータは、固定サイズのバケットに格納されます。各バケットは通常、少数のキーと値のペア（例えば8ペア）を保持できます。
    *   **オーバーフローバケット (Overflow Bucket)**: あるバケットが満杯になった場合、Goランタイムは新しいオーバーフローバケットを割り当て、それを既存のバケットにリンクします。これにより、同じハッシュ値を持つエントリが多数存在する場合でも、マップは効率的に拡張できます。オーバーフローバケットは、メインのバケットからポインタで参照されます。
    *   **`hmap`構造体**: Goランタイム内部では、マップは`hmap`という構造体で表現されます。この構造体には、バケットへのポインタ、マップのサイズ、ハッシュシードなどの情報が含まれています。
    *   **`hiter`構造体**: マップのイテレーション（`for range`ループなど）を行う際には、`hiter`というイテレータ構造体が使用されます。これもマップの内部状態へのポインタを保持します。

3.  **ポインタと非ポインタ型**:
    *   Goの型には、ポインタを含む型（例: `*int`, `interface{}`, `string`（内部的にポインタを持つ）、スライス、チャネル、マップ、ポインタを含む構造体）と、ポインタを含まない型（例: `int`, `float64`, `bool`, ポインタを含まない構造体）があります。
    *   GCは、ポインタを含む型が参照するメモリ領域を追跡し、ライブであるかどうかを判断します。ポインタを含まない型は、それ自体が他のメモリを参照しないため、GCスキャンの対象外となります。

このコミット以前は、マップのキーと値がポインタを含まない場合でも、オーバーフローバケットがポインタでリンクされているため、GCはマップの内部構造全体をスキャンする必要がありました。これが、大規模なマップでGCポーズが長くなる原因でした。

## 技術的詳細

このコミットの核心は、キーと値がポインタを含まないマップのオーバーフローバケットをGCが効率的に管理するための新しいメカニズムを導入することです。これにより、GCはマップのデータ部分全体をスキャンすることなく、オーバーフローバケットが適切に保持されることを保証できます。

具体的な変更点は以下の通りです。

1.  **`kindNoPointers`フラグの導入と利用**:
    *   `src/cmd/gc/reflect.c` (Goコンパイラの型情報生成部分) と `src/reflect/type.go` (リフレクションパッケージの型情報) が更新され、マップのバケット型（`bmap`）がキーと値の両方にポインタを含まない場合に、そのバケットの`rtype`（ランタイム型情報）に`kindNoPointers`フラグが設定されるようになりました。
    *   このフラグは、GCに対して「この型のオブジェクトの内部にはポインタがないため、詳細なスキャンは不要である」というヒントを与えます。

2.  **`hmap.overflow`フィールドの追加**:
    *   Goのマップの内部表現である`hmap`構造体（`src/runtime/hashmap.go`に定義）に、新しいフィールド`overflow *[2]*[]*bmap`が追加されました。
    *   このフィールドは、オーバーフローバケットへのポインタを保持するための専用の配列です。
        *   `hmap.overflow[0]`は現在のバケット配列に関連するオーバーフローバケットへのポインタのスライスを保持します。
        *   `hmap.overflow[1]`はマップの成長（リサイズ）中に古いバケット配列に関連するオーバーフローバケットへのポインタのスライスを保持します。
    *   重要なのは、`hmap.overflow`フィールド自体はポインタ（`*[2]*[]*bmap`）であるため、GCはこのフィールドをスキャンします。これにより、`hmap.overflow`が参照するオーバーフローバケットのスライス、そしてそのスライスが参照する個々のオーバーフローバケットがGCによって「ライブ」であると認識され、解放されるのを防ぎます。
    *   これにより、キーと値がポインタを含まないマップの場合、GCはマップの巨大なデータ部分をスキャンする代わりに、この比較的小さな`hmap.overflow`配列のみをスキャンすればよくなります。

3.  **`hiter.overflow`フィールドの追加**:
    *   マップイテレータの内部表現である`hiter`構造体（`src/runtime/hashmap.go`に定義）にも、対応する`overflow [2]*[]*bmap`フィールドが追加されました。
    *   イテレータが初期化される際、`hmap.overflow`のスナップショットが`hiter.overflow`にコピーされます。これにより、イテレーション中にマップが成長したり、新しいオーバーフローバケットが追加されたりしても、イテレータは関連するすべてのオーバーフローバケットへの参照を保持し続け、GCによる早期解放を防ぎます。

4.  **ランタイム関数の更新**:
    *   `src/runtime/hashmap.go`内の主要なマップ操作関数（`setoverflow`, `makemap`, `hashGrow`, `evacuate`など）が更新され、新しい`hmap.overflow`スライスを適切に管理するようになりました。
    *   `setoverflow`関数は、オーバーフローバケットが作成される際に、そのバケットへのポインタを`hmap.overflow[0]`スライスに追加するようになりました。
    *   `hashGrow`関数は、マップがリサイズされる際に、現在のオーバーフローバケットのスライスを`hmap.overflow[1]`（古い世代）に昇格させ、`hmap.overflow[0]`をクリアします。
    *   `evacuate`関数は、古いバケットが完全に処理された後、`hmap.overflow[1]`をクリアして古いオーバーフローバケットを解放可能にします。

この変更により、GCはマップのキーと値がポインタを含まない場合、マップのデータが格納されているバケット自体をスキャンする必要がなくなります。代わりに、`hmap.overflow`という小さなポインタの配列をスキャンするだけで、すべてのオーバーフローバケットがライブであることを保証できるようになります。これにより、GCの作業量が大幅に削減され、GCポーズ時間が短縮されます。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、以下の3つのファイルに集中しています。

1.  **`src/cmd/gc/reflect.c`**:
    *   Goコンパイラが型情報を生成する部分です。
    *   `mapbucket`関数において、マップのキーと値がポインタを含まない場合に、生成されるバケット型（`bucket`）に`haspointers = 1`（ポインタなし）というフラグを設定するロジックが追加されました。これは、GCがこのバケットの内容をスキャンしないようにするための指示です。
    *   `hmap`構造体の定義において、`overflow`フィールドが追加され、そのオフセットが適切に計算されるようになりました。
    *   `hiter`構造体の定義も更新され、`overflow`フィールドが追加され、そのサイズ計算が調整されました。

2.  **`src/reflect/type.go`**:
    *   Goのリフレクションパッケージの一部です。
    *   `bucketOf`関数において、マップのキーと値の型が両方ともポインタを含まない場合に、生成されるバケットの`rtype`に`kindNoPointers`フラグを設定するロジックが追加されました。これは、ランタイムがこのバケットのGC動作を決定するために使用します。
    *   `MapOf`関数内の`mapType`の初期化方法が微調整されました。

3.  **`src/runtime/hashmap.go`**:
    *   Goランタイムにおけるマップの実際の内部実装です。
    *   `hmap`構造体に`overflow *[2]*[]*bmap`フィールドが追加されました。
    *   `hiter`構造体にも`overflow [2]*[]*bmap`フィールドが追加されました。
    *   `setoverflow`関数が変更され、`hmap`へのポインタを受け取るようになり、キーと値がポインタを含まないマップの場合に`hmap.overflow`にオーバーフローバケットを追加するロジックが追加されました。
    *   `createOverflow`ヘルパー関数が追加され、`hmap.overflow`スライスがまだ割り当てられていない場合に初期化を行います。
    *   `makemap`、`mapiterinit`、`hashGrow`、`evacuate`などの主要なマップ操作関数が、新しい`hmap.overflow`フィールドを適切に管理するように更新されました。これには、オーバーフローバケットの追加、マップ成長時の世代交代、イテレータへのスナップショット提供などが含まれます。
    *   `hmap`と`hiter`のサイズチェックが更新され、新しいフィールドの追加に対応しました。

## コアとなるコードの解説

このコミットの核心的な変更は、`hmap`構造体への`overflow`フィールドの追加と、それに関連するランタイム関数の変更です。

### `hmap.overflow`フィールド

```go
type hmap struct {
    // ... 既存のフィールド ...
    overflow *[2]*[]*bmap
}
```
この`overflow`フィールドは、キーと値がポインタを含まないマップのオーバーフローバケットをGCから保護するための新しいメカニズムです。
*   `*[2]*[]*bmap`という型は、「2つの要素を持つ配列へのポインタ」であり、その各要素は「`*bmap`（バケットへのポインタ）のスライスへのポインタ」です。
*   `overflow[0]`は現在のマップのオーバーフローバケットを保持し、`overflow[1]`はマップのリサイズ中に古いマップのオーバーフローバケットを保持します。
*   このフィールド自体はポインタであるため、GCはこれをスキャンします。これにより、`overflow`が参照するスライス、そしてスライスが参照する個々の`bmap`（オーバーフローバケット）がGCによってライブであると認識され、解放されなくなります。

### `setoverflow`関数の変更

```go
// 変更前:
// func (b *bmap) setoverflow(t *maptype, ovf *bmap) { ... }

// 変更後:
func (h *hmap) setoverflow(t *maptype, b, ovf *bmap) {
    if t.bucket.kind&kindNoPointers != 0 { // バケットがポインタを含まない場合
        h.createOverflow()
        *h.overflow[0] = append(*h.overflow[0], ovf) // オーバーフローバケットをhmap.overflowに追加
    }
    *(**bmap)(add(unsafe.Pointer(b), uintptr(t.bucketsize)-regSize)) = ovf // 従来のリンク
}
```
この関数は、新しいオーバーフローバケットが作成されたときに呼び出されます。変更後、`hmap`へのポインタ`h`を受け取るようになりました。
*   `t.bucket.kind&kindNoPointers != 0`のチェックにより、マップのキーと値がポインタを含まない場合にのみ、新しいオーバーフローバケット`ovf`が`h.overflow[0]`スライスに追加されます。
*   これにより、GCは`hmap.overflow`をスキャンするだけで、これらのオーバーフローバケットがライブであることを認識できるようになります。
*   従来の`*(**bmap)(add(...)) = ovf`の部分は、バケット間の物理的なリンクを維持するために残されています。

### `kindNoPointers`フラグの利用

`src/reflect/type.go`の`bucketOf`関数で、マップのキーと値の型が両方ともポインタを含まない場合に、生成されるバケットの`rtype`に`kindNoPointers`フラグが設定されます。

```go
func bucketOf(ktyp, etyp *rtype) *rtype {
    // ...
    var kind uint8
    if ktyp.kind&kindNoPointers != 0 && etyp.kind&kindNoPointers != 0 {
        kind = kindNoPointers
    }
    // ...
    b.kind = kind // バケットのrtypeにkindフラグを設定
    // ...
}
```
この`kind`フラグは、ランタイムがGC時にバケットの内容をスキャンする必要があるかどうかを判断するために使用されます。`kindNoPointers`が設定されていれば、GCはバケットの内部を詳細にスキャンする必要がなくなり、`hmap.overflow`を通じてのみオーバーフローバケットの生存を追跡します。

これらの変更により、GCは大規模なマップの内部構造全体を走査する代わりに、`hmap.overflow`という小さなポインタの配列をスキャンするだけで済むようになり、GCの効率が大幅に向上しました。

# [インデックス 2366] ファイルの概要

このコミットは、Goランタイムにおける`defer`呼び出しのスタック管理に関する重要な修正を含んでいます。具体的には、`deferreturn`と`jmpdefer`という2つのランタイム関数間の結合度を低減し、スタック操作の堅牢性を向上させています。

変更されたファイルは以下の通りです。

*   `src/runtime/386/asm.s`: 32ビットアーキテクチャ（x86）向けのアセンブリコードで、`jmpdefer`関数の実装が変更されています。
*   `src/runtime/amd64/asm.s`: 64ビットアーキテクチャ（x86-64）向けのアセンブリコードで、`jmpdefer`関数の実装が変更されています。
*   `src/runtime/proc.c`: Goランタイムのプロセス管理に関するCコードで、`deferreturn`関数のシグネチャと`jmpdefer`の呼び出し方法が変更されています。
*   `src/runtime/runtime.h`: Goランタイムのヘッダーファイルで、`jmpdefer`関数のプロトタイプが変更されています。

## コミット

このコミットは、Goランタイムの`defer`メカニズムにおけるスタック管理の脆弱性を修正します。以前は、`jmpdefer`関数が`deferreturn`関数のスタックフレームサイズを「マジックナンバー」として知っていることに依存していましたが、この変更により、`deferreturn`が明示的に呼び出し元のスタックポインタを`jmpdefer`に渡すようになりました。これにより、固定値への依存が解消され、コードの堅牢性と保守性が向上しました。

```

avoid tight coupling between deferreturn and jmpdefer.
before, jmpdefer knew the exact frame size of deferreturn
in order to pop it off the stack.  now, deferreturn passes
jmpdefer a pointer to the frame above it explicitly.
that avoids a magic constant and should be less fragile.

OCL=29801
```

## 変更の背景

Go言語の`defer`ステートメントは、関数がリターンする直前に実行される関数呼び出しをスケジュールする強力な機能です。この機能は、リソースの解放（ファイルのクローズ、ロックの解除など）を確実に行うために広く利用されます。

このコミットが作成された2009年頃のGoランタイムは、まだ初期段階であり、スタック管理や関数呼び出し規約に関する最適化や堅牢化が活発に行われていました。

変更の背景にある具体的な問題は、`defer`された関数がすべて実行された後、元の呼び出し元に戻るためのメカニズムにありました。この処理は、`deferreturn`というランタイム関数が担当し、最終的に`jmpdefer`というアセンブリ関数を呼び出してスタックポインタを適切に調整し、元の実行フローに戻していました。

問題は、`jmpdefer`が`deferreturn`のスタックフレームサイズをハードコードされたオフセット（「マジック定数」）として知っていることにありました。これは、`deferreturn`の内部実装（ローカル変数の数、引数のサイズなど）が変更されると、`jmpdefer`が期待するスタックオフセットがずれ、ランタイムクラッシュや不正な動作を引き起こす可能性がありました。このような「密結合」は、コードの保守性を著しく低下させ、将来の変更を困難にします。

このコミットは、この脆弱な依存関係を解消し、`deferreturn`が自身の呼び出し元のスタックポインタを明示的に`jmpdefer`に渡すようにすることで、より柔軟で堅牢なスタック管理を実現することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goの`defer`キーワード**:
    *   `defer`は、そのステートメントを含む関数が終了する直前（`return`ステートメントの直前、またはパニック発生時）に、指定された関数呼び出しをスケジュールします。
    *   複数の`defer`ステートメントがある場合、それらはLIFO（後入れ先出し）順で実行されます。
    *   `defer`された関数の引数は、`defer`ステートメントが評価された時点で評価されます。

2.  **Goランタイムのスタック管理**:
    *   Goの各ゴルーチンは独自のスタックを持っています。
    *   関数が呼び出されると、その関数のための「スタックフレーム」がスタックにプッシュされます。スタックフレームには、関数の引数、ローカル変数、呼び出し元のリターンアドレスなどが含まれます。
    *   スタックポインタ（SPレジスタ）は、現在のスタックの最上位（または最下位、アーキテクチャによる）を指します。
    *   関数からのリターン時には、スタックフレームがポップされ、SPが元の位置に戻されます。
    *   Goランタイムは、スタックの動的な拡張（`morestack`）や縮小（`lessstack`）を管理します。

3.  **アセンブリ言語の基礎**:
    *   **`TEXT`**: 関数の開始を宣言します。例: `TEXT jmpdefer(SB), 7, $0` は、`jmpdefer`という名前の関数を定義し、スタックフレームサイズや引数の情報を含みます。
    *   **`MOVL`/`MOVQ`**: データをレジスタやメモリ間で移動させます。`MOVL`は32ビット、`MOVQ`は64ビットオペランド用です。
    *   **`ADDL`/`ADDQ`**: 加算を行います。
    *   **`SUBL`/`SUBQ`**: 減算を行います。
    *   **`LEAL`/`LEAQ`**: "Load Effective Address"（実効アドレスをロード）命令。メモリのアドレスを計算し、そのアドレスをレジスタに格納します。これは、メモリの内容を読み込むのではなく、アドレス自体を計算するために使われるため、ポインタ演算によく利用されます。`LEAL`は32ビット、`LEAQ`は64ビット用です。
    *   **`JMP`**: 無条件ジャンプ。指定されたアドレスに実行フローを移します。
    *   **`SP`**: スタックポインタレジスタ。
    *   **`AX`, `BX`, `CX`, `DI`など**: 汎用レジスタ。
    *   **`(SP)`**: SPが指すメモリ位置（スタックのトップ）。
    *   **`4(SP)` / `8(SP)` / `16(SP)`**: SPが指す位置からオフセットしたメモリ位置。これは、スタック上の引数やローカル変数にアクセスするためによく使われます。例えば、`4(SP)`はSPの指すアドレスから4バイト上位（または下位、スタックの成長方向による）のアドレスにある値を示します。

4.  **`uintptr`型**:
    *   Goにおける`uintptr`型は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタ演算を行う際に、型安全性を犠牲にしてでもアドレスを数値として扱いたい場合に用いられます。ランタイムの低レベルなコードでよく見られます。

## 技術的詳細

このコミットの核心は、`deferreturn`と`jmpdefer`間のスタックフレーム情報の受け渡し方法の変更にあります。

**変更前:**
`jmpdefer`は、`deferreturn`が呼び出された際のスタックの状態を仮定し、`deferreturn`のスタックフレームサイズをハードコードされたオフセット（例: `$(4+56)`や`$(8+56)`）として知っていました。このオフセットを使ってスタックポインタを調整し、元の呼び出し元に戻っていました。

**変更後:**
`deferreturn`は、`jmpdefer`を呼び出す際に、`defer`された関数（`fn`）だけでなく、`deferreturn`自身の呼び出し元のスタックポインタ（`sp`）も引数として渡すようになりました。
`jmpdefer`はこの`sp`引数を利用して、`LEAL -4(BX), SP` (32-bit) または `LEAQ -8(BX), SP` (64-bit) のように、動的にスタックポインタを調整します。これにより、`deferreturn`のスタックフレームサイズが変更されても、`jmpdefer`は正しく動作するようになります。

具体的な変更点は以下の通りです。

1.  **`src/runtime/runtime.h`**:
    *   `jmpdefer`関数のプロトタイプが変更されました。
        *   変更前: `void jmpdefer(byte*);` (関数ポインタのみを受け取る)
        *   変更後: `void jmpdefer(byte*, void*);` (関数ポインタとスタックポインタを受け取る)

2.  **`src/runtime/proc.c`**:
    *   `sys·deferreturn`関数のシグネチャが変更されました。
        *   変更前: `sys·deferreturn(int32 arg0)`
        *   変更後: `sys·deferreturn(uintptr arg0)`
        *   `arg0`の型が`int32`から`uintptr`に変更されています。これは、スタックポインタのようなアドレス値を扱うためにより適切な型です。
    *   `sys·deferreturn`内のコメントが削除されました。
        *   `// warning: jmpdefer knows the frame size of this routine. dont change anything that might change the frame size`
        *   この警告コメントは、まさにこのコミットで解決しようとしている「密結合」の問題を指摘していました。問題が解決されたため、コメントは不要になりました。
    *   `jmpdefer`の呼び出し方法が変更されました。
        *   変更前: `jmpdefer(sp);`
        *   変更後: `jmpdefer(fn, sp);`
        *   `defer`された関数ポインタ`fn`と、`deferreturn`の呼び出し元のスタックポインタ`sp`の両方を渡すようになりました。

3.  **`src/runtime/386/asm.s` (32-bit x86)**:
    *   `jmpdefer`関数の引数処理とスタック操作が変更されました。
        *   変更前は、`4(SP)`から関数ポインタを読み込み、`$(4+56)`をSPに加算してスタックをポップしていました。`56`という値が`deferreturn`のスタックフレームサイズに相当する「マジック定数」でした。
        *   変更後は、`4(SP)`から関数ポインタ（`fn`）を`AX`に、`8(SP)`から呼び出し元のスタックポインタ（`caller sp`）を`BX`に読み込みます。
        *   `LEAL -4(BX), SP` を使用して、`BX`（呼び出し元のSP）から4バイトを引いたアドレスを新しいSPとして設定します。これは、`CALL`命令がリターンアドレスをプッシュした後のSPの位置を正確に指すようにするためです。
        *   `SUBL $5, (SP)` は、リターンアドレスを5バイト減らします。これは、Goの関数呼び出し規約において、`CALL`命令の直後の命令（通常は次の命令）に戻るのではなく、`CALL`命令自体に戻るように調整するためと考えられます。これにより、`defer`処理後に元の関数呼び出しが再開されるような挙動を実現します。

4.  **`src/runtime/amd64/asm.s` (64-bit x86-64)**:
    *   `jmpdefer`関数の引数処理とスタック操作が変更されました。基本的なロジックは32ビット版と同じですが、レジスタサイズとスタックオフセットが64ビット用に調整されています。
        *   `MOVQ 8(SP), AX` で関数ポインタを、`MOVQ 16(SP), BX` で呼び出し元のスタックポインタを読み込みます。
        *   `LEAQ -8(BX), SP` を使用して、`BX`（呼び出し元のSP）から8バイトを引いたアドレスを新しいSPとして設定します。64ビット環境ではポインタサイズが8バイトであるため、`CALL`命令後のSP位置を調整するために8バイトのオフセットが使われます。
        *   `SUBQ $5, (SP)` は、32ビット版と同様にリターンアドレスを5バイト減らします。これは、`CALL`命令の直後の命令に戻るのではなく、`CALL`命令自体に戻るように調整するためです。

これらの変更により、`jmpdefer`は`deferreturn`の内部実装に依存することなく、動的に正しいスタックポインタを計算できるようになり、ランタイムの堅牢性が大幅に向上しました。

## コアとなるコードの解説

### `src/runtime/386/asm.s` および `src/runtime/amd64/asm.s` の変更

これらのアセンブリファイルでは、`jmpdefer`関数の実装が根本的に変更されています。

**変更前:**
`jmpdefer`は、スタック上の固定オフセット（32ビット版では`4(SP)`、64ビット版では`8(SP)`）から`defer`された関数ポインタを読み込み、その後、`$(4+56)`または`$(8+56)`という「マジック定数」を使ってスタックポインタ`SP`を調整していました。この`56`という値が`deferreturn`のスタックフレームサイズを暗黙的に仮定していました。

**変更後:**
1.  **引数の読み込み**:
    *   32ビット版: `MOVL 4(SP), AX` (関数ポインタ `fn` を `AX` に), `MOVL 8(SP), BX` (呼び出し元のスタックポインタ `caller sp` を `BX` に)
    *   64ビット版: `MOVQ 8(SP), AX` (関数ポインタ `fn` を `AX` に), `MOVQ 16(SP), BX` (呼び出し元のスタックポインタ `caller sp` を `BX` に)
    `jmpdefer`が2つの引数を受け取るようになったため、スタック上のオフセットもそれに合わせて変更されています。

2.  **スタックポインタの調整**:
    *   32ビット版: `LEAL -4(BX), SP`
    *   64ビット版: `LEAQ -8(BX), SP`
    `LEAL`/`LEAQ`命令は、`BX`レジスタ（`deferreturn`の呼び出し元のスタックポインタ）からそれぞれ4バイト/8バイトを引いたアドレスを計算し、その結果を`SP`レジスタに格納します。これにより、`SP`は`deferreturn`が呼び出される前の、`CALL`命令がリターンアドレスをプッシュした直後の位置に正確に戻されます。この操作は、`deferreturn`のスタックフレームサイズに依存せず、動的に正しいスタック位置を復元します。

3.  **リターンアドレスの調整**:
    *   `SUBL $5, (SP)` (32ビット版) / `SUBQ $5, (SP)` (64ビット版)
    これは、スタックのトップにあるリターンアドレス（`CALL`命令によってプッシュされたアドレス）を5バイト減算します。Goの関数呼び出し規約では、`CALL`命令は次の命令のアドレスをリターンアドレスとしてプッシュします。しかし、`defer`処理後には、元の関数呼び出しの`CALL`命令自体に戻り、その`CALL`命令が再度実行されるような挙動が必要な場合があります。この5バイトの減算は、x86/x86-64アーキテクチャにおける`CALL`命令の典型的なサイズ（1バイトのオペコード + 4バイトの相対アドレス）を考慮し、リターンアドレスを`CALL`命令の開始位置に戻すためのものです。これにより、`defer`処理が完了した後、元の関数が適切に再開されることを保証します。

4.  **ジャンプ**:
    *   `JMP AX`
    `AX`レジスタに格納されている`defer`された関数ポインタにジャンプし、その関数の実行を開始します。

### `src/runtime/proc.c` の変更

1.  **`sys·deferreturn`関数のシグネチャ変更**:
    *   `sys·deferreturn(int32 arg0)` から `sys·deferreturn(uintptr arg0)` へと変更されました。`uintptr`はポインタを保持するのに十分なサイズの整数型であり、スタックポインタのようなアドレス値を扱う際に、より適切で安全な型です。

2.  **警告コメントの削除**:
    *   `// warning: jmpdefer knows the frame size of this routine. dont change anything that might change the frame size`
    このコメントは、`jmpdefer`が`deferreturn`のスタックフレームサイズに依存しているという問題点を明示していました。今回の変更でこの依存関係が解消されたため、コメントは削除されました。

3.  **`jmpdefer`呼び出しの変更**:
    *   `jmpdefer(sp);` から `jmpdefer(fn, sp);` へと変更されました。
    `defer`された関数ポインタ`fn`と、`deferreturn`の呼び出し元のスタックポインタ`sp`の両方を`jmpdefer`に渡すようになりました。これにより、`jmpdefer`は固定オフセットに依存せず、動的にスタックを調整できるようになります。

### `src/runtime/runtime.h` の変更

*   `jmpdefer`関数のプロトタイプが `void jmpdefer(byte*);` から `void jmpdefer(byte*, void*);` に変更されました。これは、`jmpdefer`が2つの引数（関数ポインタと汎用ポインタとしてのスタックポインタ）を受け取るようになったことを宣言しています。

これらの変更は、Goランタイムの低レベルなスタック管理において、ハードコードされた値への依存を排除し、より柔軟で堅牢な設計へと進化させるための重要なステップでした。

# [インデックス 26939] ファイルの概要

このコミットは、Go言語の標準ライブラリ `bufio` パッケージにおける `Reader.Peek` メソッドの挙動変更に関するものです。具体的には、`Peek` メソッドが `ErrBufferFull` エラーを返す際の動作が修正され、要求されたバイト数 `n` が内部バッファのサイズ `len(b.buf)` を超える場合でも、バッファ内に存在する利用可能な部分的なデータを返すようになりました。

## 元コミット内容

`bufio: Reader.Peek returns partial results on ErrBufferFull`

既存の実装では、`n > len(b.buf)` の場合に `nil, ErrBufferFull` を返していましたが、この変更により、バッファ内の利用可能なデータと `ErrBufferFull` を返すようになります。

`Fixes #14121`

## 変更の背景

この変更は、GoのIssue #14121 で報告された問題に対応するものです。`bufio.Reader.Peek(n)` メソッドは、内部バッファから `n` バイトを読み込まずに「覗き見」する機能を提供します。しかし、これまでの実装では、要求されたバイト数 `n` が `Reader` の内部バッファの最大サイズ `len(b.buf)` を超える場合、たとえバッファ内に一部のデータが既に存在していても、`nil` と `ErrBufferFull` を返していました。

この挙動は、呼び出し元にとって不便であり、予期せぬデータ損失のように見える可能性がありました。例えば、バッファに10バイトのデータがあり、`Peek(20)` を呼び出した場合、以前は `nil` が返され、利用可能な10バイトの情報が得られませんでした。この修正は、このような状況でも利用可能な部分的なデータを返すことで、APIの使いやすさと堅牢性を向上させることを目的としています。

## 前提知識の解説

*   **`bufio` パッケージ**: Go言語の標準ライブラリの一部で、I/O操作をバッファリングすることで効率を向上させるための機能を提供します。`Reader` と `Writer` の2つの主要な型があります。
*   **`bufio.Reader`**: バッファリングされた読み取り操作を提供します。内部にバイトスライス（バッファ）を持ち、基となる `io.Reader` からデータを読み込み、必要に応じてバッファを埋めます。
*   **`Reader.Peek(n int) ([]byte, error)`**: このメソッドは、次の `n` バイトを読み込まずに返します。返されるバイトスライスは、`Reader` の内部バッファを指しており、次の読み取り操作によって無効になる可能性があります。`Peek` は、ストリームの先頭を検査して、次に何を読み取るべきかを判断するのに役立ちます。
*   **`ErrBufferFull`**: `bufio` パッケージで定義されているエラーで、`Peek` メソッドが要求された `n` バイトを内部バッファに格納できない場合に返されます。これは、`n` がバッファの最大サイズよりも大きい場合に発生します。
*   **バッファリングI/Oの利点**: 小さな読み取り/書き込み操作が頻繁に行われる場合に、基となるシステムコール（ディスクI/OやネットワークI/O）の回数を減らし、パフォーマンスを向上させます。

## 技術的詳細

このコミットの核心は、`bufio.Reader.Peek` メソッドの内部ロジックの変更にあります。

以前の実装では、`Peek` が呼び出された際に、まず `n > len(b.buf)` という条件をチェックしていました。この条件が真の場合、つまり要求されたバイト数 `n` が内部バッファの最大容量を超えている場合、メソッドは即座に `nil, ErrBufferFull` を返していました。このとき、バッファ内に既にデータが存在するかどうかは考慮されませんでした。

新しい実装では、この初期チェックが変更されています。
1.  まず、`n < 0` のチェックはそのまま残り、負の数を要求した場合は `ErrNegativeCount` を返します。
2.  次に、`for b.w-b.r < n && b.w-b.r < len(b.buf) && b.err == nil` というループが実行されます。
    *   `b.w-b.r` は現在バッファ内に利用可能なバイト数を示します。
    *   このループは、要求された `n` バイトがまだ利用可能でない（`b.w-b.r < n`）が、バッファがまだ満杯ではない（`b.w-b.r < len(b.buf)`）場合に `b.fill()` を呼び出してバッファを埋めようとします。
    *   このループの目的は、可能な限り多くのデータをバッファに読み込むことです。
3.  ループが終了した後、`if n > len(b.buf)` という条件が再度チェックされます。
    *   この時点で `n` がバッファの最大容量を超えている場合、メソッドは `b.buf[b.r:b.w]` (現在バッファ内に存在するすべてのデータ) と `ErrBufferFull` を返します。
    *   これにより、たとえ `ErrBufferFull` が返されても、呼び出し元は利用可能な部分的なデータを取得できるようになります。
4.  `n <= len(b.buf)` の場合は、以前と同様に、バッファ内のデータが `n` バイトに満たない場合に `ErrBufferFull` または `io.EOF` を返すロジックが続きます。

この変更により、`Peek` の呼び出し元は、`ErrBufferFull` を受け取った場合でも、返されたバイトスライスが空でない可能性があることを考慮する必要があります。これは、APIのセマンティクスをより柔軟にし、部分的なデータでも処理を進めたいシナリオに対応できるようになります。

テストコード `src/bufio/bufio_test.go` も、この新しい挙動を反映するように更新されています。特に、`Peek(32)` を呼び出した際に、以前は `nil, ErrBufferFull` を期待していた箇所が、`"abcdefghijklmnop", ErrBufferFull` (利用可能な16バイトのデータ) を期待するように変更されています。

## コアとなるコードの解説

`src/bufio/bufio.go` の変更点:

1.  **初期の `n > len(b.buf)` チェックの削除と移動**:
    以前は、`Peek` メソッドの冒頭で `n > len(b.buf)` の条件がチェックされ、真であれば即座に `nil, ErrBufferFull` が返されていました。この変更では、このチェックが削除され、バッファを埋めるループの後に移動されました。

2.  **バッファを埋めるループの条件変更**:
    以前のループ条件 `for b.w-b.r < n && b.err == nil` に、`b.w-b.r < len(b.buf)` という条件が追加されました。
    *   `b.w-b.r < n`: まだ要求された `n` バイトがバッファにないことを意味します。
    *   `b.w-b.r < len(b.buf)`: バッファがまだ満杯ではないことを意味します。
    この変更により、バッファが満杯になるまで、または要求された `n` バイトが利用可能になるまで `b.fill()` が呼び出され、可能な限り多くのデータがバッファに読み込まれるようになります。

3.  **`n > len(b.buf)` の場合の新しい戻り値**:
    バッファを埋めるループが終了した後、`if n > len(b.buf)` の条件がチェックされます。この条件が真の場合、つまり要求された `n` バイトが内部バッファの最大容量を超えている場合、`b.buf[b.r:b.w]` と `ErrBufferFull` が返されます。
    *   `b.buf[b.r:b.w]` は、現在バッファ内に存在するすべてのデータを表します。`b.r` は読み取りポインタ、`b.w` は書き込みポインタです。
    この変更により、`ErrBufferFull` が発生しても、バッファ内の利用可能なデータが呼び出し元に提供されるようになりました。

`src/bufio/bufio_test.go` の変更点:

*   `TestPeek` 関数内のテストケースが更新され、`buf.Peek(32)` を呼び出した際の期待値が変更されました。以前は `ErrBufferFull` のみを確認していましたが、新しいテストでは、`"abcdefghijklmnop"` という部分的なデータが返されることと `ErrBufferFull` の両方を確認しています。これは、新しい `Peek` の挙動を正確に検証するための重要な変更です。

# [インデックス 21436] ファイルの概要
このコミットは、Goランタイムにおける`Gobuf`構造体の`g`フィールドの型をポインタから`uintptr`に変更するものです。これにより、特定の状況下で発生するライトバリアの問題を回避し、ガベージコレクションの挙動をより予測可能にすることを目的としています。特に、アセンブリコードとGoコードが混在する環境でのポインタ操作におけるライトバリアの適用に関する課題に対処しています。

## 元コミット内容
```
runtime: change Gobuf.g to uintptr, not pointer

The Gobuf.g goroutine pointer is almost always updated by assembly code.
In one of the few places it is updated by Go code - func save - it must be
treated as a uintptr to avoid a write barrier being emitted at a bad time.
Instead of figuring out how to emit the write barriers missing in the
assembly manipulation, change the type of the field to uintptr, so that
it does not require write barriers at all.

Goroutine structs are published in the allg list and never freed.
That will keep the goroutine structs from being collected.
There is never a time that Gobuf.g's contain the only references
to a goroutine: the publishing of the goroutine in allg comes first.
Goroutine pointers are also kept in non-GC-visible places like TLS,
so I can't see them ever moving. If we did want to start moving data
in the GC, we'd need to allocate the goroutine structs from an
alternate arena. This CL doesn't make that problem any worse.

Found with GODEBUG=wbshadow=1 mode.
Eventually that will run automatically, but right now
it still detects other missing write barriers.
```

## 変更の背景
このコミットの主な背景は、Goランタイムにおけるガベージコレクション（GC）のライトバリア（Write Barrier）の挙動と、`Gobuf`構造体の`g`フィールド（現在のゴルーチンへのポインタ）の更新方法に関する問題です。

Goのガベージコレクタは、並行マーク・スイープ方式を採用しており、プログラムの実行と並行してGCが動作します。この際、GCがオブジェクトグラフを正確に追跡し、誤って使用中のオブジェクトを回収しないようにするために「ライトバリア」という仕組みが導入されています。ライトバリアは、ポインタの書き込み時にGCに通知するコードの断片であり、GCがオブジェクトの参照関係の変化を検出するために使用されます。

`Gobuf.g`フィールドは、ゴルーチンの実行コンテキストを保存する`Gobuf`構造体の一部であり、現在のゴルーチン（`g`構造体へのポインタ）を指します。このフィールドは、アセンブリコードによって頻繁に更新されますが、`func save`のようなGoコードからも更新されることがあります。

問題は、`func save`のようなGoコードから`Gobuf.g`が更新される際に、ライトバリアが不適切なタイミングで発行される可能性があったことです。特に、アセンブリコードによる操作ではライトバリアが明示的に挿入されていない場合があり、Goコード側でライトバリアが発行されると、GCの整合性が損なわれるリスクがありました。コミットメッセージによると、`GODEBUG=wbshadow=1`というデバッグモードでこの問題が検出されました。このモードは、ライトバリアの欠落を検出するためのもので、Goランタイムの堅牢性を高めるための取り組みの一環として導入されました。

この問題を解決するために、ライトバリアの複雑な挿入ロジックを調整するのではなく、`Gobuf.g`の型をポインタ（`*g`）から`uintptr`（符号なし整数型）に変更するという根本的なアプローチが取られました。`uintptr`はポインタを整数として扱うため、GoのGCは`uintptr`型のフィールドをポインタとして認識せず、ライトバリアを適用しません。これにより、ライトバリアの不適切な発行を回避し、ランタイムの安定性を向上させることが目的でした。

また、ゴルーチン構造体自体は`allg`リストに登録され、決して解放されないため、`Gobuf.g`がゴルーチンへの唯一の参照となることはありません。さらに、TLS（Thread Local Storage）のようなGCから見えない場所にもゴルーチンへのポインタが保持されているため、`Gobuf.g`が`uintptr`になってもゴルーチンが誤ってGCされるリスクはないと判断されました。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア (Write Barrier)
Goのガベージコレクタは、並行マーク・スイープ方式を採用しています。これは、プログラムの実行と並行してGCが動作し、メモリの解放を行う方式です。GCは、到達可能なオブジェクト（プログラムから参照されているオブジェクト）を特定し、それ以外のオブジェクトを回収します。

ライトバリアは、GCが正しく動作するために重要なメカニズムです。プログラムがポインタを書き換える（あるオブジェクトから別のオブジェクトへの参照を変更する）際に、GCにその変更を通知するための小さなコードスニペットが挿入されます。これにより、GCはオブジェクトグラフの変更をリアルタイムで追跡し、マークフェーズ中にオブジェクトが誤って回収されることを防ぎます。

GoのGCでは、主に「ハイブリッドライトバリア」が使用されています。これは、GCのマークフェーズ中にポインタの書き込みが行われた場合、古いオブジェクトと新しいオブジェクトの両方をマークする（または、古いオブジェクトがマーク済みであることを確認する）ことで、GCの正確性を保証します。

### `Gobuf` 構造体
`Gobuf`はGoランタイム内部で使用される構造体で、ゴルーチンの実行コンテキスト（スタックポインタ、プログラムカウンタなど）を保存するために使われます。これは、ゴルーチンの切り替え（コンテキストスイッチ）の際に、現在のゴルーチンの状態を保存し、次に実行されるゴルーチンの状態を復元するために不可欠です。

`Gobuf`構造体には、以下の重要なフィールドが含まれています（コミット当時の定義に基づく）：
*   `sp`: スタックポインタ (Stack Pointer)
*   `pc`: プログラムカウンタ (Program Counter)
*   `g`: 現在のゴルーチン (`g`構造体へのポインタ)
*   `ctxt`: コンテキスト情報
*   `ret`: 戻り値
*   `lr`: リンクレジスタ (Link Register)

### ゴルーチン (`g` 構造体)
Goにおけるゴルーチンは、軽量な実行スレッドです。Goランタイムは、OSのスレッド上で多数のゴルーチンを多重化して実行します。各ゴルーチンは、`g`という内部構造体によって表現されます。この`g`構造体には、ゴルーチンのスタック情報、状態（実行中、待機中など）、スケジューラ関連の情報などが含まれています。

### `allg` リスト
`allg`は、Goランタイムが管理するすべてのゴルーチン（`g`構造体）へのポインタを保持するグローバルなリストです。新しいゴルーチンが作成されると、このリストに追加されます。このリストは、GCがすべてのゴルーチンを認識し、それらが参照しているメモリを回収しないようにするために使用されます。`allg`リストに登録されているゴルーチンは、GCによって「到達可能」と見なされるため、明示的に解放されることはありません。

### `unsafe.Pointer` と `uintptr`
Goの`unsafe`パッケージは、Goの型システムをバイパスしてメモリを直接操作するための機能を提供します。
*   `unsafe.Pointer`: 任意の型のポインタを保持できる汎用ポインタ型です。C言語の`void*`に似ています。`unsafe.Pointer`は、ポインタと`uintptr`の間、または異なる型のポインタ間で変換を行う際に使用されます。
*   `uintptr`: ポインタの値を保持できる符号なし整数型です。`uintptr`は、ポインタが指すアドレスを数値として表現するために使用されます。`uintptr`型の変数自体はポインタではないため、GoのGCは`uintptr`が指すメモリを追跡しません。これは、GCのライトバリアが適用されないことを意味します。

この特性が、今回のコミットの核心部分です。ポインタを`uintptr`として扱うことで、GCの追跡から外れ、ライトバリアの適用を回避できます。ただし、これは非常に危険な操作であり、GCが追跡できない参照を作成するため、誤った使用はメモリリークやクラッシュの原因となります。

### TLS (Thread Local Storage)
TLS（Thread Local Storage）は、各OSスレッドがそれぞれ独立したデータを保持するためのメカニズムです。Goランタイムは、OSスレッド上でゴルーチンをスケジューリングしますが、一部の重要な情報（例えば、現在実行中のゴルーチンへのポインタ）は、パフォーマンス上の理由からOSスレッドのTLSに保存されることがあります。TLSに保存されたポインタは、GoのGCからは直接見えないため、GCはそれらの参照を追跡しません。

## 技術的詳細
このコミットの技術的な核心は、Goランタイムがガベージコレクションのライトバリアをどのように管理し、特に`Gobuf`構造体の`g`フィールドの更新において発生する問題を解決したかにあります。

**問題の特定:**
Goのガベージコレクタは、ポインタの書き込み時にライトバリアを挿入することで、オブジェクトグラフの整合性を保ちます。しかし、`Gobuf.g`フィールドは、主にアセンブリコードによって更新されます。アセンブリコードは、Goコンパイラが自動的に挿入するライトバリアのロジックをバイパスすることがあります。

コミットメッセージによると、`func save`というGoコードの関数内で`_g_.sched.g`（現在のゴルーチン`_g_`のスケジューラ情報に含まれる`Gobuf`の`g`フィールド）が更新される際に問題が発生しました。この更新は、ゴルーチンのコンテキストを保存する重要な操作であり、このタイミングで不適切なライトバリアが発行されると、ランタイムの動作に悪影響を及ぼす可能性がありました。具体的には、GCがオブジェクトグラフをスキャンしている最中にポインタが書き換えられ、GCがその変更を認識できないと、誤って使用中のゴルーチン構造体が回収されてしまうリスクが生じます。

この問題は、`GODEBUG=wbshadow=1`というデバッグモード（ライトバリアの欠落を検出するためのモード）で発見されました。これは、将来的に自動的に実行されるようになる予定のテストの一部であり、Goランタイムの堅牢性を高めるための取り組みの一環でした。

**解決策:**
開発チームは、アセンブリコードにおけるライトバリアの欠落を修正する複雑な作業を避けるため、より根本的な解決策を選択しました。それは、`Gobuf.g`フィールドの型をポインタ（`*g`）から`uintptr`に変更することです。

1.  **`guintptr` 型の導入**: `src/runtime/runtime2.go`に`guintptr`という新しい型が導入されました。これは`uintptr`のエイリアスであり、ゴルーチンポインタをライトバリアをバイパスして保持するためのものです。この型には、`guintptr`から`*g`への変換を行う`ptr()`メソッドも追加されました。
    ```go
    type guintptr uintptr

    func (gp guintptr) ptr() *g {
        return (*g)(unsafe.Pointer(gp))
    }
    ```
2.  **`Gobuf.g` の型変更**: `src/runtime/runtime2.go`の`gobuf`構造体において、`g`フィールドの型が`*g`から`guintptr`に変更されました。
    ```go
    type gobuf struct {
        // ...
        g    guintptr // 変更前: g *g
        // ...
    }
    ```
3.  **ポインタ操作の変更**: `src/runtime/proc1.go`内の`newextram`, `save`, `newproc1`といった関数で、`Gobuf.g`にゴルーチンポインタを代入する際に、`unsafe.Pointer`を介して`uintptr`に変換し、`guintptr`型として代入するように変更されました。
    *   例 (`func save`):
        ```go
        // 変更前:
        // *(*uintptr)(unsafe.Pointer(&_g_.sched.g)) = uintptr(unsafe.Pointer(_g_))
        // 変更後:
        _g_.sched.g = guintptr(unsafe.Pointer(_g_))
        ```
        変更前は、`_g_.sched.g`のアドレスを`uintptr`ポインタとして取得し、そこに`_g_`のアドレスを`uintptr`として直接書き込むという、より低レベルな`unsafe`操作を行っていました。変更後は、`guintptr`型へのキャストを通じて、よりGoらしい構文で`uintptr`としての代入を行っています。これは、`guintptr`型が導入されたことによるコードのクリーンアップでもあります。

**なぜこれが機能するのか？**
`uintptr`はGoのGCによってポインタとして追跡されないため、`uintptr`型のフィールドへの書き込みにはライトバリアが適用されません。これにより、`Gobuf.g`が更新される際にライトバリアが不適切に発行される問題を根本的に回避できます。

**GCへの影響と安全性:**
コミットメッセージでは、この変更がGCの安全性に悪影響を与えない理由が説明されています。
*   **`allg`リストによる参照**: ゴルーチン構造体は、`allg`というグローバルなリストに登録されており、このリストはGCによって常にスキャンされます。したがって、`Gobuf.g`が`uintptr`になっても、ゴルーチン構造体自体がGCによって誤って回収されることはありません。`Gobuf.g`がゴルーチンへの唯一の参照となることは決してありません。
*   **TLSによる参照**: ゴルーチンへのポインタは、TLS（Thread Local Storage）のようなGCから見えない場所にも保持されています。これらの参照もゴルーチンが回収されないことを保証します。
*   **将来のGCの動き**: もし将来的にGoのGCがオブジェクトをメモリ内で移動させるような（コンパクションGCのような）機能を持つようになった場合、ゴルーチン構造体も移動する可能性があります。その場合、`Gobuf.g`が`uintptr`であると、移動後のアドレスを追跡できないという問題が発生する可能性があります。しかし、コミットメッセージでは、ゴルーチン構造体は`allg`リストに登録されており、TLSにも参照があるため、現時点では移動しないと述べられています。もし移動が必要になった場合、ゴルーチン構造体を別のメモリ領域（GCの対象外となるアリーナなど）から割り当てる必要があるだろうと示唆されており、このコミットはその問題を悪化させるものではないと結論付けられています。

要するに、この変更は、特定の低レベルなポインタ操作におけるライトバリアの問題を回避しつつ、ゴルーチン構造体のGC安全性は他のメカニズムによって保証されているため、全体としてランタイムの堅牢性を向上させるものです。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の変更
1.  **`guintptr` 型の定義とコメントの追加**:
    *   `type guintptr uintptr` という新しい型が定義されました。これは`uintptr`のエイリアスであり、ゴルーチンポインタをライトバリアをバイパスして保持するために特別に導入されました。
    *   この型の定義には、詳細なコメントが追加されています。このコメントは、`guintptr`が導入された理由（ライトバリアの回避）、`Gobuf.g`がアセンブリコードで更新されることが多いこと、`func save`での問題、そしてゴルーチン構造体が`allg`リストやTLSによって常に参照されているためGCの対象にならないことなど、この変更の背景と安全性を説明しています。
2.  **`guintptr` 型の `ptr()` メソッド**:
    *   `func (gp guintptr) ptr() *g { return (*g)(unsafe.Pointer(gp)) }` というメソッドが追加されました。これは、`guintptr`型の値を元の`*g`（ゴルーチンポインタ）に安全に変換するためのヘルパー関数です。これにより、`uintptr`として保持されているゴルーチンポインタを、必要に応じて通常のポインタとして利用できるようになります。
3.  **`gobuf` 構造体の `g` フィールドの型変更**:
    *   `type gobuf struct { ... g *g ... }` が `type gobuf struct { ... g guintptr ... }` に変更されました。
    *   これにより、`gobuf`構造体内のゴルーチンポインタが、GCのライトバリアの対象とならない`uintptr`として扱われるようになります。

### `src/runtime/proc1.go` の変更
このファイルでは、`gobuf`構造体の`g`フィールドにゴルーチンポインタを代入する箇所が修正されています。具体的には、`*g`型の値を`unsafe.Pointer`を介して`uintptr`に変換し、それを新しく定義された`guintptr`型にキャストして代入する形式に変更されました。

1.  **`func newextram()`**:
    *   `gp.sched.g = gp` から `gp.sched.g = guintptr(unsafe.Pointer(gp))` に変更。
    *   `newextram`は、新しいM（OSスレッド）が作成される際に、そのMに紐付けられる初期ゴルーチン（`g0`または`m0`のゴルーチン）を設定する関数です。ここで`gp`（ゴルーチンポインタ）を`guintptr`に変換して`sched.g`に代入しています。
2.  **`func save(pc, sp uintptr)`**:
    *   `*(*uintptr)(unsafe.Pointer(&_g_.sched.g)) = uintptr(unsafe.Pointer(_g_))` から `_g_.sched.g = guintptr(unsafe.Pointer(_g_))` に変更。
    *   `save`関数は、現在のゴルーチンの実行コンテキスト（スタックポインタ、プログラムカウンタなど）を`_g_.sched`（現在のゴルーチンの`gobuf`）に保存する重要な関数です。この関数内で`_g_.sched.g`に現在のゴルーチン`_g_`を代入する際に、`guintptr`を使用するように変更されました。変更前のコードは、`_g_.sched.g`のアドレスを`uintptr`ポインタとして取得し、そこに`_g_`のアドレスを`uintptr`として直接書き込むという、より低レベルな`unsafe`操作でした。`guintptr`の導入により、より意図が明確なコードになりました。
3.  **`func newproc1(...)`**:
    *   `newg.sched.g = newg` から `newg.sched.g = guintptr(unsafe.Pointer(newg))` に変更。
    *   `newproc1`は、新しいゴルーチンを作成する内部関数です。ここで新しく作成されたゴルーチン`newg`をその`sched.g`フィールドに代入する際にも、同様に`guintptr`を使用するように変更されました。

これらの変更により、Goランタイムは`Gobuf.g`フィールドを`uintptr`として扱い、ライトバリアの適用を回避しつつ、ゴルーチンへの参照を正しく保持できるようになりました。これは、GoのGCの正確性とランタイムの安定性を向上させるための重要な改善です。

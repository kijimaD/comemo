# [インデックス 22699] ファイルの概要

このコミットは、Goランタイムが共有ライブラリ（.so, .dll, .dylibなど）としてロードされる際の初期化メカニズムを改善するものです。特に、Goプログラムではない外部のC/C++プログラムなどからGo製の共有ライブラリが利用される際に、Goランタイムの初期化が適切に行われるようにするための重要な変更です。これにより、Goの共有ライブラリがより堅牢に、かつ予測可能な形で動作するようになります。

Suggested by iant@, we use the library initialization entry point to:
    - create a new OS thread and run the "regular" runtime init stack on

## 変更の背景

Go言語は、その設計上、独自のランタイム（ガベージコレクタ、スケジューラ、goroutineなど）を持っており、プログラムの起動時にこのランタイムが初期化されることを前提としています。しかし、Goのコードを共有ライブラリ（例: `libmylib.so`）としてコンパイルし、それをC/C++などの他の言語で書かれたアプリケーションからロードして利用する場合、問題が発生する可能性がありました。

通常のGoアプリケーションでは、`main`関数が実行される前にGoランタイムが完全に初期化されます。しかし、共有ライブラリとしてロードされる場合、ライブラリをロードした側のプロセス（ローダー）のメインスレッドがGoランタイムの初期化を待つと、そのローダーがブロックされてしまい、デッドロックやパフォーマンスの問題を引き起こす可能性がありました。特に、Goランタイムの初期化は複雑で時間がかかる処理であり、メインスレッドを長時間ブロックすることは望ましくありません。

このコミットは、この問題を解決するために導入されました。Goの共有ライブラリがロードされた際に、ローダーのメインスレッドをブロックすることなく、Goランタイムの初期化をバックグラウンドで非同期に実行するメカニズムを導入しています。そして、Goの機能（特にCGOを介したGo関数の呼び出し）が実際に必要とされるまで、その初期化の完了を待機するように変更されました。これにより、Goの共有ライブラリが外部アプリケーションからよりスムーズに、かつ安全に利用できるようになります。

この変更は、Goを共有ライブラリとして利用する際の重要なステップであり、Goの相互運用性を高めるための基盤となります。コミットメッセージにある「Part 2」という記述は、この機能が段階的に導入されていることを示しており、Goランタイムの共有ライブラリ対応に向けた継続的な取り組みの一環です。

## 前提知識の解説

このコミットの理解には、以下の概念が不可欠です。

1.  **Goランタイム (Go Runtime)**:
    Go言語のプログラムは、C/C++のようにOSが提供する標準ライブラリのみに依存するのではなく、独自のランタイムシステムを持っています。このランタイムは、ガベージコレクション、goroutineスケジューリング、メモリ管理、チャネル通信など、Go言語の並行処理モデルとメモリ安全性を実現するための核となる部分です。Goプログラムが起動すると、まずこのランタイムが初期化され、その後にユーザーが記述した`main`関数が実行されます。

2.  **共有ライブラリ (Shared Library)**:
    共有ライブラリは、複数のプログラムから共有して利用できるコードの集合体です。Linuxでは`.so` (shared object)、Windowsでは`.dll` (Dynamic Link Library)、macOSでは`.dylib`という拡張子を持ちます。プログラムは実行時にこれらのライブラリをロードし、その中に定義された関数を呼び出すことができます。これにより、コードの再利用性が高まり、実行ファイルのサイズを削減できます。

3.  **CGO**:
    CGOは、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGo言語の関数を呼び出したりするためのGoの機能です。GoとCの間の相互運用を可能にし、既存のCライブラリを利用したり、Goの機能をC/C++アプリケーションに組み込んだりする際に使用されます。CGOを使用すると、GoのコードはCのABI (Application Binary Interface) に従ってコンパイルされ、Cの関数ポインタを介して呼び出しが可能になります。

4.  **ライブラリロード時の初期化**:
    共有ライブラリには、ロードされた際に自動的に実行される初期化ルーチンを持つことができます。これは、ライブラリが提供する機能を利用する前に、必要なセットアップ（例: グローバル変数の初期化、リソースの確保）を行うために使用されます。Linuxでは`_init`セクションやGCCの`__attribute__((constructor))`などがこれに該当します。

5.  **OSスレッドの作成 (`pthread_create`, `clone`)**:
    Goランタイムは、OSが提供するスレッド（カーネルスレッド）の上に独自のgoroutineスケジューラを構築しています。新しいOSスレッドを作成するには、POSIXスレッドライブラリの`pthread_create`関数（Linux, macOSなど）や、Linuxカーネルの`clone`システムコールが使用されます。これらの関数は、新しいスレッドの実行を開始し、そのスレッドが独立した実行フローを持つことを可能にします。

6.  **スレッド同期プリミティブ (`pthread_mutex_t`, `pthread_cond_t`)**:
    複数のスレッドが共有データにアクセスする際に、データの整合性を保つためにスレッド同期メカニズムが必要です。
    *   `pthread_mutex_t` (ミューテックス): 共有リソースへのアクセスを排他的に制御するためのロックメカニズムです。一度に1つのスレッドのみがミューテックスをロックでき、他のスレッドはロックが解放されるまで待機します。
    *   `pthread_cond_t` (条件変数): 特定の条件が満たされるまでスレッドを待機させ、条件が満たされた際にスレッドを再開させるためのメカニズムです。ミューテックスと組み合わせて使用され、複雑なスレッド間通信を実現します。

これらの概念を理解することで、Goランタイムが共有ライブラリとしてどのように初期化され、CGO呼び出しがどのように同期されるのか、そしてそれがなぜ重要なのかを深く把握することができます。

## 技術的詳細

このコミットは、Goランタイムを共有ライブラリとして利用する際の初期化プロセスを根本的に変更します。主な技術的変更点は以下の通りです。

1.  **非同期ランタイム初期化**:
    Goの共有ライブラリがロードされると、ローダーのメインスレッドはGoランタイムの初期化を直接実行するのではなく、新しいOSスレッドを生成し、そのスレッド上でGoランタイムの通常の初期化スタック（`runtime.main`関数など）を実行します。これにより、ローダーのメインスレッドはすぐに制御を返し、ブロックされることがなくなります。

2.  **CGO呼び出し時の初期化待機**:
    Goランタイムの初期化がバックグラウンドで行われている間、Goの共有ライブラリ内の関数がCGOを介して外部から呼び出される可能性があります。このコミットでは、最初のCGO呼び出し時に、Goランタイムの初期化が完了するまで待機するメカニズムが導入されました。これは、`_cgo_wait_runtime_init_done`という新しいC関数によって実現されます。この関数は、ランタイム初期化が完了したことを示すフラグがセットされるまで、条件変数（`pthread_cond_t`）とミューテックス（`pthread_mutex_t`）を使用してスレッドをブロックします。

3.  **ランタイム初期化完了の通知**:
    Goランタイムの初期化が完了すると、`_cgo_notify_runtime_init_done`という新しいC関数が呼び出されます。この関数は、初期化完了フラグをセットし、条件変数を使って待機しているすべてのスレッド（つまり、CGO呼び出しでブロックされているスレッド）に通知を送ります。これにより、CGO呼び出しが再開され、Goの機能が利用可能になります。

4.  **OSスレッド作成の抽象化**:
    Goランタイムが新しいOSスレッドを作成する際に、Goの内部状態を更新せずにスレッドを作成するための新しいC関数`_cgo_sys_thread_create`が導入されました。これは、`pthread_create`をラップしたもので、Goランタイムの初期化スレッドを生成するために使用されます。これにより、Goランタイムの初期化がGoのスケジューラとは独立して行われることが保証されます。

5.  **共有ライブラリのエントリポイント (`_rt0_amd64_linux_lib`)**:
    Linux/AMD64の場合、Goの共有ライブラリがロードされると、`_rt0_amd64_linux_lib`というアセンブリコードのエントリポイントが実行されます。このエントリポイントは、`_cgo_sys_thread_create`を呼び出して新しいOSスレッドを生成し、そのスレッド上でGoランタイムの初期化ルーチン（`_rt0_amd64_linux_lib_go`、最終的には`runtime.rt0_go`）を実行させます。そして、`_rt0_amd64_linux_lib`自身はすぐに`RET`（リターン）し、ローダーのメインスレッドに制御を戻します。

6.  **`islibrary` フラグ**:
    `runtime/runtime2.go`に`islibrary`という新しいグローバル変数が追加されました。これはリンカによって設定され、現在のGoバイナリが共有ライブラリとしてリンクされているかどうかを示します。このフラグは、`runtime.main`関数内で、共有ライブラリの場合に追加のM（OSスレッド）を割り当てる必要があるかどうかを判断するために使用されます。これは、`main_main()`が永遠にブロックされることが期待されるため、共有ライブラリとして動作する場合にGoランタイムが適切に機能するための追加のOSスレッドが必要となるためです。

7.  **`newosproc0` 関数**:
    `runtime/os1_linux.go`に`newosproc0`という新しい関数が追加されました。これは、Goの構造体を割り当てる必要なく新しいOSプロセス（スレッド）を作成するためのものです。Goランタイムの初期化中に、Goのメモリ管理システムがまだ完全に機能していない可能性があるため、Goの構造体に依存しないスレッド作成メカニズムが必要となります。この関数は、`clone0`という新しいアセンブリ関数（Linuxの`clone`システムコールをラップしたもの）を呼び出して、指定されたスタックサイズと関数ポインタで新しいスレッドを起動します。

これらの変更により、Goの共有ライブラリは、外部アプリケーションからロードされた際に、非同期かつ安全にGoランタイムを初期化し、必要に応じてその完了を待機する、より洗練されたメカニズムを持つことになります。

## コアとなるコードの解説

このコミットの核となる変更は、Goランタイムが共有ライブラリとしてロードされた際の初期化フローを非同期化し、CGO呼び出し時にその完了を同期する点にあります。

1.  **`src/runtime/rt0_linux_amd64.s` における共有ライブラリのエントリポイント**:
    Goの共有ライブラリがロードされると、`_rt0_amd64_linux_lib`というアセンブリ関数が実行されます。この関数は、Goランタイムの初期化をメインスレッドで直接行うのではなく、新しいOSスレッドを生成してそのスレッドに初期化を委譲します。
    ```assembly
    TEXT _rt0_amd64_linux_lib(SB),NOSPLIT,$40
        MOVQ    DI, _rt0_amd64_linux_lib_argc<>(SB)
        MOVQ    SI, _rt0_amd64_linux_lib_argv<>(SB)

        // Create a new thread to do the runtime initialization and return.
        MOVQ    _cgo_sys_thread_create(SB), AX
        TESTQ   AX, AX
        JZ      nocgo
        MOVQ    $_rt0_amd64_linux_lib_go(SB), DI
        MOVQ    $0, SI
        CALL    AX
        RET
    nocgo:
        // ... (fallback for non-cgo case, using runtime·newosproc0)
        RET
    ```
    ここで、`_cgo_sys_thread_create`（CGOが有効な場合）または`runtime·newosproc0`（CGOが無効な場合）を呼び出して、`_rt0_amd64_linux_lib_go`関数を新しいスレッドで実行させます。`_rt0_amd64_linux_lib`自身はすぐに`RET`（リターン）し、ライブラリをロードした側のプロセス（ローダー）のメインスレッドに制御を戻します。これにより、ローダーはブロックされません。

2.  **`src/runtime/cgo/gcc_libinit.c` における同期メカニズム**:
    新しいOSスレッドでGoランタイムの初期化が開始されると、その初期化が完了するまで、CGOを介したGo関数への呼び出しはブロックされる必要があります。この同期は、`_cgo_wait_runtime_init_done`と`x_cgo_notify_runtime_init_done`によって実現されます。
    ```c
    // src/runtime/cgo/gcc_libinit.c
    static pthread_cond_t runtime_init_cond;
    static pthread_mutex_t runtime_init_mu;
    static int runtime_init_done; // 0: not done, 1: done

    void
    _cgo_wait_runtime_init_done() {
        pthread_mutex_lock(&runtime_init_mu);
        while (runtime_init_done == 0) {
            pthread_cond_wait(&runtime_init_cond, &runtime_init_mu);
        }
        pthread_mutex_unlock(&runtime_init_mu);
    }

    void
    x_cgo_notify_runtime_init_done(void* dummy) {
        pthread_mutex_lock(&runtime_init_mu);
        runtime_init_done = 1; // Set flag to indicate initialization is complete
        pthread_cond_broadcast(&runtime_init_cond); // Notify waiting threads
        pthread_mutex_unlock(&runtime_init_mu);
    }
    ```
    `_cgo_wait_runtime_init_done`は、`runtime_init_done`フラグが`1`になるまでミューテックスと条件変数を使ってスレッドを待機させます。Goランタイムの初期化が完了すると、`src/runtime/proc.go`の`main`関数から`cgocall(_cgo_notify_runtime_init_done, nil)`が呼び出され、`x_cgo_notify_runtime_init_done`が実行されます。これにより`runtime_init_done`が`1`に設定され、条件変数がブロードキャストされ、待機していたCGO呼び出しが再開されます。

3.  **`src/cmd/cgo/out.go` と `src/cmd/cgo/doc.go` におけるCGOの変更**:
    CGOが生成するCコードに、Go関数を呼び出す前に`_cgo_wait_runtime_init_done()`を呼び出すコードが挿入されるようになりました。
    ```diff
    --- a/src/cmd/cgo/out.go
    +++ b/src/cmd/cgo/out.go
    @@ -739,6 +742,7 @@ func (p *Package) writeExports(fgo2, fm io.Writer) {
     		fmt.Fprintf(fgcc, "extern void _cgoexp%s_%s(void *, int);\\n", cPrefix, exp.ExpName)
     		fmt.Fprintf(fgcc, "\\n%s\\n", s)
     		fmt.Fprintf(fgcc, "{\\n")
    +		fmt.Fprintf(fgcc, "\\t_cgo_wait_runtime_init_done();\\n") // <-- Added here
     		fmt.Fprintf(fgcc, "\\t%s %v a;\\n", ctype, p.packedAttribute())
     		if gccResult != "void" && (len(fntype.Results.List) > 1 || len(fntype.Results.List[0].Names) > 1) {
     			fmt.Fprintf(fgcc, "\\t%s r;\\n", gccResult)
    ```
    これにより、Goの共有ライブラリ内のエクスポートされた関数がCGOを介して呼び出されるたびに、ランタイム初期化の完了が保証されるようになります。

これらの変更により、Goの共有ライブラリは、外部アプリケーションからロードされた際に、ローダーのメインスレッドをブロックすることなくGoランタイムを非同期に初期化し、Goの機能が実際に利用されるまでその完了を待機するという、堅牢な初期化フローを実現しています。

## 変更の背景

Go言語は、その設計上、独自のランタイム（ガベージコレクタ、スケジューラ、goroutineなど）を持っており、プログラムの起動時にこのランタイムが初期化されることを前提としています。しかし、Goのコードを共有ライブラリ（例: `libmylib.so`）としてコンパイルし、それをC/C++などの他の言語で書かれたアプリケーションからロードして利用する場合、問題が発生する可能性がありました。

通常のGoアプリケーションでは、`main`関数が実行される前にGoランタイムが完全に初期化されます。しかし、共有ライブラリとしてロードされる場合、ライブラリをロードした側のプロセス（ローダー）のメインスレッドがGoランタイムの初期化を待つと、そのローダーがブロックされてしまい、デッドロックやパフォーマンスの問題を引き起こす可能性がありました。特に、Goランタイムの初期化は複雑で時間がかかる処理であり、メインスレッドを長時間ブロックすることは望ましくありません。

このコミットは、この問題を解決するために導入されました。Goの共有ライブラリがロードされた際に、ローダーのメインスレッドをブロックすることなく、Goランタイムの初期化をバックグラウンドで非同期に実行するメカニズムを導入しています。そして、Goの機能（特にCGOを介したGo関数の呼び出し）が実際に必要とされるまで、その初期化の完了を待機するように変更されました。これにより、Goの共有ライブラリが外部アプリケーションからよりスムーズに、かつ安全に利用できるようになります。

この変更は、Goを共有ライブラリとして利用する際の重要なステップであり、Goの相互運用性を高めるための基盤となります。コミットメッセージにある「Part 2」という記述は、この機能が段階的に導入されていることを示しており、Goランタイムの共有ライブラリ対応に向けた継続的な取り組みの一環です。

## 前提知識の解説

このコミットの理解には、以下の概念が不可欠です。

1.  **Goランタイム (Go Runtime)**:
    Go言語のプログラムは、C/C++のようにOSが提供する標準ライブラリのみに依存するのではなく、独自のランタイムシステムを持っています。このランタイムは、ガベージコレクション、goroutineスケジューリング、メモリ管理、チャネル通信など、Go言語の並行処理モデルとメモリ安全性を実現するための核となる部分です。Goプログラムが起動すると、まずこのランタイムが初期化され、その後にユーザーが記述した`main`関数が実行されます。

2.  **共有ライブラリ (Shared Library)**:
    共有ライブラリは、複数のプログラムから共有して利用できるコードの集合体です。Linuxでは`.so` (shared object)、Windowsでは`.dll` (Dynamic Link Library)、macOSでは`.dylib`という拡張子を持ちます。プログラムは実行時にこれらのライブラリをロードし、その中に定義された関数を呼び出すことができます。これにより、コードの再利用性が高まり、実行ファイルのサイズを削減できます。

3.  **CGO**:
    CGOは、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGo言語の関数を呼び出したりするためのGoの機能です。GoとCの間の相互運用を可能にし、既存のCライブラリを利用したり、Goの機能をC/C++アプリケーションに組み込んだりする際に使用されます。CGOを使用すると、GoのコードはCのABI (Application Binary Interface) に従ってコンパイルされ、Cの関数ポインタを介して呼び出しが可能になります。

4.  **ライブラリロード時の初期化**:
    共有ライブラリには、ロードされた際に自動的に実行される初期化ルーチンを持つことができます。これは、ライブラリが提供する機能を利用する前に、必要なセットアップ（例: グローバル変数の初期化、リソースの確保）を行うために使用されます。Linuxでは`_init`セクションやGCCの`__attribute__((constructor))`などがこれに該当します。

5.  **OSスレッドの作成 (`pthread_create`, `clone`)**:
    Goランタイムは、OSが提供するスレッド（カーネルスレッド）の上に独自のgoroutineスケジューラを構築しています。新しいOSスレッドを作成するには、POSIXスレッドライブラリの`pthread_create`関数（Linux, macOSなど）や、Linuxカーネルの`clone`システムコールが使用されます。これらの関数は、新しいスレッドの実行を開始し、そのスレッドが独立した実行フローを持つことを可能にします。

6.  **スレッド同期プリミティブ (`pthread_mutex_t`, `pthread_cond_t`)**:
    複数のスレッドが共有データにアクセスする際に、データの整合性を保つためにスレッド同期メカニズムが必要です。
    *   `pthread_mutex_t` (ミューテックス): 共有リソースへのアクセスを排他的に制御するためのロックメカニズムです。一度に1つのスレッドのみがミューテックスをロックでき、他のスレッドはロックが解放されるまで待機します。
    *   `pthread_cond_t` (条件変数): 特定の条件が満たされるまでスレッドを待機させ、条件が満たされた際にスレッドを再開させるためのメカニズムです。ミューテックスと組み合わせて使用され、複雑なスレッド間通信を実現します。

これらの概念を理解することで、Goランタイムが共有ライブラリとしてどのように初期化され、CGO呼び出しがどのように同期されるのか、そしてそれがなぜ重要なのかを深く把握することができます。

## 技術的詳細

このコミットは、Goランタイムを共有ライブラリとして利用する際の初期化プロセスを根本的に変更します。主な技術的変更点は以下の通りです。

1.  **非同期ランタイム初期化**:
    Goの共有ライブラリがロードされると、ローダーのメインスレッドはGoランタイムの初期化を直接実行するのではなく、新しいOSスレッドを生成し、そのスレッド上でGoランタイムの通常の初期化スタック（`runtime.main`関数など）を実行します。これにより、ローダーのメインスレッドはすぐに制御を返し、ブロックされることがなくなります。

2.  **CGO呼び出し時の初期化待機**:
    Goランタイムの初期化がバックグラウンドで行われている間、Goの共有ライブラリ内の関数がCGOを介して外部から呼び出される可能性があります。このコミットでは、最初のCGO呼び出し時に、Goランタイムの初期化が完了するまで待機するメカニズムが導入されました。これは、`_cgo_wait_runtime_init_done`という新しいC関数によって実現されます。この関数は、ランタイム初期化が完了したことを示すフラグがセットされるまで、条件変数（`pthread_cond_t`）とミューテックス（`pthread_mutex_t`）を使用してスレッドをブロックします。

3.  **ランタイム初期化完了の通知**:
    Goランタイムの初期化が完了すると、`_cgo_notify_runtime_init_done`という新しいC関数が呼び出されます。この関数は、初期化完了フラグをセットし、条件変数を使って待機しているすべてのスレッド（つまり、CGO呼び出しでブロックされているスレッド）に通知を送ります。これにより、CGO呼び出しが再開され、Goの機能が利用可能になります。

4.  **OSスレッド作成の抽象化**:
    Goランタイムが新しいOSスレッドを作成する際に、Goの内部状態を更新せずにスレッドを作成するための新しいC関数`_cgo_sys_thread_create`が導入されました。これは、`pthread_create`をラップしたもので、Goランタイムの初期化スレッドを生成するために使用されます。これにより、Goランタイムの初期化がGoのスケジューラとは独立して行われることが保証されます。

5.  **共有ライブラリのエントリポイント (`_rt0_amd64_linux_lib`)**:
    Linux/AMD64の場合、Goの共有ライブラリがロードされると、`_rt0_amd64_linux_lib`というアセンブリコードのエントリポイントが実行されます。このエントリポイントは、`_cgo_sys_thread_create`を呼び出して新しいOSスレッドを生成し、そのスレッド上でGoランタイムの初期化ルーチン（`_rt0_amd64_linux_lib_go`、最終的には`runtime.rt0_go`）を実行させます。そして、`_rt0_amd64_linux_lib`自身はすぐに`RET`（リターン）し、ローダーのメインスレッドに制御を戻します。

6.  **`islibrary` フラグ**:
    `runtime/runtime2.go`に`islibrary`という新しいグローバル変数が追加されました。これはリンカによって設定され、現在のGoバイナリが共有ライブラリとしてリンクされているかどうかを示します。このフラグは、`runtime.main`関数内で、共有ライブラリの場合に追加のM（OSスレッド）を割り当てる必要があるかどうかを判断するために使用されます。これは、`main_main()`が永遠にブロックされることが期待されるため、共有ライブラリとして動作する場合にGoランタイムが適切に機能するための追加のOSスレッドが必要となるためです。

7.  **`newosproc0` 関数**:
    `runtime/os1_linux.go`に`newosproc0`という新しい関数が追加されました。これは、Goの構造体を割り当てる必要なく新しいOSプロセス（スレッド）を作成するためのものです。Goランタイムの初期化中に、Goのメモリ管理システムがまだ完全に機能していない可能性があるため、Goの構造体に依存しないスレッド作成メカニズムが必要となります。この関数は、`clone0`という新しいアセンブリ関数（Linuxの`clone`システムコールをラップしたもの）を呼び出して、指定されたスタックサイズと関数ポインタで新しいスレッドを起動します。

これらの変更により、Goの共有ライブラリは、外部アプリケーションからロードされた際に、非同期かつ安全にGoランタイムを初期化し、必要に応じてその完了を待機する、より洗練されたメカニズムを持つことになります。

これらの変更により、Goの共有ライブラリは、外部アプリケーションからロードされた際に、ローダーのメインスレッドをブロックすることなくGoランタイムを非同期に初期化し、Goの機能が実際に利用されるまでその完了を待機するという、堅牢な初期化フローを実現しています。

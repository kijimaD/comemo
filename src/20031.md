# [インデックス 20031] ファイルの概要

このコミットは、GoランタイムがPowerPC 64-bit (power64) アーキテクチャをサポートするために、Linux固有の定義ファイル群に `defs3_linux.go` を追加するものです。これにより、`power64` 環境における `ucontext` やシグナルハンドリングに関連する低レベルなC構造体や定数の定義が適切に生成されるようになります。

## 変更の背景

このコミットの背景には、Go言語がPowerPC 64-bit (power64) アーキテクチャへの対応を進めるという開発目標があります。Goランタイムは、オペレーティングシステム（この場合はLinux）と低レベルで連携するために、C言語で定義されたシステムコールやデータ構造の情報を必要とします。これらの定義は、アーキテクチャによって異なる場合があります。

特に、`ucontext`（ユーザーコンテキスト）やシグナルハンドリングに関連する構造体は、CPUのレジスタセットやメモリレイアウトに密接に関連しており、アーキテクチャごとにその定義が大きく異なることが一般的です。既存の `defs1_linux.go` や `defs_linux.go` は一般的なLinux環境の定義を扱っていましたが、`power64` のような特定のアーキテクチャでは、これらの汎用的な定義だけでは不十分でした。

このコミットは、`power64` アーキテクチャに特化した定義を `defs3_linux.go` という新しいファイルに集約し、`cgo -cdefs` ツールを使って `defs_linux_power64.h` および `defs_linux_power64le.h` (little-endian) といったアーキテクチャ固有のヘッダーファイルを生成できるようにすることで、Goランタイムが `power64` 環境で正しく動作するための基盤を確立することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Go Runtime (Goランタイム)**: Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション、ゴルーチンのスケジューリング、システムコールとの連携、メモリ管理などが含まれます。ランタイムはOSの機能に直接アクセスする必要があるため、OSやアーキテクチャ固有の定義を必要とします。

*   **cgo**: Go言語とC言語の相互運用を可能にするGoのツールです。GoプログラムからC関数を呼び出したり、CコードからGo関数を呼び出したりできます。このコミットでは、`cgo -cdefs` というモードが重要です。
    *   **`cgo -cdefs`**: このコマンドは、Goのソースファイル内に埋め込まれたC言語の定義（`import "C"` ブロック内）を解析し、GoランタイムがCの構造体や定数にアクセスするために必要なGoの型定義や定数定義を含むCヘッダーファイルを生成します。これにより、GoコードがCのABI（Application Binary Interface）に準拠した形でシステムコールなどを実行できるようになります。

*   **`defs_linux.go`, `defs1_linux.go`, `defs3_linux.go`**: これらはGoランタイムのソースコード内に存在するファイルで、Linuxシステムコールやカーネルデータ構造に関するC言語の定義をGoから利用できるようにするためのものです。これらのファイルは `cgo -cdefs` によって処理され、Goランタイムが利用するCヘッダーファイル（例: `defs_linux.h`）が生成されます。アーキテクチャや特定の機能に応じて、複数の `defs*.go` ファイルに分割されることがあります。

*   **PowerPC 64-bit (power64)**: IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、64ビットのプロセッサです。サーバーや組み込みシステムなどで利用されます。x86やARMといった他の一般的なアーキテクチャとは、レジスタの構成、システムコールの呼び出し規約、メモリの扱い方などが異なるため、低レベルなプログラミングではアーキテクチャ固有の対応が必要になります。

*   **`ucontext.h`**: POSIX標準で定義されているヘッダーファイルで、ユーザーコンテキスト（`ucontext_t`）構造体を提供します。この構造体は、プログラムの実行状態（CPUレジスタ、シグナルマスク、スタック情報など）を保存・復元するために使用されます。シグナルハンドリングやコルーチン（Goのゴルーチンも含む）の実装において非常に重要です。アーキテクチャによって `ucontext_t` の内部構造は大きく異なります。

*   **`fcntl.h`**: ファイル制御に関する定数や関数（例: `open`, `fcntl`）を定義するヘッダーファイルです。`O_RDONLY`（読み取り専用でファイルを開く）、`O_CLOEXEC`（`exec` 時にファイルディスクリプタをクローズする）などの定数が含まれます。

*   **`asm/signal.h`, `asm/ucontext.h`, `asm-generic/fcntl.h`**: これらはLinuxカーネルのヘッダーファイルで、特定のアーキテクチャ（`asm/` ディレクトリ以下）または汎用的な（`asm-generic/` ディレクトリ以下）なシステムコールやデータ構造の定義を提供します。これらはユーザー空間のアプリケーションがカーネルとやり取りする際のインターフェースを定義します。

*   **`SA_RESTORER`**: シグナルハンドリングにおいて `sigaction` システムコールに渡されるフラグの一つです。このフラグは、シグナルハンドラから戻る際に、カーネルがユーザー空間のスタックとレジスタの状態をどのように復元するかを制御するために使用されます。特に、`ucontext_t` 構造体を利用してコンテキストを復元する際に重要となることがあります。その挙動や必要性はアーキテクチャやカーネルのバージョンによって異なります。

*   **`__kernel_size_t`, `__sigset_t`**: これらはLinuxカーネル内部で使われる型定義で、ユーザー空間の標準ライブラリで定義されている `size_t` や `sigset_t` との衝突を避けるために、プレフィックス `__kernel_` や `__` が付けられることがあります。`cgo` でCのヘッダーを扱う際に、このような型名の衝突を避けるための工夫が必要になることがあります。

*   **`_SYS_TYPES_H`**: 多くのC言語のシステムヘッダーファイルで使われるマクロで、`sys/types.h` が複数回インクルードされることによる再定義エラーを防ぐためのインクルードガードとして機能します。

*   **`struct_pt_regs`, `elf_gregset_t`, `elf_fpregset_t`, `elf_vrreg_t`, `struct_sigaltstack`, `struct_sigcontext`, `struct_ucontext`**: これらは、CPUのレジスタセット（汎用レジスタ、浮動小数点レジスタ、ベクトルレジスタなど）、シグナル代替スタック、シグナルコンテキスト、ユーザーコンテキストといった、低レベルな実行状態を表現するためのC言語の構造体です。これらはシグナルハンドリング、デバッグ、コンテキストスイッチなどの操作で不可欠であり、その定義は各CPUアーキテクチャに固有です。特にPowerPCでは、`ucontext` の内部で `sigcontext` が使われるなど、他のアーキテクチャとは異なる構造を持つことがあります。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがPowerPC 64-bit (power64) アーキテクチャのLinux環境で、OSの低レベルなインターフェースと正確に連携できるようにするための定義を整備することにあります。

1.  **`defs3_linux.go` の導入**:
    *   Goランタイムは、`cgo -cdefs` を使用して、GoコードからC言語の構造体や定数にアクセスするためのGoの型定義やCヘッダーファイルを生成します。
    *   `power64` アーキテクチャは、特に `ucontext` やシグナルハンドリングに関連する構造体（`struct_pt_regs`, `elf_gregset_t`, `struct_sigcontext` など）において、他のアーキテクチャ（x86など）とは異なる定義を持っています。
    *   このため、既存の汎用的な `defs_linux.go` や `defs1_linux.go` だけでは `power64` の要件を満たせません。
    *   `defs3_linux.go` は、`power64` に特化したこれらの構造体定義をカプセル化するために導入されました。このファイルは、`+build ignore` ディレクティブによって通常のGoビルドプロセスからは除外され、`cgo -cdefs` によってのみ処理されることを意図しています。
    *   コメント `GOARCH=power64 cgo -cdefs defs_linux.go defs3_linux.go > defs_linux_power64.h` が示すように、`power64` 用のヘッダーファイル `defs_linux_power64.h` は、`defs_linux.go` と `defs3_linux.go` の両方から定義を結合して生成されます。

2.  **`SA_RESTORER` の扱い**:
    *   `SA_RESTORER` はシグナルハンドリングに関連する重要なフラグです。このコミットでは、`defs1_linux.go` に `SA_RESTORER` が追加され、`defs_linux.go` からは削除されています。
    *   さらに、`defs3_linux.go` では `SA_RESTORER = 0 // unused` と明示的に定義されています。これは、`power64` 環境では `SA_RESTORER` フラグが他のアーキテクチャとは異なる意味を持つか、あるいはGoランタイムのコンテキストでは使用されないことを示唆しています。このようなアーキテクチャ固有の差異を吸収するために、定義を分離し、それぞれのファイルで適切な値を設定しています。

3.  **型名の衝突回避とヘッダーのインクルード制御**:
    *   `defs3_linux.go` では、`#define size_t __kernel_size_t` や `#define sigset_t __sigset_t` といったCプリプロセッサディレクティブが使用されています。これは、`cgo` がCヘッダーを処理する際に、標準ライブラリの型定義とカーネルの型定義との間で発生しうる「inconsistent definitions (一貫性のない定義)」エラーを回避するためのものです。カーネル内部の型名にリネームすることで、衝突を避けています。
    *   また、`#define _SYS_TYPES_H` が `defs3_linux.go` と `defs_linux.go` の両方に追加されています。これは、`sys/types.h` が複数回インクルードされることによる再定義エラーを防ぐための一般的なC言語のテクニックです。これにより、Goランタイムが依存するCヘッダーのインクルード順序や内容に起因するビルドエラーを回避しています。
    *   `defs_linux.go` に `linux/time.h` がインクルードされたのは、おそらく `struct_timespec` や `struct_timeval` といった時間関連の構造体定義が必要になったためと考えられます。

4.  **PowerPC 64-bit の `ucontext` 特性**:
    *   `defs3_linux.go` のコメント `PPC64 uses sigcontext in place of mcontext in ucontext.` は非常に重要です。これは、PowerPC 64-bit アーキテクチャのLinuxでは、標準的な `ucontext_t` 構造体の中に含まれる `mcontext_t`（マシンコンテキスト）の代わりに、`sigcontext_t` 構造体が直接使用されることを示しています。このアーキテクチャ固有の差異に対応するために、`defs3_linux.go` で `Sigcontext C.struct_sigcontext` と `Ucontext C.struct_ucontext` を定義し、Goランタイムが `power64` の `ucontext` のレイアウトを正しく解釈できるようにしています。

これらの変更により、Goランタイムは `power64` 環境のLinuxカーネルと正確にインターフェースできるようになり、Goプログラムがこのアーキテクチャ上で安定して動作するための基盤が強化されました。

## 変更の背景

このコミットの背景には、Go言語がPowerPC 64-bit (power64) アーキテクチャへの対応を進めるという開発目標があります。Goランタイムは、オペレーティングシステム（この場合はLinux）と低レベルで連携するために、C言語で定義されたシステムコールやデータ構造の情報を必要とします。これらの定義は、アーキテクチャによって異なる場合があります。

特に、`ucontext`（ユーザーコンテキスト）やシグナルハンドリングに関連する構造体は、CPUのレジスタセットやメモリレイアウトに密接に関連しており、アーキテクチャごとにその定義が大きく異なることが一般的です。既存の `defs1_linux.go` や `defs_linux.go` は一般的なLinux環境の定義を扱っていましたが、`power64` のような特定のアーキテクチャでは、これらの汎用的な定義だけでは不十分でした。

このコミットは、`power64` アーキテクチャに特化した定義を `defs3_linux.go` という新しいファイルに集約し、`cgo -cdefs` ツールを使って `defs_linux_power64.h` および `defs_linux_power64le.h` (little-endian) といったアーキテクチャ固有のヘッダーファイルを生成できるようにすることで、Goランタイムが `power64` 環境で正しく動作するための基盤を確立することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Go Runtime (Goランタイム)**: Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション、ゴルーチンのスケジューリング、システムコールとの連携、メモリ管理などが含まれます。ランタイムはOSの機能に直接アクセスする必要があるため、OSやアーキテクチャ固有の定義を必要とします。

*   **cgo**: Go言語とC言語の相互運用を可能にするGoのツールです。GoプログラムからC関数を呼び出したり、CコードからGo関数を呼び出したりできます。このコミットでは、`cgo -cdefs` というモードが重要です。
    *   **`cgo -cdefs`**: このコマンドは、Goのソースファイル内に埋め込まれたC言語の定義（`import "C"` ブロック内）を解析し、GoランタイムがCの構造体や定数にアクセスするために必要なGoの型定義や定数定義を含むCヘッダーファイルを生成します。これにより、GoコードがCのABI（Application Binary Interface）に準拠した形でシステムコールなどを実行できるようになります。

*   **`defs_linux.go`, `defs1_linux.go`, `defs3_linux.go`**: これらはGoランタイムのソースコード内に存在するファイルで、Linuxシステムコールやカーネルデータ構造に関するC言語の定義をGoから利用できるようにするためのものです。これらのファイルは `cgo -cdefs` によって処理され、Goランタイムが利用するCヘッダーファイル（例: `defs_linux.h`）が生成されます。アーキテクチャや特定の機能に応じて、複数の `defs*.go` ファイルに分割されることがあります。

*   **PowerPC 64-bit (power64)**: IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、64ビットのプロセッサです。サーバーや組み込みシステムなどで利用されます。x86やARMといった他の一般的なアーキテクチャとは、レジスタの構成、システムコールの呼び出し規約、メモリの扱い方などが異なるため、低レベルなプログラミングではアーキテクチャ固有の対応が必要になります。

*   **`ucontext.h`**: POSIX標準で定義されているヘッダーファイルで、ユーザーコンテキスト（`ucontext_t`）構造体を提供します。この構造体は、プログラムの実行状態（CPUレジスタ、シグナルマスク、スタック情報など）を保存・復元するために使用されます。シグナルハンドリングやコルーチン（Goのゴルーチンも含む）の実装において非常に重要です。アーキテクチャによって `ucontext_t` の内部構造は大きく異なります。

*   **`fcntl.h`**: ファイル制御に関する定数や関数（例: `open`, `fcntl`）を定義するヘッダーファイルです。`O_RDONLY`（読み取り専用でファイルを開く）、`O_CLOEXEC`（`exec` 時にファイルディスクリプタをクローズする）などの定数が含まれます。

*   **`asm/signal.h`, `asm/ucontext.h`, `asm-generic/fcntl.h`**: これらはLinuxカーネルのヘッダーファイルで、特定のアーキテクチャ（`asm/` ディレクトリ以下）または汎用的な（`asm-generic/` ディレクトリ以下）なシステムコールやデータ構造の定義を提供します。これらはユーザー空間のアプリケーションがカーネルとやり取りする際のインターフェースを定義します。

*   **`SA_RESTORER`**: シグナルハンドリングにおいて `sigaction` システムコールに渡されるフラグの一つです。このフラグは、シグナルハンドラから戻る際に、カーネルがユーザー空間のスタックとレジスタの状態をどのように復元するかを制御するために使用されます。特に、`ucontext_t` 構造体を利用してコンテキストを復元する際に重要となることがあります。その挙動や必要性はアーキテクチャやカーネルのバージョンによって異なります。

*   **`__kernel_size_t`, `__sigset_t`**: これらはLinuxカーネル内部で使われる型定義で、ユーザー空間の標準ライブラリで定義されている `size_t` や `sigset_t` との衝突を避けるために、プレフィックス `__kernel_` や `__` が付けられることがあります。`cgo` でCのヘッダーを扱う際に、このような型名の衝突を避けるための工夫が必要になることがあります。

*   **`_SYS_TYPES_H`**: 多くのC言語のシステムヘッダーファイルで使われるマクロで、`sys/types.h` が複数回インクルードされることによる再定義エラーを防ぐためのインクルードガードとして機能します。

*   **`struct_pt_regs`, `elf_gregset_t`, `elf_fpregset_t`, `elf_vrreg_t`, `struct_sigaltstack`, `struct_sigcontext`, `struct_ucontext`**: これらは、CPUのレジスタセット（汎用レジスタ、浮動小数点レジスタ、ベクトルレジスタなど）、シグナル代替スタック、シグナルコンテキスト、ユーザーコンテキストといった、低レベルな実行状態を表現するためのC言語の構造体です。これらはシグナルハンドリング、デバッグ、コンテキストスイッチなどの操作で不可欠であり、その定義は各CPUアーキテクチャに固有です。特にPowerPCでは、`ucontext` の内部で `sigcontext` が使われるなど、他のアーキテクチャとは異なる構造を持つことがあります。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがPowerPC 64-bit (power64) アーキテクチャのLinux環境で、OSの低レベルなインターフェースと正確に連携できるようにするための定義を整備することにあります。

1.  **`defs3_linux.go` の導入**:
    *   Goランタイムは、`cgo -cdefs` を使用して、GoコードからC言語の構造体や定数にアクセスするためのGoの型定義やCヘッダーファイルを生成します。
    *   `power64` アーキテクチャは、特に `ucontext` やシグナルハンドリングに関連する構造体（`struct_pt_regs`, `elf_gregset_t`, `struct_sigcontext` など）において、他のアーキテクチャ（x86など）とは異なる定義を持っています。
    *   このため、既存の汎用的な `defs_linux.go` や `defs1_linux.go` だけでは `power64` の要件を満たせません。
    *   `defs3_linux.go` は、`power64` に特化したこれらの構造体定義をカプセル化するために導入されました。このファイルは、`+build ignore` ディレクティブによって通常のGoビルドプロセスからは除外され、`cgo -cdefs` によってのみ処理されることを意図しています。
    *   コメント `GOARCH=power64 cgo -cdefs defs_linux.go defs3_linux.go > defs_linux_power64.h` が示すように、`power64` 用のヘッダーファイル `defs_linux_power64.h` は、`defs_linux.go` と `defs3_linux.go` の両方から定義を結合して生成されます。

2.  **`SA_RESTORER` の扱い**:
    *   `SA_RESTORER` はシグナルハンドリングに関連する重要なフラグです。このコミットでは、`defs1_linux.go` に `SA_RESTORER` が追加され、`defs_linux.go` からは削除されています。
    *   さらに、`defs3_linux.go` では `SA_RESTORER = 0 // unused` と明示的に定義されています。これは、`power64` 環境では `SA_RESTORER` フラグが他のアーキテクチャとは異なる意味を持つか、あるいはGoランタイムのコンテキストでは使用されないことを示唆しています。このようなアーキテクチャ固有の差異を吸収するために、定義を分離し、それぞれのファイルで適切な値を設定しています。

3.  **型名の衝突回避とヘッダーのインクルード制御**:
    *   `defs3_linux.go` では、`#define size_t __kernel_size_t` や `#define sigset_t __sigset_t` といったCプリプロセッサディレクティブが使用されています。これは、`cgo` がCヘッダーを処理する際に、標準ライブラリの型定義とカーネルの型定義との間で発生しうる「inconsistent definitions (一貫性のない定義)」エラーを回避するためのものです。カーネル内部の型名にリネームすることで、衝突を避けています。
    *   また、`#define _SYS_TYPES_H` が `defs3_linux.go` と `defs_linux.go` の両方に追加されています。これは、`sys/types.h` が複数回インクルードされることによる再定義エラーを防ぐための一般的なC言語のテクニックです。これにより、Goランタイムが依存するCヘッダーのインクルード順序や内容に起因するビルドエラーを回避しています。
    *   `defs_linux.go` に `linux/time.h` がインクルードされたのは、おそらく `struct_timespec` や `struct_timeval` といった時間関連の構造体定義が必要になったためと考えられます。

4.  **PowerPC 64-bit の `ucontext` 特性**:
    *   `defs3_linux.go` のコメント `PPC64 uses sigcontext in place of mcontext in ucontext.` は非常に重要です。これは、PowerPC 64-bit アーキテクチャのLinuxでは、標準的な `ucontext_t` 構造体の中に含まれる `mcontext_t`（マシンコンテキスト）の代わりに、`sigcontext_t` 構造体が直接使用されることを示しています。このアーキテクチャ固有の差異に対応するために、`defs3_linux.go` で `Sigcontext C.struct_sigcontext` と `Ucontext C.struct_ucontext` を定義し、Goランタイムが `power64` の `ucontext` のレイアウトを正しく解釈できるようにしています。

これらの変更により、Goランタイムは `power64` 環境のLinuxカーネルと正確にインターフェースできるようになり、Goプログラムがこのアーキテクチャ上で安定して動作するための基盤が強化されました。

## コアとなるコードの解説

*   **`src/pkg/runtime/defs3_linux.go` の新規追加**:
    *   このファイルは、GoランタイムがPowerPC 64-bit (power64) アーキテクチャのLinux環境で、OSの低レベルなインターフェースと正確に連携するために不可欠な、アーキテクチャ固有のC構造体と定数の定義を提供します。
    *   `+build ignore` ディレクティブは、このファイルが通常のGoビルドプロセスには含まれず、`cgo -cdefs` ツールによってのみ特別に処理されることを示します。
    *   内部のCインクルードブロックでは、`size_t` や `sigset_t` といった一般的なC型をカーネル固有の型名（`__kernel_size_t`, `__sigset_t`）にリネームすることで、`cgo` がCヘッダーを解析する際に発生しうる型定義の衝突を回避しています。
    *   `#include <asm/ucontext.h>` は、PowerPC 64-bit の `ucontext` 構造体の定義を取り込むために重要です。このファイル内のコメント `PPC64 uses sigcontext in place of mcontext in ucontext.` は、PowerPC 64-bit が `ucontext` の内部で `mcontext` の代わりに `sigcontext` を使用するという、このアーキテクチャの特異性を明確に示しており、Goランタイムがこの違いを正しく扱うための基盤となります。
    *   `Ptregs`, `Gregset`, `FPregset`, `Vreg` などの型定義は、CPUのレジスタセットや浮動小数点レジスタ、ベクトルレジスタといった、プログラムの実行コンテキストを構成する要素をGoから参照できるようにするためのものです。これらはシグナルハンドリングやデバッグ、コンテキストスイッチといった低レベルな操作で不可欠です。
    *   `SA_RESTORER = 0 // unused` は、`power64` 環境における `SA_RESTORER` フラグの扱いが他のアーキテクチャと異なるか、Goランタイムのこのコンテキストでは使用されないことを示しています。

*   **`src/pkg/runtime/defs1_linux.go` の変更**:
    *   `#include <asm/signal.h>` の追加と `SA_RESTORER = C.SA_RESTORER` の定義は、一般的なLinux環境におけるシグナルハンドリングの定義を強化するものです。これにより、GoランタイムがLinuxカーネルのシグナル関連の機能とより正確に連携できるようになります。

*   **`src/pkg/runtime/defs_linux.go` の変更**:
    *   `#define _SYS_TYPES_H` の追加は、`sys/types.h` の多重インクルードによる再定義エラーを防ぐための標準的なCプリプロセッサのテクニックです。これにより、Goランタイムが依存するCヘッダーのインクルードの堅牢性が向上します。
    *   `#include <linux/time.h>` の追加は、おそらくGoランタイムが時間関連のシステムコールや構造体（例: `struct_timespec`, `struct_timeval`）をLinuxカーネルから直接利用する必要が生じたためと考えられます。
    *   `SA_RESTORER` の削除は、この定数が `defs1_linux.go` に移動されたため、重複を避けるためのクリーンアップです。
    *   `type Sigset C.sigset_t` の追加は、GoランタイムがC言語の `sigset_t` 型をGoの型として利用できるようにするためのものです。

これらの変更は全体として、GoランタイムがPowerPC 64-bit アーキテクチャのLinux環境で、OSの低レベルなインターフェースと正確に連携し、安定した動作を保証するための基盤を構築するものです。特に、アーキテクチャ固有の `ucontext` やシグナルハンドリングの差異を吸収するための `defs3_linux.go` の導入が、このコミットの最も重要な側面です。

# [インデックス 21500] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http/httputil` パッケージ内の `ReverseProxy` におけるリクエストキャンセル処理の改善に関するものです。具体的には、クライアントからのインバウンド接続が閉じられた際に、`ReverseProxy` がバックエンドへのアウトバウンドHTTPリクエストを適切にキャンセルするように変更されています。これにより、不要なリソース消費を防ぎ、プロキシの堅牢性を向上させることが目的です。

## 変更の背景

このコミットは、Goの`net/http/httputil.ReverseProxy`が、クライアントが接続を早期に切断した場合（例えば、ブラウザのタブを閉じる、HTTPクライアントがタイムアウトするなど）に、バックエンドへのリクエストを適切にキャンセルしないという問題（Issue #8406）を修正するために導入されました。

以前の実装では、クライアントがリクエストをキャンセルしても、`ReverseProxy`はバックエンドへのリクエストを継続してしまう可能性がありました。これは、以下のような問題を引き起こします。

1.  **不要なリソース消費**: バックエンドサーバーは、クライアントがすでに結果を必要としていないにもかかわらず、リクエストの処理を続け、CPU、メモリ、ネットワーク帯域などのリソースを無駄に消費します。
2.  **遅延の発生**: バックエンドからの応答を待つ間、プロキシサーバーのリソースも占有され、他のリクエストの処理に影響を与える可能性があります。
3.  **エラーハンドリングの不備**: クライアントが切断された状態でバックエンドからの応答をプロキシが受け取ろうとすると、`io.Copy`操作などでエラーが発生し、場合によってはパニックを引き起こしたり、不適切なエラーログが出力されたりする可能性がありました。

このコミットは、これらの問題を解決し、`ReverseProxy`がより堅牢で効率的に動作するようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のネットワークおよびHTTPに関する基本的な概念を理解しておく必要があります。

*   **`net/http` パッケージ**: Go言語の標準HTTPライブラリであり、HTTPクライアントとサーバーの実装を提供します。
*   **`net/http/httputil` パッケージ**: `net/http` パッケージのユーティリティ機能を提供し、特にリバースプロキシの実装である `ReverseProxy` が含まれます。
*   **`http.Handler` インターフェース**: HTTPリクエストを処理するためのインターフェースで、`ServeHTTP(ResponseWriter, *Request)` メソッドを持ちます。`ReverseProxy`もこのインターフェースを実装しています。
*   **`http.ResponseWriter` インターフェース**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。
*   **`http.CloseNotifier` インターフェース**: `http.ResponseWriter` が実装するオプションのインターフェースで、クライアントが接続を閉じたときに通知を受け取るためのチャネル (`CloseNotify() <-chan bool`) を提供します。これにより、サーバーはクライアントの切断を検知し、それに応じた処理を行うことができます。
*   **`http.Request` の `Body`**: HTTPリクエストのボディは `io.ReadCloser` インターフェースとして扱われます。これは、ボディからデータを読み取り、読み取りが完了したら閉じる必要があることを意味します。
*   **`http.Transport`**: HTTPクライアントが実際にネットワークリクエストを行うためのメカニズムを定義します。これには、接続の再利用、プロキシ設定、TLS設定などが含まれます。`http.DefaultTransport` はデフォルトの `http.Transport` 実装です。
*   **`http.Transport.CancelRequest` メソッド**: `http.Transport` が実装するメソッドで、進行中のHTTPリクエストをキャンセルするために使用されます。これは、リクエストがまだ完了していない場合に、そのリクエストに関連するネットワーク操作を中断するために呼び出されます。
*   **`context.Context` (Go 1.7以降)**: このコミットが作成された2014年時点では、`context.Context` はまだGoの標準ライブラリには統合されていませんでした（Go 1.7で導入）。しかし、リクエストのキャンセルやタイムアウトを伝播させるための一般的なパターンとして、このコミットで導入された `http.CloseNotifier` と `CancelRequest` の組み合わせは、後の `context.Context` の考え方に通じるものがあります。`context.Context` が導入されてからは、HTTPリクエストのキャンセルは主に `context.Context` を通じて行われるようになりました。このコミットは、`context.Context` が標準化される前の、リクエストキャンセルを扱うための初期の試みの一つと見なすことができます。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、`ReverseProxy`がクライアントの切断を検知し、それに応じてバックエンドへのリクエストをキャンセルするメカニズムが追加されたことがわかります。

主な変更点は以下の通りです。

1.  **`requestCanceler` インターフェースの導入**:
    ```go
    type requestCanceler interface {
        CancelRequest(*http.Request)
    }
    ```
    このインターフェースは、`http.Transport`が`CancelRequest`メソッドを持つかどうかをチェックするために導入されました。これにより、`ReverseProxy`は、使用している`Transport`がリクエストキャンセルをサポートしている場合にのみ、キャンセル処理を試みるようになります。`http.DefaultTransport`は内部的にこのインターフェースを実装しています。

2.  **`runOnFirstRead` 構造体の導入**:
    ```go
    type runOnFirstRead struct {
        io.Reader
        fn func() // Run before first Read, then set to nil
    }

    func (c *runOnFirstRead) Read(bs []byte) (int, error) {
        if c.fn != nil {
            c.fn()
            c.fn = nil
        }
        return c.Reader.Read(bs)
    }
    ```
    このカスタム`io.Reader`は、`outreq.Body`（バックエンドへのリクエストボディ）の最初の読み取りが行われる直前に、特定の関数`fn`を実行するためのものです。これは、リクエストボディのストリーミングが開始されるタイミングで、クライアントの切断監視を開始するために使用されます。これにより、リクエストボディが実際に送信され始めるまで、キャンセル監視のゴルーチンを起動しないことで、不要なゴルーチンの起動を避けることができます。

3.  **`ServeHTTP` メソッド内のキャンセルロジック**:
    `ReverseProxy`の`ServeHTTP`メソッド内に、以下のロジックが追加されました。
    *   `rw.(http.CloseNotifier)` を使用して、`ResponseWriter`が`http.CloseNotifier`インターフェースを実装しているかを確認します。これは、クライアントが接続を閉じたときに通知を受け取るために必要です。
    *   `transport.(requestCanceler)` を使用して、`Transport`が`requestCanceler`インターフェースを実装しているかを確認します。
    *   両方の条件が満たされた場合、以下の処理が行われます。
        *   `reqDone`というチャネルが作成され、`defer close(reqDone)`で関数終了時に閉じられるように設定されます。これは、キャンセル監視ゴルーチンに処理を終了させるシグナルを送るために使用されます。
        *   `clientGone := closeNotifier.CloseNotify()` を呼び出し、クライアントの切断を監視するチャネルを取得します。
        *   `outreq.Body`（バックエンドへのリクエストボディ）が、カスタムの`runOnFirstRead`ラッパーで置き換えられます。このラッパーの`fn`フィールドには、新しいゴルーチンを起動する関数が設定されます。
        *   新しいゴルーチンは、`select`ステートメントを使用して、`clientGone`チャネルまたは`reqDone`チャネルのいずれかからのシグナルを待ちます。
            *   `<-clientGone` が発生した場合（クライアントが切断された場合）、`requestCanceler.CancelRequest(outreq)` が呼び出され、バックエンドへのリクエストがキャンセルされます。
            *   `<-reqDone` が発生した場合（`ServeHTTP`関数が終了した場合）、ゴルーチンは正常に終了します。

このメカニズムにより、クライアントがリクエストの途中で接続を切断した場合でも、`ReverseProxy`はそれを検知し、バックエンドへの不要なリクエストを速やかにキャンセルできるようになりました。これにより、バックエンドのリソースが解放され、プロキシ全体の効率と安定性が向上します。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は、主に`src/net/http/httputil/reverseproxy.go`ファイル内の`ReverseProxy`構造体と、その`ServeHTTP`メソッドに集中しています。

具体的には、以下の要素が追加・変更されています。

1.  **新しいインターフェースの定義**:
    *   `type requestCanceler interface { CancelRequest(*http.Request) }`
2.  **新しい構造体とメソッドの定義**:
    *   `type runOnFirstRead struct { io.Reader; fn func() }`
    *   `func (c *runOnFirstRead) Read(bs []byte) (int, error)`
3.  **`ReverseProxy.ServeHTTP` メソッド内のロジック追加**:
    *   `http.CloseNotifier` と `requestCanceler` の型アサーションによるチェック。
    *   `reqDone` チャネルの作成と`defer`によるクローズ。
    *   `closeNotifier.CloseNotify()` からのチャネル取得。
    *   `outreq.Body` を `runOnFirstRead` でラップし、その `fn` フィールドにキャンセルロジックを含むゴルーチンを起動する関数を設定。このゴルーチン内で `select` を使用して `clientGone` または `reqDone` を待ち、`clientGone` の場合は `requestCanceler.CancelRequest(outreq)` を呼び出す。

また、`src/net/http/httputil/reverseproxy_test.go` には、このキャンセル機能が正しく動作するかを確認するための新しいテストケース `TestReverseProxyCancellation` が追加されています。このテストでは、バックエンドへのリクエスト中にクライアントが接続を切断するシナリオをシミュレートし、リクエストが適切にキャンセルされることを検証しています。

## コアとなるコードの解説

### `requestCanceler` インターフェース

このインターフェースは、`http.Transport`がリクエストキャンセル機能を提供するかどうかを抽象化するために導入されました。Goのインターフェースの強力な機能により、`ReverseProxy`は具体的な`Transport`の実装に依存することなく、`CancelRequest`メソッドの存在を確認し、利用することができます。これにより、将来的に異なる`Transport`実装が導入された場合でも、このキャンセルロジックを再利用できる柔軟性が生まれます。

### `runOnFirstRead` 構造体と `Read` メソッド

このカスタムリーダーは、リクエストボディのストリーミング処理において、非常に巧妙なタイミング制御を実現しています。`ReverseProxy`は、クライアントから受け取ったリクエストボディを、そのままバックエンドへのリクエストボディとして転送（ストリーミング）することがあります。このとき、クライアントの切断監視ゴルーチンを、リクエストボディの最初のバイトが読み取られる直前に起動することで、以下の利点があります。

*   **効率性**: リクエストボディが非常に大きい場合でも、実際にデータ転送が始まるまでキャンセル監視のゴルーチンを起動しないため、リソースの無駄を省けます。
*   **正確なタイミング**: リクエストが実際にバックエンドに送信され始めるタイミングと、クライアントの切断監視が開始されるタイミングを同期させることができます。

`Read`メソッド内で`c.fn()`が一度だけ実行され、その後`c.fn = nil`と設定されることで、この関数が複数回呼び出されることを防いでいます。

### `ServeHTTP` メソッド内のキャンセルロジック

この部分が、クライアントの切断を検知し、バックエンドへのリクエストをキャンセルする核心的なロジックです。

1.  **インターフェースのチェック**: `if closeNotifier, ok := rw.(http.CloseNotifier); ok { ... }` と `if requestCanceler, ok := transport.(requestCanceler); ok { ... }` は、それぞれ`ResponseWriter`と`Transport`が、必要なキャンセル機能を提供しているかを確認しています。これにより、互換性のない環境でのエラーを防ぎます。

2.  **ゴルーチンの起動とチャネルによる同期**:
    *   `clientGone := closeNotifier.CloseNotify()` は、クライアントが接続を閉じたときにシグナルを送るチャネルを取得します。
    *   `reqDone := make(chan struct{})` は、`ServeHTTP`関数が正常に終了したときに、キャンセル監視ゴルーチンに終了を伝えるためのチャネルです。`defer close(reqDone)` により、`ServeHTTP`関数がリターンする際に自動的に閉じられます。
    *   `go func() { ... }()` で起動されるゴルーチンは、`select`文を使って`clientGone`または`reqDone`からのシグナルを待ちます。
        *   `case <-clientGone:` が実行された場合、クライアントが切断されたことを意味するため、`requestCanceler.CancelRequest(outreq)` を呼び出して、バックエンドへのリクエストをキャンセルします。
        *   `case <-reqDone:` が実行された場合、`ServeHTTP`関数が正常に完了したことを意味するため、ゴルーチンは単に終了します。

この構造により、クライアントの切断が検知された場合にのみ、バックエンドへのリクエストキャンセルがトリガーされ、不要なリソース消費やエラーを効果的に防ぐことができます。

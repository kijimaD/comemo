## 変更の背景

このコミットは、Go言語の初期開発段階におけるコンパイラ最適化の一環として行われました。特に、`8g`コンパイラ（386アーキテクチャ向け）のコード生成効率を向上させることが目的です。コンパイラが生成するコードのパフォーマンスは、一時変数をどのように扱うかに大きく依存します。一時変数をスタックに割り当てるよりも、CPUレジスタに割り当てる方が、アクセス速度が格段に速いため、プログラム全体の実行速度が向上します。

コミットメッセージにある「likely to go back to registers for most temporaries.」という記述は、以前の試みで一時変数をスタックに割り当てていたが、パフォーマンス上の理由からレジスタ割り当てに戻す、あるいはレジスタ割り当てを強化する方向へ転換したことを示唆しています。これは、コンパイラの開発過程で最適なコード生成戦略を模索していた時期の典型的な変更です。

しかし、この変更はまだ安定しておらず、`datafmt`, `fmt`, `go/scanner`, `log`, `reflect`, `strconv`, `template`といった標準ライブラリのテストが失敗していることが報告されています。これは、レジスタ割り当てのロジックが複雑であり、すべてのケースで正しく機能するように調整するにはさらなる作業が必要であることを示しています。特に、これらのライブラリは文字列操作、型情報、フォーマットなど、多様なデータ型と操作を扱うため、一時変数の管理がより複雑になる可能性があります。

## 前提知識の解説

### Goコンパイラ (`8g`)

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`8g`は386（Intel 80386互換）アーキテクチャ、つまり32ビットx86システム向けのGoコンパイラを指します。Goコンパイラは、ソースコードを中間表現に変換し、その後、ターゲットアーキテクチャの機械語に変換する役割を担います。このプロセスには、レジスタ割り当て、命令選択、コード最適化などが含まれます。

### レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラの最適化フェーズの一つで、プログラムの実行中に頻繁にアクセスされる変数や一時的な計算結果を、CPUの高速なレジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速にアクセスできるため、適切にレジスタを割り当てることでプログラムの実行速度を大幅に向上させることができます。しかし、レジスタの数は限られているため、どの変数をレジスタに割り当て、どの変数をメモリ（スタック）にスピル（退避）させるかを決定する複雑なアルゴリズムが必要です。

### 一時変数 (Temporary Variables)

一時変数とは、コンパイラが複雑な式を評価する際の中間結果を保持するために内部的に生成する変数です。例えば、`a = (b + c) * d`という式では、`b + c`の結果を一時的に保持するための変数が生成されることがあります。これらの変数はソースコードには直接現れませんが、コンパイラが効率的な機械語を生成するために不可欠です。一時変数をレジスタに割り当てるか、スタックに割り当てるかは、コードのパフォーマンスに直接影響します。

### Ullman Number

Ullman Number（ウルマン数）は、コンパイラの最適化において、式の評価順序を決定するために使用されるヒューリスティックな値です。これは、式の各ノード（演算子やオペランド）に対して計算され、そのノードを評価するために必要なレジスタの最小数を示します。Ullman Numberが高いサブツリーを先に評価することで、レジスタのスピルを最小限に抑え、効率的なコードを生成できる可能性があります。

### Goコンパイラの主要ファイル (`src/cmd/8g/`)

*   **`cgen.c`**: コード生成のコアロジックが含まれています。式の評価、変数への代入、制御フローなどの高レベルな操作を機械語命令に変換します。
*   **`ggen.c`**: ジェネリックなコード生成ルーチンが含まれています。関数呼び出し、インターフェースメソッド呼び出し、算術演算など、より具体的なコード生成処理を扱います。
*   **`gobj.c`**: オブジェクトファイルの生成に関連するルーチンが含まれています。データセクションやテキストセクションの管理、シンボル情報の出力などを行います。
*   **`gsubr.c`**: サブルーチンやユーティリティ関数が含まれています。レジスタ割り当て、型変換、エラーハンドリングなど、コンパイラの様々な部分で利用される共通の機能を提供します。

## 技術的詳細

このコミットでは、主に`src/cmd/8g/cgen.c`と`src/cmd/8g/ggen.c`において、一時変数のレジスタ割り当てを強化するための変更が加えられています。

### `src/cmd/8g/cgen.c`の変更点

*   **`mgen`と`mfree`関数の導入**:
    *   `mgen(Node *n, Node *n1, Node *rg)`: ノード`n`の値を`n1`に生成する関数です。`n`がアドレス可能であれば直接`n1`にコピーし、そうでなければ一時変数を割り当てます。`n->type->width > widthptr`（ポインタ幅より大きい型、例えば64ビット整数）の場合はスタックに一時変数を割り当て（`tempalloc`）、それ以外の場合はレジスタに割り当てます（`regalloc`）。これは、小さな型はレジスタに、大きな型はスタックにという戦略を示唆しています。
    *   `mfree(Node *n)`: `mgen`で割り当てられた一時変数を解放します。スタックに割り当てられた場合は`tempfree`、レジスタに割り当てられた場合は`regfree`を呼び出します。
*   **`cgen`関数の変更**:
    *   `!n->addable && !res->addable`（ソースもデスティネーションもアドレス可能でない）場合の処理が変更されました。以前は常に`tempalloc`を使用していましたが、64ビット型の場合のみ`tempalloc`を使用し、それ以外は`regalloc`を使用するように変更されました。これにより、より多くのケースでレジスタが利用されるようになります。
    *   `OAS`（代入）や二項演算（`abop`）の処理において、`tempalloc`/`tempfree`の代わりに`mgen`/`mfree`や`regalloc`/`regfree`が使用されるようになりました。特に、`abop`ではUllman Numberに基づいて評価順序を決定し、レジスタ割り当てを最適化しようとしています。
    *   `OLEN`（`len`組み込み関数）の処理が変更され、文字列やスライスの長さ取得において、ポインタのオフセット計算とレジスタの利用がより明示的になりました。
    *   `igen`関数（アドレス生成）において、一時的なスタック割り当てが削除され、直接レジスタにアドレスを割り当てるようになりました。

 void
 cgen_shift(int op, Node *nl, Node *nr, Node *res)
 {
 	Node n1, n2;
 	int a, w;
 	Prog *p1;
 	uvlong sc;

 	if(nl->type->width > 4)
 		fatal("cgen_shift %T", nl->type->width);

 	if(nl->type->width == 1 && nl->type->etype != TUINT8)
 		fatal("cgen_shift %T", nl->type);

 	w = nl->type->width * 8;

 	a = optoas(op, nl->type);

 	if(nr->op == OLITERAL) {
 		regalloc(&n1, nl->type, res);
 		cgen(nl, &n1);
 		sc = mpgetfix(nr->val.u.xval);
 		if(sc >= nl->type->width*8) {
 			// large shift gets 2 shifts by width
 			gins(a, ncon(w-1), &n1);
 			gins(a, ncon(w-1), &n1);
 		} else
 			gins(a, nr, &n1);
 		gmove(&n1, res);
 		regfree(&n1);
 		return;
 	}

 	nodreg(&n1, types[TUINT32], D_CX);
 	regalloc(&n1, nr->type, &n1);		// to hold the shift type in CX

 	regalloc(&n2, nl->type, res);
 	if(nl->ullman >= nr->ullman) {
 		cgen(nl, &n2);
 		cgen(nr, &n1);
 	} else {
 		cgen(nr, &n1);
 		cgen(nl, &n2);
 	}

 	// test and fix up large shifts
 	gins(optoas(OCMP, types[TUINT32]), &n1, ncon(w));

 	} else {
 		gmove(ncon(0), &n2);
 	}
 	patch(p1, pc);
 	gins(a, &n1, &n2);

 	gmove(&n2, res);

 	regfree(&n1);
 	regfree(&n2);

## コアとなるコードの解説

### `mgen`と`mfree`関数

これらの関数は、一時変数の割り当てと解放を抽象化し、レジスタとスタックのどちらを使用するかを型（`n->type->width > widthptr`）に基づいて決定します。ポインタの幅（32ビットシステムでは4バイト）よりも大きい型（例: 64ビット整数）はスタックに、それより小さい型はレジスタに割り当てるというヒューリスティックを採用しています。これにより、コンパイラはより効率的に一時変数を管理し、レジスタの利用を最大化しようとします。

### `cgen`関数における一時変数の扱い

`cgen`関数内の変更は、特にソースとデスティネーションの両方がアドレス可能でない（つまり、両方が一時的な値である）場合に顕著です。以前は常にスタックに一時変数を割り当てていましたが、このコミットでは64ビット型の場合のみスタックを使用し、それ以外の場合はレジスタを使用するように変更されました。これは、32ビットアーキテクチャにおいて、64ビット値をレジスタで直接扱うのが難しい（2つの32ビットレジスタが必要になるなど）ため、スタックの方が管理しやすいという判断があった可能性があります。

二項演算（`abop`）の処理では、Ullman Numberに基づいてオペランドの評価順序を決定し、`mgen`と`mfree`を積極的に利用してレジスタ割り当てを最適化しています。これにより、中間結果を効率的にレジスタに保持し、メモリへのアクセスを減らすことを目指しています。

### `cgen_shift`関数の実装

以前は未実装だったシフト演算のコード生成が、このコミットで追加されました。これは、Go言語の基本的な演算が`8g`コンパイラでサポートされるようになったことを意味します。シフト量は`CX`レジスタにロードされ、大きなシフト量（オペランドのビット幅以上）に対する特別な処理（結果を0にする、あるいは符号拡張シフトの場合は符号ビットで埋める）が実装されています。これは、シフト演算の定義域外の挙動を正しく処理するために重要です。

### `gen_as_init`関数における静的初期化の拡張

`gen_as_init`関数の変更は、Go言語の複合リテラル（スライス、マップ）や文字列リテラルといった複雑なデータ構造の静的初期化をサポートするために不可欠です。これらのデータは、プログラムの実行開始前にデータセクションに配置される必要があります。この関数は、`ADATA`命令を生成して、これらの構造体の内容をデータセクションに書き込むロジックを提供します。これにより、Goプログラムがより複雑な静的データを初期化できるようになり、言語の表現力が向上します。

これらの変更は全体として、`8g`コンパイラがより効率的な機械語を生成し、Go言語の機能（特に複合型や基本的な演算）をより完全にサポートするための重要なステップです。しかし、一部のテストが失敗していることから、レジスタ割り当てのロジックやコード生成の正確性にはまだ調整が必要な段階であったことが伺えます。

# [インデックス 25544] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) において、ARM64アーキテクチャで共有ライブラリを使用する際のガベージコレクションデータ (gcdata) の検索方法を改善するものです。具体的には、`R_AARCH64_RELATIVE` リロケーションエントリを解析することで、共有ライブラリ内のシンボルに対応するgcdataのアドレスを正確に特定できるように変更されています。これにより、Goプログラムが共有ライブラリと連携する際のガベージコレクションの正確性と効率性が向上します。

## 変更の背景

Go言語のガベージコレクタは、プログラムの実行中にヒープ上のオブジェクトを正確に識別し、到達可能なオブジェクトを保持し、到達不能なオブジェクトを解放する役割を担っています。このプロセスにおいて、ポインタがどこにあるかを正確に知ることは非常に重要です。Goのコンパイラとリンカは、この目的のために「gcdata」と呼ばれるメタデータを生成します。gcdataは、特定のデータ構造やスタックフレーム内のどの位置にポインタが含まれているかを示す情報を含んでいます。

共有ライブラリ (Shared Libraries) を使用する場合、Goのリンカは、これらのライブラリ内のシンボルやデータ構造に関する情報を適切に処理する必要があります。特に、共有ライブラリがGoの型情報やgcdataを含む場合、リンカはそれらの情報を正確に読み取り、メインの実行可能ファイルと統合する必要があります。

ARM64アーキテクチャでは、リロケーション (relocation) の仕組みが他のアーキテクチャと異なる場合があります。リロケーションとは、プログラムがロードされる際に、コードやデータ内のアドレス参照を修正するプロセスです。`R_AARCH64_RELATIVE` はARM64特有のリロケーションタイプの一つで、これはプログラムのロードアドレスからの相対オフセットとして値を解決します。

このコミット以前は、GoのリンカがARM64上の共有ライブラリからgcdataのアドレスを正確に取得する方法に不備があった可能性があります。特に、`decodetype_gcprog_shlib` 関数が共有ライブラリ内の型情報からgcdataプログラムをデコードする際に、正しいアドレスを見つけられない問題があったと考えられます。この問題は、共有ライブラリを使用するGoプログラムのガベージコレクションの正確性に影響を与える可能性がありました。

## 前提知識の解説

### Go言語のガベージコレクション (GC) と gcdata

Goのガベージコレクタは、正確な (precise) GCです。これは、ヒープ上のすべてのポインタを正確に識別できることを意味します。この正確性を実現するために、Goコンパイラは各型、関数、スタックフレームに対して「gcdata」と呼ばれるビットマップのようなメタデータを生成します。このgcdataは、メモリ上のどのオフセットにポインタが存在するかを示し、GCがオブジェクトグラフを正確に辿ることを可能にします。

### リンカ (`cmd/link`)

`cmd/link` はGo言語のリンカであり、コンパイルされたGoパッケージ (オブジェクトファイル) を結合して実行可能ファイルや共有ライブラリを生成します。リンカの主要な役割の一つは、シンボル解決とリロケーションの適用です。シンボル解決は、異なるオブジェクトファイルで定義された関数や変数の参照を解決することです。リロケーションは、プログラムがメモリにロードされる際に、絶対アドレスや相対アドレスを修正するプロセスです。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準的なファイル形式です。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション (コード、データ、シンボルテーブル、リロケーション情報など) で構成されます。

- **シンボルテーブル**: プログラム内の関数や変数の名前とアドレスをマッピングします。
- **リロケーションセクション**: プログラムがロードされる際に修正が必要なアドレス参照のリストを含みます。各リロケーションエントリは、修正が必要な場所 (オフセット)、修正の種類 (タイプ)、参照先のシンボル、および加算値 (addend) を指定します。

### ARM64アーキテクチャと `R_AARCH64_RELATIVE` リロケーション

ARM64 (AArch64) は、64ビットのARMアーキテクチャです。このアーキテクチャでは、特定の命令やデータ参照に対して独自のリロケーションタイプが定義されています。

`R_AARCH64_RELATIVE` は、ARM64のELFリロケーションタイプの一つです。このタイプのリロケーションは、プログラムがロードされるベースアドレスからの相対オフセットとして値を解決するために使用されます。つまり、リロケーションが適用される場所の値は、`ロードアドレス + addend` に設定されます。これは、特にPosition-Independent Code (PIC) やPosition-Independent Data (PID) を生成する際に重要であり、共有ライブラリでよく使用されます。

## 技術的詳細

このコミットの核心は、GoのリンカがARM64上の共有ライブラリからgcdataのアドレスを正確に抽出する方法を改善することにあります。

1.  **`Shlib` 構造体の拡張**:
    `src/cmd/link/internal/ld/link.go` で定義されている `Shlib` 構造体は、共有ライブラリに関する情報を保持します。このコミットでは、`gcdata_addresses map[*LSym]uint64` フィールドが追加されました。これは、共有ライブラリ内の各シンボル (`*LSym`) に対応するgcdataのアドレス (`uint64`) をマッピングするためのものです。

2.  **`ldshlibsyms` 関数でのリロケーション解析**:
    `src/cmd/link/internal/ld/lib.go` 内の `ldshlibsyms` 関数は、共有ライブラリからシンボルをロードする役割を担っています。この関数内で、以下の変更が加えられました。
    *   `gcdata_locations` というマップが導入されました。これは、共有ライブラリ内の型情報シンボル (`type.`) のアドレスと、それに対応する `*LSym` を一時的にマッピングするために使用されます。具体的には、型情報シンボルのデータ内でgcdataプログラムへのポインタが格納されているオフセットを計算し、そのオフセットをキーとして `gcdata_locations` に格納します。
    *   ELFファイル内の `elf.SHT_RELA` (リロケーションエントリと加算値を持つリロケーションセクション) を走査します。
    *   各リロケーションエントリ (`rela`) について、そのタイプ (`t`) が `elf.R_AARCH64_RELATIVE` であるかどうかをチェックします。
    *   もし `R_AARCH64_RELATIVE` リロケーションであり、かつそのリロケーションのオフセット (`rela.Off`) が `gcdata_locations` マップのキーと一致する場合、それはgcdataプログラムへのポインタのリロケーションであると判断されます。
    *   この場合、リロケーションの加算値 (`rela.Addend`) が、対応するシンボルのgcdataのアドレスとして `gcdata_addresses` マップに格納されます。

3.  **`decodetype_gcprog_shlib` 関数での利用**:
    `src/cmd/link/internal/ld/decodesym.go` 内の `decodetype_gcprog_shlib` 関数は、共有ライブラリ内の型情報からgcdataプログラムをデコードする際に呼び出されます。
    *   この関数に、`Thearch.Thechar == '7'` (ARM64アーキテクチャを示す) の場合の特殊な処理が追加されました。
    *   ARM64の場合、`Ctxt.Shlibs` (ロードされた共有ライブラリのリスト) を走査し、現在のシンボル (`s`) が属する共有ライブラリを見つけます。
    *   見つかった共有ライブラリの `gcdata_addresses` マップから、現在のシンボルに対応するgcdataのアドレスを取得して返します。

これらの変更により、GoのリンカはARM64アーキテクチャにおいて、共有ライブラリ内のgcdataプログラムへのポインタが `R_AARCH64_RELATIVE` リロケーションとして表現されている場合でも、その正確なアドレスを特定できるようになりました。これにより、共有ライブラリを使用するGoプログラムのガベージコレクションが正しく機能することが保証されます。

## コアとなるコードの変更箇所

### `src/cmd/link/internal/ld/decodesym.go`

```go
func decodetype_gcprog_shlib(s *LSym) uint64 {
	if Thearch.Thechar == '7' { // ARM64の場合
		for _, shlib := range Ctxt.Shlibs {
			if shlib.Path == s.File { // シンボルが属する共有ライブラリを見つける
				return shlib.gcdata_addresses[s] // 共有ライブラリに格納されたgcdataアドレスを返す
			}
		}
		return 0
	}
	return decode_inuxi(s.P[2*int32(Thearch.Ptrsize)+8+1*int32(Thearch.Ptrsize):], Thearch.Ptrsize)
}
```

### `src/cmd/link/internal/ld/lib.go`

```go
func ldshlibsyms(shlib string) {
	// ... (既存のコード) ...

	gcdata_locations := make(map[uint64]*LSym) // gcdataプログラムへのポインタ位置を一時的に保持するマップ

	for _, elfsym := range syms {
		// ... (既存のシンボル処理) ...
		if strings.HasPrefix(lsym.Name, "type.") && !strings.HasPrefix(lsym.Name, "type..") {
			lsym.P = readelfsymboldata(f, &elfsym)
			// gcdataプログラムへのポインタが格納されているオフセットを計算し、gcdata_locationsに格納
			gcdata_locations[elfsym.Value+2*uint64(Thearch.Ptrsize)+8+1*uint64(Thearch.Ptrsize)] = lsym
		}
	}

	gcdata_addresses := make(map[*LSym]uint64) // 最終的なgcdataアドレスを格納するマップ
	if Thearch.Thechar == '7' { // ARM64の場合
		for _, sect := range f.Sections {
			if sect.Type == elf.SHT_RELA { // RELAセクションを走査
				var rela elf.Rela64
				rdr := sect.Open()
				for {
					err := binary.Read(rdr, f.ByteOrder, &rela)
					if err == io.EOF {
						break
					} else if err != nil {
						Diag("reading relocation failed %v", err)
						return
					}
					t := elf.R_AARCH64(rela.Info & 0xffff)
					if t != elf.R_AARCH64_RELATIVE { // R_AARCH64_RELATIVE リロケーションのみを対象
						continue
					}
					if lsym, ok := gcdata_locations[rela.Off]; ok { // リロケーションオフセットがgcdata_locationsのキーと一致する場合
						gcdata_addresses[lsym] = uint64(rela.Addend) // addendをgcdataアドレスとして格納
					}
				}
			}
		}
	}

	// ... (既存のコード) ...
	// Shlib構造体にgcdata_addressesを格納
	Ctxt.Shlibs = append(Ctxt.Shlibs, Shlib{Path: libpath, Hash: hash, Deps: deps, File: f, gcdata_addresses: gcdata_addresses})
}
```

## コアとなるコードの解説

### `src/cmd/link/internal/ld/link.go` の変更

`Shlib` 構造体に `gcdata_addresses map[*LSym]uint64` が追加されたことで、各共有ライブラリが、その内部で定義されているGoのシンボル (`*LSym`) と、それに対応するガベージコレクションデータ (`gcdata`) のメモリアドレスとのマッピングを保持できるようになりました。これは、リンカが共有ライブラリを処理する際に、gcdataの場所を追跡するための重要な情報源となります。

### `src/cmd/link/internal/ld/lib.go` の変更

`ldshlibsyms` 関数は、共有ライブラリをロードし、そのシンボル情報を解析する中心的な役割を担います。
1.  **`gcdata_locations` の導入**:
    このマップは、共有ライブラリ内の `type.` で始まるシンボル (Goの型情報) を処理する際に構築されます。Goの型情報シンボルには、その型に関連するgcdataプログラムへのポインタが含まれています。このポインタが格納されているオフセットを計算し、そのオフセットをキーとして、対応する `*LSym` を `gcdata_locations` に一時的に保存します。これにより、後続のリロケーション解析で、どのリロケーションがgcdataプログラムへのポインタを指しているかを効率的に特定できます。

2.  **`R_AARCH64_RELATIVE` リロケーションの解析**:
    ARM64アーキテクチャ (`Thearch.Thechar == '7'`) の場合、リンカは共有ライブラリのELFファイル内の `SHT_RELA` セクションを読み込みます。このセクションには、リロケーションエントリが含まれており、それぞれが `rela.Off` (リロケーションを適用するオフセット)、`rela.Info` (リロケーションタイプとシンボルインデックス)、`rela.Addend` (加算値) を持ちます。
    リンカは、リロケーションタイプが `R_AARCH64_RELATIVE` であるエントリに注目します。このタイプのリロケーションは、通常、ロード時のベースアドレスからの相対オフセットを解決するために使用されます。
    もし `rela.Off` が `gcdata_locations` のキー (つまり、gcdataプログラムへのポインタが格納されている場所) と一致した場合、そのリロケーションはgcdataプログラムへのポインタを修正するためのものであると判断されます。このとき、`rela.Addend` の値が、実際にgcdataプログラムがロードされるメモリアドレスを示します。このアドレスは、対応する `*LSym` とともに `gcdata_addresses` マップに格納されます。

3.  **`Shlib` への `gcdata_addresses` の格納**:
    最終的に、構築された `gcdata_addresses` マップは、`Shlib` 構造体の新しいフィールドに格納され、`Ctxt.Shlibs` リストに追加されます。これにより、リンカの他の部分やランタイムが、共有ライブラリ内のgcdataの場所を必要とする際に、この情報にアクセスできるようになります。

### `src/cmd/link/internal/ld/decodesym.go` の変更

`decodetype_gcprog_shlib` 関数は、共有ライブラリ内の型情報からgcdataプログラムをデコードする際に、そのアドレスを取得するために使用されます。
このコミットにより、ARM64アーキテクチャの場合、この関数は単に `Ctxt.Shlibs` から適切な `Shlib` エントリを見つけ、その `gcdata_addresses` マップから現在のシンボル (`s`) に対応するgcdataのアドレスを直接取得して返すようになりました。これにより、共有ライブラリ内のgcdataアドレスの解決が、`R_AARCH64_RELATIVE` リロケーションの解析結果に基づいて正確に行われるようになります。

これらの変更は、GoのリンカがARM64上で共有ライブラリを扱う際のガベージコレクションの正確性を保証するために不可欠です。特に、共有ライブラリが動的にロードされ、その中のGoの型情報やgcdataがランタイムによって参照される場合に、正しいメモリアドレスを指すようにポインタが修正されることを確実にします。

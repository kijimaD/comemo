# [インデックス 20801] ファイルの概要

このコミットでは、Go言語の標準ライブラリである `crypto/x509` パッケージ内のX.509証明書処理に関する変更が行われました。具体的には、証明書の `MaxPathLen` フィールドの扱いが修正されています。

変更されたファイルは以下の通りです。

-   `src/crypto/x509/x509.go`: X.509証明書の構造体定義と、証明書のパースおよび構築ロジックが含まれる主要なファイルです。
-   `src/crypto/x509/x509_test.go`: `crypto/x509` パッケージのテストファイルで、`MaxPathLen` の新しい挙動を検証するためのテストケースが追加されています。

## 元コミット内容

`crypto/x509: continue to recognise MaxPathLen of zero as "no value".`

このコミットは、`crypto/x509` パッケージにおいて、`MaxPathLen` がゼロ値である場合に「値なし」として引き続き認識されるようにする変更です。

以前の `encoding/asn1` パッケージの変更により、オプションの整数をマーシャリングする際の挙動が変わりました。以前はゼロ値の整数はマーシャリング時に省略されていましたが、変更後はデフォルト値が設定されている場合、その整数はデフォルト値である場合にのみ省略されるようになりました。

この変更は `crypto/x509` の挙動に影響を与えました。なぜなら、`Certificate.MaxPathLen` はデフォルト値が -1 であり、その結果、ゼロ値の `MaxPathLen` がマーシャリング時に省略されなくなったためです。これは、`MaxPathLen` のゼロ値が有効で意味のある値であり、表現できるようになったという点ではバグ修正とも言えます。しかし、`MaxPathLen` を全く設定していなかったユーザー（Dockerを含む）のコードを壊してしまいました。

このコミットは、ゼロ値の `MaxPathLen` が再び省略されるようにし、さらに `MaxPathLenZero` という新しいメンバーを導入して、本当にゼロ値を意図している場合にそれを示すようにしました。これは「醜い」解決策ではあるものの、ユーザーのコードを壊さないことを重視した結果です。

## 変更の背景

この変更の背景には、Go言語の `encoding/asn1` パッケージにおける、オプションの整数値のマーシャリング（Goのデータ構造からASN.1形式への変換）に関する挙動の変更があります。

元々、`encoding/asn1` は、Goの構造体フィールドがオプションであり、かつその値がゼロである場合、ASN.1エンコーディング時にそのフィールドを省略していました。これは、多くのプロトコル（X.509証明書も含む）において、特定のフィールドが存在しないことと、そのフィールドが明示的にゼロ値を持つこととを区別するために重要な挙動でした。

しかし、コミットメッセージで参照されている以前のコミット `[1] https://code.google.com/p/go/source/detail?r=4218b3544610e8d9771b89126553177e32687adf` によって、`encoding/asn1` の挙動が変更されました。この変更後、オプションの整数フィールドにデフォルト値が設定されている場合、そのフィールドは「デフォルト値と等しい場合にのみ」省略されるようになりました。

この変更が `crypto/x509` パッケージに影響を与えました。`crypto/x509` の `Certificate` 構造体には `MaxPathLen` というフィールドがあり、これはX.509証明書の基本制約拡張（Basic Constraints Extension）の一部として、証明書チェーンの最大長を定義します。この `MaxPathLen` フィールドは、内部的に -1 をデフォルト値として扱っていました（-1 は「制限なし」を意味することが多い）。

`encoding/asn1` の変更後、`MaxPathLen` がゼロ値の場合、以前は省略されていたものが、デフォルト値である -1 とは異なるため、明示的にエンコードされるようになりました。技術的には、`MaxPathLen` のゼロ値は「最大パス長がゼロ」という有効な意味を持つため、これをエンコードすることは「バグ修正」とも解釈できます。しかし、実際には多くの既存のアプリケーション（特にDockerなど）が、`MaxPathLen` を全く設定しない場合に、それがゼロ値としてエンコードされることを期待していませんでした。彼らは、`MaxPathLen` が設定されていない（つまり省略される）ことを「制限なし」と解釈していました。

この予期せぬ挙動変更は、既存のユーザーのコードを壊すことになったため、Goチームは後方互換性を維持するために、このコミットで元の挙動（ゼロ値の `MaxPathLen` は省略される）に戻しつつ、明示的にゼロ値を設定したい場合のメカニズムを追加することにしました。

## 前提知識の解説

### X.509証明書とBasic Constraints拡張

X.509証明書は、公開鍵暗号基盤（PKI）において、公開鍵の所有者を検証するために広く使用されるデジタル証明書の標準です。証明書には、所有者の情報、公開鍵、発行者、有効期間などの情報が含まれます。

X.509証明書には「拡張（Extensions）」という概念があり、証明書に追加の情報を付与することができます。その一つに「Basic Constraints（基本制約）」拡張があります。

**Basic Constraints拡張**は、証明書がCA（認証局）証明書であるか否か、そしてCA証明書である場合に、そのCAが発行できる下位CA証明書のパス長を制限するために使用されます。

-   `IsCA` (boolean): この証明書がCA証明書であるかどうかを示します。`true` の場合、この証明書は他の証明書に署名するために使用できます。
-   `MaxPathLen` (integer, optional): `IsCA` が `true` の場合にのみ意味を持ちます。このCA証明書の下に存在できる非CA証明書までのパスの最大長を示します。
    -   `MaxPathLen` が存在しない（省略されている）場合、または無限大を示す値（例: -1）の場合、パス長に制限はありません。
    -   `MaxPathLen` が `0` の場合、このCA証明書はエンドエンティティ証明書（CAではない証明書）にのみ署名でき、その下にさらにCA証明書を発行することはできません。
    -   `MaxPathLen` が `N` (N > 0) の場合、このCA証明書の下に `N` 個のCA証明書を連ねることができます。

### ASN.1 (Abstract Syntax Notation One)

ASN.1は、データ構造を記述するための標準的な記法であり、通信プロトコルやデータストレージにおいて、異なるシステム間でデータを交換する際に使用されます。X.509証明書もASN.1で定義された構造を持っています。

ASN.1で定義されたデータ構造は、通常、BER (Basic Encoding Rules) や DER (Distinguished Encoding Rules) などのエンコーディングルールに従ってバイト列に変換されます。Go言語の `encoding/asn1` パッケージは、Goの構造体とASN.1のバイト列との間のマーシャリング（エンコード）およびアンマーシャリング（デコード）を扱います。

### Go言語の `encoding/asn1` パッケージ

`encoding/asn1` パッケージは、Goの構造体タグを使用して、Goのデータ型をASN.1の特定の型にマッピングし、エンコード/デコードを行います。オプションのフィールドやデフォルト値を持つフィールドの扱いは、ASN.1エンコーディングの正確性に不可欠です。

このパッケージでは、構造体フィールドに `asn1:"optional"` タグを付けることで、そのフィールドがオプションであることを示します。また、`asn1:"default:X"` のようにタグを付けることで、デフォルト値を指定できます。

### マーシャリングとオプションの整数

ASN.1では、特定のフィールドが「存在しない」ことと「ゼロ値を持つ」ことを区別することが重要です。例えば、`MaxPathLen` の場合、フィールドが存在しないことは「制限なし」を意味し、フィールドが `0` の値を持つことは「パス長がゼロに制限される」という具体的な意味を持ちます。

`encoding/asn1` の以前の挙動では、オプションの整数フィールドがGoの構造体でゼロ値を持つ場合、ASN.1エンコーディング時にそのフィールドは省略されていました。これは、多くのプロトコルで「ゼロ値は省略されることで『値なし』を意味する」という慣習に合致していました。

しかし、参照されているコミット `[1]` での変更により、`asn1:"default:X"` のようにデフォルト値が指定されている場合、ゼロ値であってもそのデフォルト値と異なる場合は省略されなくなりました。`Certificate.MaxPathLen` は内部的に -1 をデフォルト値として扱っていたため、この変更の影響を受けました。

## 技術的詳細

このコミットの技術的詳細は、`encoding/asn1` パッケージの挙動変更によって生じた `crypto/x509` の `MaxPathLen` のマーシャリング問題への対処にあります。

### 問題の再確認

1.  **`encoding/asn1` の変更**: 以前は、オプションの整数フィールドがGoの構造体でゼロ値を持つ場合、ASN.1エンコーディング時にそのフィールドは省略されていました。新しい挙動では、フィールドにデフォルト値が設定されている場合、そのフィールドはデフォルト値と等しい場合にのみ省略されるようになりました。
2.  **`MaxPathLen` のデフォルト値**: `crypto/x509` の `Certificate.MaxPathLen` は、内部的に -1 を「制限なし」のデフォルト値として扱っていました。
3.  **問題の発生**: `encoding/asn1` の変更後、`MaxPathLen` がGoの構造体で `0` の値を持つ場合、これは -1 とは異なるため、ASN.1エンコーディング時に明示的に `0` としてエンコードされるようになりました。
    -   これにより、`MaxPathLen` を全く設定していなかった（つまり、Goの構造体では `0` に初期化される）ユーザーの証明書が、意図せず `MaxPathLen=0` としてエンコードされることになりました。
    -   これは、証明書チェーンの構築において、意図しない制約を課すことになり、既存のアプリケーション（例: Docker）の互換性を損ねました。

### 解決策の導入

このコミットでは、この問題を解決するために以下の変更を導入しました。

1.  **`MaxPathLenZero` フィールドの追加**: `Certificate` 構造体に新しいブール型フィールド `MaxPathLenZero` が追加されました。
    ```go
    type Certificate struct {
        // ...
        MaxPathLen            int
        // MaxPathLenZero indicates that BasicConstraintsValid==true and
        // MaxPathLen==0 should be interpreted as an actual maximum path length
        // of zero. Otherwise, that combination is interpreted as MaxPathLen
        // not being set.
        MaxPathLenZero bool
    }
    ```
    このフィールドは、`BasicConstraintsValid` が `true` かつ `MaxPathLen` が `0` の場合に、それが「実際に最大パス長がゼロである」ことを明示的に示すために使用されます。このフィールドが `false` の場合、`MaxPathLen=0` は「MaxPathLenが設定されていない」と解釈されます。

2.  **証明書パース時の `MaxPathLenZero` の設定**: `parseCertificate` 関数内で、証明書をパースする際に `MaxPathLen` が `0` であれば `MaxPathLenZero` を `true` に設定するように変更されました。
    ```go
    func parseCertificate(in *certificate) (*Certificate, error) {
        // ...
        case oidExtensionBasicConstraints:
            // ...
            out.MaxPathLen = constraints.MaxPathLen
            out.MaxPathLenZero = out.MaxPathLen == 0 // ここで設定
            // ...
    }
    ```

3.  **証明書構築時の `MaxPathLen` の調整**: `buildExtensions` 関数内で、証明書をASN.1形式にマーシャリングする際に、`MaxPathLen` の値を調整するロジックが追加されました。
    ```go
    func buildExtensions(template *Certificate) (ret []pkix.Extension, err error) {
        // ...
        if template.BasicConstraintsValid && !oidInExtensions(oidExtensionBasicConstraints, template.ExtraExtensions) {
            // Leaving MaxPathLen as zero indicates that no maximum path
            // length is desired, unless MaxPathLenZero is set. A value of
            // -1 causes encoding/asn1 to omit the value as desired.
            maxPathLen := template.MaxPathLen
            if maxPathLen == 0 && !template.MaxPathLenZero {
                maxPathLen = -1 // MaxPathLenが0で、かつMaxPathLenZeroがfalseの場合、-1に変換して省略させる
            }
            ret[n].Id = oidExtensionBasicConstraints
            ret[n].Value, err = asn1.Marshal(basicConstraints{template.IsCA, maxPathLen}) // 調整されたmaxPathLenを使用
            ret[n].Critical = true
            // ...
        }
        // ...
    }
    ```
    このロジックにより、`template.MaxPathLen` が `0` であり、かつ `template.MaxPathLenZero` が `false` の場合（つまり、ユーザーが明示的にゼロを設定したわけではなく、単に初期値のゼロである場合）、`maxPathLen` は `-1` に設定されます。これにより、`encoding/asn1` はこの値を省略し、以前の「制限なし」の挙動を再現します。

この解決策は、コミットメッセージで「醜い (ugly)」と表現されているように、`MaxPathLen` と `MaxPathLenZero` という2つのフィールドを使って `MaxPathLen` の「ゼロ値」と「値なし」を区別するという、やや回りくどい方法です。しかし、これは既存のユーザーのコードを壊さずに、かつ `MaxPathLen=0` という有効な意味を表現できるようにするための、実用的な妥協点として採用されました。

## コアとなるコードの解説

### `Certificate` 構造体への `MaxPathLenZero` の追加

`MaxPathLenZero` は、`MaxPathLen` が `0` であることと、`MaxPathLen` が「設定されていない」（つまり、ASN.1エンコーディング時に省略されるべき）こととを区別するためのフラグです。

-   `MaxPathLen=0` かつ `MaxPathLenZero=true`: 証明書チェーンの最大長が明示的にゼロに設定されていることを意味します。
-   `MaxPathLen=0` かつ `MaxPathLenZero=false`: `MaxPathLen` が設定されていない（省略されるべき）ことを意味します。これは、Goの構造体の初期値がゼロであるために `MaxPathLen` がゼロになっているが、ユーザーは特にゼロを意図していない場合に発生します。

### `parseCertificate` 関数での `MaxPathLenZero` の設定

```go
out.MaxPathLen = constraints.MaxPathLen
out.MaxPathLenZero = out.MaxPathLen == 0
```
証明書をASN.1からGoの `Certificate` 構造体にパースする際、ASN.1の `MaxPathLen` の値が `0` であれば、`MaxPathLenZero` を `true` に設定します。これにより、パースされた証明書が「明示的にゼロのパス長を持つ」ことを正しく反映します。

### `buildExtensions` 関数での `MaxPathLen` のマーシャリングロジック

```go
maxPathLen := template.MaxPathLen
if maxPathLen == 0 && !template.MaxPathLenZero {
    maxPathLen = -1
}
ret[n].Value, err = asn1.Marshal(basicConstraints{template.IsCA, maxPathLen})
```
この部分が、このコミットの核心的な変更です。
証明書をGoの `Certificate` 構造体からASN.1形式にマーシャリングする際、以下のロジックが適用されます。

1.  `template.MaxPathLen` の値が `maxPathLen` にコピーされます。
2.  もし `maxPathLen` が `0` であり、かつ `template.MaxPathLenZero` が `false` の場合、これはユーザーが明示的に `MaxPathLen=0` を設定したわけではなく、単にGoの構造体の初期値が `0` であるためにそうなっているケースと判断されます。
3.  この場合、`maxPathLen` は `-1` に変更されます。`encoding/asn1` パッケージは、デフォルト値が `-1` のオプションの整数フィールドをマーシャリングする際に、その値が `-1` であれば省略します。これにより、以前の「`MaxPathLen` が設定されていない」という挙動が再現され、既存のアプリケーションとの互換性が保たれます。
4.  もし `maxPathLen` が `0` であり、かつ `template.MaxPathLenZero` が `true` の場合、`maxPathLen` は `0` のままとなり、ASN.1エンコーディング時に明示的に `0` としてエンコードされます。これは、ユーザーが本当に `MaxPathLen=0` を意図している場合です。
5.  それ以外の `MaxPathLen` の値（例: `1` や `2` など）はそのまま使用され、ASN.1にエンコードされます。

このロジックにより、`MaxPathLen` の「値なし」（省略）と「明示的なゼロ値」が区別され、`encoding/asn1` の新しい挙動と既存のユーザーの期待との間のギャップが埋められます。

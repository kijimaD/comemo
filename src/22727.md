# [インデックス 22727] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるヒープ統計の管理方法を変更するものです。具体的には、`memstats.heap_alloc` の使用を廃止し、新たに `memstats.heap_live` を導入することで、GCトリガーの精度と効率を向上させています。

変更されたファイルは以下の通りです。

*   `src/runtime/mcache.go`
*   `src/runtime/mgc.go`
*   `src/runtime/mgcsweep.go`
*   `src/runtime/mheap.go`
*   `src/runtime/mstats.go`
*   `src/runtime/trace.go`

    runtime: introduce heap_live; replace use of heap_alloc in GC
    
    Currently there are two main consumers of memstats.heap_alloc:
    updatememstats (aka ReadMemStats) and shouldtriggergc.
    
    updatememstats recomputes heap_alloc from the ground up, so we don't
    need to keep heap_alloc up to date for it. shouldtriggergc wants to
    know how many bytes were marked by the previous GC plus how many bytes
    have been allocated since then, but this *isn't* what heap_alloc
    tracks. heap_alloc also includes objects that are not marked and
    haven't yet been swept.
    
    Introduce a new memstat called heap_live that actually tracks what
    shouldtriggergc wants to know and stop keeping heap_alloc up to date.
    
    Unlike heap_alloc, heap_live follows a simple sawtooth that drops
    during each mark termination and increases monotonically between GCs.
    heap_alloc, on the other hand, has much more complicated behavior: it
    may drop during sweep termination, slowly decreases from background
    sweeping between GCs, is roughly unaffected by allocation as long as
    there are unswept spans (because we sweep and allocate at the same
    rate), and may go up after background sweeping is done depending on
    the GC trigger.
    
    heap_live simplifies computing next_gc and using it to figure out when
    to trigger garbage collection. Currently, we guess next_gc at the end
    of a cycle and update it as we sweep and get a better idea of how much
    heap was marked. Now, since we're directly tracking how much heap is
    marked, we can directly compute next_gc.
    
    This also corrects bugs that could cause us to trigger GC early.
    Currently, in any case where sweep termination actually finds spans to
    sweep, heap_alloc is an overestimation of live heap, so we'll trigger
    GC too early. heap_live, on the other hand, is unaffected by sweeping.

## 変更の背景

Goランタイムのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。GCの重要な役割の一つは、次のGCをいつトリガーするかを決定することです。この決定には、ヒープの使用状況に関する正確な統計情報が不可欠です。

これまで、Goランタイムは `memstats.heap_alloc` という統計情報を使用して、ヒープに割り当てられたバイト数を追跡していました。この `heap_alloc` は、主に `updatememstats` (または `ReadMemStats`) と `shouldtriggergc` の2つの主要なコンシューマによって利用されていました。

しかし、`heap_alloc` にはいくつかの問題がありました。

1.  **`shouldtriggergc` の要件との不一致**: `shouldtriggergc` は、前回のGCでマークされたバイト数と、それ以降に割り当てられたバイト数の合計を知りたいと考えていました。しかし、`heap_alloc` は、マークされず、まだスイープされていない（解放されていない）オブジェクトも含むため、この要件を満たしていませんでした。つまり、`heap_alloc` は実際の「生きている」ヒープサイズを正確に反映していませんでした。
2.  **複雑な挙動**: `heap_alloc` の値は、スイープ終了時に減少したり、バックグラウンドスイープによって徐々に減少したり、未スイープのスパンが存在する間は割り当ての影響をほとんど受けなかったり、GCトリガーによってはバックグラウンドスイープ完了後に増加したりと、非常に複雑な挙動を示していました。この複雑さにより、`next_gc` (次のGCがトリガーされるべきヒープサイズ) の計算が困難になっていました。
3.  **GCの早期トリガー**: スイープ終了時に実際にスイープされるスパンが見つかる場合、`heap_alloc` は生きているヒープの過大評価となり、結果としてGCが早すぎるタイミングでトリガーされるバグがありました。これは、まだ解放されていないが、実際には到達不能なオブジェクトが `heap_alloc` に含まれているためです。

これらの問題を解決し、GCトリガーのロジックを簡素化し、より正確にするために、`heap_live` という新しい統計情報が導入されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な概念と、関連するランタイムの統計情報について理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリ領域（ガベージ）を自動的に解放するプロセスです。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
    *   **マークフェーズ (Mark Phase)**: プログラムがアクセス可能な（生きている）オブジェクトを特定し、マークします。GoのGCは、このフェーズの一部で「Stop-the-World (STW)」ポーズを導入しますが、大部分はコンカレント（並行）に実行されます。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクトが占めるメモリ領域を解放し、再利用可能な状態にします。GoのGCでは、スイープもコンカレントに、または必要に応じてレイジー（遅延）に実行されます。
    *   **マーク終了 (Mark Termination)**: マークフェーズの最終段階で、STWポーズ中に実行されます。この時点で、生きているオブジェクトのセットが確定します。
*   **`memstats`**: Goランタイムが管理するメモリ統計情報を含む構造体です。`runtime.ReadMemStats` 関数を通じてGoプログラムからアクセスできます。
    *   **`memstats.heap_alloc`**: これまでのGoランタイムで、ヒープに現在割り当てられているバイト数を追跡していた統計情報です。これには、生きているオブジェクトだけでなく、まだスイープされていない死んだオブジェクトも含まれていました。
    *   **`memstats.next_gc`**: 次のGCがトリガーされるべきヒープの目標サイズを示す値です。この値は、前回のGCでマークされた生きているヒープサイズと、`GOGC` 環境変数で設定されたGC比率に基づいて計算されます。
*   **`shouldtriggergc()`**: GCをトリガーすべきかどうかを判断するランタイム内の関数です。主に `memstats.heap_alloc` と `memstats.next_gc` を比較して判断していました。
*   **スパン (Span)**: Goのメモリ管理における基本的な単位で、連続したページ（通常は8KB）のブロックです。ヒープはスパンの集合として管理されます。オブジェクトはスパン内に割り当てられます。
*   **コンカレントスイープ (Concurrent Sweep)**: GCのスイープフェーズが、通常のプログラム実行と並行して行われることを指します。これにより、STWポーズの時間を短縮し、アプリケーションのレイテンシを改善します。

## 技術的詳細

このコミットの核心は、`memstats.heap_alloc` の代わりに `memstats.heap_live` を導入し、GCトリガーのロジックを改善することにあります。

**`heap_alloc` の問題点と `heap_live` の導入理由**:
`heap_alloc` は、ヒープに割り当てられた総バイト数を表していましたが、これにはまだスイープされていない死んだオブジェクトのメモリも含まれていました。そのため、GCが次にいつ実行されるべきかを判断する `shouldtriggergc` 関数にとって、この値は正確な「生きているヒープ」のサイズを反映していませんでした。`shouldtriggergc` が本当に必要としていたのは、「前回のGCでマークされたバイト数 + それ以降に割り当てられたバイト数」という情報でした。

そこで、`heap_live` が導入されました。`heap_live` は、この `shouldtriggergc` の要件に合致するように設計されています。

**`heap_live` の挙動**:
`heap_live` は、`heap_alloc` とは異なり、非常にシンプルで予測可能な挙動を示します。

*   **マーク終了時**: 各GCのマーク終了時に、`heap_live` はそのGCでマークされた（生きている）バイト数にリセットされます。
*   **GC間**: GCが実行されていない期間は、新しいオブジェクトが割り当てられるにつれて `heap_live` は単調に増加します。

この「のこぎり波」のような挙動は、`next_gc` の計算を大幅に簡素化します。

**`heap_alloc` の複雑な挙動との比較**:
対照的に、`heap_alloc` は以下のような複雑な挙動を持っていました。

*   **スイープ終了時の減少**: スイープが完了すると、解放されたメモリの分だけ減少する可能性がありました。
*   **バックグラウンドスイープによる減少**: GC間でもバックグラウンドスイープによって徐々に減少しました。
*   **未スイープスパンの影響**: 未スイープのスパンがある限り、割り当てとスイープが同じレートで行われるため、割り当てによる影響をほとんど受けませんでした。
*   **GCトリガーによる増加**: バックグラウンドスイープが完了した後、GCトリガーによっては増加することもありました。

このような複雑な挙動は、`next_gc` の正確な予測を困難にし、GCトリガーのロジックを複雑にしていました。

**`next_gc` 計算の簡素化とバグ修正**:
`heap_live` の導入により、`next_gc` の計算が大幅に簡素化されました。以前は、GCサイクルの終わりに `next_gc` を推測し、スイープが進むにつれてマークされたヒープのサイズがより明確になるにつれて更新する必要がありました。しかし、`heap_live` がマークされたヒープサイズを直接追跡するようになったため、`next_gc` を直接計算できるようになりました。

さらに、この変更はGCの早期トリガーに関するバグを修正します。以前は、スイープ終了時に実際にスイープされるスパンが見つかる場合、`heap_alloc` は生きているヒープを過大評価していました。これは、まだ解放されていない死んだオブジェクトのメモリが含まれていたためです。この過大評価により、GCが本来よりも早くトリガーされてしまうことがありました。`heap_live` はスイープの影響を受けないため、この問題が解消されます。`heap_live` は常に実際の生きているヒープサイズをより正確に反映するため、GCは適切なタイミングでトリガーされるようになります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルで `heap_alloc` の参照が `heap_live` に置き換えられ、`heap_live` の更新ロジックが追加されています。

*   **`src/runtime/mcache.go`**:
    *   `local_cachealloc` のコメントが変更され、`heap_alloc` ではなく `heap_live` に関連する割り当てバイト数を追跡することが示唆されています。
*   **`src/runtime/mgc.go`**:
    *   `shouldtriggergc` 関数内で `memstats.heap_alloc` が `memstats.heap_live` に変更されています。
    *   `gc` 関数内で、GCトレースのためのヒープサイズ取得に `memstats.heap_alloc` の代わりに `memstats.heap_live` が使用されています。
    *   マーク終了フェーズで `memstats.heap_live` が `work.bytesMarked` (マークされたバイト数) に設定され、`memstats.next_gc` が `heap_live` に基づいて計算されるようになりました。
    *   コンカレントスイープに関するコメントが大幅に修正され、`next_gc` の計算が `heap_live` に基づくようになったこと、およびスイープが `next_gc` を減らすロジックが削除されたことが反映されています。
*   **`src/runtime/mgcsweep.go`**:
    *   `mSpan_Sweep` 関数内で、スイープによって解放されたメモリに基づいて `memstats.next_gc` を減らすロジックが完全に削除されています。これは、`next_gc` が `heap_live` に基づいてマーク終了時に直接計算されるようになったため、スイープ中に動的に調整する必要がなくなったためです。
*   **`src/runtime/mheap.go`**:
    *   `mHeap_Alloc_m` 関数内で、ヒープへの割り当て時に `memstats.heap_alloc` ではなく `memstats.heap_live` が更新されるようになりました。
    *   `mHeap_Free` 関数内で、スパンの解放時に `memstats.heap_alloc` を減らすロジックが削除されています。
*   **`src/runtime/mstats.go`**:
    *   `mstats` 構造体に `heap_live` フィールドが追加され、その目的がコメントで説明されています。
    *   `flushallmcaches` および `purgecachedstats` 関数内で、キャッシュからの統計情報をグローバル統計にフラッシュする際に `memstats.heap_alloc` ではなく `memstats.heap_live` が更新されるようになりました。
*   **`src/runtime/trace.go`**:
    *   トレースイベント `traceEvHeapAlloc` のコメントが `memstats.heap_alloc change` から `memstats.heap_live change` に変更され、実際にトレースされる値も `memstats.heap_alloc` から `memstats.heap_live` に変更されています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

最も重要な変更は `src/runtime/mgc.go` に集中しています。

```go
// old: return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_alloc)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0
// new: return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_live)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0
func shouldtriggergc() bool {
	return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_live)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0
}
```
`shouldtriggergc` 関数は、GCをトリガーすべきかどうかを判断します。以前は `memstats.heap_alloc` を使用していましたが、これはスイープされていない死んだオブジェクトも含むため、実際の生きているヒープサイズを過大評価していました。`memstats.heap_live` に変更することで、より正確な生きているヒープサイズに基づいてGCトリガーの判断が行われるようになります。これにより、GCが早すぎるタイミングでトリガーされるバグが修正されます。

```go
// old: memstats.next_gc = memstats.heap_alloc + memstats.heap_alloc*uint64(gcpercent)/100
// new: memstats.heap_live = work.bytesMarked
// new: memstats.next_gc = memstats.heap_live + memstats.heap_live*uint64(gcpercent)/100
func gcMark(start_time int64) {
	// ...
	memstats.heap_live = work.bytesMarked
	memstats.next_gc = memstats.heap_live + memstats.heap_live*uint64(gcpercent)/100
	if memstats.next_gc < heapminimum {
		memstats.next_gc = heapminimum
	}
	// ...
}
```
`gcMark` 関数はマークフェーズの終了時に呼び出されます。ここで、`memstats.heap_live` が `work.bytesMarked` (マークされた、つまり生きているオブジェクトの総バイト数) に設定されます。そして、この正確な `heap_live` の値に基づいて `memstats.next_gc` が計算されます。これにより、`next_gc` の計算が簡素化され、GCがいつトリガーされるべきかの予測がより正確になります。以前は `heap_alloc` を使っていましたが、これはスイープの進行によって変動するため、`next_gc` の予測が困難でした。

### `src/runtime/mheap.go` の変更

```go
// old: memstats.heap_alloc += uint64(_g_.m.mcache.local_cachealloc)
// new: memstats.heap_live += uint64(_g_.m.mcache.local_cachealloc)
func mHeap_Alloc_m(h *mheap, npage uintptr, sizeclass int32, large bool) *mspan {
	// ...
	memstats.heap_live += uint64(_g_.m.mcache.local_cachealloc)
	// ...
}

// old: memstats.heap_alloc += uint64(npage << _PageShift)
// new: memstats.heap_live += uint64(npage << _PageShift)

	// ...
	if large {
		memstats.heap_objects++
		memstats.heap_live += uint64(npage << _PageShift)
		// ...
	}
	// ...
}

// Removed: memstats.heap_alloc -= uint64(s.npages << _PageShift)
func mHeap_Free(h *mheap, s *mspan, acct int32) {
	// ...
	if acct != 0 {
		// memstats.heap_alloc -= uint64(s.npages << _PageShift) // Removed

	}
	// ...

```
`mHeap_Alloc_m` はヒープからメモリを割り当てる際に呼び出されます。ここで、割り当てられたバイト数が `memstats.heap_alloc` ではなく `memstats.heap_live` に加算されるようになりました。これにより、`heap_live` がGC間の割り当てを正確に反映するようになります。
`mHeap_Free` では、スパンが解放される際に `memstats.heap_alloc` を減らすロジックが削除されました。これは、`heap_live` がマークされたバイト数のみを追跡し、解放されたメモリはスイープによって `heap_live` に影響を与えないためです。

### `src/runtime/mstats.go` の変更

```go
type mstats struct {
	// ...
	// Statistics below here are not exported to Go directly.
	tinyallocs uint64 // number of tiny allocations that didn't cause actual allocation; not exported to go directly

	// heap_live is the number of bytes considered live by the GC.
	// That is: retained by the most recent GC plus allocated
	// since then. heap_live <= heap_alloc, since heap_live
	// excludes unmarked objects that have not yet been swept.
	heap_live uint64
}
```
`mstats` 構造体に `heap_live` フィールドが追加され、その定義と目的が明確にコメントされています。これは、GCによって「生きている」と見なされるバイト数を追跡し、前回のGCで保持されたバイト数とそれ以降に割り当てられたバイト数の合計であることを示しています。また、`heap_live` が `heap_alloc` 以下であること、そして `heap_live` がまだスイープされていないマークされていないオブジェクトを除外することも明記されています。

## 変更の背景

この変更の背景には、Goのテストフレームワークにおけるテストの構造化と柔軟性の向上が挙げられます。Goの`testing`パッケージはシンプルで強力ですが、従来のテストでは、関連する複数のテストケースを一つのテスト関数内でループを使って記述することが一般的でした。しかし、この方法では、個々のテストケースの失敗を独立して報告したり、特定のテストケースだけを再実行したりすることが困難でした。

Issue #12166（"testing: allow subtests"）では、この問題が提起され、サブテストの導入が提案されました。サブテストは、親テスト関数内でさらに小さなテストを定義できる機能です。これにより、テストのセットアップとティアダウンを共有しつつ、個々のテストケースを独立したエンティティとして扱えるようになります。同様のニーズはベンチマークにも存在し、サブベンチマークによって、異なるシナリオやデータセットに対するベンチマークを構造化して実行できるようになります。

このコミットは、これらの要望に応える形で、内部的に存在していたサブテスト/サブベンチマークの実行ロジックを`*T.Run`および`*B.Run`として公開し、開発者がこの強力な機能を直接利用できるようにすることを目的としています。

## 前提知識の解説

### Goの`testing`パッケージ

Go言語には、標準でテストをサポートする`testing`パッケージが用意されています。このパッケージは、ユニットテスト、ベンチマークテスト、例（Example）テストなどを記述するための基本的な機能を提供します。

- **テスト関数**: `func TestXxx(t *testing.T)`というシグネチャを持つ関数で、`go test`コマンドによって実行されます。`*testing.T`型は、テストの状態管理（成功/失敗の記録、ログ出力など）やヘルパーメソッド（`t.Error`, `t.Fatal`など）を提供します。
- **ベンチマーク関数**: `func BenchmarkXxx(b *testing.B)`というシグネチャを持つ関数で、`go test -bench=.`コマンドによって実行されます。`*testing.B`型は、ベンチマークの実行回数（`b.N`）や時間計測、メモリ割り当ての記録などの機能を提供します。

### サブテストとサブベンチマークの概念

- **サブテスト**: 一つの`TestXxx`関数内で、さらに複数のテストケースを定義し、それぞれを独立したテストとして実行する機能です。例えば、ある関数の異なる入力値に対するテストを、それぞれ独立したサブテストとして記述できます。これにより、テストの失敗がどの特定のケースで発生したかを明確に特定でき、テストの可読性と保守性が向上します。また、`go test -run "TestParent/SubTestName"`のように、特定のサブテストのみを実行することも可能です。
- **サブベンチマーク**: サブテストと同様に、一つの`BenchmarkXxx`関数内で複数のベンチマークケースを定義し、それぞれを独立したベンチマークとして実行する機能です。これにより、異なる設定やデータサイズでのパフォーマンスを比較する際に、コードの重複を減らし、結果を構造化して表示できます。

### `testing.T`と`testing.B`の内部構造

`testing`パッケージの`*T`と`*B`は、テストやベンチマークの実行コンテキストをカプセル化しています。これらは、テストの階層構造を管理するための内部的なメカニズムを持っており、このコミット以前は、そのメカニズムが外部に公開されていませんでした。

## 技術的詳細

このコミットの主要な技術的変更は、`*testing.T`と`*testing.B`のプライベートメソッドをパブリックメソッドに昇格させたことです。

### `*testing.T.Run(name string, f func(t *T)) bool`

以前は`t.run(name, f)`というプライベートメソッドとして存在していました。このメソッドは、指定された名前`name`で新しいサブテストを作成し、そのサブテストのコンテキストで関数`f`を実行します。`f`が完了すると、サブテストの結果（成功/失敗）を返します。

- **動作**: `Run`メソッドが呼び出されると、`testing`パッケージは新しい`*T`インスタンス（サブテストのコンテキスト）を作成し、それを`f`に渡します。この新しい`*T`インスタンスは、親テストのコンテキストから派生し、独自のログバッファ、エラー状態、および実行状態を持ちます。
- **並行実行**: `t.Parallel()`を呼び出すことで、サブテストを並行して実行できます。`t.Run`は、すべての並行サブテストが完了するまでブロックします。
- **名前付け**: サブテストの名前は、親テストの名前とスラッシュ(`/`)で区切られて結合されます（例: `TestFoo/SubTestBar`）。これにより、テスト結果の報告や特定のサブテストのフィルタリングが容易になります。

### `*testing.B.Run(name string, f func(b *B)) bool`

以前は`b.runBench(name, f)`というプライベートメソッドとして存在していました。このメソッドは、指定された名前`name`で新しいサブベンチマークを作成し、そのサブベンチマークのコンテキストで関数`f`を実行します。

- **動作**: `Run`メソッドが呼び出されると、`testing`パッケージは新しい`*B`インスタンス（サブベンチマークのコンテキスト）を作成し、それを`f`に渡します。この新しい`*B`インスタンスは、親ベンチマークのコンテキストから派生し、独自の計測結果を記録します。
- **親ベンチマークの計測停止**: `*B.Run`が呼び出されたベンチマーク関数自体は、それ以降の計測を行いません。代わりに、そのサブベンチマークの合計実行時間が計測されます。これにより、親ベンチマークがサブベンチマークのオーケストレーションのみを行い、実際のパフォーマンス計測はサブベンチマークに委ねられるという明確な役割分担が実現されます。
- **名前付け**: サブベンチマークの名前も、親ベンチマークの名前とスラッシュ(`/`)で区切られて結合されます（例: `BenchmarkFoo/SubBenchmarkBar`）。

### `matchBenchmarks`フラグの変更

`matchBenchmarks`フラグの説明が「regular expression to select benchmarks to run」から「regular expression per path component to select benchmarks to run」に変更されました。これは、サブベンチマークの名前がパスのような階層構造を持つようになったため、正規表現がそのパスの各コンポーネントに対して適用されることを示唆しています。これにより、より柔軟なベンチマークのフィルタリングが可能になります。

- **名前付け**: サブテストの名前は、親テストの名前とスラッシュ(`/`)で区切られて結合されます（例: `TestFoo/SubTestBar`）。これにより、テスト結果の報告や特定のサブテストのフィルタリングが容易になります。

### `*testing.B.Run(name string, f func(b *B)) bool`

以前は`b.runBench(name, f)`というプライベートメソッドとして存在していました。このメソッドは、指定された名前`name`で新しいサブベンチマークを作成し、そのサブベンチマークのコンテキストで関数`f`を実行します。

- **動作**: `Run`メソッドが呼び出されると、`testing`パッケージは新しい`*B`インスタンス（サブベンチマークのコンテキスト）を作成し、それを`f`に渡します。この新しい`*B`インスタンスは、親ベンチマークのコンテキストから派生し、独自の計測結果を記録します。
- **親ベンチマークの計測停止**: `*B.Run`が呼び出されたベンチマーク関数自体は、それ以降の計測を行いません。代わりに、そのサブベンチマークの合計実行時間が計測されます。これにより、親ベンチマークがサブベンチマークのオーケストレーションのみを行い、実際のパフォーマンス計測はサブベンチマークに委ねられるという明確な役割分担が実現されます。
- **名前付け**: サブベンチマークの名前も、親ベンチマークの名前とスラッシュ(`/`)で区切られて結合されます（例: `BenchmarkFoo/SubBenchmarkBar`）。

### `matchBenchmarks`フラグの変更

`matchBenchmarks`フラグの説明が「regular expression to select benchmarks to run」から「regular expression per path component to select benchmarks to run」に変更されました。これは、サブベンチマークの名前がパスのような階層構造を持つようになったため、正規表現がそのパスの各コンポーネントに対して適用されることを示唆しています。これにより、より柔軟なベンチマークのフィルタリングが可能になります。

## コアとなるコードの解説

### `src/testing/benchmark.go`の変更点

-   `matchBenchmarks`フラグの説明が更新され、サブベンチマークの階層的な名前付けに対応するようになりました。
-   `runBenchmarksInternal`関数内で、ベンチマークを実行する際に`b.runBench`の代わりに`b.Run`が呼び出されるようになりました。これは、内部的な呼び出しも新しいパブリックAPIに統一されたことを意味します。
-   `*B.runBench`メソッドが`*B.Run`にリネームされ、コメントも更新されてパブリックAPIとしての役割が明確化されました。特に、「A benchmark that calls Run at least once will not be measured itself.」という記述が追加され、親ベンチマークがサブベンチマークを呼び出す場合の計測動作が明記されました。
-   `Benchmark`関数のコメントに、`f`が`Run`を呼び出す場合の動作に関する説明が追加されました。

### `src/testing/sub_test.go`の変更点

-   このファイルは、以前は`*T.Run`と`*B.Run`のスタブ実装を含んでいましたが、今回のコミットでこれらのスタブが削除されました。これは、`testing.go`と`benchmark.go`で実際の`Run`メソッドがパブリックに公開されたため、スタブが不要になったことを示しています。

### `src/testing/testing.go`の変更点

-   `*T.run`メソッドが`*T.Run`にリネームされ、コメントも更新されてパブリックAPIとしての役割が明確化されました。
-   `RunTests`関数内で、テストを実行する際に`t.run`の代わりに`t.Run`が呼び出されるようになりました。これも、内部的な呼び出しが新しいパブリックAPIに統一されたことを意味します。

これらの変更により、`testing`パッケージのユーザーは、`t.Run("subtest name", func(t *testing.T) { ... })`や`b.Run("subbenchmark name", func(b *testing.B) { ... })`といった形式で、テストやベンチマークをより構造化して記述できるようになりました。これにより、テストコードの可読性、保守性、および柔軟性が大幅に向上します。

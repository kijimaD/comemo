# [インデックス 19824] ファイルの概要

このコミットは、Go言語のツールチェインの一部であるリンカ（`liblink`）内の`src/liblink/obj5.c`ファイルに対する変更です。`obj5.c`は、ARMアーキテクチャ向けのオブジェクトファイル処理を担当しており、特に命令の変換や最適化、アーキテクチャ固有のレジスタ操作に関連する処理が含まれています。このファイルは、GoプログラムがARMプロセッサ上で正しく動作するための低レベルなコード生成とリンクの過程で重要な役割を果たします。

## 変更の背景

このコミットの背景には、ARMアーキテクチャにおけるTLS (Thread Local Storage) ベースアドレスの取得方法と、Goリンカによる特定の命令変換の挙動があります。

Go言語のランタイムは、スレッドローカルストレージ（TLS）を利用して、各ゴルーチン（またはスレッド）が独自のデータにアクセスできるようにします。ARMプロセッサ、特にARMv7より古い世代のプロセッサでは、TLSベースアドレスを取得するために`MRC` (Move to ARM Register from Coprocessor) 命令が使用されることがあります。この`MRC`命令は、コプロセッサ（通常はCP15）から特定のシステムレジスタ（TLSベースアドレスを保持するレジスタなど）の値を読み取り、汎用レジスタに書き込みます。

Goリンカは、古いARMプロセッサとの互換性を保つため、特定の`MRC`命令を`BL` (Branch with Link) 命令に変換することがあります。この`BL`命令は、`runtime.read_tls_fallback`というフォールバック関数を呼び出すために使用されます。`BL`命令による関数呼び出しの一般的な規約では、関数の戻り値は`R0`レジスタに格納されることが期待されます。

問題は、元の`MRC`命令がTLSベースアドレスを`R0`以外のレジスタに書き込むように指定されているにもかかわらず、リンカがそれを`BL`命令に変換した場合に発生します。この場合、`runtime.read_tls_fallback`関数が`R0`に結果を返しても、元の`MRC`命令が期待していたレジスタとは異なるため、データが正しく取得されず、ランタイムエラーや予期せぬ動作につながる可能性があります。

このコミットは、このような潜在的な問題を未然に防ぐために、`MRC`命令が`R0`以外のレジスタに書き込もうとしている場合にリンカが警告を発するように変更を加えるものです。これにより、開発者はコンパイル時にこの潜在的な不整合を認識し、修正することができます。

また、`tlsfallback`シンボルのルックアップ（`linklookup`関数によるシンボル検索）は比較的高コストな処理であるため、このルックアップを一度だけ行うように最適化することで、リンカのパフォーマンスをわずかに向上させることも目的としています。

## 前提知識の解説

### TLS (Thread Local Storage)

TLSは、マルチスレッドプログラミングにおいて、各スレッドがそれぞれ独立したデータを持つための仕組みです。グローバル変数や静的変数は通常、プロセス内のすべてのスレッドで共有されますが、TLSを使用すると、同じ変数名であってもスレッドごとに異なる値を保持できます。Go言語では、ゴルーチンごとに独立したスタックやスケジューリングコンテキストを持つため、TLSはランタイムの内部で重要な役割を果たします。

### ARMアーキテクチャ

ARM (Advanced RISC Machine) は、モバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。ARMプロセッサには多くの世代があり、命令セットや機能が異なります。このコミットでは、特にARMv7より古いプロセッサ（`ctxt->goarm < 7`）が対象となっています。これらの古いプロセッサでは、TLSベースアドレスの取得に特定の命令シーケンスが必要となる場合があります。

### MRC命令

`MRC` (Move to ARM Register from Coprocessor) 命令は、ARMアーキテクチャの命令セットの一部です。この命令は、ARMプロセッサの汎用レジスタとコプロセッサ（CP0からCP15まで）のレジスタ間でデータを転送するために使用されます。TLSの文脈では、`MRC`命令はCP15（システム制御コプロセッサ）の特定のレジスタからスレッドポインタやTLSベースアドレスを読み取るために使われることがあります。

`MRC`命令の一般的な形式は以下の通りです:
`MRC{cond} p<cp_num>, <opcode1>, <Rd>, <Cn>, <Cm>{, <opcode2>}`
ここで、`<Rd>`はデータを書き込むARM汎用レジスタ（R0-R15）を指定します。

### BL命令

`BL` (Branch with Link) 命令は、ARMアーキテクチャにおける関数呼び出しに使用される分岐命令です。この命令は、現在のプログラムカウンタ（PC）の次の命令のアドレスをリンクレジスタ（`LR`、通常はR14）に保存し、指定されたアドレスにジャンプします。関数が実行を終えると、`LR`レジスタに保存されたアドレスに戻ることで、呼び出し元に制御が戻ります。ARMの標準的な呼び出し規約（AAPCS: ARM Architecture Procedure Call Standard）では、関数の戻り値は`R0`レジスタに格納されることが期待されます。

### Goリンカ (`liblink`)

Go言語のビルドプロセスにおいて、リンカは非常に重要な役割を担っています。`liblink`は、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイル（またはライブラリ）を生成します。この過程で、リンカはシンボルの解決、アドレスの再配置、そして特定のアーキテクチャやプラットフォームに合わせた命令の変換や最適化を行うことがあります。今回のコミットは、このリンカの命令変換ロジックの一部を修正するものです。

### `runtime.read_tls_fallback`

これはGoランタイム内部の関数で、古いARMプロセッサなど、特定の環境でTLSベースアドレスを直接効率的に取得できない場合に、そのフォールバックとしてTLSベースアドレスを読み取る役割を担います。リンカが特定の`MRC`命令をこの関数への`BL`呼び出しに変換するのは、このような互換性維持のためです。

## 技術的詳細

このコミットの技術的な核心は、`src/liblink/obj5.c`内の`progedit`関数にあります。`progedit`関数は、Goリンカが個々のプログラム命令（`Prog`構造体で表現される）を処理し、必要に応じて変換や最適化を行う場所です。

変更は主に`AMRC`命令（`MRC`命令に対応）の処理ブロック内で行われています。

1.  **`tlsfallback`シンボルのルックアップの最適化**:
    変更前は、`tlsfallback = linklookup(ctxt, "runtime.read_tls_fallback", 0);`という行が、`if(ctxt->goarm < 7 && ...)`の条件ブロック内にありました。これは、条件が満たされるたびに`runtime.read_tls_fallback`シンボルをリンカのシンボルテーブルから検索し直すことを意味します。シンボルルックアップはI/Oやハッシュテーブル検索を伴う可能性があり、コストがかかる処理です。
    変更後は、`tlsfallback`変数が`static LSym *tlsfallback;`として宣言されました。これにより、`tlsfallback`は静的変数となり、プログラムの実行中に一度だけ初期化（つまり、`linklookup`が一度だけ呼び出される）されます。その後の`progedit`呼び出しでは、既にルックアップされた`tlsfallback`の値が再利用されるため、パフォーマンスが向上します。

2.  **`MRC`命令の`R0`書き込みチェックと警告**:
    リンカは、特定の`MRC`命令（`p->to.offset`が`0xee1d0f70`と`0xffff0fff`のマスクで一致するTLSベースアドレス取得命令）を、古いARMプロセッサ（`ctxt->goarm < 7`）向けに`runtime.read_tls_fallback`への`BL`命令に変換します。
    この変換の前に、新しいチェックが追加されました: `if ((p->to.offset & 0xf000) != 0)`。
    *   `p->to.offset`は、`MRC`命令のエンコードされた形式の一部を含んでいます。
    *   `0xf000`というマスクは、`MRC`命令のビット12-15を抽出するために使用されます。ARMの`MRC`命令フォーマットにおいて、これらのビットは通常、結果を書き込むデスティネーションレジスタ`Rd`を指定します。
    *   `Rd`が`R0`である場合、これらのビットは`0000`となり、`p->to.offset & 0xf000`の結果は`0`になります。
    *   したがって、`if ((p->to.offset & 0xf000) != 0)`という条件は、「`MRC`命令が`R0`以外のレジスタに結果を書き込もうとしている」ことを意味します。
    この条件が真の場合、リンカは`ctxt->diag`関数を呼び出して警告メッセージを出力します。警告メッセージは「TLS MRC instruction must write to R0 as it might get translated into a BL instruction」（TLS MRC命令は、BL命令に変換される可能性があるため、R0に書き込む必要があります）という内容です。これは、`BL`命令の呼び出し規約と、元の`MRC`命令のレジスタ指定との間の潜在的な不整合を開発者に知らせるものです。

この変更により、Goリンカは、古いARMプロセッサ向けのTLSベースアドレス取得において、より堅牢なコード生成を行うようになります。

## コアとなるコードの解説

1.  **`static LSym *tlsfallback;`**:
    `tlsfallback`変数の宣言に`static`キーワードが追加されました。これにより、この変数は`progedit`関数が呼び出されるたびに再初期化されるのではなく、プログラムの実行期間中に一度だけ初期化される静的変数となります。結果として、`linklookup(ctxt, "runtime.read_tls_fallback", 0)`の呼び出しが一度しか行われなくなり、リンカのパフォーマンスが向上します。

2.  **`if ((p->to.offset & 0xf000) != 0)`**:
    この新しい条件式は、`MRC`命令が結果を`R0`レジスタに書き込むかどうかをチェックします。
    *   `p->to.offset`は、処理中の`MRC`命令のエンコードされたバイナリ表現の一部を含んでいます。
    *   `0xf000`は16進数で、バイナリでは`0000 1111 0000 0000 0000 0000 0000 0000`となります。このマスクは、`MRC`命令のビット12-15（デスティネーションレジスタ`Rd`を指定する部分）を抽出するために使用されます。
    *   ARMの命令セットにおいて、`R0`レジスタは通常、レジスタ番号0で表されます。したがって、`Rd`が`R0`の場合、ビット12-15はすべて`0`になります。
    *   この条件式が真となるのは、`p->to.offset`のビット12-15のいずれかが`1`である場合、つまり`MRC`命令が`R0`以外のレジスタに書き込もうとしている場合です。

3.  **`ctxt->diag("%L: TLS MRC instruction must write to R0 as it might get translated into a BL instruction", p->lineno);`**:
    上記の条件が真の場合、この行が実行され、リンカは診断メッセージ（警告）を出力します。
    *   `%L`は、メッセージが発生したソースコードの行番号（`p->lineno`）に置き換えられます。
    *   警告メッセージは、`MRC`命令が`BL`命令に変換される可能性があるため、結果を`R0`に書き込むべきであるということを明確に伝えています。これは、`BL`命令の呼び出し規約が戻り値を`R0`に期待するため、不整合を避けるための重要な警告です。

4.  **`if(ctxt->goarm < 7)`ブロックの移動と変更**:
    元のコードでは、`if(ctxt->goarm < 7 && ...)`という単一の条件で`MRC`命令の変換と`tlsfallback`のルックアップが行われていました。
    変更後、`MRC`命令の`R0`書き込みチェックは、`ctxt->goarm < 7`の条件とは独立して、特定の`MRC`命令が検出された直後に行われるようになりました。
    そして、`ctxt->goarm < 7`の条件が満たされた場合にのみ、`BL runtime.read_tls_fallback(SB)`への変換ロジックが実行されます。このブロック内で、`tlsfallback`が`nil`の場合にのみ`linklookup`が呼び出されるようになり、`static`変数と合わせてルックアップの最適化が実現されています。

これらの変更により、Goリンカは、古いARMプロセッサ向けのTLSベースアドレス取得において、より堅牢なコード生成を行うようになり、潜在的なランタイムエラーをコンパイル時に検出できるようになりました。

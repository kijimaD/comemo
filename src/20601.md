# [インデックス 20601] ファイルの概要

このコミットは、Goランタイムにおける`runtime.Breakpoint`関数のARMv5アーキテクチャでの動作を修正するものです。具体的には、デバッガが認識するソフトウェアブレークポイント命令を、既存の誤った命令から、より適切で汎用的な「未定義命令」に置き換えることで、デバッグ時の挙動を改善しています。

## 変更の背景

この変更は、GoのIssue #8775を解決するために行われました。`runtime.Breakpoint()`関数は、プログラムの実行中にデバッガが介入できるように、意図的にブレークポイントを発生させるためのGoランタイム関数です。しかし、ARMv5アーキテクチャにおいて、この関数が期待通りに動作しない問題がありました。

従来のGoランタイムでは、ARMアーキテクチャ（特にARMv5）でのブレークポイントの実装において、`BKPT 0x0001`というコメントが付与された`0xe1200071`という命令が使用されていました。しかし、この`0xe1200071`という命令は、実際には`MOV R0, R1`というレジスタ間データ転送命令であり、デバッガが認識するブレークポイント命令ではありませんでした。このため、デバッガが`runtime.Breakpoint()`で設定されたブレークポイントで停止せず、デバッグ作業が困難になるという問題が発生していました。

このコミットは、この問題を解決し、ARMアーキテクチャ全般で`runtime.Breakpoint()`が正しく機能するように、デバッガ（特にGDB）がソフトウェアブレークポイントとして認識する「未定義命令」に置き換えることを目的としています。

## 前提知識の解説

*   **`runtime.Breakpoint()`**: Go言語の標準ライブラリ`runtime`パッケージに含まれる関数で、プログラムの実行中にデバッガが介入するためのブレークポイントを意図的に発生させます。通常、デバッグビルドでのみ有効になり、本番環境では最適化によって削除されるか、何もしないように実装されます。
*   **ARMアーキテクチャ**: Advanced RISC Machineの略で、モバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。ARMv5は、古い世代のARMプロセッサアーキテクチャの一つです。
*   **ブレークポイント (Breakpoint)**: デバッグ中にプログラムの実行を一時停止させるための指定点です。これにより、開発者はプログラムの現在の状態（変数、レジスタ、メモリなど）を検査し、問題の原因を特定できます。
*   **ソフトウェアブレークポイント**: プログラムコード自体に特定の命令を埋め込むことで実現されるブレークポイントです。デバッガは、この特殊な命令が実行されると、プログラムの実行を停止します。
*   **ハードウェアブレークポイント**: CPUのデバッグ機能を利用して、特定のアドレスへのアクセスや命令の実行を監視し、ブレークポイントを発生させる方法です。通常、ソフトウェアブレークポイントよりも数が限られます。
*   **未定義命令 (Undefined Instruction)**: CPUが認識しない、または実行できない命令のことです。このような命令が実行されると、CPUは「未定義命令例外」を発生させます。デバッガは、この例外を捕捉することで、ソフトウェアブレークポイントとして機能させることができます。
*   **`WORD`ディレクティブ (アセンブリ)**: アセンブリ言語において、指定された値をワード（通常は32ビット）としてメモリに直接配置するためのディレクティブです。ここでは、ARM命令のバイナリ表現を直接埋め込むために使用されています。
*   **`BKPT`命令**: ARMアーキテクチャにおける標準的なブレークポイント命令です。`BKPT #imm`の形式で、`imm`はデバッガに渡される任意の即値です。
*   **Google Native Client (NaCl)**: ウェブブラウザ内でネイティブコードを安全に実行するための技術です。NaCl環境では、セキュリティ上の理由から、通常のシステムコールや命令の使用が制限される場合があります。そのため、ブレークポイントの実装も通常の環境とは異なる場合があります。

## 技術的詳細

このコミットの核心は、`src/runtime/asm_arm.s`ファイル内の`runtime·breakpoint`関数の実装変更にあります。この関数は、Goプログラムが`runtime.Breakpoint()`を呼び出した際に、実際にCPUレベルでブレークポイントをトリガーするアセンブリコードを含んでいます。

変更前は、非NACL環境のARMアーキテクチャにおいて、以下の命令が使用されていました。

```assembly
WORD $0xe1200071 // BKPT 0x0001
```

ここで、`0xe1200071`という16進数値は、ARMの32ビット命令のバイナリ表現です。コメントでは`BKPT 0x0001`とされていますが、実際の命令デコード結果は`MOV R0, R1`（レジスタR1の値をR0に移動する）です。これは、デバッガがブレークポイントとして認識する命令ではないため、`runtime.Breakpoint()`が期待通りに機能しない原因となっていました。

変更後は、この命令が以下の新しい命令に置き換えられました。

```assembly
WORD $0xe7f001f0 // undefined instruction that gdb understands is a software breakpoint
```

新しい命令`0xe7f001f0`は、ARMアーキテクチャにおいて「未定義命令」として扱われます。CPUがこの命令を実行しようとすると、未定義命令例外が発生します。GDBのようなデバッガは、この未定義命令例外を捕捉するように設定されており、これをソフトウェアブレークポイントとして解釈し、プログラムの実行を停止させることができます。

この変更により、以下の利点が得られます。

1.  **デバッグの信頼性向上**: `runtime.Breakpoint()`が意図した通りにデバッガをトリガーするようになり、ARMv5を含むARMアーキテクチャでのデバッグ作業がより信頼性の高いものになります。
2.  **汎用性**: 特定の`BKPT`命令の即値に依存するのではなく、デバッガが認識する汎用的な未定義命令を使用することで、将来的な互換性や異なるデバッガとの連携が容易になる可能性があります。
3.  **問題の根本的解決**: 誤った命令がブレークポイントとして機能しないという根本的な問題が解決されます。

なお、`GOOS_nacl`（Google Native Client）環境では、引き続き`0xe125be7f`（`BKPT 0x5bef, NACL_INSTR_ARM_BREAKPOINT`）が使用されます。これは、NaClのサンドボックス環境における特殊な要件に対応するためと考えられます。

## コアとなるコードの変更箇所

`src/runtime/asm_arm.s`ファイル内の`runtime·breakpoint`関数の実装が変更されています。

```diff
--- a/src/runtime/asm_arm.s
+++ b/src/runtime/asm_arm.s
@@ -96,7 +96,7 @@ TEXT runtime·breakpoint(SB),NOSPLIT,$0-0
 #ifdef GOOS_nacl
  WORD $0xe125be7f // BKPT 0x5bef, NACL_INSTR_ARM_BREAKPOINT
 #else
- WORD $0xe1200071 // BKPT 0x0001
+ WORD $0xe7f001f0 // undefined instruction that gdb understands is a software breakpoint
 #endif
  RET
```

## コアとなるコードの解説

このコードスニペットは、`runtime·breakpoint`というアセンブリ関数の一部です。

*   `TEXT runtime·breakpoint(SB),NOSPLIT,$0-0`: `runtime·breakpoint`という名前の関数を定義しています。`SB`はStatic Baseレジスタ、`NOSPLIT`はスタックフレームを分割しないことを示し、`$0-0`はスタックフレームサイズと引数サイズが0であることを示します。
*   `#ifdef GOOS_nacl`: これはプリプロセッサディレクティブで、`GOOS_nacl`が定義されている場合（つまり、Google Native Client向けにビルドされている場合）に続くコードブロックがコンパイルされます。
    *   `WORD $0xe125be7f // BKPT 0x5bef, NACL_INSTR_ARM_BREAKPOINT`: NaCl環境では、`0xe125be7f`という命令が使用されます。これは`BKPT 0x5bef`に相当し、NaCl特有のブレークポイントメカニズムに対応しています。
*   `#else`: `GOOS_nacl`が定義されていない場合（通常のARM環境の場合）に続くコードブロックがコンパイルされます。
    *   `- WORD $0xe1200071 // BKPT 0x0001`: 変更前の行です。`0xe1200071`という命令が使用されていました。コメントでは`BKPT 0x0001`とされていますが、前述の通り、これは実際には`MOV R0, R1`命令であり、デバッガがブレークポイントとして認識しませんでした。
    *   `+ WORD $0xe7f001f0 // undefined instruction that gdb understands is a software breakpoint`: 変更後の行です。`0xe7f001f0`という命令が使用されます。この命令はARMアーキテクチャでは未定義命令であり、GDBのようなデバッガがこれをソフトウェアブレークポイントとして認識し、例外を捕捉して実行を停止させます。
*   `RET`: 関数からのリターン命令です。

この変更により、非NaCl環境のARMアーキテクチャにおいて、`runtime.Breakpoint()`が正しくデバッガをトリガーするようになり、デバッグの利便性が向上しました。

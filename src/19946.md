# [インデックス 19946] ファイルの概要

このコミットは、Goランタイムにおけるメモリ割り当て関数 `mal` および `malloc`、そしてガベージコレクション (GC) 関連のフラグである `FlagNoGC` と `FlagNoInvokeGC` を削除するものです。これにより、ランタイムのメモリ管理メカニズムが簡素化され、より統一された `runtime·mallocgc` 関数への移行が促進されます。

## 元コミット内容

Goランタイムから、メモリ割り当て関数 `mal` および `malloc`、そしてガベージコレクション (GC) 関連のフラグ `FlagNoGC` と `FlagNoInvokeGC` を削除します。

`FlagNoGC` は現在使用されていません。
`FlagNoInvokeGC` は、`g0` ゴルーチン上やロックを保持している間はGCを呼び出さないため、不要です。
`mal` と `malloc` は使用箇所が非常に少なく、それぞれの関数が使用する正確なフラグのセットやそれらの違いを覚えるのが困難でした。
さらに、将来的にはすべてのメモリ割り当てに対して正確な型情報を提供する必要があり、`mal` や `malloc` はこれをサポートしていません。

## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理とガベージコレクションの進化があります。Dmitriy Vyukov氏によるこの変更は、以下の複数の理由に基づいています。

1.  **未使用フラグの削除**: `FlagNoGC` は、もはやランタイム内で使用されていないため、コードベースから削除されました。これにより、コードの複雑性が軽減され、保守性が向上します。
2.  **冗長なフラグの削除**: `FlagNoInvokeGC` は、特定の状況下（特に`g0`ゴルーチン上やランタイムがロックを保持している間）ではGCが呼び出されないというランタイムの設計上の特性により、その存在意義が失われました。GCがこれらの状況で実行されないことが保証されているため、明示的にGCの呼び出しを禁止するフラグは不要と判断されました。
3.  **メモリ割り当てAPIの統一と簡素化**: `mal` と `malloc` は、`runtime·mallocgc` と比較して使用頻度が低く、それぞれが異なるフラグの組み合わせを持つため、開発者にとって混乱を招く可能性がありました。これらの関数を削除し、より汎用的な `runtime·mallocgc` に統一することで、メモリ割り当てインターフェースが簡素化され、一貫性が向上します。
4.  **型情報の重要性の増大**: GoのGCは、割り当てられたオブジェクトの型情報に基づいてポインタをスキャンし、到達可能性を判断します。将来的にすべてのメモリ割り当てに対して正確な型情報を提供する必要があるというランタイムの方向性において、`mal` や `malloc` のような型情報を持たない、あるいは限定的な型情報しか扱えない割り当て関数は、その目的に合致しなくなっていました。`runtime·mallocgc` は型情報を受け取る引数を持つため、この将来の要件に対応できます。

これらの変更は、Goランタイムのメモリ管理をより堅牢で、効率的で、将来の拡張性に対応できるようにするための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理する低レベルのシステムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当て、ガベージコレクション、チャネル通信などが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。

2.  **ガベージコレクション (GC)**:
    Goのガベージコレクタは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能（参照されていない）になったメモリ領域を自動的に解放するシステムです。GoのGCは並行（concurrent）かつ低遅延（low-latency）を目指して設計されており、プログラムの実行と同時に動作することで、アプリケーションの一時停止（Stop-the-World）時間を最小限に抑えます。

3.  **メモリ割り当て関数 (`runtime·mallocgc`, `mal`, `malloc`)**:
    *   `runtime·mallocgc`: Goランタイムにおける主要なメモリ割り当て関数です。`size`（割り当てるバイト数）、`typ`（割り当てるオブジェクトの型情報）、`flag`（割り当てに関する追加フラグ）の3つの引数を取ります。`typ`引数があるため、GCがオブジェクトのポインタを正確にスキャンするために必要な型情報を提供できます。
    *   `mal` および `malloc`: これらは、`runtime·mallocgc` のより限定的なラッパー関数、または古いバージョンのメモリ割り当て関数でした。コミットメッセージによると、これらは `runtime·mallocgc` の特定のフラグの組み合わせを内部的に使用していましたが、その違いが不明瞭であり、型情報も直接受け取らないため、汎用性に欠けていました。

4.  **GCフラグ (`FlagNoGC`, `FlagNoInvokeGC`, `FlagNoScan`, `FlagNoProfiling`, `FlagNoZero`)**:
    メモリ割り当て時に、GCの動作を制御するためのフラグです。
    *   `FlagNoGC`: このコミットで削除されたフラグの一つ。かつては、GCの対象外とするメモリ割り当てを示すために使われた可能性がありますが、コミット時点では未使用でした。
    *   `FlagNoInvokeGC`: このコミットで削除されたフラグの一つ。GCの呼び出しを禁止する目的で使われていましたが、特定の状況下ではGCが自動的に呼び出されないため、冗長と判断されました。
    *   `FlagNoScan`: 割り当てられたオブジェクトをGCがスキャンする必要がないことを示します（例：ポインタを含まない純粋なデータ構造）。
    *   `FlagNoProfiling`: メモリプロファイリングの対象外とすることを示します。
    *   `FlagNoZero`: 割り当てられたメモリをゼロクリアしないことを示します。通常、Goは新しく割り当てられたメモリをゼロクリアしますが、このフラグがあるとそれをスキップします。

5.  **`g0` ゴルーチン**:
    Goランタイムには、通常のユーザーゴルーチンとは別に、特別なゴルーチンが存在します。`g0` は、各OSスレッド（M: Machine）に紐付けられたランタイムの内部処理（スケジューリング、GCのStop-the-Worldフェーズ、システムコールなど）を実行するためのゴルーチンです。`g0` は、ユーザーゴルーチンとは異なるスタックを持ち、GCの対象外となるような低レベルの操作を行います。

6.  **ロックの保持**:
    Goランタイムの内部では、複数のゴルーチンやOSスレッドが同時に動作するため、共有データ構造へのアクセスを保護するためにロック（ミューテックスなど）が頻繁に使用されます。ランタイムが重要なロックを保持している間は、GCのような時間のかかる操作を避けるのが一般的です。これは、デッドロックを防ぎ、ランタイムの応答性を維持するためです。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのメモリ管理とGCの内部動作における重要な変更点を示しています。

1.  **`mal` および `malloc` の廃止と `runtime·mallocgc` への統一**:
    以前のGoランタイムには、`runtime·mallocgc` の他に `runtime·mal` と `runtime·malloc` というメモリ割り当て関数が存在しました。
    *   `runtime·mal(n)` は、`runtime·mallocgc(n, nil, 0)` と同等で、型情報なしでメモリを割り当て、GCスキャンやGC呼び出しの抑制を行わないシンプルな割り当てでした。
    *   `runtime·malloc(size)` は、`runtime·mallocgc(size, nil, FlagNoInvokeGC)` と同等で、型情報なしでメモリを割り当て、GCの呼び出しを抑制するフラグがデフォルトで付与されていました。
    このコミットでは、これらの関数が削除され、すべての内部メモリ割り当てが `runtime·mallocgc` に統一されました。これにより、ランタイムコード全体でメモリ割り当てのセマンティクスが明確になり、どの割り当てがGCの対象となるか、どのような特性を持つかが一目でわかるようになります。特に、`runtime·mallocgc` が型情報 (`Type *typ`) を引数として受け取るため、将来的にすべての割り当てに正確な型情報を付与するという目標に合致します。

2.  **`FlagNoGC` の削除**:
    このフラグは、特定のメモリ領域をGCの対象から除外するために使われていた可能性がありますが、コミット時点ではもはや使用されていませんでした。未使用のコードやフラグを削除することは、コードベースの肥大化を防ぎ、理解を容易にし、潜在的なバグのリスクを減らす上で重要です。

3.  **`FlagNoInvokeGC` の削除とGC呼び出しロジックの変更**:
    `FlagNoInvokeGC` は、メモリ割り当て時にGCの自動呼び出しを抑制するためのフラグでした。しかし、コミットメッセージにあるように、Goランタイムは既に `g0` ゴルーチン上や重要なロックを保持している間はGCを呼び出さないように設計されています。これは、GCがこれらの低レベルの操作を妨げたり、デッドロックを引き起こしたりするのを防ぐためです。
    この変更に伴い、`src/pkg/runtime/malloc.go` 内の `gomallocgc` 関数におけるGC呼び出しの条件が変更されました。
    変更前: `if flags&flagNoInvokeGC == 0 && memstats.heap_alloc >= memstats.next_gc { gogc(0) }`
    変更後: `if memstats.heap_alloc >= memstats.next_gc { gogc(0) }`
    これにより、`FlagNoInvokeGC` のチェックが削除され、GCの呼び出しは純粋にヒープの使用量 (`memstats.heap_alloc`) が次のGCトリガー閾値 (`memstats.next_gc`) を超えたかどうかに基づいて行われるようになりました。これは、GCの呼び出し抑制が、フラグではなくランタイムの内部状態と設計によって適切に管理されていることを示しています。

4.  **メモリ割り当ての透明性の向上**:
    `mal` や `malloc` のような抽象化された割り当て関数を削除し、`runtime·mallocgc` に一本化することで、ランタイム内のすべてのメモリ割り当てが、GCの挙動に対してより透明になります。開発者やデバッガは、どの割り当てがGCによってスキャンされるべきか、いつGCがトリガーされる可能性があるかを、より容易に理解できるようになります。

これらの変更は、Goランタイムのメモリ管理システムをより洗練させ、将来のGCアルゴリズムの改善や、より高度なメモリプロファイリング機能の実装に向けた基盤を強化するものです。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goランタイムのメモリ割り当てとガベージコレクションの内部インターフェースを簡素化し、統一することにあります。

1.  **`mal` および `malloc` 関数の削除と置き換え**:
    `src/pkg/runtime/malloc.c` から `runtime·mal` と `runtime·malloc` の実装が完全に削除されました。これらの関数を呼び出していたすべての箇所（`src/pkg/runtime/cgo/callbacks.c`, `src/pkg/runtime/env_posix.c`, `src/pkg/runtime/panic.c`, `src/pkg/runtime/parfor.c`, `src/pkg/runtime/proc.c`, `src/pkg/runtime/runtime.c`, `src/pkg/runtime/time.goc` など）では、代わりに `runtime·mallocgc(size, nil, 0)` または `runtime·mallocgc(size, nil, FlagNoScan)` のように、`runtime·mallocgc` が直接使用されるようになりました。
    この変更のポイントは、`runtime·mallocgc` が `Type *typ` 引数を持つことです。以前の `mal` や `malloc` はこの引数を持たず、型情報なしでメモリを割り当てていました。`nil` を渡すことで、GCがそのメモリ領域をポインタとしてスキャンしないことを示します（これは、割り当てられたメモリが純粋なデータであり、Goオブジェクトへのポインタを含まない場合に適切です）。これにより、すべてのメモリ割り当てが `runtime·mallocgc` を通るようになり、将来的な型ベースのGC最適化やデバッグが容易になります。

2.  **`FlagNoGC` および `FlagNoInvokeGC` フラグの削除**:
    `src/pkg/runtime/malloc.h` から `FlagNoGC` と `FlagNoInvokeGC` の定数定義が削除されました。
    *   `FlagNoGC` は、もはやランタイムのどこでも使用されていなかったため、単に削除されました。これは、コードのデッドコード削除とクリーンアップの一環です。
    *   `FlagNoInvokeGC` は、GCの自動呼び出しを抑制する目的で使用されていましたが、`src/pkg/runtime/malloc.go` 内の `gomallocgc` 関数におけるGC呼び出しの条件式から、このフラグのチェックが削除されました。これは、GCが `g0` ゴルーチンやロック保持中には呼び出されないというランタイムの設計が確立されたため、このフラグによる明示的な抑制が不要になったことを意味します。GCのトリガーは、ヒープの使用量 (`memstats.heap_alloc`) が閾値 (`memstats.next_gc`) を超えたかどうかにのみ依存するようになりました。これにより、GCの呼び出しロジックが簡素化され、より予測可能になります。

3.  **`FlagNoZero` のビット位置変更**:
    `src/pkg/runtime/malloc.go` と `src/pkg/runtime/malloc.h` で、`FlagNoZero` のビット位置が `1 << 3` から `1 << 2` に変更されました。これは、`FlagNoGC` (以前は `1 << 2`) が削除されたことによるビットシフトです。これにより、フラグのビット割り当てが最適化され、未使用のビットがなくなることで、将来のフラグ追加のためのスペースが確保されます。

これらの変更は、Goランタイムのメモリ管理サブシステムをより効率的で、保守しやすく、将来の進化に対応できるようにするための重要なステップです。特に、すべてのメモリ割り当てを単一の、より強力な `runtime·mallocgc` 関数に集約することで、ランタイムの内部動作の透明性が向上し、GCの精度と性能をさらに向上させるための基盤が強化されました。

## 元コミット内容

Goランタイムから、メモリ割り当て関数 `mal` および `malloc`、そしてガベージコレクション (GC) 関連のフラグ `FlagNoGC` と `FlagNoInvokeGC` を削除します。

`FlagNoGC` は現在使用されていません。
`FlagNoInvokeGC` は、`g0` ゴルーチン上やロックを保持している間はGCを呼び出さないため、不要です。
`mal` と `malloc` は使用箇所が非常に少なく、それぞれの関数が使用する正確なフラグのセットやそれらの違いを覚えるのが困難でした。
さらに、将来的にはすべてのメモリ割り当てに対して正確な型情報を提供する必要があり、`mal` や `malloc` はこれをサポートしていません。

## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理とガベージコレクションの進化があります。Dmitriy Vyukov氏によるこの変更は、以下の複数の理由に基づいています。

1.  **未使用フラグの削除**: `FlagNoGC` は、もはやランタイム内で使用されていないため、コードベースから削除されました。これにより、コードの複雑性が軽減され、保守性が向上します。
2.  **冗長なフラグの削除**: `FlagNoInvokeGC` は、特定の状況下（特に`g0`ゴルーチン上やランタイムがロックを保持している間）ではGCが呼び出されないというランタイムの設計上の特性により、その存在意義が失われました。GCがこれらの状況で実行されないことが保証されているため、明示的にGCの呼び出しを禁止するフラグは不要と判断されました。
3.  **メモリ割り当てAPIの統一と簡素化**: `mal` と `malloc` は、`runtime·mallocgc` と比較して使用頻度が低く、それぞれが異なるフラグの組み合わせを持つため、開発者にとって混乱を招く可能性がありました。これらの関数を削除し、より汎用的な `runtime·mallocgc` に統一することで、メモリ割り当てインターフェースが簡素化され、一貫性が向上します。
4.  **型情報の重要性の増大**: GoのGCは、割り当てられたオブジェクトの型情報に基づいてポインタをスキャンし、到達可能性を判断します。将来的にすべてのメモリ割り当てに対して正確な型情報を提供する必要があるというランタイムの方向性において、`mal` や `malloc` のような型情報を持たない、あるいは限定的な型情報しか扱えない割り当て関数は、その目的に合致しなくなっていました。`runtime·mallocgc` は型情報を受け取る引数を持つため、この将来の要件に対応できます。

これらの変更は、Goランタイムのメモリ管理をより堅牢で、効率的で、将来の拡張性に対応できるようにするための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理する低レベルのシステムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当て、ガベージコレクション、チャネル通信などが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。

2.  **ガベージコレクション (GC)**:
    Goのガベージコレクタは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能（参照されていない）になったメモリ領域を自動的に解放するシステムです。GoのGCは並行（concurrent）かつ低遅延（low-latency）を目指して設計されており、プログラムの実行と同時に動作することで、アプリケーションの一時停止（Stop-the-World）時間を最小限に抑えます。

3.  **メモリ割り当て関数 (`runtime·mallocgc`, `mal`, `malloc`)**:
    *   `runtime·mallocgc`: Goランタイムにおける主要なメモリ割り当て関数です。`size`（割り当てるバイト数）、`typ`（割り当てるオブジェクトの型情報）、`flag`（割り当てに関する追加フラグ）の3つの引数を取ります。`typ`引数があるため、GCがオブジェクトのポインタを正確にスキャンするために必要な型情報を提供できます。
    *   `mal` および `malloc`: これらは、`runtime·mallocgc` のより限定的なラッパー関数、または古いバージョンのメモリ割り当て関数でした。コミットメッセージによると、これらは `runtime·mallocgc` の特定のフラグの組み合わせを内部的に使用していましたが、その違いが不明瞭であり、型情報も直接受け取らないため、汎用性に欠けていました。

4.  **GCフラグ (`FlagNoGC`, `FlagNoInvokeGC`, `FlagNoScan`, `FlagNoProfiling`, `FlagNoZero`)**:
    メモリ割り当て時に、GCの動作を制御するためのフラグです。
    *   `FlagNoGC`: このコミットで削除されたフラグの一つ。かつては、GCの対象外とするメモリ割り当てを示すために使われた可能性がありますが、コミット時点では未使用でした。
    *   `FlagNoInvokeGC`: このコミットで削除されたフラグの一つ。GCの呼び出しを禁止する目的で使われていましたが、特定の状況下ではGCが自動的に呼び出されないため、冗長と判断されました。
    *   `FlagNoScan`: 割り当てられたオブジェクトをGCがスキャンする必要がないことを示します（例：ポインタを含まない純粋なデータ構造）。
    *   `FlagNoProfiling`: メモリプロファイリングの対象外とすることを示します。
    *   `FlagNoZero`: 割り当てられたメモリをゼロクリアしないことを示します。通常、Goは新しく割り当てられたメモリをゼロクリアしますが、このフラグがあるとそれをスキップします。

5.  **`g0` ゴルーチン**:
    Goランタイムには、通常のユーザーゴルーチンとは別に、特別なゴルーチンが存在します。`g0` は、各OSスレッド（M: Machine）に紐付けられたランタイムの内部処理（スケジューリング、GCのStop-the-Worldフェーズ、システムコールなど）を実行するためのゴルーチンです。`g0` は、ユーザーゴルーチンとは異なるスタックを持ち、GCの対象外となるような低レベルの操作を行います。

6.  **ロックの保持**:
    Goランタイムの内部では、複数のゴルーチンやOSスレッドが同時に動作するため、共有データ構造へのアクセスを保護するためにロック（ミューテックスなど）が頻繁に使用されます。ランタイムが重要なロックを保持している間は、GCのような時間のかかる操作を避けるのが一般的です。これは、デッドロックを防ぎ、ランタイムの応答性を維持するためです。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのメモリ管理とGCの内部動作における重要な変更点を示しています。

1.  **`mal` および `malloc` の廃止と `runtime·mallocgc` への統一**:
    以前のGoランタイムには、`runtime·mallocgc` の他に `runtime·mal` と `runtime·malloc` というメモリ割り当て関数が存在しました。
    *   `runtime·mal(n)` は、`runtime·mallocgc(n, nil, 0)` と同等で、型情報なしでメモリを割り当て、GCスキャンやGC呼び出しの抑制を行わないシンプルな割り当てでした。
    *   `runtime·malloc(size)` は、`runtime·mallocgc(size, nil, FlagNoInvokeGC)` と同等で、型情報なしでメモリを割り当て、GCの呼び出しを抑制するフラグがデフォルトで付与されていました。
    このコミットでは、これらの関数が削除され、すべての内部メモリ割り当てが `runtime·mallocgc` に統一されました。これにより、ランタイムコード全体でメモリ割り当てのセマンティクスが明確になり、どの割り当てがGCの対象となるか、どのような特性を持つかが一目でわかるようになります。特に、`runtime·mallocgc` が型情報 (`Type *typ`) を引数として受け取るため、将来的にすべての割り当てに正確な型情報を付与するという目標に合致します。

2.  **`FlagNoGC` の削除**:
    このフラグは、特定のメモリ領域をGCの対象から除外するために使われていた可能性がありますが、コミット時点ではもはや使用されていませんでした。未使用のコードやフラグを削除することは、コードベースの肥大化を防ぎ、理解を容易にし、潜在的なバグのリスクを減らす上で重要です。

3.  **`FlagNoInvokeGC` の削除とGC呼び出しロジックの変更**:
    `FlagNoInvokeGC` は、メモリ割り当て時にGCの自動呼び出しを抑制するためのフラグでした。しかし、コミットメッセージにあるように、Goランタイムは既に `g0` ゴルーチン上や重要なロックを保持している間はGCを呼び出さないように設計されています。これは、GCがこれらの低レベルの操作を妨げたり、デッドロックを引き起こしたりするのを防ぐためです。
    この変更に伴い、`src/pkg/runtime/malloc.go` 内の `gomallocgc` 関数におけるGC呼び出しの条件が変更されました。
    変更前: `if flags&flagNoInvokeGC == 0 && memstats.heap_alloc >= memstats.next_gc { gogc(0) }`
    変更後: `if memstats.heap_alloc >= memstats.next_gc { gogc(0) }`
    これにより、`FlagNoInvokeGC` のチェックが削除され、GCの呼び出しは純粋にヒープの使用量 (`memstats.heap_alloc`) が次のGCトリガー閾値 (`memstats.next_gc`) を超えたかどうかに基づいて行われるようになりました。これは、GCの呼び出し抑制が、フラグではなくランタイムの内部状態と設計によって適切に管理されていることを示しています。

4.  **メモリ割り当ての透明性の向上**:
    `mal` や `malloc` のような抽象化された割り当て関数を削除し、`runtime·mallocgc` に一本化することで、ランタイム内のすべてのメモリ割り当てが、GCの挙動に対してより透明になります。開発者やデバッガは、どの割り当てがGCによってスキャンされるべきか、いつGCがトリガーされる可能性があるかを、より容易に理解できるようになります。

これらの変更は、Goランタイムのメモリ管理システムをより洗練させ、将来のGCアルゴリズムの改善や、より高度なメモリプロファイリング機能の実装に向けた基盤を強化するものです。

1.  **`mal` および `malloc` 関数の削除と置き換え**:
    `src/pkg/runtime/malloc.c` から `runtime·mal` と `runtime·malloc` の実装が完全に削除されました。これらの関数を呼び出していたすべての箇所（`src/pkg/runtime/cgo/callbacks.c`, `src/pkg/runtime/env_posix.c`, `src/pkg/runtime/panic.c`, `src/pkg/runtime/parfor.c`, `src/pkg/runtime/proc.c`, `src/pkg/runtime/runtime.c`, `src/pkg/runtime/time.goc` など）では、代わりに `runtime·mallocgc(size, nil, 0)` または `runtime·mallocgc(size, nil, FlagNoScan)` のように、`runtime·mallocgc` が直接使用されるようになりました。
    この変更のポイントは、`runtime·mallocgc` が `Type *typ` 引数を持つことです。以前の `mal` や `malloc` はこの引数を持たず、型情報なしでメモリを割り当てていました。`nil` を渡すことで、GCがそのメモリ領域をポインタとしてスキャンしないことを示します（これは、割り当てられたメモリが純粋なデータであり、Goオブジェクトへのポインタを含まない場合に適切です）。これにより、すべてのメモリ割り当てが `runtime·mallocgc` を通るようになり、将来的な型ベースのGC最適化やデバッグが容易になります。

2.  **`FlagNoGC` および `FlagNoInvokeGC` フラグの削除**:
    `src/pkg/runtime/malloc.h` から `FlagNoGC` と `FlagNoInvokeGC` の定数定義が削除されました。
    *   `FlagNoGC` は、もはやランタイムのどこでも使用されていなかったため、単に削除されました。これは、コードのデッドコード削除とクリーンアップの一環です。
    *   `FlagNoInvokeGC` は、GCの自動呼び出しを抑制する目的で使用されていましたが、`src/pkg/runtime/malloc.go` 内の `gomallocgc` 関数におけるGC呼び出しの条件式から、このフラグのチェックが削除されました。これは、GCが `g0` ゴルーチンやロック保持中には呼び出されないというランタイムの設計が確立されたため、このフラグによる明示的な抑制が不要になったことを意味します。GCのトリガーは、ヒープの使用量 (`memstats.heap_alloc`) が閾値 (`memstats.next_gc`) を超えたかどうかにのみ依存するようになりました。これにより、GCの呼び出しロジックが簡素化され、より予測可能になります。

3.  **`FlagNoZero` のビット位置変更**:
    `src/pkg/runtime/malloc.go` と `src/pkg/runtime/malloc.h` で、`FlagNoZero` のビット位置が `1 << 3` から `1 << 2` に変更されました。これは、`FlagNoGC` (以前は `1 << 2`) が削除されたことによるビットシフトです。これにより、フラグのビット割り当てが最適化され、未使用のビットがなくなることで、将来のフラグ追加のためのスペースが確保されます。

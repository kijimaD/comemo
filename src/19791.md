# [インデックス 19791] ファイルの概要

このコミットは、Goランタイムの`amd64p32`アーキテクチャ向けアセンブリコードファイルである`src/pkg/runtime/asm_amd64p32.s`に対する変更です。このファイルは、`amd64`プロセッサ上で32ビットポインタを使用する環境（x32 ABI）における、Goランタイムの低レベルな処理、特にスタック管理や関数呼び出し規約に関連するアセンブリルーチンを定義しています。具体的には、ハッシュ計算を行う`runtime·gohash`関数のスタックフレームサイズ調整に関する修正が含まれています。

## 元コミット内容

このコミットの元の内容は、`runtime: round gohash stack frame to multiple of 8 on amd64p32` というタイトルで、`amd64p32`環境において`gohash`関数のスタックフレームを8バイトの倍数に丸めることを目的としています。ポインタが4バイトであっても、スタックにプッシュされるリターンアドレスが適切にアラインされるように、スタックフレームを8バイトの倍数に保つ必要があると説明されています。これはIssue #8379を修正するものです。

## 変更の背景

この変更の背景には、`amd64p32`アーキテクチャにおけるスタックアラインメントの要件があります。`amd64p32`は、64ビットのAMD64命令セットを使用しながらも、32ビットのポインタと整数を使用するABI（Application Binary Interface）です。これにより、64ビット環境の利点を享受しつつ、メモリ使用量を抑えることができます。

しかし、AMD64アーキテクチャ（およびSystem V ABI）では、スタックは通常16バイト境界にアラインされている必要があります。これは、特にSIMD（Single Instruction, Multiple Data）命令（SSEやAVXなど）が16バイトまたは32バイトのデータに作用し、メモリオペランドがアラインされていることを要求するため、パフォーマンスに不可欠です。

関数が呼び出される際、`call`命令は8バイトのリターンアドレスをスタックにプッシュします。これにより、呼び出し前のスタックポインタが16バイトアラインメントであったとしても、関数エントリ時にはスタックポインタが8バイトずれてしまい、アラインメントが崩れる可能性があります。関数は、このアラインメントのずれを修正し、16バイトアラインメントを維持する責任があります。

`runtime·gohash`関数は、Goランタイム内でハッシュ計算を行う重要な関数です。この関数がスタックアラインメントの要件を満たしていない場合、後続の関数呼び出しやデータアクセスにおいて、パフォーマンスの低下や、最悪の場合、クラッシュなどの未定義の動作を引き起こす可能性がありました。Issue #8379は、このスタックアラインメントの問題が原因で発生していたバグを報告していたと考えられます。

このコミットは、`gohash`関数のスタックフレームサイズを調整することで、リターンアドレスがスタックにプッシュされた後でも、スタックが適切にアラインされるようにし、この問題を解決することを目的としています。

## 前提知識の解説

### amd64p32 (x32 ABI)

`amd64p32`、またはx32 ABIは、64ビットのx86-64（AMD64）命令セットを使用しながら、32ビットのポインタ、`long`、`int`型を使用するLinuxのABIです。これにより、64ビットのレジスタと命令セットのパフォーマンス上の利点を活用しつつ、32ビットアプリケーションに近いメモリフットプリントを実現します。標準のx86-64 ABIとは異なり、ポインタサイズが32ビットである点が特徴です。

### スタックフレーム

関数が呼び出されると、その関数専用のメモリ領域がスタック上に確保されます。これをスタックフレームと呼びます。スタックフレームには、関数のローカル変数、引数、レジスタの退避領域、そして呼び出し元に戻るためのリターンアドレスなどが格納されます。

### スタックアラインメント

スタックアラインメントとは、スタックポインタ（通常は`RSP`レジスタ）が特定のバイト数の倍数になるように調整されることです。例えば、16バイトアラインメントとは、スタックポインタの値が常に16の倍数であることを意味します。

スタックアラインメントは、主に以下の理由で重要です。
*   **パフォーマンス**: SIMD命令（SSE, AVXなど）は、特定のバイト境界にアラインされたメモリからのデータアクセスを要求することが多く、アラインされていないアクセスはパフォーマンスの低下や、ハードウェア例外を引き起こす可能性があります。
*   **ABI (Application Binary Interface) 準拠**: オペレーティングシステムやコンパイラが定めるABIでは、関数呼び出し規約の一部としてスタックアラインメントの要件が規定されています。これに準拠しないと、異なるコンパイルユニット間で問題が発生する可能性があります。
*   **データ構造のアラインメント**: 特定のデータ型（例: `long double`やSIMDレジスタに格納されるデータ）は、メモリ上で特定のアラインメントを要求します。スタックが適切にアラインされていれば、これらのデータも正しく配置されます。

### リターンアドレス

関数が呼び出される際、呼び出し元のコードに戻るためのアドレス（リターンアドレス）がスタックにプッシュされます。関数が処理を終えると、このリターンアドレスがスタックからポップされ、CPUの命令ポインタ（`RIP`）にロードされることで、呼び出し元に制御が戻ります。AMD64アーキテクチャでは、リターンアドレスは8バイトです。

### Goアセンブリにおける `TEXT` 命令と `$framesize-$argsize`

Go言語は、一部の低レベルな処理に独自のPlan 9アセンブリを使用します。`TEXT`命令は関数の定義を開始し、その後に続く`$framesize-$argsize`は、その関数のスタックフレームに関する情報を示します。
*   `$framesize`: その関数が使用するローカル変数のためのスタックフレームのサイズ（バイト単位）。これには、レジスタの退避領域なども含まれます。
*   `$argsize`: その関数が引数として受け取るデータの合計サイズ（バイト単位）。

### `NOSPLIT`

Goアセンブリにおける`NOSPLIT`ディレクティブは、その関数がスタックの拡張を必要としないことをコンパイラに伝えます。これは、非常に短い関数や、スタック使用量が固定されている関数で使われ、スタックチェックのオーバーヘッドを避けるために利用されます。

## 技術的詳細

`amd64p32`環境では、ポインタは4バイトですが、基盤となるAMD64アーキテクチャのスタックアラインメント要件は依然として重要です。特に、`call`命令によってスタックにプッシュされるリターンアドレスは8バイトです。

`runtime·gohash`関数の元の定義では、`TEXT runtime·gohash(SB), NOSPLIT, $12-20`となっていました。これは、この関数が12バイトのスタックフレームを使用し、20バイトの引数を受け取ることを意味します。

ここで問題となるのは、スタックフレームサイズが12バイトであることです。
関数が呼び出される直前にスタックポインタが16バイトアラインメントであったと仮定します。
1.  `call`命令が実行され、8バイトのリターンアドレスがスタックにプッシュされます。この時点でスタックポインタは8バイトずれます（`SP % 16 == 8`）。
2.  関数内部で、`gohash`は12バイトのスタックフレームを確保します。これにより、スタックポインタはさらに12バイト減少します。
    `SP_new = SP_old - 8 (return address) - 12 (frame size) = SP_old - 20`
    もし`SP_old`が16の倍数であれば、`SP_new`は`16n - 20`となり、これは16の倍数ではありません（`16n - 16 - 4`なので、`SP_new % 16 == 12`）。
    つまり、関数内部で確保されたスタックフレームの開始アドレスが16バイトアラインメントになっていない可能性があります。

このコミットでは、スタックフレームサイズを12バイトから16バイトに変更しています。
新しい定義は`TEXT runtime·gohash(SB), NOSPLIT, $16-20`です。
この変更により、スタックポインタの挙動は以下のようになります。
1.  `call`命令が実行され、8バイトのリターンアドレスがスタックにプッシュされます。スタックポインタは8バイトずれます（`SP % 16 == 8`）。
2.  関数内部で、`gohash`は16バイトのスタックフレームを確保します。
    `SP_new = SP_old - 8 (return address) - 16 (frame size) = SP_old - 24`
    もし`SP_old`が16の倍数であれば、`SP_new`は`16n - 24`となります。これは`16n - 16 - 8`なので、`SP_new % 16 == 8`となります。
    つまり、関数内部で確保されたスタックフレームの開始アドレスは、リターンアドレスがプッシュされた後のスタックポインタと同じアラインメント（8バイトオフセット）を維持します。これにより、関数がさらに別の関数を呼び出す際に、スタックポインタが再び16バイトアラインメントになるように調整することが容易になります。

この修正は、`gohash`関数が呼び出された際に、その内部で確保されるスタック領域が、後続の操作（特にSIMD命令を使用する可能性のあるコードや、さらに別の関数呼び出し）にとって適切なアラインメントを維持するように保証します。これにより、`amd64p32`環境での安定性とパフォーマンスが向上します。

変更は`src/pkg/runtime/asm_amd64p32.s`ファイルの一箇所のみです。

具体的には、`TEXT runtime·gohash(SB), NOSPLIT, $12-20` の行が `TEXT runtime·gohash(SB), NOSPLIT, $16-20` に変更されています。

## コアとなるコードの解説

変更された行は、`runtime·gohash`関数の定義です。

*   **変更前**: `TEXT runtime·gohash(SB), NOSPLIT, $12-20`
    *   `$12`: この関数が使用するスタックフレームのサイズが12バイトであることを示します。
    *   `$20`: この関数が受け取る引数の合計サイズが20バイトであることを示します。

*   **変更後**: `TEXT runtime·gohash(SB), NOSPLIT, $16-20`
    *   `$16`: この関数が使用するスタックフレームのサイズが16バイトに増加しました。
    *   `$20`: 引数のサイズは変更されていません。

この変更により、`gohash`関数がスタック上に確保するローカルな領域が12バイトから16バイトに拡張されました。これにより、関数が呼び出された際にスタックにプッシュされる8バイトのリターンアドレスと合わせて、スタックポインタが常に8バイトの倍数（または16バイトアラインメントからの8バイトオフセット）を維持するようになります。これは、AMD64アーキテクチャにおけるスタックアラインメントの要件を満たし、特に後続の命令がアラインされたメモリアクセスを期待する場合に、正しい動作と最適なパフォーマンスを保証するために不可欠です。

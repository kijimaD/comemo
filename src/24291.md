## 変更の背景

Go 1は、そのリリース以来、厳格な後方互換性ポリシーを維持してきました。これは、Go 1で書かれたプログラムが、将来のGoのバージョンでもコンパイルされ、実行されることを保証するものです。この互換性ポリシーは、Go言語の安定性と信頼性の基盤となっています。

しかし、言語の特定の「コーナーケース」（稀な状況やエッジケース）においては、この互換性保証が完全に適用できない場合があります。このコミットは、そのようなコーナーケースの一つ、すなわち「埋め込み型に新しいメソッドが追加された際に発生しうるメソッド名の競合」について、`go1compat.html` ドキュメントに明示的な注意書きを追加することを目的としています。

コミットメッセージにある「This is a corner case but it is suggested we call it out. (これは稀なケースだが、言及しておくべきだと提案された)」という記述は、この問題が頻繁に発生するものではないものの、潜在的な互換性破壊のリスクがあるため、開発者に対して事前に情報を提供することが重要であるという判断があったことを示唆しています。`Fixes #11798` は、この変更が特定の課題（Goの内部トラッカーまたはレビューシステム上の課題）に対応するものであることを示しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、Go言語の以下の概念を理解しておく必要があります。

### Goの埋め込み (Embedding)

Go言語では、構造体（struct）内に他の構造体やインターフェースを「埋め込む」ことができます。これは、継承とは異なり、埋め込まれた型のフィールドやメソッドが、あたかも外側の構造体のメンバーであるかのように直接アクセスできるようになる機能です。これにより、コードの再利用性が高まり、より簡潔な記述が可能になります。

例:
```go
type Base struct {
    id int
}

func (b Base) GetID() int {
    return b.id
}

type User struct {
    Base // Base型を埋め込み
    name string
}

func main() {
    u := User{Base: Base{id: 1}, name: "Alice"}
    println(u.GetID()) // User型からBaseのGetIDメソッドに直接アクセス
}
```

### メソッドセット (Method Sets)

Goの型には「メソッドセット」と呼ばれるものがあります。これは、その型が持つすべてのメソッドの集合です。埋め込みが行われると、埋め込まれた型のメソッドは、外側の構造体のメソッドセットに「昇格」されます。つまり、外側の構造体は、埋め込まれた型のメソッドを自身のメソッドであるかのように呼び出すことができます。

### Go 1 互換性 (Go 1 Compatibility)

Go 1互換性ポリシーは、Go言語の最も重要な設計原則の一つです。これは、Go 1で書かれた有効なGoプログラムが、Go 1.xの将来のリリースでもコンパイルされ、同じセマンティクスで実行されることを保証するものです。このポリシーは、Goエコシステムの安定性と、開発者が安心してGoの新しいバージョンにアップグレードできることを保証するために不可欠です。`go1compat.html` は、このポリシーの詳細と、互換性が保証される範囲、および稀な例外について記述した公式ドキュメントです。

### メソッドの競合 (Method Conflicts)

Goでは、同じ名前のメソッドが複数存在する場合に競合が発生します。埋め込みの場合、以下のような状況で競合が発生する可能性があります。

1.  **外側の構造体と埋め込み型で同名のメソッド:** 外側の構造体が自身のメソッドとして定義している名前と、埋め込まれた型から昇格されるメソッドの名前が同じ場合、外側の構造体のメソッドが優先されます。
2.  **複数の埋め込み型で同名のメソッド:** 構造体に複数の型が埋め込まれており、それらの埋め込み型が同じ名前のメソッドを持っている場合、曖昧さが発生し、コンパイルエラーとなります。この場合、外側の構造体で明示的にどちらかのメソッドを呼び出すか、外側の構造体自身で同名のメソッドを定義して競合を解決する必要があります。

このコミットで言及されているのは、特に2番目のケースに関連する、より複雑なシナリオです。

## 技術的詳細

このコミットが警告している技術的詳細は、Go 1互換性ポリシーの限界を示す特定のシナリオです。

問題となるのは、以下の状況です。

1.  ある構造体 `S` が、型 `A` と型 `B` の**両方**を埋め込んでいるとします。
2.  当初、型 `A` には `MethodX` というメソッドが**なく**、型 `B` には `MethodX` というメソッドが**存在していた**とします。この場合、構造体 `S` は型 `B` から `MethodX` を昇格させ、`S.MethodX()` として呼び出すことができます。
3.  Goの将来のバージョンで、**型 `A` に `MethodX` という新しいメソッドが追加された**とします。

このシナリオでは、Go 1互換性ポリシーの観点から問題が生じます。

*   Go 1互換性ポリシーは、既存の型に新しいメソッドを追加することは互換性を破壊しないと一般的に見なしています。なぜなら、既存のコードは新しいメソッドを呼び出さない限り影響を受けないからです。
*   しかし、上記のシナリオでは、型 `A` に `MethodX` が追加されると、構造体 `S` は型 `A` と型 `B` の両方から `MethodX` を昇格させようとします。これにより、`S.MethodX()` の呼び出しが曖昧になり、コンパイルエラーが発生する可能性があります。

このコミットは、この「埋め込まれた型に新しいメソッドが追加された結果、別の埋め込み型との間でメソッド名の競合が発生する」という稀なケースに対して、Go言語が互換性を保証できないことを明示的に述べています。これは、Go 1互換性ポリシーが、言語の進化と既存コードの安定性のバランスを取る上で避けられないトレードオフの一つを示しています。開発者は、このような状況が発生する可能性を認識し、必要に応じてコードを調整する必要があります。

## コアとなるコードの解説

追加されたHTMLの `<li>` 要素は、Go 1互換性ドキュメントの「Methods」セクションに新しい項目として挿入されています。その内容は以下の通りです。

```html
<li>
Methods. As with struct fields, it may be necessary to add methods
to types.
Under some circumstances, such as when the type is embedded in
a struct along with another type,
the addition of the new method may break
the struct by creating a conflict with an existing method of the other
embedded type.
We cannot protect against this rare case and do not guarantee compatibility
should it arise.
</li>
```

この記述は、Go開発者に対して以下の点を伝えています。

1.  **型のメソッド追加の必要性:** 構造体のフィールドと同様に、型にメソッドを追加する必要が生じることがあります。これは言語の進化や機能追加の自然な流れです。
2.  **互換性破壊の可能性:** しかし、特定の状況下では、この新しいメソッドの追加が既存のコードの互換性を破壊する可能性があります。
3.  **具体的な状況:** その特定の状況とは、「型が別の型と一緒に構造体に埋め込まれている場合」です。このとき、埋め込まれた型に新しいメソッドが追加されると、それが「別の埋め込み型の既存のメソッドと競合を引き起こす」可能性があります。
4.  **Goの限界と非保証:** Go言語は、この稀なケースに対して保護を提供することはできず、このような状況が発生した場合の互換性を保証しません。

このドキュメントの追加は、Go言語の設計者たちが、Go 1互換性ポリシーの範囲と限界を明確にしようとしていることを示しています。開発者は、この情報を基に、特に複数の型を埋め込む設計を行う際に、将来的なメソッド名の競合のリスクを考慮に入れるべきです。これは、Goの進化に伴う潜在的な影響を理解し、堅牢なコードを書くための重要な指針となります。

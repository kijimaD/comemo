## 変更の背景

このコミットの主な目的は、Go言語のTLS実装に`tls-unique`チャネルバインディングを導入することです。これはRFC 5929のセクション3で定義されており、アプリケーション層の認証を基盤となるTLS接続に安全に紐付けるためのメカニズムを提供します。

従来のTLS接続では、アプリケーション層での認証（例: OAuthトークン、セッションID）が、その認証が行われた特定のTLSセッションと強く結びついていない場合がありました。これにより、攻撃者が有効な認証情報を傍受し、別のTLSセッションでそれを再利用する「リプレイ攻撃」や「資格情報の再利用」といった脅威が発生する可能性がありました。

`tls-unique`チャネルバインディングは、TLSハンドシェイク中に生成される一意の値をアプリケーションに提供することで、この問題を解決します。この値は、特定のTLSセッションに固有のものであり、アプリケーションはこの値を認証プロセスの一部として使用することで、認証情報が正しいTLSセッションでのみ有効であることを保証できます。

コミットメッセージには、「For resumed sessions this value will be nil because resumption does not include enough context (see https://secure-resumption.com/#channelbindings). This will change in future versions of Go once the TLS master-secret fix has been standardized and implemented.」と記載されています。これは、セッション再開時には`tls-unique`の値が利用できないという既知の制限があることを示しています。これは、セッション再開が完全なハンドシェイクのコンテキストを再構築しないためであり、将来的にTLSのマスターシークレットの取り扱いに関する修正（Extended Master Secret (EMS) 拡張、RFC 7627など）が標準化され実装されることで、この制限が解消される見込みであることが示唆されています。

この変更は、Go言語のTLSスタックのセキュリティを向上させ、より堅牢な認証メカニズムをサポートするための重要なステップです。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を提供するための暗号化プロトコルです。ウェブブラウザとサーバー間のHTTPS通信などで広く利用されています。TLSは、通信のプライバシー、データの完全性、および通信相手の認証を保証します。

TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行われる一連のメッセージ交換です。このプロセス中に、両者はプロトコルバージョン、暗号スイート、圧縮方法などをネゴシエートし、サーバー証明書を交換して認証を行い、共有の「マスターシークレット」を生成します。このマスターシークレットは、その後のセッションキーを導出するために使用され、通信データの暗号化と復号化に利用されます。

### チャネルバインディング (Channel Binding)

チャネルバインディングは、あるセキュリティ層（例: TLS層）で確立されたセキュリティコンテキストを、より上位のアプリケーション層の認証メカニズムに紐付ける技術です。これにより、アプリケーション層での認証が、特定の安全なチャネル上でのみ有効であることを保証できます。

チャネルバインディングの主な目的は、中間者攻撃（Man-in-the-Middle, MitM）やリプレイ攻撃を防ぐことです。例えば、攻撃者がユーザーの認証情報を傍受し、それを別の（攻撃者が制御する）接続で再利用しようとした場合、チャネルバインディングが有効であれば、その認証情報は無効と判断され、攻撃は失敗します。

### RFC 5929 (Channel Bindings for TLS)

RFC 5929は、TLSのためのチャネルバインディングのフレームワークと、いくつかの具体的なチャネルバインディングタイプを定義しています。このコミットで実装されている`tls-unique`はその一つです。

`tls-unique`チャネルバインディングは、TLSハンドシェイクの`Finished`メッセージから導出される一意の値を使用します。`Finished`メッセージは、ハンドシェイクの最後にクライアントとサーバーが互いに送信するメッセージで、ハンドシェイク全体のハッシュを含んでいます。このため、`Finished`メッセージから導出される値は、その特定のTLSハンドシェイクに固有のものとなります。

### TLSセッション再開 (TLS Session Resumption)

TLSセッション再開は、以前に確立されたTLSセッションのセキュリティパラメータ（特にマスターシークレット）を再利用することで、新しいTLSハンドシェイクのオーバーヘッドを削減し、接続確立を高速化するメカニズムです。これにより、ウェブサイトへのアクセスが速くなったり、モバイルアプリケーションのバッテリー消費が抑えられたりします。

セッション再開には主に2つの方法があります。
1.  **セッションID (Session ID)**: サーバーがセッションIDを発行し、クライアントがそれを保存します。再接続時にクライアントがセッションIDを提示し、サーバーが対応するセッション状態を見つけて再利用します。
2.  **セッションチケット (Session Ticket)**: サーバーが暗号化されたセッション状態をセッションチケットとしてクライアントに渡し、クライアントがそれを保存します。再接続時にクライアントがチケットを提示し、サーバーはそれを復号してセッション状態を再構築します。

しかし、セッション再開はセキュリティ上の課題も抱えています。特にTLS 1.2以前では、セッション再開時にマスターシークレットがそのまま再利用されるため、もしマスターシークレットが漏洩した場合、そのマスターシークレットで再開されたすべてのセッションが解読される可能性があります。また、`tls-unique`チャネルバインディングの文脈では、セッション再開は完全なハンドシェイクのコンテキストを再構築しないため、`tls-unique`の値を生成するための十分な情報が不足するという問題がありました。

### Extended Master Secret (EMS) (RFC 7627)

Extended Master Secret (EMS) は、TLS 1.2のセキュリティを強化するために導入された拡張（RFC 7627で定義）です。EMSは、マスターシークレットをハンドシェイク全体のトランスクリプト（交換されたすべてのハンドシェイクメッセージのハッシュ）にバインドします。これにより、マスターシークレットが特定のハンドシェイクに一意に結び付けられ、セッション再開時や再ネゴシエーション時のセキュリティが向上します。

EMSが導入されることで、セッション再開時にも`tls-unique`のようなチャネルバインディングの値を安全に導出するための十分なコンテキストが提供されるようになります。コミットメッセージで言及されている「TLS master-secret fix」は、このEMSのようなメカニズムを指していると考えられます。

## 技術的詳細

このコミットでは、Go言語の`crypto/tls`パッケージに`tls-unique`チャネルバインディングを実装するために、主に以下の変更が行われています。

1.  **`ConnectionState`構造体の拡張**:
    *   `ConnectionState`は、確立されたTLS接続の状態をアプリケーションに公開するための構造体です。
    *   この構造体に`TLSUnique []byte`フィールドが追加されました。このフィールドは、RFC 5929 Section 3で定義される`tls-unique`チャネルバインディングの値を保持します。
    *   コメントには、「For resumed sessions this value will be nil because resumption does not include enough context」と明記されており、セッション再開時にはこの値が設定されないことが示されています。これは、セッション再開が完全なハンドシェイクのコンテキストを再構築しないためです。

2.  **`Conn`構造体の拡張**:
    *   `Conn`は、TLS接続の内部状態を管理する主要な構造体です。
    *   `firstFinished [12]byte`という新しいフィールドが追加されました。この配列は、TLSハンドシェイク中に最初に送信される`Finished`メッセージのハッシュ（`verify_data`）を保持するために使用されます。この値が`tls-unique`チャネルバインディングのソースとなります。

3.  **ハンドシェイク処理の変更**:
    *   クライアント側 (`handshake_client.go`) とサーバー側 (`handshake_server.go`) のハンドシェイク処理において、`readFinished`および`sendFinished`関数のシグネチャが変更されました。
    *   これらの関数は、`out []byte`という新しい引数を受け取るようになりました。この引数は、`firstFinished`の値をコピーするためのバッファとして機能します。
    *   具体的には、`sendFinished`が自身の`verifyData`を`out`にコピーし、`readFinished`が受信した`Finished`メッセージの`verifyData`を`out`にコピーします。これにより、クライアントとサーバーの両方で、ハンドシェイク中に最初に送信された`Finished`メッセージのハッシュが`firstFinished`フィールドに保存されるようになります。

4.  **`ConnectionState()`メソッドでの`TLSUnique`の設定**:
    *   `Conn.ConnectionState()`メソッドは、現在のTLS接続の状態を`ConnectionState`構造体として返します。
    *   このメソッド内で、`c.didResume`（セッションが再開されたかどうかを示すフラグ）が`false`の場合にのみ、`state.TLSUnique = c.firstFinished[:]`として`TLSUnique`フィールドに`firstFinished`の値を設定するロジックが追加されました。これにより、セッション再開時には`TLSUnique`が設定されないというRFC 5929の要件が満たされます。

5.  **テストケースの追加**:
    *   `tls_test.go`に`TestTLSUniqueMatches`という新しいテスト関数が追加されました。
    *   このテストは、クライアントとサーバー間で確立されたTLS接続において、`ConnectionState().TLSUnique`の値が一致するかどうかを検証します。
    *   また、セッション再開が行われた場合（`DidResume`が`true`の場合）には`TLSUnique`が設定されないことも検証しています。これにより、`tls-unique`の実装がRFC 5929の仕様に準拠していることが確認されます。

これらの変更により、GoのTLS実装は`tls-unique`チャネルバインディングをサポートし、アプリケーションがより安全な認証メカニズムを構築するための基盤を提供します。

## コアとなるコードの解説

### `src/pkg/crypto/tls/common.go` の変更

`ConnectionState`構造体は、TLS接続が確立された後にその状態をアプリケーションに提供するために使用されます。ここに`TLSUnique []byte`フィールドが追加されたことで、アプリケーションは確立されたTLSセッションに固有の`tls-unique`チャネルバインディング値を取得できるようになります。この値は、アプリケーション層の認証をTLSセッションに紐付けるために利用されます。コメントにあるように、セッション再開時にはこの値が`nil`になるのは、再開されたセッションでは`tls-unique`値を生成するのに十分なコンテキストがないためです。これは将来のTLSマスターシークレットの修正（EMSなど）によって改善される予定です。

### `src/pkg/crypto/tls/conn.go` の変更

`Conn`構造体は、個々のTLS接続の内部状態を管理します。`firstFinished [12]byte`フィールドが追加されたのは、TLSハンドシェイク中にクライアントまたはサーバーが最初に送信する`Finished`メッセージの`verify_data`（ハッシュ値）を保存するためです。この`verify_data`が、RFC 5929で定義される`tls-unique`チャネルバインディングの基となる値です。

また、`ConnectionState()`メソッド内で、`if !c.didResume { state.TLSUnique = c.firstFinished[:] }`という条件が追加されました。これは、セッションが再開されていない（つまり、完全なハンドシェイクが行われた）場合にのみ、`firstFinished`に保存された`tls-unique`値を`ConnectionState`に設定することを意味します。これにより、セッション再開時の`tls-unique`の制限がコードレベルで反映されています。

### `src/pkg/crypto/tls/handshake_client.go` および `src/pkg/crypto/tls/handshake_server.go` の変更

これらのファイルは、それぞれクライアント側とサーバー側のTLSハンドシェイクロジックを実装しています。
`readFinished`と`sendFinished`関数のシグネチャが変更され、`out []byte`という引数が追加されました。
*   `sendFinished(out []byte)`: この関数は、自身の`Finished`メッセージの`verifyData`を計算し、それを`out`スライスにコピーします。クライアントの場合、これはクライアントの`Finished`メッセージのハッシュを`c.firstFinished`に保存するために使用されます。
*   `readFinished(out []byte)`: この関数は、ピア（相手側）から受信した`Finished`メッセージを処理し、その`verifyData`を`out`スライスにコピーします。サーバーの場合、これはクライアントの`Finished`メッセージのハッシュを`c.firstFinished`に保存するために使用されます。

これらの変更により、ハンドシェイクの初期段階で交換される`Finished`メッセージのハッシュが、`Conn.firstFinished`フィールドに確実に保存されるようになります。この`firstFinished`の値が、その後の`tls-unique`チャネルバインディングの生成に使用されます。

### `src/pkg/crypto/tls/tls_test.go` の変更

`TestTLSUniqueMatches`テスト関数が追加されました。このテストは、`tls-unique`チャネルバインディングの実装が正しく機能していることを検証します。
*   テストは、クライアントとサーバー間でTLS接続を確立し、両者の`ConnectionState().TLSUnique`値が一致するかどうかを確認します。これは、`tls-unique`値が接続の両端で同じであることを保証するために重要です。
*   さらに、セッション再開が行われた場合（`conn.ConnectionState().DidResume`が`true`の場合）には、`TLSUnique`が設定されない（`nil`または空）ことを検証します。これにより、RFC 5929で述べられているセッション再開時の`tls-unique`の制限が正しく処理されていることが確認されます。

これらのコード変更は、GoのTLSスタックに`tls-unique`チャネルバインディングを堅牢かつ仕様に準拠した形で統合するためのものです。

# [インデックス 20020] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/ld`）における重要なバグ修正を扱っています。具体的には、リンカがコードブロックとデータブロックのベースアドレスおよびサイズを扱う際に、`int32`型を使用していたために、2GBを超える大きなアドレスを正しく処理できない問題を解決します。この修正により、関連する関数の引数と内部変数の型が`int64`に変更され、64ビットシステムにおける大規模なGoアプリケーションのリンクの堅牢性が向上しました。

## 変更の背景

このコミットは、Goリンカ（`cmd/ld`）における重要なバグ修正を目的としています。Goリンカは、Goのソースコードから実行可能ファイルを生成する際に、オブジェクトファイルやライブラリを結合し、メモリレイアウトを決定する役割を担っています。

問題は、リンカ内部の`codeblk`関数と`datblk`関数が、コードブロックとデータブロックのベースアドレスおよびサイズを扱う際に、`int32`型を使用していたことにありました。`int32`型は32ビットの符号付き整数であり、表現できる値の範囲は約-20億から+20億まで（約2GB）に制限されます。

現代の64ビットシステムでは、プログラムが利用できる仮想アドレス空間ははるかに広大であり、2GBを超えるアドレスにコードやデータを配置することが一般的です。特に、大規模なアプリケーションや、特定のベースアドレスにリンクされるようなシナリオでは、この`int32`の制限が問題となります。

`int32`で表現できない大きなアドレスやサイズがこれらの関数に渡された場合、値が切り捨てられ（オーバーフロー）、リンカが誤ったメモリアドレスやサイズを計算してしまう可能性がありました。これにより、生成される実行可能ファイルが正しく動作しない、クラッシュする、あるいは予期せぬメモリ領域にアクセスするといった深刻な問題を引き起こす可能性がありました。このコミットは、このような「大きなリンクベースアドレス」を正しく扱えるようにするための修正です。

## 前提知識の解説

このコミットの理解を深めるために、以下の技術的な概念を解説します。

*   **Goリンカ (`cmd/ld`)**:
    Go言語のコンパイルプロセスにおいて、`go build`コマンドが最終的な実行可能ファイルを生成する際に使用されるツールチェーンの一部です。コンパイラが生成したオブジェクトファイル（`.o`ファイル）や、Goの標準ライブラリ、サードパーティライブラリなどを結合し、実行可能なバイナリを生成します。この過程で、各セクション（コード、データ、BSSなど）のメモリ上の配置を決定し、シンボル（関数名や変数名）を解決し、必要に応じてアドレスの再配置を行います。リンカは、プログラムがメモリ上でどのように配置され、実行されるかを定義する上で極めて重要な役割を担っています。

*   **アドレス空間とメモリレイアウト**:
    コンピュータのメモリは、アドレスによって識別されるバイトの連続した集合として抽象化されます。プログラムが実行される際、オペレーティングシステムは各プロセスに「仮想アドレス空間」を割り当てます。これは、プログラムが利用できるメモリの範囲を抽象的に表現したものです。
    *   **32ビットシステム**: 仮想アドレス空間は最大4GB（2^32バイト）です。このため、`int32`型でアドレスを表現しても問題ありませんでした。
    *   **64ビットシステム**: 仮想アドレス空間は理論上18エクサバイト（2^64バイト）と非常に広大です。実際には、オペレーティングシステムやハードウェアの制約により、利用可能なアドレス範囲は限定されますが、それでも4GBをはるかに超えるアドレスを扱うことが可能です。
    リンカは、このアドレス空間内でコード、データ、スタック、ヒープなどのセクションをどのように配置するか（メモリレイアウト）を決定します。

*   **`int32`と`int64`**:
    プログラミングにおける整数型は、そのビット幅によって表現できる値の範囲が異なります。
    *   **`int32`**: 32ビット（4バイト）の符号付き整数型です。表現できる値の範囲は、-2,147,483,648から2,147,483,647までです。これは約±2GBに相当します。
    *   **`int64`**: 64ビット（8バイト）の符号付き整数型です。表現できる値の範囲は、-9,223,372,036,854,775,808から9,223,372,036,854,775,807までと、非常に広大です。
    メモリのアドレスやサイズを扱う場合、システムのアドレス空間の大きさに合わせて適切な整数型を選択することが不可欠です。32ビットシステムでは`int32`で十分でしたが、64ビットシステムでは`int64`を使用しないと、アドレスが2GBを超えた場合に値が切り捨てられ、誤ったアドレスとして解釈されてしまいます。

*   **`codeblk`と`datblk`関数**:
    Goリンカの内部関数であり、それぞれコードセクションとデータセクションのメモリブロックを管理する役割を担っています。これらの関数は、特定のメモリアドレスから始まるブロックのサイズを扱うため、引数としてアドレスとサイズを受け取ります。リンカが実行可能ファイルを構築する際に、これらの関数を呼び出して、コードやデータの適切なメモリ配置とサイズ計算を行います。

## 技術的詳細

このコミットの技術的な核心は、Goリンカがメモリ上のコードブロックとデータブロックを管理する際に使用する内部関数の引数型を、`int32`から`int64`へ変更した点にあります。

具体的には、`src/cmd/ld/data.c`ファイル内の以下の3つの関数が修正されました。

1.  **`static void blk(LSym *start, int32 addr, int32 size)`**:
    この関数は、シンボル（`LSym`）のリストを走査し、指定されたアドレス（`addr`）とサイズ（`size`）の範囲内でシンボルを処理する汎用的なブロック処理関数と考えられます。元の実装では`addr`と`size`が`int32`でした。

2.  **`void codeblk(int32 addr, int32 size)`**:
    この関数は、実行可能ファイルのコードセクション（テキストセクション）に関連するメモリブロックを処理します。`addr`はコードブロックの開始アドレス、`size`はそのサイズを示します。

3.  **`void datblk(int32 addr, int32 size)`**:
    この関数は、実行可能ファイルのデータセクションに関連するメモリブロックを処理します。`addr`はデータブロックの開始アドレス、`size`はそのサイズを示します。

これらの関数が`int32`を引数としていたため、2GBを超えるアドレスやサイズが渡された場合、値がオーバーフローして切り捨てられていました。例えば、`0x80000000`（2GB）を超えるアドレスが渡されると、`int32`の範囲外となり、予期せぬ負の値や小さな値として解釈される可能性がありました。これにより、リンカが計算するメモリ上のオフセットやサイズが誤り、結果として生成されるバイナリが破損したり、実行時に不正なメモリアクセスを引き起こしたりする原因となっていました。

修正は非常にシンプルかつ効果的です。
*   `blk`, `codeblk`, `datblk`関数の引数`addr`と`size`の型を`int32`から`int64`に変更しました。
*   これらの関数内でアドレスやサイズを扱うローカル変数（例: `eaddr`, `n`, `i`）も、同様に`int64`に変更されました。これにより、関数内部での計算も64ビット精度で行われるようになります。
*   関連するヘッダファイル`src/cmd/ld/lib.h`も更新され、これらの関数のプロトタイプ宣言が新しい`int64`型に一致するように修正されました。これは、リンカの他の部分がこれらの関数を正しく呼び出せるようにするために不可欠です。

この変更により、Goリンカは64ビットシステム上で2GBを超える大きなベースアドレスやサイズのコード/データブロックを正確に処理できるようになり、大規模なGoアプリケーションのビルドや、特定のメモリレイアウトを必要とするシナリオでの安定性と信頼性が向上しました。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、以下の2つのファイルに集中しています。

1.  **`src/cmd/ld/data.c`**:
    *   `blk`関数のシグネチャと内部変数`eaddr`の型が`int32`から`int64`に変更されました。
    *   `codeblk`関数のシグネチャと内部変数`eaddr`, `n`の型が`int32`から`int64`に変更されました。
    *   `datblk`関数のシグネチャと内部変数`i`, `eaddr`の型が`int32`から`int64`に変更されました。

2.  **`src/cmd/ld/lib.h`**:
    *   `codeblk`関数のプロトタイプ宣言の引数型が`int32`から`int64`に変更されました。
    *   `datblk`関数のプロトタイプ宣言の引数型が`int32`から`int64`に変更されました。

*   **`blk(LSym *start, int64 addr, int64 size)`**:

*   **`codeblk(int64 addr, int64 size)`**:
    コードセクションのブロックを処理するこの関数も、64ビットのアドレスとサイズを扱えるようになりました。これにより、大規模な実行可能ファイルのコードセクションが2GBを超える場合でも、リンカが正確なメモリ配置とサイズ計算を行えるようになります。`eaddr`と`n`も`int64`になることで、コードブロック内のオフセット計算などが正確になります。

*   **`datblk(int64 addr, int64 size)`**:
    データセクションのブロックを処理するこの関数も同様に、64ビットのアドレスとサイズを扱えるようになりました。これにより、大規模なデータセクションを持つプログラムでも、リンカが正確なメモリ配置とサイズ計算を行えるようになります。`i`と`eaddr`も`int64`になることで、データブロック内の要素へのアクセスやアドレス計算が正確になります。

これらの変更は、リンカが扱うアドレスとサイズの表現能力を根本的に向上させ、64ビットシステムにおけるGoプログラムのリンクの堅牢性を高めます。

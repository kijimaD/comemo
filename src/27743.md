# [インデックス 27743] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）において、`append`組み込み関数の「高速パス（fast path）」におけるライトバリアの不要な呼び出しを回避する最適化を導入します。具体的には、`s = append(s, ...)` のように、`append`の結果が同じスライス変数に書き戻される場合に、スライスの基盤となる配列が再割り当てされない限り、要素の追加時にライトバリアを省略することでパフォーマンスを向上させます。

## 変更の背景

このコミットは、Goコンパイラにおける`append`組み込み関数の最適化に関するものです。特に、`s = append(s, ...)` のように、`append`の結果が元のスライス変数`s`に直接書き戻されるシナリオに焦点を当てています。

Goのガベージコレクション（GC）は、並行して動作する「ライトバリア」というメカニズムを利用して、ポインタの変更を追跡し、GCの正確性を保証します。しかし、`s = append(s, ...)` のような操作で、スライスの基盤となる配列が再割り当てされない（つまり、既存の容量で十分な）「高速パス」の場合、新しい要素が追加されるメモリ領域は既にGCによって「黒」とマークされているか、あるいはGCがその領域をスキャン済みであるため、個々の要素の書き込みに対してライトバリアを適用する必要がありません。

以前のGoコンパイラのバックエンドには、この特定のケースでライトバリアを省略する最適化が存在していました。しかし、GoコンパイラがSSA（Static Single Assignment）バックエンドに移行した際に、この最適化が失われ、不要なライトバリアが挿入されるようになりました。これにより、特に`append`が頻繁に呼び出されるコードにおいて、わずかながらもパフォーマンスのオーバーヘッドが発生していました。

この問題は、GoのIssue #14921「runtime, cmd/compile: consider write barrier short-circuit when *dst == src」で議論されており、`append`操作が冗長なライトバリアの主要な原因の一つであることが指摘されていました。また、Issue #14969もこの問題に関連するバグまたはパフォーマンス低下を報告していたと考えられます。

このコミットは、SSAバックエンドにおいて、この失われた最適化を再実装し、`append`の高速パスにおける不要なライトバリアの呼び出しを排除することで、パフォーマンスの改善と生成されるコードサイズの削減を目指しています。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、低レイテンシと高パフォーマンスを目標とした並行（concurrent）な三色マーク＆スイープ（tri-color mark-and-sweep）アルゴリズムを採用しています。

*   **三色マーキング**: GCはオブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって訪問されておらず、回収される可能性のあるオブジェクト。
    *   **灰 (Gray)**: 到達可能と判断されたが、その子（参照しているオブジェクト）がまだ完全にスキャンされていないオブジェクト。
    *   **黒 (Black)**: 完全にスキャンされ、そのすべての子もマーク済みであるオブジェクト。これらは生きていると確定されたオブジェクトです。
*   **並行GC**: GCのマーキングフェーズの大部分は、アプリケーションの実行（ミューテータ、mutator）と並行して行われます。これにより、アプリケーションの一時停止（Stop The World: STW）時間を最小限に抑えます。
*   **ライトバリア (Write Barrier)**: 並行GCにおいて、アプリケーションがポインタを更新する際に、GCの正確性を保証するためのメカニズムです。ミューテータがポインタを変更すると、三色不変条件（tri-color invariant）が破られる可能性があります。ライトバリアは、この不変条件が破られないように、ポインタの書き込み時に特定の処理（例えば、新しい参照先のオブジェクトを灰色にマークするなど）を実行します。Go 1.5で挿入ライトバリアが導入され、Go 1.8以降ではハイブリッドライトバリアが採用され、STW時間のさらなる短縮が図られています。ライトバリアは、コンパイラによって生成されるアセンブリコードに挿入され、`runtime.writebarrierptr`のようなランタイム関数を呼び出すことで実現されます。

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、プログラムの最適化のために中間表現としてSSA（Static Single Assignment）フォームを使用します。

*   **SSAフォーム**: 各変数が一度だけ代入されるようにする中間表現です。これにより、データフロー解析や最適化が容易になります。
*   **SSAバックエンド**: Go 1.7から導入された新しいコンパイラバックエンドで、従来のバックエンドに比べてより高度な最適化を可能にしました。しかし、新しいバックエンドへの移行に伴い、古いバックエンドで存在していた一部の最適化が一時的に失われることがありました。今回の`append`のライトバリア最適化もその一つです。

### `append`組み込み関数

`append`はGoのスライスに要素を追加するための組み込み関数です。

*   `s = append(s, elem1, elem2, ...)` の形式で使用されます。
*   **容量 (Capacity)**: スライスには、現在使用されている要素数を示す「長さ（length）」と、基盤となる配列が保持できる最大要素数を示す「容量（capacity）」があります。
*   **高速パス (Fast Path)**: `append`操作時に、既存の容量で新しい要素を格納できる場合、新しい配列の割り当ては不要です。この場合、既存の配列の末尾に要素が直接追加され、スライスの長さが更新されます。これを「高速パス」と呼びます。
*   **低速パス (Slow Path) / `growslice`**: 既存の容量が不足している場合、`append`はより大きな新しい配列を割り当て、既存の要素を新しい配列にコピーし、新しい要素を追加します。この処理は`runtime.growslice`関数によって行われます。この場合、新しい配列へのポインタの書き込みが発生するため、ライトバリアが必要になります。

## 技術的詳細

このコミットの技術的詳細は、`s = append(s, ...)` の形式で、かつスライスが成長しない（つまり、`growslice`が呼び出されない）「高速パス」において、不要なライトバリアの呼び出しを排除することにあります。

1.  **問題の特定**:
    GoのSSAバックエンドでは、`s = append(s, ...)` のような代入文が、`append`の結果を一時的なスライスとして生成し、その後に元のスライス変数`s`に代入するという形で処理されていました。この代入の際に、GCのライトバリアが常に挿入されていました。
    しかし、`append`の高速パスでは、新しい要素は既存の基盤配列の空きスペースに直接書き込まれます。このとき、スライスのデータポインタ自体は変更されません。変更されるのはスライスの長さと、追加される要素の値です。もし追加される要素がポインタ型であれば、そのポインタの書き込みに対してライトバリアが必要ですが、スライス自体へのポインタの書き込み（`s`のデータポインタの更新）は、スライスが成長しない限り発生しません。
    特に、`var x []byte; x = append(x, 1, 2, 3)` のような`[]byte`（バイトスライス）の場合、要素はポインタではないため、要素の書き込み自体にライトバリアは不要です。スライスヘッダ（データポインタ、長さ、容量）の更新も、データポインタが変わらない限り、GCの観点からは特別な処理は不要です。

2.  **最適化の再導入**:
    このコミットは、SSAバックエンドにおいて、この特定のシナリオを検出し、ライトバリアを省略するロジックを導入します。
    *   コンパイラは、`n.Left`（代入の左辺）と `rhs.List.First()`（`append`の最初の引数、つまり元のスライス）が同じ式を参照しているかどうかを `samesafeexpr` 関数でチェックします。
    *   さらに、`!s.canSSA(n.Left)` で、そのスライスがSSA化できない（つまり、スタックではなくヒープ上に存在する可能性があり、GCの対象となる）ことを確認します。スタック上のスライスはGCの対象外であるため、ライトバリアは元々不要です。
    *   これらの条件が満たされ、かつスライスが成長しない（高速パス）場合、`append`操作は「インプレース（inplace）」で行われると判断されます。

3.  **インプレース`append`の処理**:
    `inplace`フラグが`true`の場合、`append`関数は新しいスライスを生成して返すのではなく、元のスライス変数のデータポインタ、長さ、容量を直接更新します。この際、新しい要素の書き込みやスライスの長さ・容量の更新に対して、不要なライトバリアの呼び出しを抑制します。
    ただし、スライスが成長して`runtime.growslice`が呼び出される場合は、新しい基盤配列へのポインタの書き込みが発生するため、そのポインタに対してはライトバリアが適用されます。このコミットは、あくまで「高速パス」における不要なライトバリアの回避に限定されます。

この最適化により、`append`の高速パスがより効率的になり、特にポインタを含まない要素型（例: `[]byte`）のスライスに対する`append`のパフォーマンスが向上します。

## コアとなるコードの変更箇所

変更は主に `src/cmd/compile/internal/gc/ssa.go` ファイルに集中しています。

1.  **`func (s *state) stmt(n *Node)` メソッド**:
    *   `rhs.Op == OAPPEND` のケースが追加され、`append`の特殊なハンドリングが導入されました。
    *   `samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left)` という条件が追加され、代入の左辺と`append`の第一引数が同じスライスであり、かつそのスライスがSSA化できない場合に、新しい`s.append(rhs, true)`が呼び出されます。`true`は「インプレース」操作を示すフラグです。
    *   これにより、`s = append(s, ...)` の形式で、かつスライスが成長しない場合に、通常のSSA処理パスを通らずに最適化されたパスへ分岐します。

2.  **`func (s *state) exprAppend(n *Node)` メソッドの変更とリネーム**:
    *   元の `exprAppend` 関数が `append` にリネームされ、`inplace bool` という新しい引数が追加されました。
    *   関数の内部ロジックが `inplace` フラグに基づいて分岐するようになりました。
    *   `inplace` が `true` の場合（つまり、`s = append(s, ...)` の高速パスの場合）、スライスの長さ (`*a.len`) と容量 (`*a.cap`) の更新が直接行われ、`runtime.writebarrierptr` の呼び出しが条件付きになります。特に、要素の追加自体にはライトバリアが適用されなくなります。
    *   `inplace` が `false` の場合（通常の `append` 式の場合）、以前の `exprAppend` と同様に、新しいスライスを生成して返します。
    *   `growslice` が呼び出されるパスでは、新しいポインタの書き込みに対しては引き続きライトバリアが適用されます。

## コアとなるコードの解説

### `stmt` メソッドにおける `OAPPEND` の特殊処理

```go
// src/cmd/compile/internal/gc/ssa.go
func (s *state) stmt(n *Node) {
    // ...
    if rhs != nil {
        switch rhs.Op {
        case OSTRUCTLIT, OARRAYLIT:
            // ... (既存の処理)
        case OAPPEND:
            // If we're writing the result of an append back to the same slice,
            // handle it specially to avoid write barriers on the fast (non-growth) path.
            // If the slice can be SSA'd, it'll be on the stack,
            // so there will be no write barriers,
            // so there's no need to attempt to prevent them.
            if samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left) {
                s.append(rhs, true) // inplace=true で append を呼び出す
                return
            }
        }
    }
    // ...
}
```
このコードブロックは、代入文 (`n`) の右辺 (`rhs`) が `OAPPEND` (append操作) である場合に、特別な処理を行うためのものです。
*   `samesafeexpr(n.Left, rhs.List.First())`: これは、代入の左辺 (`n.Left`) と `append` の第一引数 (`rhs.List.First()`) が同じ式（つまり同じスライス変数）を参照しているかをチェックします。例えば、`x = append(x, ...)` のようなケースです。
*   `!s.canSSA(n.Left)`: これは、そのスライスがSSA化できない（つまり、スタックではなくヒープ上に存在し、GCの対象となる）ことを確認します。スタック上のスライスはGCの対象外なので、ライトバリアは元々不要です。
*   これらの条件が両方とも真の場合、`s.append(rhs, true)` が呼び出されます。ここで `true` は、`append`操作が「インプレース」で行われることを示し、高速パスでのライトバリア回避を可能にします。そして `return` することで、通常のSSA処理パスをスキップします。

### `append` メソッド (旧 `exprAppend`) の変更

```go
// src/cmd/compile/internal/gc/ssa.go
// append converts an OAPPEND node to SSA.
// If inplace is false, it converts the OAPPEND expression n to an ssa.Value,
// adds it to s, and returns the Value.
// If inplace is true, it writes the result of the OAPPEND expression n
// back to the slice being appended to, and returns nil.
// inplace MUST be set to false if the slice can be SSA'd.
func (s *state) append(n *Node, inplace bool) *ssa.Value {
    // ...
    sn := n.List.First() // the slice node is the first in the list

    var slice, addr *ssa.Value
    if inplace {
        addr = s.addr(sn, false) // スライス変数のアドレスを取得
        slice = s.newValue2(ssa.OpLoad, n.Type, addr, s.mem()) // スライス変数の値をロード
    } else {
        slice = s.expr(sn)
    }

    // ... (長さ、容量の計算)

    if inplace {
        // 新しい長さをスライス変数の len フィールドに直接ストア
        lenaddr := s.newValue1I(ssa.OpOffPtr, pt, int64(Array_nel), addr)
        s.vars[&memVar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, s.config.IntSize, lenaddr, nl, s.mem())
    }

    // ... (容量が足りない場合の growslice 呼び出しロジック)

    if inplace {
        // growslice が呼び出された場合、新しい容量とポインタをスライス変数にストア
        capaddr := s.newValue1I(ssa.OpOffPtr, pt, int64(Array_cap), addr)
        s.vars[&memVar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, s.config.IntSize, capaddr, r[2], s.mem())
        s.insertWBstore(pt, addr, r[0], n.Lineno, 0) // 新しいデータポインタに対してライトバリアを挿入
        // load the value we just stored to avoid having to spill it
        s.vars[&ptrVar] = s.newValue2(ssa.OpLoad, pt, addr, s.mem())
    } else {
        // ... (inplace=false の場合の処理)
    }

    // ... (要素の書き込みロジック)

    if inplace {
        return nil // inplace の場合は値を返さない
    }
    // ... (inplace=false の場合は新しいスライスを生成して返す)
    return s.newValue3(ssa.OpSliceMake, n.Type, p, nl, c)
}
```
この変更により、`inplace`が`true`の場合、`append`はスライスヘッダ（データポインタ、長さ、容量）を直接更新するコードを生成します。特に、スライスが成長しない「高速パス」では、新しい要素の書き込みに対してライトバリアを省略します。`growslice`が呼び出される「低速パス」では、新しい基盤配列へのポインタの書き込みに対しては`s.insertWBstore`を通じてライトバリアが適用されます。

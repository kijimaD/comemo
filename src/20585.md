## 変更の背景

このコミットの主な背景は、Goランタイムの内部的な命名規則の統一と、将来の大きな変更（CL: Change List）の準備です。GoランタイムはC言語で書かれた部分が多く、C言語の静的変数には通常、パッケージ名やモジュール名を示すプレフィックスを付けることで、名前の衝突を避け、コードの可読性を向上させる慣習があります。

`runtime·` プレフィックスは、Goランタイムの内部シンボル（関数やデータ）に使用される特別な命名規則です。特にアセンブリコードで定義されるシンボルによく見られます。このプレフィックスを静的変数に適用することで、以下の利点があります。

1.  **名前空間の明確化**: 変数がGoランタイムのどの部分に属しているかを明確にし、他のライブラリやユーザーコードとの名前衝突を防ぎます。
2.  **可読性の向上**: コードを読む際に、その変数がランタイムの内部的な要素であることを一目で理解できます。
3.  **将来の変更の簡素化**: コミットメッセージにあるように、「今後のCLの差分を小さくする」という目的があります。これは、これらの変数が関わる大規模な変更が予定されており、事前に命名規則を統一しておくことで、その変更がよりクリーンで管理しやすくなることを意味します。例えば、これらの変数を参照するコードが多数ある場合、プレフィックスを先に付けておくことで、後続のCLでは変数の論理的な変更のみに集中でき、リネームによるノイズを減らすことができます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語の知識が必要です。

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、ゴルーチン管理など、Go言語の並行処理モデルとメモリ安全性を実現するための低レベルな機能を提供します。ランタイムの多くの部分はC言語とアセンブリ言語で書かれています。

### 静的変数 (Static Variables in C)
C言語における`static`キーワードは、変数のスコープとリンケージを制御します。
-   **ファイルスコープの静的変数**: 関数外で`static`と宣言された変数は、その変数が宣言されたファイル内でのみアクセス可能です（内部リンケージ）。他のファイルからは見えません。
-   **関数スコープの静的変数**: 関数内で`static`と宣言された変数は、その関数の呼び出し間で値を保持し、一度だけ初期化されます。

このコミットでリネームされているのは、ファイルスコープの静的変数です。

### `runtime·` プレフィックス
Goランタイムでは、内部的なシンボル（特にアセンブリで定義されるもの）に対して`runtime·`というプレフィックスを使用する慣習があります。`·`（中点）は、Goのオブジェクトファイルやバイナリ内部でパッケージセパレータとして機能します。これにより、シンボルが`runtime`パッケージに属していることが明確になります。

### メモリ管理とガベージコレクション (GC)
Goのガベージコレクションは、メモリの自動管理を行います。主なコンポーネントは以下の通りです。

-   **`MSpan`**: Goランタイムのメモリ管理の基本単位です。連続したメモリページ（通常8KB）のブロックで、特定のサイズのオブジェクトを割り当てるために使用されます。ヒープオブジェクト用、スタック用など、様々な目的で使われます。
-   **`MCache` (Memory Cache)**: プロセッサ（P）ごとのメモリキャッシュです。各Pは独自の`MCache`を持ち、小さなオブジェクトの割り当てを高速化し、グローバルロックの競合を減らします。
-   **`Workbuf` (Work Buffer)**: ガベージコレクタのマークフェーズ中に使用されるバッファです。到達可能なオブジェクトを特定するためにオブジェクトグラフを走査する際、まだスキャンされていないオブジェクトへのポインタを一時的に保持します。これにより、GCの並行処理が効率化されます。
-   **`allfin` (All Finalizers)**: ファイナライザ（オブジェクトがGCによって回収される直前に実行される関数）のリストを管理するための構造体です。GCサイクル中に、ファイナライザを持つオブジェクトが適切に処理されるように、このリストが走査されます。
-   **`stackpool`**: ゴルーチンのスタックに割り当てられる`MSpan`のプールです。ゴルーチンのスタックは動的に伸縮するため、`stackpool`はスタックメモリの効率的な再利用を可能にし、メモリ割り当て/解放のオーバーヘッドを削減します。
-   **`Mutex`**: 相互排他ロックであり、共有リソースへのアクセスを同期するために使用されます。`stackpoolmu`は`stackpool`へのアクセスを保護するためのミューテックスです。

## 技術的詳細

このコミットは、`src/runtime/mcache.c`、`src/runtime/mgc0.c`、`src/runtime/stack.c`の3つのファイルにわたって、複数の静的変数に`runtime·`プレフィックスを追加しています。これは、これらの変数がGoランタイムの内部的な実装詳細であり、外部から直接参照されるべきではないことを強調し、ランタイムのシンボル管理をより厳密にするためのものです。

具体的にリネームされた変数は以下の通りです。

1.  **`emptymspan` -> `runtime·emptymspan`**:
    *   `mcache.c`に定義されている`MSpan`型の静的変数です。
    *   `MCache`が空のオブジェクトリストを持つスパンとして使用されます。`MCache`の`alloc`配列の初期値として設定され、空のスパンであることを示します。
    *   このリネームにより、`emptymspan`がランタイム内部の特別な`MSpan`であることを明確にします。

2.  **`allfin` -> `runtime·allfin`**:
    *   `mgc0.c`に定義されている`FinBlock`型の静的ポインタ変数です。
    *   Goのファイナライザシステムにおいて、すべてのファイナライザブロックのリンクリストの先頭を指します。ガベージコレクタがファイナライザを処理する際にこのリストを走査します。
    *   `runtime·allfin`とすることで、ファイナライザ管理がランタイムのコア機能であることを示します。

3.  **`work` -> `runtime·work`**:
    *   `mgc0.c`に定義されている匿名構造体型の静的変数です。
    *   ガベージコレクタのマークフェーズにおける並行処理の管理に使用されます。`nwait`（待機中のプロセッサ数）、`nproc`（GCに参加するプロセッサ数）、`spans`（マーク対象のMSpanのリスト）などのフィールドを持ちます。
    *   `runtime·work`とすることで、GCの作業管理がランタイムの内部的なメカニズムであることを強調します。

4.  **`stackpool` -> `runtime·stackpool`**:
    *   `stack.c`に定義されている`MSpan`型の静的配列です。
    *   異なるサイズのスタック（`NumStackOrders`で定義される複数のサイズクラス）に対応する`MSpan`のフリーリストを管理します。ゴルーチンスタックの割り当てと解放に使用されます。
    *   `runtime·stackpool`とすることで、スタック管理がランタイムの重要な内部コンポーネントであることを明確にします。

5.  **`stackpoolmu` -> `runtime·stackpoolmu`**:
    *   `stack.c`に定義されている`Mutex`型の静的変数です。
    *   `stackpool`へのアクセスを保護するためのミューテックスです。スタックプールの操作（割り当て、解放など）は並行して行われる可能性があるため、データ競合を防ぐためにロックが必要です。
    *   `runtime·stackpoolmu`とすることで、スタックプールの同期メカニズムがランタイムの内部的なものであることを示します。

これらのリネームは、コードの機能的な変更を伴わず、純粋に命名規則の統一と将来のコード変更の準備を目的としています。GoランタイムのCコードでは、このような内部的な静的変数に`runtime·`プレフィックスを付けることで、シンボルの可視性と管理をより厳密に行うことが一般的です。

## コアとなるコードの変更箇所

このコミットでは、以下のファイルで静的変数のリネームが行われています。

### `src/runtime/mcache.c`
- `static MSpan emptymspan;` が `static MSpan runtime·emptymspan;` に変更。
- `c->alloc[i] = &emptymspan;` が `c->alloc[i] = &runtime·emptymspan;` に変更。
- `if(s != &emptymspan)` が `if(s != &runtime·emptymspan)` に変更。

### `src/runtime/mgc0.c`
- `static FinBlock *allfin;` が `static FinBlock *runtime·allfin;` に変更。
- 匿名構造体 `work` の定義が `runtime·work` に変更され、その構造体のフィールドへのアクセスも `work.field` から `runtime·work.field` に変更。
    - 例: `if(work.nwait > 0 ...)` が `if(runtime·work.nwait > 0 ...)` に変更。
    - 例: `for(fb=allfin; fb; fb=fb->alllink)` が `for(fb=runtime·allfin; fb; fb=fb->alllink)` に変更。

### `src/runtime/stack.c`
- `static MSpan stackpool[NumStackOrders];` が `static MSpan runtime·stackpool[NumStackOrders];` に変更。
- `static Mutex stackpoolmu;` が `static Mutex runtime·stackpoolmu;` に変更。
- `stackpool` と `stackpoolmu` への参照がそれぞれ `runtime·stackpool` と `runtime·stackpoolmu` に変更。
    - 例: `runtime·MSpanList_Init(&stackpool[i]);` が `runtime·MSpanList_Init(&runtime·stackpool[i]);` に変更。
    - 例: `runtime·lock(&stackpoolmu);` が `runtime·lock(&runtime·stackpoolmu);` に変更。

## コアとなるコードの解説

変更はすべて、C言語の静的変数とその参照に対する`runtime·`プレフィックスの追加です。

-   **`emptymspan` / `runtime·emptymspan`**:
    `mcache.c`では、`MCache`が管理するメモリ領域（スパン）のリストにおいて、空のスパンを示すために`emptymspan`が使用されていました。これを`runtime·emptymspan`にリネームすることで、この特殊な`MSpan`がGoランタイムの内部的な実装詳細であることを明確にしています。これは、`MCache`の初期化や、スパンがキャッシュから解放される際の処理で参照されます。

-   **`allfin` / `runtime·allfin`**:
    `mgc0.c`では、ファイナライザを持つすべてのオブジェクトを追跡するために`allfin`リンクリストが使用されていました。ガベージコレクタのマークフェーズ中に、このリストを走査してファイナライザに関連するオブジェクトが誤って回収されないようにします。`runtime·allfin`へのリネームは、ファイナライザ管理がランタイムの重要な内部機能であることを強調します。

-   **`work` / `runtime·work`**:
    `mgc0.c`の`work`構造体は、ガベージコレクタの並行マークフェーズにおける作業管理の中心的な役割を担っていました。これには、GCに参加するプロセッサの数、待機中のプロセッサ、マーク対象のメモリ領域などが含まれます。`runtime·work`へのリネームは、この構造体がGCの内部的な調整メカニズムであることを明確にし、ランタイムの他の部分との区別を強化します。

-   **`stackpool` / `runtime·stackpool` および `stackpoolmu` / `runtime·stackpoolmu`**:
    `stack.c`では、ゴルーチンのスタックを効率的に管理するための`stackpool`と、そのプールへのアクセスを同期するための`stackpoolmu`が定義されていました。`runtime·stackpool`と`runtime·stackpoolmu`へのリネームは、これらの変数がGoランタイムのスタック管理サブシステムの不可欠な部分であり、その内部的な性質を強調します。これにより、スタックの割り当て、解放、キャッシュなどの操作が、ランタイムの制御下で行われることがより明確になります。

これらの変更は、コードの動作には影響を与えませんが、Goランタイムの内部構造の明確化と、将来のメンテナンス性を向上させるための重要なステップです。

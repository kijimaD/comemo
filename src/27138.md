# [インデックス 27138] ファイルの概要

このコミットは、Goランタイムのテスト関連コードの整理に関するものです。具体的には、スケジューラのローカルキューテスト関数が、その利用箇所に合わせて `proc.go` から `export_test.go` へ移動されました。

## コミット

Goランタイムのスケジューラに関連するテスト関数 `testSchedLocalQueueLocal` および `testSchedLocalQueueSteal` が、`proc.go` から `export_test.go` へ移動されました。これにより、テストコードとプロダクションコードの分離が促進され、コードベースの保守性が向上します。

## 変更の背景

この変更の主な背景は、Goランタイムのコードベースにおけるテストコードの適切な配置と分離です。`testSchedLocalQueue` と `testSchedLocalQueueSteal` は、Goスケジューラのローカル実行キューとワークスチール機構の動作を検証するためのテスト関数でした。これらは元々 `proc.go` という、Goスケジューラの主要なロジックが記述されているファイル内に存在していました。

しかし、これらの関数は純粋にテスト目的で使用され、プロダクションコードからは直接呼び出されることはありません。Goの慣習として、パッケージ内部のテストヘルパー関数や、外部からアクセスする必要があるが通常のAPIとしては公開したくないテスト用の関数は、`_test.go` ファイルや `export_test.go` ファイルに配置することが推奨されます。

`export_test.go` は、パッケージの内部関数や変数にテストコードからアクセスできるようにするための特別なファイルです。このファイルにテスト関連の関数を移動することで、以下の利点が得られます。

1.  **コードの分離**: プロダクションコード (`proc.go`) とテストコード (`export_test.go`) が明確に分離され、それぞれの役割が明確になります。これにより、`proc.go` は純粋なスケジューラロジックに集中でき、コードの可読性と保守性が向上します。
2.  **依存関係の明確化**: テスト関数が `export_test.go` に移動されることで、これらの関数がテスト目的でのみ使用されることが明示されます。
3.  **ビルドサイズの最適化**: `export_test.go` の内容は、通常のアプリケーションビルドには含まれません。これにより、最終的なバイナリサイズを小さく保つことができます。

この変更は、Goランタイムのコード品質と構造を改善するための継続的な取り組みの一環として行われました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラ、特にGoroutineの実行管理とワークスチールに関する基本的な知識が必要です。

### Goスケジューラ (M:Nスケジューリング)

Goランタイムは、M個のOSスレッド (M) をN個のGoroutine (G) に多重化するM:Nスケジューリングモデルを採用しています。このモデルは、以下の3つの主要な要素で構成されます。

*   **G (Goroutine)**: Goプログラムの実行単位。軽量なスレッドのようなもので、数MBのスタックを持つOSスレッドとは異なり、初期スタックサイズは数KBと非常に小さいです。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッド。Goランタイムは、このM上でGを実行します。
*   **P (Processor)**: 論理プロセッサ。MとGを仲介する役割を担います。Pはローカル実行キュー (run queue) を持ち、実行可能なGを保持します。MはPにアタッチされ、Pのローカル実行キューからGを取り出して実行します。Goプログラムの `GOMAXPROCS` 環境変数は、同時に実行可能なPの数を制御します。

### ローカル実行キューとグローバル実行キュー

各Pは、実行可能なGoroutineを保持するための**ローカル実行キュー**を持っています。Mは、アタッチされているPのローカル実行キューからGoroutineを取り出して実行します。

また、Goランタイムには**グローバル実行キュー**も存在します。これは、どのPにも割り当てられていないGoroutineや、システムコールから戻ってきたGoroutineなどが一時的に置かれる場所です。Pのローカル実行キューが空になった場合、Pはまずグローバル実行キューからGoroutineを取得しようとします。

### ワークスチール (Work Stealing)

Goスケジューラの重要な機能の一つに**ワークスチール**があります。これは、あるPのローカル実行キューが空になったときに、他のPのローカル実行キューからGoroutineを「盗んで」くるメカニズムです。

ワークスチールは、CPUリソースの利用効率を最大化し、Goroutineの負荷分散を促進するために不可欠です。もしあるPがアイドル状態になった場合、そのPは他のビジーなPからGoroutineを奪い取り、自身のローカル実行キューに追加して実行を開始します。これにより、CPUコアが遊ぶ時間を減らし、全体のスループットを向上させます。

`testSchedLocalQueue` はローカル実行キューの基本的な動作をテストし、`testSchedLocalQueueSteal` はワークスチール機構の動作を検証するための関数です。

### `export_test.go` の役割

Go言語では、通常、パッケージ内の小文字で始まる関数や変数はパッケージ外からはアクセスできません（非エクスポート）。しかし、テストコードではパッケージ内部の非エクスポートされた関数や変数にアクセスしたい場合があります。

`export_test.go` はこの目的のために使用される特別なファイルです。このファイル内で定義された関数や変数は、テストコードからパッケージ内部の非エクスポートされた要素にアクセスするための「ブリッジ」として機能します。例えば、`export_test.go` 内で `func ExportedFunc() { internalFunc() }` のように定義することで、テストコードは `ExportedFunc` を通じて `internalFunc` を呼び出すことができます。

このコミットでは、`testSchedLocalQueue` と `testSchedLocalQueueSteal` が `proc.go` から `export_test.go` に移動され、`RunSchedLocalQueueTest` と `RunSchedLocalQueueStealTest` というエクスポートされたテストヘルパー関数から呼び出される形に変更されました。これにより、これらのテスト関数が `runtime` パッケージの外部にあるテストファイル（例えば `runtime_test.go`）から呼び出せるようになります。

## 技術的詳細

このコミットは、Goランタイムのスケジューラテストの構造を改善することを目的としています。

`proc.go` はGoスケジューラの核心部分であり、Goroutineの作成、実行、スケジューリング、コンテキストスイッチ、ワークスチールなどの低レベルなロジックが含まれています。ここにテスト関数が直接記述されていると、プロダクションコードとテストコードが混在し、コードの意図が不明瞭になる可能性があります。

`export_test.go` は、Goのテストフレームワークが提供する機能の一つで、パッケージの内部状態や非公開関数をテストからアクセス可能にするための標準的な方法です。このファイルにテストヘルパー関数を定義することで、`runtime` パッケージの外部にあるテストファイル（例: `runtime/runtime_test.go`）から、`runtime` パッケージの内部動作を検証するための関数を呼び出すことができます。

具体的には、`proc.go` から `testSchedLocalQueue` と `testSchedLocalQueueSteal` が削除され、その内容が `export_test.go` 内の `RunSchedLocalQueueTest` と `RunSchedLocalQueueStealTest` という新しい関数にそれぞれ移動されました。これらの `Run...Test` 関数は、`runtime` パッケージのテストコードから呼び出されることを想定しています。

この変更により、`proc.go` はよりクリーンになり、スケジューラのコアロジックのみに集中できるようになります。また、テストコードは `export_test.go` に集約され、テストの発見性と管理が容易になります。これは、大規模なプロジェクトにおけるコードベースの健全性を維持するための一般的なプラクティスです。

## コアとなるコードの解説

### `RunSchedLocalQueueTest()` (旧 `testSchedLocalQueue()`)

この関数は、GoスケジューラのP (Processor) が持つローカル実行キュー (`runq`) の基本的な動作をテストします。

1.  `_p_ := new(p)`: 新しいPのインスタンスを作成します。これはテスト用の仮想的なプロセッサとして機能します。
2.  `gs := make([]g, len(_p_.runq))`: Pのローカル実行キューの最大サイズと同じ数のGoroutine (`g`) のスライスを作成します。
3.  ループ (`for i := 0; i < len(_p_.runq); i++`):
    *   各イテレーションで、まずキューが空であることを確認します。空でなければエラー (`throw`) を発生させます。
    *   `j` 回ループして、`gs[i]` のGoroutineをキューに `runqput` します。これにより、キューにGoroutineが追加されます。
    *   再び `j` 回ループして、キューからGoroutineを `runqget` します。取り出されたGoroutineが期待通りのものであるか (`g != &gs[i]`) を検証します。
    *   最後に、キューが再び空であることを確認します。

このテストは、ローカル実行キューへのGoroutineの追加 (`runqput`) と取り出し (`runqget`) が正しく機能し、キューの容量制限内でGoroutineが適切に管理されることを保証します。

### `RunSchedLocalQueueStealTest()` (旧 `testSchedLocalQueueSteal()`)

この関数は、Goスケジューラのワークスチール機構の動作をテストします。ワークスチールは、アイドル状態のPが他のPからGoroutineを「盗む」ことで、CPUリソースの利用効率を高めるための重要なメカニズムです。

1.  `p1 := new(p)` と `p2 := new(p)`: 2つのPのインスタンスを作成します。`p1` はGoroutineを保持する「被害者」のP、`p2` はGoroutineを盗む「加害者」のPとして機能します。
2.  `gs := make([]g, len(p1.runq))`: `p1` のローカル実行キューの最大サイズと同じ数のGoroutineのスライスを作成します。
3.  ループ (`for i := 0; i < len(p1.runq); i++`):
    *   `j` 回ループして、`gs[j]` のGoroutineを `p1` のキューに `runqput` します。これにより、`p1` のキューにGoroutineが蓄積されます。
    *   `gp := runqsteal(p2, p1, true)`: `p2` が `p1` からGoroutineを盗もうとします。`runqsteal` は盗んだGoroutineを返します。
    *   盗んだGoroutineの数 (`s`) をカウントし、`gp.sig++` でGoroutineに何らかのマークを付けます（ここではテスト目的でGoroutineが処理されたことを示す）。
    *   `p2` のキューから残りのGoroutineを `runqget` で取り出し、カウントとマークを更新します。
    *   `p1` のキューから残りのGoroutineを `runqget` で取り出し、マークを更新します。
    *   `gs[j].sig != 1` の検証: 各Goroutineが一度だけ処理されたことを確認します。
    *   `s != i/2 && s != i/2+1` の検証: ワークスチールによって盗まれたGoroutineの数が、期待される範囲内（通常はキューの半分程度）であることを確認します。これは、ワークスチールが一度にキューの半分を盗むというGoスケジューラの挙動を反映しています。

このテストは、`runqsteal` 関数が正しく機能し、GoroutineがP間で効率的に移動されることを保証します。

## 変更の背景

この変更の主な背景は、Go言語の `bytes.Compare` 関数のパフォーマンスを `amd64` アーキテクチャ上で向上させることです。特に、現代のCPUが提供する高度な命令セットであるAVX2（Advanced Vector Extensions 2）を活用することで、バイトスライスの比較処理をより効率的に実行できるようになります。

`bytes.Compare` は、2つのバイトスライスを辞書順に比較し、最初の異なるバイトの値に基づいて負の整数、ゼロ、または正の整数を返します。この関数は、データ構造のソート、ハッシュテーブルのキー比較、ネットワークプロトコルの処理など、様々な場面で頻繁に使用されます。そのため、この関数のパフォーマンス向上は、Goアプリケーション全体の実行速度に大きな影響を与える可能性があります。

コミットメッセージに示されているベンチマーク結果からもわかるように、特に大きなバイトスライス（64バイト以上）の比較において、顕著な速度向上が見られます。これは、AVX2が一度に処理できるデータ量が増えることで、ループの反復回数が減り、CPUのパイプライン効率が向上するためです。

## 前提知識の解説

### AVX (Advanced Vector Extensions) および AVX2

AVX (Advanced Vector Extensions) は、IntelとAMDが開発したx86命令セットアーキテクチャの拡張機能で、SIMD (Single Instruction, Multiple Data) 命令を強化します。SIMD命令は、単一の命令で複数のデータ要素に対して同じ操作を実行することを可能にし、特にメディア処理、科学計算、暗号化、そしてバイト配列操作のような並列性の高いタスクで大きなパフォーマンス向上をもたらします。

-   **AVX**: 2011年に導入され、256ビットのYMMレジスタを導入しました。これにより、一度に4つの倍精度浮動小数点数または8つの単精度浮動小数点数を処理できるようになりました。
-   **AVX2**: 2013年にHaswellマイクロアーキテクチャで導入され、AVXをさらに拡張しました。AVX2の主要な強化点は以下の通りです。
    *   **整数SIMD命令の追加**: AVXは主に浮動小数点数に焦点を当てていましたが、AVX2は256ビットの整数SIMD命令を導入し、整数演算の並列処理能力を大幅に向上させました。
    *   **Gather命令**: メモリ内の非連続な場所からデータを効率的にロードする命令。
    *   **FMA (Fused Multiply-Add) 命令**: 乗算と加算を1つの命令で実行し、浮動小数点演算の精度とスループットを向上させます。

このコミットでは、`bytes.Compare` のようなバイト配列の比較において、AVX2の256ビット整数SIMD命令、特に `VPCMPEQB` (Packed Compare Equal Bytes) や `VPMOVMSKB` (Packed Move Mask to K-register/General-purpose register) が活用されています。これらの命令により、一度に多くのバイトを比較し、その結果を効率的に処理することが可能になります。

### `bytes.Compare` 関数

Go言語の標準ライブラリ `bytes` パッケージに含まれる `Compare` 関数は、2つのバイトスライス `a` と `b` を辞書順に比較します。

-   `a < b` の場合、負の整数を返します。
-   `a == b` の場合、ゼロを返します。
-   `a > b` の場合、正の整数を返します。

この関数は、内部的にはバイト単位でスライスを比較し、最初の異なるバイトが見つかった時点でその比較結果を返します。両方のスライスが同じ長さで、すべてのバイトが一致する場合、ゼロを返します。

### CPU機能検出 (CPUID, OSXSAVE, XGETBV)

現代のCPUは、様々な機能拡張（命令セットなど）をサポートしており、これらの機能はCPUのモデルや世代によって異なります。ソフトウェアが特定の高度な命令セット（AVX2など）を利用するためには、まずその命令セットが現在のCPUでサポートされているかどうかを検出する必要があります。

-   **CPUID命令**: x86アーキテクチャのCPUが提供する命令で、CPUのモデル、機能、キャッシュ情報などをプログラムから問い合わせるために使用されます。特定のレジスタに値を設定してCPUID命令を実行すると、CPUはその機能情報を別のレジスタに返します。AVXやAVX2のサポートもCPUIDを通じて検出されます。
-   **OSXSAVE (Operating System eXtended State Save)**: AVXのような拡張命令セットは、追加のレジスタ（YMMレジスタなど）を使用します。これらのレジスタの状態は、コンテキストスイッチ（タスク切り替え）の際にオペレーティングシステムによって保存・復元される必要があります。OSXSAVEは、OSがこれらの拡張レジスタの状態を管理できることを示すCPUIDフラグです。
-   **XGETBV命令**: OSXSAVEが有効な場合、ソフトウェアは `XGETBV` 命令を使用して、OSがどの拡張レジスタの状態を保存・復元するかを問い合わせることができます。特に、AVXが使用するYMMレジスタのサポートは、`XGETBV` の結果をチェックすることで確認されます。

このコミットでは、`runtime/asm_amd64.s` 内でこれらの命令を組み合わせて、AVXおよびAVX2が利用可能かどうかを正確に判断するロジックが追加されています。

### VEX Prefix

VEX (Vector Extension) プレフィックスは、AVXおよびAVX2命令で使用される新しい命令エンコーディングスキームです。従来のx86命令はREXプレフィックスを使用していましたが、VEXプレフィックスはより多くの情報をエンコードでき、特に以下の利点があります。

-   **3オペランド命令のサポート**: 従来のx86命令は通常2オペランドでしたが、VEXプレフィックスは3オペランド命令を可能にし、デスティネーションレジスタと2つのソースレジスタを指定できます。これにより、非破壊的な操作（ソースオペランドを上書きしない）が可能になり、コンパイラによる最適化が容易になります。
-   **256ビットレジスタのサポート**: YMMレジスタのような256ビットレジスタを効率的に指定できます。
-   **命令のコンパクト化**: 複数のプレフィックスバイトを1つのVEXプレフィックスにまとめることで、命令のバイト数を削減できます。
-   **VEX.Lフィールド**: 128ビットまたは256ビットの操作を指定します。
-   **VEX.VVVVフィールド**: 3つ目のソースレジスタ（またはVEX.Lフィールドと組み合わせて特定の操作）を指定します。

このコミットでは、Goのアセンブラ (`src/cmd/internal/obj/x86/asm6.go`) がAVX2命令を正しくアセンブルするために、VEXプレフィックスの生成ロジックが更新されています。

### Go Assembly (Plan 9スタイル)

Go言語は、独自の「Plan 9」スタイルのアセンブリ言語を使用します。これは、IntelやAT&Tのアセンブリ構文とは異なり、より簡潔で抽象化された構文を持っています。Goのアセンブリは、主にランタイムの低レベルな部分（スケジューラ、メモリ管理、特定の最適化された関数など）や、特定のハードウェア機能（このコミットのようなSIMD命令）を利用するために使用されます。

このコミットで変更されている `src/runtime/asm_amd64.s` は、このPlan 9スタイルのアセンブリで書かれています。

## 技術的詳細

このコミットは、`bytes.Compare` 関数の `amd64` 実装において、AVX2命令セットを利用することでパフォーマンスを大幅に向上させています。技術的な詳細を以下に説明します。

### 1. CPU機能の検出

`src/runtime/asm_amd64.s` の `runtime·rt0_go` 関数（Goランタイムの初期化ルーチンの一部）に、AVXおよびAVX2のサポートを検出するロジックが追加されました。

-   まず、`CPUID` 命令を `AX=1` で実行し、`CX` レジスタのビットをチェックして `OSXSAVE` と `AVX` の両方がサポートされているかを確認します。
-   次に、`XGETBV` 命令（`0x0F; 0x01; 0xD0`）を実行し、`AX` レジスタのビットをチェックして、OSがYMMレジスタ（AVXが使用する256ビットレジスタ）の状態を保存できるかを確認します。
-   これらのチェックが成功した場合、`runtime·support_avx` フラグが `1` に設定されます。
-   さらに、`CPUID` 命令を `AX=7, CX=0` で実行し、`BX` レジスタのビットをチェックして `AVX2` がサポートされているかを確認します。
-   `AVX2` がサポートされている場合、`runtime·support_avx2` フラグが `1` に設定されます。

これらのフラグ (`runtime·support_avx` と `runtime·support_avx2`) は、`src/runtime/runtime2.go` で定義された `bool` 型の変数で、GoコードからCPUのAVX/AVX2サポート状況を参照するために使用されます。

### 2. `bytes.Compare` のAVX2最適化パス

`src/runtime/asm_amd64.s` 内の `runtime·cmpbody` 関数（`bytes.Compare` の内部実装）に、AVX2をサポートするCPU向けの新しい比較ループ `big_loop_avx2` が追加されました。

-   `runtime·cmpbody` の冒頭で、比較対象のバイトスライスの長さ (`R8`) が64バイト以上であり、かつ `runtime·support_avx2` フラグが `1` である場合、`big_loop_avx2` へジャンプします。
-   `big_loop_avx2` は、一度に64バイトを比較するように設計されています。これは、2つの256ビットYMMレジスタ (`X2`, `X3`, `X4`, `X5`) を使用して実現されます。
    -   `MOVHDU (SI), X2` と `MOVHDU (DI), X3` で、最初の32バイトをそれぞれ `X2` と `X3` にロードします。
    -   `MOVHDU 32(SI), X4` と `MOVHDU 32(DI), X5` で、次の32バイトをそれぞれ `X4` と `X5` にロードします。
    -   `VPCMPEQB X2, X3, X0` は、`X2` と `X3` の各バイトを比較し、一致するバイトに対応するビットを `X0` の対応するバイトにセットします（一致すれば0xFF、不一致なら0x00）。
    -   `VPMOVMSKB X0, AX` は、`X0` レジスタの各バイトの最上位ビットを抽出し、それらを `AX` レジスタにパックします。これにより、`X2` と `X3` の32バイトがすべて一致したかどうかを `AX` の値で効率的にチェックできます。
    -   `XORL $0xffffffff, AX` は、`AX` のビットを反転させます。もしすべてのバイトが一致していれば `AX` は0になります。
    -   `JNE diff32_avx2` は、`AX` がゼロでなければ（つまり、最初の32バイトに不一致があれば）、`diff32_avx2` へジャンプします。
    -   同様に、次の32バイト (`X4`, `X5`) も比較され、不一致があれば `diff64_avx2` へジャンプします。
-   64バイトの比較が完了すると、ポインタ (`SI`, `DI`) を64バイト進め、残りのバイト数 (`R8`) を64減らします。残りのバイト数が64未満になるまでこのループを繰り返します。
-   ループの最後に、`VZEROUPPER` 命令が呼び出されます。これは、AVX/AVX2命令の使用後にSSEレジスタ（XMMレジスタ）の上位128ビットをゼロクリアすることで、AVXからSSEへの遷移ペナルティを回避するための重要な最適化です。
-   残りのバイト数が64未満になった場合、または不一致が見つかった場合、通常のバイト単位比較ループ (`loop` または `diff16`, `diff48` など) にフォールバックして、残りのバイトや不一致箇所を処理します。

### 3. アセンブラの変更

AVX2命令をGoのアセンブリコードで使用できるようにするため、Goのアセンブラ自体にも変更が加えられました。

-   `src/cmd/internal/obj/x86/a.out.go` と `src/cmd/internal/obj/x86/anames.go` に、新しいAVX2命令である `AVPCMPEQB` と `AVPMOVMSKB` が追加されました。これにより、アセンブラがこれらの命令を認識できるようになります。
-   `src/cmd/internal/obj/x86/asm6.go` では、VEXプレフィックスを生成する `vexprefix` 関数が拡張されました。
    -   `vexprefix` 関数は、3オペランド命令をサポートするために `from3` という新しい引数を取るようになりました。
    -   VEXプレフィックスのエンコーディングロジックが更新され、`VEX.VVVV` フィールドが3つ目のソースレジスタを正しくエンコードするように変更されました。
    -   2バイトおよび3バイトのVEXプレフィックスの生成ロジックが、AVX2命令の要件に合わせて調整されました。
    -   新しい命令 (`AVPCMPEQB`, `AVPMOVMSKB`) のオペランドタイプ (`yxm_xm_xm`, `ymskb_vex`) が定義され、`optab` に追加されました。これにより、アセンブラがこれらの命令を正しく解析し、機械語に変換できるようになります。

## コアとなるコードの解説

### `src/runtime/asm_amd64.s` の解説

1.  **CPU機能検出 (`runtime·rt0_go` 内)**:
    -   `CPUID` 命令は、CPUの機能を問い合わせるための標準的な方法です。`AX=1` で実行すると、`CX` レジスタに拡張機能情報が返されます。`0x18000000` は `OSXSAVE` (bit 27) と `AVX` (bit 28) のフラグをチェックしています。
    -   `XGETBV` 命令は、OSが拡張レジスタの状態を管理しているかを確認するために使用されます。`AX` のビット6がYMMレジスタのサポートを示します。
    -   `AX=7, CX=0` で `CPUID` を実行すると、`BX` レジスタにAVX2のサポート情報が返されます。`0x20` はAVX2のフラグ（bit 5）です。
    -   これらのチェック結果に基づいて、`runtime·support_avx` と `runtime·support_avx2` というグローバルな `bool` 変数（`src/runtime/runtime2.go` で定義）が設定されます。これにより、Goのコードや他のアセンブリコードからAVX/AVX2の利用可能性を判断できます。

2.  **`bytes.Compare` のAVX2高速化パス (`runtime·cmpbody` 内)**:
    -   `CMPQ R8, $63` と `JBE loop` は、比較対象の長さ `R8` が63バイト以下の場合、従来のバイト単位比較ループ (`loop`) にフォールバックすることを示しています。これは、AVX2のオーバーヘッドが小さいデータサイズではメリットが少ないためです。
    -   `CMPB runtime·support_avx2(SB), $1` と `JEQ big_loop_avx2` は、AVX2がサポートされている場合に `big_loop_avx2` へ分岐する条件分岐です。
    -   **`big_loop_avx2`**:
        -   `MOVHDU (SI), X2` と `MOVHDU (DI), X3`: `SI` と `DI` が指すメモリ位置からそれぞれ32バイト（256ビット）のデータをYMMレジスタ `X2` と `X3` にロードします。`MOVHDU` は "Move Unaligned Doubleword" の略で、アラインメントされていないメモリからのロードを効率的に行います。
        -   `VPCMPEQB X2, X3, X0`: `X2` と `X3` の各バイトを並列に比較します。結果は `X0` に格納され、一致するバイトは `0xFF`、不一致のバイトは `0x00` となります。
        -   `VPMOVMSKB X0, AX`: `X0` レジスタの各バイトの最上位ビットを抽出し、それらを汎用レジスタ `AX` にパックします。例えば、`X0` の32バイトがすべて `0xFF` であれば、`AX` は `0xFFFFFFFF` となります。
        -   `XORL $0xffffffff, AX`: `AX` のビットを反転させます。これにより、すべてのバイトが一致していれば `AX` は `0x00000000` となり、不一致があれば非ゼロの値になります。
        -   `JNE diff32_avx2`: `AX` が非ゼロであれば、不一致が見つかったことを意味するため、`diff32_avx2` へジャンプして詳細な比較を行います。
        -   同様の処理が次の32バイト (`X4`, `X5`) に対して行われます。
        -   `ADDQ $64, SI` / `ADDQ $64, DI` / `SUBQ $64, R8`: ポインタを64バイト進め、残りのバイト数を更新します。
        -   `VZEROUPPER`: AVX命令の使用後に呼び出される重要な命令です。AVX命令はYMMレジスタを使用しますが、SSE命令はXMMレジスタ（YMMレジスタの下位128ビット）を使用します。AVX命令からSSE命令に切り替える際に、YMMレジスタの上位128ビットがダーティな状態になっていると、CPUは「AVX-SSE遷移ペナルティ」と呼ばれる性能低下を引き起こす可能性があります。`VZEROUPPER` はYMMレジスタの上位128ビットをゼロクリアすることで、このペナルティを回避し、SSE命令との共存を効率的にします。

### `src/cmd/internal/obj/x86/asm6.go` の解説

-   **`vexprefix` 関数の変更**:
    -   `vexprefix` 関数は、GoのアセンブラがVEXプレフィックスを生成するための中心的な関数です。このコミットでは、3オペランド命令をサポートするために `from3` という新しい引数が追加されました。
    -   VEXプレフィックスは、命令のオペランド、レジスタのサイズ、およびその他の制御情報をエンコードします。特に、`VEX.VVVV` フィールドは3つ目のソースレジスタ（または特定の操作）を指定するために使用されます。変更されたロジックは、この `VEX.VVVV` フィールドを `from3` 引数に基づいて正しく設定します。
    -   `VEX encodes REX.R as inversed upper bit` や `REX.[RXB] are inverted and encoded in 3 upper bits` といったコメントは、VEXプレフィックスが従来のREXプレフィックスとは異なる方法でレジスタ拡張ビットをエンコードすることを示しています。これは、アセンブラが正しい機械語を生成するために不可欠な詳細です。
-   **新しい命令の追加**:
    -   `AVPCMPEQB` と `AVPMOVMSKB` という新しい命令が `optab` に追加され、それぞれに対応するオペランドタイプ (`yxm_xm_xm`, `ymskb_vex`) が定義されました。これにより、GoのアセンブラはこれらのAVX2命令を認識し、Goのアセンブリコード内で使用できるようになります。

# [インデックス 20430] ファイルの概要

このコミットは、Goランタイムにおける`time.now`関数の実装を、Plan 9、Solaris、Windowsといった特定のオペレーティングシステム（OS）上でアセンブリ言語に移行する変更を加えています。これにより、これらのOSにおける時刻取得処理の効率とパフォーマンスが向上しています。

## コミット

```

Author: Russ Cox <rsc@golang.org>
Date:   Sun Sep 7 23:40:59 2014 -0400

    runtime: implement time.now in assembly on plan9, solaris, windows
    
    These all used a C implementation that contained 64-bit divide by 1000000000.
    On 32-bit systems that ends up in the 64-bit C divide support, which makes
    other calls and ends up using a fair amount of stack. We could convert them
    to Go but then they'd still end up in software 64-bit divide code. That would
    be okay, because Go code can split the stack, but it's still unnecessary.

    actual hardware support for 64/32 -> 64/32 division. This cuts the software
    routines out entirely.
```

## 元コミット内容

このコミットの目的は、Goランタイムの`time.now`関数（内部的には`time·now`として参照される）の実装を、Plan 9、Solaris、およびWindowsオペレーティングシステムにおいて、C言語からアセンブリ言語に切り替えることです。

以前のC言語実装では、ナノ秒単位の時刻を秒とナノ秒（またはマイクロ秒）に変換するために、64ビット整数を10億（1,000,000,000）で除算する処理が含まれていました。特に32ビットシステムでは、この64ビット除算がソフトウェアによる64ビット除算サポートルーチンを呼び出すことになり、これが追加の関数呼び出しやスタックの使用量の増加を引き起こしていました。

コミットメッセージでは、この処理をGo言語に変換することも可能だが、それでもソフトウェアによる64ビット除算コードが使用されることになり、Goのスタック分割機能があるとはいえ、不必要であると指摘しています。

そこで、他のシステム（例: Darwin）と同様に、`time·now`をアセンブリ言語で記述し、CPUの持つ64ビット/32ビット除算のハードウェアサポートを直接利用することで、ソフトウェアによる除算ルーチンを完全に排除することを目指しています。これにより、パフォーマンスの向上とリソース使用量の削減が期待されます。除算を行う実際のアセンブリコードは、既存の`sys_darwin_*.s`ファイルからコピー＆ペーストされています。

## 変更の背景

この変更の背景には、Goランタイムのパフォーマンス最適化と、特定のOSにおけるシステムコールや低レベル処理の効率化があります。

1.  **64ビット除算のオーバーヘッド**: 32ビットシステムにおいて、64ビット整数に対する除算は、CPUが直接サポートしていない場合、コンパイラが生成するソフトウェアエミュレーションルーチンによって処理されます。これは複数の命令から構成され、通常のハードウェア除算に比べてはるかに多くのCPUサイクルとスタック領域を消費します。`time.now`のような頻繁に呼び出される可能性のある関数でこのオーバーヘッドが発生すると、システム全体のパフォーマンスに影響を与えます。
2.  **スタック使用量の削減**: ソフトウェア除算ルーチンが追加の関数呼び出しを伴う場合、それらはスタック上にフレームを構築し、スタック使用量を増加させます。Goのランタイムはスタックを動的に拡張する「スタック分割」機能を持っていますが、不必要なスタック使用は、スタックの拡張・縮小に伴うオーバーヘッドや、キャッシュ効率の低下を招く可能性があります。
3.  **ハードウェアの活用**: 現代のCPUは、64ビット整数に対する除算を効率的に実行するための専用のハードウェア命令（例: x86-64アーキテクチャの`DIVQ`命令や、32ビットアーキテクチャの`DIVL`命令とレジスタの組み合わせ）を持っています。これらの命令を直接利用することで、ソフトウェアエミュレーションのオーバーヘッドを完全に回避し、最高のパフォーマンスを引き出すことができます。
4.  **一貫性の確保**: 他の主要なOS（特にDarwin）では既に`time.now`がアセンブリ言語で実装されており、ハードウェア除算を利用していました。今回の変更は、Plan 9、Solaris、Windowsにおいても同様のアプローチを採用することで、Goランタイムの低レベルな時刻取得処理における実装の一貫性を高めるものです。

これらの理由から、`time.now`のような基本的なかつ頻繁に利用される関数において、低レベルなアセンブリ最適化を行うことは、Goアプリケーション全体のパフォーマンスと効率を向上させる上で重要な意味を持ちます。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念について基本的な知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Go言語のプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、チャネル通信、メモリ管理、そしてOSとの低レベルなインタラクション（システムコールなど）といった、Goプログラムの実行に必要な多くの機能を提供します。`time.now`のような関数は、ランタイムの一部として実装され、OSの時刻取得機能と連携します。

2.  **`time.now` と `nanotime`**:
    *   `time.now` (または内部的な `time·now`): Goの標準ライブラリ`time`パッケージが提供する時刻取得機能の基盤となる関数です。通常、現在の時刻を秒とナノ秒（またはマイクロ秒）の形式で返します。
    *   `nanotime`: Goランタイムが提供する、システムからナノ秒単位のモノトニックな時刻（システム起動時からの経過時間など、単調増加する時刻）を取得する低レベルな関数です。`time.now`は、この`nanotime`の値を基に、エポック（1970年1月1日）からの経過秒数と残りのナノ秒数を計算します。

3.  **アセンブリ言語 (Assembly Language)**:
    CPUが直接実行できる機械語（バイナリコード）を、人間が読み書きしやすいようにニーモニック（命令の略語）で表現した低レベルなプログラミング言語です。アセンブリ言語を使用すると、CPUのレジスタや命令セットを直接操作できるため、C言語などの高水準言語では実現が難しい、極めて高速で効率的なコードを記述できます。Goランタイムのパフォーマンスが重要な部分では、アセンブリ言語が積極的に利用されています。

4.  **64ビット整数除算 (64-bit Integer Division)**:
    *   **32ビットシステムでの課題**: 32ビットCPUは、通常、32ビット幅のレジスタと命令セットを持っています。このため、64ビット整数を扱う場合、複数の32ビットレジスタを組み合わせて表現し、除算のような演算は複数の32ビット命令を組み合わせて実行するか、コンパイラが提供するソフトウェアルーチン（ヘルパー関数）を呼び出して処理します。このソフトウェアルーチンは、複雑なアルゴリズムと多くのCPUサイクルを必要とし、パフォーマンスのボトルネックとなることがあります。
    *   **ハードウェア除算**: 64ビットCPU（例: x86-64アーキテクチャ）は、64ビット幅のレジスタと、64ビット整数を直接除算できる専用のハードウェア命令（例: `DIVQ`）を持っています。これにより、非常に高速に除算を実行できます。
    *   **`DIVL` (32-bit division on x86)**: 32ビットx86アーキテクチャでは、`DIVL`命令は32ビット除算を行います。しかし、64ビット値を32ビット値で除算する場合、`EDX:EAX`レジスタペア（64ビット値）を32ビット値で除算し、商を`EAX`に、剰余を`EDX`に格納する形式で利用できます。これは、64ビット値を32ビット値で割る場合にハードウェアサポートを利用する典型的な方法です。

5.  **`NOSPLIT` プラグマ**:
    Goのアセンブリコードや一部のCコードに見られる`#pragma textflag NOSPLIT`は、その関数がスタックを分割しないことをコンパイラに指示するものです。これは、非常に短い、スタックをほとんど使用しない関数や、スタック分割のオーバーヘッドを避けたい低レベルな関数（特にランタイムのコア部分）で使われます。このコミットの変更前後のCコードにも見られます。

これらの知識を持つことで、なぜこのコミットが重要であり、どのような技術的課題を解決しようとしているのかを深く理解できます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の点に集約されます。

1.  **C言語実装の削除とアセンブリ言語への移行**:
    *   `src/pkg/runtime/os_plan9.c`、`src/pkg/runtime/os_solaris.c`、`src/pkg/runtime/os_windows.c`から、`time·now`関数のC言語実装が削除されました。これらの実装は、`runtime·nanotime()`から取得したナノ秒値を`1000000000LL`（10億）で除算して秒とナノ秒（またはマイクロ秒）を計算していました。
    *   特にWindowsのC実装では、`runtime·systime()`から取得した100ナノ秒単位の値を、エポックからの経過時間に変換し、さらに10億で除算していました。
    *   これらのC言語による除算が、32ビットシステムではソフトウェアエミュレーションにフォールバックし、パフォーマンスとスタック使用量の問題を引き起こしていました。

2.  **アセンブリ言語による64ビット除算の最適化**:
    *   新しいアセンブリ実装は、各OS/アーキテクチャ固有のファイル（`sys_plan9_386.s`, `sys_plan9_amd64.s`, `sys_solaris_amd64.s`, `sys_windows_386.s`, `sys_windows_amd64.s`）に追加されました。
    *   これらのアセンブリコードは、`runtime·nanotime`（またはWindowsの場合は`runtime·unixnano`）から64ビットのナノ秒値を取得し、それを10億で除算して秒とナノ秒（またはマイクロ秒）を計算します。
    *   **32ビットアーキテクチャ (i386)**: `sys_plan9_386.s`と`sys_windows_386.s`では、`DIVL`命令が使用されています。`DIVL CX`は、`EDX:EAX`レジスタペアに格納された64ビット値を`CX`レジスタの32ビット値で除算し、商を`EAX`に、剰余を`EDX`に格納します。これにより、32ビットCPU上で64ビット除算をハードウェアレベルで効率的に実行しています。
        ```assembly
        MOVL    0(SP), AX   // Load lower 32 bits of ns into EAX
        MOVL    4(SP), DX   // Load upper 32 bits of ns into EDX (EDX:EAX forms 64-bit dividend)
        MOVL    $1000000000, CX // Divisor (1 billion) into CX
        DIVL    CX          // EDX:EAX / CX -> EAX=quotient, EDX=remainder
        MOVL    AX, sec+0(FP) // Store quotient (seconds)
        MOVL    $0, sec+4(FP) // Upper 32 bits of seconds (0 for 32-bit systems)
        MOVL    DX, nsec+8(FP) // Store remainder (nanoseconds)
        ```
    *   **64ビットアーキテクチャ (amd64)**: `sys_plan9_amd64.s`, `sys_solaris_amd64.s`, `sys_windows_amd64.s`では、より複雑な、しかし非常に効率的な乗算による除算（Magic Number Division）のテクニックが使用されています。これは、除算を乗算とビットシフトの組み合わせに変換することで、`DIVQ`命令よりもさらに高速に実行できる場合があります。このコードは、コミットメッセージにあるように、`sys_darwin_amd64.s`からコピーされたものです。
        ```assembly
        MOVQ    0(SP), AX   // Load 64-bit ns into AX
        MOVQ    AX, CX      // Copy ns to CX for remainder calculation
        MOVQ    $1360296554856532783, AX // Magic number for division by 1 billion
        MULQ    CX          // AX * CX (unsigned multiplication), result in DX:AX
                            // DX contains the high 64 bits of the 128-bit product
        ADDQ    CX, DX      // Adjust DX (part of magic number division algorithm)
        RCRQ    $1, DX      // Rotate right with carry (part of magic number division algorithm)
        SHRQ    $29, DX     // Shift right by 29 bits (part of magic number division algorithm)
        MOVQ    DX, sec+0(FP) // DX now holds the quotient (seconds)
        IMULQ   $1000000000, DX // Multiply quotient by 1 billion
        SUBQ    DX, CX      // Subtract from original ns to get remainder
        MOVL    CX, nsec+8(FP) // Store remainder (nanoseconds)
        ```
        この「Magic Number Division」は、`x / D` を `x * (2^N / D) / 2^N` の形式で計算する最適化手法です。ここで `(2^N / D)` がマジックナンバーとなります。これにより、高価な除算命令を、より安価な乗算とビットシフト命令に置き換えることができます。

3.  **`runtime·unixnano`の導入 (Windows)**:
    Windowsの`os_windows.c`では、`time·now`のC実装が削除される代わりに、`runtime·unixnano`という新しいC関数が追加されました。この関数は、Windowsのシステム時刻（100ナノ秒単位）をUnixエポックからのナノ秒に変換する役割を担います。これにより、アセンブリ実装の`time·now`は、この`runtime·unixnano`を呼び出して、変換済みのナノ秒値を取得できるようになります。

これらの変更により、Goランタイムは、Plan 9、Solaris、Windowsにおいても、時刻取得処理における64ビット除算を、OSやアーキテクチャの特性に応じた最も効率的な方法で実行できるようになりました。

## コアとなるコードの解説

ここでは、追加されたアセンブリコードの主要な部分を解説します。

### 32ビットシステム (Plan 9 386, Windows 386) のアセンブリコード (`sys_plan9_386.s`, `sys_windows_386.s`より抜粋)

```assembly
// func now() (sec int64, nsec int32)
TEXT time·now(SB),NOSPLIT,$8-12
    CALL    runtime·nanotime(SB) // または runtime·unixnano(SB) for Windows
    MOVL    0(SP), AX            // runtime·nanotime()の戻り値（ナノ秒、下位32ビット）をEAXへ
    MOVL    4(SP), DX            // runtime·nanotime()の戻り値（ナノ秒、上位32ビット）をEDXへ

    MOVL    $1000000000, CX      // 除数（10億）をECXへ
    DIVL    CX                   // EDX:EAX / ECX を実行。商はEAX、剰余はEDXに格納
    MOVL    AX, sec+0(FP)        // 商（秒）の下位32ビットをsecのメモリ位置へ
    MOVL    $0, sec+4(FP)        // 商（秒）の上位32ビットを0に設定（64ビット値のsecを構成）
    MOVL    DX, nsec+8(FP)       // 剰余（ナノ秒）をnsecのメモリ位置へ
    RET
```

*   **`TEXT time·now(SB),NOSPLIT,$8-12`**: `time·now`という関数を定義します。`SB`はシンボルベースレジスタ、`NOSPLIT`はスタック分割を行わないことを示します。`$8-12`は、この関数が8バイトのスタックフレームを使用し、12バイトの戻り値（`sec`が8バイト、`nsec`が4バイト）を返すことを示します。
*   **`CALL runtime·nanotime(SB)`**: まず、システムからナノ秒単位の時刻を取得する`runtime·nanotime`（Windowsの場合は`runtime·unixnano`）を呼び出します。この関数は64ビットのナノ秒値をスタックにプッシュして返します。
*   **`MOVL 0(SP), AX` / `MOVL 4(SP), DX`**: スタックにプッシュされた64ビットのナノ秒値（下位32ビットが`0(SP)`、上位32ビットが`4(SP)`）を、それぞれ`EAX`と`EDX`レジスタにロードします。`EDX:EAX`は、x86アーキテクチャで64ビットの被除数を表す一般的なレジスタペアです。
*   **`MOVL $1000000000, CX`**: 除数である10億（ナノ秒を秒に変換するため）を`ECX`レジスタにロードします。
*   **`DIVL CX`**: これが核心的な命令です。`DIVL`命令は、`EDX:EAX`レジスタペアに格納された64ビットの値を、`CX`レジスタに格納された32ビットの値で除算します。結果として、商（秒）は`EAX`に、剰余（ナノ秒）は`EDX`に格納されます。これは、32ビットCPU上で64ビット除算をハードウェアレベルで実行する効率的な方法です。
*   **`MOVL AX, sec+0(FP)` / `MOVL $0, sec+4(FP)`**: `EAX`に格納された商（秒）を、戻り値の`sec`（64ビット整数）の下位32ビットに格納します。`sec`の上位32ビットは0に設定されます。
*   **`MOVL DX, nsec+8(FP)`**: `EDX`に格納された剰余（ナノ秒）を、戻り値の`nsec`（32ビット整数）に格納します。
*   **`RET`**: 関数から戻ります。

### 64ビットシステム (Plan 9 AMD64, Solaris AMD64, Windows AMD64) のアセンブリコード (`sys_plan9_amd64.s`, `sys_solaris_amd64.s`, `sys_windows_amd64.s`より抜粋)

```assembly
// func now() (sec int64, nsec int32)
TEXT time·now(SB),NOSPLIT,$8-12
    CALL    runtime·nanotime(SB) // または runtime·unixnano(SB) for Windows
    MOVQ    0(SP), AX            // runtime·nanotime()の戻り値（ナノ秒、64ビット）をRAXへ

    // generated code for
    //  func f(x uint64) (uint64, uint64) { return x/1000000000, x%100000000 }
    // adapted to reduce duplication
    MOVQ    AX, CX               // ナノ秒値をRCXへコピー
    MOVQ    $1360296554856532783, AX // マジックナンバーをRAXへ
    MULQ    CX                   // RAX * RCX (符号なし乗算)。結果はRDX:RAX（128ビット）
                                 // RDXには上位64ビット（商の近似値）が格納される
    ADDQ    CX, DX               // マジックナンバー除算の調整ステップ
    RCRQ    $1, DX               // マジックナンバー除算の調整ステップ
    SHRQ    $29, DX              // マジックナンバー除算の調整ステップ
    MOVQ    DX, sec+0(FP)        // RDXに格納された商（秒）をsecのメモリ位置へ
    IMULQ   $1000000000, DX      // 商（秒）に10億を乗算
    SUBQ    DX, CX               // 元のナノ秒値から乗算結果を減算して剰余を求める
    MOVL    CX, nsec+8(FP)       // 剰余（ナノ秒）をnsecのメモリ位置へ
    RET
```

*   **`MOVQ 0(SP), AX`**: `runtime·nanotime`（または`runtime·unixnano`）から返された64ビットのナノ秒値を`RAX`レジスタにロードします。
*   **`MOVQ AX, CX`**: ナノ秒値を`RCX`レジスタにコピーします。これは剰余計算のために元の値を保持するためです。
*   **`MOVQ $1360296554856532783, AX`**: ここで「マジックナンバー」を`RAX`にロードします。このマジックナンバーは、10億で除算するための乗数として機能します。
*   **`MULQ CX`**: `RAX`（マジックナンバー）と`RCX`（ナノ秒値）の符号なし64ビット乗算を実行します。結果は128ビットとなり、上位64ビットが`RDX`に、下位64ビットが`RAX`に格納されます。この`RDX`が、除算の商の近似値となります。
*   **`ADDQ CX, DX` / `RCRQ $1, DX` / `SHRQ $29, DX`**: これらの命令は、マジックナンバー除算アルゴリズムの一部であり、`RDX`に格納された近似値を正確な商に調整するためのビット操作です。
*   **`MOVQ DX, sec+0(FP)`**: 調整された`RDX`の値（正確な商、つまり秒数）を戻り値の`sec`に格納します。
*   **`IMULQ $1000000000, DX`**: 計算された秒数に10億を乗算します。
*   **`SUBQ DX, CX`**: 元のナノ秒値（`CX`に保持されていた）から、秒数に10億を乗算した値を減算することで、剰余（ナノ秒）を計算します。
*   **`MOVL CX, nsec+8(FP)`**: 計算された剰余（ナノ秒）を戻り値の`nsec`に格納します。
*   **`RET`**: 関数から戻ります。

このアセンブリコードは、Goランタイムが特定のOS/アーキテクチャで時刻取得をいかに効率的に行っているかを示す良い例です。特に64ビットシステムでのマジックナンバー除算は、高度な最適化テクニックであり、CPUのパイプラインを最大限に活用して高速な実行を実現しています。

## 変更の背景

このコミットは、Go言語のコードを整形する `go/printer` パッケージにおける、関数パラメータと関数本体のネストレベル（インデント）の修正を目的としています。Go言語のコードは、その可読性を高めるために厳格なフォーマット規則を持っています。`go/printer` は、これらの規則に従ってASTからコードを再構築する際に、正しいインデントを適用する必要があります。

以前の実装では、関数パラメータや関数本体のインデントが期待通りに適用されておらず、生成されるコードのフォーマットが不適切になる可能性がありました。特に、パラメータリストが複数行にわたる場合や、関数リテラル（匿名関数）や通常の関数宣言の本体のインデントが正しくなかったと考えられます。このコミットは、`p.level` というインデントレベルを管理する変数の増減タイミングを調整することで、これらのフォーマットの問題を解決しようとしています。

## 前提知識の解説

### Go言語の抽象構文木 (AST)

Goコンパイラやツールは、Goのソースコードを直接扱うのではなく、まずそれを抽象構文木（Abstract Syntax Tree, AST）と呼ばれるデータ構造に変換します。ASTは、プログラムの構造を木構造で表現したもので、各ノードがコードの要素（変数宣言、関数呼び出し、式など）に対応します。Go言語では、`go/ast` パッケージがこのASTの定義と操作を提供します。

### `go/printer` パッケージ

`go/printer` パッケージは、`go/ast` パッケージで定義されたASTを受け取り、それをGo言語のソースコードとして出力（pretty-print）する機能を提供します。このパッケージは、Go言語の公式フォーマッタである `gofmt` の基盤としても使用されており、Goコードの標準的なフォーマットを保証する上で非常に重要な役割を担っています。

`go/printer` は、ASTを走査しながら、適切なキーワード、識別子、演算子などを出力し、同時にGoのフォーマット規則に従って空白、改行、そして最も重要なインデントを挿入します。

### インデントレベルの管理

`go/printer` のようなコード整形ツールでは、現在のコードがどの程度の深さでネストしているかを追跡し、それに応じてインデントを適用する必要があります。通常、これは内部的なカウンタ（このコミットでは `p.level`）によって管理されます。ブロックの開始（例: `{`）でカウンタを増やし、ブロックの終了（例: `}`）でカウンタを減らすことで、正しいインデントレベルを維持します。

### `*ast.FuncLit` と `*ast.FuncDecl`

GoのASTにおいて、関数は主に以下の2つのノードで表現されます。

*   `*ast.FuncLit`: 関数リテラル（匿名関数）を表します。例えば `func(x int) { ... }` のような形式です。
*   `*ast.FuncDecl`: 通常の関数宣言を表します。例えば `func MyFunc(x int) { ... }` やメソッド宣言 `func (r *Receiver) Method() { ... }` のような形式です。

これらのノードは、それぞれ関数シグネチャ（パラメータと戻り値）と関数本体（ブロックステートメント）を含んでいます。

### `*ast.Field`

`*ast.Field` は、関数パラメータ、構造体フィールド、インターフェースメソッドのパラメータなど、名前と型を持つ要素を表すASTノードです。関数パラメータリストは `[]*ast.Field` のスライスとして表現されます。

## 技術的詳細

`go/printer` パッケージの `printer` 構造体は、コード整形のための状態を保持しています。この状態の一つが `p.level` であり、これは現在のインデントレベルを示す整数値です。`p.level` の値が増えるたびに、出力されるコードのインデントが深くなります。

このコミットの目的は、関数パラメータリストと関数本体の整形において、`p.level` の増減がGoの標準的なフォーマット規則に合致するように調整することです。

具体的には、以下のAST要素の処理において `p.level` の調整が行われています。

1.  **関数パラメータリスト (`parameters` メソッド)**:
    関数宣言や関数リテラルのパラメータリストは、括弧 `()` で囲まれます。パラメータが複数行にわたる場合、各パラメータは括弧に対してインデントされるべきです。このコミット以前は、パラメータリスト全体がインデントされないか、不適切にインデントされていた可能性があります。

2.  **関数リテラルの本体 (`expr1` メソッド内の `*ast.FuncLit` ケース)**:
    関数リテラルの本体は、その関数リテラルが記述されているコンテキストに対してインデントされるべきです。`{ ... }` で囲まれた関数本体は、その開始ブレース `{` の位置から一段階深くインデントされるのがGoの慣習です。

3.  **関数宣言の本体 (`decl` メソッド内の `*ast.FuncDecl` ケース)**:
    通常の関数宣言の本体も、関数リテラルと同様に、その関数宣言のシグネチャに対して一段階深くインデントされるべきです。

このコミットは、これらのケースで `p.level++` と `p.level--` の位置を微調整することで、`go/printer` が生成するコードのインデントがGoの標準フォーマットに完全に準拠するようにしています。

## コアとなるコードの解説

このコミットの変更は、`go/printer` がGoコードを整形する際のインデントロジックをより正確にするためのものです。

1.  **`parameters` メソッドの変更**:
    -   `if len(list) > 0 { p.level++; ... p.level--; }`
    -   この変更により、関数やメソッドのパラメータリストが空でない場合にのみ、パラメータの出力前にインデントレベルが一段階増加し、パラメータの出力後に元に戻されます。これにより、複数行にわたるパラメータリストが、開始括弧 `(` に対して適切にインデントされるようになります。例えば、以下のようなコードが正しく整形されます。
        ```go
        func MyFunc(
            param1 type1,
            param2 type2,
        ) {
            // ...
        }
        ```
        以前は、`param1` や `param2` が `(` と同じインデントレベルになってしまうなど、不適切な整形が行われていた可能性があります。

2.  **`expr1` メソッド内の `*ast.FuncLit` ケースの変更**:
    -   `p.level++;` の位置が `p.expr(x.Type);` の前から `p.stmt(x.Body);` の直前に移動しました。
    -   関数リテラル `func(args) { body }` の場合、`x.Type` は関数シグネチャ（`func(args)` の部分）を表し、`x.Body` は関数本体（`{ body }` の部分）を表します。
    -   この修正により、関数シグネチャ自体は現在のインデントレベルで出力され、その後の関数本体 `{ body }` が始まる直前でインデントレベルが一段階増加するようになりました。これにより、関数本体がシグネチャに対して適切にインデントされるようになります。

3.  **`decl` メソッド内の `*ast.FuncDecl` ケースの変更**:
    -   `p.level++;` の位置が `p.doc(d.Doc);` の前から `p.stmt(d.Body);` の直前に移動し、対応する `p.level--;` も `p.stmt(d.Body);` の直後に移動しました。
    -   `*ast.FuncDecl` は通常の関数宣言を表します。`d.Doc` はドキュメントコメント、`d.Type` は関数シグネチャ、`d.Body` は関数本体です。
    -   この変更も `*ast.FuncLit` のケースと同様に、関数宣言のシグネチャ自体は現在のインデントレベルで出力され、関数本体 `{ body }` が始まる直前でインデントレベルが一段階増加し、本体の出力後に元に戻されるように調整されました。これにより、関数本体が関数シグネチャに対して正しくインデントされることが保証されます。

これらの変更は、`go/printer` がGo言語のコードを整形する際に、関数定義（パラメータリストと本体）のインデントがGoの標準的なスタイルガイドラインに沿うようにするための、細かしかし重要な修正です。これにより、`gofmt` を通じて出力されるGoコードの一貫性と可読性が向上します。

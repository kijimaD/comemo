## 変更の背景

このコミットの背景には、Goのツールチェイン（特にコンパイラとリンカ）の内部I/O処理における設計の改善があります。以前は `src/cmd/internal/bio` パッケージに `bio.Buf` という単一の型が存在し、これがファイルの読み込みと書き込みの両方を処理していました。この `bio.Buf` は `os.File` をラップし、`bufio.Reader` と `bufio.Writer` の両方を内部に持つことで、双方向のバッファリングされたI/Oを提供していました。

しかし、このような双方向のインターフェースは、Goの標準ライブラリにおける `io.Reader` と `io.Writer` の設計思想とは異なります。Goの `io` パッケージでは、読み込みと書き込みは明確に分離されたインターフェースとして定義されており、それぞれの責務が単一であるべきという「単一責任の原則 (Single Responsibility Principle)」に則っています。`bio.Buf` のような双方向の型は、コードの意図を曖昧にし、特定の操作（読み込みか書き込みか）がどのバッファリングメカニズムに影響を与えるのかを理解しにくくする可能性がありました。

このコミットは、この設計上の不整合を解消し、Goの標準的なI/Oインターフェースの慣習に合わせることを目的としています。`bio.Buf` を `bio.Reader` と `bio.Writer` という2つの独立した型に分割することで、各型の責務が明確になり、コードの可読性、保守性、そして将来的な拡張性が向上します。また、これにより、Goの標準ライブラリの `io` パッケージとの互換性も高まります。

## 前提知識の解説

このコミットを理解するためには、以下のGoのI/Oに関する基本的な概念と、Goツールチェインの構造に関する知識が必要です。

### 1. `io.Reader` と `io.Writer` インターフェース
Go言語におけるI/O操作の根幹をなすインターフェースです。
*   **`io.Reader`**: データを読み込むためのインターフェースで、`Read(p []byte) (n int, err error)` メソッドを定義します。これは、バイトスライス `p` にデータを読み込み、読み込んだバイト数 `n` とエラー `err` を返します。
*   **`io.Writer`**: データを書き込むためのインターフェースで、`Write(p []byte) (n int, err error)` メソッドを定義します。これは、バイトスライス `p` のデータを書き込み、書き込んだバイト数 `n` とエラー `err` を返します。
これらのインターフェースは、Goの「インターフェースは小さく、責務は単一に」という設計哲学を体現しています。

### 2. `bufio.Reader` と `bufio.Writer`
`io.Reader` や `io.Writer` の上に構築され、バッファリング機能を提供することでI/O性能を向上させる型です。
*   **`bufio.Reader`**: 内部にバッファを持ち、一度に多くのデータを読み込むことで、基となる `io.Reader` への呼び出し回数を減らします。
*   **`bufio.Writer`**: 内部にバッファを持ち、データを一時的に蓄積し、バッファがいっぱいになったときや `Flush()` が呼ばれたときにまとめて基となる `io.Writer` に書き込むことで、書き込み効率を高めます。

### 3. `os.File`
ファイルシステム上のファイルを表す型です。`os.File` は `io.Reader`、`io.Writer`、`io.Seeker` などのインターフェースを実装しており、ファイルに対する読み書きやシーク操作を可能にします。

### 4. `bio.Buf` (変更前の型)
このコミットで置き換えられる `src/cmd/internal/bio` パッケージ内のカスタム型です。`os.File` をラップし、`bufio.Reader` と `bufio.Writer` の両方を内部に保持していました。これにより、一つの `bio.Buf` インスタンスでファイルの読み書き両方を行うことができましたが、そのAPIは `io.Reader` や `io.Writer` の慣習から逸脱しており、内部状態の管理が複雑になる可能性がありました。

### 5. Goのコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)
Goのビルドプロセスにおける主要なツールです。
*   **コンパイラ**: Goのソースコードをオブジェクトファイル（`.o` ファイル）に変換します。
*   **リンカ**: 複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成します。
これらのツールは、ビルド中に大量のI/O操作を行うため、効率的で堅牢なI/Oメカニズムが不可欠です。`src/cmd/internal/bio` パッケージは、これらのツール内部で利用されるI/Oユーティリティを提供していました。

## 技術的詳細

このコミットの技術的な核心は、`bio.Buf` という単一の双方向I/O型を、`bio.Reader` と `bio.Writer` という2つの単方向I/O型に分割した点にあります。この変更は、GoのI/O設計原則への回帰と、より堅牢で理解しやすいコードベースの構築を目指しています。

### 双方向I/Oの課題
`bio.Buf` は、`os.File`、`bufio.Reader`、`bufio.Writer` を一つの構造体にまとめていました。これにより、同じファイルディスクリプタに対して読み書き両方の操作が可能でしたが、以下のような課題がありました。
1.  **責務の曖昧さ**: 一つの型が読み込みと書き込みという異なる責務を持つため、コードの意図が不明瞭になりがちでした。
2.  **状態管理の複雑さ**: 読み込みバッファと書き込みバッファが共存するため、シーク操作 (`Seek`) の際に両方のバッファの状態を適切に同期させる必要がありました。特に、書き込みバッファをフラッシュしてから読み込みバッファをリセットする、あるいはその逆の操作が必要となり、エラーが発生しやすいポイントでした。
3.  **Goの慣習からの逸脱**: Goの標準ライブラリでは、`io.Reader` と `io.Writer` は明確に分離されており、合成 (`io.ReadWriter`) はそれらを組み合わせる場合にのみ使用されます。`bio.Buf` はこの慣習に反していました。

### 単方向I/Oへの分割による改善
このコミットでは、`bio.Buf` を以下のように分割しました。
*   **`bio.Reader`**: `os.File` と `bufio.Reader` のみを保持し、読み込み操作に特化します。
*   **`bio.Writer`**: `os.File` と `bufio.Writer` のみを保持し、書き込み操作に特化します。

この分割により、以下のメリットがもたらされます。
1.  **明確な責務**: 各型が単一のI/O方向（読み込みまたは書き込み）に責任を持つため、コードの意図が非常に明確になります。
2.  **簡素化された状態管理**: `bio.Reader` は読み込みバッファのみ、`bio.Writer` は書き込みバッファのみを管理すればよいため、シーク操作時のバッファ同期ロジックが簡素化されます。例えば、`bio.Reader.Seek` は `bufio.Reader` のリセットのみを考慮すればよく、`bio.Writer.Seek` は `bufio.Writer` のフラッシュのみを考慮すればよくなります。
3.  **Goの慣習への準拠**: 標準ライブラリの `io.Reader` と `io.Writer` の設計パターンに合致し、Goエコシステム全体との整合性が向上します。これにより、他のGoパッケージとの連携が容易になり、コードの理解も促進されます。
4.  **型安全性の向上**: 関数やメソッドの引数として `*bio.Reader` または `*bio.Writer` を受け取ることで、その関数が読み込み操作を行うのか、書き込み操作を行うのかが型シグネチャから一目でわかるようになります。これにより、誤ったI/O操作を防ぐことができます。

### シーク操作の変更
`bio.Buf` では `bio.Bseek` と `bio.Boffset` というグローバル関数がシークとオフセット取得のために提供されていました。これらの関数は `*bio.Buf` を引数に取り、内部で読み書きバッファの状態を考慮する必要がありました。
新しい設計では、`bio.Reader` と `bio.Writer` それぞれに `Seek` メソッドと `Offset` メソッドが追加されました。これにより、各型が自身のバッファ状態を管理しながらシーク操作を行うことが可能になり、よりオブジェクト指向的なアプローチが採用されています。

このリファクタリングは、Goツールチェインの内部I/O処理の基盤を強化し、長期的なメンテナンス性と信頼性を向上させるための重要な一歩と言えます。

## コアとなるコードの解説

ここでは、`src/cmd/internal/bio/buf.go` における主要な変更点を詳細に解説します。

### 変更前 (`bio.Buf`)

```go
// Buf implements a seekable buffered I/O abstraction.
type Buf struct {
	f *os.File
	r *bufio.Reader
	w *bufio.Writer
}

func Create(name string) (*Buf, error) {
	f, err := os.Create(name)
	if err != nil {
		return nil, err
	}
	return &Buf{f: f, w: bufio.NewWriter(f)}, nil
}

func Open(name string) (*Buf, error) {
	f, err := os.Open(name)
	if err != nil {
		return nil, err
	}
	return &Buf{f: f, r: bufio.NewReader(f)}, nil
}

// Bseek seeks in b.
func Bseek(b *Buf, offset int64, whence int) int64 {
	if b.w != nil {
		if err := b.w.Flush(); err != nil {
			log.Fatalf("writing output: %v", err)
		}
	} else if b.r != nil {
		if whence == 1 {
			offset -= int64(b.r.Buffered())
		}
	}
	off, err := b.f.Seek(offset, whence)
	if err != nil {
		log.Fatalf("seeking in output: %v", err)
	}
	if b.r != nil {
		b.r.Reset(b.f)
	}
	return off
}

// Boffset returns the current offset in b.
func Boffset(b *Buf) int64 {
	if b.w != nil {
		if err := b.w.Flush(); err != nil {
			log.Fatalf("writing output: %v", err)
		}
	}
	off, err := b.f.Seek(0, 1)
	if err != nil {
		log.Fatalf("seeking in output [0, 1]: %v", err)
	}
	if b.r != nil {
		off -= int64(b.r.Buffered())
	}
	return off
}
```

変更前の `bio.Buf` は、`os.File`、`bufio.Reader`、`bufio.Writer` の3つを保持していました。`Create` 関数は書き込み専用の `Buf` を、`Open` 関数は読み込み専用の `Buf` を返しますが、型自体は同じ `Buf` でした。`Bseek` や `Boffset` のような関数は、内部で `b.w` や `b.r` が `nil` でないかをチェックし、それぞれのバッファをフラッシュしたりリセットしたりする必要がありました。これは、一つの型で異なる状態（読み込みモードと書き込みモード）を管理することによる複雑さを示しています。

### 変更後 (`bio.Reader` と `bio.Writer`)

```go
// Reader implements a seekable buffered io.Reader.
type Reader struct {
	f *os.File
	r *bufio.Reader
}

// Writer implements a seekable buffered io.Writer.
type Writer struct {
	f *os.File
	w *bufio.Writer
}

// Create creates the file named name and returns a Writer
// for that file.
func Create(name string) (*Writer, error) {
	f, err := os.Create(name)
	if err != nil {
		return nil, err
	}
	return &Writer{f: f, w: bufio.NewWriter(f)}, nil
}

// Open returns a Reader for the file named name.
func Open(name string) (*Reader, error) {
	f, err := os.Open(name)
	if err != nil {
		return nil, err
	}
	return &Reader{f: f, r: bufio.NewReader(f)}, nil
}

func (r *Reader) Seek(offset int64, whence int) int64 {
	if whence == 1 {
		offset -= int64(r.r.Buffered())
	}
	off, err := r.f.Seek(offset, whence)
	if err != nil {
		log.Fatalf("seeking in output: %v", err)
	}
	r.r.Reset(r.f) // 読み込みバッファのみリセット
	return off
}

func (w *Writer) Seek(offset int64, whence int) int64 {
	if err := w.w.Flush(); err != nil { // 書き込みバッファのみフラッシュ
		log.Fatalf("writing output: %v", err)
	}
	off, err := w.f.Seek(offset, whence)
	if err != nil {
		log.Fatalf("seeking in output: %v", err)
	}
	return off
}

func (r *Reader) Offset() int64 {
	off, err := r.f.Seek(0, 1)
	if err != nil {
		log.Fatalf("seeking in output [0, 1]: %v", err)
	}
	off -= int64(r.r.Buffered()) // 読み込みバッファの分を考慮
	return off
}

func (w *Writer) Offset() int64 {
	if err := w.w.Flush(); err != nil { // 書き込みバッファをフラッシュ
		log.Fatalf("writing output: %v", err)
	}
	off, err := w.f.Seek(0, 1)
	if err != nil {
		log.Fatalf("seeking in output [0, 1]: %v", err)
	}
	return off
}
```

変更後、`bio.Reader` と `bio.Writer` はそれぞれ `os.File` と対応する `bufio.Reader` または `bufio.Writer` のみを保持するようになりました。
*   `Create` 関数は `*bio.Writer` を、`Open` 関数は `*bio.Reader` を明示的に返します。これにより、関数の戻り値の型からそのインスタンスが読み込み用なのか書き込み用なのかが明確になります。
*   `Seek` メソッドと `Offset` メソッドは、`*bio.Reader` と `*bio.Writer` それぞれの型に定義されました。
    *   `*bio.Reader.Seek` は、自身の `bufio.Reader` のバッファをリセットするだけでよく、書き込みバッファのフラッシュを気にする必要がありません。
    *   `*bio.Writer.Seek` は、自身の `bufio.Writer` のバッファをフラッシュするだけでよく、読み込みバッファのリセットを気にする必要がありません。
この分割により、各メソッドのロジックが簡素化され、エラーの可能性が低減し、コードの意図がより明確になりました。これは、Goのインターフェース設計のベストプラクティスに沿った、よりクリーンで堅牢なI/O抽象化を実現しています。

# [インデックス 27733] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) 形式におけるループ内の境界チェック除去 (Bound Check Elimination, BCE) 機能を拡張するものです。具体的には、配列やスライスの最大長 (`limit`) とインデックスの最大値 (`max`) がコンパイル時に定数として確定できる場合に、より多くの境界チェックを削除できるように改善しています。

*   `test/checkbce.go`: 境界チェック除去のテストケースを定義しているファイルです。既存のテストが修正され、新しい最適化が正しく機能するかどうかを確認するための変更が含まれています。
*   `test/loopbce.go`: ループ内の境界チェック除去に関する新しいテストケースが追加されたファイルです。このコミットで導入された最適化が適用されるべきシナリオを具体的に示しています。

## 変更の背景

Go言語のコンパイラは、実行時の安全性を保証するために、配列やスライスへのアクセス時にインデックスが有効な範囲内にあるかをチェックする「境界チェック (Bounds Check)」を自動的に挿入します。しかし、これらのチェックはオーバーヘッドとなり、プログラムの実行速度を低下させる可能性があります。

境界チェック除去 (BCE) は、コンパイル時にインデックスが必ず有効な範囲内にあると証明できる場合に、これらの冗長なチェックを削除する最適化手法です。Goコンパイラは以前からBCEを実装していましたが、このコミット以前は、インデックスの最大値 (`max`) や配列/スライスの長さ (`limit`) が定数である場合に、十分に最適化できていないケースが存在しました。

このコミットの目的は、そのような特定のシナリオ、特にループ内でインデックスが定数オフセットを持つ場合や、配列/スライスの長さが定数である場合に、より積極的に境界チェックを削除することです。コミットメッセージにある「Removes 49 more bound checks in make.bash」という記述は、この最適化によってGo自身のビルドプロセス (`make.bash`) において、実際に多くの境界チェックが削減され、パフォーマンスが向上したことを示唆しています。

例として挙げられているコードスニペット:
```go
var a[100]int
for i := 0; i < 50; i++ {
  use a[i+25]
}
```
この場合、`i` は `0` から `49` まで変化します。`i+25` は `25` から `74` まで変化し、これは配列 `a` の有効なインデックス範囲 `0` から `99` の中に完全に収まります。このような状況では、実行時の境界チェックは不要であり、コンパイラがそれを認識して削除することが望ましいです。

## 前提知識の解説

### 境界チェック (Bounds Check)
Go言語では、配列やスライスにアクセスする際、インデックスがそのデータ構造の有効な範囲内にあるかを確認するチェックが自動的に行われます。例えば、`a[i]` のようなアクセスでは、`0 <= i < len(a)` が満たされているかを確認します。このチェックは、C/C++のような言語で発生しうるバッファオーバーフローなどのセキュリティ脆弱性や実行時エラーを防ぐために重要です。

### 境界チェック除去 (Bound Check Elimination, BCE)
BCEは、コンパイラ最適化の一種で、コンパイル時にインデックスが必ず有効な範囲内にあると証明できる場合に、実行時の境界チェックを削除する技術です。これにより、プログラムの実行速度が向上します。例えば、`for i := 0; i < len(a); i++ { use(a[i]) }` のようなループでは、`a[i]` へのアクセスは常に有効な範囲内にあるため、コンパイラは `a[i]` の境界チェックを削除できます。

### SSA (Static Single Assignment) 形式
SSA形式は、コンパイラの中間表現の一種です。この形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、ソースコードをSSA形式に変換した後、様々な最適化パスを適用します。`src/cmd/compile/internal/ssa/` ディレクトリは、このSSA形式の処理と最適化に関連するコードを含んでいます。

### 誘導変数 (Induction Variable)
ループ内で規則的に変化する変数を誘導変数と呼びます。例えば、`for i := 0; i < N; i++` の `i` は誘導変数です。BCEでは、誘導変数の最小値 (`min`) と最大値 (`max`) を追跡し、それらが配列/スライスの境界内に収まるかを判断します。

### `OpIsInBounds` と `OpIsSliceInBounds`
これらはGoコンパイラのSSA形式における操作 (Operation) の一種で、それぞれ配列要素アクセスとスライス操作における境界チェックを表します。コンパイラはこれらの操作を生成し、BCEパスで不要なものを削除しようとします。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/loopbce.go` 内の `removeBoundsChecks` 関数に新しいロジックを追加することで、BCEの能力を向上させています。

追加されたロジックは、以下の形式の境界チェックを簡略化することを目的としています。
*   `OpIsInBounds (Add64 ind) (Const64 [c])`
*   `OpIsSliceInBounds ind (Const64 [c])`

ここで、`ind` はループの誘導変数、`Add64` は定数オフセットの加算、`Const64 [c]` は配列/スライスの長さを示す定数です。

新しいロジックは、以下の条件が満たされる場合に境界チェックを削除します。

1.  **操作の種類**: `OpIsInBounds` または `OpIsSliceInBounds` であること。
2.  **インデックスの形式**: インデックスが `ind + add` の形式であること。ここで `ind` は誘導変数であり、`add` は定数オフセットです。
3.  **誘導変数の追跡**: `ind` がループの誘導変数として認識されており、そのループの開始ブロック (`iv.entry`) が現在のブロック (`b`) の祖先または同じブロックであること。
4.  **下限チェック**: `ind + add` の最小値が `0` 以上であること。これは `iv.min + add >= 0` または `iv.min >= -add` と評価されます。`isGreaterOrEqualThan` という新しいヘルパー関数が導入され、このチェックを効率的に行います。
5.  **上限チェック**: `ind + add` の最大値が配列/スライスの長さ (`limit`) 以下であること。これは `iv.max + add <= limit` と評価されます。

特に重要なのは、`limit` (配列/スライスの長さ) と `iv.max` (誘導変数の最大値) が両方ともコンパイル時に既知の定数である場合に、この最適化が適用される点です。

`OpIsSliceInBounds` の場合、`limit` の値がインクリメントされる (`limit++`) 処理があります。これは、スライスの長さが `N` の場合、有効なインデックスは `0` から `N-1` までですが、スライス作成 (`a[low:high]`) の `high` は `N` まで許容されるため、その調整を行っています。ただし、`limit++` が符号付き整数オーバーフローを引き起こす可能性があるため、そのチェックも行われます。

この最適化により、コンパイラはループ内で定数オフセットを持つインデックスアクセスや、定数長の配列/スライスに対するアクセスにおいて、より多くの冗長な境界チェックを削除できるようになります。これにより、生成されるバイナリのサイズが小さくなり、実行速度が向上します。

## コアとなるコードの変更箇所

`src/cmd/compile/internal/ssa/loopbce.go` の `removeBoundsChecks` 関数内に、以下の新しいコードブロックが追加されています。

```go
		// Simplify
		// (IsInBounds (Add64 ind) (Const64 [c])) where 0 <= min <= ind < max <= (Const64 [c])
		// (IsSliceInBounds ind (Const64 [c])) where 0 <= min <= ind < max <= (Const64 [c])
		if v.Op == OpIsInBounds || v.Op == OpIsSliceInBounds {
			ind, add := dropAdd64(v.Args[0])
			if ind.Op != OpPhi {
				goto skip3
			}

			// ind + add >= 0 <-> min + add >= 0 <-> min >= -add
			if iv, has := m[ind]; has && sdom.isAncestorEq(iv.entry, b) && isGreaterOrEqualThan(iv.min, -add) {
				if !v.Args[1].isGenericIntConst() || !iv.max.isGenericIntConst() {
					goto skip3
				}

				limit := v.Args[1].AuxInt
				if v.Op == OpIsSliceInBounds {
					// If limit++ overflows signed integer then 0 <= max && max <= limit will be false.
					limit++
				}

				if max := iv.max.AuxInt + add; 0 <= max && max <= limit { // handle overflow
					if f.pass.debug > 0 {
						f.Config.Warnl(b.Line, "Found redundant (%s ind %d), ind < %d", v.Op, v.Args[1].AuxInt, iv.max.AuxInt+add)
					}
					goto simplify
				}
			}
		}
	skip3:

		continue

	simplify:
```

また、新しいヘルパー関数 `isGreaterOrEqualThan` が追加されています。

```go
func isGreaterOrEqualThan(v *Value, c int64) bool {
	if c == 0 {
		return isNonNegative(v)
	}
	if v.isGenericIntConst() && v.AuxInt >= c {
		return true
	}
	return false
}
```

テストファイル `test/loopbce.go` には、この最適化が適用されるべき様々なシナリオを示す新しい関数 (`k0` から `k5`) が追加されています。これらの関数は、定数オフセットを持つインデックスアクセスやスライス操作に対して、コンパイラが境界チェックを正しく削除できることを検証します。

## コアとなるコードの解説

### `removeBoundsChecks` 関数内の変更

この変更は、`removeBoundsChecks` 関数内で各SSA値 `v` を走査し、それが境界チェック操作 (`OpIsInBounds` または `OpIsSliceInBounds`) であるかどうかを確認します。

1.  **インデックスの解析**: `dropAdd64(v.Args[0])` は、インデックス値が `ind + add` の形式である場合に、誘導変数 `ind` と定数オフセット `add` を抽出します。`ind.Op != OpPhi` の場合、それは誘導変数ではないため、この最適化の対象外として `skip3` にジャンプします。
2.  **誘導変数の情報取得**: `m[ind]` を使って、誘導変数 `ind` に関連付けられた情報 (`iv`) を取得します。これには、誘導変数の最小値 (`iv.min`) と最大値 (`iv.max`) が含まれます。
3.  **下限チェック**: `isGreaterOrEqualThan(iv.min, -add)` は、`ind + add` の最小値が `0` 以上であることを確認します。これは、`iv.min >= -add` と同等です。
4.  **定数チェック**: `v.Args[1].isGenericIntConst()` と `iv.max.isGenericIntConst()` は、配列/スライスの長さ (`limit`) と誘導変数の最大値が両方ともコンパイル時に既知の定数であることを確認します。これが満たされない場合も `skip3` にジャンプします。
5.  **`limit` の調整**: `OpIsSliceInBounds` の場合、スライスの `high` インデックスのセマンティクスに合わせて `limit` をインクリメントします。
6.  **上限チェック**: `max := iv.max.AuxInt + add; 0 <= max && max <= limit` は、`ind + add` の最大値が `limit` 以下であり、かつオーバーフローが発生していないことを確認します。`0 <= max` のチェックは、`max` が負の値になることによるオーバーフローを防ぐためです。
7.  **冗長チェックの削除**: 上記のすべての条件が満たされた場合、境界チェックは冗長であると判断され、`simplify` ラベルにジャンプして削除されます。デバッグモードでは、削除されたチェックに関する警告が出力されます。

### `isGreaterOrEqualThan` 関数

この新しいヘルパー関数は、SSA値 `v` が定数 `c` 以上であるかを効率的に判断します。
*   `c == 0` の場合、`isNonNegative(v)` を呼び出して `v` が非負であるかをチェックします。
*   `v` が定数であり、その値が `c` 以上であれば `true` を返します。
*   それ以外の場合は `false` を返します。

この関数は、誘導変数の最小値が定数オフセットの負の値以上であるかを確認する際に使用され、BCEロジックの可読性と正確性を向上させています。

### テストケース (`test/loopbce.go`)

`k0` から `k5` までの新しいテスト関数は、この最適化が適用されるべき具体的なコードパターンを示しています。例えば、`k0` 関数では、`a[i-10]` や `a[i+10]` のようなアクセスが、ループの範囲と配列の長さに基づいて安全であることが証明され、境界チェックが削除されることを期待しています。`ERROR "Found redundant ..."` というコメントは、コンパイラが冗長な境界チェックを検出して削除したことを示す警告メッセージを期待していることを意味します。これにより、コンパイラが正しく最適化を行っていることを検証します。

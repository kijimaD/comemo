## 変更の背景

このコミットは、Goコンパイラのエスケープ解析中に発生していたクラッシュ（パニック）を修正するために行われました。クラッシュは、`cmd/internal/gc.haspointers` 関数が `nil` ポインタを参照しようとした際に発生していました。具体的には、エスケープ解析の過程で生成される「偽の `OADDR` ノード」の型情報が適切に設定されていなかったため、`haspointers` 関数がそのノードの型を評価しようとした際に `nil` ポインタデリファレンスが発生していました。

コミットメッセージに示されているスタックトレースは、クラッシュが `haspointers` 関数内で発生し、それが `escwalk` 関数から呼び出されていることを明確に示しています。この問題は、Goの内部バグトラッカーでIssue 10441として追跡されていました。

## 前提知識の解説

このコミットの理解には、以下のGoコンパイラとエスケープ解析に関する知識が必要です。

1.  **Goコンパイラ (gc)**: Go言語の公式コンパイラは `gc` と呼ばれ、Goのソースコードを機械語に変換します。コンパイルの過程で、様々な最適化や解析が行われます。
2.  **エスケープ解析 (Escape Analysis)**: Goコンパイラの重要な最適化の一つです。変数がヒープに割り当てられるべきか（エスケープする）、それともスタックに割り当てられるべきか（エスケープしない）を決定します。
    *   **スタック割り当て**: 関数呼び出しのたびに確保され、関数が終了すると自動的に解放されるメモリ領域です。高速でガベージコレクションの対象になりません。
    *   **ヒープ割り当て**: プログラムの実行中に動的に確保・解放されるメモリ領域です。ガベージコレクションの対象となり、スタック割り当てよりもオーバーヘッドがあります。
    エスケープ解析は、可能な限りスタック割り当てを選択することで、ガベージコレクションの負荷を減らし、プログラムのパフォーマンスを向上させます。
3.  **抽象構文木 (AST) とノード (Node)**: コンパイラはソースコードを直接扱うのではなく、それを抽象構文木というツリー構造に変換して処理します。このツリーの各要素は「ノード」と呼ばれ、変数、関数呼び出し、演算子などを表現します。
4.  **`OADDR` ノード**: Goコンパイラ内部で、アドレス演算子 `&`（ポインタを取得する演算子）を表すノードです。例えば、`&x` という式は `OADDR` ノードとして表現されます。
5.  **`escwalk` 関数**: エスケープ解析の主要な関数の一つで、ASTを走査しながら変数のエスケープ挙動を分析します。
6.  **`haspointers` 関数**: ある型がポインタを含むかどうかを判定する関数です。エスケープ解析において、ポインタを含む型がヒープにエスケープするかどうかを判断する際に使用されます。この関数は、型の構造を再帰的に調べてポインタフィールドの有無を確認します。

## 技術的詳細

クラッシュは、`src/cmd/internal/gc/esc.go` 内の `escassign` 関数において、`OADDR` ノードが「偽の」または一時的な形で作成される際に発生していました。

問題のコードは以下の部分です（コミットメッセージより）：

```go
leaks = level <= 0 && dst.Escloopdepth < src.Escloopdepth || level < 0 && dst == &e.funcParam && haspointers(src.Type)
```

この行では、`haspointers(src.Type)` が評価されています。ここで `src` は `escassign` 関数内で `Nod(OADDR, src, nil)` によって作成された一時的な `OADDR` ノードを指す可能性があります。

`escassign` 関数は、代入操作のエスケープ解析を行います。`dst`（代入先のノード）と `src`（代入元のノード）を受け取ります。特定のケース（例えば、`src` がアドレスを取られる場合）では、コンパイラは一時的な `OADDR` ノード `a` を作成します。

```go
a := Nod(OADDR, src, nil)
a.Lineno = src.Lineno
a.Escloopdepth = src.Escloopdepth
// a.Type = Ptrto(src.Type) // この行が不足していた
escflows(e, dst, a)
```

この一時的な `OADDR` ノード `a` は、`src` のアドレスを表します。しかし、このノードが作成された際に、その `Type` フィールドが適切に初期化されていませんでした。`OADDR` ノードはポインタ型を持つべきですが、この「偽の」ノードには型情報が設定されていなかったため、`nil` となっていました。

その後、エスケープ解析のロジックのどこかで、この型情報が `nil` の `OADDR` ノードが `haspointers` 関数に渡される可能性がありました。`haspointers` 関数は、引数として受け取ったノードの `Type` フィールドをデリファレンスして型の情報を調べようとします。しかし、`Type` が `nil` であったため、`nil` ポインタデリファレンスが発生し、コンパイラがパニックを起こしてクラッシュしていました。

修正は、この一時的な `OADDR` ノード `a` が作成された直後に、その `Type` フィールドを正しく初期化することです。`OADDR` ノードはポインタを表すため、`src` の型へのポインタ型 (`Ptrto(src.Type)`) を設定する必要があります。これにより、`haspointers` が呼び出された際に有効な型情報が提供され、クラッシュが回避されます。

```go
// build

package p

func bar() {
	f := func() {}
	foo(&f)
}

	defer func() {}() // prevent inlining of foo
	return *f
}
```

このテストケースは、関数ポインタのアドレスを取り、それを別の関数に渡すという、エスケープ解析が複雑になるようなシナリオを意図的に作成しています。`defer func() {}()` は、`foo` 関数がインライン化されるのを防ぐための慣用的な記述です。インライン化されると、エスケープ解析の挙動が変わる可能性があるため、バグの再現性を確保するために行われます。

## コアとなるコードの解説

追加された行 `a.Type = Ptrto(src.Type)` は、`OADDR` ノード `a` の `Type` フィールドを正しく設定しています。

-   `a`: `Nod(OADDR, src, nil)` によって作成された新しいノードで、これは `src` のアドレスを表します。
-   `Ptrto(src.Type)`: `src` の型へのポインタ型を返します。例えば、`src` が `int` 型であれば、`Ptrto(src.Type)` は `*int` 型を返します。

この修正により、`a` ノードが `haspointers` 関数に渡された際に、`a.Type` が `nil` ではなく、有効なポインタ型情報を持つようになります。これにより、`haspointers` 関数が安全に型情報を参照できるようになり、`nil` ポインタデリファレンスによるクラッシュが解消されます。

この変更は、Goコンパイラのエスケープ解析の堅牢性を高め、特定の複雑なコードパターンにおけるコンパイル時のクラッシュを防ぐ上で非常に重要です。

## 変更の背景

Go言語はかつて、Google Native Client (NaCl) プラットフォームへのコンパイルをサポートしていました。NaClは、ウェブブラウザ内でネイティブコードを安全かつ高速に実行するためのサンドボックス技術です。`amd64p32`は、NaCl環境で利用される特定のアーキテクチャであり、64ビット命令を使用しながらも32ビットポインタを持つという特徴があります。

このコミットが行われた2014年当時、GoはNaClをサポートしており、そのビルドプロセスにおいて`amd64p32`ターゲットで問題が発生していました。コミットメッセージにある`Fixes nacl/amd64p32 build.`という記述から、この特定の環境でのコンパイルが失敗していたことが伺えます。この修正は、Goコンパイラとランタイムが`nacl/amd64p32`環境の特殊な要件に正しく対応できるようにするためのものでした。

具体的には、`amd64p32`は64ビットレジスタを使用するものの、ポインタサイズが32ビットであるため、通常の`amd64`アーキテクチャとは異なるアセンブリ命令やリンカの挙動が必要となる場合があります。このコミットは、これらの差異を吸収し、ビルドが成功するように調整することを目的としています。

## 前提知識の解説

### Google Native Client (NaCl)

Google Native Client (NaCl) は、Googleが開発したオープンソースのサンドボックス技術です。C/C++などのネイティブコードをウェブブラウザ内で安全に実行することを可能にし、ウェブアプリケーションのパフォーマンス向上を目指していました。NaClは、コードの検証、メモリ保護、システムコールインターフェースの制限などにより、セキュリティを確保していました。しかし、WebAssemblyの登場と普及に伴い、NaClのサポートは終了し、Go言語もNaClのサポートを停止しています。

### `amd64p32`アーキテクチャ

`amd64p32`は、`amd64`（x86-64）命令セットを使用しながらも、ポインタサイズが32ビットに制限された特殊なアーキテクチャです。通常の`amd64`は64ビットポインタを使用しますが、`amd64p32`は32ビットポインタを使用することで、メモリフットプリントを削減し、特定の環境（特にサンドボックス化された環境）での効率を高めることを目的としていました。Go言語では、`GOOS=nacl`と`GOARCH=amd64p32`の組み合わせでこのターゲットをサポートしていました。

### Goの`liblink`と`runtime`

*   **`liblink`**: Goコンパイラの一部であり、オブジェクトファイルをリンクして実行可能ファイルを生成する役割を担います。リンカは、異なるアーキテクチャやOSの特性に合わせて、アセンブリコードの生成やシンボルの解決を行います。このコミットでは、`src/liblink/obj6.c`が変更されており、これは`amd64`アーキテクチャ（Goの内部では`obj6`として扱われることが多い）向けのリンカの挙動を定義するC言語のファイルです。
*   **`runtime`**: Goプログラムの実行を管理するランタイムシステムです。ガベージコレクション、スケジューラ、スタック管理、システムコールなど、Goプログラムが動作するために必要な低レベルの機能を提供します。`src/pkg/runtime/asm_amd64p32.s`は、`amd64p32`アーキテクチャ向けのアセンブリコードを含むファイルであり、ランタイムの特定の機能（例: スタック管理、関数呼び出し規約）を実装しています。

### アセンブリ命令の基礎知識

このコミットでは、x86-64アセンブリ命令が使用されています。

*   **`MOVL` (Move Long)**: 32ビットのデータを移動する命令。
*   **`MOVLQZX` (Move Long Quadword Zero-Extend)**: 32ビットの値を64ビットレジスタにゼロ拡張して移動する命令。
*   **`TESTQ` / `TESTL`**: 論理AND演算を行い、結果を破棄してフラグのみを設定する命令。主にレジスタの内容がゼロかどうかをチェックするために使われます。`Q`は64ビット、`L`は32ビットを意味します。
*   **`JEQ` (Jump if Equal)**: 直前の比較またはテストの結果が等しい（ゼロフラグがセットされている）場合にジャンプする命令。
*   **`JNE` (Jump if Not Equal)**: 直前の比較またはテストの結果が等しくない（ゼロフラグがクリアされている）場合にジャンプする命令。
*   **`LEAL` (Load Effective Address Long)**: メモリオペランドのアドレスを計算し、そのアドレスをレジスタにロードする命令。32ビット版。
*   **`CMPQ` / `CMPL`**: 2つのオペランドを比較し、フラグを設定する命令。`Q`は64ビット、`L`は32ビットを意味します。
*   **`CALL`**: 関数を呼び出す命令。
*   **`RET`**: 関数から戻る命令。

## 技術的詳細

このコミットは、`nacl/amd64p32`ビルドにおけるポインタサイズの不一致や、特定のランタイム挙動の調整に焦点を当てています。

### `src/liblink/obj6.c`の変更

このファイルでは、`addstacksplit`関数内で`nacl`環境向けの条件付きコードが追加されています。`addstacksplit`は、Goのスタック分割（stack splitting）メカニズムに関連するコードを生成する際に使用されるリンカの関数です。スタック分割は、Goルーチンのスタックが動的に拡張されることを可能にする重要な機能です。

変更点を見ると、`ctxt->headtype == Hnacl`という条件分岐が複数追加されています。これは、コンパイルターゲットがNaClである場合にのみ適用されるコードパスを示しています。

*   **`G.panic`へのアクセス**: 最初の変更では、`G.panic`へのアクセス方法が変更されています。通常の`amd64`では`D_INDIR+D_CX`（`CX`レジスタが指すアドレスからの間接参照）が使われていたのに対し、NaCl環境では`AMOVL`命令と`D_INDIR+D_R15`（`R15`レジスタが指すアドレスからの間接参照）が使用されています。これは、NaClが特定のレジスタ（`R15`）を特別な目的（例えば、サンドボックスのベースアドレス）に使用する可能性があり、それに応じてメモリアクセスのアドレッシングモードを調整する必要があるためと考えられます。また、`AMOVL`は32ビット移動命令であり、`amd64p32`の32ビットポインタの特性に合わせた変更です。
*   **`TEST`命令の変更**: `ATESTQ`が`ATESTL`に変更されています。これは、64ビットのテスト命令から32ビットのテスト命令への変更であり、`amd64p32`の32ビットポインタのコンテキストで、より適切な命令を選択していることを示唆しています。
*   **`LEAL`命令の追加**: スタックポインタからのアドレス計算において、NaCl環境では`ALEAL`命令が使用されるようになっています。これは、アドレス計算のセマンティクスがNaCl環境で異なるか、または32ビットポインタの計算に特化した命令が必要であることを示しています。
*   **`Panic.argp`へのアクセス**: `Panic.argp`へのアクセスも、`G.panic`と同様に`AMOVL`命令と`D_INDIR+D_R15`を用いたアドレッシングモードに変更されています。これは、NaCl環境におけるポインタの扱いとメモリレイアウトの特殊性に対応するためです。

これらの変更は、リンカがNaCl環境向けに生成するアセンブリコードが、`amd64p32`のポインタサイズとNaClのサンドボックス制約に適合するように調整されたことを意味します。

### `src/pkg/runtime/asm_amd64p32.s`の変更

このファイルは、`amd64p32`アーキテクチャ向けのGoランタイムのアセンブリコードを含んでいます。主な変更点は、`reflect·call`関数のシグネチャと、`CALLFN`マクロ内のパニック関連コードの削除です。

*   **`reflect·call`関数のシグネチャ変更**:
    元のシグネチャ: `func call(f *FuncVal, arg *byte, argsize, retoffset uint32, p *Panic).`
    変更後のシグネチャ: `func call(f *FuncVal, arg *byte, argsize, retoffset uint32).`
    `p *Panic`引数が削除されています。これは、リフレクション呼び出しにおけるパニック処理のメカニズムが、NaCl環境または`amd64p32`の特定の制約下で異なる方法で扱われるか、あるいはこのコンテキストでは不要になったことを示唆しています。
*   **`TEXT reflect·call(SB), NOSPLIT, $0-20` から `$0-16` への変更**:
    これは、関数のフレームサイズが20バイトから16バイトに減少したことを示しています。これは、`p *Panic`引数が削除されたことによる直接的な結果であり、スタック上のスペースが節約されたことを意味します。
*   **`CALLFN`マクロ内のパニック関連コードの削除**:
    `CALLFN`マクロは、リフレクション呼び出しのラッパー関数を生成するために使用されます。このマクロから、`panic+16(FP)`へのアクセスや`panic_argp`の初期化・クリアに関連するアセンブリコードが削除されています。
    具体的には、以下のコードブロックが削除されました:
    ```assembly
    /* initialize panic argp */
    MOVL    panic+16(FP), CX;
    CMPL    CX, $0;
    JEQ 2(PC);
    MOVL    SP, panic_argp(CX);
    ...
    /* clear panic argp */
    MOVL    panic+16(FP), CX;
    CMPL    CX, $0;
    JEQ 2(PC);
    MOVL    $0, panic_argp(CX);
    ```
    この削除は、`reflect·call`のシグネチャ変更と一貫しており、NaCl環境におけるパニック処理の特殊性、またはリフレクション呼び出しにおけるパニック処理の必要性の再評価を示しています。NaClはサンドボックス環境であるため、通常のOSとは異なるエラーハンドリングやシグナル処理のメカニズムを持つ可能性があり、Goランタイムがそれに合わせて調整されたと考えられます。

これらの変更は、`nacl/amd64p32`環境でのGoランタイムの動作を最適化し、ビルドエラーを解消するために、ポインタサイズ、メモリレイアウト、およびパニック処理の側面を考慮したものです。

## コアとなるコードの解説

### `src/liblink/obj6.c`

このファイルでは、Goのリンカが`amd64`アーキテクチャ向けのアセンブリコードを生成する際のロジックが定義されています。変更の核心は、`nacl`環境に特化した条件分岐（`if(ctxt->headtype == Hnacl)`）が追加されたことです。

1.  **`G.panic`へのアクセス修正**:
    ```c
    // Before:
    // p->from.type = D_INDIR+D_CX;
    // p->from.offset = 2*ctxt->arch->ptrsize; // G.panic
    // p->to.type = D_BX;

    // After (for Hnacl):
    // p->as = AMOVL;
    // p->from.type = D_INDIR+D_R15;
    // p->from.scale = 1;
    // p->from.index = D_CX;
    ```
    通常の`amd64`では、`G.panic`（ランタイムのグローバルなパニック情報）へのアクセスに`CX`レジスタを介した間接参照を使用していました。しかし、NaCl環境では、`AMOVL`（32ビット移動）命令と、`R15`レジスタをベースとしたアドレッシングモード（`D_INDIR+D_R15`）を使用するように変更されました。これは、`amd64p32`の32ビットポインタの特性と、NaClが`R15`レジスタをサンドボックスのベースアドレスなど、特別な目的で使用する可能性に対応するためです。`scale`と`index`の指定は、より複雑なメモリアドレッシングパターンを示唆しています。

2.  **`TEST`命令の変更**:
    ```c
    // Before:
    // p->as = ATESTQ;

    // After (for Hnacl):
    // p->as = ATESTL;
    ```
    `TESTQ`（64ビットテスト）命令が`ATESTL`（32ビットテスト）命令に変更されました。これは、`amd64p32`環境では32ビットの値をテストすることが適切であるためです。

3.  **`LEAL`命令の追加**:
    ```c
    // Before: (no specific LEA instruction for NaCl)

    // After (for Hnacl):
    // p->as = ALEAL;
    ```
    スタックポインタからのアドレス計算において、NaCl環境では`ALEAL`（32ビット有効アドレスロード）命令が使用されるようになりました。これは、NaCl環境でのアドレス計算のセマンティクスが異なるか、または32ビットポインタの計算に特化した命令が必要であることを示しています。

4.  **`Panic.argp`へのアクセス修正**:
    ```c
    // Before:
    // p->as = ACMPQ;
    // p->from.type = D_INDIR+D_BX;
    // p->from.offset = 0; // Panic.argp
    // p->to.type = D_DI;

    // After (for Hnacl):
    // p->as = ACMPL;
    // p->from.type = D_INDIR+D_R15;
    // p->from.scale = 1;
    // p->from.index = D_BX;
    ```
    `Panic.argp`へのアクセスも、`G.panic`と同様に`ACMPL`（32ビット比較）命令と`R15`レジスタを介したアドレッシングモードに変更されました。これは、NaCl環境におけるポインタの扱いとメモリレイアウトの特殊性に対応するためです。

5.  **スタックポインタの保存修正**:
    ```c
    // Before:
    // p->as = AMOVQ; // (implied, as it's obj6.c)
    // p->from.type = D_SP;
    // p->to.type = D_INDIR+D_BX;
    // p->to.offset = 0; // Panic.argp

    // After (for Hnacl):
    // p->as = AMOVL;
    // p->to.type = D_INDIR+D_R15;
    // p->to.scale = 1;
    // p->to.index = D_BX;
    ```
    スタックポインタの値を`Panic.argp`に保存する際も、`AMOVL`命令と`R15`レジスタを介したアドレッシングモードが使用されるようになりました。

これらの変更は、リンカが`nacl/amd64p32`ターゲット向けに生成するコードが、32ビットポインタのセマンティクスとNaClのサンドボックス環境の制約に正しく適合するように調整されたことを示しています。

### `src/pkg/runtime/asm_amd64p32.s`

    ```assembly
    	FUNCDATA $FUNCDATA_LocalsPointerMaps,gclocals_reflectcall<>(SB);\
    	/* copy arguments to stack */		\
    	MOVL	argptr+4(FP), DI;		\
    	MOVL	argsize+8(FP), CX;		\
    	MOVL	SP, DI;				\
    	REP;MOVSB;				\
    -\t/* initialize panic argp */		\
    -\tMOVL	panic+16(FP), CX;		\
    -\tCMPL	CX, $0;				\
    -\tJEQ	2(PC);				\
    -\tMOVL	SP, panic_argp(CX);		\
    	/* call function */			\
    	MOVL	f+0(FP), DX;			\
    	MOVL	(DX), AX;			\
    	CALL	AX; \
    -\t/* clear panic argp */			\
    -\tMOVL	panic+16(FP), CX;		\
    -\tCMPL	CX, $0;				\
    -\tJEQ	2(PC);				\
    -\tMOVL	$0, panic_argp(CX);		\
    	/* copy return values back */		\
    	MOVL	argptr+4(FP), DI;		\
    	MOVL	argsize+8(FP), CX;		\
    ```
    `CALLFN`マクロは、リフレクション呼び出しのラッパー関数を生成するために使用されます。このマクロから、パニック関連の引数ポインタの初期化とクリアに関するアセンブリコードが完全に削除されました。これは、`reflect·call`のシグネチャ変更と一貫しており、NaCl環境におけるパニック処理の特殊性、またはリフレクション呼び出しにおけるパニック処理の必要性の再評価を示しています。NaClはサンドボックス環境であるため、通常のOSとは異なるエラーハンドリングやシグナル処理のメカニズムを持つ可能性があり、Goランタイムがそれに合わせて調整されたと考えられます。

これらの変更は、`nacl/amd64p32`環境でのGoランタイムの動作を最適化し、ビルドエラーを解消するために、ポインタサイズ、メモリレイアウト、およびパニック処理の側面を考慮したものです。

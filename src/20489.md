## 元コミット内容

このコミットは、Goランタイムにおいて、CGO（C言語との相互運用）呼び出し中にGoルーチンのスタックがコピーされるケースに対応するための修正を施しています。これにより、CGO呼び出しからGoルールーチンに戻る際のスタックポインタの整合性が保たれます。関連するテストは、`funcdata`に関する問題が解決された後に別のチェンジリストで追加される予定です。この修正は、GoのIssue #8696に対応するものです。

## 変更の背景

GoのGoroutineは非常に軽量であり、そのスタックは必要に応じて動的に拡張・縮小されます。スタックが拡張される際、現在のスタック領域が不足すると、Goランタイムはより大きな新しいスタック領域を確保し、古いスタックの内容を新しい領域にコピーします。このとき、Goroutineのスタックポインタ（SP）やベースポインタ（BP）などのレジスタは新しいスタック領域を指すように更新されます。

CGOはGoプログラムからC言語の関数を呼び出すためのメカニズムを提供します。CGO呼び出しが行われる際、GoルーチンはCコードに制御を渡し、CコードはGoのランタイムの管理外で実行されます。このとき、Goのスタックポインタは保存され、C関数が終了してGoルーチンに制御が戻る際に復元されます。

問題は、CGO呼び出し中にGoのスタックがコピーされる可能性がある点にありました。例えば、C関数がGoのコールバック関数を呼び出し、そのコールバック関数内でGoのスタックが拡張されるようなシナリオです。もしCGO呼び出し中にスタックがコピーされて移動した場合、GoルーチンがCGOから戻る際に、以前保存しておいたスタックポインタが古い（移動前の）スタック領域を指したままになってしまいます。これにより、Goルーチンが不正なメモリ領域にアクセスしようとし、クラッシュや予期せぬ動作を引き起こす可能性がありました。

このコミットは、この「CGO呼び出し中にGoスタックがコピーされる」というエッジケースを適切に処理し、スタックポインタの復元を安全に行うことを目的としています。

## 前提知識の解説

### GoのGoroutineとスタック

Go言語のGoroutineは、OSのスレッドよりもはるかに軽量な並行実行単位です。数千、数万のGoroutineを同時に実行することが可能です。Goroutineは非常に小さなスタック（通常は数KB）で開始され、必要に応じて自動的にスタックサイズを増減させます。

*   **スタックの動的拡張**: Goroutineの関数呼び出しがスタックの現在の容量を超えそうになると、Goランタイムはより大きな新しいスタック領域を割り当て、既存のスタックの内容を新しい領域にコピーします。このプロセスは「スタックのコピー」または「スタックの移動」と呼ばれます。
*   **スタックの縮小**: 不要になったスタック領域は解放され、メモリ効率が保たれます。

この動的なスタック管理は、Goroutineの軽量性と効率性を実現する上で非常に重要です。

### CGO

CGOは、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリを利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。

CGO呼び出しの際には、GoのランタイムとCのランタイムの間でコンテキストの切り替えが発生します。GoのGoroutineはCコードの実行中は一時的に停止し、Cコードが終了するとGoのランタイムに制御が戻ります。

### スタックのコピーとCGOの相互作用

Goのスタックがコピーされると、そのGoroutineに関連するスタックポインタやフレームポインタなどのアドレスが変更されます。通常、Goランタイムはこの変更を透過的に処理します。しかし、CGO呼び出し中にGoのスタックがコピーされると、問題が発生する可能性があります。

CGO呼び出しでは、Goのスタックポインタが保存され、C関数が実行されます。もしC関数の実行中にGoのスタックがコピーされて移動した場合、保存されたスタックポインタは古い（移動前の）アドレスを指したままになります。C関数からGoルーチンに制御が戻り、保存された古いスタックポインタが復元されると、Goルーチンは存在しないか、あるいは別のデータが格納されているメモリ領域を指すことになり、プログラムがクラッシュしたり、データが破損したりする原因となります。

この問題は特に、CコードがGoのコールバック関数を呼び出すようなシナリオで顕在化しやすいです。Goのコールバック関数が実行され、その中でスタックが拡張されると、スタックがコピーされる可能性があります。

## 技術的詳細

このコミットの技術的な核心は、CGO呼び出し時にスタックポインタ（SP）の絶対アドレスを保存するのではなく、スタックの「深さ」または「オフセット」を保存するように変更した点です。

従来のCGO呼び出しでは、GoルーチンがC関数に制御を渡す前に、現在のスタックポインタ（SP）の値を直接保存していました。C関数からGoルーチンに戻る際には、この保存されたSPの値をそのまま復元していました。

しかし、前述の通り、C関数実行中にGoのスタックがコピーされて移動した場合、スタックのベースアドレス（`g->stack.lo`）やトップアドレス（`g->stack.hi`）が変更されます。このとき、スタックポインタの絶対アドレスは無効になりますが、スタックのトップからの相対的な「深さ」は、スタックの内容がそのままコピーされるため、変化しません。

このコミットでは、以下の変更を導入しています。

1.  **スタックポインタの代わりにスタックの深さを保存**:
    CGO呼び出しを行う直前に、現在のスタックポインタ `SP` の絶対アドレスを保存する代わりに、`g->stack.hi` (スタックの最上位アドレス) から `SP` までのオフセット（深さ）を計算し、そのオフセットを保存します。
    `depth = g->stack.hi - SP`

2.  **スタックの深さから新しいスタックポインタを計算して復元**:
    C関数からGoルーチンに制御が戻る際、保存しておいた `depth` を使用して、現在の `g->stack.hi` から新しいスタックポインタ `SP` を計算します。
    `new_SP = g->stack.hi - depth`
    この `new_SP` をスタックポインタとして復元します。

このアプローチにより、CGO呼び出し中にGoのスタックがコピーされて移動しても、`g->stack.hi` は常に現在のスタックのトップを指すため、そこからの相対的な深さを使って正しいスタックポインタを計算し、復元することが可能になります。これにより、Goルーチンは常に有効なスタックポインタで実行を再開でき、クラッシュや不正な動作を防ぎます。

この修正は、`asm_386.s` (x86 32-bit), `asm_amd64.s` (x86 64-bit), `asm_arm.s` (ARM 32-bit) の各アーキテクチャ固有のアセンブリコードに対して適用されています。これは、スタックポインタの操作がアーキテクチャに依存するためです。

## コアとなるコードの解説

各アーキテクチャのアセンブリコードで行われている変更は、本質的に同じロジックを異なるレジスタと命令で実装したものです。

### スタックポインタの保存部分 (`asmcgocall` の呼び出し前)

**変更前**:
`MOVL DX, 4(SP)` (386の場合)
これは、現在のスタックポインタの値（`DX`レジスタに格納されている）を、スタックフレーム上の特定のオフセット（`4(SP)`）に直接保存していました。

**変更後**:
```assembly
MOVL	(g_stack+stack_hi)(DI), DI  // g->stack.hi を DI にロード
SUBL	DX, DI                      // DI = g->stack.hi - SP (現在のSPはDXにある)
MOVL	DI, 4(SP)                   // 計算した深さ (DI) をスタックに保存
```
このシーケンスは、以下の処理を行っています。
1.  現在のGoroutine構造体（`g`）のアドレスは`DI`レジスタにあります。`g_stack+stack_hi`は、`g`構造体内の`stack`フィールドの`hi`メンバー（スタックの最上位アドレス）へのオフセットを示します。`MOVL (g_stack+stack_hi)(DI), DI` は、`g->stack.hi` の値を`DI`レジスタにロードします。
2.  `SUBL DX, DI` は、`DI`（`g->stack.hi`）から`DX`（現在のスタックポインタ`SP`）を減算します。結果として`DI`には`g->stack.hi - SP`、つまりスタックのトップからの「深さ」が計算されます。
3.  `MOVL DI, 4(SP)` は、この計算された「深さ」をスタックフレーム上の以前SPを保存していたのと同じ位置に保存します。コメントにもあるように、「スタックがコールバック中にコピーされる可能性があるため、SPを直接保存することはできない」という理由が明記されています。

### スタックポインタの復元部分 (`asmcgocall` の呼び出し後)

**変更前**:
`MOVL 4(SP), SP` (386の場合)
これは、保存しておいた絶対スタックポインタの値をそのまま`SP`レジスタに復元していました。

**変更後**:
```assembly
MOVL	8(SP), DI                   // 保存しておいた g のアドレスを DI にロード
MOVL	(g_stack+stack_hi)(DI), SI  // 現在の g->stack.hi を SI にロード
SUBL	4(SP), SI                   // SI = g->stack.hi - 保存しておいた深さ (4(SP)にある)
MOVL	SI, SP                      // 計算した新しいSP (SI) を SP レジスタに復元
```
このシーケンスは、以下の処理を行っています。
1.  `MOVL 8(SP), DI` は、CGO呼び出し前に保存しておいた`g`のアドレスを`DI`にロードします。これは、現在の`g`がTLS (Thread Local Storage) から取得される前に、正しい`g`のコンテキストで`stack_hi`にアクセスするためです。
2.  `MOVL (g_stack+stack_hi)(DI), SI` は、現在の`g`構造体から`g->stack.hi`の値を`SI`レジスタにロードします。もしスタックが移動していれば、この`g->stack.hi`は以前の値とは異なる新しいアドレスを指しています。
3.  `SUBL 4(SP), SI` は、`SI`（現在の`g->stack.hi`）から、保存しておいた「深さ」（`4(SP)`にある）を減算します。これにより、新しいスタックのトップから同じ深さの位置にある、正しいスタックポインタの絶対アドレスが計算されます。
4.  `MOVL SI, SP` は、計算された新しいスタックポインタの値を`SP`レジスタに復元します。

この一連の変更により、CGO呼び出し中にGoのスタックが移動しても、Goルーチンは常に正しいスタックポインタで実行を再開できるようになり、GoとC/C++間の相互運用における堅牢性が大幅に向上しました。

### スタックのコピーとCGOの相互作用

CGO呼び出しでは、Goのスタックポインタが保存され、C関数が実行されます。もしC関数の実行中にGoのスタックがコピーされて移動した場合、保存されたスタックポインタは古い（移動前の）アドレスを指したままになります。C関数からGoルーチンに制御が戻り、保存された古いスタックポインタが復元されると、Goルーチンは存在しないか、あるいは別のデータが格納されているメモリ領域を指すことになり、プログラムがクラッシュしたり、データが破損したりする原因となります。

この問題は特に、CコードがGoのコールバック関数を呼び出すようなシナリオで顕在化しやすいです。Goのコールバック関数が実行され、その中でスタックが拡張されると、スタックがコピーされる可能性があります。

## 技術的詳細

このコミットの技術的な核心は、CGO呼び出し時にスタックポインタ（SP）の絶対アドレスを保存するのではなく、スタックの「深さ」または「オフセット」を保存するように変更した点です。

従来のCGO呼び出しでは、GoルーチンがC関数に制御を渡す前に、現在のスタックポインタ（SP）の値を直接保存していました。C関数からGoルーチンに戻る際には、この保存されたSPの値をそのまま復元していました。

しかし、前述の通り、C関数実行中にGoのスタックがコピーされて移動した場合、スタックのベースアドレス（`g->stack.lo`）やトップアドレス（`g->stack.hi`）が変更されます。このとき、スタックポインタの絶対アドレスは無効になりますが、スタックのトップからの相対的な「深さ」は、スタックの内容がそのままコピーされるため、変化しません。

このコミットでは、以下の変更を導入しています。

1.  **スタックポインタの代わりにスタックの深さを保存**:
    CGO呼び出しを行う直前に、現在のスタックポインタ `SP` の絶対アドレスを保存する代わりに、`g->stack.hi` (スタックの最上位アドレス) から `SP` までのオフセット（深さ）を計算し、そのオフセットを保存します。
    `depth = g->stack.hi - SP`

2.  **スタックの深さから新しいスタックポインタを計算して復元**:
    C関数からGoルーチンに制御が戻る際、保存しておいた `depth` を使用して、現在の `g->stack.hi` から新しいスタックポインタ `SP` を計算します。
    `new_SP = g->stack.hi - depth`
    この `new_SP` をスタックポインタとして復元します。

このアプローチにより、CGO呼び出し中にGoのスタックがコピーされて移動しても、`g->stack.hi` は常に現在のスタックのトップを指すため、そこからの相対的な深さを使って正しいスタックポインタを計算し、復元することが可能になります。これにより、Goルーチンは常に有効なスタックポインタで実行を再開でき、クラッシュや不正な動作を防ぎます。

この修正は、`asm_386.s` (x86 32-bit), `asm_amd64.s` (x86 64-bit), `asm_arm.s` (ARM 32-bit) の各アーキテクチャ固有のアセンブリコードに対して適用されています。これは、スタックポインタの操作がアーキテクチャに依存するためです。

## コアとなるコードの解説

各アーキテクチャのアセンブリコードで行われている変更は、本質的に同じロジックを異なるレジスタと命令で実装したものです。

### スタックポインタの保存部分 (`asmcgocall` の呼び出し前)

**変更前**:
`MOVL DX, 4(SP)` (386の場合)
これは、現在のスタックポインタの値（`DX`レジスタに格納されている）を、スタックフレーム上の特定のオフセット（`4(SP)`）に直接保存していました。

**変更後**:
```assembly
MOVL	(g_stack+stack_hi)(DI), DI  // g->stack.hi を DI にロード
SUBL	DX, DI                      // DI = g->stack.hi - SP (現在のSPはDXにある)
MOVL	DI, 4(SP)                   // 計算した深さ (DI) をスタックに保存
```
このシーケンスは、以下の処理を行っています。
1.  現在のGoroutine構造体（`g`）のアドレスは`DI`レジスタにあります。`g_stack+stack_hi`は、`g`構造体内の`stack`フィールドの`hi`メンバー（スタックの最上位アドレス）へのオフセットを示します。`MOVL (g_stack+stack_hi)(DI), DI` は、`g->stack.hi` の値を`DI`レジスタにロードします。
2.  `SUBL DX, DI` は、`DI`（`g->stack.hi`）から`DX`（現在のスタックポインタ`SP`）を減算します。結果として`DI`には`g->stack.hi - SP`、つまりスタックのトップからの「深さ」が計算されます。
3.  `MOVL DI, 4(SP)` は、この計算された「深さ」をスタックフレーム上の以前SPを保存していたのと同じ位置に保存します。コメントにもあるように、「スタックがコールバック中にコピーされる可能性があるため、SPを直接保存することはできない」という理由が明記されています。

### スタックポインタの復元部分 (`asmcgocall` の呼び出し後)

**変更前**:
`MOVL 4(SP), SP` (386の場合)
これは、保存しておいた絶対スタックポインタの値をそのまま`SP`レジスタに復元していました。

**変更後**:
```assembly
MOVL	8(SP), DI                   // 保存しておいた g のアドレスを DI にロード
MOVL	(g_stack+stack_hi)(DI), SI  // 現在の g->stack.hi を SI にロード
SUBL	4(SP), SI                   // SI = g->stack.hi - 保存しておいた深さ (4(SP)にある)
MOVL	SI, SP                      // 計算した新しいSP (SI) を SP レジスタに復元
```
このシーケンスは、以下の処理を行っています。
1.  `MOVL 8(SP), DI` は、CGO呼び出し前に保存しておいた`g`のアドレスを`DI`にロードします。これは、現在の`g`がTLS (Thread Local Storage) から取得される前に、正しい`g`のコンテキストで`stack_hi`にアクセスするためです。
2.  `MOVL (g_stack+stack_hi)(DI), SI` は、現在の`g`構造体から`g->stack.hi`の値を`SI`レジスタにロードします。もしスタックが移動していれば、この`g->stack.hi`は以前の値とは異なる新しいアドレスを指しています。
3.  `SUBL 4(SP), SI` は、`SI`（現在の`g->stack.hi`）から、保存しておいた「深さ」（`4(SP)`にある）を減算します。これにより、新しいスタックのトップから同じ深さの位置にある、正しいスタックポインタの絶対アドレスが計算されます。
4.  `MOVL SI, SP` は、計算された新しいスタックポインタの値を`SP`レジスタに復元します。

この一連の変更により、CGO呼び出し中にGoのスタックが移動しても、Goルーチンは常に正しいスタックポインタで実行を再開できるようになり、GoとC/C++間の相互運用における堅牢性が大幅に向上しました。

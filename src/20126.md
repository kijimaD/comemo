## 変更の背景

Go言語のランタイムは、スタックの管理、ガベージコレクション、デバッグ情報の生成において、各関数のスタックフレームサイズを正確に把握する必要があります。これは、関数呼び出し時にスタックポインタ（SP）がどのように調整されるかをリンカが理解していることに依存します。

このコミット以前は、Power64アーキテクチャにおいて、`add`命令がスタックポインタの調整に使用された場合、リンカがその調整を正しく認識していませんでした。具体的には、`add`命令がスタックポインタレジスタ（`REGSP`）を宛先とし、定数オフセットをソースとする形式の場合、リンカはこれがスタックの増減を意味することを把握できていませんでした。

この認識不足は、リンカが生成するスタックフレーム情報に誤りをもたらし、結果として以下のような問題を引き起こす可能性がありました。

*   **不正確なスタックトレース:** デバッグ時に、関数呼び出しの連鎖が正しく表示されない。
*   **ガベージコレクションの不具合:** スタック上のオブジェクトを正確に識別できず、メモリリークや誤ったメモリ解放につながる。
*   **スタックオーバーフローの検出ミス:** スタックの使用量が正しく追跡されないため、スタックオーバーフローが発生しても適切に検出できない。

この問題を解決するため、リンカが`add`命令によるスタックポインタの調整を明示的に認識し、内部的な`spadj`（スタック調整量）フィールドに反映させる必要がありました。

## 前提知識の解説

### Goのリンカ (`liblink`)

Go言語のビルドプロセスにおいて、リンカは非常に重要な役割を担っています。Goのコンパイラはソースコードをオブジェクトファイルに変換し、リンカ（`liblink`）はこれらのオブジェクトファイルを結合して実行可能ファイルを生成します。この過程で、リンカはシンボルの解決、コードの再配置、そして特にGoランタイムの要件に合わせて、スタックフレーム情報やガベージコレクションのためのメタデータを埋め込みます。アセンブリコードを含むGoプログラムの場合、リンカはアセンブリ命令を解析し、その命令がスタックにどのような影響を与えるかを理解する必要があります。

### スタックポインタ (Stack Pointer - SP)

スタックポインタ（SP）は、プログラムの実行中にコールスタックの現在のトップを指すCPUレジスタです。関数が呼び出されると、その関数のローカル変数、引数、リターンアドレスなどがスタックにプッシュされ、SPはスタックの新しいトップを指すように調整されます。関数が終了すると、これらのデータはスタックからポップされ、SPは元の位置に戻ります。SPの正確な管理は、プログラムの正しい実行、特に関数呼び出しと戻りのメカニズムにおいて不可欠です。

### Power64アーキテクチャ

Power64は、IBMが開発したPOWERアーキテクチャの64ビット版です。サーバーや高性能コンピューティング（HPC）の分野で広く使用されています。Go言語は、様々なアーキテクチャをサポートしており、Power64もその一つです。各アーキテクチャには独自の命令セットとレジスタの規約があり、リンカはそれぞれのアーキテクチャの特性に合わせてスタック操作を処理する必要があります。

### `AADD`命令

`AADD`は、Goのアセンブラ（`go tool asm`）が内部的に使用する命令コードの一つで、加算（`ADD`）操作を表します。アセンブリ言語では、`ADD`命令はレジスタやメモリの内容に値を加算するために使用されます。スタック操作においては、スタックポインタレジスタに定数を加算することで、スタックフレームのサイズを調整したり、スタック上の特定のオフセットにアクセスしたりするために用いられます。

### `spadj`フィールド

`spadj`（stack adjustment）は、Goリンカの内部データ構造（`Prog`構造体など、個々のアセンブリ命令を表すもの）に含まれるフィールドです。このフィールドは、その命令がスタックポインタをどれだけ調整するか（スタックフレームのサイズをどれだけ変更するか）を示すために使用されます。リンカは、この`spadj`値を用いて、関数のプロローグとエピローグにおけるスタックの増減を追跡し、正確なスタックフレーム情報を構築します。

## 技術的詳細

Goランタイムは、ガベージコレクタがスタックをスキャンして到達可能なオブジェクトを特定したり、デバッガがスタックトレースを生成したりするために、各関数のスタックフレームの正確なレイアウトとサイズを知る必要があります。この情報は、リンカによって生成される実行可能ファイル内のメタデータとして埋め込まれます。

スタックフレームのサイズを正確に決定するためには、リンカは関数内のすべてのアセンブリ命令がスタックポインタに与える影響を正確に追跡しなければなりません。特に、スタックポインタを明示的に変更する命令（例: `ADD SP, #constant` や `SUB SP, #constant`）は、その調整量を`spadj`フィールドに記録する必要があります。

このコミットの対象となったPower64アーキテクチャでは、特定の`add`命令（`ADD R_SP, constant`）がスタックポインタの調整として認識されていませんでした。これは、リンカがこの命令を一般的な加算命令として扱い、スタックポインタへの影響を特別に考慮していなかったためです。

この修正は、`obj9.c`内の命令処理ロジックに、`AADD`命令がスタックポインタレジスタ（`REGSP`）を宛先とし、定数（`D_CONST`）をソースとする場合に、その定数オフセットを`spadj`フィールドに反映させる処理を追加することで、この問題を解決します。`spadj`に負の値を設定しているのは、`ADD`命令で正の定数を加算すると、スタックポインタがアドレスの小さい方向（通常、スタックが成長する方向）に移動し、結果としてスタックフレームが「縮小」または「解放」されるためです。例えば、`ADD SP, 8`はスタックポインタを8バイト分「上に」移動させ、8バイト分のスタック領域を解放する意味合いを持ちます。そのため、スタック調整量としては`-8`となります。

この修正により、Power64アーキテクチャ上でも、リンカはスタックポインタの調整を正確に追跡できるようになり、Goランタイムの安定性とデバッグ可能性が向上しました。

## コアとなるコードの解説

### `src/liblink/list9.c` の変更

`src/liblink/list9.c`の変更は、リンカが内部的に保持する命令情報（`Prog`構造体など）の`spadj`フィールドの値を、命令のテキスト表現に含めるためのものです。これは、リンカのデバッグ出力やログにおいて、各命令がスタックポインタに与える影響を視覚的に確認できるようにするために役立ちます。この変更自体がスタック調整のロジックを変更するものではなく、その結果を可視化するためのものです。

### `src/liblink/obj9.c` の変更

`src/liblink/obj9.c`の変更が、このコミットの核心部分です。`addstacksplit`関数は、リンカがスタックフレームの分割やスタック情報の解析を行う際に呼び出される関数の一つです。この関数内で、各アセンブリ命令が順に処理されます。

追加されたコードブロックは、`AADD`（加算命令）を検出した際に実行されます。

```c
case AADD:
    if(p->to.type == D_REG && p->to.reg == REGSP && p->from.type == D_CONST)
        p->spadj = -p->from.offset;
    break;
```

*   `case AADD:`: 現在処理している命令が加算命令（`ADD`）であることを示します。
*   `if(p->to.type == D_REG && p->to.reg == REGSP && p->from.type == D_CONST)`: この条件文は、特定の形式の`ADD`命令をフィルタリングしています。
    *   `p->to.type == D_REG`: 命令の宛先（`to`オペランド）がレジスタであること。
    *   `p->to.reg == REGSP`: そのレジスタがスタックポインタレジスタ（`REGSP`）であること。
    *   `p->from.type == D_CONST`: 命令のソース（`from`オペランド）が定数であること。
    *   これらの条件がすべて満たされる場合、それは「スタックポインタに定数を加算する」という形式の命令であり、スタックの調整を意味します。
*   `p->spadj = -p->from.offset;`: この行が実際のスタック調整量の計算と記録を行っています。
    *   `p->from.offset`: `ADD`命令のソースオペランドである定数の値です。
    *   `-p->from.offset`: スタックは通常、アドレスの大きい方から小さい方へ成長します。`ADD SP, N`という命令は、スタックポインタのアドレスを`N`だけ増加させます。これは、スタックフレームが`N`バイト分「解放」された、あるいは「縮小」されたことを意味します。したがって、スタック調整量としては負の値（`-N`）として記録されるべきです。例えば、`ADD SP, 8`はスタックポインタを8バイト分進めるため、スタック調整量は`-8`となります。

この変更により、リンカはPower64アーキテクチャにおける`ADD`命令によるスタックポインタの調整を正確に認識し、`spadj`フィールドにその情報を記録できるようになりました。これにより、リンカが生成するスタックフレーム情報が正確になり、Goランタイムのスタック管理メカニズムが正しく機能するようになります。

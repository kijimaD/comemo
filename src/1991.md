# [インデックス 1991] ファイルの概要

このコミットは、Go言語の初期のツールチェーンにおけるARMアーキテクチャ用リンカ `5l` の `optab.c` ファイルに対する変更です。`optab.c` は、リンカがアセンブリ命令や擬似命令を実際の機械語に変換する際に参照する「操作テーブル（Operation Table）」または「オペコードテーブル（Opcode Table）」を定義しています。このテーブルは、各命令がどのような引数（オペランド）の型をサポートし、どのように処理されるべきかをリンカに指示する役割を担っています。

## コミット

このコミットは、ARMアーキテクチャにおけるソフトウェア割り込み（SWI）命令が「long constant」をオペランドとして使用するケースをサポートするように、リンカのオペコードテーブルを修正しています。これは特にLinuxシステムコールで使用されるモードに対応するための変更です。

## 変更の背景

この変更の背景には、Go言語がARMアーキテクチャ上でLinuxシステムコールを正しく発行できるようにするという具体的な要件がありました。

ARMアーキテクチャでは、ユーザーモードのアプリケーションがカーネルのサービス（システムコール）を要求するために、ソフトウェア割り込み（SWI: Software Interrupt）命令を使用します。Linuxシステムコールの場合、通常、システムコール番号が特定のレジスタに格納されるか、あるいはSWI命令自体に埋め込まれることがあります。

問題は、Goのリンカ `5l` が、SWI命令が「long constant」をオペランドとして取る形式を認識していなかったことにあります。ここでいう「long constant」とは、命令に直接埋め込むには大きすぎる定数値を指すことが多いです。システムコール番号がこのような大きな定数として扱われる場合、リンカがその形式をサポートしていなければ、正しくシステムコールを発行する機械語を生成できません。

このコミット以前は、`5l` はSWI命令に対して `C_NONE`（オペランドなし）または `C_LOREG`（レジスタからのオフセット付きアドレス）のオペランド型しかサポートしていませんでした。しかし、Linuxシステムコールの中には、SWI命令のオペランドとして直接大きな定数（システムコール番号など）を必要とする形式が存在したため、この不足を解消する必要がありました。この修正により、GoプログラムがARM Linux環境でシステムコールを適切に利用できるようになりました。

## 前提知識の解説

### 1. Go言語の初期ツールチェーンとPlan 9

Go言語の初期のコンパイラとリンカは、Bell LabsのPlan 9オペレーティングシステムで開発されたツールチェーン（`8c`/`8l`、`6c`/`6l`、`5c`/`5l` など）の影響を強く受けていました。
*   `5c`: ARMアーキテクチャ用Cコンパイラ
*   `5l`: ARMアーキテクチャ用リンカ
これらのツールは、Goのソースコードをコンパイルし、実行可能なバイナリにリンクするために使用されました。`5l` は、Goのオブジェクトファイル（擬似命令やデータを含む）を受け取り、それらを結合して最終的なARM実行可能ファイルを生成する役割を担っていました。

### 2. ARMアーキテクチャとSWI命令

ARM（Advanced RISC Machine）は、モバイルデバイスや組み込みシステムで広く使用されているRISCベースのプロセッサアーキテクチャです。
*   **SWI (Software Interrupt) 命令**: ARMプロセッサにおけるソフトウェア割り込み命令です。ユーザーモードのプログラムが、より高い特権レベル（カーネルモード）で実行されるオペレーティングシステム（OS）のサービスを要求するために使用されます。SWI命令が実行されると、プロセッサは例外ハンドラに制御を移し、カーネルがシステムコールを処理します。現代のARMv8-Aアーキテクチャでは、SWIはSVC (Supervisor Call) と呼ばれることが多いですが、機能は同様です。

### 3. Linuxシステムコール

Linuxシステムコールは、ユーザー空間のアプリケーションがカーネルの機能（ファイルI/O、メモリ管理、プロセス制御など）にアクセスするためのインターフェースです。ARM Linuxでは、SWI命令を使用してシステムコールが発行されます。システムコール番号は、通常、特定のレジスタ（例: R7）に格納されるか、SWI命令の即値オペランドとして渡されることがあります。

### 4. リンカにおける`optab`の役割

リンカは、コンパイラが生成したオブジェクトファイル（機械語命令とデータ、シンボル情報などを含む）を結合し、実行可能なプログラムを作成します。この過程で、リンカはアセンブリ命令を最終的な機械語に変換し、アドレス解決を行います。
`optab`（Operation TableまたはOpcode Table）は、リンカがこの変換を行うためのルックアップテーブルです。各エントリは、特定のアセンブリ命令（例: `ASWI`）に対して、それがどのようなオペランドの組み合わせをサポートし、どのように機械語にエンコードされるべきかを定義します。

`optab`のエントリは通常、以下のような構造を持っています（Goの`5l`の場合）：
`{ OPCODE, ARG0, ARG1, ARG2, ... }`
*   `OPCODE`: 命令の種類（例: `ASWI`）
*   `ARG0`, `ARG1`, `ARG2`: 命令が取るオペランドの型。例えば、`C_NONE`（オペランドなし）、`C_REG`（レジスタ）、`C_LCON`（ロング定数）などがあります。

### 5. 定数（Constant）と`C_LCON`

アセンブリ言語では、命令のオペランドとして定数（数値）を指定することがよくあります。
*   **即値定数**: 命令コードの一部として直接エンコードされる定数。命令のビット幅の制約により、表現できる値の範囲が限られます。
*   **ロング定数 (Long Constant)**: 即値定数として命令に直接埋め込むには大きすぎる定数。このような定数は、通常、メモリ上のリテラルプール（定数プール）に格納され、命令はそのメモリ位置を指すようにエンコードされます。
`C_LCON` は、Goのリンカにおけるオペランド型の一つで、「ロング定数」を意味します。これは、リンカがこのオペランドをメモリ上の定数として扱い、必要に応じてそのアドレスを解決して命令に組み込むことを示します。

## 技術的詳細

このコミットの技術的詳細は、`src/cmd/5l/optab.c` 内の `Optab` 構造体配列に新しいエントリを追加することに集約されます。

`optab`配列は、GoのARMリンカ `5l` がサポートする命令とそのオペランドの組み合わせを定義しています。各エントリは、特定の命令（例: `ASWI`）がどのような種類のオペランド（ソース、デスティネーションなど）を受け入れるかを記述します。

元の `optab` には、`ASWI` 命令に対して以下の2つのエントリがありました。

```c
{ ASWI,      C_NONE, C_NONE, C_NONE,      10, 4, 0 },
{ ASWI,      C_NONE, C_NONE, C_LOREG,     10, 4, 0 },
```

*   1行目: `ASWI` 命令がオペランドを全く取らないケース。
*   2行目: `ASWI` 命令が `C_LOREG` 型のオペランドを取るケース。`C_LOREG` は、レジスタからのオフセット付きアドレスを意味します。

しかし、Linuxシステムコールの中には、SWI命令のオペランドとして直接「ロング定数」（システムコール番号など）を必要とする形式が存在しました。この形式は、既存の `optab` エントリではカバーされていませんでした。

このコミットでは、以下の新しいエントリが追加されました。

```c
{ ASWI,      C_NONE, C_NONE, C_LCON,      10, 4, 0 },
```

この新しいエントリは、`ASWI` 命令が `C_LCON` 型のオペランド（ロング定数）をサポートすることをリンカに伝えます。これにより、リンカはSWI命令のオペランドとして大きな定数値を正しく処理し、対応する機械語を生成できるようになります。

`10, 4, 0` といったマジックナンバーのような値は、`optab` の内部的なエンコーディング情報であり、命令のバイト数、アラインメント、または特定の処理フラグなどを示す可能性があります。これらはリンカが命令を正しく配置し、最終的なバイナリを生成するために必要なメタデータです。

この変更により、Goのコンパイラが生成するARMアセンブリコードが、SWI命令とロング定数を組み合わせたLinuxシステムコールを表現できるようになり、`5l` リンカがそれを正しく実行可能ファイルに変換できるようになりました。

## コアとなるコードの変更箇所

変更は `src/cmd/5l/optab.c` ファイルの1箇所です。

```diff
--- a/src/cmd/5l/optab.c
+++ b/src/cmd/5l/optab.c
@@ -75,6 +77,7 @@ Optab	optab[] =
 
 	{ ASWI,		C_NONE,\tC_NONE,\tC_NONE,\t\t10, 4, 0 },
 	{ ASWI,		C_NONE,\tC_NONE,\tC_LOREG,\t10, 4, 0 },
+	{ ASWI,		C_NONE,\tC_NONE,\tC_LCON,\t\t10, 4, 0 },
 
 	{ AWORD,\tC_NONE,\tC_NONE,\tC_LCON,\t\t11, 4, 0 },
 	{ AWORD,\tC_NONE,\tC_NONE,\tC_GCON,\t\t11, 4, 0 },
```

追加された行は以下の通りです。

```c
{ ASWI,		C_NONE,\tC_NONE,\tC_LCON,\t\t10, 4, 0 },
```

## コアとなるコードの解説

追加された行 `{ ASWI, C_NONE, C_NONE, C_LCON, 10, 4, 0 }` は、`optab` 配列の新しいエントリです。

*   `ASWI`: これはARMのソフトウェア割り込み（SWI）命令を表す内部的なオペコードです。
*   `C_NONE`: 最初の2つの `C_NONE` は、この命令が最初の2つのオペランド（通常はソースレジスタやデスティネーションレジスタなど）を必要としないことを示します。SWI命令は通常、システムコール番号を直接オペランドとして取るか、レジスタ経由で渡すため、このような形式が考えられます。
*   `C_LCON`: これは3番目のオペランドの型を示しており、「ロング定数（Long Constant）」を意味します。この `C_LCON` の追加がこのコミットの核心です。これにより、リンカはSWI命令が直接大きな定数値をオペランドとして受け取るケースを正しく処理できるようになります。この定数は、命令に直接埋め込むには大きすぎるため、リンカがリテラルプールなどからロードする処理を生成します。
*   `10, 4, 0`: これらの数値は、リンカがこの命令を処理する際の内部的なメタデータです。具体的な意味はリンカの実装に依存しますが、例えば、命令のエンコーディング形式、バイト長、アラインメント、または特定の処理フラグなどを示す可能性があります。

このエントリが追加されたことで、Goのリンカ `5l` は、ARMアーキテクチャ上でSWI命令がロング定数をオペランドとして使用する、特にLinuxシステムコールで用いられる形式を正しく解釈し、実行可能な機械語に変換できるようになりました。これにより、GoプログラムがARM Linux環境でより広範なシステムコールを問題なく利用できるようになります。

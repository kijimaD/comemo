# [インデックス 23397] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `cmd/internal/gc` における最適化に関するものです。具体的には、`x = f()` のような単純な代入文において、コンパイラが不必要に一時変数 (`tmp = f(); x = tmp`) を導入するのを避けるように変更されています。これにより、スタックフレームサイズの削減、最適化処理の負荷軽減、そして全体的なパフォーマンスの向上が期待されます。

## 元コミット内容

このコミットの目的は、Goコンパイラが `x = f()` のような代入文を処理する際に、不必要な一時変数の導入を回避することです。以前のコンパイラは、このような単純な代入であっても、`tmp = f(); x = tmp` のように一時変数 `tmp` を介して値を代入するコードを生成することがありました。この変更は、この挙動を抑制し、直接 `x = f()` の結果を `x` に代入するように試みます。

コミットメッセージには、この変更が予想以上に多くのベンチマークで速度低下を引き起こしたものの、同時に速度向上も見られ、スタックフレームサイズの削減と最適化処理の負荷軽減というメリットがあるため、全体としては「net win（純益）」であると述べられています。

ベンチマーク結果は以下の通りです（一部抜粋）：
*   `BenchmarkFannkuch11`: +0.88% (速度低下)
*   `BenchmarkFmtFprintfEmpty`: +4.31% (速度低下)
*   `BenchmarkFmtFprintfString`: +6.05% (速度低下)
*   `BenchmarkFmtFprintfInt`: -3.42% (速度向上)
*   `BenchmarkHTTPClientServer`: -1.90% (速度向上)
*   `BenchmarkRegexpMatchEasy0_32`: -9.33% (速度向上)

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な最適化を行います。その一つに、式の評価順序を決定し、必要に応じて一時変数を導入する「ordering（順序付け）」フェーズがあります。このフェーズの目的は、プログラムのセマンティクスを維持しつつ、後続の最適化パスが処理しやすいように中間表現を整形することです。

しかし、`x = f()` のような単純な代入において、`f()` の結果を一時変数に格納し、その一時変数を `x` に代入するという冗長な処理は、以下の問題を引き起こす可能性がありました。

1.  **スタックフレームサイズの増加**: 一時変数は通常、スタック上に割り当てられるため、不必要な一時変数の導入はスタックフレームサイズを増加させ、メモリ使用効率を低下させます。
2.  **最適化処理の負荷**: 一時変数を介した代入は、後続の最適化パス（例: SSA変換、レジスタ割り当て）にとって余分な処理となり、コンパイラの処理時間を増加させる可能性があります。
3.  **実行時パフォーマンスの低下**: 不必要なメモリ操作（一時変数への書き込みと読み出し）は、プログラムの実行速度に悪影響を与える可能性があります。

このコミットは、これらの問題を軽減し、コンパイラがより効率的なコードを生成できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造と、特に「ordering（順序付け）」フェーズに関する知識が必要です。

1.  **Goコンパイラのパイプライン**: Goコンパイラ (`cmd/compile`) は、ソースコードを以下の主要なフェーズで処理します。
    *   **Parsing (構文解析)**: ソースコードをトークン化し、抽象構文木 (AST: Abstract Syntax Tree) を構築します。
    *   **Type Checking (型チェック)**: ASTに対して型チェックと意味解析を行い、プログラムの正当性を検証します。
    *   **IR Construction ("Noding")**: ASTをコンパイラ独自の内部中間表現 (IR: Intermediate Representation) に変換します。
    *   **Middle End / Optimization Passes (中間最適化)**: IRに対して様々な最適化を適用します。これには、デッドコード削除、インライン化、エスケープ解析などが含まれます。
    *   **Walk (ウォーク)**: このフェーズは中間最適化の一部であり、複雑なステートメントをより単純なものに分解し、Goの高レベルな構文（`switch`文、マップ操作、チャネル操作など）をよりプリミティブな形式やランタイム呼び出しに「脱糖（desugar）」します。`src/cmd/internal/gc/order.go` はこの「Walk」フェーズ、またはそれに密接に関連する順序付けパスで動作します。
    *   **SSA (Static Single Assignment) Form Conversion**: IRをSSA形式に変換します。SSAは、さらなる最適化や機械語生成を容易にする低レベルの中間表現です。
    *   **SSA Optimization Passes**: SSA形式に対して、機械独立および機械固有の最適化パスが実行されます。
    *   **Lowering (低レベル化)**: 汎用的なSSA値をターゲットアーキテクチャに特化した機械語相当の表現に書き換えます。
    *   **Code Generation (コード生成)**: 最適化されたSSA形式からプラットフォーム固有の機械語を生成します。
    *   **Linking (リンク)**: 生成された機械語と依存関係を結合し、実行可能バイナリを作成します。

2.  **`order.go` の役割**: `src/cmd/internal/gc/order.go` は、コンパイラの「Walk」フェーズにおいて、式の評価順序を決定し、副作用を適切に処理するために一時変数を導入する役割を担っています。これは、プログラムのセマンティクスを正確に表現し、後続のコード生成フェーズが効率的に処理できるようにするために不可欠です。

3.  **`Node` 構造体**: GoコンパイラのASTおよびIRは、`Node` 構造体で表現されます。`Node` は、変数、定数、演算子、関数呼び出しなど、プログラムのあらゆる要素を表すことができます。`Node.Op` フィールドは、そのノードがどのような種類の操作を表すかを示します（例: `OAS` は代入、`ONAME` は変数名、`OCALLFUNC` は関数呼び出し）。

4.  **一時変数 (`tmp`) の導入**: コンパイラは、複雑な式や副作用を持つ式を評価する際に、中間結果を保持するための一時変数を導入することがあります。これは、評価順序を保証したり、式の値を複数回使用する必要がある場合に特に重要です。
    *   `ordercopyexpr`: 式の評価順序を決定し、必要に応じて一時変数を介して式の値をコピーする処理に関連します。
    *   `marktemp`: コンパイラが導入する一時変数を管理するための関数です。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/internal/gc/order.go` ファイル内の `orderexpr` 関数のシグネチャ変更と、それに伴うロジックの調整にあります。

以前の `orderexpr` 関数は、式を順序付けし、副作用を `order->out` に追加する役割を担っていました。しかし、この関数は、その式が代入文の左辺（LHS: Left-Hand Side）であるかどうかを知る術がありませんでした。そのため、`x = f()` のようなケースでも、`f()` の結果を一時変数に格納し、その一時変数を `x` に代入するという、冗長なコードを生成してしまう可能性がありました。

このコミットでは、`orderexpr` 関数のシグネチャに `lhs *Node` という新しいパラメータが追加されました。
変更前: `func orderexpr(np **Node, order *Order)`
変更後: `func orderexpr(np **Node, order *Order, lhs *Node)`

この `lhs` パラメータは、現在処理している式が代入文の右辺（RHS: Right-Hand Side）であり、その結果が `lhs` に代入されることを示します。`lhs` が `nil` の場合、その式は代入の右辺ではないか、あるいは代入の左辺が単純な変数ではないことを意味します。

この新しい `lhs` パラメータを活用することで、`orderexpr` 関数は、`x = f()` のような状況で、`f()` の結果を一時変数にコピーする (`ordercopyexpr` を呼び出す) かどうかをより賢く判断できるようになりました。

具体的には、`orderexpr` 関数内の関数呼び出し (`OCALL`, `OCALLFUNC`, `OCALLINTER`, `OMETHVALUE`, `OREAL`, `ORECOVER` など) を処理する部分で、一時変数の導入を制御する条件が追加されました。

```go
if lhs == nil || lhs.Op != ONAME || flag_race != 0 {
    n = ordercopyexpr(n, n.Type, order, 0)
}
```

この条件文は以下のように解釈されます。

*   `lhs == nil`: 現在の式が代入の右辺ではない場合（例: `f()` が単独で呼び出される場合）。
*   `lhs.Op != ONAME`: 代入の左辺が単純な変数名 (`ONAME`) ではない場合（例: `m[key] = f()` のようなマップ要素への代入や、構造体フィールドへの代入など）。
*   `flag_race != 0`: レース検出器 (`-race` フラグ) が有効になっている場合。レース検出器は、メモリ競合を検出するために追加のチェックや同期メカニズムを導入するため、一時変数の導入が必要になる場合があります。

上記のいずれかの条件が真である場合、`ordercopyexpr` が呼び出され、`f()` の結果は一時変数にコピーされます。しかし、これらの条件がすべて偽である場合、つまり「単純な変数 `x` への代入 (`x = f()`) であり、かつレース検出器が有効でない」という状況では、`ordercopyexpr` は呼び出されず、`f()` の結果は直接 `x` に代入されるようになります。これにより、不必要な一時変数の導入が回避されます。

## コアとなるコードの変更箇所

変更は `src/cmd/internal/gc/order.go` ファイルに集中しています。

1.  **`orderexpr` 関数のシグネチャ変更**:
    ```diff
    -func orderexpr(np **Node, order *Order) {
    +func orderexpr(np **Node, order *Order, lhs *Node) {
    ```
    `lhs *Node` パラメータが追加されました。

2.  **`orderexpr` の呼び出し箇所の変更**:
    `orderexpr` を呼び出すすべての箇所で、新しい `lhs` パラメータが追加されています。ほとんどのケースでは `nil` が渡されますが、`OAS` (単純な代入) のケースでは `n.Left` が渡されます。

    例:
    *   `orderexprinplace`: `orderexpr(&n, &order, nil)`
    *   `ordercall`: `orderexpr(&n.Left, order, nil)`
    *   `orderstmt` 内の多くの箇所: `orderexpr(&expr, order, nil)`

3.  **`orderstmt` 内の `OAS` (代入) の処理変更**:
    `OAS` のケースが `OAS2` などから分離され、`n.Left` を `lhs` として `orderexpr` が呼び出されるようになりました。

    ```diff
    -	case OAS,
    -		OAS2,
    +	case OAS:
    +		t := marktemp(order)
    +		orderexpr(&n.Left, order, nil)
    +		orderexpr(&n.Right, order, n.Left) // ここで n.Left が lhs として渡される
    +		ordermapassign(n, order)
    +		cleantemp(t, order)
    +
    +	case OAS2,
    ```

4.  **`orderexpr` 内の `ordercopyexpr` の条件付き呼び出し**:
    `orderexpr` 関数内の `OCALL` などのオペレーションを処理する `case` ブロックで、`ordercopyexpr` の呼び出しが条件付きになりました。

    ```diff
    	case OCALL,
    		OCALLFUNC,
    		OCALLINTER,
    		OMETHVALUE,
    		OREAL,
    		ORECOVER:
    		ordercall(n, order)
    -		n = ordercopyexpr(n, n.Type, order, 0)
    +		if lhs == nil || lhs.Op != ONAME || flag_race != 0 {
    +			n = ordercopyexpr(n, n.Type, order, 0)
    +		}
    ```

## コアとなるコードの解説

このコミットの核心は、Goコンパイラの「ordering」フェーズにおける式の評価と一時変数の管理をより洗練させる点にあります。

`orderexpr` 関数は、GoのASTノードを走査し、各式の評価順序を決定し、必要に応じて副作用を収集します。この関数は、コンパイラが生成するコードの効率に直接影響を与えます。

新しい `lhs *Node` パラメータの導入により、`orderexpr` はコンテキストを認識できるようになりました。つまり、現在処理している式が、特定の変数への代入の右辺であるかどうかを知ることができます。この情報は、コンパイラが一時変数を導入するかどうかを決定する上で非常に重要です。

具体的には、`x = f()` のような代入文をコンパイルする際、`f()` の結果を `x` に直接代入できるのであれば、中間の一時変数は不要です。しかし、`m[key] = f()` のように、左辺が複雑な式である場合や、`flag_race` が有効な場合は、セマンティクスを維持したり、競合状態を検出するために一時変数が必要になることがあります。

このコミットは、これらのケースを区別し、不必要な一時変数の導入を抑制することで、コンパイラが生成するコードの品質を向上させます。結果として、スタックフレームのフットプリントが減少し、コンパイラの最適化パスの負担が軽減され、全体的な実行時パフォーマンスの向上が期待されます。ベンチマーク結果が混在しているのは、この最適化が特定のコードパターンには有効であるものの、他のパターンではオーバーヘッドが発生する可能性を示唆しています。しかし、コンパイラの設計者は、長期的なメリット（スタック使用量の削減、最適化の簡素化）を考慮して、この変更が「net win」であると判断しています。

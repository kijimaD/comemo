# [インデックス 26723] ファイルの概要

このコミットは、Goコンパイラの字句解析器（lexer）の内部処理を改善し、よりシンプルで高速な字句解析を実現することを目的としています。具体的には、字句解析器が常にバイトではなくUnicodeのルーン（rune）を読み込むように変更し、それに伴うロジックの簡素化と最適化が行われています。

## 変更の背景

Goコンパイラの字句解析器は、ソースコードをトークンに分割する初期段階を担います。以前の字句解析器は、主にバイト単位で文字を読み込み、必要に応じてUnicodeルーンに変換していました。このアプローチは、特にマルチバイトのUnicode文字を扱う際に、ロジックを複雑にする傾向がありました。

このコミットの背景には、以下の課題と目的がありました。

1.  **ロジックの複雑さの解消**: バイトとルーンの混在した処理が、コードの可読性と保守性を低下させていました。常にルーンとして文字を読み込むことで、字句解析器の内部ロジックを大幅に簡素化できると考えられました。
2.  **最適化の可能性**: ロジックが簡素化されることで、将来的なパフォーマンス最適化の道が開かれる可能性があります。
3.  **識別子認識の改善**: 識別子（変数名、関数名など）の解析ロジックをより直接的かつ効率的にすることで、コードの品質とエラー報告を向上させる狙いがありました。
4.  **不正文字の早期検出**: 不正な文字（特に制御文字や特定のUnicode範囲の文字）を早期に、かつより明確なエラーメッセージで検出できるようにすることで、コンパイラのエラー報告の質を高めます。
5.  **不要な変換の削減**: バイトからルーンへの頻繁な型変換をなくすことで、コードがクリーンになり、わずかながら実行効率も向上する可能性があります。

これらの変更は、コンパイラの堅牢性と効率性を高め、開発者がより良いエラーメッセージを受け取れるようにすることを目的としています。

## 前提知識の解説

### 1. コンパイラの字句解析器（Lexer/Tokenizer）

コンパイラは、ソースコードを機械が理解できる形式に変換するソフトウェアです。その最初の段階が「字句解析（Lexical Analysis）」であり、これを担当するのが「字句解析器（Lexer）」または「トークナイザ（Tokenizer）」です。

字句解析器の役割は以下の通りです。
*   **ソースコードの読み込み**: プログラムのテキストを文字ストリームとして読み込みます。
*   **トークンへの分割**: 意味のある最小単位（「トークン」と呼ばれる）に分割します。例えば、`var x = 10;`というコードは、`var`（キーワード）、`x`（識別子）、`=`（演算子）、`10`（リテラル）、`;`（区切り文字）といったトークンに分割されます。
*   **不要な要素の除去**: コメントや空白文字など、プログラムの意味に影響しない要素を除去します。
*   **エラー報告**: 字句的に不正な文字やシーケンスを検出した場合、エラーを報告します。

### 2. Go言語におけるRuneとByte、UTF-8

Go言語では、文字列はUTF-8でエンコードされたバイト列として扱われます。
*   **`byte`**: Goにおける`byte`型は`uint8`のエイリアスであり、8ビットのデータを表します。これは通常、ASCII文字やUTF-8エンコードされたマルチバイト文字の個々のバイトを指します。
*   **`rune`**: Goにおける`rune`型は`int32`のエイリアスであり、単一のUnicodeコードポイントを表します。UTF-8では、1つのUnicodeコードポイントが1バイトから4バイトで表現されます。例えば、ASCII文字は1バイトのルーンとして、日本語の漢字などは3バイトのルーンとして表現されます。

字句解析器がバイト単位で処理する場合、マルチバイト文字の境界を意識し、正しくデコードするロジックが必要になります。一方、ルーン単位で処理する場合、文字そのものとして扱えるため、ロジックが簡素化されます。

### 3. `getc()` と `getr()` (字句解析器の文脈で)

このコミットの文脈では、`getc()`と`getr()`は字句解析器が入力ストリームから次の文字を読み込むための内部関数を指します。
*   **`getc()`**: 次の1バイトを読み込む関数。
*   **`getr()`**: 次の1ルーン（Unicodeコードポイント）を読み込む関数。`getr()`は内部で複数バイトを読み込み、UTF-8デコードを行って1つのルーンを返します。

### 4. BOM (Byte Order Mark)

BOM（バイトオーダーマーク）は、UTF-8などのUnicodeエンコーディングでファイルの先頭に付加される特殊なバイトシーケンスです。UTF-8のBOMは`EF BB BF`という3バイトで構成され、ファイルのエンコーディングを示すために使用されます。しかし、UTF-8はバイトオーダーの概念を持たないため、UTF-8ファイルにBOMを含めることは推奨されず、特にGoのソースコードではBOMは通常許可されません。

## 技術的詳細

このコミットの核となる技術的変更は、Goコンパイラの字句解析器が入力ストリームを処理する方法を、バイト単位からルーン単位へと根本的に移行した点にあります。

### 1. `getc()` から `getr()` への全面的な移行

*   以前は、字句解析器は`l.getc()`関数を使用して入力から1バイトずつ読み込んでいました。マルチバイトのUnicode文字を処理する必要がある場合、`getc()`を複数回呼び出し、その後UTF-8デコードを行う必要がありました。
*   この変更により、字句解析器は`l.getr()`関数を常に使用するようになりました。`l.getr()`は、内部で必要に応じて複数バイトを読み込み、完全なUnicodeルーンをデコードして返します。これにより、字句解析器のメインロジックは、バイトレベルの複雑さを意識することなく、直接ルーンを扱えるようになりました。
*   `lexer`構造体内の`peekc`, `peekc1` (int型) は、`peekr1`, `peekr2` (rune型) に変更され、先読みバッファもルーン単位で保持されるようになりました。
*   `ungetc()`関数は削除され、`ungetr()`関数が導入されました。これは、読み込んだルーンをストリームに戻すためのものです。

### 2. 識別子（Identifier）解析の簡素化と効率化

*   **`talph`ラベルの削除**: 以前の字句解析器では、識別子を解析するための専用の`talph`という`goto`ラベルが存在し、メインの字句解析ループからジャンプして処理を行っていました。このコミットでは、識別子の解析ロジックが`next()`関数のメインループ内に「インライン」で統合されました。これにより、コードのフローがより直線的になり、理解しやすくなりました。
*   **7ビットASCIIとマルチバイトUnicodeの効率的な処理**:
    *   `isLetter(c) || isDigit(c)`というチェックで、まず一般的な7ビットASCIIの識別子文字（英字、数字）を高速に処理します。
    *   その後、`c >= utf8.RuneSelf`（マルチバイト文字の開始を示す）の場合に、`unicode.IsLetter(c)`, `unicode.IsDigit(c)`などの`unicode`パッケージの関数を使用して、より広範なUnicode文字セットに対応します。これにより、ASCII文字とUnicode文字の両方を効率的かつ正確に識別子として認識できるようになりました。
*   **識別子の不正開始文字の厳格化**: 識別子が数字で始まることを禁止するチェックが強化され、`Yyerror("identifier cannot begin with digit %#U", c)`のような明確なエラーメッセージが出力されるようになりました。

### 3. 不正文字（"frogs"）の処理改善

*   以前は、字句解析器は`0x80`未満のすべての文字を一旦受け入れ、その後`isfrog()`関数で不正な制御文字や特定のUnicode範囲の文字（"frogs"と表現されていた）をチェックしていました。
*   この変更により、`isfrog()`関数は削除され、字句解析器は最初から有効な文字のみを許可するようになりました。これにより、不要なチェックが削減され、ロジックが簡素化されるとともに、不正な文字が検出された際には`Yyerror("syntax error: illegal character %#U", c)`のように、より具体的で分かりやすいエラーメッセージが即座に報告されるようになりました。

### 4. 不要な`int`変換の削減

`getr()`が`rune`（`int32`のエイリアス）を返すようになったため、以前は`int`型で扱われていた文字コードが直接`rune`型として扱えるようになり、多くの場所で明示的な`int`型への変換が不要になりました。これにより、コードがよりクリーンになり、型安全性が向上しました。

### 5. BOM (Byte Order Mark) 処理の統合

BOMの検出と処理ロジックが`getr()`関数内に統合されました。これにより、ファイルの途中でBOMが検出された場合に`yyerrorl`でエラーを報告し、そのBOMをスキップして字句解析を続行できるようになりました。

### 6. パフォーマンスへの影響

コミットメッセージによると、`time go build -a net/http`のベンチマークでは約1%の速度向上が見られました。これは「ノイズの範囲内」とされていますが、少なくともパフォーマンスの劣化は発生しておらず、ロジックの簡素化と同時にわずかながらも効率が向上したことを示唆しています。

## コアとなるコードの変更箇所

主な変更は `src/cmd/compile/internal/gc/lex.go` ファイルに集中しています。

1.  **`lexer` 構造体の変更**:
    *   `peekc int`, `peekc1 int` が `peekr1 rune`, `peekr2 rune` に変更されました。これにより、先読みバッファがバイトではなくルーンを保持するようになりました。

2.  **`getc()` 関数の削除と `getr()` 関数の大幅な変更**:
    *   `getc()` 関数が完全に削除されました。
    *   `getr()` 関数が、入力ストリームから直接UTF-8デコードを行い、ルーンを返すように書き換えられました。これには、7ビットASCII文字の高速パスと、マルチバイト文字のデコードロジック、そしてBOMの検出とエラー処理が含まれます。

3.  **`ungetc()` 関数の削除と `ungetr()` 関数の追加**:
    *   `ungetc()` 関数が削除され、`ungetr(r rune)` 関数が追加されました。これは、読み込んだルーンを字句解析器の先読みバッファに戻すために使用されます。

4.  **文字判定関数の変更**:
    *   `isSpace(c int)`, `isAlpha(c int)`, `isDigit(c int)` が `isSpace(c rune)`, `isLetter(c rune)`, `isDigit(c rune)` に変更され、引数が`rune`型になりました。
    *   `isAlpha` は `isLetter` に改名され、`_`（アンダースコア）も文字として認識するようになりました。
    *   `isAlnum(c int)` および `isfrog(c int)` 関数は削除されました。

5.  **`next()` 関数の字句解析ロジックの変更**:
    *   ホワイトスペースのスキップ、識別子の解析、数値リテラルの解析、文字列リテラルの解析など、字句解析の主要なロジックが`getr()`を使用するように全面的に書き換えられました。
    *   特に、識別子解析のための`talph`ラベルへの`goto`が削除され、識別子解析ロジックが`next()`関数内にインライン化されました。
    *   不正文字のチェックが`isfrog`の呼び出しから、`default`ケースでの`Yyerror`呼び出しに置き換えられました。

6.  **エラーメッセージの変更**:
    *   `test/fixedbugs/issue11610.go` のテストケースで、`var?` のエラーメッセージが `unexpected ?` から `illegal character U+003F '?'` へと、より詳細なUnicodeコードポイントを含む形式に変更されました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`lexer`構造体と、`getr()`、`ungetr()`、そして`next()`関数の実装にあります。

### `lexer` 構造体

```go
type lexer struct {
	// source
	bin    *obj.Biobuf
	peekr1 rune
	peekr2 rune // second peekc for ...

	nlsemi bool // if set, '\n' and EOF translate to ';'

	// ... (他のフィールドは省略)
}
```
`peekc`と`peekc1`が`peekr1`と`peekr2`に変わったことで、字句解析器は次に読み込むルーンを最大2つまで先読みできるようになりました。これにより、例えば`...`のような複数文字トークンの解析が容易になります。

### `getr()` 関数

```go
func (l *lexer) getr() rune {
	// unread rune != 0 available
	if r := l.peekr1; r != 0 {
		l.peekr1 = l.peekr2
		l.peekr2 = 0
		if r == '\n' && importpkg == nil {
			lexlineno++
		}
		return r
	}

redo:
	// common case: 7bit ASCII
	c := obj.Bgetc(l.bin)
	if c < utf8.RuneSelf { // utf8.RuneSelf は 0x80
		if c == 0 {
			Yyerror("illegal NUL byte")
			return 0
		}
		if c == '\n' && importpkg == nil {
			lexlineno++
		}
		return rune(c)
	}

	// uncommon case: non-ASCII
	var buf [utf8.UTFMax]byte
	buf[0] = byte(c)
	buf[1] = byte(obj.Bgetc(l.bin))
	i := 2
	for ; i < len(buf) && !utf8.FullRune(buf[:i]); i++ {
		buf[i] = byte(obj.Bgetc(l.bin))
	}

	r, w := utf8.DecodeRune(buf[:i])
	if r == utf8.RuneError && w == 1 {
		lineno = lexlineno
		Yyerror("illegal UTF-8 sequence % x", string(buf[:i+1]))
	}

	if r == BOM {
		yyerrorl(int(lexlineno), "Unicode (UTF-8) BOM in middle of file")
		goto redo
	}

	return r
}
```
この`getr()`関数は、字句解析器の新しい心臓部です。
1.  **先読みバッファのチェック**: `l.peekr1`に未読のルーンがあれば、それを返し、バッファをシフトします。
2.  **7ビットASCIIの高速パス**: `obj.Bgetc(l.bin)`で1バイト読み込み、それが`utf8.RuneSelf`（0x80）未満であれば、ASCII文字として直接`rune`に変換して返します。これにより、最も一般的なケースで高速な処理が可能です。
3.  **マルチバイトUnicodeの処理**: `c >= utf8.RuneSelf`の場合、複数バイトを読み込み、`utf8.DecodeRune`を使ってUTF-8デコードを行います。
4.  **不正なUTF-8シーケンスの検出**: `utf8.DecodeRune`が`utf8.RuneError`を返した場合、不正なUTF-8シーケンスとしてエラーを報告します。
5.  **BOMの処理**: 読み込んだルーンがBOM（`0xFEFF`）だった場合、エラーを報告し、`goto redo`で次のルーンの読み込みを再試行します。これは、ファイルの途中にBOMが出現した場合の処理です。

### `next()` 関数内の識別子解析ロジック

```go
	// identifiers and keywords
	// (for better error messages consume all chars >= utf8.RuneSelf for identifiers)
	if isLetter(c) || c >= utf8.RuneSelf {
		cp = &lexbuf
		cp.Reset()

		// accelerate common case (7bit ASCII)
		for isLetter(c) || isDigit(c) {
			cp.WriteByte(byte(c))
			c = l.getr()
		}

		// general case
		for {
			if c >= utf8.RuneSelf {
				if unicode.IsLetter(c) || c == '_' || unicode.IsDigit(c) || importpkg != nil && c == 0xb7 {
					if cp.Len() == 0 && unicode.IsDigit(c) {
						Yyerror("identifier cannot begin with digit %#U", c)
					}
				} else {
					Yyerror("invalid identifier character %#U", c)
				}
				cp.WriteRune(c)
			} else if isLetter(c) || isDigit(c) {
				cp.WriteByte(byte(c))
			} else {
				break
			}
			c = l.getr()
		}

		cp = nil
		l.ungetr(c)

		s := LookupBytes(lexbuf.Bytes())
		// ... (キーワード判定とトークン設定)
		return
	}
```
このコードブロックは、`next()`関数内で識別子とキーワードを解析する新しいロジックです。
1.  **識別子の開始判定**: `isLetter(c)`（ASCIIの英字またはアンダースコア）または`c >= utf8.RuneSelf`（マルチバイト文字）の場合、識別子として処理を開始します。
2.  **ASCII識別子の高速処理**: 最初の`for`ループで、7ビットASCIIの英字または数字が続く限り、`getr()`でルーンを読み込み、バイトとしてバッファに書き込みます。これは最も一般的なケースであり、高速に処理されます。
3.  **一般ケース（Unicode識別子）の処理**: 2番目の`for`ループで、より複雑なUnicode識別子を処理します。
    *   `c >= utf8.RuneSelf`の場合、`unicode`パッケージの関数（`unicode.IsLetter`, `unicode.IsDigit`）を使用して、そのルーンが識別子として有効かチェックします。
    *   識別子が数字で始まる不正なケースを検出し、`Yyerror`でエラーを報告します。
    *   不正なUnicode文字が識別子内に含まれる場合も`Yyerror`でエラーを報告します。
    *   有効なルーンは`cp.WriteRune(c)`でバッファに書き込まれます。
4.  **トークン化**: 識別子の終端に達したら、`l.ungetr(c)`で最後のルーンを戻し、`LookupBytes`でバッファの内容を調べて、それがキーワードか通常の識別子かを判断し、対応するトークンを設定します。

この変更により、識別子の解析ロジックが`next()`関数内に集約され、`getr()`によって常にルーン単位で処理されるため、コードがより簡潔で堅牢になりました。また、不正な文字に対するエラー報告も改善されています。

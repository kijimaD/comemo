## 変更の背景

Go言語のマップ（`map`）は、その設計上、要素をイテレートする際の順序が保証されていません。これは意図的な設計であり、プログラマがマップの特定の順序に依存するコードを書くことを防ぎ、より堅牢で移植性の高いプログラムを作成することを促すためです。もし順序が保証されてしまうと、開発者はその順序に依存したコードを書きがちになり、将来のGoのバージョンアップや異なる環境での実行時に、順序の変更によって予期せぬバグが発生するリスクが高まります。

この非決定的な挙動は、特にテストにおいて重要になります。マップのイテレーション順序に依存するバグは、特定の順序でしか顕在化しないため、テストが十分な数の異なる順序を試行しないと見過ごされる可能性があります。

このコミットは、バグトラッカーのIssue #8736に関連しています。このIssueは、従来の80回の試行では、マップのイテレーション順序が異なるケースを十分にカバーできておらず、特定の条件下で順序依存のバグがテストで検出されない可能性があったことを示唆しています。そのため、試行回数を800回に増やすことで、より多くの異なるイテレーション順序を網羅し、テストの信頼性を向上させることを目的としています。

## 前提知識の解説

### Go言語のマップ (map) の特性

Go言語のマップは、キーと値のペアを格納するハッシュテーブルに基づいたデータ構造です。その最も重要な特性の一つは、**イテレーション順序が保証されない**ことです。

*   **非決定性 (Non-determinism)**: `for range` ループを使ってマップをイテレートする際、要素が返される順序は実行ごとに異なる可能性があります。これは、マップの内部実装（ハッシュ関数のシード値、要素の追加・削除履歴など）に依存するためです。
*   **意図的な設計**: この非決定性は、Go言語の設計思想の一部です。プログラマがマップの特定の順序に依存するコードを書くことを防ぎ、より堅牢で移植性の高いプログラムを作成することを促します。もし順序が保証されてしまうと、開発者はその順序に依存したコードを書きがちになり、将来のGoのバージョンアップや異なる環境での実行時に、順序の変更によって予期せぬバグが発生するリスクが高まります。
*   **テストへの影響**: 非決定的な挙動は、テストの設計に影響を与えます。特定の順序に依存するテストは、環境や実行タイミングによって結果が変動する「flaky test」（不安定なテスト）になる可能性があります。そのため、マップのイテレーション順序に依存しないテストを書くか、あるいはこのコミットのように、非決定性を積極的に利用して多様なケースを試行するテストを書く必要があります。

### テストにおける非決定性

ソフトウェアテストにおいて、非決定的な挙動を持つコンポーネントを扱うことは課題となります。

*   **網羅性の確保**: 非決定的な挙動（例: ランダムな順序、並行処理のタイミング）を持つコードをテストする場合、単一の実行ではすべての可能なケースを網羅できない可能性があります。
*   **Flaky Test の回避**: テストが非決定的な挙動に依存していると、同じコードベース、同じテストスイートであっても、実行するたびに成功したり失敗したりする「flaky test」が発生しやすくなります。これはテストの信頼性を損ない、開発者の生産性を低下させます。
*   **ランダム性の活用**: このコミットのように、意図的にランダムな要素を導入し、それを多数回試行することで、非決定的な挙動によって引き起こされる可能性のあるバグを「揺さぶり出す」手法が有効です。これにより、特定の順序やタイミングでしか発生しないような潜在的なバグを早期に発見できます。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのマップテストにおける「異なるイテレーション順序の検出」の試行回数を増やすことにあります。

Goのマップは、内部的にハッシュテーブルとして実装されています。要素の挿入、削除、およびイテレーションの順序は、ハッシュ関数の出力、メモリレイアウト、ガベージコレクションのタイミング、さらにはGoランタイムのバージョンや実行環境によっても影響を受ける可能性があります。Goランタイムは、マップのイテレーション開始時にランダムな開始位置を選択するなど、意図的に順序を非決定的にするためのメカニズムを導入しています。

`src/runtime/map_test.go` 内のテストは、この非決定性を利用して、マップのイテレーション順序に依存するコードが誤動作しないことを確認しようとしています。テストは、まずマップを一度イテレートしてその順序（`first`）を記録します。その後、複数回マップをイテレートし、その都度、記録した `first` と異なる順序が出現するかどうかをチェックします。

従来の80回の試行では、マップの内部状態やハッシュ関数の特性によっては、常に同じ（または非常に似た）イテレーション順序しか生成されず、異なる順序が出現しない可能性がありました。これは、テストが十分に「揺さぶり」をかけられていない状態を意味します。

試行回数を800回に増やすことで、より多くの異なる内部状態やハッシュ値の組み合わせが試され、結果として異なるイテレーション順序が出現する確率が大幅に向上します。これにより、マップの順序に暗黙的に依存している可能性のあるバグが、テスト中に顕在化しやすくなります。これは、テストの網羅性と信頼性を高めるための、シンプルながらも効果的なアプローチです。

## コアとなるコードの解説

変更されたコードは、`src/runtime/map_test.go` 内の `TestMapIterationOrder` 関数（またはそれに類するテスト）の一部です。

元のコードでは、以下のコメントとループがありました。

```go
// 80 chances to get a different iteration order.
for n := 0; n < 80; n++ {
    // ... マップのイテレーションと順序の比較 ...
}
```

これは、「異なるイテレーション順序を得るために80回試行する」という意味です。ループの各イテレーションで、マップ `m` が `for i := range m` を使って走査され、その順序が `first` と呼ばれる以前に記録された順序と比較されます。もし異なる順序が見つかれば、テストは成功とみなされます（または、特定の条件が満たされたと判断されます）。

このコミットでは、この部分が以下のように変更されました。

```go
// 800 chances to get a different iteration order.
// See bug 8736 for why we need so many tries.
for n := 0; n < 800; n++ {
    // ... マップのイテレーションと順序の比較 ...
}
```

変更点は以下の通りです。

1.  **コメントの変更**: 試行回数が80回から800回に増えたことを明示しています。
2.  **バグ参照の追加**: `See bug 8736 for why we need so many tries.` というコメントが追加され、なぜこれほど多くの試行が必要になったのかが、Issue #8736に起因することが示されています。これは、80回では不十分であったという経験的な知見に基づいています。
3.  **ループ条件の変更**: `for n := 0; n < 80; n++` が `for n := 0; n < 800; n++` に変更されました。これにより、マップのイテレーションと順序の比較が10倍の回数実行されることになります。

この変更の目的は、マップのイテレーション順序が非決定論的であるというGoの特性をより厳密にテストすることです。試行回数を増やすことで、マップの内部状態がより多様なパターンを取り、その結果として異なるイテレーション順序が生成される可能性が高まります。これにより、特定のイテレーション順序に依存する潜在的なバグが、テスト中に顕在化する機会が増え、テストの信頼性と網羅性が向上します。

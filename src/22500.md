# [インデックス 22500] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における並行マークフェーズの実行方法を変更するものです。具体的には、GCの並行マークフェーズがシステムスタックではなく、通常のゴルーチン（G）スタック上で実行されるように修正されています。これにより、GC実行中のスケジューラのプリエンプション（横取り）が改善され、M（OSスレッド）とP（プロセッサ）のリソースがGCによって占有される状況が緩和されます。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作する「並行マークフェーズ」を持っています。このフェーズは、到達可能なオブジェクトをヒープ上でマークする役割を担います。

このコミット以前は、GCの並行マークフェーズがGoランタイムの「システムスタック」（`g0`スタックとも呼ばれる）上で実行されていました。システムスタックは、Goランタイムの内部的な、中断されてはならないクリティカルな操作のために使用される特別なスタックです。システムスタック上で実行されるコードは、Goスケジューラによるプリエンプション（横取り）が暗黙的に無効になります。

この特性が、並行マークフェーズの効率性に問題を引き起こしていました。並行マークフェーズがシステムスタック上で実行されると、その間、GCを実行しているM（OSスレッド）とP（プロセッサ）が完全にGCに専有されてしまい、スケジューラが他のゴルーチンに切り替えることができませんでした。これは、並行マークフェーズが本来、アプリケーションの実行と並行して進むべきであるにもかかわらず、実質的に「ストップ・ザ・ワールド」に近い状態を作り出し、アプリケーションのレイテンシに悪影響を与える可能性がありました。

コミットメッセージにあるように、「これを行う必要はなく、この方法で実行すると、スケジューラが並行マーク中であってもGCをプリエンプトできないようにすることで、GCを実行しているMとP全体を拘束してしまう」という問題意識がありました。この変更は、並行マークフェーズを通常のゴルーチンスタック上で実行することで、この問題を緩和し、将来的にGCのプリエンプションをより細かく制御できるようにするための第一歩となります。

## 前提知識の解説

### Goのガベージコレクション（GC）

GoのGCは、並行性、低レイテンシ、効率性を重視して設計されています。主な特徴は以下の通りです。

*   **三色マーキング（Tri-color Marking）**: オブジェクトを白（未訪問）、灰（訪問済みだが参照先未探索）、黒（訪問済みで参照先探索済み）の3色に分類し、到達可能なオブジェクトをマークします。
*   **並行GC（Concurrent GC）**: GCの大部分のフェーズ（特にマークフェーズ）は、アプリケーションのゴルーチンと並行して実行されます。これにより、アプリケーションの一時停止時間（Stop-The-World: STW）を最小限に抑えます。
*   **ライトバリア（Write Barrier）**: 並行マーク中にアプリケーションがポインタを書き換える際に、GCの正確性を保つために実行される小さなコードスニペットです。

GCのライフサイクルは、主に以下のフェーズで構成されます。

1.  **マーク開始（Mark Start）**: 短いSTWフェーズ。GCの準備を行い、ルートオブジェクト（グローバル変数やアクティブなゴルーチンスタック）を灰色にマークします。
2.  **並行マーク（Concurrent Mark）**: アプリケーションと並行して実行されるフェーズ。灰色オブジェクトから参照をたどり、到達可能なオブジェクトをマークしていきます。
3.  **マーク終了（Mark Termination）**: 短いSTWフェーズ。並行マークの完了を待ち、GCの最終処理を行います。
4.  **並行スイープ（Concurrent Sweep）**: アプリケーションと並行して実行されるフェーズ。マークされなかった（白い）オブジェクトが占めていたメモリを解放します。

### GoスケジューラとM-P-Gモデル

Goランタイムのスケジューラは、M（Machine）、P（Processor）、G（Goroutine）という3つの主要な抽象化を用いて、ゴルーチンをOSスレッド上で効率的に実行します。

*   **G (Goroutine)**: Goにおける軽量な実行単位。ユーザーレベルのスレッドのようなもので、独自のスタックを持ちます。Goプログラムの並行処理の基本単位です。
*   **M (Machine)**: OSスレッドを表します。Goコードを実行する実際のカーネルスレッドです。MはOSスケジューラによって管理されます。
*   **P (Processor)**: 論理プロセッサ、またはGoコードを実行するために必要なコンテキストを表します。PはMとGの間の仲介役となり、スケジューラやメモリ割り当ての状態など、ゴルーチンが実行されるために必要なリソースを提供します。通常、Pの数は論理CPUの数に設定されます（`runtime.GOMAXPROCS()`で制御可能）。

スケジューラは、PのローカルキューやグローバルキューからGを取得し、Mに割り当てて実行します。MはPと関連付けられている場合にのみGoコードを実行できます。

### スタックの種類：ゴルーチンスタック（Gスタック）とシステムスタック（g0スタック）

Goランタイムには、主に2種類のスタックが存在します。

*   **ゴルーチンスタック（Gスタック）**: 各ゴルーチンに割り当てられるスタックです。動的にサイズが変更され、必要に応じて拡大・縮小します。アプリケーションのコードは通常、このGスタック上で実行されます。GCは、到達可能なオブジェクトを特定するために、これらのGスタックをスキャンする必要があります。
*   **システムスタック（g0スタック）**: Goランタイム自体が使用する特別なスタックです。OSスレッド（M）ごとに1つ存在し、ゴルーチンスタックとは独立しています。システムスタックは、スタックの拡大・縮小、GCの特定のフェーズ、スケジューラの操作、システムコールハンドリングなど、中断されてはならないクリティカルなランタイム操作のために使用されます。システムスタック上で実行されるコードは、スケジューラによるプリエンプションの対象外となります。

### プリエンプション（Preemption）

プリエンプションとは、Goランタイムが実行中のゴルーチンを一時的に中断し、別のゴルーチンに切り替えるメカニズムです。これは、単一のゴルーチンがCPU時間を独占するのを防ぎ、公平性を確保するために不可欠です。

*   **協調的プリエンプション（Cooperative Preemption）**: 以前のGoバージョンでは、ゴルーチンが関数呼び出しなどの「セーフポイント」で自発的に実行を中断する形式が主でした。
*   **非同期プリエンプション（Asynchronous Preemption）**: Go 1.14以降で導入された機能で、関数呼び出しを含まないタイトなループ内であっても、ランタイムがゴルーチンを強制的に中断できるようになりました。これは、OSシグナルなどを利用して実現されます。

GCがゴルーチンスタックを正確にスキャンするためには、ゴルーチンがGCセーフポイントで一時停止している必要があります。プリエンプションは、GCがゴルーチンを一時停止させ、そのスタックを安全にスキャンできるようにするために重要な役割を果たします。

### `preemptoff`

`preemptoff`は、Goランタイム内でプリエンプションが無効になっている状態を指します。システムスタック上で実行されるコードは、暗黙的に`preemptoff`状態になります。これは、ランタイムのクリティカルな操作が中断されることなく完了することを保証するために重要です。`runtime.preemptoff`変数は、プリエンプションが無効になっている理由を示す文字列を格納することができ、デバッグに役立ちます。

## 技術的詳細

このコミットの技術的な核心は、GCの並行マークフェーズの実行コンテキストをシステムスタックから通常のゴルーチンスタックへ移行することです。

変更前は、`gcDrain`（並行マークの主要な処理を行う関数）の呼び出しが`systemstack`ブロック内にありました。`systemstack`は、指定された関数をシステムスタック上で実行するためのGoランタイムの内部関数です。システムスタック上で実行されるコードは、前述の通りプリエンプションの対象外となります。

このため、並行マークフェーズが実行されている間、GCを実行しているMとPは、他のゴルーチンに切り替えることができず、実質的にそのMとPはGCのために「停止」している状態でした。これは、並行GCの目的である「アプリケーションとの並行実行」を阻害し、レイテンシの増加につながる可能性がありました。

このコミットでは、`gcDrain`の呼び出しを`systemstack`ブロックの外に出すことで、並行マークフェーズが通常のゴルーチンスタック上で実行されるように変更しています。これにより、並行マークフェーズがシステムスタックに拘束されることがなくなり、スケジューラがより柔軟にMとPを管理できるようになります。

コミットメッセージには「It's still non-preemptible because we also set preemptoff around the whole GC process, but this moves us closer to making it preemptible.」とあります。これは、GCプロセス全体が`preemptoff`状態に設定されているため、この変更だけでは並行マークフェーズが完全にプリエンプト可能になるわけではないことを示しています。しかし、システムスタックからの移行は、将来的にGCのプリエンプションをより細かく制御し、GCの実行中にスケジューラがより多くのゴルーチンをプリエンプトできるようにするための重要なステップです。

具体的には、`stoptheworld`（STWフェーズを開始する関数）の呼び出しは引き続き`systemstack`内で実行されます。これは、STWが非常にクリティカルな操作であり、中断されてはならないためです。しかし、並行マークの大部分を占める`gcDrain`がGスタック上で実行されるようになったことで、GCの実行効率とスケジューラの応答性が向上する基盤が築かれました。

## コアとなるコードの解説

変更は `src/runtime/mgc.go` ファイルの `gc` 関数内で行われています。

元のコードでは、並行マークフェーズの処理（`gctimer.cycle.mark = nanotime()`から`gcw.dispose()`まで）と、それに続くマーク終了の開始（`gctimer.cycle.markterm = nanotime()`と`stoptheworld()`）が、全体として`systemstack`のクロージャ内にラップされていました。

```go
// 変更前
systemstack(func() { // このクロージャ全体がシステムスタックで実行されていた
    // Concurrent mark.
    starttheworld()
    gctimer.cycle.mark = nanotime()
    var gcw gcWork
    gcDrain(&gcw) // ここがシステムスタックで実行されていた
    gcw.dispose()

    // Begin mark termination.
    gctimer.cycle.markterm = nanotime()
    stoptheworld() // ここもシステムスタックで実行されていた
    // ...
})
```

このコミットでは、`systemstack`の適用範囲が変更されています。

```go
// 変更後
// Concurrent mark.
starttheworld()
gctimer.cycle.mark = nanotime()
var gcw gcWork
gcDrain(&gcw) // ここは通常のGスタックで実行されるようになった
gcw.dispose()

// Begin mark termination.
gctimer.cycle.markterm = nanotime()
systemstack(stoptheworld) // stoptheworldのみがシステムスタックで実行される
// ...
```

具体的には、以下の変更が行われました。

1.  **`gcDrain`の実行コンテキストの変更**:
    *   変更前は、`gcDrain(&gcw)`の呼び出しが`systemstack(func() { ... })`の内部にあり、システムスタック上で実行されていました。
    *   変更後は、`gcDrain(&gcw)`の呼び出しが`systemstack`のクロージャの外に出され、通常のゴルーチンスタック上で実行されるようになりました。これにより、並行マークフェーズの大部分がシステムスタックに拘束されなくなります。

2.  **`stoptheworld`の実行コンテキストの維持**:
    *   `stoptheworld()`の呼び出しは、引き続きシステムスタック上で実行されるように、`systemstack(stoptheworld)`という形式に変更されました。`stoptheworld`は、すべてのゴルーチンを一時停止させる非常にクリティカルな操作であり、その実行中に中断されるべきではないため、システムスタック上で実行されることが適切です。

この変更により、GCの並行マークフェーズがより「並行」に近づき、GoランタイムのスケジューラがGC実行中であっても、より効率的にゴルーチンを管理できるようになる基盤が作られました。

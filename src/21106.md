## 変更の背景

このコミットは、Go言語の初期開発段階における重要なブランチ戦略と、特定のアーキテクチャ（PowerPC 64-bit）およびガベージコレクション（GC）の進化を示しています。

当時のGo開発では、特定の大きな機能やアーキテクチャサポートのために、`dev.garbage`、`dev.power64`、`dev.cc`といった開発ブランチが並行して運用されていました。

- `dev.garbage`ブランチは、主にGoの新しいガベージコレクタ（GC）の開発と統合に焦点を当てていました。当時のGoのGCは、Stop-the-World（STW）時間が長く、パフォーマンスのボトルネックとなることがありました。このブランチは、より効率的で低レイテンシなGCの実現を目指していました。
- `dev.power64`ブランチは、PowerPC 64-bitアーキテクチャへのGoの移植と最適化を進めていました。これは、IBMのサーバーなどで利用されるPowerPCプロセッサ上でのGoの実行を可能にするための重要な取り組みでした。

このコミットは、`dev.power64`ブランチで開発されたPowerPC 64-bit関連の変更を、GCの改善が進められていた`dev.garbage`ブランチにマージするものです。これにより、`dev.garbage`ブランチはPowerPC 64-bitのサポートも含むようになり、Goの対応アーキテクチャが拡大されるとともに、GCの改善とアーキテクチャサポートが統合された形で進められることになりました。

コミットメッセージにある「Now the only difference between dev.cc and dev.garbage is the runtime conversion on the one side and the garbage collection on the other. They both have the same set of changes from default and dev.power64.」という記述は、これらの開発ブランチが最終的に`default`（メイン）ブランチに統合される前の、機能的な収束を示しています。つまり、`dev.power64`の変更がマージされたことで、`dev.garbage`と`dev.cc`は、それぞれが担当する主要な機能（GCとランタイム変換）以外の基盤部分では同等の状態になったことを意味します。

## 前提知識の解説

### Goコンパイラの歴史とアーキテクチャ（5g, 6g, 8g, 9g）

Go言語の初期のコンパイラは、Plan 9 Cコンパイラツールチェーンをベースにしていました。そのため、Goのコンパイラやリンカの実行ファイル名には、ターゲットアーキテクチャを示す数字と、Plan 9のツール名に由来する文字が使われていました。

- **5g**: ARMアーキテクチャ向けのGoコンパイラ。
- **6g**: AMD64（x86-64）アーキテクチャ向けのGoコンパイラ。Goの主要なターゲットアーキテクチャの一つ。
- **8g**: 386（x86 32-bit）アーキテクチャ向けのGoコンパイラ。
- **9g**: Plan 9アーキテクチャ向けのGoコンパイラ。しかし、実際にはGoのコンパイラツールチェーン全体を指す総称としても使われることがありました。このコミットでは、`src/cmd/9g`以下のファイルが多数変更されており、これはGoコンパイラのバックエンド、特にレジスタ割り当てやコード生成に関する広範な変更が、特定のアーキテクチャに限定されずに行われた可能性を示唆しています。

これらのコンパイラは、それぞれ異なるアーキテクチャのコード生成を担当し、Goのクロスコンパイル能力の基盤となっていました。

### Goランタイムとガベージコレクション（GC）

Goは自動メモリ管理（ガベージコレクション）を採用しています。初期のGoのGCは、プログラムの実行を一時停止させて（Stop-the-World: STW）ガベージコレクションを実行する方式でした。これは、GC中にアプリケーションが応答しなくなる「ポーズ時間」が長くなるという問題がありました。

このコミットの時期（2014年）は、GoのGCが大きな進化を遂げようとしていた時期にあたります。特に、Go 1.5（2015年リリース）で導入された新しいGCは、並行（Concurrent）かつインクリメンタルなGCであり、STWポーズ時間を大幅に短縮することを目標としていました。

- **ConcurrentSweep**: ガベージコレクションの「スイープ（Sweep）」フェーズを、アプリケーションの実行と並行して行うことを指します。スイープフェーズでは、マークされたオブジェクト以外のメモリを解放し、フリーリストに戻す作業が行われます。`src/runtime/mgc0.c`で`ConcurrentSweep`が`1`に設定されているのは、この並行スイープ機能が有効化されたことを示しており、GCのポーズ時間削減に向けた重要な一歩です。

### PowerPC 64-bitアーキテクチャ

PowerPCは、IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。特にサーバーや組み込みシステムで広く利用されていました。PowerPC 64-bitは、64ビットのレジスタとアドレス空間を持つバージョンで、より大規模なメモリと高性能な計算能力を提供します。Goがこのアーキテクチャをサポートすることは、Goアプリケーションの適用範囲を広げる上で重要でした。

### Goの開発ブランチ戦略

Goプロジェクトでは、大規模な機能開発やアーキテクチャサポートの追加のために、一時的な開発ブランチが作成されることがありました。これらのブランチは、メインの`default`ブランチに影響を与えることなく、特定の機能の実験、開発、テストを行うために使用されました。開発が安定し、機能が完成すると、これらのブランチは`default`ブランチにマージされるか、他の開発ブランチに統合されました。

- `dev.garbage`: 新しいGCの開発。
- `dev.power64`: PowerPC 64-bitサポートの開発。
- `dev.cc`: おそらく、C言語との連携やCgo関連のランタイム変換に焦点を当てたブランチ。

これらのブランチが互いにマージされることで、異なる開発ストリームの成果が統合され、最終的にGoのメインラインに組み込まれていきました。

このマージは、PowerPC 64-bitアーキテクチャのサポートが、新しいガベージコレクタの開発ブランチである`dev.garbage`に取り込まれたことを意味します。これにより、`dev.garbage`ブランチは、GCの改善と同時に、PowerPC 64-bit環境でのGoの動作を保証する責任を負うことになります。これは、Goがより多くのプラットフォームで利用可能になるための重要なステップであり、GCの改善が特定のアーキテクチャに依存しない汎用的なものであることを示唆しています。

### `ConcurrentSweep`が`1`になったことのGCへの影響

`src/runtime/mgc0.c`における`ConcurrentSweep = 1`への変更は、Goのガベージコレクタが、マークフェーズの後に続くスイープフェーズを、アプリケーションの実行と並行して行うようになったことを意味します。

従来のGCでは、スイープフェーズもSTWポーズの一部として実行されることがあり、これがポーズ時間の原因となっていました。並行スイープの導入により、GCがメモリを解放し、フリーリストに戻す作業をバックグラウンドで実行できるようになり、アプリケーションの応答性が向上します。これは、Go 1.5で導入された新しいGCの重要な要素の一つであり、このコミットはその準備段階または初期実装の一部であると考えられます。

### `src/cmd/9g/reg.c`におけるレジスタ割り当ての変更の重要性

`src/cmd/9g/reg.c`は、Goコンパイラのバックエンドにおけるレジスタ割り当てを担当するファイルです。このファイルが1200行以上の追加と多数の削除を伴う大規模な変更を受けていることは、レジスタ割り当てロジックに根本的な見直しがあったことを示唆しています。

レジスタ割り当ては、コンパイラの最適化において非常に重要な部分です。効率的なレジスタ割り当ては、生成される機械語コードのパフォーマンスに直接影響します。レジスタはCPUが最も高速にアクセスできる記憶領域であるため、変数を適切にレジスタに割り当てることで、メモリへのアクセス回数を減らし、プログラムの実行速度を向上させることができます。

この変更は、PowerPC 64-bitアーキテクチャの特性を考慮したレジスタ割り当ての改善、または新しいGCの導入に伴うランタイムの変更に対応するための汎用的なレジスタ割り当ての最適化である可能性があります。特に、PowerPC 64-bitは多くの汎用レジスタを持つため、その特性を最大限に活かすための調整が行われたと考えられます。

### `include/link.h`と`src/runtime/asm_power64x.s`の変更がPowerPC 64-bitアーキテクチャサポートにどう寄与するか

- `include/link.h`: このファイルは、Goのリンカが使用するデータ構造や定数を定義しています。変更点を見ると、`Prog`構造体（プログラム命令を表す）にPowerPC 64-bit特有のオペランド（`from3`）やレジスタの扱いに関するコメントが追加・修正されています。これは、リンカがPowerPC 64-bitの特定の命令形式やレジスタの使用法を正しく解釈し、リンクできるようにするための調整です。
- `src/runtime/asm_power64x.s`: このファイルは、PowerPC 64-bitアーキテクチャ向けのGoランタイムのアセンブリコードを含んでいます。変更点には、`runtime·casp`が`runtime·casp1`にリネームされたり、`xadd`関数のコメントが修正されたりしています。これらの変更は、PowerPC 64-bit上でのアトミック操作やその他の低レベルランタイム機能の正確性と効率性を向上させるためのものです。アセンブリコードレベルでの変更は、特定のアーキテクチャの命令セットを直接利用して、パフォーマンスを最大化するために行われます。

これらの変更は、GoがPowerPC 64-bit上で安定して、かつ高性能に動作するための基盤を固めるものです。

## コアとなるコードの解説

### `src/cmd/9g/reg.c`の変更

このファイルは、Goコンパイラが中間表現から最終的な機械語コードを生成する際に、どの変数をどのCPUレジスタに割り当てるかを決定するアルゴリズムを実装しています。レジスタ割り当ては、プログラムの実行速度に大きく影響するため、非常に複雑で重要な最適化ステップです。

1200行を超える変更は、既存のレジスタ割り当てアルゴリズムの抜本的な改善、またはPowerPC 64-bitのような新しいアーキテクチャの特性（レジスタの数、種類、使用規則など）をより効果的に利用するための適応を示唆しています。例えば、より高度なグラフ彩色アルゴリズムの導入や、特定の命令パターンに対するレジスタの最適化などが考えられます。これにより、生成されるGoプログラムの実行効率が向上します。

### `src/runtime/mgc0.c`の変更

- `ConcurrentSweep = 0`: スイープフェーズが並行して実行されないことを意味します。通常、これはGCポーズ中にスイープも行われることを意味し、ポーズ時間が長くなる可能性があります。

この変更は、Goのガベージコレクタが、より現代的で高性能な並行GCへと進化する過程における、非常に重要なマイルストーンの一つです。

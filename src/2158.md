# [インデックス 2158] ファイルの概要

このコミットは、Go言語の初期のコンパイラである`6g`におけるエラーメッセージの改善を目的としています。特に、関数呼び出し時の引数の不一致、戻り値の不一致、代入時の要素数不一致といった「形状エラー（shape error）」に対して、より詳細で分かりやすい情報を提供するように変更が加えられています。また、型変換の失敗後に型情報が失われることで、その後のエラー報告が不正確になる問題を修正し、エラーの連鎖における診断能力を向上させています。

## 変更の背景

Go言語は、その設計思想として、コンパイル時に多くの問題を捕捉し、開発者に早期にフィードバックを提供することを重視しています。しかし、初期のコンパイラ（`6g`など）では、特定のエラーシナリオにおいて、生成されるエラーメッセージが抽象的であったり、必要な情報が不足していたりすることがありました。

特に、「`shape error across CALL`」のような一般的なエラーメッセージは、具体的な問題点（例：引数の数、型、戻り値の数など）を特定するのに十分な情報を提供していませんでした。これにより、開発者はエラーの原因を特定するために、より多くの時間と労力を費やす必要がありました。

また、型変換の失敗が発生した場合に、コンパイラがその後の処理で関連する型情報を破棄してしまう問題も存在しました。これにより、最初の型変換エラーに続いて発生するエラーが、不正確な型情報に基づいて報告され、デバッグをさらに困難にしていました。

このコミットは、これらの課題に対処し、コンパイラのエラーメッセージをより具体的で、診断に役立つものにすることで、開発者の生産性向上とデバッグ体験の改善を目指しています。

## 前提知識の解説

### Goコンパイラ (6g)

`6g`は、Go言語の初期のコンパイラの一つで、特に64ビットシステム向けに設計されていました。Go言語が公開された2009年当初、Goのツールチェインは`6g`（64ビット）、`8g`（32ビット）、`5g`（ARM）といった、ターゲットアーキテクチャごとに異なるコンパイラで構成されていました。これらのコンパイラはC言語で書かれており、Go言語の進化とともに、最終的にはGo 1.5で単一の`go tool compile`コマンドに統合されました。このコミットは、Go言語がまだ初期段階にあり、コンパイラの機能とユーザーエクスペリエンスが活発に改善されていた時期のものです。

### コンパイラのエラー報告

コンパイラは、ソースコードの構文的・意味的な誤りを検出し、開発者に報告する役割を担います。エラーメッセージの質は、開発者が問題を迅速に理解し、修正するために非常に重要です。良いエラーメッセージは、問題の種類、発生箇所、そして可能であれば修正のヒントを提供します。

### 型システムと型チェック

Go言語は静的型付け言語であり、コンパイル時に厳格な型チェックが行われます。これにより、多くの型関連のエラーが実行時ではなく、開発の早期段階で検出されます。型チェックは、関数呼び出しの引数とパラメータの型の一致、代入の両辺の型の一致、演算子のオペランドの型など、様々な文脈で行われます。

### `CALL`、`RETURN`、`ASSIGNMENT`における「形状エラー」

*   **`CALL` (関数呼び出し)**: 関数を呼び出す際、渡される引数の数や型が、関数の定義で期待されるパラメータの数や型と一致しない場合にエラーが発生します。
*   **`RETURN` (戻り値)**: 関数が値を返す際、`return`ステートメントで指定された戻り値の数や型が、関数の定義で宣言された戻り値の数や型と一致しない場合にエラーが発生します。
*   **`ASSIGNMENT` (代入)**: 変数に値を代入する際、代入される値の数や型が、変数宣言で期待される数や型と一致しない場合にエラーが発生します。特に、複数の戻り値を持つ関数からの代入や、複数の変数への同時代入で発生しやすいです。

これらのエラーは、コードの「形状（shape）」、つまり構造的な整合性に関わるため、「形状エラー」と呼ばれていました。

### `nil`定数と型変換

Go言語の`nil`は、ポインタ、スライス、マップ、チャネル、インターフェース、関数といった特定の型のゼロ値を表す事前宣言された識別子です。`nil`は型を持たない定数であり、特定の型に変換されることでその型のゼロ値となります。しかし、`nil`を文字列型のような、`nil`が有効なゼロ値ではない型に変換しようとすると、コンパイルエラーとなります。このコミット以前は、このような変換失敗時に型情報が失われ、その後のエラーメッセージが不明瞭になる問題がありました。

## 技術的詳細

このコミットの主要な技術的変更点は以下の2つです。

1.  **エラーメッセージの具体化と詳細化**:
    従来の「`shape error across CALL`」のような一般的なメッセージを、より具体的な問題を示すメッセージに置き換えています。
    *   引数不足の場合: 「`not enough arguments to CALL`」
    *   代入数不一致の場合: 「`assignment count mismatch: 3 = 2`」
    *   戻り値過多の場合: 「`too many arguments to RETURN`」
    これらのメッセージには、期待される引数/戻り値の型や、実際に与えられた引数/戻り値の型が追加で表示されるようになり、開発者がコードのどの部分が問題であるかを一目で理解できるようになりました。これは、`src/cmd/gc/walk.c`内のエラー報告ロジック、特に`ascompatte`関数周辺の変更によって実現されています。

2.  **型変換失敗後の型情報の保持**:
    `nil`定数から無効な型への変換（例: `nil`から`string`への変換）が失敗した場合、以前は変換対象のノードの型がリセットされていました。このコミットでは、`src/cmd/gc/const.c`において、型変換失敗後もノードの型をそのまま保持するように変更されています。これにより、同じコード行で発生する後続のエラー（例: `nil`を`string`に変換しようとした後の比較演算子エラー）が、より正確な型情報に基づいて報告されるようになります。コミットメッセージの例では、「`illegal types for operand: EQ`」の後に、以前は空白だった`nil`の型情報が表示されるようになっています。

これらの変更は、コンパイラがエラーを検出した際に、そのエラーの根本原因と関連する型情報をより正確に保持し、開発者に提示することで、デバッグの効率を大幅に向上させることを目的としています。

## コアとなるコードの変更箇所

このコミットは主に以下の3つのファイルに影響を与えています。

1.  **`src/cmd/gc/const.c`**:
    *   `bad:`ラベルの直下、`yyerror`呼び出しの後にあった`n->type = T;`の行が削除されました。
        *   **変更前**:
            ```c
            yyerror("cannot convert %T constant to %T", n->type, t);
            n->type = T; // この行が削除された
            n->diag = 1;
            return;
            ```
        *   **変更後**:
            ```c
            yyerror("cannot convert %T constant to %T", n->type, t);
            n->diag = 1;
            return;
            ```
    この変更により、定数変換が失敗した場合でも、ノードの型情報がリセットされずに保持されるようになります。

2.  **`src/cmd/gc/walk.c`**:
    このファイルには、エラーメッセージの改善と型情報の表示に関する多くの変更が加えられています。
    *   `ascompatet`関数内で、代入数不一致のエラーメッセージが「`assignment count mismatch: %d = %d`」に変更されました。
    *   新しいヘルパー関数`dumptypes`と`dumpnodetypes`が追加されました。これらの関数は、エラーメッセージに含めるために、型リストやノードの型リストを整形して出力する役割を担います。
        *   `dumptypes(Type **nl, char *what)`: 期待される型リストを表示します。
        *   `dumpnodetypes(Node **nr, char *what)`: 与えられたノードの型リストを表示します。
    *   `ascompatte`関数内で、関数呼び出しや戻り値に関するエラーメッセージが大幅に改善されました。
        *   「`not enough arguments to %O`」または「`too many arguments to %O`」という具体的なメッセージが使用されるようになりました。
        *   これらのメッセージの後に、`dumptypes`と`dumpnodetypes`を使用して、期待される引数/戻り値と実際に与えられた引数/戻り値の型が詳細に表示されるようになりました。

3.  **`test/golden.out`**:
    このファイルは、コンパイラのテストスイートの出力の「ゴールデンファイル」であり、期待されるエラーメッセージの形式を定義しています。このコミットにより、新しい、より詳細なエラーメッセージが反映されるように更新されました。
    *   `fixedbugs/bug049.go`と`fixedbugs/bug062.go`のエントリに、`nil`定数変換失敗後の`illegal types for operand`エラーにおいて、`nil`の型情報が追加で表示されるようになったことが示されています。
    *   `fixedbugs/bug131.go`のエントリにも同様に、型情報が追加されています。

## コアとなるコードの解説

### `src/cmd/gc/const.c`の変更

`const.c`における`n->type = T;`の削除は、型変換エラー発生時のコンパイラの挙動を根本的に変更します。以前は、定数変換が失敗すると、そのノードの型が汎用的な`T`（おそらく不明な型を示す）にリセットされていました。これにより、同じ式内で後続の型チェックが行われる際に、誤った型情報に基づいてエラーが報告される可能性がありました。例えば、`nil`を`string`に変換しようとして失敗した後、その結果を比較演算子（`EQ`）のオペランドとして使用した場合、以前は`nil`の型情報が失われていたため、`illegal types for operand`エラーの際に`nil`の型が表示されませんでした。この変更により、変換が失敗しても元の型情報が保持されるため、後続のエラーメッセージがより正確になり、デバッグが容易になります。

### `src/cmd/gc/walk.c`の変更

`walk.c`は、Goコンパイラのセマンティック分析とコード生成の前処理を行う「ウォーカー」の役割を担うファイルです。このファイルにおける変更は、主にコンパイラが型チェックを行う際のロジックとエラー報告のメカニズムに焦点を当てています。

*   **`dumptypes`と`dumpnodetypes`の導入**: これらのヘルパー関数は、エラーメッセージに含めるために、型リスト（`Type **nl`）やノードの型リスト（`Node **nr`）を整形して標準出力（コンパイラの内部ログ）に出力します。これにより、エラーメッセージに「期待される型」と「与えられた型」を具体的に表示することが可能になりました。例えば、`x.go:7: not enough arguments to CALL`の後に、`a int, b int`（期待される引数）と`int`（与えられた引数）が表示されるのは、これらの関数が利用されているためです。

*   **`ascompatte`関数の改善**: `ascompatte`は、代入や関数呼び出しの引数/戻り値の互換性をチェックする重要な関数です。この関数内で、引数や戻り値の数が一致しない場合に、より具体的なエラーメッセージを生成するようにロジックが変更されました。以前は単に「`error in shape across %O`」と報告されていたものが、`if(l != T)`（期待される型リストが空でない）または`if(r != N)`（与えられたノードリストが空でない）の条件に基づいて、「`not enough arguments`」または「`too many arguments`」というメッセージに分岐するようになりました。さらに、`dumptypes`と`dumpnodetypes`を呼び出すことで、具体的な型情報がエラーメッセージに付加されるようになり、開発者はエラーの原因をより迅速に特定できるようになりました。

これらの変更は、コンパイラが検出したエラーを単に報告するだけでなく、そのエラーがなぜ発生したのか、どのような型が期待され、どのような型が与えられたのかという詳細なコンテキストを提供することで、開発者のデバッグ体験を大幅に改善するものです。

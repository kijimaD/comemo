# [インデックス 22858] ファイルの概要

## 変更の背景

Go言語は、その強力な並行処理機能とシンプルな構文により、多くのアプリケーション開発で利用されています。しかし、既存のC/C++コードベースとの連携が必要な場合、Goのコードをライブラリとして提供し、C/C++アプリケーションから呼び出す機能が求められます。

Go 1.5より前のバージョンでは、GoのコードをC言語から呼び出すための公式なサポートは限定的でした。特に、静的ライブラリ (`.a` ファイル) としてGoのコードをビルドし、それをC/C++プロジェクトに組み込む機能は、特定のプラットフォーム（特にmacOS）で不足していました。

このコミットの主な目的は、macOS (Darwin) 環境において、GoのコードをC言語の静的ライブラリとしてビルドする `c-archive` ビルドモードをサポートすることです。これにより、Goのランタイムとユーザーコードが単一の静的アーカイブファイルにまとめられ、C/C++アプリケーションがGoの関数を直接呼び出せるようになります。これは、既存のC/C++プロジェクトにGoの機能を段階的に導入したり、Goで記述された高性能なコンポーネントをC/C++アプリケーションに組み込んだりする際に非常に有用です。

この機能が追加されることで、GoとC/C++の相互運用性が向上し、開発者は両言語の強みを活かしたハイブリッドアプリケーションをより容易に構築できるようになります。

## 前提知識の解説

このコミットの理解を深めるために、以下の概念について解説します。

### Goのビルドモード (`go build -buildmode`)

`go build` コマンドには、生成されるバイナリの種類を制御するための `-buildmode` フラグがあります。主要なビルドモードには以下のようなものがあります。

*   **`exe` (デフォルト)**: 実行可能ファイルを生成します。
*   **`c-archive`**: GoパッケージとGoランタイムをCアーカイブ（静的ライブラリ、`.a` ファイル）としてコンパイルします。このアーカイブは、C/C++プログラムにリンクできます。Goの関数はCの関数としてエクスポートされ、C/C++コードから呼び出すことができます。
*   **`c-shared`**: GoパッケージとGoランタイムをC共有ライブラリ（ダイナミックライブラリ、macOSでは`.dylib`、Linuxでは`.so`）としてコンパイルします。これもC/C++プログラムにリンクできます。
*   **`shared`**: 複数のGoプログラム間で共有可能なGo共有ライブラリをコンパイルします。これはGoプログラム間でのみ使用され、C/C++プログラムからは直接利用できません。

このコミットは、特に `c-archive` モードに焦点を当てています。

### 静的ライブラリ (`.a` ファイル) と `ar` コマンド

静的ライブラリは、コンパイル時に実行可能ファイルに直接組み込まれるコードの集合です。通常、Unix系システムでは `.a` (archive) 拡張子を持ちます。静的ライブラリを使用すると、実行可能ファイルは自己完結型となり、外部の共有ライブラリに依存しません。

`ar` (archiver) コマンドは、複数のファイルを単一のアーカイブファイルにまとめるために使用されるユーティリティです。リンカは、静的ライブラリから必要なオブジェクトファイル（コンパイルされたコード）を抽出し、最終的な実行可能ファイルに結合します。

### ダイナミックライブラリ (`.so`, `.dylib`)

ダイナミックライブラリ（共有ライブラリ）は、実行時にアプリケーションによってロードされるコードの集合です。Linuxでは `.so` (shared object)、macOSでは `.dylib` (dynamic library) 拡張子を持ちます。複数のアプリケーションが同じ共有ライブラリを共有できるため、ディスクスペースとメモリを節約できます。

### Cgo

Cgoは、GoプログラムがCコードを呼び出したり、CコードからGoコードを呼び出したりするためのGoの機能です。`import "C"` をGoファイルに記述することでCgoが有効になり、Cの関数や型をGoから利用したり、Goの関数をCから呼び出せるようにエクスポートしたりできます。Goの関数をCから呼び出すには、`//export FuncName` ディレクティブを使用します。

### `_rt0_goos_goarch_lib` と初期化処理

Goのプログラムが起動する際には、ランタイムの初期化処理が実行されます。これは、ガベージコレクタの初期化、スケジューラの起動、`init` 関数の実行などを含みます。通常の実行可能ファイルでは、エントリポイントからこれらの処理が開始されます。

ライブラリとしてビルドされる場合、Goランタイムの初期化は、ライブラリがロードされたとき、またはライブラリ内の関数が最初に呼び出されたときに適切に行われる必要があります。`_rt0_goos_goarch_lib` のようなシンボルは、ライブラリのエントリポイントまたは初期化ルーチンを指すことが多く、リンカがこの初期化処理を適切に配置するために使用されます。

`.init_array` セクションは、ELF (Executable and Linkable Format) 形式のバイナリ（Linuxなどで使用）において、プログラムの起動時に実行される初期化関数のポインタの配列を格納するために使用されます。ライブラリがロードされると、このセクションに登録された関数が自動的に実行されます。

### 外部リンキング (`LinkExternal`)

Goのリンカは、Goのコードをリンクする際に、Go独自のリンカを使用することも、システムのリンカ（`gcc`など）を使用することもできます。`LinkExternal` は、Goのリンカがオブジェクトファイルを生成し、最終的なリンクステップをシステムのリンカに委ねるモードを指します。C/C++コードとGoコードを組み合わせる場合、システムのリンカを使用することが一般的です。

## 技術的詳細

このコミットは、Goのリンカ (`cmd/internal/ld`) に `c-archive` ビルドモードのサポートを追加するために、複数のファイルにわたる変更を導入しています。

### `src/cmd/internal/ld/lib.go` の変更

*   **`BuildMode` 型の拡張**: `BuildmodeCArchive` という新しい定数が `BuildMode` 型に追加されました。これにより、リンカが `c-archive` モードを認識できるようになります。
    ```go
    const (
        BuildmodeExe BuildMode = iota
        BuildmodeCArchive // 新規追加
        BuildmodeCShared
        BuildmodeShared
    )
    ```
*   **`Set` メソッドの更新**: `BuildMode` の `Set` メソッドが更新され、コマンドライン引数 `-buildmode=c-archive` を解析できるようになりました。この際、`c-archive` モードは `darwin` (macOS) 環境でのみサポートされるように制約が追加されています。他のOS/アーキテクチャで `c-archive` を指定するとエラーになります。
    ```go
    case "c-archive":
        if goos != "darwin" {
            return badmode() // darwin以外ではエラー
        }
        *mode = BuildmodeCArchive
    ```
*   **`String` メソッドの更新**: `BuildmodeCArchive` の文字列表現が追加されました。
*   **`libinit` 関数の更新**: ライブラリの初期化エントリポイント (`INITENTRY`) の決定ロジックが更新され、`BuildmodeCArchive` も `BuildmodeCShared` と同様に `_rt0_goos_goarch_lib` 形式のエントリポイントを使用するように変更されました。
*   **`loadlib` 関数の更新**: `runtime.isarchive` シンボルが導入され、`BuildmodeCArchive` の場合にこのシンボルに1を書き込むことで、Goランタイムが自身がアーカイブとしてビルドされていることを認識できるようにしました。これは `runtime.islibrary` と同様の目的です。
*   **`hostobjCopy` 関数の追加**: この新しい関数は、リンカが生成したホストオブジェクトファイル（Goのコードから生成されたオブジェクトファイル）を一時ディレクトリにコピーする役割を担います。これは、`ar` コマンドがこれらのオブジェクトファイルをアーカイブにまとめるために必要です。
*   **`archive` 関数の追加**: この関数は `BuildmodeCArchive` の場合にのみ実行され、`ar` コマンドを呼び出して、`hostobjCopy` でコピーされたオブジェクトファイルとGoランタイムのオブジェクトファイル (`go.o`) を結合し、最終的な静的ライブラリ (`.a` ファイル) を生成します。
    ```go
    func archive() {
        if Buildmode != BuildmodeCArchive {
            return
        }
        // ...
        argv := []string{"ar", "-q", "-c", outfile}
        argv = append(argv, hostobjCopy()...)
        argv = append(argv, fmt.Sprintf("%s/go.o", tmpdir))
        // ... exec.Command(argv[0], argv[1:]...).CombinedOutput()
    }
    ```
*   **`hostlink` 関数の変更**: `hostlink` 関数は、外部リンカ (`gcc` など) を呼び出して最終的な実行可能ファイルや共有ライブラリを生成する役割を担います。`BuildmodeCArchive` の場合、最終的なリンクは `ar` コマンドによって行われるため、`hostlink` は早期にリターンするように変更されました。また、`hostobjCopy()` の呼び出しが共通化され、コードの重複が削減されました。

### `src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`, `src/cmd/internal/ld/go.go` の変更

これらのファイルでは、主に `BuildmodeCShared` をチェックしていた箇所に `BuildmodeCArchive` が追加され、両方のビルドモードで同様のリンカ処理（例: `.init_array` セクションの処理、`main` 関数のシンボル処理）が適用されるように変更されました。

*   **`dosymtype` (data.go)**: `.init_array` セクションにライブラリ初期化関数 (`INITENTRY`) を追加するロジックが、`BuildmodeCShared` に加えて `BuildmodeCArchive` でも適用されるようになりました。
*   **`dodata` (data.go)**: `.init_array` セクションの作成ロジックが、`BuildmodeCShared` に加えて `BuildmodeCArchive` および `BuildmodeShared` でも適用されるようになりました。
*   **`doelf` (elf.go)**: ELFバイナリの `.init_array` セクションの処理が、`BuildmodeCShared` に加えて `BuildmodeCArchive` および `BuildmodeShared` でも適用されるようになりました。
*   **`loadcgo` (go.go)**: Cgo関連の処理で、`BuildmodeCShared` に加えて `BuildmodeCArchive` でも `main` 関数のシンボルがスキップされるようになりました。これは、ライブラリとしてビルドされる場合に `main` 関数がエクスポートされる必要がないためです。
*   **`deadcode` (go.go)**: `BuildmodeShared` に加えて `BuildmodeCArchive` でも、すべてのシンボルが到達可能としてマークされるようになりました。これは、ライブラリとしてビルドされる場合、外部から呼び出される可能性のあるすべての関数が保持される必要があるためです。

### `src/cmd/internal/ld/pobj.go` の変更

*   **`Ldmain` 関数の更新**: リンカのメインエントリポイントである `Ldmain` 関数に、新しく追加された `archive()` 関数の呼び出しが追加されました。これにより、`c-archive` ビルドモードの場合に静的ライブラリの生成処理が実行されるようになります。

これらの変更により、Goのリンカは `c-archive` ビルドモードを適切に処理し、GoのコードをmacOS上でC言語の静的ライブラリとして出力できるようになりました。特に、`ar` コマンドを直接呼び出すことで、標準的な静的ライブラリの生成プロセスにGoのビルドシステムが統合されています。

## 変更の背景

Go言語は、その強力な並行処理機能とシンプルな構文により、多くのアプリケーション開発で利用されています。しかし、既存のC/C++コードベースとの連携が必要な場合、Goのコードをライブラリとして提供し、C/C++アプリケーションから呼び出す機能が求められます。

Go 1.5より前のバージョンでは、GoのコードをC言語から呼び出すための公式なサポートは限定的でした。特に、静的ライブラリ (`.a` ファイル) としてGoのコードをビルドし、それをC/C++プロジェクトに組み込む機能は、特定のプラットフォーム（特にmacOS）で不足していました。

このコミットの主な目的は、macOS (Darwin) 環境において、GoのコードをC言語の静的ライブラリとしてビルドする `c-archive` ビルドモードをサポートすることです。これにより、Goのランタイムとユーザーコードが単一の静的アーカイブファイルにまとめられ、C/C++アプリケーションがGoの関数を直接呼び出せるようになります。これは、既存のC/C++プロジェクトにGoの機能を段階的に導入したり、Goで記述された高性能なコンポーネントをC/C++アプリケーションに組み込んだりする際に非常に有用です。

この機能が追加されることで、GoとC/C++の相互運用性が向上し、開発者は両言語の強みを活かしたハイブリッドアプリケーションをより容易に構築できるようになります。

## 前提知識の解説

このコミットの理解を深めるために、以下の概念について解説します。

### Goのビルドモード (`go build -buildmode`)

`go build` コマンドには、生成されるバイナリの種類を制御するための `-buildmode` フラグがあります。主要なビルドモードには以下のようなものがあります。

*   **`exe` (デフォルト)**: 実行可能ファイルを生成します。
*   **`c-archive`**: GoパッケージとGoランタイムをCアーカイブ（静的ライブラリ、`.a` ファイル）としてコンパイルします。このアーカイブは、C/C++プログラムにリンクできます。Goの関数はCの関数としてエクスポートされ、C/C++コードから呼び出すことができます。
*   **`c-shared`**: GoパッケージとGoランタイムをC共有ライブラリ（ダイナミックライブラリ、macOSでは`.dylib`、Linuxでは`.so`）としてコンパイルします。これもC/C++プログラムにリンクできます。
*   **`shared`**: 複数のGoプログラム間で共有可能なGo共有ライブラリをコンパイルします。これはGoプログラム間でのみ使用され、C/C++プログラムからは直接利用できません。

このコミットは、特に `c-archive` モードに焦点を当てています。

### 静的ライブラリ (`.a` ファイル) と `ar` コマンド

静的ライブラリは、コンパイル時に実行可能ファイルに直接組み込まれるコードの集合です。通常、Unix系システムでは `.a` (archive) 拡張子を持ちます。静的ライブラリを使用すると、実行可能ファイルは自己完結型となり、外部の共有ライブラリに依存しません。

`ar` (archiver) コマンドは、複数のファイルを単一のアーカイブファイルにまとめるために使用されるユーティリティです。リンカは、静的ライブラリから必要なオブジェクトファイル（コンパイルされたコード）を抽出し、最終的な実行可能ファイルに結合します。

### ダイナミックライブラリ (`.so`, `.dylib`)

ダイナミックライブラリ（共有ライブラリ）は、実行時にアプリケーションによってロードされるコードの集合です。Linuxでは `.so` (shared object)、macOSでは `.dylib` (dynamic library) 拡張子を持ちます。複数のアプリケーションが同じ共有ライブラリを共有できるため、ディスクスペースとメモリを節約できます。

### Cgo

Cgoは、GoプログラムがCコードを呼び出したり、CコードからGoコードを呼び出したりするためのGoの機能です。`import "C"` をGoファイルに記述することでCgoが有効になり、Cの関数や型をGoから利用したり、Goの関数をCから呼び出せるようにエクスポートしたりできます。Goの関数をCから呼び出すには、`//export FuncName` ディレクティブを使用します。

### `_rt0_goos_goarch_lib` と初期化処理

Goのプログラムが起動する際には、ランタイムの初期化処理が実行されます。これは、ガベージコレクタの初期化、スケジューラの起動、`init` 関数の実行などを含みます。通常の実行可能ファイルでは、エントリポイントからこれらの処理が開始されます。

ライブラリとしてビルドされる場合、Goランタイムの初期化は、ライブラリがロードされたとき、またはライブラリ内の関数が最初に呼び出されたときに適切に行われる必要があります。`_rt0_goos_goarch_lib` のようなシンボルは、ライブラリのエントリポイントまたは初期化ルーチンを指すことが多く、リンカがこの初期化処理を適切に配置するために使用されます。

`.init_array` セクションは、ELF (Executable and Linkable Format) 形式のバイナリ（Linuxなどで使用）において、プログラムの起動時に実行される初期化関数のポインタの配列を格納するために使用されます。ライブラリがロードされると、このセクションに登録された関数が自動的に実行されます。

### 外部リンキング (`LinkExternal`)

Goのリンカは、Goのコードをリンクする際に、Go独自のリンカを使用することも、システムのリンカ（`gcc`など）を使用することもできます。`LinkExternal` は、Goのリンカがオブジェクトファイルを生成し、最終的なリンクステップをシステムのリンカに委ねるモードを指します。C/C++コードとGoコードを組み合わせる場合、システムのリンカを使用することが一般的です。

## 技術的詳細

このコミットは、Goのリンカ (`cmd/internal/ld`) に `c-archive` ビルドモードのサポートを追加するために、複数のファイルにわたる変更を導入しています。

### `src/cmd/internal/ld/lib.go` の変更

*   **`BuildMode` 型の拡張**: `BuildmodeCArchive` という新しい定数が `BuildMode` 型に追加されました。これにより、リンカが `c-archive` モードを認識できるようになります。
    ```go
    const (
        BuildmodeExe BuildMode = iota
        BuildmodeCArchive // 新規追加
        BuildmodeCShared
        BuildmodeShared
    )
    ```
*   **`Set` メソッドの更新**: `BuildMode` の `Set` メソッドが更新され、コマンドライン引数 `-buildmode=c-archive` を解析できるようになりました。この際、`c-archive` モードは `darwin` (macOS) 環境でのみサポートされるように制約が追加されています。他のOS/アーキテクチャで `c-archive` を指定するとエラーになります。
    ```go
    case "c-archive":
        if goos != "darwin" {
            return badmode() // darwin以外ではエラー
        }
        *mode = BuildmodeCArchive
    ```
*   **`String` メソッドの更新**: `BuildmodeCArchive` の文字列表現が追加されました。
*   **`libinit` 関数の更新**: ライブラリの初期化エントリポイント (`INITENTRY`) の決定ロジックが更新され、`BuildmodeCArchive` も `BuildmodeCShared` と同様に `_rt0_goos_goarch_lib` 形式のエントリポイントを使用するように変更されました。
*   **`loadlib` 関数の更新**: `runtime.isarchive` シンボルが導入され、`BuildmodeCArchive` の場合にこのシンボルに1を書き込むことで、Goランタイムが自身がアーカイブとしてビルドされていることを認識できるようにしました。これは `runtime.islibrary` と同様の目的です。
*   **`hostobjCopy` 関数の追加**: この新しい関数は、リンカが生成したホストオブジェクトファイル（Goのコードから生成されたオブジェクトファイル）を一時ディレクトリにコピーする役割を担います。これは、`ar` コマンドがこれらのオブジェクトファイルをアーカイブにまとめるために必要です。
*   **`archive` 関数の追加**: この関数は `BuildmodeCArchive` の場合にのみ実行され、`ar` コマンドを呼び出して、`hostobjCopy` でコピーされたオブジェクトファイルとGoランタイムのオブジェクトファイル (`go.o`) を結合し、最終的な静的ライブラリ (`.a` ファイル) を生成します。
    ```go
    func archive() {
        if Buildmode != BuildmodeCArchive {
            return
        }
        // ...
        argv := []string{"ar", "-q", "-c", outfile}
        argv = append(argv, hostobjCopy()...)
        argv = append(argv, fmt.Sprintf("%s/go.o", tmpdir))
        // ... exec.Command(argv[0], argv[1:]...).CombinedOutput()
    }
    ```
*   **`hostlink` 関数の変更**: `hostlink` 関数は、外部リンカ (`gcc` など) を呼び出して最終的な実行可能ファイルや共有ライブラリを生成する役割を担います。`BuildmodeCArchive` の場合、最終的なリンクは `ar` コマンドによって行われるため、`hostlink` は早期にリターンするように変更されました。また、`hostobjCopy()` の呼び出しが共通化され、コードの重複が削減されました。

### `src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`, `src/cmd/internal/ld/go.go` の変更

これらのファイルでは、主に `BuildmodeCShared` をチェックしていた箇所に `BuildmodeCArchive` が追加され、両方のビルドモードで同様のリンカ処理（例: `.init_array` セクションの処理、`main` 関数のシンボル処理）が適用されるように変更されました。

*   **`dosymtype` (data.go)**: `.init_array` セクションにライブラリ初期化関数 (`INITENTRY`) を追加するロジックが、`BuildmodeCShared` に加えて `BuildmodeCArchive` でも適用されるようになりました。
*   **`dodata` (data.go)**: `.init_array` セクションの作成ロジックが、`BuildmodeCShared` に加えて `BuildmodeCArchive` および `BuildmodeShared` でも適用されるようになりました。
*   **`doelf` (elf.go)**: ELFバイナリの `.init_array` セクションの処理が、`BuildmodeCShared` に加えて `BuildmodeCArchive` および `BuildmodeShared` でも適用されるようになりました。
*   **`loadcgo` (go.go)**: Cgo関連の処理で、`BuildmodeCShared` に加えて `BuildmodeCArchive` でも `main` 関数のシンボルがスキップされるようになりました。これは、ライブラリとしてビルドされる場合に `main` 関数がエクスポートされる必要がないためです。
*   **`deadcode` (go.go)**: `BuildmodeShared` に加えて `BuildmodeCArchive` でも、すべてのシンボルが到達可能としてマークされるようになりました。これは、ライブラリとしてビルドされる場合、外部から呼び出される可能性のあるすべての関数が保持される必要があるためです。

### `src/cmd/internal/ld/pobj.go` の変更

*   **`Ldmain` 関数の更新**: リンカのメインエントリポイントである `Ldmain` 関数に、新しく追加された `archive()` 関数の呼び出しが追加されました。これにより、`c-archive` ビルドモードの場合に静的ライブラリの生成処理が実行されるようになります。

これらの変更により、Goのリンカは `c-archive` ビルドモードを適切に処理し、GoのコードをmacOS上でC言語の静的ライブラリとして出力できるようになりました。特に、`ar` コマンドを直接呼び出すことで、標準的な静的ライブラリの生成プロセスにGoのビルドシステムが統合されています。

## コアとなるコードの解説

### `src/cmd/internal/ld/lib.go`

このファイルはGoリンカの主要なロジックを含んでおり、ビルドモードの定義と処理、ライブラリの初期化、外部リンカとの連携などを担当します。

*   **`BuildmodeCArchive` の導入**: `BuildMode` 列挙型に `BuildmodeCArchive` が追加されたことで、リンカはGoコードをC静的ライブラリとしてビルドする新しいモードを認識できるようになりました。`Set` メソッドでの `darwin` 専用の制約は、この機能が特定のプラットフォームに特化していることを示しています。
*   **`hostobjCopy` と `archive` 関数**: これらは `c-archive` モードの核心部分です。
    *   `hostobjCopy` は、Goコンパイラが生成した中間オブジェクトファイルを一時的な場所にコピーします。これは、`ar` コマンドがこれらのファイルをアーカイブにまとめるためにアクセスできるようにするためです。
    *   `archive` 関数は、`ar` コマンドを外部プロセスとして実行し、コピーされたGoのオブジェクトファイルとGoランタイムのオブジェクトファイル (`go.o`) を結合して、最終的な `.a` 静的ライブラリを生成します。これは、Goのビルドシステムが標準的なUnixツールチェーンと連携する重要なポイントです。
*   **`hostlink` の変更**: `c-archive` モードでは、最終的な出力は `ar` によって生成される静的ライブラリであるため、`hostlink` 関数（通常は `gcc` などの外部リンカを呼び出す）は実行されません。これにより、不必要なリンキングステップがスキップされます。

### `src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`, `src/cmd/internal/ld/go.go`

これらのファイルは、リンカがシンボル、データセクション、ELF固有の構造、Cgo関連の処理をどのように扱うかを定義しています。

*   **`BuildmodeCArchive` の伝播**: これらのファイルでの変更は、主に既存の `BuildmodeCShared` のロジックを `BuildmodeCArchive` にも拡張するものです。
    *   `.init_array` セクションへの初期化関数の登録は、ライブラリがロードされた際にGoランタイムが適切に初期化されるために重要です。`c-archive` もライブラリであるため、この処理が必要です。
    *   `main` 関数のシンボルをスキップする処理は、ライブラリとしてビルドされるGoコードには独自の `main` エントリポイントが必要ないためです。
    *   すべてのシンボルを到達可能としてマークする処理は、静的ライブラリの場合、リンカが未使用のコードを削除しないようにするためです。C/C++アプリケーションがライブラリ内の任意のGo関数を呼び出す可能性があるため、すべてのエクスポートされたGo関数とその依存関係が最終的なアーカイブに含まれる必要があります。

### `src/cmd/internal/ld/pobj.go`

このファイルはリンカのメインエントリポイントを含んでいます。

*   **`Ldmain` での `archive()` 呼び出し**: リンカの処理フローの最後に `archive()` 関数が呼び出されるように変更されたことで、`c-archive` モードが選択された場合に、Goのオブジェクトファイルから静的ライブラリを生成するプロセスが確実に実行されるようになりました。

これらの変更は、Goのビルドシステムが `c-archive` モードを完全にサポートするために必要な、リンカの内部ロジックへの包括的な調整を示しています。特に、Goランタイムの初期化、シンボルの可視性、そして最終的なアーカイブ生成のための外部ツール (`ar`) の利用が重要な要素です。

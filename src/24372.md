# [インデックス 24372] ファイルの概要

このコミットは、Go言語の`net/http`パッケージにおいて、HTTPリクエストがレスポンスヘッダーを受信する前にキャンセルされた際に、`http.Transport`がより適切なエラー（`errRequestCanceled`）を返すように修正するものです。これにより、クライアント側でリクエストがキャンセルされたことを正確に識別し、適切なエラーハンドリングを行うことが可能になります。

## 元コミット内容

`net/http`パッケージにおいて、`Transport`がレスポンスヘッダーを受信する前にリクエストがキャンセルされた場合、適切なエラーを返すように変更します。これはIssue #11020を修正するものです。

## 変更の背景

Goの`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。クライアントがHTTPリクエストを送信し、サーバーからのレスポンスを待つ際、様々な理由でリクエストが途中でキャンセルされることがあります。例えば、ユーザーが操作を中断したり、タイムアウトが発生したりする場合です。

このコミット以前は、`http.Transport`がリクエストを処理している最中に、特にレスポンスヘッダーがまだ受信されていない段階でリクエストがキャンセルされた場合、`errClosed`のような一般的なエラーが返される可能性がありました。`errClosed`は、コネクションが閉じられたことを示すエラーであり、リクエストが明示的にキャンセルされた場合と、単にネットワークの問題でコネクションが切断された場合とを区別できませんでした。

Issue #11020は、この曖昧なエラーハンドリングの問題を指摘していました。クライアントアプリケーションは、リクエストが「キャンセルされた」のか、それとも「ネットワークエラーで失敗した」のかを正確に知る必要があります。これにより、アプリケーションはキャンセルされたリクエストに対して再試行を避けたり、ユーザーに適切なフィードバックを提供したりするなど、より賢明な判断を下すことができます。このコミットは、この問題を解決し、リクエストがキャンセルされた場合には明確に`errRequestCanceled`を返すようにすることで、より堅牢なエラーハンドリングを可能にすることを目的としています。

## 前提知識の解説

1.  **`net/http`パッケージと`Transport`**:
    *   `net/http`パッケージは、Go言語でHTTPクライアントおよびサーバーを構築するための標準ライブラリです。
    *   `http.Client`は、HTTPリクエストを送信するための高レベルなインターフェースを提供します。
    *   `http.Transport`は、`http.Client`の低レベルな実装を担い、実際のネットワーク接続の確立、リクエストの送信、レスポンスの受信、コネクションプーリングなどを管理します。
    *   `Transport`は、HTTP/1.1およびHTTP/2のプロトコル詳細を抽象化し、クライアントがサーバーと通信するための基盤を提供します。

2.  **HTTPリクエストのライフサイクルとキャンセル**:
    *   HTTPリクエストは、通常以下のフェーズを経ます。
        1.  **リクエストの準備**: `http.Request`オブジェクトの作成。
        2.  **コネクションの確立**: サーバーへのTCPコネクションの確立（または既存コネクションの再利用）。
        3.  **リクエストヘッダーとボディの送信**: サーバーへリクエストライン、ヘッダー、そしてボディを送信。
        4.  **レスポンスヘッダーの受信**: サーバーからのステータスラインとレスポンスヘッダーの受信。
        5.  **レスポンスボディの受信**: サーバーからのレスポンスボディの受信。
        6.  **コネクションのクローズ/再利用**: コネクションを閉じるか、再利用のためにプールに戻す。
    *   リクエストのキャンセルは、これらのフェーズのいずれかで発生する可能性があります。Goでは、主に`context.Context`を通じてリクエストのキャンセルを伝播させますが、このコミットが作成された時期には`http.Transport.CancelRequest`メソッドも利用されていました（現在は`context.Context`の使用が推奨され、`CancelRequest`は非推奨となっています）。

3.  **エラーハンドリングとエラータイプ**:
    *   Goでは、エラーは`error`インターフェースとして表現されます。
    *   特定のエラー条件を示すために、カスタムエラータイプや、`errors.Is`や`errors.As`で比較可能なSentinelエラー（特定の`error`変数を公開するもの）が使用されます。
    *   一般的なエラー（例: `io.EOF`、`net.ErrClosed`）と、より具体的なエラー（例: `context.Canceled`、`http.ErrRequestCanceled`）を区別することは、アプリケーションがエラーの原因を正確に特定し、適切なリカバリー戦略（例: 再試行、ユーザーへの通知、ログ記録）を適用するために非常に重要です。

## 技術的詳細

この変更は、`net/http`パッケージ内の`Transport`構造体の内部ロジック、特にレスポンスを待機している部分に焦点を当てています。

`Transport`は、HTTPリクエストを送信した後、サーバーからのレスポンスを非同期的に待機します。この待機中に、リクエストのキャンセルシグナルが送られる可能性があります。

変更前のコードでは、レスポンスヘッダーがまだ受信されていない状態でコネクションが閉じられた場合、`errClosed`という一般的なエラーが返されていました。これは、コネクションが正常に閉じられたのか、それともリクエストがキャンセルされた結果として閉じられたのかを区別できませんでした。

このコミットでは、`Transport`の内部でリクエストのキャンセル状態を追跡するメカニズム（`pc.isCanceled()`）を利用し、コネクションが閉じられた際に、それがリクエストキャンセルによるものかどうかを判断するロジックが追加されました。

具体的には、レスポンスを待機するループ内で、コネクションが閉じられたことを示す`errClosed`が発生した場合に、`pc.isCanceled()`を呼び出してリクエストがキャンセル済みであるかをチェックします。もしキャンセル済みであれば、`errClosed`の代わりに`errRequestCanceled`というより具体的なエラーを返すように上書きします。

`errRequestCanceled`は、`net/http`パッケージ内で定義されているSentinelエラーであり、リクエストがクライアントによって明示的にキャンセルされたことを示します。これにより、クライアントコードは返されたエラーが`errRequestCanceled`であるかどうかをチェックすることで、リクエストがキャンセルされたことを確実に判断できるようになります。

この変更は、`Transport`の堅牢性を高め、クライアントアプリケーションがHTTP通信のエラーをより正確に診断し、対応できるようにするための重要な改善です。

## コアとなるコードの解説

`src/net/http/transport.go` の変更は、`Transport`がレスポンスを待機している間のエラー処理ロジックを改善しています。

`WaitResponse`というラベルは、`Transport`がサーバーからのレスポンスを待機している状態を示唆しています。このコードブロックは、様々なイベント（レスポンスの受信、エラーの発生、タイムアウトなど）を処理する`select`ステートメントの一部であると推測されます。

変更前のコードでは、`default`ケース（おそらく、特定のイベントが発生しなかった場合や、予期せぬエラーが発生した場合）で`re = responseAndError{err: errClosed}`が設定されていました。これは、コネクションが閉じられたことを示す一般的なエラーです。

追加されたコードブロックは以下の通りです。

```go
			if pc.isCanceled() {
				re = responseAndError{err: errRequestCanceled}
			}
```

ここで、`pc`はおそらく`persistConn`（永続的なコネクションを表す内部構造体）のインスタンスであり、`isCanceled()`メソッドは、現在処理中のリクエストがキャンセルされたかどうかをチェックします。

もし`pc.isCanceled()`が`true`を返した場合、つまりリクエストがキャンセルされていた場合、`re`（レスポンスとエラーを保持する構造体）のエラーフィールドは`errClosed`から`errRequestCanceled`に上書きされます。これにより、リクエストがキャンセルされたという具体的な情報が呼び出し元に伝達されるようになります。

この変更により、`http.Client`のユーザーは、リクエストがネットワークの問題で失敗したのか、それともアプリケーションロジックによって意図的にキャンセルされたのかを、返されるエラータイプを見て正確に判断できるようになります。これは、エラーハンドリングの精度を大幅に向上させ、より堅牢なクライアントアプリケーションの構築に貢献します。

追加されたテストケース `TestTransportCancelBeforeResponseHeaders` は、この新しい動作を具体的に検証します。
1.  `net.Pipe()`を使ってクライアントとサーバー間の仮想的なコネクションを作成します。
2.  `http.Transport`をカスタムの`Dial`関数で設定し、この仮想コネクションを使用するようにします。
3.  `RoundTrip`をゴルーチンで実行し、リクエストを送信します。
4.  サーバー側でリクエストの最初の部分（HTTPメソッド "GET"）を読み取りますが、レスポンスヘッダーはまだ送信しません。
5.  クライアント側で`tr.CancelRequest(req)`を呼び出し、リクエストをキャンセルします。
6.  `RoundTrip`から返されるエラーを待ち、それが`ExportErrRequestCanceled`（`errRequestCanceled`の公開バージョン）であることを確認します。

このテストは、レスポンスヘッダーが受信される前にリクエストがキャンセルされた場合に、期待される`errRequestCanceled`が正しく返されることを保証します。

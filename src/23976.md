# [インデックス 23976] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおけるクライアントの挙動を修正するものです。具体的には、リクエストURLにユーザー名が含まれている場合に、開発者が明示的に設定した `Authorization` ヘッダーが上書きされてしまう問題を解決します。これにより、ユーザー名を含むURLを使用しつつ、カスタムの認証ヘッダーを送信したいシナリオでの予期せぬ認証失敗を防ぎます。

## 元コミット内容

`net/http` クライアントが、URLにユーザー名が含まれている場合に `Authorization` ヘッダーを上書きしないようにする。

Issue #11399 を修正。

## 変更の背景

Goの `net/http` パッケージのクライアントは、リクエストURLに `http://user:pass@example.com` のようにユーザー名とパスワードが含まれている場合、自動的に `Basic Authorization` ヘッダーを生成してリクエストに追加する機能を持っています。しかし、この機能には問題がありました。

ユーザーが `req.Header.Set("Authorization", "Bearer <token>")` のように、独自の `Authorization` ヘッダーを明示的に設定した場合でも、もしURLにユーザー名が含まれていれば、クライアントはURLから生成した `Basic Authorization` ヘッダーで既存のヘッダーを上書きしてしまっていたのです。

この挙動は、特にGitのクローン操作などでURLにユーザー名が含まれるケース（例: `https://user@github.com/repo.git`）で問題となりました。ユーザーがOAuthトークンなどの別の認証メカニズムを使用したい場合でも、URLのユーザー名が原因で意図しない `Basic Authorization` ヘッダーが送信され、認証が失敗する可能性がありました。

Issue #11399 はこの問題を報告しており、開発者が明示的に設定した `Authorization` ヘッダーが、URLのユーザー情報によって不本意に上書きされるべきではないという認識に基づいています。このコミットは、この予期せぬ上書きを防ぐために導入されました。

## 前提知識の解説

*   **HTTP `Authorization` ヘッダー**: HTTPリクエストにおいて、クライアントがサーバーに対して自身の認証情報（資格情報）を提示するために使用するヘッダーです。最も一般的な形式は `Basic` 認証と `Bearer` 認証です。
    *   **Basic 認証**: `Authorization: Basic <credentials>` の形式で、`<credentials>` は `username:password` をBase64エンコードしたものです。
    *   **Bearer 認証**: `Authorization: Bearer <token>` の形式で、`<token>` はOAuthなどのプロトコルで発行されるアクセストークンです。
*   **URLにおけるユーザー情報**: URLのスキームとホストの間に `user:password@` の形式で認証情報を含めることができます（例: `http://username:password@example.com/path`）。これは主にBasic認証の文脈で使われますが、セキュリティ上の理由から、パスワードをURLに含めることは推奨されません。
*   **Go `net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
    *   `http.Request`: HTTPリクエストを表す構造体です。`URL` フィールドにはリクエスト先のURLが、`Header` フィールドにはリクエストヘッダーが含まれます。
    *   `http.Client`: HTTPリクエストを送信するためのクライアントです。`Do` メソッドなどを使ってリクエストを実行します。
    *   `RoundTripper`: `http.Client` が実際にリクエストを送信する際に使用するインターフェースです。リクエストの変換、ネットワークへの送信、レスポンスの受信などを担当します。

## 技術的詳細

このコミットの核心は、`net/http` クライアントがリクエストを送信する直前に行う `Authorization` ヘッダーの自動生成ロジックの変更にあります。

変更前は、`send` 関数内でリクエストの `URL.User` フィールドにユーザー情報が存在する場合、無条件に `Basic Authorization` ヘッダーを生成し、`req.Header.Set("Authorization", ...)` を呼び出していました。`Set` メソッドは、指定されたヘッダーが存在すればその値を上書きし、存在しなければ新しく追加します。このため、開発者が事前に `Authorization` ヘッダーを設定していても、URLにユーザー名があればそれが上書きされてしまっていました。

変更後は、`req.URL.User` にユーザー情報が存在する**かつ** `req.Header.Get("Authorization") == ""`、つまり**まだ `Authorization` ヘッダーが設定されていない場合のみ**、URLのユーザー情報から `Basic Authorization` ヘッダーを生成して設定するように修正されました。

この変更により、以下の挙動が保証されます。
1.  URLにユーザー名が含まれており、かつ `Authorization` ヘッダーが明示的に設定されていない場合、クライアントは自動的に `Basic Authorization` ヘッダーを生成して追加します。これは従来の便利な挙動を維持します。
2.  URLにユーザー名が含まれていても、開発者が `Authorization` ヘッダーを既に設定している場合、クライアントはそのヘッダーを尊重し、上書きすることはありません。これにより、カスタム認証メカニズムが正しく機能するようになります。

この修正は、`net/http` クライアントの柔軟性と予測可能性を向上させ、開発者が意図した認証フローをより確実に実装できるようにします。

## コアとなるコードの変更箇所

`src/net/http/client.go` の `send` 関数内の以下の行が変更されました。

```diff
--- a/src/net/http/client.go
+++ b/src/net/http/client.go
@@ -212,7 +212,7 @@ func send(req *Request, t RoundTripper) (resp *Response, err error) {
 		req.Header = make(Header)
 	}
 
-	if u := req.URL.User; u != nil {
+	if u := req.URL.User; u != nil && req.Header.Get("Authorization") == "" {
 		username := u.Username()
 		password, _ := u.Password()
 		req.Header.Set("Authorization", "Basic "+basicAuth(username, password))
```

また、この変更の挙動を検証するために、`src/net/http/client_test.go` に `TestBasicAuthHeadersPreserved` という新しいテストケースが追加されました。

```go
func TestBasicAuthHeadersPreserved(t *testing.T) {
	defer afterTest(t)
	tr := &recordingTransport{}
	client := &Client{Transport: tr}

	// If Authorization header is provided, username in URL should not override it
	url := "http://My%20User@dummy.faketld/"
	req, err := NewRequest("GET", url, nil)
	if err != nil {
		t.Fatal(err)
	}
	req.SetBasicAuth("My User", "My Pass") // 明示的にBasic Authを設定
	expected := "My User:My Pass"
	client.Do(req)

	// ... (ヘッダーが期待通りに保持されているか検証するロジック) ...
}
```

## コアとなるコードの解説

変更された `if` 文の条件式 `if u := req.URL.User; u != nil && req.Header.Get("Authorization") == ""` がこの修正の全てです。

*   `u := req.URL.User; u != nil`: これは、リクエストのURLにユーザー情報（ユーザー名とオプションでパスワード）が含まれているかどうかをチェックします。`URL.User` は `url.Userinfo` 型のポインタを返し、ユーザー情報がない場合は `nil` になります。
*   `req.Header.Get("Authorization") == ""`: これは、リクエストヘッダーに `Authorization` ヘッダーが既に設定されているかどうかをチェックします。`Get` メソッドは、指定されたヘッダーが存在しない場合や値が空の場合に空文字列を返します。

この二つの条件が `&&` (論理AND) で結合されているため、URLにユーザー情報があり、**かつ** `Authorization` ヘッダーがまだ設定されていない場合にのみ、後続の `req.Header.Set("Authorization", ...)` が実行されます。これにより、開発者が明示的に設定した `Authorization` ヘッダーが上書きされることがなくなりました。

追加されたテストケース `TestBasicAuthHeadersPreserved` は、この新しい挙動を具体的に検証します。
1.  `url := "http://My%20User@dummy.faketld/"` のように、ユーザー名を含むURLを作成します。
2.  `req.SetBasicAuth("My User", "My Pass")` を呼び出し、明示的に `Authorization` ヘッダーを設定します。このメソッドは内部で `req.Header.Set("Authorization", "Basic "+basicAuth(username, password))` を行います。
3.  `client.Do(req)` でリクエストを送信します。
4.  `recordingTransport` を使用して、実際に送信されたリクエストのヘッダーをキャプチャし、`Authorization` ヘッダーが `req.SetBasicAuth` で設定された値と一致するかどうかを検証します。もし修正前のコードであれば、URLのユーザー名 (`My%20User`) から生成された `Basic Authorization` ヘッダーで上書きされてしまい、テストは失敗するでしょう。修正後のコードでは、明示的に設定されたヘッダーが保持されるため、テストは成功します。

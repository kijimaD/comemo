# [インデックス 26935] ファイルの概要

このコミットは、Go言語の静的解析ツールである `cmd/vet` の `printf` チェッカーの精度を向上させるものです。具体的には、`printf` スタイルの関数呼び出しにおいて、フォーマット文字列の引数の位置を特定する方法を、従来のハードコードされた関数名マップから、関数のシグネチャ（引数の型情報）を動的に解析する方法へと変更しています。これにより、`Errorf` や `Logf` のように、フォーマット文字列の前にログレベルやエラーコードなどの追加引数を持つ関数に対しても、より正確なチェックが可能になります。

## 元コミット内容

```
cmd/vet: Use function signature to find format string index.

cmd/vet's printf checker currently uses a hardcoded map of function
names to expected positions of format strings. We can be a bit more
precise than this by looking up the signature of the function, which
helps when libraries implement functions like Errorf or Logf with
extra arguments like log levels or error codes.

Specifically, the format string param is assumed to be the last string
parameter of the called function.

Fixes #12294.
```

## 変更の背景

Go言語の `cmd/vet` ツールは、Goプログラムの潜在的なバグや疑わしい構造を検出するための静的解析ツールです。その機能の一つに `printf` チェッカーがあり、`fmt.Printf` のようなフォーマット関数が正しいフォーマット文字列と引数を使用しているかを検証します。

このコミット以前の `printf` チェッカーは、フォーマット文字列の引数の位置を特定するために、関数名とフォーマット文字列の位置をマッピングしたハードコードされたリスト（`printfList`）を使用していました。例えば、`fmt.Printf` であればフォーマット文字列は最初の引数、`fmt.Fprintf` であれば2番目の引数、といった具合です。

しかし、このアプローチには限界がありました。特に、ユーザーが独自の `printf` スタイルの関数（例: `log.Errorf(level int, format string, args ...interface{})`）を定義した場合、`printfList` にその関数が登録されていないか、あるいは登録されていてもフォーマット文字列の前に独自の引数（例: `level`）が追加されていると、`vet` はフォーマット文字列の位置を誤って解釈し、誤った警告を発したり、本来検出されるべき問題を検出できなかったりする可能性がありました。

この問題を解決し、`printf` チェッカーの精度と汎用性を向上させるために、関数名だけでなく、実際の関数のシグネチャ（引数の型と順序）を解析してフォーマット文字列の位置を特定する新しいアプローチが導入されました。これにより、より柔軟で正確なチェックが可能となり、Issue #12294 で報告された問題が修正されます。

## 前提知識の解説

### `cmd/vet` (Go vet)

`go vet` は、Go言語のソースコードを静的に解析し、疑わしい構成要素や潜在的なエラーを報告するツールです。コンパイルは通るものの、実行時に問題を引き起こす可能性のあるコードパターン（例: `printf` フォーマット文字列と引数の不一致、到達不能なコード、ロックの誤用など）を検出するのに役立ちます。開発者がコードの品質と信頼性を維持するために広く利用されています。

### `printf` フォーマット文字列

`fmt.Printf` や `log.Printf` などの関数は、C言語の `printf` に似た書式指定文字列（フォーマット文字列）を使用して、可変個の引数を整形して出力します。フォーマット文字列には `%d` (整数)、`%s` (文字列)、`%v` (デフォルトフォーマット) などの「動詞」が含まれ、これらが後続の引数に対応します。`vet` の `printf` チェッカーは、これらの動詞と引数の型が一致しているかを検証します。

### Goの `types` パッケージ

`go/types` パッケージは、Goプログラムの型情報を表現および操作するためのAPIを提供します。コンパイラや静的解析ツールが、ソースコード内の識別子（変数、関数、メソッドなど）の型を解決し、そのシグネチャや構造を理解するために使用されます。このコミットでは、関数の `types.Signature` を取得し、その引数の型を調べることで、フォーマット文字列の位置を特定します。

### Goの `ast` パッケージ

`go/ast` パッケージは、Goプログラムの抽象構文木（Abstract Syntax Tree: AST）を表現するためのデータ構造と関数を提供します。Goのソースコードは、字句解析（トークン化）と構文解析を経てASTに変換されます。`cmd/vet` のような静的解析ツールは、このASTを走査してコードの構造を分析し、特定のパターンや問題を検出します。このコミットでは、`ast.CallExpr` を介して関数呼び出しのASTノードにアクセスし、その関数に関する型情報を取得します。

## 技術的詳細

この変更の核心は、`printf` スタイルの関数呼び出しにおけるフォーマット文字列の引数インデックスの特定方法を、静的なマップ参照から動的なシグネチャ解析へと移行した点にあります。

**変更前のアプローチ:**
`src/cmd/vet/print.go` 内の `printfList` という `map[string]int` が使用されていました。このマップは、関数名（小文字）をキーとして、その関数におけるフォーマット文字列の引数インデックスを値として保持していました。
例: `printfList["errorf"] = 0` は、`Errorf` 関数のフォーマット文字列が0番目の引数にあることを示していました。

この方法はシンプルですが、以下のような問題がありました。
1.  **柔軟性の欠如**: `printfList` に登録されていないカスタム関数や、登録されていても引数リストが異なる関数（例: `func MyLogf(level int, format string, args ...interface{})`）に対しては、正確なチェックができませんでした。
2.  **保守性の問題**: 新しい `printf` スタイルの関数が追加された場合、`printfList` を手動で更新する必要がありました。

**変更後のアプローチ:**
新しいアプローチでは、関数呼び出しのASTノードから関数の `types.Signature` を取得し、そのシグネチャを解析してフォーマット文字列の引数インデックスを動的に決定します。具体的なロジックは以下の通りです。

1.  **`isFormattedPrint` マップの導入**: 従来の `printfList` は削除され、代わりに `isFormattedPrint` という `map[string]bool` が導入されました。これは、特定の関数名がフォーマット関数であるかどうかを示すだけで、フォーマット文字列のインデックスは保持しません。
2.  **`signature` 関数の追加**:
    *   `signature(f *File, call *ast.CallExpr) *types.Signature` 関数が追加されました。
    *   この関数は、`ast.CallExpr`（関数呼び出しのASTノード）を受け取り、その呼び出し対象の関数の `types.Signature` を返します。
    *   `f.pkg.types[call.Fun].Type` を使用して、呼び出し対象の式の型情報を取得します。`go/types` パッケージが提供するこの情報は、関数の引数や戻り値の型、可変引数かどうかなど、詳細なシグネチャを含んでいます。
3.  **`formatIndex` 関数の追加**:
    *   `formatIndex(sig *types.Signature) int` 関数が追加されました。
    *   この関数は `types.Signature` を受け取り、そのシグネチャ内でフォーマット文字列として解釈されるべき引数のインデックスを返します。
    *   **重要なロジック**: フォーマット文字列は「呼び出された関数の最後の文字列パラメータ」であると仮定されます。
    *   `sig.Params().Len()` で引数の数を取得し、`sig.Params().At(i)` で各引数の `types.Var` を取得します。
    *   `p.Type().(*types.Basic)` で引数の基本型をチェックし、`typ.Kind() == types.String` で文字列型であるかを確認します。
    *   ループを通じて、見つかった最後の文字列型引数のインデックスを `idx` に格納し、最終的にその `idx` を返します。文字列型引数が見つからない場合は `-1` を返します。
4.  **`checkPrintf` 関数の変更**:
    *   `checkPrintf` 関数は、従来の `formatIndex` 引数を受け取らなくなりました。
    *   代わりに、関数内で `idx := formatIndex(signature(f, call))` を呼び出し、動的にフォーマット文字列のインデックスを計算します。
    *   `idx < 0` の場合（フォーマット文字列が見つからない場合）はエラーを報告します。
    *   その後のフォーマット文字列の解析ロジックは、この動的に取得した `idx` を使用するように変更されました。

この変更により、`cmd/vet` は、Goの型システムが提供する豊富な情報に基づいて、より賢く `printf` スタイルの関数を解析できるようになり、カスタムのロギング関数などに対しても正確なチェックを提供できるようになりました。

## コアとなるコードの解説

このコミットで追加された主要な関数は `signature` と `formatIndex` です。

### `signature` 関数

```go
func signature(f *File, call *ast.CallExpr) *types.Signature {
	typ := f.pkg.types[call.Fun].Type
	if typ == nil {
		return nil
	}
	sig, _ := typ.(*types.Signature)
	return sig
}
```
この関数は、`ast.CallExpr` 型の `call` 引数（Goコード内の関数呼び出しを表す抽象構文木のノード）を受け取ります。
1.  `call.Fun` は呼び出されている関数自体を表すASTノードです。
2.  `f.pkg.types[call.Fun].Type` を使用して、その関数の型情報を `go/types` パッケージから取得します。`f.pkg.types` は、現在のパッケージ内のすべての式と型のマッピングを保持しています。
3.  取得した型 `typ` が `nil` でないことを確認した後、`typ.(*types.Signature)` を使って、その型を `*types.Signature` 型に型アサートします。`types.Signature` は関数の引数、戻り値、レシーバなどの詳細なシグネチャ情報を含んでいます。
4.  最終的に、関数のシグネチャを返します。これにより、後続の処理で関数の引数リストを検査できるようになります。

### `formatIndex` 関数

```go
func formatIndex(sig *types.Signature) int {
	if sig == nil {
		return -1
	}
	idx := -1
	for i := 0; i < sig.Params().Len(); i++ {
		p := sig.Params().At(i)
		if typ, ok := p.Type().(*types.Basic); ok && typ.Kind() == types.String {
			idx = i
		}
	}
	return idx
}
```
この関数は、`*types.Signature` 型の `sig` 引数を受け取り、フォーマット文字列として機能する引数のインデックスを特定します。
1.  `sig` が `nil` の場合は、有効なシグネチャがないため `-1` を返します。
2.  `idx` を `-1` で初期化します。これは、フォーマット文字列が見つからなかった場合のデフォルト値であり、また、見つかった最後の文字列引数のインデックスを保持するために使用されます。
3.  `sig.Params().Len()` を使って関数の引数の数を取得し、`for` ループで各引数を反復処理します。
4.  `sig.Params().At(i)` で `i` 番目の引数（`types.Var` 型）を取得します。
5.  `p.Type().(*types.Basic)` で引数の型が基本型（`int`, `string`, `bool` など）であるかをチェックし、`ok` が `true` であれば型アサートが成功したことを意味します。
6.  `typ.Kind() == types.String` で、その基本型が文字列型であるかをチェックします。
7.  もし引数が文字列型であれば、そのインデックス `i` を `idx` に格納します。このループはすべての引数を走査するため、最終的に `idx` には「最後の文字列型引数」のインデックスが残ります。
8.  ループが終了した後、`idx` の値を返します。この値が `printf` チェッカーがフォーマット文字列として使用すべき引数のインデックスとなります。

これらの関数を組み合わせることで、`cmd/vet` は、関数呼び出しのコンテキストから動的にフォーマット文字列の位置を特定し、より正確な静的解析を実行できるようになりました。

## 元コミット内容

```
cmd/vet: Use function signature to find format string index.

cmd/vet's printf checker currently uses a hardcoded map of function
names to expected positions of format strings. We can be a bit more
precise than this by looking up the signature of the function, which
helps when libraries implement functions like Errorf or Logf with
extra arguments like log levels or error codes.

Specifically, the format string param is assumed to be the last string
parameter of the called function.

Fixes #12294.
```

## 変更の背景

Go言語の `cmd/vet` ツールは、Goプログラムの潜在的なバグや疑わしい構造を検出するための静的解析ツールです。その機能の一つに `printf` チェッカーがあり、`fmt.Printf` のようなフォーマット関数が正しいフォーマット文字列と引数を使用しているかを検証します。

このコミット以前の `printf` チェッカーは、フォーマット文字列の引数の位置を特定するために、関数名とフォーマット文字列の位置をマッピングしたハードコードされたリスト（`printfList`）を使用していました。例えば、`fmt.Printf` であればフォーマット文字列は最初の引数、`fmt.Fprintf` であれば2番目の引数、といった具合です。

しかし、このアプローチには限界がありました。特に、ユーザーが独自の `printf` スタイルの関数（例: `log.Errorf(level int, format string, args ...interface{})`）を定義した場合、`printfList` にその関数が登録されていないか、あるいは登録されていてもフォーマット文字列の前に独自の引数（例: `level`）が追加されていると、`vet` はフォーマット文字列の位置を誤って解釈し、誤った警告を発したり、本来検出されるべき問題を検出できなかったりする可能性がありました。

この問題を解決し、`printf` チェッカーの精度と汎用性を向上させるために、関数名だけでなく、実際の関数のシグネチャ（引数の型と順序）を解析してフォーマット文字列の位置を特定する新しいアプローチが導入されました。これにより、より柔軟で正確なチェックが可能となり、Issue #12294 で報告された問題が修正されます。

## 前提知識の解説

### `cmd/vet` (Go vet)

`go vet` は、Go言語のソースコードを静的に解析し、疑わしい構成要素や潜在的なエラーを報告するツールです。コンパイルは通るものの、実行時に問題を引き起こす可能性のあるコードパターン（例: `printf` フォーマット文字列と引数の不一致、到達不能なコード、ロックの誤用など）を検出するのに役立ちます。開発者がコードの品質と信頼性を維持するために広く利用されています。

### `printf` フォーマット文字列

`fmt.Printf` や `log.Printf` などの関数は、C言語の `printf` に似た書式指定文字列（フォーマット文字列）を使用して、可変個の引数を整形して出力します。フォーマット文字列には `%d` (整数)、`%s` (文字列)、`%v` (デフォルトフォーマット) などの「動詞」が含まれ、これらが後続の引数に対応します。`vet` の `printf` チェッカーは、これらの動詞と引数の型が一致しているかを検証します。

### Goの `types` パッケージ

`go/types` パッケージは、Goプログラムの型情報を表現および操作するためのAPIを提供します。コンパイラや静的解析ツールが、ソースコード内の識別子（変数、関数、メソッドなど）の型を解決し、そのシグネチャや構造を理解するために使用されます。このコミットでは、関数の `types.Signature` を取得し、その引数の型を調べることで、フォーマット文字列の位置を特定します。

### Goの `ast` パッケージ

`go/ast` パッケージは、Goプログラムの抽象構文木（Abstract Syntax Tree: AST）を表現するためのデータ構造と関数を提供します。Goのソースコードは、字句解析（トークン化）と構文解析を経てASTに変換されます。`cmd/vet` のような静的解析ツールは、このASTを走査してコードの構造を分析し、特定のパターンや問題を検出します。このコミットでは、`ast.CallExpr` を介して関数呼び出しのASTノードにアクセスし、その関数に関する型情報を取得します。

## 技術的詳細

この変更の核心は、`printf` スタイルの関数呼び出しにおけるフォーマット文字列の引数インデックスの特定方法を、静的なマップ参照から動的なシグネチャ解析へと移行した点にあります。

**変更前のアプローチ:**
`src/cmd/vet/print.go` 内の `printfList` という `map[string]int` が使用されていました。このマップは、関数名（小文字）をキーとして、その関数におけるフォーマット文字列の引数インデックスを値として保持していました。
例: `printfList["errorf"] = 0` は、`Errorf` 関数のフォーマット文字列が0番目の引数にあることを示していました。

この方法はシンプルですが、以下のような問題がありました。
1.  **柔軟性の欠如**: `printfList` に登録されていないカスタム関数や、登録されていても引数リストが異なる関数（例: `func MyLogf(level int, format string, args ...interface{})`）に対しては、正確なチェックができませんでした。
2.  **保守性の問題**: 新しい `printf` スタイルの関数が追加された場合、`printfList` を手動で更新する必要がありました。

**変更後のアプローチ:**
新しいアプローチでは、関数呼び出しのASTノードから関数の `types.Signature` を取得し、そのシグネチャを解析してフォーマット文字列の引数インデックスを動的に決定します。具体的なロジックは以下の通りです。

1.  **`isFormattedPrint` マップの導入**: 従来の `printfList` は削除され、代わりに `isFormattedPrint` という `map[string]bool` が導入されました。これは、特定の関数名がフォーマット関数であるかどうかを示すだけで、フォーマット文字列のインデックスは保持しません。
2.  **`signature` 関数の追加**:
    *   `signature(f *File, call *ast.CallExpr) *types.Signature` 関数が追加されました。
    *   この関数は、`ast.CallExpr`（関数呼び出しのASTノード）を受け取り、その呼び出し対象の関数の `types.Signature` を返します。
    *   `f.pkg.types[call.Fun].Type` を使用して、呼び出し対象の式の型情報を取得します。`go/types` パッケージが提供するこの情報は、関数の引数や戻り値の型、可変引数かどうかなど、詳細なシグネチャを含んでいます。
3.  **`formatIndex` 関数の追加**:
    *   `formatIndex(sig *types.Signature) int` 関数が追加されました。
    *   この関数は `types.Signature` を受け取り、そのシグネチャ内でフォーマット文字列として解釈されるべき引数のインデックスを返します。
    *   **重要なロジック**: フォーマット文字列は「呼び出された関数の最後の文字列パラメータ」であると仮定されます。
    *   `sig.Params().Len()` で引数の数を取得し、`sig.Params().At(i)` で各引数の `types.Var` を取得します。
    *   `p.Type().(*types.Basic)` で引数の基本型をチェックし、`typ.Kind() == types.String` で文字列型であるかを確認します。
    *   ループを通じて、見つかった最後の文字列型引数のインデックスを `idx` に格納し、最終的にその `idx` を返します。文字列型引数が見つからない場合は `-1` を返します。
4.  **`checkPrintf` 関数の変更**:
    *   `checkPrintf` 関数は、従来の `formatIndex` 引数を受け取らなくなりました。
    *   代わりに、関数内で `idx := formatIndex(signature(f, call))` を呼び出し、動的にフォーマット文字列のインデックスを計算します。
    *   `idx < 0` の場合（フォーマット文字列が見つからない場合）はエラーを報告します。
    *   その後のフォーマット文字列の解析ロジックは、この動的に取得した `idx` を使用するように変更されました。

この変更により、`cmd/vet` は、Goの型システムが提供する豊富な情報に基づいて、より賢く `printf` スタイルの関数を解析できるようになり、カスタムのロギング関数などに対しても正確なチェックを提供できるようになりました。

## コアとなるコードの解説

このコミットで追加された主要な関数は `signature` と `formatIndex` です。

### `signature` 関数

```go
func signature(f *File, call *ast.CallExpr) *types.Signature {
	typ := f.pkg.types[call.Fun].Type
	if typ == nil {
		return nil
	}
	sig, _ := typ.(*types.Signature)
	return sig
}
```
この関数は、`ast.CallExpr` 型の `call` 引数（Goコード内の関数呼び出しを表す抽象構文木のノード）を受け取ります。
1.  `call.Fun` は呼び出されている関数自体を表すASTノードです。
2.  `f.pkg.types[call.Fun].Type` を使用して、その関数の型情報を `go/types` パッケージから取得します。`f.pkg.types` は、現在のパッケージ内のすべての式と型のマッピングを保持しています。
3.  取得した型 `typ` が `nil` でないことを確認した後、`typ.(*types.Signature)` を使って、その型を `*types.Signature` 型に型アサートします。`types.Signature` は関数の引数、戻り値、レシーバなどの詳細なシグネチャ情報を含んでいます。
4.  最終的に、関数のシグネチャを返します。これにより、後続の処理で関数の引数リストを検査できるようになります。

### `formatIndex` 関数

```go
func formatIndex(sig *types.Signature) int {
	if sig == nil {
		return -1
	}
	idx := -1
	for i := 0; i < sig.Params().Len(); i++ {
		p := sig.Params().At(i)
		if typ, ok := p.Type().(*types.Basic); ok && typ.Kind() == types.String {
			idx = i
		}
	}
	return idx
}
```
この関数は、`*types.Signature` 型の `sig` 引数を受け取り、フォーマット文字列として機能する引数のインデックスを特定します。
1.  `sig` が `nil` の場合は、有効なシグネチャがないため `-1` を返します。
2.  `idx` を `-1` で初期化します。これは、フォーマット文字列が見つからなかった場合のデフォルト値であり、また、見つかった最後の文字列引数のインデックスを保持するために使用されます。
3.  `sig.Params().Len()` を使って関数の引数の数を取得し、`for` ループで各引数を反復処理します。
4.  `sig.Params().At(i)` で `i` 番目の引数（`types.Var` 型）を取得します。
5.  `p.Type().(*types.Basic)` で引数の型が基本型（`int`, `string`, `bool` など）であるかをチェックし、`ok` が `true` であれば型アサートが成功したことを意味します。
6.  `typ.Kind() == types.String` で、その基本型が文字列型であるかをチェックします。
7.  もし引数が文字列型であれば、そのインデックス `i` を `idx` に格納します。このループはすべての引数を走査するため、最終的に `idx` には「最後の文字列型引数」のインデックスが残ります。
8.  ループが終了した後、`idx` の値を返します。この値が `printf` チェッカーがフォーマット文字列として使用すべき引数のインデックスとなります。

これらの関数を組み合わせることで、`cmd/vet` は、関数呼び出しのコンテキストから動的にフォーマット文字列の位置を特定し、より正確な静的解析を実行できるようになりました。

# [インデックス 26199] ファイルの概要

このコミットは、Goプログラムにおける`EPIPE`エラー（Broken Pipe）の処理、特に標準出力（ファイルディスクリプタ1）と標準エラー（ファイルディスクリプタ2）に対する挙動を改善するものです。これにより、コマンドラインプログラムがUnixの一般的な挙動に近づき、パイプが切断された際に適切に`SIGPIPE`シグナルを発生させるようになります。

## 元コミット内容

このコミットは、Goプログラムが`EPIPE`エラー（Broken Pipe）に遭遇した際の挙動を変更します。

**変更前の挙動:**
任意のファイルディスクリプタで10回連続して`EPIPE`エラーが発生した場合に、プログラムが`SIGPIPE`シグナルで終了していました。これは、特定の状況下でプログラムが予期せぬ終了をする可能性があり、特にコマンドラインツールがパイプラインの一部として使用される場合に、Unixの一般的な挙動と異なっていました。

**変更後の挙動:**
ファイルディスクリプタ1（標準出力）またはファイルディスクリプタ2（標準エラー）で`EPIPE`エラーが発生した場合、プログラムは`SIGPIPE`シグナルを発生させます。もし`os/signal.Notify`を使って`SIGPIPE`シグナルを捕捉していない場合、これによりプログラムは`SIGPIPE`で終了します。
ファイルディスクリプタ1または2以外のディスクリプタで`EPIPE`エラーが発生した場合は、`Write`関数から単に`EPIPE`エラーが返されるだけとなり、プログラムは終了しません。

この変更は、Issue #11845 を修正し、Issue #9896 を更新するものです。

## 変更の背景

Unix系のシステムでは、プロセスがパイプに書き込もうとした際に、そのパイプの読み込み側が閉じられていると`EPIPE`エラーが発生します。このとき、通常はカーネルが`SIGPIPE`シグナルを書き込み側プロセスに送信し、デフォルトではプロセスを終了させます。これは、`cat file | head -n 1`のようなコマンドで、`cat`が`head`が終了した後に書き込みを続けようとした場合に、`cat`が適切に終了する挙動を保証するために重要です。

Goの以前の挙動では、`EPIPE`エラーが10回連続して発生しない限り`SIGPIPE`を発生させなかったため、Unixの標準的なパイプライン処理のセマンティクスと異なっていました。これにより、Goで書かれたコマンドラインツールがパイプラインで使われた際に、期待される挙動を示さない、あるいはリソースを無駄に消費し続ける可能性がありました。

特に、標準出力や標準エラーへの書き込みは、コマンドラインツールにおいて非常に一般的です。これらのディスクリプタに対する`EPIPE`エラーは、通常、パイプの相手側が終了したことを意味するため、即座に`SIGPIPE`を発生させてプログラムを終了させるのが自然な挙動とされます。しかし、ネットワーク接続など、他のファイルディスクリプタに対する`EPIPE`エラーは、必ずしもプログラム全体の終了を意味するものではなく、単にその書き込み操作が失敗したことを示す場合が多いです。

このコミットは、このGoの挙動をUnixの慣習に合わせることで、Goプログラムがより自然にコマンドライン環境に統合されるようにすることを目的としています。

## 前提知識の解説

*   **ファイルディスクリプタ (File Descriptor, FD)**: Unix系OSにおいて、開かれたファイルやI/Oリソース（パイプ、ソケットなど）を識別するためにカーネルがプロセスに割り当てる非負の整数です。
    *   `0`: 標準入力 (stdin)
    *   `1`: 標準出力 (stdout)
    *   `2`: 標準エラー出力 (stderr)
*   **パイプ (Pipe)**: プロセス間通信 (IPC) の一種で、一方のプロセスの出力がもう一方のプロセスの入力となるようにデータを流すための仕組みです。
*   **`EPIPE`エラー (Broken Pipe)**: パイプやソケットに書き込もうとした際に、その読み込み側が既に閉じられている場合に発生するエラーです。`syscall.EPIPE`としてGoの`syscall`パッケージで定義されています。
*   **`SIGPIPE`シグナル**: `EPIPE`エラーが発生した際に、カーネルがプロセスに送信するシグナルです。デフォルトでは、このシグナルを受け取ったプロセスは終了します。プログラムは`os/signal`パッケージを使用してこのシグナルを捕捉し、デフォルトの挙動を変更することができます。
*   **`os/signal.Notify`**: Goの`os/signal`パッケージの関数で、特定のシグナルを受信した際にチャネルに通知を送信するように設定します。これにより、プログラムはシグナルを捕捉し、カスタムのハンドリングロジックを実行できます。
*   **`syscall`パッケージ**: Goの標準ライブラリの一部で、OSのシステムコールに直接アクセスするための機能を提供します。`syscall.EPIPE`などのOS固有のエラーコードが含まれます。
*   **`runtime`パッケージ**: Goランタイムの低レベルな機能を提供するパッケージです。シグナルハンドリングなど、OSとのインタラクションの一部を管理します。

## 技術的詳細

このコミットの主要な変更点は、`src/os/file_unix.go`内の`epipecheck`関数のロジックと、`src/runtime/signal1_unix.go`内の`sigpipe`関数の呼び出し方、そして`src/os/signal/doc.go`における`SIGPIPE`の挙動に関するドキュメントの更新です。

1.  **`src/os/file_unix.go`の変更**:
    *   `file`構造体から`nepipe int32`フィールド（連続する`EPIPE`エラーのカウント）が削除されました。これは、連続エラーのカウントに基づく古い`SIGPIPE`発生ロジックが不要になったためです。
    *   `epipecheck`関数のロジックが大幅に変更されました。
        *   変更前は、`e == syscall.EPIPE`の場合に`file.nepipe`をインクリメントし、10回に達したら`sigpipe()`を呼び出すというものでした。
        *   変更後は、`e == syscall.EPIPE`かつ`file.fd`が`1`（標準出力）または`2`（標準エラー）の場合にのみ、即座に`sigpipe()`を呼び出すようになりました。それ以外の場合は何もせず、`Write`関数が`EPIPE`エラーを返すだけになります。

2.  **`src/runtime/signal1_unix.go`の変更**:
    *   `sigpipe()`関数に`if sigsend(_SIGPIPE) { return }`という行が追加されました。
    *   `sigsend`関数は、Goランタイムがシグナルを処理する内部メカニズムの一部です。この変更により、`SIGPIPE`シグナルがGoのシグナルハンドラによって捕捉されている場合（`os/signal.Notify`が使用されている場合など）は、ランタイムがそのシグナルを適切に処理し、デフォルトの終了動作を回避できるようになります。捕捉されていない場合は、以前と同様に`setsig(_SIGPIPE, _SIG_DFL, false)`でデフォルトのシグナルハンドラを設定し、`raise(_SIGPIPE)`でシグナルを再発生させ、プログラムを終了させます。

3.  **`src/os/signal/doc.go`の更新**:
    *   `SIGPIPE`セクションが追加され、新しい`EPIPE`エラー処理の挙動が明確に文書化されました。
    *   標準出力/標準エラーへの書き込みで`EPIPE`が発生した場合に`SIGPIPE`が送られること、`os/signal.Notify`で捕捉しない限りプログラムが終了すること、そして他のディスクリプタでは`EPIPE`エラーが返されるだけであることが明記されています。これにより、コマンドラインプログラムは典型的なUnixの挙動を示し、他のプログラムはネットワーク接続の切断で`SIGPIPE`によってクラッシュしないことが保証されます。

4.  **`src/os/pipe_test.go`の追加**:
    *   新しいテストファイル`pipe_test.go`が追加され、この新しい`EPIPE`/`SIGPIPE`の挙動が検証されています。
    *   `TestEPIPE`は、閉じられたパイプに書き込みを続けた場合に`EPIPE`エラーが返されることを確認します。
    *   `TestStdPipe`と`TestStdPipeHelper`は、子プロセスを起動し、標準出力、標準エラー、およびその他のファイルディスクリプタに書き込むことで、`SIGPIPE`の発生条件（標準出力/標準エラーへの書き込み時のみ）と、`os/signal.Notify`が`SIGPIPE`を捕捉した場合の挙動を詳細にテストしています。

これらの変更により、GoプログラムはUnixのパイプライン処理においてより予測可能で慣習的な挙動を示すようになります。

```go
// Copyright 2015 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Test broken pipes on Unix systems.
// +build !windows,!plan9,!nacl

package os_test

import (
	"fmt"
	"internal/testenv"
	"os"
	osexec "os/exec"
	"os/signal"
	"runtime"
	"syscall"
	"testing"
)

func TestEPIPE(t *testing.T) {
	r, w, err := os.Pipe()
	if err != nil {
		t.Fatal(err)
	}
	if err := r.Close(); err != nil {
		t.Fatal(err)
	}

	// Every time we write to the pipe we should get an EPIPE.
	for i := 0; i < 20; i++ {
		_, err = w.Write([]byte("hi"))
		if err == nil {
			t.Fatal("unexpected success of Write to broken pipe")
		}
		if pe, ok := err.(*os.PathError); ok {
			err = pe.Err
		}
		if se, ok := err.(*os.SyscallError); ok {
			err = se.Err
		}
		if err != syscall.EPIPE {
			t.Errorf("iteration %d: got %v, expected EPIPE", i, err)
		}
	}
}

func TestStdPipe(t *testing.T) {
	testenv.MustHaveExec(t)
	r, w, err := os.Pipe()
	if err != nil {
		t.Fatal(err)
	}
	if err := r.Close(); err != nil {
		t.Fatal(err)
	}
	// Invoke the test program to run the test and write to a closed pipe.
	// If sig is false:
	// writing to stdout or stderr should cause an immediate SIGPIPE;
	// writing to descriptor 3 should fail with EPIPE and then exit 0.
	// If sig is true:
	// all writes should fail with EPIPE and then exit 0.
	for _, sig := range []bool{false, true} {
		for dest := 1; dest < 4; dest++ {
			cmd := osexec.Command(os.Args[0], "-test.run", "TestStdPipeHelper")
			cmd.Stdout = w
			cmd.Stderr = w
			cmd.ExtraFiles = []*os.File{w}
			cmd.Env = append(os.Environ(), fmt.Sprintf("GO_TEST_STD_PIPE_HELPER=%d", dest))
			if sig {
				cmd.Env = append(cmd.Env, "GO_TEST_STD_PIPE_HELPER_SIGNAL=1")
			}
			if err := cmd.Run(); err == nil {
				if !sig && dest < 3 {
					t.Errorf("unexpected success of write to closed pipe %d sig %t in child", dest, sig)
				}
			} else if ee, ok := err.(*osexec.ExitError); !ok {
				t.Errorf("unexpected exec error type %T: %v", err, err)
			} else if ws, ok := ee.Sys().(syscall.WaitStatus); !ok {
				t.Errorf("unexpected wait status type %T: %v", ee.Sys(), ee.Sys())
			} else if ws.Signaled() && ws.Signal() == syscall.SIGPIPE {
				if sig || dest > 2 {
					t.Errorf("unexpected SIGPIPE signal for descriptor %d sig %t", dest, sig)
				}
			} else {
				t.Errorf("unexpected exit status %v for descriptor %ds sig %t", err, dest, sig)
			}
		}
	}
}

// This is a helper for TestStdPipe.  It's not a test in itself.
func TestStdPipeHelper(t *testing.T) {
	if os.Getenv("GO_TEST_STD_PIPE_HELPER_SIGNAL") != "" {
		signal.Notify(make(chan os.Signal, 1), syscall.SIGPIPE)
	}
	switch os.Getenv("GO_TEST_STD_PIPE_HELPER") {
	case "1":
		os.Stdout.Write([]byte("stdout"))
	case "2":
		os.Stderr.Write([]byte("stderr"))
	case "3":
		if _, err := os.NewFile(3, "3").Write([]byte("3")); err == nil {
			os.Exit(3)
		}
	default:
		t.Skip("skipping test helper")
	}
	// For stdout/stderr, we should have crashed with a broken pipe error.
	// The caller will be looking for that exit status,
	// so just exit normally here to cause a failure in the caller.
	// For descriptor 3, a normal exit is expected.
	os.Exit(0)
}
```

## コアとなるコードの解説

### `src/os/file_unix.go` の `epipecheck` 関数

この関数は、`os`パッケージ内のファイル書き込み操作で`EPIPE`エラーが発生した際に呼び出されます。

*   **変更前**: `file`構造体の`nepipe`フィールド（連続`EPIPE`エラーカウンタ）を使用していました。`EPIPE`エラーが発生するたびに`nepipe`をインクリメントし、10回に達すると`sigpipe()`を呼び出して`SIGPIPE`を発生させていました。`EPIPE`以外のエラーの場合は`nepipe`をリセットしていました。このロジックは、Goプログラムがすぐに終了しないようにするためのものでしたが、Unixの慣習とは異なっていました。
*   **変更後**: `nepipe`フィールドは削除され、`epipecheck`のロジックは大幅に簡素化されました。
    *   `e == syscall.EPIPE` かつ `file.fd == 1` (標準出力) または `file.fd == 2` (標準エラー) の場合にのみ、`sigpipe()` 関数を呼び出します。
    *   これにより、標準出力または標準エラーへの書き込みで`EPIPE`エラーが発生した場合、即座に`SIGPIPE`シグナルが生成されます。
    *   その他のファイルディスクリプタ（例：ネットワークソケット、通常のファイル）で`EPIPE`エラーが発生した場合は、`epipecheck`は何もしません。この場合、`Write`関数は単に`EPIPE`エラーを呼び出し元に返します。

この変更は、コマンドラインプログラムがパイプラインで使われる際に、標準出力/エラーが閉じられたらすぐに終了するというUnixの期待される挙動にGoを合わせるためのものです。

### `src/runtime/signal1_unix.go` の `sigpipe` 関数

この関数は、`SIGPIPE`シグナルを発生させるためのGoランタイムの内部関数です。

*   **変更前**: `setsig(_SIGPIPE, _SIG_DFL, false)` で`SIGPIPE`のデフォルトハンドラを設定し、`raise(_SIGPIPE)` でシグナルを発生させていました。これは、プログラムを強制的に終了させる挙動です。
*   **変更後**: `if sigsend(_SIGPIPE) { return }` という行が追加されました。
    *   `sigsend` はGoランタイムの内部関数で、`os/signal.Notify` を使って`SIGPIPE`が捕捉されているかどうかをチェックし、捕捉されている場合はそのチャネルにシグナルを送信します。
    *   もし`sigsend`が`true`を返した場合（つまり、シグナルがGoのハンドラによって処理された場合）、`sigpipe`関数はそこで`return`し、プログラムの終了は回避されます。
    *   `sigsend`が`false`を返した場合（つまり、`SIGPIPE`が捕捉されていない場合）、以前と同様に`setsig`と`raise`が実行され、プログラムは`SIGPIPE`で終了します。

この変更により、開発者が`os/signal.Notify`を使って`SIGPIPE`を明示的に処理したい場合に、それが可能になります。これにより、例えばネットワークサーバーがクライアントの切断によって`SIGPIPE`でクラッシュするのを防ぎつつ、コマンドラインツールはデフォルトで終了するという、より柔軟な挙動が実現されます。

### `src/os/signal/doc.go` の `SIGPIPE` セクション

このドキュメントの追加は、Goの`SIGPIPE`処理の新しい挙動を明確に説明するものです。

*   標準出力（FD 1）または標準エラー（FD 2）への書き込みで`EPIPE`が発生した場合に`SIGPIPE`が送られること。
*   `os/signal.Notify`で`SIGPIPE`を捕捉していない場合、プログラムは`SIGPIPE`で終了すること。
*   FD 1または2以外のディスクリプタでは、`EPIPE`エラーが`Write`から返されるだけで、`SIGPIPE`は発生しないこと。

このドキュメントは、Go開発者が`SIGPIPE`の挙動を理解し、それに応じてプログラムを設計する上で非常に重要です。

### `src/os/pipe_test.go`

この新規追加されたテストファイルは、新しい`EPIPE`/`SIGPIPE`の挙動が正しく実装されていることを検証します。

*   `TestEPIPE`: 閉じられたパイプへの書き込みが`syscall.EPIPE`エラーを返すことを確認します。これは、FD 1や2以外のディスクリプタに対する`EPIPE`の挙動を間接的にテストしています。
*   `TestStdPipe` と `TestStdPipeHelper`:
    *   `TestStdPipe`は、子プロセスとして`TestStdPipeHelper`を起動し、環境変数を使って標準出力、標準エラー、およびFD 3への書き込みをシミュレートします。
    *   `GO_TEST_STD_PIPE_HELPER_SIGNAL`環境変数を使って、子プロセスが`SIGPIPE`を捕捉するかどうかを切り替えます。
    *   テストは、`SIGPIPE`が捕捉されていない場合に標準出力/エラーへの書き込みが`SIGPIPE`で終了すること、FD 3への書き込みが`EPIPE`エラーを返すこと、そして`SIGPIPE`が捕捉されている場合にはすべての書き込みが`EPIPE`エラーを返すことを検証します。
    *   これにより、新しい`epipecheck`と`sigpipe`のロジックが、意図した通りに機能していることが包括的に確認されます。

# [インデックス 20066] ファイルの概要

このコミットは、Goランタイムの`src/pkg/runtime/asm_power64x.s`ファイルに対する変更です。このファイルは、POWER64アーキテクチャ向けのGoランタイムのアセンブリコードを含んでいます。具体的には、スタック管理や関数呼び出し規約に関連する低レベルな処理が記述されています。`asm_power64x.s`は、Goプログラムが実行される際の基盤となる部分であり、特にスタックの拡張や切り替えといった重要なランタイム操作を担っています。

## コミット

このコミットは、POWER64アーキテクチャにおける`newstackcall`関数内のバグを修正するものです。具体的には、`m_moreframesize`フィールドに値を設定する際に、誤って64ビットの命令（`MOVD`）を使用していた箇所を、正しい32ビットの命令（`MOVW`）に修正しています。これは、`m_moreframesize`が`uint32`型であるにもかかわらず、`uint64`として扱われていたことによる不整合を解消するものです。

## 変更の背景

この変更の背景には、Goランタイムがスタックを管理する方法と、特定のアーキテクチャ（この場合はPOWER64）におけるデータ型の扱いに関する問題があります。

Go言語は、goroutineごとに小さなスタックを割り当て、必要に応じてスタックを動的に拡張する「スタックセグメンテーション」というメカニズムを採用しています。これにより、メモリ使用量を効率的に保ちつつ、深い再帰呼び出しなどにも対応できます。スタックの拡張が必要になった場合、`newstack`というランタイム関数が呼び出され、新しい、より大きなスタックフレームが割り当てられます。

`newstackcall`は、このスタック拡張プロセスの一部として、現在のgoroutineのスタックから、新しいスタックフレームへの切り替えを調整する役割を担っています。この関数は、スタックフレームのサイズなど、スタック切り替えに必要な情報をランタイムの内部構造体（`m`構造体、`g`構造体など）に格納します。

問題は、`m`構造体（`runtime.m`、OSスレッドを表す）のフィールドである`m_moreframesize`が、Goの内部では`uint32`型として定義されているにもかかわらず、POWER64アーキテクチャ向けのアセンブリコードで、このフィールドに値を書き込む際に64ビットのデータ転送命令（`MOVD`）が使用されていたことです。

`MOVD`は64ビットの値を転送する命令であり、`m_moreframesize`が32ビットの領域しか持たない場合、隣接するメモリ領域を上書きしてしまう可能性があります。これは、メモリ破壊や予期せぬランタイムのクラッシュ、あるいはデバッグが困難なバグを引き起こす原因となります。このコミットは、この潜在的なメモリ破壊を防ぐために、正しい32ビットのデータ転送命令（`MOVW`）を使用するように修正しています。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する低レベルなシステムです。これには、ガベージコレクション、スケジューラ（goroutineの管理）、メモリ割り当て、スタック管理などが含まれます。Goプログラムは、コンパイル時にランタイムとリンクされ、ランタイムの機能を利用して実行されます。

### スタック管理と`newstack`

Goのgoroutineは、最初は小さなスタック（通常は数KB）で開始されます。関数呼び出しがスタックを使い果たしそうになると、Goランタイムは自動的にスタックを拡張します。このプロセスは「スタックセグメンテーション」と呼ばれ、`newstack`関数がその中心的な役割を担います。`newstack`は、現在のスタックフレームの情報を保存し、より大きな新しいスタックフレームを割り当て、実行を新しいスタックに切り替えます。

### `m`構造体と`g`構造体

Goランタイムには、主要な内部構造体として`m`（machine/thread）と`g`（goroutine）があります。
- `m`構造体（`runtime.m`）：OSのスレッドを表します。各`m`は、1つのOSスレッドに対応し、そのスレッド上でgoroutineを実行します。
- `g`構造体（`runtime.g`）：個々のgoroutineを表します。スタックポインタ、スタックの境界、現在の実行状態など、goroutineに関する情報が含まれます。

`m_moreframesize`は、`runtime.m`構造体内のフィールドで、スタック拡張時に使用される追加のスタックフレームのサイズを保持します。

### アセンブリ言語（POWER64x.s）

`.s`拡張子を持つファイルは、アセンブリ言語のソースコードです。Goランタイムの一部は、パフォーマンスや低レベルなハードウェア操作のためにアセンブリ言語で書かれています。`asm_power64x.s`は、POWER64アーキテクチャ（IBM PowerPC 64-bit）に特化したアセンブリコードです。

### データ型と命令

- **`uint32`と`uint64`**:
    - `uint32`は32ビット（4バイト）の符号なし整数型です。
    - `uint64`は64ビット（8バイト）の符号なし整数型です。
    プログラミングにおいて、変数の型は、その変数が占めるメモリのサイズと、そのメモリに格納されるデータの解釈方法を決定します。

- **`MOVD`と`MOVW`**:
    これらはPOWER64アセンブリ言語におけるデータ転送命令です。
    - `MOVD` (Move Doubleword): 64ビットのデータを転送する命令です。
    - `MOVW` (Move Word): 32ビットのデータを転送する命令です。
    命令の選択は、転送するデータのサイズと、ターゲットとなるメモリ領域のサイズに厳密に合わせる必要があります。誤った命令を使用すると、データの切り捨て（上位ビットの損失）や、意図しないメモリ領域の破壊を引き起こす可能性があります。

## 技術的詳細

このバグは、Goランタイムのスタック拡張メカニズムにおける、アセンブリコードとGoの型定義の間の不整合に起因していました。

`runtime.m`構造体には、`moreframesize`というフィールドがあります。Goのソースコード（`src/runtime/runtime2.go`など）を見ると、このフィールドは`uint32`型として定義されています。

```go
type m struct {
    // ...
    moreframesize uintptr // size of the frame for newstack
    // ...
}
```
（注：実際のGoのソースコードでは`uintptr`として定義されている場合もありますが、これはポインタサイズに依存し、64ビットシステムでは64ビット、32ビットシステムでは32ビットになります。しかし、このコミットの文脈では`uint32`として扱われるべき値が問題となっていました。）

問題のコードは、POWER64アーキテクチャ向けのアセンブリファイル`src/pkg/runtime/asm_power64x.s`にありました。`runtime·newstackcall`関数内で、`m_moreframesize`に値を設定する際に、以下の命令が使用されていました。

```assembly
MOVD    R10, m_moreframesize(R5)
```

ここで、`R10`レジスタには、`$1`という値が格納されています。この`$1`は、`m_moreframesize`に設定されるべき値です。`MOVD`命令は、`R10`レジスタの64ビットの内容を、`R5`レジスタが指すアドレス（`m`構造体のベースアドレス）から`m_moreframesize`フィールドのオフセットに書き込みます。

しかし、`m_moreframesize`が`uint32`（32ビット）であるため、`MOVD`（64ビット転送）を使用すると、`m_moreframesize`の32ビット領域だけでなく、その隣接する32ビット領域も上書きしてしまいます。これは、`m`構造体内の他の重要なフィールドを破壊する可能性があり、ランタイムの不安定性やクラッシュにつながる非常に危険なバグです。

このコミットは、この問題を修正するために、`MOVD`命令を`MOVW`命令に置き換えています。

```assembly
MOVW    R10, m_moreframesize(R5)
```

`MOVW`命令は32ビットのデータを転送するため、`m_moreframesize`の32ビット領域にのみ正確に書き込みを行い、隣接するメモリ領域を破壊するリスクを排除します。この修正により、Goランタイムの安定性と信頼性が向上しました。

## コアとなるコードの解説

変更された行は以下の部分です。

```assembly
-	MOVD	R10, m_moreframesize(R5)
+	MOVW	R10, m_moreframesize(R5)
```

- `R10`: レジスタR10は、`$1`という値（数値1）を保持しています。これは、`m_moreframesize`に設定されるべき値です。
- `m_moreframesize(R5)`: これは、`R5`レジスタが指すベースアドレス（`m`構造体の開始アドレス）からのオフセットで`m_moreframesize`フィールドのメモリ位置を示します。

元のコードでは、`MOVD`命令が使用されていました。`MOVD`は「Move Doubleword」の略で、64ビットのデータを転送します。しかし、`m_moreframesize`は32ビットのフィールドであるため、この命令は必要以上に多くのメモリを書き込んでいました。

修正後のコードでは、`MOVW`命令が使用されています。`MOVW`は「Move Word」の略で、32ビットのデータを転送します。これにより、`R10`レジスタの下位32ビットの値（この場合は`1`）が、`m_moreframesize`の32ビット領域に正確に書き込まれます。これにより、メモリ破壊のバグが修正され、ランタイムの整合性が保たれます。

この修正は、アセンブリレベルでのデータ型の厳密な一致がいかに重要であるかを示しています。Goの型システムは高レベルで安全ですが、ランタイムの低レベルなアセンブリコードでは、ハードウェアのレジスタサイズや命令のセマンティクスを正確に理解し、Goの型定義と一致させる必要があります。

## コアとなるコードの解説

変更された行は以下の部分です。

```assembly
-	MOVD	R10, m_moreframesize(R5)
+	MOVW	R10, m_moreframesize(R5)
```

- `R10`: レジスタR10は、`$1`という値（数値1）を保持しています。これは、`m_moreframesize`に設定されるべき値です。
- `m_moreframesize(R5)`: これは、`R5`レジスタが指すベースアドレス（`m`構造体の開始アドレス）からのオフセットで`m_moreframesize`フィールドのメモリ位置を示します。

元のコードでは、`MOVD`命令が使用されていました。`MOVD`は「Move Doubleword」の略で、64ビットのデータを転送します。しかし、`m_moreframesize`は32ビットのフィールドであるため、この命令は必要以上に多くのメモリを書き込んでいました。

修正後のコードでは、`MOVW`命令が使用されています。`MOVW`は「Move Word」の略で、32ビットのデータを転送します。これにより、`R10`レジスタの下位32ビットの値（この場合は`1`）が、`m_moreframesize`の32ビット領域に正確に書き込まれます。これにより、メモリ破壊のバグが修正され、ランタイムの整合性が保たれます。

この修正は、アセンブリレベルでのデータ型の厳密な一致がいかに重要であるかを示しています。Goの型システムは高レベルで安全ですが、ランタイムの低レベルなアセンブリコードでは、ハードウェアのレジスタサイズや命令のセマンティクスを正確に理解し、Goの型定義と一致させる必要があります。

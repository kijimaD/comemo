# [インデックス 27736] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) における、Solaris 11.2以降のシステムでの外部リンキングの問題を修正するものです。具体的には、Goコンパイラが生成する `go.o` オブジェクトファイル内の `STT_FILE` シンボルテーブルエントリがNULLである場合に発生する問題を、プレースホルダー名「go.go」を使用することで回避します。

## 変更の背景

この変更は、Solaris 11.2以降のオペレーティングシステムでGoプログラムを外部リンカと連携させる際に発生する問題に対処するために導入されました。Goコンパイラは、オブジェクトファイル（`go.o`など）を生成する際に、ELF (Executable and Linkable Format) 形式のシンボルテーブルに `STT_FILE` タイプのシンボルエントリを含めます。この `STT_FILE` シンボルは、そのオブジェクトファイルがどのソースファイルから生成されたかを示すファイル名を保持する役割があります。

問題は、Goのリンカがこの `STT_FILE` シンボルのファイル名エントリをNULL（または空）で生成していたことにありました。多くのリンカはこのようなNULLエントリを許容するか、適切に処理しますが、Solaris 11.2以降の特定のバージョンでは、このNULL `STT_FILE` シンボルエントリが存在すると、外部リンキングプロセスが失敗するという挙動を示しました。これは、リンカがファイル名エントリの存在を期待しているか、NULL値を不正な状態と見なすためと考えられます。

この問題は、GoのIssue #14957として報告され、このコミットはその問題を解決するためのワークアラウンドとして実装されました。

## 前提知識の解説

*   **ELF (Executable and Linkable Format)**: Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリなどのバイナリファイルを格納するための標準的なファイル形式です。プログラムのコード、データ、シンボルテーブル、セクション情報などが含まれます。
*   **シンボルテーブル (Symbol Table)**: ELFファイル内に含まれるデータ構造の一つで、プログラム内で定義または参照されるシンボル（関数名、変数名など）に関する情報（名前、アドレス、型、サイズなど）を格納します。リンカはシンボルテーブルを使用して、異なるオブジェクトファイル間の参照を解決します。
*   **`STT_FILE` シンボル**: ELFシンボルテーブルエントリの `st_info` フィールドで指定されるシンボルタイプの一つです。このタイプのシンボルは、オブジェクトファイルが生成された元のソースファイルの名前を示します。通常、このシンボルは `STB_LOCAL` (ローカルバインディング) を持ち、`SHN_ABS` (絶対セクションインデックス) を参照します。`st_name` フィールドは、ファイル名文字列が格納されている文字列テーブルへのオフセットを指します。
*   **`STB_LOCAL`**: シンボルのバインディング属性の一つで、そのシンボルが定義されているオブジェクトファイル内でのみ参照可能であることを示します。外部からは見えません。
*   **`SHN_ABS`**: シンボルのセクションインデックスの一つで、そのシンボルが特定のセクションに関連付けられておらず、絶対アドレスを持つことを示します。`STT_FILE` シンボルによく使用されます。
*   **Goリンカ (`cmd/link`)**: Go言語のツールチェーンの一部であり、Goコンパイラが生成したオブジェクトファイルや、C/C++コンパイラが生成したオブジェクトファイル（`cgo`を使用する場合）を結合して、最終的な実行可能ファイルやライブラリを生成する役割を担います。
*   **外部リンキング (External Linking)**: GoプログラムがC言語のライブラリなど、Go以外の言語で書かれたコードと連携する場合に、Goのリンカだけでなく、システムの標準リンカ（例: `gcc`や`ld`）も使用して最終的な実行可能ファイルを生成するプロセスを指します。このプロセスでは、Goのリンカが中間オブジェクトファイルを生成し、それを外部リンカに渡して最終的なリンクを行います。

## 技術的詳細

この問題の核心は、Goのリンカが `go.o` オブジェクトファイルに `STT_FILE` シンボルエントリを追加する際に、そのシンボルの名前（`st_name` フィールドが指す文字列）を空にしていた点にあります。ELF仕様では、`STT_FILE` シンボルの名前はオプションであり、空であっても問題ないとされることが多いです。しかし、Solaris 11.2以降の特定のリンカ実装では、この空のファイル名エントリを予期しない、あるいは不正な状態として扱い、リンキングプロセスを中断させていました。

このコミットでは、このSolarisリンカの挙動に対応するため、`STT_FILE` シンボルに「go.go」というプレースホルダー名を明示的に与えるように変更しました。この「go.go」という名前自体には特別な意味はなく、単にNULLではない有効な文字列を提供することで、Solarisリンカが期待する形式を満たし、リンキングエラーを回避することが目的です。これにより、Goのリンカが生成するオブジェクトファイルがSolarisの外部リンカと互換性を持つようになります。

この変更は、Goのリンカが「作業ディレクトリがシンボルテーブルに挿入されるのを避ける」という元々の意図（ファイル名が環境に依存しないようにするため）を維持しつつ、Solarisの特定のリンカの要件を満たすための実用的なワークアラウンドです。

## コアとなるコードの解説

変更の中心は `putelfsyment` 関数の呼び出しです。

元のコード:
```go
putelfsyment(0, 0, 0, STB_LOCAL<<4|STT_FILE, SHN_ABS, 0)
```
変更後のコード:
```go
putelfsyment(putelfstr("go.go"), 0, 0, STB_LOCAL<<4|STT_FILE, SHN_ABS, 0)
```

`putelfsyment` 関数は、ELFシンボルテーブルにエントリを追加するための内部関数です。その最初の引数は、シンボル名が格納されている文字列テーブルへのオフセット（インデックス）を期待します。

*   **変更前**: 最初の引数に `0` が渡されていました。これは、文字列テーブルの先頭（通常は空文字列）を指すか、あるいはシンボル名がないことを意図していました。この `0` が、Solarisリンカが問題視した「NULL STT_FILE symtab entry」の原因でした。
*   **変更後**: `putelfstr("go.go")` が最初の引数として渡されています。
    *   `putelfstr("go.go")` は、文字列「go.go」をELFファイルの文字列テーブルに追加し、その文字列のオフセット（インデックス）を返します。
    *   これにより、`STT_FILE` シンボルエントリは、文字列テーブル内の「go.go」という有効なファイル名を参照するようになります。

この変更により、`STT_FILE` シンボルはもはやNULL名を持たなくなり、Solaris 11.2+の外部リンカが期待する形式に合致するため、リンキングエラーが解消されます。

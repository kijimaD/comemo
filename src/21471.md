# [インデックス 21471] ファイルの概要

このコミットは、Goランタイムにおける`findfunc`関数のパフォーマンス改善を目的としています。具体的には、プログラムカウンタ（PC）から関数情報を検索する際に使用されるアルゴリズムを、従来のバイナリサーチからルックアップテーブル方式に変更することで、検索速度を大幅に向上させています。この最適化は、スタックコピーやガベージコレクションといった、`findfunc`が頻繁に呼び出されるGoランタイムの重要な処理に直接的な恩恵をもたらします。

    runtime: faster version of findfunc

    size by about 0.5% of the text segment.

## 元コミット内容

Goランタイムの`findfunc`関数を高速化する変更です。
PC（プログラムカウンタ）を含む関数を見つけるために、従来のバイナリサーチの代わりにルックアップテーブルを使用します。この変更は、主にスタックコピーとガベージコレクションで使用される`findfunc`の性能を向上させます。

ベンチマーク結果:
`BenchmarkStackCopy`が約13.35%高速化されました。
`findfunc`自体の時間は約2.5倍高速化されています。

このルックアップテーブルはリンク時に構築され、バイナリサイズをテキストセグメントの約0.5%増加させます。

また、すべての関数に16バイトの下限を課していますが、これは大きな影響はないはずです。（実際の制約は4096バイトごとに256関数以下ですが、16バイト/関数の方が実装が容易です。）

## 変更の背景

Goランタイムは、プログラムの実行中に様々な内部処理を行います。その中でも、スタックのコピー（例えば、goroutineのスタックサイズが不足した場合の拡張）やガベージコレクション（GC）は、プログラムのパフォーマンスに直結する重要な要素です。これらの処理では、特定のプログラムカウンタ（PC）がどの関数に属するかを頻繁に特定する必要があります。このPCから関数情報を検索する役割を担うのが`findfunc`関数です。

従来の`findfunc`は、関数エントリポイントのリストに対してバイナリサーチを実行していました。しかし、大規模なプログラムや、`findfunc`が繰り返し呼び出されるようなシナリオでは、このバイナリサーチが性能上のボトルネックとなる可能性がありました。特に、GCサイクル中や多数のgoroutineがスタックをコピーする際に、このオーバーヘッドが顕著になります。

このコミットの背景には、Goランタイムの全体的な効率を向上させ、特にGCの一時停止時間（stop-the-world pauses）を短縮し、アプリケーションのスループットを改善するという目標があります。`findfunc`の高速化は、これらの目標達成に向けた具体的なステップの一つとして位置づけられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とデータ構造に関する知識が不可欠です。

1.  **プログラムカウンタ (PC)**:
    PCは、現在実行中の命令のアドレスを示すレジスタです。Goランタイムは、このPC値を使用して、実行中のコードがどの関数に属しているか、どのソースファイルのどの行に対応するかといった情報を特定します。

2.  **`pclntab` (Program Counter Line Table)**:
    `pclntab`は、Goバイナリに埋め込まれている重要な内部データ構造です。その主な目的は、PC値とソースコード情報（ファイル名、行番号、関数名など）をマッピングすることです。これは、パニック時のスタックトレース生成、デバッグ、プロファイリング、そしてガベージコレクションなど、Goランタイムの多くの機能で利用されます。`pclntab`内には、関数のエントリポイントやオフセットなどの情報を含む関数シンボルテーブルが含まれています。

3.  **`findfunc` 関数**:
    `findfunc`は、Goランタイムの内部関数であり、与えられたPCアドレスに対応する関数メタデータ（`_func`構造体）を検索する役割を担っています。この関数は、スタックのウォーク（スタックトレースの生成）、ガベージコレクションにおけるスタックのスキャン、デバッガによる情報取得など、様々な場面で利用されます。その効率性は、Goプログラム全体のパフォーマンスに大きな影響を与えます。

4.  **スタックコピー**:
    Goのgoroutineは、必要に応じてスタックサイズを動的に拡張します。これは、現在のスタックの内容をより大きな新しいスタック領域にコピーすることで実現されます。このプロセス中に、スタック上の各PC値がどの関数に属するかを特定するために`findfunc`が使用されます。

5.  **ガベージコレクション (GC)**:
    Goはトレース型ガベージコレクタを使用しており、到達可能なオブジェクトを特定するためにヒープとスタックをスキャンします。スタックをスキャンする際、GCはスタック上のPC値から関数情報を取得し、その関数のスタックフレーム内のポインタを識別する必要があります。ここでも`findfunc`が重要な役割を果たします。

6.  **リンカ (`cmd/ld`)**:
    Goのビルドプロセスにおいて、リンカ（`cmd/ld`）はコンパイルされたオブジェクトファイルを結合し、実行可能なバイナリを生成します。この過程で、`pclntab`や、このコミットで導入される`findfunctab`のようなランタイムに必要なメタデータテーブルも構築され、バイナリに埋め込まれます。

## 技術的詳細

このコミットの核心は、`findfunc`の検索アルゴリズムをバイナリサーチからルックアップテーブルベースの方式に切り替えた点にあります。

**旧アプローチ（バイナリサーチ）**:
以前の`findfunc`は、`ftab`（関数テーブル）に対してバイナリサーチを実行していました。`ftab`は、関数のエントリポイントアドレスでソートされた`functab`構造体の配列です。PCが与えられると、この配列を二分探索して、`f.entry <= pc < ftab[next].entry`を満たす関数`f`を見つけ出していました。バイナリサーチは`O(log N)`の計算量を持つ効率的なアルゴリズムですが、Goバイナリ内の関数数が増加するにつれて、そのオーバーヘッドも増大します。

**新アプローチ（ルックアップテーブル `findfunctab`）**:
新しいアプローチでは、`findfunctab`という新しいルックアップテーブルが導入されます。このテーブルは、リンカ（`src/cmd/ld/pcln.c`）によってビルド時に生成され、Goバイナリのデータセグメントに埋め込まれます。

`findfunctab`は、テキストセグメント（実行可能コードが配置される領域）を一定サイズの「バケット」に分割します。各バケットは、`findfuncbucket`構造体で表現されます。

*   **`findfuncbucket` 構造体**:
    ```go
    type findfuncbucket struct {
        idx uint32
        subbuckets [16]byte
    }
    ```
    *   `idx`: このバケットがカバーするPC範囲内で最初に見つかる関数の`ftab`（関数テーブル）におけるインデックスを示します。
    *   `subbuckets`: 各バケットはさらに16個の「サブバケット」に分割されます。`subbuckets[i]`は、そのサブバケットの開始PCに対応する関数の`ftab`インデックスが、バケットの開始インデックス`idx`からどれだけオフセットしているか（デルタ値）を示します。

**検索ロジックの変更 (`src/runtime/symtab.go:findfunc`)**:
1.  与えられたPC値から、それが属するバケットとサブバケットを計算します。
    *   `x := pc - minpc` (テキストセグメントの最小PCからのオフセット)
    *   `b := x / pcbucketsize` (バケットインデックス)
    *   `i := x % pcbucketsize / (pcbucketsize/nsub)` (サブバケットインデックス)
2.  `findfunctab`から対応する`findfuncbucket`を取得します。
3.  `ffb.idx`と`ffb.subbuckets[i]`の値を合計して、`ftab`における推定開始インデックス`idx`を計算します。
4.  この`idx`から`ftab`を線形スキャンします。`ftab[idx+1].entry <= pc`である限り`idx`をインクリメントし、最終的に`ftab[idx].entry <= pc < ftab[idx+1].entry`を満たす関数を見つけます。

**性能向上**:
このルックアップテーブル方式により、`findfunc`はPC値から直接、目的の関数に近い`ftab`のインデックスを特定できるようになります。これにより、バイナリサーチのような`O(log N)`の計算量ではなく、定数時間に近い`O(1)`で検索を開始し、その後ごく短い線形スキャンで目的の関数を見つけることが可能になります。コミットメッセージにあるように、`findfunc`自体の時間は約2.5倍高速化され、`BenchmarkStackCopy`全体でも約13.35%の改善が見られました。

**バイナリサイズへの影響**:
このルックアップテーブルは、テキストセグメントの約0.5%のバイナリサイズ増加をもたらします。これは、パフォーマンス向上と引き換えに許容できるトレードオフと判断されています。

**関数サイズの制約 (`MINFUNC`)**:
この新しいルックアップテーブルの設計では、各関数が最低16バイトのサイズを持つという制約が導入されました（`MINFUNC = 16`）。これは、ルックアップテーブルのバケットとサブバケットの計算を簡素化し、PCから関数へのマッピングをより確実に、かつ効率的に行うためのものです。もし関数が16バイト未満の場合でも、リンカは次の関数との間にパディングを挿入し、あたかも16バイトであるかのように扱います。これにより、4096バイトごとに256関数以下というより複雑な制約を回避し、実装を容易にしています。

    *   `textaddress`関数内で、関数のサイズが`MINFUNC`（16バイト）より小さい場合、`MINFUNC`分のスペースを確保するように変更されています。これは、`findfunctab`の正確な動作を保証するためのパディングです。

    *   `findfunctab`関数が新規に追加されました。この関数は、Goバイナリのリンク時に`findfunc`用のルックアップテーブル（`runtime.findfunctab`シンボル）を構築し、バイナリに埋め込みます。

*   **`src/cmd/ld/pobj.c`**:
    *   リンカのメイン処理を行う`main`関数内で、`pclntab()`の後に`findfunctab()`が呼び出されるように変更されました。これにより、`findfunctab`がリンク時に生成されることが保証されます。
*   **`src/runtime/symtab.go`**:
    *   `findfunctab`シンボルが`pclntab`、`epclntab`と共に宣言されました。
    *   `minpc`, `maxpc`変数が追加され、テキストセグメントの最小/最大PCを保持します。
    *   `minfunc` (16) と `pcbucketsize` (256 * minfunc) 定数が定義されました。
    *   `findfuncbucket`構造体が定義されました。
    *   `symtabinit`関数で`minpc`と`maxpc`が初期化されるようになりました。
    *   **`findfunc`関数の実装が、バイナリサーチから`findfuncbucket`を使用したルックアップテーブル方式に完全に置き換えられました。**

## コアとなるコードの解説

### `src/cmd/ld/pcln.c` の `findfunctab` 関数

この関数は、リンカによって実行され、`runtime.findfunctab`という名前のシンボルとしてGoバイナリに埋め込まれるルックアップテーブルを構築します。

1.  **シンボルの作成**: `linklookup(ctxt, "runtime.findfunctab", 0)`で`runtime.findfunctab`シンボルを取得し、そのタイプを`SRODATA`（読み取り専用データ）に設定します。
2.  **PC範囲の特定**: テキストセグメント内の最小PC (`min`) と最大PC (`max`) を特定します。
3.  **テーブルのサイズ計算と確保**: `nbuckets`（バケット数）を計算し、`symgrow`で`runtime.findfunctab`シンボルに必要なメモリを確保します。各バケットは`4+SUBBUCKETS`バイト（`idx`用の4バイトと`subbuckets`用の`SUBBUCKETS`バイト）を占めます。
4.  **テーブルのフィルイン**:
    *   各バケットについてループします。
    *   `while`ループで、現在のバケットのPC範囲に最初に入る関数を`s`として見つけ、その`ftab`インデックスを`idx`に記録します。
    *   `setuint32`で、バケットのヘッダ（`idx`）を書き込みます。
    *   `SUBBUCKETS`個のサブバケットについてループします。
    *   各サブバケットのPC範囲に最初に入る関数を見つけ、その`ftab`インデックスとバケット開始インデックス`bidx`との差分（デルタ）を計算します。
    *   `setuint8`で、このデルタ値をサブバケットに書き込みます。これにより、各サブバケットがカバーするPC範囲内の関数の`ftab`インデックスが、バケットの開始インデックスからの相対値として効率的に表現されます。

### `src/runtime/symtab.go` の `findfunc` 関数

この関数は、Goランタイムが実行時にPCから関数情報を検索するために使用します。

1.  **PCの範囲チェック**: `pc`が`minpc`と`maxpc`の範囲外であれば`nil`を返します。
2.  **バケットとサブバケットの計算**:
    *   `x := pc - minpc`: PCをテキストセグメントの開始からのオフセットに変換します。
    *   `b := x / pcbucketsize`: オフセット`x`が属するバケットのインデックスを計算します。
    *   `i := x % pcbucketsize / (pcbucketsize/nsub)`: オフセット`x`が属するサブバケットのインデックスを計算します。
3.  **`findfuncbucket`の取得**: `findfunctab`シンボルのアドレスから、計算されたバケットインデックス`b`に対応する`findfuncbucket`構造体を取得します。
4.  **`ftab`インデックスの推定**: `ffb.idx`（バケットの開始インデックス）と`ffb.subbuckets[i]`（サブバケットのデルタ）を合計して、`ftab`における推定開始インデックス`idx`を計算します。
5.  **線形スキャン**: `ftab[idx+1].entry <= pc`である限り`idx`をインクリメントする線形スキャンを実行します。これは、推定された開始インデックスから、実際にPCを含む関数を見つけるための最終的な調整です。この線形スキャンは、バケットとサブバケットによって検索範囲が大幅に絞られているため、非常に短時間で完了します。
6.  **関数情報の返却**: 見つかった`idx`を使用して、`ftab`から対応する`_func`構造体を取得し、そのポインタを返します。

この変更により、`findfunc`はPCから関数情報を検索する際に、ほとんどの場合、数回の算術演算とメモリ参照、そしてごく短い線形スキャンで目的の関数に到達できるようになり、大幅な高速化が実現されました。

# [インデックス 23395] ファイルの概要

このコミットは、Go言語の `cmd/go` パッケージ、具体的にはバージョン管理システム (VCS) との連携を司る `vcs.go` ファイルに対する変更です。`go get` コマンドがGitリポジトリからコードを取得する際に、デフォルトブランチが `master` であるという前提を排除し、より柔軟なデフォルトブランチ名に対応できるように修正されました。これにより、`master` 以外の名前（例: `main`）をデフォルトブランチとして使用しているリポジトリでも `go get` が正しく動作するようになります。

## 変更の背景

`go get` コマンドは、Go言語のパッケージをリモートリポジトリから取得し、依存関係を解決し、ビルドするための重要なツールです。このコミットが導入される以前の `go get` は、Gitリポジトリからソースコードを取得する際に、リポジトリのデフォルトブランチが常に `master` であると仮定していました。具体的には、リポジトリをクローンした後、明示的に `master` ブランチをチェックアウトする処理が組み込まれていました。

しかし、Gitの運用において、デフォルトブランチの名前は `master` に限定されません。特に、GitHubのような主要なコードホスティングサービスでは、リポジトリ作成時にデフォルトブランチ名を `main` に設定するオプションが提供されており、多くの新しいプロジェクトで `main` が採用されています。また、既存のリポジトリでもデフォルトブランチ名を `master` から `main` やその他の名前に変更することが可能です。

このような状況下で `go get` が `master` ブランチへのハードコーディングを続けていると、以下のような問題が発生していました。

1.  **デフォルトブランチが `master` ではないリポジトリの取得失敗**: `master` ブランチが存在しないリポジトリに対して `go get` を実行すると、`checkout master` コマンドが失敗し、結果としてパッケージの取得に失敗していました。
2.  **意図しないバージョンの取得**: たとえ `master` ブランチが存在しても、それがリポジトリのデフォルトブランチではない場合、`go get` はユーザーが期待する最新の安定版（通常はデフォルトブランチが指すもの）ではなく、古い `master` ブランチのコードを取得してしまう可能性がありました。これは、依存関係の解決やアプリケーションのビルドにおいて予期せぬバグや非互換性を引き起こす原因となります。
3.  **GitHubのデフォルトブランチ変更への非対応**: コミットメッセージにある「Changing Github default branch is effectively changing HEAD」という記述は、GitHubが提供するデフォルトブランチ変更機能の重要性を強調しています。この機能により、リポジトリの「最新かつ推奨される」状態が `master` 以外のブランチによって表現されることが増えましたが、`go get` がこれに対応できていなかったため、ユーザー体験が悪化していました。

この問題はGoのIssueトラッカーで `Fixes #9032` として報告されていました。ウェブ検索ではIssue 9032の具体的な内容は確認できませんでしたが、コミットメッセージから、`go get` がGitのデフォルトブランチの柔軟性に対応できていないことが問題の本質であったと明確に理解できます。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下の概念を把握しておく必要があります。

### 1. Gitの基本概念

*   **リポジトリ (Repository)**: プロジェクトのファイル群と、それらのファイルに対するすべての変更履歴（コミット）が保存される場所です。ローカルリポジトリとリモートリポジトリがあります。
*   **ブランチ (Branch)**: 開発の並行作業を可能にするための機能です。各ブランチは独立した開発ラインを表し、メインの開発ラインから分岐して新機能開発やバグ修正などを行い、後でメインラインに統合（マージ）されます。
*   **デフォルトブランチ (Default Branch)**: リモートリポジトリがクローンされた際や、新しいリポジトリが作成された際に、最初にチェックアウトされるブランチです。伝統的に `master` という名前が使われてきましたが、近年では人種差別的な含意を避けるため `main` などの代替名が広く採用されています。
*   **タグ (Tag)**: 特定のコミットに意味のある永続的な名前（例: `v1.0.0`、`release-2023-01-15`）を付けるための機能です。主にソフトウェアのリリースバージョンを示すために使用され、後から特定のリリース時点のコードを簡単に参照できるようにします。
*   **HEAD**: 現在作業しているブランチの最新コミット、または特定のコミットを指すポインタです。Gitにおいて「現在の状態」を示す非常に重要な概念です。リモートリポジトリの `HEAD` は、そのリポジトリのデフォルトブランチを指すことが一般的です。
*   **`git checkout` コマンド**: ブランチを切り替えたり、特定のコミットやタグの状態に作業ディレクトリを戻したりするコマンドです。例えば `git checkout master` は `master` ブランチに切り替えます。

### 2. `go get` コマンド

`go get` は、Go言語のモジュール（Go 1.11以降）やパッケージ（Go 1.10以前）をダウンロードし、依存関係を解決し、必要に応じてビルドするコマンドです。
*   ユーザーは通常、`go get example.com/pkg` のようにリモートリポジトリのパスを指定して実行します。
*   `go get` は内部的にGit、Mercurial、Subversionなどのバージョン管理システム (VCS) と連携し、指定されたリポジトリからソースコードを取得します。
*   特定のバージョンを指定するには、`go get example.com/pkg@v1.2.3` のようにタグやコミットハッシュを指定できます。

### 3. バージョン管理システム (VCS) との連携

`go get` は、Goのツールチェインの一部として、様々なVCSと連携するための抽象化レイヤーを持っています。`src/cmd/go/vcs.go` ファイルは、この連携ロジックを定義しており、各VCS（Git、Mercurialなど）に対して、リポジトリのクローン、更新、タグの検索、ブランチ/タグのチェックアウトなどの操作を行うためのコマンドテンプレートを保持しています。

## 技術的詳細

このコミットの技術的な詳細な変更点は、`go get` コマンドがGitリポジトリを扱う際の内部ロジック、特に `src/cmd/go/vcs.go` ファイル内の `vcsGit` 構造体の `tagSyncDefault` フィールドの変更に集約されます。

### 変更前の挙動

変更前、`vcsGit` 構造体は以下のように定義されていました（関連部分のみ抜粋）：

```go
var vcsGit = &vcsCmd{
    // ...
    tagSyncCmd:     "checkout {tag}",
    tagSyncDefault: "checkout master", // ここが問題
    // ...
}
```

ここで `tagSyncDefault: "checkout master"` という設定は、`go get` がGitリポジトリをクローンした後、明示的に `git checkout master` コマンドを実行することを意味していました。この挙動は、以下のようなシナリオで問題を引き起こしました。

1.  **リポジトリのデフォルトブランチが `master` ではない場合**: 例えば、デフォルトブランチが `main` であるリポジトリを `go get` で取得しようとすると、`go get` はまずリポジトリをクローンします。その後、`tagSyncDefault` の指示に従って `git checkout master` を実行しようとしますが、`master` ブランチが存在しないため、このコマンドは失敗し、`go get` もエラーで終了します。
2.  **`master` ブランチが存在するが、それが最新ではない場合**: 古いプロジェクトでは `master` ブランチが残っているものの、開発のメインラインが別のブランチ（例: `develop` や `main`）に移行していることがあります。この場合、`go get` は `master` ブランチをチェックアウトするため、ユーザーは最新のコードではなく、古いコードを取得してしまうことになります。

この問題は、Gitの柔軟なブランチ運用、特にGitHubのようなプラットフォームが提供するデフォルトブランチ名のカスタマイズ機能と `go get` の内部実装との間のミスマッチによって生じていました。Gitリポジトリをクローンする際、通常はリモートの `HEAD` が指すブランチ（つまりデフォルトブランチ）が自動的にチェックアウトされます。`go get` がこのGitの標準的な挙動を上書きして `master` を強制的にチェックアウトしようとしていたことが、問題の根本原因でした。

### 変更後の挙動

このコミットでは、`tagSyncDefault` フィールドの値が `"checkout master"` から `""` (空文字列) に変更されました。

```diff
--- a/src/cmd/go/vcs.go
+++ b/src/cmd/go/vcs.go
@@ -115,8 +115,12 @@ var vcsGit = &vcsCmd{\
 	tagLookupCmd: []tagCmd{\
 		{"show-ref tags/{tag} origin/{tag}", `((?:tags|origin)/\S+)$`},\
 	},\
-	tagSyncCmd:     "checkout {tag}",
-	tagSyncDefault: "checkout master",
+	tagSyncCmd: "checkout {tag}",
+	// both createCmd and downloadCmd update the working dir.
+	// No need to do more here. We used to 'checkout master'
+	// but that doesn't work if the default branch is not named master.
+	// See golang.org/issue/9032.
+	tagSyncDefault: "",
 
 	scheme:     []string{"git", "https", "http", "git+ssh"},\
 	pingCmd:    "ls-remote {scheme}://{repo}",
```

この変更により、`go get` はGitリポジトリをクローンした後に、明示的に `master` ブランチをチェックアウトする動作を停止します。代わりに、Gitのデフォルトの挙動に依存するようになります。Gitはリポジトリをクローンする際、リモートリポジトリの `HEAD` が指すブランチ（すなわち、そのリポジトリのデフォルトブランチ）を自動的にローカルの作業ディレクトリにチェックアウトします。

この修正によって、`go get` は以下の利点を得ました。

*   **デフォルトブランチ名の柔軟性への対応**: `master` 以外の名前（`main` など）をデフォルトブランチとして使用しているリポジトリでも、`go get` が正しく動作するようになります。
*   **Gitの標準的な挙動との整合性**: `go get` がGitの標準的なクローン後の挙動（リモートの `HEAD` が指すブランチをチェックアウトする）を尊重するようになり、より予測可能で堅牢な動作を実現します。
*   **GitHubなどのプラットフォームの変更への対応**: GitHubがデフォルトブランチ名を `main` に変更する動きなど、VCSホスティングサービスの進化に `go get` が追従できるようになりました。

`tagSyncCmd: "checkout {tag}"` は変更されていないため、ユーザーが `go get example.com/pkg@v1.2.3` のように特定のタグを指定してパッケージを取得する機能は引き続き正常に機能します。このコミットは、`go get` の依存関係解決メカニズムをより現代的で柔軟なGitの運用プラクティスに適合させるための重要な改善でした。

## コアとなるコードの解説

`src/cmd/go/vcs.go` ファイルは、`go get` コマンドがGit、Mercurial、Subversionなどの様々なバージョン管理システムと連携するためのロジックを定義しています。このファイルには、各VCSタイプに対応する `vcsCmd` 構造体が定義されており、それぞれのVCS固有のコマンドや挙動が設定されています。

今回の変更は、Gitを扱うための `vcsGit` 構造体内の `tagSyncDefault` フィールドに焦点を当てています。

*   **`vcsGit` 構造体**: Gitリポジトリに対する操作（クローン、フェッチ、チェックアウトなど）を定義するための設定を保持します。
*   **`tagLookupCmd`**: 指定されたタグ（例: `v1.0.0`）がリモートリポジトリに存在するかどうかを検索するためのGitコマンド（`git show-ref tags/{tag} origin/{tag}`）を定義します。
*   **`tagSyncCmd`**: ユーザーが `go get example.com/pkg@v1.2.3` のように特定のタグを指定した場合に、そのタグをチェックアウトするためのGitコマンド（`git checkout {tag}`）を定義します。このフィールドは今回の変更の対象ではありません。
*   **`tagSyncDefault`**: このフィールドは、`go get` が特定のタグやブランチが明示的に指定されなかった場合に、どのブランチやコミットをデフォルトでチェックアウトするかを定義していました。
    *   **変更前 (`"checkout master"`)**: `go get` はリポジトリをクローンした後、強制的に `git checkout master` コマンドを実行していました。これは、デフォルトブランチが `master` であるという古い慣習に依存していました。
    *   **変更後 (`""` (空文字列))**: このフィールドが空文字列になったことで、`go get` は明示的に `master` をチェックアウトする動作を停止します。代わりに、Gitのデフォルトの挙動に委ねられます。Gitはリポジトリをクローンする際、リモートリポジトリの `HEAD` が指すブランチ（通常はリポジトリのデフォルトブランチ）を自動的にローカルの作業ディレクトリにチェックアウトします。これにより、`go get` は `master` 以外のデフォルトブランチ（例: `main`）を持つリポジトリでも正しく動作するようになります。

追加されたコメント `// both createCmd and downloadCmd update the working dir. // No need to do more here. We used to 'checkout master' // but that doesn't work if the default branch is not named master. // See golang.org/issue/9032.` は、この変更の理由を明確に説明しています。`createCmd` (リポジトリの初期クローン) と `downloadCmd` (既存リポジトリの更新) の両方が既に作業ディレクトリを適切に更新するため、`tagSyncDefault` でさらに `master` をチェックアウトする必要はなく、むしろそれが問題を引き起こしていた、という背景が示されています。

この修正は、`go get` がGitリポジトリのデフォルトブランチの命名規則に依存しなくなり、より柔軟で堅牢な依存関係管理を実現するための重要な改善です。

# [インデックス 23816] ファイルの概要

このコミットは、Go言語の型チェッカー (`go/types` パッケージ) における `Eval` 関数が、式を評価する際に正しいファイルセットを使用するように修正するものです。具体的には、式のパース時に `token.FileSet` を適切に渡すことで、型チェックエラー発生時の診断情報の正確性を向上させています。

## 元コミット内容

`go/types: fix Eval to use correct file set when evaluating an expression`

このコミットは、`go/types` パッケージ内の `Eval` 関数が、式を評価する際に正しいファイルセットを使用するように修正するものです。以前は、型チェックエラーが発生した場合に、`Eval` 関数が式の正しいファイルセットを持たないというバグが存在していました。この修正は、`parser.ParseExpr` の代わりに `parser.ParseExprFrom` を使用することで、この問題を解決しています。

この変更は、`go-review.googlesource.com/10999` で提案されたものですが、`x/tools/go/types` リポジトリではGo 1.5の機能に依存できないため、直接適用できませんでした。そのため、Go本体の `src/go/types` にこの修正が取り込まれることになりました。

## 変更の背景

Go言語のコンパイラやツールチェーンにおいて、ソースコードの解析は複数の段階を経て行われます。その中で、`go/types` パッケージはGoプログラムの型チェックを担当する重要なコンポーネントです。`Eval` 関数は、特定の式を評価し、その型と値を決定するために使用されます。

このコミットが行われる以前は、`Eval` 関数内で式をパースする際に `parser.ParseExpr(expr)` が使用されていました。この関数は、式をパースする際に新しい `token.FileSet` を内部的に作成していました。しかし、`Eval` 関数には呼び出し元から `fset *token.FileSet` が渡されており、この `fset` はプログラム全体のファイル位置情報を管理するためのものです。

問題は、`parser.ParseExpr` が独自のファイルセットを使用するため、`Eval` 関数が評価する式が、呼び出し元が提供する `fset` とは異なるファイル位置情報を持つことになっていました。これにより、式に型エラーがあった場合、エラーメッセージが参照するファイル位置が不正確になる可能性がありました。特に、`go/types` が提供する診断情報（エラーメッセージの行番号や列番号など）の正確性が損なわれるというバグ (`BUG(gri)`) が認識されていました。

この不整合を解消し、型チェックエラー発生時に正確な診断情報を提供するために、`Eval` 関数が呼び出し元から受け取った `fset` を式のパース時にも使用するように変更する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部パッケージに関する知識が必要です。

1.  **`go/token` パッケージ**:
    *   Goソースコードのトークン（識別子、キーワード、演算子など）と、それらのソースコード上の位置（ファイル名、行番号、列番号、オフセット）を管理するためのパッケージです。
    *   `token.FileSet` は、複数のソースファイルにわたる位置情報を一元的に管理するオブジェクトです。各ソースファイルは `token.File` オブジェクトとして `FileSet` に追加され、`token.Pos` 型の値がソースコード上の特定の位置を示します。`token.Pos` は `FileSet` と組み合わせて、人間が読める形式のファイル名、行番号、列番号に変換されます。

2.  **`go/parser` パッケージ**:
    *   Goソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を構築するためのパッケージです。
    *   `parser.ParseExpr(src string)`: 文字列として与えられたGoの式をパースし、ASTノードを返します。この関数は内部で新しい `token.FileSet` を作成して使用します。
    *   `parser.ParseExprFrom(fset *token.FileSet, filename string, src interface{}, mode Mode)`: `ParseExpr` とは異なり、既存の `token.FileSet` (`fset`) を受け取り、そのファイルセットに新しいファイル (`filename` と `src` で指定される内容) を追加して式をパースします。これにより、パースされた式の位置情報が、指定された `fset` のコンテキスト内で管理されるようになります。

3.  **`go/types` パッケージ**:
    *   Goプログラムの型チェックを行うためのパッケージです。Goコンパイラの重要な部分であり、Goの静的型付けを強制します。
    *   `Eval` 関数: この関数は、与えられた式 (`expr`) の型と値を評価するために使用されます。通常、デバッガやIDEのコード補完機能、あるいはリファクタリングツールなどで、特定のコードスニペットの型情報を取得するために利用されます。

これらのパッケージは、Go言語のツールチェーンにおいて、ソースコードの解析、型チェック、および診断情報の生成において密接に連携しています。特に、正確なエラーメッセージや警告を生成するためには、ソースコード上の位置情報が正確であることが不可欠です。

## 技術的詳細

このコミットの技術的な核心は、`go/types.Eval` 関数が式のパースに用いる `token.FileSet` の一貫性を確保することにあります。

以前の実装では、`Eval` 関数は以下のようなコードを使用していました。

```go
// ...
// parse expressions
// BUG(gri) In case of type-checking errors below, the type checker
//          doesn't have the correct file set for expr. The correct
//          solution requires a ParseExpr that uses the incoming
//          file set fset.
node, err := parser.ParseExpr(expr)
// ...
```

ここで `parser.ParseExpr(expr)` は、`expr` という文字列をGoの式としてパースします。しかし、この関数は内部で新しい `token.FileSet` を作成して使用するため、`Eval` 関数に引数として渡された `fset` とは異なるファイルセットが式の位置情報に関連付けられていました。

`go/types` パッケージは、型チェック中に発生したエラーを報告する際に、`token.Pos` を使用してソースコード上の正確な位置を指し示します。この `token.Pos` は、それが属する `token.FileSet` と組み合わされて初めて意味のあるファイル名、行番号、列番号に変換されます。もし式がパースされたファイルセットと、`Eval` 関数が全体として使用しているファイルセットが異なると、型チェックエラーが発生した際に、`Eval` 関数が提供するエラーメッセージの位置情報が不正確になるという問題が生じていました。これは、`BUG(gri)` コメントで明示的に指摘されていた点です。

このコミットでは、この問題を解決するために `parser.ParseExpr` の代わりに `parser.ParseExprFrom` 関数を使用するように変更されました。

```go
// ...
// parse expressions
node, err := parser.ParseExprFrom(fset, "eval", expr, 0)
// ...
```

`parser.ParseExprFrom` 関数は、以下の引数を取ります。
*   `fset *token.FileSet`: 既存のファイルセット。`Eval` 関数に渡された `fset` をそのまま使用します。
*   `filename string`: パースする式が属する仮想的なファイル名。ここでは `"eval"` が指定されています。
*   `src interface{}`: パースするソースコード。ここでは `expr` (文字列) が渡されます。
*   `mode Mode`: パースモード。ここでは `0` (デフォルトモード) が指定されています。

この変更により、`Eval` 関数が評価する式の位置情報が、呼び出し元から提供された `fset` のコンテキスト内で管理されるようになります。結果として、式に型エラーがあった場合でも、`go/types` パッケージは `fset` を通じて正確なファイル名、行番号、列番号を含む診断情報を生成できるようになりました。

この修正は、Go 1.5の機能 (`parser.ParseExprFrom` がGo 1.5で導入されたか、その挙動が安定したため) に依存しているため、`x/tools/go/types` のような、より古いGoバージョンとの互換性を維持する必要があるリポジトリにはすぐには適用できませんでした。しかし、Go本体の `src/go/types` には、Go 1.5のリリースに合わせてこの修正が取り込まれることになりました。

## コアとなるコードの解説

この変更は非常に簡潔ですが、その影響は重要です。

1.  **削除されたコメント**:
    `BUG(gri)` で始まるコメントが削除されました。これは、このコミットによってコメントで指摘されていたバグが修正されたことを意味します。コメントは、型チェックエラー時に `go/types` が式の正しいファイルセットを持たないという問題を明確に記述しており、解決策として「渡された `fset` を使用する `ParseExpr` が必要」と示唆していました。まさにその解決策がこのコミットで実装されました。

2.  **`parser.ParseExpr` から `parser.ParseExprFrom` への変更**:
    *   **旧**: `node, err := parser.ParseExpr(expr)`
        *   `parser.ParseExpr` は、与えられた式文字列 `expr` をパースしますが、この関数は内部で新しい `token.FileSet` を作成して使用します。そのため、`Eval` 関数に引数として渡された `fset` とは独立したファイルセットが、パースされたASTノード (`node`) の位置情報に関連付けられていました。
    *   **新**: `node, err := parser.ParseExprFrom(fset, "eval", expr, 0)`
        *   `parser.ParseExprFrom` は、`Eval` 関数に渡された既存の `token.FileSet` (`fset`) を直接使用します。これにより、パースされた式 `expr` の位置情報が、`Eval` 関数が動作している全体のコンテキスト (`fset`) と一貫性を持つようになります。
        *   `"eval"` というファイル名は、この式が実際のファイルではなく、評価のために一時的に生成されたものであることを示唆する仮想的な名前です。
        *   `0` は、パースモードのフラグで、ここではデフォルトの挙動を意味します。

この変更により、`Eval` 関数が式を評価する際に、その式のソースコード上の位置情報が、`Eval` 関数が受け取った `token.FileSet` に正しく登録され、管理されるようになりました。これにより、型チェック中に発生する可能性のあるエラーメッセージが、正確なファイル名、行番号、列番号を報告できるようになり、デバッグや開発体験が向上します。

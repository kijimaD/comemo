# [インデックス 25047] ファイルの概要

このコミットは、Go言語のアセンブラツール `cmd/asm` の字句解析器 (`lexer`) に関連する変更を含んでいます。具体的には、以下の2つのファイルが変更されています。

*   `src/cmd/asm/internal/lex/input.go`: 字句解析器への入力処理を司るファイルです。主にソースコードの読み込み、トークン化、プリプロセッサディレクティブ（`#ifdef` など）やマクロの展開処理を担当します。このコミットでは、特にファイルの終端（EOF）処理とエラー報告の改善が行われています。
*   `src/cmd/asm/internal/lex/lex_test.go`: `input.go` で定義されている字句解析器のテストコードが含まれるファイルです。このコミットでは、新たにエラーケースを網羅するテストが追加されています。

## 変更の背景

Go言語のアセンブラ `cmd/asm` の字句解析器は、ソースコードをトークンに分割する役割を担っています。このプロセスにおいて、不正な入力や不完全なプリプロセッサディレクティブ（例: `#ifdef` が閉じられていない）が存在する場合、字句解析器がファイルの終端 (EOF) に到達しても適切なエラーを報告せず、無限ループに陥ったり、意味のない処理を続けたりする可能性がありました。

具体的には、以下のシナリオが問題となっていました。

1.  **未クローズのプリプロセッサディレクティブ**: `#ifdef` や `#ifndef` のような条件付きコンパイルディレクティブが、対応する `#endif` なしにファイルの終端に達した場合、字句解析器が無限にEOFを読み込もうとして停止してしまう。
2.  **不完全なマクロ定義**: `#define` でマクロを定義する際に、定義の最後に改行がない場合、字句解析器がEOFに到達してもエラーを適切に検出できず、予期せぬ動作を引き起こす。

これらの問題は、アセンブリコードのコンパイル時にユーザーに混乱を招き、デバッグを困難にするため、より堅牢なEOF処理と明確なエラー診断が求められていました。このコミットは、これらの問題を解決し、アセンブラの信頼性とユーザビリティを向上させることを目的としています。

## 前提知識の解説

### Goのアセンブラ (`cmd/asm`)

`cmd/asm` は、Go言語のツールチェーンの一部として提供されるアセンブラです。Go言語のランタイムや標準ライブラリの一部は、パフォーマンスが重要な部分でGoアセンブリ言語（Plan 9アセンブリの派生）で記述されており、`cmd/asm` はこれらのアセンブリコードを機械語に変換するために使用されます。

### 字句解析 (Lexing/Tokenizing)

字句解析は、コンパイラやインタプリタの最初のフェーズです。ソースコードの文字列を読み込み、意味のある最小単位である「トークン」（キーワード、識別子、演算子、リテラルなど）のストリームに変換します。このコミットで変更されている `input.go` は、この字句解析の入力部分を管理しています。

### `scanner.EOF`

Go言語の標準ライブラリ `text/scanner` パッケージは、字句解析器を実装するためのユーティリティを提供します。`scanner.EOF` は、字句解析器が入力ストリームの終端に達したことを示す特別な定数です。字句解析器は通常、EOFを検出すると処理を停止するか、特別な方法で処理します。

### プリプロセッサディレクティブ (`#ifdef`, `#ifndef`, `#else`, `#endif`)

アセンブリ言語のソースコードでも、C言語のようにプリプロセッサディレクティブが使用されることがあります。これらはコンパイル前にソースコードを条件付きで含めたり除外したりするために使われます。

*   `#ifdef SYMBOL`: `SYMBOL` が定義されていれば、その後のコードを含める。
*   `#ifndef SYMBOL`: `SYMBOL` が定義されていなければ、その後のコードを含める。
*   `#else`: `#ifdef` または `#ifndef` の条件が偽だった場合に含めるコードを指定する。
*   `#endif`: 条件付きコンパイルブロックの終わりを示す。

これらのディレクティブはネストされることがあり、字句解析器は `ifdefStack` のような内部スタックを使って、現在どの条件付きブロック内にいるかを追跡します。

### マクロ定義 (`#define`)

`#define` ディレクティブは、テキスト置換を行うためのマクロを定義します。例えば、`#define FOO BAR` と定義すると、以降のコード中の `FOO` は `BAR` に置換されます。マクロ定義は通常、改行で終了します。

### `panic` と `recover`

Go言語におけるエラーハンドリングのメカニズムの一つです。

*   **`panic`**: プログラムの実行を中断し、現在のゴルーチンスタックをアンワインドします。通常、回復不能なエラーやプログラマの論理的誤りを示すために使用されます。
*   **`recover`**: `panic` から回復し、パニックしたゴルーチンの制御を取り戻すために `defer` 関数内で使用されます。これにより、プログラムがクラッシュするのを防ぎ、エラーを処理したり、クリーンアップを行ったりすることができます。

このコミットでは、テスト時に `os.Exit(1)` でプログラムが終了してしまうのを防ぎ、テストコード内でエラーメッセージを検証するために `panic` と `recover` が活用されています。

    func TestBadLex(t *testing.T) {

    		}

    		}

    このテスト関数は `badLexTests` スライスをループし、各テストケースに対して以下の処理を行います。
    *   `NewInput` と `NewTokenizer` を使って新しい字句解析器の入力ストリームを作成します。
    *   `firstError` ヘルパー関数を呼び出して、入力処理中に発生する最初のエラーを捕捉します。
    *   エラーが全く発生しなかった場合、または期待されるエラーメッセージが含まれていない場合にテストを失敗させます。

4.  **`firstError` ヘルパー関数の追加**:
    ```go
    func firstError(input *Input) (err error) {
    	panicOnError = true
    	defer func() {
    		panicOnError = false
    		switch e := recover(); e := e.(type) {
    		case nil:
    		case error:
    			err = e
    		default:
    			panic(e)
    		}
    	}()

    	for {
    		tok := input.Next()
    		if tok == scanner.EOF {
    			return
    		}
    	}
    }
    ```
    この重要なヘルパー関数は、`TestBadLex` から呼び出され、エラーテストを可能にします。
    *   `panicOnError = true` を設定することで、`Input.Error` が `panic` を発生させるようにします。
    *   `defer` 関数内で `recover()` を使用し、`Input.Error` が発生させた `panic` を捕捉します。これにより、テストが `os.Exit(1)` で終了するのを防ぎ、`panic` の値（エラーオブジェクト）を `err` 変数に代入して呼び出し元に返します。
    *   無限ループで `input.Next()` を呼び出し続け、`scanner.EOF` に到達するか、`panic` が発生するまで処理を続けます。

これらの変更により、`cmd/asm` の字句解析器は、不正な入力に対する堅牢性が向上し、開発者やユーザーに対してより具体的で役立つエラーメッセージを提供できるようになりました。また、`panicOnError` と `firstError` の導入により、エラーパスのテストが容易になり、将来的な回帰を防ぐための基盤が強化されました。

## コアとなるコードの解説

### `src/cmd/asm/internal/lex/input.go` の変更点

1.  **`panicOnError` の導入と `Input.Error` の変更**:
    *   `var panicOnError bool` は、テスト時にエラー処理の挙動を切り替えるためのフラグです。通常、`Input.Error` は `os.Exit(1)` を呼び出してプログラムを終了させますが、テスト中にこれが行われると、テストスイート全体が停止してしまいます。
    *   `Input.Error` メソッド内の `if panicOnError { ... panic(...) }` ブロックは、この問題を解決します。`panicOnError` が `true` の場合、`os.Exit(1)` の代わりに `panic` を発生させます。これにより、テストコード内で `recover` を使用してこの `panic` を捕捉し、エラーメッセージを検証することが可能になります。これは、Go言語でエラーをテストする際の一般的なイディオムです。

2.  **`Input.Next()` での未クローズのプリプロセッサディレクティブの検出**:
    *   `if tok == scanner.EOF && len(in.ifdefStack) > 0 { ... }` の追加は、字句解析器が入力の終端に達した (`tok == scanner.EOF`) にもかかわらず、まだ未処理のプリプロセッサディレクティブ（`#ifdef` や `#ifndef`）が存在することを示す `ifdefStack` が空でない (`len(in.ifdefStack) > 0`) 状況を検出します。
    *   このような状況は、ソースコードに `#endif` が不足していることを意味します。以前は、この状態で無限ループに陥る可能性がありましたが、この変更により `in.Error("unclosed #ifdef or #ifndef")` が呼び出され、明確なエラーメッセージとともに処理が停止するようになりました。これにより、デバッグが容易になります。

3.  **`Input.macroDefinition()` でのマクロ定義の改行不足の検出**:
    *   `for tok != '\n' { ... if tok == scanner.EOF { ... } }` の追加は、マクロ定義の解析中に `scanner.EOF` に到達した場合の処理です。マクロ定義は通常、改行で終了することが期待されます。
    *   もし改行が見つかる前にファイルの終端に達した場合、それは不完全なマクロ定義を意味します。この変更により `in.Error("missing newline in macro definition for %q\n", name)` が呼び出され、マクロ定義が正しく終了していないことをユーザーに通知します。これも、無限ループや予期せぬ動作を防ぎ、診断を改善します。

### `src/cmd/asm/internal/lex/lex_test.go` の変更点

1.  **`badLexTest` 構造体と `badLexTests` スライス**:
    *   これらは、様々な不正な入力パターンと、それらに対して期待されるエラーメッセージを構造化して定義するためのものです。これにより、多様なエラーケースを網羅的にテストできます。
    *   特に、未クローズの `#ifdef` やマクロ定義の改行不足といった、`input.go` で修正された問題に対応するテストケースが含まれています。

2.  **`TestBadLex` 関数**:
    *   このテスト関数は、`badLexTests` に定義された各不正な入力に対して、字句解析器が期待通りにエラーを発生させるかを検証します。
    *   `firstError(input)` を呼び出すことで、`Input.Error` が `panic` した際にそのエラー値を捕捉し、`strings.Contains(err.Error(), test.error)` でエラーメッセージが期待される部分文字列を含んでいるかを確認します。これにより、エラーの発生だけでなく、その内容も正確に検証できます。

3.  **`firstError` ヘルパー関数**:
    *   この関数は、`TestBadLex` の中核をなす部分です。
    *   `panicOnError = true` を設定することで、テスト対象のコードが `panic` を発生させるようにします。
    *   `defer` と `recover` の組み合わせは、Go言語で `panic` を捕捉し、エラーとして処理するための標準的なパターンです。`input.Next()` をループで呼び出し、字句解析器が `scanner.EOF` に到達するか、`panic` を発生させるまで実行します。`panic` が発生した場合、`recover` がそれを捕捉し、`err` 変数に代入して返します。
    *   これにより、`TestBadLex` は `os.Exit(1)` によるテストの中断を回避し、発生したエラーをプログラム的に検査できるようになります。

これらの変更は、`cmd/asm` の字句解析器の堅牢性を大幅に向上させ、開発者がアセンブリコードの構文エラーをより迅速かつ正確に特定できるようにするための重要な改善です。

## 変更の背景

このコミットは、Goの `net/http` パッケージにおける `MaxBytesReader` の挙動に関するバグ、具体的にはIssue #10884を修正するために導入されました。

`MaxBytesReader` は、HTTPリクエストボディの最大サイズを制限するために使用されます。このリーダーは、指定されたバイト数を超えて読み取ろうとするとエラーを返すべきです。しかし、以前の実装では、いくつかの特定のシナリオ、特に基礎となる `io.Reader` がEOFを報告する方法の曖昧さにより、問題が発生していました。

問題の核心は、`io.Reader` の `Read` メソッドが `(0, io.EOF)` を返すか、または `(n > 0, nil)` を返した後に次の呼び出しで `(0, io.EOF)` を返すか、といったEOFの報告方法が実装によって異なる点にありました。この曖昧さのため、`MaxBytesReader` は、設定された最大バイト数と完全に一致するサイズのボディを読み取った場合や、わずかに超過した場合に、EOFを正しく処理できず、誤って「リクエストボディが大きすぎる」というエラーを報告してしまうことがありました。

この修正は、`MaxBytesReader` がEOFの状態をより正確に追跡し、リクエストボディが実際に制限を超えた場合と、単に読み取りが完了してEOFに達した場合とを区別できるようにすることを目的としています。

## 前提知識の解説

*   **`io.Reader` インターフェース**: Goにおけるデータの読み取り操作を抽象化する基本的なインターフェースです。`Read([]byte) (n int, err error)` メソッドを持ち、`n` は読み取られたバイト数、`err` はエラー（通常は `nil` または `io.EOF`）を示します。
*   **`io.EOF`**: `io.Reader` の `Read` メソッドが、それ以上読み取るデータがないことを示すために返す特別なエラー値です。通常、`Read` は `(0, io.EOF)` を返しますが、一部の実装では、最後のデータブロックを読み取った際に `(n > 0, io.EOF)` を返し、その後の呼び出しで `(0, io.EOF)` を返すことがあります。
*   **`net/http.MaxBytesReader`**: HTTPリクエストボディの読み取りをラップし、指定された最大バイト数を超えて読み取ろうとするとエラーを返す `io.ReadCloser` の実装です。これにより、悪意のある大きなリクエストボディによるサービス拒否攻撃（DoS攻撃）を防ぐことができます。
*   **HTTPリクエストボディ**: クライアントがサーバーに送信するデータの一部で、POSTリクエストなどで使用されます。

## 技術的詳細

この修正は、`maxBytesReader` 構造体に `sawEOF` という新しいブール型フィールドを導入し、`Read` メソッドのロジックを大幅に改善することで、EOF処理の正確性を高めています。

1.  **`sawEOF` フィールドの導入**:
    *   `maxBytesReader` 構造体に `sawEOF bool` が追加されました。これは、基礎となるリーダーが一度でも `io.EOF` を返したかどうかを追跡するために使用されます。

2.  **`tooLarge()` ヘルパーメソッドの導入**:
    *   `tooLarge()` という新しいメソッドが追加され、リクエストボディが大きすぎる場合に共通のエラー処理ロジック（`l.stopped` の設定と `res.requestTooLarge()` の呼び出し）をカプセル化します。これにより、コードの重複が減り、可読性が向上します。

3.  **`Read` メソッドのロジック変更**:
    *   **初期チェックの変更**: 以前は `l.n <= 0` で即座にエラーを返していましたが、新しいロジックでは `toRead := l.n` を設定し、`l.n == 0` の場合に `l.sawEOF` をチェックします。
    *   **EOF時の特殊処理**: `l.n == 0` (つまり、残りの読み取り可能バイト数がゼロ) の場合、もし `l.sawEOF` が `true` であれば、それは正当なEOFであり、`tooLarge()` を呼び出してエラーを返します。しかし、`l.sawEOF` が `false` の場合、基礎となる `io.Reader` が `(0, io.EOF)` を返さない可能性があるため、`toRead` を `1` に設定して1バイトだけ読み取ろうとします。これは、`io.Reader` のドキュメントが `Read` が0バイトを要求された場合の戻り値について曖昧であること、および一部の実装（`bytes.Reader` や `strings.Reader` など）がEOFでも `(0, nil)` を返すことがあるという問題に対処するためです。
    *   **読み取りバッファの調整**: `if int64(len(p)) > toRead { p = p[:toRead] }` により、実際に読み取るバッファサイズが `toRead` を超えないように調整されます。
    *   **EOFの追跡**: `n, err = l.r.Read(p)` の呼び出し後、`if err == io.EOF { l.sawEOF = true }` によって `sawEOF` フラグが設定されます。
    *   **制限超過の最終チェック**: 読み取り後、もし `l.n == 0` (読み取り前の残りのバイト数がゼロだった) かつ `n > 0` (それでもバイトが読み取られた) であれば、それはリクエストボディが設定された制限を実際に超過したことを明確に示しているため、`tooLarge()` を呼び出します。そうでなければ、`0, err` を返します。
    *   **残りのバイト数の更新**: `l.n -= int64(n)` で残りのバイト数を減らし、`if l.n < 0 { l.n = 0 }` で負の値にならないようにします。

これらの変更により、`MaxBytesReader` は、基礎となるリーダーがEOFをどのように報告するかに関わらず、設定された最大バイト数を超過した場合のみ「リクエストボディが大きすぎる」エラーを返し、そうでない場合は正しくEOFを伝播するようになります。

## コアとなるコードの変更箇所

### `src/net/http/request.go`

```go
type maxBytesReader struct {
	r       io.ReadCloser // underlying reader
	n       int64         // max bytes remaining
	stopped bool
	sawEOF  bool // 新しく追加されたフィールド
}

// tooLarge メソッドの追加
func (l *maxBytesReader) tooLarge() (n int, err error) {
	if !l.stopped {
		l.stopped = true
		if res, ok := l.w.(*response); ok {
			res.requestTooLarge()
		}
	}
	return 0, errors.New("http: request body too large")
}

func (l *maxBytesReader) Read(p []byte) (n int, err error) {
	toRead := l.n
	if l.n == 0 {
		if l.sawEOF {
			return l.tooLarge() // EOFが既に検出されている場合は、tooLargeを返す
		}
		// 基礎となるio.Readerが0バイト要求時に(0, io.EOF)を返さない場合があるため、1バイト読み取る
		toRead = 1
	}
	if int64(len(p)) > toRead {
		p = p[:toRead]
	}
	n, err = l.r.Read(p)
	if err == io.EOF {
		l.sawEOF = true // EOFを検出したことを記録
	}
	if l.n == 0 {
		// 読み取り前の残りのバイト数がゼロだったにもかかわらず、バイトが読み取られた場合
		if n > 0 {
			return l.tooLarge() // 制限を超過したと判断
		}
		return 0, err // そうでなければ、0バイトとエラーを返す (EOFを含む)
	}
	l.n -= int64(n)
	if l.n < 0 {
		l.n = 0
	}
	return
}
```

## コアとなるコードの解説

`maxBytesReader` の `Read` メソッドは、リクエストボディの読み取りを制御する中心的なロジックを含んでいます。

1.  **`sawEOF` フィールド**: このフラグは、基礎となるリーダーが `io.EOF` を返したかどうかを記憶します。これにより、`MaxBytesReader` は、読み取り制限に達した後にさらに読み取り要求があった場合に、それが真のEOFによるものなのか、それとも制限超過によるものなのかを区別できます。
2.  **`tooLarge()` メソッド**: このメソッドは、リクエストボディが最大サイズを超過したと判断された場合に呼び出されます。これにより、エラーメッセージの一貫性が保たれ、関連する内部状態（`l.stopped`）が適切に設定されます。
3.  **`Read` メソッドの新しいフロー**:
    *   `l.n == 0` かつ `l.sawEOF` の場合、これは既にEOFに達しており、これ以上読み取るデータがないことを意味します。この場合、`tooLarge()` を呼び出すことで、これ以上の読み取り試行は制限超過と見なされます。
    *   `l.n == 0` だが `l.sawEOF` でない場合、基礎となるリーダーが `(0, io.EOF)` を返さない可能性を考慮し、`toRead` を `1` に設定して1バイトの読み取りを試みます。これにより、リーダーが実際にEOFに達しているかどうかを確実に確認できます。
    *   読み取り後、`err == io.EOF` であれば `l.sawEOF = true` を設定し、EOF状態を記録します。
    *   最も重要なのは、`l.n == 0` (読み取り前の残りのバイト数がゼロ) の状態で `n > 0` (実際にバイトが読み取られた) となった場合です。これは、リクエストボディが設定された制限を実際に超過したことを明確に示しているため、`tooLarge()` が呼び出されます。

`request_test.go` に追加された `delayedEOFReader` は、この修正が対処する具体的なエッジケースをシミュレートするために不可欠です。このリーダーは、`io.Reader` の一部の実装が `(n > 0, io.EOF)` を返さず、代わりに `(n > 0, nil)` を返し、その後の呼び出しで `(0, io.EOF)` を返すという挙動を模倣します。`TestIssue10884_MaxBytesEOF` は、このような状況下でも `MaxBytesReader` が正しく動作し、不必要なエラーを発生させないことを検証します。

この修正により、`MaxBytesReader` はより堅牢になり、さまざまな `io.Reader` の実装やEOFの報告方法に起因する潜在的な問題を回避できるようになりました。

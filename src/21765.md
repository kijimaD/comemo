# [インデックス 21765] ファイルの概要

このコミットは、Goツールチェーン内のアセンブラ（`6a`）およびCコンパイラ（`cmd/cc`）のレキサーにおける行番号の誤りを修正するものです。特に、`#ifdef`、`#else`、`#endif`といったプリプロセッサディレクティブを含む行が正しく行番号をインクリメントしていなかった問題に対処し、アセンブリファイルにおけるデバッグ情報の精度を向上させます。

## 変更の背景

Goのツールチェーン、特にアセンブラ（かつて`6a`として知られていたもの）は、生成されるアセンブリコードに元のソースコードの行番号情報を含めます。これは、デバッグ時やプロファイリング時に、アセンブリコードがGoのどのソース行に対応しているかを特定するために非常に重要です。

しかし、このコミット以前は、アセンブリファイル内で`#ifdef`、`#else`、`#endif`といったC言語スタイルのプリプロセッサディレクティブが使用されている場合、これらの行がレキサーによって正しく行番号のインクリメントとして認識されていませんでした。その結果、これらのディレクティブの後に続くコードの行番号が、実際よりも少なく記録されてしまうというバグがありました。コミットメッセージの例では、4行分のプリプロセッサディレクティブの後に続く`TEXT ·use(SB),7,$0`の行番号が、本来よりも4つ低い値で記録されていたことが示されています。この不正確な行番号情報は、`6a -S`の出力やバイナリ内のランタイム情報に影響を与え、デバッグの妨げとなっていました。

このコミットは、この行番号の不整合を解消し、アセンブリファイルにおける正確なソースコードマッピングを保証することを目的としています。

## 前提知識の解説

### Goアセンブリとプリプロセッサディレクティブ

Goのアセンブラは、C/C++のようなフル機能のプリプロセッサ（`#define`や`#include`など）を直接サポートしていません。Goのビルドシステムは、ビルドタグ（例: `// +build linux,amd64`）や`go_asm.h`といったメカニズムを通じて、条件付きコンパイルやGoの型情報へのアクセスを提供します。

しかし、このコミットが`#ifdef`、`#else`、`#endif`といったC言語スタイルのプリプロセッサディレクティブを扱っていることは、Goツールチェーン内の特定のコンポーネント（特に`cmd/cc`や`cmd/internal/asm`のレキサー）が、これらのディレクティブを何らかの形で認識し、処理する必要があることを示唆しています。これは、GoがC言語のコードと連携する`cgo`のような機能を持つため、あるいはアセンブリコード自体が特定のプラットフォーム向けに条件付きでコンパイルされる必要があるためと考えられます。

### レキサーと行番号管理

レキサー（またはスキャナー、トークナイザー）は、コンパイラのフロントエンドの一部であり、ソースコードを文字のストリームとして読み込み、それを意味のある最小単位である「トークン」に分割する役割を担います。例えば、キーワード、識別子、演算子、リテラルなどがトークンに該当します。

コンパイラやデバッグツールにとって、各トークンがソースコードのどの位置（ファイル名、行番号、列番号）にあるかを正確に知ることは非常に重要です。これは、エラーメッセージの表示、デバッガでのステップ実行、プロファイリング情報のマッピングなどに不可欠です。

レキサーが行番号を管理する一般的な方法の一つは、入力ストリームから文字を読み込む際に、改行文字（`\n`）を検出するたびに行番号カウンターをインクリメントすることです。このコミットの文脈では、この基本的なメカニズムが特定の条件下で機能していなかったことが問題でした。

### `6a`アセンブラ

`6a`は、Goの初期のバージョンで使用されていたアセンブラの名称です。これは、Plan 9オペレーティングシステムのアセンブラに由来しています。現代のGoツールチェーンでは、`go tool compile`や`go tool asm`といったコマンドを通じてアセンブリコードが処理されますが、その内部的な動作や概念は`6a`の時代から引き継がれています。

`6a`（および現在のGoアセンブラ）は、`-S`フラグを付けて実行すると、Goのソースコードと対応するアセンブリ命令を並べて表示する機能を持ちます。この出力には、各アセンブリ命令がGoソースコードのどのファイル、どの行から生成されたかを示す情報が含まれており、開発者がGoプログラムの低レベルな動作を理解する上で非常に役立ちます。この行番号情報が不正確であると、デバッグやパフォーマンス分析の際に大きな混乱を招きます。

## 技術的詳細

この問題は、Goツールチェーン内の2つの主要なレキサー、すなわち`src/cmd/cc/lexbody`（Cコンパイラ関連）と`src/cmd/internal/asm/lexbody.go`（Goアセンブラ関連）に共通して存在していました。これらのレキサーは、文字を読み取るための`getc`関数と、読み取った文字を一時的に保持する`peekc`（または`peekc`に相当するメカニズム）を使用していました。

問題の核心は、`#ifdef`などのプリプロセッサディレクティブを含む行が処理される際に、レキサーが改行文字を読み取っても、その行が「コード」として認識されないために行番号がインクリメントされない、という点にありました。レキサーは、文字を読み取る際に`getc`関数を使用し、この関数内で`peekc`に文字が格納されている場合はそれを返し、そうでない場合は実際に新しい文字を読み込みます。

修正前のコードでは、`peekc`に文字が格納されている場合、その文字が改行文字であっても`lineno`（または`Lineno`）がインクリメントされませんでした。これは、`peekc`から文字が「消費」される際に、それが新しい行の始まりであるという認識が欠けていたためです。

また、`unget`という概念も重要です。これは、一度読み取った文字を再び入力ストリームに戻す操作です。レキサーが特定のパターンを認識するために先読み（peek）を行い、その文字が現在のトークンの一部ではないと判断した場合に、その文字をストリームに戻すために使用されます。修正前のコードでは、`peekc = c`という代入が行われていましたが、これは文字を「戻す」というよりは、単に次の`getc`呼び出しのために文字を「先読み」している状態でした。この処理が、行番号の正確な管理を妨げていた可能性があります。

## コアとなるコードの解説

このコミットの修正は、レキサーが行番号を管理する方法における根本的な改善です。

1.  **`if(c == '\n') lineno++;` (または `if c == '\n' { Lineno++ }`) の追加**:
    この変更は、`getc`関数が`peekc`から文字を返す際にも、その文字が改行文字であれば行番号をインクリメントするようにします。以前は、`peekc`に格納された文字が改行文字であっても、それが「新しい文字の読み込み」として扱われなかったため、行番号が更新されませんでした。特に`#ifdef`のようなプリプロセッサディレクティブの行は、レキサーが特別な処理を行うため、通常のコード行とは異なるパスで処理されることがあり、その際に改行文字の処理が見落とされがちでした。この修正により、`peekc`から文字が消費されるタイミングで、それが改行文字であれば必ず行番号がインクリメントされるようになり、プリプロセッサディレクティブの行も正しくカウントされるようになりました。

2.  **`peekc = c;` から `unget(c);` への変更/追加**:
    `src/cmd/cc/lexbody`では`peekc = c;`が`unget(c);`に置き換えられ、`src/cmd/internal/asm/lexbody.go`では`peekc = c`の後に`unget(c)`が追加されました。
    これは、レキサーの内部状態と行番号の同期を改善するための重要な変更です。`peekc = c`は、文字を「先読み」して次の`getc`呼び出しのために保持する動作ですが、これは文字が実際に「消費」されたわけではありません。`unget(c)`を使用することで、文字が一度読み取られた後、必要に応じて入力ストリームに「戻される」という明確なセマンティクスが導入されます。これにより、文字が実際に処理され、行番号のインクリメントが必要なタイミングがより正確に管理されるようになります。特に、レキサーが特定のパターンを認識するために文字を先読みし、その文字が現在のトークンの一部ではないと判断した場合に、`unget`によって文字をストリームに戻すことで、行番号の計算が混乱することなく、後続の処理でその文字が正しく再読み込みされるようになります。

これらの変更により、レキサーはプリプロセッサディレクティブを含む行であっても、改行文字を正確に検出し、行番号をインクリメントするようになりました。これにより、`6a -S`の出力やバイナリ内のランタイム情報における行番号の精度が向上し、Goのアセンブリコードのデバッグと分析がより容易になりました。

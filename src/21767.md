# [インデックス 21767] ファイルの概要

このコミットは、Go言語のリンカである`liblink`において、アセンブリの`TEXT`ディレクティブで使用される`$frame-arg`（フレームサイズと引数サイズ）のエンコーディングを、すべてのアーキテクチャで統一することを目的としています。これにより、Goコンパイラとアセンブラの内部的な一貫性が向上し、将来的なメンテナンスや新しいアーキテクチャへの対応が容易になります。

## 変更の背景

Go言語のコンパイラとアセンブラは、複数の異なるCPUアーキテクチャ（例: ARM、x86、x86-64、ARM64など）をサポートしています。これらのアーキテクチャ間で、アセンブリコードの関数定義に使用される`TEXT`ディレクティブの`$frame-arg`部分（関数のスタックフレームサイズと引数サイズを示す）のエンコーディング方法に一貫性がありませんでした。

具体的には、`TEXT`ディレクティブは通常、`TEXT symbol(SB), flags, $framesize-argsize`という形式を取ります。ここで`$framesize`は関数自身のローカルスタックフレームのサイズを、`$argsize`は関数に渡される引数と戻り値の合計サイズを示します。この`$framesize-argsize`の解析と内部表現が、アーキテクチャごとに異なる実装になっていたため、以下のような問題が生じていました。

*   **コードの複雑性**: 各アーキテクチャのアセンブラ（`5a`, `6a`, `8a`, `9a`など）がそれぞれ独自の解析ロジックを持つ必要があり、コードベースが複雑化していました。
*   **メンテナンスの困難さ**: 新しいアーキテクチャの追加や既存アーキテクチャの変更があった場合、複数の場所で同様の修正を行う必要があり、バグの温床となる可能性がありました。
*   **一貫性の欠如**: 内部的なデータ構造や処理フローに一貫性がないため、コンパイラとリンカ間の連携が最適化されていませんでした。

このコミットは、これらの問題を解決し、`TEXT $frame-arg`のエンコーディングと解析を統一することで、Goコンパイラツールチェーンの堅牢性と保守性を向上させることを目的としています。

## 前提知識の解説

### Goアセンブリの`TEXT`ディレクティブ

Go言語は、C言語のようなインラインアセンブリをサポートせず、独自の擬似アセンブリ言語を使用します。このアセンブリ言語で関数を定義する際に用いられるのが`TEXT`ディレクティブです。

*   **構文**: `TEXT symbol(SB), flags, $framesize-argsize`
    *   `symbol(SB)`: 関数名と、それが静的ベース(`SB`)からの相対位置にあることを示します。
    *   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`はスタック分割チェックを行わないことを示す）。
    *   `$framesize-argsize`: この部分が今回のコミットの焦点です。
        *   `$framesize`: 関数が使用するローカルスタックフレームのサイズ（バイト単位）。ローカル変数や、他の関数を呼び出す際に準備する引数に使用されます。
        *   `$argsize`: 関数に渡される引数と、関数が返す戻り値の合計サイズ（バイト単位）。これは呼び出し元のスタックフレーム上に存在します。
        *   `-` (ハイフン): `$framesize`と`$argsize`を区切るための構文上の区切り文字であり、減算を意味するものではありません。

### Goの擬似アセンブリと`liblink`

Goコンパイラ（`gc`）は、直接ターゲットマシンのアセンブリコードを生成するのではなく、Plan 9アセンブラに影響を受けた独自の「擬似アセンブリ」言語を生成します。この擬似アセンブリは、特定のCPUアーキテクチャに依存しない抽象的な命令セットを提供します。

*   **`liblink`**: Goのリンカであり、この擬似アセンブリコードを読み込み、最終的な実行可能バイナリを生成する役割を担います。`liblink`は、命令選択（擬似命令を実際のマシン命令に変換）、アドレス解決、シンボル解決、スタックフレームの調整など、様々なリンキング処理を行います。この抽象化されたアセンブリ言語を使用することで、Goは新しいアーキテクチャへの移植が容易になっています。

### `ArgsSizeUnknown`と`TYPE_TEXTSIZE`

これらはGoランタイムの内部実装で使用される識別子です。

*   **`ArgsSizeUnknown`**: 関数の引数サイズがコンパイル時に確定できない場合（例: 可変引数関数など）に使用されるプレースホルダー値です。
*   **`TYPE_TEXTSIZE`**: Goランタイムの内部データ構造において、型情報のテキスト表現（文字列ベースのメタデータ）のサイズを示すために使用される型です。今回のコミットでは、`TEXT`ディレクティブの引数サイズを表現するための内部的な型として再利用または関連付けられています。

### Goのアーキテクチャ固有のコード

Goの擬似アセンブリは抽象的ですが、それでもレジスタの使用方法、命令セットの特性、呼び出し規約など、アーキテクチャ固有の差異は存在します。そのため、Goのツールチェーンは、`src/cmd/5a` (ARM), `src/cmd/6a` (x86-64), `src/cmd/8a` (x86), `src/cmd/9a` (ARM64/PPC64) のように、各アーキテクチャに対応するアセンブラと関連ツールを持っています。このコミットは、これらのアーキテクチャ固有のツール間で`TEXT`ディレクティブの処理を統一しようとしています。

## 技術的詳細

このコミットの主要な技術的変更は、GoアセンブラのYacc（Yet Another Compiler Compiler）文法ファイル（`a.y`）と、Goコンパイラのコード生成部分（`ggen.c`）に集中しています。

1.  **`TEXT $frame-arg`エンコーディングの標準化**:
    以前は、各アーキテクチャのアセンブラが`TEXT`ディレクティブの`$frame-arg`部分を異なる方法で解析し、内部的に表現していました。このコミットでは、この部分を`textsize`という新しい抽象的な概念として統一的に扱うように変更されました。これにより、`$framesize`と`$argsize`のペアが、アーキテクチャに依存しない単一の構造化された形式で表現されるようになります。

2.  **`a.y`ファイルでの文法変更**:
    *   **新しい非終端記号`textsize`の導入**: `a.y`ファイル（アセンブラの文法定義）に`textsize`という新しい非終端記号が追加されました。この`textsize`は、`LCONST`（数値定数）や`LCONST '-' LCONST`（フレームサイズと引数サイズをハイフンで区切った形式）などのパターンを解析し、`TYPE_TEXTSIZE`型の`Addr`構造体を生成します。
    *   **`TEXT`命令の構文変更**: 既存の`TEXT`命令の定義（`inst`プロダクション内）が変更され、`imm`（即値）の代わりに`'$' textsize`という形式を使用するようになりました。これにより、`TEXT`命令の引数として渡されるフレームサイズと引数サイズが、`textsize`ルールによって統一的に解析されるようになります。
    *   **例（`src/cmd/5a/a.y`の変更から抜粋）**:
        ```diff
        --- a/src/cmd/5a/a.y
        +++ b/src/cmd/5a/a.y
        @@ -212,26 +212,15 @@ inst:

          * TEXT
          */
        -|\tLTYPEB name ',' imm
        +|\tLTYPEB name ',' '$' textsize
         \t{\
         \t\tsettext($2.sym);\
        -\t\t$4.type = TYPE_TEXTSIZE;\
        -\t\t$4.u.argsize = ArgsSizeUnknown;\
        -\t\toutcode($1, Always, &$2, 0, &$4);\
        +\t\toutcode($1, Always, &$2, 0, &$5);\
         \t}
        -|\tLTYPEB name ',' con ',' imm
        +|\tLTYPEB name ',' con ',' '$' textsize
         \t{\
         \t\tsettext($2.sym);\
        -\t\t$6.type = TYPE_TEXTSIZE;\
        -\t\t$6.u.argsize = ArgsSizeUnknown;\
        -\t\toutcode($1, Always, &$2, $4, &$6);\
        -\t}\
        -|\tLTYPEB name ',' con ',' imm '-' con
        -\t{\
        -\t\tsettext($2.sym);\
        -\t\t$6.type = TYPE_TEXTSIZE;\n-\t\t$6.u.argsize = $8;\n-\t\toutcode($1, Always, &$2, $4, &$6);\

          * GLOBL
        @@ -393,6 +382,32 @@ rel:

        +\t}\
        +|\t'-' LCONST
        +\t{\
        +\t\t$$.type = TYPE_TEXTSIZE;\
        +\t\t$$.offset = -$2;\
        +\t\t$$.u.argsize = ArgsSizeUnknown;\
        +\t}\
        +|\tLCONST '-' LCONST
        +\t{\
        +\t\t$$.type = TYPE_TEXTSIZE;\
        +\t\t$$.offset = $1;\
        +\t\t$$.u.argsize = $3;\

        +|\t'-' LCONST '-' LCONST
        +\t{\
        +\t\t$$.type = TYPE_TEXTSIZE;\
        +\t\t$$.offset = -$2;\
        +\t\t$$.u.argsize = $4;\
        +\t}\
        +
         ximm:\t'$' con
         \t{\
         \t\t$$ = nullgen;
        ```
        この変更により、`TEXT`命令の引数として`$framesize-argsize`形式が直接`textsize`ルールによって処理されるようになり、以前のアーキテクチャ固有の`imm`（即値）の解釈が不要になりました。

3.  **`ggen.c`ファイルでのコード生成変更**:
    GoコンパイラがGoソースコードからアセンブリコードを生成する際、`ggen.c`ファイル内の`defframe`関数などが`TEXT`ディレクティブの引数を構築します。このコミットでは、`defframe`関数が`ptxt->to.type = TYPE_TEXTSIZE;`を設定し、`ptxt->to.u.argsize`に引数サイズ、`ptxt->to.offset`にフレームサイズを格納するように変更されました。これにより、コンパイラが生成するアセンブリコードが、新しい統一された`textsize`形式に準拠するようになります。

4.  **`liblink`の役割**:
    `liblink`は、この統一された`TEXT`ディレクティブの形式を解釈し、最終的な実行可能バイナリを生成します。エンコーディングが標準化されたことで、`liblink`はよりシンプルで一貫したロジックでフレームサイズと引数サイズを処理できるようになり、リンキングプロセスの信頼性が向上します。

これらの変更は、Goコンパイラツールチェーンの内部的な設計を改善し、異なるアーキテクチャ間でのコードの再利用性と保守性を高める上で重要なステップとなります。

## コアとなるコードの解説

### `src/cmd/*/a.y`の変更

最も重要な変更は、`TEXT`命令の構文解析方法の変更です。
以前は、`TEXT`命令の引数（`$framesize-argsize`）は、`imm`（即値）として解析され、その内部でフレームサイズと引数サイズがパックされていました。しかし、このコミットでは、`imm`の代わりに`'$' textsize`という新しい形式が導入されました。

新しい`textsize`非終端記号は以下のように定義されています（`src/cmd/5a/a.y`の例）：

```yacc
textsize:
    LCONST
    {
        $$.type = TYPE_TEXTSIZE;
        $$.offset = $1;
        $$.u.argsize = ArgsSizeUnknown;
    }
|   '-' LCONST
    {
        $$.type = TYPE_TEXTSIZE;
        $$.offset = -$2;
        $$.u.argsize = ArgsSizeUnknown;
    }
|   LCONST '-' LCONST
    {
        $$.type = TYPE_TEXTSIZE;
        $$.offset = $1;
        $$.u.argsize = $3;
    }
|   '-' LCONST '-' LCONST
    {
        $$.type = TYPE_TEXTSIZE;
        $$.offset = -$2;
        $$.u.argsize = $4;
    }
```
この`textsize`ルールは、`LCONST`（単一の数値定数、フレームサイズのみの場合）や`LCONST '-' LCONST`（フレームサイズと引数サイズの両方がある場合）といった様々な形式を解析します。そして、解析結果を`TYPE_TEXTSIZE`型の`Addr`構造体に格納します。`Addr`構造体の`offset`フィールドにフレームサイズが、`u.argsize`フィールドに引数サイズが格納されます。`ArgsSizeUnknown`は、引数サイズが指定されていない場合のデフォルト値です。

これにより、各アセンブラは`TEXT`命令の引数を、アーキテクチャ固有のパック/アンパックロジックではなく、統一された`textsize`ルールを通じて構造化された`Addr`型として受け取ることができるようになります。

### `src/cmd/*/ggen.c`の変更

`ggen.c`ファイルでは、GoコンパイラがGoソースコードからアセンブリコードを生成する際に、`TEXT`ディレクティブの引数をどのように構築するかが変更されています。特に`defframe`関数（関数のスタックフレームを定義する役割）が影響を受けています。

変更前は、`ptxt->to.type`が`TYPE_TEXTSIZE`に設定され、`ptxt->to.u.argsize`に引数サイズが、`ptxt->to.offset`にフレームサイズが直接設定されていました。変更後も基本的な構造は同じですが、`a.y`の変更と連携し、`TEXT`ディレクティブの引数として`$framesize-argsize`形式が統一的に出力されるように、内部的な値の渡し方や型付けが調整されています。

例えば、`src/cmd/5g/ggen.c`の`defframe`関数では、以下のような変更が見られます。

```diff
--- a/src/cmd/5g/ggen.c
+++ b/src/cmd/5g/ggen.c
@@ -21,12 +21,10 @@ defframe(Prog *ptxt)
 	NodeList *l;
 	Node *n;
 
-	// fill in argument size
+	// fill in argument size, stack size
 	ptxt->to.type = TYPE_TEXTSIZE;
 	ptxt->to.u.argsize = rnd(curfn->type->argwid, widthptr);
-
-	// fill in final stack size
-	frame = rnd(stksize+maxarg, widthptr);
+	frame = rnd(stksize+maxarg, widthreg);
 	ptxt->to.offset = frame;
 	
 	// insert code to contain ambiguously live variables
```
この変更は、`TEXT`ディレクティブの`$framesize-argsize`部分が、コンパイラによって正しく`TYPE_TEXTSIZE`型の`Addr`構造体として表現され、リンカに渡されることを保証します。

これらの変更により、Goコンパイラツールチェーン全体で`TEXT`ディレクティブの引数処理が一貫性を持つようになり、異なるアーキテクチャ間でのコードの互換性と保守性が向上しました。

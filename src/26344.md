# [インデックス 26344] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/http`パッケージ内のHTTP/2実装に関連する`h2_bundle.go`ファイルを更新するものです。`h2_bundle.go`は、`net/http`パッケージが内部的に使用するHTTP/2プロトコルのクライアントおよびサーバーサイドの実装をバンドルしたファイルであり、GoのHTTP/2サポートの基盤となっています。このファイルは、主に`x/net/http2`パッケージから生成され、`net/http`パッケージに組み込まれています。

## コミット

このコミットは、`net/http2`パッケージのバンドルバージョンを更新し、特定のHTTP/2関連の問題を修正することを目的としています。具体的には、クライアントコネクションが既に閉じられている場合に、ストリームの削除処理が不適切に行われる可能性のあるバグに対処しています。

## 変更の背景

この変更は、GoのHTTP/2実装における既知のバグを修正するために行われました。コミットメッセージには`Fixes golang/go#13924`と`for https://golang.org/issue/18571`と記載されており、これらのissueがこの変更の直接的なトリガーとなっています。

一般的なシナリオとして、HTTP/2クライアントコネクションが閉じられた後も、そのコネクションに関連付けられたストリームが不適切に操作されると、ランタイムパニックや競合状態（race condition）が発生する可能性があります。特に、コネクションが閉じられた後に`streamByID`のようなメソッドがストリームを削除しようとすると、既に無効な状態のデータ構造にアクセスしようとして問題を引き起こすことがあります。このコミットは、このような状況を回避し、HTTP/2クライアントの堅牢性を向上させることを目的としています。

## 前提知識の解説

### HTTP/2 (Hypertext Transfer Protocol Version 2)
HTTP/2は、HTTP/1.1の後継となるプロトコルで、ウェブのパフォーマンスを向上させるために設計されました。主な特徴として以下が挙げられます。
*   **多重化 (Multiplexing)**: 一つのTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が軽減されます。
*   **ヘッダー圧縮 (Header Compression)**: HPACKという圧縮形式を使用して、HTTPヘッダーのサイズを削減します。
*   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーが関連するリソースをクライアントに送信できます。
*   **ストリーム (Stream)**: HTTP/2コネクション内で独立した双方向のバイトフローを指します。各リクエスト/レスポンスは独自のストリームIDを持ちます。

### Goの`net/http`パッケージ
Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。Go 1.6以降、`net/http`パッケージはHTTP/2をネイティブにサポートしており、特別な設定なしにHTTP/2通信を行うことができます。このHTTP/2サポートは、主に`x/net/http2`パッケージのコードを`net/http`パッケージ内にバンドルすることで実現されています。

### HTTP/2クライアントコネクションとストリーム管理
HTTP/2クライアントは、サーバーとの間に単一のTCPコネクションを確立し、そのコネクション上で複数のストリームを管理します。`http2ClientConn`構造体は、このコネクションの状態を管理し、`streams`マップを通じてアクティブなストリームを追跡します。各ストリームは一意のIDを持ち、リクエストとレスポンスのライフサイクルを管理します。コネクションが閉じられる際には、関連するすべてのストリームも適切にクリーンアップされる必要があります。

## 技術的詳細

このコミットの技術的な核心は、HTTP/2クライアントコネクションが既に閉じられている場合に、ストリームの削除処理が安全に行われるようにすることです。

`http2ClientConn`構造体には、コネクションの状態を示す`closed`フィールド（おそらく`bool`型）が存在すると推測されます。元のコードでは、`streamByID`メソッドがストリームを削除する際に、`andRemove`フラグと`cs != nil`（ストリームが存在すること）のみをチェックしていました。

```go
// 変更前
if andRemove && cs != nil {
    delete(cc.streams, id)
    close(cs.done)
}
```

このロジックの問題点は、`cc.streams`マップが、コネクションが閉じられた後もアクセスされる可能性があることです。コネクションが閉じられると、`cc.streams`マップは無効な状態になるか、あるいは他のゴルーチンによって同時に変更されている可能性があります。このような状況で`delete(cc.streams, id)`や`close(cs.done)`を実行しようとすると、以下のような問題が発生する可能性があります。

1.  **ランタイムパニック**: 既にクリーンアップされた、または無効なメモリ領域にアクセスしようとすると、Goランタイムがパニックを起こす可能性があります。
2.  **競合状態 (Race Condition)**: コネクションのクローズ処理とストリームの削除処理が同時に実行された場合、`cc.streams`マップへのアクセスが同期されていないと、データ破損や予期せぬ動作を引き起こす可能性があります。
3.  **デッドロック**: `cs.done`チャネルが既に閉じられている状態で再度`close`を呼び出すと、パニックが発生します。

このコミットでは、`!cc.closed`という条件を追加することで、これらの問題を解決しています。

```go
// 変更後
if andRemove && cs != nil && !cc.closed {
    delete(cc.streams, id)
    close(cs.done)
}
```

この変更により、ストリームの削除処理は、コネクションがまだアクティブ（閉じられていない）である場合にのみ実行されるようになります。これにより、閉じられたコネクションに対する不適切な操作が防止され、HTTP/2クライアントの安定性と堅牢性が向上します。

## コアとなるコードの解説

変更は`src/net/http/h2_bundle.go`ファイルの`streamByID`メソッド内で行われています。

`streamByID`メソッドは、特定のストリームIDを持つHTTP/2クライアントストリームを取得し、必要に応じてマップから削除する役割を担っています。このメソッドは、`cc.mu`ミューテックスを使用して、`cc.streams`マップへのアクセスを保護しています。

変更前のコードでは、ストリームを削除する条件は`andRemove && cs != nil`でした。
*   `andRemove`: ストリームを削除する必要があることを示すブールフラグ。
*   `cs != nil`: 指定されたIDのストリームがマップに存在すること。

このコミットによって、条件式に`&& !cc.closed`が追加されました。
*   `!cc.closed`: `http2ClientConn`インスタンスがまだ閉じられていないことを示す条件。`cc.closed`は、コネクションが閉じられたときに`true`に設定されるブールフィールドであると推測されます。

この追加された条件により、`delete(cc.streams, id)`と`close(cs.done)`の操作は、以下の**全ての**条件が満たされた場合にのみ実行されるようになります。
1.  ストリームを削除する必要がある (`andRemove`が`true`)。
2.  指定されたIDのストリームが実際に存在し、`cs`が`nil`ではない。
3.  そして最も重要なこととして、**HTTP/2クライアントコネクションがまだ閉じられていない** (`cc.closed`が`false`)。

この変更は、閉じられたコネクションに対してストリーム削除操作を行おうとすることによって発生する可能性のある、パニックや競合状態といった潜在的なバグを効果的に防ぎます。これにより、`net/http`パッケージのHTTP/2クライアント実装の堅牢性と信頼性が向上します。

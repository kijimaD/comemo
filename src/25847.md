## 変更の背景

この変更の背景には、マルチコアプロセッサ環境における並行処理の効率化という、現代のソフトウェア開発における重要な課題があります。従来のロックベースの同期メカニズム（ミューテックスなど）は、並行処理の安全性を保証する一方で、ロックの競合が発生すると性能が低下するという問題がありました。特に、ロックが頻繁に取得・解放されるような細かい粒度の同期では、オーバーヘッドが顕著になります。

IntelのTransactional Synchronization Extensions (TSX) は、この問題を解決するために導入されたハードウェア機能です。TSXは、ソフトウェアトランザクショナルメモリ（STM）の概念をハードウェアレベルで実装したもので、複数のスレッドが共有データにアクセスする際に、楽観的並行性制御（Optimistic Concurrency Control）を可能にします。これにより、競合が少ない場合にはロックのオーバーヘッドなしに並行処理を進め、競合が発生した場合にのみトランザクションをロールバックして再試行するというアプローチを取ることができます。

GoランタイムにTSX命令のサポートを追加することは、Goの並行処理プリミティブ（特にセマフォやミューテックス）の基盤を強化し、特定のワークロードにおいて性能向上をもたらす可能性を秘めています。コミットメッセージにある「will later be used for semaphore implementation」という記述は、この低レベルのハードウェアサポートが、Goのより高レベルな同期メカニズムの最適化に利用される計画があることを示唆しています。

## 前提知識の解説

### x86アセンブラとGoのツールチェイン

Go言語は、そのコンパイラとアセンブラを独自に持っています。`cmd/internal/obj/x86` は、Goのツールチェインの一部であり、x86アーキテクチャ向けのオブジェクトファイルを生成するアセンブラのバックエンドを構成しています。Goのソースコード（特に`runtime`パッケージ内の低レベルな部分）は、Goのアセンブラ言語（Plan 9アセンブラの派生）で書かれることがあり、このアセンブラが最終的に機械語に変換します。このコミットは、このアセンブラが新しいx86命令セットを認識し、正しく機械語に変換できるようにするための変更です。

### Transactional Synchronization Extensions (TSX)

TSXは、Intel Haswellマイクロアーキテクチャで導入されたx86命令セットの拡張機能です。主に以下の2つのコンポーネントから構成されます。

1.  **Restricted Transactional Memory (RTM)**:
    *   `XBEGIN`: トランザクションの開始をマークします。失敗した場合のフォールバックアドレスを指定します。
    *   `XEND`: トランザクションの成功終了をマークします。
    *   `XABORT`: プログラムによってトランザクションを明示的にアボート（中止）します。
    *   `XTEST`: 現在のコードがトランザクション内で実行されているかどうかをテストします。
    RTMは、ソフトウェアがトランザクションのフォールバックパスを完全に制御できるため、より柔軟な実装が可能です。

2.  **Hardware Lock Elision (HLE)**:
    *   `XACQUIRE` プレフィックス: `LOCK` プレフィックスと組み合わせて使用され、ロック操作をトランザクション的に実行しようとします。競合がなければロックは取得されず、トランザクション的にメモリが更新されます。
    *   `XRELEASE` プレフィックス: `LOCK` プレフィックスと組み合わせて使用され、ロック解放操作をトランザクション的に実行しようとします。
    HLEは、既存のロックベースのコードを最小限の変更でトランザクション的に実行しようとするもので、RTMよりも透過的な利用を目指します。

TSXの基本的な考え方は、複数のスレッドが共有データにアクセスする際に、まず「トランザクション」として操作を試みることです。この間、変更は一時的にバッファリングされ、他のスレッドとの競合が検出されなければ、すべての変更が一度にコミットされます。競合が検出された場合（例えば、別のスレッドがトランザクション中に同じメモリ位置を書き換えた場合）、トランザクションはアボートされ、すべての変更が破棄され、元の状態に戻ります。その後、通常はロックベースのフォールバックパスに切り替えて再試行します。

### トランザクショナルメモリ

トランザクショナルメモリ（TM）は、データベースのトランザクションに似た概念を、並行プログラミングにおける共有メモリ操作に適用するものです。複数のメモリ操作をアトミックな単位として扱い、すべて成功するか、すべて失敗してロールバックされるかのいずれかになります。これにより、ロックの粒度を細かくすることなく、複雑なデータ構造への並行アクセスを簡素化し、デッドロックのリスクを低減し、性能を向上させる可能性を秘めています。

### セマフォ

セマフォは、並行プログラミングにおける同期プリミティブの一つで、共有リソースへのアクセスを制御するために使用されます。カウンタを持ち、リソースが利用可能かどうかを示します。TSXのようなハードウェアトランザクショナルメモリは、セマフォの取得（P操作）と解放（V操作）を、競合が少ない場合にロックなしで実行できるようにすることで、セマフォの実装を最適化するのに役立ちます。

### Google Native Client (Nacl)

Google Native Client (NaCl) は、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行するためのサンドボックス技術です。セキュリティ上の理由から、NaCl環境では特定の低レベルなCPU命令やシステムコールが制限されることがあります。コミットメッセージの「Nacl not supported yet」という記述は、TSX命令がNaClのサンドボックス環境ではまだ利用できないか、またはそのサポートが未実装であることを示しています。これは、セキュリティモデルや命令セットのホワイトリスト化に関連する制約によるものと考えられます。

## 技術的詳細

このコミットは、GoのアセンブラがTSX命令を正しく解釈し、対応する機械語を生成できるようにするための、低レベルなツールチェインの変更です。

1.  **命令の定義とマッピング**:
    *   `src/cmd/internal/obj/x86/a.out.go` では、`AXACQUIRE`, `AXRELEASE`, `AXBEGIN`, `AXEND`, `AXABORT`, `AXTEST` といった新しい定数が定義されています。これらはGoアセンブラ内部でTSX命令を識別するためのシンボリックな表現です。
    *   `src/cmd/internal/obj/x86/anames.go` では、これらの内部定数に対応する文字列リテラル（例: `"XACQUIRE"`, `"XBEGIN"`）が追加されています。これにより、Goのアセンブラ言語でこれらの命令を記述できるようになります。

2.  **アセンブラの命令テーブル更新**:
    *   `src/cmd/internal/obj/x86/asm6.go` の `optab` は、x86命令とそのオペランド、エンコーディング情報を定義する重要なテーブルです。このテーブルにTSX命令が追加され、それぞれの命令に対応するオペコード（例: `AXACQUIRE` は `0xf2`、`AXBEGIN` は `0xc7, 0xf8`）とオペランドの型（`ynone`, `yxbegin`, `yxabort`）が指定されています。
    *   `yxbegin` と `yxabort` は、`XBEGIN` と `XABORT` 命令のオペランドの型を定義する新しいテーブルです。`XBEGIN` は相対ジャンプアドレスをオペランドとして取り、`XABORT` はアボートコードを即値として取ります。

3.  **ジャンプ命令の認識**:
    *   `src/cmd/asm/internal/arch/arch.go` の `jumpX86` 関数は、アセンブラがジャンプ命令を識別するために使用されます。`XBEGIN` 命令はトランザクションの失敗時に指定されたアドレスにジャンプする性質を持つため、この関数に `word == "XBEGIN"` が追加され、ジャンプ命令として認識されるようになりました。これにより、アセンブラは`XBEGIN`命令のターゲットアドレスを正しく解決できるようになります。

4.  **命令のエンコーディングとオフセット計算**:
    *   `src/cmd/internal/obj/x86/asm6.go` の `span6` および `doasm` 関数は、アセンブラの主要なパスであり、命令の長さの計算や機械語へのエンコーディングを担当します。
    *   `span6` 関数では、`AXBEGIN` 命令が `AJCXZL` と同様に特殊なジャンプ命令として扱われ、そのオフセット計算ロジックが調整されています。これは、`XBEGIN` が相対アドレスをオペランドとして取るため、命令の長さやジャンプターゲットまでの距離を正確に計算する必要があるためです。
    *   `doasm` 関数では、`AXABORT` と `AXBEGIN` 命令のエンコーディングロジックが追加されています。特に、`AXABORT` のアボートコードや `AXBEGIN` の相対ジャンプオフセットが、機械語のバイト列に正しく埋め込まれるように処理が記述されています。また、相対ジャンプのオフセット計算において、`AXBEGIN` 命令の特殊なバイト長を考慮するための調整も行われています。

これらの変更により、GoのアセンブラはTSX命令を構文解析し、適切なオペコードとオペランドを伴う機械語命令に変換できるようになります。これは、GoランタイムがTSXのハードウェア機能を活用するための第一歩となります。

*   **`yxbegin` と `yxabort`**: これらの`ytab`構造体は、`XBEGIN`と`XABORT`命令がどのようなオペランドを取るかを定義します。`Ybr`は相対ジャンプアドレス、`Yu8`は8ビットの即値（アボートコード）を意味します。`Zjmp`や`Zib_`は、オペランドのタイプとエンコーディングに関する追加情報を提供します。
*   **`optab`**: この巨大なテーブルは、すべてのアセンブリ命令、そのオペランドの型、命令のクラス（`Px`はプレフィックスなしの命令）、そして実際の機械語オペコードをマッピングします。TSX命令がここに追加されることで、アセンブラはこれらの命令を認識し、対応するバイトコードを生成できるようになります。例えば、`AXBEGIN`は`0xc7, 0xf8`というオペコードを持ち、`AXACQUIRE`は`0xf2`というプレフィックスとして扱われます。
*   **`span6`**: この関数は、命令の長さを計算し、ジャンプ命令のターゲットアドレスを解決するために使用されます。`AXBEGIN`がジャンプ命令として追加されたため、そのオフセット計算ロジックが`AJCXZL`（条件付きジャンプ命令）と同様に扱われるように更新されました。これは、`XBEGIN`が相対アドレスをオペランドとして取るため、命令の長さとジャンプターゲットまでの距離を正確に計算する必要があるためです。
*   **`doasm`**: この関数は、最終的な機械語バイト列を生成する役割を担います。`AXABORT`と`AXBEGIN`命令のエンコーディングロジックが追加され、それぞれの命令のオペコードとオペランド（`AXABORT`のアボートコード、`AXBEGIN`の相対ジャンプオフセット）が、生成されるバイト列に正しく埋め込まれるように処理が記述されています。特に、相対ジャンプのオフセット計算において、`AXBEGIN`命令の特殊なバイト長を考慮するための調整も行われています。

これらの変更は、GoのツールチェインがTSX命令を完全にサポートするための基盤を構築するものであり、Goプログラムがハードウェアトランザクショナルメモリの恩恵を受けられるようになるための重要なステップです。

# [インデックス 21552] ファイルの概要

このコミットは、Go言語の `time` パッケージにおける `ParseDuration` 関数の精度問題とオーバーフロー処理の改善に関するものです。特に、大きな時間値をパースする際に発生していた浮動小数点数による精度損失を防ぎ、`int64` の最大値を超える場合のオーバーフローを適切に処理するように変更されています。

## 元コミット内容

`time: correctly parse large input durations and avoid precision loss`

このコミットは、大きな入力期間を正しくパースし、精度損失を回避することを目的としています。

具体的には、以下の点を改善しています。
*   `1<<53+1` ナノ秒のような、`int64` で表現できる分数を含まない期間について、以前は浮動小数点数変換で失われていた精度を失わないようにします。
*   `1<<63-1` ナノ秒を超える期間のオーバーフローを、それ以前ではなく、その時点で処理するようにします。
*   上記のケースをカバーするためのテストを追加します。

## 変更の背景

Go言語の `time` パッケージの `ParseDuration` 関数は、"1h30m" のような文字列から `time.Duration` 型の値をパースするために使用されます。以前の実装では、このパース処理の内部で浮動小数点数 (`float64`) を使用して期間の計算を行っていました。

`float64` は、その性質上、非常に大きな整数値を正確に表現できない場合があります。特に、`1<<53` (約9 * 10^15) を超える整数は、`float64` では正確に表現できず、精度が失われる可能性があります。`time.Duration` 型はナノ秒単位で時間を `int64` として保持するため、`int64` の範囲内で正確に表現できる値が `float64` 変換によって精度を失うことは問題でした。

また、`int64` の最大値である `1<<63-1` ナノ秒を超えるような非常に大きな期間が入力された場合、オーバーフローを適切に検出し、エラーとして処理する必要がありました。以前の実装では、このオーバーフロー検出が不十分であったり、意図しないタイミングで発生する可能性がありました。

このコミットは、これらの精度損失とオーバーフロー処理の問題を解決し、`ParseDuration` がより堅牢で正確になるようにすることを目的としています。

## 前提知識の解説

### `time.Duration` 型

Go言語の `time.Duration` 型は、時間の長さをナノ秒単位で表す `int64` 型のエイリアスです。これにより、非常に短い時間から非常に長い時間まで、広範囲の期間を正確に表現できます。

### `float64` と `int64` の精度

*   **`int64`**: 64ビットの符号付き整数型で、約 -9 * 10^18 から 9 * 10^18 までの整数値を正確に表現できます。`time.Duration` の基盤となる型です。
*   **`float64`**: 64ビットの浮動小数点数型で、IEEE 754 倍精度浮動小数点数形式に従います。非常に広い範囲の数値を表現できますが、その精度は有限です。特に、`1<<53` (約 9,007,199,254,740,992) を超える整数は、`float64` では正確に表現できず、最も近い表現可能な値に丸められてしまいます。これは、`float64` の仮数部が53ビットしかないためです。このため、`int64` で正確に表現できる大きな整数値が `float64` に変換されると、情報が失われる可能性があります。

### オーバーフロー

数値計算において、変数が表現できる最大値を超えた場合に発生する現象です。`int64` の最大値は `2^63 - 1` です。`ParseDuration` がこの値を超える期間をパースしようとした場合、適切にエラーを返す必要があります。

## 技術的詳細

このコミットの主要な変更点は、`ParseDuration` 関数内部での期間計算を `float64` から `int64` に移行したことです。これにより、浮動小数点数による精度損失を完全に回避し、`int64` の範囲内で正確な計算を保証します。

1.  **`unitMap` の変更**:
    *   以前は `map[string]float64` であった `unitMap` が `map[string]int64` に変更されました。これにより、"ns", "us", "ms" などの単位が `float64` ではなく `int64` のナノ秒値として直接マッピングされるようになりました。

2.  **`ParseDuration` 関数のロジック変更**:
    *   期間の合計を保持する変数が `f float64` から `d int64` に変更されました。
    *   各数値部分（整数部と小数部）のパースにおいて、`leadingInt` 関数が返す値が `int64` として直接扱われるようになりました。
    *   小数部の処理では、`scale` を用いて `float64` 変換を行いますが、最終的な加算は `int64` に丸め込む形で行われます。特に、`v += int64(float64(f) * (float64(unit) / scale))` の行は、小数部がナノ秒単位で正確に表現されるように `float64` を一時的に使用しつつ、最終的に `int64` に加算することで精度を維持しています。
    *   各単位（秒、ミリ秒など）を適用する際に、`int64` の乗算によるオーバーフローチェックが追加されました。`v > (1<<63-1)/unit` のようなチェックにより、乗算前にオーバーフローが発生するかどうかを予測し、エラーを返します。
    *   最終的な合計 `d` が `int64` の範囲を超えた場合（負のオーバーフローも含む）のチェックも追加され、`d < 0` のような条件でオーバーフローを検出しています。

3.  **`leadingInt` 関数の改善**:
    *   `leadingInt` 関数は、文字列の先頭から整数をパースするヘルパー関数です。この関数にも、`int64` のオーバーフローチェックが強化されました。`x > (1<<63-1)/10` や `x < 0` (符号なし整数として扱われた場合のオーバーフロー) のチェックが追加され、より堅牢になりました。

4.  **テストケースの追加**:
    *   `time_test.go` に、`1<<53+1` ナノ秒のような `float64` で精度が失われる可能性のある大きな整数値の期間や、`int64` の最大値に近い期間、およびオーバーフローを引き起こす期間のテストケースが追加されました。これにより、新しい実装がこれらのエッジケースを正しく処理することを確認しています。

これらの変更により、`ParseDuration` は `int64` の範囲内で可能な限り正確な期間のパースを実現し、オーバーフローを適切に処理できるようになりました。

## コアとなるコードの解説

### `src/time/format.go` の変更点

1.  **`leadingInt` 関数のオーバーフローチェック強化**:
    *   `x >= (1<<63-10)/10` から `x > (1<<63-1)/10` に変更されました。これは、`x*10` が `int64` の最大値を超える可能性をより厳密にチェックするためのものです。
    *   `if x < 0` のチェックが追加されました。これは、`x*10 + int64(c) - '0'` の計算結果が `int64` の正の範囲でオーバーフローし、結果として負の値になった場合にそれを検出するためのものです。

2.  **`unitMap` の型変更**:
    *   `map[string]float64` から `map[string]int64` へと変更されました。これにより、各時間単位（ナノ秒、マイクロ秒など）が `float64` ではなく、直接 `int64` のナノ秒値として扱われるようになり、浮動小数点数変換による精度損失の可能性がなくなりました。

3.  **`ParseDuration` 関数の主要な変更**:
    *   `f := float64(0)` が `var d int64` に変更され、期間の合計が `int64` で保持されるようになりました。
    *   各数値部分のパース結果を保持する変数が `g float64` から `v, f int64` に変更されました。`v` は整数部、`f` は小数部を表します。
    *   小数部の処理において、`scale` は `float64` のままですが、`g += float64(x) / scale` のような直接的な `float64` 加算はなくなりました。代わりに、`v += int64(float64(f) * (float64(unit) / scale))` のように、小数部をナノ秒に変換する際に一時的に `float64` を使用し、その結果を `int64` に丸めて `v` に加算しています。これにより、小数部の精度を保ちつつ、最終的な合計は `int64` で行われます。
    *   `if v > (1<<63-1)/unit` のようなオーバーフローチェックが追加されました。これは、`v * unit` の計算を行う前に、その結果が `int64` の最大値を超えるかどうかを事前にチェックするものです。これにより、乗算によるオーバーフローを未然に防ぎ、エラーを返します。
    *   `d += v` の後にも `if d < 0` のチェックが追加されました。これは、複数の期間を加算した結果、`int64` の最大値を超えて負の値になった場合（オーバーフロー）を検出するためのものです。
    *   最終的な戻り値が `Duration(f)` から `Duration(d)` に変更され、`int64` の合計値が直接 `Duration` 型として返されるようになりました。また、`float64` の範囲チェックも不要になりました。

### `src/time/time_test.go` の変更点

*   **新しいテストケースの追加**:
    *   `"9007199254740993ns"`: これは `1<<53+1` ナノ秒に相当し、`float64` では正確に表現できないが `int64` では可能な値です。このテストは、精度損失がなくなったことを確認します。
    *   `"9223372036854775807ns"`: これは `int64` の最大値 (`1<<63-1`) に相当するナノ秒です。このテストは、最大値を正確にパースできることを確認します。
    *   `"9223372036854775.807us"` や `"9223372036s854ms775us807ns"`: これらは、異なる単位の組み合わせで `int64` の最大値に達するケースをテストし、複合的なパースでも精度が保たれることを確認します。
    *   `"-9223372036854775807ns"`: `int64` の最小値に近い負の値をテストします。
    *   オーバーフローを意図的に引き起こすテストケース (`"9223372036854775808ns"`, `"-9223372036854775808ns"`) が追加され、これらの入力に対して `ParseDuration` がエラーを返すことを確認します。
*   **ベンチマークの追加**:
    *   `BenchmarkParseDuration` が追加され、特定の大きな期間のパース性能を測定できるようになりました。

これらの変更により、`ParseDuration` 関数は、Go言語の `time` パッケージにおける期間パースの正確性と堅牢性を大幅に向上させています。

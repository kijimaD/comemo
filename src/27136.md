# [インデックス 27136] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおいて、`Request.ParseMultipartForm` メソッドが呼び出された際に、`Request.PostForm` フィールドも適切にマルチパートフォームデータで埋められるように修正するものです。これにより、`Request.Form` と同様に `Request.PostForm` もマルチパートフォームの値を保持するようになり、開発者がより直感的にフォームデータにアクセスできるようになります。

## 元コミット内容

このコミットは、`net/http` パッケージの `Request.ParseMultipartForm` メソッドが、マルチパートフォームデータを解析した後、`Request.Form` フィールドだけでなく `Request.PostForm` フィールドもそのデータで埋めるように変更します。これにより、Issue 9305で報告された問題が解決されます。

## 変更の背景

Goの `net/http` パッケージでは、HTTPリクエストのフォームデータを扱うために `http.Request` 構造体内に `Form` と `PostForm` という2つのフィールドが用意されています。
- `Request.Form`: URLクエリパラメータとPOST/PUT/PATCHリクエストのボディの両方から解析されたフォームデータを格納します。`ParseForm()` または `ParseMultipartForm()` が呼び出された後に利用可能になります。
- `Request.PostForm`: POST/PUT/PATCHリクエストのボディからのみ解析されたフォームデータを格納します。`ParseForm()` または `ParseMultipartForm()` が呼び出された後に利用可能になります。

従来、`ParseMultipartForm` が呼び出された際、マルチパートフォームデータは `Request.Form` には適切に格納されていましたが、`Request.PostForm` には格納されていませんでした。これは、特に `multipart/form-data` 形式で送信されたフォームデータの場合に、`Request.PostForm` を参照するコードが期待通りの動作をしないという問題を引き起こしていました。

Issue 9305では、この挙動が報告され、`ParseMultipartForm` が `Request.PostForm` も埋めるべきであるという指摘がなされました。このコミットは、この一貫性のない挙動を修正し、`ParseMultipartForm` が `Request.Form` と `Request.PostForm` の両方をマルチパートフォームデータで埋めるようにすることで、開発者がどちらのフィールドを参照しても期待通りの結果を得られるようにすることを目的としています。

## 前提知識の解説

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントとサーバーを実装するための基本的な機能を提供します。Webアプリケーション開発において中心的な役割を果たすパッケージであり、HTTPリクエストの処理、レスポンスの生成、ルーティングなどが可能です。

### HTTPリクエストにおけるフォームデータ

HTTPリクエストでクライアントからサーバーにデータを送信する際、フォームデータは主に以下の2つの形式でエンコードされます。

1.  **`application/x-www-form-urlencoded`**:
    *   これは最も一般的なフォームデータのエンコード形式です。
    *   キーと値のペアが `key1=value1&key2=value2` のように `&` で区切られ、値はURLエンコードされます。
    *   主にシンプルなテキストデータや短い文字列の送信に使用されます。
    *   Goでは `http.Request.ParseForm()` メソッドで解析されます。

2.  **`multipart/form-data`**:
    *   ファイルアップロードなど、バイナリデータや大量のテキストデータを送信する際に使用されます。
    *   フォームの各フィールドが「パート」として扱われ、それぞれが独自のヘッダー（`Content-Disposition` など）とボディを持ち、特定の境界文字列（boundary）で区切られます。
    *   Goでは `http.Request.ParseMultipartForm()` メソッドで解析されます。

### `http.Request` 構造体における `Form`, `PostForm`, `MultipartForm` フィールド

`http.Request` 構造体は、受信したHTTPリクエストに関するすべての情報（メソッド、URL、ヘッダー、ボディなど）をカプセル化します。フォームデータに関連する主要なフィールドは以下の通りです。

*   **`Request.Form` (型: `url.Values`)**:
    *   `ParseForm()` または `ParseMultipartForm()` が呼び出された後に利用可能になります。
    *   URLクエリパラメータとリクエストボディ（`application/x-www-form-urlencoded` または `multipart/form-data`）の両方から解析されたすべてのフォームデータを格納します。
    *   同じキーに対して複数の値が存在する場合（例: `?key=val1&key=val2`）、それらはスライスの形で格納されます。

*   **`Request.PostForm` (型: `url.Values`)**:
    *   `ParseForm()` または `ParseMultipartForm()` が呼び出された後に利用可能になります。
    *   **POST、PUT、PATCHリクエストのボディからのみ**解析されたフォームデータを格納します。URLクエリパラメータは含まれません。
    *   `application/x-www-form-urlencoded` または `multipart/form-data` のいずれかの形式で送信されたボディデータが対象です。

*   **`Request.MultipartForm` (型: `*multipart.Form`)**:
    *   `ParseMultipartForm()` が呼び出された後にのみ利用可能になります。
    *   `multipart/form-data` 形式のリクエストボディを解析した結果を格納します。
    *   ファイルアップロード情報（`File` フィールド）や、通常のフォームフィールド（`Value` フィールド）など、マルチパートフォームの詳細な構造にアクセスするために使用されます。

### `ParseForm()` と `ParseMultipartForm()` メソッド

*   **`Request.ParseForm()`**:
    *   リクエストボディが `application/x-www-form-urlencoded` 形式の場合、またはリクエストメソッドがGETでURLクエリパラメータを解析する場合に使用されます。
    *   このメソッドを呼び出すと、`Request.Form` と `Request.PostForm` (POST/PUT/PATCHの場合) が埋められます。

*   **`Request.ParseMultipartForm(maxMemory int64)`**:
    *   リクエストボディが `multipart/form-data` 形式の場合に使用されます。
    *   `maxMemory` 引数は、ファイルデータがメモリに保持される最大バイト数を指定します。これを超えると、一時ファイルに書き込まれます。
    *   このメソッドを呼び出すと、`Request.Form` と `Request.MultipartForm` が埋められます。**このコミット以前は `Request.PostForm` は埋められませんでした。**

このコミットは、`ParseMultipartForm` が `Request.PostForm` を埋めないという、上記で強調した不整合を修正するものです。

## 技術的詳細

`http.Request` の `ParseMultipartForm` メソッドは、`multipart/form-data` 形式のリクエストボディを解析し、その結果を `Request.MultipartForm` フィールドに格納します。`Request.MultipartForm` は `multipart.Form` 型であり、これには `Value` (通常のフォームフィールド) と `File` (アップロードされたファイル) の2つのマップが含まれています。

このコミット以前の `ParseMultipartForm` の実装では、`multipart.Form` の `Value` フィールドから取得したキーと値のペアを `Request.Form` に追加する処理は行われていましたが、`Request.PostForm` には追加されていませんでした。これは、`Request.Form` がクエリパラメータとボディの両方を統合したビューを提供し、`Request.PostForm` がボディのみのビューを提供するという設計意図からすると、マルチパートフォームのボディデータが `Request.PostForm` にも反映されるべきであるという期待に反していました。

`url.Values` 型は `map[string][]string` のエイリアスであり、HTTPフォームのキーと値のペアを表現するために使用されます。同じキーに対して複数の値が存在する場合（例: 複数のチェックボックスが同じ `name` 属性を持つ場合）、それらの値は文字列のスライスとして格納されます。

このコミットの修正は、`ParseMultipartForm` が `multipart.Form` から解析した通常のフォームフィールド（ファイルではないフィールド）を `Request.Form` に追加するのと同時に、`Request.PostForm` にも追加することで、この不整合を解消します。これにより、`ParseMultipartForm` を呼び出した後、開発者は `Request.Form` または `Request.PostForm` のどちらを参照しても、マルチパートフォームのテキストフィールドにアクセスできるようになります。これは、特に `Request.PostForm` を使用してPOSTボディのデータのみを処理するロジックを持つアプリケーションにとって重要な修正となります。

## コアとなるコードの解説

### `src/net/http/request.go` の変更点

1.  **`if r.PostForm == nil { r.PostForm = make(url.Values) }`**:
    *   `ParseMultipartForm` が呼び出される前に `r.PostForm` が `nil` であった場合、新しい `url.Values` マップを初期化します。これにより、後続の `append` 操作で `nil` マップへの書き込みを防ぎ、安全に値を追加できるようになります。`ParseForm` と同様に、`PostForm` は必要に応じて初期化されるべきです。

2.  **`for k, v := range f.Value { ... r.PostForm[k] = append(r.PostForm[k], v...) }`**:
    *   既存のループは、解析されたマルチパートフォームの非ファイルフィールド（`f.Value`）を `r.Form` に追加していました。
    *   この変更では、同じループ内で `r.PostForm[k] = append(r.PostForm[k], v...)` という行が追加されています。
    *   これにより、`f.Value` から取得された各キー `k` とその値 `v` が、`r.Form` に追加されるのと同時に `r.PostForm` にも追加されるようになります。
    *   コメント `// r.PostForm should also be populated. See Issue 9305.` が追加され、この変更の理由が明確に示されています。

これらの変更により、`ParseMultipartForm` が実行された後、`Request.Form` と `Request.PostForm` の両方が、マルチパートフォームのテキストフィールドデータで適切に埋められるようになります。

### `src/net/http/request_test.go` の変更点

`TestParseMultipartFormPopulatesPostForm` という新しいテスト関数が追加されました。このテストは以下のことを検証します。

1.  **マルチパートフォームデータの準備**:
    *   `postData` という文字列で、`multipart/form-data` 形式のサンプルデータが定義されています。これには `field1`, `field2` という通常のフォームフィールドと、`file` というファイルフィールドが含まれています。
    *   この `postData` を使用して `http.Request` オブジェクトが作成され、`Content-Type` ヘッダーが `multipart/form-data` に設定されます。

2.  **`Request.Form` の初期状態の準備**:
    *   テストのシナリオとして、`req.Form` には `ParseMultipartForm` が呼び出される前に既にいくつかの値（`language`, `name`, `skill`, `field2`）が設定されています。これは、`ParseForm` などによって既にクエリパラメータや他のフォームデータが `Form` に追加されている状況をシミュレートしています。特に `field2` は、マルチパートフォームデータにも同じキーが存在する場合に、値が適切に結合されるかを確認するために重要です。

3.  **`ParseMultipartForm` の呼び出し**:
    *   `req.ParseMultipartForm(10000)` が呼び出され、マルチパートフォームデータが解析されます。

4.  **`Request.Form` の検証**:
    *   `wantForm` という期待される `url.Values` が定義され、`req.Form` の内容と比較されます。
    *   `wantForm` には、初期設定された値と、マルチパートフォームから解析された `field1` および `field2` の値がすべて含まれていることが期待されます。`field2` のように重複するキーは、スライスとして値が結合されていることを確認します。

5.  **`Request.PostForm` の検証**:
    *   `wantPostForm` という期待される `url.Values` が定義され、`req.PostForm` の内容と比較されます。
    *   `wantPostForm` には、**マルチパートフォームから解析された `field1` と `field2` の値のみ**が含まれていることが期待されます。`req.Form` に初期設定されていた値（`language`, `name`, `skill`）は、これらがURLクエリパラメータや `application/x-www-form-urlencoded` 形式のボディデータとして扱われるべきものであり、`PostForm` はPOSTボディのみを反映するため、ここには含まれないことが正しい挙動です。
    *   この検証が、このコミットの主要な目的である「`ParseMultipartForm` が `PostForm` も埋める」という修正を直接的に確認します。

このテストケースは、修正が正しく機能し、`Request.Form` と `Request.PostForm` がそれぞれの設計意図に従ってマルチパートフォームデータを保持していることを保証します。

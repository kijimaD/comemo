# [インデックス 25648] ファイルの概要

このコミットは、GoコンパイラのPPC64アーキテクチャ向けオブジェクトファイル生成部分（`cmd/internal/obj/ppc64/obj9.go`）における重要な変更を導入しています。具体的には、動的リンク時に`runtime.morestack`関数を呼び出す際、PLT（Procedure Linkage Table）を介するのではなく、直接的な呼び出しメカニズムを使用するように修正されています。これにより、PPC64LEシステムリンカが生成するPLTスタブが、TOC（Table of Contents）ポインタを誤って上書きしてしまう問題を回避します。

## 変更の背景

この変更は、PPC64LEアーキテクチャ上でGoプログラムを動的リンクする際に発生する特定の問題に対処するために行われました。問題の核心は、`runtime.morestack`というGoランタイムの重要な関数が、動的リンクされたライブラリから呼び出される際に、システムリンカが生成するPLTスタブの動作にありました。

通常、動的リンクされた関数を呼び出す際には、PLT（Procedure Linkage Table）を介して間接的に呼び出しが行われます。PLTスタブは、実際の関数のアドレスを解決し、その関数にジャンプする役割を担います。しかし、PPC64LEのABI（Application Binary Interface）では、PLTスタブが呼び出し元のスタックフレームにTOC（Table of Contents）ポインタ（`r2`レジスタ）を保存する動作が規定されています。

`runtime.morestack`は、スタックの拡張が必要になった際に呼び出される関数であり、その性質上、呼び出し元の関数が自身のスタックフレームを完全にセットアップする前に呼び出される可能性があります。このタイミングの問題が、PLTスタブのTOCポインタ保存ロジックと衝突しました。具体的には、`morestack`を呼び出すPLTスタブが、`morestack`を呼び出した関数のさらに呼び出し元（caller's caller）のTOCポインタを上書きしてしまうという問題が発生していました。これにより、プログラムの実行が不正な状態になり、クラッシュや予期せぬ動作を引き起こす可能性がありました。

コミットメッセージには、ABIドキュメントに`R_PPC64_TOCSAVE`というリロケーションタイプを使用してPLTスタブがTOCを保存するのを回避するメカニズムがあることが言及されています。しかし、当時の`gold`リンカはこの機能をサポートしておらず、`ld.bfd`リンカで試みた際には内部リンカエラーが発生したとのことです。これらの理由から、ABIの規定に沿った解決策が利用できなかったため、Goコンパイラ側でPLTを介さない直接的な呼び出しメカニズムを実装するという「ハック」が選択されました。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **Goランタイムとスタック管理**:
    *   Go言語のgoroutineは、比較的小さなスタック（通常は数KB）で開始されます。
    *   関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。このスタック拡張処理の中心となるのが`runtime.morestack`関数です。
    *   `runtime.morestack`は、現在のスタックフレームの情報を保存し、新しい大きなスタックフレームを割り当て、元の関数にジャンプバックする一連の処理を行います。この処理は非常に低レベルであり、アセンブリ言語で実装されることが多いです。

2.  **PPC64LEアーキテクチャ**:
    *   PPC64LE (PowerPC 64-bit Little Endian) は、IBM Powerアーキテクチャの64ビット版で、リトルエンディアンのバイトオーダーを採用しています。
    *   このアーキテクチャには、特定のレジスタ使用規約や関数呼び出し規約（ABI）が存在します。
    *   **TOC (Table of Contents)**: PPC64アーキテクチャでは、グローバルデータや関数へのアクセスを効率化するためにTOCが使用されます。TOCは、プログラムのグローバルシンボルへのポインタのテーブルであり、`r2`レジスタがTOCポインタとして機能します。関数は、`r2`レジスタを介してTOCにアクセスし、必要なアドレスを取得します。

3.  **動的リンクとPLT/GOT**:
    *   **動的リンク**: プログラムの実行時に、必要なライブラリ（共有ライブラリ、ダイナミックリンクライブラリ）をロードし、リンクする方式です。これにより、実行ファイルのサイズを小さくし、ライブラリの更新を容易にします。
    *   **PLT (Procedure Linkage Table)**: 動的リンクされた関数を呼び出す際に使用されるテーブルです。プログラムが初めて動的リンクされた関数を呼び出す際、PLTエントリはリンカに制御を渡し、実際の関数のアドレスを解決させます。以降の呼び出しでは、PLTエントリは解決されたアドレスに直接ジャンプします。
    *   **GOT (Global Offset Table)**: グローバル変数や動的リンクされた関数のアドレスを格納するテーブルです。PLTはGOTを参照して関数のアドレスを取得します。
    *   **PLTスタブ**: PLT内の各エントリは、特定の動的リンクされた関数を呼び出すための小さなコード片（スタブ）です。このスタブが、関数のアドレス解決やTOCポインタの保存などのABIに準拠した処理を行います。

4.  **リロケーション**:
    *   コンパイル時やリンク時に、プログラム内のアドレス参照を修正するプロセスです。動的リンクでは、実行時にライブラリがロードされるベースアドレスが異なるため、多くのリロケーションが必要になります。
    *   **`R_PPC64_TOCSAVE`**: PPC64LEのABIで定義されているリロケーションタイプの一つで、PLTスタブがTOCポインタを保存する動作を制御するために使用される可能性があります。

## 技術的詳細

このコミットの技術的な核心は、PPC64LEアーキテクチャにおける`runtime.morestack`の呼び出し方法を、動的リンクの有無によって条件分岐させる点にあります。

変更前は、`runtime.morestack`（またはそのバリアントである`morestackc`, `morestack_noctxt`）への呼び出しは、常に`ABL` (Absolute Branch and Link) 命令を使用して行われていました。これは、シンボルが直接解決できる静的リンクの場合や、PLTスタブが問題なく機能する場合に適切です。

```go
// 変更前のコードの抜粋
// BL	runtime.morestack(SB)
p = obj.Appendp(ctxt, p)
p.As = ABL
p.To.Type = obj.TYPE_BRANCH
p.To.Sym = morestacksym // morestack, morestackc, or morestack_noctxt
```

しかし、動的リンク (`ctxt.Flag_dynlink` が true の場合) では、前述のTOCポインタ上書き問題が発生するため、この直接的な`ABL`呼び出しを回避する必要があります。

コミット後のコードでは、`ctxt.Flag_dynlink`が設定されている場合に、以下の手順で`runtime.morestack`を呼び出すように変更されています。

1.  **`runtime.morestack`のアドレスをレジスタにロード**:
    *   `MOVD $runtime.morestack(SB), R12`
    *   これは、`runtime.morestack`シンボルのアドレスを、GOT (Global Offset Table) を介して`R12`レジスタにロードする命令です。`obj.NAME_GOTREF`は、GOT参照であることを示します。これにより、動的リンカが実行時に`runtime.morestack`の実際のアドレスを解決し、そのアドレスがGOTに格納され、そこから`R12`にロードされます。

2.  **`R12`レジスタの値を`CTR`レジスタに移動**:
    *   `MOVD R12, CTR`
    *   `CTR` (Count Register) は、PPCアーキテクチャにおける分岐命令のターゲットアドレスを保持するために使用される特殊なレジスタです。`BL CTR`命令は、`CTR`レジスタに格納されたアドレスにジャンプします。

3.  **`CTR`レジスタを介して関数を呼び出し**:
    *   `BL CTR`
    *   これは、`CTR`レジスタに格納されているアドレス（つまり`runtime.morestack`のアドレス）に分岐し、リンクレジスタ（`LR`）にリターンアドレスを保存する命令です。これにより、PLTスタブを介さずに`runtime.morestack`を直接呼び出すことができます。

このシーケンスにより、PLTスタブがTOCポインタを保存する動作を完全にバイパスし、`runtime.morestack`が安全に呼び出されるようになります。静的リンクの場合や、動的リンクでも問題が発生しない他のアーキテクチャでは、引き続き従来の`ABL`命令が使用されます。

この変更は、Goコンパイラのバックエンド、特にPPC64アーキテクチャ向けのコード生成ロジックに深く関わるものであり、Goランタイムの安定性と正確な動作を保証するために不可欠です。

## コアとなるコードの解説

変更の中心は、`stacksplit`関数内で`runtime.morestack`への呼び出しを生成する部分です。

1.  **`morestacksym`の決定**:
    まず、`runtime.morestack`のどのバリアント（`runtime.morestackc`, `runtime.morestack_noctxt`, `runtime.morestack`）を呼び出すべきかを決定し、そのシンボルを`morestacksym`変数に格納します。これは変更前と同じロジックです。

2.  **動的リンクの条件分岐**:
    `if ctxt.Flag_dynlink { ... } else { ... }`という条件分岐が追加されました。
    *   `ctxt.Flag_dynlink`は、現在のコンテキストが動的リンクを対象としているかどうかを示すフラグです。

3.  **動的リンク時の特殊処理 (`if ctxt.Flag_dynlink`)**:
    このブロックが、PPC64LEにおけるPLT問題を回避するための新しいコードです。
    *   `// MOVD $runtime.morestack(SB), R12`: `runtime.morestack`のアドレスを`R12`レジスタにロードするアセンブリ命令を生成します。`obj.TYPE_MEM`と`obj.NAME_GOTREF`は、このアドレスがGOTを介して解決されることを示します。
    *   `// MOVD R12, CTR`: `R12`レジスタにロードされたアドレスを`CTR`（Count Register）に移動するアセンブリ命令を生成します。
    *   `// BL CTR`: `CTR`レジスタに格納されたアドレスに分岐し、リンクレジスタにリターンアドレスを保存するアセンブリ命令を生成します。`obj.ACALL`は、Goコンパイラの内部表現で関数呼び出しを示します。

4.  **非動的リンク時の通常処理 (`else`)**:
    このブロックは、動的リンクでない場合（静的リンクなど）の従来の`ABL`命令による呼び出しを維持します。
    *   `// BL	runtime.morestack(SB)`: `runtime.morestack`シンボルへの直接的な分岐とリンクを行うアセンブリ命令を生成します。

この変更により、GoコンパイラはPPC64LEアーキテクチャにおいて、動的リンクの状況に応じて`runtime.morestack`の呼び出し方法を適切に選択できるようになり、TOCポインタ上書き問題が解決されました。

# [インデックス 22308] ファイルの概要

このコミットは、GoランタイムにおけるThread Local Storage (TLS) のオフセットを最適化するものです。特にELF形式を使用するIntelアーキテクチャにおいて、TLSに予約される領域のサイズを半減させ、`g` (goroutine) ポインタのみがTLSに格納される現在の状況に合わせて調整します。これにより、リンカとランタイムの両方でTLSの扱いが効率化されます。

## 元コミット内容

このコミットは、Goのリンカ (`cmd/internal/ld`) とオブジェクトファイル生成ツール (`cmd/internal/obj`)、そしてランタイムの各OS/アーキテクチャ固有のアセンブリコードにおいて、TLS (Thread Local Storage) のオフセット計算を変更するものです。具体的には、ELF形式を使用するIntel系アーキテクチャ (386, amd64) において、TLSのオフセットをポインタサイズの2倍 (`2*Ptrsize`) からポインタサイズ1倍 (`1*Ptrsize`) に半減させています。

## 変更の背景

Goランタイムは、各OSスレッド上で実行されるゴルーチン (`g`) のコンテキストを効率的に管理するためにTLSを利用しています。特に、現在実行中のゴルーチンを示す `g` ポインタはTLSに格納され、Go関数が呼び出される際のプロローグで高速にアクセスされます。

このコミットが導入される以前は、ELF/Intel環境においてTLSのために `2 * Ptrsize` (ポインタサイズの2倍) の領域が予約されていました。これは、過去には `g` ポインタだけでなく、OSスレッド (`m`) を表すポインタもTLSに格納されていた可能性を示唆しています。しかし、コミットメッセージに「For OSes that use elf on intel, 2*Ptrsize bytes are reserved for TLS. But only one pointer (g) has been stored in the TLS for a while now.」とあるように、このコミットの時点では既に `g` ポインタのみがTLSに格納される運用になっていました。

TLSに `g` ポインタしか格納されていないにも関わらず、`2 * Ptrsize` の領域を予約し続けることは、メモリの無駄であり、また外部リンカを使用した場合のTLSの挙動と整合性が取れない可能性がありました。この非効率性と不整合を解消し、TLSの利用をより正確かつ効率的にするために、予約されるTLSオフセットを `Ptrsize` に削減する変更が行われました。これにより、GoランタイムのTLSの利用が、実際の必要性と外部リンカの挙動に合致するようになります。

## 前提知識の解説

### Thread Local Storage (TLS)

TLS (Thread Local Storage) は、各スレッドがそれぞれ独立したデータを保持するためのメカニズムです。通常、グローバル変数や静的変数はプロセス内の全てのスレッドで共有されますが、TLSに格納された変数は、その変数にアクセスするスレッドごとに異なる値を持ちます。これは、スレッド固有のコンテキストや状態を管理する際に非常に有用です。

Intel x86/x86-64アーキテクチャでは、TLSは通常、セグメントレジスタ (`FS` または `GS`) を利用して実装されます。これらのレジスタは、特定のメモリ領域のベースアドレスを指し、そのベースアドレスからのオフセットを使ってTLS変数にアクセスします。例えば、`0(FS)` や `-8(GS)` のように記述されます。

### ELF (Executable and Linkable Format)

ELFは、Unix系OS (Linux, FreeBSD, NetBSD, OpenBSD, DragonflyBSDなど) で広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFは、プログラムのロード、リンク、実行の方法を定義しており、TLSの管理方法もELF仕様の一部として定義されています。

ELFにおけるTLSは、`PT_TLS` セグメントを通じて定義され、各スレッドの開始時にその内容がコピーされます。Goランタイムは、ELFのTLSモデル（特に "initial exec" (IE) や "local exec" (LE) モデル）を利用して、`g` ポインタをTLSに格納しています。

### GoランタイムのGPMモデル

Goランタイムは、ゴルーチン (`G`)、論理プロセッサ (`P`)、OSスレッド (`M`) の3つのエンティティからなるGPMスケジューラモデルを採用しています。
*   **G (Goroutine)**: Goにおける軽量な実行単位。Goプログラムの並行性の基本です。
*   **P (Processor)**: OSスレッドがGoコードを実行するために必要なリソース（スケジューラキューなど）を表す論理プロセッサ。
*   **M (Machine)**: OSスレッド。Goコードを実行する実際のOSスレッドです。

Goランタイムは、`g` ポインタをTLSに格納することで、現在実行中のゴルーチン (`G`) の情報をOSスレッド (`M`) から高速に参照できるようにしています。これにより、スタックの拡張チェックやスケジューラの操作など、ランタイムの重要な処理が効率的に行われます。

### ポインタサイズ (Ptrsize)

`Ptrsize` は、システムにおけるポインタのサイズをバイト単位で表します。32ビットシステムでは4バイト、64ビットシステムでは8バイトです。TLSのオフセットは、このポインタサイズを基準に計算されます。

## 技術的詳細

このコミットの核心は、TLSオフセットの計算ロジックの変更です。

1.  **リンカ (`cmd/internal/ld`) とオブジェクトファイル生成ツール (`cmd/internal/obj`) の変更**:
    `src/cmd/internal/ld/sym.go` と `src/cmd/internal/obj/sym.go` の両方で、`ctxt.Tlsoffset` の設定が変更されています。
    変更前: `ctxt.Tlsoffset = -2 * ctxt.Arch.Ptrsize`
    変更後: `ctxt.Tlsoffset = -1 * ctxt.Arch.Ptrsize`
    これは、リンカがTLS関連のシンボルを解決する際に使用するオフセットの基準値を変更するものです。TLSのベースアドレスからのオフセットが、以前はポインタ2つ分の領域を考慮していましたが、今後はポインタ1つ分の領域を考慮するように調整されます。負の値は、TLSベースアドレスからのオフセットが負の方向（通常はTLSブロックの先頭より手前）にあることを示します。

2.  **ランタイムのアセンブリコードの変更**:
    `src/runtime/sys_*.s` ファイル群（DragonFly BSD, FreeBSD, Linux, NetBSD, OpenBSDの386およびamd64アーキテクチャ向け）において、TLSベースアドレスの調整を行うアセンブリコードが変更されています。
    これらのファイルでは、`runtime·settls` 関数内でTLSベースアドレスに特定の値を加算してオフセットを調整しています。
    例えば、`src/runtime/sys_dragonfly_386.s` では、`ADDL $8, CX` が `ADDL $4, CX` に変更されています。これは、32ビットシステム (`Ptrsize` が4バイト) において、TLSベースアドレスに加算するオフセットを8バイトから4バイトに削減していることを意味します。
    同様に、64ビットシステム (`Ptrsize` が8バイト) のファイルでは、`ADDQ $16, DI` が `ADDQ $8, DI` に変更されています。これは、TLSベースアドレスに加算するオフセットを16バイトから8バイトに削減していることを意味します。

これらの変更は、TLSに格納されるデータが `g` ポインタのみであるという事実に基づいています。以前は `g` と `m` の両方がTLSに格納されていた時期があったため、`2 * Ptrsize` の領域が予約されていましたが、`m` ポインタがTLSから削除された後もオフセットの計算が更新されていませんでした。このコミットは、その古い仮定を修正し、TLSの利用をより正確かつ効率的にします。

特に、`src/runtime/sys_linux_386.s` のコメントが変更されている点も重要です。
変更前: `* we get is not at 0(GS), 4(GS), but -8(GS), -4(GS).`
変更後: `* we get is not at 0(GS), but -4(GS).`
このコメントの変更は、TLSのオフセットが `0(GS)` と `4(GS)` ではなく、`-8(GS)` と `-4(GS)` を使用していた状況から、`-4(GS)` のみを使用する状況に変わったことを明確に示しています。これは、TLSに格納されるポインタの数が2つから1つに減ったことを裏付けています。

この変更は、GoのリンカがTLS関連のシンボルを処理する際のオフセット計算に影響を与えます。`ctxt.Tlsoffset` は、TLSのベースアドレスからのオフセットを定義しており、この値を `-1 * ctxt.Arch.Ptrsize` に変更することで、TLSに格納されるデータが1つのポインタ (`g` ポインタ) のみであることをリンカに伝えます。これにより、リンカはTLS関連の参照を正しく解決し、生成されるバイナリがTLSを効率的に利用できるようになります。

このアセンブリコードは、OSスレッドがTLSをセットアップする際に実行されます。`runtime·settls` 関数は、TLSベースアドレスを調整し、`g` ポインタが格納されるTLS領域を正しく設定します。
変更前は `ADDL $0x8, CX` で8バイトのオフセットを加えていましたが、変更後は `ADDL $0x4, CX` で4バイトのオフセットに削減しています。これは32ビットシステムにおけるポインタサイズが4バイトであるため、TLSに1つのポインタ (`g`) のみが格納されることを反映しています。

同様の変更が、他のOS/アーキテクチャのアセンブリファイルにも適用されており、TLSに予約される領域がポインタ1つ分に統一されています。これにより、GoランタイムはTLSをより正確かつ効率的に利用し、外部リンカとの互換性も向上させます。

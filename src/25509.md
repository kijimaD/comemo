# [インデックス 25509] ファイルの概要

このコミットは、Goランタイムのガベージコレクション (GC) におけるスイープ終了とマーキングへの移行の処理を分散化することを目的としています。これにより、GCの初期化、スイープ終了、および並行マーキングへの移行が、GC状態の終了条件を検出したゴルーチンによって直接処理されるようになり、GCの開始がより効率的になります。また、GCコーディネーターの起動メカニズムも一時的にセマフォベースに変更されています。

## 変更の背景

Go 1.5で導入された並行ガベージコレクション (GC) は、アプリケーションの実行と並行して動作することで、GCによる一時停止時間（Stop-The-World: STW）を大幅に削減しました。しかし、初期のGo 1.5 GCでは、GCの各フェーズ間の変更を管理するために単一の「コーディネーター」ゴルーチンに依存していました。

この集中型アプローチにはいくつかの課題がありました。
1.  **遅延の発生**: コーディネーターがスケジューラに依存していたため、GCサイクルの開始やフェーズ移行に遅延が発生する可能性がありました。これにより、GCサイクルの延長やメモリ割り当てのブロック、さらにはアプリケーションの一時的なポーズにつながることがありました。
2.  **過剰なメモリ割り当て**: コーディネーターがアイドル状態になるのを待つ間に、ミューテーターゴルーチン（アプリケーションの実行を担当するゴルーチン）がメモリを過剰に割り当ててしまう可能性がありました。
3.  **堅牢性の欠如**: コーディネーターの起動メカニズムが`park/ready`ベースであったため、前のGCサイクルからコーディネーターがパークしようとしているがまだパークしていない場合に、新しいGCサイクルの開始が失敗する可能性がありました。

これらの問題を解決するため、GoチームはGCの調整を分散化するアプローチを検討し、Issue #11970「Proposal: Decentralized GC coordination」が提案されました。このコミットは、その分散化アプローチの初期段階を実装するもので、GCの初期化、スイープ終了、および並行マーキングへの移行を、GC状態の終了条件を検出したゴルーチンが直接処理するように変更しています。これにより、GCの開始がより迅速かつ効率的になり、集中型コーディネーターへの依存が軽減されます。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoのガベージコレクションに関する前提知識を解説します。

*   **Goのガベージコレクション (GC)**: Goは、プログラムが使用しなくなったメモリ領域を自動的に解放するガベージコレクタを備えています。Go 1.5以降、低レイテンシを実現するために、ほとんどのGC処理がアプリケーションの実行と並行して行われる「並行GC」が導入されました。
*   **GCフェーズ**: GoのGCは、いくつかの主要なフェーズに分かれています。
    *   **Mark (マーキング)**: プログラムが現在使用している（到達可能な）オブジェクトを識別するフェーズです。
    *   **Sweep (スイープ)**: マーキングフェーズで到達不可能と判断された（デッドな）オブジェクトが占めていたメモリ領域を解放し、再利用可能にするフェーズです。
    *   **Sweep Termination (スイープ終了)**: スイープフェーズが完了したことを調整し、次のGCフェーズへの移行を準備するフェーズです。
    *   **Mark Termination (マーキング終了)**: マーキングフェーズが完了したことを調整するフェーズです。
*   **並行GC**: アプリケーションの実行（ミューテーターゴルーチン）とGC処理（GCワーカーゴルーチン）が同時に動作するGCのモードです。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、アプリケーションの応答性を向上させます。
*   **Stop-The-World (STW)**: GCの特定のクリティカルなフェーズで、すべてのアプリケーションゴルーチンが一時的に停止される期間です。STWはGCの正確性と一貫性を保証するために必要ですが、アプリケーションの応答性に直接影響するため、その時間を可能な限り短縮することがGo GCの重要な目標です。
*   **GCコーディネーター**: 以前のGo GCでは、GCの各フェーズ間の移行や全体の進行を調整する役割を担う単一の特別なゴルーチンが存在しました。このコーディネーターがGCの「司令塔」として機能していました。
*   **`Gosched()`**: Goのランタイム関数で、現在のゴルーチンを一時停止し、他の実行可能なゴルーチンにCPUを譲る（スケジューリングを委ねる）ために使用されます。GCの開始時など、特定の状況でメモリの過剰割り当てを防ぐために、アプリケーションゴルーチンが自発的にCPUを譲る目的で使用されることがありました。
*   **セマフォ (`semacquire`/`semrelease`)**: 複数のゴルーチン間で共有リソースへのアクセスを制御したり、ゴルーチン間の同期を取ったりするための同期プリミティブです。`semacquire`はセマフォを取得（デクリメント）し、セマフォが0の場合は待機します。`semrelease`はセマフォを解放（インクリメント）します。

## 技術的詳細

このコミットの核となる技術的変更は、GoランタイムのGCにおける「off->mark」遷移（GCが非アクティブな状態からマーキングフェーズに移行するプロセス）の処理方法を根本的に見直した点にあります。

1.  **GC初期化と状態遷移の分散化**:
    *   以前は、GCの初期化、スイープ終了、および並行マーキングへの移行といった一連の処理は、GCコーディネーターゴルーチンによって集中管理されていました。
    *   このコミットでは、これらの処理が`off->mark`遷移関数に統合され、GC状態の終了条件（例えば、ヒープサイズがGCトリガーを超えたなど）を検出した**任意のゴルーチン**によって直接処理されるようになりました。
    *   これにより、GCの開始がより迅速かつ効率的になります。特定のゴルーチンがGCの開始を「支援」する形になるため、集中型コーディネーターがスケジューリングされるのを待つ必要がなくなります。これは、GCのレイテンシをさらに削減し、アプリケーションの応答性を向上させる上で重要なステップです。

2.  **`mallocgc`の動作変更**:
    *   以前のGCサイクル開始時には、`mallocgc`（メモリ割り当てを行う関数）が、GCが完全に起動する前にメモリが過剰に割り当てられるのを防ぐために`Gosched()`を呼び出し、他のゴルーチンにCPUを譲っていました。
    *   分散化されたGCでは、`mallocgc`を呼び出したゴルーチン自体がGCの開始を支援する役割を果たすため、GCサイクル開始時の`Gosched()`は不要になりました。これにより、メモリ割り当てのパスがわずかに高速化されます。
    *   ただし、GCシャットダウン時には、依然として`Gosched()`によるCPUの譲渡が必要であるとコメントされています。これは、GCの終了処理中にミューテーターゴルーチンが過剰に割り当てを行うことを防ぐためです。

3.  **GCコーディネーターの起動メカニズムの一時的な変更**:
    *   このコミットの時点では、GCコーディネーターはまだGCの後続フェーズ（例えば、マーキング終了やスイープ）を処理する役割を担っていました。
    *   以前のコーディネーターの起動メカニズムは`park/ready`ベースでしたが、これはコーディネーターが前のサイクルからパークしようとしているがまだパークしていない場合に、新しいGCサイクルの開始が失敗する可能性がありました。
    *   この問題を解決するため、コーディネーターを起動するメカニズムが`park/ready`からセマフォ (`wakeSema`) に置き換えられました。これにより、コーディネーターの起動がより堅牢になります。
    *   コミットメッセージには、このセマフォへの変更は一時的なものであり、数コミット後にはGCコーディネーター自体が完全に廃止される予定であると明記されています。これは、GCの完全な分散化に向けた中間ステップであることを示しています。

これらの変更は、GoのGCをより反応性が高く、効率的で、予測可能なものにするための継続的な取り組みの一環です。特に、GCの開始とフェーズ移行のオーバーヘッドを削減し、STW時間をさらに短縮することに貢献します。

## コアとなるコードの解説

### `src/runtime/malloc.go`

*   `mallocgc`関数内のコメントが変更されました。以前はGCの開始時とシャットダウン時の両方で`Gosched()`が必要である可能性を示唆していましたが、変更後はGCシャットダウン時のみに`Gosched()`が必要であることを明確にしています。これは、GC開始時の処理が分散化された結果、`mallocgc`がGCの開始を支援するようになったため、GC開始時にCPUを譲る必要がなくなったことを反映しています。

### `src/runtime/mgc.go`

*   **`startGCCoordinator`関数の変更**:
    *   関数のシグネチャから`mode gcMode`引数が削除され、`startGCCoordinator()`となりました。これは、この関数が常に並行GCをトリガーするようになり、同期的なGCモードの処理が別の場所（`gc`関数内）に移動したことを示しています。
    *   GCコーディネーターの起動ロジックが変更され、`bggc.wakeSema = 1`と`semrelease(&bggc.wakeSema)`が導入されました。これにより、以前の`park/ready`メカニズムがセマフォベースの同期に置き換えられ、コーディネーターの起動がより堅牢になりました。
*   **`bggc`構造体の変更**:
    *   `bggc`構造体から`g *g`フィールドが削除されました。これは、GCコーディネーターゴルーチンへの直接参照が不要になったことを意味し、分散化されたアプローチへの移行を示唆しています。
    *   代わりに、`wakeSema uint32`フィールドが追加されました。これは、GCコーディネーターゴルーチンを起動するためのセマフォとして機能します。
*   **`backgroundgc`関数の変更**:
    *   `bggc.g = getg()`の行が削除されました。これは、`bggc`構造体から`g *g`フィールドが削除されたことと一致します。
    *   `goparkunlock(&bggc.lock, "Concurrent GC wait", traceEvGoBlock, 1)`が`semacquire(&bggc.wakeSema, false)`に置き換えられました。これにより、バックグラウンドGCゴルーチンは、セマフォが解放されるまで待機するようになり、コーディネーターの起動メカニズムの変更に対応しています。
    *   `bggc.working`のインクリメント/デクリメントロジックが変更され、複数のゴルーチンがGCの開始をトリガーしようとした場合の動作がより正確に制御されるようになりました。
*   **`gcStart`関数の変更**:
    *   `startGCCoordinator(mode)`の呼び出しが削除されました。これは、GCの初期化と`off->mark`遷移が`gc`関数内で直接処理されるようになったためです。
*   **`gc`関数の変更**:
    *   `gc`関数は、GCの主要なロジックを含んでいます。このコミットでは、`off->mark`遷移の処理がこの関数内に統合されました。
    *   特に、`gcBackgroundMode`でない場合の`gc`関数の呼び出しが変更され、`off->mark`遷移のロジックがより直接的に制御されるようになりました。
    *   `mode == gcBackgroundMode`の場合の処理が変更され、バックグラウンドマーキングの完了を待機するロジックが追加されました。
    *   `startGCCoordinator()`の呼び出しが`gc`関数内に移動しました。これは、GCコーディネーターの起動がGCの特定のフェーズ（この場合はマーキングフェーズの開始）と密接に連携するようになったことを示しています。

### `src/runtime/trace.go`

*   `traceGCStart`関数内の`traceEvent`の引数が`5`から`3`に変更されました。これは、GC開始イベントのトレース情報の詳細度や形式が変更されたことを示唆しています。

これらの変更は全体として、GoのGCをより分散化された、イベント駆動型のモデルに移行させるための重要なステップであり、GCのパフォーマンスと堅牢性を向上させることを目的としています。

# [インデックス 23102] ファイルの概要

このコミットは、Goランタイムにおけるメモリ統計の更新方法を改善し、特にARMアーキテクチャでの`sysAlloc`/`sysFree`呼び出しの安全性を高めることを目的としています。具体的には、`xadduintptr`という新しいアトミック操作を導入し、既存の`xadd64`が特定の条件下（有効なGがない場合）でロックを必要とし、問題を引き起こす可能性があった点を解決しています。これにより、Goランタイムの堅牢性と移植性が向上しています。

## コミット

```
runtime: implement xadduintptr and update system mstats using it

The motivation is that sysAlloc/Free() currently aren't safe to be
called without a valid G, because arm's xadd64() uses locks that require
a valid G.

The solution here was proposed by Dmitry Vyukov: use xadduintptr()
instead of xadd64(), until arm can support xadd64 on all of its
architectures (not a trivial task for arm).

Reviewed-on: https://go-review.googlesource.com/9002
Reviewed-by: Dmitry Vyukov <dvyukov@google.com>
```

## 変更の背景

このコミットの主な動機は、Goランタイムの`sysAlloc()`および`sysFree()`関数が、有効なGoルーチン（G）のコンテキストなしで呼び出された場合に安全ではないという問題にありました。この問題は特にARMアーキテクチャにおいて顕著でした。

Goランタイムは、システムコールを通じてメモリを割り当てたり解放したりする際に、内部のメモリ統計（`mstats`）を更新する必要があります。この更新には、アトミックな加算操作が用いられます。以前は`xadd64()`という64ビットのアトミック加算関数が使用されていました。しかし、ARMアーキテクチャの一部実装では、`xadd64()`が内部的にロックを使用しており、このロックは有効なG（Goルーチン）が存在することを前提としていました。

`sysAlloc()`や`sysFree()`のような低レベルのメモリ管理関数は、Goルーチンがまだ完全に初期化されていない、あるいはすでに終了しているような、有効なGが存在しない状況で呼び出される可能性があります。このような状況で`xadd64()`がロックを取得しようとすると、デッドロックやクラッシュといった未定義の動作を引き起こす可能性がありました。

この問題を解決するため、Dmitry Vyukov氏によって、一時的な解決策として`xadduintptr()`を使用することが提案されました。これは、ARMがすべてのアーキテクチャでロックを使用しない`xadd64()`をサポートするようになるまでのつなぎとして機能します。`xadduintptr()`は、ポインタサイズ（`uintptr`）のアトミック加算を行うため、64ビット値の更新にはオーバーフローチェックが必要になりますが、有効なGを必要としないため、低レベルのメモリ管理関数から安全に呼び出すことができます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とアトミック操作に関する知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、コンパイルされるとGoランタイムと呼ばれる小さなライブラリが組み込まれます。このランタイムは、ガベージコレクション、Goルーチンのスケジューリング、メモリ管理、チャネル操作など、Go言語の多くのコア機能を提供します。Goランタイムのコードは、Go言語自体で書かれている部分が多いですが、OSとの直接的なやり取りやパフォーマンスが重要な部分では、C言語やアセンブリ言語も使用されます。

2.  **Goルーチン (Goroutine) と G**:
    Goルーチンは、Goにおける軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムは、これらのGoルーチンをOSスレッドにマッピングし、スケジューリングを行います。
    `G`は、Goランタイム内部でGoルーチンを表すデータ構造（`runtime.g`構造体）を指します。この`G`構造体には、Goルーチンのスタック情報、現在の状態、スケジューリングに関連するデータなどが含まれています。多くのランタイム関数は、現在のGoルーチンの`G`コンテキストに依存して動作します。

3.  **アトミック操作 (Atomic Operations)**:
    アトミック操作とは、複数のCPUコアやスレッドから同時にアクセスされた場合でも、その操作全体が不可分（中断されない）であることを保証する操作です。これにより、競合状態（Race Condition）を防ぎ、データの整合性を保つことができます。Goでは`sync/atomic`パッケージを通じてアトミック操作が提供されますが、ランタイム内部ではさらに低レベルのアセンブリ命令や組み込み関数が使用されます。
    *   **`xadd64()`**: 64ビット整数に対するアトミックな加算操作を指します。通常、指定されたメモリ位置の値に指定されたデルタ値をアトミックに加算し、加算前の元の値を返します。
    *   **`xadduintptr()`**: `uintptr`型（ポインタサイズに依存する符号なし整数型）に対するアトミックな加算操作を指します。これも同様に、指定されたメモリ位置の値にデルタ値をアトミックに加算し、加算前の元の値を返します。`uintptr`は32ビットシステムでは32ビット、64ビットシステムでは64ビットのサイズを持ちます。

4.  **ARMアーキテクチャ**:
    ARMは、モバイルデバイスや組み込みシステムで広く使用されているプロセッサアーキテクチャです。GoはARMを含む様々なアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたランタイムコードを含んでいます。ARMv8.2以降のアーキテクチャでは、`LDADD`のようなハードウェアレベルのアトミック命令が提供されており、Goランタイムはこれらを活用して効率的な並行処理を実現しています。しかし、古いARMアーキテクチャや特定の実装では、64ビットのアトミック操作がハードウェアで直接サポートされていない場合があり、その場合はソフトウェア的にロックを使用してエミュレートされることがあります。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ統計更新におけるアトミック操作の安全性の問題と、その解決策としての`xadduintptr`の導入です。

**問題点**:
Goランタイムの`sysAlloc`や`sysFree`といった低レベルのメモリ割り当て/解放関数は、システムから直接メモリを要求したり解放したりします。これらの関数は、Goルーチンがまだ存在しない、あるいはすでに終了しているような、Goルーチン（G）のコンテキストが確立されていない状況でも呼び出される可能性があります。
Goランタイムは、割り当てられたメモリや解放されたメモリの量を追跡するために、`mstats`（メモリ統計）を更新します。この更新には、`xadd64`のようなアトミックな加算操作が使用されていました。
しかし、ARMアーキテクチャの一部では、`xadd64`の実装が内部的にロック（ミューテックスなど）を使用しています。このロックは、Goランタイムのスケジューラが管理する有効なGが存在することを前提としています。Gが存在しない状態でロックを取得しようとすると、ランタイムがデッドロックに陥ったり、クラッシュしたりする可能性がありました。これは、Goランタイムの初期化フェーズや終了フェーズなど、Gが利用できない状況でメモリ操作が行われる場合に特に問題となります。

**解決策**:
Dmitry Vyukov氏の提案に基づき、`xadduintptr`という新しいアトミック操作が導入されました。
`xadduintptr`は、`uintptr`型（ポインタサイズに依存する整数型）の値をアトミックに加算します。32ビットシステムでは32ビット、64ビットシステムでは64ビットの値を扱います。
この`xadduintptr`は、ARMアーキテクチャにおいて、有効なGを必要としないアトミック操作として実装されています。これにより、`sysAlloc`や`sysFree`のようなGに依存しない関数からでも安全にメモリ統計を更新できるようになりました。

**実装の詳細**:
*   **`xadduintptr`の導入**: `src/runtime/atomic_*.go`ファイル群（`atomic_386.go`, `atomic_amd64x.go`, `atomic_arm.go`, `atomic_arm64.go`, `atomic_ppc64x.go`など）に`xadduintptr`関数の宣言が追加されました。これらの関数は、各アーキテクチャのアセンブリコード（例: `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`）で実装され、既存の`xadd64`または`xadd`を呼び出すようにリダイレクトされています。これは、`uintptr`のサイズが`xadd64`または`xadd`が扱うサイズと一致する場合に、既存の実装を再利用できるためです。
*   **`mSysStatInc`と`mSysStatDec`の導入**: `src/runtime/mstats.go`に`mSysStatInc`と`mSysStatDec`という新しいヘルパー関数が追加されました。これらの関数は、システムメモリ統計をアトミックに増減させるためのラッパーです。
    *   これらの関数は、`_BigEndian`（ビッグエンディアンアーキテクチャかどうか）をチェックします。ビッグエンディアンの場合、`xadd64`を直接使用します。
    *   リトルエンディアンアーキテクチャの場合、`xadduintptr`を使用して統計を更新します。
    *   `xadduintptr`は`uintptr`を扱うため、64ビットの統計を更新する際にオーバーフローが発生する可能性があります。そのため、`mSysStatInc`と`mSysStatDec`では、`val < n`（インクリメント時のオーバーフロー）や`val+n < n`（デクリメント時のアンダーフロー）といったオーバーフロー/アンダーフローチェックが追加され、異常な場合は`exit(2)`でプログラムを終了させます。これは、`xadduintptr`が64ビット値を完全に安全に扱えないことに対する一時的な対策です。
*   **`sysAlloc`/`sysFree`の変更**: `src/runtime/malloc.go`および各OS固有のメモリ管理ファイル（`mem_bsd.go`, `mem_darwin.go`, `mem_linux.go`, `mem_plan9.go`, `mem_windows.go`）において、`sysAlloc`、`sysFree`、`sysMap`関数が、メモリ統計を更新する際に直接`xadd64`を呼び出す代わりに、新しく導入された`mSysStatInc`および`mSysStatDec`を呼び出すように変更されました。これにより、Gのコンテキストに依存しない安全なアトミック操作が保証されます。
*   **テストの追加**: `src/runtime/atomic_test.go`という新しいテストファイルが追加され、`xadduintptr`の機能と、それが64ビット値に対して正しく動作するか（特に下位ビットの更新）が検証されています。

この変更は、ARMアーキテクチャにおける`xadd64`のロック依存性の問題を回避するための暫定的な措置であり、将来的にはARMがロックフリーな64ビットアトミック操作をネイティブにサポートすることが望まれています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/runtime/mstats.go`に導入された`mSysStatInc`と`mSysStatDec`関数、およびそれらが`sysAlloc`/`sysFree`などの低レベルメモリ管理関数でどのように利用されるかです。

### `src/runtime/mstats.go`における変更

```go
// Atomically increases a given *system* memory stat.  We are counting on this
// stat never overflowing a uintptr, so this function must only be used for
// system memory stats.
//
// The current implementation for little endian architectures is based on
// xadduintptr(), which is less than ideal: xadd64() should really be used.
// Using xadduintptr() is a stop-gap solution until arm supports xadd64() that
// doesn't use locks.  (Locks are a problem as they require a valid G, which
// restricts their useability.)
//
// A side-effect of using xadduintptr() is that we need to check for
// overflow errors.
//go:nosplit
func mSysStatInc(sysStat *uint64, n uintptr) {
	if _BigEndian != 0 {
		xadd64(sysStat, int64(n))
		return
	}
	if val := xadduintptr((*uintptr)(unsafe.Pointer(sysStat)), n); val < n {
		print("runtime: stat overflow: val ", val, ", n ", n, "\n")
		exit(2)
	}
}

// Atomically decreases a given *system* memory stat.  Same comments as
// mSysStatInc apply.
//go:nosplit
func mSysStatDec(sysStat *uint64, n uintptr) {
	if _BigEndian != 0 {
		xadd64(sysStat, -int64(n))
		return
	}
	if val := xadduintptr((*uintptr)(unsafe.Pointer(sysStat)), uintptr(-int64(n))); val+n < n {
		print("runtime: stat underflow: val ", val, ", n ", n, "\n")
		exit(2)
	}
}
```

*   **`mSysStatInc(sysStat *uint64, n uintptr)`**:
    *   この関数は、システムメモリ統計（`sysStat`、`*uint64`型）を`n`（`uintptr`型）だけアトミックに増加させます。
    *   `//go:nosplit`ディレクティブは、この関数がスタックを分割しないことを保証します。これは、有効なGがない状況でも安全に呼び出せるようにするために重要です。
    *   `_BigEndian != 0`の条件で、システムがビッグエンディアンアーキテクチャであるかをチェックします。ビッグエンディアンの場合、既存の`xadd64`関数を直接使用します。これは、ビッグエンディアンシステムでは`xadd64`がロックを必要としない安全な実装を持っているためです。
    *   リトルエンディアンアーキテクチャの場合（特にARMのような問題のあるアーキテクチャを想定）、`xadduintptr`を使用します。`sysStat`は`*uint64`ですが、`xadduintptr`は`*uintptr`を期待するため、`unsafe.Pointer`を使って型変換を行っています。
    *   `xadduintptr`の戻り値`val`は、加算前の元の値です。`val < n`という条件でオーバーフローをチェックしています。これは、`uintptr`が64ビット値の一部しか表現できない場合（例: 32ビットシステムで64ビット統計を更新しようとする場合）や、`uintptr`の最大値を超えた場合に発生する可能性があります。オーバーフローが検出された場合、エラーメッセージを出力してプログラムを終了します。

*   **`mSysStatDec(sysStat *uint64, n uintptr)`**:
    *   この関数は、システムメモリ統計を`n`だけアトミックに減少させます。
    *   基本的なロジックは`mSysStatInc`と同様で、ビッグエンディアンの場合は`xadd64`を、リトルエンディアンの場合は`xadduintptr`を使用します。
    *   デクリメントの場合、`uintptr(-int64(n))`を使って負のデルタ値を`uintptr`に変換します。
    *   アンダーフローのチェックは`val+n < n`で行われます。これは、`val`（元の値）に`n`（減少量）を加えたものが`n`よりも小さい場合、アンダーフローが発生したことを意味します。

### `sysAlloc`/`sysFree`などにおける変更

以前は、`src/runtime/malloc.go`の`persistentalloc`関数や、`src/runtime/mem_*.go`ファイル群（`mem_bsd.go`, `mem_darwin.go`, `mem_linux.go`, `mem_plan9.go`, `mem_windows.go`）にある`sysAlloc`、`sysFree`、`sysMap`関数が、メモリ統計を更新する際に直接`xadd64`を呼び出していました。

このコミットでは、これらの関数が`xadd64`の直接呼び出しを`mSysStatInc`または`mSysStatDec`に置き換えるように変更されました。

この変更により、`sysAlloc`や`sysFree`のような低レベル関数は、Gのコンテキストに依存しない`mSysStatInc`/`mSysStatDec`を通じてメモリ統計を安全に更新できるようになり、ARMアーキテクチャにおける潜在的なデッドロックやクラッシュの問題が回避されます。これは、Goランタイムの堅牢性と、様々なアーキテクチャへの移植性を高める上で重要な改善です。

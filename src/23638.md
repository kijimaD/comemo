# [インデックス 23638] ファイルの概要

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal/gc` において、AST (Abstract Syntax Tree) ノードを表す `Node` 構造体から `Alloc` フィールドを削除し、代わりに `prealloc` というグローバルマップを使用して一時的な割り当て情報を管理するように変更したものです。これにより、`Node` 構造体のメモリフットプリントが削減され、コンパイラのパフォーマンス向上に寄与します。

## 変更の背景

Goコンパイラは、ソースコードを解析し、中間表現（ASTなど）を構築して最適化を行い、最終的に機械語に変換します。この過程で、ASTノードを表す `Node` 構造体は頻繁に生成され、多くの情報を持つため、そのサイズはコンパイラのメモリ使用量とパフォーマンスに大きな影響を与えます。

以前のGoコンパイラでは、`Node` 構造体内に `Alloc` というフィールドがあり、これは特定のASTノードに関連付けられた一時的なメモリ割り当て情報を保持していました。しかし、この `Alloc` フィールドは全ての `Node` で常に使用されるわけではなく、一部のノードでのみ意味を持つものでした。`Node` 構造体はコンパイラ内で非常に多用されるため、未使用のフィールドが存在すると、全体のメモリフットプリントが増大し、キャッシュ効率の低下やガベージコレクションの負荷増加につながります。

このコミットの目的は、`Node` 構造体から `Alloc` フィールドを削除し、その結果として `Node` のサイズを削減することです。コミットメッセージにある `$ sizeof -p cmd/compile/internal/gc Node` の出力 `Node 240` は、この変更によって `Node` 構造体のサイズが削減されたことを示唆しています（変更前のサイズは不明ですが、削減されたことが強調されています）。これにより、コンパイラのメモリ効率が向上し、全体的なコンパイル時間の短縮が期待されます。

## 前提知識の解説

### Goコンパイラ (`cmd/compile/internal/gc`) の概要

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。`cmd/compile/internal/gc` パッケージは、Goコンパイラの主要な部分であり、字句解析、構文解析、型チェック、中間コード生成、最適化、コード生成といったコンパイルの各フェーズを担当します。

### AST (Abstract Syntax Tree) と `Node` 構造体

AST (Abstract Syntax Tree) は、ソースコードの構造を木構造で表現したものです。コンパイラはソースコードを解析してASTを構築し、このASTを基に様々な処理を行います。Goコンパイラでは、このASTの各要素（変数、式、関数呼び出しなど）を `Node` 構造体で表現します。`Node` 構造体は、その種類（`Op`）、型情報（`Type`）、名前（`Name`）、子ノード（`Left`, `Right`, `List`, `Rlist`）など、ASTの要素に関する詳細な情報を保持します。

### メモリ割り当てとガベージコレクションの基本

プログラムが実行中に必要とするメモリは、ヒープ領域から動的に割り当てられます。Go言語にはガベージコレクタ (GC) が組み込まれており、不要になったメモリ領域を自動的に解放します。しかし、頻繁な小さなメモリ割り当ては、GCのオーバーヘッドを増加させ、プログラムのパフォーマンスに悪影響を与える可能性があります。

### Goにおける一時的なオブジェクトの扱い

コンパイラのようなシステムでは、一時的に使用されるオブジェクトが大量に生成されます。これらのオブジェクトがヒープに割り当てられると、GCの対象となり、パフォーマンスのボトルネックになることがあります。そのため、コンパイラは一時的なオブジェクトの割り当てを最適化するための様々な手法を用います。例えば、スタック割り当て（エスケープ解析によってヒープ割り当てが不要と判断された場合）や、アリーナ割り当て（特定の期間だけ有効なオブジェクトをまとめて管理する）などがあります。

### `Node.Alloc` と `prealloc` マップの役割

*   **`Node.Alloc` (変更前)**: 以前は `Node` 構造体の中に `Alloc *Node` というフィールドがありました。これは、特定の `Node` に関連付けられた一時的な割り当て（例えば、クロージャのキャプチャ変数やスライスリテラルのバッキング配列など）を指す `Node` へのポインタでした。このフィールドは、主にコンパイラの `walk` フェーズや `order` フェーズで、一時的な変数やバッファの割り当てを管理するために使われていました。しかし、全ての `Node` がこのフィールドを必要とするわけではないため、メモリの無駄が生じていました。
*   **`prealloc` マップ (変更後)**: このコミットでは、`Node.Alloc` フィールドを削除し、代わりに `var prealloc = map[*Node]*Node{}` というグローバルマップを導入しました。このマップは、`*Node` をキーとして、それに関連付けられた一時的な割り当てを表す `*Node` を値として保持します。これにより、`Node` 構造体自体のサイズを削減しつつ、必要なノードに対してのみ一時的な割り当て情報を管理できるようになります。マップを使用することで、必要な時にのみ情報を格納し、不要になったら削除（`delete(prealloc, func_)`）することで、より柔軟かつ効率的なメモリ管理が可能になります。

## 技術的詳細

このコミットの核心は、`Node` 構造体から `Alloc` フィールドを削除し、その機能を `prealloc` というグローバルマップに移行した点にあります。

1.  **`Node.Alloc` フィールドの削除**:
    `src/cmd/compile/internal/gc/syntax.go` に定義されている `Node` 構造体から `Alloc *Node` フィールドが削除されました。これにより、`Node` 構造体のサイズが小さくなり、コンパイラ全体のメモリ使用量が削減されます。特に、ASTノードは大量に生成されるため、このサイズ削減は大きな効果をもたらします。

3.  **`Node.Alloc` から `prealloc[n]` への置き換え**:
    コンパイラの様々な箇所で `n.Alloc` へのアクセスが `prealloc[n]` へのアクセスに置き換えられました。これにより、一時的な割り当て情報の管理が `Node` 構造体から `prealloc` マップへと移管されました。

    *   **`src/cmd/compile/internal/gc/closure.go`**: クロージャや部分適用 (`OCLOSURE`, `OCALLPART`) の処理において、一時的な割り当ての型設定や関連付けが `prealloc` マップを介して行われるようになりました。処理が完了すると、`delete(prealloc, func_)` でマップからエントリが削除されます。
    *   **`src/cmd/compile/internal/gc/gen.go`**: `cgen_dcl` 関数内で、ヒープエスケープする変数に対する割り当てが `prealloc` マップを通じて行われます。
    *   **`src/cmd/compile/internal/gc/order.go`**: `orderstmt` や `orderexpr` 関数内で、`ordertemp` によって生成された一時変数が `prealloc[n]` に格納されるようになりました。`ordertemp` は、コンパイラが一時的に使用する変数を生成する関数です。
    *   **`src/cmd/compile/internal/gc/range.go`**: `walkrange` 関数内で、`range` ループのイテレータに対する一時的な割り当てが `prealloc[n]` から取得されます。
    *   **`src/cmd/compile/internal/gc/sinit.go`**: スライスリテラル (`OSLICELIT`) の処理において、一時的なバッキング配列の割り当てが `prealloc` マップを介して管理されます。
    *   **`src/cmd/compile/internal/gc/walk.go`**: `mkdotargslice` や `paramstoheap`, `addstr` といった関数で、可変引数スライス、ヒープエスケープするパラメータ、文字列結合などに関連する一時的な割り当てが `prealloc` マップを通じて処理されます。

この変更により、`Node` 構造体はより汎用的なASTノードの情報を保持するようになり、特定の割り当てに関する情報は必要な場合にのみ `prealloc` マップから参照されるようになりました。これは、メモリ効率とコードの関心事の分離という点で改善をもたらします。

## コアとなるコードの解説

### `Node` 構造体からの `Alloc` フィールド削除

`Node` 構造体から `Alloc *Node` フィールドが削除されたことで、`Node` オブジェクトのインスタンスごとに `Alloc` フィールド分のメモリが不要になりました。これは、コンパイラが扱うASTノードの総数が非常に多いため、全体としてかなりのメモリ削減につながります。`Alloc` フィールドは、特定のノード（例えば、クロージャやスライスリテラルなど）にのみ関連する一時的な割り当て情報を保持していましたが、全ての `Node` がこの情報を必要とするわけではありませんでした。この変更により、`Node` 構造体はより汎用的なASTノードの表現に特化し、メモリ効率が向上しました。

### `prealloc` マップの導入

`prealloc` は `map[*Node]*Node` 型のグローバル変数として導入されました。このマップは、ASTノード (`*Node`) をキーとして、そのノードに関連付けられた一時的な割り当て (`*Node`) を値として格納します。
例えば、`ordertemp` 関数で一時変数が作成される際、その一時変数を表す `Node` が `prealloc[元のNode]` に格納されます。これにより、`Node` 構造体自体に割り当て情報を直接持たせるのではなく、必要なノードに対してのみ、このマップを介して割り当て情報を参照・更新する仕組みが実現されました。
マップを使用することで、必要な時にのみエントリを追加し、不要になったら `delete(prealloc, key)` でエントリを削除できるため、メモリをより動的に、かつ効率的に管理できます。

### `closure.go` における `n.Alloc` から `prealloc[n]` への置き換え例

上記の `closure.go` の変更箇所では、`walkclosure` 関数内でクロージャに関連する一時的な割り当ての処理が行われています。

変更前は `func_.Alloc` を直接参照・更新していました。`func_.Alloc` が `nil` でない場合、その `Alloc` フィールドが指す `Node` の型を設定し、`clos.Left.Right` に割り当て、最後に `func_.Alloc` を `nil` にしていました。

変更後は、`if x := prealloc[func_]; x != nil` という形で `prealloc` マップから `func_` に関連付けられた一時的な割り当て `x` を取得します。`x` が存在すれば、その `x` の型を設定し、`clos.Left.Right` に割り当てます。そして、処理が完了したことを示すために `delete(prealloc, func_)` を呼び出し、マップからこのエントリを削除しています。

この変更により、`Node` 構造体から `Alloc` フィールドが削除された後も、クロージャの一時的な割り当てを適切に管理できるようになりました。マップを使用することで、必要なノードにのみ割り当て情報を関連付け、処理完了後にクリーンアップするメカニズムが提供されています。

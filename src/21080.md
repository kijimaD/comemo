## 元コミット内容

`[dev.power64] 9g: fix width check and width calculation for OADDR`

このコミットは、PowerPC 64-bitアーキテクチャ向けのGoコンパイラ（`9g`）において、`OADDR`（アドレスオペランド）の幅チェックと幅計算に関する問題を修正するものです。

## 変更の背景

Goコンパイラは、様々なアーキテクチャ向けにコードを生成します。このコミットは、特にPowerPC 64-bit (`power64`) アーキテクチャをターゲットとした`9g`コンパイラに焦点を当てています。

問題の核心は、`OADDR`、つまりメモリ上のアドレスを指すオペランドの扱いに関するものでした。コンパイラがコードを生成する際、各オペランドが占めるメモリ上の「幅」（バイト数）を正確に把握する必要があります。PowerPC 64-bitのような64-bitアーキテクチャでは、ポインタやアドレスは通常64-bit（8バイト）の幅を持ちます。

しかし、このコミット以前の`9g`コンパイラには、`OADDR`の幅チェックと計算に不具合がありました。特に、`AMOVD`や`AMOVDU`といった命令（データを移動させる命令）において、定数（`D_CONST`）がアドレスとして扱われる場合に、不適切な幅チェックが行われる可能性がありました。また、`naddr`関数では、`OADDR`の幅を無条件に`widthptr`（ポインタの幅、通常は8バイト）に設定していましたが、これが常に正しいとは限りませんでした。

これらの不正確な幅の扱いは、コンパイラが生成するアセンブリコードの誤りや、実行時のクラッシュ、または非効率なコード生成につながる可能性がありました。このコミットは、これらの問題を修正し、PowerPC 64-bit環境でのGoプログラムの安定性と正確性を向上させることを目的としています。

## 前提知識の解説

*   **Goコンパイラと`9g`**: Go言語のコンパイラは、ソースコードを機械語に変換する役割を担います。歴史的に、Goのツールチェインでは、各アーキテクチャ向けのコンパイラが`{arch}g`という命名規則で呼ばれていました。例えば、x86-64向けは`6g`、ARM向けは`5g`、そしてPowerPC向けは`9g`でした。現在では、これらのコンパイラは統合され、`go tool compile`として抽象化されていますが、内部的にはこれらのバックエンドの概念が残っています。このコミットは、特にPowerPC 64-bit (`power64`) アーキテクチャ向けのバックエンドに関するものです。
*   **`OADDR` (Address Operand)**: コンパイラ内部で、メモリ上のアドレスを指すオペランドの種類です。例えば、`*ptr`や`struct.field`のように、メモリ上の特定の位置を参照する際に使用されます。
*   **`width` (幅)**: データ型やオペランドがメモリ上で占めるバイト数を指します。例えば、64-bit整数は8バイトの幅を持ちます。ポインタの幅は、ターゲットアーキテクチャのアドレス空間のサイズに依存し、64-bitアーキテクチャでは通常8バイトです。
*   **`gins`関数**: Goコンパイラのバックエンドにおいて、アセンブリ命令を生成する役割を持つ関数の一つです。オペランドの型や命令の種類に応じて、適切なアセンブリコードを生成します。
*   **`naddr`関数**: 抽象構文木（AST）のノードから、アセンブラが理解できるアドレス表現（`Addr`構造体）を構築する関数です。この関数は、変数のアドレスや構造体メンバーのアドレスなどを計算し、その結果を`Addr`構造体に格納します。
*   **`D_CONST`**: オペランドが定数であることを示す型です。
*   **`AMOVD` / `AMOVDU`**: PowerPCアーキテクチャにおけるデータ移動命令です。`AMOVD`はダブルワード（64-bit）の移動、`AMOVDU`は更新付きのダブルワード移動（ロード後にベースレジスタを更新）を意味します。
*   **PowerPC 64-bit (`power64`)**: IBMが開発したRISCプロセッサアーキテクチャであるPowerPCの64-bit版です。このアーキテクチャは、サーバーや組み込みシステムなどで広く利用されています。64-bitアーキテクチャであるため、アドレス空間も64-bit幅を持ちます。

## 技術的詳細

このコミットは、`src/cmd/9g/gsubr.c`ファイル内の2つの主要な関数、`gins`と`naddr`における`OADDR`の処理を改善しています。

1.  **`gins`関数における`AMOVD`/`AMOVDU`命令の幅チェックの修正**:
    *   以前のコードでは、`AMOVD`または`AMOVDU`命令の場合、無条件に幅を8バイト（`w = 8`）に設定していました。
    *   しかし、`af.type == D_CONST`（つまり、ソースオペランドが定数である場合）には、幅のチェックや設定を行う必要がありませんでした。定数はメモリ上のアドレスではなく、直接命令に埋め込まれるか、レジスタにロードされるため、その「幅」をアドレスとして扱うのは不適切です。
    *   修正後は、`af.type == D_CONST`の場合に`break`することで、この不必要な幅チェックと設定をスキップするように変更されました。これにより、定数がアドレスとして誤って扱われることを防ぎ、コンパイラの正確性が向上します。

2.  **`naddr`関数における`OADDR`の幅計算の修正**:
    *   以前のコードでは、`OADDR`の場合に`naddr(n->left, a, canemitcode)`を呼び出した後、無条件に`a->width = widthptr;`と設定していました。`widthptr`はポインタの幅（PowerPC 64-bitでは8バイト）を意味します。
    *   しかし、`OADDR`が常にポインタの幅を持つとは限りません。例えば、構造体のフィールドへのオフセット計算など、アドレス自体が直接的なポインタではない場合もあります。`naddr`関数は、`OADDR`の左の子ノード（`n->left`）を再帰的に処理することで、そのアドレスの基底となる部分を計算します。この基底部分の幅は、その型によって適切に設定されるべきであり、`OADDR`であるという理由だけで無条件に`widthptr`を設定するのは誤りでした。
    *   この行を削除することで、`OADDR`の実際の幅は、その基底となるアドレスの型から適切に推論されるようになります。これにより、コンパイラが生成するアドレス計算がより正確になり、潜在的なバグが修正されます。

これらの変更により、GoコンパイラはPowerPC 64-bitアーキテクチャにおいて、アドレスオペランドの幅をより正確に扱い、より堅牢なコードを生成できるようになります。

## コアとなるコードの解説

1.  **`gins`関数内の変更**:
    *   `case AMOVD:` と `case AMOVDU:` のブロック内に、以下の行が追加されました。
        ```c
        if(af.type == D_CONST)
            break;
        ```
    *   これは、`AMOVD`または`AMOVDU`命令のソースオペランド（`af`）が定数（`D_CONST`）である場合、それ以降の幅設定（`w = 8;`）をスキップすることを意味します。定数はアドレスではないため、アドレスの幅を割り当てるのは不適切であり、この修正によってコンパイラのロジックがより正確になりました。

2.  **`naddr`関数内の変更**:
    *   `case OADDR:` のブロック内から、以下の行が削除されました。
        ```c
        a->width = widthptr;
        ```
    *   この行は、`OADDR`タイプのオペランドに対して、無条件にポインタの幅（`widthptr`）を割り当てていました。しかし、`OADDR`が常にポインタの幅を持つとは限らず、その実際の幅は`n->left`（アドレスの基底となる部分）の型から適切に推論されるべきです。この行の削除により、`naddr`関数はより柔軟かつ正確にアドレスの幅を決定できるようになりました。

これらの変更は、GoコンパイラがPowerPC 64-bitアーキテクチャにおいて、メモリ上のアドレスと定数の扱いを区別し、オペランドの幅をより正確に計算することを保証します。これにより、生成される機械語コードの正確性と信頼性が向上します。

# [インデックス 23325] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）におけるスキャン作業量の見積もり方法を改善するものです。具体的には、GCが次回のサイクルで必要となるスキャン作業量を推定する際に、過去のスキャン作業比率の移動平均を使用する代わりに、現在のスキャン可能なヒープサイズを直接使用するように変更しています。これにより、ヒープの構造が大きく変化した場合にGCが作業量を見誤り、パフォーマンスが著しく低下する問題を解決します。

    runtime: use heap scan size as estimate of GC scan work

    Currently, the GC uses a moving average of recent scan work ratios to
    estimate the total scan work required by this cycle. This is in turn
    used to compute how much scan work should be done by mutators when
    they allocate in order to perform all expected scan work by the time
    the allocated heap reaches the heap goal.

    However, our current scan work estimate can be arbitrarily wrong if
    the heap topography changes significantly from one cycle to the
    next. For example, in the go1 benchmarks, at the beginning of each
    benchmark, the heap is dominated by a 256MB no-scan object, so the GC
    learns that the scan density of the heap is very low. In benchmarks
    that then rapidly allocate pointer-dense objects, by the time of the
    next GC cycle, our estimate of the scan work can be too low by a large
    factor. This in turn lets the mutator allocate faster than the GC can
    collect, allowing it to get arbitrarily far ahead of the scan work
    estimate, which leads to very long GC cycles with very little mutator
    assist that can overshoot the heap goal by large margins. This is
    particularly easy to demonstrate with BinaryTree17:

## 元コミット内容

GoのGCは現在、過去のスキャン作業比率の移動平均を使用して、現在のGCサイクルで必要となる総スキャン作業量を見積もっています。この見積もりは、アロケータ（ミューテータ）がヒープゴールに達するまでに必要なスキャン作業量を計算するために使用されます。

しかし、ヒープのトポグラフィ（構造）がサイクル間で大きく変化すると、現在のスキャン作業量の見積もりが著しく不正確になる可能性があります。例えば、go1ベンチマークの開始時には、ヒープが256MBの「スキャン不要オブジェクト」で占められているため、GCはヒープのスキャン密度が非常に低いと学習します。その後、ポインタ密度の高いオブジェクトが急速に割り当てられるベンチマークでは、次のGCサイクルまでにスキャン作業量の見積もりが大幅に過小評価される可能性があります。

これにより、ミューテータはGCが回収できるよりも速くオブジェクトを割り当ててしまい、スキャン作業量の見積もりを大幅に上回ってしまいます。その結果、ミューテータアシストがほとんど行われない非常に長いGCサイクルが発生し、ヒープゴールを大幅に超過する可能性があります。これは特に`BinaryTree17`ベンチマークで顕著に現れていました。

このコミットは、この見積もりを代わりに「現在のスキャン可能なヒープサイズ」を使用するように変更します。このアプローチは、過去の密度や到達可能なヒープサイズに依存せず、ヒープの現在の状態のみに基づいているため、このような「フェーズ変化」中にGCが遅れをとることを防ぎます。これは厳密には過大評価になりますが、過小評価して制御不能になるよりも、必要以上にアシストを行う方が良いと判断されました。この見積もりをスケールバックする実験では、ミューテータの利用率、ヒープサイズ、またはアシスト時間において明確な利点は見られませんでした。

この新しい見積もりは、ほとんどのベンチマーク（go1ベンチマーク、x/benchmarks、6gベンチマークを含む）にはほとんど影響を与えません。しかし、以前の不適切なペーサー動作を引き起こしていたベンチマークには大きな影響を与え、特に`BinaryTree17`では実行時間が64.93%改善されました。

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCの効率性を維持するためには、プログラム（ミューテータ）がオブジェクトを割り当てる速度と、GCがそれらを回収・スキャンする速度のバランスを取ることが重要です。このバランスを調整するメカニズムが「GCペーシング」です。

従来のGCペーシングでは、GCが次回のサイクルでどれだけのスキャン作業が必要になるかを予測するために、過去のGCサイクルにおける「スキャン作業量とマークされたヒープサイズの比率（`workRatioAvg`）」の移動平均を使用していました。この比率は、ヒープ内のポインタ密度（スキャンが必要なオブジェクトの割合）を間接的に示していました。

しかし、このアプローチには大きな問題がありました。プログラムの実行中にヒープの「トポグラフィ」が劇的に変化するシナリオ、例えば、最初はポインタを含まない大きなオブジェクト（例：バイト配列）が大量に割り当てられ、その後、ポインタを多数含む小さなオブジェクト（例：ツリー構造）が急速に割り当てられるような場合です。

このような状況では、GCは最初の段階でヒープのスキャン密度が低いと学習し、`workRatioAvg`が低い値になります。その結果、次のGCサイクルでポインタ密度の高いオブジェクトが大量に発生しても、GCは過去の低い`workRatioAvg`に基づいてスキャン作業量を過小評価してしまいます。これにより、ミューテータはGCの処理能力を上回る速度でオブジェクトを割り当て続け、GCは追いつけなくなります。この状態は「GCの暴走」や「ヒープゴールの超過」と呼ばれ、GCサイクルが非常に長くなり、プログラム全体のパフォーマンスが著しく低下する原因となっていました。

この問題は、特に`BinaryTree17`のような特定のベンチマークで顕著に現れており、GCがヒープの急激な変化に適応できないことが示されていました。このコミットは、この根本的な問題を解決し、GCペーシングの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な概念と、特にGCペーシングに関する知識が必要です。

1.  **ガベージコレクション (GC)**:
    *   GoのGCは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降、コンカレント（並行）マーク＆スイープGCが採用されており、プログラムの実行（ミューテータの動作）と並行してGCが動作します。これにより、GCによるプログラムの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ**: GCは、到達可能なオブジェクト（プログラムから参照されているオブジェクト）をマークします。
    *   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）をメモリから解放します。
    *   **スキャン作業**: マークフェーズにおいて、オブジェクトがポインタを含んでいる場合、そのポインタが指す先のオブジェクトも到達可能であるかをチェックする必要があります。このポインタをたどる作業が「スキャン作業」です。ポインタ密度の高いオブジェクトが多いほど、スキャン作業量は増大します。

2.  **GCペーシング (GC Pacing)**:
    *   GCペーシングは、GCの作業量とミューテータ（ユーザープログラム）のメモリ割り当て速度のバランスを調整するメカニズムです。目標は、GCがヒープの成長に追いつき、ヒープサイズを一定の目標値（ヒープゴール）に保ちながら、ミューテータの実行を可能な限り妨げないことです。
    *   **ヒープゴール (Heap Goal)**: 次のGCサイクルが完了するまでにヒープが到達してもよい最大サイズです。この目標を超えると、GCはより積極的に動作する必要があります。
    *   **ミューテータアシスト (Mutator Assist)**: GCがヒープの成長に追いつけない場合、ミューテータ（ユーザープログラム）がメモリを割り当てる際に、GC作業の一部を肩代わりさせることがあります。これをミューテータアシストと呼びます。これにより、GCの遅延を補償し、ヒープゴールを超過するのを防ぎます。ミューテータアシストはプログラムの実行速度を低下させるため、最小限に抑えることが望ましいです。

3.  **`workRatioAvg` (旧来の推定方法)**:
    *   これは、過去のGCサイクルで「マークされたバイト数あたりのスキャン作業量」の移動平均を計算した値です。GCはこれを使って、次回のGCサイクルでどれだけのスキャン作業が必要になるかを予測していました。
    *   問題点：ヒープのポインタ密度が急激に変化すると、過去の平均値が現在の状況を正確に反映できず、スキャン作業量を過小評価する可能性がありました。

4.  **`memstats.heap_scan` (新しい推定方法)**:
    *   これは、現在のヒープ内で「スキャンが必要なバイト数」を直接示す統計値です。つまり、ポインタを含む可能性のあるオブジェクトが占めるメモリの総量です。
    *   この値は、ヒープの現在の状態を直接反映するため、ヒープトポグラフィの急激な変化にも即座に対応できます。

これらの概念を理解することで、このコミットがGo GCの安定性とパフォーマンスにどのように貢献しているかを深く把握できます。

## 技術的詳細

このコミットの核心は、Goランタイムのガベージコレクタ（GC）におけるスキャン作業量の見積もりロジックの変更です。具体的には、`src/runtime/mgc.go`ファイル内の`gcControllerState`構造体と、そのメソッドである`revise()`および`endCycle()`が変更されています。

### 変更前の問題点と`workRatioAvg`

変更前は、GCペーシングの主要なパラメータの一つとして`gcControllerState.workRatioAvg`が使用されていました。これは、過去のGCサイクルで実際に発生した「スキャン作業量（`scanWork`）をマークされたヒープサイズ（`work.bytesMarked`）で割った比率」の移動平均（Exponentially Weighted Moving Average, EWMA）でした。

この`workRatioAvg`は、ヒープ内のポインタ密度、つまり「1バイトのメモリをマークするのに平均してどれくらいのポインタスキャン作業が必要か」を推定するために使われていました。`revise()`関数内で、この`workRatioAvg`と前回のGCでマークされたヒープサイズ（`heapMarkedEstimate`）を乗算することで、次回のGCサイクルで予想される総スキャン作業量（`scanWorkExpected`）を計算していました。

```go
// 変更前のコード (抜粋)
heapMarkedEstimate := memstats.heap_marked
if heapMarkedEstimate < work.bytesMarked {
    heapMarkedEstimate = work.bytesMarked
}
scanWorkExpected := uint64(float64(heapMarkedEstimate) * c.workRatioAvg) // ここでworkRatioAvgを使用
```

このアプローチの問題は、`workRatioAvg`が過去のデータに依存しているため、ヒープの構造が急激に変化した場合に、現在のヒープのポインタ密度を正確に反映できない点にありました。例えば、大量のポインタを含まないデータ（例: `[]byte`）が解放され、その後すぐに大量のポインタを含むデータ（例: `*Node`）が割り当てられるようなシナリオでは、`workRatioAvg`は低い値のままとなり、`scanWorkExpected`が過小評価されてしまいます。これにより、GCは必要なスキャン作業量を予測できず、ミューテータアシストが不足し、GCがヒープの成長に追いつけなくなる「GCの暴走」が発生していました。

### 変更後の解決策と`memstats.heap_scan`

このコミットでは、`scanWorkExpected`の計算方法を根本的に変更しました。`workRatioAvg`とその関連ロジックを削除し、代わりに`memstats.heap_scan`という統計値を直接使用するようにしました。

`memstats.heap_scan`は、現在のヒープ内で「スキャンが必要なバイト数」を直接表す値です。これは、ポインタを含む可能性のあるオブジェクトが占めるメモリの総量であり、ヒープの現在の状態をリアルタイムに反映します。

```go
// 変更後のコード (抜粋)
scanWorkExpected := memstats.heap_scan // ここでheap_scanを直接使用
```

この変更により、`scanWorkExpected`は常に現在のヒープのスキャン可能な部分のサイズに基づいて計算されるため、ヒープトポグラフィの急激な変化にも即座に適応できるようになります。コミットメッセージにもあるように、これは厳密には「過大評価」になります。なぜなら、`heap_scan`はスキャンが必要な可能性のある全バイト数を示すため、実際にスキャンされるポインタの数よりも多くなる可能性があるからです。しかし、GCペーシングにおいては、過小評価してGCが暴走するよりも、過大評価してミューテータアシストを多めに実行する方が、全体の安定性とパフォーマンスにとって望ましいと判断されました。

### コード変更の具体的な影響

*   **`gcControllerState`構造体**: `workRatioAvg`フィールドが削除されました。
*   **`startCycle()`メソッド**: 変更なし。
*   **`revise()`メソッド**: `scanWorkExpected`の計算ロジックが、`workRatioAvg`を使用するものから`memstats.heap_scan`を直接使用するものに変更されました。これにより、GCがサイクル中にスキャン作業量を再評価する際の精度が向上します。
*   **`endCycle()`メソッド**: `workRatio`の計算、`workRatioAvg`の更新、および`w_a`、`w_ewma`といったデバッグ出力の関連部分が削除されました。これは、`workRatioAvg`が不要になったためです。

この変更は、GCペーシングの堅牢性を大幅に向上させ、特にヒープのポインタ密度が大きく変動するワークロードにおいて、GCの暴走を防ぎ、より安定したパフォーマンスを提供します。

## 元コミット内容

GoのGCは現在、過去のスキャン作業比率の移動平均を使用して、現在のGCサイクルで必要となる総スキャン作業量を見積もっています。この見積もりは、アロケータ（ミューテータ）がヒープゴールに達するまでに必要なスキャン作業量を計算するために使用されます。

しかし、ヒープのトポグラフィ（構造）がサイクル間で大きく変化すると、現在のスキャン作業量の見積もりが著しく不正確になる可能性があります。例えば、go1ベンチマークの開始時には、ヒープが256MBの「スキャン不要オブジェクト」で占められているため、GCはヒープのスキャン密度が非常に低いと学習します。その後、ポインタ密度の高いオブジェクトが急速に割り当てられるベンチマークでは、次のGCサイクルまでにスキャン作業量の見積もりが大幅に過小評価される可能性があります。

これにより、ミューテータはGCが回収できるよりも速くオブジェクトを割り当ててしまい、スキャン作業量の見積もりを大幅に上回ってしまいます。その結果、ミューテータアシストがほとんど行われない非常に長いGCサイクルが発生し、ヒープゴールを大幅に超過する可能性があります。これは特に`BinaryTree17`ベンチマークで顕著に現れていました。

このコミットは、この見積もりを代わりに「現在のスキャン可能なヒープサイズ」を使用するように変更します。このアプローチは、過去の密度や到達可能なヒープサイズに依存せず、ヒープの現在の状態のみに基づいているため、このような「フェーズ変化」中にGCが遅れをとることを防ぎます。これは厳密には過大評価になりますが、過小評価して制御不能になるよりも、必要以上にアシストを行う方が良いと判断されました。この見積もりをスケールバックする実験では、ミューテータの利用率、ヒープサイズ、またはアシスト時間において明確な利点は見られませんでした。

この新しい見積もりは、ほとんどのベンチマーク（go1ベンチマーク、x/benchmarks、6gベンチマークを含む）にはほとんど影響を与えません。しかし、以前の不適切なペーサー動作を引き起こしていたベンチマークには大きな影響を与え、特に`BinaryTree17`では実行時間が64.93%改善されました。

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCの効率性を維持するためには、プログラム（ミューテータ）がオブジェクトを割り当てる速度と、GCがそれらを回収・スキャンする速度のバランスを取ることが重要です。このバランスを調整するメカニズムが「GCペーシング」です。

従来のGCペーシングでは、GCが次回のサイクルでどれだけのスキャン作業が必要になるかを予測するために、過去のGCサイクルにおける「スキャン作業量とマークされたヒープサイズの比率（`workRatioAvg`）」の移動平均を使用していました。この比率は、ヒープ内のポインタ密度（スキャンが必要なオブジェクトの割合）を間接的に示していました。

しかし、このアプローチには大きな問題がありました。プログラムの実行中にヒープの「トポグラフィ」が劇的に変化するシナリオ、例えば、最初はポインタを含まない大きなオブジェクト（例：バイト配列）が大量に割り当てられ、その後、ポインタを多数含む小さなオブジェクト（例：ツリー構造）が急速に割り当てられるような場合です。

このような状況では、GCは最初の段階でヒープのスキャン密度が低いと学習し、`workRatioAvg`が低い値になります。その結果、次のGCサイクルでポインタ密度の高いオブジェクトが大量に発生しても、GCは過去の低い`workRatioAvg`に基づいてスキャン作業量を過小評価してしまいます。これにより、ミューテータはGCの処理能力を上回る速度でオブジェクトを割り当て続け、GCは追いつけなくなります。この状態は「GCの暴走」や「ヒープゴールの超過」と呼ばれ、GCサイクルが非常に長くなり、プログラム全体のパフォーマンスが著しく低下する原因となっていました。

この問題は、特に`BinaryTree17`のような特定のベンチマークで顕著に現れており、GCがヒープの急激な変化に適応できないことが示されていました。このコミットは、この根本的な問題を解決し、GCペーシングの堅牢性を向上させることを目的としています。

1.  **ガベージコレクション (GC)**:
    *   GoのGCは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降、コンカレント（並行）マーク＆スイープGCが採用されており、プログラムの実行（ミューテータの動作）と並行してGCが動作します。これにより、GCによるプログラムの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ**: GCは、到達可能なオブジェクト（プログラムから参照されているオブジェクト）をマークします。
    *   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）をメモリから解放します。
    *   **スキャン作業**: マークフェーズにおいて、オブジェクトがポインタを含んでいる場合、そのポインタが指す先のオブジェクトも到達可能であるかをチェックする必要があります。このポインタをたどる作業が「スキャン作業」です。ポインタ密度の高いオブジェクトが多いほど、スキャン作業量は増大します。

2.  **GCペーシング (GC Pacing)**:
    *   GCペーシングは、GCの作業量とミューテータ（ユーザープログラム）のメモリ割り当て速度のバランスを調整するメカニズムです。目標は、GCがヒープの成長に追いつき、ヒープサイズを一定の目標値（ヒープゴール）に保ちながら、ミューテータの実行を可能な限り妨げないことです。
    *   **ヒープゴール (Heap Goal)**: 次のGCサイクルが完了するまでにヒープが到達してもよい最大サイズです。この目標を超えると、GCはより積極的に動作する必要があります。
    *   **ミューテータアシスト (Mutator Assist)**: GCがヒープの成長に追いつけない場合、ミューテータ（ユーザープログラム）がメモリを割り当てる際に、GC作業の一部を肩代わりさせることがあります。これをミューテータアシストと呼びます。これにより、GCの遅延を補償し、ヒープゴールを超過するのを防ぎます。ミューテータアシストはプログラムの実行速度を低下させるため、最小限に抑えることが望ましいです。

3.  **`workRatioAvg` (旧来の推定方法)**:
    *   これは、過去のGCサイクルで「マークされたバイト数あたりのスキャン作業量」の移動平均を計算した値です。GCはこれを使って、次回のGCサイクルでどれだけのスキャン作業が必要になるかを予測していました。
    *   問題点：ヒープのポインタ密度が急激に変化すると、過去の平均値が現在の状況を正確に反映できず、スキャン作業量を過小評価する可能性がありました。

4.  **`memstats.heap_scan` (新しい推定方法)**:
    *   これは、現在のヒープ内で「スキャンが必要なバイト数」を直接示す統計値です。つまり、ポインタを含む可能性のあるオブジェクトが占めるメモリの総量です。
    *   この値は、ヒープの現在の状態を直接反映するため、ヒープトポグラフィの急激な変化にも即座に対応できます。

これらの概念を理解することで、このコミットがGo GCの安定性とパフォーマンスにどのように貢献しているかを深く把握できます。

## 技術的詳細

このコミットの核心は、Goランタイムのガベージコレクタ（GC）におけるスキャン作業量の見積もりロジックの変更です。具体的には、`src/runtime/mgc.go`ファイル内の`gcControllerState`構造体と、そのメソッドである`revise()`および`endCycle()`が変更されています。

### 変更前の問題点と`workRatioAvg`

変更前は、GCペーシングの主要なパラメータの一つとして`gcControllerState.workRatioAvg`が使用されていました。これは、過去のGCサイクルで実際に発生した「スキャン作業量（`scanWork`）をマークされたヒープサイズ（`work.bytesMarked`）で割った比率」の移動平均（Exponentially Weighted Moving Average, EWMA）でした。

この`workRatioAvg`は、ヒープ内のポインタ密度、つまり「1バイトのメモリをマークするのに平均してどれくらいのポインタスキャン作業が必要か」を推定するために使われていました。`revise()`関数内で、この`workRatioAvg`と前回のGCでマークされたヒープサイズ（`heapMarkedEstimate`）を乗算することで、次回のGCサイクルで予想される総スキャン作業量（`scanWorkExpected`）を計算していました。

```go
// 変更前のコード (抜粋)
heapMarkedEstimate := memstats.heap_marked
if heapMarkedEstimate < work.bytesMarked {
    heapMarkedEstimate = work.bytesMarked
}
scanWorkExpected := uint64(float64(heapMarkedEstimate) * c.workRatioAvg) // ここでworkRatioAvgを使用
```

このアプローチの問題は、`workRatioAvg`が過去のデータに依存しているため、ヒープの構造が急激に変化した場合に、現在のヒープのポインタ密度を正確に反映できない点にありました。例えば、大量のポインタを含まないデータ（例: `[]byte`）が解放され、その後すぐに大量のポインタを含むデータ（例: `*Node`）が割り当てられるようなシナリオでは、`workRatioAvg`は低い値のままとなり、`scanWorkExpected`が過小評価されてしまいます。これにより、GCは必要なスキャン作業量を予測できず、ミューテータアシストが不足し、GCがヒープの成長に追いつけなくなる「GCの暴走」が発生していました。

### 変更後の解決策と`memstats.heap_scan`

このコミットでは、`scanWorkExpected`の計算方法を根本的に変更しました。`workRatioAvg`とその関連ロジックを削除し、代わりに`memstats.heap_scan`という統計値を直接使用するようにしました。

`memstats.heap_scan`は、現在のヒープ内で「スキャンが必要なバイト数」を直接表す値です。これは、ポインタを含む可能性のあるオブジェクトが占めるメモリの総量であり、ヒープの現在の状態をリアルタイムに反映します。

```go
// 変更後のコード (抜粋)
scanWorkExpected := memstats.heap_scan // ここでheap_scanを直接使用
```

この変更により、`scanWorkExpected`は常に現在のヒープのスキャン可能な部分のサイズに基づいて計算されるため、ヒープトポグラフィの急激な変化にも即座に適応できるようになります。コミットメッセージにもあるように、これは厳密には「過大評価」になります。なぜなら、`heap_scan`はスキャンが必要な可能性のある全バイト数を示すため、実際にスキャンされるポインタの数よりも多くなる可能性があるからです。しかし、GCペーシングにおいては、過小評価してGCが暴走するよりも、過大評価してミューテータアシストを多めに実行する方が、全体の安定性とパフォーマンスにとって望ましいと判断されました。

### コード変更の具体的な影響

*   **`gcControllerState`構造体**: `workRatioAvg`フィールドが削除されました。
*   **`startCycle()`メソッド**: 変更なし。
*   **`revise()`メソッド**: `scanWorkExpected`の計算ロジックが、`workRatioAvg`を使用するものから`memstats.heap_scan`を直接使用するものに変更されました。これにより、GCがサイクル中にスキャン作業量を再評価する際の精度が向上します。
*   **`endCycle()`メソッド**: `workRatio`の計算、`workRatioAvg`の更新、および`w_a`、`w_ewma`といったデバッグ出力の関連部分が削除されました。これは、`workRatioAvg`が不要になったためです。

これらの変更は、Go GCのペーシング戦略を、過去の動的な学習に基づくものから、現在のヒープの状態に直接基づく、より堅牢で即応性の高いものへとシフトさせるものです。これにより、ヒープトポグラフィの急激な変化によって引き起こされるGCのパフォーマンス問題が大幅に軽減されます。

## コアとなるコードの解説

このコミットの主要な変更点は、Goランタイムのガベージコレクタ（GC）のペーシングロジックにおけるスキャン作業量の見積もり方法の変更です。具体的には、`src/runtime/mgc.go`ファイル内の`gcControllerState`構造体と、その`revise()`メソッドが影響を受けています。

1.  **`gcControllerState`構造体からの`workRatioAvg`フィールドの削除**:
    *   変更前: `gcControllerState`には`workRatioAvg float64`というフィールドがありました。これは、過去のGCサイクルにおける「マークされたバイトあたりのスキャン作業量」の移動平均を保持していました。
    *   変更後: このフィールドは完全に削除されました。これは、スキャン作業量の見積もりに過去の比率を使用するアプローチが廃止されたことを意味します。

2.  **`gcController`初期化時の`workRatioAvg`の削除**:
    *   変更前: `var gcController = gcControllerState{ ... workRatioAvg: 0.5 / float64(ptrSize), ... }` のように、`workRatioAvg`が初期値で設定されていました。
    *   変更後: この初期化行も削除されています。

3.  **`gcControllerState.scanWork`フィールドのコメント更新**:
    *   `scanWork`フィールドは、GCサイクル中に蓄積されたスキャン作業量を表します。
    *   変更後: コメントが追加され、「現在、これはヒープのスキャンされたバイト数である。ほとんどの用途では不透明な作業単位だが、見積もりにおいてはその定義が重要である」と明記されました。これは、`scanWork`が単なる抽象的な作業量ではなく、具体的なヒープのスキャンバイト数として扱われるようになったことを示唆しています。

4.  **`revise()`メソッドにおける`scanWorkExpected`の計算ロジックの変更**:
    *   `revise()`メソッドは、コンカレントマーク中に定期的に呼び出され、GCの進行状況に基づいて見積もりを改善する役割を担います。
    *   変更前: `scanWorkExpected`は、`heapMarkedEstimate`（前回のGCでマークされたヒープサイズ、または現在の`work.bytesMarked`の大きい方）と`c.workRatioAvg`を乗算して計算されていました。
        ```go
        // 変更前のコード
        heapMarkedEstimate := memstats.heap_marked
        if heapMarkedEstimate < work.bytesMarked {
            heapMarkedEstimate = work.bytesMarked
        }
        scanWorkExpected := uint64(float64(heapMarkedEstimate) * c.workRatioAvg)
        ```
    *   変更後: `scanWorkExpected`の計算ロジックが大幅に簡素化され、`memstats.heap_scan`を直接使用するようになりました。
        ```go
        // 変更後のコード
        scanWorkExpected := memstats.heap_scan
        ```
        この変更により、スキャン作業量の見積もりは、過去の動的な比率ではなく、**現在のヒープ内でスキャン可能なバイト数の総量**に直接基づくことになります。コミットメッセージにあるように、これは「現在のヒープにおける可能なスキャン作業の厳密な上限」であり、過大評価ではあるものの、GCがヒープの急激な変化に追従できない問題を解決します。

5.  **`endCycle()`メソッドからの`workRatio`関連ロジックの削除**:
    *   `endCycle()`メソッドはGCサイクルの終了時に呼び出され、次回のGCサイクルのためのパラメータを更新します。
    *   変更前: `workRatio`（現在のサイクルのスキャン作業比率）を計算し、それを使って`workRatioAvg`を更新するロジック（EWMA）が存在しました。また、デバッグ出力にも`w_a`（`workRatio`）と`w_ewma`（`workRatioAvg`）が含まれていました。
    *   変更後: これらの`workRatio`の計算、`workRatioAvg`の更新、および関連するデバッグ出力がすべて削除されました。これは、`workRatioAvg`がGCペーシングの計算から完全に排除されたことを明確に示しています。

これらの変更は、Go GCのペーシング戦略を、過去の動的な学習に基づくものから、現在のヒープの状態に直接基づく、より堅牢で即応性の高いものへとシフトさせるものです。これにより、ヒープトポグラフィの急激な変化によって引き起こされるGCのパフォーマンス問題が大幅に軽減されます。

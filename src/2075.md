# [インデックス 2075] ファイルの概要

`src/cmd/6g/gen.c`は、Go言語のコンパイラの一部であり、特に`6g`という名前が示すように、64ビットアーキテクチャ（具体的にはx86-64）向けのコード生成を担当するファイルです。このファイルは、Goのソースコードから中間表現（AST: Abstract Syntax Tree）を受け取り、ターゲットアーキテクチャの機械語に近いアセンブリコードを生成する役割を担っています。`gen.c`には、様々なGoの操作（算術演算、論理演算、メモリ操作など）に対応するアセンブリ命令を生成するための関数群が含まれています。今回のコミットで変更された`cgen_shift`関数は、Go言語のシフト演算子（`<<`, `>>`）に対応するコードを生成する部分です。

## コミット

このコミットは、Goコンパイラのコード生成におけるシフト演算のバグを修正するものです。具体的には、より長いオペランド（シフト対象）をより短いオペランド（シフト量）でシフトする際に、シフト量のレジスタの上位ビットが適切にクリアされず、その結果、誤ったシフトが行われる可能性があった問題に対処しています。この修正により、シフト量がシフト対象のビット幅を超える場合に、期待通りに結果がゼロ（または符号拡張された値）になるように保証されます。

## 変更の背景

Go言語のシフト演算は、シフト量がシフト対象の型のビット幅以上である場合、結果がゼロになる（右シフトで符号付きの場合を除く）という明確なセマンティクスを持っています。しかし、このコミット以前の`6g`コンパイラでは、このセマンティクスが一部のケースで正しく実装されていませんでした。

具体的には、x86アーキテクチャのシフト命令（`SHL`, `SHR`, `SAR`など）は、シフト量を`CL`レジスタ（`CX`レジスタの下位8ビット）から取得します。もしGoのコードで指定されたシフト量が、例えば64ビット整数をシフトする際に64以上であったとしても、`CL`レジスタにはその値の`mod 256`の結果が格納されます。さらに重要なのは、`CX`レジスタの残りのビット（上位ビット）がゼロクリアされていない場合、その残存値がシフト命令の動作に影響を与える可能性があるという点です。

このバグは、シフト対象が64ビットのような「長い」オペランドであり、シフト量が32ビットのような「短い」オペランドとして扱われる場合に顕在化しました。コンパイラがシフト量を`CX`レジスタにロードする際、`CX`レジスタの残りのビットがゼロクリアされないままだと、シフト命令が意図しない動作をする可能性がありました。例えば、シフト量が65であったとしても、`CL`レジスタには65が格納されますが、`CX`レジスタ全体としては`0x...0041`のような値になり、この上位ビットの残存が問題を引き起こすことがありました。このコミットは、この「クリアされていないビット」の問題を解決し、Go言語のシフト演算のセマンティクスを正確に反映させることを目的としています。

## 前提知識の解説

### 1. Go言語のシフト演算

Go言語には、以下のシフト演算子があります。
*   `x << y`: `x`を`y`ビット左にシフトします。
*   `x >> y`: `x`を`y`ビット右にシフトします。
    *   符号なし整数または符号付き整数の非負値の場合、論理右シフト（上位ビットに0を挿入）。
    *   符号付き整数の負値の場合、算術右シフト（上位ビットに符号ビットを挿入）。

Go言語の仕様では、シフト量`y`がシフト対象`x`の型のビット幅以上の場合、結果は以下のようになります。
*   左シフト (`<<`) の場合、結果は常にゼロです。
*   右シフト (`>>`) の場合、結果は常にゼロです（ただし、符号付き整数で負の値を算術右シフトする場合は、結果はすべて1になります）。

### 2. Goコンパイラ (`6g`) とコード生成

*   **`6g`**: Goの初期のコンパイラの一つで、x86-64アーキテクチャ（AMD64）向けのコードを生成します。Goコンパイラは、Goのソースコードを解析し、抽象構文木（AST）を構築します。その後、ASTを中間表現に変換し、最終的にターゲットアーキテクチャの機械語（アセンブリコード）を生成します。
*   **`src/cmd/6g/gen.c`**: このファイルは、GoのASTノードを対応するアセンブリ命令に変換する「コードジェネレータ」の一部です。`cgen_shift`のような関数は、特定のGoの操作（この場合はシフト）に対して、適切なアセンブリ命令シーケンスを生成する責任を負います。
*   **`Node`**: コンパイラ内部でASTのノードを表す構造体です。Goの式や文が`Node`として表現されます。
*   **`Prog`**: 生成されるアセンブリ命令（`Prog`構造体）のリストを管理します。
*   **`optoas`**: Goの演算子（`OP_LSH`, `OP_RSH`など）をアセンブリ命令のオペコード（`ASHL`, `ASHR`など）に変換する関数です。
*   **`nodreg`, `regalloc`, `regfree`**: レジスタを割り当てたり、解放したり、レジスタを表す`Node`を作成したりするためのヘルパー関数です。コンパイラは、効率的なコードを生成するために、変数を一時的にCPUレジスタに割り当てます。
*   **`cgen`**: ASTノードからコードを生成する再帰的な関数です。
*   **`gmove`**: あるレジスタやメモリ位置から別の場所へ値を移動するアセンブリ命令を生成します。
*   **`nodconst`**: 定数を表す`Node`を作成します。
*   **`gins`**: アセンブリ命令を生成リストに追加します。
*   **`gbranch`**: 条件分岐命令を生成します。

### 3. x86アセンブリのシフト命令と`CL`レジスタ

x86アーキテクチャでは、シフト命令（例: `SHL`, `SHR`, `SAR`）は、シフト量を`CL`レジスタ（`ECX`または`RCX`レジスタの下位8ビット）から取得します。
*   例えば、`SHL RAX, CL`という命令は、`RAX`レジスタの内容を`CL`レジスタの値だけ左にシフトします。
*   重要なのは、シフト命令が参照するのは`CL`レジスタのみであり、`CX`、`ECX`、`RCX`レジスタの残りのビットはシフト量としては直接使用されないという点です。
*   しかし、`CL`レジスタに値をロードする際に、`CX`レジスタ全体に値が書き込まれることがあります。このとき、`CL`以外の`CH`や`CX`の上位ビットにゴミが残っていると、その後の処理で問題を引き起こす可能性があります。特に、シフト量がオペランドのビット幅（例: 64ビット整数に対する64）を超える場合、x86のシフト命令は通常、シフト量が64（または32）でモジュロ演算されたかのように振る舞います。Goのセマンティクスではゼロになるべきですが、アセンブリレベルではそうならない場合があります。

## 技術的詳細

このコミットの技術的詳細は、`cgen_shift`関数におけるシフト量の取り扱いと、それに伴うレジスタの管理の改善にあります。

1.  **シフト量レジスタの型変更と上位ビットのクリア**:
    *   変更前: `nodreg(&n1, types[TINT64], D_CX);`
        *   シフト量を格納する`n1`ノードが`TINT64`（64ビット整数）として扱われていました。`D_CX`は`CX`レジスタを指します。
    *   変更後:
        ```c
        nodreg(&n1, types[TUINT32], D_CX);        // to hold the shift type in CX
        regalloc(&n3, types[TUINT64], &n1);        // to clear high bits of CX
        ```
        *   `n1`の型が`TUINT32`（32ビット符号なし整数）に変更されました。これは、x86のシフト命令が`CL`レジスタ（8ビット）を使用することを考慮し、シフト量が32ビットの範囲で十分であることを示唆しています。
        *   さらに、`n3`という新しい一時レジスタが`TUINT64`型で導入されました。この`n3`は、`n1`（シフト量）を`CX`レジスタにロードする際に、`CX`レジスタの上位ビットを確実にゼロクリアするために使用されます。
        *   `regalloc(&n3, types[TUINT64], &n1);`は、`n3`を`n1`と同じレジスタ（`D_CX`）に割り当てつつ、その型を`TUINT64`とすることで、`CX`レジスタ全体を64ビットとして扱い、その内容をクリアする準備をします。

2.  **シフト量の移動と上位ビットのクリアの実行**:
    *   変更前は、シフト量`nr`を`n1`に`cgen(nr, &n1);`で直接生成していました。
    *   変更後:
        ```c
        cgen(nr, &n1);
        gmove(&n1, &n3);
        ```
        または
        ```c
        cgen(nr, &n1);
        gmove(&n1, &n3);
        cgen(nl, &n2);
        ```
        *   `cgen(nr, &n1);`でシフト量`nr`を`n1`（`CX`レジスタ）に生成した後、`gmove(&n1, &n3);`が追加されました。
        *   この`gmove`は、`n1`（`CX`レジスタの下位32ビットにシフト量が入っている）の内容を、`TUINT64`として扱われる`n3`（これも`CX`レジスタを指す）に移動します。この操作により、`CX`レジスタ全体が`n1`の値で上書きされ、特に`CL`以外の`CX`の上位ビットが確実にゼロクリアされます。これにより、シフト命令が`CL`レジスタを参照する際に、意図しない残存ビットの影響を受けることがなくなります。

3.  **シフト量とオペランド幅の比較の修正**:
    *   変更前:
        ```c
        nodconst(&n3, types[TUINT32], nl->type->width*8);
        gins(optoas(OCMP, types[TUINT32]), &n1, &n3);
        p1 = gbranch(optoas(OLT, types[TUINT32]), T);
        ```
    *   変更後:
        ```c
        nodconst(&n3, types[TUINT64], nl->type->width*8);
        gins(optoas(OCMP, types[TUINT64]), &n1, &n3);
        p1 = gbranch(optoas(OLT, types[TUINT64]), T);
        ```
        *   シフト量がオペランドのビット幅（`nl->type->width*8`）以上であるかをチェックする比較処理において、定数`n3`の型と比較命令のオペランド型が`TUINT32`から`TUINT64`に変更されました。
        *   これは、64ビットオペランドのシフト量を比較する際に、より正確な比較を行うためです。シフト量が64ビットの範囲で表現されるべきであり、比較もその範囲で行われるべきという意図があります。これにより、Goの仕様で定められた「シフト量がビット幅以上なら結果はゼロ」というセマンティクスが、64ビットオペランドに対しても正しく適用されるようになります。

これらの変更により、シフト量を格納するレジスタの準備がより厳密になり、特に`CX`レジスタの上位ビットの残存値がシフト演算に悪影響を与えるというバグが解消されました。

## 変更の背景

Go言語のシフト演算は、シフト量がシフト対象の型のビット幅以上である場合、結果がゼロになる（右シフトで符号付きの場合を除く）という明確なセマンティクスを持っています。しかし、このコミット以前の`6g`コンパイラでは、このセマンティクスが一部のケースで正しく実装されていませんでした。

具体的には、x86アーキテクチャのシフト命令（`SHL`, `SHR`, `SAR`など）は、シフト量を`CL`レジスタ（`ECX`または`RCX`レジスタの下位8ビット）から取得します。もしGoのコードで指定されたシフト量が、例えば64ビット整数をシフトする際に64以上であったとしても、`CL`レジスタにはその値の`mod 256`の結果が格納されます。さらに重要なのは、`CX`レジスタの残りのビット（上位ビット）がゼロクリアされていない場合、その残存値がシフト命令の動作に影響を与える可能性があるという点です。

このバグは、シフト対象が64ビットのような「長い」オペランドであり、シフト量が32ビットのような「短い」オペランドとして扱われる場合に顕在化しました。コンパイラがシフト量を`CX`レジスタにロードする際、`CX`レジスタの残りのビットがゼロクリアされないままだと、シフト命令が意図しない動作をする可能性がありました。例えば、シフト量が65であったとしても、`CL`レジスタには65が格納されますが、`CX`レジスタ全体としては`0x...0041`のような値になり、この上位ビットの残存が問題を引き起こすことがありました。このコミットは、この「クリアされていないビット」の問題を解決し、Go言語のシフト演算のセマンティクスを正確に反映させることを目的としています。

## 前提知識の解説

### 1. Go言語のシフト演算

Go言語には、以下のシフト演算子があります。
*   `x << y`: `x`を`y`ビット左にシフトします。
*   `x >> y`: `x`を`y`ビット右にシフトします。
    *   符号なし整数または符号付き整数の非負値の場合、論理右シフト（上位ビットに0を挿入）。
    *   符号付き整数の負値の場合、算術右シフト（上位ビットに符号ビットを挿入）。

Go言語の仕様では、シフト量`y`がシフト対象`x`の型のビット幅以上の場合、結果は以下のようになります。
*   左シフト (`<<`) の場合、結果は常にゼロです。
*   右シフト (`>>`) の場合、結果は常にゼロです（ただし、符号付き整数で負の値を算術右シフトする場合は、結果はすべて1になります）。

### 2. Goコンパイラ (`6g`) とコード生成

*   **`6g`**: Goの初期のコンパイラの一つで、x86-64アーキテクチャ（AMD64）向けのコードを生成します。Goコンパイラは、Goのソースコードを解析し、抽象構文木（AST）を構築します。その後、ASTを中間表現に変換し、最終的にターゲットアーキテクチャの機械語（アセンブリコード）を生成します。
*   **`src/cmd/6g/gen.c`**: このファイルは、GoのASTノードを対応するアセンブリ命令に変換する「コードジェネレータ」の一部です。`cgen_shift`のような関数は、特定のGoの操作（この場合はシフト）に対して、適切なアセンブリ命令シーケンスを生成する責任を負います。
*   **`Node`**: コンパイラ内部でASTのノードを表す構造体です。Goの式や文が`Node`として表現されます。
*   **`Prog`**: 生成されるアセンブリ命令（`Prog`構造体）のリストを管理します。
*   **`optoas`**: Goの演算子（`OP_LSH`, `OP_RSH`など）をアセンブリ命令のオペコード（`ASHL`, `ASHR`など）に変換する関数です。
*   **`nodreg`, `regalloc`, `regfree`**: レジスタを割り当てたり、解放したり、レジスタを表す`Node`を作成したりするためのヘルパー関数です。コンパイラは、効率的なコードを生成するために、変数を一時的にCPUレジスタに割り当てます。
*   **`cgen`**: ASTノードからコードを生成する再帰的な関数です。
*   **`gmove`**: あるレジスタやメモリ位置から別の場所へ値を移動するアセンブリ命令を生成します。
*   **`nodconst`**: 定数を表す`Node`を作成します。
*   **`gins`**: アセンブリ命令を生成リストに追加します。
*   **`gbranch`**: 条件分岐命令を生成します。

### 3. x86アセンブリのシフト命令と`CL`レジスタ

x86アーキテクチャでは、シフト命令（例: `SHL`, `SHR`, `SAR`）は、シフト量を`CL`レジスタ（`ECX`または`RCX`レジスタの下位8ビット）から取得します。
*   例えば、`SHL RAX, CL`という命令は、`RAX`レジスタの内容を`CL`レジスタの値だけ左にシフトします。
*   重要なのは、シフト命令が参照するのは`CL`レジスタのみであり、`CX`、`ECX`、`RCX`レジスタの残りのビットはシフト量としては直接使用されないという点です。
*   しかし、`CL`レジスタに値をロードする際に、`CX`レジスタ全体に値が書き込まれることがあります。このとき、`CL`以外の`CH`や`CX`の上位ビットにゴミが残っていると、その後の処理で問題を引き起こす可能性があります。特に、シフト量がオペランドのビット幅（例: 64ビット整数に対する64）を超える場合、x86のシフト命令は通常、シフト量が64（または32）でモジュロ演算されたかのように振る舞います。Goのセマンティクスではゼロになるべきですが、アセンブリレベルではそうならない場合があります。

## 技術的詳細

このコミットの技術的詳細は、`cgen_shift`関数におけるシフト量の取り扱いと、それに伴うレジスタの管理の改善にあります。

1.  **シフト量レジスタの型変更と上位ビットのクリア**:
    *   変更前: `nodreg(&n1, types[TINT64], D_CX);`
        *   シフト量を格納する`n1`ノードが`TINT64`（64ビット整数）として扱われていました。`D_CX`は`CX`レジスタを指します。
    *   変更後:
        ```c
        nodreg(&n1, types[TUINT32], D_CX);        // to hold the shift type in CX
        regalloc(&n3, types[TUINT64], &n1);        // to clear high bits of CX
        ```
        *   `n1`の型が`TUINT32`（32ビット符号なし整数）に変更されました。これは、x86のシフト命令が`CL`レジスタ（8ビット）を使用することを考慮し、シフト量が32ビットの範囲で十分であることを示唆しています。
        *   さらに、`n3`という新しい一時レジスタが`TUINT64`型で導入されました。この`n3`は、`n1`（シフト量）を`CX`レジスタにロードする際に、`CX`レジスタの上位ビットを確実にゼロクリアするために使用されます。
        *   `regalloc(&n3, types[TUINT64], &n1);`は、`n3`を`n1`と同じレジスタ（`D_CX`）に割り当てつつ、その型を`TUINT64`とすることで、`CX`レジスタ全体を64ビットとして扱い、その内容をクリアする準備をします。

2.  **シフト量の移動と上位ビットのクリアの実行**:
    *   変更前は、シフト量`nr`を`n1`に`cgen(nr, &n1);`で直接生成していました。
    *   変更後:
        ```c
        cgen(nr, &n1);
        gmove(&n1, &n3);
        ```
        または
        ```c
        cgen(nr, &n1);
        gmove(&n1, &n3);
        cgen(nl, &n2);
        ```
        *   `cgen(nr, &n1);`でシフト量`nr`を`n1`（`CX`レジスタ）に生成した後、`gmove(&n1, &n3);`が追加されました。
        *   この`gmove`は、`n1`（`CX`レジスタの下位32ビットにシフト量が入っている）の内容を、`TUINT64`として扱われる`n3`（これも`CX`レジスタを指す）に移動します。この操作により、`CX`レジスタ全体が`n1`の値で上書きされ、特に`CL`以外の`CX`の上位ビットが確実にゼロクリアされます。これにより、シフト命令が`CL`レジスタを参照する際に、意図しない残存ビットの影響を受けることがなくなります。

3.  **シフト量とオペランド幅の比較の修正**:
    *   変更前:
        ```c
        nodconst(&n3, types[TUINT32], nl->type->width*8);
        gins(optoas(OCMP, types[TUINT32]), &n1, &n3);
        p1 = gbranch(optoas(OLT, types[TUINT32]), T);
        ```
    *   変更後:
        ```c
        nodconst(&n3, types[TUINT64], nl->type->width*8);
        gins(optoas(OCMP, types[TUINT64]), &n1, &n3);
        p1 = gbranch(optoas(OLT, types[TUINT64]), T);
        ```
        *   シフト量がオペランドのビット幅（`nl->type->width*8`）以上であるかをチェックする比較処理において、定数`n3`の型と比較命令のオペランド型が`TUINT32`から`TUINT64`に変更されました。
        *   これは、64ビットオペランドのシフト量を比較する際に、より正確な比較を行うためです。シフト量が64ビットの範囲で表現されるべきであり、比較もその範囲で行われるべきという意図があります。これにより、Goの仕様で定められた「シフト量がビット幅以上なら結果はゼロ」というセマンティクスが、64ビットオペランドに対しても正しく適用されるようになります。

これらの変更により、シフト量を格納するレジスタの準備がより厳密になり、特に`CX`レジスタの上位ビットの残存値がシフト演算に悪影響を与えるというバグが解消されました。

## コアとなるコードの解説

1.  **`- int a, rcl;` から `+ int a;`**:
    *   `rcl`変数が削除されました。これは、以前のコードで`CX`レジスタの状態を保存するために使われていたものですが、新しいアプローチでは不要になったためです。

2.  **`- rcl = reg[D_CX];`**:
    *   `CX`レジスタの値を`rcl`に保存する行が削除されました。これは、シフト量の処理方法が変わったため、レジスタの明示的な保存が不要になったことを示します。

3.  **`- nodreg(&n1, types[TINT64], D_CX);`**:
    *   シフト量を格納する`n1`ノードを`TINT64`型（64ビット符号付き整数）として`CX`レジスタに割り当てる行が削除されました。

4.  **`- regalloc(&n1, nr->type, &n1);`**:
    *   `n1`にシフト量`nr`の型でレジスタを割り当てる行が削除されました。

5.  **`+ nodreg(&n1, types[TUINT32], D_CX); // to hold the shift type in CX`**:
    *   新しい`n1`の定義です。シフト量を格納する`n1`ノードを`TUINT32`型（32ビット符号なし整数）として`CX`レジスタに割り当てます。これにより、シフト量が32ビットの範囲で扱われることが明確になります。

6.  **`+ regalloc(&n3, types[TUINT64], &n1); // to clear high bits of CX`**:
    *   新しい一時レジスタ`n3`を導入し、`TUINT64`型（64ビット符号なし整数）として`n1`と同じレジスタ（`CX`）に割り当てます。この`n3`の目的は、`CX`レジスタの上位ビットを確実にゼロクリアすることです。

7.  **`+ gmove(&n1, &n3);` (2箇所)**:
    *   シフト量`nr`を`n1`に生成した後、`gmove(&n1, &n3);`が追加されました。この命令は、`n1`（`CX`レジスタの下位32ビットにシフト量が入っている）の内容を、`TUINT64`として扱われる`n3`（これも`CX`レジスタを指す）に移動します。これにより、`CX`レジスタ全体が`n1`の値で上書きされ、特に`CL`以外の`CX`の上位ビットが確実にゼロクリアされます。これは、x86のシフト命令が`CL`レジスタのみを参照する際に、`CX`レジスタの残存ビットが問題を引き起こすのを防ぐための重要なステップです。

8.  **`+ regfree(&n3);`**:
    *   一時レジスタ`n3`を解放します。これは、`n3`がその役割を終えたことをコンパイラに伝え、レジスタを再利用可能にするためのクリーンアップです。

9.  **`- nodconst(&n3, types[TUINT32], nl->type->width*8);`**:
    *   シフト量がオペランドのビット幅（`nl->type->width*8`）以上であるかをチェックするための定数`n3`の型が`TUINT32`から変更されました。

10. **`+ nodconst(&n3, types[TUINT64], nl->type->width*8);`**:
    *   定数`n3`の型が`TUINT64`に変更されました。これにより、64ビットオペランドのシフト量を比較する際に、より正確な比較が行われます。

11. **`- gins(optoas(OCMP, types[TUINT32]), &n1, &n3);`**:
    *   比較命令のオペランド型が`TUINT32`から変更されました。

12. **`+ gins(optoas(OCMP, types[TUINT64]), &n1, &n3);`**:
    *   比較命令のオペランド型が`TUINT64`に変更されました。これにより、シフト量が64ビットの範囲で表現されるべきであり、比較もその範囲で行われるべきという意図が反映されます。

13. **`- p1 = gbranch(optoas(OLT, types[TUINT32]), T);`**:
    *   条件分岐命令のオペランド型が`TUINT32`から変更されました。

14. **`+ p1 = gbranch(optoas(OLT, types[TUINT64]), T);`**:
    *   条件分岐命令のオペランド型が`TUINT64`に変更されました。

これらの変更は、シフト量を扱うレジスタの型をより適切に設定し、特に`CX`レジスタの上位ビットの残存値がシフト演算に悪影響を与えるというバグを解消するために、`gmove`による明示的なゼロクリア処理を追加したものです。これにより、Go言語のシフト演算のセマンティクスが、コンパイラによって正確に機械語に変換されるようになりました。

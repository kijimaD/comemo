# [インデックス 25565] ファイルの概要

このコミットは、GoとC言語間でポインタを渡す際の安全性チェックを導入するものです。特に、Goのガベージコレクタが管理するメモリへのポインタ（Goポインタ）をCコードに渡す際に発生しうる問題を軽減するための動的なチェックが追加されました。これにより、GoのランタイムとCコード間の相互運用におけるメモリ安全性が向上します。

## 元コミット内容

`cmd/cgo` および `runtime` パッケージにおいて、GoからCへポインタを渡す際のチェックを追加します。
これは、Issue 12416で提案された内容の一部を実装するもので、GoからCへポインタを渡す際の動的なチェックを追加します。このコードは常に有効になることを意図しています。ただし、すべてのケースを捕捉しようとするものではなく、CからGo関数を呼び出す際のチェックは実装していません。
新しいcgoチェックは `GODEBUG=cgocheck=0` を設定することで無効にできます。
Issue #12416を更新します。

## 変更の背景

Go言語はガベージコレクタ（GC）を持つ言語であり、GCはメモリを効率的に管理するために、Goヒープ上のオブジェクトを移動させることがあります。一方、C言語はGCを持たず、ポインタは通常、メモリ上の固定されたアドレスを指します。この根本的な違いが、GoとCの間でポインタを直接やり取りする際に問題を引き起こす可能性があります。

具体的には、GoのガベージコレクタがGoヒープ上のオブジェクトを移動させた場合、Cコードがそのオブジェクトを指すGoポインタを保持していると、Cコードが不正なメモリ領域にアクセスしようとしてクラッシュしたり、予期せぬ動作を引き起こしたりする可能性があります（Use-After-Freeのような問題）。

この問題に対処するため、GoコミュニティではIssue 12416「cmd/cgo: specify rules for passing pointers between Go and C」が提起されました。このIssueでは、GoとCの間でポインタを安全に受け渡すための厳格なルールを定義し、そのルールを強制するためのメカニズムを `cgo` ツールとGoランタイムに導入することが議論されました。

このコミットは、その提案の一部として、GoからCへポインタを渡す際に、GoポインタがGoポインタを含むメモリを指していないかを動的にチェックする機能を追加することで、このメモリ安全性の問題を解決しようとするものです。これにより、開発者が意図せず危険なポインタの受け渡しを行ってしまうことを防ぎ、Goプログラムの堅牢性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **Goのガベージコレクタ (GC)**: Goランタイムは自動的にメモリを管理します。不要になったメモリはGCによって解放されますが、GCはメモリの断片化を防ぐために、ヒープ上のオブジェクトを移動（コンパクション）させることがあります。
2.  **GoポインタとCポインタ**:
    *   **Goポインタ**: Goランタイムによって割り当てられたメモリ（`&`演算子や`new`関数など）を指すポインタを指します。これらのポインタが指すメモリはGCによって移動される可能性があります。
    *   **Cポインタ**: C言語の`malloc`などの関数によって割り当てられたメモリを指すポインタを指します。これらのポインタが指すメモリはGCの管理外であり、通常は移動しません。
3.  **cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。`import "C"` を使用してCコードをGoプログラムに組み込むことができます。
4.  **ポインタの受け渡しルール (Issue 12416で定義)**:
    *   **GoからCへGoポインタを渡す場合**: 渡されるGoポインタが指すGoメモリ領域が、**他のGoポインタを含んでいてはならない**という厳格なルールがあります。これは、Cコードがそのメモリを操作する際に、GCが移動させる可能性のあるGoポインタを誤って参照することを防ぐためです。
    *   **CコードがGoポインタを保持する場合**: Cコードは、Go関数呼び出しが終了した後、Goポインタのコピーを保持してはなりません。GoポインタはC関数が実行されている間のみ有効です。
    *   **CからGo関数を呼び出す場合**: Go関数はGoポインタを返してはなりません。また、Cポインタが指すメモリにGoポインタを格納してはなりません。
    *   **`unsafe.Pointer`**: Goの型システムを迂回して、任意の型をポインタとして扱うことができる特殊な型です。これを使用すると、上記のルールを意図的に破ることが可能ですが、その結果は予測不能な動作やクラッシュにつながる可能性があります。
5.  **`GODEBUG` 環境変数**: Goランタイムのデバッグ設定を制御するための環境変数です。`GODEBUG=name=value` の形式で設定し、ランタイムの挙動を変更できます。このコミットでは `cgocheck` という新しい設定が追加されました。

## 技術的詳細

このコミットは、`cgo`ツールとGoランタイムの両方に変更を加え、GoからCへポインタを渡す際の動的なチェックを実装しています。

**`cmd/cgo` (コンパイル時)**:
`cgo`ツールは、Goコード内のC関数呼び出しを解析し、ポインタ引数に対して追加のチェックコードを挿入するように変更されました。
1.  **AST解析の拡張**: `src/cmd/cgo/ast.go` では、Goコードの抽象構文木 (AST) を走査し、`C.xxx`形式のC関数呼び出しを特定する機能が強化されました。特に、`saveExprs`と`saveCall`関数が追加され、C関数への呼び出しを`File`構造体の`Calls`フィールドに収集するようになりました。
2.  **呼び出しの書き換え (`rewriteCalls`)**: `src/cmd/cgo/gcc.go` に`rewriteCalls`関数が追加されました。この関数は、GoコードからC関数への各呼び出しを走査し、ポインタ型の引数に対して`_cgoCheckPointer`というランタイム関数を呼び出すようにコードを書き換えます。
3.  **ポインタチェックの必要性判定 (`needsPointerCheck`, `hasPointer`)**: `needsPointerCheck`および`hasPointer`関数は、特定のGoの型がGoポインタを含む可能性があるかどうかを再帰的に判定します。例えば、スライス、マップ、チャネル、関数型、インターフェース型、またはGoポインタを含む構造体や配列は、Goポインタを含む可能性があると見なされます。
4.  **アドレス式に対する追加引数 (`checkAddrArgs`)**: `&s.f`のようなアドレス式が渡される場合、`_cgoCheckPointer`に追加の引数を渡すことで、チェックの範囲を最適化します。例えば、`&s.a[i]`のようにスライス要素のアドレスが渡される場合、スライス全体をチェックする必要があることをランタイムに伝えます。
5.  **`unsafe.Pointer`の特殊処理**: `unsafe.Pointer`を使用する型の場合、型アサーションの問題を回避するために、`_cgoCheckPointer`の特殊なバリアント（例: `_cgoCheckPointer0`, `_cgoCheckPointer1`など）が生成されます。これは`src/cmd/cgo/out.go`で実装されています。

**`runtime` (実行時)**:
`src/runtime/cgocall.go` に`cgoCheckPointer`関数が追加され、`cgo`ツールによって挿入されたチェックが実行時に機能します。
1.  **`cgoCheckPointer`関数**: `cgo`ツールによってGoからCへのポインタ引数に挿入されるエントリポイントです。この関数は、渡されたポインタがGoポインタであるかどうか、そしてそのGoポインタがさらにGoポインタを含むメモリを指しているかどうかを検査します。
2.  **`cgoCheckArg`関数**: `cgoCheckPointer`から呼び出され、実際の型に応じた詳細なポインタチェックを行います。
    *   配列、スライス、構造体などの複合型の場合、その要素やフィールドを再帰的に検査します。
    *   チャネル、マップ、関数型など、常にGoヒープに割り当てられる内部ポインタを持つ型がCに渡されようとすると、`panic`を発生させます。
    *   インターフェース型の場合、その動的な型情報やデータポインタがGoヒープにあるかを検査します。
3.  **`cgoCheckUnknownPointer`関数**: 任意のGoメモリへのポインタが、さらにGoポインタを含むかどうかを検査します。これは、ヒープビットマップ（GoのGCがオブジェクト内のポインタを識別するために使用する情報）を利用して行われます。
4.  **`cgoIsGoPointer`関数**: 与えられたポインタがGoランタイムによって管理されているメモリ（Goヒープ、データセクション、BSSセクションなど）を指しているかどうかを判定します。
5.  **`GODEBUG=cgocheck`**: `src/runtime/runtime1.go` に`debug.cgocheck`という新しいランタイムデバッグフラグが追加されました。デフォルトで`1`（有効）に設定されており、`GODEBUG=cgocheck=0`を設定することでこのチェックを無効にできます。

これらの変更により、GoからCへポインタを渡す際に、GoのメモリモデルとCのメモリモデルの不整合によって引き起こされる潜在的なバグを、コンパイル時と実行時の両方で検出できるようになりました。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go` における `rewriteCall` の概要

`rewriteCall`関数は、Goコード内の`C.funcName(arg1, arg2, ...)`のようなC関数呼び出しを、ポインタチェックを伴う形式に変換します。

```go
func (p *Package) rewriteCall(f *File, call *ast.CallExpr, name *Name) {
	for i, param := range name.FuncType.Params {
		// ... (nil引数のスキップなど) ...

		if !p.needsPointerCheck(f, param.Go) {
			continue // ポインタチェックが不要な型はスキップ
		}

		c := &ast.CallExpr{
			Fun: ast.NewIdent("_cgoCheckPointer"), // _cgoCheckPointerを呼び出す
			Args: []ast.Expr{
				call.Args[i], // 元の引数を渡す
			},
		}

		// アドレス式の場合、追加の引数を渡す
		if u, ok := call.Args[i].(*ast.UnaryExpr); ok && u.Op == token.AND {
			c.Args = p.checkAddrArgs(f, c.Args, u.X)
		}

		// _cgoCheckPointerの戻り値はinterface{}なので、型アサーションまたは特殊なバリアントを使用
		var arg ast.Expr
		if n := p.unsafeCheckPointerName(param.Go); n != "" {
			c.Fun = ast.NewIdent(n) // unsafe.Pointerを含む型の場合、特殊なバリアントを呼び出す
			arg = c
		} else {
			// 型アサーションを挿入
			c.Args[0] = &ast.CallExpr{
				Fun: param.Go,
				Args: []ast.Expr{
					c.Args[0],
				},
			}
			arg = &ast.TypeAssertExpr{
				X:    c,
				Type: param.Go,
			}
		}
		call.Args[i] = arg // 元の引数を書き換えられた引数に置き換える
	}
}
```
このコードは、C関数に渡される各引数について、それがポインタチェックを必要とする型であるかを`needsPointerCheck`で判断します。必要であれば、元の引数を`_cgoCheckPointer`関数（またはそのバリアント）の呼び出しでラップし、その結果を元の引数の位置に挿入します。これにより、C関数が実行される前にランタイムレベルでのポインタチェックが強制されます。

### `src/runtime/cgocall.go` における `cgoCheckPointer` の概要

`cgoCheckPointer`は、`cgo`ツールによって挿入された呼び出しを受け取り、実際のランタイムチェックを実行します。

```go
func cgoCheckPointer(ptr interface{}, args ...interface{}) interface{} {
	if debug.cgocheck == 0 {
		return ptr // デバッグフラグで無効化されている場合は何もしない
	}

	ep := (*eface)(unsafe.Pointer(&ptr)) // 渡されたinterface{}の型情報とデータポインタを取得
	t := ep._type

	top := true
	if len(args) > 0 && t.kind&kindMask == kindPtr {
		// ... (アドレス式に対する特殊処理) ...
	}

	cgoCheckArg(t, ep.data, t.kind&kindDirectIface == 0, top) // 実際のチェックロジックを呼び出す
	return ptr
}

func cgoCheckArg(t *_type, p unsafe.Pointer, indir, top bool) {
	if t.kind&kindNoPointers != 0 {
		return // ポインタを含まない型はスキップ
	}

	switch t.kind & kindMask {
	case kindArray:
		// 配列の各要素を再帰的にチェック
	case kindChan, kindMap:
		// チャネルやマップは常にGoポインタを含むため、panic
		panic(errorString(cgoCheckPointerFail))
	case kindFunc:
		// 関数ポインタがGoポインタであればpanic
	case kindInterface:
		// インターフェースの型情報やデータポインタがGoヒープにあればpanic
	case kindSlice:
		// スライスのバッキング配列の各要素を再帰的にチェック
	case kindStruct:
		// 構造体の各フィールドを再帰的にチェック
	case kindPtr, kindUnsafePointer:
		// ポインタがGoポインタであり、かつトップレベルでなければpanic
		// さらに、そのポインタが指すメモリが他のGoポインタを含んでいないかをcgoCheckUnknownPointerで検査
		cgoCheckUnknownPointer(p)
	// ...
	}
}
```
`cgoCheckPointer`は、まず`GODEBUG=cgocheck=0`で無効化されていないかを確認します。その後、渡された`interface{}`から型情報とデータポインタを抽出し、`cgoCheckArg`を呼び出して詳細なチェックを行います。`cgoCheckArg`は、Goの型システムに基づいて、ポインタが指すメモリがGoポインタを含んでいないか、または特定のGo型（チャネル、マップなど）がCに渡されようとしていないかを検査します。`cgoCheckUnknownPointer`は、Goヒープ上の任意のオブジェクトについて、その内部に他のGoポインタが含まれていないかを、GCのヒープビットマップを利用して効率的に検査します。これらのチェックに違反した場合、ランタイムは`panic`を発生させ、プログラムの異常終了を促します。

具体的には、GoのガベージコレクタがGoヒープ上のオブジェクトを移動させた場合、Cコードがそのオブジェクトを指すGoポインタを保持していると、Cコードが不正なメモリ領域にアクセスしようとしてクラッシュしたり、予期せぬ動作を引き起こしたりする可能性があります（Use-After-Freeのような問題）。

この問題に対処するため、GoコミュニティではIssue 12416「cmd/cgo: specify rules for passing pointers between Go and C」が提起されました。このIssueでは、GoとCの間でポインタを安全に受け渡すための厳格なルールを定義し、そのルールを強制するためのメカニズムを `cgo` ツールとGoランタイムに導入することが議論されました。

このコミットは、その提案の一部として、GoからCへポインタを渡す際に、GoポインタがGoポインタを含むメモリを指していないかを動的にチェックする機能を追加することで、このメモリ安全性の問題を解決しようとするものです。これにより、開発者が意図せず危険なポインタの受け渡しを行ってしまうことを防ぎ、Goプログラムの堅牢性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **Goのガベージコレクタ (GC)**: Goランタイムは自動的にメモリを管理します。不要になったメモリはGCによって解放されますが、GCはメモリの断片化を防ぐために、ヒープ上のオブジェクトを移動（コンパクション）させることがあります。
2.  **GoポインタとCポインタ**:
    *   **Goポインタ**: Goランタイムによって割り当てられたメモリ（`&`演算子や`new`関数など）を指すポインタを指します。これらのポインタが指すメモリはGCによって移動される可能性があります。
    *   **Cポインタ**: C言語の`malloc`などの関数によって割り当てられたメモリを指すポインタを指します。これらのポインタが指すメモリはGCの管理外であり、通常は移動しません。
3.  **cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。`import "C"` を使用してCコードをGoプログラムに組み込むことができます。
4.  **ポインタの受け渡しルール (Issue 12416で定義)**:
    *   **GoからCへGoポインタを渡す場合**: 渡されるGoポインタが指すGoメモリ領域が、**他のGoポインタを含んでいてはならない**という厳格なルールがあります。これは、Cコードがそのメモリを操作する際に、GCが移動させる可能性のあるGoポインタを誤って参照することを防ぐためです。
    *   **CコードがGoポインタを保持する場合**: Cコードは、Go関数呼び出しが終了した後、Goポインタのコピーを保持してはなりません。GoポインタはC関数が実行されている間のみ有効です。
    *   **CからGo関数を呼び出す場合**: Go関数はGoポインタを返してはなりません。また、Cポインタが指すメモリにGoポインタを格納してはなりません。
    *   **`unsafe.Pointer`**: Goの型システムを迂回して、任意の型をポインタとして扱うことができる特殊な型です。これを使用すると、上記のルールを意図的に破ることが可能ですが、その結果は予測不能な動作やクラッシュにつながる可能性があります。
5.  **`GODEBUG` 環境変数**: Goランタイムのデバッグ設定を制御するための環境変数です。`GODEBUG=name=value` の形式で設定し、ランタイムの挙動を変更できます。このコミットでは `cgocheck` という新しい設定が追加されました。

## 技術的詳細

このコミットは、`cgo`ツールとGoランタイムの両方に変更を加え、GoからCへポインタを渡す際の動的なチェックを実装しています。

**`cmd/cgo` (コンパイル時)**:
`cgo`ツールは、Goコード内のC関数呼び出しを解析し、ポインタ引数に対して追加のチェックコードを挿入するように変更されました。
1.  **AST解析の拡張**: `src/cmd/cgo/ast.go` では、Goコードの抽象構文木 (AST) を走査し、`C.xxx`形式のC関数呼び出しを特定する機能が強化されました。特に、`saveExprs`と`saveCall`関数が追加され、C関数への呼び出しを`File`構造体の`Calls`フィールドに収集するようになりました。
2.  **呼び出しの書き換え (`rewriteCalls`)**: `src/cmd/cgo/gcc.go` に`rewriteCalls`関数が追加されました。この関数は、GoコードからC関数への各呼び出しを走査し、ポインタ型の引数に対して`_cgoCheckPointer`というランタイム関数を呼び出すようにコードを書き換えます。
3.  **ポインタチェックの必要性判定 (`needsPointerCheck`, `hasPointer`)**: `needsPointerCheck`および`hasPointer`関数は、特定のGoの型がGoポインタを含む可能性があるかどうかを再帰的に判定します。例えば、スライス、マップ、チャネル、関数型、インターフェース型、またはGoポインタを含む構造体や配列は、Goポインタを含む可能性があると見なされます。
4.  **アドレス式に対する追加引数 (`checkAddrArgs`)**: `&s.f`のようなアドレス式が渡される場合、`_cgoCheckPointer`に追加の引数を渡すことで、チェックの範囲を最適化します。例えば、`&s.a[i]`のようにスライス要素のアドレスが渡される場合、スライス全体をチェックする必要があることをランタイムに伝えます。
5.  **`unsafe.Pointer`の特殊処理**: `unsafe.Pointer`を使用する型の場合、型アサーションの問題を回避するために、`_cgoCheckPointer`の特殊なバリアント（例: `_cgoCheckPointer0`, `_cgoCheckPointer1`など）が生成されます。これは`src/cmd/cgo/out.go`で実装されています。

**`runtime` (実行時)**:
`src/runtime/cgocall.go` に`cgoCheckPointer`関数が追加され、`cgo`ツールによって挿入されたチェックが実行時に機能します。
1.  **`cgoCheckPointer`関数**: `cgo`ツールによってGoからCへのポインタ引数に挿入されるエントリポイントです。この関数は、渡されたポインタがGoポインタであるかどうか、そしてそのGoポインタがさらにGoポインタを含むメモリを指しているかどうかを検査します。
2.  **`cgoCheckArg`関数**: `cgoCheckPointer`から呼び出され、実際の型に応じた詳細なポインタチェックを行います。
    *   配列、スライス、構造体などの複合型の場合、その要素やフィールドを再帰的にチェックします。
    *   チャネル、マップ、関数型など、常にGoヒープに割り当てられる内部ポインタを持つ型がCに渡されようとすると、`panic`を発生させます。
    *   インターフェース型の場合、その動的な型情報やデータポインタがGoヒープにあるかを検査します。
3.  **`cgoCheckUnknownPointer`関数**: 任意のGoメモリへのポインタが、さらにGoポインタを含むかどうかを検査します。これは、ヒープビットマップ（GoのGCがオブジェクト内のポインタを識別するために使用する情報）を利用して行われます。
4.  **`cgoIsGoPointer`関数**: 与えられたポインタがGoランタイムによって管理されているメモリ（Goヒープ、データセクション、BSSセクションなど）を指しているかどうかを判定します。
5.  **`GODEBUG=cgocheck`**: `src/runtime/runtime1.go` に`debug.cgocheck`という新しいランタイムデバッグフラグが追加されました。デフォルトで`1`（有効）に設定されており、`GODEBUG=cgocheck=0`を設定することでこのチェックを無効にできます。

これらの変更により、GoからCへポインタを渡す際に、GoのメモリモデルとCのメモリモデルの不整合によって引き起こされる潜在的なバグを、コンパイル時と実行時の両方で検出できるようになりました。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go` における `rewriteCall` の概要

`rewriteCall`関数は、Goコード内の`C.funcName(arg1, arg2, ...)`のようなC関数呼び出しを、ポインタチェックを伴う形式に変換します。

```go
func (p *Package) rewriteCall(f *File, call *ast.CallExpr, name *Name) {
	for i, param := range name.FuncType.Params {
		// ... (nil引数のスキップなど) ...

		if !p.needsPointerCheck(f, param.Go) {
			continue // ポインタチェックが不要な型はスキップ
		}

		c := &ast.CallExpr{
			Fun: ast.NewIdent("_cgoCheckPointer"), // _cgoCheckPointerを呼び出す
			Args: []ast.Expr{
				call.Args[i], // 元の引数を渡す
			},
		}

		// アドレス式の場合、追加の引数を渡す
		if u, ok := call.Args[i].(*ast.UnaryExpr); ok && u.Op == token.AND {
			c.Args = p.checkAddrArgs(f, c.Args, u.X)
		}

		// _cgoCheckPointerの戻り値はinterface{}なので、型アサーションまたは特殊なバリアントを使用
		var arg ast.Expr
		if n := p.unsafeCheckPointerName(param.Go); n != "" {
			c.Fun = ast.NewIdent(n) // unsafe.Pointerを含む型の場合、特殊なバリアントを呼び出す
			arg = c
		} else {
			// 型アサーションを挿入
			c.Args[0] = &ast.CallExpr{
				Fun: param.Go,
				Args: []ast.Expr{
					c.Args[0],
				},
			}
			arg = &ast.TypeAssertExpr{
				X:    c,
				Type: param.Go,
			}
		}
		call.Args[i] = arg // 元の引数を書き換えられた引数に置き換える
	}
}
```
このコードは、C関数に渡される各引数について、それがポインタチェックを必要とする型であるかを`needsPointerCheck`で判断します。必要であれば、元の引数を`_cgoCheckPointer`関数（またはそのバリアント）の呼び出しでラップし、その結果を元の引数の位置に挿入します。これにより、C関数が実行される前にランタイムレベルでのポインタチェックが強制されます。

### `src/runtime/cgocall.go` における `cgoCheckPointer` の概要

`cgoCheckPointer`は、`cgo`ツールによって挿入された呼び出しを受け取り、実際のランタイムチェックを実行します。

```go
func cgoCheckPointer(ptr interface{}, args ...interface{}) interface{} {
	if debug.cgocheck == 0 {
		return ptr // デバッグフラグで無効化されている場合は何もしない
	}

	ep := (*eface)(unsafe.Pointer(&ptr)) // 渡されたinterface{}の型情報とデータポインタを取得
	t := ep._type

	top := true
	if len(args) > 0 && t.kind&kindMask == kindPtr {
		// ... (アドレス式に対する特殊処理) ...
	}

	cgoCheckArg(t, ep.data, t.kind&kindDirectIface == 0, top) // 実際のチェックロジックを呼び出す
	return ptr
}

func cgoCheckArg(t *_type, p unsafe.Pointer, indir, top bool) {
	if t.kind&kindNoPointers != 0 {
		return // ポインタを含まない型はスキップ
	}

	switch t.kind & kindMask {
	case kindArray:
		// 配列の各要素を再帰的にチェック
	case kindChan, kindMap:
		// チャネルやマップは常にGoポインタを含むため、panic
		panic(errorString(cgoCheckPointerFail))
	case kindFunc:
		// 関数ポインタがGoポインタであればpanic
	case kindInterface:
		// インターフェースの型情報やデータポインタがGoヒープにあればpanic
	case kindSlice:
		// スライスのバッキング配列の各要素を再帰的にチェック
	case kindStruct:
		// 構造体の各フィールドを再帰的にチェック
	case kindPtr, kindUnsafePointer:
		// ポインタがGoポインタであり、かつトップレベルでなければpanic
		// さらに、そのポインタが指すメモリが他のGoポインタを含んでいないかをcgoCheckUnknownPointerで検査
		cgoCheckUnknownPointer(p)
	// ...
	}
}
```
`cgoCheckPointer`は、まず`GODEBUG=cgocheck=0`で無効化されていないかを確認します。その後、渡された`interface{}`から型情報とデータポインタを抽出し、`cgoCheckArg`を呼び出して詳細なチェックを行います。`cgoCheckArg`は、Goの型システムに基づいて、ポインタが指すメモリがGoポインタを含んでいないか、または特定のGo型（チャネル、マップなど）がCに渡されようとしていないかを検査します。`cgoCheckUnknownPointer`は、Goヒープ上の任意のオブジェクトについて、その内部に他のGoポインタが含まれていないかを、GCのヒープビットマップを利用して効率的に検査します。これらのチェックに違反した場合、ランタイムは`panic`を発生させ、プログラムの異常終了を促します。

## 変更の背景

この変更の背景には、WebアプリケーションにおけるURLの正規化（canonicalization）の重要性があります。

1.  **URLの一貫性**: Webサイトでは、同じコンテンツに対して複数のURLが存在することがあります（例: `/pkg/fmt` と `/pkg/fmt/`）。このような場合、検索エンジンはこれらを別々のページとして認識し、SEO（検索エンジン最適化）に悪影響を与える可能性があります。また、ユーザーにとっても、一貫性のないURLは混乱を招くことがあります。
2.  **キャッシュの効率化**: 正規化されていないURLは、Webキャッシュの効率を低下させる可能性があります。同じコンテンツが異なるURLで提供されると、それぞれが個別にキャッシュされ、リソースの無駄遣いにつながります。
3.  **HTTPリダイレクトの利用**: HTTPリダイレクト（特に301 Moved Permanently）は、古いURLや非正規なURLから新しい正規なURLへユーザーエージェント（ブラウザや検索エンジンクローラー）を自動的に転送するための標準的なメカニズムです。これにより、URLの変更や正規化を透過的に行うことができます。

このコミットは、`godoc` サーバーが提供するパッケージドキュメンテーションのURLについて、特に末尾のスラッシュの有無に関する一貫性を確保するために、HTTPリダイレクトを導入しました。これにより、例えば `/pkg/fmt` へのアクセスがあった場合に、自動的に `/pkg/fmt/` へリダイレクトすることで、常に正規のURLが使用されるようにします。

## 前提知識の解説

### 1. `godoc`

`godoc` は、Go言語のソースコードからドキュメンテーションを抽出し、Webブラウザで閲覧可能な形式で提供するツールです。Goの標準ライブラリやサードパーティのパッケージのドキュメンテーションは、`godoc` を通じて提供されています。`godoc` は、コード内のコメント（特にエクスポートされた識別子に付随するコメント）を解析し、Markdownのような形式で整形して表示します。

### 2. HTTPリダイレクト (301 Moved Permanently)

HTTPリダイレクトは、Webサーバーがクライアント（ブラウザなど）に対して、要求されたリソースが別のURLに移動したことを伝えるメカニズムです。
- **301 Moved Permanently**: 永続的な移動を示すステータスコードです。これは、リソースが恒久的に新しいURLに移動したことを意味し、検索エンジンは新しいURLをインデックスし、古いURLのランキングを新しいURLに引き継ぎます。ブラウザは通常、このリダイレクトをキャッシュします。
- **302 Found (または Moved Temporarily)**: 一時的な移動を示すステータスコードです。リソースが一時的に別のURLにあることを意味し、検索エンジンは古いURLをインデックスし続けます。

このコミットでは、URLの正規化という永続的な変更を意図しているため、`http.StatusMovedPermanently` (301) が使用されています。

### 3. Canonical URL (正規URL)

Canonical URLとは、同じコンテンツを持つ複数のURLの中から、検索エンジンにインデックスしてほしい「代表的な」URLを指します。WebサイトのSEOにおいて非常に重要であり、URLの重複コンテンツ問題を解決するために使用されます。このコミットでは、パッケージのURLの末尾にスラッシュを付ける形式を正規URLとして採用しています。

### 4. `pathutil.Clean`

`pathutil.Clean` は、Go言語の `path` パッケージ（またはその前身となるユーティリティ）に含まれる関数で、パス文字列を正規化するために使用されます。具体的には、以下のような処理を行います。
- 冗長なスラッシュ（例: `//`）を単一のスラッシュに置き換える。
- `.`（カレントディレクトリ）や `..`（親ディレクトリ）を解決する。
- 末尾のスラッシュを削除する（ただし、ルートパス `/` は例外）。

このコミットでは、`pathutil.Clean` を使用してパスを正規化し、その後に明示的に末尾にスラッシュを追加することで、パッケージの正規URLを生成しています。

-   **戻り値の調整**:
    `findPackage` 関数内のすべての `return` ステートメントが更新され、新しい `canonical` 戻り値を含むようになりました。例えば、パッケージが見つからない場合でも `return canonical, nil, subdirs;` のように `canonical` パスが返されるようになっています。

## コアとなるコードの解説

### `findPackage` 関数の変更点

1.  **`canonical string` の追加**: `findPackage` 関数が、パッケージのドキュメンテーション情報だけでなく、そのパッケージの「正規URLパス」も返すようになりました。これにより、呼び出し元はどのURLがそのパッケージの正式なアドレスであるかを知ることができます。
2.  **正規URLの計算**: `canonical = pathutil.Clean(Pkg + path) + "/";` この行が、正規URLを生成する核心部分です。`pathutil.Clean` でパスをクリーンアップした後、末尾にスラッシュを明示的に追加することで、`/pkg/fmt` のようなパスが `/pkg/fmt/` として正規化されます。これは、ディレクトリを表すURLには末尾にスラッシュがあるべきというWebの慣習に従っています。
3.  **一貫した戻り値**: パッケージが見つからない場合やエラーが発生した場合でも、`canonical` パスは常に返されるようになりました。これにより、`servePkg` 関数は常にリダイレクトの判断に必要な情報を得ることができます。

### `servePkg` 関数の変更点

1.  **`canonical` パスの取得**: `canonical, desc, dirs := findPackage(path);` `findPackage` から返される `canonical` パスを受け取ります。
2.  **リダイレクト条件のチェック**: `if r.Url.Path != canonical { ... }` この条件文が、現在のリクエストURLが正規URLと異なるかどうかをチェックします。例えば、ユーザーが `/pkg/fmt` にアクセスした場合、`r.Url.Path` は `/pkg/fmt` であり、`canonical` は `/pkg/fmt/` となるため、この条件が真になります。
3.  **HTTP 301リダイレクトの実行**: `http.Redirect(c, canonical, http.StatusMovedPermanently);` 条件が真の場合、`http.Redirect` 関数が呼び出され、クライアントを `canonical` パスに永続的にリダイレクトします。`http.StatusMovedPermanently` は、このリダイレクトが恒久的なものであることを示し、検索エンジンやブラウザにキャッシュされるべきであることを伝えます。
4.  **早期リターン**: リダイレクトが実行された場合、`return;` によって関数はそこで終了し、ドキュメンテーションのレンダリングなどの後続処理は行われません。これにより、無駄な処理を防ぎ、リダイレクトの効率を向上させます。
5.  **`path == ""` ロジックの移動**: `if path == ""` の処理がリダイレクトの後ろに移動されたのは、リダイレクトがURLの正規化というより高優先度のタスクであるためです。まずURLを正規化し、その後に表示上のパスの調整を行うという論理的な順序に従っています。

これらの変更により、`godoc` サーバーは、ユーザーがパッケージドキュメンテーションにアクセスする際に、常に正規化されたURLを使用するように強制し、Webサイトの健全性とSEOを向上させます。

## 変更の背景

この変更の背景には、WebアプリケーションにおけるURLの正規化（canonicalization）の重要性があります。

1.  **URLの一貫性**: Webサイトでは、同じコンテンツに対して複数のURLが存在することがあります（例: `/pkg/fmt` と `/pkg/fmt/`）。このような場合、検索エンジンはこれらを別々のページとして認識し、SEO（検索エンジン最適化）に悪影響を与える可能性があります。また、ユーザーにとっても、一貫性のないURLは混乱を招くことがあります。
2.  **キャッシュの効率化**: 正規化されていないURLは、Webキャッシュの効率を低下させる可能性があります。同じコンテンツが異なるURLで提供されると、それぞれが個別にキャッシュされ、リソースの無駄遣いにつながります。
3.  **HTTPリダイレクトの利用**: HTTPリダイレクト（特に301 Moved Permanently）は、古いURLや非正規なURLから新しい正規なURLへユーザーエージェント（ブラウザや検索エンジンクローラー）を自動的に転送するための標準的なメカニズムです。これにより、URLの変更や正規化を透過的に行うことができます。

このコミットは、`godoc` サーバーが提供するパッケージドキュメンテーションのURLについて、特に末尾のスラッシュの有無に関する一貫性を確保するために、HTTPリダイレクトを導入しました。これにより、例えば `/pkg/fmt` へのアクセスがあった場合に、自動的に `/pkg/fmt/` へリダイレクトすることで、常に正規のURLが使用されるようにします。

## 前提知識の解説

### 1. `godoc`

`godoc` は、Go言語のソースコードからドキュメンテーションを抽出し、Webブラウザで閲覧可能な形式で提供するツールです。Goの標準ライブラリやサードパーティのパッケージのドキュメンテーションは、`godoc` を通じて提供されています。`godoc` は、コード内のコメント（特にエクスポートされた識別子に付随するコメント）を解析し、Markdownのような形式で整形して表示します。

### 2. HTTPリダイレクト (301 Moved Permanently)

HTTPリダイレクトは、Webサーバーがクライアント（ブラウザなど）に対して、要求されたリソースが別のURLに移動したことを伝えるメカニズムです。
-   **301 Moved Permanently**: 永続的な移動を示すステータスコードです。これは、リソースが恒久的に新しいURLに移動したことを意味し、検索エンジンは新しいURLをインデックスし、古いURLのランキングを新しいURLに引き継ぎます。ブラウザは通常、このリダイレクトをキャッシュします。
-   **302 Found (または Moved Temporarily)**: 一時的な移動を示すステータスコードです。リソースが一時的に別のURLにあることを意味し、検索エンジンは古いURLをインデックスし続けます。

このコミットでは、URLの正規化という永続的な変更を意図しているため、`http.StatusMovedPermanently` (301) が使用されています。

### 3. Canonical URL (正規URL)

Canonical URLとは、同じコンテンツを持つ複数のURLの中から、検索エンジンにインデックスしてほしい「代表的な」URLを指します。WebサイトのSEOにおいて非常に重要であり、URLの重複コンテンツ問題を解決するために使用されます。このコミットでは、パッケージのURLの末尾にスラッシュを付ける形式を正規URLとして採用しています。

### 4. `pathutil.Clean`

`pathutil.Clean` は、Go言語の `path` パッケージ（またはその前身となるユーティリティ）に含まれる関数で、パス文字列を正規化するために使用されます。具体的には、以下のような処理を行います。
-   冗長なスラッシュ（例: `//`）を単一のスラッシュに置き換える。
-   `.`（カレントディレクトリ）や `..`（親ディレクトリ）を解決する。
-   末尾のスラッシュを削除する（ただし、ルートパス `/` は例外）。

このコミットでは、`pathutil.Clean` を使用してパスを正規化し、その後に明示的に末尾にスラッシュを追加することで、パッケージの正規URLを生成しています。

## 技術的詳細

このコミットの主要な変更点は、`findPackage` 関数のシグネチャと実装、および `servePkg` 関数でのその利用方法にあります。

### `findPackage` 関数の変更

-   **シグネチャの変更**:
    変更前: `func findPackage(path string) (*pakDesc, dirList)`
    変更後: `func findPackage(path string) (canonical string, pd *pakDesc, dirs dirList)`
    `findPackage` 関数は、これまでのパッケージ記述子 (`*pakDesc`) とサブディレクトリリスト (`dirList`) に加えて、新たに `canonical string` という戻り値を持つようになりました。この `canonical` 文字列が、そのパッケージの正規URLパスを表します。

-   **正規URLの生成**:
    関数内で、`canonical = pathutil.Clean(Pkg + path) + "/"` という行が追加されました。
    -   `Pkg` は、`godoc` サーバーがパッケージドキュメンテーションを提供するベースパス（例: `/pkg/`）であると推測されます。
    -   `Pkg + path` は、リクエストされたパッケージのフルパスを構築します。
    -   `pathutil.Clean(...)` は、このパスを正規化します（冗長なスラッシュの除去、`.` や `..` の解決、末尾スラッシュの除去）。
    -   最後に `+ "/"` を追加することで、正規化されたパスの末尾に明示的にスラッシュを付加し、これをパッケージの正規URLとして定義しています。

-   **戻り値の調整**:
    `findPackage` 関数内のすべての `return` ステートメントが更新され、新しい `canonical` 戻り値を含むようになりました。例えば、パッケージが見つからない場合でも `return canonical, nil, subdirs;` のように `canonical` パスが返されるようになっています。

### `servePkg` 関数の変更

-   **`findPackage` の呼び出し**:
    変更前: `desc, dirs := findPackage(path);`
    変更後: `canonical, desc, dirs := findPackage(path);`
    `servePkg` 関数は、`findPackage` の呼び出し結果から `canonical` パスを受け取るようになりました。

-   **HTTPリダイレクトの実装**:
    以前はコメントアウトされていたHTTPリダイレクトのロジックが有効化され、`canonical` パスを利用するように修正されました。
    ```go
    if r.Url.Path != canonical {
        http.Redirect(c, canonical, http.StatusMovedPermanently);
        return;
    }
    ```
    このコードは、現在のリクエストのURLパス (`r.Url.Path`) が `findPackage` によって計算された正規URLパス (`canonical`) と異なる場合、クライアントを正規URLに `301 Moved Permanently` ステータスでリダイレクトします。リダイレクト後、関数の残りの処理は実行されずに `return` します。

-   **`path == ""` ロジックの移動**:
    `if path == ""` のチェックと `path = "."` の割り当ては、リダイレクト処理の後に移動されました。これは、リダイレクトが優先されるべきであり、パスの表示形式の調整はリダイレクトが不要な場合にのみ行われるべきであるためです。

### `main` 関数の変更

-   `main` 関数での `findPackage` の呼び出しも、新しいシグネチャに合わせて変更されましたが、`canonical` 戻り値は使用されないため、`_` で無視されています。
    変更前: `desc, dirs := findPackage(flag.Arg(0));`
    変更後: `_, desc, dirs := findPackage(flag.Arg(0));`

これらの変更により、`godoc` サーバーは、パッケージのURLが常に末尾にスラッシュを持つ正規形式であることを保証し、URLの正規化と一貫性を実現しています。

## コアとなるコードの解説

### `findPackage` 関数の変更点

1.  **`canonical string` の追加**: `findPackage` 関数が、パッケージのドキュメンテーション情報だけでなく、そのパッケージの「正規URLパス」も返すようになりました。これにより、呼び出し元はどのURLがそのパッケージの正式なアドレスであるかを知ることができます。
2.  **正規URLの計算**: `canonical = pathutil.Clean(Pkg + path) + "/";` この行が、正規URLを生成する核心部分です。`pathutil.Clean` でパスをクリーンアップした後、末尾にスラッシュを明示的に追加することで、`/pkg/fmt` のようなパスが `/pkg/fmt/` として正規化されます。これは、ディレクトリを表すURLには末尾にスラッシュがあるべきというWebの慣習に従っています。
3.  **一貫した戻り値**: パッケージが見つからない場合やエラーが発生した場合でも、`canonical` パスは常に返されるようになりました。これにより、`servePkg` 関数は常にリダイレクトの判断に必要な情報を得ることができます。

### `servePkg` 関数の変更点

1.  **`canonical` パスの取得**: `canonical, desc, dirs := findPackage(path);` `findPackage` から返される `canonical` パスを受け取ります。
2.  **リダイレクト条件のチェック**: `if r.Url.Path != canonical { ... }` この条件文が、現在のリクエストURLが正規URLと異なるかどうかをチェックします。例えば、ユーザーが `/pkg/fmt` にアクセスした場合、`r.Url.Path` は `/pkg/fmt` であり、`canonical` は `/pkg/fmt/` となるため、この条件が真になります。
3.  **HTTP 301リダイレクトの実行**: `http.Redirect(c, canonical, http.StatusMovedPermanently);` 条件が真の場合、`http.Redirect` 関数が呼び出され、クライアントを `canonical` パスに永続的にリダイレクトします。`http.StatusMovedPermanently` は、このリダイレクトが恒久的なものであることを示し、検索エンジンやブラウザにキャッシュされるべきであることを伝えます。
4.  **早期リターン**: リダイレクトが実行された場合、`return;` によって関数はそこで終了し、ドキュメンテーションのレンダリングなどの後続処理は行われません。これにより、無駄な処理を防ぎ、リダイレクトの効率を向上させます。
5.  **`path == ""` ロジックの移動**: `if path == ""` の処理がリダイレクトの後ろに移動されたのは、リダイレクトがURLの正規化というより高優先度のタスクであるためです。まずURLを正規化し、その後に表示上のパスの調整を行うという論理的な順序に従っています。

これらの変更により、`godoc` サーバーは、ユーザーがパッケージドキュメンテーションにアクセスする際に、常に正規化されたURLを使用するように強制し、Webサイトの健全性とSEOを向上させます。

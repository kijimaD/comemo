# [インデックス 26076] ファイルの概要

このコミットは、Go言語のビルドシステムにおけるベンダーディレクトリ（`vendor`ディレクトリ）のサポートを強化するものです。具体的には、`go/build`パッケージの`Import`関数が、ベンダーディレクトリ内のパッケージを適切に解決し、インポートできるように変更されています。これにより、`go/loader`のようなツールがベンダーパッケージを使用するソースコードをより正確に処理できるようになります。

## 元コミット内容

`go/build: support vendor directories in Import`

この修正は、`golang.org/x/tools/go/loader`への1行の変更と合わせて、`loader`パッケージがベンダーパッケージを使用するソースコードを処理できるようにするものです。例えば、`GOPATH="" ssadump net/http`というコマンドは、`net/http`がベンダー化された`golang.org/x/net/http2/hpack`をインポートしている場合、以前は失敗していました。

このCL（変更リスト）と`loader`への修正（CL 17727）により、`ssadump`が動作するようになり、`golang.org/x/tools/go/loader`上に構築された他のほとんどのソースコード処理も同様に動作するようになることが期待されます。

Issue #12278 を修正します。

## 変更の背景

Go 1.5では、依存関係管理の改善を目的として「ベンダーエクスペリメント（Vendor Experiment）」が導入されました。これは、プロジェクトのルートディレクトリまたはそのサブディレクトリに`vendor`という名前のディレクトリを作成し、その中にプロジェクト固有の依存関係を配置することで、`GOPATH`に依存せずに依存関係を管理できるようにする仕組みです。

このコミット以前は、`go/build`パッケージの`Import`関数は、`vendor`ディレクトリ内のパッケージを自動的に解決する機能を持っていませんでした。そのため、`cmd/go`ツール自体が、`go/build`パッケージの外部でベンダーパスの解決ロジックを一部持っていました。しかし、`golang.org/x/tools/go/loader`のような、`go/build`パッケージを利用してGoのソースコードを解析するツールは、この外部ロジックを利用できず、ベンダーパッケージを含むプロジェクトを正しく処理できませんでした。

このコミットの目的は、`vendor`ディレクトリの解決ロジックを`go/build`パッケージの`Import`関数に組み込むことで、Goエコシステム全体でベンダーパッケージのサポートを一貫性のあるものにし、`go/loader`のようなツールがベンダーパッケージを透過的に扱えるようにすることです。これにより、Go 1.5のベンダーエクスペリメントの意図がより完全に実現されます。

## 前提知識の解説

### Go ModulesとVendorディレクトリ

Go言語の依存関係管理は、歴史的に`GOPATH`という環境変数に大きく依存していました。しかし、これは複数のプロジェクトで異なるバージョンの依存関係を管理する際に問題を引き起こすことがありました。

Go 1.5で導入された**ベンダーエクスペリメント**は、この問題に対する初期の解決策の一つでした。プロジェクトのルートディレクトリまたはそのサブディレクトリに`vendor`という名前のディレクトリを作成し、その中にプロジェクトが依存する外部パッケージのコピーを配置します。Goのツールチェインは、パッケージをインポートする際に、まず現在のパッケージの階層を遡って`vendor`ディレクトリを探し、そこに目的のパッケージがあればそれを使用します。これにより、`GOPATH`にインストールされているグローバルなパッケージよりも、プロジェクトローカルなベンダーパッケージが優先されるようになります。

Go 1.11でGo Modulesが導入され、Goの依存関係管理の主流はGo Modulesへと移行しましたが、`vendor`ディレクトリの概念はGo Modulesにおいても引き続き利用されます（`go mod vendor`コマンドで依存関係を`vendor`ディレクトリにコピーできます）。このコミットは、Go Modules以前のベンダーエクスペリメントの時代に、その基盤となる`go/build`パッケージの機能を強化したものです。

### `go/build`パッケージ

`go/build`パッケージは、Goのソースコードを解析し、パッケージのビルド情報を取得するための標準ライブラリです。このパッケージは、Goのツールチェイン（`go build`, `go install`など）や、IDE、リンター、コード分析ツールなどがGoのソースコードを理解するために利用します。

`go/build.Context`構造体は、ビルド環境（`GOROOT`, `GOPATH`, コンパイラなど）を表現し、`Import`メソッドは指定されたパスとソースディレクトリに基づいてGoパッケージの情報を検索・解決します。この`Import`メソッドが、Goのパッケージ解決ロジックの核心を担っています。

### `golang.org/x/tools/go/loader`

`golang.org/x/tools/go/loader`パッケージは、Goのソースコードをロードし、型情報や構文木などの詳細な解析結果を提供するツールです。これは、Goの静的解析ツールやリファクタリングツールなどで広く利用されています。`loader`パッケージは内部的に`go/build`パッケージを利用して、ソースファイルのパス解決やパッケージの依存関係の特定を行います。したがって、`go/build`がベンダーパッケージを正しく解決できない場合、`loader`もベンダーパッケージを含むプロジェクトを正しく処理できませんでした。

## 技術的詳細

このコミットの主要な技術的変更点は、`go/build`パッケージの`Context.Import`メソッドにベンダーディレクトリの検索ロジックを直接組み込んだことです。

1.  **`AllowVendor`フラグの導入**:
    `go/build.ImportMode`に新しいフラグ`AllowVendor`が追加されました。このフラグが`Context.Import`に渡されると、`Import`関数は`GOROOT`や`GOPATH`を検索する前に、現在のソースディレクトリから親ディレクトリへと遡りながら`vendor`ディレクトリを検索するようになります。

2.  **ベンダーディレクトリ検索ロジックの実装**:
    `Context.Import`メソッド内に、`searchVendor`という内部関数が追加されました。この関数は以下のロジックで動作します。
    *   与えられた`root`ディレクトリ（`GOROOT`または`GOPATH`のエントリ）と`srcDir`（インポート元のディレクトリ）から、`srcDir`が`root`のサブディレクトリであるかどうかを判断します。
    *   `srcDir`から`root`に向かって親ディレクトリを辿りながら、各階層に`vendor`ディレクトリが存在するかをチェックします。
    *   `vendor`ディレクトリが見つかった場合、その中にインポートしようとしているパッケージ（`path`）が存在するかを確認します。
    *   パッケージが見つかった場合、そのパッケージの`ImportPath`は、`root`からの相対パスに`vendor`ディレクトリを含めた形式（例: `x/vendor/y`）で設定されます。これは、ベンダーパッケージがそのプロジェクト固有のパスを持つことを明確にするためです。

3.  **エラーメッセージの改善**:
    パッケージが見つからなかった場合のエラーメッセージに、検索されたベンダーディレクトリのパスが含まれるようになりました。これにより、ユーザーはパッケージがどこで検索されたのか、なぜ見つからなかったのかをより明確に理解できます。以前は`cmd/go`が独自にエラーメッセージを加工していましたが、この変更により`go/build`がその責任を負うことになります。

4.  **`cmd/go`の簡素化**:
    `src/cmd/go/pkg.go`内の`loadImport`関数から、ベンダーパス解決とエラーメッセージ生成に関するカスタムロジックが削除されました。代わりに、`go/build.Import`を呼び出す際に`build.AllowVendor`フラグを渡すことで、`go/build`パッケージに処理を委譲するようになりました。これにより、`cmd/go`と`go/build`の間でベンダー解決ロジックが重複することがなくなり、コードの保守性が向上しました。

5.  **`pkga`パスの再計算**:
    `go/build.Context.Import`内で、パッケージの`ImportPath`がベンダー解決によって変更される可能性があるため、`pkga`（アーカイブファイルのパス）を再計算する`setPkga()`ヘルパー関数が導入され、適切なタイミングで呼び出されるようになりました。

## コアとなるコードの変更箇所

### `src/go/build/build.go`

*   `ImportMode`型に`AllowVendor`定数が追加されました。
    ```go
    const (
        // ...
        AllowVendor
    )
    ```
*   `Context.Import`メソッド内に、ベンダーディレクトリを検索する新しいロジックが追加されました。特に、`mode&AllowVendor != 0`の条件分岐内で`searchVendor`関数が定義され、`GOROOT`と`GOPATH`の各エントリに対して呼び出されています。
    ```go
    // ...
    		// Vendor directories get first chance to satisfy import.
    		if mode&AllowVendor != 0 && srcDir != "" {
    			searchVendor := func(root string, isGoroot bool) bool {
    				// ... (ベンダー検索ロジック) ...
    			}
    			if searchVendor(ctxt.GOROOT, true) {
    				goto Found
    			}
    			for _, root := range gopath {
    				if searchVendor(root, false) {
    					goto Found
    				}
    			}
    		}
    // ...
    ```
*   パッケージが見つからなかった場合のエラーメッセージ生成ロジックが更新され、`tried.vendor`に記録されたベンダーディレクトリのパスが含まれるようになりました。
    ```go
    // ...
    		var paths []string
    		format := "\\t%s (vendor tree)"
    		for _, dir := range tried.vendor {
    			paths = append(paths, fmt.Sprintf(format, dir))
    			format = "\\t%s"
    		}
    // ...
    ```

### `src/cmd/go/pkg.go`

*   `loadImport`関数内で、`vendorSearch`変数の宣言と、`go/build`からのエラーメッセージを加工するロジックが削除されました。
*   `buildContext.Import`の呼び出し時に`build.AllowVendor`フラグが追加されるようになりました。
    ```go
    // ...
    	buildMode := build.ImportComment
    	if go15VendorExperiment && mode&useVendor != 0 && path == origPath {
    		// We've already searched the vendor directories and didn't find anything.
    		// Let Import search them again so that, if the package is not found anywhere,
    		// the error includes the vendor directories in the list of places considered.
    		buildMode |= build.AllowVendor
    	}
    	bp, err := buildContext.Import(path, srcDir, buildMode)
    // ...
    ```
*   `vendoredImportPath`関数のシグネチャが変更され、`searched []string`の戻り値が削除されました。

## コアとなるコードの解説

このコミットの核心は、Goのパッケージ解決の権限を`cmd/go`から`go/build`パッケージへと移譲した点にあります。

以前は、`cmd/go`が`go/build.Import`を呼び出す前に、独自にベンダーディレクトリを検索し、その結果を`go/build`に渡すか、あるいは`go/build`がパッケージを見つけられなかった場合に、検索したベンダーディレクトリの情報をエラーメッセージに手動で追加していました。これは、`go/build`パッケージがベンダーエクスペリメントの初期段階で、まだベンダー解決の知識を持っていなかったためです。

このコミットでは、`go/build`パッケージに`AllowVendor`という新しい`ImportMode`フラグと、それに対応するベンダー検索ロジックを導入しました。これにより、`cmd/go`は単に`build.AllowVendor`フラグを`go/build.Import`に渡すだけでよくなりました。`go/build.Import`は、このフラグを受け取ると、`GOROOT`や`GOPATH`を検索する前に、インポート元のディレクトリから親ディレクトリへと遡りながら`vendor`ディレクトリを探索し、パッケージを解決します。

この変更のメリットは以下の通りです。

*   **一貫性**: Goのパッケージ解決ロジックが`go/build`パッケージに一元化され、`cmd/go`だけでなく、`golang.org/x/tools/go/loader`のような他のツールも同じベンダー解決ルールを適用できるようになりました。
*   **保守性**: ベンダー解決のロジックが`go/build`にカプセル化されたことで、将来的な変更や改善が容易になります。
*   **正確なエラー報告**: `go/build`が直接ベンダーディレクトリを検索するため、パッケージが見つからなかった場合のエラーメッセージに、実際に検索されたベンダーディレクトリのパスが正確に含められるようになりました。

`TestImportVendor`と`TestImportVendorFailure`という新しいテストケースが追加され、`go/build`パッケージがベンダーパッケージを正しく解決し、また解決できなかった場合に適切なエラーメッセージを生成することを確認しています。

# [インデックス 21052] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）におけるシンボル解決のロジックを改善し、特にBSSセグメントに属するシンボルと、それ以外のセグメントに属するシンボルが同じ名前で定義されている場合の競合解決を、シンボルが見つかる順序に依存しないように修正したものです。これにより、Goのコードがホストオブジェクトファイル（C/C++など、Go以外の言語でコンパイルされたオブジェクトファイル）で定義されたシンボルを参照する際に発生する可能性のある問題が解決されます。

## コミット

```
[dev.cc] liblink: resolve bss vs other conflict regardless of order found

If the linker finds the same name given a BSS and a non-BSS
symbol, the assumption is that the non-BSS symbol is the
true one, and the BSS symbol is just the best Go can do toward
an "extern" declaration. This has always been the case,
as long as the object files were read in the right order.

The old code worked when the BSS symbol is found before
the non-BSS symbol. This CL adds equivalent logic for when
the non-BSS symbol is found before the BSS symbol.
This comes up when Go must refer to symbols defined in
host object files.

## 変更の背景

Go言語のリンカ（`liblink`）は、複数のオブジェクトファイルからシンボルを読み込み、それらを結合して最終的な実行可能ファイルを生成します。このプロセスにおいて、同じ名前のシンボルが異なるオブジェクトファイルで定義されている場合、リンカはどの定義を採用するかを決定する必要があります。

特に問題となるのは、BSS（Block Started by Symbol）セグメントに属するシンボルと、データセグメントやテキストセグメントなど、他のセグメントに属するシンボルが同じ名前で存在する場合です。Goのリンカの従来の挙動では、「BSSシンボルは、Goが外部宣言（`extern`）に対してできる最善の表現であり、非BSSシンボルが真の定義である」という前提がありました。つまり、同じ名前のシンボルが存在する場合、非BSSシンボルが優先されるべきでした。

しかし、この優先順位付けは、オブジェクトファイルがリンカに読み込まれる順序に依存していました。具体的には、BSSシンボルが非BSSシンボルよりも先に発見された場合にのみ、期待通りの動作をしていました。もし非BSSシンボルが先に発見され、その後に同じ名前のBSSシンボルが発見された場合、リンカは非BSSシンボルを適切に保持せず、誤った解決を行う可能性がありました。

この問題は、GoのコードがC/C++などのホスト言語でコンパイルされたオブジェクトファイル（ホストオブジェクトファイル）内のシンボルを参照する必要がある場合に顕著に現れました。ホストオブジェクトファイルからのシンボルがGoのオブジェクトファイルよりも先に処理されると、リンカが正しいシンボル定義を選択できないという状況が発生していました。このコミットは、この順序依存性を排除し、シンボルが見つかる順序に関わらず、常に非BSSシンボルがBSSシンボルよりも優先されるようにリンカのロジックを修正することを目的としています。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o`ファイルなど）とライブラリを結合し、実行可能なプログラムや共有ライブラリを生成するシステムプログラムです。リンカの主要な役割には、シンボル解決（異なるファイルで定義されたシンボルへの参照を解決する）と、アドレスの再配置（各コードやデータがメモリ上のどこに配置されるかを決定する）があります。

### シンボル (Symbol)
シンボルは、プログラム内の関数やグローバル変数などの名前を表します。リンカはこれらのシンボルを使って、異なるオブジェクトファイル間の参照を解決します。例えば、あるファイルで定義された関数を別のファイルから呼び出す場合、リンカはその関数のシンボル定義を見つけて、呼び出し元から定義へのリンクを確立します。

### セグメント (Segment)
実行可能ファイルは通常、複数の論理的なセグメントに分割されます。主要なセグメントには以下のようなものがあります。
*   **テキストセグメント (Text Segment)**: 実行可能な機械語コードが格納されます。
*   **データセグメント (Data Segment)**: 初期化されたグローバル変数や静的変数が格納されます。
*   **BSSセグメント (Block Started by Symbol Segment)**: 初期化されていないグローバル変数や静的変数が格納されます。BSSセグメントのデータは、プログラムのロード時にゼロで初期化されることが保証されます。ディスク上の実行可能ファイルでは、BSSセグメントは実際のデータを保持せず、そのサイズ情報のみが格納されるため、ファイルサイズを小さく保つことができます。
*   **RODATAセグメント (Read-Only Data Segment)**: 読み取り専用のデータ（文字列リテラルなど）が格納されます。

### シンボルタイプ (Symbol Type)
Goのリンカ内部では、シンボルは様々なタイプで管理されます。このコミットに関連する主なシンボルタイプは以下の通りです。
*   `SXREF`: 外部参照シンボル。このオブジェクトファイルでは定義されておらず、他のオブジェクトファイルで定義されていることを期待するシンボル。
*   `SDATA`: 初期化されたデータセグメントに属するシンボル。
*   `SBSS`: 初期化されていないBSSセグメントに属するシンボル。
*   `SNOPTRBSS`: ポインタを含まないBSSセグメントに属するシンボル。ガベージコレクタがスキャンする必要がないため、特別な扱いを受けます。
*   `SRODATA`: 読み取り専用データセグメントに属するシンボル。

### `dupok` フラグ
`dupok` (duplicate OK) フラグは、シンボルが複数回定義されても許容されるかどうかを示すリンカの内部フラグです。通常、同じ名前のシンボルが複数回定義されるとリンカエラーになりますが、特定の状況（例えば、弱いシンボル定義など）では重複が許容される場合があります。

### `extern` 宣言
C言語などにおける`extern`キーワードは、変数が現在のファイルではなく、他のファイルで定義されていることをコンパイラに伝えます。リンカは、この`extern`宣言に対応する実際の定義を見つける責任があります。Goの文脈では、BSSシンボルがこのような外部参照の「最善の表現」として扱われることがあります。

## 技術的詳細

Goのリンカは、`readsym`関数内でオブジェクトファイルからシンボル情報を読み込み、既存のシンボルテーブルと照合します。このプロセスにおいて、同じ名前のシンボルが既に存在する場合、リンカは新しいシンボルで既存のシンボルを上書きするか、既存のシンボルを保持するか、あるいは重複エラーを報告するかを決定します。

このコミットが修正する問題は、特にBSSシンボルと非BSSシンボル（`SDATA`, `SRODATA`など）の間で発生します。リンカの設計思想として、同じ名前のシンボルが存在する場合、BSSシンボルは「初期化されていないメモリ領域を予約する」という性質上、実際のデータを持つ非BSSシンボルよりも優先度が低いと見なされます。つまり、非BSSシンボルが「真の定義」であり、BSSシンボルは単なる「外部参照のプレースホルダー」として扱われるべきです。

従来のリンカのロジックでは、この優先順位付けがシンボルが発見される順序に依存していました。
1.  **BSSシンボルが先に発見された場合**: リンカはBSSシンボルを登録します。その後、同じ名前の非BSSシンボルが発見されると、リンカは非BSSシンボルがより具体的な定義であると認識し、BSSシンボルを非BSSシンボルで上書きしていました。これは期待通りの動作です。
2.  **非BSSシンボルが先に発見された場合**: リンカは非BSSシンボルを登録します。その後、同じ名前のBSSシンボルが発見された場合、リンカは既に「真の定義」が存在すると判断し、BSSシンボルを無視するか、あるいは誤って既存の非BSSシンボルをBSSシンボルで上書きしてしまう可能性がありました。コミットメッセージによると、このケースで問題が発生し、特にGoのコードがC/C++のライブラリ（ホストオブジェクトファイル）にリンクされる際に、C/C++側で定義されたシンボルがGo側でBSSとして扱われるシンボルよりも先にリンカに渡されると、正しいシンボルが採用されないという問題がありました。

このコミットは、`readsym`関数内のロジックを修正し、シンボルが読み込まれる順序に関わらず、常に非BSSシンボルがBSSシンボルよりも優先されるようにします。これは、既存のシンボルがBSSタイプであり、かつデータやリロケーション情報を持たない（つまり、単なるプレースホルダーである）場合に、新しく読み込まれたシンボルで上書きすることを明示的に許可する新しい条件を追加することで実現されます。

## コアとなるコードの解説

このコミットの核心的な変更は、`readsym` 関数におけるシンボル解決ロジックの調整です。

1.  **シンボルデータとリロケーション情報の先行読み込み**:
    変更前は、シンボルのタイプやサイズを読み込んだ後に、そのシンボルに関連するデータ（`s->p`, `s->np`）やリロケーション情報（`s->r`, `s->nr`）を読み込んでいました。変更後は、`typ = rdsym(ctxt, f, pkg);`, `rddata(f, &data, &ndata);`, `nreloc = rdint(f);` の行が、シンボルをルックアップする `linklookup` の前に移動されました。これにより、新しいシンボルが持つデータやリロケーションの有無を、既存のシンボルとの競合解決ロジックに利用できるようになります。

2.  **新しいシンボルがBSS/データ型で、データやリロケーションを持たない場合の処理**:
    ```c
    if((t == SDATA || t == SBSS || t == SNOPTRBSS) && ndata == 0 && nreloc == 0) {
        if(s->size < size)
            s->size = size;
        if(typ != nil && s->gotype == nil)
            s->gotype = typ;
        return;
    }
    ```
    この新しいブロックは、現在読み込んでいるシンボル（`t`）が `SDATA`, `SBSS`, `SNOPTRBSS` のいずれかであり、かつ実際のデータ（`ndata == 0`）やリロケーション（`nreloc == 0`）を持たない場合に適用されます。これは、そのシンボルが単なる「外部参照」や「プレースホルダー」としてのBSSシンボルであることを示唆します。
    この条件が真の場合、既存のシンボル `s` のサイズを新しいシンボルのサイズと比較して大きい方を採用し、型情報（`gotype`）が未設定であれば設定します。そして `return` することで、既存のシンボルを保持し、新しいBSSシンボルによる上書きを防ぎます。これは、既に非BSSシンボルが登録されており、後からデータを持たないBSSシンボルが来た場合に、既存の非BSSシンボルを優先するロジックです。

3.  **既存のシンボルがBSS/データ型で、データやリロケーションを持たない場合の `overwrite` へのジャンプ**:
    ```c
    if((s->type == SDATA || s->type == SBSS || s->type == SNOPTRBSS) && s->np == 0 && s->nr == 0)
        goto overwrite;
    ```
    これがこのコミットの最も重要な変更点です。この条件は、`linklookup` で見つかった既存のシンボル `s` が `SDATA`, `SBSS`, `SNOPTRBSS` のいずれかであり、かつ既存のシンボルが実際のデータ（`s->np == 0`）やリロケーション（`s->nr == 0`）を持たない場合に真となります。
    この状況は、既存のシンボルが単なる「プレースホルダー」としてのBSSシンボルであることを意味します。このような場合、`goto overwrite;` によって、シンボル情報を上書きする共通のセクションに処理がジャンプします。これにより、新しく読み込まれたシンボル（おそらく非BSSシンボル）が、既存のプレースホルダーBSSシンボルを上書きすることが保証されます。これは、非BSSシンボルが先に発見され、その後にBSSシンボルが来た場合に、非BSSシンボルを優先するロジックを補完します。

4.  **シンボルタイプ解決の微調整**:
    ```c
    if(t == SBSS && (s->type == SRODATA || s->type == SNOPTRBSS))
        t = s->type;
    ```
    この行は、新しく読み込んだシンボル `t` が `SBSS` であり、かつ既存のシンボル `s` のタイプが `SRODATA`（読み取り専用データ）または `SNOPTRBSS`（ポインタを含まないBSS）である場合に、新しいシンボルのタイプを既存のシンボルのタイプに設定し直します。これは、より具体的な（または安全な）既存のシンボルタイプを保持するための微調整です。

これらの変更により、リンカはシンボルを読み込む順序に依存せず、常に「非BSSシンボルがBSSシンボルよりも優先される」というルールを適用できるようになりました。特に、Goのコードが外部のC/C++ライブラリとリンクする際に、シンボル解決の堅牢性が向上します。

## 変更の背景

Go言語のリンカ（`liblink`）は、複数のオブジェクトファイルからシンボルを読み込み、それらを結合して最終的な実行可能ファイルを生成します。このプロセスにおいて、同じ名前のシンボルが異なるオブジェクトファイルで定義されている場合、リンカはどの定義を採用するかを決定する必要があります。

特に問題となるのは、BSS（Block Started by Symbol）セグメントに属するシンボルと、データセグメントやテキストセグメントなど、他のセグメントに属するシンボルが同じ名前で存在する場合です。Goのリンカの従来の挙動では、「BSSシンボルは、Goが外部宣言（`extern`）に対してできる最善の表現であり、非BSSシンボルが真の定義である」という前提がありました。つまり、同じ名前のシンボルが存在する場合、非BSSシンボルが優先されるべきでした。

しかし、この優先順位付けは、オブジェクトファイルがリンカに読み込まれる順序に依存していました。具体的には、BSSシンボルが非BSSシンボルよりも先に発見された場合にのみ、期待通りの動作をしていました。もし非BSSシンボルが先に発見され、その後に同じ名前のBSSシンボルが発見された場合、リンカは非BSSシンボルを適切に保持せず、誤った解決を行う可能性がありました。

この問題は、GoのコードがC/C++などのホスト言語でコンパイルされたオブジェクトファイル（ホストオブジェクトファイル）内のシンボルを参照する必要がある場合に顕著に現れました。ホストオブジェクトファイルからのシンボルがGoのオブジェクトファイルよりも先に処理されると、リンカが正しいシンボル定義を選択できないという状況が発生していました。このコミットは、この順序依存性を排除し、シンボルが見つかる順序に関わらず、常に非BSSシンボルがBSSシンボルよりも優先されるようにリンカのロジックを修正することを目的としています。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o`ファイルなど）とライブラリを結合し、実行可能なプログラムや共有ライブラリを生成するシステムプログラムです。リンカの主要な役割には、シンボル解決（異なるファイルで定義されたシンボルへの参照を解決する）と、アドレスの再配置（各コードやデータがメモリ上のどこに配置されるかを決定する）があります。

### シンボル (Symbol)
シンボルは、プログラム内の関数やグローバル変数などの名前を表します。リンカはこれらのシンボルを使って、異なるオブジェクトファイル間の参照を解決します。例えば、あるファイルで定義された関数を別のファイルから呼び出す場合、リンカはその関数のシンボル定義を見つけて、呼び出し元から定義へのリンクを確立します。

### セグメント (Segment)
実行可能ファイルは通常、複数の論理的なセグメントに分割されます。主要なセグメントには以下のようなものがあります。
*   **テキストセグメント (Text Segment)**: 実行可能な機械語コードが格納されます。
*   **データセグメント (Data Segment)**: 初期化されたグローバル変数や静的変数が格納されます。
*   **BSSセグメント (Block Started by Symbol Segment)**: 初期化されていないグローバル変数や静的変数が格納されます。BSSセグメントのデータは、プログラムのロード時にゼロで初期化されることが保証されます。ディスク上の実行可能ファイルでは、BSSセグメントは実際のデータを保持せず、そのサイズ情報のみが格納されるため、ファイルサイズを小さく保つことができます。
*   **RODATAセグメント (Read-Only Data Segment)**: 読み取り専用のデータ（文字列リテラルなど）が格納されます。

### シンボルタイプ (Symbol Type)
Goのリンカ内部では、シンボルは様々なタイプで管理されます。このコミットに関連する主なシンボルタイプは以下の通りです。
*   `SXREF`: 外部参照シンボル。このオブジェクトファイルでは定義されておらず、他のオブジェクトファイルで定義されていることを期待するシンボル。
*   `SDATA`: 初期化されたデータセグメントに属するシンボル。
*   `SBSS`: 初期化されていないBSSセグメントに属するシンボル。
*   `SNOPTRBSS`: ポインタを含まないBSSセグメントに属するシンボル。ガベージコレクタがスキャンする必要がないため、特別な扱いを受けます。
*   `SRODATA`: 読み取り専用データセグメントに属するシンボル。

### `dupok` フラグ
`dupok` (duplicate OK) フラグは、シンボルが複数回定義されても許容されるかどうかを示すリンカの内部フラグです。通常、同じ名前のシンボルが複数回定義されるとリンカエラーになりますが、特定の状況（例えば、弱いシンボル定義など）では重複が許容される場合があります。

### `extern` 宣言
C言語などにおける`extern`キーワードは、変数が現在のファイルではなく、他のファイルで定義されていることをコンパイラに伝えます。リンカは、この`extern`宣言に対応する実際の定義を見つける責任があります。Goの文脈では、BSSシンボルがこのような外部参照の「最善の表現」として扱われることがあります。

## 技術的詳細

Goのリンカは、`readsym`関数内でオブジェクトファイルからシンボル情報を読み込み、既存のシンボルテーブルと照合します。このプロセスにおいて、同じ名前のシンボルが既に存在する場合、リンカは新しいシンボルで既存のシンボルを上書きするか、既存のシンボルを保持するか、あるいは重複エラーを報告するかを決定します。

このコミットが修正する問題は、特にBSSシンボルと非BSSシンボル（`SDATA`, `SRODATA`など）の間で発生します。リンカの設計思想として、同じ名前のシンボルが存在する場合、BSSシンボルは「初期化されていないメモリ領域を予約する」という性質上、実際のデータを持つ非BSSシンボルよりも優先度が低いと見なされます。つまり、非BSSシンボルが「真の定義」であり、BSSシンボルは単なる「外部参照のプレースホルダー」として扱われるべきです。

従来のリンカのロジックでは、この優先順位付けがシンボルが発見される順序に依存していました。
1.  **BSSシンボルが先に発見された場合**: リンカはBSSシンボルを登録します。その後、同じ名前の非BSSシンボルが発見されると、リンカは非BSSシンボルがより具体的な定義であると認識し、BSSシンボルを非BSSシンボルで上書きしていました。これは期待通りの動作です。
2.  **非BSSシンボルが先に発見された場合**: リンカは非BSSシンボルを登録します。その後、同じ名前のBSSシンボルが発見された場合、リンカは既に「真の定義」が存在すると判断し、BSSシンボルを無視するか、あるいは誤って既存の非BSSシンボルをBSSシンボルで上書きしてしまう可能性がありました。コミットメッセージによると、このケースで問題が発生し、特にGoのコードがC/C++のライブラリ（ホストオブジェクトファイル）にリンクされる際に、C/C++側で定義されたシンボルがGo側でBSSとして扱われるシンボルよりも先にリンカに渡されると、正しいシンボルが採用されないという問題がありました。

このコミットは、`readsym`関数内のロジックを修正し、シンボルが読み込まれる順序に関わらず、常に非BSSシンボルがBSSシンボルよりも優先されるようにします。これは、既存のシンボルがBSSタイプであり、かつデータやリロケーション情報を持たない（つまり、単なるプレースホルダーである）場合に、新しく読み込まれたシンボルで上書きすることを明示的に許可する新しい条件を追加することで実現されます。

## コアとなるコードの解説

このコミットの核心的な変更は、`readsym` 関数におけるシンボル解決ロジックの調整です。

1.  **シンボルデータとリロケーション情報の先行読み込み**:
    変更前は、シンボルのタイプやサイズを読み込んだ後に、そのシンボルに関連するデータ（`s->p`, `s->np`）やリロケーション情報（`s->r`, `s->nr`）を読み込んでいました。変更後は、`typ = rdsym(ctxt, f, pkg);`, `rddata(f, &data, &ndata);`, `nreloc = rdint(f);` の行が、シンボルをルックアップする `linklookup` の前に移動されました。これにより、新しいシンボルが持つデータやリロケーションの有無を、既存のシンボルとの競合解決ロジックに利用できるようになります。

2.  **新しいシンボルがBSS/データ型で、データやリロケーションを持たない場合の処理**:
    ```c
    if((t == SDATA || t == SBSS || t == SNOPTRBSS) && ndata == 0 && nreloc == 0) {
        if(s->size < size)
            s->size = size;
        if(typ != nil && s->gotype == nil)
            s->gotype = typ;
        return;
    }
    ```
    この新しいブロックは、現在読み込んでいるシンボル（`t`）が `SDATA`, `SBSS`, `SNOPTRBSS` のいずれかであり、かつ実際のデータ（`ndata == 0`）やリロケーション（`nreloc == 0`）を持たない場合に適用されます。これは、そのシンボルが単なる「外部参照」や「プレースホルダー」としてのBSSシンボルであることを示唆します。
    この条件が真の場合、既存のシンボル `s` のサイズを新しいシンボルのサイズと比較して大きい方を採用し、型情報（`gotype`）が未設定であれば設定します。そして `return` することで、既存のシンボルを保持し、新しいBSSシンボルによる上書きを防ぎます。これは、既に非BSSシンボルが登録されており、後からデータを持たないBSSシンボルが来た場合に、既存の非BSSシンボルを優先するロジックです。

3.  **既存のシンボルがBSS/データ型で、データやリロケーションを持たない場合の `overwrite` へのジャンプ**:
    ```c
    if((s->type == SDATA || s->type == SBSS || s->type == SNOPTRBSS) && s->np == 0 && s->nr == 0)
        goto overwrite;
    ```
    これがこのコミットの最も重要な変更点です。この条件は、`linklookup` で見つかった既存のシンボル `s` が `SDATA`, `SBSS`, `SNOPTRBSS` のいずれかであり、かつ既存のシンボルが実際のデータ（`s->np == 0`）やリロケーション（`s->nr == 0`）を持たない場合に真となります。
    この状況は、既存のシンボルが単なる「プレースホルダー」としてのBSSシンボルであることを意味します。このような場合、`goto overwrite;` によって、シンボル情報を上書きする共通のセクションに処理がジャンプします。これにより、新しく読み込まれたシンボル（おそらく非BSSシンボル）が、既存のプレースホルダーBSSシンボルを上書きすることが保証されます。これは、非BSSシンボルが先に発見され、その後にBSSシンボルが来た場合に、非BSSシンボルを優先するロジックを補完します。

4.  **シンボルタイプ解決の微調整**:
    ```c
    if(t == SBSS && (s->type == SRODATA || s->type == SNOPTRBSS))
        t = s->type;
    ```
    この行は、新しく読み込んだシンボル `t` が `SBSS` であり、かつ既存のシンボル `s` のタイプが `SRODATA`（読み取り専用データ）または `SNOPTRBSS`（ポインタを含まないBSS）である場合に、新しいシンボルのタイプを既存のシンボルのタイプに設定し直します。これは、より具体的な（または安全な）既存のシンボルタイプを保持するための微調整です。

これらの変更により、リンカはシンボルを読み込む順序に依存せず、常に「非BSSシンボルがBSSシンボルよりも優先される」というルールを適用できるようになりました。特に、Goのコードが外部のC/C++ライブラリとリンクする際に、シンボル解決の堅牢性が向上します。

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal/gc` において、字句解析に関連するユーティリティ関数を `util.go` から `lex.go` へ移動させるコード整理を目的としています。具体的には、文字種判定関数 (`isSpace`, `isAlpha`, `isDigit`, `isAlnum`) と、Plan 9形式の文字列引用符付け関数 (`plan9quote`) が移動されました。これにより、字句解析器のコードとその補助関数が一箇所に集約され、コードの可読性と保守性が向上します。

## 変更の背景

Goコンパイラの開発では、コードベースの整理とモジュール性の向上が常に重視されています。このコミットの背景には、以下の理由が考えられます。

1.  **関心の分離 (Separation of Concerns)**: `lex.go` はGoコンパイラの字句解析器（lexer）を実装するファイルであり、ソースコードをトークンに分解する役割を担っています。`isSpace`、`isAlpha`、`isDigit`、`isAlnum` といった文字種判定関数は、字句解析の過程でトークンの境界を識別したり、識別子や数値リテラルを構成する文字を分類したりするために不可欠です。これらの関数が `util.go` のような汎用ユーティリティファイルに置かれていると、字句解析器のロジックを理解する際に、関連する関数が別のファイルに散らばっているため、追跡が困難になる可能性があります。`lex.go` に移動することで、字句解析に関連するすべてのコードが一箇所にまとまり、関心の分離がより明確になります。
2.  **コードの局所性 (Locality of Code)**: 関連するコードが物理的に近い場所にあると、開発者は特定の機能について作業する際に、必要な情報を探しやすくなります。字句解析器が頻繁に利用する補助関数を `lex.go` に配置することで、字句解析器のコードを読む際に `util.go` を参照する必要がなくなり、コードの局所性が高まります。
3.  **依存関係の明確化**: `util.go` は多くのパッケージから利用される可能性のある汎用関数を含む傾向があります。字句解析器に特化した関数を `lex.go` に移動することで、`util.go` の依存関係が整理され、その役割がより明確になります。また、`lex.go` がこれらの関数を内部的に持つことで、外部からの不必要な依存を防ぐことができます。
4.  **歴史的経緯とリファクタリング**: 多くの大規模プロジェクトでは、初期段階で汎用的なユーティリティファイルに多くの機能が詰め込まれることがあります。プロジェクトが成熟するにつれて、これらの機能が特定のモジュールに強く関連していることが明らかになり、リファクタリングの一環として適切な場所へ移動されることがあります。このコミットも、そのような継続的なコードベースの改善の一環と見なせます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは、Goのソースコードを機械語に変換するプログラムです。`cmd/compile` はGoツールチェインの一部であり、Go言語で書かれたプログラムをビルドする際に使用されます。コンパイラは通常、以下の主要なフェーズで構成されます。

1.  **字句解析 (Lexical Analysis)**: ソースコードの文字列を、意味を持つ最小単位である「トークン」のストリームに変換します。例えば、`var x = 10` というコードは、`var` (キーワード)、`x` (識別子)、`=` (演算子)、`10` (数値リテラル) といったトークンに分解されます。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、言語の文法規則に従って抽象構文木 (AST: Abstract Syntax Tree) を構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、定数畳み込みなどの意味的な検証を行います。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、ターゲットマシンに依存しない中間表現 (IR: Intermediate Representation) を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **ターゲットコード生成 (Target Code Generation)**: 最適化された中間コードを、特定のCPUアーキテクチャ（例: x86-64, ARM）向けの機械語に変換します。

### `gc` パッケージ

`cmd/compile/internal/gc` は、Goコンパイラの主要なロジックを含む内部パッケージです。`gc` は "Go Compiler" の略であり、Goコンパイラのフロントエンドとバックエンドの大部分を実装しています。このパッケージ内には、字句解析器、構文解析器、型チェッカー、コードジェネレータなど、コンパイラの各フェーズに対応する多数のファイルが含まれています。

### `lex.go`

`lex.go` は `gc` パッケージ内で字句解析器（lexer）を実装するファイルです。このファイルには、ソースコードを読み込み、Go言語のトークン（キーワード、識別子、演算子、リテラルなど）に変換するためのロジックが含まれています。字句解析器は、文字のストリームを処理し、特定のパターンに基づいてトークンを生成します。

### `util.go`

`util.go` は `gc` パッケージ内で汎用的なユーティリティ関数やヘルパー関数をまとめたファイルです。特定のコンパイラフェーズに直接関連しないが、複数の場所で利用される可能性のある関数がここに置かれる傾向があります。しかし、時間の経過とともに、特定のフェーズに強く関連する関数が誤ってここに置かれることもあります。

### 文字種判定関数 (`isSpace`, `isAlpha`, `isDigit`, `isAlnum`)

これらの関数は、与えられた文字（`int` 型で表現されるUnicodeコードポイント）が特定のカテゴリに属するかどうかを判定する基本的なユーティリティです。

*   `isSpace(c int) bool`: 文字 `c` が空白文字（スペース、タブ、改行、キャリッジリターン）であるかを判定します。
*   `isAlpha(c int) bool`: 文字 `c` が英字（大文字または小文字）であるかを判定します。
*   `isDigit(c int) bool`: 文字 `c` が数字（0-9）であるかを判定します。
*   `isAlnum(c int) bool`: 文字 `c` が英数字（英字または数字）であるかを判定します。

これらの関数は、字句解析において、識別子の開始文字や後続文字、数値リテラルの構成文字、文字列リテラルの区切りなどを判断するために頻繁に利用されます。

### `plan9quote(string) string`

`plan9quote` 関数は、文字列をPlan 9オペレーティングシステムのシェルが解釈できる形式で引用符付け（クォート）するユーティリティです。Plan 9はベル研究所で開発された分散オペレーティングシステムであり、Go言語の開発者の一部がPlan 9の設計に深く関わっていたため、GoのツールチェインにはPlan 9の影響が見られます。

Plan 9シェルの引用符付けルールは、Unixシェルのそれとは異なります。例えば、スペースや特殊文字を含む文字列を単一の引数として渡すために、引用符で囲む必要があります。`plan9quote` は、与えられた文字列が既に引用符付けが必要な文字を含んでいる場合に、適切にエスケープ処理を施して引用符で囲まれた文字列を返します。

### `go build -toolexec 'toolstash -cmp' -a std`

これはGoのビルドコマンドと、その動作を検証するためのオプションです。

*   `go build`: Goのソースコードをコンパイルして実行可能ファイルを生成するコマンドです。
*   `-toolexec 'toolstash -cmp'`: これは、`go build` が内部的に呼び出すツール（コンパイラ、アセンブラ、リンカなど）の実行を `toolstash -cmp` コマンドでラップすることを指示します。`toolstash -cmp` は、ビルド結果が以前のビルドと同一であることを検証するためのツールです。これにより、コード変更がコンパイラの出力に意図しない影響を与えていないことを確認できます。
*   `-a`: 依存関係にあるすべてのパッケージを強制的に再ビルドします。
*   `std`: 標準ライブラリ全体を対象とします。

このコマンドは、変更がGoの標準ライブラリ全体のビルドに影響を与えず、コンパイラの出力が以前と変わらないことを保証するために実行されました。これは、コンパイラの内部変更が外部の動作に影響を与えないことを確認する重要なテストです。

## 技術的詳細

このコミットの技術的な詳細は、主にコードの再編成と、それがコンパイラの保守性に与える影響に集約されます。

### コードの再編成の意義

`isSpace`, `isAlpha`, `isDigit`, `isAlnum` といった文字種判定関数は、字句解析器がソースコードの文字ストリームを処理する上で非常に基本的な操作です。これらの関数は、トークンの開始、終了、または特定のトークン（識別子、数値、文字列など）の内部構造を決定するために、字句解析器のコアロジックから頻繁に呼び出されます。

`util.go` は汎用的なユーティリティの「ごみ箱」になりがちですが、`lex.go` は字句解析という特定のタスクに特化しています。これらの関数を `lex.go` に移動することで、以下の利点が得られます。

*   **凝集度 (Cohesion) の向上**: `lex.go` の内部で字句解析に関連するすべてのロジックと補助関数が完結するため、モジュールの凝集度が高まります。これは、ソフトウェア設計の重要な原則の一つであり、モジュールが単一の明確な責任を持つことを意味します。
*   **結合度 (Coupling) の低下**: `util.go` からこれらの関数が削除されることで、`lex.go` が `util.go` に依存する度合いが減少し、`util.go` の変更が `lex.go` に与える影響が少なくなります。また、`util.go` 自体も、より汎用的なユーティリティのみを含むようになり、その役割が明確になります。
*   **ナビゲーションの容易さ**: 開発者が字句解析器の動作を理解しようとする際、`lex.go` を開けば、その動作に必要なすべての補助関数がすぐに見つかります。これにより、コードベースを横断して関連関数を探す手間が省け、開発効率が向上します。

`plan9quote` 関数も同様に、Goツールチェインの特定の側面（Plan 9の影響）に関連するユーティリティであり、字句解析器が特定のコンテキストで文字列を処理する際に必要となる可能性があります。これも `lex.go` に移動することで、関連する機能がより論理的にグループ化されます。

### 変更の検証

コミットメッセージにある `Passes go build -toolexec 'toolstash -cmp' -a std.` という記述は、この変更がコンパイラの出力に影響を与えないことを保証するための重要な検証ステップです。

*   `toolstash -cmp`: このツールは、コンパイラの出力（生成されるオブジェクトファイルや実行可能ファイル）が、変更前と変更後でバイナリレベルで同一であることを比較します。コンパイラの内部的なコード整理は、最終的な生成コードの動作やパフォーマンスに影響を与えないことが理想です。この検証により、リファクタリングが安全に行われたことが確認されます。
*   `-a std`: 標準ライブラリ全体を再ビルドすることで、コンパイラの変更がGo言語の最も広範なコードベースに対して互換性があり、予期せぬ副作用がないことを確認します。

この検証ステップは、コンパイラのようなクリティカルなソフトウェアの変更において、安定性と信頼性を維持するために不可欠です。

## コアとなるコードの解説

移動された各関数について、その役割と実装を解説します。

### `isSpace(c int) bool`

この関数は、入力された文字 `c` が空白文字（スペース ` `、タブ `\t`、改行 `\n`、キャリッジリターン `\r`）のいずれかであるかを判定します。字句解析器は、これらの空白文字をスキップしたり、トークンの区切りとして認識したりするためにこの関数を使用します。

```go
func isSpace(c int) bool {
	return c == ' ' || c == '\t' || c == '\n' || c == '\r'
}
```

### `isAlpha(c int) bool`

この関数は、入力された文字 `c` が英字（大文字 'A' から 'Z'、または小文字 'a' から 'z'）であるかを判定します。Go言語の識別子（変数名、関数名など）は英字で始まる必要があるため、字句解析器は識別子を認識する際にこの関数を利用します。

```go
func isAlpha(c int) bool {
	return 'A' <= c && c <= 'Z' || 'a' <= c && c <= 'z'
}
```

### `isDigit(c int) bool`

この関数は、入力された文字 `c` が数字（'0' から '9'）であるかを判定します。数値リテラルや識別子の後続文字（数字を含むことができる）を認識する際に使用されます。

```go
func isDigit(c int) bool {
	return '0' <= c && c <= '9'
}
```

### `isAlnum(c int) bool`

この関数は、入力された文字 `c` が英数字（`isAlpha(c)` が真であるか、または `isDigit(c)` が真であるか）であるかを判定します。Go言語の識別子は英字またはアンダースコアで始まり、その後は英数字またはアンダースコアが続くため、識別子の構成文字を判定する際にこの関数が役立ちます。

```go
func isAlnum(c int) bool {
	return isAlpha(c) || isDigit(c)
}
```

### `plan9quote(s string) string`

この関数は、与えられた文字列 `s` をPlan 9シェルのルールに従って引用符付けします。

*   空文字列 `""` の場合は、`"''"` を返します。
*   文字列 `s` 内にスペース文字（`c <= ' '`）または単一引用符 `'` が含まれている場合、文字列全体を単一引用符で囲み、内部の単一引用符は `''` と二重にエスケープされます。
*   それ以外の場合（引用符付けが不要な場合）は、元の文字列 `s` をそのまま返します。

この関数は、Goツールチェインが内部的にPlan 9の慣習に従ってコマンドライン引数などを処理する必要がある場合に利用されます。

```go
func plan9quote(s string) string {
	if s == "" {
		return "''"
	}
	for _, c := range s {
		if c <= ' ' || c == '\'' {
			return "'" + strings.Replace(s, "'", "''", -1) + "'"
		}
	}
	return s
}
```

`util.go` から `strings` パッケージのインポートが削除されている点も注目に値します。これは、`plan9quote` 関数が `lex.go` に移動したことで、`util.go` 内で `strings.Replace` が不要になったためです。これにより、`util.go` の依存関係がさらに簡素化されました。

## 変更の背景

Goコンパイラの開発では、コードベースの整理とモジュール性の向上が常に重視されています。このコミットの背景には、以下の理由が考えられます。

1.  **関心の分離 (Separation of Concerns)**: `lex.go` はGoコンパイラの字句解析器（lexer）を実装するファイルであり、ソースコードをトークンに分解する役割を担っています。`isSpace`、`isAlpha`、`isDigit`、`isAlnum` といった文字種判定関数は、字句解析の過程でトークンの境界を識別したり、識別子や数値リテラルを構成する文字を分類したりするために不可欠です。これらの関数が `util.go` のような汎用ユーティリティファイルに置かれていると、字句解析器のロジックを理解する際に、関連する関数が別のファイルに散らばっているため、追跡が困難になる可能性があります。`lex.go` に移動することで、字句解析に関連するすべてのコードが一箇所にまとまり、関心の分離がより明確になります。
2.  **コードの局所性 (Locality of Code)**: 関連するコードが物理的に近い場所にあると、開発者は特定の機能について作業する際に、必要な情報を探しやすくなります。字句解析器が頻繁に利用する補助関数を `lex.go` に配置することで、字句解析器のコードを読む際に `util.go` を参照する必要がなくなり、コードの局所性が高まります。
3.  **依存関係の明確化**: `util.go` は多くのパッケージから利用される可能性のある汎用関数を含む傾向があります。字句解析器に特化した関数を `lex.go` に移動することで、`util.go` の依存関係が整理され、その役割がより明確になります。また、`lex.go` がこれらの関数を内部的に持つことで、外部からの不必要な依存を防ぐことができます。
4.  **歴史的経緯とリファクタリング**: 多くの大規模プロジェクトでは、初期段階で汎用的なユーティリティファイルに多くの機能が詰め込まれることがあります。プロジェクトが成熟するにつれて、これらの機能が特定のモジュールに強く関連していることが明らかになり、リファクタリングの一環として適切な場所へ移動されることがあります。このコミットも、そのような継続的なコードベースの改善の一環と見なせます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは、Goのソースコードを機械語に変換するプログラムです。`cmd/compile` はGoツールチェインの一部であり、Go言語で書かれたプログラムをビルドする際に使用されます。コンパイラは通常、以下の主要なフェーズで構成されます。

1.  **字句解析 (Lexical Analysis)**: ソースコードの文字列を、意味を持つ最小単位である「トークン」のストリームに変換します。例えば、`var x = 10` というコードは、`var` (キーワード)、`x` (識別子)、`=` (演算子)、`10` (数値リテラル) といったトークンに分解されます。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、言語の文法規則に従って抽象構文木 (AST: Abstract Syntax Tree) を構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、定数畳み込みなどの意味的な検証を行います。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、ターゲットマシンに依存しない中間表現 (IR: Intermediate Representation) を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **ターゲットコード生成 (Target Code Generation)**: 最適化された中間コードを、特定のCPUアーキテクチャ（例: x86-64, ARM）向けの機械語に変換します。

### `gc` パッケージ

`cmd/compile/internal/gc` は、Goコンパイラの主要なロジックを含む内部パッケージです。`gc` は "Go Compiler" の略であり、Goコンパイラのフロントエンドとバックエンドの大部分を実装しています。このパッケージ内には、字句解析器、構文解析器、型チェッカー、コードジェネレータなど、コンパイラの各フェーズに対応する多数のファイルが含まれています。

### `lex.go`

`lex.go` は `gc` パッケージ内で字句解析器（lexer）を実装するファイルです。このファイルには、ソースコードを読み込み、Go言語のトークン（キーワード、識別子、演算子、リテラルなど）に変換するためのロジックが含まれています。字句解析器は、文字のストリームを処理し、特定のパターンに基づいてトークンを生成します。

### `util.go`

`util.go` は `gc` パッケージ内で汎用的なユーティリティ関数やヘルパー関数をまとめたファイルです。特定のコンパイラフェーズに直接関連しないが、複数の場所で利用される可能性のある関数がここに置かれる傾向があります。しかし、時間の経過とともに、特定のフェーズに強く関連する関数が誤ってここに置かれることもあります。

### 文字種判定関数 (`isSpace`, `isAlpha`, `isDigit`, `isAlnum`)

これらの関数は、与えられた文字（`int` 型で表現されるUnicodeコードポイント）が特定のカテゴリに属するかどうかを判定する基本的なユーティリティです。

*   `isSpace(c int) bool`: 文字 `c` が空白文字（スペース、タブ、改行、キャリッジリターン）であるかを判定します。
*   `isAlpha(c int) bool`: 文字 `c` が英字（大文字または小文字）であるかを判定します。
*   `isDigit(c int) bool`: 文字 `c` が数字（0-9）であるかを判定します。
*   `isAlnum(c int) bool`: 文字 `c` が英数字（英字または数字）であるかを判定します。

これらの関数は、字句解析において、識別子の開始文字や後続文字、数値リテラルの構成文字、文字列リテラルの区切りなどを判断するために頻繁に利用されます。

### `plan9quote(string) string`

`plan9quote` 関数は、文字列をPlan 9オペレーティングシステムのシェルが解釈できる形式で引用符付け（クォート）するユーティリティです。Plan 9はベル研究所で開発された分散オペレーティングシステムであり、Go言語の開発者の一部がPlan 9の設計に深く関わっていたため、GoのツールチェインにはPlan 9の影響が見られます。

Plan 9シェルの引用符付けルールは、Unixシェルのそれとは異なります。例えば、スペースや特殊文字を含む文字列を単一の引数として渡すために、引用符で囲む必要があります。`plan9quote` は、与えられた文字列が既に引用符付けが必要な文字を含んでいる場合に、適切にエスケープ処理を施して引用符で囲まれた文字列を返します。

### `go build -toolexec 'toolstash -cmp' -a std`

これはGoのビルドコマンドと、その動作を検証するためのオプションです。

*   `go build`: Goのソースコードをコンパイルして実行可能ファイルを生成するコマンドです。
*   `-toolexec 'toolstash -cmp'`: これは、`go build` が内部的に呼び出すツール（コンパイラ、アセンブラ、リンカなど）の実行を `toolstash -cmp` コマンドでラップすることを指示します。`toolstash -cmp` は、ビルド結果が以前のビルドと同一であることを検証するためのツールです。これにより、コード変更がコンパイラの出力に意図しない影響を与えていないことを確認できます。
*   `-a`: 依存関係にあるすべてのパッケージを強制的に再ビルドします。
*   `std`: 標準ライブラリ全体を対象とします。

このコマンドは、変更がGoの標準ライブラリ全体のビルドに影響を与えず、コンパイラの出力が以前と変わらないことを保証するために実行されました。これは、コンパイラの内部変更が外部の動作に影響を与えないことを確認する重要なテストです。

## 技術的詳細

このコミットの技術的な詳細は、主にコードの再編成と、それがコンパイラの保守性に与える影響に集約されます。

### コードの再編成の意義

`isSpace`, `isAlpha`, `isDigit`, `isAlnum` といった文字種判定関数は、字句解析器がソースコードの文字ストリームを処理する上で非常に基本的な操作です。これらの関数は、トークンの開始、終了、または特定のトークン（識別子、数値、文字列など）の内部構造を決定するために、字句解析器のコアロジックから頻繁に呼び出されます。

`util.go` は汎用的なユーティリティの「ごみ箱」になりがちですが、`lex.go` は字句解析という特定のタスクに特化しています。これらの関数を `lex.go` に移動することで、以下の利点が得られます。

*   **凝集度 (Cohesion) の向上**: `lex.go` の内部で字句解析に関連するすべてのロジックと補助関数が完結するため、モジュールの凝集度が高まります。これは、ソフトウェア設計の重要な原則の一つであり、モジュールが単一の明確な責任を持つことを意味します。
*   **結合度 (Coupling) の低下**: `util.go` からこれらの関数が削除されることで、`lex.go` が `util.go` に依存する度合いが減少し、`util.go` の変更が `lex.go` に与える影響が少なくなります。また、`util.go` 自体も、より汎用的なユーティリティのみを含むようになり、その役割が明確になります。
*   **ナビゲーションの容易さ**: 開発者が字句解析器の動作を理解しようとする際、`lex.go` を開けば、その動作に必要なすべての補助関数がすぐに見つかります。これにより、コードベースを横断して関連関数を探す手間が省け、開発効率が向上します。

`plan9quote` 関数も同様に、Goツールチェインの特定の側面（Plan 9の影響）に関連するユーティリティであり、字句解析器が特定のコンテキストで文字列を処理する際に必要となる可能性があります。これも `lex.go` に移動することで、関連する機能がより論理的にグループ化されます。

コミットメッセージにある `Passes go build -toolexec 'toolstash -cmp' -a std.` という記述は、この変更がコンパイラの出力に影響を与えないことを保証するための重要な検証ステップです。

*   `toolstash -cmp`: このツールは、コンパイラの出力（生成されるオブジェクトファイルや実行可能ファイル）が、変更前と変更後でバイナリレベルで同一であることを比較します。コンパイラの内部的なコード整理は、最終的な生成コードの動作やパフォーマンスに影響を与えないことが理想です。この検証により、リファクタリングが安全に行われたことが確認されます。

## コアとなるコードの解説

移動された各関数について、その役割と実装を解説します。

### `isSpace(c int) bool`

この関数は、入力された文字 `c` が空白文字（スペース ` `、タブ `\t`、改行 `\n`、キャリッジリターン `\r`）のいずれかであるかを判定します。字句解析器は、これらの空白文字をスキップしたり、トークンの区切りとして認識したりするためにこの関数を使用します。

```go
func isSpace(c int) bool {
	return c == ' ' || c == '\t' || c == '\n' || c == '\r'
}
```

### `isAlpha(c int) bool`

この関数は、入力された文字 `c` が英字（大文字 'A' から 'Z'、または小文字 'a' から 'z'）であるかを判定します。Go言語の識別子（変数名、関数名など）は英字で始まる必要があるため、字句解析器は識別子を認識する際にこの関数を利用します。

```go
func isAlpha(c int) bool {
	return 'A' <= c && c <= 'Z' || 'a' <= c && c <= 'z'
}
```

### `isDigit(c int) bool`

この関数は、入力された文字 `c` が数字（'0' から '9'）であるかを判定します。数値リテラルや識別子の後続文字（数字を含むことができる）を認識する際に使用されます。

```go
func isDigit(c int) bool {
	return '0' <= c && c <= '9'
}
```

### `isAlnum(c int) bool`

この関数は、入力された文字 `c` が英数字（`isAlpha(c)` が真であるか、または `isDigit(c)` が真であるか）であるかを判定します。Go言語の識別子は英字またはアンダースコアで始まり、その後は英数字またはアンダースコアが続くため、識別子の構成文字を判定する際にこの関数が役立ちます。

```go
func isAlnum(c int) bool {
	return isAlpha(c) || isDigit(c)
}
```

### `plan9quote(s string) string`

この関数は、与えられた文字列 `s` をPlan 9シェルのルールに従って引用符付けします。

*   空文字列 `""` の場合は、`"''"` を返します。
*   文字列 `s` 内にスペース文字（`c <= ' '`）または単一引用符 `'` が含まれている場合、文字列全体を単一引用符で囲み、内部の単一引用符は `''` と二重にエスケープされます。
*   それ以外の場合（引用符付けが不要な場合）は、元の文字列 `s` をそのまま返します。

この関数は、Goツールチェインが内部的にPlan 9の慣習に従ってコマンドライン引数などを処理する必要がある場合に利用されます。

```go
func plan9quote(s string) string {
	if s == "" {
		return "''"
	}
	for _, c := range s {
		if c <= ' ' || c == '\'' {
			return "'" + strings.Replace(s, "'", "''", -1) + "'"
		}
	}
	return s
}
```

`util.go` から `strings` パッケージのインポートが削除されている点も注目に値します。これは、`plan9quote` 関数が `lex.go` に移動したことで、`util.go` 内で `strings.Replace` が不要になったためです。これにより、`util.go` の依存関係がさらに簡素化されました。

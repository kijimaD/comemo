# [インデックス 26892] ファイルの概要

## コミット
`cmd/link`におけるDWARF PCテーブルの書き込み方法の改善。以前の「オフセットを記録し、仮ヘッダを書き込み、本体を書き込み、仮ヘッダに戻って本物のヘッダを書き込む」というシーケンスを、「本体をバイトスライスに収集し、本物のヘッダと本体を一度に書き込む」方式に変更。これにより、シンボルごとのシーク回数を減らし、コードの可読性を向上させた。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/3601a1e77d7fdd4c98c3dbd6f1bfa0028bc24fdd](https://github.com/golang/go/commit/3601a1e77d7fdd4c98c3dbd6f1bfa0028bc24fdd)

## 元コミット内容
```
cmd/link: write DWARF PC table without seeking

This per-symbol table was written with the strategy:

        1. record offset and write fake header
        2. write body
        3. seek back to fake header
        4. write real header

This CL collects the per-symbol body into a []byte, then writes the
real header followed by the body to the output file. This saves two
seeks per-symbol and overwriting the fake header.

Small performance improvement (3.5%) in best-of-ten links of godoc:

tip:  real 0m1.132s user 0m1.256s
this: real 0m1.090s user 0m1.210s

I'm not sure if the performance measured here alone justifies it,
but I think this is an easier to read style of code.

Reviewed-on: https://go-review.googlesource.com/20074

```

## 変更の背景
Goリンカ（`cmd/link`）がDWARFデバッグ情報を生成する際、特にPC (Program Counter) テーブルの書き込みにおいて、非効率なI/Oパターンが存在していました。具体的には、各シンボル（関数など）のデバッグ情報（Frame Description Entry, FDE）をファイルに書き込む際、FDEの全長が確定する前にその内容を書き始める必要がありました。このため、まず仮のヘッダ（例えば長さ0）を書き込み、その後にFDEの本体を書き込み、最後にファイルポインタを仮ヘッダの位置に戻して正しい長さを上書きするという手順を踏んでいました。

この「シーク＆上書き」のプロセスは、シンボルごとに2回のファイルシークと1回の上書きを伴い、特に多数のシンボルを持つ大きなバイナリをリンクする際にI/Oオーバーヘッドとなっていました。ファイルシークはディスクI/Oにおいて比較的コストの高い操作であり、頻繁に行われるとリンカのパフォーマンスに影響を与えます。

このコミットは、この非効率性を解消し、リンカのパフォーマンスを向上させるとともに、コードの可読性を高めることを目的としています。コミットメッセージには、`godoc`のリンクで3.5%のパフォーマンス改善が見られたと記載されていますが、それ以上にコードのスタイル改善（可読性向上）も重要な動機とされています。

## 前提知識の解説

### DWARF (Debugging With Attributed Record Formats)
DWARFは、ソースレベルデバッガがプログラムの実行状態を解釈するために必要な情報を提供する標準的なデバッグファイル形式です。コンパイルされたバイナリと元のソースコードとの間のマッピング、変数情報、型情報、スタックフレームの構造などを記述します。これにより、デバッガは実行中のプログラムの内部状態を、開発者が理解しやすいソースコードのレベルで表示・操作できます。

### PC (Program Counter) テーブル
DWARF情報の一部として、PCテーブル（より正確には、FDE内のLocation ListやLine Number Programなど）は、プログラムカウンタ（命令ポインタ）の値と、それに対応するソースコードの行番号、ファイル名、スコープ、スタックフレーム情報などのデバッグ情報を関連付けます。デバッガはPCテーブルを使用して、特定の実行ポイントにおけるプログラムの状態を正確に表示し、ステップ実行やブレークポイントの設定を可能にします。

### Goリンカ (`cmd/link`)
Go言語のリンカは、Goコンパイラによって生成された複数のオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、最終的な実行可能なバイナリを生成するツールです。この過程で、Goランタイムのコード、標準ライブラリ、およびユーザーコードが結合され、デバッグ情報（DWARF）もバイナリに埋め込まれます。リンカは、シンボルの解決、再配置、セクションの配置など、バイナリ生成における重要な役割を担います。

### ファイルI/Oにおけるシークと書き込み
ファイルI/Oにおいて、シーク（`seek`）はファイルポインタを特定のオフセットに移動させる操作です。これは、ファイルの特定の位置から読み書きを開始するために必要です。ディスクI/Oにおいてシークは、特にランダムアクセスの場合、シーケンシャルアクセスに比べて時間がかかる操作です。以前の実装では、ヘッダのサイズが確定する前に本体を書き込む必要があったため、仮ヘッダを書き込んだ後に本体を書き込み、その後ファイルポインタを巻き戻して本物のヘッダを書き込むという「シーク＆上書き」パターンが用いられていました。この頻繁なシークがパフォーマンスボトルネックとなっていました。

### ULEB128 (Unsigned Little Endian Base 128) と SLEB128 (Signed Little Endian Base 128)
これらはDWARFで広く使用される可変長エンコーディング形式です。
-   **ULEB128**: 符号なし整数をエンコードするために使用されます。各バイトの最上位ビット（MSB）は、さらにバイトが続くかどうかを示します（1なら続く、0なら終わり）。残りの7ビットがデータのペイロードです。
-   **SLEB128**: 符号付き整数をエンコードするために使用されます。ULEB128と同様に可変長ですが、符号を正しく処理するために、最後のバイトのMSBが0の場合、そのバイトの6ビット目が符号拡張のために使用されます。
これらのエンコーディングは、小さな数値を効率的に表現し、大きな数値にはより多くのバイトを使用することで、デバッグ情報のファイルサイズを最適化するのに役立ちます。

### CFA (Call Frame Address)
DWARFにおけるCFAは、関数の呼び出しフレーム（スタックフレーム）のアドレスを指します。デバッガがスタックトレースを生成したり、ローカル変数の値を読み取ったりするために不可欠な情報です。CFAは通常、スタックポインタやフレームポインタとオフセットの組み合わせで計算されます。DWARFのCall Frame Information (CFI) は、プログラムカウンタの各ポイントでCFAがどのように計算されるかを記述し、デバッガが正確なスタックウォークを実行できるようにします。

## 技術的詳細

このコミットの主要な変更点は、DWARF PCテーブル、特にFDE (Frame Description Entry) の書き込みロジックを、ファイルシークと上書きを伴う逐次的なI/Oから、メモリバッファ（`[]byte`）への書き込みと、その後の単一のファイルI/O操作へと変更したことです。

以前の方式では、各シンボルのFDEを書き込む際に、FDEの全長が確定する前にその内容を書き始める必要がありました。FDEのヘッダにはそのFDEの全長が含まれるため、この情報が不明な段階でヘッダを書き込むことはできませんでした。そのため、以下のような非効率な手順が取られていました。
1.  FDEの開始オフセットを記録する。
2.  FDEの長さを表すプレースホルダ（例えば0）を書き込む（仮ヘッダ）。
3.  FDEの本体（PC-CFAデルタなど）をファイルに書き込む。
4.  FDE本体の書き込みが完了した後、ファイルポインタを仮ヘッダの位置に戻すためにシークする。
5.  FDEの正確な長さを計算し、仮ヘッダを上書きして本物のヘッダを書き込む。
6.  ファイルポインタをFDEの末尾に戻すために再度シークする。

新しい方式では、FDEの本体部分を一時的なバイトスライス`deltaBuf`にすべて書き込みます。このスライスが完成した時点でFDEの全長が確定するため、その長さを計算し、正しいFDEヘッダ（長さ、CIEへのポインタ、初期位置、アドレス範囲）を直接ファイルに書き込みます。その後、`deltaBuf`の内容を一度にファイルに書き出すことで、中間的なファイルシークと上書きを完全に排除します。

これにより、以下のメリットが生まれます。
1.  **I/Oパフォーマンスの向上**: シンボルごとに発生していた2回のファイルシークと1回の上書きが不要になるため、特に多数のシンボルを持つ大規模なプログラムのリンク時間が短縮されます。コミットメッセージには`godoc`のリンクで3.5%の改善が示されており、これはI/Oバウンドな処理において顕著な効果です。
2.  **コードの可読性と保守性の向上**: 複雑なシークと上書きのロジックが、メモリバッファへのアペンドと単一の書き込みというより単純なパターンに置き換えられるため、コードが理解しやすくなります。これにより、将来の機能追加やバグ修正が容易になります。
3.  **Goらしいイディオムへの適合**: Go言語では、バイトスライスへのアペンドと一括書き込みは一般的なパターンであり、この変更はGoのイディオムにより適合しています。

また、`uleb128enc`や`sleb128enc`といったエンコーディング関数も、`dst []byte`に直接書き込み、書き込んだバイト数を返す形式から、`appendUleb128`や`appendSleb128`のようにバイトスライスにアペンドして新しいスライスを返す形式に変更されています。これにより、呼び出し元でバッファの管理がより柔軟になり、コードの簡潔さにも寄与しています。

## コアとなるコードの変更箇所

変更は主に`src/cmd/link/internal/ld/dwarf.go`ファイルに集中しています。

1.  **`uleb128enc` / `sleb128enc` の変更**:
    -   以前は`dst []byte`に直接書き込み、書き込んだバイト数を返していました。
    -   新しい`appendUleb128` / `appendSleb128`関数は、既存のバイトスライス`b`にエンコード結果をアペンドし、更新されたバイトスライスを返します。これにより、呼び出し元でのバッファ管理がよりGoらしく、効率的になります。

2.  **`uleb128put` / `sleb128put` の変更**:
    -   これらの関数は、`uleb128enc` / `sleb128enc`の変更に合わせて、`encbuf`スライスに直接書き込むのではなく、`appendUleb128` / `appendSleb128`を使用して一時的なバイトスライスを構築し、それを`Cwrite`で書き出すように変更されました。

3.  **`newmemberoffsetattr` / `newcfaoffsetattr` の変更**:
    -   これらの関数も、DWARF属性ブロックを構築する際に、以前は`block`配列に逐次的に書き込み、インデックス`i`を更新していましたが、新しい実装では`append`関数を使ってバイトスライス`b`に要素を追加していく形に変更されています。これにより、コードがより簡潔になっています。

4.  **`putpccfadelta` の変更と `appendPCDeltaCFA` の導入**:
    -   以前の`putpccfadelta`関数は、PC-CFAデルタ情報を直接ファイルに書き込んでいました。
    -   新しい`appendPCDeltaCFA`関数は、PC-CFAデルタ情報をバイトスライス`b`にアペンドし、更新されたスライスを返します。これにより、FDE本体の情報をメモリバッファに収集できるようになります。

5.  **`writeframes` 関数の主要な変更**:
    -   この関数内で、各シンボル（`s`）のFDEを書き込むロジックが大幅に変更されました。
    -   以前は、FDEの開始オフセット`fdeo`を記録し、仮の長さ（`Thearch.Lput(0)`）を書き込み、その後FDE本体を書き込み、最後に`Cseek(fdeo)`で戻って正しい長さを上書きしていました。
    -   新しい実装では、`var deltaBuf []byte`を導入し、FDE本体（PC-CFAデルタなど）をすべて`deltaBuf`にアペンドします。
    -   `deltaBuf`が完成した後、その`len(deltaBuf)`に基づいてFDEの全長を計算し、正しいFDEヘッダ（長さ、CIEへのポインタ、初期位置、アドレス範囲）を直接`Thearch.Lput`や`addrput`でファイルに書き込みます。
    -   最後に、`Cwrite(deltaBuf)`を呼び出して、収集したFDE本体の内容を一度にファイルに書き出します。
    -   これにより、`Cseek`の呼び出しが不要になり、ファイルI/Oの効率が向上しています。

## コアとなるコードの解説

### `appendUleb128` / `appendSleb128` (例: `src/cmd/link/internal/ld/dwarf.go` L111-139)

```go
func appendUleb128(b []byte, v uint64) []byte {
	for {
		c := uint8(v & 0x7f) // 下位7ビットを取得
		v >>= 7              // 値を右に7ビットシフト
		if v != 0 {          // まだ上位ビットがある場合
			c |= 0x80        // 最上位ビットを1に設定（後続バイトあり）
		}
		b = append(b, c)     // バイトスライスにアペンド
		if c&0x80 == 0 {     // 最上位ビットが0なら終了
			break
		}
	}
	return b
}

func appendSleb128(b []byte, v int64) []byte {
	for {
		c := uint8(v & 0x7f) // 下位7ビットを取得
		s := uint8(v & 0x40) // 現在の7ビットチャンクの符号ビット（6ビット目）
		v >>= 7              // 値を右に7ビットシフト
		// 継続条件:
		// (v != -1 || s == 0) : 正の数でまだビットがある、または負の数だがまだビットがある
		// (v != 0 || s != 0)  : 0ではない、または符号ビットが立っている
		// これら両方が真の場合、まだ上位ビットがある
		if (v != -1 || s == 0) && (v != 0 || s != 0) {
			c |= 0x80 // 最上位ビットを1に設定（後続バイトあり）
		}
		b = append(b, c) // バイトスライスにアペンド
		if c&0x80 == 0 { // 最上位ビットが0なら終了
			break
		}
	}
	return b
}
```
これらの関数は、符号なし（ULEB128）および符号付き（SLEB128）の整数を可変長バイト列にエンコードし、既存のバイトスライス`b`にアペンドして返します。各バイトの最上位ビット（MSB）が1であれば後続バイトがあることを示し、0であればそのバイトが最後のバイトであることを示します。SLEB128では、符号拡張のロジックが追加されており、負の数を正しく表現するために特別な継続条件が設けられています。これにより、小さな数値は少ないバイトで、大きな数値はより多くのバイトで表現され、デバッグ情報のファイルサイズを効率的に保ちます。

### `writeframes` 関数内のFDE書き込みロジック (例: `src/cmd/link/internal/ld/dwarf.go` L1779-1820)

```go
func writeframes() {
	// ... (関数の冒頭部分、省略) ...

	var deltaBuf []byte // FDE本体を一時的に格納するバイトスライス
	var pcsp Pciter
	for Ctxt.Cursym = Ctxt.Textp; Ctxt.Cursym != nil; Ctxt.Cursym = Ctxt.Cursym.Next {
		s := Ctxt.Cursym // 現在処理中のシンボル
		if s.Type == obj.STEXT && s.Text != nil && s.Text.From.Sym != nil {
			// ... (シンボルがテキストセクションに属し、有効な場合のみ処理、省略) ...

			// FDE (Frame Description Entry) を出力する。DWARF標準のセクション6.4.1を参照。
			// まず、FDEの本体部分をバイトバッファに構築する。
			deltaBuf = deltaBuf[:0] // 各シンボル処理の開始時にバッファをクリアし、再利用

			// PC (Program Counter) の範囲をイテレートし、CFA (Call Frame Address) のデルタ情報を収集
			for pciterinit(Ctxt, &pcsp, &s.Pcln.Pcsp); pcsp.done == 0; pciternext(&pcsp) {
				nextpc := pcsp.nextpc
				// ... (PCの範囲チェックなど、省略) ...

				// PC-CFAデルタ情報をdeltaBufにアペンド
				if haslinkregister() {
					deltaBuf = appendPCDeltaCFA(deltaBuf, int64(nextpc)-int64(pcsp.pc), int64(pcsp.value))
				} else {
					deltaBuf = appendPCDeltaCFA(deltaBuf, int64(nextpc)-int64(pcsp.pc), int64(Thearch.Ptrsize)+int64(pcsp.value))
				}
			}
			// DWARFの要件に合わせてパディングを追加
			pad := int(Rnd(int64(len(deltaBuf)), int64(Thearch.Ptrsize))) - len(deltaBuf)
			deltaBuf = append(deltaBuf, zeros[:pad]...) // パディングバイトを追加

			// FDEヘッダを出力する。DWARF標準のセクション6.4.1を参照。
			//	4バイト: FDEの全長（自身を除く）、Thearch.Ptrsizeの倍数である必要がある
			//	4バイト: CIE (Common Information Entry) へのポインタ（オフセット0）
			//	ptrsize: 初期位置 (initial location)
			//	ptrsize: アドレス範囲 (address range)
			// FDEの全長を計算し、ファイルに書き込む
			Thearch.Lput(uint32(4 + 2*Thearch.Ptrsize + len(deltaBuf)))
			if Linkmode == LinkExternal {
				// 外部リンカの場合、リロケーション情報を追加
				adddwarfrel(framesec, framesym, frameo, 4, 0)        // CIEオフセットのリロケーション
				adddwarfrel(framesec, s, frameo, Thearch.Ptrsize, 0) // 初期位置のリロケーション
			} else {
				// 内部リンカの場合、直接値を書き込む
				Thearch.Lput(0)  // CIEオフセット
				addrput(s.Value) // 初期位置
			}
			addrput(s.Size) // アドレス範囲

			Cwrite(deltaBuf) // 収集したFDE本体の全データを一度にファイルに書き出す
		}
	}
	Cflush() // バッファリングされたI/Oをフラッシュ
}
```
このコードスニペットは、`writeframes`関数内で各シンボル（`s`）のFDEをどのように書き込むかを示しています。
-   `var deltaBuf []byte`は、FDEの本体部分を一時的に保持するためのバイトスライスです。各シンボルの処理開始時に`deltaBuf = deltaBuf[:0]`でクリアされ、再利用されます。
-   `for pciterinit(...)`ループ内で、`appendPCDeltaCFA`を呼び出してPC-CFAデルタ情報（プログラムカウンタの変更とCFAの変更を記述するDWARF命令）を`deltaBuf`に順次追加していきます。
-   ループ終了後、`len(deltaBuf)`を使ってFDE本体の正確な長さを計算し、DWARFの要件（`Thearch.Ptrsize`の倍数）に合わせてパディングバイトを追加します。
-   その後、`Thearch.Lput`や`addrput`などの関数を使って、計算されたFDEの全長、CIEへのポインタ、初期位置、アドレス範囲といったFDEヘッダ情報を直接ファイルに書き込みます。
-   最後に、`Cwrite(deltaBuf)`によって、`deltaBuf`に蓄積されたFDE本体の全データを一度のI/O操作でファイルに書き出します。これにより、以前のシークと上書きが不要になり、ファイルI/Oの効率が大幅に向上します。

# [インデックス 20243] ファイルの概要

このコミットは、Goランタイムにおける`nosplit`（スタック分割不可）関数のスタック使用可能領域を32バイト拡張し、128バイトから160バイトに増やしたものです。これにより、特定のアーキテクチャで発生していたリンク時のスタックオーバーフローエラーを解消し、Goの呼び出し規約がC言語よりも多くのスタック空間を使用するという問題に対処しています。

## コミット

commit fe91006a02b4892d95d1625889632aa4e0fe2b58
Author: Russ Cox <rsc@golang.org>
Date:   Wed Aug 27 14:08:26 2014 -0400

    runtime: give nosplit functions 32 more bytes of headroom
    
    The Go calling convention uses more stack space than C.
    On 64-bit systems we've been right up against the limit
    (128 bytes, so only 16 words) and doing awful things to
    our source code to work around it. Instead of continuing
    to do awful things, raise the limit to 160 bytes.
    I am prepared to raise the limit to 192 bytes if necessary,
    but I think this will be enough.
    
    Should fix current link-time stack overflow errors on
            - nacl/arm
            - netbsd/amd64
            - openbsd/amd64
            - solaris/amd64
            - windows/amd64

    CC=golang-codereviews, iant

## 元コミット内容

このコミットは、Goランタイムにおいて、`nosplit`（スタック分割不可）とマークされた関数が利用できるスタック空間を32バイト増やすことを目的としています。Goの呼び出し規約はC言語と比較してより多くのスタック空間を消費するため、特に64ビットシステムでは128バイト（16ワード）という既存の制限に非常に厳しく、この制限を回避するために「ひどいこと」（コード上の不自然な回避策）を講じる必要がありました。このコミットは、そのような回避策を続ける代わりに、制限を160バイトに引き上げることで、問題の根本的な解決を図っています。必要であれば192バイトまで引き上げる準備があるものの、160バイトで十分であると判断されています。

この変更により、以下のアーキテクチャで発生していたリンク時のスタックオーバーフローエラーが修正されることが期待されています。

*   nacl/arm
*   netbsd/amd64
*   openbsd/amd64
*   solaris/amd64
*   windows/amd64

## 変更の背景

Go言語の設計思想の一つに、軽量なゴルーチンと効率的なスタック管理があります。Goランタイムは、必要に応じてスタックを動的に拡張する「スタック分割（stack splitting）」というメカニズムを持っています。しかし、ランタイムの非常に低レベルな部分や、パフォーマンスが極めて重要な一部の関数は、スタック分割のオーバーヘッドを避けるために`nosplit`（スタック分割不可）とマークされます。これらの`nosplit`関数は、あらかじめ決められた小さなスタック領域内で実行を完了する必要があります。

コミットメッセージによると、Goの呼び出し規約はC言語のそれよりも多くのスタック空間を消費します。特に64ビットシステムにおいて、`nosplit`関数に割り当てられていた128バイトというスタック制限は非常に厳しく、開発者はこの制限に「ぎりぎり」の状態でした。この厳しい制限のために、コードベースでは不自然な「ひどいこと」をせざるを得ない状況が発生していました。これは、おそらく関数を不必要に分割したり、スタック使用量を最小限に抑えるためにコードの可読性や構造を犠牲にしたりするような、開発体験を損なう回避策を指していると考えられます。

このような状況は、特にクロスプラットフォーム開発において、特定のアーキテクチャ（nacl/arm, netbsd/amd64, openbsd/amd64, solaris/amd64, windows/amd64）でリンク時のスタックオーバーフローエラーとして顕在化していました。これは、コンパイラやリンカが`nosplit`関数のスタック使用量を正確に予測し、その制限内に収めることが困難であったことを示唆しています。

このコミットは、これらの問題を解決し、開発者が不必要な回避策に頼ることなく、より自然なコードを書けるようにするために、`nosplit`関数のスタック制限を緩和することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスタック管理、特に「スタック分割」と「`nosplit`関数」に関する知識が不可欠です。

1.  **ゴルーチンとスタック**:
    *   Go言語の並行処理の基本単位は「ゴルーチン（goroutine）」です。ゴルーチンはOSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。
    *   各ゴルーチンは独自のスタックを持っています。Goのスタックは、C言語のように固定サイズで大きく確保されるのではなく、最初は非常に小さく（数KB程度）確保され、必要に応じて動的に拡張されます。

2.  **スタック分割（Stack Splitting）**:
    *   Goランタイムは、関数呼び出しの際にスタックの残量をチェックします。もしスタックが不足しそうになった場合、ランタイムは現在のスタックを一時停止し、より大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーします。このプロセスを「スタック分割」と呼びます。
    *   スタック分割は、ゴルーチンが小さなメモリフットプリントで開始し、必要な分だけスタックを成長させることを可能にし、メモリ効率を高めます。

3.  **`nosplit`関数**:
    *   Goランタイムの内部には、スタック分割のメカニズムが適用されない特殊な関数群が存在します。これらは「`nosplit`関数」と呼ばれます。
    *   `nosplit`関数は、通常、ランタイムの非常に低レベルな部分（例: スケジューラ、ガベージコレクタ、コンテキストスイッチ、システムコールハンドラなど）で使用されます。これらの関数は、スタック分割による中断やオーバーヘッドを許容できないため、`nosplit`とマークされます。
    *   `nosplit`関数は、あらかじめ決められた非常に小さな固定サイズのスタック領域内で実行を完了する必要があります。この領域を超えてスタックを使用しようとすると、スタックオーバーフローが発生し、プログラムがクラッシュする可能性があります。
    *   コンパイラは、`nosplit`関数がこの制限を超えないように、厳密なチェックを行います。

4.  **スタックガード（Stack Guard）とスタックリミット（Stack Limit）**:
    *   Goランタイムは、スタックの境界を監視するために「スタックガード」というメカニズムを使用します。スタックガードは、スタックの末尾近くに設定された特別なメモリ領域です。
    *   関数が呼び出される際、スタックポインタがスタックガードの領域に近づくと、スタック分割が必要であると判断されます。
    *   `nosplit`関数には、スタックガードとは別に、より厳密な「スタックリミット」が設定されています。これは、`nosplit`関数が使用できる最大スタックサイズを定義します。このコミットで変更されたのは、この`nosplit`関数のスタックリミットに関連する値です。

5.  **Goの呼び出し規約**:
    *   Goコンパイラは、関数呼び出しの際に引数をスタックにプッシュしたり、戻り値をスタックに格納したり、レジスタを保存したりするための特定の規約（Calling Convention）に従います。
    *   コミットメッセージが示唆するように、Goの呼び出し規約はC言語のそれと比較して、より多くのスタック空間を消費する傾向があるようです。これは、Goが持つ特定の機能（例: インターフェース、クロージャ、deferなど）の実装に関連している可能性があります。

## 技術的詳細

このコミットの核心は、`nosplit`関数が利用できるスタック空間の計算方法を変更し、その実効的な上限を増やすことにあります。

Goランタイムのスタック管理において、`src/pkg/runtime/stack.h`で定義されている`StackSmall`と`StackGuard`という定数が重要な役割を果たします。

*   `StackGuard`: スタックガードの基準となる値で、通常はスタックの開始点から一定のオフセットに設定されます。`src/pkg/runtime/stack_test.go`では`256`と定義されています。
*   `StackSmall`: スタック分割チェック後、スタックポインタがスタックガードからどれだけ下（アドレスが小さい方向）に移動できるかを許容するバイト数です。この値が小さいほど、スタックポインタがスタックガードから離れることができ、結果として`nosplit`関数が利用できるスタック空間が大きくなります。

以前の定義では、`StackSmall`は`128`バイトでした。そして、`nosplit`関数が利用できる実効的なスタックリミット（`StackLimit`）は、`src/pkg/runtime/stack_test.go`で直接`128`と定義されていました。

このコミットでは、以下の変更が行われました。

1.  **`src/pkg/runtime/stack.h`における`StackSmall`の変更**:
    *   `StackSmall`の値が`128`から`96`に減少しました。
    *   この変更は、スタックポインタがスタックガードからさらに`32`バイト（`128 - 96 = 32`）下がることを許容することを意味します。

2.  **`src/pkg/runtime/stack_test.go`における`StackLimit`の計算変更**:
    *   以前は固定値`128`だった`StackLimit`が、`StackGuard - StackSmall`という計算式で導出されるようになりました。
    *   `StackGuard`が`256`、新しい`StackSmall`が`96`であるため、新しい`StackLimit`は`256 - 96 = 160`バイトとなります。

この変更により、`nosplit`関数が利用できるスタック空間の実効的な上限が、以前の`128`バイトから`160`バイトへと`32`バイト増加しました。これは、コミットメッセージで述べられている「32 more bytes of headroom」と完全に一致します。

このスタック空間の拡張は、特に64ビットシステムにおいて、Goの呼び出し規約がC言語よりも多くのスタック空間を必要とするという問題に対処するためのものです。128バイトという制限は、64ビットシステムではわずか16ワードに相当し、非常に小さな関数でも容易にこの制限に達してしまう可能性がありました。32バイトの追加は、4ワード分の余裕を与えることになり、これにより多くのリンク時のスタックオーバーフローエラーが解消されることが期待されます。

影響を受けるアーキテクチャとして具体的に挙げられているのは、`nacl/arm`, `netbsd/amd64`, `openbsd/amd64`, `solaris/amd64`, `windows/amd64`です。これらの環境で特にスタック使用量が厳しく、問題が顕在化していたことを示しています。

`test/nosplit.go`の変更は、このスタック制限の増加をテストケースに反映させるためのものです。既存のテストケースを書き直すのではなく、最初のスタックフレームに意図的に32バイトを追加することで、新しい160バイトの制限をテストできるように調整されています。これは、テストの安定性を保ちつつ、変更が正しく機能することを確認するための賢明なアプローチです。

## コアとなるコードの解説

### `src/pkg/runtime/stack.h`の変更

*   `StackSmall`定数の値が`128`から`96`に変更されました。
*   この`StackSmall`は、スタック分割チェック後にスタックポインタがスタックガードからどれだけ下（アドレスが小さい方向）に移動できるかを定義します。この値を小さくすることで、`nosplit`関数がスタックガードからより遠くまでスタックを使用できるようになり、結果として利用可能なスタック空間が増加します。

### `src/pkg/runtime/stack_test.go`の変更

*   `StackLimit`定数の定義が変更されました。以前は固定値`128`でしたが、新しい定義では`StackGuard - StackSmall`という計算式で導出されるようになりました。
*   `StackGuard`は`256`と定義されており、`StackSmall`が`96`になったため、`StackLimit`は`256 - 96 = 160`となります。
*   この変更により、`nosplit`関数が利用できるスタックの最大サイズが、明示的に128バイトから160バイトに拡張されたことが確認できます。これは、コミットメッセージの意図と完全に一致します。

### `test/nosplit.go`の変更

*   `strings.Split(line, ";")`のループにインデックス変数`i`が追加されました。
*   追加されたコメントにもあるように、この変更は「CL 131450043が制限を128から160に引き上げた」ことを考慮したものです。
*   既存のテストケースを書き直す手間を省くため、ループの最初の要素（`i == 0`）に対してのみ、スタックフレームサイズ`size`に`32`バイトが追加されるようになりました。
*   これにより、テストケースが新しい160バイトの制限を適切に検証できるようになります。これは、テストの保守性を高めつつ、変更の検証を確実に行うための実用的なアプローチです。

これらの変更は、Goランタイムのスタック管理の根幹に関わる部分であり、特に`nosplit`関数の安定性と移植性を向上させる上で重要な役割を果たします。

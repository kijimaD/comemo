## 元コミット内容

このコミットの目的は、Goランタイムにおけるビットマップアロケーションデータ構造のプロトタイプを導入することです。リリース前にはこれらの基盤となるデータ構造のパフォーマンスを向上させる必要がありますが、これらの構造を利用するヘルパー関数のシグネチャは安定したままであると述べられています。これは、将来のパフォーマンス最適化を見据えつつ、現在の設計の方向性を示すものです。

## 変更の背景

Goのガベージコレクタ（GC）は、アプリケーションの実行と並行して動作するコンカレントなマーク＆スイープ方式を採用しています。この方式では、GCがオブジェクトグラフを走査して到達可能なオブジェクトをマークしている間も、アプリケーションは新しいオブジェクトを割り当てたり、既存のオブジェクトへのポインタを変更したりします。このような並行処理の複雑さを管理し、GCのオーバーヘッドを最小限に抑えるためには、効率的なメモリ管理とオブジェクトの状態追跡メカニズムが不可欠です。

このコミットは、特に`mspan`（メモリのスパン）内でオブジェクトの割り当て状態とGCマーキング状態を追跡するためのビットマップ構造を導入することで、この課題に対処しようとしています。これにより、GCは`mspan`内の個々のオブジェクトの状態を高速に判断できるようになり、コンカレントGCの効率と精度が向上します。

具体的には、GoのGCは「三色抽象化」という概念を用いてオブジェクトを分類します。
*   **白（White）**: GCによってまだ発見されていない、または死んでいると見なされるオブジェクト。
*   **灰（Gray）**: GCによって発見されたが、そのポインタがまだ走査されていないオブジェクト。
*   **黒（Black）**: GCによって発見され、そのポインタがすべて走査されたオブジェクト。

このビットマップ構造は、これらの状態を効率的に管理し、特にマークフェーズ中にオブジェクトが生きているかどうかを追跡するために使用されます。また、新しいオブジェクトの割り当て時に空きスロットを迅速に見つけるためにも利用されます。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリ管理システムを持っています。これは、OSから大きなメモリブロックを確保し、それを`mheap`、`mcentral`、`mcache`という階層構造で管理します。

*   **`mheap`**: 全ての動的に割り当てられたメモリを管理する最上位のコンポーネント。OSからメモリを要求し、`mcentral`に`mspan`を提供します。
*   **`mcentral`**: 各サイズクラス（特定のサイズのオブジェクトを格納するための`mspan`のグループ）ごとに`mspan`のリストを管理します。`mcache`が`mspan`を使い切ると、`mcentral`から新しい`mspan`を要求します。
*   **`mcache`**: 各論理プロセッサ（P）に割り当てられたキャッシュで、ロックなしで小さなオブジェクトの割り当てを高速に行うために`mspan`を提供します。

### `mspan`

`mspan`は、Goランタイムにおけるメモリの基本的な単位です。これは1つ以上の連続した8KBのページで構成され、特定の「サイズクラス」のオブジェクトを格納するために使用されます。つまり、1つの`mspan`内のすべてのオブジェクトは同じサイズです。この「segregated fit」アロケーション戦略は、メモリの断片化を減らすのに役立ちます。

### ガベージコレクション（GC）

GoのGCは、コンカレントなマーク＆スイープアルゴリズムを使用します。これは、アプリケーションの実行と並行して動作し、Stop-The-World（STW）ポーズを最小限に抑えることを目指します。

*   **マークフェーズ**: GCは、グローバル変数やアクティブなスタックフレームなどの「ルート」オブジェクトから開始し、到達可能なすべてのオブジェクトを「生きている」とマークします。
*   **ライトバリア**: コンカレントマークフェーズ中に、アプリケーションのゴルーチンがオブジェクトグラフを変更する可能性があります。ライトバリアは、これらの変更を追跡し、生きているオブジェクトが誤って回収されないようにするためのメカニズムです。
*   **スイープフェーズ**: マークフェーズの後、専用のスイープゴルーチンが、マークされていない（死んでいる）オブジェクトが占めるメモリを並行して回収します。このメモリは、将来の割り当てのために利用可能になります。スイーププロセスには、新しく解放されたスロットを反映するように`mspan`の割り当てビットマップを更新することも含まれます。

### ビットマップ

ビットマップは、メモリ領域内の各要素の状態を1ビットで表現するデータ構造です。GCの文脈では、オブジェクトが割り当てられているか、ポインタを含んでいるか、GCによってマークされているか、といった情報を効率的に追跡するために使用されます。

## 技術的詳細

このコミットの主要な変更点は、`src/runtime/mheap.go`内の`mspan`構造体への新しいフィールドの追加です。これらのフィールドは、`mspan`内のオブジェクトの割り当てとGCマーキングの状態をビットマップ形式で管理するために導入されました。

### `mspan`構造体への追加フィールド

*   `freelist gclinkptr`: 以前から存在し、`_MSpanInUse`状態の`mspan`における空きオブジェクトのリストを指します。
*   `stackfreelist gclinkptr`: 新しく追加され、`_MSpanStack`状態の`mspan`における空きスタックのリストを指します。これにより、`freelist`のオーバーロードが回避されます。
*   `freeindex uintptr`: この`mspan`内で次に空きオブジェクトをスキャンし始めるスロットインデックスです。割り当てごとに、`allocBits`を`freeindex`からスキャンし、空きオブジェクトを示す`0`を見つけます。その後、`freeindex`は新しく見つかった空きオブジェクトの直後に調整されます。`freeindex == nelem`の場合、この`mspan`には空きオブジェクトがありません。
*   `allocBits *[maxObjsPerSpan / 8]uint8`: この`mspan`内のオブジェクトの割り当て状態を示すビットマップです。`allocBits[n/8] & (1<<(n%8))`が`0`であればオブジェクト`n`は空きであり、そうでなければ割り当て済みです。`nelem`を超えるビットは未定義であり、参照されるべきではありません。
*   `gcmarkBits *[maxObjsPerSpan / 8]uint8`: この`mspan`内のオブジェクトのGCマーキング状態を示すビットマップです。`allocBits`と同様の形式で、GCマークフェーズ中にオブジェクトが到達可能であるかどうかを追跡します。
*   `nelems uintptr`: `mspan`内のオブジェクトの総数です。
*   `markbits1 [maxObjsPerSpan / 8]uint8`: 各オブジェクトに対応するビットを持つビットマップです。
*   `markbits2 [maxObjsPerSpan / 8]uint8`: `markbits1`と同様に、各オブジェクトに対応するビットを持つビットマップです。

`allocBits`と`gcmarkBits`は、実際には`markbits1`または`markbits2`のいずれかを指すポインタとして機能します。GCサイクルが終了すると、`allocBits`と`gcmarkBits`はポインタを交換することで役割を入れ替えます。この間接参照のレベルは、`markbits1`と`markbits2`が`mspan`にインライン化されていない実装も容易にします。

### `maxObjsPerSpan`定数

`src/runtime/malloc.go`に`maxObjsPerSpan`定数が追加されました。これは、最小のオブジェクトクラスの単一ページスパンが持つオブジェクトの最大数を定義します。この定数は、`allocBits`や`gcmarkBits`の配列サイズを決定するために使用されます。

```go
const (
	pageShift = _PageShift
	pageSize  = _PageSize
	pageMask  = _PageMask
	// By construction, single page spans of the smallest object class
	// have the most objects per span.
	maxObjsPerSpan = pageSize / 8
)
```
`pageSize / 8`という計算は、1ページ（8KB）を8バイト（ポインタサイズ）で割ることで、1ページに格納できる最小オブジェクトの最大数を概算しています。これは、ビットマップのサイズを決定する上で重要な上限となります。

### `msize.go`の変更

`src/runtime/msize.go`では、エラーメッセージがより簡潔になり、`maxObjsPerSpan`の不変条件をチェックする新しいロジックが追加されました。

```go
	// Check maxObjsPerSpan => number of objects invariant.
	for i, size := range class_to_size {
		if size != 0 && class_to_allocnpages[i]*pageSize/size > maxObjsPerSpan {
			throw("span contains too many objects")
		}
		if size == 0 && i != 0 {
			throw("size is 0 but class is not 0")
		}
	}
```
このループは、各サイズクラスについて、そのサイズクラスのオブジェクトが`mspan`に収まるかどうか、そして`maxObjsPerSpan`を超えないかどうかを検証します。これは、ビットマップの設計がメモリレイアウトと整合していることを保証するための重要なチェックです。

## コアとなるコードの解説

### `src/runtime/malloc.go`における`maxObjsPerSpan`の導入

`maxObjsPerSpan`定数は、`mspan`が保持できるオブジェクトの最大数を定義します。これは、特に最小サイズのオブジェクトクラスにおいて、1つのページスパンに収まるオブジェクトの数を考慮して計算されます。この値は、`mspan`構造体内のビットマップ（`allocBits`、`gcmarkBits`、`markbits1`、`markbits2`）のサイズを決定する上で上限として機能します。これにより、ビットマップが`mspan`内のすべての可能なオブジェクトをカバーするのに十分な大きさであることが保証されます。

### `src/runtime/mheap.go`における`mspan`構造体の拡張

`mspan`構造体への新しいフィールドの追加は、GoのコンカレントGCの効率を大幅に向上させることを目的としています。

*   **`stackfreelist`**: `mspan`がスタックを管理する場合に、空きスタックのリストを保持するために導入されました。これにより、既存の`freelist`がオブジェクトとスタックの両方を管理する負担から解放され、コードの明確性が向上します。
*   **`freeindex`**: 新しいオブジェクトを割り当てる際に、`mspan`内の空きスロットを効率的に見つけるための最適化です。以前は、空きリストを走査する必要がありましたが、`freeindex`を使用することで、ビットマップを線形にスキャンするだけで済み、割り当てのレイテンシが削減されます。
*   **`allocBits`と`gcmarkBits`**: これらは、それぞれオブジェクトの割り当て状態とGCマーキング状態を追跡するためのビットマップへのポインタです。これらのビットマップは、`mspan`内の各オブジェクトに対応するビットを持ちます。
    *   `allocBits`は、どのオブジェクトが現在割り当てられているかを示します。
    *   `gcmarkBits`は、GCのマークフェーズ中にどのオブジェクトが到達可能であるかを示します。
*   **`nelems`**: `mspan`内のオブジェクトの総数を正確に追跡します。これは、ビットマップの範囲を管理し、`freeindex`が`mspan`の境界を超えないようにするために重要です。
*   **`markbits1`と`markbits2`**: これらは、`allocBits`と`gcmarkBits`が指す実際のビットマップデータです。GCサイクルごとに、これらのポインタが交換されることで、`allocBits`と`gcmarkBits`の役割が入れ替わります。この「ポインタスワップ」メカニズムは、GCのマークフェーズとスイープフェーズの間でオブジェクトの状態を効率的に切り替えることを可能にし、コンカレントGCの複雑さを管理する上で非常に重要です。また、この間接参照により、将来的に`markbits1`と`markbits2`が`mspan`構造体自体にインライン化されないような実装も可能になります。

これらの変更により、Goランタイムは`mspan`レベルでオブジェクトの割り当てとGCマーキングの状態をよりきめ細かく、かつ効率的に管理できるようになります。これは、GCのSTWポーズをさらに短縮し、全体的なアプリケーションのパフォーマンスを向上させる上で不可欠な基盤となります。

### `src/runtime/msize.go`におけるエラーメッセージの改善と不変条件のチェック

`msize.go`では、エラーメッセージがより簡潔で情報量の少ないものに変更されました。これは、内部エラーメッセージの冗長性を減らすための一般的なクリーンアップの一部である可能性があります。

最も重要な変更は、`initSizes`関数に`maxObjsPerSpan`に関する新しい不変条件チェックが追加されたことです。このチェックは、各サイズクラスについて、そのサイズクラスのオブジェクトが`mspan`に収まる数と`maxObjsPerSpan`で定義された最大数との間に矛盾がないことを保証します。これにより、ビットマップのサイズが`mspan`内のすべてのオブジェクトを適切にカバーできることが保証され、メモリ管理の整合性が強化されます。

# [インデックス 24631] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）中間表現におけるストア操作のサイズ決定ロジックに関するバグを修正します。具体的には、ストア操作のサイズを格納される値の型から推論するのではなく、明示的なサイズを`auxint`フィールドに持たせることで、リライトパスでの型の変更によって誤ったストア幅が選択される問題を解決しています。

## コミット

Author: Keith Randall <khr@golang.org>
Date:   Fri Aug 14 21:47:20 2015 -0700

    [dev.ssa] cmd/compile/internal/ssa: Use explicit size for store ops
    
    Using the type of the store argument is not safe, it may change
    during rewriting, giving us the wrong store width.
    
    (Store ptr (Trunc32to16 val) mem)
    
    This should be a 2-byte store.  But we have the rule:
    
    (Trunc32to16 x) -> x
    
    So if the Trunc rewrite happens before the Store -> MOVW rewrite,
    then the Store thinks that the value it is storing is 4 bytes
    in size and uses a MOVL.  Bad things ensue.
    
    Fix this by encoding the store width explicitly in the auxint field.
    
    In general, we can't rely on the type of arguments, as they may
    change during rewrites.  The type of the op itself (as used by
    the Load rules) is still ok to use.

## 元コミット内容

GoコンパイラのSSA（Static Single Assignment）パスにおいて、ストア操作のサイズを明示的に指定するように変更します。これは、ストアされる引数の型に依存してストアサイズを決定することが安全ではないためです。引数の型はSSAのリライト中に変更される可能性があり、その結果、誤ったストア幅が選択される恐れがありました。

具体的には、`(Store ptr (Trunc32to16 val) mem)`のようなケースで、これは2バイトのストアであるべきです。しかし、`(Trunc32to16 x) -> x`というリライトルールが存在するため、`Trunc`のリライトが`Store -> MOVW`のリライトよりも先に発生すると、`Store`は格納する値が4バイトであると誤解し、`MOVL`（4バイトストア）を使用してしまいます。この問題を解決するため、ストア幅を`auxint`フィールドに明示的にエンコードするように修正します。

一般的に、SSAのリライト中に引数の型が変更される可能性があるため、引数の型に依存することはできません。ただし、操作自体の型（`Load`ルールで使用されるものなど）は引き続き使用しても問題ありません。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、SSA（Static Single Assignment）という中間表現を使用します。SSAは最適化を容易にするための表現形式であり、このSSA形式のコードに対して様々なリライト（変換）ルールが適用され、より効率的なコードに変換されます。

このコミット以前は、メモリへのストア操作（`Store`オペレーション）の際に、何バイトのデータをストアするか（例えば、1バイト、2バイト、4バイト、8バイトなど）は、ストアされる値の型（`val.Type`）から決定されていました。例えば、`uint16`型の値をストアする場合は2バイトストア、`uint32`型なら4バイトストア、といった具合です。

しかし、SSAのリライトルールの中には、値の型を変更する、あるいは型を実質的に無視するようなものがあります。コミットメッセージで挙げられている例は、`Trunc32to16`（32ビット値を16ビット値に切り詰める）という操作です。この操作は、特定の条件下で最適化され、実質的に何もしない操作（`x`）にリライトされることがあります。

問題は、この`Trunc32to16`が`x`にリライトされた後、`Store`オペレーションがその引数の型を再度評価する際に発生します。もし元の値が32ビット型で、`Trunc32to16`が`x`にリライトされた場合、`Store`は引数の型がまだ32ビットであると誤解し、本来2バイトストアであるべきところを4バイトストア（`MOVL`）として処理してしまう可能性がありました。これはメモリ破壊や不正な動作につながる重大なバグです。

このバグを回避するため、ストア操作の「意図されたサイズ」を、値の型に依存しない形で明示的にSSAオペレーションに埋め込む必要がありました。

## 前提知識の解説

### GoコンパイラのSSA

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、SSA（Static Single Assignment）形式の中間表現に変換します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化が容易になります。SSAは、複数のパス（フェーズ）を経て、最終的にターゲットアーキテクチャの機械語に変換されます。

### SSAオペレーションと`Value`、`Type`、`AuxInt`

SSA中間表現では、プログラムの各操作が`Value`オブジェクトとして表現されます。`Value`は、その操作の種類（`Op`）、結果の型（`Type`）、引数（`Args`）、そして補助情報（`AuxInt`や`Aux`）を持ちます。

*   **`Op`**: 実行される操作の種類（例: `OpStore`, `OpLoad`, `OpAdd`, `OpTrunc32to16`など）。
*   **`Type`**: `Value`が生成する結果の型。
*   **`Args`**: その`Value`が依存する他の`Value`（オペランド）。
*   **`AuxInt`**: 整数型の補助情報。例えば、定数値、シフト量、メモリ操作のサイズなど、オペレーションの種類に応じて異なる意味を持ちます。
*   **`Aux`**: 任意の型の補助情報。例えば、シンボルへのポインタなど。

### リライトルール

SSAの最適化は、主にリライトルール（rewrite rules）によって行われます。これらは、特定のパターンにマッチするSSAオペレーションの組み合わせを、より効率的な別のオペレーションの組み合わせに変換する規則です。例えば、`x + 0`を`x`にリライトする、といった単純なものから、より複雑な命令の組み合わせをターゲットアーキテクチャの特定の命令にマッピングするものまで多岐にわたります。

リライトルールは、`src/cmd/compile/internal/ssa/gen/*.rules`ファイルに記述されており、これらはコード生成ツールによってGoのソースコードに変換されます。

### `Trunc32to16`と型の不一致問題

`Trunc32to16`は、32ビットの値を16ビットに切り詰める操作です。例えば、`uint32`型の変数`v`を`uint16`型の変数`w`に代入する際に発生します。
`w = uint16(v)`

この操作は、特定のコンテキスト（例えば、値が既に16ビットの範囲に収まっていることが保証されている場合など）では、実際には何もしなくても良い場合があります。このような場合、SSAリライトルールによって`Trunc32to16 x`が単に`x`に変換されることがあります。

問題は、このリライトが`Store`オペレーションの前に発生すると、`Store`が`x`の元の型（32ビット）を見てしまい、誤って4バイトストアを生成してしまうことです。本来は`uint16`へのストアなので2バイトストアであるべきです。

## 技術的詳細

このコミットの核心は、`Store`オペレーションがその引数の型に依存してストアサイズを決定するのではなく、ストアすべきバイト数を`Value`の`AuxInt`フィールドに明示的に格納するように変更することです。

1.  **`ssa.go`の変更**:
    *   `state`構造体に`newValue3I`という新しいヘルパー関数が追加されました。これは、3つの引数と`auxint`を持つ新しいSSA `Value`を作成するためのものです。
    *   `assign`関数内で、メモリへのストア操作（`OpStore`）を生成する際に、`left.Type.Size()`（ストア対象の型のサイズ）を`newValue3I`の`aux`引数として渡すように変更されました。これにより、`Store`オペレーションが生成される時点で、正しいストアサイズが`AuxInt`に埋め込まれます。

2.  **`func.go`の変更**:
    *   `Block`構造体に`NewValue3I`メソッドが追加されました。これは、`newValue3I`ヘルパー関数が内部的に呼び出すもので、実際に`Value`オブジェクトを生成し、その`AuxInt`フィールドに渡されたサイズをセットします。

3.  **`genericOps.go`の変更**:
    *   `Store`オペレーションのコメントが更新され、`auxint=size`が追加されました。これは、`AuxInt`フィールドがストアサイズを保持することを示すドキュメントの変更です。

4.  **リライトルールの変更 (`AMD64.rules`, `generic.rules`, `rewriteAMD64.go`, `rewritegeneric.go`)**:
    *   最も重要な変更点の一つは、SSAリライトルールがストアサイズを決定する方法です。以前は、`Store ptr val mem`というパターンにマッチし、`val.Type`のプロパティ（`is64BitInt(val.Type)`など）を条件としていました。
    *   このコミットでは、パターンが`Store [size] ptr val mem`のように変更され、`AuxInt`フィールドに格納されたサイズ（`[8]`, `[4]`, `[2]`, `[1]`）を直接条件として使用するようになりました。これにより、`val`の型がリライトによって変更されても、ストアサイズは`AuxInt`によって保証されます。
    *   `rewriteAMD64.go`と`rewritegeneric.go`内の自動生成されたリライト関数も、`v.AuxInt`をチェックするように更新されています。

5.  **テストケースの追加と修正**:
    *   `loadstore_ssa.go`に`testStoreSize`という新しいテスト関数が追加されました。このテストは、`uint16`型の配列要素へのストアが、`Trunc32to16`のリライト後も正しく2バイトストアとして扱われることを検証します。これは、まさにこのコミットが修正しようとしているバグを狙ったものです。
    *   既存のテストファイル（`deadstore_test.go`, `schedule_test.go`, `shift_test.go`）も、`OpStore`オペレーションの`AuxInt`フィールドに適切なサイズ（例えば、`TypeMem`や`TypeInt64`のストアに対しては`8`）が設定されるように更新されています。

この変更により、SSAリライトの順序に依存することなく、ストア操作が常に正しいバイト幅で実行されることが保証されます。

### `src/cmd/compile/internal/gc/ssa.go`

 func (s *state) newValue3I(op ssa.Op, t ssa.Type, aux int64, arg0, arg1, arg2 *ssa.Value) *ssa.Value {
 	return s.curBlock.NewValue3I(s.peekLine(), op, t, aux, arg0, arg1, arg2)
 }

 // ... (assign関数の変更部分)
 func (s *state) assign(op uint8, left *Node, right *Node) {
 	// ...
 	t := left.Type
 	dowidth(t) // 型のサイズを計算・キャッシュする関数
 	var val *ssa.Value
 	// ...
 	// not ssa-able.  Treat as a store.
 	addr := s.addr(left)

### `src/cmd/compile/internal/ssa/func.go`

```go
 // NewValue3I returns a new value in the block with three arguments and an auxint value.
 func (b *Block) NewValue3I(line int32, op Op, t Type, aux int64, arg0, arg1, arg2 *Value) *Value {
 	v := &Value{
 		ID:     b.Func.vid.get(),
 		Op:     op,
 		Type:   t,
 		AuxInt: aux, // ここでauxintがセットされる
 		Block:  b,
 		Line:   line,
 	}
 	v.Args = []*Value{arg0, arg1, arg2}
 	b.Values = append(b.Values, v)
 	return v
 }
```

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` (抜粋)

```
-(Store ptr val mem) && (is64BitInt(val.Type) || isPtr(val.Type)) -> (MOVQstore ptr val mem)
-(Store ptr val mem) && is32BitInt(val.Type) -> (MOVLstore ptr val mem)
-(Store ptr val mem) && is16BitInt(val.Type) -> (MOVWstore ptr val mem)
-(Store ptr val mem) && is8BitInt(val.Type) -> (MOVBstore ptr val mem)

+(Store [8] ptr val mem) -> (MOVQstore ptr val mem)
+(Store [4] ptr val mem) -> (MOVLstore ptr val mem)
+(Store [2] ptr val mem) -> (MOVWstore ptr val mem)
+(Store [1] ptr val mem) -> (MOVBstore ptr val mem)
```

## コアとなるコードの解説

`src/cmd/compile/internal/gc/ssa.go`の`assign`関数は、Go言語の代入操作をSSA形式に変換する主要な部分です。この関数内で、メモリへのストアが必要な場合に`ssa.OpStore`オペレーションが生成されます。

変更前は、`s.newValue3(ssa.OpStore, ssa.TypeMem, addr, val, s.mem())`が呼び出されていました。ここで`newValue3`は`AuxInt`を持たない`Value`を作成します。ストアサイズは、`val`（ストアされる値）の型からリライトルールによって推論されていました。

変更後は、`s.newValue3I(ssa.OpStore, ssa.TypeMem, t.Size(), addr, val, s.mem())`が呼び出されています。ここで`t`は`left.Type`、つまり代入先の変数の型です。`t.Size()`は、その型のバイトサイズを返します。このサイズが`newValue3I`の`aux`引数として渡され、結果として生成される`ssa.Value`の`AuxInt`フィールドに格納されます。

`src/cmd/compile/internal/ssa/func.go`の`NewValue3I`メソッドは、この`aux`引数を直接`Value.AuxInt`に代入しています。これにより、`OpStore`オペレーションが生成された時点で、その`Value`オブジェクトはストアすべき正確なバイトサイズを`AuxInt`として保持することになります。

そして、`src/cmd/compile/internal/ssa/gen/AMD64.rules`のようなリライトルールでは、以前のように`val.Type`のプロパティをチェックする代わりに、`Store [size] ...`という形式で`AuxInt`の値を直接パターンマッチングの条件として使用するようになりました。例えば、`Store [2] ptr val mem`は、`AuxInt`が2である`Store`オペレーションにマッチし、`MOVWstore`（2バイトストア）にリライトされます。

この一連の変更により、ストア操作のサイズ決定が、SSAリライトパスの初期段階で明示的に固定され、その後のリライトによって引数の型が変化しても、ストアのバイト幅が誤って解釈されることがなくなりました。これは、コンパイラの堅牢性と正確性を向上させる上で非常に重要な修正です。

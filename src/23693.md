## 元コミット内容

`cmd/go: read new non-ELF build ID in binaries`

このコミットは、Goバイナリ内のビルドIDを読み取る方法を更新します。特に、ELF形式ではないバイナリ（例：Mach-O、PE、Plan 9）に対して新しいビルドIDの格納形式を導入し、それに対応する読み取りロジックを実装しています。これにより、以前のビルドIDの取り扱いに関する問題（Issue #11048と#11075）が解決されます。

## 変更の背景

Goバイナリには、そのバイナリがどのソースコードからビルドされたかを一意に識別するための「ビルドID」が含まれています。これはデバッグやバージョン管理において非常に有用な情報です。

以前のGoのビルドIDの格納方法にはいくつかの課題がありました。

1.  **非ELFバイナリでの非効率な格納**: ELF形式のバイナリでは、ビルドIDは`PT_NOTE`セクションという専用の領域に格納されていました。これは標準的で効率的な方法です。しかし、Mach-O (macOS)、PE (Windows)、Plan 9といった非ELF形式のバイナリでは、ビルドIDを専用のセクションに格納する標準的な方法がありませんでした。そのため、Goツールチェインは、これらのバイナリの**末尾にビルドIDを文字列として追記する**という、ややハック的な方法を採用していました。
2.  **Issue #11048 (cmd/go: build ID appended to binary breaks signing)**: バイナリの末尾にビルドIDを追記する方法は、バイナリのデジタル署名プロセスと相性が悪いという問題がありました。デジタル署名はバイナリ全体のハッシュに基づいて行われるため、ビルド後に内容が変更されると署名が無効になってしまいます。これは特にmacOSやWindowsで問題となりました。
3.  **Issue #11075 (cmd/go: build ID appended to binary breaks some tools)**: バイナリの末尾に任意のデータを追記することは、一部のツール（特にバイナリの構造を厳密に解析するリンカやローダー、セキュリティツールなど）が予期しない動作をする原因となる可能性がありました。

これらの問題を解決するため、非ELFバイナリにおけるビルドIDの格納方法を見直し、より堅牢で互換性の高いメカニズムを導入する必要がありました。

## 前提知識の解説

*   **ビルドID (Build ID)**: コンパイルされたバイナリに埋め込まれる一意の識別子。通常、ソースコードのリビジョン情報（Gitコミットハッシュなど）やビルド時の環境情報に基づいて生成されます。これにより、特定のバイナリがどのソースコードから生成されたかを追跡できます。Goでは、`go version -m <binary>`コマンドでビルドIDを確認できます。
*   **ELF (Executable and Linkable Format)**: LinuxやUnix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマット。`PT_NOTE`セクションなど、メタデータを格納するための柔軟な構造を持っています。
*   **Mach-O (Mach Object)**: macOSやiOSで使われている実行可能ファイル、オブジェクトファイル、共有ライブラリのフォーマット。ELFとは異なる構造を持ちます。
*   **PE (Portable Executable)**: Windowsで使われている実行可能ファイル、オブジェクトファイル、DLLのフォーマット。Mach-Oと同様に、ELFとは異なる構造を持ちます。
*   **Plan 9**: ベル研究所が開発した分散オペレーティングシステム。独自のバイナリフォーマットを使用します。
*   **テキストセグメント (Text Segment)**: 実行可能バイナリのセクションの一つで、プログラムの実行可能な機械語コード（命令）が格納されている領域。通常、バイナリの先頭に近い位置に配置されます。
*   **`strconv.Unquote`**: Go言語の標準ライブラリ`strconv`パッケージの関数で、引用符で囲まれた文字列リテラル（例: `"hello"`）から引用符を取り除き、エスケープシーケンスを解釈して元の文字列を返す関数です。

## 技術的詳細

このコミットの主要な変更点は、非ELFバイナリにおけるビルドIDの格納戦略の変更と、それに伴う読み取りロジックの更新です。

**旧戦略（非ELFバイナリ）**:
バイナリの末尾に以下の形式の文字列を追記していました。

```
<NUL>
go binary
build id "XXX"
end go binary
```

この方法はシンプルでしたが、前述の通りデジタル署名や一部のツールとの互換性問題がありました。

**新戦略（非ELFバイナリ）**:
ビルドIDをバイナリの末尾に追記する代わりに、リンカが**テキストセグメントの先頭付近に非命令バイトとしてビルドIDを格納する**ようになりました。具体的には、以下の形式のバイトシーケンスが使用されます。

```
\xff Go build ID: "XXX"\n \xff
```

*   `\xff`: これは、GoバイナリのビルドIDマーカーとして機能する特殊なバイトです。命令コードとしては無効なバイトシーケンスであることが期待され、実行時に誤ってコードとして解釈されることを防ぎます。
*   `Go build ID: "XXX"\n \xff`: 実際のビルドID文字列が引用符で囲まれ、特定のプレフィックスとサフィックスで挟まれています。

この新しい格納場所は、以下の理由から選択されました。

1.  **バイナリの末尾変更の回避**: バイナリの末尾を変更しないため、デジタル署名やバイナリサイズに依存するツールとの互換性が向上します。
2.  **ポータビリティ**: テキストセグメントの先頭付近は、ほとんどのバイナリフォーマットで比較的安定した位置であり、様々なOSやアーキテクチャでこの方法を適用しやすいという利点があります。
3.  **読み取りの効率化**: バイナリ全体を読み込む必要がなく、先頭の数KBを読み込むだけでビルドIDを検出できます。コミットのコメントにもあるように、テキストセグメントの開始オフセットは、Plan 9で0x20、Windowsで0x600、Mach-Oで0x1000と、いずれも8KBの範囲内に収まります。

**読み取りロジックの変更**:
`readBuildIDFromBinary`関数が、この新しい格納形式に対応するように変更されました。

1.  **先頭8KBの読み込み**: ファイルの先頭8KBを読み込むように変更されました。これは、ELFヘッダや非ELFバイナリのテキストセグメントの先頭を含むのに十分なサイズです。
2.  **ELFバイナリの優先処理**: 最初に、読み込んだデータがELF形式であるかをチェックし、もしそうであれば既存の`readELFGoBuildID`関数を使ってビルドIDを読み取ります。
3.  **非ELFバイナリの処理**: ELFではない場合、読み込んだデータの中から新しいビルドIDマーカー`\xff Go build ID: "`と`"\n \xff`を探します。これらが見つかれば、その間の引用符で囲まれた文字列を`strconv.Unquote`でデコードしてビルドIDとして返します。

この変更により、GoバイナリのビルドIDの取り扱いがより堅牢になり、様々なプラットフォームでの互換性が向上しました。

*   変更後は、`darwin/arm`, `darwin/arm64`, `nacl/386`, `nacl/amd64p32`, `nacl/arm`といった特定のアーキテクチャとOSの組み合わせで「ファイルシステムがない」という理由でスキップされるようになりました。これは、テスト環境の制約によるもので、ビルドIDの読み取りロジック自体の変更とは直接関係ありませんが、テストの適用範囲を調整しています。
*   `defer os.RemoveAll(d)`が追加され、テスト後に一時ディレクトリを確実にクリーンアップするようになりました。

### `src/cmd/go/pkg.go`

*   `goBinary`, `endGoBinary`, `newlineAndBuildid`といった、古いビルドIDの末尾追記形式に関連するバイトスライス定義が削除され、代わりに新しい形式のプレフィックスとサフィックスである`goBuildPrefix`と`goBuildEnd`が定義されました。
    *   `goBuildPrefix = []byte("\xff Go build ID: \"")`
    *   `goBuildEnd = []byte("\"\n \xff")`
*   `readBuildIDFromBinary`関数の実装が大幅に変更されました。
    *   バイナリの末尾から読み取るロジックが削除され、代わりにファイルの**先頭8KB**を読み込むように変更されました (`data := make([]byte, 8192)`).
    *   ELFバイナリの検出と処理は引き続き行われます。
    *   非ELFバイナリの場合、読み込んだデータの中から`goBuildPrefix`と`goBuildEnd`を探し、その間の引用符で囲まれた文字列をビルドIDとして抽出するロジックが実装されました。
    *   ビルドIDの抽出には`bytes.Index`と`strconv.Unquote`が使用されます。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/go/pkg.go`内の`readBuildIDFromBinary`関数の変更にあります。

```go
// pkg.go
var (
	goBuildPrefix = []byte("\xff Go build ID: \"")
	goBuildEnd    = []byte("\"\n \xff")

	elfPrefix = []byte("ELF\x7F")
)

func readBuildIDFromBinary(filename string) (id string, err error) {
	// ... (エラーハンドリング、ファイルオープンなど)

	// Read the first 8 kB of the binary file.
	// That should be enough to find the build ID.
	f, err := os.Open(filename)
	if err != nil {
		return "", err
	}
	defer f.Close()

	data := make([]byte, 8192) // 先頭8KBを読み込む
	_, err = io.ReadFull(f, data)
	if err == io.ErrUnexpectedEOF {
		err = nil
	}
	if err != nil {
		return "", err
	}

	// Check for ELF first
	if bytes.HasPrefix(data, elfPrefix) {
		return readELFGoBuildID(filename, f, data)
	}

	// For non-ELF, search for the new build ID marker
	i := bytes.Index(data, goBuildPrefix) // goBuildPrefixを探す
	if i < 0 {
		// Missing. Treat as successful but build ID empty.
		return "", nil
	}

	j := bytes.Index(data[i+len(goBuildPrefix):], goBuildEnd) // goBuildEndを探す
	if j < 0 {
		return "", &os.PathError{Op: "parse", Path: filename, Err: errBuildIDMalformed}
	}

	// Extract the quoted string and unquote it
	quoted := data[i+len(goBuildPrefix)-1 : i+len(goBuildPrefix)+j+1]
	id, err = strconv.Unquote(string(quoted))
	if err != nil {
		return "", &os.PathError{Op: "parse", Path: filename, Err: errBuildIDMalformed}
	}

	return id, nil
}
```

このコードは、以下の手順でビルドIDを読み取ります。

1.  **ファイルオープンと先頭読み込み**: 指定されたバイナリファイルを開き、その先頭8192バイト（8KB）を`data`バイトスライスに読み込みます。これは、ELFヘッダや非ELFバイナリのテキストセグメントの先頭部分をカバーするのに十分なサイズです。
2.  **ELF形式のチェック**: 読み込んだ`data`が`ELF\x7F`で始まる場合、それはELFバイナリであると判断し、専用の`readELFGoBuildID`関数に処理を委譲します。
3.  **非ELF形式のビルドID検索**: ELFではない場合、`data`スライス内で`goBuildPrefix` (`\xff Go build ID: "`) の出現箇所を`bytes.Index`で検索します。
4.  **ビルドIDの抽出**: `goBuildPrefix`が見つかった場合、その直後から`goBuildEnd` (`"\n \xff`) までの範囲を検索し、ビルドIDの引用符で囲まれた部分を特定します。
5.  **デコード**: 特定された引用符付き文字列（例: `"de305a197f5c9ca3bb09da024e06ba7be0c7435d"`) を`strconv.Unquote`関数でデコードし、実際のビルドID文字列を取得します。
6.  **エラーハンドリング**: 検索に失敗したり、デコード中にエラーが発生した場合は、適切なエラーを返します。

この変更により、Goツールチェインは、バイナリの末尾にデータを追記するという非標準的な方法から脱却し、より標準的で互換性の高い方法でビルドIDを管理できるようになりました。

## 前提知識の解説

*   **ビルドID (Build ID)**: コンパイルされたバイナリに埋め込まれる一意の識別子です。通常、ソースコードのリビジョン情報（Gitコミットハッシュなど）やビルド時の環境情報に基づいて生成されます。これにより、特定のバイナリがどのソースコードから生成されたかを追跡できます。Goでは、`go version -m <binary>`コマンドでビルドIDを確認できます。ビルドIDは通常、`actionID/contentID`の形式に従います。`actionID`はビルド入力のハッシュであり、ビルドキャッシュの最適化に利用されます。`contentID`はコンパイルされたアーカイブまたはバイナリ自体のハッシュであり、再現可能なビルドの検証に重要です。
*   **ELF (Executable and Linkable Format)**: LinuxやUnix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。`PT_NOTE`セクションなど、メタデータを格納するための柔軟な構造を持っています。
*   **Mach-O (Mach Object)**: macOSやiOSで使われている実行可能ファイル、オブジェクトファイル、共有ライブラリのフォーマットです。ELFとは異なる構造を持ちます。
*   **PE (Portable Executable)**: Windowsで使われている実行可能ファイル、オブジェクトファイル、DLLのフォーマットです。Mach-Oと同様に、ELFとは異なる構造を持ちます。
*   **Plan 9**: ベル研究所が開発した分散オペレーティングシステムです。独自のバイナリフォーマットを使用します。
*   **テキストセグメント (Text Segment)**: 実行可能バイナリのセクションの一つで、プログラムの実行可能な機械語コード（命令）が格納されている領域です。通常、バイナリの先頭に近い位置に配置されます。
*   **`strconv.Unquote`**: Go言語の標準ライブラリ`strconv`パッケージの関数で、引用符で囲まれた文字列リテラル（例: `"hello"`）から引用符を取り除き、エスケープシーケンスを解釈して元の文字列を返す関数です。

## 技術的詳細

このコミットの主要な変更点は、非ELFバイナリにおけるビルドIDの格納戦略の変更と、それに伴う読み取りロジックの更新です。

**旧戦略（非ELFバイナリ）**:
バイナリの末尾に以下の形式の文字列を追記していました。

```
<NUL>
go binary
build id "XXX"
end go binary
```

この方法はシンプルでしたが、前述の通りデジタル署名や一部のツールとの互換性問題がありました。

**新戦略（非ELFバイナリ）**:
ビルドIDをバイナリの末尾に追記する代わりに、リンカが**テキストセグメントの先頭付近に非命令バイトとしてビルドIDを格納する**ようになりました。具体的には、以下の形式のバイトシーケンスが使用されます。

```
\xff Go build ID: "XXX"\n \xff
```

*   `\xff`: これは、GoバイナリのビルドIDマーカーとして機能する特殊なバイトです。命令コードとしては無効なバイトシーケンスであることが期待され、実行時に誤ってコードとして解釈されることを防ぎます。
*   `Go build ID: "XXX"\n \xff`: 実際のビルドID文字列が引用符で囲まれ、特定のプレフィックスとサフィックスで挟まれています。

この新しい格納場所は、以下の理由から選択されました。

1.  **バイナリの末尾変更の回避**: バイナリの末尾を変更しないため、デジタル署名やバイナリサイズに依存するツールとの互換性が向上します。
2.  **ポータビリティ**: テキストセグメントの先頭付近は、ほとんどのバイナリフォーマットで比較的安定した位置であり、様々なOSやアーキテクチャでこの方法を適用しやすいという利点があります。
3.  **読み取りの効率化**: バイナリ全体を読み込む必要がなく、先頭の数KBを読み込むだけでビルドIDを検出できます。コミットのコメントにもあるように、テキストセグメントの開始オフセットは、Plan 9で0x20、Windowsで0x600、Mach-Oで0x1000と、いずれも8KBの範囲内に収まります。

**読み取りロジックの変更**:
`readBuildIDFromBinary`関数が、この新しい格納形式に対応するように変更されました。

1.  **先頭8KBの読み込み**: ファイルの先頭8KBを読み込むように変更されました。これは、ELFヘッダや非ELFバイナリのテキストセグメントの先頭を含むのに十分なサイズです。
2.  **ELFバイナリの優先処理**: 最初に、読み込んだデータがELF形式であるかをチェックし、もしそうであれば既存の`readELFGoBuildID`関数を使ってビルドIDを読み取ります。
3.  **非ELFバイナリの処理**: ELFではない場合、読み込んだデータの中から新しいビルドIDマーカー`\xff Go build ID: "`と`"\n \xff`を探します。これらが見つかれば、その間の引用符で囲まれた文字列を`strconv.Unquote`でデコードしてビルドIDとして返します。

この変更により、GoバイナリのビルドIDの取り扱いがより堅牢になり、様々なプラットフォームでの互換性が向上しました。

    *   `goBuildPrefix = []byte("\xff Go build ID: \"")`
    *   `goBuildEnd = []byte("\"\n \xff")`
*   `readBuildIDFromBinary`関数の実装が大幅に変更されました。
    *   バイナリの末尾から読み取るロジックが削除され、代わりにファイルの**先頭8KB**を読み込むように変更されました (`data := make([]byte, 8192)`).
    *   ELFバイナリの検出と処理は引き続き行われます。
    *   非ELFバイナリの場合、読み込んだデータの中から`goBuildPrefix`と`goBuildEnd`を探し、その間の引用符で囲まれた文字列をビルドIDとして抽出するロジックが実装されました。
    *   ビルドIDの抽出には`bytes.Index`と`strconv.Unquote`が使用されます。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/go/pkg.go`内の`readBuildIDFromBinary`関数の変更にあります。

```go
// pkg.go
var (
	goBuildPrefix = []byte("\xff Go build ID: \"")
	goBuildEnd    = []byte("\"\n \xff")

	elfPrefix = []byte("ELF\x7F")
)

func readBuildIDFromBinary(filename string) (id string, err error) {
	// ... (エラーハンドリング、ファイルオープンなど)

	// Read the first 8 kB of the binary file.
	// That should be enough to find the build ID.
	f, err := os.Open(filename)
	if err != nil {
		return "", err
	}
	defer f.Close()

	data := make([]byte, 8192) // 先頭8KBを読み込む
	_, err = io.ReadFull(f, data)
	if err == io.ErrUnexpectedEOF {
		err = nil
	}
	if err != nil {
		return "", err
	}

	// Check for ELF first
	if bytes.HasPrefix(data, elfPrefix) {
		return readELFGoBuildID(filename, f, data)
	}

	// For non-ELF, search for the new build ID marker
	i := bytes.Index(data, goBuildPrefix) // goBuildPrefixを探す
	if i < 0 {
		// Missing. Treat as successful but build ID empty.
		return "", nil
	}

	j := bytes.Index(data[i+len(goBuildPrefix):], goBuildEnd) // goBuildEndを探す
	if j < 0 {
		return "", &os.PathError{Op: "parse", Path: filename, Err: errBuildIDMalformed}
	}

	// Extract the quoted string and unquote it
	quoted := data[i+len(goBuildPrefix)-1 : i+len(goBuildPrefix)+j+1]
	id, err = strconv.Unquote(string(quoted))
	if err != nil {
		return "", &os.PathError{Op: "parse", Path: filename, Err: errBuildIDMalformed}
	}

	return id, nil
}
```

このコードは、以下の手順でビルドIDを読み取ります。

1.  **ファイルオープンと先頭読み込み**: 指定されたバイナリファイルを開き、その先頭8192バイト（8KB）を`data`バイトスライスに読み込みます。これは、ELFヘッダや非ELFバイナリのテキストセグメントの先頭部分をカバーするのに十分なサイズです。
2.  **ELF形式のチェック**: 読み込んだ`data`が`ELF\x7F`で始まる場合、それはELFバイナリであると判断し、専用の`readELFGoBuildID`関数に処理を委譲します。
3.  **非ELF形式のビルドID検索**: ELFではない場合、`data`スライス内で`goBuildPrefix` (`\xff Go build ID: "`) の出現箇所を`bytes.Index`で検索します。
4.  **ビルドIDの抽出**: `goBuildPrefix`が見つかった場合、その直後から`goBuildEnd` (`"\n \xff`) までの範囲を検索し、ビルドIDの引用符で囲まれた部分を特定します。
5.  **デコード**: 特定された引用符付き文字列（例: `"de305a197f5c9ca3bb09da024e06ba7be0c7435d"`) を`strconv.Unquote`関数でデコードし、実際のビルドID文字列を取得します。
6.  **エラーハンドリング**: 検索に失敗したり、デコード中にエラーが発生した場合は、適切なエラーを返します。

この変更により、Goツールチェインは、バイナリの末尾にデータを追記するという非標準的な方法から脱却し、より標準的で互換性の高い方法でビルドIDを管理できるようになりました。

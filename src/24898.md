## 変更の背景

この変更の背景には、Goのビルドシステムにおける `go build` と `go install` コマンドの挙動の微妙な違いと、それによって引き起こされる可能性のある混乱がありました。

従来の `go build` コマンドは、通常、カレントディレクトリに実行可能バイナリを生成します。一方、`go install` コマンドは、ソースコードをコンパイルした後、生成されたバイナリを `$GOPATH/bin` (または `$GOBIN` 環境変数で指定されたパス) に配置します。

問題は、ユーザーがまず `go build` を実行してソースディレクトリにバイナリを作成し、その後 `go install` を実行した場合に発生しました。このシナリオでは、ソースディレクトリには `go build` によって生成されたバイナリが残り、`$GOPATH/bin` には `go install` によって生成されたバイナリが存在することになります。これにより、以下のような問題が生じる可能性がありました。

1.  **意図しないバイナリの実行**: ユーザーがソースディレクトリ内で作業している際に、誤って古い `go build` バイナリを実行してしまう可能性がありました。特に、`go install` で新しいバージョンをインストールしたつもりでも、ソースディレクトリの古いバイナリが実行され続けるという混乱が生じやすかったです。
2.  **ディスクスペースの無駄**: 同じプログラムのバイナリが複数箇所に存在することになり、わずかながらディスクスペースを無駄にしていました。
3.  **ビルド環境のクリーンさの欠如**: 開発者が常にクリーンなビルド環境を期待する中で、このような重複は望ましくありませんでした。

このコミットは、これらの問題を解決するために、`go install` が実行された際に、ソースディレクトリに存在する `go build` によって生成されたバイナリを自動的に削除するようになったことをドキュメントに明記するものです。これにより、ユーザーは `go install` を実行すれば、常に `$GOPATH/bin` にある最新のバイナリが使用されることを期待できるようになり、ビルド環境がよりクリーンに保たれるようになりました。

コミットメッセージには `Fixes #12288` と記載されていますが、Web検索ではこの番号のIssueがGo modulesに関する別のトピックを指しているようです。しかし、コミット内容と差分から判断すると、このIssueは `go install` と `go build` のバイナリ重複に関する問題であったと推測されます。

## 前提知識の解説

この変更を理解するためには、Goの基本的なビルドコマンドとそのエコシステムに関する知識が必要です。

### Goのワークスペースと環境変数

*   **`GOPATH`**: Go 1.11以前のバージョンでは、Goのプロジェクトは通常 `$GOPATH` と呼ばれるワークスペース内で管理されていました。ソースコード、コンパイル済みパッケージ、およびインストールされたバイナリがこのパスの下に配置されました。`$GOPATH` は通常、`src`、`pkg`、`bin` の3つのサブディレクトリを持ちます。
    *   `$GOPATH/src`: ソースコードが配置される場所。
    *   `$GOPATH/pkg`: コンパイル済みのパッケージアーカイブが配置される場所。
    *   `$GOPATH/bin`: `go install` によって生成された実行可能バイナリが配置される場所。
*   **`GOBIN`**: `go install` コマンドがバイナリをインストールするディレクトリを明示的に指定するための環境変数です。設定されていない場合、デフォルトで `$GOPATH/bin` が使用されます。
*   **Go Modules**: Go 1.11で導入され、Go 1.13でデフォルトとなったモジュールシステムは、`GOPATH` の制約から解放され、プロジェクトを任意のディレクトリに配置できるようになりました。しかし、`go build` や `go install` の基本的な挙動（特にバイナリの生成場所）は、モジュールモードでも同様の概念が適用されます。

### `go build` コマンド

`go build` はGoのソースファイルをコンパイルして実行可能バイナリを生成するコマンドです。

*   **基本的な挙動**: 引数なしで実行された場合、カレントディレクトリのパッケージをコンパイルし、そのパッケージ名（またはディレクトリ名）と同じ名前の実行可能ファイルをカレントディレクトリに生成します。
*   **出力パスの指定**: `-o` フラグを使用して、出力バイナリのパスと名前を明示的に指定できます（例: `go build -o myapp`）。
*   **目的**: 主に開発中にプログラムをコンパイルしてテストしたり、特定のディレクトリにバイナリを生成したりするために使用されます。

### `go install` コマンド

`go install` はGoのソースファイルをコンパイルし、生成された実行可能バイナリを標準のインストール場所（`$GOPATH/bin` または `$GOBIN`）に配置するコマンドです。

*   **基本的な挙動**: `go build` と同様にコンパイルを行いますが、生成されたバイナリはカレントディレクトリではなく、システム全体のパスが通っている可能性のある `$GOPATH/bin` または `$GOBIN` に配置されます。
*   **目的**: 主にプログラムをシステムにインストールし、どこからでも実行できるようにするために使用されます。これにより、`PATH` 環境変数に `$GOPATH/bin` が含まれていれば、コマンド名を直接入力してプログラムを実行できます。
*   **パッケージのキャッシュ**: `go install` は、コンパイル済みのパッケージを `$GOPATH/pkg` にキャッシュする機能も持っており、これにより後続のビルドが高速化されることがあります。

### Go 1.5 リリース

Go 1.5は、Go言語にとって非常に重要なリリースでした。このリリースでは、GoコンパイラとランタイムがGo自身で書かれるようになり（セルフホスティング）、ガベージコレクタのレイテンシが大幅に改善されるなど、多くの重要な変更が導入されました。このコミットは、Go 1.5のリリース後に発見された問題に対するパッチリリースであるGo 1.5.1に含まれるドキュメントの更新です。

## 技術的詳細

このコミット自体はコードの動作を変更するものではなく、Go 1.5のリリースノート (`doc/go1.5.html`) に、`go install` コマンドの新しい挙動に関する説明を追加するものです。しかし、このドキュメントの追加が示唆する `go install` の内部的な変更は、Goのビルドシステムにおける重要な改善を意味します。

### `go install` の変更点（ドキュメントが示す内容）

Go 1.5.1以降の `go install` コマンドは、以下の新しいロジックを含むようになりました。

1.  **コンパイルとバイナリ生成**: 指定されたGoパッケージのソースコードをコンパイルし、実行可能バイナリを生成します。
2.  **ソースディレクトリ内のバイナリ検出**: コンパイル対象のパッケージのソースディレクトリ内に、`go build` によって以前に生成された可能性のある同名の実行可能バイナリが存在するかどうかを検出します。
3.  **既存バイナリの削除**: もしソースディレクトリ内に既存のバイナリが検出された場合、`go install` はそのバイナリを自動的に削除します。
4.  **新しいバイナリのインストール**: 最後に、新しく生成されたバイナリを `$GOPATH/bin` または `$GOBIN` にインストールします。

この変更により、開発者は `go build` で一時的にバイナリを作成した後、`go install` で正式にインストールする際に、ソースディレクトリに残る古いバイナリについて心配する必要がなくなりました。`go install` がクリーンアップの責任を負うことで、ビルドプロセスがより堅牢で予測可能になります。

### この変更の意義

*   **一貫性の向上**: `go install` が常に「公式」なバイナリを管理し、他の場所にある潜在的に古いバイナリを排除することで、ビルドシステム全体の一貫性が向上します。
*   **ユーザーエクスペリエンスの改善**: 開発者が手動でソースディレクトリのバイナリを削除する手間が省け、混乱が減少します。特に、Goに不慣れなユーザーにとっては、この自動クリーンアップは非常に役立ちます。
*   **デバッグの簡素化**: 意図しない古いバイナリが実行されることによるデバッグの困難さが解消されます。

このドキュメントの追加は、この重要な挙動変更をユーザーに明確に伝えるためのものであり、Goツールの使いやすさと信頼性を高めるための継続的な取り組みの一環です。

## コアとなるコードの解説

追加されたHTMLスニペットは、Go 1.5のリリースノートの「ツール」セクションに新しいリストアイテム (`<li>`) を追加しています。

```html
<li>
The <code>install</code> subcommand now removes the
binary created by the <code>build</code> subcommand
in the source directory, if present,
to avoid problems having two binaries present in the tree.
</li>
```

このテキストは、以下の重要な情報をユーザーに伝えています。

*   **対象コマンド**: `install` サブコマンド (`go install`)。
*   **新しい挙動**: `build` サブコマンド (`go build`) によってソースディレクトリに作成されたバイナリを削除するようになった。
*   **条件**: ソースディレクトリにバイナリが存在する場合のみ。
*   **理由**: ツリー内に2つのバイナリが存在することによる問題を避けるため。

この簡潔な説明により、Go 1.5.1以降の `go install` の挙動が明確になり、開発者がビルドプロセスをより正確に理解し、予期せぬ問題に遭遇するのを防ぐことができます。これは、ツールの変更点をユーザーに適切に伝えるための、ドキュメンテーションの重要な役割を示しています。

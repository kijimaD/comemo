## 変更の背景

Goのプロファイリングツール`pprof`は、プログラムのパフォーマンスボトルネックを特定するために非常に強力なツールです。しかし、特定のシナリオ、特にGoランタイムのスケジューラ（`g0`ゴルーチン）がユーザーゴルーチン（`mp->curg`）のコンテキストで実行されている際にプロファイラが割り込むと、生成されるスタックトレースが不正確になるという問題がありました。

具体的には、プロファイラがサンプリングを行う際、プログラムカウンタ（`pc`）とスタックポインタ（`sp`）は、割り込みが発生した時点のCPUの状態を指します。もしこの時、CPUが`g0`ゴルーチン（ランタイムの内部処理を行うゴルーチン）のコンテキストで動作しており、かつその`g0`がユーザーゴルーチンのために何らかの処理を行っていた場合、プロファイルには`g0`のスタックトレースが記録されてしまい、実際にCPU時間を使っていたユーザーゴルーチンの情報が欠落するか、不正確になる可能性がありました。

Issue #8942（公開されているGoのissueトラッカーでは直接見つかりませんが、このコミットメッセージから存在が示唆される内部的な課題）は、この`pprof`のスタックトレースの精度に関する問題を扱っていたと考えられます。このコミットは、その問題に対する完全な解決ではないものの、プロファイルがより「有用」になるように、この特定のケースでのスタックトレースの収集方法を改善することを目的としています。これにより、ユーザーはより正確なパフォーマンスデータを取得できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とプロファイリングの基本を理解しておく必要があります。

1.  **Goランタイム (Go Runtime):** Goプログラムの実行を管理する部分です。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、システムコールなど、低レベルの操作を処理します。
2.  **ゴルーチン (Goroutine):** Goにおける軽量な実行スレッドです。Goランタイムによって管理され、OSのスレッドに多重化されて実行されます。
3.  **M (Machine) と P (Processor) と G (Goroutine):** Goスケジューラの主要な要素です。
    *   **G (Goroutine):** 実行されるコードの単位。
    *   **M (Machine):** OSのスレッドを表します。MはGを実行します。
    *   **P (Processor):** MがGを実行するために必要な論理プロセッサです。PはMにGを供給し、MはPにアタッチされてGを実行します。
4.  **`g0` ゴルーチン:** 各M（OSスレッド）には、特別なシステムゴルーチンである`g0`が関連付けられています。`g0`は、Goランタイムの内部処理（スケジューリング、スタックの拡張/縮小、システムコールへの移行など）を実行するために使用されます。ユーザーコードは`g0`上で直接実行されることはありませんが、ユーザーゴルーチンがシステムコールを行う際など、`g0`のスタックに切り替わることがあります。
5.  **`mp->curg`:** 現在M（`mp`）上で実行されているユーザーゴルーチンを指します。`g0`がランタイム処理を実行している間でも、その`g0`がどのユーザーゴルーチンのために動作しているかを示す場合があります。
6.  **`pprof`:** Goに組み込まれているプロファイリングツールです。CPU使用率、メモリ割り当て、ブロックプロファイル、ミューテックス競合など、様々な種類のプロファイルを収集し、可視化することができます。CPUプロファイリングは、一定の間隔でプログラムの実行をサンプリングし、その時点のスタックトレースを記録することで行われます。
7.  **スタックトレース (Stack Trace):** プログラムの実行中に、ある時点での関数呼び出しの連鎖（コールスタック）を示します。プロファイリングにおいては、CPUがどこで時間を使っているかを特定するために不可欠な情報です。
8.  **プログラムカウンタ (PC) と スタックポインタ (SP):**
    *   **PC (Program Counter):** 現在実行中の命令のアドレスを指すレジスタ。
    *   **SP (Stack Pointer):** 現在のスタックフレームの最上位（または最下位）のアドレスを指すレジスタ。スタックトレースを生成する際には、これらのレジスタの値が起点となります。

## 技術的詳細

このコミットの技術的な核心は、`runtime·sigprof`関数におけるスタックトレース収集ロジックの改善にあります。`runtime·sigprof`は、プロファイリングシグナル（通常は`SIGPROF`）がGoプロセスに送信されたときに呼び出される関数で、CPUプロファイリングのサンプリングポイントとなります。

変更前は、`runtime·sigprof`が呼び出された際、`pc`と`sp`はシグナル発生時のCPUの状態をそのまま反映していました。これが`g0`ゴルーチンのコンテキストであった場合、`runtime·gentraceback`（スタックトレースを生成する関数）は`g0`のスタックをトレースしてしまい、ユーザーゴルーチンの実行パスがプロファイルに正確に反映されない問題がありました。

このコミットでは、以下のロジックが追加されています。

1.  `off`という新しい変数が導入され、スタックトレースのオフセットを管理します。
2.  `if(gp == mp->g0 && mp->curg != nil)`という条件が追加されました。これは、現在プロファイリングされているゴルーチン（`gp`）が`g0`であり、かつそのM（`mp`）に現在実行中のユーザーゴルーチン（`mp->curg`）が存在する場合を検出します。
3.  この条件が真の場合、以下の処理が行われます。
    *   `stk[0] = (uintptr)pc;`：`g0`の`pc`（シグナル発生時の`pc`）をスタックトレースバッファの最初の要素に保存します。これにより、`g0`のコンテキストからユーザーゴルーチンへの遷移がプロファイルに記録されるようになります。
    *   `off = 1;`：スタックトレースの開始オフセットを1に設定します。これは、`stk[0]`に`g0`の`pc`が格納されたため、実際のユーザーゴルーチンのスタックトレースは`stk[1]`から開始する必要があることを示します。
    *   `gp = mp->curg;`：プロファイリング対象のゴルーチンを`g0`から`mp->curg`（現在のユーザーゴルーチン）に切り替えます。
    *   `pc = (uint8*)gp->sched.pc;`：ユーザーゴルーチンのスケジューリングされた`pc`に更新します。
    *   `sp = (uint8*)gp->sched.sp;`：ユーザーゴルーチンのスケジューリングされた`sp`に更新します。
    *   `lr = 0;`：リンクレジスタ（`lr`）を0に設定します。これは、ユーザーゴルーチンのコンテキストに切り替えたため、`lr`が直接利用できないか、関連性が低いことを示唆している可能性があります。
    *   `traceback = true;`：トレースバックを続行することを保証します。
4.  最後に、`runtime·gentraceback`の呼び出しが変更され、`stk+off`と`nelem(stk)-off`が引数として渡されます。これにより、`gentraceback`は`off`で指定されたオフセットからスタックトレースの収集を開始し、バッファの残りの部分を使用します。

この変更により、`g0`がユーザーゴルーチンのために動作している間にプロファイラが割り込んでも、生成されるプロファイルはユーザーゴルーチンの実際の実行パスをより正確に反映するようになります。結果として、`pprof`の出力がより意味のあるものとなり、開発者はパフォーマンスの問題をより効果的に診断できるようになります。

## コアとなるコードの解説

-   **`int32 n, off;`**: `runtime·sigprof`関数のローカル変数に`off`が追加されました。この`off`は、スタックトレースを記録するバッファ`stk`の開始オフセットを制御するために使用されます。
-   **新しい条件ブロック**:
    ```c
    off = 0;
    if(gp == mp->g0 && mp->curg != nil) {
        stk[0] = (uintptr)pc;
        off = 1;
        gp = mp->curg;
        pc = (uint8*)gp->sched.pc;
        sp = (uint8*)gp->sched.sp;
        lr = 0;
        traceback = true;
    }
    ```
    このブロックは、プロファイリングシグナルが`g0`ゴルーチン（`gp == mp->g0`）で発生し、かつそのM（OSスレッド）に現在実行中のユーザーゴルーチン（`mp->curg != nil`）が存在する場合に実行されます。
    *   `stk[0] = (uintptr)pc;`：シグナル発生時の`g0`のプログラムカウンタ（`pc`）をスタックトレースバッファの最初の位置に保存します。これにより、`g0`からユーザーゴルーチンへの遷移がプロファイルに明示的に示されます。
    *   `off = 1;`：`stk[0]`に`g0`の`pc`が格納されたため、実際のユーザーゴルーチンのスタックトレースは`stk`のインデックス1から開始するようにオフセットを設定します。
    *   `gp = mp->curg;`、`pc = (uint8*)gp->sched.pc;`、`sp = (uint8*)gp->sched.sp;`：プロファイリングのコンテキストを`g0`から、現在実行中のユーザーゴルーチン`mp->curg`のコンテキストに切り替えます。これにより、`runtime·gentraceback`はユーザーゴルーチンのスタックをトレースするようになります。
    *   `lr = 0;`：リンクレジスタをクリアします。これは、コンテキスト切り替え後の`lr`の有効性が保証されないため、安全のために行われます。
    *   `traceback = true;`：このケースでは必ずトレースバックを行うように設定します。
-   **`runtime·gentraceback`の呼び出し変更**:
    ```c
    n = runtime·gentraceback((uintptr)pc, (uintptr)sp, (uintptr)lr, gp, 0, stk+off, nelem(stk)-off, nil, nil, false);
    ```
    `runtime·gentraceback`関数は、スタックトレースを生成するGoランタイムの内部関数です。変更前は`stk`と`nelem(stk)`が渡されていましたが、変更後は`stk+off`と`nelem(stk)-off`が渡されます。
    *   `stk+off`：スタックトレースの書き込みを開始するメモリ位置を`off`分ずらします。これにより、`stk[0]`に`g0`の`pc`が既に格納されている場合でも、ユーザーゴルーチンのスタックトレースが正しく`stk[1]`以降に書き込まれます。
    *   `nelem(stk)-off`：スタックトレースバッファの残りの容量を`off`分減らします。これにより、バッファオーバーフローを防ぎます。

この一連の変更により、`pprof`が`g0`ゴルーチンをサンプリングした場合でも、その`g0`がどのユーザーゴルーチンのために動作していたかを正確に特定し、そのユーザーゴルーチンのスタックトレースをプロファイルに含めることができるようになります。これにより、プロファイルの「有用性」が大幅に向上し、開発者はより正確なパフォーマンス分析を行うことが可能になります。

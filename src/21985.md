# [インデックス 21985] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/asm`）におけるx86アーキテクチャ向けのビルド問題を修正するものです。特に、ARMアーキテクチャ関連の作業によって発生した、複雑なアドレッシングモードの誤った処理が原因でした。

## 元コミット内容

このコミットは、`cmd/asm`（Goアセンブラ）がx86アーキテクチャ向けにビルドされる際に発生していた問題を修正します。具体的には、ARMアーキテクチャ関連の変更が原因で、`masks<>(SB)(CX*8)`のような複雑なアドレッシングモードの処理が誤っていたことが判明しました。この修正は、`registerIndirect`関数が常に開き括弧（`(`）で始まる入力で呼び出されるように、処理フローを調整することで行われました。これにより、`linux-arm`、`linux-386`、`linux-amd64`を含む複数のアーキテクチャでのビルドが正常に完了するようになりました。

## 変更の背景

Go言語はクロスプラットフォーム開発を強く意識しており、様々なCPUアーキテクチャをサポートしています。`cmd/asm`はGoのアセンブリコードを機械語に変換するツールであり、各アーキテクチャ固有のアドレッシングモードや命令セットを正確に解釈・処理する必要があります。

このコミットの背景には、ARMアーキテクチャ向けのサポート強化作業がありました。Goのツールチェイン開発では、新しいアーキテクチャのサポートを追加する際、既存のコードベースに意図しない副作用が生じることがあります。今回のケースでは、ARM向けのアドレッシングモードの処理ロジックが変更された結果、x86アーキテクチャにおける特定の複雑なアドレッシングモード（`masks<>(SB)(CX*8)`）の解釈に問題が生じました。これは、アセンブラのパーサーが、アドレッシングモードの開始点（開き括弧）の処理を誤ったために発生したと考えられます。

結果として、x86アーキテクチャ（特に`linux-386`と`linux-amd64`）でのビルドが失敗する、または正しくないコードが生成される可能性がありました。この問題を解決し、Goツールチェインの安定性とクロスプラットフォーム互換性を維持することが、このコミットの目的です。

## 前提知識の解説

### Goアセンブラ (`cmd/asm`)

Go言語は、パフォーマンスが要求される低レベルな処理のために、Goアセンブラ（`cmd/asm`）を用いたアセンブリコードの記述をサポートしています。Goのアセンブリは、一般的なアセンブリ言語とは異なり、Go独自の擬似命令やシンタックスシュガーを含んでいます。これは、異なるアーキテクチャ間での移植性を高めるための工夫です。`cmd/asm`は、このGoアセンブリコードを各ターゲットアーキテクチャの機械語に変換する役割を担います。

### アドレッシングモード

アドレッシングモードとは、CPUがメモリ上のデータにアクセスする際に、そのデータの物理アドレスをどのように計算するかを決定する方式のことです。様々なアドレッシングモードが存在し、それぞれが異なる柔軟性と効率性を提供します。

*   **レジスタ間接アドレッシング (Register Indirect Addressing)**: レジスタに格納されている値をアドレスとして使用する方式です。例えば、`(R1)`はR1レジスタが指すメモリ位置を意味します。
*   **ベースレジスタ + インデックスレジスタ * スケール + ディスプレイスメント**: 複雑なアドレッシングモードの一例で、`ディスプレイスメント(ベースレジスタ, インデックスレジスタ*スケール)`のような形式を取ります。これは、`ベースレジスタ`の値に`インデックスレジスタ`の値を`スケール`倍したものを加算し、さらに`ディスプレイスメント`を加算して最終的なアドレスを計算します。

### `SB` (Static Base)

Goアセンブリにおける`SB`は「Static Base」の略で、静的データやグローバルシンボルの基準アドレスを示す擬似レジスタです。これは物理的なCPUレジスタではなく、Goリンカがプログラムのロード時に解決する仮想的なベースアドレスです。`シンボル名<>(SB)`のような形式で使われ、`SB`からのオフセットでグローバル変数や関数を参照します。`<>`（または`·`）は、シンボルが現在のソースファイルにプライベートであることを示します。

### `CX` レジスタ (x86)

x86アーキテクチャにおいて、`CX`レジスタは汎用レジスタの一つです。歴史的にはカウンタとして使われることが多かったですが、現代では他の汎用レジスタと同様に様々な目的で使用されます。

### `(CX*8)`

これは、`CX`レジスタの値に8を乗算したものをオフセットとして使用することを示します。8倍のスケールは、64ビットシステムにおいてポインタや`float64`型など、8バイトの要素を持つ配列やスライスにアクセスする際によく用いられます。

### `parse.go`

`src/cmd/asm/internal/asm/parse.go`ファイルは、Goアセンブラのパーサーの中核をなす部分です。このファイルは、アセンブリコードの文字列を解析し、抽象構文木（AST）のような内部表現に変換する役割を担っています。アドレッシングモードの解釈やレジスタの識別など、アセンブリコードの文法的な正しさを検証し、意味を理解するためのロジックが含まれています。

## 技術的詳細

このコミットの核心は、`cmd/asm`のパーサーが、複雑なアドレッシングモードを処理する際の「状態管理」の誤りにあります。特に、`registerIndirect`関数が呼び出される時点での入力ストリームの状態が問題でした。

元々の実装では、`registerIndirect`関数が呼び出される前に、アドレッシングモードの開始を示す開き括弧（`(`）が既に消費されていることを前提としていました。しかし、ARM関連の作業で導入された変更により、この前提が崩れ、特定のケース（`masks<>(SB)(CX*8)`のような形式）で開き括弧が消費されずに`registerIndirect`が呼び出される状況が発生しました。

これにより、パーサーは期待する入力形式と異なる状態で処理を開始し、結果としてアドレッシングモードを正しく解釈できず、ビルドエラーや不正なコード生成につながっていました。

修正の戦略は、「`registerIndirect`関数が常に開き括弧で始まる入力で呼び出される」という一貫した状態を保証することです。これは、`parse.go`内の`operand`関数において、`registerIndirect`を呼び出す直前に開き括弧を明示的に消費する（`p.get('(')`）ように変更することで実現されました。また、`operand`関数内で`haveConstant`が`false`の場合（つまり、定数ではなくレジスタ間接アドレッシングの場合）に、`p.back()`で開き括弧をストリームに戻す処理が追加されています。これにより、`registerIndirect`が常に開き括弧から処理を開始できるようになります。

この変更により、パーサーの内部状態がより堅牢になり、異なるアーキテクチャの複雑なアドレッシングモードが混在する状況でも、一貫した解析が可能になりました。

## コアとなるコードの解説

1.  **`operand`関数内の変更 (行 313-316):**
    ```go
    		if !haveConstant {
    			p.back() // Put back the '('.
    		}
    ```
    `operand`関数は、アセンブリ命令のオペランドを解析する役割を担っています。この部分では、オペランドが定数ではない場合（つまり、レジスタ間接アドレッシングの可能性がある場合）、以前に`p.next()`で消費された開き括弧（`(`）を`p.back()`を使って入力ストリームに戻しています。これにより、後続の`registerIndirect`関数が常に開き括弧から処理を開始できる状態が保証されます。

2.  **`operand`関数内の変更 (行 355-358):**
    ```diff
    -		p.get('(')
    	}
    
    -	// Register indirection: (reg) or (index*scale). We have consumed the opening paren.
    +	// Register indirection: (reg) or (index*scale). We are on the opening paren.
    ```
    以前は`registerIndirect`を呼び出す前に`p.get('(')`で開き括弧を明示的に消費していましたが、この行が削除されました。これは、上記の変更（行 313-316）により、`registerIndirect`が呼び出される時点で既に開き括弧が入力ストリームの先頭にあることが保証されるためです。コメントも「We have consumed the opening paren.」から「We are on the opening paren.」に変更され、現在の状態を正確に反映しています。

3.  **`registerIndirect`関数内の変更 (行 535-538):**
    ```diff
    // The opening parenthesis has already been consumed.
    // We are sitting on the opening parenthesis.
    func (p *Parser) registerIndirect(a *obj.Addr, prefix rune) {
    +	p.get('(')
    	tok := p.next()
    ```
    `registerIndirect`関数は、レジスタ間接アドレッシングモード（例: `(reg)`、`(index*scale)`）を解析します。この関数が呼び出された時点で、入力ストリームの先頭に開き括弧があることが保証されるようになったため、ここで改めて`p.get('(')`を呼び出して開き括弧を消費しています。これにより、`registerIndirect`関数自身の内部ロジックが、常に開き括弧の直後からオペランドの解析を開始できるという、より明確で堅牢な状態になります。

4.  **`setPseudoRegister`関数内のエラーメッセージの改善 (行 505-507):**
    ```diff
    	if addr.Reg != 0 {
    -		p.errorf("internal error: reg already set in psuedo")
    +		p.errorf("internal error: reg %s already set in pseudo", name)
    	}
    ```
    これは直接的なバグ修正ではありませんが、デバッグを容易にするための改善です。`setPseudoRegister`関数内で内部エラーが発生した場合に、どのレジスタが問題を引き起こしたかをエラーメッセージに含めることで、より詳細な情報が得られるようになります。

これらの変更は、アセンブラのパーサーにおける状態管理をより厳密にし、特に複雑なアドレッシングモードの解析において、異なるアーキテクチャ間での互換性と正確性を向上させることを目的としています。

## 元コミット内容

このコミットは、`regexp` パッケージにおいて、正規表現の内部表現（プログラム）が長すぎる場合に、バックトラッカーの使用をスキップするように変更します。具体的には、`maxBacktrackLen` 関数が、プログラムの命令数 (`len(prog.Inst)`) が `maxBacktrackProg` という閾値を超えた場合に `0` を返すように修正されました。これにより、`nil` の `bitstate` に対してバックトラックを試みることを防ぎます。この変更は、Go issue #10319 を修正するものです。

## 変更の背景

Go言語の `regexp` パッケージは、GoogleのRE2エンジンをベースにしており、線形時間でのマッチングを保証するように設計されています。これは、一般的な正規表現エンジンで問題となる「壊滅的バックトラッキング（catastrophic backtracking）」を防ぐための重要な設計思想です。RE2は、非決定性有限オートマトン（NFA）を決定性有限オートマトン（DFA）のようにシミュレートすることで、この線形時間性能を実現しています。

しかし、`regexp` パッケージの内部には、特定の最適化のために「バックトラッカー」と呼ばれる限定的なメカニズムが存在します。これは、一般的な正規表現エンジンにおける指数関数的な時間計算量につながるようなバックトラッキングとは異なり、より効率的なマッチングのために、特定の条件下（特に正規表現プログラムが短い場合）で利用されるものです。このバックトラッカーは、`bitstate` と呼ばれるビットセットを用いた状態管理によって、効率的に動作します。

このコミットが行われる前は、正規表現のプログラムが `maxBacktrackProg`（デフォルト値は500）という閾値を超えて長くなった場合、`newBitState` 関数はバックトラッカーを使用しないことを示すために `nil` の `bitstate` を返していました。しかし、`maxBacktrackLen` 関数は、この `nil` の `bitstate` が返される状況でも、バックトラッカーが使用されることを前提とした計算を試みていました。これにより、`nil` ポインタに対する不正なアクセスが発生し、ランタイムパニックやクラッシュにつながる可能性がありました。

このコミットは、このような不正なアクセスを防ぎ、正規表現エンジンが長大な正規表現プログラムに対しても安定して動作するようにするために導入されました。

## 前提知識の解説

*   **正規表現エンジンとバックトラッキング**:
    *   **NFA (Non-deterministic Finite Automaton)**: 非決定性有限オートマトン。複数の状態遷移の可能性を持つ。一般的な正規表現エンジン（Perl互換正規表現など）はNFAベースで、マッチングにバックトラッキング（試行錯誤的にパスを探索し、失敗したら前の分岐点に戻る）を使用します。これにより強力な機能（後方参照など）が実現できますが、特定のパターンと入力に対しては指数関数的な時間計算量となり、「壊滅的バックトラッキング」と呼ばれる性能問題を引き起こす可能性があります。
    *   **DFA (Deterministic Finite Automaton)**: 決定性有限オートマトン。各状態と入力に対して一意の次の状態を持つ。DFAベースのエンジンは線形時間でマッチングを保証しますが、NFAに比べて表現力が劣る場合があります。
    *   **Go `regexp` と RE2**: Goの `regexp` パッケージはGoogleのRE2エンジンを基盤としています。RE2はNFAをDFAのようにシミュレートするハイブリッドアプローチを採用しており、線形時間でのマッチングを保証しつつ、壊滅的バックトラッキングを回避します。そのため、Goの `regexp` は後方参照などの一部の機能はサポートしていません。
*   **`prog.Inst`**: 正規表現は、内部的には一連の命令（インストラクション）からなる「プログラム」として表現されます。`prog.Inst` は、この命令のリストを指します。正規表現の複雑さや長さは、この命令の数 (`len(prog.Inst)`) に比例します。
*   **`bitstate`**: Goの `regexp` パッケージ内部で、限定的なバックトラッキングや最適化のために使用されるデータ構造です。これはビットセットを用いて、オートマトンの現在のアクティブな状態を効率的に追跡します。`nil bitstate` は、この `bitstate` が初期化されていない、または意図的に使用されない場合に `nil` となる状態を指します。
*   **`maxBacktrackProg`**: `src/regexp/backtrack.go` で定義されている内部定数で、デフォルト値は `500` です。これは、バックトラッカーが適用される正規表現プログラムの命令数の上限を定めます。この値を超えるプログラムに対しては、バックトラッカーは使用されません。
*   **`maxBacktrackLen`**: バックトラッカーが使用される場合に、マッチング対象の文字列の最大長を計算する関数です。この関数は、`bitstate` のサイズと `prog.Inst` の長さに基づいて計算を行います。
*   **`newBitState`**: 新しい `bitstate` オブジェクトを生成する関数です。正規表現プログラムが `maxBacktrackProg` を超える長さの場合、この関数はバックトラッカーを使用しないことを示すために `nil` (具体的には `notBacktrack` という `nil` の `bitstate` ポインタ) を返します。

## 技術的詳細

このコミットの核心は、正規表現プログラムの長さ (`len(prog.Inst)`) に応じて、`regexp` パッケージ内の限定的なバックトラッカーの挙動を適切に制御することにあります。

1.  **`shouldBacktrack` 関数の導入**:
    *   このコミットでは、`shouldBacktrack(prog *syntax.Prog) bool` という新しいヘルパー関数が導入されました。
    *   この関数は、`len(prog.Inst) <= maxBacktrackProg` という条件をチェックし、正規表現プログラムがバックトラッカーを使用するのに十分な長さであるかどうかを返します。
    *   これにより、バックトラッカーを使用するかどうかの判断ロジックが一元化され、コードの可読性と保守性が向上しました。

2.  **`maxBacktrackLen` の修正**:
    *   修正前は、`maxBacktrackLen` 関数は常に `prog.Inst` の長さに基づいて計算を行っていました。
    *   修正後は、まず `shouldBacktrack(prog)` を呼び出し、バックトラッカーが使用されないと判断された場合（つまり、プログラムが長すぎる場合）は、即座に `0` を返すようになりました。
    *   これにより、バックトラッカーが使用されない状況で、`nil` の `bitstate` を前提とした計算が試みられることを防ぎます。

3.  **`newBitState` の修正**:
    *   修正前は、`newBitState` 関数内で `len(prog.Inst) > maxBacktrackProg` という条件でバックトラッカーを使用しないかを判断していました。
    *   修正後は、ここでも `shouldBacktrack(prog)` を使用するように変更されました。これにより、`maxBacktrackLen` と同様に、バックトラッカーを使用するかどうかの判断ロジックが統一されました。プログラムが長すぎる場合は、`notBacktrack` (実質的に `nil` の `bitstate` ポインタ) が返されます。

この一連の変更により、正規表現プログラムが `maxBacktrackProg` を超える長さになった場合、`maxBacktrackLen` は `0` を返し、`newBitState` は `nil` の `bitstate` を返すようになります。これにより、`nil` の `bitstate` に対して不正な操作が行われる可能性が完全に排除され、ランタイムパニックが回避されます。

*   **`maxBacktrackProg`**: `src/regexp/backtrack.go` で定義されている内部定数で、デフォルト値は `500` です。これは、バックトラッカーが適用される正規表現プログラムの命令数の上限を定めます。この値を超えるプログラムに対しては、バックトラッカーは使用されません。
*   **`maxBacktrackLen`**: バックトラッカーが使用される場合に、マッチング対象の文字列の最大長を計算する関数です。この関数は、`bitstate` のサイズと `prog.Inst` の長さに基づいて計算を行います。
*   **`newBitState`**: 新しい `bitstate` オブジェクトを生成する関数です。正規表現プログラムが `maxBacktrackProg` を超える長さの場合、この関数はバックトラッカーを使用しないことを示すために `nil` (具体的には `notBacktrack` という `nil` の `bitstate` ポインタ) を返します。

## 技術的詳細

このコミットの核心は、正規表現プログラムの長さ (`len(prog.Inst)`) に応じて、`regexp` パッケージ内の限定的なバックトラッカーの挙動を適切に制御することにあります。

1.  **`shouldBacktrack` 関数の導入**:
    *   このコミットでは、`shouldBacktrack(prog *syntax.Prog) bool` という新しいヘルパー関数が導入されました。
    *   この関数は、`len(prog.Inst) <= maxBacktrackProg` という条件をチェックし、正規表現プログラムがバックトラッカーを使用するのに十分な長さであるかどうかを返します。
    *   これにより、バックトラッカーを使用するかどうかの判断ロジックが一元化され、コードの可読性と保守性が向上しました。

2.  **`maxBacktrackLen` の修正**:
    *   修正前は、`maxBacktrackLen` 関数は常に `prog.Inst` の長さに基づいて計算を行っていました。
    *   修正後は、まず `shouldBacktrack(prog)` を呼び出し、バックトラッカーが使用されないと判断された場合（つまり、プログラムが長すぎる場合）は、即座に `0` を返すようになりました。
    *   これにより、バックトラッカーが使用されない状況で、`nil` の `bitstate` を前提とした計算が試みられることを防ぎます。

3.  **`newBitState` の修正**:
    *   修正前は、`newBitState` 関数内で `len(prog.Inst) > maxBacktrackProg` という条件でバックトラッカーを使用しないかを判断していました。
    *   修正後は、ここでも `shouldBacktrack(prog)` を使用するように変更されました。これにより、`maxBacktrackLen` と同様に、バックトラッカーを使用するかどうかの判断ロジックが統一されました。プログラムが長すぎる場合は、`notBacktrack` (実質的に `nil` の `bitstate` ポインタ) が返されます。

この一連の変更により、正規表現プログラムが `maxBacktrackProg` を超える長さになった場合、`maxBacktrackLen` は `0` を返し、`newBitState` は `nil` の `bitstate` を返すようになります。これにより、`nil` の `bitstate` に対して不正な操作が行われる可能性が完全に排除され、ランタイムパニックが回避されます。

## コアとなるコードの解説

*   **`src/regexp/backtrack.go`**:
    *   `shouldBacktrack` 関数は、正規表現プログラム `prog` がバックトラッカーを使用するのに適した長さであるか（`maxBacktrackProg` 以下であるか）を判断します。この関数は、バックトラッカーの利用条件をカプセル化し、他の関数での判断ロジックの重複を避けます。
    *   `maxBitStateLen` 関数は、バックトラッカーが使用される場合に、マッチング対象の文字列の最大長を計算します。このコミットでは、`shouldBacktrack(prog)` が `false`（つまりプログラムが長すぎる）の場合、即座に `0` を返すように変更されました。これにより、バックトラッカーが使用されない状況で、`nil` の `bitstate` を前提とした計算が試みられることを防ぎます。
    *   `newBitState` 関数は、新しい `bitstate` オブジェクトを生成します。ここでも `shouldBacktrack(prog)` を用いて、プログラムが長すぎる場合は `notBacktrack`（`nil` の `bitstate` ポインタ）を返すように変更されました。これにより、バックトラッカーが不要な場合に `bitstate` の生成をスキップし、`nil` ポインタの問題を回避します。

*   **`src/regexp/exec_test.go`**:
    *   `TestProgramTooLongForBacktrack` という新しいテストケースが追加されました。このテストは、非常に長い正規表現（`maxBacktrackProg` を超える命令数を持つと想定される）をコンパイルし、その正規表現が正しく文字列にマッチするかどうかを検証します。
    *   このテストの目的は、バックトラッカーがスキップされるような長大な正規表現に対しても、`regexp` パッケージが期待通りに動作することを確認することです。これにより、今回の修正が意図した通りに機能し、長大な正規表現の処理における安定性が確保されていることが保証されます。

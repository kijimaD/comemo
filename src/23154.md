## 変更の背景

Go言語のランタイムは、並行ガベージコレクション（GC）を採用しており、アプリケーションの実行と並行してGCが動作することで、Stop-The-World (STW) ポーズを最小限に抑えています。この並行GCの正確性と効率性を保つ上で、ライトバリアは極めて重要な役割を果たします。

以前のGoランタイムでは、ライトバリアが必要かどうかを判断するために `needwb()` という関数が使用されていました。この関数は、GCの現在のフェーズ（`_GCmark` や `_GCmarktermination`）やシャドウメモリの有効状態（`mheap_.shadow_enabled`）など、複数の条件を評価していました。しかし、このような複数の条件分岐を含む関数呼び出しは、コンパイラによるインライン化（関数呼び出しをその本体のコードで直接置き換える最適化）が困難でした。

ライトバリアは、ポインタの書き込みが発生するたびに実行される可能性があるため、そのチェックのオーバーヘッドはアプリケーション全体のパフォーマンスに大きな影響を与えます。`needwb()` のような複雑なチェックがインライン化されない場合、各ライトバリアの呼び出しには関数呼び出しのコストが伴い、これが積み重なることでパフォーマンスのボトルネックとなる可能性がありました。

このコミットの背景にあるのは、この `needwb()` によるオーバーヘッドを削減し、ライトバリアのチェックをより高速化することです。具体的には、チェックを単一のロードと比較命令に簡素化することで、コンパイラがライトバリアのチェックコードを呼び出し元に容易にインライン化できるようにし、全体的な実行効率を向上させることを目指しています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語は、自動メモリ管理のためにガベージコレクション（GC）を採用しています。GoのGCは、主に「並行マーク＆スイープ」アルゴリズムに基づいており、アプリケーションの実行（ミューテーター）と並行してGCが動作するように設計されています。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、高いスループットと低いレイテンシを実現しています。

GCの主なフェーズは以下の通りです。
1.  **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定します。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、メモリを再利用可能にします。

並行GCでは、マークフェーズの一部がアプリケーションの実行と並行して行われます。この並行性により、GCが動作している間もアプリケーションはメモリを読み書きできますが、同時にメモリの一貫性を保つための特別なメカニズムが必要になります。

### 三色マーキング (Tri-color marking)

GoのGCは、オブジェクトを以下の三色で分類する「三色マーキング」という概念を使用します。

*   **白 (White)**: GCによってまだ訪問されていないオブジェクト。到達可能であれば灰色または黒に変わりますが、最終的に白のまま残ったオブジェクトは到達不能とみなされ、スイープの対象となります。
*   **灰 (Gray)**: GCによって到達可能とマークされたが、そのオブジェクトが参照する他のオブジェクト（子オブジェクト）がまだスキャンされていない状態のオブジェクト。GCワーカーは灰色のオブジェクトをスキャンし、その子を灰色にマークしてワークリストに追加し、自身は黒に遷移します。
*   **黒 (Black)**: GCによって到達可能とマークされ、かつそのオブジェクトが参照する全ての子オブジェクトもスキャン済みである状態のオブジェクト。黒オブジェクトは、GCサイクル中に白オブジェクトを指してはならないという「三色不変条件」があります。

### ライトバリア (Write Barrier)

並行GCにおいて、アプリケーション（ミューテーター）がポインタを書き換える際に、GCの正確性を保証するために実行される特別な処理がライトバリアです。ライトバリアの主な目的は、「黒オブジェクトが白オブジェクトを指してはならない」という三色不変条件を維持することです。

もしライトバリアがない場合、GCがオブジェクトをスキャンしている最中にアプリケーションがポインタを書き換えると、以下のような問題が発生する可能性があります。
1.  GCが既に黒とマークしたオブジェクトが、まだ白とマークされている新しいオブジェクトを指すようになる。
2.  GCがその新しいオブジェクトをスキャンする前に、そのオブジェクトへの唯一の参照が失われ、到達可能なはずのオブジェクトが誤って解放されてしまう（ポインタの消失問題）。

ライトバリアは、このような問題を回避するために、ポインタの書き込み操作を監視し、特定の条件が満たされた場合に介入します。GoのGCでは、主に「挿入ライトバリア」と「削除ライトバリア」のハイブリッド方式が採用されています。ポインタの書き込みが発生した際、ライトバリアは書き込まれるオブジェクト（`src`）が白であれば、それを灰色にマークしてGCのワークリストに追加します。これにより、GCはそのオブジェクトを確実にスキャンし、到達可能であれば解放されないようにします。

### インライン化 (Inlining)

インライン化は、コンパイラ最適化の一種です。関数呼び出しが発生する箇所で、その関数の本体のコードを直接埋め込むことで、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数のプッシュ、リターンアドレスの保存など）を削減します。インライン化は、特に小さな関数や頻繁に呼び出される関数において、実行速度を大幅に向上させる効果があります。また、インライン化によって関数本体のコードが呼び出し元に展開されることで、コンパイラはより広範なコンテキストで最適化を適用できるようになります。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムがライトバリアを有効にする必要があるかどうかを判断するメカニズムを、より効率的なものに置き換えることです。

### `needwb()` の問題点

以前のGoランタイムでは、ライトバリアの有効性を判断するために `needwb()` という関数が使用されていました。この関数は以下のようなロジックを持っていました（コミット前のコードから推測される）：

```go
func needwb() bool {
    return gcphase == _GCmark || gcphase == _GCmarktermination || mheap_.shadow_enabled
}
```

この関数は、`gcphase`（GCの現在のフェーズ）が `_GCmark` または `_GCmarktermination` であるか、あるいは `mheap_.shadow_enabled`（シャドウメモリが有効かどうか）であるかをチェックしていました。
`needwb()` が抱えていた問題点は以下の通りです。
*   **関数呼び出しのオーバーヘッド**: `needwb()` は関数呼び出しであるため、そのたびにスタックフレームのセットアップなどのオーバーヘッドが発生します。
*   **複雑な条件分岐**: 複数の `||`（OR）条件を含むため、コンパイラがこの関数を呼び出し元にインライン化して最適化することが困難でした。インライン化されない場合、ライトバリアが必要かどうかを判断するたびに、この関数呼び出しのコストが毎回発生していました。

### `writeBarrierEnabled` の導入と `setGCPhase`

このコミットでは、`needwb()` 関数を廃止し、代わりに `writeBarrierEnabled` というグローバルな `bool` 変数を導入しました。この変数は、ライトバリアが現在有効であるべきかどうかを直接示します。

さらに、`gcphase` の変更を管理し、それに伴って `writeBarrierEnabled` の状態を更新するためのヘルパー関数 `setGCPhase(x uint32)` が導入されました。この関数は以下のロジックで `writeBarrierEnabled` を設定します。

```go
//go:nosplit
func setGCPhase(x uint32) {
    atomicstore(&gcphase, x) // gcphaseをアトミックに更新
    writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination || mheap_.shadow_enabled
}
```

この変更により、ライトバリアが必要かどうかを判断する箇所では、`needwb()` 関数を呼び出す代わりに、単に `writeBarrierEnabled` 変数の値を参照するだけでよくなりました。

### 最適化の効果

`writeBarrierEnabled` は単一の `bool` 変数であるため、その値をチェックする操作は、CPUのレジスタから値をロードし、それを比較するだけの非常に単純な命令にコンパイルされます。このような単純な操作は、コンパイラによって非常に容易にインライン化されます。

インライン化されることで、ライトバリアのチェックは関数呼び出しのオーバーヘッドなしに、直接呼び出し元のコードに埋め込まれます。これにより、各ライトバリア操作の実行速度が向上し、特にポインタの書き込みが頻繁に発生するようなアプリケーションにおいて、全体的なパフォーマンスの改善が期待できます。

コミットメッセージには、この変更によるベンチマーク結果が示されています。いくつかのベンチマークでパフォーマンスの向上が見られます。

## コアとなるコードの解説

このコミットの核心は、ライトバリアの有効/無効を判断するロジックを、動的な関数呼び出しから静的なブール変数への参照に置き換えることで、実行時のオーバーヘッドを最小限に抑える点にあります。

以前の `needwb()` 関数は、GCの現在のフェーズ（`_GCmark` や `_GCmarktermination`）とシャドウメモリの有効状態という複数の条件を評価していました。この評価は、関数呼び出しのオーバーヘッドと、複数の条件分岐によるコンパイラのインライン化の妨げとなっていました。

新しいアプローチでは、`writeBarrierEnabled` という単一のグローバルブール変数が導入されます。この変数は、ライトバリアが必要なGCフェーズへの移行時、またはシャドウメモリが有効になった際に、`setGCPhase` 関数によって適切に `true` または `false` に更新されます。

`setGCPhase` 関数は、`gcphase` の値をアトミックに更新した後、その新しい `gcphase` の値と `mheap_.shadow_enabled` の状態に基づいて `writeBarrierEnabled` の値を計算し、設定します。これにより、ライトバリアの有効/無効の判断ロジックが `setGCPhase` 関数内に集約され、他のライトバリア使用箇所では単に `writeBarrierEnabled` の値を参照するだけでよくなります。

結果として、ライトバリアが必要かどうかをチェックするコードは、`!needwb()` という関数呼び出しから `!writeBarrierEnabled` という単純なブール変数のロードと比較に変わります。この変更により、コンパイラはライトバリアのチェックコードを呼び出し元に容易にインライン化できるようになります。インライン化されたコードは、関数呼び出しのオーバーヘッドなしに直接実行されるため、ポインタの書き込みが発生するたびに発生する小さなオーバーヘッドが累積的に削減され、Goアプリケーション全体のパフォーマンスが向上します。特に、GCが頻繁に動作する、または多くのポインタ操作が行われるワークロードにおいて、この最適化の効果は顕著に現れます。

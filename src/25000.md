# [インデックス 25000] ファイルの概要

このコミットは、Goランタイムにおけるネットワークポーリング（`netpoll`）処理中の予期せぬエラー発生時の挙動を変更するものです。具体的には、`epollwait`、`kevent`、`port_getn`といったシステムコールがエラーを返した場合に、以前はエラーメッセージを出力して処理を継続しようとしていたのに対し、このコミットではプログラムをクラッシュさせる（`throw`する）ように修正されています。これにより、無限ループに陥る可能性のある未定義の挙動を防ぎ、問題の早期発見とデバッグを促進することを目的としています。

## 元コミット内容

Goランタイムにおいて、`netpoll`（ネットワークポーリング）処理中に予期せぬエラーが発生した場合、エラーメッセージを出力して処理を継続しようとする現在の挙動を、プログラムをクラッシュさせる（`throw`する）ように変更する。これは、ユーザーにとって意味不明なエラーメッセージが表示され、対処できない状況を改善するためである。特に、issue 11498で報告されたケースでは、`netpoll`コードが無限ループに陥った可能性が指摘されており、これを防ぐためにプログラムを強制終了させる方針が採用された。

## 変更の背景

Goランタイムの`netpoll`メカニズムは、ネットワークI/Oの効率的な多重化を可能にするための重要なコンポーネントです。しかし、このメカニズムが基盤となるOSのシステムコール（Linuxの`epoll`、BSD系の`kqueue`、Solarisの`port_getn`など）とやり取りする際に、予期せぬエラーが発生することがあります。

以前のGoランタイムの挙動では、これらのシステムコールがエラーを返した場合、`_EINTR`（システムコールがシグナルによって中断されたことを示すエラー）ではない、かつ前回の`netpoll`エラーと同じではない場合にのみエラーメッセージを`println`で出力し、その後`goto retry`で処理を再試行していました。この「エラーをログに出力して継続する」というアプローチは、以下のような問題を引き起こしていました。

1.  **ユーザーにとっての不透明性**: エラーメッセージは低レベルなシステムコールに関するものであり、Goアプリケーションのユーザーにとっては理解しにくく、対処のしようがないものでした。
2.  **デバッグの困難さ**: エラーが発生してもプログラムがクラッシュしないため、問題の根本原因を特定するのが困難でした。特に、issue 11498で報告されたように、`netpoll`コードが無限ループに陥る可能性があり、これはシステムリソースの枯渇やアプリケーションのハングアップにつながる深刻な問題でした。
3.  **未定義の挙動**: 予期せぬエラーからの回復を試みることは、かえってシステムの不安定性を招く可能性がありました。

このコミットは、このような状況を改善し、予期せぬ`netpoll`エラーが発生した場合には、明確にプログラムをクラッシュさせることで、問題の早期発見と開発者による迅速な対応を促すことを目的としています。これにより、曖昧なエラーメッセージに悩まされることなく、根本的な問題を解決するための情報（クラッシュ時のスタックトレースなど）が得られるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. Goランタイムとスケジューラ

Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。Goランタイムは、Goのゴルーチン（goroutine）をOSのスレッドにマッピングし、効率的にスケジューリングする役割を担っています。このスケジューラは、I/O処理などのブロッキング操作が発生した際に、ゴルーチンをブロックせずに他のゴルーチンを実行できるように、ノンブロッキングI/Oとネットワークポーリングメカニズムを積極的に利用します。

### 2. ネットワークポーリング (netpoll)

`netpoll`は、Goランタイムが多数のネットワーク接続からのI/Oイベントを効率的に監視するためのメカニズムです。これは、OSが提供するイベント通知API（`epoll`、`kqueue`、`port_getn`など）を利用して実装されています。

*   **ノンブロッキングI/O**: 通常のソケットI/Oはブロッキングモードで動作し、データが利用可能になるまで、または書き込みが完了するまでプログラムの実行を停止させます。`netpoll`は、ソケットをノンブロッキングモードに設定し、I/O操作がすぐに完了しない場合でも、ゴルーチンをブロックせずに他の処理を続行できるようにします。
*   **イベント駆動**: `netpoll`は、複数のファイルディスクリプタ（ソケットなど）を監視し、いずれかのディスクリプタでI/Oイベント（読み取り可能、書き込み可能など）が発生したときに通知を受け取ります。これにより、GoランタイムはI/Oが準備できたゴルーチンのみを再開し、CPUリソースを効率的に利用できます。

### 3. OS固有のネットワークポーリングAPI

Goランタイムは、実行されているOSに応じて異なるネットワークポーリングAPIを使用します。

*   **epoll (Linux)**: Linuxカーネルが提供する高性能なI/Oイベント通知メカニズムです。`epoll_create`でインスタンスを作成し、`epoll_ctl`で監視対象のファイルディスクリプタを追加/削除し、`epoll_wait`でイベントを待ちます。
*   **kqueue (FreeBSD, macOS, NetBSD, OpenBSD)**: BSD系OSで利用されるイベント通知APIです。`kqueue`でキューを作成し、`kevent`で監視対象のイベントを登録/変更し、イベントを待ちます。
*   **port_getn (Solaris)**: Solaris OSで利用されるI/Oイベント通知メカニズムです。`port_create`でポートを作成し、`port_associate`でファイルディスクリプタをポートに関連付け、`port_getn`でイベントを待ちます。

これらのAPIは、それぞれ異なる関数名と引数を持ちますが、基本的な目的は同じです。

### 4. `_EINTR` エラー

`_EINTR`は、多くのシステムコールが返す可能性のあるエラーコードの一つです。これは、システムコールが完了する前にシグナルによって中断されたことを示します。`_EINTR`は一時的なエラーであり、通常はシステムコールを再試行することで解決できます。そのため、`netpoll`の実装では、`_EINTR`エラーの場合は処理を再試行する（`goto retry`）のが一般的なパターンです。

### 5. `throw` 関数 (Goランタイム内部)

Goランタイム内部には、`throw`という関数が存在します。これは、Goプログラムが回復不可能なエラーに遭遇した際に、プログラムを強制的に終了させるために使用されます。`panic`とは異なり、`throw`はスタックアンワインドや`defer`関数の実行を行わず、直接プログラムを終了させます。これは、ランタイム自体の整合性が損なわれた場合など、非常に深刻な状況で使用される低レベルなメカニズムです。

## 技術的詳細

このコミットの技術的な核心は、`netpoll`関連のシステムコール（`epollwait`, `kevent`, `port_getn`）が`_EINTR`以外のエラーを返した場合のGoランタイムの挙動変更にあります。

以前のコードでは、`netpolllasterr`という変数を導入し、前回の`netpoll`エラーコードを記憶していました。エラーが発生した場合、以下の条件で処理を継続していました。

1.  エラーが`_EINTR`ではない。
2.  かつ、エラーが前回の`netpoll`エラーと同じではない。

この条件が真の場合にのみ、エラーメッセージを`println`で出力し、`netpolllasterr`を更新して`goto retry`で処理を再試行していました。このロジックの意図は、同じエラーが連続して発生するのを防ぎ、ログのスパムを避けることだったと考えられます。しかし、このアプローチは、予期せぬエラーが繰り返し発生してもプログラムが終了せず、無限ループに陥る可能性がありました。特に、`netpolllasterr`が同じエラーコードを記憶している間は、エラーメッセージすら出力されずに無限ループに陥る可能性がありました。

このコミットでは、この`netpolllasterr`変数とその関連ロジックが完全に削除されました。新しい挙動は以下の通りです。

*   `epollwait`、`kevent`、`port_getn`が負の値（エラーを示す）を返した場合。
*   エラーが`_EINTR`ではない場合。

上記の条件が満たされた場合、Goランタイムはエラーメッセージを`println`で出力した後、**`throw`関数を呼び出してプログラムを強制終了させます**。

この変更により、`_EINTR`のような一時的なエラーは引き続き再試行されますが、それ以外の予期せぬ、かつ回復不能と判断される`netpoll`エラーが発生した場合には、プログラムが即座にクラッシュします。これにより、開発者はスタックトレースなどの情報から問題の根本原因を特定しやすくなり、無限ループのような未定義の挙動に悩まされることがなくなります。

`netpolllasterr`変数の削除は、コードの複雑性を減らす効果もあります。エラーのログ出力頻度を制御するロジックが不要になったため、コードがよりシンプルになりました。

## コアとなるコードの解説

各ファイルにおける変更のパターンは以下の通りです。

1.  **`netpolllasterr` 変数の削除**:
    *   `epollwait`、`kevent`、`port_getn`の各実装において、`netpolllasterr`というグローバル変数が削除されました。この変数は、以前はエラーログのスパムを防ぐために、同じエラーが連続して発生した場合にログ出力を行わないようにするために使用されていました。

2.  **エラー条件の簡素化**:
    *   エラー処理の`if`文の条件が簡素化されました。
    *   変更前: `if n != -_EINTR && n != netpolllasterr` (または `e != _EINTR && e != netpolllasterr` for Solaris)
    *   変更後: `if n != -_EINTR` (または `e != _EINTR` for Solaris)
    *   これにより、`_EINTR`以外のエラーであれば、それが前回のエラーと同じかどうかに関わらず、常に新しいエラーとして扱われるようになりました。

3.  **`throw` の導入**:
    *   簡素化されたエラー条件が真（つまり、`_EINTR`ではない予期せぬエラー）の場合、エラーメッセージを`println`（または`print` for Solaris）で出力した後、`throw`関数が呼び出されるようになりました。
    *   `throw("epollwait failed")`
    *   `throw("kevent failed")`
    *   `throw("port_getn failed")`
    *   `throw`関数は、Goランタイムの内部関数であり、回復不可能なエラーが発生した際にプログラムを強制終了させます。これにより、無限ループや未定義の挙動を防ぎ、問題の根本原因を特定するためのスタックトレースを提供します。

この変更により、Goランタイムは`netpoll`システムコールからの予期せぬエラーに対して、より積極的かつ明確な対応を取るようになりました。これにより、開発者はGoアプリケーションの安定性とデバッグのしやすさが向上することを期待できます。

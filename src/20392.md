# [インデックス 20392] ファイルの概要

このコミットは、GoランタイムにおけるC言語からGo言語への変換作業の一環として、特にARMアーキテクチャ向けの調整と、スタック分割（stack splitting）に関する改善を目的としています。主な変更点として、`atomic_arm.c`ファイルがGo言語で再実装された`atomic_arm.go`に置き換えられ、多くのランタイム関数に`NOSPLIT`ディレクティブが追加されています。これにより、Goランタイムのコードベースの統一性が高まり、スタック管理の効率と安全性が向上しています。

## 元コミット内容

このコミットは、GoランタイムのC言語からGo言語への変換におけるさらなる調整を含んでいます。主に`NOSPLIT`ディレクティブの追加が行われました。`atomic_arm.c`は`lock`関数を呼び出すため、その複雑さからGo言語で書き直す必要がありました。この変更により、SolarisとWindowsを除くすべてのシステムで、スタックを分割できるGoからCへの呼び出しはなくなりました。SolarisとWindowsについては、別途作業が必要です。

## 変更の背景

Go言語のランタイムは、初期にはパフォーマンス上の理由や既存のC言語コードとの連携のためにC言語で書かれた部分が多く存在しました。しかし、Go言語の進化とともに、ランタイム全体をGo言語で記述することのメリットが大きくなっていきました。

この変更の背景には、以下の主要な動機があります。

1.  **コードベースの統一と保守性の向上**: ランタイムをGo言語で統一することで、Go開発者にとってコードの理解、デバッグ、保守が容易になります。C言語とGo言語の混在は、異なる言語の知識とツールチェインの管理を必要とし、開発の複雑性を増大させます。
2.  **Go言語の機能活用**: Go言語の持つ強力な並行処理モデル（ゴルーチン、チャネル）や自動メモリ管理（ガベージコレクション）をランタイム自体でより深く活用することで、より効率的で堅牢なランタイムを構築できます。C言語では手動でのメモリ管理やスレッド管理が必要となり、バグの温床となる可能性がありました。
3.  **スタック管理の最適化と安全性**: Goのゴルーチンは非常に軽量であり、動的にスタックサイズを増減させます（スタック分割）。しかし、低レベルのランタイムコード、特にアトミック操作やスケジューラ関連のコードでは、スタック分割がデッドロックやデータ競合、その他の予期せぬ動作を引き起こす可能性があります。`NOSPLIT`ディレクティブの導入は、これらのクリティカルなセクションでのスタック分割を禁止し、ランタイムの安定性と安全性を確保します。
4.  **CGoオーバーヘッドの削減**: GoからCへの呼び出し（CGo）は、言語間のインターフェースを介するため、一定のオーバーヘッドを伴います。ランタイム内のCGo呼び出しを減らすことで、このオーバーヘッドを削減し、全体的なパフォーマンスを向上させることができます。特に、頻繁に呼び出されるアトミック操作のような関数をGoで実装することは、このオーバーヘッド削減に大きく貢献します。
5.  **クロスプラットフォーム対応の簡素化**: C言語のコードはOSやアーキテクチャに依存する部分が多く、異なるプラットフォームへの移植には手間がかかります。Go言語でランタイムを記述することで、Goコンパイラが提供するクロスコンパイルの恩恵を最大限に受け、より容易に多様なプラットフォームをサポートできるようになります。

このコミットは、特にARMアーキテクチャにおけるアトミック操作の実装をCからGoへ移行し、さらに多くのランタイム関数に`NOSPLIT`を追加することで、上記の目標達成に貢献しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムと関連する概念についての知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、OSが提供する機能（スレッド、メモリ管理など）を直接利用するのではなく、Goランタイムと呼ばれる独自の実行環境上で動作します。ランタイムは、ゴルーチンのスケジューリング、ガベージコレクション、チャネル操作、メモリ割り当て、システムコールインターフェースなど、Goプログラムの実行に必要な低レベルの機能を提供します。

2.  **ゴルーチン (Goroutine)**:
    Go言語の軽量な並行処理単位です。OSスレッドよりもはるかに少ないメモリ（初期スタックサイズは2KB程度）で起動でき、数百万のゴルーチンを同時に実行することも可能です。Goランタイムのスケジューラが、これらのゴルーチンをOSスレッドにマッピングして実行します。

3.  **スタック分割 (Stack Splitting)**:
    Goのゴルーチンは、必要に応じてスタックサイズを動的に増減させます。関数呼び出し時にスタックが不足しそうになると、ランタイムはより大きな新しいスタック領域を割り当て、古いスタックの内容を新しいスタックにコピーします。このプロセスを「スタック分割」と呼びます。Go 1.4以降では、セグメントスタック方式から、より効率的な連続スタック（スタックコピー）方式に移行しました。

4.  **`NOSPLIT` ディレクティブ**:
    Goコンパイラに対する特殊な指示で、関数にスタックオーバーフローチェックを挿入しないように命令します。通常、Goの関数は呼び出し時にスタックが足りるかチェックし、足りなければスタックを拡張します。しかし、ランタイムの非常に低レベルな部分（例: スケジューラ、アトミック操作）では、スタック拡張処理自体がデッドロックや競合状態を引き起こす可能性があります。`NOSPLIT`を付与された関数は、スタック拡張を行わないため、呼び出し元が十分なスタックを持っていることを前提とします。誤用するとスタックオーバーフローによるクラッシュを引き起こすため、Goランタイムの内部でのみ慎重に使用されます。アセンブリコードでは`NOSPLIT`、Goコードでは`//go:nosplit`として記述されます。

5.  **アトミック操作 (Atomic Operations)**:
    複数のCPUコアやスレッドから同時にアクセスされる共有メモリ上のデータに対して、不可分（atomic）な操作を行うための仕組みです。不可分とは、その操作が完全に実行されるか、全く実行されないかのどちらかであり、途中で他の操作に割り込まれることがないことを意味します。これにより、データ競合を防ぎ、正確な並行処理を実現します。CPUが提供する特別な命令（例: Compare-and-Swap (CAS)）やメモリバリア（memory barrier）を利用して実装されます。Goでは`sync/atomic`パッケージやランタイム内部で利用されます。

6.  **`lock` 関数とミューテックス (Mutex)**:
    `lock`関数は、共有リソースへのアクセスを排他的に制御するための同期プリミティブであるミューテックス（相互排他ロック）に関連する操作です。ミューテックスは、一度に一つのゴルーチン（またはスレッド）のみがクリティカルセクション（共有リソースにアクセスするコード領域）に入ることができるように保証します。これにより、データ競合を防ぎます。アトミック操作と比較して、より複雑なクリティカルセクションを保護するのに適していますが、オーバーヘッドが大きくなる可能性があります。

7.  **`onM` 関数**:
    Goランタイムの内部関数で、特定の処理を現在のOSスレッド（GoスケジューラのM: Machine）上で直接実行するために使用されます。通常のゴルーチンはGoスケジューラによってOSスレッド間で移動される可能性がありますが、`onM`で実行されるコードは、そのOSスレッドのコンテキスト内で、スケジューラによるプリエンプション（横取り）なしに実行されます。これは、システムコール、メモリ管理、シグナルハンドリングなど、非常に低レベルで中断されてはならない処理に利用されます。

8.  **Futex (Fast Userspace Mutex)**:
    Linuxカーネルが提供するシステムコールで、ユーザー空間でのミューテックスやセマフォなどの同期プリミティブを効率的に実装するために使用されます。競合がない場合はカーネルへの移行なしにユーザー空間で処理を完結させ、競合が発生した場合にのみカーネルに処理を委ねてスレッドをスリープ/ウェイクアップさせます。Goランタイムは、ゴルーチンのスケジューリングや`sync`パッケージの同期プリミティブの実装にFutexを広く利用しています。

9.  **`semasleep` / `semawakeup`**:
    Goランタイム内部のセマフォ（semaphore）操作に関連する関数です。`semasleep`はゴルーチンをスリープさせ、`semawakeup`はスリープ中のゴルーチンをウェイクアップさせます。これらは`sync.Mutex`や`sync.WaitGroup`などの高レベルな同期プリミティブの基盤として機能します。OS固有のシステムコール（例: Futex）を利用して実装されます。

10. **ソフトフロート (Softfloat)**:
    ハードウェア浮動小数点ユニット（FPU）を持たないCPUアーキテクチャ（特に古いARMv5など）で浮動小数点演算をソフトウェアでエミュレートする技術です。ハードウェアFPUに比べて性能は劣りますが、互換性を確保するために使用されます。

## 技術的詳細

このコミットの技術的詳細は、GoランタイムのCからGoへの移行戦略と、低レベルなスタック管理の最適化に集約されます。

### CからGoへの移行戦略

GoランタイムのCからGoへの移行は、単なる言語の置き換え以上の意味を持ちます。C言語のコードは、ポインタの自由な操作、`goto`文、マクロ、OS固有のAPI呼び出しなど、Go言語には直接的な対応物がない機能や慣習を多用していました。このため、移行は機械的な変換ではなく、Goのイディオムとランタイム設計思想に合わせた再設計を伴います。

このコミットでは、特にARMアーキテクチャ向けのアトミック操作の実装がC言語の`atomic_arm.c`からGo言語の`atomic_arm.go`へと移行されました。元のC言語実装では、`lock`関数（ミューテックス）を呼び出して64ビットのアトミック操作をエミュレートしていました。これは、当時のARMv5/v6アーキテクチャが64ビットのアトミック命令を直接サポートしていなかったため、ソフトウェア的にロックを用いて実現していたためです。しかし、`lock`関数自体が複雑であり、スタック分割の可能性を持つため、ランタイムの低レベルな部分での使用は望ましくありませんでした。

Go言語で`atomic_arm.go`を再実装するにあたり、`lock`関数への依存を排除し、Goの`onM`関数を利用してOSスレッド上で直接アトミック操作を実行するアプローチが取られました。`onM`は、Goスケジューラによるプリエンプションなしに、現在のOSスレッドのコンテキストでコードを実行できるため、アトミック操作のようなクリティカルな処理に適しています。これにより、`lock`の複雑性やスタック分割の問題を回避しつつ、Go言語のコードとしてアトミック操作を表現できるようになりました。

### `NOSPLIT`ディレクティブの広範な適用

コミットメッセージにある「Mostly NOSPLIT additions」が示すように、このコミットのもう一つの重要な側面は、多くのランタイム関数に`NOSPLIT`ディレクティブが追加されたことです。

Goのスタック分割メカニズムは、ゴルーチンの軽量性を実現する上で不可欠ですが、ランタイムの非常に低レベルな部分では問題を引き起こす可能性があります。例えば、ガベージコレクタがメモリをスキャンしている最中や、スケジューラがゴルーチンを切り替えている最中にスタック分割が発生すると、ランタイムの内部状態が破壊されたり、デッドロックが発生したりする危険性があります。

`NOSPLIT`ディレクティブは、これらの関数がスタックチェックを行わず、スタックを拡張しないことを保証します。これにより、これらの関数は常に固定された小さなスタック領域内で実行され、スタック分割による中断や予期せぬ動作を防ぎます。このコミットでは、`runtime·gosave`, `runtime·gogo`, `runtime·mcall`, `runtime·switchtoM`, `runtime·onM`, `runtime·newstackcall`, `reflect·call`, `runtime·lessstack`, `runtime·jmpdefer`, `runtime·setg`, `runtime·casuintptr`, `runtime·atomicloaduintptr`, `runtime·atomicloaduint`, `runtime·timenow`, `runtime·duffzero`, `runtime·duffcopy`, `runtime·fastrand1`, `runtime·gocputicks`, `runtime·return0`, `runtime·procyield`といったアセンブリ関数や、OS固有の`futexsleep`, `semacreate`, `semasleep`, `semawakeup`, `exit`, `read`, `write`などのC言語関数（後にGoに移行されるものも含む）に`NOSPLIT`が追加されています。

特に、`atomic_arm.s`内のアセンブリ関数に`NOSPLIT`が追加されたことは、アトミック操作の実行中にスタック分割が発生しないようにするための重要な措置です。これにより、アトミック操作の不可分性がより確実に保証されます。

### OS固有の調整

コミットには、Dragonfly BSD, FreeBSD, NetBSD, OpenBSD, Plan 9といった様々なOS向けのランタイムファイル（`os_dragonfly.c`, `os_freebsd.c`, `os_netbsd.c`, `os_openbsd.c`, `os_plan9.c`）への変更も含まれています。これらの変更は、主に`futexsleep`や`semasleep`/`semawakeup`といった同期プリミティブの実装を、`onM`関数を利用してGoランタイムの管理下で実行するように調整するものです。これにより、OS固有の低レベルな同期処理もGoランタイムの統一されたスタック管理とスケジューリングモデルに組み込まれ、Goの並行処理モデルとの整合性が高まります。

例えば、`futexsleep`や`semasleep`のような関数は、OSのシステムコールを呼び出してスレッドをスリープさせるため、その呼び出し自体がスタック分割を伴う可能性があります。`onM`を介してこれらの処理を実行することで、GoランタイムはOSスレッドのコンテキストをより細かく制御し、安全にスリープ/ウェイクアップ処理を行えるようになります。

### `_CacheLineSize`の追加

`src/cmd/api/goapi.go`に`_CacheLineSize = 64;`が追加されています。これは、CPUのキャッシュラインサイズを定数として定義するもので、特にアトミック操作や同期プリミティブの実装において、キャッシュコヒーレンシ（キャッシュの一貫性）を考慮したデータ配置を行う際に重要となります。例えば、ミューテックスやアトミック変数をキャッシュラインの境界に配置することで、偽共有（false sharing）を防ぎ、パフォーマンスを向上させることができます。`atomic_arm.go`の`locktab`構造体で`_CacheLineSize`が使用されていることからも、この定数の目的が伺えます。

## コアとなるコードの解説

### `atomic_arm.go` の新規実装

`atomic_arm.go`は、ARMアーキテクチャにおけるアトミック操作をGo言語で提供します。特に注目すべきは、64ビットのアトミック操作（`cas64`, `xadd64`, `xchg64`, `atomicload64`, `atomicstore64`）の実装です。

```go
//go:nosplit
func cas64(addr *uint64, old, new uint64) bool {
	var ok bool
	onM(func() {
		lock(addrLock(addr))
		if *addr == old {
			*addr = new
			ok = true
		}
		unlock(addrLock(addr))
	})
	return ok
}

func addrLock(addr *uint64) *mutex {
	return &locktab[(uintptr(unsafe.Pointer(addr))>>3)%uintptr(len(locktab))].l
}
```

*   **`//go:nosplit`**: これらの関数は`NOSPLIT`ディレクティブを持つため、スタック分割を行いません。これは、アトミック操作の実行中にスタックが拡張されることによる中断や競合を防ぐために重要です。
*   **`onM(func() { ... })`**: 64ビットのアトミック操作は、`onM`関数を介して実行されます。これは、Goスケジューラによるプリエンプションなしに、現在のOSスレッド（M）上で直接クロージャ内のコードを実行することを意味します。これにより、アトミック操作の不可分性を保証し、Goランタイムの低レベルな同期処理を安全に行うことができます。
*   **`lock(addrLock(addr))` / `unlock(addrLock(addr))`**: 64ビットのアトミック操作がハードウェアで直接サポートされていないARMアーキテクチャ（当時のARMv5/v6など）では、ソフトウェア的にミューテックス（`lock`）を使用して排他制御を実現しています。`addrLock`は、アドレスに基づいてハッシュ化されたミューテックスのテーブル（`locktab`）から適切なミューテックスを取得します。これにより、複数の64ビットアトミック操作が同時に実行されることを防ぎ、データ競合を回避します。
*   **`_CacheLineSize`**: `locktab`の定義で`_CacheLineSize`が使用されています。これは、ミューテックスが異なるキャッシュラインに配置されるようにパディングを追加し、偽共有（false sharing）によるパフォーマンス劣化を防ぐための最適化です。

32ビットのアトミック操作（`xadd`, `xchg`, `atomicload`, `atomicstore`など）は、`cas`（Compare-and-Swap）ループを使用して実装されています。これは、CPUが提供するCAS命令を利用して、ロックなしでアトミック性を実現する一般的な手法です。

### `asm_arm.s` における `NOSPLIT` の追加

`asm_arm.s`ファイルでは、Goランタイムの重要なアセンブリ関数に`NOSPLIT`ディレクティブが追加されています。

```assembly
TEXT runtime·gosave(SB),NOSPLIT,$-4-4
TEXT runtime·gogo(SB),NOSPLIT,$-4-4
TEXT runtime·mcall(SB),NOSPLIT,$-4-4
...
```

これらの関数は、ゴルーチンのコンテキストスイッチ、スケジューラの呼び出し、スタック管理など、Goランタイムの根幹をなす処理を担当しています。これらの関数に`NOSPLIT`を付与することで、実行中にスタック分割が発生しないことが保証され、ランタイムの安定性と予測可能性が向上します。特に、`runtime·mcall`や`runtime·onM`のような関数は、OSスレッドのコンテキストを直接操作するため、スタック分割による中断は致命的な問題を引き起こす可能性があります。

### OS固有のファイルにおける `onM` の利用

OS固有のC言語ファイル（例: `os_dragonfly.c`, `os_netbsd.c`）では、`futexsleep`や`semasleep`といった関数が`onM`を介して呼び出されるように変更されています。

変更前（概念図）：
```c
void runtime·futexsleep(uint32 *addr, uint32 val, int64 ns) {
    // 直接 futex システムコールを呼び出す
    // ...
}
```

変更後（概念図）：
```c
static void futexsleep(void); // 内部関数として定義

#pragma textflag NOSPLIT
void runtime·futexsleep(uint32 *addr, uint32 val, int64 ns) {
    // 引数を g->m->ptrarg/scalararg に保存
    g->m->ptrarg[0] = addr;
    g->m->scalararg[0] = val;
    g->m->ptrarg[1] = &ns;

    void (*fn)(void) = futexsleep;
    runtime·onM(&fn); // onM を介して futexsleep を呼び出す
    // g->m->ptrarg/scalararg から結果を取得
}

static void futexsleep(void) {
    // g->m->ptrarg/scalararg から引数を復元
    uint32 *addr = g->m->ptrarg[0];
    uint32 val = g->m->scalararg[0];
    int64 ns = *(int64*)g->m->ptrarg[1];
    // futex システムコールを呼び出す
    // ...
}
```

この変更により、`runtime·futexsleep`のような外部から呼び出される関数は、直接OSシステムコールを呼び出すのではなく、一度`onM`を介して内部の`futexsleep`関数を呼び出すようになります。これにより、GoランタイムはOSスレッドのコンテキストをより細かく制御し、システムコール呼び出しに伴うスタック管理やスケジューリングの複雑性をGoランタイムの内部で吸収できるようになります。これは、GoランタイムのCからGoへの移行戦略の一環であり、OS固有の低レベルな処理もGoのスケジューリングモデルに統合していく方向性を示しています。

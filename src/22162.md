# [インデックス 22162] ファイルの概要

このコミットは、Goランタイムのスケジューラにおけるネットワークポーリング（netpoll）の挙動を最適化するものです。特に、`findrunnable`関数内で実行される非ブロッキングな`netpoll`呼び出しが、既に別のスレッドがブロッキング`netpoll`を実行している場合に無駄になることを防ぎ、CPU時間の消費を削減することを目的としています。

## 元コミット内容

```
runtime: do not do futile netpolls

There is no sense in trying to netpoll while there is
already a thread blocked in netpoll. And in most cases
there must be a thread blocked in netpoll, because
the first otherwise idle thread does blocking netpoll.

On some program I see that netpoll called from findrunnable
consumes 3% of time.
```

## 変更の背景

Goランタイムのスケジューラは、実行可能なゴルーチン（goroutine）を見つけるために様々な戦略をとります。その一つに、ネットワークI/Oの準備ができたゴルーチンをポーリングする`netpoll`があります。

コミットメッセージによると、`findrunnable`関数（実行可能なゴルーチンを探すGoスケジューラの主要な関数の一つ）内で非ブロッキングな`netpoll`が呼び出されることがありました。しかし、Goランタイムの設計上、通常は常に少なくとも1つのOSスレッド（M）がブロッキングモードで`netpoll`を実行しており、ネットワークイベントを待機しています。このブロッキング`netpoll`が既にアクティブであるにもかかわらず、他のスレッドが非ブロッキング`netpoll`を繰り返し実行することは、CPUサイクルを無駄に消費する「無益な（futile）netpoll」となります。

コミットの作者は、特定のプログラムにおいて、`findrunnable`からの`netpoll`呼び出しがCPU時間の3%を消費していることを観測しました。この無駄な消費を削減し、ランタイムの効率を向上させることが、この変更の主な動機です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とネットワークI/Oの仕組みに関する知識が必要です。

1.  **Goスケジューラ (M, P, Gモデル)**:
    *   **G (Goroutine)**: Goにおける軽量な実行単位。ユーザーが記述する並行処理の最小単位です。
    *   **M (Machine/OS Thread)**: オペレーティングシステムのスレッド。Goのコードを実行する物理的なスレッドです。
    *   **P (Processor/Context)**: MとGを仲介する論理的なプロセッサ。実行可能なGのキューを持ち、MがGを実行するためのコンテキストを提供します。Pの数は通常、CPUコア数に等しく設定されます。
    *   Goスケジューラは、GをPにディスパッチし、PにアタッチされたMがGを実行します。Mがブロックされると、Pは別のMに引き継がれるか、新しいMが作成されます。

2.  **ネットワークポーリング (netpoll)**:
    *   Goの非同期ネットワークI/Oは、OSのI/O多重化メカニズム（Linuxのepoll、macOS/FreeBSDのkqueue、WindowsのIOCPなど）を利用して実装されています。
    *   `netpoll`は、これらのOSメカニズムを抽象化し、ネットワークI/Oの準備ができたファイルディスクリプタ（ソケットなど）を監視します。
    *   ネットワークI/O操作（例: `Read`, `Write`）がブロックされる可能性がある場合、Goランタイムはそのゴルーチンを`_Gwaiting`状態にし、Mを解放して他のゴルーチンを実行できるようにします。
    *   I/Oが完了すると、`netpoll`がそれを検知し、対応するゴルーチンを`_Grunnable`状態に戻し、実行キューに戻します。
    *   `netpoll`には、ブロッキングモードと非ブロッキングモードがあります。
        *   **ブロッキング `netpoll`**: ネットワークイベントが発生するまでOSスレッドをブロックします。通常、アイドル状態のMがこのモードでネットワークイベントを待ちます。
        *   **非ブロッキング `netpoll`**: ネットワークイベントが利用可能であればすぐにそれを返し、そうでなければすぐに制御を返します。CPUをブロックしませんが、イベントがない場合は繰り返し呼び出すとCPUを無駄に消費します。

3.  **`findrunnable`関数**:
    *   Goスケジューラの中心的な関数の一つで、現在のPで実行可能なゴルーチンを見つける役割を担います。
    *   ローカルキュー、グローバルキュー、ネットワークポーラーなど、様々な場所からゴルーチンを探します。
    *   ゴルーチンが見つからない場合、他のPからゴルーチンを「盗む（steal）」ことも試みます。

4.  **`sched.lastpoll`**:
    *   Goランタイムのグローバルなスケジューラ状態の一部で、最後にブロッキング`netpoll`が実行された時刻を記録します。
    *   この値は、現在ブロッキング`netpoll`を実行しているスレッドが存在するかどうか、または最近実行されたかどうかを推測するためのヒントとして使用されます。

## 技術的詳細

このコミットの核心は、`src/runtime/proc1.go`内の`findrunnable`関数における`netpoll(false)`（非ブロッキング`netpoll`）の呼び出しを条件付きにすることです。

変更前は、`findrunnable`は常に非ブロッキング`netpoll`を試行していました。

```go
// poll network - returns list of goroutines
if gp := netpoll(false); gp != nil { // non-blocking
    injectglist(gp.schedlink)
    casgstatus(gp, _Gwaiting, _Grunnable)
    if trace.enabled {
        traceGoUnpark(gp)
    }
    return gp
}
```

変更後は、この非ブロッキング`netpoll`の呼び出しが以下の2つの条件を満たす場合にのみ実行されるようになりました。

1.  `netpollinited()`: ネットワークポーラーが初期化されていること。これは通常、プログラムの起動時に行われます。
2.  `sched.lastpoll != 0`: 少なくとも一度、ブロッキング`netpoll`が実行されたことがある、または現在ブロッキング`netpoll`を実行しているスレッドが存在する可能性が高いことを示します。`sched.lastpoll`が0でないということは、ネットワークポーラーがアクティブであり、イベントを待機しているスレッドが存在する可能性が高いことを意味します。

新しいコメントでは、この非ブロッキング`netpoll`が「スティール（stealing）」に頼る前の最適化に過ぎないことが強調されています。つまり、他のPからゴルーチンを盗むというコストの高い操作を行う前に、手軽にネットワークイベントをチェックするものです。

そして、最も重要な点として、**「既にブロッキング`netpoll`を実行しているスレッドが存在する場合、この非ブロッキング`netpoll`は安全にスキップできる」**と説明されています。これは、もしブロッキングスレッドが既に`netpoll`から戻っていたとしても（しかし`sched.lastpoll`がまだ更新されていないような論理的な競合状態があったとしても）、この現在のスレッドは後でブロッキング`netpoll`を実行する機会があるため、問題ないというロバスト性が考慮されています。

この変更により、複数のMが同時に無駄な非ブロッキング`netpoll`を繰り返し実行する状況が回避され、CPUサイクルの無駄が削減されます。特に、ネットワークI/Oが頻繁に発生しない、またはネットワークイベントの発生頻度が低いアプリケーションにおいて、この最適化は効果を発揮します。

## コアとなるコードの解説

変更の中心は、`netpoll(false)`の呼び出しを囲む`if`条件文です。

**変更前:**
```go
if gp := netpoll(false); gp != nil { // non-blocking
    // ... ネットワークイベント処理 ...
    return gp
}
```
`findrunnable`は、実行可能なゴルーチンを探す過程で、常に非ブロッキングな`netpoll`を試行していました。これにより、ネットワークイベントがなくても`netpoll`が呼び出され、CPUサイクルが無駄になる可能性がありました。

**変更後:**
```go
// Poll network.
// This netpoll is only an optimization before we resort to stealing.
// We can safely skip it if there a thread blocked in netpoll already.
// If there is any kind of logical race with that blocked thread
// (e.g. it has already returned from netpoll, but does not set lastpoll yet),
// this thread will do blocking netpoll below anyway.
if netpollinited() && sched.lastpoll != 0 {
    if gp := netpoll(false); gp != nil { // non-blocking
        // netpoll returns list of goroutines linked by schedlink.
        injectglist(gp.schedlink)
        casgstatus(gp, _Gwaiting, _Grunnable)
        if trace.enabled {
            traceGoUnpark(gp)
        }
        return gp
    }
}
```
新しい`if`条件`netpollinited() && sched.lastpoll != 0`が追加されました。
*   `netpollinited()`: ネットワークポーラーがシステムで利用可能かつ初期化済みであることを確認します。これは通常、Goプログラムのライフサイクルを通じて真です。
*   `sched.lastpoll != 0`: これは、Goランタイムが最後にブロッキング`netpoll`を実行した時刻のタイムスタンプです。この値が0でないということは、少なくとも一度はブロッキング`netpoll`が実行されており、現在もネットワークイベントを待機しているスレッドが存在する可能性が高いことを示唆します。つまり、既に誰かがネットワークイベントを監視しているので、このMがわざわざ非ブロッキングでポーリングする必要はない、という判断基準になります。

この条件が真の場合にのみ、内側の`if gp := netpoll(false); gp != nil`が実行されます。これにより、既にブロッキング`netpoll`がアクティブな場合に、無駄な非ブロッキング`netpoll`の呼び出しが抑制され、CPU使用率が改善されます。

また、コメントが追加され、この非ブロッキング`netpoll`が「スティールに頼る前の最適化に過ぎない」こと、そして「既にブロッキング`netpoll`を実行しているスレッドが存在する場合、安全にスキップできる」ことが明記されています。これは、この最適化がランタイムの正確性やロバスト性を損なわないことを保証するための重要な説明です。

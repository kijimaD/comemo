# [インデックス 27704] ファイルの概要

このコミットは、Windows環境におけるGoランタイムのタイマー解像度設定に関する重要な変更を元に戻すものです。具体的には、以前のコミットで無効化されていた `timeBeginPeriod(1)` の呼び出しを再度有効にすることで、システムモニター（Sysmon）の正確な動作を保証し、システムコールでブロックされたGoroutineのパフォーマンス低下を防ぐことを目的としています。

## 元コミット内容

このコミットは、コミット `ab4c9298b8185a056ff1152f2c7bd9b38d3d06f3` を元に戻すものです。元のコミットの意図は、Windows上で `timeBeginPeriod` を呼び出さないようにすることでした。これはおそらく、`timeBeginPeriod` がシステム全体のタイマー解像度を変更し、電力消費の増加や他のアプリケーションへの影響といった副作用を持つため、その使用を避けることを目的としていたと考えられます。

## 変更の背景

元のコミット `ab4c9298b8185a056ff1152f2c7bd9b38d3d06f3` では、Windows環境で `timeBeginPeriod(1)` の呼び出しを停止しました。しかし、この変更により、Goランタイムの重要なコンポーネントであるシステムモニター（Sysmon）の動作に深刻な問題が発生することが判明しました。

Sysmonは、システムコールでブロックされているP（プロセッサ、OSスレッドに相当）を再取得するために、システムのタイマー解像度に大きく依存しています。タイマー解像度が低いと、SysmonがこれらのPを効率的に監視・再利用できなくなり、結果としてGoroutineの実行が遅延します。コミットメッセージでは、この問題の具体的な例として、`timeBeginPeriod(1)` を使用しない場合にプログラムの実行時間が2msから30msに増加するケース（Issue #14790）が挙げられています。

このパフォーマンス低下は許容できないため、`timeBeginPeriod(1)` の呼び出しを元に戻し、タイマー解像度を高く保つことが決定されました。将来的には、Windowsのユーザーモードスケジューリング（UMS）がGoランタイムでサポートされるようになれば（Issue #7876）、`timeBeginPeriod(1)` の必要性はなくなるとされています。UMSが利用可能になれば、GoランタイムはOSのタイマー解像度に依存することなく、より効率的にGoroutineのスケジューリングとタイマー管理を行えるようになるためです。

## 前提知識の解説

### `timeBeginPeriod` (Windows API)

`timeBeginPeriod` はWindows API関数の一つで、システム全体のタイマーイベントの最小解像度を設定します。この関数を呼び出すことで、アプリケーションはOSのタイマー割り込みの頻度を増やすことができます。

*   **デフォルトのタイマー解像度**: 多くのWindowsシステムでは、デフォルトのタイマー解像度は約15.6ミリ秒（ms）です。これは、OSが約15.6msごとにタイマーイベントを発生させることを意味します。
*   **`timeBeginPeriod(1)` の効果**: `timeBeginPeriod(1)` を呼び出すと、タイマー解像度が1msに設定されます。これにより、OSは1msごとにタイマーイベントを発生させるようになり、より高精度なタイミング処理が可能になります。
*   **副作用**: `timeBeginPeriod` はシステム全体に影響を与えます。タイマー解像度を高く設定すると、OSの割り込み頻度が増加し、CPUの使用率がわずかに上昇したり、電力消費が増加したりする可能性があります。また、他のアプリケーションの動作にも影響を与えることがあります。

### Go Runtime `Sysmon` (システムモニター)

`Sysmon` はGoランタイム内で動作する特別なバックグラウンドGoroutine（またはOSスレッド）です。通常のGoスケジューラ（G-M-Pモデル）とは独立して動作し、Goアプリケーションの健全性を維持するための様々な重要なタスクを実行します。

*   **主な役割**:
    *   **タイマー管理**: アプリケーションが設定したタイマー（`time.After`、`time.NewTimer`など）の期限切れをチェックし、トリガーします。
    *   **Goroutineのプリエンプション**: 長時間実行されているGoroutine（通常10ms以上）を検出し、強制的にプリエンプト（中断）して、他のGoroutineにCPU時間を割り当て、公平なスケジューリングを保証します。
    *   **ガベージコレクション (GC)**: 必要に応じてGCサイクルをトリガーします。
    *   **ネットワークポーリングとシステムコール**: ネットワーク操作やシステムコールでブロックされているGoroutineを監視し、それらが完了した際にスケジューラに通知して、関連するP（OSスレッド）を再利用できるようにします。
*   **タイマー解像度の重要性**: Sysmonがこれらのタスク、特にGoroutineのプリエンプションやシステムコールでブロックされたPの再取得を効率的に行うためには、高精度なタイマー解像度が必要です。タイマー解像度が低いと、Sysmonがイベントを検出するまでの時間が長くなり、Goroutineの遅延やパフォーマンス低下を引き起こします。

### ユーザーモードスケジューリング (UMS)

ユーザーモードスケジューリング（UMS）は、Windowsが提供する機能で、アプリケーションが自身のスレッドスケジューリングをより細かく制御できるようにします。Goランタイムの文脈では、UMSがサポートされれば、GoはOSのスケジューラに依存することなく、Goroutineのスケジューリングとタイマー管理を完全にユーザー空間で行えるようになります。これにより、`timeBeginPeriod` のようなシステム全体のタイマー解像度を変更するAPIに頼ることなく、高精度なタイミング処理を実現できるようになります。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがWindows上で高精度なタイマーイベントを必要とすること、そしてそのために `timeBeginPeriod(1)` の呼び出しが不可欠であるという点にあります。

1.  **Sysmonの依存性**: GoランタイムのSysmonは、システムコールでブロックされたGoroutine（正確には、そのGoroutineが実行されていたP、つまりOSスレッド）を監視し、ブロックが解除された際にそのPをGoスケジューラに再利用させる役割を担っています。この監視はタイマーイベントに基づいて行われるため、OSのタイマー解像度が低いと、Sysmonがブロック解除を検出するまでの時間が長くなり、Pの再利用が遅延します。結果として、他のGoroutineが実行される機会が失われ、アプリケーション全体のパフォーマンスが低下します。
2.  **パフォーマンスへの影響**: コミットメッセージに記載されているように、`timeBeginPeriod(1)` を使用しない場合、特定のプログラムの実行時間が2msから30msへと大幅に増加しました。これは、デフォルトの15.6msというタイマー解像度が、Goランタイムが期待する粒度よりも粗すぎるため、SysmonがGoroutineのブロック状態を適切に管理できないことに起因します。
3.  **`winmm.dll` との連携**: `timeBeginPeriod` 関数は `winmm.dll` (Windows Multimedia Library) に含まれています。Goランタイムがこの関数を呼び出すためには、`winmm.dll` をロードし、関数ポインタを取得する必要があります。これは `go:cgo_import_dynamic` ディレクティブと `stdcall` を用いて行われます。
4.  **将来的な展望**: `timeBeginPeriod(1)` の使用は、システム全体への影響という点で理想的ではありません。そのため、GoチームはWindowsのUMSサポート（Issue #7876）を将来的な解決策として位置づけています。UMSが実装されれば、GoランタイムはOSのタイマーに依存せず、より効率的かつ独立してGoroutineのタイミングを管理できるようになり、`timeBeginPeriod` の呼び出しを安全に削除できるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/os_windows.go` における `timeBeginPeriod(1)` の再導入と、それに関連するテストおよびビルドシステムの調整です。

*   **`os_windows.go` の変更**:
    *   `//go:cgo_import_dynamic runtime._timeBeginPeriod timeBeginPeriod%1 "winmm.dll"`: この行は、Goコンパイラに対して、`winmm.dll` から `timeBeginPeriod` という名前の関数を動的にロードするように指示します。`%1` は、この関数が1つの引数を取ることを示しています。これにより、GoランタイムはWindowsのマルチメディアライブラリにアクセスできるようになります。
    *   `_timeBeginPeriod, _ stdFunction`: ロードされた `timeBeginPeriod` 関数のエントリポイントを保持するための内部変数 `_timeBeginPeriod` を宣言しています。
    *   `timeBeginPeriodRetValue = uint32(stdcall1(_timeBeginPeriod, 1))`: ランタイムの初期化フェーズである `osinit()` 関数内で、実際に `timeBeginPeriod(1)` を呼び出しています。`stdcall1` は、1つの引数を取るWindows API関数を呼び出すためのGoランタイムの内部ヘルパー関数です。引数 `1` は、タイマー解像度を1ミリ秒に設定することを意味します。この呼び出しの戻り値（成功/失敗を示すコード）は `timeBeginPeriodRetValue` に格納され、後続のテストで検証されます。

*   **`syscall_windows_test.go` の変更**:
    *   `TestTimeBeginPeriod`: この新しいテストは、`osinit()` で行われた `timeBeginPeriod(1)` の呼び出しが成功したことを確認します。`TIMERR_NOERROR` は、関数がエラーなく実行されたことを示す定数です。これにより、ランタイムが正しくタイマー解像度を設定していることが保証されます。
    *   ベンチマークからの `timeBeginPeriod` 呼び出しの削除: 以前は、特定のベンチマークが `timeBeginPeriod` を個別に呼び出してタイマー解像度を一時的に変更していました。しかし、ランタイム全体で `timeBeginPeriod(1)` が設定されるようになったため、これらの個別の呼び出しは不要となり、削除されました。これにより、ベンチマークはランタイムのグローバルなタイマー設定の下で実行されるようになります。

これらの変更により、GoランタイムはWindows環境で高精度なタイマー解像度を確保し、SysmonがGoroutineのスケジューリングとリソース管理を効率的に行えるようになります。

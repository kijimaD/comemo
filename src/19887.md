## 変更の背景

このコミットの背景には、Go言語の並行処理における「データ競合 (Data Race)」の検出と、それをテストで確実に捉えることの重要性があります。

`mime/multipart` パッケージは、HTTPリクエストなどで使用されるマルチパート形式のデータを扱うためのものです。このパッケージの `Writer` は、複数のパートを書き込む際に内部状態を管理します。並行処理の文脈では、複数のゴルーチンが同時に `Writer` のメソッド（例: `CreateFormField` や `Boundary`）を呼び出すと、内部状態の共有リソースに対して競合が発生し、予期せぬ動作やデータの破損につながる可能性があります。

Goにはデータ競合を検出するための強力な「レース検出器 (Race Detector)」が組み込まれていますが、これはプログラムがデータ競合を実際に「実行」した場合にのみ機能します。元の `TestWriterBoundaryGoroutines` テストでは、データ競合を引き起こす可能性のあるゴルーチンを起動していましたが、そのゴルーチンが完了する前にテスト関数自体が終了してしまう可能性がありました。テスト関数が先に終了してしまうと、データ競合が発生するコードパスが実行されず、レース検出器がその問題を報告する機会を失ってしまいます。

したがって、このコミットの目的は、テストがデータ競合を確実に検出できるように、ゴルーチンがその処理を完了するまでテストの実行を待機させるメカニズムを追加することでした。これにより、テストがより堅牢になり、潜在的な並行処理の問題を見逃すリスクが低減されます。

## 前提知識の解説

### 1. データ競合 (Data Race)

データ競合は、並行プログラミングにおける最も一般的なバグの一つです。Go言語において、データ競合は以下の3つの条件がすべて満たされた場合に発生します。

*   少なくとも2つのゴルーチンが同時に同じメモリ位置にアクセスする。
*   それらのアクセスのうち少なくとも1つが書き込みである。
*   それらのアクセスが同期メカニズム（ミューテックス、チャネルなど）によって保護されていない。

データ競合が発生すると、プログラムの動作は非決定論的になり、結果が実行ごとに変わる可能性があります。これはデバッグを非常に困難にします。Goのレース検出器は、`go run -race` や `go test -race` のように `-race` フラグを付けてプログラムを実行することで、実行時にデータ競合を検出して報告してくれます。

### 2. ゴルーチン (Goroutine)

ゴルーチンはGo言語における軽量な並行実行単位です。関数呼び出しの前に `go` キーワードを付けるだけで、その関数は新しいゴルーチンとして並行して実行されます。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数千、数万のゴルーチンを同時に実行することが可能です。

### 3. チャネル (Channel)

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、ゴルーチン間の同期と通信を安全に行うための主要な手段であり、データ競合を防ぐために推奨される方法です。チャネルは、送信操作と受信操作が同期する（ブロックする）ことで、ゴルーチン間の順序付けを保証できます。

*   **バッファなしチャネル**: 送信側は受信側が値を受け取るまでブロックし、受信側は送信側が値を送るまでブロックします。これにより、2つのゴルーチン間の同期が保証されます。
*   **バッファありチャネル**: チャネルにバッファがある場合、バッファが満杯になるまで送信はブロックせず、バッファが空になるまで受信はブロックしません。

このコミットでは、バッファなしチャネルを使用して、ゴルーチン間の同期を実現しています。

## 技術的詳細

このコミットは、`mime/multipart` パッケージの `TestWriterBoundaryGoroutines` テストが、データ競合を確実に検出できるようにするためのものです。元のテストでは、`w.CreateFormField("foo")` を呼び出すゴルーチンを起動した後、すぐに `w.Boundary()` を呼び出していました。この `w.Boundary()` の呼び出しは、`CreateFormField` が内部的に `Writer` の境界文字列を生成またはアクセスする際に、データ競合を引き起こす可能性のある操作です。

問題は、`go func() { w.CreateFormField("foo") }()` で起動されたゴルーチンが、`w.Boundary()` が呼び出される前に完了してしまうか、あるいはテスト関数全体が終了してしまう可能性があったことです。もしゴルーチンがデータ競合を引き起こす操作を完了する前にテストが終了した場合、Goのレース検出器はその競合を報告できません。

この修正は、バッファなしチャネル `done` を導入することで、このタイミングの問題を解決しています。

1.  `done := make(chan int)`: バッファなしチャネル `done` を作成します。
2.  ゴルーチン内で `w.CreateFormField("foo")` の呼び出し後に `done <- 1` を実行します。これは、ゴルーチンが `CreateFormField` の処理を完了したことを `done` チャネルに送信することで通知します。バッファなしチャネルなので、この送信操作は、メインのテストゴルーチンが `<-done` で値を受信するまでブロックします。
3.  メインのテストゴルーチンで `w.Boundary()` を呼び出した後、`<-done` を実行します。これは、`done` チャネルから値を受信するまでブロックします。これにより、メインのテストゴルーチンは、データ競合を引き起こす可能性のあるゴルーチンが `CreateFormField` の処理を完了するまで待機することが保証されます。

この同期メカニズムにより、`CreateFormField` と `Boundary` の両方が実行され、もしデータ競合が存在すれば、レース検出器がそれを確実に捉えることができるようになります。

## コアとなるコードの解説

*   `done := make(chan int)`:
    これは、`int` 型の値を送受信するためのバッファなしチャネル `done` を作成します。バッファなしチャネルは、送信操作と受信操作が同時に行われるまでブロックするという特性を持ち、ゴルーチン間の同期に非常に適しています。

*   `go func() { ... done <- 1 }()`:
    この部分では、匿名関数が新しいゴルーチンとして起動されます。このゴルーチンは `w.CreateFormField("foo")` を呼び出します。この呼び出しが完了した後、`done <- 1` が実行されます。これは、`done` チャネルに整数値 `1` を送信しようとします。チャネルがバッファなしであるため、この送信操作は、メインのテストゴルーチンが `<-done` で値を受信するまでブロックします。これにより、`CreateFormField` の処理が確実に完了するまで、ゴルーチンが終了しないことが保証されます。

*   `w.Boundary()`:
    これは、メインのテストゴルーチンで実行される元のコードの一部です。この呼び出しは、`CreateFormField` と並行して実行され、データ競合を引き起こす可能性のある操作です。

*   `<-done`:
    これは、メインのテストゴルーチンで実行されます。`done` チャネルから値を受信しようとします。チャネルがバッファなしであるため、この受信操作は、先に起動されたゴルーチンが `done <- 1` を実行するまでブロックします。これにより、メインのテストゴルーチンは、データ競合を引き起こす可能性のあるゴルーチンがその処理を完了するまで待機します。

これらの変更により、`TestWriterBoundaryGoroutines` は、`CreateFormField` と `Boundary` の両方の操作が、データ競合を検出できるようなタイミングで確実に実行されることを保証します。これにより、Goのレース検出器が潜在的な問題をより確実に捉えることができるようになります。

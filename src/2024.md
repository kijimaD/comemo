# [インデックス 2024] ファイルの概要

このコミットは、Go言語の初期の`http`パッケージ（現在の`net/http`パッケージの前身）におけるリダイレクト処理の改善と、URL解析機能の強化を目的としています。具体的には、HTTPリダイレクトの`Location`ヘッダーが相対パスで指定された場合に、それを絶対パスに変換するロジックが導入されました。また、URL構造体を文字列に再構築する`String()`メソッドが追加され、URL解析機能のテストカバレッジが大幅に向上しました。

## 元コミット内容

```

(HTTP requires absolute in protocol).

```

これは、`Location`ヘッダーがHTTPプロトコルで絶対URIを要求しているため、相対パスを絶対パスに変換するように変更したこと、そしてURL関連のテストを追加したことを簡潔に示しています。

## 変更の背景

この変更の背景には、HTTPプロトコルの仕様と、実際のウェブブラウザの挙動との間の乖離があります。HTTP/1.1の仕様を定めたRFC 2616では、`Location`ヘッダーには絶対URI（例: `http://www.example.com/path/to/resource`）を指定することが義務付けられていました。しかし、多くのウェブサーバーやアプリケーションでは、利便性のため、あるいはサーバーが自身の完全なホスト名を知らない場合があるため、相対パス（例: `/path/to/resource`）を`Location`ヘッダーに含めてリダイレクトを行うことが一般的でした。

ウェブブラウザはこのような相対パスのリダイレクトを許容し、適切に処理することが多かったため、事実上の標準となっていました。しかし、Goの`http`パッケージが厳密にRFC 2616に従おうとすると、相対パスのリダイレクトが正しく機能しない可能性がありました。

このコミットは、この問題に対処するために、`http.Redirect`関数が相対パスを受け取った場合に、リクエストのパスに基づいてそれを絶対パスに変換するロジックを追加しました。これにより、GoのHTTPサーバーがより多くの既存のウェブクライアント（ブラウザなど）と互換性を持つようになります。また、URLの解析と再構築の正確性を保証するために、広範なテストが追加されました。

## 前提知識の解説

### HTTPリダイレクトと`Location`ヘッダー

HTTPリダイレクトは、クライアント（通常はウェブブラウザ）を別のURLに誘導するための仕組みです。サーバーは、3xx番台のステータスコード（例: `301 Moved Permanently`, `302 Found`, `303 See Other`）を返すと共に、`Location`ヘッダーに新しいURLを含めます。クライアントはこの`Location`ヘッダーのURLに再度リクエストを送信します。

### RFC 2616

RFC 2616は、HTTP/1.1の主要な仕様を定義した文書です。このRFCでは、`Location`ヘッダーのURIは絶対URIでなければならないと規定されていました。しかし、この厳格な要件は、後のRFC 7231やRFC 9110で緩和され、相対URIも許容されるようになりました。このコミットが行われた2009年時点では、RFC 2616が最新の主要なHTTP/1.1仕様であり、その制約が考慮されていました。

### URLの構造と解析

URL（Uniform Resource Locator）は、インターネット上のリソースの位置を示す文字列です。一般的なURLは、スキーム（`http`, `https`など）、ホスト名、ポート番号、パス、クエリ、フラグメントなどの要素で構成されます。URLの解析とは、この文字列から各要素を抽出し、構造化されたデータとして扱うことです。Go言語の`net/url`パッケージ（当時は`http`パッケージの一部）は、このURL解析機能を提供します。

### Go言語の`path`パッケージ

Go言語の標準ライブラリには、ファイルパスを操作するための`path`パッケージがあります。このコミットで利用されている`path.Split`関数は、パスをディレクトリ部分とファイル部分に分割します。`path.Clean`関数は、パスを正規化し、冗長な要素（例: `.`、`..`）を削除したり、スラッシュの重複を解消したりして、最も短くクリーンな形式にします。

## 技術的詳細

このコミットの技術的な核心は、`src/lib/http/server.go`内の`Redirect`関数における`Location`ヘッダーの処理と、`src/lib/http/url.go`における`URL`構造体の`String()`メソッドの実装、そしてそれらを検証するテストの追加です。

### `http.Redirect`関数の変更

変更前の`Redirect`関数は、与えられたURLをそのまま`Location`ヘッダーに設定していました。
変更後、`Redirect`関数は以下のロジックを追加しました。

1.  **URLの解析**: まず、`ParseURL(url)`を呼び出して、与えられた`url`文字列を`URL`構造体に解析します。これにより、スキーム、ホスト、パスなどの各要素にアクセスできるようになります。
2.  **エラーハンドリング**: `ParseURL`がエラーを返した場合、元のURLをそのまま`Location`ヘッダーに設定し、`StatusMovedPermanently`（301）を返します。これは、内部エラーが発生した場合のフォールバックです。
3.  **相対パスの絶対パス化**:
    *   `u.Scheme == ""`の条件で、与えられたURLがスキーム（例: `http://`）を持たない、つまり相対パスであるかを判断します。
    *   もしURLが空文字列であるか、または`/`で始まらない場合（例: `../foo`や`bar`）、それは現在のリクエストパスに対する相対パスと見なされます。
    *   この場合、現在のリクエストのパス（`c.Req.Url.Path`）を基準にして、`path.Split`でディレクトリ部分を取得し、それに相対URLを結合することで絶対パスを構築します。
    *   例: リクエストパスが`/foo/bar`で、リダイレクトURLが`../baz`の場合、`path.Split("/foo/bar")`は`("/foo/", "bar")`を返し、`olddir`は`/foo/`となります。これに`../baz`を結合すると`/foo/../baz`となります。
4.  **パスの正規化**:
    *   `path.Clean(url)`を呼び出して、構築されたパスを正規化します。これにより、`/foo/../baz`のようなパスが`/baz`に変換されます。
    *   元のURLが末尾に`/`を持っていた場合（例: `/foo/`）、`path.Clean`は末尾のスラッシュを削除する可能性があるため、その情報を保持し、必要であれば正規化後に再度追加します。これは、ディレクトリを示すURLのセマンティクスを維持するためです。
5.  **`Location`ヘッダーの設定**: 最終的に、処理された絶対パス（または元のURL）が`Location`ヘッダーに設定され、リダイレクトレスポンスが送信されます。

このロジックは、RFC 2616の厳密な要件と、実際のウェブの挙動との間のギャップを埋めるための実用的なアプローチを示しています。コメントにあるように、サーバーが自身の完全な絶対URI（スキームとホスト名を含む）を常に知っているわけではないため、絶対パスを返すという妥協がなされています。

### `URL.String()`メソッドの追加

`src/lib/http/url.go`に`URL`構造体の`String()`メソッドが追加されました。これはGoの`fmt.Stringer`インターフェースを満たすもので、`URL`構造体の内容から完全なURL文字列を再構築します。

このメソッドは、`URL`構造体の以下のフィールドを結合して文字列を生成します。
*   `Scheme` (例: `http`)
*   `Userinfo` (例: `user:pass`)
*   `Host` (例: `www.example.com:8080`)
*   `Path` (例: `/path/to/resource`)
*   `Query` (例: `key=value`)
*   `Fragment` (例: `section`)

このメソッドの追加は、URLの解析だけでなく、プログラム内で操作されたURLを再度文字列として表現する能力を提供し、特に`Redirect`関数のように`Location`ヘッダーにURLを設定する際に不可欠な機能となります。

### `url_test.go`の追加

`src/lib/http/url_test.go`という新しいテストファイルが追加され、`URL`の解析（`ParseURL`, `ParseURLReference`）と文字列化（`URL.String()`）に関する広範なテストケースが導入されました。これには、スキームなし、ユーザー情報あり、クエリあり、フラグメントあり、非権威型URLなど、様々な形式のURLが含まれています。

テストの追加は、Go言語の開発における品質保証の重要な側面であり、新しい機能や変更が正しく動作することを保証し、将来のリファクタリングや変更によるデグレードを防ぐ上で不可欠です。

## コアとなるコードの変更箇所

### `src/lib/http/server.go`

```go
 // Redirect replies to the request with a redirect to url,
 // which may be a path relative to the request path.
 func Redirect(c *Conn, url string) {
+	u, err := ParseURL(url);
+	if err != nil {
+		// TODO report internal error instead?
+		c.SetHeader("Location", url);
+		c.WriteHeader(StatusMovedPermanently);
+	}
+
+	// If url was relative, make absolute by
+	// combining with request path.
+	// The browser would probably do this for us,
+	// but doing it ourselves is more reliable.
+
+	// NOTE(rsc): RFC 2616 says that the Location
+	// line must be an absolute URI, like
+	// "http://www.google.com/redirect/",
+	// not a path like "/redirect/".
+	// Unfortunately, we don't know what to
+	// put in the host name section to get the
+	// client to connect to us again, so we can't
+	// know the right absolute URI to send back.
+	// Because of this problem, no one pays attention
+	// to the RFC; they all send back just a new path.
+	// So do we.
+	oldpath := c.Req.Url.Path;
+	if oldpath == "" {	// should not happen, but avoid a crash if it does
+		oldpath = "/"
+	}
+	if u.Scheme == "" {
+		// no leading http://server
+		if url == "" || url[0] != '/' {
+			// make relative path absolute
+			olddir, oldfile := path.Split(oldpath);
+			url = olddir + url;
+		}
+
+		// clean up but preserve trailing slash
+		trailing := url[len(url) - 1] == '/';
+		url = path.Clean(url);
+		if trailing && url[len(url) - 1] != '/' {
+			url += "/";
+		}
+	}
+
  	c.SetHeader("Location", url);
  	c.WriteHeader(StatusMovedPermanently);
 }
```

### `src/lib/http/url.go`

```go
 // String reassembles url into a valid URL string.
 //
 // There are redundant fields stored in the URL structure:
 // the String method consults Scheme, Path, Host, Userinfo,
 // Query, and Fragment, but not RawPath or Authority.
+func (url *URL) String() string {
+	result := "";
+	if url.Scheme != "" {
+		result += url.Scheme + ":";
+	}
+	if url.Host != "" || url.Userinfo != "" {
+		result += "//";
+		if url.Userinfo != "" {
+			result += url.Userinfo + "@";
+		}
+		result += url.Host;
+	}
+	result += url.Path;
+	if url.Query != "" {
+		result += "?" + url.Query;
+	}
+	if url.Fragment != "" {
+		result += "#" + url.Fragment;
+	}
+	return result;
+}
```

## コアとなるコードの解説

### `Redirect`関数における相対パスの絶対パス化

`Redirect`関数に追加されたコードは、HTTPリダイレクトの`Location`ヘッダーに設定されるURLが相対パスである場合に、それを現在のリクエストのパスを基準とした絶対パスに変換します。

1.  `u, err := ParseURL(url)`: まず、リダイレクト先の`url`文字列を`URL`構造体に解析します。これにより、URLの各構成要素（スキーム、ホスト、パスなど）にアクセスできるようになります。
2.  `if u.Scheme == ""`: この条件は、解析されたURLがスキーム（例: `http://`）を持たない、つまり相対URLであることを示します。
3.  `if url == "" || url[0] != '/'`: 相対URLがさらに、ルートからの絶対パス（`/`で始まる）ではない場合、現在のリクエストのパスを基準とした相対パスとして扱います。
4.  `olddir, oldfile := path.Split(oldpath)`: 現在のリクエストパス（`c.Req.Url.Path`）をディレクトリ部分とファイル部分に分割します。例えば、`/foo/bar`は`/foo/`と`bar`に分割されます。
5.  `url = olddir + url`: 分割されたディレクトリ部分に、リダイレクト先の相対URLを結合します。これにより、例えば`/foo/`と`../baz`が結合されて`/foo/../baz`のようなパスが生成されます。
6.  `url = path.Clean(url)`: `path.Clean`関数は、`../`のような冗長な要素を解決し、パスを正規化します。例えば、`/foo/../baz`は`/baz`に変換されます。
7.  `if trailing && url[len(url) - 1] != '/' { url += "/"; }`: 元のURLが末尾にスラッシュを持っていた場合（ディレクトリを示す慣習）、`path.Clean`によってスラッシュが削除される可能性があるため、このロジックで再度追加し、元のセマンティクスを維持します。

この一連の処理により、GoのHTTPサーバーは、RFC 2616の厳密な要件（絶対URI）と、ウェブブラウザが相対パスのリダイレクトを許容するという現実との間で、実用的なバランスを取ることができるようになりました。サーバーが自身の完全なホスト名を知らない場合でも、少なくとも絶対パス形式でリダイレクトを提供できるようになります。

### `URL.String()`メソッド

`URL`構造体に追加された`String()`メソッドは、Goの慣習に従い、構造体の内容を人間が読める文字列形式に変換します。このメソッドは、`URL`構造体の各フィールド（`Scheme`, `Userinfo`, `Host`, `Path`, `Query`, `Fragment`）を適切な順序で結合し、完全なURL文字列を再構築します。

このメソッドは、デバッグ目的だけでなく、`Redirect`関数が`Location`ヘッダーに設定するURLを生成する際など、プログラム内でURLを文字列として扱う必要がある場合に非常に有用です。これにより、URLの各要素を個別に操作した後でも、簡単に有効なURL文字列に戻すことができます。

# [インデックス 20254] ファイルの概要

このコミットは、Go言語の`debug/elf`パッケージにARM64 (AArch64) アーキテクチャ用のELF (Executable and Linkable Format) リロケーション（再配置）のサポートを追加するものです。具体的には、`elf.go`、`file.go`、`file_test.go`の3つのGoソースファイルと、新しいテストデータファイルが変更されています。

- `src/pkg/debug/elf/elf.go`: ELF構造体と定数、特に`Machine`タイプに`EM_AARCH64`を追加し、AArch64固有のリロケーションタイプ（`R_AARCH64`）を多数定義しています。
- `src/pkg/debug/elf/file.go`: ELFファイルの再配置を適用するロジックに、AArch64用の`applyRelocationsARM64`関数を追加し、既存のDWARF情報処理にもAArch64のサポートを組み込んでいます。
- `src/pkg/debug/elf/file_test.go`: AArch64用の新しい再配置テストケースを追加しています。
- `src/pkg/debug/elf/testdata/go-relocation-test-gcc482-aarch64.obj`: AArch64の再配置テストに使用されるバイナリデータです。

## 変更の背景

このコミットの主な背景は、Go言語がARM64 (AArch64) アーキテクチャ上で`cgo`（C言語との相互運用機能）を適切に動作させるために必要な、ELFバイナリのリロケーションサポートの欠如を解消することです。

Go言語は、C言語で書かれたライブラリを呼び出すための`cgo`というメカニズムを提供しています。`cgo`を使用すると、Goプログラムは既存のCライブラリとリンクできます。このリンクプロセスでは、コンパイラとリンカが生成するオブジェクトファイル（ELF形式）内の「リロケーション」情報を正しく処理する必要があります。リロケーションとは、プログラムがロードされる実行時までアドレスが確定しないシンボル（変数や関数など）への参照を、正しいメモリアドレスに解決するプロセスです。

当時、Goのツールチェイン（特に`debug/elf`パッケージ）はARM64アーキテクチャのELFリロケーションタイプを完全に理解していませんでした。そのため、ARM64上で`cgo`を利用しようとすると、リンカが正しいアドレス解決を行えず、プログラムが正常に動作しない問題が発生していました（`Fixes #8533`が示す問題）。

このコミットは、`gccgo`（GCCベースのGoコンパイラ）にも同様のパッチが適用されることを前提として、Goの標準ツールチェインがARM64のELFリロケーションを処理できるようにするための最小限のサポートを追加します。これにより、ARM64環境でのGoとCの相互運用性が向上し、より多くのシステムでGoアプリケーションが利用できるようになります。

また、コミットメッセージでは、アーキテクチャ名を「arm64」ではなく「AArch64」と表記している理由が明記されています。これは、ARMが発行する関連ドキュメント（特に「ELF for the ARM® 64-bit Architecture (AArch64)」IHI0056B）が「AArch64」という名称を使用しているため、それに準拠していることを示しています。これは、技術文書における一貫性と正確性を重視する姿勢の表れです。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システム（Linux、FreeBSDなど）で広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイル形式です。プログラムのコード、データ、シンボル、リロケーション情報などが構造化されて格納されています。

ELFファイルは、主に以下のセクションで構成されます。
- **ELFヘッダ**: ファイルの種類（実行可能、オブジェクトなど）、ターゲットアーキテクチャ、エントリポイントなどの基本的な情報。
- **プログラムヘッダテーブル**: 実行可能ファイルや共有ライブラリで使用され、メモリへのロード方法を記述します。
- **セクションヘッダテーブル**: オブジェクトファイルや共有ライブラリで使用され、ファイル内の各セクション（`.text`、`.data`、`.bss`など）の情報を記述します。
- **セクション**: 実際のコード（`.text`）、初期化済みデータ（`.data`）、初期化されていないデータ（`.bss`）、シンボルテーブル（`.symtab`）、文字列テーブル（`.strtab`）、リロケーション情報（`.rel`、`.rela`）など。

### リロケーション (Relocation)

リロケーションとは、コンパイル時やリンク時には確定できないメモリアドレスを、プログラムのロード時または実行時に解決するプロセスです。
- **オブジェクトファイル**: コンパイルされたコードは、他のモジュールやライブラリの関数や変数への参照を含んでいます。これらの参照は、最終的な実行可能ファイルが作成されるまで具体的なアドレスが分かりません。リロケーションエントリは、これらの「未解決の参照」を記録します。
- **リンカ**: 複数のオブジェクトファイルを結合して実行可能ファイルや共有ライブラリを作成する際、リンカはリロケーションエントリを読み取り、未解決の参照を正しいアドレスに「再配置」します。
- **動的リンカ**: 共有ライブラリを使用する場合、プログラムが実行される際に動的リンカがリロケーションを実行し、共有ライブラリ内の関数や変数への参照を解決します。

ELFにおけるリロケーションエントリには、主に2つの形式があります。
- `Elf32_Rel` / `Elf64_Rel`: 加算値（addend）がリロケーションエントリ自体に含まれない形式。
- `Elf32_Rela` / `Elf64_Rela`: 加算値がリロケーションエントリに含まれる形式。AArch64では通常`Rela`形式が使用されます。

各リロケーションエントリは、以下の情報を含みます。
- `r_offset`: 再配置が必要な場所のオフセット。
- `r_info`: シンボルテーブルのインデックスとリロケーションタイプをエンコードした値。
- `r_addend` (Rela形式のみ): 再配置計算に使用される加算値。

### ARM64 (AArch64)

ARM64、または正式にはAArch64は、ARMアーキテクチャの64ビット命令セットアーキテクチャです。スマートフォン、タブレット、サーバー、組み込みシステムなど、幅広いデバイスで採用されています。AArch64は、従来の32ビットARM (AArch32) とは異なる命令セットとレジスタセットを持ち、より大きなアドレス空間と高性能な処理能力を提供します。

### cgo

`cgo`は、Go言語のプログラムからC言語のコードを呼び出したり、C言語のコードからGo言語の関数を呼び出したりするためのGoのツールです。GoとCの間の相互運用を可能にし、既存のCライブラリをGoプロジェクトで利用する際に不可欠です。`cgo`は、Goのビルドプロセスの一部として、Cコードをコンパイルし、Goコードとリンクするための接着剤（glue code）を生成します。このリンクプロセスにおいて、ELFのリロケーション処理が重要になります。

## 技術的詳細

このコミットは、Goの`debug/elf`パッケージがAArch64のELFバイナリを正しく解析し、その中のリロケーション情報を処理できるようにするためのものです。

1.  **`EM_AARCH64`の追加**:
    `src/pkg/debug/elf/elf.go`において、`Machine`型に新しい定数`EM_AARCH64`が追加されました。この値は`183`であり、これはELF標準でAArch64アーキテクチャを識別するために割り当てられたマジックナンバーです。これにより、GoのELFパーサーはAArch64のELFファイルを認識できるようになります。

    ```go
    const (
        // ... 既存のMachine定数 ...
        EM_X86_64      Machine = 62 /* Advanced Micro Devices x86-64 */
        EM_AARCH64     Machine = 183 /* ARM 64-bit Architecture (AArch64) */
    )
    ```

2.  **AArch64リロケーションタイプの定義**:
    `src/pkg/debug/elf/elf.go`には、`R_AARCH64`という新しい型が定義され、AArch64アーキテクチャに特有の多数のリロケーションタイプが定数として追加されました。これらの定数は、ARMのELF仕様（IHI0056B）に準拠しており、例えば`R_AARCH64_ABS64`、`R_AARCH64_PREL32`、`R_AARCH64_CALL26`など、絶対アドレス、相対アドレス、関数呼び出しなど、様々な種類のリロケーションを表します。これらのリロケーションタイプは、AArch64の命令セットとリンキング規則に合わせて設計されています。

    ```go
    // Relocation types for AArch64 (aka arm64)
    type R_AARCH64 int

    const (
        R_AARCH64_NONE                            R_AARCH64 = 0
        R_AARCH64_P32_ABS32                       R_AARCH64 = 1
        // ... 多数のリロケーションタイプ ...
        R_AARCH64_IRELATIVE                       R_AARCH64 = 1032
    )
    ```
    これらのリロケーションタイプは、Goの`debug/elf`パッケージがAArch64のオブジェクトファイルや実行可能ファイル内のリロケーションエントリを正しく解釈するために不可欠です。

3.  **AArch64リロケーションの適用ロジック**:
    `src/pkg/debug/elf/file.go`に、`applyRelocationsARM64`という新しい関数が追加されました。この関数は、AArch64のELFファイルから読み取られたリロケーション情報（`Rela64`構造体）を解析し、指定されたバイトスライス（`dst`）に実際の再配置を適用します。

    現在の実装では、`R_AARCH64_ABS64`と`R_AARCH64_ABS32`という2つの絶対アドレスリロケーションタイプのみを処理しています。
    - `R_AARCH64_ABS64`: 64ビットの絶対アドレスを再配置します。`rela.Addend`の値を`dst`の`rela.Off`で指定された位置に64ビット値として書き込みます。
    - `R_AARCH64_ABS32`: 32ビットの絶対アドレスを再配置します。`rela.Addend`の値を`dst`の`rela.Off`で指定された位置に32ビット値として書き込みます。

    この関数は、シンボルテーブルからセクションシンボルを取得し、リロケーションエントリがセクションシンボルを参照している場合にのみ処理を進めます。これは、`cgo`が生成するオブジェクトファイルで必要とされる最小限のリロケーション処理をカバーするためのものです。

4.  **DWARF情報のリロケーションサポート**:
    `src/pkg/debug/elf/file.go`の`DWARF()`関数内で、`.rela.debug_info`セクションのリロケーション処理に`EM_AARCH64`が追加されました。これにより、AArch64のELFファイルに含まれるDWARFデバッグ情報も、必要に応じてリロケーションが適用されるようになります。これは、デバッガがAArch64バイナリのデバッグ情報を正しく解釈するために重要です。

    ```go

    // now otherwise the data in .debug_info is invalid for x86-64 objects.
    rela := f.Section(".rela.debug_info")
    if rela != nil && rela.Type == SHT_RELA && (f.Machine == EM_X86_64 || f.Machine == EM_AARCH64) {
        // ... リロケーション適用ロジック ...
    }
    ```

5.  **テストケースの追加**:
    `src/pkg/debug/elf/file_test.go`に、`testdata/go-relocation-test-gcc482-aarch64.obj`を使用した新しいリロケーションテストケースが追加されました。このテストは、AArch64のELFファイルが正しく解析され、DWARF情報が期待通りに読み取れることを検証します。

これらの変更により、GoのツールチェインはARM64アーキテクチャのELFバイナリをより深く理解し、特に`cgo`が生成するオブジェクトファイルのリロケーションを処理できるようになります。

## コアとなるコードの解説

### `src/pkg/debug/elf/elf.go` の変更

このファイルでは、ELFヘッダの`e_machine`フィールドでアーキテクチャを識別するための新しい定数`EM_AARCH64`が追加されました。これにより、GoのELFパーサーはAArch64のELFファイルを認識し、適切な処理パスに分岐できるようになります。

さらに重要なのは、AArch64アーキテクチャに特有の多数のリロケーションタイプが`R_AARCH64`という新しい型として定義されたことです。これらの定数は、ARMのELF仕様書（IHI0056B）に記載されているリロケーションタイプに対応しています。例えば、`R_AARCH64_ABS64`は64ビット絶対アドレスのリロケーション、`R_AARCH64_CALL26`は26ビット相対アドレスの関数呼び出しリロケーションなど、AArch64の命令セットとリンキングモデルに合わせた詳細なリロケーションセマンティクスを表現します。これらの定義は、GoがAArch64のオブジェクトファイルや共有ライブラリを正確に解析し、リンクするために不可欠です。

### `src/pkg/debug/elf/file.go` の変更

`File`構造体の`applyRelocations`メソッドは、ELFファイルのクラス（32ビットまたは64ビット）とマシンタイプに基づいて、適切なリロケーション適用関数を呼び出すディスパッチャとして機能します。このコミットでは、`ELFCLASS64`かつ`EM_AARCH64`の場合に、新しく追加された`applyRelocationsARM64`関数を呼び出すように変更されました。

`applyRelocationsARM64`関数は、AArch64のELFファイルから読み取られた`Rela64`形式のリロケーションエントリを処理します。
1.  **リロケーションエントリの読み取り**: `rels`バイトスライスから`Rela64`構造体を順次読み取ります。`Rela64`は、リロケーションのオフセット、シンボル情報、加算値（addend）を含む64ビットのリロケーションエントリです。
2.  **シンボルの解決**: `rela.Info`フィールドからシンボル番号とリロケーションタイプを抽出します。現在の実装では、リロケーションがセクションシンボル（`STT_SECTION`）を参照している場合にのみ処理を進めます。これは、`cgo`が生成するオブジェクトファイルで必要とされる最小限のサポートを提供するためです。
3.  **リロケーションの適用**: `switch t`文でリロケーションタイプをチェックし、現在サポートされている`R_AARCH64_ABS64`と`R_AARCH64_ABS32`のリロケーションを適用します。
    - `R_AARCH64_ABS64`: `dst`バイトスライスの`rela.Off`で指定された位置に、`rela.Addend`の値を64ビット整数として書き込みます。
    - `R_AARCH64_ABS32`: `dst`バイトスライスの`rela.Off`で指定された位置に、`rela.Addend`の値を32ビット整数として書き込みます。
    これらの操作は、ELFファイルのバイトオーダー（エンディアン）に従って行われます。

また、`DWARF()`関数も更新され、`.rela.debug_info`セクションのリロケーション処理が`EM_X86_64`だけでなく`EM_AARCH64`にも適用されるようになりました。これにより、AArch64のELFファイルに含まれるデバッグ情報も正しく処理され、デバッガが利用できるようになります。

## 元コミット内容

このコミットは、Goコンパイラの `compile` 関数のクリーンアップを目的としています。主な変更点は以下の通りです。

1.  `defer` ステートメントを用いたクリーンアップ処理を導入し、よりGoらしい（idiomatic）コードスタイルに改善しました。これにより、変数をその最初の使用箇所により近い場所で宣言できるようになり、以前のように最初の `goto` ステートメントの前にまとめて宣言する必要がなくなりました。
2.  従来のコード生成パスを `genlegacy` という独立した関数に分割しました。これは、新しいSSA（Static Single Assignment）ベースのコード生成パスを処理する `genssa` 関数と対をなすものです。

これらの変更は `toolstash -cmp` テストをパスしており、機能的な回帰がないことが確認されています。

## 変更の背景

このコミットの背景には、Goコンパイラの進化とコード品質の向上が挙げられます。

Goコンパイラは、パフォーマンスと保守性の両面で継続的に改善されています。特に、コード生成のバックエンドは、より最適化されたコードを生成するためにSSA（Static Single Assignment）形式への移行が進められていました。SSAは、変数の定義と使用の関係を明確にし、より高度な最適化を可能にする中間表現です。

しかし、SSAベースのコード生成が導入される過渡期には、従来のコード生成パス（レガシーコード生成）も並行して存在していました。`compile` 関数は、これらの両方のパスを処理する必要があり、コードが複雑化する傾向がありました。

このコミットは、以下の課題に対処するために行われました。

*   **コードの可読性と保守性の向上**: 従来の `compile` 関数は、複数の `goto` ステートメントを使用してエラー処理や終了処理を行っていました。これにより、変数の宣言が関数の冒頭に集中し、変数のスコープが広がりすぎて可読性を損ねていました。`defer` の導入により、クリーンアップ処理を関数の終了時に確実に実行できるようになり、`goto` の使用を減らすことでコードの流れがより自然になります。
*   **コード生成パスの明確な分離**: SSAベースのコード生成とレガシーコード生成が混在していると、どちらのパスが実行されているのか、それぞれのパスがどのような役割を担っているのかが分かりにくくなります。`genlegacy` 関数としてレガシーパスを分離することで、コードの構造が明確になり、将来的なSSAへの完全移行やレガシーパスの削除が容易になります。
*   **Goイディオムへの準拠**: `defer` はGo言語の強力な機能の一つであり、リソースの解放やクリーンアップ処理を簡潔かつ安全に記述するためのGoイディオムです。このコミットは、コンパイラ自身のコードをGoのベストプラクティスに合わせることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、`cmd/compile` ディレクトリ以下に実装されています。その中でも `internal/gc` パッケージは、コンパイラの主要なロジック（字句解析、構文解析、型チェック、中間表現の生成、コード生成など）を担っています。`pgen.go` はこのパッケージの一部であり、主にプログラムの最終的なコード生成フェーズに関わります。

### 2. `defer` ステートメント

`defer` はGo言語のキーワードで、`defer` に続く関数呼び出しを、その関数がリターンする直前（パニックが発生した場合も含む）に実行することを保証します。これは、リソースの解放（ファイルクローズ、ロック解除など）やクリーンアップ処理を記述するのに非常に便利です。`defer` を使うことで、関数の複数の終了点（`return` ステートメントやパニック）で同じクリーンアップコードを重複して書く必要がなくなります。

### 3. `goto` ステートメント

`goto` は、プログラムの実行フローを特定のラベルにジャンプさせるステートメントです。C言語などではよく使われますが、コードの可読性を損ね、スパゲッティコードの原因となることがあるため、現代のプログラミングではその使用は推奨されません。Go言語でも `goto` は存在しますが、限定的な状況（例えば、多重ループからの脱出や、エラー処理の共通化）でのみ使用が検討されます。このコミットでは、`goto` の使用を減らし、より構造化された制御フローに移行しています。

### 4. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化で用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されることが保証されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。Goコンパイラは、より効率的なコードを生成するために、従来のAST（Abstract Syntax Tree）ベースのコード生成からSSAベースのコード生成へと移行を進めていました。

### 5. レガシーコード生成とSSAコード生成

Goコンパイラには、歴史的にASTを直接操作してコードを生成する「レガシーコード生成」パスと、SSA形式に変換してからコードを生成する「SSAコード生成」パスの2種類が存在していました。SSAコード生成はより高度な最適化を可能にしますが、すべてのケースでSSAが利用できるわけではなかったり、移行期間中であったりするため、両方のパスが共存していました。

### 6. `toolstash -cmp`

`toolstash -cmp` はGoの開発ツールの一つで、コンパイラの変更が生成されるバイナリコードに影響を与えないことを検証するために使用されます。具体的には、変更前と変更後のコンパイラで同じソースコードをコンパイルし、生成されたバイナリコードが同一であるか（または許容範囲内の差分であるか）を比較します。これにより、コンパイラの内部的なリファクタリングが、ユーザーに提供される最終的な実行ファイルに意図しない変更をもたらさないことを保証します。

## 技術的詳細

このコミットの技術的詳細は、主に `compile` 関数の制御フローの改善と、コード生成ロジックのモジュール化にあります。

### `defer` によるクリーンアップの改善

従来の `compile` 関数では、関数の冒頭で `lno := setlineno(fn)` のように現在の行番号を保存し、関数の複数の終了点（`goto ret`）で `lineno = lno` を実行して行番号を元に戻していました。これは、コンパイル中にエラーが発生した場合でも、正確な行番号情報を保持するために必要な処理でした。

しかし、このパターンは `goto` ステートメントを多用することになり、コードの可読性を低下させます。また、`goto` の前に多くの変数を宣言する必要があり、変数のスコープが不必要に広がるという問題もありました。

このコミットでは、以下の `defer` ステートメントを導入することで、この問題を解決しています。

```go
	defer func(lno int32) {
		lineno = lno
	}(setlineno(fn))
```

このコードは、`compile` 関数が終了する直前に、`setlineno(fn)` で取得した元の行番号を `lineno` グローバル変数に復元することを保証します。これにより、関数内のどこで `return` しても、あるいはパニックが発生しても、クリーンアップ処理が自動的に実行されます。結果として、関数内の複数の `goto ret` ステートメントを単純な `return` に置き換えることが可能になり、コードの線形性が向上し、理解しやすくなりました。

### 変数宣言の局所化

`goto` ステートメントが存在すると、`goto` のターゲットとなるラベルの前に、そのラベル以降で使用されるすべての変数を宣言しておく必要がありました。これは、変数が実際に使用される場所から離れた位置で宣言されることを意味し、コードの可読性を損ねます。

`defer` の導入と `goto` の削減により、多くの変数をその最初の使用箇所により近い場所で宣言できるようになりました。例えば、コミットの差分を見ると、`nod1`, `ptxt`, `pl`, `p`, `n`, `nam`, `gcargs`, `gclocals`, `ssafn` といった変数が関数の冒頭でまとめて宣言されていたのが、それぞれが必要なブロック内で宣言されるように変更されています。これにより、変数のスコープが適切に制限され、コードの理解が容易になります。

### コード生成パスの分離 (`genlegacy` の導入)

Goコンパイラは、SSAベースのコード生成 (`genssa`) を導入していましたが、すべての関数がSSAでコンパイルされるわけではありませんでした。`compile` 関数は、SSAでコンパイル可能な場合は `genssa` を呼び出し、そうでない場合は従来のコード生成ロジックを実行していました。

このコミットでは、従来のコード生成ロジックを `genlegacy` という新しい関数に抽出しました。

```go
	if ssafn != nil {
		genssa(ssafn, ptxt, gcargs, gclocals)
		ssafn.Free()
	} else {
		genlegacy(ptxt, gcargs, gclocals)
	}
}

// genlegacy compiles Curfn using the legacy non-SSA code generator.
func genlegacy(ptxt *obj.Prog, gcargs, gclocals *Sym) {
	Genlist(Curfn.Func.Enter)
	Genlist(Curfn.Nbody)
	gclean()
	checklabels()
	if nerrors != 0 {
		return
	}
	// ... (rest of the legacy code generation logic)
}
```

この変更により、`compile` 関数はSSAとレガシーのどちらのコード生成パスを使用するかを明確に分岐させ、それぞれのパスの具体的な実装は独立した関数に委譲する形になりました。これは、以下の利点をもたらします。

*   **モジュール性の向上**: コード生成のロジックが `compile` 関数から分離され、`genssa` と `genlegacy` という2つの独立したモジュールとして扱われるようになりました。これにより、それぞれの関数の責任が明確になり、理解しやすくなります。
*   **保守性の向上**: レガシーコード生成パスにバグが見つかった場合や、SSAコード生成パスをさらに改善する場合でも、それぞれの関数内で変更を完結させやすくなります。
*   **将来的な拡張性**: 将来的に新しいコード生成パスが導入された場合でも、`compile` 関数は単に適切なコード生成関数を呼び出すだけで済み、関数の複雑性が増大するのを防ぎます。また、レガシーパスが不要になった際には、`genlegacy` 関数を削除するだけで済みます。

## コアとなるコードの解説

### `defer` によるクリーンアップと `goto` の排除

最も顕著な変更は、`compile` 関数の冒リーンに導入された `defer` ステートメントです。

```go
	defer func(lno int32) {
		lineno = lno
	}(setlineno(fn))
```

これは、`compile` 関数が実行される前に現在の行番号を保存し、関数が終了する際にその行番号を `lineno` グローバル変数に復元するためのものです。以前は、関数の複数の終了点（エラー発生時など）で `goto ret` を使用し、`ret` ラベルの直前で `lineno = lno` を実行していました。`defer` を使うことで、このクリーンアップ処理が関数の終了時に自動的に、かつ確実に実行されるようになり、`goto` ステートメントを排除することができました。これにより、コードのフローがより直線的になり、理解しやすくなっています。

### 変数宣言の最適化

`goto` ステートメントが排除されたことで、変数の宣言位置を最適化できるようになりました。以前は、`goto` のターゲットとなるラベルの前に、そのラベル以降で使われるすべての変数を宣言する必要がありました。これは、変数が実際に使われる場所から遠く離れて宣言されることを意味し、変数のライフタイムが不必要に長くなり、コードの可読性を低下させていました。

このコミットでは、`var nod1 Node` や `var ptxt *obj.Prog` といった変数の宣言が削除され、それぞれの変数が実際に初期化され、使用されるブロック内で `nod1 := Node{}` や `ptxt := Thearch.Gins(...)` のように宣言されるようになりました。これにより、変数のスコープが最小限に抑えられ、コードの局所性が向上し、どの変数がどこで使われているのかがより明確になります。

### `genlegacy` 関数の分離

`compile` 関数は、GoコンパイラのSSAバックエンドが有効な場合は `genssa` を呼び出し、そうでない場合は従来のコード生成ロジックを実行していました。このコミットでは、従来のコード生成ロジックを `genlegacy` という独立した関数に切り出しました。

```go
	if ssafn != nil {
		genssa(ssafn, ptxt, gcargs, gclocals)
		ssafn.Free()
	} else {
		genlegacy(ptxt, gcargs, gclocals)
	}
```

この変更により、`compile` 関数の役割が「SSAまたはレガシーのどちらかのコード生成パスを選択し、適切な関数を呼び出す」という高レベルなものに簡素化されました。具体的なコード生成の詳細は `genssa` または `genlegacy` にカプセル化され、`compile` 関数の複雑性が軽減されました。これは、コードのモジュール性を高め、将来的なSSAへの完全移行やレガシーコードの削除を容易にするための重要なステップです。

# [インデックス 25281] ファイルの概要

このコミットは、Goコンパイラおよびオブジェクトコード生成において、スタックフレームの固定部分のサイズに関する知識を一元化することを目的としています。特に、ppc64leアーキテクチャにおける共有ライブラリのABI要件に対応するため、スタックフレームのオフセット計算ロジックを`Ctxt.FixedFrameSize()`という単一の関数に集約しています。これにより、コードの重複を排除し、将来的なアーキテクチャ固有の変更への対応を容易にしています。

## 変更の背景

この変更の主な背景は、ppc64leアーキテクチャにおける共有ライブラリのサポート準備です。ppc64leのABI（Application Binary Interface）では、TOC（Table Of Contents）ポインタがレジスタR1（スタックポインタ）から24バイトのオフセット位置に存在することが義務付けられています。これは、Goの関数が呼び出された際に確保するスタックフレームの最小サイズに影響を与えます。

以前のGoコンパイラでは、スタックフレームの固定部分のサイズ（特にリンクレジスタの保存などによって生じるオフセット）に関するロジックが、`HasLinkRegister()`関数とポインタサイズ（`Widthptr`）の直接加算によって、`src/cmd/compile/internal/gc/cgen.go`のような複数のファイルに分散していました。この分散したロジックは、特定のアーキテクチャ（ppc64leなど）のABI要件に対応する際に、変更が複雑になり、エラーを引き起こす可能性がありました。

このコミットは、ppc64leの共有ライブラリサポートに向けた「パート2a」として位置づけられており、スタックフレームの固定部分のサイズに関する知識を一元化することで、将来的なABI変更や新しいアーキテクチャのサポートをより容易にすることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **Goコンパイラとアセンブラ (`cmd/compile`, `cmd/internal/obj`)**:
    *   `cmd/compile`はGo言語のソースコードを中間表現に変換し、最終的に各アーキテクチャのアセンブリコードを生成するGoのコンパイラです。
    *   `cmd/internal/obj`は、Goのツールチェーン内でアセンブリコードの生成やオブジェクトファイルのリンクを扱うための共通の基盤を提供するパッケージです。アセンブラやリンカの低レベルな処理を抽象化します。
*   **スタックフレーム (Stack Frame)**:
    *   関数が呼び出されるたびに、プログラムのスタック上に確保されるメモリ領域です。この領域には、関数の引数、ローカル変数、呼び出し元のリターンアドレス、保存されたレジスタの値などが格納されます。
    *   スタックフレームは、関数が実行を終えると解放されます。
*   **固定スタックフレームサイズ (Fixed Stack Frame Size)**:
    *   スタックフレームのうち、関数が実行される前に、アーキテクチャのABIやコンパイラの規約によって固定的に確保される部分のサイズを指します。これには、リターンアドレスの保存領域や、特定のレジスタの保存領域などが含まれることがあります。
*   **ppc64leアーキテクチャ**:
    *   IBM PowerPC 64-bit Little Endianの略で、高性能コンピューティングやサーバー分野で利用されるCPUアーキテクチャの一つです。
    *   他のアーキテクチャと同様に、独自のABIを持ち、関数呼び出し規約やスタックフレームのレイアウトに特定のルールがあります。
*   **ABI (Application Binary Interface)**:
    *   アプリケーションバイナリインターフェースは、オペレーティングシステムとプログラム、またはプログラムの異なるモジュール（例えば、共有ライブラリと実行ファイル）の間で、バイナリレベルでの互換性を保証するための取り決めです。
    *   これには、関数呼び出し規約（引数の渡し方、戻り値の受け取り方）、レジスタの使用規約、データ型のメモリ上での表現、スタックフレームのレイアウトなどが含まれます。ABIに準拠することで、異なるコンパイラでコンパイルされたコードや、異なる言語で書かれたコードが相互に連携できるようになります。
*   **TOCポインタ (Table Of Contents Pointer)**:
    *   ppc64leなどの一部のアーキテクチャで、グローバルデータや関数へのアクセスを効率的に行うために使用されるポインタです。特に共有ライブラリにおいて、コードがロードされるアドレスに依存しないように、TOCを介してシンボルにアクセスします。
    *   ppc64leのABIでは、TOCポインタが特定のレジスタ（R2）に保持され、さらにスタック上の特定のオフセット（R1+24）からもアクセス可能であることが義務付けられています。
*   **リンクレジスタ (Link Register)**:
    *   一部のCPUアーキテクチャ（ARM, PowerPCなど）に存在する特殊なレジスタで、関数呼び出し時に呼び出し元のリターンアドレスを一時的に保持します。
    *   関数が別の関数を呼び出す場合、現在のリンクレジスタの内容をスタックに保存し、新しいリターンアドレスをリンクレジスタに格納する必要があります。これにより、関数が戻る際に正しいアドレスに戻ることができます。x86/amd64アーキテクチャでは、リターンアドレスは直接スタックにプッシュされます。
*   **Widthptr**:
    *   Goのコンパイラ内部で使用される定数で、ポインタのサイズ（バイト単位）を表します。64ビットシステムでは8、32ビットシステムでは4となります。

## 技術的詳細

このコミットの核心は、Goコンパイラがスタックフレームの固定部分のサイズを決定する方法を一元化することにあります。

1.  **`FixedFrameSize()`メソッドの導入**:
    *   `src/cmd/internal/obj/link.go`ファイル内の`Link`構造体に、`FixedFrameSize() int64`という新しいメソッドが追加されました。
    *   このメソッドは、現在のターゲットアーキテクチャ（`ctxt.Arch.Thechar`）に基づいて、スタックフレームの固定部分のサイズを返します。
    *   具体的には、`'6'` (x86) や `'8'` (amd64) のようなリンクレジスタをスタックに保存する必要がないアーキテクチャの場合、`0`を返します。
    *   それ以外のアーキテクチャ（ppc64leなど、リンクレジスタを使用するアーキテクチャ）の場合、`int64(ctxt.Arch.Ptrsize)`、つまりポインタのサイズを返します。これは、リターンアドレスを保存するためにスタック上にポインタ分の領域が必要であることを意味します。
    *   このメソッドの導入により、スタックフレームの固定サイズに関する知識が`obj/link.go`に集約され、コンパイラの他の部分はこのメソッドを呼び出すだけで適切なサイズを取得できるようになります。

2.  **既存ロジックの置き換え**:
    *   以前は、スタックオフセットの計算において、`HasLinkRegister()`関数（リンクレジスタを持つアーキテクチャかどうかを判定する関数）の戻り値と`Widthptr`（ポインタサイズ）を直接加算する形で、アーキテクチャ固有のオフセットが計算されていました。
    *   このコミットでは、`src/cmd/compile/internal/gc/cgen.go`、`src/cmd/compile/internal/gc/gsubr.go`、`src/cmd/compile/internal/ppc64/ggen.go`、`src/cmd/internal/obj/ppc64/asm9.go`、`src/cmd/internal/obj/ppc64/obj9.go`といった複数のファイルに散らばっていたこれらの計算箇所が、新しく導入された`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。
    *   特に`src/cmd/compile/internal/gc/cgen.go`からは`HasLinkRegister()`関数自体が削除され、その役割は`FixedFrameSize()`に引き継がれました。

3.  **ppc64leへの影響**:
    *   ppc64leアーキテクチャでは、ABIによってTOCポインタがスタック上の特定のオフセット（R1+24）に存在することが義務付けられています。このため、Goの関数が共有ライブラリとしてコンパイルされる場合、このABI要件を満たすためにスタックフレームのレイアウトを調整する必要があります。
    *   `FixedFrameSize()`の導入により、ppc64leのようなアーキテクチャでは、ポインタサイズ分の固定オフセットが常にスタックフレームに考慮されるようになります。これにより、TOCポインタの配置に必要な追加のスタック領域が暗黙的に確保され、ABIへの準拠が容易になります。

この変更は、Goコンパイラのコードベースの保守性を大幅に向上させるとともに、異なるアーキテクチャのABI要件への対応をより柔軟かつ正確に行うための基盤を築いています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/cmd/internal/obj/link.go`**:
    *   `Link`構造体に`FixedFrameSize()`メソッドが追加されました。このメソッドが、アーキテクチャに基づいて固定スタックフレームサイズを計算する中心的なロジックを担います。

    ```go
    // The smallest possible offset from the hardware stack pointer to a local
    // variable on the stack. Architectures that use a link register save its value
    // on the stack in the function prologue and so always have a pointer between
    // the hardware stack pointer and the local variable area.
    func (ctxt *Link) FixedFrameSize() int64 {
        switch ctxt.Arch.Thechar {
        case '6', '8': // x86, amd64
            return 0
        default: // Other architectures, e.g., ppc64le, arm
            return int64(ctxt.Arch.Ptrsize)
        }
    }
    ```

*   **`src/cmd/compile/internal/gc/cgen.go`**:
    *   `HasLinkRegister()`関数の呼び出しと`Widthptr`の直接加算によるスタックオフセット計算が、`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。
    *   例:
        ```diff
        -	a.Offset = 0
        -	if HasLinkRegister() {
        -		a.Offset += int64(Widthptr)
        -	}
        +	a.Offset = Ctxt.FixedFrameSize()
        ```
    *   `HasLinkRegister()`関数自体が削除されました。

*   **`src/cmd/compile/internal/gc/gsubr.go`**:
    *   同様に、スタックオフセット計算が`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。

    ```diff
    -	if HasLinkRegister() {
    -		n.Xoffset += int64(Ctxt.Arch.Ptrsize)
    -	}
    +	n.Xoffset += Ctxt.FixedFrameSize()
    ```

*   **`src/cmd/compile/internal/ppc64/ggen.go`**:
    *   ppc64le固有のコード生成において、スタックオフセット計算が`gc.Ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	p = appendpp(p, ppc64.AMOVD, obj.TYPE_REG, ppc64.REGZERO, 0, obj.TYPE_MEM, ppc64.REGSP, 8+frame+lo+i)
    +	p = appendpp(p, ppc64.AMOVD, obj.TYPE_REG, ppc64.REGZERO, 0, obj.TYPE_MEM, ppc64.REGSP, gc.Ctxt.FixedFrameSize()+frame+lo+i)
    ```

*   **`src/cmd/internal/obj/ppc64/asm9.go`**:
    *   ppc64leのアセンブラコード生成において、スタックオフセット計算が`ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	ctxt.Instoffset = int64(ctxt.Autosize) + a.Offset + 8
    +	ctxt.Instoffset = int64(ctxt.Autosize) + a.Offset + ctxt.FixedFrameSize()
    ```

*   **`src/cmd/internal/obj/ppc64/obj9.go`**:
    *   ppc64leのオブジェクトコード生成において、スタックフレームサイズの調整が`ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	autosize += 8
    +	autosize += int32(ctxt.FixedFrameSize())
    ```

## コアとなるコードの解説

`FixedFrameSize()`メソッドは、Goのコンパイラとリンカがスタックフレームの固定部分のサイズを決定するための、アーキテクチャに依存しない単一のインターフェースを提供します。

*   **一元化されたロジック**: 以前は、リンクレジスタの有無によってスタックオフセットを調整するロジックがコンパイラの複数の箇所に散らばっていました。`FixedFrameSize()`の導入により、このロジックが`obj/link.go`に集約され、Goツールチェーン全体でスタックフレームの固定部分のサイズに関する「真実の情報源」となります。
*   **ABIへの準拠**: ppc64leのような特定のABI要件を持つアーキテクチャでは、関数呼び出し時にリターンアドレスやTOCポインタなどの情報をスタック上の特定の場所に保存する必要があります。`FixedFrameSize()`は、これらの要件を満たすために必要な最小限の固定スタック領域を正確に報告します。例えば、リンクレジスタを持つアーキテクチャでは、リターンアドレスを保存するためにポインタサイズ分の領域が固定的に確保されます。
*   **保守性と拡張性**: この変更により、新しいアーキテクチャのサポートや既存アーキテクチャのABI変更があった場合でも、`FixedFrameSize()`メソッド内のロジックを更新するだけで、コンパイラ全体にその変更を反映させることができます。これにより、コードの保守性が向上し、将来的な拡張が容易になります。
*   **コードの簡素化**: `HasLinkRegister()`のようなアーキテクチャ固有の条件分岐がコンパイラの多くの箇所から削除され、より簡潔で読みやすいコードになりました。

    *   ppc64leなどの一部のアーキテクチャで、グローバルデータや関数へのアクセスを効率的に行うために使用されるポインタです。特に共有ライブラリにおいて、コードがロードされるアドレスに依存しないように、TOCを介してシンボルにアクセスします。
    *   ppc64leのABIでは、TOCポインタが特定のレジスタ（R2）に保持され、さらにスタック上の特定のオフセット（R1+24）からもアクセス可能であることが義務付けられています。
*   **リンクレジスタ (Link Register)**:
    *   一部のCPUアーキテクチャ（ARM, PowerPCなど）に存在する特殊なレジスタで、関数呼び出し時に呼び出し元のリターンアドレスを一時的に保持します。
    *   関数が別の関数を呼び出す場合、現在のリンクレジスタの内容をスタックに保存し、新しいリターンアドレスをリンクレジスタに格納する必要があります。これにより、関数が戻る際に正しいアドレスに戻ることができます。x86/amd64アーキテクチャでは、リターンアドレスは直接スタックにプッシュされます。
*   **Widthptr**:
    *   Goのコンパイラ内部で使用される定数で、ポインタのサイズ（バイト単位）を表します。64ビットシステムでは8、32ビットシステムでは4となります。

## 技術的詳細

このコミットの核心は、Goコンパイラがスタックフレームの固定部分のサイズを決定する方法を一元化することにあります。

1.  **`FixedFrameSize()`メソッドの導入**:
    *   `src/cmd/internal/obj/link.go`ファイル内の`Link`構造体に、`FixedFrameSize() int64`という新しいメソッドが追加されました。
    *   このメソッドは、現在のターゲットアーキテクチャ（`ctxt.Arch.Thechar`）に基づいて、スタックフレームの固定部分のサイズを返します。
    *   具体的には、`'6'` (x86) や `'8'` (amd64) のようなリンクレジスタをスタックに保存する必要がないアーキテクチャの場合、`0`を返します。
    *   それ以外のアーキテクチャ（ppc64leなど、リンクレジスタを使用するアーキテクチャ）の場合、`int64(ctxt.Arch.Ptrsize)`、つまりポインタのサイズを返します。これは、リターンアドレスを保存するためにスタック上にポインタ分の領域が必要であることを意味します。
    *   このメソッドの導入により、スタックフレームの固定サイズに関する知識が`obj/link.go`に集約され、コンパイラの他の部分はこのメソッドを呼び出すだけで適切なサイズを取得できるようになります。

2.  **既存ロジックの置き換え**:
    *   以前は、スタックオフセットの計算において、`HasLinkRegister()`関数（リンクレジスタを持つアーキテクチャかどうかを判定する関数）の戻り値と`Widthptr`（ポインタサイズ）を直接加算する形で、アーキテクチャ固有のオフセットが計算されていました。
    *   このコミットでは、`src/cmd/compile/internal/gc/cgen.go`、`src/cmd/compile/internal/gc/gsubr.go`、`src/cmd/compile/internal/ppc64/ggen.go`、`src/cmd/internal/obj/ppc64/asm9.go`、`src/cmd/internal/obj/ppc64/obj9.go`といった複数のファイルに散らばっていたこれらの計算箇所が、新しく導入された`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。
    *   特に`src/cmd/compile/internal/gc/cgen.go`からは`HasLinkRegister()`関数自体が削除され、その役割は`FixedFrameSize()`に引き継がれました。

3.  **ppc64leへの影響**:
    *   ppc64leアーキテクチャでは、ABIによってTOCポインタがスタック上の特定のオフセット（R1+24）に存在することが義務付けられています。このため、Goの関数が共有ライブラリとしてコンパイルされる場合、このABI要件を満たすためにスタックフレームのレイアウトを調整する必要があります。
    *   `FixedFrameSize()`の導入により、ppc64leのようなアーキテクチャでは、ポインタサイズ分の固定オフセットが常にスタックフレームに考慮されるようになります。これにより、TOCポインタの配置に必要な追加のスタック領域が暗黙的に確保され、ABIへの準拠が容易になります。

この変更は、Goコンパイラのコードベースの保守性を大幅に向上させるとともに、異なるアーキテクチャのABI要件への対応をより柔軟かつ正確に行うための基盤を築いています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/cmd/internal/obj/link.go`**:
    *   `Link`構造体に`FixedFrameSize()`メソッドが追加されました。このメソッドが、アーキテクチャに基づいて固定スタックフレームサイズを計算する中心的なロジックを担います。

    ```go
    // The smallest possible offset from the hardware stack pointer to a local
    // variable on the stack. Architectures that use a link register save its value
    // on the stack in the function prologue and so always have a pointer between
    // the hardware stack pointer and the local variable area.
    func (ctxt *Link) FixedFrameSize() int64 {
        switch ctxt.Arch.Thechar {
        case '6', '8': // x86, amd64
            return 0
        default: // Other architectures, e.g., ppc64le, arm
            return int64(ctxt.Arch.Ptrsize)
        }
    }
    ```

*   **`src/cmd/compile/internal/gc/cgen.go`**:
    *   `HasLinkRegister()`関数の呼び出しと`Widthptr`の直接加算によるスタックオフセット計算が、`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。
    *   例:
        ```diff
        -	a.Offset = 0
        -	if HasLinkRegister() {
        -		a.Offset += int64(Widthptr)
        -	}
        +	a.Offset = Ctxt.FixedFrameSize()
        ```
    *   `HasLinkRegister()`関数自体が削除されました。

*   **`src/cmd/compile/internal/gc/gsubr.go`**:
    *   同様に、スタックオフセット計算が`Ctxt.FixedFrameSize()`の呼び出しに置き換えられました。

    ```diff
    -	if HasLinkRegister() {
    -		n.Xoffset += int64(Ctxt.Arch.Ptrsize)
    -	}
    +	n.Xoffset += Ctxt.FixedFrameSize()
    ```

*   **`src/cmd/compile/internal/ppc64/ggen.go`**:
    *   ppc64le固有のコード生成において、スタックオフセット計算が`gc.Ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	p = appendpp(p, ppc64.AMOVD, obj.TYPE_REG, ppc64.REGZERO, 0, obj.TYPE_MEM, ppc64.REGSP, 8+frame+lo+i)
    +	p = appendpp(p, ppc64.AMOVD, obj.TYPE_REG, ppc64.REGZERO, 0, obj.TYPE_MEM, ppc64.REGSP, gc.Ctxt.FixedFrameSize()+frame+lo+i)
    ```

*   **`src/cmd/internal/obj/ppc64/asm9.go`**:
    *   ppc64leのアセンブラコード生成において、スタックオフセット計算が`ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	ctxt.Instoffset = int64(ctxt.Autosize) + a.Offset + 8
    +	ctxt.Instoffset = int64(ctxt.Autosize) + a.Offset + ctxt.FixedFrameSize()
    ```

*   **`src/cmd/internal/obj/ppc64/obj9.go`**:
    *   ppc64leのオブジェクトコード生成において、スタックフレームサイズの調整が`ctxt.FixedFrameSize()`を使用するように変更されました。

    ```diff
    -	autosize += 8
    +	autosize += int32(ctxt.FixedFrameSize())
    ```

## コアとなるコードの解説

`FixedFrameSize()`メソッドは、Goのコンパイラとリンカがスタックフレームの固定部分のサイズを決定するための、アーキテクチャに依存しない単一のインターフェースを提供します。

*   **一元化されたロジック**: 以前は、リンクレジスタの有無によってスタックオフセットを調整するロジックがコンパイラの複数の箇所に散らばっていました。`FixedFrameSize()`の導入により、このロジックが`obj/link.go`に集約され、Goツールチェーン全体でスタックフレームの固定部分のサイズに関する「真実の情報源」となります。
*   **ABIへの準拠**: ppc64leのような特定のABI要件を持つアーキテクチャでは、関数呼び出し時にリターンアドレスやTOCポインタなどの情報をスタック上の特定の場所に保存する必要があります。`FixedFrameSize()`は、これらの要件を満たすために必要な最小限の固定スタック領域を正確に報告します。例えば、リンクレジスタを持つアーキテクチャでは、リターンアドレスを保存するためにポインタサイズ分の領域が固定的に確保されます。
*   **保守性と拡張性**: この変更により、新しいアーキテクチャのサポートや既存アーキテクチャのABI変更があった場合でも、`FixedFrameSize()`メソッド内のロジックを更新するだけで、コンパイラ全体にその変更を反映させることができます。これにより、コードの保守性が向上し、将来的な拡張が容易になります。
*   **コードの簡素化**: `HasLinkRegister()`のようなアーキテクチャ固有の条件分岐がコンパイラの多くの箇所から削除され、より簡潔で読みやすいコードになりました。

このコミットは、Goのクロスプラットフォーム対応と、低レベルなシステムプログラミングにおける正確なスタック管理の重要性を示す良い例です。

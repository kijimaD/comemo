# [インデックス 23161] ファイルの概要

このコミットは、Go言語の `crypto/x509` パッケージにおけるX.509証明書のパースと検証の挙動を変更するものです。特に、未知のクリティカル拡張を持つ証明書の扱いが改善され、パース時にエラーを発生させるのではなく、検証時にその未知の拡張を検出してエラーとするように変更されました。これにより、TLSサーバーなどの特定のユースケースにおいて、未知のクリティカル拡張が存在する証明書からSNI（Server Name Indication）などの情報を抽出することが可能になります。

    some cases one wishes to parse and use a certificate that may contain

## 元コミット内容

`crypto/x509: allow parsing of certificates with unknown critical extensions.`

このコミットは、未知のクリティカル拡張を持つ証明書のパースを許可します。以前は、未知のクリティカル拡張はパースエラーを引き起こしていました。しかし、TLSサーバーで証明書を使用する場合など、これらの拡張を含む証明書をパースして使用したい場合があります。例えば、クライアントがクリティカル拡張を理解しているかどうかはクライアント側の問題ですが、サーバーは証明書からSNI値などをパースしたいと考えるでしょう。

## 変更の背景

X.509証明書には、その証明書の利用方法や制約を定義する「拡張」が含まれています。これらの拡張には「クリティカル」フラグが設定されている場合があります。X.509の仕様では、クリティカルな拡張が理解できない場合、その証明書は無効とみなされ、処理を続行してはならないと定められています。これはセキュリティ上の重要な要件であり、証明書が意図しない方法で利用されることを防ぐためのものです。

Go言語の `crypto/x509` パッケージでは、以前は `ParseCertificate` 関数が証明書をパースする際に、未知のクリティカル拡張に遭遇すると即座にパースエラーを返していました。しかし、この厳格な挙動は、特定のユースケースにおいて不都合が生じることがありました。

例えば、TLSサーバーがクライアントから提示された証明書を処理するシナリオを考えます。サーバーは、クライアントが提示した証明書からSNI（Server Name Indication）などの情報を抽出したい場合があります。SNIは、単一のIPアドレスで複数のドメインをホストする際に、クライアントがどのドメインに接続しようとしているかをサーバーに伝えるためのTLS拡張です。この情報は、証明書自体の検証が成功するかどうかにかかわらず、サーバーが適切な証明書を選択するために必要となることがあります。

もし証明書にサーバーが理解できない未知のクリティカル拡張が含まれていた場合、従来の挙動では `ParseCertificate` がエラーを返し、SNIなどの情報すら抽出できませんでした。しかし、この未知のクリティカル拡張がクライアント側で適切に処理されるべきものであり、サーバー側でのSNI抽出には影響しない場合、サーバーは証明書をパースし、SNI情報を取得したいと考えるのが自然です。

このコミットは、このような現実的なニーズに対応するために導入されました。パースと検証のフェーズを分離することで、未知のクリティカル拡張があっても証明書の基本的な情報を抽出できるようにし、その上で、X.509のセキュリティ要件に従って検証フェーズで適切に拒否するという、より柔軟なアプローチを提供します。

## 前提知識の解説

### X.509 証明書

X.509は、公開鍵証明書の標準フォーマットを定義するITU-T（国際電気通信連合電気通信標準化部門）の勧告です。インターネット上での身元確認や暗号化通信（TLS/SSLなど）において広く利用されています。X.509証明書は、公開鍵と、その公開鍵の所有者に関する情報（名前、組織など）、そしてその情報を保証する認証局（CA）のデジタル署名を含んでいます。

### 証明書拡張 (Certificate Extensions)

X.509 v3証明書では、「拡張 (Extensions)」という概念が導入されました。これにより、証明書に標準化された、またはカスタムの追加情報を柔軟に含めることができるようになりました。拡張は、証明書の用途（例：鍵の使用目的）、ポリシー、代替名（例：複数のドメイン名）、証明書失効リスト（CRL）の配布点など、多岐にわたる情報を提供します。

各拡張は、以下の要素で構成されます。
*   **OID (Object Identifier)**: 拡張の種類を一意に識別する数値のシーケンス。
*   **Critical フラグ**: この拡張が「クリティカル」であるか「非クリティカル」であるかを示すブール値。
*   **Value**: 拡張の実際のデータ。

### クリティカル拡張 (Critical Extensions) と非クリティカル拡張 (Non-Critical Extensions)

拡張の「Critical」フラグは、その拡張が証明書を処理するアプリケーションにとってどれほど重要であるかを示します。

*   **クリティカル拡張 (Critical Extensions)**:
    *   このフラグが `TRUE` に設定されている場合、証明書を処理するアプリケーションは、その拡張を**理解し、適切に処理できなければなりません**。
    *   もしアプリケーションがクリティカル拡張を理解できない、または処理できない場合、X.509の仕様により、その証明書は**無効とみなされ、拒否されなければなりません**。これは、未知のクリティカル拡張が証明書のセキュリティポリシーや利用方法に根本的な影響を与える可能性があるため、安全側に倒した設計です。
    *   例: `Basic Constraints` (証明書がCAであるか否か、パス長の制約など)、`Key Usage` (鍵の用途)。

*   **非クリティカル拡張 (Non-Critical Extensions)**:
    *   このフラグが `FALSE` に設定されている場合、アプリケーションはその拡張を理解できなくても、証明書の処理を続行できます。
    *   理解できない非クリティカル拡張は無視しても構いません。
    *   例: `Subject Alternative Name` (SAN、証明書がカバーする追加のドメイン名やIPアドレス)、`Authority Information Access` (CA証明書やOCSPレスポンダーの場所)。

### SNI (Server Name Indication)

SNIは、TLSプロトコルの拡張であり、クライアントがTLSハンドシェイクの初期段階で接続しようとしているホスト名（ドメイン名）をサーバーに伝えるメカニズムです。これにより、単一のIPアドレスとポートで複数のウェブサイトをホストするサーバー（バーチャルホスティング）が、クライアントが要求しているドメイン名に基づいて適切なSSL/TLS証明書を提示できるようになります。SNIは、証明書の内容そのものではなく、TLSハンドシェイクの一部として送信される情報ですが、サーバーが適切な証明書を選択する際には、証明書内のドメイン名情報（Subject Alternative Nameなど）と照合されます。

### Go言語の `crypto/x509` パッケージ

`crypto/x509` パッケージは、Go言語におけるX.509証明書のパース、検証、生成のための標準ライブラリです。このパッケージは、証明書の構造をGoのデータ構造にマッピングし、証明書の署名検証、有効期限チェック、証明書パスの構築と検証など、X.509証明書に関連する様々な機能を提供します。

## 技術的詳細

このコミットの核心は、X.509証明書における「未知のクリティカル拡張」の取り扱いを変更することにあります。従来の `crypto/x509` パッケージでは、`ParseCertificate` 関数が証明書をASN.1形式からGoの `Certificate` 構造体にデコードする際に、もしクリティカルとマークされた拡張がパッケージによって認識または処理できないものであった場合、即座にエラーを返していました。この挙動は、X.509の仕様に厳密に従ったものでしたが、特定のシナリオで柔軟性に欠けるという問題がありました。

この変更により、以下の点が技術的に改善されました。

1.  **パースと検証の分離**:
    *   `ParseCertificate` 関数は、未知のクリティカル拡張に遭遇してもエラーを返さなくなりました。その代わり、これらの拡張のOID（Object Identifier）を `Certificate` 構造体の新しいフィールド `UnhandledCriticalExtensions` に記録します。
    *   証明書の検証を担当する `Certificate.Verify` メソッドが、この `UnhandledCriticalExtensions` フィールドをチェックするようになりました。もしこのフィールドが空でなければ（つまり、未知のクリティカル拡張が存在すれば）、`Verify` メソッドは `UnhandledCriticalExtension` エラーを返して検証を失敗させます。
    *   この分離により、アプリケーションは、たとえ証明書が最終的に検証に失敗するとしても、まず証明書をパースしてその内容（例えば、Subject Alternative Nameに含まれるSNI関連のホスト名）を検査できるようになります。

2.  **`Certificate` 構造体の拡張**:
    *   `src/crypto/x509/x509.go` 内の `Certificate` 構造体に、`UnhandledCriticalExtensions []asn1.ObjectIdentifier` という新しいフィールドが追加されました。
    *   このフィールドは、パース時に処理されなかったクリティカル拡張のOIDを格納するために使用されます。

3.  **柔軟なハンドリングの提供**:
    *   この変更は、パッケージのユーザーが未知のクリティカル拡張を「自分で処理する」ためのメカニズムも提供します。もしアプリケーションが特定の未知のクリティカル拡張を独自に解釈し、その意味を理解できる場合、`Certificate.Extensions` からその拡張の生データを抽出し、処理することができます。
    *   処理が完了した後、ユーザーは `Certificate.UnhandledCriticalExtensions` スライスから該当するOIDを削除することで、`Certificate.Verify` がその拡張を「処理済み」とみなし、検証を続行できるようにすることができます。ただし、これは高度なユースケースであり、X.509のセキュリティモデルを十分に理解した上で行う必要があります。

4.  **テストケースの更新**:
    *   `src/crypto/x509/x509_test.go` 内の `TestUnknownCriticalExtension` テストが更新され、新しい挙動を反映しています。
    *   テストは、未知のクリティカル拡張を含む証明書が `ParseCertificate` によってエラーなくパースされることを確認します。
    *   その後、`Certificate.Verify` が `UnhandledCriticalExtension` エラーを返すことを確認します。
    *   さらに、`UnhandledCriticalExtensions` フィールドをクリアした後に `Verify` を呼び出すと、エラーなく検証が成功することもテストしています。これは、ユーザーが独自に拡張を処理できるという柔軟性を示しています。

この変更は、X.509の厳格なセキュリティモデルを維持しつつ、特定のアプリケーションシナリオにおける実用性と柔軟性を向上させるためのものです。

## コアとなるコードの解説

### `src/crypto/x509/verify.go`

*   **変更点**: `Certificate.Verify` メソッドの冒頭に、`c.UnhandledCriticalExtensions` スライスの長さが0より大きい場合に `UnhandledCriticalExtension{}` エラーを返す条件が追加されました。
*   **解説**: これは、パース時に未知のクリティカル拡張が検出され、`Certificate` 構造体の `UnhandledCriticalExtensions` フィールドに記録された場合、証明書の検証を意図的に失敗させるための変更です。X.509の仕様に従い、理解できないクリティカル拡張を持つ証明書は信頼できないと判断されます。ただし、`systemVerify` が呼び出される場合はこのチェックはスキップされます。これは、OSのライブラリが独自の拡張処理メカニズムを持っている可能性があるためです。

### `src/crypto/x509/x509.go`

*   **`Certificate` 構造体へのフィールド追加**:
    *   `UnhandledCriticalExtensions []asn1.ObjectIdentifier` が追加されました。このフィールドは、`ParseCertificate` が処理できなかったクリティカル拡張のOIDを保持します。これにより、パースエラーを発生させることなく、未知のクリティカル拡張の存在を記録できるようになります。コメントには、ユーザーがこのスライスを操作して、独自に処理した拡張を「処理済み」としてマークできる可能性も示唆されています。

*   **`parseCertificate` 関数内のロジック変更**:
    *   `failIfCritical` というブール変数が `unhandled` にリネームされました。これは、もはや即座にパースを失敗させるのではなく、「処理されていない」状態を示すためです。
    *   様々な拡張タイプ（例: `Subject Alternative Name`、未知の拡張）を処理する `switch` ステートメント内で、以前は `failIfCritical = true` と設定されていた箇所が、`unhandled = true` と設定されるように変更されました。これは、これらの拡張がパッケージによって完全に処理されなかった場合に、その状態をマークするためです。
    *   最も重要な変更は、ループの最後にあるクリティカル拡張のチェック部分です。
        ```diff
        -		if e.Critical && failIfCritical {
        -			return out, UnhandledCriticalExtension{}
        +		if e.Critical && unhandled {
        +			out.UnhandledCriticalExtensions = append(out.UnhandledCriticalExtensions, e.Id)
        		}
        ```
        以前は、拡張がクリティカルであり、かつ `failIfCritical` が `true` であった場合、`ParseCertificate` は `UnhandledCriticalExtension{}` エラーを返してパースを中断していました。
        この変更により、同じ条件（拡張がクリティカルであり、かつ `unhandled` が `true`）の場合でも、エラーを返す代わりに、その拡張のOID (`e.Id`) を `out.UnhandledCriticalExtensions` スライスに追加するようになりました。これにより、パース自体は成功し、証明書の他の部分を読み取ることが可能になります。

## 変更の背景

X.509証明書には、その証明書の利用方法や制約を定義する「拡張」が含まれています。これらの拡張には「クリティカル」フラグが設定されている場合があります。X.509の仕様では、クリティカルな拡張が理解できない場合、その証明書は無効とみなされ、処理を続行してはならないと定められています。これはセキュリティ上の重要な要件であり、証明書が意図しない方法で利用されることを防ぐためのものです。

Go言語の `crypto/x509` パッケージでは、以前は `ParseCertificate` 関数が証明書をASN.1形式からGoの `Certificate` 構造体にデコードする際に、もしクリティカルとマークされた拡張がパッケージによって認識または処理できないものであった場合、即座にエラーを返していました。この厳格な挙動は、特定のユースケースにおいて不都合が生じることがありました。

例えば、TLSサーバーがクライアントから提示された証明書を処理するシナリオを考えます。サーバーは、クライアントが提示した証明書からSNI（Server Name Indication）などの情報を抽出したい場合があります。SNIは、単一のIPアドレスで複数のドメインをホストする際に、クライアントがどのドメインに接続しようとしているかをサーバーに伝えるためのTLS拡張です。この情報は、証明書自体の検証が成功するかどうかにかかわらず、サーバーが適切な証明書を選択するために必要となることがあります。

もし証明書にサーバーが理解できない未知のクリティカル拡張が含まれていた場合、従来の挙動では `ParseCertificate` がエラーを返し、SNIなどの情報すら抽出できませんでした。しかし、この未知のクリティカル拡張がクライアント側で適切に処理されるべきものであり、サーバー側でのSNI抽出には影響しない場合、サーバーは証明書をパースし、SNI情報を取得したいと考えるのが自然です。

このコミットは、このような現実的なニーズに対応するために導入されました。パースと検証のフェーズを分離することで、未知のクリティカル拡張があっても証明書の基本的な情報を抽出できるようにし、その上で、X.509のセキュリティ要件に従って検証フェーズで適切に拒否するという、より柔軟なアプローチを提供します。

## 前提知識の解説

### X.509 証明書

X.509は、公開鍵証明書の標準フォーマットを定義するITU-T（国際電気通信連合電気通信標準化部門）の勧告です。インターネット上での身元確認や暗号化通信（TLS/SSLなど）において広く利用されています。X.509証明書は、公開鍵と、その公開鍵の所有者に関する情報（名前、組織など）、そしてその情報を保証する認証局（CA）のデジタル署名を含んでいます。

### 証明書拡張 (Certificate Extensions)

X.509 v3証明書では、「拡張 (Extensions)」という概念が導入されました。これにより、証明書に標準化された、またはカスタムの追加情報を柔軟に含めることができるようになりました。拡張は、証明書の用途（例：鍵の使用目的）、ポリシー、代替名（例：複数のドメイン名）、証明書失効リスト（CRL）の配布点など、多岐にわたる情報を提供します。

各拡張は、以下の要素で構成されます。
*   **OID (Object Identifier)**: 拡張の種類を一意に識別する数値のシーケンス。
*   **Critical フラグ**: この拡張が「クリティカル」であるか「非クリティカル」であるかを示すブール値。
*   **Value**: 拡張の実際のデータ。

### クリティカル拡張 (Critical Extensions) と非クリティカル拡張 (Non-Critical Extensions)

拡張の「Critical」フラグは、その拡張が証明書を処理するアプリケーションにとってどれほど重要であるかを示します。

*   **クリティカル拡張 (Critical Extensions)**:
    *   このフラグが `TRUE` に設定されている場合、証明書を処理するアプリケーションは、その拡張を**理解し、適切に処理できなければなりません**。
    *   もしアプリケーションがクリティカル拡張を理解できない、または処理できない場合、X.509の仕様により、その証明書は**無効とみなされ、拒否されなければなりません**。これは、未知のクリティカル拡張が証明書のセキュリティポリシーや利用方法に根本的な影響を与える可能性があるため、安全側に倒した設計です。
    *   例: `Basic Constraints` (証明書がCAであるか否か、パス長の制約など)、`Key Usage` (鍵の用途)。

*   **非クリティカル拡張 (Non-Critical Extensions)**:
    *   このフラグが `FALSE` に設定されている場合、アプリケーションはその拡張を理解できなくても、証明書の処理を続行できます。
    *   理解できない非クリティカル拡張は無視しても構いません。
    *   例: `Subject Alternative Name` (SAN、証明書がカバーする追加のドメイン名やIPアドレス)、`Authority Information Access` (CA証明書やOCSPレスポンダーの場所)。

### SNI (Server Name Indication)

SNIは、TLSプロトコルの拡張であり、クライアントがTLSハンドシェイクの初期段階で接続しようとしているホスト名（ドメイン名）をサーバーに伝えるメカニズムです。これにより、単一のIPアドレスとポートで複数のウェブサイトをホストするサーバー（バーチャルホスティング）が、クライアントが要求しているドメイン名に基づいて適切なSSL/TLS証明書を提示できるようになります。SNIは、証明書の内容そのものではなく、TLSハンドシェイクの一部として送信される情報ですが、サーバーが適切な証明書を選択する際には、証明書内のドメイン名情報（Subject Alternative Nameなど）と照合されます。

### Go言語の `crypto/x509` パッケージ

`crypto/x509` パッケージは、Go言語におけるX.509証明書のパース、検証、生成のための標準ライブラリです。このパッケージは、証明書の構造をGoのデータ構造にマッピングし、証明書の署名検証、有効期限チェック、証明書パスの構築と検証など、X.509証明書に関連する様々な機能を提供します。

## 技術的詳細

このコミットの核心は、X.509証明書における「未知のクリティカル拡張」の取り扱いを変更することにあります。従来の `crypto/x509` パッケージでは、`ParseCertificate` 関数が証明書をASN.1形式からGoの `Certificate` 構造体にデコードする際に、もしクリティカルとマークされた拡張がパッケージによって認識または処理できないものであった場合、即座にエラーを返していました。この挙動は、X.509の仕様に厳密に従ったものでしたが、特定のシナリオで柔軟性に欠けるという問題がありました。

この変更により、以下の点が技術的に改善されました。

1.  **パースと検証の分離**:
    *   `ParseCertificate` 関数は、未知のクリティカル拡張に遭遇してもエラーを返さなくなりました。その代わり、これらの拡張のOID（Object Identifier）を `Certificate` 構造体の新しいフィールド `UnhandledCriticalExtensions` に記録します。
    *   証明書の検証を担当する `Certificate.Verify` メソッドが、この `UnhandledCriticalExtensions` フィールドをチェックするようになりました。もしこのフィールドが空でなければ（つまり、未知のクリティカル拡張が存在すれば）、`Verify` メソッドは `UnhandledCriticalExtension` エラーを返して検証を失敗させます。
    *   この分離により、アプリケーションは、たとえ証明書が最終的に検証に失敗するとしても、まず証明書をパースしてその内容（例えば、Subject Alternative Nameに含まれるSNI関連のホスト名）を検査できるようになります。

2.  **`Certificate` 構造体の拡張**:
    *   `src/crypto/x509/x509.go` 内の `Certificate` 構造体に、`UnhandledCriticalExtensions []asn1.ObjectIdentifier` という新しいフィールドが追加されました。
    *   このフィールドは、パース時に処理されなかったクリティカル拡張のOIDを格納するために使用されます。

3.  **柔軟なハンドリングの提供**:
    *   この変更は、パッケージのユーザーが未知のクリティカル拡張を「自分で処理する」ためのメカニズムも提供します。もしアプリケーションが特定の未知のクリティカル拡張を独自に解釈し、その意味を理解できる場合、`Certificate.Extensions` からその拡張の生データを抽出し、処理することができます。
    *   処理が完了した後、ユーザーは `Certificate.UnhandledCriticalExtensions` スライスから該当するOIDを削除することで、`Certificate.Verify` がその拡張を「処理済み」とみなし、検証を続行できるようにすることができます。ただし、これは高度なユースケースであり、X.509のセキュリティモデルを十分に理解した上で行う必要があります。

4.  **テストケースの更新**:
    *   `src/crypto/x509/x509_test.go` 内の `TestUnknownCriticalExtension` テストが更新され、新しい挙動を反映しています。
    *   テストは、未知のクリティカル拡張を含む証明書が `ParseCertificate` によってエラーなくパースされることを確認します。
    *   その後、`Certificate.Verify` が `UnhandledCriticalExtension` エラーを返すことを確認します。
    *   さらに、`UnhandledCriticalExtensions` フィールドをクリアした後に `Verify` を呼び出すと、エラーなく検証が成功することもテストしています。これは、ユーザーが独自に拡張を処理できるという柔軟性を示しています。

この変更は、X.509の厳格なセキュリティモデルを維持しつつ、特定のアプリケーションシナリオにおける実用性と柔軟性を向上させるためのものです。

## コアとなるコードの解説

### `src/crypto/x509/verify.go`

*   **変更点**: `Certificate.Verify` メソッドの冒頭に、`c.UnhandledCriticalExtensions` スライスの長さが0より大きい場合に `UnhandledCriticalExtension{}` エラーを返す条件が追加されました。
*   **解説**: これは、パース時に未知のクリティカル拡張が検出され、`Certificate` 構造体の `UnhandledCriticalExtensions` フィールドに記録された場合、証明書の検証を意図的に失敗させるための変更です。X.509の仕様に従い、理解できないクリティカル拡張を持つ証明書は信頼できないと判断されます。ただし、`systemVerify` が呼び出される場合はこのチェックはスキップされます。これは、OSのライブラリが独自の拡張処理メカニズムを持っている可能性があるためです。

### `src/crypto/x509/x509.go`

*   **`Certificate` 構造体へのフィールド追加**:
    *   `UnhandledCriticalExtensions []asn1.ObjectIdentifier` が追加されました。このフィールドは、`ParseCertificate` が処理できなかったクリティカル拡張のOIDを保持します。これにより、パースエラーを発生させることなく、未知のクリティカル拡張の存在を記録できるようになります。コメントには、ユーザーがこのスライスを操作して、独自に処理した拡張を「処理済み」としてマークできる可能性も示唆されています。

*   **`parseCertificate` 関数内のロジック変更**:
    *   `failIfCritical` というブール変数が `unhandled` にリネームされました。これは、もはや即座にパースを失敗させるのではなく、「処理されていない」状態を示すためです。
    *   様々な拡張タイプ（例: `Subject Alternative Name`、未知の拡張）を処理する `switch` ステートメント内で、以前は `failIfCritical = true` と設定されていた箇所が、`unhandled = true` と設定されるように変更されました。これは、これらの拡張がパッケージによって完全に処理されなかった場合に、その状態をマークするためです。
    *   最も重要な変更は、ループの最後にあるクリティカル拡張のチェック部分です。
        ```diff
        -		if e.Critical && failIfCritical {
        -			return out, UnhandledCriticalExtension{}
        +		if e.Critical && unhandled {
        +			out.UnhandledCriticalExtensions = append(out.UnhandledCriticalExtensions, e.Id)
        		}
        ```
        以前は、拡張がクリティカルであり、かつ `failIfCritical` が `true` であった場合、`ParseCertificate` は `UnhandledCriticalExtension{}` エラーを返してパースを中断していました。
        この変更により、同じ条件（拡張がクリティカルであり、かつ `unhandled` が `true`）の場合でも、エラーを返す代わりに、その拡張のOID (`e.Id`) を `out.UnhandledCriticalExtensions` スライスに追加するようになりました。これにより、パース自体は成功し、証明書の他の部分を読み取ることが可能になります。

### `src/crypto/x509/x509_test.go`

*   **テストロジックの更新**:
    *   テスト証明書の `NotAfter` フィールドが、固定値から `time.Now().AddDate(1, 0, 0)` に変更され、常に将来の日付になるように調整されました。また、`BasicConstraintsValid`, `IsCA`, `KeyUsage`, `ExtKeyUsage` が追加され、より現実的なテスト証明書が生成されるようになりました。
    *   以前は `ParseCertificate` がエラーを返すことを期待していましたが、変更後は `ParseCertificate` がエラーなく成功し、`cert` オブジェクトが返されることを期待するように変更されました。
    *   `cert.Verify` を呼び出し、`UnhandledCriticalExtension` エラーが返されることを確認します。これは、パースは成功したが、未知のクリティカル拡張が存在するため検証は失敗するという新しい挙動をテストしています。
    *   最後に、`cert.UnhandledCriticalExtensions = nil` と設定して、未知のクリティカル拡張が「処理された」状態をシミュレートし、その後に `cert.Verify` がエラーなく成功することを確認します。これは、ユーザーが独自に拡張を処理できるという柔軟性を示す重要なテストケースです。

これらの変更により、Goの `crypto/x509` パッケージは、X.509のセキュリティ要件を維持しつつ、未知のクリティカル拡張を持つ証明書に対するより実用的なアプローチを提供できるようになりました。

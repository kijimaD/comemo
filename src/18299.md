# [インデックス 18299] ファイルの概要

このコミットは、Goランタイムのメモリ管理、特にアロケータ (`malloc.goc`) とガベージコレクタのスイープフェーズ (`mgc0.c`) におけるメモリのゼロクリア処理に関する最適化を扱っています。`malloc.goc` はメモリ確保の主要なロジックを含み、`mgc0.c` はガベージコレクションのマーク＆スイープサイクルのスイープフェーズを担当します。

## 元コミット内容

このコミットは、Goランタイムが2ワード（`2 * sizeof(uintptr)`）サイズのメモリブロックをゼロクリアする方法を最適化することを目的としています。以前の実装では、2ワードのブロックに対して、ゼロクリアが必要であることを示すフラグを設定し、その後すぐにそのフラグをクリアするという無意味な処理が行われていました。特に32ビットシステムでは、この非効率な処理により常に `memclr` が呼び出されていました。この変更は、この冗長な処理を排除し、2ワードブロックのゼロクリアをインプレースで行うことで、効率を向上させます。

## 変更の背景

Goランタイムは、確保されたメモリブロックが使用される前にゼロクリアされることを保証します。これはセキュリティと予測可能性のために重要です。しかし、このコミット以前のGoランタイムのメモリ管理では、特定の小さなメモリブロック、特に2ワードサイズのブロックのゼロクリア処理に非効率なロジックが存在していました。

具体的には、`runtime·mallocgc`（メモリ確保）や `runtime·free`（メモリ解放）、そしてガベージコレクションのスイープフェーズ (`sweepspan`) において、メモリブロックがゼロクリアされるべきかどうかを判断するためのフラグ（`0xfeedfeedfeedfeedll` や `0xdeaddeaddeaddeadll` といったマジックナンバー）が使用されていました。

問題は、2ワードサイズのブロックの場合、このフラグを設定しても、その直後に `memclr` が呼び出されてゼロクリアされるため、フラグの設定自体が無意味になっていた点です。特に32ビットアーキテクチャでは、`sizeof(uintptr)` が4バイトであるため、`2 * sizeof(uintptr)` は8バイトとなり、このサイズのブロックに対して常に `memclr` が呼ばれていました。これは、フラグのチェックと設定のオーバーヘッドが無駄になっていたことを意味します。

このコミットは、この非効率性を解消し、2ワードブロックのゼロクリアをより直接的かつ効率的に行うことを目的としています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは独自のメモリ管理システムを持っています。これは、OSからのメモリ確保（ヒープ）を管理し、Goのオブジェクトに割り当て、不要になったオブジェクトをガベージコレクションによって回収します。

*   **`mallocgc`**: Goランタイムにおけるメモリ確保の主要な関数です。オブジェクトのサイズに基づいて適切なメモリ領域を割り当てます。
*   **`free`**: オブジェクトが不要になった際にメモリを解放する関数です。
*   **ゼロクリア**: Goでは、新しく確保されたメモリはデフォルトでゼロクリアされます。これにより、古いデータが残ることを防ぎ、プログラムの予測可能性とセキュリティを向上させます。
*   **`memclr`**: 指定されたメモリ領域をゼロで埋める（クリアする）ための低レベル関数です。
*   **`uintptr`**: ポインタを保持できる符号なし整数型です。そのサイズはアーキテクチャに依存し、32ビットシステムでは4バイト、64ビットシステムでは8バイトです。
*   **`sizeof(uintptr)`**: `uintptr` 型のサイズをバイト単位で返します。
*   **ガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に回収するプロセスです。マーク＆スイープアルゴリズムを採用しており、スイープフェーズでは、マークされなかった（到達不能な）オブジェクトが占めていたメモリ領域が再利用可能になります。
*   **スイープフェーズ (`sweepspan`)**: GCのスイープフェーズでは、マークされなかったメモリブロックが解放され、必要に応じてゼロクリアされます。

### メモリのゼロクリアとマジックナンバー

Goランタイムでは、メモリブロックがゼロクリアされるべきかどうかを示すために、特定の「マジックナンバー」がメモリの特定の場所に書き込まれることがあります。

*   **`0xfeedfeedfeedfeedll`**: これは、メモリブロックが解放され、次に再利用される際にゼロクリアされる必要があることを示すために使用されるマジックナンバーです。これは主に64ビットシステムで有効な値です。
*   **`0xdeaddeaddeaddeadll`**: 同様に、ガベージコレクションのスイープフェーズで、メモリブロックが解放され、ゼロクリアされる必要があることを示すために使用されるマジックナンバーです。

これらのマジックナンバーは、デバッグ目的や、メモリが適切にゼロクリアされたかどうかの検証のために使用されることがあります。しかし、このコミットの背景にある問題は、これらのフラグが設定されても、すぐに `memclr` でゼロクリアされるため、フラグの存在意義が薄れていた点にあります。

## 技術的詳細

このコミットの核心は、Goランタイムがメモリブロックをゼロクリアする際の条件分岐の修正にあります。特に、`sizeof(uintptr)` の2倍のサイズ（つまり2ワード）のメモリブロックに対する処理が変更されています。

以前のコードでは、`mallocgc`、`free`、`sweepspan` の各関数において、メモリブロックのサイズが `sizeof(uintptr)` より大きい場合に、そのブロックの2番目のワードにマジックナンバー（`0xfeedfeedfeedfeedll` や `0xdeaddeaddeaddeadll`）を書き込んで「ゼロクリアが必要」というフラグを設定していました。しかし、その直後に `memclr` が呼び出され、ブロック全体がゼロクリアされていました。

このコミットは、この条件を `size > 2*sizeof(uintptr)` に変更することで、2ワードサイズのブロックに対するマジックナンバーの書き込みをスキップします。代わりに、`else if(size > sizeof(uintptr))` という新しい条件を追加し、2ワードサイズのブロック（`size` が `sizeof(uintptr)` より大きく、かつ `2*sizeof(uintptr)` 以下の場合）に対しては、2番目のワードを直接 `0` に設定するように変更しています。

これにより、2ワードブロックに対しては、無意味なマジックナンバーの設定と、その後の `memclr` による上書きという冗長なステップが排除されます。代わりに、必要なゼロクリアがインプレースで、より直接的に行われるようになります。

特に32ビットシステムでは、`sizeof(uintptr)` が4バイトであるため、`size > sizeof(uintptr)` は `size > 4` を意味し、`size > 2*sizeof(uintptr)` は `size > 8` を意味します。この変更により、4バイト超8バイト以下のブロック（つまり2ワードブロック）に対しては、マジックナンバーの設定がスキップされ、直接ゼロクリアされるようになります。

この最適化は、特に頻繁に確保・解放される小さなオブジェクト（例えば、ポインタ1つと何らかのフラグを持つ構造体など）の処理効率を向上させ、ランタイムのオーバーヘッドを削減します。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.goc` の変更点

1.  **`runtime·mallocgc` 関数内**:
    *   変更前: `if(size > sizeof(uintptr) && ((uintptr*)v)[1] != 0)`
    *   変更後: `if(size > 2*sizeof(uintptr) && ((uintptr*)v)[1] != 0)`
    *   この変更は、`mallocgc` が確保したメモリをゼロクリアする条件を調整しています。以前は `sizeof(uintptr)` より大きいブロックであれば2番目のワードをチェックしていましたが、変更後は `2*sizeof(uintptr)` より大きいブロックに限定されます。これは、2ワードブロックの場合、後続の `memclr` が常に実行されるため、この条件分岐自体が冗長であったことを示唆しています。

2.  **`runtime·free` 関数内**:
    *   変更前:
        ```c
        if(size > sizeof(uintptr))
            ((uintptr*)v)[1] = (uintptr)0xfeedfeedfeedfeedll;	// mark as "needs to be zeroed"
        ```
    *   変更後:
        ```c
        if(size > 2*sizeof(uintptr))
            ((uintptr*)v)[1] = (uintptr)0xfeedfeedfeedfeedll;	// mark as "needs to be zeroed"
        else if(size > sizeof(uintptr))
            ((uintptr*)v)[1] = 0;
        ```
    *   この変更が最も重要です。メモリ解放時、以前は `sizeof(uintptr)` より大きいブロックであれば無条件に2番目のワードに `0xfeedfeedfeedfeedll` を書き込んでいました。
    *   変更後は、`2*sizeof(uintptr)` より大きいブロックに対してのみマジックナンバーを書き込みます。
    *   新しく追加された `else if(size > sizeof(uintptr))` の条件は、`sizeof(uintptr)` より大きく、かつ `2*sizeof(uintptr)` 以下のブロック（つまり2ワードブロック）を対象とします。これらのブロックに対しては、2番目のワードを直接 `0` に設定します。これにより、マジックナンバーを書き込んでから `memclr` で上書きするという無駄なステップがなくなります。

### `src/pkg/runtime/mgc0.c` の変更点

1.  **`sweepspan` 関数内**:
    *   変更前:
        ```c
        if(size > sizeof(uintptr))
            ((uintptr*)p)[1] = (uintptr)0xdeaddeaddeaddeadll;	// mark as "needs to be zeroed"
        ```
    *   変更後:
        ```c
        if(size > 2*sizeof(uintptr))
            ((uintptr*)p)[1] = (uintptr)0xdeaddeaddeaddeadll;	// mark as "needs to be zeroed"
        else if(size > sizeof(uintptr))
            ((uintptr*)p)[1] = 0;
        ```
    *   `runtime·free` と同様に、ガベージコレクションのスイープフェーズでも同様の最適化が行われています。`sweepspan` は、到達不能なメモリブロックを再利用可能にする際に、そのブロックをゼロクリアする必要があるかどうかを管理します。
    *   ここでも、2ワードブロックに対してはマジックナンバーの設定をスキップし、直接2番目のワードを `0` に設定することで、冗長な処理を排除しています。

これらの変更により、Goランタイムは2ワードサイズのメモリブロックのゼロクリアをより効率的に行い、特に32ビットシステムでのパフォーマンスが向上します。

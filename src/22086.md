# [インデックス 22086] ファイルの概要

このコミットは、Goランタイムのメモリ割り当てコードにプリフェッチ命令を追加することで、パフォーマンスの改善を図るものです。具体的には、`mallocgc`ルーチンがフリーリストからオブジェクトを取得する際に、次に返されるオブジェクトを事前にプリフェッチすることで、キャッシュミスを減らし、全体的な実行速度を向上させます。

## 元コミット内容

Goランタイムのメモリ割り当てコードにプリフェッチ命令を追加します。`mallocgc`ルーチンはフリーリストからオブジェクトを取得しますが、次に`mallocgc`が呼び出されたときに返されるオブジェクトをプリフェッチします。実験では、`prefetchnta`を使用した場合に1%の改善が見られ、`prefetcht0`、`prefetcht1`、`prefetcht2`を使用した場合よりも効果的でした。

ベンチマーク結果（`MAXPROCS=4`での`garbage`ベンチマーク）は以下の通りです。

*   プリフェッチなし: 5.96 / 5.77 / 5.89
*   `prefetcht0(uintptr(v.ptr().next))`: 5.88 / 6.17 / 5.84
*   `prefetcht1(uintptr(v.ptr().next))`: 5.88 / 5.89 / 5.91
*   `prefetcht2(uintptr(v.ptr().next))`: 5.87 / 6.47 / 5.92
*   `prefetchnta(uintptr(v.ptr().next))`: 5.72 / 5.84 / 5.85

## 変更の背景

Goランタイムのパフォーマンス最適化は継続的に行われています。特にメモリ割り当てとガベージコレクションは、プログラム全体の実行速度に大きな影響を与えるため、常に改善の対象となります。このコミットは、CPUのキャッシュ効率を向上させることで、`mallocgc`のボトルネックを解消し、全体的なアプリケーションのパフォーマンスを向上させることを目的としています。

`mallocgc`はGoのメモリ割り当ての根幹をなす関数であり、頻繁に呼び出されます。この関数がフリーリストから次のオブジェクトを取得する際、そのオブジェクトがメインメモリからCPUキャッシュにロードされるまでに時間がかかることがあります（キャッシュミス）。このレイテンシを削減するために、次に必要となるデータを事前にキャッシュに読み込んでおく「プリフェッチ」という技術が有効です。

このコミットは、特定のプリフェッチ命令（`prefetchnta`）が他のプリフェッチ命令よりも効果的であることをベンチマークで確認し、それをコードに適用することで、実測で1%のパフォーマンス改善を達成しています。1%という数字は小さく見えるかもしれませんが、`mallocgc`のような頻繁に呼び出される低レベルの関数における1%の改善は、Goプログラム全体の実行速度に累積的に大きな影響を与える可能性があります。

## 前提知識の解説

### 1. CPUキャッシュとプリフェッチ

現代のCPUは、メインメモリ（DRAM）よりもはるかに高速なSRAMベースのキャッシュメモリを内蔵しています。CPUがデータにアクセスする際、まずキャッシュを検索し、データが見つかれば高速にアクセスできます（キャッシュヒット）。しかし、キャッシュにデータがない場合（キャッシュミス）、CPUはメインメモリからデータをロードする必要があり、これは数百サイクルもの遅延を引き起こす可能性があります。

**プリフェッチ（Prefetching）**とは、CPUが将来必要になると予測されるデータを、実際に必要になる前にメインメモリからキャッシュに読み込んでおく最適化技術です。これにより、データが実際に使用される時点でのキャッシュミスを減らし、プログラムの実行効率を向上させることができます。

プリフェッチには、ハードウェアによる自動プリフェッチと、ソフトウェアによる明示的なプリフェッチ命令があります。このコミットで追加されているのは、後者のソフトウェアプリフェッチです。

### 2. プリフェッチ命令の種類 (x86/x64アーキテクチャ)

x86/x64アーキテクチャには、いくつかのプリフェッチ命令が存在し、それぞれ異なるキャッシュレベルやキャッシュポリシーを指示します。

*   **`PREFETCHT0`**: データを最も高いレベルのキャッシュ（通常はL1キャッシュ）にプリフェッチします。データは「時間的局所性」が高いと見なされ、将来的に何度もアクセスされる可能性が高い場合に適しています。
*   **`PREFETCHT1`**: データをL2キャッシュにプリフェッチします。L1キャッシュよりも大きく、L3キャッシュよりも高速な中間レベルのキャッシュにデータを置くことで、L1キャッシュの汚染を避けつつ、ある程度の高速アクセスを可能にします。
*   **`PREFETCHT2`**: データをL3キャッシュ（または利用可能な最も低いレベルのキャッシュ）にプリフェッチします。これは、データが一度だけアクセスされる可能性が高いが、それでもキャッシュに入れておくと有利な場合に適しています。
*   **`PREFETCHNTA` (Non-Temporal Access)**: データをキャッシュにプリフェッチしますが、そのデータがキャッシュラインを汚染しないように、非一時的な（non-temporal）ヒントを与えます。これは、データが一度だけアクセスされ、その後すぐに不要になる可能性が高い場合に特に有効です。通常のキャッシュラインは、キャッシュにロードされると、そのキャッシュラインが変更された場合にメインメモリに書き戻される可能性がありますが、`NTA`ヒントは、そのキャッシュラインがキャッシュから追い出される際にメインメモリへの書き戻しをスキップできる可能性を示唆します。これにより、キャッシュの他の有用なデータが追い出されるのを防ぎ、キャッシュの効率を向上させます。このコミットでは、この`PREFETCHNTA`が最も効果的であることが示されています。

### 3. Goのメモリ管理と`mallocgc`、フリーリスト

Go言語は独自のランタイムとガベージコレクタ（GC）を持っています。Goプログラムがメモリを要求すると、ランタイムは`mallocgc`関数を通じてメモリを割り当てます。

*   **`mallocgc`**: Goランタイムにおける主要なメモリ割り当て関数です。ユーザーコードからのメモリ割り当て要求（例: `make`、`new`）は、最終的にこの関数に到達します。
*   **フリーリスト（Freelist）**: Goランタイムは、オブジェクトの割り当てと解放を効率的に行うために、サイズごとに分類されたフリーリストを管理しています。これは、以前に解放されたがまだ再利用されていないメモリブロックのリストです。新しいオブジェクトの割り当て要求があった場合、ランタイムはまず適切なサイズのフリーリストから利用可能なブロックを探します。見つかれば、そのブロックを再利用することで、システムコールを介したOSからのメモリ割り当て（これは非常にコストが高い）を避けることができます。
*   **`v.ptr().next`**: フリーリストは通常、リンクされたリストとして実装されており、各フリーブロックは次のフリーブロックへのポインタを持っています。`v.ptr().next`は、現在のフリーブロック`v`の次にあるフリーブロックへのポインタを指します。`mallocgc`が現在のブロックを割り当てた後、次に割り当てる可能性のあるブロックは`v.ptr().next`が指すブロックになります。

このコミットは、この`v.ptr().next`が指すアドレスのデータを事前にプリフェッチすることで、`mallocgc`が次にフリーリストからオブジェクトを取得する際のキャッシュミスを減らし、パフォーマンスを向上させています。

## 技術的詳細

このコミットの技術的詳細の核心は、Goランタイムのメモリ割り当て関数`mallocgc`内にプリフェッチ命令を戦略的に配置した点にあります。

`mallocgc`は、Goプログラムが新しいオブジェクトをヒープに割り当てる際に呼び出される中心的な関数です。この関数は、まず適切なサイズのフリーリストから利用可能なメモリブロックを探します。フリーリストは、以前に解放されたオブジェクトが連結リストとして格納されているものです。

コミットメッセージとコードの変更点からわかるように、`mallocgc`がフリーリストから`v`というオブジェクトを取得し、それを割り当てて返す直前に、次にフリーリストから取得されるであろうオブジェクト（`v.ptr().next`が指すアドレス）をプリフェッチしています。

具体的には、`prefetchnta(uintptr(v.ptr().next))`という命令が追加されています。
*   `prefetchnta`: これはIntel/AMDプロセッサが提供するプリフェッチ命令の一つで、「Non-Temporal Access」ヒントを伴います。このヒントは、プリフェッチされるデータが一度だけアクセスされる可能性が高いことをCPUに示唆します。これにより、CPUはデータをキャッシュにロードする際に、既存のキャッシュラインを追い出す際にメインメモリへの書き戻しを避けるなど、キャッシュの汚染を最小限に抑えるような最適化を行うことができます。`mallocgc`がフリーリストからオブジェクトを次々に取得していくシナリオでは、各オブジェクトは一度割り当てられたら、そのフリーリストからは一時的に削除されるため、`NTA`ヒントが適切であると考えられます。
*   `uintptr(v.ptr().next)`: `v.ptr().next`は、Goの`unsafe.Pointer`型またはそれに類するポインタ型であり、次のフリーオブジェクトのアドレスを指します。`uintptr`にキャストすることで、プリフェッチ命令が期待するメモリアドレス（整数値）として渡しています。

コミットメッセージのベンチマーク結果は、`prefetchnta`が他のプリフェッチ命令（`prefetcht0`, `prefetcht1`, `prefetcht2`）よりも優れたパフォーマンス改善を示したことを明確に示しています。これは、Goのメモリ割り当てパターンとCPUキャッシュの動作特性が、`prefetchnta`の非一時的なヒントと相性が良かったことを示唆しています。

この最適化は、CPUのパイプラインストール（キャッシュミスによるデータ待ち）を減らすことで、`mallocgc`の実行時間を短縮し、結果としてGoプログラム全体の実行速度を向上させます。特に、メモリ割り当てが頻繁に発生するアプリケーションや、ガベージコレクションの頻度が高いアプリケーションにおいて、その効果が顕著に現れると期待されます。

    			s.ref++
    			// prefetchnta offers best performance, see change list message.

### 1. CPUキャッシュとプリフェッチ

現代のCPUは、メインメモリ（DRAM）よりもはるかに高速なSRAMベースのキャッシュメモリを内蔵しています。CPUがデータにアクセスする際、まずキャッシュを検索し、データが見つかれば高速にアクセスできます（キャッシュヒット）。しかし、キャッシュにデータがない場合（キャッシュミス）、CPUはメインメモリからデータをロードする必要があり、これは数百サイクルもの遅延を引き起こす可能性があります。

**プリフェッチ（Prefetching）**とは、CPUが将来必要になると予測されるデータを、実際に必要になる前にメインメモリからキャッシュに読み込んでおく最適化技術です。これにより、データが実際に使用される時点でのキャッシュミスを減らし、プログラムの実行効率を向上させることができます。

プリフェッチには、ハードウェアによる自動プリフェッチと、ソフトウェアによる明示的なプリフェッチ命令があります。このコミットで追加されているのは、後者のソフトウェアプリフェッチです。

### 2. プリフェッチ命令の種類 (x86/x64アーキテクチャ)

x86/x64アーキテクチャには、いくつかのプリフェッチ命令が存在し、それぞれ異なるキャッシュレベルやキャッシュポリシーを指示します。

*   **`PREFETCHT0`**: データを最も高いレベルのキャッシュ（通常はL1キャッシュ）にプリフェッチします。データは「時間的局所性」が高いと見なされ、将来的に何度もアクセスされる可能性が高い場合に適しています。
*   **`PREFETCHT1`**: データをL2キャッシュにプリフェッチします。L1キャッシュよりも大きく、L3キャッシュよりも高速な中間レベルのキャッシュにデータを置くことで、L1キャッシュの汚染を避けつつ、ある程度の高速アクセスを可能にします。
*   **`PREFETCHT2`**: データをL3キャッシュ（または利用可能な最も低いレベルのキャッシュ）にプリフェッチします。これは、データが一度だけアクセスされる可能性が高いが、それでもキャッシュに入れておくと有利な場合に適しています。
*   **`PREFETCHNTA` (Non-Temporal Access)**: データをキャッシュにプリフェッチしますが、そのデータがキャッシュラインを汚染しないように、非一時的な（non-temporal）ヒントを与えます。これは、データが一度だけアクセスされ、その後すぐに不要になる可能性が高い場合に特に有効です。通常のキャッシュラインは、キャッシュにロードされると、そのキャッシュラインが変更された場合にメインメモリに書き戻される可能性がありますが、`NTA`ヒントは、そのキャッシュラインがキャッシュから追い出される際にメインメモリへの書き戻しをスキップできる可能性を示唆します。これにより、キャッシュの他の有用なデータが追い出されるのを防ぎ、キャッシュの効率を向上させます。このコミットでは、この`PREFETCHNTA`が最も効果的であることが示されています。

### 3. Goのメモリ管理と`mallocgc`、フリーリスト

Go言語は独自のランタイムとガベージコレクタ（GC）を持っています。Goプログラムがメモリを要求すると、ランタイムは`mallocgc`関数を通じてメモリを割り当てます。

*   **`mallocgc`**: Goランタイムにおける主要なメモリ割り当て関数です。ユーザーコードからのメモリ割り当て要求（例: `make`、`new`）は、最終的にこの関数に到達します。
*   **フリーリスト（Freelist）**: Goランタイムは、オブジェクトの割り当てと解放を効率的に行うために、サイズごとに分類されたフリーリストを管理しています。これは、以前に解放されたがまだ再利用されていないメモリブロックのリストです。新しいオブジェクトの割り当て要求があった場合、ランタイムはまず適切なサイズのフリーリストから利用可能なブロックを探します。見つかれば、そのブロックを再利用することで、システムコールを介したOSからのメモリ割り当て（これは非常にコストが高い）を避けることができます。
*   **`v.ptr().next`**: フリーリストは通常、リンクされたリストとして実装されており、各フリーブロックは次のフリーブロックへのポインタを持っています。`v.ptr().next`は、現在のフリーブロック`v`の次にあるフリーブロックへのポインタを指します。`mallocgc`が現在のブロックを割り当てた後、次に割り当てる可能性のあるブロックは`v.ptr().next`が指すブロックになります。

このコミットは、この`v.ptr().next`が指すアドレスのデータを事前にプリフェッチすることで、`mallocgc`が次にフリーリストからオブジェクトを取得する際のキャッシュミスを減らし、パフォーマンスを向上させています。

## 技術的詳細

このコミットの技術的詳細の核心は、Goランタイムのメモリ割り当て関数`mallocgc`内にプリフェッチ命令を戦略的に配置した点にあります。

`mallocgc`は、Goプログラムが新しいオブジェクトをヒープに割り当てる際に呼び出される中心的な関数です。この関数は、まず適切なサイズのフリーリストから利用可能なメモリブロックを探します。フリーリストは、以前に解放されたオブジェクトが連結リストとして格納されているものです。

コミットメッセージとコードの変更点からわかるように、`mallocgc`がフリーリストから`v`というオブジェクトを取得し、それを割り当てて返す直前に、次にフリーリストから取得されるであろうオブジェクト（`v.ptr().next`が指すアドレス）をプリフェッチしています。

具体的には、`prefetchnta(uintptr(v.ptr().next))`という命令が追加されています。
*   `prefetchnta`: これはIntel/AMDプロセッサが提供するプリフェッチ命令の一つで、「Non-Temporal Access」ヒントを伴います。このヒントは、プリフェッチされるデータが一度だけアクセスされる可能性が高いことをCPUに示唆します。これにより、CPUはデータをキャッシュにロードする際に、既存のキャッシュラインを追い出す際にメインメモリへの書き戻しを避けるなど、キャッシュの汚染を最小限に抑えるような最適化を行うことができます。`mallocgc`がフリーリストからオブジェクトを次々に取得していくシナリオでは、各オブジェクトは一度割り当てられたら、そのフリーリストからは一時的に削除されるため、`NTA`ヒントが適切であると考えられます。
*   `uintptr(v.ptr().next)`: `v.ptr().next`は、Goの`unsafe.Pointer`型またはそれに類するポインタ型であり、次のフリーオブジェクトのアドレスを指します。`uintptr`にキャストすることで、プリフェッチ命令が期待するメモリアドレス（整数値）として渡しています。

コミットメッセージのベンチマーク結果は、`prefetchnta`が他のプリフェッチ命令（`prefetcht0`, `prefetcht1`, `prefetcht2`）よりも優れたパフォーマンス改善を示したことを明確に示しています。これは、Goのメモリ割り当てパターンとCPUキャッシュの動作特性が、`prefetchnta`の非一時的なヒントと相性が良かったことを示唆しています。

この最適化は、CPUのパイプラインストール（キャッシュミスによるデータ待ち）を減らすことで、`mallocgc`の実行時間を短縮し、結果としてGoプログラム全体の実行速度を向上させます。特に、メモリ割り当てが頻繁に発生するアプリケーションや、ガベージコレクションの頻度が高いアプリケーションにおいて、その効果が顕著に現れると期待されます。

## コアとなるコードの解説

変更は`mallocgc`関数内の2箇所にあります。どちらも、フリーリストからオブジェクト`v`を取得し、その`s.freelist`を`v.ptr().next`に更新した直後に、`prefetchnta`命令が追加されています。

1.  **最初の変更箇所 (行 553付近)**:
    ```go
    			s.freelist = v.ptr().next
    			s.ref++
    			// prefetchnta offers best performance, see change list message.
    			prefetchnta(uintptr(v.ptr().next))
    			x = unsafe.Pointer(v)
    ```
    このブロックは、`mallocgc`が特定のサイズのオブジェクトを割り当てる際の一般的なパスの一つです。`s.freelist = v.ptr().next`で、現在のフリーリストの先頭を次のオブジェクトに更新しています。その直後に`prefetchnta(uintptr(v.ptr().next))`が挿入され、次に割り当てられる可能性のあるオブジェクトのデータをキャッシュにプリフェッチしています。これにより、次に`mallocgc`が呼び出された際に、このデータが既にキャッシュに存在し、高速にアクセスできるようになります。

2.  **二番目の変更箇所 (行 584付近)**:
    ```go
    			s.freelist = v.ptr().next
    			s.ref++
    			// prefetchnta offers best performance, see change list message.
    			prefetchnta(uintptr(v.ptr().next))
    			x = unsafe.Pointer(v)
    			if flags&flagNoZero == 0 {
    				v.ptr().next = 0
    ```
    このブロックも同様に、`mallocgc`内の別の割り当てパスです。ここでも、フリーリストの更新直後に同じ`prefetchnta`命令が追加されています。`if flags&flagNoZero == 0`の条件分岐があることから、これはオブジェクトをゼロクリアする必要がある場合とない場合で処理が異なるパスの一部であることが示唆されますが、プリフェッチのロジック自体は共通しています。

両方の変更箇所で、以前は`//TODO: prefetch v.next`や`//TODO: prefetch`といったコメントがあった部分が、具体的な`prefetchnta`命令に置き換えられています。これは、以前からプリフェッチの必要性が認識されており、今回のコミットで最適なプリフェッチ命令が特定され、実装されたことを示しています。

この変更は、Goランタイムの低レベルな部分に手を加えるものであり、CPUのハードウェア特性を最大限に活用してパフォーマンスを絞り出すための典型的な最適化手法と言えます。

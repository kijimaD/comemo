## 変更の背景

このコミットは、Goコンパイラのコード生成フェーズにおける最適化を目的としています。特に、`sudoaddable`関数の振る舞いを改善し、生成されるアセンブリコードの効率を高めることが狙いです。

Goコンパイラは、ソースコードを機械語に変換する際に、中間表現（IR）からアセンブリ命令を生成します。この過程で、オペランド（命令の対象となるデータ）をどのように扱うか（レジスタにロードするか、メモリから直接アクセスするか、即値として埋め込むかなど）は、生成されるコードのパフォーマンスに大きく影響します。

`sudoaddable`関数は、あるノード（抽象構文木の一部）が特定のアセンブリ命令のオペランドとして直接「追加可能」（addable）であるかどうかを判断するために使用されていました。このコミット以前は、`sudoaddable`はノードの情報のみに基づいて判断していましたが、変更後は、生成しようとしているアセンブリ命令の種類（`as`引数）も考慮に入れるようになりました。これにより、より文脈に応じた正確な判断が可能となり、結果としてより最適化されたアセンブリコードの生成に繋がります。例えば、特定の命令では即値が直接オペランドとして使えるが、別の命令では使えない、といったケースに対応できるようになります。

## 前提知識の解説

*   **Goコンパイラ (`6g`)**:
    Go言語の初期のコンパイラは、`gc`ツールチェーンとして知られ、C言語で書かれていました。`6g`は、その中でも特にx86-64アーキテクチャ（AMD64）向けのコンパイラを指します。同様に、`8g`は386（32ビット）向け、`5g`はARM向けでした。Go 1.5以降、コンパイラ自体がGo言語で書き直され、これらのアーキテクチャ固有の名称は廃止され、現在は単一の`compile`ツールが使用されています。このコミットは、Go言語がまだ初期段階にあった2009年のものであり、当時のコンパイラの内部構造を理解する上で重要です。

*   **コード生成 (Code Generation)**:
    コンパイラの最終段階であり、最適化された中間表現（IR）をターゲットアーキテクチャの機械語命令に変換するプロセスです。これには、命令選択（どの機械語命令を使用するか）、レジスタ割り当て（プログラムの値をCPUレジスタに割り当てる）、スタックフレームのレイアウト（ローカル変数や関数呼び出しのためのメモリ割り当て）などが含まれます。効率的なコード生成は、プログラムの実行速度に直結します。

*   **抽象構文木 (Abstract Syntax Tree, AST)**:
    ソースコードの構文構造を木構造で表現したものです。コンパイラのフロントエンドで生成され、その後のセマンティック解析、最適化、コード生成の入力となります。Goコンパイラでは、`Node`構造体がASTのノードを表します。

*   **`Node`**:
    Goコンパイラの内部で、抽象構文木（AST）の各要素を表すデータ構造です。変数、定数、演算子、関数呼び出しなど、プログラムのあらゆる構成要素が`Node`として表現されます。

*   **`Addr`**:
    アセンブリ命令におけるオペランドのアドレス指定モードを表す構造体です。レジスタ、メモリ位置、即値などを表現します。

*   **`Prog`**:
    Goコンパイラの内部で、単一のアセンブリ命令を表すデータ構造です。`gins`関数などによって生成されます。

*   **`gins(as, from, to)`**:
    "generate instruction"の略で、指定されたアセンブリ命令（`as`）、ソースオペランド（`from`）、デスティネーションオペランド（`to`）を持つ`Prog`構造体を生成し、命令リストに追加する関数です。

*   **`regalloc(Node *n, Type *t, Node *res)`**:
    "register allocate"の略で、指定された型`t`のノード`n`に対してレジスタを割り当てる関数です。`res`は結果を格納するノードです。

*   **`sudoaddable(Node *n, Addr *a)` (変更前)**:
    この関数は、与えられたASTノード`n`が、アセンブリ命令のオペランドとして直接使用できる形式（`Addr`）に変換可能かどうかを判断していました。例えば、即値や特定のメモリ参照は直接オペランドとして使用できますが、複雑な式の結果は一時レジスタにロードする必要がある場合があります。

*   **`optoas(Op op, Type *t)`**:
    Goコンパイラの内部関数で、Go言語のASTノードの操作タイプ（`Op`、例: `OAS`、`OINC`）と型（`Type`）を受け取り、対応するアセンブリ命令のオペレーションコード（`as`）を返します。

*   **アセンブリ命令のオペレーションコード**:
    *   `OAS`: 代入 (`MOV`)
    *   `OINC`: インクリメント (`INC`)
    *   `ODEC`: デクリメント (`DEC`)
    *   `OXOR`: ビットごとのXOR (`XOR`)
    *   `OAND`: ビットごとのAND (`AND`)
    *   `OOR`: ビットごとのOR (`OR`)
    これらはGo言語の操作に対応するアセンブリ命令の種類を示します。

## 技術的詳細

このコミットの主要な変更点は、`sudoaddable`関数のシグネチャが変更され、その呼び出し箇所が修正されたことです。

**変更前**: `int sudoaddable(Node *n, Addr *a)`
**変更後**: `int sudoaddable(int as, Node *n, Addr *a)`

新しいシグネチャでは、第一引数に`int as`が追加されています。この`as`は、生成しようとしているアセンブリ命令のオペレーションコード（例: `AADDB`, `AINCL`など）を表します。

この変更の意図は、`sudoaddable`関数が、単にノードの性質だけでなく、**どのような種類のアセンブリ命令のオペランドとして使用されるか**という文脈も考慮に入れて、より賢明な判断を下せるようにすることです。

具体的な変更箇所を見てみましょう。

1.  **`src/cmd/6g/cgen.c`**:
    `cgen`関数は、Go言語の式や文をアセンブリコードに変換する役割を担っています。このファイルでは、`sudoaddable`の呼び出しが、`a = optoas(OAS, res->type);` または `a = optoas(OAS, n->type);` のように、まず代入命令のオペレーションコードを取得し、それを`sudoaddable`の第一引数として渡すように変更されています。これにより、代入操作の文脈でオペランドが直接使用可能かを判断します。

2.  **`src/cmd/6g/gen.c`**:
    `cgen_asop`関数は、複合代入演算子（`+=`, `-=`, `^=`など）のコード生成を扱います。ここでも、`sudoaddable`の呼び出しに、対応するアセンブリ命令のオペレーションコード（`OINC`, `ODEC`, `n->etype`など）が第一引数として渡されるようになりました。例えば、`ADD`操作の場合、`a = optoas(OINC, nl->type);` でインクリメント命令のオペレーションコードを取得し、`sudoaddable(a, nl, &addr)` のように呼び出しています。これにより、インクリメントやデクリメント、ビット演算などの特定の命令において、オペランドが直接使用可能かをより正確に判断できるようになります。

3.  **`src/cmd/6g/gg.h`**:
    `sudoaddable`関数のプロトタイプ宣言が、新しいシグネチャに合わせて更新されています。

4.  **`src/cmd/6g/gsubr.c`**:
    `sudoaddable`関数の実装自体が変更されています。
    *   関数のシグネチャが `int sudoaddable(int as, Node *n, Addr *a)` に更新されました。
    *   `OLITERAL`（即値）の場合の処理が追加されました。即値が-32000から32000の範囲内であれば、特定の命令（`AADDB`, `ASUBB`, `AMOVB`など）のオペランドとして直接使用可能であると判断するロジックが追加されています。これは、アセンブリ命令によっては、即値オペランドのサイズに制限があるため、その制約を考慮に入れた最適化です。
    *   `switch(as)`文が追加され、`as`引数で渡されたアセンブリ命令の種類に基づいて、`OLITERAL`が「addable」であるかどうかの判断が行われるようになりました。これにより、例えば`MOV`命令では即値が直接使えるが、他の命令では使えないといった、命令ごとの特性を考慮したコード生成が可能になります。

この変更により、コンパイラはより多くのケースで、一時レジスタへのロードやメモリへのストアといった余分な操作を回避し、直接オペランドを使用するアセンブリ命令を生成できるようになります。これは、生成されるバイナリのサイズを削減し、実行速度を向上させる効果が期待できます。

## コアとなるコードの解説

このコミットの核心は、`sudoaddable`関数の機能拡張と、それに伴うコード生成ロジックの洗練です。

1.  **`sudoaddable`関数のシグネチャ変更**:
    `sudoaddable`関数は、以前は`Node`と`Addr`のポインタのみを受け取っていましたが、新たに`int as`（アセンブリ命令のオペレーションコード）を受け取るようになりました。これにより、`sudoaddable`は、単にノードの型や構造だけでなく、**そのノードがどのような種類のアセンブリ命令のオペランドとして使われるか**という文脈情報を利用して、より正確な「addable」判定を行えるようになりました。

2.  **`cgen.c`と`gen.c`における`sudoaddable`の呼び出し変更**:
    これらのファイルでは、`sudoaddable`を呼び出す前に、`optoas`関数を使って現在生成しようとしているアセンブリ命令のオペレーションコードを取得し、それを`sudoaddable`の第一引数として渡すように変更されています。例えば、代入操作（`OAS`）やインクリメント（`OINC`）、ビット演算（`OXOR`, `OAND`, `OOR`）など、それぞれのGo言語の操作に対応するアセンブリ命令の種類が渡されます。これにより、`sudoaddable`は、その命令が即値を直接サポートするか、特定のレジスタを必要とするかなど、命令固有の制約を考慮した上で、オペランドが直接使用可能かを判断できるようになります。

3.  **`gsubr.c`における`sudoaddable`の実装変更**:
    *   **`OLITERAL`（即値）の特別扱い**: `sudoaddable`関数内で、`OLITERAL`ノード（定数）が追加可能であるかどうかの判定ロジックが強化されました。特に、即値が-32000から32000の範囲内にある場合に、特定のバイト/ワード/ロング/クワッドワード操作（`AADDB`, `AMOVW`など）のオペランドとして直接使用できると判断するようになりました。これは、x86-64アーキテクチャにおいて、一部の命令が特定の範囲の即値を直接オペランドとして受け入れることができるという特性を利用したものです。
    *   **`switch(as)`による命令種別ごとの判定**: 新たに追加された`as`引数に基づいて、`switch`文が導入されました。これにより、`sudoaddable`は、`as`が`ADD`系の命令なのか、`SUB`系の命令なのか、`MOV`系の命令なのかなどを判別し、それぞれの命令が即値オペランドをサポートするかどうかを細かく制御できるようになりました。例えば、`MOV`命令は広範囲の即値を直接扱えますが、`ADD`命令はより制限された範囲の即値しか直接扱えない場合があります。この変更により、コンパイラは命令セットの特性をより深く理解し、より効率的な命令選択を行うことが可能になります。

これらの変更は、Goコンパイラが生成するアセンブリコードの品質を向上させるための、低レベルかつ重要な最適化です。不要なレジスタのロード/ストアやメモリへのアクセスを減らすことで、生成されるバイナリのサイズを小さくし、実行時のパフォーマンスを向上させる効果があります。

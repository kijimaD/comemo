## 変更の背景

このコミットは、Go言語のアセンブラ（`cmd/asm`）がシフト演算（`LSH`: 左シフト、`RSH`: 右シフト）を処理する際に、シフト量が負の値になるケースを適切に扱えていなかった問題に対処しています。

元々、シフト量は符号なし整数（`uint`）として扱われるため、理論上は負の値にはなり得ません。しかし、アセンブラのパーサーが値を`uint64`として読み取った後、その値が実際には負の数として意図されていた場合（例えば、2の補数表現で負の数を表すビットパターンが`uint64`として解釈された場合）、予期せぬ動作を引き起こす可能性がありました。

以前の修正では、`LSH`に対しては「`shift`は`uint`なので負にはならない」というコメントがあり、負のシフト量をチェックしていませんでした。`RSH`に対しては、`value&(1<<63) != 0`というチェックがありましたが、これはシフト量ではなく、シフトされる値（`value`）の最上位ビットがセットされているかを確認するもので、負のシフト量を検出する目的には不適切でした。

このコミットは、これらの不正確または不十分なチェックを修正し、シフト量が64ビットの符号付き整数として負である場合に、明確にエラーとして扱うように変更することで、アセンブラの堅牢性を向上させています。これにより、`issue #11278` で報告された問題が真に解決されます。

## 前提知識の解説

### 1. Go言語のアセンブラ (`cmd/asm`)

Go言語は、そのコンパイラツールチェーンの一部として独自のアセンブラ `cmd/asm` を持っています。これは、Goのランタイムや特定のパフォーマンスが要求されるコード（例: 暗号化ライブラリ）で、Goのコードから直接呼び出されるアセンブリコードを記述するために使用されます。Goのアセンブリ言語は、一般的なx86-64アセンブリとは異なる独自の構文を持っています。

### 2. シフト演算子 (`LSH`, `RSH`)

- **LSH (Left Shift)**: 左シフト演算子。`A LSH B` は `A` のビットを `B` の数だけ左にシフトします。通常、`A * (2^B)` と同等です。
- **RSH (Right Shift)**: 右シフト演算子。`A RSH B` は `A` のビットを `B` の数だけ右にシフトします。通常、`A / (2^B)` と同等です。

これらの演算では、シフト量 `B` は通常、非負の整数であると期待されます。負のシフト量は、プログラミング言語の仕様によっては未定義動作を引き起こしたり、エラーになったりします。

### 3. 符号付き整数と符号なし整数

- **符号なし整数 (unsigned integer)**: 常に0以上の値を表します。ビットパターンはそのまま数値として解釈されます。例えば、8ビットの符号なし整数では `11111111` は `255` を表します。
- **符号付き整数 (signed integer)**: 正の値、負の値、0を表します。一般的に2の補数表現が用いられます。8ビットの2の補数表現では `11111111` は `-1` を表します。最上位ビット（MSB）が符号ビットとして機能し、`0` なら正、`1` なら負を示します。

このコミットの文脈では、アセンブラのパーサーが読み取った64ビットの値（`uint64`）が、実際には負のシフト量（`int64`）として意図されていた場合に問題が発生していました。`uint64`として見ると大きな正の数ですが、`int64`として解釈すると負の数になるビットパターンが存在します。

### 4. `p.errorf`

`p.errorf` は、アセンブラのパーサー内でエラーを報告するための関数です。これにより、不正なアセンブリコードが検出された際に、適切なエラーメッセージを出力してコンパイルを停止させることができます。

## 技術的詳細

このコミットの核心は、シフト量の検証ロジックの改善にあります。

### 以前の問題点

1.  **`LSH` (左シフト)**:
    *   以前のコードでは、シフト量 `shift` が `uint` 型であるため負にならないという前提がありました。しかし、これはパーサーが値を`uint64`として読み取った後の解釈の問題を見落としていました。もし入力されたリテラルが、`uint64`としては大きな正の数だが、`int64`として解釈すると負の数になるようなビットパターンであった場合、その値がそのままシフト量として使われてしまう可能性がありました。
    *   例えば、`0xFFFFFFFFFFFFFFFF` は `uint64` では `18446744073709551615` ですが、`int64` では `-1` です。このような値がシフト量として渡された場合、予期せぬ動作を引き起こします。

2.  **`RSH` (右シフト)**:
    *   以前のコードでは、`if value&(1<<63) != 0` というチェックがありました。これはシフトされる値 `value` の最上位ビットがセットされているか（つまり、`value` が負の数であるか）を確認するものでした。これはシフト量 `shift` が負であることとは無関係であり、誤った条件でエラーを検出していました。
    *   また、`value >>= uint(shift)` と、シフト量を`uint`にキャストしていましたが、これも`uint64`から`uint`への変換で情報が失われる可能性があり、意図しない動作につながる恐れがありました。

### 修正内容

このコミットでは、`LSH` と `RSH` の両方で、シフト量 `shift` を `int64` にキャストし、その結果が負であるかどうかをチェックする統一されたロジックを導入しています。

```go
if int64(shift) < 0 {
    p.errorf("left shift with high bit set") // または "right shift with high bit set"
}
```

この変更により、パーサーが読み取った`uint64`のシフト量が、実際には負の数として意図されていた場合に、`int64`として解釈した際に負の値となるため、適切にエラーが報告されるようになります。これにより、不正なシフト量による未定義動作や予期せぬ結果を防ぎ、アセンブラの堅牢性が向上します。

また、`RSH` の `value >>= uint(shift)` は `value >>= shift` に変更され、不要な `uint` へのキャストが削除されています。これは、`shift` が既に `uint64` であり、`value` も `uint64` であるため、直接シフト演算を行うのが適切であるためです。

## コアとなるコードの解説

### `case lex.LSH:` の変更点

-   **削除された行**: `// shift is a uint, so can never be negative.`
    -   このコメントは、`shift` が `uint` であるため負にならないという誤った前提に基づいていました。`shift` は `p.factor()` から `uint64` として返されるため、ビットパターンによっては `int64` として解釈すると負になる可能性があります。
-   **追加された行**:
    ```go
    if int64(shift) < 0 {
        p.errorf("left shift with high bit set")
    }
    ```
    -   ここで、`shift` (型は `uint64`) を `int64` に明示的にキャストしています。
    -   `int64(shift) < 0` の条件は、`shift` の最上位ビットが `1` である場合に真となります。これは、`uint64` としては非常に大きな正の数ですが、`int64` としては負の数を表すビットパターンです。
    -   このようなケースを検出した場合、`p.errorf` を呼び出して「left shift with high bit set」（最上位ビットがセットされた左シフト）というエラーメッセージを出力し、コンパイルを停止させます。これにより、不正なシフト量による潜在的な問題を未然に防ぎます。

### `case lex.RSH:` の変更点

-   **削除された行**:
    ```go
    // shift is a uint, so can never be negative.
    if value&(1<<63) != 0 {
        p.errorf("right shift with high bit set")
    }
    value >>= uint(shift)
    ```
    -   最初のコメントは `LSH` と同様に誤った前提でした。
    -   `if value&(1<<63) != 0` の条件は、シフトされる値 `value` の最上位ビットがセットされているかをチェックするもので、シフト量 `shift` の正負とは無関係でした。このため、負のシフト量を検出する目的には不適切でした。
    -   `value >>= uint(shift)` は、`shift` を `uint` にキャストしていましたが、`shift` は既に `uint64` であり、`value` も `uint64` であるため、このキャストは不要であり、場合によっては情報損失のリスクがありました。
-   **追加された行**:
    ```go
    if int64(shift) < 0 {
        p.errorf("right shift with high bit set")
    }
    value >>= shift
    ```
    -   `LSH` と同様に、`shift` を `int64` にキャストして負のシフト量を検出するロジックが導入されました。これにより、`RSH` においても不正なシフト量に対する堅牢性が向上します。
    -   `value >>= shift` は、`shift` を `uint` にキャストすることなく、直接 `uint64` 型の `shift` を使用して右シフトを実行します。これはより正確で効率的な方法です。

これらの変更により、Goのアセンブラは、シフト演算における負のシフト量という、通常は不正とされる入力に対して、より適切にエラーを報告し、堅牢な動作を保証するようになりました。

# [インデックス 26953] ファイルの概要

このコミットは、Goバイナリ内の読み取り専用文字列データの重複排除を実装するものです。特に、型情報など、互いに部分文字列となるような文字列の重複を排除することで、最終的なバイナリサイズを削減することを目的としています。

## 変更の背景

Goのバイナリは、特に型情報などのメタデータを文字列として保持することが多く、その結果としてバイナリサイズが大きくなる傾向がありました。例えば、`struct { X int }`という型情報と、そのポインタ型である`*struct { X int }`という型情報は、後者が前者を部分文字列として含んでいます。同様に、`*bytes.Reader`と`func(*bytes.Reader)`も部分文字列の関係にあります。

これらの文字列は、それぞれ独立した文字列ヘッダによって参照されるため、たとえ内容が重複していても、バイナリ内では別々のデータとして格納されていました。この非効率性は、特に大規模なアプリケーションにおいて、バイナリサイズの肥大化を招いていました。

このコミットの目的は、リンカの段階でこれらの重複する読み取り専用文字列を検出し、より短い文字列がより長い文字列の部分文字列として存在する場合、短い文字列のデータ自体をバイナリに書き込むのをスキップし、その参照（ポインタ）を長い文字列内の適切なオフセットにリダイレクトすることで、バイナリサイズを削減することです。これにより、ディスク使用量とロード時間の削減が期待されます。

## 前提知識の解説

### Goリンカ (cmd/link)
Goリンカは、Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。このプロセスには、シンボルの解決、メモリレイアウトの決定、そしてリロケーションの適用などが含まれます。

### シンボル (LSym)
Goリンカ内部では、プログラム内のすべてのエンティティ（関数、変数、文字列定数など）が`LSym`（Linker Symbol）として表現されます。各`LSym`は、そのデータ、サイズ、型、属性、そして他のシンボルへの参照（リロケーション）などの情報を持っています。読み取り専用文字列も`LSym`として扱われます。

### リロケーション (Relocation)
リロケーションとは、リンカがプログラム内のアドレス参照を修正するプロセスです。コンパイル時には、コードやデータが最終的にメモリ上のどこに配置されるか分からないため、相対アドレスやプレースホルダーが使用されます。リンカは、すべてのオブジェクトファイルを結合し、最終的なメモリレイアウトを決定した後、これらのプレースホルダーを実際の絶対アドレスやオフセットに置き換えます。文字列の参照も、このリロケーションの対象となります。

### 読み取り専用データ
Goバイナリには、変更されないデータ（文字列定数、型情報など）が格納される読み取り専用セクションがあります。これらのデータはプログラムの実行中に変更されることはなく、通常はバイナリの`.rodata`セクションに配置されます。

### サフィックス配列 (Suffix Array)
サフィックス配列は、文字列`S`のすべてのサフィックス（接尾辞）を辞書順にソートした配列です。これにより、文字列`S`内の任意の部分文字列の出現箇所を効率的に検索することができます。このコミットでは、Goバイナリ内のすべての読み取り専用文字列を連結した巨大な文字列に対してサフィックス配列を構築し、各文字列が他の文字列の部分文字列として存在するかどうかを高速に検出するために利用されています。

### `index/suffixarray`パッケージ
Go標準ライブラリの`index/suffixarray`パッケージは、サフィックス配列を構築し、それを用いて部分文字列の検索を行う機能を提供します。このコミットでは、このパッケージが文字列の重複排除の核となるアルゴリズムとして採用されています。

## 技術的詳細

この変更は、Goリンカの`cmd/link/internal/ld/mergestrings.go`ファイルに実装されています。`mergestrings`関数は、Goバイナリ内のすべての到達可能な読み取り専用文字列を処理し、それらを単一の大きなシンボル`go.string.alldata`に結合する役割を担っています。このコミットは、この結合プロセスに文字列の重複排除ロジックを追加します。

1.  **文字列の収集とソート**:
    まず、リンカによって到達可能と判断されたすべての読み取り専用文字列（`*LSym`）が収集されます。これらの文字列は、`strSymsByLen`という新しい型によって、その長さが短い順にソートされます。長さが同じ場合は、バイト列の辞書順でソートされます。このソート順は重要で、短い文字列から処理することで、より長い文字列の部分文字列として短い文字列を効率的に見つけ、重複排除の恩恵を最大化します。また、これにより、後で到達不能とマークされる可能性のある文字列の部分文字列を使用しないようにします。

2.  **サフィックス配列の構築**:
    ソートされたすべての文字列のバイトデータを連結し、一つの巨大なバイト列`data`を作成します。この`data`に対して`index/suffixarray.New(data)`を呼び出し、サフィックス配列`index`を構築します。このサフィックス配列は、`data`内の任意の部分文字列の出現箇所を高速に検索するために使用されます。

3.  **部分文字列の検索と置換の決定**:
    各文字列`s`について、そのバイトデータ`s.P`がサフィックス配列`index`内で検索されます（`index.Lookup(s.P, -1)`）。検索結果は、`s.P`が出現する`data`内のオフセットのリストです。
    *   最も大きなオフセット（`res`）が選択されます。これは、ソート順の特性を活かし、より長い文字列の部分文字列として見つけるためです。
    *   `res`がどの元の文字列`strs[x]`のどのオフセット`off`に該当するかを特定します。
    *   自己参照（`x == i`）や、部分文字列が元の文字列の境界をまたぐ場合、アライメント要件を満たさない場合（`off%Thearch.Minalign != 0`）はスキップされます。
    *   有効な部分文字列が見つかった場合、その文字列`s`は、より長い文字列`strs[x]`のオフセット`off`に置き換えられるべきであると判断され、`replacements`マップに記録されます。

4.  **リロケーションの調整とデータ結合**:
    すべての文字列は、最終的に`go.string.alldata`という単一のシンボルに結合されます。
    *   各文字列`str`について、`replacements`マップにエントリがあるか確認します。
    *   もし`str`が置き換え対象であれば、その`str`を参照していたすべてのリロケーション（`relocsToStrs[str]`）は、置き換え先の文字列`rep.str`のリロケーションリストに移動されます。この際、リロケーションのオフセット（`r.Add`）は、`rep.off`（置き換え先の文字列内でのオフセット）だけ調整されます。これにより、元の文字列データは`go.string.alldata`には追加されず、バイナリサイズが削減されます。
    *   置き換え対象でない文字列は、そのまま`go.string.alldata`にそのデータが追加されます。追加後、その文字列を参照していたリロケーションは、`go.string.alldata`内の新しいオフセットに調整され、参照シンボルも`alldata`に変更されます。

このプロセスにより、重複する文字列データがバイナリから物理的に削除され、その参照が既存のより長い文字列の部分文字列を指すように変更されます。これにより、バイナリサイズが削減されます。コミットメッセージによると、`juju`というプロジェクトで765KB（DWARFなしで1.4%）のサイズ削減が達成されたとのことです。

## コアとなるコードの解説

### `strSymsByLen`型

```go
// strSymsByLen implements sort.Interface. It sorts *LSym by the length of P.
type strSymsByLen []*LSym

func (s strSymsByLen) Len() int      { return len(s) }
func (s strSymsByLen) Swap(i, j int) { s[i], s[j] = s[j], s[i] }
func (s strSymsByLen) Less(i, j int) bool {
	if len(s[i].P) == len(s[j].P) {
		return bytes.Compare(s[i].P, s[j].P) == -1
	}
	return len(s[i].P) < len(s[j].P)
}
```
この新しい型は、`sort.Interface`を実装しており、`*LSym`のスライスをソートするために使用されます。ソートの基準は、まず`LSym`が持つバイトデータ`P`の長さです。短い文字列が先にくるようにソートされます。長さが同じ場合は、`bytes.Compare`を使用してバイト列の辞書順でソートされます。このソート順は、部分文字列の検出において、短い文字列が常に長い文字列よりも先に処理されることを保証し、効率的な重複排除を可能にします。

### サフィックス配列の構築と検索ロジック

```go
	// Sort the strings, shortest first.
	// ... (コメント省略) ...
	sort.Sort(strSymsByLen(strs))

	// Build a suffix array.
	dataOff := make([]int, len(strs))
	data := make([]byte, 0, size)
	for i := range strs {
		dataOff[i] = len(data)
		data = append(data, strs[i].P...)
	}
	index := suffixarray.New(data)

	// Search for substring replacements.
	type replacement struct {
		str *LSym
		off int
	}
	replacements := make(map[*LSym]replacement)
	for i, s := range strs {
		results := index.Lookup(s.P, -1)
		if len(results) == 0 {
			continue
		}
		var res int
		for _, result := range results {
			if result > res {
				res = result
			}
		}
		var off int
		x := sort.SearchInts(dataOff, res)
		if x == len(dataOff) || dataOff[x] > res {
			x--
			off = res - dataOff[x]
		}
		if x == i {
			continue // found ourself
		}
		if len(s.P) > len(strs[x].P[off:]) {
			// Do not use substrings that match across strings.
			// ... (コメント省略) ...
			continue
		}
		if off%Thearch.Minalign != 0 {
			continue // Cannot relcate to this substring.
		}
		replacements[s] = replacement{
			str: strs[x],
			off: off,
		}
	}
```
1.  **ソート**: まず、前述の`strSymsByLen`を使ってすべての文字列がソートされます。
2.  **データ連結とオフセット記録**: ソートされた文字列のバイトデータが`data`バイトスライスに順次連結されます。同時に、各文字列が`data`内でどこから始まるかのオフセットが`dataOff`スライスに記録されます。
3.  **サフィックス配列構築**: 連結された`data`バイトスライスから`suffixarray.New(data)`を用いてサフィックス配列`index`が構築されます。
4.  **部分文字列検索**: 各文字列`s`（短い順に処理される）について、そのバイトデータ`s.P`が`index.Lookup`を使って`data`内で検索されます。`index.Lookup`は、`s.P`が出現するすべての開始オフセットを返します。
5.  **最適な置換の選択**: 複数の出現箇所が見つかった場合、最も大きなオフセット`res`が選択されます。これは、ソート順により、より長い文字列の部分文字列として見つける可能性が高いためです。
6.  **元の文字列とオフセットの特定**: `sort.SearchInts`を使って`res`が`dataOff`内のどの文字列`strs[x]`に属するか、そしてその文字列内でのオフセット`off`を特定します。
7.  **条件チェック**:
    *   自己参照（`x == i`）はスキップされます。
    *   部分文字列が元の文字列の境界をまたぐ場合（`len(s.P) > len(strs[x].P[off:])`）はスキップされます。これは、実装の複雑さを避けるためと、そのようなケースが稀であるためです。
    *   アライメント要件（`off%Thearch.Minalign != 0`）を満たさないオフセットはスキップされます。これは、リロケーションが正しく機能するために必要です。
8.  **置換の記録**: 上記の条件をすべて満たす場合、文字列`s`は`strs[x]`のオフセット`off`に置き換えられるべきであると判断され、`replacements`マップに記録されます。

### リロケーションの調整とデータ結合

```go
 	// Put all string data into a single symbol and update the relocations.
 	alldata := Linklookup(Ctxt, "go.string.alldata", 0)
 	alldata.Type = obj.SGOSTRING
 	alldata.Attr |= AttrReachable
 	alldata.P = make([]byte, 0, size)
 	for _, str := range strs {
 		str.Attr.Set(AttrReachable, false)
 		if rep, isReplaced := replacements[str]; isReplaced {
 			// As strs is sorted, the replacement string
 			// is always later in the strs range. Shift the
 			// relocations to the replacement string symbol
 			// and process then.
 			relocs := relocsToStrs[rep.str]
 			for _, r := range relocsToStrs[str] {
 				r.Add += int64(rep.off)
 				relocs = append(relocs, r)
 			}
 			relocsToStrs[rep.str] = relocs
 			continue
 		}

 		off := len(alldata.P)
 		alldata.P = append(alldata.P, str.P...)
 		// Architectures with Minalign > 1 cannot have relocations pointing
 		// to unaligned addresses. Pad with zeros.
 		for r := len(alldata.P) % Thearch.Minalign; r > 0; r-- {
 			alldata.P = append(alldata.P, 0)
 		}
 		for _, r := range relocsToStrs[str] {
 			r.Add += int64(off)
 			r.Sym = alldata
 		}
 	}
 	alldata.Size = int64(len(alldata.P))
```
この部分では、すべての文字列が`go.string.alldata`という単一のシンボルに結合され、同時にリロケーションが調整されます。
1.  **到達可能性のマーク解除**: 各文字列`str`は、まず`AttrReachable`属性が`false`に設定されます。これは、元の文字列データが直接バイナリに書き込まれるのではなく、`go.string.alldata`を通じて参照されることを意味します。
2.  **置換された文字列の処理**: `replacements`マップに`str`のエントリがある場合（つまり、`str`が他の文字列の部分文字列として置き換えられる場合）、以下の処理が行われます。
    *   `str`を参照していたすべてのリロケーション（`relocsToStrs[str]`）が取得されます。
    *   これらのリロケーションのオフセット`r.Add`は、置き換え先の文字列`rep.str`内でのオフセット`rep.off`だけ増加されます。
    *   調整されたリロケーションは、`rep.str`のリロケーションリスト（`relocsToStrs[rep.str]`）に追加されます。これにより、`str`のデータは`go.string.alldata`には追加されず、`rep.str`のデータが共有されます。
3.  **置換されていない文字列の処理**: `str`が置き換え対象でない場合、そのデータ`str.P`は`go.string.alldata.P`に直接追加されます。
    *   アライメント要件を満たすために、必要に応じてゼロがパディングされます。
    *   `str`を参照していたすべてのリロケーションは、`go.string.alldata`内での新しいオフセット`off`だけ増加され、参照シンボルも`alldata`に変更されます。

この一連の処理により、Goバイナリ内の読み取り専用文字列の重複が効率的に排除され、バイナリサイズの削減が実現されます。

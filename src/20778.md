## 元コミット内容

Goリンカ (`cmd/ld`) において、Dwarf Frame Description Entry (FDE) の最終アドレスに対して行番号情報を追加しないように変更しました。これにより、`dwardump --verify` ツールが期待通りに動作するようになります。

## 変更の背景

このコミットは、Goのリンカが生成するDwarfデバッグ情報に存在する、特定の不整合を修正するために行われました。Dwarfは、コンパイルされたプログラムのデバッグを可能にするための標準的なデバッグ情報フォーマットです。特に、スタックフレームの情報を記述するFrame Description Entry (FDE) は、デバッガが関数呼び出しのスタックトレースを正確に再構築するために不可欠です。

問題は、リンカがFDEの情報を生成する際に、関数の終了アドレス（またはその直後）に対して誤って行番号情報を関連付けてしまうことにありました。Dwarfの仕様では、FDEの範囲は関数のコード領域全体をカバーしますが、行番号情報は通常、実行可能なコードの各命令に対応付けられます。関数の「最終アドレス」は、多くの場合、次の関数の開始点や、関数の実行が終了した後のメモリ位置を指すため、そこに特定のソースコードの行番号を関連付けるのは不適切です。

この不適切な情報が原因で、Dwarfデバッグ情報を検証するツール、例えば `dwardump --verify` がエラーを報告していました。`dwardump` は、Dwarfデバッグ情報の整合性をチェックするためのユーティリティであり、その検証に失敗するということは、生成されたデバッグ情報がDwarfの仕様に完全に準拠していないか、デバッガが誤解釈する可能性があることを意味します。

したがって、このコミットの目的は、Dwarfデバッグ情報の正確性を向上させ、デバッグツールとの互換性を確保することにありました。コミットメッセージにある `#8846` は、この問題がGoのIssueトラッカーで追跡されていたことを示唆しています。

## 前提知識の解説

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッグを可能にするために、コンパイラやリンカによって生成されるデバッグ情報の標準フォーマットです。実行可能ファイルに埋め込まれるか、別のファイルとして提供されます。DWARF情報は、変数、型、関数、ソースコードの行番号と実行可能コードのアドレスのマッピング、スタックフレームの構造など、プログラムの実行時の状態をソースコードレベルで理解するために必要な情報を提供します。

### FDE (Frame Description Entry)

FDEは、DWARFデバッグ情報の一部であり、特定の関数（またはコードの範囲）のスタックフレームの構造と、その関数内でのレジスタの保存・復元方法を記述します。デバッガはFDE情報を使用して、関数呼び出しのバックトレースを生成したり、特定の時点でのレジスタの値を復元したりします。FDEは通常、そのFDEが記述するコードの開始アドレスと終了アドレスの範囲を持ちます。

### 行番号情報 (Line Number Information)

DWARFの行番号情報は、実行可能コードのアドレスとソースコードのファイル名、行番号、列番号をマッピングします。これにより、デバッガはプログラムの実行がどのソースコードの行に対応するかを正確に表示できます。

### `cmd/ld` (Go リンカ)

`cmd/ld` は、Go言語のプログラムをビルドする際に使用されるリンカです。コンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合し、最終的な実行可能ファイルを生成します。この過程で、デバッグ情報（DWARFを含む）も生成し、実行可能ファイルに埋め込みます。

### `dwardump --verify`

`dwardump` は、Dwarfデバッグ情報を解析・表示するためのツールです。`--verify` オプションは、Dwarf情報の整合性や仕様への準拠をチェックするために使用されます。このツールがエラーを報告するということは、生成されたDwarf情報に何らかの問題があることを示します。

### `pciterinit`, `pciternext`, `putpccfadelta`

これらは、GoリンカのDwarf生成コード内で使用される内部関数や構造体に関連する概念です。
- `pciterinit`: プログラムカウンタ (PC) のイテレータを初期化します。特定の関数のコード範囲をPC値で走査するために使用されます。
- `pciternext`: PCイテレータを次のPC値に進めます。
- `putpccfadelta`: PCとCFA (Canonical Frame Address) のデルタ情報をDwarfフレーム情報に書き込みます。これは、特定のPC値におけるスタックフレームの構造変化を記述するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、GoリンカがDwarfフレーム情報を生成する際の、関数のコード範囲の終端処理の修正にあります。

DwarfのFDEは、そのFDEがカバーするコードの範囲を定義します。この範囲は通常、関数の開始アドレスから終了アドレスまでです。行番号情報は、この範囲内の各実行可能命令に対応付けられます。しかし、関数の「最終アドレス」は、その関数内の最後の命令のアドレスではなく、その関数が占めるメモリ領域の「次のバイト」を指すことがあります。Dwarfの行番号テーブルでは、通常、コードの実行が終了する直前までのアドレスに対して行番号情報が提供されます。関数の終了アドレス自体に、意味のあるソースコードの行番号を関連付けることは稀であり、多くの場合、不適切です。

既存の実装では、`pciterinit` と `pciternext` を使用して関数のPC範囲を走査していました。このイテレータは、関数のコード領域の「終わり」まで（つまり、関数のサイズに等しいPC値まで）進むように設計されていました。これにより、`putpccfadelta` が呼び出される際に、関数の最終アドレス（`s->size`）に対応する `nextpc` の値が渡される可能性がありました。

コミット前のコードでは、`for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp))` ループ内で、`putpccfadelta(pcsp.nextpc - pcsp.pc, PtrSize + pcsp.value);` が直接呼び出されていました。ここで `pcsp.nextpc` は、現在のPC範囲の次のアドレスを示します。問題は、この `pcsp.nextpc` が関数のサイズ (`s->size`) と等しくなる場合に発生しました。このとき、`s->size` は関数のコードの「終わり」を意味し、そこに新たな行番号情報を追加するのはDwarfのセマンティクスに反していました。

修正は、この `nextpc` の値が関数のサイズと等しい場合に、その値をデクリメント (`nextpc--`) することで、関数の最後の命令のアドレスを指すように調整することです。これにより、Dwarfの行番号情報が関数の実際のコード領域の終端を超えて生成されることを防ぎます。

さらに、`nextpc--` を行った結果、`nextpc` が `pcsp.pc` よりも小さくなってしまう（つまり、範囲が逆転してしまう）エッジケースを考慮し、その場合は `continue` して処理をスキップするガード句が追加されています。これは、非常に短い関数や、関数のサイズが小さい場合に発生する可能性のある、無効な範囲指定を防ぐためのものです。

この変更により、生成されるDwarfデバッグ情報がより正確になり、`dwardump --verify` のような検証ツールが期待通りにパスするようになります。

## コアとなるコードの解説

変更の核心は、`for` ループ内の `putpccfadelta` の呼び出し方法にあります。

**変更前:**

```c
		for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp))
			putpccfadelta(pcsp.nextpc - pcsp.pc, PtrSize + pcsp.value);
```
ここでは、`pcsp.nextpc` が直接 `putpccfadelta` に渡されていました。`pcsp.nextpc` は、現在のPC範囲の次のアドレスを示します。`pciterinit` は関数の最後まで（`s->size` まで）イテレートするため、最後のイテレーションでは `pcsp.nextpc` が `s->size` と等しくなる可能性がありました。

**変更後:**

```c
		for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp)) {
			uint32 nextpc = pcsp.nextpc; // nextpc を一時変数にコピー

			// pciterinit goes up to the end of the function,
			// but DWARF expects us to stop just before the end.
			if(nextpc == s->size) { // nextpc が関数のサイズと等しい場合（関数の終端）
				nextpc--; // nextpc を1減らす（関数の最後の命令のアドレスを指すように調整）
				if(nextpc < pcsp.pc) // 調整後、nextpc が現在のpcsp.pcより小さくなった場合（無効な範囲）
					continue; // このエントリはスキップ
			}
			putpccfadelta(nextpc - pcsp.pc, PtrSize + pcsp.value);
		}
```

1.  `uint32 nextpc;` がループの外で宣言され、ループ内で `nextpc = pcsp.nextpc;` として現在の `pcsp.nextpc` の値がコピーされます。
2.  `if(nextpc == s->size)` という条件が追加されました。これは、`nextpc` が関数の終端アドレス（関数のサイズ）と一致するかどうかをチェックします。
3.  もし一致した場合、`nextpc--;` によって `nextpc` の値が1デクリメントされます。これにより、Dwarfの行番号情報が関数の実際のコード領域の終端を超えて生成されることを防ぎます。Dwarfの行番号テーブルは、通常、コードの実行が終了する直前までのアドレスに対して情報を提供するため、この調整はDwarfのセマンティクスに合致します。
4.  さらに、`if(nextpc < pcsp.pc)` というガード句が追加されました。これは、`nextpc--` を行った結果、`nextpc` が現在の `pcsp.pc` よりも小さくなってしまう（つまり、範囲が逆転してしまう）ようなエッジケース（例えば、非常に短い関数で `s->size` が `pcsp.pc + 1` のような場合）を考慮したものです。このような無効な範囲指定はDwarfの仕様に反するため、`continue` してこのエントリの処理をスキップします。

この修正により、リンカはDwarf FDEの行番号情報をより正確に生成し、`dwardump --verify` のようなツールが期待通りに動作するようになります。

既存の実装では、`pciterinit` と `pciternext` を使用して関数のPC範囲を走査していました。このイテレータは、関数のコード領域の「終わり」まで（つまり、関数のサイズに等しいPC値まで）進むように設計されていました。これにより、`putpccfadelta` が呼び出される際に、関数の最終アドレス（`s->size`）に対応する `nextpc` の値が渡される可能性がありました。

コミット前のコードでは、`for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp))` ループ内で、`putpccfadelta(pcsp.nextpc - pcsp.pc, PtrSize + pcsp.value);` が直接呼び出されていました。ここで `pcsp.nextpc` は、現在のPC範囲の次のアドレスを示します。問題は、この `pcsp.nextpc` が関数のサイズ (`s->size`) と等しくなる場合に発生しました。このとき、`s->size` は関数のコードの「終わり」を意味し、そこに新たな行番号情報を追加するのはDwarfのセマンティクスに反していました。

修正は、この `nextpc` の値が関数のサイズと等しい場合に、その値をデクリメント (`nextpc--`) することで、関数の最後の命令のアドレスを指すように調整することです。これにより、Dwarfの行番号情報が関数の実際のコード領域の終端を超えて生成されることを防ぎます。

さらに、`nextpc--` を行った結果、`nextpc` が `pcsp.pc` よりも小さくなってしまう（つまり、範囲が逆転してしまう）エッジケースを考慮し、その場合は `continue` して処理をスキップするガード句が追加されています。これは、非常に短い関数や、関数のサイズが小さい場合に発生する可能性のある、無効な範囲指定を防ぐためのものです。

この変更により、生成されるDwarfデバッグ情報がより正確になり、`dwardump --verify` のような検証ツールが期待通りにパスするようになります。

## コアとなるコードの解説

変更の核心は、`for` ループ内の `putpccfadelta` の呼び出し方法にあります。

**変更前:**

```c
		for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp))
			putpccfadelta(pcsp.nextpc - pcsp.pc, PtrSize + pcsp.value);
```
ここでは、`pcsp.nextpc` が直接 `putpccfadelta` に渡されていました。`pcsp.nextpc` は、現在のPC範囲の次のアドレスを示します。`pciterinit` は関数の最後まで（`s->size` まで）イテレートするため、最後のイテレーションでは `pcsp.nextpc` が `s->size` と等しくなる可能性がありました。

**変更後:**

```c
		for(pciterinit(ctxt, &pcsp, &s->pcln->pcsp); !pcsp.done; pciternext(&pcsp)) {
			uint32 nextpc = pcsp.nextpc; // nextpc を一時変数にコピー

			// pciterinit goes up to the end of the function,
			// but DWARF expects us to stop just before the end.
			if(nextpc == s->size) { // nextpc が関数のサイズと等しい場合（関数の終端）
				nextpc--; // nextpc を1減らす（関数の最後の命令のアドレスを指すように調整）
				if(nextpc < pcsp.pc) // 調整後、nextpc が現在のpcsp.pcより小さくなった場合（無効な範囲）
					continue; // このエントリはスキップ
			}
			putpccfadelta(nextpc - pcsp.pc, PtrSize + pcsp.value);
		}
```

1.  `uint32 nextpc;` がループの外で宣言され、ループ内で `nextpc = pcsp.nextpc;` として現在の `pcsp.nextpc` の値がコピーされます。
2.  `if(nextpc == s->size)` という条件が追加されました。これは、`nextpc` が関数の終端アドレス（関数のサイズ）と一致するかどうかをチェックします。
3.  もし一致した場合、`nextpc--;` によって `nextpc` の値が1デクリメントされます。これにより、Dwarfの行番号情報が関数の実際のコード領域の終端を超えて生成されることを防ぎます。Dwarfの行番号テーブルは、通常、コードの実行が終了する直前までのアドレスに対して情報を提供するため、この調整はDwarfのセマンティクスに合致します。
4.  さらに、`if(nextpc < pcsp.pc)` というガード句が追加されました。これは、`nextpc--` を行った結果、`nextpc` が現在の `pcsp.pc` よりも小さくなってしまう（つまり、範囲が逆転してしまう）ようなエッジケース（例えば、非常に短い関数で `s->size` が `pcsp.pc + 1` のような場合）を考慮したものです。このような無効な範囲指定はDwarfの仕様に反するため、`continue` してこのエントリの処理をスキップします。

この修正により、リンカはDwarf FDEの行番号情報をより正確に生成し、`dwardump --verify` のようなツールが期待通りに動作するようになります。

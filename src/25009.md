# [インデックス 25009] ファイルの概要

このコミットは、Goランタイムのテストスイートに含まれる `recover4` テストにおける、特定のアーキテクチャ（ARM64）でのみ発生する稀なメモリ割り当ての競合問題を修正するものです。具体的には、`munmap` によるメモリ領域の解放と、その後のGoランタイムによる新たなメモリ割り当ての順序が原因で、カーネルが予期せぬメモリの再マッピングを行う挙動を回避するための変更が加えられています。

## 元コミット内容

`test: move allocation before munmap in recover4`

`recover4` テストは `mmap` を介して16ページ分のメモリを割り当て、その中に `munmap` で4ページ分の穴を開け、その後通常の割り当てでさらに16ページ分のメモリを割り当て、最後にそれらの間でコピーを試みます。なぜかARM64上でのみ（他のテストしたプラットフォームでは発生しない）、2回目の割り当てがランタイムにカーネルへ4ページ分の追加メモリを要求させることがあり、カーネルはこれを、ちょうど `munmap` で解放されたばかりのページを再マッピングすることで満たしていました。

2回目の割り当てを `munmap` の前に移動することで、この挙動は修正されます。この修正により、`recover4` を何万回も失敗なく実行できるようになりました。修正前は約0.5%の失敗率でした。

`Fixes #12549`

## 変更の背景

この変更は、Goランタイムの `recover4` テストがARM64アーキテクチャ上で稀に失敗するという問題に対処するために行われました。`recover4` テストは、メモリの割り当てと解放、そしてその後のメモリコピー操作を通じて、Goプログラムがクラッシュから回復するメカニズムを検証することを目的としています。

問題の根本原因は、`mmap` で確保したメモリ領域の一部を `munmap` で解放した後、Goランタイムがヒープから新たなメモリを割り当てようとした際に、Linuxカーネルが以前 `munmap` で解放されたばかりの仮想メモリページを再利用（再マッピング）してしまうという、特定のタイミングとカーネルの挙動にありました。これにより、テストが期待するメモリレイアウトが崩れ、不正なメモリアクセスやテストの失敗につながっていました。

特にARM64でのみこの問題が顕著に発生したことから、メモリ管理ユニット（MMU）の挙動や、カーネルの仮想メモリ管理戦略が他のアーキテクチャと異なる、あるいは特定の条件下で異なる最適化を行うことが示唆されます。この問題は、GoランタイムがOSからメモリを要求する際の挙動と、OSカーネルがその要求をどのように処理するかの間の相互作用における、微妙な競合状態を浮き彫りにしました。

## 前提知識の解説

### 仮想メモリ管理 (`mmap`, `munmap`)

現代のオペレーティングシステム（OS）は、プロセスごとに「仮想メモリ」という抽象化されたメモリ空間を提供します。これにより、各プロセスは独立した広大なメモリ空間を持っているかのように振る舞うことができます。

*   **`mmap` (memory map)**: プロセスが仮想メモリ空間内に新しいメモリ領域を確保したり、ファイルの内容をメモリにマッピングしたりするために使用されるシステムコールです。`recover4` テストでは、これを使って大きな匿名メモリ領域（ファイルに関連付けられていないメモリ）を確保しています。
*   **`munmap` (memory unmap)**: `mmap` で確保された仮想メモリ領域を解放するために使用されるシステムコールです。これにより、その仮想アドレス範囲はプロセスのアドレス空間から削除され、対応する物理メモリページもOSに返却されるか、他の用途に再利用可能になります。

`recover4` テストでは、`mmap` で確保した領域の中央に `munmap` で「穴」を開けることで、不連続なメモリ領域を作成し、その後のメモリ操作がどのように振る舞うかをテストしています。

### Goのメモリ管理とランタイム

Goランタイムは、プログラムのメモリ割り当てと解放を自動的に管理します（ガベージコレクション）。Goプログラムが `make` を使ってメモリを要求すると、ランタイムはまず自身の管理するヒープ領域からメモリを割り当てようとします。ヒープに十分なメモリがない場合、ランタイムはOSに対して `mmap` などのシステムコールを使って新たなメモリ領域を要求します。

Goランタイムは、OSから取得したメモリをページ単位で管理し、必要に応じて小さなオブジェクトに分割してユーザープログラムに提供します。メモリが解放されると、ランタイムはそれを再利用可能な状態に戻しますが、OSにすぐに返却するとは限りません。

### `recover4` テストの目的

`recover4` テストは、Goプログラムがメモリ関連の障害（例えば、不正なメモリアクセス）から回復できるかどうかを検証するテストの一つです。この種のテストは、Goランタイムの堅牢性を保証するために重要であり、特にOSとのメモリ管理の相互作用におけるエッジケースを検出することを目的としています。

テストのシナリオは以下の通りです。
1.  `mmap` で大きなメモリ領域を確保。
2.  その領域の中央に `munmap` で穴を開ける。
3.  別のメモリ領域を `make` で確保。
4.  穴の開いた領域から、新しく確保した領域へメモリコピーを試みる。
5.  このコピー操作中に発生する可能性のあるシグナル（例: `SIGSEGV`）を捕捉し、回復できることを確認する。

## 技術的詳細

問題は、`recover4` テストの元のロジックフローにありました。

1.  `data := syscall.Mmap(...)` で16ページ分のメモリを確保。
2.  `syscall.Munmap(data[4*size:8*size], 4*size)` で `data` の中央に4ページ分の穴を開ける。
3.  `other := make([]byte, 16*size)` でGoランタイムを通じて別の16ページ分のメモリを割り当てる。
4.  `memcopy(data[5:], other)` で `data` から `other` へメモリコピーを試みる。

ARM64プラットフォームでのみ、ステップ3の `make` 呼び出しが問題を引き起こしました。Goランタイムが `make` のためにOSにメモリを要求した際、Linuxカーネルは、ステップ2で `munmap` されたばかりの4ページ分の仮想アドレス空間を、新しい `make` の要求に対して再マッピングしてしまったのです。

これは、カーネルの仮想メモリ管理の最適化戦略に起因すると考えられます。`munmap` されたメモリ領域は、すぐに他のプロセスや同じプロセスの別のメモリ要求に再利用される可能性があります。特に、解放されたばかりの領域が、次に要求されるメモリのサイズやアラインメントに合致する場合、カーネルは効率のためにそれを再利用しようとします。

ARM64アーキテクチャの特定の特性（例えば、ページテーブルの管理方法、TLBの挙動、または特定のカーネルバージョンでのメモリ割り当てアルゴリズム）が、この再マッピングの挙動を他のアーキテクチャよりも頻繁に、または特定のタイミングで引き起こした可能性があります。結果として、`data` 配列の一部が `munmap` されたにもかかわらず、その仮想アドレスが `other` 配列の一部として再マッピングされてしまい、`memcopy` 時に予期せぬメモリ内容の衝突や、不正なメモリ領域へのアクセスが発生し、テストが失敗していました。

この問題は、GoランタイムがOSからメモリを取得するタイミングと、OSがそのメモリをどのように管理・再利用するかの間の、デッドロックに近い競合状態を示しています。

## コアとなるコードの解説

この変更の核心は、メモリ割り当ての順序を入れ替えることです。

**変更前:**
1.  `mmap` で `data` を割り当てる。
2.  `munmap` で `data` の一部を解放する。
3.  `make` で `other` を割り当てる。

**変更後:**
1.  `mmap` で `data` を割り当てる。
2.  `make` で `other` を割り当てる。
3.  `munmap` で `data` の一部を解放する。

この順序の変更により、`other` のためのメモリが `munmap` で `data` の一部が解放される**前**にOSから要求され、割り当てられるようになります。

これにより、以下の問題が回避されます。
*   `munmap` によって解放された仮想アドレス空間が、Goランタイムが `make` のためにOSにメモリを要求した際に、カーネルによって即座に再利用される可能性がなくなります。
*   `other` が割り当てられる時点では、`data` の領域はまだ完全に割り当てられた状態であり、`munmap` による「穴」はまだ存在しません。これにより、カーネルが `other` のために割り当てるメモリが、`data` の一部と重複する可能性が根本的に排除されます。

結果として、`recover4` テストは、意図した通りのメモリレイアウトで実行されるようになり、ARM64上での稀な失敗が解消されました。この修正は、GoランタイムとOSカーネル間のメモリ管理の相互作用における、タイミングに依存する競合状態を効果的に解決したと言えます。

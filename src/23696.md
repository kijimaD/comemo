# [インデックス 23696] ファイルの概要

このコミットは、Goランタイムにおける`GOMAXPROCS`環境変数のデフォルト値を、従来の`1`からシステムが持つ論理CPUの数（`NumCPU()`）に変更するものです。これにより、Goプログラムはデフォルトで利用可能なすべてのCPUコアを活用し、並列処理の恩恵を最大限に受けられるようになります。

## 変更の背景

Go言語の初期バージョンでは、`GOMAXPROCS`のデフォルト値は`1`に設定されていました。これは、Goのスケジューラがまだ成熟しておらず、複数のOSスレッド（P: Processor）を使用した場合に、コンテキストスイッチのオーバーヘッドやキャッシュの競合などにより、かえってパフォーマンスが低下する可能性があったためです。特に、GoのスケジューラはユーザーレベルのゴルーチンをOSスレッドにマッピングするM:Nスケジューリングモデルを採用しており、このM:Nスケジューラが効率的に機能するためには、適切な`GOMAXPROCS`の設定が重要でした。

しかし、Go 1.1以降、スケジューラの改善が重ねられ、特にGo 1.5では大幅な改良が加えられました。これらの改善により、複数のOSスレッドを使用した場合のオーバーヘッドが大幅に削減され、多くのGoプログラムがデフォルトで並列処理の恩恵を受けられるようになりました。このコミットは、Go 1.5におけるスケジューラの成熟を背景に、デフォルトの`GOMAXPROCS`値を`NumCPU()`に変更することで、Goプログラムのデフォルトのパフォーマンスを向上させることを目的としています。

この変更は、Goプログラムが明示的に`GOMAXPROCS`を設定しない限り、システムが持つすべてのCPUコアを自動的に利用するようになることを意味します。これにより、特に並列処理を前提としたアプリケーションにおいて、設定なしで高いパフォーマンスを発揮できるようになります。

## 前提知識の解説

### GOMAXPROCSとは

`GOMAXPROCS`は、Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数、またはGoの`runtime`パッケージの関数です。Goのスケジューラは、Goプログラム内で作成される軽量な並行処理単位である「ゴルーチン（goroutine）」を、OSスレッド上で実行します。`GOMAXPROCS`は、このゴルーチンを実行するためにGoランタイムが利用するOSスレッド（Goの用語では「P (Processor)」と呼ばれる論理プロセッサ）の数を決定します。

*   **`GOMAXPROCS=1`**: Goランタイムは1つのOSスレッドのみを使用してゴルーチンを実行します。これにより、並行処理は行われますが、真の並列処理（複数のCPUコアでの同時実行）は行われません。これは、I/Oバウンドな処理や、スケジューラのオーバーヘッドが大きかった初期のGoバージョンで有効な設定でした。
*   **`GOMAXPROCS > 1`**: Goランタイムは指定された数のOSスレッドを使用してゴルーチンを実行します。これにより、複数のCPUコアが利用可能なシステムでは、複数のゴルーチンが同時に異なるCPUコアで実行され、真の並列処理が実現されます。

### Goのスケジューラ (M:Nスケジューリング)

Goランタイムは、M個のゴルーチンをN個のOSスレッドにマッピングする「M:Nスケジューリング」モデルを採用しています。
*   **G (Goroutine)**: Goの軽量な並行処理単位。数百万個作成することも可能。
*   **M (Machine/OS Thread)**: OSが管理するスレッド。CPUコア上で実際にコードを実行する。
*   **P (Processor)**: Goランタイムが管理する論理プロセッサ。MとGの間のコンテキストとして機能し、GをMにディスパッチする役割を担う。`GOMAXPROCS`はこのPの数を決定します。

Goのスケジューラは、Pの数に基づいてMを生成し、各Pに実行可能なGを割り当てます。Pはローカルな実行キューを持ち、Gを効率的に実行します。`GOMAXPROCS`の値を増やすことは、利用可能なPの数を増やすことであり、これによりより多くのOSスレッドが同時にゴルーチンを実行できるようになります。

### `NumCPU()`

`runtime.NumCPU()`関数は、現在のシステムが持つ論理CPUコアの数を返します。これは、ハイパースレッディングなどの技術を考慮した、OSが利用可能と報告するCPUの総数です。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムの初期化プロセスにおいて、`GOMAXPROCS`のデフォルト値を設定するロジックを変更した点にあります。

変更前は、`src/runtime/proc1.go`の`schedinit()`関数内で、`procs`変数が明示的に`1`に初期化されていました。これは、ユーザーが`GOMAXPROCS`環境変数を設定しない限り、Goプログラムが単一のOSスレッドで実行されることを意味していました。

変更後は、`procs`変数が`int(ncpu)`、つまり`runtime.NumCPU()`が返す値に初期化されるようになりました。これにより、Goプログラムはデフォルトでシステムが持つすべての論理CPUコアを利用してゴルーチンを並列実行するようになります。

この変更が可能になったのは、Go 1.5で導入された以下のスケジューラ改善が大きく寄与しています。
1.  **プリエンプティブスケジューリングの強化**: Go 1.2で導入されたプリエンプティブスケジューリングがさらに改善され、長時間実行されるゴルーチンが他のゴルーチンの実行を妨げることが少なくなりました。
2.  **GCの並列化**: Go 1.5では、ガベージコレクタ（GC）が大幅に改良され、並列実行されるようになりました。`GOMAXPROCS > 1`の場合、GCは複数のCPUコアを利用してより高速に動作します。
3.  **スケジューラのオーバーヘッド削減**: 複数のOSスレッド間でのゴルーチンの移動やコンテキストスイッチのオーバーヘッドが削減され、`GOMAXPROCS > 1`でも効率的に動作するようになりました。

この変更により、多くのGoプログラムは追加の設定なしに、マルチコアプロセッサの性能を最大限に引き出すことができるようになります。特に、CPUバウンドな並列処理を行うアプリケーションでは、デフォルトで大幅なパフォーマンス向上が期待されます。

一方で、この変更は、既存のGoプログラムに潜在するレースコンディションを顕在化させる可能性も指摘されました。`GOMAXPROCS=1`で実行されていたプログラムは、真の並列実行が行われないため、特定のレースコンディションが表面化しにくい場合があります。しかし、`GOMAXPROCS=NumCPU()`となることで、複数のゴルーチンが同時に共有リソースにアクセスする機会が増え、これまで隠れていたレースコンディションが露呈する可能性があります。Go開発チームは、Go 1.1で導入されたレース検出器や、Go 1.2以降のプリエンプティブスケジューリングによって、多くのレースコンディションは既に検出・修正されているはずだと考えていました。もし問題が発生した場合でも、ユーザーは明示的に`GOMAXPROCS=1`を設定することで、以前の動作に戻すことが可能です。

## コアとなるコードの解説

`src/runtime/proc1.go`ファイルは、Goランタイムの初期化に関する重要なロジックを含んでいます。
`schedinit()`関数は、Goプログラムの起動時に一度だけ呼び出され、スケジューラやガベージコレクタなどのランタイムコンポーネントを初期化します。

変更前のコード:
```go
	procs := 1
```
この行は、`GOMAXPROCS`のデフォルト値を`1`に設定していました。`procs`変数は、Goランタイムが利用する論理プロセッサ（P）の数を決定するための初期値として使われます。

変更後のコード:
```go
	procs := int(ncpu)
```
この行は、`procs`変数を`ncpu`（`runtime.NumCPU()`が返すシステムの論理CPU数）に初期化するように変更されました。これにより、明示的に`GOMAXPROCS`が設定されない限り、Goプログラムはデフォルトでシステムが持つすべてのCPUコアを利用するようになります。

その後のコードブロック:
```go
	if n := atoi(gogetenv("GOMAXPROCS")); n > 0 {
		if n > _MaxGomaxprocs {
			n = _MaxGomaxprocs
		}
		procs = n
	}
```
この部分は変更されていませんが、非常に重要です。これは、ユーザーが環境変数`GOMAXPROCS`を明示的に設定しているかどうかをチェックし、設定されていればその値を`procs`に適用します。これにより、ユーザーは依然として`GOMAXPROCS`の値を手動でオーバーライドすることが可能です。`_MaxGomaxprocs`は、`GOMAXPROCS`に設定できる最大値（通常は256）を定義しており、過度に大きな値が設定されるのを防ぎます。

このコミットは、Goランタイムのデフォルトの動作を根本的に変更し、Goプログラムがより効率的にマルチコア環境を活用できるようにするための重要な一歩となりました。

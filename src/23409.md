# [インデックス 23409] ファイルの概要

このコミットは、GoランタイムにおけるLinux/PPC64LEアーキテクチャでのシステムコール定義に関する修正です。具体的には、`_FILE_OFFSET_BITS`マクロの定義が`__LP64__`が定義されている環境で不要となり、`fcntl`システムコールに関連する定数の値がカーネルの期待する値と一致するように調整されています。

## 元コミット内容

`syscall: mkerrors.sh: don't define _FILE_OFFSET_BITS if __LP64__`

`__LP64__`が定義されている場合、型`long`は64ビットであるため、明示的に`_FILE_OFFSET_BITS == 64`を要求する必要はありません。この変更により、PPCアーキテクチャにおける`F_GETLK`、`F_SETLK`、`F_SETLKW`の定義が、カーネルが要求する値に修正されます。`_FILE_OFFSET_BITS == 64`が設定されたC言語で使われる値は、システムコールを行う前にglibcの`fcntl`関数によって修正されます。

この変更に伴い、Ubuntu trusty上でppc64leのファイルを再生成します。

## 変更の背景

このコミットの背景には、64ビットシステムにおけるファイルオフセットの扱いと、C標準ライブラリ（glibc）およびLinuxカーネル間の`fcntl`システムコール定数の解釈の違いがあります。

従来の32ビットシステムでは、ファイルオフセットは32ビット整数で表現されていました。しかし、4GBを超えるファイルを扱うためには、64ビットのファイルオフセットが必要になります。これを実現するために、POSIX標準では`_FILE_OFFSET_BITS`マクロを導入し、これを`64`に定義することで、`off_t`などのファイルオフセット関連の型を64ビットに拡張する仕組みが提供されました。また、`fcntl`などのシステムコールも、`_FILE_OFFSET_BITS=64`が定義されていると、対応する64ビット版のシステムコール（例: `fcntl64`）が呼ばれるようにglibcが仲介します。

しかし、`__LP64__`が定義されている64ビットアーキテクチャ（例: `ppc64le`）では、`long`型自体がすでに64ビット幅を持っています。このような環境では、`off_t`型もデフォルトで64ビットになるため、`_FILE_OFFSET_BITS 64`を明示的に定義することは冗長であり、場合によっては問題を引き起こす可能性があります。

特に、`fcntl`システムコールで使用されるコマンド定数（`F_SETLK`, `F_SETLKW`など）は、`_FILE_OFFSET_BITS`の定義の有無によってglibcが異なる値を内部的に使用することがあります。カーネルが期待する値と、glibcが`_FILE_OFFSET_BITS=64`を考慮して変換した後の値が異なる場合、Goプログラムから発行されるシステムコールが正しく解釈されず、予期せぬ動作やエラーにつながる可能性がありました。

このコミットは、`ppc64le`環境において、`__LP64__`が定義されている場合に`_FILE_OFFSET_BITS 64`の定義を抑制することで、`fcntl`関連の定数がカーネルが直接期待する値と一致するように修正し、システムコールの整合性を確保することを目的としています。

## 前提知識の解説

*   **`_FILE_OFFSET_BITS`**:
    C言語のコンパイル時に定義されるマクロの一つで、ファイルオフセット関連の型（`off_t`など）のビット幅を制御します。`_FILE_OFFSET_BITS 64`と定義すると、これらの型が64ビット幅になり、4GBを超えるファイルを扱う「ラージファイルサポート」が有効になります。これは主に32ビットシステムで64ビットファイルオフセットを扱うために使用されます。

*   **`__LP64__`**:
    コンパイラによって定義されるマクロで、現在のコンパイルターゲットがLP64データモデル（`long`型とポインタが64ビット幅）を使用していることを示します。Linux/PPC64LEのような64ビットシステムでは通常このマクロが定義されています。`__LP64__`が定義されている場合、`long`型はすでに64ビットであるため、`off_t`も通常は64ビットになります。

*   **`fcntl`システムコール**:
    ファイルディスクリプタの操作を行うためのシステムコールです。ファイルのロック（`F_SETLK`, `F_SETLKW`）、ファイルステータスフラグの取得/設定（`F_GETFL`, `F_SETFL`）など、多岐にわたる機能を提供します。`fcntl`はコマンド引数によってその動作が決定されます。

*   **`F_GETLK`, `F_SETLK`, `F_SETLKW`**:
    `fcntl`システムコールで使用されるコマンド定数で、ファイルのロックに関連する操作を指定します。
    *   `F_GETLK`: ファイルロックの情報を取得します。
    *   `F_SETLK`: ファイルロックを設定または解除します（非ブロック）。
    *   `F_SETLKW`: ファイルロックを設定または解除します（ブロック）。
    これらの定数の具体的な値は、システムやライブラリのバージョンによって異なる場合があります。

*   **glibc (GNU C Library)**:
    Linuxシステムで広く使われているC標準ライブラリです。アプリケーションからのシステムコールを仲介し、高レベルなAPIを低レベルなカーネルシステムコールに変換する役割を担います。`_FILE_OFFSET_BITS`のようなマクロの解釈や、32ビット/64ビット環境でのシステムコール引数の調整などもglibcが行います。

*   **PPC64LE (PowerPC 64-bit Little Endian)**:
    IBMが開発したPowerPCアーキテクチャの64ビット版で、リトルエンディアンのバイト順序を持つものです。Go言語は様々なアーキテクチャをサポートしており、PPC64LEもその一つです。

## 技術的詳細

このコミットの核心は、`_FILE_OFFSET_BITS`マクロが64ビット環境（`__LP64__`が定義されている場合）でどのように振る舞うか、そしてそれが`fcntl`システムコールのコマンド定数にどう影響するかという点にあります。

通常、32ビットシステムで`_FILE_OFFSET_BITS 64`を定義すると、`fcntl`システムコールは内部的に`fcntl64`という別のシステムコールを呼び出すようにglibcによって変換されます。この際、`F_SETLK`や`F_SETLKW`などのコマンド定数も、`fcntl64`に対応する値にglibcが変換します。例えば、32ビット環境で`_FILE_OFFSET_BITS 64`が定義されている場合、`F_SETLK`は`0xd`（13）として定義され、glibcがこれを`fcntl64`の適切なコマンドに変換します。

しかし、`ppc64le`のような64ビットシステムでは、`__LP64__`が定義されているため、`long`型はすでに64ビットです。この場合、`off_t`もデフォルトで64ビットになるため、`_FILE_OFFSET_BITS 64`を明示的に定義する必要はありません。さらに重要なのは、`__LP64__`環境では、glibcは`_FILE_OFFSET_BITS 64`が定義されていなくても、`fcntl`システムコールを直接64ビット対応として扱います。

問題は、`_FILE_OFFSET_BITS 64`が`__LP64__`環境で**誤って**定義されている場合に発生します。この場合、glibcは二重に「64ビット対応」の変換を試みるか、あるいは`_FILE_OFFSET_BITS 64`の定義によって、カーネルが期待する`fcntl`コマンド定数とは異なる値（32ビット環境で`_FILE_OFFSET_BITS 64`が定義された場合の値）をGoプログラムが使用してしまう可能性があります。

具体的には、`ppc64le`のLinuxカーネルが`F_SETLK`に対して期待する値は`0x6`（6）であり、`F_SETLKW`に対して期待する値は`0x7`（7）です。しかし、`_FILE_OFFSET_BITS 64`が定義されていると、Goの`mkerrors.sh`スクリプトが生成する定数ファイルでは、これらの値がそれぞれ`0xd`（13）と`0xe`（14）になっていました。これは、32ビットシステムで`_FILE_OFFSET_BITS 64`が定義された場合のglibcの挙動に合わせた値であり、`ppc64le`の64ビット環境で直接カーネルに渡す値としては不適切でした。

このコミットは、`mkerrors.sh`スクリプトにおいて、`__LP64__`が定義されている場合には`_FILE_OFFSET_BITS 64`の定義をスキップすることで、Goが生成するシステムコール定数がカーネルの期待する値と一致するように修正しています。これにより、`fcntl`システムコールが`ppc64le`環境で正しく機能するようになります。

`ztypes_linux_ppc64le.go`の`Sysinfo_t`構造体の変更は、`X_f`フィールドの型が`[0]byte`から`[0]uint8`に変更されていますが、これは主にGoの型システムにおける表現の整合性や、CgoによるC言語との相互運用性における細かな調整であり、今回の`fcntl`の定数問題とは直接的な関連はありませんが、`mkerrors.sh`の再生成に伴う副次的な変更である可能性が高いです。

## コアとなるコードの解説

*   **`src/syscall/mkerrors.sh`の変更**:
    この変更は、`_FILE_OFFSET_BITS 64`の定義を条件付きにすることで、64ビット環境での冗長な定義を排除します。`__LP64__`が定義されている（つまり、`long`型がすでに64ビットである）場合、`_FILE_OFFSET_BITS 64`を定義する必要はありません。この条件付き定義により、`mkerrors.sh`がCヘッダファイルを処理する際に、`fcntl`関連の定数がカーネルが期待する値に正しく解決されるようになります。これにより、glibcが余計な変換を行わず、Goプログラムが直接カーネルと整合性の取れたシステムコール定数を使用できるようになります。

*   **`src/syscall/zerrors_linux_ppc64le.go`の変更**:
    このファイルは`mkerrors.sh`によって自動生成されるため、`mkerrors.sh`の変更の結果として、`F_SETLK`と`F_SETLKW`の定数値が修正されました。
    *   `F_SETLK`が`0xd`から`0x6`へ: `0x6`はLinuxカーネルが`fcntl`システムコールにおける`F_SETLK`コマンドとして期待する値です。
    *   `F_SETLKW`が`0xe`から`0x7`へ: `0x7`はLinuxカーネルが`fcntl`システムコールにおける`F_SETLKW`コマンドとして期待する値です。
    これらの修正により、Goプログラムが`ppc64le`上で`fcntl`システムコールを呼び出す際に、カーネルが正しくコマンドを解釈し、ファイルロック操作が期待通りに機能するようになります。

*   **`src/syscall/ztypes_linux_ppc64le.go`の変更**:
    `Sysinfo_t`構造体の`X_f`フィールドの型が`[0]byte`から`[0]uint8`に変更されました。`[0]byte`と`[0]uint8`はGoにおいて実質的に同じ意味を持つことが多いですが、Cgoとの連携や特定のコンパイラ/リンカの挙動において、より明示的な`uint8`を使用することで、潜在的な互換性問題を回避したり、コード生成の整合性を高めたりする意図があると考えられます。この変更は、`mkerrors.sh`の再生成プロセスの一部として行われた可能性が高いです。

これらの変更は、Goの`syscall`パッケージがLinux/PPC64LEアーキテクチャで、特にファイルロックのような`fcntl`システムコールを介した操作において、カーネルとの正確なインターフェースを維持するために不可欠です。

## 変更の背景

この変更は、macOS (Darwin) の最新カーネルにおいて、Goランタイムに統合されたネットワークポーラーが`kevent`システムコールを使用する際に発生する問題に対処するために行われました。具体的には、TCP接続がまだ`SYN-SENT`状態であるにもかかわらず、`kevent`が誤って`ESTABLISHED`状態として報告することがありました。この「誤報」は、Goアプリケーションがまだ完全に確立されていないTCP接続を確立済みと誤認し、データの送受信を試みることで予期せぬエラーや接続の不安定さを引き起こす可能性がありました。コミットメッセージでは根本原因は不明とされていますが、この誤報を防ぐための対策が必要とされました。

## 前提知識の解説

### TCP 3-wayハンドシェイクと接続状態

TCP (Transmission Control Protocol) は、信頼性の高いデータ転送を提供するために3-wayハンドシェイクと呼ばれる接続確立プロセスを使用します。
1.  **SYN (Synchronize)**: クライアントがサーバーに接続要求を送信します。このとき、クライアント側のソケットは`SYN-SENT`状態になります。
2.  **SYN-ACK (Synchronize-Acknowledge)**: サーバーがクライアントの要求を受け入れ、自身のSYNとクライアントのSYNに対するACKを返します。サーバー側のソケットは`SYN-RCVD`状態になります。
3.  **ACK (Acknowledge)**: クライアントがサーバーのSYN-ACKに対するACKを返します。この時点で、クライアントとサーバーの両方のソケットは`ESTABLISHED`状態となり、データの送受信が可能になります。

### `SYN-SENT`状態と`ESTABLISHED`状態

*   **`SYN-SENT`**: クライアントが接続要求 (SYN) を送信したが、サーバーからの応答 (SYN-ACK) をまだ受信していない状態。接続はまだ確立されていません。
*   **`ESTABLISHED`**: 3-wayハンドシェイクが完了し、クライアントとサーバー間でデータの送受信が可能な状態。

### `kevent` (kqueue) とネットワークポーリング

`kevent`は、macOS (Darwin) やFreeBSDなどのBSD系OSで利用される、イベント通知インターフェースである`kqueue`の主要なシステムコールです。`kqueue`は、ファイルディスクリプタ（ソケットも含む）に対するI/Oイベント（読み込み可能、書き込み可能、エラーなど）を効率的に監視するために使用されます。Goランタイムのネットワークポーラーは、ノンブロッキングI/Oと組み合わせて`kqueue`を利用し、多数のネットワーク接続を同時に効率的に処理します。これにより、Goのゴルーチンがブロッキングすることなく、ネットワークI/Oを待機できるようになります。

### ノンブロッキングソケットと`connect`システムコール

通常の（ブロッキング）ソケットで`connect`システムコールを呼び出すと、3-wayハンドシェイクが完了するか、エラーが発生するまで呼び出し元はブロックされます。
一方、ノンブロッキングソケットで`connect`を呼び出すと、接続が即座に確立できない場合でも、`EINPROGRESS`（接続処理中）や`EALREADY`（既に接続処理中）などのエラーコードを返してすぐに制御を呼び出し元に戻します。この場合、アプリケーションは`kevent`などのイベント通知メカニズムを使用して、接続が確立された（または失敗した）ことを非同期に検出する必要があります。接続が確立されると、`getsockopt`システムコールで`SO_ERROR`オプションをチェックすることで、接続の最終的な状態（成功または失敗）を確認できます。

## 技術的詳細

この問題の核心は、Darwinカーネルの`kevent`が、TCP接続がまだ`SYN-SENT`状態であるにもかかわらず、誤って`ESTABLISHED`状態としてイベントを報告してしまう点にありました。Goのネットワークポーラーは`kevent`からの通知に基づいてソケットの状態を判断するため、この誤報はGoランタイムが接続確立を早まって完了したと判断し、アプリケーションに通知してしまう原因となります。

このコミットでは、この誤報を防ぐために、`netFD.connect`関数内で`syscall.EISCONN`（既に接続済み）または`syscall.Errno(0)`（エラーなし、つまり成功）が返された場合に、**追加の`connect`システムコール**を呼び出すというアプローチを採用しています。

なぜこのアプローチが有効なのかというと、コミットメッセージに「On Darwin, multiple connect system calls on a non-blocking socket never harm SO_ERROR.」とあるように、Darwinではノンブロッキングソケットに対して複数回`connect`システムコールを呼び出しても、ソケットの`SO_ERROR`状態に悪影響を与えないという特性があるためです。

具体的には、
1.  最初の`connect`呼び出しが`EINPROGRESS`を返し、`kevent`が接続完了を通知したとします。
2.  Goランタイムは`getsockopt`で`SO_ERROR`をチェックし、`EISCONN`または`Errno(0)`を受け取ります。
3.  しかし、これが`kevent`の誤報である可能性があるため、Darwinの場合に限り、**もう一度`connect`システムコールを呼び出します**。
4.  もし接続が本当に確立されていれば、この2回目の`connect`も`nil`または`EISCONN`を返します。
5.  もし接続がまだ`SYN-SENT`状態であったり、何らかの理由で確立されていなかったりすれば、2回目の`connect`は適切なエラー（例: `EINPROGRESS`、`ECONNREFUSED`など）を返すはずです。これにより、Goランタイムは正確な接続状態を把握し、誤った通知を防ぐことができます。

この修正は、`kevent`の誤報というカーネルレベルの挙動に起因する問題を、アプリケーションレベルで回避するための実用的なワークアラウンドと言えます。

## コアとなるコードの解説

### `src/net/fd_unix.go` の変更

`netFD.connect`関数は、GoのネットワークパッケージにおけるノンブロッキングTCP接続の確立を担当する重要な部分です。
変更の中心は、`syscall.Errno(nerr)`が`syscall.Errno(0)`（成功）または`syscall.EISCONN`（既に接続済み）を返した場合の処理です。

```go
			if runtime.GOOS != "darwin" {
				return nil
			}
			// See golang.org/issue/14548.
			// On Darwin, multiple connect system calls on
			// a non-blocking socket never harm SO_ERROR.
			switch err := connectFunc(fd.sysfd, ra); err {
			case nil, syscall.EISCONN:
				return nil
			}
```

このコードブロックは、現在のOSがDarwinでない場合は、以前と同様にすぐに`nil`（エラーなし）を返して接続確立を完了させます。しかし、OSがDarwinである場合は、`golang.org/issue/14548`で報告された問題に対処するため、追加の`connect`システムコール（`connectFunc`）を呼び出します。この2回目の`connect`呼び出しが`nil`または`syscall.EISCONN`を返した場合にのみ、実際の接続確立が成功したと判断し、`nil`を返します。これにより、`kevent`の誤報によって`EISCONN`が報告された場合でも、実際の接続状態を再確認し、誤った通知を防ぐことができます。

### `src/net/error_unix_test.go` の変更

`samePlatformError`関数は、テストコード内でエラー比較を容易にするために導入されました。Goの`net`パッケージは、`*OpError`や`*os.SyscallError`のようなカスタムエラー型でシステムコールエラーをラップすることがよくあります。このヘルパー関数は、これらのラッパーを剥がして、基となる`syscall.Errno`を直接比較できるようにします。これにより、特定のシステムコールエラー（例: `syscall.ENOTCONN`）が発生したかどうかを正確にテストできます。

### `src/net/tcpsock_unix_test.go` の新しいテスト

`TestTCPSupriousConnSetupCompletion`テストは、Darwin環境でのみ実行されるように設計されています。このテストの目的は、多数の同時接続試行をシミュレートし、`kevent`の誤報によって`SYN-SENT`状態のソケットが`ESTABLISHED`と誤認されるシナリオを再現し、修正が正しく機能することを確認することです。

テストの主要なロジックは以下の通りです。
1.  ローカルリスナー (`ln`) を作成し、バックグラウンドで`Accept`ループを実行します。これにより、クライアントからの接続を受け入れ、簡単な読み書きを行った後に閉じます。
2.  `attempts`回（10,000回）の接続試行を行います。
3.  各試行では、`Dialer`に短いタイムアウト（50ミリ秒）を設定して、ノンブロッキング接続の確立を試みます。
4.  接続が確立された後、クライアントは1バイトのデータを書き込みます。
5.  この書き込み操作でエラーが発生した場合、特に`syscall.ENOTCONN`（接続されていない）エラーが発生した場合は、テストを失敗させます。これは、接続が`ESTABLISHED`と誤認されたにもかかわらず、実際にはデータ送信ができない状態であったことを示唆するためです。

このテストは、Goのネットワークポーラーが`kevent`からの誤った`ESTABLISHED`通知を正しく処理し、まだ確立されていない接続に対して`Write`を試みた際に`ENOTCONN`のようなエラーが発生しないことを検証します。これにより、修正が意図した通りに機能していることが確認されます。

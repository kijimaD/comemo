# [インデックス 2087] ファイルの概要

このコミットは、Goコンパイラ（`gc`）におけるバグ修正を目的としています。具体的には、定義済みの定数が、その後の宣言（特に短い変数宣言 `:=`）において新しい名前として正しく認識されない問題に対処しています。この修正により、定数の再宣言やスコープ内での使用が、より直感的かつGo言語の仕様に沿った形で行えるようになります。

## 変更の背景

Go言語の初期のコンパイラ（`gc`）において、既に定義されている定数（`const`キーワードで宣言された値）が、特定の状況下、特に短い変数宣言（`:=`）の左辺で使用された場合に、コンパイラがそれを新しい名前として正しく認識できないというバグが存在していました。

例えば、以下のようなコードが問題を引き起こす可能性がありました。

```go
const MyConst = 10

func main() {
    // 別のスコープでMyConstを新しい変数として宣言しようとした場合
    // コンパイラがこれを定数として認識し、エラーを出す可能性があった
    MyConst := "hello" // このようなコードが意図せずエラーになるケース
}
```

Go言語では、`:=` を使用した短い変数宣言は、左辺に新しい変数が含まれている場合にのみ有効です。もし左辺の全ての識別子が既に現在のスコープで宣言されている場合、コンパイルエラーとなります。しかし、このバグでは、定数が「名前」として適切に扱われないために、本来許容されるべき再宣言のシナリオで誤ってエラーが発生していました。

この問題は、コンパイラが抽象構文木（AST）を処理する際に、定数ノード（`OLITERAL`）が持つシンボル情報（`sym`）を、名前として認識するための十分な情報として利用できていなかったことに起因します。結果として、`:=` の左辺の妥当性チェックが厳しすぎ、開発者の意図に反するコンパイルエラーが発生していました。

## 前提知識の解説

このコミットの理解には、以下のGoコンパイラの概念とGo言語の仕様に関する知識が必要です。

1.  **Goコンパイラ（`gc`）の構造**:
    *   **`go.y`**: これはYacc（Yet Another Compiler Compiler）形式で記述されたGo言語の文法定義ファイルです。コンパイラの字句解析器と構文解析器がGoのソースコードを解析し、抽象構文木（AST）を構築するために使用されます。
    *   **`walk.c`**: コンパイラのバックエンドに近い部分で、ASTを走査（"walk"）し、最適化や型チェック、コード生成のための変換を行うファイルです。ASTノードの操作や、Go言語のセマンティクス（意味論）の適用が行われます。
    *   **ASTノード**: GoコンパイラはソースコードをASTとして内部的に表現します。各ノードは言語の構成要素（変数、定数、関数呼び出し、演算子など）を表します。
        *   `ONAME`: 名前付きの識別子（変数名、関数名など）を表すノード。
        *   `ONONAME`: 名前を持たない識別子（一時変数など）を表すノード。
        *   `OLITERAL`: リテラル値（数値、文字列、真偽値など）を表すノード。
        *   `sym` (Symbol): コンパイラが識別子を管理するために使用するデータ構造。識別子の名前、型、スコープなどの情報を含みます。定数も名前を持つため、`OLITERAL`ノードが`sym`を持つことがあります。

2.  **Go言語の短い変数宣言（`:=`）**:
    *   Go言語には、`var`キーワードを使わずに変数を宣言し、初期化する短い変数宣言 `:=` があります。
    *   `name := expression` の形式で、`name` が現在のスコープでまだ宣言されていない場合に新しい変数を宣言します。
    *   重要なルールとして、`:=` の左辺には少なくとも1つの新しい変数が含まれていなければなりません。もし左辺の全ての識別子が既に現在のスコープで宣言されている場合、コンパイルエラーとなります。
    *   例:
        ```go
        x := 10 // x は新しい変数
        x, y := 20, 30 // x は既存、y は新しい変数 (OK)
        x := 40 // x は既存、新しい変数が無いのでエラー (No new variables on left side of :=)
        ```

3.  **定数（`const`）とスコープ**:
    *   Goの定数はコンパイル時に値が決定される不変の識別子です。
    *   定数も変数と同様にスコープを持ちます。異なるスコープでは、同じ名前の定数を再宣言することが可能です。この場合、内側のスコープの定数が外側のスコープの定数をシャドウイング（隠蔽）します。

このコミットは、`OLITERAL`ノードが持つ`sym`情報を利用して、コンパイラが短い変数宣言の左辺で定数を「新しい名前」として適切に扱えるようにすることで、上記のバグを修正しています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラが短い変数宣言（`:=`）の左辺を評価する際の「名前」の認識ロジックを改善した点にあります。

以前のコンパイラでは、`:=` の左辺が新しい名前であるかどうかを判断する際に、ノードのオペレーション（`n->op`）が`ONAME`または`ONONAME`であるかどうかにのみ依存していました。しかし、Go言語では、`const`キーワードで宣言された定数も名前を持ち、特定の文脈では新しい変数として再宣言される可能性があります（特に異なるスコープで同じ名前を使用する場合）。このような場合、定数ノード（`OLITERAL`）は、その値だけでなく、関連するシンボル（`sym`）も持っています。

このコミットは、このギャップを埋めるために以下の変更を導入しました。

1.  **`src/cmd/gc/go.y` の変更**:
    *   `pexpr` ルール内の `laconst`（リテラル定数）の処理において、`$$->sym = $1;` という行が追加されました。
    *   これは、構文解析の段階で、リテラル定数ノード（`OLITERAL`）が、そのリテラル値だけでなく、対応するシンボル（`$1`はリテラル定数のシンボルを指す）も保持するように明示的に設定することを意味します。これにより、コンパイラの後のフェーズで、このリテラルが単なる値ではなく、名前を持つ定数であることが正確に識別できるようになります。

2.  **`src/cmd/gc/walk.c` の変更**:
    *   **`colasname` 関数の導入**:
        *   `int colasname(Node *n)` という新しいヘルパー関数が追加されました。この関数の目的は、与えられたASTノード `n` が、短い変数宣言の左辺において「名前」として扱われるべきかどうかを判断することです。
        *   この関数は、`ONAME`（通常の名前）と `ONONAME`（名前なし）のノードを「名前」として認識します。
        *   さらに重要なのは、`OLITERAL`（リテラル定数）ノードの場合もチェックを行う点です。`if(n->sym != S) break;` という条件は、「もしリテラルノードがシンボル（`S`はnilシンボル）を持っていれば、それは名前として扱える」というロジックを導入しています。つまり、名前付き定数（`const MyConst = 10` のようなもの）は、この関数によって「名前」として認識されるようになります。
    *   **`old2new` 関数の修正**:
        *   `old2new` 関数は、短い変数宣言 `:=` の左辺を処理する際に呼び出されます。
        *   以前は `if(n->op != ONAME && n->op != ONONAME)` という条件で左辺が名前であるかをチェックしていました。
        *   このコミットでは、この条件が `if(!colasname(n))` に変更されました。これにより、`colasname` 関数が提供するより柔軟な「名前」の定義（名前付き定数を含む）が適用されるようになります。もし `colasname` が偽を返した場合（つまり、ノードが名前として扱えない場合）、`yyerror("left side of := must be a name");` というエラーが報告されます。
    *   **`checkmixed` 関数の修正**:
        *   `checkmixed` 関数も同様に、短い変数宣言の左辺のノードをチェックする際に、`if(l->op != ONAME && l->op != ONONAME)` の代わりに `if(!colasname(l))` を使用するように変更されました。これにより、`checkmixed` も名前付き定数を正しく扱えるようになります。

これらの変更により、コンパイラは、`const`で宣言された定数が短い変数宣言の左辺に現れた際に、それが単なるリテラル値ではなく、名前を持つ識別子として扱われるべきであることを正しく認識できるようになりました。これにより、Go言語のセマンティクスに沿った、より正確なコンパイルが可能になります。

## コアとなるコードの解説

### `src/cmd/gc/go.y` の変更

`go.y` の変更は、構文解析の段階でリテラル定数（`laconst`）がASTノード（`OLITERAL`）に変換される際に、そのシンボル情報（`$1`）をノードの `sym` フィールドに明示的に割り当てるようにした点です。

```c
$$ = nod(OLITERAL, N, N);
$$->sym = $1; // 追加された行
$$->val = $1->oconst->val;
$$->type = $1->oconst->type;
```

この変更は、コンパイラの後のフェーズ、特に意味解析や型チェックの段階で、この`OLITERAL`ノードが単なる数値や文字列のリテラルではなく、名前を持つ定数として扱われるべきであることを正確に伝えるための重要なステップです。これにより、コンパイラは定数の識別子としての性質を保持し、短い変数宣言の左辺での使用時に正しく評価できるようになります。

### `src/cmd/gc/walk.c` の変更

`walk.c` の変更は、コンパイラの意味解析フェーズにおける「名前」の認識ロジックを根本的に改善しています。

1.  **`colasname` 関数の導入**:
    この新しい関数は、ノードが短い変数宣言の左辺で有効な「名前」として機能するかどうかを判断します。

    ```c
    int
    colasname(Node *n)
    {
        switch(n->op) {
        case ONAME: // 通常の名前付き識別子
        case ONONAME: // 名前なし識別子（例: 一時変数）
            break;
        case OLITERAL: // リテラル定数
            if(n->sym != S) // リテラルがシンボルを持っている場合（つまり、名前付き定数）
                break;
            // fallthrough: シンボルを持たないリテラルは名前ではない
        default:
            return 0; // 上記以外は名前ではない
        }
        return 1; // 名前として認識できる
    }
    ```
    この関数は、`ONAME` や `ONONAME` に加えて、**シンボルを持つ `OLITERAL` ノード**も「名前」として認識するように拡張されています。これがこのバグ修正の核心であり、`const` で宣言された定数が、`:=` の左辺で新しい変数として再宣言される際に正しく扱われることを可能にします。

2.  **`old2new` 関数の修正**:
    `old2new` 関数は、`:=` 宣言の左辺のノードを処理し、それが新しい変数宣言であるか、既存の変数への代入であるかを判断します。

    ```c
    // 変更前:
    // if(n->op != ONAME && n->op != ONONAME) {
    // 変更後:
    if(!colasname(n)) {
        yyerror("left side of := must be a name");
        return n;
    }
    ```
    以前は、ノードが `ONAME` または `ONONAME` でない場合にエラーを報告していました。しかし、`colasname` 関数を使用することで、名前付き定数も有効な左辺として認識されるようになり、誤ったコンパイルエラーが回避されます。

3.  **`checkmixed` 関数の修正**:
    `checkmixed` 関数も同様に、`:=` 宣言の左辺のノードをチェックするロジックを持っています。

    ```c
    // 変更前:
    // if(l->op != ONAME && l->op != ONONAME)
    // 変更後:
    if(!colasname(l))
        goto allnew;
    ```
    ここでも `colasname` 関数が導入され、より正確な「名前」の判断が行われるようになりました。

これらの変更により、Goコンパイラは、定数が持つシンボル情報を活用し、短い変数宣言のセマンティクスをより正確に実装できるようになりました。これにより、開発者はGo言語の仕様に沿った形で定数を柔軟に利用できるようになります。

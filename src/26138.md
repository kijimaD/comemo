## 元コミット内容

Goコンパイラ (`cmd/compile`) におけるSSA (Static Single Assignment) コンパイルのトリガー方法を変更します。以前は、すべての関数をSSA形式でコンパイルし、その後でその結果を使用するかどうかを判断していました。これは、SSAの網羅率を向上させる初期段階では有用でしたが、正確性への配慮が深まるにつれて非効率的になりました。

この変更により、SSAでコンパイルすべき関数を事前に決定し、その選ばれた関数のみをSSAコンパイラに通すようにします。これにより、不要なコンパイル作業を削減し、コンパイラの効率を向上させます。

次回の変更では、`UnimplementedF`関連のコードを削除する予定です。

## 変更の背景

Goコンパイラは、パフォーマンス最適化のためにSSA (Static Single Assignment) 形式を導入していました。SSAの初期開発段階では、その適用範囲や効果を検証するために、すべての関数に対してSSAコンパイルを試行し、その後で実際にそのSSA結果を使用するかどうかを決定するアプローチが取られていました。これは、SSAの「カバレッジ」（どれだけのコードがSSAで処理できるか）を広げる上では有効でしたが、SSAが成熟し、正確性が重視される段階になると、この「すべてをコンパイルしてから選別する」方法は非効率的であることが明らかになりました。

具体的には、SSAコンパイルはリソースを消費するプロセスであり、最終的に使用されないSSA結果を生成することは無駄なオーバーヘッドとなります。このコミットの目的は、この非効率性を解消し、SSAコンパイルの対象を、実際にSSA形式で処理されるべき関数に限定することで、コンパイラの全体的なパフォーマンスと効率を向上させることにあります。これにより、コンパイラはより賢く、必要な作業のみを行うようになります。

## 前提知識の解説

### 1. Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは `cmd/compile` と呼ばれます。これは、Goのソースコードを機械語に変換する役割を担います。コンパイルプロセスは複数のステージに分かれており、構文解析、型チェック、中間表現 (IR) の生成、最適化、コード生成などが含まれます。

### 2. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化において広く使用される中間表現 (IR) の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化され、より強力な最適化（例：デッドコード削除、共通部分式除去、レジスタ割り当てなど）が可能になります。

Goコンパイラは、Go 1.7からSSAバックエンドを導入し、コード生成と最適化の大部分をSSA形式で行うようになりました。

### 3. `gc` (Go Compiler Frontend)

`src/cmd/compile/internal/gc` は、Goコンパイラのフロントエンド部分を指します。ここでは、Goのソースコードの構文解析、型チェック、抽象構文木 (AST) の構築、そしてSSA形式への変換の初期段階が行われます。

### 4. `GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` 環境変数

これらは、GoコンパイラのSSAバックエンドのデバッグやテストを支援するための環境変数です。

*   **`GOSSAFUNC`**: 特定の関数名が指定された場合、その関数のみをSSAでコンパイルし、詳細なSSAダンプ（HTML形式など）を生成します。これは、特定の関数のSSA変換や最適化の挙動を調査する際に非常に有用です。
*   **`GOSSAPKG`**: 特定のパッケージ名が指定された場合、そのパッケージ内のすべての関数をSSAでコンパイルします。
*   **`GOSSAHASH`**: 関数の名前のハッシュ値に基づいて、SSAコンパイルの対象を絞り込むための変数です。例えば、`GOSSAHASH=01` のように指定すると、関数名のハッシュ値が `01` で終わる関数のみがSSAコンパイルの対象となります。これは、特定のバグがどの関数で発生しているかをバイナリサーチで特定するような、高度なデバッグシナリオで利用されます。また、`y` や `n` を指定することで、SSAコンパイルを全体的に有効/無効にすることもできます。

これらの環境変数は、開発者がSSAバックエンドの挙動を細かく制御し、問題の特定やパフォーマンス分析を行うための強力なツールです。

## 技術的詳細

このコミットの主要な技術的変更点は、SSAコンパイルの「決定ロジック」と「実行ロジック」を分離したことです。

### 変更前のアプローチ

変更前は、`buildssa` 関数がSSA形式の関数 (`*ssa.Func`) を構築するだけでなく、そのSSA結果を実際に使用すべきかどうかを示すブール値 (`usessa`) も返していました。`pgen.go` の `compile` 関数は、まず `buildssa` を呼び出してSSAを構築し、その後 `usessa` の値を見て、`genssa` (SSAからコードを生成する関数) を呼び出すかどうかを決定していました。

このアプローチの問題点は、`usessa` が `false` であっても、`buildssa` が常にSSA形式の構築を試みていた点です。これは、SSAバックエンドの初期開発段階では、すべての関数に対してSSAを試行し、そのカバレッジを評価するために有用でしたが、SSAが安定した後は無駄な計算となっていました。

### 変更後のアプローチ

このコミットでは、以下の変更が行われました。

1.  **`shouldssa` 関数の導入**: `ssa.go` に `shouldssa(fn *Node) bool` という新しい関数が導入されました。この関数は、与えられた関数 (`fn`) がSSAコンパイルの対象となるべきかどうかを純粋に決定する役割を担います。この決定は、ターゲットアーキテクチャ (`amd64` のみ) と、前述の `GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` といった環境変数の設定に基づいて行われます。
2.  **`buildssa` 関数のシグネチャ変更**: `buildssa` 関数は、もはや `usessa` ブール値を返さなくなりました。その代わり、SSA形式の関数 (`*ssa.Func`) のみを返します。これにより、`buildssa` はSSA形式の構築に専念するようになります。
3.  **`compile` 関数の変更**: `pgen.go` の `compile` 関数は、まず `shouldssa(Curfn)` を呼び出して、現在の関数がSSAコンパイルの対象であるかを判断します。`shouldssa` が `true` を返した場合にのみ、`buildssa(Curfn)` を呼び出してSSA形式を構築します。その後、`ssafn != nil` (SSA構築が成功した場合) であれば、`genssa` を呼び出してコードを生成します。

この変更により、SSAコンパイルの実行が、実際にその結果が使用される場合に限定されるようになりました。これにより、コンパイラの実行時における不要なSSA構築が回避され、全体的なコンパイル時間の短縮とリソース消費の削減が期待できます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/pgen.go` の変更点

*   **`usessa` 変数の削除**: `compile` 関数内で `var usessa bool` が削除されました。これは、SSAコンパイルを使用するかどうかの決定が `buildssa` から分離されたため、この変数が不要になったことを示します。
*   **`buildssa` の呼び出し条件の変更**:
    *   変更前: `if Thearch.Thestring == "amd64" { ssafn, usessa = buildssa(Curfn) }`
    *   変更後: `if shouldssa(Curfn) { ssafn = buildssa(Curfn) }`
    この変更により、`buildssa` を呼び出す前に、新しく導入された `shouldssa` 関数がSSAコンパイルの必要性を判断するようになりました。`amd64` アーキテクチャに限定されていた条件も `shouldssa` の内部に移動しました。また、`buildssa` が `usessa` を返さなくなったため、戻り値の受け取り方も変更されています。
*   **`genssa` の呼び出し条件の変更**:
    *   変更前: `if ssafn != nil && usessa { genssa(ssafn, ptxt, gcargs, gclocals) }`
    *   変更後: `if ssafn != nil { genssa(ssafn, ptxt, gcargs, gclocals) }`
    `shouldssa` が `true` を返した場合にのみ `buildssa` が呼び出されるようになったため、`ssafn` が `nil` でなければ、そのSSA結果は使用されるべきであると判断できます。したがって、`usessa` のチェックは不要になりました。

### `src/cmd/compile/internal/gc/ssa.go` の変更点

*   **`shouldssa` 関数の新規導入**:
    この関数は、特定の関数 `fn` がSSAコンパイルの対象となるべきかを判断するロジックをカプセル化します。
    *   まず、ターゲットアーキテクチャが `amd64` でない場合は `false` を返します。これは、SSAバックエンドが当初 `amd64` のみをサポートしていたためです。
    *   次に、`GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` といった環境変数の設定をチェックし、それらの条件に基づいて `true` または `false` を返します。これにより、開発者は特定の関数、パッケージ、またはハッシュ値に一致する関数のみをSSAでコンパイルするように制御できます。
*   **`buildssa` 関数のシグネチャ変更と内部ロジックの整理**:
    *   変更前: `func buildssa(fn *Node) (ssafn *ssa.Func, usessa bool)`
    *   変更後: `func buildssa(fn *Node) *ssa.Func`
    `buildssa` はもはや `usessa` ブール値を返しません。その代わり、SSA形式の関数 (`*ssa.Func`) の構築に特化します。
    *   以前 `buildssa` 内にあった `usessa` の決定ロジック（環境変数チェックなど）は、すべて `shouldssa` 関数に移動されました。
    *   `e.log = usessa` や `if !usessa { s.config.HTML.Close() }` といった `usessa` に依存する処理は、`printssa` という新しいローカル変数に置き換えられました。この `printssa` は、`GOSSAFUNC` などが設定されている場合にSSAのデバッグ情報を出力するかどうかを制御するためのものです。
    *   エラー発生時の戻り値も `return nil, false` から `return nil` に変更されました。
    *   関数の最後にあった、`usessa` の値に基づいて `s.f` と `true/false` を返すロジックが完全に削除され、単に `return s.f` となりました。

これらの変更により、SSAコンパイルの決定と実行が明確に分離され、コンパイラのコードベースがよりモジュール化され、理解しやすくなりました。また、不要なSSA構築が削減されることで、コンパイル効率が向上します。

## 元コミット内容

Goコンパイラ (`cmd/compile`) におけるSSA (Static Single Assignment) コンパイルのトリガー方法を変更します。以前は、すべての関数をSSA形式でコンパイルし、その後でその結果を使用するかどうかを判断していました。これは、SSAの網羅率を向上させる初期段階では有用でしたが、正確性への配慮が深まるにつれて非効率的になりました。

この変更により、SSAでコンパイルすべき関数を事前に決定し、その選ばれた関数のみをSSAコンパイラに通すようにします。これにより、不要なコンパイル作業を削減し、コンパイラの全体的なパフォーマンスと効率を向上させます。

次回の変更では、`UnimplementedF`関連のコードを削除する予定です。

## 変更の背景

Goコンパイラは、パフォーマンス最適化のためにSSA (Static Single Assignment) 形式を導入していました。SSAの初期開発段階では、その適用範囲や効果を検証するために、すべての関数に対してSSAコンパイルを試行し、その後で実際にそのSSA結果を使用するかどうかを決定するアプローチが取られていました。これは、SSAの「カバレッジ」（どれだけのコードがSSAで処理できるか）を広げる上では有効でしたが、SSAが成熟し、正確性が重視される段階になると、この「すべてをコンパイルしてから選別する」方法は非効率的であることが明らかになりました。

具体的には、SSAコンパイルはリソースを消費するプロセスであり、最終的に使用されないSSA結果を生成することは無駄なオーバーヘッドとなります。このコミットの目的は、この非効率性を解消し、SSAコンパイルの対象を、実際にSSA形式で処理されるべき関数に限定することで、コンパイラの全体的なパフォーマンスと効率を向上させることにあります。これにより、コンパイラはより賢く、必要な作業のみを行うようになります。

## 前提知識の解説

### 1. Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラは `cmd/compile` と呼ばれます。これは、Goのソースコードを機械語に変換する役割を担います。コンパイルプロセスは複数のステージに分かれており、構文解析、型チェック、中間表現 (IR) の生成、最適化、コード生成などが含まれます。

### 2. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化において広く使用される中間表現 (IR) の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化され、より強力な最適化（例：デッドコード削除、共通部分式除去、レジスタ割り当てなど）が可能になります。

Goコンパイラは、Go 1.7からSSAバックエンドを導入し、コード生成と最適化の大部分をSSA形式で行うようになりました。

### 3. `gc` (Go Compiler Frontend)

`src/cmd/compile/internal/gc` は、Goコンパイラのフロントエンド部分を指します。ここでは、Goのソースコードの構文解析、型チェック、抽象構文木 (AST) の構築、そしてSSA形式への変換の初期段階が行われます。

### 4. `GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` 環境変数

これらは、GoコンパイラのSSAバックエンドのデバッグやテストを支援するための環境変数です。

*   **`GOSSAFUNC`**: 特定の関数名が指定された場合、その関数のみをSSAでコンパイルし、詳細なSSAダンプ（HTML形式など）を生成します。これは、特定の関数のSSA変換や最適化の挙動を調査する際に非常に有用です。
*   **`GOSSAPKG`**: 特定のパッケージ名が指定された場合、そのパッケージ内のすべての関数をSSAでコンパイルします。
*   **`GOSSAHASH`**: 関数の名前のハッシュ値に基づいて、SSAコンパイルの対象を絞り込むための変数です。例えば、`GOSSAHASH=01` のように指定すると、関数名のハッシュ値が `01` で終わる関数のみがSSAコンパイルの対象となります。これは、特定のバグがどの関数で発生しているかをバイナリサーチで特定するような、高度なデバッグシナリオで利用されます。また、`y` や `n` を指定することで、SSAコンパイルを全体的に有効/無効にすることもできます。

これらの環境変数は、開発者がSSAバックエンドの挙動を細かく制御し、問題の特定やパフォーマンス分析を行うための強力なツールです。

## 技術的詳細

このコミットの主要な技術的変更点は、SSAコンパイルの「決定ロジック」と「実行ロジック」を分離したことです。

### 変更前のアプローチ

変更前は、`buildssa` 関数がSSA形式の関数 (`*ssa.Func`) を構築するだけでなく、そのSSA結果を実際に使用すべきかどうかを示すブール値 (`usessa`) も返していました。`pgen.go` の `compile` 関数は、まず `buildssa` を呼び出してSSAを構築し、その後 `usessa` の値を見て、`genssa` (SSAからコードを生成する関数) を呼び出すかどうかを決定していました。

このアプローチの問題点は、`usessa` が `false` であっても、`buildssa` が常にSSA形式の構築を試みていた点です。これは、SSAバックエンドの初期開発段階では、すべての関数に対してSSAを試行し、そのカバレッジを評価するために有用でしたが、SSAが安定した後は無駄な計算となっていました。

### 変更後のアプローチ

このコミットでは、以下の変更が行われました。

1.  **`shouldssa` 関数の導入**: `ssa.go` に `shouldssa(fn *Node) bool` という新しい関数が導入されました。この関数は、与えられた関数 (`fn`) がSSAコンパイルの対象となるべきかどうかを純粋に決定する役割を担います。この決定は、ターゲットアーキテクチャ (`amd64` のみ) と、前述の `GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` といった環境変数の設定に基づいて行われます。
2.  **`buildssa` 関数のシグネチャ変更**: `buildssa` 関数は、もはや `usessa` ブール値を返さなくなりました。その代わり、SSA形式の関数 (`*ssa.Func`) のみを返します。これにより、`buildssa` はSSA形式の構築に専念するようになります。
3.  **`compile` 関数の変更**: `pgen.go` の `compile` 関数は、まず `shouldssa(Curfn)` を呼び出して、現在の関数がSSAコンパイルの対象であるかを判断します。`shouldssa` が `true` を返した場合にのみ、`buildssa(Curfn)` を呼び出してSSA形式を構築します。その後、`ssafn != nil` (SSA構築が成功した場合) であれば、`genssa` を呼び出してコードを生成します。

この変更により、SSAコンパイルの実行が、実際にその結果が使用される場合に限定されるようになりました。これにより、コンパイラの実行時における不要なSSA構築が回避され、全体的なコンパイル時間の短縮とリソース消費の削減が期待できます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/pgen.go` の変更点

*   **`usessa` 変数の削除**: `compile` 関数内で `var usessa bool` が削除されました。これは、SSAコンパイルを使用するかどうかの決定が `buildssa` から分離されたため、この変数が不要になったことを示します。
*   **`buildssa` の呼び出し条件の変更**:
    *   変更前: `if Thearch.Thestring == "amd64" { ssafn, usessa = buildssa(Curfn) }`
    *   変更後: `if shouldssa(Curfn) { ssafn = buildssa(Curfn) }`
    この変更により、`buildssa` を呼び出す前に、新しく導入された `shouldssa` 関数がSSAコンパイルの必要性を判断するようになりました。`amd64` アーキテクチャに限定されていた条件も `shouldssa` の内部に移動しました。また、`buildssa` が `usessa` を返さなくなったため、戻り値の受け取り方も変更されています。
*   **`genssa` の呼び出し条件の変更**:
    *   変更前: `if ssafn != nil && usessa { genssa(ssafn, ptxt, gcargs, gclocals) }`
    *   変更後: `if ssafn != nil { genssa(ssafn, ptxt, gcargs, gclocals) }`
    `shouldssa` が `true` を返した場合にのみ `buildssa` が呼び出されるようになったため、`ssafn` が `nil` でなければ、そのSSA結果は使用されるべきであると判断できます。したがって、`usessa` のチェックは不要になりました。

### `src/cmd/compile/internal/gc/ssa.go` の変更点

*   **`shouldssa` 関数の新規導入**:
    この関数は、特定の関数 `fn` がSSAコンパイルの対象となるべきかを判断するロジックをカプセル化します。
    *   まず、ターゲットアーキテクチャが `amd64` でない場合は `false` を返します。これは、SSAバックエンドが当初 `amd64` のみをサポートしていたためです。
    *   次に、`GOSSAFUNC`, `GOSSAPKG`, `GOSSAHASH` といった環境変数の設定をチェックし、それらの条件に基づいて `true` または `false` を返します。これにより、開発者は特定の関数、パッケージ、またはハッシュ値に一致する関数のみをSSAでコンパイルするように制御できます。
*   **`buildssa` 関数のシグネチャ変更と内部ロジックの整理**:
    *   変更前: `func buildssa(fn *Node) (ssafn *ssa.Func, usessa bool)`
    *   変更後: `func buildssa(fn *Node) *ssa.Func`
    `buildssa` はもはや `usessa` ブール値を返しません。その代わり、SSA形式の関数 (`*ssa.Func`) の構築に特化します。
    *   以前 `buildssa` 内にあった `usessa` の決定ロジック（環境変数チェックなど）は、すべて `shouldssa` 関数に移動されました。
    *   `e.log = usessa` や `if !usessa { s.config.HTML.Close() }` といった `usessa` に依存する処理は、`printssa` という新しいローカル変数に置き換えられました。この `printssa` は、`GOSSAFUNC` などが設定されている場合にSSAのデバッグ情報を出力するかどうかを制御するためのものです。
    *   エラー発生時の戻り値も `return nil, false` から `return nil` に変更されました。
    *   関数の最後にあった、`usessa` の値に基づいて `s.f` と `true/false` を返すロジックが完全に削除され、単に `return s.f` となりました。

これらの変更により、SSAコンパイルの決定と実行が明確に分離され、コンパイラのコードベースがよりモジュール化され、理解しやすくなりました。また、不要なSSA構築が削減されることで、コンパイル効率が向上します。

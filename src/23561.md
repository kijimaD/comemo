# [インデックス 23561] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/zip` パッケージにおいて、ZIPファイルの読み込み時に予期せぬEOF（End Of File）が発生した場合の検証ロジックを追加するものです。具体的には、`io.ReadCloser` の実装である `checksumReader` が、ZIPファイル内の個々のエントリ（ファイル）のデータを読み込む際に、宣言されている非圧縮サイズと実際に読み込んだバイト数を比較し、不一致があれば `io.ErrUnexpectedEOF` を返すように修正されています。これにより、破損したZIPファイルや、意図的に短縮されたファイルデータを持つZIPファイルに対する堅牢性が向上します。

## 変更の背景

この変更は、Goの `archive/zip` パッケージが、ZIPファイル内のエントリ（ファイル）のデータが、ヘッダで宣言されている非圧縮サイズよりも短い場合に、それを適切に検出できないという問題（Issue 10957）を修正するために導入されました。

従来の `checksumReader` は、`io.ReadCloser` の `Read` メソッドが `io.EOF` を返した際に、読み込みが完了したと判断していました。しかし、悪意のある、あるいは破損したZIPファイルでは、ファイルデータが途中で切り詰められているにもかかわらず、`io.EOF` が返されることがあります。この場合、`checksumReader` はデータの不足を検知できず、不完全なデータを正常として処理してしまう可能性がありました。

この脆弱性は、特にセキュリティの観点から問題となります。例えば、ZIP爆弾のような攻撃において、ファイルサイズを偽装してシステムリソースを枯渇させようとする試みに対して、不完全なデータでも正常とみなしてしまうと、適切なエラーハンドリングが行われません。このコミットは、このようなシナリオにおいて、実際に読み込んだバイト数と期待される非圧縮サイズを比較することで、データの完全性を検証し、より堅牢なZIPファイル処理を実現することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **ZIPファイルフォーマット**: ZIPファイルは、複数のファイルやディレクトリを一つにまとめるためのアーカイブフォーマットです。各エントリ（ファイル）は、ローカルファイルヘッダ、オプションのデータ記述子、ファイルデータ、およびセントラルディレクトリヘッダで構成されます。ローカルファイルヘッダには、そのファイルの非圧縮サイズ（`UncompressedSize64`）などのメタデータが含まれています。
*   **`io.Reader` と `io.ReadCloser` インターフェース**: Go言語の `io` パッケージで定義されているインターフェースです。
    *   `io.Reader` は `Read(p []byte) (n int, err error)` メソッドを持ち、データを読み込むための基本的なインターフェースです。
    *   `io.ReadCloser` は `io.Reader` に加えて `Close() error` メソッドを持ち、読み込み後にリソースを解放する機能を提供します。
*   **`io.EOF`**: `io.Reader` の `Read` メソッドが、それ以上読み込むデータがない場合に返すエラーです。これは通常、ストリームの正常な終了を示します。
*   **`io.ErrUnexpectedEOF`**: `io.Reader` の `Read` メソッドが、期待されるデータ量に達する前にストリームが終了した場合に返すエラーです。これは通常、データが途中で切り詰められているなど、予期せぬ終了を示します。
*   **`crc32.NewIEEE()`**: `hash/crc32` パッケージの関数で、CRC-32チェックサムを計算するためのハッシュ関数を生成します。ZIPファイルでは、データの完全性検証のためにCRC-32チェックサムが使用されます。
*   **`checksumReader` 構造体**: `archive/zip` パッケージ内部で使用される構造体で、ZIPエントリのデータを読み込みながらCRC-32チェックサムを計算し、必要に応じてデータ記述子を処理する役割を担います。

## 技術的詳細

このコミットの技術的な核心は、`checksumReader` 構造体に `nread` フィールドを追加し、`Read` メソッド内で実際に読み込んだバイト数を追跡すること、そして `io.EOF` が返された際にこの `nread` と期待される非圧縮サイズ `f.UncompressedSize64` を比較するロジックを追加した点にあります。

1.  **`checksumReader` 構造体の変更**:
    *   `nread uint64` フィールドが追加されました。これは、`checksumReader` がこれまでに読み込んだバイト数の合計を保持します。`uint64` 型であるため、非常に大きなファイルサイズにも対応できます。

2.  **`File.Open()` メソッドの変更**:
    *   `checksumReader` の初期化時に、新しい `nread` フィールドはゼロ値（`0`）で初期化されます。これは、ファイルを開いた時点ではまだ何も読み込まれていないためです。

3.  **`checksumReader.Read()` メソッドの変更**:
    *   `n, err = r.rc.Read(b)` の呼び出し後、実際に読み込まれたバイト数 `n` が `r.nread` に加算されます (`r.nread += uint64(n)`)。これにより、`nread` は常にこれまでに読み込まれた総バイト数を正確に反映します。
    *   `if err == io.EOF` ブロック内で、新しい検証ロジックが追加されました。
        ```go
        if r.nread != r.f.UncompressedSize64 {
            return 0, io.ErrUnexpectedEOF
        }
        ```
        このコードは、`io.EOF` が発生した際に、`checksumReader` がこれまでに読み込んだバイト数 `r.nread` が、ZIPヘッダに記載されている期待される非圧縮サイズ `r.f.UncompressedSize64` と一致するかどうかをチェックします。
        *   もし一致しない場合（つまり、期待されるサイズよりも少ないバイト数でEOFに達した場合）、`io.ErrUnexpectedEOF` を返します。これにより、呼び出し元はデータが不完全であることを明確に認識できます。
        *   一致する場合、通常のEOF処理（データ記述子の読み込みなど）に進みます。

この変更により、`archive/zip` パッケージは、ZIPファイル内の個々のエントリのデータが途中で切り詰められているような不正なケースを、より正確に検出できるようになりました。

## コアとなるコードの解説

このコミットの主要な変更は、`src/archive/zip/reader.go` 内の `checksumReader` 構造体とその `Read` メソッドに集中しています。

1.  **`checksumReader` 構造体への `nread` フィールド追加**:
    *   `nread uint64 // number of bytes read so far`
    *   このフィールドは、`checksumReader` が特定のZIPファイルエントリからこれまでに読み込んだバイト数を累積するために導入されました。`uint64` を使用することで、非常に大きなファイルサイズにも対応できます。

2.  **`checksumReader.Read()` メソッドでの `nread` の更新**:
    *   `n, err = r.rc.Read(b)` の行の直後に `r.nread += uint64(n)` が追加されました。
    *   これは、基となる `io.ReadCloser` (`r.rc`) から実際に読み込まれたバイト数 `n` を、`r.nread` に加算することで、読み込みの進行状況を正確に追跡します。

3.  **`io.EOF` 検出時のサイズ検証ロジックの追加**:
    *   `if err == io.EOF { ... }` ブロックの先頭に以下のコードが挿入されました。
        ```go
        if r.nread != r.f.UncompressedSize64 {
            return 0, io.ErrUnexpectedEOF
        }
        ```
    *   このロジックは、`Read` メソッドが `io.EOF` を返した（つまり、データの終端に達した）ときに発動します。
    *   `r.nread`（実際に読み込んだバイト数）と `r.f.UncompressedSize64`（ZIPヘッダに記載された期待される非圧縮サイズ）を比較します。
    *   もし両者が一致しない場合、それはデータが期待されるサイズよりも早く終了したことを意味します。この状況は、破損したZIPファイルや、意図的に切り詰められたファイルデータを示唆するため、`0` バイトを読み込み、エラーとして `io.ErrUnexpectedEOF` を返します。
    *   両者が一致する場合、読み込みは正常に完了したと判断され、既存のデータ記述子処理ロジックに進みます。

これらの変更により、`archive/zip` パッケージは、ZIPファイル内の個々のエントリのデータが、宣言されたサイズに満たない場合に、それを明確なエラー `io.ErrUnexpectedEOF` として報告できるようになり、不正なZIPファイルに対する堅牢性が大幅に向上しました。

また、`src/archive/zip/reader_test.go` に追加された `TestIssue10957` は、この新しい検証ロジックが正しく機能することを確認するためのテストケースです。意図的に短縮されたZIPファイルデータを作成し、特定のファイルエントリを読み込んだ際に `io.ErrUnexpectedEOF` が返されることを検証しています。

# [インデックス 24229] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）中間表現において、関数呼び出し時の`outargs`（呼び出し先関数への引数領域）のサイズ計算を修正するものです。具体的には、各関数呼び出しサイトで必要となる`outargs`のサイズを正確に追跡し、スタックフレームの`outargs`セクションのサイズを、その関数内の全ての呼び出しサイトで必要とされる`outargs`サイズの最大値として計算するように変更しています。これにより、スタックフレームの割り当てがより正確かつ効率的になります。

## 変更の背景

Goコンパイラは、プログラムを機械語に変換する過程で、ソースコードを様々な中間表現に変換します。その一つがSSA（Static Single Assignment）形式です。関数呼び出しを行う際、呼び出し元は呼び出し先関数に引数を渡すための領域（`outargs`セクション）をスタックフレーム内に確保する必要があります。この`outargs`セクションのサイズは、その関数内で発生する全ての呼び出しの中で、最も大きな引数リストを持つ呼び出しに合わせる必要があります。

このコミット以前は、`outargs`セクションのサイズ計算が正確に行われていなかった可能性があります。`src/cmd/compile/internal/ssa/TODO`ファイルに「Compute size of outargs section correctly」というTODO項目があったことからも、この問題が認識されていたことが伺えます。不正確なサイズ計算は、スタック領域の無駄な消費や、最悪の場合、スタックオーバーフローなどの実行時エラーを引き起こす可能性がありました。

この変更の目的は、Goコンパイラが生成するコードの効率性と堅牢性を向上させるために、`outargs`セクションのサイズを正確に決定することです。これにより、スタックフレームのメモリ使用量が最適化され、ランタイムの安定性が向上します。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、最適化のためにプログラムをSSA形式に変換します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。コンパイルの過程で、抽象構文木（AST）からSSA形式に変換され、様々な最適化パスが適用された後、最終的に機械語に変換されます。

### スタックフレームの構造（特に`outargs`セクション）

関数が呼び出されると、その関数専用のスタックフレームがスタック上に作成されます。一般的なスタックフレームには、以下のような領域が含まれます。

*   **リターンアドレス**: 呼び出し元に戻るためのアドレス。
*   **保存されたレジスタ**: 呼び出し元が使用していたレジスタの値を保存する領域。
*   **ローカル変数**: 呼び出された関数内で宣言されたローカル変数の領域。
*   **`inargs` (または `args`)**: 呼び出し元から渡された引数を受け取る領域。
*   **`outargs`**: 呼び出し先関数に引数を渡すために、呼び出し元が確保する領域。

`outargs`セクションは、呼び出し元が次に呼び出す関数に渡す引数を格納するために予約される領域です。Goの呼び出し規約では、引数はスタックまたはレジスタを通じて渡されますが、スタックを通じて渡される引数や、レジスタに収まらない引数、可変長引数などはこの`outargs`セクションに配置されます。

### `cmd/compile`パッケージの役割

`cmd/compile`はGo言語の公式コンパイラです。Goのソースコードを解析し、中間表現を経て、最終的に実行可能なバイナリコードを生成します。このパッケージの内部には、フロントエンド（字句解析、構文解析、型チェック）、中間表現の生成（AST、SSA）、最適化、バックエンド（コード生成）など、コンパイルの各段階を処理するサブパッケージが含まれています。

### `Argwid`の概念

`Argwid`は "Argument Width" の略で、関数呼び出しにおける引数の合計サイズ（バイト単位）を指します。Goコンパイラでは、この`Argwid`を正確に把握することが、スタックフレームの`outargs`セクションを適切に割り当てる上で非常に重要となります。

## 技術的詳細

このコミットの技術的な核心は、関数呼び出しにおける`outargs`サイズの正確な伝播と集計にあります。

1.  **`src/cmd/compile/internal/gc/ssa.go`における`Argwid`の付与**:
    `gc/ssa.go`は、GoのASTからSSA形式への変換を担当する部分です。この変更では、関数呼び出しを表すSSAの`Value`（`call`）に対して、呼び出し先関数の引数サイズ（`n.Left.Type.Argwid`）を`call.AuxInt`として付与しています。`AuxInt`は、SSA `Value`に付随する整数型の補助情報で、このようなメタデータを伝達するために使用されます。
    ```go
    // ...
    		call = s.newValue3(ssa.OpClosureCall, ssa.TypeMem, entry, closure, s.mem())
    // ...
    		dowidth(n.Left.Type) // n.Left.Type は呼び出し先関数の型
    		call.AuxInt = n.Left.Type.Argwid // call operations carry the argsize of the callee along with them
    // ...
    ```
    `dowidth`関数は、型のサイズとアライメントを計算する役割を担っており、ここで`n.Left.Type.Argwid`が確定されます。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`における`argwid`の伝播**:
    `AMD64.rules`は、AMD64アーキテクチャ向けのSSA最適化およびコード生成ルールを定義するファイルです。この変更により、`StaticCall`および`ClosureCall`といった関数呼び出しを表すSSAオペレーションのルールに`[argwid]`が追加されました。これは、`argwid`がSSA `Value`の補助情報として、これらのオペレーションを通じて下流のパスに伝播されることを意味します。
    ```diff
    - (StaticCall {target} mem) -> (CALLstatic {target} mem)
    - (ClosureCall entry closure mem) -> (CALLclosure entry closure mem)
    + (StaticCall [argwid] {target} mem) -> (CALLstatic [argwid] {target} mem)
    + (ClosureCall [argwid] entry closure mem) -> (CALLclosure [argwid] entry closure mem)
    ```
    この変更は、SSAのルールエンジンが`argwid`を認識し、それを`CALLstatic`や`CALLclosure`といった低レベルの呼び出しオペレーションに引き継ぐように指示します。

3.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`における`argwid`の利用**:
    `rewriteAMD64.go`は、AMD64アーキテクチャ固有のSSA `Value`の書き換えルールを実装しています。`ClosureCall`と`StaticCall`の書き換えロジックが更新され、`v.AuxInt`から`argwid`を取得し、それを新しい`CALLclosure`または`CALLstatic`オペレーションの`AuxInt`として設定するように変更されました。
    ```go
    // case OpClosureCall:
    // ...
    // result: (CALLclosure [argwid] entry closure mem)
    // {
    //    argwid := v.AuxInt // ここで元のAuxIntからargwidを取得
    //    // ...
    //    v.AuxInt = argwid // 新しいCALLclosureオペレーションにargwidを設定
    //    // ...
    // }
    ```
    これにより、`argwid`がSSAの変換パス全体で正しく保持され、最終的なスタック割り当てフェーズで利用可能になります。

4.  **`src/cmd/compile/internal/ssa/stackalloc.go`における`outargs`サイズの計算**:
    `stackalloc.go`は、スタックフレームの割り当てを担当するファイルです。このコミットの最も重要な変更点の一つは、`outargs`セクションのサイズ計算ロジックです。以前は固定値（`16`バイト）やTODOコメントがあった箇所が、以下のように修正されました。
    ```go
    // Start with space for callee arguments/returns.
    var n int64
    for _, b := range f.Blocks {
        if b.Kind != BlockCall {
            continue
        }
        v := b.Control
        if n < v.AuxInt {
            n = v.AuxInt
        }
    }
    ```
    このコードは、関数`f`内の全ての基本ブロック（`f.Blocks`）をイテレートします。
    *   `b.Kind != BlockCall`で、関数呼び出しを行うブロックのみをフィルタリングします。
    *   `v := b.Control`で、そのブロックの制御`Value`（つまり関数呼び出しオペレーション）を取得します。
    *   `v.AuxInt`には、前述の`gc/ssa.go`で設定された`Argwid`が格納されています。
    *   `if n < v.AuxInt { n = v.AuxInt }`により、全ての呼び出しサイトの`Argwid`の中で最大値が`n`に保持されます。

    最終的に`n`に格納された値が、その関数のスタックフレームにおける`outargs`セクションの正確なサイズとして使用されます。これにより、スタックフレームは、その関数内で最も多くの引数を必要とする呼び出しに十分な領域を確保できるようになります。

## 変更の背景

Goコンパイラは、プログラムを機械語に変換する過程で、ソースコードを様々な中間表現に変換します。その一つがSSA（Static Single Assignment）形式です。関数呼び出しを行う際、呼び出し元は呼び出し先関数に引数を渡すための領域（`outargs`セクション）をスタックフレーム内に確保する必要があります。この`outargs`セクションのサイズは、その関数内で発生する全ての呼び出しの中で、最も大きな引数リストを持つ呼び出しに合わせる必要があります。

このコミット以前は、`outargs`セクションのサイズ計算が正確に行われていなかった可能性があります。`src/cmd/compile/internal/ssa/TODO`ファイルに「Compute size of outargs section correctly」というTODO項目があったことからも、この問題が認識されていたことが伺えます。不正確なサイズ計算は、スタック領域の無駄な消費や、最悪の場合、スタックオーバーフローなどの実行時エラーを引き起こす可能性がありました。

この変更の目的は、Goコンパイラが生成するコードの効率性と堅牢性を向上させるために、`outargs`セクションのサイズを正確に決定することです。これにより、スタックフレームのメモリ使用量が最適化され、ランタイムの安定性が向上します。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、最適化のためにプログラムをSSA形式に変換します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。コンパイルの過程で、抽象構文木（AST）からSSA形式に変換され、様々な最適化パスが適用された後、最終的に機械語に変換されます。

### スタックフレームの構造（特に`outargs`セクション）

関数が呼び出されると、その関数専用のスタックフレームがスタック上に作成されます。一般的なスタックフレームには、以下のような領域が含まれます。

*   **リターンアドレス**: 呼び出し元に戻るためのアドレス。
*   **保存されたレジスタ**: 呼び出し元が使用していたレジスタの値を保存する領域。
*   **ローカル変数**: 呼び出された関数内で宣言されたローカル変数の領域。
*   **`inargs` (または `args`)**: 呼び出し元から渡された引数を受け取る領域。
*   **`outargs`**: 呼び出し先関数に引数を渡すために、呼び出し元が確保する領域。

`outargs`セクションは、呼び出し元が次に呼び出す関数に渡す引数を格納するために予約される領域です。Goの呼び出し規約では、引数はスタックまたはレジスタを通じて渡されますが、スタックを通じて渡される引数や、レジスタに収まらない引数、可変長引数などはこの`outargs`セクションに配置されます。

### `cmd/compile`パッケージの役割

`cmd/compile`はGo言語の公式コンパイラです。Goのソースコードを解析し、中間表現を経て、最終的に実行可能なバイナリコードを生成します。このパッケージの内部には、フロントエンド（字句解析、構文解析、型チェック）、中間表現の生成（AST、SSA）、最適化、バックエンド（コード生成）など、コンパイルの各段階を処理するサブパッケージが含まれています。

### `Argwid`の概念

`Argwid`は "Argument Width" の略で、関数呼び出しにおける引数の合計サイズ（バイト単位）を指します。Goコンパイラでは、この`Argwid`を正確に把握することが、スタックフレームの`outargs`セクションを適切に割り当てる上で非常に重要となります。

## 技術的詳細

このコミットの技術的な核心は、関数呼び出しにおける`outargs`サイズの正確な伝播と集計にあります。

1.  **`src/cmd/compile/internal/gc/ssa.go`における`Argwid`の付与**:
    `gc/ssa.go`は、GoのASTからSSA形式への変換を担当する部分です。この変更では、関数呼び出しを表すSSAの`Value`（`call`）に対して、呼び出し先関数の引数サイズ（`n.Left.Type.Argwid`）を`call.AuxInt`として付与しています。`AuxInt`は、SSA `Value`に付随する整数型の補助情報で、このようなメタデータを伝達するために使用されます。
    ```go
    // ...
    		call = s.newValue3(ssa.OpClosureCall, ssa.TypeMem, entry, closure, s.mem())
    // ...
    		dowidth(n.Left.Type) // n.Left.Type は呼び出し先関数の型
    		call.AuxInt = n.Left.Type.Argwid // call operations carry the argsize of the callee along with them
    // ...
    ```
    `dowidth`関数は、型のサイズとアライメントを計算する役割を担っており、ここで`n.Left.Type.Argwid`が確定されます。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`における`argwid`の伝播**:
    `AMD64.rules`は、AMD64アーキテクチャ向けのSSA最適化およびコード生成ルールを定義するファイルです。この変更により、`StaticCall`および`ClosureCall`といった関数呼び出しを表すSSAオペレーションのルールに`[argwid]`が追加されました。これは、`argwid`がSSA `Value`の補助情報として、これらのオペレーションを通じて下流のパスに伝播されることを意味します。
    ```diff
    - (StaticCall {target} mem) -> (CALLstatic {target} mem)
    - (ClosureCall entry closure mem) -> (CALLclosure entry closure mem)
    + (StaticCall [argwid] {target} mem) -> (CALLstatic [argwid] {target} mem)
    + (ClosureCall [argwid] entry closure mem) -> (CALLclosure [argwid] entry closure mem)
    ```
    この変更は、SSAのルールエンジンが`argwid`を認識し、それを`CALLstatic`や`CALLclosure`といった低レベルの呼び出しオペレーションに引き継ぐように指示します。

3.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`における`argwid`の利用**:
    `rewriteAMD64.go`は、AMD64アーキテクチャ固有のSSA `Value`の書き換えルールを実装しています。`ClosureCall`と`StaticCall`の書き換えロジックが更新され、`v.AuxInt`から`argwid`を取得し、それを新しい`CALLclosure`または`CALLstatic`オペレーションの`AuxInt`として設定するように変更されました。
    ```go
    // case OpClosureCall:
    // ...
    // result: (CALLclosure [argwid] entry closure mem)
    // {
    //    argwid := v.AuxInt // ここで元のAuxIntからargwidを取得
    //    // ...
    //    v.AuxInt = argwid // 新しいCALLclosureオペレーションにargwidを設定
    //    // ...
    // }
    ```
    これにより、`argwid`がSSAの変換パス全体で正しく保持され、最終的なスタック割り当てフェーズで利用可能になります。

4.  **`src/cmd/compile/internal/ssa/stackalloc.go`における`outargs`サイズの計算**:
    `stackalloc.go`は、スタックフレームの割り当てを担当するファイルです。このコミットの最も重要な変更点の一つは、`outargs`セクションのサイズ計算ロジックです。以前は固定値（`16`バイト）やTODOコメントがあった箇所が、以下のように修正されました。
    ```go
    // Start with space for callee arguments/returns.
    var n int64
    for _, b := range f.Blocks {
        if b.Kind != BlockCall {
            continue
        }
        v := b.Control
        if n < v.AuxInt {
            n = v.AuxInt
        }
    }
    ```
    このコードは、関数`f`内の全ての基本ブロック（`f.Blocks`）をイテレートします。
    *   `b.Kind != BlockCall`で、関数呼び出しを行うブロックのみをフィルタリングします。
    *   `v := b.Control`で、そのブロックの制御`Value`（つまり関数呼び出しオペレーション）を取得します。
    *   `v.AuxInt`には、前述の`gc/ssa.go`で設定された`Argwid`が格納されています。
    *   `if n < v.AuxInt { n = v.AuxInt }`により、全ての呼び出しサイトの`Argwid`の中で最大値が`n`に保持されます。

    最終的に`n`に格納された値が、その関数のスタックフレームにおける`outargs`セクションの正確なサイズとして使用されます。これにより、どのような関数呼び出しが行われても、引数を格納するための十分なスタック領域が確保されることが保証されます。

### `src/cmd/compile/internal/ssa/stackalloc.go`

```go

 	home := f.RegAlloc
 
 	// Start with space for callee arguments/returns.
 	var n int64
 	for _, b := range f.Blocks {
 		if b.Kind != BlockCall {
 			continue
 		}
 		v := b.Control
 		if n < v.AuxInt {
 			n = v.AuxInt
 		}
 	}
 
 	// ... (rest of stack allocation logic)
 }
```
このコードブロックは、関数のスタックフレームにおける`outargs`セクションのサイズを決定する中心的なロジックです。
1.  `var n int64`で、`outargs`の最大サイズを保持する変数`n`を初期化します。
2.  `for _, b := range f.Blocks`で、現在の関数`f`内の全ての基本ブロックをループします。
3.  `if b.Kind != BlockCall { continue }`により、関数呼び出しを含むブロックのみを処理対象とします。
4.  `v := b.Control`で、その`BlockCall`の制御`Value`（つまり、関数呼び出しオペレーション自体）を取得します。
5.  `if n < v.AuxInt { n = v.AuxInt }`がこの変更の核心です。`v.AuxInt`には、`gc/ssa.go`で設定され、`AMD64.rules`と`rewriteAMD64.go`を通じて伝播されてきた`Argwid`（呼び出し先関数への引数の合計サイズ）が格納されています。このループを通じて、関数内の全ての呼び出しサイトで必要とされる`Argwid`の最大値が`n`に集計されます。

この`n`の値が、その関数のスタックフレームに割り当てられる`outargs`セクションの最終的なサイズとなります。これにより、どのような関数呼び出しが行われても、引数を格納するための十分なスタック領域が確保されることが保証されます。

# [インデックス 28247] ファイルの概要

このコミットは、Goランタイムの32ビットシステムにおけるメモリ管理を改善することを目的としています。特に、ヒープビットマップが仮想アドレス空間全体をカバーできるようにすることで、カーネルが低すぎるアドレスにメモリを割り当てた場合に発生する可能性のある障害モードを解消します。これにより、32ビット環境でのGoプログラムの堅牢性と効率が向上します。

## 元コミット内容

```
runtime: use entire address space on 32 bit

In issue #13992, Russ mentioned that the heap bitmap footprint was
halved but that the bitmap size calculation hadn't been updated. This
presents the opportunity to either halve the bitmap size or double
the addressable virtual space. This CL doubles the addressable virtual
space. On 32 bit this can be tweaked further to allow the bitmap to
cover the entire 4GB virtual address space, removing a failure mode
if the kernel hands out memory with a too low address.

First, fix the calculation and double _MaxArena32 to cover 4GB virtual
memory space with the same bitmap size (256 MB).

Then, allow the fallback mode for the initial memory reservation
on 32 bit (or 64 bit with too little available virtual memory) to not
include space for the arena. mheap.sysAlloc will automatically reserve
additional space when the existing arena is full.

Finally, set arena_start to 0 in 32 bit mode, so that any address is
acceptable for subsequent (additional) reservations.

Before, the bitmap was always located just before arena_start, so
fix the two places relying on that assumption: Point the otherwise unused
mheap.bitmap to one byte after the end of the bitmap, and use it for
bitmap addressing instead of arena_start.

With arena_start set to 0 on 32 bit, the cgoInRange check is no longer a
sufficient check for Go pointers. Introduce and call inHeapOrStack to
check whether a pointer is to the Go heap or stack.

While we're here, remove sysReserveHigh which seems to be unused.

Fixes #13992
```

## 変更の背景

このコミットは、Goランタイムが32ビットシステムで直面していたメモリ管理の課題に対処するために行われました。特に、Goのガベージコレクタ（GC）がヒープ内のポインタを追跡するために使用する「ヒープビットマップ」の配置とサイズ計算に関する問題が背景にあります。

Goランタイムは、ヒープのために連続した仮想メモリ領域を確保しようとしますが、32ビットシステムでは仮想アドレス空間が4GBに制限されており、他のプロセスやライブラリ（特にAndroid LのARTなど）が積極的に仮想メモリを予約するため、メモリの断片化が発生しやすいという問題がありました。

コミットメッセージで言及されているIssue #13992では、ヒープビットマップのフットプリント（占有するメモリ量）が半減されたにもかかわらず、そのサイズ計算が更新されていなかったことが指摘されています。この計算の不整合により、ビットマップがカバーできる仮想アドレス空間の範囲が限定され、カーネルがビットマップがカバーできない低すぎるアドレスにメモリを割り当てた場合に、Goランタイムが正常に動作しないという障害モードが発生する可能性がありました。

このコミットは、この問題を解決し、32ビットシステム上でのGoランタイムのメモリ割り当ての堅牢性を高めることを目的としています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリマネージャを使用して、ヒープ、スタック、およびその他の内部データ構造を管理します。

*   **ヒープ (Heap)**: プログラムが動的に割り当てるオブジェクト（`make`や`new`で作成されるもの）が格納される領域です。Goのガベージコレクタによって管理されます。
*   **スタック (Stack)**: 関数呼び出しのローカル変数や引数、リターンアドレスなどが格納される領域です。Goでは、ゴルーチンごとに独立したスタックを持ち、必要に応じてスタックサイズが動的に増減します。
*   **アリーナ (Arena)**: Goランタイムは、OSから大きな仮想メモリ領域をまとめて確保し、それを「アリーナ」と呼ばれる固定サイズのチャンクに分割して管理します。これにより、OSへのシステムコールを減らし、メモリ割り当ての効率を高めます。

### ヒープビットマップ

ヒープビットマップは、Goのガベージコレクタにとって非常に重要なデータ構造です。ヒープ上の各ワード（通常はポインタサイズ）がポインタであるかどうか、またはポインタを含む構造体の一部であるかどうかを示すビットを格納します。GCは、このビットマップを参照することで、ヒープをスキャンして到達可能なオブジェクトを正確に識別し、不要なオブジェクトを解放します。ビットマップの正確な管理は、GCの正確性と効率に直結します。

### 32ビットシステムのアドレス空間の制約

32ビットシステムでは、仮想アドレス空間が2^32バイト、つまり4GBに制限されています。これは、64ビットシステム（2^64バイト）と比較して非常に小さいです。この限られたアドレス空間内で、OS、アプリケーション、共有ライブラリなどがそれぞれメモリを要求するため、連続した大きな仮想メモリ領域を確保することが困難になることがあります。これを「仮想メモリの断片化」と呼びます。Goランタイムがヒープビットマップやアリーナのために大きな連続領域を必要とする場合、この断片化が問題を引き起こす可能性があります。

### Cgoとポインタの安全性

Cgoは、GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用する際には、GoとCの間でポインタを渡す際の厳格なルールがあります。GoのガベージコレクタはGoが管理するメモリ（ヒープやスタック）内のポインタのみを認識するため、Cが割り当てたメモリ内のポインタを追跡することはできません。`cgoInRange`のようなチェックは、Goが管理するメモリ範囲内にポインタがあるかどうかを確認するために使用され、GoとCの間のポインタの安全性を維持する上で重要です。

## 技術的詳細

このコミットは、32ビットシステムにおけるGoランタイムのメモリ管理、特にヒープビットマップとアリーナの取り扱いを根本的に改善します。

1.  **`_MaxArena32`の拡張**:
    *   以前は、`_MaxArena32`は32ビットシステムで利用可能な仮想アドレス空間の一部（例えば2GB）を想定していました。
    *   このコミットでは、`_MaxArena32`を`1<<32 - 1`、つまり32ビットシステムで利用可能な仮想アドレス空間の最大値（約4GB）に設定し直します。これにより、ヒープビットマップが理論上4GBの仮想アドレス空間全体をカバーできるようになります。

2.  **ヒープビットマップサイズ計算の修正**:
    *   ヒープビットマップは、ヒープ内の各ワードに対して2ビット（以前は4ビット）を使用するように変更されました。この変更は以前に行われていましたが、ビットマップのサイズ計算が更新されていませんでした。
    *   このコミットでは、`mallocinit`関数内の`bitmapSize`の計算を`arenaSize / (sys.PtrSize * 8 / 2)`に修正し、2ビット/ワードの新しいフットプリントを正確に反映させます。これにより、ビットマップがより効率的にメモリを使用し、より広いアドレス空間をカバーできるようになります。

3.  **`arena_start`の0への設定**:
    *   32ビットモードでは、`mheap_.arena_start`が0に設定されます。これは、GoランタイムがOSからメモリを要求する際に、特定のアドレス範囲に縛られず、OSが提供する任意のアドレスを受け入れられるようにするためです。
    *   これにより、カーネルが低すぎるアドレスにメモリを割り当てた場合でも、Goランタイムがそのメモリを使用できるようになり、障害モードが解消されます。

4.  **`mheap.bitmap`のアドレス指定の変更**:
    *   以前は、`mheap_.bitmap`は`mheap_.arena_start`の直前に配置されているという仮定に基づいてアドレス指定が行われていました。
    *   `arena_start`が0に設定されるとこの仮定が崩れるため、`mheap_.bitmap`はビットマップの終端の1バイト後を指すように変更されます。そして、ビットマップのアドレス指定は`arena_start`ではなく、この`mheap_.bitmap`フィールドを基準に行われるようになります。

5.  **`mheap.sysAlloc`のフォールバックメカニズムの改善**:
    *   初期メモリ予約が失敗した場合（特に32ビットシステムや、64ビットシステムで利用可能な仮想メモリが少ない場合）、`mheap.sysAlloc`はアリーナのためのスペースを含まないフォールバックモードを許可するようになります。
    *   これにより、既存のアリーナが満杯になったときに、`mheap.sysAlloc`が自動的に追加のスペースを予約できるようになり、メモリ割り当ての柔軟性が向上します。`arenaSizes`のリストに`0`が追加され、初期アリーナサイズが0でも起動できるように変更されています。

6.  **`cgoInRange`から`inHeapOrStack`への移行**:
    *   `arena_start`が0に設定されると、`cgoInRange`（ポインタが`mheap_.arena_start`と`mheap_.arena_used`の間にあるかをチェックする）は、Goポインタの有効性をチェックするのに十分ではなくなります。
    *   このため、`inHeapOrStack`という新しい関数が導入されます。この関数は、与えられたポインタがGoのヒープまたはスタックのいずれかを指しているかをより正確にチェックします。`cgocall.go`内の`cgoIsGoPointer`関数が`cgoInRange`の代わりに`inHeapOrStack`を呼び出すように変更されます。

7.  **`sysReserveHigh`の削除**:
    *   `sysReserveHigh`関数は、使用されていないと判断されたため削除されます。これはコードの簡素化と保守性の向上に貢献します。

これらの変更により、Goランタイムは32ビットシステム上でより広範な仮想アドレス空間を効率的に利用し、メモリ割り当ての失敗を減らし、全体的な安定性を向上させます。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/cgocall.go`: `cgoIsGoPointer`関数が`cgoInRange`の代わりに`inHeapOrStack`を呼び出すように変更。
*   `src/runtime/malloc.go`: `_MaxArena32`定数の変更、`bitmapSize`の計算修正、`mallocinit`における`arena_start`の設定ロジックの変更、`mheap.sysAlloc`のロジック修正、`sysReserveHigh`関数の削除。
*   `src/runtime/mbitmap.go`: `mapBits`および`heapBitsForAddr`関数におけるビットマップアドレス指定の変更。
*   `src/runtime/mheap.go`: `mheap`構造体の`bitmap`フィールドのコメント更新、`inHeapOrStack`関数の追加。

```go
+// inHeapOrStack is a variant of inheap that returns true for pointers into stack spans.
+//go:nowritebarrier
+//go:nosplit
+func inHeapOrStack(b uintptr) bool {
+	if b == 0 || b < mheap_.arena_start || b >= mheap_.arena_used {
+		return false
+	}
+	// Not a beginning of a block, consult span table to find the block beginning.
+	s := h_spans[(b-mheap_.arena_start)>>_PageShift]
+	if s == nil || b < s.base() {
+		return false
+	}
+	switch s.state {
+	case mSpanInUse:
+		return b < s.limit
+	case _MSpanStack:
+		return b < s.base()+s.npages<<_PageShift
+	default:
+		return false
+	}
+}
```
`inHeapOrStack`関数が追加されました。この関数は、与えられたポインタ`b`がGoのヒープ（`mSpanInUse`）またはスタック（`_MSpanStack`）のいずれかのスパン内にあるかどうかをチェックします。これにより、`arena_start`が0に設定された場合でも、Goが管理するポインタの有効性を正確に判断できるようになります。

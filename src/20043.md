# [インデックス 20043] ファイルの概要

このコミットは、Goコンパイラ（`cmd/9g`）、Goガーベージコレクタ（`cmd/gc`）、およびGoリンカ（`cmd/ld`）におけるPowerPC 64ビットアーキテクチャ（`dev.power64`）関連のビルド問題を修正するものです。具体的には、スタックオーバーフローチェック、OLROT（Optimized Load/Rotate/Test）認識、およびアドレスオフセット加算命令の生成に関する修正が含まれています。

## 変更の背景

このコミットは、Go言語のPowerPC 64ビットアーキテクチャ（`dev.power64`）におけるビルドプロセスで発生していた問題を解決するために導入されました。Goはクロスプラットフォーム対応を重視しており、様々なアーキテクチャで正しく動作することが求められます。PowerPC 64ビット環境でのビルドが失敗したり、生成されるコードが正しくなかったりする問題があったため、それらを修正する必要がありました。

具体的には、以下の3つの主要な問題に対処しています。

1.  **nonsplit stack overflow checkの無効化**: Goのランタイムは、スタックの拡張（スプリットスタック）を効率的に管理しますが、特定の状況下では「nonsplit」なスタック、つまり分割されないスタックのオーバーフローチェックが必要になることがあります。PowerPC 64ビット環境でのビルドにおいて、このチェックが問題を引き起こしていた可能性があります。
2.  **OLROT認識の無効化**: OLROT（Optimized Load/Rotate/Test）は、特定の最適化された命令シーケンスを指す可能性があります。コンパイラがこれらのパターンを誤って認識したり、PowerPC 64ビットアーキテクチャの特性と合わない方法で最適化を試みたりすることで、ビルドエラーや不正なコード生成につながっていたと考えられます。
3.  **アドレスオフセット加算命令の修正**: アドレス計算は、プログラムがメモリ上のデータにアクセスするために不可欠です。コンパイラやリンカが、PowerPC 64ビットアーキテクチャの命令セットに合致しない方法でアドレスにオフセットを加算する命令を生成していたため、実行時エラーやクラッシュの原因となっていた可能性があります。

これらの問題は、Goコンパイラ（`cmd/9g`）、Goガーベージコレクタ（`cmd/gc`）、およびGoリンカ（`cmd/ld`）の各コンポーネントに影響を与えていたため、それぞれのコードベースで修正が必要でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ・リンカに関する基本的な知識が必要です。

*   **Go言語のツールチェイン**: Go言語は、`go build`コマンドを通じてソースコードをコンパイルし、実行可能ファイルを生成します。このプロセスには、コンパイラ（`gc`、`9g`など）、アセンブラ（`as`）、リンカ（`ld`）などのツールが含まれます。
    *   `cmd/gc`: Go言語のフロントエンドコンパイラで、Goのソースコードを中間表現に変換します。
    *   `cmd/9g`: Goのコンパイラの一部で、PowerPC 64ビットアーキテクチャ（`9g`はPowerPCを指す）向けのコード生成を担当します。
    *   `cmd/ld`: Goのリンカで、コンパイルされたオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。
*   **スタックとスタックオーバーフロー**: プログラムが関数を呼び出す際、ローカル変数や関数の引数などはスタックと呼ばれるメモリ領域に割り当てられます。スタックは通常、固定されたサイズを持っており、関数呼び出しが深くネストしたり、大きなローカル変数が宣言されたりすると、スタック領域を使い果たしてしまうことがあります。これをスタックオーバーフローと呼びます。
*   **スプリットスタック (Split Stack)**: Go言語のランタイムは、スタックオーバーフローを防ぐために「スプリットスタック」というメカニズムを採用しています。これは、必要に応じてスタックを動的に拡張する仕組みです。関数呼び出し時にスタックの残量が少ない場合、ランタイムは新しい、より大きなスタックセグメントを割り当て、古いスタックの内容を新しいスタックにコピーします。
*   **nonsplit stack overflow check**: 通常のスプリットスタックのメカニズムとは異なり、特定の状況（例えば、ランタイムの非常に低レベルな部分や、スタックの拡張が許されないコンテキスト）では、スタックが分割されない（nonsplit）状態でオーバーフローが発生しないかを確認するチェックが必要になることがあります。
*   **OLROT (Optimized Load/Rotate/Test)**: これは特定のCPUアーキテクチャ（特にPowerPCのようなRISCアーキテクチャ）における、ロード、ローテート、テストといった一連の操作を最適化するための命令パターンやコンパイラの最適化戦略を指す可能性があります。コンパイラがこれらのパターンを認識し、より効率的な機械語命令を生成しようとします。
*   **アドレスオフセット加算**: プログラムがメモリ上のデータにアクセスする際、ベースアドレスにオフセット（相対的な位置）を加算して目的のデータの正確なアドレスを計算します。例えば、構造体のメンバーにアクセスする場合、構造体のベースアドレスにメンバーのオフセットを加算します。この計算は、CPUの命令セットによって効率的に行われる必要があります。
*   **`thechar`変数**: Goのコンパイラやリンカのソースコードでは、`thechar`というグローバル変数がよく使われます。これは、現在コンパイルまたはリンクしているターゲットアーキテクチャを示す文字コードです。例えば、`'9'`はPowerPC 64ビット（`ppc64`）を、`'6'`はx86-64（`amd64`）を、`'8'`はx86（`386`）を指します。この変数を使って、アーキテクチャ固有のコードパスを条件分岐させます。

## 技術的詳細

このコミットは、GoのツールチェインにおけるPowerPC 64ビットアーキテクチャ固有の3つの問題を解決しています。

1.  **`src/cmd/ld/lib.c`におけるnonsplit stack overflow checkの無効化**:
    `dostkcheck`関数は、スタックチェックに関連する処理を行うGoリンカの関数です。この関数内で、`thechar == '9'`（つまりPowerPC 64ビットアーキテクチャの場合）に限り、関数の残りの処理を`return`でスキップするように変更されています。これは、PowerPC 64ビット環境において、`dostkcheck`が実行するnonsplit stack overflow checkが不適切であるか、またはビルドを妨げる原因となっていたため、一時的に無効化されたことを意味します。このチェックは、通常、ランタイムがスタックの健全性を保証するために重要ですが、特定のアーキテクチャやビルド構成では問題を引き起こすことがあります。

2.  **`src/cmd/gc/walk.c`におけるOLROT認識の無効化**:
    `walkrotate`関数は、Goコンパイラの`gc`部分で、コードの最適化、特にビット回転（rotate）操作に関連する最適化を行う関数です。この関数もまた、`thechar == '9'`（PowerPC 64ビットアーキテクチャの場合）に限り、関数の残りの処理を`return`でスキップするように変更されています。これは、PowerPC 64ビット環境において、`walkrotate`が試みるOLROT（Optimized Load/Rotate/Test）の認識や最適化が、PowerPCの命令セットと互換性がなかったり、誤ったコードを生成したりしていたため、この最適化パスを無効化したことを示唆しています。

3.  **`src/cmd/9g/cgen.c`におけるアドレスオフセット加算命令の修正**:
    `src/cmd/9g/cgen.c`は、PowerPC 64ビット向けのコード生成を担当するファイルです。このファイルでは、`ginsadd`という新しい静的関数が導入されました。
    *   `ginsadd`関数は、`ginscon`（定数を命令に組み込む関数）の代わりに、アドレスにオフセットを加算する際に使用されます。
    *   元のコードでは、`agen`関数（アドレス生成を担当）内で、`n->xoffset`（構造体メンバーのオフセットなど）をアドレスに加算する際に、直接`ginscon(optoas(OADD, types[tptr]), n->xoffset, res);`が使われていました。
    *   この変更により、`ginscon`の代わりに新しく定義された`ginsadd`が呼び出されるようになりました。`ginsadd`は、まず`dst`レジスタの内容を一時的なレジスタ`n1`に移動し、その`n1`に対してオフセットを加算し、最後に`n1`の内容を`dst`レジスタに戻すという一連の操作を行います。
    *   この修正は、PowerPC 64ビットアーキテクチャにおいて、アドレスにオフセットを加算する際の命令生成が正しく行われていなかったことを示しています。`ginsadd`の導入により、より正確でアーキテクチャに適合した命令シーケンスが生成されるようになり、メモリ参照の正確性が保証されます。これは、PowerPCの命令セットが、特定のオフセット加算操作に対して直接的な命令を持たない場合や、レジスタ間での中間操作が必要な場合に特に重要です。

これらの変更は、GoのツールチェインがPowerPC 64ビットアーキテクチャ上で安定して動作し、正しい機械語コードを生成するために不可欠な修正です。

## コアとなるコードの解説

### `src/cmd/9g/cgen.c`

*   **`ginsadd`関数の追加**:
    このコミットの最も重要な変更点の一つは、`ginsadd`という新しいヘルパー関数が追加されたことです。この関数は、アドレスにオフセットを加算する操作をカプセル化します。
    ```c
    static void
    ginsadd(int as, vlong off, Node *dst)
    {
        Node n1;

        regalloc(&n1, types[tptr], dst); // dstレジスタの内容を一時レジスタn1に割り当て
        gmove(dst, &n1);                 // dstの内容をn1に移動
        ginscon(as, off, &n1);           // n1にオフセットoffを加算する命令を生成
        gmove(&n1, dst);                 // n1の内容をdstに戻す
        regfree(&n1);                    // n1レジスタを解放
    }
    ```
    このシーケンスは、PowerPC 64ビットアーキテクチャにおいて、直接的な「レジスタ + 定数オフセット」の加算命令が効率的でない場合や、特定の命令制約がある場合に必要となる可能性があります。一時レジスタを使用することで、より複雑なアドレス計算を正確に表現しています。
*   **`agen`関数での`ginsadd`の利用**:
    `agen`関数は、GoのAST（抽象構文木）ノードからアドレスを生成する役割を担っています。以前は、`n->xoffset`（構造体フィールドのオフセットなど）をアドレスに加算する際に、直接`ginscon`を呼び出していました。
    ```c
    // 変更前
    ginscon(optoas(OADD, types[tptr]), n->xoffset, res);
    // 変更後
    ginsadd(optoas(OADD, types[tptr]), n->xoffset, res);
    ```
    この変更により、アドレスオフセット加算のロジックが`ginsadd`に集約され、PowerPC 64ビットアーキテクチャ向けの正確な命令シーケンスが生成されるようになりました。これは、コンパイラが生成する機械語コードの正確性と効率性を向上させるための重要な修正です。

### `src/cmd/gc/walk.c`

*   **`walkrotate`関数の条件付きスキップ**:
    `walkrotate`関数は、コンパイラの最適化フェーズの一部で、ビット回転操作に関連する最適化を行います。このコミットでは、PowerPC 64ビットアーキテクチャ（`thechar == '9'`）の場合に、この関数の残りの処理をスキップするように変更されました。
    ```c
    if(thechar == '9')
        return;
    ```
    これは、PowerPC 64ビット環境において、この最適化が正しく機能しないか、または問題を引き起こす可能性があったため、一時的に無効化されたことを意味します。これにより、不正な最適化によるビルドエラーや実行時エラーを防ぎます。

### `src/cmd/ld/lib.c`

*   **`dostkcheck`関数の条件付きスキップ**:
    `dostkcheck`関数は、リンカにおけるスタックチェックに関連する処理を行います。このコミットでは、`walkrotate`と同様に、PowerPC 64ビットアーキテクチャ（`thechar == '9'`）の場合に、この関数の残りの処理をスキップするように変更されました。
    ```c
    if(thechar == '9')
        return;
    ```
    この変更は、PowerPC 64ビット環境でのnonsplit stack overflow checkが、ビルドプロセスに問題を引き起こしていたため、このチェックを無効化することでビルドを成功させることを目的としています。

これらの変更は、GoのツールチェインがPowerPC 64ビットアーキテクチャ上で正しく機能し、安定したビルドを可能にするための、アーキテクチャ固有の重要な修正です。

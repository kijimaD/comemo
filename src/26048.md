## 変更の背景

このコミットが導入される以前は、Goの`net/http`パッケージが提供するHTTP/2サーバーにおいて、リクエストハンドラ（`http.Handler`インターフェースを実装する`ServeHTTP`メソッド）内でパニックが発生した場合、そのパニックが適切に捕捉されず、HTTP/2コネクション全体が予期せず終了してしまう可能性がありました。これは、サーバーの安定性や可用性に大きな影響を与える問題であり、特に本番環境での運用においては致命的となり得ます。

この問題は、Goのissue #13555として報告されており、このコミットはその問題を解決するために、`x/net/http2`パッケージの更新を取り込む形で実装されました。具体的には、ハンドラ内で発生したパニックを`recover`メカニズムで捕捉し、そのストリームに対してHTTP/2の`RST_STREAM`フレームを送信することで、他のアクティブなストリームへの影響を最小限に抑えつつ、エラーを適切にクライアントに通知するように変更されています。

## 前提知識の解説

### Goの`panic`と`recover`

Go言語には、プログラムの異常な状態を示すための`panic`と、そのパニックから回復するための`recover`という組み込み関数があります。
*   **`panic`**: 通常のエラー処理では対応できないような、プログラムの回復不可能なエラーが発生した場合に呼び出されます。`panic`が呼び出されると、現在の関数の実行が中断され、遅延関数（`defer`で登録された関数）が実行されながら、呼び出し元の関数へとスタックを遡っていきます。最終的に`main`関数までパニックが到達すると、プログラムはクラッシュします。
*   **`recover`**: `defer`関数内で呼び出された場合にのみ有効です。`recover`が呼び出されると、現在進行中のパニックを捕捉し、パニックの引数（`panic`に渡された値）を返します。`recover`がパニックを捕捉すると、スタックの巻き戻しは停止し、`recover`を呼び出した`defer`関数の次のステートメントから通常の実行が再開されます。これにより、プログラムのクラッシュを防ぎ、エラー回復処理を行うことができます。

### HTTP/2プロトコル

HTTP/2は、HTTP/1.1の主要な欠点を克服するために設計されたWebプロトコルです。主な特徴は以下の通りです。
*   **多重化 (Multiplexing)**: 一つのTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が解消され、ページの読み込み速度が向上します。
*   **ストリーム (Stream)**: HTTP/2では、各リクエスト/レスポンスの交換は「ストリーム」と呼ばれる独立した双方向のシーケンスとして扱われます。各ストリームには一意の識別子が付与されます。
*   **フレーム (Frame)**: HTTP/2の通信は、小さなバイナリ単位である「フレーム」に分割されます。ヘッダフレーム、データフレーム、設定フレーム、`RST_STREAM`フレームなど、様々な種類のフレームがあります。
*   **`RST_STREAM`フレーム**: ストリームを異常終了させるために使用されるフレームです。クライアントまたはサーバーが、特定のストリームにエラーが発生したことを相手に通知するために送信します。エラーコードを含めることができ、これによりエラーの種類を伝えることができます。

### Goの`net/http`パッケージと`ServeHTTP`

`net/http`パッケージは、GoでWebサーバーを構築する際の基盤となります。
*   **`http.Handler`インターフェース**: HTTPリクエストを処理するためのインターフェースで、`ServeHTTP(ResponseWriter, *Request)`メソッドを一つだけ持ちます。このメソッドが実際のリクエスト処理ロジックを実装します。
*   **`ServeHTTP`メソッド**: クライアントからのHTTPリクエストを受け取り、それに応じたレスポンスを生成してクライアントに返します。

### `x/net/http2`のバンドル

Go 1.6以降、`net/http`パッケージはHTTP/2プロトコルをサポートするために、外部パッケージである`golang.org/x/net/http2`のコードを内部にバンドルしています。これにより、開発者は追加のインポートなしにHTTP/2の機能を利用できるようになっています。このコミットは、そのバンドルされたコードを更新するものです。

## 技術的詳細

このコミットの主要な目的は、HTTP/2ハンドラ内で発生したパニックを捕捉し、適切に処理することです。そのために、以下の技術的な変更が導入されています。

1.  **`runHandler`関数でのパニック捕捉**:
    *   `http2serverConn.runHandler`関数は、HTTP/2リクエストを処理するハンドラを実行するゴルーチンで動作します。
    *   この関数に`defer`文が追加され、ハンドラの実行中にパニックが発生した場合に`recover()`を呼び出すことでパニックを捕捉します。
    *   パニックが捕捉された場合、スタックトレースをログに出力し、クライアントに対して`RST_STREAM`フレームを送信します。

2.  **`http2handlerPanicRST`型の導入**:
    *   ハンドラがパニックを起こした際に、そのストリームをリセットするための特別なフレームメッセージ`http2handlerPanicRST`が新しく定義されました。
    *   この型は`writeFrame`メソッドを実装しており、`http2ErrCodeInternal`エラーコードと共に`RST_STREAM`フレームを書き込む役割を担います。これにより、クライアントはサーバー内部でエラーが発生したことを知ることができます。

3.  **`http2errHandlerPanicked`エラーの定義**:
    *   `Request.Body`からの読み取り中にハンドラがパニックを起こした場合に、呼び出し元に返される新しいエラー`http2errHandlerPanicked`が定義されました。これは、パニックがリクエストボディの処理に影響を与えたことを示します。

4.  **`wroteFrame`関数での`http2handlerPanicRST`の処理**:
    *   `http2serverConn.wroteFrame`関数は、フレームの書き込み結果を処理する役割を持ちます。
    *   この関数に、書き込みメッセージが`http2handlerPanicRST`型であるかどうかをチェックするロジックが追加されました。もしそうであれば、該当するストリームを`http2errHandlerPanicked`エラーでクローズします。

5.  **クライアント側のリクエストキャンセル処理の統一**:
    *   `http2requestCancel`というヘルパー関数が導入され、`req.Cancel`チャネルへのアクセスを統一しました。これにより、クライアント側の`RoundTrip`関数や`awaitRequestCancel`関数で、リクエストキャンセルをより一貫して処理できるようになります。
    *   また、クライアント側の`RoundTrip`関数では、`cs.peerReset`チャネルからのエラーも処理するようになり、サーバーからの`RST_STREAM`フレームによるストリームのリセットを適切にエラーとして返すようになりました。

6.  **テストの有効化**:
    *   `src/net/http/serve_test.go`内の`TestHandlerPanicNil_h2`と`TestHandlerPanic_h2`という、HTTP/2ハンドラでのパニックをテストする項目が、以前は「既知の失敗」としてスキップされていましたが、このコミットによってスキップが解除され、有効化されました。これにより、ハンドラパニック処理が正しく機能することが自動テストで検証されるようになります。

これらの変更により、HTTP/2ハンドラがパニックを起こしても、サーバー全体がクラッシュすることなく、影響を限定されたストリームに留め、クライアントに適切なエラーを通知できるようになります。

## コアとなるコードの解説

### `src/net/http/h2_bundle.go`

1.  **`func http2requestCancel(req *Request) <-chan struct{} { return req.Cancel }` の追加**:
    *   これは`Request.Cancel`チャネルを返すシンプルなヘルパー関数です。クライアント側のコードで`req.Cancel`を直接参照する代わりにこの関数を使用することで、将来的に`Request.Cancel`の実装が変更された場合でも、コードの変更箇所を局所化しやすくなります。

2.  **`var http2errHandlerPanicked = errors.New("http2: handler panicked")` の追加**:
    *   ハンドラがパニックを起こした際に、関連する操作（特に`Request.Body`からの読み取り）がブロックされている呼び出し元に返されるエラーとして定義されます。これにより、パニックが原因で操作が中断されたことを明確に伝えることができます。

3.  **`func (sc *http2serverConn) wroteFrame(res http2frameWriteResult)` 内の変更**:
    *   `if _, ok := wm.write.(http2handlerPanicRST); ok { sc.closeStream(st, http2errHandlerPanicked) }` の追加。
    *   フレーム書き込みの結果を処理する`wroteFrame`関数内で、書き込みメッセージが`http2handlerPanicRST`型であるかをチェックします。もしそうであれば、そのストリームを`http2errHandlerPanicked`エラーでクローズします。これは、ハンドラパニックによってストリームが異常終了したことをサーバー側で認識し、適切に処理するための重要なステップです。

4.  **`func (sc *http2serverConn) runHandler(...)` の変更**:
    *   この関数は、HTTP/2リクエストを処理するハンドラを実行するゴルーチンです。
    *   **`didPanic := true` と `defer func() { ... }()` の追加**:
        *   `didPanic`フラグは、ハンドラが正常に完了したか、パニックを起こしたかを追跡するために使用されます。
        *   `defer`関数ブロック内で`recover()`を呼び出すことで、`handler(rw, req)`の実行中に発生したパニックを捕捉します。
        *   パニックが捕捉された場合（`didPanic`が`true`のままの場合）、`runtime.Stack`でスタックトレースを取得し、ログに出力します。
        *   さらに、`http2handlerPanicRST`型のフレームメッセージを作成し、`sc.writeFrameFromHandler`を通じてクライアントに`RST_STREAM`フレームを送信します。これにより、クライアントはサーバー側のハンドラでエラーが発生したことを認識し、そのストリームを終了させることができます。
    *   **`handler(rw, req)` の後に `didPanic = false` の追加**:
        *   ハンドラがパニックを起こさずに正常に完了した場合、`didPanic`を`false`に設定します。これにより、`defer`関数はパニック回復ロジックを実行せず、`rw.handlerDone()`を呼び出して正常な終了処理を行います。

5.  **`func (w *http2responseWriter) handlerDone()` 内の変更**:
    *   `if rws == nil { panic("handlerDone called twice") }` の削除。
    *   このパニックチェックは、`runHandler`でのパニック捕捉ロジックの導入により不要になったか、あるいは新しいロジックと競合する可能性があったため削除されました。ハンドラがパニックを起こした場合、`handlerDone`が複数回呼び出される可能性があり、その際に不要なパニックを引き起こすのを防ぎます。

6.  **`func (cc *http2ClientConn) RoundTrip(req *Request) (*Response, error)` 内の変更**:
    *   `case <-req.Cancel:` が `case <-http2requestCancel(req):` に変更され、前述のヘルパー関数を使用するように統一されました。
    *   **`case <-cs.peerReset: return nil, cs.resetErr` の追加**:
        *   クライアント側で、サーバーから`RST_STREAM`フレームが送信された場合（`peerReset`チャネルで通知される）、そのリセットエラーを`RoundTrip`の呼び出し元に返すように変更されました。これにより、サーバー側のハンドラパニックによるストリームリセットをクライアント側で適切にエラーとして処理できるようになります。

7.  **`func (rl *http2clientConnReadLoop) processHeaderBlockFragment(...)` 内の変更**:
    *   `go cs.awaitRequestCancel(cs.req.Cancel)` が `go cs.awaitRequestCancel(http2requestCancel(cs.req))` に変更され、ここでも`http2requestCancel`ヘルパー関数が使用されるようになりました。

8.  **`type http2handlerPanicRST struct { StreamID uint32 }` と `func (hp http2handlerPanicRST) writeFrame(...)` の追加**:
    *   ハンドラパニック時に送信される`RST_STREAM`フレームの情報を保持する新しい型です。
    *   `writeFrame`メソッドは、指定された`StreamID`に対して`http2ErrCodeInternal`エラーコードで`RST_STREAM`フレームを書き込む実装を提供します。

### `src/net/http/serve_test.go`

1.  **`TestHandlerPanicNil_h2` と `TestHandlerPanic_h2` から `t.Skip(...)` 行の削除**:
    *   これらのテストは、HTTP/2ハンドラがパニックを起こした場合の挙動を検証するためのものです。
    *   以前は「既知の失敗」としてスキップされていましたが、`h2_bundle.go`の変更によってパニック処理が実装されたため、これらのテストが有効化され、パニック処理が正しく機能するかどうかをCI/CDパイプラインで継続的に検証できるようになりました。

これらの変更により、GoのHTTP/2サーバーは、ハンドラ内の予期せぬパニックに対してもより堅牢になり、サービス全体の安定性が向上します。

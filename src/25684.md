このコミットは、GoランタイムがLinux/386アーキテクチャ上でvsyscallヘルパーを呼び出す方法に関する変更です。具体的には、動的リンク時だけでなく、常に位置独立コード（PIC）シーケンス `CALL 0x10(GS)` を使用するように統一し、それに伴う不要なビルドモード関連のロジックを削除しています。

## 元コミット内容

`cmd/go, runtime: always use position-independent code to invoke vsyscall helper on linux/386`

このコミットは、Linux/386環境において、vsyscallヘルパーを呼び出す際に常に位置独立コードを使用するように変更します。

以前の `golang.org/cl/16346` の変更では、動的リンク時にのみ `CALL 0x10(GS)` というPICシーケンスを介してvsyscallヘルパーを呼び出すようにGoランタイムが変更されました。しかし、このコミットでは、このコードシーケンスを常に機能させるのが比較的容易であることが判明したため、そのように変更し、Goツールからアセンブリにビルドモードを渡すための複雑なメカニズムを削除しました。

この変更に伴い、`m.tls` のサイズを拡張し、`0x10(GS)` への安全なアクセスを可能にしています（`GS` レジスタは `&m.tls + 4` に設定されるため、`0x10(GS)` は `m_tls[5]` にアクセスします）。

## 変更の背景

Goランタイムは、システムコールを効率的に実行するために、Linuxカーネルが提供するvsyscallメカニズムを利用していました。特にLinux/386アーキテクチャでは、vsyscallページは固定アドレスにマップされており、システムコールを高速に実行するためのエントリポイントを提供します。

以前のGoの変更（`golang.org/cl/16346`）では、動的リンクされたGoプログラムがvsyscallヘルパーを呼び出す際に、位置独立コード（PIC）である `CALL 0x10(GS)` を使用するようにしていました。これは、動的リンクされたプログラムがロードされるアドレスが実行時に決定されるため、絶対アドレスに依存しないコードが必要となるためです。しかし、静的リンクされたプログラムでは、`runtime·_vdso(SB)` のようなシンボルを直接参照するアプローチが取られていました。

このコミットの背景には、動的リンクと静的リンクでvsyscall呼び出しのメカニズムを分けることによる複雑さの解消があります。コミットメッセージにあるように、「そのコードシーケンスを常に機能させるのが比較的容易である」と判断されたため、動的リンクか静的リンクかに関わらず、一貫してPICシーケンス `CALL 0x10(GS)` を使用するように変更することで、コードの簡素化と保守性の向上が図られました。これにより、Goツールがビルドモード情報をアセンブリコードに渡すための「醜いメカニズム」が不要になります。

## 前提知識の解説

### 1. vsyscall (Virtual System Call)
Linuxカーネルは、一部のシステムコール（例: `gettimeofday`, `time`, `getcpu`）を高速化するために、ユーザー空間から直接呼び出せる「vsyscall」メカニズムを提供しています。これは、カーネルモードへの切り替えを伴わずに、ユーザー空間にマップされた特別なページ（vsyscallページ）上のコードを実行することで実現されます。これにより、システムコールのオーバーヘッドが削減され、パフォーマンスが向上します。
Linux/386アーキテクチャでは、vsyscallページは固定されたアドレスに配置されており、そのエントリポイントは通常、`0xffffe000` から `0xfffff000` の範囲にあります。

### 2. PIC (Position-Independent Code)
位置独立コード（PIC）は、メモリ上の任意のアドレスにロードされても正しく実行されるように設計された機械語コードです。これは、共有ライブラリ（.soファイル）や動的リンクされた実行可能ファイルで特に重要です。PICは、絶対アドレスではなく、現在のプログラムカウンタ（PC）からの相対アドレスや、特定のレジスタ（例: `GS` レジスタ）を基準としたオフセットを使用してメモリにアクセスします。これにより、プログラムがロードされるベースアドレスが実行時に変更されても、コードは正しく動作します。

### 3. GS レジスタ (Segment Register)
x86アーキテクチャには、`CS`, `DS`, `ES`, `FS`, `GS`, `SS` といったセグメントレジスタがあります。これらは、メモリセグメントのベースアドレスを保持し、メモリへのアクセスをセグメント化するために使用されます。
Linux/386環境では、`GS` レジスタはしばしばスレッドローカルストレージ（TLS: Thread-Local Storage）のベースアドレスを指すように設定されます。TLSは、各スレッドが独自のデータコピーを持つことを可能にするメカニズムで、グローバル変数や静的変数をスレッドごとに独立して管理するために使用されます。Goランタイムでは、`m` 構造体（マシンを表す構造体）の `tls` フィールドがこの目的で使用されます。

### 4. TLS (Thread-Local Storage)
スレッドローカルストレージ（TLS）は、マルチスレッドプログラミングにおいて、各スレッドが独自のデータインスタンスを持つことを可能にする記憶域期間です。これにより、グローバル変数や静的変数をスレッド間で共有することなく、各スレッドが独立した状態を保持できます。Goランタイムでは、`m` 構造体の一部としてTLSが利用され、特定のCPUレジスタ（Linux/386では `GS`）を介してアクセスされます。

### 5. `m` 構造体と `m.tls`
Goランタイムでは、`m` 構造体はOSのスレッド（マシン）を表します。各 `m` には、そのスレッド固有の情報が格納されており、その中には `tls` フィールドも含まれます。`m.tls` は、スレッドローカルストレージとして使用される配列であり、`GS` レジスタがこの配列の特定の位置を指すように設定されます。このコミットでは、`0x10(GS)` を安全にアクセスするために `m.tls` のサイズが拡張されています。`GS` が `&m.tls + 4` に設定されている場合、`0x10(GS)` は `(&m.tls + 4) + 0x10` を意味し、これは `m.tls` の5番目の要素（インデックス4）の次のワードに相当します。

## 技術的詳細

このコミットの核心は、Linux/386アーキテクチャにおけるvsyscallヘルパーの呼び出し方法を統一することです。

以前は、Goプログラムが動的リンクされているか静的リンクされているかによって、vsyscallヘルパーの呼び出し方法が異なっていました。
- **動的リンク時**: `CALL 0x10(GS)` を使用。これはPICであり、`GS` レジスタを基準としたオフセットでvsyscallエントリポイントを呼び出します。動的リンカは、vsyscallエントリポイントのアドレスを `0x10(GS)` に書き込むことで、このメカニズムを機能させます。
- **静的リンク時**: `CALL *runtime·_vdso(SB)` を使用。これは、`runtime·_vdso` シンボルが指す絶対アドレスを直接呼び出す方法です。

このコミットでは、動的リンカが `0x10(GS)` にvsyscallエントリポイントを格納する動作を模倣し、Goランタイム自身が `runtime·_vdso(SB)` のアドレスを `0x10(GS)` に書き込むように変更します。これにより、静的リンクされたプログラムでも `CALL 0x10(GS)` を使用できるようになり、呼び出しメカニズムが統一されます。

この変更の利点は以下の通りです。
1.  **コードの簡素化**: ビルドモードに応じて異なるアセンブリコードを生成する必要がなくなり、`src/cmd/go/build.go` からビルドモードをアセンブリに渡すための複雑なロジックが削除されます。
2.  **一貫性**: 動的リンクと静的リンクの両方で同じvsyscall呼び出しシーケンスを使用することで、ランタイムの動作が一貫し、デバッグや理解が容易になります。
3.  **保守性の向上**: 条件付きコンパイルディレクティブ（`#ifdef GOBUILDMODE_shared`）が不要になり、アセンブリコードがよりクリーンになります。

この変更を実現するために、`m.tls` のサイズが `[4]uintptr` から `[6]uintptr` に拡張されています。これは、`GS` レジスタが `&m.tls + 4` を指すように設定されているため、`0x10(GS)` が `m.tls` の5番目の要素（インデックス4）の次のワードにアクセスするためです。具体的には、`GS` が `m.tls[1]` のアドレスを指しているとすると、`0x10(GS)` は `m.tls[1] + 0x10` を意味し、これは `m.tls[1 + 0x10/sizeof(uintptr)]` となります。`uintptr` が4バイトの場合、`0x10/4 = 4` なので、`m.tls[5]` にアクセスすることになります。したがって、`m.tls` は少なくとも6つの要素（インデックス0から5）を保持できる必要があります。

`src/runtime/sys_linux_386.s` の `runtime·setldt` 関数内で、`runtime·_vdso(SB)` のアドレスを `0x10(CX)` (ここで `CX` は `GS` レジスタのベースアドレスに相当) に書き込む処理が追加されています。これにより、`CALL 0x10(GS)` が常にvsyscallエントリポイントを正しく呼び出すことができるようになります。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更
このファイルはGoコマンドのビルドロジックを扱います。以前は、`buildBuildmode` 変数（Goプログラムのビルドモード、例: `shared`, `archive` など）に基づいて、アセンブリコンパイラに `-D=GOBUILDMODE_...=1` というフラグを渡していました。このフラグは、アセンブリコード内で条件付きコンパイル（`#ifdef GOBUILDMODE_shared` など）を可能にするために使用されていました。
このコミットでは、vsyscall呼び出しのメカニズムが統一されたため、ビルドモードによってアセンブリコードを分岐させる必要がなくなりました。したがって、このビルドモード関連のアセンブリフラグを生成するロジックが削除され、Goコマンドのビルドプロセスが簡素化されました。

### `src/runtime/runtime2.go` の変更
`m` 構造体はGoランタイムにおけるOSスレッドの表現です。`tls` フィールドはスレッドローカルストレージとして使用され、`GS` セグメントレジスタがこの領域を指すように設定されます。
元の `tls [4]uintptr` は、4つの `uintptr` サイズの要素を保持できる配列でした。`GS` が `&m.tls + 4` に設定されている場合、`0x10(GS)` は `m.tls` のインデックス5の要素にアクセスします。`uintptr` が4バイト（32ビットシステム）の場合、`0x10` は16バイトであり、`4 * sizeof(uintptr)` に相当します。したがって、`m.tls[1]` のアドレスが `GS` のベースアドレスだとすると、`0x10(GS)` は `m.tls[1 + 4] = m.tls[5]` にアクセスします。
この変更により、`tls` のサイズが `[6]uintptr` に拡張され、`m.tls[5]` へのアクセスが配列の境界外アクセスにならないように保証されます。これにより、vsyscallエントリポイントを安全に格納し、アクセスできるようになります。

### `src/runtime/sys_linux_386.s` の変更
このアセンブリファイルは、Linux/386アーキテクチャにおけるGoランタイムの低レベルなシステムコール呼び出しを定義しています。

- **`INVOKE_SYSINFO` マクロの削除と `CALL 0x10(GS)` への統一**:
  以前は `INVOKE_SYSINFO` マクロが定義されており、`GOBUILDMODE_shared` が定義されているか否かによって、`CALL 0x10(GS)` または `CALL *runtime·_vdso(SB)` のいずれかに展開されていました。このコミットでは、このマクロが完全に削除され、すべてのvsyscall呼び出し箇所（`runtime·exit`, `runtime·open`, `runtime·read`, `runtime·nanotime` など多数）で直接 `CALL 0x10(GS)` が使用されるようになりました。これにより、アセンブリコードの条件分岐が解消され、よりシンプルで一貫性のあるコードベースが実現されました。

- **`runtime·setldt` における `0x10(GS)` の設定**:
  `runtime·setldt` 関数は、スレッドローカルストレージ（TLS）のセットアップに関連する処理を行います。このコミットで最も重要な変更の一つは、この関数内に以下の行が追加されたことです。
  ```assembly
          // We copy the dynamic linker behaviour of storing the vsyscall entry point
          // at 0x10(GS) so that it can be invoked by "CALL 0x10(GS)" in all
          // situations, not only those where the binary is actually dynamically
          // linked.
  	MOVL	runtime·_vdso(SB), AX
  	MOVL	AX, 0x10(CX)
  ```
  ここで、`runtime·_vdso(SB)` はvsyscallエントリポイントのアドレスを保持するGoランタイムのシンボルです。このアドレスが `AX` レジスタにロードされ、その後 `0x10(CX)` （`CX` は `GS` レジスタのベースアドレスに相当）に書き込まれます。これにより、Goランタイム自身が、動的リンカが行うのと同様に、`0x10(GS)` にvsyscallエントリポイントのアドレスを配置します。その結果、静的リンクされたGoプログラムでも `CALL 0x10(GS)` を使用してvsyscallヘルパーを呼び出すことが可能になります。

- **`runtime·setldt` 内の `modify_ldt` システムコール呼び出し**:
  `runtime·setldt` 関数は、`modify_ldt` システムコールを呼び出してLDT（Local Descriptor Table）を設定します。このシステムコール自体は、`0x10(GS)` がまだ正しく設定されていない段階で呼び出されるため、`CALL 0x10(GS)` を使用することはできません。そのため、この特定のシステムコール呼び出しは、直接 `INT $0x80` （Linux/386におけるソフトウェア割り込みによるシステムコール呼び出し）を使用するように変更されています。これは、`0x10(GS)` を介した呼び出しメカニズムが確立される前の初期化段階であるため、適切な対応です。

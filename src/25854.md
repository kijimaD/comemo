# [インデックス 25854] ファイルの概要

このコミットは、Go言語の`cmd/yacc`ツールにおけるメモリ割り当ての改善を目的としています。具体的には、生成されるパーサーの内部構造を変更し、固定サイズの初期スタックと`lval`（字句解析値）をパーサーステートメント内に直接配置することで、動的なメモリ割り当てを削減しています。また、`$$char`（ルックアヘッド文字）もパーサーステートメントに移動させ、`Lookahead()`メソッド内でクロージャを使用しないようにすることで、さらなるメモリ割り当ての最適化を図っています。これにより、パーサーのパフォーマンス向上とガベージコレクションの負荷軽減が期待されます。

## 変更の背景

この変更の主な背景は、`cmd/yacc`によって生成されるパーサーの実行時パフォーマンスを最適化することにあります。特に、動的なメモリ割り当て（ヒープ割り当て）を減らすことで、ガベージコレクション（GC）の頻度と負荷を軽減し、全体的な処理速度を向上させることを目指しています。

従来の`yacc`生成パーサーでは、パーシングスタックやルックアヘッドトークンに関連する一部のデータがヒープに割り当てられたり、クロージャを通じてアクセスされたりしていました。これらの動的な割り当てやクロージャの使用は、オーバーヘッドを発生させ、特に頻繁にパーサーが実行されるようなシナリオでは性能ボトルネックとなる可能性がありました。

このコミットは、これらの要素をパーサーの構造体（`$$ParserImpl`）に直接埋め込むことで、スタック割り当て（または構造体の一部としての連続したメモリ割り当て）を促進し、メモリの局所性を高め、GCの負担を減らすことを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **`cmd/yacc`**: Go言語の標準ライブラリに含まれる、Yacc（Yet Another Compiler Compiler）に似たパーサー生成ツールです。文法定義ファイル（通常`.y`拡張子）から、Go言語のパーサーコードを生成します。Goコンパイラやその他のツールチェーンの一部で利用されています。
2.  **Yacc/LALR(1)パーサー**: YaccはLALR(1)パーサーを生成します。これは、入力トークンストリームを読み込み、文法規則に従って構文木を構築するボトムアップパーサーの一種です。パーシングプロセスでは、状態スタックとルックアヘッドトークン（次に読み込まれるトークン）が重要な役割を果たします。
3.  **パーシングスタック**: LALR(1)パーサーは、現在のパーシング状態と、これまでに認識された文法記号を保持するためにスタックを使用します。このスタックは、シフト/還元操作のたびに操作されます。
4.  **`lval` (Lexical Value)**: 字句解析器（lexer）がトークンを返すと、そのトークンに関連付けられた意味的な値（例えば、数値リテラルの実際の数値、識別子の名前など）が`lval`と呼ばれる変数に格納され、パーサーに渡されます。
5.  **ルックアヘッドトークン (`$$char`)**: パーサーが次にどの文法規則を適用するかを決定するために、入力ストリームから1つ先のトークン（ルックアヘッドトークン）を事前に読み込むことがあります。`$$char`はこのルックアヘッドトークンを表す内部変数です。
6.  **クロージャ (Closure)**: Goにおいて、クロージャは、それが定義された関数スコープ外の変数を参照できる関数値です。クロージャ自体はヒープに割り当てられることが多く、そのライフサイクルはガベージコレクタによって管理されます。頻繁に生成・破棄されるクロージャはGCのオーバーヘッドを増加させる可能性があります。
7.  **メモリ割り当て (Heap vs. Stack)**:
    *   **スタック割り当て**: 関数呼び出し時に自動的に確保され、関数終了時に自動的に解放されるメモリ領域です。高速で、GCの対象外です。サイズがコンパイル時に決定できるローカル変数などに使われます。
    *   **ヒープ割り当て**: プログラムの実行中に動的に確保・解放されるメモリ領域です。GCによって管理され、スタック割り当てよりも低速です。サイズが実行時に決定されるデータ構造（スライス、マップ、チャネルなど）や、関数のスコープを超えて存続する必要があるデータに使われます。ヒープ割り当てを減らすことは、GCの負荷を軽減し、パフォーマンスを向上させる一般的な最適化手法です。

## 技術的詳細

このコミットは、`cmd/yacc`が生成するパーサーコード（`yacc.go`）の構造を根本的に変更し、メモリ割り当ての特性を改善しています。

1.  **固定サイズ初期スタックの導入**:
    *   以前は`var stacksize = 200`というグローバル変数が存在し、パーシングスタックは`make([]$$SymType, $$MaxDepth)`のように動的にスライスとしてヒープに割り当てられていました。
    *   変更後、`stacksize`は`initialstacksize = 16`に変わり、`$$ParserImpl`構造体内に`stack [$$InitialStackSize]$$SymType`という固定サイズの配列が追加されました。
    *   `Parse`メソッド内では、`$$S := $$rcvr.stack[:]`として、この構造体内の配列を基にしたスライスが使用されます。これにより、パーサーが作成される際にスタックの初期部分がヒープではなく、`$$ParserImpl`構造体の一部として割り当てられるようになります。これは、小さなパーシングタスクであればヒープ割り当てを完全に回避できることを意味します。もしスタックが`initialstacksize`を超えて成長する必要がある場合、Goのスライスのメカニズムにより、必要に応じてより大きなバッキング配列がヒープに割り当てられますが、多くの場合、初期の固定サイズで十分です。

2.  **`lval`の構造体への埋め込み**:
    *   以前は、`Parse`メソッド内で`var $$lval $$SymType`としてローカル変数として宣言されていました。これはスタックに割り当てられますが、`$$lex1`関数にポインタで渡され、その値が`$$VAL`にコピーされるという流れでした。
    *   変更後、`$$ParserImpl`構造体に`lval $$SymType`フィールドが追加されました。`$$lex1`関数は`&$$rcvr.lval`としてこの構造体フィールドへのポインタを受け取るようになり、`$$VAL`への代入も`$$rcvr.lval`から行われます。これにより、`lval`の管理が一元化され、パーサーの状態の一部として扱われるようになります。

3.  **`$$char`の構造体への埋め込みとクロージャの排除**:
    *   以前は、`$$ParserImpl`構造体には`lookahead func() int`というフィールドがあり、`$$NewParser`で`func() int { return -1 }`というクロージャで初期化され、`Parse`メソッド内で`$$rcvr.lookahead = func() int { return $$char }`という別のクロージャで更新されていました。`Lookahead()`メソッドはこのクロージャを呼び出していました。
    *   変更後、`$$ParserImpl`構造体から`lookahead func() int`フィールドが削除され、代わりに`char int`フィールドが追加されました。
    *   `Lookahead()`メソッドは単に`return p.char`を返すようになり、クロージャの生成と呼び出しが完全に排除されました。
    *   `$$char`というローカル変数はなくなり、パーサー全体で`$$rcvr.char`として構造体フィールドが直接使用されるようになりました。

これらの変更により、パーサーの実行中に発生するヒープ割り当てが大幅に削減され、特に`Lookahead()`のような頻繁に呼び出されるメソッドでのクロージャのオーバーヘッドがなくなります。結果として、パーサーのメモリフットプリントが小さくなり、GCの実行回数が減り、全体的なパフォーマンスが向上します。

## コアとなるコードの解説

このコミットの核心は、`$$ParserImpl`構造体の再設計と、それに伴うパーシングロジックの変更です。

1.  **`$$ParserImpl`構造体の変更**:
    *   以前は、`lookahead func() int`というクロージャを保持するフィールドがありましたが、これは動的なメモリ割り当てを伴う可能性がありました。
    *   新しい構造体では、`lval $$SymType`、`stack [$$InitialStackSize]$$SymType`、`char int`が直接埋め込まれています。
        *   `lval`は、字句解析器から受け取ったトークンの意味値を保持します。これが構造体の一部となることで、ヒープ割り当てが不要になります。
        *   `stack`は、パーシングスタックの初期部分を保持する固定サイズの配列です。これにより、小さなパーシングタスクではヒープ割り当てを回避し、スタック割り当ての恩恵を受けられます。
        *   `char`は、ルックアヘッドトークンを直接保持する整数フィールドです。これにより、`Lookahead()`メソッドでクロージャを使用する必要がなくなり、その分のオーバーヘッドが削減されます。

2.  **`Lookahead()`メソッドの簡素化**:
    *   以前は、`p.lookahead()`というクロージャ呼び出しを通じてルックアヘッドトークンを取得していましたが、これは間接的な呼び出しであり、クロージャのオーバーヘッドがありました。
    *   変更後は、`return p.char`と直接構造体フィールドの値を返すようになり、非常に効率的になりました。

3.  **`$$NewParser()`での初期化の簡素化**:
    *   以前は、`lookahead`フィールドを初期化するためにクロージャを生成していましたが、これが不要になりました。
    *   `return &$$ParserImpl{}`だけで構造体のゼロ値が返され、必要なフィールドは後続のパーシングプロセスで適切に設定されます。

4.  **`Parse()`メソッド内のメモリ管理の変更**:
    *   パーシングスタックの初期化が`make([]$$SymType, $$MaxDepth)`から`$$S := $$rcvr.stack[:]`に変更されたことで、スタックのバッキング配列が`$$ParserImpl`構造体の一部として確保されるようになりました。
    *   `$$char`と`$$lval`へのアクセスが、ローカル変数から`$$rcvr.char`と`$$rcvr.lval`という構造体フィールドへの直接アクセスに変わりました。これにより、これらの値の管理が構造体内部に統合され、ヒープ割り当てやクロージャを介した間接的なアクセスが排除されました。

これらの変更は、`cmd/yacc`が生成するパーサーの実行効率を向上させ、特にリソースが限られた環境や、パーサーが頻繁に呼び出されるようなアプリケーションにおいて、顕著なパフォーマンス改善をもたらす可能性があります。

# [インデックス 2790] ファイルの概要

このコミットは、Go言語のランタイムにおける`codeBuf`型に存在するバグを修正するものです。具体的には、`codeBuf`に命令（`instr func(*vm)`）を追加したり、その内容を取得したりするメソッドが、誤って値レシーバで定義されていたため、バッファへの変更が永続化されないという問題が解決されました。この修正により、`codeBuf`が意図した通りに機能し、仮想マシン（`vm`）の命令を正しく格納・管理できるようになります。

## 変更の背景

このコミットの背景には、`codeBuf`というデータ構造がその設計意図通りに機能していなかったという重大なバグが存在していました。コミットメッセージにある「Fix bug where nothing could ever be added to a code buffer.」（コードバッファに何も追加できないバグを修正）という記述が示す通り、このバッファは命令を格納するために使用されるにもかかわらず、実際には命令を一切追加できない状態でした。

`codeBuf`は、おそらくGo言語の初期の仮想マシン（`vm`）や評価器（`eval`）の一部として、実行される命令のシーケンスを動的に構築するために設計されたものと推測されます。このようなバッファが機能しないということは、命令の生成や実行が不可能であり、関連するシステム全体が動作しないことを意味します。

このバグは、Go言語のメソッドレシーバの基本的な理解、特に値レシーバとポインタレシーバの違いに関する誤用が原因でした。メソッドがレシーバの内部状態を変更する必要がある場合、ポインタレシーバを使用しなければ、その変更は元のインスタンスには反映されません。このコミットは、この根本的な問題を修正し、`codeBuf`が命令を正しく受け入れ、管理できるようにすることで、システムの安定性と機能性を回復させました。

## 前提知識の解説

### Go言語のメソッドレシーバ（値レシーバ vs ポインタレシーバ）

Go言語では、構造体に対してメソッドを定義する際に、レシーバを「値」または「ポインタ」として指定できます。この選択は、メソッドがレシーバのインスタンスにどのようにアクセスし、変更を反映させるかに大きな影響を与えます。

*   **値レシーバ (`func (b Type) Method(...)`)**:
    メソッドが呼び出されると、レシーバのインスタンスの**コピー**がメソッドに渡されます。メソッド内でレシーバのフィールドを変更しても、それはコピーに対する変更であり、元のインスタンスには影響しません。これは、メソッドがレシーバのデータを読み取るだけで、変更しない場合に適しています。

*   **ポインタレシーバ (`func (b *Type) Method(...)`)**:
    メソッドが呼び出されると、レシーバのインスタンスへの**ポインタ**がメソッドに渡されます。メソッド内でポインタを介してレシーバのフィールドを変更すると、その変更は元のインスタンスに直接反映されます。これは、メソッドがレシーバの内部状態を変更する必要がある場合に必須です。

今回のバグは、`codeBuf`の`push`メソッドが`codeBuf`の内部状態（`instrs`スライス）を変更する必要があるにもかかわらず、値レシーバで定義されていたために発生しました。

### Go言語のスライスと`append`の動作

Go言語のスライスは、可変長シーケンスを扱うための強力なデータ型です。スライスは、基盤となる配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。

*   **`len`**: スライスに含まれる要素の数。
*   **`cap`**: スライスの基盤となる配列が保持できる要素の最大数。

`append`関数は、スライスに要素を追加するために使用されます。`append`の重要な特性は以下の通りです。

1.  **容量が十分な場合**: スライスの容量に余裕がある場合、`append`は既存の基盤配列の空きスペースに要素を追加し、新しいスライスヘッダ（長さが更新されたもの）を返します。この場合、基盤配列は変更されません。
2.  **容量が不足する場合**: スライスの容量が不足している場合、`append`はより大きな新しい基盤配列を割り当て、既存の要素を新しい配列にコピーし、新しい要素を追加します。そして、新しい基盤配列を参照する新しいスライスヘッダを返します。

今回の`codeBuf`の`push`メソッドでは、`append`を直接使用しているわけではありませんが、`n >= cap(b.instrs)`の条件で新しいスライスを割り当ててコピーするロジックが含まれています。このロジックが値レシーバのメソッド内で実行されると、新しいスライスが割り当てられても、それはメソッドに渡された`codeBuf`の**コピー**の`instrs`フィールドにのみ反映され、元の`codeBuf`インスタンスの`instrs`は更新されません。

### `codeBuf`と`vm`の役割（推測）

コミットのファイルパス（`usr/austin/eval/func.go`）とコードの内容から、`codeBuf`はGo言語の初期の実験的な評価器（`eval`）または仮想マシン（`vm`）の一部であると推測されます。

*   **`codeBuf`**: 仮想マシンが実行する命令（`instr func(*vm)`）を一時的に格納・構築するためのバッファ。`push`メソッドで命令を追加し、`get`メソッドで最終的な命令シーケンスを取得する役割を担います。
*   **`instr func(*vm)`**: 仮想マシン（`vm`）のインスタンスを引数にとる関数型の命令。これは、Go言語の関数を直接命令として扱うことで、柔軟な命令セットを構築しようとしていた可能性を示唆しています。
*   **`vm`**: 仮想マシンまたは評価器のインスタンス。`instr`がこの`vm`の状態を変更したり、`vm`の機能を利用したりすると考えられます。

この文脈において、`codeBuf`が命令を正しく格納できないことは、仮想マシンが命令を実行できないことを意味し、システム全体の機能不全に直結します。

## 技術的詳細

このコミットの技術的な核心は、Go言語のメソッドレシーバの型を値レシーバからポインタレシーバに変更した点にあります。

変更前の`codeBuf`の`push`メソッドと`get`メソッドは、以下のように値レシーバで定義されていました。

```go
func (b codeBuf) push(instr func(*vm)) { ... }
func (b codeBuf) get() code { ... }
```

ここで、`b codeBuf`は`codeBuf`型の値レシーバを意味します。Go言語では、メソッドが値レシーバを持つ場合、メソッドが呼び出される際にレシーバのインスタンスの**コピー**が作成され、そのコピーがメソッドの内部で使用されます。

`push`メソッドの内部では、`b.instrs`というスライスに命令を追加する操作が行われています。特に、スライスの容量が不足した場合（`if n >= cap(b.instrs)`）、新しい基盤配列が割り当てられ、既存の要素がコピーされ、`b.instrs`が新しいスライスヘッダを指すように更新されます。

```go
	if n >= cap(b.instrs) {
		a := make(code, n, n*2);
		for i := range b.instrs {
			a[i] = b.instrs[i];
		}
		b.instrs = a; // ここでb.instrsが更新される
	}
```

しかし、`b`が値レシーバであるため、この`b.instrs = a;`という代入は、メソッドに渡された`codeBuf`の**コピー**の`instrs`フィールドを更新するに過ぎません。メソッドの呼び出し元が持っている元の`codeBuf`インスタンスの`instrs`フィールドは一切変更されません。結果として、`push`メソッドが何度呼び出されても、元の`codeBuf`には命令が追加されることはなく、「何も追加できない」というバグが発生していました。

同様に、`get`メソッドも値レシーバで定義されていましたが、このメソッドは`codeBuf`の内部状態を変更するわけではないため、機能的なバグには直結しませんでした。しかし、一貫性と将来的な変更の可能性を考慮し、`push`メソッドと同様にポインタレシーバに変更されました。

このコミットでは、これらのメソッドのレシーバをポインタレシーバに変更しました。

```go
func (b *codeBuf) push(instr func(*vm)) { ... }
func (b *codeBuf) get() code { ... }
```

`b *codeBuf`は`codeBuf`型へのポインタレシーバを意味します。これにより、メソッドが呼び出されると、元の`codeBuf`インスタンスへのポインタが渡されます。`push`メソッド内で`b.instrs`が更新される際、それはポインタを介して元の`codeBuf`インスタンスの`instrs`フィールドを直接変更するため、変更が永続化されるようになります。これにより、`codeBuf`に命令が正しく追加され、バッファが意図した通りに機能するようになりました。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、`codeBuf`型の`push`メソッドと`get`メソッドのレシーバの型を、値レシーバ（`codeBuf`）からポインタレシーバ（`*codeBuf`）へ変更した点です。

1.  **`func (b codeBuf) push(instr func(*vm))` から `func (b *codeBuf) push(instr func(*vm))` への変更**:
    *   **変更前**: `push`メソッドは`codeBuf`の**値**をレシーバとして受け取っていました。これは、メソッド内で`b`に対して行われるすべての操作（特に`b.instrs`スライスへの要素追加や、容量不足時の新しい基盤配列への再割り当て）が、元の`codeBuf`インスタンスのコピーに対して行われることを意味します。したがって、メソッドが終了しても、呼び出し元の`codeBuf`インスタンスの`instrs`スライスは変更されず、命令が実際には追加されないというバグが発生していました。
    *   **変更後**: `push`メソッドは`codeBuf`への**ポインタ**をレシーバとして受け取るようになりました。これにより、メソッド内で`b`を介して`b.instrs`スライスを変更する操作は、元の`codeBuf`インスタンスの`instrs`スライスに直接作用します。結果として、命令が正しく`codeBuf`に追加され、その変更が永続化されるようになりました。

2.  **`func (b codeBuf) get() code` から `func (b *codeBuf) get() code` への変更**:
    *   `get`メソッドは`codeBuf`の内部状態を変更するわけではありませんが、`push`メソッドと同様に値レシーバからポインタレシーバに変更されました。これは、`codeBuf`のメソッド定義における一貫性を保つため、および将来的に`get`メソッドが内部状態にアクセスしたり、より複雑な操作を行ったりする可能性を考慮した変更と考えられます。ポインタレシーバを使用することで、メソッドが常に元のインスタンスにアクセスできることが保証されます。

このシンプルなレシーバの変更により、`codeBuf`は命令を正しく格納・管理できるようになり、Go言語の仮想マシンまたは評価器の基本的な機能が回復しました。これは、Go言語におけるポインタと値のセマンティクス、特にメソッドレシーバの選択の重要性を示す典型的な例です。

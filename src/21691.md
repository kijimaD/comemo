# [インデックス 21691] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の効率を改善することを目的としています。特に、コンカレントGC中にゴルーチンのスタックを不必要に再スキャンするのを避けるための最適化が導入されています。これにより、GCのオーバーヘッドが削減され、アプリケーションのパフォーマンスが向上する可能性があります。

## 元コミット内容

runtime: avoid redundant scans

During a concurrent GC stacks are scanned in
an initial scan phase informing the GC of all
pointers on the stack. The GC only needs to rescan
the stack if it potentially changes which can only
happen if the goroutine runs.
This CL tracks whether the Goroutine has run
since it was last scanned and thus may have changed
its stack. If necessary the stack is rescanned.

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCプロセスでは、ヒープ上のオブジェクトだけでなく、ゴルーチンのスタックもスキャンして、到達可能なポインタを特定し、マークする必要があります。

従来のGCサイクルでは、コンカレントGCの初期スキャンフェーズでスタックがスキャンされ、スタック上のすべてのポインタがGCに通知されます。しかし、GCがスタックを再スキャンする必要があるのは、そのスタックが変更された可能性がある場合のみです。スタックが変更されるのは、そのゴルーチンが実行された場合のみです。

このコミット以前は、ゴルーチンが最後にスキャンされてから実行されたかどうかに関わらず、不必要にスタックが再スキャンされる可能性がありました。これはGCのオーバーヘッドを増加させ、特に多数のゴルーチンが存在し、その多くが長時間ブロックされているようなシナリオでは、パフォーマンスに悪影響を与える可能性がありました。

この変更の目的は、この冗長なスタックスキャンを排除し、GCの効率を向上させることです。具体的には、ゴルーチンが最後にスキャンされてから実行されたかどうかを追跡するメカニズムを導入し、スタックが変更された可能性がある場合にのみ再スキャンを行うようにします。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしたコンカレント（並行）GCです。これは、アプリケーションの実行とGCのマークフェーズが同時に進行することを意味します。

*   **マークフェーズ**: GCは、ルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを「マーク」します。マークされたオブジェクトは生きていると見なされ、マークされていないオブジェクトは死んでいると見なされます。
*   **スイープフェーズ**: マークされていない死んだオブジェクトがメモリから解放されます。
*   **コンカレントGC**: GoのGCは、ほとんどの作業をアプリケーションの実行と並行して行います。これにより、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、レイテンシを低減します。
*   **STWフェーズ**: コンカレントGCであっても、GCの特定の段階（例えば、マークの開始時や終了時）では、すべてのゴルーチンを一時的に停止させるSTWフェーズが必要です。これは、GCがメモリの状態を一貫して把握し、正確なマークを行うために不可欠です。

### スタックスキャンとポインタの特定

GCは、ヒープ上のオブジェクトだけでなく、ゴルーチンのスタックもスキャンします。スタックには、ローカル変数や関数呼び出しの引数など、ヒープ上のオブジェクトへのポインタが含まれている可能性があります。これらのポインタを正確に特定し、参照先のオブジェクトをマークすることは、GCが到達可能なオブジェクトをすべて見つける上で非常に重要です。

*   **スタックの構造**: Goのゴルーチンスタックは、必要に応じて動的に拡大・縮小します。スタックフレームには、関数呼び出しの情報、ローカル変数、レジスタの値などが含まれます。
*   **ポインタの識別**: GCは、スタック上のどのメモリ領域がポインタであるかを識別する必要があります。これは、コンパイラが生成する情報（スタックマップなど）に基づいて行われます。

### Goroutineの状態

Goのゴルーチンは、そのライフサイクルにおいて様々な状態を取ります。`runtime/proc.go`や`runtime/runtime2.go`で定義されている`g`構造体の`status`フィールドがこれらの状態を管理します。

*   `_Grunning`: ゴルーチンが現在CPU上で実行中である状態。
*   `_Gidle`: ゴルーチンが実行されておらず、スケジューリングの準備ができていない状態。
*   `_Grunnable`: ゴルーチンが実行可能であり、スケジューラによって実行されるのを待っている状態。
*   `_Gsyscall`: ゴルーチンがシステムコールを実行中である状態。
*   `_Gwaiting`: ゴルーチンがイベント（チャネル操作、ロックなど）を待っている状態。
*   `_Gscan`: GCがゴルーチンのスタックをスキャンしている状態。

このコミットでは、特に`_Grunning`状態が重要になります。ゴルーチンが`_Grunning`状態になると、そのスタックの内容が変更される可能性があるため、GCはスタックの再スキャンが必要かどうかを判断する必要があります。

## 技術的詳細

このコミットの核心は、`g`（ゴルーチン）構造体に`gcscanvalid`という新しいフィールドを追加し、これを利用してスタックの冗長なスキャンを回避することです。

### `g.gcscanvalid`フィールドの導入

`src/runtime/runtime2.go`の`g`構造体に以下のフィールドが追加されました。

```go
type g struct {
    // ... 既存のフィールド ...
    gcscanvalid  bool // false at start of gc cycle, true if G has not run since last scan
    // ... その他のフィールド ...
}
```

*   `gcscanvalid`はブーリアン値で、GCサイクル開始時に`false`に設定されます。
*   このフィールドが`true`の場合、そのゴルーチンのスタックは最後にスキャンされてから変更されていない（つまり、ゴルーチンが実行されていない）ことを示します。
*   `false`の場合、スタックが変更された可能性があるため、再スキャンが必要です。

### `gcscanvalid`のライフサイクルと利用

1.  **GCサイクル開始時**:
    *   `src/runtime/malloc.go`の`gcwork`関数（非コンカレントGCの場合）と`src/runtime/mgc.go`の`gcscan_m`関数（コンカレントGCのマークフェーズ開始時）で、すべてのゴルーチン（`allgs`）の`gp.gcscanvalid`が`false`にリセットされます。これは、新しいGCサイクルが始まるにあたり、すべてのスタックが「未検証」の状態に戻ることを意味します。

2.  **スタックスキャン時 (`scanstack`)**:
    *   `src/runtime/mgc.go`の`scanstack(gp *g)`関数は、特定のゴルーチン`gp`のスタックをスキャンする役割を担います。
    *   この関数は、最初に`if gp.gcscanvalid { return }`というチェックを行います。もし`gcscanvalid`が`true`であれば、スタックは既に有効な状態であるため、冗長なスキャンをスキップしてすぐにリターンします。
    *   スタックが実際にスキャンされた後、`gp.gcscanvalid = true`が設定されます。これは、この時点でのスタックの内容がGCによって把握され、有効であるとマークされたことを意味します。

3.  **ゴルーチンが実行状態に遷移する時 (`casfrom_Gscanstatus`, `casgstatus`)**:
    *   `src/runtime/proc1.go`の`casfrom_Gscanstatus`と`casgstatus`関数は、ゴルーチンの状態遷移を管理します。
    *   特に、ゴルーチンが`_Grunning`状態に遷移する際（`newval == _Grunning`）、`gp.gcscanvalid = false`が設定されます。これは、ゴルーチンが実行されることでスタックの内容が変更される可能性があるため、以前のスタックスキャン結果は無効になることを示します。次のGCスキャン時には、このスタックは再スキャンされる必要があります。

4.  **GC作業フェーズ (`gcphasework`)**:
    *   `src/runtime/mgc.go`の`gcphasework`関数は、GCの各フェーズでゴルーチンに対して実行される作業を定義します。
    *   `_GCscan`フェーズでは、`scanstack(gp)`が呼び出されます。この際、`gcscanvalid`が`true`に設定されることで、スキャンが完了したことが示されます。

### `shrinkstack`の変更

*   `src/runtime/mgc.go`の`markroot`関数内で、スタックの縮小（`shrinkstack`）が行われるタイミングが変更されました。
*   以前は`gcphase != _GCscan`の場合に縮小が行われていましたが、この変更により`gcphase == _GCmarktermination`（STWのマーク終了フェーズ）でのみ縮小が行われるようになりました。
*   これは、非STWフェーズでのスタック縮小による複雑さを回避し、GCの正確性を保つための調整です。

これらの変更により、GCはゴルーチンのスタックが実際に変更された場合にのみ再スキャンを行うようになり、GCの効率が向上します。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

*   **`g` 構造体への `gcscanvalid` フィールドの追加**:
    *   この変更の基盤となる部分です。`g`構造体はGoのゴルーチンを表し、その状態や関連情報が格納されています。
    *   `gcscanvalid`は、そのゴルーチンのスタックが最後にGCによってスキャンされてから、ゴルーチンが実行されていない（したがってスタックの内容が変更されていない）場合に`true`となるフラグです。GCサイクル開始時には`false`にリセットされます。

### `src/runtime/malloc.go`

*   **`gcwork` 関数内の `gcscanvalid` の初期化**:
    *   `gcwork`関数は、GCの主要な作業を調整する関数の一つです。
    *   非コンカレントGC（`force != 0`）の場合のパスに、すべてのゴルーチン（`allgs`）に対して`gp.gcscanvalid = false`を設定するループが追加されました。
    *   これは、GCがSTW（Stop-The-World）フェーズにあるため、競合状態を心配することなく、すべてのスタックが新しいGCサイクルで再検証される必要があることを示します。

### `src/runtime/mgc.go`

*   **`markroot` 関数内の `shrinkstack` のタイミング変更**:
    *   `markroot`はGCルートをマークする関数です。この中で、スタックの縮小を行う`shrinkstack`の呼び出し条件が変更されました。
    *   以前は`gcphase != _GCscan`（スキャンフェーズ以外）で縮小が行われていましたが、`gcphase == _GCmarktermination`（STWのマーク終了フェーズ）に限定されました。
    *   これにより、コンカレントなフェーズでのスタック縮小による複雑な問題を回避し、GCの正確性と安定性を向上させています。

*   **`scanstack` 関数での冗長スキャン回避ロジック**:
    *   `scanstack(gp *g)`は、指定されたゴルーチン`gp`のスタックをスキャンする関数です。
    *   この関数に`if gp.gcscanvalid { return }`というガード句が追加されました。これにより、もし`gcscanvalid`が`true`であれば、スタックは既に有効な状態であると判断され、実際のスタック内容のスキャン処理がスキップされます。
    *   スタックが実際にスキャンされた後、`gp.gcscanvalid = true`が設定され、このスタックが現在有効であるとマークされます。

*   **`gcphasework` 関数での `gcscanvalid` の設定**:
    *   `gcphasework`は、GCの各フェーズでゴルーチンに対して行われる作業を定義します。
    *   `_GCscan`フェーズにおいて`scanstack(gp)`が呼び出された後、コメントが追加され、スキャンが有効であることを示し、ゴルーチンが再度実行されるまで有効であることが示唆されています。`scanstack`内で`gcscanvalid`が`true`に設定されるため、ここでの変更はコメントの追加のみですが、`scanstack`の動作と密接に関連しています。

*   **`gcscan_m` 関数での `gcscanvalid` の初期化**:
    *   `gcscan_m`は、コンカレントGCのマークフェーズ開始時に呼び出される関数です。
    *   `malloc.go`と同様に、すべてのゴルーチンに対して`gp.gcscanvalid = false`が設定されます。これは、新しいGCサイクルが始まるにあたり、すべてのスタックが再検証される必要があることを示します。

### `src/runtime/proc1.go`

*   **ゴルーチン状態遷移時の `gcscanvalid` のリセット**:
    *   `casfrom_Gscanstatus`、`castogscanstatus`、`casgstatus`といった関数は、ゴルーチンの状態（`g.atomicstatus`）をアトミックに更新する役割を担います。
    *   これらの関数内で、ゴルーチンが`_Grunning`状態（実行中）に遷移する際（`newval == _Grunning`）、`gp.gcscanvalid = false`が設定されるようになりました。
    *   これは非常に重要です。ゴルーチンが実行されると、そのスタックの内容が変更される可能性があるため、以前のスタックスキャン結果は無効になります。したがって、次にGCがスタックをスキャンする際には、必ず再スキャンが必要であることを`gcscanvalid = false`で示します。
    *   `castogscanstatus`には、`_Grunning`状態への遷移時に`gcscanvalid`が`true`である場合に`throw`するデバッグ用のチェックも追加されています。これは、論理的な矛盾を早期に検出するためのものです。

これらの変更が連携することで、GoランタイムはGC中にゴルーチンのスタックをより効率的に管理し、不必要なスキャンを削減することで、GCのパフォーマンスを向上させています。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCプロセスでは、ヒープ上のオブジェクトだけでなく、ゴルーチンのスタックもスキャンして、到達可能なポインタを特定し、マークする必要があります。

従来のGCサイクルでは、コンカレントGCの初期スキャンフェーズでスタックがスキャンされ、スタック上のすべてのポインタがGCに通知されます。しかし、GCがスタックを再スキャンする必要があるのは、そのスタックが変更された可能性がある場合のみです。スタックが変更されるのは、そのゴルーチンが実行された場合のみです。

このコミット以前は、ゴルーチンが最後にスキャンされてから実行されたかどうかに関わらず、不必要にスタックが再スキャンされる可能性がありました。これはGCのオーバーヘッドを増加させ、特に多数のゴルーチンが存在し、その多くが長時間ブロックされているようなシナリオでは、パフォーマンスに悪影響を与える可能性がありました。

この変更の目的は、この冗長なスタックスキャンを排除し、GCの効率を向上させることです。具体的には、ゴルーチンが最後にスキャンされてから実行されたかどうかを追跡するメカニズムを導入し、スタックが変更された可能性がある場合にのみ再スキャンを行うようにします。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしたコンカレント（並行）GCです。これは、アプリケーションの実行とGCのマークフェーズが同時に進行することを意味します。

*   **マークフェーズ**: GCは、ルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを「マーク」します。マークされたオブジェクトは生きていると見なされ、マークされていないオブジェクトは死んでいると見なされます。
*   **スイープフェーズ**: マークされていない死んだオブジェクトがメモリから解放されます。
*   **コンカレントGC**: GoのGCは、ほとんどの作業をアプリケーションの実行と並行して行います。これにより、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、レイテンシを低減します。
*   **STWフェーズ**: コンカレントGCであっても、GCの特定の段階（例えば、マークの開始時や終了時）では、すべてのゴルーチンを一時的に停止させるSTWフェーズが必要です。これは、GCがメモリの状態を一貫して把握し、正確なマークを行うために不可欠です。

### スタックスキャンとポインタの特定

GCは、ヒープ上のオブジェクトだけでなく、ゴルーチンのスタックもスキャンします。スタックには、ローカル変数や関数呼び出しの引数など、ヒープ上のオブジェクトへのポインタが含まれている可能性があります。これらのポインタを正確に特定し、参照先のオブジェクトをマークすることは、GCが到達可能なオブジェクトをすべて見つける上で非常に重要です。

*   **スタックの構造**: Goのゴルーチンスタックは、必要に応じて動的に拡大・縮小します。スタックフレームには、関数呼び出しの情報、ローカル変数、レジスタの値などが含まれます。
*   **ポインタの識別**: GCは、スタック上のどのメモリ領域がポインタであるかを識別する必要があります。これは、コンパイラが生成する情報（スタックマップなど）に基づいて行われます。

### Goroutineの状態

Goのゴルーチンは、そのライフサイクルにおいて様々な状態を取ります。`runtime/proc.go`や`runtime/runtime2.go`で定義されている`g`構造体の`status`フィールドがこれらの状態を管理します。

*   `_Grunning`: ゴルーチンが現在CPU上で実行中である状態。
*   `_Gidle`: ゴルーチンが実行されておらず、スケジューリングの準備ができていない状態。
*   `_Grunnable`: ゴルーチンが実行可能であり、スケジューラによって実行されるのを待っている状態。
*   `_Gsyscall`: ゴルーチンがシステムコールを実行中である状態。
*   `_Gwaiting`: ゴルーチンがイベント（チャネル操作、ロックなど）を待っている状態。
*   `_Gscan`: GCがゴルーチンのスタックをスキャンしている状態。

このコミットでは、特に`_Grunning`状態が重要になります。ゴルーチンが`_Grunning`状態になると、そのスタックの内容が変更される可能性があるため、GCはスタックの再スキャンが必要かどうかを判断する必要があります。

## 技術的詳細

このコミットの核心は、`g`（ゴルーチン）構造体に`gcscanvalid`という新しいフィールドを追加し、これを利用してスタックの冗長なスキャンを回避することです。

### `g.gcscanvalid`フィールドの導入

`src/runtime/runtime2.go`の`g`構造体に以下のフィールドが追加されました。

```go
type g struct {
    // ... 既存のフィールド ...
    gcscanvalid  bool // false at start of gc cycle, true if G has not run since last scan
    // ... その他のフィールド ...
}
```

*   `gcscanvalid`はブーリアン値で、GCサイクル開始時に`false`に設定されます。
*   このフィールドが`true`の場合、そのゴルーチンのスタックは最後にスキャンされてから変更されていない（つまり、ゴルーチンが実行されていない）ことを示します。
*   `false`の場合、スタックが変更された可能性があるため、再スキャンが必要です。

### `gcscanvalid`のライフサイクルと利用

1.  **GCサイクル開始時**:
    *   `src/runtime/malloc.go`の`gcwork`関数（非コンカレントGCの場合）と`src/runtime/mgc.go`の`gcscan_m`関数（コンカレントGCのマークフェーズ開始時）で、すべてのゴルーチン（`allgs`）の`gp.gcscanvalid`が`false`にリセットされます。これは、新しいGCサイクルが始まるにあたり、すべてのスタックが「未検証」の状態に戻ることを意味します。

2.  **スタックスキャン時 (`scanstack`)**:
    *   `src/runtime/mgc.go`の`scanstack(gp *g)`関数は、特定のゴルーチン`gp`のスタックをスキャンする役割を担います。
    *   この関数は、最初に`if gp.gcscanvalid { return }`というチェックを行います。もし`gcscanvalid`が`true`であれば、スタックは既に有効な状態であるため、冗長なスキャンをスキップしてすぐにリターンします。
    *   スタックが実際にスキャンされた後、`gp.gcscanvalid = true`が設定されます。これは、この時点でのスタックの内容がGCによって把握され、有効であるとマークされたことを意味します。

3.  **ゴルーチンが実行状態に遷移する時 (`casfrom_Gscanstatus`, `casgstatus`)**:
    *   `src/runtime/proc1.go`の`casfrom_Gscanstatus`と`casgstatus`関数は、ゴルーチンの状態遷移を管理します。
    *   特に、ゴルーチンが`_Grunning`状態に遷移する際（`newval == _Grunning`）、`gp.gcscanvalid = false`が設定されます。これは、ゴルーチンが実行されることでスタックの内容が変更される可能性があるため、以前のスタックスキャン結果は無効になることを示します。次のGCスキャン時には、このスタックは再スキャンされる必要があります。

4.  **GC作業フェーズ (`gcphasework`)**:
    *   `src/runtime/mgc.go`の`gcphasework`関数は、GCの各フェーズでゴルーチンに対して実行される作業を定義します。
    *   `_GCscan`フェーズでは、`scanstack(gp)`が呼び出されます。この際、`gcscanvalid`が`true`に設定されることで、スキャンが完了したことが示されます。

### `shrinkstack`の変更

*   `src/runtime/mgc.go`の`markroot`関数内で、スタックの縮小（`shrinkstack`）が行われるタイミングが変更されました。
*   以前は`gcphase != _GCscan`の場合に縮小が行われていましたが、この変更により`gcphase == _GCmarktermination`（STWのマーク終了フェーズ）でのみ縮小が行われるようになりました。
*   これは、非STWフェーズでのスタック縮小による複雑さを回避し、GCの正確性を保つための調整です。

これらの変更により、GCはゴルーチンのスタックが実際に変更された場合にのみ再スキャンを行うようになり、GCの効率が向上します。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

*   **`g` 構造体への `gcscanvalid` フィールドの追加**:
    *   この変更の基盤となる部分です。`g`構造体はGoのゴルーチンを表し、その状態や関連情報が格納されています。
    *   `gcscanvalid`は、そのゴルーチンのスタックが最後にGCによってスキャンされてから、ゴルーチンが実行されていない（したがってスタックの内容が変更されていない）場合に`true`となるフラグです。GCサイクル開始時には`false`にリセットされます。

### `src/runtime/malloc.go`

*   **`gcwork` 関数内の `gcscanvalid` の初期化**:
    *   `gcwork`関数は、GCの主要な作業を調整する関数の一つです。
    *   非コンカレントGC（`force != 0`）の場合のパスに、すべてのゴルーチン（`allgs`）に対して`gp.gcscanvalid = false`を設定するループが追加されました。
    *   これは、GCがSTW（Stop-The-World）フェーズにあるため、競合状態を心配することなく、すべてのスタックが新しいGCサイクルで再検証される必要があることを示します。

### `src/runtime/mgc.go`

*   **`markroot` 関数内の `shrinkstack` のタイミング変更**:
    *   `markroot`はGCルートをマークする関数です。この中で、スタックの縮小を行う`shrinkstack`の呼び出し条件が変更されました。
    *   以前は`gcphase != _GCscan`（スキャンフェーズ以外）で縮小が行われていましたが、`gcphase == _GCmarktermination`（STWのマーク終了フェーズ）に限定されました。
    *   これにより、コンカレントなフェーズでのスタック縮小による複雑な問題を回避し、GCの正確性と安定性を向上させています。

*   **`scanstack` 関数での冗長スキャン回避ロジック**:
    *   `scanstack(gp *g)`は、指定されたゴルーチン`gp`のスタックをスキャンする関数です。
    *   この関数に`if gp.gcscanvalid { return }`というガード句が追加されました。これにより、もし`gcscanvalid`が`true`であれば、スタックは既に有効な状態であると判断され、実際のスタック内容のスキャン処理がスキップされます。
    *   スタックが実際にスキャンされた後、`gp.gcscanvalid = true`が設定され、このスタックが現在有効であるとマークされます。

*   **`gcphasework` 関数での `gcscanvalid` の設定**:
    *   `gcphasework`は、GCの各フェーズでゴルーチンに対して行われる作業を定義します。
    *   `_GCscan`フェーズにおいて`scanstack(gp)`が呼び出された後、コメントが追加され、スキャンが有効であることを示し、ゴルーチンが再度実行されるまで有効であることが示唆されています。`scanstack`内で`gcscanvalid`が`true`に設定されるため、ここでの変更はコメントの追加のみですが、`scanstack`の動作と密接に関連しています。

*   **`gcscan_m` 関数での `gcscanvalid` の初期化**:
    *   `gcscan_m`は、コンカレントGCのマークフェーズ開始時に呼び出される関数です。
    *   `malloc.go`と同様に、すべてのゴルーチンに対して`gp.gcscanvalid = false`が設定されます。これは、新しいGCサイクルが始まるにあたり、すべてのスタックが再検証される必要があることを示します。

### `src/runtime/proc1.go`

*   **ゴルーチン状態遷移時の `gcscanvalid` のリセット**:
    *   `casfrom_Gscanstatus`、`castogscanstatus`、`casgstatus`といった関数は、ゴルーチンの状態（`g.atomicstatus`）をアトミックに更新する役割を担います。
    *   これらの関数内で、ゴルーチンが`_Grunning`状態（実行中）に遷移する際（`newval == _Grunning`）、`gp.gcscanvalid = false`が設定されるようになりました。
    *   これは非常に重要です。ゴルーチンが実行されると、そのスタックの内容が変更される可能性があるため、以前のスタックスキャン結果は無効になります。したがって、次にGCがスタックをスキャンする際には、必ず再スキャンが必要であることを`gcscanvalid = false`で示します。
    *   `castogscanstatus`には、`_Grunning`状態への遷移時に`gcscanvalid`が`true`である場合に`throw`するデバッグ用のチェックも追加されています。これは、論理的な矛盾を早期に検出するためのものです。

これらの変更が連携することで、GoランタイムはGC中にゴルーチンのスタックをより効率的に管理し、不必要なスキャンを削減することで、GCのパフォーマンスを向上させています。

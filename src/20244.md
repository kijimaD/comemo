# [インデックス 20244] ファイルの概要

## コミット
このコミットは、GoランタイムにおけるWindowsシグナルハンドラの不具合を修正するものです。具体的には、シグナルハンドラからの戻り値がWindowsが期待する`AX`レジスタに正しく設定されない問題を解決します。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/c548cc2ec8c5c83ba16ab92c1cf8bcc3320ba624](https://github.com/golang/go/commit/c548cc2ec8c5c83ba16ab92c1cf8bcc3320ba624)

## 元コミット内容
```
runtime: fix windows signal handlers

Windows needs the return result in AX, but runtime.sighandler
no longer stores it in AX. Load it back during the assembly trampoline.

TBR=brainman
CC=golang-codereviews
https://golang.org/cl/133980043
```

## 変更の背景
Goランタイムは、オペレーティングシステムからのシグナル（例えば、プログラムの異常終了、割り込みなど）を処理するために、OS固有のシグナルハンドラを設定します。Windows環境では、シグナルハンドラが処理を終えた後、特定の戻り値（シグナルが処理されたか否かを示す）を`AX`レジスタ（x86アーキテクチャにおけるアキュムレータレジスタ）に格納してOSに返すことが期待されます。

このコミット以前のGoランタイムでは、`runtime.sighandler`というGo言語で実装されたシグナルハンドラが、その戻り値を`AX`レジスタに直接格納しなくなっていました。これは、おそらくランタイム内部の変更（例えば、レジスタの使用方法の最適化や、スタックフレームのレイアウト変更など）によって引き起こされたものと考えられます。結果として、Windowsはシグナルハンドラからの正しい戻り値を受け取ることができず、シグナル処理が期待通りに行われない、あるいはシステムが不安定になる可能性がありました。

この問題は、特にWindows上でのGoプログラムの安定性や、シグナルベースのデバッグ、あるいは特定のシステムコールとの連携において影響を及ぼす可能性がありました。このコミットは、このWindows固有のABI（Application Binary Interface）要件を満たすために導入されました。

## 前提知識の解説

### 1. シグナルハンドラ (Signal Handler)
シグナルハンドラは、オペレーティングシステムがプロセスに送信する非同期イベント（シグナル）を捕捉し、処理するための特別な関数です。シグナルには、プログラムの異常終了（例: ゼロ除算、不正なメモリアクセス）、ユーザーからの割り込み（Ctrl+C）、タイマーイベントなど、様々な種類があります。シグナルハンドラは、これらのイベントが発生した際に、プログラムが適切に対応できるようにするために不可欠です。

### 2. アセンブリ言語 (Assembly Language)
アセンブリ言語は、CPUが直接実行できる機械語と1対1に対応する低レベルのプログラミング言語です。レジスタの操作、メモリへの直接アクセス、ジャンプ命令など、ハードウェアに近い操作を記述します。Goランタイムのような低レベルのシステムプログラミングでは、OSとのインターフェースやパフォーマンスが重要な部分でアセンブリ言語が使用されます。

### 3. レジスタ (Registers)
レジスタは、CPU内部にある高速な記憶領域です。CPUは、演算を行う際にデータをメモリからレジスタに読み込み、処理結果をレジスタに書き込みます。`AX` (Accumulator Register) は、x86アーキテクチャにおいて、算術演算の結果や関数の戻り値を格納するためによく使われる汎用レジスタです。`BX`, `BP`, `SI`, `DI`, `R12`, `R13`, `R14`, `R15`なども汎用レジスタやポインタレジスタであり、データの保持やメモリアドレスの計算に用いられます。

### 4. スタック (Stack)
スタックは、プログラムが関数呼び出しを行う際に、ローカル変数、関数の引数、戻りアドレス、およびレジスタの退避領域として使用するメモリ領域です。スタックはLIFO（Last-In, First-Out）の原則で動作します。`SP` (Stack Pointer) レジスタは、スタックの現在のトップを指します。`SUBL $X, SP` や `SUBQ $X, SP` は、スタックポインタからXバイトを減算することで、スタック上にXバイトの領域を確保する操作です。`ADDL $X, SP` や `ADDQ $X, SP` は、スタックポインタにXバイトを加算することで、確保した領域を解放する操作です。

### 5. ABI (Application Binary Interface)
ABIは、オペレーティングシステムとアプリケーション、または異なるモジュール間でバイナリレベルでの互換性を保証するための規約です。これには、関数呼び出し規約（引数の渡し方、戻り値の格納場所）、レジスタの使用規約、スタックフレームのレイアウトなどが含まれます。WindowsのようなOSは、シグナルハンドラからの戻り値が特定のレジスタ（この場合は`AX`）に格納されることをABIとして要求します。

### 6. アセンブリトランポリン (Assembly Trampoline)
トランポリンとは、ある関数を呼び出す前に、追加の処理（例えば、レジスタの保存・復元、スタックの調整、引数の変換など）を行うための中間的なアセンブリコードの断片を指します。このコミットでは、Goの`runtime.sighandler`が呼び出された後、Windowsが期待する形式で戻り値を`AX`レジスタに設定するために、このアセンブリトランポリンが利用されています。

## 技術的詳細
このコミットの核心は、WindowsのシグナルハンドリングにおけるABI要件と、Goランタイムの内部実装の間の不整合を解消することにあります。

Windowsでは、シグナルハンドラ（より正確には、例外ハンドラ）が実行された後、その結果を`AX`レジスタに格納して呼び出し元（OSの例外ディスパッチャ）に返す必要があります。この戻り値は、シグナルが処理されたか（-1）、それとも未処理であるか（0）を示します。

Goランタイムの`runtime.sighandler`関数は、Go言語で記述されており、シグナル処理のロジックをカプセル化しています。しかし、この関数が実行された後、その戻り値が自動的に`AX`レジスタに格納されるわけではありませんでした。これは、Goのコンパイラやランタイムが、WindowsのシグナルハンドラABIとは異なる内部的な呼び出し規約やレジスタ使用規約を持っているためです。

このコミットは、`runtime.sighandler`が呼び出されるアセンブリコードの「トランポリン」部分に修正を加えることで、この問題を解決します。具体的には、`runtime.sighandler`が戻り値をスタック上の特定のオフセットに格納していることを前提とし、そのスタック上の値を明示的に`AX`レジスタにロードする命令を追加しています。

また、スタックフレームのサイズが変更されています。
- `sys_windows_386.s` (32-bit): スタック確保サイズが`28`バイトから`32`バイトに増加 (`SUBL $28, SP` -> `SUBL $32, SP`)。
- `sys_windows_amd64.s` (64-bit): スタック確保サイズが`88`バイトから`96`バイトに増加 (`SUBQ $88, SP` -> `SUBQ $96, SP`)。

このスタックサイズの変更は、レジスタの退避領域の再配置や、将来的な拡張のためのパディング、あるいはスタックアライメントの要件を満たすためである可能性があります。スタックサイズが増加したことに伴い、退避されたレジスタ（`BX`, `R15`など）をスタックから読み書きする際のオフセットも調整されています。例えば、32-bit版では`BX`の保存先が`12(SP)`から`28(SP)`に、64-bit版では`R15`の保存先が`24(SP)`から`88(SP)`に変更されています。

最も重要な変更は、`runtime.sighandler`の呼び出し後に追加された`MOVL 12(SP), AX` (32-bit) および `MOVL 24(SP), AX` (64-bit) です。これは、`runtime.sighandler`がスタック上の特定のオフセット（32-bitでは`12(SP)`、64-bitでは`24(SP)`）に格納した戻り値を、Windowsが期待する`AX`レジスタにコピーする役割を果たします。これにより、GoランタイムのシグナルハンドラがWindowsのABIに準拠し、シグナル処理が正しく完了するようになります。

## コアとなるコードの解説

このコミットは、GoランタイムがWindows上でシグナルを処理する際のアセンブリコード（`sigtramp`関数）を修正しています。`sigtramp`は、OSからのシグナルを受け取り、Go言語で書かれた`runtime.sighandler`を呼び出すためのアセンブリトランポリンです。

**主な変更点:**

1.  **スタックフレームサイズの調整:**
    *   32-bit版 (`sys_windows_386.s`): `SUBL $28, SP` が `SUBL $32, SP` に変更されました。これにより、スタック上に確保される領域が4バイト増加しました。
    *   64-bit版 (`sys_windows_amd64.s`): `SUBQ $88, SP` が `SUBQ $96, SP` に変更されました。これにより、スタック上に確保される領域が8バイト増加しました。
    この変更は、レジスタの退避領域の再配置や、スタックアライメントの要件を満たすために行われたと考えられます。

2.  **レジスタ退避/復元オフセットの変更:**
    スタックフレームサイズの変更に伴い、`sigtramp`関数内で退避されるカリィセーブドレジスタ（呼び出し先が保存・復元する責任を持つレジスタ）のスタック上のオフセットが調整されました。
    *   32-bit版では、`BX`レジスタの保存先が`12(SP)`から`28(SP)`に、復元元も同様に変更されています。
    *   64-bit版では、`R15`レジスタの保存先が`24(SP)`から`88(SP)`に、復元元も同様に変更されています。
    これらの変更は、新しいスタックレイアウトに合わせてレジスタの保存場所を正しく指定するためのものです。

3.  **`AX`レジスタへの戻り値のロード (最も重要):**
    `CALL runtime·sighandler(SB)` の直後に、以下の命令が追加されました。
    *   32-bit版: `MOVL 12(SP), AX`
    *   64-bit版: `MOVL 24(SP), AX`
    この命令がこのコミットの核心です。`runtime.sighandler`は、シグナル処理の結果をスタック上の特定のオフセット（32-bitでは`12(SP)`、64-bitでは`24(SP)`）に格納します。しかし、WindowsのABIでは、シグナルハンドラからの戻り値は`AX`レジスタに格納されている必要があります。この追加された`MOVL`命令は、`runtime.sighandler`がスタックに書き込んだ戻り値を、明示的に`AX`レジスタにコピーします。これにより、`sigtramp`関数がWindowsに制御を戻す際に、`AX`レジスタに正しい戻り値が設定されるようになり、Windowsがシグナル処理の結果を正しく解釈できるようになります。

これらの変更により、GoランタイムはWindowsのシグナルハンドリング規約に完全に準拠し、シグナル処理の信頼性と安定性が向上しました。

## 変更の背景
このコミットの主な目的は、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるリライトルールの可読性と保守性を向上させることです。具体的には、以下の点が背景にあります。

1.  **コードの可読性向上**: 長すぎる行を分割し、列を揃えるためのスペースを追加することで、ルール定義ファイル（`.rules`ファイル）と生成されたGoコード（`rewrite*.go`ファイル）が人間にとって読みやすくなります。これは、コンパイラの開発者がこれらのルールを理解し、デバッグし、変更する際の効率を高めます。
2.  **ルールの適用順序の明確化**: AMD64アーキテクチャ向けのリライトルールにおいて、「最適化ルール」を「ローワーリングルール」の後に配置するように順序が変更されました。これは、コンパイラのパスにおけるルールの意図と適用フェーズをより明確にするための構造的な改善です。一般的に、ローワーリングは高レベルの抽象的な操作を低レベルの機械語に近い操作に変換するプロセスであり、最適化はその低レベル表現をさらに効率化するプロセスです。この順序は、コンパイラの設計思想に合致し、予期せぬルールの相互作用を防ぐのに役立ちます。

これらの変更は、機能的な振る舞いを変更するものではなく、主にコードベースの品質と開発者の体験を向上させるためのものです。

## 前提知識の解説

### GoコンパイラのSSAバックエンド
Goコンパイラは、ソースコードを中間表現（IR）に変換し、最終的に機械語を生成します。この中間表現の一つにSSA（Static Single Assignment）形式があります。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。

GoコンパイラのSSAバックエンドは、以下の主要なフェーズで構成されます。
*   **構築 (Construction)**: 抽象構文木 (AST) からSSA形式のグラフを構築します。
*   **ローワーリング (Lowering)**: プラットフォーム非依存のSSA操作を、特定のアーキテクチャ（例: AMD64）の命令セットに近い、より低レベルの操作に変換します。例えば、`Add64`のような汎用的な加算操作が、AMD64の`ADDQ`命令に変換されます。
*   **最適化 (Optimization)**: ローワーリングされたSSAグラフに対して、定数畳み込み、不要コード削除、共通部分式除去などの様々な最適化を適用し、生成されるコードの効率を高めます。
*   **レジスタ割り当て (Register Allocation)**: SSA値に物理レジスタを割り当てます。
*   **コード生成 (Code Generation)**: 最終的な機械語命令を生成します。

### リライトルール (`.rules`ファイル)
GoコンパイラのSSAバックエンドでは、ローワーリングと最適化の多くが「リライトルール」として定義されています。これらのルールは、`src/cmd/compile/internal/ssa/gen/*.rules`ファイルに記述されており、特定のSSA操作パターンを別のSSA操作パターンに変換する方法を定義します。

リライトルールは、以下のような形式で記述されます。
`マッチパターン -> 置換パターン`
`マッチパターン && 条件 -> 置換パターン`

例:
`(Add64 x y) -> (ADDQ x y)`
これは、「64ビットの加算操作 `Add64` が `x` と `y` を引数にとる場合、それをAMD64の `ADDQ` 命令に変換する」というローワーリングルールです。

これらの`.rules`ファイルは、`go generate`コマンドによってGoのソースコード（`src/cmd/compile/internal/ssa/rewrite*.go`）に変換されます。この生成されたGoコードが、実際にSSAグラフを走査し、ルールを適用するロジックを含んでいます。

### ローワーリングルールと最適化ルール
*   **ローワーリングルール**: 高レベルの抽象的な操作（例: `Add64`）を、ターゲットアーキテクチャの具体的な命令（例: `ADDQ`）や、よりプリミティブな操作の組み合わせに変換するルールです。これらは、コンパイラが最終的な機械語を生成するために不可欠なステップです。
*   **最適化ルール**: 既にローワーリングされた、あるいは中間的なSSA操作に対して、より効率的な等価な操作に変換するルールです。例えば、`(Add64 x (Const64 [0])) -> x` のようなルールは、「0を加算する操作は不要なので、元の値 `x` に置き換える」という最適化です。

このコミットでは、AMD64のルールにおいて、ローワーリングルールが先に適用され、その後に最適化ルールが適用されるように順序が整理されました。これは、まず基本的な命令への変換を行い、その後にそれらの命令シーケンスを改善するという、コンパイラの一般的な最適化パスの考え方に沿っています。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおけるリライトルールの定義ファイルと、それらから生成されるGoコードの構造的な改善に焦点を当てています。

1.  **行の分割と列の整形**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/gen/generic.rules` ファイルにおいて、非常に長かったリライトルールの定義行が複数行に分割されました。これにより、各ルールの構成要素（マッチパターン、条件、置換パターン）が視覚的に分離され、一目で理解しやすくなっています。
    *   また、各要素が縦に揃うようにスペースが追加されています。例えば、オペレーションコード、引数、条件などが整列されることで、ルールのパターンマッチング部分と置換部分の対応関係が明確になります。

    **例（AMD64.rulesの変更前と変更後）**:
    変更前:
    `(Add64 x y) -> (ADDQ x y)`
    変更後:
    `(Add64  x y) -> (ADDQ  x y)`
    この例では、オペレーションコードの後にスペースが追加され、引数 `x` と `y` が揃えられています。

2.  **AMD64ルールの順序変更**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64.rules` ファイル内で、リライトルールのセクションが再編成されました。
    *   以前はローワーリングルールと最適化ルールが混在している箇所がありましたが、このコミットにより、すべてのローワーリングルールが先に配置され、その後にすべての最適化ルールが配置される構造になりました。
    *   具体的には、`// Above: lowering rules // Below: optimizations` というコメントが挿入され、その境界が明確にされました。これにより、コンパイラがSSAグラフを処理する際に、まず高レベルの操作を低レベルの命令に変換し（ローワーリング）、その後でそれらの低レベル命令シーケンスを効率化する（最適化）という、論理的な処理フローがルールの物理的な配置に反映されました。
    *   この順序付けは、コンパイラのパス設計において重要です。ローワーリングは通常、特定の命令セットの制約を満たすために行われ、最適化はその後、パフォーマンスを向上させるために行われます。この分離により、ルールの意図が明確になり、将来的なルールの追加や変更が容易になります。また、ローワーリングが最適化に依存したり、その逆であったりするような、意図しない循環的な依存関係や複雑な相互作用のリスクを低減します。

3.  **生成されるGoコードへの影響**:
    *   `.rules`ファイルの変更は、`src/cmd/compile/internal/ssa/rewriteAMD64.go` および `src/cmd/compile/internal/ssa/rewritegeneric.go` ファイルに直接影響を与えます。これらのGoファイルは、`.rules`ファイルから自動生成されるため、ルールの整形や順序変更がそのまま反映されます。
    *   生成されたGoコードでは、各リライトルールが `rewriteValueAMD64_OpXxx` のような関数として実装されます。このコミットによる変更は、これらの関数の内部ロジックではなく、主にその定義のフォーマットと、AMD64における関数の呼び出し順序（ローワーリング関数が先に、最適化関数が後に）に影響を与えます。
    *   特に、`rewriteAMD64.go`では、`Zero`命令のローワーリングに関するルールが移動され、より整理されたセクションに配置されています。これは、メモリのゼロ初期化に関する最適化が、一般的なローワーリングの後に行われるべきであるという設計思想を反映しています。

これらの変更は、コンパイラの内部構造をより理解しやすく、メンテナンスしやすいものにすることで、長期的な開発効率とコード品質の向上に貢献します。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルは以下の通りです。

*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: AMD64アーキテクチャ向けのリライトルール定義ファイル。行の整形、列の整列、ローワーリングルールと最適化ルールの順序変更が主な変更点です。特に、`Zero`命令に関するルールが移動され、最適化ルール群の前に配置されました。
*   `src/cmd/compile/internal/ssa/gen/generic.rules`: 汎用的な（アーキテクチャ非依存の）リライトルール定義ファイル。主に、行の整形と列の整列が行われています。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: `AMD64.rules`から自動生成されるGoコード。ルールの整形と順序変更が反映されています。
*   `src/cmd/compile/internal/ssa/rewritegeneric.go`: `generic.rules`から自動生成されるGoコード。ルールの整形が反映されています。

具体的な変更内容としては、各ルール定義の行末にスペースが追加されたり、オペランドが揃えられたり、長すぎる行が改行されたりしています。また、`AMD64.rules`では、`Zero`命令のローワーリングに関するルールが、以前は最適化ルール群の中にあったものが、ローワーリングルール群の適切な位置に移動されています。同様に、条件付き移動命令（CMOV）に関する最適化ルールも、最適化ルール群のセクションに移動されています。

## コアとなるコードの解説

このコミットは、主にGoコンパイラのSSAバックエンドにおけるリライトルールの**表現形式と構造**を改善するものです。機能的な変更は含まれていませんが、その変更はコンパイラの内部動作の理解に役立ちます。

例として、`src/cmd/compile/internal/ssa/gen/AMD64.rules` の一部の変更を見てみましょう。

**変更前**:
```
(Add64 x y) -> (ADDQ x y)
...
(Div8 x y) ->  (DIVW (SignExt8to16 x) (SignExt8to16 y))
...
(Zero [0] _ mem) -> mem
(Zero [1] destptr mem) -> (MOVBstoreconst [0] destptr mem)
...
// Rules below here apply some simple optimizations after lowering.
// TODO: Should this be a separate pass?
```

**変更後**:
```
// Lowering arithmetic
(Add64  x y) -> (ADDQ  x y)
...
(Div8   x y) -> (DIVW  (SignExt8to16 x) (SignExt8to16 y))
...
// Lowering Zero instructions
(Zero [0] _ mem) -> mem
(Zero [1] destptr mem) -> (MOVBstoreconst [0] destptr mem)
...
// ***************************
// Above: lowering rules
// Below: optimizations
// ***************************
// TODO: Should the optimizations be a separate pass?
```

この変更から読み取れることは以下の通りです。

1.  **整形と整列**: `(Add64 x y)` が `(Add64 x y)` のように、オペランドとオペレータの間にスペースが追加され、縦に揃えられています。これは、ルールのパターンマッチング部分と置換部分の構造を視覚的に明確にし、ルールの意図を素早く把握できるようにするためのものです。特に、複数のルールが並んだ際に、どの部分がオペレータでどの部分がオペランドなのかが分かりやすくなります。

2.  **`Zero` 命令の移動**: `Zero` 命令（メモリ領域をゼロで埋める操作）に関するローワーリングルールが、以前は最適化ルール群の中にあったものが、算術演算のローワーリングルール群の後に移動され、`// Lowering Zero instructions` という新しいセクションの下に配置されました。これは、`Zero` 操作が基本的なメモリ操作であり、最適化の前に低レベルの命令に変換されるべきであるというコンパイラの設計思想を反映しています。`Zero` 命令は、特定のサイズに応じて `MOVBstoreconst` (バイトストア)、`MOVWstoreconst` (ワードストア)、`MOVLstoreconst` (ロングワードストア)、`MOVQstoreconst` (クアッドワードストア) などの命令にローワーリングされます。また、大きなサイズの場合は、Duff's device や `REP STOSQ` (繰り返しストア文字列) 命令といった効率的なメカニズムに変換されるルールも含まれています。

3.  **ローワーリングと最適化の明確な分離**: `// *************************** Above: lowering rules Below: optimizations ***************************` というコメントが追加され、AMD64のリライトルールが「ローワーリング」と「最適化」の2つの主要なセクションに明確に分割されました。これにより、コンパイラがSSAグラフを処理する際のフェーズが、ルールの定義レベルで視覚的に表現されるようになりました。この分離は、コンパイラのパスがまず高レベルの抽象化を低レベルの命令に変換し、その後でそれらの低レベル命令をさらに効率化するという、一般的なコンパイラ設計の原則に従っていることを示しています。

これらの変更は、コンパイラのコードベースの内部的な整合性を高め、将来的な拡張やデバッグを容易にするための重要なステップです。

# [インデックス 28176] ファイルの概要

このコミットは、Go言語の`net`パッケージにおいて、`netgo`ビルドタグを使用してコンパイルされたバイナリが、システムの名前解決設定ファイルである`nsswitch.conf`を適切に利用できるようにする変更を導入します。これにより、`netgo`ビルドでも`nsswitch.conf`で指定された名前解決の順序（例: `files`、`dns`など）に従うことが可能になり、より柔軟でシステム設定に準拠した名前解決動作を実現します。特に、`nsswitch.conf`の解析結果がCgoベースの解決（`hostLookupCgo`）を要求する場合でも、`netgo`ビルドの特性に合わせて`hostLookupFilesDNS`にフォールバックするロジックが追加されています。

## コミット

```
net: allow netgo to use lookup from nsswitch.conf

Change https://golang.org/cl/8945 allowed Go to use its own DNS resolver
instead of libc in a number of cases. The code parses nsswitch.conf and
attempts to resolve things in the same order. Unfortunately, builds with
netgo completely ignore this parsing and always search via
hostLookupFilesDNS.

This commit modifies the logic to allow binaries built with netgo to
parse nsswitch.conf and attempt to resolve using the order specified
there. If the parsing results in hostLookupCGo, it falls back to the
original hostLookupFilesDNS. Tests are also added to ensure that both
the parsing and the fallback work properly.

Fixes #14354
```

## 元コミット内容

このコミットの目的は、`netgo`ビルドタグを使用してコンパイルされたGoバイナリが、システムの名前解決設定ファイルである`nsswitch.conf`で定義された名前解決の順序を尊重するようにすることです。以前は、Goの`net`パッケージは、特定の条件下で独自のDNSリゾルバを使用し、`nsswitch.conf`を解析して名前解決の順序を決定していました。しかし、`netgo`ビルドの場合、この`nsswitch.conf`の解析が完全に無視され、常に`hostLookupFilesDNS`という固定の順序で名前解決が試みられていました。この挙動は、`nsswitch.conf`で指定されたシステム全体の名前解決ポリシーと矛盾し、予期せぬ動作を引き起こす可能性がありました。

## 変更の背景

Goの`net`パッケージは、ネットワーク操作、特にホスト名の解決において重要な役割を果たします。Goは、Cgoを介してlibcのDNSリゾルバを使用する方法と、Go自身のネイティブなDNSリゾルバを使用する方法の2つを提供しています。

以前の変更（`https://golang.org/cl/8945`）により、Goは多くの場合でlibcではなく独自のDNSリゾルバを使用するようになりました。この変更の一環として、Goは`nsswitch.conf`を解析し、システムが設定した名前解決の順序（例: `/etc/hosts`ファイル、DNSサーバーなど）に従うようになりました。

しかし、`netgo`ビルドタグを使用してGoプログラムをコンパイルすると、Cgoへの依存関係が排除され、完全に静的にリンクされたバイナリが生成されます。これは、クロスコンパイルや、特定の環境でlibcのバージョンに依存したくない場合に有用です。問題は、`netgo`ビルドが`nsswitch.conf`の解析ロジックを完全に無視し、常に`hostLookupFilesDNS`（まず`/etc/hosts`ファイルを検索し、次にDNSを検索する）という固定の順序で名前解決を行っていた点にありました。

この挙動は、`nsswitch.conf`で`hosts: dns files`のように異なる順序が指定されているシステムでは問題となります。`netgo`ビルドのGoアプリケーションは、システムの設定を無視して名前解決を行うため、期待される動作と異なる結果を返す可能性がありました。このコミットは、この`netgo`ビルドの制限を解消し、`nsswitch.conf`の指定を尊重しつつ、`netgo`の特性（Cgoを使用しない）を維持することを目的としています。

## 前提知識の解説

### `netgo`ビルドタグ

`netgo`はGoコンパイラに渡すことができるビルドタグの一つです。`go build -tags netgo`のように使用されます。このタグを使用すると、Goの`net`パッケージがCgo（C言語のコードをGoから呼び出すためのメカニズム）を使用せずに、完全にGo言語で実装されたネイティブなネットワークスタックとDNSリゾルバを使用するように強制されます。

*   **利点**:
    *   **静的リンク**: 生成されるバイナリはlibcなどの外部Cライブラリに依存しないため、完全に静的にリンクされます。これにより、異なるLinuxディストリビューション間でのバイナリの移植性が向上します。
    *   **クロスコンパイル**: Cgoの依存関係がないため、クロスコンパイルが容易になります。
    *   **コンテナ環境**: コンテナイメージのサイズを削減したり、ベースイメージに特定のCライブラリが含まれていない環境でGoアプリケーションを実行したりするのに役立ちます。
*   **欠点**:
    *   **システム設定の無視**: 以前は、`nsswitch.conf`のようなシステム固有の名前解決設定を無視する傾向がありました。
    *   **機能の制限**: Cgoを使用しないため、一部の高度なネットワーク機能や、システム固有のDNSリゾルバのプラグイン（例: mDNS、LDAPベースの名前解決など）を利用できません。

### `nsswitch.conf`

`nsswitch.conf`（Name Service Switch configuration file）は、Unix系オペレーティングシステム（特にLinux）において、様々な「名前サービス」（ホスト名、ユーザー、グループ、パスワードなど）の情報をどのソースから、どのような順序で取得するかを定義する設定ファイルです。

例えば、ホスト名の解決に関して、`nsswitch.conf`の`hosts`エントリは以下のように記述されます。

```
hosts: files dns myhostname
```

これは、「ホスト名を解決する際には、まず`/etc/hosts`ファイル（`files`）を調べ、次にDNSサーバー（`dns`）に問い合わせ、最後に`myhostname`というカスタムサービスを使用する」という意味になります。

`nsswitch.conf`は、システム全体の名前解決ポリシーを決定するため、アプリケーションがこの設定を尊重することは、一貫した動作とセキュリティの観点から重要です。

### Goの名前解決順序 (`hostLookupOrder`)

Goの`net`パッケージ内部では、ホスト名の解決順序を決定するためにいくつかの内部定数が使用されます。

*   `hostLookupCgo`: Cgoを介してlibcのDNSリゾルバを使用する。これは、システムが提供するすべての名前解決メカニズム（`nsswitch.conf`で指定されたものを含む）を完全に利用できる最も包括的な方法です。
*   `hostLookupFilesDNS`: まず`/etc/hosts`ファイル（`files`）を検索し、次にDNSサーバー（`dns`）に問い合わせる順序。これはGoのネイティブリゾルバが提供する一般的な順序の一つです。
*   `hostLookupDNSFiles`: まずDNSサーバー（`dns`）に問い合わせ、次に`/etc/hosts`ファイル（`files`）を検索する順序。
*   `hostLookupFiles`: `/etc/hosts`ファイルのみを検索する順序。
*   `hostLookupDNS`: DNSサーバーのみを検索する順序。

これらの順序は、`nsswitch.conf`の解析結果や、`netgo`ビルドタグの有無、その他の環境要因に基づいて`net`パッケージが内部的に選択します。

## 技術的詳細

このコミットの核心は、`src/net/conf.go`内の`(*conf) hostLookupOrder(hostname string)`メソッドの変更にあります。このメソッドは、特定のホスト名を解決する際に使用すべき名前解決の順序を決定します。

変更前は、`c.netGo`が`true`（つまり`netgo`ビルド）の場合、このメソッドは即座に`hostLookupFilesDNS`を返していました。これは、`nsswitch.conf`の解析結果を完全に無視することを意味していました。

変更後、`netgo`ビルドの場合でも、`nsswitch.conf`の解析ロジックが実行されるようになりました。しかし、`netgo`ビルドはCgoを使用できないため、`nsswitch.conf`の解析結果が`hostLookupCgo`を要求するようなケース（例えば、`nsswitch.conf`がGoのネイティブリゾルバでは扱えない複雑な名前解決サービスを指定している場合）では問題が発生します。

この問題を解決するために、`fallbackOrder`という新しい変数が導入されました。

1.  まず、`fallbackOrder`はデフォルトで`hostLookupCgo`に設定されます。
2.  もし`c.netGo`が`true`であれば、`fallbackOrder`は`hostLookupFilesDNS`に上書きされます。これは、`netgo`ビルドではCgoを使用できないため、Cgoが必要な場合に`hostLookupFilesDNS`にフォールバックするというポリシーを確立します。
3.  その後、`nsswitch.conf`の解析ロジックが実行されます。この解析ロジックの様々な箇所で、以前は`hostLookupCgo`を直接返していた部分が、新しく導入された`fallbackOrder`を返すように変更されました。

これにより、以下の挙動が実現されます。

*   **非`netgo`ビルド**: `nsswitch.conf`の解析結果が`hostLookupCgo`を要求する場合、そのまま`hostLookupCgo`が返され、libcのDNSリゾルバが使用されます。
*   **`netgo`ビルド**:
    *   `nsswitch.conf`の解析結果がGoのネイティブリゾルバで処理可能な順序（例: `hostLookupFilesDNS`、`hostLookupDNSFiles`など）を要求する場合、その順序が使用されます。
    *   `nsswitch.conf`の解析結果が`hostLookupCgo`を要求する場合（Goのネイティブリゾルバでは扱えない複雑な設定など）、`fallbackOrder`の値である`hostLookupFilesDNS`が返されます。これにより、`netgo`ビルドでもCgoを使用せずに名前解決を試みることができます。

この変更により、`netgo`ビルドのGoアプリケーションは、`nsswitch.conf`の指定をより適切に尊重しつつ、Cgoへの依存を回避するという`netgo`の目的も達成できるようになります。

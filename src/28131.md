# [インデックス 28131] ファイルの概要

このコミットは、GoランタイムのARM64アーキテクチャ向けアセンブリコード、具体的には`src/runtime/asm_arm64.s`ファイルにおける`cgocallback_gofunc`の引数渡しに関するバグ修正です。`asm_arm64.s`は、GoプログラムがARM64プロセッサ上で動作する際の低レベルな処理、特にスケジューラ、スタック管理、CGOコールバックなどのコア機能を提供するアセンブリコードを含んでいます。

## コミット

GoランタイムにおけるARM64アーキテクチャでの`cgocallback_gofunc`の引数渡しに関する問題を修正します。具体的には、スタックアライメントを維持しつつ、引数が正しく配置されるようにスタックオフセットを調整します。

## 変更の背景

この変更は、GoプログラムがC言語のコードと相互運用する際に使用されるCGOメカニズムにおいて、CコードからGoコードへのコールバック（`cgocallback_gofunc`）がARM64アーキテクチャ上で正しく機能しない問題を修正するために行われました。

CGOコールバックでは、CコードがGo関数を呼び出す際に、GoランタイムがCスタックからGoスタックへのコンテキスト切り替えを行い、引数を適切に渡す必要があります。ARM64アーキテクチャでは、スタックポインタが常に16バイト境界にアライメントされている必要があります。このアライメントが崩れると、プログラムのクラッシュや未定義の動作を引き起こす可能性があります。

元のコードでは、`cgocallback_gofunc`がGo関数に引数を渡す際に、スタックオフセットの計算が誤っていたため、この16バイトアライメントの要件を満たせていなかったか、あるいは引数の配置が期待通りに行われていませんでした。この不具合により、CGOコールバックを使用するGoプログラムがARM64環境で不安定になる可能性がありました。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する低レベルなシステムです。これには、ガベージコレクション、スケジューリング（ゴルーチンの管理）、メモリ割り当て、CGO（C言語との相互運用）などが含まれます。Goランタイムの多くの部分は、パフォーマンスと低レベルな制御のためにアセンブリ言語で書かれています。

### CGO
CGOは、GoプログラムがC言語の関数を呼び出したり、C言語のコードからGo関数を呼び出したりするためのメカニズムです。これにより、既存のCライブラリをGoから利用したり、Goの特定の機能をCから利用したりすることが可能になります。CGOは、GoとCの間の異なる呼び出し規約、スタック管理、データ表現などを橋渡しする複雑な処理を伴います。

### `cgocallback_gofunc`
`cgocallback_gofunc`は、CGOメカニズムの一部であり、CコードがGo関数を呼び出す際に使用される特別なエントリポイントです。CコードからGo関数が呼び出されると、Goランタイムはこの`cgocallback_gofunc`を通じて制御を受け取り、CスタックからGoスタックへの切り替え、引数の変換と渡し、そして最終的に目的のGo関数の実行を行います。

### ARM64アーキテクチャとスタックアライメント
ARM64（AArch64）は、64ビットのARMプロセッサアーキテクチャです。このアーキテクチャでは、関数呼び出し規約の一部として、スタックポインタ（SPレジスタ）が常に16バイト境界にアライメントされている必要があります。これは、特定の命令が16バイトアライメントされたメモリアドレスを期待するためであり、この要件が満たされない場合、パフォーマンスの低下やハードウェア例外（クラッシュ）が発生する可能性があります。

### アセンブリ言語 (`.s`ファイル)
Goランタイムの`src/runtime/asm_arm64.s`のようなファイルは、ARM64プロセッサ向けのアセンブリ言語で書かれています。アセンブリ言語は、プロセッサが直接実行できる機械語に非常に近い低レベルなプログラミング言語です。Goランタイムでは、ゴルーチンのスケジューリング、コンテキストスイッチ、CGOの橋渡しなど、OSやハードウェアと密接に連携するクリティカルな部分でアセンブリが使用されます。

### スタックフレームと引数渡し
関数が呼び出されると、その関数専用のメモリ領域がスタック上に確保されます。これをスタックフレームと呼びます。スタックフレームには、関数のローカル変数、レジスタの退避領域、そして呼び出し元から渡された引数などが格納されます。引数は通常、スタックポインタからのオフセットを使ってアクセスされます。

## 技術的詳細

このコミットの技術的な核心は、ARM64におけるスタックアライメントと引数渡しの正確な管理です。`cgocallback_gofunc`は、CコードからGo関数への呼び出しを仲介する際に、CスタックからGoスタックへの移行を処理します。この過程で、Go関数が期待する形式で引数をGoスタックに配置する必要があります。

元のコードでは、Go関数に渡される引数（この場合は`ctxt`）をスタックにプッシュする際のオフセット計算に誤りがありました。

```armasm
// 修正前
MOVD    R5, -(16+8)(R4)
MOVD    R0, -(24+8)(R4) // maintain 16-byte SP alignment
MOVD    $-(24+8)(R4), R0
```

ここで、`R4`はスタックポインタ（`g_sched+gobuf_sp`から取得されるGoスタックのポインタ）を表しています。`MOVD R0, -(24+8)(R4)`の行は、`ctxt`（引数）をスタックにプッシュしようとしていますが、このオフセットが問題でした。`-(24+8)(R4)`は、`R4`から32バイト下にデータを書き込むことを意味します。

ARM64の呼び出し規約では、スタックポインタは常に16バイトアライメントされている必要があります。また、引数の配置も特定のルールに従う必要があります。このオフセットの誤りにより、以下のいずれかの問題が発生したと考えられます。

1.  **スタックアライメントの違反**: `MOVD R0, -(24+8)(R4)`の操作が、スタックポインタを16バイト境界からずらしてしまった可能性があります。
2.  **引数の誤配置**: `ctxt`がGo関数が期待するスタック上の位置に配置されず、Go関数が間違ったメモリ位置から引数を読み取ろうとした可能性があります。

この修正は、これらのオフセットを調整することで、引数が正しく配置され、かつスタックアライメントが維持されるようにします。

## コアとなるコードの解説

変更されたのは以下の3行です。

**修正前:**
```armasm
MOVD    R5, -(16+8)(R4)
MOVD    R0, -(24+8)(R4) // maintain 16-byte SP alignment
MOVD    $-(24+8)(R4), R0
```

**修正後:**
```armasm
MOVD    R5, -(24+8)(R4)
MOVD    R0, -(16+8)(R4)
MOVD    $-(24+8)(R4), R0 // maintain 16-byte SP alignment
```

各行の変更点を詳しく見ていきます。

1.  `MOVD R5, -(16+8)(R4)` から `MOVD R5, -(24+8)(R4)` へ:
    *   `R5`には、Go関数が実行を再開するアドレス（`g_sched+gobuf_pc`）が格納されています。これは、Go関数へのリターンアドレスまたは開始アドレスとしてスタックに保存されます。
    *   元のコードでは、`R4`（Goスタックポインタ）から24バイト（16+8）下に`R5`を保存していました。
    *   修正後では、`R4`から32バイト（24+8）下に`R5`を保存するように変更されました。これは、スタック上の他のデータ（特に次の`ctxt`）との相対的な位置を調整し、全体的なスタックフレームの整合性を保つためです。

2.  `MOVD R0, -(24+8)(R4)` から `MOVD R0, -(16+8)(R4)` へ:
    *   `R0`には、CGOコールバックのコンテキスト情報（`ctxt+24(FP)`）が格納されています。これは、Go関数に渡される引数の一つです。
    *   元のコードでは、`R4`から32バイト（24+8）下に`R0`を保存していました。
    *   修正後では、`R4`から24バイト（16+8）下に`R0`を保存するように変更されました。この変更により、`ctxt`がGo関数が期待する正しいスタック上の位置に配置されるようになります。

3.  `MOVD $-(24+8)(R4), R0` は変更なし。コメント `// maintain 16-byte SP alignment` が移動。
    *   この行は、新しいスタックポインタの値を計算し、`R0`に格納しています。そして、次の行で`R0`の値を`RSP`（スタックポインタレジスタ）に設定しています。
    *   `-(24+8)(R4)`は、`R4`から32バイト下に新しいスタックポインタを設定することを意味します。この値は、前の2つの`MOVD`命令でプッシュされたデータ（合計で16バイト + 8バイト = 24バイト、または8バイト + 8バイト = 16バイト）と、ARM64の16バイトスタックアライメント要件を考慮して計算されます。
    *   コメントが移動したことで、この行がスタックアライメントの維持に直接関与していることがより明確になりました。

これらの変更により、`cgocallback_gofunc`がGo関数を呼び出す際に、引数（`ctxt`）がGoスタック上の正しい位置に配置され、かつARM64の16バイトスタックアライメント要件が満たされるようになります。これにより、CGOコールバックの安定性と信頼性が向上します。

# [インデックス 27288] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるインライン化の挙動を改善するものです。具体的には、関数内で定数（`const`）を宣言している場合でも、その関数がインライン化の対象となるように変更が加えられました。これにより、コンパイラの最適化能力が向上し、生成されるバイナリのパフォーマンスが改善される可能性があります。また、エクスポート処理におけるシンボルの扱いも修正されています。

## 変更の背景

Goコンパイラには、プログラムの実行速度を向上させるための最適化手法の一つとして「インライン化（inlining）」があります。インライン化とは、関数呼び出しのオーバーヘッドを削減するために、呼び出される関数の本体を呼び出し元に直接展開する最適化です。しかし、以前のGoコンパイラでは、関数内で定数（`const`）が宣言されている場合、その関数はインライン化の対象から除外されていました。

この制限は、コンパイラの内部表現における`ODCLCONST`ノード（定数宣言を表す抽象構文木（AST）ノード）の扱いに起因していました。特に、関数のインライン化可能性を判断するロジックや、コンパイル済みコードをエクスポートする際の処理において、`ODCLCONST`ノードが適切に処理されていなかったため、インライン化が妨げられていました。

この問題は、Go issue #7655として報告されており、関数内で定数を宣言するだけでインライン化が阻害されるという、開発者にとって直感的ではない挙動を修正することが求められていました。このコミットは、この問題を解決し、より多くの関数がインライン化の恩恵を受けられるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部概念と最適化技術に関する知識が必要です。

1.  **Goコンパイラ（`cmd/compile`）**: Go言語のソースコードを機械語に変換するツールチェーンの一部です。ASTの構築、型チェック、最適化、コード生成などのフェーズがあります。
2.  **抽象構文木（AST: Abstract Syntax Tree）**: ソースコードの構造を木構造で表現したものです。GoコンパイラはソースコードをASTにパースし、このASTに対して様々な処理を行います。
    *   **ノードの種類**: ASTの各要素はノードとして表現され、それぞれが特定の操作や宣言に対応する種類（`Op`）を持ちます。
        *   `ODCLCONST`: 定数宣言（`const`）を表すノード。
        *   `OLITERAL`: リテラル値（例: `10`, `"hello"`, `true`）を表すノード。
        *   `OEMPTY`: 空のステートメントを表すノード。
3.  **インライン化（Inlining）**: コンパイラ最適化の一種で、小さな関数の呼び出しを、その関数の本体で置き換えることで、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数の渡し、戻り値の処理など）を削減します。これにより、実行速度が向上し、さらに他の最適化（例: 定数伝播）の機会が増えることがあります。
    *   Goコンパイラは、関数の複雑さやサイズに基づいてインライン化の可否を判断します。
4.  **エクスポート（Export）とインポート（Import）**: Goコンパイラは、パッケージ間で情報を共有するために、コンパイル済みのパッケージのASTや型情報をエクスポート（書き出し）し、他のパッケージがそれをインポート（読み込み）します。
    *   `bexport.go` / `bimport.go`: バイナリ形式でのエクスポート/インポート処理を担当するファイル。
    *   `export.go`: エクスポートされるシンボルや型の処理を担当するファイル。
5.  **`exprfmt`**: Goコンパイラの内部関数で、ASTノードを文字列形式にフォーマットする役割を持ちます。デバッグ出力や、特定のコンテキスト（例: エクスポート時の表現）でASTノードを処理する際に使用されます。
6.  **`Pkglookup`**: パッケージ内のシンボルを検索する関数。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラが`ODCLCONST`ノードをインライン化の妨げと見なさないように、その内部処理を変更した点にあります。

1.  **`ODCLCONST`ノードの扱い変更**:
    *   `src/cmd/compile/internal/gc/bexport.go`と`src/cmd/compile/internal/gc/bimport.go`において、`OEMPTY`ノードと同様に`ODCLCONST`ノードが「何もしない」（`// nothing to do`）ケースとして扱われるようになりました。これは、バイナリ形式でのエクスポート/インポート時に`ODCLCONST`ノード自体を特別に処理する必要がないことを意味します。定数宣言は、最終的にはリテラル値に置き換えられるため、ASTのこの段階ではその存在が問題とならないように調整されました。
    *   `src/cmd/compile/internal/gc/inl.go`の`ishairy`関数から`ODCLCONST`が削除されました。`ishairy`関数は、インライン化を妨げる「複雑な」ノードの種類をチェックする役割を担っています。`ODCLCONST`がこのリストから削除されたことで、定数宣言を含む関数もインライン化の候補として適切に評価されるようになりました。
2.  **`exprfmt`の修正**:
    *   `src/cmd/compile/internal/gc/fmt.go`の`exprfmt`関数に`ODCLCONST`ケースが追加されました。この変更により、`exprfmt`がエクスポートコンテキスト（`fmtbody`フラグが`true`の場合）で`ODCLCONST`ノードに遭遇した際、空文字列を返すように指示されます。これは、定数宣言が既にリテラルに置き換えられているため、エクスポート時にはその宣言自体を出力する必要がないという考えに基づいています。
3.  **エクスポートリストへのシンボル追加ロジックの改善**:
    *   `src/cmd/compile/internal/gc/export.go`の`reexportdep`関数において、`OTYPE`ノードの処理に`n.Sym.Def != nil`という条件が追加されました。これは、シンボルがエクスポートリストに追加される前に、そのシンボルに実際の定義が存在するかどうかを確認するためのものです。コミットメッセージによると、`OLITERAL`シンボルが非エクスポートシンボルに対して`Pkglookup`経由で検索された際に、定義がないにもかかわらずエクスポートリストに追加される問題があったため、このチェックが導入されました。これにより、不必要なシンボルがエクスポートされるのを防ぎ、エクスポート処理の正確性が向上します。
    *   `dumpexporttype`関数内の`exportf`呼び出しで、インライン化された関数のボディをエクスポートする際に`FmtBody`フラグが追加されました。これにより、インライン化された関数の詳細な情報がエクスポートされるようになり、インライン化の判断に必要な情報がより正確に伝達されるようになります。

これらの変更により、Goコンパイラは関数内の定数宣言を適切に扱い、インライン化の機会を増やすとともに、エクスポート処理の堅牢性を高めています。

## コアとなるコードの解説

*   **`bexport.go` と `bimport.go` の変更**:
    *   `ODCLCONST`が`OEMPTY`と同じく「何もしない」ケースとして追加されたことで、バイナリ形式でのパッケージのエクスポート/インポート時に、定数宣言ノードが特別な処理を必要としないことが明示されました。これは、定数自体はコンパイル時にリテラル値に置き換えられるため、ASTのこの段階ではその存在が問題にならないという設計思想を反映しています。
*   **`export.go` の変更**:
    *   `reexportdep`関数における`OTYPE`ケースでの`n.Sym.Def != nil`の追加は、エクスポートされるシンボルが実際に定義を持っていることを保証するための重要なチェックです。これにより、定義を持たない`OLITERAL`シンボルが誤ってエクスポートリストに追加されることを防ぎ、コンパイラの健全性を保ちます。
    *   `dumpexporttype`関数での`Hconv(f.Type.Nname.Func.Inl, FmtSharp|FmtBody)`への変更は、インライン化された関数のボディ情報もエクスポートされるようにすることで、コンパイラがインライン化の判断をより正確に行えるようにするためのものです。
*   **`fmt.go` の変更**:
    *   `exprfmt`関数に`ODCLCONST`ケースが追加され、`fmtbody`が`true`（エクスポートコンテキスト）の場合に空文字列を返すようにしたことで、エクスポート時に定数宣言ノードが冗長に出力されるのを防ぎます。これは、定数が既にリテラルに展開されているという前提に基づいています。
*   **`inl.go` の変更**:
    *   `ishairy`関数から`ODCLCONST`が削除されたことが、このコミットの最も直接的な目的達成部分です。`ishairy`はインライン化を阻害する複雑な構造を検出する役割を担っており、`ODCLCONST`がこのリストから除外されたことで、定数宣言を含む関数もインライン化の対象として考慮されるようになりました。
*   **`test/inline.go` の変更**:
    *   新しいテストケース`func i(x int) int { const y = 2; return x + y }`が追加されました。この関数は内部で定数`y`を宣言していますが、`// ERROR "can inline i"`というコメントが付与されており、コンパイラがこの関数をインライン化可能であると判断することを期待しています。これは、変更が正しく機能していることを検証するためのものです。

これらの変更は、Goコンパイラの内部でASTノードがどのように処理され、インライン化の判断にどのように影響するかを再調整することで、より効率的なコード生成を可能にしています。

# [インデックス 24358] ファイルの概要

このコミットは、GoランタイムのLinux固有のOSインタラクションを扱う`src/runtime/os1_linux.go`ファイルに対するものです。具体的には、CPUアフィニティ情報を取得するための`sched_getaffinity`システムコールに関連するバッファサイズの問題を修正しています。

## コミット

runtime: pass a smaller buffer to sched_getaffinity on ARM

The system stack is only around 8kb on ARM so one can't put an 8kb buffer on
the stack. More than 1024 ARM cores seems sufficiently unlikely for the
foreseeable future.

Fixes #11853

## 元コミット内容

このコミットは、GoランタイムがLinux上で`sched_getaffinity`システムコールを呼び出す際に使用するバッファのサイズに関する問題を修正しています。元々、このバッファは最大65536個のCPUをサポートするように設計されており、そのためのバッファサイズは8KBでした。しかし、ARMアーキテクチャではシステムスタックのサイズが約8KBと非常に小さいため、この8KBのバッファをスタック上に確保しようとするとスタックオーバーフローを引き起こす可能性がありました。この問題は、GoのランタイムがCPUアフィニティ情報を安全に取得できない原因となっていました。

## 変更の背景

この変更の背景には、Goランタイムが特定のアーキテクチャ（特にARM）上で直面していたスタックサイズに関する制約があります。

1.  **ARMのシステムスタックサイズ**: ARMアーキテクチャでは、Goランタイムが使用するシステムスタックのサイズが約8KBに制限されていました（`golang.org/issue/11873`で言及されています）。
2.  **`sched_getaffinity`のバッファ要件**: `sched_getaffinity`システムコールは、システム上のCPUアフィニティマスクを格納するためのバッファを必要とします。Goランタイムは、最大65536個のCPUをサポートするために、このバッファに8KBのメモリを割り当てていました。
3.  **スタックオーバーフローの危険性**: 8KBのシステムスタック上で8KBのバッファを確保しようとすると、スタック領域が不足し、スタックオーバーフローが発生する危険性がありました。これは、Goプログラムのクラッシュや予期せぬ動作につながる可能性があります。
4.  **現実的なCPUコア数**: コミットメッセージでは、「予見可能な将来において、1024個を超えるARMコアは十分にありそうにない」と指摘されています。これは、8KBのバッファが必要とする65536個のCPUサポートが、ARM環境では過剰であることを示唆しています。
5.  **問題の特定**: この問題は`golang.org/issue/11853`として報告され、Goチームによって認識されていました。

これらの背景から、ARM環境での安定性を確保するために、`sched_getaffinity`に渡すバッファサイズをARMに特化して小さくする必要がありました。

## 前提知識の解説

### `sched_getaffinity`システムコール

`sched_getaffinity`はLinuxカーネルが提供するシステムコールの一つで、特定のプロセスまたはスレッドが実行を許可されているCPUのセット（CPUアフィニティマスク）を取得するために使用されます。

*   **CPUアフィニティマスク**: これはビットマスクであり、各ビットがシステム上のCPUに対応します。ビットがセットされていれば、そのCPU上でプロセスまたはスレッドが実行可能であることを意味します。
*   **目的**: プロセスがどのCPUで実行されているか、または実行できるかを把握するために使用されます。これは、マルチプロセッサシステムでのパフォーマンス最適化（例えば、キャッシュの局所性を高めるためにスレッドを特定のCPUに「ピン留め」する）に役立ちます。
*   **引数**: `sched_getaffinity`は、プロセスID、CPUセットのサイズ、および`cpu_set_t`構造体へのポインタを引数として取ります。CPUセットのサイズは、カーネルが返すCPUマスクを格納するバッファのサイズを示します。

### Goのランタイムにおけるシステムスタック

Goプログラムは、ユーザーレベルのゴルーチンスケジューラによって管理される軽量なゴルーチンを使用します。各ゴルーチンは独自のスタックを持ちますが、システムコールを実行する際には、Goランタイムはカーネルが提供するシステムスタックに切り替える必要があります。

*   **システムスタックの役割**: システムコールが実行される際、カーネルは現在のコンテキスト（レジスタ、スタックポインタなど）を保存し、カーネルモードに移行します。このとき、カーネルは自身のスタック（システムスタック）を使用します。
*   **サイズ制約**: システムスタックのサイズは、OSやアーキテクチャによって異なります。ARMのような組み込みシステムやリソースが限られた環境では、システムスタックのサイズが比較的小さく設定されていることがあります。このコミットの文脈では、ARMのシステムスタックが約8KBであることが問題となりました。

### `goarch_arm`ビルド定数

Go言語では、コンパイル時にターゲットアーキテクチャを識別するためのビルド定数が提供されています。`goarch_arm`は、GoプログラムがARMアーキテクチャ向けにコンパイルされている場合に`true`（または1）となる定数です。これにより、特定のアーキテクチャに合わせた条件付きコンパイルやコードの調整が可能になります。

## 技術的詳細

このコミットの技術的詳細は、`sched_getaffinity`システムコールに渡すバッファのサイズを、ターゲットアーキテクチャがARMであるかどうかに応じて動的に調整する点にあります。

`sched_getaffinity`は、CPUアフィニティマスクを`cpu_set_t`型の構造体に書き込みます。この構造体の実体は、CPUの数に応じて必要なビット数を保持できるバイト配列です。Goランタイムでは、このバッファをスタック上に確保していました。

元のコードでは、`maxCPUs`という定数を使ってバッファの最大サイズを決定していました。

```go
const maxCPUs = 64 * 1024 // 65536
var buf [maxCPUs / (ptrSize * 8)]uintptr
```

ここで、`ptrSize`はポインタのサイズ（通常4バイトまたは8バイト）、`8`は1バイトあたりのビット数です。この計算により、`buf`は65536個のCPUを表現できるだけのサイズ（約8KB）を持っていました。

問題は、ARMアーキテクチャのシステムスタックが8KBしかないため、この8KBのバッファをスタック上に確保しようとするとスタックオーバーフローが発生する可能性があったことです。

このコミットでは、`maxCPUs`の定義を以下のように変更しました。

```go
const maxCPUs = 64*1024*(1-goarch_arm) + 1024*goarch_arm
```

この式は、`goarch_arm`がビルド時に`1`（ARMアーキテクチャの場合）または`0`（非ARMアーキテクチャの場合）に評価されることを利用した条件付きコンパイルのイディオムです。

*   **`goarch_arm`が`1`の場合（ARMアーキテクチャ）**:
    `maxCPUs = 64*1024*(1-1) + 1024*1`
    `maxCPUs = 64*1024*0 + 1024`
    `maxCPUs = 0 + 1024`
    `maxCPUs = 1024`
    この場合、`maxCPUs`は1024となり、`buf`のサイズは1024個のCPUを表現できるサイズ（約128バイト）に縮小されます。これは、8KBのシステムスタックに収まる十分小さなサイズです。

*   **`goarch_arm`が`0`の場合（非ARMアーキテクチャ）**:
    `maxCPUs = 64*1024*(1-0) + 1024*0`
    `maxCPUs = 64*1024*1 + 0`
    `maxCPUs = 65536`
    この場合、`maxCPUs`は元の65536のままであり、`buf`のサイズも元の約8KBのままです。これは、非ARMアーキテクチャではシステムスタックが十分に大きいため問題ありません。

このようにして、GoランタイムはARMアーキテクチャに特有のスタックサイズ制約に対応しつつ、他のアーキテクチャでは引き続きより多くのCPUをサポートできる柔軟性を維持しています。

## コアとなるコードの解説

変更は`src/runtime/os1_linux.go`ファイルの`getproccount`関数内で行われています。

1.  **コメントの更新**:
    元のコメント: `// This buffer is huge (8 kB) but we are on the system stack // and there should be plenty of space (64 kB).`
    変更後: `// This buffer is huge (8 kB) but we are on the system stack // and there should be plenty of space (64 kB) -- except on ARM where // the system stack itself is only 8kb (see golang.org/issue/11873).`
    この変更は、ARMアーキテクチャにおけるシステムスタックのサイズが8KBであるという重要な制約と、関連するIssue番号（#11873）を明示的に追加し、コードの背景をより明確にしています。

2.  **`maxCPUs`定数の変更**:
    元の定義: `const maxCPUs = 64 * 1024`
    変更後: `const maxCPUs = 64*1024*(1-goarch_arm) + 1024*goarch_arm`
    これがこのコミットの核心的な変更です。
    *   `goarch_arm`は、GoがARMアーキテクチャ向けにビルドされている場合に`1`、それ以外の場合に`0`となるビルド定数です。
    *   この式により、ARMアーキテクチャでは`maxCPUs`が`1024`に設定されます。これは、1024個のCPUをサポートするのに十分なバッファサイズ（約128バイト）を意味し、8KBのシステムスタックに安全に収まります。
    *   非ARMアーキテクチャでは、`maxCPUs`は元の`65536`のままとなり、約8KBのバッファサイズが維持されます。

この変更により、`sched_getaffinity`システムコールに渡される`buf`配列のサイズが、ARM環境では大幅に縮小され、スタックオーバーフローのリスクが解消されました。同時に、他のアーキテクチャでは、より多くのCPUをサポートするための十分なバッファサイズが維持されています。

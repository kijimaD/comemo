# [インデックス 26298] ファイルの概要

このコミットは、Go言語の正規表現エンジンにおける共通プレフィックスのファクタリング処理に関するバグ修正です。特に、非貪欲量指定子を含む選択肢（alternations）において、正規表現の最適化が誤ったマッチング結果を引き起こす可能性があった問題に対処しています。

## コミット

```
regexp/syntax: fix factoring of common prefixes in alternations

In the past, `a.*?c|a.*?b` was factored to `a.*?[bc]`. Thus, given
"abc" as its input string, the automaton would consume "ab" and
then stop (when unanchored) whereas it should consume all of "abc"
as per leftmost semantics.

Fixes #13812.

Change-Id: I67ac0a353d7793b3d0c9c4aaf22d157621dfe784
Reviewed-on: https://go-review.googlesource.com/18357
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

`regexp/syntax`パッケージにおいて、選択肢（alternations）内の共通プレフィックスのファクタリング処理を修正します。

以前は、`a.*?c|a.*?b`のような正規表現が`a.*?[bc]`のようにファクタリングされていました。このため、入力文字列が"abc"の場合、オートマトンは"ab"までを消費して停止してしまい（アンカーされていない場合）、左端優先マッチのセマンティクスに従って"abc"全体を消費すべきであるにもかかわらず、正しく動作しませんでした。

このコミットはIssue #13812を修正します。

## 変更の背景

Go言語の正規表現エンジンは、パフォーマンス向上のために正規表現を解析する際に様々な最適化を行います。その一つが「ファクタリング（factoring）」と呼ばれる処理で、複数の選択肢（`|`で区切られた部分）が共通のプレフィックスを持つ場合に、その共通部分を抽出して正規表現の構造を簡素化します。例えば、`abc|abd`は`ab(c|d)`のようにファクタリングされます。

しかし、このファクタリング処理が非貪欲量指定子（`*?`, `+?`など）を含む複雑なパターンに適用されると、意図しないマッチング結果を引き起こすことが判明しました。具体的には、`a.*?c|a.*?b`という正規表現が`a.*?[bc]`とファクタリングされると、"abc"という文字列に対して、本来`a.*?c`が"abc"全体にマッチすべきところ、ファクタリングされた`a.*?[bc]`は"ab"まででマッチを終えてしまうという問題がありました。これはGoの正規表現が採用している「左端優先マッチ（leftmost semantics）」の原則に反する動作です。

この問題はIssue #13812として報告され、本コミットによって修正されました。修正の目的は、最適化によるパフォーマンス向上と、正規表現の正しいセマンティクス（特に左端優先マッチ）の維持とのバランスを取ることにあります。

## 前提知識の解説

### 1. 正規表現のファクタリング (Factoring)

正規表現のファクタリングは、複数の選択肢（`|`で結合された部分）が共通の開始パターンを持つ場合に、その共通部分を抽出して正規表現の構造を簡素化する最適化手法です。これにより、正規表現エンジンの処理効率が向上し、オートマトンの状態数を減らすことができます。

*   **例**: `fooA|fooB` は `foo(A|B)` にファクタリングされます。
*   **目的**: パフォーマンス向上と、よりコンパクトなオートマトンの生成。

### 2. 左端優先マッチ (Leftmost Semantics)

Go言語の`regexp`パッケージは、PerlやPythonなどと同様に「左端優先マッチ」のセマンティクスを採用しています。これは、入力文字列の最も左で開始するマッチを優先するという原則です。複数のマッチ候補がある場合、最も左で開始するものが選ばれ、その中で最も長いマッチが優先される（貪欲マッチの場合）か、最も短いマッチが優先される（非貪欲マッチの場合）かが決定されます。

本件の`a.*?c|a.*?b`の例では、"abc"に対して`a.*?c`は"abc"全体にマッチし、`a.*?b`は"ab"にマッチします。どちらも'a'から始まるため、左端優先の原則に従い、より長い"abc"がマッチすべきです。しかし、誤ったファクタリングにより"ab"がマッチしてしまっていました。

### 3. 非貪欲マッチ (Non-greedy/Reluctant Quantifiers)

正規表現の量指定子（`*`, `+`, `?`, `{n,m}`など）は、デフォルトでは「貪欲（greedy）」です。これは、可能な限り長い文字列にマッチしようとします。
一方、量指定子の後に`?`を付けると「非貪欲（non-greedy）」または「最小マッチ（reluctant）」になります。これは、可能な限り短い文字列にマッチしようとします。

*   **例**:
    *   `a.*b` (貪欲): "axbyb" に対して "axbyb" にマッチ。
    *   `a.*?b` (非貪欲): "axbyb" に対して "axb" にマッチ。

本コミットの例では`.*?`という非貪欲量指定子が関与しており、ファクタリングが非貪欲マッチの挙動を誤って変更してしまったことが問題でした。

### 4. Goの`regexp/syntax`パッケージ

`regexp/syntax`パッケージは、Go言語の標準ライブラリ`regexp`パッケージの一部であり、正規表現の構文解析（パース）と抽象構文木（AST）の構築を担当します。このパッケージは、正規表現文字列を内部的な表現（`Regexp`構造体）に変換し、その後の最適化やオートマトン構築の基盤を提供します。

*   **`Regexp`構造体**: 正規表現の各要素（リテラル、文字クラス、繰り返し、選択肢など）を表すノードを持つAST。
*   **`OpRepeat`**: `Regexp`構造体の`Op`フィールドが`OpRepeat`の場合、そのノードが繰り返し操作（例: `*`, `+`, `{n,m}`）を表すことを示す。
*   **`isCharClass`**: `Regexp`ノードが文字クラス（例: `[a-z]`, `.`）を表すかどうかを判定するヘルパー関数。

## 技術的詳細

この修正は、`src/regexp/syntax/parse.go`ファイル内の`parser.factor`メソッドに集中しています。このメソッドは、正規表現のASTを最適化する過程で、共通のプレフィックスを持つ選択肢をファクタリングする役割を担っています。

以前の実装では、`factor`メソッドは「共通の複雑なプレフィックス（common complex prefixes）」もファクタリングしようとしていました。しかし、コミットメッセージが指摘するように、非貪欲量指定子を含むような「複雑なサブ式」をファクタリングすると、オートマトンの異なるパスが誤って結合され、正規表現のセマンティクス（特に左端優先マッチ）が損なわれる可能性がありました。

このコミットでは、ファクタリングの条件を厳格化し、**「共通の単純なプレフィックス（common simple prefixes）」のみをファクタリングする**ように変更されました。具体的には、ファクタリングの対象となるプレフィックスが「文字クラス」であるか、または「文字クラスの固定回数の繰り返し」である場合に限定されます。これにより、非貪欲量指定子のような複雑な構造を持つプレフィックスが誤ってファクタリングされることを防ぎ、正規表現の正しいマッチング挙動を保証します。

この変更は、最適化の恩恵を享受しつつも、正規表現の正確性を維持するための重要なバランス調整です。

## コアとなるコードの解説

### `src/regexp/syntax/parse.go`の変更点

1.  **コメントの更新**:
    `// Round 2: Factor out common complex prefixes,`
    から
    `// Round 2: Factor out common simple prefixes,`
    に変更されました。これは、ファクタリングの対象を「複雑な」プレフィックスから「単純な」プレフィックスに限定するという意図を明確に示しています。
    さらに、
    `// Complex subexpressions (e.g. involving quantifiers)`
    `// are not safe to factor because that collapses their`
    `// distinct paths through the automaton, which affects`
    `// correctness in some cases.`
    という詳細な説明が追加され、なぜこの制限が必要なのかが明記されました。非貪欲量指定子のような複雑なサブ式をファクタリングすると、オートマトンの異なるパスが結合され、結果として正規表現の正確性に影響を与えるため、安全ではないと説明されています。

2.  **ファクタリング条件の追加**:
    以前の条件 `if first != nil && first.Equal(ifirst)` に加えて、以下の条件が追加されました。
    `&& (isCharClass(first) || (first.Op == OpRepeat && first.Min == first.Max && isCharClass(first.Sub[0])))`
    この新しい条件は、ファクタリングされる共通プレフィックス`first`が以下のいずれかである場合に限定します。
    *   `isCharClass(first)`: `first`が文字クラス（例: `[a-z]`, `.`）である場合。
    *   `(first.Op == OpRepeat && first.Min == first.Max && isCharClass(first.Sub[0]))`: `first`が`OpRepeat`操作であり、かつ繰り返し回数が固定（`Min == Max`）で、その繰り返しの対象が文字クラスである場合（例: `x{2}`のような固定回数の繰り返し）。

    この厳格な条件により、`a.*?`のような非貪欲量指定子を含むプレフィックスは「単純なプレフィックス」とは見なされなくなり、ファクタリングの対象から外れることになります。これにより、`a.*?c|a.*?b`が`a.*?[bc]`のように誤ってファクタリングされることがなくなります。

### `src/regexp/syntax/parse_test.go`の変更点

*   `ax+y|ax+z|ay+w` のテストケースにおいて、期待されるASTが変更されました。以前は`cat{lit{a}alt{cat{plus{lit{x}}cc{0x79-0x7a}}cat{plus{lit{y}}lit{w}}}}`のようにファクタリングされていましたが、修正後は`cat{lit{a}alt{cat{plus{lit{x}}lit{y}}cat{plus{lit{x}}lit{z}}cat{plus{lit{y}}lit{w}}}}`となり、`a`の後の`x+`や`y+`がファクタリングされずに残るようになりました。これは、`x+`や`y+`が「単純なプレフィックス」ではないため、ファクタリングの対象外となったことを示しています。
*   `a.*?c|a.*?b` の新しいテストケースが追加されました。期待されるASTは`cat{lit{a}alt{cat{nstar{dot{}}lit{c}}cat{nstar{dot{}}lit{b}}}}`です。ここで注目すべきは、`a`はファクタリングされていますが、`.*?`はファクタリングされずに`alt`（選択肢）の中に残っている点です。これは、`.*?`が「単純なプレフィックス」ではないため、ファクタリングの新しい条件によって正しく処理されたことを示しています。

### `src/regexp/testdata/re2-search.txt`の変更点

*   `strings`セクションに`"abc"`が、`regexps`セクションに`"a.*?c|a.*?b"`が追加されました。
*   期待されるマッチ結果として`0-3;0-3;0-3;0-3`が指定されています。これは、入力文字列"abc"に対して正規表現`a.*?c|a.*?b`が"abc"全体（インデックス0から3まで）にマッチすることを意味します。このテストケースは、以前の誤ったファクタリング（`a.*?[bc]`が"ab"にマッチ）が修正され、左端優先マッチのセマンティクスに従って正しい結果が得られることを検証します。

これらの変更により、Goの正規表現エンジンは、複雑なパターンを含む場合でも、より正確なマッチング挙動を保証できるようになりました。

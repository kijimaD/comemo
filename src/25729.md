このコミットは、PICへの一般的なアプローチの最初の部分を含んでいます。必要に応じてPCをCXレジスタにロードします。これはバイナリを大きくし、パフォーマンスを低下させる可能性がありますが、始まりとしては正しく実装しやすいものです。

## 変更の背景

この変更の背景には、Goプログラムが共有ライブラリとしてビルドされる場合や、Position-Independent Executable (PIE) としてビルドされる場合の互換性と機能性の向上が挙げられます。特にLinux/386環境では、TLS (Thread-Local Storage) のアクセス方法やPICの実現方法に特有の課題があります。

従来のGoのリンカは、静的リンクされた実行ファイルを生成することを主眼に置いていました。しかし、現代のシステムでは、セキュリティ上の理由（ASLR: Address Space Layout Randomization）や、他の言語で書かれたコードとの連携のために、共有ライブラリやPIEのサポートが不可欠です。

TLSは、各スレッドが独自のデータインスタンスを持つことを可能にするメカニズムです。Goランタイムでは、`g` (goroutine構造体) などの重要なデータがTLSに格納されており、これに効率的にアクセスする必要があります。Linux/386環境では、TLSへのアクセスにはいくつかのモデルがあり、共有ライブラリやPIEでは「Initial Executable (IE) モデル」や「General Dynamic (GD) モデル」といった、より柔軟なアクセス方法が求められます。

また、PICは、実行ファイルや共有ライブラリがメモリ上の任意のアドレスにロードされても正しく動作するようにする技術です。これは、コード内の絶対アドレス参照を相対アドレス参照に置き換えることで実現されます。x86アーキテクチャ、特に32ビット環境では、PC (プログラムカウンタ) の値を取得して相対アドレスを計算する際に、特定の慣習や命令シーケンスが必要となります。

このコミットは、これらの課題に対処し、Goがより多様なビルドモードと実行環境をサポートできるようにするための重要な一歩です。

## 前提知識の解説

### Thread-Local Storage (TLS)

TLSは、マルチスレッドプログラミングにおいて、各スレッドが自分専用のグローバル変数を持つためのメカニズムです。これにより、スレッド間でデータを共有することなく、グローバル変数のようにアクセスできるため、競合状態の発生を防ぎ、プログラミングを簡素化できます。

Linux/x86環境では、TLSは通常、`FS`または`GS`セグメントレジスタを介してアクセスされます。これらのレジスタは、スレッド固有のデータ領域のベースアドレスを指すように設定されます。

TLSのアクセスモデルにはいくつか種類があります。

*   **Local Executable (LE) モデル**: 実行ファイル自体がTLS変数を定義し、他の共有ライブラリから参照されない場合に用いられます。最も効率的なアクセス方法で、通常は`mov %fs:offset, %reg`のような命令で直接アクセスします。
*   **Initial Executable (IE) モデル**: 実行ファイルと、それにリンクされる共有ライブラリの両方からTLS変数が参照される可能性がある場合に用いられます。このモデルでは、TLS変数のアドレスはGOT (Global Offset Table) を介して間接的に取得されます。
*   **General Dynamic (GD) モデル**: 最も汎用的なモデルで、TLS変数がどのモジュール（実行ファイルか共有ライブラリか）で定義されているかに関わらずアクセスできます。最も柔軟ですが、最もオーバーヘッドが大きいです。

このコミットでは、IEモデルのサポートが追加されています。

### Position-Independent Code (PIC)

PICは、実行ファイルや共有ライブラリがメモリ上の任意のアドレスにロードされても正しく動作するコードのことです。これは、ASLR (Address Space Layout Randomization) のようなセキュリティ機能や、共有ライブラリの効率的な利用に不可欠です。

PICを実現するためには、コード内の絶対アドレス参照を避ける必要があります。代わりに、相対アドレス参照や、GOT (Global Offset Table) およびPLT (Procedure Linkage Table) を使用して、実行時にアドレスを解決します。

x86アーキテクチャ、特に32ビット環境では、PC (プログラムカウンタ) の値を取得する標準的な方法として、`call`命令を利用するテクニックがよく用いられます。`call`命令は、次の命令のアドレスをスタックにプッシュしてからジャンプするため、その直後に`pop`命令を実行することでPCの値をレジスタにロードできます。

### ELF Relocation Types (R_TLS_LE, R_TLS_IE)

ELF (Executable and Linkable Format) は、Unix系システムで広く使われている実行ファイル、共有ライブラリ、オブジェクトファイルのフォーマットです。ELFファイルには、プログラムがロードされる際にアドレスを修正するための「再配置 (relocation)」情報が含まれています。

TLSに関連する再配置タイプには以下のようなものがあります。

*   **R_386_TLS_LE**: LEモデルのTLS変数へのアクセスに使用されます。リンカは、TLS変数のオフセットを直接命令に埋め込みます。
*   **R_386_TLS_IE**: IEモデルのTLS変数へのアクセスに使用されます。リンカは、GOT内のエントリへのオフセットを計算し、実行時にそのエントリを介してTLS変数のアドレスを取得します。

このコミットでは、`R_TLS_IE`という新しい再配置タイプが導入され、その処理がリンカに追加されています。

### `__x86.get_pc_thunk.cx`

これは、x86 32ビット環境でPC (プログラムカウンタ) の値を取得するための一般的な慣用句です。`call`命令を利用してPCをスタックにプッシュし、その後`pop %ecx`で`ECX`レジスタにPCの値をロードします。この関数は、PICを生成する際に、現在の命令ポインタからの相対オフセットを計算するために使用されます。

## 技術的詳細

このコミットは、主にGoのコンパイラバックエンド (`cmd/internal/obj/x86`) とリンカ (`cmd/link/internal/x86`) に変更を加えています。

### `src/cmd/internal/obj/x86/asm6.go` の変更

このファイルは、Goのアセンブラがx86命令を生成する際のロジックを含んでいます。

*   **TLSアクセス命令の変更**:
    *   `prefixof`関数内で、`a.Index == REG_TLS` (TLSレジスタへのアクセス) かつ `ctxt.Flag_shared != 0` (共有ライブラリとしてビルドされている場合) の条件が追加されました。
    *   この条件下では、`MOVL 0(CX)(TLS*1), AX`のような命令が`mov %gs:(%ecx), %eax`に変換されるようになります。これは、`%ecx`に正しいTLSオフセットがロードされていることを前提としています。この場合、セグメントプリフィックス`0x65` (GS) が付加されます。
    *   `a.Offset != 0`の場合に`ctxt.Diag("cannot handle non-0 offsets to TLS")`という診断メッセージが出力されるようになり、現時点ではTLS変数への非ゼロオフセットアクセスがサポートされていないことが示唆されています。
*   **`vaddr`関数における再配置タイプの条件付き設定**:
    *   `r.Type = obj.R_TLS_LE`の設定が`ctxt.Flag_shared == 0`の条件の下に移動しました。これは、共有ライブラリとしてビルドされていない場合にのみLEモデルの再配置を使用することを示しています。共有ライブラリの場合は、後述のIEモデルの再配置が使用されます。
*   **`doasm`関数における`MOV TLS, R_to`命令の処理**:
    *   `obj.AAS` (アセンブラ命令) が`obj.ATLS` (TLSアクセス命令) の場合、`ctxt.Flag_shared != 0`の条件分岐が追加されました。
    *   共有ライブラリとしてビルドされている場合、`MOV TLS, R_to`命令は以下のような命令シーケンスに変換されます。
        1.  `call __x86.get_pc_thunk.cx`: PCをCXレジスタにロードするための呼び出し。
        2.  `movl (gotpc + g@gotntpoff)(%ecx),$R_To`: GOT (Global Offset Table) を介してTLS変数のアドレスを取得し、`R_to`レジスタにロードします。
    *   このシーケンスには、`R_CALL`と`R_TLS_IE`の再配置が関連付けられます。`R_CALL`は`__x86.get_pc_thunk.cx`への呼び出しを解決し、`R_TLS_IE`はTLS変数のアドレス解決を処理します。
    *   `ctxt.Flag_shared == 0`の場合は、従来の`GS`セグメントレジスタを介した直接アクセスが維持されます。

### `src/cmd/link/internal/ld/lib.go` の変更

*   `stkcheck`関数内で、外部関数呼び出しの診断ロジックに`Buildmode != BuildmodePIE`という条件が追加されました。これは、PIEモードでビルドされている場合には、特定の外部関数呼び出しに関する診断を抑制することを示唆しています。PIEでは、外部シンボルへの参照がGOTを介して行われるため、静的リンクの場合とは異なる扱いが必要になることがあります。

### `src/cmd/link/internal/x86/asm.go` の変更

このファイルは、x86アーキテクチャ固有のリンカのロジックを含んでいます。

*   **`gentext`関数における`__x86.get_pc_thunk.cx`の生成**:
    *   `ld.DynlinkingGo()` (Goが動的リンクされている場合) または `ld.Buildmode == ld.BuildmodePIE` (PIEモードでビルドされている場合) の条件が追加されました。
    *   これらの条件下で、`__x86.get_pc_thunk.cx`というシンボルがリンカによって生成されます。この関数は、以下のx86アセンブリ命令で構成されます。
        *   `8b 0c 24` (`mov (%esp),%ecx`): スタックトップ（`call`命令によってプッシュされたリターンアドレス、すなわちPC）を`ECX`レジスタに移動します。
        *   `c3` (`ret`): 関数からリターンします。
    *   この関数は、PICを生成する際に、現在の命令ポインタを`ECX`レジスタにロードするために使用されます。
*   **`elfreloc1`関数における`R_TLS_IE`の処理**:
    *   `obj.R_TLS_IE`という新しい再配置タイプに対するケースが追加されました。
    *   この再配置タイプは、`R_386_GOTPC`と`R_386_TLS_GOTIE`というELF再配置タイプに変換されます。これらは、GOTを介してTLS変数のアドレスを取得するためのものです。

### `src/cmd/link/internal/x86/obj.go` の変更

*   **`archinit`関数におけるリンクモードの設定**:
    *   `ld.Buildmode == ld.BuildmodeCShared` (C共有ライブラリとしてビルドされている場合)、`ld.Buildmode == ld.BuildmodePIE` (PIEとしてビルドされている場合)、または`ld.DynlinkingGo()` のいずれかの条件が満たされた場合、`ld.Linkmode`が`ld.LinkExternal`に設定されます。これは、外部リンカを使用することを示唆しています。
    *   また、`_GLOBAL_OFFSET_TABLE_`シンボルが`obj.SDYNIMPORT` (動的インポートシンボル) としてリンカに登録され、`Reachable`が`true`に設定されます。これは、GOTが動的リンクにおいて重要な役割を果たすためです。

これらの変更により、GoはLinux/386環境で共有ライブラリやPIEとしてビルドされた際に、TLS変数に正しくアクセスし、位置独立なコードを生成できるようになります。ただし、コミットメッセージにもあるように、PCをCXレジスタにロードするアプローチは、バイナリサイズの増大やパフォーマンスの低下を招く可能性があるというトレードオフがあります。これは、より洗練されたPIC生成メカニズムが将来的に導入されるまでの暫定的な解決策と考えられます。

## コアとなるコードの解説

### `src/cmd/internal/obj/x86/asm6.go`

*   **`prefixof`関数**: この変更は、共有ライブラリとしてビルドされるGoプログラムがTLS変数にアクセスする際に、`GS`セグメントプリフィックスを使用するように指示します。これは、Linux/386におけるIEモデルTLSアクセスの一部です。`MOVL 0(CX)(TLS*1), AX`のような抽象的な命令が、`mov %gs:(%ecx), %eax`のような具体的なアセンブリ命令に変換されることを意図しています。`%ecx`には、`__x86.get_pc_thunk.cx`によってロードされたPC値が格納され、これを用いてGOTからのオフセット計算が行われます。
*   **`vaddr`関数**: `r.Type = obj.R_TLS_LE`の行が`if ctxt.Flag_shared == 0`ブロック内に移動したことで、LEモデルのTLS再配置は静的リンクされたバイナリに限定されるようになりました。共有ライブラリの場合は、後述の`R_TLS_IE`が使用されます。
*   **`doasm`関数**: `MOV TLS, R_to`というGoアセンブリ命令が、共有ライブラリビルド時 (`ctxt.Flag_shared != 0`) に特別な処理を受けるようになりました。
    *   まず、`call __x86.get_pc_thunk.cx`命令が挿入されます。これにより、現在のPCが`ECX`レジスタにロードされます。
    *   次に、`movl (gotpc + g@gotntpoff)(%ecx),$R_To`に相当する命令が生成されます。これは、`ECX`レジスタに格納されたPC値と、`g@gotntpoff` (TLS変数`g`のGOTエントリへのオフセット) を用いて、TLS変数のアドレスを計算し、`R_to`レジスタにロードします。
    *   この命令シーケンスには、`R_CALL` (関数呼び出しの解決) と`R_TLS_IE` (IEモデルTLSの解決) の2つの再配置が関連付けられます。これにより、実行時にTLS変数の正しいアドレスが解決されます。

### `src/cmd/link/internal/x86/asm.go`

*   **`gentext`関数**: この関数は、Goのリンカがテキストセクション（コード）を生成する際に呼び出されます。この変更により、Goが動的リンクされる場合やPIEモードでビルドされる場合に、`__x86.get_pc_thunk.cx`という特別な関数が生成されるようになりました。この関数は、`mov (%esp),%ecx`と`ret`という非常に短いアセンブリ命令で構成され、`call`命令によってスタックにプッシュされたリターンアドレス（PC）を`ECX`レジスタにロードする役割を果たします。これは、x86 32ビット環境でPICを生成する際の標準的な手法です。
*   **`elfreloc1`関数**: この関数は、ELF再配置エントリを生成する際に呼び出されます。`obj.R_TLS_IE`という新しいGo固有の再配置タイプが追加され、これがELFの`R_386_GOTPC`と`R_386_TLS_GOTIE`という再配置タイプに変換されるようになりました。`R_386_TLS_GOTIE`は、IEモデルのTLS変数へのアクセスを解決するために使用されるELF再配置タイプです。

### `src/cmd/link/internal/x86/obj.go`

*   **`archinit`関数**: リンカの初期化時に呼び出されるこの関数は、GoがC共有ライブラリ、PIE、または動的リンクモードでビルドされる場合に、リンクモードを`LinkExternal`に設定するようになりました。これは、Goの内部リンカではなく、システムの外部リンカ（例: `ld`）を使用して最終的なバイナリを生成することを示唆しています。また、`_GLOBAL_OFFSET_TABLE_`シンボルを動的インポートとしてマークすることで、外部リンカがGOTを正しく処理できるようにします。

これらの変更は、GoがLinux/386環境でより柔軟なビルドモード（共有ライブラリ、PIE）をサポートするための基盤を築くものです。特に、TLS変数へのアクセスとPICの生成という、低レベルなアセンブリとリンカの挙動に関わる重要な側面が改善されています。

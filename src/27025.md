# [インデックス 27025] ファイルの概要

このコミットは、Goリンカーにおける文字列マージ処理を廃止し、その代わりにバイナリサイズへの影響を最小限に抑えるための2つの最適化を導入するものです。これにより、リンカーの速度が大幅に向上し、Goプログラムのビルド時間が短縮されます。

## コミット

```
cmd/compile, cmd/link: eliminate string merging pass

Deleting the string merging pass makes the linker 30-35% faster
but makes jujud (using the github.com/davecheney/benchjuju snapshot) 2.5% larger.
Two optimizations bring the space overhead down to 0.6%.

First, change the default alignment for string data to 1 byte.
(It was previously defaulting to larger amounts, usually pointer width.)

Second, write out the type string for T (usually a bigger expression) as "*T"[1:],
so that the type strings for T and *T share storage.

Combined, these obtain the bulk of the benefit of string merging
at essentially no cost. The remaining benefit from string merging
is not worth the excessive cost, so delete it.

As penance for making the jujud binary 0.6% larger,
the next CL in this sequence trims the reflect functype
information enough to make the jujud binary overall 0.75% smaller
(that is, that CL has a net -1.35% effect).

Fixes #14648.

## 元コミット内容

このコミットは、Goコンパイラとリンカーにおける文字列マージの処理を削除し、その影響を緩和するための代替最適化を導入します。具体的には、以下の変更が含まれます。

1.  **文字列マージパスの削除**: リンカーから文字列マージを行うパス（`mergestrings.go`）が完全に削除されました。これにより、リンカーの処理速度が30-35%向上します。
2.  **文字列データのアライメント変更**: 文字列データ（`go.string.`で始まるシンボル）のデフォルトアライメントが1バイトに変更されました。これにより、パディングによるメモリの無駄が削減されます。
3.  **型文字列のストレージ共有**: 型`T`とポインタ型`*T`の型文字列がストレージを共有するように最適化されました。具体的には、`T`の型文字列を`"*T"[1:]`として表現することで、`*T`の文字列データの一部を再利用します。
4.  **新しいシンボルタイプの導入**: `SGOSTRINGHDR`および`SGOSTRINGHDRRELRO`という新しいシンボルタイプが導入され、文字列ヘッダの扱いが明確化されました。

これらの変更により、文字列マージパスの削除によって発生するバイナリサイズの増加（`jujud`バイナリで2.5%）が、0.6%にまで抑制されています。

## 変更の背景

Goのリンカーには、バイナリサイズを削減するために重複する文字列リテラルをマージする「文字列マージパス」が存在していました。しかし、このパスはリンカーの処理時間を大幅に増加させるという問題がありました。特に大規模なプロジェクトでは、ビルド時間のボトルネックとなることが指摘されていました（関連Issue: #6853）。

このコミットの目的は、リンカーの速度を向上させることでした。文字列マージパスを削除することで、リンカーの処理速度は劇的に改善されますが、その代償として生成されるバイナリのサイズが増加する可能性があります。このバイナリサイズの増加を最小限に抑えつつ、リンカーの高速化という主要な目標を達成するために、代替の最適化手法が検討・導入されました。

コミットメッセージでは、`jujud`という特定のベンチマークバイナリを例に挙げ、文字列マージパス削除によるサイズ増加が2.5%であったこと、そして導入された2つの最適化によってその増加が0.6%にまで抑えられたことが説明されています。さらに、残りの文字列マージのメリットは、その処理コストに見合わないと判断され、パスの削除が決定されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部動作に関する知識が必要です。

1.  **Goリンカー (cmd/link)**: Goプログラムのコンパイルプロセスにおいて、コンパイラ（`cmd/compile`）によって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。リンカーは、シンボルの解決、メモリレイアウトの決定、リロケーションの適用など、様々な最適化を行います。
2.  **シンボル (Symbol)**: プログラム内の変数、関数、型などの名前付きエンティティを表すものです。リンカーはこれらのシンボルを管理し、参照を解決します。Goのリンカーでは、`LSym`構造体がシンボルを表し、その`Type`フィールドはシンボルの種類（例: `STEXT`はコード、`SRODATA`は読み取り専用データ）を示します。
3.  **文字列リテラルとバイナリサイズ**: Goプログラム内で使用される文字列リテラル（例: `"hello"`）は、コンパイル時にバイナリのデータセクションに格納されます。同じ文字列リテラルが複数回出現する場合、リンカーはそれらを一つにまとめて（マージして）バイナリサイズを削減する最適化を行うことがあります。
4.  **データアライメント (Data Alignment)**: メモリ上のデータが特定のバイト境界に配置されることを指します。CPUは通常、特定のバイト境界にアライメントされたデータにアクセスする方が高速です。しかし、アライメント要件を満たすために、データの間にパディング（未使用のバイト）が挿入されることがあり、これがバイナリサイズを増加させる要因となります。
5.  **Goの型システムとリフレクション**: Goは強力なリフレクション機能を持っており、実行時に型の情報を取得・操作できます。この型情報は、バイナリ内に型記述文字列として格納されます。例えば、`int`型は`"int"`、`*string`型は`"*string"`といった文字列で表現されます。これらの型文字列もバイナリサイズに影響を与えます。
6.  **`go.string.`シンボル**: Goのリンカーが内部的に生成するシンボルで、文字列リテラルのデータ本体を表します。`go.string.hdr.`は文字列のヘッダ（ポインタと長さ）を表すシンボルです。
7.  **`obj.FmtLeft|obj.FmtUnsigned`**: `Tconv`関数に渡されるフラグで、型を文字列に変換する際のフォーマット指定です。`FmtLeft`は左寄せ、`FmtUnsigned`は符号なし整数として扱うことを示唆します。

## 技術的詳細

このコミットは、リンカーのパフォーマンスとバイナリサイズのバランスを取るためのトレードオフの決定と、それを実現するための巧妙な最適化を含んでいます。

### 文字列マージパスの削除

Goリンカーの`src/cmd/link/internal/ld/mergestrings.go`に実装されていた文字列マージパスは、バイナリ内の重複する文字列リテラルを検出し、それらを単一のインスタンスに置き換えることでバイナリサイズを削減していました。このプロセスは、すべての文字列データを収集し、サフィックス配列（`index/suffixarray`パッケージを使用）を構築して共通のサブストリングを効率的に検索するという、計算コストの高いものでした。

このコミットでは、この`mergestrings.go`ファイルが完全に削除され、`src/cmd/link/internal/ld/pobj.go`内の`Ldmain`関数から`mergestrings()`の呼び出しも削除されました。これにより、リンカーは文字列マージのための複雑な処理を行う必要がなくなり、その結果としてリンカーの実行時間が30-35%短縮されました。

### 文字列データのアライメント変更 (1バイトアライメント)

文字列データは本質的にバイトのシーケンスであり、特定のCPUアーキテクチャのワードサイズ（例: 4バイトや8バイト）にアライメントする必要は必ずしもありません。以前は、文字列データもデフォルトでポインタ幅などの大きなアライメントが適用されることがあり、これにより文字列の間に不要なパディングバイトが挿入され、バイナリサイズが増加していました。

このコミットでは、`src/cmd/link/internal/ld/data.go`の`symalign`関数が変更され、`go.string.`で始まるシンボル（ただし`go.string.hdr.`を除く）に対して、アライメントを明示的に1バイトに設定するロジックが追加されました。

```go
if strings.HasPrefix(s.Name, "go.string.") && !strings.HasPrefix(s.Name, "go.string.hdr.") {
    // String data is just bytes.
    // If we align it, we waste a lot of space to padding.
    return 1
}
```

これにより、文字列データは最小限の1バイト境界に配置されるようになり、パディングによるスペースの無駄が大幅に削減され、バイナリサイズの増加を抑制します。

### 型文字列のストレージ共有

Goのリフレクション機能は、実行時に型の情報を利用するために、型名を文字列としてバイナリに格納します。例えば、`int`と`*int`という2つの型がある場合、以前は`"int"`と`"*int"`という2つの異なる文字列が格納されていました。

このコミットでは、`src/cmd/compile/internal/gc/reflect.go`の`dcommontype`関数が変更され、型`T`の文字列を生成する際に、`"*T"`という文字列のサブストリングとして表現する工夫が導入されました。

具体的には、型`T`の文字列`p`を生成する際に、まず`"*"+p`という文字列を作成し、その文字列の2文字目以降（`[1:]`）を`T`の型文字列として参照するようにします。これにより、`T`と`*T`の型文字列が共通の基底文字列`"*T"`のストレージを共有できるようになります。

```go
// If we're writing out type T,
// we are very likely to write out type *T as well.
// Use the string "*T"[1:] for "T", so that the two
// share storage. This is a cheap way to reduce the
// amount of space taken up by reflect strings.
prefix := 0
if !strings.HasPrefix(p, "*") {
    p = "*" + p
    prefix = 1
}
_, symdata := stringsym(p) // string
ot = dsymptr(s, ot, symdata, prefix) // prefixをオフセットとして渡す
ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint) // 長さも調整
```

この最適化は、特にポインタ型が頻繁に登場するGoのコードベースにおいて、リフレクション関連の型文字列が占めるスペースを効果的に削減します。

### 新しいシンボルタイプ `SGOSTRINGHDR` の導入

`src/cmd/internal/obj/link.go`では、`SGOSTRINGHDR`と`SGOSTRINGHDRRELRO`という新しいシンボルタイプが追加されました。これらは、Goの文字列ヘッダ（文字列のポインタと長さを含む構造体）を表すために使用されます。

`src/cmd/link/internal/ld/symtab.go`では、`go.string.hdr.`で始まるシンボルに対して`SGOSTRINGHDR`タイプを割り当てるロジックが追加され、`src/cmd/link/internal/ld/data.go`や`src/cmd/link/internal/ld/lib.go`でもこれらの新しいシンボルタイプが適切に処理されるように更新されています。これにより、文字列データ本体と文字列ヘッダが区別され、リンカーがより細かく最適化を適用できるようになります。

これらの変更は、文字列マージパスの削除によるバイナリサイズ増加を相殺し、リンカーの高速化という主要な目標を達成するための、Goリンカーの内部構造に対する重要な改善です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go` の変更

```go
 // If we're writing out type T,
 // we are very likely to write out type *T as well.
 // Use the string "*T"[1:] for "T", so that the two
 // share storage. This is a cheap way to reduce the
 // amount of space taken up by reflect strings.
 prefix := 0
 if !strings.HasPrefix(p, "*") {
     p = "*" + p
     prefix = 1
 }
 _, symdata := stringsym(p) // string
 ot = dsymptr(s, ot, symdata, prefix)
 ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint)
```

このコードブロックは、Goのリフレクションで使用される型文字列の格納方法を最適化しています。
`p`は現在の型`T`の文字列表現です。
1.  `if !strings.HasPrefix(p, "*")`: もし型文字列`p`がポインタ型（`*`で始まる）でなければ、
    *   `p = "*" + p`: `p`の前に`*`を付加して、一時的に`*T`のような文字列を作成します。
    *   `prefix = 1`: `prefix`を1に設定します。これは、元の型`T`の文字列が、この新しい`*T`文字列の2文字目（インデックス1）から始まることを示します。
2.  `_, symdata := stringsym(p)`: 変更された`p`（`*T`形式）に対応するシンボルデータを取得します。これにより、`*T`の文字列データがリンカーによって管理されます。
3.  `ot = dsymptr(s, ot, symdata, prefix)`: シンボル`s`に、`symdata`へのポインタを書き込みます。ここで重要なのは`prefix`がオフセットとして渡されることです。`prefix`が1の場合、ポインタは`symdata`の先頭から1バイトオフセットされた位置を指すようになります。つまり、`T`の型文字列は`*T`の文字列データの一部を指すことになります。
4.  `ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint)`: 型文字列の長さを書き込みます。`len(p)-prefix`とすることで、`*T`の文字列から`*`を除いた、元の`T`の文字列の正しい長さが記録されます。

このメカニズムにより、`T`と`*T`の型文字列がバイナリ内で同じ基底文字列データ（`*T`のデータ）を共有し、メモリ使用量を削減します。

### `src/cmd/link/internal/ld/data.go` の `symalign` 関数の変更

```go
 if strings.HasPrefix(s.Name, "go.string.") && !strings.HasPrefix(s.Name, "go.string.hdr.") {
     // String data is just bytes.
     // If we align it, we waste a lot of space to padding.
     return 1
 }
```

このコードは、リンカーがシンボルのアライメントを決定する`symalign`関数内にあります。
*   `strings.HasPrefix(s.Name, "go.string.")`: シンボル名が`go.string.`で始まるかどうかをチェックします。これはGoの文字列リテラルデータを示すシンボルです。
*   `!strings.HasPrefix(s.Name, "go.string.hdr.")`: ただし、文字列ヘッダ（`go.string.hdr.`）ではないことを確認します。文字列ヘッダはポインタと長さを保持するため、通常のアライメントが必要です。
*   上記の条件が満たされた場合、`return 1`によって、そのシンボル（文字列データ本体）のアライメントが1バイトに設定されます。これにより、文字列データはメモリ上で密に配置され、パディングによる無駄がなくなります。

## 変更の背景

Goのリンカーには、バイナリサイズを削減するために重複する文字列リテラルをマージする「文字列マージパス」が存在していました。しかし、このパスはリンカーの処理時間を大幅に増加させるという問題がありました。特に大規模なプロジェクトでは、ビルド時間のボトルネックとなることが指摘されていました（関連Issue: #6853）。

このコミットの目的は、リンカーの速度を向上させることでした。文字列マージパスを削除することで、リンカーの処理速度は劇的に改善されますが、その代償として生成されるバイナリのサイズが増加する可能性があります。このバイナリサイズの増加を最小限に抑えつつ、リンカーの高速化という主要な目標を達成するために、代替の最適化手法が検討・導入されました。

コミットメッセージでは、`jujud`という特定のベンチマークバイナリを例に挙げ、文字列マージパス削除によるサイズ増加が2.5%であったこと、そして導入された2つの最適化によってその増加が0.6%にまで抑えられたことが説明されています。さらに、残りの文字列マージのメリットは、その処理コストに見合わないと判断され、パスの削除が決定されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部動作に関する知識が必要です。

1.  **Goリンカー (cmd/link)**: Goプログラムのコンパイルプロセスにおいて、コンパイラ（`cmd/compile`）によって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。リンカーは、シンボルの解決、メモリレイアウトの決定、リロケーションの適用など、様々な最適化を行います。
2.  **シンボル (Symbol)**: プログラム内の変数、関数、型などの名前付きエンティティを表すものです。リンカーはこれらのシンボルを管理し、参照を解決します。Goのリンカーでは、`LSym`構造体がシンボルを表し、その`Type`フィールドはシンボルの種類（例: `STEXT`はコード、`SRODATA`は読み取り専用データ）を示します。
3.  **文字列リテラルとバイナリサイズ**: Goプログラム内で使用される文字列リテラル（例: `"hello"`）は、コンパイル時にバイナリのデータセクションに格納されます。同じ文字列リテラルが複数回出現する場合、リンカーはそれらを一つにまとめて（マージして）バイナリサイズを削減する最適化を行うことがあります。
4.  **データアライメント (Data Alignment)**: メモリ上のデータが特定のバイト境界に配置されることを指します。CPUは通常、特定のバイト境界にアライメントされたデータにアクセスする方が高速です。しかし、アライメント要件を満たすために、データの間にパディング（未使用のバイト）が挿入されることがあり、これがバイナリサイズを増加させる要因となります。
5.  **Goの型システムとリフレクション**: Goは強力なリフレクション機能を持っており、実行時に型の情報を取得・操作できます。この型情報は、バイナリ内に型記述文字列として格納されます。例えば、`int`型は`"int"`、`*string`型は`"*string"`といった文字列で表現されます。これらの型文字列もバイナリサイズに影響を与えます。
6.  **`go.string.`シンボル**: Goのリンカーが内部的に生成するシンボルで、文字列リテラルのデータ本体を表します。`go.string.hdr.`は文字列のヘッダ（ポインタと長さ）を表すシンボルです。
7.  **`obj.FmtLeft|obj.FmtUnsigned`**: `Tconv`関数に渡されるフラグで、型を文字列に変換する際のフォーマット指定です。`FmtLeft`は左寄せ、`FmtUnsigned`は符号なし整数として扱うことを示唆します。

## 技術的詳細

このコミットは、リンカーのパフォーマンスとバイナリサイズのバランスを取るためのトレードオフの決定と、それを実現するための巧妙な最適化を含んでいます。

### 文字列マージパスの削除

Goリンカーの`src/cmd/link/internal/ld/mergestrings.go`に実装されていた文字列マージパスは、バイナリ内の重複する文字列リテラルを検出し、それらを単一のインスタンスに置き換えることでバイナリサイズを削減していました。このプロセスは、すべての文字列データを収集し、サフィックス配列（`index/suffixarray`パッケージを使用）を構築して共通のサブストリングを効率的に検索するという、計算コストの高いものでした。

このコミットでは、この`mergestrings.go`ファイルが完全に削除され、`src/cmd/link/internal/ld/pobj.go`内の`Ldmain`関数から`mergestrings()`の呼び出しも削除されました。これにより、リンカーは文字列マージのための複雑な処理を行う必要がなくなり、その結果としてリンカーの実行時間が30-35%短縮されました。

### 文字列データのアライメント変更 (1バイトアライメント)

文字列データは本質的にバイトのシーケンスであり、特定のCPUアーキテクチャのワードサイズ（例: 4バイトや8バイト）にアライメントする必要は必ずしもありません。以前は、文字列データもデフォルトでポインタ幅などの大きなアライメントが適用されることがあり、これにより文字列の間に不要なパディングバイトが挿入され、バイナリサイズが増加していました。

このコミットでは、`src/cmd/link/internal/ld/data.go`の`symalign`関数が変更され、`go.string.`で始まるシンボル（ただし`go.string.hdr.`を除く）に対して、アライメントを明示的に1バイトに設定するロジックが追加されました。

```go
if strings.HasPrefix(s.Name, "go.string.") && !strings.HasPrefix(s.Name, "go.string.hdr.") {
    // String data is just bytes.
    // If we align it, we waste a lot of space to padding.
    return 1
}
```

これにより、文字列データは最小限の1バイト境界に配置されるようになり、パディングによるスペースの無駄が大幅に削減され、バイナリサイズの増加を抑制します。

### 型文字列のストレージ共有

Goのリフレクション機能は、実行時に型の情報を利用するために、型名を文字列としてバイナリに格納します。例えば、`int`と`*int`という2つの型がある場合、以前は`"int"`と`"*int"`という2つの異なる文字列が格納されていました。

このコミットでは、`src/cmd/compile/internal/gc/reflect.go`の`dcommontype`関数が変更され、型`T`の文字列を生成する際に、`"*T"`という文字列のサブストリングとして表現する工夫が導入されました。

具体的には、型`T`の文字列`p`を生成する際に、まず`"*"+p`という文字列を作成し、その文字列の2文字目以降（`[1:]`）を`T`の型文字列として参照するようにします。これにより、`T`と`*T`の型文字列が共通の基底文字列`"*T"`のストレージを共有できるようになります。

```go
// If we're writing out type T,
// we are very likely to write out type *T as well.
// Use the string "*T"[1:] for "T", so that the two
// share storage. This is a cheap way to reduce the
// amount of space taken up by reflect strings.
prefix := 0
if !strings.HasPrefix(p, "*") {
    p = "*" + p
    prefix = 1
}
_, symdata := stringsym(p) // string
ot = dsymptr(s, ot, symdata, prefix) // prefixをオフセットとして渡す
ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint) // 長さも調整
```

この最適化は、特にポインタ型が頻繁に登場するGoのコードベースにおいて、リフレクション関連の型文字列が占めるスペースを効果的に削減します。

### 新しいシンボルタイプ `SGOSTRINGHDR` の導入

`src/cmd/internal/obj/link.go`では、`SGOSTRINGHDR`と`SGOSTRINGHDRRELRO`という新しいシンボルタイプが追加されました。これらは、Goの文字列ヘッダ（文字列のポインタと長さを含む構造体）を表すために使用されます。

`src/cmd/link/internal/ld/symtab.go`では、`go.string.hdr.`で始まるシンボルに対して`SGOSTRINGHDR`タイプを割り当てるロジックが追加され、`src/cmd/link/internal/ld/data.go`や`src/cmd/link/internal/ld/lib.go`でもこれらの新しいシンボルタイプが適切に処理されるように更新されています。これにより、文字列データ本体と文字列ヘッダが区別され、リンカーがより細かく最適化を適用できるようになります。

これらの変更は、文字列マージパスの削除によるバイナリサイズ増加を相殺し、リンカーの高速化という主要な目標を達成するための、Goリンカーの内部構造に対する重要な改善です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go` の変更

```go
 // If we're writing out type T,
 // we are very likely to write out type *T as well.
 // Use the string "*T"[1:] for "T", so that the two
 // share storage. This is a cheap way to reduce the
 // amount of space taken up by reflect strings.
 prefix := 0
 if !strings.HasPrefix(p, "*") {
     p = "*" + p
     prefix = 1
 }
 _, symdata := stringsym(p) // string
 ot = dsymptr(s, ot, symdata, prefix)
 ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint)
```

このコードブロックは、Goのリフレクションで使用される型文字列の格納方法を最適化しています。
`p`は現在の型`T`の文字列表現です。
1.  `if !strings.HasPrefix(p, "*")`: もし型文字列`p`がポインタ型（`*`で始まる）でなければ、
    *   `p = "*" + p`: `p`の前に`*`を付加して、一時的に`*T`のような文字列を作成します。
    *   `prefix = 1`: `prefix`を1に設定します。これは、元の型`T`の文字列が、この新しい`*T`文字列の2文字目（インデックス1）から始まることを示します。
2.  `_, symdata := stringsym(p)`: 変更された`p`（`*T`形式）に対応するシンボルデータを取得します。これにより、`*T`の文字列データがリンカーによって管理されます。
3.  `ot = dsymptr(s, ot, symdata, prefix)`: シンボル`s`に、`symdata`へのポインタを書き込みます。ここで重要なのは`prefix`がオフセットとして渡されることです。`prefix`が1の場合、ポインタは`symdata`の先頭から1バイトオフセットされた位置を指すようになります。つまり、`T`の型文字列は`*T`の文字列データの一部を指すことになります。
4.  `ot = duintxx(s, ot, uint64(len(p)-prefix), Widthint)`: 型文字列の長さを書き込みます。`len(p)-prefix`とすることで、`*T`の文字列から`*`を除いた、元の`T`の文字列の正しい長さが記録されます。

このメカニズムにより、`T`と`*T`の型文字列がバイナリ内で同じ基底文字列データ（`*T`のデータ）を共有し、メモリ使用量を削減します。

### `src/cmd/link/internal/ld/data.go` の `symalign` 関数の変更

```go
 if strings.HasPrefix(s.Name, "go.string.") && !strings.HasPrefix(s.Name, "go.string.hdr.") {
     // String data is just bytes.
     // If we align it, we waste a lot of space to padding.
     return 1
 }
```

このコードは、リンカーがシンボルのアライメントを決定する`symalign`関数内にあります。
*   `strings.HasPrefix(s.Name, "go.string.")`: シンボル名が`go.string.`で始まるかどうかをチェックします。これはGoの文字列リテラルデータを示すシンボルです。
*   `!strings.HasPrefix(s.Name, "go.string.hdr.")`: ただし、文字列ヘッダ（`go.string.hdr.`）ではないことを確認します。文字列ヘッダはポインタと長さを保持するため、通常のアライメントが必要です。
*   上記の条件が満たされた場合、`return 1`によって、そのシンボル（文字列データ本体）のアライメントが1バイトに設定されます。これにより、文字列データはメモリ上で密に配置され、パディングによる無駄がなくなります。

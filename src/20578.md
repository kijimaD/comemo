# [インデックス 20578] ファイルの概要

このコミットは、Go言語の標準ライブラリ `path/filepath` パッケージ内の `Glob` 関数に関するものです。具体的には、`Glob` 関数がディレクトリの読み取り中に発生するI/Oエラーを無視するという動作を明示的にドキュメントに追加し、その動作をコード上でより明確にする変更を行っています。これにより、`Glob` 関数の挙動に関する誤解を防ぎ、APIの意図を明確にすることが目的です。

## 元コミット内容

`path/filepath` パッケージの `Glob` 関数がI/Oエラーを無視するという動作をドキュメントに追記する。Issue #8008 を修正する。

## 変更の背景

この変更の背景には、`path/filepath.Glob` 関数の既存の挙動と、その挙動がドキュメントに明記されていなかったことによる潜在的な混乱があります。`Glob` 関数は、指定されたパターンに一致するファイルパスを検索する際に、内部でディレクトリの内容を読み取る操作（`os.File.Readdirnames` など）を行います。これらの操作中に、パーミッションの問題やディスクエラーといったI/Oエラーが発生する可能性があります。

コミットメッセージにある "Fixes #8008" は、この変更が特定の課題（Issue 8008）を解決するために行われたことを示唆しています。GoのIssueトラッカーで直接Issue 8008を見つけることは困難でしたが、コミット内容から推測すると、このIssueは `Glob` 関数がI/Oエラーをどのように扱うかについて、ユーザーが混乱したり、予期しない動作に遭遇したりしたことに関連していると考えられます。

具体的には、`Glob` 関数は以前からディレクトリの読み取り中に発生したI/Oエラーを内部的に無視し、エラーを呼び出し元に伝播させない実装になっていました。しかし、この重要な挙動が関数のドキュメントに明記されていなかったため、ユーザーは `Glob` がI/Oエラーを返さないことに疑問を感じたり、エラーが発生した場合に `Glob` がどのように振る舞うべきかについて誤った期待を抱いたりする可能性がありました。

このコミットは、このギャップを埋め、`Glob` 関数の実際の挙動をドキュメントに正確に反映させることで、APIの透明性を高め、ユーザーの誤解を解消することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と標準ライブラリの知識が必要です。

*   **`path/filepath` パッケージ**: ファイルパスの操作、特にプラットフォームに依存しないパスの結合、クリーンアップ、そしてパターンマッチング（グロビング）機能を提供するパッケージです。
*   **`Glob` 関数**: `path/filepath` パッケージの主要な関数の一つで、シェルスタイルのパターン（例: `*.txt`, `dir/**/*.go`）に一致するファイルパスを検索し、そのリストを返します。この関数は、内部的にファイルシステムを走査して一致するパスを見つけます。
*   **`os` パッケージ**: オペレーティングシステムとのインタフェースを提供するパッケージです。ファイル操作、プロセス管理、環境変数へのアクセスなどが含まれます。
*   **`os.Lstat` 関数**: 指定されたパスのファイル情報を返します。シンボリックリンクの場合、リンク自体の情報を返します（リンク先の情報ではない）。
*   **`os.File.Readdirnames` メソッド**: `os.File` 型のメソッドで、ディレクトリの内容を読み取り、そのディレクトリ内のファイルおよびサブディレクトリの名前のリストを文字列スライスとして返します。引数に `-1` を指定すると、すべてのエントリを読み取ります。このメソッドは、読み取り中にエラーが発生する可能性があります。
*   **Go言語のエラーハンドリング**: Goでは、関数は通常、最後の戻り値として `error` 型の値を返します。`nil` はエラーがないことを意味し、非`nil` の `error` 値はエラーが発生したことを示します。
*   **ブランク識別子 (`_`)**: Go言語では、変数に代入された値を明示的に使用しない場合、コンパイルエラーになります。これを避けるために、使用しない戻り値や変数をブランク識別子 `_` に代入することができます。これは、その値を意図的に無視することを示します。

## 技術的詳細

このコミットの技術的な詳細は、`path/filepath.Glob` 関数の内部実装におけるエラーハンドリングの変更と、それに対応するドキュメントの更新に集約されます。

`Glob` 関数は、パターンマッチングのためにファイルシステムを再帰的に走査します。この走査の過程で、ディレクトリの内容を読み取るために `os.File.Readdirnames` メソッドが呼び出されます。`Readdirnames` は、ディレクトリの読み取り中に発生したI/Oエラー（例: アクセス拒否、ディレクトリが存在しない、ディスク障害など）を `error` 型の戻り値として返します。

変更前のコードでは、`names, err := d.Readdirnames(-1)` のように `err` 変数にエラーを受け取り、その後に `if err != nil { return }` のようにエラーをチェックし、エラーがあれば関数から早期リターンしていました。しかし、`Glob` 関数の設計意図としては、部分的なマッチングを可能にし、I/Oエラーによって全体の処理が中断されることを避けるべきであるという考えがあったと推測されます。つまり、特定のディレクトリが読み取れない場合でも、他のアクセス可能なディレクトリでパターンに一致するパスの検索を続行することが望ましいとされていました。

このコミットでは、この挙動を明示的にするために、`names, err := d.Readdirnames(-1)` の行が `names, _ := d.Readdirnames(-1)` に変更されました。これは、`Readdirnames` が返す `error` 値をブランク識別子 `_` に代入することで、そのエラーを意図的に無視することを示しています。これにより、`Readdirnames` がエラーを返しても、`Glob` 関数は処理を続行し、エラーを呼び出し元に伝播させなくなります。

同時に、この内部的な挙動の変更（または既存の挙動の明確化）に合わせて、`Glob` 関数のドキュメントが更新されました。ドキュメントには、「`Glob` はディレクトリの読み取り中のI/Oエラーのようなファイルシステムエラーを無視する」という記述が追加されました。これにより、ユーザーは `Glob` がI/Oエラーを返さないことを明確に理解できるようになります。`Glob` 関数が返す唯一のエラーは、パターン自体が不正な場合に発生する `ErrBadPattern` のみであることも明記されました。

この変更は、`Glob` 関数の堅牢性を高め、部分的なファイルシステムの問題があっても可能な限り多くのマッチング結果を返すという設計思想を強化するものです。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は2箇所です。

1.  **ドキュメントの追加 (L230-232)**:
    ```go
    // Glob ignores file system errors such as I/O errors reading directories.
    // The only possible returned error is ErrBadPattern, when pattern
    // is malformed.
    ```
    これは `Glob` 関数のコメントブロックに追加された新しい行です。このコメントは、`Glob` 関数がディレクトリの読み取り中に発生するI/Oエラー（例: パーミッションエラー、ディスク障害など）を意図的に無視するという重要な挙動を明記しています。また、`Glob` 関数がエラーを返すのは、パターン文字列自体が不正な形式である場合に限られる（`ErrBadPattern`）ことも明確にしています。これにより、APIの契約がより明確になり、ユーザーは `Glob` がファイルシステムエラーを伝播しないことを期待できるようになります。

2.  **エラー変数のブランク識別子への変更 (L286)**:
    ```diff
    -\tnames, err := d.Readdirnames(-1)
    -\tif err != nil {\n-\t\treturn\n-\t}\n+\tnames, _ := d.Readdirnames(-1)
    ```
    この変更は、`glob` 関数（`Glob` 関数から内部的に呼び出されるヘルパー関数）内で、ディレクトリの内容を読み取る `d.Readdirnames(-1)` の呼び出し箇所で行われています。
    *   変更前: `names, err := d.Readdirnames(-1)` と `if err != nil { return }` のように、`Readdirnames` が返すエラーを `err` 変数で受け取り、エラーが発生した場合は関数から早期リターンしていました。これは、エラーを処理しているように見えますが、実際には `glob` 関数が返す `e error` は、この `Readdirnames` のエラーとは直接関係なく、最終的に `Glob` 関数が返すエラーは `ErrBadPattern` のみでした。
    *   変更後: `names, _ := d.Readdirnames(-1)` と変更されました。ここで `_` (ブランク識別子) を使用することで、`Readdirnames` が返す `error` 値を明示的に破棄し、無視することを宣言しています。これにより、`Readdirnames` からエラーが返されても、`glob` 関数は処理を続行し、そのエラーを上位に伝播させないという `Glob` 関数の設計意図がコード上で明確に表現されています。

この2つの変更は連携しており、ドキュメントで宣言された `Glob` の挙動（I/Oエラーを無視する）を、実際のコードの変更によって裏付けています。これにより、コードとドキュメントの一貫性が保たれ、`Glob` 関数の動作がより予測可能になります。

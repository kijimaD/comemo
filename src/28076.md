## 変更の背景

このコミットは、`origin/master` ブランチからの大規模なマージであり、複数の機能追加、パフォーマンス改善、バグ修正、および新しいアーキテクチャサポートを統合することを目的としています。特に、Go ランタイムのメモリ管理とガベージコレクションは、Go アプリケーションのパフォーマンスに直接影響するため、継続的に最適化の対象となります。また、Go 言語がより多くのプラットフォームで利用されるようになるにつれて、新しいハードウェアアーキテクチャ（この場合は s390x）への対応も重要になります。

具体的な背景としては、以下の点が考えられます。

1.  **メモリ割り当ての効率化**: 小さなオブジェクトの割り当ては頻繁に行われるため、そのオーバーヘッドを削減することは全体的なパフォーマンス向上に繋がります。`mcache` の最適化は、この目的を達成するためのものです。
2.  **GC の精度と効率の向上**: ガベージコレクタがオブジェクトをマークし、スキャンするプロセスをより効率的かつ正確にすることで、GC の一時停止時間を短縮し、スループットを向上させることができます。`gcw` (GC work) の導入や `scanSize` の利用は、この方向性を示唆しています。
3.  **s390x アーキテクチャのサポート**: IBM のメインフレームシステムである s390x は、エンタープライズ環境で広く利用されています。Go がこのプラットフォームをサポートすることで、Go アプリケーションの適用範囲が拡大し、より多くの開発者が Go を選択する動機付けとなります。これには、コンパイラ、アセンブラ、リンカ、ランタイムなど、Go ツールチェーンの多くの部分でアーキテクチャ固有の実装が必要となります。

## 前提知識の解説

### Go ランタイムのメモリ管理 (mcache, mspan, mheap)

Go のメモリ管理は、主に以下の3つのコンポーネントによって行われます。

*   **mheap**: ヒープ全体の管理を担当します。大きなメモリチャンクをオペレーティングシステムから取得し、それを `mspan` に分割します。
*   **mspan**: 連続したメモリページの集合体で、特定のサイズのオブジェクトを格納するために使用されます。各 `mspan` は、その `sizeclass` に応じて、同じサイズのオブジェクトを多数保持できます。
*   **mcache**: 各論理プロセッサ (P) にローカルなキャッシュです。小さなオブジェクトの割り当て要求に対して、グローバルな `mheap` へのアクセスを避けることで、ロックの競合を減らし、高速な割り当てを可能にします。`mcache` は、様々な `sizeclass` の `mspan` をキャッシュしています。

オブジェクトの割り当て要求が来ると、まず現在の P の `mcache` を確認します。`mcache` に適切な `mspan` があり、かつ空きスロットがあれば、そこからオブジェクトが割り当てられます。`mcache` が空の場合、`mheap` から新しい `mspan` を取得して補充します。

### Go のガベージコレクション (GC)

Go のガベージコレクタは、並行マーク・スイープ方式を採用しています。これは、アプリケーションの実行と並行してガベージコレクションの大部分を実行することで、GC による一時停止 (Stop-The-World, STW) 時間を最小限に抑えることを目指しています。

主要なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**: ライブオブジェクト（到達可能なオブジェクト）を識別します。このフェーズは、STW フェーズと並行フェーズに分かれます。
    *   **マーク開始 (Mark Start)**: 短い STW フェーズで、GC を開始するための初期設定を行います。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、ライブオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: 短い STW フェーズで、並行マーク中に発生した変更を処理し、マークフェーズを終了します。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（ガベージ）が占めていたメモリを解放し、再利用可能にします。このフェーズも並行して行われます。

### s390x アーキテクチャ

s390x は、IBM のメインフレームコンピュータで使用される 64 ビットの命令セットアーキテクチャ (ISA) です。これは、高い信頼性、可用性、保守性 (RAS) と、大規模なトランザクション処理やデータ処理に最適化された設計が特徴です。Go が s390x をサポートするということは、Go プログラムがこれらのメインフレーム上でネイティブに実行できるようになることを意味し、エンタープライズ分野での Go の採用を促進します。

### SSA (Static Single Assignment) フォーム

SSA フォームは、コンパイラの最適化パスで使用される中間表現 (IR) の一種です。SSA フォームでは、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Go コンパイラは、Go 1.7 から SSA フォームを導入し、より高度な最適化（例: 共通部分式除去 (CSE)、デッドコード除去、レジスタ割り当ての改善など）を可能にしました。

## 技術的詳細

### メモリ割り当ての最適化 (`src/runtime/malloc.go`)

このコミットでは、`mcache` からのオブジェクト割り当てロジックが大幅に改善されています。

*   **`_FlagNoScan` と `_FlagNoZero` の廃止**: 以前は `mallocgc` 関数に `flags` パラメータとして渡されていた `_FlagNoScan` (GC がオブジェクトをスキャンする必要がないことを示す) と `_FlagNoZero` (メモリをゼロクリアしないことを示す) が削除されました。代わりに、型情報 (`typ`) から `noscan` (ポインタを含まない型か) と `needzero` (ゼロクリアが必要か) を直接導出するように変更されています。これにより、割り当ての意図がより明確になり、型システムとの統合が強化されます。
*   **`nextFreeFast` 関数の導入**: `mcache` の `alloc` 配列から、高速に空きオブジェクトを見つけるための新しい関数 `nextFreeFast` が追加されました。これは、`s.allocCache` を利用して、ビットマップから空きスロットを効率的に検索します。`ctzIndex` や `ctzVals` (Count Trailing Zeros) を用いることで、ビット操作によって高速に次の空きインデックスを特定します。これにより、頻繁な小さなオブジェクトの割り当てが、より低レイテンシで実行できるようになります。
*   **`nextFree` 関数の導入**: `nextFreeFast` で空きオブジェクトが見つからなかった場合に呼び出される関数です。`mspan` が満杯の場合、`systemstack` を使って `c.refill` を呼び出し、新しい `mspan` を `mcache` に補充します。この関数は、GC のアシストが必要かどうかを示す `shouldhelpgc` フラグも返します。これは、GC がアクティブな場合に、現在のゴルーチンが GC 作業を支援する必要があることをランタイムに通知するために使用されます。
*   **`mallocgc` の変更**: `mallocgc` 関数は、これらの新しい `nextFreeFast` と `nextFree` を利用するように書き換えられました。これにより、小規模なオブジェクトの割り当てパスが最適化され、GC のオーバーヘッドが削減されます。

### ガベージコレクションの改善 (`src/runtime/mgcmark.go`)

GC のマーキングプロセスも変更されています。

*   **`markBitsForAddr` への変更**: `heapBitsForAddr(obj).setMarked()` が `markBitsForAddr(obj).setMarked()` に変更されました。これは、GC のマークビット管理に関する内部的なリファクタリングを示唆しています。
*   **GC 作業量の計測 (`gcw`)**: `atomic.Xadd64(&work.bytesMarked, int64(size))` が、現在のゴルーチンが属する P の `gcw` (GC work) カウンタ (`getg().m.p.ptr().gcw`) を直接更新するように変更されました。具体的には、`gcw.bytesMarked` と `gcw.scanWork` が追加されています。
    *   `gcw.bytesMarked`: マークされたバイト数を追跡します。
    *   `gcw.scanWork`: スキャンされたポインタの作業量を追跡します。
    この変更により、GC 作業量の計測がより粒度細かく、かつ並行処理に適した形で行われるようになります。グローバルなアトミック操作を減らすことで、競合を緩和し、GC のスケーラビリティを向上させることが期待されます。`scanSize` パラメータが `gcmarknewobject` に渡されるようになったのも、この `scanWork` の計測のためです。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

#### `nextFreeFast` 関数

```go
// nextFreeFast returns the next free object if one is quickly available.
// Otherwise it returns 0.
func (c *mcache) nextFreeFast(sizeclass int8) gclinkptr {
	s := c.alloc[sizeclass]
	ctzIndex := uint8(s.allocCache & 0xff)
	if ctzIndex != 0 {
		theBit := uint64(ctzVals[ctzIndex])
		freeidx := s.freeindex // help the pre ssa compiler out here with cse.
		result := freeidx + uintptr(theBit)
		if result < s.nelems {
			s.allocCache >>= (theBit + 1)
			freeidx = result + 1
			if freeidx%64 == 0 && freeidx != s.nelems {
				// We just incremented s.freeindex so it isn't 0
				// so we are moving to the next aCache.
				whichByte := freeidx / 8
				s.refillAllocCache(whichByte)
			}
			s.freeindex = freeidx
			v := gclinkptr(result*s.elemsize + s.base())
			s.allocCount++
			return v
		}
	}
	return 0
}
```
この関数は、`mcache` 内の `mspan` (`s`) から、利用可能な空きオブジェクトを非常に高速に取得しようとします。`s.allocCache` は、`mspan` 内の空きスロットを示すビットマップのようなものとして機能します。`ctzIndex` は、`allocCache` の下位バイトから「末尾のゼロの数 (Count Trailing Zeros)」を取得し、`ctzVals` テーブルを使って対応するビット位置 (`theBit`) を見つけます。これにより、`mspan` 内の次の空きオブジェクトのインデックス (`result`) を効率的に計算します。オブジェクトが取得されたら、`allocCache` を更新し、`s.freeindex` と `s.allocCount` をインクリメントします。このメカニズムは、ロックフリーで非常に高速な割り当てを可能にし、Go アプリケーションのレイテンシを低減します。

#### `nextFree` 関数

```go
// nextFree returns the next free object from the cached span if one is available.
// Otherwise it refills the cache with a span with an available object and
// returns that object along with a flag indicating that this was a heavy
// weight allocation. If it is a heavy weight allocation the caller must
// determine whether a new GC cycle needs to be started or if the GC is active
// whether this goroutine needs to assist the GC.
func (c *mcache) nextFree(sizeclass int8) (v gclinkptr, shouldhelpgc bool) {
	s := c.alloc[sizeclass]
	shouldhelpgc = false
	freeIndex := s.nextFreeIndex()
	if freeIndex == s.nelems {
		// The span is full.
		// ... (error checks) ...
		systemstack(func() {
			c.refill(int32(sizeclass))
		})
		shouldhelpgc = true
		s = c.alloc[sizeclass]

		freeIndex = s.nextFreeIndex()
	}

	// ... (error checks) ...

	v = gclinkptr(freeIndex*s.elemsize + s.base())
	s.allocCount++
	// ... (error checks) ...
	return
}
```
`nextFreeFast` が失敗した場合に呼び出される `nextFree` は、`mspan` が満杯であれば `c.refill` を呼び出して新しい `mspan` を取得します。`c.refill` は `systemstack` 内で実行され、グローバルな `mheap` から `mspan` を取得する際に必要なロック操作を安全に行います。この関数は `shouldhelpgc` フラグを返す点が重要です。これは、`mcache` の補充という「重い」割り当てが発生したことを呼び出し元 (`mallocgc`) に通知し、GC が現在アクティブであれば、このゴルーチンが GC 作業を支援する必要があることを示唆します。これにより、GC の進行を妨げずに、メモリ割り当てと GC のバランスを取ることができます。

#### `mallocgc` の変更点

`mallocgc` 関数は、オブジェクトのサイズと型に基づいて、`nextFreeFast` と `nextFree` を利用するように変更されました。
```go
// ...
	noscan := typ == nil || typ.kind&kindNoPointers != 0
	// ...
	if size <= maxSmallSize {
		if noscan && size < maxTinySize {
			// Tiny allocator.
			// ...
		} else {
			// ...

			if v == 0 {
				v, shouldhelpgc = c.nextFree(sizeclass)
			}
			x = unsafe.Pointer(v)
			if needzero {
				memclr(unsafe.Pointer(v), size)
			}
		}
	} else { // large objects
		// ...

			s = largeAlloc(size, needzero)
		})
		s.freeindex = 1
		x = unsafe.Pointer(s.base())
		size = s.elemsize
	}

	if noscan {
		heapBitsSetTypeNoScan(uintptr(x), size)
	} else {
		// ...
	}

	}
// ...
```
`mallocgc` は、`_FlagNoScan` と `_FlagNoZero` の代わりに `noscan` と `needzero` を使用するようになりました。これにより、割り当てられるオブジェクトの型に基づいて、GC スキャンが必要か、メモリのゼロクリアが必要かをより正確に判断します。小規模オブジェクトの割り当てでは、まず `nextFreeFast` を試み、失敗した場合に `nextFree` を呼び出します。大規模オブジェクトの割り当て (`largeAlloc`) も `needzero` パラメータを受け取るようになり、`s.freeindex` の初期化も行われます。
また、GC がアクティブな場合 (`gcphase != _GCoff`)、新しく割り当てられたオブジェクトは `gcmarknewobject` を通じて GC に認識されます。

### `src/runtime/mgcmark.go` の変更

#### `gcmarknewobject` 関数

```go
func gcmarknewobject(obj, size, scanSize uintptr) {
	// ...
	markBitsForAddr(obj).setMarked()
	gcw := &getg().m.p.ptr().gcw
	gcw.bytesMarked += uint64(size)
	gcw.scanWork += int64(scanSize)
}
```
この関数は、新しく割り当てられたオブジェクトを GC がマークする際に呼び出されます。変更点として、`heapBitsForAddr` が `markBitsForAddr` に置き換えられ、GC 作業量の計測方法が変更されました。以前はグローバルなアトミックカウンタ (`atomic.Xadd64(&work.bytesMarked, ...)` ) を使用していましたが、このコミットでは、現在のゴルーチンが実行されている P (プロセッサ) に関連付けられた `gcw` (GC work) 構造体 (`getg().m.p.ptr().gcw`) を直接更新するようになりました。
`gcw.bytesMarked` は割り当てられたオブジェクトのバイト数を、`gcw.scanWork` はそのオブジェクトが持つポインタをスキャンするのに必要な作業量を記録します。このローカルなカウンタの利用は、グローバルなロック競合を減らし、並行 GC のパフォーマンスとスケーラビリティを向上させるための重要な最適化です。

### s390x アーキテクチャサポートの追加

s390x アーキテクチャのサポートは、Go のツールチェーン全体にわたる大規模な変更です。
*   **コンパイラ**: s390x の命令セット、レジスタ、呼び出し規約に合わせたコード生成ロジックが実装されます。これには、SSA フォームから s390x 固有のアセンブリコードへの変換ルール、レジスタ割り当て戦略、およびアーキテクチャ固有の最適化が含まれます。
*   **アセンブラ**: s390x のアセンブリ言語を Go のオブジェクトファイル形式に変換するためのツールが更新されます。
*   **リンカ**: s390x の実行可能ファイルを生成するために、オブジェクトファイルの結合、シンボル解決、再配置処理を行うロジックが追加されます。
*   **ランタイム**: s390x 上で Go プログラムが動作するために必要な低レベルの機能（例: ゴルーチンのスケジューリング、スタック管理、システムコールインターフェース、アトミック操作、メモリ管理のフックなど）が s390x 固有のアセンブリコードや Go コードで実装されます。
*   **標準ライブラリ**: 暗号化、ハッシュ、数値計算などのパフォーマンスが重要なライブラリ関数に対して、s390x の特殊な命令（例: 暗号化アクセラレータ、CRC 命令など）を利用した最適化されたアセンブリ実装が提供されます。これにより、s390x プラットフォーム上での Go アプリケーションの実行速度が向上します。

これらの変更は、Go が s390x という新しいプラットフォームで完全に機能し、そのハードウェア特性を最大限に活用できるようにするための包括的な取り組みです。

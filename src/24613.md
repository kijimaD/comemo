## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおける関数呼び出し後のメモリ状態の正確な伝播に関する問題がありました。SSA形式では、すべての値が一度だけ割り当てられるという原則がありますが、メモリのように複数回書き換えられる可能性のあるエンティティは、この原則に直接適合しません。そのため、GoのSSAでは「メモリ変数」（`memvar`）という特殊な値を用いて、プログラムの各時点でのメモリの状態を表現し、メモリ操作の順序を強制します。

問題は、関数呼び出しが行われた後、その呼び出しによってメモリの状態が変化するにもかかわらず、その新しいメモリ状態が後続のブロック（サクセッサ）に正しく伝播されない可能性があったことです。具体的には、`memvar` の更新が `endBlock` の後に行われていたため、`endBlock` が生成するサクセッサブロックが、関数呼び出しによる最新のメモリ状態ではなく、古いメモリ状態を参照してしまうというバグが存在しました。これにより、コンパイラが誤ったメモリ状態に基づいて最適化を行ったり、不正なコードを生成したりするリスクがありました。

このコミットは、このメモリ変数の更新タイミングを修正し、関数呼び出しによって生成された新しいメモリ状態が、その呼び出しの直後に続くすべてのコードパス（サクセッサブロック）で確実に利用されるようにすることを目的としています。

## 前提知識の解説

### 静的単一割り当て (Static Single Assignment, SSA) 形式

SSA形式は、コンパイラの最適化段階で中間表現として広く用いられるプログラム表現形式です。SSAの主要な特性は以下の通りです。

1.  **単一割り当て**: 各変数はプログラム内で一度だけ定義（割り当て）されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
2.  **Φ関数 (Phi function)**: 複数の制御フローパスが合流する点（例: if文の終わり、ループの終わり）で、同じ論理変数に対応する異なるSSA変数を結合するために使用されます。Φ関数は、どのパスから来たかに応じて適切な値を「選択」します。

### Goコンパイラにおけるメモリ変数 (`memvar` / `TypeMem`)

SSA形式は、通常のレジスタやスタック上の値に対しては非常に効果的ですが、グローバルなメモリの状態を扱う際には課題が生じます。メモリは複数の場所から読み書きされるため、単一割り当ての原則に直接当てはめることが困難です。

GoコンパイラのSSAバックエンドでは、この問題を解決するために特別な「メモリ変数」の概念を導入しています。

*   **`TypeMem`**: これはSSA値の一種で、プログラムの特定の時点における「グローバルなメモリの状態」を表すトークンのようなものです。
*   **メモリ操作の連鎖**: `Store`（書き込み）や `Load`（読み込み）、`Call`（関数呼び出し）など、メモリに影響を与えるすべてのSSA操作は、入力として現在の `TypeMem` 値を受け取ります。そして、メモリを変更する操作（`Store`や`Call`）は、新しい `TypeMem` 値を出力として生成します。
*   **順序の強制**: この `TypeMem` 値の連鎖によって、コンパイラはメモリ操作の正しい順序を強制します。あるメモリ操作が生成した `TypeMem` 値は、その後のメモリ操作の入力として使用されなければなりません。これにより、コンパイラは依存関係のあるメモリ操作を勝手に並べ替えたり、削除したりすることを防ぎ、プログラムのセマンティクスを維持します。
*   **`s.vars[&memvar]`**: コンパイラの内部では、現在のブロックにおける最新のメモリ状態を表す `TypeMem` 値が `s.vars[&memvar]` のような形で管理されます。`s` はSSA生成の状態を保持する構造体で、`vars` は変数とそれに対応するSSA値のマッピングを保持します。`&memvar` は、このメモリ状態を表す特別な「変数」への参照と考えることができます。

関数呼び出しは、その性質上、メモリの任意の場所を読み書きする可能性があるため、常に新しいメモリ状態を生成すると見なされます。したがって、関数呼び出しを表すSSA値（`call`）は、新しい `TypeMem` 値としても機能します。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSA生成フェーズにおける関数呼び出しの処理と、メモリ変数の更新タイミングに集約されます。

`src/cmd/compile/internal/gc/ssa.go` 内の `(s *state) expr(n *Node)` メソッドは、抽象構文木 (AST) のノード `n` をSSA値に変換する役割を担っています。関数呼び出しのノードを処理する際、コンパイラは以下のステップを実行します（簡略化）。

1.  関数呼び出しを表すSSA値 `call` を生成します。この `call` 値は、関数呼び出しの結果（戻り値）だけでなく、新しいメモリ状態も表します。
2.  `s.vars[&memvar] = call` を通じて、現在のメモリ状態をこの新しい `call` 値に更新します。
3.  `s.endBlock()` を呼び出して現在のSSAブロックを終了し、新しいブロックを開始します。`endBlock` は、現在のブロックから後続のブロックへの制御フローを確立し、必要に応じてΦ関数を挿入します。

元のコードでは、`s.vars[&memvar] = call` の行が `s.endBlock()` の *後に* 配置されていました。

```go
// Original code snippet (simplified)
// ...
call := s.newValue(ssa.OpCall, types.TypeMem, ...) // 関数呼び出しを表すSSA値を生成
// ...
b := s.endBlock() // 現在のブロックを終了し、新しいブロックを開始
b.Kind = ssa.BlockCall
b.Control = call
// ...
s.startBlock(bNext) // フォールスルーブロックを開始
s.vars[&memvar] = call // ここでメモリ変数を更新していた
// ...
```

この順序の問題点は、`s.endBlock()` が呼び出された時点で、まだ `s.vars[&memvar]` が古いメモリ状態を指していることです。`endBlock` は、現在のブロックのサクセッサ（後続ブロック）を決定し、これらのサクセッサブロックが参照すべき変数の状態を解決する可能性があります。もしサクセッサブロックが関数呼び出しの直後に実行されるコードパスである場合、それらのブロックは関数呼び出しによって更新された新しいメモリ状態 `call` を参照すべきです。しかし、`s.vars[&memvar] = call` が `endBlock` の後にあったため、サクセッサブロックは古いメモリ状態を参照してしまう可能性がありました。

このコミットは、`s.vars[&memvar] = call` の行を `s.endBlock()` の *前* に移動することで、この問題を解決します。

```go
// Modified code snippet (simplified)
// ...
call := s.newValue(ssa.OpCall, types.TypeMem, ...) // 関数呼び出しを表すSSA値を生成
// ...
s.vars[&memvar] = call // ここでメモリ変数を更新
b := s.endBlock() // 現在のブロックを終了し、新しいブロックを開始
b.Kind = ssa.BlockCall
b.Control = call
// ...
s.startBlock(bNext) // フォールスルーブロックを開始
// ...
```

これにより、`s.endBlock()` が呼び出される時点では、`s.vars[&memvar]` は既に新しいメモリ状態 `call` を指しています。その結果、`endBlock` が生成するすべてのサクセッサブロックは、関数呼び出しによって更新された正しいメモリ状態を参照するようになり、コンパイラのメモリ状態管理の正確性が保証されます。

## コアとなるコードの解説

変更は `src/cmd/compile/internal/gc/ssa.go` ファイルの `(s *state) expr(n *Node)` メソッド内で行われています。このメソッドは、GoのASTノードをSSA形式に変換する際の中心的な部分です。

具体的には、関数呼び出しを処理するコードパスにおいて、`s.vars[&memvar] = call` という行が移動されました。

*   **削除された行**: `s.vars[&memvar] = call` が `s.startBlock(bNext)` の直後にあった箇所から削除されました。これは、関数呼び出し後のフォールスルーブロックが開始されるタイミングでメモリ変数を更新していたことを意味します。
*   **追加された行**: 同じ `s.vars[&memvar] = call` が、`call.AuxInt = left.Type.Argwid` の直後、かつ `b := s.endBlock()` の直前に移動されました。

この変更により、関数呼び出しを表すSSA値 `call` が生成され、その `AuxInt` フィールドが設定された直後、つまり関数呼び出しのSSA表現が完全に構築された時点で、現在のメモリ状態が `call` に更新されるようになりました。この更新は、現在のSSAブロックが終了し、後続のブロックが生成される `s.endBlock()` の呼び出しよりも前に行われるため、`endBlock` が処理するすべてのサクセッサブロックは、関数呼び出しによって変更された最新のメモリ状態を正しく参照できるようになります。

この修正は、GoコンパイラのSSAバックエンドにおけるメモリ状態の正確なトラッキングを保証し、結果としてより正確なコード生成と最適化に貢献します。

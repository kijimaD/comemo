## 変更の背景

Go言語の初期のランタイムでは、ゴルーチン（goroutine）のスタック管理に「セグメント化されたスタック（segmented stacks）」という手法が採用されていました。これは、各ゴルーチンが小さなスタックで開始し、必要に応じて動的にスタックサイズを拡張できるようにするためのものでした。しかし、この設計はスタックトレースの生成において課題を抱えていました。

通常のスタックトレースは、連続したメモリ領域を逆方向に辿ることで呼び出し履歴を再構築します。しかし、セグメント化されたスタックでは、ゴルーチンのスタックが複数の非連続なメモリセグメントに分散しているため、単純なスタックウォークでは正しいトレースを生成できませんでした。特に、スタックが拡張される際に呼び出される`_morestack`関数を跨ぐ場合、スタックポインタやプログラムカウンタが異なるスタックセグメントを指すため、特別な処理が必要でした。

このコミットは、この問題を解決し、セグメント化されたスタック環境下でも正確なスタックトレースを生成できるようにすることを目的としています。これにより、パニック発生時やデバッグ時に、ゴルーチンの正確な呼び出し履歴を把握できるようになります。

## 前提知識の解説

### セグメント化されたスタック (Segmented Stacks)

Goの初期ランタイムにおけるセグメント化されたスタックは、以下の特徴を持っていました。

1.  **動的なスタック拡張**: ゴルーチンは非常に小さなスタック（例: 8KB）で開始します。関数呼び出しのプロローグでスタックの残量チェックが行われ、不足しそうになるとランタイムの`_morestack`関数が呼び出されます。
2.  **`_morestack`関数**: スタックが不足した際に呼び出される特殊な関数です。この関数は、より大きな新しいスタックセグメントを割り当て、それを既存のスタックセグメントにリンクします。これにより、ゴルーチンは必要に応じてスタックを拡張できます。
3.  **非連続なメモリ領域**: 結果として、1つのゴルーチンの論理的なスタックは、物理的には複数の非連続なメモリセグメントに分散して存在することになります。これらのセグメントはポインタによって連結されています。
4.  **`_endmorestack`**: `_morestack`関数の終了を示すマーカーとして機能するアセンブリ関数です。`traceback`関数が`_morestack`の呼び出しを検出するために使用されます。

### スタックトレース (Stack Trace)

スタックトレースは、プログラムの実行中に特定の時点（通常はエラーやパニック発生時）で、現在実行中の関数からその関数を呼び出した関数、さらにその呼び出し元へと遡って、一連の関数呼び出しの履歴を表示するものです。これはデバッグにおいて非常に重要な情報であり、問題発生時のプログラムの状態を理解するのに役立ちます。

### `U` と `Stktop` 構造体

このコミットで関連する`U`と`Stktop`は、Goランタイムがゴルーチンごとのスタック情報を管理するために使用する内部構造体です。

-   `U`構造体: ゴルーチンごとのユーザーコンテキスト（スタックガード、スタックベースなど）を保持します。
-   `Stktop`構造体: スタックセグメントが切り替わる際に、古いスタックセグメントのベースアドレス、スタックポインタ、ガード値などを保存するために使用されます。これにより、複数のセグメントにまたがるスタックを辿ることが可能になります。

## 技術的詳細

このコミットの核心は、`traceback`関数がセグメント化されたスタックの境界を正しく認識し、複数のスタックセグメントを跨いで呼び出し履歴を辿れるようにすることです。

1.  **`traceback`関数のシグネチャ変更**:
    `traceback`関数は、従来の`traceback(uint8 *pc, uint8 *sp)`から`traceback(uint8 *pc, uint8 *sp, void* up)`へと変更されました。`up`引数は、現在のゴルーチンのユーザーコンテキスト（`U`構造体）へのポインタを渡すために使用されます。これは、`r15`レジスタに格納されているゴルーチンごとのデータブロックへのポインタを`getu()`関数を通じて取得し、`traceback`に渡すことで実現されます。

2.  **`_morestack`呼び出しの検出とスタックセグメントの切り替え**:
    `traceback`関数内で、現在のプログラムカウンタ`pc`が`_morestack`関数と`_endmorestack`関数の間にあるかどうかをチェックします。これは、現在のフレームがスタック拡張のために`_morestack`を呼び出した直後であることを意味します。
    ```c
    if((uint8*)_morestack < pc && pc < (uint8*)_endmorestack) {
        // call site in _morestack(); pop to earlier stack block to get true caller
        stktop = (Stktop*)u.stackbase;
        u.stackbase = stktop->oldbase;
        u.stackguard = stktop->oldguard;
        sp = stktop->oldsp;
        pc = ((uint8**)sp)[1];
        sp += 16;  // two irrelevant calls on stack - morestack, plus the call morestack made
        continue;
    }
    ```
    このコードブロックが、セグメント化されたスタックトレースの鍵となります。
    -   `stktop = (Stktop*)u.stackbase;`: 現在のスタックセグメントのベースアドレスから`Stktop`構造体を取得します。この`Stktop`には、前のスタックセグメントの情報が保存されています。
    -   `u.stackbase = stktop->oldbase;`: `U`構造体の`stackbase`を前のスタックセグメントのベースアドレスに更新します。
    -   `u.stackguard = stktop->oldguard;`: `U`構造体の`stackguard`を前のスタックセグメントのガード値に更新します。
    -   `sp = stktop->oldsp;`: スタックポインタ`sp`を前のスタックセグメントのスタックポインタに更新します。
    -   `pc = ((uint8**)sp)[1];`: プログラムカウンタ`pc`を、`_morestack`を呼び出した真の呼び出し元のアドレスに更新します。`_morestack`が呼び出された際のスタックには、`_morestack`自体のリターンアドレスと、その呼び出し元のリターンアドレスが積まれているため、`sp`から適切なオフセットで真の呼び出し元を取得します。
    -   `sp += 16;`: `_morestack`とその呼び出しに関連するスタックフレームをスキップするために、スタックポインタを調整します。
    -   `continue;`: これにより、`traceback`は前のスタックセグメントからスタックトレースの処理を続行できます。

3.  **`_endmorestack`マーカー**:
    `src/runtime/rt0_amd64.s`に追加された`_endmorestack`は、`_morestack`関数の実質的な終了位置を示すマーカーです。`traceback`関数はこのマーカーを使って、`pc`が`_morestack`の範囲内にあるかどうかを効率的に判断します。

4.  **`getu`関数**:
    `src/runtime/rt0_amd64.s`に追加された`getu`関数は、`r15`レジスタの値を返します。Goランタイムでは、`r15`レジスタが現在のゴルーチンのユーザーコンテキスト（`U`構造体）へのポインタを保持するために使用されていました。これにより、Cコードからこの重要な情報にアクセスできるようになります。

これらの変更により、`traceback`関数はスタックセグメントの境界を越えても、ゴルーチンの完全な呼び出し履歴を正確に再構築できるようになりました。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/rt2_amd64.c`内の`traceback`関数に集約されています。

1.  **`U`と`Stktop`構造体の導入**: これらの構造体は、ゴルーチンごとのスタック情報と、スタックセグメント切り替え時のコンテキストを保持するために定義されました。`U`は現在のゴルーチンのスタックベースやスタックガードを、`Stktop`は前のスタックセグメントの情報を格納します。

2.  **`getu()`関数の利用**: `traceback`関数が呼び出される際、`getu()`関数を通じて`r15`レジスタに格納されている現在のゴルーチンの`U`構造体へのポインタが渡されます。これにより、`traceback`関数はゴルーチン固有のスタック管理情報にアクセスできます。

3.  **`_morestack`呼び出しの検出**: `traceback`ループの冒頭で、現在のプログラムカウンタ`pc`が`_morestack`と`_endmorestack`の範囲内にあるかどうかがチェックされます。この範囲内にある場合、それはスタック拡張のために`_morestack`が呼び出された直後の状態であることを示します。

4.  **スタックセグメントの巻き戻し**: `_morestack`の範囲内と判断された場合、`traceback`は以下の手順で前のスタックセグメントに移動します。
    -   現在の`u.stackbase`（現在のスタックセグメントのベース）から`Stktop`構造体を取得します。この`Stktop`には、前のスタックセグメントの`oldbase`、`oldsp`、`oldguard`が保存されています。
    -   `u`構造体の`stackbase`と`stackguard`を、`Stktop`から取得した`oldbase`と`oldguard`に更新します。これにより、`traceback`は論理的に前のスタックセグメントに切り替わります。
    -   スタックポインタ`sp`を`Stktop->oldsp`に更新します。
    -   プログラムカウンタ`pc`を、`_morestack`を呼び出した真の呼び出し元のアドレスに更新します。これは、`sp`から適切なオフセット（`((uint8**)sp)[1]`）を計算することで行われます。
    -   `sp`をさらに`16`バイト進めます。これは、`_morestack`呼び出しに関連する不要なスタックフレーム（`_morestack`自体のリターンアドレスと、その呼び出し元のリターンアドレス）をスキップするためです。
    -   `continue`文により、ループの先頭に戻り、新しい`pc`と`sp`でスタックトレースの処理を続行します。

このメカニズムにより、`traceback`関数は複数の非連続なスタックセグメントを透過的に辿り、ゴルーチンの完全で正確な呼び出し履歴を生成することが可能になりました。

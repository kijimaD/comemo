# [インデックス 23047] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）に関する変更です。具体的には、`src/runtime/mgc.go` ファイルが変更されています。このファイルは、Go言語のランタイムにおけるメモリ管理とガベージコレクションのロジックを司る重要な部分です。GoのGCは並行（concurrent）かつ世代別（generational）ではないマーク＆スイープ方式を採用しており、このファイルはその中核をなすコントローラとワーカーの挙動を定義しています。

## コミット

このコミットは、Goランタイムのガベージコレクタにおいて、GCが推定されたマーク済みヒープサイズを超過した場合に、より積極的にミューテータアシスト（mutator assist）を行うように改善するものです。これにより、ヒープサイズが目標値を超えるのを防ぎ、GCの効率と予測可能性を向上させます。

    runtime: assist harder if GC exceeds the estimated marked heap
    
    Currently, the GC controller computes the mutator assist ratio at the
    beginning of the cycle by estimating that the marked heap size this
    cycle will be the same as it was the previous cycle. It then uses that
    assist ratio for the rest of the cycle. However, this means that if
    the mutator is quickly growing its reachable heap, the heap size is
    likely to exceed the heap goal and currently there's no additional
    pressure on mutator assists when this happens. For example, 6g (with
    GOMAXPROCS=1) frequently exceeds the goal heap size by ~25% because of
    this.
    
    This change makes GC revise its work estimate and the resulting assist
    ratio every 10ms during the concurrent mark. Instead of
    unconditionally using the marked heap size from the last cycle as an
    estimate for this cycle, it takes the minimum of the previously marked
    heap and the currently marked heap. As a result, as the cycle
    approaches or exceeds its heap goal, this will increase the assist
    ratio to put more pressure on mutator assist to bring the cycle to
    an end. For 6g, this causes the GC to always finish within 5% and
    often within 1% of its heap goal.

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行（ミューテータ）と並行して動作する並行マーク＆スイープ方式を採用しています。GCコントローラは、GCサイクルの開始時に、前回のサイクルでマークされたヒープサイズを基に、今回のサイクルでマークされるヒープサイズを推定し、それに基づいてミューテータアシスト比率を計算します。この比率は、GCサイクル全体で固定的に使用されていました。

しかし、この固定的な比率には問題がありました。もしミューテータ（アプリケーションコード）が到達可能なヒープサイズを急速に増加させている場合、GCコントローラが最初に推定したマーク済みヒープサイズを簡単に超えてしまう可能性がありました。その結果、ヒープサイズがGCの目標値（heap goal）を大幅に超過してしまうことが頻繁に発生していました。コミットメッセージの例では、`6g`（Goコンパイラ）が`GOMAXPROCS=1`の環境で、この問題により目標ヒープサイズを約25%も超過することがあったと述べられています。

このような状況では、GCがヒープ目標を達成するための追加的な圧力がミューテータアシストにかからず、ヒープ使用量が意図せず増大し、最悪の場合、メモリ不足によるパフォーマンス低下やクラッシュにつながる可能性がありました。この変更は、この問題を解決し、GCがより厳密にヒープ目標を達成できるようにすることを目的としています。

## 前提知識の解説

このコミットの理解には、Goのガベージコレクションに関するいくつかの基本的な概念が必要です。

*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリ領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しています。
*   **並行マーク＆スイープ (Concurrent Mark and Sweep)**:
    *   **マークフェーズ (Mark Phase)**: GCが到達可能なオブジェクト（使用中のメモリ）を特定し、マークするフェーズです。Goでは、このフェーズの大部分がアプリケーションの実行（ミューテータ）と並行して行われます。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なメモリ、つまりガベージ）を解放するフェーズです。
*   **ミューテータ (Mutator)**: アプリケーションの実行スレッドを指します。ミューテータは新しいオブジェクトを割り当て、既存のオブジェクトを変更します。
*   **GCワーカー (GC Worker)**: ガベージコレクションのタスクを実行する専用のゴルーチンです。
*   **ミューテータアシスト (Mutator Assist)**: 並行マークフェーズ中に、ミューテータ自身がGC作業の一部を分担して実行するメカニズムです。ミューテータが新しいメモリを割り当てようとした際に、GCが十分な進捗を上げていない場合、ミューテータは割り当てを行う前にGC作業を「アシスト」します。これにより、GCの進捗を加速させ、ヒープの過度な膨張を防ぎます。アシストの量は「ミューテータアシスト比率 (mutator assist ratio)」によって制御されます。この比率が高いほど、ミューテータはより多くのGC作業を分担します。
*   **ヒープ目標 (Heap Goal)**: 次のGCサイクルが開始されるまでに、ヒープが到達すべき目標サイズです。GoのGCは、この目標サイズを超えないように動作することを目指します。これは、`GOGC`環境変数によって設定される`gcpercent`（デフォルトは100）に基づいて計算されます。`gcpercent`が100の場合、ライブヒープサイズが前回のGC終了時のライブヒープサイズの2倍になったときに次のGCがトリガーされます。
*   **`memstats.heap_marked`**: 前回のGCサイクルでマークされた（到達可能と判断された）ヒープのバイト数を示します。
*   **`memstats.heap_live`**: 現在のライブヒープ（到達可能なオブジェクトが占めるメモリ）のバイト数を示します。
*   **`gcpercent`**: `GOGC`環境変数で設定される値で、GCの積極性を制御します。デフォルトは100です。これは、前回のGC終了時のライブヒープサイズに対して、どれだけの割合でヒープが成長したら次のGCを開始するかを決定します。例えば、`gcpercent=100`の場合、ライブヒープが前回の2倍になったらGCが開始されます。
*   **`workRatioAvg`**: GCが1バイトのライブヒープをスキャンするのに必要な作業量の平均推定値です。

## 技術的詳細

このコミットの核心は、GCコントローラがミューテータアシスト比率を動的に調整するメカニズムを導入した点にあります。以前はGCサイクルの開始時に一度計算された比率が固定されていましたが、この変更により、並行マークフェーズ中に約10ミリ秒ごとにこの比率が見直されるようになりました。

具体的な変更点は以下の通りです。

1.  **`gcControllerState`構造体の拡張**:
    *   `initialHeapLive`: 現在のGCサイクルが開始された時点での`memstats.heap_live`（ライブヒープサイズ）を記録するためのフィールドが追加されました。
    *   `heapGoal`: 現在のGCサイクルが終了する時点での目標ヒープサイズを記録するためのフィールドが追加されました。これは各サイクルの開始時に計算されます。

2.  **`startCycle`関数の変更**:
    *   以前は`startCycle`内で`scanWorkExpected`と`assistRatio`が計算されていましたが、これらの計算ロジックは新しい`revise`関数に移動されました。
    *   `heapGoal`の計算が`startCycle`内で行われるようになりました。
    *   `startCycle`の最後に、新しい`revise`関数が一度呼び出され、初期のミューテータアシスト比率が設定されます。

3.  **新しい`revise`関数の導入**:
    *   この関数は、GCサイクル中にミューテータアシスト比率を更新するために導入されました。
    *   **`heapMarkedEstimate`の計算**: ここが最も重要な変更点です。以前は前回のサイクルでマークされたヒープサイズ（`memstats.heap_marked`）を無条件に推定値として使用していました。しかし、`revise`関数では、`memstats.heap_marked`（前回のマーク済みヒープ）と`work.bytesMarked`（現在のサイクルで既にマークされたバイト数）の**大きい方**を`heapMarkedEstimate`として採用します。コミットメッセージには「minimum」とありますが、コードのロジックを見ると`if heapMarkedEstimate < work.bytesMarked { heapMarkedEstimate = work.bytesMarked }`となっており、これは実質的に`max`を取っていることになります。つまり、GCが進行するにつれて実際にマークされたバイト数が増加した場合、推定値もそれに合わせて増加します。
    *   **`scanWorkExpected`の再計算**: 新しい`heapMarkedEstimate`に基づいて、GCが期待するスキャン作業量（`scanWorkExpected`）が再計算されます。
    *   **`assistRatio`の再計算**: `scanWorkExpected`と、`heapGoal`から`initialHeapLive`を引いた残りのヒープ距離（`heapDistance`）に基づいて、ミューテータアシスト比率が再計算されます。`heapDistance`が非常に小さい場合（1MB以下）は、ゼロ除算や極端に高い比率になるのを防ぐために最小値が適用されます。

4.  **`gc`関数内での`revise`の定期的な呼び出し**:
    *   `gc`関数内の並行マークフェーズ中、`notetsleepg`による待機ループ内で、約10ミリ秒（`10*1000*1000`ナノ秒）ごとに`gcController.revise()`が呼び出されるようになりました。これにより、GCの進行状況とヒープの成長に合わせて、ミューテータアシスト比率が動的に調整されます。

この動的な調整により、ミューテータがヒープを急速に成長させている場合でも、`heapMarkedEstimate`が現在のマーク済みバイト数に合わせて増加し、それに伴って`assistRatio`も上昇します。これにより、ミューテータはより多くのGC作業を分担するようになり、ヒープが目標値を超えるのを防ぐための圧力が強化されます。結果として、GCはより厳密にヒープ目標を達成できるようになり、`6g`の例では目標の5%以内、しばしば1%以内に収まるようになりました。

## コアとなるコードの解説

### `gcControllerState`構造体の変更

*   `initialHeapLive uint64`: GCサイクルが開始された時点でのライブヒープサイズを保持します。これは、`revise`関数で`heapDistance`（ヒープ目標までの残り距離）を計算する際の基準点となります。
*   `heapGoal uint64`: 現在のGCサイクルが終了する時点での目標ヒープサイズを保持します。これは`startCycle`で計算され、`revise`関数で利用されます。

### `startCycle`関数の変更

*   `c.initialHeapLive = memstats.heap_live`: GCサイクルの開始時に、現在のライブヒープサイズを`initialHeapLive`に保存します。
*   `c.heapGoal = memstats.heap_marked + memstats.heap_marked*uint64(gcpercent)/100`: 新しいGCサイクルのヒープ目標を計算し、`heapGoal`に設定します。これは、前回のマーク済みヒープサイズに`gcpercent`で指定された割合を上乗せした値です。
*   `c.revise()`: GCサイクルの開始時に、新しい`revise`関数を呼び出して、初期のミューテータアシスト比率を設定します。以前の`scanWorkExpected`と`assistRatio`の計算ロジックはここから削除され、`revise`関数に移されました。

### `revise`関数の追加

この新しい関数は、GCサイクル中にミューテータアシスト比率を動的に調整する役割を担います。

*   `heapMarkedEstimate := memstats.heap_marked`: まず、`heapMarkedEstimate`を前回のGCサイクルでマークされたヒープサイズ（`memstats.heap_marked`）で初期化します。
*   `if heapMarkedEstimate < work.bytesMarked { heapMarkedEstimate = work.bytesMarked }`: ここが重要なロジックです。もし現在のGCサイクルで既にマークされたバイト数（`work.bytesMarked`）が、前回のマーク済みヒープサイズ（`memstats.heap_marked`）よりも大きい場合、`heapMarkedEstimate`を`work.bytesMarked`に更新します。これにより、GCが進行するにつれて実際にマークされたヒープサイズが当初の推定を超えた場合でも、推定値が現実の状況に追従するようになります。
*   `scanWorkExpected := uint64(float64(heapMarkedEstimate) * c.workRatioAvg)`: 更新された`heapMarkedEstimate`に基づいて、GCが期待するスキャン作業量（`scanWorkExpected`）を再計算します。
*   `heapDistance := int64(c.heapGoal) - int64(c.initialHeapLive)`: ヒープ目標（`c.heapGoal`）から、GCサイクル開始時のライブヒープサイズ（`c.initialHeapLive`）を引くことで、GCサイクル中にミューテータが割り当て可能なヒープの残り距離を計算します。
*   `if heapDistance <= 1024*1024 { heapDistance = 1024 * 1024 }`: `heapDistance`が非常に小さい場合（1MB以下）は、ゼロ除算や極端に高いアシスト比率になるのを防ぐために、最小値1MBを適用します。
*   `c.assistRatio = float64(scanWorkExpected) / float64(heapDistance)`: 最後に、再計算された`scanWorkExpected`と`heapDistance`に基づいて、新しいミューテータアシスト比率（`c.assistRatio`）を設定します。この比率が高くなると、ミューテータはより多くのGC作業を分担するようになります。

### `gc`関数の変更

*   `for !notetsleepg(&work.bgMarkNote, 10*1000*1000) { gcController.revise() }`: 並行マークフェーズ中の待機ループが変更されました。以前は`notetsleepg(&work.bgMarkNote, -1)`で無限に待機していましたが、この変更により、約10ミリ秒（10,000,000ナノ秒）ごとに`notetsleepg`がタイムアウトし、そのたびに`gcController.revise()`が呼び出されるようになりました。これにより、GCの進行状況とヒープの成長に合わせて、ミューテータアシスト比率が定期的に更新され、GCがヒープ目標をより厳密に達成するための動的な圧力が維持されます。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行（ミューテータ）と並行して動作する並行マーク＆スイープ方式を採用しています。GCコントローラは、GCサイクルの開始時に、前回のサイクルでマークされたヒープサイズを基に、今回のサイクルでマークされるヒープサイズを推定し、それに基づいてミューテータアシスト比率を計算します。この比率は、GCサイクル全体で固定的に使用されていました。

しかし、この固定的な比率には問題がありました。もしミューテータ（アプリケーションコード）が到達可能なヒープサイズを急速に増加させている場合、GCコントローラが最初に推定したマーク済みヒープサイズを簡単に超えてしまう可能性がありました。その結果、ヒープサイズがGCの目標値（heap goal）を大幅に超過してしまうことが頻繁に発生していました。コミットメッセージの例では、`6g`（Goコンパイラ）が`GOMAXPROCS=1`の環境で、この問題により目標ヒープサイズを約25%も超過することがあったと述べられています。

このような状況では、GCがヒープ目標を達成するための追加的な圧力がミューテータアシストにかからず、ヒープ使用量が意図せず増大し、最悪の場合、メモリ不足によるパフォーマンス低下やクラッシュにつながる可能性がありました。この変更は、この問題を解決し、GCがより厳密にヒープ目標を達成できるようにすることを目的としています。

## 前提知識の解説

このコミットの理解には、Goのガベージコレクションに関するいくつかの基本的な概念が必要です。

*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリ領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しています。
*   **並行マーク＆スイープ (Concurrent Mark and Sweep)**:
    *   **マークフェーズ (Mark Phase)**: GCが到達可能なオブジェクト（使用中のメモリ）を特定し、マークするフェーズです。Goでは、このフェーズの大部分がアプリケーションの実行（ミューテータ）と並行して行われます。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なメモリ、つまりガベージ）を解放するフェーズです。
*   **ミューテータ (Mutator)**: アプリケーションの実行スレッドを指します。ミューテータは新しいオブジェクトを割り当て、既存のオブジェクトを変更します。
*   **GCワーカー (GC Worker)**: ガベージコレクションのタスクを実行する専用のゴルーチンです。
*   **ミューテータアシスト (Mutator Assist)**: 並行マークフェーズ中に、ミューテータ自身がGC作業の一部を分担して実行するメカニズムです。ミューテータが新しいメモリを割り当てようとした際に、GCが十分な進捗を上げていない場合、ミューテータは割り当てを行う前にGC作業を「アシスト」します。これにより、GCの進捗を加速させ、ヒープの過度な膨張を防ぎます。アシストの量は「ミューテータアシスト比率 (mutator assist ratio)」によって制御されます。この比率が高いほど、ミューテータはより多くのGC作業を分担します。
*   **ヒープ目標 (Heap Goal)**: 次のGCサイクルが開始されるまでに、ヒープが到達すべき目標サイズです。GoのGCは、この目標サイズを超えないように動作することを目指します。これは、`GOGC`環境変数によって設定される`gcpercent`（デフォルトは100）に基づいて計算されます。`gcpercent`が100の場合、ライブヒープサイズが前回のGC終了時のライブヒープサイズの2倍になったときに次のGCがトリガーされます。
*   **`memstats.heap_marked`**: 前回のGCサイクルでマークされた（到達可能と判断された）ヒープのバイト数を示します。
*   **`memstats.heap_live`**: 現在のライブヒープ（到達可能なオブジェクトが占めるメモリ）のバイト数を示します。
*   **`gcpercent`**: `GOGC`環境変数で設定される値で、GCの積極性を制御します。デフォルトは100です。これは、前回のGC終了時のライブヒープサイズに対して、どれだけの割合でヒープが成長したら次のGCを開始するかを決定します。例えば、`gcpercent=100`の場合、ライブヒープが前回の2倍になったらGCが開始されます。
*   **`workRatioAvg`**: GCが1バイトのライブヒープをスキャンするのに必要な作業量の平均推定値です。

## 技術的詳細

このコミットの核心は、GCコントローラがミューテータアシスト比率を動的に調整するメカニズムを導入した点にあります。以前はGCサイクルの開始時に一度計算された比率が固定されていましたが、この変更により、並行マークフェーズ中に約10ミリ秒ごとにこの比率が見直されるようになりました。

具体的な変更点は以下の通りです。

1.  **`gcControllerState`構造体の拡張**:
    *   `initialHeapLive`: 現在のGCサイクルが開始された時点での`memstats.heap_live`（ライブヒープサイズ）を記録するためのフィールドが追加されました。
    *   `heapGoal`: 現在のGCサイクルが終了する時点での目標ヒープサイズを記録するためのフィールドが追加されました。これは各サイクルの開始時に計算されます。

2.  **`startCycle`関数の変更**:
    *   以前は`startCycle`内で`scanWorkExpected`と`assistRatio`が計算されていましたが、これらの計算ロジックは新しい`revise`関数に移動されました。
    *   `heapGoal`の計算が`startCycle`内で行われるようになりました。
    *   `startCycle`の最後に、新しい`revise`関数が一度呼び出され、初期のミューテータアシスト比率が設定されます。

3.  **新しい`revise`関数の導入**:
    *   この関数は、GCサイクル中にミューテータアシスト比率を更新するために導入されました。
    *   **`heapMarkedEstimate`の計算**: ここが最も重要なロジックです。以前は前回のサイクルでマークされたヒープサイズ（`memstats.heap_marked`）を無条件に推定値として使用していました。しかし、`revise`関数では、`memstats.heap_marked`（前回のマーク済みヒープ）と`work.bytesMarked`（現在のサイクルで既にマークされたバイト数）の**大きい方**を`heapMarkedEstimate`として採用します。コミットメッセージには「minimum」とありますが、コードのロジックを見ると`if heapMarkedEstimate < work.bytesMarked { heapMarkedEstimate = work.bytesMarked }`となっており、これは実質的に`max`を取っていることになります。つまり、GCが進行するにつれて実際にマークされたバイト数が増加した場合、推定値もそれに合わせて増加します。
    *   **`scanWorkExpected`の再計算**: 新しい`heapMarkedEstimate`に基づいて、GCが期待するスキャン作業量（`scanWorkExpected`）が再計算されます。
    *   **`assistRatio`の再計算**: `scanWorkExpected`と、`heapGoal`から`initialHeapLive`を引いた残りのヒープ距離（`heapDistance`）に基づいて、ミューテータアシスト比率が再計算されます。`heapDistance`が非常に小さい場合（1MB以下）は、ゼロ除算や極端に高い比率になるのを防ぐために最小値が適用されます。

4.  **`gc`関数内での`revise`の定期的な呼び出し**:
    *   `gc`関数内の並行マークフェーズ中、`notetsleepg`による待機ループ内で、約10ミリ秒（`10*1000*1000`ナノ秒）ごとに`gcController.revise()`が呼び出されるようになりました。これにより、GCの進行状況とヒープの成長に合わせて、ミューテータアシスト比率が動的に調整されます。

この動的な調整により、ミューテータがヒープを急速に成長させている場合でも、`heapMarkedEstimate`が現在のマーク済みバイト数に合わせて増加し、それに伴って`assistRatio`も上昇します。これにより、ミューテータはより多くのGC作業を分担するようになり、ヒープが目標値を超えるのを防ぐための圧力が強化されます。結果として、GCはより厳密にヒープ目標を達成できるようになり、`6g`の例では目標の5%以内、しばしば1%以内に収まるようになりました。

## コアとなるコードの解説

### `gcControllerState`構造体の変更

*   `initialHeapLive uint64`: GCサイクルが開始された時点でのライブヒープサイズを保持します。これは、`revise`関数で`heapDistance`（ヒープ目標までの残り距離）を計算する際の基準点となります。
*   `heapGoal uint64`: 現在のGCサイクルが終了する時点での目標ヒープサイズを保持します。これは`startCycle`で計算され、`revise`関数で利用されます。

### `startCycle`関数の変更

*   `c.initialHeapLive = memstats.heap_live`: GCサイクルの開始時に、現在のライブヒープサイズを`initialHeapLive`に保存します。
*   `c.heapGoal = memstats.heap_marked + memstats.heap_marked*uint64(gcpercent)/100`: 新しいGCサイクルのヒープ目標を計算し、`heapGoal`に設定します。これは、前回のマーク済みヒープサイズに`gcpercent`で指定された割合を上乗せした値です。
*   `c.revise()`: GCサイクルの開始時に、新しい`revise`関数を呼び出して、初期のミューテータアシスト比率を設定します。以前の`scanWorkExpected`と`assistRatio`の計算ロジックはここから削除され、`revise`関数に移されました。

### `revise`関数の追加

この新しい関数は、GCサイクル中にミューテータアシスト比率を動的に調整する役割を担います。

*   `heapMarkedEstimate := memstats.heap_marked`: まず、`heapMarkedEstimate`を前回のGCサイクルでマークされたヒープサイズ（`memstats.heap_marked`）で初期化します。
*   `if heapMarkedEstimate < work.bytesMarked { heapMarkedEstimate = work.bytesMarked }`: ここが重要なロジックです。もし現在のGCサイクルで既にマークされたバイト数（`work.bytesMarked`）が、前回のマーク済みヒープサイズ（`memstats.heap_marked`）よりも大きい場合、`heapMarkedEstimate`を`work.bytesMarked`に更新します。これにより、GCが進行するにつれて実際にマークされたヒープサイズが当初の推定を超えた場合でも、推定値が現実の状況に追従するようになります。
*   `scanWorkExpected := uint64(float64(heapMarkedEstimate) * c.workRatioAvg)`: 更新された`heapMarkedEstimate`に基づいて、GCが期待するスキャン作業量（`scanWorkExpected`）を再計算します。
*   `heapDistance := int64(c.heapGoal) - int64(c.initialHeapLive)`: ヒープ目標（`c.heapGoal`）から、GCサイクル開始時のライブヒープサイズ（`c.initialHeapLive`）を引くことで、GCサイクル中にミューテータが割り当て可能なヒープの残り距離を計算します。
*   `if heapDistance <= 1024*1024 { heapDistance = 1024 * 1024 }`: `heapDistance`が非常に小さい場合（1MB以下）は、ゼロ除算や極端に高いアシスト比率になるのを防ぐために、最小値1MBを適用します。
*   `c.assistRatio = float64(scanWorkExpected) / float64(heapDistance)`: 最後に、再計算された`scanWorkExpected`と`heapDistance`に基づいて、新しいミューテータアシスト比率（`c.assistRatio`）を設定します。この比率が高くなると、ミューテータはより多くのGC作業を分担するようになります。

### `gc`関数の変更

*   `for !notetsleepg(&work.bgMarkNote, 10*1000*1000) { gcController.revise() }`: 並行マークフェーズ中の待機ループが変更されました。以前は`notetsleepg(&work.bgMarkNote, -1)`で無限に待機していましたが、この変更により、約10ミリ秒（10,000,000ナノ秒）ごとに`notetsleepg`がタイムアウトし、そのたびに`gcController.revise()`が呼び出されるようになりました。これにより、GCの進行状況とヒープの成長に合わせて、ミューテータアシスト比率が定期的に更新され、GCがヒープ目標をより厳密に達成するための動的な圧力が維持されます。

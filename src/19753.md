# [インデックス 19753] ファイルの概要

このコミットは、Go言語の`archive/tar`パッケージにおけるバグ修正に関するものです。具体的には、PAXヘッダーの書き込み時に発生していた、ヘッダーが二重に書き込まれる問題を解決しています。この問題は、以前のコミットで導入された一時バッファの再利用ロジックが原因で発生していました。

    archive/tar: fix writing of pax headers
    
    "archive/tar: reuse temporary buffer in writeHeader" introduced a
    change which was supposed to help lower the number of allocations from

    example correct header:
    PaxHeaders.4290/NetLock_Arany_=Class_Gold=_Ftanstvny.crt00000000000000000000000000000071123012166340216634007250 0ustar0000000000000000
    0100644000000000000000000000270412301216634007250 0ustar0000000000000000
    
    This commit adds a dedicated buffer for pax headers to the Writer
    struct. This change increases the size of the struct by 512 bytes, but
    allows tar/writer to avoid allocating 512 bytes for all written
    headers and it avoids allocating 512 more bytes for pax headers.

## 変更の背景

このコミットは、以前のコミット「archive/tar: reuse temporary buffer in writeHeader」によって導入されたバグを修正するために行われました。この以前のコミットは、`writeHeader`関数が呼び出されるたびに512バイトのメモリ割り当てを削減することを目的として、一時バッファを再利用するように変更しました。しかし、この変更がPAXヘッダーの書き込み処理を壊してしまいました。

具体的には、`writeHeader`関数がPAXヘッダーを書き込むために`writePAXHeader`を呼び出し、その`writePAXHeader`がさらに`writeHeader`を再帰的に呼び出すという構造になっていました。この再帰的な呼び出しの際に、同じ一時バッファ（`hdrBuff`）が再利用されてしまうため、PAXヘッダーが二重に書き込まれるという問題が発生していました。コミットメッセージに示されている「broken header」の例では、PAXヘッダーが2回連続して出現していることが確認できます。

このバグは、tarアーカイブの破損や、正しくないアーカイブの生成につながる可能性がありました。

## 前提知識の解説

### `archive/tar`パッケージ

`archive/tar`はGo言語の標準ライブラリの一部で、TAR (Tape ARchive) ファイル形式の読み書きをサポートします。TARファイルは、複数のファイルを1つのアーカイブにまとめるための一般的な形式です。このパッケージは、ファイルのメタデータ（ファイル名、サイズ、パーミッションなど）と内容を効率的に処理するための機能を提供します。

### PAXヘッダー (Portable Archive eXchange Header)

PAXヘッダーは、POSIX.1-2001 (またはustar) 形式のtarアーカイブの拡張機能です。従来のtarヘッダーでは表現できない、より長いファイル名、大きなファイルサイズ、高精度なタイムスタンプ、Unicode文字などのメタデータを格納するために使用されます。PAXヘッダーは、通常のファイルデータとは別に、特別なエントリとしてtarアーカイブ内に格納されます。これらは通常、`PaxHeaders.XXXX/filename`のような形式の名前を持ち、その後に実際のファイルエントリが続きます。

### `writeHeader`関数と`writePAXHeader`関数

*   **`writeHeader`**: この関数は、tarアーカイブに個々のファイルエントリのヘッダーを書き込む主要な関数です。ファイル名、サイズ、タイムスタンプなどの標準的なtarヘッダー情報を処理します。
*   **`writePAXHeader`**: この関数は、PAXヘッダーを生成し、それをtarアーカイブに書き込むための補助関数です。`writeHeader`が、標準tarヘッダーで表現できない情報（例：長すぎるファイル名）を検出した場合に、この`writePAXHeader`を呼び出してPAXヘッダーを書き込みます。重要なのは、`writePAXHeader`自身が、PAXヘッダーの内容を通常のtarエントリとして書き込むために、再び`writeHeader`を呼び出す点です。

### `blockSize`と一時バッファ

tarアーカイブのヘッダーは、通常512バイトの固定長ブロックで構成されます。Goの`archive/tar`パッケージでは、この512バイトのブロックを効率的に処理するために、内部で`[blockSize]byte`のような固定サイズのバイト配列を一時バッファとして使用することがあります。これにより、ヘッダーを構築する際に毎回メモリを動的に割り当てるオーバーヘッドを避けることができます。

## 技術的詳細

このバグの核心は、`Writer`構造体内の単一の一時バッファ`hdrBuff`が、再帰的な呼び出しパスで不適切に再利用されていたことにあります。

1.  ユーザーが`Writer.WriteHeader(hdr)`を呼び出し、これが`Writer.writeHeader(hdr, true)`を呼び出します（`allowPax`は`true`）。
2.  `writeHeader`関数内で、渡された`hdr`にPAXヘッダーが必要な情報（例：長すぎるファイル名）が含まれていると判断されます。
3.  `writeHeader`は、PAXヘッダーを書き込むために`writePAXHeader`を呼び出します。
4.  `writePAXHeader`は、PAXヘッダー自体をtarエントリとして書き込むために、再び`Writer.writeHeader(paxHdr, false)`を呼び出します（`allowPax`は`false`）。
5.  この再帰的な`writeHeader`の呼び出しにおいて、元の`writeHeader`呼び出しで使用されていたのと同じ`tw.hdrBuff`が、PAXヘッダーの構築にも使用されてしまいます。
6.  結果として、PAXヘッダーが構築され、書き込まれた後、元の`writeHeader`の実行が再開されますが、その時点では`tw.hdrBuff`の内容はPAXヘッダーの情報で上書きされてしまっています。
7.  これにより、元のファイルエントリのヘッダーが正しく構築されず、PAXヘッダーが二重に書き込まれるという現象が発生していました。コミットメッセージの例では、同じPAXヘッダーが2回連続して出力されていることが示されています。

## コアとなるコードの解説

このコミットの主要な修正は、`Writer`構造体に`paxHdrBuff [blockSize]byte`という新しいバッファを追加し、`writeHeader`関数内でこの新しいバッファを適切に利用するようにロジックを変更した点です。

1.  **`Writer`構造体への`paxHdrBuff`の追加**:
    *   `hdrBuff`は通常のヘッダー書き込み用の一時バッファとして残されます。
    *   新しく追加された`paxHdrBuff`は、PAXヘッダーを書き込むための専用の一時バッファとして機能します。これにより、再帰的な`writeHeader`の呼び出し時に、元のヘッダーの構築に使用されている`hdrBuff`を上書きしてしまうことを防ぎます。

2.  **`writeHeader`関数内のバッファ選択ロジックの変更**:
    *   `writeHeader`関数は、`allowPax`というブール型の引数を受け取ります。
    *   `allowPax`が`true`の場合（これは通常、ユーザーが`WriteHeader`を直接呼び出した最初の非再帰的な呼び出しの場合）、`tw.hdrBuff`がヘッダーの構築に使用されます。
    *   `allowPax`が`false`の場合（これは`writePAXHeader`から再帰的に呼び出された場合）、`tw.paxHdrBuff`がヘッダーの構築に使用されます。
    *   この条件分岐により、再帰的な呼び出しパスで異なるバッファが使用されることが保証され、バッファの衝突とデータの破損が回避されます。

この変更により、`Writer`構造体のサイズは512バイト増加しますが、コミットメッセージにもあるように、これにより`tar/writer`はすべてのヘッダー書き込みで512バイトの割り当てを回避でき、さらにPAXヘッダーのために追加で512バイトの割り当てを回避できるため、全体的なメモリ効率とパフォーマンスが向上します。

また、`writer_test.go`には`TestValidTypeflagWithPAXHeader`という新しいテストケースが追加されています。このテストは、非常に長いファイル名（PAXヘッダーが必要となるケース）を持つファイルを書き込み、その後に読み戻して、`Typeflag`が正しく0（通常のファイル）であることを検証します。これにより、PAXヘッダーが正しく処理され、ヘッダーの破損や二重書き込みが発生していないことを確認できます。

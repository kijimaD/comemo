## 変更の背景

このコミットの主な背景は、Go 1.4のリリースノートにおいて、Go言語の代替コンパイラである`gccgo`の現状を正確に反映させる必要があったためです。Go言語の公式コンパイラである`gc`と`gccgo`は異なるリリースサイクルを持っており、`gccgo`が特定のGoバージョンに対応するまでに時間差が生じることがあります。このコミットは、その時間差と、GCCの特定のバージョン（GCC 4.9とGCC 5）がどのGoバージョン（Go 1.2とGo 1.4）の`gccgo`を搭載しているかを明確にするために行われました。

また、`crypto/tls`パッケージに関する記述の微調整も含まれています。これは、POODLE攻撃のようなダウングレード攻撃に対する防御策である`TLS_FALLBACK_SCSV`のサポートについて、より正確な情報を提供し、GoクライアントのSSLv3に対する脆弱性がないことを明確にするためのものです。

## 前提知識の解説

### Go言語のリリースサイクル

Go言語は、通常6ヶ月ごとにメジャーリリースを行います。各リリースでは、言語仕様の改善、ランタイムの最適化、標準ライブラリの機能追加や修正などが行われます。Go 1.4は、2014年12月にリリースされた重要なバージョンであり、Go 1.3の約6ヶ月後に登場しました。

### gccgo

`gccgo`は、Go言語のプログラムをコンパイルするための代替コンパイラであり、GNU Compiler Collection (GCC) の一部として開発されています。Go言語の公式コンパイラである`gc`とは異なり、`gccgo`はGCCの最適化パスを利用できるため、特定のシナリオで異なるパフォーマンス特性を示すことがあります。しかし、`gccgo`のリリースはGCCのリリースサイクルに依存するため、最新のGo言語の機能が`gccgo`に統合されるまでにタイムラグが生じることが一般的です。

### Go 1.4の主要な変更点

Go 1.4は、Go言語の進化においていくつかの重要な変更をもたらしました。

*   **ランタイムの改善**: ランタイムの大部分がC言語からGo言語に書き換えられました。これにより、ガベージコレクタがプログラムスタックを正確にスキャンできるようになり、より正確なガベージコレクションが可能になりました。
*   **連続したスタック**: スタックが連続的になり、必要に応じて再割り当てされるようになりました。これにより、以前のバージョンで問題となっていた「ホットスタック分割」の問題が解消されました。
*   **`go generate`コマンド**: ビルド時にソースコードを生成するための新しいツール`go generate`が導入されました。これにより、コード生成のワークフローが簡素化されました。
*   **Androidサポート**: AndroidプラットフォームでのARMプロセッサの公式サポートが追加され、Androidアプリケーション用のバイナリや`.so`ライブラリをビルドできるようになりました。
*   **TLS_FALLBACK_SCSV**: `crypto/tls`パッケージにおいて、ダウングレード攻撃を防ぐための`TLS_FALLBACK_SCSV`のサポートが追加されました。

### TLS_FALLBACK_SCSVとPOODLE攻撃

**POODLE (Padding Oracle On Downgraded Legacy Encryption) 攻撃**は、2014年にGoogleのセキュリティチームによって発見されたセキュリティ脆弱性です。この攻撃は、主にSSL 3.0プロトコルの脆弱性を悪用し、セッションクッキーなどの機密情報を復号化することで、攻撃者がユーザーになりすますことを可能にします。

POODLE攻撃は、以下の2段階で機能します。

1.  **プロトコルダウングレード**: 攻撃者（通常は中間者攻撃 (MITM) を実行）は、クライアントとサーバー間の接続を、よりセキュアなTLSプロトコル（TLS 1.0、1.1、1.2など）から、脆弱な古いSSL 3.0に強制的にダウングレードさせます。これは、多くのサーバーが古いクライアントとの互換性のためにSSL 3.0を歴史的にサポートしていたために可能でした。
2.  **パディングオラクル攻撃**: 接続がSSL 3.0にダウングレードされると、攻撃者はSSL 3.0のCBC (Cipher Block Chaining) モードにおけるパディングオラクル脆弱性を悪用します。特別に細工されたリクエストを送信し、サーバーの応答（特にパディングエラー）を観察することで、攻撃者は暗号化されたデータをバイトごとに復号化できます。これにより、認証トークンやパスワードなどの機密情報が漏洩する可能性があります。

**TLS_FALLBACK_SCSV (TLS Fallback Signaling Cipher Suite Value)** は、POODLE攻撃のような強制的なプロトコルダウングレードを防ぐために設計されたメカニズムです。

*   **機能**: クライアントが、最初に試行したTLSバージョンよりも低いSSL/TLSバージョンで接続を試みる場合（例えば、より高いバージョンでの試行が失敗した後）、`ClientHello`メッセージに`TLS_FALLBACK_SCSV`シグナルを含めます。
*   **サーバーの応答**: サーバーが`TLS_FALLBACK_SCSV`を含む`ClientHello`を受け取り、クライアントが要求しているプロトコルバージョンよりも高いプロトコルバージョンをサポートしていることを検出した場合、サーバーは「inappropriate_fallback」アラートで接続を終了します。これは、正当なクライアントはより高いバージョンが本当に失敗した場合にのみフォールバックするため、悪意のあるダウングレード試行が行われている可能性が高いことを示します。
*   **広範な保護**: `TLS_FALLBACK_SCSV`は、SSL 3.0へのダウングレードだけでなく、より安全性の低い任意のプロトコルバージョンへの強制的なダウングレードを防ぐのに役立ちます。

POODLE攻撃に対する最も効果的な対策は、SSL 3.0のサポートを完全に無効にすることです。`TLS_FALLBACK_SCSV`は重要な中間的な解決策ですが、最終的にはSSL 3.0を無効にし、TLS 1.2以降のモダンなTLSバージョンを使用することが推奨されます。

## 技術的詳細

このコミットは、Go 1.4の公式リリースノートである `doc/go1.4.html` ファイルに対する変更です。HTMLドキュメントの特定のセクションが更新されています。

### `gccgo`ステータスの更新

最も重要な変更は、`<h3 id="gccgo">Status of gccgo</h3>` セクションの更新です。以前は「TODO gccgo news」というプレースホルダー的な記述でしたが、これが具体的な情報に置き換えられました。

変更後の記述は、GCCとGoのリリーススケジュールが一致しないことを明確に述べ、以下の具体的な情報を提供しています。

*   **GCC 4.9**: Go 1.2バージョンの`gccgo`が含まれている。
*   **GCC 5**: Go 1.4バージョンの`gccgo`が含まれる可能性が高い。

これにより、Go 1.4のユーザーは、どのGCCバージョンがどのGoバージョンの`gccgo`に対応しているかを正確に理解できるようになります。これは、`gccgo`を利用する開発者にとって非常に重要な情報です。

### `go`コマンドの記述修正

`go`コマンドに関する記述で、「build-time source code generation and TODO.」となっていた部分から「and TODO.」が削除され、「build-time source code generation.」と修正されました。これは、リリースノートの記述から不要なプレースホルダーを削除し、より簡潔で正確な情報を提供するためのクリーンアップです。

### `crypto/tls`パッケージに関する記述修正

`crypto/tls`パッケージに関する記述も微調整されています。特に、`TLS_FALLBACK_SCSV`とPOODLE攻撃に関する説明が修正されました。

変更前:
「(The crypto/tls package's client has never supported SSLv3, so it is not vulnerable to the POODLE attack.)」

変更後:
「(The Go client does not support fallback at all, so it is not vulnerable to those attacks.)」

この変更は、GoクライアントがSSLv3をサポートしないためPOODLE攻撃に脆弱ではないという点に加え、そもそもGoクライアントがプロトコルダウングレード（fallback）をサポートしていないため、ダウングレード攻撃全般に対して脆弱ではないという、より広範で正確な情報を提供しています。これにより、GoのTLS実装の堅牢性が強調されています。

## コアとなるコードの解説

このコミットでは、`doc/go1.4.html`ファイル内の3つの主要な箇所が変更されています。

1.  **`go`コマンドの記述の修正**:
    ```diff
    -for build-time source code generation
    -and TODO.
    +for build-time source code generation.
    ```
    この変更では、`go`コマンドがビルド時のソースコード生成をサポートすることを示す記述から、不要な「and TODO.」というプレースホルダーが削除されました。これにより、リリースノートの記述がより簡潔かつ正確になりました。

2.  **`gccgo`ステータスの更新**:
    ```diff
    -TODO gccgo news
    +The release schedules for the GCC and Go projects do not coincide.
    +GCC release 4.9 contains the Go 1.2 version of gccgo.
    +The next release, GCC 5, will likely have the Go 1.4 version of gccgo.
    ```
    これはこのコミットの最も重要な変更点です。以前は「TODO gccgo news」という一般的な記述でしたが、GoとGCCのリリースサイクルの違いを明確にし、具体的な`gccgo`のバージョン対応情報が追加されました。具体的には、GCC 4.9がGo 1.2の`gccgo`を含み、次のGCC 5がGo 1.4の`gccgo`を含む可能性が高いことが明記されました。これにより、`gccgo`ユーザーは自身の環境とGoバージョンの互換性をより正確に把握できるようになります。

3.  **`crypto/tls`パッケージに関する記述の修正**:
    ```diff

    -the server now supports

    -to help clients detect fallback attacks like
    -<a href="http://googleonlinesecurity.blogspot.com/2014/10/this-poodle-bites-exploiting-ssl-30.html">POODLE</a>.
    -(The crypto/tls package\'s client has never supported SSLv3, so it is not
    -vulnerable to the POODLE attack.)
    +to help clients detect fallback attacks.
    +(The Go client does not support fallback at all, so it is not vulnerable to
    +those attacks.)
    ```
    この変更では、`crypto/tls`パッケージに関する記述が修正されました。
    *   まず、HTMLタグの`<a>`と`<code>`が削除され、より簡潔なテキスト表現になりました。
    *   次に、`TLS_FALLBACK_SCSV`がPOODLE攻撃のような特定の攻撃だけでなく、「fallback attacks」全般を検出するのに役立つという、より一般的な表現に変更されました。
    *   最後に、GoクライアントがPOODLE攻撃に脆弱ではない理由について、「SSLv3をサポートしていないため」という限定的な理由から、「fallbackを全くサポートしていないため」という、より広範な理由に修正されました。これは、Goクライアントがダウングレード攻撃に対してより堅牢であることを示唆しています。

これらの変更は、Go 1.4のリリースノートの正確性、明確性、および最新性を向上させることを目的としています。

## 元コミット内容

`[dev.ssa] cmd/compile: don't move mem-using values in tighten pass`

このコミットは、GoコンパイラのSSAバックエンドにおける `tighten` パスにおいて、メモリを使用する値（mem-using values）の移動を禁止するものです。その理由は、移動先の場所が異なる「ライブメモリ」（有効なメモリ状態）を持つ可能性があり、その結果、2つの異なるメモリ状態が同時にライブになるという安全でない状況を引き起こすためです。

## 変更の背景

GoコンパイラのSSAバックエンドには、コードを最適化するための様々なパスが存在します。`tighten` パスもその一つで、特定の条件を満たす値をプログラム内の別の場所（別の基本ブロック）に移動させることで、コードの効率を向上させることを目的としていました。

しかし、この最適化ロジックには、メモリ操作に関連する値（例えば、メモリの読み書きや、メモリ状態を変更する可能性のある関数呼び出しなど）を扱う際に潜在的な問題がありました。SSA形式では、メモリの状態も一種の「値」として扱われ、メモリ操作は前のメモリ状態を入力として受け取り、新しいメモリ状態を出力として生成するという形で表現されます。これにより、メモリ操作の順序が明確になり、データフロー解析が容易になります。

問題は、`tighten` パスがメモリに依存する値を、その値が元々依存していたメモリ状態とは異なる「ライブメモリ」を持つ基本ブロックに移動させようとした場合に発生しました。このような移動が行われると、SSAの原則である「各変数は一度だけ割り当てられる」というルールがメモリ状態に関して破られ、プログラムの異なる箇所で同時に複数のメモリ状態が有効であるかのように扱われることになります。これはコンパイラの内部状態の不整合を引き起こし、最終的には不正なコード生成やランタイムエラーにつながる可能性がありました。

このコミットは、このようなメモリ状態の不整合を防ぐための安全策として導入されました。メモリに依存する値の移動を明示的に禁止することで、SSAバックエンドの堅牢性と正確性を保証しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **GoコンパイラとSSA (Static Single Assignment) フォーム**:
    *   **Goコンパイラ**: Go言語のソースコードを機械語に変換するツールです。最適化段階で中間表現を使用します。
    *   **SSAフォーム**: コンパイラ最適化で広く用いられる中間表現の一つです。SSA形式では、プログラム中の各変数が「一度だけ」代入されるように変換されます。例えば、`x = a + b; x = c + d;` はSSAでは `x1 = a + b; x2 = c + d;` のようになります。これにより、データフロー解析が非常に容易になり、様々な最適化（デッドコード削除、共通部分式除去など）が効率的に行えます。
    *   **GoコンパイラのSSAバックエンド**: Go 1.7以降、GoコンパイラはSSA形式を主要な中間表現として採用し、より強力な最適化を実現しています。

2.  **SSAにおけるメモリの表現**:
    *   SSA形式は通常、レジスタに格納されるようなスカラー値のデータフローを扱うのに適していますが、メモリ（ヒープやスタック上のデータ）の読み書きは副作用を伴うため、直接SSAの原則に当てはめるのが難しい場合があります。
    *   GoのSSAバックエンドでは、メモリの状態を抽象的な「メモリ値」として扱います。メモリを読み書きする操作（例: `Load`, `Store`, `Call`）は、現在のメモリ状態を表す「メモリ値」を入力として受け取り、操作後の新しいメモリ状態を表す「メモリ値」を出力として生成します。
    *   これにより、メモリ操作もSSAのデータフローグラフの一部として表現され、コンパイラはメモリ操作の順序や依存関係を正確に追跡できるようになります。`Type.IsMemory()` は、ある値がこの「メモリ値」であることを示す型チェックです。

3.  **基本ブロック (Basic Block)**:
    *   コンパイラ最適化における基本的な概念で、プログラムの制御フローグラフのノードです。
    *   基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令シーケンスです。
    *   コード移動の最適化は、通常、値をある基本ブロックから別の基本ブロックへ移動させることを含みます。

4.  **`tighten` パス**:
    *   GoコンパイラのSSAバックエンドにおける最適化パスの一つです。
    *   その具体的な目的は、コードの局所性を高めたり、不要な命令を削除したりすることにあります。このコミットの文脈では、特定の条件を満たす値を、その値が使用されるブロックの近くに移動させることで、レジスタ割り当ての効率を向上させるなどの最適化を試みていました。

5.  **ライブメモリ (Live Memory)**:
    *   特定のプログラムポイントにおいて、有効であるとコンパイラが認識しているメモリの状態を指します。SSA形式では、メモリ値のデータフローによって、どのメモリ状態がどの時点で「ライブ」であるかが決定されます。

## 技術的詳細

このコミットが修正しているのは、GoコンパイラのSSAバックエンドにおける `tighten` パスのロジックです。`tighten` パスは、関数 `tighten(f *Func)` 内で、各値 `v` について移動の可否を判断しています。

既存のロジックでは、以下の条件を満たす値 `v` を移動対象としていました（簡略化された条件）：
*   `v` が `GetClosurePtr` のような特定の特殊な値ではない。
*   `v` がちょうど1箇所でしか使用されていない (`uses[v.ID] == 1`)。
*   `v` が φ関数（Phi function）ではない (`!phi[v.ID]`)。
*   `v` が定義された基本ブロック (`home[v.ID]`) と、使用される基本ブロック (`b`) が異なる。
*   `v` が持つ引数の数が2未満である (`len(v.Args) < 2`)。

これらの条件は、スカラー値の移動には適切かもしれませんが、メモリに依存する値に対しては不十分でした。メモリに依存する値は、その値が定義された時点のメモリ状態を「消費」し、新しいメモリ状態を「生成」します。もしこの値を、その消費すべきメモリ状態が「ライブ」ではない別の基本ブロックに移動させてしまうと、コンパイラはどのメモリ状態をその値の入力として使うべきか判断できなくなります。

具体的には、コミットメッセージにある「might have a different live memory」とは、移動先のブロックでは、移動しようとしている値が依存するメモリ値とは異なるメモリ値が「現在の有効なメモリ状態」として認識されている可能性があることを意味します。その結果、「Moving will introduce two simultaneously live memories」となり、SSAのメモリモデルが破綻します。これは、メモリ状態のデータフローグラフに矛盾が生じることを意味し、コンパイラがメモリの整合性を正しく追跡できなくなります。

このコミットは、この問題を解決するために、移動の条件に新たな制約を追加しています。

## コアとなるコードの解説

追加されたコードは、`tighten` パスが値を移動させるかどうかの判断ロジックに、新たな条件を追加しています。

1.  `len(v.Args) > 0`:
    *   これは、現在処理している値 `v` が少なくとも1つ以上の引数を持っていることを確認する条件です。引数を持たない値（例: 定数）はメモリに依存しないため、このチェックの対象外となります。

2.  `v.Args[len(v.Args)-1].Type.IsMemory()`:
    *   これがこのコミットの核心となるチェックです。
    *   `v.Args[len(v.Args)-1]` は、値 `v` の最後の引数を参照します。GoのSSAバックエンドでは、メモリ操作を表す値（例: `OpLoad`, `OpStore`, `OpCall` など）は、慣習的に現在のメモリ状態を最後の引数として受け取ります。
    *   `.Type.IsMemory()` は、その引数の型がメモリ型であるかどうかを判定するメソッドです。
    *   したがって、この条件全体は、「値 `v` が引数を持ち、かつその最後の引数がメモリ型である」ことを意味します。これは、`v` がメモリ状態に依存する操作、またはメモリ状態を生成する操作であることを示唆しています。

3.  `continue`:
    *   上記の条件が `true` の場合、つまり `v` がメモリに依存する値であると判断された場合、`tighten` パスは現在の `v` の処理をスキップし、次の値の処理に移ります。
    *   これにより、メモリに依存する値が、安全でない方法で別の基本ブロックに移動されることが防止されます。

4.  コメント:
    *   `// We can't move values which have a memory arg - it might`
    *   `// make two memory values live across a block boundary.`
    *   このコメントは、なぜこの制約が必要なのかを明確に説明しています。メモリ引数を持つ値を移動させると、基本ブロックの境界を越えて2つの異なるメモリ値が同時に「ライブ」になる可能性があり、これはSSAのメモリモデルの整合性を損なうため、移動は許可されない、という理由が述べられています。

この変更により、GoコンパイラのSSAバックエンドは、メモリ操作の安全性をより厳密に保証し、不正な最適化による潜在的なバグを防ぐことができるようになりました。

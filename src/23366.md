# [インデックス 23366] ファイルの概要

このコミットは、Goランタイムにおける`heapBitsSetType`関数のベンチマークを追加するものです。以前は間接的にアロケーションを介して測定されていましたが、アロケーションコストが測定結果に与える影響が大きく、正確な評価が困難でした。この変更により、`heapBitsSetType`単体の性能を直接測定できる新しいベンチマークが導入されました。これは、`heapBitsSetType`が`mallocgc`から分離されたことで可能になりました。

## 元コミット内容

このコミットは、Goランタイムのベンチマークに関するものです。具体的には、`heapBitsSetType`という関数の性能を測定するための新しいベンチマークを追加し、既存の不正確なベンチマークを置き換えています。

変更の概要は以下の通りです。

-   `src/runtime/export_test.go` に `BenchSetType` というテスト用関数を追加。この関数は、指定された型とサイズに基づいて `heapBitsSetType` を直接呼び出す。
-   `src/runtime/gc_test.go` から、アロケーションを伴う古い `BenchmarkSetTypeNoPtrX` および `BenchmarkSetTypePtrX` ベンチマークを削除。
-   `src/runtime/gc_test.go` に、`BenchSetType` を利用して様々なデータ構造（ポインタ、スライス、構造体など）に対して `heapBitsSetType` の性能を測定する新しいベンチマーク群を追加。

## 変更の背景

Goのランタイム、特にガベージコレクション（GC）の性能は、アプリケーション全体のパフォーマンスに直結する重要な要素です。`heapBitsSetType`は、GCがヒープ上のオブジェクトのポインタ情報を管理するために使用する低レベルの関数であり、その効率性はGCのサイクルタイムに大きな影響を与えます。

以前のベンチマークは、`heapBitsSetType`の性能を間接的に測定していました。具体的には、オブジェクトのアロケーション（`mallocgc`）を通じて測定していましたが、この方法ではアロケーション自体のコストと`heapBitsSetType`のコストを分離して評価することが困難でした。そのため、得られたベンチマーク結果の解釈が難しく、`heapBitsSetType`の真の性能特性を把握することができませんでした。

このコミットの背景には、`heapBitsSetType`が`mallocgc`から独立した関数として切り出されたという重要な変更があります。これにより、`heapBitsSetType`を直接呼び出してその性能を測定することが技術的に可能になりました。この機会を捉え、より正確で直接的なベンチマークを導入することで、Goランタイム開発者が`heapBitsSetType`の最適化やGCの改善を行う際の信頼性の高いデータを提供することが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **Goのメモリ管理とヒープ**:
    *   Goプログラムは、実行時にメモリを動的に確保します。この動的に確保されるメモリ領域を「ヒープ」と呼びます。
    *   ヒープ上のオブジェクトは、ガベージコレクタによって管理され、不要になったオブジェクトは自動的に解放されます。

2.  **ガベージコレクション (GC)**:
    *   GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。これは、到達可能なオブジェクトをマークし、マークされなかった（到達不可能な）オブジェクトをスイープ（解放）するプロセスです。
    *   GCは、ヒープ上のオブジェクトがポインタを含むかどうか、そしてどのフィールドがポインタであるかを知る必要があります。これにより、GCはオブジェクトグラフをたどって到達可能なオブジェクトを正確に識別できます。

3.  **ヒープビット (Heap Bits)**:
    *   Goランタイムは、ヒープ上の各メモリブロック（オブジェクト）について、そのブロックがポインタを含むかどうか、そしてポインタがどこにあるかを示すメタデータ（「ヒープビット」または「ポインタビット」）を管理しています。
    *   このヒープビットは、GCがオブジェクトをスキャンする際に非常に重要です。GCはヒープビットを参照して、どのメモリ位置をポインタとして解釈し、さらにたどるべきかを判断します。

4.  **`heapBitsSetType` 関数**:
    *   `heapBitsSetType`は、Goランタイムの内部関数で、新しくアロケートされたオブジェクトのヒープビットを設定する役割を担います。
    *   オブジェクトがヒープに割り当てられる際、そのオブジェクトの型情報に基づいて、どの部分がポインタであるかをヒープビットに記録します。これにより、GCが後でそのオブジェクトを正確にスキャンできるようになります。

5.  **`mallocgc` 関数**:
    *   `mallocgc`は、Goランタイムの内部関数で、ヒープからメモリをアロケートする主要な関数です。
    *   以前は、`heapBitsSetType`の機能が`mallocgc`の内部に組み込まれていました。つまり、メモリをアロケートするたびに、そのオブジェクトのヒープビット設定も同時に行われていました。

6.  **`systemstack`**:
    *   Goランタイムには、通常のGoルーチンのスタックとは異なる「システムスタック」という概念があります。
    *   `systemstack`は、GCやスケジューラなどのランタイムの低レベルな処理を実行するために使用されます。これらの処理は、GoルーチンのスケジューリングやGCの動作に影響を与えないように、特別なコンテキストで実行される必要があります。
    *   `systemstack`内で実行されるコードは、Goルーチンのプリエンプション（横取り）の影響を受けず、より予測可能な実行が可能です。

7.  **`reflect` パッケージ**:
    *   Goの`reflect`パッケージは、実行時に型情報を検査したり、値の操作を行ったりするための機能を提供します。
    *   ベンチマークコードでは、`reflect.ValueOf(x)`や`v.Type()`、`t.Kind()`、`t.Elem().Size()`などを使用して、ベンチマーク対象のオブジェクトの型やサイズ情報を動的に取得しています。

8.  **`unsafe` パッケージ**:
    *   `unsafe`パッケージは、Goの型安全性をバイパスして、ポインタとメモリを直接操作するための機能を提供します。
    *   `BenchSetType`関数では、`unsafe.Pointer`を使用してインターフェース値から基となる型情報やデータポインタを抽出しています。これは、Goの型システムでは通常許されない低レベルな操作であり、ランタイムの内部処理やベンチマークのような特殊なケースでのみ使用されます。

## 技術的詳細

このコミットの技術的な核心は、`heapBitsSetType`のベンチマーク方法の改善にあります。

### `heapBitsSetType`の分離と直接ベンチマークの可能性

以前は`mallocgc`の一部であった`heapBitsSetType`が独立した関数として切り出されたことで、その関数単体の性能を測定することが可能になりました。これは、Goランタイムのモジュール化と、各コンポーネントの独立した評価を可能にする上で重要な進歩です。

### `export_test.go`における`BenchSetType`の実装

`src/runtime/export_test.go`に追加された`BenchSetType`関数は、Goランタイムの内部関数である`heapBitsSetType`をテストパッケージから呼び出すためのエクスポートされたラッパーです。

```go
func BenchSetType(n int, x interface{}) {
	e := *(*eface)(unsafe.Pointer(&x)) // インターフェース値から内部表現 (eface) を抽出
	t := e._type                     // 型情報 (runtime._type) を取得
	var size uintptr
	var p unsafe.Pointer

	// xの型に応じて、要素の型、サイズ、データポインタを決定
	switch t.kind & kindMask {
	case _KindPtr: // ポインタ型の場合
		t = (*ptrtype)(unsafe.Pointer(t)).elem // ポインタが指す要素の型を取得
		size = t.size                          // 要素のサイズ
		p = e.data                             // データポインタ
	case _KindSlice: // スライス型の場合
		slice := *(*struct {
			ptr      unsafe.Pointer
			len, cap uintptr
		})(e.data) // スライスの内部構造を抽出
		t = (*slicetype)(unsafe.Pointer(t)).elem // スライスの要素の型を取得
		size = t.size * slice.len                // スライス全体のサイズ
		p = slice.ptr                            // スライスのデータポインタ
	}
	allocSize := roundupsize(size) // アロケーションサイズを丸める

	systemstack(func() { // システムスタックで実行
		for i := 0; i < n; i++ {
			// heapBitsSetTypeを直接呼び出し
			heapBitsSetType(uintptr(p), allocSize, size, t)
		}
	})
}
```

この関数は以下の重要な技術的側面を含んでいます。

*   **`unsafe`パッケージの使用**: `interface{}`から基となる型情報やデータポインタを抽出するために`unsafe.Pointer`が多用されています。これは、Goの型システムをバイパスしてランタイムの内部構造にアクセスするための典型的なパターンです。
*   **型情報の解析**: `_type`構造体や`kindMask`、`_KindPtr`、`_KindSlice`などのランタイム内部の定数や構造体を使用して、渡されたインターフェース`x`の具体的な型（ポインタ、スライスなど）を判別し、その要素の型やサイズ、データポインタを正確に特定しています。
*   **`systemstack`での実行**: `heapBitsSetType`はランタイムの低レベルなGC関連処理であるため、Goルーチンのスケジューリングやプリエンプションの影響を受けない`systemstack`上で実行されます。これにより、ベンチマークの測定精度が向上します。
*   **`heapBitsSetType`の直接呼び出し**: `for`ループ内で`heapBitsSetType(uintptr(p), allocSize, size, t)`を直接呼び出すことで、アロケーションのオーバーヘッドなしに、この関数単体の実行時間を測定しています。

### `gc_test.go`におけるベンチマークの再構築

`src/runtime/gc_test.go`では、`BenchmarkSetTypeNoPtrX`や`BenchmarkSetTypePtrX`といった古いベンチマークが削除され、新しい`benchSetType`ヘルパー関数とそれを利用した多数のベンチマークが追加されました。

```go
func benchSetType(b *testing.B, x interface{}) {
	v := reflect.ValueOf(x)
	t := v.Type()
	switch t.Kind() {
	case reflect.Ptr:
		b.SetBytes(int64(t.Elem().Size())) // ポインタが指す要素のサイズをベンチマークのバイト数として設定
	case reflect.Slice:
		b.SetBytes(int64(t.Elem().Size()) * int64(v.Len())) // スライス全体のサイズをベンチマークのバイト数として設定
	}
	b.ResetTimer() // タイマーをリセットし、準備段階の時間を測定から除外
	runtime.BenchSetType(b.N, x) // 実際のベンチマーク実行
}
```

このヘルパー関数は、`reflect`パッケージを使用してベンチマーク対象のオブジェクトの型とサイズを動的に取得し、`b.SetBytes()`を呼び出してベンチマークの処理バイト数を設定します。これにより、ベンチマーク結果がより意味のあるものになります（例: 1操作あたり何バイト処理したか）。`b.ResetTimer()`は、ベンチマークの準備にかかる時間を測定から除外するために重要です。

新しいベンチマーク群は、以下のような様々なシナリオをカバーしています。

*   **ポインタの数**: `*byte`, `[8]*byte`, `[128]*byte` など、ポインタの数が異なる配列や構造体。
*   **スライス**: `make([]*byte, 1<<10)` のような大きなスライス。
*   **構造体のレイアウト**: `Node1`, `Node8`, `Node64`, `Node124`, `Node126`, `Node1024` といった、`uintptr`フィールドとポインタフィールドの配置が異なる構造体。特に`Node64Dead`のようにポインタフィールドが構造体の最後に配置されているケースも含まれており、これはGCがポインタをスキャンする際の挙動に影響を与える可能性があります。

これらの多様なベンチマークケースにより、`heapBitsSetType`が様々なデータ構造やサイズに対してどのように振る舞うかを詳細に分析できるようになります。

## コアとなるコードの解説

### `src/runtime/export_test.go` の `BenchSetType` 関数

この関数は、`runtime`パッケージの内部関数である`heapBitsSetType`を、`runtime_test`パッケージから呼び出せるようにエクスポートするためのラッパーです。

1.  **インターフェース値の解析**:
    `e := *(*eface)(unsafe.Pointer(&x))`
    `t := e._type`
    Goのインターフェース値`x`は、内部的には`eface`（または`iface`）という構造体で表現されます。`eface`は、値の型情報（`_type`）とデータポインタ（`data`）を含んでいます。`unsafe.Pointer`を使って`x`のアドレスを`eface`ポインタにキャストし、その内容をデリファレンスすることで、型情報`t`を取得しています。

2.  **型に応じたデータ抽出**:
    `switch t.kind & kindMask`
    `_type`構造体の`kind`フィールドは、その型がプリミティブ型、構造体、ポインタ、スライスなど、どのような種類であるかを示します。`kindMask`を使って種類を抽出し、`_KindPtr`（ポインタ）や`_KindSlice`（スライス）の場合に特別な処理を行います。
    *   **ポインタ型**: `t = (*ptrtype)(unsafe.Pointer(t)).elem` で、ポインタが指す要素の型（`elem`）を取得します。`size`はその要素のサイズ、`p`はデータポインタとなります。
    *   **スライス型**: スライスの内部構造（データポインタ`ptr`、長さ`len`、容量`cap`）を`unsafe.Pointer`で抽出し、スライスの要素型`elem`とスライス全体のサイズ`t.size * slice.len`、データポインタ`slice.ptr`を特定します。

3.  **アロケーションサイズの丸め**:
    `allocSize := roundupsize(size)`
    `roundupsize`は、Goランタイムの内部関数で、指定されたサイズをメモリページサイズやアロケータのチャンクサイズに合わせて切り上げる役割があります。これは、実際のメモリ割り当てが常に特定の単位で行われるためです。

4.  **`systemstack`での実行**:
    `systemstack(func() { ... })`

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

1.  **Goのメモリ管理とヒープ**:
    *   Goプログラムは、実行時にメモリを動的に確保します。この動的に確保されるメモリ領域を「ヒープ」と呼びます。
    *   ヒープ上のオブジェクトは、ガベージコレクタによって管理され、不要になったオブジェクトは自動的に解放されます。

2.  **ガベージコレクション (GC)**:
    *   GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。これは、到達可能なオブジェクトをマークし、マークされなかった（到達不可能な）オブジェクトをスイープ（解放）するプロセスです。
    *   GCは、ヒープ上のオブジェクトがポインタを含むかどうか、そしてどのフィールドがポインタであるかを知る必要があります。これにより、GCはオブジェクトグラフをたどって到達可能なオブジェクトを正確に識別できます。

3.  **ヒープビット (Heap Bits)**:
    *   Goランタイムは、ヒープ上の各メモリブロック（オブジェクト）について、そのブロックがポインタを含むかどうか、そしてポインタがどこにあるかを示すメタデータ（「ヒープビット」または「ポインタビット」）を管理しています。
    *   このヒープビットは、GCがオブジェクトをスキャンする際に非常に重要です。GCはヒープビットを参照して、どのメモリ位置をポインタとして解釈し、さらにたどるべきかを判断します。

4.  **`heapBitsSetType` 関数**:
    *   `heapBitsSetType`は、Goランタイムの内部関数で、新しくアロケートされたオブジェクトのヒープビットを設定する役割を担います。
    *   オブジェクトがヒープに割り当てられる際、そのオブジェクトの型情報に基づいて、どの部分がポインタであるかをヒープビットに記録します。これにより、GCが後でそのオブジェクトを正確にスキャンできるようになります。

5.  **`mallocgc` 関数**:
    *   `mallocgc`は、Goランタイムの内部関数で、ヒープからメモリをアロケートする主要な関数です。
    *   以前は、`heapBitsSetType`の機能が`mallocgc`の内部に組み込まれていました。つまり、メモリをアロケートするたびに、そのオブジェクトのヒープビット設定も同時に行われていました。

6.  **`systemstack`**:
    *   Goランタイムには、通常のGoルーチンのスタックとは異なる「システムスタック」という概念があります。
    *   `systemstack`は、GCやスケジューラなどのランタイムの低レベルな処理を実行するために使用されます。これらの処理は、GoルーチンのスケジューリングやGCの動作に影響を与えないように、特別なコンテキストで実行される必要があります。
    *   `systemstack`内で実行されるコードは、Goルーチンのプリエンプション（横取り）の影響を受けず、より予測可能な実行が可能です。

7.  **`reflect` パッケージ**:
    *   Goの`reflect`パッケージは、実行時に型情報を検査したり、値の操作を行ったりするための機能を提供します。
    *   ベンチマークコードでは、`reflect.ValueOf(x)`や`v.Type()`、`t.Kind()`、`t.Elem().Size()`などを使用して、ベンチマーク対象のオブジェクトの型やサイズ情報を動的に取得しています。

8.  **`unsafe` パッケージ**:
    *   `unsafe`パッケージは、Goの型安全性をバイパスして、ポインタとメモリを直接操作するための機能を提供します。
    *   `BenchSetType`関数では、`unsafe.Pointer`を使用してインターフェース値から基となる型情報やデータポインタを抽出しています。これは、Goの型システムでは通常許されない低レベルな操作であり、ランタイムの内部処理やベンチマークのような特殊なケースでのみ使用されます。

### `heapBitsSetType`の分離と直接ベンチマークの可能性

以前は`mallocgc`の一部であった`heapBitsSetType`が独立した関数として切り出されたことで、その関数単体の性能を測定することが可能になりました。これは、Goランタイムのモジュール化と、各コンポーネントの独立した評価を可能にする上で重要な進歩です。

### `export_test.go`における`BenchSetType`の実装

`src/runtime/export_test.go`に追加された`BenchSetType`関数は、Goランタイムの内部関数である`heapBitsSetType`をテストパッケージから呼び出すためのエクスポートされたラッパーです。

```go
func BenchSetType(n int, x interface{}) {
	e := *(*eface)(unsafe.Pointer(&x)) // インターフェース値から内部表現 (eface) を抽出
	t := e._type                     // 型情報 (runtime._type) を取得
	var size uintptr
	var p unsafe.Pointer

	// xの型に応じて、要素の型、サイズ、データポインタを決定
	switch t.kind & kindMask {
	case _KindPtr: // ポインタ型の場合
		t = (*ptrtype)(unsafe.Pointer(t)).elem // ポインタが指す要素の型を取得
		size = t.size                          // 要素のサイズ
		p = e.data                             // データポインタ
	case _KindSlice: // スライス型の場合
		slice := *(*struct {
			ptr      unsafe.Pointer
			len, cap uintptr
		})(e.data) // スライスの内部構造を抽出
		t = (*slicetype)(unsafe.Pointer(t)).elem // スライスの要素の型を取得
		size = t.size * slice.len                // スライス全体のサイズ
		p = slice.ptr                            // スライスのデータポインタ
	}
	allocSize := roundupsize(size) // アロケーションサイズを丸める

	systemstack(func() { // システムスタックで実行
		for i := 0; i < n; i++ {
			// heapBitsSetTypeを直接呼び出し
			heapBitsSetType(uintptr(p), allocSize, size, t)
		}
	})
}
```

この関数は以下の重要な技術的側面を含んでいます。

*   **`unsafe`パッケージの使用**: `interface{}`から基となる型情報やデータポインタを抽出するために`unsafe.Pointer`が多用されています。これは、Goの型システムをバイパスしてランタイムの内部構造にアクセスするための典型的なパターンです。
*   **型情報の解析**: `_type`構造体や`kindMask`、`_KindPtr`、`_KindSlice`などのランタイム内部の定数や構造体を使用して、渡されたインターフェース`x`の具体的な型（ポインタ、スライスなど）を判別し、その要素の型やサイズ、データポインタを正確に特定しています。
*   **`systemstack`での実行**: `heapBitsSetType`はランタイムの低レベルなGC関連処理であるため、Goルーチンのスケジューリングやプリエンプションの影響を受けない`systemstack`上で実行されます。これにより、ベンチマークの測定精度が向上します。
*   **`heapBitsSetType`の直接呼び出し**: `for`ループ内で`heapBitsSetType(uintptr(p), allocSize, size, t)`を直接呼び出すことで、アロケーションのオーバーヘッドなしに、ヒープビット設定処理の純粋なコストを測定できます。

## コアとなるコードの解説

### `src/runtime/export_test.go` の `BenchSetType` 関数

この関数は、`runtime`パッケージの内部関数である`heapBitsSetType`を、`runtime_test`パッケージから呼び出せるようにエクスポートするためのラッパーです。

1.  **インターフェース値の解析**:
    `e := *(*eface)(unsafe.Pointer(&x))`
    `t := e._type`
    Goのインターフェース値`x`は、内部的には`eface`（または`iface`）という構造体で表現されます。`eface`は、値の型情報（`_type`）とデータポインタ（`data`）を含んでいます。`unsafe.Pointer`を使って`x`のアドレスを`eface`ポインタにキャストし、その内容をデリファレンスすることで、型情報`t`を取得しています。

2.  **型に応じたデータ抽出**:
    `switch t.kind & kindMask`
    `_type`構造体の`kind`フィールドは、その型がプリミティブ型、構造体、ポインタ、スライスなど、どのような種類であるかを示します。`kindMask`を使って種類を抽出し、`_KindPtr`（ポインタ）や`_KindSlice`（スライス）の場合に特別な処理を行います。
    *   **ポインタ型**: `t = (*ptrtype)(unsafe.Pointer(t)).elem` で、ポインタが指す要素の型（`elem`）を取得します。`size`はその要素のサイズ、`p`はデータポインタとなります。
    *   **スライス型**: スライスの内部構造（データポインタ`ptr`、長さ`len`、容量`cap`）を`unsafe.Pointer`で抽出し、スライスの要素型`elem`とスライス全体のサイズ`t.size * slice.len`、データポインタ`slice.ptr`を特定します。

3.  **アロケーションサイズの丸め**:
    `allocSize := roundupsize(size)`
    `roundupsize`は、Goランタイムの内部関数で、指定されたサイズをメモリページサイズやアロケータのチャンクサイズに合わせて切り上げる役割があります。これは、実際のメモリ割り当てが常に特定の単位で行われるためです。

4.  **`systemstack`での実行**:
    `systemstack(func() { ... })`
    `heapBitsSetType`はGCの根幹に関わる低レベルな処理であり、Goルーチンの通常のスケジューリングから独立して実行される必要があります。`systemstack`内で実行することで、GCのプリエンプションなどによる影響を受けずに、安定したベンチマーク測定を可能にします。

5.  **`heapBitsSetType`の呼び出し**:
    `heapBitsSetType(uintptr(p), allocSize, size, t)`
    ループ内で`heapBitsSetType`を`n`回呼び出します。引数として、データポインタ`p`、アロケーションサイズ`allocSize`、実際のデータサイズ`size`、そして型情報`t`を渡します。これにより、アロケーションのオーバーヘッドなしに、ヒープビット設定処理の純粋なコストを測定できます。

### `src/runtime/gc_test.go` の `benchSetType` ヘルパー関数とベンチマーク群

このファイルでは、`testing`パッケージのベンチマーク機能を利用して、`BenchSetType`関数を呼び出すためのヘルパー関数と、様々なデータ構造に対するベンチマークが定義されています。

1.  **`benchSetType` ヘルパー関数**:
    `func benchSetType(b *testing.B, x interface{})`
    この関数は、各ベンチマーク関数から呼び出され、共通のセットアップと実行ロジックを提供します。
    *   **`reflect`による型とサイズの取得**: `reflect.ValueOf(x)`と`v.Type()`を使って、ベンチマーク対象`x`の型情報を取得します。
    *   **`b.SetBytes()`**: `b.SetBytes(int64(t.Elem().Size()))` または `b.SetBytes(int64(t.Elem().Size()) * int64(v.Len()))` を呼び出すことで、ベンチマークの1操作あたりに処理されたバイト数を`testing`パッケージに伝えます。これにより、ベンチマーク結果が「ops/sec」だけでなく「MB/sec」のような形で表示され、より意味のある性能指標が得られます。
    *   **`b.ResetTimer()`**: `b.ResetTimer()`は、ベンチマークのセットアップ（この場合は`reflect`による型情報の取得など）にかかる時間を測定から除外するために呼び出されます。これにより、`heapBitsSetType`の純粋な実行時間のみが測定対象となります。
    *   **`runtime.BenchSetType(b.N, x)`**: `export_test.go`で定義された`BenchSetType`関数を呼び出し、`b.N`回（ベンチマークフレームワークが決定する繰り返し回数）`heapBitsSetType`を実行します。

2.  **新しいベンチマーク群**:
    `BenchmarkSetTypePtr`, `BenchmarkSetTypePtr8`, ..., `BenchmarkSetTypeNode1024Slice`
    これらのベンチマークは、`benchSetType`ヘルパー関数を呼び出し、様々な型のオブジェクト（ポインタ、ポインタの配列、スライス、`uintptr`とポインタを含む構造体など）を渡します。これにより、`heapBitsSetType`が異なるメモリレイアウトやポインタ密度を持つオブジェクトに対して、どのように性能が変化するかを詳細に分析できるようになります。特に、`NodeX`構造体は、`uintptr`フィールドとポインタフィールドの配置が異なる複数のバリエーションがあり、GCがポインタをスキャンする際のキャッシュ効率や処理パスの違いを評価するのに役立ちます。

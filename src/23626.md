# [インデックス 23626] ファイルの概要

このコミットは、Goランタイムにおいて、スタックバリア追跡のための領域をスタック自体から確保する変更を導入します。これは、ガベージコレクション（GC）の際にスタックをスキャンする効率を向上させるための準備作業の一環です。具体的には、スタックバリアのブックキーピング構造体をスタック割り当て時に確保し、GC中の再帰的な割り当てを避けるためのメカニズムを実装しています。

## コミット

Goランタイムにおいて、スタックバリア追跡に必要なブックキーピング構造体を、スタック割り当て時にスタック領域から「盗む」形で確保するように変更しました。これにより、GC中に発生しうる再帰的なメモリ割り当ての問題を回避し、将来的に導入されるスタックバリア機能の基盤を構築します。

of the overwritten return PCs. This commit introduces and allocates
this structure, but does not yet use the structure.

## 変更の背景

Goのガベージコレクタは、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCプロセスにおいて、スタックは重要なスキャン対象の一つです。特に、スタックが成長したり縮小したりする際に、GCが正確にルート（参照元）を特定できるようにする必要があります。

このコミットの背景には、Goランタイムが将来的に導入する「スタックバリア (stack barrier)」というメカニズムがあります。スタックバリアは、GCがスタックをスキャンする際に、特定のポイントでスタックの状態を記録し、GCの正確性を保証するためのものです。例えば、関数呼び出しの戻りアドレス (Return PC) がGCによって一時的に書き換えられるような状況で、元の値を追跡する必要が生じます。

このブックキーピング構造体は、スタックバリアがオーバーライトした戻りPCの情報を追跡するために必要となります。しかし、この構造体をGC中に通常のメモリ割り当て（`mallocgc`）で確保しようとすると、`mallocgc`自体がスタックを拡張する可能性があり、結果として再帰的な割り当てが発生し、デッドロックやランタイムエラーを引き起こす可能性があります。

この問題を回避するため、このコミットでは、スタックバリア追跡用の構造体を、**スタック自体の割り当て時に、そのスタック領域の一部を「盗む」形で確保する**というアプローチを採用しています。これにより、GC中の動的なメモリ割り当てを避け、安全かつ効率的にスタックバリアの基盤を構築することが目的です。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ (Tri-color Mark and Sweep)」アルゴリズムをベースにしたコンカレントGCです。これは、プログラムの実行と並行してGCが動作することを意味します。

*   **マークフェーズ**: GCは、到達可能なオブジェクト（プログラムから参照されているオブジェクト）をマークします。
*   **スキャンフェーズ**: マークされたオブジェクトからさらに参照をたどり、到達可能なすべてのオブジェクトをマークします。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）をメモリから解放します。

コンカレントGCでは、GCがマークフェーズを実行している間に、プログラム（ミューテータ）がオブジェクトグラフを変更する可能性があります。この変更によってGCの正確性が損なわれないように、Goランタイムは「ライトバリア (write barrier)」などのメカニズムを使用します。

### スタック管理とスタックの成長/縮小

GoのGoroutineは、比較的小さなスタック（通常は数KB）で開始し、必要に応じて動的にスタックを成長させたり縮小させたりします。

*   **スタックの成長**: 関数呼び出しが深くネストしたり、大きなローカル変数が確保されたりして、現在のスタック領域が不足すると、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、スタックポインタを更新します。
*   **スタックの縮小**: 関数がリターンしてスタックの使用量が減ると、ランタイムはスタックを縮小してメモリを解放することがあります。

GCは、これらのスタック領域もスキャンして、スタック上に存在するポインタ（他のオブジェクトへの参照）を特定し、マークする必要があります。

### スタックバリア (Stack Barrier)

スタックバリアは、GoのGCがスタックをスキャンする際の正確性を保証するためのメカニズムの一つです。特に、スタックの成長や縮小、あるいは特定の最適化によって、スタック上の戻りアドレス (Return PC) が一時的に書き換えられるような状況で重要になります。

例えば、GCがスタックをスキャンしている最中に、ある関数が別の関数を呼び出し、その際にスタックが成長したとします。このとき、GCが古いスタックと新しいスタックの両方を正しく処理し、ポインタを見落とさないようにするために、スタックバリアが役立ちます。

このコミットで導入されるブックキーピング構造体は、スタックバリアが「オーバーライトした戻りPC」の元の値を記録するために使用されます。これにより、GCがスタックをスキャンする際に、一時的に変更された戻りPCであっても、その元の値を参照して正確なポインタを特定できるようになります。

## 技術的詳細

このコミットの主要な技術的ポイントは、スタックバリア追跡用のブックキーピング構造体 `stkbar` を、通常のメモリ割り当てではなく、スタック自体の割り当て時にその領域の一部として確保する点です。

1.  **`stkbar` 構造体の定義**:
    `src/runtime/runtime2.go` に `stkbar` 構造体が新しく定義されています。
    ```go
    type stkbar struct {
        savedLRPtr uintptr // location overwritten by stack barrier PC
        savedLRVal uintptr // value overwritten at savedLRPtr
    }
    ```
    この構造体は、スタックバリアによって上書きされる戻りPCのアドレス (`savedLRPtr`) と、そのアドレスに元々格納されていた値 (`savedLRVal`) を記録します。

2.  **`g` 構造体への追加**:
    各Goroutineを表す `g` 構造体 (`src/runtime/runtime2.go`) に、`stkbar` のスライスと現在の位置を追跡するためのフィールドが追加されました。
    ```go
    type g struct {
        // ...
        stkbar       []stkbar       // stack barriers, from low to high
        stkbarPos    uintptr        // index of lowest stack barrier not hit
        // ...
    }
    ```
    `stkbar` は、そのGoroutineのスタックに設定されるスタックバリアの情報を保持するスライスです。`stkbarPos` は、まだヒットしていない（処理されていない）最も低いスタックバリアのインデックスを示します。

3.  **`gcMaxStackBarriers` 関数の導入**:
    `src/runtime/mgcmark.go` に `gcMaxStackBarriers` 関数が追加されました。この関数は、与えられたスタックサイズに対して、最大でいくつのスタックバリアをインストールできるかを計算します。
    *   `firstStackBarrierOffset` (デフォルト1024バイト) を基準に、スタックサイズが大きくなるにつれて指数関数的にバリアの間隔を広げていきます。
    *   デバッグ目的で `firstStackBarrierOffset` が0に設定されている場合、すべてのフレームにスタックバリアを挿入する特殊なケースも考慮されています。この場合、スタックの半分を `stkbar` のために使用すると仮定しています。

4.  **`stackalloc` での `stkbar` 領域の確保**:
    `src/runtime/stack1.go` の `stackalloc` 関数が変更され、スタックを割り当てる際に `stkbar` のための領域も同時に確保するようになりました。
    *   `gcMaxStackBarriers` を使用して必要な `stkbar` の数を計算し、そのサイズ (`nstkbar`) を求めます。
    *   割り当てられるスタック領域の「上部」から `nstkbar` 分の領域を `stkbar` のために「盗み」ます。つまり、スタックの実際の使用可能領域は `n - nstkbar` となります。
    *   `stackalloc` は、割り当てられたスタック (`stack` 型) と、そのスタック領域内に作成された `stkbar` のスライス (`[]stkbar` 型) の両方を返すように変更されました。

5.  **`malg` および `gfput` での `stkbar` の初期化/クリア**:
    `src/runtime/proc1.go` の `malg` (Goroutineの割り当て) および `gfput` (Goroutineの解放/再利用) 関数が更新され、`g` 構造体の `stkbar` フィールドが適切に初期化またはクリアされるようになりました。これにより、Goroutineのライフサイクルを通じて `stkbar` が正しく管理されます。

6.  **`copystack` での `stkbar` のコピー**:
    `src/runtime/stack1.go` の `copystack` 関数 (スタックの成長時に古いスタックの内容を新しいスタックにコピーする処理) が変更され、古いスタックの `stkbar` の内容も新しいスタックの `stkbar` にコピーされるようになりました。これにより、スタックが成長してもスタックバリアの情報が失われないことが保証されます。

このアプローチの利点は、GC中に動的なメモリ割り当てを避けることで、GCの安定性とパフォーマンスを向上させる点にあります。`stkbar` のサイズはスタックサイズに対して対数的に増加するため、スタックの動作への影響は最小限に抑えられます。

### `src/runtime/mgcmark.go`

```go
func gcMaxStackBarriers(stackSize int) (n int) {
	if firstStackBarrierOffset == 0 {
		// Special debugging case for inserting stack barriers
		// at every frame. Steal half of the stack for the
		// []stkbar. Technically, if the stack were to consist
		// solely of return PCs we would need two thirds of
		// the stack, but stealing that much breaks things and
		// this doesn't happen in practice.
		return stackSize / 2 / int(unsafe.Sizeof(stkbar{}))
	}

	offset := firstStackBarrierOffset
	for offset < stackSize {
		n++
		offset *= 2
	}
	return n + 1
}
```
この関数は、与えられた `stackSize` に対して、いくつの `stkbar` エントリが必要かを計算します。`firstStackBarrierOffset` を開始点として、スタックサイズが大きくなるにつれてバリアの間隔を倍にすることで、必要な `stkbar` の数を対数的に抑えています。デバッグ用の特殊なケースも含まれています。

### `src/runtime/stack1.go`

```go
func stackalloc(n uint32) (stack, []stkbar) {
	// ...
	// Compute the size of stack barrier array.
	maxstkbar := gcMaxStackBarriers(int(n))
	nstkbar := unsafe.Sizeof(stkbar{}) * uintptr(maxstkbar)

	if debug.efence != 0 || stackFromSystem != 0 {
		v := sysAlloc(round(uintptr(n), _PageSize), &memstats.stacks_sys)
		if v == nil {
			throw("out of memory (stackalloc)")
		}
		top := uintptr(n) - nstkbar
		stkbarSlice := slice{add(v, top), 0, maxstkbar}
		return stack{uintptr(v), uintptr(v) + top}, *(*[]stkbar)(unsafe.Pointer(&stkbarSlice))
	}

	// ... (既存のスタック割り当てロジック) ...

	top := uintptr(n) - nstkbar
	stkbarSlice := slice{add(v, top), 0, maxstkbar}
	return stack{uintptr(v), uintptr(v) + top}, *(*[]stkbar)(unsafe.Pointer(&stkbarSlice))
}
```
`stackalloc` 関数は、スタックのサイズ `n` に加えて、`stkbar` のスライスを返すように変更されました。`nstkbar` は `stkbar` のために確保されるバイト数です。この `nstkbar` 分の領域は、割り当てられたスタックの「上部」から差し引かれ、`stkbarSlice` として初期化されます。これにより、`stkbar` のデータはスタック領域の一部として存在し、別途メモリ割り当てを行う必要がなくなります。

### `src/runtime/proc1.go`

func malg(stacksize int32) *g {
	// ...
	systemstack(func() {
		newg.stack, newg.stkbar = stackalloc(uint32(stacksize))
	})
	// ...
}

func gfput(_p_ *p, gp *g) {
	// ...
	if gp.stack.lo == 0 {
		// ...
		gp.stkbar = nil
		gp.stkbarPos = 0
	}
	// ...
}
```
`malg` 関数では、新しいGoroutine (`newg`) のスタックを割り当てる際に、`stackalloc` から返される `stkbar` スライスも `newg.stkbar` に設定しています。`gfput` 関数では、Goroutineが解放される際に `gp.stkbar` を `nil` に、`gp.stkbarPos` を `0` にリセットし、クリーンな状態を保っています。

### `src/runtime/stack1.go` (copystack)

```go
func copystack(gp *g, newsize uintptr) {
	// ...
	new, newstkbar := stackalloc(uint32(newsize))
	// ...
	memmove(unsafe.Pointer(new.hi-used), unsafe.Pointer(old.hi-used), used)

	// copy old stack barriers to new stack barrier array
	newstkbar = newstkbar[:len(gp.stkbar)]
	copy(newstkbar, gp.stkbar)

	// Swap out old stack for new one
	gp.stack = new
	// ...
	gp.stkbar = newstkbar
	// ...
}
```
`copystack` 関数では、スタックが成長して新しいスタックが割り当てられる際に、古いスタックの `stkbar` の内容が新しいスタックの `newstkbar` にコピーされます。これにより、スタックバリアの追跡情報がスタックの成長後も維持されます。

*   **スタックの成長**: 関数呼び出しが深くネストしたり、大きなローカル変数が確保されたりして、現在のスタック領域が不足すると、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、スタックポインタを更新します。
*   **スタックの縮小**: 関数がリターンしてスタックの使用量が減ると、ランタイムはスタックを縮小してメモリを解放することがあります。

GCは、これらのスタック領域もスキャンして、スタック上に存在するポインタ（他のオブジェクトへの参照）を特定し、マークする必要があります。

### スタックバリア (Stack Barrier)

スタックバリアは、GoのGCがスタックをスキャンする際の正確性を保証するためのメカニズムの一つです。特に、スタックの成長や縮小、あるいは特定の最適化によって、スタック上の戻りアドレス (Return PC) が一時的に書き換えられるような状況で重要になります。

例えば、GCがスタックをスキャンしている最中に、ある関数が別の関数を呼び出し、その際にスタックが成長したとします。このとき、GCが古いスタックと新しいスタックの両方を正しく処理し、ポインタを見落とさないようにするために、スタックバリアが役立ちます。

このコミットで導入されるブックキーピング構造体は、スタックバリアが「オーバーライトした戻りPC」の元の値を記録するために使用されます。これにより、GCがスタックをスキャンする際に、一時的に変更された戻りPCであっても、その元の値を参照して正確なポインタを特定できるようになります。

## 技術的詳細

このコミットの主要な技術的ポイントは、スタックバリア追跡用のブックキーピング構造体 `stkbar` を、通常のメモリ割り当てではなく、スタック自体の割り当て時にその領域の一部として確保する点です。

1.  **`stkbar` 構造体の定義**:
    `src/runtime/runtime2.go` に `stkbar` 構造体が新しく定義されています。
    ```go
    type stkbar struct {
        savedLRPtr uintptr // location overwritten by stack barrier PC
        savedLRVal uintptr // value overwritten at savedLRPtr
    }
    ```
    この構造体は、スタックバリアによって上書きされる戻りPCのアドレス (`savedLRPtr`) と、そのアドレスに元々格納されていた値 (`savedLRVal`) を記録します。

2.  **`g` 構造体への追加**:
    各Goroutineを表す `g` 構造体 (`src/runtime/runtime2.go`) に、`stkbar` のスライスと現在の位置を追跡するためのフィールドが追加されました。
    ```go
    type g struct {
        // ...
        stkbar       []stkbar       // stack barriers, from low to high
        stkbarPos    uintptr        // index of lowest stack barrier not hit
        // ...
    }
    ```
    `stkbar` は、そのGoroutineのスタックに設定されるスタックバリアの情報を保持するスライスです。`stkbarPos` は、まだヒットしていない（処理されていない）最も低いスタックバリアのインデックスを示します。

3.  **`gcMaxStackBarriers` 関数の導入**:
    `src/runtime/mgcmark.go` に `gcMaxStackBarriers` 関数が追加されました。この関数は、与えられたスタックサイズに対して、最大でいくつのスタックバリアをインストールできるかを計算します。
    *   `firstStackBarrierOffset` (デフォルト1024バイト) を基準に、スタックサイズが大きくなるにつれて指数関数的にバリアの間隔を広げていきます。
    *   デバッグ目的で `firstStackBarrierOffset` が0に設定されている場合、すべてのフレームにスタックバリアを挿入する特殊なケースも考慮されています。この場合、スタックの半分を `stkbar` のために使用すると仮定しています。

4.  **`stackalloc` での `stkbar` 領域の確保**:
    `src/runtime/stack1.go` の `stackalloc` 関数が変更され、スタックを割り当てる際に `stkbar` のための領域も同時に確保するようになりました。
    *   `gcMaxStackBarriers` を使用して必要な `stkbar` の数を計算し、そのサイズ (`nstkbar`) を求めます。
    *   割り当てられるスタック領域の「上部」から `nstkbar` 分の領域を `stkbar` のために「盗み」ます。つまり、スタックの実際の使用可能領域は `n - nstkbar` となります。
    *   `stackalloc` は、割り当てられたスタック (`stack` 型) と、そのスタック領域内に作成された `stkbar` のスライス (`[]stkbar` 型) の両方を返すように変更されました。

5.  **`malg` および `gfput` での `stkbar` の初期化/クリア**:
    `src/runtime/proc1.go` の `malg` (Goroutineの割り当て) および `gfput` (Goroutineの解放/再利用) 関数が更新され、`g` 構造体の `stkbar` フィールドが適切に初期化またはクリアされるようになりました。これにより、Goroutineのライフサイクルを通じて `stkbar` が正しく管理されます。

6.  **`copystack` での `stkbar` のコピー**:
    `src/runtime/stack1.go` の `copystack` 関数 (スタックの成長時に古いスタックの内容を新しいスタックにコピーする処理) が変更され、古いスタックの `stkbar` の内容も新しいスタックの `stkbar` にコピーされるようになりました。これにより、スタックバリアの追跡情報がスタックの成長後も維持されます。

このアプローチの利点は、GC中に動的なメモリ割り当てを避けることで、GCの安定性とパフォーマンスを向上させる点にあります。`stkbar` のサイズはスタックサイズに対して対数的に増加するため、スタックの動作への影響は最小限に抑えられます。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

```go
// stkbar records the state of a G's stack barrier.
type stkbar struct {
	savedLRPtr uintptr // location overwritten by stack barrier PC
	savedLRVal uintptr // value overwritten at savedLRPtr
}

type g struct {
	// ...
	stkbar       []stkbar       // stack barriers, from low to high
	stkbarPos    uintptr        // index of lowest stack barrier not hit
	// ...
}
```
`stkbar` 構造体は、スタックバリアが戻りPCを上書きする際に、その元の位置と値を保存するためのものです。`g` 構造体に追加された `stkbar` フィールドは、そのGoroutineに関連付けられた `stkbar` のスライスであり、`stkbarPos` は、次に処理すべきスタックバリアの位置を示します。

### `src/runtime/mgcmark.go`

```go
func gcMaxStackBarriers(stackSize int) (n int) {
	if firstStackBarrierOffset == 0 {
		// Special debugging case for inserting stack barriers
		// at every frame. Steal half of the stack for the
		// []stkbar. Technically, if the stack were to consist
		// solely of return PCs we would need two thirds of
		// the stack, but stealing that much breaks things and
		// this doesn't happen in practice.
		return stackSize / 2 / int(unsafe.Sizeof(stkbar{}))
	}

	offset := firstStackBarrierOffset
	for offset < stackSize {
		n++
		offset *= 2
	}
	return n + 1
}
```
この関数は、与えられた `stackSize` に対して、いくつの `stkbar` エントリが必要かを計算します。`firstStackBarrierOffset` を開始点として、スタックサイズが大きくなるにつれてバリアの間隔を倍にすることで、必要な `stkbar` の数を対数的に抑えています。デバッグ用の特殊なケースも含まれています。

### `src/runtime/stack1.go`

```go
func stackalloc(n uint32) (stack, []stkbar) {
	// ...
	// Compute the size of stack barrier array.
	maxstkbar := gcMaxStackBarriers(int(n))
	nstkbar := unsafe.Sizeof(stkbar{}) * uintptr(maxstkbar)

	if debug.efence != 0 || stackFromSystem != 0 {
		v := sysAlloc(round(uintptr(n), _PageSize), &memstats.stacks_sys)
		if v == nil {
			throw("out of memory (stackalloc)")
		}
		top := uintptr(n) - nstkbar
		stkbarSlice := slice{add(v, top), 0, maxstkbar}
		return stack{uintptr(v), uintptr(v) + top}, *(*[]stkbar)(unsafe.Pointer(&stkbarSlice))
	}

	// ... (既存のスタック割り当てロジック) ...

	top := uintptr(n) - nstkbar
	stkbarSlice := slice{add(v, top), 0, maxstkbar}
	return stack{uintptr(v), uintptr(v) + top}, *(*[]stkbar)(unsafe.Pointer(&stkbarSlice))
}
```
`stackalloc` 関数は、スタックのサイズ `n` に加えて、`stkbar` のスライスを返すように変更されました。`nstkbar` は `stkbar` のために確保されるバイト数です。この `nstkbar` 分の領域は、割り当てられたスタックの「上部」から差し引かれ、`stkbarSlice` として初期化されます。これにより、`stkbar` のデータはスタック領域の一部として存在し、別途メモリ割り当てを行う必要がなくなります。

### `src/runtime/proc1.go` (malg, gfput)

```go
func malg(stacksize int32) *g {
	// ...
	systemstack(func() {
		newg.stack, newg.stkbar = stackalloc(uint32(stacksize))
	})
	// ...
}

func gfput(_p_ *p, gp *g) {
	// ...
	if gp.stack.lo == 0 {
		// ...
		gp.stkbar = nil
		gp.stkbarPos = 0
	}
	// ...
}
```
`malg` 関数では、新しいGoroutine (`newg`) のスタックを割り当てる際に、`stackalloc` から返される `stkbar` スライスも `newg.stkbar` に設定しています。`gfput` 関数では、Goroutineが解放される際に `gp.stkbar` を `nil` に、`gp.stkbarPos` を `0` にリセットし、クリーンな状態を保っています。

### `src/runtime/stack1.go` (copystack)

```go
func copystack(gp *g, newsize uintptr) {
	// ...
	new, newstkbar := stackalloc(uint32(newsize))
	// ...
	memmove(unsafe.Pointer(new.hi-used), unsafe.Pointer(old.hi-used), used)

	// copy old stack barriers to new stack barrier array
	newstkbar = newstkbar[:len(gp.stkbar)]
	copy(newstkbar, gp.stkbar)

	// Swap out old stack for new one
	gp.stack = new
	// ...
	gp.stkbar = newstkbar
	// ...
}
```
`copystack` 関数では、スタックが成長して新しいスタックが割り当てられる際に、古いスタックの `stkbar` の内容が新しいスタックの `newstkbar` にコピーされます。これにより、スタックバリアの追跡情報がスタックの成長後も維持されます。

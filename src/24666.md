## 元コミット内容

このコミットは、Go言語の型チェッカー (`go/types` パッケージ) における `complex` 組み込み関数の挙動を修正するものです。具体的には、`complex(a, b)` の引数 `a` と `b` が型なし (untyped) の場合に発生していた問題を解決します。

## 変更の背景

Go言語では、数値リテラルや一部の定数式は「型なし定数 (untyped constant)」として扱われます。これらは、使用される文脈によって適切な型に推論されます。`complex` 組み込み関数は、実部と虚部を表す2つの浮動小数点数型の引数を取り、複素数型の値を生成します。

このコミット以前の `go/types` パッケージの実装では、`complex(a, b)` の引数 `a` と `b` が両方とも型なしの場合、型推論のロジックに不備がありました。特に、両方の引数が型なし定数である場合や、片方が型なしで非定数である場合において、期待される型への変換が正しく行われず、コンパイルエラーや不正確な型推論を引き起こす可能性がありました。

この問題は Go issue #11669 で報告されており、このコミットはその問題を修正するために導入されました。型なし引数の柔軟な扱いはGo言語の重要な特徴の一つであるため、`complex` 関数がこの原則に沿って正しく機能することは、言語の一貫性と使いやすさのために不可欠でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびGoコンパイラの型システムに関する知識が必要です。

1.  **Goの型システムと型なし定数 (Untyped Constants)**:
    *   Go言語の数値リテラル（例: `10`, `3.14`, `1i`）は、デフォルトでは特定の型を持ちません。これらは「型なし定数」と呼ばれ、その値が表現できる範囲であれば、任意の互換性のある型に変換できます。
    *   例えば、`var x float64 = 10` の場合、`10` は型なし整数定数ですが、`float64` 型に変換されて `x` に代入されます。
    *   型なし定数は、演算中に精度を失うことなく、より大きな精度で計算されることがあります。最終的に変数に代入されるか、型付きのコンテキストで使用される際に型が決定されます。
    *   `UntypedInt`, `UntypedRune`, `UntypedFloat`, `UntypedComplex` など、型なし定数にはそれぞれカテゴリがあります。

2.  **`complex` 組み込み関数**:
    *   `complex(real, imag)` は、Go言語の組み込み関数で、実部 `real` と虚部 `imag` から複素数を作成します。
    *   引数 `real` と `imag` は同じ浮動小数点数型（`float32` または `float64`）であるか、型なしの数値である必要があります。
    *   結果の型は、引数の型に基づいて `complex64` または `complex128` になります。引数が型なしの場合、結果は `untyped complex` になり、文脈によって `complex128` にデフォルトで型付けされます。

3.  **`go/types` パッケージ**:
    *   Goコンパイラの一部であり、Goプログラムの型チェックを担当します。
    *   AST (Abstract Syntax Tree) を走査し、各式の型を決定し、型の一貫性を検証します。
    *   組み込み関数 (`len`, `cap`, `complex` など) の呼び出しもこのパッケージで処理されます。

4.  **`operand` 構造体**:
    *   `go/types` パッケージ内で、式や値の型チェック中の状態を表すために使用される内部構造体です。
    *   `typ` フィールドは現在の型を、`mode` フィールドは値の種類（定数、変数、型なしなど）を示します。
    *   `val` フィールドは、定数の場合はその値を保持します。

5.  **`constant` パッケージ**:
    *   Go言語の定数値を表現および操作するためのパッケージです。
    *   型なし定数の高精度な算術演算をサポートします。

## 技術的詳細

このコミットの主要な変更点は、`src/go/types/builtins.go` 内の `builtin` メソッドにおける `_Complex` ケースのロジックの再構築です。以前の実装では、`check.complexArg` というヘルパー関数を使用して引数の型チェックを行っていましたが、この関数は削除され、そのロジックが `_Complex` ケース内に直接統合され、より堅牢な型変換ロジックが導入されました。

新しいロジックは、`complex(x, y)` の引数 `x` と `y` の型なし状態を詳細に分析し、適切な型変換を適用します。

1.  **型なし引数の検出**:
    `d` というビットフラグ変数 (`d := 0`) を導入し、`x` と `y` のどちらが型なしであるかを記録します。
    *   `d = 0`: `x` と `y` の両方が型付き。
    *   `d = 1`: `x` のみが型なし。
    *   `d = 2`: `y` のみが型なし。
    *   `d = 3`: `x` と `y` の両方が型なし。

2.  **型変換ロジック (`switch d`)**:
    *   **`d = 0` (両方型付き)**: 何もせず、既存の型を使用します。
    *   **`d = 1` (`x` のみ型なし)**: `x` を `y` の型に変換します (`check.convertUntyped(x, y.typ)`)。
    *   **`d = 2` (`y` のみ型なし)**: `y` を `x` の型に変換します (`check.convertUntyped(&y, x.typ)`)。
    *   **`d = 3` (両方型なし)**: ここが最も重要な変更点です。
        *   **両方が定数 (`x.mode == constant_ && y.mode == constant_`) の場合**:
            `toFloat` というローカル関数を定義し、引数が数値型で虚部を持たない場合、その型を `UntypedFloat` に設定します。これにより、型なし浮動小数点数としての高精度な計算が可能になります。
        *   **どちらか一方が非定数 (`else`) の場合**:
            両方の引数を `float64` に変換します (`check.convertUntyped(x, Typ[Float64])`, `check.convertUntyped(&y, Typ[Float64])`)。これは、型なしの非定数引数（例えば、型なしのシフト演算の結果など）が存在する場合、両方の引数が同じ型を持つ必要があり、`float64` がデフォルトの浮動小数点型として選択されるためです。

3.  **型の一致と浮動小数点型チェック**:
    型変換後、`x.typ` と `y.typ` が同一であること (`Identical(x.typ, y.typ)`)、および両方の型が浮動小数点型であること (`isFloat(x.typ)`) を厳密にチェックします。これにより、`complex` 関数の引数として不適切な型が渡された場合に、より正確なエラーメッセージが生成されるようになります。

4.  **結果の型決定**:
    引数の型 (`x.typ`) に基づいて、結果の複素数型 (`resTyp`) を決定します。
    *   `Float32` -> `Complex64`
    *   `Float64` -> `Complex128`
    *   `UntypedFloat` -> `UntypedComplex`
    以前は `realT` という変数を使っていましたが、より直接的に `res` (BasicKind) を使って結果の型を決定しています。

5.  **`check.complexArg` 関数の削除**:
    以前の `complexArg` ヘルパー関数は、引数が `float32`, `float64`, `UntypedInt`, `UntypedRune` のいずれかであるかをチェックしていました。このロジックは新しい `_Complex` ケースの型変換ロジックに吸収され、より詳細な型なし引数の処理が可能になったため、不要となりました。

この変更により、`complex` 関数は型なし引数をより正確かつGoの型推論ルールに沿って処理できるようになり、特に型なし定数と型なし非定数が混在する複雑なシナリオでの挙動が改善されました。

## コアとなるコードの解説

### `src/go/types/builtins.go` の `case _Complex:` ブロック

```go
	case _Complex:
		// complex(x, y floatT) complexT
		var y operand
		arg(&y, 1)
		if y.mode == invalid {
			return
		}

		// Convert or check untyped arguments.
		d := 0
		if isUntyped(x.typ) {
			d |= 1
		}
		if isUntyped(y.typ) {
			d |= 2
		}
		switch d {
		case 0:
			// x and y are typed => nothing to do
		case 1:
			// only x is untyped => convert to type of y
			check.convertUntyped(x, y.typ)
		case 2:
			// only y is untyped => convert to type of x
			check.convertUntyped(&y, x.typ)
		case 3:
			// x and y are untyped =>
			// 1) if both are constants, convert them to untyped
			//    floating-point numbers if possible,
			// 2) if one of them is not constant (possible because
			//    it contains a shift that is yet untyped), convert
			//    both of them to float64 since they must have the
			//    same type to succeed
			if x.mode == constant_ && y.mode == constant_ {
				toFloat := func(x *operand) {
					if isNumeric(x.typ) && constant.Sign(constant.Imag(x.val)) == 0 {
						x.typ = Typ[UntypedFloat]
					}
				}
				toFloat(x)
				toFloat(&y)
			} else {
				check.convertUntyped(x, Typ[Float64])
				check.convertUntyped(&y, Typ[Float64])
			}
		}
		if x.mode == invalid || y.mode == invalid {
			return
		}

		// both argument types must be identical
		if !Identical(x.typ, y.typ) {
			check.invalidArg(x.pos(), "mismatched types %s and %s", x.typ, y.typ)
			return
		}

		// the argument types must be of floating-point type
		if !isFloat(x.typ) {
			check.invalidArg(x.pos(), "arguments have type %s, expected floating-point", x.typ)
			return
		}

		// if both arguments are constant, the result is a constant
		if x.mode == constant_ && y.mode == constant_ {
			x.val = constant.BinaryOp(x.val, token.ADD, constant.MakeImag(y.val))
		} else {
			x.mode = value
		}

		// determine result type
		var res BasicKind
		switch x.typ.Underlying().(*Basic).kind {
		case Float32:
			res = Complex64
		case Float64:
			res = Complex128
		case UntypedFloat:
			res = UntypedComplex
		default:
			unreachable()
		}
		resTyp := Typ[res]

		if check.Types != nil && x.mode != constant_ {
			check.recordBuiltinType(call.Fun, makeSig(resTyp, x.typ, x.typ))
		}

		x.typ = resTyp
```

このコードブロックは、`complex` 組み込み関数の型チェックロジックの核心です。

1.  **引数の取得と初期チェック**: `arg(&y, 1)` で2番目の引数 `y` を取得し、無効な場合は早期リターンします。
2.  **型なし引数の処理**:
    *   `d` 変数を使って、`x` と `y` のどちらが型なしであるかを効率的に判定します。
    *   `switch d` ステートメントにより、以下のケースを処理します。
        *   `case 0` (両方型付き): 何もせず、既存の型を維持します。
        *   `case 1` (`x` のみ型なし): `x` を `y` の型に変換します。これにより、両方の引数が同じ型を持つようになります。
        *   `case 2` (`y` のみ型なし): `y` を `x` の型に変換します。同様に、両方の引数を同じ型にします。
        *   `case 3` (両方型なし): ここが最も複雑で重要な部分です。
            *   両方の引数が定数 (`constant_`) の場合、`toFloat` ヘルパー関数を使って、数値型で虚部を持たない引数を `UntypedFloat` に変換します。これにより、`complex(1, 2)` のような式が `complex(UntypedFloat, UntypedFloat)` として扱われ、最終的に `UntypedComplex` に推論される道筋が作られます。
            *   どちらか一方が非定数 (`else`) の場合、両方の引数を `Typ[Float64]` に変換します。これは、型なしの非定数式（例: `complex(1 << s, 2)` で `s` が型なしの場合）が `float64` にデフォルトで型付けされるというGoのルールに沿ったものです。
3.  **型の一致と浮動小数点型チェック**:
    型変換後、`Identical(x.typ, y.typ)` で引数の型が完全に一致するかを確認し、`isFloat(x.typ)` でそれらが浮動小数点型であることを確認します。これにより、`complex(1, "hello")` のような不正な呼び出しが適切にエラーとして報告されます。
4.  **結果の定数性**:
    両方の引数が定数であれば、結果も定数として `x.val` に実部と虚部を結合した値を設定します。そうでなければ、結果は非定数 (`value`) となります。
5.  **結果の型決定**:
    引数の型 (`x.typ`) に基づいて、結果の複素数型 (`resTyp`) を決定します。`Float32` から `Complex64`、`Float64` から `Complex128`、`UntypedFloat` から `UntypedComplex` へとマッピングされます。
6.  **型情報の記録と最終的な型設定**:
    `check.recordBuiltinType` で組み込み関数の型シグネチャを記録し、最終的に `x.typ` を決定された `resTyp` に設定します。

この再構築されたロジックにより、`complex` 関数は型なし引数をより正確に処理し、Goの型推論規則に厳密に従うようになりました。

    *   `d = 0`: `x` と `y` の両方が型付き。
    *   `d = 1`: `x` のみが型なし。
    *   `d = 2`: `y` のみが型なし。
    *   `d = 3`: `x` と `y` の両方が型なし。

2.  **型変換ロジック (`switch d`)**:
    *   **`d = 0` (両方型付き)**: 何もせず、既存の型を使用します。
    *   **`d = 1` (`x` のみ型なし)**: `x` を `y` の型に変換します (`check.convertUntyped(x, y.typ)`)。
    *   **`d = 2` (`y` のみ型なし)**: `y` を `x` の型に変換します (`check.convertUntyped(&y, x.typ)`)。
    *   **`d = 3` (両方型なし)**: ここが最も重要な変更点です。
        *   **両方が定数 (`x.mode == constant_ && y.mode == constant_`) の場合**:
            `toFloat` というローカル関数を定義し、引数が数値型で虚部を持たない場合、その型を `UntypedFloat` に設定します。これにより、型なし浮動小数点数としての高精度な計算が可能になります。
        *   **どちらか一方が非定数 (`else`) の場合**:
            両方の引数を `float64` に変換します (`check.convertUntyped(x, Typ[Float64])`, `check.convertUntyped(&y, Typ[Float64])`)。これは、型なしの非定数引数（例えば、型なしのシフト演算の結果など）が存在する場合、両方の引数が同じ型を持つ必要があり、`float64` がデフォルトの浮動小数点型として選択されるためです。

3.  **型の一致と浮動小数点型チェック**:
    型変換後、`x.typ` と `y.typ` が同一であること (`Identical(x.typ, y.typ)`)、および両方の型が浮動小数点型であること (`isFloat(x.typ)`) を厳密にチェックします。これにより、`complex` 関数の引数として不適切な型が渡された場合に、より正確なエラーメッセージが生成されるようになります。

4.  **結果の定数性**:
    両方の引数が定数であれば、結果も定数として `x.val` に実部と虚部を結合した値を設定します。そうでなければ、結果は非定数 (`value`) となります。
5.  **結果の型決定**:
    引数の型 (`x.typ`) に基づいて、結果の複素数型 (`resTyp`) を決定します。
    *   `Float32` -> `Complex64`
    *   `Float64` -> `Complex128`
    *   `UntypedFloat` -> `UntypedComplex`
    以前は `realT` という変数を使っていましたが、より直接的に `res` (BasicKind) を使って結果の型を決定しています。

6.  **`check.complexArg` 関数の削除**:
    以前の `complexArg` ヘルパー関数は、引数が `float32`, `float64`, `UntypedInt`, `UntypedRune` のいずれかであるかをチェックしていました。このロジックは新しい `_Complex` ケースの型変換ロジックに吸収され、より詳細な型なし引数の処理が可能になったため、不要となりました。

この変更により、`complex` 関数は型なし引数をより正確に処理し、Goの型推論ルールに沿って処理できるようになり、特に型なし定数と型なし非定数が混在する複雑なシナリオでの挙動が改善されました。

## コアとなるコードの解説

### `src/go/types/builtins.go` の `case _Complex:` ブロック

```go
	case _Complex:
		// complex(x, y floatT) complexT
		var y operand
		arg(&y, 1)
		if y.mode == invalid {
			return
		}

		// Convert or check untyped arguments.
		d := 0
		if isUntyped(x.typ) {
			d |= 1
		}
		if isUntyped(y.typ) {
			d |= 2
		}
		switch d {
		case 0:
			// x and y are typed => nothing to do
		case 1:
			// only x is untyped => convert to type of y
			check.convertUntyped(x, y.typ)
		case 2:
			// only y is untyped => convert to type of x
			check.convertUntyped(&y, x.typ)
		case 3:
			// x and y are untyped =>
			// 1) if both are constants, convert them to untyped
			//    floating-point numbers if possible,
			// 2) if one of them is not constant (possible because
			//    it contains a shift that is yet untyped), convert
			//    both of them to float64 since they must have the
			//    same type to succeed
			if x.mode == constant_ && y.mode == constant_ {
				toFloat := func(x *operand) {
					if isNumeric(x.typ) && constant.Sign(constant.Imag(x.val)) == 0 {
						x.typ = Typ[UntypedFloat]
					}
				}
				toFloat(x)
				toFloat(&y)
			} else {
				check.convertUntyped(x, Typ[Float64])
				check.convertUntyped(&y, Typ[Float64])
			}
		}
		if x.mode == invalid || y.mode == invalid {
			return
		}

		// both argument types must be identical
		if !Identical(x.typ, y.typ) {
			check.invalidArg(x.pos(), "mismatched types %s and %s", x.typ, y.typ)
			return
		}

		// the argument types must be of floating-point type
		if !isFloat(x.typ) {
			check.invalidArg(x.pos(), "arguments have type %s, expected floating-point", x.typ)
			return
		}

		// if both arguments are constant, the result is a constant
		if x.mode == constant_ && y.mode == constant_ {
			x.val = constant.BinaryOp(x.val, token.ADD, constant.MakeImag(y.val))
		} else {
			x.mode = value
		}

		// determine result type
		var res BasicKind
		switch x.typ.Underlying().(*Basic).kind {
		case Float32:
			res = Complex64
		case Float64:
			res = Complex128
		case UntypedFloat:
			res = UntypedComplex
		default:
			unreachable()
		}
		resTyp := Typ[res]

		if check.Types != nil && x.mode != constant_ {
			check.recordBuiltinType(call.Fun, makeSig(resTyp, x.typ, x.typ))
		}

		x.typ = resTyp
```

このコードブロックは、`complex` 組み込み関数の型チェックロジックの核心です。

1.  **引数の取得と初期チェック**: `arg(&y, 1)` で2番目の引数 `y` を取得し、無効な場合は早期リターンします。
2.  **型なし引数の処理**:
    *   `d` 変数を使って、`x` と `y` のどちらが型なしであるかを効率的に判定します。
    *   `switch d` ステートメントにより、以下のケースを処理します。
        *   `case 0` (両方型付き): 何もせず、既存の型を維持します。
        *   `case 1` (`x` のみ型なし): `x` を `y` の型に変換します。これにより、両方の引数が同じ型を持つようになります。
        *   `case 2` (`y` のみ型なし): `y` を `x` の型に変換します。同様に、両方の引数を同じ型にします。
        *   `case 3` (両方型なし): ここが最も複雑で重要な部分です。
            *   両方の引数が定数 (`constant_`) の場合、`toFloat` ヘルパー関数を使って、数値型で虚部を持たない引数を `UntypedFloat` に変換します。これにより、`complex(1, 2)` のような式が `complex(UntypedFloat, UntypedFloat)` として扱われ、最終的に `UntypedComplex` に推論される道筋が作られます。
            *   どちらか一方が非定数 (`else`) の場合、両方の引数を `Typ[Float64]` に変換します。これは、型なしの非定数式（例: `complex(1 << s, 2)` で `s` が型なしの場合）が `float64` にデフォルトで型付けされるというGoのルールに沿ったものです。
3.  **型の一致と浮動小数点型チェック**:
    型変換後、`Identical(x.typ, y.typ)` で引数の型が完全に一致するかを確認し、`isFloat(x.typ)` でそれらが浮動小数点型であることを確認します。これにより、`complex(1, "hello")` のような不正な呼び出しが適切にエラーとして報告されます。
4.  **結果の定数性**:
    両方の引数が定数であれば、結果も定数として `x.val` に実部と虚部を結合した値を設定します。そうでなければ、結果は非定数 (`value`) となります。
5.  **結果の型決定**:
    引数の型 (`x.typ`) に基づいて、結果の複素数型 (`resTyp`) を決定します。`Float32` から `Complex64`、`Float64` から `Complex128`、`UntypedFloat` から `UntypedComplex` へとマッピングされます。
6.  **型情報の記録と最終的な型設定**:
    `check.recordBuiltinType` で組み込み関数の型シグネチャを記録し、最終的に `x.typ` を決定された `resTyp` に設定します。

この再構築されたロジックにより、`complex` 関数は型なし引数をより正確に処理し、Goの型推論規則に厳密に従うようになりました。

## 変更の背景

この変更の背景には、GoプログラムをGDB（GNU Debugger）でデバッグする際に、特にリンクレジスタ（Link Register, LR）を使用するCPUアーキテクチャ（例: PowerPC (ppc64), IBM System/390 (s390x), ARMなど）で、GDBが正確なバックトレース（スタックトレース）を生成できないという問題がありました。

GDBがバックトレースを生成するためには、実行中のプログラムのスタックフレーム構造に関する情報が必要です。この情報は通常、コンパイラやリンカーによって生成されるDWARF (Debugging With Attributed Record Formats) デバッグ情報に含まれる「Call Frame Information (CFI)」によって提供されます。

問題の核心は、Goのリンカー (`cmd/link`) が生成するDWARF CFIが、リンクレジスタを使用するアーキテクチャにおける関数の呼び出し規約（特にリターンアドレスの保存方法）を正確に記述していなかったことにあります。その結果、GDBはスタック上のリターンアドレスの位置を誤解し、呼び出し元の関数を特定できず、不正確な、あるいは途切れたバックトレースしか表示できませんでした。

この問題はGoのIssue #14628として報告されており、このコミットはその問題を解決するために導入されました。

## 前提知識の解説

### 1. スタックとスタックフレーム

プログラムが関数を呼び出す際、その関数のローカル変数、引数、そして呼び出し元に戻るためのリターンアドレスなどがスタックと呼ばれるメモリ領域に積まれます。この一連の情報を「スタックフレーム」と呼びます。関数が呼び出されるたびに新しいスタックフレームが作成され、関数から戻る際にそのスタックフレームは破棄されます。

### 2. バックトレース（スタックトレース）

バックトレースは、プログラムの現在の実行点に至るまでの関数呼び出しの履歴（スタックフレームの連なり）を表示するものです。デバッグ時に、どの関数がどの関数を呼び出したか、どの行でエラーが発生したかなどを特定するために不可欠な情報です。

### 3. リンクレジスタ (Link Register, LR)

多くのRISCアーキテクチャ（ARM, PowerPC, MIPSなど）では、関数呼び出し時にリターンアドレスを一時的に保存するための専用レジスタとして「リンクレジスタ」が使用されます。x86のようなCISCアーキテクチャでは、リターンアドレスは通常直接スタックにプッシュされますが、RISCではLRに保存されるのが一般的です。

*   **LRの動作:** 関数Aが関数Bを呼び出す際、関数Aの次の命令のアドレス（リターンアドレス）がLRに格納されます。関数Bがさらに別の関数Cを呼び出す場合、関数Bは自身のLRの値をスタックに保存してから関数Cを呼び出します。これにより、関数Bから戻る際に正しいリターンアドレスが利用できるようになります。
*   **問題点:** LRの値をスタックに保存するタイミングや場所はアーキテクチャやコンパイラの最適化によって異なるため、デバッガがこの情報を正確に把握できないと、リターンアドレスを見つけられず、スタックアンワインドに失敗します。

### 4. DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイルされたプログラムのソースコードレベルでのデバッグを可能にするための標準的なデバッグ情報フォーマットです。実行可能ファイルやライブラリに埋め込まれ、デバッガが変数名、型情報、ソースコードの行番号、関数名、スタックフレームの構造などを理解するために使用します。

### 5. DWARF Call Frame Information (CFI)

DWARF CFIは、DWARF情報の一部であり、スタックフレームの構造と、デバッガがスタックをアンワインドするために必要なレジスタの保存・復元方法を記述します。CFIは、以下の主要な要素で構成されます。

*   **Canonical Frame Address (CFA):** スタックフレームの基準となるアドレス。通常、スタックポインタ (SP) にオフセットを加えた値として定義されます。
*   **CFI命令:** デバッガがスタックフレームをアンワインドするために実行すべき一連の命令。これには、特定のレジスタがどこに保存されているか（スタック上のオフセット、別のレジスタに保存されているなど）を示す情報が含まれます。

このコミットで関連するCFI命令は以下の通りです。

*   `DW_CFA_def_cfa`: CFAを定義します。通常、あるレジスタ（例: スタックポインタ）とそのレジスタからのオフセットで指定されます。
*   `DW_CFA_offset_extended`: 指定されたレジスタの以前の値が、CFAからの相対オフセットでスタックに保存されていることを示します。
*   `DW_CFA_same_value`: 指定されたレジスタの値が、呼び出し元と呼び出し先で同じであることを示します（つまり、そのレジスタは保存されていないか、変更されていない）。
*   `DW_CFA_val_offset`: 指定されたレジスタの以前の値が、CFAからの相対オフセットで計算されるアドレスに保存されていることを示します。

## 技術的詳細

このコミットの技術的詳細は、Goリンカー (`src/cmd/link/internal/ld/dwarf.go`) が生成するDWARF CFIの正確性を、リンクレジスタを使用するアーキテクチャ向けに改善することにあります。具体的には、以下の点が修正されています。

1.  **CIE (Common Information Entry) のサイズ調整:**
    *   CIEは、FDE (Frame Description Entry) が参照する共通情報を定義します。CIEのサイズ (`cieReserve`) が、リンクレジスタを使用するアーキテクチャの場合に適切に設定されるようになりました。以前は固定値 (`CIERESERVE = 16`) でしたが、リンクレジスタを使用する場合は `32` に拡張されています。これは、リンクレジスタの情報を記述するために必要なCFI命令が増えるためです。

2.  **CFA (Canonical Frame Address) の定義の修正:**
    *   `DW_CFA_def_cfa` 命令は、CFAがスタックポインタ (`Thearch.Dwarfregsp`) とオフセットによって定義されることを示します。
    *   リンクレジスタを使用しないアーキテクチャでは、CFAはスタックポインタに `SysArch.PtrSize` (ポインタサイズ) を加えた値として定義されていました。これは、関数呼び出し命令がリターンアドレスをスタックにプッシュすることで、スタックポインタが1ワード分減少するため、CFAをその分補正する必要があるためです。
    *   しかし、リンクレジスタを使用するアーキテクチャでは、リターンアドレスは最初はLRに保存され、スタックには直接プッシュされません。そのため、CFAのオフセットは `0` となります。このコミットでは、`haslinkregister()` が真の場合にオフセットを `0` に設定するように修正されています。

3.  **リンクレジスタ (リターンアドレス) の保存場所の記述修正:**
    *   最も重要な変更点の一つは、リターンアドレス（リンクレジスタの値）がスタック上のどこに保存されるかをGDBに伝える方法の修正です。
    *   リンクレジスタを使用するアーキテクチャでは、関数プロローグ中にLRの値がスタックに保存されます。このコミットでは、`DW_CFA_same_value` と `DW_CFA_val_offset` 命令を組み合わせて、この動作を正確に記述しています。
        *   `DW_CFA_same_value` (`Thearch.Dwarfreglr`): プロローグ中、リンクレジスタの値は変更されないことを示します。
        *   `DW_CFA_val_offset` (`Thearch.Dwarfregsp`, `0`): 以前のスタックポインタの値がCFA+0に保存されていることを示します。これは、スタックポインタ自体がCFAの定義に使われているため、その値がCFAと同じ場所にあることを意味します。
    *   リンクレジスタを使用しないアーキテクチャでは、リターンアドレスはスタックに直接プッシュされるため、`DW_CFA_offset_extended` を使用して、リターンアドレスが `CFA - PtrSize` の位置に保存されていることを示します。

4.  **動的なCFAデルタの計算修正:**
    *   `appendPCDeltaCFA` 関数内で、`pcsp.value` (スタックフレームサイズ) に基づいてリターンアドレスの保存場所を記述するロジックが追加されています。
    *   `haslinkregister()` が真の場合、`pcsp.value > 0` であれば、リターンアドレスが `CFA - frame_size` の位置に保存されることを `DW_CFA_offset_extended_sf` で記述します。
    *   `pcsp.value == 0` の場合（スタックフレームが解放された場合）、リターンアドレスがリンクレジスタに復元されることを `DW_CFA_same_value` で記述します。

これらの変更により、GDBはDWARF CFIを正確に解釈し、リンクレジスタを使用するアーキテクチャでもGoプログラムのスタックを正しくアンワインドできるようになります。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/dwarf.go` の変更解説

このファイルでは、DWARFのCall Frame Information (CFI) を生成するロジックが修正されています。

1.  **`CIERESERVE` の動的な設定:**
    *   以前は `CIERESERVE` が定数 `16` でしたが、`cieReserve` という変数になり、`haslinkregister()` 関数（現在のアーキテクチャがリンクレジスタを使用するかどうかを判定）の結果に基づいて `16` または `32` に設定されるようになりました。これにより、リンクレジスタの情報を格納するためのCIEのサイズが適切に確保されます。

2.  **`DATAALIGNMENTFACTOR` の定数化と利用:**
    *   `DATAALIGNMENTFACTOR` が `dataAlignmentFactor` という小文字始まりの定数に変更され、CFIオフセット計算の際に使用されています。これは、DWARFのCFI命令がオフセットを特定の係数で割った値で表現するためです。

3.  **`DW_CFA_def_cfa` 命令のオフセット修正:**
    *   `DW_CFA_def_cfa` はCFA (Canonical Frame Address) を定義します。リンクレジスタを使用するアーキテクチャ (`haslinkregister()` が真) の場合、CFAのオフセットが `0` に設定されます。これは、関数呼び出し時にリターンアドレスがスタックに直接プッシュされないため、スタックポインタからのオフセットが不要になるためです。
    *   リンクレジスタを使用しないアーキテクチャでは、以前と同様に `SysArch.PtrSize` (ポインタサイズ) がオフセットとして使用されます。これは、リターンアドレスがスタックにプッシュされることでスタックポインタが1ワード分移動するため、その補正を行うためです。

4.  **リンクレジスタの保存方法の記述修正:**
    *   リンクレジスタを使用するアーキテクチャの場合、以下のCFI命令が追加されています。
        *   `DW_CFA_same_value` (`Thearch.Dwarfreglr`): プロローグ中、リンクレジスタの値は変更されないことをGDBに伝えます。
        *   `DW_CFA_val_offset` (`Thearch.Dwarfregsp`, `0`): 以前のスタックポインタの値がCFA+0に保存されていることを示します。これは、スタックポインタ自体がCFAの基準として使われているため、その値がCFAと同じ場所にあることを意味します。
    *   これらの命令により、GDBはリンクレジスタの値がスタック上のどこに保存されているかを正確に追跡できるようになります。

5.  **動的なCFAデルタの生成ロジックの追加:**
    *   `writeframes` 関数内の `if haslinkregister()` ブロックに新しいロジックが追加されています。
    *   `pcsp.value > 0` の場合（スタックフレームが割り当てられた後）、リターンアドレスが `CFA - frame_size` の位置に保存されることを `DW_CFA_offset_extended_sf` を用いて記述します。
    *   `pcsp.value == 0` の場合（スタックフレームが解放された後）、リターンアドレスがリンクレジスタに復元されることを `DW_CFA_same_value` を用いて記述します。
    *   これにより、関数のプロローグとエピローグにおけるリンクレジスタのライフサイクルがDWARF CFIでより正確に表現されます。

### `src/runtime/runtime-gdb_test.go` の変更解説

このファイルでは、GDBバックトレースの修正を検証するための新しいテスト `TestGdbBacktrace` が追加されています。

1.  **`checkGdbEnvironment` 関数の追加:**
    *   GDBテストを実行するための共通の環境チェックをまとめた関数です。Goビルドが可能か、OSがDarwinでないか（GDBがDarwinで動作しないため）、`GOROOT_FINAL` が設定されていないか（保留中の場合にGDBテストが失敗する可能性があるため）などを確認します。

2.  **`checkGdbVersion` 関数の追加:**
    *   GDBのバージョンが古すぎないかを確認する関数です。特定の古いGDBバージョンで問題が報告されているため、バージョンチェックを行うことでテストの信頼性を高めます。

3.  **`TestGdbPython` のリファクタリング:**
    *   既存の `TestGdbPython` 関数から環境チェックとバージョンチェックのロジックが `checkGdbEnvironment` と `checkGdbVersion` に分離され、コードの重複が排除されました。

4.  **`TestGdbBacktrace` 関数の追加:**
    *   このテストは、GDBがDWARFデバッグ情報のみを使用してスタックを正しくアンワインドできることを検証します。
    *   `backtraceSource` というGoのソースコード文字列を定義しています。これは、`aaa` -> `bbb` -> `ccc` -> `ddd` -> `eee` という一連の関数呼び出しチェーンを持つシンプルなプログラムです。`//go:noinline` ディレクティブにより、これらの関数がインライン化されないようにし、明確なスタックフレームが生成されるようにしています。
    *   テストは、このソースコードをビルドし、生成された実行可能ファイルに対してGDBを実行します。
    *   GDBコマンドとして、`main.eee` にブレークポイントを設定し、プログラムを実行し、ブレークポイントで停止した後に `backtrace` コマンドを実行します。
    *   GDBの出力から、期待される関数呼び出しチェーン (`eee`, `ddd`, `ccc`, `bbb`, `aaa`, `main`) が正しい順序で含まれているかを正規表現で検証します。これにより、GDBがスタックを正確にアンワインドできたことを確認します。

これらの変更により、リンクレジスタを使用するアーキテクチャでのGDBバックトレースの信頼性が向上し、その機能が自動テストによって継続的に検証されるようになりました。

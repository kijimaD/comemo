## 変更の背景

Goコンパイラは、より最適化されたコードを生成するために、SSA (Static Single Assignment) 形式の中間表現への移行を進めていました。しかし、SSAバックエンドはまだ開発途上であり、全てのGoコードに対して安定して動作するわけではありませんでした。このコミットの主な目的は、SSAバックエンドのテストとデバッグのプロセスを効率化することにありました。

具体的には、以下の課題がありました。
1.  **SSAの段階的な導入**: SSAバックエンドはまだ実験的な段階であり、全てのコードに適用すると予期せぬバグやパフォーマンスの問題が発生する可能性がありました。そのため、特定のコードパスや機能に限定してSSAを有効にし、その影響を評価する必要がありました。
2.  **デバッグの困難さ**: SSAバックエンドで問題が発生した場合、どの関数やパッケージが原因であるかを特定するのが困難でした。コンパイラ全体をSSAモードでビルドし直すのは時間がかかり、イテレーションサイクルが長くなっていました。
3.  **バルクテストの必要性**: SSAバックエンドの安定性を確保するためには、Goの標準ライブラリ全体や、より広範なコードベースに対してSSAを適用し、大量のテストを実行する必要がありました。

これらの課題を解決するため、このコミットでは、コンパイラを再ビルドすることなく、実行時に環境変数を通じてSSAの有効化範囲を制御できるメカニズムを導入しました。これにより、開発者は特定の関数やパッケージに焦点を当ててSSAの動作を検証し、バグを効率的に特定・修正できるようになりました。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化され、より強力な最適化を適用できるようになります。

*   **利点**:
    *   **データフロー解析の簡素化**: 各変数の定義と使用が明確になるため、変数の値がどこから来てどこへ行くのかを追跡しやすくなります。
    *   **最適化の強化**: 共通部分式除去 (CSE)、定数伝播、デッドコード除去など、多くの最適化がSSA形式上でより効果的に行えます。
    *   **レジスタ割り当ての改善**: 変数のライフタイムが明確になるため、レジスタ割り当ての効率が向上します。

Goコンパイラは、パフォーマンス向上のため、従来のAST (Abstract Syntax Tree) ベースのIRからSSAベースのIRへの移行を進めていました。

### Goコンパイラ (`cmd/compile`)

`cmd/compile` はGo言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っています。コンパイルプロセスは、字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成などの段階を経て行われます。SSAバックエンドは、この中間表現生成から最適化、コード生成の段階に深く関わります。

### 環境変数 `GOSSAFUNC` と `GOSSAPKG`

これらの環境変数は、GoコンパイラのSSAバックエンドの動作を制御するために一時的に導入されたものです。
*   `GOSSAFUNC`: 特定の関数名が指定された場合、その関数に対してのみSSAバックエンドを有効にします。
*   `GOSSAPKG`: 特定のパッケージ名が指定された場合、そのパッケージ内の全ての関数に対してSSAバックエンドを有効にします。

これらの変数は、開発者がSSAバックエンドの動作を細かく制御し、問題のある箇所を特定するためのデバッグツールとして機能します。

### スタックマップとGCマップ

Goランタイムでは、ガベージコレクタ (GC) が正確に動作するために、スタック上のポインタの位置を知る必要があります。これを実現するのが「スタックマップ」や「GCマップ」と呼ばれるメタデータです。
*   **スタックマップ**: 関数呼び出し時にスタック上に存在するポインタの位置を示す情報。GCはこれを利用して、スタック上のポインタをスキャンし、到達可能なオブジェクトを特定します。
*   **GCマップ**: ヒープ上のオブジェクト内のポインタの位置を示す情報。

コミットメッセージで「without stackmaps we can't grow stacks」とあるように、SSAバックエンドがまだスタックマップを正確に生成できない段階では、スタックの動的な拡張（スタックグロース）が困難になります。そのため、一時的にデフォルトのスタックサイズを大きくすることで、スタックオーバーフローを防ぐ措置が取られました。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドのデバッグとテストを容易にするための重要な変更を導入しています。

1.  **SSA有効化の制御**:
    *   `src/cmd/compile/internal/gc/ssa.go` の `buildssa` 関数が変更され、`usessa` フラグに加えて、環境変数 `GOSSAFUNC` または `GOSSAPKG` の値と現在の関数名/パッケージ名が一致する場合にSSAを有効にするロジックが追加されました。
    *   これにより、コンパイラを再ビルドすることなく、特定の関数やパッケージに対してSSAをオン/オフできるようになります。これは、SSAバックエンドのバグを特定し、修正する際のイテレーションサイクルを大幅に短縮します。

2.  **スタックサイズの増加**:
    *   コミットメッセージでは、`runtime/stack2.go` の `_StackMin` を一時的に `32768` のような大きな値に増やすことが推奨されています。これは、SSAバックエンドがまだスタックマップを正確に生成できないため、スタックの動的な拡張ができないことへの一時的な対処です。スタックマップがないと、GCがスタック上のポインタを正確に識別できず、スタックグロースの際に問題が発生する可能性があります。デフォルトのスタックサイズを大きくすることで、スタックオーバーフローのリスクを減らします。

3.  **未実装コード生成の報告改善**:
    *   `genValue` および `genBlock` 関数における `Unimplementedf` の呼び出しが変更され、より詳細な情報（例: `genValue not implemented: REPMOVSB`）を出力するように改善されました。これにより、SSAバックエンドでまだサポートされていない命令や制御フローの種類を開発者が迅速に特定できるようになります。
    *   特に、`ssaExport` 構造体に `mustImplement` フィールドが追加され、`genssa` 関数内で `e.mustImplement = true` が設定されます。これにより、SSAコード生成が明示的に要求された場合（つまり `GOSSAFUNC` や `GOSSAPKG` が使用された場合）、未実装のコード生成パスに遭遇した際に、単にSSAを無効にするのではなく、`Fatal` エラーとしてコンパイルを停止させるようになります。これは、未実装部分を早期に発見し、修正を促すための強力なメカニズムです。

4.  **初期テスト結果の報告**:
    *   コミットメッセージには、この変更を適用して標準ライブラリに対してSSAを有効にした際の初期テスト結果が記載されています。
        *   いくつかのパッケージではSSA生成コードでテストがパスしたこと。
        *   `encoding/base64` ではコード生成はできたもののテストが失敗し、バグの存在が示唆されたこと。
        *   ランタイムのビルド中に `panic: interface conversion: ssa.Location is nil, not *ssa.LocalSlot` というパニックが発生したこと。
        *   未実装のコード生成項目（`REPMOVSB`, `REPSTOSQ`, `SUBQ` など）のトップリストが示されており、今後の開発の優先順位付けに役立つ情報が提供されています。

これらの変更は、GoコンパイラのSSAバックエンドを実用的なものにするための、体系的なデバッグとテスト戦略の一環として非常に重要です。

    *   `ssaExport` 構造体に `mustImplement bool` フィールドが追加され、`Unimplementedf` メソッド内でこのフラグが `true` の場合に `Fatal` エラーを発生させるロジックが追加されました。

2.  `src/cmd/compile/internal/ssa/config.go`
    *   `Config` 構造体の `Frontend()` メソッドが追加されました。これは、`Config` から `Frontend` インターフェースを取得するためのシンプルなアクセサメソッドです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go`

```go
// 変更前
// return s.f, usessa // TODO: return s.f, true once runtime support is in (gc maps, write barriers, etc.)

// 変更後
// TODO: enable codegen more broadly once the codegen stabilizes
// and runtime support is in (gc maps, write barriers, etc.)
return s.f, usessa || name == os.Getenv("GOSSAFUNC") || localpkg.Name == os.Getenv("GOSSAPKG")
```
`buildssa` 関数は、特定の関数に対してSSAバックエンドを使用するかどうかを決定します。変更前は `usessa` フラグのみに依存していましたが、変更後は `os.Getenv("GOSSAFUNC")` または `os.Getenv("GOSSAPKG")` の値が現在の関数名 (`name`) またはパッケージ名 (`localpkg.Name`) と一致する場合にもSSAを有効にするようになりました。これにより、開発者はコンパイラを再ビルドすることなく、特定のターゲットに対してSSAをテストできるようになります。

```go
// genssa 関数内
e := f.Config.Frontend().(*ssaExport)
// We're about to emit a bunch of Progs.
// Since the only way to get here is to explicitly request it,
// just fail on unimplemented instead of trying to unwind our mess.
e.mustImplement = true
```
`genssa` 関数は、SSA形式から最終的な機械語コードを生成する段階です。この段階で `e.mustImplement = true` を設定することで、もしSSAコード生成が明示的に要求された（つまり `GOSSAFUNC` や `GOSSAPKG` が使われた）にもかかわらず、未実装のコード生成パスに遭遇した場合、コンパイラは致命的なエラー (`Fatal`) を発生させるようになります。これは、未実装部分を早期に発見し、修正を強制するためのデバッグ支援機能です。

```go
// genValue 関数内
// 変更前
// v.Unimplementedf("value %s not implemented", v.LongString())
// 変更後
v.Unimplementedf("genValue not implemented: %s", v.LongString())

// genBlock 関数内
// 変更前
// b.Unimplementedf("branch %s not implemented", b.LongString())
// 変更後
b.Unimplementedf("branch not implemented: %s. Control: %s", b.LongString(), b.Control.LongString())
```
`genValue` と `genBlock` は、それぞれSSAの値とブロックから機械語コードを生成する関数です。これらの関数内で未実装のケースに遭遇した場合に呼び出される `Unimplementedf` のメッセージがより具体的になりました。これにより、どのSSA値や制御フローが未実装であるかを開発者が一目で理解できるようになり、デバッグが容易になります。

```go
// ssaExport 構造体
type ssaExport struct {
	log           bool

	mustImplement bool // 追加
}

// Unimplementedf メソッド
func (e *ssaExport) Unimplementedf(msg string, args ...interface{}) {
	if e.mustImplement { // 追加
		Fatal(msg, args...) // 追加
	} // 追加
	const alwaysLog = false // enable to calculate top unimplemented features
	if !e.unimplemented && (e.log || alwaysLog) {
		// first implementation failure, print explanation
```
`ssaExport` は、SSAバックエンドとコンパイラのフロントエンド間のインターフェースを扱う構造体です。`mustImplement` フィールドが追加され、`Unimplementedf` メソッド内でこのフラグが `true` の場合に `Fatal` エラーを発生させるロジックが追加されました。これは、前述の `genssa` 関数での設定と連携し、明示的にSSAを有効にした場合に未実装部分でコンパイルを停止させることで、開発者が問題を見逃さないようにします。

### `src/cmd/compile/internal/ssa/config.go`

```go
func (c *Config) Frontend() Frontend { return c.fe }
```
`Config` 構造体はSSAバックエンドの設定を保持します。この変更は、`Config` オブジェクトから `Frontend` インターフェース（`ssaExport` が実装している）を取得するためのシンプルなアクセサメソッド `Frontend()` を追加するものです。これにより、`genssa` 関数内で `f.Config.Frontend().(*ssaExport)` のように、`Config` から `ssaExport` インスタンスにアクセスできるようになります。

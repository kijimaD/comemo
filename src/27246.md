## 変更の背景

Goコンパイラは、最適化のためにプログラムをSSA（Static Single Assignment）形式という中間表現に変換します。SSA形式では、各変数は一度だけ代入されるという特性を持ち、これによりデータフロー解析や様々な最適化が容易になります。

SSA形式において、複数の制御フローパスが合流する地点では、異なるパスから来る同じ変数の値をマージするために「Phi関数（Φ関数）」が導入されます。また、制御フローグラフ（CFG）には「クリティカルエッジ」と呼ばれる特殊なエッジが存在することがあります。クリティカルエッジは、複数の後続ブロックを持つブロックから、複数の先行ブロックを持つブロックへのエッジを指します。

クリティカルエッジは、レジスタ割り当てやPhi関数の適切な配置を複雑にするため、コンパイラは通常、これらのエッジを解消する処理を行います。この解消は、クリティカルエッジの間に新しい空のブロックを挿入することで行われます（クリティカルエッジの分割）。

このコミット以前のクリティカルエッジ分割ロジックでは、Phi関数が重複する引数を持つ場合（つまり、同じ値が複数のクリティカルエッジを介して同じPhi関数に到達する場合）、それぞれの重複する引数に対して個別の新しい中間ブロックが作成される可能性がありました。これは冗長なブロック生成につながり、結果として生成されるコードのサイズが増加します。

このコミットの目的は、この冗長性を排除し、Phi関数が重複する引数を持つ場合に、それらの引数すべてに対して単一の中間ブロックを再利用することです。これにより、生成されるコードのサイズを削減し、コンパイラの効率を向上させます。コミットメッセージに記載されている「read-only data = -904 bytes」「global text (code) = -2240 bytes」といったサイズ削減の数値は、この最適化が実際にコードサイズを減少させたことを示しています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現です。この形式の主要な特性は、「各変数がプログラム内で一度だけ代入される」という点です。例えば、通常のコードで `x = 1; x = 2;` と書かれた場合、SSA形式では `x1 = 1; x2 = 2;` のように、代入ごとに新しいバージョン（新しい変数）が作成されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が大幅に簡素化されます。多くのコンパイラ最適化（デッドコード削除、定数伝播、共通部分式除去など）は、SSA形式上でより効果的に実行できます。

### 2. Phi関数 (Φ関数)

SSA形式の重要な要素の一つがPhi関数です。プログラムの制御フローが分岐し、その後再び合流する地点（例えば、`if-else`文の終わりやループの先頭）では、同じ論理変数に対して複数の異なる定義が存在する可能性があります。Phi関数は、これらの異なるパスから来る値を「マージ」し、合流後のコードが単一のSSA変数として扱えるようにするために導入されます。

例:
```
if condition {
    x = 1
} else {
    x = 2
}
// ここで x の値は 1 か 2 のどちらか
```
SSA形式では、これは以下のように表現されます。
```
if condition {
    x1 = 1
} else {
    x2 = 2
}
x3 = Φ(x1, x2) // x3 は x1 または x2 のいずれか
```
Phi関数は仮想的なものであり、直接機械語命令に変換されるわけではありません。最終的には、レジスタ割り当ての段階で適切なムーブ命令（コピー命令）に置き換えられます。

### 3. クリティカルエッジ (Critical Edge)

制御フローグラフ（CFG）は、プログラムの実行パスをノード（基本ブロック）とエッジ（制御フローの遷移）で表現したものです。クリティカルエッジは、CFGにおいて以下の条件を満たすエッジを指します。

*   **ソースブロックが複数の後続ブロックを持つ**: エッジの出発点となるブロックが、複数の異なるパスに分岐する。
*   **ターゲットブロックが複数の先行ブロックを持つ**: エッジの終着点となるブロックが、複数の異なるパスから合流する。

つまり、「多対多」の関係にあるエッジがクリティカルエッジです。クリティカルエッジが存在すると、Phi関数の配置やレジスタ割り当ての際に問題が生じることがあります。特に、Phi関数を機械語のムーブ命令に変換する「Phi関数除去」のプロセスにおいて、クリティカルエッジは複雑さを増します。

### 4. クリティカルエッジの分割 (Splitting Critical Edges)

クリティカルエッジがコンパイラの最適化やコード生成に与える問題を回避するため、コンパイラは通常、クリティカルエッジを「分割」します。これは、クリティカルエッジの間に新しい空の基本ブロックを挿入することで行われます。

例:
`ブロックA` -> `ブロックB` がクリティカルエッジである場合、
`ブロックA` -> `新しい空のブロックX` -> `ブロックB`
のように変更されます。

この変換により、`ブロックA` -> `ブロックX` はクリティカルエッジではなくなり（`ブロックX`は単一の先行ブロックしか持たない）、`ブロックX` -> `ブロックB` もクリティカルエッジではなくなります（`ブロックX`は単一の後続ブロックしか持たない）。
クリティカルエッジの分割は、Phi関数除去を簡素化し、レジスタ割り当ての効率を向上させるために不可欠な前処理です。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおけるクリティカルエッジ分割のプロセスを最適化します。特に、Phi関数が重複する引数を持つ場合に発生する冗長な中間ブロックの生成を防ぐことに焦点を当てています。

従来のクリティカルエッジ分割では、クリティカルエッジが見つかるたびに新しい空のブロックが挿入されていました。しかし、もしターゲットブロックのPhi関数が、複数の異なるクリティカルエッジから同じ値を受け取る場合（つまり、Phi関数の引数リストに同じ`Value`が複数回出現する場合）、それぞれのクリティカルエッジに対して個別の新しい中間ブロックが作成されていました。これは、同じ目的（同じ値の伝達）を持つ複数のブロックが生成されることを意味し、コードサイズの増加につながります。

このコミットは、この問題を解決するために以下のメカニズムを導入しています。

1.  **Phi関数の引数と中間ブロックのマッピング**:
    `blocks`という配列が導入され、Phi関数の引数（`Value`）のIDをキーとして、その引数に対応するクリティカルエッジ解消のために挿入された新しいブロックを格納します。これにより、特定のPhi引数に対して既に中間ブロックが作成されているかどうかを追跡できます。

2.  **単一Phi関数の優先処理**:
    ターゲットブロックにPhi関数が複数ある場合よりも、単一のPhi関数しかない場合の方が処理が単純であるため、まずブロック内に単一のPhi関数が存在するかどうかをチェックします。単一のPhi関数である場合に、この最適化ロジックが適用されます。

3.  **中間ブロックの再利用**:
    クリティカルエッジを分割する際、現在のPhi関数の引数に対応する中間ブロックが`blocks`配列に既に存在するかどうかを確認します。
    *   もし存在すれば、新しいブロックを作成する代わりに、既存のブロックを再利用します。この場合、元の先行ブロックとPhi関数の引数は`nil`に設定され、後でリストから除去されます。
    *   もし存在しなければ、新しいブロックを作成し、それを`blocks`配列に登録します。

この再利用メカニズムにより、Phi関数が重複する引数を持つクリティカルエッジを処理する際に、冗長な中間ブロックの生成が抑制されます。結果として、コンパイル後のバイナリサイズが削減され、コンパイラの全体的な効率が向上します。コミットメッセージに示されているように、この変更によって読み取り専用データとグローバルテキスト（コード）のサイズが減少しています。

## コアとなるコードの変更箇所

変更は主に `src/cmd/compile/internal/ssa/critical.go` ファイルの `critical` 関数に集中しています。

主な変更点は以下の通りです。

1.  **`blocks` 配列の導入**:
    ```go
    // maps from phi arg ID to the new block created for that argument
    blocks := make([]*Block, f.NumValues())
    ```
    `f.NumValues()` は関数内のSSA値の総数を返します。この配列は、Phi関数の引数（`Value`）のIDをインデックスとして、その引数に対応するクリティカルエッジ解消のために挿入された新しいブロックを格納するために使用されます。

2.  **`f.Blocks` のイテレーション方法の変更**:
    ```go
    // need to iterate over f.Blocks without range, as we might
    // need to split critical edges on newly constructed blocks
    for j := 0; j < len(f.Blocks); j++ {
    	b := f.Blocks[j]
    	// ...
    }
    ```
    `range` ループではなく、`len(f.Blocks)` を使用した通常の `for` ループに変更されました。これは、クリティカルエッジの分割によって新しいブロックが `f.Blocks` スライスに追加される可能性があるため、ループ中にスライスの長さが変化しても正しく処理できるようにするためです。

3.  **単一Phi関数の検出ロジック**:
    ```go
    var phi *Value
    // determine if we've only got a single phi in this
    // block, this is easier to handle than the general
    // case of a block with multiple phi values.
    for _, v := range b.Values {
    	if v.Op == OpPhi {
    		if phi != nil {
    			phi = nil
    			break
    		}
    		phi = v
    	}
    }
    ```
    現在のブロック `b` にPhi関数が一つだけ存在するかどうかをチェックします。この最適化は、単一のPhi関数を持つブロックに対してより効果的に適用されます。

4.  **`blocks` 配列のリセット**:
    ```go
    // reset our block map
    if phi != nil {
    	for _, v := range phi.Args {
    		blocks[v.ID] = nil
    	}
    }
    ```
    各ブロック `b` の処理を開始する前に、`blocks` 配列をリセットします。これにより、異なるブロックのPhi関数が同じ `Value.ID` を持つ可能性があっても、前のブロックの処理による影響を受けないようにします。

5.  **クリティカルエッジ分割ロジック内のブロック再利用**:
    ```go
    			var d *Block         // new block used to remove critical edge
    			reusedBlock := false // if true, then this is not the first use of this block
    			if phi != nil {
    				argID := phi.Args[i].ID
    				// find or record the block that we used to split
    				// critical edges for this argument
    				if d = blocks[argID]; d == nil {
    					d = f.NewBlock(BlockPlain)
    					d.Line = c.Line
    					blocks[argID] = d
    					if f.pass.debug > 0 {
    						f.Config.Warnl(c.Line, "split critical edge")
    					}
    				} else {
    					reusedBlock = true
    				}
    			} else {
    				// no existing block, so allocate a new block
    				// to place on the edge
    				d = f.NewBlock(BlockPlain)
    				d.Line = c.Line
    				if f.pass.debug > 0 {
    					f.Config.Warnl(c.Line, "split critical edge")
    				}
    			}
    ```
    この部分で、Phi関数の引数ID (`argID`) を使って `blocks` 配列を検索し、対応する中間ブロック `d` が既に存在するかどうかを確認します。存在すれば `reusedBlock` フラグを `true` に設定し、既存のブロックを再利用します。存在しなければ新しいブロックを作成し、`blocks` 配列に格納します。

6.  **再利用されたブロックの処理**:
    ```go
    			// if this not the first argument for the
    			// block, then we need to remove the
    			// corresponding elements from the block
    			// predecessors and phi args
    			if reusedBlock {
    				d.Preds = append(d.Preds, c)
    				b.Preds[i] = nil
    				phi.Args[i] = nil
    			} else {
    				// splice it in
    				d.Preds = append(d.Preds, c)
    				d.Succs = append(d.Succs, b)
    				b.Preds[i] = d
    			}
    ```
    `reusedBlock` が `true` の場合、再利用されるブロック `d` の先行ブロックリストに現在の先行ブロック `c` を追加します。しかし、ターゲットブロック `b` の先行ブロックリスト (`b.Preds[i]`) とPhi関数の引数リスト (`phi.Args[i]`) の対応するエントリは `nil` に設定されます。これは、後でこれらの `nil` エントリをフィルタリングして削除するための準備です。

7.  **`filterNilValues` および `filterNilBlocks` 関数の追加**:
    ```go
    // filterNilValues preserves the order of v, while filtering out nils.
    func filterNilValues(v []*Value) []*Value {
    	nv := v[:0]
    	for i := range v {
    		if v[i] != nil {
    			nv = append(nv, v[i])
    		}
    	}
    	return nv
    }

    // filterNilBlocks preserves the order of b, while filtering out nils.
    func filterNilBlocks(b []*Block) []*Block {
    	nb := b[:0]
    	for i := range b {
    		if b[i] != nil {
    			nb = append(nb, b[i])
    		}
    	}
    	return nb
    }
    ```
    これらの新しいヘルパー関数は、スライス内の `nil` エントリを効率的に削除し、元の要素の順序を維持します。`reusedBlock` のケースで `nil` に設定された `phi.Args` と `b.Preds` のエントリをクリーンアップするために、`critical` 関数の最後に呼び出されます。

## コアとなるコードの解説

`critical` 関数は、GoコンパイラのSSAバックエンドにおいて、制御フローグラフからクリティカルエッジを削除する役割を担っています。このコミットによる変更は、特にPhi関数が重複する引数を持つ場合に、この処理をより効率的に行うためのものです。

変更の核心は、`blocks` 配列と `reusedBlock` フラグを用いた中間ブロックの再利用ロジックにあります。

1.  **`blocks` 配列によるマッピング**:
    `blocks := make([]*Block, f.NumValues())` は、関数内のすべてのSSA値に対して、その値がPhi関数の引数として使われた場合に、クリティカルエッジ分割によって挿入された中間ブロックを記録するためのマップとして機能します。`Value.ID` をインデックスとして使用することで、特定のSSA値に対応する中間ブロックを一意に識別し、再利用することが可能になります。

2.  **動的なブロックリストのイテレーション**:
    `for j := 0; j < len(f.Blocks); j++` というループ構造は、クリティカルエッジの分割中に新しいブロックが `f.Blocks` リストに追加される可能性があるため、非常に重要です。これにより、新しく挿入されたブロック自体がクリティカルエッジのソースまたはターゲットになる場合でも、適切に処理が継続されます。

3.  **単一Phi関数の最適化パス**:
    `phi` 変数とそれに続くチェックは、ブロックに単一のPhi関数しかない場合に、より特化した最適化パスを適用するためのものです。複数のPhi関数がある場合、引数の重複を効率的に管理するのがより複雑になるため、このコミットでは単一Phi関数に焦点を当てています。

4.  **ブロック再利用の判断**:
    クリティカルエッジが見つかり、ターゲットブロックに単一のPhi関数がある場合、`argID := phi.Args[i].ID` で現在のPhi引数のIDを取得します。そして `if d = blocks[argID]; d == nil` で、この `argID` に対応する中間ブロックが既に `blocks` 配列に存在するかどうかを確認します。
    *   `d == nil` の場合、そのPhi引数に対してはまだ中間ブロックが作成されていないため、`f.NewBlock(BlockPlain)` を呼び出して新しいブロック `d` を作成し、`blocks[argID] = d` で記録します。
    *   `d != nil` の場合、既に同じPhi引数に対応する中間ブロックが存在するため、`reusedBlock = true` を設定し、その既存のブロック `d` を再利用します。

5.  **再利用時のリスト操作**:
    `if reusedBlock` のブロックでは、既存のブロック `d` の先行ブロックリストに現在の先行ブロック `c` を追加します。しかし、ターゲットブロック `b` の先行ブロックリスト (`b.Preds[i]`) とPhi関数の引数リスト (`phi.Args[i]`) の対応するエントリは `nil` に設定されます。これは、これらのエントリが論理的には再利用されたブロックによって置き換えられたため、最終的なリストからは削除されるべきであることを示します。

6.  **`filterNilValues` と `filterNilBlocks` によるクリーンアップ**:
    `critical` 関数の最後に、`phi.Args = filterNilValues(phi.Args)` と `b.Preds = filterNilBlocks(b.Preds)` が呼び出されます。これらの関数は、前述のステップで `nil` に設定されたエントリをスライスから除去し、最終的な制御フローグラフとPhi関数の定義をクリーンな状態に保ちます。これにより、冗長なエントリが削除され、コードの正確性と効率が維持されます。

この一連の変更により、Goコンパイラはクリティカルエッジの分割において、よりスマートなブロック管理を行うようになり、特にPhi関数が重複する引数を持つシナリオでのコード生成の効率が向上しました。これは、コンパイルされたプログラムのサイズ削減という具体的なメリットをもたらします。

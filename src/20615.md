# [インデックス 20615] ファイルの概要

このコミットは、Go言語のランタイム、コンパイラ（`cmd/cc`）、リンカ（`cmd/ld`）にわたる広範な変更を含んでおり、主にガベージコレクション（GC）の精度向上を目的としています。具体的には、データセクションやBSSセクション（初期化されていないグローバル変数）における「保守的な（conservative）」GCスキャンを排除し、より正確なGCを実現するための型情報伝達メカニズムを強化しています。

## 変更の背景

Go言語のガベージコレクション（GC）は、その効率性と低レイテンシが特徴の一つです。GoのGCは基本的に「正確な（precise）」GCを目指しており、これはヒープ上のオブジェクトがポインタであるか否かを正確に識別できることを意味します。正確なGCは、誤って非ポインタ値をポインタと解釈してオブジェクトを保持してしまう「保守的な（conservative）」GCに比べて、メモリリークのリスクを減らし、より効率的なメモリ再利用を可能にします。

しかし、GoプログラムがC言語のコードと連携するCgoを使用する場合や、Goランタイム自体がC言語で書かれた部分を持つ場合、Goの型システムがC言語のデータ構造内のポインタを完全に把握できない状況が発生することがありました。特に、データセクション（初期化されたグローバル変数）やBSSセクション（初期化されていないグローバル変数）に配置されるC言語由来のグローバル変数や静的変数について、Goランタイムがその内容を保守的にスキャンせざるを得ないケースが存在しました。

保守的なスキャンとは、メモリ領域内のすべてのワードをポインタである可能性があるものとして扱い、それが有効なポインタであれば参照先のオブジェクトを「生きている」とマークする方式です。これは安全ではありますが、実際にはポインタではない整数値などを誤ってポインタと解釈し、本来回収されるべきメモリを保持し続けてしまう（偽の参照、false positive）可能性があります。これにより、メモリ使用量が増加したり、GCの効率が低下したりする問題がありました。

このコミットの主な目的は、Goプログラム（特にCgoを使用しない、またはSWIGを使用しないプログラム）におけるデータ/BSSセクションの保守的なGCスキャンを完全に排除し、GoのGCをより正確にすることです。これは、GoとCの境界における型情報の伝達を改善し、リンカがC言語由来のグローバル変数についても正確なGC型情報を利用できるようにすることで実現されます。

具体的には、GoランタイムがC言語のグローバル変数や静的変数について、それがポインタを含むかどうか、あるいはGoのヒープオブジェクトへのポインタを含むかどうかを正確に識別できるようにするためのメカニズムが導入されました。これにより、GCは不要なメモリを保持することなく、より効率的に動作できるようになります。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について理解しておく必要があります。

1.  **ガベージコレクション (GC)**:
    *   **正確なGC (Precise GC)**: GCがメモリ内のどの値がポインタであり、どの値がポインタではないかを正確に識別できる方式です。これにより、GCは到達可能なオブジェクトのみを正確にマークし、到達不能なオブジェクトを確実に回収できます。GoのGCは基本的に正確なGCを目指しています。
    *   **保守的なGC (Conservative GC)**: GCがメモリ内の値がポインタであるかどうかを確実に識別できない場合に用いられる方式です。この場合、GCはメモリ内のすべてのワードをポインタである可能性があるものとして扱い、それが有効なポインタのように見える場合は、その参照先のオブジェクトを「生きている」と見なします。これにより、誤って非ポインタ値をポインタと解釈し、本来回収されるべきメモリを保持し続けてしまう「偽の参照（false positive）」が発生する可能性があります。
    *   **データセクションとBSSセクション**: プログラムの実行可能ファイルには、様々なセクションが含まれます。
        *   **データセクション (.data)**: 初期化されたグローバル変数や静的変数が格納される領域です。
        *   **BSSセクション (.bss)**: 初期化されていないグローバル変数や静的変数が格納される領域です。プログラム開始時にゼロで初期化されます。
        これらのセクションにC言語由来の変数が存在する場合、GoのGCがその内容を正確に理解できないことが問題でした。

2.  **Goのコンパイルとリンクプロセス**:
    *   **`cmd/cc` (Cコンパイラ)**: Goのツールチェーンに含まれるCコンパイラで、CgoによってGoコードから呼び出されるCコードや、Goランタイムの一部としてCで書かれたコードをコンパイルします。
    *   **`cmd/ld` (リンカ)**: コンパイルされたオブジェクトファイル（Goコード、Cコード）を結合し、最終的な実行可能ファイルを生成します。この過程で、異なるオブジェクトファイル間で重複するシンボルを解決（dedup）したり、GCに必要な型情報を埋め込んだりします。
    *   **`cmd/dist`**: Goのビルドシステムの一部で、Goツールチェーン自体のビルドや、ランタイムのCコードからGoの型情報を生成するなどの役割を担います。

3.  **Cgo**: GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を扱ったりするためのGoの機能です。Cgoを使用すると、GoとCのメモリモデルや型システムの間の橋渡しが必要になります。

4.  **GC型情報**: GoのGCが正確に動作するためには、メモリ上の各オブジェクトがどのような型を持ち、その中にポインタがどこに含まれているかという情報（GC型情報）が必要です。この情報は、コンパイラとリンカによって生成され、実行可能ファイルに埋め込まれます。

5.  **`NOPTR` フラグ**: このコミットで導入または活用が強化された概念です。これは、特定のメモリ領域やデータ構造がポインタを含まないことをGCに明示的に伝えるためのフラグです。`NOPTR`とマークされた領域は、GCスキャンの対象から除外されるため、保守的なスキャンが不要になります。

## 技術的詳細

このコミットは、GoのGCがデータ/BSSセクションを保守的にスキャンする問題を解決するために、複数のコンポーネントにわたる協調的な変更を導入しています。

1.  **リンカ (`src/cmd/ld/data.c`, `src/liblink/objfile.c`) の変更**:
    *   **保守的なGC型情報の拒否**: リンカは、データ/BSSセクションの変数に対して「保守的な（array of pointers）」GC型情報を書き込むことを拒否するようになりました。これにより、リンカはGC型情報が不完全な場合に警告を発し、開発者に問題の存在を知らせます。
    *   **C宣言へのGo型情報の付与**: リンカは、重複排除（dedup）の際に、既に読み込まれたC言語の宣言にGoの型情報を付与するようになりました。これは、`cmd/dist`によって生成されたGoコードがC言語のグローバル変数に対応する宣言を含んでいる場合に特に有効です。GoランタイムのC言語宣言の多くは、対応するGo宣言を持っており、リンカはこれらをBSS宣言として重複排除します。この変更により、C言語のグローバル変数に対してもGoの型情報が自動的に利用できるようになります。

2.  **`cmd/dist` (`src/cmd/dist/buildruntime.c`) の変更**:
    *   **自動Go宣言リストへのCファイルの追加**: `cmd/dist`は、Goの型情報をリンカに提供するために、いくつかのCファイルを自動Go宣言リストに追加しました。これにより、これらのCファイル内のC言語宣言についても、Goの型情報がリンカに伝達されるようになります。具体的には、`mcache.c`と`stack.c`が追加されています。

3.  **Cコンパイラ (`src/cmd/cc/dcl.c`, `src/cmd/cc/lex.c`) の変更**:
    *   **`NOPTR` フラグの導入と適用**: Cコンパイラは、ポインタを含まないグローバル宣言とすべての文字列データに `NOPTR` フラグをマークするようになりました。これにより、これらのC言語ファイル内の変数が対応するGo宣言を持たない場合でも、GCがそれらをスキャンする必要がなくなります。
    *   **C関数ポインタの扱い**: C関数ポインタは、ヒープに割り当てられたC関数が存在しないため、「ポインタを含まない」ものとして扱われます。これは、C関数ポインタがGoのヒープオブジェクトを指す可能性がないため、GCスキャンの対象から除外できることを意味します。

4.  **ランタイム (`src/runtime/*`) の変更**:
    *   **残りのポインタを含む宣言への `NOPTR` の追加**: ランタイム内の、Goヒープオブジェクトを参照しない残りのポインタを含む宣言にも `NOPTR` フラグが追加されました。これにより、これらの変数がGCスキャンの対象から除外され、GCの精度が向上します。
    *   **`os.Args` と `syscall.envs` のランタイム所有変数への移動**: `os.Args`（コマンドライン引数）と `syscall.envs`（環境変数）のデータが、Goランタイムが所有する変数に移動されました。これは、`os`や`syscall`パッケージがインポートされていないプログラムでも、これらのランタイム変数が型情報を欠落しないようにするためです。型情報が欠落すると、保守的なスキャンが必要になる可能性があります。この変更により、これらの重要なデータ構造についても正確なGCが可能になります。

これらの変更は、Goのコンパイル、リンク、ランタイムの各段階で連携し、C言語由来のデータに対するGCの精度を向上させ、最終的に非SWIG Goプログラムにおける保守的なGCスキャンを排除することを目指しています。

## コアとなるコードの解説

このコミットの核心は、GoのGCがC言語由来のグローバル変数や静的変数をスキャンする際に、その内容がポインタであるか否かを正確に判断できるようにすることです。

*   **`NOPTR` フラグの活用**: 最も重要な変更は、`NOPTR` フラグの適用範囲を拡大したことです。Cコンパイラ（`cmd/cc`）は、文字列リテラルや、Goヒープオブジェクトを指さないことが確実なC言語のグローバル変数（C関数ポインタを含む）にこのフラグを付与します。これにより、リンカやランタイムはこれらの領域をGCスキャンから除外できます。これは、保守的なスキャンを不要にする直接的な手段です。

*   **リンカにおける型情報の強化**: リンカ（`cmd/ld`, `src/liblink/objfile.c`）は、C言語のシンボルに対してもGoの型情報をより積極的に関連付けるようになりました。`cmd/dist`が生成するGoコードがC言語のグローバル変数に対応する宣言を持つ場合、リンカはそのGoの型情報をC言語のシンボルに「重複排除」の過程で付与します。これにより、C言語のデータ構造であっても、GoのGCがその内部のポインタを正確に識別できるようになります。型情報が欠落している場合は、リンカが警告を発することで、問題の早期発見を促します。

*   **`os.Args` と `syscall.envs` の管理**: `os.Args` と `syscall.envs` は、Goプログラムにとって非常に重要なデータですが、これらがC言語のランタイム初期化プロセスで設定されるため、Goの型システムがその内容を完全に把握できない可能性がありました。このコミットでは、これらのデータをGoランタイムが直接所有する変数に移動し、`os`や`syscall`パッケージがインポートされていない場合でも、GCがこれらのデータ構造内のポインタを正確に追跡できるようにしました。これにより、これらのデータに対する保守的なスキャンが不要になります。

これらの変更は、GoのGCがC言語との相互運用性を持つ環境においても、より「正確」に動作するための基盤を強化するものです。結果として、メモリ使用量の削減、GCの一時停止時間の短縮、そして全体的なパフォーマンスの向上が期待されます。特に、GoとCgoを組み合わせたアプリケーションにおいて、メモリリークのリスクを低減し、より予測可能なGC動作を実現します。

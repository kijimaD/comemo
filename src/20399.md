# [インデックス 20399] ファイルの概要

このコミットは、Goランタイムの`src/pkg/runtime/proc.c`ファイルに対する変更です。`proc.c`はGoランタイムの中核をなすファイルの一つで、プロセスの管理、スケジューリング、シグナルハンドリングなど、低レベルな操作を司っています。特に、CPUプロファイリングに関連する`runtime·sigprof`（シグナルハンドラ）や`runtime·setcpuprofilerate`（プロファイルレート設定関数）のロジックが含まれています。

## コミット

このコミットは、GoランタイムにおけるCPUプロファイリングのシグナルハンドラ（`sigprof`）とプロファイルレート設定関数（`setcpuprofilerate`）間の同期メカニズムを改善するものです。既存の`Mutex`ベースの同期がシグナルスタック上でのデッドロックの可能性や`onM`コンテキストでの問題を引き起こすため、よりシンプルで安全なCompare-and-Swap（CAS）ループによる同期に置き換えられました。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/e0f08b938a37490cd6e4f6bb33360678ac5f42b0](https://github.com/golang/go/commit/e0f08b938a37490cd6e4f6bb33360678ac5f42b0)

## 元コミット内容

```
runtime: use cas loop to coordinate with sigprof

sigprof and setcpuprofilerate coordinate the enabling/disabling
of the handler using a Mutex. This has always been a bit dodgy:
setcpuprofilerate must be careful to turn off signals before acquiring
the lock to avoid a deadlock.

Now the lock implementations use onM, and onM isn't okay on the
signal stack. We know how to make it okay, but it's more work than
is probably worth doing.

Since this is super-dodgy anyway, replace the lock with a simple
cas loop. It is only contended if setcpuprofilerate is being called,
and that doesn't happen frequently enough to care about the
raw speed or about using futexes/semaphores.

TBR to fix freebsd/amd64 and dragonfly/amd64 builds.
Happy to make changes in a follow-up CL.

TBR=dvyukov
CC=golang-codereviews
https://golang.org/cl/141080044
```

## 変更の背景

この変更の背景には、GoランタイムのCPUプロファイリングにおける既存の同期メカニズムが抱えていた問題があります。

1.  **Mutexによるデッドロックの可能性**: CPUプロファイリングは`SIGPROF`シグナルを利用して行われます。`runtime·sigprof`は`SIGPROF`シグナルを受け取った際に実行されるハンドラであり、`runtime·setcpuprofilerate`はプロファイリングのレートを設定する関数です。これら二つの関数は、プロファイリングの有効/無効を調整するために`Mutex`（ミューテックス）を使用していました。しかし、`setcpuprofilerate`がロックを取得する前にシグナルをオフにしないと、デッドロックが発生する可能性がありました。これは、シグナルハンドラがロックを保持している間に`setcpuprofilerate`がロックを取得しようとすると、シグナルハンドラがブロックされ、結果としてデッドロックに陥るためです。

2.  **シグナルスタックと`onM`コンテキストの問題**: Goランタイムのロック実装は、`onM`コンテキスト（OSスレッドM上でGoルーチンGが実行されている状態）に依存しています。しかし、シグナルハンドラは通常のGoルーチンとは異なるシグナルスタック上で実行されるため、`onM`コンテキストが適切に設定されていない場合があります。このため、シグナルスタック上で`Mutex`を使用すると、予期せぬ動作やクラッシュを引き起こす可能性がありました。コミットメッセージにある「onM isn't okay on the signal stack」という記述は、この問題を指しています。この問題を解決するには、シグナルスタック上での`onM`の振る舞いを適切に処理するための追加作業が必要でしたが、コミット作成者はその労力に見合わないと判断しました。

これらの問題を解決し、より堅牢でシンプルな同期メカニズムを導入するために、`Mutex`の使用を避け、Compare-and-Swap（CAS）ループに置き換えることが決定されました。`setcpuprofilerate`の呼び出し頻度が低いため、CASループによる同期でもパフォーマンス上の問題は発生しないと判断されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびOSの概念に関する知識が必要です。

*   **`SIGPROF`シグナル**: Unix系OSで利用されるシグナルの一つで、プロファイリングのために定期的にプロセスに送信されます。GoのCPUプロファイラは、このシグナルを受信した際に実行中のGoルーチンのスタックトレースをサンプリングします。
*   **`runtime·sigprof`**: Goランタイム内部の関数で、`SIGPROF`シグナルを受信した際に呼び出されるシグナルハンドラです。CPUプロファイリングのサンプリング処理を行います。
*   **`runtime·setcpuprofilerate`**: Goランタイム内部の関数で、CPUプロファイリングのサンプリングレート（頻度）を設定します。`pprof.StartCPUProfile`などの高レベルなAPIから呼び出されます。
*   **`Mutex` (ミューテックス)**: 相互排他ロックの一種で、複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスするのを防ぐために使用されます。Goの`sync.Mutex`は、内部的にCAS操作や`futex`（Linuxの場合）などを組み合わせて効率的なロックを実現しています。
*   **Compare-and-Swap (CAS)**: アトミック操作の一種で、メモリ上の特定のアドレスにある値が期待する値と一致する場合にのみ、その値を新しい値に更新します。この操作は不可分（アトミック）であるため、複数のスレッドが同時にアクセスしても競合状態が発生しません。ロックフリーなデータ構造やアルゴリズムを実装する際によく用いられます。
*   **`onM`コンテキスト**: Goランタイムのスケジューラモデル（M-P-Gモデル）における概念です。MはOSスレッド（Machine）、Pはプロセッサ（Processor）、GはGoルーチン（Goroutine）を表します。`onM`コンテキストとは、OSスレッドMがPを占有し、その上でGoルーチンGを実行している状態を指します。Goランタイムの多くの内部処理は、この`onM`コンテキストが前提となっています。シグナルハンドラは通常のGoルーチンとは異なるコンテキストで実行されるため、`onM`コンテキストが保証されない場合があります。
*   **シグナルスタック**: OSがシグナルハンドラを実行するために使用する特別なスタック領域です。通常のプログラムスタックとは独立しており、シグナルハンドラが安全に実行されることを保証します。
*   **`futex` (Fast user-space mutex)**: Linuxカーネルが提供するシステムコールで、ユーザー空間での高速なミューテックス実装を可能にします。競合がない場合はユーザー空間でロックの取得・解放を完結させ、競合が発生した場合にのみカーネルに介入を要求します。
*   **`semaphores` (セマフォ)**: 複数のプロセスやスレッドが共有リソースにアクセスする際の同期を制御するためのメカニズムです。カウンタを持ち、リソースの利用可能数を管理します。

## 技術的詳細

このコミットの技術的な核心は、`prof`構造体の`lock`フィールドの型を`Mutex`から`uint32`に変更し、その同期メカニズムを`Mutex`のロック/アンロックからCASループに置き換えた点にあります。

**変更前:**

```c
static struct {
	Mutex lock; // Mutex型のロック
	int32 hz;
} prof;

// runtime·sigprof 内
if(prof.hz != 0) {
	runtime·lock(&prof.lock); // Mutexのロック
	if(prof.hz != 0)
		runtime·cpuproftick(stk, n);
	runtime·unlock(&prof.lock); // Mutexのアンロック
}

// runtime·setcpuprofilerate_m 内
runtime·lock(&prof.lock); // Mutexのロック
prof.hz = hz;
runtime·unlock(&prof.lock); // Mutexのアンロック
```

**変更後:**

```c
static struct {
	uint32 lock; // uint32型のロック（0: アンロック, 1: ロック）
	int32 hz;
} prof;

// runtime·sigprof 内
if(prof.hz != 0) {
	// Simple cas-lock to coordinate with setcpuprofilerate.
	while(!runtime·cas(&prof.lock, 0, 1)) // CASループでロック取得
		runtime·osyield(); // ロック取得失敗時はOSに制御を譲る
	if(prof.hz != 0)
		runtime·cpuproftick(stk, n);
	runtime·atomicstore(&prof.lock, 0); // アトミックストアでロック解放
}

// runtime·setcpuprofilerate_m 内
while(!runtime·cas(&prof.lock, 0, 1)) // CASループでロック取得
	runtime·osyield(); // ロック取得失敗時はOSに制御を譲る
prof.hz = hz;
runtime·atomicstore(&prof.lock, 0); // アトミックストアでロック解放
```

**詳細な変更点と理由:**

1.  **`prof.lock`の型変更**: `Mutex`型から`uint32`型に変更されました。これは、`Mutex`が内部的に`onM`コンテキストに依存する複雑なロジックを持つため、シグナルスタック上で安全に使用できないという問題を回避するためです。`uint32`は単純な整数型であり、アトミック操作と組み合わせることで軽量なロックとして機能させることができます。
2.  **`runtime·lock` / `runtime·unlock` から CASループへの置き換え**:
    *   **ロック取得**: `runtime·lock(&prof.lock)`の代わりに、`while(!runtime·cas(&prof.lock, 0, 1))`というCASループが導入されました。
        *   `runtime·cas(&prof.lock, 0, 1)`は、`prof.lock`の値が`0`（アンロック状態）であれば`1`（ロック状態）に設定し、`true`を返します。そうでなければ`false`を返します。
        *   ループは、`prof.lock`が`0`になるまで（つまり、ロックが解放されるまで）`runtime·cas`を繰り返し試行します。
        *   `runtime·osyield()`は、CAS操作が失敗した場合にOSに制御を一時的に譲り、他のスレッドが実行される機会を与えます。これにより、ビジーループによるCPUの無駄な消費を抑えつつ、ロックが解放されるのを待つことができます。
    *   **ロック解放**: `runtime·unlock(&prof.lock)`の代わりに、`runtime·atomicstore(&prof.lock, 0)`が使用されました。
        *   `runtime·atomicstore(&prof.lock, 0)`は、`prof.lock`の値をアトミックに`0`に設定します。これにより、ロックが安全かつ不可分に解放されます。
3.  **`setcpuprofilerate`のデッドロック回避**: 以前は`setcpuprofilerate`がロックを取得する前にシグナルをオフにする必要がありましたが、CASループはシグナルハンドラと`setcpuprofilerate`の両方から安全にアクセスできるため、この複雑な調整が不要になりました。シグナルハンドラはシグナルスタック上で実行されるため、`Mutex`のような複雑な同期プリミティブを使用すると問題が発生する可能性がありましたが、CASはより低レベルでアトミックな操作であるため、このコンテキストでも安全に機能します。
4.  **パフォーマンスへの影響**: コミットメッセージにもあるように、`setcpuprofilerate`は頻繁に呼び出される関数ではないため、CASループによるビジーループ（`runtime·osyield()`があるため厳密にはビジーループではないが、スピンロックに近い）でもパフォーマンス上の大きな問題は発生しません。`futex`やセマフォのようなより複雑なカーネルレベルの同期メカニズムを使用するよりも、シンプルでオーバーヘッドの少ないCASが選択されました。

この変更により、CPUプロファイリングの同期メカニズムがより堅牢になり、シグナルハンドラとプロファイルレート設定関数間の競合状態が安全に解決されました。

## コアとなるコードの解説

上記の差分は、`prof`構造体の`lock`フィールドの型変更と、その`lock`フィールドを使用する`runtime·sigprof`および`runtime·setcpuprofilerate_m`関数の同期ロジックの変更を示しています。

1.  **`prof`構造体の変更**:
    ```diff
    -	Mutex lock;
    +	uint32 lock;
    ```
    `prof`構造体内の`lock`フィールドの型が`Mutex`から`uint32`に変更されました。これにより、`Mutex`の複雑な内部実装（特に`onM`コンテキストへの依存）を回避し、より低レベルなアトミック操作で同期を制御できるようになります。`uint32`型の`lock`は、`0`がロックされていない状態、`1`がロックされている状態を表すフラグとして機能します。

2.  **`runtime·sigprof`関数の変更**:
    ```diff
    -		runtime·lock(&prof.lock);
    +		// Simple cas-lock to coordinate with setcpuprofilerate.
    +		while(!runtime·cas(&prof.lock, 0, 1))
    +			runtime·osyield();
    		if(prof.hz != 0)
    			runtime·cpuproftick(stk, n);
    -		runtime·unlock(&prof.lock);
    +		runtime·atomicstore(&prof.lock, 0);
    ```
    `runtime·sigprof`は`SIGPROF`シグナルハンドラです。
    *   `runtime·lock(&prof.lock)`の呼び出しが削除され、代わりにCASループが導入されました。`while(!runtime·cas(&prof.lock, 0, 1))`は、`prof.lock`が`0`（アンロック状態）になるまで`runtime·cas`を繰り返し試行し、`0`であれば`1`に設定してロックを取得します。
    *   `runtime·osyield()`は、CAS操作が失敗した場合（つまり、他のスレッドがロックを保持している場合）に、現在のOSスレッドの実行を一時停止し、OSスケジューラに制御を戻します。これにより、CPUを無駄に消費するビジーループを避け、他のスレッドが実行される機会を与えます。
    *   `runtime·unlock(&prof.lock)`の呼び出しが削除され、代わりに`runtime·atomicstore(&prof.lock, 0)`が使用されました。これは、`prof.lock`の値をアトミックに`0`に設定し、ロックを安全に解放します。

3.  **`runtime·setcpuprofilerate_m`関数の変更**:
    ```diff
    -	runtime·lock(&prof.lock);
    +	while(!runtime·cas(&prof.lock, 0, 1))
    +		runtime·osyield();
     	prof.hz = hz;
    -	runtime·unlock(&prof.lock);
    +	runtime·atomicstore(&prof.lock, 0);
    ```
    `runtime·setcpuprofilerate_m`はCPUプロファイリングのレートを設定する関数です。
    *   ここでも`runtime·lock(&prof.lock)`がCASループに置き換えられ、`runtime·unlock(&prof.lock)`が`runtime·atomicstore(&prof.lock, 0)`に置き換えられました。
    *   これにより、`runtime·sigprof`と同様に、`setcpuprofilerate_m`もCASベースの同期メカニズムを使用するようになり、`Mutex`使用時のデッドロックの可能性やシグナルスタック上での問題を回避します。

これらの変更により、`prof`構造体へのアクセスは、`Mutex`のような高レベルな同期プリミティブではなく、より低レベルでシグナルセーフなアトミック操作（CASとアトミックストア）によって調整されるようになりました。これにより、シグナルハンドラとプロファイルレート設定関数間の同期がより堅牢かつシンプルになります。

# [インデックス 20399] ファイルの概要

このコミットは、Goランタイムの`src/pkg/runtime/proc.c`ファイルに対する変更です。`proc.c`はGoランタイムの中核をなすファイルの一つで、プロセスの管理、スケジューリング、シグナルハンドリングなど、低レベルな操作を司っています。特に、CPUプロファイリングに関連する`runtime·sigprof`（シグナルハンドラ）や`runtime·setcpuprofilerate`（プロファイルレート設定関数）のロジックが含まれています。

## コミット

このコミットは、GoランタイムにおけるCPUプロファイリングのシグナルハンドラ（`sigprof`）とプロファイルレート設定関数（`setcpuprofilerate`）間の同期メカニズムを改善するものです。既存の`Mutex`ベースの同期がシグナルスタック上でのデッドロックの可能性や`onM`コンテキストでの問題を引き起こすため、よりシンプルで安全なCompare-and-Swap（CAS）ループによる同期に置き換えられました。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/e0f08b938a37490cd6e4f6bb33360678ac5f42b0](https://github.com/golang/go/commit/e0f08b938a37490cd6e4f6bb33360678ac5f42b0)

## 元コミット内容

```
runtime: use cas loop to coordinate with sigprof

sigprof and setcpuprofilerate coordinate the enabling/disabling
of the handler using a Mutex. This has always been a bit dodgy:
setcpuprofilerate must be careful to turn off signals before acquiring
the lock to avoid a deadlock.

Now the lock implementations use onM, and onM isn't okay on the
signal stack. We know how to make it okay, but it's more work than
is probably worth doing.

Since this is super-dodgy anyway, replace the lock with a simple
cas loop. It is only contended if setcpuprofilerate is being called,
and that doesn't happen frequently enough to care about the
raw speed or about using futexes/semaphores.

TBR to fix freebsd/amd64 and dragonfly/amd64 builds.
Happy to make changes in a follow-up CL.

TBR=dvyukov
CC=golang-codereviews
https://golang.org/cl/141080044
```

## 変更の背景

この変更の背景には、GoランタイムのCPUプロファイリングにおける既存の同期メカニズムが抱えていた問題があります。

1.  **Mutexによるデッドロックの可能性**: CPUプロファイリングは`SIGPROF`シグナルを利用して行われます。`runtime·sigprof`は`SIGPROF`シグナルを受け取った際に実行されるハンドラであり、`runtime·setcpuprofilerate`はプロファイリングのレートを設定する関数です。これら二つの関数は、プロファイリングの有効/無効を調整するために`Mutex`（ミューテックス）を使用していました。しかし、`setcpuprofilerate`がロックを取得する前にシグナルをオフにしないと、デッドロックが発生する可能性がありました。これは、シグナルハンドラがロックを保持している間に`setcpuprofilerate`がロックを取得しようとすると、シグナルハンドラがブロックされ、結果としてデッドロックに陥るためです。

2.  **シグナルスタックと`onM`コンテキストの問題**: Goランタイムのロック実装は、`onM`コンテキスト（OSスレッドM上でGoルーチンGが実行されている状態）に依存しています。しかし、シグナルハンドラは通常のGoルーチンとは異なるシグナルスタック上で実行されるため、`onM`コンテキストが適切に設定されていない場合があります。このため、シグナルスタック上で`Mutex`を使用すると、予期せぬ動作やクラッシュを引き起こす可能性がありました。コミットメッセージにある「onM isn't okay on the signal stack」という記述は、この問題を指しています。この問題を解決するには、シグナルスタック上での`onM`の振る舞いを適切に処理するための追加作業が必要でしたが、コミット作成者はその労力に見合わないと判断しました。

これらの問題を解決し、より堅牢でシンプルな同期メカニズムを導入するために、`Mutex`の使用を避け、Compare-and-Swap（CAS）ループに置き換えることが決定されました。`setcpuprofilerate`の呼び出し頻度が低いため、CASループによる同期でもパフォーマンス上の問題は発生しないと判断されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびOSの概念に関する知識が必要です。

*   **`SIGPROF`シグナル**: Unix系OSで利用されるシグナルの一つで、プロファイリングのために定期的にプロセスに送信されます。GoのCPUプロファイラは、このシグナルを受信した際に実行中のGoルーチンのスタックトレースをサンプリングします。
*   **`runtime·sigprof`**: Goランタイム内部の関数で、`SIGPROF`シグナルを受信した際に呼び出されるシグナルハンドラです。CPUプロファイリングのサンプリング処理を行います。
*   **`runtime·setcpuprofilerate`**: Goランタイム内部の関数で、CPUプロファイリングのサンプリングレート（頻度）を設定します。`pprof.StartCPUProfile`などの高レベルなAPIから呼び出されます。
*   **`Mutex` (ミューテックス)**: 相互排他ロックの一種で、複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスするのを防ぐために使用されます。Goの`sync.Mutex`は、内部的にCAS操作や`futex`（Linuxの場合）などを組み合わせて効率的なロックを実現しています。
*   **Compare-and-Swap (CAS)**: アトミック操作の一種で、メモリ上の特定のアドレスにある値が期待する値と一致する場合にのみ、その値を新しい値に更新します。この操作は不可分（アトミック）であるため、複数のスレッドが同時にアクセスしても競合状態が発生しません。ロックフリーなデータ構造やアルゴリズムを実装する際によく用いられます。
*   **`onM`コンテキスト**: Goランタイムのスケジューラモデル（M-P-Gモデル）における概念です。MはOSスレッド（Machine）、Pはプロセッサ（Processor）、GはGoルーチン（Goroutine）を表します。`onM`コンテキストとは、OSスレッドMがPを占有し、その上でGoルーチンGを実行している状態を指します。Goランタイムの多くの内部処理は、この`onM`コンテキストが前提となっています。シグナルハンドラは通常のGoルーチンとは異なるコンテキストで実行されるため、`onM`コンテキストが保証されない場合があります。
*   **シグナルスタック**: OSがシグナルハンドラを実行するために使用する特別なスタック領域です。通常のプログラムスタックとは独立しており、シグナルハンドラが安全に実行されることを保証します。
*   **`futex` (Fast user-space mutex)**: Linuxカーネルが提供するシステムコールで、ユーザー空間での高速なミューテックス実装を可能にします。競合がない場合はユーザー空間でロックの取得・解放を完結させ、競合が発生した場合にのみカーネルに介入を要求します。
*   **`semaphores` (セマフォ)**: 複数のプロセスやスレッドが共有リソースにアクセスする際の同期を制御するためのメカニズムです。カウンタを持ち、リソースの利用可能数を管理します。

## 技術的詳細

このコミットの技術的な核心は、`prof`構造体の`lock`フィールドの型を`Mutex`から`uint32`に変更し、その同期メカニズムを`Mutex`のロック/アンロックからCASループに置き換えた点にあります。

**変更前:**

```c
static struct {
	Mutex lock; // Mutex型のロック
	int32 hz;
} prof;

// runtime·sigprof 内
if(prof.hz != 0) {
	runtime·lock(&prof.lock); // Mutexのロック
	if(prof.hz != 0)
		runtime·cpuproftick(stk, n);
	runtime·unlock(&prof.lock); // Mutexのアンロック
}

// runtime·setcpuprofilerate_m 内
runtime·lock(&prof.lock); // Mutexのロック
prof.hz = hz;
runtime·unlock(&prof.lock); // Mutexのアンロック
```

**変更後:**

```c
static struct {
	uint32 lock; // uint32型のロック（0: アンロック, 1: ロック）
	int32 hz;
} prof;

// runtime·sigprof 内
if(prof.hz != 0) {
	// Simple cas-lock to coordinate with setcpuprofilerate.
	while(!runtime·cas(&prof.lock, 0, 1)) // CASループでロック取得
		runtime·osyield(); // ロック取得失敗時はOSに制御を譲る
	if(prof.hz != 0)
		runtime·cpuproftick(stk, n);
	runtime·atomicstore(&prof.lock, 0); // アトミックストアでロック解放
}

// runtime·setcpuprofilerate_m 内
while(!runtime·cas(&prof.lock, 0, 1)) // CASループでロック取得
	runtime·osyield(); // ロック取得失敗時はOSに制御を譲る
prof.hz = hz;
runtime·atomicstore(&prof.lock, 0); // アトミックストアでロック解放
```

**詳細な変更点と理由:**

1.  **`prof.lock`の型変更**: `Mutex`型から`uint32`型に変更されました。これは、`Mutex`が内部的に`onM`コンテキストに依存する複雑なロジックを持つため、シグナルスタック上で安全に使用できないという問題を回避するためです。`uint32`は単純な整数型であり、アトミック操作と組み合わせることで軽量なロックとして機能させることができます。
2.  **`runtime·lock` / `runtime·unlock` から CASループへの置き換え**:
    *   **ロック取得**: `runtime·lock(&prof.lock)`の代わりに、`while(!runtime·cas(&prof.lock, 0, 1))`というCASループが導入されました。
        *   `runtime·cas(&prof.lock, 0, 1)`は、`prof.lock`の値が`0`（アンロック状態）であれば`1`（ロック状態）に設定し、`true`を返します。そうでなければ`false`を返します。
        *   ループは、`prof.lock`が`0`になるまで（つまり、ロックが解放されるまで）`runtime·cas`を繰り返し試行します。
        *   `runtime·osyield()`は、CAS操作が失敗した場合にOSに制御を一時的に譲り、他のスレッドが実行される機会を与えます。これにより、ビジーループによるCPUの無駄な消費を抑えつつ、ロックが解放されるのを待つことができます。
    *   **ロック解放**: `runtime·unlock(&prof.lock)`の代わりに、`runtime·atomicstore(&prof.lock, 0)`が使用されました。
        *   `runtime·atomicstore(&prof.lock, 0)`は、`prof.lock`の値をアトミックに`0`に設定します。これにより、ロックが安全かつ不可分に解放されます。
3.  **`setcpuprofilerate`のデッドロック回避**: 以前は`setcpuprofilerate`がロックを取得する前にシグナルをオフにする必要がありましたが、CASループはシグナルハンドラと`setcpuprofilerate`の両方から安全にアクセスできるため、この複雑な調整が不要になりました。シグナルハンドラはシグナルスタック上で実行されるため、`Mutex`のような複雑な同期プリミティブを使用すると問題が発生する可能性がありましたが、CASはより低レベルでアトミックな操作であるため、このコンテキストでも安全に機能します。
4.  **パフォーマンスへの影響**: コミットメッセージにもあるように、`setcpuprofilerate`は頻繁に呼び出される関数ではないため、CASループによるビジーループ（`runtime·osyield()`があるため厳密にはビジーループではないが、スピンロックに近い）でもパフォーマンス上の大きな問題は発生しません。`futex`やセマフォのようなより複雑なカーネルレベルの同期メカニズムを使用するよりも、シンプルでオーバーヘッドの少ないCASが選択されました。

この変更により、CPUプロファイリングの同期メカニズムがより堅牢になり、シグナルハンドラとプロファイルレート設定関数間の競合状態が安全に解決されました。

## コアとなるコードの解説

上記の差分は、`prof`構造体の`lock`フィールドの型変更と、その`lock`フィールドを使用する`runtime·sigprof`および`runtime·setcpuprofilerate_m`関数の同期ロジックの変更を示しています。

1.  **`prof`構造体の変更**:
    ```diff
    -	Mutex lock;
    +	uint32 lock;
    ```
    `prof`構造体内の`lock`フィールドの型が`Mutex`から`uint32`に変更されました。これにより、`Mutex`の複雑な内部実装（特に`onM`コンテキストへの依存）を回避し、より低レベルなアトミック操作で同期を制御できるようになります。`uint32`型の`lock`は、`0`がロックされていない状態、`1`がロックされている状態を表すフラグとして機能します。

2.  **`runtime·sigprof`関数の変更**:
    ```diff
    -		runtime·lock(&prof.lock);
    +		// Simple cas-lock to coordinate with setcpuprofilerate.
    +		while(!runtime·cas(&prof.lock, 0, 1))
    +			runtime·osyield();
    		if(prof.hz != 0)
    			runtime·cpuproftick(stk, n);
    -		runtime·unlock(&prof.lock);
    +		runtime·atomicstore(&prof.lock, 0);
    ```
    `runtime·sigprof`は`SIGPROF`シグナルハンドラです。
    *   `runtime·lock(&prof.lock)`の呼び出しが削除され、代わりにCASループが導入されました。`while(!runtime·cas(&prof.lock, 0, 1))`は、`prof.lock`が`0`（アンロック状態）になるまで`runtime·cas`を繰り返し試行し、`0`であれば`1`に設定してロックを取得します。
    *   `runtime·osyield()`は、CAS操作が失敗した場合（つまり、他のスレッドがロックを保持している場合）に、現在のOSスレッドの実行を一時停止し、OSスケジューラに制御を戻します。これにより、CPUを無駄に消費するビジーループを避け、他のスレッドが実行される機会を与えます。
    *   `runtime·unlock(&prof.lock)`の呼び出しが削除され、代わりに`runtime·atomicstore(&prof.lock, 0)`が使用されました。これは、`prof.lock`の値をアトミックに`0`に設定し、ロックを安全に解放します。

3.  **`runtime·setcpuprofilerate_m`関数の変更**:
    ```diff
    -	runtime·lock(&prof.lock);
    +	while(!runtime·cas(&prof.lock, 0, 1))
    +		runtime·osyield();
     	prof.hz = hz;
    -	runtime·unlock(&prof.lock);
    +	runtime·atomicstore(&prof.lock, 0);
    ```
    `runtime·setcpuprofilerate_m`はCPUプロファイリングのレートを設定する関数です。
    *   ここでも`runtime·lock(&prof.lock)`がCASループに置き換えられ、`runtime·unlock(&prof.lock)`が`runtime·atomicstore(&prof.lock, 0)`に置き換えられました。
    *   これにより、`runtime·sigprof`と同様に、`setcpuprofilerate_m`もCASベースの同期メカニズムを使用するようになり、`Mutex`使用時のデッドロックの可能性やシグナルスタック上での問題を回避します。

これらの変更により、`prof`構造体へのアクセスは、`Mutex`のような高レベルな同期プリミティブではなく、より低レベルでシグナルセーフなアトミック操作（CASとアトミックストア）によって調整されるようになりました。これにより、シグナルハンドラとプロファイルレート設定関数間の同期がより堅牢かつシンプルになります。

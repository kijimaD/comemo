## 変更の背景

このコミットの主な背景は、Go言語で開発されたアプリケーションがAndroidプラットフォーム向けにビルドできなくなっていた問題の解決です。具体的には、Goランタイムの重要なシンボルである `runtime.tlsg` の型が、Android環境 (`GOOS=android`) でリンカによって正しく認識されないためにビルドエラーが発生していました。

問題の根源は、GoランタイムのARMアーキテクチャ向けTLS（Thread Local Storage）実装ファイルである `runtime/tls_arm.s` において、`runtime.tlsg` が `SNOPTRBSS` (Static No-Pointer BSS) 型として定義されていたことにあります。しかし、Goリンカ (`cmd/ld`) は、この `runtime.tlsg` シンボルが `STLSBSS` (Static Thread Local Storage BSS) 型であることを期待していました。この型定義の不一致が、リンカがシンボルを正しく処理できない原因となっていました。

この問題は、以前のコミット `d738c6b0cad` によって導入されたリンカのロジック変更に起因します。その変更では、`tlsg->type` が既に設定されている場合には `STLSBSS` への上書きを行わないという条件が追加されました。Androidの場合、`runtime/tls_arm.s` で `SNOPTRBSS` として型が設定されていたため、この条件によって `STLSBSS` への変更がスキップされ、結果としてリンカが期待する型と異なる状態のまま処理が進んでしまい、ビルドが失敗していました。

このコミットは、Android向けビルドの機能を回復させることを目的としています。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下のGo言語の内部動作に関する知識が必要です。

1.  **GoのTLS (Thread Local Storage)**:
    *   TLSは、各スレッド（またはGoランタイムの文脈ではゴルーチン）が独立したデータを持つためのメカニズムです。Goランタイムでは、ゴルーチンの状態（`g` 構造体など）を管理するためにTLSが利用されます。特に、C言語のコードと相互作用する際に、Goのゴルーチン状態を保持するために `runtime.tlsg` のようなTLS変数が使用されます。
    *   `runtime.tlsg` は、現在のゴルーチン (`g`) 構造体へのポインタを格納するために使用される、Goランタイム内部の特殊な変数です。

2.  **Goのリンカ (`cmd/ld`)**:
    *   Go言語のビルドプロセスにおいて、リンカ (`cmd/ld`) は非常に重要な役割を担います。コンパイラによって生成されたオブジェクトファイルやアーカイブファイル、そして必要なライブラリ（Goランタイムを含む）を結合し、最終的な実行可能バイナリを生成します。
    *   リンカは、プログラム内のすべてのシンボル（変数、関数など）を解決し、それらをメモリ上の適切なセクションに配置します。この際、シンボルの型情報（例: `STLSBSS`, `SNOPTRBSS`）がリンカの動作に影響を与えます。

3.  **シンボルタイプ (`STLSBSS`, `SNOPTRBSS`)**:
    *   Goリンカは、シンボルをその特性に基づいて様々な型に分類します。
    *   **`STLSBSS` (Static Thread Local Storage BSS)**: これは、TLSセグメントのBSS（Block Started by Symbol）セクションに配置される静的変数を示すシンボルタイプです。BSSセクションは、初期化されていない静的変数やグローバル変数を格納するために使用され、プログラムの起動時にゼロで初期化されます。`STLSBSS` は、特にTLSに格納される変数がこのカテゴリに属することを示します。
    *   **`SNOPTRBSS` (Static No-Pointer BSS)**: これは、ポインタを含まない静的変数やグローバル変数が配置されるBSSセクションを示すシンボルタイプです。この型は、Goのガベージコレクタ (GC) にとって非常に重要です。`SNOPTRBSS` としてマークされたメモリ領域はポインタを含まないことが保証されるため、GCがその領域をスキャンする必要がなくなり、GCの効率が向上します。

4.  **`GOOS=android`**:
    *   Go言語のクロスコンパイル機能により、`GOOS` 環境変数を設定することで、異なるオペレーティングシステム向けのバイナリを生成できます。`GOOS=android` は、Androidプラットフォーム向けのビルドを指定します。Android環境は、その特殊なシステムライブラリやリンカの挙動により、他のプラットフォームとは異なる考慮が必要となる場合があります。

## 技術的詳細

このコミットが解決する技術的な問題は、Goリンカが `runtime.tlsg` シンボルを処理する際の型の一貫性の欠如にあります。

Goランタイムは、`runtime.tlsg` をTLSに配置される変数として扱います。歴史的に、Goリンカは `src/cmd/ld/lib.c` 内で `runtime.tlsg` シンボルを検索し、その型を明示的に `STLSBSS` に設定していました。これは、`runtime.tlsg` がTLSセグメントのBSS領域に属する静的変数であることをリンカに伝えるためです。

しかし、以前のコミット `d738c6b0cad` では、この型設定ロジックに条件が追加されました。具体的には、`tlsg->type` が既に `0` でない場合（つまり、ランタイム側で既に型が設定されている場合）には、リンカが `STLSBSS` を上書きしないという変更です。

Android向けのARMアーキテクチャの場合、`runtime/tls_arm.s` というアセンブリファイル内で `runtime.tlsg` が `SNOPTRBSS` 型として定義されていました。`SNOPTRBSS` は `0` ではない有効な型であるため、`d738c6b0cad` で導入された条件 `if(tlsg->type == 0)` は `false` となり、リンカは `runtime.tlsg` の型を `STLSBSS` に変更しませんでした。

結果として、リンカは `runtime.tlsg` を `SNOPTRBSS` 型として処理しようとしましたが、リンカの他の部分やAndroidビルドの特定の要件が `STLSBSS` 型を期待していたため、型不一致によるビルドエラーが発生しました。

このコミットの修正は、この条件を緩和することで、ほとんどのプラットフォーム（Androidを含む）で `runtime.tlsg` が常に `STLSBSS` 型としてマークされるようにします。ただし、`darwin/arm` (macOS/iOSのARMアーキテクチャ) は例外として扱われます。これは、`darwin/arm` ではランタイムが提供する `SNOPTRBSS` 型をそのまま使用することが期待されており、リンカ側で `STLSBSS` に変更する必要がないためです。コミットメッセージの `TODO` コメントは、将来的にはAndroidも `darwin/arm` と同様にランタイムが提供する `SNOPTRBSS` をそのまま利用できるべきだが、現状ではリンカの他の部分が `STLSBSS` を期待しているという、より深い問題を示唆しています。

## コアとなるコードの解説

変更の中心は、`runtime.tlsg` シンボルの型を `STLSBSS` に設定する条件文の修正です。

**変更前:**

```c
	if(tlsg->type == 0)
		tlsg->type = STLSBSS;
```

この条件文は、「もし `tlsg` シンボルの型がまだ設定されていない（`0` である）ならば、`STLSBSS` に設定する」という意味でした。前述の通り、AndroidのARM環境では `runtime/tls_arm.s` で `tlsg` が `SNOPTRBSS` として定義されていたため、`tlsg->type` は `0` ではなく、この `if` 文の条件が偽となり、`STLSBSS` への設定がスキップされていました。

**変更後:**

```c
	if (!(strcmp(goos, "darwin") == 0 && thearch.thechar == '5'))
		tlsg->type = STLSBSS;
```

この新しい条件文は、「もし現在のOSが `darwin` (macOS/iOS) でなく、かつアーキテクチャがARM (`thearch.thechar == '5'`) でないならば、`tlsg` の型を `STLSBSS` に設定する」という意味になります。

*   `strcmp(goos, "darwin") == 0`: 現在のOSが `darwin` であるかをチェックします。
*   `thearch.thechar == '5'`: 現在のアーキテクチャがARMであるかをチェックします（GoリンカではARMを `'5'` で表すことがあります）。
*   `!(...)`: 上記の条件の否定を取ります。

つまり、この変更により、`darwin/arm` 以外のすべてのプラットフォームにおいて、`runtime.tlsg` の型が強制的に `STLSBSS` に設定されるようになりました。これにより、Android環境でも `runtime.tlsg` がリンカの期待する `STLSBSS` 型として正しく処理され、ビルドエラーが解消されました。

`darwin/arm` が例外として扱われるのは、そのプラットフォームでは `runtime.tlsg` がランタイム側で `SNOPTRBSS` として定義されていることをリンカがそのまま受け入れることができ、`STLSBSS` への変更が不要であるためです。コミットメッセージの `TODO` コメントは、Androidも将来的には同様の挙動を目指すべきだが、現状ではリンカの他の部分が `STLSBSS` を期待しているという課題が残っていることを示しています。

このコミットの修正は、この条件を緩和することで、ほとんどのプラットフォーム（Androidを含む）で `runtime.tlsg` が常に `STLSBSS` 型としてマークされるようにします。ただし、`darwin/arm` (macOS/iOSのARMアーキテクチャ) は例外として扱われます。これは、`darwin/arm` ではランタイムが提供する `SNOPTRBSS` 型をそのまま使用することが期待されており、リンカ側で `STLSBSS` に変更する必要がないためです。コミットメッセージの `TODO` コメントは、将来的にはAndroidも `darwin/arm` と同様にランタイムが提供する `SNOPTRBSS` をそのまま利用できるべきだが、現状ではリンカの他の部分が `STLSBSS` を期待しているという課題が残っていることを示唆しています。

## コアとなるコードの変更箇所

## コアとなるコードの解説

変更の中心は、`runtime.tlsg` シンボルの型を `STLSBSS` に設定する条件文の修正です。

**変更前:**

```c
	if(tlsg->type == 0)
		tlsg->type = STLSBSS;
```

この条件文は、「もし `tlsg` シンボルの型がまだ設定されていない（`0` である）ならば、`STLSBSS` に設定する」という意味でした。前述の通り、AndroidのARM環境では `runtime/tls_arm.s` で `tlsg` が `SNOPTRBSS` として定義されていたため、`tlsg->type` は `0` ではなく、この `if` 文の条件が偽となり、`STLSBSS` への設定がスキップされていました。

**変更後:**

```c
	if (!(strcmp(goos, "darwin") == 0 && thearch.thechar == '5'))
		tlsg->type = STLSBSS;
```

この新しい条件文は、「もし現在のOSが `darwin` (macOS/iOS) でなく、かつアーキテクチャがARM (`thearch.thechar == '5'`) でないならば、`tlsg` の型を `STLSBSS` に設定する」という意味になります。

*   `strcmp(goos, "darwin") == 0`: 現在のOSが `darwin` であるかをチェックします。
*   `thearch.thechar == '5'`: 現在のアーキテクチャがARMであるかをチェックします（GoリンカではARMを `'5'` で表すことがあります）。
*   `!(...)`: 上記の条件の否定を取ります。

つまり、この変更により、`darwin/arm` 以外のすべてのプラットフォームにおいて、`runtime.tlsg` の型が強制的に `STLSBSS` に設定されるようになりました。これにより、Android環境でも `runtime.tlsg` がリンカの期待する `STLSBSS` 型として正しく処理され、ビルドエラーが解消されました。

`darwin/arm` が例外として扱われるのは、そのプラットフォームでは `runtime.tlsg` がランタイム側で `SNOPTRBSS` として定義されていることをリンカがそのまま受け入れることができ、`STLSBSS` への変更が不要であるためです。コミットメッセージの `TODO` コメントは、Androidも将来的には同様の挙動を目指すべきだが、現状ではリンカの他の部分が `STLSBSS` を期待しているという課題が残っていることを示しています。

# [インデックス 24049] ファイルの概要

このコミットは、Goコンパイラのバックエンドの一部である `src/cmd/compile/internal/gc/obj.go` ファイルに対する変更です。`obj.go` は、Goコンパイラが生成するオブジェクトファイル内のシンボル（変数、関数、型など）の定義と配置を管理する役割を担っています。特に、文字列リテラルがどのようにオブジェクトファイルに表現され、リンカによって処理されるかに影響を与える部分です。

## コミット

`cmd/compile`: リンカが不要な文字列ヘッダを削除できるようにする

## 変更の背景

このコミットの主な背景は、Goプログラムのバイナリサイズ、特に大量の文字列リテラルを含む場合のバイナリサイズの肥大化問題に対処することでした。コミットメッセージに記載されているように、100,000個の文字列スライスを含む単純なファイルをコンパイルした場合、バイナリサイズが約5.9MBから約3.5MBへと大幅に削減されています。これは、約2.4MBの削減であり、文字列データそのもののサイズにほぼ相当します。

Go言語では、文字列は内部的にポインタと長さのペアとして表現されます。コンパイラは、各文字列リテラルに対して、その文字列データ（バイト列）と、そのデータへのポインタおよび長さを格納する「文字列ヘッダ」を生成します。以前の実装では、これらの文字列ヘッダと文字列データが単一のシンボルとして扱われていました。

問題は、リンカが不要なコードやデータを削除する際に、文字列ヘッダと文字列データが密接に結合しているため、たとえ文字列ヘッダがプログラムのどこからも参照されていない場合でも、リンカがそれを削除できない可能性があったことです。特に、文字列データ自体は参照されているが、その文字列ヘッダが直接参照されていないようなケースで、リンカはヘッダを削除する機会を失っていました。これにより、特に多くの文字列リテラルを持つプログラムにおいて、最終的なバイナリサイズが不必要に大きくなるという問題が発生していました。

このコミットは、この非効率性を解消し、リンカがより積極的に不要な文字列ヘッダを削除できるようにすることで、バイナリサイズの削減を目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラとリンカに関する前提知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**:
    *   Goソースコードを中間表現（ASTなど）に変換し、最終的にアセンブリコードやオブジェクトファイルを生成するツールです。
    *   `src/cmd/compile/internal/gc` は、Goコンパイラの主要な部分であり、型チェック、コード生成、最適化などを行います。
    *   `obj.go` は、オブジェクトファイルに書き込まれるシンボル（データやコードの塊）の生成と管理を担当します。

2.  **Goリンカ (`cmd/link`)**:
    *   コンパイラによって生成された複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するツールです。
    *   リンカの重要な機能の一つに「デッドコードエリミネーション（Dead Code Elimination）」があります。これは、プログラムの実行に不要なコードやデータを最終的なバイナリから削除することで、ファイルサイズを削減し、起動時間を短縮する最適化です。

3.  **Goにおける文字列の内部表現**:
    *   Goの文字列は、読み取り専用のバイトスライスであり、内部的には `struct StringHeader { Data uintptr; Len int }` のような構造体として表現されます。`Data` は文字列のバイトデータへのポインタ、`Len` は文字列の長さを表します。
    *   コンパイラは、ソースコード中の文字列リテラルに対して、この `StringHeader` に対応するデータ（文字列ヘッダ）と、実際の文字列のバイトデータ（文字列データ）を生成します。

4.  **シンボル (`*Sym`)**:
    *   コンパイラやリンカがコードやデータを識別するために使用する名前付きのエントリです。変数、関数、型、文字列リテラルなどがシンボルとして扱われます。
    *   各シンボルは、その種類、サイズ、メモリ上の配置、属性（読み取り専用データ、グローバルなど）などの情報を持っています。
    *   `Pkglookup` は、指定された名前とパッケージに基づいてシンボルを検索または作成する関数です。
    *   `SymUniq` フラグは、そのシンボルが既に一意に生成されていることを示すために使用されます。これにより、同じ内容のシンボルが複数回生成されるのを防ぎます。
    *   `ggloblsym` は、シンボルをグローバルシンボルとして定義し、そのサイズと属性（例: `obj.DUPOK` (重複を許可), `obj.RODATA` (読み取り専用データ), `obj.LOCAL` (ローカルシンボル)) を指定します。

5.  **リンカによる最適化**:
    *   リンカは、プログラムの実行に直接的または間接的に参照されていないシンボルを削除しようとします。しかし、シンボルが複数の論理的な部分（例: ヘッダとデータ）から構成されている場合、それらが単一のシンボルとして扱われると、一部が不要であっても全体が削除されないことがあります。

## 技術的詳細

このコミットの核心は、Goコンパイラが文字列リテラルをオブジェクトファイルに表現する方法を変更し、文字列の「ヘッダ」と「データ」をリンカが独立して扱えるようにした点にあります。

以前は、`stringsym` 関数は文字列ヘッダと文字列データをまとめて一つのシンボルとして生成していました。このため、リンカが文字列ヘッダが不要であると判断しても、文字列データが参照されている限り、ヘッダ部分も削除されずに残ってしまう可能性がありました。

変更後、`stringsym` 関数は、文字列ヘッダ用のシンボル (`symhdr`) と文字列データ用のシンボル (`symdata`) の二つを生成して返すようになりました。

1.  **文字列ヘッダシンボル (`symhdr`)**:
    *   このシンボルは、文字列データへのポインタと文字列の長さを格納します。
    *   `dsymptr(symhdr, off, symdata, 0)`: `symhdr` の中に `symdata` へのポインタを埋め込みます。これにより、文字列ヘッダが文字列データを指すようになります。
    *   `duintxx(symhdr, off, uint64(len(s)), Widthint)`: 文字列の長さを埋め込みます。
    *   `ggloblsym(symhdr, int32(off), obj.DUPOK|obj.RODATA|obj.LOCAL)`: `symhdr` をグローバルシンボルとして定義します。

2.  **文字列データシンボル (`symdata`)**:
    *   このシンボルは、実際の文字列のバイトデータを格納します。
    *   `dsname(symdata, off, s[n:n+m])`: 文字列のバイトデータを `symdata` に書き込みます。
    *   `duint8(symdata, off, 0)`: 実行時（runtime）のための終端NULバイトを追加します。
    *   `ggloblsym(symdata, int32(off), obj.DUPOK|obj.RODATA|obj.LOCAL)`: `symdata` をグローバルシンボルとして定義します。

このように、文字列ヘッダと文字列データが別々のシンボルとして定義されることで、リンカはそれぞれのシンボルの参照状況を独立して追跡できるようになります。もしプログラムのどこからも特定の文字列ヘッダが参照されていない場合、リンカはそのヘッダシンボルを安全に削除できます。しかし、文字列データ自体が（例えば、別の文字列スライスの一部として）参照されている場合は、データシンボルは保持されます。

`Datastring` 関数と `datagostring` 関数も、この新しい `stringsym` の戻り値に合わせて変更されました。
*   `Datastring` は、文字列データへの参照が必要な場合に `symdata` を使用するように変更されました。以前はヘッダをスキップするためにオフセットを調整していましたが、`symdata` を直接参照することでオフセットは `0` になりました。
*   `datagostring` は、完全な文字列（ヘッダとデータ）への参照が必要な場合に `symhdr` を使用するように変更されました。

この変更により、リンカはよりきめ細かく不要な文字列ヘッダを削除できるようになり、結果としてバイナリサイズの大幅な削減が実現されました。

## コアとなるコードの変更箇所

変更は `src/cmd/compile/internal/gc/obj.go` ファイルに集中しています。

1.  `stringsym` 関数のシグネチャ変更:
    ```diff

    +func stringsym(s string) (hdr, data *Sym) {
    ```

    *   `symhdr` と `symdata` の2つのシンボルを生成。

    *   文字列ヘッダのデータ定義を `symhdr` に対して行う。
    *   文字列データのデータ定義を `symdata` に対して行う。

## コアとなるコードの解説

### `stringsym` 関数の変更

最も重要な変更は `stringsym` 関数のシグネチャと内部ロジックです。

```go
// 変更前
// func stringsym(s string) *Sym {
//     // ... シンボル 'sym' を生成し、ヘッダとデータをまとめて定義 ...
//     return sym
// }

// 変更後
func stringsym(s string) (hdr, data *Sym) {
    // ...
    symhdr := Pkglookup("hdr."+symname, pkg) // ヘッダ用シンボル
    symdata := Pkglookup(symname, pkg)       // データ用シンボル

    // symhdr の定義
    if symhdr.Flags&SymUniq == 0 {
        symhdr.Flags |= SymUniq
        symhdr.Def = newname(symhdr)
        off := 0
        off = dsymptr(symhdr, off, symdata, 0) // symdata へのポインタ
        off = duintxx(symhdr, off, uint64(len(s)), Widthint) // 長さ
        ggloblsym(symhdr, int32(off), obj.DUPOK|obj.RODATA|obj.LOCAL)
    }

    // symdata の定義
    if symdata.Flags&SymUniq == 0 {
        symdata.Flags |= SymUniq
        symdata.Def = newname(symdata)
        off := 0
        // 文字列バイトデータを symdata に書き込む
        for n := 0; n < len(s); n += m {
            m = 8
            if m > len(s)-n {
                m = len(s) - n
            }
            off = dsname(symdata, off, s[n:n+m])
        }
        off = duint8(symdata, off, 0) // 終端NUL
        off = (off + Widthptr - 1) &^ (Widthptr - 1) // ポインタアラインメント
        ggloblsym(symdata, int32(off), obj.DUPOK|obj.RODATA|obj.LOCAL)
    }

    return symhdr, symdata
}
```

この変更により、`stringsym` は文字列ヘッダと文字列データをそれぞれ独立したシンボルとしてコンパイラに登録します。`symhdr` は `symdata` への参照を持つため、両者は関連付けられていますが、リンカはそれぞれのシンボルがプログラムの他の部分から参照されているかどうかを個別に判断できるようになります。

### `Datastring` および `datagostring` 関数の変更

これらの関数は、コンパイラが文字列リテラルをコード内で参照する際に使用されます。

*   `Datastring` は、文字列のバイトデータそのものへの参照が必要な場合（例: `[]byte` への変換など）に呼び出されます。変更後は `stringsym` から返される `symdata` を直接使用し、オフセットを `0` に設定することで、文字列データの先頭を指すようにします。
*   `datagostring` は、Goの `string` 型として文字列リテラルを参照する場合に呼び出されます。変更後は `stringsym` から返される `symhdr` を使用し、オフセットを `0` に設定することで、文字列ヘッダの先頭を指すようにします。

これらの変更により、コンパイラは文字列のヘッダとデータを必要に応じて個別のシンボルとして参照できるようになり、リンカの最適化の機会を最大化します。

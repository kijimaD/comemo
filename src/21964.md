## 元コミット内容

`doc/asm`: アセンブリ関数は短い名前を使用する必要があることを文書化。

例: Goプロトタイプから自動スタックマップが適用されるようにするためには、`package·Name`ではなく`·Name`を使用します。

根本的な理由は、`liblink`がGoプロトタイプから来るスタックマップのために、サフィックス`.args_stackmap`を持つ名前を検索するが、この段階ではすべてのGo関数は`""·Name`という名前になっているためです。したがって、`package·Name`という名前のアセンブリ関数は、`""·package·Name.args_stackmap`という名前のスタックマップを見つけることができません。

おそらく`cmd/vet`はこの件について警告を出すべきでしょう。

## 変更の背景

このコミットは、Goのアセンブリ言語で書かれた関数が、Goのプロトタイプ（Go言語で定義された対応する関数シグネチャ）から自動的にスタックマップ情報を継承するための命名規則に関する重要なドキュメントの追加です。

Goのランタイムとガベージコレクタは、スタック上のポインタのレイアウトを正確に把握するために「スタックマップ」というメタデータを使用します。これにより、ガベージコレクタはどのスタック上の値がポインタであり、スキャンする必要があるかを正確に判断できます。アセンブリ関数がGoの関数と連携する場合、このスタックマップ情報が正しく適用されることが不可欠です。

コミットメッセージが示唆するように、以前はアセンブリ関数が`package·Name`という形式で命名されていると、`liblink`（Goリンカ）がGoプロトタイプから生成されたスタックマップ情報を見つけられないという問題がありました。`liblink`はスタックマップ情報を検索する際に、Go関数が内部的に持つ`""·Name`という形式の名前と、それに付加される`.args_stackmap`サフィックスを使用します。しかし、アセンブリ関数が`package·Name`という形式で定義されていると、`liblink`が期待する`""·package·Name.args_stackmap`という名前と一致せず、結果としてスタックマップが適用されませんでした。

この問題は、アセンブリ関数がポインタを扱う場合に、ガベージコレクタが正しく動作しない可能性を示唆していました。そのため、アセンブリ関数の命名規則を明確にし、Goプロトタイプとの連携を保証することが必要とされました。このコミットは、その解決策として、アセンブリ関数にはパッケージ名を含まない短い形式（`·Name`）を使用すべきであることを公式ドキュメントに明記するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部動作に関する知識が必要です。

1.  **Goアセンブリ (Go Assembly)**:
    Go言語は、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある場合に、アセンブリ言語で関数を記述することをサポートしています。Goのアセンブリは、一般的なアセンブリ言語とは異なり、Goツールチェーン（特に`cmd/asm`）によって処理される独自の構文を持っています。Goアセンブリ関数は、Goのソースファイル内で対応するGoの関数プロトタイプを持つことが一般的です。

2.  **スタックマップ (Stack Map)**:
    Goのガベージコレクタは、正確なガベージコレクション（GC）のために、スタック上のポインタの位置を正確に知る必要があります。スタックマップは、各関数のスタックフレーム内で、どのオフセットにポインタが存在するかを示すビットマップのようなメタデータです。これにより、GCはスタックをスキャンする際に、ポインタではない値を誤って参照したり、ポインタである値を見落としたりすることを防ぎます。Goコンパイラは、Go言語で書かれた関数に対してこのスタックマップを自動的に生成します。アセンブリ関数では、通常、`FUNCDATA`や`PCDATA`といった擬似命令を使って手動でこの情報を提供する必要がありますが、Goプロトタイプを持つ場合は自動適用される仕組みがあります。

3.  **`liblink` (Go Linker)**:
    `liblink`はGoのリンカであり、コンパイルされたオブジェクトファイル（Goソースコードから生成されたものとアセンブリソースコードから生成されたもの）を結合して実行可能ファイルを生成する役割を担っています。このプロセスの中で、`liblink`は関数間の参照を解決し、ランタイムに必要なメタデータ（スタックマップなど）を適切に配置します。スタックマップの適用においては、`liblink`が特定の命名規則に基づいてGoプロトタイプとアセンブリ関数を関連付けます。

4.  **Go関数の命名規則とシンボル名**:
    Goの内部では、関数やシンボルは特定の命名規則に従って表現されます。
    *   Goのソースコードで定義された関数は、コンパイル時に内部的に`""·FunctionName`という形式のシンボル名を持ちます。ここで`""`は現在のパッケージ名を表し、リンカが最終的なパッケージ名に置き換えます。
    *   アセンブリ関数も`TEXT`ディレクティブを使って定義されますが、その名前の指定方法が重要になります。Goのシンボル名では、パッケージ名と関数名の区切りに中点（`·`、U+00B7）が使用されます。例えば、`fmt`パッケージの`Printf`関数は`fmt·Printf`となります。

5.  **`.args_stackmap`サフィックス**:
    GoのコンパイラがGoプロトタイプからスタックマップ情報を生成する際、その情報は通常、対応する関数シンボル名に`.args_stackmap`というサフィックスが付加された形でリンカに提供されます。例えば、`""·MyGoFunc`というGo関数プロトタイプに対応するスタックマップは、`""·MyGoFunc.args_stackmap`という名前で参照されます。

これらの知識が、アセンブリ関数の命名がなぜスタックマップの自動適用に影響を与えるのかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的な核心は、Goのリンカである`liblink`がスタックマップ情報をどのように検索し、アセンブリ関数の命名がその検索プロセスにどのように影響するかという点にあります。

Goのコンパイラは、Go言語で書かれた関数（Goプロトタイプ）のスタックフレームに関するポインタ情報を抽出し、これをスタックマップとして生成します。このスタックマップは、対応するGo関数のシンボル名に`.args_stackmap`というサフィックスを付加した形でリンカに提供されます。例えば、`main`パッケージの`MyFunc`というGo関数があれば、そのスタックマップは内部的に`""·MyFunc.args_stackmap`という名前で参照されます（`""`はリンカによって実際のパッケージ名に解決されます）。

アセンブリ関数がGoプロトタイプを持つ場合、`liblink`はアセンブリ関数のシンボル名に対応するスタックマップ情報を検索し、それをアセンブリ関数に適用しようとします。ここで問題となるのが、アセンブリ関数の命名規則です。

*   **Goプロトタイプからのスタックマップの期待される名前**: `liblink`は、Goプロトタイプから生成されたスタックマップを、`""·FunctionName.args_stackmap`という形式の名前で検索します。ここで`FunctionName`はGoプロトタイプの関数名です。

*   **アセンブリ関数の命名**:
    *   もしアセンブリ関数が`TEXT ·FunctionName(SB), $framesize`のように、パッケージ名を含まない「短い名前」（`·FunctionName`）で定義されている場合、`liblink`はGoプロトタイプとアセンブリ関数の名前が一致すると判断し、`""·FunctionName.args_stackmap`という名前のスタックマップを正しく見つけることができます。
    *   しかし、もしアセンブリ関数が`TEXT package·FunctionName(SB), $framesize`のように、明示的にパッケージ名を含む「長い名前」（`package·FunctionName`）で定義されている場合、`liblink`はアセンブリ関数の名前を`package·FunctionName`と認識します。この場合、`liblink`がGoプロトタイプから期待するスタックマップの名前は`""·package·FunctionName.args_stackmap`となりますが、実際のGoプロトタイプから生成されるスタックマップは`""·FunctionName.args_stackmap`であるため、名前が一致せず、スタックマップを見つけることができません。

この不一致が、アセンブリ関数にGoプロトタイプからの自動スタックマップが適用されない根本的な原因でした。このコミットは、この技術的な詳細を`doc/asm.html`に明記することで、開発者が正しい命名規則に従い、ガベージコレクションの正確性を保証できるようにすることを目的としています。

## コアとなるコードの解説

このコミットによるコードの変更は、`doc/asm.html`というGoのアセンブリ言語に関する公式ドキュメントの更新です。具体的には、アセンブリ関数の命名規則に関する説明が追加されています。

変更前のドキュメントでは、ポインタ結果がなく、ローカルスタックフレームがないか関数呼び出しがないアセンブリ関数について、同じパッケージ内のGoソースファイルにGoプロトタイプを定義することが唯一の要件であると述べていました。

変更後、以下の重要な文が追加されました。

> The name of the assembly function must not contain the package name component (for example, function `Syscall` in package `syscall` should use the name `·Syscall` instead of the equivalent name `syscall·Syscall` in its `TEXT` directive).

これは、アセンブリ関数の名前がパッケージ名コンポーネントを含んではならないことを明確に指示しています。例として、`syscall`パッケージの`Syscall`関数を挙げており、`TEXT`ディレクティブでは`syscall·Syscall`ではなく`·Syscall`を使用すべきだと具体的に示しています。

この変更は、前述の「変更の背景」と「技術的詳細」で説明した、`liblink`がGoプロトタイプから生成されたスタックマップ情報を正しく見つけるための命名規則の要件を、公式ドキュメントとして明文化したものです。これにより、Goのアセンブリコードを書く開発者が、ガベージコレクションの正確性を損なうことなく、Goプロトタイプとの連携を正しく行えるようになります。

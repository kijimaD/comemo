# [インデックス 27840] ファイルの概要

このコミットは、Goコンパイラのバイナリ形式のエクスポートデータに、ソースコードの位置情報（ファイル名と行番号）を含めるための最初の実装を導入します。これにより、デバッグ情報やツールがより正確なソースコード参照を提供できるようになります。また、エクスポートデータの効率性を高めるために、文字列の正規化（canonicalization）と行番号のデルタエンコーディングが導入されています。

## 変更の背景

Goコンパイラは、パッケージの型情報やエクスポートされたシンボルなどのメタデータを、他のパッケージがインポートできるようにエクスポートデータとして出力します。このエクスポートデータは、以前はテキスト形式でしたが、パフォーマンスとサイズの最適化のためにバイナリ形式に移行しました。

このコミットの主な背景は、Goのツールチェイン（デバッガ、プロファイラ、コード分析ツールなど）が、コンパイルされたコード内の要素（変数、関数、型など）がソースコードのどの位置（ファイル名と行番号）で定義されているかを知る必要性が高まったことです。以前のバイナリ形式のエクスポートデータには、この詳細な位置情報が含まれていませんでした。

位置情報を含めることで、エクスポートデータのサイズが増加する可能性があります。そのため、このコミットでは、サイズ増加を最小限に抑えるための効率的なエンコーディング手法（デルタエンコーディングと文字列の正規化）も同時に導入されています。コミットメッセージの統計情報が示すように、位置情報を追加しても、以前のテキスト形式と比較して大幅なサイズ削減が維持されており、直前のバイナリ形式と比較しても全体で14%の増加に留まっています。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する知識が役立ちます。

1.  **Goコンパイラのエクスポートデータ (Export Data)**:
    Goコンパイラは、パッケージをコンパイルする際に、そのパッケージが外部に公開する（エクスポートする）情報（型定義、関数シグネチャ、変数宣言など）を特殊な形式でファイルに保存します。これをエクスポートデータと呼びます。他のパッケージがこのパッケージをインポートする際、コンパイラはこのエクスポートデータを読み込み、型チェックやシンボル解決を行います。Go 1.5以降、このエクスポートデータはバイナリ形式で保存されるようになりました。

2.  **`gcimporter`**:
    `gcimporter`は、Goコンパイラ（`gc`）が生成するバイナリ形式のエクスポートデータを読み込むためのパッケージです。`go/importer`パッケージの一部として提供され、`go/types`パッケージが型情報を構築するために利用します。

3.  **位置情報 (Position Information)**:
    ソースコード内の特定の要素（変数、関数、型、ステートメントなど）が、どのファイルのどの行番号に存在するかを示す情報です。デバッグ、エラー報告、コード分析、IDEの機能（定義へのジャンプなど）において不可欠です。

4.  **デルタエンコーディング (Delta Encoding)**:
    連続するデータの差分（デルタ）を記録することで、データを圧縮する手法です。特に、連続する行番号のように値が徐々に変化する場合に有効です。例えば、行番号が100, 101, 105, 106と続く場合、デルタエンコーディングでは100, +1, +4, +1と記録され、小さな値が多くなるため、可変長整数エンコーディングと組み合わせることで効率的な圧縮が期待できます。

5.  **文字列の正規化 (String Canonicalization)**:
    データ内で繰り返し出現する文字列（特にファイル名や識別子など）を、一度だけ保存し、それ以降はその文字列への参照（インデックス）で置き換える手法です。これにより、冗長なデータの保存を避け、データサイズを削減できます。

6.  **可変長整数エンコーディング (Variable-length Integer Encoding)**:
    整数の値を、その大きさに応じて異なるバイト数でエンコードする手法です。小さな値は少ないバイト数で、大きな値は多くのバイト数で表現されるため、平均的にデータサイズを削減できます。Goコンパイラのエクスポートデータでは、`binary.PutVarint`のような関数が使用されます。

## 技術的詳細

このコミットは、Goコンパイラのバイナリ形式エクスポートデータに位置情報を埋め込むためのメカニズムを導入しています。主要な技術的変更点は以下の通りです。

1.  **位置情報の追加**:
    *   エクスポートされるすべてのグローバル変数、メソッド、フィールドに対して、ソースコード上の位置情報（ファイル名と行番号）が関連付けられるようになりました。
    *   `exporter`構造体に`prevFile`と`prevLine`フィールドが追加され、直前の位置情報を保持することでデルタエンコーディングを可能にしています。
    *   `exporter.pos(n *Node)`という新しいメソッドが追加され、`*Node`から位置情報を抽出し、効率的にエクスポートデータに書き込む役割を担います。

2.  **デルタエンコーディングによる行番号の圧縮**:
    *   `exporter.pos`メソッド内で、現在の行番号と直前の行番号の差分（デルタ）を計算し、そのデルタ値を書き込みます。
    *   ファイル名が同じで、行番号のみが変化する場合（一般的なケース）は、デルタ値のみを書き込むことでデータ量を削減します。
    *   ファイル名が変更された場合、または行番号が変化しない場合は、デルタ値として`0`を書き込み、その後に新しいファイル名と絶対行番号を書き込みます。これにより、ファイル名の変更や、同じ行に複数の要素が定義されているケースにも対応できます。

3.  **文字列の正規化 (Canonicalization)**:
    *   `exporter`構造体に`strIndex map[string]int`が追加され、エクスポートされたすべての文字列（ファイル名、識別子など）を管理します。
    *   文字列が初めてエクスポートされる場合、その文字列自体と、`strIndex`内での新しいインデックスが記録されます。エクスポートデータには、文字列の負の長さ（負の値で文字列自体であることを示す）と文字列のバイト列が書き込まれます。
    *   同じ文字列が再度エクスポートされる場合、文字列自体を書き込む代わりに、`strIndex`に保存されているその文字列のインデックス（非負の値）のみが書き込まれます。
    *   空文字列はインデックス`0`にマッピングされ、特別な扱いを受けます。
    *   これにより、特にファイル名のように繰り返し出現する文字列の冗長な保存が避けられ、エクスポートデータのサイズが大幅に削減されます。

4.  **インポート側の対応**:
    *   `importer`構造体にも`strList []string`、`prevFile`、`prevLine`フィールドが追加され、エクスポートされた位置情報と文字列を正しくデコードできるように対応しています。
    *   `importer.pos()`メソッドが追加され、エクスポートデータからデルタエンコードされた行番号と正規化されたファイル名を読み込み、現在の位置情報を復元します。
    *   `importer.string()`メソッドは、読み込んだ値が負であれば文字列のバイト列を読み込み、正であれば`strList`から既存の文字列をルックアップします。

5.  **データサイズへの影響**:
    *   コミットメッセージの統計によると、位置情報を追加した結果、エクスポートデータの全体サイズは平均で14%増加しました。
    *   しかし、これは以前のテキスト形式のエクスポートデータと比較すると65%の削減を維持しており、直前のバイナリ形式からの14%の減少（このコミット以前の最適化による）を考慮すると、位置情報の追加によるオーバーヘッドは許容範囲内と判断されています。特に、`cmd/addr2line`や`cmd/compile`のような一部のパッケージでは、位置情報の追加によりサイズが大幅に増加していますが、これはこれらのパッケージが多くのシンボルや定義を持つためと考えられます。

`exporter.pos`メソッドは、ノード`n`からファイル名と行番号を取得し、`prevFile`と`prevLine`と比較してデルタエンコーディングを行います。

```go
func (p *exporter) pos(n *Node) {
	var file string
	var line int
	if n != nil {
		file, line = Ctxt.LineHist.FileLine(int(n.Lineno)) // ノードからファイルと行番号を取得
	}

	if file == p.prevFile && line != p.prevLine {
		// 最も一般的なケース: ファイルは同じで、行番号のみが変更された場合
		// デルタエンコードされた行番号を書き込む
		p.int(line - p.prevLine) // != 0
	} else {
		// ファイルが変更されたか、行番号が変更されていない場合
		// デルタ値0を書き込み、その後で新しいファイル名と絶対行番号を書き込む
		p.int(0)
		p.string(file) // ファイル名は正規化されて書き込まれる
		p.int(line)
		p.prevFile = file
	}
	p.prevLine = line
}

```go
func (p *exporter) string(s string) {
	if p.trace {
		p.tracef("%q ", s)
	}
	// 文字列が既にエクスポートされている場合、そのインデックスを書き込む
	if i, ok := p.strIndex[s]; ok {
		p.rawInt64(int64(i))
		return
	}
	// そうでない場合、文字列を記憶し、負の長さとバイト列を書き込む
	p.strIndex[s] = len(p.strIndex) // 新しいインデックスを割り当てる
	p.rawInt64(-int64(len(s)))      // 負の長さで文字列自体であることを示す
	for i := 0; i < len(s); i++ {
		p.rawByte(s[i])
	}
}

	if debugFormat {
		p.marker('s')
	}
	// 読み込んだ値が文字列のインデックス（>= 0）の場合
	i := p.rawInt64()
	if i >= 0 {
		return p.strList[i] // 記憶されている文字列を返す
	}

## 変更の背景

Goコンパイラは、パッケージをコンパイルする際に、そのパッケージが外部に公開する（エクスポートする）情報（型定義、関数シグネチャ、変数宣言など）を特殊な形式でファイルに保存します。これをエクスポートデータと呼びます。他のパッケージがこのパッケージをインポートする際、コンパイラはこのエクスポートデータを読み込み、型チェックやシンボル解決を行います。Go 1.5以降、このエクスポートデータはパフォーマンスとサイズの最適化のためにバイナリ形式に移行しました。

このコミットの主な背景は、Goのツールチェイン（デバッガ、プロファイラ、コード分析ツールなど）が、コンパイルされたコード内の要素（変数、関数、型など）がソースコードのどの位置（ファイル名と行番号）で定義されているかを知る必要性が高まったことです。以前のバイナリ形式のエクスポートデータには、この詳細な位置情報が含まれていませんでした。

位置情報を含めることで、エクスポートデータのサイズが増加する可能性があります。そのため、このコミットでは、サイズ増加を最小限に抑えるための効率的なエンコーディング手法（デルタエンコーディングと文字列の正規化）も同時に導入されています。コミットメッセージの統計情報が示すように、位置情報を追加しても、以前のテキスト形式と比較して大幅なサイズ削減が維持されており、直前のバイナリ形式と比較しても全体で14%の増加に留まっています。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する知識が役立ちます。

1.  **Goコンパイラのエクスポートデータ (Export Data)**:
    Goコンパイラは、パッケージをコンパイルする際に、そのパッケージが外部に公開する（エクスポートする）情報（型定義、関数シグネチャ、変数宣言など）を特殊な形式でファイルに保存します。これをエクスポートデータと呼びます。他のパッケージがこのパッケージをインポートする際、コンパイラはこのエクスポートデータを読み込み、型チェックやシンボル解決を行います。Go 1.5以降、このエクスポートデータはバイナリ形式で保存されるようになりました。

2.  **`gcimporter`**:
    `gcimporter`は、Goコンパイラ（`gc`）が生成するバイナリ形式のエクスポートデータを読み込むためのパッケージです。`go/importer`パッケージの一部として提供され、`go/types`パッケージが型情報を構築するために利用します。

3.  **位置情報 (Position Information)**:
    ソースコード内の特定の要素（変数、関数、型、ステートメントなど）が、どのファイルのどの行番号に存在するかを示す情報です。デバッグ、エラー報告、コード分析、IDEの機能（定義へのジャンプなど）において不可欠です。

4.  **デルタエンコーディング (Delta Encoding)**:
    連続するデータの差分（デルタ）を記録することで、データを圧縮する手法です。特に、連続する行番号のように値が徐々に変化する場合に有効です。例えば、行番号が100, 101, 105, 106と続く場合、デルタエンコーディングでは100, +1, +4, +1と記録され、小さな値が多くなるため、可変長整数エンコーディングと組み合わせることで効率的な圧縮が期待できます。

5.  **文字列の正規化 (String Canonicalization)**:
    データ内で繰り返し出現する文字列（特にファイル名や識別子など）を、一度だけ保存し、それ以降はその文字列への参照（インデックス）で置き換える手法です。これにより、冗長なデータの保存を避け、データサイズを削減できます。

6.  **可変長整数エンコーディング (Variable-length Integer Encoding)**:
    整数の値を、その大きさに応じて異なるバイト数でエンコードする手法です。小さな値は少ないバイト数で、大きな値は多くのバイト数で表現されるため、平均的にデータサイズを削減できます。Goコンパイラのエクスポートデータでは、`binary.PutVarint`のような関数が使用されます。

## 技術的詳細

このコミットは、Goコンパイラのバイナリ形式エクスポートデータに位置情報を埋め込むためのメカニズムを導入しています。主要な技術的変更点は以下の通りです。

1.  **位置情報の追加**:
    *   エクスポートされるすべてのグローバル変数、メソッド、フィールドに対して、ソースコード上の位置情報（ファイル名と行番号）が関連付けられるようになりました。
    *   `exporter`構造体に`prevFile`と`prevLine`フィールドが追加され、直前の位置情報を保持することでデルタエンコーディングを可能にしています。
    *   `exporter.pos(n *Node)`という新しいメソッドが追加され、`*Node`から位置情報を抽出し、効率的にエクスポートデータに書き込む役割を担います。

2.  **デルタエンコーディングによる行番号の圧縮**:
    *   `exporter.pos`メソッド内で、現在の行番号と直前の行番号の差分（デルタ）を計算し、そのデルタ値を書き込みます。
    *   ファイル名が同じで、行番号のみが変化する場合（一般的なケース）は、デルタ値のみを書き込むことでデータ量を削減します。
    *   ファイル名が変更された場合、または行番号が変化しない場合は、デルタ値として`0`を書き込み、その後に新しいファイル名と絶対行番号を書き込みます。これにより、ファイル名の変更や、同じ行に複数の要素が定義されているケースにも対応できます。

3.  **文字列の正規化 (Canonicalization)**:
    *   `exporter`構造体に`strIndex map[string]int`が追加され、エクスポートされたすべての文字列（ファイル名、識別子など）を管理します。
    *   文字列が初めてエクスポートされる場合、その文字列自体と、`strIndex`内での新しいインデックスが記録されます。エクスポートデータには、文字列の負の長さ（負の値で文字列自体であることを示す）と文字列のバイト列が書き込まれます。
    *   同じ文字列が再度エクスポートされる場合、文字列自体を書き込む代わりに、`strIndex`に保存されているその文字列のインデックス（非負の値）のみが書き込まれます。
    *   空文字列はインデックス`0`にマッピングされ、特別な扱いを受けます。
    *   これにより、特にファイル名のように繰り返し出現する文字列の冗長な保存が避けられ、エクスポートデータのサイズが大幅に削減されます。

4.  **インポート側の対応**:
    *   `importer`構造体にも`strList []string`、`prevFile`、`prevLine`フィールドが追加され、エクスポートされた位置情報と文字列を正しくデコードできるように対応しています。
    *   `importer.pos()`メソッドが追加され、エクスポートデータからデルタエンコードされた行番号と正規化されたファイル名を読み込み、現在の位置情報を復元します。
    *   `importer.string()`メソッドは、読み込んだ値が負であれば文字列のバイト列を読み込み、正であれば`strList`から既存の文字列をルックアップします。

5.  **データサイズへの影響**:
    *   コミットメッセージの統計によると、位置情報を追加した結果、エクスポートデータの全体サイズは平均で14%増加しました。
    *   しかし、これは以前のテキスト形式のエクスポートデータと比較すると65%の削減を維持しており、直前のバイナリ形式からの14%の減少（このコミット以前の最適化による）を考慮すると、位置情報の追加によるオーバーヘッドは許容範囲内と判断されています。特に、`cmd/addr2line`や`cmd/compile`のような一部のパッケージでは、位置情報の追加によりサイズが大幅に増加していますが、これはこれらのパッケージが多くのシンボルや定義を持つためと考えられます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/bexport.go` の変更点

`exporter`構造体には、エクスポート中に遭遇した文字列と位置情報を追跡するための新しいフィールドが追加されています。

```go
type exporter struct {
	out *bufio.Writer

	// object -> index maps, indexed in order of serialization
	strIndex map[string]int // 新規追加: 文字列の正規化用
	pkgIndex map[*Pkg]int
	typIndex map[*Type]int
	funcList []*Func

	// position encoding
	prevFile string // 新規追加: デルタエンコーディング用
	prevLine int    // 新規追加: デルタエンコーディング用

	// debugging support
	written int // bytes written
	trace   bool
}

func export(out *bufio.Writer, trace bool) int {
	p := exporter{
		out:      out,
		strIndex: map[string]int{"": 0}, // 空文字列をインデックス0にマッピングして初期化
		pkgIndex: make(map[*Pkg]int),
		typIndex: make(map[*Type]int),
		trace:    trace,
	}
    // ...
}
```

`exporter.pos`メソッドは、ノード`n`からファイル名と行番号を取得し、`prevFile`と`prevLine`と比較してデルタエンコーディングを行います。

```go
func (p *exporter) pos(n *Node) {
	var file string
	var line int
	if n != nil {
		file, line = Ctxt.LineHist.FileLine(int(n.Lineno)) // ノードからファイルと行番号を取得
	}

	if file == p.prevFile && line != p.prevLine {
		// 最も一般的なケース: ファイルは同じで、行番号のみが変更された場合
		// デルタエンコードされた行番号を書き込む
		p.int(line - p.prevLine) // != 0
	} else {
		// ファイルが変更されたか、行番号が変更されていない場合
		// デルタ値0を書き込み、その後で新しいファイル名と絶対行番号を書き込む
		p.int(0)
		p.string(file) // ファイル名は正規化されて書き込まれる
		p.int(line)
		p.prevFile = file
	}
	p.prevLine = line
}
```

`exporter.string`メソッドは、文字列の正規化を実装しています。

```go
func (p *exporter) string(s string) {
	if p.trace {
		p.tracef("%q ", s)
	}
	// 文字列が既にエクスポートされている場合、そのインデックスを書き込む
	if i, ok := p.strIndex[s]; ok {
		p.rawInt64(int64(i))
		return
	}
	// そうでない場合、文字列を記憶し、負の長さとバイト列を書き込む
	p.strIndex[s] = len(p.strIndex) // 新しいインデックスを割り当てる
	p.rawInt64(-int64(len(s)))      // 負の長さで文字列自体であることを示す
	for i := 0; i < len(s); i++ {
		p.rawByte(s[i])
	}
}
```

### `src/cmd/compile/internal/gc/bimport.go` および `src/go/internal/gcimporter/bimport.go` の変更点

これらのファイルでは、`importer`構造体が`strList`、`prevFile`、`prevLine`を保持するように更新され、`importer.pos()`と`importer.string()`メソッドが追加または変更されています。これらは`bexport.go`で行われたエンコーディングと対称的に、デコード処理を行います。

`importer.pos`メソッドは、エクスポートデータから位置情報を読み込み、`prevFile`と`prevLine`を更新します。

```go
func (p *importer) pos() {
	file := p.prevFile
	line := p.prevLine

	if delta := p.int(); delta != 0 {
		// デルタ値が0でない場合、行番号を更新
		line += delta
	} else {
		// デルタ値が0の場合、新しいファイル名と絶対行番号を読み込む
		file = p.string() // 正規化された文字列をデコード
		line = p.int()
		p.prevFile = file
	}
	p.prevLine = line

	// TODO(gri) register new position - この時点ではまだ位置情報を登録する処理は実装されていない
}
```

`importer.string`メソッドは、正規化された文字列をデコードします。

```go
func (p *importer) string() string {
	if debugFormat {
		p.marker('s')
	}
	// 読み込んだ値が文字列のインデックス（>= 0）の場合
	i := p.rawInt64()
	if i >= 0 {
		return p.strList[i] // 記憶されている文字列を返す
	}
	// 読み込んだ値が負の文字列の長さ（< 0）の場合
	if n := int(-i); n <= cap(p.buf) {
		p.buf = p.buf[:n]
	} else {
		p.buf = make([]byte, n)
	}
	for i := range p.buf {
		p.buf[i] = p.rawByte()
	}
	s := string(p.buf)
	p.strList = append(p.strList, s) // 新しい文字列を記憶する
	return s
}
```

# [インデックス 27298] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）とGoリンカ（`cmd/link`）が内部的に使用するリロケーション情報から、未使用のフィールドを削除することを目的としています。具体的には、`Xadd`と`Xsym`というフィールドがオブジェクトファイルのリロケーション構造に含まれていましたが、これらは実際にはGoツールチェインのどの部分でも利用されていませんでした。これらの未使用フィールドを削除することで、生成されるアーカイブファイルのサイズを削減し、`pkg/linux_amd64`の場合で約3%（41.5MBから40.2MBへ）のファイルサイズ削減を実現しています。これは、Goのビルド成果物の効率化とディスク使用量の最適化に貢献する変更です。

## 元コミット内容

`cmd/compile, cmd/link: remove unused fields from relocations`

このコミットは、Goコンパイラ（`cmd/compile`）とGoリンカ（`cmd/link`）が扱うリロケーション情報から、未使用のフィールドを削除します。

これにより、`pkg/linux_amd64`におけるアーカイブファイルのサイズが41.5MBから40.2MBへと3%削減されます。

## 変更の背景

Goのツールチェインは、ソースコードをコンパイルして実行可能なバイナリやライブラリを生成します。このプロセスでは、中間形式としてオブジェクトファイルが生成され、これらがリンカによって結合されて最終的な成果物となります。オブジェクトファイルには、コード、データ、そして「リロケーション」と呼ばれる情報が含まれています。リロケーションは、プログラムがメモリにロードされる際に、シンボル（変数や関数のアドレスなど）の最終的なアドレスを解決するために必要な指示です。

このコミットの背景には、Goのビルド成果物のサイズを最適化したいという意図があります。Goのツールチェインは、その設計上、自己完結型のバイナリを生成することが多く、その結果としてバイナリサイズが大きくなる傾向があります。特に、標準ライブラリのパッケージ（`pkg/linux_amd64`のようなプラットフォーム固有のアーカイブ）は、多くのオブジェクトファイルを含んでおり、その合計サイズは無視できません。

過去の設計や実装の過程で、リロケーション構造に`Xadd`と`Xsym`というフィールドが追加された可能性があります。しかし、時間の経過とともに、これらのフィールドがGoのコンパイラやリンカの現在のロジックでは使用されていないことが判明しました。つまり、これらのフィールドはオブジェクトファイル内に存在し、ディスクスペースを消費しているにもかかわらず、何の機能も果たしていなかったのです。

このコミットは、このような「死んだコード」ならぬ「死んだデータ」を特定し、削除することで、ビルド成果物のサイズを削減し、全体的な効率を向上させることを目的としています。特に、`pkg/linux_amd64`のような頻繁に利用されるプラットフォームのアーカイブサイズが削減されることは、ディスク使用量の節約だけでなく、配布やデプロイの効率化にも繋がります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Goコンパイラ (`cmd/compile`)**: Goのソースコード（`.go`ファイル）を、マシンが理解できるオブジェクトコード（`.o`ファイル）に変換するツールです。このオブジェクトコードには、コンパイルされた関数、変数、そして後でリンカが処理するためのリロケーション情報などが含まれます。
2.  **Goリンカ (`cmd/link`)**: コンパイラによって生成された複数のオブジェクトファイルやアーカイブファイル（`.a`ファイル）を結合し、最終的な実行可能ファイルや共有ライブラリを生成するツールです。リンカは、オブジェクトファイル内のリロケーション情報を解決し、シンボル参照を正しいメモリアドレスに置き換えます。
3.  **オブジェクトファイル**: コンパイラによって生成される中間ファイルで、機械語コード、データ、シンボルテーブル、リロケーションエントリなどが含まれます。Goの場合、内部的なオブジェクトファイル形式を使用しています。
4.  **アーカイブファイル (`.a`ファイル)**: 複数のオブジェクトファイルを一つにまとめたファイルです。Goの標準ライブラリパッケージは、通常、アーカイブファイルとして配布されます（例: `pkg/linux_amd64/fmt.a`）。
5.  **リロケーション (Relocation)**: プログラムがコンパイルされる際、関数や変数の正確なメモリアドレスはまだ決定されていません。リンカが複数のオブジェクトファイルを結合し、最終的な実行可能ファイルを生成する際に、これらのシンボル参照を実際のメモリアドレスに「再配置（relocate）」する必要があります。リロケーションエントリは、どの場所のどのシンボル参照を、どのように修正すべきかという指示をリンカに与えます。
    *   リロケーションエントリは通常、以下のような情報を含みます。
        *   `Offset`: リロケーションが必要なコードまたはデータ内の位置。
        *   `Type`: リロケーションの種類（例: 絶対アドレス、相対アドレス、GOT/PLTエントリなど）。
        *   `Symbol`: 参照しているシンボル（関数名、変数名など）。
        *   `Addend`: リロケーション計算に追加される定数オフセット。
6.  **`goobj`パッケージ (`src/cmd/internal/goobj`)**: Goのツールチェイン内部で使用されるパッケージで、Go独自のオブジェクトファイル形式の読み書きを扱います。コンパイラやリンカがオブジェクトファイルを相互にやり取りする際のデータ構造やシリアライズ/デシリアライズロジックを定義しています。
7.  **`objfile`パッケージ (`src/cmd/internal/obj`)**: Goのアセンブラやコンパイラがオブジェクトファイルを生成する際に使用される低レベルの抽象化を提供します。シンボル、リロケーション、セクションなどの概念を扱います。
8.  **`ld`パッケージ (`src/cmd/link/internal/ld`)**: Goリンカの主要なロジックが含まれるパッケージです。オブジェクトファイルの解析、シンボル解決、リロケーション処理、最終的なバイナリの生成などを行います。
9.  **未使用フィールド (Unused fields)**: データ構造内に定義されているが、プログラムの実行ロジックのどこからも読み書きされたり、利用されたりしないフィールドのことです。これらはメモリやディスクスペースを無駄に消費します。

## 技術的詳細

Goのツールチェインは、独自のオブジェクトファイル形式を使用しており、これは一般的なELFやMach-O形式とは異なります。この内部形式は、Goのコンパイラとリンカの間で効率的に情報をやり取りするために最適化されています。リロケーション情報は、このオブジェクトファイル形式の重要な部分を占めています。

このコミットで削除された`Xadd`と`Xsym`は、リロケーションエントリの構造体の一部として定義されていましたが、Goのコンパイラやリンカのコードベースを調査した結果、これらが実際に利用されていないことが判明しました。

具体的には、以下のファイルでこれらのフィールドが扱われていました。

*   `src/cmd/internal/goobj/read.go`: このファイルは、Goのオブジェクトファイルを読み込む際のロジックを定義しています。`parseObject`関数内でリロケーションエントリをパースする際に、`Xadd`と`Xsym`に対応するデータをファイルから読み込んでいましたが、その直後にコメントで「ignored」と明記されているように、読み込んだ値はどこにも格納されず、単に読み飛ばされていました。
*   `src/cmd/internal/obj/objfile.go`: このファイルは、オブジェクトファイルを書き出す際のロジックを定義しています。`writesym`関数内でリロケーションエントリを書き出す際に、`Xadd`と`Xsym`に対応するデータとして、それぞれ`0`と`nil`（またはそれに相当する値）を書き込んでいました。これもまた、コメントで「ignored」とされており、意味のある値が書き込まれているわけではありませんでした。
*   `src/cmd/link/internal/ld/objfile.go`: リンカがオブジェクトファイルを読み込む際のロジックを定義しています。`objfile`パッケージと同様に、`Xadd`と`Xsym`に対応するデータをファイルから読み込んでいましたが、これも読み飛ばされていました。

これらのフィールドが未使用であるにもかかわらず、オブジェクトファイル内に存在していたため、各リロケーションエントリのサイズが不必要に大きくなっていました。Goのプログラムは多数のリロケーションエントリを持つことが多いため、このわずかなオーバーヘッドが積み重なり、最終的なアーカイブファイルのサイズに影響を与えていました。

このコミットは、これらの未使用フィールドをオブジェクトファイル形式から完全に削除することで、以下の効果をもたらします。

1.  **ディスクスペースの削減**: オブジェクトファイルおよびそれらをまとめたアーカイブファイルのサイズが小さくなります。これにより、Goのツールチェインのインストールサイズや、ビルドされたGoアプリケーションの配布サイズが削減されます。
2.  **I/Oパフォーマンスの向上**: オブジェクトファイルの読み書きに必要なデータ量が減るため、コンパイルやリンクの際のディスクI/Oがわずかに削減され、ビルド時間の短縮に寄与する可能性があります。
3.  **メモリ使用量の削減**: オブジェクトファイルをメモリにロードして処理する際のメモリフットプリントがわずかに削減される可能性があります。

この変更は、Goのツールチェインの内部実装に関するものであり、Go言語の構文やセマンティクス、またはGoプログラムの実行時の動作に直接的な影響を与えるものではありません。しかし、Go開発者にとっては、より効率的なビルドプロセスと、より小さなバイナリという形で間接的な恩恵があります。

## コアとなるコードの解説

上記の変更箇所は、Goの内部オブジェクトファイル形式におけるリロケーションエントリの構造と、その読み書きロジックから、未使用の`Xadd`と`Xsym`フィールドを削除しています。

1.  **`src/cmd/internal/goobj/read.go` の変更**:
    *   `r.readInt() // Xadd - ignored` と `r.readSymID() // Xsym - ignored` の行が削除されました。
    *   これは、オブジェクトファイルを読み込む際に、`Xadd`と`Xsym`に対応するバイト列をファイルから読み飛ばしていた処理を完全に削除したことを意味します。これらのフィールドがもはやファイルに存在しないため、読み込む必要がなくなりました。

2.  **`src/cmd/internal/obj/objfile.go` の変更**:
    *   リロケーションエントリのエンコーディングを説明するコメントから、`- xadd [int]` と `- xsym [symref index]` の記述が削除されました。
    *   `wrint(b, 0) // Xadd, ignored` と `wrsym(b, nil) // Xsym, ignored` の行が削除されました。
    *   これは、オブジェクトファイルを書き出す際に、`Xadd`と`Xsym`に対応するダミーの値（`0`や`nil`）を書き込んでいた処理を完全に削除したことを意味します。これらのフィールドがもはやオブジェクトファイル形式の一部ではないため、書き込む必要がなくなりました。

3.  **`src/cmd/link/internal/ld/objfile.go` の変更**:
    *   リロケーションエントリのエンコーディングを説明するコメントから、`- xadd [int]` と `- xsym [symref index]` の記述が削除されました。
    *   `rdint64(f) // Xadd, ignored` と `rdsym(ctxt, f, pkg) // Xsym, ignored` の行が削除されました。
    *   これは、リンカがオブジェクトファイルを読み込む際に、`Xadd`と`Xsym`に対応するバイト列をファイルから読み飛ばしていた処理を完全に削除したことを意味します。`goobj/read.go`と同様に、これらのフィールドがファイルに存在しないため、読み込む必要がなくなりました。

これらの変更は、Goのツールチェイン全体で`Xadd`と`Xsym`が完全に不要であることを確認した上で行われています。これにより、オブジェクトファイル形式が簡素化され、ディスク上のフットプリントが削減されるという直接的なメリットが生まれます。特に、`pkg/linux_amd64`のような多くのオブジェクトファイルを含むアーカイブでは、この小さな変更が積み重なって顕著なサイズ削減効果をもたらしました。

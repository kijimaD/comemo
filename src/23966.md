# [インデックス 23966] ファイルの概要

このコミットは、Goコンパイラのレース検出器（Race Detector）のインストゥルメンテーションロジックを更新し、`OKEY`ノードと`OSLICESTR`ノードのオペランドに対してもレース検出のための監視コードが挿入されるように変更します。特に`OSLICESTR`については、以前は先行する境界チェックによって保護されていたためインストゥルメンテーションが不要でしたが、その境界チェックがなくなったため、明示的なインストゥルメンテーションが必要となりました。

cmd/compile: add instrumentation of OKEY

Instrument operands of OKEY.
Also instrument OSLICESTR. Previously it was not needed

## 変更の背景

Goのレース検出器は、並行処理におけるデータ競合（data race）を検出するための強力なツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。このような競合は、プログラムの予測不能な動作やバグの原因となります。

レース検出器は、コンパイル時に特定のメモリ操作（読み書き）に対してインストゥルメンテーションコードを挿入することで機能します。このインストゥルメンテーションコードは、実行時にメモリアクセスを監視し、競合が発生した際に報告します。

このコミットの背景には、Goコンパイラの内部的な変更があります。具体的には、`OSLICESTR`（文字列スライス操作）に関連する先行する境界チェックが削除されたことが挙げられます。以前は、これらの境界チェック自体がインストゥルメンテーションの対象となっていたため、`OSLICESTR`ノード自体を直接インストゥルメントする必要はありませんでした。しかし、その境界チェックがなくなったことで、文字列スライス操作のオペランドへのアクセスがレース検出器の監視から漏れる可能性が生じました。これを防ぐため、`OSLICESTR`ノードのオペランドも明示的にインストゥルメントの対象に加える必要が生じました。

また、`OKEY`ノード（マップのキーアクセスなど、インデックスアクセスに関連する可能性のある操作）についても、同様にレース検出の対象とすることで、より広範なデータ競合を検出できるように改善されています。

## 前提知識の解説

### Go Race Detector (レース検出器)

Goのレース検出器は、Goプログラムの実行中にデータ競合を動的に検出するツールです。`go run -race`、`go build -race`、`go test -race`などのコマンドで有効にできます。有効にすると、コンパイラはメモリの読み書き操作に対して追加のコード（インストゥルメンテーション）を挿入します。この追加コードは、実行時に各メモリアクセスを追跡し、並行するアクセスが競合しているかどうかを判断します。競合が検出されると、レース検出器は詳細なレポート（スタックトレースなど）を出力し、開発者が問題を特定して修正するのを助けます。

### Goコンパイラ (`cmd/compile`)

`cmd/compile`はGo言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担います。コンパイルプロセスは、字句解析、構文解析、抽象構文木（AST）の構築、型チェック、中間表現（IR）への変換、最適化、コード生成など、複数のフェーズに分かれています。レース検出器のインストゥルメンテーションは、通常、ASTのトラバース中や中間表現の段階で挿入されます。

### 抽象構文木（AST）とコンパイラノード

コンパイラは、ソースコードを解析してプログラムの構造を木構造で表現した抽象構文木（AST）を構築します。ASTの各ノードは、プログラム内の特定の構文要素（変数宣言、関数呼び出し、演算子など）を表します。Goコンパイラでは、これらのノードは`Node`構造体で表現され、`Op`フィールドによってノードの種類が識別されます。

*   **`OKEY`**: マップのキーアクセスや配列/スライスのインデックスアクセスなど、キーやインデックスに関連する操作を表すノードタイプです。
*   **`OSLICE`, `OSLICEARR`, `OSLICE3`, `OSLICE3ARR`**: これらはスライス操作を表すノードタイプです。
    *   `OSLICE`: `a[low:high]`のような2インデックススライス。
    *   `OSLICEARR`: 配列に対する2インデックススライス。
    *   `OSLICE3`: `a[low:high:max]`のような3インデックススライス。
    *   `OSLICE3ARR`: 配列に対する3インデックススライス。
*   **`OSLICESTR`**: 文字列に対するスライス操作（例: `s[low:high]`）を表すノードタイプです。Goでは文字列はバイトの読み取り専用スライスとして扱われるため、文字列スライスもメモリアクセスを伴います。

### インストゥルメンテーション

インストゥルメンテーションとは、プログラムの実行を監視したり、特定の情報を収集したりするために、追加のコードを挿入するプロセスを指します。レース検出器の場合、これはメモリの読み書き操作の直前に、そのアクセスに関する情報を記録するコードを挿入することを意味します。これにより、実行時に並行するアクセスが競合しているかを判断できます。

## 技術的詳細

このコミットの主要な変更は、Goコンパイラの`src/cmd/compile/internal/gc/racewalk.go`ファイル内の`racewalknode`関数にあります。この関数は、ASTを再帰的にトラバースし、レース検出器のインストゥルメンテーションが必要なノードに対して処理を行います。

`racewalknode`関数内には、さまざまなノードタイプを処理するための`switch`文があります。この`switch`文に、`OSLICESTR`と`OKEY`ノードの処理が追加されました。

変更前は、`OSLICESTR`は以下のコメントと共に、インストゥルメンテーションをスキップするノードのリストに含まれていました。
`OSLICESTR, // always preceded by bounds checking, avoid double instrumentation.`
これは、「常に境界チェックが先行するため、二重のインストゥルメンテーションを避ける」という意味です。つまり、文字列スライス操作の前に実行される境界チェックが既にインストゥルメンテーションの対象となっており、それによって文字列スライス操作自体も間接的に監視されていたため、`OSLICESTR`ノード自体を直接インストゥルメントする必要がなかったことを示しています。

しかし、このコミットの変更説明にあるように、「先行する境界チェックがなくなった」ため、`OSLICESTR`ノードを明示的にインストゥルメントの対象に加える必要が生じました。これにより、文字列スライス操作のオペランド（例えば、スライスされる文字列自体やインデックス変数）へのアクセスがレース検出器によって適切に監視されるようになります。

`OKEY`ノードについても、同様にそのオペランド（`n.Left`と`n.Right`）が`racewalknode`関数によって再帰的に処理されるようになり、レース検出の対象となります。これにより、マップのキーアクセスやその他のインデックスアクセスにおけるデータ競合も検出できるようになります。

また、`src/runtime/race/testdata/slice_test.go`には、`TestRaceSlice3`という新しいテストケースが追加されました。このテストは、3インデックススライス（`x[:1:i]`）の容量インデックス`i`が別のゴルーチンによって並行して変更されるシナリオをシミュレートし、レース検出器がこの種のデータ競合を正しく検出できることを検証します。これは、`OSLICE3`ノードのインストゥルメンテーションが正しく機能していることを確認するためのものです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/racewalk.go`の変更点

1.  **`OSLICESTR`のインストゥルメンテーション追加**:
    *   `case OSLICE, OSLICEARR, OSLICE3, OSLICE3ARR:` の行が `case OSLICE, OSLICEARR, OSLICE3, OSLICE3ARR, OSLICESTR:` に変更されました。
    *   これにより、文字列スライス操作（`OSLICESTR`）も、他のスライス操作と同様に、そのオペランド（`n.Left`と`n.Right`）に対して`racewalknode`が再帰的に呼び出され、レース検出のためのインストゥルメンテーションが適用されるようになります。`n.Left`はスライスされる元の文字列、`n.Right`はスライスのインデックスや長さに関連する式を表すと考えられます。
2.  **`OKEY`のインストゥルメンテーション追加**:
    *   新たに `case OKEY:` ブロックが追加されました。
    *   このブロック内で、`OKEY`ノードのオペランド（`n.Left`と`n.Right`）に対しても`racewalknode`が再帰的に呼び出されます。これにより、マップのキーアクセスなど、`OKEY`が表す操作のオペランドもレース検出の対象となります。
3.  **`OSLICESTR`のコメントからの削除**:
    *   インストゥルメンテーションをスキップするノードのリストから `OSLICESTR` が削除されました。
    *   以前のコメント `// always preceded by bounds checking, avoid double instrumentation.` が削除されたことで、`OSLICESTR`がもはや先行する境界チェックによって保護されていないことが明確になり、直接インストゥルメンテーションが必要になったという背景と一致します。

これらの変更により、Goのレース検出器は、文字列スライス操作やキーアクセスにおけるデータ競合をより確実に検出できるようになります。

### `src/runtime/race/testdata/slice_test.go`の変更点

1.  **`TestRaceSlice3`関数の追加**:
    *   この新しいテスト関数は、3インデックススライス（`x[:1:i]`）の容量インデックス`i`が、メインゴルーチンと別のゴルーチンによって同時にアクセスされるシナリオをテストします。
    *   `x := make([]int, 10)`で整数スライスを初期化し、`i := 2`でインデックス変数を設定します。
    *   別のゴルーチンが`i = 3`と`i`を書き換えます。
    *   メインゴルーチンは`_ = x[:1:i]`という3インデックススライス操作を実行します。この操作は`i`の値を読み取ります。
    *   `done`チャネルを使ってゴルーチン間の同期を取り、データ競合が発生する可能性のあるタイミングを制御しています。
    *   このテストは、`go test -race`で実行された際に、`i`への並行アクセス（書き込みと読み取り）がデータ競合として検出されることを期待しています。これにより、`OSLICE3`ノードのインストゥルメンテーションが正しく機能していることが検証されます。

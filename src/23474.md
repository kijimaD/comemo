## 変更の背景

Goランタイムの`mapzero`関数は、マップ要素のゼロ値を初期化する役割を担っています。この関数内で、`atomicloadp`というアトミック操作が使用されています。しかし、ARMアーキテクチャにおいて、`atomicloadp`の実装が特定の条件下で問題を引き起こすことが判明しました。

具体的には、ARMでは`atomicloadp(p)`が`xadd(p, 0)`（アトミックな加算操作で0を加える）として実装されている場合があります。この`xadd`命令は、たとえ0を加えるだけであっても、メモリへの書き込み操作と見なされます。問題は、`mapzero`が読み取り専用メモリ領域にある型情報（`_type`構造体）に対して`atomicloadp`を呼び出す可能性がある点です。読み取り専用メモリに対して書き込み操作を行おうとすると、セグメンテーション違反などのクラッシュが発生します。

このコミットは、ARMアーキテクチャで、かつ対象のメモリがヒープ上にない（つまり、読み取り専用である可能性が高い）場合に、`atomicloadp`の呼び出しをスキップすることで、このクラッシュを回避することを目的としています。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、スケジューリング、メモリ管理、プリミティブな同期操作など、Go言語の多くの低レベルな側面を処理します。`src/runtime`ディレクトリには、これらの機能の実装が含まれています。

### `mapzero`関数
`mapzero`はGoランタイム内の関数で、マップの要素型が持つゼロ値を初期化するために使用されます。Goのマップは、要素が初めてアクセスされる際にその型のゼロ値で初期化されることがあります。このプロセスは、特にリフレクションを通じて型が動的に扱われる場合に重要になります。

### `_type`構造体
Goランタイムでは、すべての型が`_type`構造体によって内部的に表現されます。この構造体には、型のサイズ、アラインメント、名前などのメタデータが含まれています。`_type`構造体は通常、プログラムの静的なデータセクションや読み取り専用メモリ領域に配置されます。

### `atomicloadp`
`atomicloadp`は、Goランタイムが提供するアトミック操作の一つで、ポインタをアトミックに読み込むために使用されます。アトミック操作は、複数のゴルーチンが同時に同じメモリ位置にアクセスしても、データ競合が発生しないことを保証します。これは、並行プログラミングにおいて非常に重要です。

### `xadd`命令 (Exchange and Add)
`xadd`は、一部のCPUアーキテクチャ（特にx86）で利用可能なアトミック命令です。これは、メモリ位置の値を指定された値で加算し、元の値を返す操作を単一のアトミックなステップで実行します。ARMアーキテクチャでは、直接的な`xadd`命令がない場合でも、コンパイラやアセンブリコードが同様のアトミックな加算操作をエミュレートすることがあります。このコミットの文脈では、`atomicloadp`が`xadd(p, 0)`として実装されている、つまり「0を加算する」という書き込み操作として扱われることが問題でした。

### `inheap`関数
`inheap`はGoランタイム内の関数で、与えられたメモリアドレスがGoのヒープ領域内にあるかどうかを判定します。ヒープは、プログラムが実行時に動的にメモリを割り当てる領域です。ヒープ上のメモリは通常、書き込み可能ですが、ヒープ外のメモリ（例えば、静的データやコードセグメント）は読み取り専用である場合があります。

### `unsafe.Pointer`
Goの`unsafe`パッケージは、型安全性をバイパスして、ポインタと任意の型の間で変換を行うことを可能にします。`unsafe.Pointer`は、任意の型のポインタを保持できる特別なポインタ型です。これは低レベルのシステムプログラミングやランタイムの実装でよく使用されますが、誤用するとメモリ安全性の問題を引き起こす可能性があります。

## 技術的詳細

この問題の核心は、ARMアーキテクチャにおける`atomicloadp`の実装にあります。Goランタイムは、異なるCPUアーキテクチャに対して最適化されたアトミック操作を提供します。ARMの場合、`atomicloadp(p)`は、ポインタ`p`が指す値をアトミックに読み込むことを意図していますが、その内部実装が`xadd(p, 0)`、つまり「`p`が指す値に0をアトミックに加算する」という書き込み操作として行われていました。

`mapzero`関数は、`_type`構造体の`zero`フィールド（その型のゼロ値を指すポインタ）をチェックするために`atomicloadp(unsafe.Pointer(&t.zero))`を呼び出します。`_type`構造体は、Goプログラムの静的な型情報の一部として、通常は読み取り専用のメモリセグメントに配置されます。

したがって、ARM上で`mapzero`が読み取り専用メモリにある`_type`構造体の`t.zero`フィールドに対して`atomicloadp`を呼び出すと、`xadd(p, 0)`という書き込み操作が実行され、これが読み取り専用メモリへの書き込み違反となり、プログラムがクラッシュしていました。

このコミットは、この特定のケースを検出し、`atomicloadp`の呼び出しを回避することで問題を解決します。

## コアとなるコードの変更箇所

`src/runtime/hashmap.go`ファイルの`mapzero`関数に以下のコードが追加されました。

```go
	// On ARM, atomicloadp is implemented as xadd(p, 0),
	// so we cannot use atomicloadp on read-only memory.
	// Check whether the pointer is in the heap; if not, it's not writable
	// so the zero value must already be set.
	if GOARCH == "arm" && !inheap(uintptr(unsafe.Pointer(t))) {
		if t.zero == nil {
			print("runtime: map element ", *t._string, " missing zero value\n")
			throw("mapzero")
		}
		return
	}
```

## コアとなるコードの解説

追加されたコードブロックは、以下の条件をチェックします。

1.  `GOARCH == "arm"`: 現在のビルドターゲットがARMアーキテクチャであるかどうかを確認します。この問題はARM固有の実装に起因するため、他のアーキテクチャではこのチェックは不要です。
2.  `!inheap(uintptr(unsafe.Pointer(t)))`: `t`（`_type`構造体へのポインタ）が指すメモリがヒープ上にないかどうかを確認します。`_type`構造体は通常、読み取り専用の静的データセグメントに存在するため、この条件が真になる可能性が高いです。

この両方の条件が真である場合、つまり「ARMアーキテクチャで、かつ`_type`構造体がヒープ外（読み取り専用の可能性が高い）にある」場合、以下の処理が行われます。

*   `if t.zero == nil`: `t.zero`フィールドが`nil`であるかどうかをチェックします。`_type`構造体が読み取り専用メモリにある場合、その`zero`フィールドは既に適切に初期化されているべきです。もし`nil`であれば、それはランタイムの内部的な不整合を示しており、エラーとして扱われます。
*   `print(...)` と `throw("mapzero")`: `t.zero`が`nil`の場合、エラーメッセージを出力し、ランタイムパニックを引き起こします。これは、予期せぬ状態が発生したことを示します。
*   `return`: 上記の条件が満たされ、かつ`t.zero`が`nil`でない場合（つまり、ゼロ値が既に設定されている場合）、`mapzero`関数はそれ以上の処理を行わずに早期リターンします。これにより、問題のある`atomicloadp`の呼び出しが回避され、クラッシュが防止されます。

この修正により、ARMアーキテクチャで読み取り専用メモリ上の`_type`構造体に対して`mapzero`が呼び出された際に、`atomicloadp`による意図しない書き込み操作が実行されることがなくなり、安定性が向上しました。

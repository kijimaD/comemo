# [インデックス 22587] ファイルの概要

`src/runtime/proc1.go` は、Goランタイムの重要な部分を構成するファイルの一つです。このファイルは、Goプログラムの実行時におけるプロセスの初期化、スケジューリング、およびゴルーチン管理に関連する低レベルの機能を含んでいます。具体的には、GoランタイムがどのようにOSスレッドを管理し、ゴルーチンをそれらのスレッド上で実行するかといった、Goの並行処理モデルの基盤となるロジックが記述されています。

## コミット

このコミットは、GoランタイムのWindows固有のコードから、もはや使用されていないコメントを削除するものです。削除されたコメントは、Windowsの構造化例外処理（SEH）に関するもので、GoランタイムがSEHを例外処理に使用しなくなったことを反映しています。これは、コードベースのクリーンアップと、現在のランタイムの動作との整合性を保つための変更です。

## 変更の背景

この変更の背景には、GoランタイムがWindows上での例外処理メカニズムをどのように進化させてきたかという歴史があります。かつて、GoランタイムはWindowsの構造化例外処理（SEH）を利用して、ハードウェア例外やその他の致命的なエラーを捕捉することを検討していたか、あるいは実際に一部で利用していました。しかし、Goのランタイムは、より柔軟でGoの並行処理モデルに適した、Vectored Exception Handling (VEH) を含む他のメカニズムに移行しました。

削除されたコメントは、`mstart1()` 関数内に存在し、「スケジューラがOSスレッドを解放しないため、このポイントには到達しないが、このパスが有効になったらSEHを削除する必要がある」という内容でした。これは、Goランタイムの進化に伴い、SEHが不要になった、あるいは別の方法で例外が処理されるようになったことを示唆しています。このコミットは、その古い設計思想やTODOコメントが現在のランタイムの動作と一致しなくなったため、コードベースから削除されたものです。これにより、コードの可読性が向上し、誤解を招く可能性のある情報が排除されました。

## 前提知識の解説

### Goランタイムとゴルーチン、M、P

Go言語は、軽量な並行処理の単位である「ゴルーチン（goroutine）」を特徴としています。ゴルーチンはOSスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムは、これらのゴルーチンをOSスレッド上で効率的にスケジューリングするための独自のメカニズムを持っています。

このスケジューリングモデルは、主に以下の3つの要素で構成されます。

*   **G (Goroutine)**: Goプログラム内で実行される軽量なスレッド。
*   **M (Machine)**: OSスレッドを表します。Goランタイムは、OSスレッドを抽象化したMを管理し、その上でゴルーチンを実行します。
*   **P (Processor)**: 論理プロセッサを表します。PはMにアタッチされ、ゴルーチンを実行するためのコンテキストを提供します。Pの数は通常、CPUのコア数に等しく、同時に実行できるゴルーチンの数を制限します。

Goランタイムは、GOMAXPROCS環境変数や`runtime.GOMAXPROCS()`関数によって設定されたPの数に基づいて、MとPを管理し、ゴルーチンを効率的にM上で実行するようにスケジューリングします。

### Windowsの例外処理メカニズム (SEHとVEH)

Windowsオペレーティングシステムは、プログラム実行中に発生する異常なイベント（例外）を処理するための複数のメカニズムを提供しています。

*   **構造化例外処理 (Structured Exception Handling - SEH)**:
    SEHは、MicrosoftがC/C++言語向けに提供する拡張機能で、ハードウェア例外（例: ゼロ除算、無効なメモリアクセス）とソフトウェア例外の両方を処理できます。`__try`, `__except`, `__finally` といったキーワードを使用して、例外発生時の処理を記述します。64ビットWindowsでは、SEHハンドラは実行可能ファイルの`.pdata`セクション内の静的なアンワインドテーブルに定義され、システムが例外発生時にこれを解釈します。SEHは、特定のコードブロック内で発生した例外を捕捉する、より局所的なメカニズムです。

*   **Vectored Exception Handling (VEH)**:
    Windows XPで導入されたVEHは、プロセス全体で例外を処理するためのメカニズムです。VEHハンドラは動的に登録され、SEHハンドラよりも先に呼び出されます。これにより、アプリケーションは、特定のコードブロックに限定されずに、プロセス全体で発生するあらゆる例外を捕捉し、カスタムの処理ロジックを適用することができます。Goランタイムは、Windows上での致命的なエラーやハードウェア障害を捕捉するために、主にこのVEHを利用しています。

Goのランタイムは、Goの独自のパニック/リカバリーメカニズムとは別に、OSレベルの例外を適切に処理する必要があります。これは、Goプログラムがクラッシュすることなく、予期せぬOSレベルのイベントから回復したり、少なくともクリーンに終了したりするために不可欠です。

## 技術的詳細

削除されたコメントは、`mstart1()` 関数内にありました。この関数は、Goランタイムが新しいOSスレッド（M）を開始する際に呼び出される初期化ルーチンの一部です。コメントの内容は、この関数が実行されるコードパスが、スケジューラの動作により「到達しない」と認識されていたことを示しています。そして、もしこのパスが将来的に到達可能になった場合、SEH関連のクリーンアップが必要になるだろうというTODOが残されていました。

GoランタイムがSEHを使用しなくなったという事実は、GoがWindows上での例外処理をより洗練された方法で、おそらくVEHを主軸として行うようになったことを意味します。VEHはプロセス全体で例外を捕捉できるため、特定のOSスレッドのライフサイクルに密接に結びついたSEHよりも、GoのM-P-Gモデルにおける柔軟なスレッド管理に適していると考えられます。

Goのランタイムは、OSスレッドが終了する際に、そのスレッドに関連するリソースを適切にクリーンアップする必要があります。以前の設計では、SEHが使用されていた場合、スレッド終了時にSEHハンドラを解除するなどのクリーンアップが必要だった可能性があります。しかし、SEHが使用されなくなったことで、この特定のクリーンアップの必要性もなくなりました。したがって、このTODOコメントは、もはや関連性がなくなり、削除されることになりました。

この変更は、GoランタイムがWindowsの低レベルな挙動をどのように抽象化し、Goの並行処理モデルに適合させているかを示す一例です。Goは、OSのネイティブな例外処理メカニズムと連携しつつも、Go独自のパニック/リカバリーシステムを通じて、より高レベルで安全なエラーハンドリングを提供しています。

## コアとなるコードの解説

削除されたコメントは、`src/runtime/proc1.go` ファイル内の `mstart1()` 関数にありました。

```go
	// TODO(brainman): This point is never reached, because scheduler
	// does not release os threads at the moment. But once this path
	// is enabled, we must remove our seh here.
```

このコメントは、以下の点を説明していました。

*   `This point is never reached`: コメントが置かれていたコードの場所は、Goスケジューラの現在の実装では実行パスとして到達しない、と認識されていました。これは、OSスレッドのライフサイクル管理における特定の状態遷移が、当時のGoランタイムの設計では発生しなかったことを意味します。
*   `because scheduler does not release os threads at the moment`: その理由として、スケジューラがOSスレッドを「解放しない」ことが挙げられています。これは、OSスレッドが一度作成されると、Goランタイムによって再利用されるか、プログラム終了時まで保持される傾向があることを示唆しています。
*   `But once this path is enabled, we must remove our seh here.`: しかし、もし将来的にこのコードパスが有効になり、OSスレッドが解放されるようなシナリオが発生した場合、SEH（構造化例外処理）に関連するクリーンアップコードをこの場所から削除する必要がある、というTODO（やるべきこと）が示されていました。これは、SEHがOSスレッドのコンテキストに紐付いており、スレッドが解放される際にSEHハンドラも適切に解除する必要があったためと考えられます。

このコミットによってこのコメントが削除されたのは、GoランタイムがWindows上での例外処理にSEHを使用しなくなったためです。SEHがもはやGoランタイムの例外処理戦略の一部ではないため、このTODOコメントは無意味になり、コードベースから取り除かれました。これは、Goランタイムの継続的な改善と、古い設計上の考慮事項のクリーンアップを反映しています。

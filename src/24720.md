このコミットは、Goリンカ (`cmd/link`) における `runtime.firstmoduledata` シンボルの扱いを修正し、特にAMD64以外のアーキテクチャ（例: ARM64）でのリンクエラーを解決することを目的としています。リンカがモジュールデータシンボルを生成する際に、"local.moduledata" という名前を使用するように変更することで、既存のコードがGOT (Global Offset Table) を介してアクセスしようとする問題に対処しています。

## 変更の背景

Goのリンカ (`cmd/link`) は、コンパイルされたGoプログラムの各モジュールに関するメタデータを含む `runtime.firstmoduledata` というシンボルを扱います。このシンボルは、ランタイムがモジュールに関する情報を取得するために非常に重要です。

以前の実装では、リンカは `runtime.firstmoduledata` を常にローカルシンボルとして上書きしていました。しかし、`cmd/internal/obj` パッケージ（Goのアセンブラとオブジェクトファイル処理を担当）は、このシンボルへのアクセスをGOT (Global Offset Table) を介して行うようにコードを書き換えていました。

このGOTを介したアクセスは、AMD64アーキテクチャでは問題なく機能していました。AMD64では、GOTエントリがローカルシンボルを指すように解決されることが許容されるためです。しかし、ARM64のような他のアーキテクチャでは、GOTを介してローカルシンボルにアクセスしようとすると、リンカがシンボルを解決できずにリンクエラーが発生するという問題がありました。これは、これらのアーキテクチャではGOTが主に共有ライブラリ内の外部シンボルへのアクセスに使用されるためです。

このコミットは、このアーキテクチャ間の不整合を解消し、特に非AMD64プラットフォームでのリンクエラーを防ぐために導入されました。

## 前提知識の解説

### Goリンカ (`cmd/link`) の役割

Goのビルドプロセスにおいて、`cmd/link` はコンパイルされたオブジェクトファイル（`.o` ファイル）を結合し、実行可能ファイルや共有ライブラリを生成するツールです。シンボルの解決、メモリレイアウトの決定、リロケーションの適用など、プログラムが正しく実行されるために必要な最終的な処理を行います。

### Goランタイムのモジュールデータ (`runtime.firstmoduledata`)

Goプログラムは、実行時に自身の構造に関するメタデータ（型情報、シンボルテーブル、ガベージコレクタのビットマップなど）を必要とします。この情報は「モジュールデータ」として知られ、`runtime.moduledata` 構造体で表現されます。
`runtime.firstmoduledata` は、実行可能ファイルにリンクされる最初のモジュールデータのインスタンスを指すシンボルです。ランタイムはこのシンボルを通じて、プログラム全体のモジュールデータチェーンにアクセスし、リフレクションやスタックトレースなどの機能を実現します。

### シンボルとリンキング

*   **シンボル**: プログラム内の関数、変数、データセクションなどを識別するための名前です。リンカはこれらのシンボルを解決し、参照を正しいメモリ位置に結びつけます。
*   **ローカルシンボル**: 定義されたオブジェクトファイル内でのみ参照されるシンボルです。外部からは直接アクセスできません。
*   **グローバルシンボル**: 複数のオブジェクトファイルやライブラリ間で参照されるシンボルです。
*   **ダイナミックインポート (`obj.SDYNIMPORT`)**: 実行時に動的にロードされる共有ライブラリからインポートされるシンボルを示します。

### GOT (Global Offset Table) と位置独立コード (PIC)

*   **位置独立コード (PIC - Position-Independent Code)**: 実行時のロードアドレスに関わらず正しく実行できるコードです。共有ライブラリなどで使用され、メモリ上の任意の位置にロードされても動作します。
*   **Global Offset Table (GOT)**: PICにおいて、グローバル変数や外部関数へのアクセスを可能にするために使用されるテーブルです。PICでは、絶対アドレスを直接参照する代わりに、GOT内のエントリを介して間接的にアクセスします。これにより、コード自体はロードアドレスに依存せず、GOTのエントリだけが実行時に修正されます。

### `obj.SNOPTRDATA` とガベージコレクション

`obj.SNOPTRDATA` は、Goリンカが使用するシンボルタイプの一つで、「ポインタを含まないデータ」を意味します。Goのガベージコレクタは、メモリ上のポインタを追跡して到達可能なオブジェクトを特定します。`SNOPTRDATA` とマークされたデータセクションは、ガベージコレクタがスキャンする必要がないことを示し、GCの効率を向上させます。`runtime.moduledata` 構造体自体はポインタを多く含みますが、`runtime.firstmoduledata` シンボルが指すメモリ領域は、リンカがその内容を構築する際に、GCから隠蔽する必要がある場合があります。

### `LSym` と `Link` コンテキスト

*   **`LSym`**: Goリンカ内部でシンボルを表す構造体です。シンボルの名前、タイプ、サイズ、アドレス、リロケーション情報などを含みます。
*   **`Link` コンテキスト (`ld.Ctxt`)**: リンカのグローバルな状態を保持する主要な構造体です。現在のアーキテクチャ、シンボルテーブル、リンキングオプションなど、リンカの操作に必要なすべての情報が含まれています。

## 技術的詳細

このコミット以前は、`runtime.firstmoduledata` シンボルは `src/cmd/link/internal/ld/symtab.go` 内で直接 `Linklookup` を介して取得され、`obj.SNOPTRDATA` タイプに設定され、ローカルシンボルとしてマークされていました。しかし、`src/cmd/link/internal/amd64/asm.go` のようなアーキテクチャ固有のアセンブリコードでは、`runtime.firstmoduledata` への参照が `R_X86_64_PC32` のようなPC相対リロケーションとして生成され、これがGOTを介したアクセスに変換されることがありました。

AMD64では、PC相対リロケーションがGOTエントリを指す場合でも、リンカはそれを適切に解決できました。しかし、ARM64などの他のアーキテクチャでは、GOTは通常、共有ライブラリからの外部シンボルへのアクセスに限定されており、ローカルシンボルへのGOTアクセスはサポートされていませんでした。このため、リンカは `runtime.firstmoduledata` へのGOT参照を解決できず、リンクエラーが発生していました。

このコミットによる変更は、この問題を根本的に解決するために、`runtime.firstmoduledata` の扱いをリンカの初期段階で一元化し、アーキテクチャに依存しない方法でシンボルを管理するようにしました。

1.  **`Link` コンテキストへの `Moduledata` フィールドの追加**:
    `src/cmd/link/internal/ld/link.go` に `Moduledata *LSym` フィールドが追加されました。これにより、リンカのコンテキスト (`ld.Ctxt`) が、現在処理中のモジュールデータシンボルへのポインタを直接保持できるようになります。これは、`runtime.firstmoduledata` シンボルをリンカ全体で一貫して参照するための中心的なポイントとなります。

2.  **`lib.go` でのモジュールデータシンボルの初期化ロジックの変更**:
    `src/cmd/link/internal/ld/lib.go` の `loadlib()` 関数内で、`runtime.firstmoduledata` シンボルの初期化ロジックが変更されました。
    *   まず、`runtime.firstmoduledata` を `Linklookup` で検索します。
    *   もし、このシンボルがモジュールによって定義されていない（`Type == 0`）か、またはダイナミックインポート (`obj.SDYNIMPORT`) である場合、リンカは `local.moduledata` という新しいローカルシンボルを作成し、これを `Ctxt.Moduledata` に設定します。これにより、リンカが生成するモジュールデータは明確にローカルなものとして扱われます。
    *   もし、`runtime.firstmoduledata` がモジュールによって定義されている場合、そのシンボルの `Size` を0に設定して内容を再定義できるようにし、`Ctxt.Moduledata` に設定します。
    *   どちらの場合も、`Ctxt.Moduledata` に設定されたシンボルは `obj.SNOPTRDATA` タイプに設定され、ガベージコレクタから隠蔽されます。また、`Reachable` フラグが `true` に設定され、リンカがこのシンボルを最終的なバイナリに含めるようにします。

3.  **`amd64/asm.go` と `symtab.go` での `Ctxt.Moduledata` の利用**:
    *   `src/cmd/link/internal/amd64/asm.go` では、`runtime.firstmoduledata` を直接 `Linklookup` する代わりに、`ld.Ctxt.Moduledata` を使用するように変更されました。これにより、アーキテクチャ固有のアセンブリコードが、`lib.go` で適切に初期化されたモジュールデータシンボルを参照するようになります。
    *   `src/cmd/link/internal/ld/symtab.go` では、以前 `runtime.firstmoduledata` を直接検索し、そのタイプとサイズを設定していたコードが削除され、代わりに `Ctxt.Moduledata` を直接使用するように変更されました。これは、モジュールデータシンボルの初期化と設定が `lib.go` で一元的に行われるようになったためです。

この変更により、リンカは `runtime.firstmoduledata` シンボルを、それがモジュールによって提供されるかリンカによって生成されるかにかかわらず、一貫した方法で管理できるようになります。特に、リンカが生成するモジュールデータには `local.moduledata` というローカルな名前が与えられ、GOTを介したアクセスが不要になるため、ARM64などのプラットフォームでのリンクエラーが解消されます。

## コアとなるコードの解説

### `src/cmd/link/internal/amd64/asm.go` の変更

`ld.Addpcrelplus(ld.Ctxt, initfunc, ld.Linklookup(ld.Ctxt, "runtime.firstmoduledata", 0), 0)`
から
`ld.Addpcrelplus(ld.Ctxt, initfunc, ld.Ctxt.Moduledata, 0)`
への変更は、AMD64アーキテクチャ固有のアセンブリコードが `runtime.firstmoduledata` シンボルを参照する方法を修正しています。以前は、リンカのコンテキストから直接シンボルを検索していましたが、変更後は `ld.Ctxt` に新しく追加された `Moduledata` フィールドを直接参照するようになりました。これにより、`lib.go` で一元的に管理・初期化されたモジュールデータシンボルが使用されることが保証され、GOTを介した不適切なアクセスが回避されます。

### `src/cmd/link/internal/ld/lib.go` の変更

このファイルでは、`loadlib()` 関数内でモジュールデータシンボルの初期化ロジックが大幅に変更されました。

```go
	moduledata := Linklookup(Ctxt, "runtime.firstmoduledata", 0)
	if moduledata.Type == 0 || moduledata.Type == obj.SDYNIMPORT {
		// If the module we are linking does not define the
		// runtime.firstmoduledata symbol, create a local symbol for
		// the moduledata.
		moduledata = Linklookup(Ctxt, "local.moduledata", 0)
		moduledata.Local = true
	} else {
		// If OTOH the module does define the symbol, we truncate the
		// symbol back to 0 bytes so we can define its entire
		// contents.
		moduledata.Size = 0
	}
	// Either way we mark it as noptrdata to hide it from the GC.
	moduledata.Type = obj.SNOPTRDATA
	moduledata.Reachable = true
	Ctxt.Moduledata = moduledata
```
このコードブロックは、`runtime.firstmoduledata` シンボルが現在のモジュールによって定義されているかどうかをチェックします。
*   もし定義されていない（`Type == 0`）か、動的にインポートされるシンボル（`obj.SDYNIMPORT`）である場合、リンカは `local.moduledata` という新しいローカルシンボルを作成します。これにより、リンカが生成するモジュールデータは、外部から参照される `runtime.firstmoduledata` とは異なる、完全にローカルなエンティティとして扱われます。
*   もし `runtime.firstmoduledata` が既に定義されている場合（つまり、現在のモジュールがそれを提供している場合）、そのシンボルの `Size` を0に設定します。これは、リンカがそのシンボルの内容を最初から構築し直すことを可能にするためです。
*   最終的に、どちらのケースでも、選択された `moduledata` シンボルは `obj.SNOPTRDATA` タイプに設定され、ガベージコレクタから隠蔽されます。また、`Reachable` フラグが `true` に設定され、このシンボルが最終的なバイナリに含まれることを保証します。そして、このシンボルが `Ctxt.Moduledata` に格納され、リンカの他の部分からアクセス可能になります。

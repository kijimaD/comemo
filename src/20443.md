# [インデックス 20443] ファイルの概要

このコミットは、GoランタイムにおけるWindows環境でのシグナルハンドラ（`sighandler`）の実行スタックを変更するものです。具体的には、これまで通常のゴルーチンスタック（`g`スタック）の底で実行されていたシグナルハンドラを、Goランタイム専用のスタックである`g0`スタックで実行するように修正しています。これにより、スタックの安全性と安定性が向上し、関連する複雑なコードの削除が可能になります。

## 元コミット内容

このコミットの目的は、Windows環境におけるGoランタイムのシグナルハンドラ（`sighandler`）の実行場所を、現在のゴルーチンスタックから`g0`スタックへ移行することです。

コミットメッセージによると、これまでのシグナルハンドラは、現在実行中のゴルーチンスタックの最下部で実行されていました。しかし、このハンドラはC言語で書かれており、通常のゴルーチンスタック上にC言語のコードが存在することは望ましくありませんでした。さらに、シグナルハンドラは多くの処理を行うため、より多くのスタック領域を必要とする可能性がありました。

特に問題となっていたのは、`traceback_windows.go`というファイルに記述されていた、シグナルハンドラ実行中のスタック分割に関する「恐ろしい」コードの存在です。スタック分割は、ゴルーチンのスタックが不足した際に動的に拡張するGoのメカニズムですが、シグナルハンドラのような低レベルかつ非同期的な処理中に発生すると、複雑な問題を引き起こす可能性がありました。

この変更により、シグナルハンドラを`g0`スタックで実行することで、スタック分割の可能性を排除し、`traceback_windows.go`のコードを完全に削除できる見込みがありました。これは、ランタイムの安定性と保守性の向上に寄与する「Win-Win」の状況であると述べられています。

ビルドテストでは、`GOARCH=amd64`で全てのテストがパスし、`GOARCH=386`でもDLLローディングに関する無関係と思われるテストを除いて大部分がパスしたと報告されています。これにより、Windowsビルドの問題が修正されることが期待されました。

## 変更の背景

Goランタイムは、軽量な並行処理単位であるゴルーチンを管理します。各ゴルーチンは独自のスタックを持ち、必要に応じてスタックを動的に拡張する「スタック分割（stack split）」というメカニズムを備えています。しかし、シグナルハンドラのようなOSからの非同期イベントを処理するコードは、非常に低レベルであり、通常のGoコードとは異なる特性を持ちます。

Windows環境におけるGoのシグナルハンドラはC言語で実装されており、これが通常のゴルーチンスタック上で実行されることにはいくつかの問題がありました。

1.  **CコードとGoスタックの混在**: GoのスタックはGoランタイムによって厳密に管理されており、C言語のコードが直接Goのスタックを操作することは、予期せぬ動作やバグの原因となる可能性がありました。Goのガベージコレクタやスタックウォーカーは、Goのスタックフレーム構造を前提としているため、Cコードが介在するとその前提が崩れる恐れがありました。
2.  **スタック領域の不足とスタック分割**: シグナルハンドラは、OSからの割り込みによって非同期に実行されるため、その実行中に現在のゴルーチンスタックが不足し、スタック分割が発生する可能性がありました。コミットメッセージにある「`traceback_windows.go`に記述された恐ろしいコード」は、まさにこの問題に対処するための複雑なロジックを示唆しています。シグナルハンドラのようなクリティカルな処理中にスタック分割が発生すると、デッドロック、クラッシュ、または不正な状態に陥るリスクが高まります。
3.  **デバッグとトレースの複雑化**: シグナルハンドラが通常のゴルーチンスタック上で実行されると、スタックトレースの解析が複雑になることがあります。特に、CコードとGoコードが混在するスタックトレースは、問題の特定を困難にします。

これらの問題を解決し、Goランタイムの堅牢性と保守性を向上させるために、シグナルハンドラをGoランタイム専用の`g0`スタックで実行するという変更が提案されました。`g0`スタックは、Goランタイムの内部処理やシステムコール、Cgoコールバックなどのために予約されたスタックであり、通常のゴルーチンスタックとは独立して管理されます。これにより、シグナルハンドラの実行がGoのスタック管理メカニズムから切り離され、より安全かつ予測可能な動作が期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとOSの基本的な概念を理解しておく必要があります。

### 1. Goのゴルーチンとスタック管理

*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。Goランタイムがゴルーチンのスケジューリング、スタック管理、同期などを担当します。
*   **スタック (Stack)**: 各ゴルーチンは独自のスタックを持ち、関数呼び出しの引数、ローカル変数、リターンアドレスなどが格納されます。Goのスタックは比較的小さなサイズ（初期は数KB）で開始され、必要に応じて動的に拡張されます。
*   **スタック分割 (Stack Split)**: Goのスタックは、関数呼び出し時にスタックが不足しそうになると、より大きなスタックを割り当てて内容をコピーし、新しいスタックに切り替えることで自動的に拡張されます。このプロセスをスタック分割と呼びます。これにより、Goプログラムはスタックオーバーフローを気にすることなく、深い再帰呼び出しなどを行うことができます。
*   **`g0`スタック (System Stack / Master Goroutine Stack)**: Goランタイムには、通常のゴルーチンスタックとは別に、`g0`と呼ばれる特別なスタックが存在します。これは、Goランタイム自身の内部処理、システムコール、Cgo（C言語との相互運用）コールバック、およびOSからのシグナルハンドリングなどの、低レベルでクリティカルな処理のために使用されます。`g0`スタックは、通常のゴルーチンスタックのように動的に拡張されることはなく、固定サイズで確保されます。

### 2. シグナルハンドリング

*   **シグナル (Signal)**: オペレーティングシステムがプロセスに対して送信する、非同期のイベント通知メカニズムです。例えば、Ctrl+Cによるプログラム終了（SIGINT）、不正なメモリアクセス（SIGSEGV）、タイマーの満了（SIGALRM）などがあります。
*   **シグナルハンドラ (Signal Handler)**: シグナルを受信した際に実行される特別な関数です。シグナルハンドラは、通常のプログラムの実行フローとは独立して、非同期に割り込んで実行されます。そのため、シグナルハンドラ内で実行されるコードは、再入可能性（reentrancy）や、グローバルな状態へのアクセス、スタックの使用量などに細心の注意を払う必要があります。
*   **Windowsにおけるシグナルハンドリング**: Windowsでは、Unix/Linuxのようなシグナルとは異なる「構造化例外処理（Structured Exception Handling, SEH）」や「コンソール制御ハンドラ（Console Control Handler）」などのメカニズムがシグナルに相当する機能を提供します。Goランタイムは、これらのWindows固有のメカニズムを捕捉し、Goの内部的なシグナルとして処理します。このコミットで言及されている`sighandler`は、これらのWindows例外をGoランタイムが処理するためのエントリポイントです。

### 3. アセンブリ言語とスタックポインタ

*   **アセンブリ言語 (.sファイル)**: Goランタイムの低レベルな部分は、Go言語だけでなく、アセンブリ言語（特にPlan 9アセンブリ）で記述されています。これは、OSとのインタフェース、コンテキストスイッチ、スタック操作など、Go言語では直接制御できない部分を実装するためです。
*   **スタックポインタ (Stack Pointer, SP)**: CPUのレジスタの一つで、現在のスタックの最上部（または最下部、アーキテクチャによる）のアドレスを指します。関数呼び出しやローカル変数の割り当てに伴い、SPは増減します。
*   **`MOVL` / `MOVQ`**: アセンブリ命令で、データを移動（Move）する命令です。`MOVL`は32ビット（Long）データを、`MOVQ`は64ビット（Quad）データを扱います。
*   **`SUBL` / `SUBQ`**: アセンブリ命令で、減算（Subtract）する命令です。スタックフレームを確保するためにスタックポインタを減らす際などに使用されます。
*   **`ADDL` / `ADDQ`**: アセンブリ命令で、加算（Add）する命令です。スタックフレームを解放するためにスタックポインタを増やす際などに使用されます。
*   **`JEQ` / `JNE`**: アセンブリ命令で、条件付きジャンプ（Jump if Equal / Jump if Not Equal）です。比較結果に基づいてプログラムの実行フローを変更します。
*   **`get_tls(reg)`**: Goランタイムのアセンブリコードでよく見られるマクロで、現在のスレッドローカルストレージ（TLS）から現在のゴルーチン（`g`）へのポインタを取得します。

これらの知識は、コミットの変更内容、特にアセンブリコードの変更が何を意味するのかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的な核心は、Windows環境におけるGoランタイムのシグナルハンドラ`runtime·sigtramp`が、通常のゴルーチンスタック（`g`スタック）から`g0`スタックへ切り替えて実行されるように変更された点です。これは、`src/runtime/sys_windows_386.s`と`src/runtime/sys_windows_amd64.s`の2つのアセンブリファイルにわたる変更によって実現されています。

変更の主なロジックは以下の通りです。

1.  **スタック領域の確保**: `runtime·sigtramp`関数の冒頭で、スタックポインタ（SP）を減算して、必要なローカル変数やレジスタ保存のためのスタック領域を確保します。
    *   386アーキテクチャ (`sys_windows_386.s`): `SUBL $32, SP` が `SUBL $40, SP` に変更され、8バイト追加で確保されます。
    *   AMD64アーキテクチャ (`sys_windows_amd64.s`): `SUBQ $96, SP` が `SUBQ $112, SP` に変更され、16バイト追加で確保されます。
    この追加領域は、`g`ポインタと元のスタックポインタを保存するために使用されます。

2.  **現在のゴルーチン (`g`) の特定**: `get_tls`マクロを使用して、現在のスレッドローカルストレージから現在のゴルーチン（`g`）へのポインタを取得します。

3.  **`g0`スタックへの切り替え判定**:
    *   現在のゴルーチンが既に`g0`であるかどうかを判定します。`g_m(DX)`で現在のゴルーチンが属するM（マシン、OSスレッド）を取得し、そのMの`m_g0`フィールドから`g0`ゴルーチンへのポインタを取得します。
    *   現在のゴルーチン（`DX`）と`g0`ゴルーチン（`BX`）を比較し、`JEQ sigtramp_g0`で、もし既に`g0`スタック上にいる場合はスタック切り替えをスキップして`sigtramp_g0`ラベルへジャンプします。

4.  **`g0`スタックへの切り替え処理**:
    *   現在のゴルーチン（`DX`）とスタックポインタ（`SP`）を、新しく確保したスタック領域に保存します。これは、シグナルハンドラの処理が完了した後に元のスタックに戻るために必要です。
        *   386: `MOVL DX, 32(SP)` (g), `MOVL SP, 36(SP)` (old SP)
        *   AMD64: `MOVQ DX, 96(SP)` (g), `MOVQ SP, 104(SP)` (old SP)
    *   `get_tls(BP)`でTLSポインタを再度取得し、`MOVL BX, g(BP)` (386) / `MOVQ BX, g(BP)` (AMD64) で、現在のスレッドのゴルーチンを`g0`に設定します。これにより、Goランタイムの内部状態が`g0`スタックで実行されていることを反映します。
    *   `g0`スタックの現在のスタックポインタを取得します: `MOVL (g_sched+gobuf_sp)(BX), DI` (386) / `MOVQ (g_sched+gobuf_sp)(BX), DI` (AMD64)。ここで`g_sched`はゴルーチンのスケジューラ関連の情報を保持する構造体、`gobuf_sp`はその中のスタックポインタを指すフィールドです。
    *   **トレースバックの調整**: `runtime·mstart`を呼び出し元に見せかけることで、トレースバックがシグナルハンドラ内でスタック分割を試みないようにします。これは、`g0`スタックへの切り替えが、あたかも`mstart`関数から呼び出されたかのように見せかけることで、Goのスタックトレース機構が混乱しないようにするためのトリックです。
        *   386: `SUBL $4, DI`, `MOVL $runtime·mstart(SB), 0(DI)`
        *   AMD64: `SUBQ $8, DI`, `MOVQ $runtime·mstart(SB), SI`, `MOVQ SI, 0(DI)`
    *   `g0`スタックのスタックポインタをさらに減算し、シグナルハンドラの引数やレジスタ保存のための領域を確保します。この減算量は、元のスタックで確保した領域と一致するように調整されます。
        *   386: `SUBL $40, DI`
        *   AMD64: `SUBQ $(112+8), DI`
    *   `MOVL SP, 36(DI)` (386) / `MOVQ SP, 104(DI)` (AMD64) で、元のスタックポインタを`g0`スタックの適切な位置に保存します。
    *   `MOVL DI, SP` (386) / `MOVQ DI, SP` (AMD64) で、現在のスタックポインタを`g0`スタックのポインタに切り替えます。

5.  **シグナルハンドラの実行**: `sigtramp_g0`ラベルに到達した後、Windowsの例外レコードとコンテキストポインタをレジスタにロードし、`runtime·sighandler`関数を呼び出します。この`sighandler`は、Goランタイムが提供する実際のシグナル処理ロジックです。

6.  **元のスタックへの復帰**:
    *   シグナルハンドラの処理が完了した後、`MOVQ 104(SP), SP` (AMD64) / `MOVL 36(SP), SP` (386) で、保存しておいた元のスタックポインタを復元し、元のゴルーチンスタックに戻ります。
    *   `MOVQ 96(SP), DX` (AMD64) / `MOVL 32(SP), DX` (386) で、保存しておいた元のゴルーチン（`g`）ポインタを復元します。
    *   `get_tls(BP)`でTLSポインタを再度取得し、`MOVQ DX, g(BP)` (AMD64) / `MOVL DX, g(BP)` (386) で、現在のスレッドのゴルーチンを元のゴルーチンに戻します。

7.  **レジスタの復元とリターン**: 最後に、保存しておいたカリ―セーブドレジスタ（呼び出し先で保存・復元すべきレジスタ）を復元し、`ADDL $40, SP` (386) / `ADDQ $112, SP` (AMD64) でスタック領域を解放して、`RET`命令で呼び出し元に戻ります。

この一連の処理により、シグナルハンドラは一時的に`g0`スタックに切り替えて実行され、処理が完了すると元のゴルーチンスタックに戻るという、安全かつ透過的なメカニズムが実現されています。これにより、通常のゴルーチンスタック上でのCコードの実行や、シグナルハンドラ中のスタック分割といった問題が回避されます。

## コアとなるコードの解説

上記の変更箇所を基に、`runtime·sigtramp`関数における`g0`スタックへの切り替えロジックを詳細に解説します。

### 1. スタックフレームの準備とレジスタの保存

関数冒頭で、`SUBL`または`SUBQ`命令によりスタックポインタ（SP）を減算し、シグナルハンドラ内で使用するローカル変数や、呼び出し元（Windows）のコンテキストを保存するための領域を確保します。このコミットでは、元のスタックポインタと現在のゴルーチン（`g`）へのポインタを保存するために、追加の領域が確保されています。

### 2. 現在のゴルーチン (`g`) の取得

`get_tls(DX)`命令は、現在のOSスレッドに紐付けられたスレッドローカルストレージ（TLS）から、現在実行中のゴルーチン（`g`）のポインタを`DX`レジスタにロードします。Goランタイムは、各OSスレッドがどのゴルーチンを実行しているかをTLSを通じて管理しています。

### 3. `g0`スタックへの切り替え判定

```assembly
	// save g and SP in case of stack switch
	MOVL	DX, 32(SP)	// g (386) / MOVQ DX, 96(SP) // g (AMD64)
	MOVL	SP, 36(SP)  // old SP (386) / MOVQ SP, 104(SP) (AMD64)

	// do we need to switch to the g0 stack?
	MOVL	g_m(DX), BX   // Get M from current g
	MOVL	m_g0(BX), BX  // Get g0 from M
	CMPL	DX, BX        // Compare current g with g0
	JEQ	sigtramp_g0   // If current g is g0, jump to sigtramp_g0
```
ここでは、まず現在のゴルーチン（`DX`）と現在のスタックポインタ（`SP`）を、新しく確保したスタック領域に保存します。これは、シグナルハンドラの処理が完了した後に元のゴルーチンとスタックに戻るために不可欠です。

次に、現在のゴルーチンが既に`g0`スタック上で実行されているかどうかをチェックします。
*   `g_m(DX), BX`: 現在のゴルーチン`DX`から、それが属するM（Machine、OSスレッド）の構造体へのポインタを`BX`にロードします。
*   `m_g0(BX), BX`: そのMの構造体から、そのMに紐付けられた`g0`ゴルーチンへのポインタを`BX`にロードします。
*   `CMPL DX, BX` (386) / `CMPQ DX, BX` (AMD64): 現在のゴルーチン`DX`と、そのMの`g0`ゴルーチン`BX`を比較します。
*   `JEQ sigtramp_g0`: もし両者が等しければ（つまり、既に`g0`スタック上で実行されている場合）、スタック切り替えのロジックをスキップして`sigtramp_g0`ラベルへジャンプします。

### 4. `g0`スタックへの切り替え実行

現在のゴルーチンが`g0`でない場合、以下のスタック切り替え処理が実行されます。

```assembly
	// switch to the g0 stack
	get_tls(BP)           // Get TLS pointer
	MOVL	BX, g(BP)     // Set current g to g0 (BX holds g0)
	MOVL	(g_sched+gobuf_sp)(BX), DI // Get g0's stack pointer
	// make it look like mstart called us on g0, to stop traceback
	SUBL	$4, DI        // Adjust g0's stack pointer for fake return address
	MOVL	$runtime·mstart(SB), 0(DI) // Place fake return address (runtime·mstart)
	// traceback will think that we've done SUBL
	// on this stack, so subtract them here to match.
	// (we need room for sighandler arguments anyway).
	// and re-save old SP for restoring later.
	SUBL	$40, DI       // Further adjust g0's stack pointer for sighandler frame
	MOVL	SP, 36(DI)    // Save original SP on g0's stack
	MOVL	DI, SP        // Switch SP to g0's stack
```
*   `MOVL BX, g(BP)` (386) / `MOVQ BX, g(BP)` (AMD64): 現在のOSスレッドのTLSに、現在実行中のゴルーチンが`g0`であると設定します。これにより、Goランタイムの内部状態が`g0`スタックで実行されていることを認識します。
*   `MOVL (g_sched+gobuf_sp)(BX), DI` (386) / `MOVQ (g_sched+gobuf_sp)(BX), DI` (AMD64): `g0`ゴルーチン（`BX`）のスケジューラ情報（`g_sched`）から、そのスタックポインタ（`gobuf_sp`）を取得し、`DI`レジスタにロードします。これが`g0`スタックの現在のトップになります。
*   **トレースバックのトリック**: `SUBL $4, DI` (386) / `SUBQ $8, DI` (AMD64) で`g0`スタックポインタを少し減らし、その位置に`runtime·mstart`関数のアドレスを書き込みます。これは、Goのスタックトレース機構が、シグナルハンドラが`runtime·mstart`から呼び出されたかのように誤認させるためのものです。これにより、シグナルハンドラ実行中にスタックトレースが試みられた際に、通常のゴルーチンスタックのスタック分割ロジックが発動するのを防ぎます。
*   `SUBL $40, DI` (386) / `SUBQ $(112+8), DI` (AMD64): シグナルハンドラの引数やレジスタ保存のための領域を確保するために、`g0`スタックポインタをさらに減算します。この減算量は、元のスタックで確保した領域と一致するように調整されます。
*   `MOVL SP, 36(DI)` (386) / `MOVQ SP, 104(DI)` (AMD64): 元のスタックポインタ（`SP`）を、`g0`スタックの適切な位置に保存します。
*   `MOVL DI, SP` (386) / `MOVQ DI, SP` (AMD64): 最後に、CPUのスタックポインタレジスタ（`SP`）を、`g0`スタックのポインタ（`DI`）に切り替えます。これにより、以降の命令は`g0`スタック上で実行されるようになります。

### 5. シグナルハンドラの呼び出し

`sigtramp_g0`ラベルに到達すると、Windowsから渡された例外レコードとコンテキストポインタをレジスタにロードし、Goランタイムの実際のシグナル処理関数である`runtime·sighandler`を呼び出します。この`sighandler`は、`g0`スタック上で安全に実行されます。

### 6. 元のスタックへの復帰

`runtime·sighandler`の実行が完了し、`runtime·sigtramp`に戻ってきた後、以下のロジックで元のゴルーチンスタックに復帰します。

```assembly
	// switch back to original stack and g
	// no-op if we never left.
	MOVL	36(SP), SP    // Restore original SP (386) / MOVQ 104(SP), SP (AMD64)
	MOVL	32(SP), DX    // Restore original g (386) / MOVQ 96(SP), DX (AMD64)
	get_tls(BP)           // Get TLS pointer
	MOVL	DX, g(BP)     // Set current g back to original g
```
*   `MOVL 36(SP), SP` (386) / `MOVQ 104(SP), SP` (AMD64): シグナルハンドラに入る前に保存しておいた元のスタックポインタを、CPUの`SP`レジスタに復元します。これにより、実行コンテキストが元のゴルーチンスタックに戻ります。
*   `MOVL 32(SP), DX` (386) / `MOVQ 96(SP), DX` (AMD64): 同様に、保存しておいた元のゴルーチン（`g`）ポインタを`DX`レジスタにロードします。
*   `MOVL DX, g(BP)` (386) / `MOVQ DX, g(BP)` (AMD64): 現在のOSスレッドのTLSに、現在実行中のゴルーチンが元のゴルーチンであると設定し直します。

この一連のスタック切り替えと復帰のロジックにより、シグナルハンドラは`g0`スタックという隔離された安全な環境で実行され、Goランタイムの安定性と堅牢性が向上します。

## 変更の背景

Goランタイムは、軽量な並行処理単位であるゴルーチンを管理します。各ゴルーチンは独自のスタックを持ち、必要に応じてスタックを動的に拡張する「スタック分割（stack split）」というメカニズムを備えています。しかし、シグナルハンドラのようなOSからの非同期イベントを処理するコードは、非常に低レベルであり、通常のGoコードとは異なる特性を持ちます。

Windows環境におけるGoのシグナルハンドラはC言語で実装されており、これが通常のゴルーチンスタック上で実行されることにはいくつかの問題がありました。

1.  **CコードとGoスタックの混在**: GoのスタックはGoランタイムによって厳密に管理されており、C言語のコードが直接Goのスタックを操作することは、予期せぬ動作やバグの原因となる可能性がありました。Goのガベージコレクタやスタックウォーカーは、Goのスタックフレーム構造を前提としているため、Cコードが介在するとその前提が崩れる恐れがありました。
2.  **スタック領域の不足とスタック分割**: シグナルハンドラは、OSからの割り込みによって非同期に実行されるため、その実行中に現在のゴルーチンスタックが不足し、スタック分割が発生する可能性がありました。コミットメッセージにある「`traceback_windows.go`に記述された恐ろしいコード」は、まさにこの問題に対処するための複雑なロジックを示唆しています。シグナルハンドラのようなクリティカルな処理中にスタック分割が発生すると、デッドロック、クラッシュ、または不正な状態に陥るリスクが高まります。
3.  **デバッグとトレースの複雑化**: シグナルハンドラが通常のゴルーチンスタック上で実行されると、スタックトレースの解析が複雑になることがあります。特に、CコードとGoコードが混在するスタックトレースは、問題の特定を困難にします。

これらの問題を解決し、Goランタイムの堅牢性と保守性を向上させるために、シグナルハンドラをGoランタイム専用の`g0`スタックで実行するという変更が提案されました。`g0`スタックは、Goランタイムの内部処理やシステムコール、Cgoコールバックなどのために予約されたスタックであり、通常のゴルーチンスタックとは独立して管理されます。これにより、シグナルハンドラの実行がGoのスタック管理メカニズムから切り離され、より安全かつ予測可能な動作が期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとOSの基本的な概念を理解しておく必要があります。

### 1. Goのゴルーチンとスタック管理

*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。Goランタイムがゴルーチンのスケジューリング、スタック管理、同期などを担当します。
*   **スタック (Stack)**: 各ゴルーチンは独自のスタックを持ち、関数呼び出しの引数、ローカル変数、リターンアドレスなどが格納されます。Goのスタックは比較的小さなサイズ（初期は数KB）で開始され、必要に応じて動的に拡張されます。
*   **スタック分割 (Stack Split)**: Goのスタックは、関数呼び出し時にスタックが不足しそうになると、より大きなスタックを割り当てて内容をコピーし、新しいスタックに切り替えることで自動的に拡張されます。このプロセスをスタック分割と呼びます。これにより、Goプログラムはスタックオーバーフローを気にすることなく、深い再帰呼び出しなどを行うことができます。
*   **`g0`スタック (System Stack / Master Goroutine Stack)**: Goランタイムには、通常のゴルーチンスタックとは別に、`g0`と呼ばれる特別なスタックが存在します。これは、Goランタイム自身の内部処理、システムコール、Cgo（C言語との相互運用）コールバック、およびOSからのシグナルハンドリングなどの、低レベルでクリティカルな処理のために使用されます。`g0`スタックは、通常のゴルーチンスタックのように動的に拡張されることはなく、固定サイズで確保されます。

### 2. シグナルハンドリング

*   **シグナル (Signal)**: オペレーティングシステムがプロセスに対して送信する、非同期のイベント通知メカニズムです。例えば、Ctrl+Cによるプログラム終了（SIGINT）、不正なメモリアクセス（SIGSEGV）、タイマーの満了（SIGALRM）などがあります。
*   **シグナルハンドラ (Signal Handler)**: シグナルを受信した際に実行される特別な関数です。シグナルハンドラは、通常のプログラムの実行フローとは独立して、非同期に割り込んで実行されます。そのため、シグナルハンドラ内で実行されるコードは、再入可能性（reentrancy）や、グローバルな状態へのアクセス、スタックの使用量などに細心の注意を払う必要があります。
*   **Windowsにおけるシグナルハンドリング**: Windowsでは、Unix/Linuxのようなシグナルとは異なる「構造化例外処理（Structured Exception Handling, SEH）」や「コンソール制御ハンドラ（Console Control Handler）」などのメカニズムがシグナルに相当する機能を提供します。Goランタイムは、これらのWindows固有のメカニズムを捕捉し、Goの内部的なシグナルとして処理します。このコミットで言及されている`sighandler`は、これらのWindows例外をGoランタイムが処理するためのエントリポイントです。

### 3. アセンブリ言語とスタックポインタ

*   **アセンブリ言語 (.sファイル)**: Goランタイムの低レベルな部分は、Go言語だけでなく、アセンブリ言語（特にPlan 9アセンブリ）で記述されています。これは、OSとのインタフェース、コンテキストスイッチ、スタック操作など、Go言語では直接制御できない部分を実装するためです。
*   **スタックポインタ (Stack Pointer, SP)**: CPUのレジスタの一つで、現在のスタックの最上部（または最下部、アーキテクチャによる）のアドレスを指します。関数呼び出しやローカル変数の割り当てに伴い、SPは増減します。
*   **`MOVL` / `MOVQ`**: アセンブリ命令で、データを移動（Move）する命令です。`MOVL`は32ビット（Long）データを、`MOVQ`は64ビット（Quad）データを扱います。
*   **`SUBL` / `SUBQ`**: アセンブリ命令で、減算（Subtract）する命令です。スタックフレームを確保するためにスタックポインタを減らす際などに使用されます。
*   **`ADDL` / `ADDQ`**: アセンブリ命令で、加算（Add）する命令です。スタックフレームを解放するためにスタックポインタを増やす際などに使用されます。
*   **`JEQ` / `JNE`**: アセンブリ命令で、条件付きジャンプ（Jump if Equal / Jump if Not Equal）です。比較結果に基づいてプログラムの実行フローを変更します。
*   **`get_tls(reg)`**: Goランタイムのアセンブリコードでよく見られるマクロで、現在のスレッドローカルストレージ（TLS）から現在のゴルーチン（`g`）へのポインタを取得します。

これらの知識は、コミットの変更内容、特にアセンブリコードの変更が何を意味するのかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的な核心は、Windows環境におけるGoランタイムのシグナルハンドラ`runtime·sigtramp`が、通常のゴルーチンスタック（`g`スタック）から`g0`スタックへ切り替えて実行されるように変更された点です。これは、`src/runtime/sys_windows_386.s`と`src/runtime/sys_windows_amd64.s`の2つのアセンブリファイルにわたる変更によって実現されています。

変更の主なロジックは以下の通りです。

1.  **スタック領域の確保**: `runtime·sigtramp`関数の冒頭で、スタックポインタ（SP）を減算して、必要なローカル変数やレジスタ保存のためのスタック領域を確保します。
    *   386アーキテクチャ (`sys_windows_386.s`): `SUBL $32, SP` が `SUBL $40, SP` に変更され、8バイト追加で確保されます。
    *   AMD64アーキテクチャ (`sys_windows_amd64.s`): `SUBQ $96, SP` が `SUBQ $112, SP` に変更され、16バイト追加で確保されます。
    この追加領域は、`g`ポインタと元のスタックポインタを保存するために使用されます。

2.  **現在のゴルーチン (`g`) の特定**: `get_tls`マクロを使用して、現在のスレッドローカルストレージから現在のゴルーチン（`g`）へのポインタを取得します。

3.  **`g0`スタックへの切り替え判定**:
    *   現在のゴルーチンが既に`g0`であるかどうかを判定します。`g_m(DX)`で現在のゴルーチンが属するM（マシン、OSスレッド）を取得し、そのMの`m_g0`フィールドから`g0`ゴルーチンへのポインタを取得します。
    *   現在のゴルーチン（`DX`）と`g0`ゴルーチン（`BX`）を比較し、`JEQ sigtramp_g0`で、もし既に`g0`スタック上にいる場合はスタック切り替えをスキップして`sigtramp_g0`ラベルへジャンプします。

4.  **`g0`スタックへの切り替え処理**:
    *   現在のゴルーチン（`DX`）とスタックポインタ（`SP`）を、新しく確保したスタック領域に保存します。これは、シグナルハンドラの処理が完了した後に元のスタックに戻るために必要です。
        *   386: `MOVL DX, 32(SP)` (g), `MOVL SP, 36(SP)` (old SP)
        *   AMD64: `MOVQ DX, 96(SP)` (g), `MOVQ SP, 104(SP)` (old SP)
    *   `get_tls(BP)`でTLSポインタを再度取得し、`MOVL BX, g(BP)` (386) / `MOVQ BX, g(BP)` (AMD64) で、現在のスレッドのゴルーチンを`g0`に設定します。これにより、Goランタイムの内部状態が`g0`スタックで実行されていることを反映します。
    *   `g0`スタックの現在のスタックポインタを取得します: `MOVL (g_sched+gobuf_sp)(BX), DI` (386) / `MOVQ (g_sched+gobuf_sp)(BX), DI` (AMD64)。ここで`g_sched`はゴルーチンのスケジューラ関連の情報を保持する構造体、`gobuf_sp`はその中のスタックポインタを指すフィールドです。
    *   **トレースバックの調整**: `runtime·mstart`を呼び出し元に見せかけることで、トレースバックがシグナルハンドラ内でスタック分割を試みないようにします。これは、`g0`スタックへの切り替えが、あたかも`mstart`関数から呼び出されたかのように見せかけることで、Goのスタックトレース機構が混乱しないようにするためのトリックです。
        *   386: `SUBL $4, DI`, `MOVL $runtime·mstart(SB), 0(DI)`
        *   AMD64: `SUBQ $8, DI`, `MOVQ $runtime·mstart(SB), SI`, `MOVQ SI, 0(DI)`
    *   `g0`スタックのスタックポインタをさらに減算し、シグナルハンドラの引数やレジスタ保存のための領域を確保します。この減算量は、元のスタックで確保した領域と一致するように調整されます。
        *   386: `SUBL $40, DI`
        *   AMD64: `SUBQ $(112+8), DI`
    *   `MOVL SP, 36(DI)` (386) / `MOVQ SP, 104(DI)` (AMD64) で、元のスタックポインタを`g0`スタックの適切な位置に保存します。
    *   `MOVL DI, SP` (386) / `MOVQ DI, SP` (AMD64) で、現在のスタックポインタを`g0`スタックのポインタに切り替えます。

5.  **シグナルハンドラの実行**: `sigtramp_g0`ラベルに到達した後、Windowsの例外レコードとコンテキストポインタをレジスタにロードし、`runtime·sighandler`関数を呼び出します。この`sighandler`は、Goランタイムが提供する実際のシグナル処理ロジックです。

6.  **元のスタックへの復帰**:
    *   シグナルハンドラの処理が完了した後、`MOVQ 104(SP), SP` (AMD64) / `MOVL 36(SP), SP` (386) で、保存しておいた元のスタックポインタを復元し、元のゴルーチンスタックに戻ります。
    *   `MOVQ 96(SP), DX` (AMD64) / `MOVL 32(SP), DX` (386) で、保存しておいた元のゴルーチン（`g`）ポインタを復元します。
    *   `get_tls(BP)`でTLSポインタを再度取得し、`MOVQ DX, g(BP)` (AMD64) / `MOVL DX, g(BP)` (386) で、現在のスレッドのゴルーチンを元のゴルーチンに戻します。

7.  **レジスタの復元とリターン**: 最後に、保存しておいたカリ―セーブドレジスタ（呼び出し先で保存・復元すべきレジスタ）を復元し、`ADDL $40, SP` (386) / `ADDQ $112, SP` (AMD64) でスタック領域を解放して、`RET`命令で呼び出し元に戻ります。

この一連の処理により、シグナルハンドラは一時的に`g0`スタックに切り替えて実行され、処理が完了すると元のゴルーチンスタックに戻るという、安全かつ透過的なメカニズムが実現されています。これにより、通常のゴルーチンスタック上でのCコードの実行や、シグナルハンドラ中のスタック分割といった問題が回避されます。

## コアとなるコードの解説

上記の変更箇所を基に、`runtime·sigtramp`関数における`g0`スタックへの切り替えロジックを詳細に解説します。

### 1. スタックフレームの準備とレジスタの保存

関数冒頭で、`SUBL`または`SUBQ`命令によりスタックポインタ（SP）を減算し、シグナルハンドラ内で使用するローカル変数や、呼び出し元（Windows）のコンテキストを保存するための領域を確保します。このコミットでは、元のスタックポインタと現在のゴルーチン（`g`）へのポインタを保存するために、追加の領域が確保されています。

### 2. 現在のゴルーチン (`g`) の取得

`get_tls(DX)`命令は、現在のOSスレッドに紐付けられたスレッドローカルストレージ（TLS）から、現在実行中のゴルーチン（`g`）のポインタを`DX`レジスタにロードします。Goランタイムは、各OSスレッドがどのゴルーチンを実行しているかをTLSを通じて管理しています。

### 3. `g0`スタックへの切り替え判定

```assembly
	// save g and SP in case of stack switch
	MOVL	DX, 32(SP)	// g (386) / MOVQ DX, 96(SP) // g (AMD64)
	MOVL	SP, 36(SP)  // old SP (386) / MOVQ SP, 104(SP) (AMD64)

	// do we need to switch to the g0 stack?
	MOVL	g_m(DX), BX   // Get M from current g
	MOVL	m_g0(BX), BX  // Get g0 from M
	CMPL	DX, BX        // Compare current g with g0
	JEQ	sigtramp_g0   // If current g is g0, jump to sigtramp_g0
```
ここでは、まず現在のゴルーチン（`DX`）と現在のスタックポインタ（`SP`）を、新しく確保したスタック領域に保存します。これは、シグナルハンドラの処理が完了した後に元のゴルーチンとスタックに戻るために不可欠です。

次に、現在のゴルーチンが既に`g0`スタック上で実行されているかどうかをチェックします。
*   `g_m(DX), BX`: 現在のゴルーチン`DX`から、それが属するM（Machine、OSスレッド）の構造体へのポインタを`BX`にロードします。
*   `m_g0(BX), BX`: そのMの構造体から、そのMに紐付けられた`g0`ゴルーチンへのポインタを`BX`にロードします。
*   `CMPL DX, BX` (386) / `CMPQ DX, BX` (AMD64): 現在のゴルーチン`DX`と、そのMの`g0`ゴルーチン`BX`を比較します。
*   `JEQ sigtramp_g0`: もし両者が等しければ（つまり、既に`g0`スタック上で実行されている場合）、スタック切り替えのロジックをスキップして`sigtramp_g0`ラベルへジャンプします。

### 4. `g0`スタックへの切り替え実行

現在のゴルーチンが`g0`でない場合、以下のスタック切り替え処理が実行されます。

```assembly
	// switch to the g0 stack
	get_tls(BP)           // Get TLS pointer
	MOVL	BX, g(BP)     // Set current g to g0 (BX holds g0)
	MOVL	(g_sched+gobuf_sp)(BX), DI // Get g0's stack pointer
	// make it look like mstart called us on g0, to stop traceback
	SUBL	$4, DI        // Adjust g0's stack pointer for fake return address
	MOVL	$runtime·mstart(SB), 0(DI) // Place fake return address (runtime·mstart)
	// traceback will think that we've done SUBL
	// on this stack, so subtract them here to match.
	// (we need room for sighandler arguments anyway).
	// and re-save old SP for restoring later.
	SUBL	$40, DI       // Further adjust g0's stack pointer for sighandler frame
	MOVL	SP, 36(DI)    // Save original SP on g0's stack
	MOVL	DI, SP        // Switch SP to g0's stack
```
*   `MOVL BX, g(BP)` (386) / `MOVQ BX, g(BP)` (AMD64): 現在のOSスレッドのTLSに、現在実行中のゴルーチンが`g0`であると設定します。これにより、Goランタイムの内部状態が`g0`スタックで実行されていることを認識します。
*   `MOVL (g_sched+gobuf_sp)(BX), DI` (386) / `MOVQ (g_sched+gobuf_sp)(BX), DI` (AMD64): `g0`ゴルーチン（`BX`）のスケジューラ情報（`g_sched`）から、そのスタックポインタ（`gobuf_sp`）を取得し、`DI`レジスタにロードします。これが`g0`スタックの現在のトップになります。
*   **トレースバックのトリック**: `SUBL $4, DI` (386) / `SUBQ $8, DI` (AMD64) で`g0`スタックポインタを少し減らし、その位置に`runtime·mstart`関数のアドレスを書き込みます。これは、Goのスタックトレース機構が、シグナルハンドラが`runtime·mstart`から呼び出されたかのように誤認させるためのものです。これにより、シグナルハンドラ実行中にスタックトレースが試みられた際に、通常のゴルーチンスタックのスタック分割ロジックが発動するのを防ぎます。
*   `SUBL $40, DI` (386) / `SUBQ $(112+8), DI` (AMD64): シグナルハンドラの引数やレジスタ保存のための領域を確保するために、`g0`スタックポインタをさらに減算します。この減算量は、元のスタックで確保した領域と一致するように調整されます。
*   `MOVL SP, 36(DI)` (386) / `MOVQ SP, 104(DI)` (AMD64): 元のスタックポインタ（`SP`）を、`g0`スタックの適切な位置に保存します。
*   `MOVL DI, SP` (386) / `MOVQ DI, SP` (AMD64): 最後に、CPUのスタックポインタレジスタ（`SP`）を、`g0`スタックのポインタ（`DI`）に切り替えます。これにより、以降の命令は`g0`スタック上で実行されるようになります。

### 5. シグナルハンドラの呼び出し

`sigtramp_g0`ラベルに到達すると、Windowsから渡された例外レコードとコンテキストポインタをレジスタにロードし、Goランタイムの実際のシグナル処理関数である`runtime·sighandler`を呼び出します。この`sighandler`は、`g0`スタック上で安全に実行されます。

### 6. 元のスタックへの復帰

`runtime·sighandler`の実行が完了し、`runtime·sigtramp`に戻ってきた後、以下のロジックで元のゴルーチンスタックに復帰します。

```assembly
	// switch back to original stack and g
	// no-op if we never left.
	MOVL	36(SP), SP    // Restore original SP (386) / MOVQ 104(SP), SP (AMD64)
	MOVL	32(SP), DX    // Restore original g (386) / MOVQ 96(SP), DX (AMD64)
	get_tls(BP)           // Get TLS pointer
	MOVL	DX, g(BP)     // Set current g back to original g
```
*   `MOVL 36(SP), SP` (386) / `MOVQ 104(SP), SP` (AMD64): シグナルハンドラに入る前に保存しておいた元のスタックポインタを、CPUの`SP`レジスタに復元します。これにより、実行コンテキストが元のゴルーチンスタックに戻ります。
*   `MOVL 32(SP), DX` (386) / `MOVQ 96(SP), DX` (AMD64): 同様に、保存しておいた元のゴルーチン（`g`）ポインタを`DX`レジスタにロードします。
*   `MOVL DX, g(BP)` (386) / `MOVQ DX, g(BP)` (AMD64): 現在のOSスレッドのTLSに、現在実行中のゴルーチンが元のゴルーチンであると設定し直します。

この一連のスタック切り替えと復帰のロジックにより、シグナルハンドラは`g0`スタックという隔離された安全な環境で実行され、Goランタイムの安定性と堅牢性が向上します。

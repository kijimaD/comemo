    crypto/tls: decouple handshake signatures from the handshake hash.
    
    Prior to TLS 1.2, the handshake had a pleasing property that one could
    incrementally hash it and, from that, get the needed hashes for both
    the CertificateVerify and Finished messages.
    
    TLS 1.2 introduced negotiation for the signature and hash and it became
    possible for the handshake hash to be, say, SHA-384, but for the
    CertificateVerify to sign the handshake with SHA-1. The problem is that
    one doesn't know in advance which hashes will be needed and thus the
    handshake needs to be buffered.
    
    Go ignored this, always kept a single handshake hash, and any signatures
    over the handshake had to use that hash.
    
    However, there are a set of servers that inspect the client's offered
    signature hash functions and will abort the handshake if one of the
    server's certificates is signed with a hash function outside of that
    set. https://robertsspaceindustries.com/ is an example of such a server.
    
    Clearly not a lot of thought happened when that server code was written,
    but its out there and we have to deal with it.
    
    This change decouples the handshake hash from the CertificateVerify
    hash. This lays the groundwork for advertising support for SHA-384 but
    doesn't actually make that change in the interests of reviewability.
    Updating the advertised hash functions will cause changes in many of the
    testdata/ files and some errors might get lost in the noise. This change
    only needs to update four testdata/ files: one because a SHA-384-based
    handshake is now being signed with SHA-256 and the others because the
    TLS 1.2 CertificateRequest message now includes SHA-1.
    
    This change also has the effect of adding support for
    client-certificates in SSLv3 servers. However, SSLv3 is now disabled by
    default so this should be moot.

    SHA-384 for the ServerKeyExchange as the SKX only signs over the nonces
    and SKX params (a design mistake in TLS). However, that would leave Go
    in the odd situation where it advertised support for SHA-384, but would
    only use the handshake hash when signing client certificates. I fear
    that'll just cause problems in the future.

## 元コミット内容

`crypto/tls: decouple handshake signatures from the handshake hash.`

このコミットは、TLSハンドシェイクにおける署名とハンドシェイクハッシュの間の結合を解消します。

## 変更の背景

TLS 1.2以前では、ハンドシェイクのハッシュは段階的に計算され、その結果から `CertificateVerify` および `Finished` メッセージに必要なハッシュを導出することができました。しかし、TLS 1.2では署名とハッシュのネゴシエーションが導入され、ハンドシェイクハッシュがSHA-384であるにもかかわらず、`CertificateVerify` がSHA-1でハンドシェイクに署名するといった状況が発生する可能性が出てきました。この問題は、事前にどのハッシュが必要になるか分からないため、ハンドシェイク全体をバッファリングする必要があるという点にあります。

GoのTLS実装はこれまでこの点を無視し、常に単一のハンドシェイクハッシュを保持し、ハンドシェイクに対するすべての署名はそのハッシュを使用する必要がありました。しかし、一部のサーバーはクライアントが提示する署名ハッシュ関数を検査し、サーバーの証明書がそのセット外のハッシュ関数で署名されている場合、ハンドシェイクを中断するという問題がありました（例: `https://robertsspaceindustries.com/`）。このようなサーバーのコードは設計が不十分であるものの、実際に存在するため、GoのTLS実装はこれに対応する必要がありました。

この変更は、`CertificateVerify` のハッシュからハンドシェイクハッシュを切り離すことで、この問題に対処します。これにより、SHA-384のサポートを宣伝するための基盤が築かれますが、このコミット自体ではその変更は行われていません。これは、テストデータファイルの変更が多岐にわたり、潜在的なエラーが見過ごされる可能性を避けるためです。このコミットでは、SHA-384ベースのハンドシェイクがSHA-256で署名されるようになったこと、およびTLS 1.2の `CertificateRequest` メッセージにSHA-1が含まれるようになったことに関連して、4つのテストデータファイルのみが更新されています。

また、この変更はSSLv3サーバーにおけるクライアント証明書のサポートを追加する効果もありますが、SSLv3は現在デフォルトで無効になっているため、この点は実質的な影響はありません。

コミットメッセージでは、`ServerKeyExchange` (SKX) の署名にSHA-384をサポートするだけでこの変更の多くを回避できる可能性についても言及されています。しかし、SKXはノンスとSKXパラメータのみに署名するため（TLSの設計上の誤り）、GoがSHA-384のサポートを宣伝しつつも、クライアント証明書の署名にのみハンドシェイクハッシュを使用するという奇妙な状況に陥ることを避けるため、このアプローチは採用されませんでした。これは将来的な問題を引き起こす可能性があると判断されたためです。

このコードの多くは、BoringSSLのテスト目的でdavidben@によって書かれたものです。

このコミットは、Issue #9757 に部分的に対応しています。

## 前提知識の解説

*   **TLS (Transport Layer Security)**: インターネット上でデータを安全にやり取りするための暗号化プロトコルです。ウェブブラウジング（HTTPS）などで広く利用されています。
*   **TLSハンドシェイク**: クライアントとサーバーが安全な通信チャネルを確立するために行う一連のメッセージ交換プロセスです。このプロセス中に、暗号スイートのネゴシエーション、鍵交換、認証などが行われます。
*   **ハンドシェイクハッシュ**: TLSハンドシェイク中に交換されるすべてのメッセージのハッシュ値です。このハッシュは、ハンドシェイクの整合性を保証し、`Finished` メッセージや `CertificateVerify` メッセージの計算に使用されます。
*   **`CertificateVerify` メッセージ**: クライアントまたはサーバーが自身の証明書を提示した後、その証明書が正当であることを証明するために送信するメッセージです。このメッセージには、ハンドシェイクのハッシュに対するデジタル署名が含まれます。
*   **`Finished` メッセージ**: ハンドシェイクの最後にクライアントとサーバーがそれぞれ送信するメッセージで、ハンドシェイクが正常に完了したことを確認するために使用されます。このメッセージには、ハンドシェイクのハッシュから導出された検証データが含まれます。
*   **署名ハッシュアルゴリズム (Signature and Hash Algorithm)**: TLS 1.2で導入された概念で、デジタル署名に使用されるハッシュアルゴリズム（例: SHA-256）と署名アルゴリズム（例: RSA、ECDSA）の組み合わせを指定します。これにより、柔軟なアルゴリズム選択が可能になりました。
*   **SHA-1, SHA-256, SHA-384**: Secure Hash Algorithm (SHA) ファミリーに属する暗号学的ハッシュ関数です。SHA-1は現在ではセキュリティ上の脆弱性が指摘されており、SHA-256やSHA-384などのより強力なハッシュ関数への移行が進められています。
*   **クライアント証明書**: サーバーがクライアントの身元を確認するために使用するデジタル証明書です。クライアント認証が必要な場合に利用されます。
*   **SSLv3**: TLSの古いバージョンで、POODLE攻撃などの深刻な脆弱性が発見されたため、現在ではほとんど使用されていません。

## 技術的詳細

このコミットの核心は、TLS 1.2におけるハンドシェイクハッシュと `CertificateVerify` メッセージの署名ハッシュの間の結合を解消することです。

従来のGoの実装では、`cipherSuite` 構造体に `tls12Hash crypto.Hash` フィールドがあり、これがハンドシェイクハッシュと `CertificateVerify` の署名ハッシュの両方に使用されていました。これはTLS 1.2以前のプロトコルでは問題ありませんでしたが、TLS 1.2で署名ハッシュアルゴリズムのネゴシエーションが導入されたことで、ハンドシェイクハッシュと `CertificateVerify` の署名ハッシュが異なるハッシュアルゴリズムを使用する可能性が生じました。

このコミットでは、以下の主要な変更が行われています。

1.  **`cipherSuite` 構造体からの `tls12Hash` フィールドの削除**:
    `src/crypto/tls/cipher_suites.go` で、`cipherSuite` 構造体から `tls12Hash crypto.Hash` フィールドが削除されました。これにより、暗号スイートが特定のTLS 1.2ハッシュアルゴリズムに直接関連付けられることがなくなりました。

2.  **`suiteSHA384` フラグの導入**:
    `src/crypto/tls/cipher_suites.go` に `suiteSHA384` という新しいフラグが追加されました。これは、その暗号スイートがハンドシェイクハッシュとしてSHA-384を使用することを示すものです。これにより、ハンドシェイクハッシュの選択がより柔軟になります。

3.  **`supportedSignatureAlgorithms` の統合と簡素化**:
    `src/crypto/tls/common.go` で、以前は `supportedSKXSignatureAlgorithms` と `supportedClientCertSignatureAlgorithms` に分かれていた署名ハッシュアルゴリズムのリストが `supportedSignatureAlgorithms` に統合されました。これにより、コードの重複が解消され、管理が容易になります。また、`isSupportedSignatureAndHash` 関数が追加され、特定の署名ハッシュの組み合わせがサポートされているかを効率的にチェックできるようになりました。

4.  **ハンドシェイクバッファリングの明示的な管理**:
    `src/crypto/tls/prf.go` の `finishedHash` 構造体に `buffer []byte` フィールドが追加されました。TLS 1.2では、`CertificateVerify` メッセージの署名のためにハンドシェイク全体をバッファリングする必要があるため、このバッファが導入されました。
    `discardHandshakeBuffer()` メソッドが追加され、ハンドシェイクのバッファリングが不要になった時点でバッファを破棄できるようになりました。これは、セッション再開時やクライアント認証が不要な場合など、パフォーマンス最適化のために行われます。

5.  **ハッシュ計算ロジックの更新**:
    `src/crypto/tls/prf.go` および `src/crypto/tls/key_agreement.go` で、`masterFromPreMasterSecret`、`keysFromMasterSecret`、`newFinishedHash`、`hashForClientCertificate` などの関数が、`crypto.Hash` の代わりに `*cipherSuite` を引数として受け取るように変更されました。これにより、ハッシュアルゴリズムの選択が暗号スイートのフラグに基づいて動的に行われるようになり、ハンドシェイクハッシュと署名ハッシュの独立性が高まりました。
    特に、`hashForClientCertificate` は、クライアント証明書の署名に使用するハッシュアルゴリズムを、サーバーが提示する `signature_algorithms` 拡張に基づいて選択できるようになりました。

6.  **テストデータファイルの更新**:
    この変更により、TLS 1.2のハンドシェイクにおけるハッシュの計算方法が変わるため、関連するテストデータファイルが更新されました。これは、SHA-384ベースのハンドシェイクがSHA-256で署名されるケースや、TLS 1.2の `CertificateRequest` メッセージにSHA-1が含まれるケースを反映しています。

これらの変更により、GoのTLS実装は、TLS 1.2の仕様に準拠し、ハンドシェイクハッシュと署名ハッシュの独立性を確保することで、より堅牢で互換性の高い動作を実現しています。特に、一部の厳格なサーバーとの互換性問題が解消されることが期待されます。

## コアとなるコードの解説

このコミットの主要な変更は、TLS 1.2におけるハンドシェイクハッシュと署名ハッシュの独立性を実現するための `crypto/tls` パッケージ内のデータ構造と関数の再設計にあります。

1.  **`cipherSuite` 構造体からの `tls12Hash` の削除と `suiteSHA384` の導入**:
    以前は `cipherSuite` に直接 `tls12Hash` が含まれていましたが、これは特定の暗号スイートが特定のハッシュアルゴリズムに固定されることを意味していました。この結合を解消するために `tls12Hash` が削除され、代わりに `flags` フィールドに `suiteSHA384` というビットフラグが追加されました。これにより、暗号スイート自体はハッシュアルゴリズムに依存せず、ハンドシェイクハッシュの選択は `prfAndHashForVersion` のような関数で動的に行われるようになります。

    ```go
    // src/crypto/tls/cipher_suites.go
    type cipherSuite struct {
        // ...
        flags  int // suiteSHA384 などのフラグを含む
        // tls12Hash crypto.Hash // 削除された
    }

    const (
        // ...
        suiteSHA384 // ハンドシェイクハッシュとしてSHA384を使用することを示す
    )
    ```

2.  **`supportedSignatureAlgorithms` の統合**:
    クライアントとサーバーがサポートする署名ハッシュアルゴリズムのリストが `supportedSignatureAlgorithms` に一元化されました。これにより、コードの重複が減り、管理が容易になります。

    ```go
    // src/crypto/tls/common.go
    var supportedSignatureAlgorithms = []signatureAndHash{
        {hashSHA256, signatureRSA},
        {hashSHA256, signatureECDSA},
        {hashSHA1, signatureRSA},
        {hashSHA1, signatureECDSA},
    }
    ```

3.  **`finishedHash` 構造体とハンドシェイクバッファリング**:
    TLS 1.2では、`CertificateVerify` メッセージの署名のためにハンドシェイク全体をバッファリングする必要があるという問題がありました。これを解決するために、`finishedHash` 構造体に `buffer []byte` が追加されました。ハンドシェイクメッセージが書き込まれるたびに、このバッファにも追加されます。

    ```go
    // src/crypto/tls/prf.go
    type finishedHash struct {
        client hash.Hash
        server hash.Hash

        clientMD5 hash.Hash
        serverMD5 hash.Hash

        buffer []byte // TLS 1.2 でハンドシェイクメッセージ全体をバッファリングするために使用
        version uint16
        prf     func(result, secret, label, seed []byte)
    }

    func (h *finishedHash) Write(msg []byte) (n int, err error) {
        // ...
        if h.buffer != nil {
            h.buffer = append(h.buffer, msg...)
        }
        return len(msg), nil
    }
    ```
    また、`discardHandshakeBuffer()` メソッドが追加され、ハンドシェイクのバッファリングが不要になった時点でバッファを解放できるようになりました。これは、セッション再開時やクライアント認証が不要な場合など、リソースの最適化に役立ちます。

    ```go
    // src/crypto/tls/prf.go
    func (h *finishedHash) discardHandshakeBuffer() {
        h.buffer = nil
    }
    ```

4.  **PRF (Pseudo-Random Function) とハッシュ選択の動的化**:
    `prf.go` 内のPRF関連関数（`prfForVersion`, `masterFromPreMasterSecret`, `keysFromMasterSecret`）が、`crypto.Hash` の代わりに `*cipherSuite` を引数として受け取るように変更されました。これにより、PRFが使用するハッシュアルゴリズムが、選択された暗号スイートのフラグ（特に `suiteSHA384`）に基づいて動的に決定されるようになりました。

    ```go
    // src/crypto/tls/prf.go
    func prfAndHashForVersion(version uint16, suite *cipherSuite) (func(result, secret, label, seed []byte), crypto.Hash) {
        switch version {
        // ...
        case VersionTLS12:
            if suite.flags&suiteSHA384 != 0 {
                return prf12(sha512.New384), crypto.SHA384
            }
            return prf12(sha256.New), crypto.SHA256
        // ...
        }
    }
    ```
    この変更により、ハンドシェイクハッシュと `CertificateVerify` の署名ハッシュが異なるハッシュアルゴリズムを使用できる柔軟性が実現されます。

5.  **クライアント証明書署名ロジックの改善**:
    `handshake_client.go` と `prf.go` の `hashForClientCertificate` 関数が、クライアント証明書の署名に使用するハッシュアルゴリズムを、サーバーが提示する `signature_algorithms` 拡張に基づいて選択できるようになりました。これにより、クライアントはサーバーがサポートするハッシュアルゴリズムで署名を行うことができ、互換性の問題が解消されます。

    ```go
    // src/crypto/tls/prf.go
    func (h finishedHash) hashForClientCertificate(signatureAndHash signatureAndHash, masterSecret []byte) ([]byte, crypto.Hash, error) {
        // ...
        if h.version >= VersionTLS12 {
            hashAlg, err := lookupTLSHash(signatureAndHash.hash)
            if err != nil {
                return nil, 0, err
            }
            hash := hashAlg.New()
            hash.Write(h.buffer) // バッファリングされたハンドシェイクメッセージを使用
            return hash.Sum(nil), hashAlg, nil
        }
        // ...
    }
    ```
    この関数は、`finishedHash` の `buffer` に蓄積されたハンドシェイクメッセージ全体をハッシュ計算の入力として使用します。

これらの変更は、GoのTLS実装がTLS 1.2の複雑なハッシュと署名のネゴシエーションをより正確に処理できるようにし、特定のサーバーとの互換性問題を解決するための重要なステップです。

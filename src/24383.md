# [インデックス 24383] ファイルの概要

このコミットは、Goランタイムのガベージコレクション(GC)トレース出力におけるヒープサイズ報告の挙動を修正するものです。具体的には、GCが開始された時点での実際のヒープサイズを常に報告するように変更し、以前のトリガーヒープサイズ報告による誤解を招く可能性のある挙動を解消します。

## コミット

```
commit 7eeeae2a5cc5087347c2fcdfc9731c87143dab4a
Author: Austin Clements <austin@google.com>
Date:   Tue Jul 21 11:38:14 2015 -0400

    runtime: always report starting heap size in gctrace
    
    Currently the gctrace output reports the trigger heap size, rather
    than the actual heap size at the beginning of GC. Often these are the
    same, or at least very close. However, it's possible for the heap to
    already have exceeded this trigger when we first check the trigger and
    start GC; in this case, this output is very misleading. We've
    encountered this confusion a few times when debugging and this
    behavior is difficult to document succinctly.
    
    Change the gctrace output to report the actual heap size when GC
    starts, rather than the trigger.
```

## 元コミット内容

Goランタイムの`gctrace`出力において、GC開始時のヒープサイズ報告を、GCトリガー時のヒープサイズではなく、GCが実際に開始された時点での実際のヒープサイズに変更する。これにより、デバッグ時の混乱を避ける。

## 変更の背景

Goのガベージコレクタは、ヒープの使用量が特定の閾値（トリガーヒープサイズ）を超えるとGCサイクルを開始します。`gctrace`は、GCの動作を詳細にログ出力する機能で、デバッグやパフォーマンス分析に非常に有用です。

このコミット以前は、`gctrace`の出力ではGCがトリガーされた時点でのヒープサイズが報告されていました。しかし、GCトリガーが検出されてから実際にGCが開始されるまでの間に、ミューテータ（ユーザープログラム）がさらにメモリを割り当てる可能性があります。この場合、GC開始時の実際のヒープサイズはトリガーヒープサイズよりも大きくなります。

このような状況でトリガーヒープサイズが報告されると、ユーザーはGCが開始された時点での実際のメモリ使用量を誤解する可能性がありました。コミットメッセージにもあるように、「この出力は非常に誤解を招く可能性があり、デバッグ時に何度か混乱に遭遇した」という経験が背景にあります。この混乱を解消し、より正確な情報を提供するために、GC開始時の実際のヒープサイズを報告するように変更されました。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: Goは自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは並行マーク＆スイープ方式をベースにしており、プログラムの実行と並行して動作することで、アプリケーションの一時停止（ストップ・ザ・ワールド、STW）時間を最小限に抑えるように設計されています。
*   **`gctrace`**: Goプログラムの実行時に環境変数`GODEBUG=gctrace=1`を設定することで有効になるデバッグ機能です。GCの各サイクルに関する詳細な情報（GCの開始、終了、ヒープサイズ、STW時間、CPU使用率など）を標準エラー出力にログとして出力します。これにより、GCのパフォーマンス特性を理解し、メモリリークやGCのボトルネックを特定するのに役立ちます。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域です。Goでは、`make`や`new`で確保されるメモリはヒープに配置されます。
*   **`memstats.heap_live`**: Goランタイムが管理する構造体`memstats`の一部で、現在ライブ（参照されている）オブジェクトによって占有されているヒープメモリの量を示します。これはGCが実際に考慮するメモリ量に近いです。
*   **`memstats.next_gc`**: 次のGCサイクルがトリガーされるべきヒープの目標サイズを示します。現在のヒープサイズが`next_gc`を超えると、GCが開始されます。
*   **ミューテータ (Mutator)**: ガベージコレクタの文脈で、ユーザープログラム（アプリケーションコード）を指します。ミューテータはオブジェクトを生成し、ヒープの状態を変更します。

## 技術的詳細

このコミットの核心は、`src/runtime/mgc.go`内の`gc`関数における`heap0`変数の設定ロジックの変更です。

`gc`関数はGoランタイムのガベージコレクタの主要なエントリポイントです。`gctrace`が有効な場合（`debug.gctrace > 0`）、GCサイクルの開始時にいくつかの統計情報が収集されます。その一つが`heap0`で、これはGC開始時のヒープサイズを記録するために使用されます。

変更前は、`heap0`の設定はGCのモードによって異なっていました。
*   `gcBackgroundMode`の場合（バックグラウンドGC）、`heap0`は`memstats.next_gc`に設定されていました。これは、GCがトリガーされた時点での目標ヒープサイズを意味します。コミットメッセージが指摘するように、GCトリガーから実際のGC開始までの間にミューテータがメモリを割り当てた場合、この値は実際のヒープサイズと異なる可能性がありました。
*   それ以外の場合（例えば、同期GC）、`heap0`は`memstats.heap_live`に設定されていました。これは、GC開始時の実際のライブヒープサイズです。

このコミットでは、GCのモードに関わらず、常に`heap0 = memstats.heap_live`を設定するように変更されました。これにより、`gctrace`の出力は、GCが実際に開始された時点でのライブヒープサイズを常に正確に反映するようになります。

この変更は、`gctrace`の出力の信頼性と解釈の容易さを向上させ、デバッグやパフォーマンスチューニングを行う開発者にとってより有用な情報を提供することを目的としています。

## コアとなるコードの変更箇所

`src/runtime/mgc.go`ファイルの`gc`関数内の以下の部分が変更されました。

```diff
--- a/src/runtime/mgc.go
+++ b/src/runtime/mgc.go
@@ -884,14 +884,7 @@ func gc(mode int) {
 	if debug.gctrace > 0 {
 		stwprocs, maxprocs = gcprocs(), gomaxprocs
 		tSweepTerm = now
-		if mode == gcBackgroundMode {
-			// We started GC when heap_live == next_gc,
-			// but the mutator may have allocated between
-			// then and now. Report heap when GC started.
-			heap0 = memstats.next_gc
-		} else {
-			heap0 = memstats.heap_live
-		}
+		heap0 = memstats.heap_live
 	}
 
 	pauseStart = now
```

## コアとなるコードの解説

変更前のコードでは、`gctrace`が有効な場合（`debug.gctrace > 0`）、`heap0`変数の値はGCの`mode`によって条件分岐していました。

*   `if mode == gcBackgroundMode { ... }` のブロックでは、GCがバックグラウンドモードで実行されている場合、`heap0`は`memstats.next_gc`に設定されていました。コメントにもあるように、「GCは`heap_live == next_gc`のときに開始されたが、ミューテータがその間に割り当てを行った可能性がある。GC開始時のヒープを報告する」と書かれていますが、実際には`next_gc`を報告していました。これは、GCがトリガーされた時点の目標値であり、GC開始時の実際の値ではないため、誤解を招く可能性がありました。
*   `else { ... }` のブロックでは、それ以外のGCモード（例えば、同期GC）の場合、`heap0`は`memstats.heap_live`に設定されていました。これは、GC開始時の実際のライブヒープサイズを正確に反映していました。

このコミットでは、この条件分岐が削除され、`heap0 = memstats.heap_live`という行が直接配置されました。これにより、GCのモードに関わらず、`heap0`は常に`memstats.heap_live`、つまりGCが実際に開始された時点でのライブヒープサイズを報告するようになります。

この変更は、`gctrace`の出力の一貫性と正確性を高め、GCの挙動を分析する際に開発者がより信頼性の高い情報に基づいて判断できるようにすることを目的としています。

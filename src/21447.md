# [インデックス 21447] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）における2つの重要なバグを修正します。一つは`checkmark`フラグとGCビットマップ間の不整合期間の短縮、もう一つは`gcphase`変数の変更がStop-the-World（STW）中にのみ行われるようにすることです。これらの修正は、GCの正確性と安定性を向上させ、特に並行実行環境下での潜在的な競合状態を解消します。

## コミット

```
commit 02f89331c2ec09923806611bc1a8fbb2ffcbcca5
Author: Russ Cox <rsc@golang.org>
Date:   Mon Jan 5 15:02:09 2015 -0500

    runtime: fix two garbage collector bugs
    
    First, call clearcheckmarks immediately after changing checkmark,
    so that there is less time when the checkmark flag and the bitmap
    are inconsistent. The tiny gap between the two lines is fine, because
    the world is stopped. Before, the gap was much larger and included
    such code as "go bgsweep()", which allocated.
    
    Second, modify gcphase only when the world is stopped.
    As written, gcscan_m was changing gcphase from 0 to GCscan
    and back to 0 while other goroutines were running.
    Another goroutine running at the same time might decide to
    sleep, see GCscan, call gcphasework, and start "helping" by
    scanning its stack. That's fine, except that if gcphase flips back
    to 0 as the goroutine calls scanblock, it will start draining the
    work buffers prematurely.
    
    Both of these were found wbshadow=2 (and a lot of hard work).
    Eventually that will run automatically, but right now it still
    doesn't quite work for all.bash, due to mmap conflicts with
    pthread-created threads.
```

## 元コミット内容

Goランタイムのガベージコレクタにおける2つのバグを修正します。

1.  `checkmark`フラグを変更した直後に`clearcheckmarks`を呼び出すことで、`checkmark`フラグとビットマップが不整合な状態にある時間を短縮します。以前は、この不整合期間が長く、`go bgsweep()`のようなメモリ割り当てを伴うコードが含まれていました。
2.  `gcphase`の変更を、Stop-the-World（STW）中にのみ行うようにします。以前は、`gcscan_m`が他のゴルーチンが実行中に`gcphase`を`0`から`_GCscan`、そしてまた`0`へと変更していました。これにより、同時に実行されているゴルーチンが`gcphase`が`_GCscan`であることを見てGCを手伝い始め、`gcphase`が`0`に戻るとワークバッファを時期尚早にドレインしてしまう問題がありました。

これらのバグは、`wbshadow=2`というツール（および多大な労力）によって発見されました。

## 変更の背景

このコミットは、Goランタイムのガベージコレクタが抱えていた2つの微妙なバグに対処するために行われました。これらのバグは、GCの内部状態の不整合や、並行実行されるゴルーチンとGCフェーズ管理との間の競合状態に起因していました。

最初のバグは、GCのデバッグ/検証メカニズムである`checkmark`機能に関連していました。`checkmark`フラグが設定された後、それに対応するビットマップがクリアされるまでの間に時間差があり、この期間中にメモリ割り当てが発生すると、GCの内部状態が一時的に不整合になる可能性がありました。特に、`go bgsweep()`のようなバックグラウンドのスイープ処理がこの期間に実行されると、問題が顕在化するリスクがありました。GCの正確性を保つためには、このような不整合期間を可能な限り短縮する必要がありました。

二つ目のバグは、Goの並行GCのフェーズ管理に関するものでした。`gcphase`という変数は、ランタイムが現在どのGCフェーズにあるかを示します。`gcscan_m`関数が、システム全体が停止していない（Stop-the-Worldではない）状態でこの`gcphase`を頻繁に変更していました。これにより、他のゴルーチンがGCフェーズを誤って認識し、GCの「ヘルプ」を開始したり、あるいはGCがまだ完了していないにもかかわらず、GCのワークバッファを時期尚早に処理し始めてしまうという競合状態が発生していました。これは、GCの進行を妨げたり、最悪の場合、メモリの破損やクラッシュにつながる可能性がありました。

これらのバグは、通常のテストでは見つけにくい、非常にデリケートなタイミングの問題でした。コミットメッセージにあるように、`wbshadow=2`という特殊なデバッグツールと、開発者の多大な労力によって発見されました。この修正は、Goランタイムの堅牢性とGCの信頼性を高める上で不可欠でした。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション（GC）の基本的な概念と、関連する内部メカニズムについて知る必要があります。

*   **Goのガベージコレクション (GC)**: Goは、主に並行マーク＆スイープ方式のGCを採用しています。これは、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止（Stop-the-World: STW）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ (Mark Phase)**: GCの開始時に、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを「ライブ」としてマークします。GoのGCは、このマークフェーズの大部分をアプリケーションと並行して実行します。
    *   **スキャンフェーズ (Scan Phase)**: マークされたオブジェクトが参照している他のオブジェクトを再帰的にスキャンし、それらもライブとしてマークします。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。これも通常、アプリケーションと並行して行われます。
    *   **Stop-the-World (STW)**: GCの特定の短い期間（例えば、マークフェーズの開始時や終了時）において、全てのゴルーチン（Goの軽量スレッド）の実行が一時的に停止されます。これは、GCの内部状態の一貫性を保つために必要ですが、アプリケーションの応答性に影響を与えるため、GoランタイムはSTW時間を極力短くするよう設計されています。

*   **`gcphase`**: Goランタイムの内部変数で、現在のGCのフェーズ（例: `_GCoff` (GC非アクティブ), `_GCmark` (マーク中), `_GCscan` (スキャン中), `_GCsweep` (スイープ中) など）を示します。この変数は、GCの進行状況を管理し、他のランタイムコンポーネントがGCの状態に応じて適切に動作するために重要です。

*   **`checkmark`と`clearcheckmarkbits`**: これらは、GoのGCのデバッグおよび検証メカニズムの一部です。
    *   `checkmark`は、GCの整合性チェックを有効にするためのブールフラグです。これが`true`の場合、ランタイムはメモリ操作がGCのルールに違反していないか（例えば、マークされていないオブジェクトへのポインタが作成されていないか）をチェックします。
    *   `clearcheckmarkbits()`は、GCビットマップ（メモリ上のオブジェクトがマークされているかどうかを示すビット列）から、特定のチェックマーク関連のビットをクリアする関数です。これは、チェックマークフェーズの終了時や、GCの状態が変化する際に呼び出され、ビットマップの整合性を保ちます。

*   **`greyobject`と`scanblock`**:
    *   `greyobject(obj, mbits, wbuf)`: GC中にオブジェクト`obj`を「グレイ」（マーク済みだが、まだその参照先がスキャンされていない状態）としてマークし、GCワークバッファ`wbuf`に追加する関数です。ワークバッファは、並行GC中にスキャンすべきオブジェクトのポインタを一時的に保持するために使用されます。
    *   `scanblock(b0, n0, ptrmask)`: メモリブロック`b0`から`n0`バイトをスキャンし、その中に含まれるポインタを見つけて、参照先のオブジェクトをグレイ化する関数です。

*   **`wbshadow`**: Write Barrier Shadowの略で、Goランタイムの高度なデバッグおよびテスト機能です。ライトバリアは、GCが実行中にヒープ上のポインタが変更された際に、GCがオブジェクトを見失わないようにするためのメカニズムです。`wbshadow`は、このライトバリアの動作をシミュレートまたは検証し、GCのバグ（特に並行性に関連するもの）を検出するために使用されます。`wbshadow=2`は、特定の厳格な検証モードを示唆しており、通常の実行では検出が困難な競合状態を露呈させることができます。

## 技術的詳細

このコミットは、Goランタイムのガベージコレクタにおける2つの異なる、しかしGCの正確性と並行性に深く関わるバグを修正しています。

### 1. `checkmark`フラグとGCビットマップの不整合期間の短縮

**問題点**:
GoのGCには、デバッグや検証のために`checkmark`という機能があります。これは、GCがメモリを正しく追跡しているかを検証するためのものです。`checkmark`フラグが`true`に設定されると、ランタイムはメモリ操作の整合性をチェックします。このチェックが終了すると、`clearcheckmarkbits()`が呼び出され、GCビットマップから関連するチェックマーク情報がクリアされます。

元のコードでは、`checkmark`フラグが`true`に設定された後、`clearcheckmarkbits()`が呼び出されるまでの間に、比較的大きな時間差がありました。この「ギャップ」の間に、`go bgsweep()`のようなバックグラウンドのスイープ処理が実行される可能性がありました。`bgsweep()`はメモリを割り当てる可能性があり、`checkmark`フラグが`true`であるにもかかわらず、ビットマップがまだ完全にクリアされていないという不整合な状態に陥ることがありました。この不整合は、特にStop-the-World（STW）期間外で発生すると、GCの正確性に影響を与える可能性がありました。コミットメッセージでは、「世界が停止している間は、2行の間の小さなギャップは問題ない」と述べていますが、以前はSTW期間外でこのギャップが大きかったことが問題でした。

**修正内容**:
この修正では、`checkmark`フラグが`false`に設定された直後、つまりGCのチェックマークフェーズが終了したと判断された直後に、`clearcheckmarkbits()`を即座に呼び出すように変更されました。これにより、`checkmark`フラグとGCビットマップの間の不整合期間が最小限に抑えられ、GCの内部状態の一貫性がより厳密に保たれるようになりました。

### 2. `gcphase`の不適切な変更による競合状態

**問題点**:
`gcphase`は、Goランタイムが現在どのGCフェーズにあるかを示す重要な変数です。この変数は、GCの進行を調整し、他のゴルーチンがGC処理に協力（「ヘルプ」）すべきかどうかを判断するために使用されます。

元のコードでは、`gcscan_m`という関数が、システム全体が停止していない（つまり、他のゴルーチンが実行中である）状態で`gcphase`の値を頻繁に変更していました。具体的には、`0`（GC非アクティブまたは別のフェーズ）から`_GCscan`（スキャンフェーズ）、そしてまた`0`へと切り替えていました。

この振る舞いが問題を引き起こしました。同時に実行されている別のゴルーチンが、何らかの理由でスリープ状態に入り、その後再開した際に`gcphase`が`_GCscan`になっていることを検出する可能性がありました。このゴルーチンは、GCを「手伝う」ために`gcphasework`を呼び出し、自身のスタックをスキャンし始めるかもしれません。しかし、そのゴルーチンが実際に`scanblock`などのGC処理関数を呼び出す直前に、`gcphase`が`0`に戻ってしまうと、ゴルーチンはGCがまだ完了していないにもかかわらず、GCのワークバッファ（スキャンすべきオブジェクトのポインタが格納されている）を時期尚早にドレインし始めてしまうという競合状態が発生しました。これは、GCの進行を妨げたり、GCがオブジェクトを見落とす原因となる可能性がありました。

**修正内容**:
この修正では、`gcphase`の変更がStop-the-World（STW）期間中にのみ行われるように変更されました。具体的には、`src/runtime/malloc.go`の`gogc`関数内で、`stoptheworld()`が呼び出された直後に`gcphase = _GCscan`が設定され、`starttheworld()`が呼び出される前に設定されるようになりました。また、`src/runtime/mgc.go`の`gcscan_m`関数から`gcphase`の変更ロジックが削除されました。これにより、`gcphase`の値が安定し、他のゴルーチンがGCフェーズを誤って認識して不適切な動作をするリスクがなくなりました。GCフェーズの変更がSTW中にのみ行われることで、ランタイム全体の整合性が保証されます。

### `wbshadow=2`による発見

コミットメッセージは、これらのバグが`wbshadow=2`というツールによって発見されたことを強調しています。`wbshadow`は、Goのライトバリア（GC中にポインタの変更を追跡するメカニズム）の動作を検証するための高度なデバッグツールです。`wbshadow=2`は、特に厳格な検証モードであり、通常の実行では再現が困難な、非常にデリケートなタイミングの競合状態やGCの整合性問題を検出する能力があります。このツールがなければ、これらのバグは長期間にわたって未発見のまま残り、Goアプリケーションの安定性に潜在的な影響を与え続けていた可能性があります。コミットメッセージには、`wbshadow=2`が`mmap`の競合によりまだ全てのテストケースで完全に機能しないという言及もあり、このツールの開発と利用がいかに困難であったかを示唆しています。

*   **`greyobject`関数のシグネチャ変更とデバッグ出力の追加**:

*   **`scanblock`における`gcphase`のチェック**:
    `scanblock`はメモリブロックをスキャンする関数であり、GCのマークフェーズまたはマーク終了フェーズ中にのみ実行されるべきです。この変更では、`gcphase`が`_GCmark`または`_GCmarktermination`でない場合に`throw("scanblock phase")`でパニックを起こすチェックが追加されました。これは、`gcphase`が不適切に設定されている状態で`scanblock`が呼び出されるという、前述の競合状態を防ぐための防御的なプログラミングです。これにより、GCの内部状態の整合性が強制されます。

*   **`gccheckmark_m`における`clearcheckmarkbits()`の重複削除**:
    以前のコードでは、`gccheckmark_m`内で`gc_m`の呼び出し後に`clearcheckmarkbits()`が二重に呼び出されていました。コミットメッセージによると、`gc_m`自体が`checkmark`をオフにし、`clearcheckmarkbits`を呼び出すようになったため、この重複は不要になりました。これはコードのクリーンアップと、`checkmark`とビットマップの不整合期間を短縮するという最初のバグ修正に関連しています。

*   **`gcscan_m`からの`gcphase`変更ロジックの削除**:
    `gcscan_m`は、GCのスキャン処理の一部を担う関数です。この関数から`gcphase`を`0`から`_GCscan`、そしてまた`0`へと変更するロジックが完全に削除されました。これは、`gcphase`の変更をSTW中に限定するという方針に沿ったものです。これにより、`gcscan_m`が並行して実行されている間に`gcphase`が変動し、他のゴルーチンがGCフェーズを誤認識する問題が解消されます。

*   **`gc`関数における`clearcheckmarkbits()`の追加**:
    `gc`関数はGCの全体的な調整を行う関数です。ここで`checkmark = false`（チェックマークの終了）の直後に`clearcheckmarkbits()`が呼び出されるようになりました。これは、`checkmark`フラグとGCビットマップの不整合期間を最小限に抑えるという最初のバグ修正のもう一つの側面です。これにより、チェックマークがオフになった瞬間にビットマップがクリーンな状態になることが保証されます。

これらの変更は、GoランタイムのGCの内部動作をより堅牢にし、特に並行実行環境下での潜在的な競合状態や不整合を排除することを目的としています。

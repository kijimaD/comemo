## 元コミット内容

```
runtime: use uintXX instead of *byte for si_addr on Darwin

Currently, Darwin's siginfo type uses *byte for the si_addr
field. This results in unwanted write barriers in set_sigaddr. It's
also pointless since it never points to anything real and the get/set
methods return/take uintXX and cast it from/to the pointer.

All other arches use a uint type for this field. Change Darwin to
match. This simplifies the get/set methods and eliminates the unwanted
write barriers.

Change-Id: Ifdb5646d35e1f2f6808b87a3d59745ec9718add1
Reviewed-on: https://go-review.googlesource.com/8086
Reviewed-by: Austin Clements <austin@google.com>
```

## 変更の背景

この変更の背景には、GoランタイムがDarwinプラットフォームでシグナルを処理する際の非効率性と、他のアーキテクチャとの不整合がありました。

1.  **不要なライトバリアの発生**: Darwinの`siginfo`構造体において、`si_addr`フィールドが`*byte`（バイトへのポインタ）型として定義されていました。Goのガベージコレクタは、ポインタ型のフィールドへの書き込み時に「ライトバリア（Write Barrier）」と呼ばれる処理を挿入します。これは、ガベージコレクタがオブジェクトの参照関係を正確に追跡し、並行処理中に整合性を保つために必要なものです。しかし、コミットメッセージにあるように、`si_addr`は「実際には何も指していない」にもかかわらずポインタ型であったため、`set_sigaddr`関数でこのフィールドに値を設定する際に、不要なライトバリアが挿入されていました。このライトバリアはパフォーマンスのオーバーヘッドを引き起こします。
2.  **型の不整合と冗長なキャスト**: `si_addr`フィールドは内部的にはポインタ型でしたが、その値を取得する`sigaddr()`（または`fault()`）関数や設定する`set_sigaddr()`関数では、`uintXX`型（符号なし整数型）として扱われ、ポインタと整数の間で冗長な型変換（`unsafe.Pointer`と`uintptr`を使ったキャスト）が行われていました。これはコードの複雑さを増し、可読性を低下させていました。
3.  **他のアーキテクチャとの不整合**: Goランタイムは、Darwin以外のほとんどのアーキテクチャでは`siginfo`構造体の対応するフィールドに`uint`型の整数を使用しています。Darwinのみが`*byte`を使用しているのは一貫性がなく、コードの統一性を損なっていました。

これらの問題を解決し、パフォーマンスを改善し、コードを簡素化するために、`si_addr`の型を`uintXX`に変更する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **シグナル (Signals)**:
    Unix系OSにおけるシグナルは、プロセスに対して非同期的にイベントを通知するメカニズムです。例えば、Ctrl+Cを押すと`SIGINT`シグナルが、不正なメモリアクセスが発生すると`SIGSEGV`シグナルがプロセスに送信されます。Goランタイムは、プログラムのクラッシュハンドリングやデバッガとの連携のためにシグナルを内部的に利用します。

2.  **`siginfo_t`構造体**:
    シグナルハンドラが呼び出される際、シグナルに関する詳細情報が`siginfo_t`構造体を通じて提供されます。この構造体は、どのシグナルが送信されたか（`si_signo`）、シグナルを送信したプロセスID（`si_pid`）、エラーの原因となったアドレス（`si_addr`）など、様々な情報を含みます。OSによって構造体の定義は異なりますが、概念は共通です。

3.  **`si_addr`フィールド**:
    `siginfo_t`構造体内の`si_addr`フィールドは、通常、メモリアクセス違反（`SIGSEGV`）や不正な命令（`SIGILL`）など、特定のエラーが発生した際に関連するアドレス情報を提供します。しかし、Goランタイムの内部的なシグナル処理においては、このフィールドが必ずしも有効なメモリ位置を指すわけではない場合があります。コミットメッセージにある「never points to anything real」という記述は、Goランタイムがこのフィールドを特定の目的で利用する際に、その値が実際のGoのヒープオブジェクトを指すポインタではないことを示唆しています。

4.  **Goのガベージコレクションとライトバリア (Write Barriers)**:
    Goは自動メモリ管理（ガベージコレクション、GC）を採用しています。GCは、プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは、並行（concurrent）かつ低遅延（low-latency）で動作するように設計されています。
    ライトバリアは、GCが正しく動作するために重要な技術です。GoのGCは、オブジェクトの参照関係を追跡して到達可能なオブジェクトを特定します。プログラムが実行中にポインタを書き換える（あるオブジェクトが別のオブジェクトを指すように変更する）と、GCが参照グラフをスキャンしている最中にその変更が発生した場合、GCが誤った判断をする可能性があります。
    ライトバリアは、ポインタ型のフィールドに新しい値を書き込む直前または直後に、GCが必要な情報を記録するための小さなコードスニペットです。これにより、GCは参照関係の変更を検出し、メモリの安全性を保証できます。ライトバリアは非常に高速に設計されていますが、それでもオーバーヘッドは存在します。特に、不要なライトバリアはパフォーマンスに悪影響を与えます。

5.  **`unsafe.Pointer`と`uintptr`**:
    Goは通常、型安全性を厳密に強制しますが、`unsafe`パッケージを使用することで、低レベルのメモリ操作が可能になります。
    *   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムをバイパスして、異なる型のポインタ間で変換を行うことができます。
    *   `uintptr`: ポインタの値を保持できる符号なし整数型です。`unsafe.Pointer`と`uintptr`の間で相互に変換できます。これにより、ポインタの値を整数として扱ったり、整数値をポインタとして解釈したりすることが可能になります。
    これらの型は、Goの型安全性を損なう可能性があるため、慎重に使用する必要があります。Goランタイムのような低レベルのコードでは、OSとのインターフェースやハードウェアとの直接的なやり取りのために使用されることがあります。

## 技術的詳細

このコミットの技術的な核心は、Darwinプラットフォームにおける`siginfo`構造体の`si_addr`フィールドの型定義の変更と、それに伴うGoランタイムのシグナルハンドリングロジックの簡素化にあります。

**変更前**:
DarwinのGoランタイムでは、`siginfo`構造体の`si_addr`フィールドが以下のように定義されていました（例: `defs_darwin_386.go`）。

```go
type siginfo struct {
    // ...
    si_addr   *byte // バイトへのポインタ
    // ...
}
```

この`*byte`型はポインタ型であるため、Goのガベージコレクタは、このフィールドへの書き込み操作（`set_sigaddr`関数内）に対して自動的にライトバリアを挿入していました。しかし、コミットメッセージが指摘するように、この`si_addr`は「never points to anything real」（実際のGoヒープ上のオブジェクトを指すわけではない）ため、このライトバリアは完全に不要なオーバーヘッドでした。

さらに、`si_addr`の値を取得する`sigaddr()`関数や設定する`set_sigaddr()`関数では、このポインタ型を`uintXX`（符号なし整数）型に変換する必要がありました。

```go
// 変更前のsigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) sigaddr() uint32 { return uint32(uintptr(unsafe.Pointer(c.info.si_addr))) }

// 変更前のset_sigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) set_sigaddr(x uint32) { c.info.si_addr = (*byte)(unsafe.Pointer(uintptr(x))) }
```

これらのコードは、`unsafe.Pointer`と`uintptr`を介した冗長な型変換を含んでおり、コードの複雑性と潜在的なエラーのリスクを増大させていました。

**変更後**:
このコミットでは、`si_addr`フィールドの型を、各アーキテクチャのポインタサイズに対応する符号なし整数型に変更しました。

*   `defs_darwin_386.go` および `defs_darwin_arm.go` では `uint32` に変更。
*   `defs_darwin_amd64.go` では `uint64` に変更。

```go
// 変更後のsiginfo構造体の定義例 (386アーキテクチャ)
type siginfo struct {
    // ...
    si_addr   uint32 // 符号なし整数
    // ...
}
```

この変更により、`si_addr`はもはやポインタ型ではないため、`set_sigaddr`関数での書き込み時にガベージコレクタによるライトバリアが挿入されなくなりました。これにより、不要なパフォーマンスオーバーヘッドが解消されます。

また、`sigaddr()`および`set_sigaddr()`関数内の冗長な型変換も不要になり、コードが大幅に簡素化されました。

```go
// 変更後のsigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) sigaddr() uint32 { return c.info.si_addr }

// 変更後のset_sigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) set_sigaddr(x uint32) { c.info.si_addr = x }
```

この変更は、GoランタイムがDarwinのシグナルハンドリングをより効率的かつGoの他のアーキテクチャと一貫性のある方法で処理できるようにするための重要な改善です。`si_addr`が実際にメモリ上のオブジェクトを指すわけではないという特性を考慮し、その型をより適切な整数型にすることで、ガベージコレクタの動作を最適化し、コードの保守性を向上させています。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがDarwin上でシグナル情報をどのように扱うかという低レベルな部分にあります。

Goランタイムは、OSからシグナルを受け取ると、そのシグナルに関する情報を`siginfo`構造体として受け取ります。この構造体はOSのシステムコールによって提供されるもので、Goランタイムはその定義をGoのコード内でミラーリングしています（`src/runtime/defs_darwin_*.go`）。

変更前は、Darwinの`siginfo`構造体内の`si_addr`フィールドが`*byte`型として定義されていました。これはGoの型システムにおいてポインタ型と認識されます。Goのガベージコレクタは、ポインタ型のフィールドへの書き込み操作を監視し、必要に応じてライトバリアを挿入します。ライトバリアは、GCがメモリの整合性を保つために、ポインタの変更を記録する小さな処理です。

しかし、この`si_addr`フィールドは、Goランタイムの文脈では「実際にはGoのヒープ上のオブジェクトを指すポインタではない」という特殊な性質を持っていました。例えば、`SIGSEGV`（セグメンテーション違反）のようなシグナルで`si_addr`がエラー発生アドレスを示す場合でも、そのアドレスはGoのガベージコレクタが管理するヒープ内のオブジェクトを指すとは限りません。そのため、`si_addr`への書き込み時にライトバリアが挿入されるのは、完全に無駄なオーバーヘッドとなっていました。

また、`siginfo`構造体から`si_addr`の値を取得する`sigctxt.sigaddr()`（または`sigctxt.fault()`）関数や、値を設定する`sigctxt.set_sigaddr()`関数では、この`*byte`型の`si_addr`を`uintXX`（符号なし整数）型として扱っていました。そのため、`unsafe.Pointer`と`uintptr`を介した複雑な型変換が必須となっていました。

このコミットでは、`si_addr`の型を`uint32`または`uint64`（アーキテクチャに応じて）に変更しました。これにより、以下のメリットが生まれました。

1.  **ライトバリアの排除**: `si_addr`がもはやポインタ型ではないため、`set_sigaddr()`関数での書き込み時にガベージコレクタによるライトバリアが挿入されなくなりました。これにより、Goランタイムのパフォーマンスがわずかに向上します。
2.  **コードの簡素化**: `sigaddr()`/`fault()`および`set_sigaddr()`関数から、`unsafe.Pointer`と`uintptr`を使った冗長な型変換が完全に削除されました。これにより、コードがより直接的で読みやすくなり、保守性が向上します。
3.  **アーキテクチャ間の一貫性**: Darwinプラットフォームの`si_addr`の型が、他のGoがサポートするアーキテクチャ（これらは既に`uint`型を使用していた）と一致するようになり、Goランタイム全体のコードベースの一貫性が高まりました。

この変更は、Goランタイムの内部的な最適化であり、Goプログラムのユーザーが直接その影響を感じることは少ないかもしれませんが、Goの実行効率と内部コードの品質向上に貢献しています。

## 元コミット内容

```
runtime: use uintXX instead of *byte for si_addr on Darwin

Currently, Darwin's siginfo type uses *byte for the si_addr
field. This results in unwanted write barriers in set_sigaddr. It's
also pointless since it never points to anything real and the get/set
methods return/take uintXX and cast it from/to the pointer.

All other arches use a uint type for this field. Change Darwin to
match. This simplifies the get/set methods and eliminates the unwanted
write barriers.

Change-Id: Ifdb5646d35e1f2f6808b87a3d59745ec9718add1
Reviewed-on: https://go-review.googlesource.com/8086
Reviewed-by: Austin Clements <austin@google.com>
```

## 変更の背景

この変更の背景には、GoランタイムがDarwinプラットフォームでシグナルを処理する際の非効率性と、他のアーキテクチャとの不整合がありました。

1.  **不要なライトバリアの発生**: Darwinの`siginfo`構造体において、`si_addr`フィールドが`*byte`（バイトへのポインタ）型として定義されていました。Goのガベージコレクタは、ポインタ型のフィールドへの書き込み時に「ライトバリア（Write Barrier）」と呼ばれる処理を挿入します。これは、ガベージコレクタがオブジェクトの参照関係を正確に追跡し、並行処理中に整合性を保つために必要なものです。しかし、コミットメッセージにあるように、`si_addr`は「実際には何も指していない」にもかかわらずポインタ型であったため、`set_sigaddr`関数でこのフィールドに値を設定する際に、不要なライトバリアが挿入されていました。このライトバリアはパフォーマンスのオーバーヘッドを引き起こします。
2.  **型の不整合と冗長なキャスト**: `si_addr`フィールドは内部的にはポインタ型でしたが、その値を取得する`sigaddr()`（または`fault()`）関数や設定する`set_sigaddr()`関数では、`uintXX`型（符号なし整数型）として扱われ、ポインタと整数の間で冗長な型変換（`unsafe.Pointer`と`uintptr`を使ったキャスト）が行われていました。これはコードの複雑さを増し、可読性を低下させていました。
3.  **他のアーキテクチャとの不整合**: Goランタイムは、Darwin以外のほとんどのアーキテクチャでは`siginfo`構造体の対応するフィールドに`uint`型の整数を使用しています。Darwinのみが`*byte`を使用しているのは一貫性がなく、コードの統一性を損なっていました。

これらの問題を解決し、パフォーマンスを改善し、コードを簡素化するために、`si_addr`の型を`uintXX`に変更する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **シグナル (Signals)**:
    Unix系OSにおけるシグナルは、プロセスに対して非同期的にイベントを通知するメカニズムです。例えば、Ctrl+Cを押すと`SIGINT`シグナルが、不正なメモリアクセスが発生すると`SIGSEGV`シグナルがプロセスに送信されます。Goランタイムは、プログラムのクラッシュハンドリングやデバッガとの連携のためにシグナルを内部的に利用します。

2.  **`siginfo_t`構造体**:
    シグナルハンドラが呼び出される際、シグナルに関する詳細情報が`siginfo_t`構造体を通じて提供されます。この構造体は、どのシグナルが送信されたか（`si_signo`）、シグナルを送信したプロセスID（`si_pid`）、エラーの原因となったアドレス（`si_addr`）など、様々な情報を含みます。OSによって構造体の定義は異なりますが、概念は共通です。

3.  **`si_addr`フィールド**:
    `siginfo_t`構造体内の`si_addr`フィールドは、通常、メモリアクセス違反（`SIGSEGV`）や不正な命令（`SIGILL`）など、特定のエラーが発生した際に関連するアドレス情報を提供します。しかし、Goランタイムの内部的なシグナル処理においては、このフィールドが必ずしも有効なメモリ位置を指すわけではない場合があります。コミットメッセージにある「never points to anything real」という記述は、Goランタイムがこのフィールドを特定の目的で利用する際に、その値が実際のGoのヒープオブジェクトを指すポインタではないことを示唆しています。

4.  **Goのガベージコレクションとライトバリア (Write Barriers)**:
    Goは自動メモリ管理（ガベージコレクション、GC）を採用しています。GCは、プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは、並行（concurrent）かつ低遅延（low-latency）で動作するように設計されています。
    ライトバリアは、GCが正しく動作するために重要な技術です。GoのGCは、オブジェクトの参照関係を追跡して到達可能なオブジェクトを特定します。プログラムが実行中にポインタを書き換える（あるオブジェクトが別のオブジェクトを指すように変更する）と、GCが参照グラフをスキャンしている最中にその変更が発生した場合、GCが誤った判断をする可能性があります。
    ライトバリアは、ポインタ型のフィールドに新しい値を書き込む直前または直後に、GCが必要な情報を記録するための小さなコードスニペットです。これにより、GCは参照関係の変更を検出し、メモリの安全性を保証できます。ライトバリアは非常に高速に設計されていますが、それでもオーバーヘッドは存在します。特に、不要なライトバリアはパフォーマンスに悪影響を与えます。

5.  **`unsafe.Pointer`と`uintptr`**:
    Goは通常、型安全性を厳密に強制しますが、`unsafe`パッケージを使用することで、低レベルのメモリ操作が可能になります。
    *   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムをバイパスして、異なる型のポインタ間で変換を行うことができます。
    *   `uintptr`: ポインタの値を保持できる符号なし整数型です。`unsafe.Pointer`と`uintptr`の間で相互に変換できます。これにより、ポインタの値を整数として扱ったり、整数値をポインタとして解釈したりすることが可能になります。
    これらの型は、Goの型安全性を損なう可能性があるため、慎重に使用する必要があります。Goランタイムのような低レベルのコードでは、OSとのインターフェースやハードウェアとの直接的なやり取りのために使用されることがあります。

## 技術的詳細

このコミットの技術的な核心は、Darwinプラットフォームにおける`siginfo`構造体の`si_addr`フィールドの型定義の変更と、それに伴うGoランタイムのシグナルハンドリングロジックの簡素化にあります。

**変更前**:
DarwinのGoランタイムでは、`siginfo`構造体の`si_addr`フィールドが以下のように定義されていました（例: `defs_darwin_386.go`）。

```go
type siginfo struct {
    // ...
    si_addr   *byte // バイトへのポインタ
    // ...
}
```

この`*byte`型はポインタ型であるため、Goのガベージコレクタは、このフィールドへの書き込み操作（`set_sigaddr`関数内）に対して自動的にライトバリアを挿入していました。しかし、コミットメッセージが指摘するように、この`si_addr`は「never points to anything real」（実際のGoヒープ上のオブジェクトを指すわけではない）ため、このライトバリアは完全に不要なオーバーヘッドでした。

さらに、`si_addr`の値を取得する`sigaddr()`関数や設定する`set_sigaddr()`関数では、このポインタ型を`uintXX`（符号なし整数）型に変換する必要がありました。

```go
// 変更前のsigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) sigaddr() uint32 { return uint32(uintptr(unsafe.Pointer(c.info.si_addr))) }

// 変更前のset_sigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) set_sigaddr(x uint32) { c.info.si_addr = (*byte)(unsafe.Pointer(uintptr(x))) }
```

これらのコードは、`unsafe.Pointer`と`uintptr`を介した冗長な型変換を含んでおり、コードの複雑性と潜在的なエラーのリスクを増大させていました。

**変更後**:
このコミットでは、`si_addr`フィールドの型を、各アーキテクチャのポインタサイズに対応する符号なし整数型に変更しました。

*   `defs_darwin_386.go` および `defs_darwin_arm.go` では `uint32` に変更。
*   `defs_darwin_amd64.go` では `uint64` に変更。

```go
// 変更後のsiginfo構造体の定義例 (386アーキテクチャ)
type siginfo struct {
    // ...
    si_addr   uint32 // 符号なし整数
    // ...
}
```

この変更により、`si_addr`はもはやポインタ型ではないため、`set_sigaddr`関数での書き込み時にガベージコレクタによるライトバリアが挿入されなくなりました。これにより、不要なパフォーマンスオーバーヘッドが解消されます。

また、`sigaddr()`および`set_sigaddr()`関数内の冗長な型変換も不要になり、コードが大幅に簡素化されました。

```go
// 変更後のsigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) sigaddr() uint32 { return c.info.si_addr }

// 変更後のset_sigaddr()の例 (386アーキテクチャ)
func (c *sigctxt) set_sigaddr(x uint32) { c.info.si_addr = x }
```

この変更は、GoランタイムがDarwinのシグナルハンドリングをより効率的かつGoの他のアーキテクチャと一貫性のある方法で処理できるようにするための重要な改善です。`si_addr`が実際にメモリ上のオブジェクトを指すわけではないという特性を考慮し、その型をより適切な整数型にすることで、ガベージコレクタの動作を最適化し、コードの保守性を向上させています。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがDarwin上でシグナル情報をどのように扱うかという低レベルな部分にあります。

Goランタイムは、OSからシグナルを受け取ると、そのシグナルに関する情報を`siginfo`構造体として受け取ります。この構造体はOSのシステムコールによって提供されるもので、Goランタイムはその定義をGoのコード内でミラーリングしています（`src/runtime/defs_darwin_*.go`）。

変更前は、Darwinの`siginfo`構造体内の`si_addr`フィールドが`*byte`型として定義されていました。これはGoの型システムにおいてポインタ型と認識されます。Goのガベージコレクタは、ポインタ型のフィールドへの書き込み操作を監視し、必要に応じてライトバリアを挿入します。ライトバリアは、GCがメモリの整合性を保つために、ポインタの変更を記録する小さな処理です。

しかし、この`si_addr`フィールドは、Goランタイムの文脈では「実際にはGoのヒープ上のオブジェクトを指すポインタではない」という特殊な性質を持っていました。例えば、`SIGSEGV`（セグメンテーション違反）のようなシグナルで`si_addr`がエラー発生アドレスを示す場合でも、そのアドレスはGoのガベージコレクタが管理するヒープ内のオブジェクトを指すとは限りません。そのため、`si_addr`への書き込み時にライトバリアが挿入されるのは、完全に無駄なオーバーヘッドとなっていました。

また、`siginfo`構造体から`si_addr`の値を取得する`sigctxt.sigaddr()`（または`sigctxt.fault()`）関数や、値を設定する`sigctxt.set_sigaddr()`関数では、この`*byte`型の`si_addr`を`uintXX`（符号なし整数）型として扱っていました。そのため、`unsafe.Pointer`と`uintptr`を介した複雑な型変換が必須となっていました。

このコミットでは、`si_addr`の型を`uint32`または`uint64`（アーキテクチャに応じて）に変更しました。これにより、以下のメリットが生まれました。

1.  **ライトバリアの排除**: `si_addr`がもはやポインタ型ではないため、`set_sigaddr()`関数での書き込み時にガベージコレクタによるライトバリアが挿入されなくなりました。これにより、Goランタイムのパフォーマンスがわずかに向上します。
2.  **コードの簡素化**: `sigaddr()`/`fault()`および`set_sigaddr()`関数から、`unsafe.Pointer`と`uintptr`を使った冗長な型変換が完全に削除されました。これにより、コードがより直接的で読みやすくなり、保守性が向上します。
3.  **アーキテクチャ間の一貫性**: Darwinプラットフォームの`si_addr`の型が、他のGoがサポートするアーキテクチャ（これらは既に`uint`型を使用していた）と一致するようになり、Goランタイム全体のコードベースの一貫性が高まりました。

この変更は、Goランタイムの内部的な最適化であり、Goプログラムのユーザーが直接その影響を感じることは少ないかもしれませんが、Goの実行効率と内部コードの品質向上に貢献しています。

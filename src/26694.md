# [インデックス 26694] ファイルの概要

このコミットは、Goランタイムにおけるメモリ比較関数 `memeq` と `memequal` の統合に関するものです。具体的には、`memequal` が `memeq` を呼び出す前に実行していたポインタの同一性チェック（ショートサーキット）を `memequal` 関数自体に組み込み、`memeq` 関数を廃止することで、関数呼び出しのオーバーヘッドを削減し、パフォーマンスを向上させています。

## 元コミット内容

このコミットは、Goランタイム内のメモリ比較関数 `memeq` と `memequal` を統合することを目的としています。これら二つの関数は本質的に同じメモリ領域の比較を行いますが、`memequal` は比較対象の二つのポインタが同一である場合に早期に `true` を返すショートサーキットチェックを含んでいました。

コミットの主な理由は以下の二点です。
A) ポインタの同一性チェックはわずか2命令で実行できるため、常にこのチェックを行うことにはほとんどコストがかかりません。
B) `memequal` が `memeq` を呼び出すという余分な関数呼び出しは、パフォーマンス上のオーバーヘッドとなっていました。

この変更により、`BenchmarkArrayEqual-8` ベンチマークでは、8.56 ns/op から 5.31 ns/op へと約37.97%の顕著なパフォーマンス改善が見られました。以前 `memeq` を使用していたマップ操作には目立った影響はありませんでした。

この変更は Issue #14302 を修正するものです。

## 変更の背景

Goランタイムには、メモリ領域を比較するための低レベルな関数がいくつか存在していました。その中でも `memeq` と `memequal` は、バイト列の等価性をチェックするという点で共通の目的を持っていました。しかし、`memequal` は、比較対象の2つのポインタ `p` と `q` が物理的に同じメモリ位置を指している場合、実際にメモリの内容を比較する前に `true` を返すという最適化（ショートサーキット）を含んでいました。一方、`memeq` はこのショートサーキットチェックを持たず、常にメモリの内容を比較していました。

問題は、`memequal` がこのショートサーキットチェックを行った後、実際のメモリ比較のために `memeq` を呼び出していた点にありました。これは、`memequal` が `memeq` のラッパーとして機能している状態であり、無駄な関数呼び出しのオーバーヘッドが発生していました。特に、頻繁に呼び出される可能性のあるメモリ比較処理において、このオーバーヘッドは無視できないものでした。

このコミットは、この冗長な構造を解消し、パフォーマンスを向上させることを目的としています。ポインタの同一性チェックは非常に安価な操作であるため、これを常に `memequal` の内部に含めることで、`memeq` を廃止し、関数呼び出しのコストを削減できるという背景があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、プリミティブな操作（メモリ比較など）といった低レベルな機能を提供します。Goの標準ライブラリの一部であり、Goプログラムのパフォーマンスに直接影響を与えます。

2.  **アセンブリ言語 (Assembly Language)**: コンピュータのプロセッサが直接理解できる機械語に非常に近い低レベルなプログラミング言語です。Goランタイムのパフォーマンスが重要な部分は、C言語やGo言語ではなく、特定のアセンブリ言語で実装されることがあります。これにより、プロセッサのレジスタや命令を直接操作し、最大限の効率を引き出すことが可能になります。このコミットでは、`src/runtime/asm_*.s` ファイル群が各アーキテクチャ（386, amd64, arm, arm64, mips64x, ppc64x）向けのアセンブリコードを含んでいます。

3.  **ポインタ (Pointer)**: メモリ上の特定のアドレスを指し示す変数です。Goでは `unsafe.Pointer` を使用することで、型安全性をバイパスして任意のメモリ位置を指すことができます。このコミットでは、`p` と `q` という二つの `unsafe.Pointer` が比較対象のメモリ領域の開始アドレスを示しています。

4.  **ショートサーキット評価 (Short-circuit Evaluation)**: 論理演算において、結果が確定した時点でそれ以降の評価を省略する最適化手法です。例えば、`A && B` の場合、`A` が `false` であれば `B` を評価せずに結果は `false` となります。このコミットの文脈では、`p == q` であれば、メモリの内容を比較するまでもなく `true` であると判断できるため、残りの比較処理をスキップするものです。

5.  **関数呼び出しのオーバーヘッド (Function Call Overhead)**: 関数を呼び出す際には、引数のスタックへのプッシュ、リターンアドレスの保存、レジスタの保存・復元、ジャンプ命令の実行など、いくつかの追加的な処理が発生します。これらの処理は、特に頻繁に呼び出される小さな関数において、プログラムの実行時間に無視できない影響を与えることがあります。このコミットは、`memequal` から `memeq` への余分な関数呼び出しを排除することで、このオーバーヘッドを削減しています。

6.  **ベンチマーク (Benchmark)**: プログラムの性能を測定するためのテストです。Goには `testing` パッケージがあり、`go test -bench=.` コマンドでベンチマークを実行できます。コミットメッセージにある `BenchmarkArrayEqual-8` は、配列の等価性チェックの性能を測定するベンチマークであり、`-8` はGOMAXPROCSが8であることを示します。

7.  **Goのマップ (Go Maps)**: Goの組み込みのハッシュマップデータ構造です。キーと値のペアを格納し、高速なルックアップを提供します。マップのキーの比較には、内部的にメモリ比較関数が使用されることがあります。コミットメッセージで「No noticeable affect on the former memeq user (maps)」とあるのは、この変更がマップの性能に悪影響を与えなかったことを示しています。

## 技術的詳細

このコミットの核心は、Goランタイムにおけるメモリ比較の効率化です。以前のGoランタイムでは、`memequal` と `memeq` という2つの関数がメモリ領域の等価性チェックを担当していました。

*   `memequal(p, q unsafe.Pointer, size uintptr) bool`: この関数は、まず `p == q` （つまり、2つのポインタが同じメモリ位置を指しているか）をチェックしていました。もし同じであれば、メモリの内容を比較するまでもなく `true` を返していました。そうでなければ、`memeq(p, q, size)` を呼び出して実際のバイト列比較を行っていました。
*   `memeq(p, q unsafe.Pointer, size uintptr) bool`: この関数は、`p` と `q` が指す `size` バイトのメモリ領域の内容を直接比較し、等しければ `true`、そうでなければ `false` を返していました。

この構造の問題点は、`memequal` が `memeq` を呼び出す際に発生する関数呼び出しのオーバーヘッドでした。特に、`memequal` のショートサーキットチェックが失敗し、かつ比較する `size` が小さい場合、関数呼び出しのコストが実際のメモリ比較のコストに比べて相対的に大きくなる可能性がありました。

このコミットでは、この冗長性を排除するために以下の変更が行われました。

1.  **`memeq` 関数の廃止**: `src/runtime/alg.go` からGo言語で実装されていた `memequal` のラッパー部分が削除され、`src/runtime/stubs.go` から `memeq` の宣言が削除されました。これにより、Go言語レベルでの `memeq` の存在がなくなりました。

2.  **`memequal` へのショートサーキットロジックの統合**: 各アーキテクチャ（386, amd64, arm, arm64, mips64x, ppc64x）向けのアセンブリ言語で実装されている `runtime·memeq` 関数が `runtime·memequal` にリネームされました。そして、この新しい `runtime·memequal` のアセンブリコードの冒頭に、ポインタ `p` と `q` が等しいかをチェックする命令が追加されました。
    *   例えば、x86-64 (amd64) アーキテクチャの場合、`CMPQ SI, DI` (SIとDIレジスタに格納されたポインタを比較) と `JEQ eq` (等しければ `eq` ラベルにジャンプ) という命令が追加されます。`eq` ラベルでは、結果を `true` に設定してすぐにリターンします。
    *   これにより、`memequal` は単一の関数として、ポインタの同一性チェックと実際のメモリ内容比較の両方を効率的に処理できるようになりました。

3.  **呼び出し箇所の更新**: `src/runtime/hashmap_fast.go` など、以前 `memeq` を呼び出していた箇所はすべて `memequal` を呼び出すように変更されました。また、`src/runtime/asm_arm.s` や `src/runtime/asm_arm64.s` の `memequal_varlen` のような関連するアセンブリ関数も、`memeq` ではなく `memequal` を呼び出すように修正されています。

この変更の技術的な利点は以下の通りです。

*   **関数呼び出しオーバーヘッドの削減**: `memequal` が `memeq` を呼び出すという二重の関数呼び出しが解消され、特にショートサーキットが適用されないケースでの実行パスが短縮されました。
*   **性能向上**: ベンチマーク結果が示すように、配列の等価性チェックのような操作で顕著な性能改善が見られました。これは、アセンブリレベルでの最適化と関数呼び出しの削減が直接的に寄与した結果です。
*   **コードの簡素化**: `memeq` と `memequal` という2つの類似した関数が存在する状態が解消され、コードベースがよりシンプルになりました。

このコミットは、Goランタイムが低レベルな最適化をいかに重視しているかを示す良い例です。わずか数命令の追加と関数呼び出しの削減が、特定の操作において数十パーセントの性能向上をもたらすことがあります。

## コアとなるコードの解説

このコミットの最も重要な変更は、各アーキテクチャのアセンブリコードにおける `memeq` から `memequal` への移行と、その内部でのショートサーキットロジックの実装です。

例として、`src/runtime/asm_amd64.s` の変更を見てみましょう。

```assembly
// memequal(p, q unsafe.Pointer, size uintptr) bool
TEXT runtime·memequal(SB),NOSPLIT,$0-25
	MOVQ	a+0(FP), SI  // p (unsafe.Pointer) を SI レジスタにロード
	MOVQ	b+8(FP), DI  // q (unsafe.Pointer) を DI レジスタにロード
	CMPQ	SI, DI       // SI (p) と DI (q) を比較
	JEQ	eq           // もし等しければ、eq ラベルにジャンプ（ショートサーキット）
	MOVQ	size+16(FP), BX // size (uintptr) を BX レジスタにロード
	LEAQ	ret+24(FP), AX // 戻り値のアドレスを AX レジスタにロード
	JMP	runtime·memeqbody(SB) // 実際のメモリ比較を行う memeqbody にジャンプ
eq:
	MOVB	$1, ret+24(FP) // 戻り値 (bool) を true (1) に設定
	RET                  // 関数からリターン
```

**解説:**

1.  **`TEXT runtime·memequal(SB),NOSPLIT,$0-25`**:
    *   これは `runtime·memequal` という名前のアセンブリ関数を定義しています。`SB` は静的ベースポインタ、`NOSPLIT` はスタックフレームの分割を行わないことを示し、`$0-25` はスタックフレームサイズが0バイト、引数と戻り値の合計サイズが25バイトであることを示します。
    *   `// memequal(p, q unsafe.Pointer, size uintptr) bool` は、このアセンブリ関数がGo言語の `memequal(p, q unsafe.Pointer, size uintptr) bool` に対応することを示しています。

2.  **`MOVQ a+0(FP), SI` / `MOVQ b+8(FP), DI`**:
    *   `a+0(FP)` はフレームポインタ (FP) からのオフセットで、Go関数 `memequal` の最初の引数 `p` (unsafe.Pointer) を参照します。その値を `SI` レジスタに移動します。
    *   同様に、`b+8(FP)` は2番目の引数 `q` (unsafe.Pointer) を参照し、その値を `DI` レジスタに移動します。`MOVQ` は64ビット値を移動する命令です。

3.  **`CMPQ SI, DI`**:
    *   `CMPQ` 命令は、`SI` レジスタと `DI` レジスタの内容を比較します。これは、ポインタ `p` と `q` が同じメモリアドレスを指しているかどうかをチェックするものです。

4.  **`JEQ eq`**:
    *   `JEQ` (Jump if Equal) 命令は、直前の比較 (`CMPQ`) の結果が等しい場合、つまり `p == q` である場合に、`eq` というラベルにジャンプします。これがショートサーキットロジックの核心です。ポインタが同じであれば、メモリの内容を比較する必要はありません。

5.  **`MOVQ size+16(FP), BX` / `LEAQ ret+24(FP), AX` / `JMP runtime·memeqbody(SB)`**:
    *   もし `p != q` であれば、ショートサーキットは発生せず、通常のメモリ比較に進みます。
    *   `size+16(FP)` から3番目の引数 `size` を `BX` レジスタにロードします。
    *   `ret+24(FP)` は戻り値 `bool` のメモリ位置を参照します。そのアドレスを `AX` レジスタにロードします。
    *   `JMP runtime·memeqbody(SB)` は、実際のバイト列比較を行う `runtime·memeqbody` 関数にジャンプします。この関数は、`p` と `q` が指す `size` バイトのメモリ領域を比較し、結果を `AX` が指すアドレスに書き込みます。

6.  **`eq:`**:
    *   `JEQ eq` によってジャンプしてきた場合の処理です。

7.  **`MOVB $1, ret+24(FP)`**:
    *   `MOVB` 命令は1バイトの値を移動します。`$1` は即値の1（`true` を意味する）です。
    *   `ret+24(FP)` は戻り値のメモリ位置なので、ここに `1` を書き込むことで、`memequal` が `true` を返すように設定します。

8.  **`RET`**:
    *   関数から呼び出し元にリターンします。

このアセンブリコードの変更により、`memequal` はポインタの同一性チェックを非常に効率的に行い、もしポインタが同じであれば、高価なメモリ比較ループを実行することなく即座に結果を返すことができるようになりました。これにより、特に同じオブジェクトへの参照を比較するようなシナリオで、顕著なパフォーマンス向上が期待できます。

## 元コミット内容

このコミットは、Goランタイム内のメモリ比較関数 `memeq` と `memequal` を統合することを目的としています。これら二つの関数は本質的に同じメモリ領域の比較を行いますが、`memequal` は比較対象の二つのポインタが同一である場合に早期に `true` を返すショートサーキットチェックを含んでいました。

コミットの主な理由は以下の二点です。
A) ポインタの同一性チェックはわずか2命令で実行できるため、常にこのチェックを行うことにはほとんどコストがかかりません。
B) `memequal` が `memeq` を呼び出すという余分な関数呼び出しは、パフォーマンス上のオーバーヘッドとなっていました。

この変更により、`BenchmarkArrayEqual-8` ベンチマークでは、8.56 ns/op から 5.31 ns/op へと約37.97%の顕著なパフォーマンス改善が見られました。以前 `memeq` を使用していたマップ操作には目立った影響はありませんでした。

この変更は Issue #14302 を修正するものです。

## 変更の背景

Goランタイムには、メモリ領域を比較するための低レベルな関数がいくつか存在していました。その中でも `memeq` と `memequal` は、バイト列の等価性をチェックするという点で共通の目的を持っていました。しかし、`memequal` は、比較対象の二つのポインタ `p` と `q` が物理的に同じメモリ位置を指している場合、実際にメモリの内容を比較する前に `true` を返すという最適化（ショートサーキット）を含んでいました。一方、`memeq` はこのショートサーキットチェックを持たず、常にメモリの内容を比較していました。

問題は、`memequal` がこのショートサーキットチェックを行った後、実際のメモリ比較のために `memeq` を呼び出していた点にありました。これは、`memequal` が `memeq` のラッパーとして機能している状態であり、無駄な関数呼び出しのオーバーヘッドが発生していました。特に、頻繁に呼び出される可能性のあるメモリ比較処理において、このオーバーヘッドは無視できないものでした。

このコミットは、この冗長な構造を解消し、パフォーマンスを向上させることを目的としています。ポインタの同一性チェックは非常に安価な操作であるため、これを常に `memequal` の内部に含めることで、`memeq` を廃止し、関数呼び出しのコストを削減できるという背景があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、プリミティブな操作（メモリ比較など）といった低レベルな機能を提供します。Goの標準ライブラリの一部であり、Goプログラムのパフォーマンスに直接影響を与えます。

2.  **アセンブリ言語 (Assembly Language)**: コンピュータのプロセッサが直接理解できる機械語に非常に近い低レベルなプログラミング言語です。Goランタイムのパフォーマンスが重要な部分は、C言語やGo言語ではなく、特定のアセンブリ言語で実装されることがあります。これにより、プロセッサのレジスタや命令を直接操作し、最大限の効率を引き出すことが可能になります。このコミットでは、`src/runtime/asm_*.s` ファイル群が各アーキテクチャ（386, amd64, arm, arm64, mips64x, ppc64x）向けのアセンブリコードを含んでいます。

3.  **ポインタ (Pointer)**: メモリ上の特定のアドレスを指し示す変数です。Goでは `unsafe.Pointer` を使用することで、型安全性をバイパスして任意のメモリ位置を指すことができます。このコミットでは、`p` と `q` という二つの `unsafe.Pointer` が比較対象のメモリ領域の開始アドレスを示しています。

4.  **ショートサーキット評価 (Short-circuit Evaluation)**: 論理演算において、結果が確定した時点でそれ以降の評価を省略する最適化手法です。例えば、`A && B` の場合、`A` が `false` であれば `B` を評価せずに結果は `false` となります。このコミットの文脈では、`p == q` であれば、メモリの内容を比較するまでもなく `true` であると判断できるため、残りの比較処理をスキップするものです。

5.  **関数呼び出しのオーバーヘッド (Function Call Overhead)**: 関数を呼び出す際には、引数のスタックへのプッシュ、リターンアドレスの保存、レジスタの保存・復元、ジャンプ命令の実行など、いくつかの追加的な処理が発生します。これらの処理は、特に頻繁に呼び出される小さな関数において、プログラムの実行時間に無視できない影響を与えることがあります。このコミットは、`memequal` から `memeq` への余分な関数呼び出しを排除することで、このオーバーヘッドを削減しています。

6.  **ベンチマーク (Benchmark)**: プログラムの性能を測定するためのテストです。Goには `testing` パッケージがあり、`go test -bench=.` コマンドでベンチマークを実行できます。コミットメッセージにある `BenchmarkArrayEqual-8` は、配列の等価性チェックの性能を測定するベンチマークであり、`-8` はGOMAXPROCSが8であることを示します。

7.  **Goのマップ (Go Maps)**: Goの組み込みのハッシュマップデータ構造です。キーと値のペアを格納し、高速なルックアップを提供します。マップのキーの比較には、内部的にメモリ比較関数が使用されることがあります。コミットメッセージで「No noticeable affect on the former memeq user (maps)」とあるのは、この変更がマップの性能に悪影響を与えなかったことを示しています。

## 技術的詳細

このコミットの核心は、Goランタイムにおけるメモリ比較の効率化です。以前のGoランタイムでは、`memequal` と `memeq` という2つの関数がメモリ領域の等価性チェックを担当していました。

*   `memequal(p, q unsafe.Pointer, size uintptr) bool`: この関数は、まず `p == q` （つまり、2つのポインタが同じメモリ位置を指しているか）をチェックしていました。もし同じであれば、メモリの内容を比較するまでもなく `true` を返していました。そうでなければ、`memeq(p, q, size)` を呼び出して実際のバイト列比較を行っていました。
*   `memeq(p, q unsafe.Pointer, size uintptr) bool`: この関数は、`p` と `q` が指す `size` バイトのメモリ領域の内容を直接比較し、等しければ `true`、そうでなければ `false` を返していました。

この構造の問題点は、`memequal` が `memeq` を呼び出す際に発生する関数呼び出しのオーバーヘッドでした。特に、`memequal` のショートサーキットチェックが失敗し、かつ比較する `size` が小さい場合、関数呼び出しのコストが実際のメモリ比較のコストに比べて相対的に大きくなる可能性がありました。

このコミットでは、この冗長性を排除するために以下の変更が行われました。

1.  **`memeq` 関数の廃止**: `src/runtime/alg.go` からGo言語で実装されていた `memequal` のラッパー部分が削除され、`src/runtime/stubs.go` から `memeq` の宣言が削除されました。これにより、Go言語レベルでの `memeq` の存在がなくなりました。

2.  **`memequal` へのショートサーキットロジックの統合**: 各アーキテクチャ（386, amd64, arm, arm64, mips64x, ppc64x）向けのアセンブリ言語で実装されている `runtime·memeq` 関数が `runtime·memequal` にリネームされました。そして、この新しい `runtime·memequal` のアセンブリコードの冒頭に、ポインタ `p` と `q` が等しいかをチェックする命令が追加されました。
    *   例えば、x86-64 (amd64) アーキテクチャの場合、`CMPQ SI, DI` (SIとDIレジスタに格納されたポインタを比較) と `JEQ eq` (等しければ `eq` ラベルにジャンプ) という命令が追加されます。`eq` ラベルでは、結果を `true` に設定してすぐにリターンします。
    *   これにより、`memequal` は単一の関数として、ポインタの同一性チェックと実際のメモリ内容比較の両方を効率的に処理できるようになりました。

3.  **呼び出し箇所の更新**: `src/runtime/hashmap_fast.go` など、以前 `memeq` を呼び出していた箇所はすべて `memequal` を呼び出すように変更されました。また、`src/runtime/asm_arm.s` や `src/runtime/asm_arm64.s` の `memequal_varlen` のような関連するアセンブリ関数も、`memeq` ではなく `memequal` を呼び出すように修正されています。

この変更の技術的な利点は以下の通りです。

*   **関数呼び出しオーバーヘッドの削減**: `memequal` が `memeq` を呼び出すという二重の関数呼び出しが解消され、特にショートサーキットが適用されないケースでの実行パスが短縮されました。
*   **性能向上**: ベンチマーク結果が示すように、配列の等価性チェックのような操作で顕著な性能改善が見られました。これは、アセンブリレベルでの最適化と関数呼び出しの削減が直接的に寄与した結果です。
*   **コードの簡素化**: `memeq` と `memequal` という2つの類似した関数が存在する状態が解消され、コードベースがよりシンプルになりました。

このコミットは、Goランタイムが低レベルな最適化をいかに重視しているかを示す良い例です。わずか数命令の追加と関数呼び出しの削減が、特定の操作において数十パーセントの性能向上をもたらすことがあります。

## コアとなるコードの解説

このコミットの最も重要な変更は、各アーキテクチャのアセンブリコードにおける `memeq` から `memequal` への移行と、その内部でのショートサーキットロジックの実装です。

例として、`src/runtime/asm_amd64.s` の変更を見てみましょう。

```assembly
// memequal(p, q unsafe.Pointer, size uintptr) bool
TEXT runtime·memequal(SB),NOSPLIT,$0-25
	MOVQ	a+0(FP), SI  // p (unsafe.Pointer) を SI レジスタにロード
	MOVQ	b+8(FP), DI  // q (unsafe.Pointer) を DI レジスタにロード
	CMPQ	SI, DI       // SI (p) と DI (q) を比較
	JEQ	eq           // もし等しければ、eq ラベルにジャンプ（ショートサーキット）
	MOVQ	size+16(FP), BX // size (uintptr) を BX レジスタにロード
	LEAQ	ret+24(FP), AX // 戻り値のアドレスを AX レジスタにロード
	JMP	runtime·memeqbody(SB) // 実際のメモリ比較を行う memeqbody にジャンプ
eq:
	MOVB	$1, ret+24(FP) // 戻り値 (bool) を true (1) に設定
	RET                  // 関数からリターン
```

**解説:**

1.  **`TEXT runtime·memequal(SB),NOSPLIT,$0-25`**:
    *   これは `runtime·memequal` という名前のアセンブリ関数を定義しています。`SB` は静的ベースポインタ、`NOSPLIT` はスタックフレームの分割を行わないことを示し、`$0-25` はスタックフレームサイズが0バイト、引数と戻り値の合計サイズが25バイトであることを示します。
    *   `// memequal(p, q unsafe.Pointer, size uintptr) bool` は、このアセンブリ関数がGo言語の `memequal(p, q unsafe.Pointer, size uintptr) bool` に対応することを示しています。

2.  **`MOVQ a+0(FP), SI` / `MOVQ b+8(FP), DI`**:
    *   `a+0(FP)` はフレームポインタ (FP) からのオフセットで、Go関数 `memequal` の最初の引数 `p` (unsafe.Pointer) を参照します。その値を `SI` レジスタに移動します。
    *   同様に、`b+8(FP)` は2番目の引数 `q` (unsafe.Pointer) を参照し、その値を `DI` レジスタに移動します。`MOVQ` は64ビット値を移動する命令です。

3.  **`CMPQ SI, DI`**:
    *   `CMPQ` 命令は、`SI` レジスタと `DI` レジスタの内容を比較します。これは、ポインタ `p` と `q` が同じメモリアドレスを指しているかどうかをチェックするものです。

4.  **`JEQ eq`**:
    *   `JEQ` (Jump if Equal) 命令は、直前の比較 (`CMPQ`) の結果が等しい場合、つまり `p == q` である場合に、`eq` というラベルにジャンプします。これがショートサーキットロジックの核心です。ポインタが同じであれば、メモリの内容を比較する必要はありません。

5.  **`MOVQ size+16(FP), BX` / `LEAQ ret+24(FP), AX` / `JMP runtime·memeqbody(SB)`**:
    *   もし `p != q` であれば、ショートサーキットは発生せず、通常のメモリ比較に進みます。
    *   `size+16(FP)` から3番目の引数 `size` を `BX` レジスタにロードします。
    *   `ret+24(FP)` は戻り値 `bool` のメモリ位置を参照します。そのアドレスを `AX` レジスタにロードします。
    *   `JMP runtime·memeqbody(SB)` は、実際のバイト列比較を行う `runtime·memeqbody` 関数にジャンプします。この関数は、`p` と `q` が指す `size` バイトのメモリ領域を比較し、結果を `AX` が指すアドレスに書き込みます。

6.  **`eq:`**:
    *   `JEQ eq` によってジャンプしてきた場合の処理です。

7.  **`MOVB $1, ret+24(FP)`**:
    *   `MOVB` 命令は1バイトの値を移動します。`$1` は即値の1（`true` を意味する）です。
    *   `ret+24(FP)` は戻り値のメモリ位置なので、ここに `1` を書き込むことで、`memequal` が `true` を返すように設定します。

8.  **`RET`**:
    *   関数から呼び出し元にリターンします。

このアセンブリコードの変更により、`memequal` はポインタの同一性チェックを非常に効率的に行い、もしポインタが同じであれば、高価なメモリ比較ループを実行することなく即座に結果を返すことができるようになりました。これにより、特に同じオブジェクトへの参照を比較するようなシナリオで、顕著なパフォーマンス向上が期待できます。

## 元コミット内容

`cmd/link: concurrent obj copy for external linking`

このコミットは、外部リンキングの際にオブジェクトファイルをコピーする処理を並行化することで、パフォーマンスを向上させることを目的としています。

## 変更の背景

Go言語のビルドプロセスにおいて、`cmd/link` はコンパイルされたオブジェクトファイルを結合し、実行可能ファイルを生成する役割を担います。特に、C/C++コードなどGo以外の言語で書かれたライブラリとリンクする「外部リンキング (external linking)」の場合、Goのリンカは外部のリンカ（通常はGCCなど）を呼び出す必要があります。

この外部リンキングの過程で、Goのリンカは外部リンカが処理できるように、Goのオブジェクトファイルを一時ディレクトリにコピーすることがあります。このコピー処理が、特に多数のオブジェクトファイルが存在する場合や、ファイルサイズが大きい場合に、ビルド時間のボトルネックとなる可能性がありました。

このコミットの背景には、このオブジェクトファイルのコピー処理を並行化することで、ビルド時間を短縮し、開発者の生産性を向上させるという目的があります。複数のファイルを同時にコピーすることで、I/Oの待ち時間を有効活用し、全体のスループットを向上させることが期待されます。

## 前提知識の解説

### Goのリンカ (`cmd/link`)

`cmd/link` はGoツールチェーンの一部であり、Goコンパイラ (`cmd/compile`) によって生成されたオブジェクトファイル（`.o` ファイル）を結合して、実行可能なバイナリや共有ライブラリを生成するプログラムです。Goのリンカは、Go独自のオブジェクトファイル形式を理解し、シンボル解決、再配置、デッドコード削除などの処理を行います。

### 外部リンキング (External Linking)

GoプログラムがC言語のライブラリ（cgo経由）や、システムライブラリ（例: `net` パッケージが使用するDNSリゾルバなど）とリンクする場合、Goの標準リンカだけでは完結できないことがあります。このような場合、Goのリンカは外部のシステムリンカ（通常はGCCやClang）を呼び出して最終的なリンク処理を行わせます。これを「外部リンキング」と呼びます。

外部リンキングでは、Goのオブジェクトファイルが外部リンカが理解できる形式（通常はELFやMach-Oなど）に変換され、一時ディレクトリに配置された後、外部リンカに渡されます。この一時ディレクトリへのオブジェクトファイルのコピーが、本コミットで並行化の対象となった処理です。

### `sync.WaitGroup`

`sync.WaitGroup` はGoの標準ライブラリ `sync` パッケージで提供される同期プリミティブの一つです。複数のGoroutineが完了するのを待つために使用されます。

*   `Add(delta int)`: 待機するGoroutineのカウンターを `delta` だけ増やします。
*   `Done()`: 待機するGoroutineのカウンターを1だけ減らします。通常は `defer` ステートメントで呼び出されます。
*   `Wait()`: カウンターがゼロになるまでブロックします。

### `chan struct{}` を用いたセマフォ

Goのチャネルは、Goroutine間の通信だけでなく、並行処理の制御（セマフォやミューテックスなど）にも利用できます。`chan struct{}` は、要素の型が空の構造体であるチャネルです。`struct{}` はメモリを消費しないため、セマフォとして使用する際に効率的です。

このコミットでは、バッファ付きチャネル `make(chan struct{}, N)` をセマフォとして使用しています。
*   `sema <- struct{}{}`: チャネルに値を送信しようとします。チャネルが満杯の場合（`N`個のGoroutineが既に実行中の場合）、ブロックされます。これにより、同時に実行されるGoroutineの数を `N` に制限できます。
*   `<-sema`: チャネルから値を受信します。これにより、Goroutineが完了したことを示し、他のGoroutineがチャネルに値を送信できるようになります。

このメカニズムは、リソース（この場合はファイルディスクリプタやCPUコア）の利用を制限し、システムへの過負荷を防ぐために非常に有効です。

### ファイルI/Oにおける並行処理のメリットと注意点

**メリット:**
*   **スループットの向上:** 複数のファイルを同時に読み書きすることで、ディスクI/Oの並列性を高め、全体のスループットを向上させることができます。特にSSDのような高速なストレージでは、複数のI/Oリクエストを同時に処理できるため効果的です。
*   **CPUの有効活用:** I/O待ちの間に他のGoroutineがCPUを利用できるため、CPUリソースをより効率的に活用できます。

**注意点:**
*   **リソースの枯渇:** ファイルディスクリプタ、メモリ、CPUなどのシステムリソースには限りがあります。無制限に並行処理を行うと、これらのリソースが枯渇し、システム全体のパフォーマンスが低下したり、エラーが発生したりする可能性があります。
*   **競合状態:** 複数のGoroutineが同じリソース（例: 同じファイルへの書き込み）にアクセスする場合、競合状態が発生しないように適切な同期メカニズム（ミューテックス、セマフォなど）が必要です。このコミットでは、各ファイルが独立してコピーされるため、ファイル自体への競合は発生しませんが、システムリソースの制限が重要になります。

## 技術的詳細

このコミットは、`src/cmd/link/internal/ld/lib.go` 内の `hostobjCopy` 関数を修正し、外部リンキングのためにオブジェクトファイルを一時ディレクトリにコピーする処理を並行化します。

### `hostobjCopy` 関数の役割

`hostobjCopy` 関数は、`hostobj` スライスに格納されているオブジェクトファイルの情報（ファイルパス、オフセット、長さなど）を基に、それらのオブジェクトファイルを一時ディレクトリ (`tmpdir`) にコピーし、コピーされたファイルのパスのリストを返します。

### 変更前と変更後のコードの比較

**変更前:**
変更前のコードは、`hostobj` スライスをループで順次処理し、各オブジェクトファイルを一つずつコピーしていました。これは単純で理解しやすい実装ですが、I/Oバウンドな処理であるため、コピー対象のファイル数が増えるにつれて線形に時間がかかっていました。

```go
func hostobjCopy() (paths []string) {
	for i, h := range hostobj {
		f, err := os.Open(h.file)
		// ... エラーハンドリング ...
		if _, err := f.Seek(h.off, 0); err != nil {
			// ... エラーハンドリング ...
		}

		p := fmt.Sprintf("%s/%06d.o", tmpdir, i)
		paths = append(paths, p)
		w, err := os.Create(p)
		// ... エラーハンドリング ...
		if _, err := io.CopyN(w, f, h.length); err != nil {
			// ... エラーハンドリング ...
		}
		if err := w.Close(); err != nil {
			// ... エラーハンドリング ...
		}
	}
	return paths
}
```

**変更後:**
変更後のコードでは、`sync.WaitGroup` と `chan struct{}` を用いたセマフォを導入し、オブジェクトファイルのコピー処理をGoroutineで並行実行するようにしました。

### `sync.WaitGroup` の導入方法

`var wg sync.WaitGroup` を宣言し、各コピー処理をGoroutineで起動する前に `wg.Add(1)` を呼び出します。各Goroutineの処理が完了する際には `defer wg.Done()` を呼び出し、全てのGoroutineの完了を待つためにループの後に `wg.Wait()` を呼び出しています。

### `sema` (セマフォ) の実装と目的

`sema := make(chan struct{}, runtime.NumCPU())`
この行で、CPUの論理コア数 (`runtime.NumCPU()`) に等しいバッファサイズを持つ `struct{}` 型のチャネルを作成しています。これは、同時に実行されるファイルコピーGoroutineの数をCPUコア数に制限するためのセマフォとして機能します。

*   `sema <- struct{}{}`: 各Goroutineが処理を開始する前にチャネルに値を送信します。これにより、同時に実行されるGoroutineの数が `runtime.NumCPU()` を超えないように制御されます。チャネルが満杯の場合、Goroutineはブロックされ、他のGoroutineが完了してチャネルから値が読み出されるのを待ちます。
*   `defer func() { <-sema; wg.Done() }()`: 各Goroutineが終了する際に、チャネルから値を読み出し、セマフォを解放します。これにより、別のGoroutineが処理を開始できるようになります。`wg.Done()` もここで呼び出され、`WaitGroup` のカウンターを減らします。

このセマフォの導入により、システムのリソース（特にファイルディスクリプタやI/O帯域）を過度に消費することなく、効率的に並行処理を行うことができます。`runtime.NumCPU()` を上限とすることで、CPUバウンドな処理ではないものの、I/O処理のオーバーヘッドやコンテキストスイッチのコストを考慮し、最適な並行度を模索しています。

### `go func()` でのGoroutineの起動とクロージャのキャプチャ

`for i, h := range hostobj` ループ内で、各オブジェクトファイルに対して `go func() { ... }()` を使って新しいGoroutineを起動しています。

重要な変更点として、ループ変数 `h` をGoroutine内で直接使用するのではなく、`h := h` という行を追加して、ループ変数の値をGoroutineローカルな変数 `h` にコピーしています。これはGoのクロージャの挙動によるもので、ループ内でGoroutineを起動する際にループ変数を直接参照すると、全てのGoroutineがループの最後の値を見てしまうという一般的なバグを防ぐためのイディオムです。これにより、各Goroutineは自身の `h` のコピーを参照し、正しいオブジェクトファイル情報を処理できます。

### `defer` を使ったセマフォの解放と`WaitGroup`の完了通知

各Goroutineの内部では、`defer func() { <-sema; wg.Done() }()` が使用されています。これにより、Goroutineが正常に完了した場合でも、エラーで早期リターンした場合でも、必ずセマフォが解放され、`WaitGroup` のカウンターが減らされることが保証されます。これは堅牢な並行処理を実装する上で非常に重要です。

## コアとなるコードの解説

1.  **`import "sync"` の追加**:
    並行処理を制御するために `sync.WaitGroup` を使用するため、`sync` パッケージがインポートされました。

2.  **`var wg sync.WaitGroup` の宣言**:
    `hostobjCopy` 関数の冒頭で `sync.WaitGroup` のインスタンス `wg` が宣言されました。これは、起動するすべてのGoroutineの完了を待つために使用されます。

3.  **`sema := make(chan struct{}, runtime.NumCPU())` の宣言**:
    セマフォとして機能するバッファ付きチャネル `sema` が作成されました。バッファサイズは `runtime.NumCPU()` によって決定され、同時に実行されるファイルコピーGoroutineの数をCPUコア数に制限します。これにより、システムリソースの過負荷を防ぎます。

4.  **`for` ループ内の変更**:
    *   **`h := h`**: ループ変数 `h` の値をGoroutineローカルな変数 `h` にコピーしています。これにより、各Goroutineがループの反復ごとに正しい `h` の値（オブジェクトファイル情報）を参照することが保証されます。
    *   **`dst := fmt.Sprintf("%s/%06d.o", tmpdir, i)`**: コピー先ファイルパスの生成はループ内で引き続き行われます。
    *   **`paths = append(paths, dst)`**: コピーされたファイルのパスを `paths` スライスに追加します。この操作はGoroutineの外で行われるため、競合状態は発生しません。
    *   **`wg.Add(1)`**: 各Goroutineを起動する直前に `wg.Add(1)` が呼び出され、`WaitGroup` のカウンターを増やします。
    *   **`go func() { ... }()`**: ファイルコピーのロジック全体が匿名関数内にラップされ、`go` キーワードを使って新しいGoroutineとして起動されます。
        *   **`sema <- struct{}{}`**: Goroutineが実行を開始する前にセマフォを取得します。これにより、並行実行されるGoroutineの数が制限されます。
        *   **`defer func() { <-sema; wg.Done() }()`**: Goroutineが終了する際に、セマフォを解放し (`<-sema`)、`WaitGroup` のカウンターを減らします (`wg.Done()`)。`defer` を使用することで、Goroutineがどのように終了しても（正常終了、エラーによるパニックなど）、これらのクリーンアップ処理が確実に実行されます。
        *   ファイルを開き、シークし、一時ファイルを作成し、`io.CopyN` で内容をコピーし、ファイルを閉じるという一連のファイルI/O処理がこのGoroutine内で実行されます。エラーが発生した場合は `Exitf` でプログラムを終了させます。

5.  **`wg.Wait()` の呼び出し**:
    `for` ループの後に `wg.Wait()` が呼び出されます。これにより、`hostobj` スライス内のすべてのオブジェクトファイルのコピーが完了するまで、`hostobjCopy` 関数はブロックされます。すべてのGoroutineが `wg.Done()` を呼び出してカウンターがゼロになると、`wg.Wait()` はブロックを解除し、関数はコピーされたファイルのパスを返します。

この変更により、複数のオブジェクトファイルのコピーが並行して行われるようになり、特にI/Oがボトルネックとなる環境において、外部リンキングを含むビルドプロセスの全体的な速度が向上します。

# [インデックス 28118] ファイルの概要

このコミットは、Goランタイムにおけるメモリ割り当て時のゼロ初期化処理を最適化するものです。具体的には、新しく割り当てられるオブジェクトがすでにゼロであることが保証されている場合に、不要なゼロ初期化（`memclr`呼び出し）をスキップするメカニズムを再導入しています。これにより、特に多数の小さなオブジェクトを頻繁に割り当てるアプリケーションにおいて、パフォーマンスの向上が期待されます。

    Currently we always zero objects when we allocate them. We used to
    have an optimization that would not zero objects that had not been
    allocated since the whole span was last zeroed (either by getting it
    from the system or by getting it from the heap, which does a bulk
    zero), but this depended on the sweeper clobbering the first two words
    of each object. Hence, we lost this optimization when the bitmap
    sweeper went away.

    Re-introduce this optimization using a different mechanism. Each span
    already keeps a flag indicating that it just came from the OS or was
    just bulk zeroed by the mheap. We can simply use this flag to know
    when we don't need to zero an object. This is slightly less efficient
    than the old optimization: if a span gets allocated and partially
    used, then GC happens and the span gets returned to the mcentral, then
    the span gets re-acquired, the old optimization knew that it only had
    to re-zero the objects that had been reclaimed, whereas this
    optimization will re-zero everything. However, in this case, you're
    already paying for the garbage collection, and you've only wasted one
    zeroing of the span, so in practice there seems to be little
    difference. (If we did want to revive the full optimization, each span
    could keep track of a frontier beyond which all free slots are zeroed.
    I prototyped this and it didn't obvious do any better than the much
    simpler approach in this commit.)

    This significantly improves BinaryTree17, which is allocation-heavy
    (and runs first, so most pages are already zeroed), and slightly
    improves everything else.

## 変更の背景

Goランタイムでは、メモリの安全性を確保し、予測可能な動作を提供するために、新しく割り当てられたオブジェクトのメモリ領域をゼロで初期化することが一般的です。しかし、このゼロ初期化はパフォーマンス上のオーバーヘッドを伴います。

過去には、Goランタイムには「no-zeroing optimization」（ゼロ初期化をスキップする最適化）が存在していました。これは、OSから取得したばかりのメモリ領域や、ヒープによって一括でゼロ初期化されたメモリ領域（スパン）からオブジェクトを割り当てる際に、そのオブジェクトがすでにゼロであることが保証されているため、個別のゼロ初期化をスキップするというものでした。この最適化は、ガベージコレクタ（GC）のスイーパーが各オブジェクトの最初の2ワードを上書きすることに依存していました。

しかし、Goランタイムの進化に伴い、この「ビットマップスイーパー」の動作が変更された（または「なくなった」とコミットメッセージに記載されている）結果、この依存関係が失われ、no-zeroing optimizationも機能しなくなりました。その結果、すべてのオブジェクトが割り当て時に常にゼロ初期化されるようになり、特にメモリ割り当てが頻繁に行われるシナリオでパフォーマンスが低下していました。

このコミットの目的は、失われたno-zeroing optimizationを、より堅牢で現在のランタイムアーキテクチャに適した新しいメカニズムで再導入することです。これにより、不要なゼロ初期化を削減し、全体的なメモリ割り当て性能を向上させることを目指しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理の基本的な概念と、ガベージコレクションの仕組みについて知っておく必要があります。

### Goランタイムのメモリ管理階層

Goのメモリ管理は、TCMallocにインスパイアされた階層的な構造を持っています。

1.  **`mheap` (グローバルヒープ)**:
    *   Goランタイムが管理するすべての動的に割り当てられたメモリの最上位の管理者です。
    *   OSから直接メモリページ（通常8KB単位）を取得し、それらを`mspan`に分割して管理します。
    *   大きなオブジェクト（通常32KB以上）は`mheap`から直接割り当てられます。

2.  **`mcentral` (セントラルキャッシュ)**:
    *   各オブジェクトサイズクラス（Goはオブジェクトを約68種類のサイズクラスに分類します）ごとに1つ存在します。
    *   `mcache`と`mheap`の間の橋渡し役を担います。
    *   空きオブジェクトを持つ`mspan`のリスト（`nonempty`）と、空きオブジェクトがない`mspan`のリスト（`empty`）を管理します。
    *   `mcache`が`mspan`を要求した際に提供し、`mspan`が不足した場合は`mheap`から新しいページを取得して`mspan`を作成します。`mcentral`へのアクセスはロックを伴います。

3.  **`mcache` (Pごとのキャッシュ)**:
    *   Goスケジューラにおける各論理プロセッサ（P）に紐付けられたローカルキャッシュです。
    *   ロックなしで高速に小さなオブジェクト（通常32KB未満）を割り当てるために使用されます。
    *   各サイズクラスに対応する`mspan`のコレクションを保持しています。
    *   ゴルーチンが小さなオブジェクトを割り当てる際、まず自身のPの`mcache`からメモリを取得しようとします。

4.  **`mspan`**:
    *   Goメモリ管理の基本的な単位であり、1つ以上の連続した8KBメモリページで構成されます。
    *   特定のサイズクラスのオブジェクトのみを格納します。
    *   `allocBits`などのビットマップを持ち、スパン内のどのオブジェクトが割り当て済みか、空きか、を追跡します。
    *   このコミットで重要なのは、`mspan`構造体に含まれる`needzero`フラグです。

### `mspan.needzero`フラグ

`mspan`構造体内の`needzero`フラグ（`uint8`型）は、そのスパン内の空きオブジェクトスロットが割り当て前にゼロ初期化される必要があるかどうかを示します。

*   **`needzero == 0`**: スパン内のメモリがすでにゼロであることが保証されている場合。例えば、OSから新しく取得されたメモリページや、`mheap`によって一括でゼロ初期化されたスパンの場合です。この場合、個別のオブジェクト割り当て時に`memclr`によるゼロ初期化はスキップされます。
*   **`needzero != 0` (通常は1)**: スパン内のメモリがゼロであることが保証されていない場合。この場合、オブジェクトが割り当てられる際に、そのメモリ領域は明示的にゼロ初期化（`memclr`）されます。

このフラグは、不要なゼロ初期化を避けるための重要な最適化ポイントとなります。

### `BinaryTree17`ベンチマーク

`BinaryTree17`は、Computer Language Benchmark Gameに含まれるベンチマークの一つで、Goランタイムのメモリ割り当てとガベージコレクションの性能を厳しくテストするために設計されています。このベンチマークは、多数の小さなバイナリツリーノードを繰り返し作成するため、「allocation-heavy」（割り当て負荷が高い）と見なされます。このようなワークロードでは、メモリ割り当ての効率が全体のパフォーマンスに大きく影響します。

## 技術的詳細

このコミットは、`mspan`構造体の`needzero`フラグを活用して、メモリ割り当て時のゼロ初期化を条件付きでスキップするメカニズムを再構築します。

### 以前の最適化と問題点

以前のno-zeroing optimizationは、GCのスイーパーがオブジェクトの先頭2ワードを上書きするという特性に依存していました。これにより、スイープ後に再利用されるオブジェクトは、その先頭部分が「クリーン」な状態になることを利用して、ゼロ初期化をスキップしていました。しかし、このスイーパーの内部実装が変更された際に、この依存関係が崩れ、最適化が失われました。

### 新しい最適化メカニズム

新しいアプローチでは、`mspan`がOSから取得されたばかりであるか、または`mheap`によって一括でゼロ初期化されたばかりであるかを示すフラグを直接利用します。

1.  **`mspan.needzero`フラグの導入/利用**:
    *   `mspan`構造体には、そのスパンがゼロ初期化を必要とするかどうかを示す`needzero`フィールドが追加されたか、既存のフィールドがその目的で利用されるようになりました。
    *   OSから新しいメモリページが取得された場合や、`mheap`が一括でゼロ初期化した場合、そのスパンの`needzero`フラグは`0`に設定されます。これは、そのスパン内のすべてのメモリがすでにゼロであることを意味します。

2.  **`mcentral.freeSpan`での`needzero`設定**:
    *   `mcentral.freeSpan`関数は、`mspan`が`mcentral`に返却される際に呼び出されます。
    *   この関数内で、返却される`mspan`の`needzero`フラグが`1`に設定されます。これは、このスパンが再利用される際には、その中のオブジェクトがゼロ初期化される必要があることを示します。なぜなら、このスパンは以前に使用されており、その内容がゼロである保証がないためです。

3.  **`mallocgc`での条件付きゼロ初期化**:
    *   `mallocgc`関数は、Goランタイムの主要なメモリ割り当て関数です。
    *   この関数内でオブジェクトが割り当てられる際、`needzero`引数（割り当て元がゼロ初期化を要求しているか）と、割り当て対象の`mspan`の`needzero`フラグの両方をチェックします。
    *   具体的には、`if needzero && span.needzero != 0 { memclr(unsafe.Pointer(v), size) }` という条件が導入されます。
        *   `needzero`が`true`（ゼロ初期化が必要）であり、かつ`span.needzero`が`0`でない（スパン自体がゼロであることが保証されていない）場合にのみ、`memclr`関数が呼び出されてメモリ領域がゼロ初期化されます。
        *   もし`span.needzero`が`0`であれば、`memclr`はスキップされ、パフォーマンスが向上します。

### 新旧最適化の比較

コミットメッセージでは、この新しいアプローチが以前の最適化よりも「わずかに効率が悪い」ケースがあることに言及しています。

*   **シナリオ**: スパンが部分的に使用され、GCが発生し、そのスパンが`mcentral`に返却され、その後再取得される場合。
*   **古い最適化**: 再利用されるオブジェクトのみをゼロ初期化すればよいことを知っていました。
*   **新しい最適化**: スパン全体を再ゼロ初期化します（`mcentral.freeSpan`で`span.needzero = 1`が設定されるため）。

しかし、コミットの作者は、このケースではすでにGCのコストを支払っており、スパンのゼロ初期化が一度無駄になるだけであり、実際にはほとんど差がないと結論付けています。より複雑な「フロンティア」追跡メカニズムも試作されましたが、このシンプルなアプローチよりも明確な改善は見られなかったとのことです。

### パフォーマンスへの影響

この最適化は、特に`BinaryTree17`ベンチマークにおいて顕著な改善をもたらしました。`BinaryTree17`は大量の小さなオブジェクトを割り当てるため、ゼロ初期化のオーバーヘッド削減が直接的に性能向上に繋がります。他のベンチマークでもわずかながら改善が見られます。

## コアとなるコードの解説

このコミットの核心は、Goランタイムのメモリ割り当てパスにおけるゼロ初期化の条件付けです。

1.  **`mspan.needzero`の役割**:
    *   `mspan`がOSから新しく取得されたり、`mheap`によって一括でゼロ初期化されたりした場合、そのメモリ領域は内容がすべてゼロであることが保証されます。このとき、`mspan.needzero`は`0`に設定されます。
    *   一方、`mspan`が一度使用され、その後GCによってオブジェクトが解放されて`mcentral`に戻された場合、そのスパン内の残りのメモリ領域がすべてゼロであるとは限りません。そのため、`mcentral.freeSpan`関数内で`mspan.needzero`が`1`に設定されます。これは、このスパンから次にオブジェクトが割り当てられる際には、そのオブジェクトのメモリ領域を明示的にゼロ初期化する必要があることを示します。

2.  **`mallocgc`での最適化判断**:
    *   `mallocgc`関数は、新しいオブジェクトを割り当てる際に、まず`mcache`から適切な`mspan`を取得しようとします。
    *   取得した`mspan`からオブジェクトのアドレス`v`を得た後、ゼロ初期化が必要かどうかを判断します。
    *   判断ロジックは `if needzero && span.needzero != 0` です。
        *   `needzero`は、Goの言語仕様やコンパイラが、割り当てられるオブジェクトがゼロ初期化されるべきだと判断した場合に`true`になります（例: 構造体のフィールドや配列の要素はデフォルトでゼロ値に初期化される）。
        *   `span.needzero != 0`は、現在割り当てを行おうとしている`mspan`が、その内容がゼロであることが保証されていない状態であることを意味します。
    *   この両方の条件が満たされた場合にのみ、`memclr`関数が呼び出され、割り当てられたオブジェクトのメモリ領域がゼロで埋められます。
    *   もし`span.needzero`が`0`であれば、たとえ`needzero`が`true`であっても、`memclr`は実行されません。これは、スパン全体がすでにゼロであることが分かっているため、個別のオブジェクトをゼロ初期化する手間を省けるからです。

このメカニズムにより、Goランタイムはメモリ割り当てのたびに無条件にゼロ初期化を行うのではなく、必要な場合にのみゼロ初期化を実行することで、CPUサイクルを節約し、特にメモリ割り当てが頻繁なワークロードでのパフォーマンスを向上させます。`BinaryTree17`のようなベンチマークが改善されたのは、この最適化が直接的に効いたためです。

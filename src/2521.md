## 前提知識の解説

### Go言語のポインタ

Go言語におけるポインタは、変数のメモリアドレスを指し示す値です。C/C++のポインタと似ていますが、ポインタ演算は許可されておらず、より安全に扱えるようになっています。

- `var x int`: `x` は `int` 型の変数です。
- `var p *int`: `p` は `int` 型へのポインタです。
- `p = &x`: `p` に `x` のメモリアドレスを代入します。
- `*p`: ポインタ `p` が指すメモリアドレスに格納されている値（`x` の値）にアクセスします。

### `len()` 関数

`len()` はGoの組み込み関数で、以下の型の「長さ」を返します。

- **文字列 (string)**: 文字列内のバイト数（UTF-8エンコードされたバイト列の長さ）。
- **スライス ([]T)**: スライスに含まれる要素の数。
- **配列 ([N]T)**: 配列の要素の数（コンパイル時に固定）。
- **マップ (map[K]V)**: マップに含まれるキーと値のペアの数。
- **チャネル (chan T)**: チャネル内のキューに入っている要素の数。

### `cap()` 関数

`cap()` はGoの組み込み関数で、以下の型の「容量」を返します。

- **スライス ([]T)**: スライスが参照している基底配列の最大容量。
- **配列 ([N]T)**: 配列の要素の数（`len` と同じ）。
- **チャネル (chan T)**: チャネルのバッファ容量。

### `len()` と `cap()` のポインタ型への適用

Go言語では、`len()` や `cap()` は通常、直接的なデータ構造（スライス、マップ、文字列など）に対して適用されます。これらの関数は、データ構造そのものの特性（要素数や容量）を問い合わせるものであり、そのデータ構造へのポインタに対して直接適用することは、一般的に型システムによって不正とされます。

例えば、`s` がスライスである場合、`len(s)` は有効ですが、`p` が `*[]T` 型（スライスへのポインタ）である場合、`len(p)` は不正です。正しいアクセス方法は `len(*p)` とポインタをデリファレンスしてから関数を適用することです。これは、`len` や `cap` がポインタが指す「値」の長さを知りたいのであって、ポインタそのものの長さを知りたいわけではないためです。ポインタの長さは通常、システムアーキテクチャによって固定されており、意味のある情報ではありません。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラが `len` および `cap` 関数をポインタ型に適用しようとした際に、どのように型エラーを検出・報告するかという点にあります。

Go言語の設計哲学の一つに「明示性」があります。ポインタをデリファレンスせずにその先の値のプロパティにアクセスしようとすることは、意図しない挙動やバグにつながる可能性があります。そのため、コンパイラはこのような操作を型エラーとして検出し、開発者に修正を促します。

具体的には、以下の型に対するポインタに `len` や `cap` を適用しようとすると、コンパイラはエラーを発生させるべきです。

- `*map[K]V` (マップへのポインタ)
- `*string` (文字列へのポインタ)
- `*[]T` (スライスへのポインタ)

一方、配列へのポインタ `*[N]T` の場合は少し異なります。Goの配列は値型であり、`len` と `cap` は配列の要素数を返します。配列へのポインタをデリファレンスせずに `len` や `cap` を適用した場合、コンパイラはポインタを自動的にデリファレンスして配列の長さを返すことがあります（これはGoの言語仕様の進化やコンパイラの実装によって挙動が異なる可能性がありますが、一般的には配列の長さはポインタの有無に関わらず固定であるため、より寛容に扱われることがあります）。しかし、このコミットの時点では、配列へのポインタに対しても `len` や `cap` を直接適用することは不正であると見なされていた可能性があります。`test/indirect1.go` の内容を見ると、`len(a1)` や `cap(a1)` (ここで `a1` は `*[10]int` 型) はエラーとしてマークされていません。これは、配列へのポインタに対しては `len` や `cap` が許容される、あるいはコンパイラが自動的にデリファレンスして処理する挙動がこの時点で確立されていたことを示唆しています。

このコミットは、これらの型チェックルールがGoコンパイラに正しく実装されていることを確認するためのテストケースを整備するものです。特に、`test/indirect1.go` は、様々なポインタ型に対して `len` および `cap` を適用した場合に、期待されるエラーが正しく報告されることを `ERROR "illegal"` コメントで明示的に指定しています。

## コアとなるコードの解説

`test/indirect1.go` は、Goコンパイラの型チェックの正確性を検証するための重要なテストファイルです。このファイルは、`errchk $G -e $D/$F.go` というディレクティブで始まっており、これはGoコンパイラ (`$G`) がこのファイルをコンパイルした際に、指定されたエラーメッセージ (`-e`) が出力されることを期待していることを意味します。

ファイル内で定義されている変数とそれに対する `len`/`cap` の呼び出しは以下の点をテストしています。

- **マップ (`map[string]int`)**:
    - `len(m0)`: `map` 型への直接の `len` は有効です。
    - `len(m1)`, `len(m2)`, `len(m4)`: `*map[string]int` 型（マップへのポインタ）に対する `len` は `ERROR "illegal"` とマークされており、コンパイルエラーとなるべきです。これは、`len` がマップそのものの要素数を数えるものであり、マップへのポインタの長さを数えるものではないためです。
- **文字列 (`string`)**:
    - `len(s0)`, `len(s3)`: `string` 型への直接の `len` は有効です。
    - `len(s1)`, `len(s2)`, `len(s4)`: `*string` 型（文字列へのポインタ）に対する `len` は `ERROR "illegal"` とマークされており、コンパイルエラーとなるべきです。`len` は文字列のバイト数を数えるものであり、文字列へのポインタの長さを数えるものではないためです。
- **配列 (`[10]int`)**:
    - `len(a0)`, `len(a1)`, `len(a2)`: `[10]int` 型（配列）および `*[10]int` 型（配列へのポインタ）に対する `len` はエラーとしてマークされていません。これは、Go言語において配列の長さはコンパイル時に固定されており、配列へのポインタに対しても `len` が許容される、またはコンパイラが自動的にデリファレンスして処理する挙動がこの時点で確立されていたことを示唆しています。`cap` も同様です。
- **スライス (`[]int`)**:
    - `len(b0)`, `len(b3)`: `[]int` 型への直接の `len` は有効です。
    - `len(b1)`, `len(b2)`, `len(b4)`: `*[]int` 型（スライスへのポインタ）に対する `len` は `ERROR "illegal"` とマークされており、コンパイルエラーとなるべきです。`len` はスライスの要素数を数えるものであり、スライスへのポインタの長さを数えるものではないためです。
    - `cap(b0)`, `cap(b3)`: `[]int` 型への直接の `cap` は有効です。
    - `cap(b1)`, `cap(b2)`, `cap(b4)`: `*[]int` 型（スライスへのポインタ）に対する `cap` は `ERROR "illegal"` とマークされており、コンパイルエラーとなるべきです。`cap` はスライスの容量を数えるものであり、スライスへのポインタの容量を数えるものではないためです。

# [インデックス 20076] ファイルの概要

このコミットは、Go言語のリンカー（`liblink`）におけるPowerPC 64-bit (power64) アーキテクチャ向けの浮動小数点数ロード/ストア命令の生成に関するバグ修正です。具体的には、スタックポインタからのオフセットが大きい場合に、浮動小数点数のロードおよびストアが正しく行われない問題を解決します。この問題は、`test/cmplxdivide` テストの失敗として顕在化していました。

## 変更の背景

このコミットは、Go言語のコンパイラおよびリンカーがPowerPC 64-bit (power64) アーキテクチャ上で浮動小数点数を含むプログラムを処理する際に発生していたバグを修正するために導入されました。

Go言語のコンパイラは、Goのソースコードを中間表現に変換し、最終的にターゲットアーキテクチャの機械語に変換します。この過程で、変数がメモリ上のどこに配置されるか（特にスタック上）が決定され、それに応じてロード（メモリからレジスタへ）およびストア（レジスタからメモリへ）命令が生成されます。

問題は、PowerPC 64-bitアーキテクチャにおいて、スタックポインタ（`SP`）からのオフセットが特定のサイズ（例えば16ビット符号付き整数の範囲）を超える場合に、浮動小数点数（特に倍精度浮動小数点数）のロード/ストア命令が正しく生成されないことにありました。これにより、`test/cmplxdivide` というGoの標準テストスイートに含まれる複素数除算のテストが失敗していました。複素数演算は内部的に浮動小数点数演算を多用するため、この問題が顕在化したと考えられます。

リンカーが不正な命令を生成すると、プログラムの実行時に「mishandled instruction」（不正な命令）のような致命的なエラーが発生したり、計算結果が誤ったりする可能性があります。このコミットは、このような状況を防ぎ、PowerPC 64-bit上でのGoプログラムの正確性と安定性を確保することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

1.  **Go言語のツールチェインとリンカー (`liblink`)**:
    *   Go言語のビルドプロセスは、ソースコードをコンパイルし、最終的に実行可能なバイナリを生成します。このプロセスには、コンパイラとリンカーが含まれます。
    *   `liblink` はGoの内部リンカーであり、コンパイラが生成したオブジェクトファイルを結合し、最終的な実行ファイルを生成する役割を担います。このリンカーは、Go独自の「擬似アセンブリ」命令をターゲットアーキテクチャの実際の機械語命令に変換する部分も担当します。
    *   `src/liblink/asm9.c` は、このリンカーの一部であり、特にPowerPC 64-bitのような特定のアーキテクチャ向けのアセンブリコード生成ロジックを含んでいます。

2.  **PowerPC 64-bit (power64) アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一つで、サーバーや組み込みシステムなどで使用されます。
    *   64ビットの汎用レジスタ（GPRs）と浮動小数点レジスタ（FPRs）を持ち、浮動小数点演算は専用のFPRsを使用して行われます。
    *   命令セットには、メモリからレジスタへのロード命令（例: `lfd` - load floating-point double）や、レジスタからメモリへのストア命令（例: `stfd` - store floating-point double）が含まれます。これらの命令は、通常、ベースレジスタとオフセット値を使用してメモリアドレスを指定します。

3.  **スタックとスタックポインタ (`SP`)**:
    *   プログラムの実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどが一時的に保存されるメモリ領域を「スタック」と呼びます。
    *   「スタックポインタ」（`SP`）は、スタックの現在のトップを指すレジスタです。ローカル変数などは、`SP`からの相対的なオフセットでアクセスされます。
    *   `$large(SP)` という表現は、スタックポインタからのオフセットが非常に大きい場合、つまり、スタックフレームが大きく、ローカル変数がスタックの深い位置にある場合を指します。

4.  **`Optab` (Operation Table)**:
    *   Goのリンカー内部で使用されるテーブルで、Goの擬似アセンブリ命令（例: `AFMOVD`）と、それに対応するオペランドの型（例: `C_LEXT`, `C_LAUTO`, `C_LOREG`）に基づいて、どのような機械語命令を生成するか、その命令のサイズ、エンコーディング、および関連するフラグを定義します。
    *   `AFMOVD`: Goの擬似アセンブリ命令で、倍精度浮動小数点数（`double`）を移動（ロードまたはストア）する操作を表します。
    *   `C_LEXT`: 外部シンボル（グローバル変数など）への参照を示します。
    *   `C_LAUTO`: 自動変数（スタック上のローカル変数）への参照を示します。
    *   `C_LOREG`: レジスタベースのオフセットを持つメモリ参照を示します。

5.  **即値 (Immediate Value)**:
    *   命令の一部として直接エンコードされる定数値を指します。多くのアーキテクチャでは、ロード/ストア命令のオフセット値として即値が使用されますが、そのサイズには制限があります（例: 16ビット符号付き整数）。

6.  **`sysfatal`**:
    *   Goランタイムにおける致命的なエラー発生時に呼び出される関数です。これは回復不可能なエラーを示し、プログラムを即座に終了させます。通常、内部的な整合性チェックの失敗や、予期せぬ低レベルのハードウェア/OSエラーで発生します。

## 技術的詳細

このコミットの核心は、PowerPC 64-bitアーキテクチャにおける浮動小数点数ロード/ストア命令のオフセット値の扱いにあります。PowerPCのロード/ストア命令は、通常、ベースレジスタ（この場合はスタックポインタ `SP`）と、それに加算されるオフセット値でメモリアドレスを指定します。このオフセット値は、命令のビットフィールドに即値としてエンコードされることが多く、そのサイズには制限があります（例えば、16ビット符号付き整数）。

問題は、Goプログラムのスタックフレームが大きくなり、ローカル変数がスタックポインタから遠い位置に配置された場合、そのオフセット値が16ビット符号付き整数の範囲（-32768から32767）を超える可能性があったことです。リンカーがこの大きなオフセット値を、16ビットしかサポートしない命令の即値フィールドに無理やりエンコードしようとすると、値が切り捨てられたり、不正なアドレスが生成されたりします。これにより、プログラムが誤ったメモリ位置にアクセスし、結果として`test/cmplxdivide`のような浮動小数点演算を多用するテストが失敗していました。

このコミットは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **`Optab` エントリの修正**:
    `src/liblink/asm9.c` 内の `Optab` テーブルにおいて、`AFMOVD` 命令（倍精度浮動小数点数の移動）に関連するエントリが変更されました。
    *   `C_LEXT` (外部シンボル), `C_LAUTO` (スタック上のローカル変数), `C_LOREG` (レジスタベースのオフセット) の各オペランド型に対する `AFMOVD` のエントリで、命令のエンコーディングやサイズを示す数値が変更されています。
        *   `{ AFMOVD, C_LEXT, C_NONE, C_NONE, C_FREG, 8, 4, REGSB }` が `36, 8` に
        *   `{ AFMOVD, C_LAUTO, C_NONE, C_NONE, C_FREG, 8, 4, REGSP }` が `36, 8` に
        *   `{ AFMOVD, C_LOREG, C_NONE, C_NONE, C_FREG, 8, 4, REGZERO }` が `36, 8` に
        *   同様に、ストア操作側（`C_FREG` からメモリへ）のエントリも `7, 4` から `35, 8` に変更されています。
    これらの数値の変更は、リンカーが大きなオフセットを扱うために、異なる命令シーケンスを生成するか、より大きなオフセットをサポートするPowerPC命令のバリアントを使用するように指示していると考えられます。例えば、直接即値で指定できない大きなオフセットは、複数の命令（例: オフセットをレジスタにロードしてから、そのレジスタをベースとしてロード/ストア命令を実行）を使って間接的にアクセスされるように変更された可能性があります。

2.  **`asmout` 関数における `sysfatal` チェックの追加**:
    `asmout` 関数は、Goの擬似アセンブリ命令を実際の機械語命令に変換するリンカーの主要な部分です。この関数内に、即値 `v` が `int16` の範囲を超えていないかをチェックする新しいコードが追加されました。
    ```c
    if((int16)v != v)
        sysfatal("mishandled instruction %P", p);
    ```
    このチェックは、`v` が16ビット符号付き整数の範囲に収まらない場合に `sysfatal` を呼び出し、「mishandled instruction」（不正な命令）という致命的なエラーを発生させます。これは、リンカーが不正な機械語命令を生成しようとしていることを早期に検出し、コンパイル/リンク時に問題を特定するためのセーフガードとして機能します。これにより、実行時に予期せぬクラッシュや誤動作が発生するのを防ぎます。

これらの変更により、GoリンカーはPowerPC 64-bit上で、スタック上の大きなオフセットにある浮動小数点変数に対しても、正確なロード/ストア命令を生成できるようになり、`test/cmplxdivide` のようなテストが正しくパスするようになりました。

## コアとなるコードの解説

1.  **`Optab` の変更**:
    `Optab` は、Goのリンカーが擬似アセンブリ命令を機械語に変換する際の「レシピ」のようなものです。各エントリは、特定の命令（`AFMOVD`）とオペランドの組み合わせに対して、生成すべき機械語命令のタイプ、サイズ、およびその他の属性を定義します。
    変更された数値（例: `8, 4` から `36, 8`、`7, 4` から `35, 8`）は、PowerPC 64-bitアーキテクチャにおける浮動小数点ロード/ストア命令のエンコーディング方法が変更されたことを示唆しています。
    *   最初の数値（例: `8` から `36`）は、命令のタイプやフォーマット、あるいは命令を生成するための内部的な処理ロジックの識別子である可能性があります。この変更は、リンカーが、より大きなオフセットを扱うための新しい命令シーケンスや、拡張されたアドレッシングモードをサポートするPowerPC命令のバリアントを使用するように指示していると考えられます。
    *   2番目の数値（例: `4` から `8`）は、生成される機械語命令のバイト数、または命令が占めるスロット数を示す可能性があります。`4`から`8`への増加は、単一の命令では表現できない大きなオフセットを扱うために、複数の命令（例えば、オフセットをレジスタにロードする命令と、そのレジスタをベースとするロード/ストア命令）を生成する必要があることを示唆しています。

2.  **`asmout` 関数内の `sysfatal` チェック**:
    `asmout` 関数は、個々のアセンブリ命令（`Prog` 構造体で表現される）を受け取り、それに対応する機械語命令を生成します。
    追加された `if((int16)v != v)` チェックは、`v` という変数が、命令の即値フィールドに収まる16ビット符号付き整数の範囲内にあるかどうかを検証しています。
    *   `v` は、スタックポインタからのオフセット値など、命令の即値としてエンコードされるべき値を表します。
    *   `int16` にキャストして元の `v` と比較することで、`v` が16ビット符号付き整数の範囲を超えていないかを確認します。もし `v` がこの範囲を超えている場合、キャストによって値が切り捨てられるため、`((int16)v != v)` は真となります。
    *   この条件が真の場合、`sysfatal("mishandled instruction %P", p)` が呼び出されます。これは、リンカーが現在の命令 `p` に対して、有効な機械語命令を生成できない（または生成しようとしている命令が不正である）ことを示し、ビルドプロセスを即座に停止させます。
    このチェックは、リンカーが不正な機械語を生成してしまい、それが実行時にクラッシュを引き起こす前に、問題を早期に発見するための重要な防御策です。

これらの変更は、GoのリンカーがPowerPC 64-bitアーキテクチャの特性（特に命令の即値オフセットの制限）をより正確に考慮し、大きなスタックオフセットを持つ浮動小数点変数に対しても堅牢な機械語を生成できるようにするためのものです。

このコミットは、Go言語のコンパイラおよびリンカーがPowerPC 64-bit (power64) アーキテクチャ上で浮動小数点数を含むプログラムを処理する際に発生していたバグを修正するために導入されました。

Go言語のコンパイラは、Goのソースコードを中間表現に変換し、最終的にターゲットアーキテクチャの機械語に変換します。この過程で、変数がメモリ上のどこに配置されるか（特にスタック上）が決定され、それに応じてロード（メモリからレジスタへ）およびストア（レジスタからメモリへ）命令が生成されます。

問題は、PowerPC 64-bitアーキテクチャにおいて、スタックポインタ（`SP`）からのオフセットが特定のサイズ（例えば16ビット符号付き整数の範囲）を超える場合に、浮動小数点数（特に倍精度浮動小数点数）のロード/ストア命令が正しく生成されないことにありました。これにより、`test/cmplxdivide` というGoの標準テストスイートに含まれる複素数除算のテストが失敗していました。複素数演算は内部的に浮動小数点数演算を多用するため、この問題が顕在化したと考えられます。

リンカーが不正な命令を生成すると、プログラムの実行時に「mishandled instruction」（不正な命令）のような致命的なエラーが発生したり、計算結果が誤ったりする可能性があります。このコミットは、このような状況を防ぎ、PowerPC 64-bit上でのGoプログラムの正確性と安定性を確保することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

1.  **Go言語のツールチェインとリンカー (`liblink`)**:
    *   Go言語のビルドプロセスは、ソースコードをコンパイルし、最終的に実行可能なバイナリを生成します。このプロセスには、コンパイラとリンカーが含まれます。
    *   `liblink` はGoの内部リンカーであり、コンパイラが生成したオブジェクトファイルを結合し、最終的な実行ファイルを生成する役割を担います。このリンカーは、Go独自の「擬似アセンブリ」命令をターゲットアーキテクチャの実際の機械語命令に変換する部分も担当します。
    *   `src/liblink/asm9.c` は、このリンカーの一部であり、特にPowerPC 64-bitのような特定のアーキテクチャ向けのアセンブリコード生成ロジックを含んでいます。

2.  **PowerPC 64-bit (power64) アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一つで、サーバーや組み込みシステムなどで使用されます。
    *   64ビットの汎用レジスタ（GPRs）と浮動小数点レジスタ（FPRs）を持ち、浮動小数点演算は専用のFPRsを使用して行われます。
    *   命令セットには、メモリからレジスタへのロード命令（例: `lfd` - load floating-point double）や、レジスタからメモリへのストア命令（例: `stfd` - store floating-point double）が含まれます。これらの命令は、通常、ベースレジスタとオフセット値を使用してメモリアドレスを指定します。

3.  **スタックとスタックポインタ (`SP`)**:
    *   プログラムの実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどが一時的に保存されるメモリ領域を「スタック」と呼びます。
    *   「スタックポインタ」（`SP`）は、スタックの現在のトップを指すレジスタです。ローカル変数などは、`SP`からの相対的なオフセットでアクセスされます。
    *   `$large(SP)` という表現は、スタックポインタからのオフセットが非常に大きい場合、つまり、スタックフレームが大きく、ローカル変数がスタックの深い位置にある場合を指します。

4.  **`Optab` (Operation Table)**:
    *   Goのリンカー内部で使用されるテーブルで、Goの擬似アセンブリ命令（例: `AFMOVD`）と、それに対応するオペランドの型（例: `C_LEXT`, `C_LAUTO`, `C_LOREG`）に基づいて、どのような機械語命令を生成するか、その命令のサイズ、エンコーディング、および関連するフラグを定義します。
    *   `AFMOVD`: Goの擬似アセンブリ命令で、倍精度浮動小数点数（`double`）を移動（ロードまたはストア）する操作を表します。
    *   `C_LEXT`: 外部シンボル（グローバル変数など）への参照を示します。
    *   `C_LAUTO`: 自動変数（スタック上のローカル変数）への参照を示します。
    *   `C_LOREG`: レジスタベースのオフセットを持つメモリ参照を示します。

5.  **即値 (Immediate Value)**:
    *   命令の一部として直接エンコードされる定数値を指します。多くのアーキテクチャでは、ロード/ストア命令のオフセット値として即値が使用されますが、そのサイズには制限があります（例: 16ビット符号付き整数）。

6.  **`sysfatal`**:
    *   Goランタイムにおける致命的なエラー発生時に呼び出される関数です。これは回復不可能なエラーを示し、プログラムを即座に終了させます。通常、内部的な整合性チェックの失敗や、予期せぬ低レベルのハードウェア/OSエラーで発生します。

## 技術的詳細

このコミットの核心は、PowerPC 64-bitアーキテクチャにおける浮動小数点数ロード/ストア命令のオフセット値の扱いにあります。PowerPCのロード/ストア命令は、通常、ベースレジスタ（この場合はスタックポインタ `SP`）と、それに加算されるオフセット値でメモリアドレスを指定します。このオフセット値は、命令のビットフィールドに即値としてエンコードされることが多く、そのサイズには制限があります（例えば、16ビット符号付き整数）。

問題は、Goプログラムのスタックフレームが大きくなり、ローカル変数がスタックポインタから遠い位置に配置された場合、そのオフセット値が16ビット符号付き整数の範囲（-32768から32767）を超える可能性があったことです。リンカーがこの大きなオフセット値を、16ビットしかサポートしない命令の即値フィールドに無理やりエンコードしようとすると、値が切り捨てられたり、不正なアドレスが生成されたりします。これにより、プログラムが誤ったメモリ位置にアクセスし、結果として`test/cmplxdivide`のような浮動小数点演算を多用するテストが失敗していました。

このコミットは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **`Optab` エントリの修正**:
    `src/liblink/asm9.c` 内の `Optab` テーブルにおいて、`AFMOVD` 命令（倍精度浮動小数点数の移動）に関連するエントリが変更されました。
    *   `C_LEXT` (外部シンボル), `C_LAUTO` (スタック上のローカル変数), `C_LOREG` (レジスタベースのオフセット) の各オペランド型に対する `AFMOVD` のエントリで、命令のエンコーディングやサイズを示す数値が変更されています。
        *   `{ AFMOVD, C_LEXT, C_NONE, C_NONE, C_FREG, 8, 4, REGSB }` が `36, 8` に
        *   `{ AFMOVD, C_LAUTO, C_NONE, C_NONE, C_FREG, 8, 4, REGSP }` が `36, 8` に
        *   `{ AFMOVD, C_LOREG, C_NONE, C_NONE, C_FREG, 8, 4, REGZERO }` が `36, 8` に
        *   同様に、ストア操作側（`C_FREG` からメモリへ）のエントリも `7, 4` から `35, 8` に変更されています。
    これらの数値の変更は、リンカーが大きなオフセットを扱うために、異なる命令シーケンスを生成するか、より大きなオフセットをサポートするPowerPC命令のバリアントを使用するように指示していると考えられます。例えば、直接即値で指定できない大きなオフセットは、複数の命令（例: オフセットをレジスタにロードしてから、そのレジスタをベースとしてロード/ストア命令を実行）を使って間接的にアクセスされるように変更された可能性があります。

2.  **`asmout` 関数における `sysfatal` チェックの追加**:
    `asmout` 関数は、Goの擬似アセンブリ命令を実際の機械語命令に変換するリンカーの主要な部分です。この関数内に、即値 `v` が `int16` の範囲を超えていないかをチェックする新しいコードが追加されました。
    ```c
    if((int16)v != v)
        sysfatal("mishandled instruction %P", p);
    ```
    このチェックは、`v` が16ビット符号付き整数の範囲に収まらない場合に `sysfatal` を呼び出し、「mishandled instruction」（不正な命令）という致命的なエラーを発生させます。これは、リンカーが不正な機械語命令を生成しようとしていることを早期に検出し、コンパイル/リンク時に問題を特定するためのセーフガードとして機能します。これにより、実行時に予期せぬクラッシュや誤動作が発生するのを防ぎます。

これらの変更により、GoリンカーはPowerPC 64-bit上で、スタック上の大きなオフセットにある浮動小数点変数に対しても、正確なロード/ストア命令を生成できるようになり、`test/cmplxdivide` のようなテストが正しくパスするようになりました。

## コアとなるコードの解説

1.  **`Optab` の変更**:
    `Optab` は、Goのリンカーが擬似アセンブリ命令を機械語に変換する際の「レシピ」のようなものです。各エントリは、特定の命令（`AFMOVD`）とオペランドの組み合わせに対して、生成すべき機械語命令のタイプ、サイズ、およびその他の属性を定義します。
    変更された数値（例: `8, 4` から `36, 8`、`7, 4` から `35, 8`）は、PowerPC 64-bitアーキテクチャにおける浮動小数点ロード/ストア命令のエンコーディング方法が変更されたことを示唆しています。
    *   最初の数値（例: `8` から `36`）は、命令のタイプやフォーマット、あるいは命令を生成するための内部的な処理ロジックの識別子である可能性があります。この変更は、リンカーが、より大きなオフセットを扱うための新しい命令シーケンスや、拡張されたアドレッシングモードをサポートするPowerPC命令のバリアントを使用するように指示していると考えられます。
    *   2番目の数値（例: `4` から `8`）は、生成される機械語命令のバイト数、または命令が占めるスロット数を示す可能性があります。`4`から`8`への増加は、単一の命令では表現できない大きなオフセットを扱うために、複数の命令（例えば、オフセットをレジスタにロードする命令と、そのレジスタをベースとするロード/ストア命令）を生成する必要があることを示唆しています。

2.  **`asmout` 関数内の `sysfatal` チェック**:
    `asmout` 関数は、個々のアセンブリ命令（`Prog` 構造体で表現される）を受け取り、それに対応する機械語命令を生成します。
    追加された `if((int16)v != v)` チェックは、`v` という変数が、命令の即値フィールドに収まる16ビット符号付き整数の範囲内にあるかどうかを検証しています。
    *   `v` は、スタックポインタからのオフセット値など、命令の即値としてエンコードされるべき値を表します。
    *   `int16` にキャストして元の `v` と比較することで、`v` が16ビット符号付き整数の範囲を超えていないかを確認します。もし `v` がこの範囲を超えている場合、キャストによって値が切り捨てられるため、`((int16)v != v)` は真となります。
    *   この条件が真の場合、`sysfatal("mishandled instruction %P", p)` が呼び出されます。これは、リンカーが現在の命令 `p` に対して、有効な機械語命令を生成できない（または生成しようとしている命令が不正である）ことを示し、ビルドプロセスを即座に停止させます。
    このチェックは、リンカーが不正な機械語を生成してしまい、それが実行時にクラッシュを引き起こす前に、問題を早期に発見するための重要な防御策です。

これらの変更は、GoのリンカーがPowerPC 64-bitアーキテクチャの特性（特に命令の即値オフセットの制限）をより正確に考慮し、大きなスタックオフセットを持つ浮動小数点変数に対しても堅牢な機械語を生成できるようにするためのものです。

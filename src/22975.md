# [インデックス 22975] ファイルの概要

このコミットは、GoランタイムがAndroid上でどのように初期化され、アプリケーションの`main`関数が呼び出されるかというメカニズムに関する重要な変更を導入しています。特に、`golang.org/x/mobile/app`パッケージを使用して開発された「オールGo」アプリケーションが、AndroidのJava Native Interface (JNI) を介してGoの`main.main`関数を適切に呼び出せるようにするための修正です。

## コミット

```
commit c8aba85e4a83c2023bed4e1e8ae3c480ecf835ec
Author: David Crawshaw <crawshaw@golang.org>
Date:   Thu Apr 16 22:01:20 2015 -0400

    runtime: export main.main for android
    
    Previously we started the Go runtime from a JNI function call, which
    eventually called the program's main function. Now the runtime is
    initialized by an ELF initialization function as a c-shared library,
    and the program's main function is not called. So now we export main
    so it can be called from JNI.
    
    This is necessary for all-Go apps because unlike a normal shared
    library, the program loading the library is not written by or known
    to the programmer. As far as they are concerned, the .so is
    everything. In fact the same code is compiled for iOS as a normal Go
    program.
```

## 元コミット内容

このコミットの目的は、Android向けに`main.main`関数をエクスポートすることです。

以前は、JNI関数呼び出しからGoランタイムが起動され、それが最終的にプログラムの`main`関数を呼び出していました。しかし、この変更時点では、ランタイムはc-sharedライブラリとしてのELF初期化関数によって初期化されるようになり、プログラムの`main`関数は自動的に呼び出されなくなりました。そのため、JNIから`main`関数を呼び出せるように、`main`をエクスポートする必要が生じました。

これは「オールGo」アプリケーションにとって不可欠な変更です。通常の共有ライブラリとは異なり、ライブラリをロードするプログラムがプログラマによって書かれたり、知られたりしているわけではないためです。プログラマにとって、`.so`ファイル（共有ライブラリ）がすべてです。実際、同じコードがiOS向けには通常のGoプログラムとしてコンパイルされます。

## 変更の背景

このコミットが行われた2015年頃は、Go言語がモバイル開発、特にAndroidとiOSへの対応を強化していた時期にあたります。`golang.org/x/mobile`プロジェクト、特に`golang.org/x/mobile/app`パッケージは、Go言語だけでモバイルアプリケーションを開発するためのフレームワークを提供することを目指していました。

従来のAndroidにおけるGoランタイムの起動方法は、Java層からJNI (Java Native Interface) を介して特定のGo関数を呼び出し、そのGo関数がGoランタイムを初期化し、最終的にGoプログラムのエントリポイントである`main.main`関数を呼び出すというものでした。これは、Goコードが既存のAndroidアプリケーションの一部として組み込まれるシナリオでは機能していました。

しかし、Go言語だけでアプリケーション全体を構築する「オールGo」アプリケーションの場合、Goランタイムの初期化と`main.main`の呼び出しのタイミングが問題となりました。Androidの共有ライブラリ（`.so`ファイル）は、ロード時にELF (Executable and Linkable Format) の初期化関数（例: `.init_array`セクションに登録された関数）を自動的に実行するメカニズムを持っています。Goランタイムは、このELF初期化関数を利用して自身を初期化するように変更されました。

この新しい初期化フローでは、GoランタイムはELF初期化関数によって起動されますが、Goプログラムの`main.main`関数は自動的には呼び出されません。これは、共有ライブラリがロードされた際に、そのライブラリ内の特定のエントリポイントが自動的に実行されることを期待するC/C++の慣習とは異なり、Goの`main`関数はアプリケーションの論理的な開始点であるためです。

「オールGo」アプリケーションでは、Java層（AndroidのActivityなど）からGoのアプリケーションロジックを起動する必要があります。この際、JNIを介してGoの特定関数を呼び出すことになりますが、その「特定関数」がGoプログラムの真のエントリポイントである`main.main`であるべきです。しかし、`main.main`がGoランタイムによって自動的に呼び出されないため、外部（JNI）から明示的に呼び出せるように、`main.main`を共有ライブラリの外部シンボルとしてエクスポートする必要が生じました。

この変更は、GoがAndroid上でより自立したアプリケーション開発を可能にするための重要なステップであり、Goのモバイル開発エコシステムが成熟していく過程の一部と言えます。

## 前提知識の解説

このコミットの理解には、以下の技術的背景知識が不可欠です。

1.  **Go言語の`main.main`関数**:
    Goプログラムの実行は、`main`パッケージ内の`main`関数から開始されます。これはC/C++における`main`関数と同様に、プログラムのエントリポイントです。通常、Goプログラムがコンパイルされ実行されると、Goランタイムが初期化された後、この`main.main`関数が自動的に呼び出されます。

2.  **Androidアプリケーションの構造とJNI (Java Native Interface)**:
    Androidアプリケーションは主にJava（またはKotlin）で書かれており、Dalvik/ART (Android Runtime) 上で動作します。しかし、パフォーマンスが要求される処理や既存のC/C++ライブラリを利用するために、ネイティブコード（C/C++、Goなど）を組み込むことができます。
    JNIは、Javaコードとネイティブコードの間で相互運用を可能にするフレームワークです。Javaコードからネイティブ関数を呼び出したり、ネイティブコードからJavaオブジェクトを操作したりするために使用されます。Androidでは、ネイティブライブラリ（`.so`ファイル）をロードし、その中の関数をJavaの`native`メソッドにマッピングすることでJNIを利用します。

3.  **ELF (Executable and Linkable Format) と初期化関数**:
    ELFは、Unix系システム（Linux、Androidなど）で実行可能ファイル、共有ライブラリ、オブジェクトファイルなどのバイナリ形式として広く使用されています。ELFバイナリには、プログラムの実行開始前や共有ライブラリのロード時に自動的に実行される初期化関数を登録するメカニズムがあります。これらは通常、`.init`セクションや`.init_array`セクションに配置され、ライブラリがメモリにロードされた直後にリンカによって呼び出されます。Goランタイムは、このELF初期化メカニズムを利用して、Goコードが実行される前に自身をセットアップします。

4.  **Goのc-sharedビルドモード**:
    Go言語は、`go build -buildmode=c-shared`コマンドを使用することで、GoパッケージをC言語から呼び出し可能な共有ライブラリ（Linux/Androidでは`.so`ファイル）としてコンパイルする機能を提供します。このモードでビルドされたライブラリは、Goランタイム全体を含んでおり、Cの関数シグネチャに準拠したエクスポートされたGo関数を外部から呼び出すことができます。

5.  **`go:cgo_export_static` および `go:cgo_export_dynamic` ディレクティブ**:
    これらはGoのCgo（GoとCの相互運用機能）に関連する特殊なビルドディレクティブです。
    *   `//go:cgo_export_static <symbol_name>`: 指定されたGoのシンボル（関数など）を、静的ライブラリとしてビルドする際にC言語からリンク可能なシンボルとしてエクスポートするようGoコンパイラに指示します。
    *   `//go:cgo_export_dynamic <symbol_name>`: 指定されたGoのシンボルを、共有ライブラリとしてビルドする際にC言語から動的にリンク可能なシンボルとしてエクスポートするようGoコンパイラに指示します。
    これらのディレクティブは、Goの内部ランタイムやCgoのメカニズムによって使用され、Go関数をC言語のABI (Application Binary Interface) に従って外部に公開するために利用されます。

6.  **`golang.org/x/mobile/app`パッケージ**:
    このパッケージは、Go言語でAndroidおよびiOS向けのモバイルアプリケーションを開発するためのフレームワークの一部です。モバイルアプリケーションのライフサイクルイベント（起動、停止、一時停止、再開など）や、タッチイベント、描画イベントなどをGoコードで処理するためのAPIを提供します。このパッケージを使用する「オールGo」アプリケーションは、Goコードがアプリケーションの主要なロジックとUIを制御することを意図しています。

## 技術的詳細

このコミットの核心は、GoランタイムがAndroid上で初期化される方法の変更と、それに伴うGoアプリケーションの`main.main`関数の呼び出し方法の調整にあります。

**変更前**:
Goランタイムは、AndroidのJava層からJNIを介して呼び出される特定のGo関数（例えば、`_rt0_arm_linux1`のようなランタイム内部のエントリポイント）によって起動されていました。このGo関数がGoランタイムの初期化プロセスを開始し、そのプロセスの一部としてGoプログラムの`main.main`関数が呼び出されていました。このモデルは、Goコードが既存のJava/Kotlinアプリケーションに組み込まれる場合に適していました。Java側がGoランタイムの起動を明示的にトリガーし、Go側がその後のアプリケーションロジックを制御するという連携です。

**変更後**:
Goランタイムは、Androidの共有ライブラリ（`.so`ファイル）がロードされる際に、ELFの初期化関数（例: `.init_array`セクションに登録された関数）を利用して自身を初期化するように変更されました。これは、Goランタイムがより「自律的」に、かつAndroidのネイティブライブラリのロードメカニズムに沿って起動されることを意味します。
しかし、この新しい初期化フローでは、Goランタイムは起動されますが、Goプログラムの`main.main`関数は自動的には呼び出されなくなりました。これは、ELF初期化関数がライブラリのロード時に実行される一般的な初期化コードであり、必ずしもアプリケーションの論理的なエントリポイントを呼び出すことを意図していないためです。

**問題点**:
`golang.org/x/mobile/app`のような「オールGo」アプリケーションでは、Goの`main.main`関数がアプリケーションの実際の開始点であり、AndroidのJava層からこの`main.main`関数を呼び出す必要があります。しかし、自動的に呼び出されないため、JNIを介して明示的に呼び出すための手段が必要になりました。

**解決策**:
このコミットは、Goの`main.main`関数を共有ライブラリの外部シンボルとしてエクスポートすることでこの問題を解決します。具体的には、`src/runtime/os_android_arm.go`ファイル内で、`main.main`関数に対して`//go:cgo_export_static main.main`と`//go:cgo_export_dynamic main.main`ディレクティブを追加しています。これにより、Goのビルドシステムは`main.main`をC言語から呼び出し可能なシンボルとして共有ライブラリに含めるようになります。

**影響**:
この変更により、AndroidのJava層はJNIを介してエクスポートされた`main.main`シンボルを直接参照し、呼び出すことができるようになります。これにより、「オールGo」アプリケーションは、GoランタイムがELF初期化関数によって起動された後、Java層からの明示的な呼び出しによってGoのアプリケーションロジックを開始できるようになります。
コミットメッセージが指摘するように、これは「オールGo」アプリにとって特に重要です。なぜなら、これらのアプリでは`.so`ファイルがアプリケーション全体を構成し、Java層はGoのロジックを起動するための最小限のラッパーとして機能するためです。iOSの場合、Goプログラムは通常通りコンパイルされ、`main.main`が自動的に呼び出されるため、この問題は発生しません。

## コアとなるコードの変更箇所

変更は`src/runtime/os_android_arm.go`ファイルに集中しています。

```diff
--- a/src/runtime/os_android_arm.go
+++ b/src/runtime/os_android_arm.go
@@ -6,10 +6,10 @@ package runtime
 
 import _ "unsafe" // for go:cgo_export_static and go:cgo_export_dynamic
 
-// Export the runtime entry point symbol.
+// Export the main function.
 //
-// Used by the app package to start the Go runtime after loading
-// a shared library via JNI. See golang.org/x/mobile/app.\n
+// Used by the app package to start all-Go Android apps that are
+// loaded via JNI. See golang.org/x/mobile/app.\n
 \n-//go:cgo_export_static _rt0_arm_linux1
-//go:cgo_export_dynamic _rt0_arm_linux1
+//go:cgo_export_static main.main
+//go:cgo_export_dynamic main.main
```

具体的には、以下の変更が行われています。

1.  コメントの変更:
    *   `// Export the runtime entry point symbol.` から `// Export the main function.` へ。
    *   `// Used by the app package to start the Go runtime after loading // a shared library via JNI. See golang.org/x/mobile/app.` から `// Used by the app package to start all-Go Android apps that are // loaded via JNI. See golang.org/x/mobile/app.` へ。
    これらのコメントは、エクスポートされるシンボルがGoランタイムの内部エントリポイントではなく、アプリケーションの`main`関数そのものであること、そしてその用途が「オールGo」Androidアプリの起動であることを明確にしています。

2.  `go:cgo_export_static` および `go:cgo_export_dynamic` ディレクティブの変更:
    *   `//go:cgo_export_static _rt0_arm_linux1` が `//go:cgo_export_static main.main` に変更。
    *   `//go:cgo_export_dynamic _rt0_arm_linux1` が `//go:cgo_export_dynamic main.main` に変更。
    これがこのコミットの最も重要な変更点です。エクスポートされるシンボルが、Goランタイムの内部的な初期化ルーチンである`_rt0_arm_linux1`から、Goプログラムの標準的なエントリポイントである`main.main`に切り替わっています。

## コアとなるコードの解説

`src/runtime/os_android_arm.go`は、GoランタイムのAndroid ARMアーキテクチャ固有のOSインタフェースを定義するファイルです。このファイルは、GoランタイムがAndroid環境でどのように動作するか、特にCgoとの連携や外部からの呼び出しに関する設定を含んでいます。

変更前のコードでは、`_rt0_arm_linux1`というシンボルがエクスポートされていました。このシンボルは、Goランタイムの内部的な初期化ルーチンであり、Goプログラムが起動する際に最初に実行されるコードの一部です。以前のGo on Androidのモデルでは、JNIを介してこの`_rt0_arm_linux1`を呼び出すことでGoランタイムを起動し、その内部で`main.main`が呼び出されることを期待していました。

しかし、Goランタイムの初期化方法がELF初期化関数を利用する形に変わったことで、`_rt0_arm_linux1`を外部から呼び出す必要がなくなり、また、ELF初期化関数が`main.main`を自動的に呼び出さなくなりました。

そこで、このコミットでは、`//go:cgo_export_static main.main`と`//go:cgo_export_dynamic main.main`というディレクティブを追加することで、Goプログラムの真のエントリポイントである`main.main`関数を直接、共有ライブラリの外部シンボルとして公開しています。

*   `go:cgo_export_static main.main`: Goコードが静的ライブラリとしてビルドされる場合（例えば、`go build -buildmode=c-archive`）、`main.main`がC言語からリンク可能な静的シンボルとしてエクスポートされることを保証します。
*   `go:cgo_export_dynamic main.main`: Goコードが共有ライブラリとしてビルドされる場合（例えば、`go build -buildmode=c-shared`）、`main.main`がC言語から動的にリンク可能なシンボルとしてエクスポートされることを保証します。

これにより、AndroidのJava層は、JNIを通じてこのエクスポートされた`main.main`シンボルを直接参照し、呼び出すことができるようになります。`golang.org/x/mobile/app`のようなフレームワークは、このエクスポートされた`main.main`をAndroidのライフサイクルイベント（例: `onCreate`）から呼び出すことで、Goアプリケーションの起動と制御を行います。

この変更は、GoがAndroid上でよりネイティブな共有ライブラリとして振る舞い、かつ「オールGo」アプリケーションがそのエントリポイントを外部に公開して適切に起動できるようにするための、重要な橋渡しとなる修正です。

# [インデックス 2639] ファイルの概要

このコミットは、Go言語の初期開発段階において、リンカが型情報（`typestrings`および`typesigs`）を処理する方法に関する重要な内部変更を示しています。具体的には、リンカ（`ld`）が直接提供していた型情報の収集および定義メカニズムが廃止され、関連するコードが削除されました。これは、Goランタイムの型システム管理における責任の再配分、またはより洗練された型情報表現への移行を意味すると考えられます。

## 変更の背景

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われたものです。Goは当初から強力なランタイム型システムを持っていましたが、その実装方法は時間の経過とともに進化してきました。この変更の背景には、Goのコンパイラ、リンカ、およびランタイムが型情報をどのように連携して管理するかという内部アーキテクチャの再設計があったと考えられます。

初期のGoリンカ（`ld`）は、プログラム内で使用される型に関するメタデータ（`typestrings`や`typesigs`）を収集し、最終的なバイナリに埋め込む役割の一部を担っていました。しかし、このコミットによって、リンカが直接これらの型情報を生成・管理するアプローチが「不要になった（obsolete）」と判断されました。これは、型情報の生成がコンパイラ側に完全に移管されたか、あるいはランタイムが型情報を取得する新しい、より効率的なメカニズムが導入されたことを示唆しています。

Go言語の進化の過程では、リンカの役割は継続的に見直され、最適化されてきました。例えば、後のGo 1.15や1.16では、リンカの古いデータ構造のクリーンアップや、DWARFデバッグ情報の型生成がリンカからコンパイラへ移動するといった大きな変更が行われています。この2009年のコミットは、そうしたリンカの役割分担と型情報管理の進化の初期段階における一例と見ることができます。

## 前提知識の解説

### リンカ（Linker）の役割

リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o`ファイルなど）やライブラリを結合し、実行可能なプログラムを生成するツールです。このプロセスには、シンボル解決（あるオブジェクトファイルで定義された関数や変数を、別のオブジェクトファイルから参照できるようにする）や、再配置（メモリ上の最終的な位置に基づいてアドレスを調整する）などが含まれます。

Go言語のような、リフレクションやガベージコレクションといったランタイム機能を持つ言語では、リンカは単にコードを結合するだけでなく、ランタイムが必要とするメタデータ（型情報、ガベージコレクション情報など）をバイナリに埋め込む重要な役割も担います。

### Goの型システムとランタイム型情報

Goは静的型付け言語ですが、`interface{}`や`reflect`パッケージを通じて、実行時に型情報を扱うことができます。このランタイム型情報は、コンパイラとリンカによって協力して生成され、最終的な実行可能ファイルに埋め込まれます。これにより、プログラムは実行時に自身の型を検査したり、未知の型の値を操作したりすることが可能になります。

### `typestrings`と`typesigs` (推測される役割)

コミットメッセージと削除されたコードから推測すると、`typestrings`と`typesigs`は、Goのランタイムがリフレクションや型アサーションなどの機能を実現するために必要とする型メタデータの一部であったと考えられます。

*   **`typestrings`**: 型の名前や構造を文字列として表現したもので、例えば`struct { A int; B string }`のような型定義を文字列形式で保持していた可能性があります。これは、デバッグ情報や、実行時の型情報の可読性向上に利用されたかもしれません。
*   **`typesigs`**: 型のシグネチャ（関数の引数と戻り値の型、構造体のフィールドの型など）を表現するデータ構造へのポインタの配列であったと推測されます。これは、ランタイムが特定の型の構造を効率的に参照するために使用された可能性があります。

これらの情報は、リンカがプログラム全体から収集し、`gotypestrings`や`gotypesigs`といったグローバル変数として最終バイナリに埋め込んでいたと考えられます。

## 技術的詳細

このコミットでは、Goのリンカ（`src/cmd/ld/go.c`）から`definetypestrings`関数と`definetypesigs`関数、およびそれらを呼び出すコードが削除されています。これらの関数は、Goの初期のリンカが型情報を収集し、実行可能ファイルに埋め込むための主要なメカニズムでした。

### `definetypestrings`関数の詳細（削除されたコードから推測）

削除された`definetypestrings`関数は、以下の処理を行っていたと見られます。

1.  **型エクスポートの収集**: リンカが処理するすべてのパッケージからエクスポートされた型情報を収集していました。これは、`ihash`というハッシュテーブルを走査し、プレフィックスが"type"であるエクスポートを識別することで行われていました。
2.  **型情報のソート**: 収集した型情報を名前でソートしていました。これにより、バイナリ内の型情報の配置が一貫性を持つようになります。
3.  **Go文字列の構築**: ソートされた型情報を結合し、単一の大きなGo文字列（先頭に4バイトの長さ情報を持つ）を構築していました。この文字列には、各型の名前とその定義が含まれていました。
4.  **リンカデータ構造への変換**: 構築されたGo文字列を、リンカがバイナリに書き込むためのデータ構造（`Prog`構造体）に変換していました。特に、大きなデータは100バイトのチャンクに分割され、`D_SBIG`というタイプでリンカに渡されていました。これは、リンカが大きなデータを効率的に処理するための内部的な最適化です。
5.  **シンボル`gotypestrings`の定義**: このGo文字列は、`gotypestrings`というシンボルとして定義され、プログラムから参照可能になっていました。

### `definetypesigs`関数の詳細（削除されたコードから推測）

削除された`definetypesigs`関数は、以下の処理を行っていたと見られます。

1.  **型シグネチャシンボルの収集**: `sigt·`というプレフィックスを持つシンボルを収集していました。これらのシンボルは、特定の型のシグネチャ（構造体のレイアウト、関数の引数・戻り値の型など）を表すデータ構造へのポインタであったと推測されます。
2.  **シグネチャシンボルのソート**: 収集したシグネチャシンボルを名前でソートしていました。
3.  **ポインタ配列の構築**: ソートされたシグネチャシンボルへのポインタの配列を構築していました。
4.  **リンカデータ構造への変換**: このポインタ配列をリンカデータ構造に変換し、`D_ADDR`タイプでリンカに渡していました。
5.  **シンボル`gotypesigs`と`ngotypesigs`の定義**: この配列は`gotypesigs`というシンボルとして定義され、配列の要素数（シグネチャの数）は`ngotypesigs`というシンボルとして定義されていました。

### 影響範囲

これらの関数は、Goの初期のリンカである`5l` (ARM), `6l` (x86-64), `8l` (x86) の共通部分である`src/cmd/ld/go.c`に存在し、各アーキテクチャ固有のリンカのメイン処理（`obj.c`）から呼び出されていました。そのため、これらの関数の削除は、すべてのサポート対象アーキテクチャにおけるGoプログラムのリンクプロセスに影響を与えました。

この変更は、Goの型情報管理がリンカから切り離され、コンパイラやランタイムのより低レベルな部分で直接処理されるようになったことを強く示唆しています。これにより、リンカの複雑性が軽減され、型情報の表現や処理の柔軟性が向上した可能性があります。

## コアとなるコードの解説

削除された`definetypestrings`および`definetypesigs`関数は、Goのリンカがプログラムの型情報を収集し、最終的な実行可能ファイルに埋め込むための具体的な実装でした。

`definetypestrings`は、プログラム内で定義されたすべてのエクスポートされた型（`type`プレフィックスを持つシンボル）を走査し、それらの名前と定義を結合して一つの大きな文字列を作成していました。この文字列は、Goのランタイムが実行時に型情報を参照するために使用される`gotypestrings`というグローバルシンボルとしてバイナリに埋め込まれていました。特に、Go文字列のフォーマット（先頭4バイトが長さ）に合わせてデータを構築し、リンカの内部表現（`Prog`構造体と`D_SBIG`タイプ）に変換する処理が含まれていました。

一方、`definetypesigs`は、`sigt·`プレフィックスを持つシンボル（型シグネチャを表す）を収集し、それらへのポインタの配列を作成していました。この配列は`gotypesigs`というグローバルシンボルとして、その要素数（シグネチャの数）は`ngotypesigs`というグローバルシンボルとしてバイナリに埋め込まれていました。これは、ランタイムが特定の型の構造や動作に関する情報を効率的に取得するために利用されていたと考えられます。

これらの関数の削除は、Goの型情報管理のパラダイムシフトを意味します。リンカが直接これらの情報を収集・整形してバイナリに埋め込むのではなく、コンパイラがより詳細な型情報を生成し、それをリンカがより単純な形式で処理するか、あるいはランタイムが型情報を動的に構築するメカニズムが導入された可能性が高いです。これにより、リンカの役割が簡素化され、型システムの柔軟性や効率が向上したと考えられます。

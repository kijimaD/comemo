## 変更の背景

このコミットは、Go言語の初期開発段階における`eval`パッケージ（おそらくはGoコードを評価・実行するためのインタプリタまたはJITコンパイラのプロトタイプ）の機能拡張と堅牢化を目的としています。当時のGo言語はまだ発展途上にあり、言語仕様の策定と同時に、そのセマンティクスを正確に反映する実行環境の構築が進められていました。

主な背景としては以下の点が挙げられます。

1.  **関数機能の導入**: Go言語の重要な要素である関数リテラル（匿名関数）と関数呼び出しを`eval`環境でサポートする必要がありました。特に、単一値を返す非可変長引数関数に焦点を当てることで、段階的に機能を実装しています。
2.  **型システムの強化**: Goの型システムは静的で厳格ですが、`eval`パッケージ内でこれを正確に扱うための基盤が不足していました。名前付き型（`type MyInt int`のような定義）の導入と、それらを適切に処理するための型コンパイラ、そして組み込み型（`int`, `bool`など）を管理するユニバーサルスコープが必要とされていました。
3.  **型情報の正確性**: `Type.Zero`メソッドが型のゼロ値を生成する際に、特にアーキテクチャ依存の型（例: `int`, `uintptr`）や境界を持つ型（例: 配列）において、`unsafe.Sizeof`のような低レベルな情報を用いて正確なサイズと表現を決定する必要がありました。これにより、異なるアーキテクチャ（例: 32ビットと64ビット）間での型の振る舞いの不整合を解消することが目指されました。
4.  **型比較の統一**: `Type.compatible`メソッドが全ての型で同等の実装を持つことが判明したため、これを廃止し、より汎用的な`Type.rep`（代表型）を導入することで、名前付き型を剥がした基底型での比較を可能にし、型システムの内部処理を簡素化・統一化しています。
5.  **代入演算子のセマンティクス**: `a += b`のような複合代入演算子（assign-op）において、左辺の式が複数回評価される可能性のあるバグを修正し、Go言語の仕様に沿って一度だけ評価されるように変更する必要がありました。これは、副作用を持つ式（例: `f()[0] += 1`）の挙動を正確にするために不可欠です。

これらの変更は、Go言語の`eval`パッケージがより広範なGoコードを正確に解釈・実行できるような、より堅牢で仕様に忠実な基盤を構築するためのものでした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/インタプリタの基本的な概念を理解しておく必要があります。

1.  **Go言語の型システム**:
    *   **基底型 (Underlying Type)**: `int`, `bool`, `string`などのプリミティブ型や、`[]T`, `map[K]V`, `struct{...}`などの複合型。
    *   **名前付き型 (Named Type)**: `type MyInt int`のように、既存の型に新しい名前を付けて定義された型。`MyInt`は`int`とは異なる型ですが、その基底型は`int`です。Goでは、名前付き型と基底型は異なる型として扱われますが、特定の状況下（例: 代入互換性）では基底型が考慮されます。
    *   **型互換性 (Type Compatibility)**: Goでは、型が「同一 (identical)」であるか「代入可能 (assignable)」であるかによって互換性が判断されます。名前付き型は、その基底型が同じであっても、異なる名前を持つ限り同一ではありません。
    *   **`unsafe.Sizeof`**: Goの`unsafe`パッケージに含まれる関数で、任意の型のバイトサイズを返します。これは、メモリレイアウトやアライメントに依存する低レベルな操作で利用されます。

2.  **関数リテラル (Function Literals)**:
    *   Goにおける匿名関数（クロージャ）のことです。`func(args) { ... }`のような構文で定義され、変数に代入したり、直接呼び出したり、他の関数に引数として渡したりできます。このコミットでは、特に単一の戻り値を持つ非可変長引数関数リテラルの実装に焦点を当てています。

3.  **スコープ (Scope)**:
    *   プログラム内で識別子（変数名、型名など）が有効な範囲を指します。Goでは、ブロック、関数、パッケージレベルでスコープが定義されます。
    *   **ユニバーサルスコープ (Universal Scope)**: Goプログラム全体で常に利用可能な組み込みの識別子（`int`, `true`, `false`など）が定義されている最上位のスコープです。

4.  **仮想マシン (Virtual Machine, VM)**:
    *   Goの`eval`パッケージは、Goコードを直接機械語にコンパイルするのではなく、中間表現（バイトコードなど）に変換し、そのバイトコードを解釈・実行するVMを内部に持っていると考えられます。このコミットでは、ステートメントの実行と単一値の戻りを扱うシンプルなVMの基盤が実装されています。

5.  **コンパイラのフェーズ**:
    *   **字句解析 (Lexical Analysis)**: ソースコードをトークンに分割。
    *   **構文解析 (Syntax Analysis)**: トークン列から抽象構文木 (AST) を構築。
    *   **意味解析 (Semantic Analysis)**: ASTに対して型チェック、スコープ解決などを行い、意味的な正当性を検証。このフェーズで型コンパイラが活躍します。
    *   **コード生成 (Code Generation)**: 意味解析されたASTから、VMが実行できる中間コード（バイトコード）を生成。

6.  **`go/ast`, `go/token`, `go/scanner`パッケージ**:
    *   Go言語の標準ライブラリに含まれるパッケージで、Goソースコードの解析に使用されます。
        *   `go/token`: ソースコードの位置情報（ファイル、行、列）やトークン（識別子、キーワード、演算子など）を定義します。
        *   `go/scanner`: 字句解析器を提供し、ソースコードをトークンに分割します。
        *   `go/ast`: 抽象構文木 (AST) のデータ構造を定義し、Goソースコードの構文構造を表現します。

## コアとなるコードの解説

### `Type.rep()`の導入と型システムの統一

以前は`Type.literal()`というメソッドがありましたが、このコミットでは`Type.rep()`が導入され、`Type.literal()`のほとんどの用途が置き換えられました。
`Type.rep()`は、名前付き型（例: `type MyInt int`における`MyInt`）が与えられた場合に、その基底型（この例では`int`）を返します。名前付き型でない場合は、その型自身を返します。
これにより、型チェックや型変換のロジックにおいて、名前付き型と基底型を区別する必要がある場合に、常に基底型に基づいて処理を行うことができるようになり、型システムの内部的な一貫性と簡潔性が向上しました。

例えば、`expr.go`の`convertTo`関数では、型変換の際に`t.rep().(BoundedType)`のように`rep()`を呼び出すことで、名前付き型であってもその基底型が`BoundedType`であるかを正確に判断しています。また、`mkAssign`関数では、代入互換性のチェックに`lt.literal() != r.t.literal()`ではなく、`lt.literal() != r.t.literal()`が使われていますが、これはコミットメッセージの「The spec is wrong here. The types must be identical, not compatible.」というコメントと関連しており、より厳密な型同一性チェックに移行していることを示唆しています。

### `extractEffect()`による代入演算子の副作用分離

`expr.go`に新しく追加された`extractEffect()`メソッドは、複合代入演算子（`+=`, `-=`など）のセマンティクスを正確に実装するために非常に重要です。Go言語の仕様では、`x op= y`という形式の代入演算子は、`x = x op y`と等価ですが、`x`が副作用を持つ式（例: `m[f()]`）である場合、`f()`は一度だけ評価される必要があります。

`extractEffect()`は、この問題を解決するために、以下のような処理を行います。

1.  **一時変数の作成**: 左辺の式`x`の評価結果を保持するための一時変数をスコープ内に作成します。
2.  **アドレスの取得と代入**: `x`のアドレスを取得し、そのアドレスを一時変数に代入する「効果 (effect)」を表現する関数を生成します。これは「`temp := &x`」に相当します。
3.  **副作用のない式**: 一時変数へのポインタを逆参照する「`*temp`」に相当する、副作用のない新しい式を生成します。

`stmt.go`の`doAssignOp`メソッドでは、複合代入演算子を処理する際に、まず左辺の式`l`に対して`l.extractEffect()`を呼び出します。これにより、`effect`関数と、副作用のない新しい左辺の式`l'`が得られます。その後、`l'`と右辺`r`を使って二項演算を行い、その結果を`l`の元の場所（一時変数経由で）に代入します。この一連の操作は、VMの命令としてキューに追加され、実行時に`effect`が一度だけ実行されることを保証します。

### 関数リテラルとVMの連携

`func.go`で定義された`vm`と`evalFunc`は、Goの関数リテラルを`eval`パッケージ内で実行するための基盤を提供します。

*   `evalFunc`は、関数が定義された時点のスコープ（クロージャのキャプチャ）と、その関数が実行すべきバイトコード（`code`）を保持します。
*   `expr.go`の`DoFuncLit`は、`ast.FuncLit`（Goのソースコード上の関数リテラル）を解析し、`compileFunc`を呼び出して`evalFunc`を生成します。この`evalFunc`は、`exprCompiler`の`evalFunc`フィールドに設定され、式として関数リテラルが評価された際にこの`evalFunc`オブジェクトが返されるようになります。
*   `DoCallExpr`は、関数呼び出しを処理する際に、呼び出される関数を表す式を評価して`evalFunc`オブジェクトを取得します。そして、その`evalFunc`の`NewFrame()`メソッドで新しい実行フレームを作成し、引数をそのフレームに設定した後、`Call()`メソッドで関数本体のバイトコードを実行します。

`stmt.go`の`compileFunc`関数は、関数宣言（`FuncDecl`）と関数本体のASTを受け取り、関数本体のスコープを構築し、引数と戻り値を変数として定義します。そして、`blockCompiler`を使って関数本体のステートメントをVMの命令（`code`）にコンパイルします。この`code`が`evalFunc`に格納され、実行時に利用されます。

これらの変更により、Goの`eval`パッケージは、関数リテラル、関数呼び出し、名前付き型、そして正確な代入セマンティクスといった、Go言語のより高度な機能をサポートできるようになりました。これは、Go言語の初期のインタプリタ/コンパイラ開発における重要なマイルストーンと言えます。

# [インデックス 21473] ファイルの概要

このコミットは、Goランタイムにおけるハッシュアルゴリズムと等価性比較アルゴリズムの関数シグネチャから、`size` 引数を削除する大規模なリファクタリングを実施しています。これにより、コンパイラ、ランタイム、およびアセンブリコード全体にわたる変更が行われ、Goバイナリのサイズ削減とコードの簡素化が図られています。

## 元コミット内容

このコミットは、Goランタイムのハッシュおよび等価性比較アルゴリズムから `size` 引数を削除することを目的としています。以前は `equal(p, q *T, size uintptr) bool` のように `size` 引数を受け取っていましたが、この変更により `equal(p, q *T) bool` のように `size` 引数がなくなります。ハッシュアルゴリズムについても同様です。

`size` 引数はほとんどの場合不要であり、例えば `f32equal` のような特定の型に対する比較関数は、比較対象のサイズ（この場合は4バイト）を既に知っているためです。

サイズが不明なケース（例えば、ジェネリックなメモリ操作）では、必要なサイズごとにクロージャが割り当てられます。このクロージャは、クロージャからサイズを読み取り、サイズ引数を持つジェネリックなコードを呼び出すアセンブリスタブを指します。

この変更により、Goバイナリのサイズが0.07%削減され、パフォーマンスへの影響は測定されていません。

## 変更の背景

Goランタイムのハッシュおよび等価性比較関数において、`size` 引数は多くの場合冗長でした。これは、`int32` や `float64` のようなプリミティブ型に対する比較関数は、その型のサイズをコンパイル時に静的に知っているためです。例えば、`f32equal` は常に4バイトのデータを比較します。このような状況で毎回 `size` 引数を渡すことは、関数呼び出しのオーバーヘッドをわずかに増加させ、またコードの記述を複雑にしていました。

このコミットの主な背景は以下の通りです。

1.  **コードの簡素化と効率化**: `size` 引数を削除することで、関数シグネチャが簡素化され、コンパイラがより最適化されたコードを生成しやすくなります。
2.  **バイナリサイズの削減**: `size` 引数を渡すためのコードや、その引数を処理するためのロジックが不要になることで、Goバイナリ全体のサイズがわずかながら削減されます。これは、特に組み込みシステムやリソースが限られた環境でのデプロイにおいて重要です。
3.  **ジェネリックなケースの最適化**: サイズが動的に決定されるようなジェネリックなメモリ操作（`memhash` や `memequal`）の場合、クロージャとアセンブリスタブを組み合わせることで、必要なサイズ情報を効率的に渡す新しいメカニズムが導入されました。これにより、一般的なケースでは `size` 引数を省略しつつ、特殊なケースにも対応できる柔軟性が確保されました。

## 前提知識の解説

このコミットの変更を理解するためには、以下のGoランタイムとコンパイラの概念に関する知識が必要です。

### 1. Goのハッシュと等価性比較

Go言語では、マップのキーやインターフェースの比較など、様々な場面で値のハッシュ計算と等価性比較が行われます。これらの操作は、Goランタイム内部で型ごとに定義されたアルゴリズム (`typeAlg` 構造体) を通じて実行されます。

*   **ハッシュ関数**: `func(unsafe.Pointer, uintptr, uintptr) uintptr` のようなシグネチャを持ち、データへのポインタ、サイズ、シード値を受け取ってハッシュ値を返します。
*   **等価性比較関数**: `func(unsafe.Pointer, unsafe.Pointer, uintptr) bool` のようなシグネチャを持ち、2つのデータへのポインタとサイズを受け取って真偽値を返します。

これらの関数は、`algarray` という配列に格納され、Goの型システムと連携して適切なアルゴリズムが選択されます。

### 2. `unsafe.Pointer` と `uintptr`

*   **`unsafe.Pointer`**: 任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムをバイパスしてメモリを直接操作するために使用されます。ランタイム内部やCGOとの連携でよく使われます。
*   **`uintptr`**: ポインタを整数として表現する型です。ポインタ演算を行う際に使用されますが、ガベージコレクタは `uintptr` をポインタとして認識しないため、注意が必要です。

### 3. クロージャ (Closures)

Goにおけるクロージャは、関数と、その関数が定義された環境（レキシカルスコープ）を組み合わせたものです。このコミットでは、サイズが動的に決まるハッシュ/等価性比較のために、クロージャが利用されます。具体的には、クロージャが特定の `size` 値を「キャプチャ」し、その `size` 値をアセンブリスタブに渡すことで、ジェネリックなメモリ操作関数が適切なサイズで呼び出されるようにします。

### 4. アセンブリスタブ (Assembly Stubs)

Goランタイムは、パフォーマンスが重要な部分や、Go言語では直接アクセスできない低レベルな操作（CPUレジスタの操作など）のために、アセンブリ言語で書かれたコードを含んでいます。このコミットでは、クロージャから渡された `size` 情報を読み取り、それを引数としてジェネリックなGo関数（または別のアセンブリ関数）に渡すための「スタブ」としてアセンブリコードが利用されます。

### 5. Goコンパイラ (`gc`) の役割

Goコンパイラ (`gc`) は、Goソースコードを機械語に変換するだけでなく、ランタイムとの連携に必要なメタデータや関数呼び出し規約を生成します。このコミットでは、コンパイラがハッシュ/等価性比較関数の新しいシグネチャに合わせて、これらの関数を呼び出すコードを生成するように変更されています。特に、`src/cmd/gc` 以下のファイルは、コンパイラのバックエンド部分であり、型の情報から適切なランタイム関数を選択し、コードを生成する役割を担っています。

### 6. `AMEM` 型

Goランタイム内部では、型をその特性に基づいて分類します。`AMEM` (Algorithm Memory) は、その値が単なるメモリブロックとして扱われ、バイト単位で比較やハッシュ計算が可能な型を指します。例えば、構造体や配列などがこれに該当します。このコミットでは、`AMEM` 型のハッシュ/等価性比較の扱いが特に変更されています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのハッシュおよび等価性比較関数のシグネチャから `size` 引数を削除し、その情報を必要とするケースでは別のメカニズムで提供するように変更した点にあります。

### 1. 関数シグネチャの変更

最も顕著な変更は、`src/runtime/alg.go` 内の `typeAlg` 構造体です。

**変更前**:
```go
type typeAlg struct {
	hash  func(unsafe.Pointer, uintptr, uintptr) uintptr // (ptr to object, size, seed) -> hash
	equal func(unsafe.Pointer, unsafe.Pointer, uintptr) bool // (ptr to object A, ptr to object B, size) -> ==?
}
```

**変更後**:
```go
type typeAlg struct {
	hash  func(unsafe.Pointer, uintptr) uintptr // (ptr to object, seed) -> hash
	equal func(unsafe.Pointer, unsafe.Pointer) bool // (ptr to object A, ptr to object B) -> ==?
}
```
`hash` 関数から `size` 引数 (`uintptr`) が、`equal` 関数から `size` 引数 (`uintptr`) がそれぞれ削除されました。

### 2. サイズが既知のケースの簡素化

`int32`, `float64`, `string` などのプリミティブ型や、固定サイズの構造体/配列に対するハッシュ/等価性比較関数は、元々その型のサイズを静的に知っていました。これらの関数は、新しいシグネチャに合わせて `size` 引数を取り除くように変更されました。例えば、`f32hash` や `f64hash` は、それぞれ4バイト、8バイトという固定サイズを内部で利用するため、外部から `size` を渡す必要がなくなりました。

### 3. サイズが動的なケース（`memhash_varlen`, `memequal_varlen`）

Goのマップキーやインターフェースの比較など、ランタイムが任意の型のハッシュや比較を行う必要がある場合、その型のサイズは動的に決定されます。このような「サイズが不明」または「可変長」のケースに対応するため、新しいメカニズムが導入されました。

*   **クロージャの利用**: コンパイラ (`src/cmd/gc/reflect.c` の `dalgsym` 関数など) は、`AMEM` (メモリベースのアルゴリズム) 型に対して、特定のサイズを持つクロージャを生成します。このクロージャは、そのサイズ情報を内部に保持します。
*   **アセンブリスタブ**: 生成されたクロージャは、`runtime·memhash_varlen` や `runtime·memequal_varlen` といったアセンブリ言語で書かれたスタブ関数を指します。
*   **サイズ情報の取得とジェネリック関数呼び出し**: これらのアセンブリスタブは、クロージャから埋め込まれた `size` 情報を読み取ります。そして、その `size` を引数として、実際のメモリハッシュ/比較を行うジェネリックな関数（例: `runtime·memhash` や `runtime·memeq`）を呼び出します。

このアプローチにより、`typeAlg` の関数シグネチャは簡素化されつつ、必要な場所ではサイズ情報が透過的に提供されるようになります。

### 4. コンパイラ (`gc`) の変更

コンパイラは、ランタイムの変更に合わせて、ハッシュ/等価性比較関数を呼び出すコード生成ロジックを調整しました。

*   `src/cmd/gc/builtin.c` および `src/cmd/gc/runtime.go`: `memequal` 関連の組み込み関数の宣言から `size` 引数が削除されました。
*   `src/cmd/gc/reflect.c`: 型のアルゴリズムシンボルを生成する `dalgsym` 関数が変更されました。特に `AMEM` 型の場合、サイズに応じた `memhash_varlen` および `memequal_varlen` のクロージャを生成するロジックが追加されました。
*   `src/cmd/gc/subr.c`: `genhash` および `geneq` 関数（ハッシュ/等価性比較関数を生成する）が、`size` 引数を渡さないように変更されました。また、`eqmemfunc` や `eqmem` といったメモリ比較関連のヘルパー関数も、`size` 引数の扱いが調整されました。
*   `src/cmd/gc/walk.c`: 比較演算子 (`==`, `!=`) のコード生成を担当する `walkcompare` 関数が、`eqfor` 関数（等価性比較関数を取得する）から返される関数が `size` 引数を取らないことを前提とするように変更されました。

### 5. アセンブリコードの変更

各アーキテクチャ (`386`, `amd64`, `amd64p32`, `arm`, `ppc64x`) のアセンブリファイルに、`runtime·memhash_varlen` と `runtime·memequal_varlen` が追加されました。これらの関数は、Goのクロージャが呼び出すエントリポイントとして機能し、クロージャに埋め込まれたサイズ情報をレジスタにロードし、それを引数として実際の `memhash` や `memeq` 関数に渡します。

### 6. `memhash` 関数の引数順序変更

`src/runtime/hash32.go` と `src/runtime/hash64.go` の `memhash` 関数では、引数の順序が `(p unsafe.Pointer, s, seed uintptr)` から `(p unsafe.Pointer, seed, s uintptr)` に変更されました。これは、`aeshash` などのアセンブリ関数との整合性を保つためと考えられます。

### 7. マップ実装の更新

`src/runtime/hashmap.go` および `src/runtime/hashmap_fast.go` では、マップの内部実装でキーのハッシュ計算や比較を行う際に、`alg.hash` および `alg.equal` の呼び出しから `size` 引数が削除されました。

これらの変更により、Goランタイムのハッシュおよび等価性比較のメカニズムは、よりクリーンで効率的なものになりました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は多岐にわたりますが、特に重要なファイルと変更点を以下に示します。

1.  **`src/runtime/alg.go`**:
    *   `typeAlg` 構造体の `hash` および `equal` フィールドの関数シグネチャから `uintptr` 型の `size` 引数が削除されました。
    *   `memhash0`, `memhash8`, `memhash16`, `memhash32`, `memhash64`, `memhash128` といった、特定の固定サイズに対するハッシュ関数が追加されました。
    *   `memhash_varlen` と `memequal_varlen` という、可変長サイズを扱うためのアセンブリ実装される関数が宣言されました。
    *   `algarray` の初期化が変更され、`alg_MEM` が `nil, nil` になり、固定サイズハッシュ関数が対応する `alg_MEMx` エントリに割り当てられました。
    *   既存のハッシュ/等価性比較関数（`f32hash`, `f64hash`, `interhash`, `memequal0` など）のシグネチャと内部の呼び出しが、`size` 引数なしの新しい形式に更新されました。

2.  **`src/cmd/gc/reflect.c`**:
    *   `dalgsym` 関数（型のアルゴリズムシンボルを生成）が大幅に変更されました。
    *   `AMEM` (メモリベースのアルゴリズム) 型の場合、`t->width` (型のサイズ) に基づいて、`memhash_varlen` および `memequal_varlen` を指すクロージャ (`.hashfunc%lld`, `.eqfunc%lld`) を生成するロジックが追加されました。これらのクロージャには、サイズ情報が埋め込まれます。
    *   それ以外の型については、引き続き型固有のハッシュ/等価性比較関数が生成されます。

3.  **`src/cmd/gc/subr.c`**:
    *   `genhash` 関数（ハッシュ関数を生成）のシグネチャから `s uintptr` 引数が削除され、内部のコード生成ロジックも `size` 引数を渡さないように変更されました。
    *   `geneq` 関数（等価性比較関数を生成）も同様に、`s uintptr` 引数が削除され、内部のコード生成ロジックが変更されました。
    *   `eqmemfunc` 関数は、`needsize` という新しい引数を受け取るようになり、`memequal` のようなジェネリックな関数を呼び出す際に `size` 引数が必要かどうかを示すようになりました。
    *   `hashfor` 関数で `AMEM` 型が渡された場合に `fatal` エラーを出すようになりました。これは、`AMEM` 型のハッシュは `memhash_varlen` を通じて処理されるためです。

4.  **`src/cmd/gc/walk.c`**:
    *   `eqfor` 関数（等価性比較関数を取得）が `needsize` 引数を受け取るようになり、返される関数が `size` 引数を必要とするかどうかを示すようになりました。
    *   `walkcompare` 関数（比較演算子のコード生成）が、`eqfor` から返される `needsize` の値に基づいて、`size` 引数を渡すかどうかを条件分岐するようになりました。

5.  **`src/runtime/asm_*.s` (アセンブリファイル群)**:
    *   各アーキテクチャ (`386`, `amd64`, `amd64p32`, `arm`, `ppc64x`) に、`runtime·memhash_varlen` と `runtime·memequal_varlen` という新しいアセンブリ関数が追加されました。これらの関数は、クロージャから `size` 情報を読み取り、それを引数として `runtime·memhash` や `runtime·memeq` といったジェネリックなメモリ操作関数に渡します。
    *   `aeshash` 関連のアセンブリ関数（`aeshash`, `aeshashstr`, `aeshash32`, `aeshash64`）の引数レジスタの割り当てが、`size` 引数の削除に合わせて調整されました。

6.  **`src/runtime/hash32.go`, `src/runtime/hash64.go`**:
    *   `memhash` 関数の引数順序が `(p unsafe.Pointer, s, seed uintptr)` から `(p unsafe.Pointer, seed, s uintptr)` に変更されました。

7.  **`src/runtime/hashmap.go`, `src/runtime/hashmap_fast.go`**:
    *   マップの内部実装で `alg.hash` および `alg.equal` を呼び出す箇所から、`size` 引数が削除されました。

これらの変更は、Goランタイムの低レベルな部分に深く関わっており、コンパイラとランタイムの密接な連携によって実現されています。

## コアとなるコードの解説

### `src/runtime/alg.go` の変更

`typeAlg` 構造体の変更は、Goランタイムが型ごとのハッシュおよび等価性比較アルゴリズムをどのように表現するかという、根本的な部分に影響を与えます。`size` 引数を削除することで、より特定の型に特化した関数シグネチャとなり、コンパイラがより直接的な呼び出しを生成できるようになります。

```go
type typeAlg struct {
	hash  func(unsafe.Pointer, uintptr) uintptr // (ptr to object, seed) -> hash
	equal func(unsafe.Pointer, unsafe.Pointer) bool // (ptr to object A, ptr to object B) -> ==?
}
```
この変更により、`algarray` に格納される関数ポインタの型が変更され、それに合わせて `memhash0` から `memhash128` までの固定サイズハッシュ関数が導入されました。これらは、それぞれ0バイト、1バイト、2バイト、4バイト、8バイト、16バイトのデータをハッシュするための専用関数です。

`memhash_varlen` と `memequal_varlen` は、Goコード上では宣言のみで、実際の本体はアセンブリで実装されます。これは、Goの関数呼び出し規約ではクロージャから追加の情報を直接受け取るのが難しいため、アセンブリで低レベルな操作を行う必要があるからです。

### `src/cmd/gc/reflect.c` の `dalgsym` 関数

`dalgsym` 関数は、Goの型システムがランタイムのハッシュ/等価性比較アルゴリズムと連携するための重要な部分です。このコミットでは、特に `AMEM` 型（メモリブロックとして扱われる型）の処理が変更されました。

```c
	if(algtype(t) == AMEM) {
		// we use one algorithm table for all AMEM types of a given size
		p = smprint(".alg%lld", t->width);
		s = pkglookup(p, typepkg);
		free(p);
		if(s->flags & SymAlgGen)
			return s;
		s->flags |= SymAlgGen;

		// make hash closure
		p = smprint(".hashfunc%lld", t->width);
		hashfunc = pkglookup(p, typepkg);
		free(p);
		ot = 0;
		ot = dsymptr(hashfunc, ot, pkglookup("memhash_varlen", runtimepkg), 0);
		ot = duintxx(hashfunc, ot, t->width, widthptr); // size encoded in closure
		ggloblsym(hashfunc, ot, DUPOK|RODATA);

		// make equality closure
		p = smprint(".eqfunc%lld", t->width);
		eqfunc = pkglookup(p, typepkg);
		free(p);
		ot = 0;
		ot = dsymptr(eqfunc, ot, pkglookup("memequal_varlen", runtimepkg), 0);
		ot = duintxx(eqfunc, ot, t->width, widthptr);
		ggloblsym(eqfunc, ot, DUPOK|RODATA);
	} else {
		// generate an alg table specific to this type
		// ... (既存のロジック)
	}
```
このコードは、`AMEM` 型の場合、その型のサイズ (`t->width`) に応じて、`memhash_varlen` および `memequal_varlen` を呼び出すためのクロージャを生成しています。重要なのは、`duintxx(hashfunc, ot, t->width, widthptr)` の行で、**型のサイズ (`t->width`) がクロージャのデータ部分に埋め込まれている**点です。この埋め込まれたサイズ情報は、後でアセンブリスタブによって読み取られます。

### アセンブリスタブ (`src/runtime/asm_*.s`)

各アーキテクチャのアセンブリファイルに追加された `runtime·memhash_varlen` と `runtime·memequal_varlen` は、このコミットの鍵となる部分です。これらは、Goのクロージャから呼び出され、クロージャに埋め込まれたサイズ情報を取得して、ジェネリックなメモリ操作関数に渡す役割を担います。

例として、`src/runtime/asm_amd64.s` の `runtime·memhash_varlen` を見てみましょう。

```assembly
// memhash_varlen(p unsafe.Pointer, h seed) uintptr
// redirects to memhash(p, h, size) using the size
// stored in the closure.
TEXT runtime·memhash_varlen(SB),NOSPLIT,$32-24
	GO_ARGS
	NO_LOCAL_POINTERS
	MOVQ	p+0(FP), AX
	MOVQ	h+8(FP), BX
	MOVQ	8(DX), CX    // compiler stores size at offset 8 in the closure
	MOVQ	AX, 0(SP)
	MOVQ	BX, 8(SP)
	MOVQ	CX, 16(SP)
	CALL	runtime·memhash(SB)
	MOVQ	24(SP), AX
	MOVQ	AX, ret+16(FP)
	RET
```
このアセンブリコードでは、以下の処理が行われています。
1.  `p` (データポインタ) と `h` (シード) をスタックからレジスタ (`AX`, `BX`) にロードします。
2.  `MOVQ 8(DX), CX` の行が重要です。`DX` レジスタには、現在の関数（`memhash_varlen`）を呼び出したクロージャのポインタが含まれています。`8(DX)` は、そのクロージャのオフセット8バイトの位置にある値（つまり、コンパイラが埋め込んだ `size` 情報）を `CX` レジスタにロードしています。
3.  `AX`, `BX`, `CX` (データポインタ、シード、サイズ) を引数としてスタックにプッシュし、`runtime·memhash` というジェネリックなメモリハッシュ関数を呼び出します。
4.  `runtime·memhash` の結果をスタックから取得し、戻り値として返します。

これにより、Goのコードからは `size` 引数なしでハッシュ関数を呼び出せるようになり、ランタイムの内部で必要に応じて `size` 情報が透過的に提供されるという仕組みが実現されています。`memequal_varlen` も同様のロジックで動作します。

### `src/runtime/hashmap.go` の変更

マップの内部実装では、キーのハッシュ計算や比較に `alg.hash` と `alg.equal` が使用されます。これらの呼び出しから `size` 引数が削除されたことで、マップのコードが簡素化されました。


## 変更の背景

Go言語は設計当初から、シンプルさと明確さを重視していました。このコミットが行われた2009年6月は、Go言語が一般に公開される直前の非常に初期の段階であり、言語仕様やコンパイラの実装が活発に開発・調整されていました。

1.  **識別子の文字セットの厳密化 (bug163)**: 多くのプログラミング言語では、識別子に使用できる文字に制限があります。Go言語も例外ではなく、特に初期の段階では、Unicode文字のどの範囲を識別子として許可するかについて試行錯誤がありました。このバグ修正は、識別子の定義をより厳密にし、予期せぬ挙動や移植性の問題を避けるために、非ASCII文字（特に日本語の表意文字）を識別子として認めない方針を明確にしたものと考えられます。これは、コンパイラの堅牢性を高め、言語の安定した基盤を築く上で重要なステップでした。

2.  **生文字列リテラルの改行許可 (bug164)**: Goの生文字列リテラル（バッククォート `` ` `` で囲まれた文字列）は、エスケープシーケンスを解釈せず、記述された通りの内容を文字列として扱う機能です。これは正規表現やHTML、JSONなどの複数行にわたるテキストをコード内に埋め込む際に非常に便利です。初期の実装では、この生文字列リテラル内に改行文字を含めることが仕様上許されていなかったか、あるいはコンパイラが正しく処理できていなかった可能性があります。この修正により、生文字列リテラルがその本来の意図通り、複数行のテキストをそのまま表現できるようになり、言語の表現力が向上しました。

3.  **コンパイラの堅牢性向上 (bug166, `go.y` の変更)**: `go.y` はGoコンパイラの構文解析器の定義ファイルであり、`yyoptsemi` はGoの自動セミコロン挿入（Automatic Semicolon Insertion, ASI）メカニズムに関連する関数です。この変更は、特定の文脈でのセミコロン挿入の挙動をより正確に制御し、構文解析の誤りを防ぐことを目的としています。これは、言語仕様の細部をコンパイラが正確に解釈し、開発者が意図しない構文エラーに遭遇するのを防ぐために不可欠な改善です。

これらの修正は、Go言語がより使いやすく、予測可能で、堅牢な言語として成長していくための基礎を固める上で重要な役割を果たしました。

## 前提知識の解説

### Go言語のコンパイラ (`gc`)

Go言語の公式コンパイラは、初期には `gc` (Go Compiler) と呼ばれていました。これは、C言語で書かれたコンパイラであり、Go言語のソースコードを機械語に変換する役割を担っていました。`gc` は、字句解析、構文解析、意味解析、最適化、コード生成といったコンパイラの一般的なフェーズを実行します。

*   **字句解析 (Lexical Analysis)**: ソースコードをトークン（単語のようなもの）の並びに分解するプロセス。例えば、`日本語 := 1;` というコードは、`日本語`（識別子）、`:=`（代入演算子）、`1`（数値リテラル）、`;`（セミコロン）といったトークンに分解されます。
*   **構文解析 (Syntactic Analysis)**: 字句解析で生成されたトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST）を構築するプロセス。`go.y` ファイルは、この構文解析器の文法規則を定義するために使用されるYacc（Yet Another Compiler Compiler）形式のファイルです。

### Yacc/Bison (`.y` ファイル)

`go.y` のような `.y` ファイルは、Yacc（またはGNU Bison）というツールで使用される文法定義ファイルです。Yaccは、文法規則に基づいて構文解析器を自動生成するツールであり、プログラマはBNF（Backus-Naur Form）に似た形式で言語の文法を記述します。

*   **`go.y`**: Go言語の構文規則が記述されており、GoコンパイラがGoのソースコードをどのように解釈するかを定義しています。

### 字句解析器 (`lex.c`)

`lex.c` のようなファイルは、字句解析器（lexerまたはscanner）の実装を含んでいます。字句解析器は、ソースコードの文字ストリームを読み込み、意味のあるトークンに分割します。

*   **`lex.c`**: Goコンパイラの字句解析器の実装が含まれており、ソースコードから識別子、キーワード、リテラルなどを認識するロジックが記述されています。

### Go言語の識別子

Go言語の識別子（変数名、関数名など）は、文字で始まり、その後に文字または数字が続く必要があります。初期のGo言語では、Unicode文字のどの範囲を「文字」として許容するかが議論の対象でした。このコミット以前は、一部の非ASCII文字が誤って識別子として許可されていた可能性があります。

### Go言語の生文字列リテラル (Raw String Literals)

Go言語には、バッククォート `` ` `` で囲まれた生文字列リテラルがあります。このリテラル内では、バックスラッシュ `\` によるエスケープシーケンス（例: `\n` や `\t`）は解釈されず、記述された文字がそのまま文字列の内容となります。複数行にわたるテキストを扱う際に非常に便利です。

### Go言語の自動セミコロン挿入 (Automatic Semicolon Insertion, ASI)

Go言語では、行末にセミコロンを明示的に記述する必要がない場合があります。これは、コンパイラが特定のルールに基づいて自動的にセミコロンを挿入するためです。このメカニズムはASIと呼ばれ、コードの記述を簡潔にする一方で、そのルールを正確に理解していないと予期せぬ構文エラーを引き起こすこともあります。`yyoptsemi` 関数は、このASIのロジックの一部を担っています。

## 技術的詳細

### `src/cmd/gc/go.y` の変更

`go.y` ファイルにおける `varoptsemi` ルールの変更は、Goの自動セミコロン挿入（ASI）の挙動をより厳密に制御するためのものです。

変更前:
```yacc
varoptsemi:
	{
		yyoptsemi('=');
	}
```

変更後:
```yacc
varoptsemi:
	{
		if(yylast == LSEMIBRACE)
			yyoptsemi('=');
	}
```

この変更は、`varoptsemi` ルールが適用される際に、`yyoptsemi('=')` が常に呼び出されるのではなく、直前のトークンが `LSEMIBRACE`（おそらく自動挿入されたセミコロン、またはブロックの終わりを示すトークン）である場合にのみ呼び出されるように条件を追加しています。これにより、特定の構文コンテキストでの不要な、あるいは誤ったセミコロンの挿入を防ぎ、パーサーの正確性を向上させています。これは、GoのASIが、改行だけでなく、特定のトークンの後にのみ発動するという仕様に合致させるための調整と考えられます。

### `src/cmd/gc/lex.c` の変更 (bug163 関連)

`lex.c` ファイルにおける `talph` 関数内の変更は、識別子として有効な文字の定義を厳密化しています。

変更前:
```c
					if(isfrog(rune)) {
					 	yyerror("illegal character 0x%ux", rune);
					 	goto l0;
					 }
```

変更後:
```c
					if(isfrog(rune)) {
						yyerror("illegal character 0x%ux", rune);
						goto l0;
					}
					// 0xb7 · is used for internal names
					if(!isalpharune(c) && !isdigitrune(c) && c != 0xb7)
						yyerror("invalid identifier character 0x%ux", rune);

```

この変更により、`isfrog(rune)`（おそらくGoの予約語や特殊文字など、完全に不正な文字を検出する関数）によるチェックに加えて、以下の条件が追加されました。

*   `!isalpharune(c)`: アルファベットではない
*   `!isdigitrune(c)`: 数字ではない
*   `c != 0xb7`: `0xb7` (Unicodeの `·` (Middle Dot)) ではない

この3つの条件がすべて真である場合、つまり、文字がアルファベットでも数字でもなく、かつ `·` でもない場合に、「無効な識別子文字」としてエラー (`yyerror`) が報告されます。コメントにある `0xb7 · is used for internal names` は、Goコンパイラ内部で生成される識別子に `·` が使用されることがあるため、この文字は特別に許可されていることを示唆しています。

この修正は、`bug163.go` のテストケースが示すように、日本語の表意文字のような非ASCII文字が識別子として使用された場合にエラーを発生させることを目的としています。Go言語の識別子は、ASCIIの英数字とアンダースコア `_` で構成されるべきであり、この変更はその規則をコンパイラレベルで強制するものです。

## コアとなるコードの解説

### `src/cmd/gc/go.y` の `varoptsemi` ルール

この変更は、Go言語の構文解析器における自動セミコロン挿入（ASI）のロジックを微調整するものです。`yyoptsemi('=')` は、特定の状況下でセミコロンを挿入する関数ですが、変更後は `if(yylast == LSEMIBRACE)` という条件が追加されました。これは、「直前のトークンが `LSEMIBRACE`（おそらくブロックの終わりを示す中括弧 `}` や、既に自動挿入されたセミコロン）である場合にのみ、セミコロン挿入のロジックを適用する」という意味になります。これにより、`varoptsemi` が関与する文脈で、より正確かつ意図された通りにセミコロンが挿入されるようになり、構文解析の堅牢性が向上します。例えば、`var x int = 1` のような宣言の後に、誤ってセミコロンが挿入されるのを防ぐ、あるいは特定のブロック構造の後にのみ挿入を許可するといった制御が考えられます。

### `src/cmd/gc/lex.c` の `talph` 関数

`talph` 関数は、Goコンパイラの字句解析器において、識別子を構成する文字を処理する部分です。この変更は、識別子として許可される文字の範囲を厳密に定義し直しています。

1.  **`isfrog(rune)` チェック**: 既存の `isfrog(rune)` チェックは、Go言語の文法上、完全に不正な文字（例えば、制御文字など）を検出するためのものです。これが検出された場合は、`illegal character` エラーとして処理され、字句解析が中断されます。

2.  **新しい識別子文字チェック**: 新たに追加された `if(!isalpharune(c) && !isdigitrune(c) && c != 0xb7)` という条件は、より具体的な識別子文字のルールを適用します。
    *   `!isalpharune(c)`: 現在の文字 `c` がアルファベットではない。
    *   `!isdigitrune(c)`: 現在の文字 `c` が数字ではない。
    *   `c != 0xb7`: 現在の文字 `c` が Unicode の `·` (Middle Dot) ではない。
    これらの条件がすべて真である場合、つまり、文字がアルファベットでも数字でもなく、かつ `·` でもない場合に、`invalid identifier character` エラーが報告されます。
    `0xb7` (Middle Dot) が特別に許可されているのは、コメントにもあるように、Goコンパイラが内部的に生成するシンボル名などでこの文字を使用するためです。これは、ユーザーが直接記述する識別子とは異なる、コンパイラ内部の命名規則に対応するための例外処理です。

この変更により、`bug163.go` のテストケースが示すように、日本語の表意文字のような非ASCII文字は、`isalpharune` や `isdigitrune` の条件を満たさないため、`invalid identifier character` エラーとして扱われるようになります。これは、Go言語の識別子がASCII英数字とアンダースコアに限定されるという、より明確なルールをコンパイラが強制するようになったことを意味します。

### `src/pkg/http/request.go` の変数宣言

この変更は、`var er, ew os.Error` という変数宣言の行末にセミコロン `;` を追加するものです。Go言語では通常、行末のセミコロンは自動挿入されるため省略可能ですが、この特定のケースでは、初期のコンパイラがこの構文を正しく解釈できなかったか、あるいは特定の文脈でセミコロンの明示的な記述が必要とされていた可能性があります。これは、コンパイラの初期のバグ修正、または言語仕様の解釈の調整による、非常に軽微な構文修正です。

*   **bug166**: 詳細不明だが、テストケースの移動と`golden.out`からの削除から、以前は失敗していたテストが修正されたことを示唆。

具体的な変更点としては、Goコンパイラの字句解析器が識別子として許容する文字の範囲を厳密化し、日本語文字のような非ASCII文字を識別子として許可しないように修正されました。また、生文字列リテラル内で改行が許可されるようになり、HTTPパッケージ内の構文エラーも修正されています。

## 変更の背景

Go言語は設計当初から、シンプルさと明確さを重視していました。このコミットが行われた2009年6月は、Go言語が一般に公開される直前の非常に初期の段階であり、言語仕様やコンパイラの実装が活発に開発・調整されていました。

1.  **識別子の文字セットの厳密化 (bug163)**: 多くのプログラミング言語では、識別子に使用できる文字に制限があります。Go言語も例外ではなく、特に初期の段階では、Unicode文字のどの範囲を識別子として許可するかについて試行錯誤がありました。このバグ修正は、識別子の定義をより厳密にし、予期せぬ挙動や移植性の問題を避けるために、非ASCII文字（特に日本語の表意文字）を識別子として認めない方針を明確にしたものと考えられます。これは、コンパイラの堅牢性を高め、言語の安定した基盤を築く上で重要なステップでした。

2.  **生文字列リテラルの改行許可 (bug164)**: Goの生文字列リテラル（バッククォート `` ` `` で囲まれた文字列）は、エスケープシーケンスを解釈せず、記述された通りの内容を文字列として扱う機能です。これは正規表現やHTML、JSONなどの複数行にわたるテキストをコード内に埋め込む際に非常に便利です。初期の実装では、この生文字列リテラル内に改行文字を含めることが仕様上許されていなかったか、あるいはコンパイラが正しく処理できていなかった可能性があります。この修正により、生文字列リテラルがその本来の意図通り、複数行のテキストをそのまま表現できるようになり、言語の表現力が向上しました。

3.  **コンパイラの堅牢性向上 (bug166, `go.y` の変更)**: `go.y` はGoコンパイラの構文解析器の定義ファイルであり、`yyoptsemi` はGoの自動セミコロン挿入（Automatic Semicolon Insertion, ASI）メカニズムに関連する関数です。この変更は、特定の文脈でのセミコロン挿入の挙動をより正確に制御し、構文解析の誤りを防ぐことを目的としています。これは、言語仕様の細部をコンパイラが正確に解釈し、開発者が意図しない構文エラーに遭遇するのを防ぐために不可欠な改善です。

これらの修正は、Go言語がより使いやすく、予測可能で、堅牢な言語として成長していくための基礎を固める上で重要な役割を果たしました。

## 前提知識の解説

### Go言語のコンパイラ (`gc`)

Go言語の公式コンパイラは、初期には `gc` (Go Compiler) と呼ばれていました。これは、C言語で書かれたコンパイラであり、Go言語のソースコードを機械語に変換する役割を担っていました。`gc` は、字句解析、構文解析、意味解析、最適化、コード生成といったコンパイラの一般的なフェーズを実行します。

*   **字句解析 (Lexical Analysis)**: ソースコードをトークン（単語のようなもの）の並びに分解するプロセス。例えば、`日本語 := 1;` というコードは、`日本語`（識別子）、`:=`（代入演算子）、`1`（数値リテラル）、`;`（セミコロン）といったトークンに分解されます。
*   **構文解析 (Syntactic Analysis)**: 字句解析で生成されたトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST）を構築するプロセス。`go.y` ファイルは、この構文解析器の文法規則を定義するために使用されるYacc（Yet Another Compiler Compiler）形式のファイルです。

### Yacc/Bison (`.y` ファイル)

`go.y` のような `.y` ファイルは、Yacc（またはGNU Bison）というツールで使用される文法定義ファイルです。Yaccは、文法規則に基づいて構文解析器を自動生成するツールであり、プログラマはBNF（Backus-Naur Form）に似た形式で言語の文法を記述します。

*   **`go.y`**: Go言語の構文規則が記述されており、GoコンパイラがGoのソースコードをどのように解釈するかを定義しています。

### 字句解析器 (`lex.c`)

`lex.c` のようなファイルは、字句解析器（lexerまたはscanner）の実装を含んでいます。字句解析器は、ソースコードの文字ストリームを読み込み、意味のあるトークンに分割します。

*   **`lex.c`**: Goコンパイラの字句解析器の実装が含まれており、ソースコードから識別子、キーワード、リテラルなどを認識するロジックが記述されています。

### Go言語の識別子

Go言語の識別子（変数名、関数名など）は、文字で始まり、その後に文字または数字が続く必要があります。初期のGo言語では、Unicode文字のどの範囲を「文字」として許容するかが議論の対象でした。このコミット以前は、一部の非ASCII文字が誤って識別子として許可されていた可能性があります。

### Go言語の生文字列リテラル (Raw String Literals)

Go言語には、バッククォート `` ` `` で囲まれた生文字列リテラルがあります。このリテラル内では、バックスラッシュ `\` によるエスケープシーケンス（例: `\n` や `\t`）は解釈されず、記述された文字がそのまま文字列の内容となります。複数行にわたるテキストを扱う際に非常に便利です。

### Go言語の自動セミコロン挿入 (Automatic Semicolon Insertion, ASI)

Go言語では、行末にセミコロンを明示的に記述する必要がない場合があります。これは、コンパイラが特定のルールに基づいて自動的にセミコロンを挿入するためです。このメカニズムはASIと呼ばれ、コードの記述を簡潔にする一方で、そのルールを正確に理解していないと予期せぬ構文エラーを引き起こすこともあります。`yyoptsemi` 関数は、このASIのロジックの一部を担っています。

## 技術的詳細

### `src/cmd/gc/go.y` の変更

`go.y` ファイルにおける `varoptsemi` ルールの変更は、Goの自動セミコロン挿入（ASI）の挙動をより厳密に制御するためのものです。

変更前:
```yacc
varoptsemi:
	{
		yyoptsemi('=');
	}
```

変更後:
```yacc
varoptsemi:
	{
		if(yylast == LSEMIBRACE)
			yyoptsemi('=');
	}
```

この変更は、`varoptsemi` ルールが適用される際に、`yyoptsemi('=')` が常に呼び出されるのではなく、直前のトークンが `LSEMIBRACE`（おそらく自動挿入されたセミコロン、またはブロックの終わりを示すトークン）である場合にのみ呼び出されるように条件を追加しています。これにより、特定の構文コンテキストでの不要な、あるいは誤ったセミコロンの挿入を防ぎ、パーサーの正確性を向上させています。これは、GoのASIが、改行だけでなく、特定のトークンの後にのみ発動するという仕様に合致させるための調整と考えられます。

### `src/cmd/gc/lex.c` の変更 (bug163 関連)

`lex.c` ファイルにおける `talph` 関数内の変更は、識別子として有効な文字の定義を厳密化しています。

変更前:
```c
					if(isfrog(rune)) {
					 	yyerror("illegal character 0x%ux", rune);
					 	goto l0;
					 }
```

変更後:
```c
					if(isfrog(rune)) {
						yyerror("illegal character 0x%ux", rune);
						goto l0;
					}
					// 0xb7 · is used for internal names
					if(!isalpharune(c) && !isdigitrune(c) && c != 0xb7)
						yyerror("invalid identifier character 0x%ux", rune);
					break;
```

この変更により、`isfrog(rune)`（おそらくGoの予約語や特殊文字など、完全に不正な文字を検出する関数）によるチェックに加えて、以下の条件が追加されました。

*   `!isalpharune(c)`: アルファベットではない
*   `!isdigitrune(c)`: 数字ではない
*   `c != 0xb7`: `0xb7` (Unicodeの `·` (Middle Dot)) ではない
これらの条件がすべて真である場合、つまり、文字がアルファベットでも数字でもなく、かつ `·` でもない場合に、「無効な識別子文字」としてエラー (`yyerror`) が報告されます。コメントにある `0xb7 · is used for internal names` は、Goコンパイラ内部で生成される識別子に `·` が使用されることがあるため、この文字は特別に許可されていることを示唆しています。

この修正は、`bug163.go` のテストケースが示すように、日本語の表意文字のような非ASCII文字は、`isalpharune` や `isdigitrune` の条件を満たさないため、`invalid identifier character` エラーとして扱われるようになります。これは、Go言語の識別子がASCII英数字とアンダースコアに限定されるという、より明確なルールをコンパイラが強制するようになったことを意味します。

### `src/pkg/http/request.go` の変更

## コアとなるコードの解説

### `src/cmd/gc/go.y` の `varoptsemi` ルール

この変更は、Go言語の構文解析器における自動セミコロン挿入（ASI）のロジックを微調整するものです。`yyoptsemi('=')` は、特定の状況下でセミコロンを挿入する関数ですが、変更後は `if(yylast == LSEMIBRACE)` という条件が追加されました。これは、「直前のトークンが `LSEMIBRACE`（おそらくブロックの終わりを示す中括弧 `}` や、既に自動挿入されたセミコロン）である場合にのみ、セミコロン挿入のロジックを適用する」という意味になります。これにより、`varoptsemi` が関与する文脈で、より正確かつ意図された通りにセミコロンが挿入されるようになり、構文解析の堅牢性が向上します。例えば、`var x int = 1` のような宣言の後に、誤ってセミコロンが挿入されるのを防ぐ、あるいは特定のブロック構造の後にのみ挿入を許可するといった制御が考えられます。

### `src/cmd/gc/lex.c` の `talph` 関数

`talph` 関数は、Goコンパイラの字句解析器において、識別子を構成する文字を処理する部分です。この変更は、識別子として許可される文字の範囲を厳密に定義し直しています。

1.  **`isfrog(rune)` チェック**: 既存の `isfrog(rune)` チェックは、Go言語の文法上、完全に不正な文字（例えば、制御文字など）を検出するためのものです。これが検出された場合は、`illegal character` エラーとして処理され、字句解析が中断されます。

2.  **新しい識別子文字チェック**: 新たに追加された `if(!isalpharune(c) && !isdigitrune(c) && c != 0xb7)` という条件は、より具体的な識別子文字のルールを適用します。
    *   `!isalpharune(c)`: 現在の文字 `c` がアルファベットではない。
    *   `!isdigitrune(c)`: 現在の文字 `c` が数字ではない。
    *   `c != 0xb7`: 現在の文字 `c` が Unicode の `·` (Middle Dot) ではない。
    これらの条件がすべて真である場合、つまり、文字がアルファベットでも数字でもなく、かつ `·` でもない場合に、`invalid identifier character` エラーが報告されます。
    `0xb7` (Middle Dot) が特別に許可されているのは、コメントにもあるように、Goコンパイラが内部的に生成するシンボル名などでこの文字を使用するためです。これは、ユーザーが直接記述する識別子とは異なる、コンパイラ内部の命名規則に対応するための例外処理です。

この変更により、`bug163.go` のテストケースが示すように、日本語の表意文字のような非ASCII文字は、`isalpharune` や `isdigitrune` の条件を満たさないため、`invalid identifier character` エラーとして扱われるようになります。これは、Go言語の識別子がASCII英数字とアンダースコアに限定されるという、より明確なルールをコンパイラが強制するようになったことを意味します。

### `src/pkg/http/request.go` の変数宣言

この変更は、`var er, ew os.Error` という変数宣言の行末にセミコロン `;` を追加するものです。Go言語では通常、行末のセミコロンは自動挿入されるため省略可能ですが、この特定のケースでは、初期のコンパイラがこの構文を正しく解釈できなかったか、あるいは特定の文脈でセミコロンの明示的な記述が必要とされていた可能性があります。これは、コンパイラの初期のバグ修正、または言語仕様の解釈の調整による、非常に軽微な構文修正です。

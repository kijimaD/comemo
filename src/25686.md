# [インデックス 25686] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージに、2つの新しいTLS (Transport Layer Security) 暗号スイート `TLS_RSA_WITH_AES_128_GCM_SHA256` と `TLS_RSA_WITH_AES_256_GCM_SHA384` を追加するものです。これにより、GoのTLS実装がより現代的でセキュアな暗号化方式をサポートし、TLS 1.2プロトコルにおけるGCM (Galois/Counter Mode) モードのAES (Advanced Encryption Standard) 暗号の利用を促進します。

## 元コミット内容

このコミットは、Goの `crypto/tls` パッケージに以下の2つのTLS 1.2暗号スイートを追加します。

- `TLS_RSA_WITH_AES_128_GCM_SHA256`
- `TLS_RSA_WITH_AES_256_GCM_SHA384`

これらの暗号スイートは、RSA鍵交換、AES-GCMによる認証付き暗号化、およびSHA-256またはSHA-384によるハッシュ関数を使用します。また、関連するテストデータファイル (`src/crypto/tls/testdata/Client-TLSv12-AES128-GCM-SHA256` および `src/crypto/tls/testdata/Client-TLSv12-AES256-GCM-SHA384`) が新規追加され、既存のテストデータファイルも更新されています。これは、新しい暗号スイートがTLSハンドシェイクで正しく機能することを確認するためのものです。

## 変更の背景

この変更の背景には、TLSプロトコルにおけるセキュリティとパフォーマンスの進化があります。特に、以下の点が挙げられます。

1.  **AEAD (Authenticated Encryption with Associated Data) 暗号の推奨**: 以前のTLSバージョンで広く使われていたCBC (Cipher Block Chaining) モードの暗号スイートは、Padding Oracle Attackなどの脆弱性の影響を受けやすいことが知られていました。これに対し、GCMモードのようなAEAD暗号は、暗号化と認証を同時に行うことで、より強力なセキュリティ保証を提供します。TLS 1.2ではAEAD暗号が導入され、RFC 5288でAES-GCMが定義されました。
2.  **RC4の非推奨化**: RC4ストリーム暗号も、その設計上の欠陥からセキュリティ上の懸念が指摘され、RFC 7465によってTLSでの使用が非推奨とされました。
3.  **SHA-256/SHA-384の利用**: 以前のTLS暗号スイートではSHA-1が広く使われていましたが、SHA-1も衝突攻撃の可能性が指摘され、より強力なSHA-256やSHA-384への移行が進められていました。
4.  **相互運用性の向上**: これらの新しい暗号スイートを追加することで、GoのTLS実装が他のモダンなTLS実装（Webブラウザやサーバーなど）との相互運用性を高め、よりセキュアな通信を確立できるようになります。
5.  **Issue #9894の解決**: このコミットは、GoのIssueトラッカーで報告されていた「TLS_RSA_WITH_AES_128_GCM_SHA256とTLS_RSA_WITH_AES_256_GCM_SHA384暗号スイートの追加」という要望 (Fixes #9894) に対応するものです。

## 前提知識の解説

このコミットを理解するためには、以下のTLSおよび暗号技術に関する基本的な知識が必要です。

### 1. TLS (Transport Layer Security)
TLSは、インターネット上で安全な通信を行うためのプロトコルです。クライアントとサーバー間で、データの暗号化、認証、およびデータ整合性の保護を提供します。TLSハンドシェイクと呼ばれるプロセスを通じて、通信に使用する暗号スイート（鍵交換、暗号化、ハッシュアルゴリズムの組み合わせ）を決定します。

### 2. 暗号スイート (Cipher Suite)
暗号スイートは、TLS通信で使用される一連のアルゴリズムの組み合わせを定義します。通常、以下の要素から構成されます。

-   **鍵交換アルゴリズム (Key Exchange Algorithm)**: クライアントとサーバーが共有秘密鍵を安全に確立する方法を決定します。例: RSA, ECDHE (Elliptic Curve Diffie-Hellman Ephemeral)。
-   **認証アルゴリズム (Authentication Algorithm)**: サーバー（およびオプションでクライアント）の身元を確認するために使用されます。通常、デジタル署名アルゴリズム（例: RSA, ECDSA）が使われます。
-   **バルク暗号化アルゴリズム (Bulk Encryption Algorithm)**: 実際のデータを暗号化するために使用される対称鍵暗号アルゴリズムです。例: AES (Advanced Encryption Standard), 3DES (Triple DES)。
-   **メッセージ認証コード (MAC) または認証付き暗号 (AEAD) アルゴリズム**: データの改ざんを検出するために使用されます。MACは暗号化とは別に認証を提供しますが、AEADは暗号化と認証を一体化して提供します。例: SHA (Secure Hash Algorithm) を用いたHMAC, GCM (Galois/Counter Mode)。

このコミットで追加される暗号スイートは、`TLS_RSA_WITH_AES_128_GCM_SHA256` のように命名規則に従っています。
-   `TLS`: TLSプロトコルで使用されることを示します。
-   `RSA`: 鍵交換および認証にRSAアルゴリズムを使用することを示します。
-   `WITH_AES_128_GCM`: バルク暗号化にAESを128ビットキー長でGCMモードで使用することを示します。
-   `SHA256`: メッセージ認証コード（または擬似乱数関数P_PRF）にSHA-256ハッシュ関数を使用することを示します。

### 3. AES (Advanced Encryption Standard)
AESは、現在最も広く使用されている対称鍵暗号アルゴリズムの一つです。128ビット、192ビット、256ビットの鍵長をサポートします。

### 4. GCM (Galois/Counter Mode)
GCMは、AESと組み合わせて使用される認証付き暗号 (AEAD) モードです。データの機密性（暗号化）と完全性・認証（改ざん検出）を同時に提供します。CBCモードと比較して、並列処理が可能でパフォーマンスが高く、Padding Oracle Attackなどの脆弱性に対して耐性があります。

### 5. SHA-256 / SHA-384 (Secure Hash Algorithm)
SHA-2は、NISTによって開発されたハッシュ関数ファミリーです。SHA-256は256ビットのハッシュ値を生成し、SHA-384は384ビットのハッシュ値を生成します。これらは、データの整合性チェックやデジタル署名、鍵導出関数などに使用されます。SHA-1よりも強力なセキュリティを提供します。

### 6. TLS 1.2
TLS 1.2は、2008年にRFC 5246として定義されたTLSプロトコルのバージョンです。以前のバージョン（TLS 1.0, 1.1）と比較して、より強力なハッシュ関数（SHA-256など）とAEAD暗号（AES-GCMなど）のサポートが強化されました。現代のインターネット通信では、TLS 1.2以降のバージョンが推奨されています。

## 技術的詳細

このコミットで追加される `TLS_RSA_WITH_AES_128_GCM_SHA256` と `TLS_RSA_WITH_AES_256_GCM_SHA384` は、TLS 1.2プロトコルに特化した暗号スイートです。

-   **鍵交換/認証**: `RSA` を使用します。これは、サーバーの公開鍵証明書に含まれるRSA公開鍵を用いて、プリマスターシークレットを暗号化し、クライアントからサーバーへ送信する方式です。サーバーは対応する秘密鍵で復号します。また、サーバー認証にもRSA署名が使用されます。
-   **認証付き暗号 (AEAD)**: `AES_128_GCM` または `AES_256_GCM` を使用します。
    -   **AES**: 対称鍵暗号アルゴリズム。128ビットまたは256ビットの鍵長でデータを暗号化します。
    -   **GCM (Galois/Counter Mode)**: AESの動作モードの一つで、認証付き暗号を提供します。GCMはカウンタモードとGaloisフィールド乗算を組み合わせることで、高速な暗号化と強力な認証を両立します。各レコードにはユニークなNonce (Number used once) が使用され、これが再利用されるとセキュリティが著しく低下するため、Nonceの管理が非常に重要です。
-   **ハッシュ関数**:
    -   `SHA256`: `TLS_RSA_WITH_AES_128_GCM_SHA256` では、TLSの擬似乱数関数 (PRF) やハンドシェイクメッセージのハッシュ計算にSHA-256が使用されます。
    -   `SHA384`: `TLS_RSA_WITH_AES_256_GCM_SHA384` では、同様にSHA-384が使用されます。SHA-384はSHA-256よりも長いハッシュ値を生成し、より高いセキュリティレベルを提供します。

これらの暗号スイートは、TLS 1.2の仕様 (RFC 5246) およびAES-GCMの仕様 (RFC 5288) に準拠しています。特に、GCMモードの採用は、TLS通信のセキュリティを大幅に向上させる重要な要素です。GCMは、データの機密性だけでなく、完全性（データが改ざんされていないこと）と認証（送信者が正当であること）を同時に保証するため、中間者攻撃などに対する耐性が高まります。

## コアとなるコードの変更箇所

主要な変更は `src/crypto/tls/cipher_suites.go` ファイルにあります。

1.  `cipherSuites` 変数に新しい `cipherSuite` 構造体のエントリが追加されています。
    ```go
    // src/crypto/tls/cipher_suites.go
    // ...
    var cipherSuites = []*cipherSuite{
        // ... 既存のスイート
        {TLS_ECDHE_ECDSA_WITH_AES_256_CBC_SHA, 32, 20, 16, ecdheECDSAKA, suiteECDHE | suiteECDSA, cipherAES, macSHA1, nil},
        {TLS_RSA_WITH_AES_128_GCM_SHA256, 16, 0, 4, rsaKA, suiteTLS12, nil, nil, aeadAESGCM}, // 追加
        {TLS_RSA_WITH_AES_256_GCM_SHA384, 32, 0, 4, rsaKA, suiteTLS12 | suiteSHA384, nil, nil, aeadAESGCM}, // 追加
        {TLS_RSA_WITH_RC4_128_SHA, 16, 20, 0, rsaKA, suiteDefaultOff, cipherRC4, macSHA1, nil},
        // ...
    }
    // ...
    ```
    -   `TLS_RSA_WITH_AES_128_GCM_SHA256`:
        -   `keyLen`: 16 (AES-128の鍵長)
        -   `macLen`: 0 (GCMはAEADなので別途MACは不要)
        -   `ivLen`: 4 (GCMの固定IV部分の長さ)
        -   `ka`: `rsaKA` (鍵交換/認証はRSA)
        -   `flags`: `suiteTLS12` (TLS 1.2専用)
        -   `cipher`: `nil` (AEADなので別途cipherは指定しない)
        -   `mac`: `nil` (AEADなので別途MACは指定しない)
        -   `aead`: `aeadAESGCM` (AEADとしてAES-GCMを使用)
    -   `TLS_RSA_WITH_AES_256_GCM_SHA384`:
        -   `keyLen`: 32 (AES-256の鍵長)
        -   `macLen`: 0
        -   `ivLen`: 4
        -   `ka`: `rsaKA`
        -   `flags`: `suiteTLS12 | suiteSHA384` (TLS 1.2専用で、SHA-384を使用)
        -   `cipher`: `nil`
        -   `mac`: `nil`
        -   `aead`: `aeadAESGCM`

2.  `const` ブロックに新しい暗号スイートの定数 (`uint16` 型の識別子) が追加されています。

## コアとなるコードの解説

`cipher_suites.go` における `cipherSuite` 構造体の定義と、新しいエントリの追加は、GoのTLS実装がどのように暗号スイートを管理しているかを示しています。

`cipherSuite` 構造体は、各暗号スイートの特性を定義します。
-   `id`: 暗号スイートの一意な識別子 (RFCで定義された `uint16` 値)。
-   `keyLen`: 対称鍵暗号の鍵長（バイト単位）。
-   `macLen`: MACの長さ（バイト単位）。AEAD暗号の場合は0。
-   `ivLen`: IV (Initialization Vector) またはNonceの長さ（バイト単位）。GCMの場合は固定の4バイト。
-   `ka`: 鍵交換アルゴリズムを識別するフラグ。
-   `flags`: その他の特性を示すフラグ（例: `suiteTLS12` はTLS 1.2専用であることを示す）。
-   `cipher`: 対称鍵暗号アルゴリズムを識別するフラグ。AEADの場合は `nil`。
-   `mac`: MACアルゴリズムを識別するフラグ。AEADの場合は `nil`。
-   `aead`: AEADアルゴリズムを識別するフラグ。

新しい `TLS_RSA_WITH_AES_128_GCM_SHA256` と `TLS_RSA_WITH_AES_256_GCM_SHA384` のエントリでは、`macLen` と `cipher` および `mac` が `nil` に設定され、代わりに `aeadAESGCM` が指定されています。これは、これらのスイートがAEAD暗号であるAES-GCMを使用しており、従来のMACと暗号化を分離した方式とは異なることを明確に示しています。

`flags` に `suiteTLS12` が含まれているのは、これらのGCMベースの暗号スイートがTLS 1.2以降で導入された機能であるためです。また、`TLS_RSA_WITH_AES_256_GCM_SHA384` には `suiteSHA384` フラグも追加されており、これはPRFにSHA-384を使用することを示唆しています。

`handshake_client_test.go` のテストコードは、GoのTLSクライアントがOpenSSLサーバーと新しい暗号スイートで正常にハンドシェイクできることを検証します。これは、GoのTLS実装が業界標準のツールと相互運用可能であることを保証するために重要です。

`testdata` ディレクトリ内のバイナリダンプの変更は、TLSハンドシェイクメッセージの構造が新しい暗号スイートの追加によってどのように変化するかを示しています。これらのダンプは、プロトコルの実装が仕様に厳密に従っていることを確認するためのリファレンスとして機能します。

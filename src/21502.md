# [インデックス 21502] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるスライスおよび配列のゼロクリア処理の最適化に関するものです。特定の形式のループを、より高速な`memclr`ランタイム関数呼び出しに置き換えることで、パフォーマンスの向上を図っています。

## 変更の背景

Go言語では、スライスや配列の要素をゼロ値で初期化する（クリアする）操作は頻繁に行われます。例えば、`make([]byte, N)`で作成されたバイトスライスはデフォルトでゼロ初期化されますが、既存のスライスを再利用して内容をクリアしたい場合などには、明示的にループを使って各要素にゼロを代入するコードが書かれることがあります。

従来のGoコンパイラでは、このようなループは個々の要素への代入操作としてコンパイルされていました。しかし、メモリ領域全体をゼロで埋める操作は、CPUの特定の命令（例: `rep stos` on x86）や最適化されたライブラリ関数（例: `memset`）を利用することで、非常に高速に実行できます。Goランタイムには、このような低レベルのメモリ操作を行うための`memclr`関数が既に存在していました。

このコミットの背景には、Goプログラム内で頻繁に現れる「スライス/配列のゼロクリアループ」を検出し、それを手動で書かれたループよりもはるかに効率的な`memclr`関数呼び出しに自動的に置き換えることで、Goプログラム全体のパフォーマンスを向上させるという目的がありました。特に、バイトスライスのような連続したメモリ領域を扱う場合に、この最適化は大きな効果を発揮します。コミットメッセージに示されているベンチマーク結果は、この最適化が特に大きなサイズのデータに対して劇的な速度向上をもたらすことを明確に示しています。

また、この変更はGoのIssue #5373に関連しています。このIssueは、`for range`ループにおけるインデックス変数の挙動と、最適化がその挙動に影響を与えないことの保証に関するものでした。このコミットは、最適化を適用する際に、ループの副作用（特にインデックス変数の最終値や、スライス/配列の評価における副作用）が正しく扱われることを保証する必要があることを示唆しています。

## 前提知識の解説

### Goコンパイラ (`cmd/gc`)

Go言語の公式コンパイラは`gc`と呼ばれ、`cmd/gc`ディレクトリにそのソースコードがあります。`gc`は、Goのソースコードを中間表現に変換し、様々な最適化を適用した後、最終的な機械語コードを生成します。このコミットは、`gc`の最適化フェーズ、特に`range`ループの処理を担当する部分に手を入れています。

### `for range` ループ

Go言語の`for range`ループは、配列、スライス、文字列、マップ、チャネルをイテレートするための構文です。
`for i := range a { ... }` の形式では、`i`はインデックス、`a`はイテレートされるコレクションです。
このコミットが対象とするのは、`for i := range a { a[i] = zero }` のような、コレクションの各要素をゼロ値でクリアするパターンです。

### `memclr` 関数

`memclr`はGoランタイム内部で提供される低レベルのメモリ操作関数の一つです。指定されたメモリ領域を指定された長さだけゼロで埋める役割を持ちます。これはC言語の`memset(ptr, 0, len)`に相当し、通常はアセンブリ言語で実装されるなど、非常に高速に動作するように最適化されています。Goのガベージコレクタやメモリ管理ルーチンが内部的に利用するほか、今回のようにコンパイラが特定のコードパターンを最適化するために利用することもあります。

### 副作用 (Side Effects)

プログラミングにおいて「副作用」とは、関数や式の評価が、その戻り値以外にプログラムの状態を変更する効果を指します。例えば、グローバル変数の変更、I/O操作、ポインタのデリファレンスなどが副作用にあたります。
このコミットでは、`for i := range a { a[i] = zero }` の `a` の評価に副作用がないことが最適化の条件となっています。もし `a` の評価に副作用がある場合（例: `a` が関数呼び出しの結果であり、その関数が何らかの状態を変更する場合）、ループを`memclr`に置き換えることはできません。なぜなら、ループが毎回 `a` を評価するのに対し、`memclr`は一度しか評価しないため、副作用の発生回数が変わってしまうからです。

### Issue #5373

GoのIssue #5373は、`for range`ループにおけるインデックス変数の挙動に関するバグ報告でした。具体的には、`for i := range s` のようなループで、`s`が空の場合に`i`が初期値のまま変更されないという挙動が、一部の最適化によって変わってしまう可能性が指摘されていました。このコミットは、`memclr`最適化を導入する際に、このようなインデックス変数の挙動や、ループ本体およびレンジ式の評価における副作用が正しく保持されることを保証するためのテストを追加しています。

## 技術的詳細

この最適化は、Goコンパイラの`cmd/gc`がコードを抽象構文木（AST）として処理する段階で行われます。具体的には、`src/cmd/gc/range.c`内の`walkrange`関数が、`for range`ループのASTを走査する際に、特定のパターンを検出します。

検出されるパターンは以下の条件を満たすループです。

1.  **対象が配列またはスライスであること**: `for i := range a` の `a` が配列またはスライスである必要があります。
2.  **ループ本体が単一の代入文であること**: `a[i] = zero` のような形式であること。
3.  **代入の右辺がゼロ値であること**: `zero` は、その型のゼロ値（例: `int`なら`0`、`byte`なら`0`、ポインタなら`nil`）である必要があります。
4.  **インデックスがループ変数であること**: `a[i]` の `i` が `for range` のインデックス変数であること。
5.  **スライス/配列 `a` の評価に副作用がないこと**: `samesafeexpr`関数によってチェックされます。これは、`a`が単純な変数参照であり、その評価がプログラムの状態を変化させないことを保証します。
6.  **デバッグフラグや競合検出フラグが有効でないこと**: `debug['N']` や `flag_race` が設定されている場合は最適化をスキップします。これは、デバッグや競合検出の目的で元のループ構造を保持する必要があるためです。

これらの条件が満たされた場合、コンパイラは元の`for range`ループを以下のようなコードに変換します（擬似コード）：

```go
if len(a) != 0 {
    hp := &a[0] // スライス/配列の先頭アドレスを取得
    hn := len(a) * sizeof(elem(a)) // クリアするバイト数を計算
    memclr(hp, hn) // memclrを呼び出してメモリをゼロクリア
    i = len(a) - 1 // ループ変数の最終値を設定 (Issue #5373対応)
}
```

この変換により、Goのソースコードレベルではループとして記述されたゼロクリア処理が、コンパイル時には低レベルで最適化された`memclr`関数呼び出しに置き換えられ、大幅なパフォーマンス向上が実現されます。

`issue5373.go`のテストケースは、この最適化がインデックス変数の最終値や、レンジ式およびインデックス式の評価における副作用を正しく扱うことを保証するために重要です。特に、`for i := range s` のようなループで`s`が空の場合、`i`はループに入らず初期値のままですが、最適化されたコードでもこの挙動が維持される必要があります。また、`a[f()] = range s` のように、レンジ式やインデックス式に副作用のある関数呼び出しが含まれる場合、`memclr`に置き換えることはできません。このコミットは、`samesafeexpr`関数を用いてこれらのケースを適切に識別し、安全な場合にのみ最適化を適用するようにしています。

## コアとなるコードの変更箇所

このコミットの主要な変更は以下のファイルに集中しています。

1.  **`src/cmd/gc/range.c`**:
    *   `walkrange`関数内の`TARRAY`（配列/スライス）を処理する部分に、ゼロクリアループの最適化ロジックが追加されました。
    *   特定の条件（前述の「技術的詳細」参照）を満たす`for range`ループを検出し、`runtime·memclr`関数呼び出しに変換するコードが実装されています。
    *   この変換では、スライス/配列の先頭アドレスとサイズを計算し、`memclr`に渡すためのASTノードが構築されます。

    *   Goコンパイラが認識する組み込み関数リストに`runtime·memclr`が追加されました。これにより、コンパイラが`memclr`関数を正しく型チェックし、呼び出しを生成できるようになります。

    *   `samesafeexpr`関数のプロトタイプ宣言が追加されました。この関数は、式が副作用を持たず、安全に再評価できるかどうかを判断するために使用されます。

## コアとなるコードの解説

### `src/cmd/gc/range.c` の変更

このファイルが最適化の心臓部です。`walkrange`関数は、`for range`ループのASTを走査し、最適化の機会を探します。

```c
case TARRAY:
    // Lower n into runtime·memclr if possible, for
    // fast zeroing of slices and arrays (issue 5373).
    // Look for instances of
    //
    // for i := range a {
    //  a[i] = zero
    // }
    //
    // in which the evaluation of a is side-effect-free.
    if(!debug['N']) // デバッグモードでないこと
    if(!flag_race) // 競合検出モードでないこと
    if(v1 != N) // インデックス変数があること
    if(v2 == N) // 値変数が使われていないこと (for i := range a の形式)
    if(n->nbody != nil) // ループ本体があること
    if(n->nbody->n != N) // ループ本体に少なくとも1つのステートメントがあること
    if(n->nbody->next == nil) { // ループ本体に最大1つのステートメントがあること
        tmp = n->nbody->n; // ループ本体の最初のステートメント
        if(tmp->op == OAS) // 代入演算子であること (a[i] = zero)
        if(tmp->left->op == OINDEX) // 左辺がインデックスアクセスであること (a[i])
        if(samesafeexpr(tmp->left->left, a)) // a[i] の a と range a の a が同じで副作用がないこと
        if(samesafeexpr(tmp->left->right, v1)) // a[i] の i と range のインデックス変数が同じで副作用がないこと
        if(t->type->width > 0) // 要素のサイズが0より大きいこと
        if(iszero(tmp->right)) { // 右辺がゼロ値であること
            // Convert to
            // if len(a) != 0 {
            //  hp = &a[0]
            //  hn = len(a)*sizeof(elem(a))
            //  memclr(hp, hn)
            //  i = len(a) - 1
            // }
            n->op = OIF; // ループをif文に変換
            n->nbody = nil;
            n->ntest = nod(ONE, nod(OLEN, a, N), nodintconst(0)); // len(a) != 0 の条件
            n->nincr = nil;

            // hp = &a[0]
            hp = temp(ptrto(types[TUINT8])); // ポインタ変数 hp を作成
            tmp = nod(OINDEX, a, nodintconst(0)); // a[0] を表すノード
            tmp->bounded = 1;
            tmp = nod(OADDR, tmp, N); // &a[0] を表すノード
            tmp = nod(OCONVNOP, tmp, N); // 型変換 (ポインタ型をuint8ポインタに)
            n->nbody = list(n->nbody, nod(OAS, hp, tmp)); // hp = &a[0] をnbodyに追加

            // hn = len(a) * sizeof(elem(a))
            hn = temp(types[TUINTPTR]); // サイズ変数 hn を作成
            tmp = nod(OLEN, a, N); // len(a) を表すノード
            tmp = nod(OMUL, tmp, nodintconst(t->type->width)); // len(a) * sizeof(elem(a))
            tmp = conv(tmp, types[TUINTPTR]); // uintptr に型変換
            n->nbody = list(n->nbody, nod(OAS, hn, tmp)); // hn = ... をnbodyに追加

            // memclr(hp, hn)
            fn = mkcall("memclr", T, nil, hp, hn); // memclr(hp, hn) の呼び出しノードを作成
            n->nbody = list(n->nbody, fn); // memclr呼び出しをnbodyに追加

            // i = len(a) - 1
            v1 = nod(OAS, v1, nod(OSUB, nod(OLEN, a, N), nodintconst(1))); // インデックス変数の最終値を設定
            n->nbody = list(n->nbody, v1); // インデックス変数の代入をnbodyに追加

            typecheck(&n->ntest, Erv); // if文の条件を型チェック
            typechecklist(n->nbody, Etop); // if文の本体を型チェック
            walkstmt(&n); // 新しいASTを再帰的にウォーク
            lineno = lno;
            return;
        }
    }
```

このコードブロックは、Goコンパイラが`for range`ループを最適化された`memclr`呼び出しに変換する具体的なロジックを示しています。各`if`文は最適化を適用するための条件をチェックし、条件が満たされた場合にASTを再構築して`memclr`呼び出しを含む新しい構造に置き換えます。特に、`samesafeexpr`関数による副作用のチェックと、`i = len(a) - 1`によるインデックス変数の最終値の調整が、この最適化の正確性を保証する上で重要です。

### `test/fixedbugs/issue5373.go` の変更

このテストファイルは、最適化がGoのセマンティクスを壊さないことを確認するために非常に重要です。

```go
func check(n int) {
    // ... (インデックス変数の最終値のテスト) ...

    // Index variable whose evaluation has side-effects
    var x int
    f := func() int {
        x++
        return 0
    }
    var a [1]int
    for a[f()] = range s { // インデックス式に副作用のある関数呼び出し
        s[a[f()]] = 0
    }
    if want := n * 2; x != want {
        fmt.Printf("index function calls = %d want %d\n", x, want)
        os.Exit(1)
    }

    // Range expression whose evaluation has side-effects
    x = 0
    b := [1][]byte{s}
    for i := range b[f()] { // レンジ式に副作用のある関数呼び出し
        b[f()][i] = 0
    }
    if want := n + 1; x != n+1 {
        fmt.Printf("range expr function calls = %d want %d\n", x, want)
        os.Exit(1)
    }
}
```

このテストは、`samesafeexpr`関数が正しく機能し、副作用のある式を含むループが`memclr`に最適化されないことを保証します。もしこれらのケースが誤って最適化されると、`f()`関数の呼び出し回数が変わり、`x`の値が期待と異なるため、テストが失敗します。これにより、コンパイラの最適化が安全かつ正確であることが検証されます。

# [インデックス 23034] ファイルの概要

このコミットで変更された `src/runtime/stubs.go` ファイルは、Goランタイムの内部で利用される低レベルのスタブ関数やアトミック操作の宣言、および一部の実装を含むファイルです。Go言語のランタイムは、ガベージコレクション、スケジューリング、メモリ管理など、言語の基本的な動作を支える重要なコンポーネントであり、`stubs.go`はその中でも特に、ハードウェアに依存しないポータブルなアトミック操作の基盤を提供しています。

## コミット

```
These currently use portable implementations in terms of their uint64
counterparts.

Reviewed-on: https://go-review.googlesource.com/8831
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/fb9fd2bdd7024e8d92e7c2a1436843cbca6e1ed1](https://github.com/golang/go/commit/fb9fd2bdd7024e8d92e7c2a1436843cbca6e1ed1)

## 元コミット内容

このコミットは、Goランタイムに `int64` 型のアトミック操作を追加するものです。これらの操作は、現時点では `uint64` 型のアトミック操作を基盤としたポータブルな実装を使用しています。

## 変更の背景

Go言語のような並行処理を重視する言語において、複数のゴルーチン（軽量スレッド）が共有データにアクセスする際に、データの整合性を保つことは非常に重要です。アトミック操作は、このような共有データへのアクセスを安全に行うためのプリミティブな手段を提供します。

このコミットが導入された背景には、`int64` 型に対する直接的なアトミック操作がGoランタイムに不足していたという点があります。既存の`uint64`型のアトミック操作は存在していましたが、`int64`型に対してアトミックな読み書きや加算を行うには、型変換を伴う非アトミックな操作を行うか、より高レベルな同期プリミティブ（ミューテックスなど）を使用する必要がありました。しかし、これらの方法はパフォーマンスのオーバーヘッドを伴うか、競合状態を引き起こす可能性がありました。

コミットメッセージ内のTODOコメント「`TODO: Write native implementations of int64 atomic ops (or improve // inliner). These portable ones can't be inlined right now, so we're // taking an extra function call hit.`」が示すように、この変更は一時的なポータブルな実装であり、将来的にはより効率的なネイティブ実装やインライン化の改善が望まれていました。この「extra function call hit」（余分な関数呼び出しの発生）は、パフォーマンス上の懸念を示しており、アトミック操作のような頻繁に利用される可能性のある低レベルな操作においては、このオーバーヘッドを削減することが重要でした。

## 前提知識の解説

### アトミック操作 (Atomic Operations)

アトミック操作とは、複数のCPUコアやゴルーチンが同時に共有メモリにアクセスするような並行環境において、その操作が不可分（atomic）であることを保証するものです。不可分であるとは、その操作が完全に実行されるか、全く実行されないかのどちらかであり、途中で他の操作に割り込まれることがないという意味です。これにより、データの破損や競合状態（race condition）を防ぎ、プログラムの正確性を保証します。

Go言語では、`sync/atomic`パッケージを通じてアトミック操作が提供されていますが、このコミットで追加されているのは、その`sync/atomic`パッケージの基盤となるランタイムレベルのプリミティブです。

*   **`atomicstore`**: 指定されたメモリ位置に新しい値をアトミックに書き込みます。
*   **`atomicload`**: 指定されたメモリ位置から値をアトミックに読み込みます。
*   **`xadd` (Exchange and Add)**: 指定されたメモリ位置の値に、指定されたデルタ値をアトミックに加算し、加算前の値を返します。これは、カウンタのインクリメント/デクリメントなどによく使用されます。

### `unsafe.Pointer`

`unsafe.Pointer`はGo言語の`unsafe`パッケージで提供される特殊なポインタ型です。これは、任意の型のポインタを保持でき、また任意の型のポインタに変換することができます。これにより、Goの型安全性の制約をバイパスして、C言語のようにメモリを直接操作することが可能になります。

このコミットでは、`int64`型のポインタを`uint64`型のポインタに変換するために`unsafe.Pointer`が使用されています。これは、`int64`と`uint64`がメモリ上では同じビット幅（64ビット）を持つため、ビットパターンをそのまま解釈し直すことで、既存の`uint64`アトミック操作を再利用するためです。

### 型変換 (Type Casting)

Go言語における型変換は通常、厳密なルールに従いますが、`unsafe.Pointer`を介することで、異なる型のポインタ間で変換が可能になります。このコミットでは、`*int64`から`*uint64`への変換、および`int64`から`uint64`への値の変換が行われています。これは、`int64`と`uint64`が同じメモリ表現を持つことを利用したテクニックです。

## 技術的詳細

このコミットの主要な技術的詳細は、`int64`型に対するアトミック操作を、既存の`uint64`型のアトミック操作を再利用して実装している点にあります。具体的には、以下の3つの関数が追加されました。

1.  `atomicstoreint64(ptr *int64, new int64)`
2.  `atomicloadint64(ptr *int64) int64`
3.  `xaddint64(ptr *int64, delta int64) int64`

これらの関数は、それぞれ`atomicstore64`、`atomicload64`、`xadd64`という`uint64`型のアトミック操作を内部で呼び出しています。この際、`*int64`型のポインタは`unsafe.Pointer`を介して`*uint64`型にキャストされ、`int64`型の値は`uint64`型にキャストされます。

このアプローチの利点は、新しいアトミック操作を迅速に提供できることです。`int64`と`uint64`はどちらも64ビットの整数型であり、メモリ上での表現は同じです。したがって、ビットパターンをそのまま解釈し直すことで、既存の`uint64`向けのアトミック操作を`int64`向けに流用できます。

しかし、この実装は「ポータブルな実装」とされており、コミットメッセージのTODOコメントが示すように、パフォーマンス上の課題を抱えていました。具体的には、これらの関数がインライン化されないため、アトミック操作を行うたびに余分な関数呼び出しのオーバーヘッドが発生していました。理想的には、各アーキテクチャ（x86, ARMなど）のCPUが提供するネイティブなアトミック命令を直接利用する実装が最も効率的です。このコミットは、そのネイティブ実装がまだ存在しない段階での暫定的な解決策として導入されました。

`//go:noescape`ディレクティブは、このコミットで追加された関数には直接適用されていませんが、`stubs.go`ファイル内の他のアトミック操作関数には適用されています。これは、コンパイラに対して、その関数が引数として受け取ったポインタが、関数の実行後もヒープにエスケープしないことを示唆するものです。これにより、コンパイラはより積極的な最適化（例えば、スタック上に変数を割り当てるなど）を行うことができます。このコミットで追加された関数が`//go:noescape`ではないのは、それらが内部で他の関数を呼び出しており、その呼び出し先の関数がエスケープ解析に影響を与える可能性があるためかもしれません。

## コアとなるコードの解説

追加された3つの関数について、それぞれ詳しく解説します。

### `func atomicstoreint64(ptr *int64, new int64)`

この関数は、`int64`型のポインタ`ptr`が指すメモリ位置に、`new`の値をアトミックに書き込みます。

```go
func atomicstoreint64(ptr *int64, new int64) {
	atomicstore64((*uint64)(unsafe.Pointer(ptr)), uint64(new))
}
```

*   `unsafe.Pointer(ptr)`: まず、`*int64`型のポインタ`ptr`を`unsafe.Pointer`に変換します。これにより、Goの型システムによる制約が一時的に解除され、任意のポインタ型への変換が可能になります。
*   `(*uint64)(unsafe.Pointer(ptr))`: 次に、`unsafe.Pointer`を`*uint64`型にキャストします。これは、`int64`と`uint64`がメモリ上で同じ64ビットの領域を占めることを利用し、`int64`のメモリ位置を`uint64`として解釈し直すためです。
*   `uint64(new)`: 書き込む値`new`（`int64`型）も`uint64`型に変換されます。これは、`atomicstore64`関数が`uint64`型の値を受け取るためです。
*   `atomicstore64(...)`: 最終的に、`uint64`型のアトミックストア関数`atomicstore64`が呼び出され、指定されたメモリ位置に値がアトミックに書き込まれます。

### `func atomicloadint64(ptr *int64) int64`

この関数は、`int64`型のポインタ`ptr`が指すメモリ位置から、値をアトミックに読み込みます。

```go
func atomicloadint64(ptr *int64) int64 {
	return int64(atomicload64((*uint64)(unsafe.Pointer(ptr))))
}
```

*   `(*uint64)(unsafe.Pointer(ptr))`: `atomicstoreint64`と同様に、`*int64`型のポインタ`ptr`を`unsafe.Pointer`を介して`*uint64`型にキャストします。
*   `atomicload64(...)`: `uint64`型のアトミックロード関数`atomicload64`が呼び出され、メモリ位置から値がアトミックに読み込まれます。このとき返される値は`uint64`型です。
*   `int64(...)`: `atomicload64`から返された`uint64`型の値を、最終的に`int64`型に変換して返します。

### `func xaddint64(ptr *int64, delta int64) int64`

この関数は、`int64`型のポインタ`ptr`が指すメモリ位置の値に、`delta`の値をアトミックに加算し、加算前の値を返します。

```go
func xaddint64(ptr *int64, delta int64) int64 {
	return int64(xadd64((*uint64)(unsafe.Pointer(ptr)), delta))
}
```

*   `(*uint64)(unsafe.Pointer(ptr))`: `atomicstoreint64`や`atomicloadint64`と同様に、`*int64`型のポインタ`ptr`を`unsafe.Pointer`を介して`*uint64`型にキャストします。
*   `xadd64(...)`: `uint64`型のアトミック加算関数`xadd64`が呼び出されます。この関数は、`uint64`型のポインタと、加算する値（`delta`）を受け取ります。`delta`は`int64`型ですが、`xadd64`は`uint64`型のデルタを受け取るため、Goの型推論や暗黙の型変換が働くか、あるいは`xadd64`の定義が`int64`も受け入れるようになっているか、または`delta`が内部で`uint64`に変換されて渡されるかのいずれかです。Goの`sync/atomic`パッケージの`AddUint64`は`uint64`を受け取るため、ここでは`delta`が`uint64`に変換されて渡されると考えるのが自然です。
*   `int64(...)`: `xadd64`から返された`uint64`型の値を、最終的に`int64`型に変換して返します。

これらの実装は、`int64`と`uint64`のビット表現が同じであることを利用した、Goランタイムにおける一般的なパターンです。これにより、異なる符号付き/符号なし整数型に対しても、共通のアトミック操作の基盤を再利用できます。

*   `unsafe.Pointer(ptr)`: まず、`*int64`型のポインタ`ptr`を`unsafe.Pointer`に変換します。これにより、Goの型システムによる制約が一時的に解除され、任意のポインタ型への変換が可能になります。
*   `(*uint64)(unsafe.Pointer(ptr))`: 次に、`unsafe.Pointer`を`*uint64`型にキャストします。これは、`int64`と`uint64`がメモリ上で同じ64ビットの領域を占めることを利用し、`int64`のメモリ位置を`uint64`として解釈し直すためです。
*   `uint64(new)`: 書き込む値`new`（`int64`型）も`uint64`型に変換されます。これは、`atomicstore64`関数が`uint64`型の値を受け取るためです。
*   `atomicstore64(...)`: 最終的に、`uint64`型のアトミックストア関数`atomicstore64`が呼び出され、指定されたメモリ位置に値がアトミックに書き込まれます。

### `func atomicloadint64(ptr *int64) int64`

この関数は、`int64`型のポインタ`ptr`が指すメモリ位置から、値をアトミックに読み込みます。

```go
func atomicloadint64(ptr *int64) int64 {
	return int64(atomicload64((*uint64)(unsafe.Pointer(ptr))))
}
```

*   `(*uint64)(unsafe.Pointer(ptr))`: `atomicstoreint64`と同様に、`*int64`型のポインタ`ptr`を`unsafe.Pointer`を介して`*uint64`型にキャストします。
*   `atomicload64(...)`: `uint64`型のアトミックロード関数`atomicload64`が呼び出され、メモリ位置から値がアトミックに読み込まれます。このとき返される値は`uint64`型です。
*   `int64(...)`: `atomicload64`から返された`uint64`型の値を、最終的に`int64`型に変換して返します。

### `func xaddint64(ptr *int64, delta int64) int64`

この関数は、`int64`型のポインタ`ptr`が指すメモリ位置の値に、`delta`の値をアトミックに加算し、加算前の値を返します。

```go
func xaddint64(ptr *int64, delta int64) int64 {
	return int64(xadd64((*uint64)(unsafe.Pointer(ptr)), delta))
}
```

*   `(*uint64)(unsafe.Pointer(ptr))`: `atomicstoreint64`や`atomicloadint64`と同様に、`*int64`型のポインタ`ptr`を`unsafe.Pointer`を介して`*uint64`型にキャストします。
*   `xadd64(...)`: `uint64`型のアトミック加算関数`xadd64`が呼び出されます。この関数は、`uint64`型のポインタと、加算する値（`delta`）を受け取ります。`delta`は`int64`型ですが、`xadd64`は`uint64`型のデルタを受け取るため、Goの型推論や暗黙の型変換が働くか、あるいは`xadd64`の定義が`int64`も受け入れるようになっているか、または`delta`が内部で`uint64`に変換されて渡されるかのいずれかです。Goの`sync/atomic`パッケージの`AddUint64`は`uint64`を受け取るため、ここでは`delta`が`uint64`に変換されて渡されると考えるのが自然です。
*   `int64(...)`: `xadd64`から返された`uint64`型の値を、最終的に`int64`型に変換して返します。

これらの実装は、`int64`と`uint64`のビット表現が同じであることを利用した、Goランタイムにおける一般的なパターンです。これにより、異なる符号付き/符号なし整数型に対しても、共通のアトミック操作の基盤を再利用できます。

# [インデックス 24145] ファイルの概要

このコミットは、Goランタイムにおけるメモリ統計（`MemStats`）の一部、具体的には`PauseNS`、`PauseEnd`、`PauseTotalNS`、`LastGC`の計算方法の修正に関するものです。これらの統計は、Goのガベージコレクション（GC）のポーズ時間に関する重要な情報を提供しますが、Go 1.5で導入された新しいGCメカニズムに対応していなかったため、不正確な値が報告されていました。

## 元コミット内容

`runtime: fix MemStats.{PauseNS,PauseEnd,PauseTotalNS,LastGC}`

これらのメモリ統計は現在`gcMark`によって計算されていますが、これはGo 1.4では適切でした。しかし、`gcMark`は現在、より大きな全体像の一部に過ぎません。特に、スイープ終了時のポーズ時間やマーク終了時のポーズ時間の一部を考慮できず、報告される「ポーズ終了」時間と「最後のGC」時間は実際よりもわずかに早くなります。

これらの統計の計算を`func gc`に移動させ、プロセス全体を適切に把握して正確に計算できるようにします。

これはIssue #10323の1つの問題を修正します。この変更は、並行コレクタに適した新しい統計を追加するものではなく、誤って報告されていた既存の統計を修正するものです。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクタ（GC）の進化があります。Go 1.4までは、GCは「Stop-The-World (STW)」方式が主流であり、GCが実行されている間はアプリケーションの実行が完全に停止していました。このため、GCのポーズ時間はアプリケーションのレイテンシに直接影響を与え、重要なパフォーマンス指標でした。

Go 1.5では、より低レイテンシを実現するために、並行（concurrent）かつインクリメンタル（incremental）なGCが導入されました。この新しいGCは、アプリケーションの実行と並行してマークフェーズの大部分を実行することで、STWポーズ時間を大幅に短縮しました。しかし、GCのライフサイクルが複雑になったため、従来の`gcMark`関数だけではGCのポーズ時間を正確に測定することが困難になりました。

具体的には、以下の問題が発生していました。
1.  **スイープ終了時のポーズ時間（sweep termination pause time）の考慮不足**: 新しいGCサイクルでは、マークフェーズの後にスイープフェーズが続きますが、このスイープの終了時にもSTWポーズが発生する可能性があります。`gcMark`はマークフェーズに特化していたため、このポーズ時間を適切に含めることができませんでした。
2.  **マーク終了時のポーズ時間（mark termination pause time）の不完全な考慮**: マークフェーズの終了時にもSTWポーズが発生しますが、`gcMark`が測定していたのはその一部に過ぎず、全体をカバーしていませんでした。
3.  **`PauseEnd`と`LastGC`の不正確さ**: 上記の理由により、GCの実際の終了時刻が正しく反映されず、報告される`PauseEnd`（ポーズ終了時刻）と`LastGC`（最後のGC実行時刻）が実際よりも早く記録されていました。

これらの問題により、`MemStats`が提供するGCポーズ時間に関する情報が信頼できないものとなり、開発者がアプリケーションのパフォーマンスを正確に分析する上で支障をきたしていました。このコミットは、これらの既存の統計の正確性を回復することを目的としています。

## 前提知識の解説

### Goのガベージコレクタ (GC)

GoのGCは、自動メモリ管理システムであり、不要になったメモリを自動的に解放します。Go 1.5以前と以降でその動作は大きく異なります。

*   **Go 1.4までのGC**: 主に「マーク＆スイープ」アルゴリズムを採用し、GCの主要なフェーズ（マークフェーズとスイープフェーズ）のほとんどがSTW（Stop-The-World）ポーズ中に実行されました。これは、GCが実行されている間、すべてのゴルーチン（Goの軽量スレッド）が一時停止することを意味し、アプリケーションの応答時間に大きな影響を与える可能性がありました。
    *   **マークフェーズ**: どのオブジェクトがまだ使用されているか（到達可能か）を識別します。
    *   **スイープフェーズ**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。
*   **Go 1.5以降のGC**: 「並行マーク＆スイープ」アルゴリズムを導入しました。これにより、マークフェーズの大部分がアプリケーションのゴルーチンと並行して実行されるようになりました。STWポーズは、GCの開始時（マーク開始）と終了時（マーク終了）の短い期間に限定され、全体的なレイテンシが大幅に改善されました。
    *   **並行マーク**: アプリケーションが実行されている間に、バックグラウンドで到達可能なオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: 並行マークフェーズの最終段階で、STWポーズが発生し、マークフェーズの残りの作業（例えば、ミューテータがマーク中に変更したオブジェクトの再スキャン）を完了します。
    *   **並行スイープ**: マーク終了後、アプリケーションと並行して不要なメモリを解放します。
    *   **スイープ終了 (Sweep Termination)**: 次のGCサイクルが開始される前に、前のサイクルのスイープが完全に終了していることを保証するための処理。ここでも短いSTWポーズが発生する可能性があります。

### `runtime.MemStats`

`runtime.MemStats`は、Goプログラムのメモリ使用状況とGC統計に関する情報を提供する構造体です。`runtime.ReadMemStats`関数を呼び出すことで、この構造体の現在の値を読み取ることができます。開発者はこの情報を使用して、メモリリークの検出、GCパフォーマンスの分析、アプリケーションのチューニングなどを行います。

このコミットで修正対象となった主要なフィールドは以下の通りです。

*   `PauseNS [256]uint64`: 直近256回のGCポーズ時間のナノ秒単位での記録。リングバッファとして機能します。
*   `PauseEnd [256]uint64`: 直近256回のGCポーズが終了したUnixナノ秒単位の時刻。リングバッファとして機能します。
*   `PauseTotalNs uint64`: プログラム開始からのGCポーズ時間の合計（ナノ秒単位）。
*   `LastGC uint64`: 最後のGCが終了したUnixナノ秒単位の時刻。

### `gcMark`と`func gc`

*   **`gcMark`**: 主にGCのマークフェーズに関連する処理を担当する関数です。Go 1.4までは、GCの主要なロジックがここに集中していました。
*   **`func gc`**: GoランタイムにおけるGCの全体的なオーケストレーションを担当する高レベルの関数です。GCサイクルの開始から終了まで、様々なフェーズ（マーク、スイープ、STWポーズなど）を調整します。Go 1.5以降の並行GCでは、この関数がGCプロセスの全体像を把握する上で中心的な役割を担います。

### Issue #10323

このコミットが修正する問題の一つとして言及されているIssue #10323は、Go 1.5の並行GCにおける`MemStats`の不正確さに関するものです。特に、`PauseTotalNs`が正しく計算されていないことや、GCポーズ時間の測定が不完全であることが報告されていました。このコミットは、その中の特定の側面（`gcMark`による統計計算の不正確さ）に対処しています。

## 技術的詳細

このコミットの核心は、GCポーズ時間関連の`MemStats`フィールドの計算ロジックを、`gcMark`関数から`func gc`関数へ移動し、その計算方法を改善することです。

Go 1.5の並行GCでは、GCサイクルは複数の段階に分かれています。
1.  **GC開始**: `func gc`が呼び出され、GCサイクルが開始されます。
2.  **STW (Stop-The-World) フェーズ**:
    *   **マーク開始**: 短いSTWポーズが発生し、マークフェーズの準備が行われます。
    *   **マーク終了**: 並行マークフェーズの後に発生するSTWポーズで、マーク作業の最終処理が行われます。
    *   **スイープ終了**: 次のGCサイクルが始まる前に、前のサイクルのスイープが完了していることを確認するためのSTWポーズ。
3.  **並行フェーズ**: STWポーズの間に挟まれて、アプリケーションのゴルーチンと並行してGC作業（並行マーク、並行スイープ）が実行されます。

従来の`gcMark`関数は、主にマークフェーズのSTW部分に焦点を当てていました。しかし、並行GCの導入により、GCポーズは`gcMark`の実行範囲外でも発生するようになりました（例：スイープ終了時のポーズ）。また、マーク終了時のポーズも、`gcMark`が把握できる範囲を超えていました。

このコミットでは、`func gc`がGCサイクルの全体を制御しているという特性を利用し、GCポーズの開始と終了をより正確に追跡できるように変更されています。具体的には、`func gc`内で`nanotime()`を呼び出してタイムスタンプを記録し、STWポーズの開始と終了を検出することで、ポーズ時間を正確に計算します。

### 変更の具体的なポイント:

*   **`now`, `pauseStart`, `pauseNS`変数の導入**: `func gc`内にこれらの変数を導入し、GCサイクルの様々な段階での時刻記録とポーズ時間の累積に使用します。
    *   `now`: 現在のナノ秒時刻を保持します。
    *   `pauseStart`: STWポーズが開始された時刻を保持します。
    *   `pauseNS`: 現在のGCサイクルにおける累積ポーズ時間を保持します。
*   **`nanotime()`と`unixnanotime()`の活用**:
    *   `nanotime()`: システムのモノトニックな時間（起動からの経過時間）をナノ秒単位で取得します。ポーズ時間の計算に使用されます。
    *   `unixnanotime()`: Unixエポックからの時間をナノ秒単位で取得します。`LastGC`や`PauseEnd`のように、絶対的な時刻を示す統計に使用されます。
*   **STWポーズの開始と終了の追跡**: `systemstack(stopTheWorldWithSema)`と`systemstack(startTheWorldWithSema)`の呼び出し前後で`now`と`pauseStart`を更新し、`pauseNS`にポーズ時間を加算します。これにより、GCサイクル全体にわたるすべてのSTWポーズ時間を正確に捕捉します。
*   **`MemStats`の更新箇所の移動**: `MemStats.PauseNS`, `MemStats.PauseEnd`, `MemStats.PauseTotalNs`, `MemStats.LastGC`の更新ロジックが、`gcMark`の末尾から`func gc`のSTW解除直前（GCサイクル終了間際）に移動されます。これにより、GCサイクル全体のポーズ時間を反映した正確な統計が記録されます。
*   **テストの追加**: `malloc_test.go`に`PauseTotalNs`が`PauseNs`の合計と一致するかどうかを検証するテストが追加され、修正の正確性が保証されます。

この修正は、GoのGCがより複雑な並行処理を行うようになった結果として生じた、統計報告の不整合を解消するものです。既存の統計の正確性を高めることで、Goプログラムのパフォーマンス監視とデバッグの信頼性を向上させます。

## コアとなるコードの解説

### `src/runtime/malloc_test.go`の変更

*   `TestMemStats`関数内の`t.Fatalf`条件に`st.PauseTotalNs > 1e11`が追加されました。これは、`PauseTotalNs`が異常に大きな値になる（オーバーフローなど）ケースを検出するためのチェックです。
*   新しいテストブロックが追加されました。このブロックは、`MemStats.PauseTotalNs`が`MemStats.PauseNs`配列内の個々のポーズ時間の合計と一致するかどうかを検証します。
    *   `pauseTotal`変数を初期化し、`st.PauseNs`配列の要素を合計します。
    *   `st.NumGC`（GC実行回数）が`st.PauseNs`配列の長さよりも小さい場合（つまり、すべてのポーズ時間が配列に収まっている場合）、`st.PauseTotalNs`が`pauseTotal`と完全に一致することを期待します。一致しない場合はテストが失敗します。
    *   `st.NumGC`が配列の長さ以上の場合（リングバッファが一周している場合）、`st.PauseTotalNs`は`pauseTotal`以上であることを期待します。これは、`PauseNs`が直近のポーズ時間しか保持しないのに対し、`PauseTotalNs`は累積値であるためです。

このテストの追加により、`PauseTotalNs`の計算が正確に行われていることが保証されます。

### `src/runtime/mgc.go`の変更

このファイルでは、`func gc`と`func gcMark`の2つの主要な関数に変更が加えられています。

#### `func gc`の変更

1.  **新しい変数の導入**:
    ```go
    	var now, pauseStart, pauseNS int64
    ```
    `func gc`の冒頭に、`now`（現在の時刻）、`pauseStart`（STWポーズ開始時刻）、`pauseNS`（現在のGCサイクルにおける累積ポーズ時間）を追跡するための変数が導入されました。

2.  **`nanotime()`の呼び出し箇所の変更**:
    *   GC開始時、`gcBgMarkStartWorkers()`の直後に`now = nanotime()`が追加され、GCサイクルの初期時刻が記録されます。
    *   `debug.gctrace > 0`の場合の`tSweepTerm`の初期化が`nanotime()`から`now`に変更され、一貫性が保たれます。
    *   `pauseStart = now`が`systemstack(stopTheWorldWithSema)`の直前に移動され、STWポーズの開始時刻が正確に記録されます。

3.  **STWポーズ時間の累積**:
    *   並行スキャン（Concurrent scan）の終了後、`startTheWorldWithSema()`が呼び出されてSTWが解除された直後に、`now = nanotime()`と`pauseNS += now - pauseStart`が追加されました。これにより、マーク開始から並行スキャン終了までのSTWポーズ時間が`pauseNS`に加算されます。
    *   マーク終了（Mark termination）の開始時、`now = nanotime()`と`pauseStart = now`が追加されました。これにより、マーク終了フェーズのSTWポーズ開始時刻が記録されます。

4.  **`MemStats`の更新ロジックの移動と修正**:
    `func gc`の末尾、`systemstack(startTheWorldWithSema)`が呼び出される直前に、`MemStats`のポーズ時間関連フィールドを更新する新しいブロックが追加されました。
    ```go
    	// Update timing memstats
    	now, unixNow := nanotime(), unixnanotime()
    	pauseNS += now - pauseStart

    *   最後のSTWポーズ（マーク終了フェーズ）の時間を`pauseNS`に加算します。

    *   `memstats.pause_ns`配列に現在のGCサイクルの合計ポーズ時間`pauseNS`を記録します（リングバッファ）。
    *   `memstats.pause_end`配列に現在のUnix時刻を記録します。
    *   `memstats.pause_total_ns`に現在のGCサイクルの合計ポーズ時間`pauseNS`を加算します。
    *   `memstats.numgc`（GC実行回数）をインクリメントします。

    このブロックは、GCサイクル全体を通して累積されたポーズ時間と、GCが実際に終了した時刻を正確に`MemStats`に反映させます。

#### `func gcMark`の変更

*   `func gcMark`の末尾にあった`MemStats`の更新ロジック（`t0`、`t4`、`unixNow`を使った`memstats.pause_ns`、`memstats.pause_end`、`memstats.pause_total_ns`、`memstats.last_gc`の更新）が完全に削除されました。これは、これらの統計の計算が`func gc`に一元化されたためです。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクタ（GC）の進化があります。Go 1.4までは、GCは「Stop-The-World (STW)」方式が主流であり、GCが実行されている間はアプリケーションの実行が完全に停止していました。このため、GCのポーズ時間はアプリケーションのレイテンシに直接影響を与え、重要なパフォーマンス指標でした。

Go 1.5では、より低レイテンシを実現するために、並行（concurrent）かつインクリメンタル（incremental）なGCが導入されました。この新しいGCは、アプリケーションの実行と並行してマークフェーズの大部分を実行することで、STWポーズ時間を大幅に短縮しました。しかし、GCのライフサイクルが複雑になったため、従来の`gcMark`関数だけではGCのポーズ時間を正確に測定することが困難になりました。

具体的には、以下の問題が発生していました。
1.  **スイープ終了時のポーズ時間（sweep termination pause time）の考慮不足**: 新しいGCサイクルでは、マークフェーズの後にスイープフェーズが続きますが、このスイープの終了時にもSTWポーズが発生する可能性があります。`gcMark`はマークフェーズに特化していたため、このポーズ時間を適切に含めることができませんでした。
2.  **マーク終了時のポーズ時間（mark termination pause time）の不完全な考慮**: マークフェーズの終了時にもSTWポーズが発生しますが、`gcMark`が測定していたのはその一部に過ぎず、全体をカバーしていませんでした。
3.  **`PauseEnd`と`LastGC`の不正確さ**: 上記の理由により、GCの実際の終了時刻が正しく反映されず、報告される`PauseEnd`（ポーズ終了時刻）と`LastGC`（最後のGC実行時刻）が実際よりも早く記録されていました。

これらの問題により、`MemStats`が提供するGCポーズ時間に関する情報が信頼できないものとなり、開発者がアプリケーションのパフォーマンスを正確に分析する上で支障をきたしていました。このコミットは、これらの既存の統計の正確性を回復することを目的としています。

## 前提知識の解説

### Goのガベージコレクタ (GC)

GoのGCは、自動メモリ管理システムであり、不要になったメモリを自動的に解放します。Go 1.5以前と以降でその動作は大きく異なります。

*   **Go 1.4までのGC**: 主に「マーク＆スイープ」アルゴリズムを採用し、GCの主要なフェーズ（マークフェーズとスイープフェーズ）のほとんどがSTW（Stop-The-World）ポーズ中に実行されました。これは、GCが実行されている間、すべてのゴルーチン（Goの軽量スレッド）が一時停止することを意味し、アプリケーションの応答時間に大きな影響を与える可能性がありました。
    *   **マークフェーズ**: どのオブジェクトがまだ使用されているか（到達可能か）を識別します。
    *   **スイープフェーズ**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。
*   **Go 1.5以降のGC**: 「並行マーク＆スイープ」アルゴリズムを導入しました。これにより、マークフェーズの大部分がアプリケーションのゴルーチンと並行して実行されるようになりました。STWポーズは、GCの開始時（マーク開始）と終了時（マーク終了）の短い期間に限定され、全体的なレイテンシが大幅に改善されました。
    *   **並行マーク**: アプリケーションが実行されている間に、バックグラウンドで到達可能なオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: 並行マークフェーズの最終段階で、STWポーズが発生し、マークフェーズの残りの作業（例えば、ミューテータがマーク中に変更したオブジェクトの再スキャン）を完了します。
    *   **並行スイープ**: マーク終了後、アプリケーションと並行して不要なメモリを解放します。
    *   **スイープ終了 (Sweep Termination)**: 次のGCサイクルが開始される前に、前のサイクルのスイープが完全に終了していることを保証するための処理。ここでも短いSTWポーズが発生する可能性があります。

### `runtime.MemStats`

`runtime.MemStats`は、Goプログラムのメモリ使用状況とGC統計に関する情報を提供する構造体です。`runtime.ReadMemStats`関数を呼び出すことで、この構造体の現在の値を読み取ることができます。開発者はこの情報を使用して、メモリリークの検出、GCパフォーマンスの分析、アプリケーションのチューニングなどを行います。

このコミットで修正対象となった主要なフィールドは以下の通りです。

*   `PauseNS [256]uint64`: 直近256回のGCポーズ時間のナノ秒単位での記録。リングバッファとして機能します。
*   `PauseEnd [256]uint64`: 直近256回のGCポーズが終了したUnixナノ秒単位の時刻。リングバッファとして機能します。
*   `PauseTotalNs uint64`: プログラム開始からのGCポーズ時間の合計（ナノ秒単位）。
*   `LastGC uint64`: 最後のGCが終了したUnixナノ秒単位の時刻。

### `gcMark`と`func gc`

*   **`gcMark`**: 主にGCのマークフェーズに関連する処理を担当する関数です。Go 1.4までは、GCの主要なロジックがここに集中していました。
*   **`func gc`**: GoランタイムにおけるGCの全体的なオーケストレーションを担当する高レベルの関数です。GCサイクルの開始から終了まで、様々なフェーズ（マーク、スイープ、STWポーズなど）を調整します。Go 1.5以降の並行GCでは、この関数がGCプロセスの全体像を把握する上で中心的な役割を担います。

### Issue #10323

このコミットが修正する問題の一つとして言及されているIssue #10323は、Go 1.5の並行GCにおける`MemStats`の不正確さに関するものです。特に、`PauseTotalNs`が正しく計算されていないことや、GCポーズ時間の測定が不完全であることが報告されていました。このコミットは、その中の特定の側面（`gcMark`による統計計算の不正確さ）に対処しています。

## 技術的詳細

このコミットの核心は、GCポーズ時間関連の`MemStats`フィールドの計算ロジックを、`gcMark`関数から`func gc`関数へ移動し、その計算方法を改善することです。

Go 1.5の並行GCでは、GCサイクルは複数の段階に分かれています。
1.  **GC開始**: `func gc`が呼び出され、GCサイクルが開始されます。
2.  **STW (Stop-The-World) フェーズ**:
    *   **マーク開始**: 短いSTWポーズが発生し、マークフェーズの準備が行われます。
    *   **マーク終了**: 並行マークフェーズの後に発生するSTWポーズで、マーク作業の最終処理が行われます。
    *   **スイープ終了**: 次のGCサイクルが始まる前に、前のサイクルのスイープが完了していることを確認するためのSTWポーズ。
3.  **並行フェーズ**: STWポーズの間に挟まれて、アプリケーションのゴルーチンと並行してGC作業（並行マーク、並行スイープ）が実行されます。

従来の`gcMark`関数は、主にマークフェーズのSTW部分に焦点を当てていました。しかし、並行GCの導入により、GCポーズは`gcMark`の実行範囲外でも発生するようになりました（例：スイープ終了時のポーズ）。また、マーク終了時のポーズも、`gcMark`が把握できる範囲を超えていました。

このコミットでは、`func gc`がGCサイクルの全体を制御しているという特性を利用し、GCポーズの開始と終了をより正確に追跡できるように変更されています。具体的には、`func gc`内で`nanotime()`を呼び出してタイムスタンプを記録し、STWポーズの開始と終了を検出することで、ポーズ時間を正確に計算します。

### 変更の具体的なポイント:

*   **`now`, `pauseStart`, `pauseNS`変数の導入**: `func gc`内にこれらの変数を導入し、GCサイクルの様々な段階での時刻記録とポーズ時間の累積に使用します。
    *   `now`: 現在のナノ秒時刻を保持します。
    *   `pauseStart`: STWポーズが開始された時刻を保持します。
    *   `pauseNS`: 現在のGCサイクルにおける累積ポーズ時間を保持します。
*   **`nanotime()`と`unixnanotime()`の活用**:
    *   `nanotime()`: システムのモノトニックな時間（起動からの経過時間）をナノ秒単位で取得します。ポーズ時間の計算に使用されます。
    *   `unixnanotime()`: Unixエポックからの時間をナノ秒単位で取得します。`LastGC`や`PauseEnd`のように、絶対的な時刻を示す統計に使用されます。
*   **STWポーズの開始と終了の追跡**: `systemstack(stopTheWorldWithSema)`と`systemstack(startTheWorldWithSema)`の呼び出し前後で`now`と`pauseStart`を更新し、`pauseNS`にポーズ時間を加算します。これにより、GCサイクル全体にわたるすべてのSTWポーズ時間を正確に捕捉します。
*   **`MemStats`の更新箇所の移動**: `MemStats.PauseNS`, `MemStats.PauseEnd`, `MemStats.PauseTotalNs`, `MemStats.LastGC`の更新ロジックが、`gcMark`の末尾から`func gc`のSTW解除直前（GCサイクル終了間際）に移動されます。これにより、GCサイクル全体のポーズ時間を反映した正確な統計が記録されます。
*   **テストの追加**: `malloc_test.go`に`PauseTotalNs`が`PauseNs`の合計と一致するかどうかを検証するテストが追加され、修正の正確性が保証されます。

この修正は、GoのGCがより複雑な並行処理を行うようになった結果として生じた、統計報告の不整合を解消するものです。既存の統計の正確性を高めることで、Goプログラムのパフォーマンス監視とデバッグの信頼性を向上させます。

## コアとなるコードの解説

### `src/runtime/malloc_test.go`の変更

*   `TestMemStats`関数内の`t.Fatalf`条件に`st.PauseTotalNs > 1e11`が追加されました。これは、`PauseTotalNs`が異常に大きな値になる（オーバーフローなど）ケースを検出するためのチェックです。
*   新しいテストブロックが追加されました。このブロックは、`MemStats.PauseTotalNs`が`MemStats.PauseNs`配列内の個々のポーズ時間の合計と一致するかどうかを検証します。
    *   `pauseTotal`変数を初期化し、`st.PauseNs`配列の要素を合計します。
    *   `st.NumGC`（GC実行回数）が`st.PauseNs`配列の長さよりも小さい場合（つまり、すべてのポーズ時間が配列に収まっている場合）、`st.PauseTotalNs`が`pauseTotal`と完全に一致することを期待します。一致しない場合はテストが失敗します。
    *   `st.NumGC`が配列の長さ以上の場合（リングバッファが一周している場合）、`st.PauseTotalNs`は`pauseTotal`以上であることを期待します。これは、`PauseNs`が直近のポーズ時間しか保持しないのに対し、`PauseTotalNs`は累積値であるためです。

このテストの追加により、`PauseTotalNs`の計算が正確に行われていることが保証されます。

### `src/runtime/mgc.go`の変更

このファイルでは、`func gc`と`func gcMark`の2つの主要な関数に変更が加えられています。

#### `func gc`の変更

1.  **新しい変数の導入**:
    ```go
    	var now, pauseStart, pauseNS int64
    ```
    `func gc`の冒頭に、`now`（現在の時刻）、`pauseStart`（STWポーズ開始時刻）、`pauseNS`（現在のGCサイクルにおける累積ポーズ時間）を追跡するための変数が導入されました。

2.  **`nanotime()`の呼び出し箇所の変更**:
    *   GC開始時、`gcBgMarkStartWorkers()`の直後に`now = nanotime()`が追加され、GCサイクルの初期時刻が記録されます。
    *   `debug.gctrace > 0`の場合の`tSweepTerm`の初期化が`nanotime()`から`now`に変更され、一貫性が保たれます。
    *   `pauseStart = now`が`systemstack(stopTheWorldWithSema)`の直前に移動され、STWポーズの開始時刻が正確に記録されます。

3.  **STWポーズ時間の累積**:
    *   並行スキャン（Concurrent scan）の終了後、`startTheWorldWithSema()`が呼び出されてSTWが解除された直後に、`now = nanotime()`と`pauseNS += now - pauseStart`が追加されました。これにより、マーク開始から並行スキャン終了までのSTWポーズ時間が`pauseNS`に加算されます。
    *   マーク終了（Mark termination）の開始時、`now = nanotime()`と`pauseStart = now`が追加されました。これにより、マーク終了フェーズのSTWポーズ開始時刻が記録されます。

4.  **`MemStats`の更新ロジックの移動と修正**:
    `func gc`の末尾、`systemstack(startTheWorldWithSema)`が呼び出される直前に、`MemStats`のポーズ時間関連フィールドを更新する新しいブロックが追加されました。
    ```go
    	// Update timing memstats
    	now, unixNow := nanotime(), unixnanotime()
    	pauseNS += now - pauseStart
    	atomicstore64(&memstats.last_gc, uint64(unixNow)) // must be Unix time to make sense to user
    	memstats.pause_ns[memstats.numgc%uint32(len(memstats.pause_ns))] = uint64(pauseNS)
    	memstats.pause_end[memstats.numgc%uint32(len(memstats.pause_end))] = uint64(unixNow)
    	memstats.pause_total_ns += uint64(pauseNS)

    	memstats.numgc++
    ```
    *   `now`と`unixNow`で現在の時刻（モノトニックとUnix時間）を取得します。
    *   最後のSTWポーズ（マーク終了フェーズ）の時間を`pauseNS`に加算します。
    *   `memstats.last_gc`を現在のUnix時刻で更新します。
    *   `memstats.pause_ns`配列に現在のGCサイクルの合計ポーズ時間`pauseNS`を記録します（リングバッファ）。
    *   `memstats.pause_end`配列に現在のUnix時刻を記録します。
    *   `memstats.pause_total_ns`に現在のGCサイクルの合計ポーズ時間`pauseNS`を加算します。
    *   `memstats.numgc`（GC実行回数）をインクリメントします。

    このブロックは、GCサイクル全体を通して累積されたポーズ時間と、GCが実際に終了した時刻を正確に`MemStats`に反映させます。

#### `func gcMark`の変更

*   `func gcMark`の末尾にあった`MemStats`の更新ロジック（`t0`、`t4`、`unixNow`を使った`memstats.pause_ns`、`memstats.pause_end`、`memstats.pause_total_ns`、`memstats.last_gc`の更新）が完全に削除されました。これは、これらの統計の計算が`func gc`に一元化されたためです。
*   `t0 := start_time`の行も削除されました。

これらの変更により、`func gc`がGCプロセスの全体像を把握し、すべてのSTWポーズ時間を正確に集計して`MemStats`に報告できるようになりました。これにより、Go 1.5以降の並行GC環境下でも、GCポーズ時間に関する統計の信頼性が向上します。

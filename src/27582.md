## 変更の背景

Go言語のマップ（`map`）は、キーと値のペアを格納するデータ構造です。Goのマップは、値のセマンティクス（value semantics）を採用しており、マップから値を取得すると、その値の**コピー**が返されます。これは、マップに格納されている元の値への直接の参照ではありません。

この特性のため、マップから取得した構造体のフィールドを直接変更しようとすると、実際にはその構造体の**コピー**のフィールドを変更していることになり、マップに格納されている元の構造体には変更が反映されません。Goコンパイラはこのような操作を許可せず、コンパイル時にエラーを発生させます。

しかし、このコミット以前は、このようなケースで表示されるエラーメッセージは「`cannot assign to students["sally"].age`」のように非常に一般的でした。このメッセージだけでは、なぜ代入できないのか、Goのマップのどのような特性が原因なのかが初心者には分かりにくく、混乱を招く可能性がありました。

このコミットの背景には、Go言語の設計哲学の一つである「明確なエラーメッセージによる開発者の支援」があります。より具体的で分かりやすいエラーメッセージを提供することで、開発者がGoのマップの動作原理をより深く理解し、適切なコードを書けるようにすることが目的です。Issue #13779でこの問題が報告され、その解決策としてエラーメッセージの改善が提案されました。

## 前提知識の解説

### Go言語のマップ（`map`）の動作

Go言語のマップは参照型ですが、マップから値を取得する際には、その値のコピーが返されます。例えば、`m[key]` のようにアクセスすると、`m` に格納されている `key` に対応する値のコピーが手元に渡されます。

```go
package main

import "fmt"

type Person struct {
    Age int
}

func main() {
    students := map[string]Person{
        "sally": {Age: 12},
    }

    // ここで students["sally"] は Person 型の値のコピーを返す
    // そのコピーの Age フィールドを変更しても、元のマップの値は変わらない
    // students["sally"].Age = 13 // これはコンパイルエラーになる
    
    // 正しい更新方法
    sally := students["sally"] // 値のコピーを取得
    sally.Age = 13             // コピーのフィールドを変更
    students["sally"] = sally  // 変更されたコピーをマップに書き戻す

    fmt.Println(students["sally"].Age) // 出力: 13
}
```

もしマップの値がポインタ型（例: `map[string]*Person`）であれば、マップから取得されるのはポインタのコピーであり、そのポインタが指す先の構造体は元のマップの値と同じ実体であるため、フィールドを直接変更できます。

```go
package main

import "fmt"

type Person struct {
    Age int
}

func main() {
    students := map[string]*Person{
        "sally": {Age: 12},
    }

    // ポインタのコピーが返されるが、そのポインタが指す先の構造体は同じ
    students["sally"].Age = 13 // これは有効な操作

    fmt.Println(students["sally"].Age) // 出力: 13
}
```

### Goコンパイラと抽象構文木（AST）

Goコンパイラは、ソースコードを解析して抽象構文木（AST: Abstract Syntax Tree）を構築します。ASTは、プログラムの構造を木構造で表現したものです。コンパイラは、このASTを走査しながら型チェックやコード生成などの処理を行います。

*   **`ODOT`**: ASTノードの一種で、構造体のフィールドアクセス（例: `obj.field`）を表します。
*   **`OINDEXMAP`**: ASTノードの一種で、マップのインデックスアクセス（例: `m[key]`）を表します。

このコミットの変更は、コンパイラの型チェックフェーズ (`typecheck.go`) で、ASTノードのパターンを識別することで実現されています。

## 技術的詳細

この変更は、Goコンパイラの型チェックを担当する `src/cmd/compile/internal/gc/typecheck.go` ファイル内の `checkassign` 関数に実装されています。

`checkassign` 関数は、代入文の左辺（LHS: Left-Hand Side）が有効な代入先であるかをチェックする役割を担っています。Go言語では、代入の左辺は「アドレス可能（addressable）」である必要があります。つまり、その値がメモリ上の特定の位置に存在し、そのアドレスを取得できる必要があります。

マップから取得した構造体の値は、前述の通りコピーであるため、一時的な値であり、アドレス可能ではありません。したがって、そのフィールドに直接代入することはできません。

このコミットでは、`checkassign` 関数内に新しい条件分岐が追加されました。

```go
if n.Op == ODOT && n.Left.Op == OINDEXMAP {
    Yyerror("cannot directly assign to struct field %v in map", n)
    return
}
```

この条件は、代入の左辺 `n` が以下の構造を持つ場合に真となります。

1.  `n.Op == ODOT`: `n` が構造体のフィールドアクセス（`.`演算子）である。
2.  `n.Left.Op == OINDEXMAP`: フィールドアクセスが行われている対象 (`n.Left`) が、マップのインデックスアクセス（`[]`演算子）の結果である。

つまり、`map[key].field` のような形式の代入を正確に識別しています。このパターンが検出された場合、コンパイラは `Yyerror` 関数を呼び出して、新しい、より具体的なエラーメッセージ「`cannot directly assign to struct field %v in map`」を出力します。`%v` には、代入しようとした具体的な式（例: `students["sally"].age`）が挿入されます。

この変更により、コンパイラは特定の無効な代入パターンをより詳細に識別し、開発者にとってより有益なフィードバックを提供できるようになりました。

## コアとなるコードの解説

追加されたコードブロックは、Goコンパイラの型チェックロジックの一部です。

`if n.Op == ODOT && n.Left.Op == OINDEXMAP { ... }`

この `if` 文は、代入の左辺 `n` が特定のAST構造を持っているかをチェックします。
*   `n.Op == ODOT`: `n` がドット演算子（`.`）によるフィールドアクセスを表すASTノードであることを意味します。例えば、`students["sally"].age` の `age` の部分がこれに該当します。
*   `n.Left.Op == OINDEXMAP`: `n` の左の子ノード（`n.Left`）が、マップのインデックスアクセス（`[]`演算子）を表すASTノードであることを意味します。例えば、`students["sally"]` の部分がこれに該当します。

この二つの条件が同時に真となる場合、それは「マップから取得した構造体のフィールドに直接代入しようとしている」という、Go言語では許可されない操作パターンを正確に捉えています。

`Yyerror("cannot directly assign to struct field %v in map", n)`

条件が真の場合、`Yyerror` 関数が呼び出され、コンパイルエラーが報告されます。`Yyerror` はコンパイラのエラー報告メカニズムの一部です。
エラーメッセージ文字列「`cannot directly assign to struct field %v in map`」は、以前の一般的なエラーメッセージよりもはるかに具体的です。`%v` プレースホルダーには、`n`（代入の左辺全体、例: `students["sally"].age`）がフォーマットされて挿入されます。これにより、開発者はどの部分のコードが問題を引き起こしているのか、そしてその根本的な理由（マップの値セマンティクス）をより容易に理解できます。

`return`

エラーが報告された後、`checkassign` 関数はすぐに処理を終了します。これにより、この特定の無効な代入に対する重複した、あるいは一般的なエラーメッセージの出力が避けられます。

この変更は、Goコンパイラがより「賢く」なり、開発者が遭遇する可能性のある一般的な落とし穴に対して、より的確なガイダンスを提供できるようになることを示しています。

このテストケースは、`students["sally"].age = 3` という行が、期待される新しいエラーメッセージ「`cannot directly assign to struct field .* in map`」を生成することを確認します。`errorcheck` ディレクティブは、コンパイラが指定されたエラーメッセージを出力するかどうかをテストフレームワークに指示します。

## コアとなるコードの解説

追加されたコードブロックは、Goコンパイラの型チェックロジックの一部です。

`if n.Op == ODOT && n.Left.Op == OINDEXMAP { ... }`

この `if` 文は、代入の左辺 `n` が特定のAST構造を持っているかをチェックします。
*   `n.Op == ODOT`: `n` がドット演算子（`.`）によるフィールドアクセスを表すASTノードであることを意味します。例えば、`students["sally"].age` の `age` の部分がこれに該当します。
*   `n.Left.Op == OINDEXMAP`: `n` の左の子ノード（`n.Left`）が、マップのインデックスアクセス（`[]`演算子）を表すASTノードであることを意味します。例えば、`students["sally"]` の部分がこれに該当します。

この二つの条件が同時に真となる場合、それは「マップから取得した構造体のフィールドに直接代入しようとしている」という、Go言語では許可されない操作パターンを正確に捉えています。

`Yyerror("cannot directly assign to struct field %v in map", n)`

条件が真の場合、`Yyerror` 関数が呼び出され、コンパイルエラーが報告されます。`Yyerror` はコンパイラのエラー報告メカニズムの一部です。
エラーメッセージ文字列「`cannot directly assign to struct field %v in map`」は、以前の一般的なエラーメッセージよりもはるかに具体的です。`%v` プレースホルダーには、`n`（代入の左辺全体、例: `students["sally"].age`）がフォーマットされて挿入されます。これにより、開発者はどの部分のコードが問題を引き起こしているのか、そしてその根本的な理由（マップの値セマンティクス）をより容易に理解できます。

`return`

エラーが報告された後、`checkassign` 関数はすぐに処理を終了します。これにより、この特定の無効な代入に対する重複した、あるいは一般的なエラーメッセージの出力が避けられます。

この変更は、Goコンパイラがより「賢く」なり、開発者が遭遇する可能性のある一般的な落とし穴に対して、より的確なガイダンスを提供できるようになることを示しています。

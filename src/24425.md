# [インデックス 24425] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける符号拡張の取り扱い方を根本的に変更するものです。特に、マシンレジスタのサイズよりも小さい整数型（例：`int8`, `int16`, `int32`）を扱う際のレジスタの上位ビットの挙動に関するポリシーが変更されています。

## コミット

```
[dev.ssa] cmd/compile/internal/ssa: redo how sign extension is handled

For integer types less than a machine register, we have to decide
what the invariants are for the high bits of the register.  We used
to set the high bits to the correct extension (sign or zero, as
determined by the type) of the low bits.

This CL makes the compiler ignore the high bits of the register
altogether (they are junk).

On this plus side, this means ops that generate subword results don't
have to worry about correctly extending them.  On the minus side,
ops that consume subword arguments have to deal with the input
registers not being correctly extended.

For x86, this tradeoff is probably worth it.  Almost all opcodes
have versions that use only the correct subword piece of their
inputs.  (The one big exception is array indexing.)  Not many opcodes
can correctly sign extend on output.

For other architectures, the tradeoff is probably not so clear, as
they don't have many subword-safe opcodes (e.g. 16-bit compare,
ignoring the high 16/48 bits).  Fortunately we can decide whether
we do this per-architecture.

For the machine-independent opcodes, we pretend that the "register"
size is equal to the type width, so sign extension is immaterial.
Opcodes that care about the signedness of the input (e.g. compare,
right shift) have two different variants.
```

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムを最適化された機械語に変換する上で重要な役割を担っています。このプロセスにおいて、CPUレジスタのサイズ（例えば64ビット）よりも小さい整数型（例えば`int8`や`int32`）を扱う際に、レジスタの未使用の上位ビットをどのように扱うかという問題がありました。

以前のGoコンパイラでは、これらの上位ビットは、元の整数型の値に応じて適切に符号拡張（signed extension）またはゼロ拡張（zero extension）されていました。これは、例えば`int8`の値を64ビットレジスタにロードする際に、その`int8`の最上位ビット（符号ビット）をレジスタの残りの上位ビットにコピーするか、あるいは`uint8`の場合には上位ビットを全てゼロで埋める、という処理を意味します。このアプローチは、値の正確性を保証する一方で、常に拡張処理を行うための追加の命令や複雑さを伴う可能性がありました。

このコミットの背景には、コンパイラの効率性と生成されるコードのパフォーマンスを向上させるという目的があります。特にx86アーキテクチャのような、サブワード（レジスタ幅より小さいデータ幅）操作に特化した命令が豊富な環境では、レジスタの上位ビットの厳密な管理が必ずしも最適ではない場合があります。上位ビットを「ジャンク」（無関係な値）として扱うことで、一部の操作で不要な拡張処理を省略し、コード生成を簡素化できる可能性があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **SSA (Static Single Assignment) 形式**:
    Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、SSA形式という中間表現に変換します。SSA形式では、全ての変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析が容易になり、様々なコンパイラ最適化（デッドコード削除、冗長なnilチェックの除去など）が効率的に行えます。SSAは、高レベルなASTと低レベルな機械語の間の橋渡し役となります。

2.  **符号拡張 (Sign Extension) とゼロ拡張 (Zero Extension)**:
    *   **符号拡張**: 符号付き整数型（例: `int8`）の値を、より広いビット幅の型（例: `int64`）に変換する際に、元の値の符号を保持するために行われる処理です。元の値の最上位ビット（符号ビット）を、新しい広いビット幅の上位ビットにコピーして埋めます。例えば、`int8`の`-1`（`11111111`）を`int16`に符号拡張すると`1111111111111111`となり、値は`-1`のままです。
    *   **ゼロ拡張**: 符号なし整数型（例: `uint8`）の値を、より広いビット幅の型（例: `uint64`）に変換する際に、新しい広いビット幅の上位ビットを全てゼロで埋める処理です。例えば、`uint8`の`255`（`11111111`）を`uint16`にゼロ拡張すると`0000000011111111`となり、値は`255`のままです。

3.  **サブワード操作 (Subword Operations)**:
    CPUのレジスタは通常、特定のビット幅（例: 64ビット）を持っていますが、プログラムではそれよりも小さいビット幅のデータ型（例: 8ビット、16ビット、32ビット整数）を扱うことがよくあります。これらの小さいデータ型に対する操作をサブワード操作と呼びます。コンパイラは、これらのサブワード操作を、CPUが提供する適切な命令にマッピングする必要があります。

4.  **Goコンパイラのバックエンド**:
    Goコンパイラのバックエンドは、SSA形式のコードをターゲットアーキテクチャ（例: AMD64）の機械語に変換します。この過程で、「Lowering（低レベル化）」と呼ばれるフェーズがあり、汎用的なSSA操作がアーキテクチャ固有の命令に変換されます。この変換ルールは、`AMD64.rules`のようなファイルに記述されています。

5.  **「レジスタの上位ビットはジャンク」という概念**:
    これは、コンパイラがレジスタの特定のビット幅（例えば、`int32`の値を格納する際の64ビットレジスタの上位32ビット）について、その内容が有効なデータではない、つまり「何が入っていても構わない」と見なすポリシーを指します。これにより、コンパイラは不要なゼロクリアや符号拡張の命令を省略でき、コード生成の効率を向上させることができます。ただし、このポリシーを採用する場合、そのレジスタの値を消費する側の操作は、必要な場合に自身で適切な拡張を行う責任を負うことになります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるレジスタの上位ビットの不変条件（invariants）の変更です。

**変更前のアプローチ**:
レジスタのサイズよりも小さい整数型（例: `int8`, `int16`, `int32`）を扱う際、コンパイラはレジスタの上位ビットを、その型のセマンティクス（符号付きか符号なしか）に従って、常に正しく符号拡張またはゼロ拡張していました。例えば、`int8`の値を64ビットレジスタにロードした場合、レジスタのビット0-7に`int8`の値が入り、ビット8-63にはビット7（符号ビット）がコピーされていました。`uint8`の場合、ビット8-63はゼロで埋められていました。

**変更後のアプローチ**:
このコミットにより、コンパイラはレジスタの上位ビットを「ジャンク」（無効な、または無関係なデータ）として扱うようになります。つまり、サブワードの結果を生成する操作（例: `int8`の加算結果をレジスタに格納する）は、その結果を正しく拡張する責任を負う必要がなくなります。レジスタの低位ビットに正しい値が入っていれば十分であり、上位ビットの内容は保証されません。

この変更にはトレードオフがあります。

*   **利点**:
    *   サブワードの結果を生成する操作（例: `ADDB`命令で8ビットの加算を行う）は、結果をレジスタの全幅にわたって正しく拡張する手間を省くことができます。これにより、コンパイラのコード生成ロジックが簡素化され、生成される命令数も削減される可能性があります。

*   **欠点**:
    *   サブワードの引数を消費する操作（例: `int8`の値を引数として受け取り、それを使って`int64`の演算を行う）は、入力レジスタが正しく拡張されていない可能性があるため、自身で適切な符号拡張またはゼロ拡張を行う必要があります。

**アーキテクチャごとの考慮事項**:

*   **x86アーキテクチャ**:
    コミットメッセージによると、x86アーキテクチャではこのトレードオフは「おそらく価値がある」とされています。これは、x86の命令セットには、入力のサブワード部分のみを使用する（上位ビットを無視する）多くの命令が存在するためです。例えば、`ADDL`命令は32ビットの加算を行い、64ビットレジスタの上位32ビットは変更しません。しかし、出力で正しく符号拡張を行う命令は多くありません。配列インデックス処理は、この新しいポリシーの大きな例外として挙げられています。配列インデックスはポインタ演算に変換されるため、レジスタの全幅にわたって正しく拡張された値が必要となるため、`extendIndex`関数が導入されています。

*   **その他のアーキテクチャ**:
    x86以外のアーキテクチャでは、サブワードセーフな命令（入力のサブワード部分のみを使用する命令）が少ない場合があり、このトレードオフが明確ではない可能性があります。しかし、Goコンパイラはアーキテクチャごとにこのポリシーを決定できる柔軟性を持っています。

**機械独立なSSA操作**:
機械独立なSSA操作（`genericOps.go`などで定義される）については、「レジスタサイズが型幅に等しい」と仮定することで、符号拡張の問題は本質的に無関係になります。ただし、入力の符号を気にする操作（比較、右シフトなど）は、符号付きと符号なしの2つの異なるバリアントを持つことになります。これにより、コンパイラは適切なセマンティクスを維持できます。

この変更は、SSA形式における型の表現と、それらが機械語に「Lowering」される際のルールに大きな影響を与えます。特に、`src/cmd/compile/internal/gc/ssa.go`における型変換（`OCONV`）の処理が大幅に書き換えられ、明示的な符号拡張（`SignExt`）およびゼロ拡張（`ZeroExt`）のSSA操作が導入されています。また、`src/cmd/compile/internal/ssa/gen/AMD64.rules`では、以前は`MOVWQSX (ADDW <v.Type> x y)`のように演算結果を符号拡張していたルールが、単に`ADDW x y`のように変更され、拡張処理が省略されています。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、その中でのコアとなる変更箇所は以下の通りです。

1.  **`src/cmd/compile/internal/gc/ssa.go`**:
    *   `ssaOp`関数の変更: `TINT`, `TUINT`, `TUINTPTR`などの型を、`config.IntSize`や`config.PtrSize`に基づいて具体的なサイズ（`TINT32`, `TINT64`など）に解決する`concreteEtype`関数が導入されました。
    *   `expr`関数内の`OCONV`（型変換）処理の大幅な変更:
        *   以前は単一の`ssa.OpConvert`オペレーションで処理されていた型変換が、より詳細な`ssa.OpConvNop`、`ssa.OpTrunc`（切り捨て）、`ssa.OpSignExt`（符号拡張）、`ssa.OpZeroExt`（ゼロ拡張）の各オペレーションに分割されました。
        *   `ft.Size()`と`tt.Size()`（変換元と変換先の型のサイズ）に基づいて、適切な拡張または切り捨てのSSAオペレーションが選択されるようになりました。
    *   `expr`関数内の配列インデックス処理（`OINDEX`）および`addr`関数内のスライス/配列インデックス処理に`s.extendIndex(i)`の呼び出しが追加されました。これは、インデックス値がポインタサイズに拡張されることを保証します。
    *   `extendIndex`関数が新しく追加されました。この関数は、与えられたSSA値（インデックス）をポインタサイズに符号拡張またはゼロ拡張します。

2.  **`src/cmd/compile/internal/ssa/config.go`**:
    *   `Config`構造体に`IntSize`フィールドが追加され、ターゲットアーキテクチャのデフォルトの整数サイズ（32ビットまたは64ビット）を保持するようになりました。
    *   `NewConfig`関数で、アーキテクチャ（`amd64`, `386`など）に基づいて`IntSize`が設定されるようになりました。

3.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`**:
    *   コメントが変更され、「Integer types live in the low portion of registers. Upper portions are correctly extended.」から「Integer types live in the low portion of registers. Upper portions are junk.」に変わりました。これは、レジスタ上位ビットのポリシー変更を明確に示しています。
    *   `Add`, `And`, `Sub`, `Neg`, `Mul`などの多くの演算ルールから、`U`サフィックス（`Add64U`など）を持つ符号なし演算が削除されました。これは、機械独立なSSA操作が符号付き/符号なしの区別をレジスタ上位ビットの拡張に依存しなくなったためです。
    *   以前は演算結果を`MOVWQSX`（符号拡張）などで囲んでいたルールが、直接`ADDW`などのサブワード命令を生成するように変更されました。
    *   `SignExt`、`ZeroExt`、`Trunc`の新しいSSAオペレーションに対するAMD64固有のルールが追加されました。例えば、`(SignExt8to16 x) -> (MOVBQSX x)`のように、明示的な拡張命令にマッピングされます。
    *   `(Trunc16to8 x) -> (Copy x)`のように、切り捨て操作が単なるコピーとして扱われるようになりました。これは、上位ビットがジャンクであるため、切り捨ては実質的に何もしないことを意味します。

4.  **`src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/opGen.go`**:
    *   `Add8U`, `Add16U`, `Add32U`, `Add64U`などの符号なし演算のSSAオペレーションが削除されました。
    *   `Convert`オペレーションが削除され、代わりに`SignExt`、`ZeroExt`、`Trunc`の各オペレーションが追加されました。

5.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`**:
    *   `rewriteValueAMD64`関数内で、`OpAdd16`, `OpAdd32`, `OpAdd8`, `OpAnd16`, `OpAnd32`, `OpAnd8`, `OpMul16`, `OpMul32`, `OpMul8`, `OpNeg16`, `OpNeg32`, `OpNeg8`, `OpSub16`, `OpSub32`, `OpSub8`などの多くの演算の書き換えルールが変更されました。以前は演算結果を`MOVWQSX`などで囲んで符号拡張していましたが、新しいルールでは直接`ADDW`などのサブワード命令を生成し、拡張処理を省略しています。
    *   `OpConvert`の書き換えルールが削除され、`OpConvNop`のルールが変更されました。
    *   `OpSignExt*`および`OpZeroExt*`の新しいSSAオペレーションに対する書き換えルールが追加され、対応するAMD64の符号拡張/ゼロ拡張命令（`MOVBQSX`, `MOVWQSX`, `MOVLQSX`, `MOVBQZX`, `MOVWQZX`, `MOVLQZX`）にマッピングされるようになりました。
    *   `OpTrunc*`の新しいSSAオペレーションに対する書き換えルールが追加され、`Copy`オペレーションにマッピングされるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、GoコンパイラのSSA中間表現における整数型の「値」の定義と、それが機械語に変換される際の「Lowering」ルールにあります。

以前は、`int8`のようなサブワード整数型がレジスタにロードされると、そのレジスタの全幅にわたって値が正しく拡張されることが保証されていました。例えば、`int8`の変数`x`が`0xFF`（-1）である場合、64ビットレジスタにロードされると、レジスタ全体が`0xFFFFFFFFFFFFFFFF`となるように符号拡張されていました。

新しいアプローチでは、この保証がなくなります。`int8`の`x`が`0xFF`である場合、64ビットレジスタの低位8ビットには`0xFF`が入りますが、上位56ビットには何が入っているか保証されません（「ジャンク」）。

この変更の具体的な影響は、`src/cmd/compile/internal/gc/ssa.go`の`OCONV`処理と、`src/cmd/compile/internal/ssa/gen/AMD64.rules`および`src/cmd/compile/internal/ssa/rewriteAMD64.go`のルールに顕著に現れています。

**`src/cmd/compile/internal/gc/ssa.go`の`OCONV`処理**:
型変換（`OCONV`）は、以前は単一の`ssa.OpConvert`で抽象的に扱われていましたが、この変更により、変換元と変換先の型のサイズと符号に応じて、より具体的なSSAオペレーション（`OpSignExt8to16`, `OpZeroExt32to64`, `OpTrunc64to8`など）が明示的に生成されるようになりました。これにより、コンパイラはどの時点でどのような拡張/切り捨てが必要かを正確に把握し、後続のLoweringフェーズで適切な機械語命令を選択できるようになります。

**`extendIndex`関数の導入**:
配列やスライスのインデックスは、ポインタ演算に使用されるため、ポインタのサイズ（32ビットまたは64ビット）に一致する必要があります。インデックスがポインタサイズよりも小さい型である場合、その値はポインタサイズに拡張される必要があります。`extendIndex`関数は、この拡張処理をカプセル化し、インデックスが符号付きであれば符号拡張、符号なしであればゼロ拡張を行います。これは、レジスタの上位ビットがジャンクになった新しいポリシーの下で、インデックスの正確性を保証するために不可欠な変更です。

**`src/cmd/compile/internal/ssa/gen/AMD64.rules`と`src/cmd/compile/internal/ssa/rewriteAMD64.go`の変更**:
これらのファイルでは、AMD64アーキテクチャ固有のSSAルールが定義されています。以前は、例えば`Add16`（16ビット加算）のような操作は、結果を`MOVWQSX`（16ビットから64ビットへの符号拡張）で囲んでいました。これは、演算結果がレジスタの全幅にわたって正しく拡張されることを保証するためです。しかし、新しいポリシーでは上位ビットがジャンクであるため、この`MOVWQSX`は不要となり、ルールは単に`ADDW`（16ビット加算）を生成するように簡素化されました。

一方で、`SignExt*`や`ZeroExt*`といった明示的な拡張オペレーションが導入されたことで、これらのオペレーションはAMD64の`MOVBQSX`（バイトからクワッドワードへの符号拡張）や`MOVLQZX`（ロングワードからクワッドワードへのゼロ拡張）といった専用の命令にマッピングされるようになりました。これにより、必要な場所でのみ拡張処理が行われ、不要な場所では省略されるという、より効率的なコード生成が可能になります。

この変更は、GoコンパイラのSSAバックエンドの設計思想における重要な進化を示しており、レジスタの利用効率とコード生成の柔軟性を向上させることを目的としています。

# [インデックス 20737] ファイルの概要

このコミットは、Go言語の386アーキテクチャ向けリンカである `cmd/8l` における、`R_386_GOT32` リロケーションタイプの取り扱いに関する修正です。具体的には、`push` 命令における `R_386_GOT32` リロケーションが正しく処理されるように変更が加えられました。

## 元コミット内容

`cmd/8l: accept R_386_GOT32 in push instruction`

このコミットは、`cmd/8l` リンカが `push` 命令内で `R_386_GOT32` リロケーションタイプを適切に処理できるようにするものです。これにより、Issue #8382 で報告された問題が修正されます。

## 変更の背景

Go言語のリンカ `cmd/8l` は、32ビットx86アーキテクチャ（i386）向けのバイナリを生成します。動的リンクを使用するプログラムでは、共有ライブラリ内のシンボル（関数やデータ）への参照を解決するためにリロケーションという仕組みが用いられます。`R_386_GOT32` は、Global Offset Table (GOT) を介してシンボルを参照するためのリロケーションタイプです。

以前の `cmd/8l` の実装では、`MOVL` (Move Long) 命令に対する `R_386_GOT32` リロケーションは適切に処理されていました。`MOVL` 命令は、メモリからレジスタへ値をロードする際などに使用されます。しかし、`PUSHL` (Push Long) 命令、つまりスタックに値をプッシュする命令に対する `R_386_GOT32` リロケーションが正しく処理されていませんでした。

この不整合により、特定の条件下で `PUSHL` 命令が `R_386_GOT32` リロケーションを伴う場合に、リンカが「unexpected GOT reloc for non-dynamic symbol」という診断メッセージを出力し、正しくリンクできない問題が発生していました。これは、リンカが `PUSHL` 命令のコンテキストで `R_386_GOT32` を処理するロジックを欠いていたためです。

このコミットは、この問題を解決し、`PUSHL` 命令に対しても `R_386_GOT36` リロケーションが正しく適用されるようにリンカの動作を拡張することを目的としています。

## 前提知識の解説

*   **リンカ (`cmd/8l`)**: Go言語のツールチェインの一部であり、コンパイルされたオブジェクトファイルを結合して実行可能ファイルや共有ライブラリを生成するプログラムです。`8l` は386アーキテクチャ（32ビットx86）を対象とするリンカを指します。
*   **リロケーション**: プログラムがロードされる際に、コード内のアドレス参照を実際のメモリ上のアドレスに調整するプロセスです。特に動的リンクでは、共有ライブラリがロードされるメモリ上の位置が実行時まで分からないため、リロケーション情報に基づいてアドレスが修正されます。
*   **`R_386_GOT32`**: 32ビットx86アーキテクチャにおけるリロケーションタイプの一つです。これは、Global Offset Table (GOT) を介してシンボルを参照するために使用されます。GOTは、共有ライブラリ内の外部シンボルへの参照を解決するためのテーブルであり、Position-Independent Code (PIC) の実現に不可欠です。`R_386_GOT32` は、GOT内のエントリへのオフセットを計算するために使用されます。
*   **Global Offset Table (GOT)**: 動的リンクされたプログラムにおいて、外部の共有ライブラリ内の関数やデータへの参照を解決するために使用されるテーブルです。PICでは、コードがメモリ上のどこにロードされても実行できるように、直接的な絶対アドレス参照を避けます。代わりに、GOT内のエントリを介して間接的に外部シンボルを参照します。実行時に動的リンカがGOTエントリを実際のシンボルアドレスで埋めます。
*   **`MOVL` (Move Long)**: x86アセンブリ命令の一つで、32ビットの値を移動（コピー）します。例えば、`MOVL $0x12345678, %eax` は即値 `0x12345678` を `eax` レジスタに移動します。
*   **`LEAL` (Load Effective Address Long)**: x86アセンブリ命令の一つで、オペランドの「実効アドレス」を計算し、その結果をレジスタにロードします。これは、メモリの内容を読み込むのではなく、アドレス自体を計算してレジスタに入れるため、アドレス計算に非常に便利です。例えば、`LEAL (%ebx,%ecx,4), %eax` は `ebx + ecx * 4` のアドレスを計算し、その結果を `eax` に格納します。
*   **`PUSHL` (Push Long)**: x86アセンブリ命令の一つで、32ビットの値をスタックにプッシュします。例えば、`PUSHL %eax` は `eax` レジスタの値をスタックにプッシュします。
*   **オペコード (Opcode)**: CPUが実行する命令のバイナリコードです。例えば、`MOVL` 命令の特定の形式には `0x8b` というオペコードが、`LEAL` 命令の特定の形式には `0x8d` というオペコードが対応します。`PUSHL` 命令の特定の形式には `0xff` と `0xb3` の組み合わせが使われることがあります。

## 技術的詳細

このコミットの核心は、`adddynrel` 関数における `R_386_GOT32` リロケーションの処理ロジックの拡張です。`adddynrel` 関数は、動的リロケーションを追加する際に呼び出されます。

既存のコードでは、`R_386_GOT32` リロケーションが非動的シンボル（つまり、同じバイナリ内で定義されているシンボル）に対して適用される場合、リンカは `MOVL` 命令（オペコード `0x8b`）を `LEAL` 命令（オペコード `0x8d`）に変換していました。これは、GOTを介して間接的に参照する代わりに、シンボル自体のアドレスを直接ロードするように命令を書き換えることで、不要な間接参照を排除し、パフォーマンスを向上させるための最適化です。

しかし、`PUSHL` 命令に対する同様の最適化が欠けていました。`PUSHL` 命令は、`0xff` (PUSH/POP/CALL/JMP indirect) と `0xb3` (ModR/Mバイトの一部で、レジスタ間接アドレッシングを示す) の組み合わせで表現されることがあります。このコミットでは、`PUSHL` 命令が `R_386_GOT32` リロケーションを伴う場合に、リンカがこれを認識し、`PUSHL` 命令をシンボル自体のアドレスをプッシュするように変換するロジックが追加されました。

具体的には、以下の変換が行われます：

1.  **`MOVL` から `LEAL` への変換 (既存のロジック)**:
    *   元の命令のオペコードが `0x8b` (MOVL) であれば、それを `0x8d` (LEAL) に変更します。
    *   リロケーションタイプを `R_GOTOFF` に変更します。これは、GOTからのオフセットではなく、シンボル自体へのオフセットとして扱われることを示します。

2.  **`PUSHL` から `PUSHL` (直接アドレス) への変換 (新規追加ロジック)**:
    *   元の命令のオペコードが `0xff` と `0xb3` の組み合わせ (PUSHL) であれば、それを `0x36` (SSセグメントプレフィックス) と `0x68` (PUSHL immediate) の組み合わせに変更します。
    *   `0x36` は通常不要なSSセグメントプレフィックスですが、命令の長さを維持するために使用されます。これにより、命令のバイト数が変わらず、コードの再配置が容易になります。
    *   リロケーションタイプを `R_ADDR` に変更します。これは、シンボルの絶対アドレスを直接プッシュすることを示します。

この変更により、リンカは `PUSHL` 命令に対する `R_386_GOT32` リロケーションを適切に処理できるようになり、非動的シンボルへの参照が最適化され、リンカのエラーが解消されます。

## コアとなるコードの変更箇所

変更は `src/cmd/8l/asm.c` ファイルの `adddynrel` 関数内で行われています。

```diff
--- a/src/cmd/8l/asm.c
+++ b/src/cmd/8l/asm.c
@@ -117,13 +117,21 @@ adddynrel(LSym *s, Reloc *r)
 	case 256 + R_386_GOT32:
 		if(targ->type != SDYNIMPORT) {
 			// have symbol
-			// turn MOVL of GOT entry into LEAL of symbol itself
-			if(r->off < 2 || s->p[r->off-2] != 0x8b) {
-				diag("unexpected GOT reloc for non-dynamic symbol %s", targ->name);
+			if(r->off >= 2 && s->p[r->off-2] == 0x8b) {
+				// turn MOVL of GOT entry into LEAL of symbol address, relative to GOT.
+				s->p[r->off-2] = 0x8d;
+				r->type = R_GOTOFF;
 				return;
 			}
-			s->p[r->off-2] = 0x8d;
-			r->type = R_GOTOFF;
+			if(r->off >= 2 && s->p[r->off-2] == 0xff && s->p[r->off-1] == 0xb3) {
+				// turn PUSHL of GOT entry into PUSHL of symbol itself.
+				// use unnecessary SS prefix to keep instruction same length.
+				s->p[r->off-2] = 0x36;
+				s->p[r->off-1] = 0x68;
+				r->type = R_ADDR;
+				return;
+			}
+			diag("unexpected GOT reloc for non-dynamic symbol %s", targ->name);
 			return;
 		}
 		addgotsym(ctxt, targ);
```

## コアとなるコードの解説

変更された `adddynrel` 関数は、`R_386_GOT32` リロケーションを処理する部分です。

1.  **`case 256 + R_386_GOT32:`**: この `case` 文は、リロケーションタイプが `R_386_GOT32` である場合に実行されるコードブロックを示します。`256` は、Goリンカ内部でリロケーションタイプを識別するためのオフセットです。
2.  **`if(targ->type != SDYNIMPORT)`**: この条件は、リロケーションの対象となるシンボル (`targ`) が動的にインポートされたシンボルではない（つまり、同じバイナリ内で定義されている）場合に真となります。この最適化は、非動的シンボルに対してのみ適用されます。
3.  **既存の `MOVL` 処理**:
    *   `if(r->off >= 2 && s->p[r->off-2] == 0x8b)`: これは、リロケーションのオフセット `r->off` から2バイト前の命令が `MOVL` 命令のオペコード `0x8b` であるかをチェックします。`r->off-2` は、リロケーションが適用されるアドレスの直前の命令の開始位置を指します。
    *   `s->p[r->off-2] = 0x8d;`: `MOVL` のオペコード `0x8b` を `LEAL` のオペコード `0x8d` に書き換えます。
    *   `r->type = R_GOTOFF;`: リロケーションタイプを `R_GOTOFF` に変更します。
    *   `return;`: 処理を終了します。
4.  **新規追加の `PUSHL` 処理**:
    *   `if(r->off >= 2 && s->p[r->off-2] == 0xff && s->p[r->off-1] == 0xb3)`: これは、リロケーションのオフセット `r->off` から2バイト前の命令が `0xff`、そして1バイト前の命令が `0xb3` であるかをチェックします。この組み合わせは、特定の形式の `PUSHL` 命令のオペコードとModR/Mバイトに相当します。
    *   `s->p[r->off-2] = 0x36;`: `0xff` を `0x36` (SSセグメントプレフィックス) に書き換えます。
    *   `s->p[r->off-1] = 0x68;`: `0xb3` を `0x68` (PUSHL immediate) に書き換えます。これにより、`PUSHL` 命令が即値をプッシュする形式に変わります。
    *   `r->type = R_ADDR;`: リロケーションタイプを `R_ADDR` に変更します。これは、シンボルの絶対アドレスを直接プッシュすることを示します。
    *   `return;`: 処理を終了します。
5.  **エラーハンドリング**:
    *   上記のいずれの `if` 条件にも合致しない場合、つまり `MOVL` でも `PUSHL` でもない命令に対して `R_386_GOT32` リロケーションが適用された場合、`diag("unexpected GOT reloc for non-dynamic symbol %s", targ->name);` という診断メッセージを出力し、エラーとして扱います。

この変更により、リンカは `PUSHL` 命令に対する `R_386_GOT32` リロケーションを適切に処理し、非動的シンボルへの参照を最適化できるようになりました。

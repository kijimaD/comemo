# [インデックス 28248] ファイルの概要

このコミットでは、Goコンパイラの`src/cmd/compile/internal/gc/order.go`ファイルと、バグ修正を検証するための新しいテストファイル`test/fixedbugs/issue14678.go`が変更されています。

## コミット

このコミットは、Goコンパイラが`OAS2DOTTYPE`（型アサーションと代入を組み合わせた操作）において、マップへの代入を正しく処理するように修正します。以前は、`OAS2DOTTYPE`式でブール型の結果をマップエントリに代入しようとすると、コンパイル時に問題が発生していました。これは、スライスエントリとは異なり、マップエントリがメモリ上で直接アドレス指定できないためです。この修正では、ブール型の代入先ノードの順序付けを適切に行い、マップエントリが`autotmp`（自動生成される一時変数）を介して設定されるようにすることで、この問題を解決しています。

## 変更の背景

この変更は、Go言語のコンパイラにおける特定のバグを修正するために導入されました。具体的には、`interface{}`型の変数を型アサーションし、その結果を複数の変数（例えば、値と成功を示すブール値）に代入する際に、その代入先の一つがマップのエントリである場合に問題が発生していました。

Go言語では、`i.(T)`のような型アサーションは、成功した場合は`T`型の値と`true`を、失敗した場合は`T`型のゼロ値と`false`を返します。これを`v, ok = i.(T)`のように複数の変数に代入することができます。

問題は、`ok`のようなブール値がマップのエントリ（例: `m[key]`）に直接代入される場合に顕在化しました。マップのエントリは、スライスや配列のエントリとは異なり、メモリ上で直接アドレス指定可能な場所ではありません。マップへの書き込みは、内部的にはハッシュ計算とデータ構造の操作を伴う関数呼び出しとして処理されます。

コンパイラの`order.go`ファイルは、Goのソースコードを中間表現に変換し、実行順序を決定する役割を担っています。以前の実装では、`OAS2DOTTYPE`の処理において、マップエントリへの直接代入を試みてしまい、これがコンパイルエラーや不正なコード生成の原因となっていました。このバグは、Go issue #14678として報告されていました。

## 前提知識の解説

### Goコンパイラのフェーズと`order.go`

Goコンパイラは、ソースコードを機械語に変換するまでに複数のフェーズを経ます。主要なフェーズには、字句解析、構文解析、型チェック、中間コード生成、最適化、コード生成などがあります。
`src/cmd/compile/internal/gc/order.go`ファイルは、主に「順序付け（ordering）」フェーズの一部を担当します。このフェーズでは、式の評価順序を決定し、必要に応じて一時変数（`autotmp`）を導入して、複雑な式を単純な操作のシーケンスに分解します。これにより、後続のコード生成フェーズが処理しやすい形に中間表現が整理されます。

### `OAS2DOTTYPE`

`OAS2DOTTYPE`は、Goコンパイラ内部で使われるノードタイプの一つで、`v, ok = i.(T)`のような2値代入を伴う型アサーションを表します。
*   `i.(T)`: インターフェース値`i`が型`T`を保持しているかをチェックし、保持していればその値と`true`を、そうでなければ`T`のゼロ値と`false`を返します。
*   `v, ok = ...`: この2つの戻り値をそれぞれ`v`と`ok`に代入します。

### マップの動作とアドレス指定可能性

Goのマップ（`map[K]V`）は、キーと値のペアを格納するハッシュテーブルとして実装されています。マップのエントリ（例: `m[key]`）は、その性質上、メモリ上の固定されたアドレスに直接対応していません。マップへの値の読み書きは、内部的にはランタイム関数（例: `mapaccess`、`mapassign`）を介して行われます。
これに対し、スライスや配列のエントリ（例: `s[index]`）は、基盤となる配列の特定のアドレスに直接対応するため、アドレス指定可能です。
この「アドレス指定可能性」の違いが、今回のバグの根本原因でした。コンパイラがマップエントリを直接アドレス指定可能な変数と同様に扱おうとしたため、問題が発生したのです。

### `autotmp`変数

`autotmp`（automatic temporary variable）は、Goコンパイラが複雑な式の評価中に中間結果を一時的に保持するために自動的に生成する変数です。例えば、関数呼び出しの戻り値や、複数の操作が連鎖する式の中間結果を格納するために使用されます。これにより、式の評価順序を明確にし、コード生成を簡素化できます。今回の修正では、マップエントリへの代入を`autotmp`を介して行うことで、直接アドレス指定できないという問題を回避しています。

## 技術的詳細

このコミットの技術的詳細の中心は、Goコンパイラの`order.go`ファイル内の`orderstmt`関数における`OAS2DOTTYPE`ノードの処理方法の変更です。

### 以前の問題点

`OAS2DOTTYPE`ノードは、`n.List`に代入先の変数リストを、`n.Rlist.First().Left`に型アサーションの対象となる式（例: `i.(T)`）を保持しています。
以前の実装では、`n.List.First()`（型アサーションの結果の値）がブランク識別子（`_`）でない場合、コンパイラは以下のような処理を行っていました。

1.  型アサーションの結果の型に基づいて一時変数`tmp1`を生成。
2.  `OAS2DOTTYPE`ノード自体を`order.out`に追加。
3.  `n.List.First()`（実際の代入先）に`tmp1`を代入する`OAS`（代入）ノードを生成。
4.  この`OAS`ノードを`ordermapassign`で処理。
5.  `n.List`を`tmp1`と`n.List.Second()`（ブール値の代入先）に書き換える。

このアプローチは、`n.List.Second()`（ブール値の代入先）がマップエントリである場合に問題を引き起こしました。`ordermapassign`は、マップエントリへの代入を適切に処理するための関数ですが、`n.List.First()`に`tmp1`を代入する際に、`n.List.Second()`がまだ「生の」マップエントリノードのままであり、その評価順序が適切に制御されていませんでした。特に、`n.List.Second()`がマップエントリである場合、そのエントリは直接アドレス指定できないため、`ordermapassign`が期待する形式で処理できませんでした。結果として、コンパイルエラーが発生するか、不正なコードが生成される可能性がありました。

### 修正後のアプローチ

修正後のコードでは、この問題を解決するために、代入先の処理順序をより厳密に制御しています。

1.  まず、`n.List.Slice()`で代入先のノードリストを取得し、`results`スライスに格納します。
2.  `assigns`という2つの`*Node`を保持する配列を宣言します。これは、最終的な代入操作を一時的に保持するためです。
3.  `results`スライスをループし、各代入先`res`についてチェックします。
    *   もし`res`がブランク識別子（`_`）でない場合、その型に応じた一時変数（`ordertemp`）を生成し、`results[r]`をこの一時変数に置き換えます。
    *   同時に、実際の代入先`res`にこの一時変数を代入する`OAS`ノード（例: `res = temp_var`）が作成され、`assigns[r]`に保存されます。
4.  `order.out = append(order.out, n)`を実行し、`OAS2DOTTYPE`ノード自体を`order`リストに追加します。この時点では、`n.List`は一時変数への代入を指すように変更されています。つまり、型アサーションの結果はまず一時変数に格納されます。
5.  次に、`assigns`配列をループします。
    *   `assign`ノードが`nil`でない場合（つまり、ブランク識別子でない代入先があった場合）、その`assign`ノードを`typecheck`し、`ordermapassign`で処理します。

この新しいアプローチの重要な点は、型アサーションの結果をまず一時変数に格納し、その後に、一時変数から実際の代入先（マップエントリを含む）への代入を独立したステップとして処理する点です。これにより、マップエントリへの代入が`ordermapassign`によって適切に処理されることが保証され、マップエントリが直接アドレス指定できないという問題が回避されます。`autotmp`変数が、マップエントリへの間接的な書き込みを可能にする「橋渡し」の役割を果たします。

## コアとなるコードの解説

変更された`order.go`の`orderstmt`関数内の`OAS2DOTTYPE`ケースは、型アサーションの2値代入（例: `val, ok = interfaceVar.(Type)`）のコンパイル時の処理フローを再構築しています。

**変更前:**
以前のコードは、代入先の最初の要素（`n.List.First()`）がブランク識別子でない場合に、その要素に対して直接的な代入処理を試みていました。特に、ブール値の代入先（`n.List.Second()`）がマップエントリである場合、そのマップエントリは直接アドレス指定できないため、`ordermapassign`が正しく機能せず、問題が発生していました。

**変更後:**
新しいコードは、より汎用的で堅牢なアプローチを採用しています。

1.  **代入先の一時変数化:**
    ```go
    		results := n.List.Slice()
    		var assigns [2]*Node
    
    		for r, res := range results {
    			if !isblank(res) {
    				results[r] = ordertemp(res.Type, order, haspointers(res.Type))
    				assigns[r] = Nod(OAS, res, results[r])
    			}
    		}
    ```
    *   `n.List.Slice()`で、型アサーションの戻り値を受け取る変数（`val`と`ok`に相当）のリストを取得します。
    *   `assigns`配列は、後で実行される実際の代入操作（一時変数から最終的な代入先への代入）を保持するために使用されます。
    *   `for`ループ内で、各代入先`res`がブランク識別子（`_`）でない場合、その型に応じた一時変数（`ordertemp`）を生成します。
    *   `results[r]`（つまり、`n.List`内の元の代入先ノード）は、この新しく生成された一時変数に置き換えられます。これにより、`OAS2DOTTYPE`ノード自体は、型アサーションの結果を一時変数に格納する操作として扱われるようになります。
    *   同時に、元の代入先`res`に一時変数`results[r]`を代入する`OAS`ノード（例: `m[1] = tmp_bool`）が作成され、`assigns[r]`に保存されます。

2.  **`OAS2DOTTYPE`ノードの処理:**
    ```go
    		order.out = append(order.out, n)
    ```
    この行は、変更された`n`（型アサーションの結果を一時変数に格納するノード）を`order`リストに追加します。このステップで、型アサーションの評価と、その結果の一時変数への格納が完了します。

3.  **実際の代入の実行:**
    ```go
    		for _, assign := range assigns {
    			if assign != nil {
    				assign = typecheck(assign, Etop)
    				ordermapassign(assign, order)
    			}
    		}
    ```
    *   `assigns`配列をループし、保存されていた各代入ノード（`res = temp_var`）を取り出します。
    *   これらの代入ノードは`typecheck`され、その後`ordermapassign`関数によって処理されます。
    *   `ordermapassign`は、代入先がマップエントリである場合に、マップへの書き込みを適切に行うためのランタイム関数呼び出しに変換する役割を担います。一時変数を介することで、マップエントリが直接アドレス指定できないという問題が完全に回避され、コンパイラはマップへの代入を安全かつ正確に処理できるようになります。

この修正により、`OAS2DOTTYPE`のセマンティクスが正しく維持され、特にマップエントリへの代入を含むケースで、コンパイラが堅牢に動作するようになりました。

# [インデックス 21185] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）中のハングアップを修正するものです。具体的には、スタックの縮小（`shrinkstack`）処理とネットワークポーリング（`netpoll`）の間の競合状態によって発生する問題に対処しています。

## コミット

    runtime: fix hang in GC due to shrinkstack vs netpoll race

    During garbage collection, after scanning a stack, we think about
    shrinking it to reclaim some memory. The shrinking code (called
    while the world is stopped) checked that the status was Gwaiting
    or Grunnable and then changed the state to Gcopystack, to essentially
    lock the stack so that no other GC thread is scanning it.
    The same locking happens for stack growth (and is more necessary there).

            oldstatus = runtime·readgstatus(gp);
            oldstatus &= ~Gscan;
            if(oldstatus == Gwaiting || oldstatus == Grunnable)
                    runtime·casgstatus(gp, oldstatus, Gcopystack); // oldstatus is Gwaiting or Grunnable
            else
                    runtime·throw("copystack: bad status, not Gwaiting or Grunnable");

    Unfortunately, "stop the world" doesn't stop everything. It stops all
    normal goroutine execution, but the network polling thread is still
    blocked in epoll and may wake up. If it does, and it chooses a goroutine
    to mark runnable, and that goroutine is the one whose stack is shrinking,
    then it can happen that between readgstatus and casgstatus, the status
    changes from Gwaiting to Grunnable.

    casgstatus assumes that if the status is not what is expected, it is a
    transient change (like from Gwaiting to Gscanwaiting and back, or like
    from Gwaiting to Gcopystack and back), and it loops until the status
    has been restored to the expected value. In this case, the status has
    changed semi-permanently from Gwaiting to Grunnable - it won't
    change again until the GC is done and the world can continue, but the
    GC is waiting for the status to change back. This wedges the program.

    To fix, call a special variant of casgstatus that accepts either Gwaiting
    or Grunnable as valid statuses.

    Without the fix bug with the extra check+throw in casgstatus, the
    program below dies in a few seconds (2-10) with GOMAXPROCS=8
    on a 2012 Retina MacBook Pro. With the fix, it runs for minutes
    and minutes.

            "io"

            "net"

                            log.Fatal(err)
                    }
                    ch := make(chan net.Conn, 1)

                    c1.Write(make([]byte, 100))

            }

## 変更の背景

Goランタイムのガベージコレクション（GC）は、プログラムの実行を一時停止してメモリを回収する「Stop The World (STW)」フェーズを含みます。このSTWフェーズ中、GCはゴルーチンのスタックをスキャンし、場合によってはメモリを解放するためにスタックを縮小（`shrinkstack`）しようとします。

スタックの縮小処理では、対象のゴルーチンの状態を`Gcopystack`に変更することで、他のGCスレッドがそのスタックをスキャンしないようにロックします。この状態変更は、`runtime·readgstatus`で現在の状態を読み取り、その後`runtime·casgstatus`（Compare-And-Swap Goroutine Status）で状態をアトミックに更新することで行われます。

問題は、STWが「すべて」を停止させるわけではない点にありました。特に、ネットワークポーリングスレッド（`netpoll`）は、`epoll`などのシステムコールでブロックされており、STW中であってもウェイクアップして、特定のゴルーチンを`Grunnable`（実行可能）状態にマークする可能性があります。

もし、スタックを縮小しようとしているゴルーチンが`Gwaiting`（待機中）状態であり、`runtime·readgstatus`でその状態を読み取った直後、かつ`runtime·casgstatus`で状態を更新する前に、`netpoll`がそのゴルーチンを`Grunnable`に変更した場合、競合状態が発生しました。

従来の`runtime·casgstatus`の実装では、期待する`oldval`（この場合は`Gwaiting`）と現在のゴルーチン状態が一致しない場合、一時的な状態変化（例: `Gwaiting`から`Gscanwaiting`への遷移）と見なし、期待する状態に戻るまでループして待機する設計になっていました。しかし、`netpoll`によって`Gwaiting`から`Grunnable`に変わった状態は「半永続的」なものであり、GCが完了してSTWが解除されるまで`Gwaiting`に戻ることはありませんでした。

このため、`runtime·casgstatus`は無限ループに陥り、GCが完了せず、結果としてプログラム全体がハングアップするという深刻なバグが発生していました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。Goランタイムによってスケジューリングされます。
2.  **ガベージコレクション (GC)**: Goの自動メモリ管理機能です。不要になったメモリを自動的に回収し、再利用可能にします。
3.  **Stop The World (STW)**: GCの特定のフェーズで、すべてのアプリケーションゴルーチンの実行を一時的に停止する期間です。これにより、GCは一貫性のあるメモリ状態を確保し、安全にメモリをスキャン・回収できます。
4.  **ゴルーチンステータス (Goroutine Status)**: ゴルーチンは、そのライフサイクルにおいて様々な状態を取ります。このコミットに関連する主な状態は以下の通りです。
    *   `Gwaiting`: ゴルーチンがイベント（ネットワークI/O、チャネル操作など）を待機している状態。
    *   `Grunnable`: ゴルーチンが実行可能であり、スケジューラによってCPUに割り当てられるのを待っている状態。
    *   `Grunning`: ゴルーチンが現在CPU上で実行されている状態。
    *   `Gcopystack`: ゴルーチンのスタックがコピー中であることを示す状態。スタックの成長や縮小時に使用されます。
    *   `Gscan`: GCがゴルーチンのスタックをスキャン中であることを示すフラグ。
5.  **スタックの成長と縮小 (Stack Growth and Shrinkage)**: Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます。関数呼び出しが深くなるとスタックは成長し、関数から戻るとスタックは縮小される可能性があります。これにより、メモリ使用量を効率的に管理します。
6.  **ネットワークポーリング (Netpoll)**: GoランタイムのネットワークI/O処理の一部です。`epoll` (Linux), `kqueue` (macOS/FreeBSD), `IOCP` (Windows) などのOS固有の非同期I/Oメカニズムを利用して、複数のネットワーク接続からのイベントを効率的に監視します。`netpoll`スレッドは、I/Oイベントが発生した際に、待機中のゴルーチンを`Gwaiting`から`Grunnable`状態に遷移させ、スケジューラがそれらを再開できるようにします。
7.  **アトミック操作 (Atomic Operations)**: 複数のスレッドやゴルーチンが同時にアクセスする可能性のある共有データに対して、不可分（アトミック）な操作を行うことで、データの一貫性を保つための仕組みです。`Compare-And-Swap (CAS)`はその代表的な例で、特定のメモリ位置の値が期待する値と一致する場合にのみ、新しい値に更新します。Goランタイムでは、`runtime·cas`のような関数がこれを提供します。
8.  **`runtime·readgstatus(G *gp)`**: 指定されたゴルーチン`gp`の現在の状態を読み取るランタイム関数。
9.  **`runtime·casgstatus(G *gp, uint32 oldval, uint32 newval)`**: 指定されたゴルーチン`gp`の状態を`oldval`から`newval`へアトミックに変更しようとするランタイム関数。`oldval`と現在の状態が一致しない場合は、ループして再試行するロジックが含まれています。

## 技術的詳細

このバグの核心は、`runtime·casgstatus`の再試行ロジックが、`netpoll`による`Gwaiting`から`Grunnable`への状態遷移を適切に扱えなかったことにあります。

スタック縮小処理（`copystack`関数内）では、以下のようなロジックでゴルーチンの状態を`Gcopystack`に設定しようとしていました。

```c
oldstatus = runtime·readgstatus(gp);
oldstatus &= ~Gscan; // Gscanフラグを除去
if(oldstatus == Gwaiting || oldstatus == Grunnable)
        runtime·casgstatus(gp, oldstatus, Gcopystack); // oldstatusはGwaitingまたはGrunnable
else
        runtime·throw("copystack: bad status, not Gwaiting or Grunnable");
```

ここで、`runtime·readgstatus(gp)`が`Gwaiting`を返したとします。しかし、その直後に`netpoll`が介入し、同じゴルーチンを`Grunnable`に遷移させたとします。この場合、`runtime·casgstatus(gp, Gwaiting, Gcopystack)`が呼び出されますが、ゴルーチンの実際の状態は`Grunnable`であるため、`Gwaiting`とは一致しません。

`runtime·casgstatus`の内部では、以下のようなループが存在します。

```c
while(!runtime·cas(&gp->atomicstatus, oldval, newval)) {
    // ...
    // Help GC if needed.
    // ...
}
```

このループは、`gp->atomicstatus`が`oldval`（この例では`Gwaiting`）になるまで`runtime·cas`を再試行し続けます。しかし、`netpoll`によって`Grunnable`に遷移したゴルーチンは、GCが完了するまで`Gwaiting`に戻ることはありません。結果として、`runtime·casgstatus`は無限ループに陥り、GCの進行を妨げ、プログラム全体がデッドロック状態になりました。

この問題は、STWがネットワークI/Oを完全に停止させないというGoランタイムの設計上の特性と、`casgstatus`の再試行ロジックが特定の非同期状態遷移を考慮していなかったことの組み合わせによって引き起こされました。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/runtime/proc.c`**:

3.  **`src/runtime/stack.c`**:

#### `runtime·casgcopystack` の追加

```c
+static void
+badgstatusrunnable(void)
+{
+	runtime·throw("casgstatus: waiting for Gwaiting but is Grunnable");
+}
+
+// casgstatus(gp, oldstatus, Gcopystack), assuming oldstatus is Gwaiting or Grunnable.
+// Returns old status. Cannot call casgstatus directly, because we are racing with an
+// async wakeup that might come in from netpoll. If we see Gwaiting from the readgstatus,
+// it might have become Grunnable by the time we get to the cas. If we called casgstatus,
+// it would loop waiting for the status to go back to Gwaiting, which it never will.
+#pragma textflag NOSPLIT
+uint32
+runtime·casgcopystack(G *gp)
+{
+	uint32 oldstatus;
+
+	for(;;) {
+		oldstatus = runtime·readgstatus(gp) & ~Gscan;
+		if(oldstatus != Gwaiting && oldstatus != Grunnable)
+			runtime·throw("copystack: bad status, not Gwaiting or Grunnable");
+		if(runtime·cas(&gp->atomicstatus, oldstatus, Gcopystack))
+			break;
+	}
+	return oldstatus;
+}
```
この新しい関数`runtime·casgcopystack`が、このコミットの主要な修正点です。
*   `for(;;)`ループで無限に再試行します。
*   ループ内で`runtime·readgstatus(gp) & ~Gscan`を呼び出し、現在のゴルーチン状態を読み取ります。
*   読み取った`oldstatus`が`Gwaiting`でも`Grunnable`でもない場合、`runtime·throw`でパニックを発生させます。これは、スタックコピーの対象となるゴルーチンがこれらの状態のいずれかであるべきという前提に基づいています。
*   最も重要なのは、`runtime·cas(&gp->atomicstatus, oldstatus, Gcopystack)`です。ここで`oldstatus`として、**直前に読み取ったばかりの`Gwaiting`または`Grunnable`のいずれかの状態**を使用します。これにより、`readgstatus`と`cas`の間に状態が`Gwaiting`から`Grunnable`に変化した場合でも、`cas`が成功する可能性が生まれます。
*   `cas`が成功した場合、ループを抜けて元の`oldstatus`を返します。

このアプローチにより、`netpoll`による非同期な状態遷移を許容し、`casgstatus`が無限ループに陥ることを防ぎます。

## 変更の背景

Goランタイムのガベージコレクション（GC）は、プログラムの実行を一時停止してメモリを回収する「Stop The World (STW)」フェーズを含みます。このSTWフェーズ中、GCはゴルーチンのスタックをスキャンし、場合によってはメモリを解放するためにスタックを縮小（`shrinkstack`）しようとします。

スタックの縮小処理では、対象のゴルーチンの状態を`Gcopystack`に変更することで、他のGCスレッドがそのスタックをスキャンしないようにロックします。この状態変更は、`runtime·readgstatus`で現在の状態を読み取り、その後`runtime·casgstatus`（Compare-And-Swap Goroutine Status）で状態をアトミックに更新することで行われます。

問題は、STWが「すべて」を停止させるわけではない点にありました。特に、ネットワークポーリングスレッド（`netpoll`）は、`epoll`などのシステムコールでブロックされており、STW中であってもウェイクアップして、特定のゴルーチンを`Grunnable`（実行可能）状態にマークする可能性があります。

もし、スタックを縮小しようとしているゴルーチンが`Gwaiting`（待機中）状態であり、`runtime·readgstatus`でその状態を読み取った直後、かつ`runtime·casgstatus`で状態を更新する前に、`netpoll`がそのゴルーチンを`Grunnable`に変更した場合、競合状態が発生しました。

従来の`runtime·casgstatus`の実装では、期待する`oldval`（この場合は`Gwaiting`）と現在のゴルーチン状態が一致しない場合、一時的な状態変化（例: `Gwaiting`から`Gscanwaiting`への遷移）と見なし、期待する状態に戻るまでループして待機する設計になっていました。しかし、`netpoll`によって`Gwaiting`から`Grunnable`に変わった状態は「半永続的」なものであり、GCが完了してSTWが解除されるまで`Gwaiting`に戻ることはありませんでした。

このため、`runtime·casgstatus`は無限ループに陥り、GCが完了せず、結果としてプログラム全体がハングアップするという深刻なバグが発生していました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。Goランタイムによってスケジューリングされます。
2.  **ガベージコレクション (GC)**: Goの自動メモリ管理機能です。不要になったメモリを自動的に回収し、再利用可能にします。
3.  **Stop The World (STW)**: GCの特定のフェーズで、すべてのアプリケーションゴルーチンの実行を一時的に停止する期間です。これにより、GCは一貫性のあるメモリ状態を確保し、安全にメモリをスキャン・回収できます。
4.  **ゴルーチンステータス (Goroutine Status)**: ゴルーチンは、そのライフサイクルにおいて様々な状態を取ります。このコミットに関連する主な状態は以下の通りです。
    *   `Gwaiting`: ゴルーチンがイベント（ネットワークI/O、チャネル操作など）を待機している状態。
    *   `Grunnable`: ゴルーチンが実行可能であり、スケジューラによってCPUに割り当てられるのを待っている状態。
    *   `Grunning`: ゴルーチンが現在CPU上で実行されている状態。
    *   `Gcopystack`: ゴルーチンのスタックがコピー中であることを示す状態。スタックの成長や縮小時に使用されます。
    *   `Gscan`: GCがゴルーチンのスタックをスキャン中であることを示すフラグ。
5.  **スタックの成長と縮小 (Stack Growth and Shrinkage)**: Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます。関数呼び出しが深くなるとスタックは成長し、関数から戻るとスタックは縮小される可能性があります。これにより、メモリ使用量を効率的に管理します。
6.  **ネットワークポーリング (Netpoll)**: GoランタイムのネットワークI/O処理の一部です。`epoll` (Linux), `kqueue` (macOS/FreeBSD), `IOCP` (Windows) などのOS固有の非同期I/Oメカニズムを利用して、複数のネットワーク接続からのイベントを効率的に監視します。`netpoll`スレッドは、I/Oイベントが発生した際に、待機中のゴルーチンを`Gwaiting`から`Grunnable`状態に遷移させ、スケジューラがそれらを再開できるようにします。
7.  **アトミック操作 (Atomic Operations)**: 複数のスレッドやゴルーチンが同時にアクセスする可能性のある共有データに対して、不可分（アトミック）な操作を行うことで、データの一貫性を保つための仕組みです。`Compare-And-Swap (CAS)`はその代表的な例で、特定のメモリ位置の値が期待する値と一致する場合にのみ、新しい値に更新します。Goランタイムでは、`runtime·cas`のような関数がこれを提供します。
8.  **`runtime·readgstatus(G *gp)`**: 指定されたゴルーチン`gp`の現在の状態を読み取るランタイム関数。
9.  **`runtime·casgstatus(G *gp, uint32 oldval, uint32 newval)`**: 指定されたゴルーチン`gp`の状態を`oldval`から`newval`へアトミックに変更しようとするランタイム関数。`oldval`と現在の状態が一致しない場合は、ループして再試行するロジックが含まれています。

## 技術的詳細

このバグの核心は、`runtime·casgstatus`の再試行ロジックが、`netpoll`による`Gwaiting`から`Grunnable`への状態遷移を適切に扱えなかったことにあります。

スタック縮小処理（`copystack`関数内）では、以下のようなロジックでゴルーチンの状態を`Gcopystack`に設定しようとしていました。

```c
oldstatus = runtime·readgstatus(gp);
oldstatus &= ~Gscan; // Gscanフラグを除去
if(oldstatus == Gwaiting || oldstatus == Grunnable)
        runtime·casgstatus(gp, oldstatus, Gcopystack); // oldstatusはGwaitingまたはGrunnable
else
        runtime·throw("copystack: bad status, not Gwaiting or Grunnable");
```

ここで、`runtime·readgstatus(gp)`が`Gwaiting`を返したとします。しかし、その直後に`netpoll`が介入し、同じゴルーチンを`Grunnable`に遷移させたとします。この場合、`runtime·casgstatus(gp, Gwaiting, Gcopystack)`が呼び出されますが、ゴルーチンの実際の状態は`Grunnable`であるため、`Gwaiting`とは一致しません。

`runtime·casgstatus`の内部では、以下のようなループが存在します。

```c
while(!runtime·cas(&gp->atomicstatus, oldval, newval)) {
    // ...
    // Help GC if needed.
    // ...
}
```

このループは、`gp->atomicstatus`が`oldval`（この例では`Gwaiting`）になるまで`runtime·cas`を再試行し続けます。しかし、`netpoll`によって`Grunnable`に遷移したゴルーチンは、GCが完了するまで`Gwaiting`に戻ることはありません。結果として、`runtime·casgstatus`は無限ループに陥り、GCの進行を妨げ、プログラム全体がデッドロック状態になりました。

この問題は、STWがネットワークI/Oを完全に停止させないというGoランタイムの設計上の特性と、`casgstatus`の再試行ロジックが特定の非同期状態遷移を考慮していなかったことの組み合わせによって引き起こされました。

#### `runtime·casgcopystack` の追加

```c
+static void
+badgstatusrunnable(void)
+{
+	runtime·throw("casgstatus: waiting for Gwaiting but is Grunnable");
+}
+
+// casgstatus(gp, oldstatus, Gcopystack), assuming oldstatus is Gwaiting or Grunnable.
+// Returns old status. Cannot call casgstatus directly, because we are racing with an
+// async wakeup that might come in from netpoll. If we see Gwaiting from the readgstatus,
+// it might have become Grunnable by the time we get to the cas. If we called casgstatus,
+// it would loop waiting for the status to go back to Gwaiting, which it never will.
+#pragma textflag NOSPLIT
+uint32
+runtime·casgcopystack(G *gp)
+{
+	uint32 oldstatus;
+
+	for(;;) {
+		oldstatus = runtime·readgstatus(gp) & ~Gscan;
+		if(oldstatus != Gwaiting && oldstatus != Grunnable)
+			runtime·throw("copystack: bad status, not Gwaiting or Grunnable");
+		if(runtime·cas(&gp->atomicstatus, oldstatus, Gcopystack))
+			break;
+	}
+	return oldstatus;
+}
```
この新しい関数`runtime·casgcopystack`が、このコミットの主要な修正点です。
*   `for(;;)`ループで無限に再試行します。
*   ループ内で`runtime·readgstatus(gp) & ~Gscan`を呼び出し、現在のゴルーチン状態を読み取ります。
*   読み取った`oldstatus`が`Gwaiting`でも`Grunnable`でもない場合、`runtime·throw`でパニックを発生させます。これは、スタックコピーの対象となるゴルーチンがこれらの状態のいずれかであるべきという前提に基づいています。
*   最も重要なのは、`runtime·cas(&gp->atomicstatus, oldstatus, Gcopystack)`です。ここで`oldstatus`として、**直前に読み取ったばかりの`Gwaiting`または`Grunnable`のいずれかの状態**を使用します。これにより、`readgstatus`と`cas`の間に状態が`Gwaiting`から`Grunnable`に変化した場合でも、`cas`が成功する可能性が生まれます。
*   `cas`が成功した場合、ループを抜けて元の`oldstatus`を返します。

このアプローチにより、`netpoll`による非同期な状態遷移を許容し、`casgstatus`が無限ループに陥ることを防ぎます。

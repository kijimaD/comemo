## 変更の背景

このコミットは、Go 1.6リリース直前の段階で発生した、`net/http`パッケージにおけるHTTP/2の有効化に関する重要なバグを修正するものです。

元々、Goの`net/http`パッケージは、HTTP/2を透過的にサポートするように設計されていました。しかし、`Transport`構造体の`ExpectContinueTimeout`フィールドがHTTP/2ではサポートされていないという問題（Issue 13851）がありました。この非互換性に対処するため、以前の変更で`ExpectContinueTimeout`が設定されている場合にHTTP/2を無効にするロジックが導入されました。

この変更自体は意図されたものでしたが、`DefaultTransport`（`http.Client`がデフォルトで使用する`Transport`インスタンス）も`ExpectContinueTimeout`にデフォルト値（1秒）を設定しているため、このロジックが`DefaultTransport`にも適用されてしまい、結果として`DefaultTransport`を使用するすべてのHTTPクライアントでHTTP/2が意図せず無効になってしまうという副作用が発生しました。

コミットメッセージにある「I had accidentally disabled a headline feature at the last second. :(」という記述は、この予期せぬ副作用によって、Go 1.6の主要な機能の一つであるHTTP/2の自動有効化が、リリース直前で無効になってしまったことへの言及です。このコミットは、この「意図しない無効化」を修正し、`DefaultTransport`ではHTTP/2が正しく有効になるようにするためのものです（Issue 14391）。

## 前提知識の解説

### 1. `net/http`パッケージと`Transport`

Go言語の`net/http`パッケージは、HTTPクライアントとサーバーを実装するための標準ライブラリです。
`http.Client`はHTTPリクエストを送信するためのクライアントを提供し、その内部で`http.RoundTripper`インターフェースを実装する`Transport`を使用します。
`http.Transport`は、`http.RoundTripper`の具体的な実装の一つで、HTTP/1.1およびHTTP/2のプロトコル詳細、接続の再利用、プロキシ設定、TLS設定などを管理します。

### 2. `http.DefaultTransport`

`http.DefaultTransport`は、`net/http`パッケージが提供するグローバルな`Transport`インスタンスです。`http.Client`を明示的に`Transport`を設定せずに作成した場合（例: `http.DefaultClient`を使用する場合や、`&http.Client{}`のように`Transport`フィールドを省略した場合）、この`DefaultTransport`が使用されます。`DefaultTransport`は、デフォルトでいくつかのタイムアウト設定（例: `ExpectContinueTimeout`）を持っています。

### 3. HTTP/2 (Hypertext Transfer Protocol Version 2)

HTTP/2は、HTTP/1.1の後継となるプロトコルで、パフォーマンスの向上を目的としています。多重化、ヘッダー圧縮、サーバープッシュなどの機能が導入されています。Goの`net/http`パッケージは、TLS接続を介してHTTP/2を自動的にネゴシエートし、サポートするように設計されています。

### 4. `ExpectContinueTimeout`

`ExpectContinueTimeout`は、HTTP/1.1プロトコルにおける「Expect: 100-continue」ヘッダーに関連するタイムアウト設定です。
クライアントが大きなリクエストボディを送信する際、まずヘッダーに`Expect: 100-continue`を含めてサーバーに送信します。サーバーは、リクエストボディを受け入れる準備ができている場合、「100 Continue」レスポンスを返します。クライアントはこのレスポンスを受け取ってからリクエストボディの送信を開始します。
`ExpectContinueTimeout`は、クライアントが「100 Continue」レスポンスを待つ最大時間を指定します。このタイムアウトはHTTP/1.1の機能であり、HTTP/2では異なるメカニズムでフロー制御が行われるため、直接的な対応がありません。

### 5. `http2configureTransport`

`http2configureTransport`は、`net/http`パッケージの内部関数で、既存の`http.Transport`インスタンスをHTTP/2に対応するように設定します。この関数は、`Transport`のフィールドを検査し、HTTP/2の要件に合わせて調整を行います。

## 技術的詳細

このコミットの核心は、`http.Transport`の`onceSetNextProtoDefaults`メソッド内のHTTP/2有効化ロジックの修正にあります。

Go 1.6では、`net/http`クライアントがHTTPS接続を行う際に、ALPN (Application-Layer Protocol Negotiation) を利用して自動的にHTTP/2をネゴシエートする機能が導入されました。この機能は、`http2configureTransport`関数によって`Transport`インスタンスにHTTP/2サポートを追加することで実現されます。

しかし、`ExpectContinueTimeout`がHTTP/2では意味を持たないため、以前のコミット（Issue 13851）で、`ExpectContinueTimeout`が設定されている`Transport`に対してはHTTP/2を無効にするというロジックが追加されました。これは、`ExpectContinueTimeout != 0`という条件で判定されていました。

問題は、`http.DefaultTransport`がデフォルトで`ExpectContinueTimeout`に1秒という非ゼロの値を設定している点にありました。このため、`DefaultTransport`を使用するすべてのクライアントは、`ExpectContinueTimeout != 0`の条件に合致し、結果としてHTTP/2が自動的に無効化されてしまっていたのです。これは、ユーザーが明示的に`ExpectContinueTimeout`を設定したわけではなく、単に`DefaultTransport`のデフォルト値が適用されただけの場合でも発生しました。

このコミットは、このロジックを修正し、`ExpectContinueTimeout`が設定されている場合でも、それが`DefaultTransport`であるならばHTTP/2を有効にするように変更しました。つまり、「ユーザーが明示的に`ExpectContinueTimeout`を設定した場合のみHTTP/2を無効にする」という意図を正確に反映させるための修正です。

具体的には、`ExpectContinueTimeout != 0`という条件に加えて、`t != DefaultTransport`という条件を追加しました。これにより、`DefaultTransport`の場合には`ExpectContinueTimeout`が設定されていてもHTTP/2が無効化されるのを防ぎ、ユーザーがカスタムの`Transport`を作成し、そこで明示的に`ExpectContinueTimeout`を設定した場合にのみHTTP/2が無効化されるようにしました。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更

変更の中心は、`Transport`構造体の`onceSetNextProtoDefaults`メソッド内の条件文です。

元のコード:
```go
	if t.ExpectContinueTimeout != 0 {
		// Unsupported in http2, so disable http2 for now.
		// Issue 13851.
		return
	}
```
このコードは、「`ExpectContinueTimeout`がゼロでない値に設定されている場合、HTTP/2を無効にする」というロジックでした。前述の通り、`DefaultTransport`も`ExpectContinueTimeout`にデフォルト値が設定されているため、この条件に合致し、`DefaultTransport`でのHTTP/2が意図せず無効になっていました。

修正後のコード:
```go
	if t.ExpectContinueTimeout != 0 && t != DefaultTransport {
		// ExpectContinueTimeout is unsupported in http2, so
		// if they explicitly asked for it (as opposed to just
		// using the DefaultTransport, which sets it), then
		// disable http2 for now.
		//
		// Issue 13851. (and changed in Issue 14391)
		return
	}
```
この修正では、条件に`&& t != DefaultTransport`が追加されました。
これにより、HTTP/2を無効にする条件は「`ExpectContinueTimeout`がゼロでない**かつ**現在の`Transport`インスタンスが`DefaultTransport`ではない」となります。

この変更の意図は以下の通りです。
-   **`DefaultTransport`の場合**: `t == DefaultTransport`となるため、`t != DefaultTransport`の条件が偽となり、`ExpectContinueTimeout`がゼロでなくてもHTTP/2は無効化されません。これにより、`DefaultTransport`を使用するクライアントでHTTP/2が正しく有効になります。
-   **カスタム`Transport`の場合**: ユーザーが独自の`Transport`インスタンスを作成し、そこで明示的に`ExpectContinueTimeout`をゼロ以外の値に設定した場合、`t != DefaultTransport`は真となり、`ExpectContinueTimeout != 0`も真となるため、HTTP/2は無効化されます。これは、ユーザーがHTTP/1.1の特定の動作（100-continue）を意図的に要求していると解釈され、HTTP/2との非互換性を避けるための措置です。

この修正により、`ExpectContinueTimeout`とHTTP/2の間の非互換性に対処しつつ、`DefaultTransport`のユーザー体験を損なわないようにバランスが取られました。

### `src/net/http/transport_test.go` の変更

追加されたテストケース `TestTransportAutomaticHTTP2_DefaultTransport` は、`DefaultTransport`がHTTP/2を自動的に有効にするかどうかを検証します。

```go
func TestTransportAutomaticHTTP2_DefaultTransport(t *testing.T) {
	testTransportAutoHTTP(t, DefaultTransport.(*Transport), true)
}
```
このテストは、既存のヘルパー関数`testTransportAutoHTTP`を呼び出しています。
-   第一引数には`DefaultTransport`を`*Transport`型にキャストして渡しています。
-   第二引数には`true`を渡しており、これはHTTP/2が有効になることを期待していることを示します。

このテストの追加により、`DefaultTransport`がHTTP/2を正しくサポートしていることが保証され、将来的に同様の回帰バグが発生するのを防ぐことができます。

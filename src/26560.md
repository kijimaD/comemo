# [インデックス 26560] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージ内のテストファイル `src/net/http/serve_test.go` に関連するものです。具体的には、HTTP/1.1 のパイプライン処理における `CloseNotifier` の動作を検証するテスト `TestCloseNotifierPipelined` の不安定性（flakiness）を解消するための変更です。

## コミット

`net/http` パッケージの `TestCloseNotifierPipelined` テストの不安定性を修正し、異なるGoコンパイラ（`gc`と`gccgo`）間での動作の違いによって発生していたハングアップの問題を解決します。

## 元コミット内容

```
net/http: deflake TestCloseNotifierPipelined

The test sends two HTTP/1.1 pipelined requests. The first is
completedly by the second, and as such triggers an immediate call to the
CloseNotify channel. The second calls the CloseNotify channel after the
overall connection is closed.

The test was passing fine on gc because the code would enter the select
loop before running the handler, so the send on gotReq would always be
seen first. On gccgo the code would sometimes enter the select loop
after the handler had already finished, meaning that the select could
choose between gotReq and sawClose. If it picked sawClose, it would
never close the overall connection, and the httptest server would hang.
The same hang could be induced with gc by adding a time.Sleep
immediately before the select loop.

Deflake the test by 1) don't close the overall connection until both
requests have been seen; 2) don't exit the loop until both closes have
been seen.

Fixes #14231.
```

## 変更の背景

この変更の背景には、`net/http` パッケージの `TestCloseNotifierPipelined` というテストが特定の環境（特に `gccgo` コンパイラを使用した場合）で不安定に失敗（ハングアップ）するという問題がありました。このテストは、HTTP/1.1 のパイプライン処理において、クライアント接続がクローズされたことをサーバー側で検知する `http.CloseNotifier` インターフェースの動作を検証するものです。

問題の根本原因は、Goの標準コンパイラ `gc` と `gccgo` のスケジューリングや実行順序の違いにありました。テストでは2つのパイプラインリクエストを送信し、それぞれが `CloseNotify` チャネルをトリガーするタイミングが異なります。

`gc` では、テストコードが `select` ループに入る前にハンドラが実行される傾向があったため、`gotReq` チャネルへの送信が常に先に処理され、テストは問題なくパスしていました。しかし、`gccgo` では、ハンドラが完了した後に `select` ループに入る場合があり、その結果 `gotReq` と `sawClose` のどちらのチャネルが先に準備できるかが不確定でした。もし `sawClose` が先に選択されてしまうと、テストは全体のコネクションをクローズすることなくループを抜けてしまい、`httptest` サーバーがハングアップするという状況が発生していました。

この不安定性は、`gc` でも `select` ループの直前に `time.Sleep` を挿入することで再現可能であり、これは実行順序のタイミングに依存する競合状態（race condition）であることを示していました。この問題を解決し、テストの信頼性を向上させることが、このコミットの目的です。

## 前提知識の解説

### HTTP/1.1 パイプライン処理

HTTP/1.1 のパイプライン処理（Pipelining）は、クライアントがサーバーからの応答を待たずに複数のHTTPリクエストを連続して送信できる技術です。これにより、ネットワークのレイテンシを隠蔽し、通信効率を向上させることができます。サーバーはリクエストを受信した順序で処理し、応答も同じ順序で返します。ただし、HTTP/1.1 パイプラインはヘッドオブラインブロッキング（HOL blocking）の問題を抱えることがあり、現代のWebではHTTP/2やHTTP/3が主流となっていますが、一部のシステムやテストシナリオでは依然として関連性があります。

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。このパッケージは、HTTPプロトコルの低レベルな詳細を抽象化し、開発者が簡単にWebアプリケーションを構築できるようにします。`http.Handler` インターフェースを実装することで、カスタムのHTTPリクエストハンドラを作成できます。

### `httptest.Server`

`net/http/httptest` パッケージは、HTTPサーバーのテストを容易にするためのユーティリティを提供します。`httptest.Server` は、テスト中に実際のHTTPサーバーを起動し、テスト対象のハンドラに対してリクエストを送信し、その応答を検証することを可能にします。これにより、ネットワーク越しに実際のHTTP通信をシミュレートし、より現実的なテストが書けます。

### `http.CloseNotifier` インターフェース

`http.CloseNotifier` は、Goの `net/http` パッケージで提供されるインターフェースです。このインターフェースは、HTTPリクエストの処理中にクライアントの接続が予期せずクローズされたことをサーバー側で検知するために使用されます。`CloseNotifier` を実装する `http.ResponseWriter` は、`CloseNotify() <-chan bool` メソッドを提供します。このメソッドは、クライアント接続がクローズされたときに値が送信されるチャネルを返します。ハンドラはこのチャネルを `select` ステートメントで監視することで、クライアントの切断イベントに対応できます。例えば、長時間かかる処理中にクライアントが切断された場合、サーバーはその処理を中断してリソースを解放することができます。

### `gc` と `gccgo`

Go言語には主に2つのコンパイラ実装があります。
*   **`gc`**: Goプロジェクトによって公式に開発されている標準のコンパイラです。Go言語のソースコードを直接機械語にコンパイルします。ほとんどのGo開発者が日常的に使用しているのはこのコンパイラです。
*   **`gccgo`**: GCC（GNU Compiler Collection）のフロントエンドとして実装されたGoコンパイラです。Go言語のソースコードをGCCの中間表現に変換し、その後GCCのバックエンドを使用して機械語にコンパイルします。`gc` とは異なる最適化やランタイム特性を持つことがあり、特に並行処理のスケジューリングやメモリ管理の挙動に微妙な違いが生じることがあります。この違いが、今回のテストの不安定性の原因となりました。

## 技術的詳細

このコミットが修正する問題は、`TestCloseNotifierPipelined` テストにおける競合状態（race condition）です。テストは、HTTP/1.1 パイプラインで2つのリクエストを送信し、サーバー側でこれらのリクエストと接続クローズイベントを非同期に処理します。

元のテストコードでは、`select` ステートメントを使用して `gotReq`（リクエスト受信）と `sawClose`（接続クローズ通知）のイベントを待機していました。

```go
For:
	for {
		select {
		case <-gotReq:
			diec <- true
		case <-sawClose:
			break For
		case <-time.After(5 * time.Second):
			ts.CloseClientConnections()
			t.Fatal("timeout")
		}
	}
```

問題は、`gccgo` 環境において、`select` ループに入るタイミングとハンドラが `gotReq` に値を送信するタイミング、そして `sawClose` に値が送信されるタイミングの相対的な順序が不確定であったことです。

1.  **最初のパイプラインリクエスト**: 最初のリクエストは、2番目のリクエストによって「完了」し、すぐに `CloseNotify` チャネルをトリガーします。
2.  **2番目のパイプラインリクエスト**: 2番目のリクエストは、全体の接続がクローズされた後に `CloseNotify` チャネルをトリガーします。

`gc` では、`select` ループに入る前にハンドラが実行され、`gotReq` に値が送信されることが多かったため、`select` は通常 `gotReq` を選択していました。しかし、`gccgo` では、ハンドラが完了する前に `select` ループに入ることがあり、その結果、`gotReq` と `sawClose` の両方が準備完了状態になる可能性がありました。

この状況で `select` が `sawClose` を選択してしまうと、`break For` によってループが終了し、`diec <- true` が実行されないままになります。`diec` チャネルはクライアント接続をクローズするゴルーチンが待機しているため、`diec` に値が送信されないと、そのゴルーチンは永遠にブロックされ、結果として `httptest` サーバーがハングアップしていました。

この競合状態は、`gc` でも `select` ループの直前に `time.Sleep` を追加することで再現可能であり、これは実行スケジューリングのタイミングに依存する問題であることを裏付けています。

修正は、このタイミング依存性を排除し、イベントの処理順序をより堅牢にすることで、テストの信頼性を確保することを目的としています。具体的には、すべてのリクエストが処理され、すべてのクローズ通知が受信されるまで、テストが終了しないようにロジックを変更しています。

## コアとなるコードの解説

変更の目的は、テストの実行順序のタイミングに依存する競合状態を排除し、テストをより堅牢にすることです。

1.  **`diec` チャネルのバッファサイズ変更**:
    *   変更前: `diec := make(chan bool, 2)`
    *   変更後: `diec := make(chan bool, 1)`
    *   `diec` チャネルは、クライアント接続をクローズするゴルーチンに終了を通知するために使用されます。元のコードではバッファサイズが2でしたが、これは2つのリクエストがそれぞれ `diec <- true` を実行することを意図していた可能性があります。しかし、修正後のロジックでは、`diec <- true` は2番目のリクエストが受信された後に一度だけ実行されるため、バッファサイズは1で十分です。これにより、チャネルの意図がより明確になります。

2.  **リクエストとクローズイベントのカウンタ導入**:
    *   `reqs := 0` と `closes := 0` という2つのカウンタ変数が導入されました。
    *   `reqs` は受信したリクエストの数を追跡します。
    *   `closes` は受信した `CloseNotify` イベントの数を追跡します。

3.  **`select` ループ内のロジック変更**:
    *   **`case <-gotReq:` の変更**:
        *   変更前は、`gotReq` が受信されるとすぐに `diec <- true` が実行され、クライアント接続をクローズするゴルーチンに通知していました。
        *   変更後、`reqs` カウンタが増加します。
        *   `if reqs > 2 { t.Fatal("too many requests") }`：2つ以上のリクエストが想定されているため、3つ目のリクエストが来たらエラーとします。
        *   `else if reqs > 1 { diec <- true }`：2番目のリクエストが受信された場合にのみ `diec <- true` を実行します。これにより、クライアント接続のクローズは、両方のリクエストが処理された後にのみトリガーされるようになります。これは、元のコミットメッセージで「don't close the overall connection until both requests have been seen」と述べられている点に対応します。
    *   **`case <-sawClose:` の変更**:
        *   変更前は、`sawClose` が受信されるとすぐに `break For` でループを抜けていました。これが競合状態の原因でした。
        *   変更後、`closes` カウンタが増加します。
        *   `if closes > 1 { break For }`：2つ目の `CloseNotify` イベントが受信された場合にのみループを抜けます。これにより、テストは両方の `CloseNotify` イベントが処理されるまで待機するようになります。これは、元のコミットメッセージで「don't exit the loop until both closes have been seen」と述べられている点に対応します。

これらの変更により、テストはリクエストの受信とクローズ通知のイベントをより厳密にカウントし、特定の順序で処理されることを保証します。これにより、`gc` と `gccgo` の実行スケジューリングの違いによるタイミング依存性が排除され、テストの不安定性が解消されます。

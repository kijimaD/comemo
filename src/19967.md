このコミットは、Goランタイムにおけるインターフェース関連のルーチンをC言語からGo言語へ移行するものです。これにより、Goランタイムの大部分がGo言語で記述されることになり、保守性、可読性、そしてGo言語のツールチェインとの統合が向上します。

変更されたファイルは以下の通りです。

## 変更の背景

Go言語のランタイムは、初期にはC言語とPlan 9アセンブリで記述されていました。これは、低レベルな操作やOSとの連携、パフォーマンスが要求される部分を効率的に実装するためでした。しかし、C言語で記述された部分は、Go言語のガベージコレクションの恩恵を受けられず、Go言語のツールチェイン（例えば、Goのプロファイラやデバッガ）との統合が難しいという課題がありました。また、Go言語の進化に伴い、Go言語自体で低レベルな操作をより安全かつ効率的に記述できるようになってきたことも背景にあります。

このコミットの主な目的は、インターフェースの動的なディスパッチや型アサーションといった、Go言語の根幹をなすインターフェース関連のルーチンをC言語からGo言語に移行することです。これにより、以下のようなメリットが期待されます。

1.  **保守性の向上**: Go言語で記述されたコードは、Go開発者にとってより理解しやすく、デバッグや修正が容易になります。
2.  **可読性の向上**: Go言語の構文と慣習に従うことで、コードの可読性が向上します。
3.  **Goツールチェインとの統合**: Go言語のプロファイラ、デバッガ、リンタなどのツールが、ランタイムのインターフェース関連コードに対してもより効果的に機能するようになります。
4.  **ガベージコレクションの恩恵**: Go言語のコードはガベージコレクションの管理下に置かれるため、メモリリークのリスクが低減し、メモリ管理が簡素化されます。
5.  **一貫性の向上**: ランタイムの大部分がGo言語で記述されることで、コードベース全体の一貫性が高まります。

特にインターフェースはGo言語のポリモーフィズムを実現する重要な機能であり、その実装がGo言語に移行されることは、Go言語の自己ホスト化（self-hosting）の進展を示す重要な一歩と言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部構造とランタイムの概念を理解しておく必要があります。

### Go言語のインターフェース

Go言語のインターフェースは、メソッドのシグネチャの集合を定義します。Goのインターフェースは、JavaやC++のような明示的な`implements`キーワードを必要とせず、型がインターフェースで定義されたすべてのメソッドを実装していれば、そのインターフェースを満たすと見なされます（構造的型付け）。

Goのインターフェース値は、内部的には2つのポインタで構成されます。

1.  **型情報ポインタ**: インターフェース値が保持する具体的な型（`_type`構造体）へのポインタ。
2.  **データポインタ**: インターフェース値が保持する具体的な値へのポインタ。

ただし、これは空のインターフェース`interface{}`（`eface`）の場合です。非空のインターフェース（`iface`）の場合、型情報ポインタは`itab`（インターフェーステーブル）へのポインタに置き換わります。

### `eface`と`iface`

-   **`eface` (empty interface)**: `interface{}`型を表す内部構造体。
    ```go
    type eface struct {
        _type *_type      // 実際の型情報へのポインタ
        data  unsafe.Pointer // 実際の値へのポインタ
    }
    ```
-   **`iface` (non-empty interface)**: メソッドを持つインターフェース型を表す内部構造体。
    ```go
    type iface struct {
        tab   *itab         // itab（インターフェーステーブル）へのポインタ
        data  unsafe.Pointer // 実際の値へのポインタ
    }
    ```

### `_type`と`interfacetype`

-   **`_type`**: Goのすべての型（int, string, struct, funcなど）のメタデータを記述するランタイム内部の構造体。型のサイズ、アラインメント、ハッシュ関数、等価比較関数、メソッド情報などが含まれます。
-   **`interfacetype`**: インターフェース型に特化した`_type`の拡張構造体。インターフェースが持つメソッドのリスト（`mhdr`）が含まれます。

### `itab` (Interface Table)

`itab`は、特定の具体的な型が特定のインターフェースを実装しているかどうか、そしてそのインターフェースのメソッドが具体的な型のどのメソッドに対応するかをキャッシュするためのテーブルです。

```go
type itab struct {
    inter *interfacetype // インターフェース型情報へのポインタ
    _type *_type         // 具体的な型情報へのポインタ
    hash  uint32         // interと_typeのハッシュ値
    _     [4]byte        // パディング
    fun   [1]uintptr     // インターフェースメソッドの実装関数ポインタの配列（可変長）
}
```
`itab`は、インターフェースの型と具体的な型のペアごとに一度だけ計算され、ランタイムのハッシュテーブルにキャッシュされます。これにより、インターフェースのメソッド呼び出しや型アサーションの際に、毎回メソッドのルックアップを行う必要がなくなり、パフォーマンスが向上します。

### GoランタイムのCGoとアセンブリ

Goランタイムの一部は、C言語（`.goc`ファイル）やアセンブリ言語（`.s`ファイル）で記述されています。
-   `.goc`ファイルは、GoのツールチェインによってC言語に変換され、Cコンパイラでコンパイルされます。これらはGoのランタイムとCのランタイムの橋渡しをする役割を担っていました。
-   `.s`ファイルは、特定のアーキテクチャ向けのアセンブリコードで、Goの関数からCのランタイム関数を呼び出すためのスタブや、パフォーマンスが重要な低レベルな操作を実装するために使用されます。

このコミットでは、`iface.goc`のCコードが`iface.go`のGoコードに置き換えられ、`asm_*.s`ファイルも新しいGo関数を呼び出すように更新されています。

### `go:nosplit`

`go:nosplit`は、Goコンパイラに対するディレクティブ（指示）で、その関数がスタックを分割しないことを保証します。これは、ガベージコレクタがスタックをスキャンする際に、スタックの途中で関数が中断されないようにするために重要です。ランタイムの低レベルな関数、特にガベージコレクションやスケジューラに関連する関数でよく使用されます。

### `unsafe`パッケージ

`unsafe`パッケージは、Goの型安全性をバイパスして、ポインタ演算や任意の型へのポインタ変換を可能にします。ランタイムのような低レベルなコードでは、メモリを直接操作する必要があるため、`unsafe`パッケージが頻繁に使用されます。

## 技術的詳細

このコミットの技術的な核心は、インターフェースの動的なディスパッチと型アサーションのロジックをC言語からGo言語に再実装した点にあります。

### `itab`のルックアップとキャッシュ

`getitab`関数は、インターフェース型 (`interfacetype`) と具体的な型 (`_type`) のペアを受け取り、対応する `itab` を返します。

1.  **ハッシュ計算**: `interfacetype`と`_type`のハッシュ値に基づいて、`itab`ハッシュテーブルのインデックスを計算します。
2.  **キャッシュルックアップ**:
    -   まず、ロックなしでハッシュテーブルを検索し、既存の`itab`が見つかればそれを返します。これは、競合が少ない場合の高速パスです。
    -   見つからない場合、`ifaceLock`というグローバルロックを取得し、再度ハッシュテーブルを検索します。これにより、複数のゴルーチンが同時に`itab`を生成しようとするのを防ぎます。
3.  **`itab`の生成**:
    -   既存の`itab`が見つからない場合、新しい`itab`を割り当てます。この割り当てには`gopersistentalloc`が使用されます。これはガベージコレクションの対象とならない永続的なメモリ領域を割り当てる関数です。`itab`は一度生成されるとアプリケーションのライフサイクルを通じて存在し続けるため、GCのオーバーヘッドを避けるために永続メモリに配置されます。
    -   インターフェースのメソッドと具体的な型のメソッドを比較し、一致するメソッドの実装関数ポインタを`itab`の`fun`配列に格納します。この比較は、インターフェースと型の両方のメソッドが名前順にソートされていることを利用して、効率的に行われます（O(ni+nt)ではなくO(ni\*nt)）。
    -   もし具体的な型がインターフェースのすべてのメソッドを実装していない場合、`canfail`が`false`であればパニックを発生させます（例: `v := i.(T)`）。`canfail`が`true`であれば`itab`の`bad`フラグを立てて`nil`を返します（例: `v, ok := i.(T)`）。
4.  **キャッシュへの追加**: 生成された`itab`は、ハッシュテーブルにリンクされ、`goatomicstorep`（アトミックなポインタストア）を使用して安全に公開されます。

### 型変換と型アサーション

`iface.go`には、Goのインターフェース値と具体的な値の間での型変換および型アサーションを行うための様々な関数が実装されています。

-   **`convT2E(t *_type, elem unsafe.Pointer) (e interface{})`**: 具体的な型`t`の要素`elem`を空のインターフェース`eface`に変換します。値のサイズがポインタサイズ以下であれば直接`eface.data`にコピーし、それより大きければ新しいオブジェクトを割り当ててそこにコピーします。
-   **`convT2I(t *_type, inter *interfacetype, cache **itab, elem unsafe.Pointer) (i fInterface)`**: 具体的な型`t`の要素`elem`を非空のインターフェース`iface`に変換します。`getitab`を呼び出して適切な`itab`を取得し、`iface.tab`と`iface.data`を設定します。
-   **`assertI2T(t *_type, i fInterface) (r struct{})`**: 非空のインターフェース`i`を具体的な型`t`に型アサートします。`i`の`itab`が`nil`であるか、`itab`の型が`t`と一致しない場合はパニックを発生させます。
-   **`assertI2T2(t *_type, i fInterface) (r byte)`**: `assertI2T`と同様ですが、`ok`ブール値を返す形式（`v, ok := i.(T)`）に対応します。型アサートが失敗した場合でもパニックせず、`ok`を`false`に設定します。
-   **`assertI2TOK(t *_type, i fInterface) bool`**: 型アサートが成功するかどうかのみをチェックします。
-   **`efaceeq(e1 interface{}, e2 interface{}) bool` / `ifaceeq(i1 fInterface, i2 fInterface) bool`**: インターフェース値の等価性を比較する関数。内部的には、具体的な型の`equal`アルゴリズム（`t.alg.equal`）を使用して値の比較を行います。比較不可能な型（例: スライス、マップ、関数）の場合、パニックを発生させます。

### アセンブリコードの変更

`src/pkg/reflect/asm_*.s`ファイルは、`reflect`パッケージからランタイムのインターフェース関連関数を呼び出すためのアセンブリスタブです。このコミットでは、これらのスタブがC言語の関数（例: `runtime·ifaceE2I`）からGo言語の関数（例: `runtime·reflect_ifaceE2I`）を呼び出すように変更されています。これは、Goコンパイラが生成するGo関数呼び出し規約に合わせるための変更です。

### `stubs.go`と`stubs.goc`の変更

`stubs.go`には、Go言語から呼び出されるランタイム関数のGo側の宣言が含まれます。`stubs.goc`は、それらのC言語側の実装の一部を含んでいました。
このコミットでは、`stubs.go`に`go:noescape`ディレクティブが追加されたり、`nohashcode`に加えて`noequalcode`が導入されたりしています。また、`gopersistentalloc`のGo側の宣言が追加され、`stubs.goc`からそのC側の実装が削除されています。これは、`itab`の割り当てに`gopersistentalloc`が使用されるようになったためです。

全体として、このコミットはGoランタイムのC言語依存性を減らし、Go言語の自己ホスト化をさらに進める重要なステップです。低レベルなインターフェース操作がGo言語で記述されることで、Go言語の進化と最適化の恩恵をより直接的に受けられるようになります。

## コアとなるコードの解説

### `src/pkg/runtime/iface.go`

このファイルは、Goランタイムにおけるインターフェースの挙動を定義する中心的な役割を担っています。

#### `getitab`関数

```go
func getitab(inter *interfacetype, typ *_type, canfail bool) *itab {
    // ... (ハッシュ計算、ロックなしでのルックアップ) ...

    // ロックを取得して再度ルックアップ、または新規itabを生成
    for locked = 0; locked < 2; locked++ {
        if locked != 0 {
            golock(&ifaceLock) // グローバルロック
        }
        for m = (*itab)(goatomicloadp(unsafe.Pointer(&hash[h]))); m != nil; m = m.link {
            if m.inter == inter && m._type == typ {
                // ... (既存itabの処理) ...
                return m
            }
        }
    }

    // 新しいitabの割り当て
    m = (*itab)(gopersistentalloc(unsafe.Sizeof(itab{}) + uintptr(len(inter.mhdr))*ptrSize))
    m.inter = inter
    m._type = typ

search:
    // インターフェースと型のメソッドを比較し、itabのfun配列に実装関数ポインタを設定
    ni := len(inter.mhdr)
    nt := len(x.mhdr) // xはtyp._typeのuncommon type
    j := 0
    for k := 0; k < ni; k++ {
        i := (*imethod)(add(unsafe.Pointer(inter), unsafe.Sizeof(interfacetype{})+uintptr(k)*unsafe.Sizeof(imethod{})))
        iname := i.name
        ipkgpath := i.pkgpath
        itype := i._type
        for ; j < nt; j++ {
            t := (*method)(add(unsafe.Pointer(x), unsafe.Sizeof(uncommontype{})+uintptr(j)*unsafe.Sizeof(method{})))
            if t.mtyp == itype && t.name == iname && t.pkgpath == ipkgpath {
                if m != nil {
                    f := (*func())(add(unsafe.Pointer(m), unsafe.Sizeof(itab{})+uintptr(k)*ptrSize))
                    *f = t.ifn // 実装関数ポインタをitabに格納
                }
                goto nextimethod
            }
        }
        // メソッドが見つからなかった場合
        if !canfail {
            panic(&TypeAssertionError{"", *typ._string, *inter.typ._string, *iname})
        }
        m.bad = 1 // badフラグを立てて、このitabが不正であることを示す
        break
    nextimethod:
    }

    // ... (itabをハッシュテーブルに追加、ロック解除) ...
    return m
}
```
この関数は、Goのインターフェースの動的な性質を支える最も重要な部分です。`itab`の効率的なルックアップと生成により、インターフェースのメソッド呼び出しが高速に行われます。`gopersistentalloc`の使用は、`itab`が永続的なデータ構造であり、ガベージコレクションの対象外とすることでパフォーマンスを最適化していることを示しています。

#### `convT2E`と`convT2I`関数

```go
func convT2E(t *_type, elem unsafe.Pointer) (e interface{}) {
    size := uintptr(t.size)
    ep := (*eface)(unsafe.Pointer(&e))
    if size <= ptrSize { // 値がポインタサイズ以下の場合
        ep._type = t
        memmove(unsafe.Pointer(&ep.data), elem, size) // 直接コピー
    } else { // 値がポインタサイズより大きい場合
        x := newobject(t) // 新しいオブジェクトを割り当て
        memmove(x, elem, size) // 値をコピー
        ep._type = t
        ep.data = x // データポインタを割り当てたオブジェクトに設定
    }
    return
}

func convT2I(t *_type, inter *interfacetype, cache **itab, elem unsafe.Pointer) (i fInterface) {
    // ... (itabの取得) ...
    pi := (*iface)(unsafe.Pointer(&i))
    if size <= ptrSize { // 値がポインタサイズ以下の場合
        pi.tab = tab
        memmove(unsafe.Pointer(&pi.data), elem, size)
    } else { // 値がポインタサイズより大きい場合
        x := newobject(t)
        memmove(x, elem, size)
        pi.tab = tab
        pi.data = x
    }
    return
}
```
これらの関数は、Goの具体的な値がインターフェース値に変換される際のメモリ管理とデータコピーのロジックを扱います。値のサイズに応じて、直接コピーするか、新しいメモリを割り当ててそこにコピーするかが決定されます。これは、Goのインターフェースが値のコピーを保持する（またはポインタを保持する）というセマンティクスを反映しています。

#### 型アサーション関数群

## 変更の背景

Go言語のランタイムは、初期にはC言語とPlan 9アセンブリで記述されていました。これは、低レベルな操作やOSとの連携、パフォーマンスが要求される部分を効率的に実装するためでした。しかし、C言語で記述された部分は、Go言語のガベージコレクションの恩恵を受けられず、Go言語のツールチェイン（例えば、Goのプロファイラやデバッガ）との統合が難しいという課題がありました。また、Go言語の進化に伴い、Go言語自体で低レベルな操作をより安全かつ効率的に記述できるようになってきたことも背景にあります。

このコミットの主な目的は、インターフェースの動的なディスパッチや型アサーションといった、Go言語の根幹をなすインターフェース関連のルーチンをC言語からGo言語に移行することです。これにより、以下のようなメリットが期待されます。

1.  **保守性の向上**: Go言語で記述されたコードは、Go開発者にとってより理解しやすく、デバッグや修正が容易になります。
2.  **可読性の向上**: Go言語の構文と慣習に従うことで、コードの可読性が向上します。
3.  **Goツールチェインとの統合**: Go言語のプロファイラ、デバッガ、リンタなどのツールが、ランタイムのインターフェース関連コードに対してもより効果的に機能するようになります。
4.  **ガベージコレクションの恩恵**: Go言語のコードはガベージコレクションの管理下に置かれるため、メモリリークのリスクが低減し、メモリ管理が簡素化されます。
5.  **一貫性の向上**: ランタイムの大部分がGo言語で記述されることで、コードベース全体の一貫性が高まります。

特にインターフェースはGo言語のポリモーフィズムを実現する重要な機能であり、その実装がGo言語に移行されることは、Go言語の自己ホスト化（self-hosting）の進展を示す重要な一歩と言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部構造とランタイムの概念を理解しておく必要があります。

### Go言語のインターフェース

Go言語のインターフェースは、メソッドのシグネチャの集合を定義します。Goのインターフェースは、JavaやC++のような明示的な`implements`キーワードを必要とせず、型がインターフェースで定義されたすべてのメソッドを実装していれば、そのインターフェースを満たすと見なされます（構造的型付け）。

Goのインターフェース値は、内部的には2つのポインタで構成されます。

1.  **型情報ポインタ**: インターフェース値が保持する具体的な型（`_type`構造体）へのポインタ。
2.  **データポインタ**: インターフェース値が保持する具体的な値へのポインタ。

ただし、これは空のインターフェース`interface{}`（`eface`）の場合です。非空のインターフェース（`iface`）の場合、型情報ポインタは`itab`（インターフェーステーブル）へのポインタに置き換わります。

### `eface`と`iface`

-   **`eface` (empty interface)**: `interface{}`型を表す内部構造体。
    ```go
    type eface struct {
        _type *_type      // 実際の型情報へのポインタ
        data  unsafe.Pointer // 実際の値へのポインタ
    }
    ```
-   **`iface` (non-empty interface)**: メソッドを持つインターフェース型を表す内部構造体。
    ```go
    type iface struct {
        tab   *itab         // itab（インターフェーステーブル）へのポインタ
        data  unsafe.Pointer // 実際の値へのポインタ
    }
    ```

### `_type`と`interfacetype`

-   **`_type`**: Goのすべての型（int, string, struct, funcなど）のメタデータを記述するランタイム内部の構造体。型のサイズ、アラインメント、ハッシュ関数、等価比較関数、メソッド情報などが含まれます。
-   **`interfacetype`**: インターフェース型に特化した`_type`の拡張構造体。インターフェースが持つメソッドのリスト（`mhdr`）が含まれます。

### `itab` (Interface Table)

`itab`は、特定の具体的な型が特定のインターフェースを実装しているかどうか、そしてそのインターフェースのメソッドが具体的な型のどのメソッドに対応するかをキャッシュするためのテーブルです。

```go
type itab struct {
    inter *interfacetype // インターフェース型情報へのポインタ
    _type *_type         // 具体的な型情報へのポインタ
    hash  uint32         // interと_typeのハッシュ値
    _     [4]byte        // パディング
    fun   [1]uintptr     // インターフェースメソッドの実装関数ポインタの配列（可変長）
}
```
`itab`は、インターフェースの型と具体的な型のペアごとに一度だけ計算され、ランタイムのハッシュテーブルにキャッシュされます。これにより、インターフェースのメソッド呼び出しや型アサーションの際に、毎回メソッドのルックアップを行う必要がなくなり、パフォーマンスが向上します。

### GoランタイムのCGoとアセンブリ

Goランタイムの一部は、C言語（`.goc`ファイル）やアセンブリ言語（`.s`ファイル）で記述されています。
-   `.goc`ファイルは、GoのツールチェインによってC言語に変換され、Cコンパイラでコンパイルされます。これらはGoのランタイムとCのランタイムの橋渡しをする役割を担っていました。
-   `.s`ファイルは、特定のアーキテクチャ向けのアセンブリコードで、Goの関数からCのランタイム関数を呼び出すためのスタブや、パフォーマンスが重要な低レベルな操作を実装するために使用されます。

このコミットでは、`iface.goc`のCコードが`iface.go`のGoコードに置き換えられ、`asm_*.s`ファイルも新しいGo関数を呼び出すように更新されています。

### `go:nosplit`

`go:nosplit`は、Goコンパイラに対するディレクティブ（指示）で、その関数がスタックを分割しないことを保証します。これは、ガベージコレクタがスタックをスキャンする際に、スタックの途中で関数が中断されないようにするために重要です。ランタイムの低レベルな関数、特にガベージコレクションやスケジューラに関連する関数でよく使用されます。

### `unsafe`パッケージ

`unsafe`パッケージは、Goの型安全性をバイパスして、ポインタ演算や任意の型へのポインタ変換を可能にします。ランタイムのような低レベルなコードでは、メモリを直接操作する必要があるため、`unsafe`パッケージが頻繁に使用されます。

## 技術的詳細

このコミットの技術的な核心は、インターフェースの動的なディスパッチと型アサーションのロジックをC言語からGo言語に再実装した点にあります。

### `itab`のルックアップとキャッシュ

`getitab`関数は、インターフェース型 (`interfacetype`) と具体的な型 (`_type`) のペアを受け取り、対応する `itab` を返します。

1.  **ハッシュ計算**: `interfacetype`と`_type`のハッシュ値に基づいて、`itab`ハッシュテーブルのインデックスを計算します。
2.  **キャッシュルックアップ**:
    -   まず、ロックなしでハッシュテーブルを検索し、既存の`itab`が見つかればそれを返します。これは、競合が少ない場合の高速パスです。
    -   見つからない場合、`ifaceLock`というグローバルロックを取得し、再度ハッシュテーブルを検索します。これにより、複数のゴルーチンが同時に`itab`を生成しようとするのを防ぎます。
3.  **`itab`の生成**:
    -   既存の`itab`が見つからない場合、新しい`itab`を割り当てます。この割り当てには`gopersistentalloc`が使用されます。これはガベージコレクションの対象とならない永続的なメモリ領域を割り当てる関数です。`itab`は一度生成されるとアプリケーションのライフサイクルを通じて存在し続けるため、GCのオーバーヘッドを避けるために永続メモリに配置されます。
    -   インターフェースのメソッドと具体的な型のメソッドを比較し、一致するメソッドの実装関数ポインタを`itab`の`fun`配列に格納します。この比較は、インターフェースと型の両方のメソッドが名前順にソートされていることを利用して、効率的に行われます（O(ni+nt)ではなくO(ni\*nt)）。
    -   もし具体的な型がインターフェースのすべてのメソッドを実装していない場合、`canfail`が`false`であればパニックを発生させます（例: `v := i.(T)`）。`canfail`が`true`であれば`itab`の`bad`フラグを立てて`nil`を返します（例: `v, ok := i.(T)`）。
4.  **キャッシュへの追加**: 生成された`itab`は、ハッシュテーブルにリンクされ、`goatomicstorep`（アトミックなポインタストア）を使用して安全に公開されます。

### 型変換と型アサーション

`iface.go`には、Goのインターフェース値と具体的な値の間での型変換および型アサーションを行うための様々な関数が実装されています。

-   **`convT2E(t *_type, elem unsafe.Pointer) (e interface{})`**: 具体的な型`t`の要素`elem`を空のインターフェース`eface`に変換します。値のサイズがポインタサイズ以下であれば直接`eface.data`にコピーし、それより大きければ新しいオブジェクトを割り当ててそこにコピーします。
-   **`convT2I(t *_type, inter *interfacetype, cache **itab, elem unsafe.Pointer) (i fInterface)`**: 具体的な型`t`の要素`elem`を非空のインターフェース`iface`に変換します。`getitab`を呼び出して適切な`itab`を取得し、`iface.tab`と`iface.data`を設定します。
-   **`assertI2T(t *_type, i fInterface) (r struct{})`**: 非空のインターフェース`i`を具体的な型`t`に型アサートします。`i`の`itab`が`nil`であるか、`itab`の型が`t`と一致しない場合はパニックを発生させます。
-   **`assertI2T2(t *_type, i fInterface) (r byte)`**: `assertI2T`と同様ですが、`ok`ブール値を返す形式（`v, ok := i.(T)`）に対応します。型アサートが失敗した場合でもパニックせず、`ok`を`false`に設定します。
-   **`assertI2TOK(t *_type, i fInterface) bool`**: 型アサートが成功するかどうかのみをチェックします。
-   **`efaceeq(e1 interface{}, e2 interface{}) bool` / `ifaceeq(i1 fInterface, i2 fInterface) bool`**: インターフェース値の等価性を比較する関数。内部的には、具体的な型の`equal`アルゴリズム（`t.alg.equal`）を使用して値の比較を行います。比較不可能な型（例: スライス、マップ、関数）の場合、パニックを発生させます。

### アセンブリコードの変更

`src/pkg/reflect/asm_*.s`ファイルは、`reflect`パッケージからランタイムのインターフェース関連関数を呼び出すためのアセンブリスタブです。このコミットでは、これらのスタブがC言語の関数（例: `runtime·ifaceE2I`）からGo言語の関数（例: `runtime·reflect_ifaceE2I`）を呼び出すように変更されています。これは、Goコンパイラが生成するGo関数呼び出し規約に合わせるための変更です。

### `stubs.go`と`stubs.goc`の変更

`stubs.go`には、Go言語から呼び出されるランタイム関数のGo側の宣言が含まれます。`stubs.goc`は、それらのC言語側の実装の一部を含んでいました。
このコミットでは、`stubs.go`に`go:noescape`ディレクティブが追加されたり、`nohashcode`に加えて`noequalcode`が導入されたりしています。また、`gopersistentalloc`のGo側の宣言が追加され、`stubs.goc`からそのC側の実装が削除されています。これは、`itab`の割り当てに`gopersistentalloc`が使用されるようになったためです。

全体として、このコミットはGoランタイムのC言語依存性を減らし、Go言語の自己ホスト化をさらに進める重要なステップです。低レベルなインターフェース操作がGo言語で記述されることで、Goランタイムの進化と最適化の恩恵をより直接的に受けられるようになります。

                if m != nil {
                    f := (*func())(add(unsafe.Pointer(m), unsafe.Sizeof(itab{})+uintptr(k)*ptrSize))
                    *f = t.ifn // 実装関数ポインタをitabに格納
                }
                goto nextimethod
            }
        }
        // メソッドが見つからなかった場合
        if !canfail {
            panic(&TypeAssertionError{"", *typ._string, *inter.typ._string, *iname})
        }
        m.bad = 1 // badフラグを立てて、このitabが不正であることを示す
        break
    nextimethod:
    }

    // ... (itabをハッシュテーブルに追加、ロック解除) ...
    return m
}
```
この関数は、Goのインターフェースの動的な性質を支える最も重要な部分です。`itab`の効率的なルックアップと生成により、インターフェースのメソッド呼び出しが高速に行われます。`gopersistentalloc`の使用は、`itab`が永続的なデータ構造であり、ガベージコレクションの対象外とすることでパフォーマンスを最適化していることを示しています。

#### `convT2E`と`convT2I`関数

```go
func convT2E(t *_type, elem unsafe.Pointer) (e interface{}) {
    size := uintptr(t.size)
    ep := (*eface)(unsafe.Pointer(&e))
    if size <= ptrSize { // 値がポインタサイズ以下の場合
        ep._type = t
        memmove(unsafe.Pointer(&ep.data), elem, size) // 直接コピー
    } else { // 値がポインタサイズより大きい場合
        x := newobject(t) // 新しいオブジェクトを割り当て
        memmove(x, elem, size) // 値をコピー
        ep._type = t
        ep.data = x // データポインタを割り当てたオブジェクトに設定
    }
    return
}

func convT2I(t *_type, inter *interfacetype, cache **itab, elem unsafe.Pointer) (i fInterface) {
    // ... (itabの取得) ...
    pi := (*iface)(unsafe.Pointer(&i))
    if size <= ptrSize { // 値がポインタサイズ以下の場合
        pi.tab = tab
        memmove(unsafe.Pointer(&pi.data), elem, size)
    } else { // 値がポインタサイズより大きい場合
        x := newobject(t)
        memmove(x, elem, size)
        pi.tab = tab
        pi.data = x
    }
    return
}
```
これらの関数は、Goの具体的な値がインターフェース値に変換される際のメモリ管理とデータコピーのロジックを扱います。値のサイズに応じて、直接コピーするか、新しいメモリを割り当ててそこにコピーするかが決定されます。これは、Goのインターフェースが値のコピーを保持する（またはポインタを保持する）というセマンティクスを反映しています。

#### 型アサーション関数群

`assertI2T`, `assertE2T`, `assertI2I`, `assertE2I`など、様々な型アサーション関数がGoで実装されています。これらは、インターフェース値の内部の型情報（`itab`または`_type`）をチェックし、アサーションが成功すれば値を抽出し、失敗すればパニックを発生させるか、`ok`ブール値を返します。

### `src/pkg/runtime/iface.goc`

このファイルは、Goランタイムのインターフェース関連のC言語コードが大幅に削減されたことを示しています。残っているのは、`runtime·ifaceE2I2`のような、まだC言語から呼び出される必要がある一部の関数のみです。これは、GoランタイムのC言語依存性が着実に減少していることを明確に示しています。

### `src/pkg/reflect/asm_*.s`

これらのアセンブリファイルは、`reflect`パッケージがGoランタイムのインターフェース関連機能を利用するための橋渡しをします。C言語の関数呼び出し規約からGo言語の関数呼び出し規約への変更は、Goコンパイラとランタイムの連携がより密接になったことを意味します。これにより、`reflect`パッケージの操作もGoランタイムの最適化の恩恵を受けやすくなります。

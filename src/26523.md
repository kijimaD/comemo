# [インデックス 26523] ファイルの概要

このコミットは、Goランタイムにおける特定の条件下でのデッドロックの可能性を修正します。具体的には、`runtime.LockOSThread`を使用しているGoroutine、GCアシスト、およびバックグラウンドマークワーカーのスケジューリングが特定の順序で発生した場合に、Goスケジューラがデッドロックに陥る問題を解決します。このデッドロックは、`handoffp`関数がGC作業のみが存在する場合にM（OSスレッド）を起動しないために発生していました。

## 変更の背景

このコミットは、Goランタイムのスケジューラが特定の状況下でデッドロックに陥る可能性があった問題を修正するために導入されました。このデッドロックは、主に以下の要素が組み合わさることで発生していました。

1.  **`runtime.LockOSThread`の使用**: あるGoroutine (G) が `runtime.LockOSThread` を呼び出すと、そのGは特定のOSスレッド (M) にロックされ、他のGはそのMで実行できなくなります。
2.  **GCアシスト**: Goのガベージコレクション (GC) は、アプリケーションのGoroutineがメモリを割り当てる際に、GC作業を「アシスト」させることがあります。これは、GCが完了するまでGoroutineの実行を一時停止し、GC作業を手伝わせるメカニズムです。
3.  **バックグラウンドマークワーカー**: GCのマークフェーズでは、バックグラウンドでオブジェクトの到達可能性をマークするワーカーGoroutineが動作します。
4.  **`handoffp`関数の挙動**: スケジューラがP (プロセッサ、実行コンテキスト) を別のMに引き渡す際に使用される`handoffp`関数は、実行キューにユーザーGoroutineがない場合、Pをアイドル状態にしてしまうことがあります。

具体的なデッドロックのシナリオは以下の通りです。

*   **初期状態**: ユーザーGoroutine (G1) が1つだけ存在し、複数のPのうちG1を実行しているP以外はすべてアイドル状態です。
*   **G1がMにロック**: G1が `runtime.LockOSThread` を使用して自身をMにロックします。
*   **GC開始**: GCが開始され、マークフェーズに入ります。
*   **GCアシストとパーク**: G1がGCアシストを実行しますが、完全に満足されることなくマークフェーズが完了します。マークフェーズの完了により、すべてのバックグラウンドマークワーカーはパーク（待機）状態になります。G1自身も、残りのアシスト債務を解消するためにバックグラウンドマークワーカーが作業を完了するのを待ってパークします。
*   **スケジューラへの移行とPの解放**: G1がパークすると、スケジューラに制御が移ります。G1はMにロックされているため、スケジューラはPを解放し、`handoffp`を呼び出してPを別のMに引き渡そうとします。
*   **`handoffp`の誤った判断**: `handoffp`はローカルおよびグローバルの実行キューをチェックしますが、これらは空です。また、アイドル状態のPが存在することを確認し、新しいMを起動する代わりに、Pをアイドル状態にしてしまいます。

この結果、すべてのGoroutineは待機状態になり、すべてのPはアイドル状態になります。特に、GCワーカーはどれも実行されず、マーク作業が進まないため、メインのGoroutineのアシスト債務も解消されません。これにより、プロセス全体がソフトロックアップ（デッドロック）状態に陥っていました。

## 前提知識の解説

### Goスケジューラ (GPMモデル)

Goランタイムのスケジューラは、GPMモデルと呼ばれる3つの主要なエンティティで構成されています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書いた関数やメソッドがGoroutineとして実行されます。数百万のGoroutineを同時に実行できます。
*   **P (Processor)**: OSスレッド (M) がGoコードを実行するために必要な論理プロセッサです。Pは実行可能なGoroutineのローカルキューを保持し、Mに割り当てられてGoroutineを実行します。GとMの間のコンテキストとして機能し、GoスケジューラがGoroutineを効率的にスケジューリングするためのリソースを提供します。`GOMAXPROCS`環境変数によってPの最大数が決定されます。
*   **M (Machine/OS Thread)**: OSによって管理される実際のOSスレッドです。MはPに割り当てられ、PのローカルキューからGoroutineを取り出して実行します。Mがブロックされる（システムコールなど）と、そのMはPを解放し、別のMがそのPを引き継いでGoroutineの実行を継続します。

### `runtime.LockOSThread`

`runtime.LockOSThread`関数は、現在のGoroutineを現在のOSスレッド (M) にロックします。これにより、そのGoroutineは他のMに移動したり、他のGoroutineがそのMで実行されたりすることがなくなります。これは、特定のOSスレッドのプロパティ（例: スレッドローカルストレージ、Cgoコールバック）に依存するCgoコードや、特定のOSスレッドでしか実行できないGUIライブラリなどを使用する場合に必要となることがあります。

### ガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されます。

*   **マークフェーズ**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定するフェーズです。Go 1.5以降、このフェーズは並行（concurrent）かつインクリメンタル（incremental）に実行されます。
    *   **GCアシスト**: アプリケーションのGoroutineがメモリを割り当てる際に、GCが遅れている場合、そのGoroutineにGC作業の一部を手伝わせるメカニズムです。これにより、GCの進行を加速し、STW (Stop The World) 時間を短縮します。GoroutineはGCアシストを完了するまでブロックされることがあります。
    *   **バックグラウンドマークワーカー**: GCのマークフェーズ中に、バックグラウンドでオブジェクトのマーク作業を行うGoroutineです。これらは通常、アイドル状態のPを利用して実行されます。

### `handoffp` と `findrunnable`

*   **`findrunnable`**: スケジューラが実行可能なGoroutine (G) を見つけるために呼び出す関数です。ローカルPの実行キュー、グローバル実行キュー、ネットワークポーラーなどを探索し、実行すべきGを返します。
*   **`handoffp`**: あるMがPを解放し、そのPを別のMに引き渡す必要がある場合に呼び出される関数です。例えば、Mがシステムコールでブロックされたり、`runtime.LockOSThread`によってGがMにロックされた状態でGがパークしたりした場合に発生します。`handoffp`の主な目的は、解放されたPがアイドル状態にならないように、可能な限り早く別のMに割り当ててGoroutineの実行を継続させることです。

## 技術的詳細

デッドロックの根本原因は、`handoffp`関数が`findrunnable`関数よりも「厳格」であったことにあります。

`findrunnable`は、Pに割り当てて実行すべきGoroutineを探す際に、ユーザーGoroutineだけでなく、GC作業（特にバックグラウンドマークワーカー）も考慮します。つまり、ユーザーGoroutineがなくてもGC作業があれば、`findrunnable`はそのGC作業を実行するためにPをアクティブに保つことができます。

しかし、以前の`handoffp`の実装では、Pのローカル実行キューとグローバル実行キューにユーザーGoroutineが存在しない場合、Pをアイドル状態にしていました。GC作業が残っているにもかかわらず、`handoffp`はそのGC作業を「実行すべき仕事」とは認識せず、Pをアイドル状態のプールに戻してしまっていたのです。

上記のデッドロックシナリオでは、G1がGCアシストを完了できずにパークし、そのPが`handoffp`に渡されます。このとき、ユーザーGoroutineの実行キューは空ですが、GCアシストの残債を解消するためのGCマーク作業は残っています。しかし、`handoffp`はGC作業を考慮しないため、Pをアイドル状態にしてしまいます。結果として、GC作業を実行するMが起動されず、GCアシストを待つG1も、バックグラウンドマークワーカーも、永遠に待機することになり、システム全体が停止します。

この問題は、`findrunnable`がGC作業を考慮する一方で、`handoffp`が考慮しないという不整合によって引き起こされていました。この不整合が、`runtime.LockOSThread`のような特定のMにGを固定するメカニズムと組み合わさることで、デッドロックという形で顕在化しました。

変更前は、`handoffp`はPのローカル実行キュー (`!runqempty(_p_)`) またはグローバル実行キュー (`sched.runqsize != 0`) にユーザーGoroutineが存在する場合にのみ、`startm`を呼び出して新しいMを起動していました。これにより、Pがアイドル状態になるのを防ぎ、Goroutineの実行を継続させます。

追加されたコードブロック:
```go

	if gcBlackenEnabled != 0 && gcMarkWorkAvailable(_p_) {
		startm(_p_, false)
		return
	}
```
このコードは、既存のユーザーGoroutineのチェックの直後に追加されています。
*   `gcBlackenEnabled != 0`: これはGCのマークフェーズがアクティブであることを示します。GCが実行中でなければ、GC作業をチェックする必要はありません。
*   `gcMarkWorkAvailable(_p_)`: この関数は、指定されたPにGCマーク作業が残っているかどうかをチェックします。具体的には、PのローカルGCワークキューやグローバルGCワークキューに作業があるかを確認します。

この条件が真（GCがアクティブで、かつGCマーク作業が利用可能）であれば、`handoffp`は直ちに`startm(_p_, false)`を呼び出して新しいMを起動し、そのMにPを割り当ててGC作業を実行させます。これにより、GC作業が残っているにもかかわらずPがアイドル状態になることを防ぎ、デッドロックを回避します。

この変更は、コミットメッセージで述べられている「`findrunnable`がPで実行するGを返すような状況では、`handoffp`はそのPで作業を実行するためにMを起動する」という重要な不変条件を再導入します。つまり、`findrunnable`がGC作業を「実行すべき仕事」と認識するのと同様に、`handoffp`もGC作業を認識し、それに応じてMを起動するようになったことで、スケジューラの挙動の一貫性が保たれ、デッドロックが解消されました。

## 変更の背景

このコミットは、Goランタイムのスケジューラが特定の状況下でデッドロックに陥る可能性があった問題を修正するために導入されました。このデッドロックは、主に以下の要素が組み合わさることで発生していました。

1.  **`runtime.LockOSThread`の使用**: あるGoroutine (G) が `runtime.LockOSThread` を呼び出すと、そのGは特定のOSスレッド (M) にロックされ、他のGはそのMで実行できなくなります。
2.  **GCアシスト**: Goのガベージコレクション (GC) は、アプリケーションのGoroutineがメモリを割り当てる際に、GC作業を「アシスト」させることがあります。これは、GCが完了するまでGoroutineの実行を一時停止し、GC作業を手伝わせるメカニズムです。
3.  **バックグラウンドマークワーカー**: GCのマークフェーズでは、バックグラウンドでオブジェクトの到達可能性をマークするワーカーGoroutineが動作します。
4.  **`handoffp`関数の挙動**: スケジューラがP (プロセッサ、実行コンテキスト) を別のMに引き渡す際に使用される`handoffp`関数は、実行可能なユーザーGoroutineがない場合、Pをアイドル状態にしてしまうことがあります。

具体的なデッドロックのシナリオは以下の通りです。

*   **初期状態**: ユーザーGoroutine (G1) が1つだけ存在し、複数のPのうちG1を実行しているP以外はすべてアイドル状態です。
*   **G1がMにロック**: G1が `runtime.LockOSThread` を使用して自身をMにロックします。
*   **GC開始**: GCが開始され、マークフェーズに入ります。
*   **GCアシストとパーク**: G1がGCアシストを実行しますが、完全に満足されることなくマークフェーズが完了します。マークフェーズの完了により、すべてのバックグラウンドマークワーカーはパーク（待機）状態になります。G1自身も、残りのアシスト債務を解消するためにバックグラウンドマークワーカーが作業を完了するのを待ってパークします。
*   **スケジューラへの移行とPの解放**: G1がパークすると、スケジューラに制御が移ります。G1はMにロックされているため、スケジューラはPを解放し、`handoffp`を呼び出してPを別のMに引き渡そうとします。
*   **`handoffp`の誤った判断**: `handoffp`はローカルおよびグローバルの実行キューをチェックしますが、これらは空です。また、アイドル状態のPが存在することを確認し、新しいMを起動する代わりに、Pをアイドル状態にしてしまいます。

この結果、すべてのGoroutineは待機状態になり、すべてのPはアイドル状態になります。特に、GCワーカーはどれも実行されず、マーク作業が進まないため、メインのGoroutineのアシスト債務も解消されません。これにより、プロセス全体がソフトロックアップ（デッドロック）状態に陥っていました。

## 前提知識の解説

### Goスケジューラ (GPMモデル)

Goランタイムのスケジューラは、GPMモデルと呼ばれる3つの主要なエンティティで構成されています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書いた関数やメソッドがGoroutineとして実行されます。数百万のGoroutineを同時に実行できます。
*   **P (Processor)**: OSスレッド (M) がGoコードを実行するために必要な論理プロセッサです。Pは実行可能なGoroutineのローカルキューを保持し、Mに割り当てられてGoroutineを実行します。GとMの間のコンテキストとして機能し、GoスケジューラがGoroutineを効率的にスケジューリングするためのリソースを提供します。`GOMAXPROCS`環境変数によってPの最大数が決定されます。
*   **M (Machine/OS Thread)**: OSによって管理される実際のOSスレッドです。MはPに割り当てられ、PのローカルキューからGoroutineを取り出して実行します。Mがブロックされる（システムコールなど）と、そのMはPを解放し、別のMがそのPを引き継いでGoroutineの実行を継続します。

### `runtime.LockOSThread`

`runtime.LockOSThread`関数は、現在のGoroutineを現在のOSスレッド (M) にロックします。これにより、そのGoroutineは他のMに移動したり、他のGoroutineがそのMで実行されたりすることがなくなります。これは、特定のOSスレッドのプロパティ（例: スレッドローカルストレージ、Cgoコールバック）に依存するCgoコードや、特定のOSスレッドでしか実行できないGUIライブラリなどを使用する場合に必要となることがあります。

### ガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されます。

*   **マークフェーズ**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定するフェーズです。Go 1.5以降、このフェーズは並行（concurrent）かつインクリメンタル（incremental）に実行されます。
    *   **GCアシスト**: アプリケーションのGoroutineがメモリを割り当てる際に、GCが遅れている場合、そのGoroutineにGC作業の一部を手伝わせるメカニズムです。これにより、GCの進行を加速し、STW (Stop The World) 時間を短縮します。GoroutineはGCアシストを完了するまでブロックされることがあります。
    *   **バックグラウンドマークワーカー**: GCのマークフェーズ中に、バックグラウンドでオブジェクトのマーク作業を行うGoroutineです。これらは通常、アイドル状態のPを利用して実行されます。

### `handoffp` と `findrunnable`

*   **`findrunnable`**: スケジューラが実行可能なGoroutine (G) を見つけるために呼び出す関数です。ローカルPの実行キュー、グローバル実行キュー、ネットワークポーラーなどを探索し、実行すべきGを返します。
*   **`handoffp`**: あるMがPを解放し、そのPを別のMに引き渡す必要がある場合に呼び出される関数です。例えば、Mがシステムコールでブロックされたり、`runtime.LockOSThread`によってGがMにロックされた状態でGがパークしたりした場合に発生します。`handoffp`の主な目的は、解放されたPがアイドル状態にならないように、可能な限り早く別のMに割り当ててGoroutineの実行を継続させることです。

## 技術的詳細

デッドロックの根本原因は、`handoffp`関数が`findrunnable`関数よりも「厳格」であったことにあります。

`findrunnable`は、Pに割り当てて実行すべきGoroutineを探す際に、ユーザーGoroutineだけでなく、GC作業（特にバックグラウンドマークワーカー）も考慮します。つまり、ユーザーGoroutineがなくてもGC作業があれば、`findrunnable`はそのGC作業を実行するためにPをアクティブに保つことができます。

しかし、以前の`handoffp`の実装では、Pのローカル実行キューとグローバル実行キューにユーザーGoroutineが存在しない場合、Pをアイドル状態にしていました。GC作業が残っているにもかかわらず、`handoffp`はそのGC作業を「実行すべき仕事」とは認識せず、Pをアイドル状態のプールに戻してしまっていたのです。

上記のデッドロックシナリオでは、G1がGCアシストを完了できずにパークし、そのPが`handoffp`に渡されます。このとき、ユーザーGoroutineの実行キューは空ですが、GCアシストの残債を解消するためのGCマーク作業は残っています。しかし、`handoffp`はGC作業を考慮しないため、Pをアイドル状態にしてしまいます。結果として、GC作業を実行するMが起動されず、GCアシストを待つG1も、バックグラウンドマークワーカーも、永遠に待機することになり、システム全体が停止します。

この問題は、`findrunnable`がGC作業を考慮する一方で、`handoffp`が考慮しないという不整合によって引き起こされていました。この不整合が、`runtime.LockOSThread`のような特定のMにGを固定するメカニズムと組み合わさることで、デッドロックという形で顕在化しました。

## コアとなるコードの解説

このコミットの核心は、`handoffp`関数にGC作業の存在をチェックするロジックを追加したことです。

変更前は、`handoffp`はPのローカル実行キュー (`!runqempty(_p_)`) またはグローバル実行キュー (`sched.runqsize != 0`) にユーザーGoroutineが存在する場合にのみ、`startm`を呼び出して新しいMを起動していました。これにより、Pがアイドル状態になるのを防ぎ、Goroutineの実行を継続させます。

追加されたコードブロック:
```go
	// if it has GC work, start it straight away
	if gcBlackenEnabled != 0 && gcMarkWorkAvailable(_p_) {
		startm(_p_, false)
		return
	}
```
このコードは、既存のユーザーGoroutineのチェックの直後に追加されています。
*   `gcBlackenEnabled != 0`: これはGCのマークフェーズがアクティブであることを示します。GCが実行中でなければ、GC作業をチェックする必要はありません。
*   `gcMarkWorkAvailable(_p_)`: この関数は、指定されたPにGCマーク作業が残っているかどうかをチェックします。具体的には、PのローカルGCワークキューやグローバルGCワークキューに作業があるかを確認します。

この条件が真（GCがアクティブで、かつGCマーク作業が利用可能）であれば、`handoffp`は直ちに`startm(_p_, false)`を呼び出して新しいMを起動し、そのMにPを割り当ててGC作業を実行させます。これにより、GC作業が残っているにもかかわらずPがアイドル状態になることを防ぎ、デッドロックを回避します。

この変更は、コミットメッセージで述べられている「`findrunnable`がPで実行するGを返すような状況では、`handoffp`はそのPで作業を実行するためにMを起動する」という重要な不変条件を再導入します。つまり、`findrunnable`がGC作業を「実行すべき仕事」と認識するのと同様に、`handoffp`もGC作業を認識し、それに応じてMを起動するようになったことで、スケジューラの挙動の一貫性が保たれ、デッドロックが解消されました。

# [インデックス 22139] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）におけるメソッドセレクタの挙動に関するバグ修正です。具体的には、名前付きポインタ型（`type P *S` のような型）に対してメソッドを呼び出す際に、コンパイラが暗黙的にポインタをデリファレンスしてメソッドを解決してしまう問題を修正しています。この挙動は、Goの型システムにおけるメソッド解決のルールに反しており、予期せぬ動作やコンパイルエラーの回避を引き起こす可能性がありました。

## 変更の背景

Go言語では、メソッドはレシーバ（メソッドが関連付けられる型）に関連付けられます。レシーバには値レシーバとポインタレシーバの2種類があります。Goコンパイラは、メソッド呼び出しの際に、レシーバの型とメソッドのレシーバ型が一致しない場合でも、特定の条件下で自動的な変換（ポインタのデリファレンスやアドレス取得）を行います。

このコミット以前は、Goコンパイラ（`cmd/internal/gc`）が、**名前付きポインタ型**（例: `type P *S`）に対してメソッドを呼び出す際に、そのポインタ型を暗黙的にデリファレンスして、基底の型（例: `*S` や `S`）のメソッドを解決しようとする誤った挙動がありました。これは、Goの言語仕様におけるメソッドセットのルール、特に名前付き型と基底型のメソッドセットの違いに反していました。

具体的には、`type P *S` という型 `P` は、基底型 `*S` とは異なる型であり、`P` 自身のメソッドセットは `*S` のメソッドセットとは直接的に同じではありません。しかし、コンパイラが `P` のメソッド解決時に `*P` を `*S` として扱い、さらに `*S` を `S` として自動的にデリファレンスして `S` のメソッドを解決しようとしていました。これにより、本来コンパイルエラーとなるべきコードが誤ってコンパイルされてしまう問題が発生していました。

この問題は、Goの型システムの厳密性を損ない、開発者が予期しない動作に遭遇する可能性がありました。このコミットは、この誤った自動デリファレンスを禁止し、言語仕様に準拠した厳密なメソッド解決を行うように修正することを目的としています。

## 前提知識の解説

### Goのメソッドとレシーバ

Go言語のメソッドは、特定の型に関連付けられた関数です。メソッドの定義には「レシーバ」と呼ばれる特別な引数が含まれます。レシーバには以下の2種類があります。

1.  **値レシーバ (Value Receiver)**: `func (t T) MethodName() {}` のように定義されます。このメソッドは、型 `T` の値に対して呼び出すことができます。また、型 `*T` のポインタに対しても、コンパイラが自動的にポインタをデリファレンスして値を取得し、メソッドを呼び出すことができます。
2.  **ポインタレシーバ (Pointer Receiver)**: `func (t *T) MethodName() {}` のように定義されます。このメソッドは、型 `*T` のポインタに対して呼び出すことができます。また、型 `T` の値に対しても、コンパイラが自動的にその値のアドレスを取得し、ポインタとしてメソッドを呼び出すことができます。

### 型定義と名前付き型

Goでは、`type MyInt int` のように既存の型に新しい名前を付けて「名前付き型 (Named Type)」を定義できます。名前付き型は、その基底型 (Underlying Type) とは異なる独立した型として扱われます。

*   **名前付き型**: `type P *S` の `P` のように、`type` キーワードで定義された型。
*   **基底型**: `P` の場合は `*S`。`*S` の基底型は `S`。

重要なのは、名前付き型は基底型とは異なるメソッドセットを持つということです。基底型のメソッドは自動的に名前付き型に継承されるわけではありません。

### メソッドセット (Method Sets)

Goの各型は「メソッドセット」と呼ばれる、その型が持つメソッドの集合を持っています。

*   型 `T` のメソッドセットは、レシーバが `T` であるすべてのメソッドを含みます。
*   型 `*T` のメソッドセットは、レシーバが `T` または `*T` であるすべてのメソッドを含みます。

このルールにより、ポインタ型は対応する値型のメソッドも呼び出すことができますが、その逆は常に真ではありません（ポインタレシーバのメソッドは値型からは直接呼び出せない場合がある）。

### 自動デリファレンスとアドレス取得

Goコンパイラは、メソッド呼び出しの際に、レシーバの型とメソッドのレシーバ型が一致しない場合に、利便性のために暗黙的な変換を行います。

*   `var t T; (&t).Method()` のようにポインタレシーバのメソッドを値 `t` に対して呼び出す場合、コンパイラは自動的に `&t` を生成します。
*   `var pt *T; (*pt).Method()` のように値レシーバのメソッドをポインタ `pt` に対して呼び出す場合、コンパイラは自動的に `*pt` をデリファレンスします。

しかし、この自動変換は、**名前付きポインタ型**に対しては、その名前付き型が持つメソッドセットの解決において、基底型への自動デリファレンスを伴うべきではありません。名前付きポインタ型は、その基底型とは異なる型として扱われるため、その型自身に定義されたメソッドのみが直接適用されるべきです。

## 技術的詳細

このバグは、Goコンパイラの型チェックフェーズ、特にメソッドセレクタ（`.`演算子）の処理において発生していました。Goコンパイラは、`expr.Method()` のような形式の式を処理する際に、`expr` の型から `Method` という名前のメソッドを探します。

問題の核心は、`cmd/internal/gc/typecheck.go` 内の `lookdot` 関数にありました。この関数は、セレクタ（`.`）の左側の式（レシーバ）の型からメソッドを検索する役割を担っています。以前の実装では、`lookdot` が名前付きポインタ型（例: `P` が `*S` の名前付き型）を受け取った際に、その型がポインタであると判断すると、そのポインタを暗黙的にデリファレンスして基底の型（例: `S`）のメソッドセットを検索しようとしていました。

具体的には、`P` 型の変数 `p` に対して `p.mS()` のようなメソッド呼び出しがあった場合、コンパイラは `P` がポインタ型であるため、`*p` を評価し、その結果の型（`S`）のメソッドセットから `mS` を探していました。しかし、Goの言語仕様では、名前付きポインタ型 `P` は、その基底型 `*S` とは異なる型であり、`P` のメソッドセットは `P` 自身に定義されたメソッドのみを含みます。`*S` や `S` のメソッドは、`P` のメソッドセットには含まれません。したがって、`p.mS()` は、`P` に `mS` メソッドが定義されていない限り、コンパイルエラーとなるべきでした。

この誤った挙動は、特にインターフェースの型アサーションや代入において問題を引き起こす可能性がありました。例えば、`I` インターフェースが `mT()` メソッドを持つ場合、`var p P` に対して `i = p` のような代入が行われた際に、コンパイラが `p` を `*S` として、さらに `S` として自動的にデリファレンスして `S` の `mT()` メソッドを解決しようとすると、本来は型不一致でエラーとなるべきところが、誤って成功してしまう可能性がありました。

修正は、`lookdot` 関数において、レシーバが「名前付きポインタ型」である場合に、その型が暗黙的にデリファレンスされることを明示的に禁止するロジックを追加することで行われました。これにより、名前付きポインタ型は、その型自身に定義されたメソッドのみを解決対象とし、基底型への自動デリファレンスは行われなくなりました。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/internal/gc/subr.go`**:
    *   `out:` ラベルの直前、`for c := d - 1; c >= 0; c-- { ... }` ループ内に新しい条件分岐が追加されました。
    *   `n.Left.Type != nil && Isptr[n.Left.Type.Etype] != 0` という条件で、左側の式がポインタ型である場合に `n.Left.Implicit = 1` を設定しています。これは、後続の型チェックでこのポインタが暗黙的にデリファレンスされたものであることを示すフラグです。

2.  **`src/cmd/internal/gc/typecheck.go`**:
    *   `func lookdot(...)` 関数内に新しいロジックが追加されました。
    *   `ll := n.Left` から始まり、`for ll.Left != nil { ll = ll.Left }` でセレクタチェーンの最も左のノード（元のレシーバ式）を取得しています。
    *   `if ll.Implicit != 0 { ... }` のブロック内で、そのノードが暗黙的にデリファレンスされたポインタであるかチェックします。
    *   さらに、`Isptr[ll.Type.Etype] != 0 && ll.Type.Sym != nil && ll.Type.Sym.Def != nil && ll.Type.Sym.Def.Op == OTYPE` という条件で、それが「名前付きポインタ型」であるかを厳密にチェックしています。
    *   この条件が真の場合、つまり名前付きポインタ型が暗黙的にデリファレンスされた場合は、`n.Left = ll` と設定し、`return false` を返すことで、メソッド解決を失敗させ、コンパイルエラーを発生させます。これは、エラーメッセージをより明確にするための措置でもあります。

3.  **`test/fixedbugs/issue9017.go`**:
    *   このファイルは新規追加されたテストケースで、バグを再現し、修正後の正しい挙動（コンパイルエラー）を検証します。
    *   `type T struct{ x int }`, `func (T) mT() {}`
    *   `type S struct { T }`, `func (S) mS() {}`
    *   `type P *S` という名前付きポインタ型を定義しています。
    *   テストケースの重要な部分は、`var p P = ps` の後に続く `p.mS()` と `p.mT()` の呼び出しです。これらは、`P` 型には `mS` や `mT` メソッドが直接定義されていないため、修正後は「undefined」エラーとなるべきです。
    *   また、インターフェースへの代入 `i = p` や `i = p.T` も、型不一致でエラーとなるべきことを検証しています。

この変更は `lookdot` 関数の核心部分です。
1.  `ll := n.Left` から始まるループは、セレクタチェーンの最も根元にあるノード（つまり、元のレシーバ式）を取得します。例えば `p.T.mT()` の場合、`p` のノードが `ll` になります。
2.  `if ll.Implicit != 0` は、その根元ノードが `subr.go` で設定されたように、コンパイラによって暗黙的にデリファレンスされた結果であるかをチェックします。
3.  内側の `if` 文 `Isptr[ll.Type.Etype] != 0 && ll.Type.Sym != nil && ll.Type.Sym.Def != nil && ll.Type.Sym.Def.Op == OTYPE` が、この修正の最も重要な部分です。

    *   `ll.Type.Sym != nil`: 型にシンボルが関連付けられているか（名前付き型である可能性を示唆）。

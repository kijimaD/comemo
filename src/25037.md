# [インデックス 25037] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `src/cmd/compile/internal/gc` 内の `const.go` および `walk.go` ファイルに対する変更です。

*   `src/cmd/compile/internal/gc/const.go`: このファイルは、Goコンパイラにおける定数評価（constant evaluation）のロジックを扱います。特に、コンパイル時に値が確定する式（定数式）の評価を担当し、文字列リテラル間の比較などもここで行われます。
*   `src/cmd/compile/internal/gc/walk.go`: このファイルは、Goコンパイラの「ウォーク（walk）」フェーズの一部を構成します。ウォークフェーズでは、抽象構文木（AST）を走査し、型チェック、定数畳み込み、最適化、コード生成のための準備など、様々な変換を行います。

## コミット

Goコンパイラ (`cmd/compile/internal/gc`) において、文字列リテラル間の比較を行う際に、`strings.Compare` 関数を使用するのを避けるように変更されました。これにより、コンパイル時の定数評価の効率が向上します。

## 変更の背景

この変更の背景には、Goコンパイラにおける最適化の追求があります。Go言語では、文字列リテラル（例: `"hello"`）はコンパイル時にその値が完全に既知であり、不変です。このような文字列リテラル間の比較（`==`, `!=`, `<`, `<=`, `>`, `>=`）は、実行時に汎用的な文字列比較関数（`strings.Compare`）を呼び出すよりも、コンパイル時に直接評価するか、より効率的なコードを生成することが可能です。

`strings.Compare` は、任意の2つの文字列を比較するための汎用的な関数であり、内部的にはバイト列の比較を行います。しかし、コンパイル時に値が確定している文字列リテラルに対してこの関数を呼び出すことは、不要な関数呼び出しのオーバーヘッドや、コンパイラがより直接的な比較ロジックを生成する機会を奪うことになります。

このコミットは、コンパイル時の定数評価において、文字列リテラル間の比較を `strings.Compare` を介さず、Go言語の組み込み比較演算子（`==`, `<`, `>`など）を直接利用するように変更することで、コンパイラの効率を向上させることを目的としています。これにより、コンパイル時間の短縮や、場合によっては生成されるバイナリのパフォーマンス向上に寄与する可能性があります。

## 前提知識の解説

### Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、`cmd/compile` ディレクトリ以下に存在します。その中でも `internal/gc` は、Go言語のフロントエンドとバックエンドの大部分を担う主要なパッケージです。ソースコードのパース、抽象構文木（AST）の構築、型チェック、定数評価、最適化、中間表現（IR）への変換、そして最終的な機械語コードの生成まで、コンパイルプロセスの中心的な役割を果たします。

### `Node` とは何か (ASTノード)

Goコンパイラは、ソースコードを解析して抽象構文木（AST: Abstract Syntax Tree）を構築します。ASTは、プログラムの構造を木構造で表現したものです。この木構造の各要素が `Node` と呼ばれます。`Node` は、変数、定数、演算子、関数呼び出し、制御構造など、プログラムのあらゆる構成要素を表します。コンパイラは、この `Node` を走査し、情報を付加し、変換していくことでコンパイルを進めます。

### `CTSTR` (Compile-Time String) とは何か

`CTSTR` は "Compile-Time String" の略で、Goコンパイラが内部的に使用する定数型の一つです。これは、コンパイル時にその値が完全に既知である文字列リテラルを表します。例えば、`"hello world"` のような文字列は `CTSTR` として扱われ、コンパイル時にその値が確定しているため、様々な最適化の対象となります。

### `strings.Compare` 関数の動作とコスト

Go標準ライブラリの `strings.Compare(a, b string) int` 関数は、2つの文字列 `a` と `b` を辞書順に比較し、以下のいずれかの整数を返します。
*   `a == b` の場合: `0`
*   `a < b` の場合: `-1`
*   `a > b` の場合: `1`

この関数は、文字列のバイト列を比較することで動作します。実行時に呼び出される関数であるため、関数呼び出しのオーバーヘッド、引数の準備、戻り値の処理といったコストが発生します。コンパイル時に値が既知の文字列リテラルに対してこの関数を使用することは、これらのオーバーヘッドが不要であるため、非効率的と見なされます。

### Goにおける文字列リテラルの比較の特性 (コンパイル時評価)

Go言語では、文字列リテラルは不変であり、コンパイル時にその値が確定します。コンパイラは、このような定数式をコンパイル時に評価（定数畳み込み）して、結果を直接コードに埋め込むことができます。例えば、`"a" == "a"` のような式は、実行時に比較を行うまでもなく、コンパイル時に `true` であると評価できます。この最適化は、プログラムの実行効率を高める上で非常に重要です。

### `OEQ`, `ONE`, `OLT`, `OLE`, `OGE`, `OGT` などの演算子定数

これらはGoコンパイラがASTノードの操作（`Node.Op`フィールドなど）に使用する内部的な定数で、それぞれ以下の演算子を表します。
*   `OEQ`: 等しい (`==`)
*   `ONE`: 等しくない (`!=`)
*   `OLT`: より小さい (`<`)
*   `OLE`: より小さいか等しい (`<=`)
*   `OGE`: より大きいか等しい (`>=`)
*   `OGT`: より大きい (`>`)

これらの定数は、コンパイラがASTを走査し、特定の演算子を見つけたときに、それに応じた処理を行うために使われます。

## 技術的詳細

このコミットの核心は、Goコンパイラの定数評価ロジックにおいて、文字列リテラル間の比較をより直接的かつ効率的な方法に切り替えた点にあります。

変更前は、`const.go` 内の `evconst` 関数において、文字列リテラル（`CTSTR`）間の比較（`OEQ`, `ONE`, `OLT`, `OLE`, `OGE`, `OGT`）を行う際に、`cmpslit` というヘルパー関数を呼び出していました。この `cmpslit` 関数は、内部でGo標準ライブラリの `strings.Compare` 関数を呼び出し、その結果に基づいて比較を行っていました。

```go
// 変更前のcmpslit関数
func cmpslit(l, r *Node) int {
	return stringsCompare(l.Val().U.(string), r.Val().U.(string))
}
```

このアプローチの問題点は、コンパイル時に値が完全に既知である文字列リテラルに対して、実行時関数である `strings.Compare` を呼び出すための準備やオーバーヘッドが発生することです。コンパイラは、文字列リテラルの値を直接取得し、Go言語の組み込みの文字列比較演算子（`==`, `<`, `>`など）を適用することで、より効率的に比較結果を導き出すことができます。

このコミットでは、以下の変更が行われました。

1.  **`cmpslit` 関数の削除**: `strings.Compare` を呼び出していた `cmpslit` 関数が削除されました。
2.  **`strlit` 関数の導入**: `Node` から文字列リテラルの値（`string`型）を直接抽出するための新しいヘルパー関数 `strlit` が導入されました。

    ```go
    // 新しく導入されたstrlit関数
    // strlit returns the value of a literal string Node as a string.
    func strlit(n *Node) string {
    	return n.Val().U.(string)
    }
    ```

    この関数は、`Node` の `Val()` メソッドで取得した値（`U`フィールドに格納されているインターフェース値）を直接 `string` 型に型アサートすることで、文字列リテラルの値を取得します。
3.  **`evconst` 関数内の比較ロジックの変更**: `const.go` の `evconst` 関数内で、文字列リテラル間の比較を行う箇所が、`cmpslit` の呼び出しから `strlit` を使った直接的なGoの比較演算子に置き換えられました。

    例えば、等価比較（`OEQ`）の場合、変更前は `cmpslit(nl, nr) == 0` でしたが、変更後は `strlit(nl) == strlit(nr)` となりました。他の比較演算子（`ONE`, `OLT`, `OLE`, `OGE`, `OGT`）についても同様に、`strlit` を介した直接比較に置き換えられています。

4.  **`walk.go` 内の変更**: `walk.go` 内にも、文字列リテラル間の比較を行っていた箇所があり、ここも `cmpslit` の呼び出しから `strlit` を使った直接比較に修正されました。これは、特定の最適化パターン（例: `s + "literal" == "literal"` のような式）を処理する際に、文字列リテラルの比較を効率化するためです。

この変更により、コンパイラは文字列リテラルの比較を、より低レベルで直接的な方法で処理できるようになります。これにより、コンパイル時の定数評価のパスが簡素化され、不要な関数呼び出しのオーバーヘッドが削減されます。結果として、コンパイラのパフォーマンスが向上し、Goプログラムのビルド時間が短縮される可能性があります。

コミットメッセージにある `Passes go build -a -toolexec 'toolstash -cmp' std cmp.` は、この変更がGo標準ライブラリのビルドとテストに悪影響を与えないことを確認するためのテストコマンドです。`toolstash -cmp` は、変更前後のコンパイラで生成されるコードを比較し、意図しない変更がないかを確認するツールです。これにより、変更の安全性が保証されています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/const.go` の変更

`evconst` 関数は、Goコンパイラが定数式を評価する主要な場所です。`switch` ステートメント内で、演算子の種類（`OEQ`, `ONE` など）とオペランドの型（`CTSTR`）の組み合わせに基づいて、異なる定数評価ロジックが適用されます。

変更前は、文字列リテラル間の比較を行う各 `case` ブロックで `cmpslit(nl, nr)` が呼び出されていました。`nl` と `nr` は比較対象の左右の `Node` を表します。`cmpslit` は `strings.Compare` をラップしていたため、このパスでは常にランタイム関数が呼び出されていました。

変更後は、`cmpslit` 関数が削除され、代わりに新しく導入された `strlit` 関数を使用して `Node` から直接文字列値を取得し、Go言語の組み込み比較演算子（`==`, `!=`, `<`, `<=`, `>`, `>=`）で比較するように変更されました。

例: `OEQ<<16 | CTSTR` のケース（文字列リテラルの等価比較）
*   **変更前**: `if cmpslit(nl, nr) == 0 { goto settrue }`
*   **変更後**: `if strlit(nl) == strlit(nr) { goto settrue }`

この変更により、コンパイラは文字列リテラルの値を直接比較できるため、`strings.Compare` の呼び出しに伴うオーバーヘッドがなくなります。これは、コンパイル時の定数畳み込みの効率を向上させる直接的な最適化です。

また、`cmpslit` 関数が削除され、その代わりに `strlit` 関数が追加されました。`strlit` は `Node` オブジェクトからその文字列リテラル値（`string`型）を安全に抽出するシンプルなヘルパー関数です。`n.Val().U.(string)` は、`Node` の値が格納されている `Val()` メソッドの戻り値（`Val`構造体）の `U` フィールド（インターフェース型）を `string` 型に型アサートしています。これは、コンパイラが `CTSTR` 型の `Node` の `U` フィールドに文字列値が格納されていることを知っているため、安全に行える操作です。

### `src/cmd/compile/internal/gc/walk.go` の変更

`walk.go` の変更は、特定の最適化パターンに関連しています。コメント `// s + "badgerbadgerbadger" == "badgerbadgerbadger"` が示すように、これは文字列連結と文字列リテラルの比較を含む式を最適化する部分です。

変更前は、この最適化ロジック内で `cmpslit(n.Right, n.Left.List.Next.N) == 0` を使用して、右辺の文字列リテラルと連結された文字列リテラルが等しいかどうかを比較していました。

変更後は、ここでも `cmpslit` の代わりに `strlit` を使用した直接比較 `strlit(n.Right) == strlit(n.Left.List.Next.N)` に置き換えられました。これにより、`walk` フェーズにおけるこの特定の最適化パスも、より効率的な文字列リテラル比較の恩恵を受けることになります。

### `Node` とは何か (ASTノード)

Goコンパイラは、ソースコードを解析して抽象構文木（AST: Abstract Syntax Tree）を構築します。ASTは、プログラムの構造を木構造で表現したものです。この木構造の各要素が `Node` と呼ばれます。`Node` は、変数、定数、演算子、関数呼び出し、制御構造など、プログラムのあらゆる構成要素を表します。コンパイラは、この `Node` を走査し、情報を付加し、変換していくことでコンパイルを進めます。

### `CTSTR` (Compile-Time String) とは何か

`CTSTR` は "Compile-Time String" の略で、Goコンパイラが内部的に使用する定数型の一つです。これは、コンパイル時にその値が完全に既知である文字列リテラルを表します。例えば、`"hello world"` のような文字列は `CTSTR` として扱われ、コンパイル時にその値が確定しているため、様々な最適化の対象となります。

### `strings.Compare` 関数の動作とコスト

Go標準ライブラリの `strings.Compare(a, b string) int` 関数は、2つの文字列 `a` と `b` を辞書順に比較し、以下のいずれかの整数を返します。
*   `a == b` の場合: `0`
*   `a < b` の場合: `-1`
*   `a > b` の場合: `1`

この関数は、文字列のバイト列を比較することで動作します。実行時に呼び出される関数であるため、関数呼び出しのオーバーヘッド、引数の準備、戻り値の処理といったコストが発生します。コンパイル時に値が既知の文字列リテラルに対してこの関数を使用することは、これらのオーバーヘッドが不要であるため、非効率的と見なされます。

### Goにおける文字列リテラルの比較の特性 (コンパイル時評価)

Go言語では、文字列リテラルは不変であり、コンパイル時にその値が確定します。コンパイラは、このような定数式をコンパイル時に評価（定数畳み込み）して、結果を直接コードに埋め込むことができます。例えば、`"a" == "a"` のような式は、実行時に比較を行うまでもなく、コンパイル時に `true` であると評価できます。この最適化は、プログラムの実行効率を高める上で非常に重要です。

### `OEQ`, `ONE`, `OLT`, `OLE`, `OGE`, `OGT` などの演算子定数

これらはGoコンパイラがASTノードの操作（`Node.Op`フィールドなど）に使用する内部的な定数で、それぞれ以下の演算子を表します。
*   `OEQ`: 等しい (`==`)
*   `ONE`: 等しくない (`!=`)
*   `OLT`: より小さい (`<`)
*   `OLE`: より小さいか等しい (`<=`)
*   `OGE`: より大きいか等しい (`>=`)
*   `OGT`: より大きい (`>`)

これらの定数は、コンパイラがASTを走査し、特定の演算子を見つけたときに、それに応じた処理を行うために使われます。

## 技術的詳細

このコミットの核心は、Goコンパイラの定数評価ロジックにおいて、文字列リテラル間の比較をより直接的かつ効率的な方法に切り替えた点にあります。

変更前は、`const.go` 内の `evconst` 関数において、文字列リテラル（`CTSTR`）間の比較（`OEQ`, `ONE`, `OLT`, `OLE`, `OGE`, `OGT`）を行う際に、`cmpslit` というヘルパー関数を呼び出していました。この `cmpslit` 関数は、内部でGo標準ライブラリの `strings.Compare` 関数を呼び出し、その結果に基づいて比較を行っていました。

```go
// 変更前のcmpslit関数
func cmpslit(l, r *Node) int {
	return stringsCompare(l.Val().U.(string), r.Val().U.(string))
}
```

このアプローチの問題点は、コンパイル時に値が完全に既知である文字列リテラルに対して、実行時関数である `strings.Compare` を呼び出すための準備やオーバーヘッドが発生することです。コンパイラは、文字列リテラルの値を直接取得し、Go言語の組み込みの文字列比較演算子（`==`, `<`, `>`など）を適用することで、より効率的に比較結果を導き出すことができます。

このコミットでは、以下の変更が行われました。

1.  **`cmpslit` 関数の削除**: `strings.Compare` を呼び出していた `cmpslit` 関数が削除されました。
2.  **`strlit` 関数の導入**: `Node` から文字列リテラルの値（`string`型）を直接抽出するための新しいヘルパー関数 `strlit` が導入されました。

    ```go
    // 新しく導入されたstrlit関数
    // strlit returns the value of a literal string Node as a string.
    func strlit(n *Node) string {
    	return n.Val().U.(string)
    }
    ```

    この関数は、`Node` の `Val()` メソッドで取得した値（`U`フィールドに格納されているインターフェース値）を直接 `string` 型に型アサートすることで、文字列リテラルの値を取得します。
3.  **`evconst` 関数内の比較ロジックの変更**: `const.go` の `evconst` 関数内で、文字列リテラル間の比較を行う箇所が、`cmpslit` の呼び出しから `strlit` を使った直接的なGoの比較演算子に置き換えられました。

    例えば、等価比較（`OEQ`）の場合、変更前は `cmpslit(nl, nr) == 0` でしたが、変更後は `strlit(nl) == strlit(nr)` となりました。他の比較演算子（`ONE`, `OLT`, `OLE`, `OGE`, `OGT`）についても同様に、`strlit` を介した直接比較に置き換えられています。

4.  **`walk.go` 内の変更**: `walk.go` 内にも、文字列リテラル間の比較を行っていた箇所があり、ここも `cmpslit` の呼び出しから `strlit` を使った直接比較に修正されました。これは、特定の最適化パターン（例: `s + "literal" == "literal"` のような式）を処理する際に、文字列リテラルの比較を効率化するためです。

この変更により、コンパイラは文字列リテラルの比較を、より低レベルで直接的な方法で処理できるようになります。これにより、コンパイル時の定数評価のパスが簡素化され、不要な関数呼び出しのオーバーヘッドが削減されます。結果として、コンパイラのパフォーマンスが向上し、Goプログラムのビルド時間が短縮される可能性があります。

コミットメッセージにある `Passes go build -a -toolexec 'toolstash -cmp' std cmp.` は、この変更がGo標準ライブラリのビルドとテストに悪影響を与えないことを確認するためのテストコマンドです。`toolstash -cmp` は、変更前後のコンパイラで生成されるコードを比較し、意図しない変更がないかを確認するツールです。これにより、変更の安全性が保証されています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/const.go` の変更

`evconst` 関数は、Goコンパイラが定数式を評価する主要な場所です。`switch` ステートメント内で、演算子の種類（`OEQ`, `ONE` など）とオペランドの型（`CTSTR`）の組み合わせに基づいて、異なる定数評価ロジックが適用されます。

変更前は、文字列リテラル間の比較を行う各 `case` ブロックで `cmpslit(nl, nr)` が呼び出されていました。`nl` と `nr` は比較対象の左右の `Node` を表します。`cmpslit` は `strings.Compare` をラップしていたため、このパスでは常にランタイム関数が呼び出されていました。

変更後は、`cmpslit` 関数が削除され、代わりに新しく導入された `strlit` 関数を使用して `Node` から直接文字列値を取得し、Go言語の組み込み比較演算子（`==`, `!=`, `<`, `<=`, `>`, `>=`）で比較するように変更されました。

例: `OEQ<<16 | CTSTR` のケース（文字列リテラルの等価比較）
*   **変更前**: `if cmpslit(nl, nr) == 0 { goto settrue }`
*   **変更後**: `if strlit(nl) == strlit(nr) { goto settrue }`

この変更により、コンパイラは文字列リテラルの値を直接比較できるため、`strings.Compare` の呼び出しに伴うオーバーヘッドがなくなります。これは、コンパイル時の定数畳み込みの効率を向上させる直接的な最適化です。

また、`cmpslit` 関数が削除され、その代わりに `strlit` 関数が追加されました。`strlit` は `Node` オブジェクトからその文字列リテラル値（`string`型）を安全に抽出するシンプルなヘルパー関数です。`n.Val().U.(string)` は、`Node` の値が格納されている `Val()` メソッドの戻り値（`Val`構造体）の `U` フィールド（インターフェース型）を `string` 型に型アサートしています。これは、コンパイラが `CTSTR` 型の `Node` の `U` フィールドに文字列値が格納されていることを知っているため、安全に行える操作です。

### `src/cmd/compile/internal/gc/walk.go` の変更

`walk.go` の変更は、特定の最適化パターンに関連しています。コメント `// s + "badgerbadgerbadger" == "badgerbadgerbadger"` が示すように、これは文字列連結と文字列リテラルの比較を含む式を最適化する部分です。

変更前は、この最適化ロジック内で `cmpslit(n.Right, n.Left.List.Next.N) == 0` を使用して、右辺の文字列リテラルと連結された文字列リテラルが等しいかどうかを比較していました。

変更後は、ここでも `cmpslit` の代わりに `strlit` を使用した直接比較 `strlit(n.Right) == strlit(n.Left.List.Next.N)` に置き換えられました。これにより、`walk` フェーズにおけるこの特定の最適化パスも、より効率的な文字列リテラル比較の恩恵を受けることになります。

# [インデックス 22924] ファイルの概要

このコミットは、Goランタイムにおけるメモリゼロクリア処理のパフォーマンスを改善するものです。特に、`duffzero`と呼ばれるアセンブリルーチンの実装を最適化し、小さなメモリ領域のクリアには`STOSQ`命令を、大きなメモリ領域のクリアには`MOVQ`と`ADDQ`命令の組み合わせをハイブリッドで利用することで、全体的なスループットを向上させています。

## 変更の背景

Go言語のランタイムでは、新しく確保されたメモリ領域をゼロクリアする処理が頻繁に発生します。これはGoのメモリモデルの要件であり、セキュリティと予測可能性を保証するために重要です。このゼロクリア処理は、`duffzero`と呼ばれるアセンブリルーチンによって最適化されています。

従来の`duffzero`の実装では、主に`STOSQ`（Store String Quadword）命令を使用してメモリをゼロクリアしていました。`STOSQ`は`RAX`レジスタの内容を`RDI`レジスタが指すメモリ位置にストアし、`RDI`を自動的にインクリメントする命令で、ループ処理を効率化するのに適しています。

しかし、このコミットの背景には、より高速なメモリクリア方法の探求がありました。コミットメッセージが示唆するように、`MOVQ AX,(DI)`、`MOVQ AX,8(DI)`、`MOVQ AX,16(DI)`、`MOVQ AX,24(DI)`といった複数の`MOVQ`命令と、それに続く`ADDQ $32,DI`（`DI`レジスタを32バイト進める）の組み合わせが、`STOSQ`を連続して実行するよりもスループットが高いことが判明しました。これは、現代のCPUのパイプライン処理やキャッシュの振る舞いにおいて、`MOVQ`命令がより効率的に実行される場合があるためと考えられます。

しかし、`MOVQ`ブロックを使用する際には課題がありました。`duffzero`のようなDuff's Deviceの最適化では、特定のバイト数だけメモリをクリアするために、ルーチンの中間地点にジャンプして処理を開始することがあります。`STOSQ`の場合は、各命令が同じサイズで、`DI`の自動インクリメントも一貫しているため、ジャンプ先と`DI`の調整が比較的単純でした。しかし、`MOVQ`ブロックの場合、ジャンプして処理を開始するためには、事前に`DI`レジスタを適切に調整（プリ・アジャスト）する必要がありました。この`DI`のプリ・アジャストにはオーバーヘッドが伴い、特にクリアするメモリ領域が小さい場合には、そのオーバーヘッドが`MOVQ`ブロックによるパフォーマンス向上を相殺してしまう、あるいは逆に遅くなる可能性がありました。

このコミットは、このジレンマを解決し、あらゆるサイズのメモリクリアにおいて最適なパフォーマンスを達成するために導入されました。

## 前提知識の解説

### 1. Goランタイムとメモリ管理

Go言語はガベージコレクション（GC）を備えた言語であり、メモリ管理はランタイムが担当します。プログラムが新しいメモリを要求すると、ランタイムはヒープからメモリを割り当てます。この際、Goの仕様により、割り当てられたメモリは必ずゼロ値で初期化される必要があります。これにより、未初期化のメモリ内容に依存するバグを防ぎ、プログラムの安全性を高めます。このゼロクリア処理は、Goアプリケーションのパフォーマンスに直接影響するため、非常に効率的に行われる必要があります。

### 2. Duff's Device (ダフのデバイス)

Duff's Deviceは、ループのオーバーヘッドを削減するために使用されるプログラミングのテクニックです。特に、固定回数の繰り返し処理を効率的に行うためにアセンブリ言語で実装されることが多いです。通常のループでは、各イテレーションでカウンタのデクリメントと条件分岐が発生しますが、Duff's Deviceでは、処理の開始位置をジャンプで調整することで、これらのオーバーヘッドを最小限に抑えます。

例えば、N回繰り返す処理がある場合、Duff's DeviceはNをブロックサイズで割った商と余りを計算し、余りに応じてループの途中から処理を開始し、その後はブロック単位で処理を進めます。これにより、ループの開始と終了のチェックを減らし、CPUのパイプライン予測を助け、全体的なスループットを向上させます。Goランタイムの`duffzero`は、このDuff's Deviceの原理をメモリゼロクリアに応用したものです。

### 3. x86-64 アセンブリ命令

*   **`STOSQ` (Store String Quadword)**:
    *   `RAX`レジスタ（64ビット）の内容を`RDI`レジスタが指すメモリ位置にストアします。
    *   その後、`RDI`レジスタの値を8（クアッドワードのサイズ）だけ自動的にインクリメント（またはデクリメント、DFフラグによる）します。
    *   `REP`プレフィックスと組み合わせることで、`RCX`レジスタで指定された回数だけこの操作を繰り返すことができ、効率的なブロック操作が可能です。メモリを連続してゼロクリアする際に非常に便利です。

*   **`MOVQ` (Move Quadword)**:
    *   64ビットのデータを移動する命令です。
    *   例: `MOVQ AX,(DI)` は、`AX`レジスタ（実際には`RAX`レジスタの下位部分、または`RAX`全体）の内容を、`DI`レジスタ（実際には`RDI`）が指すメモリ位置にストアします。
    *   `MOVQ AX,8(DI)` は、`DI`が指すアドレスから8バイトオフセットした位置にストアします。
    *   `MOVQ`命令は、特定のメモリ位置に値を書き込むための基本的な命令であり、`STOSQ`のように自動的なポインタのインクリメントは行いません。

*   **`ADDQ` (Add Quadword)**:
    *   64ビットの値を加算する命令です。
    *   例: `ADDQ $32,DI` は、`DI`レジスタに即値`32`を加算します。これは、`MOVQ`命令を複数回使用して32バイト分のメモリを処理した後、次のブロックの開始位置に`DI`を移動させるために使用されます。

### 4. レジスタ

*   **`AX` / `RAX` (Accumulator Register)**: 汎用レジスタで、通常は演算結果や関数の戻り値を保持します。メモリゼロクリアでは、ゼロ値（0x0000000000000000）を保持するために使われます。
*   **`DI` / `RDI` (Destination Index Register)**: 汎用レジスタで、通常はメモリ操作の宛先アドレスを保持します。`STOSQ`や`MOVQ`命令で書き込み先のポインタとして使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムの`duffzero`ルーチンにおけるメモリゼロクリア戦略の変更です。

### 従来の`STOSQ`ベースの実装

以前の`duffzero`は、主に`STOSQ`命令を連続して使用していました。`STOSQ`は`RAX`レジスタの内容（ゼロ）を`RDI`が指すメモリに書き込み、`RDI`を8バイト進めるため、非常にコンパクトで効率的なループを構築できました。Duff's Deviceの原理により、必要なバイト数に応じて`duffzero`ルーチン内の適切な`STOSQ`命令の開始位置にジャンプすることで、ループのオーバーヘッドを最小限に抑えていました。

### `MOVQ`/`ADDQ`ブロックの導入

コミットメッセージが示すように、`MOVQ AX,(DI)`、`MOVQ AX,8(DI)`、`MOVQ AX,16(DI)`、`MOVQ AX,24(DI)`の4つの`MOVQ`命令と、それに続く`ADDQ $32,DI`という命令シーケンスは、32バイトのメモリをゼロクリアし、`DI`を32バイト進めます。このブロックは、`STOSQ`を4回実行するよりも高速であることがベンチマークで示されました。これは、現代のCPUが複数の`MOVQ`命令を並列に実行できる能力や、キャッシュラインの効率的な利用によるものと考えられます。

### `DI`のプリ・アジャスト問題

`MOVQ`ブロックをDuff's Deviceとして利用する際の課題は、ジャンプしてルーチンの中間地点から実行する場合に、`DI`レジスタの事前調整が必要になる点です。`STOSQ`は常に8バイトずつ`DI`を進めますが、`MOVQ`ブロックは32バイト単位で`DI`を進めます。もし、クリアしたいバイト数が32の倍数でない場合、またはブロックの途中から実行を開始する場合、`DI`が指すアドレスが期待する開始位置とずれてしまう可能性があります。このずれを補正するために、`duffzero`ルーチンを呼び出す前に`DI`を適切に調整する必要がありました。この調整自体が小さなオーバーヘッドとなり、特にクリアするメモリ領域が小さい場合には、`MOVQ`ブロックの利点を打ち消してしまう可能性がありました。

### ハイブリッド戦略の採用

このコミットでは、上記の課題を解決するためにハイブリッド戦略が採用されました。

1.  **小さなクリア領域**: クリアするメモリ領域が非常に小さい場合（コミットメッセージでは`dzTailLen`、つまり4ワード以下）、`DI`のプリ・アジャストのオーバーヘッドが大きくなるため、引き続き従来の`STOSQ`命令を使用します。これにより、小さなクリアにおけるパフォーマンスの低下を防ぎます。
2.  **大きなクリア領域**: クリアするメモリ領域が大きい場合、`MOVQ`/`ADDQ`ブロックのパフォーマンス上の利点が`DI`のプリ・アジャストのオーバーヘッドを上回るため、主に`MOVQ`/`ADDQ`ブロックを使用します。

具体的には、`src/runtime/duff_amd64.s`の`runtime·duffzero`ルーチンは、複数の`MOVQ`/`ADDQ`ブロックの後に、少数の`STOSQ`命令を配置する構造に変更されました。`src/cmd/6g/ggen.go`のコンパイラ側では、`zerorange`関数と`clearfat`関数が変更され、クリアするワード数に応じて`DI`のプリ・アジャスト量（`dzDI`関数）と`duffzero`ルーチンへのジャンプオフセット（`dzOff`関数）を計算するようになりました。これにより、コンパイラが生成するコードが、最適な`duffzero`の開始点と`DI`の初期値を決定し、ハイブリッド戦略を効果的に実行します。

ベンチマーク結果は、このハイブリッド戦略が特に中規模から大規模なメモリクリアにおいて顕著なパフォーマンス向上をもたらしたことを明確に示しています。例えば、`BenchmarkClearFat56`では27.39%の改善が見られます。

## コアとなるコードの解説

### `src/cmd/6g/ggen.go` の変更点

このファイルでは、コンパイラが`duffzero`を呼び出す際のロジックが賢くなりました。

```go
// DUFFZERO consists of repeated blocks of 4 MOVs + ADD,
// with 4 STOSQs at the very end.
// The trailing STOSQs prevent the need for a DI preadjustment
// for small numbers of words to clear.
// See runtime/mkduff.go.
const (
	dzBlocks    = 31 // number of MOV/ADD blocks
	dzBlockLen  = 4  // number of clears per block
	dzBlockSize = 19 // size of instructions in a single block
	dzMovSize   = 4  // size of single MOV instruction w/ offset
	dzAddSize   = 4  // size of single ADD instruction
	dzDIStep    = 8  // number of bytes cleared by each MOV instruction

	dzTailLen  = 4 // number of final STOSQ instructions
	dzTailSize = 2 // size of single STOSQ instruction

	dzSize = dzBlocks*dzBlockSize + dzTailLen*dzTailSize // total size of DUFFZERO routine
)

// duffzeroDI returns the pre-adjustment to DI for a call to DUFFZERO.
// q is the number of words to zero.
func dzDI(q int64) int64 {
	if q < dzTailLen {
		return 0
	}
	q -= dzTailLen
	if q%dzBlockLen == 0 {
		return 0
	}
	return -dzDIStep * (dzBlockLen - q%dzBlockLen)
}

// dzOff returns the offset for a jump into DUFFZERO.
// q is the number of words to zero.
func dzOff(q int64) int64 {
	off := int64(dzSize)
	if q < dzTailLen {
		return off - q*dzTailSize
	}
	off -= dzTailLen * dzTailSize
	q -= dzTailLen
	blocks, steps := q/dzBlockLen, q%dzBlockLen
	off -= dzBlockSize * blocks
	if steps > 0 {
		off -= dzAddSize + dzMovSize*steps
	}
	return off
}
```
`dzDI`関数は、クリアするワード数`q`に基づいて、`DI`レジスタをどれだけ事前に調整すべきかを計算します。特に、`q`が`dzTailLen`（4ワード）より小さい場合は調整が不要（`STOSQ`のみで処理されるため）で、それ以外の場合は`MOVQ`ブロックの境界に合わせて`DI`を調整します。
`dzOff`関数は、`duffzero`ルーチン内のどこにジャンプすべきかのオフセットを計算します。これも`q`の値に基づいて、`STOSQ`部分にジャンプするか、`MOVQ`ブロックの適切な開始位置にジャンプするかを決定します。

そして、`zerorange`関数と`clearfat`関数内で、これらの`dzDI`と`dzOff`が実際に使用されます。

### `src/runtime/duff_amd64.s` の変更点

このファイルは、実際の`duffzero`アセンブリルーチンの実装です。

```assembly
// src/runtime/duff_amd64.s (抜粋)
TEXT runtime·duffzero(SB), NOSPLIT, $0-0
	MOVQ	AX,(DI)
	MOVQ	AX,8(DI)
	MOVQ	AX,16(DI)
	MOVQ	AX,24(DI)
	ADDQ	$32,DI

	MOVQ	AX,(DI)
	MOVQ	AX,8(DI)
	MOVQ	AX,16(DI)
	MOVQ	AX,24(DI)
	ADDQ	$32,DI
// ... (上記MOVQ/ADDQブロックが31回繰り返される) ...

	MOVQ	AX,(DI)
	MOVQ	AX,8(DI)
	MOVQ	AX,16(DI)
	MOVQ	AX,24(DI)
	ADDQ	$32,DI

	STOSQ
	STOSQ
	STOSQ
	STOSQ
	RET
```
従来の`STOSQ`の連続から、31個の`MOVQ`/`ADDQ`ブロックと、その後に続く4つの`STOSQ`命令という構造に変わりました。これにより、`dzOff`関数で計算されたオフセットに応じて、ルーチン内の任意の場所（`MOVQ`ブロックの途中、または`STOSQ`の開始点）から実行を開始できるようになります。

### `src/runtime/mkduff.go` の変更点

このGoプログラムは、`duffzero`アセンブリルーチンを自動生成するためのものです。

```go
// src/runtime/mkduff.go (抜粋)
func zeroAMD64(w io.Writer) {
	// ...
	fmt.Fprintln(w, "TEXT runtime·duffzero(SB), NOSPLIT, $0-0")
	for i := 0; i < 31; i++ { // 31個のMOVQ/ADDQブロックを生成
		fmt.Fprintln(w, "\tMOVQ\tAX,(DI)")
		fmt.Fprintln(w, "\tMOVQ\tAX,8(DI)")
		fmt.Fprintln(w, "\tMOVQ\tAX,16(DI)")
		fmt.Fprintln(w, "\tMOVQ\tAX,24(DI)")
		fmt.Fprintln(w, "\tADDQ\t$32,DI")
		fmt.Fprintln(w)
	}
	for i := 0; i < 4; i++ { // 4つのSTOSQ命令を生成
		fmt.Fprintln(w, "\tSTOSQ")
	}
	fmt.Fprintln(w, "\tRET")
}
```
この変更により、`mkduff.go`が生成する`duff_amd64.s`ファイルの内容が、新しいハイブリッド戦略を反映したものになります。

これらの変更が連携することで、Goランタイムはメモリゼロクリア処理をより効率的に実行できるようになり、特に中規模から大規模なメモリ割り当てにおけるパフォーマンスが向上しました。

## 変更の背景

Go言語のランタイムでは、新しく確保されたメモリ領域をゼロクリアする処理が頻繁に発生します。これはGoのメモリモデルの要件であり、セキュリティと予測可能性を保証するために重要です。このゼロクリア処理は、`duffzero`と呼ばれるアセンブリルーチンによって最適化されています。

従来の`duffzero`の実装では、主に`STOSQ`（Store String Quadword）命令を使用してメモリをゼロクリアしていました。`STOSQ`は`RAX`レジスタの内容を`RDI`レジスタが指すメモリ位置にストアし、`RDI`を自動的にインクリメントする命令で、ループ処理を効率化するのに適しています。

しかし、このコミットの背景には、より高速なメモリクリア方法の探求がありました。コミットメッセージが示唆するように、`MOVQ AX,(DI)`、`MOVQ AX,8(DI)`、`MOVQ AX,16(DI)`、`MOVQ AX,24(DI)`といった複数の`MOVQ`命令と、それに続く`ADDQ $32,DI`（`DI`レジスタを32バイト進める）の組み合わせが、`STOSQ`を連続して実行するよりもスループットが高いことが判明しました。これは、現代のCPUのパイプライン処理やキャッシュの振る舞いにおいて、`MOVQ`命令がより効率的に実行される場合があるためと考えられます。

しかし、`MOVQ`ブロックを使用する際には課題がありました。`duffzero`のようなDuff's Deviceの最適化では、特定のバイト数だけメモリをクリアするために、ルーチンの中間地点にジャンプして処理を開始することがあります。`STOSQ`の場合は、各命令が同じサイズで、`DI`の自動インクリメントも一貫しているため、ジャンプ先と`DI`の調整が比較的単純でした。しかし、`MOVQ`ブロックの場合、ジャンプして処理を開始するためには、事前に`DI`レジスタを適切に調整（プリ・アジャスト）する必要がありました。この`DI`のプリ・アジャストにはオーバーヘッドが伴い、特にクリアするメモリ領域が小さい場合には、そのオーバーヘッドが`MOVQ`ブロックによるパフォーマンス向上を相殺してしまう、あるいは逆に遅くなる可能性がありました。

このコミットは、このジレンマを解決し、あらゆるサイズのメモリクリアにおいて最適なパフォーマンスを達成するために導入されました。

## 前提知識の解説

### 1. Goランタイムとメモリ管理

Go言語はガベージコレクション（GC）を備えた言語であり、メモリ管理はランタイムが担当します。プログラムが新しいメモリを要求すると、ランタイムはヒープからメモリを割り当てます。この際、Goの仕様により、割り当てられたメモリは必ずゼロ値で初期化される必要があります。これにより、未初期化のメモリ内容に依存するバグを防ぎ、プログラムの安全性を高めます。このゼロクリア処理は、Goアプリケーションのパフォーマンスに直接影響するため、非常に効率的に行われる必要があります。

### 2. Duff's Device (ダフのデバイス)

Duff's Deviceは、ループのオーバーヘッドを削減するために使用されるプログラミングのテクニックです。特に、固定回数の繰り返し処理を効率的に行うためにアセンブリ言語で実装されることが多いです。通常のループでは、各イテレーションでカウンタのデクリメントと条件分岐が発生しますが、Duff's Deviceでは、処理の開始位置をジャンプで調整することで、これらのオーバーヘッドを最小限に抑えます。

例えば、N回繰り返す処理がある場合、Duff's DeviceはNをブロックサイズで割った商と余りを計算し、余りに応じてループの途中から処理を開始し、その後はブロック単位で処理を進めます。これにより、ループの開始と終了のチェックを減らし、CPUのパイプライン予測を助け、全体的なスループットを向上させます。Goランタイムの`duffzero`は、このDuff's Deviceの原理をメモリゼロクリアに応用したものです。

### 3. x86-64 アセンブリ命令

*   **`STOSQ` (Store String Quadword)**:
    *   `RAX`レジスタ（64ビット）の内容を`RDI`レジスタが指すメモリ位置にストアします。
    *   その後、`RDI`レジスタの値を8（クアッドワードのサイズ）だけ自動的にインクリメント（またはデクリメント、DFフラグによる）します。
    *   `REP`プレフィックスと組み合わせることで、`RCX`レジスタで指定された回数だけこの操作を繰り返すことができ、効率的なブロック操作が可能です。メモリを連続してゼロクリアする際に非常に便利です。

*   **`MOVQ` (Move Quadword)**:
    *   64ビットのデータを移動する命令です。
    *   例: `MOVQ AX,(DI)` は、`AX`レジスタ（実際には`RAX`レジスタの下位部分、または`RAX`全体）の内容を、`DI`レジスタ（実際には`RDI`）が指すメモリ位置にストアします。
    *   `MOVQ AX,8(DI)` は、`DI`が指すアドレスから8バイトオフセットした位置にストアします。
    *   `MOVQ`命令は、特定のメモリ位置に値を書き込むための基本的な命令であり、`STOSQ`のように自動的なポインタのインクリメントは行いません。

*   **`ADDQ` (Add Quadword)**:
    *   64ビットの値を加算する命令です。
    *   例: `ADDQ $32,DI` は、`DI`レジスタに即値`32`を加算します。これは、`MOVQ`命令を複数回使用して32バイト分のメモリを処理した後、次のブロックの開始位置に`DI`を移動させるために使用されます。

### 4. レジスタ

*   **`AX` / `RAX` (Accumulator Register)**: 汎用レジスタで、通常は演算結果や関数の戻り値を保持します。メモリゼロクリアでは、ゼロ値（0x0000000000000000）を保持するために使われます。
*   **`DI` / `RDI` (Destination Index Register)**: 汎用レジスタで、通常はメモリ操作の宛先アドレスを保持します。`STOSQ`や`MOVQ`命令で書き込み先のポインタとして使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムの`duffzero`ルーチンにおけるメモリゼロクリア戦略の変更です。

### 従来の`STOSQ`ベースの実装

以前の`duffzero`は、主に`STOSQ`命令を連続して使用していました。`STOSQ`は`RAX`レジスタの内容（ゼロ）を`RDI`が指すメモリに書き込み、`RDI`を8バイト進めるため、非常にコンパクトで効率的なループを構築できました。Duff's Deviceの原理により、必要なバイト数に応じて`duffzero`ルーチン内の適切な`STOSQ`命令の開始位置にジャンプすることで、ループのオーバーヘッドを最小限に抑えていました。

### `MOVQ`/`ADDQ`ブロックの導入

コミットメッセージが示すように、`MOVQ AX,(DI)`、`MOVQ AX,8(DI)`、`MOVQ AX,16(DI)`、`MOVQ AX,24(DI)`の4つの`MOVQ`命令と、それに続く`ADDQ $32,DI`という命令シーケンスは、32バイトのメモリをゼロクリアし、`DI`を32バイト進めます。このブロックは、`STOSQ`を4回実行するよりも高速であることがベンチマークで示されました。これは、現代のCPUが複数の`MOVQ`命令を並列に実行できる能力や、キャッシュラインの効率的な利用によるものと考えられます。

### `DI`のプリ・アジャスト問題

`MOVQ`ブロックをDuff's Deviceとして利用する際の課題は、ジャンプしてルーチンの中間地点から実行する場合に、`DI`レジスタの事前調整が必要になる点です。`STOSQ`は常に8バイトずつ`DI`を進めますが、`MOVQ`ブロックは32バイト単位で`DI`を進めます。もし、クリアしたいバイト数が32の倍数でない場合、またはブロックの途中から実行を開始する場合、`DI`が指すアドレスが期待する開始位置とずれてしまう可能性があります。このずれを補正するために、`duffzero`ルーチンを呼び出す前に`DI`を適切に調整する必要がありました。この調整自体が小さなオーバーヘッドとなり、特にクリアするメモリ領域が小さい場合には、`MOVQ`ブロックの利点を打ち消してしまう可能性がありました。

### ハイブリッド戦略の採用

このコミットでは、上記の課題を解決するためにハイブリッド戦略が採用されました。

1.  **小さなクリア領域**: クリアするメモリ領域が非常に小さい場合（コミットメッセージでは`dzTailLen`、つまり4ワード以下）、`DI`のプリ・アジャストのオーバーヘッドが大きくなるため、引き続き従来の`STOSQ`命令を使用します。これにより、小さなクリアにおけるパフォーマンスの低下を防ぎます。
2.  **大きなクリア領域**: クリアするメモリ領域が大きい場合、`MOVQ`/`ADDQ`ブロックのパフォーマンス上の利点が`DI`のプリ・アジャストのオーバーヘッドを上回るため、主に`MOVQ`/`ADDQ`ブロックを使用します。

具体的には、`src/runtime/duff_amd64.s`の`runtime·duffzero`ルーチンは、複数の`MOVQ`/`ADDQ`ブロックの後に、少数の`STOSQ`命令を配置する構造に変更されました。`src/cmd/6g/ggen.go`のコンパイラ側では、`zerorange`関数と`clearfat`関数が変更され、クリアするワード数に応じて`DI`のプリ・アジャスト量（`dzDI`関数）と`duffzero`ルーチンへのジャンプオフセット（`dzOff`関数）を計算するようになりました。これにより、コンパイラが生成するコードが、最適な`duffzero`の開始点と`DI`の初期値を決定し、ハイブリッド戦略を効果的に実行します。

ベンチマーク結果は、このハイブリッド戦略が特に中規模から大規模なメモリクリアにおいて顕著なパフォーマンス向上をもたらしたことを明確に示しています。例えば、`BenchmarkClearFat56`では27.39%の改善が見られます。

### `src/cmd/6g/ggen.go` の変更点

このファイルでは、コンパイラが`duffzero`を呼び出す際のロジックが賢くなりました。

```go
// DUFFZERO consists of repeated blocks of 4 MOVs + ADD,
// with 4 STOSQs at the very end.
// The trailing STOSQs prevent the need for a DI preadjustment
// for small numbers of words to clear.
// See runtime/mkduff.go.
const (
	dzBlocks    = 31 // number of MOV/ADD blocks
	dzBlockLen  = 4  // number of clears per block
	dzBlockSize = 19 // size of instructions in a single block
	dzMovSize   = 4  // size of single MOV instruction w/ offset
	dzAddSize   = 4  // size of single ADD instruction
	dzDIStep    = 8  // number of bytes cleared by each MOV instruction

	dzTailLen  = 4 // number of final STOSQ instructions
	dzTailSize = 2 // size of single STOSQ instruction

	dzSize = dzBlocks*dzBlockSize + dzTailLen*dzTailSize // total size of DUFFZERO routine
)

// duffzeroDI returns the pre-adjustment to DI for a call to DUFFZERO.
// q is the number of words to zero.
func dzDI(q int64) int64 {
	if q < dzTailLen {
		return 0
	}
	q -= dzTailLen
	if q%dzBlockLen == 0 {
		return 0
	}
	return -dzDIStep * (dzBlockLen - q%dzBlockLen)
}

// dzOff returns the offset for a jump into DUFFZERO.
// q is the number of words to zero.
func dzOff(q int64) int64 {
	off := int64(dzSize)
	if q < dzTailLen {
		return off - q*dzTailSize
	}
	off -= dzTailLen * dzTailSize
	q -= dzTailLen
	blocks, steps := q/dzBlockLen, q%dzBlockLen
	off -= dzBlockSize * blocks
	if steps > 0 {
		off -= dzAddSize + dzMovSize*steps
	}
}
```
`dzDI`関数は、クリアするワード数`q`に基づいて、`DI`レジスタをどれだけ事前に調整すべきかを計算します。特に、`q`が`dzTailLen`（4ワード）より小さい場合は調整が不要（`STOSQ`のみで処理されるため）で、それ以外の場合は`MOVQ`ブロックの境界に合わせて`DI`を調整します。

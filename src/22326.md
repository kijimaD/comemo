## 元コミット内容

このコミットは、Goコンパイラのx86バックエンドにおいて、`PINSRD`命令が`from3`オペランドとしてメモリ位置を参照する場合に発生するアドレス計算の不具合を修正することを目的としています。`PINSRD`命令は、特定のレジスタ（XMMレジスタ）にメモリからデータを挿入するために使用されますが、その際に参照されるメモリアドレスのオフセット計算が、ローカル変数（`NAME_AUTO`）や関数引数（`NAME_PARAM`）の場合に誤っていたため、これを修正しています。

## 変更の背景

Goコンパイラは、Go言語のソースコードを機械語に変換する際に、中間表現を生成し、それをターゲットアーキテクチャ（この場合はx86）の特定のアセンブリ命令にマッピングします。このプロセスにおいて、変数や引数などのメモリ上の位置を正確に計算し、アセンブリ命令のオペランドとして設定する必要があります。

`PINSRD`命令は、SSE4.1命令セットの一部であり、XMMレジスタの指定された32ビット要素に、メモリまたは汎用レジスタから32ビットデータを挿入するために使用されます。この命令は、特にSIMD（Single Instruction, Multiple Data）演算において、データのパッキングやアンパッキングに利用されます。

Goコンパイラのバックエンドでは、`preprocess`関数がアセンブリ命令のオペランドのアドレスを調整する役割を担っています。これは、スタックフレームのサイズ変更や、ベースポインタ（BP）とスタックポインタ（SP）の相対アドレスの調整を考慮に入れるためです。

このコミット以前は、`PINSRD`命令の`from3`オペランド（多くの命令では存在しない、特殊な3番目のソースオペランド）がメモリを参照する場合、そのアドレスオフセットが正しく調整されていませんでした。具体的には、ローカル変数（`NAME_AUTO`）や関数引数（`NAME_PARAM`）としてスタック上に配置されたデータへの参照が、スタックフレームの調整後に誤ったアドレスを指してしまう可能性がありました。このバグは、`PINSRD`命令を使用する特定のGoプログラムが、実行時に不正なメモリアクセスを引き起こす原因となっていました。

## 前提知識の解説

### Goコンパイラのバックエンドの役割

Goコンパイラは、フロントエンド、ミドルエンド、バックエンドの3つの主要なフェーズに分けられます。
*   **フロントエンド**: ソースコードの字句解析、構文解析、意味解析を行い、抽象構文木（AST）を生成します。
*   **ミドルエンド**: ASTを中間表現（IR）に変換し、最適化を行います。
*   **バックエンド**: 中間表現をターゲットアーキテクチャ（例: x86, ARM）の機械語に変換します。このフェーズでは、レジスタ割り当て、命令選択、コード生成、そしてアドレス解決などが行われます。

このコミットが関連するのは、バックエンドのコード生成部分、特にx86アーキテクチャ向けのアセンブリ命令の生成とアドレス解決です。

### `cmd/internal/obj/x86` パッケージの役割

`cmd/internal/obj`パッケージは、Goコンパイラのバックエンドにおける共通のオブジェクトファイル生成ロジックを提供します。その中の`x86`サブパッケージ（`cmd/internal/obj/x86`）は、x86およびx86-64アーキテクチャに特化したアセンブリ命令の定義と、それらの命令を表現するためのデータ構造、そして命令の生成ロジックを含んでいます。

このパッケージは、Goコンパイラが生成するアセンブリコードの低レベルな詳細を扱います。例えば、命令のオペコード、オペランドのタイプ（レジスタ、メモリ、即値）、アドレッシングモードなどを定義し、GoのIRからこれらのアセンブリ命令への変換を行います。

### x86アセンブリにおけるメモリアドレッシングモード

x86アーキテクチャでは、メモリ上のデータにアクセスするために様々なアドレッシングモードが提供されています。
*   **ベースレジスタ相対アドレッシング**: ベースレジスタ（例: `RBP`, `RSP`）の値にオフセットを加算してメモリアドレスを計算します。
*   **スタックポインタ (RSP) 相対アドレッシング**: スタック上のローカル変数や関数引数にアクセスする際によく使用されます。`[RSP + offset]` の形式で表現されます。
*   **ベースポインタ (RBP) 相対アドレッシング**: 過去のスタックフレームや関数引数にアクセスする際に使用されることがあります。`[RBP + offset]` の形式で表現されます。

Goコンパイラは、関数呼び出し規約やスタックフレームのレイアウトに基づいて、これらのアドレッシングモードを適切に利用して変数や引数にアクセスします。

### `PINSRD` 命令の概要

`PINSRD` (Packed Insert Doubleword) 命令は、SSE4.1命令セットの一部です。
*   **目的**: 32ビットのデータを、ソースオペランドからデスティネーションのXMMレジスタの指定された32ビット要素に挿入します。
*   **形式**: `PINSRD xmm1, r/m32, imm8`
    *   `xmm1`: デスティネーションのXMMレジスタ。
    *   `r/m32`: ソースオペランド。32ビット汎用レジスタまたは32ビットメモリ位置。
    *   `imm8`: 即値。`xmm1`内のどの32ビット要素（0から3）にデータを挿入するかを指定します。

この命令は、例えば、4つの32ビット整数を格納できるXMMレジスタに、個別の32ビット整数をメモリからロードして挿入するような場合に利用されます。

### `obj.NAME_AUTO` と `obj.NAME_PARAM` の意味

Goコンパイラの内部では、メモリ上のシンボル（変数、引数など）を識別するために、`obj.NAME`という列挙型が使用されます。
*   `obj.NAME_AUTO`: 関数内のローカル変数（自動変数）を指します。これらは通常、スタックフレーム上に割り当てられます。
*   `obj.NAME_PARAM`: 関数の引数を指します。これらも通常、スタックフレーム上に割り当てられます。

これらのシンボルは、スタックポインタやベースポインタからの相対オフセットでアクセスされます。

### `deltasp` と `pcsize`, `bpsize` の役割

Goコンパイラのバックエンドでは、スタックフレームの管理が非常に重要です。
*   `deltasp`: 関数プロローグで調整されるスタックポインタの差分（スタックフレームのサイズ）を表します。コンパイラは、関数内のローカル変数や一時的なストレージのために必要なスタック領域を確保します。
*   `pcsize`: プログラムカウンタ（PC）のサイズ、またはリターンアドレスのサイズを指すことがあります。これは、関数呼び出し時にスタックにプッシュされるリターンアドレスのオフセット計算に影響します。
*   `bpsize`: ベースポインタ（BP）のサイズ、またはBPがスタックにプッシュされる場合のオフセット計算に影響します。

これらの値は、`NAME_AUTO`や`NAME_PARAM`のようなスタック上のシンボルへのオフセットを正確に計算するために使用されます。

## 技術的詳細

このバグは、`src/cmd/internal/obj/x86/obj6.go`ファイル内の`preprocess`関数で発生していました。`preprocess`関数は、Goコンパイラが生成したアセンブリ命令（`obj.Prog`構造体で表現される）を走査し、スタックフレームの調整（`deltasp`）に基づいて、メモリを参照するオペランドのオフセットを修正する役割を担っています。

通常、アセンブリ命令には最大で2つのオペランド（ソースとデスティネーション）があります。Goコンパイラの内部表現では、これらは`p.From`と`p.To`フィールドに対応します。しかし、`PINSRD`命令のように、一部の命令は3つ目のオペランドを持つことがあります。`PINSRD`の場合、この3つ目のオペランドは`imm8`（即値）ですが、Goコンパイラの内部表現では、特定の命令の特殊なオペランドを扱うために`p.From3`というフィールドが使用されることがあります。

問題は、`preprocess`関数が`p.From`と`p.To`オペランドに対してはスタックフレームの調整を適用していたものの、`PINSRD`命令が使用する`p.From3`オペランドがメモリを参照する場合に、同様の調整が欠けていた点にありました。

具体的には、`PINSRD`命令の`r/m32`オペランドが`obj.NAME_AUTO`（ローカル変数）または`obj.NAME_PARAM`（関数引数）としてスタック上のメモリ位置を指している場合、`preprocess`関数は`deltasp`と`bpsize`/`pcsize`を考慮してオフセットを調整する必要がありました。この調整が欠けていたため、コンパイラが生成するアセンブリコードでは、`PINSRD`命令が誤ったメモリアドレスからデータを読み込もうとし、結果として実行時エラーや不正な動作を引き起こしていました。

このコミットは、`preprocess`関数に`p.From3`オペランドに対する同様のオフセット調整ロジックを追加することで、この問題を解決しています。これにより、`PINSRD`命令がメモリを`from3`オペランドとして使用する場合でも、常に正しいメモリアドレスが参照されるようになります。

## コアとなるコードの解説

追加されたコードは、`preprocess`関数内で`p.From`オペランドのオフセット調整ロジックの直後に挿入されています。

```go
		a = int(p.From3.Name)
		if a == obj.NAME_AUTO {
			p.From3.Offset += int64(deltasp) - int64(bpsize)
		}
		if a == obj.NAME_PARAM {
			p.From3.Offset += int64(deltasp) + int64(pcsize)
		}
```

1.  `a = int(p.From3.Name)`:
    *   `p.From3`は、現在の命令（`p`）の3番目のオペランドを表す`obj.Addr`構造体です。
    *   `p.From3.Name`は、このオペランドが参照するシンボルの種類（例: `NAME_AUTO`, `NAME_PARAM`）を示します。
    *   この行では、`From3`オペランドのシンボルタイプを整数型に変換して変数`a`に格納しています。

2.  `if a == obj.NAME_AUTO { p.From3.Offset += int64(deltasp) - int64(bpsize) }`:
    *   もし`From3`オペランドがローカル変数（`obj.NAME_AUTO`）を参照している場合、そのオフセットを調整します。
    *   `deltasp`は、関数プロローグでスタックポインタがどれだけ移動したか（スタックフレームのサイズ）を示します。この値を加算することで、スタックフレームの拡張によるオフセットの変化を補正します。
    *   `bpsize`は、ベースポインタがスタックにプッシュされる場合のサイズに関連するオフセットです。`deltasp`から`bpsize`を減算することで、`NAME_AUTO`シンボルがベースポインタに対して相対的に配置される場合の正確なオフセットを計算します。

3.  `if a == obj.NAME_PARAM { p.From3.Offset += int64(deltasp) + int64(pcsize) }`:
    *   もし`From3`オペランドが関数引数（`obj.NAME_PARAM`）を参照している場合、そのオフセットを調整します。
    *   `deltasp`を加算することで、スタックフレームの拡張によるオフセットの変化を補正します。
    *   `pcsize`は、リターンアドレスのサイズに関連するオフセットです。関数引数は通常、リターンアドレスの後にスタックにプッシュされるため、`deltasp`に`pcsize`を加算することで、`NAME_PARAM`シンボルがスタックポインタに対して相対的に配置される場合の正確なオフセットを計算します。

これらの変更により、`PINSRD`命令が`from3`オペランドとしてスタック上のメモリ位置（ローカル変数や関数引数）を参照する際に、`preprocess`関数がそのオフセットを正しく調整するようになります。これにより、生成されるアセンブリコードが常に正しいメモリアドレスにアクセスすることが保証され、バグが解消されます。

`PINSRD` (Packed Insert Doubleword) 命令は、SSE4.1命令セットの一部です。
*   **目的**: 32ビットのデータを、ソースオペランドからデスティネーションのXMMレジスタの指定された32ビット要素に挿入します。
*   **形式**: `PINSRD xmm1, r/m32, imm8`
    *   `xmm1`: デスティネーションのXMMレジスタ。
    *   `r/m32`: ソースオペランド。32ビット汎用レジスタまたは32ビットメモリ位置。
    *   `imm8`: 即値。`xmm1`内のどの32ビット要素（0から3）にデータを挿入するかを指定します。

この命令は、例えば、4つの32ビット整数を格納できるXMMレジスタに、個別の32ビット整数をメモリからロードして挿入するような場合に利用されます。

### `obj.NAME_AUTO` と `obj.NAME_PARAM` の意味

Goコンパイラの内部では、メモリ上のシンボル（変数、引数など）を識別するために、`obj.NAME`という列挙型が使用されます。
*   `obj.NAME_AUTO`: 関数内のローカル変数（自動変数）を指します。これらは通常、スタックフレーム上に割り当てられます。
*   `obj.NAME_PARAM`: 関数の引数を指します。これらも通常、スタックフレーム上に割り当てられます。

これらのシンボルは、スタックポインタやベースポインタからの相対オフセットでアクセスされます。

### `deltasp` と `pcsize`, `bpsize` の役割

Goコンパイラのバックエンドでは、スタックフレームの管理が非常に重要です。
*   `deltasp`: 関数プロローグで調整されるスタックポインタの差分（スタックフレームのサイズ）を表します。コンパイラは、関数内のローカル変数や一時的なストレージのために必要なスタック領域を確保します。
*   `pcsize`: プログラムカウンタ（PC）のサイズ、またはリターンアドレスのサイズを指すことがあります。これは、関数呼び出し時にスタックにプッシュされるリターンアドレスのオフセット計算に影響します。
*   `bpsize`: ベースポインタ（BP）のサイズ、またはBPがスタックにプッシュされる場合のオフセット計算に影響します。

これらの値は、`NAME_AUTO`や`NAME_PARAM`のようなスタック上のシンボルへのオフセットを正確に計算するために使用されます。

## 技術的詳細

このバグは、`src/cmd/internal/obj/x86/obj6.go`ファイル内の`preprocess`関数で発生していました。`preprocess`関数は、Goコンパイラが生成したアセンブリ命令（`obj.Prog`構造体で表現される）を走査し、スタックフレームの調整（`deltasp`）に基づいて、メモリを参照するオペランドのオフセットを修正する役割を担っています。

通常、アセンブリ命令には最大で2つのオペランド（ソースとデスティネーション）があります。Goコンパイラの内部表現では、これらは`p.From`と`p.To`フィールドに対応します。しかし、`PINSRD`命令のように、一部の命令は3つ目のオペランドを持つことがあります。`PINSRD`の場合、この3つ目のオペランドは`imm8`（即値）ですが、Goコンパイラの内部表現では、特定の命令の特殊なオペランドを扱うために`p.From3`というフィールドが使用されることがあります。

問題は、`preprocess`関数が`p.From`と`p.To`オペランドに対してはスタックフレームの調整を適用していたものの、`PINSRD`命令が使用する`p.From3`オペランドがメモリを参照する場合に、同様の調整が欠けていた点にありました。

具体的には、`PINSRD`命令の`r/m32`オペランドが`obj.NAME_AUTO`（ローカル変数）または`obj.NAME_PARAM`（関数引数）としてスタック上のメモリ位置を指している場合、`preprocess`関数は`deltasp`と`bpsize`/`pcsize`を考慮してオフセットを調整する必要がありました。この調整が欠けていたため、コンパイラが生成するアセンブリコードでは、`PINSRD`命令が誤ったメモリアドレスからデータを読み込もうとし、結果として実行時エラーや不正な動作を引き起こしていました。

このコミットは、`preprocess`関数に`p.From3`オペランドに対する同様のオフセット調整ロジックを追加することで、この問題を解決しています。これにより、`PINSRD`命令がメモリを`from3`オペランドとして使用する場合でも、常に正しいメモリアドレスが参照されるようになります。

## コアとなるコードの解説

追加されたコードは、`preprocess`関数内で`p.From`オペランドのオフセット調整ロジックの直後に挿入されています。

```go
		a = int(p.From3.Name)
		if a == obj.NAME_AUTO {
			p.From3.Offset += int64(deltasp) - int64(bpsize)
		}
		if a == obj.NAME_PARAM {
			p.From3.Offset += int64(deltasp) + int64(pcsize)
		}
```

1.  `a = int(p.From3.Name)`:
    *   `p.From3`は、現在の命令（`p`）の3番目のオペランドを表す`obj.Addr`構造体です。
    *   `p.From3.Name`は、このオペランドが参照するシンボルの種類（例: `NAME_AUTO`, `NAME_PARAM`）を示します。
    *   この行では、`From3`オペランドのシンボルタイプを整数型に変換して変数`a`に格納しています。

2.  `if a == obj.NAME_AUTO { p.From3.Offset += int64(deltasp) - int64(bpsize) }`:
    *   もし`From3`オペランドがローカル変数（`obj.NAME_AUTO`）を参照している場合、そのオフセットを調整します。
    *   `deltasp`は、関数プロローグでスタックポインタがどれだけ移動したか（スタックフレームのサイズ）を示します。この値を加算することで、スタックフレームの拡張によるオフセットの変化を補正します。
    *   `bpsize`は、ベースポインタがスタックにプッシュされる場合のサイズに関連するオフセットです。`deltasp`から`bpsize`を減算することで、`NAME_AUTO`シンボルがベースポインタに対して相対的に配置される場合の正確なオフセットを計算します。

3.  `if a == obj.NAME_PARAM { p.From3.Offset += int64(deltasp) + int64(pcsize) }`:
    *   もし`From3`オペランドが関数引数（`obj.NAME_PARAM`）を参照している場合、そのオフセットを調整します。
    *   `deltasp`を加算することで、スタックフレームの拡張によるオフセットの変化を補正します。
    *   `pcsize`は、リターンアドレスのサイズに関連するオフセットです。関数引数は通常、リターンアドレスの後にスタックにプッシュされるため、`deltasp`に`pcsize`を加算することで、`NAME_PARAM`シンボルがスタックポインタに対して相対的に配置される場合の正確なオフセットを計算します。

これらの変更により、`PINSRD`命令が`from3`オペランドとしてスタック上のメモリ位置（ローカル変数や関数引数）を参照する際に、`preprocess`関数がそのオフセットを正しく調整するようになります。これにより、生成されるアセンブリコードが常に正しいメモリアドレスにアクセスすることが保証され、バグが解消されます。

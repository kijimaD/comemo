# [インデックス 20112] ファイルの概要

このコミットは、Goランタイムのメモリ管理において、ガベージコレクション後のスパン（メモリ領域）の処理を最適化するために「転送キャッシュ（transfer cache）」の概念を導入するものです。これにより、スパンの再利用プロセスにおけるロックの取得と解放、およびリスト操作の回数が大幅に削減され、メモリ割り当てのパフォーマンスが向上しています。

## コミット

Author: Dmitriy Vyukov <dvyukov@google.com>
Date:   Mon Aug 18 16:52:31 2014 +0400

    runtime: implement transfer cache
    Currently we do the following dance after sweeping a span:
    1. lock mcentral
    2. remove the span from a list
    3. unlock mcentral
    4. unmark span
    5. lock mheap
    6. insert the span into heap
    7. unlock mheap
    8. lock mcentral
    9. observe empty list
    10. unlock mcentral
    11. lock mheap
    12. grab the span
    13. unlock mheap
    14. mark span
    15. lock mcentral
    16. insert the span into empty list
    17. unlock mcentral
    
    This change short-circuits this sequence to nothing,
    that is, we just cache and use the span after sweeping.
    
    This gives us functionality similar (even better) to tcmalloc's transfer cache.

## 元コミット内容

Goランタイムにおいて、スパンのスイープ（ガベージコレクション後の未使用メモリの回収）後に発生する一連の複雑な処理を簡素化し、転送キャッシュを実装します。

既存のプロセスでは、スパンのスイープ後、`mcentral`と`mheap`という2つの主要なメモリ管理コンポーネント間でスパンを移動させるために、多数のロック操作とリスト操作（合計17ステップ）が必要でした。このコミットは、スイープされたスパンを直接キャッシュし、再利用することで、この複雑なシーケンスを排除します。

この変更は、Googleのtcmallocの転送キャッシュに似た（あるいはそれ以上の）機能を提供し、`BenchmarkMalloc8`で12.16%、`BenchmarkMalloc16`で14.19%のパフォーマンス向上をもたらしています。

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープメモリを`MSpan`と呼ばれる固定サイズのチャンクに分割して管理しています。これらのスパンは、特定のサイズのオブジェクトを割り当てるために使用されます。GCのマークフェーズが完了した後、スイープフェーズが実行され、マークされなかった（つまり、到達不能な）オブジェクトが占めていたメモリが解放されます。

スイープされたスパンは、再利用のためにメモリ管理システムに戻されます。コミットメッセージに記載されているように、この「戻す」プロセスは非常に複雑で、`mcentral`と`mheap`という2つの異なるメモリ管理層の間でスパンを移動させるために、多くのロックとアンロック、およびリスト操作を伴っていました。

この複雑なシーケンスは、特に高負荷なメモリ割り当てが行われるアプリケーションにおいて、パフォーマンスのボトルネックとなる可能性がありました。ロックの競合は並行性を低下させ、頻繁なリスト操作はオーバーヘッドを増加させます。このコミットの目的は、この非効率性を解消し、スイープされたスパンをより効率的に再利用できるようにすることでした。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理の基本的な概念を把握しておく必要があります。

*   **ヒープ (Heap)**: Goプログラムが動的にメモリを割り当てる領域です。
*   **MSpan**: ヒープは`MSpan`と呼ばれる固定サイズの連続したページ（通常は8KB）のチャンクに分割されます。各`MSpan`は、特定のサイズのオブジェクトを割り当てるために使用されます。例えば、小さなオブジェクト用のスパン、大きなオブジェクト用のスパンなどがあります。
*   **mheap**: 全ての`MSpan`を管理するグローバルなデータ構造です。`mheap`は、利用可能な空きスパンのリストや、大きなオブジェクト用のスパンなどを管理します。
*   **mcentral**: 各CPUコア（P: Processor）に紐付けられたローカルなメモリキャッシュ（`mcache`）と、グローバルな`mheap`の間に位置する中間層です。`mcentral`は、特定のサイズクラスのスパンを管理し、`mcache`からのスパン要求に応じたり、`mcache`から返却されたスパンを受け取ったりします。`mcentral`は、空きオブジェクトを持つスパンのリスト（`nonempty`）と、完全に割り当て済みのスパンのリスト（`empty`）を持っています。
*   **mcache**: 各ゴルーチンが実行される論理プロセッサ（P）に紐付けられたローカルなメモリキャッシュです。`mcache`は、ロックなしで高速にメモリを割り当てられるように、小さなオブジェクト用のスパンを一時的に保持します。`mcache`がスパンを使い切ると、`mcentral`から新しいスパンを取得します。
*   **スイープ (Sweep)**: ガベージコレクションのフェーズの一つで、マークフェーズで到達不能と判断されたオブジェクトが占めていたメモリを解放し、スパンを再利用可能な状態に戻すプロセスです。スイープ後、スパンは`mcentral`に戻され、最終的には`mheap`に返却されるか、再利用のために`mcache`に提供されます。
*   **転送キャッシュ (Transfer Cache)**: tcmalloc（GoogleのC++用メモリ割り当てライブラリ）で導入された概念で、頻繁に再利用される小さなメモリブロックのリストをキャッシュすることで、ロックの競合を減らし、割り当て性能を向上させる仕組みです。Goのこのコミットでは、スイープされたスパンを直接キャッシュすることで、同様の効果を狙っています。

## 技術的詳細

このコミットの核心は、`MSpan_Sweep`関数と`MCentral_FreeSpan`関数の挙動を変更し、`MCentral_CacheSpan`関数に新しいロジックを導入することで、スイープされたスパンの再利用プロセスを大幅に簡素化することです。

変更前は、スパンがスイープされると、そのスパンは`mcentral`から削除され、`mheap`に返却され、その後必要に応じて`mheap`から再度取得され、`mcentral`のリストに再挿入されるという、非常に多くのロックとアンロックを伴う複雑な手順を踏んでいました。これは、スパンが一時的に`mheap`に「返却」されることで、他の`mcentral`がそのスパンを取得できる可能性を考慮した設計でした。

このコミットでは、`MSpan_Sweep`関数に`preserve`という新しい引数が追加されています。
*   `preserve=true`の場合、スイープされたスパンは`mheap`に返却されず、`mcentral`のリストからも一時的に削除されません。代わりに、スイープが完了した後も、そのスパンは`mcentral`の`empty`リスト（空になったスパンのリスト）に保持されます。
*   `MCentral_CacheSpan`関数は、`mcache`が新しいスパンを要求した際に`mcentral`からスパンを取得する役割を担います。この関数内で、スイープが必要なスパンが見つかった場合、以前は`MSpan_Sweep`を呼び出した後に`mcentral`のロックを解放し、スパンが`mheap`に移動する可能性を考慮して`goto retry`で再試行していました。
*   新しい実装では、`MCentral_CacheSpan`内でスイープを行う際に`MSpan_Sweep(s, true)`を呼び出します。これにより、スイープされたスパンは`mcentral`の`empty`リストにそのまま残り、`mheap`への移動や複雑なロックシーケンスが不要になります。スイープ後、スパンに空きオブジェクトがあれば、すぐに`mcache`に提供されます。
*   `MCentral_Grow`関数も変更され、`MSpan*`を返すようになりました。これは、`mheap`から新しいスパンを取得する際に、そのスパンを直接`mcentral`の`empty`リストに挿入できるようにするためです。

この「転送キャッシュ」の考え方は、スイープされたスパンがすぐに再利用される可能性が高いという仮定に基づいています。スパンを`mheap`に返却して再度取得する手間を省くことで、ロックの競合を減らし、メモリ割り当てのレイテンシを大幅に改善しています。特に、小さなオブジェクトの頻繁な割り当てと解放が行われるワークロードにおいて、この最適化は顕著な効果を発揮します。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.h` の変更

```c
// Before
bool	runtime·MSpan_Sweep(MSpan *span);
bool	runtime·MCentral_FreeSpan(MCentral *c, MSpan *s, int32 n, MLink *start, MLink *end);
static bool MCentral_Grow(MCentral *c);

// After
bool	runtime·MSpan_Sweep(MSpan *span, bool preserve);
bool	runtime·MCentral_FreeSpan(MCentral *c, MSpan *s, int32 n, MLink *start, MLink *end, bool preserve);
static MSpan* MCentral_Grow(MCentral *c);
```
`MSpan_Sweep`と`MCentral_FreeSpan`に`preserve`引数が追加されたことで、スイープ後のスパンを`mheap`に返却するか、`mcentral`内に保持するかを制御できるようになりました。`MCentral_Grow`の戻り値が`MSpan*`になったのは、`mheap`から取得したスパンを直接`mcentral`のリストに挿入するためです。

### `src/pkg/runtime/mcentral.c` の変更

`runtime·MCentral_CacheSpan`関数内の変更が最も重要です。

```c
// Before (simplified)
runtime·unlock(&c->lock);
runtime·MSpan_Sweep(s); // Sweeps and potentially returns to mheap
runtime·lock(&c->lock);
// the span could have been moved to heap, retry
goto retry;

// After (simplified)
runtime·MSpanList_Remove(s); // Remove from current list (e.g., nonempty)
runtime·MSpanList_InsertBack(&c->empty, s); // Insert into empty list
runtime·unlock(&c->lock);
runtime·MSpan_Sweep(s, true); // Sweep, but PRESERVE in mcentral
goto havespan; // If freelist is not nil, we have a span
```
変更前は、スイープ後にスパンが`mheap`に移動する可能性があったため、`mcentral`のロックを解放し、`MSpan_Sweep`を呼び出し、再度ロックを取得して`retry`していました。これは、スパンが`mheap`に返却され、別の`mcentral`によって取得される可能性を考慮したもので、多くのロック操作と競合の機会を生んでいました。

変更後では、`MSpan_Sweep(s, true)`を呼び出すことで、スイープされたスパンは`mcentral`の`empty`リストにそのまま保持されます。これにより、`mheap`との間の複雑なやり取りが不要になり、ロックの取得・解放の回数が大幅に削減されます。`goto havespan`に直接ジャンプすることで、スイープされたスパンがすぐに再利用可能であれば、それを`mcache`に提供できます。

`runtime·MCentral_FreeSpan`関数では、`preserve`が`true`の場合、スパンのフリーリストを更新するものの、`mcentral`のロックを取得せず、`mheap`への返却も行いません。これは、`MCentral_CacheSpan`内でスイープされたスパンが既に`mcentral`の`empty`リストに存在し、その場で再利用されることを意図しているためです。

### `src/pkg/runtime/mgc0.c` の変更

`runtime·MSpan_Sweep`関数のシグネチャ変更と、それに伴う呼び出し箇所の修正です。

```c
// Before
bool runtime·MSpan_Sweep(MSpan *s)

// After
bool runtime·MSpan_Sweep(MSpan *s, bool preserve)
```
`preserve`引数が追加され、`true`の場合にはスパンを`mheap`に返却しないロジックが追加されました。特に、大きなスパン（`cl == 0`）を`preserve=true`でスイープしようとすると`throw("can't preserve large span")`でパニックを起こすガードが追加されています。これは、大きなスパンは通常`mheap`で直接管理され、`mcentral`の転送キャッシュの対象ではないためです。

## 変更の背景

Goの`net`パッケージでは、ネットワーク接続の確立やデータ送受信に対してタイムアウトを設定する機能が提供されています。例えば、`net.Dialer`構造体には`Timeout`フィールドや`Deadline`フィールドがあり、これらを使って接続試行の最大時間を指定できます。

このコミットが修正する問題は、ユーザーが非常に大きなタイムアウト値（例えば、`time.Duration`で表現できる最大値に近い値）を設定した場合に発生していました。内部的には、デッドライン（期限）は現在の時刻からの相対的な時間差を`int64`型のナノ秒単位で表現し、`runtimeNano()`（システム起動からの経過ナノ秒）に加算して絶対的なデッドライン時刻を計算します。

`d = runtimeNano() + int64(t.Sub(time.Now()))`

ここで、`t.Sub(time.Now())`が非常に大きな正の値（例えば`time.Duration`の最大値`math.MaxInt64`に相当するナノ秒）である場合、`runtimeNano()`に加算すると`int64`型の最大値を超えてしまい、オーバーフローが発生することがありました。`int64`のオーバーフローは、正の値が負の値として解釈されるという結果を招きます。

その結果、計算されたデッドライン`d`が負の値になってしまい、システムは「デッドラインが過去である」と誤って判断し、`DialTimeout`などの操作が即座にタイムアウトエラーを返してしまうという不具合がありました。これは、ユーザーが将来のデッドラインを意図して設定したにもかかわらず、実際にはその意図が反映されないという深刻な問題でした。

この問題はGoのIssue #14431として報告されていました。

## 前提知識の解説

### Goの`net`パッケージと`DialTimeout`

Goの`net`パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。`net.Dial`関数や`net.Dialer`構造体は、TCP/UDP接続の確立によく使われます。
`net.Dialer`の`Timeout`フィールドは、接続が確立されるまでの最大時間を指定します。`Deadline`フィールドは、接続試行が完了しなければならない絶対的な時刻を指定します。

### `time.Duration`と`time.Time`

*   **`time.Duration`**: 期間を表す型で、ナノ秒単位の`int64`として内部的に表現されます。例えば、`5 * time.Second`は5秒間の期間を表します。
*   **`time.Time`**: 特定の時点を表す型です。`time.Now()`で現在の時刻を取得できます。`t.Sub(time.Now())`は、`t`と`time.Now()`の間の期間を`time.Duration`として返します。

### `runtimeNano()`

Goランタイム内部で使用される関数で、システム起動からの経過時間をナノ秒単位で`int64`として返します。これは、システムクロックの変更に影響されない単調増加する時間源として利用されます。デッドラインの計算では、この`runtimeNano()`を基準として絶対的なデッドライン時刻を決定します。

### `int64`のオーバーフロー

`int64`は64ビット符号付き整数型で、約`-9 * 10^18`から`+9 * 10^18`までの値を表現できます。`time.Duration`も内部的には`int64`でナノ秒を表現するため、最大で約292年間の期間を表すことができます。
しかし、`runtimeNano()`も`int64`であり、これに非常に大きな`time.Duration`（ナノ秒）を加算すると、`int64`の最大値`math.MaxInt64`（`1<<63 - 1`）を超えてしまう可能性があります。符号付き整数型で最大値を超えると、値が「ラップアラウンド」して負の値になる現象（オーバーフロー）が発生します。

### デッドライン（期限）の概念

ネットワーク操作におけるデッドラインは、その操作が完了しなければならない絶対的な時刻を指します。Goの`net`パッケージでは、このデッドラインを`runtimeNano()`を基準としたナノ秒で内部的に管理しています。デッドラインが設定されると、ランタイムはその時刻までに操作が完了しない場合、エラーを返すようにします。

## 技術的詳細

このコミットの核心は、`src/net/fd_poll_runtime.go`内の`setDeadlineImpl`関数におけるデッドライン計算の修正です。

元のコードは以下のようでした。
`d := runtimeNano() + int64(t.Sub(time.Now()))`

ここで、`t`はユーザーが設定したデッドライン時刻、`time.Now()`は現在の時刻です。`t.Sub(time.Now())`は、現在の時刻からデッドラインまでの期間を`time.Duration`（ナノ秒単位の`int64`）で返します。この期間が非常に大きい場合、`runtimeNano()`に加算した結果が`int64`の最大値を超えてオーバーフローし、`d`が負の値になることが問題でした。

修正後のコードでは、このオーバーフローを検出し、適切に処理します。

1.  まず、`diff := int64(t.Sub(time.Now()))`として、デッドラインまでの期間を`diff`変数に格納します。
2.  次に、`d := runtimeNano() + diff`として、通常のデッドライン計算を行います。
3.  **重要な修正点**: 以下の条件文が追加されました。
    `if d <= 0 && diff > 0 { ... }`
    *   `d <= 0`: 計算されたデッドライン`d`が負の値またはゼロであること。これはオーバーフローが発生した可能性を示唆します。
    *   `diff > 0`: ユーザーが指定したデッドライン`t`が現在の時刻`time.Now()`よりも将来の時刻であること。つまり、ユーザーは実際に将来のデッドラインを意図していることを示します。

    この二つの条件が同時に真である場合、それは`int64`オーバーフローによって`d`が負の値になったと判断できます。
4.  このオーバーフローが検出された場合、`d = 1<<63 - 1`と設定されます。`1<<63 - 1`は`math.MaxInt64`に相当し、`int64`で表現できる最大の正の値です。これにより、デッドラインは事実上「非常に遠い未来」に設定され、ユーザーが意図した「非常に長いタイムアウト」が正しく機能するようになります。即座にタイムアウトエラーが発生するのを防ぎます。

この修正により、Goの`net`パッケージは、非常に大きなタイムアウト値が指定された場合でも、`int64`オーバーフローによる誤ったデッドライン処理を回避し、期待通りの動作をするようになります。

また、この変更には、この修正が正しく機能することを検証するための新しいテストケースが`src/net/timeout_test.go`に追加されています。特に、`1<<63 - 1`という`int64`の最大値に近い`time.Duration`を`Dialer`の`Timeout`や`Deadline`に設定した場合の挙動をテストしています。

## コアとなるコードの解説

### `src/net/fd_poll_runtime.go`の変更

`setDeadlineImpl`関数は、ファイルディスクリプタ（`fd`）の読み書きデッドラインを設定する内部関数です。

```go
func setDeadlineImpl(fd *netFD, t time.Time, mode int) error {
	diff := int64(t.Sub(time.Now())) // ユーザー指定のデッドラインまでの期間を計算
	d := runtimeNano() + diff        // 現在のランタイムナノ秒に期間を加算して絶対デッドラインを計算

	// オーバーフロー検出と修正
	if d <= 0 && diff > 0 {
		// ユーザーが将来のデッドラインを指定している（diff > 0）にもかかわらず、
		// 計算されたデッドラインが負の値またはゼロになった場合（d <= 0）は、
		// int64オーバーフローが発生したと判断する。
		// この場合、デッドラインをint64の最大値に設定し、事実上タイムアウトしないようにする。
		d = 1<<63 - 1 // math.MaxInt64
	}
	if t.IsZero() {
		d = 0 // tがゼロ値の場合はデッドラインを無効にする
	}
	// ... (後続のデッドライン設定ロジック)
	return nil
}
```

この変更により、`diff`が非常に大きく`runtimeNano() + diff`がオーバーフローして負の値になったとしても、`diff > 0`（つまりユーザーは将来のデッドラインを意図している）という条件が真であれば、`d`は`math.MaxInt64`に設定され、意図しない即時タイムアウトが回避されます。

### `src/net/timeout_test.go`の変更

新しいテストケース`dialTimeoutMaxDurationTests`と`TestDialTimeoutMaxDuration`が追加されました。

`dialTimeoutMaxDurationTests`は、`int64`の最大値に近い`time.Duration`を`timeout`または`delta`（`Deadline`計算用）として設定するシナリオを定義しています。

```go
var dialTimeoutMaxDurationTests = []struct {
	timeout time.Duration
	delta   time.Duration // for deadline
}{
	// int64 Unixナノ秒でオーバーフローする可能性のある大きなタイムアウト
	{1<<63 - 1, 0}, // TimeoutにMaxInt64を設定
	{0, 1<<63 - 1}, // DeadlineにMaxInt64に相当する期間を設定
}
```

`TestDialTimeoutMaxDuration`関数は、これらの大きなタイムアウト値が設定された`Dialer`を使って接続を試みます。
テストの重要な点は、`max := time.NewTimer(100 * time.Millisecond)`という短いタイマーを設定していることです。これは、もしオーバーフロー修正が機能せず、接続が即座にタイムアウトしてしまった場合、`Dial`呼び出しがすぐにエラーを返すため、この短いタイマーが切れる前にエラーが返ってくることを期待しています。
しかし、修正が正しく機能していれば、`Dial`は即座にタイムアウトせず、接続試行が継続されるため、この短いタイマーが切れて`t.Fatalf`が呼び出されることになります。
テストの目的は、これらの大きなタイムアウト値が設定されたときに、`Dial`が即座にエラーを返さず、むしろ「期待される時間内に戻らなかった」ことを確認することです。これは、デッドラインが正しく`math.MaxInt64`に設定され、即座のタイムアウトが回避されていることを間接的に検証しています。

元のコードは以下のようでした。
`d := runtimeNano() + int64(t.Sub(time.Now()))`

ここで、`t`はユーザーが設定したデッドライン時刻、`time.Now()`は現在の時刻です。`t.Sub(time.Now())`は、現在の時刻からデッドラインまでの期間を`time.Duration`（ナノ秒単位の`int64`）で返します。この期間が非常に大きい場合、`runtimeNano()`に加算した結果が`int64`の最大値を超えてオーバーフローし、`d`が負の値になることが問題でした。

修正後のコードでは、このオーバーフローを検出し、適切に処理します。

1.  まず、`diff := int64(t.Sub(time.Now()))`として、デッドラインまでの期間を`diff`変数に格納します。
2.  次に、`d := runtimeNano() + diff`として、通常のデッドライン計算を行います。
3.  **重要な修正点**: 以下の条件文が追加されました。
    `if d <= 0 && diff > 0 { ... }`
    *   `d <= 0`: 計算されたデッドライン`d`が負の値またはゼロであること。これはオーバーフローが発生した可能性を示唆します。
    *   `diff > 0`: ユーザーが指定したデッドライン`t`が現在の時刻`time.Now()`よりも将来の時刻であること。つまり、ユーザーは実際に将来のデッドラインを意図していることを示します。

    この二つの条件が同時に真である場合、それは`int64`オーバーフローによって`d`が負の値になったと判断できます。
4.  このオーバーフローが検出された場合、`d = 1<<63 - 1`と設定されます。`1<<63 - 1`は`math.MaxInt64`に相当し、`int64`で表現できる最大の正の値です。これにより、デッドラインは事実上「非常に遠い未来」に設定され、ユーザーが意図した「非常に長いタイムアウト」が正しく機能するようになります。即座にタイムアウトエラーが発生するのを防ぎます。

この修正により、Goの`net`パッケージは、非常に大きなタイムアウト値が指定された場合でも、`int64`オーバーフローによる誤ったデッドライン処理を回避し、期待通りの動作をするようになります。

また、この変更には、この修正が正しく機能することを検証するための新しいテストケースが`src/net/timeout_test.go`に追加されています。特に、`1<<63 - 1`という`int64`の最大値に近い`time.Duration`を`Dialer`の`Timeout`や`Deadline`に設定した場合の挙動をテストしています。

## コアとなるコードの解説

### `src/net/fd_poll_runtime.go`の変更

`setDeadlineImpl`関数は、ファイルディスクリプタ（`fd`）の読み書きデッドラインを設定する内部関数です。

```go
func setDeadlineImpl(fd *netFD, t time.Time, mode int) error {
	diff := int64(t.Sub(time.Now())) // ユーザー指定のデッドラインまでの期間を計算
	d := runtimeNano() + diff        // 現在のランタイムナノ秒に期間を加算して絶対デッドラインを計算

	// オーバーフロー検出と修正
	if d <= 0 && diff > 0 {
		// ユーザーが将来のデッドラインを指定している（diff > 0）にもかかわらず、
		// 計算されたデッドラインが負の値またはゼロになった場合（d <= 0）は、
		// int64オーバーフローが発生したと判断する。
		// この場合、デッドラインをint64の最大値に設定し、事実上タイムアウトしないようにする。
		d = 1<<63 - 1 // math.MaxInt64
	}
	if t.IsZero() {
		d = 0 // tがゼロ値の場合はデッドラインを無効にする
	}
	// ... (後続のデッドライン設定ロジック)
	return nil
}
```

この変更により、`diff`が非常に大きく`runtimeNano() + diff`がオーバーフローして負の値になったとしても、`diff > 0`（つまりユーザーは将来のデッドラインを意図している）という条件が真であれば、`d`は`math.MaxInt64`に設定され、意図しない即時タイムアウトが回避されます。

### `src/net/timeout_test.go`の変更

新しいテストケース`dialTimeoutMaxDurationTests`と`TestDialTimeoutMaxDuration`が追加されました。

`dialTimeoutMaxDurationTests`は、`int64`の最大値に近い`time.Duration`を`timeout`または`delta`（`Deadline`計算用）として設定するシナリオを定義しています。

```go
var dialTimeoutMaxDurationTests = []struct {
	timeout time.Duration
	delta   time.Duration // for deadline
}{
	// int64 Unixナノ秒でオーバーフローする可能性のある大きなタイムアウト
	{1<<63 - 1, 0}, // TimeoutにMaxInt64を設定
	{0, 1<<63 - 1}, // DeadlineにMaxInt64に相当する期間を設定
}
```

`TestDialTimeoutMaxDuration`関数は、これらの大きなタイムアウト値が設定された`Dialer`を使って接続を試みます。
テストの重要な点は、`max := time.NewTimer(100 * time.Millisecond)`という短いタイマーを設定していることです。これは、もしオーバーフロー修正が機能せず、接続が即座にタイムアウトしてしまった場合、`Dial`呼び出しがすぐにエラーを返すため、この短いタイマーが切れる前にエラーが返ってくることを期待しています。
しかし、修正が正しく機能していれば、`Dial`は即座にタイムアウトせず、接続試行が継続されるため、この短いタイマーが切れて`t.Fatalf`が呼び出されることになります。
テストの目的は、これらの大きなタイムアウト値が設定されたときに、`Dial`が即座にエラーを返さず、むしろ「期待される時間内に戻らなかった」ことを確認することです。これは、デッドラインが正しく`math.MaxInt64`に設定され、即座のタイムアウトが回避されていることを間接的に検証しています。

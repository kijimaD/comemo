# [インデックス 27716] ファイルの概要

このコミットは、Goコンパイラの`append`組み込み関数の最適化に関するものです。具体的には、`append`の「高速パス」（スライスが再割り当てなしで拡張できる場合）において、`newlen`（新しい長さ）変数のスタックへのスピル（一時的な退避）を回避することで、スタック使用量を削減し、パフォーマンスを向上させることを目的としています。これは、`newlen`を必要に応じて再計算するというアプローチで実現されています。

## 変更の背景

Go言語の`append`組み込み関数は、非常に頻繁に使用される操作であり、そのパフォーマンスはGoプログラム全体の実行速度に大きな影響を与えます。特に、スライスの容量が足りている場合に要素を追加する「高速パス」は、可能な限り効率的である必要があります。

このコミットの主な目的は、`append`の高速パスにおけるコンパイラ生成コードの効率を改善することです。以前の実装では、`append`後の新しいスライスの長さ（`newlen`）を計算し、その値をスタックに一時的に保存（スピル）していました。しかし、この`newlen`は、スライスの容量が足りている場合にはすぐに使用され、容量が足りない場合には`growslice`関数が呼ばれて新しいスライスが作成されるため、その値は無効になります。

コミットの著者は、この`newlen`のスピルが不要なスタック使用量とメモリアクセスを引き起こしていることに着目しました。`newlen`をスタックに保存する代わりに、必要になったときに（特に`growslice`が呼ばれた後に）再計算することで、高速パスでのスピルをなくし、スタック使用量を8バイト削減できると判断しました。これにより、CPUレジスタをより効率的に利用できるようになり、全体的なパフォーマンスの向上が期待されます。

ただし、この変更は、まれに発生する「成長パス」（スライスの容量が足りず、新しいメモリ割り当てが必要な場合）において、`newlen`の再計算というわずかなオーバーヘッドを導入します。しかし、この再計算は非常に安価な操作であり、高速パスでのメリットがそれを上回ると考えられています。

コミットメッセージには、マイクロベンチマークの結果が「all over the map」（ばらつきが大きい）と記載されており、コードのわずかな変更によって結果が変動しやすいことが示唆されています。これは、このような低レベルの最適化が、他の要因（レジスタ割り当ての変更など）によって容易に影響を受けることを示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### Goのスライス (Slice)
Goのスライスは、配列への参照のようなものです。内部的には、以下の3つの要素で構成される構造体です。
1.  **ポインタ (Pointer)**: スライスの要素が格納されている基底配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。`len()`関数で取得できます。
3.  **容量 (Capacity)**: 基底配列の先頭から、スライスが拡張できる最大要素数。`cap()`関数で取得できます。

スライスは、基底配列の容量内で長さを変更できますが、容量を超えて要素を追加しようとすると、より大きな新しい基底配列が割り当てられ、既存の要素がコピーされます。

### `append` 組み込み関数
`append`は、スライスに要素を追加するために使用されるGoの組み込み関数です。
`s = append(s, elem1, elem2, ...)` のように使用します。
`append`の動作は、現在のスライスの容量に依存します。
*   **高速パス (Fast Path)**: スライスの容量が十分にある場合、新しい要素は既存の基底配列の末尾に追加され、スライスの長さが更新されます。この場合、新しいメモリ割り当てや要素のコピーは発生しません。
*   **成長パス (Growth Path)**: スライスの容量が不足している場合、`append`はより大きな新しい基底配列を割り当て、既存の要素と新しい要素をその新しい配列にコピーします。この処理は`runtime.growslice`関数によって行われます。

### SSA (Static Single Assignment) フォーム
SSAは、コンパイラ最適化の中間表現（IR: Intermediate Representation）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、より高度な最適化を可能にしました。このコミットは、SSAバックエンドにおける`append`のコード生成ロジックを改善するものです。

### スピル (Spill) とレジスタ割り当て (Register Allocation)
CPUには、高速なデータアクセスが可能な少数のレジスタがあります。コンパイラは、プログラムの実行中に頻繁に使用される変数をこれらのレジスタに割り当てようとします。しかし、レジスタの数が限られているため、すべての変数をレジスタに保持することはできません。
**スピル**とは、レジスタに割り当てられなかった変数や、一時的にレジスタが不足した場合に、その変数の値をメインメモリ（通常はスタック）に退避させる操作のことです。スピルはメモリアクセスを伴うため、パフォーマンスの低下につながります。
**レジスタ割り当て**は、どの変数をどのレジスタに割り当てるかを決定するコンパイラの重要なフェーズです。

### `runtime.growslice` 関数
Goランタイムの一部であり、スライスの容量が不足した際に新しい基底配列を割り当て、既存の要素をコピーする役割を担います。この関数は、新しいスライスのポインタ、長さ、容量を返します。

## 技術的詳細

このコミットの技術的詳細を理解するには、Goコンパイラが`append`をどのようにSSA形式に変換し、最終的な機械語を生成するかを追う必要があります。

`append(s, e1, e2, e3)`のような操作は、コンパイラ内部で以下のようなロジックに変換されます（コミットメッセージのコメントより）：

```go
// ptr, len, cap := s // スライスのポインタ、長さ、容量を取得
// newlen := len + 3  // 新しい長さを計算
// if newlen > s.cap { // 容量チェック
//     ptr, len, cap = growslice(s, newlen) // 容量不足ならgrowsliceを呼び出し、新しいスライス情報を取得
//     newlen = len + 3 // recalculate to avoid a spill // ここでnewlenを再計算！
// }
// *(ptr+len) = e1    // 新しい要素をコピー
// *(ptr+len+1) = e2
// *(ptr+len+2) = e3
// makeslice(ptr, newlen, cap) // 最終的なスライス構造を構築
```

変更前は、`newlen := len + 3`で計算された`newlen`が、`if newlen > s.cap`の条件分岐をまたいで使用されるため、コンパイラはこれをスタックにスピルする必要がありました。これは、`growslice`が呼ばれる可能性のあるパスと、呼ばれないパスの両方で`newlen`の値が利用されるため、SSAの`phi`関数（異なる制御フローパスから来る値を結合する）の入力として、スピルされた値が必要になるためです。

このコミットでは、このスピルを回避するために、`growslice`が呼ばれた後に`newlen`を再計算するという戦略を採用しました。
1.  まず、`newlen := len + 3`で新しい長さを計算します。
2.  この`newlen`と既存の`cap`を比較し、容量が足りるかどうかを判断します。
3.  容量が足りる場合（高速パス）、`newlen`はレジスタに保持されたまま、直接要素の追加と最終的なスライスの構築に使用されます。スピルは発生しません。
4.  容量が足りない場合（成長パス）、`runtime.growslice`が呼び出されます。`growslice`は新しい基底配列と、そのポインタ、**古いスライスの長さ**、新しい容量を返します。ここで重要なのは、`growslice`が返す長さは、`append`によって追加される要素の数を考慮していない、**古いスライスの長さ**であるという点です。
5.  `growslice`から戻った後、`newlen = len + 3`という再計算が行われます。ここで使用される`len`は、`growslice`が返した**古いスライスの長さ**であり、これに`append`で追加する要素数（この例では3）を加えることで、正しい`newlen`が再度得られます。

このアプローチにより、`newlen`は高速パスではスピルされず、成長パスでは`growslice`の呼び出し後に再計算されるため、常にレジスタに保持されるか、必要に応じて計算される形となり、スタックへのスピルが不要になります。結果として、スタック使用量が8バイト削減されます。

コミットメッセージの後半にあるアセンブリコードの比較では、`Before`のコードで`MOVQ DX, "".autotmp_0+64(SP)`という命令が`newlen`をスタックにスピルしているのに対し、`After`のコードではこのスピルがなくなっていることが確認できます。また、`After`のコードでは`growslice`呼び出し後に`ADDQ $3, CX`と`MOVQ CX, DX`という命令で`newlen`が再計算されていることが示されています。

ただし、コミットメッセージでは、レジスタ割り当ての最適化が不十分なため、コードサイズが2バイト増加している点も指摘されています。これは、`growslice`から返された値を一時的に`CX`レジスタに格納し、その後`DX`レジスタに移動しているためであり、理想的には`DX`レジスタに直接格納されるべきであると述べられています。これは、コンパイラのレジスタ割り当てアルゴリズムの改善の余地を示唆しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go`

1.  **`newlenVar` の追加**:
    `ptrVar`, `capVar`などと同様に、`newlenVar`というダミーノードが追加されました。これは、SSA形式で`newlen`変数を表現するために使用されます。

2.  **`exprAppend` 関数のコメント更新**:
    `append`のコンパイルロジックを示すコメントが更新され、`growslice`呼び出し後に`newlen = len + 3 // recalculate to avoid a spill`という行が追加されました。これは、このコミットの主要な最適化戦略を明確に示しています。

3.  **`s.vars[&newlenVar] = nl` の追加**:
    `exprAppend`関数内で、最初に計算された`newlen`（`nl`）が`s.vars[&newlenVar]`に格納されるようになりました。これは、SSA形式で`newlen`の値を追跡するために必要です。

4.  **`growslice` 呼び出し後の `newlen` 再計算**:
    最も重要な変更点です。`runtime.growslice`が呼び出された後、以前は`newlen`の値をスタックから読み出す必要がありましたが、この変更により、`growslice`が返す新しいスライスの長さ（`r[1]`）に、`append`で追加する要素数（`nargs`）を直接加算することで、`newlen`を再計算するようになりました。
    `s.vars[&newlenVar] = s.newValue2(s.ssaOp(OADD, Types[TINT]), Types[TINT], r[1], s.constInt(Types[TINT], nargs))`
    この再計算により、`newlen`をスタックにスピルする必要がなくなります。

5.  **`nl = s.variable(&newlenVar, Types[TINT])` の追加**:
    `append`の処理の終盤で、`ptr`や`cap`と同様に、`newlen`も`phi`関数を通じて適切な値が取得されるように変更されました。これにより、条件分岐（高速パスと成長パス）のどちらを通っても、正しい`newlen`が後続の処理に渡されます。

6.  **`delete(s.vars, &newlenVar)` の追加**:
    `append`処理の最後に、一時変数として使用された`newlenVar`がクリーンアップされます。

これらの変更により、コンパイラは`append`の高速パスにおいて`newlen`をスタックにスピルすることなく、レジスタをより効率的に利用できるようになります。

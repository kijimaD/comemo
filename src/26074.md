# [インデックス 26074] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおけるHTTPサーバーが `Host` ヘッダーを検証する方法を改善するものです。具体的には、HTTP/1.1の仕様に準拠し、`Host` ヘッダーが必須であることを強制し、また `Host` ヘッダー内に不正なバイトが含まれていないかを検証する機能を追加しています。これにより、潜在的なセキュリティ脆弱性（HTTP Request/Response Splittingなど）を防ぎ、HTTPプロトコルの厳格な解釈を保証します。

## 変更の背景

このコミットの主な背景には、HTTP/1.1プロトコルにおける `Host` ヘッダーの重要性と、それに関連するセキュリティ上の懸念があります。

1.  **HTTP/1.1仕様への準拠**: HTTP/1.1 (RFC 7230 Section 5.4) では、`Host` ヘッダーは必須とされています。しかし、Goの `net/http` パッケージのサーバー実装は、これまでこの要件を厳密に強制していませんでした（Issue #13624）。これにより、仕様に準拠しないリクエストが処理される可能性がありました。
2.  **セキュリティ脆弱性の解消 (Issue #11206)**: 以前のGoの `net/http` パッケージは、`Host` ヘッダー内に不正なバイト（非ASCII文字や制御文字など）が含まれていても、それを許容していました。このような不適切な検証は、HTTP Request/Response Splitting (CWE-113) や HTTP Response Smuggling といったセキュリティ脆弱性を引き起こす可能性があります。攻撃者は、`Host` ヘッダーに改行文字などを挿入することで、サーバーがリクエストの境界を誤認識するように仕向け、意図しないレスポンスを生成させたり、キャッシュポイズニングを行ったりすることが可能になります。このコミットは、`Host` ヘッダーの厳格なバイト検証を導入することで、これらの攻撃経路を塞ぐことを目的としています。
3.  **堅牢性の向上**: プロトコル仕様に厳密に従うことで、サーバーの堅牢性と予測可能性が向上し、予期せぬ動作や互換性の問題を未然に防ぎます。

これらの背景から、`Host` ヘッダーの検証を強化し、HTTP/1.1の仕様に厳密に準拠することが必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

*   **HTTP/1.1プロトコル**: Web上でデータをやり取りするための主要なプロトコルです。リクエストとレスポンスの構造、ヘッダーの役割などが定義されています。
*   **`Host` ヘッダー**: HTTP/1.1リクエストにおいて必須のヘッダーです。クライアントがアクセスしようとしているサーバーのドメイン名と、オプションでポート番号を指定します。これは、単一のIPアドレスで複数のドメイン（バーチャルホスト）をホストしているサーバーが、どのドメイン宛のリクエストであるかを識別するために不可欠です。
    *   **RFC 7230 Section 5.4**: `Host` ヘッダーの構文と要件を定義しています。`Host = uri-host [ \":\" port ]` の形式でなければなりません。`uri-host` はRFC 3986 Section 3.2.2で定義されており、特定の文字セットのみが許可されます。
*   **HTTP Request/Response Splitting (CWE-113)**: 攻撃者がHTTPリクエストヘッダーに改行文字（CRLF）を挿入することで、サーバーがリクエストの終わりを誤認識し、後続のデータが新しいリクエストまたはレスポンスヘッダーの一部として解釈されるように仕向ける脆弱性です。これにより、攻撃者はキャッシュポイズニング、クロスサイトスクリプティング (XSS)、セッションハイジャックなどの様々な攻撃を実行できます。`Host` ヘッダーのような重要なヘッダーの不適切な検証がこの脆弱性の原因となることがあります。
*   **`net/http` パッケージ**: Go言語の標準ライブラリの一部で、HTTPクライアントとサーバーの実装を提供します。WebアプリケーションやAPIサーバーを構築する際に広く利用されます。
*   **`bufio.Reader` と `textproto.Reader`**: `bufio.Reader` はバッファリングされたI/Oを提供し、効率的な読み取りを可能にします。`textproto.Reader` は、HTTPヘッダーのようなテキストベースのプロトコルを解析するために `bufio.Reader` の上に構築されたユーティリティです。

## 技術的詳細

このコミットでは、`net/http` パッケージのサーバーサイドにおける `Host` ヘッダーの検証ロジックが大幅に強化されています。

1.  **`readRequest` 関数の導入と変更**:
    *   既存の `ReadRequest` 関数は、内部的に新しい `readRequest(b *bufio.Reader, deleteHostHeader bool)` 関数を呼び出すように変更されました。
    *   `readRequest` 関数は、リクエストのパース処理を担当し、`deleteHostHeader` 引数によって `Host` ヘッダーを `req.Header` マップから削除するかどうかを制御します。サーバーの内部処理では `Host` ヘッダーは `req.Host` フィールドに昇格されるため、`req.Header` からは削除されます。
    *   この変更により、`Host` ヘッダーの処理がより柔軟になり、サーバー内部での `Host` ヘッダーの取り扱いが一元化されます。

2.  **`Host` ヘッダーの必須化 (HTTP/1.1)**:
    *   `src/net/http/server.go` の `(c *conn) readRequest()` メソッド内で、HTTP/1.1以上のプロトコルバージョン (`req.ProtoAtLeast(1, 1)`) の場合、`Host` ヘッダーが存在しない、または空である場合に `400 Bad Request` を返すようになりました。これはRFC 7230の仕様に厳密に準拠するための変更です。

3.  **`Host` ヘッダーの重複チェック**:
    *   複数の `Host` ヘッダーが検出された場合も `400 Bad Request` を返すようになりました。HTTP仕様では `Host` ヘッダーは単一であるべきです。

4.  **`Host` ヘッダーのバイト検証 (`validHostHeader` と `validHostByte`)**:
    *   `src/net/http/request.go` に `validHostHeader(h string) bool` という新しい関数が追加されました。この関数は、与えられた `Host` ヘッダー文字列 `h` が有効なバイトのみで構成されているかをチェックします。
    *   検証には、`validHostByte` という `[256]bool` 型の配列が使用されます。この配列は、`Host` ヘッダーとして許可されるASCII文字（数字、英字、一部の記号 `!$%&'()*+,-.:;=[]_~`）に対応するインデックスが `true` に設定されています。
    *   `validHostHeader` は、`Host` ヘッダー文字列の各バイトをループし、`validHostByte` 配列でそのバイトが許可されているかを確認します。許可されていないバイトが見つかった場合、`false` を返します。
    *   この検証は、RFC 7230およびRFC 3986で定義されている `uri-host` の文字セットに準拠しようとするものですが、コミットメッセージには「当面は、これらの表現のいずれにおいても有効なバイトではないバイトを検索する」とあり、より広範な文字を許容しつつも、明らかに不正なバイトを排除するアプローチを取っていることが示唆されています。
    *   `Host` ヘッダーがこの検証に失敗した場合も、`400 Bad Request` が返されます。

5.  **エラーハンドリングの改善 (`badRequestError`)**:
    *   `src/net/http/server.go` に `badRequestError` という新しい型が導入されました。これは `string` 型のエイリアスで、`Error()` メソッドを実装することで `error` インターフェースを満たします。
    *   `badRequestError` は、クライアントに返される `400 Bad Request` レスポンスの本文に、より具体的なエラーメッセージを含めるために使用されます。これにより、デバッグや問題の特定が容易になります。

6.  **テストケースの追加と修正**:
    *   `src/net/http/serve_test.go` に `TestServerValidatesHostHeader` という新しいテスト関数が追加され、様々な有効/無効な `Host` ヘッダーのシナリオがテストされています。これには、空の `Host` ヘッダー、不正なバイトを含む `Host` ヘッダー、複数の `Host` ヘッダーなどが含まれます。
    *   既存のテストケースも、HTTP/1.1リクエストに `Host` ヘッダーを追加するように修正され、新しい検証ロジックが正しく機能することを確認しています。

これらの変更により、Goの `net/http` サーバーは、`Host` ヘッダーの処理においてよりセキュアで仕様に準拠した動作をするようになりました。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、それぞれの変更の概要は以下の通りです。

*   **`src/net/http/request.go`**:
    *   `ReadRequest` 関数が `readRequest` を呼び出すように変更。
    *   `readRequest` 関数に `deleteHostHeader` 引数を追加。
    *   `validHostHeader` 関数と `validHostByte` 配列が追加され、`Host` ヘッダーのバイトレベルの検証ロジックが実装されました。
*   **`src/net/http/serve_test.go`**:
    *   `TestServerValidatesHostHeader` という新しいテスト関数が追加され、`Host` ヘッダーの様々な検証シナリオ（有効なもの、無効なもの、欠落しているもの、重複しているもの）が網羅的にテストされています。
    *   既存のテストケース（例: `TestServerBufferedChunking`, `TestCodesPreventingContentTypeAndBody`, `TestContentTypeOkayOn204`）において、HTTP/1.1リクエストに `Host` ヘッダーが明示的に追加されるように修正されました。
*   **`src/net/http/server.go`**:
    *   `(*conn) readRequest()` メソッド内で、`Host` ヘッダーの存在チェック、重複チェック、および `validHostHeader` 関数によるバイト検証が統合されました。
    *   HTTP/1.1リクエストで `Host` ヘッダーが欠落している場合、または不正な場合に `400 Bad Request` を返すロジックが追加されました。
    *   `badRequestError` 型が導入され、エラーメッセージのカスタマイズが可能になりました。
    *   `io.WriteString` を用いたエラーレスポンスの生成部分が、`badRequestError` を利用してより詳細なエラーメッセージを返すように変更されました。

## コアとなるコードの解説

このコミットの核心は、`Host` ヘッダーの検証ロジックと、それがリクエスト処理パイプラインにどのように統合されたかにあります。

1.  **`validHostHeader` 関数と `validHostByte` 配列**:
    `src/net/http/request.go` に追加された `validHostHeader` 関数は、`Host` ヘッダーのセキュリティと仕様準拠を保証する主要なメカニズムです。

    ```go
    func validHostHeader(h string) bool {
        // The latests spec is actually this:
        //
        // http://tools.ietf.org/html/rfc7230#section-5.4
        //     Host = uri-host [ ":" port ]
        //
        // Where uri-host is:
        //     http://tools.ietf.org/html/rfc3986#section-3.2.2
        //
        // But we're going to be much more lenient for now and just
        // search for any byte that's not a valid byte in any of those
        // expressions.
        for i := 0; i < len(h); i++ {
            if !validHostByte[h[i]] {
                return false
            }
        }
        return true
    }

    // See the validHostHeader comment.
    var validHostByte = [256]bool{
        '0': true, '1': true, '2': true, '3': true, '4': true, '5': true, '6': true, '7': true,
        '8': true, '9': true,

        'a': true, 'b': true, 'c': true, 'd': true, 'e': true, 'f': true, 'g': true, 'h': true,
        'i': true, 'j': true, 'k': true, 'l': true, 'm': true, 'n': true, 'o': true, 'p': true,
        'q': true, 'r': true, 's': true, 't': true, 'u': true, 'v': true, 'w': true, 'x': true,
        'y': true, 'z': true,

        'A': true, 'B': true, 'C': true, 'D': true, 'E': true, 'F': true, 'G': true, 'H': true,
        'I': true, 'J': true, 'K': true, 'L': true, 'M': true, 'N': true, 'O': true, 'P': true,
        'Q': true, 'R': true, 'S': true, 'T': true, 'U': true, 'V': true, 'W': true, 'X': true,
        'Y': true, 'Z': true,

        '!':  true, // sub-delims
        '$':  true, // sub-delims
        '%':  true, // pct-encoded (and used in IPv6 zones)
        '&':  true, // sub-delims
        '(':  true, // sub-delims
        ')':  true, // sub-delims
        '*':  true, // sub-delims
        '+':  true, // sub-delims
        ',':  true, // sub-delims
        '-':  true, // unreserved
        '.':  true, // unreserved
        ':':  true, // IPv6address + Host expression's optional port
        ';':  true, // sub-delims
        '=':  true, // sub-delims
        '[':  true,
        '\'': true, // sub-delims
        ']':  true,
        '_':  true, // unreserved
        '~':  true, // unreserved
    }
    ```
    `validHostByte` は、ASCII文字の各バイト値が `Host` ヘッダーで許可されているかどうかを高速にルックアップするための真偽値テーブルです。`validHostHeader` 関数はこのテーブルを使って、`Host` ヘッダー文字列内の各バイトが許可された文字セットに含まれているかを効率的にチェックします。これにより、不正な制御文字やその他の危険なバイトが `Host` ヘッダーに挿入されるのを防ぎます。

2.  **`(*conn) readRequest()` メソッドでの検証統合**:
    `src/net/http/server.go` の `(*conn) readRequest()` メソッドは、クライアントからのリクエストを読み取り、パースするサーバーの主要な部分です。このメソッド内で、`Host` ヘッダーの検証が早期に行われるようになりました。

    ```go
    // ... (既存のコード) ...

    req, err := readRequest(c.bufr, false) // readRequestを呼び出し
    // ... (エラーハンドリング) ...

    hosts, haveHost := req.Header["Host"]
    if req.ProtoAtLeast(1, 1) && (!haveHost || len(hosts) == 0) {
        return nil, badRequestError("missing required Host header") // HTTP/1.1でHostヘッダーがない場合
    }
    if len(hosts) > 1 {
        return nil, badRequestError("too many Host headers") // 複数のHostヘッダーがある場合
    }
    if len(hosts) == 1 && !validHostHeader(hosts[0]) {
        return nil, badRequestError("malformed Host header") // 不正なバイトを含むHostヘッダーの場合
    }
    delete(req.Header, "Host") // 処理後、HeaderマップからHostを削除

    // ... (既存のコード) ...
    ```
    このコードブロックは、以下の順序で `Host` ヘッダーを検証します。
    *   まず、`readRequest` を呼び出してリクエストをパースし、`req` オブジェクトを取得します。
    *   HTTP/1.1以上のプロトコルである場合、`Host` ヘッダーが存在し、かつ空でないことを確認します。満たされない場合は `badRequestError` を返します。
    *   `Host` ヘッダーが複数存在しないことを確認します。存在する場合は `badRequestError` を返します。
    *   `Host` ヘッダーが1つだけ存在する場合、`validHostHeader` 関数を呼び出して、その内容が有効なバイトのみで構成されているかを検証します。無効な場合は `badRequestError` を返します。
    *   すべての検証を通過した後、`req.Header` マップから `Host` ヘッダーを削除します。これは、`req.Host` フィールドに値が昇格されるため、ヘッダーマップには不要となるためです。

3.  **`badRequestError` の導入**:
    `badRequestError` 型は、サーバーが `400 Bad Request` レスポンスを返す際に、より具体的なエラー原因をクライアントに伝えるためのメカニズムです。

    ```go
    type badRequestError string

    func (e badRequestError) Error() string { return "Bad Request: " + string(e) }

    // ... (エラーレスポンス生成部分) ...
    var publicErr string
    if v, ok := err.(badRequestError); ok {
        publicErr = ": " + string(v)
    }
    io.WriteString(c.rwc, "HTTP/1.1 400 Bad Request\\r\\nContent-Type: text/plain\\r\\nConnection: close\\r\\n\\r\\n400 Bad Request"+publicErr)
    ```
    これにより、例えば「missing required Host header」や「malformed Host header」といった具体的なメッセージが `400 Bad Request` の後に付加され、クライアント側でのデバッグが容易になります。

これらの変更は、Goの `net/http` サーバーがHTTPプロトコルをより厳格に解釈し、セキュリティ上のリスクを軽減するための重要なステップです。

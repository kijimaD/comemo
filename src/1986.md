## 変更の背景

このコミットは、Go言語の初期のコンパイラ `6g` における内部バグトラッキングID `bug 142` を修正するために行われました。具体的には、Go言語における論理AND (`&&`) および論理OR (`||`) 演算子の評価順序に関する問題に対処しています。

多くのプログラミング言語と同様に、Go言語の論理演算子も「短絡評価（short-circuit evaluation）」の原則に従います。これは、式全体の真偽が左側のオペランドだけで決定できる場合、右側のオペランドは評価されないというものです。例えば、`A && B` の場合、`A` が `false` であれば `B` は評価されません。`A || B` の場合、`A` が `true` であれば `B` は評価されません。この特性は、パフォーマンスの最適化（不要な計算のスキップ）や、安全なコードの記述（例えば、`if (ptr != nil && ptr.method())` のように、`nil` ポインタのデリファレンスを防ぐ）に不可欠です。

このコミット以前の `6g` コンパイラでは、特定の条件下で、論理演算子の右側のオペランドが左側のオペランドよりも先に評価されてしまう、あるいは不適切な順序で評価されてしまうバグが存在したと考えられます。これは、短絡評価のセマンティクスを破り、予期せぬ副作用や誤った結果を引き起こす可能性がありました。例えば、右側のオペランドが関数呼び出しを含んでいた場合、本来実行されるべきではない関数が実行されてしまうといった問題が発生し得ます。

この修正は、コンパイラが論理演算子を正しく処理し、Go言語の仕様に準拠した評価順序を保証するために不可欠でした。

## 前提知識の解説

*   **Go言語のコンパイラ `6g`**:
    `6g` は、Go言語の初期開発段階で使用されていたコンパイラツールチェーンの一部です。特に、64-bit x86 (AMD64) アーキテクチャ向けのGoプログラムをコンパイルするために設計されていました。Goのコンパイラは、Go言語自体で書かれるようになる前は、C言語で実装されていました。`6g` は、その後のGoコンパイラの進化の基礎となりましたが、現在ではより汎用的な `go tool compile` コマンドに統合されています。

*   **論理演算子の短絡評価 (Short-circuit Evaluation)**:
    プログラミングにおける論理AND (`&&`) および論理OR (`||`) 演算子の重要な特性です。
    *   `A && B`: `A` が `false` と評価された場合、式全体の結果は `false` であることが確定するため、`B` は評価されません。
    *   `A || B`: `A` が `true` と評価された場合、式全体の結果は `true` であることが確定するため、`B` は評価されません。
    この特性は、パフォーマンスの最適化（不要な計算のスキップ）や、安全なコードの記述（例えば、`if (ptr != nil && ptr.method())` のように、`nil` ポインタのデリファレンスを防ぐ）に不可欠です。

*   **抽象構文木 (Abstract Syntax Tree, AST)**:
    コンパイラのフロントエンドがソースコードを解析して生成する、プログラムの構造を表現するツリー構造のデータです。各ノードは、変数、演算子、関数呼び出しなどのプログラム要素を表します。コンパイラのバックエンド（コード生成部分）は、このASTをトラバースして機械語コードを生成します。

*   **Sethi-Ullman アルゴリズム**:
    コンパイラ設計において、式ツリーのコード生成とレジスタ割り当てを最適化するためのアルゴリズムです。このアルゴリズムは、式を評価するために必要なレジスタの最小数を決定し、それに基づいて効率的なコードシーケンスを生成することを目的としています。
    `cgen.c` 内の `ullman` というフィールドは、このアルゴリズムに関連する「コスト」や「レジスタ必要数」を示す値である可能性が高いです。`UINF` (Ullman Infinity) は、非常に高いコストや、特定の条件下での評価順序の制約を示す定数として使用されていたと考えられます。
    このアルゴリズムは、式の評価順序がレジスタ使用量に影響を与える場合に特に重要です。論理演算子のように、オペランドの評価順序がセマンティクスに影響を与える場合、このアルゴリズムの適用には細心の注意が必要です。

*   **`tempname` 関数**:
    コンパイラが一時的な変数やレジスタを必要とする際に、それらに割り当てる名前（または識別子）を生成するためのユーティリティ関数です。コード生成の過程で、中間結果を保持するために一時的な記憶領域が必要になることがよくあります。

*   **`Node` 構造体**:
    ASTの各ノードを表すデータ構造です。`n->left` や `n->right` は、それぞれ二項演算子（この場合は `&&` や `||`）の左オペランドと右オペランドに対応する子ノードを指します。

## 技術的詳細

変更は `src/cmd/6g/cgen.c` ファイル内の `cgen` 関数に集中しています。この関数は、ASTノード `n` を受け取り、そのノードに対応するコードを生成する役割を担っています。

問題の箇所は、`nl` (左オペランド) と `nr` (右オペランド) の両方が `ullman >= UINF` という条件を満たす場合です。これは、両方のオペランドが複雑な式であり、Sethi-Ullmanアルゴリズムにおいて評価に多くのレジスタを必要とする、あるいは特定の評価順序の制約があることを示唆しています。

修正前は、この条件下で右オペランド `nr` が先に評価され、その結果が一時変数 `n1` に格納されていました (`cgen(nr, &n1);`)。その後、元のノード `n` の右オペランドがこの一時変数 `n1` に置き換えられ (`n2.right = &n1;`)、`n2` (元のノードのコピー) が評価されていました。

この評価順序は、論理ANDや論理ORの短絡評価のセマンティクスに反していました。短絡評価では、常に左オペランドが先に評価され、その結果に基づいて右オペランドの評価が必要かどうかが判断されるべきです。

修正は、この評価順序を反転させるものです。
*   `tempname(&n1, nr->type);` が `tempname(&n1, nl->type);` に変更され、一時変数の型が右オペランドではなく左オペランドの型に基づいて決定されるようになりました。これは、左オペランドの結果を保持するための一時変数であることを明確にしています。
*   `cgen(nr, &n1);` が `cgen(nl, &n1);` に変更され、**左オペランド `nl` が先に評価され、その結果が一時変数 `n1` に格納される**ようになりました。
*   `n2.right = &n1;` が `n2.left = &n1;` に変更され、元のノードの**左オペランド**がこの一時変数 `n1` に置き換えられるようになりました。

この変更により、コンパイラは論理演算子の左オペランドを常に先に評価し、その結果を一時的に保持するようになりました。これにより、短絡評価の原則が正しく適用され、右オペランドの評価が必要な場合にのみ行われるようになります。これは、Go言語のセマンティクスに合致し、予期せぬ動作やバグを防ぐ上で極めて重要です。

## コアとなるコードの解説

変更が行われたのは、`cgen` 関数内の特定の条件ブロックです。このブロックは、論理演算子（`&&` や `||`）のような二項演算子を処理する際に、両方のオペランド（`nl` と `nr`）が複雑な式であり、Sethi-Ullmanアルゴリズムにおいて高いコスト（`ullman >= UINF`）を持つ場合に実行されます。

*   **修正前**:
    1.  `tempname(&n1, nr->type);`: 右オペランド `nr` の型に基づいて一時変数 `n1` を準備します。
    2.  `cgen(nr, &n1);`: **右オペランド `nr` のコードを生成し、その結果を一時変数 `n1` に格納します。**
    3.  `n2 = *n;`: 現在のノード `n` のコピー `n2` を作成します。
    4.  `n2.right = &n1;`: コピー `n2` の**右オペランド**を、先ほど評価した一時変数 `n1` に置き換えます。
    5.  `cgen(&n2, res);`: 変更された `n2` に対してコード生成を続行します。
    このシーケンスは、短絡評価の原則に反し、右オペランドが左オペランドよりも先に評価される可能性がありました。

*   **修正後**:
    1.  `tempname(&n1, nl->type);`: **左オペランド `nl` の型に基づいて一時変数 `n1` を準備します。**
    2.  `cgen(nl, &n1);`: **左オペランド `nl` のコードを生成し、その結果を一時変数 `n1` に格納します。**
    3.  `n2 = *n;`: 現在のノード `n` のコピー `n2` を作成します。
    4.  `n2.left = &n1;`: コピー `n2` の**左オペランド**を、先ほど評価した一時変数 `n1` に置き換えます。
    5.  `cgen(&n2, res);`: 変更された `n2` に対してコード生成を続行します。
    この修正により、常に左オペランドが先に評価され、その結果が一時変数に保持されるようになりました。これにより、短絡評価のセマンティクスが正しく実装され、論理演算子の評価順序がGo言語の仕様に準拠するようになりました。

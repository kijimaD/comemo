## 元コミット内容

このコミットの主な目的は、Go言語の標準ライブラリである`image/jpeg`パッケージに、JPEG画像のクロマサブサンプリング形式のうち、4:1:1と4:1:0のサポートを追加することです。これにより、これらの形式でエンコードされたJPEG画像を正しくデコードできるようになります。

## 変更の背景

JPEG画像は、色情報を効率的に圧縮するために「クロマサブサンプリング」という技術を使用します。これは、人間の目が輝度（明るさ）の変化には敏感である一方で、色（色相と彩度）の変化には比較的鈍感であるという特性を利用したものです。そのため、色情報を間引くことで、視覚的な品質を大きく損なうことなくファイルサイズを削減できます。

Goの`image/jpeg`パッケージは、これまで4:4:4（非サブサンプリング）、4:4:0、4:2:2、4:2:0といった一般的なクロマサブサンプリング形式をサポートしていました。しかし、4:1:1や4:1:0といった、より積極的に色情報を間引く形式はサポートされていませんでした。これらの形式は、特に帯域幅が限られた環境や、ファイルサイズを極限まで小さくしたい場合に利用されることがあります。

このサポートの欠如は、Goアプリケーションがこれらの形式のJPEG画像を処理しようとした際に、デコードエラーや不正な画像表示を引き起こす可能性がありました。このコミットは、このような互換性の問題を解消し、`image/jpeg`パッケージの堅牢性と汎用性を向上させることを目的としています。

コミットメッセージにあるように、新しいテストデータは`cjpeg`ツールを使って生成されており、これはこれらの新しいサブサンプリング形式が実際に使用されていることを示唆しています。

## 前提知識の解説

### JPEGとYCbCr色空間

JPEG（Joint Photographic Experts Group）は、静止画像の圧縮方式の一つであり、特に写真のような自然画の圧縮に適しています。JPEGは通常、画像をRGB色空間からYCbCr色空間に変換して処理します。

*   **Y (Luma)**: 輝度成分。画像の明るさを表します。人間の目が最も敏感に感じる情報です。
*   **Cb (Chroma Blue)**: 青色差成分。青と黄色の間の色情報を表します。
*   **Cr (Chroma Red)**: 赤色差成分。赤とシアンの間の色情報を表します。

YCbCr色空間を使用することで、輝度と色度を分離して扱うことができ、色度情報を間引く「クロマサブサンプリング」が可能になります。

### クロマサブサンプリング

クロマサブサンプリングは、色度情報（CbとCr）を輝度情報（Y）よりも低い解像度で保存する技術です。これにより、ファイルサイズを削減できます。表記は通常「J:a:b」形式で表されます。

*   **J**: 輝度情報の水平サンプリング係数（通常4）。
*   **a**: 最初の行におけるCb/Crの水平サンプリング係数。
*   **b**: 2行目におけるCb/Crの水平サンプリング係数。

主要なクロマサブサンプリング形式は以下の通りです。

*   **4:4:4 (Full Sampling)**: CbとCrの解像度がYと同じ。色情報が完全に保持されるため、最高品質ですがファイルサイズは大きくなります。プロフェッショナルな用途や、色情報の損失が許されない場合に用いられます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり4サンプル
*   **4:2:2 (Horizontal Subsampling)**: CbとCrが水平方向に半分に間引かれます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり2サンプル
*   **4:2:0 (Horizontal and Vertical Subsampling)**: CbとCrが水平方向と垂直方向の両方で半分に間引かれます。最も一般的な形式で、ウェブ画像やデジタルカメラで広く使われています。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり1サンプル
*   **4:1:1 (More Horizontal Subsampling)**: CbとCrが水平方向に4分の1に間引かれます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり1サンプル（水平方向で4分の1）
*   **4:1:0 (More Horizontal and Vertical Subsampling)**: CbとCrが水平方向に4分の1、垂直方向に半分に間引かれます。これは4:1:1よりもさらに色情報を間引く形式です。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり0.5サンプル（水平方向で4分の1、垂直方向で半分）

これらの形式は、輝度成分（Y）のサンプリングを基準として、色差成分（Cb, Cr）がどれだけ間引かれているかを示します。例えば、4:1:1は、4つの輝度サンプルに対して1つの色差サンプルが存在することを意味します。

### JPEGデコードのプロセス概要

JPEGデコードは、主に以下のステップで構成されます。

1.  **データ読み込みと解析**: JPEGファイルのヘッダ情報を読み込み、画像サイズ、コンポーネント数（Y, Cb, Crなど）、量子化テーブル、ハフマンテーブル、クロマサブサンプリング比などを解析します。
2.  **逆量子化**: 圧縮されたDCT係数を量子化テーブルを使って逆量子化し、元のDCT係数に戻します。
3.  **逆DCT (IDCT)**: DCT係数を空間ドメインのピクセルデータに変換します。
4.  **クロマアップサンプリング**: 間引かれた色差成分（Cb, Cr）を、輝度成分（Y）の解像度に合わせて補間します。このステップが、今回の変更の核心部分です。
5.  **YCbCrからRGBへの変換**: YCbCr色空間のピクセルデータを、表示に適したRGB色空間に変換します。

このコミットは、ステップ4のクロマアップサンプリングのロジックに、4:1:1と4:1:0の新しいサブサンプリング比率を認識させ、適切に処理できるようにするものです。

## 技術的詳細

このコミットは、主に`src/image/jpeg/reader.go`と`src/image/jpeg/scan.go`の2つのファイルに修正を加えています。

### `src/image/jpeg/reader.go`の変更

このファイルはJPEGデコーダの主要なロジックを含んでいます。特に、JPEGのフレームヘッダ（SOF: Start Of Frame）を処理する`processSOF`関数が変更されています。

`processSOF`関数は、各コンポーネント（Y, Cb, Cr）の水平サンプリング係数（h）と垂直サンプリング係数（v）を読み取ります。これまでの実装では、Yコンポーネントの`(h, v)`の組み合わせとして、`(1, 1)`, `(1, 2)`, `(2, 1)`, `(2, 2)`のみをサポートしていました。これらはそれぞれ、4:4:4, 4:4:0, 4:2:2, 4:2:0のサブサンプリング比率に対応します。

今回の変更では、Yコンポーネントの`(h, v)`の組み合わせに、新たに`(4, 1)`と`(4, 2)`が追加されました。

*   `(4, 1)`: これは4:1:1サブサンプリングに対応します。輝度情報が水平方向に4倍、垂直方向に1倍の解像度でサンプリングされ、色差情報が水平方向に1倍、垂直方向に1倍の解像度でサンプリングされることを意味します。全体として、輝度ブロック4x1に対して色差ブロック1x1となります。
*   `(4, 2)`: これは4:1:0サブサンプリングに対応します。輝度情報が水平方向に4倍、垂直方向に2倍の解像度でサンプリングされ、色差情報が水平方向に1倍、垂直方向に1倍の解像度でサンプリングされることを意味します。全体として、輝度ブロック4x2に対して色差ブロック1x1となります。

これらの新しい`(h, v)`値が`hv`変数（`h`と`v`をパックしたもの）に追加され、サポートされていない比率の場合に`UnsupportedError`を返すチェックロジックが更新されました。

また、以前のコードにあった`maxH = 2`と`maxV = 2`という定数が削除されています。これは、水平サンプリング係数が最大4になる新しいサブサンプリング形式をサポートするために、これらの制約が不要になったためです。

### `src/image/jpeg/scan.go`の変更

このファイルは、JPEGの走査（スキャン）処理、特にYCbCrからRGBへの変換や、クロマアップサンプリングに関連するロジックを含んでいます。

`makeImg`関数は、デコードされたYCbCrデータから最終的な`image.YCbCr`構造体を生成する際に、適切な`image.YCbCrSubsampleRatio`を設定します。この関数に、新しい`(h0, v0)`の組み合わせに対する`image.YCbCrSubsampleRatio411`と`image.YCbCrSubsampleRatio410`のケースが追加されました。

*   `h0 == 4 && v0 == 1`: `image.YCbCrSubsampleRatio411`が設定されます。
*   `h0 == 4 && v0 == 2`: `image.YCbCrSubsampleRatio410`が設定されます。

これにより、Goの`image`パッケージがこれらの新しいサブサンプリング比率を認識し、それに応じた内部処理（特にアップサンプリング）を行うことができるようになります。

さらに重要な変更は、`processSOS`関数内のブロック座標計算ロジックです。この関数は、スキャンデータからDCTブロックを読み取り、適切なピクセル位置に配置する役割を担っています。特に、色差成分のブロックを配置する際の座標計算が修正されました。

以前のコードでは、`bx`と`by`の計算が特定のサブサンプリング比率（主に4:2:0など）に特化しており、`h0`が1の場合とそうでない場合で異なるロジックを持っていました。新しいコードでは、`bx = d.comp[compIndex].h*mx + j%h0`と`by = d.comp[compIndex].v*my + j/h0`という汎用的な計算式に置き換えられました。

この変更は、異なる水平サンプリング係数（特に新しい`h0=4`の場合）を持つサブサンプリング形式でも、色差ブロックの正しいピクセル位置を計算できるようにするために不可欠です。`j%h0`と`j/h0`を使用することで、現在のブロック内のサブサンプルインデックス`j`とコンポーネントの水平サンプリング係数`h0`に基づいて、より柔軟かつ正確に座標を決定できるようになります。

### テストデータの追加

コミットメッセージに記載されているように、新しいテストデータファイルが`src/image/testdata/`ディレクトリに追加されました。これらは`cjpeg`ツールを使用して生成された、4:1:0および4:1:1形式のJPEG画像（プログレッシブJPEG版も含む）です。

*   `video-001.q50.410.progressive.jpeg`

*   `video-001.q50.411.progressive.jpeg`

これらのテストデータは、`src/image/jpeg/reader_test.go`の`TestDecodeProgressive`関数に追加され、新しいサブサンプリング形式のデコードが正しく行われることを検証します。バイナリファイルとして追加されているため、差分表示では`Bin 0 -> XXXX bytes`と表示されます。

## コアとなるコードの解説

### `src/image/jpeg/reader.go`

*   **`maxH`と`maxV`定数の削除**:
    *   以前は、サポートするクロマサブサンプリング形式の輝度サンプリング係数（h, v）が最大2x2に制限されていました。これは、4:4:4 (1,1), 4:4:0 (1,2), 4:2:2 (2,1), 4:2:0 (2,2) のみをサポートしていたためです。
    *   4:1:1 (4,1) や 4:1:0 (4,2) のような水平サンプリング係数 `h=4` を持つ形式をサポートするためには、この制限が不適切になるため削除されました。
*   **`processSOF`関数内の`hv`チェックの拡張**:
    *   `processSOF`関数は、JPEGのSOFマーカー（Start Of Frame）を解析し、画像の基本情報（幅、高さ、コンポーネント数、サンプリング係数など）を読み取ります。
    *   特に、Yコンポーネントの水平サンプリング係数`h`と垂直サンプリング係数`v`を組み合わせた`hv`値のチェックロジックが変更されました。
    *   `if hv != 0x11 && hv != 0x21 && hv != 0x22 && hv != 0x12` の行に、新たに `&& hv != 0x41 && hv != 0x42` が追加されました。
        *   `0x41`は`h=4, v=1`（4:1:1サブサンプリング）に対応します。
        *   `0x42`は`h=4, v=2`（4:1:0サブサンプリング）に対応します。
    *   これにより、デコーダはこれらの新しいサブサンプリング形式を認識し、`UnsupportedError`を発生させることなく処理を続行できるようになります。

### `src/image/jpeg/reader_test.go`

*   **`TestDecodeProgressive`へのテストケース追加**:
    *   プログレッシブJPEGのデコードをテストする`TestDecodeProgressive`関数に、新しく追加された4:1:0および4:1:1形式のテスト画像が追加されました。
    *   `"../testdata/video-001.q50.410"` と `"../testdata/video-001.q50.411"` が追加されています。
    *   これにより、新しいサブサンプリング形式のプログレッシブJPEGが正しくデコードされることが保証されます。

### `src/image/jpeg/scan.go`

*   **`makeImg`関数での`subsampleRatio`設定の拡張**:
    *   `makeImg`関数は、デコードされたYCbCrデータからGoの`image.YCbCr`構造体を構築する際に、適切なクロマサブサンプリング比率を設定します。
    *   `switch`文に新しい`case`が追加されました。
        *   `case h0 == 4 && v0 == 1:` の場合、`subsampleRatio = image.YCbCrSubsampleRatio411` を設定します。
        *   `case h0 == 4 && v0 == 2:` の場合、`subsampleRatio = image.YCbCrSubsampleRatio410` を設定します。
    *   これにより、Goの`image`パッケージの他の部分が、これらの新しいサブサンプリング形式の画像を正しく処理できるようになります。
*   **`processSOS`関数内のブロック座標計算の汎用化**:
    *   `processSOS`関数は、JPEGのSOSマーカー（Start Of Scan）を解析し、実際の画像データ（スキャンデータ）を処理します。この中で、DCTブロックをデコードし、最終的なピクセルバッファに配置する際の座標計算が行われます。
    *   特に、色差成分（Cb, Cr）のブロックを配置する際の`bx`（ブロックのX座標）と`by`（ブロックのY座標）の計算ロジックが大幅に簡素化され、汎用化されました。
    *   変更前は、`h0`（輝度コンポーネントの水平サンプリング係数）が1の場合とそうでない場合で条件分岐があり、`j%2`や`j/2`といった特定のサブサンプリング比率に依存した計算が行われていました。
    *   変更後は、`bx = d.comp[compIndex].h*mx + j%h0` と `by = d.comp[compIndex].v*my + j/h0` という単一の式に統一されました。
        *   `d.comp[compIndex].h`と`d.comp[compIndex].v`は、現在のコンポーネントのサンプリング係数です。
        *   `mx`と`my`は、MCU（Minimum Coded Unit）のサイズに関連する係数です。
        *   `j`は、現在のMCU内のブロックのインデックスです。
        *   `j%h0`と`j/h0`は、現在のブロックがMCU内でどの位置にあるかを、コンポーネントの水平サンプリング係数`h0`に基づいて計算します。
    *   この汎用的な計算式により、4:1:1や4:1:0のように`h0`が4となる新しいサブサンプリング形式でも、色差ブロックの正しい配置が可能になります。これは、異なるサンプリング比率を持つブロックを統一的に処理するための重要な改善です。

## 変更の背景

JPEG画像は、色情報を効率的に圧縮するために「クロマサブサンプリング」という技術を使用します。これは、人間の目が輝度（明るさ）の変化には敏感である一方で、色（色相と彩度）の変化には比較的鈍感であるという特性を利用したものです。そのため、色情報を間引くことで、視覚的な品質を大きく損なうことなくファイルサイズを削減できます。

Goの`image/jpeg`パッケージは、これまで4:4:4（非サブサンプリング）、4:4:0、4:2:2、4:2:0といった一般的なクロマサブサンプリング形式をサポートしていました。しかし、4:1:1や4:1:0といった、より積極的に色情報を間引く形式はサポートされていませんでした。これらの形式は、特に帯域幅が限られた環境や、ファイルサイズを極限まで小さくしたい場合に利用されることがあります。

このサポートの欠如は、Goアプリケーションがこれらの形式のJPEG画像を処理しようとした際に、デコードエラーや不正な画像表示を引き起こす可能性がありました。このコミットは、このような互換性の問題を解消し、`image/jpeg`パッケージの堅牢性と汎用性を向上させることを目的としています。

## 前提知識の解説

### JPEGとYCbCr色空間

JPEG（Joint Photographic Experts Group）は、静止画像の圧縮方式の一つであり、特に写真のような自然画の圧縮に適しています。JPEGは通常、画像をRGB色空間からYCbCr色空間に変換して処理します。

*   **Y (Luma)**: 輝度成分。画像の明るさを表します。人間の目が最も敏感に感じる情報です。
*   **Cb (Chroma Blue)**: 青色差成分。青と黄色の間の色情報を表します。
*   **Cr (Chroma Red)**: 赤色差成分。赤とシアンの間の色情報を表します。

YCbCr色空間を使用することで、輝度と色度を分離して扱うことができ、色度情報を間引く「クロマサブサンプリング」が可能になります。

### クロマサブサンプリング

クロマサブサンプリングは、色度情報（CbとCr）を輝度情報（Y）よりも低い解像度で保存する技術です。これにより、ファイルサイズを削減できます。表記は通常「J:a:b」形式で表されます。

*   **J**: 輝度情報の水平サンプリング係数（通常4）。
*   **a**: 最初の行におけるCb/Crの水平サンプリング係数。
*   **b**: 2行目におけるCb/Crの水平サンプリング係数。

主要なクロマサブサンプリング形式は以下の通りです。

*   **4:4:4 (Full Sampling)**: CbとCrの解像度がYと同じ。色情報が完全に保持されるため、最高品質ですがファイルサイズは大きくなります。プロフェッショナルな用途や、色情報の損失が許されない場合に用いられます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり4サンプル
*   **4:2:2 (Horizontal Subsampling)**: CbとCrが水平方向に半分に間引かれます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり2サンプル
*   **4:2:0 (Horizontal and Vertical Subsampling)**: CbとCrが水平方向と垂直方向の両方で半分に間引かれます。最も一般的な形式で、ウェブ画像やデジタルカメラで広く使われています。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり1サンプル
*   **4:1:1 (More Horizontal Subsampling)**: CbとCrが水平方向に4分の1に間引かれます。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり1サンプル（水平方向で4分の1）
*   **4:1:0 (More Horizontal and Vertical Subsampling)**: CbとCrが水平方向に4分の1、垂直方向に半分に間引かれます。これは4:1:1よりもさらに色情報を間引く形式です。
    *   Y: 4x2ピクセルブロックあたり4サンプル
    *   Cb/Cr: 4x2ピクセルブロックあたり0.5サンプル（水平方向で4分の1、垂直方向で半分）

これらの形式は、輝度成分（Y）のサンプリングを基準として、色差成分（Cb, Cr）がどれだけ間引かれているかを示します。例えば、4:1:1は、4つの輝度サンプルに対して1つの色差サンプルが存在することを意味します。

### JPEGデコードのプロセス概要

JPEGデコードは、主に以下のステップで構成されます。

1.  **データ読み込みと解析**: JPEGファイルのヘッダ情報を読み込み、画像サイズ、コンポーネント数（Y, Cb, Crなど）、量子化テーブル、ハフマンテーブル、クロマサブサンプリング比などを解析します。
2.  **逆量子化**: 圧縮されたDCT係数を量子化テーブルを使って逆量子化し、元のDCT係数に戻します。
3.  **逆DCT (IDCT)**: DCT係数を空間ドメインのピクセルデータに変換します。
4.  **クロマアップサンプリング**: 間引かれた色差成分（Cb, Cr）を、輝度成分（Y）の解像度に合わせて補間します。このステップが、今回の変更の核心部分です。
5.  **YCbCrからRGBへの変換**: YCbCr色空間のピクセルデータを、表示に適したRGB色空間に変換します。

このコミットは、ステップ4のクロマアップサンプリングのロジックに、4:1:1と4:1:0の新しいサブサンプリング比率を認識させ、適切に処理できるようにするものです。

### `src/image/jpeg/reader.go`の変更

このファイルはJPEGデコーダの主要なロジックを含んでいます。特に、JPEGのフレームヘッダ（SOF: Start Of Frame）を処理する`processSOF`関数が変更されています。

`processSOF`関数は、各コンポーネント（Y, Cb, Cr）の水平サンプリング係数（h）と垂直サンプリング係数（v）を読み取ります。これまでの実装では、Yコンポーネントの`(h, v)`の組み合わせとして、`(1, 1)`, `(1, 2)`, `(2, 1)`, `(2, 2)`のみをサポートしていました。これらはそれぞれ、4:4:4, 4:4:0, 4:2:2, 4:2:0のサブサンプリング比率に対応します。

今回の変更では、Yコンポーネントの`(h, v)`の組み合わせに、新たに`(4, 1)`と`(4, 2)`が追加されました。

*   `(4, 1)`: これは4:1:1サブサンプリングに対応します。輝度情報が水平方向に4倍、垂直方向に1倍の解像度でサンプリングされ、色差情報が水平方向に1倍、垂直方向に1倍の解像度でサンプリングされることを意味します。全体として、輝度ブロック4x1に対して色差ブロック1x1となります。
*   `(4, 2)`: これは4:1:0サブサンプリングに対応します。輝度情報が水平方向に4倍、垂直方向に2倍の解像度でサンプリングされ、色差情報が水平方向に1倍、垂直方向に1倍の解像度でサンプリングされることを意味します。全体として、輝度ブロック4x2に対して色差ブロック1x1となります。

これらの新しい`(h, v)`値が`hv`変数（`h`と`v`をパックしたもの）に追加され、サポートされていない比率の場合に`UnsupportedError`を返すチェックロジックが更新されました。

また、以前のコードにあった`maxH = 2`と`maxV = 2`という定数が削除されています。これは、水平サンプリング係数が最大4になる新しいサブサンプリング形式をサポートするために、これらの制約が不要になったためです。

### `src/image/jpeg/scan.go`の変更

このファイルは、JPEGの走査（スキャン）処理、特にYCbCrからRGBへの変換や、クロマアップサンプリングに関連するロジックを含んでいます。

`makeImg`関数は、デコードされたYCbCrデータから最終的な`image.YCbCr`構造体を生成する際に、適切な`image.YCbCrSubsampleRatio`を設定します。この関数に、新しい`(h0, v0)`の組み合わせに対する`image.YCbCrSubsampleRatio411`と`image.YCbCrSubsampleRatio410`のケースが追加されました。

*   `h0 == 4 && v0 == 1`: `image.YCbCrSubsampleRatio411`が設定されます。
*   `h0 == 4 && v0 == 2`: `image.YCbCrSubsampleRatio410`が設定されます。

これにより、Goの`image`パッケージがこれらの新しいサブサンプリング比率を認識し、それに応じた内部処理（特にアップサンプリング）を行うことができるようになります。

さらに重要な変更は、`processSOS`関数内のブロック座標計算ロジックです。この関数は、スキャンデータからDCTブロックを読み取り、適切なピクセル位置に配置する役割を担っています。特に、色差成分のブロックを配置する際の座標計算が修正されました。

以前のコードでは、`bx`と`by`の計算が特定のサブサンプリング比率（主に4:2:0など）に特化しており、`h0`が1の場合とそうでない場合で異なるロジックを持っていました。新しいコードでは、`bx = d.comp[compIndex].h*mx + j%h0`と`by = d.comp[compIndex].v*my + j/h0`という汎用的な計算式に置き換えられました。

この変更は、異なる水平サンプリング係数（特に新しい`h0=4`の場合）を持つサブサンプリング形式でも、色差ブロックの正しいピクセル位置を計算できるようにするために不可欠です。`j%h0`と`j/h0`を使用することで、現在のブロック内のサブサンプルインデックス`j`とコンポーネントの水平サンプリング係数`h0`に基づいて、より柔軟かつ正確に座標を決定できるようになります。

*   **`processSOS`関数内のブロック座標計算の汎用化**:
    *   `processSOS`関数は、JPEGのSOSマーカー（Start Of Scan）を解析し、実際の画像データ（スキャンデータ）を処理します。この中で、DCTブロックをデコードし、最終的なピクセルバッファに配置する際の座標計算が行われます。
    *   特に、色差成分（Cb, Cr）のブロックを配置する際の`bx`（ブロックのX座標）と`by`（ブロックのY座標）の計算ロジックが大幅に簡素化され、汎用化されました。
    *   変更前は、`h0`（輝度コンポーネントの水平サンプリング係数）が1の場合とそうでない場合で条件分岐があり、`j%2`や`j/2`といった特定のサブサンプリング比率に依存した計算が行われていました。
    *   変更後は、`bx = d.comp[compIndex].h*mx + j%h0` と `by = d.comp[compIndex].v*my + j/h0` という単一の式に統一されました。
        *   `d.comp[compIndex].h`と`d.comp[compIndex].v`は、現在のコンポーネントのサンプリング係数です。
        *   `mx`と`my`は、MCU（Minimum Coded Unit）のサイズに関連する係数です。
        *   `j`は、現在のMCU内のブロックのインデックスです。
        *   `j%h0`と`j/h0`は、現在のブロックがMCU内でどの位置にあるかを、コンポーネントの水平サンプリング係数`h0`に基づいて計算します。
    *   この汎用的な計算式により、4:1:1や4:1:0のように`h0`が4となる新しいサブサンプリング形式でも、色差ブロックの正しい配置が可能になります。これは、異なるサンプリング比率を持つブロックを統一的に処理するための重要な改善です。

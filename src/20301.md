# [インデックス 20301] ファイルの概要

このコミットはGoランタイムの内部実装に関するもので、主に`src/pkg/runtime/proc.c`と`src/pkg/runtime/runtime.h`の2つのファイルが変更されています。

*   `src/pkg/runtime/proc.c`: Goランタイムのスケジューラの中核部分を実装しているファイルです。プロセッサ（P）、ゴルーチン（G）、マシン（M）の管理、スケジューリングロジックなどが含まれます。
*   `src/pkg/runtime/runtime.h`: Goランタイムの主要なデータ構造、定数、外部宣言などが定義されているヘッダーファイルです。

## コミット

Goランタイムにおいて、`allp`（すべてのプロセッサPを保持する配列）を動的に確保されたものから静的な配列に変更しました。これにより、Goからのアクセスがより簡潔になります。

## 変更の背景

この変更の背景には、Goランタイムの内部で`allp`というプロセッサ（P）のポインタを保持する配列が、実質的に固定サイズで運用されていたという事実があります。以前は動的にメモリが確保されていましたが、`GOMAXPROCS`の最大値（`MaxGomaxprocs`）によってそのサイズが実質的に制限されていました。

コミットメッセージにある「It is anyway, just an allocated one. Giving it a sized type makes Go access nicer.」という記述は、以下の意図を示唆しています。

1.  **実質的な固定サイズ運用**: `allp`は`GOMAXPROCS`の最大値に基づいてサイズが決定されており、実行中にそのサイズが大きく変動することは想定されていませんでした。そのため、動的なメモリ確保（`mallocgc`）を行う必要性が薄かったと考えられます。
2.  **アクセス性の向上**: 静的配列として宣言することで、コンパイラが配列のサイズを事前に把握できるようになり、Goコードからのアクセス（特にポインタのデリファレンスやインデックスアクセス）がより直接的かつ効率的になる可能性があります。これにより、コードの可読性や保守性も向上します。
3.  **メモリ管理の簡素化**: 動的なメモリ確保が不要になることで、ランタイム起動時の初期化処理が簡素化され、ガベージコレクションのオーバーヘッドもわずかながら削減される可能性があります。`allp`のようなランタイムの中核的なデータ構造のメモリ管理を静的にすることで、より予測可能な動作が期待できます。

この変更は、Goランタイムの内部最適化とコードのクリーンアップの一環として行われたと考えられます。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ、メモリ管理、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、Goランタイム上で動作します。ランタイムは、ゴルーチン（軽量スレッド）のスケジューリング、チャネル通信、メモリ割り当てと解放など、Go言語の並行処理モデルとメモリモデルを支える重要な役割を担っています。

### P (Processor)

Goランタイムのスケジューラにおける「P」（Processor）は、論理的なプロセッサを表します。これは、Goのゴルーチンを実行するためのコンテキストを提供します。Pは、M（Machine、OSスレッド）とG（Goroutine）の間に位置し、MがGを実行するために必要なリソース（例えば、ローカルな実行キュー、メモリキャッシュなど）を管理します。`GOMAXPROCS`の値は、同時に実行できるPの数を決定します。

### GOMAXPROCS

`GOMAXPROCS`は、Goプログラムが同時に利用できるOSスレッド（M）の最大数を制御する環境変数またはランタイム関数です。これは、Goスケジューラが同時に実行できるPの数を設定します。例えば、`GOMAXPROCS=4`と設定すると、Goランタイムは最大4つのOSスレッドを使用してGoコードを並行して実行します。この値は、CPUコア数に合わせて設定されることが推奨されます。

### `runtime·allp`

`runtime·allp`は、Goランタイムが管理するすべてのP（プロセッサ）のポインタを格納する配列です。Goスケジューラは、この配列を通じて利用可能なPを管理し、ゴルーチンをPにディスパッチして実行します。この配列のサイズは、`GOMAXPROCS`の最大値によって決定されます。

### 静的配列と動的配列 (Static vs. Dynamic Arrays)

*   **静的配列**: コンパイル時にサイズが決定され、そのサイズが固定されている配列です。メモリはプログラムの実行開始時（またはコンパイル時）に割り当てられます。スタックまたはデータセグメントに配置されることが多いです。アクセスが高速で、メモリ管理のオーバーヘッドがありません。
*   **動的配列**: 実行時にサイズが決定され、必要に応じてメモリが確保される配列です。メモリはヒープに割り当てられ、プログラムの実行中にサイズを変更できる場合があります。メモリの確保と解放にはオーバーヘッドが伴います。Goでは、スライスが動的配列に似た機能を提供しますが、内部的には配列へのポインタと長さ、容量を保持しています。

### `mallocgc`

`mallocgc`は、Goランタイムの内部で使用されるメモリ割り当て関数の一つで、ガベージコレクタによって管理されるヒープメモリからメモリを割り当てます。Goプログラムが新しいオブジェクトを作成する際に、この関数（または関連する低レベルの関数）が呼び出され、メモリが確保されます。割り当てられたメモリは、不要になった際にガベージコレクタによって自動的に解放されます。

## 技術的詳細

このコミットの核心は、Goランタイムのスケジューラが使用する`runtime·allp`配列のメモリ管理方法の変更です。

以前のバージョンでは、`runtime·allp`は`P**`として宣言されており、これは`P`構造体へのポインタのポインタ、つまり`P`へのポインタの配列を指すポインタでした。この宣言は、`allp`が動的にメモリを割り当てられることを示唆しています。実際に、`runtime·schedinit`関数内で`runtime·mallocgc`を使用してメモリが割り当てられていました。

```c
// 変更前 (proc.c)
runtime·allp = runtime·mallocgc((MaxGomaxprocs+1)*sizeof(runtime·allp[0]), nil, 0);
```

このコミットでは、`runtime·allp`の宣言が`P* runtime·allp[MaxGomaxprocs+1];`に変更されました。これは、`runtime·allp`が`MaxGomaxprocs+1`個の`P`へのポインタを格納できる静的配列であることを意味します。`MaxGomaxprocs`は`1<<8`（256）と定義されているため、この配列は257個の`P*`を保持できます。

この変更の技術的な影響は以下の通りです。

1.  **メモリ割り当ての変更**: `runtime·allp`のメモリは、プログラムの起動時（またはコンパイル時）に静的に割り当てられるようになります。これにより、`runtime·schedinit`関数内の`runtime·mallocgc`による動的なメモリ割り当てが不要になります。
2.  **アクセス効率の向上**: 静的配列は、そのサイズがコンパイル時に既知であるため、コンパイラはより最適化されたコードを生成できます。これにより、`allp`へのアクセス（例えば、`allp[i]`のようなインデックスアクセス）が、ポインタのデリファレンスを介する動的配列よりも直接的かつ高速になる可能性があります。キャッシュの局所性も向上する可能性があります。
3.  **コードの簡素化**: `mallocgc`の呼び出しが削除され、`allp`の型がより具体的な静的配列になったことで、関連するコードの記述が簡潔になります。
4.  **`MaxGomaxprocs`の移動**: `MaxGomaxprocs`の定義が`proc.c`から`runtime.h`に移動されました。これは、`MaxGomaxprocs`が`allp`のサイズを決定する重要な定数であり、ランタイム全体で共有されるべき情報であることを明確にするためです。`runtime.h`はランタイムのグローバルな定義を置く場所として適切です。

この変更は、Goランタイムの起動時のオーバーヘッドをわずかに削減し、`allp`へのアクセスを最適化することで、全体的なパフォーマンスと安定性に寄与することを目的としています。`GOMAXPROCS`の最大値が固定されているという前提に基づいた、堅実な最適化と言えます。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c`の変更点

1.  **`MaxGomaxprocs`の定義削除**:
    `proc.c`ファイルから`MaxGomaxprocs = 1<<8,`の定義が削除されました。これは、この定数が`runtime.h`に移動されたためです。これにより、`MaxGomaxprocs`がランタイム全体で共有されるグローバルな定数であることが明確になります。

2.  **`runtime·allp`の宣言変更**:
    `M* runtime·extram;`の後に、`P* runtime·allp[MaxGomaxprocs+1];`という行が追加されました。これは、`runtime·allp`が`P`へのポインタの静的配列として宣言されたことを意味します。以前は`runtime.h`で`extern P** runtime·allp;`として宣言され、動的にメモリが割り当てられていました。この変更により、`allp`のメモリはコンパイル時に（またはプログラムのデータセグメントに）静的に確保されるようになります。

3.  **`runtime·mallocgc`呼び出しの削除**:
    `runtime·schedinit`関数内で、`runtime·allp = runtime·mallocgc((MaxGomaxprocs+1)*sizeof(runtime·allp[0]), nil, 0);`という行が削除されました。`allp`が静的配列になったため、実行時に`mallocgc`を使ってメモリを動的に割り当てる必要がなくなったためです。これにより、ランタイムの初期化プロセスが簡素化されます。

### `src/pkg/runtime/runtime.h`の変更点

1.  **`MaxGomaxprocs`の定義追加**:
    `struct P`の定義の後に、`MaxGomaxprocs = 1<<8,`という`enum`ブロックが追加されました。これにより、`MaxGomaxprocs`がランタイム全体で利用可能なグローバルな定数として定義されます。この値は、`GOMAXPROCS`の最大値を256に設定します。

2.  **`runtime·allp`の宣言変更**:
    `extern P** runtime·allp;`という宣言が`extern P* runtime·allp[MaxGomaxprocs+1];`に変更されました。これは、`runtime·allp`が`MaxGomaxprocs+1`個の`P`へのポインタを格納する静的配列であることを外部に宣言しています。この変更により、コンパイラは`allp`のサイズを事前に把握し、より効率的なコードを生成できるようになります。

これらの変更は、`allp`のメモリ管理を動的なものから静的なものへと移行させ、ランタイムの初期化と`P`へのアクセスを最適化することを目的としています。

1.  **メモリ割り当ての変更**: `runtime·allp`のメモリは、プログラムの起動時（またはコンパイル時）に静的に割り当てられるようになります。これにより、`runtime·schedinit`関数内の`runtime·mallocgc`による動的なメモリ割り当てが不要になります。
2.  **アクセス効率の向上**: 静的配列は、そのサイズがコンパイル時に既知であるため、コンパイラはより最適化されたコードを生成できます。これにより、`allp`へのアクセス（例えば、`allp[i]`のようなインデックスアクセス）が、ポインタのデリファレンスを介する動的配列よりも直接的かつ高速になる可能性があります。キャッシュの局所性も向上する可能性があります。
3.  **コードの簡素化**: `mallocgc`の呼び出しが削除され、`allp`の型がより具体的な静的配列になったことで、関連するコードの記述が簡潔になります。
4.  **`MaxGomaxprocs`の移動**: `MaxGomaxprocs`の定義が`proc.c`から`runtime.h`に移動されました。これは、`MaxGomaxprocs`が`allp`のサイズを決定する重要な定数であり、ランタイム全体で共有されるべき情報であることを明確にするためです。`runtime.h`はランタイムのグローバルな定義を置く場所として適切です。

この変更は、Goランタイムの起動時のオーバーヘッドをわずかに削減し、`allp`へのアクセスを最適化することで、全体的なパフォーマンスと安定性に寄与することを目的としています。`GOMAXPROCS`の最大値が固定されているという前提に基づいた、堅実な最適化と言えます。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c`の変更点

1.  **`MaxGomaxprocs`の定義削除**:
    `proc.c`ファイルから`MaxGomaxprocs = 1<<8,`の定義が削除されました。これは、この定数が`runtime.h`に移動されたためです。これにより、`MaxGomaxprocs`がランタイム全体で共有されるグローバルな定数であることが明確になります。

2.  **`runtime·allp`の宣言変更**:
    `M* runtime·extram;`の後に、`P* runtime·allp[MaxGomaxprocs+1];`という行が追加されました。これは、`runtime·allp`が`P`へのポインタの静的配列として宣言されたことを意味します。以前は`runtime.h`で`extern P** runtime·allp;`として宣言され、動的にメモリが割り当てられていました。この変更により、`allp`のメモリはコンパイル時に（またはプログラムのデータセグメントに）静的に確保されるようになります。

3.  **`runtime·mallocgc`呼び出しの削除**:
    `runtime·schedinit`関数内で、`runtime·allp = runtime·mallocgc((MaxGomaxprocs+1)*sizeof(runtime·allp[0]), nil, 0);`という行が削除されました。`allp`が静的配列になったため、実行時に`mallocgc`を使ってメモリを動的に割り当てる必要がなくなったためです。これにより、ランタイムの初期化プロセスが簡素化されます。

### `src/pkg/runtime/runtime.h`の変更点

1.  **`MaxGomaxprocs`の定義追加**:
    `struct P`の定義の後に、`MaxGomaxprocs = 1<<8,`という`enum`ブロックが追加されました。これにより、`MaxGomaxprocs`がランタイム全体で利用可能なグローバルな定数として定義されます。この値は、`GOMAXPROCS`の最大値を256に設定します。

2.  **`runtime·allp`の宣言変更**:
    `extern P** runtime·allp;`という宣言が`extern P* runtime·allp[MaxGomaxprocs+1];`に変更されました。これは、`runtime·allp`が`MaxGomaxprocs+1`個の`P`へのポインタを格納する静的配列であることを外部に宣言しています。この変更により、コンパイラは`allp`のサイズを事前に把握し、より効率的なコードを生成できるようになります。

これらの変更は、`allp`のメモリ管理を動的なものから静的なものへと移行させ、ランタイムの初期化と`P`へのアクセスを最適化することを目的としています。

## 変更の背景

このコミットは、Goの `net/http` パッケージにおける `http.TimeoutHandler` の深刻なバグを修正するために行われました。元の実装では、`TimeoutHandler` が作成される際にタイマーが初期化されていました。これは、HTTPハンドラが一度作成されると、そのハンドラが処理するすべてのリクエストに対して同じタイマーインスタンスが共有されることを意味します。

しかし、HTTPリクエストはそれぞれ異なるタイミングで開始され、異なる処理時間を持ちます。もしタイマーが共有されていると、最初のリクエストが開始された時点でタイマーが動き出し、後続のリクエストが開始される前にタイマーが期限切れになってしまう可能性がありました。これにより、まだ処理を開始していない、あるいは処理中のリクエストが不当にタイムアウトとして扱われるという誤った挙動が発生していました。

この問題は、GitHub Issue #14568 で報告されており、このコミットはその問題を解決することを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の概念と `net/http` パッケージの基本的な知識が必要です。

1.  **`net/http` パッケージ**: Go言語でHTTPクライアントおよびサーバーを構築するための標準ライブラリです。
    *   **`http.Handler` インターフェース**: `ServeHTTP(ResponseWriter, *Request)` メソッドを持つインターフェースで、HTTPリクエストを処理するすべてのオブジェクトが実装します。
    *   **`http.ResponseWriter`**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。
    *   **`http.Request`**: クライアントからのHTTPリクエストを表す構造体です。
    *   **`http.TimeoutHandler`**: 指定された時間内に完了しないHTTPリクエストをタイムアウトさせるためのハンドララッパーです。タイムアウトが発生した場合、`http.StatusServiceUnavailable` (503) ステータスコードと指定されたメッセージを返します。

2.  **`time` パッケージ**: 時間の測定と操作のための標準ライブラリです。
    *   **`time.Duration`**: 時間の長さを表す型です（例: `300 * time.Millisecond`）。
    *   **`time.NewTimer(d time.Duration)`**: 指定された期間 `d` が経過した後に、単一のイベントを送信する `*time.Timer` を作成します。
    *   **`*time.Timer.C`**: `time.NewTimer` によって返される `*time.Timer` 構造体には、`C` という名前の読み取り専用チャネルが含まれています。このチャネルは、タイマーが期限切れになると現在の時刻を送信します。
    *   **`*time.Timer.Stop()`**: タイマーがまだ期限切れになっていない場合、タイマーを停止し、`C` チャネルへの値の送信を防ぎます。タイマーが停止されたか、すでに期限切れになっていた場合は `true` を返します。

3.  **Goの並行処理**:
    *   **Goroutine**: Goランタイムによって管理される軽量なスレッドです。
    *   **Channel**: Goroutine間で値を安全に送受信するための通信メカニズムです。
    *   **`select` ステートメント**: 複数のチャネル操作を待機し、準備ができた最初の操作を実行します。このコミットでは、リクエストの完了とタイマーの期限切れのどちらが先に発生するかを待機するために使用されます。

## 技術的詳細

このコミットの核心は、`http.TimeoutHandler` がタイマーをどのように管理するかという点にあります。

**元の実装の問題点**:
`http.TimeoutHandler` 関数は、ハンドラをラップする `timeoutHandler` 構造体を返します。元の実装では、この `TimeoutHandler` 関数内で `time.NewTimer(dt)` が一度だけ呼び出され、その結果得られる `*time.Timer` のチャネル (`t.C`) と `Stop` メソッドが `timeoutHandler` 構造体のフィールドとして保存されていました。

```go
// 変更前のTimeoutHandler関数の一部
func TimeoutHandler(h Handler, dt time.Duration, msg string) Handler {
	t := time.NewTimer(dt) // ここでタイマーが一度だけ作成される
	return &timeoutHandler{
		handler: h,
		body:    msg,
		timeout:     func() <-chan time.Time { return t.C }, // t.Cが共有される
		cancelTimer: t.Stop,
	}
}
```
この設計では、`TimeoutHandler` が作成された瞬間にタイマーが開始され、そのタイマーがすべてのリクエストで共有されていました。これは、複数のリクエストが異なるタイミングで到着し、それぞれ独立したタイムアウト期間を持つべきであるという `TimeoutHandler` の意図に反していました。結果として、最初のリクエストが処理されている間にタイマーが期限切れになり、後続のリクエストが不当にタイムアウトとして扱われる可能性がありました。

**修正後の実装**:
このコミットでは、この問題を解決するために以下の変更が加えられました。

1.  **タイマーの遅延初期化**: `TimeoutHandler` 関数内では `time.NewTimer` を呼び出さず、タイムアウト期間 `dt` のみ `timeoutHandler` 構造体に保存するように変更されました。
    ```go
    // 変更後のTimeoutHandler関数の一部
    func TimeoutHandler(h Handler, dt time.Duration, msg string) Handler {
    	return &timeoutHandler{
    		handler: h,
    		body:    msg,
    		dt:      dt, // タイムアウト期間のみを保存
    	}
    }
    ```
2.  **リクエストごとのタイマー作成**: `timeoutHandler` の `ServeHTTP` メソッドが呼び出されるたびに、つまり**各HTTPリクエストが処理される直前に**、新しい `time.NewTimer(h.dt)` が作成されるようになりました。これにより、各リクエストは独自の独立したタイマーを持つことが保証されます。
    ```go
    // 変更後のServeHTTPメソッドの一部
    func (h *timeoutHandler) ServeHTTP(w ResponseWriter, r *Request) {
    	var t *time.Timer
    	timeout := h.testTimeout // テスト用のチャネルがあればそれを使用
    	if timeout == nil {
    		t = time.NewTimer(h.dt) // リクエストごとに新しいタイマーを作成
    		timeout = t.C
    	}
    	// ...
    }
    ```
3.  **タイマーの停止**: リクエストの処理がタイムアウトする前に完了した場合、作成されたタイマーは `t.Stop()` を呼び出すことで停止されます。これにより、タイマーチャネルへの不要な送信を防ぎ、リソースリークを回避します。
    ```go
    // 変更後のServeHTTPメソッドの一部 (select文内)
    case <-done: // リクエストが完了した場合
    	// ...
    	if t != nil {
    		t.Stop() // タイマーを停止
    	}
    // ...
    ```
4.  **テスト用フックの簡素化**: テストを容易にするために、`timeoutHandler` 構造体に `testTimeout <-chan time.Time` フィールドが追加されました。これにより、テストコードは実際の `time.Timer` を使用する代わりに、このチャネルを介してタイムアウトイベントをシミュレートできるようになり、テストの制御が容易になりました。

これらの変更により、`TimeoutHandler` は各リクエストに対して正しく独立したタイムアウト処理を提供するようになり、元のバグが修正されました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/net/http/server.go` 内の `TimeoutHandler` 関数と `timeoutHandler.ServeHTTP` メソッドにあります。

1.  **`TimeoutHandler` 関数の変更**:
    *   以前は、`TimeoutHandler` が呼び出された時点で `time.NewTimer(dt)` を使ってタイマーを作成し、そのタイマーのチャネル (`t.C`) と停止関数 (`t.Stop`) を `timeoutHandler` 構造体に保存していました。
    *   修正後は、`time.NewTimer` の呼び出しが削除され、代わりにタイムアウト期間 `dt` そのものが `timeoutHandler` 構造体の新しいフィールド `dt` に保存されるようになりました。これにより、タイマーの作成が遅延され、リクエスト処理時まで行われないようになります。

2.  **`timeoutHandler` 構造体の変更**:
    *   `timeout func() <-chan time.Time` と `cancelTimer func() bool` のフィールドが削除されました。これらは、共有タイマーのチャネルと停止関数を保持するためのものでした。
    *   `dt time.Duration` フィールドが追加され、各リクエストのタイムアウト期間を保持します。
    *   `testTimeout <-chan time.Time` フィールドが追加されました。これはテスト専用のフックであり、テスト時に実際のタイマーの代わりにカスタムチャネルを使用してタイムアウトイベントをシミュレートすることを可能にします。これにより、テストの信頼性と制御性が向上します。

3.  **`timeoutHandler.ServeHTTP` メソッドの変更**:
    *   このメソッドは、各HTTPリクエストが到着したときに呼び出されます。
    *   メソッドの冒頭で、`testTimeout` フィールドが `nil` でない（つまりテストモードである）場合は、そのチャネルを `timeout` 変数に割り当てます。
    *   `testTimeout` が `nil` の場合（通常の運用時）、`time.NewTimer(h.dt)` を呼び出して**新しいタイマー**を作成し、そのチャネル (`t.C`) を `timeout` 変数に割り当てます。これにより、リクエストごとに独立したタイマーが保証されます。
    *   `select` ステートメント内で、以前は `<-h.timeout()` を待機していましたが、これは `<-timeout` に変更されました。これにより、リクエスト固有のタイマーチャネル、またはテスト用のチャネルのいずれかを待機するようになります。
    *   リクエストがタイムアウトする前に正常に完了した場合 (`case <-done:`)、`t != nil` のチェックが追加され、実際のタイマーが作成されていた場合にのみ `t.Stop()` が呼び出されます。これは、タイマーが期限切れになる前に停止することで、リソースリークを防ぎ、ガベージコレクションを助けるための重要なステップです。

これらの変更により、`TimeoutHandler` は各リクエストに対して独立したタイムアウトメカニズムを提供し、複数のリクエストが同時に処理される環境でも正しく機能するようになりました。

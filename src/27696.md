# [インデックス 27696] ファイルの概要

このコミットは、Goランタイムのトレース機能において、スタックトレースのファイル名と行番号の情報をトレースデータ自体に直接埋め込むように変更するものです。これにより、トレースが自己完結型となり、特にクラウド環境のような現代的な分散システムでのトレース解析ワークフローが大幅に簡素化されます。

## 変更の背景

Goのトレースツールは、Goプログラムの実行中のイベント（スケジューリング、GC、システムコールなど）を記録し、そのパフォーマンス特性や並行処理の問題を視覚的に分析するために使用されます。従来のGoトレースでは、スタックトレース情報はプログラムカウンタ（PC）のリストとして記録されていました。これらのPCアドレスを人間が読める関数名、ファイル名、行番号に変換する「シンボル化」のプロセスは、トレース解析時に別途実行する必要がありました。

このシンボル化は、`go tool addr2line`のようなツールを使用して、トレース対象のGoバイナリファイルからデバッグ情報を読み取ることで行われていました。しかし、このアプローチにはいくつかの課題がありました。

1.  **バイナリへのアクセス要件**: トレースを解析するマシンが、トレースが生成されたGoバイナリにアクセスできる必要がありました。これは、特にクラウド環境やコンテナ化された環境でサービスがデプロイされている場合、バイナリを解析マシンに転送したり、解析マシンからサービスにアクセスしてバイナリを取得したりする手間が発生し、ワークフローを複雑にしていました。
2.  **環境の不一致**: トレースが生成された環境と解析される環境で、バイナリやデバッグ情報のバージョンが異なる場合、シンボル化が正しく行われない可能性がありました。
3.  **ワークフローの複雑化**: トレースの取得、バイナリの取得、シンボル化、解析という複数のステップが必要となり、特に自動化されたシステムやCI/CDパイプラインに組み込む際にオーバーヘッドがありました。

このコミットは、これらの課題を解決するために、シンボル化に必要なファイル名と行番号の情報をトレースデータ自体に直接埋め込むことを目的としています。これにより、トレースファイルが自己完結型となり、バイナリへの依存なしにどこでも解析できるようになります。

## 前提知識の解説

### Goトレースの仕組み

Goトレースは、Goランタイムが生成するバイナリ形式のイベントログです。このログには、ゴルーチンの生成・終了、スケジューリング、ガベージコレクション、システムコールなどの様々なイベントが含まれます。各イベントにはタイムスタンプや関連するゴルーチンIDなどの情報が付随し、一部のイベントにはスタックトレースが含まれます。

### プログラムカウンタ (PC)

プログラムカウンタ（PC）は、CPUが次に実行する命令のアドレスを指すレジスタです。Goのスタックトレースでは、各スタックフレームが呼び出し元の関数のPC（リターンアドレス）として表現されます。

### シンボル化

シンボル化とは、プログラムカウンタのような数値アドレスを、対応するソースコードの関数名、ファイル名、行番号に変換するプロセスです。これは、デバッグ情報（DWARFなど）を含む実行可能バイナリを解析することで実現されます。Goでは、`go tool addr2line`がこの役割を担っていました。

### `go tool addr2line`

`go tool addr2line`は、Goのツールチェインに含まれるコマンドラインツールで、指定されたGoバイナリとPCアドレスのリストを受け取り、それに対応する関数名、ファイル名、行番号を出力します。

### GoランタイムにおけるスタックトレースとPCの扱い

Goランタイムは、スタックトレースを生成する際に、各関数の呼び出し元のアドレス（リターンPC）を記録します。`runtime.Func.FileLine(pc)`のような関数は、このリターンPCを受け取り、対応するファイル名と行番号を返します。PCは通常、命令の開始アドレスを指しますが、Goの`funcline`関数は、PCから`sys.PCQuantum`を引いたアドレスを渡すことで、より正確な行情報を取得することがあります。これは、Goコンパイラが生成するコードの特性や、PCが指すアドレスが命令のどの部分に対応するかといった低レベルな詳細に起因します。

### `sys.PCQuantum`

`sys.PCQuantum`は、Goランタイム内部で使用される定数で、プログラムカウンタの最小単位を表します。x86アーキテクチャでは通常1、それ以外の多くのシステムでは4です。Goランタイムは、PC値を`PCQuantum`で割った値として内部的に格納することで、デバッグ情報のサイズを最適化しています。`funcline`関数がPCから`sys.PCQuantum`を引くのは、PCが指すアドレスが呼び出し命令の直後である場合、その命令自体ではなく、呼び出し元の命令の行情報を正確に取得するための一種のオフセット調整です。

## 技術的詳細

このコミットの核心は、トレースデータにファイル名と行番号を直接埋め込むための新しいメカニズムの導入です。

1.  **トレースフォーマットの変更**:
    *   `EvStack`イベントのフォーマットが変更されました。従来の`[stack id, number of PCs, array of PCs]`から、`[stack id, number of PCs, array of {PC, func string ID, file string ID, line}]`へと拡張されました。これにより、各スタックフレームはPCだけでなく、関数名、ファイル名、行番号の情報を直接持つことになります。
    *   新しいイベントタイプ`EvString`が導入されました。これは`[ID, length, string]`というフォーマットを持ち、トレース内で使用される文字列（関数名やファイル名など）を辞書形式で格納するために使われます。これにより、同じ文字列が複数回出現する場合でも、IDを記録するだけで済み、トレースファイルのサイズを効率的に保つことができます。

2.  **文字列辞書の実装**:
    *   `src/runtime/trace.go`内の`trace`構造体に、`strings map[string]uint64`と`stringSeq uint64`が追加されました。`strings`マップは、文字列とその一意のIDをマッピングし、`stringSeq`は新しい文字列IDを生成するためのカウンタです。
    *   `traceString(buf *traceBuf, s string) (uint64, *traceBuf)`関数が追加されました。この関数は、与えられた文字列`s`が既に辞書に存在すればそのIDを返し、存在しなければ新しいIDを割り当てて辞書に追加し、`EvString`イベントとしてトレースバッファに書き込みます。

3.  **スタックフレーム情報の取得と埋め込み**:
    *   `src/runtime/trace.go`に`traceFrame`構造体が導入され、`funcID`, `fileID`, `line`を保持します。
    *   `traceFrameForPC(buf *traceBuf, frames map[uintptr]traceFrame, pc uintptr) (traceFrame, *traceBuf)`関数が追加されました。この関数は、与えられたPCから`runtime.findfunc`と`runtime.funcline`を使用して関数名、ファイル名、行番号を取得します。取得した関数名とファイル名は`traceString`関数を使って文字列IDに変換され、`traceFrame`構造体に格納されます。これにより、PCからシンボル情報を取得し、それを文字列IDとしてトレースに埋め込む準備が整います。
    *   `traceStackTable.dump()`関数が大幅に修正されました。この関数は、キャッシュされたスタックトレースをトレースバッファに書き出す役割を担っています。変更後、各PCに対して`traceFrameForPC`を呼び出し、PC、関数名ID、ファイル名ID、行番号を`EvStack`イベントの一部として書き込むようになりました。

4.  **シンボル化処理の削除**:
    *   `src/cmd/trace/main.go`から、トレース解析時に`trace.Symbolize`を呼び出す部分が削除されました。これは、シンボル情報が既にトレースデータに含まれているため、外部ツールによるシンボル化が不要になったことを意味します。
    *   `src/internal/trace/parser.go`からも`Symbolize`関数が完全に削除されました。

5.  **`traceGoCreate`の変更**:
    *   `traceGoCreate`関数は、新しいゴルーチンが作成された際に、その開始PCを直接記録する代わりに、`trace.stackTab.put([]uintptr{pc + sys.PCQuantum})`を呼び出してスタックIDを記録するように変更されました。ここで`pc + sys.PCQuantum`が使われているのは、`funcline`がリターンPCを期待するため、呼び出し元のPCを調整して渡す必要があるためです。

これらの変更により、Goトレースファイルは、解析時に外部のGoバイナリや`addr2line`ツールを必要とせず、それ自体で完全なスタックトレース情報（関数名、ファイル名、行番号）を提供できるようになりました。

## コアとなるコードの解説

### `src/internal/trace/parser.go`の変更

*   `readTrace`関数は、トレースファイルを読み込む際に、従来のイベントデータに加えて、新しく導入された`EvString`イベントから文字列辞書（`map[uint64]string`）を構築するようになりました。これにより、トレースファイル内の文字列IDを実際の文字列に解決できるようになります。
*   `parseEvents`関数は、この文字列辞書を受け取るようになり、`EvStack`イベントを解析する際に、PCだけでなく、埋め込まれた関数名ID、ファイル名ID、行番号を読み取り、それらを文字列辞書を使って実際の関数名とファイル名に変換して`Frame`構造体に格納します。
*   `Symbolize`関数が削除されたことで、トレース解析時に外部の`addr2line`ツールを呼び出す必要がなくなりました。

### `src/runtime/trace.go`の変更

*   **`trace`構造体の拡張**: `trace`構造体に`strings`マップと`stringSeq`カウンタが追加され、ランタイム内で文字列辞書を管理するようになりました。
*   **`traceString`関数の導入**: この関数は、任意の文字列（関数名やファイル名など）を受け取り、それが既に辞書に存在すればそのIDを返します。存在しなければ、新しいIDを割り当てて辞書に追加し、その文字列とIDを`traceEvString`イベントとしてトレースバッファに書き込みます。これにより、トレースファイル内で文字列が重複して記録されるのを防ぎ、効率的に情報を格納できます。
*   **`traceFrame`構造体と`traceFrameForPC`関数の導入**: `traceFrame`は、関数名ID、ファイル名ID、行番号を保持する新しい構造体です。`traceFrameForPC`関数は、与えられたPCから`runtime.findfunc`と`runtime.funcline`を使って関数名、ファイル名、行番号を取得し、それらを`traceString`関数で文字列IDに変換して`traceFrame`を構築します。この関数は、PCからシンボル情報を取得し、それをトレースに埋め込むための中心的な役割を担います。`pc-sys.PCQuantum`というオフセットが使われているのは、`funcline`がリターンPCを期待するため、呼び出し元のPCを調整して渡すことで正確な行情報を得るためです。
*   **`traceStackTable.dump()`の変更**: この関数は、スタックトレースをトレースバッファに書き出す際に、各スタックフレームのPCに対して`traceFrameForPC`を呼び出し、PC、関数名ID、ファイル名ID、行番号を`EvStack`イベントとしてまとめて書き込むようになりました。
*   **`traceGoCreate`の変更**: ゴルーチン作成イベントで、開始PCを直接記録する代わりに、`trace.stackTab.put`を使ってスタックIDを記録するように変更されました。これにより、ゴルーチン作成時のスタックトレースも、新しいフォーマットで記録されるようになります。

これらの変更により、Goランタイムはトレース生成時にシンボル情報を直接トレースファイルに埋め込むようになり、トレースファイルが自己完結型で、外部ツールなしに解析可能になりました。

# [インデックス 24496] ファイルの概要

このコミットは、GoコンパイラのARMアーキテクチャ向けバックエンドにおいて、Native Client (NaCl) 環境での大きなスタックオフセットを持つメモリ参照の処理に関するバグを修正します。具体的には、これまで大きなオフセットを持つ非スタック参照に対して適用されていた修正ロジックを、スタック参照にも適用するように変更することで、最新のNaCl環境で発生する可能性のあるコード検証エラーを回避します。

## 変更の背景

この変更の背景には、Goコンパイラが生成するARMアーキテクチャ向けNative Client (NaCl) バイナリが、最新のNaCl環境で実行時に問題を引き起こす可能性があったという事情があります。

GoコンパイラのARMバックエンドでは、メモリへのアクセス（ロード/ストア）において、ベースレジスタからのオフセット値が大きすぎる場合に、それを複数の命令に分割して処理するロジックが実装されていました。これは、ARM命令セットが直接扱えるオフセット値に制限があるためです。しかし、このロジックはスタックポインタ (SP, `REG_R13`) をベースとするメモリ参照（すなわちスタック上の変数へのアクセス）を明示的に除外していました。

以前のNaClのバージョンでは、このようなスタック参照の扱いが許容されていた可能性があります。しかし、NaClのセキュリティモデルは非常に厳格であり、時間の経過とともにその検証ルールは強化されていきます。最新のNaCl環境では、大きなオフセットを持つスタック参照が、そのセキュリティポリシーに違反すると見なされ、コード検証フェーズで拒否されるようになったと考えられます。

このコミットは、この新しいNaClの制約に対応するために行われました。スタック参照を特別扱いせず、他のメモリ参照と同様に、大きなオフセットを適切に処理するロジックを適用することで、NaClのコード検証をパスし、GoプログラムがNaCl環境で正しく動作するようにすることが目的です。コミットメッセージにある「For #11956 but probably not the last problem.」という記述は、この問題が特定のバグ報告（Issue 11956）に対応するものであること、そしてNaCl環境におけるGoの互換性には今後も課題が生じる可能性があることを示唆しています。（注: Issue 11956の公開情報は確認できませんでした。）

## 前提知識の解説

### Goコンパイラのバックエンド (`cmd/internal/obj/arm`)

Go言語のコンパイラは、ソースコードを中間表現に変換した後、最終的にターゲットアーキテクチャ（x86, ARMなど）の機械語に変換します。この機械語生成を担当する部分が「バックエンド」と呼ばれます。`cmd/internal/obj/arm`は、Goコンパイラの内部パッケージであり、ARMアーキテクチャ向けのアセンブリコード生成とオブジェクトファイル生成に関連する処理を担っています。ここで定義されるルールや最適化が、最終的なバイナリの動作に直接影響します。

### ARMアーキテクチャのレジスタとメモリ参照

ARMアーキテクチャは、ロード/ストアアーキテクチャであり、データ操作はレジスタ間で行われ、メモリとのやり取りは専用のロード（LDR）およびストア（STR）命令を介して行われます。

*   **レジスタ**: ARMプロセッサには汎用レジスタ（R0-R12）、スタックポインタ（SP, R13）、リンクレジスタ（LR, R14）、プログラムカウンタ（PC, R15）などがあります。
    *   **`REG_R13` (SP - Stack Pointer)**: 現在のスタックフレームの最上位を指すレジスタです。関数呼び出し時のローカル変数や引数、戻りアドレスなどがスタックに格納され、SPからの相対アドレスでアクセスされます。
    *   **`REG_R9` (SB - Static Base)**: Goランタイムでは、`R9`レジスタが「Static Base」として使用されることがあります。これは、グローバル変数やパッケージレベルのデータへのアクセスを効率化するためのベースレジスタとして機能します。
*   **メモリ参照とオフセット**: ARMのロード/ストア命令は、ベースレジスタ（例: SP, SB, または他の汎用レジスタ）とオフセット値を組み合わせてメモリのアドレスを指定します。例えば、`LDR R0, [SP, #offset]`は、SPレジスタの値に`offset`を加算したアドレスからデータをロードし、R0に格納します。この`offset`値には命令形式によって制限があり、大きなオフセットを直接指定することはできません。

### Native Client (NaCl)

Native Client (NaCl) は、Googleが開発した技術で、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行するためのサンドボックス環境を提供します。NaClの主な目的は、ウェブアプリケーションにネイティブコードのパフォーマンスと機能をもたらしつつ、セキュリティ上のリスクを最小限に抑えることです。

*   **サンドボックス化**: NaClは、実行されるネイティブコードを厳重に隔離された環境（サンドボックス）に閉じ込めます。これにより、悪意のあるコードがシステムリソースに直接アクセスしたり、ユーザーデータに不正にアクセスしたりすることを防ぎます。
*   **コード検証**: NaClの重要なセキュリティ機能の一つが「コード検証」です。NaClモジュールがロードされる前に、そのバイナリコードが厳格なセキュリティルールに準拠しているかどうかが検証されます。これには、メモリ安全性の確保、不正なシステムコールや特権命令の使用の禁止、制御フローの制限などが含まれます。
    *   特に、メモリ参照（ロード/ストア命令）のアドレス計算がサンドボックスの境界内で安全に行われることを保証するために、オフセット値の範囲やアドレッシングモードに厳しい制約が課せられます。大きなオフセットを持つメモリ参照は、アドレス計算が複雑になり、サンドボックスの境界チェックを迂回する潜在的なリスクがあると見なされるため、拒否されることがあります。

### スタックオフセットと非スタックオフセット

*   **スタックオフセット**: スタックポインタ (SP) をベースレジスタとして、スタック上のデータ（ローカル変数、関数引数など）にアクセスする際のオフセットです。通常、関数内で使用されるスタック領域は比較的限定的であるため、オフセットも小さい範囲に収まることが多いと想定されます。
*   **非スタックオフセット**: スタックポインタ以外のレジスタ（例: グローバル変数アクセス用のStatic Baseレジスタ `R9`、またはヒープ上のデータへのポインタを保持する汎用レジスタ）をベースレジスタとして、メモリ上のデータにアクセスする際のオフセットです。これらのオフセットは、スタックオフセットよりもはるかに大きな値になる可能性があります。

大きなオフセットが問題になるのは、ARM命令が直接扱えるオフセット値に制限があるためです。例えば、一部のLDR/STR命令は±4095バイトのオフセットしか直接扱えません。これを超えるオフセットにアクセスするには、オフセット値を別のレジスタにロードしてから、そのレジスタをインデックスとして使用するなどの複数命令による処理が必要になります。

## 技術的詳細

このコミットが修正しているのは、GoコンパイラのARMバックエンドにおける、大きなメモリオフセットの処理ロジックです。特にNaCl環境下での挙動に焦点を当てています。

ARMアーキテクチャでは、メモリロード/ストア命令（LDR/STR）がベースレジスタとオフセット値を用いてメモリ位置を指定します。しかし、このオフセット値には命令形式によって上限があります。例えば、一般的なLDR/STR命令では、オフセットは12ビット符号なし整数（0〜4095）または符号付き8ビット整数（-255〜255）に制限されることがあります。これを超えるオフセットにアクセスしようとすると、コンパイラは複数の命令を生成してアドレスを構築する必要があります。例えば、オフセット値を別のレジスタにロードし、そのレジスタをインデックスとして使用するようなシーケンスです。

Goコンパイラの`cmd/internal/obj/arm/asm5.go`内の`asmoutnacl`関数は、NaCl向けにアセンブリコードを生成する際に、このような大きなオフセットを処理するためのロジックを含んでいました。このロジックは、メモリ参照のオフセットがARM命令の直接アドレッシング範囲を超える場合に、それを安全に処理するための追加の命令シーケンスを生成する役割を担っています。

しかし、以前の実装では、この大きなオフセット処理ロジックが、スタックポインタ（`REG_R13`）をベースレジスタとするメモリ参照に対しては適用されませんでした。これは、スタック上のデータへのアクセスは通常、スタックポインタからのオフセットが比較的小さい範囲に収まるという仮定に基づいていた可能性があります。

ところが、Native Clientのコード検証器は、そのセキュリティモデルの厳格さから、生成されるバイナリコードに対して非常に厳しい制約を課します。特に、メモリ参照のアドレス計算がサンドボックスの境界内で安全に行われることを保証するため、オフセット値の範囲やアドレッシングモードに細心の注意を払います。最新のNaClバージョンでは、たとえスタック参照であっても、特定の大きなオフセットを持つメモリ参照が、セキュリティポリシーに違反すると見なされ、拒否されるようになったと考えられます。これは、コンパイラが生成するコードが、NaClの期待する「安全な」アドレッシングパターンに従っていない場合に発生します。

このコミットは、このNaClの新しい制約に対応するため、スタックポインタ（`REG_R13`）をベースとするメモリ参照も、他のメモリ参照と同様に、大きなオフセット処理ロジックの対象とすることで、NaClのコード検証をパスできるようにします。これにより、GoプログラムがNaCl環境でより堅牢に動作するようになります。

## コアとなるコードの解説

この変更は、`asmoutnacl` 関数内の条件式を修正しています。`asmoutnacl` は、GoコンパイラがNaClターゲット向けにARMアセンブリコードを生成する際に、特定の命令（特にメモリ参照を伴うもの）を調整するために使用される関数です。

変更前のコードは以下のようになっていました。

```go
if (p.To.Type == obj.TYPE_MEM && p.To.Reg != REG_R13 && p.To.Reg != REG_R9) || // MOVW Rx, X(Ry), y != 13 && y != 9
	(p.From.Type == obj.TYPE_MEM && p.From.Reg != REG_R13 && p.From.Reg != REG_R9) { // MOVW X(Rx), Ry, x != 13 && x != 9
```

この条件式は、メモリ参照（`obj.TYPE_MEM`）が、宛先オペランド（`p.To`）またはソースオペランド（`p.From`）のいずれかにある場合に、特定の処理（大きなオフセットの修正ロジック）を適用するかどうかを決定していました。
重要なのは、`p.To.Reg != REG_R13 && p.To.Reg != REG_R9` および `p.From.Reg != REG_R13 && p.From.Reg != REG_R9` という部分です。これは、ベースレジスタがスタックポインタ（`REG_R13`）またはStatic Base（`REG_R9`）であるメモリ参照を、この大きなオフセット修正ロジックの対象から**除外**していました。

変更後のコードは以下のようになります。

```go
if (p.To.Type == obj.TYPE_MEM && p.To.Reg != REG_R9) || // MOVW Rx, X(Ry), y != 9
	(p.From.Type == obj.TYPE_MEM && p.From.Reg != REG_R9) { // MOVW X(Rx), Ry, x != 9
```

この変更により、条件式から `p.To.Reg != REG_R13` および `p.From.Reg != REG_R13` の部分が削除されました。つまり、スタックポインタ（`REG_R13`）をベースレジスタとするメモリ参照が、もはやこの大きなオフセット修正ロジックの対象から除外されなくなりました。

結果として、スタック上の変数へのアクセスで大きなオフセットが使用される場合でも、GoコンパイラはNaClのコード検証器が許容する形式に変換するための追加の命令シーケンスを生成するようになります。これにより、最新のNaCl環境で発生していた、大きなスタックオフセットを持つメモリ参照が拒否される問題が解決されます。`REG_R9`（Static Base）は引き続き除外されていますが、これはグローバルデータへのアクセスに関する別の考慮事項があるためと考えられます。

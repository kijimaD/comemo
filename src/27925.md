## 変更の背景

この変更の背景には、Go言語における一般的なプログラミングのベストプラクティスと、コードの可読性および保守性の向上が挙げられます。コミットメッセージにある「(Split out from CL 22205.)」という記述から、元々はより大きな変更セットの一部であったことが伺えます。このような変数のスコープを限定する変更は、以下の理由から推奨されます。

1.  **変数のライフサイクルの短縮**: 変数を必要とされる最小限のスコープで宣言することで、その変数が意図しない場所で再利用されたり、古い値が残存したりするリスクを減らします。
2.  **可読性の向上**: 変数が使用される直前で宣言されるため、その変数が何のために使われているのかがコードを読んだ際にすぐに理解しやすくなります。
3.  **バグの抑制**: 広すぎるスコープを持つ変数は、特に複雑なループ処理において、意図しない副作用やバグの原因となることがあります。ループ内で毎回新しい変数を宣言することで、このような問題を回避できます。
4.  **Go言語のイディオム**: Go言語では、`:=` (短い変数宣言) を用いて変数をその場で宣言・初期化することが一般的であり、この変更はそのイディオムに沿ったものです。

この特定のケースでは、Goリンカの内部処理において、リロケーション情報を扱うループ内で `r` (リロケーション構造体へのポインタ) と `ri` (インデックス) がループの外で宣言されていました。これをループ内に移動させることで、各ループイテレーションで新しい `r` と `ri` が作成され、コードの意図がより明確になります。

## 前提知識の解説

### Go言語のリンカ (`cmd/link`)

Go言語のコンパイラツールチェーンの一部であり、Goプログラムのコンパイル済みオブジェクトファイルを結合して、実行可能なバイナリを生成する役割を担います。リンカは、異なるソースファイルで定義された関数や変数への参照を解決し、最終的な実行ファイルに必要なすべてのコードとデータを配置します。

### 実行ファイルフォーマット (ELF, Mach-O, PE)

コンピュータのオペレーティングシステムは、それぞれ異なる実行ファイルフォーマットを使用しています。
*   **ELF (Executable and Linkable Format)**: LinuxやUnix系システムで広く使用される標準的な実行ファイルフォーマットです。
*   **Mach-O (Mach Object)**: macOSやiOSなどのApple製システムで使用される実行ファイルフォーマットです。
*   **PE (Portable Executable)**: Windowsシステムで使用される実行ファイルフォーマットです。

Goリンカは、これらの異なるプラットフォーム向けに実行ファイルを生成するため、それぞれのフォーマットの仕様を理解し、適切に処理する必要があります。このコミットで変更された `elf.go`、`macho.go`、`pe.go` は、それぞれのフォーマット固有のリロケーション処理を担当する部分です。

### リロケーション (Relocation)

リロケーションとは、プログラムがメモリにロードされる際に、コードやデータ内のアドレス参照を修正するプロセスです。コンパイル時やリンク時には、最終的なメモリ上のアドレスが確定していないため、相対アドレスやシンボル名で参照が行われます。リンカは、これらの参照を解決し、最終的な絶対アドレスに変換する役割を担います。

例えば、ある関数が別の関数を呼び出す場合、コンパイル時には呼び出される関数の正確なメモリ位置は不明です。リンカは、すべてのオブジェクトファイルを結合し、各関数の最終的なアドレスを決定した後、呼び出し元のコード内の参照をそのアドレスに「リロケート（再配置）」します。

### `*Reloc` と `LSym`

Goリンカの内部で使用されるデータ構造です。
*   **`LSym` (Linker Symbol)**: リンカが扱うシンボル（関数、グローバル変数など）を表す構造体です。各 `LSym` は、そのシンボルに関する情報（名前、サイズ、アドレス、関連するリロケーションなど）を含んでいます。
*   **`*Reloc`**: リロケーション情報を表す構造体へのポインタです。`LSym` には、そのシンボルに関連するリロケーションのリスト (`sym.R`) が含まれており、各 `Reloc` エントリは、どのシンボルを、どのタイプのリロケーションで、どこに適用するかといった詳細を保持しています。

### 変数のスコープと初期化

Go言語において、変数のスコープは変数がアクセス可能なコードの領域を指します。
*   **ブロックレベルスコープ**: Goの変数は、宣言されたブロック（`{}`で囲まれた領域）内で有効です。
*   **短い変数宣言 (`:=`)**: Goでは、`var` キーワードを使わずに `:=` 演算子を使って変数を宣言し、同時に初期化することができます。この方法は、変数の型をコンパイラに推論させるため、簡潔に記述できます。`:=` で宣言された変数は、そのブロック内で新しい変数として扱われます。

ループ内で変数を宣言する場合、`var` を使ってループの外で宣言すると、その変数はループ全体で共有され、各イテレーションで値が上書きされます。一方、`:=` を使ってループ内で宣言すると、各イテレーションで新しい変数が作成され、そのスコープはそのイテレーションに限定されます。

## 技術的詳細

このコミットの技術的詳細は、Go言語のリンカが実行ファイルフォーマット（ELF, Mach-O, PE）のリロケーション処理を行う際の内部ループにおける変数のスコープ管理にあります。

変更前は、リロケーション情報を処理するループの外部で `r *Reloc` と `ri int` という変数が宣言されていました。

```go
// 変更前 (例: elf.go)
func elfrelocsect(sect *Section, first *LSym) {
    // ...
    eaddr := int32(sect.Vaddr + sect.Length)
    var r *Reloc // ループの外で宣言
    var ri int   // ループの外で宣言
    for ; sym != nil; sym = sym.Next {
        // ...
        for ri = 0; ri < len(sym.R); ri++ { // ri はここで再代入
            r = &sym.R[ri] // r はここで再代入
            // ...
        }
    }
}
```

このコードでは、`r` と `ri` は `elfrelocsect` 関数のスコープ内で一度だけ宣言され、内側のループの各イテレーションで値が再代入されていました。これは機能的には問題ありませんが、以下の点で改善の余地がありました。

1.  **スコープの広さ**: `r` と `ri` のスコープが、それらが実際に使用される内側のループのイテレーションよりも広くなっていました。
2.  **意図の不明確さ**: `r` と `ri` が各イテレーションで新しい意味を持つのか、それとも前のイテレーションの状態を引き継ぐのかが、コードを一見しただけでは分かりにくい可能性がありました。

変更後は、`ri` と `r` の宣言が内側のループの初期化部分に移動され、Goの短い変数宣言 `:=` が使用されています。

```go
// 変更後 (例: elf.go)
func elfrelocsect(sect *Section, first *LSym) {
    // ...
    eaddr := int32(sect.Vaddr + sect.Length)
    for ; sym != nil; sym = sym.Next {
        // ...
        for ri := 0; ri < len(sym.R); ri++ { // ri はループ内で宣言・初期化
            r := &sym.R[ri] // r はループ内で宣言・初期化
            // ...
        }
    }
}
```

この変更により、以下の利点が得られます。

*   **スコープの限定**: `ri` と `r` は、それぞれが宣言された内側の `for` ループの各イテレーションのブロック内でのみ有効となります。これにより、変数のライフサイクルが短くなり、コードの意図がより明確になります。
*   **バグの防止**: `r` がループの外で宣言されていると、もしループの途中で `break` や `continue` が発生した場合、`r` が指す値が前のイテレーションのまま残ってしまう可能性があります。ループ内で `r := ...` とすることで、各イテレーションで新しい `r` が作成されるため、このような潜在的なバグが回避されます。
*   **Goイディオムへの準拠**: Go言語では、変数を必要とされる最小限のスコープで宣言し、`:=` を活用することが推奨されるイディオムです。この変更はそれに従っています。

この変更は、パフォーマンスに大きな影響を与えるものではなく、主にコードの品質、可読性、保守性を向上させるためのものです。リンカのような低レベルで複雑なコードベースでは、このような細かな改善が長期的な安定性と開発効率に寄与します。

## コアとなるコードの解説

変更の核心は、Go言語の短い変数宣言 `:=` を活用して、変数のスコープを最小限に限定することです。

**変更前:**

```go
    var r *Reloc
    var ri int
    for ; sym != nil; sym = sym.Next {
        // ...
        for ri = 0; ri < len(sym.R); ri++ {
            r = &sym.R[ri]
            // ...
        }
    }
```

このコードでは、`r` と `ri` は外側の `for` ループが始まる前に一度だけ宣言されています。内側の `for` ループの各イテレーションでは、既存の `ri` と `r` に新しい値が**再代入**されます。このため、`r` と `ri` は内側のループの各イテレーション間で状態を共有していることになります。

**変更後:**

```go
    for ; sym != nil; sym = sym.Next {
        // ...
        for ri := 0; ri < len(sym.R); ri++ {
            r := &sym.R[ri]
            // ...
        }
    }
```

変更後では、`ri` と `r` は内側の `for` ループの初期化部分で `:=` を使って宣言されています。Go言語において、`for` ループの初期化ステートメントで `:=` を使うと、その変数はループの各イテレーションのブロック内で新しい変数として宣言され、初期化されます。

具体的には、
*   `for ri := 0; ...` の部分で、`ri` は各イテレーションの開始時に `0` から `len(sym.R)-1` までの新しい整数として宣言されます。
*   `r := &sym.R[ri]` の部分で、`r` は各イテレーションで `sym.R[ri]` のアドレスを指す新しい `*Reloc` 型の変数として宣言されます。

これにより、`ri` と `r` のスコープは内側のループの単一のイテレーションに限定され、そのイテレーションが終了すると変数は「消滅」します（ガベージコレクションの対象となり得ます）。このアプローチは、変数の意図しない再利用を防ぎ、コードの安全性を高め、読み手が変数のライフサイクルをより簡単に追跡できるようにします。

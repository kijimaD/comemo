# [インデックス 25164] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における「Stop The World (STW)」ポーズ時間の削減を目的としています。具体的には、GCのスイープ終了フェーズで`finishsweep_m`関数が実行される際に、STW中であれば不要なスイープ待機ループをスキップするように変更されています。これにより、特に大容量ヒープを持つアプリケーションにおいて、GCポーズ時間が大幅に短縮されます。

## コミット

Goランタイムの`finishsweep_m`関数から、STW（Stop The World）中に実行される際の不要なスイープ待機ループを削除します。これにより、GCポーズ時間が大幅に削減され、特に大容量ヒープでのパフォーマンスが向上します。

## 元コミット内容

```
runtime: remove sweep wait loop in finishsweep_m

In general, finishsweep_m must block until any spans that are
concurrently being swept have been swept. It accomplishes this by
looping over all spans, which, as in the previous commit, takes
~1ms/heap GB. Unfortunately, we do this during the STW sweep
termination phase, so multi-gigabyte heaps can push our STW time past
10ms.

However, there's no need to do this wait if the world is stopped
because, in effect, stopping the world already had to wait for
anything that was sweeping (and if it didn't, the wait in
finishsweep_m would deadlock). Hence, we can simply skip this loop if
the world is stopped, such as during sweep termination. In fact,
currently all calls to finishsweep_m are STW, but this hasn't always
been the case and may not be the case in the future, so we keep the
logic around.

For 24GB heaps, this reduces max pause time by 75% relative to tip and
by 90% relative to Go 1.5. Notably, all pauses are now well under
10ms. Here are the results for the garbage benchmark:

24GB      4        3.7ms          16ms         37ms

In the 4GB/4P case, it seems the "before change" run got lucky: the
max went up, but the 99%ile pause time went down from 3ms to 2.04ms.

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行中にメモリを自動的に管理する重要な機能です。しかし、GCプロセスの一部には「Stop The World (STW)」と呼ばれるフェーズがあり、この間はすべてのアプリケーションゴルーチンが一時停止されます。STWポーズ時間が長くなると、アプリケーションの応答性やスループットに悪影響を及ぼすため、Goランタイムの開発者は常にこの時間の短縮に努めています。

このコミット以前は、GCのスイープ終了フェーズで呼び出される`finishsweep_m`関数内に、並行してスイープされているスパン（メモリ領域の単位）が完了するのを待機するループが存在していました。この待機ループは、ヒープサイズが大きくなるにつれて線形に時間がかかり、特に数ギガバイトを超えるような大容量ヒープを持つアプリケーションでは、STWポーズ時間を10ミリ秒以上に押し上げる原因となっていました。

しかし、この`finishsweep_m`がSTW中に呼び出される場合、そもそもSTW自体が、並行して実行されていたスイープ処理が完了するのを待機しているはずです。したがって、STW中に再度同じような待機ループを実行することは冗長であり、デッドロックを引き起こす可能性さえありました。この冗長な待機が、大容量ヒープにおけるGCポーズ時間の増加の主な原因となっていたため、この部分を最適化する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に解放するプロセスです。Go 1.5以降、GCは主に並行（concurrent）に動作し、STWポーズ時間を最小限に抑えるように設計されています。
*   **GCフェーズ**: GoのGCは複数のフェーズに分かれています。
    *   **Mark (マーク)**: どのオブジェクトが到達可能（使用中）かを識別するフェーズ。
    *   **Sweep (スイープ)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放するフェーズ。Go 1.5以降、スイープは並行して行われることが多いです。
    *   **Stop The World (STW)**: GCの特定のクリティカルな段階で、すべてのアプリケーションゴルーチンが一時停止されるフェーズ。このフェーズは可能な限り短くすることが目標です。
*   **スパン (Span)**: Goランタイムのメモリ管理における基本的な単位です。ヒープメモリは、ページ（通常8KB）の集まりであるスパンに分割されます。オブジェクトはこれらのスパン内に割り当てられます。
*   **`mheap_`**: Goランタイムのグローバルなヒープ構造体で、すべてのスパンやメモリ管理に関する情報が含まれています。
*   **`sweepgen`**: スイープ世代（sweep generation）を表すカウンターです。GCサイクルごとにインクリメントされ、スパンがどのGCサイクルでスイープされたか（またはスイープされるべきか）を追跡するために使用されます。
*   **`_MSpanInUse`**: スパンの状態を示す定数の一つで、そのスパンが現在使用中であることを示します。
*   **`mSpan_EnsureSwept(s)`**: 特定のスパン`s`がまだスイープされていない場合に、そのスパンを強制的にスイープする関数です。
*   **`finishsweep_m()`**: GCのスイープフェーズの終了時に呼び出される関数で、すべてのスパンが適切にスイープされたことを確認する役割を担います。

## 技術的詳細

このコミットの核心は、`finishsweep_m`関数内のスイープ待機ロジックの条件付き実行です。

以前の`finishsweep_m`関数は、まず`sweepone()`を繰り返し呼び出して、まだスイープされていないスパンを積極的にスイープしようとします。その後、`mheap_.sweepgen`と各スパンの`sweepgen`を比較し、`_MSpanInUse`状態のスパンで`sweepgen`が一致しないもの（つまり、現在のGCサイクルでまだスイープされていないスパン）があれば、`mSpan_EnsureSwept`を呼び出して強制的にスイープを完了させていました。この2番目のループが、大容量ヒープでSTWポーズ時間を増加させる原因でした。

コミットの変更点では、`finishsweep_m`関数に`stw`というブーリアン引数が追加されました。この引数は、`finishsweep_m`がSTW中に呼び出されているかどうかを示します。

変更後のロジックは以下のようになります。

1.  `finishsweep_m(stw bool)`が呼び出される。
2.  まず、`sweepone()`を繰り返し呼び出して、まだスイープされていないスパンを積極的にスイープしようとする部分は変更ありません。
3.  次に、以前は無条件に実行されていた「他の並行スイープ中のスパンが完了するのを待機するループ」が、`if !stw { ... }`という条件ブロックで囲まれます。
4.  これにより、`stw`が`true`（つまり、STW中）の場合、この待機ループは完全にスキップされます。

この変更の根拠は、STWが既に発生している場合、STW自体が、並行して実行されていたすべてのGCワーカー（スイープを含む）が安全な状態になるまで待機しているという事実に基づいています。したがって、`finishsweep_m`がSTW中に呼び出される際には、既にすべてのスパンのスイープが完了しているか、少なくとも安全に処理できる状態になっているため、追加の待機は不要であり、むしろパフォーマンスのボトルネックとなっていました。

コミットメッセージにあるベンチマーク結果が示すように、この変更により、特に24GBのような大容量ヒープにおいて、最大ポーズ時間が大幅に短縮されています。Go 1.5と比較して90%、変更前と比較しても75%の削減が達成され、すべてのポーズ時間が10ミリ秒以下に収まるようになりました。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

`mgc.go`では、`gc`関数内で`finishsweep_m`が呼び出される箇所が2箇所変更されています。

1.  `systemstack(stopTheWorldWithSema)`の直後:
    以前は`systemstack(finishsweep_m)`と直接呼び出されていましたが、変更後は`systemstack(func() { finishsweep_m(true) })`という匿名関数を介して呼び出されるようになりました。これは、`finishsweep_m`が引数を取るようになったため、`systemstack`に直接渡すことができなくなったためです。重要なのは、`finishsweep_m`に`true`が渡されている点です。これは、この呼び出しがSTW中に行われていることを明示しています。
2.  GCのマーク終了フェーズの再初期化中:
    同様に、`gcResetGState()`と`gcResetMarkState()`の後に呼び出される`finishsweep_m()`も`finishsweep_m(true)`に変更されています。ここでも`true`が渡され、STW中であることを示しています。

これらの変更により、`finishsweep_m`がSTW中に呼び出される際には、必ず`stw`引数に`true`が渡されるようになります。

### `src/runtime/mgcsweep.go` の変更

`mgcsweep.go`では、`finishsweep_m`関数のシグネチャと内部ロジックが変更されています。

1.  **関数のシグネチャ変更**:
    `func finishsweep_m()`から`func finishsweep_m(stw bool)`に変更され、`stw`というブーリアン引数を受け取るようになりました。
2.  **スイープ待機ループの条件化**:
    最も重要な変更は、以下のコードブロックが`if !stw { ... }`という条件文で囲まれたことです。

    ```go
    	sg := mheap_.sweepgen
    	for _, s := range work.spans {
    		if s.sweepgen != sg && s.state == _MSpanInUse {
    			mSpan_EnsureSwept(s)
    		}
    	}
    ```
    このブロックは、`mheap_.sweepgen`と異なる`sweepgen`を持つ`_MSpanInUse`状態のスパン（つまり、まだスイープされていないスパン）を強制的にスイープする役割を担っていました。
    `if !stw`という条件が追加されたことで、`stw`が`true`（STW中）の場合、このループは実行されなくなります。これにより、STW中に不要な待機がスキップされ、GCポーズ時間が大幅に短縮されます。

コミットメッセージのコメント`TODO(austin): As of this writing, we always pass true for stw. Consider removing this code.`は、このコミット時点では`finishsweep_m`のすべての呼び出しがSTW中に行われているため、`if !stw`の条件が常に`false`となり、この待機ループが実質的に実行されないことを示唆しています。しかし、将来的にSTW外から`finishsweep_m`が呼び出される可能性を考慮して、このロジック自体は残されています。これは、Goランタイムの設計における将来性への配慮と堅牢性を示しています。

コミットの変更点では、`finishsweep_m`関数に`stw`というブーリアン引数が追加されました。この引数は、`finishsweep_m`がSTW中に呼び出されているかどうかを示します。

変更後のロジックは以下のようになります。

1.  `finishsweep_m(stw bool)`が呼び出される。
2.  まず、`sweepone()`を繰り返し呼び出して、まだスイープされていないスパンを積極的にスイープしようとする部分は変更ありません。
3.  次に、以前は無条件に実行されていた「他の並行スイープ中のスパンが完了するのを待機するループ」が、`if !stw { ... }`という条件ブロックで囲まれます。
4.  これにより、`stw`が`true`（つまり、STW中）の場合、この待機ループは完全にスキップされます。

この変更の根拠は、STWが既に発生している場合、STW自体が、並行して実行されていたすべてのGCワーカー（スイープを含む）が安全な状態になるまで待機しているという事実に基づいています。したがって、`finishsweep_m`がSTW中に呼び出される際には、既にすべてのスパンのスイープが完了しているか、少なくとも安全に処理できる状態になっているため、追加の待機は不要であり、むしろパフォーマンスのボトルネックとなっていました。

コミットメッセージにあるベンチマーク結果が示すように、この変更により、特に24GBのような大容量ヒープにおいて、最大ポーズ時間が大幅に短縮されています。Go 1.5と比較して90%、変更前と比較しても75%の削減が達成され、すべてのポーズ時間が10ミリ秒以下に収まるようになりました。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

`mgc.go`では、`gc`関数内で`finishsweep_m`が呼び出される箇所が2箇所変更されています。

1.  `systemstack(stopTheWorldWithSema)`の直後:
    以前は`systemstack(finishsweep_m)`と直接呼び出されていましたが、変更後は`systemstack(func() { finishsweep_m(true) })`という匿名関数を介して呼び出されるようになりました。これは、`finishsweep_m`が引数を取るようになったため、`systemstack`に直接渡すことができなくなったためです。重要なのは、`finishsweep_m`に`true`が渡されている点です。これは、この呼び出しがSTW中に行われていることを明示しています。
2.  GCのマーク終了フェーズの再初期化中:
    同様に、`gcResetGState()`と`gcResetMarkState()`の後に呼び出される`finishsweep_m()`も`finishsweep_m(true)`に変更されています。ここでも`true`が渡され、STW中であることを示しています。

これらの変更により、`finishsweep_m`がSTW中に呼び出される際には、必ず`stw`引数に`true`が渡されるようになります。

### `src/runtime/mgcsweep.go` の変更

`mgcsweep.go`では、`finishsweep_m`関数のシグネチャと内部ロジックが変更されています。

1.  **関数のシグネチャ変更**:
    `func finishsweep_m()`から`func finishsweep_m(stw bool)`に変更され、`stw`というブーリアン引数を受け取るようになりました。
2.  **スイープ待機ループの条件化**:
    最も重要な変更は、以下のコードブロックが`if !stw { ... }`という条件文で囲まれたことです。

    ```go
    	sg := mheap_.sweepgen
    	for _, s := range work.spans {
    		if s.sweepgen != sg && s.state == _MSpanInUse {
    			mSpan_EnsureSwept(s)
    		}
    	}
    ```
    このブロックは、`mheap_.sweepgen`と異なる`sweepgen`を持つ`_MSpanInUse`状態のスパン（つまり、まだスイープされていないスパン）を強制的にスイープする役割を担っていました。
    `if !stw`という条件が追加されたことで、`stw`が`true`（STW中）の場合、このループは実行されなくなります。これにより、STW中に不要な待機がスキップされ、GCポーズ時間が大幅に短縮されます。

コミットメッセージのコメント`TODO(austin): As of this writing, we always pass true for stw. Consider removing this code.`は、このコミット時点では`finishsweep_m`のすべての呼び出しがSTW中に行われているため、`if !stw`の条件が常に`false`となり、この待機ループが実質的に実行されないことを示唆しています。しかし、将来的にSTW外から`finishsweep_m`が呼び出される可能性を考慮して、このロジック自体は残されています。これは、Goランタイムの設計における将来性への配慮と堅牢性を示しています。

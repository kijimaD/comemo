このコミットは、`src/net/http/server.go` と `src/net/http/transport.go` の2つのファイルを変更しています。

## コミット

`net/http` パッケージにおけるTLS設定のクローン処理で発生する競合状態（レースコンディション）を修正するコミットです。特に、`tls.Config` 構造体のシャローコピーが原因で発生する問題を解決するため、安全なクローン関数 `cloneTLSConfig` および `cloneTLSClientConfig` が導入されました。この修正は、Googleの内部プログラムでレース検出器によって発見された問題に対応し、`cmd/vet` の静的解析機能の改善とも関連しています。

## 変更の背景

この変更の主な背景は、Goの `net/http` パッケージにおいて、TLS (Transport Layer Security) 設定を扱う際に発生する競合状態（レースコンディション）の発見です。この問題は、Googleの内部プログラムをGoのレース検出器 (`go run -race`) で実行中に見つかりました。

具体的には、`crypto/tls.Config` 構造体をシャローコピー（浅いコピー）する際に問題が発生していました。`tls.Config` 構造体には、内部的にミューテックス（`sync.Once` などの形で）を含むフィールドが存在する可能性があり、これを単純にコピーすると、元の構造体とコピーされた構造体の両方が同じミューテックスを参照することになります。複数のゴルーチンが同時にこれらの構造体を使用しようとすると、ミューテックスの二重ロックや不正な状態変更が発生し、プログラムのクラッシュや予期せぬ動作につながる競合状態を引き起こします。

コミットメッセージには、この問題を再現するための具体的なコード例が示されており、`httptest.NewTLSServer` と `http.Transport` が同じ `tls.Config` インスタンスを共有し、異なるゴルーチンからアクセスされるシナリオで競合が発生することが示唆されています。

この問題に対処するため、`tls.Config` を安全にクローンするための専用関数を導入し、ミューテックスを含む可能性のある内部フィールドが適切に処理されるようにする必要がありました。また、このコミットと並行して、`cmd/vet` ツールがミューテックスのコピーに関する静的解析警告を報告するように改善されました (CL 13646)。これにより、将来的に同様の問題がコードベースに混入するのを防ぐ狙いもありましたが、`cloneTLSConfig` と `cloneTLSClientConfig` のような特定のユースケースにおける微妙な違いは `vet` では検出できないことも指摘されています。

## 前提知識の解説

### 1. Goのレース検出器 (`go run -race`)

Go言語には、プログラム実行中に競合状態を検出するための組み込みツールであるレース検出器が用意されています。`go run -race` や `go test -race` のように `-race` フラグを付けてコマンドを実行することで有効になります。レース検出器は、複数のゴルーチンが同時に同じメモリ領域にアクセスし、少なくとも一方が書き込み操作である場合に警告を発します。これは、並行処理におけるバグ（競合状態）を見つける上で非常に強力なツールです。

### 2. `crypto/tls.Config` 構造体

`crypto/tls` パッケージは、TLSプロトコルを実装するための機能を提供します。`tls.Config` 構造体は、TLS接続の振る舞いを定義するための様々な設定オプションを保持します。これには、証明書、鍵、サポートされるプロトコルバージョン、暗号スイート、セッションチケットの管理、クライアント認証設定などが含まれます。この構造体は、TLSサーバーとクライアントの両方で使用されます。

重要な点として、`tls.Config` 構造体の一部のフィールドは、内部的に `sync.Once` や `sync.Mutex` といった同期プリミティブを含むことがあります。例えば、セッションチケット鍵の生成などは一度だけ行われるべき処理であり、`sync.Once` を使用して保護されることがあります。

### 3. `sync.Once` とミューテックスのコピー問題

`sync.Once` は、Goにおいて特定のコードブロックが一度だけ実行されることを保証するためのプリミティブです。内部的には、実行状態を管理するためのフラグと、そのフラグへのアクセスを保護するためのミューテックスを含んでいます。

Goでは、構造体を `=` 演算子や `*` 演算子でシャローコピーすると、その構造体のすべてのフィールドがビット単位でコピーされます。もし構造体の中に `sync.Once` や `sync.Mutex` のような同期プリミティブが含まれている場合、そのコピーは元のインスタンスと同じミューテックスを参照することになります。

例えば、`var a A; b := a` のようにコピーした場合、`a` と `b` はそれぞれ独立した構造体インスタンスですが、もし `A` が `sync.Mutex` をフィールドとして持っていたら、`a.Mutex` と `b.Mutex` は同じメモリ上のミューテックスを指すことになります。これにより、`a.Mutex.Lock()` と `b.Mutex.Lock()` が同時に呼ばれた場合、デッドロックや競合状態が発生する可能性があります。これはGoの公式ドキュメントでも「ミューテックスはコピーしてはいけない」という形で警告されています。

### 4. `net/http` パッケージ

`net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。
*   **`http.Server`**: HTTPサーバーを構築するための構造体で、`ListenAndServeTLS` メソッドを通じてTLSを有効にしたHTTPSサーバーを起動できます。この際、`tls.Config` を使用してTLSの挙動を設定します。
*   **`http.Transport`**: HTTPクライアントがリクエストを送信する際の低レベルな詳細（接続の確立、TLSハンドシェイク、プロキシ設定など）を管理する構造体です。`TLSClientConfig` フィールドを通じて、クライアント側のTLS設定をカスタマイズできます。

## 技術的詳細

このコミットの核心は、`tls.Config` 構造体の安全なコピーメカニズムを導入し、既存のシャローコピーに起因する競合状態を解消することにあります。

### 既存のシャローコピーの問題点

コミットメッセージとコード変更からわかるように、以前のコードでは `http.Server` の `ListenAndServeTLS` メソッド内や `http.Transport` の `dialConn` メソッド内で、`tls.Config` インスタンスを直接コピーする、あるいはフィールドを個別に設定する際に、シャローコピーが行われていました。

例えば、`*config = *srv.TLSConfig` のような記述は、`srv.TLSConfig` が指す `tls.Config` 構造体の内容を、新しく作成された `config` 構造体にビット単位でコピーします。もし `tls.Config` の内部に `sync.Once` や `sync.Mutex` のような同期プリミティブが含まれている場合、このシャローコピーによって、元の `srv.TLSConfig` とコピー先の `config` が同じ同期プリミティブを共有することになります。

この共有された同期プリミティブに対して、異なるゴルーチン（例えば、サーバーのリスニングゴルーチンと、リクエストを処理するゴルーチン）が同時にアクセスしようとすると、競合状態が発生し、プログラムの不安定性やクラッシュにつながります。特に `tls.Config` の `SessionTicketKey` のようなフィールドは、内部で `sync.Once` を使って初期化される可能性があり、これが問題の根源となります。

### `cloneTLSConfig` 関数の導入

この問題を解決するために、`cloneTLSConfig` 関数が `src/net/http/transport.go` に新しく追加されました。この関数は、`*tls.Config` を引数に取り、そのエクスポートされたフィールドのみを新しい `tls.Config` インスタンスに「シャロークローン」します。

重要なのは、このクローン処理が `sync.Once` のような非エクスポートフィールド（内部フィールド）を意図的に無視する点です。`sync.Once` はミューテックスを含むため、これをコピーすると競合状態を引き起こします。`cloneTLSConfig` は、`tls.Config` の各エクスポートフィールドを明示的に新しい構造体にコピーすることで、同期プリミティブの共有を防ぎます。

ただし、`cloneTLSConfig` のコメントには重要な注意書きがあります。
> The cfg must not be in active use by tls.Server, or else there can still be a race with tls.Server updating SessionTicketKey and our copying it, and also a race with the server setting SessionTicketsDisabled=false on failure to set the random ticket key.

これは、`tls.Server` が `SessionTicketKey` を更新する可能性があり、その最中に `cloneTLSConfig` が呼ばれると、まだ競合状態が発生する可能性があることを示唆しています。この関数は、主にサーバーが起動する前の初期設定段階で、`srv.TLSConfig` をベースに新しい設定を作成する用途を想定しています。

### `cloneTLSClientConfig` 関数の導入

さらに、`cloneTLSClientConfig` 関数も導入されました。この関数は `cloneTLSConfig` と非常に似ていますが、`SessionTicketsDisabled` と `SessionTicketKey` の2つのフィールドを意図的にコピーしません。

この違いは、クライアント側のTLS設定のクローンにおいて重要です。`SessionTicketKey` はサーバー側でセッション再開のために使用される鍵であり、クライアント側では通常設定する必要がありません。また、`SessionTicketsDisabled` もサーバー側の挙動に影響するフィールドです。これらのフィールドをクライアント側の設定から除外することで、`tls.Server` がアクティブに使用している `tls.Config` をクローンする場合でも、`SessionTicketKey` の更新に関する競合のリスクを完全に回避できます。これにより、`http.Transport` が `TLSClientConfig` をクローンする際に、より安全な方法を提供します。

### `cmd/vet` との関連

コミットメッセージでは、`cmd/vet` がミューテックスのコピーバグを静的に報告するように変更されたこと (CL 13646) にも言及しています。`vet` はGoコードの一般的なエラーや疑わしい構造を検出するツールであり、ミューテックスのコピーは典型的なバグパターンです。この改善により、多くのミューテックスコピーバグが静的に検出できるようになりました。しかし、`cloneTLSConfig` と `cloneTLSClientConfig` のような、特定のフィールドを選択的にコピーする複雑なロジックにおける競合の可能性は、`vet` の静的解析では完全に捉えきれないことも示唆されています。これは、動的な実行時の挙動や、特定のAPIのセマンティクスに依存する問題であるためです。

## コアとなるコードの解説

### `src/net/http/server.go` の変更

`ListenAndServeTLS` 関数は、HTTPSサーバーを起動する際に使用されます。以前は、`srv.TLSConfig` が設定されている場合、その内容を `*config = *srv.TLSConfig` という形で新しい `tls.Config` インスタンスにシャローコピーしていました。このシャローコピーが競合状態の原因となる可能性がありました。

変更後、この行は `config := cloneTLSConfig(srv.TLSConfig)` に置き換えられました。これにより、`srv.TLSConfig` が持つTLS設定が、新しく導入された `cloneTLSConfig` 関数を通じて安全にクローンされるようになりました。`cloneTLSConfig` は、ミューテックスを含む可能性のある内部フィールドをコピーしないため、サーバーのTLS設定の初期化における競合状態のリスクが軽減されます。

### `src/net/http/transport.go` の変更

`dialConn` 関数は、HTTPクライアントが接続を確立する際に使用され、HTTPS接続の場合はTLSハンドシェイクを行います。以前は、`t.TLSClientConfig` をベースにクライアント側の `tls.Config` を構築する際に、手動でシャローコピーを行ったり、`ServerName` フィールドを設定するために一時的なクローンを作成したりしていました。

変更後、この部分は `cfg := cloneTLSClientConfig(t.TLSClientConfig)` に置き換えられました。これにより、クライアントのTLS設定が `cloneTLSClientConfig` 関数を通じて安全にクローンされるようになりました。この関数は、サーバー側のセッションチケット関連のフィールドを意図的に除外することで、サーバーがアクティブに使用している `tls.Config` をクローンする場合でも安全性を確保します。その後、必要に応じて `cfg.ServerName` が設定されます。

### `cloneTLSConfig` 関数の実装

この関数は、与えられた `*tls.Config` ポインタが `nil` の場合は、新しいゼロ値の `tls.Config` を返します。`nil` でない場合は、新しい `tls.Config` インスタンスを作成し、元の `cfg` の**エクスポートされた**各フィールドを明示的にコピーします。

この明示的なフィールドごとのコピーが重要です。これにより、`sync.Once` のような非エクスポートフィールド（内部フィールド）はコピーされず、新しい `tls.Config` インスタンスは独自の同期プリミティブを持つことになります。これにより、元の `tls.Config` とクローンされた `tls.Config` が同じミューテックスを共有することによる競合状態が回避されます。

### `cloneTLSClientConfig` 関数の実装

この関数も `cloneTLSConfig` と同様に、`nil` チェックとエクスポートフィールドの明示的なコピーを行います。しかし、`cloneTLSClientConfig` は `SessionTicketsDisabled` と `SessionTicketKey` の2つのフィールドを意図的にコピーしません。

この設計は、クライアント側のTLS設定の特殊性を考慮したものです。`SessionTicketKey` はサーバーがセッション再開のために使用する鍵であり、クライアント側では通常不要です。また、`SessionTicketsDisabled` もサーバーのセッションチケット発行挙動に影響します。これらのフィールドをコピーしないことで、`tls.Server` がアクティブに使用している `tls.Config` を `TLSClientConfig` としてクローンする場合でも、サーバー側のセッションチケット鍵の更新とクライアント側のクローン処理の間で競合が発生するリスクを完全に排除します。これにより、クライアント側のTLS設定の安全性がさらに向上します。

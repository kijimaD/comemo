## 元コミット内容

`runtime: fix windows/amd64 build after pc-relative 6l change`

## 変更の背景

このコミットは、Goリンカ（当時は `6l` と呼ばれていた、AMD64アーキテクチャ向けのリンカ）に加えられた「PC相対アドレス指定」に関する変更によって引き起こされたビルド問題を解決するために行われました。

Goのリンカは、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する役割を担っています。この過程で、コード内のシンボル（変数や関数の名前）が実際のメモリアドレスに解決されます。以前のリンカの挙動では、特定のアセンブリコードが期待するアドレス解決が行われていましたが、新しいリンカの変更により、シンボル参照がPC（プログラムカウンタ）からの相対オフセットとして扱われるようになりました。

この変更は、位置独立コード（PIC: Position-Independent Code）の生成を容易にしたり、コードサイズを削減したり、パフォーマンスを向上させたりする目的で行われることが多いです。しかし、Goランタイムの一部は、パフォーマンス上の理由や特定のシステムコールインターフェースとの連携のために、手書きのアセンブリ言語で記述されています。これらのアセンブリコードは、メモリアドレスの計算方法について特定の仮定を持っていることがあり、リンカの挙動変更がその仮定を破ると、ビルドエラーや実行時エラーにつながります。

今回のケースでは、Windows/amd64環境におけるGoランタイムのビルドが、このリンカの変更によって影響を受け、正しくコンパイルできなくなったため、その修正が必要となりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

*   **Go Runtime (Goランタイム)**:
    Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション、ゴルーチンのスケジューリング、チャネル操作、システムコールインターフェースなどが含まれます。Goプログラムは、このランタイムのサポートなしには動作しません。ランタイムの一部は、パフォーマンスが非常に重要であるため、Go言語ではなくアセンブリ言語で記述されています。

*   **Assembly Language (アセンブリ言語)**:
    CPUが直接実行できる機械語命令を、人間が読み書きしやすいようにニーモニック（記号）で表現した低レベルなプログラミング言語です。ここでは、x86-64（またはAMD64）アーキテクチャ向けのアセンブリ言語が使用されています。

    *   **レジスタ**: CPU内部にある高速な記憶領域です。
        *   `AX` (Accumulator Register): 算術演算の主要なオペランドとしてよく使われます。
        *   `DX` (Data Register): `AX` と組み合わせて64ビット演算に使われたり、汎用レジスタとして使われたりします。
        *   `SP` (Stack Pointer): スタックの最上位アドレスを指します。
        *   `CX` (Count Register): ループのカウンタや除算命令のオペランドとして使われることがあります。
    *   **命令**:
        *   `MOVQ`: 64ビット（Quadword）の値を移動する命令です。
        *   `SUBQ`: 64ビットの値を減算する命令です。
    *   **Goアセンブリの特殊なシンボル**:
        *   `SB` (Static Base): Goアセンブリにおける擬似レジスタで、グローバルシンボルや静的データへのオフセットを計算する際の基準点として使われます。`シンボル名(SB)` の形式で、そのシンボルのアドレスを参照します。
        *   `TEXT 関数名(SB),フラグ,$ローカル変数サイズ`: Goアセンブリにおける関数定義の構文です。`NOSPLIT` などのフラグは、スタックフレームの挙動を制御します。

*   **PC-relative addressing (PC相対アドレス指定)**:
    メモリアドレスを指定する方式の一つで、プログラムカウンタ（PC、次に実行される命令のアドレスを保持するレジスタ）の現在の値からの相対的なオフセットとしてアドレスを表現します。
    *   **利点**: コードがメモリ上のどこにロードされても、PCからの相対的な位置関係が変わらないため、コードを再配置可能（位置独立）にすることができます。これは、共有ライブラリや動的ロードされるモジュールで特に重要です。
    *   **対義語**: 絶対アドレス指定（メモリ上の固定された物理アドレスや仮想アドレスを直接指定する方式）。

*   **Go Linker (リンカ)**:
    Goコンパイラによって生成された複数のオブジェクトファイル（`.o` ファイル）を結合し、最終的な実行可能ファイルやライブラリを生成するツールです。シンボルのアドレス解決、外部ライブラリとのリンク、コードの最終的な配置などを行います。Go 1.4以前では、AMD64アーキテクチャ向けのリンカは `6l` と呼ばれていました。現在は `go tool link` コマンドを通じて利用されます。

*   **Windows/amd64 build**:
    Microsoft Windowsオペレーティングシステム上で、AMD64（x86-64）アーキテクチャのCPUをターゲットとしてGoプログラムをビルドすること。Goはクロスコンパイルをサポートしており、異なるOSやアーキテクチャ向けのバイナリを生成できます。

## 技術的詳細

このコミットの核心は、GoリンカのPC相対アドレス指定の変更が、特定のアセンブリコードの挙動に与えた影響とその修正方法にあります。

Goランタイムの `src/pkg/runtime/sys_windows_amd64.s` ファイルには、Windowsのコールバックメカニズムを処理するためのアセンブリコードが含まれています。このコードの一部で、`runtime·cbctxts` というテーブルへのインデックスを計算する処理が行われています。このインデックスは、コールバックが呼び出された際のエントリポイントのアドレスと、`runtime·callbackasm` という特定のアセンブリコードブロックの開始アドレスとの差分に基づいて計算されます。

**問題の発生**:
以前のリンカの挙動では、`$runtime·callbackasm(SB)` のようなシンボル参照は、アセンブリコードが期待する絶対アドレスとして解決されるか、あるいは `SUBQ` 命令のオペランドとして直接使用されても正しく機能していました。
しかし、リンカがPC相対アドレス指定を導入したことで、`$runtime·callbackasm(SB)` がPCからの相対オフセットとして評価されるようになりました。このオフセット値を `SUBQ` 命令の即値オペランドとして直接使用すると、期待される絶対アドレスの減算ではなく、誤ったオフセット値が減算されてしまい、結果として `runtime·cbctxts` テーブルへのインデックス計算が狂ってしまいました。これにより、Windows/amd64環境でのGoランタイムのビルドが失敗するか、正しく動作しなくなりました。

**修正の内容**:
修正は、このアドレス計算を2段階に分けることで、リンカのPC相対アドレス指定の変更の影響を回避しています。

1.  **`MOVQ $runtime·callbackasm(SB), DX`**:
    まず、`runtime·callbackasm(SB)` のアドレス（リンカが解決したその値）を `DX` レジスタに明示的にロードします。`MOVQ` 命令は、シンボルのアドレスをレジスタにロードする際に、リンカがそのシンボルの絶対アドレスを正しく解決するように処理します。これにより、`DX` レジスタには `runtime·callbackasm` の正確な絶対アドレスが格納されます。

2.  **`SUBQ DX, AX`**:
    次に、`AX` レジスタ（コールバックエントリポイントのアドレスが含まれていると推測される）から、`DX` レジスタに格納された `runtime·callbackasm` の絶対アドレスを減算します。

この2段階の操作により、`runtime·callbackasm` のアドレスが確実にレジスタにロードされ、その絶対値が減算に使用されるため、リンカのPC相対アドレス解決の変更がアセンブリコードの意図を壊すことなく、正しいインデックス計算が行われるようになります。

## コアとなるコードの変更箇所

変更は `src/pkg/runtime/sys_windows_amd64.s` ファイルの以下の部分です。

```diff
--- a/src/pkg/runtime/sys_windows_amd64.s
+++ b/src/pkg/runtime/sys_windows_amd64.s
@@ -228,7 +228,8 @@ TEXT runtime·callbackasm1(SB),NOSPLIT,$0
 	ADDQ	$8, SP
 
 	// determine index into runtime·cbctxts table
-	SUBQ	$runtime·callbackasm(SB), AX
+	MOVQ	$runtime·callbackasm(SB), DX
+	SUBQ	DX, AX
 	MOVQ	$0, DX
 	MOVQ	$5, CX	// divide by 5 because each call instruction in runtime·callbacks is 5 bytes long
 	DIVL	CX,
```

## コアとなるコードの解説

このアセンブリコードスニペットは、Windowsのコールバック処理において、`runtime·cbctxts` というテーブルから適切なコンテキスト情報を取得するためのインデックスを計算する部分です。

*   `TEXT runtime·callbackasm1(SB),NOSPLIT,$0` は、`runtime·callbackasm1` という関数の開始を示しています。
*   `ADDQ $8, SP` は、スタックポインタを調整し、スタックフレームをセットアップしている可能性があります。

問題のあった行は、`// determine index into runtime·cbctxts table` のコメントの下にあります。

*   **変更前**:
    ```assembly
    SUBQ	$runtime·callbackasm(SB), AX
    ```
    この命令は、`AX` レジスタの値から `$runtime·callbackasm(SB)` の値を直接減算しようとしていました。`AX` にはコールバックのエントリポイントのアドレスが含まれており、`$runtime·callbackasm(SB)` はGoランタイム内の特定のアセンブリコードブロックの開始アドレスを指します。この減算によって、コールバックエントリポイントが `runtime·callbackasm` の開始点からどれだけ離れているか（オフセット）を計算し、それをインデックスとして利用する意図がありました。
    しかし、リンカのPC相対アドレス指定の変更により、`$runtime·callbackasm(SB)` が即値として扱われる際に、期待される絶対アドレスではなく、PCからの相対オフセットとして解釈されてしまい、計算が狂いました。

*   **変更後**:
    ```assembly
    MOVQ	$runtime·callbackasm(SB), DX
    SUBQ	DX, AX
    ```
    この修正では、計算を2つのステップに分割しています。
    1.  `MOVQ $runtime·callbackasm(SB), DX`: まず、`runtime·callbackasm` のアドレスを `DX` レジスタにロードします。`MOVQ` 命令は、シンボルのアドレスをレジスタにロードする際に、リンカがそのシンボルの絶対アドレスを正しく解決するように処理します。これにより、`DX` には `runtime·callbackasm` の正確な絶対アドレスが格納されます。
    2.  `SUBQ DX, AX`: 次に、`AX` レジスタ（コールバックエントリポイントのアドレス）から、`DX` レジスタに格納された `runtime·callbackasm` の絶対アドレスを減算します。

この変更により、`AX` レジスタには、`runtime·callbackasm` の開始点からコールバックエントリポイントまでの正確なオフセットが格納されるようになります。このオフセットは、その後の `MOVQ $0, DX` と `MOVQ $5, CX`、そして `DIVL CX,` 命令によって、各コール命令のサイズ（5バイト）に基づいて `runtime·cbctxts` テーブルの正確なインデックスに変換されます。

この修正は、GoランタイムがWindows/AMD64環境でコールバックを正しく処理し、ビルドが成功するために不可欠でした。

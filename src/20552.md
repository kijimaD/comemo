このコミットは、Goランタイムのスタック管理に関連する `src/runtime/stack.c` ファイルに対する変更です。具体的には、`adjustframe` 関数におけるクラッシュ発生時のデバッグ情報を強化し、特にARMアーキテクチャでのビルド失敗の原因究明を目的としています。

## 元コミット内容

このコミットは、`adjustframe` 関数がクラッシュした場合に、より詳細なデバッグ情報を出力するように変更を加えるものです。このロジックは、ガベージコレクタの `mgc0.c` にある `scanframe` からコピーされたもので、主にメッセージの追加と、新しい `minsize` コードの導入が含まれています。コミットの目的は、当時のARMビルドの失敗に関するより多くの情報を得るか、あるいは `minsize` の問題であればそれを修正することにありました。

## 変更の背景

Goランタイムは、ゴルーチンのスタックを動的に管理する「連続スタック」モデルを採用しています。これにより、ゴルーチンは小さなスタックで開始し、必要に応じてスタック領域を拡張または縮小できます。このスタックの拡張・縮小時には、スタックフレーム内のポインタを新しいメモリ位置に合わせて調整する必要があります。この調整を行うのが `adjustframe` 関数です。

2014年当時、GoランタイムはARMアーキテクチャでのビルドにおいて、クラッシュや失敗が頻繁に発生していました。これらの問題は、リソースの制約、浮動小数点演算の差異、CGO（C-Go相互運用）の複雑さなど、様々な要因に起因していました。`adjustframe` 関数内でのクラッシュは、スタックポインタの不正確な調整や、ガベージコレクション（GC）がスタック上のポインタを正しく識別できないことに起因する可能性がありました。

このコミットの背景には、これらのARMビルド失敗の原因を特定し、デバッグを容易にするという強い動機がありました。`adjustframe` がクラッシュした際に、より詳細な診断情報を出力することで、問題の根本原因を特定するための手がかりを得ようとしたのです。また、`mgc0.c` の `scanframe` からロジックをコピーしたことは、スタック調整とGCによるスタック走査の間の整合性を高め、ポインタの扱いをより堅牢にすることを目指したことを示唆しています。特に `minsize` の導入は、特定の条件下でのスタックフレームの最小サイズに関する問題を解決するためのものであったと考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **ゴルーチンとスタック管理**: Goのゴルーチンは軽量な実行単位であり、それぞれが独自のスタックを持っています。Goランタイムは、必要に応じてスタックを動的に拡張・縮小する「連続スタック」モデルを採用しています。これにより、スタックオーバーフローを防ぎつつ、メモリ使用量を最適化します。スタックが拡張される際には、古いスタックの内容が新しい大きなスタック領域にコピーされ、スタックフレーム内のポインタが新しいアドレスに「調整」される必要があります。
*   **`adjustframe` 関数**: `src/runtime/stack.c` に存在するこの関数は、ゴルーチンのスタックが成長または縮小する際に、スタックフレーム内のポインタを調整する役割を担います。これは、スタック上のローカル変数や引数に含まれるポインタが、新しいスタックのメモリ位置を正しく参照するように更新することを意味します。
*   **ガベージコレクション (GC) とスタック走査**: Goのガベージコレクタは、ヒープ上の到達可能なオブジェクトを正確に識別するために、ルートセット（グローバル変数、レジスタ、そしてゴルーチンのスタックなど）からポインタを走査します。スタック走査は、ゴルーチンのスタックフレーム内にあるポインタを特定し、それらが参照するヒープオブジェクトを「ライブ」としてマークするプロセスです。
*   **`mgc0.c` と `scanframe`**: `mgc0.c` は、Goランタイムの初期バージョンにおいて、ガベージコレクタの低レベルな部分を実装していたC言語のソースファイルです。`scanframe` 関数は、GCのマークフェーズ中にゴルーチンのスタックフレームを走査し、ヒープに割り当てられたオブジェクトへのポインタを見つける役割を担っていました。このコミットでは、`adjustframe` が `scanframe` のロジックの一部を取り込んでいることが言及されており、スタック調整とGCのポインタ走査の間の連携が重要であることを示しています。
*   **`FUNCDATA_LocalsPointerMaps` と `FUNCDATA_ArgsPointerMaps`**: これらは、GoコンパイラとリンカによってGoバイナリに埋め込まれる `FUNCDATA` (Function Data) ディレクティブの一種です。これらは、関数のローカル変数と引数に関する「ポインタマップ」をガベージコレクタに提供します。これらのマップは、スタックフレーム内のどの位置にヒープオブジェクトへのポインタが含まれているかを正確に示し、GCがライブオブジェクトを正確に識別するために不可欠です。
*   **`PCDATA` と `stackmap`**: `PCDATA` (Program Counter Data) は、プログラムカウンタ (PC) の値と様々な種類のデータを関連付けるためのメカニズムです。`PCDATA_StackMapIndex` は、特定のPC位置におけるスタックマップへのインデックスを提供する `PCDATA` エントリです。`stackmap` は、特定のPC位置における関数のスタックフレーム内のポインタのレイアウトを記述するコンパクトなデータ構造です。GCはこれらのスタックマップを参照して、スタック上のどの値が実際にポインタであり、走査する必要があるかを判断します。

これらの概念は、`adjustframe` がスタック上のポインタを正確に処理し、GCと連携してメモリ安全性を確保するためにどのように機能するかを理解する上で重要です。

## 技術的詳細

このコミットの技術的詳細は、`adjustframe` 関数がスタックフレーム内のポインタを調整する際の堅牢性を高め、デバッグ能力を向上させることにあります。

主な変更点は以下の通りです。

1.  **`minsize` の導入**: `adjustframe` 関数内で、スタックフレームのサイズをチェックするための `minsize` 変数が導入されました。これは、特にARMアーキテクチャのような特定の環境で、スタックフレームが予期せぬ小さなサイズになることによるクラッシュを防ぐためのものです。`thechar` (ターゲットアーキテクチャを示す文字) に応じて `minsize` の値が設定され、スタックフレームの実際のサイズ (`size`) が `minsize` より大きい場合にのみ、ローカル変数の調整ロジックが実行されるようになります。これは、スタックフレームのサイズが小さすぎる場合に、無効なメモリ領域へのアクセスを試みることを防ぐための安全策と考えられます。
    *   `thechar != '6' && thechar != '8'` (つまり、x86/x64以外のアーキテクチャ、例えばARMの場合) は `sizeof(uintptr)` (ポインタのサイズ) を `minsize` とします。
    *   x86/x64の場合は `0` とします。これは、これらのアーキテクチャではスタックフレームの最小サイズに関する特定の制約が少ないか、異なる方法で処理されるためと考えられます。

2.  **詳細なエラーメッセージの追加**: `adjustframe` が `stackmap` 情報を見つけられない場合や、`pcdata` の値が不正な場合に、より詳細なエラーメッセージを `runtime·printf` を使用して出力するようになりました。
    *   ローカル変数の調整 (`FUNCDATA_LocalsPointerMaps` 関連) において、`stackmap` が `nil` または `stackmap->n <= 0` の場合、「`runtime: frame %s untyped locals %p+%p\n`」というメッセージと共に「`missing stackmap`」というエラーで `runtime·throw` するようになりました。これにより、どの関数 (`runtime·funcname(f)`) のどのメモリ範囲 (`(byte*)(frame->varp-size), size`) でスタックマップが欠落しているかを特定できます。
    *   `pcdata` が `stackmap->n` の範囲外である場合、「`runtime: pcdata is %d and %d locals stack map entries for %s (targetpc=%p)\n`」というメッセージと共に「`bad symbol table`」というエラーで `runtime·throw` するようになりました。これにより、`pcdata` の値、スタックマップエントリの数、関数名、ターゲットPCといった詳細な情報が得られます。
    *   引数の調整 (`FUNCDATA_ArgsPointerMaps` 関連) においても同様に、`stackmap` が欠落している場合や `pcdata` が不正な場合に、詳細なエラーメッセージが出力されるようになりました。

3.  **`mgc0.c` の `scanframe` ロジックの適用**: コミットメッセージにあるように、この変更は `mgc0.c` の `scanframe` からロジックをコピーしたものです。これは、ガベージコレクタがスタックを走査する際のポインタ識別ロジックを `adjustframe` にも適用することで、スタック調整時のポインタの扱いをより正確かつ堅牢にすることを目指しています。特に、`bv.n` (BitVectorのビット数) を使用してポインタのサイズを計算し、`adjustpointers` 関数に渡すアドレスを `(byte**)(frame->varp - size)` のように調整している点が、このコピーされたロジックの一部と考えられます。

これらの変更は、`adjustframe` がクラッシュする原因を特定するための診断情報を大幅に増やし、特にARMのような特定のアーキテクチャでのスタック関連の問題のデバッグを容易にすることを目的としています。`minsize` の導入は、特定の条件下でのスタックフレームのサイズに関する潜在的なバグを修正する可能性も秘めています。

## コアとなるコードの解説

このコミットは、`adjustframe` 関数におけるスタックフレームのポインタ調整ロジックを強化し、特にデバッグ情報を充実させることに焦点を当てています。

1.  **`uintptr targetpc, size, minsize;` の追加**:
    *   `adjustframe` 関数のローカル変数に `size` と `minsize` が追加されました。`targetpc` は元々存在していましたが、この行でまとめて宣言されています。
    *   `size` はスタックフレームの実際のサイズを保持するために使用されます。
    *   `minsize` は、スタックフレームが処理されるべき最小のサイズを定義するために導入されました。

2.  **ローカル変数の調整ロジックの変更**:
    *   変更前は `if((byte*)frame->varp != (byte*)frame->sp)` という条件でローカル変数の調整が行われていました。これは `frame->varp` と `frame->sp` が異なる場合に調整を行うというものでした。
    *   変更後は、まず `size = frame->varp - frame->sp;` でスタックフレームのサイズを計算します。
    *   次に、`minsize` の値が設定されます。`thechar` が `'6'` (x86) または `'8'` (x64) でない場合（つまりARMなどの他のアーキテクチャの場合）、`minsize` は `sizeof(uintptr)` に設定されます。それ以外の場合は `0` に設定されます。これは、特定のアーキテクチャでスタックフレームの最小サイズに関する異なる要件があることを示唆しています。
    *   そして、`if(size > minsize)` という条件でローカル変数の調整が行われるようになりました。これにより、スタックフレームが `minsize` よりも小さい場合は、調整処理がスキップされることになります。これは、不正なスタックフレームサイズによるクラッシュを防ぐための重要な安全策です。
    *   `stackmap == nil` または `stackmap->n <= 0` の場合のエラーハンドリングが強化されました。以前は単に「`no locals info`」や「`locals size info only`」というメッセージで `runtime·throw` していましたが、変更後は `runtime·printf` を用いて関数名やメモリ範囲などの詳細な情報を出力し、「`missing stackmap`」というより具体的なエラーメッセージで `runtime·throw` するようになりました。
    *   `pcdata` が `stackmap->n` の範囲外である場合のエラーハンドリングが追加されました。この場合も、`runtime·printf` で `pcdata` の値、スタックマップエントリの数、関数名、ターゲットPCなどの詳細な情報を出力し、「`bad symbol table`」というエラーで `runtime·throw` するようになりました。
    *   `bv = runtime·stackmapdata(stackmap, pcdata);` の後に、`size = (bv.n * PtrSize) / BitsPerPointer;` という行が追加されました。これは、`BitVector` (`bv`) のビット数 (`bv.n`) を基に、ポインタの総サイズを計算し直すものです。これは `mgc0.c` の `scanframe` からコピーされたロジックの一部であり、ポインタの正確な範囲を特定するために使用されます。
    *   `adjustpointers` 関数に渡すアドレスが `(byte**)frame->varp - bv.n / BitsPerPointer` から `(byte**)(frame->varp - size)` に変更されました。これは、計算し直された `size` を使用して、ポインタの開始アドレスをより正確に指定するためのものです。

3.  **引数の調整ロジックの変更**:
    *   引数の調整も同様に、`frame->arglen != 0` から `frame->arglen > 0` に条件が変更されました。意味的には同じですが、より明確な表現です。
    *   `stackmap == nil` の場合のエラーハンドリングが強化されました。ローカル変数と同様に、`runtime·printf` で関数名やメモリ範囲などの詳細な情報を出力し、「`missing stackmap`」というエラーで `runtime·throw` するようになりました。
    *   `pcdata` が `stackmap->n` の範囲外である場合のエラーハンドリングが追加されました。これもローカル変数と同様に、詳細な情報を出力し、「`bad symbol table`」というエラーで `runtime·throw` するようになりました。

これらの変更により、`adjustframe` 関数がスタックフレームのポインタを調整する際に、より厳密なチェックが行われるようになり、エラー発生時にはより豊富な診断情報が提供されるようになりました。特に `minsize` の導入と詳細なエラーメッセージは、当時のARMビルド失敗のようなデバッグが困難な問題の解決に大きく貢献したと考えられます。

## 元コミット内容

Goコンパイラの`cmd/compile`パッケージにおいて、`OCAP`（`cap`組み込み関数）をSSA形式で実装しました。これには、関連する修正と様々なクリーンアップ作業が含まれています。この作業はGopherconでjosharian氏との共同作業として行われました。

## 変更の背景

Go言語の`len`および`cap`組み込み関数は、スライス、配列、文字列、マップ、チャネルなどの長さを取得するために使用されます。特にスライスにおいては、`len`が現在の要素数を返し、`cap`が基底配列の最大容量を返します。コンパイラがこれらの操作を効率的に処理し、可能な限り最適化されたコードを生成するためには、コンパイラの内部表現（特にSSA形式）でこれらの概念を正確にモデル化する必要があります。

このコミット以前は、`len`関数はSSAで処理されていましたが、`cap`関数はSSAバックエンドで明示的にサポートされていなかった可能性があります。SSAはプログラムのデータフローを明確にし、より高度な最適化を可能にするため、`cap`のような基本的な操作もSSA形式で表現することが望ましいです。これにより、コンパイラは`cap`の値を利用した境界チェックの最適化や、不要な計算の削除など、より多くの最適化を適用できるようになります。

また、Goの`len`や`cap`は`int`型を返しますが、コンパイラの内部では`uintptr`（ポインタサイズに合わせた符号なし整数）として扱われることがありました。このコミットでは、`len`と`cap`の戻り値の型をSSA内部で`int`型に統一することで、よりGo言語のセマンティクスに近づけ、コンパイラの型システムの一貫性を向上させています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、ソースコードを機械語に変換する過程で複数のステージを経ます。主要なステージには以下が含まれます。

1.  **パーシングとAST生成**: ソースコードを解析し、抽象構文木（AST）を生成します。
2.  **型チェックとセマンティック解析**: ASTに対して型チェックを行い、意味的な正しさを検証します。
3.  **中間表現（IR）生成**: ASTをより低レベルの中間表現に変換します。Goコンパイラでは、初期のIRとして「汎用ノード（Generic Nodes）」が使われ、その後SSA形式に変換されます。
4.  **SSA（Static Single Assignment）フォーム**: プログラムの各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析が容易になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの高度な最適化が可能になります。
5.  **バックエンドコード生成**: SSA形式から特定アーキテクチャの機械語コードを生成します。

### `len`と`cap`組み込み関数

*   **`len(v)`**: `v`の長さ（要素数）を返します。
    *   配列: 配列の要素数。
    *   スライス: スライスの現在の要素数。
    *   文字列: 文字列のバイト数。
    *   マップ: マップ内のキーと値のペアの数。
    *   チャネル: チャネル内のキューに入れられた要素の数。
*   **`cap(v)`**: `v`の容量を返します。
    *   配列: 配列の要素数（`len`と同じ）。
    *   スライス: スライスが参照する基底配列の最大容量。スライスを拡張できる最大値を示します。

これらの関数はGo言語の基本的な操作であり、コンパイラはこれらを効率的に処理する必要があります。

### `Type`構造体と`Bound`フィールド

Goコンパイラの内部では、`Type`構造体がGo言語の型情報を表現します。`TARRAY`は配列型を表す`Etype`（基本型）の一つです。`Bound`フィールドは、配列のサイズやスライスの特性を格納するために使用されます。このコミットの変更前は、`Bound`が負の値の場合に「動的配列」とコメントされていましたが、これは実質的にスライスを指していました。このコミットで「スライス」と明示的にコメントが修正され、`IsSlice()`ヘルパー関数が導入されました。

### `ssa.OpSliceLen`と`ssa.OpSliceCap`

SSA形式では、各操作が特定の「オペレーション（Op）」として表現されます。
*   `ssa.OpSliceLen`: スライスの長さを取得するSSAオペレーション。
*   `ssa.OpSliceCap`: スライスの容量を取得するSSAオペレーション。
これらのオペレーションは、SSAバックエンドがスライスの`len`や`cap`呼び出しをどのように処理するかを定義します。

## 技術的詳細

このコミットの主要な技術的変更点は、GoコンパイラのSSAバックエンドが`cap`組み込み関数を認識し、適切に処理できるようにしたことです。

1.  **`OCAP`の導入**: `cmd/compile/internal/gc/ssa.go`の`expr`関数内で、`OLEN`（`len`組み込み関数）を処理する`case`に`OCAP`（`cap`組み込み関数）が追加されました。これにより、コンパイラは`cap`呼び出しをSSA形式に変換する際に、`ssa.OpSliceCap`という新しいSSAオペレーションを生成するようになります。
2.  **スライス判定の改善**:
    *   `src/cmd/compile/internal/gc/go.go`で、`Type`構造体の`Bound`フィールドに関するコメントが「negative is dynamic array」から「negative is slice」に修正され、スライスが`Bound < 0`で表現されることが明確化されました。
    *   `src/cmd/compile/internal/gc/type.go`に`func (t *Type) IsSlice() bool { return t.Etype == TARRAY && t.Bound < 0 }`というヘルパー関数が追加されました。これにより、`ssa.go`内でスライスであるかどうかの判定がより簡潔かつ意図が明確になりました。
3.  **`len`/`cap`の戻り値型の一貫性**:
    *   `src/cmd/compile/internal/ssa/config.go`に`Int Type`フィールドが追加され、コンパイラのSSA設定でプラットフォームに応じた`int`型（`TypeInt32`または`TypeInt64`）が利用可能になりました。
    *   `ssa.go`の`OLEN`/`OCAP`処理において、`len`や`cap`の戻り値の型が`s.config.Uintptr`から`s.config.Int`に変更されました。これは、Go言語の仕様で`len`や`cap`が`int`型を返すことに合わせて、SSA内部での型表現を統一するものです。これにより、型変換のオーバーヘッドが減少し、コンパイラの型システムがより正確になります。
4.  **`OEMPTY`ステートメントの処理**: `ssa.go`の`stmt`関数に`case OEMPTY:`が追加されました。これは、空のステートメントがSSA生成時に適切に処理されるようにするためのクリーンアップであり、潜在的なバグを防ぎ、コンパイラの堅牢性を高めます。
5.  **文字列処理の改善**: `ssa.go`で`strings.HasSuffix`が導入され、関数名のサフィックスチェックがより安全かつ読みやすくなりました。

これらの変更により、Goコンパイラは`cap`組み込み関数をSSA形式で効率的に処理できるようになり、結果として生成される機械語コードの品質と最適化の機会が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/go.go` の変更

`Type`構造体の`Bound`フィールドのコメントが「negative is dynamic array」から「negative is slice」に変更されました。これは、Goコンパイラ内部で`TARRAY`型の`Bound`が負の値を持つ場合に、それが動的配列ではなくスライスを意味するという、より正確なセマンティクスを反映しています。この変更自体は機能的なものではなく、コードの可読性と意図の明確化を目的としています。

### `src/cmd/compile/internal/gc/ssa.go` の変更

1.  **`strings`パッケージのインポートと利用**: `strings`パッケージがインポートされ、`buildssa`関数内の`_ssa`サフィックスチェックが`len(name) > 4 && name[len(name)-4:] == "_ssa"`から`strings.HasSuffix(name, "_ssa")`に変更されました。これは、より慣用的で堅牢な文字列操作に置き換えるためのクリーンアップです。
2.  **`OEMPTY`ステートメントの追加**: `stmt`関数に`case OEMPTY:`が追加されました。これは、Go言語の空のステートメント（例: `;`）がSSA生成時に適切に処理されるようにするためのものです。これにより、コンパイラが予期しない動作をする可能性が低減されます。
3.  **`OLEN`, `OCAP`の統合と型の一貫性**:
    *   `OLEN`を処理していた`case`に`OCAP`が追加され、`len`と`cap`の両方がこのブロックで処理されるようになりました。
    *   `n.Left.Type.Bound < 0`という直接的なチェックの代わりに、新しく導入された`n.Left.Type.IsSlice()`ヘルパー関数が使用され、スライス判定のロジックが抽象化され、読みやすくなりました。
    *   `OCAP`の場合には`ssa.OpSliceCap`オペレーションが、`OLEN`の場合には`ssa.OpSliceLen`オペレーションが生成されるように分岐が追加されました。
    *   最も重要な変更点として、`len`、`cap`、および配列の長さ（`Bound`）を返すSSA値の型が`s.config.Uintptr`から`s.config.Int`に変更されました。これは、Go言語の仕様でこれらの関数が`int`型を返すことに合わせて、SSA内部での型表現を統一し、コンパイラの型システムの一貫性を向上させるものです。
4.  **`OINDEX`（インデックスアクセス）のロジック改善**: `OINDEX`の処理において、スライスと配列のインデックスアクセスロジックが`n.Left.Type.IsSlice()`を使って明確に分離されました。これにより、コードの意図がより明確になり、将来的なメンテナンスが容易になります。機能的には大きな変更はありませんが、構造が改善されています。

### `src/cmd/compile/internal/gc/type.go` の変更

`func (t *Type) IsSlice() bool`という新しいメソッドが`Type`構造体に追加されました。このメソッドは、`Etype`が`TARRAY`であり、かつ`Bound`が負の値である場合に`true`を返します。これは、Goコンパイラ内部でスライス型を識別するための標準的かつ簡潔な方法を提供し、`ssa.go`のような他のファイルでのスライス判定ロジックを簡素化します。

### `src/cmd/compile/internal/ssa/config.go` の変更

1.  **`Int Type`フィールドの追加**: `Config`構造体に`Int Type`という新しいフィールドが追加されました。このフィールドは、SSAバックエンドがGoの`int`型を表現するために使用するSSA型をキャッシュします。
2.  **`Int`フィールドの初期化**: `NewConfig`関数内で、`c.Int`フィールドがプラットフォームのポインタサイズ（`ptrSize`）に基づいて`TypeInt32`または`TypeInt64`に初期化されます。これにより、SSAバックエンドは、`len`や`cap`のような組み込み関数が返す`int`型を、ターゲットアーキテクチャに適したサイズで一貫して参照できるようになります。この変更は、`ssa.go`での`len`/`cap`の戻り値型を`s.config.Int`に変更する基盤となります。

これらの変更は、GoコンパイラのSSAバックエンドが`cap`組み込み関数を正確かつ効率的に処理できるようにするための重要なステップであり、コンパイラの内部型システムの一貫性と堅牢性を向上させます。

## 変更の背景

Go言語の`len`および`cap`組み込み関数は、スライス、配列、文字列、マップ、チャネルなどの長さを取得するために使用されます。特にスライスにおいては、`len`が現在の要素数を返し、`cap`が基底配列の最大容量を返します。コンパイラがこれらの操作を効率的に処理し、可能な限り最適化されたコードを生成するためには、コンパイラの内部表現（特にSSA形式）でこれらの概念を正確にモデル化する必要があります。

このコミット以前は、`len`関数はSSAで処理されていましたが、`cap`関数はSSAバックエンドで明示的にサポートされていなかった可能性があります。SSAはプログラムのデータフローを明確にし、より高度な最適化を可能にするため、`cap`のような基本的な操作もSSA形式で表現することが望ましいです。これにより、コンパイラは`cap`の値を利用した境界チェックの最適化や、不要な計算の削除など、より多くの最適化を適用できるようになります。

また、Goの`len`や`cap`は`int`型を返しますが、コンパイラの内部では`uintptr`（ポインタサイズに合わせた符号なし整数）として扱われることがありました。このコミットでは、`len`と`cap`の戻り値の型をSSA内部で`int`型に統一することで、よりGo言語のセマンティクスに近づけ、コンパイラの型システムの一貫性を向上させています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、ソースコードを機械語に変換する過程で複数のステージを経ます。主要なステージには以下が含まれます。

1.  **パーシングとAST生成**: ソースコードを解析し、抽象構文木（AST）を生成します。
2.  **型チェックとセマンティック解析**: ASTに対して型チェックを行い、意味的な正しさを検証します。
3.  **中間表現（IR）生成**: ASTをより低レベルの中間表現に変換します。Goコンパイラでは、初期のIRとして「汎用ノード（Generic Nodes）」が使われ、その後SSA形式に変換されます。
4.  **SSA（Static Single Assignment）フォーム**: プログラムの各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析が容易になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの高度な最適化が可能になります。
5.  **バックエンドコード生成**: SSA形式から特定アーキテクチャの機械語コードを生成します。

### `len`と`cap`組み込み関数

*   **`len(v)`**: `v`の長さ（要素数）を返します。
    *   配列: 配列の要素数。
    *   スライス: スライスの現在の要素数。
    *   文字列: 文字列のバイト数。
    *   マップ: マップ内のキーと値のペアの数。
    *   チャネル: チャネル内のキューに入れられた要素の数。
*   **`cap(v)`**: `v`の容量を返します。
    *   配列: 配列の要素数（`len`と同じ）。
    *   スライス: スライスが参照する基底配列の最大容量。スライスを拡張できる最大値を示します。

これらの関数はGo言語の基本的な操作であり、コンパイラはこれらを効率的に処理する必要があります。

### `Type`構造体と`Bound`フィールド

Goコンパイラの内部では、`Type`構造体がGo言語の型情報を表現します。`TARRAY`は配列型を表す`Etype`（基本型）の一つです。`Bound`フィールドは、配列のサイズやスライスの特性を格納するために使用されます。このコミットの変更前は、`Bound`が負の値の場合に「動的配列」とコメントされていましたが、これは実質的にスライスを指していました。このコミットで「スライス」と明示的にコメントが修正され、`IsSlice()`ヘルパー関数が導入されました。

### `ssa.OpSliceLen`と`ssa.OpSliceCap`

SSA形式では、各操作が特定の「オペレーション（Op）」として表現されます。
*   `ssa.OpSliceLen`: スライスの長さを取得するSSAオペレーション。
*   `ssa.OpSliceCap`: スライスの容量を取得するSSAオペレーション。
これらのオペレーションは、SSAバックエンドがスライスの`len`や`cap`呼び出しをどのように処理するかを定義します。

## 技術的詳細

このコミットの主要な技術的変更点は、GoコンパイラのSSAバックエンドが`cap`組み込み関数を認識し、適切に処理できるようにしたことです。

1.  **`OCAP`の導入**: `cmd/compile/internal/gc/ssa.go`の`expr`関数内で、`OLEN`（`len`組み込み関数）を処理する`case`に`OCAP`（`cap`組み込み関数）が追加されました。これにより、コンパイラは`cap`呼び出しをSSA形式に変換する際に、`ssa.OpSliceCap`という新しいSSAオペレーションを生成するようになります。
2.  **スライス判定の改善**:
    *   `src/cmd/compile/internal/gc/go.go`で、`Type`構造体の`Bound`フィールドに関するコメントが「negative is dynamic array」から「negative is slice」に修正され、スライスが`Bound < 0`で表現されることが明確化されました。
    *   `src/cmd/compile/internal/gc/type.go`に`func (t *Type) IsSlice() bool { return t.Etype == TARRAY && t.Bound < 0 }`というヘルパー関数が追加されました。これにより、`ssa.go`内でスライスであるかどうかの判定がより簡潔かつ意図が明確になりました。
3.  **`len`/`cap`の戻り値型の一貫性**:
    *   `src/cmd/compile/internal/ssa/config.go`に`Int Type`フィールドが追加され、コンパイラのSSA設定でプラットフォームに応じた`int`型（`TypeInt32`または`TypeInt64`）が利用可能になりました。
    *   `ssa.go`の`OLEN`/`OCAP`処理において、`len`や`cap`の戻り値の型が`s.config.Uintptr`から`s.config.Int`に変更されました。これは、Go言語の仕様で`len`や`cap`が`int`型を返すことに合わせて、SSA内部での型表現を統一するものです。これにより、型変換のオーバーヘッドが減少し、コンパイラの型システムがより正確になります。
4.  **`OEMPTY`ステートメントの処理**: `ssa.go`の`stmt`関数に`case OEMPTY:`が追加されました。これは、Go言語の空のステートメント（例: `;`）がSSA生成時に適切に処理されるようにするためのものです。これにより、コンパイラが予期しない動作をする可能性が低減されます。
5.  **文字列処理の改善**: `ssa.go`で`strings.HasSuffix`が導入され、関数名のサフィックスチェックがより安全かつ読みやすくなりました。

これらの変更により、Goコンパイラは`cap`組み込み関数をSSA形式で効率的に処理できるようになり、結果として生成される機械語コードの品質と最適化の機会が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/go.go` の変更

`Type`構造体の`Bound`フィールドのコメントが「negative is dynamic array」から「negative is slice」に変更されました。これは、Goコンパイラ内部で`TARRAY`型の`Bound`が負の値を持つ場合に、それが動的配列ではなくスライスを意味するという、より正確なセマンティクスを反映しています。この変更自体は機能的なものではなく、コードの可読性と意図の明確化を目的としています。

### `src/cmd/compile/internal/gc/ssa.go` の変更

1.  **`strings`パッケージのインポートと利用**: `strings`パッケージがインポートされ、`buildssa`関数内の`_ssa`サフィックスチェックが`len(name) > 4 && name[len(name)-4:] == "_ssa"`から`strings.HasSuffix(name, "_ssa")`に変更されました。これは、より慣用的で堅牢な文字列操作に置き換えるためのクリーンアップです。
2.  **`OEMPTY`ステートメントの追加**: `stmt`関数に`case OEMPTY:`が追加されました。これは、Go言語の空のステートメント（例: `;`）がSSA生成時に適切に処理されるようにするためのものです。これにより、コンパイラが予期しない動作をする可能性が低減されます。
3.  **`OLEN`, `OCAP`の統合と型の一貫性**:
    *   `OLEN`を処理していた`case`に`OCAP`が追加され、`len`と`cap`の両方がこのブロックで処理されるようになりました。
    *   `n.Left.Type.Bound < 0`という直接的なチェックの代わりに、新しく導入された`n.Left.Type.IsSlice()`ヘルパー関数が使用され、スライス判定のロジックが抽象化され、読みやすくなりました。
    *   `OCAP`の場合には`ssa.OpSliceCap`オペレーションが、`OLEN`の場合には`ssa.OpSliceLen`オペレーションが生成されるように分岐が追加されました。
    *   最も重要な変更点として、`len`、`cap`、および配列の長さ（`Bound`）を返すSSA値の型が`s.config.Uintptr`から`s.config.Int`に変更されました。これは、Go言語の仕様でこれらの関数が`int`型を返すことに合わせて、SSA内部での型表現を統一し、コンパイラの型システムの一貫性を向上させるものです。
4.  **`OINDEX`（インデックスアクセス）のロジック改善**: `OINDEX`の処理において、スライスと配列のインデックスアクセスロジックが`n.Left.Type.IsSlice()`を使って明確に分離されました。これにより、コードの意図がより明確になり、将来的なメンテナンスが容易になります。機能的には大きな変更はありませんが、構造が改善されています。

### `src/cmd/compile/internal/gc/type.go` の変更

`func (t *Type) IsSlice() bool`という新しいメソッドが`Type`構造体に追加されました。このメソッドは、`Etype`が`TARRAY`であり、かつ`Bound`が負の値である場合に`true`を返します。これは、Goコンパイラ内部でスライス型を識別するための標準的かつ簡潔な方法を提供し、`ssa.go`のような他のファイルでのスライス判定ロジックを簡素化します。

### `src/cmd/compile/internal/ssa/config.go` の変更

1.  **`Int Type`フィールドの追加**: `Config`構造体に`Int Type`という新しいフィールドが追加されました。このフィールドは、SSAバックエンドがGoの`int`型を表現するために使用するSSA型をキャッシュします。
2.  **`Int`フィールドの初期化**: `NewConfig`関数内で、`c.Int`フィールドがプラットフォームのポインタサイズ（`ptrSize`）に基づいて`TypeInt32`または`TypeInt64`に初期化されます。これにより、SSAバックエンドは、`len`や`cap`のような組み込み関数が返す`int`型を、ターゲットアーキテクチャに適したサイズで一貫して参照できるようになります。この変更は、`ssa.go`での`len`/`cap`の戻り値型を`s.config.Int`に変更する基盤となります。

これらの変更は、GoコンパイラのSSAバックエンドが`cap`組み込み関数を正確かつ効率的に処理できるようにするための重要なステップであり、コンパイラの内部型システムの一貫性と堅牢性を向上させます。

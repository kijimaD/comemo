# [インデックス 26362] ファイルの概要

このコミットは、Goコンパイラのビルドプロセスに関連する`src/cmd/go/build.go`ファイル内の変更です。具体的には、`go`コマンドがGCCコンパイラが`-no-pie`オプションをサポートしているかどうかを検出する方法を修正しています。

## コミット

このコミットは、`cmd/go`ツールが古いGCCバージョン（特にGCC 4.4および4.5）で`-no-pie`オプションのサポートを誤って検出する問題を修正します。これらの古いGCCバージョンは、認識できないオプションが渡された場合でも終了コード0を返すことがあり、`go`コマンドが`-no-pie`がサポートされていると誤解していました。この修正により、GCCの出力に「unrecognized」という文字列が含まれているかどうかをチェックすることで、より堅牢な検出が可能になります。

## 変更の背景

Goのビルドシステムは、実行可能ファイルをリンクする際に、Position-Independent Executable (PIE) の生成を制御するためにGCCの`-no-pie`オプションを使用するかどうかを決定する必要があります。PIEはセキュリティ機能であり、実行可能ファイルがメモリ内の任意のアドレスにロードされることを可能にし、Address Space Layout Randomization (ASLR) と組み合わせて、特定の種類の攻撃を困難にします。しかし、一部のシナリオや古いシステムでは、PIEを無効にするために`-no-pie`オプションが必要になることがあります。

`cmd/go`ツールは、`gccSupportsNoPie`関数を通じて、現在使用されているGCCコンパイラがこの`-no-pie`オプションをサポートしているかどうかをテストします。このテストは、GCCに`-no-pie`オプションを渡して実行し、その終了コードをチェックすることで行われていました。

問題は、GCCのバージョンによって、認識できないオプションが渡されたときの動作が異なることでした。
*   GCC 4.8以降の新しいバージョンでは、認識できないオプションが渡されると終了コード1（エラー）を返します。これは期待される動作であり、`go`コマンドは`-no-pie`がサポートされていないと正しく判断できます。
*   しかし、GCC 4.4および4.5のような古いバージョンでは、認識できないオプションが渡されても終了コード0（成功）を返していました。このため、`go`コマンドは`-no-pie`オプションがサポートされていると誤って判断し、実際にはサポートされていない環境でそのオプションを使用しようとして、ビルドエラーや予期せぬ動作を引き起こす可能性がありました。

この誤った検出が、Goのビルドプロセスにおけるバグ（Issue #13937）として報告され、このコミットによって修正されました。

## 前提知識の解説

### Position-Independent Executable (PIE) と `-no-pie`

*   **PIE (Position-Independent Executable)**: PIEは、実行可能ファイルがメモリ内の任意のアドレスにロードできる形式でコンパイルおよびリンクされることを意味します。これは、ASLR（Address Space Layout Randomization）というセキュリティ機能と組み合わせて使用され、プログラムのメモリレイアウトをランダム化することで、バッファオーバーフローなどの脆弱性を悪用する攻撃者が特定のコードやデータを予測可能なアドレスに配置することを困難にします。現代のLinuxディストリビューションでは、セキュリティ向上のためPIEがデフォルトで有効になっていることが多いです。
*   **`-no-pie`オプション**: このオプションは、リンカに対してPIEではない実行可能ファイルを生成するように指示します。つまり、実行可能ファイルは固定されたメモリアドレスにロードされることになります。これは、古いシステムとの互換性、特定のデバッグツールやプロファイリングツールとの連携、あるいはわずかなパフォーマンスオーバーヘッドを避けるために使用されることがあります。

### GCCの終了コード

Unix/Linuxシステムでは、プログラムが終了する際に終了コード（exit code）を返します。
*   **終了コード0**: 通常、プログラムが正常に終了したことを示します。
*   **終了コード1以上**: 通常、プログラムの実行中にエラーが発生したことを示します。

`cmd/go`は、GCCが`-no-pie`オプションを認識するかどうかを判断するために、この終了コードを利用していました。しかし、前述のように、古いGCCバージョンでは認識できないオプションに対しても終了コード0を返すという、この慣例に反する動作がありました。

### `exec.Command`と`CombinedOutput`

Go言語の`os/exec`パッケージは、外部コマンドを実行するための機能を提供します。
*   `exec.Command(name string, arg ...string)`: 実行するコマンドと引数を指定して`Cmd`構造体を作成します。
*   `cmd.Run()`: コマンドを実行し、コマンドが正常に終了した場合は`nil`を、エラーが発生した場合は`error`を返します。このメソッドは、コマンドの標準出力と標準エラー出力を破棄します。
*   `cmd.CombinedOutput()`: コマンドを実行し、その標準出力と標準エラー出力を結合したバイトスライスとして返します。コマンドが正常に終了した場合は`nil`を、エラーが発生した場合は`error`を返します。このメソッドは、コマンドの出力内容を検査する必要がある場合に特に有用です。

このコミットでは、`cmd.Run()`から`cmd.CombinedOutput()`への変更が、GCCの出力内容を検査するために重要となります。

## 技術的詳細

このコミットの核心は、`cmd/go`がGCCの`-no-pie`サポートを検出するロジックを改善することにあります。以前は、`gccSupportsNoPie`関数は以下のロジックを使用していました。

1.  GCCに`-no-pie`オプションを渡して実行する。
2.  `cmd.Run()`を呼び出し、その戻り値のエラーが`nil`であるかどうか（つまり、終了コードが0であるかどうか）をチェックする。
3.  エラーが`nil`であれば、`-no-pie`がサポートされていると判断する。

このロジックは、GCC 4.8のように認識できないオプションに対して終了コード1を返すバージョンでは正しく機能しました。しかし、GCC 4.4や4.5のように認識できないオプションに対しても終了コード0を返すバージョンでは、誤った肯定（false positive）を引き起こしました。

新しいロジックでは、この問題を解決するために以下の変更が導入されました。

1.  `cmd.Run()`の代わりに`cmd.CombinedOutput()`を使用します。これにより、GCCコマンドの標準出力と標準エラー出力の両方をキャプチャできるようになります。
2.  コマンドの実行結果のエラーが`nil`であること（`err == nil`）に加えて、キャプチャした出力（`out`）に「unrecognized」という文字列が含まれていないこと（`!bytes.Contains(out, []byte("unrecognized"))`）をチェックします。

この二重のチェックにより、GCCが`-no-pie`オプションを認識しない場合でも終了コード0を返すような古いバージョンであっても、その出力に「unrecognized option」のような警告メッセージが含まれていれば、`go`コマンドは`-no-pie`がサポートされていないと正しく判断できるようになります。これにより、`cmd/go`のビルドプロセスがより堅牢になり、様々なGCCバージョンとの互換性が向上します。

## コアとなるコードの解説

変更は`src/cmd/go/build.go`ファイルの`gccSupportsNoPie`関数内で行われています。

*   **変更前**:
    ```go
    err := cmd.Run()
    return err == nil
    ```
    ここでは、`cmd.Run()`を呼び出してGCCコマンドを実行し、その結果としてエラーが返されなかった場合（`err == nil`）にのみ、`-no-pie`オプションがサポートされていると判断していました。これは、GCCが認識できないオプションに対して常に非ゼロの終了コードを返すという前提に基づいています。

*   **変更後**:
    ```go
    out, err := cmd.CombinedOutput()
    return err == nil && !bytes.Contains(out, []byte("unrecognized"))
    ```
    1.  `cmd.Run()`が`cmd.CombinedOutput()`に置き換えられました。これにより、GCCコマンドの標準出力と標準エラー出力が`out`変数にキャプチャされます。
    2.  戻り値の条件が`err == nil`だけでなく、`!bytes.Contains(out, []byte("unrecognized"))`が追加されました。これは、キャプチャされた出力`out`の中にバイトスライス`[]byte("unrecognized")`（つまり文字列「unrecognized」）が含まれていないことを確認するものです。

この修正により、GCCが`-no-pie`オプションを認識しない場合でも終了コード0を返すような状況（古いGCCバージョンで発生）において、`go`コマンドはGCCの出力内容を検査することで、オプションが実際にサポートされていないことを正確に検出できるようになります。これにより、`go`コマンドは`-no-pie`オプションのサポート状況をより確実に判断し、適切なビルドフラグを使用できるようになります。

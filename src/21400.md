# [インデックス 21400] ファイルの概要

このコミットは、GoランタイムのCGO（C Foreign Function Interface）実装に関連するファイル、具体的にはOpenBSDオペレーティングシステム上の386およびAMD64アーキテクチャ向けの`src/runtime/cgo/gcc_openbsd_386.c`と`src/runtime/cgo/gcc_openbsd_amd64.c`に変更を加えています。これらのファイルは、GoプログラムがC言語のライブラリと連携する際に、システムコールである`pthread_create`を適切にラップするためのロジックを含んでいます。

Author: Shenghou Ma <minux@golang.org>
Date:   Wed Dec 31 20:30:57 2014 -0500

    runtime/cgo: initialize our pthread_create wrapper earlier on openbsd
    
    This is a genuine bug exposed by our test for issue 9456: our wrapper
    for pthread_create is not initialized until we initialize cgo itself,
    but it is possible that a static constructor could call pthread_create,
    and in that case, it will be calling a nil function pointer.
    
    Fix that by also initializing the sys_pthread_create function pointer
    inside our pthread_create wrapper function, and use a pthread_once to
    make sure it is only initialized once.
    
    Fix build for openbsd.

## 元コミット内容

このコミットは、OpenBSDにおけるGoランタイムのCGO部分で発見されたバグを修正します。このバグは、`pthread_create`のGoラッパーがCGO自体の初期化が完了するまで適切に初期化されないために発生していました。その結果、静的コンストラクタ（`main`関数が実行される前に呼び出されるコード）が`pthread_create`を呼び出すと、ラッパー内の関数ポインタが`nil`であるためにクラッシュする可能性がありました。

この問題を解決するため、`sys_pthread_create`関数ポインタの初期化を`pthread_create`ラッパー関数内でより早期に行うように変更されました。初期化が一度だけ行われることを保証するために`pthread_once`が使用されています。また、OpenBSDでのビルドの問題も修正されました。

## 変更の背景

この変更の背景には、GoランタイムのCGO部分における`pthread_create`のラッパー関数の初期化タイミングに関する潜在的な競合状態とバグが存在していました。

GoプログラムがC言語のコードを呼び出す際（CGOを使用する場合）、Goランタイムはシステムコールや標準ライブラリ関数の一部をラップすることがあります。`pthread_create`もその一つで、Goの内部的なスレッド管理とCライブラリのスレッド作成を橋渡しするためにラッパーが提供されています。

問題は、この`pthread_create`ラッパーが内部的に使用する実際のシステム`pthread_create`関数のポインタ（`sys_pthread_create`）が、CGO全体の初期化プロセスの一部として設定されていた点にありました。しかし、C++などの言語で書かれたライブラリがGoプログラムにリンクされている場合、それらのライブラリは「静的コンストラクタ」を持つことがあります。静的コンストラクタは、`main`関数が実行されるよりも前に、プログラムの起動時に自動的に実行される特殊な関数です。

もし、静的コンストラクタが実行されるタイミングで`pthread_create`を呼び出す必要があった場合、その時点ではGoランタイムのCGO初期化がまだ完了しておらず、`sys_pthread_create`が`nil`（または未初期化）のままになっている可能性がありました。`nil`の関数ポインタを呼び出そうとすると、プログラムはセグメンテーション違反などの致命的なエラーでクラッシュします。

このバグは、コミットメッセージに「issue 9456のテストによって露呈した」と記載されており、特定のテストケースがこの初期化タイミングの問題を再現したことを示しています。この修正は、このような早期の`pthread_create`呼び出しでも安全に処理できるようにするために不可欠でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の技術的な概念を把握しておく必要があります。

*   **CGO (C Foreign Function Interface)**:
    Go言語の機能の一つで、GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を扱ったりするための仕組みです。GoとCの間の相互運用を可能にします。Goランタイムは、CGOを介してCライブラリと連携する際に、システムコールの一部をラップしてGoの実行モデルに適合させることがあります。

*   **`pthread_create`**:
    POSIXスレッド（pthreads）ライブラリの一部であり、新しいスレッドを作成するための標準的なC言語関数です。この関数は、新しいスレッドの属性、開始ルーチン（新しいスレッドで実行される関数）、およびそのルーチンに渡される引数を指定します。

*   **`dlopen` と `dlsym`**:
    これらは、Unix系システムで動的リンクライブラリ（共有ライブラリ、例: `.so`ファイル）をプログラムの実行時にロードし、そのライブラリ内のシンボル（関数や変数）のアドレスを取得するための関数です。
    *   `dlopen(filename, flags)`: 指定された`filename`の共有ライブラリをロードします。成功すると、ライブラリへのハンドルを返します。
    *   `dlsym(handle, symbol_name)`: `dlopen`で取得した`handle`を使ってロードされたライブラリから、指定された`symbol_name`のアドレスを探して返します。
    Goランタイムは、システムにインストールされている`libpthread.so`から`pthread_create`関数の実際のアドレスを動的に取得するためにこれらを使用します。

*   **`pthread_once`**:
    pthreadsライブラリが提供するメカニズムで、特定の初期化ルーチンがプロセス内で一度だけ実行されることを保証します。これは、マルチスレッド環境で共有リソースの初期化を安全に行うためによく使用されます。
    *   `pthread_once_t`型の変数を`PTHREAD_ONCE_INIT`で初期化し、`pthread_once(&once_control, init_routine)`のように呼び出します。`init_routine`は、`pthread_once`が初めて呼び出されたときに一度だけ実行されます。

*   **静的コンストラクタ (Static Constructors)**:
    C++などの言語において、グローバルスコープで定義されたオブジェクトや変数が`main`関数が実行されるよりも前に初期化される際に呼び出される特殊な関数です。これらのコンストラクタは、プログラムの起動時に自動的に実行され、ライブラリの初期設定やグローバルなデータ構造の準備などを行います。GoプログラムがC/C++ライブラリをCGO経由で利用する場合、これらのライブラリに含まれる静的コンストラクタがGoランタイムの初期化と並行して、あるいはそれよりも早く実行される可能性があります。

*   **nil関数ポインタ**:
    関数を指し示すポインタが、有効な関数のアドレスではなく、`nil`（C言語では`NULL`）を指している状態です。このようなポインタを介して関数を呼び出そうとすると、通常は未定義の動作となり、多くの場合、プログラムのクラッシュ（セグメンテーション違反など）を引き起こします。

これらの概念は、GoランタイムがどのようにCライブラリと連携し、マルチスレッド環境での安全な初期化をどのように保証しようとしているかを理解する上で重要です。

## 技術的詳細

このコミットが修正する技術的な問題は、GoランタイムがOpenBSD上で`pthread_create`システムコールをラップする際の初期化順序の不備にありました。

**問題の核心**:
Goランタイムは、CGOを介してCライブラリと連携する際に、システム提供の`pthread_create`関数を直接呼び出すのではなく、その呼び出しをGoランタイムが制御するラッパー関数を介して行います。このラッパー関数は、実際のシステム`pthread_create`関数のアドレスを`sys_pthread_create`という関数ポインタに格納し、それを利用してシステムコールを実行します。

従来のコードでは、この`sys_pthread_create`ポインタの初期化（`dlopen`と`dlsym`を使って`libpthread.so`から`pthread_create`のアドレスを取得する処理）は、`x_cgo_init`というCGO全体の初期化ルーチンの中で行われていました。

しかし、C/C++ライブラリがGoプログラムにリンクされている場合、それらのライブラリに含まれる静的コンストラクタは、Goランタイムの`x_cgo_init`が実行されるよりも前に呼び出される可能性があります。もし、この静的コンストラクタの内部で何らかの理由でスレッドが作成され（つまり`pthread_create`が呼び出され）た場合、Goの`pthread_create`ラッパーが呼び出されます。この時点では`sys_pthread_create`ポインタはまだ初期化されておらず、`nil`のままです。結果として、`nil`の関数ポインタを呼び出そうとしてプログラムがクラッシュするというバグが発生していました。

**解決策**:
このコミットは、`sys_pthread_create`ポインタの初期化を、`pthread_create`ラッパー関数自体の中で行うように変更することで問題を解決しました。

1.  **`init_pthread_wrapper`関数の導入**: `dlopen`と`dlsym`を使って`sys_pthread_create`を初期化するロジックを`static void init_pthread_wrapper(void)`という新しい関数に分離しました。
2.  **`pthread_once`の利用**: `static pthread_once_t init_pthread_wrapper_once = PTHREAD_ONCE_INIT;`という制御変数を導入し、`pthread_create`ラッパー関数の冒頭で`pthread_once(&init_pthread_wrapper_once, init_pthread_wrapper)`を呼び出すようにしました。
    *   `pthread_once`を使用することで、`init_pthread_wrapper`関数は、`pthread_create`ラッパーがプロセス内で最初に呼び出されたときに一度だけ実行されることが保証されます。
    *   これにより、静的コンストラクタから`pthread_create`が呼び出されたとしても、その呼び出しの時点で`sys_pthread_create`が確実に初期化されるため、`nil`ポインタの呼び出しによるクラッシュを防ぐことができます。
3.  **既存の初期化コードの削除**: `x_cgo_init`関数から、重複する`sys_pthread_create`の初期化ロジックが削除されました。これにより、初期化ロジックが一元化され、より堅牢になりました。

この変更により、Goランタイムは、プログラム起動の非常に早い段階で`pthread_create`が呼び出されるようなシナリオ（特にC/C++ライブラリの静的コンストラクタによるもの）においても、安全かつ正しく動作するようになりました。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、`src/runtime/cgo/gcc_openbsd_386.c`と`src/runtime/cgo/gcc_openbsd_amd64.c`の2つのファイルにわたって行われています。両ファイルで同様のロジックが適用されています。

以下に、`src/runtime/cgo/gcc_openbsd_386.c`を例にとって変更の概要を示します。

1.  **新しい初期化関数の追加**:
    `init_pthread_wrapper`という静的関数が追加されました。この関数は、`libpthread.so`を`dlopen`でロードし、その中から`pthread_create`シンボルを`dlsym`で探し、そのアドレスをグローバル変数`sys_pthread_create`に格納します。

    ```c
    static void init_pthread_wrapper(void) {
    	void *handle;

    	// Locate symbol for the system pthread_create function.
    	handle = dlopen("libpthread.so", RTLD_LAZY);
    	if(handle == NULL) {
    		fprintf(stderr, "runtime/cgo: dlopen failed to load libpthread: %s\n", dlerror());
    		abort();
    	}
    	sys_pthread_create = dlsym(handle, "pthread_create");
    	if(sys_pthread_create == NULL) {
    		fprintf(stderr, "runtime/cgo: dlsym failed to find pthread_create: %s\n", dlerror());
    		abort();
    	}
    	dlclose(handle);
    }
    ```

2.  **`pthread_once`制御変数の追加**:
    `init_pthread_wrapper`関数が一度だけ実行されることを保証するための`pthread_once_t`型の静的変数が追加され、`PTHREAD_ONCE_INIT`で初期化されています。

    ```c
    static pthread_once_t init_pthread_wrapper_once = PTHREAD_ONCE_INIT;
    ```

3.  **`pthread_create`ラッパー関数内での初期化呼び出し**:
    Goランタイムが提供する`pthread_create`ラッパー関数の冒頭に、`pthread_once`を介した`init_pthread_wrapper`の呼び出しが追加されました。

    ```c
    int
    pthread_create(pthread_t *thread, const pthread_attr_t *attr,
    	void *(*start_routine)(void *), void *arg)
    {
    	struct thread_args *p;

    	// we must initialize our wrapper in pthread_create, because it is valid to call
    	// pthread_create in a static constructor, and in fact, our test for issue 9456
    	// does just that.
    	if(pthread_once(&init_pthread_wrapper_once, init_pthread_wrapper) != 0) {
    		fprintf(stderr, "runtime/cgo: failed to initialize pthread_create wrapper\n");
    		abort();
    	}

    	p = malloc(sizeof(*p));
    	// ... (既存のコード)
    }
    ```

4.  **`x_cgo_init`からの初期化コードの削除**:
    以前`sys_pthread_create`の初期化を行っていた`x_cgo_init`関数から、対応する`dlopen`/`dlsym`の呼び出しと関連するエラーハンドリングコードが削除されました。これにより、初期化ロジックが`pthread_create`ラッパー関数内に一元化されました。

    ```c
    // 削除されたコードの概要
    // x_cgo_init関数内から以下の部分が削除された
    // Locate symbol for the system pthread_create function.
    // handle = dlopen("libpthread.so", RTLD_LAZY);
    // ...
    // sys_pthread_create = dlsym(handle, "pthread_create");
    // ...
    // dlclose(handle);
    ```

これらの変更により、`sys_pthread_create`ポインタの初期化が、`pthread_create`ラッパー関数が初めて呼び出されたときに確実に、かつ一度だけ行われるようになり、静的コンストラクタからの早期呼び出しによるクラッシュを防ぐことができます。

## コアとなるコードの解説

このコミットのコアとなるコード変更は、`pthread_create`ラッパー関数の初期化ロジックを、より安全で適切なタイミングで実行されるように再構築した点にあります。

1.  **`init_pthread_wrapper` 関数**:
    この関数は、システムが提供する実際の`pthread_create`関数のアドレスを動的に取得する責任を負います。
    *   `dlopen("libpthread.so", RTLD_LAZY)`: `libpthread.so`という共有ライブラリ（POSIXスレッドの実装を含む）をロードします。`RTLD_LAZY`フラグは、シンボルが実際に必要になるまで解決を遅延させることを意味します。
    *   `dlsym(handle, "pthread_create")`: ロードしたライブラリのハンドル（`handle`）を使って、`pthread_create`という名前のシンボル（関数）のアドレスを探します。
    *   取得したアドレスは、GoランタイムのCGO部分が内部的に使用する関数ポインタ`sys_pthread_create`に格納されます。
    *   エラーチェックも含まれており、ライブラリのロードやシンボルの検索に失敗した場合は、エラーメッセージを出力してプログラムを異常終了（`abort()`）させます。これは、`pthread_create`が利用できない状態ではGoランタイムが正しく動作できないため、早期に問題を検出するためです。

2.  **`pthread_once_t init_pthread_wrapper_once = PTHREAD_ONCE_INIT;`**:
    これは`pthread_once`メカニズムで使用される制御変数です。`PTHREAD_ONCE_INIT`マクロで初期化され、`init_pthread_wrapper`関数がプロセス内で一度だけ実行されることを保証します。

3.  **`pthread_create`ラッパー関数内の `pthread_once` 呼び出し**:
    Goランタイムが提供する`pthread_create`ラッパー関数の冒頭に、以下のコードが追加されました。
    ```c
    if(pthread_once(&init_pthread_wrapper_once, init_pthread_wrapper) != 0) {
    	fprintf(stderr, "runtime/cgo: failed to initialize pthread_create wrapper\n");
    	abort();
    }
    ```
    *   この行が、このコミットの最も重要な変更点です。`pthread_create`ラッパー関数が呼び出されるたびに、まず`pthread_once`がチェックされます。
    *   `pthread_once`は、`init_pthread_wrapper_once`変数の状態を確認し、`init_pthread_wrapper`関数がまだ実行されていない場合のみ、それを実行します。一度実行されると、それ以降の`pthread_once`の呼び出しでは`init_pthread_wrapper`は実行されません。
    *   これにより、`sys_pthread_create`ポインタの初期化が、`pthread_create`ラッパーが初めて呼び出された時点で確実に行われるようになります。これは、静的コンストラクタのような`main`関数よりも早く実行されるコードから`pthread_create`が呼び出された場合でも、`sys_pthread_create`が`nil`でないことを保証します。

4.  **`x_cgo_init`からの初期化コードの削除**:
    以前、`sys_pthread_create`の初期化を行っていた`x_cgo_init`関数から、そのロジックが削除されました。これは、初期化の責任を`pthread_create`ラッパー関数自体に移し、初期化ロジックの重複をなくすことで、コードの保守性と堅牢性を向上させます。

これらの変更により、Goランタイムは、`pthread_create`の呼び出しがプログラムライフサイクルのどの時点で行われても、そのラッパーが適切に初期化され、`nil`ポインタの呼び出しによるクラッシュを防ぐことができるようになりました。

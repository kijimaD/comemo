# [インデックス 22649] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における`gcWork`構造体の使用に関するコメントの改善と一般化を目的としています。特に、GC作業中にプリエンプション（横取り）を無効にする必要性について、より正確で包括的な説明を提供するように修正されています。以前のコメントは`gcDrainN`関数に特化しており、システムスタック上での実行を必須としていましたが、このコミットでは、問題の本質がプリエンプションの無効化であり、`gcWork`を使用するあらゆる箇所に適用されることを明確にしています。

## コミット

```
runtime: improve comment about non-preemption during GC work

Currently, gcDrainN is documented saying that it must be run on the system
stack. In fact, the problem and solution here are somewhat subtler. First,
it doesn't have to happen on the system stack, it just has to be
non-stoppable (that is, non-preemptible). Second, this isn't specific to
gcDrainN (though gcDrainN is perhaps the most surprising instance); it's
general to anything that uses the gcWork structure.

Move the comment to gcWork and generalize it.

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）におけるプリエンプション（横取り）と、GC作業バッファの整合性に関する理解の深化があります。

以前のGoランタイムのコードでは、`gcDrainN`関数に関するコメントが、「この関数はシステムスタック上で実行されなければならない」と記述していました。これは、GC作業バッファをローカルに保持している間に、ストップ・ザ・ワールド（STW）が発生するのを防ぐため、という理由付けがされていました。

しかし、このコミットの著者であるAustin Clementsは、この説明が不正確であり、問題の本質を捉えきれていないと指摘しています。

1.  **システムスタックの誤解**: `gcDrainN`がシステムスタック上で実行される必要があるのではなく、重要なのは「プリエンプション不可能であること（non-preemptible）」でした。システムスタック上での実行は、プリエンプションを無効にするための一つの手段に過ぎません。Goランタイムには、`systemstack`以外にも`acquirem`などのプリエンプションを無効にするメカニズムが存在します。
2.  **汎用性の欠如**: このプリエンプションの必要性は`gcDrainN`に限定されるものではなく、`gcWork`構造体を使用するあらゆるGC関連の処理に共通する要件でした。`gcWork`はGCのマークフェーズ中に到達可能なオブジェクトを追跡するための重要なデータ構造であり、その内部にはGC作業バッファが保持されます。これらのバッファが処理中に不整合な状態になることを防ぐため、プリエンプションを無効にする必要があるのです。

したがって、このコミットは、より正確で汎用的な情報を提供するために、コメントを`gcDrainN`から`gcWork`構造体の定義元に移動し、その内容を一般化することを目的としています。これにより、GoランタイムのGCの内部動作に関する開発者の理解が深まり、将来的なコードの保守性や正確性が向上します。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション（GC）の基本的な概念と、関連するいくつかのメカニズムについて知っておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    GoのGCは、並行（Concurrent）、三色（Tri-color）、マーク・アンド・スイープ（Mark-and-Sweep）アルゴリズムを採用しています。これは、アプリケーションの実行と並行してGC処理を進めることで、プログラムの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ**: GCの主要なフェーズの一つで、プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。このフェーズ中に、新しいオブジェクトが割り当てられたり、既存のオブジェクトへの参照が変更されたりするため、GCの正確性を保つための特別なメカニズムが必要です。
    *   **STW (Stop-The-World)**: GC処理の特定の短い期間（例えば、マークフェーズの開始時や終了時）に、すべてのゴルーチン（Goの軽量スレッド）の実行を一時的に停止させるフェーズです。これにより、GCがメモリの状態を安全にスキャンし、変更が加えられないようにします。STW時間は、GCのパフォーマンスにおいて非常に重要な指標です。

2.  **プリエンプション (Preemption)**:
    Goランタイムのスケジューラは、ゴルーチンをCPU上で実行し、必要に応じてその実行を中断（プリエンプト）して別のゴルーチンに切り替えることができます。これにより、多数のゴルーチンが効率的にCPU時間を共有し、並行性が実現されます。
    *   **非同期プリエンプション**: Go 1.14以降で導入された重要な機能です。以前は、ゴルーチンは関数呼び出しなどの特定の安全なポイントでしかプリエンプトできませんでしたが、非同期プリエンプションはシグナルを使用して、ほぼ任意の時点でゴルーチンを中断できるようになりました。これにより、GCのSTW時間を短縮し、レイテンシを改善するのに役立っています。
    *   **プリエンプションの無効化**: GCのようなクリティカルなランタイム操作では、処理の途中でゴルーチンがプリエンプトされると、データ構造の不整合やGCの誤動作を引き起こす可能性があります。そのため、特定のコードセクションでは意図的にプリエンプションを無効にする必要があります。

3.  **`systemstack`**:
    Goランタイムには、通常のゴルーチンのスタックとは別に、ランタイム内部のクリティカルな処理を実行するための「システムスタック」が存在します。`go:systemstack`ディレクティブが付けられた関数は、このシステムスタック上で実行されます。システムスタック上での実行は、通常、プリエンプションが自動的に無効になるため、GCやスケジューラのような中断されてはならない処理に適しています。

4.  **`gcWork`構造体**:
    `gcWork`は、GoのGCのマークフェーズにおいて、到達可能なオブジェクトを追跡し、スキャン作業を管理するための中心的なデータ構造です。
    *   **ワークバッファ**: `gcWork`の内部には、スキャンが必要なオブジェクトへのポインタを一時的に保持するための「ワークバッファ」が含まれています。GCは、これらのバッファにポインタをエンキューし、デキューして処理を進めます。
    *   **整合性**: `gcWork`がローカルにGC作業バッファを保持している間は、GCがマーク終了フェーズに移行するのを防ぐことが重要です。もし、`gcWork`がバッファを保持している間にGCがマーク終了に移行すると、バッファ内のオブジェクトが正しく処理されず、メモリリークやクラッシュの原因となる可能性があります。

5.  **`gcDrain`と`gcDrainN`関数**:
    これらは、GCのマークフェーズ中に実際にオブジェクトをスキャンし、マークする役割を担う関数です。
    *   `gcDrain`: ルート（グローバル変数やゴルーチンのスタックなど）や`gcWork`バッファ内のオブジェクトをスキャンし、グレー（部分的にスキャン済み）のオブジェクトをブラック（完全にスキャン済み）にマークします。
    *   `gcDrainN`: `gcDrain`のバリアントで、指定された量のスキャン作業（`n`オブジェクト）を実行します。

これらの概念を理解することで、このコミットがなぜ重要であり、GoランタイムのGCの堅牢性をどのように向上させるのかが明確になります。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのガベージコレクション（GC）における「プリエンプションの無効化」の重要性と、`gcWork`構造体の役割に深く関連しています。

GoのGCは並行処理であり、アプリケーションのゴルーチンと並行して動作します。しかし、GCの特定のフェーズ、特にマークフェーズ中に、GCが管理する内部データ構造（`gcWork`のワークバッファなど）の整合性を保つことが極めて重要です。

`gcWork`構造体は、GCのマークフェーズ中にスキャンすべきオブジェクトのポインタを一時的に保持するワークバッファ（`wbuf`）を持っています。このワークバッファは、GCがオブジェクトグラフを探索し、到達可能なオブジェクトをマークしていく過程で動的に内容が変化します。

問題となるのは、`gcWork`がこれらのワークバッファを「ローカルに保持している」間に、GCがマークフェーズから「マーク終了（mark termination）」フェーズに移行してしまう可能性があることです。マーク終了フェーズでは、GCはマーク作業を完了し、次のフェーズ（スイープなど）に備えます。もし、`gcWork`がまだ処理中のポインタをワークバッファ内に持っている状態でマーク終了フェーズに移行してしまうと、これらのポインタが適切に処理されず、結果として到達可能なオブジェクトが解放されてしまったり、メモリリークが発生したりする可能性があります。これは、GCの正確性と安全性を損なう重大な問題です。

この問題を回避するために、`gcWork`を使用するコードは、その使用期間中（`gcw.put()`でオブジェクトを投入し、`gcw.get()`で消費する間）に「プリエンプションを無効にする」必要があります。プリエンプションを無効にすることで、そのゴルーチンはGCによって中断されることなく、`gcWork`の処理を完了させることができます。これにより、`gcWork`がワークバッファを保持している間は、GCが安全にマーク終了フェーズに移行できないことが保証されます。

以前のコメントが`gcDrainN`に特化し、「システムスタック上で実行されなければならない」と述べていたのは、システムスタック上での実行がプリエンプションを無効にする一般的な方法であったためです。しかし、このコミットが指摘するように、システムスタック上での実行はプリエンプションを無効にする「手段」の一つに過ぎず、本質的な要件は「プリエンプション不可能であること」です。`acquirem`のような他のメカニズムもプリエンプションを無効にすることができます。

したがって、このコミットは、`gcWork`を使用する際の正しいパターンとして、`disable preemption`と`enable preemption`で`gcWork`の利用を囲むことを明示し、この要件が`gcDrainN`だけでなく、`gcWork`を使用するすべてのコードに適用されることを明確にしています。これにより、GoランタイムのGCの堅牢性と正確性が向上し、開発者がGC関連のコードを記述する際の誤解を防ぐことができます。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、GoランタイムのGCに関する重要な設計原則を反映したコメントの更新です。

`src/runtime/mgcmark.go`から削除されたコメントは、`gcDrainN`関数がシステムスタック上で実行されるべきであるという、より具体的な（しかし不正確な）指示でした。このコメントは、`gcDrainN`がGC作業バッファを保持している間にSTWを防ぐという目的を述べていましたが、その解決策としてシステムスタックへの依存を強調しすぎていました。実際には、システムスタックはプリエンプションを無効にするための一つの手段に過ぎず、本質的な要件はプリエンプションを無効にすることでした。

一方、`src/runtime/mgcwork.go`に追加された新しいコメントは、より抽象的で汎用的な`gcWork`構造体のレベルで、この重要な原則を説明しています。

新しいコメントのポイントは以下の通りです。

1.  **`gcWork`の利用パターン**: `var gcw gcWork`で`gcWork`インスタンスを宣言し、`gcw.put()`でオブジェクトを投入し、`gcw.get()`で消費し、最後に`gcw.dispose()`でクリーンアップするという、`gcWork`の典型的な利用パターンを提示しています。
2.  **プリエンプションの無効化の明示**: この利用パターンの前後に`disable preemption`と`enable preemption`を明示的に記述することで、`gcWork`を使用する期間全体でプリエンプションを無効にする必要があることを強調しています。これは、以前のコメントが`gcDrainN`という特定の関数に限定していたのに対し、`gcWork`を使用するすべてのコードに適用されるべき一般的なルールであることを示しています。
3.  **理由の明確化**: 「マークフェーズ中に`gcWork`を使用する際は、GCがマーク終了に移行するのを防ぐことが重要である。なぜなら、`gcWork`がGC作業バッファをローカルに保持している可能性があるためである。」と、プリエンプションを無効にする具体的な理由を詳細に説明しています。これにより、開発者は単に指示に従うだけでなく、その背後にあるGCのメカニズムを理解することができます。
4.  **プリエンプション無効化の手段の例示**: プリエンプションを無効にする具体的な方法として、`systemstack`（システムスタック上での実行）または`acquirem`（M（OSスレッド）を占有し、プリエンプションを無効にする）を例示しています。これにより、システムスタックが唯一の選択肢ではないことが明確になります。

この変更は、単なるコメントの修正以上の意味を持ちます。GoランタイムのGCは非常に複雑であり、その内部動作に関する正確なドキュメントは、開発者がGC関連のバグをデバッグしたり、新しいGC機能を開発したりする上で不可欠です。このコミットは、GCのコアとなるデータ構造である`gcWork`の安全な利用方法に関する重要な知識を正確に伝達することで、ランタイムの堅牢性と保守性を向上させています。

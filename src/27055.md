このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおいて、組み込み関数（`len`や`cap`など）の「ローワーリング（lowering）」処理のタイミングと方法を改善するものです。具体的には、ローワーリング処理を独立したパスに分離し、`SliceLen`や`SliceCap`といったスライス関連の組み込み関数の情報をSSAの中間パスでより早期に利用可能にすることで、境界チェックの最適化（Bounds Check Elimination: BCE）を強化し、結果として生成されるバイナリのコードサイズを約45KB削減しています。

## 変更の背景

Go言語はメモリ安全性を重視しており、スライスや配列へのアクセス時には必ず境界チェック（bounds check）を行います。これは実行時エラー（パニック）を防ぐための重要な仕組みですが、不必要なチェックはパフォーマンスのオーバーヘッドとなります。Goコンパイラは、静的解析によって境界チェックが不要であることを証明できる場合に、そのチェックを削除する最適化（Bounds Check Elimination: BCE）を行います。

このコミットの背景には、BCEの効率をさらに向上させ、結果として生成されるバイナリのコードサイズを削減するという目的があります。以前のコンパイラでは、`len`や`cap`といった組み込み関数の情報がSSAの中間パスの早い段階で低レベルな表現に「ローワーリング」されてしまい、その後の最適化パスでこれらの高レベルな情報を利用することが困難でした。

このコミットは、`SliceLen`や`SliceCap`のような重要な情報をより長い期間、高レベルなSSA形式で保持することで、コンパイラがより多くの最適化機会（特にBCE）を見つけられるようにすることを目的としています。これにより、冗長な境界チェックが減少し、コードサイズが削減され、実行時のパフォーマンスも向上する可能性があります。実際に、`pkg/tool/linux_amd64`のバイナリで約45KBのコードサイズ削減が報告されています。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラのバックエンドは、プログラムの抽象構文木（AST）をSSA形式という中間表現に変換します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や様々な最適化が容易になります。SSA形式では、プログラムの操作は`Value`と呼ばれるノードで表現され、これらの`Value`がグラフ構造を形成します。

### 2. コンパイラにおける「ローワーリング (Lowering)」

コンパイラにおけるローワーリングとは、高レベルな抽象的な操作を、より低レベルで具体的な操作に変換するプロセスのことです。例えば、Go言語の`len(slice)`という組み込み関数は、SSA形式では`OpSliceLen`のような高レベルな操作として表現されますが、最終的にはメモリからスライスの長さを読み出すような低レベルな機械語命令に変換されます。この変換プロセスがローワーリングです。ローワーリングのタイミングは最適化の機会に大きく影響します。早すぎると高レベルな情報が失われ、最適化が難しくなります。

### 3. Goのスライスと`len`/`cap`

Goのスライスは、基盤となる配列へのポインタ、現在の要素数（`len`）、そして基盤配列の容量（`cap`）の3つの要素から構成されるデータ構造です。
- `len(s)`: スライス`s`に含まれる要素の数を返します。
- `cap(s)`: スライス`s`の基盤となる配列が保持できる要素の最大数を返します。
これらの情報は、スライスの操作（要素アクセス、`append`など）において非常に重要です。

### 4. 境界チェック (Bounds Checking) と Bounds Check Elimination (BCE)

Goはメモリ安全な言語であり、スライスや配列の要素にアクセスする際（例: `s[i]`）には、インデックス`i`がスライスの有効範囲内（`0 <= i < len(s)`）にあるかを実行時に確認する「境界チェック」が行われます。範囲外のアクセスはパニックを引き起こし、未定義動作を防ぎます。

「Bounds Check Elimination (BCE)」は、コンパイラ最適化の一種です。コンパイラが静的解析によって、ある特定のアクセスに対する境界チェックが常に成功することが保証できる場合、そのチェックを生成される機械語から削除します。これにより、実行時のオーバーヘッドが削減され、プログラムのパフォーマンスが向上します。`len`や`cap`といったスライスに関する情報は、BCEを適用するための重要な手がかりとなります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける組み込み関数のローワーリング戦略の変更にあります。

1.  **ローワーリングの独立パス化**: 以前は、`len`や`cap`のような組み込み関数のSSA操作（`OpSliceLen`, `OpSliceCap`など）は、SSAグラフの構築後、比較的早い段階で低レベルな操作にローワーリングされていました。このコミットでは、このローワーリング処理を`dec`という名前の独立したSSAパスとして分離しました。これにより、これらの高レベルな操作がSSAグラフ内でより長く保持されるようになります。

2.  **`SliceLen`/`SliceCap`の早期利用**: `dec`パスが後回しにされたことで、`OpSliceLen`や`OpSliceCap`といったSSA操作が、`phiopt`、`nilcheckelim`、`prove`などの最適化パスにおいて、まだ高レベルな形式で利用可能になりました。これにより、これらのパスはスライスの長さや容量に関する情報を活用して、より効果的な最適化（特に境界チェックの削除）を実行できるようになります。例えば、`prove`パスは、特定のインデックスアクセスが常に有効であることを証明するために、`SliceLen`の情報を利用できます。

3.  **第2の最適化パスの追加**: 新しいローワーリング戦略によって生まれた最適化の機会を最大限に活用するため、`late opt`という名前の2番目の最適化パスが追加されました。このパスは、`dec`パスによってローワーリングされた後のSSAグラフに対して、さらなる最適化を適用します。これにより、ローワーリング後の低レベルな表現に対しても、より効率的なコード生成が可能になります。

これらの変更により、コンパイラはスライス関連の情報をより賢く扱い、冗長な境界チェックをより多く削除できるようになります。結果として、生成される機械語の命令数が減少し、バイナリのコードサイズが削減され、実行時の効率が向上します。

## コアとなるコードの解説

このコミットは、GoコンパイラのSSAバックエンドにおける最適化パスの構成と、組み込み関数（特に文字列とスライス関連）のローワーリングルールに大きな変更を加えています。

1.  **`src/cmd/compile/internal/ssa/compile.go`**:
    *   SSAパスのリスト`passes`に、新たに`dec`パスと`late opt`パスが追加されています。
    *   `dec`パスは`required: true`とマークされており、これはこのパスが常に実行されるべき必須のパスであることを示します。このパスが、組み込み関数のローワーリングを担当します。
    *   `late opt`パスは、`dec`パスの後に実行される2番目の最適化パスです。これにより、ローワーリング後に生じる新たな最適化機会を捉えることができます。

2.  **`src/cmd/compile/internal/ssa/gen/dec.rules` (新規ファイル)**:
    *   このファイルは、`dec`パスで適用されるSSA書き換えルールを定義しています。
    *   ルールは、`StringPtr`, `StringLen`, `SlicePtr`, `SliceLen`, `SliceCap`といった操作が、それぞれ`StringMake`や`SliceMake`操作から直接、対応するポインタ、長さ、容量の値を抽出するように定義されています。
    *   例えば、`(StringPtr (StringMake ptr _)) -> ptr` は、`StringPtr`操作が`StringMake`操作の最初の引数（ポインタ）を直接返すように書き換えることを意味します。これにより、これらの組み込み関数の意味が、より低レベルなSSA操作に変換されます。

3.  **`src/cmd/compile/internal/ssa/gen/decOps.go` (新規ファイル)**:
    *   このファイルは、`dec`パスで使用されるSSA操作の定義を生成するためのGoコードです。
    *   `archs`スライスに`dec`という新しいアーキテクチャが追加されており、これは`dec`パスが独自の書き換えルールセットを持つことを示しています。

## 変更の背景

この変更の主な背景は、`math/big` パッケージのドキュメンテーションの可読性と網羅性を向上させることにあります。

1.  **ドキュメンテーションの配置の標準化**: Go言語のパッケージでは、パッケージ全体の概要説明は慣習的に `doc.go` というファイルに記述されます。これにより、`go doc` コマンドや GoDoc ウェブサイトでパッケージのドキュメンテーションを参照する際に、ユーザーは一貫した場所で情報を得ることができます。以前は `nat.go` という特定の型 (`nat` は "natural number" の略で、符号なし多倍長整数を扱う内部型) の実装ファイル内にパッケージドキュメンテーションが混在しており、これは標準的なプラクティスではありませんでした。
2.  **ドキュメンテーションの拡充**: `math/big` パッケージは、`Int` (符号付き整数)、`Rat` (有理数)、`Float` (浮動小数点数) といった多倍長算術型を提供しており、その利用方法には特定のイディオムが存在します。特に、結果をレシーバーとして渡す（`z.Add(x, y)` のように、`z` に結果が格納される）という設計パターンは、Goの他の標準ライブラリとは異なる場合があり、新規ユーザーにとっては混乱を招く可能性がありました。このコミットでは、これらの設計上の選択とその理由、および具体的な利用例について、より詳細な説明を追加することで、ユーザーがパッケージをより効果的に利用できるようにすることを目指しました。
3.  **Issue #11241への対応**: この変更は、GoのIssueトラッカーで報告された #11241 に対応するものです。このIssueは、`math/big` パッケージのドキュメンテーションの改善を求めるものでした。

## 前提知識の解説

### 1. Go言語のパッケージドキュメンテーション

Go言語では、パッケージのドキュメンテーションはソースコード内のコメントとして記述されます。特に、パッケージ全体の概要説明は、慣習的に `doc.go` という名前のファイルに記述されることが推奨されています。このファイルは、パッケージのインポートパスの直下に配置され、`package <パッケージ名>` の宣言の直前に記述されたコメントがパッケージドキュメンテーションとして認識されます。`go doc <パッケージ名>` コマンドや [pkg.go.dev](https://pkg.go.dev/) (旧 GoDoc) で表示されるパッケージのトップレベルのドキュメンテーションは、この `doc.go` ファイルから取得されます。

### 2. `math/big` パッケージ

`math/big` パッケージは、Go言語で任意精度（多倍長）の数値演算を行うための型と関数を提供します。標準の `int`, `int64`, `float64` などでは表現できない非常に大きな整数、正確な有理数、または高精度な浮動小数点数を扱う際に使用されます。

主要な型は以下の通りです。
*   `*Int`: 符号付き多倍長整数
*   `*Rat`: 有理数（分子と分母が `*Int` で表現される）
*   `*Float`: 浮動小数点数（任意精度）

### 3. Go言語におけるメソッドのイディオム（レシーバーの利用）

Go言語では、メソッドのレシーバーは通常、そのメソッドが操作するオブジェクトを指します。`math/big` パッケージでは、特に数値演算において、結果を格納するためのオブジェクトをメソッドのレシーバーとして渡すという独特のイディオムを採用しています。

一般的な形式は以下の通りです。
*   `func (z *T) SetV(v V) *T`: `z = v` (値を設定)
*   `func (z *T) Unary(x *T) *T`: `z = unary x` (単項演算)
*   `func (z *T) Binary(x, y *T) *T`: `z = x binary y` (二項演算)

ここで `z` は結果を格納するレシーバーであり、`x` や `y` は演算のオペランドです。この設計の主な理由は、**メモリ割り当ての制御**にあります。各演算で新しい結果オブジェクトを割り当てるのではなく、既存のレシーバーオブジェクトのメモリを再利用することで、ガベージコレクションの負荷を軽減し、パフォーマンスを向上させることができます。

また、このイディオムでは、レシーバー `z` がオペランド `x` や `y` とエイリアス（同じメモリを指すこと）することを許容しています。例えば `sum.Add(sum, x)` のように記述することで、`sum` に `x` を累積加算するといった操作が安全に行えます。

## 技術的詳細

このコミットの技術的詳細は、主に `math/big` パッケージのドキュメンテーションの構造と内容の改善に焦点を当てています。

### 1. `doc.go` の導入と役割

*   **目的**: パッケージ全体のドキュメンテーションを `nat.go` から `doc.go` へ移動することで、Goの標準的なドキュメンテーション慣習に準拠させ、パッケージの概要がより見つけやすく、理解しやすくなりました。
*   **内容**: 新しい `doc.go` ファイルには、`math/big` パッケージが提供する主要な型 (`Int`, `Rat`, `Float`) の紹介から始まり、それらのゼロ値の宣言方法、そして最も重要な「算術演算のイディオム」について詳細に説明されています。

### 2. 算術演算のイディオムの詳細な説明

新しいドキュメンテーションでは、`math/big` パッケージのメソッドシグネチャの背後にある設計思想が深く掘り下げられています。

*   **メソッドシグネチャのパターン**:
    *   `func (z *T) SetV(v V) *T` (設定)
    *   `func (z *T) Unary(x *T) *T` (単項演算)
    *   `func (z *T) Binary(x, y *T) *T` (二項演算)
    *   `func (x *T) Pred() T1` (述語/プロパティ取得)
    これらのパターンが明示され、`z` が結果、`x`, `y` がオペランドであるという命名規則が強調されています。

*   **レシーバーの再利用とエイリアシング**:
    *   「結果はレシーバー（通常 `z` と命名）であり、それがオペランド `x` または `y` のいずれかである場合でも安全に上書きできる（メモリを再利用できる）」という点が明確に説明されています。
    *   `sum.Add(sum, x)` のようなエイリアシングを許容する例が示され、これがメモリ効率の向上に寄与することが強調されています。

*   **設計の根拠 (Rationale)**:
    *   「結果値を常にレシーバー経由で渡すことで、メモリ使用量をはるかに良く制御できる」という設計の根拠が説明されています。これにより、各結果に対して新しいメモリを割り当てる必要がなくなり、既存のメモリ空間を再利用できるため、ガベージコレクションの頻度と負荷が軽減されます。これは、多倍長演算のように頻繁に新しい数値オブジェクトが生成される可能性がある状況で特に重要です。

*   **表記規則 (Notational convention)**:
    *   メソッドの引数（レシーバーを含む）の命名規則が統一されていることが説明されています。結果を指定するパラメータは `z`、入力オペランドは `x`, `y`, `a`, `b` などと命名され、`z` がオペランドとして使われることはない、という規則が明示されています。
    *   例として `func (z *Int) Add(x, y *Int) *Int` が挙げられ、レシーバー `z` が結果、`x` と `y` がオペランドであることを示しています。
    *   メソッドがレシーバーを返すことで、`z.Add(a, b).Mul(c, d)` のようなメソッドチェーンが可能になることも説明されています。
    *   結果値をレシーバーとして受け取らないメソッド（例: `Int.Sign()`) の場合、レシーバーは通常 `x` と命名され、最初のオペランドとして機能することが示されています。

これらの詳細な説明は、`math/big` パッケージの設計思想を深く理解し、それを効果的に利用するために不可欠な情報を提供します。

### `src/math/big/doc.go` の追加内容 (抜粋)

```go
// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

/*
Package big implements arbitrary-precision arithmetic (big numbers).
The following numeric types are supported:

	Int    signed integers
	Rat    rational numbers
	Float  floating-point numbers

Declaration: The zero value for an Int, Rat, or Float (not the pointers
*Int, *Rat, *Float!) correspond to 0. Thus, new values can be declared
in the usual ways and denote 0 without further initialization:

	var x Int        // &x is an an *Int of value 0
	var r = &Rat{}   // r is a *Rat of value 0
	y := new(Float)  // y is a *Float of value 0

Arithmetic: Setters, numeric operations and predicates are represented
as methods of the form:

	func (z *T) SetV(v V) *T          // z = v
	func (z *T) Unary(x *T) *T        // z = unary x
	func (z *T) Binary(x, y *T) *T    // z = x binary y
	func (x *T) Pred() T1             // v = pred(x)

with T one of Int, Rat, or Float. For unary and binary operations, the
result is the receiver (usually named z in that case); if it is one of
the operands x or y it may be safely overwritten (and its memory reused).

Arithmetic expressions are typically written as a sequence of individual
method calls, with each call corresponding to an operation. The receiver
denotes the result and the method arguments are the operation's operands.
For instance, given three *Int values a, b and c, the invocation

	c.Add(a, b)

computes the sum a + b and stores the result in c, overwriting whatever
value was held in c before. Unless specified otherwise, operations permit
aliasing of parameters, so it is perfectly ok to write

	sum.Add(sum, x)

to accumulate values x in a sum.

Rationale: By always passing in a result value via the receiver, memory
use can be much better controlled. Instead of having to allocate new memory
for each result, an operation can reuse the space allocated for the result
value, and overwrite that value with the new result in the process.

Notational convention: Incoming method parameters (including the receiver)
are named consistently in the API to clarify their use. Incoming operands
are usually named x, y, a, b, and so on, but never z. A parameter specifying
the result is named z (typically the receiver).

For instance, the arguments for (*Int).Add are named x and y, and because
the receiver specifies the result destination, it is called z:

	func (z *Int) Add(x, y *Int) *Int

Methods of this form typically return the incoming receiver as well, to
enable simple call chaining.

Methods which don't require a result value to be passed in (for instance,
Int.Sign), simply return the result. In this case, the receiver is typically
the first operand, named x:

	func (x *Int) Sign() int
*/
package big
```

## コアとなるコードの解説

このコミットの「コアとなるコード」は、新しく作成された `src/math/big/doc.go` ファイルの内容そのものです。このファイルは実行可能なコードを含まず、完全にドキュメンテーションのために存在します。

`doc.go` の内容は、`math/big` パッケージの利用者が直面する可能性のある主要な疑問点や、パッケージの設計上の特徴について、非常に詳細かつ体系的に説明しています。

1.  **パッケージの概要**: `Int`, `Rat`, `Float` の3つの主要な数値型がサポートされていることを明記しています。
2.  **ゼロ値の宣言**: 各型のゼロ値がどのように宣言され、それが `0` を表すことが説明されています。ポインタ型 (`*Int`, `*Rat`, `*Float`) ではなく、基底型 (`Int`, `Rat`, `Float`) のゼロ値が `0` に対応することが強調されています。
3.  **算術演算のイディオム**:
    *   `z = v`, `z = unary x`, `z = x binary y`, `v = pred(x)` という4つの一般的なメソッドパターンが提示されています。

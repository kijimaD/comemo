# [インデックス 20289] ファイルの概要

このコミットは、GoランタイムにおけるWindows上での`stdcall`呼び出しメカニズムを改善するものです。特に、`nosplit`関数から`stdcall`を呼び出す際に、引数の数が多くなるとスタック領域がオーバーフローする問題を解決するために、引数の数に応じた専用の`stdcall`ラッパー関数を導入しています。

## 元コミット内容

GoランタイムがWindows APIを呼び出す際に使用する`stdcall`メカニズムにおいて、引数の数が多い場合に`nosplit`関数からの呼び出しでスタック領域がオーバーフローする問題に対処します。具体的には、引数の数に応じて`stdcall`を呼び出すための複数のヘルパー関数を導入し、この問題を回避します。

## 変更の背景

Goランタイムは、Windows固有のシステムコール（Windows API）を呼び出す際に、`stdcall`という呼び出し規約を使用します。これらの呼び出しは、Goのスケジューラやメモリ管理といった低レベルな部分から行われることが多く、特に`nosplit`とマークされた関数内から実行される場合があります。

`nosplit`関数は、Goランタイムにおいて非常に重要な役割を担っています。これらの関数は、スタックの動的な拡張（スタックの分割）を許可しないようにコンパイラに指示されます。これは、これらの関数が非常に高速で予測可能な実行を必要とするため、またはスタックの成長がデッドロックなどの問題を引き起こす可能性があるためです。

元の`runtime·stdcall`関数は、C言語の可変引数（`...`）を使用していました。可変引数を使用すると、コンパイラは呼び出し時の引数の数を事前に知ることが難しく、結果としてスタックフレームのサイズが予測不能になったり、必要以上に大きくなったりする可能性があります。コミットメッセージにあるように、「8引数の関数から始めたが、`stdcall`は`nosplit`関数から呼ばれるため、8引数では`nosplit`領域がオーバーフローする」という問題が発生しました。

このオーバーフローは、`nosplit`関数の厳格なスタックサイズ制限に違反し、ランタイムのクラッシュや未定義の動作を引き起こす可能性がありました。このコミットは、この問題を解決し、Windows上でのGoランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

*   **stdcall (Standard Calling Convention):**
    Windows API関数で主に使用される呼び出し規約です。特徴は以下の通りです。
    *   **引数のプッシュ順序:** 引数は右から左へ（最後の引数から最初へ）スタックにプッシュされます。
    *   **スタックのクリーンアップ:** 呼び出された関数（callee）がスタックをクリーンアップ（引数によって占有されたスタック領域を解放）します。これにより、呼び出し元（caller）はスタッククリーンアップのコードを生成する必要がなくなり、コードサイズが小さくなる利点があります。
    *   **名前の装飾 (Name Decoration):** 関数名には、引数のバイト数を示すプレフィックスやサフィックスが付加されることがあります（例: `_FunctionName@N`）。

*   **Go Runtime:**
    Goプログラムの実行を管理する低レベルな部分です。これには、ゴルーチンのスケジューリング、ガベージコレクション、メモリ割り当て、OSとのインタラクションなどが含まれます。Goプログラムは、OSのネイティブスレッド上で実行されますが、その上で多数の軽量なゴルーチンを効率的に管理するために、独自のランタイムシステムを持っています。

*   **nosplit functions (非分割関数):**
    GoランタイムのCコードやアセンブリコードにおいて、`#pragma textflag NOSPLIT`（またはGoコードでは`//go:nosplit`）というディレクティブでマークされた関数です。これらの関数は、スタックの動的な拡張（スタックの分割）を許可しません。これは、以下のような理由によります。
    *   **低レイテンシ:** スタックの拡張処理はオーバーヘッドを伴うため、非常に低レイテンシが求められるクリティカルなパスで使用されます。
    *   **デッドロック回避:** スケジューラがスタックを拡張しようとすると、自身がデッドロックに陥る可能性があるような状況で使用されます。
    *   **固定スタックフレーム:** `nosplit`関数は、コンパイル時にスタックフレームのサイズが固定され、非常に小さく保たれることが期待されます。

*   **スタックオーバーフロー / nosplit領域のオーバーフロー:**
    関数が使用するスタック領域が、割り当てられたスタックサイズや`nosplit`領域の制限を超えてしまう状態です。通常の関数では、スタックが不足すると自動的に拡張されるメカニズムがありますが、`nosplit`関数ではそれが許されません。そのため、`nosplit`関数内で呼び出される関数が大きなスタックフレームを必要とすると、このオーバーフローが発生し、プログラムのクラッシュにつながります。

## 技術的詳細

このコミットの核心は、Windows API呼び出しのための`stdcall`ラッパー関数`runtime·stdcall`の設計変更にあります。

**変更前:**
変更前は、`runtime·stdcall`という単一の関数が可変引数（`int32 count, ...`）を受け取っていました。この可変引数のメカニズムは、C言語の機能であり、コンパイラは実行時に引数の数と型を決定するために、スタック上の特定の情報（`count`引数など）に依存します。しかし、`nosplit`関数のような厳密なスタック管理が求められるコンテキストでは、可変引数によるスタックフレームの動的な性質が問題となります。コンパイラがスタックフレームの正確なサイズを事前に決定できないため、`nosplit`領域の制限を超過するリスクがありました。

**変更後:**
このコミットでは、`runtime·stdcall`を廃止し、代わりに引数の数に応じた複数の専用関数を導入しました。具体的には、`runtime·stdcall0`（引数なし）から`runtime·stdcall7`（7つの引数）までの関数が追加されました。

1.  **`static void* stdcall(void *fn)` ヘルパー関数の導入:**
    新しい`stdcall`関数は、実際のWindows API関数ポインタ`fn`のみを受け取る静的なヘルパー関数として定義されました。この関数は、Goランタイムの`g->m->libcall`構造体（外部関数呼び出しに関する情報を保持する）を設定し、アセンブリコードで実装された実際の`stdcall`呼び出しロジックを実行します。このヘルパー関数自体は引数を直接受け取らないため、スタックフレームが非常に小さく、予測可能です。

2.  **引数ごとの`runtime·stdcallN`関数の導入:**
    `runtime·stdcall0`, `runtime·stdcall1`, ..., `runtime·stdcall7`といった関数が追加されました。これらの関数は、それぞれ固定数の`uintptr`型引数を受け取ります。
    *   各`stdcallN`関数は、受け取った引数を`g->m->libcall.args`に設定し、`g->m->libcall.n`に引数の数を設定します。
    *   その後、共通の`stdcall`ヘルパー関数を呼び出します。

このアプローチにより、以下の利点が得られます。
*   **スタックフレームサイズの固定化:** 各`stdcallN`関数は固定数の引数を持つため、コンパイラはこれらの関数のスタックフレームサイズをコンパイル時に正確に決定できます。これにより、`nosplit`関数から呼び出された場合でも、スタックオーバーフローのリスクがなくなります。
*   **効率的なコード生成:** 可変引数処理のオーバーヘッドが排除され、より効率的なアセンブリコードが生成されます。
*   **明確なインターフェース:** 呼び出し元は、必要な引数の数に応じて適切な`stdcallN`関数を選択するだけでよくなり、コードの意図がより明確になります。

この変更は、GoランタイムがWindows上で安定して動作するために不可欠であり、特に低レベルなシステムコールを扱う際の堅牢性を高めます。

4.  **`src/pkg/runtime/os_windows.go`**:
    *   新しい`stdcallN`関数群のGo側の宣言が追加されました。これにより、Goコードからこれらの関数を呼び出す際の型安全性が確保されます。

    *   新しい`stdcallN`関数群のC側のプロトタイプ宣言が追加されました。
    *   元の`runtime·stdcall`に関する`#pragma varargck`ディレクティブが削除されました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/pkg/runtime/os_windows.c`における`stdcall`呼び出しメカニズムの再設計です。

```c
// 変更前: 可変引数を受け取る単一の関数
// void *runtime·stdcall(void *fn, int32 count, ...);

// 変更後: 静的ヘルパー関数
#pragma textflag NOSPLIT
static void*
stdcall(void *fn)
{
	g->m->libcall.fn = fn;
	// g->m->libcall.n と g->m->libcall.args は、呼び出し元のstdcallN関数で設定される
	if(g->m->profilehz != 0) {
		// leave pc/sp for cpu profiler
		g->m->libcallg = g;
		g->m->libcallpc = (uintptr)runtime·getcallerpc(&fn);
		g->m->libcallsp = (uintptr)runtime·getcallersp(&fn);
	}
	runtime·asmstdcall(nil); // 実際のアセンブリによるstdcall呼び出しを実行
	return (void*)g->m->libcall.r1;
}

// 変更後: 引数の数に応じたラッパー関数群 (例: stdcall4)
#pragma textflag NOSPLIT
void*
runtime·stdcall4(void *fn, uintptr a0, uintptr a1, uintptr a2, uintptr a3)
{
	USED(a0, a1, a2, a3); // コンパイラの警告を抑制
	g->m->libcall.n = 4; // 引数の数を明示的に設定
	g->m->libcall.args = &a0; // 最初の引数へのポインタを設定
	return stdcall(fn); // ヘルパー関数を呼び出す
}
```

**解説:**

1.  **`static void* stdcall(void *fn)`:**
    この関数は、`NOSPLIT`としてマークされており、GoランタイムのM（Machine）構造体にある`libcall`フィールドをセットアップします。`libcall`は、外部（Windows API）関数を呼び出すために必要な情報（呼び出す関数ポインタ`fn`、引数の数`n`、引数へのポインタ`args`、戻り値`r1`, `r2`など）を保持します。このヘルパー関数自体は引数を直接受け取らず、`libcall.n`と`libcall.args`は、この関数を呼び出す`runtime·stdcallN`関数によって設定されます。その後、`runtime·asmstdcall(nil)`を呼び出して、実際のアセンブリレベルでの`stdcall`呼び出しを実行します。

2.  **`runtime·stdcallN` 関数群 (例: `runtime·stdcall4`)**:
    これらの関数も`NOSPLIT`としてマークされています。それぞれの関数は、特定の数の`uintptr`型引数（例: `a0, a1, a2, a3`）を明示的に受け取ります。
    *   `g->m->libcall.n = N;`: ここで、呼び出すWindows API関数の引数の数を正確に`libcall.n`に設定します。
    *   `g->m->libcall.args = &a0;`: 最初の引数`a0`のアドレスを`libcall.args`に設定します。これにより、アセンブリコードはスタック上の引数にアクセスできます。
    *   `return stdcall(fn);`: 最後に、共通の`stdcall`ヘルパー関数を呼び出して、実際のAPI呼び出しを実行します。

この設計により、各`runtime·stdcallN`関数はコンパイル時にスタックフレームのサイズが固定され、`NOSPLIT`領域の制約を確実に満たすことができます。これにより、可変引数によるスタックオーバーフローの問題が根本的に解決され、Windows上でのGoランタイムの安定性と信頼性が向上します。

1.  **`static void* stdcall(void *fn)` ヘルパー関数の導入:**
    新しい`stdcall`関数は、実際のWindows API関数ポインタ`fn`のみを受け取る静的なヘルパー関数として定義されました。この関数は、Goランタイムの`g->m->libcall`構造体（外部関数呼び出しに関する情報を保持する）を設定し、アセンブリコードで実装された実際の`stdcall`呼び出しロジックを実行します。このヘルパー関数自体は引数を直接受け取らないため、スタックフレームが非常に小さく、予測可能です。

2.  **引数ごとの`runtime·stdcallN`関数の導入:**
    `runtime·stdcall0`, `runtime·stdcall1`, ..., `runtime·stdcall7`といった関数が追加されました。これらの関数は、それぞれ固定数の`uintptr`型引数を受け取ります。
    *   各`stdcallN`関数は、受け取った引数を`g->m->libcall.args`に設定し、`g->m->libcall.n`に引数の数を設定します。
    *   その後、共通の`stdcall`ヘルパー関数を呼び出します。

このアプローチにより、以下の利点が得られます。
*   **スタックフレームサイズの固定化:** 各`stdcallN`関数は固定数の引数を持つため、コンパイラはこれらの関数のスタックフレームサイズをコンパイル時に正確に決定できます。これにより、`nosplit`関数から呼び出された場合でも、スタックオーバーフローのリスクがなくなります。
*   **効率的なコード生成:** 可変引数処理のオーバーヘッドが排除され、より効率的なアセンブリコードが生成されます。
*   **明確なインターフェース:** 呼び出し元は、必要な引数の数に応じて適切な`stdcallN`関数を選択するだけでよくなり、コードの意図がより明確になります。

この変更は、GoランタイムがWindows上で安定して動作するために不可欠であり、特に低レベルなシステムコールを扱う際の堅牢性を高めます。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/pkg/runtime/os_windows.c`における`stdcall`呼び出しメカニズムの再設計です。

```c
// 変更前: 可変引数を受け取る単一の関数
// void *runtime·stdcall(void *fn, int32 count, ...);

// 変更後: 静的ヘルパー関数
#pragma textflag NOSPLIT
static void*
stdcall(void *fn)
{
	g->m->libcall.fn = fn;
	// g->m->libcall.n と g->m->libcall.args は、呼び出し元のstdcallN関数で設定される
	if(g->m->profilehz != 0) {
		// leave pc/sp for cpu profiler
		g->m->libcallg = g;
		g->m->libcallpc = (uintptr)runtime·getcallerpc(&fn);
		g->m->libcallsp = (uintptr)runtime·getcallersp(&fn);
	}
	runtime·asmstdcall(nil); // 実際のアセンブリによるstdcall呼び出しを実行
	return (void*)g->m->libcall.r1;
}

// 変更後: 引数の数に応じたラッパー関数群 (例: stdcall4)
#pragma textflag NOSPLIT
void*
runtime·stdcall4(void *fn, uintptr a0, uintptr a1, uintptr a2, uintptr a3)
{
	USED(a0, a1, a2, a3); // コンパイラの警告を抑制
	g->m->libcall.n = 4; // 引数の数を明示的に設定
	g->m->libcall.args = &a0; // 最初の引数へのポインタを設定
	return stdcall(fn); // ヘルパー関数を呼び出す
}
```

**解説:**

1.  **`static void* stdcall(void *fn)`:**
    この関数は、`NOSPLIT`としてマークされており、GoランタイムのM（Machine）構造体にある`libcall`フィールドをセットアップします。`libcall`は、外部（Windows API）関数を呼び出すために必要な情報（呼び出す関数ポインタ`fn`、引数の数`n`、引数へのポインタ`args`、戻り値`r1`, `r2`など）を保持します。このヘルパー関数自体は引数を直接受け取らず、`libcall.n`と`libcall.args`は、この関数を呼び出す`runtime·stdcallN`関数によって設定されます。その後、`runtime·asmstdcall(nil)`を呼び出して、実際のアセンブリレベルでの`stdcall`呼び出しを実行します。

2.  **`runtime·stdcallN` 関数群 (例: `runtime·stdcall4`)**:
    これらの関数も`NOSPLIT`としてマークされています。それぞれの関数は、特定の数の`uintptr`型引数（例: `a0, a1, a2, a3`）を明示的に受け取ります。
    *   `g->m->libcall.n = N;`: ここで、呼び出すWindows API関数の引数の数を正確に`libcall.n`に設定します。
    *   `g->m->libcall.args = &a0;`: 最初の引数`a0`のアドレスを`libcall.args`に設定します。これにより、アセンブリコードはスタック上の引数にアクセスできます。
    *   `return stdcall(fn);`: 最後に、共通の`stdcall`ヘルパー関数を呼び出して、実際のAPI呼び出しを実行します。

この設計により、各`runtime·stdcallN`関数はコンパイル時にスタックフレームのサイズが固定され、`NOSPLIT`領域の制約を確実に満たすことができます。これにより、可変引数によるスタックオーバーフローの問題が根本的に解決され、Windows上でのGoランタイムの安定性と信頼性が向上します。

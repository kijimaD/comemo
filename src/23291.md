## 変更の背景

`TestSCMCredentials` は、Unixドメインソケットを介してプロセス認証情報（`SCM_CREDENTIALS`）を送信する際の権限エラー（`EPERM`）をテストするためのものです。しかし、このテストは `WriteMsgUnix` 関数が返すエラーの型を厳密に `*net.OpError` と仮定していました。

Go言語のエラーハンドリングの仕組みや、異なるオペレーティングシステム、あるいはGoのバージョンアップに伴う内部実装の変化により、`WriteMsgUnix` が返すエラーが直接 `*net.OpError` ではない場合や、`*net.OpError` の内部にさらに別のエラー型（例: `*os.SyscallError`）がラップされている場合がありました。

このような状況下では、基となる `syscall.EPERM` エラーが発生していても、テストが期待するエラー型と一致しないためにテストが失敗するという問題が発生していました。このコミットは、エラーのラップ構造を考慮し、より柔軟に `EPERM` エラーを検出できるようにすることで、テストの堅牢性と信頼性を向上させることを目的としています。

## 前提知識の解説

### UnixドメインソケットとSCM_CREDENTIALS

*   **Unixドメインソケット**: 同じホスト上のプロセス間通信 (IPC) の一種で、ファイルシステム上のパス名によって識別されます。ネットワークソケットと同様のAPIを提供しますが、実際の通信はカーネル内で行われるため、ネットワークスタックを介するよりも効率的です。
*   **`SCM_CREDENTIALS`**: Unixドメインソケットを介して、送信元プロセスの認証情報（実効ユーザーID、実効グループID、プロセスID）を相手プロセスに送信するための制御メッセージです。これにより、受信側プロセスは送信元プロセスの身元を確認し、認証や権限チェックを行うことができます。
*   **`syscall.UnixCredentials`**: Go言語の `syscall` パッケージ（またはより新しい `golang.org/x/sys/unix` パッケージ）で提供される関数で、`ucred` 構造体（ユーザーID、グループID、プロセスIDを含む）を `SCM_CREDENTIALS` 制御メッセージとしてエンコードするために使用されます。このメッセージは `WriteMsgUnix` などの関数で送信されます。

### Goのエラーハンドリング

Go言語では、エラーは組み込みの `error` インターフェースによって表現されます。このインターフェースは `Error() string` メソッドを一つだけ持ちます。Go 1.13以降ではエラーラッピングの概念が導入され、エラーが別のエラーを「ラップ」して、より詳細なコンテキストを提供できるようになりました。これにより、エラーチェーンを辿って根本原因を特定することが可能になります。

### `net.OpError`

`net` パッケージ（ネットワーク操作を扱う）で発生するエラーを表す構造体です。ネットワーク操作の種類（例: "read", "write", "dial"）、ネットワークの種類（例: "tcp", "unix"）、アドレス、そして基となるエラー（`Err` フィールド）などの情報を含みます。

### `os.SyscallError`

`os` パッケージで、システムコールが失敗した際に返されるエラーを表す構造体です。失敗したシステムコールの名前（`Syscall` フィールド）と、基となるシステムエラー（`Err` フィールド、通常は `syscall.Errno` 型）を含みます。

### `syscall.EPERM`

`syscall` パッケージで定義されているエラー定数の一つで、Unix系システムにおける `EPERM` エラーコードに対応します。「Operation not permitted（操作が許可されていません）」を意味し、通常はプロセスがその操作を実行するための適切な権限を持っていない場合に発生します。例えば、特権ポートへのバインドや、特定のシステムリソースへのアクセスなどが挙げられます。

## 技術的詳細

このコミットの技術的な核心は、Go言語におけるエラーの「アンラッピング」処理にあります。`WriteMsgUnix` 関数は、内部でシステムコールを呼び出すため、その結果として返されるエラーは、`net` パッケージや `os` パッケージによってラップされることがあります。

元のコードでは、`WriteMsgUnix` が返したエラーが直接 `*net.OpError` 型であり、かつその内部の `Err` フィールドが `syscall.EPERM` であることを期待していました。しかし、実際には以下のような状況が発生し得ます。

1.  `WriteMsgUnix` が返すエラーが、`*net.OpError` ではない場合。
2.  `WriteMsgUnix` が返すエラーが `*net.OpError` であったとしても、その `Err` フィールドが直接 `syscall.EPERM` ではなく、さらに `*os.SyscallError` のような別のエラー型でラップされている場合。

このコミットは、これらのケースに対応するために、エラーが `*net.OpError` であればその内部の `Err` を抽出し、さらにそれが `*os.SyscallError` であればその内部の `Err` を抽出するという、多段階のエラーアンラッピングロジックを追加しました。これにより、エラーがどのようにラップされていても、最終的に基となる `syscall.EPERM` を正確に比較できるようになります。

この変更は、テストのロバスト性を高めるだけでなく、Go言語でシステムコールやネットワーク操作に関連するエラーを扱う際の一般的なプラクティスとしても参考になります。エラーが多重にラップされる可能性がある場合、適切なエラー型アサーションとアンラッピングを行うことで、より正確なエラーハンドリングが可能になります。

## コアとなるコードの変更箇所

変更は `src/syscall/creds_test.go` ファイルの `TestSCMCredentials` 関数内で行われています。

```diff
--- a/src/syscall/creds_test.go
+++ b/src/syscall/creds_test.go
@@ -56,7 +56,13 @@ func TestSCMCredentials(t *testing.T) {
 		ucred.Gid = 0
 		oob := syscall.UnixCredentials(&ucred)
 		_, _, err := cli.(*net.UnixConn).WriteMsgUnix(nil, oob, nil)
-		if err.(*net.OpError).Err != syscall.EPERM {
+		if op, ok := err.(*net.OpError); ok {
+			err = op.Err

+			err = sys.Err
+		}

 			t.Fatalf("WriteMsgUnix failed with %v, want EPERM", err)
 		}
 	}
```

## コアとなるコードの解説

変更前のコードは以下のようになっていました。

```go
if err.(*net.OpError).Err != syscall.EPERM {
    t.Fatalf("WriteMsgUnix failed with %v, want EPERM", err)
}
```

このコードは、`err` が必ず `*net.OpError` 型であることを前提とし、その `Err` フィールドが `syscall.EPERM` と等しくない場合にテストを失敗させていました。

変更後のコードは、このエラーチェックをより柔軟にしています。

```go
if op, ok := err.(*net.OpError); ok {
    err = op.Err
}
if sys, ok := err.(*os.SyscallError); ok {
    err = sys.Err
}
if err != syscall.EPERM {
    t.Fatalf("WriteMsgUnix failed with %v, want EPERM", err)
}
```

1.  **`if op, ok := err.(*net.OpError); ok { err = op.Err }`**:
    *   まず、`err` が `*net.OpError` 型であるかどうかを型アサーション `err.(*net.OpError)` とカンマokイディオム `op, ok := ...` を使ってチェックします。
    *   もし `err` が `*net.OpError` であれば (`ok` が `true`)、その内部の `Err` フィールド（基となるエラー）を新たな `err` 変数に代入し直します。これにより、`net.OpError` のラッパーが剥がされます。

2.  **`if sys, ok := err.(*os.SyscallError); ok { err = sys.Err }`**:
    *   次に、更新された `err` 変数（`*net.OpError` が剥がされた後のエラー、または元々 `*net.OpError` ではなかったエラー）が `*os.SyscallError` 型であるかどうかをチェックします。
    *   もし `err` が `*os.SyscallError` であれば (`ok` が `true`)、その内部の `Err` フィールド（基となるシステムエラー、通常は `syscall.Errno`）を新たな `err` 変数に代入し直します。これにより、`os.SyscallError` のラッパーが剥がされます。

3.  **`if err != syscall.EPERM { ... }`**:
    *   上記2つのステップでエラーのラップが解除された後、最終的に `err` 変数が `syscall.EPERM` と等しいかどうかをチェックします。
    *   これにより、エラーが `*net.OpError` や `*os.SyscallError` で多重にラップされていたとしても、最終的に `syscall.EPERM` が検出されるようになり、テストが意図通りに動作するようになります。

この変更は、Go言語におけるエラーハンドリングのベストプラクティスを示しており、特に低レベルなシステムコールやネットワーク操作を扱う際に、エラーがどのようにラップされるかを考慮することの重要性を強調しています。

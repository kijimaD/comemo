# [インデックス 22966] ファイルの概要

このコミットは、Goコンパイラの内部における中間表現（IR）から静的単一割り当て（SSA）形式への変換を初期的に導入するものです。これにより、コンパイラのバックエンドがSSAベースの最適化とコード生成の恩恵を受けられるようになります。具体的には、特定の関数（名前に `_ssa` が付くもの）に対してSSA変換パスを有効にし、生成されたアセンブリを出力するものの、まだ実際のコード生成には利用しない段階です。また、SSA内部でGoの型を扱う際に、既存の `gc.Type` を直接利用することで、変換処理を簡素化しています。

## 変更の背景

Goコンパイラは、長らくツリーベースの中間表現（IR）を使用していました。しかし、より高度な最適化や効率的なコード生成を実現するためには、SSA（Static Single Assignment）形式への移行が不可欠でした。SSAは、各変数が一度だけ定義されるという特性を持つため、データフロー解析や最適化が格段に行いやすくなります。

このコミットは、GoコンパイラのバックエンドをSSAベースに移行する「dev.ssa」プロジェクトの初期段階の一部です。従来のIRからSSAへの変換パスを導入することで、将来的にSSAベースの最適化パスを実装するための基盤を築いています。この段階では、まだSSAから生成されたアセンブリは破棄されますが、これはSSA変換の正確性を検証するための重要なステップです。

## 前提知識の解説

### 中間表現 (IR: Intermediate Representation)

コンパイラは、ソースコードを直接機械語に変換するのではなく、通常、いくつかの段階を経て変換を行います。中間表現（IR）は、この変換プロセスの中間段階で用いられる、ソースコードとターゲットマシンコードの中間的な形式です。IRは、コンパイラのフロントエンド（構文解析、意味解析など）とバックエンド（最適化、コード生成など）の間の橋渡し役となります。

IRには様々な種類がありますが、一般的には、ソース言語のセマンティクスを保持しつつ、機械に依存しない形で表現されます。これにより、コンパイラの各ステージを独立して開発・最適化することが可能になります。

### 静的単一割り当て (SSA: Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において非常に重要な中間表現の一種です。SSA形式では、プログラム中の各変数が「一度だけ」定義されるという特性を持ちます。もし同じ変数名が複数回代入される場合、SSA形式ではそれぞれの代入に対して新しい「バージョン」の変数を導入します（例: `x1 = ...`, `x2 = ...`）。

SSA形式の主な利点は以下の通りです。

*   **データフロー解析の簡素化**: 各変数の定義が単一であるため、変数の値がどこから来るのか、どこで使われるのかといったデータフローを容易に追跡できます。
*   **最適化の効率化**: 共通部分式除去（CSE）、定数伝播、デッドコード除去など、多くのコンパイラ最適化がSSA形式上で効率的に実装できます。
*   **レジスタ割り当ての改善**: 変数のライフタイムが明確になるため、レジスタ割り当ての精度が向上します。

SSA形式への変換には、複数の制御フローパスが合流する点（例: if文の終わり、ループの終わり）で、異なるバージョンの変数を結合するための特別な命令「Φ（ファイ）関数」が導入されます。Φ関数は、どのパスから来たかによって適切な変数のバージョンを選択します。

### Goコンパイラのアーキテクチャ（概要）

Goコンパイラは、伝統的に以下のような構造を持っています。

1.  **フロントエンド**: ソースコードを解析し、抽象構文木（AST）を構築します。型チェックや名前解決もここで行われます。
2.  **中間処理（Walk）**: ASTを走査し、一部の最適化や変換（例: スライス操作の展開、マップ操作の組み込み関数呼び出しへの変換）を行います。この段階で、Go独自のツリーベースIRが生成されます。
3.  **バックエンド（コード生成）**: 中間表現からターゲットアーキテクチャの機械語コードを生成します。

このコミットは、上記の中間処理（Walk）の後、バックエンドのコード生成の前にSSA変換を挿入するものです。

## 技術的詳細

このコミットの主要な目的は、Goコンパイラの既存のツリーベースIRをSSA形式に変換する初期的なパイプラインを構築することです。

### SSA変換のトリガー

`src/cmd/internal/gc/pgen.go` の `compile` 関数にフックが追加されています。これにより、関数名が `_ssa` で終わる場合、新しい `buildssa` 関数が呼び出され、SSA変換パスが実行されます。この段階では、生成されたアセンブリはデバッグ目的で出力されるだけで、実際のコード生成には使用されません。

```go
// src/cmd/internal/gc/pgen.go
func compile(fn *Node) {
    // ...
    // Build an SSA backend function
    {
        name := Curfn.Nname.Sym.Name
        if len(name) > 4 && name[len(name)-4:] == "_ssa" {
            buildssa(Curfn)
            // TODO(khr): use result of buildssa
        }
    }
    // ...
}
```

### `gc.Type` の直接利用

コミットメッセージにもあるように、SSA内部でGoの型を扱う際に、`gc.Type` を直接利用するように変更されています。これにより、型情報の変換やラッパーの導入が不要になり、IRからSSAへの変換ロジックが大幅に簡素化されています。`src/cmd/internal/gc/type.go` には、`gc.Type` を `cmd/internal/ssa.Type` としてエクスポートするためのメソッドが追加されています。

### `ssaState` 構造体

SSA変換の主要なロジックは、新しく追加された `src/cmd/internal/gc/ssa.go` ファイル内の `ssaState` 構造体にカプセル化されています。この構造体は、SSA変換中の状態を管理します。

```go
// src/cmd/internal/gc/ssa.go
type ssaState struct {
    // configuration (arch) information
    config *ssa.Config

    // function we're building
    f *ssa.Func

    // exit block that "return" jumps to (and panics jump to)
    exit *ssa.Block

    // the target block for each label in f
    labels map[string]*ssa.Block

    // current location where we're interpreting the AST
    curBlock *ssa.Block

    // variable assignments in the current block (map from variable name to ssa value)
    vars map[string]*ssa.Value

    // all defined variables at the end of each block.  Indexed by block ID.
    defvars []map[string]*ssa.Value

    // offsets of argument slots
    // unnamed and unused args are not listed.
    argOffsets map[string]int64
}
```

`ssaState` は、現在のSSA関数 (`f`)、終了ブロック (`exit`)、ラベルのマッピング (`labels`)、現在のブロック (`curBlock`)、現在のブロックでの変数定義 (`vars`)、各ブロック終了時の変数定義 (`defvars`)、引数のオフセット (`argOffsets`) などの情報を含んでいます。

### SSAグラフ構築アルゴリズム

`buildssa` 関数は、ASTベースのIRをSSAベースのIRに変換するために、Brau, Buchwald, Hack, Leißa, Mallon, and Zwinkau の論文で記述されているアルゴリズムに類似した手法を使用しています。このアルゴリズムは、主に以下のステップでSSAグラフを構築します。

1.  **初期ブロックと終了ブロックの作成**: 関数のエントリブロックと終了ブロックを初期化します。
2.  **ASTの走査とSSA値の生成**: `stmtList` および `stmt` 関数がASTノードを再帰的に走査し、対応するSSA値を生成します。`expr` 関数は式をSSA値に変換します。
3.  **前方参照の解決とΦ関数の挿入**: `linkForwardReferences` 関数が、各変数の最初の使用箇所（前方参照）を、その変数の定義とリンクします。複数の制御フローパスが合流する点では、必要に応じてΦ関数が挿入され、適切な変数のバージョンが選択されます。これは `lookupVarIncoming` と `lookupVarOutgoing` 関数によって実現されます。

### 実装されたオペコード

このコミットでは、ごく一部のSSAオペコードのみが実装されています。これは、`func f(p *int) int { return *p }` や `func g(a []int, i int) int { return a[i] }` のような単純な例をコンパイルするのに十分な範囲です。具体的には、`OAS` (代入)、`OIF` (if文)、`OFOR` (forループ)、`ORETURN` (return文) などのASTノードに対応するSSA変換ロジックが追加されています。また、`OLITERAL` (リテラル)、`OLT` (より小さい)、`OADD` (加算)、`OSUB` (減算)、`OIND` (間接参照)、`ODOTPTR` (ポインタフィールドアクセス)、`OINDEX` (配列/スライスインデックス)、`OCALLFUNC` (関数呼び出し) などの式に対応するSSA値生成も含まれています。

## コアとなるコードの解説

### `src/cmd/internal/gc/ssa.go`

このファイルは、GoコンパイラのAST（抽象構文木）からSSA形式への変換を行う中心的なロジックを含んでいます。

*   **`buildssa(fn *Node)`**:
    *   Go関数のASTノード `fn` を受け取り、SSA形式の関数 `s.f` を構築します。
    *   `ssa.NewConfig` を呼び出してアーキテクチャ固有のSSA設定を初期化します。
    *   関数のエントリブロック (`s.f.Entry`) と終了ブロック (`s.exit`) を作成します。
    *   `ssaState` 構造体の `vars` (現在のブロックの変数定義) と `labels` (GOTOラベルのターゲットブロック) を初期化します。
    *   `s.stmtList(fn.Nbody)` を呼び出して、関数の本体（ステートメントリスト）をSSAに変換します。
    *   終了ブロックの処理を行い、`s.exit.Control = s.mem()` でメモリ状態を制御値として設定します。
    *   `s.linkForwardReferences()` を呼び出して、SSA形式の重要なステップである前方参照の解決とΦ関数の挿入を行います。
    *   最後に `ssa.Compile(s.f)` を呼び出しますが、この段階ではまだSSAからコード生成は行われず、生成されたアセンブリは破棄されます。

*   **`ssaState` 構造体**:
    *   `config`: SSAのアーキテクチャ設定（例: "amd64"）。
    *   `f`: 現在構築中のSSA関数。
    *   `exit`: 関数の終了ブロック。`return` や `panic` がジャンプする先。
    *   `labels`: GOTOラベル名と対応するSSAブロックのマッピング。
    *   `curBlock`: 現在SSA値を生成しているブロック。
    *   `vars`: 現在のブロックで定義された変数名とSSA値のマッピング。
    *   `defvars`: 各ブロックの終了時点で定義されている変数（ブロックIDでインデックス付け）。Φ関数挿入のために使用されます。
    *   `argOffsets`: 引数スロットのオフセット。

*   **`startBlock(b *ssa.Block)` / `endBlock() *ssa.Block`**:
    *   `startBlock` は、SSA値を生成する現在のブロックを設定し、`vars` マップをクリアします。
    *   `endBlock` は、現在のブロックでのSSA値生成の終了をマークし、そのブロックの終了時点での変数定義を `defvars` に保存します。

*   **`stmt(n *Node)` / `stmtList(l *NodeList)`**:
    *   ASTのステートメントノード `n` を受け取り、対応するSSA値を生成します。
    *   `OBLOCK` (ブロック)、`OLABEL` (ラベル)、`OGOTO` (GOTO)、`OAS` (代入)、`OIF` (if文)、`OFOR` (forループ)、`ORETURN` (return文) などのASTノードに対応するSSA変換ロジックが含まれています。
    *   `OIF` や `OFOR` のような制御フローを伴うステートメントでは、新しいSSAブロックを作成し、エッジを追加して制御フローグラフを構築します。

*   **`expr(n *Node) *ssa.Value`**:
    *   ASTの式ノード `n` を受け取り、対応するSSA値（`*ssa.Value`）を返します。
    *   `ONAME` (変数名)、`OLITERAL` (リテラル)、`OLT` (より小さい)、`OADD` (加算)、`OSUB` (減算)、`OIND` (間接参照)、`ODOTPTR` (ポインタフィールドアクセス)、`OINDEX` (配列/スライスインデックス)、`OCALLFUNC` (関数呼び出し) などのASTノードに対応するSSA値生成ロジックが含まれています。
    *   ポインタのデリファレンス (`OIND`) やスライス/配列のインデックスアクセス (`OINDEX`) の際には、nilチェックや境界チェックのためのSSA値が挿入され、チェック失敗時には `s.exit` ブロック（パニックを発生させる可能性のあるブロック）へのエッジが追加されます。

*   **`variable(name string, t ssa.Type) *ssa.Value`**:
    *   指定された名前 `name` と型 `t` を持つ変数のSSA値を返します。
    *   もし変数が現在のブロックでまだ定義されていない場合、`OpFwdRef` (前方参照) オペコードを持つ新しいSSA値を作成します。これは後で `linkForwardReferences` によって解決されます。

*   **`mem() *ssa.Value`**:
    *   メモリ状態を表す特別なSSA値（`.mem` という名前）を返します。SSAでは、メモリ操作も値として扱われ、メモリの依存関係を明示的に表現します。

*   **`linkForwardReferences()`**:
    *   SSAグラフ構築の重要なフェーズです。各SSAブロックを走査し、`OpFwdRef` オペコードを持つSSA値（前方参照）を見つけます。
    *   これらの前方参照を、その変数の実際の定義とリンクします。
    *   複数の制御フローパスが合流するブロックでは、必要に応じてΦ関数（`OpPhi`）を挿入します。Φ関数は、そのブロックに到達したパスに応じて、適切な変数のバージョンを選択します。

*   **`lookupVarIncoming(b *ssa.Block, t ssa.Type, name string) *ssa.Value`**:
    *   ブロック `b` の開始時点での変数 `name` のSSA値を見つけます。
    *   もし `b` がエントリブロックの場合、引数として渡された変数をロードします。
    *   それ以外の場合、先行ブロックからの変数の値を探し、もし複数の先行ブロックから異なる値が来る場合はΦ関数を生成します。

*   **`lookupVarOutgoing(b *ssa.Block, t ssa.Type, name string) *ssa.Value`**:
    *   ブロック `b` の終了時点での変数 `name` のSSA値を見つけます。
    *   もし変数が `b` 内で定義されている場合、その定義されたSSA値を返します。
    *   定義されていない場合、`OpCopy` オペコードを持つSSA値を作成し、`lookupVarIncoming` を再帰的に呼び出して、その変数の入力値を解決します。

### `src/cmd/internal/ssa/lowerAmd64.go`

このファイルは、AMD64アーキテクチャに特化したSSAオペコードのローワーリングルールを含んでいます。ローワーリングとは、高レベルのSSAオペコードを、より低レベルでターゲットマシンに特化したオペコードに変換するプロセスです。

*   **`lowerAmd64(v *Value) bool`**:
    *   SSA値 `v` を受け取り、そのオペコードに基づいてAMD64固有の命令に変換できるかどうかをチェックします。
    *   例えば、`OpAdd` (汎用加算) が `OpADDQ` (64ビット加算) や `OpADDL` (32ビット加算) に変換されるルールが含まれています。
    *   `OpLoad` や `OpStore` のようなメモリ操作は、`OpMOVQload` や `OpMOVQstore` のような具体的なロード/ストア命令に変換されます。
    *   `OpCheckBound` (境界チェック) や `OpCheckNil` (nilチェック) は、`OpSETB` (セットバイト) や `OpSETNE` (セット非等しい) といったフラグ操作と組み合わせた比較命令に変換されます。
    *   `OpMULQ` (64ビット乗算) は、定数乗算の場合に `OpSHLCQ` (左シフト) に最適化されるルールも含まれています。
    *   これらのルールは、`rulegen` ツールによって生成されたGoコードであり、パターンマッチングと置換によってSSAグラフを変換します。

## 変更の背景

Goコンパイラは、長らくツリーベースの中間表現（IR）を使用していました。しかし、より高度な最適化や効率的なコード生成を実現するためには、SSA（Static Single Assignment）形式への移行が不可欠でした。SSAは、各変数が一度だけ定義されるという特性を持つため、データフロー解析や最適化が格段に行いやすくなります。

このコミットは、GoコンパイラのバックエンドをSSAベースに移行する「dev.ssa」プロジェクトの初期段階の一部です。従来のIRからSSAへの変換パスを導入することで、将来的にSSAベースの最適化パスを実装するための基盤を築いています。この段階では、まだSSAから生成されたアセンブリは破棄されますが、これはSSA変換の正確性を検証するための重要なステップです。

## 前提知識の解説

### 中間表現 (IR: Intermediate Representation)

コンパイラは、ソースコードを直接機械語に変換するのではなく、通常、いくつかの段階を経て変換を行います。中間表現（IR）は、この変換プロセスの中間段階で用いられる、ソースコードとターゲットマシンコードの中間的な形式です。IRは、コンパイラのフロントエンド（構文解析、意味解析など）とバックエンド（最適化、コード生成など）の間の橋渡し役となります。

IRには様々な種類がありますが、一般的には、ソース言語のセマンティクスを保持しつつ、機械に依存しない形で表現されます。これにより、コンパイラの各ステージを独立して開発・最適化することが可能になります。

### 静的単一割り当て (SSA: Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において非常に重要な中間表現の一種です。SSA形式では、プログラム中の各変数が「一度だけ」定義されるという特性を持ちます。もし同じ変数名が複数回代入される場合、SSA形式ではそれぞれの代入に対して新しい「バージョン」の変数を導入します（例: `x1 = ...`, `x2 = ...`）。

SSA形式の主な利点は以下の通りです。

*   **データフロー解析の簡素化**: 各変数の定義が単一であるため、変数の値がどこから来るのか、どこで使われるのかといったデータフローを容易に追跡できます。
*   **最適化の効率化**: 共通部分式除去（CSE）、定数伝播、デッドコード除去など、多くのコンパイラ最適化がSSA形式上で効率的に実装できます。
*   **レジスタ割り当ての改善**: 変数のライフタイムが明確になるため、レジスタ割り当ての精度が向上します。

SSA形式への変換には、複数の制御フローパスが合流する点（例: if文の終わり、ループの終わり）で、異なるバージョンの変数を結合するための特別な命令「Φ（ファイ）関数」が導入されます。Φ関数は、どのパスから来たかによって適切な変数のバージョンを選択します。

### Goコンパイラのアーキテクチャ（概要）

Goコンパイラは、伝統的に以下のような構造を持っています。

1.  **フロントエンド**: ソースコードを解析し、抽象構文木（AST）を構築します。型チェックや名前解決もここで行われます。
2.  **中間処理（Walk）**: ASTを走査し、一部の最適化や変換（例: スライス操作の展開、マップ操作の組み込み関数呼び出しへの変換）を行います。この段階で、Go独自のツリーベースIRが生成されます。
3.  **バックエンド（コード生成）**: 中間表現からターゲットアーキテクチャの機械語コードを生成します。

このコミットは、上記の中間処理（Walk）の後、バックエンドのコード生成の前にSSA変換を挿入するものです。

### `gc.Type` の直接利用

コミットメッセージにもあるように、SSA内部でGoの型を扱う際に、`gc.Type` を直接利用するように変更されています。これにより、型情報の変換やラッパーの導入が不要になり、IRからSSAへの変換ロジックが大幅に簡素化されています。`src/cmd/internal/gc/type.go` には、`gc.Type` を `cmd/internal/ssa.Type` としてエクスポートするためのメソッドが追加されています。

### `ssaState` 構造体

SSA変換の主要なロジックは、新しく追加された `src/cmd/internal/gc/ssa.go` ファイル内の `ssaState` 構造体にカプセル化されています。この構造体は、SSA変換中の状態を管理します。

```go
// src/cmd/internal/gc/ssa.go
type ssaState struct {
    // configuration (arch) information
    config *ssa.Config

    // function we're building
    f *ssa.Func

    // exit block that "return" jumps to (and panics jump to)
    exit *ssa.Block

    // the target block for each label in f
    labels map[string]*ssa.Block

    // current location where we're interpreting the AST
    curBlock *ssa.Block

    // variable assignments in the current block (map from variable name to ssa value)
    vars map[string]*ssa.Value

    // all defined variables at the end of each block.  Indexed by block ID.
    defvars []map[string]*ssa.Value

    // offsets of argument slots
    // unnamed and unused args are not listed.
    argOffsets map[string]int64
}
```

`ssaState` は、現在のSSA関数 (`f`)、終了ブロック (`exit`)、ラベルのマッピング (`labels`)、現在のブロック (`curBlock`)、現在のブロックでの変数定義 (`vars`)、各ブロック終了時の変数定義 (`defvars`)、引数のオフセット (`argOffsets`) などの情報を含んでいます。

### SSAグラフ構築アルゴリズム

`buildssa` 関数は、ASTベースのIRをSSAベースのIRに変換するために、Brau, Buchwald, Hack, Leißa, Mallon, and Zwinkau の論文で記述されているアルゴリズムに類似した手法を使用しています。このアルゴリズムは、主に以下のステップでSSAグラフを構築します。

1.  **初期ブロックと終了ブロックの作成**: 関数のエントリブロックと終了ブロックを初期化します。
2.  **ASTの走査とSSA値の生成**: `stmtList` および `stmt` 関数がASTノードを再帰的に走査し、対応するSSA値を生成します。`expr` 関数は式をSSA値に変換します。
3.  **前方参照の解決とΦ関数の挿入**: `linkForwardReferences` 関数が、各変数の最初の使用箇所（前方参照）を、その変数の定義とリンクします。複数の制御フローパスが合流する点では、必要に応じてΦ関数が挿入され、適切な変数のバージョンが選択されます。これは `lookupVarIncoming` と `lookupVarOutgoing` 関数によって実現されます。

### 実装されたオペコード

このコミットでは、ごく一部のSSAオペコードのみが実装されています。これは、`func f(p *int) int { return *p }` や `func g(a []int, i int) int { return a[i] }` のような単純な例をコンパイルするのに十分な範囲です。具体的には、`OAS` (代入)、`OIF` (if文)、`OFOR` (forループ)、`ORETURN` (return文) などのASTノードに対応するSSA変換ロジックが追加されています。また、`OLITERAL` (リテラル)、`OLT` (より小さい)、`OADD` (加算)、`OSUB` (減算)、`OIND` (間接参照)、`ODOTPTR` (ポインタフィールドアクセス)、`OINDEX` (配列/スライスインデックス)、`OCALLFUNC` (関数呼び出し) などの式に対応するSSA値生成も含まれています。

## コアとなるコードの解説

### `src/cmd/internal/gc/ssa.go`

このファイルは、GoコンパイラのAST（抽象構文木）からSSA形式への変換を行う中心的なロジックを含んでいます。

*   **`buildssa(fn *Node)`**:
    *   Go関数のASTノード `fn` を受け取り、SSA形式の関数 `s.f` を構築します。
    *   `ssa.NewConfig` を呼び出してアーキテクチャ固有のSSA設定を初期化します。
    *   関数のエントリブロック (`s.f.Entry`) と終了ブロック (`s.exit`) を作成します。
    *   `ssaState` 構造体の `vars` (現在のブロックの変数定義) と `labels` (GOTOラベルのターゲットブロック) を初期化します。
    *   `s.stmtList(fn.Nbody)` を呼び出して、関数の本体（ステートメントリスト）をSSAに変換します。
    *   終了ブロックの処理を行い、`s.exit.Control = s.mem()` でメモリ状態を制御値として設定します。
    *   `s.linkForwardReferences()` を呼び出して、SSA形式の重要なステップである前方参照の解決とΦ関数の挿入を行います。
    *   最後に `ssa.Compile(s.f)` を呼び出しますが、この段階ではまだSSAからコード生成は行われず、生成されたアセンブリは破棄されます。

*   **`ssaState` 構造体**:
    *   `config`: SSAのアーキテクチャ設定（例: "amd64"）。
    *   `f`: 現在構築中のSSA関数。
    *   `exit`: 関数の終了ブロック。`return` や `panic` がジャンプする先。
    *   `labels`: GOTOラベル名と対応するSSAブロックのマッピング。
    *   `curBlock`: 現在SSA値を生成しているブロック。
    *   `vars`: 現在のブロックで定義された変数名とSSA値のマッピング。
    *   `defvars`: 各ブロックの終了時点で定義されている変数（ブロックIDでインデックス付け）。Φ関数挿入のために使用されます。
    *   `argOffsets`: 引数スロットのオフセット。

*   **`startBlock(b *ssa.Block)` / `endBlock() *ssa.Block`**:
    *   `startBlock` は、SSA値を生成する現在のブロックを設定し、`vars` マップをクリアします。
    *   `endBlock` は、現在のブロックでのSSA値生成の終了をマークし、そのブロックの終了時点での変数定義を `defvars` に保存します。

*   **`stmt(n *Node)` / `stmtList(l *NodeList)`**:
    *   ASTのステートメントノード `n` を受け取り、対応するSSA値を生成します。
    *   `OBLOCK` (ブロック)、`OLABEL` (ラベル)、`OGOTO` (GOTO)、`OAS` (代入)、`OIF` (if文)、`OFOR` (forループ)、`ORETURN` (return文) などのASTノードに対応するSSA変換ロジックが含まれています。
    *   `OIF` や `OFOR` のような制御フローを伴うステートメントでは、新しいSSAブロックを作成し、エッジを追加して制御フローグラフを構築します。

*   **`expr(n *Node) *ssa.Value`**:
    *   ASTの式ノード `n` を受け取り、対応するSSA値（`*ssa.Value`）を返します。
    *   `ONAME` (変数名)、`OLITERAL` (リテラル)、`OLT` (より小さい)、`OADD` (加算)、`OSUB` (減算)、`OIND` (間接参照)、`ODOTPTR` (ポインタフィールドアクセス)、`OINDEX` (配列/スライスインデックス)、`OCALLFUNC` (関数呼び出し) などのASTノードに対応するSSA値生成ロジックが含まれています。
    *   ポインタのデリファレンス (`OIND`) やスライス/配列のインデックスアクセス (`OINDEX`) の際には、nilチェックや境界チェックのためのSSA値が挿入され、チェック失敗時には `s.exit` ブロック（パニックを発生させる可能性のあるブロック）へのエッジが追加されます。

*   **`variable(name string, t ssa.Type) *ssa.Value`**:
    *   指定された名前 `name` と型 `t` を持つ変数のSSA値を返します。
    *   もし変数が現在のブロックでまだ定義されていない場合、`OpFwdRef` (前方参照) オペコードを持つ新しいSSA値を作成します。これは後で `linkForwardReferences` によって解決されます。

*   **`mem() *ssa.Value`**:
    *   メモリ状態を表す特別なSSA値（`.mem` という名前）を返します。SSAでは、メモリ操作も値として扱われ、メモリの依存関係を明示的に表現します。

*   **`linkForwardReferences()`**:
    *   SSAグラフ構築の重要なフェーズです。各SSAブロックを走査し、`OpFwdRef` オペコードを持つSSA値（前方参照）を見つけます。
    *   これらの前方参照を、その変数の実際の定義とリンクします。
    *   複数の制御フローパスが合流するブロックでは、必要に応じてΦ関数（`OpPhi`）を挿入します。Φ関数は、そのブロックに到達したパスに応じて、適切な変数のバージョンを選択します。

*   **`lookupVarIncoming(b *ssa.Block, t ssa.Type, name string) *ssa.Value`**:
    *   ブロック `b` の開始時点での変数 `name` のSSA値を見つけます。
    *   もし `b` がエントリブロックの場合、引数として渡された変数をロードします。
    *   それ以外の場合、先行ブロックからの変数の値を探し、もし複数の先行ブロックから異なる値が来る場合はΦ関数を生成します。

*   **`lookupVarOutgoing(b *ssa.Block, t ssa.Type, name string) *ssa.Value`**:
    *   ブロック `b` の終了時点での変数 `name` のSSA値を見つけます。
    *   もし変数が `b` 内で定義されている場合、その定義されたSSA値を返します。
    *   定義されていない場合、`OpCopy` オペコードを持つSSA値を作成し、`lookupVarIncoming` を再帰的に呼び出して、その変数の入力値を解決します。

### `src/cmd/internal/ssa/lowerAmd64.go`

このファイルは、AMD64アーキテクチャに特化したSSAオペコードのローワーリングルールを含んでいます。ローワーリングとは、高レベルのSSAオペコードを、より低レベルでターゲットマシンに特化したオペコードに変換するプロセスです。

*   **`lowerAmd64(v *Value) bool`**:
    *   SSA値 `v` を受け取り、そのオペコードに基づいてAMD64固有の命令に変換できるかどうかをチェックします。
    *   例えば、`OpAdd` (汎用加算) が `OpADDQ` (64ビット加算) や `OpADDL` (32ビット加算) に変換されるルールが含まれています。
    *   `OpLoad` や `OpStore` のようなメモリ操作は、`OpMOVQload` や `OpMOVQstore` のような具体的なロード/ストア命令に変換されます。
    *   `OpCheckBound` (境界チェック) や `OpCheckNil` (nilチェック) は、`OpSETB` (セットバイト) や `OpSETNE` (セット非等しい) といったフラグ操作と組み合わせた比較命令に変換されます。
    *   `OpMULQ` (64ビット乗算) は、定数乗算の場合に `OpSHLCQ` (左シフト) に最適化されるルールも含まれています。
    *   これらのルールは、`rulegen` ツールによって生成されたGoコードであり、パターンマッチングと置換によってSSAグラフを変換します。

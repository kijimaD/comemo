# [インデックス 19848] ファイルの概要

このコミットは、Goランタイムのメモリ割り当てメカニズムをC言語からGo言語へ移行する重要な変更を含んでいます。具体的には、`mallocgc`というメモリ割り当て関数がGo言語で再実装され、`gomallocgc`として導入されました。これにより、Goランタイムのより多くの部分がGo言語で記述されることになり、Goのガベージコレクションとの連携や、将来的な最適化の可能性が広がります。

変更された主なファイルは以下の通りです。

*   `src/cmd/api/goapi.go`: Go API定義に関連する変更。
*   `src/cmd/cc/godefs.c`: C言語の定義をGoに変換する部分の変更。
*   `src/cmd/gc/builtin.c`, `src/cmd/gc/runtime.go`, `src/cmd/gc/walk.c`: Goコンパイラのバックエンドにおける組み込み関数やランタイム関数の参照に関する変更。特に`new`が`newobject`にリネームされています。
*   `src/pkg/runtime/asm_*.s`: 各アーキテクチャ（386, amd64, amd64p32, arm）のアセンブリコードに、GoルーチンとOSスレッド間のスタック切り替えを管理する`onM`関数が追加されています。
*   `src/pkg/runtime/extern.go`: 外部から参照されるGoランタイムの関数定義に関する変更。`SetFinalizer`の定義が削除されています。
*   `src/pkg/runtime/hashmap.go`: マップの内部実装で、`unsafe_NewArray`や`unsafe_New`の代わりに新しいGoベースのメモリ割り当て関数（`newarray`, `newobject`）が使用されるように変更されています。
*   `src/pkg/runtime/{malloc.goc => malloc.c}`: 従来のC言語で書かれた`mallocgc`の実装ファイルが`malloc.c`にリネームされ、その内容が大幅に削減されています。Go言語で実装された`gomallocgc`を呼び出すためのラッパー関数`cmallocgc`が追加されています。
*   `src/pkg/runtime/malloc.go`: 新たにGo言語で`gomallocgc`が実装されたファイルです。Goのメモリ割り当てロジックの大部分がここに記述されています。
*   `src/pkg/runtime/malloc.h`: メモリ割り当てに関連するC言語のヘッダファイル。新しい構造体やマクロが追加・変更されています。
*   `src/pkg/runtime/mem.go`: メモリ統計に関するGoファイル。
*   `src/pkg/runtime/mgc0.c`: ガベージコレクションのC言語実装ファイル。GCのトリガーや統計更新ロジックが変更されています。
*   `src/pkg/runtime/mprof.goc`: メモリプロファイリングに関するC言語実装ファイル。Go言語からの呼び出しに対応するための変更が含まれています。
*   `src/pkg/runtime/proc.c`: プロセス管理に関するC言語実装ファイル。スタックトレースの終端条件に`onM`が追加されています。
*   `src/pkg/runtime/race.go`: データ競合検出に関するGoファイル。
*   `src/pkg/runtime/runtime.h`: GoランタイムのC言語ヘッダファイル。新しい型定義や関数プロトタイプが追加されています。
*   `src/pkg/runtime/string.go`: 文字列操作に関するGoファイル。`rawstring`, `rawbyteslice`, `rawruneslice`といった生データからの文字列・スライス生成関数がGo言語で再実装されています。

## 変更の背景

Go言語の初期のランタイムは、パフォーマンスと低レベルなシステム操作の必要性から、C言語とアセンブリ言語で記述された部分が多く存在しました。しかし、Go言語自体が成熟し、ガベージコレクション（GC）やスケジューラといったランタイムのコア機能が複雑になるにつれて、C言語とGo言語の混在は開発の複雑性を増し、デバッグを困難にする要因となっていました。

特にメモリ割り当ては、GCと密接に連携する必要があるため、C言語で実装されているとGoのGCの進化に追従するのが難しくなるという課題がありました。このコミットの背景には、Goランタイムの「Go化」を進めるという長期的な目標があります。メモリ割り当てのロジックをGo言語で再実装することで、以下のようなメリットが期待されます。

1.  **GCとの連携強化**: Go言語でメモリ割り当てを行うことで、GCがオブジェクトのライフサイクルやポインタ情報をより正確に把握し、効率的なマーク＆スイープ処理を行うことが容易になります。
2.  **コードの可読性と保守性の向上**: Go言語はC言語に比べて抽象度が高く、並行処理を記述しやすい特性があります。メモリ割り当てロジックがGoで書かれることで、開発者がコードを理解し、変更を加える際の障壁が低減されます。
3.  **Go言語の機能活用**: Go言語の持つ豊富な機能やツール（例: プロファイラ、デバッガ）をメモリ割り当てのデバッグや最適化に直接活用できるようになります。
4.  **将来的な最適化の可能性**: Go言語のコンパイラやランタイムの最適化が、メモリ割り当てパスにも直接適用されるようになり、全体的なパフォーマンス向上が期待されます。

このコミットは、`mallocgc`というGoオブジェクトのメモリ割り当てを担う重要な関数をGo言語で再実装する第一歩であり、ランタイムのGo化に向けた大きなマイルストーンと言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

### Goランタイムの基本要素 (GMPモデル)

Goランタイムは、Goroutine (G)、Logical Processor (P)、OS Thread (M) の3つの要素からなるGMPモデルで並行処理を管理しています。

*   **G (Goroutine)**: Go言語の軽量な実行単位。数KB程度のスタックを持ち、数百万個作成することも可能です。Goプログラムの関数呼び出しはGoroutine上で行われます。
*   **M (OS Thread)**: オペレーティングシステムのスレッド。Goのコードを実行する実際のOSスレッドです。MはGのコードを実行し、システムコールなどを担当します。
*   **P (Logical Processor)**: MとGを仲介する論理的なプロセッサ。PはMにGを割り当て、Gの実行をスケジュールします。Pの数は通常、CPUのコア数に設定され、並行実行の度合いを制御します。

このコミットでは、GoコードがMスタック上で実行される`onM`関数が導入されており、GとMのスタック管理の理解が重要になります。

### Goのメモリ管理とガベージコレクション (GC)

Goのメモリ管理は、主にヒープ領域からのオブジェクト割り当てと、ガベージコレクタによる不要なオブジェクトの自動解放によって行われます。

*   **ヒープ (Heap)**: Goプログラムが動的に確保するメモリ領域。`new`や`make`で作成されるオブジェクトはヒープに割り当てられます。
*   **スタック (Stack)**: 関数呼び出しやローカル変数が格納されるメモリ領域。Goroutineごとに独立したスタックを持ちます。
*   **`mcache` (Per-P/M Cache)**: 各P（またはM）が持つローカルなメモリキャッシュ。小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`からの割り当てはロックフリーで行われます。
*   **`mspan`**: 連続したメモリページ（通常は8KB）の塊。`mcache`は`mspan`からメモリブロックを割り当てます。
*   **`mheap` (Global Heap)**: 全ての`mcache`がメモリを要求するグローバルなヒープ。`mheap`からの割り当てはロックを伴います。
*   **ガベージコレクション (GC)**: GoのGCは、到達可能なオブジェクトをマークし、到達不能なオブジェクトをスイープ（解放）するマーク＆スイープ方式を採用しています。GCはGoプログラムの実行中に並行して動作します。

`mallocgc`（そして新しい`gomallocgc`）は、これらのメモリ管理コンポーネンの最上位に位置し、Goプログラムからのメモリ割り当て要求を処理し、適切な`mcache`や`mheap`からメモリを取得する役割を担います。

### CgoとGo/C間の相互作用

Go言語はC言語のコードを呼び出すためのCgoというメカニズムを提供しています。Goランタイムの初期バージョンでは、メモリ割り当てのような低レベルな処理はC言語で実装されていました。Cgoを介したGoとCの間の呼び出しにはオーバーヘッドがあり、また、異なるメモリ管理モデルを持つため、複雑な相互作用が発生することがあります。このコミットは、このCgoの依存関係を減らし、Goランタイムの「純粋なGo」化を進める一環です。

### アセンブリ言語の役割

Goランタイムには、OSとのインタフェースや、パフォーマンスがクリティカルな部分（例: コンテキストスイッチ、アトミック操作）でアセンブリ言語が使用されています。このコミットでは、`onM`のようなスタック操作に関連する関数がアセンブリで実装されており、GoルーチンとOSスレッドのスタック切り替えの理解に役立ちます。

## 技術的詳細

このコミットの核となる変更は、Goランタイムのメモリ割り当て関数である`mallocgc`をC言語からGo言語に移植し、`gomallocgc`として導入したことです。

### `mallocgc`から`gomallocgc`への移行

従来のGoランタイムでは、Goオブジェクトのメモリ割り当てはC言語で実装された`runtime.mallocgc`関数によって行われていました。このコミットでは、その機能をGo言語で再実装した`runtime.gomallocgc`が導入されました。

*   **`src/pkg/runtime/malloc.go`の新規追加**: このファイルに`gomallocgc`のGo言語実装が記述されています。`gomallocgc`は、Goプログラムからのメモリ割り当て要求を受け付け、サイズに応じて「Tinyオブジェクト」「Smallオブジェクト」「Largeオブジェクト」のいずれかの割り当てパスを選択します。
    *   **Tinyオブジェクト**: 16バイト以下のポインタを含まないオブジェクト（`flagNoScan`がセットされているもの）。`mcache`の`tiny`フィールドから割り当てられます。これは、小さな文字列やエスケープする変数の割り当てを最適化するためのものです。
    *   **Smallオブジェクト**: `maxSmallSize` (32KB) 以下のオブジェクト。`mcache`のフリーリストから割り当てられます。`mcache`が空の場合、`mcacheRefill`を呼び出して`mspan`を補充します。
    *   **Largeオブジェクト**: `maxSmallSize`を超えるオブジェクト。`mheap`から直接割り当てられます。`largeAlloc`関数がこの処理を担当します。
*   **`src/pkg/runtime/malloc.goc`から`src/pkg/runtime/malloc.c`へのリネームと簡素化**: 従来のC言語の`mallocgc`実装は`malloc.c`に移動され、その内容は大幅に簡素化されました。C言語側からGo言語の`gomallocgc`を呼び出すためのラッパー関数`runtime.cmallocgc`が追加されています。これにより、まだC言語のコードから`mallocgc`を呼び出している箇所は、`cmallocgc`を介してGo言語の`gomallocgc`を利用する形になります。

### `onM`関数の導入とMスタックでのGoコード実行

Goランタイムでは、GoroutineはGスタック上で実行されますが、一部の低レベルなランタイム処理（例: GCの開始、メモリ割り当てのクリティカルパス）はOSスレッドのMスタック上で実行される必要があります。これは、GスタックがGCの対象となるため、GC中にGスタックを操作するとデッドロックや不整合が発生する可能性があるためです。

このコミットでは、`runtime.onM`という関数が導入されました。これは、Go言語の関数をMスタック上で実行するためのメカニズムを提供します。

*   `onM`は各アーキテクチャのアセンブリファイル（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）で実装されています。
*   `onM`は引数としてGo関数のポインタを受け取り、現在のGスタックの状態を保存し、Mスタックに切り替えてからそのGo関数を実行します。関数が終了すると、元のGスタックに戻ります。
*   `gomallocgc`内部では、`mcacheRefill`（`mcache`の補充）や`largeAlloc`（大きなオブジェクトの割り当て）、`markallocated_m`（割り当てられたオブジェクトのマーク）といった処理が`onM`を介してMスタック上で実行されるようになっています。これにより、これらのクリティカルな処理がGCの影響を受けずに安全に実行できるようになります。

### `new`組み込み関数の変更

Go言語の組み込み関数である`new`は、型に基づいて新しいオブジェクトを割り当てるために使用されます。このコミットでは、`new`の内部実装が変更され、`runtime.newobject`という新しい関数を呼び出すようになりました。`newobject`は最終的にGo言語で実装された`gomallocgc`を呼び出します。同様に、`make`でスライスを生成する際に使われる`unsafe_NewArray`も`newarray`に置き換えられ、これも`gomallocgc`を利用します。

### `SetFinalizer`の変更

`runtime.SetFinalizer`は、オブジェクトがGCによって到達不能になったときに実行される関数を設定するためのものです。このコミットでは、`SetFinalizer`のGo言語実装が`src/pkg/runtime/malloc.go`に移動され、その内部で`onM`を介してC言語の`setFinalizer`を呼び出すようになりました。これは、ファイナライザの設定がメモリ割り当てと密接に関連しており、Mスタック上で安全に実行する必要があるためです。

### メモリプロファイリングとGC統計の更新

メモリ割り当てロジックがGo言語に移行したことに伴い、メモリプロファイリング（`profilealloc`）やGC統計の更新（`memstats.next_gc`の計算）もGo言語側から呼び出されるようになりました。これらの処理も`onM`を介してMスタック上で実行されることで、正確性と安全性が保たれます。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.go` の `gomallocgc`

```go
func gomallocgc(size uintptr, typ *_type, flags int) unsafe.Pointer {
	if size == 0 {
		return unsafe.Pointer(&zeroObject)
	}
	mp := acquirem() // Mを取得し、ロックカウントを増やす
	if mp.mallocing != 0 {
		gothrow("malloc/free - deadlock")
	}
	mp.mallocing = 1 // mallocingフラグをセット

	// ... (Tiny, Small, Largeオブジェクトの割り当てロジック) ...

	// TODO: write markallocated in Go
	// 割り当てられたオブジェクトのマーク処理をMスタック上で実行
	mp.ptrarg[0] = x
	mp.scalararg[0] = uint(size)
	mp.scalararg[1] = uint(size0)
	mp.ptrarg[1] = unsafe.Pointer(typ)
	mp.scalararg[2] = uint(flags & flagNoScan)
	onM(&markallocated_m) // Mスタック上でmarkallocated_mを呼び出す

	mp.mallocing = 0 // mallocingフラグをクリア

	// ... (レース検出、プロファイリング、GCトリガーのロジック) ...

	releasem(mp) // Mを解放し、ロックカウントを減らす

	return x
}
```
`gomallocgc`は、Go言語で書かれた新しいメモリ割り当てのメイン関数です。
*   `acquirem()`と`releasem(mp)`: メモリ割り当て処理中にM（OSスレッド）を「取得」し、処理が完了したら「解放」します。これにより、メモリ割り当て中のプリエンプション（横取り）を防ぎ、アトミックな操作を保証します。`mp.mallocing`フラグは、再入を検出してデッドロックを防ぐために使用されます。
*   **割り当てロジック**: `size`に基づいて、Tiny、Small、Largeのいずれかの割り当てパスに分岐します。
    *   **Tinyオブジェクト**: `maxTinySize` (16バイト) 未満でポインタを含まないオブジェクト向け。`mcache`の`tiny`バッファから高速に割り当てます。
    *   **Smallオブジェクト**: `maxSmallSize` (32KB) 未満のオブジェクト向け。`mcache`のサイズクラスに応じたフリーリストから割り当てます。フリーリストが空の場合、`onM(&mcacheRefill)`を呼び出して`mcache`を補充します。
    *   **Largeオブジェクト**: `maxSmallSize`以上のオブジェクト向け。`onM(&largeAlloc)`を呼び出して`mheap`から直接割り当てます。
*   `onM(&markallocated_m)`: 割り当てられたメモリブロックをGCがスキャンできるようにマークする処理です。この処理はGCと密接に関連するため、Mスタック上で安全に実行されます。

### `src/pkg/runtime/asm_*.s` の `onM`

```assembly
// void onM(void (*fn)())
// calls fn() on the M stack.
// switches to the M stack if not already on it, and
// switches back when fn() returns.
TEXT runtime·onM(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn (Go関数のポインタ)
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g (現在のGoroutine)
	MOVQ	g_m(AX), BX	// BX = m (現在のOSスレッド)
	MOVQ	m_g0(BX), DX	// DX = g0 (Mスタックに対応するGoroutine)
	CMPQ	AX, DX
	JEQ	onm // 既にMスタック上なら直接呼び出し

	// save our state in g->sched.  Pretend to
	// be switchtoM if the G stack is scanned.
	MOVQ	$runtime·switchtoM(SB), (g_sched+gobuf_pc)(AX) // GスタックのPCを保存
	MOVQ	SP, (g_sched+gobuf_sp)(AX) // GスタックのSPを保存
	MOVQ	AX, (g_sched+gobuf_g)(AX) // Gを保存

	// switch to g0
	MOVQ	DX, g(CX) // gをg0に切り替え
	MOVQ	(g_sched+gobuf_sp)(DX), SP // SPをg0のスタックポインタに切り替え

	// call target function
	ARGSIZE(0)
	CALL	DI // Go関数を呼び出し

	// switch back to g
	get_tls(CX)
	MOVQ	g(CX), AX
	MOVQ	g_m(AX), BX
	MOVQ	m_curg(BX), AX // 現在のGを取得
	MOVQ	AX, g(CX) // gを元のGに戻す
	MOVQ	(g_sched+gobuf_sp)(AX), SP // SPを元のGスタックポインタに戻す
	MOVQ	$0, (g_sched+gobuf_sp)(AX) // 保存したSPをクリア
	RET

onm:
	// already on m stack, just call directly
	CALL	DI // 直接Go関数を呼び出し
	RET
```
`onM`は、Goランタイムの重要なアセンブリ関数で、Go関数をMスタック上で実行するために使用されます。
*   **スタック切り替え**: 現在のGoroutine (G) がMスタック上で実行されていない場合、`onM`は現在のGのコンテキスト（プログラムカウンタ、スタックポインタなど）を保存し、Mスタックに対応する特別なGoroutine (`g0`) に切り替えます。これにより、Go関数はMスタック上で安全に実行されます。
*   **関数呼び出し**: Mスタックに切り替わった後、引数として渡されたGo関数を呼び出します。
*   **スタック復元**: Go関数の実行が完了すると、`onM`は元のGのコンテキストを復元し、Gスタックに戻ります。
このメカニズムにより、GC中にGスタックが移動する可能性のあるGoコードを、GCの影響を受けないMスタック上で実行できるようになります。

	flags := 0
	if typ.kind&kindNoPointers != 0 {
		flags |= flagNoScan
	}

3.  **Go言語の機能活用**: Go言語の持つ豊富な機能やツール（例: プロファイラ、デバッガ）をメモリ割り当てのデバッグや最適化に直接活用できるようになります。
4.  **将来的な最適化の可能性**: Go言語のコンパイラやランタイムの最適化が、メモリ割り当てパスにも直接適用されるようになり、全体的なパフォーマンス向上が期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

### Goランタイムの基本要素 (GMPモデル)

Goランタイムは、Goroutine (G)、Logical Processor (P)、OS Thread (M) の3つの要素からなるGMPモデルで並行処理を管理しています。

*   **G (Goroutine)**: Go言語の軽量な実行単位。数KB程度のスタックを持ち、数百万個作成することも可能です。Goプログラムの関数呼び出しはGoroutine上で行われます。
*   **M (OS Thread)**: オペレーティングシステムのスレッド。Goのコードを実行する実際のOSスレッドです。MはGのコードを実行し、システムコールなどを担当します。
*   **P (Logical Processor)**: MとGを仲介する論理的なプロセッサ。PはMにGを割り当て、Gの実行をスケジュールします。Pの数は通常、CPUのコア数に設定され、並行実行の度合いを制御します。

このコミットでは、GoコードがMスタック上で実行される`onM`関数が導入されており、GとMのスタック管理の理解が重要になります。

### Goのメモリ管理とガベージコレクション (GC)

Goのメモリ管理は、主にヒープ領域からのオブジェクト割り当てと、ガベージコレクタによる不要なオブジェクトの自動解放によって行われます。

*   **ヒープ (Heap)**: Goプログラムが動的に確保するメモリ領域。`new`や`make`で作成されるオブジェクトはヒープに割り当てられます。
*   **スタック (Stack)**: 関数呼び出しやローカル変数が格納されるメモリ領域。Goroutineごとに独立したスタックを持ちます。
*   **`mcache` (Per-P/M Cache)**: 各P（またはM）が持つローカルなメモリキャッシュ。小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`からの割り当てはロックフリーで行われます。
*   **`mspan`**: 連続したメモリページ（通常は8KB）の塊。`mcache`は`mspan`からメモリブロックを割り当てます。
*   **`mheap` (Global Heap)**: 全ての`mcache`がメモリを要求するグローバルなヒープ。`mheap`からの割り当てはロックを伴います。
*   **ガベージコレクション (GC)**: GoのGCは、到達可能なオブジェクトをマークし、到達不能なオブジェクトをスイープ（解放）するマーク＆スイープ方式を採用しています。GCはGoプログラムの実行中に並行して動作します。

`mallocgc`（そして新しい`gomallocgc`）は、これらのメモリ管理コンポーネントの最上位に位置し、Goプログラムからのメモリ割り当て要求を処理し、適切な`mcache`や`mheap`からメモリを取得する役割を担います。

### CgoとGo/C間の相互作用

Go言語はC言語のコードを呼び出すためのCgoというメカニズムを提供しています。Goランタイムの初期バージョンでは、メモリ割り当てのような低レベルな処理はC言語で実装されていました。Cgoを介したGoとCの間の呼び出しにはオーバーヘッドがあり、また、異なるメモリ管理モデルを持つため、複雑な相互作用が発生することがあります。このコミットは、このCgoの依存関係を減らし、Goランタイムの「純粋なGo」化を進める一環です。

### アセンブリ言語の役割

Goランタイムには、OSとのインタフェースや、パフォーマンスがクリティカルな部分（例: コンテキストスイッチ、アトミック操作）でアセンブリ言語が使用されています。このコミットでは、`onM`のようなスタック操作に関連する関数がアセンブリで実装されており、GoルーチンとOSスレッドのスタック切り替えの理解に役立ちます。

## 技術的詳細

### `mallocgc`から`gomallocgc`への移行

従来のGoランタイムでは、Goオブジェクトのメモリ割り当てはC言語で実装された`runtime.mallocgc`関数によって行われていました。このコミットでは、その機能をGo言語で再実装した`runtime.gomallocgc`が導入されました。

*   **`src/pkg/runtime/malloc.go`の新規追加**: このファイルに`gomallocgc`のGo言語実装が記述されています。`gomallocgc`は、Goプログラムからのメモリ割り当て要求を受け付け、サイズに応じて「Tinyオブジェクト」「Smallオブジェクト」「Largeオブジェクト」のいずれかの割り当てパスを選択します。
    *   **Tinyオブジェクト**: 16バイト以下のポインタを含まないオブジェクト（`flagNoScan`がセットされているもの）。`mcache`の`tiny`フィールドから割り当てられます。これは、小さな文字列やエスケープする変数の割り当てを最適化するためのものです。
    *   **Smallオブジェクト**: `maxSmallSize` (32KB) 以下のオブジェクト。`mcache`のフリーリストから割り当てられます。`mcache`が空の場合、`mcacheRefill`を呼び出して`mspan`を補充します。
    *   **Largeオブジェクト**: `maxSmallSize`を超えるオブジェクト。`mheap`から直接割り当てられます。`largeAlloc`関数がこの処理を担当します。
*   **`src/pkg/runtime/malloc.goc`から`src/pkg/runtime/malloc.c`へのリネームと簡素化**: 従来のC言語の`mallocgc`実装は`malloc.c`に移動され、その内容は大幅に簡素化されました。C言語側からGo言語の`gomallocgc`を呼び出すためのラッパー関数`runtime.cmallocgc`が追加されています。これにより、まだC言語のコードから`mallocgc`を呼び出している箇所は、`cmallocgc`を介してGo言語の`gomallocgc`を利用する形になります。

### `onM`関数の導入とMスタックでのGoコード実行

Goランタイムでは、GoroutineはGスタック上で実行されますが、一部の低レベルなランタイム処理（例: GCの開始、メモリ割り当てのクリティカルパス）はOSスレッドのMスタック上で実行される必要があります。これは、GスタックがGCの対象となるため、GC中にGスタックを操作するとデッドロックや不整合が発生する可能性があるためです。

このコミットでは、`runtime.onM`という関数が導入されました。これは、Go言語の関数をMスタック上で実行するためのメカニズムを提供します。

*   `onM`は各アーキテクチャのアセンブリファイル（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）で実装されています。
*   `onM`は引数としてGo関数のポインタを受け取り、現在のGスタックの状態を保存し、Mスタックに切り替えてからそのGo関数を実行します。関数が終了すると、元のGスタックに戻ります。
*   `gomallocgc`内部では、`mcacheRefill`（`mcache`の補充）や`largeAlloc`（大きなオブジェクトの割り当て）、`markallocated_m`（割り当てられたオブジェクトのマーク）といった処理が`onM`を介してMスタック上で実行されるようになっています。これにより、これらのクリティカルな処理がGCの影響を受けずに安全に実行できるようになります。

### `new`組み込み関数の変更

Go言語の組み込み関数である`new`は、型に基づいて新しいオブジェクトを割り当てるために使用されます。このコミットでは、`new`の内部実装が変更され、`runtime.newobject`という新しい関数を呼び出すようになりました。`newobject`は最終的にGo言語で実装された`gomallocgc`を呼び出します。同様に、`make`でスライスを生成する際に使われる`unsafe_NewArray`も`newarray`に置き換えられ、これも`gomallocgc`を利用します。

### `SetFinalizer`の変更

`runtime.SetFinalizer`は、オブジェクトがGCによって到達不能になったときに実行される関数を設定するためのものです。このコミットでは、`SetFinalizer`のGo言語実装が`src/pkg/runtime/malloc.go`に移動され、その内部で`onM`を介してC言語の`setFinalizer`を呼び出すようになりました。これは、ファイナライザの設定がメモリ割り当てと密接に関連しており、Mスタック上で安全に実行する必要があるためです。

### メモリプロファイリングとGC統計の更新

メモリ割り当てロジックがGo言語に移行したことに伴い、メモリプロファイリング（`profilealloc`）やGC統計の更新（`memstats.next_gc`の計算）もGo言語側から呼び出されるようになりました。これらの処理も`onM`を介してMスタック上で実行されることで、正確性と安全性が保たれます。

### `src/pkg/runtime/malloc.go` の `gomallocgc`

```go
func gomallocgc(size uintptr, typ *_type, flags int) unsafe.Pointer {
	if size == 0 {
		return unsafe.Pointer(&zeroObject)
	}
	mp := acquirem() // Mを取得し、ロックカウントを増やす
	if mp.mallocing != 0 {
		gothrow("malloc/free - deadlock")
	}
	mp.mallocing = 1 // mallocingフラグをセット

	// ... (Tiny, Small, Largeオブジェクトの割り当てロジック) ...

	// TODO: write markallocated in Go
	// 割り当てられたオブジェクトのマーク処理をMスタック上で実行
	mp.ptrarg[0] = x
	mp.scalararg[0] = uint(size)
	mp.scalararg[1] = uint(size0)
	mp.ptrarg[1] = unsafe.Pointer(typ)
	mp.scalararg[2] = uint(flags & flagNoScan)
	onM(&markallocated_m) // Mスタック上でmarkallocated_mを呼び出す

	mp.mallocing = 0 // mallocingフラグをクリア

	// ... (レース検出、プロファイリング、GCトリガーのロジック) ...

	releasem(mp) // Mを解放し、ロックカウントを減らす

	return x
}
```
`gomallocgc`は、Go言語で書かれた新しいメモリ割り当てのメイン関数です。
*   `acquirem()`と`releasem(mp)`: メモリ割り当て処理中にM（OSスレッド）を「取得」し、処理が完了したら「解放」します。これにより、メモリ割り当て中のプリエンプション（横取り）を防ぎ、アトミックな操作を保証します。`mp.mallocing`フラグは、再入を検出してデッドロックを防ぐために使用されます。
*   **割り当てロジック**: `size`に基づいて、Tiny、Small、Largeのいずれかの割り当てパスに分岐します。
    *   **Tinyオブジェクト**: `maxTinySize` (16バイト) 未満でポインタを含まないオブジェクト向け。`mcache`の`tiny`バッファから高速に割り当てます。
    *   **Smallオブジェクト**: `maxSmallSize` (32KB) 未満のオブジェクト向け。`mcache`のサイズクラスに応じたフリーリストから割り当てます。フリーリストが空の場合、`onM(&mcacheRefill)`を呼び出して`mcache`を補充します。
    *   **Largeオブジェクト**: `maxSmallSize`以上のオブジェクト向け。`onM(&largeAlloc)`を呼び出して`mheap`から直接割り当てます。
*   `onM(&markallocated_m)`: 割り当てられたメモリブロックをGCがスキャンできるようにマークする処理です。この処理はGCと密接に関連するため、Mスタック上で安全に実行されます。

### `src/pkg/runtime/asm_*.s` の `onM`

```assembly
// void onM(void (*fn)())
// calls fn() on the M stack.
// switches to the M stack if not already on it, and
// switches back when fn() returns.
TEXT runtime·onM(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn (Go関数のポインタ)
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g (現在のGoroutine)
	MOVQ	g_m(AX), BX	// BX = m (現在のOSスレッド)
	MOVQ	m_g0(BX), DX	// DX = g0 (Mスタックに対応するGoroutine)
	CMPQ	AX, DX
	JEQ	onm // 既にMスタック上なら直接呼び出し

	// save our state in g->sched.  Pretend to
	// be switchtoM if the G stack is scanned.
	MOVQ	$runtime·switchtoM(SB), (g_sched+gobuf_pc)(AX) // GスタックのPCを保存
	MOVQ	SP, (g_sched+gobuf_sp)(AX) // GスタックのSPを保存
	MOVQ	AX, (g_sched+gobuf_g)(AX) // Gを保存

	// switch to g0
	MOVQ	DX, g(CX) // gをg0に切り替え
	MOVQ	(g_sched+gobuf_sp)(DX), SP // SPをg0のスタックポインタに切り替え

	// call target function
	ARGSIZE(0)
	CALL	DI // Go関数を呼び出し

	// switch back to g
	get_tls(CX)
	MOVQ	g(CX), AX
	MOVQ	g_m(AX), BX
	MOVQ	m_curg(BX), AX // 現在のGを取得
	MOVQ	AX, g(CX) // gを元のGに戻す
	MOVQ	(g_sched+gobuf_sp)(AX), SP // SPを元のGスタックポインタに戻す
	MOVQ	$0, (g_sched+gobuf_sp)(AX) // 保存したSPをクリア
	RET

onm:
	// already on m stack, just call directly
	CALL	DI // 直接Go関数を呼び出し
	RET
```
`onM`は、Goランタイムの重要なアセンブリ関数で、Go関数をMスタック上で実行するために使用されます。
*   **スタック切り替え**: 現在のGoroutine (G) がMスタック上で実行されていない場合、`onM`は現在のGのコンテキスト（プログラムカウンタ、スタックポインタなど）を保存し、Mスタックに対応する特別なGoroutine (`g0`) に切り替えます。これにより、Go関数はMスタック上で安全に実行されます。
*   **関数呼び出し**: Mスタックに切り替わった後、引数として渡されたGo関数を呼び出します。
*   **スタック復元**: Go関数の実行が完了すると、`onM`は元のGのコンテキストを復元し、Gスタックに戻ります。
このメカニズムにより、GC中にGスタックが移動する可能性のあるGoコードを、GCの影響を受けないMスタック上で実行できるようになります。

### `src/pkg/runtime/malloc.go` の `newobject` と `newarray`

```go
// implementation of new builtin
func newobject(typ *_type) unsafe.Pointer {
	flags := 0
	if typ.kind&kindNoPointers != 0 {
		flags |= flagNoScan
	}
	return gomallocgc(uintptr(typ.size), typ, flags)
}

// implementation of make builtin for slices
func newarray(typ *_type, n uintptr) unsafe.Pointer {
	flags := 0
	if typ.kind&kindNoPointers != 0 {
		flags |= flagNoScan
	}
	if int(n) < 0 || (typ.size > 0 && n > maxMem/uintptr(typ.size)) {
		panic("runtime: allocation size out of range")
	}
	return gomallocgc(uintptr(typ.size)*n, typ, flags)
}
```
`newobject`と`newarray`は、それぞれGoの組み込み関数`new`と`make`（スライス用）の内部実装です。これらは、割り当てるオブジェクトの型情報（`_type`）とサイズに基づいて、最終的に`gomallocgc`を呼び出します。`kindNoPointers`フラグは、オブジェクトがポインタを含まない場合に`flagNoScan`を設定するために使用され、GCの効率を向上させます。

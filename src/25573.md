# [インデックス 25573] ファイルの概要

このコミットは、Goランタイムのガベージコレクタにおけるプロポーショナルスイープの挙動を修正するものです。具体的には、`src/runtime/mcentral.go` と `src/runtime/mgcsweep.go` の2つのファイルが変更されています。

## コミット

runtime: fix over-aggressive proportional sweep

Currently, sweeping is performed before allocating a span by charging
for the entire size of the span requested, rather than the number of
bytes actually available for allocation from the returned span. That
is, if the returned span is 8K, but already has 6K in use, the mutator
is charged for 8K of heap allocation even though it can only allocate
2K more from the span. As a result, proportional sweep is
over-aggressive and tends to finish much earlier than it needs to.
This effect is more amplified by fragmented heaps.

Fix this by reimbursing the mutator for the used space in a span once
it has allocated that span. We still have to charge up-front for the
worst-case because we don't know which span the mutator will get, but
at least we can correct the over-charge once it has a span, which will
go toward later span allocations.

This has negligible effect on the throughput of the go1 benchmarks and
the garbage benchmark.

Fixes #12040.

## 変更の背景

Goのガベージコレクタは、プログラムの実行と並行してメモリのクリーンアップを行う「コンカレントGC」を採用しています。このGCサイクルの一部として「スイープ（sweep）」というフェーズがあり、これはマークされなかった（つまり不要になった）オブジェクトが占めていたメモリを解放し、再利用可能にするプロセスです。

このスイープの実行量を調整するために「プロポーショナルスイープ（proportional sweep）」というメカニズムが導入されています。これは、ミューテータ（ユーザープログラム）がヒープにメモリを割り当てる量に応じて、スイープ作業を「チャージ」する（割り当てる）ことで、GC作業がヒープの成長に比例して行われるようにするものです。これにより、GCが一度に大量の作業を行う必要がなくなり、アプリケーションのレイテンシを低減する効果が期待されます。

しかし、このコミット以前のGoランタイムでは、プロポーショナルスイープのチャージ方法に問題がありました。具体的には、ミューテータが新しいメモリ領域（スパン）を要求した際、そのスパンの「全サイズ」に対してスイープクレジットがチャージされていました。たとえそのスパンが既に一部使用済みで、実際にミューテータが利用できる空き容量が少なかったとしても、全サイズがチャージの対象となっていたのです。

例えば、8KBのスパンが要求され、そのうち6KBが既に使われている場合、ミューテータは8KB分のヒープ割り当てとしてチャージされますが、実際に利用できるのは残りの2KBだけです。この「過剰なチャージ」により、プロポーショナルスイープは必要以上に早く完了してしまい、GCの効率が低下したり、特にヒープが断片化している場合にこの問題が顕著になることが指摘されていました。このコミットは、この過剰なチャージを是正し、プロポーショナルスイープの精度と効率を向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

Goのガベージコレクタは、主に以下の特徴を持ちます。

*   **コンカレントGC**: ユーザープログラム（ミューテータ）の実行と並行してGC処理の大部分が行われます。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、低レイテンシを実現します。
*   **トライカラーマーク＆スイープ**: オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みで参照先も訪問済み）」の3色でマークし、不要なオブジェクトを特定します。マークフェーズの後、スイープフェーズで不要なオブジェクトが占めるメモリを解放します。
*   **プロポーショナルスイープ**: ヒープの成長に合わせてスイープ作業を分散して実行するメカニズムです。ミューテータがメモリを割り当てるたびに、その割り当て量に応じてスイープ作業が「チャージ」され、GCワーカーがバックグラウンドでスイープを実行します。これにより、GCの作業がヒープの成長に追いつき、GCサイクル終了時に大量のスイープ作業が集中するのを防ぎます。

### `mspan` とは何か、その役割

Goのランタイムにおいて、ヒープメモリは `mspan` と呼ばれる単位で管理されます。

*   **`mspan`**: 連続したページ（通常は8KB）の集まりで、特定のサイズのオブジェクトを格納するために使用されます。Goのメモリ管理は、オブジェクトサイズに応じて異なる `mspan` を使用します（例: 8バイトオブジェクト用、16バイトオブジェクト用など）。
*   **`mcentral`**: 特定のサイズのオブジェクトを割り当てるための `mspan` のリストを管理します。ミューテータがメモリを要求すると、`mcentral` から適切な `mspan` が提供されます。
*   **`freelist`**: `mspan` 内の空きオブジェクトスロットを管理するリストです。オブジェクトが解放されると、そのスロットは `freelist` に戻され、再利用可能になります。
*   **`ref`**: `mspan` 内で現在使用されているオブジェクトの数を追跡するカウンタです。
*   **`elemsize`**: `mspan` が保持するオブジェクトのサイズです。

### ヒープフラグメンテーション

ヒープフラグメンテーションとは、メモリが割り当てと解放を繰り返すうちに、利用可能な空きメモリが小さな断片として散らばり、大きな連続したメモリブロックが不足する現象を指します。GoのGCはコンパクション（メモリを再配置して断片化を解消する）を行わないため、フラグメンテーションが発生しやすい特性があります。フラグメンテーションが進むと、大きなオブジェクトを割り当てる際に、利用可能な小さなスパンを複数組み合わせる必要が生じたり、新しいスパンをOSから取得する必要が生じたりすることがあります。

### `deductSweepCredit` の役割

`deductSweepCredit` 関数は、プロポーショナルスイープの中核をなす関数です。ミューテータがメモリを割り当てる際に呼び出され、割り当てられたメモリ量に基づいてスイープクレジットを「差し引く（deduct）」ことで、GCワーカーが実行すべきスイープ作業量を決定します。このクレジットが減ることで、GCワーカーはより多くのスイープ作業を行う必要が生じます。

## 技術的詳細

このコミットの技術的な核心は、`deductSweepCredit` によるスイープクレジットのチャージが、実際にミューテータが利用できるメモリ量ではなく、スパンの「論理的な」全サイズに基づいて行われていたという問題の修正にあります。

### 問題点と影響

*   **過剰なチャージ**: `mcentral` から `mspan` が取得される際、そのスパンが既に一部使用済み（例えば、以前のGCサイクルで一部のオブジェクトがマークされ、残りが解放された状態）であっても、`deductSweepCredit` はスパン全体のサイズ（`spanBytes`）を基にクレジットを差し引いていました。
*   **`mspan` の `ref` と `elemsize`**: `mspan` の `ref` フィールドは、そのスパン内で現在参照されている（つまり使用中の）オブジェクトの数を表します。`elemsize` はそのスパンが管理するオブジェクトの個々のサイズです。したがって、`ref * elemsize` は、スパン内で既に使われているバイト数を正確に示します。
*   **フラグメンテーションとの関連**: ヒープが断片化している場合、`mcentral` は新しいスパンをOSから取得する代わりに、既に一部使用済みだが空きスロットがある既存のスパンを再利用することが多くなります。このようなスパンが返されると、過剰なチャージの問題がより頻繁に発生し、プロポーショナルスイープがさらに過敏に反応する結果となっていました。
*   **結果**: プロポーショナルスイープが「過剰にアグレッシブ」になり、本来必要とされるよりも早くスイープ作業を終えてしまう傾向がありました。これは、GCの作業がヒープの成長に適切に比例しなくなり、GCの効率やタイミングに影響を与える可能性がありました。

### 修正アプローチ

このコミットでは、以下の方法で問題を解決しています。

1.  **`usedBytes` の計算**: `mcentral.go` の `mcentral.cacheSpan` メソッド内で、`mspan` がミューテータに返される直前に、そのスパン内で既に使われているバイト数 `usedBytes` を計算します。これは `uintptr(s.ref) * s.elemsize` で求められます。
2.  **`reimburseSweepCredit` の導入**: 新たに `reimburseSweepCredit` 関数が `mgcsweep.go` に追加されました。この関数は、`deductSweepCredit` によって行われた「過剰なチャージ」を相殺するために、`usedBytes` の分だけスイープクレジットを「払い戻し（reimburse）」ます。
3.  **アトミックな更新**: `reimburseSweepCredit` は、グローバルなヒープ統計カウンタである `mheap_.spanBytesAlloc` を `xadd64` 関数を使ってアトミックに更新します。`mheap_.spanBytesAlloc` は、ミューテータが割り当てたバイト数の合計を追跡しており、プロポーショナルスイープのチャージ計算の基礎となります。`xadd64` は、複数のゴルーチンからの同時アクセスに対して安全に値を加算（または減算）するためのアトミック操作です。
4.  **最悪ケースのチャージは維持**: コミットメッセージにもあるように、`deductSweepCredit` は依然としてスパンの全サイズに対して最悪ケースのチャージを行います。これは、`mcentral` がどのスパンを返すか（完全に空のスパンか、一部使用済みのスパンか）を事前に知ることができないためです。しかし、スパンが実際に割り当てられた後で、`reimburseSweepCredit` を使って過剰なチャージを修正することで、最終的なクレジット計算の精度を向上させています。

この修正により、プロポーショナルスイープはより正確にヒープの成長に比例して動作するようになり、GCの効率が向上し、特に断片化されたヒープでの挙動が改善されます。コミットメッセージによると、この変更はGo1ベンチマークやガベージベンチマークのスループットに無視できる程度の影響しか与えないとされています。

## コアとなるコードの解説

### `src/runtime/mcentral.go` の変更

`mcentral.go` の `mcentral.cacheSpan` 関数は、`mcentral` から `mspan` を取得する際に呼び出されます。この関数内で、取得したスパン `s` がミューテータに返される直前に以下のコードが追加されました。

```go
	usedBytes := uintptr(s.ref) * s.elemsize
	if usedBytes > 0 {
		reimburseSweepCredit(usedBytes)
	}
```

*   `usedBytes := uintptr(s.ref) * s.elemsize`:
    *   `s.ref` は、この `mspan` 内で現在参照されている（つまり使用中の）オブジェクトの数を表します。
    *   `s.elemsize` は、この `mspan` が管理する個々のオブジェクトのサイズです。
    *   この2つを掛け合わせることで、スパン `s` の中で既にオブジェクトによって占有されているバイト数 `usedBytes` が正確に計算されます。
*   `if usedBytes > 0`:
    *   もし `usedBytes` が0より大きい場合、つまりスパンが完全に空ではなく、一部が使用済みである場合にのみ、払い戻し処理を行います。完全に空のスパンであれば、過剰なチャージは発生していないため、払い戻しは不要です。
*   `reimburseSweepCredit(usedBytes)`:
    *   計算された `usedBytes` を引数として、新しく追加された `reimburseSweepCredit` 関数を呼び出します。これにより、`deductSweepCredit` によって以前に行われた過剰なチャージが相殺されます。

この変更により、ミューテータが実際に利用できるメモリ量に基づいてスイープクレジットが調整されるようになり、プロポーショナルスイープの精度が向上します。

### `src/runtime/mgcsweep.go` の変更

`mgcsweep.go` には、`reimburseSweepCredit` 関数が新しく追加されました。

```go
// reimburseSweepCredit records that unusableBytes bytes of a
// just-allocated span are not available for object allocation. This
// offsets the worst-case charge performed by deductSweepCredit.
func reimburseSweepCredit(unusableBytes uintptr) {
	if mheap_.sweepPagesPerByte == 0 {
		// Nobody cares about the credit. Avoid the atomic.
		return
	}
	xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))
}
```

*   **関数の目的**: コメントにもあるように、この関数は「割り当てられたばかりのスパンの `unusableBytes` バイトがオブジェクト割り当てに利用できないことを記録する」ものです。これは `deductSweepCredit` が行った最悪ケースのチャージを相殺します。
*   `if mheap_.sweepPagesPerByte == 0`:
    *   `mheap_.sweepPagesPerByte` は、プロポーショナルスイープが有効かどうか、またはその比率を示す値です。この値が0の場合、プロポーショナルスイープは行われていないため、クレジットの調整も不要です。このチェックにより、不要な処理（特にアトミック操作）を避けることができます。
*   `xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))`:
    *   `mheap_.spanBytesAlloc` は、Goランタイムのヒープ統計の一部であり、ミューテータがこれまでに割り当てたバイト数の合計を追跡します。この値は、プロポーショナルスイープのチャージ計算の基礎となります。
    *   `xadd64` は、指定されたメモリ位置の値をアトミックに加算する（または減算する）関数です。ここでは、`unusableBytes` の負の値（`-int64(unusableBytes)`）を加算することで、実質的に `mheap_.spanBytesAlloc` から `unusableBytes` を減算しています。
    *   これにより、`deductSweepCredit` が過剰にチャージした分が `mheap_.spanBytesAlloc` から差し引かれ、プロポーショナルスイープのクレジットが正確に調整されます。

この `reimburseSweepCredit` 関数の導入により、Goのガベージコレクタは、ミューテータが実際に利用可能なメモリ量に基づいてスイープ作業をより正確にスケジューリングできるようになり、GCの効率と応答性が向上します。

## 変更の背景

Goのガベージコレクタは、プログラムの実行と並行してメモリのクリーンアップを行う「コンカレントGC」を採用しています。このGCサイクルの一部として「スイープ（sweep）」というフェーズがあり、これはマークされなかった（つまり不要になった）オブジェクトが占めていたメモリを解放し、再利用可能にするプロセスです。

このスイープの実行量を調整するために「プロポーショナルスイープ（proportional sweep）」というメカニズムが導入されています。これは、ミューテータ（ユーザープログラム）がヒープにメモリを割り当てる量に応じて、スイープ作業を「チャージ」する（割り当てる）ことで、GC作業がヒープの成長に比例して行われるようにするものです。これにより、GCが一度に大量の作業を行う必要がなくなり、アプリケーションのレイテンシを低減する効果が期待されます。

しかし、このコミット以前のGoランタイムでは、プロポーショナルスイープのチャージ方法に問題がありました。具体的には、ミューテータが新しいメモリ領域（スパン）を要求した際、そのスパンの「全サイズ」に対してスイープクレジットがチャージされていました。たとえそのスパンが既に一部使用済みで、実際にミューテータが利用できる空き容量が少なかったとしても、全サイズがチャージの対象となっていたのです。

例えば、8KBのスパンが要求され、そのうち6KBが既に使われている場合、ミューテータは8KB分のヒープ割り当てとしてチャージされますが、実際に利用できるのは残りの2KBだけです。この「過剰なチャージ」により、プロポーショナルスイープは必要以上に早く完了してしまい、GCの効率が低下したり、特にヒープが断片化している場合にこの問題が顕著になることが指摘されていました。このコミットは、この過剰なチャージを是正し、プロポーショナルスイープの精度と効率を向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

Goのガベージコレクタは、主に以下の特徴を持ちます。

*   **コンカレントGC**: ユーザープログラム（ミューテータ）の実行と並行してGC処理の大部分が行われます。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、低レイテンシを実現します。
*   **トライカラーマーク＆スイープ**: オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みで参照先も訪問済み）」の3色でマークし、不要なオブジェクトを特定します。マークフェーズの後、スイープフェーズで不要なオブジェクトが占めるメモリを解放します。
*   **プロポーショナルスイープ**: ヒープの成長に合わせてスイープ作業を分散して実行するメカニズムです。ミューテータがメモリを割り当てるたびに、その割り当て量に応じてスイープ作業が「チャージ」され、GCワーカーがバックグラウンドでスイープを実行します。これにより、GCの作業がヒープの成長に追いつき、GCサイクル終了時に大量のスイープ作業が集中するのを防ぎます。

### `mspan` とは何か、その役割

Goのランタイムにおいて、ヒープメモリは `mspan` と呼ばれる単位で管理されます。

*   **`mspan`**: 連続したページ（通常は8KB）の集まりで、特定のサイズのオブジェクトを格納するために使用されます。Goのメモリ管理は、オブジェクトサイズに応じて異なる `mspan` を使用します（例: 8バイトオブジェクト用、16バイトオブジェクト用など）。
*   **`mcentral`**: 特定のサイズのオブジェクトを割り当てるための `mspan` のリストを管理します。ミューテータがメモリを要求すると、`mcentral` から適切な `mspan` が提供されます。
*   **`freelist`**: `mspan` 内の空きオブジェクトスロットを管理するリストです。オブジェクトが解放されると、そのスロットは `freelist` に戻され、再利用可能になります。
*   **`ref`**: `mspan` 内で現在使用されているオブジェクトの数を追跡するカウンタです。
*   **`elemsize`**: `mspan` が保持するオブジェクトのサイズです。

### ヒープフラグメンテーション

ヒープフラグメンテーションとは、メモリが割り当てと解放を繰り返すうちに、利用可能な空きメモリが小さな断片として散らばり、大きな連続したメモリブロックが不足する現象を指します。GoのGCはコンパクション（メモリを再配置して断片化を解消する）を行わないため、フラグメンテーションが発生しやすい特性があります。フラグメンテーションが進むと、大きなオブジェクトを割り当てる際に、利用可能な小さなスパンを複数組み合わせる必要が生じたり、新しいスパンをOSから取得する必要が生じたりすることがあります。

### `deductSweepCredit` の役割

`deductSweepCredit` 関数は、プロポーショナルスイープの中核をなす関数です。ミューテータがメモリを割り当てる際に呼び出され、割り当てられたメモリ量に基づいてスイープクレジットを「差し引く（deduct）」ことで、GCワーカーが実行すべきスイープ作業量を決定します。このクレジットが減ることで、GCワーカーはより多くのスイープ作業を行う必要が生じます。

## 技術的詳細

このコミットの技術的な核心は、`deductSweepCredit` によるスイープクレジットのチャージが、実際にミューテータが利用できるメモリ量ではなく、スパンの「論理的な」全サイズに基づいて行われていたという問題の修正にあります。

### 問題点と影響

*   **過剰なチャージ**: `mcentral` から `mspan` が取得される際、そのスパンが既に一部使用済み（例えば、以前のGCサイクルで一部のオブジェクトがマークされ、残りが解放された状態）であっても、`deductSweepCredit` はスパン全体のサイズ（`spanBytes`）を基にクレジットを差し引いていました。
*   **`mspan` の `ref` と `elemsize`**: `mspan` の `ref` フィールドは、そのスパン内で現在参照されている（つまり使用中の）オブジェクトの数を表します。`elemsize` はそのスパンが管理するオブジェクトの個々のサイズです。したがって、`ref * elemsize` は、スパン内で既に使われているバイト数を正確に示します。
*   **フラグメンテーションとの関連**: ヒープが断片化している場合、`mcentral` は新しいスパンをOSから取得する代わりに、既に一部使用済みだが空きスロットがある既存のスパンを再利用することが多くなります。このようなスパンが返されると、過剰なチャージの問題がより頻繁に発生し、プロポーショナルスイープがさらに過敏に反応する結果となっていました。
*   **結果**: プロポーショナルスイープが「過剰にアグレッシブ」になり、本来必要とされるよりも早くスイープ作業を終えてしまう傾向がありました。これは、GCの作業がヒープの成長に適切に比例しなくなり、GCの効率やタイミングに影響を与える可能性がありました。

### 修正アプローチ

このコミットでは、以下の方法で問題を解決しています。

1.  **`usedBytes` の計算**: `mcentral.go` の `mcentral.cacheSpan` メソッド内で、`mspan` がミューテータに返される直前に、そのスパン内で既に使われているバイト数 `usedBytes` を計算します。これは `uintptr(s.ref) * s.elemsize` で求められます。
2.  **`reimburseSweepCredit` の導入**: 新たに `reimburseSweepCredit` 関数が `mgcsweep.go` に追加されました。この関数は、`deductSweepCredit` によって行われた「過剰なチャージ」を相殺するために、`usedBytes` の分だけスイープクレジットを「払い戻し（reimburse）」ます。
3.  **アトミックな更新**: `reimburseSweepCredit` は、グローバルなヒープ統計カウンタである `mheap_.spanBytesAlloc` を `xadd64` 関数を使ってアトミックに更新します。`mheap_.spanBytesAlloc` は、ミューテータが割り当てたバイト数の合計を追跡しており、プロポーショナルスイープのチャージ計算の基礎となります。`xadd64` は、複数のゴルーチンからの同時アクセスに対して安全に値を加算（または減算）するためのアトミック操作です。
4.  **最悪ケースのチャージは維持**: コミットメッセージにもあるように、`deductSweepCredit` は依然としてスパンの全サイズに対して最悪ケースのチャージを行います。これは、`mcentral` がどのスパンを返すか（完全に空のスパンか、一部使用済みのスパンか）を事前に知ることができないためです。しかし、スパンが実際に割り当てられた後で、`reimburseSweepCredit` を使って過剰なチャージを修正することで、最終的なクレジット計算の精度を向上させています。

この修正により、プロポーショナルスイープはより正確にヒープの成長に比例して動作するようになり、GCの効率が向上し、特に断片化されたヒープでの挙動が改善されます。コミットメッセージによると、この変更はGo1ベンチマークやガベージベンチマークのスループットに無視できる程度の影響しか与えないとされています。

## コアとなるコードの解説

### `src/runtime/mcentral.go` の変更

`mcentral.go` の `mcentral.cacheSpan` 関数は、`mcentral` から `mspan` を取得する際に呼び出されます。この関数内で、取得したスパン `s` がミューテータに返される直前に以下のコードが追加されました。

```go
	usedBytes := uintptr(s.ref) * s.elemsize
	if usedBytes > 0 {
		reimburseSweepCredit(usedBytes)
	}
```

*   `usedBytes := uintptr(s.ref) * s.elemsize`:
    *   `s.ref` は、この `mspan` 内で現在参照されている（つまり使用中の）オブジェクトの数を表します。
    *   `s.elemsize` は、この `mspan` が管理する個々のオブジェクトのサイズです。
    *   この2つを掛け合わせることで、スパン `s` の中で既にオブジェクトによって占有されているバイト数 `usedBytes` が正確に計算されます。
*   `if usedBytes > 0`:
    *   もし `usedBytes` が0より大きい場合、つまりスパンが完全に空ではなく、一部が使用済みである場合にのみ、払い戻し処理を行います。完全に空のスパンであれば、過剰なチャージは発生していないため、払い戻しは不要です。
*   `reimburseSweepCredit(usedBytes)`:
    *   計算された `usedBytes` を引数として、新しく追加された `reimburseSweepCredit` 関数を呼び出します。これにより、`deductSweepCredit` によって以前に行われた過剰なチャージが相殺されます。

この変更により、ミューテータが実際に利用できるメモリ量に基づいてスイープクレジットが調整されるようになり、プロポーショナルスイープの精度が向上します。

### `src/runtime/mgcsweep.go` の変更

`mgcsweep.go` には、`reimburseSweepCredit` 関数が新しく追加されました。

```go
// reimburseSweepCredit records that unusableBytes bytes of a
// just-allocated span are not available for object allocation. This
// offsets the worst-case charge performed by deductSweepCredit.
func reimburseSweepCredit(unusableBytes uintptr) {
	if mheap_.sweepPagesPerByte == 0 {
		// Nobody cares about the credit. Avoid the atomic.
		return
	}
	xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))
}
```

*   **関数の目的**: コメントにもあるように、この関数は「割り当てられたばかりのスパンの `unusableBytes` バイトがオブジェクト割り当てに利用できないことを記録する」ものです。これは `deductSweepCredit` が行った最悪ケースのチャージを相殺します。
*   `if mheap_.sweepPagesPerByte == 0`:
    *   `mheap_.sweepPagesPerByte` は、プロポーショナルスイープが有効かどうか、またはその比率を示す値です。この値が0の場合、プロポーショナルスイープは行われていないため、クレジットの調整も不要です。このチェックにより、不要な処理（特にアトミック操作）を避けることができます。
*   `xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))`:
    *   `mheap_.spanBytesAlloc` は、Goランタイムのヒープ統計の一部であり、ミューテータがこれまでに割り当てたバイト数の合計を追跡します。この値は、プロポーショナルスイープのチャージ計算の基礎となります。
    *   `xadd64` は、指定されたメモリ位置の値をアトミックに加算する（または減算する）関数です。ここでは、`unusableBytes` の負の値（`-int64(unusableBytes)`）を加算することで、実質的に `mheap_.spanBytesAlloc` から `unusableBytes` を減算しています。
    *   これにより、`deductSweepCredit` が過剰にチャージした分が `mheap_.spanBytesAlloc` から差し引かれ、プロポーショナルスイープのクレジットが正確に調整されます。

この `reimburseSweepCredit` 関数の導入により、Goのガベージコレクタは、ミューテータが実際に利用可能なメモリ量に基づいてスイープ作業をより正確にスケジューリングできるようになり、GCの効率と応答性が向上します。

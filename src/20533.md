# [インデックス 20533] ファイルの概要

このコミットは、Go言語の標準ライブラリ `sync` パッケージ内の `Once` 型の挙動に関する修正です。具体的には、`Once.Do` メソッドに渡された関数 `f` がパニック（panic）を起こした場合の `Once` の状態管理が変更されています。以前の挙動では、パニックが発生すると `Once` はその関数が完了しなかったとみなし、後続の `Do` 呼び出しで再度 `f` を実行しようとする可能性がありました。このコミットにより、`f` がパニックを起こした場合でも `Once` はその実行を「完了」とみなし、二度と `f` を実行しないように変更されました。

## 元コミット内容

`sync/once: panicking functions still marked as complete`

このコミットは、`sync.Once` に渡された関数がパニックを起こした場合でも、その関数が「完了した」とマークされるように挙動を変更します。これは、`sync.Once` が関数を一度だけ実行するという本来の意図をより厳密に反映するための変更であり、関数が正常に終了するかパニックするかに関わらず、最初の呼び出しでのみ実行されるべきであるという考えに基づいています。

## 変更の背景

この変更の背景には、`sync.Once` の設計思想と、Go言語におけるパニックの扱いがあります。

`sync.Once` は、プログラムのライフサイクルにおいて、ある初期化処理やリソースのセットアップなどを「一度だけ」実行することを保証するためのプリミティブです。例えば、データベース接続の確立、設定ファイルの読み込み、シングルトンインスタンスの生成など、アプリケーション全体で一度だけ行われるべき操作に利用されます。

問題となっていたのは、`Once.Do` に渡された関数 `f` が実行中にパニックを起こした場合の挙動でした。従来の `Once` の実装では、`f` がパニックを起こすと、`Once` はその実行が「完了しなかった」と判断し、後続の `Do` 呼び出しで再度 `f` を実行しようとする可能性がありました。これは、`Once` の「一度だけ実行する」という保証に反する挙動であり、予期せぬ副作用や無限ループ、リソースの重複初期化などを引き起こす可能性がありました。

コミットメッセージにある `Fixes #8118` は、この問題がGoのIssueトラッカーで報告されていたことを示しています。このIssueでは、`Once.Do` に渡された関数がパニックした場合に、`Once` がその関数を再度実行しようとする挙動が問題視されていました。

このコミットは、`Once` の本来の意図である「関数は一度だけ実行される」という原則を、パニックが発生した場合にも適用することで、より堅牢で予測可能な挙動を実現することを目的としています。パニックはGoにおいてエラーハンドリングの最終手段として用いられることが多く、通常はプログラムの異常終了を意味します。このような状況で `Once` が再試行を試みるのは、多くの場合、望ましくない挙動と判断されたため、この修正が導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と `sync` パッケージの知識が必要です。

1.  **`sync.Once`**:
    *   `sync.Once` は、Go言語の標準ライブラリ `sync` パッケージが提供する型で、特定の関数がプログラムの実行中に一度だけ実行されることを保証するためのプリミティブです。
    *   主なメソッドは `Do(f func())` です。このメソッドは、引数 `f` で指定された関数を、`Once` インスタンスに対して一度だけ実行します。
    *   複数のGoroutineから同時に `Do` が呼び出された場合でも、`Once` は内部的にロック機構（通常は `sync.Mutex` と `atomic` 操作）を使用して、`f` が一度だけ実行されることを保証します。最初の `Do` 呼び出しが `f` の実行を開始し、他のGoroutineは `f` の実行が完了するまでブロックされます。
    *   `Once` は、シングルトンパターンの実装、遅延初期化（lazy initialization）、リソースのセットアップなど、一度だけ実行されるべき処理に広く利用されます。

2.  **`panic` と `recover`**:
    *   **`panic`**: Go言語における `panic` は、プログラムの通常の実行フローを中断させるランタイムエラーです。これは、回復不可能なエラーやプログラマーの論理的な誤り（例: nilポインタのデリファレンス、配列の範囲外アクセス）を示すために使用されます。`panic` が発生すると、現在のGoroutineの関数呼び出しスタックを遡りながら、`defer` ステートメントに登録された関数が実行されます。
    *   **`recover`**: `recover` は、`panic` から回復するための組み込み関数です。`recover` は `defer` 関数内でのみ有効であり、`panic` が発生したGoroutineのスタックを遡る過程で `recover` が呼び出されると、`panic` の値（通常はエラーメッセージ）を返します。`recover` が非`nil`の値を返した場合、`panic` は停止し、プログラムの実行は `recover` が呼び出された `defer` 関数の直後から再開されます。これにより、プログラムのクラッシュを防ぎ、エラーを適切に処理する機会が与えられます。
    *   このコミットの文脈では、`Once.Do` に渡された関数 `f` が `panic` を起こした場合に、`Once` がどのように振る舞うかが焦点となります。

3.  **`sync/atomic` パッケージ**:
    *   `sync/atomic` パッケージは、低レベルのアトミック操作（不可分操作）を提供します。アトミック操作は、複数のGoroutineから同時にアクセスされても、その操作全体が単一の不可分なステップとして実行されることを保証します。これにより、ミューテックス（`sync.Mutex`）のようなロック機構を使用せずに、共有変数の安全な更新が可能になります。
    *   `Once` の内部実装では、`atomic.LoadUint32` や `atomic.StoreUint32` のような関数が、`f` が既に実行されたかどうかを示すフラグ（`done` フィールド）を安全に読み書きするために使用されます。これにより、ロックのオーバーヘッドを最小限に抑えつつ、スレッドセーフな初期化を実現しています。

これらの概念を理解することで、`Once` がどのように動作し、なぜパニック時の挙動の変更が重要であったかを深く把握できます。

## 技術的詳細

このコミットの技術的な核心は、`sync.Once` の `Do` メソッドにおける `done` フラグの更新タイミングの変更にあります。

`sync.Once` の内部には、`done` という `uint32` 型のフィールドがあり、これは `f` が既に実行されたかどうかを示すフラグとして機能します。`done` が `1` であれば `f` は実行済み、`0` であれば未実行です。

従来の `Do` メソッドの実装では、`f()` の呼び出しが成功した**後**に `atomic.StoreUint32(&o.done, 1)` を実行していました。

```go
// 変更前 (概念的なコード)
func (o *Once) Do(f func()) {
    if atomic.LoadUint32(&o.done) == 1 {
        return
    }
    o.m.Lock()
    defer o.m.Unlock()
    if o.done == 0 {
        f() // ここでパニックが発生すると...
        atomic.StoreUint32(&o.done, 1) // ...この行は実行されない
    }
}
```

この実装の問題点は、`f()` の実行中にパニックが発生した場合、`atomic.StoreUint32(&o.done, 1)` の行が実行されないことです。その結果、`o.done` は `0` のままとなり、`Once` は `f` がまだ実行されていないと誤って判断します。これにより、後続の `Do` 呼び出しで再度 `f` が実行されてしまう可能性がありました。

新しい実装では、`f()` の呼び出しを `defer` ステートメントで囲まれた `atomic.StoreUint32(&o.done, 1)` の**前**に移動しました。

```go
// 変更後 (概念的なコード)
func (o *Once) Do(f func()) {
    if atomic.LoadUint32(&o.done) == 1 {
        return
    }
    o.m.Lock()
    defer o.m.Unlock()
    if o.done == 0 {
        defer atomic.StoreUint32(&o.done, 1) // パニックが発生しても、このdeferは実行される
        f()
    }
}
```

Go言語の `defer` ステートメントは、関数がリターンする直前（正常終了、`return` ステートメント、または `panic` によるスタックアンワインドのいずれの場合でも）に実行されることが保証されています。したがって、`f()` がパニックを起こした場合でも、`defer atomic.StoreUint32(&o.done, 1)` は必ず実行され、`o.done` フラグが `1` に設定されます。これにより、`Once` は `f` の実行が「完了した」（パニックしたとしても）と正しく認識し、以降の `Do` 呼び出しでは `f` を二度と実行しなくなります。

この変更は、`Once` の「一度だけ実行する」という保証を、パニックが発生した場合にも厳密に適用するためのものです。パニックは通常、プログラムの異常終了を意味するため、その後の再試行は多くの場合、無意味であるか、さらなる問題を引き起こす可能性があります。この修正により、`Once` の挙動はより予測可能で堅牢になります。

テストコード `src/sync/once_test.go` も、この新しい挙動を検証するために修正されています。特に `TestOncePanic` 関数は、`Once.Do` にパニックする関数を渡し、最初の呼び出しでパニックが発生し、二度目の呼び出しでは関数が実行されないことを確認するように変更されました。

## コアとなるコードの解説

### `src/sync/once.go` の変更点

1.  **コメントの追加**:
    `Do` メソッドのドキュメンテーションコメントに以下の行が追加されました。
    `// If f panics, Do considers it to have returned; future calls of Do return`
    `// without calling f.`
    これは、`f` がパニックを起こした場合でも `Do` は `f` が完了したとみなし、以降の `Do` 呼び出しでは `f` を実行しないことを明確に示しています。

2.  **`atomic.StoreUint32(&o.done, 1)` の移動**:
    最も重要な変更は、`o.m.Lock()` と `defer o.m.Unlock()` のブロック内で、`f()` の呼び出しの**直前**に `defer atomic.StoreUint32(&o.done, 1)` が追加され、`f()` の呼び出しの**直後**にあった `atomic.StoreUint32(&o.done, 1)` が削除された点です。
    *   **変更前**:
        ```go
        f()
        atomic.StoreUint32(&o.done, 1) // f()がパニックすると、この行は実行されない
        ```
    *   **変更後**:
        ```go
        defer atomic.StoreUint32(&o.done, 1) // f()がパニックしても、このdeferは実行される
        f()
        ```
    この変更により、`f()` が正常に完了するか、あるいはパニックを起こしてスタックアンワインドが開始されるかに関わらず、`defer` ステートメントによって `o.done` フラグが確実に `1` に設定されるようになりました。これにより、`Once` は `f` の実行が一度行われたことを常に正しく記録し、二度目の実行を防ぎます。

### `src/sync/once_test.go` の変更点

`TestOncePanic` 関数は、`Once.Do` にパニックする関数を渡した場合の挙動をテストします。

1.  **`recover()` の結果の確認ロジックの変更**:
    `defer` 関数内の `recover()` の結果をチェックするロジックがより詳細になりました。
    *   **変更前**:
        `if recover() == nil { t.Fatalf("Once.Do() has not panic'ed") }`
        これは、`Once.Do()` がパニックを起こさなかった場合にテストを失敗させる単純なチェックでした。
    *   **変更後**:
        ```go
        r := recover()
        if r == nil && i == 0 {
            t.Fatalf("Once.Do() has not panic'ed on first iteration")
        }
        if r != nil && i == 1 {
            t.Fatalf("Once.Do() has panic'ed on second iteration")
        }
        ```
    この新しいロジックは、ループの最初のイテレーション (`i == 0`) ではパニックが発生することを期待し、二番目のイテレーション (`i == 1`) ではパニックが発生しないこと（つまり、`Once` が関数を再実行しないこと）を期待しています。これにより、`Once` がパニックする関数を一度だけ実行し、その後は実行しないという新しい挙動が正確に検証されます。

これらの変更は、`sync.Once` のセマンティクスをより堅牢にし、パニックが発生するようなエッジケースにおいても、その「一度だけ実行する」という保証を維持することを目的としています。

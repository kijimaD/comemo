## 変更の背景
Goコンパイラは、以前は主にx86-64アーキテクチャに最適化されていましたが、より多くのプラットフォームをサポートするために、SSAバックエンドを他のアーキテクチャ（ARMなど）に移植する必要がありました。このコミットは、そのARMアーキテクチャへのSSAバックエンドの初期移植作業の一環です。

具体的な背景としては、Go 1.7リリースに向けてSSAバックエンドが導入され、コンパイラの最適化とコード生成の柔軟性が大幅に向上しました。この新しいSSAフレームワークをARMのような異なるアーキテクチャで利用できるようにすることは、Go言語のクロスプラットフォーム対応を強化する上で不可欠なステップでした。ARMはモバイルデバイスや組み込みシステムで広く普及しており、Goがこれらの分野で採用されるためには、効率的なARMコード生成が必須となります。

このコミットの目的は、ARMアーキテクチャ向けにSSAベースのコード生成を開始し、特に基本的な関数（例：フィボナッチ関数）が正しくコンパイルされることを確認することです。また、既存のレジスタ割り当てロジックがアーキテクチャに依存しすぎている部分を汎用化し、新しいアーキテクチャの追加を容易にすることも含まれています。これにより、将来的な他のアーキテクチャへの拡張性も考慮されています。

## 前提知識の解説

### Goコンパイラの構造
Goコンパイラ（`cmd/compile`）は、ソースコードを機械語に変換するプロセスを複数のステージに分けて実行します。主要なステージは以下の通りです。
1.  **フロントエンド (Parsing & Type Checking)**: Goのソースコードを解析し、抽象構文木（AST）を構築し、型チェックを行います。
2.  **ミドルエンド (SSA生成)**: ASTをSSA形式に変換します。SSAは、各変数が一度だけ代入されるようにする中間表現であり、データフロー解析や最適化を容易にします。
3.  **バックエンド (コード生成)**: SSA形式のコードをターゲットアーキテクチャ（例: x86-64, ARM）の機械語に変換します。このステージには、レジスタ割り当て、命令選択、アセンブリコード生成などが含まれます。

### SSA (Static Single Assignment) 形式
SSAは、コンパイラ最適化において非常に重要な中間表現です。SSA形式では、各変数はプログラム内で一度だけ定義（代入）されます。例えば、`x = a + b; x = x * 2;` はSSAでは `x1 = a + b; x2 = x1 * 2;` のようになります。これにより、変数の値がどこで定義され、どこで使用されるかというデータフローが明確になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が効率的に行えます。GoコンパイラのSSAバックエンドは、この形式を利用して高度な最適化と効率的なコード生成を実現しています。

### レジスタ割り当て (Register Allocation)
レジスタ割り当ては、プログラムの実行中に使用される変数をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりも高速にアクセスできるため、効率的なレジスタ割り当てはプログラムのパフォーマンスに大きく影響します。SSAバックエンドでは、通常、グラフ彩色アルゴリズムなどの高度な手法を用いて、変数のライフタイム（変数が定義されてから最後に使用されるまでの期間）を分析し、最適なレジスタ割り当てを行います。このプロセスはアーキテクチャ固有のレジスタセットと制約を考慮する必要があります。

### ARMアーキテクチャ
ARM（Advanced RISC Machine）は、モバイルデバイス、組み込みシステム、最近ではサーバーやデスクトップPCでも広く使用されているRISC（Reduced Instruction Set Computer）アーキテクチャです。x86-64とは異なる命令セット、レジスタセット、呼び出し規約を持っています。例えば、ARMは通常、汎用レジスタ（R0-R12）、スタックポインタ（SP/R13）、リンクレジスタ（LR/R14）、プログラムカウンタ（PC/R15）などを持っています。GoコンパイラがARMをサポートするためには、これらのアーキテクチャ固有の特性に合わせてコード生成ロジックを調整し、ARMのアセンブリ命令（例: `ADD`, `MOVW`, `CMP`, `BGE`など）を正確に生成する必要があります。

### `cmd/compile/internal/ssa/gen` ディレクトリ
このディレクトリには、SSAバックエンドのコード生成を自動化するためのツールが含まれています。
*   `.rules` ファイル: 特定のアーキテクチャ向けのSSA変換ルールを定義します。例えば、`ARM.rules`は汎用的なSSA操作をARM固有の命令に変換する方法を記述します。これらのルールは、より高レベルなSSAオペレーションを、ターゲットアーキテクチャの低レベルな命令に「書き換え（rewrite）」るために使用されます。
*   `ARMOps.go` (生成されるファイル): ARMアーキテクチャで利用可能なSSA操作（オペレーション）とそのレジスタ使用情報、アセンブリ命令へのマッピングを定義します。
*   `rewriteARM.go` (生成されるファイル): `.rules`ファイルに基づいて、SSA値をARM固有の命令に書き換える関数を自動生成します。これにより、手動でのコード記述ミスを防ぎ、移植作業の効率を高めます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドをARMアーキテクチャに移植するための基盤を構築しています。主な技術的変更点は以下の通りです。

1.  **ARM固有のSSAコード生成ロジックの導入**:
    *   `src/cmd/compile/internal/arm/ssa.go` が新規作成され、ARMアーキテクチャ向けの `ssaGenValue` および `ssaGenBlock` 関数が実装されています。これらの関数は、SSA形式の各値（`ssa.Value`）やブロック（`ssa.Block`）を、ARMアセンブリ命令に変換する役割を担います。これは、SSA中間表現から最終的な機械語への橋渡しとなる重要な部分です。
    *   `ssaGenValue` は、`ssa.OpInitMem`, `ssa.OpArg`, `ssa.OpSP`, `ssa.OpSB`, `ssa.OpCopy`, `ssa.OpLoadReg`, `ssa.OpStoreReg`, `ssa.OpARMADD`, `ssa.OpARMADDconst`, `ssa.OpARMMOVWconst`, `ssa.OpARMCMP`, `ssa.OpARMMOVWload`, `ssa.OpARMMOVWstore`, `ssa.OpARMCALLstatic`, `ssa.OpVarDef`, `ssa.OpVarKill`, `ssa.OpVarLive` などのSSAオペレーションに対応するARMアセンブリ命令を生成します。各オペレーションに対して、適切なARM命令（例: `AMOVW` for move word, `AADD` for add）とオペランド（レジスタ、メモリ、定数）を設定します。
    *   `ssaGenBlock` は、`ssa.BlockCall`, `ssa.BlockRet`, `ssa.BlockARMLT` などのブロックタイプに対応する制御フロー命令（例: `AJMP` for jump, `ARET` for return, `ABGE` for branch if greater than or equal）を生成します。これにより、SSAの制御フローグラフがARMの分岐命令にマッピングされます。

2.  **SSAバックエンドのARMサポート有効化**:
    *   `src/cmd/compile/internal/gc/ssa.go` の `shouldssa` 関数が変更され、`Thearch.Thestring` が "arm" の場合にSSAが有効になるように調整されています。これにより、ARMターゲットでコンパイルする際にSSAバックエンドが使用されるようになります。初期段階では、`SSATEST` 環境変数が設定されている場合にのみ有効になるようなテスト用のロジックも含まれており、開発中の機能を安全にテストできるようになっています。

3.  **アーキテクチャ固有のSSA設定**:
    *   `src/cmd/compile/internal/ssa/config.go` の `NewConfig` 関数に "arm" ケースが追加されました。これにより、ARMアーキテクチャ向けに `IntSize` (4バイト), `PtrSize` (4バイト), `lowerBlock` (rewriteBlockARM), `lowerValue` (rewriteValueARM), および `registers` (registersARM) が設定されます。`lowerBlock` と `lowerValue` は、SSAの最適化パスで汎用的なSSAオペレーションをARM固有のオペレーションに変換するために使用される、自動生成された書き換え関数を指します。

4.  **ARM固有のSSAオペレーションとルール**:
    *   `src/cmd/compile/internal/ssa/gen/ARM.rules` が新規作成され、ARMアーキテクチャ向けのSSA書き換えルールが定義されています。例えば、`(Add32 x y) -> (ADD x y)` のように、汎用的な32ビット加算をARMの加算命令に変換するルールや、`(Const32 [val]) -> (MOVWconst [val])` のように定数をARMの定数移動命令に変換するルールなどが含まれています。これらのルールは、SSAの最適化フェーズで適用され、アーキテクチャに特化した命令選択を行います。
    *   `src/cmd/compile/internal/ssa/gen/ARMOps.go` が新規作成され、ARM固有のSSAオペレーション（`ADD`, `ADDconst`, `MOVWconst`, `CMP`, `MOVWload`, `MOVWstore`, `CALLstatic`, `LessThan`）が定義されています。これらのオペレーションには、引数の数、レジスタの使用方法（入力レジスタ、出力レジスタ、クローバーレジスタ）、対応するアセンブリ命令などが記述されており、SSAバックエンドがこれらのオペレーションをどのように扱うべきかを指示します。
    *   `src/cmd/compile/internal/ssa/op.go` および `src/cmd/compile/internal/ssa/opGen.go` に、新しいARM固有のSSAオペレーション（`OpARMADD`など）とブロックタイプ（`BlockARMEQ`など）が追加されています。これらは、SSA中間表現内でARM固有のセマンティクスを表現するために必要です。

5.  **レジスタ割り当ての汎用化**:
    *   `src/cmd/compile/internal/ssa/regalloc.go` では、レジスタ割り当てロジックがアーキテクチャ固有の定数（例: `numRegs`, `registers`配列の直接参照）に依存しないように変更されました。代わりに、`regAllocState` 構造体に `registers`, `numRegs`, `SPReg`, `SBReg` フィールドが追加され、`Config` からこれらの情報が初期化されるようになりました。
    *   特に、SPレジスタ（スタックポインタ）とSBレジスタ（スタティックベースポインタ）の扱いが汎用化され、ハードコードされたインデックス（例: `1<<4` や `1<<32`）ではなく、`1<<s.SPReg` や `1<<s.SBReg` を使用するようになりました。これにより、異なるアーキテクチャでSPやSBが異なるレジスタ番号を持つ場合でも、レジスタ割り当てコードを変更する必要がなくなります。この変更は、コンパイラの保守性と拡張性を大幅に向上させます。

これらの変更により、GoコンパイラのSSAバックエンドは、ARMアーキテクチャのサポートを開始し、将来的に他のアーキテクチャへの移植も容易になるような、より柔軟でモジュール化された設計へと進化しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/arm/ssa.go`
このファイルは、GoコンパイラのSSAバックエンドがARMアーキテクチャ向けのアセンブリコードを生成するための具体的なロジックを含んでいます。

*   **`ssaRegToReg`**: これは、SSAのレジスタ番号をARMの物理レジスタ番号にマッピングするための配列です。初期段階では、R0-R3とSP（R13）が定義されており、GoのSSAレジスタ抽象化とARMの物理レジスタ間の変換を可能にします。
*   **`ssaGenValue(s *gc.SSAGenState, v *ssa.Value)`**:
    *   この関数は、SSA形式の個々の値（`v`）を受け取り、それに対応するARMアセンブリ命令を生成します。
    *   `switch v.Op` ステートメントにより、様々なSSAオペレーション（例: `OpLoadReg`, `OpStoreReg`, `OpARMADD`, `OpARMCALLstatic`）が処理されます。
    *   例えば、`ssa.OpLoadReg` のケースでは、メモリからレジスタへのロード命令 (`arm.AMOVW` - Move Word) を生成します。`gc.AutoVar` を使ってスタック上の変数のオフセットを計算し、`obj.TYPE_MEM` と `obj.TYPE_REG` を適切に設定して命令を構築します。これは、変数の値をメモリからCPUレジスタに読み込む操作に対応します。
    *   `ssa.OpARMADD` のケースでは、2つのレジスタの値を加算し、結果を別のレジスタに格納するARMの加算命令を生成します。これは、`ADD Rdest, Rsrc1, Rsrc2` のようなARMアセンブリ命令に相当します。
    *   `ssa.OpARMCALLstatic` は、静的関数呼び出しに対応する `obj.ACALL` 命令を生成します。これは、Goランタイムや他のGo関数への呼び出しを処理します。
*   **`ssaGenBlock(s *gc.SSAGenState, b, next *ssa.Block)`**:
    *   この関数は、SSA形式のブロック（`b`）を受け取り、ブロック間の制御フローを処理するためのARMアセンブリ命令を生成します。
    *   `ssa.BlockCall` は、次のブロックへの無条件ジャンプ (`obj.AJMP`) を生成する可能性があります。これは、関数呼び出し後の制御フローの継続を保証します。
    *   `ssa.BlockRet` は、関数からのリターン命令 (`obj.ARET`) を生成します。
    *   `ssa.BlockARMLT` は、条件付き分岐命令を生成します。具体的には、"less than" (LT) 条件が偽の場合に次のブロック (`b.Succs[0]`) へ分岐する `arm.ABGE` (Branch if Greater than or Equal) と、それ以外の場合に無条件ジャンプ (`obj.AJMP`) で別のブロック (`b.Succs[1]`) へ分岐する命令を生成します。これは、SSAの条件分岐をARMの条件コードと分岐命令にマッピングする典型的な方法であり、`if` 文などの制御構造を実装するために不可欠です。

### `src/cmd/compile/internal/ssa/regalloc.go`
このファイルは、レジスタ割り当ての汎用性を高めるための重要な変更を含んでいます。

*   **`regAllocState` 構造体の拡張**:
    *   `registers []Register`, `numRegs register`, `SPReg register`, `SBReg register` の各フィールドが追加されました。これにより、レジスタ割り当てロジックは、特定のアーキテクチャのレジスタセットや特殊レジスタ（スタックポインタSP、スタティックベースSB）のインデックスを、コンフィグレーションから動的に取得できるようになります。これは、レジスタ割り当てアルゴリズムがアーキテクチャの詳細から分離されることを意味します。
*   **レジスタ参照の抽象化**:
    *   以前はハードコードされていた `numRegs` や `registers` 配列への直接参照が、`s.numRegs` や `s.registers` を介した参照に置き換えられました。
    *   特に、SPレジスタ（スタックポインタ）とSBレジスタ（スタティックベースポインタ）の扱いが汎用化され、ハードコードされたインデックス（例: `1<<4` や `1<<32` はそれぞれAMD64のSPとSBのレジスタマスクビット）ではなく、`1<<s.SPReg` や `1<<s.SBReg` を使用するようになりました。これにより、異なるアーキテクチャでSPやSBが異なるレジスタ番号を持つ場合でも、レジスタ割り当てコードを変更する必要がなくなります。この変更は、コンパイラの保守性と拡張性を大幅に向上させ、新しいアーキテクチャの追加を容易にします。
*   **`init` メソッドの変更**:
    *   `regAllocState.init` メソッドが、`f.Config.registers` からアーキテクチャ固有のレジスタ情報を取得し、`s.numRegs`, `s.SPReg`, `s.SBReg` を初期化するように変更されました。これにより、レジスタ割り当ての状態が、現在コンパイルしているターゲットアーキテクチャの正確なレジスタ構成で初期化されることが保証されます。

これらの変更は、GoコンパイラのSSAバックエンドがARMアーキテクチャのサポートを開始し、将来的に他のアーキテクチャへの移植も容易になるような、より柔軟でモジュール化された設計へと進化していることを示しています。

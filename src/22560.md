# [インデックス 22560] ファイルの概要

このコミットは、Go言語のWindows環境における外部リンキング（特にCgoを介した`stdcall`呼び出し規約を使用するシステムコール）のサポートを改善するためのものです。具体的には、`stdcall`関数が引数として消費するバイト数をリンカが正確に認識し、Windowsの標準的な名前装飾（`_function@N`形式）を適切に生成できるように、新しいメカニズムを導入しています。これにより、386とamd64の両アーキテクチャで一貫した名前装飾が可能になり、MinGWが提供するインポートライブラリとの互換性が確保されます。

## 元コミット内容

`cmd/internal/ld, runtime: record argument size for cgo_dynimport stdcall syscalls`

外部リンキングを行う際、MinGWが提供するインポートライブラリにリンクする必要があるため、`stdcall`関数には適切に装飾された名前を使用しなければなりません。

この機能はGoランタイムでのみ使用されるため、386とamd64の両方で同じ装飾名を使用できる新しい装飾スキームを設計しました。

例えば、`bar16.dll`から3つのパラメータを取る`FooEx`という名前の`stdcall`関数は、次のようにインポートされます。
`//go:cgo_import_dynamic runtime._FooEx FooEx%3 "bar16.dll"`
`uintptr`のサイズに応じて、リンカは後でこれを`_FooEx@12`または`_FooEx@24`に変換します。

これは、windows/386向けの外部リンキングサポートを追加する次の変更セット（CL）の準備です。

## 変更の背景

Go言語は、デフォルトでは自己完結型の静的リンクされたバイナリを生成しますが、Cgoを使用してC言語のコードやシステムライブラリと連携する場合、外部リンキングが必要になることがあります。特にWindows環境では、システムAPIの多くが`stdcall`呼び出し規約を使用しており、これらの関数をGoから呼び出す際には、Windowsのリンカが期待する特定の方法で関数名が「装飾」（name decorationまたはname mangling）されている必要があります。

Windowsのx86アーキテクチャにおける`stdcall`関数の名前装飾は、通常`_FunctionName@N`の形式を取ります。ここで`N`は、関数が受け取る引数の合計バイト数を示します。この`N`の値は、呼び出し規約の特性（呼び出された関数がスタックをクリーンアップする）上、リンカが正確なスタック操作を行うために不可欠です。

Goの既存の`cgo_import_dynamic`メカニズムでは、この`N`の情報を直接指定する方法がありませんでした。そのため、GoランタイムがWindowsのシステムコールを外部リンキングで利用しようとすると、リンカが正しい名前装飾を生成できず、リンクエラーや実行時エラーが発生する可能性がありました。

このコミットは、特にWindows/386向けの外部リンキングサポートを強化する次の変更セットの「準備」として行われました。既存の`cgo_import_dynamic`ディレクティブに引数のサイズ情報を含める新しい方法を導入することで、Goリンカが`stdcall`関数の正しい名前装飾を生成できるようにし、MinGWなどの外部リンカが提供するインポートライブラリとの互換性を確保することが目的です。

## 前提知識の解説

### 1. `stdcall`呼び出し規約

`stdcall`（Standard Call）は、主にMicrosoft Windows APIで使用される呼び出し規約です。その主な特徴は以下の通りです。

*   **引数の渡し方**: 引数は右から左へスタックにプッシュされます。
*   **スタックのクリーンアップ**: 呼び出された関数（callee）が、自身の実行後にスタックから引数をポップしてクリーンアップする責任を持ちます。これにより、呼び出し元（caller）のコードサイズを削減できますが、可変長引数を持つ関数には使用できません。
*   **名前装飾**: Windowsのx86アーキテクチャでは、`stdcall`関数はリンカによって特定の方法で名前が装飾されます。この形式は通常 `_FunctionName@N` です。
    *   `_`: 関数名の前にアンダースコアが追加されます。
    *   `FunctionName`: 元の関数名です。
    *   `@`: アットマークが追加されます。
    *   `N`: 関数が受け取る引数の合計バイト数です。例えば、`int`型が4バイトの場合、2つの`int`引数を取る関数であれば`@8`となります。この情報は、呼び出された関数がスタックを正しくクリーンアップするために必要です。
    *   x64（64ビット）アーキテクチャでは、引数は主にレジスタで渡されるため、`stdcall`は通常無視され、名前装飾も行われません。

### 2. `//go:cgo_import_dynamic` ディレクティブ

`//go:cgo_import_dynamic`は、Go言語のリンカに対する特殊なディレクティブであり、主にGoランタイム内部で動的ライブラリからシンボルをインポートするために使用されます。これは、Goバイナリが静的にコンパイルされる場合でも、`libc`のようなシステムレベルの動的ライブラリ内の関数を呼び出す必要がある場合に特に重要です。

構文は通常 `//go:cgo_import_dynamic <ローカル名> [<リモート名> ["<ライブラリ名>"]]` の形式を取ります。
*   `<ローカル名>`: Goのコード内で参照されるシンボル名。
*   `<リモート名>`: 動的ライブラリ内の実際のシンボル名。
*   `<ライブラリ名>`: シンボルが見つかる動的ライブラリのファイル名（例: `"kernel32.dll"`）。

このディレクティブを使用すると、Goリンカは最終的な実行可能ファイルが指定されたライブラリに実行時に動的にリンクされるようにします。これは一般的にユーザーが書くGoコードでは使用されず、Goランタイムが低レベルのシステムコールやOSライブラリとのやり取りを管理するために内部的に利用されます。

### 3. Goの外部リンキングとMinGW

Goはデフォルトで、すべての依存関係を単一の実行可能ファイルにバンドルする静的リンクを使用します。これにより、生成されるバイナリは非常にポータブルになります。しかし、Cgoを使用してC言語のコードやライブラリを呼び出す場合、Goは外部リンキングモードに切り替えることがあります。この場合、Goは最終的なリンクステップを外部のCリンカ（例えばGCCの`ld`）に委譲します。

Windows環境では、MinGW（Minimalist GNU for Windows）またはMinGW-w64ツールチェーンが、GoのCgo機能が必要とするGCCコンパイラと関連ツール（`ld`など）を提供します。GoプログラムがCgoを使用する場合、適切にインストールおよび設定されたMinGW環境が必要になります。

`go build`コマンドでCgoが有効になっている場合（デフォルトで有効）、Goは必要に応じて自動的に外部リンカを使用します。`-ldflags "-linkmode 'external'"`オプションを使用して、明示的に外部リンキングを強制することも可能です。

外部リンキングは、Goの内部リンカと互換性のないCライブラリにリンクする場合や、Cリンカに特定のフラグを渡す必要がある場合に必要となります。

## 技術的詳細

このコミットの核心は、`stdcall`関数の引数サイズ情報をGoリンカに伝える新しいメカニズムの導入です。これまでは、`//go:cgo_import_dynamic`ディレクティブでは関数名とライブラリ名しか指定できませんでしたが、`stdcall`の名前装飾に必要な引数サイズの情報が欠けていました。

新しいスキームでは、`//go:cgo_import_dynamic`ディレクティブの関数名に`%N`というサフィックスを追加します。ここで`N`は、関数が受け取る引数の数（`uintptr`単位）を示します。

例: `//go:cgo_import_dynamic runtime._FooEx FooEx%3 "bar16.dll"`

この例では、`FooEx`関数が3つの引数を取ることを示しています。Goリンカ（`cmd/internal/ld`）は、この`%3`サフィックスを解析し、実際の引数の合計バイト数を計算します。この計算は、ターゲットアーキテクチャの`uintptr`のサイズ（386では4バイト、amd64では8バイト）に基づいて行われます。

*   **386アーキテクチャの場合**: `uintptr`は4バイトなので、3つの引数は `3 * 4 = 12` バイトとなります。リンカはこれを `_FooEx@12` に変換します。
*   **amd64アーキテクチャの場合**: `uintptr`は8バイトなので、3つの引数は `3 * 8 = 24` バイトとなります。リンカはこれを `_FooEx@24` に変換します。

このように、`%N`という単一の装飾スキームを使用することで、386とamd64の両アーキテクチャで、リンカがそれぞれの環境に適した`stdcall`の名前装飾（`_function@N`）を動的に生成できるようになります。これにより、GoランタイムがWindowsのシステムAPIを外部リンキングで利用する際の互換性が大幅に向上します。

この変更は、リンカ（`cmd/internal/ld`）が`Imp`構造体に引数サイズを格納する新しいフィールド`argsize`を追加し、`//go:cgo_import_dynamic`ディレクティブから`%N`サフィックスを解析するロジックを実装することで実現されています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  `src/cmd/internal/ld/pe.go`: GoリンカのPortable Executable (PE) フォーマット関連の処理を定義するファイルです。
    *   `Imp`構造体に`argsize`フィールドが追加されました。
    *   `initdynimport`関数内で、`s.Extname`（外部シンボル名）に`%`が含まれている場合、その後の数値を解析して`argsize`に格納し、`s.Extname`から`%N`サフィックスを削除するロジックが追加されました。

2.  `src/runtime/os1_windows.go`: GoランタイムのWindows固有のOSインターフェースを定義するファイルです。
    *   既存の`//go:cgo_import_dynamic`ディレクティブの多くがコメントアウトされ、新しい`%N`形式のディレクティブに置き換えられました。これにより、各`stdcall`システムコールが受け取る引数の数が明示的に指定されるようになりました。

## コアとなるコードの解説

### `src/cmd/internal/ld/pe.go` の変更

```go
type Imp struct {
	s       *LSym
	off     uint64
	next    *Imp
	argsize int // 新しく追加されたフィールド
}

// ... (initdynimport 関数内) ...

		// Because external link requires properly stdcall decorated name,
		// all external symbols in runtime use %n to denote that the number
		// of uinptrs this function consumes. Store the argsize and discard
		// the %n suffix if any.
		m.argsize = -1
		if i := strings.IndexByte(s.Extname, '%'); i >= 0 {
			var err error
			m.argsize, err = strconv.Atoi(s.Extname[i+1:])
			if err != nil {
				Diag("failed to parse stdcall decoration: %v", err)
			}
			m.argsize *= Thearch.Ptrsize // uintptrのサイズを掛けてバイト数に変換
			s.Extname = s.Extname[:i]   // %nサフィックスを削除
		}

		m.s = s
		m.next = d.ms
		d.ms = m
```

*   **`Imp`構造体への`argsize`追加**: `Imp`構造体は、インポートされるシンボル（関数など）の情報を保持します。ここに追加された`argsize`フィールドは、`stdcall`関数の引数の合計バイト数を格納するために使用されます。初期値は`-1`です。
*   **`initdynimport`関数内のロジック**:
    *   このコードブロックは、外部リンキングが必要な`stdcall`関数の名前装飾を処理します。
    *   `s.Extname`は、`//go:cgo_import_dynamic`ディレクティブで指定された外部シンボル名（例: `FooEx%3`）です。
    *   `strings.IndexByte(s.Extname, '%')`で、シンボル名に`%`文字が含まれているかをチェックします。
    *   `%`が見つかった場合、その後の文字列（例: `3`）を`strconv.Atoi`で整数に変換し、`m.argsize`に格納します。これが引数の数（`uintptr`単位）です。
    *   `m.argsize *= Thearch.Ptrsize`によって、この引数の数に現在のアーキテクチャの`uintptr`のサイズ（386では4バイト、amd64では8バイト）を掛け合わせ、引数の合計バイト数を計算します。この合計バイト数が、`_function@N`形式の`N`に相当する値となります。
    *   `s.Extname = s.Extname[:i]`によって、元のシンボル名から`%N`サフィックスを削除します。これにより、リンカはクリーンな関数名（例: `FooEx`）と、計算された`argsize`の両方を持つことになります。

この変更により、Goリンカは`//go:cgo_import_dynamic`ディレクティブから`stdcall`関数の引数サイズを抽出し、Windowsの外部リンカが期待する正しい名前装飾を生成するための情報を内部的に保持できるようになります。

### `src/runtime/os1_windows.go` の変更

このファイルでは、多くの`//go:cgo_import_dynamic`ディレクティブが変更されています。

**変更前（例）**:
`//go:cgo_import_dynamic runtime._CloseHandle CloseHandle "kernel32.dll"`

**変更後（例）**:
`//go:cgo_import_dynamic runtime._CloseHandle CloseHandle%1 "kernel32.dll"`

*   変更前は、`CloseHandle`関数が引数をいくつ取るかという情報がありませんでした。
*   変更後には、`CloseHandle%1`のように`%1`が追加されています。これは、`CloseHandle`関数が1つの`uintptr`サイズの引数を取ることを示しています。
*   同様に、`CreateEventA%4`は4つの引数を、`GetEnvironmentStringsW%0`は0個の引数を取ることを示しています。

これらの変更は、GoランタイムがWindows APIを呼び出す際に、各`stdcall`関数の引数サイズを明示的にリンカに伝えるためのものです。これにより、リンカは前述の`pe.go`のロジックを使用して、正確な`_function@N`形式の名前装飾を生成できるようになります。

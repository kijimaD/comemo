# [インデックス 22673] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるベンチマークテストで発生していたデータ競合（data race）を修正するものです。具体的には、ベンチマーク実行時にテストフックのアンインストール処理が複数回並行して実行される可能性があり、これがデータ競合を引き起こしていました。`sync.Once`の導入により、このアンインストール処理が一度だけ確実に実行されるように変更されています。

## 変更の背景

Go言語のベンチマークテストは、コードのパフォーマンスを測定するために使用されます。しかし、並行処理が絡むテストでは、共有リソースへのアクセスが適切に同期されていないと「データ競合（data race）」が発生する可能性があります。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、そのうち少なくとも1つが書き込み操作である場合に発生し、予測不能な結果やベンチマークの信頼性の低下を招きます。

このコミットの背景には、`net`パッケージのベンチマークテストにおいて、テストフック（`installTestHooks`と`uninstallTestHooks`）の管理方法に問題があったことが挙げられます。
従来のコードでは、各ベンチマーク関数内で`uninstallTestHooks()`が`defer`キーワードを使って呼び出され、さらに`TestMain`関数（テストスイート全体のセットアップとティアダウンを制御する関数）の終了時にも`uninstallTestHooks()`が呼び出されていました。

`defer`は関数の終了時に実行されることを保証しますが、ベンチマークが並行して実行される場合、複数のベンチマーク関数が同時に`uninstallTestHooks()`を呼び出そうとする可能性があります。また、`TestMain`が終了する際にも`uninstallTestHooks()`が呼び出されるため、これらの呼び出しが競合し、テストフックが管理する共有状態に対してデータ競合が発生していました。

このデータ競合は、ベンチマークの実行結果の不安定性や、最悪の場合にはテストのクラッシュを引き起こす可能性がありました。この問題を解決し、ベンチマークの信頼性を向上させることが、このコミットの目的です。

## 前提知識の解説

### 1. Go言語のベンチマークテスト

Go言語の`testing`パッケージは、ユニットテストだけでなくベンチマークテストもサポートしています。ベンチマーク関数は`BenchmarkXxx(*testing.B)`というシグネチャを持ち、`b.N`回繰り返されるループ内で測定対象のコードを実行します。`go test -bench .`コマンドで実行できます。

### 2. `defer`キーワード

`defer`ステートメントは、それを囲む関数がリターンする直前に、指定された関数呼び出しを実行することをスケジュールします。これはリソースのクリーンアップ（ファイルのクローズ、ロックの解放など）によく使用されます。しかし、複数のゴルーチンが同じ`defer`された関数を呼び出す場合、その関数が共有リソースにアクセスするならば、データ競合に注意が必要です。

### 3. データ競合 (Data Race)

データ競合は、並行プログラミングにおけるバグの一種で、以下の3つの条件がすべて満たされたときに発生します。
*   2つ以上のゴルーチンが同時に同じメモリ位置にアクセスする。
*   それらのアクセスのうち少なくとも1つが書き込み操作である。
*   それらのアクセスが同期メカニズム（ミューテックス、チャネルなど）によって保護されていない。

データ競合が発生すると、プログラムの動作が予測不能になり、結果が誤ったり、クラッシュしたりする可能性があります。Goには`go test -race`という組み込みのデータ競合検出機能があり、開発中にデータ競合を特定するのに非常に役立ちます。

### 4. `sync.Once`

`sync.Once`は、Go言語の`sync`パッケージが提供する型で、特定の操作がプログラムの実行中に一度だけ実行されることを保証するために使用されます。これは、初期化処理やリソースのセットアップなど、一度だけ実行されるべき処理に非常に有用です。

`sync.Once`の`Do`メソッドは、引数として渡された関数を一度だけ実行します。複数のゴルーチンが同時に`Do`メソッドを呼び出しても、Goランタイムは内部的に同期を行い、渡された関数が一度だけ実行されることを保証します。これにより、データ競合を防ぎつつ、初期化処理の重複実行を回避できます。

### 5. `TestMain`関数

Goの`testing`パッケージでは、`TestMain(m *testing.M)`という関数を定義することで、テストスイート全体のセットアップ（`installTestHooks`など）とティアダウン（`uninstallTestHooks`など）を制御できます。`m.Run()`を呼び出すことで、実際のテストが実行されます。

## 技術的詳細

このコミットの核心は、`uninstallTestHooks()`の呼び出しを`defer`から`sync.Once`を使った呼び出しに置き換えることで、データ競合を解消した点にあります。

従来のコードでは、`src/net`パッケージ内の複数のベンチマーク関数（例: `BenchmarkGoLookupIP`, `BenchmarkInterfaces`, `BenchmarkParseIP`など）が、それぞれ以下のパターンを持っていました。

```go
func BenchmarkGoLookupIP(b *testing.B) {
	uninstallTestHooks() // ここでフックをアンインストール
	defer installTestHooks() // 関数終了時にフックを再インストール

	for i := 0; i < b.N; i++ {
		// ... ベンチマーク対象のコード ...
	}
}
```

この`uninstallTestHooks()`と`defer installTestHooks()`のペアは、各ベンチマークの開始時にフックをアンインストールし、終了時に再インストールすることを意図していました。しかし、Goのベンチマークは並行して実行されることがあり、複数のベンチマークが同時に`uninstallTestHooks()`を呼び出す可能性がありました。

さらに、`src/net/main_test.go`の`TestMain`関数では、テストスイートの終了時に`uninstallTestHooks()`が呼び出されていました。

```go
func TestMain(m *testing.M) {
	installTestHooks()

	st := m.Run()

	// ...
	uninstallTestHooks() // ここでもフックをアンインストール
	os.Exit(st)
}
```

この二重のアンインストール呼び出しと、ベンチマークの並行実行が組み合わさることで、`uninstallTestHooks()`が管理する共有状態（おそらくグローバル変数やパッケージレベルの変数）に対して、複数のゴルーチンからの非同期なアクセスが発生し、データ競合を引き起こしていました。

この問題を解決するため、コミットでは以下の変更が行われました。

1.  **`sync.Once`インスタンスの導入**: `src/net/main_test.go`に`testHookUninstaller sync.Once`というグローバル変数が追加されました。
2.  **`defer`呼び出しの置き換え**: 各ベンチマーク関数内の`uninstallTestHooks()`と`defer installTestHooks()`のペアが、`testHookUninstaller.Do(func() { uninstallTestHooks() })`という形式に置き換えられました。これにより、`uninstallTestHooks()`は`testHookUninstaller`によって一度だけ実行されることが保証されます。
3.  **`TestMain`からの`uninstallTestHooks()`呼び出しの変更**: `TestMain`関数内の`uninstallTestHooks()`の直接呼び出しも、`testHookUninstaller.Do(func() { uninstallTestHooks() })`に置き換えられました。これにより、`TestMain`が終了する際にも、`uninstallTestHooks()`がまだ実行されていなければ一度だけ実行されるようになります。

この変更により、`uninstallTestHooks()`は、どのベンチマーク関数から呼び出されようと、あるいは`TestMain`から呼び出されようと、プログラムの実行中に一度だけ実行されることが保証され、共有状態への非同期アクセスによるデータ競合が解消されました。

## コアとなるコードの解説

### `src/net/main_test.go`

1.  **`sync`パッケージのインポート**: `import ("sync")`が追加され、`sync.Once`を使用できるようになりました。
2.  **`testHookUninstaller`の宣言**: `var testHookUninstaller sync.Once`が宣言されました。これは、`uninstallTestHooks`関数が一度だけ実行されることを保証するための`sync.Once`インスタンスです。コメントで「`uninstallTestHooks` runs just before a run of benchmarks.」と説明されており、ベンチマーク実行の直前にフックがアンインストールされる意図が示されています。
3.  **`TestMain`内の変更**:
    *   `m.Run()`の後にあった`uninstallTestHooks()`の直接呼び出しが削除されました。
    *   代わりに`testHookUninstaller.Do(func() { uninstallTestHooks() })`が追加されました。これにより、`TestMain`が終了する際に、まだ`uninstallTestHooks()`が実行されていなければ、この`Do`メソッドによって一度だけ実行されます。

### 各ベンチマークテストファイル

各ベンチマーク関数（例: `BenchmarkGoLookupIP`）内で、以下の変更が行われました。

1.  **`uninstallTestHooks()`と`defer installTestHooks()`の削除**: 以前はベンチマークの開始時に`uninstallTestHooks()`を呼び出し、終了時に`installTestHooks()`を`defer`で呼び出していましたが、これらが削除されました。
2.  **`testHookUninstaller.Do(...)`の追加**: 代わりに`testHookUninstaller.Do(func() { uninstallTestHooks() })`が追加されました。これにより、各ベンチマーク関数が実行される際に、`uninstallTestHooks()`が`sync.Once`によって一度だけ実行されるように調整されます。

この変更のポイントは、`uninstallTestHooks()`の呼び出しを`sync.Once`でラップすることで、複数のベンチマークが並行して実行されても、あるいは`TestMain`が終了する際にも、`uninstallTestHooks()`が一度しか実行されないようにした点です。これにより、`uninstallTestHooks()`が操作する共有リソースに対するデータ競合が効果的に防止されます。

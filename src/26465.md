## 変更の背景

このコミットの背景には、`net/http` パッケージの `TimeFormat` 定数のドキュメントが不十分であり、開発者がHTTPヘッダーで時刻を扱う際に誤解や誤用を招く可能性があったという問題があります。特に、HTTPヘッダーの時刻フォーマットはRFC 1123に準拠しており、タイムゾーンとしてGMT（グリニッジ標準時）を使用することが求められます。しかし、Goの `time.Format` メソッドは、指定された `time.Time` オブジェクトのロケーション（タイムゾーン）に基づいて文字列を生成するため、`TimeFormat` を使用して時刻をフォーマットする際に、`time.Time` オブジェクトがUTC（協定世界時）に設定されていないと、期待されるGMT形式にならないという問題が発生する可能性がありました。

また、`TimeFormat` は主に時刻の「生成」に使われることを意図していましたが、時刻の「パース」についても明確なガイダンスが不足していました。このコミットは、これらの点を明確にし、開発者が `net/http` パッケージで時刻を正しく扱うための情報を提供することを目的としています。コミットメッセージにある `Fixes #14103` は、このドキュメントの不備に関する課題がGoのIssueトラッカーで報告されていたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびHTTPプロトコルに関する前提知識が必要です。

1.  **Go言語の `time` パッケージ**:
    *   `time.Time`: 時刻を表す構造体です。
    *   `time.Format(layout string) string`: `time.Time` オブジェクトを指定されたレイアウト文字列に従ってフォーマットし、文字列として返します。レイアウト文字列は、特定の参照時刻（`Mon Jan 2 15:04:05 MST 2006`）を基準に、その各要素がどのように表示されるかを定義します。
    *   `time.Parse(layout string, value string) (Time, error)`: 指定されたレイアウト文字列と時刻文字列から `time.Time` オブジェクトをパースします。
    *   `time.UTC()`: `time.Time` オブジェクトをUTCロケーションに変換します。
    *   `time.RFC1123`: `time` パッケージで定義されている標準の時刻フォーマットレイアウトの一つで、HTTPヘッダーでよく使用される形式（例: `Mon, 02 Jan 2006 15:04:05 MST`）に似ています。

2.  **HTTPヘッダーの時刻フォーマット**:
    *   HTTP/1.1では、日付/時刻のフォーマットとしてRFC 1123で定義された形式（例: `Date: Tue, 15 Nov 1994 08:12:31 GMT`）が推奨されています。
    *   この形式では、タイムゾーンとして常にGMTが使用されます。これは、クライアントとサーバー間で時刻の解釈に一貫性を持たせるためです。

3.  **`net/http` パッケージ**:
    *   Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
    *   `http.TimeFormat`: HTTPヘッダーで使用される時刻フォーマットのレイアウト文字列を定義する定数です。このコミットの対象となっています。
    *   `http.ParseTime(text string) (Time, error)`: HTTPヘッダーの時刻文字列をパースするための関数です。

## 技術的詳細

このコミットの技術的な詳細は、`http.TimeFormat` 定数のドキュメントコメントの修正に集約されます。以前のドキュメントは、`TimeFormat` が `time.RFC1123` に似ており、GMTをタイムゾーンとしてハードコードしていると説明していました。しかし、この説明だけでは、`time.Time.Format` メソッドの挙動と組み合わせた際の潜在的な落とし穴が明確ではありませんでした。

具体的には、`time.Time.Format` は、`time.Time` オブジェクトが持つロケーション情報に基づいて時刻をフォーマットします。もし `time.Time` オブジェクトがローカルタイムゾーンや他のタイムゾーンに設定されている場合、`http.TimeFormat` を使用してフォーマットしても、出力されるタイムゾーンはGMTではなく、元のオブジェクトのタイムゾーンが反映されてしまいます。HTTPヘッダーではGMTが必須であるため、これは問題となります。

新しいドキュメントは、この重要な制約を明確にしています。「The time being formatted must be in UTC for Format to generate the correct format.」（フォーマットされる時刻は、正しい形式を生成するためにUTCである必要があります。）という一文が追加され、開発者が `time.Time` オブジェクトを `http.TimeFormat` でフォーマットする前に、必ず `t.UTC()` を呼び出してUTCに変換する必要があることを強調しています。

さらに、時刻の「パース」についてもガイダンスが追加されました。以前のドキュメントは時刻の生成とパースの両方に言及していましたが、新しいドキュメントでは `TimeFormat` が主に「生成」のためのものであることを明確にし、「For parsing this time format, see ParseTime.」（この時刻フォーマットをパースするには、`ParseTime` を参照してください。）と追記することで、`http.ParseTime` 関数への誘導を行っています。これにより、開発者は時刻のパースに適切なAPIを使用するよう促されます。

これらの変更は、コードの動作自体を変更するものではなく、APIの正しい使用方法に関する開発者の理解を深め、一般的な誤用を防ぐための純粋なドキュメント改善です。

## コアとなるコードの解説

変更されたドキュメントコメントは、以下の2つの主要な点を明確にしています。

1.  **時刻の生成におけるUTCの要件**:
    *   変更前: `// TimeFormat is the time format to use with // time.Parse and time.Time.Format when parsing // or generating times in HTTP headers. // It is like time.RFC1123 but hard codes GMT as the time zone.`
    *   変更後: `// TimeFormat is the time format to use when generating times in HTTP // headers. It is like time.RFC1123 but hard-codes GMT as the time // zone. The time being formatted must be in UTC for Format to // generate the correct format.`
    *   この修正により、`TimeFormat` を使用してHTTPヘッダーの時刻を生成する際には、`time.Time` オブジェクトが必ずUTCである必要があることが明示されました。これは、`time.Format` が `time.Time` オブジェクトのロケーション情報を使用するため、GMTを期待するHTTPヘッダーの要件を満たすためには、事前に `t.UTC()` を呼び出す必要があることを意味します。

2.  **時刻のパースに関するガイダンス**:
    *   変更前: `time.Parse` と `time.Time.Format` の両方で `TimeFormat` を使用すると記載されていました。
    *   変更後: `// For parsing this time format, see ParseTime.`
    *   この追加により、`TimeFormat` が主に時刻の「生成」に特化していることを示唆し、時刻の「パース」には `net/http` パッケージが提供する専用の `ParseTime` 関数を使用すべきであることが明確にされました。これにより、開発者はより堅牢で正しいパース処理を行うことができます。

これらの変更は、`net/http` パッケージのAPIをより安全かつ正確に使用するための重要な情報を提供し、開発者の混乱を減らすことに貢献します。

`syscall: fix uint64->int cast of control message header`

このコミットは、ソケット制御メッセージヘッダーの`uint64`から`int`への型キャストに関する問題を修正するものです。

## 変更の背景

Go言語の`syscall`パッケージは、オペレーティングシステムの低レベルな機能にアクセスするためのインターフェースを提供します。特にUnix系システムでは、ソケット通信において通常のデータに加えて補助データ（ancillary data）をやり取りするために「制御メッセージ（control message）」が使用されます。この制御メッセージは`Cmsghdr`構造体によって表現され、その長さを示すフィールド`Len`は`uint64`型（またはシステムによっては`uint32`型）で定義されています。

変更前のコードでは、制御メッセージの長さをチェックする際に、`h.Len`（`uint64`型）を`int`型にキャストしてから、バイトスライス`b`の長さ（`len(b)`は`int`型を返す）と比較していました。この`uint64`から`int`へのキャストは、特に`h.Len`が`int`型で表現できる最大値を超える場合に問題を引き起こす可能性がありました。`uint64`の大きな値が`int`にキャストされると、オーバーフローによって負の値になったり、予期せぬ小さな値になったりする可能性があります。これにより、`int(h.Len) > len(b)`という比較が誤った結果を返し、バッファオーバーリードやセキュリティ上の脆弱性につながる可能性がありました。

このコミットは、このような潜在的なバグやセキュリティリスクを回避するために、型キャストの安全性を確保することを目的としています。

## 前提知識の解説

### Go言語の`syscall`パッケージ

`syscall`パッケージは、GoプログラムからOSのシステムコールを直接呼び出すための機能を提供します。これにより、ファイル操作、ネットワーク通信、プロセス管理など、OSレベルの低レイヤーな操作が可能になります。このパッケージは、OS固有の機能にアクセスする必要がある場合や、パフォーマンスが重要な場面で利用されます。

### ソケット制御メッセージ（Control Message）と`Cmsghdr`

UnixドメインソケットやIPソケットでは、通常のデータ（ペイロード）に加えて、ファイルディスクリプタの受け渡し、資格情報の送信、IPオプションの設定など、様々な補助情報をやり取りするために「制御メッセージ」が使用されます。
制御メッセージは、`Cmsghdr`（Control Message Header）構造体とそれに続くデータで構成されます。`Cmsghdr`はC言語の`cmsghdr`構造体に対応しており、メッセージのタイプ、レベル、そしてメッセージ全体の長さ（`cmsg_len`）などの情報を含みます。Go言語の`syscall.Cmsghdr`も同様の役割を果たします。

### `uint64`と`int`の型キャスト問題

Go言語において、`uint64`は符号なし64ビット整数、`int`はシステムに依存する符号付き整数型（通常32ビットまたは64ビット）です。
- `uint64`は`0`から`18,446,744,073,709,551,615`までの値を表現できます。
- `int`（64ビットシステムの場合）は`-9,223,372,036,854,775,808`から`9,223,372,036,854,775,807`までの値を表現できます。

`uint64`の値を`int`にキャストする際、もし`uint64`の値が`int`の最大値を超えている場合、値が切り捨てられたり、符号が反転したりする「整数オーバーフロー」が発生します。これは予期せぬ動作やセキュリティ上の脆弱性（例: バッファサイズの誤認識）につながる可能性があります。

### `len(b)`の戻り値

Go言語の組み込み関数`len()`は、スライスや配列の長さを返す際に`int`型を返します。これは、Goの設計思想として、メモリ上のオブジェクトのサイズは通常`int`で十分表現できるという考えに基づいています。

### `EINVAL`エラー

`EINVAL`は"Invalid argument"（無効な引数）を意味するエラーコードです。システムコールが不正な引数で呼び出された場合に返されます。このコミットの文脈では、制御メッセージの長さが不正であると判断された場合に返されるエラーとして使用されています。

## 技術的詳細

変更が行われたのは、`src/syscall/sockcmsg_unix.go`ファイル内の`socketControlMessageHeaderAndData`関数です。この関数は、バイトスライス`b`からソケット制御メッセージヘッダー（`Cmsghdr`）とそのデータを抽出する役割を担っています。

変更前のコードでは、制御メッセージヘッダーの`Len`フィールド（`uint64`型）と入力バイトスライス`b`の長さ（`int`型）を比較する際に、以下のような条件式が使われていました。

```go
if h.Len < SizeofCmsghdr || int(h.Len) > len(b) {
    return nil, nil, EINVAL
}
```

ここで問題となるのは、`int(h.Len)`の部分です。もし`h.Len`が`int`型で表現できる最大値（例えば`2^63 - 1`）を超えるような非常に大きな値であった場合、`int(h.Len)`のキャストによって値がオーバーフローし、負の値や非常に小さな値になってしまう可能性があります。その結果、`int(h.Len) > len(b)`という比較が、本来は`h.Len`が`len(b)`よりも大きいにもかかわらず、`false`と評価されてしまうことがあり得ました。これは、`b`の範囲を超えてメモリにアクセスしようとするバッファオーバーリードの脆弱性につながる可能性があります。

このコミットでは、この問題を解決するために、比較の両辺を`uint64`型に明示的にキャストするように変更されました。

```go
if h.Len < SizeofCmsghdr || uint64(h.Len) > uint64(len(b)) {
    return nil, nil, EINVAL
}
```

この変更により、`h.Len`と`len(b)`の比較は両方とも`uint64`型で行われるため、`int`型へのキャストによるオーバーフローの問題が解消されます。`len(b)`は常に非負の値であるため、`uint64(len(b))`へのキャストは安全です。これにより、制御メッセージの長さがバッファの実際の長さを超えていないかを正確にチェックできるようになり、堅牢性とセキュリティが向上します。

## コアとなるコードの解説

変更された行は、`socketControlMessageHeaderAndData`関数内の`if`文の条件式です。

- **変更前**: `if h.Len < SizeofCmsghdr || int(h.Len) > len(b) {`
    - `h.Len`は`Cmsghdr`構造体の`Len`フィールドで、`uint64`型です。
    - `SizeofCmsghdr`は`Cmsghdr`構造体のサイズで、定数です。
    - `len(b)`はバイトスライス`b`の長さで、`int`型です。
    - ここで`int(h.Len)`とキャストしているため、`h.Len`が`int`の最大値を超えるとオーバーフローが発生し、比較が不正になる可能性がありました。

- **変更後**: `if h.Len < SizeofCmsghdr || uint64(h.Len) > uint64(len(b)) {`
    - `h.Len`は引き続き`uint64`型です。
    - `len(b)`を`uint64(len(b))`と明示的に`uint64`型にキャストしています。
    - これにより、`h.Len`と`len(b)`の比較が両方とも`uint64`型で行われるようになります。
    - `len(b)`は常に非負であるため、`uint64`へのキャストは安全であり、オーバーフローの心配がなくなります。
    - 結果として、制御メッセージの長さがバッファの範囲内に収まっているかを正確かつ安全に検証できるようになりました。

この修正は、低レベルなシステムコールインターフェースにおける型安全性を確保し、潜在的なメモリ関連のバグやセキュリティ脆弱性を防ぐ上で非常に重要です。

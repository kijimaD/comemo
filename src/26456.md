## 変更の背景

この変更の背景には、Go言語の `time` パッケージがタイムゾーン情報を効率的に処理するための内部キャッシュメカニズムがあります。`time.Location` 構造体は、特定のタイムゾーンにおける時間変換ルール（夏時間など）をカプセル化します。これらのルールは時間の経過とともに変化する可能性があるため、`Location` は内部的にタイムゾーンの遷移情報を保持しています。

パフォーマンスを向上させるため、`Location` は最近アクセスされた時間範囲のタイムゾーン情報をキャッシュします。このキャッシュは `cacheStart`, `cacheEnd`, `cacheZone` といったフィールドで管理されます。

元のコメントでは、キャッシュが有効な時間範囲を `cacheStart <= t <= cacheEnd` と記述していました。しかし、多くのプログラミング言語や時間処理ライブラリでは、時間範囲の終端は排他的（exclusive）に扱われるのが一般的です。例えば、`[start, end)` のように `start` は含み `end` は含まないという形式です。これは、連続する時間区間を定義する際に、区間の境界が重複しないようにするため、また、区間の長さを `end - start` で正確に計算できるようにするためです。

このコミットは、`time.Location` の内部実装が `cacheEnd` を排他的な境界として扱っているにもかかわらず、コメントが包括的（inclusive）であるかのように誤解を招く表現になっていた点を修正しています。このコメントの不一致は、コードを理解しようとする開発者にとって混乱の原因となる可能性がありました。したがって、コメントを実際のコードの動作と一致させることで、コードの可読性と保守性を向上させることが変更の主な目的です。

## 前提知識の解説

### Go言語の `time` パッケージ

Go言語の `time` パッケージは、時刻の表現、時間間隔、タイムゾーン処理、日付と時刻のフォーマットなど、時間に関連する機能を提供します。

*   **`time.Time`**: 特定の瞬間を表す構造体です。UTC（協定世界時）または特定の `time.Location` に関連付けられます。
*   **`time.Duration`**: 時間の長さを表す型です。
*   **`time.Location`**: タイムゾーン情報を表す構造体です。特定の地理的地域における時間オフセットや夏時間（Daylight Saving Time, DST）のルールを定義します。`time.LoadLocation` 関数や `time.FixedZone` 関数で取得できます。

### タイムゾーンと夏時間

タイムゾーンは、地球上の特定の地域で共通して使用される標準時を定義します。夏時間は、特定の期間（通常は夏の間）に時計を1時間進める制度で、エネルギー節約などを目的とします。

タイムゾーンのルールは複雑で、歴史的、政治的な理由により頻繁に変更されることがあります。また、夏時間の開始・終了時刻は年によって異なる場合があります。Goの `time` パッケージは、これらの複雑なルールを `zoneinfo` データ（通常はIANA Time Zone Databaseから派生）に基づいて処理します。

### キャッシュの重要性

`time.Location` が `time.Time` オブジェクトを特定のタイムゾーンに変換する際、その時刻がどのタイムゾーンルール（例えば、夏時間中か否か）に該当するかを判断する必要があります。これには、タイムゾーンの遷移情報（`tx` フィールド）を検索する処理が含まれます。この検索は、特に頻繁に時間変換が行われる場合にパフォーマンスのボトルネックとなる可能性があります。

そこで、`Location` 構造体は、最近変換された時間範囲のタイムゾーン情報をキャッシュするメカニズムを持っています。これにより、同じ時間範囲内の変換要求に対しては、高コストな検索処理をスキップし、キャッシュされた情報（`cacheZone`）を直接利用することで、パフォーマンスを向上させます。

### 範囲の包括性（Inclusive）と排他性（Exclusive）

プログラミングにおいて、数値の範囲を扱う際には、その範囲の開始点と終了点を含むか含まないか（包括的か排他的か）を明確に定義することが非常に重要です。

*   **包括的 (Inclusive)**: 範囲の開始点と終了点の両方を含む場合。例: `[a, b]` は `a <= x <= b` を意味します。
*   **排他的 (Exclusive)**: 範囲の開始点を含み、終了点を含まない場合（またはその逆）。例: `[a, b)` は `a <= x < b` を意味します。

時間範囲を扱う場合、`[start, end)` の形式がよく用いられます。これは、`start` から始まり `end` の直前までを意味し、`end` は次の区間の開始点として機能するため、区間の連続性と非重複性を保証しやすいためです。

	// ...
	// To avoid the binary search through tx, keep a
	// static one-element cache that gives the correct
	// zone for the time when the Location was created.

コメントの修正は、この `cacheEnd` が排他的であるという実装の事実を明示するものです。もし `cacheEnd` が包括的であると誤解された場合、`t == cacheEnd` のケースでキャッシュが使用されることになりますが、実際の実装では `cacheEnd` は次の時間区間の開始点であるため、これは誤りとなります。特に、タイムゾーンのルールが切り替わる境界時刻において、この包括性/排他性の違いは、正しいタイムゾーン情報を取得できるかどうかに直接影響します。

例えば、夏時間が終了し標準時間に戻る瞬間など、タイムゾーンのオフセットが変化する境界時刻では、`cacheEnd` がその変化の瞬間を指すことが多いです。この場合、`cacheEnd` の時刻自体は既に新しい（次の）タイムゾーンルールに属するため、現在のキャッシュ範囲には含めるべきではありません。

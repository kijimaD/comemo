## 元コミット内容

このコミットは、`src/runtime/append_test.go` ファイルに129行の追加を行い、`append` 関数のインプレース最適化に関する新しいベンチマークスイートを導入しています。具体的には、`BenchmarkAppendInPlace` という新しいベンチマーク関数が追加され、`NoGrow`（容量拡張なし）と `Grow`（容量拡張あり）の2つのシナリオで、異なる型のスライス（`byte`, `uintptr`, `[2]uintptr`, `[3]uintptr`, `[4]uintptr`）に対する `append` のパフォーマンスを測定します。

## 変更の背景

Go言語の `append` 関数は、スライスに要素を追加するための組み込み関数です。スライスの基底配列に十分な容量がある場合、`append` は新しい配列を割り当てることなく、既存の配列の末尾に要素を追加できます。この挙動は「インプレース（in-place）」での追加と呼ばれ、メモリ割り当てとデータコピーのオーバーヘッドを避けるため、パフォーマンス上の重要な最適化となります。

このコミットが追加された背景には、`append` のインプレース最適化が実際にどの程度のパフォーマンス向上をもたらすのか、またどのような条件下でその恩恵が最大化されるのかを定量的に把握したいという意図があります。特に、`append` の結果が元のスライス変数に直接代入される（`s = append(s, x)` のような形式）場合に、コンパイラやランタイムがインプレースでの操作をより効率的に行える可能性があります。

ベンチマークを追加することで、以下の目的が達成されます。
*   **パフォーマンスの監視**: 将来のランタイム変更がインプレース `append` のパフォーマンスに与える影響を継続的に監視できます。
*   **最適化の検証**: インプレース `append` の最適化が期待通りに機能しているか、あるいはさらなる改善の余地があるかを評価できます。
*   **挙動の理解**: 開発者が `append` のパフォーマンス特性をより深く理解するためのデータを提供します。

## 前提知識の解説

### Go言語のスライス (Slice)

Go言語のスライスは、配列のセグメントを参照するデータ構造です。スライスは以下の3つの要素で構成されます。
1.  **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。
3.  **容量 (Capacity)**: スライスの先頭要素から基底配列の末尾までの要素の数。

スライスは動的なサイズ変更が可能ですが、これは実際には新しい基底配列の割り当てと要素のコピーを伴う場合があります。

### `append` 関数

`append` 関数は、スライスに要素を追加するために使用されます。その挙動はスライスの容量に依存します。
*   **容量が十分な場合 (No Grow)**: スライスの容量が追加する要素を格納するのに十分な場合、`append` は既存の基底配列の空きスペースに要素を追加し、スライスの長さを更新します。この操作はインプレースで行われ、新しいメモリ割り当てやデータコピーは発生しません。
*   **容量が不足する場合 (Grow)**: スライスの容量が不足している場合、`append` はより大きな新しい基底配列を割り当て、既存の要素を新しい配列にコピーし、その後で新しい要素を追加します。この操作はメモリ割り当てとデータコピーのオーバーヘッドを伴います。

### インプレース `append` の最適化

`s = append(s, x)` のように、`append` の結果が元のスライス変数 `s` に直接代入される場合、Goコンパイラやランタイムは特別な最適化を適用することがあります。特に、`s` がグローバル変数やポインタを通じて参照されている場合、コンパイラは `append` が新しいスライスヘッダを返す代わりに、既存のスライスヘッダを直接変更できると判断し、より効率的なコードを生成する可能性があります。これにより、スライスヘッダのコピーが不要になり、パフォーマンスが向上します。

### Goのベンチマーク

Go言語には、`testing` パッケージを通じて組み込みのベンチマーク機能が提供されています。ベンチマーク関数は `BenchmarkXxx(*testing.B)` というシグネチャを持ち、`b.N` 回の操作の実行時間を測定します。`b.Run` を使用することで、サブベンチマークを作成し、異なるシナリオやパラメータでのパフォーマンスを比較できます。

### Write Barrier (書き込みバリア)

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、ガベージコレクション中にプログラムがオブジェクトグラフを変更するのを管理するために「書き込みバリア」を使用します。これは、ポインタの書き込み時に特定の処理（例えば、オブジェクトがマーク済みであることの確認）を実行するメカニズムです。ベンチマークでは、書き込みバリアのオーバーヘッドを避けるために、ポインタ型ではなくスカラー型（`uintptr` など）を使用することがあります。これは、ガベージコレクションのオーバーヘッドがベンチマーク結果に影響を与えるのを防ぐためです。

## 技術的詳細

このコミットで追加されたベンチマーク `BenchmarkAppendInPlace` は、`append` のインプレース最適化の挙動を詳細にテストするために設計されています。

### グローバル変数の使用

ベンチマークコードでは、`sByte`, `s1Ptr`, `s2Ptr`, `s3Ptr`, `s4Ptr` といったグローバル変数が使用されています。これは、コミットメッセージにもあるように「インプレース最適化が発生するためには、スライスがアドレスによって参照される必要がある。グローバル変数を使用することは、それをトリガーする簡単な方法である」という理由からです。グローバル変数は常にアドレスが既知であるため、コンパイラは `append` がスライスヘッダをインプレースで更新できる可能性をより容易に判断できます。

### `NoGrow` と `Grow` シナリオの分離

ベンチマークは `NoGrow` と `Grow` の2つの主要なシナリオに分けられています。
*   **`NoGrow` シナリオ**:
    *   `make([]byte, C)` のように、事前に十分な容量を持つスライスを作成します。
    *   `C` は `128` に設定されており、ループ内で `C` 回 `append` を呼び出しても容量が不足しないようにします。
    *   これにより、メモリ再割り当てやデータコピーが発生しない、純粋なインプレース `append` のパフォーマンスが測定されます。
*   **`Grow` シナリオ**:
    *   `make([]byte, 0)` のように、初期容量がゼロのスライスを作成します。
    *   ループ内で `append` を呼び出すたびに容量が不足し、新しい基底配列が割り当てられ、要素がコピーされる挙動を強制します。
    *   `sByte = sByte[:cap(sByte)]` のように、`append` の後にスライスの長さを容量いっぱいに拡張する操作が含まれています。これは、次の `append` で確実に容量が不足するようにするための工夫です。
    *   `C` は `5` に設定されており、メモリ割り当てとコピーのオーバーヘッドがベンチマーク結果に明確に現れるように、比較的小さな回数で容量拡張を繰り返します。

### 異なる型のスライス

ベンチマークは、以下の異なる型のスライスに対して実行されます。
*   `[]byte`: バイトスライス。最も一般的なスライスの一つ。
*   `[]uintptr`: ポインタサイズのスカラー値のスライス。書き込みバリアのオーバーヘッドを避けるために使用されます。
*   `[][2]uintptr`, `[][3]uintptr`, `[][4]uintptr`: 複数の `uintptr` を含む構造体のスライス。これは、文字列/インターフェースやスライスといった、より大きな要素サイズをシミュレートするために使用されます。これにより、要素サイズがパフォーマンスに与える影響を評価できます。

### ベンチマークの目的

コミットメッセージに記載されているように、このベンチマークは「メモリ割り当てとコピーのベンチマークを避けるために、小さな数値と小さなサイズを使用する」ことを意図しています。また、「書き込みバリアのベンチマークを避けるために、ポインタではなくスカラーを使用する」とも述べられています。これは、`append` 自体のインプレース操作の効率性、特にスライスヘッダの更新や要素の追加にかかる純粋なコストを測定することに焦点を当てていることを示しています。

## コアとなるコードの変更箇所

`src/runtime/append_test.go` に以下のコードが追加されました。

```go
var (
	sByte []byte
	s1Ptr []uintptr
	s2Ptr [][2]uintptr
	s3Ptr [][3]uintptr
	s4Ptr [][4]uintptr
)

// BenchmarkAppendInPlace tests the performance of append
// when the result is being written back to the same slice.
// In order for the in-place optimization to occur,
// the slice must be referred to by address;
// using a global is an easy way to trigger that.
// We test the "grow" and "no grow" paths separately,
// but not the "normal" (occasionally grow) path,
// because it is a blend of the other two.
// We use small numbers and small sizes in an attempt
// to avoid benchmarking memory allocation and copying.
// We use scalars instead of pointers in an attempt
// to avoid benchmarking the write barriers.
// We benchmark four common sizes (byte, pointer, string/interface, slice),
// and one larger size.
func BenchmarkAppendInPlace(b *testing.B) {
	b.Run("NoGrow", func(b *testing.B) {
		const C = 128

		b.Run("Byte", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				sByte = make([]byte, C)
				for j := 0; j < C; j++ {
					sByte = append(sByte, 0x77)
				}
			}
		})

		b.Run("1Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s1Ptr = make([]uintptr, C)
				for j := 0; j < C; j++ {
					s1Ptr = append(s1Ptr, 0x77)
				}
			}
		})

		b.Run("2Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s2Ptr = make([][2]uintptr, C)
				for j := 0; j < C; j++ {
					s2Ptr = append(s2Ptr, [2]uintptr{0x77, 0x88})
				}
			}
		})

		b.Run("3Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s3Ptr = make([][3]uintptr, C)
				for j := 0; j < C; j++ {
					s3Ptr = append(s3Ptr, [3]uintptr{0x77, 0x88, 0x99})
				}
			}
		})

		b.Run("4Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s4Ptr = make([][4]uintptr, C)
				for j := 0; j < C; j++ {
					s4Ptr = append(s4Ptr, [4]uintptr{0x77, 0x88, 0x99, 0xAA})
				}
			}
		})

	})

	b.Run("Grow", func(b *testing.B) {
		const C = 5

		b.Run("Byte", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				sByte = make([]byte, 0)
				for j := 0; j < C; j++ {
					sByte = append(sByte, 0x77)
					sByte = sByte[:cap(sByte)]
				}
			}
		})

		b.Run("1Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s1Ptr = make([]uintptr, 0)
				for j := 0; j < C; j++ {
					s1Ptr = append(s1Ptr, 0x77)
					s1Ptr = s1Ptr[:cap(s1Ptr)]
				}
			}
		})

		b.Run("2Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s2Ptr = make([][2]uintptr, 0)
				for j := 0; j < C; j++ {
					s2Ptr = append(s2Ptr, [2]uintptr{0x77, 0x88})
					s2Ptr = s2Ptr[:cap(s2Ptr)]
				}
			}
		})

		b.Run("3Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s3Ptr = make([][3]uintptr, 0)
				for j := 0; j < C; j++ {
					s3Ptr = append(s3Ptr, [3]uintptr{0x77, 0x88, 0x99})
					s3Ptr = s3Ptr[:cap(s3Ptr)]
				}
			}
		})

		b.Run("4Ptr", func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				s4Ptr = make([][4]uintptr, 0)
				for j := 0; j < C; j++ {
					s4Ptr = append(s4Ptr, [4]uintptr{0x77, 0x88, 0x99, 0xAA})
					s4Ptr = s4Ptr[:cap(s4Ptr)]
				}
			}
		})

	})
}
```

## コアとなるコードの解説

追加されたベンチマークコードは、`append` のインプレース最適化の挙動を詳細に分析するためのものです。

1.  **グローバル変数の宣言**:
    `sByte`, `s1Ptr`, `s2Ptr`, `s3Ptr`, `s4Ptr` は、それぞれ異なる型のスライスを保持するためのグローバル変数です。これらをグローバルにすることで、`append` の結果が元のスライス変数に直接書き戻される際に、コンパイラがインプレース最適化を適用しやすくなります。

2.  **`BenchmarkAppendInPlace` 関数**:
    このメインのベンチマーク関数は、`b.Run` を使用して `NoGrow` と `Grow` の2つのサブベンチマークに分割されています。これにより、容量拡張の有無によるパフォーマンスの違いを明確に比較できます。

3.  **`NoGrow` サブベンチマーク**:
    *   `const C = 128`: 各テストケースで `append` を呼び出す回数を定義しています。この値は、`make` で初期化されるスライスの容量と同じかそれ以下になるように選ばれています。
    *   各 `b.Run` ブロック内では、`make` を使って `C` の長さと容量を持つスライスを初期化します。
    *   `for j := 0; j < C; j++ { ... sByte = append(sByte, 0x77) ... }`: ループ内で `append` を `C` 回呼び出します。この際、スライスは常に十分な容量を持っているため、新しい基底配列の割り当てやコピーは発生しません。これにより、純粋なインプレース `append` のコストが測定されます。
    *   `0x77` などの定数値が追加されていますが、これはベンチマークの対象が `append` のメカニズム自体であり、追加される値の内容ではないため、具体的な意味はありません。

4.  **`Grow` サブベンチマーク**:
    *   `const C = 5`: 各テストケースで `append` を呼び出す回数を定義しています。この値は小さく設定されており、各 `append` 呼び出しで容量が不足し、再割り当てが発生するように意図されています。
    *   各 `b.Run` ブロック内では、`make` を使って長さ0、容量0のスライスを初期化します。
    *   `for j := 0; j < C; j++ { ... sByte = append(sByte, 0x77) ... sByte = sByte[:cap(sByte)] }`: ループ内で `append` を呼び出します。
        *   `sByte = append(sByte, 0x77)`: 容量が不足しているため、新しい基底配列が割り当てられ、要素がコピーされ、新しい要素が追加されます。
        *   `sByte = sByte[:cap(sByte)]`: この行は非常に重要です。`append` によってスライスの長さは増えますが、容量は変わらない可能性があります。この操作は、スライスの長さをその容量いっぱいに設定し直すことで、次の `append` 呼び出しで確実に容量が不足するように仕向けています。これにより、各イテレーションで容量拡張のコストが測定されます。

5.  **型のバリエーション**:
    `Byte`, `1Ptr`, `2Ptr`, `3Ptr`, `4Ptr` の各サブベンチマークは、`byte`、`uintptr`、および複数の `uintptr` を含む構造体のスライスに対して実行されます。
    *   `uintptr` はポインタサイズのスカラー型であり、書き込みバリアのオーバーヘッドを避けるために使用されます。
    *   `[2]uintptr`、`[3]uintptr`、`[4]uintptr` は、より大きな要素サイズを持つスライスをシミュレートし、要素サイズが `append` のパフォーマンス（特にコピー操作）に与える影響を評価します。

このベンチマークスイートは、Goランタイムの `append` 関数の内部挙動、特にインプレース最適化と容量拡張のコストを、様々な条件下で詳細に分析するための強力なツールとなります。

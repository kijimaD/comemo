# [インデックス 2378] ファイルの概要

このコミットは、Goランタイムの386アーキテクチャ（特にDarwin、つまりmacOS上）における複数の修正を目的としています。主な焦点は、386環境でのテスト通過率を向上させることと、当時のGoツールチェインにおける386リンカ（`8l`）の既知のバグに対処することにありました。具体的には、`kqueue`システムコール関連の修正、スレッドローカルストレージ（TLS）の初期化、およびスレッド作成メカニズム（`bsdthread_create`、`bsdthread_register`）の調整が含まれています。

## 変更の背景

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われたものです。当時のGoは、異なるアーキテクチャ（386、amd64、armなど）やオペレーティングシステム（Linux、Darwinなど）への対応を確立している最中でした。特に386アーキテクチャは、メモリ管理やシステムコールインターフェースにおいてamd64とは異なる特性を持つため、ランタイムの移植には細心の注意が必要でした。

コミットメッセージにある「more 386 runtime fixes」は、386環境でのGoプログラムの安定性と正確性を向上させるための継続的な取り組みの一部であることを示しています。また、「can pass many tests; current stumbling block is an 8l bug.」という記述は、多くのテストが通過するようになったものの、当時の386向けGoリンカ（`8l`）に存在するバグが、さらなる進捗を妨げる主要な課題であったことを示唆しています。このコミットは、そのリンカのバグが解決されるまでの間、ランタイム側で可能な限りの修正を行い、386環境での動作を改善しようとする試みと解釈できます。

具体的には、Darwin（macOS）上での386アーキテクチャにおけるスレッド管理、システムコール（特に`kqueue`）、およびスレッドローカルストレージ（TLS）の取り扱いに関する問題が背景にあったと考えられます。これらの要素は、Goの並行処理モデルとガベージコレクションの正確な動作に不可欠であり、初期のランタイム開発において頻繁に調整が必要となる部分でした。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する一連のライブラリとメカニズムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当て（ガベージコレクションを含む）、チャネル通信、システムコールインターフェースなどが含まれます。ランタイムは、GoプログラムがOSとどのように対話するかを定義し、Goの並行処理モデルを可能にする基盤を提供します。

### 386アーキテクチャ
Intel 80386プロセッサに由来する32ビットのx86アーキテクチャを指します。現代の64ビットシステム（amd64）とは異なり、レジスタサイズ、アドレス空間、システムコール規約などが異なります。Goの初期開発では、32ビットシステムも重要なターゲットでした。

### Darwin (macOS) カーネル
AppleのmacOS（旧OS X）の基盤となるオペレーティングシステムカーネルです。MachマイクロカーネルとBSDサブシステムを組み合わせたハイブリッドカーネルであり、UNIX系のシステムコールインターフェースを提供します。

### kqueue
FreeBSD、macOS、NetBSDなどのBSD系OSで利用される、効率的なI/Oイベント通知メカニズムです。ファイルディスクリプタ（ソケット、ファイルなど）に対する読み書き可能イベント、タイマーイベント、シグナルイベントなど、様々な種類のイベントを監視し、アプリケーションに通知します。`select()`や`poll()`よりもスケーラブルで高性能なI/O多重化を実現します。

### システムコール (Syscall)
オペレーティングシステムが提供するサービスをプログラムが利用するためのインターフェースです。ファイル操作、ネットワーク通信、メモリ管理、プロセス・スレッド管理など、OSの機能にアクセスするために使用されます。Goランタイムは、OS固有のシステムコールを抽象化し、Goプログラムから利用できるようにします。

### スレッドローカルストレージ (TLS: Thread-Local Storage)
各スレッドがそれぞれ独立したデータを持つことができるメモリ領域です。グローバル変数とは異なり、TLSに格納されたデータは、そのスレッドからのみアクセス可能であり、他のスレッドからは見えません。Goランタイムでは、M（マシン、OSスレッド）やG（ゴルーチン）といったランタイム内部の重要な構造体へのポインタをTLSに格納し、高速なアクセスを実現することがあります。386アーキテクチャでは、FSまたはGSセグメントレジスタをTLSのベースアドレスとして利用することが一般的です。

### bsdthread_create / bsdthread_register
Darwinカーネルが提供する、ユーザーレベルスレッド（pthread）の作成と管理に関連するシステムコールです。
*   `bsdthread_create`: 新しいOSスレッドを作成するためのシステムコール。Goランタイムでは、新しいM（OSスレッド）を起動するために使用されます。
*   `bsdthread_register`: スレッドのライフサイクルイベント（スレッド開始時など）にフックするためのコールバック関数を登録するシステムコール。Goランタイムは、新しく作成されたOSスレッドがGoランタイムの初期化ルーチンを実行できるように、このメカニズムを利用します。

### 8l (Go Linker for 386)
Goツールチェインにおける386アーキテクチャ向けのリンカです。Goのコンパイラ（`8c`）、アセンブラ（`8a`）によって生成されたオブジェクトファイルを結合し、実行可能ファイルを生成します。Goの初期開発では、各アーキテクチャごとに専用のコンパイラ、アセンブラ、リンカが用意されていました（例: 6l/6a/6cはamd64向け、8l/8a/8cは386向け）。

## 技術的詳細

このコミットは、主にDarwin上の386アーキテクチャにおけるGoランタイムの低レベルな動作を改善しています。

1.  **ビルドスクリプトの修正 (`src/cmd/clean.bash`, `src/cmd/gobuild/Makefile`, `src/cmd/make.bash`)**:
    *   `clean.bash`と`make.bash`において、386アーキテクチャ向けのGoコンパイラ/アセンブラ/リンカである`8g`, `8l`, `8a`, `8c`が正しくクリーンアップおよびビルドプロセスに含まれるように修正されています。これは、386環境での開発・テストワークフローを円滑にするために不可欠です。
    *   `gobuild/Makefile`では、`O`変数の設定方法が変更され、`GOARCH`環境変数に基づいて適切なアーキテクチャ（arm=5, amd64=6, 386=8）のツールが選択されるようになりました。これにより、クロスコンパイルや異なるアーキテクチャでのビルドがより柔軟になります。

2.  **`kqueue`システムコール利用の改善 (`src/lib/net/fd_darwin.go`)**:
    *   `AddFD`および`DelFD`関数内で、`kmode`変数の型が`int16`から`int`に変更されています。これは、`syscall.Kevent_t`構造体の`Filter`フィールドが`int16`型であるにもかかわらず、`syscall.EVFILT_READ`などの定数が`int`型であることによる型ミスマッチを避けるためかもしれません。
    *   `syscall.SetKevent`という新しいヘルパー関数が導入され、`Kevent_t`構造体のフィールド設定が抽象化されました。これにより、`Ident`, `Filter`, `Flags`といったフィールドを直接設定する代わりに、より安全で簡潔な方法で`Kevent_t`を初期化できるようになりました。
    *   `AddFD`内のイベントチェックロジックも、`ev.Ident`と`ev.Filter`を`int`型にキャストして比較するように変更され、型の一貫性が保たれています。

3.  **システムコールヘルパー関数の追加 (`src/lib/syscall/syscall_darwin_386.go`, `src/lib/syscall/syscall_darwin_amd64.go`)**:
    *   `syscall_darwin_386.go`に`Getpagesize()`関数が追加され、386アーキテクチャでのページサイズ（4096バイト）を返すようになりました。これはメモリ管理やアライメントの計算に利用されます。
    *   `syscall_darwin_386.go`と`syscall_darwin_amd64.go`の両方に`SetKevent`関数が追加されました。この関数は、`Kevent_t`構造体の`Ident`、`Filter`、`Flags`フィールドを、それぞれ`uint32`、`int16`、`uint16`にキャストして設定する役割を担います。これにより、`kqueue`イベントの準備がより堅牢になります。

4.  **386 Darwinランタイムのスレッド管理修正 (`src/runtime/darwin/386/sys.s`)**:
    *   `bsdthread_create`アセンブリ関数が大幅に修正され、新しいOSスレッドを作成する際の引数渡しとフラグ設定が更新されました。特に`PTHREAD_START_CUSTOM`フラグ（`0x1000000`）が設定されており、これはスレッドの開始ルーチンをカスタム指定するためのものです。
    *   `bsdthread_start`アセンブリ関数が新しく実装されました。これは`bsdthread_create`によって作成されたスレッドが最初に実行するコードです。
        *   この関数は、スレッドローカルストレージ（TLS）のセットアップを行います。具体的には、`m->tls`（M構造体内のTLS配列）を指すようにLDT（Local Descriptor Table）エントリを設定し、FSセグメントレジスタを介してTLSにアクセスできるようにします。これは、386アーキテクチャでTLSを効率的に利用するための重要なステップです。
        *   TLSが確立された後、`g`（ゴルーチン）と`m`（OSスレッド）のポインタがTLSに格納されます。
        *   `m->procid`にスレッドポートIDが設定されます（デバッガ向け）。
        *   最後に、Goランタイムが指定したスレッド開始関数（`fn()`）を呼び出し、その後に`exit1()`を呼び出してスレッドを終了します。
    *   `bsdthread_register`アセンブリ関数も修正され、`bsdthread_start`をスレッド開始コールバックとして登録する際の引数渡しが調整されました。

5.  **ランタイム構造体の更新 (`src/runtime/runtime.h`)**:
    *   `M`構造体（OSスレッドを表すランタイム構造体）に`tls[8]`という`uint32`型の配列が追加されました。これは、386アーキテクチャでスレッドローカルストレージとして使用され、特にアセンブリコードからMやGのポインタにアクセスするために利用されます。`tls`フィールドには「must not move」というコメントが付加されており、ランタイムの安定性にとってその位置が重要であることを示しています。

6.  **`newosproc`の修正 (`src/runtime/darwin/thread.c`)**:
    *   `newosproc`関数（新しいOSスレッドを起動するGoランタイム関数）内で、`m->tls[0] = m->id;`という行が追加されました。これは、386のアセンブリコードがTLSを介してMのIDを見つけられるようにするための初期化ステップです。

7.  **テスト環境の修正 (`test/env.go`)**:
    *   `test/env.go`が、`GOARCH`が`386`または`arm`の場合もテストが実行されるように修正されました。これにより、386アーキテクチャでのテストカバレッジが向上します。

これらの変更は、GoランタイムがDarwin上の386アーキテクチャで正しく動作し、Goの並行処理モデルをサポートするために必要な低レベルの調整を反映しています。特にTLSのセットアップと`bsdthread_create`/`bsdthread_register`の利用は、GoのM-GスケジューラがOSスレッドとゴルーチンを効率的に管理するための基盤となります。

## コアとなるコードの解説

### `src/lib/net/fd_darwin.go` と `src/lib/syscall/syscall_darwin_386.go` / `syscall_darwin_amd64.go` の `SetKevent`

`kqueue`はDarwinにおける高性能なI/Oイベント通知メカニズムです。`Kevent_t`構造体は、監視するイベントの詳細を定義します。以前のコードでは、この構造体のフィールド（`Ident`, `Filter`, `Flags`）を直接設定していましたが、このコミットでは`syscall.SetKevent`というヘルパー関数を導入しました。

```go
// src/lib/syscall/syscall_darwin_386.go (および amd64版)
func SetKevent(k *Kevent_t, fd, mode, flags int) {
	k.Ident = uint32(fd);
	k.Filter = int16(mode);
	k.Flags = uint16(flags);
}

// src/lib/net/fd_darwin.go の変更箇所
// 以前:
// ev.Ident = uint64(fd);
// ev.Filter = kmode;
// ev.Flags = syscall.EV_ADD | syscall.EV_RECEIPT;
// if !repeat {
//    ev.Flags |= syscall.EV_ONESHOT
// }
//
// 変更後:
// flags := syscall.EV_ADD | syscall.EV_RECEIPT;
// if !repeat {
//    flags |= syscall.EV_ONESHOT
// }
// syscall.SetKevent(ev, fd, kmode, flags);
```

この変更により、`Kevent_t`のフィールド設定がカプセル化され、型変換のミスを防ぎ、コードの可読性と保守性が向上します。特に、`fd`（ファイルディスクリプタ）が`uint32`に、`mode`（イベントフィルター）が`int16`に、`flags`が`uint16`に明示的にキャストされることで、基盤となるC言語のシステムコールインターフェースとの整合性が確保されます。

### `src/runtime/darwin/386/sys.s` の `bsdthread_start` と TLS セットアップ

このアセンブリコードは、Goランタイムが新しいOSスレッド（M）を起動した際に、そのスレッドが最初に実行する重要な初期化ルーチンです。特に386アーキテクチャでは、スレッドローカルストレージ（TLS）のセットアップが複雑になります。

```assembly
// src/runtime/darwin/386/sys.s
TEXT bsdthread_start(SB),7,$0
    // set up ldt 7+id to point at m->tls.
    // m->tls is at m+40.  newosproc left
    // the m->id in tls[0].
    LEAL    40(DX), BP      // BP = &m->tls (DXはmへのポインタ)
    MOVL    0(BP), DI       // DI = m->tls[0] (m->idが格納されている)
    ADDL    $7, DI          // DI = LDTエントリ番号 (m0はLDT#7)
    // setldt(tls#, &tls, sizeof tls)
    PUSHAL                  // レジスタを保存
    PUSHL   $32             // sizeof tls (M構造体のtls[8]は32バイト)
    PUSHL   BP              // &tls
    PUSHL   DI              // tls #
    CALL    setldt(SB)      // setldtシステムコールを呼び出し
    POPL    AX              // スタックをクリーンアップ
    POPL    AX
    POPL    AX
    POPAL                   // レジスタを復元
    SHLL    $3, DI          // セグメントセレクタを計算 (LDTエントリ番号 * 8 + 7)
    ADDL    $7, DI
    MOVW    DI, FS          // FSセグメントレジスタに設定

    // Now segment is established.  Initialize m, g.
    MOVL    AX, 0(FS)       // AXはgへのポインタ。TLSのオフセット0にgを格納
    MOVL    DX, 4(FS)       // DXはmへのポインタ。TLSのオフセット4にmを格納
    MOVL    BX, 20(DX)      // m->procid = thread port (for debuggers)
    CALL    CX              // fn() (Goランタイムが指定したスレッド開始関数)
    CALL    exit1(SB)       // スレッド終了
    RET
```

このコードは、以下の重要な処理を実行します。
1.  **TLSベースアドレスの確立**: `setldt`システムコールを呼び出して、現在のOSスレッドのLDT（Local Descriptor Table）エントリを設定します。これにより、FSセグメントレジスタを介して`M`構造体内の`tls`配列にアクセスできるようになります。これは、386アーキテクチャでスレッドローカルなデータ（特に現在のMとGのポインタ）を効率的に取得するための標準的なメカニズムです。
2.  **MとGのポインタの格納**: FSレジスタを介してアクセスできるTLS領域に、現在のゴルーチン（`g`）とOSスレッド（`m`）のポインタを格納します。これにより、GoランタイムのCコードやアセンブリコードが、現在の実行コンテキスト（どのゴルーチンがどのOSスレッドで実行されているか）を迅速に参照できるようになります。
3.  **スレッド開始関数の実行**: `bsdthread_create`に渡されたGoランタイムの開始関数（`fn`）を呼び出します。これは、新しいOSスレッドがGoランタイムのスケジューラに参加し、ゴルーチンを実行するためのエントリポイントとなります。

このTLSのセットアップは、GoのM-Gスケジューラが正しく機能し、各OSスレッドが自身のコンテキストを維持するために不可欠です。

### `src/runtime/runtime.h` の `M` 構造体への `tls[8]` 追加

```c
// src/runtime/runtime.h
struct	M
{
    // ... 既存のフィールド ...
	G*\tlastg;\t\t// last running goroutine - to emulate fifo - must not move
	uint32\ttls[8];\t\t// thread-local storage (for 386 extern register) - must not move
	Gobuf\tsched;
    // ... 続くフィールド ...
};
```

`M`構造体はGoランタイムにおけるOSスレッドの抽象化です。この構造体に`tls[8]`という配列が追加されたことは、386アーキテクチャにおいて、OSスレッドごとに固有のデータを保持するための専用領域が必要とされたことを示しています。この配列は、前述の`bsdthread_start`アセンブリコードによってFSセグメントレジスタのベースアドレスとして設定され、現在のMやGのポインタなどの重要なランタイム情報を格納するために使用されます。`must not move`というコメントは、アセンブリコードがこのフィールドのオフセットに依存しているため、構造体内の位置を変更してはならないことを強調しています。

## 変更の背景

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われたものです。当時のGoは、異なるアーキテクチャ（386、amd64、armなど）やオペレーティングシステム（Linux、Darwinなど）への対応を確立している最中でした。特に386アーキテクチャは、メモリ管理やシステムコールインターフェースにおいてamd64とは異なる特性を持つため、ランタイムの移植には細心の注意が必要でした。

コミットメッセージにある「more 386 runtime fixes」は、386環境でのGoプログラムの安定性と正確性を向上させるための継続的な取り組みの一部であることを示しています。また、「can pass many tests; current stumbling block is an 8l bug.」という記述は、多くのテストが通過するようになったものの、当時の386向けGoリンカ（`8l`）に存在するバグが、さらなる進捗を妨げる主要な課題であったことを示唆しています。このコミットは、そのリンカのバグが解決されるまでの間、ランタイム側で可能な限りの修正を行い、386環境での動作を改善しようとする試みと解釈できます。

具体的には、Darwin（macOS）上での386アーキテクチャにおけるスレッド管理、システムコール（特に`kqueue`）、およびスレッドローカルストレージ（TLS）の取り扱いに関する問題が背景にあったと考えられます。これらの要素は、Goの並行処理モデルとガベージコレクションの正確な動作に不可欠であり、初期のランタイム開発において頻繁に調整が必要となる部分でした。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する一連のライブラリとメカニズムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当て（ガベージコレクションを含む）、チャネル通信、システムコールインターフェースなどが含まれます。ランタイムは、GoプログラムがOSとどのように対話するかを定義し、Goの並行処理モデルを可能にする基盤を提供します。

### 386アーキテクチャ
Intel 80386プロセッサに由来する32ビットのx86アーキテクチャを指します。現代の64ビットシステム（amd64）とは異なり、レジスタサイズ、アドレス空間、システムコール規約などが異なります。Goの初期開発では、32ビットシステムも重要なターゲットでした。

### Darwin (macOS) カーネル
AppleのmacOS（旧OS X）の基盤となるオペレーティングシステムカーネルです。MachマイクロカーネルとBSDサブシステムを組み合わせたハイブリッドカーネルであり、UNIX系のシステムコールインターフェースを提供します。

### kqueue
FreeBSD、macOS、NetBSDなどのBSD系OSで利用される、効率的なI/Oイベント通知メカニズムです。ファイルディスクリプタ（ソケット、ファイルなど）に対する読み書き可能イベント、タイマーイベント、シグナルイベントなど、様々な種類のイベントを監視し、アプリケーションに通知します。`select()`や`poll()`よりもスケーラブルで高性能なI/O多重化を実現します。

### システムコール (Syscall)
オペレーティングシステムが提供するサービスをプログラムが利用するためのインターフェースです。ファイル操作、ネットワーク通信、メモリ管理、プロセス・スレッド管理など、OSの機能にアクセスするために使用されます。Goランタイムは、OS固有のシステムコールを抽象化し、Goプログラムから利用できるようにします。

### スレッドローカルストレージ (TLS: Thread-Local Storage)
各スレッドがそれぞれ独立したデータを持つことができるメモリ領域です。グローバル変数とは異なり、TLSに格納されたデータは、そのスレッドからのみアクセス可能であり、他のスレッドからは見えません。Goランタイムでは、M（マシン、OSスレッド）やG（ゴルーチン）といったランタイム内部の重要な構造体へのポインタをTLSに格納し、高速なアクセスを実現することがあります。386アーキテクチャでは、FSまたはGSセグメントレジスタをTLSのベースアドレスとして利用することが一般的です。

### bsdthread_create / bsdthread_register
Darwinカーネルが提供する、ユーザーレベルスレッド（pthread）の作成と管理に関連するシステムコールです。
*   `bsdthread_create`: 新しいOSスレッドを作成するためのシステムコール。Goランタイムでは、新しいM（OSスレッド）を起動するために使用されます。
*   `bsdthread_register`: スレッドのライフサイクルイベント（スレッド開始時など）にフックするためのコールバック関数を登録するシステムコール。Goランタイムは、新しく作成されたOSスレッドがGoランタイムの初期化ルーチンを実行できるように、このメカニズムを利用します。

### 8l (Go Linker for 386)
Goツールチェインにおける386アーキテクチャ向けのリンカです。Goのコンパイラ（`8c`）、アセンブラ（`8a`）によって生成されたオブジェクトファイルを結合し、実行可能ファイルを生成します。Goの初期開発では、各アーキテクチャごとに専用のコンパイラ、アセンブラ、リンカが用意されていました（例: 6l/6a/6cはamd64向け、8l/8a/8cは386向け）。

## 技術的詳細

このコミットは、主にDarwin上の386アーキテクチャにおけるGoランタイムの低レベルな動作を改善しています。

1.  **ビルドスクリプトの修正 (`src/cmd/clean.bash`, `src/cmd/gobuild/Makefile`, `src/cmd/make.bash`)**:
    *   `clean.bash`と`make.bash`において、386アーキテクチャ向けのGoコンパイラ/アセンブラ/リンカである`8g`, `8l`, `8a`, `8c`が正しくクリーンアップおよびビルドプロセスに含まれるように修正されています。これは、386環境での開発・テストワークフローを円滑にするために不可欠です。
    *   `gobuild/Makefile`では、`O`変数の設定方法が変更され、`GOARCH`環境変数に基づいて適切なアーキテクチャ（arm=5, amd64=6, 386=8）のツールが選択されるようになりました。これにより、クロスコンパイルや異なるアーキテクチャでのビルドがより柔軟になります。

2.  **`kqueue`システムコール利用の改善 (`src/lib/net/fd_darwin.go`)**:
    *   `AddFD`および`DelFD`関数内で、`kmode`変数の型が`int16`から`int`に変更されています。これは、`syscall.Kevent_t`構造体の`Filter`フィールドが`int16`型であるにもかかわらず、`syscall.EVFILT_READ`などの定数が`int`型であることによる型ミスマッチを避けるためかもしれません。
    *   `syscall.SetKevent`という新しいヘルパー関数が導入され、`Kevent_t`構造体のフィールド設定が抽象化されました。これにより、`Ident`, `Filter`, `Flags`といったフィールドを直接設定する代わりに、より安全で簡潔な方法で`Kevent_t`を初期化できるようになりました。
    *   `AddFD`内のイベントチェックロジックも、`ev.Ident`と`ev.Filter`を`int`型にキャストして比較するように変更され、型の一貫性が保たれています。

3.  **システムコールヘルパー関数の追加 (`src/lib/syscall/syscall_darwin_386.go`, `src/lib/syscall/syscall_darwin_amd64.go`)**:
    *   `syscall_darwin_386.go`に`Getpagesize()`関数が追加され、386アーキテクチャでのページサイズ（4096バイト）を返すようになりました。これはメモリ管理やアライメントの計算に利用されます。
    *   `syscall_darwin_386.go`と`syscall_darwin_amd64.go`の両方に`SetKevent`関数が追加されました。この関数は、`Kevent_t`構造体の`Ident`、`Filter`、`Flags`フィールドを、それぞれ`uint32`、`int16`、`uint16`にキャストして設定する役割を担います。これにより、`kqueue`イベントの準備がより堅牢になります。

4.  **386 Darwinランタイムのスレッド管理修正 (`src/runtime/darwin/386/sys.s`)**:
    *   `bsdthread_create`アセンブリ関数が大幅に修正され、新しいOSスレッドを作成する際の引数渡しとフラグ設定が更新されました。特に`PTHREAD_START_CUSTOM`フラグ（`0x1000000`）が設定されており、これはスレッドの開始ルーチンをカスタム指定するためのものです。
    *   `bsdthread_start`アセンブリ関数が新しく実装されました。これは`bsdthread_create`によって作成されたスレッドが最初に実行するコードです。
        *   この関数は、スレッドローカルストレージ（TLS）のセットアップを行います。具体的には、`m->tls`（M構造体内のTLS配列）を指すようにLDT（Local Descriptor Table）エントリを設定し、FSセグメントレジスタを介してTLSにアクセスできるようにします。これは、386アーキテクチャでTLSを効率的に利用するための重要なステップです。
        *   TLSが確立された後、`g`（ゴルーチン）と`m`（OSスレッド）のポインタがTLSに格納されます。
        *   `m->procid`にスレッドポートIDが設定されます（デバッガ向け）。
        *   最後に、Goランタイムが指定したスレッド開始関数（`fn()`）を呼び出し、その後に`exit1()`を呼び出してスレッドを終了します。
    *   `bsdthread_register`アセンブリ関数も修正され、`bsdthread_start`をスレッド開始コールバックとして登録する際の引数渡しが調整されました。

5.  **ランタイム構造体の更新 (`src/runtime/runtime.h`)**:
    *   `M`構造体（OSスレッドを表すランタイム構造体）に`tls[8]`という`uint32`型の配列が追加されました。これは、386アーキテクチャでスレッドローカルストレージとして使用され、特にアセンブリコードからMやGのポインタにアクセスするために利用されます。`tls`フィールドには「must not move」というコメントが付加されており、ランタイムの安定性にとってその位置が重要であることを示しています。

6.  **`newosproc`の修正 (`src/runtime/darwin/thread.c`)**:
    *   `newosproc`関数（新しいOSスレッドを起動するGoランタイム関数）内で、`m->tls[0] = m->id;`という行が追加されました。これは、386のアセンブリコードがTLSを介してMのIDを見つけられるようにするための初期化ステップです。

7.  **テスト環境の修正 (`test/env.go`)**:
    *   `test/env.go`が、`GOARCH`が`386`または`arm`の場合もテストが実行されるように修正されました。これにより、386アーキテクチャでのテストカバレッジが向上します。

これらの変更は、GoランタイムがDarwin上の386アーキテクチャで正しく動作し、Goの並行処理モデルをサポートするために必要な低レベルの調整を反映しています。特にTLSのセットアップと`bsdthread_create`/`bsdthread_register`の利用は、GoのM-GスケジューラがOSスレッドとゴルーチンを効率的に管理するための基盤となります。

## コアとなるコードの解説

### `src/lib/net/fd_darwin.go` と `src/lib/syscall/syscall_darwin_386.go` / `syscall_darwin_amd64.go` の `SetKevent`

`kqueue`はDarwinにおける高性能なI/Oイベント通知メカニズムです。`Kevent_t`構造体は、監視するイベントの詳細を定義します。以前のコードでは、この構造体のフィールド（`Ident`, `Filter`, `Flags`）を直接設定していましたが、このコミットでは`syscall.SetKevent`というヘルパー関数を導入しました。

```go
// src/lib/syscall/syscall_darwin_386.go (および amd64版)
func SetKevent(k *Kevent_t, fd, mode, flags int) {
	k.Ident = uint32(fd);
	k.Filter = int16(mode);
	k.Flags = uint16(flags);
}

// src/lib/net/fd_darwin.go の変更箇所
// 以前:
// ev.Ident = uint64(fd);
// ev.Filter = kmode;
// ev.Flags = syscall.EV_ADD | syscall.EV_RECEIPT;
// if !repeat {
//    ev.Flags |= syscall.EV_ONESHOT
// }
//
// 変更後:
// flags := syscall.EV_ADD | syscall.EV_RECEIPT;
// if !repeat {
//    flags |= syscall.EV_ONESHOT
// }
// syscall.SetKevent(ev, fd, kmode, flags);
```

この変更により、`Kevent_t`のフィールド設定がカプセル化され、型変換のミスを防ぎ、コードの可読性と保守性が向上します。特に、`fd`（ファイルディスクリプタ）が`uint32`に、`mode`（イベントフィルター）が`int16`に、`flags`が`uint16`に明示的にキャストされることで、基盤となるC言語のシステムコールインターフェースとの整合性が確保されます。

### `src/runtime/darwin/386/sys.s` の `bsdthread_start` と TLS セットアップ

このアセンブリコードは、Goランタイムが新しいOSスレッド（M）を起動した際に、そのスレッドが最初に実行する重要な初期化ルーチンです。特に386アーキテクチャでは、スレッドローカルストレージ（TLS）のセットアップが複雑になります。

```assembly
// src/runtime/darwin/386/sys.s
TEXT bsdthread_start(SB),7,$0
    // set up ldt 7+id to point at m->tls.
    // m->tls is at m+40.  newosproc left
    // the m->id in tls[0].
    LEAL    40(DX), BP      // BP = &m->tls (DXはmへのポインタ)
    MOVL    0(BP), DI       // DI = m->tls[0] (m->idが格納されている)
    ADDL    $7, DI          // DI = LDTエントリ番号 (m0はLDT#7)
    // setldt(tls#, &tls, sizeof tls)
    PUSHAL                  // レジスタを保存
    PUSHL   $32             // sizeof tls (M構造体のtls[8]は32バイト)
    PUSHL   BP              // &tls
    PUSHL   DI              // tls #
    CALL    setldt(SB)      // setldtシステムコールを呼び出し
    POPL    AX              // スタックをクリーンアップ
    POPL    AX
    POPL    AX
    POPAL                   // レジスタを復元
    SHLL    $3, DI          // セグメントセレクタを計算 (LDTエントリ番号 * 8 + 7)
    ADDL    $7, DI
    MOVW    DI, FS          // FSセグメントレジスタに設定

    // Now segment is established.  Initialize m, g.
    MOVL    AX, 0(FS)       // AXはgへのポインタ。TLSのオフセット0にgを格納
    MOVL    DX, 4(FS)       // DXはmへのポインタ。TLSのオフセット4にmを格納
    MOVL    BX, 20(DX)      // m->procid = thread port (for debuggers)
    CALL    CX              // fn() (Goランタイムが指定したスレッド開始関数)
    CALL    exit1(SB)       // スレッド終了
    RET
```

このコードは、以下の重要な処理を実行します。
1.  **TLSベースアドレスの確立**: `setldt`システムコールを呼び出して、現在のOSスレッドのLDT（Local Descriptor Table）エントリを設定します。これにより、FSセグメントレジスタを介して`M`構造体内の`tls`配列にアクセスできるようになります。これは、386アーキテクチャでスレッドローカルなデータ（特に現在のMとGのポインタ）を効率的に取得するための標準的なメカニズムです。
2.  **MとGのポインタの格納**: FSレジスタを介してアクセスできるTLS領域に、現在のゴルーチン（`g`）とOSスレッド（`m`）のポインタを格納します。これにより、GoランタイムのCコードやアセンブリコードが、現在の実行コンテキスト（どのゴルーチンがどのOSスレッドで実行されているか）を迅速に参照できるようになります。
3.  **スレッド開始関数の実行**: `bsdthread_create`に渡されたGoランタイムの開始関数（`fn`）を呼び出します。これは、新しいOSスレッドがGoランタイムのスケジューラに参加し、ゴルーチンを実行するためのエントリポイントとなります。

このTLSのセットアップは、GoのM-Gスケジューラが正しく機能し、各OSスレッドが自身のコンテキストを維持するために不可欠です。

### `src/runtime/runtime.h` の `M` 構造体への `tls[8]` 追加

```c
// src/runtime/runtime.h
struct	M
{
    // ... 既存のフィールド ...
	G*\tlastg;\t\t// last running goroutine - to emulate fifo - must not move
	uint32\ttls[8];\t\t// thread-local storage (for 386 extern register) - must not move
	Gobuf\tsched;
    // ... 続くフィールド ...
};
```

`M`構造体はGoランタイムにおけるOSスレッドの抽象化です。この構造体に`tls[8]`という配列が追加されたことは、386アーキテクチャにおいて、OSスレッドごとに固有のデータを保持するための専用領域が必要とされたことを示しています。この配列は、前述の`bsdthread_start`アセンブリコードによってFSセグメントレジスタのベースアドレスとして設定され、現在のMやGのポインタなどの重要なランタイム情報を格納するために使用されます。`must not move`というコメントは、アセンブリコードがこのフィールドのオフセットに依存しているため、構造体内の位置を変更してはならないことを強調しています。

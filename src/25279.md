# [インデックス 25279] ファイルの概要

このコミットは、GoランタイムにおけるPPC64xアーキテクチャ向けのアセンブリコードにおいて、スタックフレームのセットアップを抑制するための新しい`NOFRAME`フラグを導入するものです。これにより、これまで`-8`という特殊なフレームサイズ指定によって暗黙的に行われていたスタックフレーム抑制のメカニズムが、より明示的で理解しやすいフラグに置き換えられました。

## 元コミット内容

`cmd/internal/obj, runtime: ppc64xでのスタックフレーム設定を抑制するNOFRAMEフラグを追加`

`-8`というフレームサイズがスタックフレームの暗黙的な設定を抑制するという紛らわしい仕組みを、明確な明示的フラグに置き換える。

関数プロローグを設定するコードはまだ少し紛らわしいが、以前よりは改善された。

## 変更の背景

Go言語のランタイムは、パフォーマンスが非常に重要となる部分や、特定のアーキテクチャ固有の処理のために、Goアセンブリ言語（Plan 9アセンブリの派生）を使用しています。これらのアセンブリ関数では、通常のGo関数とは異なり、コンパイラが自動的に生成するスタックフレームのセットアップを制御する必要があります。

PPC64xアーキテクチャにおいて、これまでスタックフレームのセットアップを抑制するためには、関数の`TEXT`ディレクティブでフレームサイズを`$-8`と指定するという、非常に特殊で直感的ではない慣習が用いられていました。この`-8`という値は、単に「スタックフレームを生成しない」という意図をアセンブラに伝えるための「マジックナンバー」のようなものであり、コードの可読性や保守性を著しく低下させていました。

このコミットの背景には、このような暗黙的で紛らわしいメカニズムを排除し、より明示的で理解しやすい方法でスタックフレームの抑制を制御したいという意図があります。新しい`NOFRAME`フラグの導入により、開発者はコードの意図をより明確に表現できるようになり、将来的なメンテナンスやデバッグが容易になることが期待されます。コミットメッセージにも「関数プロローグを設定するコードはまだ少し紛らわしいが、以前よりは改善された」とあるように、この変更はコードベースの健全性を高める一歩と位置づけられています。

## 前提知識の解説

### Goのアセンブリ（Plan 9アセンブリ）

Go言語は、そのランタイムや一部の標準ライブラリにおいて、Goアセンブリ言語（Plan 9アセンブリの構文をベースにしたもの）を使用しています。これは、C言語のインラインアセンブリとは異なり、独立したアセンブリファイルとして記述されます。Goアセンブリは、主に以下の目的で利用されます。

*   **パフォーマンス最適化**: 特定のクリティカルな処理（例: スケジューラ、GCヘルパー、アトミック操作）で最大限のパフォーマンスを引き出すため。
*   **アーキテクチャ固有の機能**: 特定のCPU命令（例: SIMD命令）やレジスタ、システムコールへの直接アクセスが必要な場合。
*   **ランタイムのブートストラップ**: Goランタイムの初期化など、Go言語自体がまだ完全に動作していない段階での処理。

Goアセンブリ関数は、`TEXT`ディレクティブで定義され、その後にシンボル名、フラグ、フレームサイズ、引数サイズが続きます。

### スタックフレーム

スタックフレームは、関数が呼び出されたときにスタック上に確保されるメモリ領域です。各関数呼び出しごとに新しいスタックフレームが作成され、関数が終了すると解放されます。スタックフレームには通常、以下の情報が含まれます。

*   **ローカル変数**: 関数内で宣言された変数。
*   **引数**: 関数に渡された値。
*   **リターンアドレス**: 関数が終了した後に実行を再開するアドレス。
*   **保存されたレジスタ**: 呼び出し元が使用していたレジスタの値を、呼び出された関数が変更する前に保存しておく領域。

スタックフレームのセットアップは、関数のプロローグ（開始部分）で行われ、解放はエピローグ（終了部分）で行われます。これは通常、コンパイラによって自動的に生成されますが、アセンブリ言語で記述された関数では手動で制御する必要があります。

### PPC64xアーキテクチャ

PPC64xは、IBM PowerPCアーキテクチャの64ビット版を指します。Go言語は、このアーキテクチャもサポートしており、ランタイムの一部はPPC64x向けのアセンブリで記述されています。PPC64xの関数呼び出し規約（ABI）では、特定のレジスタがスタックポインタ（R1）、リンクレジスタ（LR、リターンアドレスを保持）、引数、戻り値などに使用されます。スタックフレームの管理も、これらのレジスタと密接に関連しています。特に、PPC64xでは、呼び出し元が呼び出された関数のためにスタック上に特定の領域（セーブエリア）を確保することが一般的です。

### `TEXT`ディレクティブとフレームサイズ

Goアセンブリでは、`TEXT`ディレクティブを使って関数を定義します。その構文は以下のようになります。

```asm
TEXT symbol(SB), flags, framesize-argsize
```

*   `symbol(SB)`: 関数のシンボル名。`SB`はStatic Baseを意味し、グローバルシンボルであることを示します。
*   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`）。
*   `framesize`: この関数が自身のローカル変数や保存レジスタのために必要とするスタックフレームのサイズ。
*   `argsize`: この関数が受け取る引数の合計サイズ。

これまでのPPC64xでは、`framesize`に`$-8`を指定することで、アセンブラがスタックフレームのセットアップコードを生成しないようにする、という特殊な挙動がありました。これは、特定のランタイム関数など、スタックフレームが不要な、あるいは手動で管理される関数で使用されていました。

### `NOSPLIT`フラグ

`NOSPLIT`フラグは、Goアセンブリ関数において、スタックの成長チェック（スタックオーバーフローの検出と新しいスタックへの切り替え）を行わないことを示すフラグです。これは、スタックの成長チェック自体がスタックを消費するため、非常に小さなスタックフレームしか持たない関数や、スタックの成長チェックが不適切なコンテキスト（例: スケジューラの一部）で使用されます。`NOSPLIT`関数は、通常、非常に短い処理を行うか、他の関数を呼び出さない（リーフ関数である）ことが期待されます。

## 技術的詳細

このコミットの核心は、PPC64xアーキテクチャにおけるGoアセンブリ関数のスタックフレーム管理を、より明確で安全な方法に改善することです。

1.  **`NOFRAME`フラグの導入**:
    *   `src/cmd/internal/obj/textflag.go`と`src/runtime/textflag.h`に新しい定数`NOFRAME`が追加されました。このフラグは、関数がスタックフレームを割り当てないことを明示的に示します。
    *   このフラグは「フレームサイズが0の関数でのみ有効」という制約があります。これは、スタックフレームを割り当てない関数は、ローカル変数や保存レジスタのための領域を必要としない、という論理的な整合性を保つためです。

2.  **`-8`フレームサイズとの互換性処理**:
    *   `src/cmd/internal/obj/ppc64/obj9.go`内の`preprocess`関数が変更され、古い慣習である`textstksiz == -8`が検出された場合、これを新しい`NOFRAME`フラグに変換するようにしました。これにより、既存の`-8`を使用しているアセンブリコードは、自動的に`NOFRAME`として扱われるようになり、後方互換性が保たれます。
    *   変換後、`textstksiz`は`0`に設定されます。これは、`NOFRAME`関数がフレームサイズを持たないことを意味します。

3.  **スタックフレームサイズの検証と調整**:
    *   `obj9.go`では、フレームサイズが8の倍数であることの検証が追加されました。これはPPC64xのABI要件に合致するためです。
    *   `NOFRAME`フラグが設定されている関数に対して、フレームサイズが0であることを強制する検証が追加されました。もし`NOFRAME`が設定されているにもかかわらずフレームサイズが0でない場合、コンパイル時にエラー（`ctxt.Diag`）が報告されます。
    *   関数プロローグにおける`autosize`（自動的に計算されるスタックフレームサイズ）の計算ロジックが変更されました。
        *   以前は、`autosize`は`textstksiz + 8`（LR保存領域）として計算され、リーフ関数で`autosize <= 8`の場合に`0`に設定される、という複雑なロジックでした。
        *   新しいロジックでは、まず`autosize`を`textstksiz`として初期化します。
        *   `NOFRAME`が設定されていない関数（つまりスタックフレームが必要な関数）の場合にのみ、LR（リンクレジスタ）を保存するための8バイトが`autosize`に追加されます。これにより、スタックフレームの有無とLR保存の有無がより明確に分離されます。
        *   リーフ関数（`LEAF`フラグ）で、ローカル変数もなく（`autosize == 0`）、かつ`NOFRAME`が設定されていない場合、その関数は自動的に`NOFRAME`としてマークされるようになりました。これは、真のリーフ関数であればスタックフレームは不要であるという最適化です。

4.  **アセンブリコードの更新**:
    *   `src/runtime/`以下の多数のアセンブリファイル（例: `asm_ppc64x.s`, `atomic_ppc64x.s`, `sys_linux_ppc64x.s`など）において、`TEXT`ディレクティブのフレームサイズ指定が`$-8-X`から`$0-X`に変更され、同時に`NOFRAME`フラグが追加されました（例: `TEXT runtime·gosave(SB), NOSPLIT, $-8-8` が `TEXT runtime·gosave(SB), NOSPLIT|NOFRAME, $0-8` に）。
    *   これにより、これらの関数は明示的にスタックフレームを生成しないことを宣言するようになりました。

この変更により、Goコンパイラ（アセンブラ）は、`NOFRAME`フラグに基づいて、PPC64xアーキテクチャにおける関数プロローグでのスタックフレームのセットアップを抑制するようになります。これは、特にGoランタイムの低レベルな部分で、スタックフレームのオーバーヘッドを避けたい場合や、スタックフレームの管理を完全に手動で行いたい場合に重要です。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/internal/obj/textflag.go`**:
    *   `NOFRAME`という新しい定数が追加され、その値は`512`です。これは、アセンブラが関数プロローグを生成する際に使用するフラグの一つとなります。

    ```go
    // Do not insert instructions to allocate a stack frame for this function.
    // Only valid on functions that declare a frame size of 0.
    // TODO(mwhudson): only implemented for ppc64x at present.
    NOFRAME = 512
    ```

2.  **`src/runtime/textflag.h`**:
    *   Goアセンブリファイルから参照されるCヘッダファイルにも、`NOFRAME`マクロが追加されました。

    ```c
    // Do not insert instructions to allocate a stack frame for this function.
    // Only valid on functions that declare a frame size of 0.
    // TODO(mwhudson): only implemented for ppc64x at present.
    #define NOFRAME 512
    ```

3.  **`src/cmd/internal/obj/ppc64/obj9.go`**:
    *   アセンブラのバックエンド処理を行うファイルで、特に`preprocess`関数が変更されました。
    *   古い`-8`フレームサイズを`NOFRAME`フラグに変換するロジックが追加されました。
    *   `NOFRAME`フラグが設定された関数のフレームサイズが0であることを検証するロジックが追加されました。
    *   スタックフレームの自動サイズ計算（`autosize`）ロジックが修正され、`NOFRAME`フラグの有無に応じてLR保存領域の追加を制御するようになりました。
    *   リーフ関数（`LEAF`）でフレームサイズが0の場合に、自動的に`NOFRAME`フラグを設定する最適化が追加されました。

    ```go
    // ...
    	textstksiz := p.To.Offset
    	if textstksiz == -8 {
    		// Compatibility hack.
    		p.From3.Offset |= obj.NOFRAME
    		textstksiz = 0
    	}
    	if textstksiz%8 != 0 {
    		ctxt.Diag("frame size %d not a multiple of 8", textstksiz)
    	}
    	if p.From3.Offset&obj.NOFRAME != 0 {
    		if textstksiz != 0 {
    			ctxt.Diag("NOFRAME functions must have a frame size of 0, not %d", textstksiz)
    		}
    	}
    // ...
    		case obj.ATEXT:
    			// ...
    			autosize = int32(textstksiz)

    			if p.Mark&LEAF != 0 && autosize == 0 && p.From3.Offset&obj.NOFRAME == 0 {
    				// A leaf function with no locals has no frame.
    				p.From3.Offset |= obj.NOFRAME
    			}

    			if p.From3.Offset&obj.NOFRAME == 0 {
    				// If there is a stack frame at all, it includes
    				// space to save the LR.
    				autosize += 8
    			}

    			p.To.Offset = int64(autosize)
    // ...
    ```

4.  **`src/runtime/*.s`および関連アセンブリファイル**:
    *   `misc/cgo/test/issue9400/asm_ppc64x.s`
    *   `src/runtime/asm_ppc64x.s`
    *   `src/runtime/atomic_ppc64x.s`
    *   `src/runtime/cgo/asm_ppc64x.s`
    *   `src/runtime/duff_ppc64x.s`
    *   `src/runtime/memclr_ppc64x.s`
    *   `src/runtime/memmove_ppc64x.s`
    *   `src/runtime/mkduff.go` (アセンブリコードを生成するGoファイル)
    *   `src/runtime/sys_linux_ppc64x.s`
    *   `src/runtime/tls_ppc64x.s`
    これらのファイルでは、`TEXT`ディレクティブのフレームサイズ指定が、古い`$-8-X`形式から、新しい`NOSPLIT|NOFRAME,$0-X`形式に一括して変更されています。

    例:
    `-TEXT runtime·breakpoint(SB),NOSPLIT,$-8-0`
    `+TEXT runtime·breakpoint(SB),NOSPLIT|NOFRAME,$0-0`

## コアとなるコードの解説

### `src/cmd/internal/obj/textflag.go` と `src/runtime/textflag.h`

これらのファイルは、GoアセンブラとGoランタイムのアセンブリコードが共有するフラグ定義を提供します。`NOFRAME = 512`の追加は、アセンブラが関数プロローグを生成する際に、このフラグを認識し、スタックフレームのセットアップを抑制するための新しいメカニズムを導入したことを意味します。`TODO`コメントは、この機能がPPC64xに限定されていることを示唆しており、将来的に他のアーキテクチャにも拡張される可能性を示しています。

### `src/cmd/internal/obj/ppc64/obj9.go` の `preprocess` 関数

この関数は、PPC64xアーキテクチャ向けのアセンブリコードを処理するアセンブラの重要な部分です。

1.  **`-8`フレームサイズの互換性処理**:
    ```go
    	textstksiz := p.To.Offset
    	if textstksiz == -8 {
    		// Compatibility hack.
    		p.From3.Offset |= obj.NOFRAME
    		textstksiz = 0
    	}
    ```
    ここで、もしアセンブリコードが古い慣習に従って`$-8`というフレームサイズを指定していた場合（`p.To.Offset`が`-8`）、アセンブラはその関数のフラグ（`p.From3.Offset`）に新しい`obj.NOFRAME`フラグをOR演算で追加します。そして、`textstksiz`を`0`にリセットします。これにより、古いコードは新しい`NOFRAME`メカニズムに透過的に移行されます。

2.  **フレームサイズの検証**:
    ```go
    	if textstksiz%8 != 0 {
    		ctxt.Diag("frame size %d not a multiple of 8", textstksiz)
    	}
    	if p.From3.Offset&obj.NOFRAME != 0 {
    		if textstksiz != 0 {
    			ctxt.Diag("NOFRAME functions must have a frame size of 0, not %d", textstksiz)
    		}
    	}
    ```
    最初の`if`文は、PPC64xのABI要件に従い、スタックフレームサイズが8バイトの倍数であることを確認します。
    2番目の`if`文は、`NOFRAME`フラグが設定されている関数に対して、そのフレームサイズが厳密に`0`であることを強制します。これは、`NOFRAME`の意図（スタックフレームを割り当てない）と矛盾するフレームサイズが指定された場合に、コンパイル時エラーを発生させることで、コードの整合性を保ちます。

3.  **`autosize`の計算ロジックの変更**:
    ```go
    			autosize = int32(textstksiz)

    			if p.Mark&LEAF != 0 && autosize == 0 && p.From3.Offset&obj.NOFRAME == 0 {
    				// A leaf function with no locals has no frame.
    				p.From3.Offset |= obj.NOFRAME
    			}

    			if p.From3.Offset&obj.NOFRAME == 0 {
    				// If there is a stack frame at all, it includes
    				// space to save the LR.
    				autosize += 8
    			}

    			p.To.Offset = int64(autosize)
    ```
    *   `autosize = int32(textstksiz)`: まず、`autosize`はアセンブリコードで指定されたフレームサイズ（または`-8`から変換された`0`）で初期化されます。
    *   リーフ関数（`LEAF`フラグが設定され、ローカル変数もなく、かつ`NOFRAME`がまだ設定されていない関数）の場合、自動的に`NOFRAME`フラグが設定されます。これは、真のリーフ関数はスタックフレームを必要としないため、最適化としてフレーム生成を抑制するためです。
    *   `if p.From3.Offset&obj.NOFRAME == 0`: ここが重要な変更点です。`NOFRAME`フラグが設定されていない関数（つまり、スタックフレームが必要な関数）の場合にのみ、リンクレジスタ（LR）を保存するための8バイトが`autosize`に追加されます。これにより、スタックフレームの有無とLR保存の有無が明確に分離され、`NOFRAME`関数はLR保存領域も持たないことになります。
    *   最終的に計算された`autosize`が関数の`p.To.Offset`に設定され、これがアセンブラが生成するプロローグコードの基盤となります。

### `src/runtime/*.s` ファイル群

これらのアセンブリファイルでは、`TEXT`ディレクティブのフラグが`NOSPLIT,$-8-X`から`NOSPLIT|NOFRAME,$0-X`に変更されています。

例: `TEXT runtime·gosave(SB), NOSPLIT|NOFRAME, $0-8`

これは、これらの関数が明示的にスタックフレームを生成しないことをアセンブラに指示しています。`$0`はフレームサイズが0であることを示し、`NOFRAME`フラグと整合しています。`NOSPLIT`は引き続きスタック成長チェックを抑制します。これらの関数は、Goランタイムの非常に低レベルな部分であり、スタックフレームの管理を厳密に制御する必要があるため、この変更はコードの意図を明確にし、将来的なバグのリスクを低減します。

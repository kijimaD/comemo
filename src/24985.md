# [インデックス 24985] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるスイープ処理の一部である `mSpan_Sweep` 関数のロジックを簡素化するものです。特に、`sweepgen` の更新処理を統合し、大規模なスパン（メモリブロック）の解放タイミングの変更によって不要になった重複コードを削除しています。

## コミット

```
runtime: simplify mSpan_Sweep

This is a cleanup following cc8f544, which was a minimal change to fix
issue #11617. This consolidates the two places in mSpan_Sweep that
update sweepgen. Previously this was necessary because sweepgen must
be updated before freeing the span, but we freed large spans early.
Now we free large spans later, so there's no need to duplicate the
sweepgen update. This also means large spans can take advantage of the
sweepgen sanity checking performed for other spans.

Change-Id: I23b79dbd9ec81d08575cd307cdc0fa6b20831768
Reviewed-on: https://go-review.googlesource.com/12451
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

このコミットは、以前のコミット `cc8f544` および関連する `issue #11617` の修正に続くクリーンアップ作業です。`cc8f544` は、Goランタイムのガベージコレクションにおける大規模なスパン（メモリブロック）の解放タイミングを変更したと考えられます。

以前のGoランタイムでは、`mSpan_Sweep` 関数内で `sweepgen` の更新が2箇所で行われていました。これは、`sweepgen` がスパンを解放する前に更新される必要があった一方で、大規模なスパンは早期に解放されていたためです。この早期解放のロジックにより、`sweepgen` の更新が重複して存在する必要がありました。

`cc8f544` の変更により、大規模なスパンの解放が遅延されるようになったため、`sweepgen` の更新を重複させる必要がなくなりました。このコミットは、その結果として生じたコードの重複を解消し、`sweepgen` の更新ロジックを単一の場所に統合することを目的としています。これにより、コードの可読性と保守性が向上し、大規模なスパンも他のスパンと同様に `sweepgen` の健全性チェックの恩恵を受けられるようになります。

## 前提知識の解説

Goランタイムのガベージコレクション（GC）は、メモリ管理の重要な部分であり、主に以下のフェーズで動作します。

1.  **STW (Stop-the-World) - GC開始**: 全てのゴルーチンを一時的に停止し、ルート参照（グローバル変数、スタックなど）をマークします。
2.  **並行マーク**: ユーザーゴルーチンが実行され続ける間に、ヒープをスキャンして到達可能なオブジェクトをマークします。
3.  **STW - マーク終了 / スイープ開始**: 再び短い停止期間を設け、マーク処理を完了します。
4.  **並行スイープ**: マークされなかった（到達不能な）オブジェクトが占有していたメモリブロックを解放します。このフェーズもユーザーゴルーチンと並行して実行されます。スイープ作業の一部は、後続のメモリ割り当て時に遅延して実行されることもあります。

このコミットで関連するのは、特に「並行スイープ」フェーズです。

*   **スパン (`mSpan`)**: Goランタイムは、メモリを「スパン」と呼ばれるブロック単位で管理します。各スパンは、特定のサイズクラスのオブジェクトを保持する連続したメモリ領域です。
*   **スイープ (`mSpan_Sweep`)**: スイープ処理は、マークフェーズで到達可能とマークされなかったオブジェクトからメモリを回収する役割を担います。これには、スパン内のマークされていないスロットの特定、これらのオブジェクトの解放、そして場合によっては、スパン内の全てのオブジェクトがマークされていない場合にスパン全体を解放する作業が含まれます。
*   **スイープ世代 (`sweepgen`)**: `sweepgen` は、Goランタイム内で、スイープ処理中のスパンの状態を追跡するために使用されるメカニズムです。これはガベージコレクションサイクルの世代カウンターとして機能します。`mheap_.sweepgen` と `s.sweepgen` (ここで `s` はスパンを表す) のフィールドは、特定のスパンが現在のGCサイクルでスイープされたかどうかを判断するために使用されます。スパンの `sweepgen` は、そのスパン内の全てのブロックがスイープされた後にのみ更新されます。これは、並行な解放操作やファイナライザの管理にとって非常に重要です。

要するに、`sweepgen` はGoランタイムがガベージコレクタのスイープフェーズによってどのメモリスパンが処理されたかを効率的に管理し、メモリが正しく回収され、将来の割り当てのために準備されることを保証するのに役立ちます。

## 技術的詳細

このコミットの核心は、`mSpan_Sweep` 関数内の `sweepgen` 更新ロジックの統合です。

以前のコードでは、`mSpan_Sweep` の冒頭付近、特に大規模なスパンが早期に解放される可能性のあるパスで、`atomicstore(&s.sweepgen, sweepgen)` という行が存在していました。この行は、スパンがヒープに返される前に `sweepgen` を設定することが重要であるため、配置されていました。

しかし、`cc8f544` の変更により、大規模なスパンの解放タイミングが変更され、この早期の `sweepgen` 更新が不要になりました。その結果、コードの後半部分にある、他のスパンに対する `sweepgen` 更新ロジックと重複が生じていました。

このコミットでは、以下の変更が行われています。

1.  **早期 `sweepgen` 更新の削除**: `src/runtime/mgcsweep.go` の235行目付近にあった `atomicstore(&s.sweepgen, sweepgen)` の行が削除されました。これにより、大規模なスパンの早期解放パスにおける `sweepgen` の重複更新がなくなります。
2.  **条件式の変更**: 264行目付近の条件式が `if !freeToHeap && nfree == 0 {` から `if freeToHeap || nfree == 0 {` に変更されました。
    *   元の条件式 `!freeToHeap && nfree == 0` は、「ヒープに解放されず、かつ空きブロックがない場合」に `sweepgen` を更新するという意味でした。
    *   新しい条件式 `freeToHeap || nfree == 0` は、「ヒープに解放される場合、または空きブロックがない場合」に `sweepgen` を更新するという意味になります。

この変更により、`sweepgen` の更新は、スパンがヒープに返される場合（`freeToHeap` が `true` の場合）か、スパン内に空きブロックがない場合（`nfree == 0` の場合）に実行されるようになります。これは、スパンが割り当て可能になる前に `sweepgen` が更新されるという要件を満たしつつ、大規模なスパンの解放タイミングの変更と整合性が取れるようにロジックを簡素化しています。

結果として、`sweepgen` の更新ロジックが単一の、より一般的なパスに統合され、コードの重複が解消されました。これにより、大規模なスパンも他のスパンと同様に `sweepgen` の健全性チェック（`s.state != mSpanInUse || s.sweepgen != sweepgen-1`）の恩恵を受けられるようになります。

## コアとなるコードの解説

変更前のコードでは、`mSpan_Sweep` 関数内で `sweepgen` の更新が論理的に2つの異なる場所で行われていました。

1.  **大規模スパンの早期解放パス**: スパンが `freeToHeap = true` とマークされ、ヒープに返される準備ができた場合、`atomicstore(&s.sweepgen, sweepgen)` が実行されていました。これは、スパンが再利用可能になる前に `sweepgen` が最新の状態であることを保証するためでした。
2.  **一般的なスパンのパス**: 関数後半の `if !freeToHeap && nfree == 0 { ... }` ブロック内で、`sweepgen` の更新と健全性チェックが行われていました。このブロックは、スパンがヒープに返されない（`!freeToHeap`）が、空きブロックがない（`nfree == 0`）場合に実行され、スパンが割り当て可能になる前に `sweepgen` を更新していました。

このコミットは、`cc8f544` によって大規模スパンの解放タイミングが変更されたことを受けて、上記1の早期解放パスでの `sweepgen` 更新を削除しました。これにより、`sweepgen` の更新は、関数後半の単一のロジックに集約されることになります。

新しい条件式 `if freeToHeap || nfree == 0 {` は、この統合されたロジックを表現しています。
*   `freeToHeap` が `true` の場合、スパンはヒープに返されるため、`sweepgen` を更新する必要があります。
*   `nfree == 0` の場合、スパン内に空きブロックがないため、このスパンは完全にスイープされたと見なされ、`sweepgen` を更新する必要があります。

この変更により、`sweepgen` の更新ロジックが簡素化され、コードの重複が解消されました。また、大規模スパンも、他のスパンと同様に、`sweepgen` の更新時に行われる健全性チェック（`s.state != mSpanInUse || s.sweepgen != sweepgen-1`）の恩恵を受けられるようになり、GCの堅牢性が向上します。

# [インデックス 25930] ファイルの概要

このコミットは、Go言語の `net/mail` パッケージにおけるメールアドレスの解析ロジックのバグ修正に関するものです。具体的には、RFC 2047で定義されているエンコードされたワード（`=?charset?encoding?text?=`) が、引用符で囲まれた文字列（quoted strings）内に出現した場合に、誤ってデコードを試みてしまう問題を修正しています。RFC 2047の仕様では、これらのエンコードされたワードは引用符で囲まれていないプレーンなテキストとしてのみ出現が許されており、引用符で囲まれた文字列内の内容はそのまま保持されるべきです。

## 変更の背景

この変更は、Goの `net/mail` パッケージがメールアドレスの表示名（display name）を解析する際に、RFC 2047の仕様に準拠していない挙動を示していたバグ（Issue #11294）を修正するために行われました。

RFC 2047は、非ASCII文字をメールヘッダー（特に表示名）で使用するためのエンコーディングメカニズムを定義しています。例えば、日本語の名前をメールアドレスの表示名に含める場合、`=?UTF-8?B?...encoded_text...?=` のような形式でエンコードされます。このエンコードされた文字列は「encoded-word」と呼ばれます。

問題は、`net/mail` パッケージのパーサーが、メールアドレスの表示名が引用符で囲まれている場合（例: `"=?UTF-8?B?...encoded_text...?=" <user@example.com>`）でも、その引用符内の文字列をRFC 2047のencoded-wordとしてデコードしようとしていた点にありました。しかし、RFC 2047の仕様（特にセクション 5.2）では、encoded-wordは「`atom` または `word` の一部としてのみ出現できる」とされており、`quoted-string` の中に出現することは許されていません。`quoted-string` の内容は、特別なエスケープシーケンスを除いて、リテラルとして扱われるべきです。

この誤ったデコード処理により、引用符で囲まれた表示名にたまたまRFC 2047のパターンに似た文字列が含まれていた場合、意図しないデコードが行われ、結果として不正な表示名が生成される可能性がありました。このコミットは、この仕様違反を修正し、RFC 2047のencoded-wordは引用符で囲まれていない場合にのみデコードされるようにすることで、より堅牢で正確なメールアドレス解析を実現しています。

## 前提知識の解説

### 1. RFC 5322 (Internet Message Format)

RFC 5322は、インターネットメールメッセージの標準フォーマットを定義しています。メールアドレスの構造、ヘッダーフィールドの構文などが規定されており、`net/mail` パッケージはこのRFCに準拠してメールメッセージを解析します。メールアドレスは通常、`"Display Name" <local-part@domain>` の形式を取ります。

### 2. RFC 2047 (MIME (Multipurpose Internet Mail Extensions) Part Three: Message Header Extensions for Non-ASCII Text)

RFC 2047は、RFC 5322で定義されているメールヘッダーフィールド（特に `Subject`, `From`, `To` などの表示名部分）で非ASCII文字を使用するためのメカニズムを提供します。これは「Encoded-Word」構文を用いて実現されます。

**Encoded-Wordの形式:**
`=?charset?encoding?encoded-text?=`

*   `charset`: 使用される文字セット（例: `UTF-8`, `ISO-2022-JP`）。
*   `encoding`: エンコーディング方式（`Q` for Quoted-Printable, `B` for Base64）。
*   `encoded-text`: 指定された文字セットとエンコーディングでエンコードされた元のテキスト。

**例:**
`=?UTF-8?B?44GZ44Gk44Go?= <user@example.com>` (「テスト」という日本語がBase64でエンコードされている)

**RFC 2047の重要な制約:**
RFC 2047のセクション 5.2「Use of Encoded-Words in Headers」には、Encoded-Wordがどこに出現できるかについての厳格なルールがあります。特に重要なのは、Encoded-Wordは `atom` または `word` の一部としてのみ出現でき、`quoted-string` の中に出現してはならないという点です。`quoted-string` の内容は、特別なエスケープシーケンス（バックスラッシュでエスケープされた文字）を除いて、リテラルな文字データとして扱われます。

### 3. `net/mail` パッケージ

Go言語の標準ライブラリ `net/mail` は、RFC 5322および関連するRFC（RFC 2047など）に準拠したメールメッセージの解析と生成を提供します。このパッケージは、メールヘッダーの解析、アドレスの抽出、エンコードされたテキストのデコードなどを担当します。

### 4. `addrParser` 構造体と `consumePhrase` メソッド

`net/mail` パッケージ内部では、メールアドレスの解析に `addrParser` という構造体が使用されます。この構造体には、メールアドレスの各部分（表示名、ローカルパート、ドメインなど）を消費（解析）するためのメソッド群が含まれています。`consumePhrase` メソッドは、特に表示名のような「フレーズ」部分を解析する際に使用され、RFC 2047のEncoded-Wordのデコードもこの過程で行われます。

## 技術的詳細

このコミットの核心は、`net/mail` パッケージ内の `addrParser` 構造体の `consumePhrase` メソッドにおける条件分岐の変更です。

`consumePhrase` メソッドは、メールアドレスの表示名部分を解析する際に、引用符で囲まれていない「アトム」（`atom`）や引用符で囲まれた文字列（`quoted-string`）を処理します。元のコードでは、`quoted-string` を消費した後でも、その結果得られた `word` に対して無条件に `p.decodeRFC2047Word(word)` を呼び出していました。

RFC 2047の仕様では、Encoded-Wordは `quoted-string` の中に出現してはならないため、`quoted-string` から得られた文字列はRFC 2047のデコード対象とすべきではありません。引用符で囲まれた文字列は、その内容がリテラルであると見なされるべきだからです。

このコミットでは、このロジックを修正し、`p.decodeRFC2047Word(word)` の呼び出しが、`quoted-string` ではなく、`atom` や `word` として解析された場合にのみ行われるように変更されています。これにより、RFC 2047の仕様に厳密に準拠し、引用符で囲まれた文字列内の `?=` パターンを誤ってデコードしようとする問題を回避します。

具体的には、`consumePhrase` メソッド内で `p.consumeAtom(true, true)` が成功した場合にのみ `p.decodeRFC2047Word(word)` が呼び出されるように、条件分岐が変更されています。`p.consumeAtom` は、引用符で囲まれていない部分を解析する役割を担っています。

また、この変更を検証するために、`src/net/mail/message_test.go` に新しいテストケースが追加されています。これらのテストケースは、表示名が引用符で囲まれており、その中にRFC 2047のパターンに似た文字列が含まれている場合に、それがデコードされずにリテラルとして扱われることを確認します。例えば、`"=?Q?x?="` や `"?=hello"` のような文字列が、デコードされずにそのまま保持されることをテストしています。

## コアとなるコードの解説

### `src/net/mail/message.go` の変更点

元のコードでは、`consumePhrase` メソッド内で `word, err = p.consumeAtom(true, true)` の呼び出しが完了した後、その結果が `quoted-string` から来たものであっても、無条件に `if err == nil { word, err = p.decodeRFC2047Word(word) }` のブロックに入っていました。

変更後のコードでは、`p.consumeAtom(true, true)` の呼び出しが成功した場合にのみ、その内部で `p.decodeRFC2047Word(word)` が呼び出されるように、`if err == nil` の条件が `p.consumeAtom` の呼び出しの直後に移動しています。

具体的には、以下の部分が変更されました。

**変更前:**
```go
			word, err = p.consumeAtom(true, true)
		} // ここで `if p.peek == '"'` のブロックが閉じている
		// `quoted-string` から来た `word` もこの `if` に入ってしまう
		if err == nil {
			word, err = p.decodeRFC2047Word(word)
		}
```

**変更後:**
```go
			word, err = p.consumeAtom(true, true)
			// `p.consumeAtom` が成功した場合のみデコードを試みる
			if err == nil {
				word, err = p.decodeRFC2047Word(word)
			}
		} // ここで `if p.peek == '"'` のブロックが閉じている
```

この変更により、`p.consumeAtom` が解析した `word`（これは引用符で囲まれていない部分）に対してのみ `decodeRFC2047Word` が適用されるようになります。もし `p.peek == '"'` のブロック（引用符で囲まれた文字列を処理する部分）が実行された場合、その結果得られた `word` は `p.decodeRFC2047Word` の対象外となり、RFC 2047の仕様に準拠した動作となります。

### `src/net/mail/message_test.go` の変更点

テストファイルでは、`TestAddressFormatting` 関数が `TestAddressString` にリネームされ、さらに重要な新しいテストケースが追加されています。

追加されたテストケースは以下の通りです。
*   `&Address{Name: "=??Q?x?=", Address: "hello@world.com"}, `"`=??Q?x?=\" <hello@world.com>`",`
*   `&Address{Name: "=?hello", Address: "hello@world.com"}, `"`=?hello\" <hello@world.com>`",`
*   `&Address{Name: "world?=", Address: "hello@world.com"}, `"`world?=\" <hello@world.com>`",`

これらのテストケースは、表示名が引用符で囲まれており、その中に `?=` や `=?` といったRFC 2047のEncoded-Wordのパターンに似た文字列が含まれている状況をシミュレートしています。期待される出力は、これらの文字列がデコードされずに、引用符で囲まれたリテラル文字列としてそのまま保持されることです。

さらに、各テストケースの後に「ラウンドトリップ」チェックが追加されています。これは、`Address.String()` メソッドでフォーマットされた文字列を `ParseAddress` で再度解析し、元の `Address` 構造体と一致するかどうかを確認するものです。これにより、フォーマットと解析の両方のロジックが正しく機能していることを保証しています。

これらの変更により、`net/mail` パッケージはRFC 2047の仕様をより正確に実装し、メールアドレスの表示名解析における堅牢性と信頼性が向上しました。

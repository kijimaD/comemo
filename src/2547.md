# [インデックス 2547] ファイルの概要

このコミットは、Go言語のコンパイラ (`gc`)、アーカイバ (`ar`)、およびリンカ (`ld`) における、同一パッケージ内の複数ファイル間での前方宣言の扱いに関する重要な変更を導入しています。具体的には、構造体 (`struct`) の前方宣言と、メソッドの実装が異なるファイルに存在することを許可するようになります。ただし、メソッドの宣言自体はレシーバ型と同じファイル内で行われる必要があります。

## 変更の背景

Go言語は、設計当初からパッケージ内のソースコードを複数のファイルに分割することをサポートしています。しかし、このコミット以前は、構造体やインターフェースの定義、およびそれらのメソッドの実装に関して、複数ファイルにまたがる前方宣言の扱いが厳格でした。特に、あるファイルで型が宣言され、別のファイルでその型のメソッドが実装されるようなケースでは、コンパイラが型の完全な情報を把握できず、エラーとなる可能性がありました。

この制限は、大規模なパッケージや、コード生成によって型定義とメソッド実装が異なるファイルに配置されるようなシナリオにおいて、開発の柔軟性を損なう要因となっていました。このコミットは、同一パッケージ内であれば、構造体の前方宣言やメソッドの実装を異なるファイルで行えるようにすることで、この制約を緩和し、コードの組織化と柔軟性を向上させることを目的としています。ただし、メソッドの宣言（シグネチャ）自体は、そのレシーバ型が定義されているファイルと同じファイル内になければならないという重要な制約が残されています。これは、型の完全性を保証し、コンパイラがメソッドセットを正しく構築できるようにするためと考えられます。

## 前提知識の解説

### 前方宣言 (Forward Declaration)

前方宣言とは、プログラム中で識別子（変数、関数、型など）が使用される前に、その存在と型をコンパイラに伝える仕組みです。これにより、コンパイラは識別子の完全な定義が後で提供されることを期待し、一時的にその識別子を使用するコードを処理できます。C/C++などの言語では、ヘッダファイルに関数プロトタイプや構造体の宣言を記述することで前方宣言を実現します。Go言語では、パッケージ内のファイルはすべて同じコンパイル単位と見なされるため、通常は前方宣言を明示的に記述する必要はありませんが、コンパイラ内部では型の解決順序が重要になります。

### Go言語のパッケージとコンパイル

Go言語では、同じパッケージに属するすべてのソースファイルは、単一の論理的な単位としてコンパイルされます。これは、C/C++のように個々のファイルを独立してコンパイルし、後でリンクするモデルとは異なります。Goコンパイラは、パッケージ内のすべてのファイルを一度に読み込み、シンボル解決や型チェックを行います。このため、あるファイルで定義された型や関数は、同じパッケージ内の他のファイルから直接参照できます。しかし、型の完全な定義がコンパイラにとって不明な場合、循環参照や未定義エラーが発生する可能性があります。

### `gc` (Go Compiler)

`gc` はGo言語の公式コンパイラです。Goソースコードを中間表現に変換し、最終的に実行可能なバイナリを生成します。型チェック、シンボル解決、最適化など、コンパイルプロセスの主要な部分を担います。

### `ar` (Go Archiver)

`ar` は、Go言語のパッケージアーカイブファイル（`.a` ファイル）を操作するためのツールです。Goのコンパイル済みパッケージは、通常、`.a` ファイルとして保存され、他のパッケージからインポートされる際に使用されます。このアーカイブファイルには、パッケージのシンボル情報やコンパイル済みコードが含まれます。

### `ld` (Go Linker)

`ld` はGo言語のリンカです。コンパイルされたオブジェクトファイルやパッケージアーカイブファイルを結合し、最終的な実行可能ファイルや共有ライブラリを生成します。シンボル解決、アドレス割り当て、再配置などを行います。

### `TFORW`, `TFORWSTRUCT`, `TFORWINTER`

これらはGoコンパイラ内部で使用される型を表す定数です。
- `TFORW`: 一般的な前方宣言された型を示します。
- `TFORWSTRUCT`: 前方宣言された構造体型を示します。
- `TFORWINTER`: 前方宣言されたインターフェース型を示します。
これらの型は、コンパイルの初期段階で型が参照されたものの、その完全な定義がまだ処理されていない状態を表すために使用されます。

## 技術的詳細

このコミットの主要な変更点は、Goコンパイラが同一パッケージ内の複数ファイルにまたがる型定義とメソッド実装をどのように扱うかという点にあります。

1.  **構造体の前方宣言の許可**:
    *   以前は、構造体が使用される前にその完全な定義が必要でした。この変更により、あるファイルで `type MyStruct struct` のような宣言が行われ、その詳細なフィールド定義が別のファイルで行われることが可能になります。
    *   これは、コンパイラが `TFORWSTRUCT` という内部型を使用して、一時的に構造体の存在を記録し、後で完全な定義が提供されるのを待つことで実現されます。

2.  **メソッドの実装の柔軟性**:
    *   メソッドの宣言（シグネチャ）はレシーバ型と同じファイルに存在する必要がありますが、そのメソッドの実装（関数本体）は同じパッケージ内の別のファイルに記述できるようになります。
    *   これにより、例えば、型定義ファイルが非常に大きくなるのを避けたり、特定の機能に関連するメソッドを別のファイルにまとめたりする柔軟性が生まれます。

3.  **`ar` および `ld` の変更**:
    *   `ar` と `ld` は、パッケージのメタデータ（エクスポート情報）を処理する際に、前方宣言された型を正しく扱う必要があります。
    *   特に、`Import` 構造体から `export` フィールドが削除され、パッケージデータのパースロジック (`parsepkgdata`) からエクスポート/パッケージスコープのフラグを読み取る部分が削除されています。これは、前方宣言の導入により、型の「エクスポート状態」がより動的に解決されるようになったため、静的な `export` フラグが不要になったか、あるいはその管理方法が変更されたことを示唆しています。
    *   `forwardfix` 関数が導入されました。この関数は、`"struct"` と `"struct ..."` のような前方宣言と完全な定義の間の不一致を解決するために使用されます。これにより、コンパイラやリンカが複数のファイルから同じ型の情報を読み込んだ際に、前方宣言を完全な定義で上書きできるようになります。

4.  **`gc` の変更**:
    *   `src/cmd/gc/dcl.c` の `addmethod` 関数では、メソッドが非ローカル型（つまり、現在のファイルで定義されていない型）に対して定義される場合、そのメソッドは既に前方宣言されている必要があるというチェックが追加されました。これは、「すべてのメソッドはレシーバ型と同じファイルで宣言されなければならない」というルールを強制するためです。
    *   `src/cmd/gc/export.c` では、`dumpexporttype` 関数が `TFORWSTRUCT` と `TFORWINTER` 型をエクスポートする際に、それぞれ `"type %#T struct\\n"` と `"type %#T interface\\n"` という形式で出力するように変更されました。これにより、前方宣言された型もパッケージのエクスポート情報に含まれるようになります。
    *   `importtype` 関数では、`TFORWSTRUCT` や `TFORWINTER` 型の再宣言を許可するロジックが追加されました。これは、前方宣言された型が後で完全な定義で上書きされることを可能にするためです。

5.  **`go.y` の変更**:
    *   `src/cmd/gc/go.y` はGo言語の文法定義ファイルです。このファイルには、`hidden_pkg_importsym LSTRUCT` と `hidden_pkg_importsym LINTERFACE` という新しいルールが追加され、それぞれ `TFORWSTRUCT` と `TFORWINTER` 型をインポートする際に使用されるようになりました。これは、パーサーが前方宣言された構造体やインターフェースを正しく認識し、内部表現に変換できるようにするための変更です。

これらの変更により、Goコンパイラは、同一パッケージ内の複数ファイルにまたがる型定義とメソッド実装をより柔軟に処理できるようになり、開発者はコードの構造化においてより多くの選択肢を持つことになります。

### `src/cmd/ar/ar.c` および `src/cmd/ld/go.c`

### `src/cmd/gc/go.y`

*   `hidden_pkg_importsym LSTRUCT` と `hidden_pkg_importsym LINTERFACE` という新しい文法ルールが追加され、それぞれ `TFORWSTRUCT` と `TFORWINTER` 型をインポートする際に使用されるようになりました。

## コアとなるコードの解説

### `forwardfix` 関数 (ar.c, ld.c)

```c
char*
forwardfix(char *a, char *b)
{
	char *t;

	if(strlen(a) > strlen(b)) {
		t = a;
		a = b;
		b = t;
	}
	if(strcmp(a, "struct") == 0 && strncmp(b, "struct ", 7) == 0)
		return b;
	if(strcmp(a, "interface") == 0 && strncmp(b, "interface ", 10) == 0)
		return b;
	return nil;
}
```
この関数は、2つの文字列 `a` と `b` を比較し、一方が前方宣言（例: `"struct"`）で、もう一方がその完全な定義（例: `"struct { ... }"`）である場合に、完全な定義の方を返します。これにより、パッケージのメタデータを処理する際に、前方宣言と完全な定義が混在していても、最終的に完全な定義が採用されるようになります。

### `loadpkgdata` 内の競合解決ロジック (ar.c, ld.c)

```c
// ...
	while(parsepkgdata(&p, ep, &prefix, &name, &def) > 0) {
		x = ilookup(name);
		if(x->prefix == nil) {
			x->prefix = prefix;
			x->def = def;
			x->file = file;
		} else if(strcmp(x->prefix, prefix) != 0) {
			// ... conflicting definitions ...
		} else if(strcmp(x->def, def) == 0) {
			// fine
		} else if((ndef = forwardfix(x->def, def)) != nil) {
			x->def = ndef; // 前方宣言を完全な定義で更新
		} else {
			// ... conflicting definitions ...
		}
	}
// ...
```
`loadpkgdata` 関数は、パッケージアーカイブからシンボル情報を読み込みます。ここで、同じ名前のシンボルが複数回見つかった場合、`forwardfix` 関数を使って、既存の定義 (`x->def`) が前方宣言であり、新しい定義 (`def`) が完全な定義であるかをチェックします。もしそうであれば、`x->def` を新しい完全な定義で更新し、前方宣言を解決します。これにより、複数ファイルにまたがる型定義が正しく統合されます。

### `addmethod` 関数内のメソッド定義チェック (dcl.c)

```c
// ...
	if(local && !pa->local) {
		// defining method on non-local type.
		// method must have been forward declared
		// elsewhere, i.e. where the type was.
		yyerror("cannot define new methods on non-local type %T", pa);
		return;
	}
// ...
```
このコードスニペットは、`addmethod` 関数内で、メソッドが非ローカル型 (`!pa->local`) に対して定義されようとしている場合に、重要な制約を強制します。`local` は現在のファイルでメソッドが定義されていることを示します。もし型 `pa` が現在のファイルで定義されていない（非ローカル）にもかかわらず、新しいメソッドを定義しようとするとエラーになります。これは、メソッドの宣言（シグネチャ）が、そのレシーバ型が定義されているファイルと同じファイル内になければならないというルールを厳密に適用するためのものです。つまり、別のファイルで定義された型に対して、そのファイルで宣言されていない新しいメソッドを定義することはできません。

### `importtype` 関数内の前方宣言の扱い (export.c)

```c
// ...
	if(n != N && n->op == OTYPE) {
		if(cvttype(t, n->type))
			return;
		if(t->etype == TFORWSTRUCT && n->type->etype == TSTRUCT)
			return; // TFORWSTRUCTがTSTRUCTで上書きされるケース
		if(t->etype == TFORWINTER && n->type->etype == TINTER)
			return; // TFORWINTERがTINTERで上書きされるケース
		if(n->type->etype != TFORW && n->type->etype != TFORWSTRUCT && n->type->etype != TFORWINTER) {
			yyerror("redeclare import type %S from %lT to %lT", s, n->type, t);
			n = s->def = typenod(typ(0));
		}
	}
// ...
	switch(n->type->etype) {
	case TFORWINTER:
	case TFORWSTRUCT:
		// allow re-export in case it gets defined
		s->export = 0;
		s->imported = 0;
		break;
	default:
		checkwidth(n->type);
	}
// ...
```
`importtype` 関数は、パッケージから型をインポートする際に呼び出されます。この変更により、インポートされる型 `t` が `TFORWSTRUCT` であり、既存の型 `n->type` が `TSTRUCT` である場合（または `TFORWINTER` と `TINTER` の場合）、これは前方宣言が完全な定義で解決されたケースとして扱われ、エラーにはなりません。
また、`TFORWINTER` や `TFORWSTRUCT` のような前方宣言された型の場合、`s->export = 0; s->imported = 0;` と設定されます。これは、前方宣言された型はまだ完全な定義ではないため、すぐにエクスポート対象とはせず、後で完全な定義が提供された場合に再エクスポートされる可能性があることを示唆しています。

前方宣言とは、プログラム中で識別子（変数、関数、型など）が使用される前に、その存在と型をコンパイラに伝える仕組みです。これにより、コンパイラは識別子の完全な定義が後で提供されることを期待し、一時的にその識別子を使用するコードを処理できます。C/C++などの言語では、ヘッダファイルに関数プロトタイプや構造体の宣言を記述することで前方宣言を実現します。Go言語では、パッケージ内のファイルはすべて同じコンパイル単位と見なされるため、通常は前方宣言を明示的に記述する必要はありませんが、コンパイラ内部では型の解決順序が重要になります。

### Go言語のパッケージとコンパイル

Go言語では、同じパッケージに属するすべてのソースファイルは、単一の論理的な単位としてコンパイルされます。これは、C/C++のように個々のファイルを独立してコンパイルし、後でリンクするモデルとは異なります。Goコンパイラは、パッケージ内のすべてのファイルを一度に読み込み、シンボル解決や型チェックを行います。このため、あるファイルで定義された型や関数は、同じパッケージ内の他のファイルから直接参照できます。しかし、型の完全な定義がコンパイラにとって不明な場合、循環参照や未定義エラーが発生する可能性があります。

### `gc` (Go Compiler)

`gc` はGo言語の公式コンパイラです。Goソースコードを中間表現に変換し、最終的に実行可能なバイナリを生成します。型チェック、シンボル解決、最適化など、コンパイルプロセスの主要な部分を担います。

### `ar` (Go Archiver)

`ar` は、Go言語のパッケージアーカイブファイル（`.a` ファイル）を操作するためのツールです。Goのコンパイル済みパッケージは、通常、`.a` ファイルとして保存され、他のパッケージからインポートされる際に使用されます。このアーカイブファイルには、パッケージのシンボル情報やコンパイル済みコードが含まれます。

### `ld` (Go Linker)

`ld` はGo言語のリンカです。コンパイルされたオブジェクトファイルやパッケージアーカイブファイルを結合し、最終的な実行可能ファイルや共有ライブラリを生成します。シンボル解決、アドレス割り当て、再配置などを行います。

### `TFORW`, `TFORWSTRUCT`, `TFORWINTER`

これらはGoコンパイラ内部で使用される型を表す定数です。
- `TFORW`: 一般的な前方宣言された型を示します。
- `TFORWSTRUCT`: 前方宣言された構造体型を示します。
- `TFORWINTER`: 前方宣言されたインターフェース型を示します。
これらの型は、コンパイルの初期段階で型が参照されたものの、その完全な定義がまだ処理されていない状態を表すために使用されます。

## 技術的詳細

このコミットの主要な変更点は、Goコンパイラが同一パッケージ内の複数ファイルにまたがる型定義とメソッド実装をどのように扱うかという点にあります。

1.  **構造体の前方宣言の許可**:
    *   以前は、構造体が使用される前にその完全な定義が必要でした。この変更により、あるファイルで `type MyStruct struct` のような宣言が行われ、その詳細なフィールド定義が別のファイルで行われることが可能になります。
    *   これは、コンパイラが `TFORWSTRUCT` という内部型を使用して、一時的に構造体の存在を記録し、後で完全な定義が提供されるのを待つことで実現されます。

2.  **メソッドの実装の柔軟性**:
    *   メソッドの宣言（シグネチャ）はレシーバ型と同じファイルに存在する必要がありますが、そのメソッドの実装（関数本体）は同じパッケージ内の別のファイルに記述できるようになります。
    *   これにより、例えば、型定義ファイルが非常に大きくなるのを避けたり、特定の機能に関連するメソッドを別のファイルにまとめたりする柔軟性が生まれます。

3.  **`ar` および `ld` の変更**:
    *   `ar` と `ld` は、パッケージのメタデータ（エクスポート情報）を処理する際に、前方宣言された型を正しく扱う必要があります。
    *   特に、`Import` 構造体から `export` フィールドが削除され、パッケージデータのパースロジック (`parsepkgdata`) からエクスポート/パッケージスコープのフラグを読み取る部分が削除されています。これは、前方宣言の導入により、型の「エクスポート状態」がより動的に解決されるようになったため、静的な `export` フラグが不要になったか、あるいはその管理方法が変更されたことを示唆しています。
    *   `forwardfix` 関数が導入されました。この関数は、`"struct"` と `"struct ..."` のような前方宣言と完全な定義の間の不一致を解決するために使用されます。これにより、コンパイラやリンカが複数のファイルから同じ型の情報を読み込んだ際に、前方宣言を完全な定義で上書きできるようになります。

4.  **`gc` の変更**:
    *   `src/cmd/gc/dcl.c` の `addmethod` 関数では、メソッドが非ローカル型（つまり、現在のファイルで定義されていない型）に対して定義される場合、そのメソッドは既に前方宣言されている必要があるというチェックが追加されました。これは、「すべてのメソッドはレシーバ型と同じファイルで宣言されなければならない」というルールを強制するためです。
    *   `src/cmd/gc/export.c` では、`dumpexporttype` 関数が `TFORWSTRUCT` と `TFORWINTER` 型をエクスポートする際に、それぞれ `"type %#T struct\\n"` と `"type %#T interface\\n"` という形式で出力するように変更されました。これにより、前方宣言された型もパッケージのエクスポート情報に含まれるようになります。
    *   `importtype` 関数では、`TFORWSTRUCT` や `TFORWINTER` 型の再宣言を許可するロジックが追加されました。これは、前方宣言された型が後で完全な定義で上書きされることを可能にするためです。

5.  **`go.y` の変更**:
    *   `src/cmd/gc/go.y` はGo言語の文法定義ファイルです。このファイルには、`hidden_pkg_importsym LSTRUCT` と `hidden_pkg_importsym LINTERFACE` という新しいルールが追加され、それぞれ `TFORWSTRUCT` と `TFORWINTER` 型をインポートする際に使用されるようになりました。これは、パーサーが前方宣言された構造体やインターフェースを正しく認識し、内部表現に変換できるようにするための変更です。

これらの変更により、Goコンパイラは、同一パッケージ内の複数ファイルにまたがる型定義とメソッド実装をより柔軟に処理できるようになり、開発者はコードの構造化においてより多くの選択肢を持つことになります。

## コアとなるコードの変更箇所

### `src/cmd/ar/ar.c` および `src/cmd/ld/go.c`

*   `Import` 構造体から `export` フィールドが削除されました。
*   `parsepkgdata` 関数のシグネチャが変更され、`exportp` 引数が削除されました。
*   `loadpkgdata` 関数内で、`export` フラグに関するロジックが削除されました。
*   `forwardfix` 関数が追加されました。この関数は、前方宣言 (`"struct"`, `"interface"`) と完全な定義 (`"struct ..."` , `"interface ..."`) の間の不一致を解決し、完全な定義を優先します。
*   `loadpkgdata` 内の競合定義チェックロジックが更新され、`forwardfix` を利用して前方宣言と完全な定義の解決を試みるようになりました。

### `src/cmd/gc/dcl.c`

*   `addmethod` 関数内で、非ローカル型に対するメソッド定義に関するチェックが追加されました。具体的には、非ローカル型に新しいメソッドを定義しようとするとエラーになります。これは、メソッドの宣言がレシーバ型と同じファイルになければならないというルールを強制するためです。

### `src/cmd/gc/export.c`

*   `dumpexporttype` 関数で、`TFORWSTRUCT` と `TFORWINTER` 型がエクスポートされる際に、それぞれ `"type %#T struct\\n"` と `"type %#T interface\\n"` という形式で出力されるようになりました。
*   `importtype` 関数で、`TFORWSTRUCT` や `TFORWINTER` 型の再宣言が許可されるようになりました。これにより、前方宣言された型が後で完全な定義で上書きされることが可能になります。

### `src/cmd/gc/go.y`

*   `hidden_pkg_importsym LSTRUCT` と `hidden_pkg_importsym LINTERFACE` という新しい文法ルールが追加され、それぞれ `TFORWSTRUCT` と `TFORWINTER` 型をインポートする際に使用されるようになりました。

## コアとなるコードの解説

### `forwardfix` 関数 (ar.c, ld.c)

```c
char*
forwardfix(char *a, char *b)
{
	char *t;

	if(strlen(a) > strlen(b)) {
		t = a;
		a = b;
		b = t;
	}
	if(strcmp(a, "struct") == 0 && strncmp(b, "struct ", 7) == 0)
		return b;
	if(strcmp(a, "interface") == 0 && strncmp(b, "interface ", 10) == 0)
		return b;
	return nil;
}
```
この関数は、2つの文字列 `a` と `b` を比較し、一方が前方宣言（例: `"struct"`）で、もう一方がその完全な定義（例: `"struct { ... }"`）である場合に、完全な定義の方を返します。これにより、パッケージのメタデータを処理する際に、前方宣言と完全な定義が混在していても、最終的に完全な定義が採用されるようになります。

### `loadpkgdata` 内の競合解決ロジック (ar.c, ld.c)

```c
// ...
	while(parsepkgdata(&p, ep, &prefix, &name, &def) > 0) {
		x = ilookup(name);
		if(x->prefix == nil) {
			x->prefix = prefix;
			x->def = def;
			x->file = file;
		} else if(strcmp(x->prefix, prefix) != 0) {
			// ... conflicting definitions ...
		} else if(strcmp(x->def, def) == 0) {
			// fine
		} else if((ndef = forwardfix(x->def, def)) != nil) {
			x->def = ndef; // 前方宣言を完全な定義で更新
		} else {
			// ... conflicting definitions ...
		}
	}
// ...
```
`loadpkgdata` 関数は、パッケージアーカイブからシンボル情報を読み込みます。ここで、同じ名前のシンボルが複数回見つかった場合、`forwardfix` 関数を使って、既存の定義 (`x->def`) が前方宣言であり、新しい定義 (`def`) が完全な定義であるかをチェックします。もしそうであれば、`x->def` を新しい完全な定義で更新し、前方宣言を解決します。これにより、複数ファイルにまたがる型定義が正しく統合されます。

### `addmethod` 関数内のメソッド定義チェック (dcl.c)

```c
// ...
	if(local && !pa->local) {
		// defining method on non-local type.
		// method must have been forward declared
		// elsewhere, i.e. where the type was.
		yyerror("cannot define new methods on non-local type %T", pa);
		return;
	}
// ...
```
このコードスニペットは、`addmethod` 関数内で、メソッドが非ローカル型 (`!pa->local`) に対して定義されようとしている場合に、重要な制約を強制します。`local` は現在のファイルでメソッドが定義されていることを示します。もし型 `pa` が現在のファイルで定義されていない（非ローカル）にもかかわらず、新しいメソッドを定義しようとするとエラーになります。これは、メソッドの宣言（シグネチャ）が、そのレシーバ型が定義されているファイルと同じファイル内になければならないというルールを厳密に適用するためのものです。つまり、別のファイルで定義された型に対して、そのファイルで宣言されていない新しいメソッドを定義することはできません。

### `importtype` 関数内の前方宣言の扱い (export.c)

```c
// ...
	if(n != N && n->op == OTYPE) {
		if(cvttype(t, n->type))
			return;
		if(t->etype == TFORWSTRUCT && n->type->etype == TSTRUCT)
			return; // TFORWSTRUCTがTSTRUCTで上書きされるケース
		if(t->etype == TFORWINTER && n->type->etype == TINTER)
			return; // TFORWINTERがTINTERで上書きされるケース
		if(n->type->etype != TFORW && n->type->etype != TFORWSTRUCT && n->type->etype != TFORWINTER) {
			yyerror("redeclare import type %S from %lT to %lT", s, n->type, t);
			n = s->def = typenod(typ(0));
		}
	}
// ...
	switch(n->type->etype) {
	case TFORWINTER:
	case TFORWSTRUCT:
		// allow re-export in case it gets defined
		s->export = 0;
		s->imported = 0;
		break;
	default:
		checkwidth(n->type);
	}
// ...
```
`importtype` 関数は、パッケージから型をインポートする際に呼び出されます。この変更により、インポートされる型 `t` が `TFORWSTRUCT` であり、既存の型 `n->type` が `TSTRUCT` である場合（または `TFORWINTER` と `TINTER` の場合）、これは前方宣言が完全な定義で解決されたケースとして扱われ、エラーにはなりません。
また、`TFORWINTER` や `TFORWSTRUCT` のような前方宣言された型の場合、`s->export = 0; s->imported = 0;` と設定されます。これは、前方宣言された型はまだ完全な定義ではないため、すぐにエクスポート対象とはせず、後で完全な定義が提供された場合に再エクスポートされる可能性があることを示唆しています。

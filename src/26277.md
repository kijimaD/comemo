## 変更の背景

このコミットの背景には、HTTP/2プロトコルが導入され、既存のHTTP/1.1の機能がHTTP/2でも期待通りに動作するかどうかを確認する必要があったという点があります。特に、HTTPの`OPTIONS`メソッドと、リクエストターゲットとしてアスタリスク（`*`）を使用する「スターリクエスト」の挙動が焦点となっています。

コミットメッセージによると、作者は当初、HTTP/2で`OPTIONS *`リクエストを処理するために追加の作業が必要だと考えていました。しかし、調査の結果、`net/url`パッケージが既にこのようなリクエストのパースを適切に処理しており、`net/http`の`serverHandler`が`OPTIONS *`のハンドリングを既にサポートしていることが判明しました。これらの既存のメカニズムはHTTP/2でも再利用されるため、新たな実装は不要であることが確認されました。

しかし、実装が既に存在しているからといって、その動作が将来にわたって保証されるわけではありません。そのため、このコミットでは、既存の機能がHTTP/1.1とHTTP/2の両方で正しく機能することを検証するためのテストケースを追加しています。これにより、将来の変更によってこの重要な挙動が意図せず壊れることを防ぐための安全網が提供されます。

## 前提知識の解説

### HTTP OPTIONSメソッド

HTTPの`OPTIONS`メソッドは、特定のURLまたはWebサーバー全体で利用可能な通信オプションをクライアントが問い合わせるために使用されます。これは、リソースに対して実際のアクション（`GET`、`POST`など）を実行する前に、どのようなメソッドやヘッダーがサポートされているかを知るために役立ちます。

### OPTIONS * リクエスト

`OPTIONS`メソッドにおいて、リクエストターゲットとしてアスタリスク（`*`）が使用される場合（例: `OPTIONS * HTTP/1.1`）、これは特定のURIではなく、**サーバー全体**の通信オプションを問い合わせることを意味します。これは、サーバーがサポートする一般的なメソッドや機能について知るために使用されることがあります。

最も一般的なユースケースの一つは、**CORS（Cross-Origin Resource Sharing）のプリフライトリクエスト**です。Webブラウザは、特定の種類のクロスオリジンHTTPリクエスト（例えば、`PUT`や`DELETE`、カスタムヘッダーを含む`POST`など）を送信する前に、まず`OPTIONS`プリフライトリクエストを送信して、サーバーがその実際のリクエストを許可するかどうかを確認します。このプリフライトリクエストは、通常、特定のパスに対して行われますが、サーバー全体のポリシーを問い合わせるために`OPTIONS *`が使われることもあります。

### HTTP/1.1とHTTP/2におけるスターリクエスト

*   **HTTP/1.1**: `OPTIONS *`はHTTP/1.1の仕様で定義されており、サーバー全体のオプションを問い合わせるための有効なリクエスト形式です。
*   **HTTP/2**: HTTP/2は、HTTP/1.1のセマンティクスを維持しつつ、パフォーマンスを向上させるために設計されたプロトコルです。`OPTIONS *`のようなHTTP/1.1の概念は、HTTP/2のフレームワーク内で引き続き有効です。HTTP/2では、リクエストはバイナリフレームとしてエンコードされますが、その論理的な構造（メソッド、パス、ヘッダーなど）はHTTP/1.1と互換性があります。コミットメッセージが示唆するように、Goの`net/url`がパスのパースを、`net/http`の`serverHandler`が`OPTIONS *`のハンドリングを既に担当しているため、HTTP/2でもこれらの既存のロジックが利用されます。

### Go言語の`net/http`と`net/url`パッケージ

*   **`net/url`**: このパッケージはURLのパースと操作を担当します。URL文字列をスキーム、ホスト、パス、クエリパラメータなどのコンポーネントに分解します。`OPTIONS *`リクエストの場合、`*`はURLのパス部分としてパースされます。
*   **`net/http`**: このパッケージはHTTPクライアントとサーバーの実装を提供します。サーバー側では、受信したリクエストを解析し、適切なハンドラにルーティングします。`serverHandler`は、受信したリクエストのメソッドとパスに基づいて、どのように応答するかを決定するGoのHTTPサーバーの内部コンポーネントです。

## 技術的詳細

このコミットで追加されたテストは、`net/http`パッケージがHTTP/1.1とHTTP/2の両方で「スターリクエスト」を正しく処理できることを検証します。具体的には、`clientserver_test.go`ファイルに`testStarRequest`というヘルパー関数が追加され、この関数を使って様々なシナリオがテストされます。

`testStarRequest`関数は以下の主要な要素をテストします。

1.  **HTTPモードの切り替え**: `h2`引数によって、テストがHTTP/1.1モード（`h1Mode`）またはHTTP/2モード（`h2Mode`）で実行されるかを制御します。これにより、両方のプロトコルで一貫した動作が保証されます。
2.  **メソッドの指定**: `method`引数によって、`OPTIONS`メソッドと、`FOO`のようなカスタムメソッド（`OPTIONS`以外のメソッドが`*`パスでどのように扱われるかを確認するため）の両方がテストされます。
3.  **サーバーのセットアップ**: `newClientServerTest`関数を使用して、テスト用のHTTPサーバーが起動されます。このサーバーは、受信したリクエストを`gotc`チャネルに送信し、`foo: bar`ヘッダーを設定して応答します。`OPTIONS`メソッドの場合は、`Content-Length`を0に設定し、`foo`ヘッダーは設定しません。
4.  **リクエストの構築**: クライアントは、`URL.Path`を`*`に設定した`Request`オブジェクトを構築し、指定されたメソッドでサーバーに送信します。
5.  **応答の検証**:
    *   ステータスコードが200であることを確認します。
    *   `OPTIONS`メソッドの場合、`Content-Length`が0であることを確認します。それ以外の場合は`-1`（不明な長さ）を期待します。
    *   `OPTIONS`メソッドの場合、`foo`ヘッダーが空であることを確認します。それ以外の場合は`bar`であることを確認します。
6.  **サーバー側でのリクエストの検証**:
    *   サーバーがリクエストを受信したことを確認します。
    *   受信したリクエストのメソッドが期待通りであることを確認します。
    *   受信したリクエストの`URL.Path`が`*`であることを確認します。
    *   受信したリクエストの`RequestURI`が`*`であることを確認します。

特に、`OPTIONS`メソッドの場合、サーバーは通常、リクエストボディなしで応答し、`Content-Length`は0になります。また、`OPTIONS *`リクエストはサーバー全体のオプションを問い合わせるため、特定のアプリケーションレベルのヘッダー（このテストの`foo`ヘッダーなど）は期待されない場合があります。テストではこれらの挙動の違いを考慮して検証が行われています。

## コアとなるコードの解説

追加されたコードは、`testStarRequest`というテストヘルパー関数と、それを利用する4つのテストケースで構成されています。

### `testStarRequest` 関数

```go
func testStarRequest(t *testing.T, method string, h2 bool) {
	defer afterTest(t) // テスト後のクリーンアップ処理を登録

	gotc := make(chan *Request, 1) // サーバーが受信したリクエストを送信するためのチャネル
	cst := newClientServerTest(t, h2, HandlerFunc(func(w ResponseWriter, r *Request) {
		w.Header().Set("foo", "bar") // 応答ヘッダーに "foo: bar" を設定
		gotc <- r                     // 受信したリクエストをチャネルに送信
		w.(Flusher).Flush()           // 応答をフラッシュ
	}))
	defer cst.close() // テストサーバーのクリーンアップを登録

	u, err := url.Parse(cst.ts.URL) // テストサーバーのURLをパース
	if err != nil {
		t.Fatal(err)
	}
	u.Path = "*" // URLのパスを "*" に設定

	req := &Request{
		Method: method, // 指定されたメソッド (例: "OPTIONS", "FOO")
		Header: Header{},
		URL:    u, // パスが "*" のURL
	}

	res, err := cst.c.Do(req) // クライアントでリクエストを送信
	if err != nil {
		t.Fatalf("RoundTrip = %v", err)
	}
	res.Body.Close() // 応答ボディを閉じる

	wantFoo := "bar"
	wantLen := int64(-1)
	if method == "OPTIONS" {
		wantFoo = "" // OPTIONSメソッドの場合、"foo"ヘッダーは期待しない
		wantLen = 0  // OPTIONSメソッドの場合、Content-Lengthは0を期待
	}
	if res.StatusCode != 200 {
		t.Errorf("status code = %v; want %d", res.Status, 200)
	}
	if res.ContentLength != wantLen {
		t.Errorf("content length = %v; want %d", res.ContentLength, wantLen)
	}
	if got := res.Header.Get("foo"); got != wantFoo {
		t.Errorf("response \"foo\" header = %q; want %q", got, wantFoo)
	}

	// サーバーがリクエストを受信したか、およびその内容を検証
	select {
	case req = <-gotc: // チャネルからリクエストを受信
	default:
		req = nil
	}
	if req == nil {
		if method != "OPTIONS" { // OPTIONSメソッド以外でリクエストが受信されなかった場合はエラー
			t.Fatalf("handler never got request")
		}
		return // OPTIONSメソッドの場合は、ハンドラがリクエストを処理しないこともあるため、ここで終了
	}
	if req.Method != method {
		t.Errorf("method = %q; want %q", req.Method, method)
	}
	if req.URL.Path != "*" {
		t.Errorf("URL.Path = %q; want *", req.URL.Path)
	}
	if req.RequestURI != "*" {
		t.Errorf("RequestURI = %q; want *", req.RequestURI)
	}
}
```

この関数は、HTTPクライアントとサーバー間の通信をシミュレートし、`*`パスを持つリクエストが両側でどのように扱われるかを詳細に検証します。特に、`OPTIONS *`リクエストの特殊な挙動（例えば、`Content-Length`が0になることや、サーバーが必ずしもアプリケーションレベルのハンドラに到達しない可能性があること）を考慮したアサーションが含まれています。

### テストケース

`testStarRequest`関数は以下の4つのテストケースから呼び出されます。

*   `TestStarRequestFoo_h1`: HTTP/1.1で`FOO *`リクエストをテスト
*   `TestStarRequestFoo_h2`: HTTP/2で`FOO *`リクエストをテスト
*   `TestStarRequestOptions_h1`: HTTP/1.1で`OPTIONS *`リクエストをテスト
*   `TestStarRequestOptions_h2`: HTTP/2で`OPTIONS *`リクエストをテスト

これらのテストケースにより、`net/http`パッケージがHTTP/1.1とHTTP/2の両方で、一般的なメソッドと`OPTIONS`メソッドの両方において、`*`パスを持つリクエストを正しく処理できることが保証されます。

## 元コミット内容

```
cmd/compile: avoid pointers in go.string.* symbols

When creating binaries for dynamic linking, the linker moves
read-only data symbols that contain pointers into relro sections.
It is not setup for handling a go.string symbol moving to relro.

Instead of teaching it how (because go.string symbols with pointers
are unusual anyhow), put the data in a type.. section.

Fixes the android builder.

Change-Id: Ica4722d32241643c060923517b90276ff8ac6b07
Reviewed-on: https://go-review.googlesource.com/21110
Reviewed-by: Brad Fitzpatrick <bradfitz@golang.org>
```

## 変更の背景

このコミットは、Goコンパイラが生成する`go.string.*`シンボルが、動的リンクされたバイナリの作成時に問題を引き起こすという特定のバグを修正するために導入されました。特に、Androidビルド環境でこの問題が発生し、ビルドが失敗していました。

問題の根源は、動的リンカがポインタを含む読み取り専用データシンボルを`RELRO` (Relocation Read-Only) セクションに移動させる挙動にありました。`go.string`シンボルは通常、文字列リテラルを表すために使用されますが、特定の状況下（この場合は`reflect.go`内の`dname`関数が生成するシンボル）でポインタを含むことがありました。動的リンカは、`go.string`シンボルが`RELRO`セクションに移動された際に、その内容（特にポインタ）を適切に処理するようには設計されていませんでした。

このコミットの目的は、リンカに`go.string`シンボル内のポインタの処理方法を教えるのではなく、ポインタを含む可能性のある`go.string`関連のデータを、リンカが`RELRO`セクションへの移動を適切に処理できる別のセクション（`type..`セクション）に配置することで、この問題を回避することでした。これにより、Androidビルダの問題が解決されました。

## 前提知識の解説

### Goの文字列シンボル (`go.string.*`)
Go言語において、文字列リテラルは不変なバイトスライスとして扱われます。コンパイル時、これらの文字列リテラルはバイナリの読み取り専用データセクション（ELFバイナリでは通常`.rodata`）に埋め込まれます。Goコンパイラは、これらの文字列データにアクセスするための内部的なシンボルを生成することがあり、これらは慣習的に`go.string.*`のような形式で命名されます。これらのシンボルは、文字列データへのポインタと長さを保持するGoの`string`型構造体に関連付けられることがあります。

### 動的リンク (Dynamic Linking)
動的リンクは、プログラムが実行時に共有ライブラリ（例: `.so`ファイルや`.dll`ファイル）をロードしてリンクするプロセスです。Goは通常、静的リンクを好みますが、`cgo`を使用してC言語のライブラリと連携する場合や、特定のビルドモード（例: `-buildmode=pie`や`plugin`パッケージの使用）では動的リンクが使用されます。動的リンクされたバイナリは、実行時に外部の共有ライブラリに依存するため、起動時にリンカがシンボル解決や再配置を行います。

### RELRO (Relocation Read-Only) セクション
`RELRO`は、動的リンクされたELFバイナリにおけるセキュリティ強化メカニズムです。その主な目的は、動的リンカが使用する重要なデータ構造（特にGlobal Offset Table: `GOT`）が、プログラムの起動後に攻撃者によって上書きされるのを防ぐことです。

*   **GOT (Global Offset Table):** 動的リンクされたプログラムでは、`GOT`は共有ライブラリ内の関数のメモリアドレスを保持します。共有ライブラリの関数が初めて呼び出されると、動的リンカがその実際のアドレスを解決し、`GOT`に格納します。
*   **RELROの役割:** `RELRO`は、必要な動的再配置がすべて処理された後、`GOT`を含む特定のセクションを読み取り専用としてマークします。
    *   **Partial RELRO:** 一部の再配置セクションを読み取り専用にしますが、遅延バインディングが使用されている場合、`GOT`の一部は書き込み可能のままになることがあります。
    *   **Full RELRO:** すべての動的シンボルをプログラム起動時に解決（即時バインディング）し、その後、`GOT`全体を読み取り専用としてマークします。これによりセキュリティは向上しますが、プログラムの起動時間がわずかに増加する可能性があります。

動的リンカは、ポインタを含む読み取り専用データシンボルを`RELRO`セクションに移動させることがあります。これは、これらのポインタが実行時に変更される可能性があるため、セキュリティ上の理由から保護する必要があるためです。

### `type..` セクション
Goコンパイラとリンカは、Goの型情報やリフレクション関連のデータを格納するために、`type..`というプレフィックスを持つシンボルやセクションを使用します。これらのセクションは、Goのランタイムが型情報を効率的に検索・利用できるように設計されており、リンカが特定のルールに基づいて処理します。このコミットでは、`go.string`シンボルが`RELRO`セクションで問題を引き起こす代わりに、この`type..`セクションのメカニズムを利用してデータを格納することで問題を回避しています。

## 技術的詳細
このコミットが解決しようとしている問題は、Goコンパイラが生成する特定の`go.string`シンボルが、動的リンク環境下での`RELRO`処理と衝突することにありました。

具体的には、`src/cmd/compile/internal/gc/reflect.go`内の`dname`関数は、リフレクションのためにメソッド名などの文字列データを表現するシンボルを生成します。この関数は、`fmt.Sprintf(\`go.string."".methodname.%d\`, dnameCount)`という形式でシンボル名を生成していました。

問題は、これらの`go.string`シンボルが、文字列データだけでなく、その文字列データへのポインタを含む可能性があった点です。動的リンカは、ポインタを含む読み取り専用データシンボルを`RELRO`セクションに移動させようとします。しかし、リンカは`go.string`というプレフィックスを持つシンボルが`RELRO`セクションに移動された際に、その内部のポインタを適切に再配置したり、保護したりするメカニズムを持っていませんでした。これにより、特にAndroidのような特定の環境で、動的リンクされたGoバイナリのビルドが失敗する原因となっていました。

このコミットの解決策は、リンカの挙動を変更するのではなく、Goコンパイラがシンボルを生成する方法を変更することでした。具体的には、ポインタを含む可能性のある`go.string`関連のデータを、`type..`というプレフィックスを持つシンボル名に変更しました。新しいシンボル名は`fmt.Sprintf(\`type..methodname."".%d\`, dnameCount)`となります。

コミットメッセージにあるように、`type..`というプレフィックスを使用することで、リンカに対して以下の2つのシグナルを送ります。
1.  動的リンク時に、このシンボルを`RELRO`セクションに移動させるべきであること。
2.  この内容を型としてデコードすべきではないこと。

これにより、リンカは`type..`セクションのデータとして適切に処理し、`RELRO`セクションへの移動とポインタの取り扱いに関する問題を回避できるようになります。結果として、`go.string`シンボルが`RELRO`セクションで不適切に扱われることがなくなり、Androidビルダの問題が解決されました。

## コアとなるコードの解説

変更されたのは、`dname`関数内で`bsymname`というシンボル名を生成している箇所です。

*   **変更前:**
    ```go
    bsymname := fmt.Sprintf(`go.string."".methodname.%d`, dnameCount)
    ```
    この行では、`go.string.`というプレフィックスを持つシンボル名が生成されていました。これは、リンカに対してこのシンボルが文字列データに関連していることを示唆します。しかし、前述の問題により、ポインタを含むこの種のシンボルが`RELRO`セクションに移動されると問題が発生しました。

*   **変更後:**
    ```go
    // Write out data as "type.." to signal two things to the
    // linker, first that when dynamically linking, the symbol
    // should be moved to a relro section, and second that the
    // contents should not be decoded as a type.
    bsymname := fmt.Sprintf(`type..methodname."".%d`, dnameCount)
    ```
    変更後では、シンボル名のプレフィックスが`go.string.`から`type..`に変更されています。この変更は、リンカに対する指示を根本的に変えます。
    1.  `type..`プレフィックスは、リンカに対して、このシンボルがGoの型情報に関連するデータであり、動的リンク時に`RELRO`セクションに移動されるべきであることを示唆します。これにより、リンカはポインタを含む読み取り専用データを`RELRO`セクションに適切に配置し、保護することができます。
    2.  同時に、コメントにもあるように、「その内容を型としてデコードすべきではない」という指示も含まれています。これは、`type..`セクションが通常Goの型記述子を格納するために使用されるため、リンカやデバッガがこの特定のシンボルを誤って型情報として解釈しないようにするためのものです。

この修正により、Goコンパイラは、動的リンカが`RELRO`セクションを処理する際の既存の挙動と互換性のある方法でシンボルを生成するようになり、`go.string`シンボル内のポインタが原因で発生していたAndroidビルダの問題が解決されました。これは、リンカの複雑な挙動をGoコンパイラ側で吸収する、実用的な解決策と言えます。

## 変更の背景

Go言語の型システムは厳格であり、変数への代入、関数呼び出しの引数渡し、戻り値の処理など、様々な場面で型の一致が求められます。`go/types` パッケージは、Goプログラムの静的解析を行い、これらの型制約が満たされているかを検証する役割を担っています。

このコミット以前は、`go/types` パッケージとGoコンパイラ (`gc`) の間で、代入エラーに関するエラーメッセージの報告方法に差異がありました。これにより、開発者が同じコードに対して異なるエラーメッセージを受け取る可能性があり、混乱を招くことがありました。また、エラーメッセージが常に十分なコンテキスト情報を提供しているわけではなく、問題の特定とデバッグを困難にする場合がありました。

このコミットの主な動機は、以下の点を改善することにありました。
1.  **エラーメッセージの一貫性:** `go/types` が報告するエラーメッセージを `gc` のそれと近づけることで、ツールとコンパイラの間で一貫したユーザー体験を提供する。
2.  **コードの簡素化:** 代入エラーのチェックと報告のロジックを `assignment` 関数内に集約することで、コードベース全体の複雑性を低減する。
3.  **診断情報の強化:** エラーメッセージに、代入が行われた具体的なコンテキスト（例: "variable declaration", "argument to panic", "map literal"）を含めることで、開発者がエラーの原因をより迅速に理解できるようにする。

これらの改善は、Go言語のエコシステム全体の品質と開発者の生産性向上に寄与します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および型システムに関する前提知識が必要です。

1.  **`go/types` パッケージ:**
    Go言語の標準ライブラリの一部であり、Goプログラムの型チェックとセマンティック解析を行うためのAPIを提供します。これは、IDE、リンター、その他の静的解析ツールで広く利用されています。`go/types` は、抽象構文木 (AST) を入力として受け取り、各式の型、変数のスコープ、メソッドセットなどを解決し、Go言語の型規則に違反がないかを検証します。

2.  **型チェック (Type Checking):**
    プログラムが型規則に従っているかを検証するプロセスです。Goでは静的型付けが採用されており、コンパイル時に型チェックが行われます。これにより、多くの型関連のエラーが実行時ではなくコンパイル時に検出されます。

3.  **代入可能性 (Assignability):**
    Go言語の仕様では、ある値が特定の型の変数に代入可能であるかどうかの規則が定義されています。これには、型の同一性、インターフェースの実装、チャネルの方向、定数の型変換などが含まれます。例えば、`int` 型の値を `string` 型の変数に直接代入することはできません。

4.  **`gc` (Go Compiler):**
    Go言語の公式コンパイラです。`go/types` パッケージが提供する型チェック機能は、`gc` の型チェックロジックと密接に関連していますが、歴史的に実装の詳細やエラー報告のニュアンスに違いがありました。

5.  **`operand` 構造体:**
    `go/types` パッケージ内で、式の結果を表すために使用される内部的な構造体です。式の型、値、モード（例: `constant_`, `variable`, `invalid` など）などの情報を含みます。`x.mode == invalid` は、そのオペランドが既にエラー状態にあることを示します。

6.  **`token.Pos`:**
    Goのソースコード内の位置（ファイル、行、列、オフセット）を表す型です。エラーメッセージの正確な位置を報告するために使用されます。

7.  **`check.errorf` および `check.xerrorf`:**
    `go/types.Checker` 構造体のメソッドで、型チェック中にエラーを報告するために使用されます。`errorf` は一般的なエラー報告に、`xerrorf` は追加の理由 (`reason`) を伴うエラー報告に使用されていました。このコミットでは `xerrorf` が廃止され、`errorf` にコンテキスト情報を渡す形に統一されます。

## 技術的詳細

このコミットの核心的な変更は、`go/types` パッケージ内の代入エラー処理ロジックの集約と再設計にあります。

以前の実装では、`check.assignment` 関数は代入が可能かどうかを示す `bool` 値と、代入が失敗した場合の理由を格納する `*string` ポインタを返していました。呼び出し元は、この `bool` 値と `reason` をチェックし、必要に応じて `check.xerrorf` を使用してエラーを報告していました。このアプローチは、エラー報告ロジックが `assignment` 関数とその呼び出し元の両方に分散しているため、コードが複雑になり、エラーメッセージの一貫性を保つのが難しいという問題がありました。

新しい実装では、`check.assignment` 関数のシグネチャが `func (check *Checker) assignment(x *operand, T Type, context string)` に変更されました。
-   `reason *string` パラメータが削除され、代わりに `context string` パラメータが導入されました。
-   `assignment` 関数は `bool` 値を返さなくなり、代入が失敗した場合は `x.mode` を `invalid` に設定し、**自身でエラーを報告する**ようになりました。

この変更により、以下の技術的改善が実現されました。

1.  **エラー報告の一元化:** 代入エラーに関するすべてのエラー報告ロジックが `assignment` 関数内にカプセル化されました。これにより、エラーメッセージの生成とフォーマットが一箇所で管理されるため、`gc` とのメッセージの一貫性を確保しやすくなります。
2.  **コンテキスト情報の組み込み:** `context` 文字列パラメータは、代入が行われている具体的な状況（例: "variable declaration", "argument to panic", "map literal", "assignment"）を `assignment` 関数に直接伝達します。これにより、`assignment` 関数はより詳細で役立つエラーメッセージを生成できます。例えば、「cannot use X as Y value in Z: reason」のような形式で、Zがコンテキスト情報となります。
3.  **`xerrorf` の廃止:** `check.xerrorf` 関数は、`reason` パラメータを処理するために存在していましたが、エラー報告が `assignment` 関数内に統合されたため、不要となり削除されました。これにより、エラー報告APIが簡素化されました。
4.  **コードの簡素化と保守性の向上:** 呼び出し元は `assignment` の戻り値をチェックしてエラーを報告する必要がなくなり、単に `x.mode == invalid` を確認するだけでよくなりました。これにより、`go/types` パッケージ全体のコードが簡素化され、将来的な変更やデバッグが容易になります。

例えば、以前は `if reason := ""; !check.assignment(x, lhs.typ, &reason) { ... check.xerrorf(...) }` のようなパターンが使われていましたが、これが `check.assignment(x, lhs.typ, context); if x.mode == invalid { ... }` のように簡潔になりました。

テストデータ (`src/go/types/testdata/*.src`) の変更も、この新しいエラー報告ロジックに合わせて、期待されるエラーメッセージが更新されていることを示しています。特に、`cannot assign` や `cannot pass argument` といった一般的なエラーメッセージが、`cannot use .* in assignment` や `cannot use .* in argument` のように、より具体的なコンテキストを示す正規表現パターンに置き換えられています。これは、エラーメッセージがより詳細になったことを反映しています。

## コアとなるコードの解説

最も重要な変更は `src/go/types/assignments.go` の `assignment` 関数にあります。

**変更前 (`assignment` 関数の一部):**

```go
func (check *Checker) assignment(x *operand, T Type, reason *string) bool {
    // ...
    if T == nil || x.assignableTo(check.conf, T, reason) {
        return true
    }
    return false
}
```
このコードでは、`assignment` 関数は代入の成否を `bool` で返し、失敗した場合は `reason` ポインタを通じて詳細な理由を呼び出し元に伝えていました。呼び出し元は、この `bool` と `reason` を基にエラーメッセージを構築する必要がありました。

**変更後 (`assignment` 関数の一部):**

```go
func (check *Checker) assignment(x *operand, T Type, context string) {
    // ...
    if T == nil {
        return
    }

    if reason := ""; !x.assignableTo(check.conf, T, &reason) {
        if reason != "" {
            check.errorf(x.pos(), "cannot use %s as %s value in %s: %s", x, T, context, reason)
        } else {
            check.errorf(x.pos(), "cannot use %s as %s value in %s", x, T, context)
        }
        x.mode = invalid
    }
}
```
変更後では、`assignment` 関数は `bool` を返さず、`context` 文字列を受け取ります。代入が不可能であると判断された場合、`assignment` 関数自身が `check.errorf` を呼び出してエラーを報告し、`x.mode` を `invalid` に設定します。これにより、エラー報告ロジックが `assignment` 関数内に集約され、呼び出し元はエラー報告の詳細を気にする必要がなくなりました。`context` 文字列は、エラーメッセージの `%s` プレースホルダーに挿入され、エラーが発生した具体的な状況を明確に示します。

例えば、`src/go/types/decl.go` の `varDecl` 関数では、変数の初期化時に `check.initVar` を呼び出しますが、その中で `check.assignment` が呼ばれます。変更前は `check.initVar` が `assignment` の結果を処理してエラーを報告していましたが、変更後は `check.initVar` が `check.assignment(obj, &x, "variable declaration")` のようにコンテキストを渡し、`assignment` が直接エラーを報告します。

また、`src/go/types/errors.go` から `xerrorf` が削除されたことも重要です。これは、`assignment` 関数が `reason` を直接処理するようになったため、`reason` を特別に扱うエラー報告関数が不要になったことを意味します。

これらの変更により、`go/types` パッケージ全体で代入エラーの報告がより統一され、開発者にとって理解しやすい、より情報量の多いエラーメッセージが提供されるようになりました。

    `go/types.Checker` 構造体のメソッドで、型チェック中にエラーを報告するために使用されます。`errorf` は一般的なエラー報告に、`xerrorf` は追加の理由 (`reason`) を伴うエラー報告に使用されていました。このコミットでは `xerrorf` が廃止され、`errorf` にコンテキスト情報を渡す形に統一されます。

## 技術的詳細

このコミットの核心的な変更は、`go/types` パッケージ内の代入エラー処理ロジックの集約と再設計にあります。

以前の実装では、`check.assignment` 関数は代入が可能かどうかを示す `bool` 値と、代入が失敗した場合の理由を格納する `*string` ポインタを返していました。呼び出し元は、この `bool` 値と `reason` をチェックし、必要に応じて `check.xerrorf` を使用してエラーを報告していました。このアプローチは、エラー報告ロジックが `assignment` 関数とその呼び出し元の両方に分散しているため、コードが複雑になり、エラーメッセージの一貫性を保つのが難しいという問題がありました。

新しい実装では、`check.assignment` 関数のシグネチャが `func (check *Checker) assignment(x *operand, T Type, context string)` に変更されました。
-   `reason *string` パラメータが削除され、代わりに `context string` パラメータが導入されました。
-   `assignment` 関数は `bool` 値を返さなくなり、代入が失敗した場合は `x.mode` を `invalid` に設定し、**自身でエラーを報告する**ようになりました。

この変更により、以下の技術的改善が実現されました。

1.  **エラー報告の一元化:** 代入エラーに関するすべてのエラー報告ロジックが `assignment` 関数内にカプセル化されました。これにより、エラーメッセージの生成とフォーマットが一箇所で管理されるため、`gc` とのメッセージの一貫性を確保しやすくなります。
2.  **コンテキスト情報の組み込み:** `context` 文字列パラメータは、代入が行われている具体的な状況（例: "variable declaration", "argument to panic", "map literal", "assignment"）を `assignment` 関数に直接伝達します。これにより、`assignment` 関数はより詳細で役立つエラーメッセージを生成できます。例えば、「cannot use X as Y value in Z: reason」のような形式で、Zがコンテキスト情報となります。
3.  **`xerrorf` の廃止:** `check.xerrorf` 関数は、`reason` パラメータを処理するために存在していましたが、エラー報告が `assignment` 関数内に統合されたため、不要となり削除されました。これにより、エラー報告APIが簡素化されました。
4.  **コードの簡素化と保守性の向上:** 呼び出し元は `assignment` の戻り値をチェックしてエラーを報告する必要がなくなり、単に `x.mode == invalid` を確認するだけでよくなりました。これにより、`go/types` パッケージ全体のコードが簡素化され、将来的な変更やデバッグが容易になります。

例えば、以前は `if reason := ""; !check.assignment(x, lhs.typ, &reason) { ... check.xerrorf(...) }` のようなパターンが使われていましたが、これが `check.assignment(x, lhs.typ, context); if x.mode == invalid { ... }` のように簡潔になりました。

テストデータ (`src/go/types/testdata/*.src`) の変更も、この新しいエラー報告ロジックに合わせて、期待されるエラーメッセージが更新されていることを示しています。特に、`cannot assign` や `cannot pass argument` といった一般的なエラーメッセージが、`cannot use .* in assignment` や `cannot use .* in argument` のように、より具体的なコンテキストを示す正規表現パターンに置き換えられています。これは、エラーメッセージがより詳細になったことを反映しています。

## コアとなるコードの解説

最も重要な変更は `src/go/types/assignments.go` の `assignment` 関数にあります。

**変更前 (`assignment` 関数の一部):**

```go
func (check *Checker) assignment(x *operand, T Type, reason *string) bool {
    // ...
    if T == nil || x.assignableTo(check.conf, T, reason) {
        return true
    }
    return false
}
```
このコードでは、`assignment` 関数は代入の成否を `bool` で返し、失敗した場合は `reason` ポインタを通じて詳細な理由を呼び出し元に伝えていました。呼び出し元は、この `bool` と `reason` を基にエラーメッセージを構築する必要がありました。

**変更後 (`assignment` 関数の一部):**

```go
func (check *Checker) assignment(x *operand, T Type, context string) {
    // ...
    if T == nil {
        return
    }

    if reason := ""; !x.assignableTo(check.conf, T, &reason) {
        if reason != "" {
            check.errorf(x.pos(), "cannot use %s as %s value in %s: %s", x, T, context, reason)
        } else {
            check.errorf(x.pos(), "cannot use %s as %s value in %s", x, T, context)
        }
        x.mode = invalid
    }
}
```
変更後では、`assignment` 関数は `bool` を返さず、`context` 文字列を受け取ります。代入が不可能であると判断された場合、`assignment` 関数自身が `check.errorf` を呼び出してエラーを報告し、`x.mode` を `invalid` に設定します。これにより、エラー報告ロジックが `assignment` 関数内に集約され、呼び出し元はエラー報告の詳細を気にする必要がなくなりました。`context` 文字列は、エラーメッセージの `%s` プレースホルダーに挿入され、エラーが発生した具体的な状況を明確に示します。

例えば、`src/go/types/decl.go` の `varDecl` 関数では、変数の初期化時に `check.initVar` を呼び出しますが、その中で `check.assignment` が呼ばれます。変更前は `check.initVar` が `assignment` の結果を処理してエラーを報告していましたが、変更後は `check.initVar` が `check.assignment(obj, &x, "variable declaration")` のようにコンテキストを渡し、`assignment` が直接エラーを報告します。

また、`src/go/types/errors.go` から `xerrorf` が削除されたことも重要です。これは、`assignment` 関数が `reason` を直接処理するようになったため、`reason` を特別に扱うエラー報告関数が不要になったことを意味します。

これらの変更により、`go/types` パッケージ全体で代入エラーの報告がより統一され、開発者にとって理解しやすい、より情報量の多いエラーメッセージが提供されるようになりました。

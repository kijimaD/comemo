# [インデックス 28137] ファイルの概要

このコミットは、Go言語の`database/sql`パッケージにおいて、`[]byte`型を基にしたカスタム型（例: `json.RawMessage`）がデータベースからスキャンされる際に発生する潜在的なデータ破損バグを修正します。具体的には、`Scan`メソッドがデータベースから取得したバイトデータを、カスタム`[]byte`型に直接割り当てる際にディープコピーを行わないため、他のゴルーチンがその基盤となるメモリを上書きする可能性がありました。このコミットは、`[]byte`型の場合に明示的にデータをクローンすることで、この問題を解決します。

## 元コミット内容

```
database/sql: clone data for named []byte types

Previously named byte types like json.RawMessage could get dirty
database memory from a call to Scan. These types would activate a
code path that didn't clone the byte data coming from the database
before assigning it. Another thread could then overwrite the byte
array in src, which has unexpected consequences.

Originally reported by Jason Moiron; the patch and test are his
suggestions. Fixes #13905.

Change-Id: Iacfef61cbc9dd51c8fccef9b2b9d9544c77dd0e0
Reviewed-on: https://go-review.googlesource.com/22393
Reviewed-by: Brad Fitzpatrick <bradfitz@golang.org>
```

## 変更の背景

この変更は、Goの`database/sql`パッケージにおける、特定の状況下でのデータ破損の可能性に対処するために導入されました。問題は、`database/sql`パッケージの`Scan`メソッドが、データベースから取得したバイトデータをGoの変数に割り当てる際に発生しました。特に、`json.RawMessage`のような、基盤となる型が`[]byte`であるカスタム型（名前付き`[]byte`型）がターゲットとなる場合に顕著でした。

従来の`Scan`の実装では、データベースドライバが提供する`[]byte`スライスを、ターゲット変数に直接割り当てることがありました。Goのスライスは、基盤となる配列へのポインタ、長さ、容量を持つ構造体であり、スライス自体をコピーしても、そのスライスが指す基盤の配列はコピーされません（シャローコピー）。

この挙動が問題となるのは、データベースドライバが内部的に使用するメモリバッファを、複数の`Scan`操作や異なるゴルーチン間で再利用する可能性があるためです。もし`Scan`がデータベースのメモリバッファへの参照を直接カスタム`[]byte`型に渡してしまい、その後に別の`Scan`操作や他の処理が同じメモリバッファを上書きした場合、既にアプリケーションコードに渡されたはずのデータが意図せず変更されてしまう、いわゆる「ダーティなメモリ」問題が発生しました。これは、並行処理環境において予測不能な結果やデータ破損を引き起こす可能性がありました。

このバグはJason Moironによって報告され、Go issue #13905で追跡されていました。このコミットは、その報告と提案に基づいて実装されたものです。

## 前提知識の解説

### 1. `database/sql`パッケージの`Scan`メソッド

`database/sql`パッケージは、GoアプリケーションからSQLデータベースにアクセスするための汎用インターフェースを提供します。`Rows`インターフェースの`Scan`メソッドは、クエリ結果の現在の行の列を、指定されたGoの変数にコピーするために使用されます。
`Scan`は、データベースの型をGoの型に変換する役割を担っており、この変換ロジックは内部的に`convertAssign`関数によって処理されます。

### 2. Goにおけるスライス（`[]byte`）の内部構造とコピー挙動

Goのスライスは、基盤となる配列の一部を参照する軽量なデータ構造です。スライスは以下の3つの要素で構成されます。
*   **ポインタ**: 基盤となる配列の先頭要素へのポインタ。
*   **長さ (Length)**: スライスに含まれる要素の数。
*   **容量 (Capacity)**: スライスの先頭要素から基盤となる配列の末尾までの要素の数。

スライスを別のスライス変数に代入したり、関数に引数として渡したりする場合、スライスヘッダ（ポインタ、長さ、容量）がコピーされますが、基盤となる配列自体はコピーされません。これは「シャローコピー」と呼ばれます。したがって、複数のスライスが同じ基盤配列を参照している場合、いずれかのスライスを通じて基盤配列の要素を変更すると、他のスライスからもその変更が見えてしまいます。

このコミットの文脈では、`database/sql`がデータベースドライバから受け取った`[]byte`スライスを、ユーザー定義の`[]byte`型変数に直接割り当てた場合、両者が同じ基盤配列を共有することになり、ドライバがその配列を再利用・上書きすると、ユーザー変数の内容も変わってしまうという問題が発生していました。

### 3. `reflect`パッケージ

`reflect`パッケージは、実行時にGoの型、値、構造を検査・操作するための機能を提供します。
*   `reflect.ValueOf(i interface{})`: インターフェース値`i`の`reflect.Value`表現を返します。
*   `reflect.Indirect(v reflect.Value)`: ポインタが指す要素の`reflect.Value`を返します。`v`がポインタでない場合は`v`自身を返します。
*   `Type().AssignableTo(T Type)`: `v`の型が型`T`に割り当て可能（代入可能）であるかどうかをチェックします。
*   `Set(v reflect.Value)`: `v`の値を、呼び出し元の`reflect.Value`が表す変数に設定します。

`database/sql`パッケージは、`Scan`メソッドで任意のGoの型にデータを割り当てるために、この`reflect`パッケージを広範に利用しています。

### 4. 名前付きバイト型（Named `[]byte` types）

Goでは、既存の型に新しい名前を付けて新しい型を定義できます。例えば、`type MyBytes []byte`のように定義された`MyBytes`は、基盤となる型は`[]byte`ですが、`MyBytes`と`[]byte`は異なる型として扱われます。
`json.RawMessage`は、`type RawMessage []byte`として定義されており、JSONの生データをバイトスライスとして保持するために使用されます。このコミットのバグは、このような名前付き`[]byte`型が`Scan`のターゲットになった場合に特に問題となりました。

### 5. データ競合（Data Race）

複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みである場合に、データ競合が発生します。データ競合はGoプログラムの予測不能な動作やクラッシュの原因となり、デバッグが非常に困難です。このバグは、データベースドライバが内部バッファを再利用し、別のゴルーチンがそのバッファを上書きする可能性があったため、一種のデータ競合を引き起こしていました。

## 技術的詳細

このコミットの核心は、`database/sql`パッケージ内の`convertAssign`関数における型変換ロジックの改善です。`convertAssign`は、`Scan`メソッドがデータベースから読み取った`src`（ソース）データを、ユーザーが指定した`dest`（デスティネーション）変数に適切に変換して割り当てる役割を担っています。

バグの発生メカニズムは以下の通りでした。
1.  `Scan`メソッドがデータベースドライバから`[]byte`型のデータを受け取ります。
2.  この`[]byte`データは、ドライバが管理する内部メモリバッファへの参照です。
3.  `convertAssign`関数が、この`[]byte`データを、`json.RawMessage`のような名前付き`[]byte`型変数に割り当てようとします。
4.  従来のコードでは、`sv.Type().AssignableTo(dv.Type())`が`true`となる場合（基盤の型が同じため）、`dv.Set(sv)`という行で`src`スライスが`dest`変数に直接シャローコピーされていました。
5.  このシャローコピーにより、`dest`変数もデータベースドライバの内部メモリバッファを指すことになります。
6.  その後、データベースドライバが別の`Scan`操作のために同じ内部メモリバッファを再利用し、新しいデータで上書きした場合、`dest`変数が指すメモリの内容も意図せず変更されてしまい、アプリケーション側で保持していたはずのデータが破損するという問題が発生しました。

このコミットでは、この問題を解決するために、`convertAssign`関数に`switch`文が追加されました。
変更後のロジックは以下のようになります。
*   `sv.IsValid() && sv.Type().AssignableTo(dv.Type())`という条件は引き続き評価されます。これは、ソースデータが有効であり、かつデスティネーション変数に割り当て可能であるかを確認するものです。
*   この条件が満たされた場合、`src`の具体的な型をチェックするための`switch b := src.(type)`が導入されます。
*   もし`src`が`[]byte`型であった場合、`dv.Set(reflect.ValueOf(cloneBytes(b)))`が実行されます。ここで重要なのは`cloneBytes(b)`の呼び出しです。`cloneBytes`は、元の`[]byte`スライスの内容を新しいメモリ領域に完全にコピー（ディープコピー）して、新しい`[]byte`スライスを返します。この新しいスライスが`dv`に割り当てられるため、`dv`はデータベースドライバの内部バッファとは独立したメモリを参照するようになります。
*   `[]byte`型以外のケースでは、以前と同様に`dv.Set(sv)`が実行され、シャローコピーが行われます。これは、他の型ではこのメモリ破損の問題が発生しないため、パフォーマンスへの影響を最小限に抑えるための設計判断です。

この修正により、`json.RawMessage`のような名前付き`[]byte`型が`Scan`される際に、常にデータのディープコピーが行われるようになり、データベースドライバの内部メモリ再利用によるデータ破損のリスクが排除されました。

## コアとなるコードの解説

### `src/database/sql/convert.go` の変更

`convertAssign`関数は、`database/sql`パッケージ内で型変換と値の割り当てを行う中心的な関数です。
変更前は、`sv.Type().AssignableTo(dv.Type())`が真の場合、単純に`dv.Set(sv)`としていました。これは、`src`が`[]byte`型であっても、そのスライスヘッダを`dest`変数にコピーするだけで、基盤となるバイト配列は共有されたままでした。

変更後は、この`dv.Set(sv)`の前に`switch`文が追加されました。
```go
		switch b := src.(type) {
		case []byte:
			dv.Set(reflect.ValueOf(cloneBytes(b)))
		default:
			dv.Set(sv)
		}
```
この`switch`文は、`src`インターフェースの動的な型を検査します。
*   `case []byte:`: もし`src`が`[]byte`型（またはその基盤型が`[]byte`である名前付き型）である場合、`cloneBytes(b)`が呼び出されます。`cloneBytes`関数（このdiffには含まれていませんが、`database/sql`パッケージ内に存在するヘルパー関数で、バイトスライスをディープコピーします）は、`b`の内容を新しいメモリ領域にコピーした新しい`[]byte`スライスを返します。その新しいスライスが`reflect.ValueOf()`で`reflect.Value`に変換され、最終的に`dv.Set()`によって`dest`変数に割り当てられます。これにより、`dest`変数は元の`src`が参照していたメモリとは完全に独立したメモリを持つことになり、データ破損が防止されます。
*   `default:`: `src`が`[]byte`型ではない場合、以前と同様に`dv.Set(sv)`が実行されます。これは、他の型ではこの問題が発生しないため、既存の挙動を維持し、不要なコピーによるオーバーヘッドを避けるためです。

この変更により、`database/sql`は、データベースから取得した`[]byte`データを扱う際に、安全なディープコピーを保証するようになりました。

### `src/database/sql/convert_test.go` の変更

`TestUserDefinedBytes`という新しいテスト関数が追加されました。このテストの目的は、`convertAssign`関数が名前付き`[]byte`型に対して正しくディープコピーを実行していることを検証することです。

```go
func TestUserDefinedBytes(t *testing.T) {
	type userDefinedBytes []byte // 名前付き[]byte型を定義
	var u userDefinedBytes       // ターゲット変数
	v := []byte("foo")           // ソースデータ

	convertAssign(&u, v) // convertAssignを呼び出し

	// u[0]とv[0]のアドレスが同じであれば、シャローコピーが行われたことを意味する。
	// ディープコピーが正しく行われていれば、アドレスは異なるはず。
	if &u[0] == &v[0] {
		t.Fatal("userDefinedBytes got potentially dirty driver memory")
	}
}
```
このテストでは、まず`userDefinedBytes`という`[]byte`のエイリアス型を定義します。次に、`v`という`[]byte`スライスを作成し、`convertAssign`関数を使って`v`の内容を`u`（`userDefinedBytes`型）に割り当てます。

テストの核心は、`if &u[0] == &v[0]`という条件です。
*   `&u[0]`は、`u`スライスの最初の要素が格納されているメモリのアドレスを取得します。
*   `&v[0]`は、`v`スライスの最初の要素が格納されているメモリのアドレスを取得します。

もし`convertAssign`がディープコピーを行っていれば、`u`と`v`は異なる基盤配列を参照するため、`&u[0]`と`&v[0]`は異なるアドレスを指すはずです。もしアドレスが同じであれば、それはシャローコピーが行われ、`u`が`v`と同じ（そして潜在的に「ダーティな」）メモリを指していることを意味し、テストは失敗します。このテストの追加により、修正が意図通りに機能していることが保証されます。

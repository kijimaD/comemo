# [インデックス 25023] ファイルの概要

このコミットは、Go言語の`os`パッケージにおいて、`open(2)`システムコールが`EINTR`エラーを返した場合のハンドリングを改善するものです。特にmacOS環境下で、FUSE (Filesystem in Userspace) ファイルシステムを使用している際に、シグナルによって`open(2)`が中断され`EINTR`エラーが発生する問題に対処しています。これにより、`os.OpenFile`の呼び出しが予期せず失敗する可能性を低減し、堅牢性を向上させています。

## 元コミット内容

```
os: handle EINTR from open(2).

The man page for sigaction(2) on OS X doesn't guarantee that SA_RESTART
will work for open(2) on regular files:

    The affected system calls include open(2), read(2), write(2),
    sendto(2), recvfrom(2), sendmsg(2) and recvmsg(2) on a
    communications channel or a slow device (such as a terminal, but not
    a regular file) and during a wait(2) or ioctl(2).

I've never observed EINTR from open(2) for a traditional file system
such as HFS+, but it's easy to observe with a fuse file system that is
slightly slow (cf. https://goo.gl/UxsVgB). After this change, the
problem can no longer be reproduced when calling os.OpenFile.

Fixes #11180.
```

## 変更の背景

この変更は、macOS環境における`open(2)`システムコールの特定の挙動に起因するバグを修正するために導入されました。通常、システムコールがシグナルによって中断された場合、`EINTR`エラーが返されます。多くのUNIX系システムでは、`sigaction(2)`システムコールで`SA_RESTART`フラグを設定することで、一部のシステムコール（特に低速なデバイスに対するもの）が自動的に再開されることが期待されます。

しかし、macOSの`sigaction(2)`のmanページには、`open(2)`が通常のファイルに対して`SA_RESTART`の恩恵を受けることを保証しないと明記されています。具体的には、「通信チャネルまたは低速デバイス（端末など、ただし通常のファイルではない）に対する`open(2)`、`read(2)`、`write(2)`、`sendto(2)`、`recvfrom(2)`、`sendmsg(2)`、`recvmsg(2)`、および`wait(2)`または`ioctl(2)`中に影響を受ける」と記述されています。

このため、特にFUSE (Filesystem in Userspace) ベースのファイルシステムのように、通常のファイルシステムよりもわずかに遅延がある環境では、`open(2)`が`EINTR`を返すことが容易に再現されました。この問題はGoのIssue #11180として報告されており、`os.OpenFile`を呼び出した際にファイルオープンが失敗するという形で現れていました。このコミットは、この特定のシナリオで`EINTR`エラーが発生した場合に、`open(2)`システムコールを再試行することで問題を解決することを目的としています。

## 前提知識の解説

### `open(2)` システムコール

`open(2)`は、UNIX系オペレーティングシステムにおいて、ファイルやデバイスを開くためのシステムコールです。ファイルパス、オープンモード（読み書き、作成など）、およびパーミッションを指定して呼び出され、成功するとファイルディスクリプタ（整数値）を返します。このファイルディスクリプタは、その後の`read(2)`や`write(2)`などの操作で使用されます。

### `EINTR` エラー

`EINTR` (Interrupted system call) は、システムコールが完了する前にシグナルによって中断された場合に返されるエラーコードです。例えば、プログラムがファイルI/O操作中に`SIGINT`（Ctrl+C）などのシグナルを受け取ると、そのシステムコールは中断され、`EINTR`を返して呼び出し元に戻ることがあります。プログラムは通常、このエラーを適切に処理し、操作を再試行するか、エラーとして報告する必要があります。

### `SA_RESTART` フラグと `sigaction(2)`

`sigaction(2)`は、シグナルの処理方法を設定するためのシステムコールです。このシステムコールを通じて、特定のシグナルが配送された際のハンドラ関数や、シグナルマスクなどの詳細な動作を定義できます。
`SA_RESTART`は`sigaction(2)`で設定できるフラグの一つで、シグナルによって中断されたシステムコールをカーネルが自動的に再開しようと試みることを指示します。これにより、アプリケーションコードで`EINTR`エラーを明示的に処理する手間を省くことができます。しかし、前述の通り、すべてのシステムコールやすべてのOSで`SA_RESTART`が期待通りに機能するわけではありません。特にmacOSの`open(2)`と通常のファイルの場合がその例です。

### FUSE (Filesystem in Userspace)

FUSEは、ユーザー空間でファイルシステムを実装するためのフレームワークです。通常、ファイルシステムはカーネル空間で動作しますが、FUSEを使用すると、開発者はユーザー空間のプログラムとしてファイルシステムを実装し、それをカーネルモジュールが仲介してマウントできます。これにより、新しいファイルシステムの開発が容易になりますが、カーネル空間のファイルシステムに比べてパフォーマンスがわずかに低下したり、特定のシステムコール挙動が異なる場合があります。このコミットの背景にある問題は、FUSEファイルシステムが通常のファイルシステムよりも遅延があるために、`open(2)`がシグナルによって中断されやすくなるという状況で顕在化しました。

### Goにおける`syscall.Open`と`os.OpenFile`

Go言語では、低レベルなシステムコールを直接呼び出すために`syscall`パッケージが提供されています。`syscall.Open`は、OSの`open(2)`システムコールをGoから呼び出すためのラッパーです。
一方、`os.OpenFile`は、`syscall.Open`を内部的に利用しつつ、より高レベルでGoらしいエラーハンドリングやファイルモードの抽象化を提供します。このコミットは、`os.OpenFile`が内部で呼び出す`syscall.Open`の挙動を修正することで、`os.OpenFile`の堅牢性を向上させています。

## 技術的詳細

この問題の核心は、macOSの`open(2)`システムコールが、通常のファイルに対して`SA_RESTART`フラグが設定されていても、シグナルによって中断された際に`EINTR`を返す可能性があるという点にあります。これは、macOSの`sigaction(2)`のmanページに記載されているように、`open(2)`が「通常のファイル」に対しては再開が保証されないシステムコールの一つであるためです。

FUSEファイルシステムは、ユーザー空間で動作するため、通常のカーネル空間のファイルシステムに比べてI/O操作にわずかなオーバーヘッドや遅延が生じることがあります。このわずかな遅延が、`open(2)`システムコールが完了する前にシグナルが配送される可能性を高め、結果として`EINTR`エラーが頻繁に発生する原因となります。

Goの`os.OpenFile`関数は、内部で`syscall.Open`を呼び出してファイルを開きます。もし`syscall.Open`が`EINTR`を返した場合、従来のGoのコードではこれを一般的なエラーとして扱い、ファイルオープンが失敗していました。これは、アプリケーションがファイルを開こうとした際に、実際にはファイルが存在し、アクセス権もあるにもかかわらず、一時的なシグナルによって操作が中断されただけでエラーとなるという、予期せぬ挙動を引き起こしていました。

このコミットは、このmacOS特有の挙動とFUSEファイルシステムとの組み合わせによって引き起こされる問題を、`EINTR`エラーが発生した場合に`syscall.Open`を再試行するというシンプルなロジックで解決しています。これにより、一時的なシグナルによる中断は透過的に処理され、`os.OpenFile`の呼び出しがより堅牢になります。

## コアとなるコードの解説

変更は`src/os/file_unix.go`ファイルの`OpenFile`関数内で行われています。

1.  **`retry:` ラベルの追加**:
    `syscall.Open`の呼び出しの直前に`retry:`というラベルが追加されました。これは、Goの`goto`ステートメントのターゲットとして使用されます。

2.  **`syscall.Open`の呼び出し**:
    `r, e := syscall.Open(name, flag|syscall.O_CLOEXEC, syscallMode(perm))`
    ここで実際の`open(2)`システムコールが実行されます。`name`はファイルパス、`flag`はオープンモード（読み書き、作成など）、`syscall.O_CLOEXEC`は`exec`時にファイルディスクリプタをクローズするフラグ、`syscallMode(perm)`はパーミッションを表します。結果としてファイルディスクリプタ`r`とエラー`e`が返されます。

3.  **エラーハンドリングの追加**:
    `if e != nil { ... }` のエラーチェックブロック内で、新しいロジックが追加されました。
    `if e == syscall.EINTR { goto retry }`
    この部分がこのコミットの核心です。`syscall.Open`がエラーを返し、そのエラーが`syscall.EINTR`（システムコールがシグナルによって中断されたことを示す）である場合、コードは`goto retry`ステートメントを使って`retry:`ラベルの位置に戻り、`syscall.Open`を再試行します。

この変更により、macOS上で`open(2)`が一時的に`EINTR`エラーを返しても、Goの`os.OpenFile`は自動的に操作を再試行するため、アプリケーションレベルでは透過的に処理され、ファイルオープンが成功する可能性が高まります。これにより、FUSEファイルシステムなど特定の環境下でのファイル操作の堅牢性が向上します。

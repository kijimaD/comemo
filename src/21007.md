## 変更の背景

Goプロジェクトは、初期にはGoogle Codeの`code.google.com/p/go`でホストされていました。しかし、プロジェクトの成長とエコシステムの拡大に伴い、より柔軟で分散された開発モデルへの移行が必要となりました。この移行の一環として、Goの標準ライブラリには含まれないが、Goチームによって公式にメンテナンスされているツールやライブラリ（サブリポジトリ）が、`golang.org/x/`という新しいドメイン配下に移動されることになりました。

この変更は、GoプロジェクトがGoogle CodeからGitHubへの移行を進める中で行われた重要なステップの一つです。`golang.org/x/`というパスは、Goの公式ウェブサイトが管理するドメインであり、これによりサブリポジトリのインポートパスがより安定し、Goプロジェクトの公式な位置づけが明確になります。このコミットは、Go 1.4のリリースノートにこの重要な変更を反映させ、ユーザーに新しいインポートパスへの移行を促すためのものです。特に、2015年6月1日頃には古い`code.google.com`パスがGo 1.4以降で受け入れられなくなるという期限が設定されており、ユーザーへの周知が急務でした。

## 前提知識の解説

*   **Goのインポートパス**: Go言語では、パッケージをインポートする際に、そのパッケージのソースコードがどこにあるかを示す「インポートパス」を使用します。例えば、`import "fmt"`は標準ライブラリの`fmt`パッケージをインポートしますが、`import "github.com/user/repo/package"`のように、外部のパッケージは通常、そのリポジトリのURLを基にしたパスでインポートされます。
*   **Goのサブリポジトリ (Subrepositories)**: Goプロジェクトには、標準ライブラリとは別に、Goチームが公式に開発・メンテナンスしているが、標準ライブラリには含まれないツールやライブラリ群が存在します。これらは「サブリポジトリ」と呼ばれ、以前は`code.google.com/p/go.tools`や`code.google.com/p/go.mobile`などのパスで提供されていました。これらはGoの公式なエコシステムの一部として非常に重要です。
*   **`go get`コマンド**: `go get`は、指定されたインポートパスに基づいてGoのパッケージとその依存関係をダウンロードし、インストールするためのコマンドです。このコマンドは、インポートパスを解析して、対応するバージョン管理システム（Git, Mercurialなど）のリポジトリからソースコードを取得します。
*   **Canonical Import Comments**: Goのソースコードには、`//go:build ignore`のようなビルドタグの他に、`// import "example.com/path/to/package"`のような「canonical import comment」を記述することができます。これは、パッケージの「公式な」インポートパスを示すもので、`go get`などのツールがリダイレクトを処理する際に利用されます。このコミットの背景にある変更では、古いパスから新しいパスへのリダイレクトを`go get`が適切に処理するために、このコメントが利用されることが示唆されています。

## 技術的詳細

このコミットは、Go 1.4のリリースノートである`doc/go1.4.html`を修正し、Goプロジェクトのサブリポジトリのインポートパスが`code.google.com/p/go.*`から`golang.org/x/*`へ変更されたことを明記しています。この変更は、GoプロジェクトがGoogle CodeからGitHubへの移行を進める中で、インポートパスの永続性と安定性を確保するために行われました。

具体的には、以下の点が技術的な詳細として挙げられます。

1.  **インポートパスの変更**:
    *   古いパスの例: `code.google.com/p/go.tools`, `code.google.com/p/go.mobile`, `code.google.com/p/go.sys`
    *   新しいパスの例: `golang.org/x/tools`, `golang.org/x/mobile`, `golang.org/x/sys`
    この変更は、Goのパッケージ管理において非常に重要です。Goのツールチェーン、特に`go get`コマンドは、インポートパスに基づいてソースコードのリポジトリを特定します。したがって、このパスの変更は、既存のコードベースが新しいパスを使用するように更新される必要があることを意味します。

2.  **移行期間と互換性**:
    *   ドキュメントには、「2015年6月1日頃に、Go 1.4以降は古い`code.google.com`パスを受け入れなくなる」と明記されています。これは、ユーザーがコードを更新するための明確な期限を示しています。
    *   重要な点として、「Go 1.0以降は新しい`golang.org`パスを解決してインポートできるため、更新しても古いリリースとの互換性は損なわれない」と述べられています。これは、新しいパスへの移行が、古いGoのバージョンを使用しているユーザーに即座に問題を引き起こすわけではないことを意味します。しかし、期限を過ぎるとGo 1.4以降では古いパスのコードはコンパイルできなくなります。
    *   この互換性は、`go get`がカスタムインポートパスを解決するメカニズム（HTMLメタタグや、後に導入されるcanonical import comments）を利用しているためと考えられます。これにより、`golang.org/x/tools`のようなパスが、実際にはGitHub上のリポジトリ（例: `github.com/golang/tools`）にマッピングされるようになります。

3.  **`go generate`コマンドへの影響**:
    *   `go generate`コマンドのセクションでも、`stringer`ツールのインポートパスが`code.google.com/p/go.tools/cmd/stringer`から`golang.org/x/tools/cmd/stringer`に更新されています。これは、`go generate`を使用する既存のプロジェクトも、このパス変更の影響を受けることを示しています。

4.  **`go.sys`サブリポジトリの導入**:
    *   このコミットでは、新しいサブリポジトリである`go.sys`（新しいパスは`golang.org/x/sys`）が導入されたこともドキュメントに追記されています。これは、システムコールをサポートするための新しい場所として機能し、`unix`、`windows`、`plan9`の各パッケージが含まれることが説明されています。
    *   既存の`syscall`パッケージはGo 1.3から大きく変更されていないため、既存のプログラムには影響がないとされていますが、将来的に`syscall`パッケージにないシステムコールが必要な場合は、`golang.org/x/sys`を使用すべきであると推奨されています。これは、Goのシステムコール関連のコードがより整理され、進化していく方向性を示しています。

このドキュメントの更新は、Goエコシステム全体の整合性を保ち、将来的な開発の基盤を強化するための重要な一歩でした。ユーザーは、この変更を理解し、自身のプロジェクトのインポートパスを適切に更新することが求められました。

## コアとなるコードの解説

このコミットの「コード」は、Go 1.4のリリースノートのHTMLドキュメント`doc/go1.4.html`です。このドキュメントの変更は、Goエコシステムにおける重要なインフラストラクチャの変更をユーザーに伝えるためのものです。

*   **`go.mobile`のインポートパスの更新**:
    Go 1.4でAndroid向けのバイナリビルドがサポートされることに関連して、`go.mobile`リポジトリのサポートパッケージへのリンクが`http://code.google.com/p/go.mobile`から`http://golang.org/x/mobile`に変更されています。これは、Goのモバイル開発関連のツールが新しい`golang.org/x`パスに移行したことを示しています。

*   **サブリポジトリのインポートパスに関する新しいセクションの追加**:
    このセクションは、このコミットの最も重要な部分です。
    *   `code.google.com/p/go.tools`などのGoプロジェクトのサブリポジトリが、`golang.org/x/tools`のように`golang.org/x/`をプレフィックスとするカスタムインポートパスで利用可能になったことを明確に述べています。
    *   2015年6月1日頃に、コードにcanonical import commentsが追加され、その時点でGo 1.4以降は古い`code.google.com`パスを受け入れなくなるという重要な期限が示されています。これは、ユーザーが自身のコードベースを更新する必要があることを強調しています。
    *   既存のコードを更新するよう促し、Go 1.0以降であれば新しいパスを解決できるため、古いリリースとの互換性を損なうことなく更新できることを保証しています。これは、開発者が安心して移行を進められるようにするための重要な情報です。

*   **`stringer`ツールのインポートパスの更新**:
    `go generate`コマンドのセクションで、`stringer`ツールのリンクが`http://godoc.org/code.google.com/p/go.tools/cmd/stringer`から`http://godoc.org/golang.org/x/tools/cmd/stringer`に変更されています。これは、`go generate`を使用する開発者も、関連するツールが新しいインポートパスに移行したことを認識する必要があることを示しています。

*   **`go.sys`サブリポジトリのインポートパスの更新と説明の追加**:
    新しいサブリポジトリである`go.sys`（新しいパスは`golang.org/x/sys`）が導入されたことが説明されています。このサブリポジトリは、システムコールをサポートするためのもので、`unix`、`windows`、`plan9`の各パッケージが含まれます。これは、Goが異なるオペレーティングシステムでのシステムコールインターフェースをより柔軟に扱うための新しいアプローチを示しており、将来のシステムコール関連の開発は`golang.org/x/sys`を基盤とすべきであると推奨されています。

これらの変更は、Goプロジェクトの進化と、そのエコシステムがどのように組織され、アクセスされるかについての重要な指針をユーザーに提供しています。

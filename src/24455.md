    runtime/trace: record event sequence numbers explicitly

    Nearly all the flaky failures we've seen in trace tests have been
    due to the use of time stamps to determine relative event ordering.
    This is tricky for many reasons, including:
     - different cores might not have exactly synchronized clocks
     - VMs are worse than real hardware
     - non-x86 chips have different timer resolution than x86 chips
     - on fast systems two events can end up with the same time stamp

    Stop trying to make time reliable. It's clearly not going to be for Go 1.5.
    Instead, record an explicit event sequence number for ordering.
    Using our own counter solves all of the above problems.

    The trace still contains time stamps, of course. The sequence number
    is just used for ordering.

    Should alleviate #10554 somewhat. Then tickDiv can be chosen to
    be a useful time unit instead of having to be exact for ordering.

    Separating ordering and time stamps lets the trace parser diagnose
    systems where the time stamp order and actual order do not match
    for one reason or another. This CL adds that check to the end of
    trace.Parse, after all other sequence order-based checking.
    If that error is found, we skip the test instead of failing it.
    Putting the check in trace.Parse means that cmd/trace will pick
    up the same check, refusing to display a trace where the time stamps
    do not match actual ordering.

## 元コミット内容

Goランタイムのトレース機能において、イベントの相対的な順序を決定するためにタイムスタンプを使用するのではなく、明示的なイベントシーケンス番号を記録するように変更します。これにより、タイムスタンプの信頼性の問題に起因するトレーステストの不安定な失敗（flaky failures）を解決します。

## 変更の背景

Goランタイムのトレース機能は、プログラムの実行状況を詳細に記録し、パフォーマンス分析やデバッグに役立てるための重要なツールです。しかし、これまでの実装では、トレースイベントの順序を決定するためにタイムスタンプに依存していました。このアプローチには、以下のような複数の問題がありました。

*   **クロックの非同期性**: 異なるCPUコアは完全に同期されたクロックを持っているとは限りません。特にマルチコアシステムでは、各コアのタイマーがわずかにずれることがあります。
*   **仮想環境での問題**: 仮想マシン（VM）環境では、ハードウェアの抽象化層が追加されるため、タイムスタンプの精度や同期の問題がさらに悪化します。
*   **タイマー解像度の違い**: x86以外のアーキテクチャでは、タイマーの解像度がx86チップと異なる場合があり、これがイベント間の時間差の正確な測定を困難にします。
*   **高速システムでのタイムスタンプ衝突**: 非常に高速なシステムでは、複数のイベントが同じタイムスタンプを持つことがあり、これによりイベントの正確な順序を特定できなくなります。

これらの問題により、トレーステストが不安定に失敗する（flaky failures）という状況が頻繁に発生していました。特に、Go 1.5のリリースに向けて、このタイムスタンプの信頼性の問題が解決されないことが明らかになりました。このコミットは、これらの問題を根本的に解決するために、タイムスタンプに代わる信頼性の高いイベント順序付けメカニズムを導入することを目的としています。また、この変更はIssue #10512を修正し、Issue #10554で報告されていた不安定なテストの問題を軽減することが期待されています。

## 前提知識の解説

### Goランタイムトレーシングの目的
Goランタイムトレーシングは、Goプログラムの実行中に発生する様々なイベント（ガーベージコレクション、ゴルーチンのスケジューリング、システムコールなど）を記録する機能です。これにより、開発者はプログラムのパフォーマンスボトルネックを特定したり、並行処理の挙動を理解したりすることができます。トレースデータは、`go tool trace`コマンドで視覚化され、詳細な分析が可能です。

### タイムスタンプの課題
コンピュータシステムにおけるタイムスタンプは、イベントが発生した時刻を記録するために広く使用されます。しかし、上記で述べたように、特に分散システムやマルチコア環境では、タイムスタンプの正確な比較や順序付けには多くの課題が伴います。CPUのサイクルカウンタ（`cputicks`）は非常に高精度ですが、異なるCPUコア間での同期が保証されないため、絶対的な時間順序を保証するものではありません。

### イベントシーケンス番号の必要性
タイムスタンプの信頼性の問題を回避するため、イベントの発生順序を保証する別のメカニズムが必要となります。イベントシーケンス番号は、イベントが発生するたびに単調増加するカウンタであり、これによりイベントの論理的な順序を確実に追跡できます。たとえタイムスタンプが同じであっても、シーケンス番号が異なれば、それらのイベントの相対的な順序を明確に区別できます。

### `cputicks()`と`nanotime()`
*   `cputicks()`: CPUのサイクルカウンタの値を返します。非常に高精度で、短い時間間隔の測定に適していますが、異なるCPUコア間での同期は保証されません。
*   `nanotime()`: システムのモノトニッククロック（単調増加するクロック）のナノ秒単位の値を返します。これは壁時計時間（wall-clock time）とは異なり、システム時刻の変更に影響されません。`cputicks()`よりも解像度は低いですが、システム全体で一貫した時間を提供します。

このコミットでは、`cputicks()`は引き続きイベントの発生時刻の「目安」として記録されますが、イベントの順序付けには`tracestamp()`によって生成されるシーケンス番号が使用されます。

### アトミック操作
アトミック操作は、複数のCPUコアやゴルーチンから同時にアクセスされた場合でも、その操作が中断されずに完全に実行されることを保証する操作です。`atomicload64`、`cas64`（Compare-And-Swap）、`atomicstore64`は、64ビット整数に対するアトミックな読み込み、比較と交換、書き込みを行う関数です。これらは、複数のゴルーチンが共有カウンタ（`traceseq`）を安全に更新するために不可欠です。

### `go:nosplit`
`//go:nosplit`ディレクティブは、Goコンパイラに対して、その関数がスタックを拡張しないように指示します。これは、スタックの拡張処理中に発生する可能性のあるプリエンプション（横取り）を避けたい場合に特に重要です。`tracestamp()`のような時間測定やアトミック操作を含むクリティカルなセクションでは、プリエンプションによる遅延や競合状態を避けるために`nosplit`が使用されることがあります。

## 技術的詳細

このコミットの主要な変更点は、Goランタイムトレーシングシステムに明示的なイベントシーケンス番号を導入し、イベントの順序付けをタイムスタンプからシーケンス番号に切り替えたことです。

### `Event`構造体の変更
`src/internal/trace/parser.go`内の`Event`構造体に`Seq int64`フィールドが追加されました。これにより、各トレースイベントはタイムスタンプ（`Ts`）だけでなく、一意のシーケンス番号を持つようになります。また、`Args`フィールドのサイズが`[2]uint64`から`[3]uint64`に拡張され、シーケンス番号を格納するための追加スペースが確保されました。

```go
type Event struct {
	Off   int       // offset in input file (for debugging and error reporting)
	Type  byte      // one of Ev*
	Seq   int64     // sequence number // 追加
	Ts    int64     // timestamp in nanoseconds
	P     int       // P on which the event happened (can be one of TimerP, NetpollP, SyscallP)
	G     uint64    // G on which the event happened
	StkID uint64    // unique stack ID
	Stk   []*Frame  // stack trace (can be empty)
	Args  [3]uint64 // event-type-specific arguments // サイズ変更
	// ...
}
```

### トレースヘッダの変更
トレースファイルのヘッダが`"gotrace\x00"`から`"go 1.5 trace\x00\x00\x00\x00"`に変更されました。これにより、Go 1.5以降のトレースファイル形式であることを明示し、古いパーサーとの互換性を保ちつつ、新しい形式を識別できるようになります。`readTrace`関数でのヘッダ読み込みサイズも8バイトから16バイトに増えました。

### `tracestamp()`関数の導入
`src/runtime/trace.go`に`tracestamp()`関数が導入されました。この関数は、アトミック操作を使用してグローバルなシーケンスカウンタ`traceseq`を安全にインクリメントし、現在のCPUティック値（`cputicks()`）と共に返します。

```go
var traceseq uint64 // global trace sequence number

//go:nosplit
func tracestamp() (seq uint64, ts int64) {
	seq = atomicload64(&traceseq)
	for seq&1 != 0 || !cas64(&traceseq, seq, seq+1) {
		seq = atomicload64(&traceseq)
	}
	ts = cputicks()
	atomicstore64(&traceseq, seq+2)
	return seq >> 1, ts
}
```
この関数は、`traceseq`が偶数であることを確認し、`cas64`（Compare-And-Swap）で`seq+1`に設定することで、他のゴルーチンが同時に`traceseq`を更新するのを防ぎます。`cputicks()`を読み取った後、`traceseq`を`seq+2`に設定して、次のイベントのために偶数に戻します。これにより、`seq`は常に偶数で始まり、`seq+1`で一時的に奇数になり、`seq+2`で次の偶数になるというサイクルを繰り返します。返される`seq`は`seq >> 1`とすることで、実際のイベントシーケンス番号として使用されます。

### イベントの記録方法の変更（シーケンス番号の追加）
`traceEvent`関数（`src/runtime/trace.go`）が変更され、イベントを記録する際に`tracestamp()`から取得したシーケンス番号とタイムスタンプを使用するようになりました。これにより、各イベントにはシーケンス番号とタイムスタンプの両方が含まれるようになります。

### トレース解析時のソート順序の変更
`src/internal/trace/parser.go`内の`eventList`型に実装されている`Less`メソッドが、`l[i].Ts < l[j].Ts`（タイムスタンプによる比較）から`l[i].Seq < l[j].Seq`（シーケンス番号による比較）に変更されました。これにより、トレースイベントはタイムスタンプではなく、明示的なシーケンス番号に基づいてソートされるようになり、イベントの論理的な順序が保証されます。

```go
func (l eventList) Less(i, j int) bool {
	return l[i].Seq < l[j].Seq // タイムスタンプからシーケンス番号に変更
}
```

### タイムスタンプ順序の検証
`src/internal/trace/parser.go`の`postProcessTrace`関数に、シーケンス番号に基づいてソートされたイベントのタイムスタンプが単調増加しているかをチェックする新しい検証ロジックが追加されました。もしタイムスタンプの順序がシーケンス番号の順序と一致しない場合（つまり、`ev.Ts < lastTs`となる場合）、`ErrTimeOrder`エラーが返されます。このエラーが発生した場合、トレーステストは失敗するのではなくスキップされるようになります。これにより、タイムスタンプの信頼性の問題が診断可能になります。

```go
// Last, after all the other consistency checks,
// make sure time stamps respect sequence numbers.
// The tests will skip (not fail) the test case if they see this error,
// so check everything else that could possibly be wrong first.
var ErrTimeOrder = fmt.Errorf("time stamps out of order") // 新しいエラー定義

func postProcessTrace(events []*Event) error {
	// ...
	lastTs := int64(0)
	for _, ev := range events {
		if ev.Ts < lastTs {
			return ErrTimeOrder // タイムスタンプの逆転を検出
		}
		lastTs = ev.Ts
	}
	return nil
}
```

### `EvGoSysExit`イベントの変更
`EvGoSysExit`イベント（システムコール終了イベント）の記録方法も変更されました。以前はタイムスタンプのみを記録していましたが、このコミットによりシーケンス番号も記録するようになりました。これにより、システムコール終了イベントの正確な順序付けが可能になります。

### ベンチマーク結果の分析
コミットメッセージには、`net/http`の`BenchmarkClientServerParallel4`を使用したベンチマーク結果が示されています。トレースを有効にした場合、`time/op`（操作あたりの時間）が約60%から90%増加していることがわかります。これは、シーケンス番号の記録やアトミック操作の追加によるオーバーヘッドを示していますが、トレースの正確性と信頼性を向上させるための許容可能なコストと見なされています。

## コアとなるコードの解説

### `Event` struct (`src/internal/trace/parser.go`)
```go
type Event struct {
	// ...
	Seq   int64     // sequence number
	Ts    int64     // timestamp in nanoseconds
	// ...
	Args  [3]uint64 // event-type-specific arguments
	// ...
}
```
この構造体は、トレースファイルから読み込まれた個々のイベントを表します。`Seq`フィールドの追加により、イベントの論理的な順序が保証されるようになりました。`Args`のサイズ変更は、イベントタイプによっては追加の引数（シーケンス番号など）を格納する必要があるためです。

### `tracestamp()` (`src/runtime/trace.go`)
```go
//go:nosplit
func tracestamp() (seq uint64, ts int64) {
	seq = atomicload64(&traceseq)
	for seq&1 != 0 || !cas64(&traceseq, seq, seq+1) {
		seq = atomicload64(&traceseq)
	}
	ts = cputicks()
	atomicstore64(&traceseq, seq+2)
	return seq >> 1, ts
}
```
この関数は、このコミットの核心部分の一つです。`traceseq`というグローバルなカウンタをアトミックに操作することで、複数のゴルーチンが同時にイベントを記録しようとしても、一貫したシーケンス番号が割り当てられることを保証します。`seq&1 != 0`のチェックは、他のゴルーチンが現在`traceseq`を更新中である（一時的に奇数になっている）ことを検出し、その完了を待つためのスピンロックのような役割を果たします。`seq >> 1`とすることで、実際のシーケンス番号は`traceseq`の半分として扱われ、`traceseq`の偶数/奇数状態を利用して競合を管理します。

### `traceEvent()` (`src/runtime/trace.go`)
```go
func traceEvent(ev byte, skip int, args ...uint64) {
	// ...
	seq, ticksraw := tracestamp() // シーケンス番号と生ティック値を取得
	seqDiff := seq - buf.lastSeq
	ticks := uint64(ticksraw) / traceTickDiv
	tickDiff := ticks - buf.lastTicks
	// ...
	data = traceAppend(data, seqDiff) // シーケンス番号の差分を記録
	data = traceAppend(data, tickDiff) // ティック値の差分を記録
	for _, a := range args {
		data = traceAppend(data, a)
	}
	// ...
	buf.lastSeq = seq
	buf.lastTicks = ticks
}
```
`traceEvent`は、個々のトレースイベントをバッファに書き込む役割を担います。ここで`tracestamp()`が呼び出され、イベントにシーケンス番号とタイムスタンプが付与されます。`seqDiff`と`tickDiff`は、前のイベントからの差分を記録することで、トレースデータのサイズを削減する最適化です。

### `parseEvents()` (sorting logic) (`src/internal/trace/parser.go`)
```go
func parseEvents(rawEvents []rawEvent) (events []*Event, err error) {
	// ...
	// Sort by sequence number and translate cpu ticks to real time.
	sort.Sort(eventList(events)) // タイムスタンプではなくシーケンス番号でソート
	// ...
}

func (l eventList) Less(i, j int) bool {
	return l[i].Seq < l[j].Seq // シーケンス番号で比較
}
```
トレースデータを解析する際、`parseEvents`関数は`eventList`インターフェースを介してイベントをソートします。このコミットにより、ソートの基準が`Event.Ts`（タイムスタンプ）から`Event.Seq`（シーケンス番号）に変更されました。これにより、トレースイベントは常に論理的な発生順序で処理されることが保証され、タイムスタンプの不正確さに起因する問題が解消されます。

### `postProcessTrace()` (time order check) (`src/internal/trace/parser.go`)
```go
// Last, after all the other consistency checks,
// make sure time stamps respect sequence numbers.
// The tests will skip (not fail) the test case if they see this error,
// so check everything else that could possibly be wrong first.
var ErrTimeOrder = fmt.Errorf("time stamps out of order") // 新しいエラー定義

func postProcessTrace(events []*Event) error {
	// ...
	lastTs := int64(0)
	for _, ev := range events {
		if ev.Ts < lastTs {
			return ErrTimeOrder // タイムスタンプの逆転を検出
		}
		lastTs = ev.Ts
	}
	return nil
}
```
この関数は、トレースデータの整合性を最終的に検証する役割を担います。シーケンス番号でソートされたイベントリストに対して、タイムスタンプが単調増加しているかをチェックすることで、システムクロックの異常や同期の問題を診断できるようになりました。`ErrTimeOrder`が返された場合、テストはスキップされるため、不安定なテストがCI/CDパイプラインをブロックするのを防ぎつつ、問題の存在を通知できます。また、`cmd/trace`ツールもこのチェックを利用して、タイムスタンプの順序が不正なトレースの表示を拒否するようになります。

# [インデックス 23832] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) における共有ライブラリからのシンボル読み込み時の挙動を修正するものです。具体的には、BSSセクションに存在する重複シンボルを許可するように変更し、Cgoを使用する実行ファイルが共有ライブラリにリンクされる際に発生していた `cgoAlwaysFalse` に関するエラーを解決します。

変更されたファイルは以下の通りです。

*   `misc/cgo/testshared/shared_test.go`: Cgoと共有ライブラリを使用する実行ファイルのテストケースが追加されています。
*   `misc/cgo/testshared/src/execgo/exe.go`: Cgoを使用するシンプルな実行ファイルのソースコードが新規追加されています。これは上記のテストケースで利用されます。
*   `src/cmd/link/internal/ld/lib.go`: リンカが共有ライブラリからシンボルを読み込む際のロジックが修正されています。

## 変更の背景

Go言語のリンカ (`cmd/link`) は、通常、重複するシンボルを検出するとエラーを報告します。これは、プログラム内で同じ名前の関数や変数が複数定義されている場合に、どの定義を使用すべきかリンカが判断できないため、曖昧さを排除し、予期せぬ動作を防ぐための重要なメカニズムです。

しかし、共有ライブラリ（特にCgoを介して利用されるもの）からシンボルを読み込む際、特定の状況下でこの厳格な重複チェックが問題を引き起こしていました。具体的には、Cgoを使用するGoの実行ファイルを共有ライブラリにリンクする際に、`cgoAlwaysFalse` というシンボルが重複しているとリンカが判断し、エラーでビルドが失敗するという問題です。

`cgoAlwaysFalse` は、Cgoの内部的なメカニズムで使用される、通常は初期化されていないグローバル変数であり、BSS (Block Started by Symbol) セクションに配置されます。BSSセクションのシンボルは、プログラムの実行開始時にゼロで初期化されることが保証されています。このような特性を持つシンボルが、異なるオブジェクトファイルや共有ライブラリで重複して定義されていても、その意味は通常同じ（ゼロ値）であるため、リンカがエラーを出す必要はありません。むしろ、このような重複は許容されるべきであり、通常のオブジェクトファイルからのシンボル読み込みでは既に許容されていました。

このコミットは、共有ライブラリからのシンボル読み込み時にも、通常のオブジェクトファイルからの読み込み時と同様に、BSSセクション内の重複シンボルを特別扱いすることで、この問題を解決し、Cgoと共有ライブラリの連携をスムーズにすることを目的としています。

## 前提知識の解説

### Goリンカ (`cmd/link`)
Go言語のビルドツールチェーンの一部であり、Goのソースコードから生成されたオブジェクトファイル（`.o` ファイル）やアーカイブファイル（`.a` ファイル）、共有ライブラリなどを結合して、最終的な実行ファイルや共有ライブラリを生成する役割を担います。シンボル解決、アドレスの再配置、セクションの結合などを行います。

### 共有ライブラリ (Shared Libraries)
複数のプログラムで共有されるライブラリの形式です。プログラムの実行時にメモリにロードされ、複数のプロセスが同じライブラリのコードを共有することで、メモリ使用量の削減やディスク容量の節約に貢献します。Go言語では、Cgoを介してC/C++の共有ライブラリを利用したり、Goプログラム自体を共有ライブラリとしてビルドしたりすることが可能です。

### Cgo
Go言語とC言語（およびC互換の言語、C++など）のコードを相互運用するためのGoの機能です。Cgoを使用することで、既存のCライブラリをGoプログラムから呼び出したり、Goの関数をCコードから呼び出したりすることができます。

### シンボル (Symbols)
プログラムのソースコード内で定義される関数、グローバル変数、静的変数などの識別子です。コンパイルされたオブジェクトファイルや実行ファイルには、これらのシンボルとそのメモリ上のアドレスや型などの情報が格納されたシンボルテーブルが含まれます。リンカはシンボルテーブルを参照して、異なるオブジェクトファイル間の参照を解決します。

### BSSセクション (Block Started by Symbol Section)
実行ファイルやオブジェクトファイル内のデータセクションの一つです。初期化されていない静的変数やグローバル変数が配置されます。BSSセクションに配置されたデータは、プログラムのロード時にはディスク上のファイルには含まれず、プログラムの実行開始時にOSによってゼロで初期化されることが保証されます。これにより、実行ファイルのサイズを小さく保つことができます。

### ELF (Executable and Linkable Format)
Unix系オペレーティングシステム（Linuxなど）で広く使用されている、実行ファイル、共有ライブラリ、オブジェクトファイルなどのバイナリ形式です。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション（`.text`、`.data`、`.bss`など）で構成されます。

### `obj.SDYNIMPORT`, `obj.SBSS`, `obj.SNOPTRBSS`
これらはGoリンカの内部で使用されるシンボルタイプを表す定数です。
*   `obj.SDYNIMPORT`: 動的にインポートされるシンボル（共有ライブラリから解決されるシンボル）を示します。
*   `obj.SBSS`: BSSセクションに配置されるシンボルを示します。
*   `obj.SNOPTRBSS`: ポインタを含まないBSSセクションに配置されるシンボルを示します。ガベージコレクションの対象とならないBSSデータに使用されます。

### `elf.ST_TYPE`, `elf.SHT_NOBITS`
これらはELFファイルの構造に関連する定数です。
*   `elf.ST_TYPE`: ELFシンボル情報の `st_info` フィールドからシンボルタイプ（関数、オブジェクト、セクションなど）を抽出するためのマスクです。
*   `elf.SHT_NOBITS`: ELFセクションヘッダの `sh_type` フィールドで、セクションがファイル内にデータを保持しないことを示します。BSSセクションは通常このタイプです。

## 技術的詳細

このコミットの核心は、`src/cmd/link/internal/ld/lib.go` 内の `ldshlibsyms` 関数にあります。この関数は、共有ライブラリからシンボルを読み込み、Goリンカの内部シンボルテーブルに登録する役割を担っています。

変更前は、`ldshlibsyms` 関数内で共有ライブラリから読み込んだシンボル (`s`) が、既にGoリンカのシンボルテーブルに存在し (`lsym.Type != 0`)、それが動的インポートシンボルではなく (`lsym.Type != obj.SDYNIMPORT`)、かつ重複が許可されていない (`lsym.Dupok == 0`) 場合、リンカは「重複シンボルが見つかりました」というエラー (`Diag`) を出力していました。

このコミットでは、この重複シンボルチェックのロジックがより洗練されています。新しいロジックでは、以下の条件が追加されました。

1.  **BSSセクションの重複シンボルを許可**:
    リンカは、既存のシンボル (`lsym`) がBSSセクション (`obj.SBSS` または `obj.SNOPTRBSS`) にあり、かつ、共有ライブラリから読み込んだシンボル (`elfsym`) が参照 (`lsym.R` や `lsym.P`) を持たず、さらにそのセクションがELFの `SHT_NOBITS` タイプ（BSSセクションの典型的な特徴）である場合に限り、重複をエラーとしないように変更されました。
    これは、BSSセクションのシンボルは通常ゼロ初期化されるため、複数の場所で定義されていても意味的に衝突しないという前提に基づいています。

2.  **BSSシンボルのサイズ比較**:
    もし既存のシンボル (`lsym`) がBSSシンボルであり、そのサイズが共有ライブラリから読み込んだシンボル (`elfsym`) のサイズよりも大きい場合、既存のシンボルを優先して参照を維持します。これは、より大きなBSS領域が必要な場合に、そのサイズを尊重するためです。逆に、共有ライブラリからのシンボルの方が大きい場合は、そのサイズが採用されるように、既存のシンボルを上書きします。

この変更により、`cgoAlwaysFalse` のようなBSSセクションに配置されるシンボルが、Goのオブジェクトファイルと共有ライブラリの両方で定義されていても、リンカがエラーを報告することなく、正しくリンクできるようになりました。

また、`misc/cgo/testshared/shared_test.go` に `TestCgoExecutable` という新しいテストケースが追加され、Cgoを使用する実行ファイルが共有ライブラリにリンクされるシナリオがカバーされるようになりました。このテストは、`misc/cgo/testshared/src/execgo/exe.go` に新しく追加されたシンプルなCgo実行ファイルをビルドし、実行することで、修正が正しく機能することを確認します。

## コアとなるコードの解説

変更の中心は、`if lsym.Type != 0 && lsym.Type != obj.SDYNIMPORT && lsym.Dupok == 0` の条件ブロック内です。

**変更前:**
この条件が真の場合、無条件に重複シンボルエラー (`Diag`) が報告されていました。

**変更後:**
1.  **BSSシンボルに対する追加チェック:**
    `if (lsym.Type != obj.SBSS && lsym.Type != obj.SNOPTRBSS) || len(lsym.R) != 0 || len(lsym.P) != 0 || f.Sections[elfsym.Section].Type != elf.SHT_NOBITS`
    この新しい `if` 文は、既存のシンボル (`lsym`) がBSSセクションにない場合、または参照を持っている場合、または共有ライブラリからのシンボル (`elfsym`) がBSSセクションではない場合、従来通り重複エラーを報告します。
    しかし、既存のシンボルと共有ライブラリからのシンボルが両方ともBSSセクションにあり、かつ参照を持たない場合は、この `if` 文の条件が偽となり、エラーは報告されません。これにより、BSSセクションの重複シンボルが許容されるようになります。

2.  **BSSシンボルのサイズ比較と優先順位付け:**
    `if lsym.Size > int64(elfsym.Size)`
    このブロックは、既存のシンボルがBSSシンボルであり、そのサイズが共有ライブラリから読み込んだシンボルのサイズよりも大きい場合に実行されます。この場合、既存のシンボル（より大きなサイズを持つ方）が優先され、`continue` によって現在の `elfsym` の処理をスキップし、既存の `lsym` の情報が保持されます。
    コメントにもあるように、これは「既存のシンボルが共有ライブラリから読み込んだものよりも大きいBSS値である場合、その参照を保持する。逆に、共有ライブラリからのバージョンが大きい場合は、すべての参照をそちらにする」というロジックを実装しています。つまり、`lsym.Size <= int64(elfsym.Size)` の場合は、後続のコードで `lsym.Size = int64(elfsym.Size)` が実行され、共有ライブラリからのより大きなサイズが採用されます。

これらの変更により、リンカは共有ライブラリからシンボルを読み込む際に、BSSセクションに存在する重複シンボルに対してより柔軟な対応をするようになり、`cgoAlwaysFalse` のような特定のケースでのリンクエラーが解消されました。

また、`lsym.Size = int64(elfsym.Size)` の行が追加され、シンボルのサイズ情報も共有ライブラリから正しく伝播されるようになりました。`readelfsymboldata` 関数の呼び出しも、`&s` から `&elfsym` に変更され、ループ変数名に合わせて修正されています。

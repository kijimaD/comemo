# [インデックス 27512] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおいて、送信されるHTTPヘッダーフィールドのキーと値の検証機能を追加するものです。これにより、不正なヘッダーがネットワークに送信される前に捕捉され、ユーザーにエラーとして通知されるようになります。これは、サーバー側でのエラー処理に依存するのではなく、クライアント側で早期に問題を検出する「フェイルファスト」の原則に基づいています。

## 元コミット内容

`net/http` パッケージが不正なヘッダーフィールドのキーや値を送信しようとしないようにし、代わりにサーバーがエラーを返すことに依存するのではなく、ユーザーにエラーを返して早期に失敗するようにします。

`x/net/http2.Transport` を直接使用して不正なデータを送信することはまだ可能ですが、この変更は `net/http` パッケージを介したHTTP/1.1およびHTTP/2の使用のみを停止します。将来の変更で `x/net/http2` も更新される予定です。

この変更はまた、`request.go` から `lex.go` へ一部のコードを移動させます。これは、将来的にHTTP/2と共有してコードの重複を減らすためのものです。

Issue #14048 を更新します。

## 変更の背景

この変更の主な背景は、HTTPヘッダーのセキュリティと堅牢性の向上です。HTTPプロトコルは、ヘッダーフィールドのキーと値に特定の文字セットとフォーマットを要求します。これに違反するヘッダーを送信すると、以下のような問題が発生する可能性があります。

1.  **セキュリティ脆弱性**: 不正な文字を含むヘッダーは、HTTPヘッダーインジェクションなどの攻撃に利用される可能性があります。これは、攻撃者が改行文字などを挿入することで、追加のヘッダーやHTTPレスポンスのボディの一部を制御できる脆弱性です。
2.  **相互運用性の問題**: 多くのHTTPサーバーやプロキシは、RFCに準拠しないヘッダーを正しく処理できません。これにより、予期しない動作や接続エラーが発生する可能性があります。
3.  **デバッグの困難さ**: 不正なヘッダーが原因で発生する問題は、ネットワークの奥深くで発生するため、デバッグが困難になることがあります。

このコミットは、これらの問題を未然に防ぐために、`net/http` パッケージがクライアント側でヘッダーの有効性を積極的に検証するようにします。これにより、不正なヘッダーがネットワークに到達する前にエラーとしてユーザーに通知され、開発者は問題を早期に特定し修正できるようになります。これは「フェイルファスト」の原則に従い、問題がシステムの下流でより深刻な影響を及ぼす前に検出することを目的としています。

コミットメッセージで言及されている `Updates #14048` は、この変更が解決または関連する特定のGoのIssueトラッカー上の問題を示しています。具体的なIssueの内容は不明ですが、通常、このようなIssueは、ユーザーからのバグレポート、セキュリティ上の懸念、またはプロトコル準拠の改善提案に関連しています。

## 前提知識の解説

### HTTPヘッダーの構造と制約
HTTPヘッダーは、クライアントとサーバー間で追加の情報をやり取りするために使用されます。各ヘッダーは「フィールド名: フィールド値」の形式で構成されます。

*   **フィールド名 (Field Name)**: ヘッダーの種類を示します（例: `Content-Type`, `User-Agent`）。RFC 7230では、フィールド名はトークン（token）として定義されており、ASCII文字、数字、および一部の記号（`!`, `#`, `$`, `%`, `&`, `'`, `*`, `+`, `-`, `.`, `^`, `_`, `` ` ``, `|`, `~`）のみが許可されます。特に、スペース、制御文字（CTLs）、および非ASCII文字は許可されません。
*   **フィールド値 (Field Value)**: フィールド名に対応する値です。RFC 2616では、フィールド値は「TEXT」または「TEXTとLWS（Line White Space）の組み合わせ」として定義されています。TEXTは、制御文字（CTLs）を除く任意のオクテット（バイト）を指しますが、LWS（CRLFに続くスペースまたは水平タブ）は複数行の値を表現するために使用されます。しかし、実際には、多くの実装ではフィールド値に制御文字（特に改行文字 `\n` やヌル文字 `\x00`）が含まれることを許容せず、セキュリティ上の理由からこれらを禁止しています。

### RFC 2616, RFC 7230, RFC 3986
これらのRFC (Request for Comments) は、HTTPプロトコルの仕様を定義する重要な文書です。

*   **RFC 2616 (HTTP/1.1)**: 1999年に発行されたHTTP/1.1の主要な仕様です。ヘッダーの構文に関する基本的なルールを定義しています。このコミットの `validHeaderValue` 関数は、RFC 2616のセクション4.2と2.2を参照しています。
*   **RFC 7230 (HTTP/1.1: Message Syntax and Routing)**: 2014年に発行され、RFC 2616を改訂・置き換える一連のRFCの一つです。HTTPメッセージの構文とルーティングに関する詳細な仕様を提供し、ヘッダーフィールド名の定義などを更新しています。このコミットの `validHostHeader` 関数は、RFC 7230のセクション5.4を参照しています。
*   **RFC 3986 (Uniform Resource Identifier (URI): Generic Syntax)**: URIの一般的な構文を定義するRFCです。RFC 7230の `uri-host` の定義がRFC 3986のセクション3.2.2を参照しているため、このコミットでも間接的に関連しています。

### HTTP/1.1 と HTTP/2
*   **HTTP/1.1**: 広く使われているHTTPプロトコルのバージョンです。ヘッダーはテキスト形式で送信されます。
*   **HTTP/2**: HTTP/1.1の後継プロトコルで、パフォーマンス改善のためにバイナリフレーミング層を導入しています。ヘッダーはHPACKという圧縮形式で送信されます。HTTP/2では、ヘッダーフィールド名には小文字のみが許可されるなど、HTTP/1.1とは異なる制約があります。

### Go言語の `net/http` パッケージと `x/net/http2` パッケージ
*   **`net/http`**: Go言語の標準ライブラリに含まれるHTTPクライアントおよびサーバーの実装です。HTTP/1.1とHTTP/2の両方をサポートしますが、HTTP/2の具体的な実装は `x/net/http2` パッケージに依存しています。
*   **`x/net/http2`**: Go言語の実験的なまたはより高度なネットワーク機能を提供する `x/net` リポジトリに含まれるHTTP/2の実装です。`net/http` パッケージがHTTP/2を扱う際に内部的に利用することがあります。

### フェイルファスト (Fail-fast)
ソフトウェア設計の原則の一つで、システム内でエラーや不正な状態が検出された場合、可能な限り早くその問題を報告し、処理を停止するという考え方です。これにより、問題がシステム全体に波及するのを防ぎ、デバッグを容易にします。このコミットは、不正なHTTPヘッダーを早期に検出することで、この原則を適用しています。

## 技術的詳細

このコミットの技術的な核心は、HTTPヘッダーのキーと値の有効性を検証するための新しい関数 `validHeaderName`、`validHeaderValue`、および `validHostHeader` の導入と、それらを `net/http` パッケージの `Transport.RoundTrip` メソッドに統合した点にあります。

### ヘッダー検証のロジック
1.  **`validHeaderName(v string) bool`**:
    *   HTTPヘッダーのフィールド名がRFCの仕様に準拠しているかをチェックします。
    *   フィールド名が空でないこと、および各文字が `isToken` 関数で定義された有効なトークン文字（ASCII文字、数字、一部の記号）であることを確認します。
    *   これにより、フィールド名にスペース、制御文字、非ASCII文字などが含まれることを防ぎます。

2.  **`validHeaderValue(v string) bool`**:
    *   HTTPヘッダーのフィールド値がRFC 2616の仕様に準拠しているかをチェックします。
    *   フィールド値内の各バイトが制御文字（CTLs）である場合、それがLWS（Line White Space、つまり改行に続くスペースやタブ）でないことを確認します。
    *   これは、フィールド値にヌル文字 (`\x00`) や単独の改行文字 (`\n`) など、不正な制御文字が含まれることを防ぐためのものです。

3.  **`validHostHeader(h string) bool` と `validHostByte`**:
    *   `Host` ヘッダーの値が有効であるかをチェックします。
    *   RFC 7230の `Host = uri-host [ ":" port ]` の定義を参照していますが、実装はより寛容で、`validHostByte` 配列で定義されたバイトのみを許可します。
    *   `validHostByte` は、数字、英字、およびURIホストやポートで許可される一部の記号（`!`, `$`, `%`, `&`, `(`, `)`, `*`, `+`, `,`, `-`, `.`, `:`, `;`, `=`, `[`, `\`, `]`, `_`, `~`）を `true` とする256要素のブール配列です。これにより、`Host` ヘッダーに不正な文字が含まれることを防ぎます。

### コードの移動と再利用性
*   以前 `request.go` にあった `validHostHeader` と `validHeaderName` (および関連する `validHostByte`) のロジックは、`lex.go` に移動されました。
*   この移動は、将来的にこれらの検証ロジックを `x/net/http2` パッケージと共有し、コードの重複（code bloat）を減らすための準備ステップです。`lex.go` は、HTTPプロトコルの字句解析に関連するユーティリティ関数を置くのに適した場所です。

### `Transport.RoundTrip` メソッドへの統合
*   `net/http/transport.go` の `Transport.RoundTrip` メソッドは、HTTPリクエストを送信する直前にヘッダーの検証を行うように変更されました。
*   リクエストの `Header` マップをイテレートし、各ヘッダーのキーと値に対して `validHeaderName` と `validHeaderValue` を呼び出します。
*   いずれかの検証が失敗した場合、`fmt.Errorf` を使用してエラーを返し、リクエストの送信を中止します。これにより、不正なヘッダーがネットワークに送信される前に、クライアント側で早期にエラーが報告されます。
*   この検証は、HTTP/1.1とHTTP/2の両方で `net/http` パッケージを介して行われるリクエストに適用されます。

### テストケースの追加
*   `src/net/http/clientserver_test.go` に `TestTransportRejectsInvalidHeaders_h1` と `TestTransportRejectsInvalidHeaders_h2` という新しいテスト関数が追加されました。
*   これらのテストは、HTTP/1.1とHTTP/2の両方で、様々な不正なヘッダー（例: 値にヌル文字や改行文字を含む、キーに改行文字やスペースを含む、キーが非ASCII文字、キーが空）を送信しようとしたときに、`Transport` が正しくエラーを返すことを検証します。
*   特に、`dialed` フラグを使用して、不正なヘッダーの場合には実際にネットワーク接続が確立されない（つまり、ローカルでエラーが検出される）ことを確認しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/net/http/lex.go` に追加されたヘッダー検証関数と、`src/net/http/transport.go` の `RoundTrip` メソッドにおけるその利用です。

### `src/net/http/lex.go` の新しい検証関数

```go
// lex.go
func validHeaderName(v string) bool {
	if len(v) == 0 {
		return false
	}
	for _, r := range v {
		if !isToken(r) { // isTokenはRFCで定義されたトークン文字かをチェックする関数
			return false
		}
	}
	return true
}

// validHostHeaderとvalidHostByteはrequest.goから移動
func validHostHeader(h string) bool {
	// ... (RFC 7230, RFC 3986に基づくホスト名の検証ロジック)
	for i := 0; i < len(h); i++ {
		if !validHostByte[h[i]] {
			return false
		}
	}
	return true
}

var validHostByte = [256]bool{
	// ... (有効なホストバイトの定義)
}

func validHeaderValue(v string) bool {
	for i := 0; i < len(v); i++ {
		b := v[i]
		if isCTL(b) && !isLWS(b) { // 制御文字だがLWSでない場合は不正
			return false
		}
	}
	return true
}
```
*   `validHeaderName`: ヘッダー名が空でないこと、および各文字がHTTPプロトコルで許可される「トークン」文字であることを確認します。`isToken` 関数（このコミットでは変更されていませんが、`lex.go` に既存の関数）は、RFCで定義された有効な文字セット（英数字と一部の記号）をチェックします。
*   `validHostHeader` と `validHostByte`: `Host` ヘッダーの値を検証します。`validHostByte` は、ホスト名やポート番号に許可される文字を効率的にチェックするためのルックアップテーブルです。
*   `validHeaderValue`: ヘッダー値に不正な制御文字が含まれていないことを確認します。HTTP/1.1のRFC 2616では、ヘッダー値は「TEXT」または「TEXTとLWSの組み合わせ」と定義されています。TEXTは制御文字を除く任意のオクテットですが、LWS（改行に続くスペースやタブ）は複数行の値を許容するために特別に扱われます。この関数は、LWSではない制御文字（例: ヌル文字 `\x00` や単独の改行 `\n`）を不正と判断します。

### `src/net/http/transport.go` の `RoundTrip` メソッド

```go
// transport.go
func (t *Transport) RoundTrip(req *Request) (*Response, error) {
	// ... (既存の処理)

	scheme := req.URL.Scheme
	isHTTP := scheme == "http" || scheme == "https"
	if isHTTP {
		for k, vv := range req.Header {
			if !validHeaderName(k) {
				return nil, fmt.Errorf("net/http: invalid header field name %q", k)
			}
			for _, v := range vv {
				if !validHeaderValue(v) {
					return nil, fmt.Errorf("net/http: invalid header field value %q for key %v", v, k)
				}
			}
		}
	}

	// ... (既存の処理)
}
```
`RoundTrip` メソッドは、`net/http` クライアントが実際のリクエストを送信する直前に呼び出される中心的な関数です。この変更により、リクエストがHTTPまたはHTTPSスキームを使用している場合、`req.Header` マップ内のすべてのヘッダーフィールドに対して以下の検証が実行されます。
1.  ヘッダーのキー (`k`) が `validHeaderName` によって検証されます。不正なキーが見つかった場合、`"net/http: invalid header field name %q"` というエラーが返されます。
2.  各ヘッダーキーに関連付けられたすべての値 (`vv` の各 `v`) が `validHeaderValue` によって検証されます。不正な値が見つかった場合、`"net/http: invalid header field value %q for key %v"` というエラーが返されます。

これらのチェックにより、不正なヘッダーがネットワーク層に到達する前に捕捉され、ユーザーに明確なエラーメッセージが提供されます。これにより、デバッグが容易になり、潜在的なプロトコル違反やセキュリティ問題が未然に防がれます。

		if !tt.ok && dialed {

		} else if (err == nil) != tt.ok {

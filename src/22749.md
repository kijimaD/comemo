# [インデックス 22749] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）が`runtime.getg`関数をインライン化するように変更するものです。これにより、`runtime.getg`の呼び出しが、実際の関数呼び出しではなく、コンパイラによって直接生成される機械語命令に置き換えられます。この変更は、GoランタイムがC言語で実装されていた頃の`g`ポインタ（現在のゴルーチンを示すポインタ）の取得方法に近づけることを目的としており、パフォーマンスの向上をもたらします。

## 元コミット内容

このコミットの目的は、`runtime.getg`関数をGoコンパイラによって直接インライン化することです。これにより、`runtime.getg`の呼び出しが、実際の関数呼び出しのオーバーヘッドなしに、現在のゴルーチン（`g`）ポインタを直接取得する機械語命令に置き換えられます。

コミットメッセージには、この変更が「古いCランタイムが行っていたことをより密接に復元する」と述べられています。C言語で書かれていたGoランタイムでは、`g`ポインタは「extern register」として扱われ、現在のスレッド（Goではゴルーチン）のコンテキストに紐付けられたレジスタから直接アクセスされていました。このコミットは、Goコンパイラが同様の最適化を適用することで、この効率的なアクセス方法をGoのコードベースに持ち込むものです。

ベンチマーク結果も示されており、多くのベンチマークでパフォーマンスが向上していることが確認できます。特に`BenchmarkBinaryTree17`や`BenchmarkFmtFprintfEmpty`では10%以上の改善が見られます。

## 変更の背景

Goランタイムは、各ゴルーチンが自身の状態（スタック、スケジューラ情報など）を管理するために、現在のゴルーチンを表す`g`ポインタに頻繁にアクセスする必要があります。この`g`ポインタへのアクセスは、Goプログラムの実行において非常に頻繁に行われる操作であり、その効率性はランタイム全体のパフォーマンスに大きく影響します。

以前のGoランタイムでは、`runtime.getg`はアセンブリ言語で実装された関数として提供されていました。この関数を呼び出すたびに、通常の関数呼び出しのオーバーヘッド（スタックフレームのセットアップ、レジスタの保存・復元など）が発生していました。これは、`g`ポインタの取得という非常に単純で頻繁な操作にとっては非効率的でした。

このコミットの背景には、以下の点が挙げられます。

1.  **パフォーマンスの最適化**: `g`ポインタへのアクセスを高速化することで、Goプログラム全体の実行速度を向上させる。
2.  **Cランタイムの効率性の再現**: GoランタイムがC言語で書かれていた時代には、`g`ポインタはレジスタに割り当てられ、直接アクセスされていました。GoがGo言語で再実装された後も、この効率的なアクセス方法を維持または再現することが望まれていました。
3.  **コンパイラの能力向上**: コンパイラが特定のランタイム関数を「組み込み関数（intrinsic function）」として認識し、特別なコード生成を行うことで、手動でアセンブリを書くよりも柔軟かつ効率的な最適化を可能にする。

この変更により、`runtime.getg`の呼び出しはコンパイラによって直接、プラットフォーム固有の効率的な命令（例えば、スレッドローカルストレージからの読み込みや、特定のレジスタからの読み込み）に変換されるようになります。これにより、関数呼び出しのオーバーヘッドが完全に排除され、`g`ポインタへのアクセスが大幅に高速化されます。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

1.  **Goランタイム**: Goプログラムの実行を管理する低レベルのシステム。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信などを担当します。
2.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッド。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。各ゴルーチンは`g`という構造体で表現され、その状態（スタック、現在のM（OSスレッド）、P（プロセッサ）など）を保持します。
3.  **`g`ポインタ**: 現在実行中のゴルーチンを表す`g`構造体へのポインタ。Goランタイムは、スケジューリング、スタック管理、エラーハンドリングなど、多くの内部処理でこの`g`ポインタにアクセスします。
4.  **インライン化 (Inlining)**: コンパイラ最適化の一種で、関数呼び出しをその関数の本体のコードで直接置き換えること。これにより、関数呼び出しのオーバーヘッド（スタックフレームの作成、レジスタの保存・復元、ジャンプ命令など）が排除され、プログラムの実行速度が向上します。ただし、コードサイズが増加する可能性があります。
5.  **コンパイラフロントエンドとバックエンド**:
    *   **フロントエンド**: ソースコードを解析し、抽象構文木（AST）などの中間表現に変換します。型チェック、構文解析、意味解析などを行います。
    *   **バックエンド**: 中間表現を受け取り、ターゲットマシンコードを生成します。最適化、レジスタ割り当て、アセンブリコード生成などを行います。
6.  **スレッドローカルストレージ (TLS: Thread Local Storage)**: 各スレッドが独自のデータを保存できるメモリ領域。OSが提供する機能で、スレッドごとに異なるグローバル変数のようなものとして利用できます。Goランタイムでは、`g`ポインタをTLSに保存することで、現在のゴルーチンに効率的にアクセスする手段として利用されることがあります。
7.  **レジスタ (Register)**: CPU内部にある高速な記憶領域。プログラムの実行中に頻繁にアクセスされるデータを一時的に保持するために使用されます。レジスタへのアクセスは、メインメモリへのアクセスよりもはるかに高速です。
8.  **`cmd/internal/gc`**: Goコンパイラの内部パッケージ。Goのソースコードを機械語に変換する主要なロジックが含まれています。
9.  **`cmd/*/ggen.go` と `cmd/*/galign.go`**: Goコンパイラの各アーキテクチャ（例: `5g`はARM、`6g`はx86-64、`8g`はx86-32）固有のコード生成（`ggen.go`）とアラインメント（`galign.go`）を担当するファイル。
10. **`obj.Prog`**: Goコンパイラが生成するアセンブリ命令の抽象表現。
11. **`gc.Node`**: Goコンパイラ内部で抽象構文木（AST）のノードを表す構造体。

## 技術的詳細

このコミットの技術的な核心は、`runtime.getg`関数をコンパイラ組み込み関数（intrinsic function）として扱い、その呼び出しをコンパイル時に直接機械語命令に置き換える点にあります。

具体的な変更点は以下の通りです。

1.  **`OGETG`オペレーションの導入**:
    *   `src/cmd/internal/gc/syntax.go`に新しいオペレーションコード`OGETG`が追加されました。これは`runtime.getg()`の呼び出しを表します。
    ```go
    // src/cmd/internal/gc/syntax.go
    const (
        // ...
        OGETG   // runtime.getg() (read g pointer)
        // ...
    )
    ```

2.  **型チェック時の`OCALLFUNC`から`OGETG`への変換**:
    *   `src/cmd/internal/gc/typecheck.go`の`typecheck`関数内で、`runtime.getg()`への関数呼び出し（`OCALLFUNC`）が`OGETG`オペレーションに変換されるようになりました。
    *   この変換は、`compiling_runtime`が設定されている場合、または呼び出しが`Runtimepkg`（`runtime`パッケージ）の`getg`シンボルである場合に実行されます。
    *   重要なのは、この変換が`walk`フェーズ（通常、組み込み関数の書き換えが行われる場所）よりも早い`typecheck`フェーズで行われることです。コミットメッセージのコメントには、「`getg()`は常に同じ結果を返すため、一時変数を避けるために通常よりも早く書き換える」と説明されています。これにより、コンパイラは`getg()`の戻り値を一時変数に保存する必要がなくなり、より効率的なコードを生成できます。
    ```go
    // src/cmd/internal/gc/typecheck.go
    // ...
    			if n.Op == OCALLFUNC && n.Left.Op == ONAME && (compiling_runtime != 0 || n.Left.Sym.Pkg == Runtimepkg) && n.Left.Sym.Name == "getg" {
    				// Emit code for runtime.getg() directly instead of calling function.
    				// Most such rewrites (for example the similar one for math.Sqrt) should be done in walk,
    				// so that the ordering pass can make sure to preserve the semantics of the original code
    				// (in particular, the exact time of the function call) by introducing temporaries.
    				// In this case, we know getg() always returns the same result within a given function
    				// and we want to avoid the temporaries, so we do the rewrite earlier than is typical.
    				n.Op = OGETG
    			}
    // ...
    ```

3.  **アーキテクチャ固有の`Getg`実装の追加**:
    *   `src/cmd/internal/gc/go.go`の`Arch`構造体に`Getg func(*Node)`フィールドが追加されました。これは、各アーキテクチャが`g`ポインタを取得するための独自の関数を提供できるようにするためです。
    *   各アーキテクチャの`galign.go`ファイル（例: `src/cmd/5g/galign.go`）で、この`Getg`フィールドにアーキテクチャ固有の`getg`関数が割り当てられます。
    *   各アーキテクチャの`ggen.go`ファイル（例: `src/cmd/5g/ggen.go`、`src/cmd/6g/ggen.go`）に、`getg`関数が実装されました。これらの関数は、ターゲットアーキテクチャに応じて、`g`ポインタをレジスタから直接読み込むか、スレッドローカルストレージ（TLS）から読み込むための機械語命令を生成します。
        *   例えば、x86-64 (`src/cmd/6g/ggen.go`) では、TLS (Thread Local Storage) から `g` ポインタを読み込むための命令が生成されます。`x86.REG_TLS` レジスタ（またはそれに相当するもの）からオフセットを適用して `g` ポインタを取得します。
        *   ARM (`src/cmd/5g/ggen.go`) や ARM64 (`src/cmd/7g/ggen.go`) では、`arm.REGG` や `arm64.REGG` といった専用レジスタから `g` ポインタを直接読み込む命令が生成されます。これは、これらのアーキテクチャでは `g` ポインタが特定のレジスタに保持される慣例があるためです。

4.  **コード生成フェーズでの`OGETG`の処理**:
    *   `src/cmd/internal/gc/cgen.go`の`Cgen`関数に`OGETG`ケースが追加され、`Thearch.Getg(res)`が呼び出されるようになりました。これにより、コンパイラは`OGETG`オペレーションを検出すると、現在選択されているアーキテクチャの`Getg`関数を呼び出し、`g`ポインタを取得するための適切な機械語命令を生成します。
    *   `src/cmd/internal/gc/gen.go`では、トップレベルの`OGETG`呼び出しは「何もしない」とマークされています。これは、`typecheck`フェーズで既に適切なコード生成が指示されているため、`gen`フェーズでは追加の処理が不要であることを意味します。

5.  **アセンブリ実装の削除**:
    *   `src/runtime/asm_*.s`ファイル（例: `src/runtime/asm_386.s`、`src/runtime/asm_amd64.s`など）から、`runtime.getg`のアセンブリ実装が削除されました。これは、コンパイラが直接コードを生成するため、これらのアセンブリ関数が不要になったためです。

6.  **`stubs.go`のコメント更新**:
    *   `src/runtime/stubs.go`の`getg()`関数宣言に、コンパイラがこの呼び出しを直接命令に書き換えるという説明が追加されました。
    ```go
    // src/runtime/stubs.go
    // ...
    // getg returns the pointer to the current g.
    // The compiler rewrites calls to this function into instructions
    // that fetch the g directly (from TLS or from the dedicated register).
    func getg() *g
    // ...
    ```

これらの変更により、`runtime.getg()`の呼び出しは、コンパイル時に直接、現在のゴルーチンポインタを効率的に取得する機械語命令に変換されるようになり、関数呼び出しのオーバーヘッドが完全に排除されます。

## コアとなるコードの解説

ここでは、特に重要なコード変更箇所を抜粋し、その役割を詳しく解説します。

### `src/cmd/internal/gc/typecheck.go` における `OGETG` への変換

```go
// src/cmd/internal/gc/typecheck.go
// ...
			if n.Op == OCALLFUNC && n.Left.Op == ONAME && (compiling_runtime != 0 || n.Left.Sym.Pkg == Runtimepkg) && n.Left.Sym.Name == "getg" {
				// Emit code for runtime.getg() directly instead of calling function.
				// Most such rewrites (for example the similar one for math.Sqrt) should be done in walk,
				// so that the ordering pass can make sure to preserve the semantics of the original code
				// (in particular, the exact time of the function call) by introducing temporaries.
				// In this case, we know getg() always returns the same result within a given function
				// and we want to avoid the temporaries, so we do the rewrite earlier than is typical.
				n.Op = OGETG
			}
// ...
```
このコードブロックは、Goコンパイラの型チェックフェーズで実行されます。
*   `n.Op == OCALLFUNC`: 現在処理しているASTノードが関数呼び出しであることを確認します。
*   `n.Left.Op == ONAME`: 呼び出されている関数が名前（シンボル）によって参照されていることを確認します。
*   `(compiling_runtime != 0 || n.Left.Sym.Pkg == Runtimepkg) && n.Left.Sym.Name == "getg"`: 呼び出されている関数が`runtime`パッケージの`getg`関数であることを特定します。`compiling_runtime != 0`は、コンパイラ自身がランタイムをコンパイルしている特殊なケースを扱います。
*   `n.Op = OGETG`: 条件が満たされた場合、関数呼び出しを表す`OCALLFUNC`オペレーションを、新しく定義された`OGETG`オペレーションに書き換えます。

この書き換えが型チェックフェーズという早い段階で行われるのは、`runtime.getg()`が常に同じゴルーチンポインタを返すという特性を利用するためです。これにより、コンパイラは`getg()`の戻り値を一時変数に保存する必要がなくなり、より直接的で効率的なコード生成が可能になります。通常の組み込み関数のインライン化は`walk`フェーズで行われますが、`getg`の場合はこの特殊な最適化のために前倒しされています。

### `src/cmd/6g/ggen.go` における `getg` 関数の実装 (x86-64の例)

```go
// src/cmd/6g/ggen.go
// ...
// res = runtime.getg()
func getg(res *gc.Node) {
	var n1 gc.Node
	gc.Regalloc(&n1, res.Type, res) // レジスタを割り当てる
	mov := optoas(gc.OAS, gc.Types[gc.Tptr]) // MOV命令のオペコードを取得
	p := gins(mov, nil, &n1) // MOV命令を生成 (TLSベースレジスタからn1へ)
	p.From.Type = obj.TYPE_REG
	p.From.Reg = x86.REG_TLS // TLSベースレジスタ (x86-64ではFS/GSセグメントレジスタに関連付けられる)
	p = gins(mov, nil, &n1) // MOV命令を生成 (n1からTLSオフセットを適用してn1へ)
	p.From = p.To
	p.From.Type = obj.TYPE_MEM
	p.From.Index = x86.REG_TLS
	p.From.Scale = 1 // スケールは1 (バイト単位)
	gmove(&n1, res) // n1の内容を結果レジスタ(res)へ移動
	gc.Regfree(&n1) // 割り当てたレジスタを解放
}
// ...
```
この`getg`関数は、x86-64アーキテクチャ向けに`runtime.getg()`のインラインコードを生成します。
1.  `gc.Regalloc(&n1, res.Type, res)`: `g`ポインタを一時的に保持するためのレジスタ`n1`を割り当てます。
2.  `mov := optoas(gc.OAS, gc.Types[gc.Tptr])`: ポインタ型（`Tptr`）のデータを移動するためのMOV命令のオペコードを取得します。
3.  最初の`gins(mov, nil, &n1)`とそれに続く`p.From.Type = obj.TYPE_REG; p.From.Reg = x86.REG_TLS;`: これは、スレッドローカルストレージ（TLS）のベースアドレスを一時レジスタ`n1`にロードする命令を生成します。x86-64では、TLSは通常、FSまたはGSセグメントレジスタによって間接的にアクセスされます。`x86.REG_TLS`は、このTLSベースアドレスを指す仮想的なレジスタとして扱われます。
4.  2番目の`gins(mov, nil, &n1)`とそれに続く`p.From = p.To; p.From.Type = obj.TYPE_MEM; p.From.Index = x86.REG_TLS; p.From.Scale = 1;`: これは、TLSベースアドレスから`g`ポインタのオフセットを適用して、実際の`g`ポインタの値を`n1`にロードする命令を生成します。`p.From.Index = x86.REG_TLS`は、TLSベースレジスタをインデックスとして使用し、`p.From.Scale = 1`はバイト単位のオフセットを示します。
5.  `gmove(&n1, res)`: 一時レジスタ`n1`にロードされた`g`ポインタの値を、最終的な結果を格納するレジスタ`res`に移動します。
6.  `gc.Regfree(&n1)`: 一時的に使用したレジスタ`n1`を解放します。

この一連の処理により、`runtime.getg()`の呼び出しは、TLSから`g`ポインタを直接読み込むための効率的な機械語命令に置き換えられます。

### `src/runtime/asm_amd64.s` からの `runtime·getg` の削除

```diff
--- a/src/runtime/asm_amd64.s
+++ b/src/runtime/asm_amd64.s
@@ -1673,12 +1673,6 @@ TEXT runtime·goexit(SB),NOSPLIT,$0-0
  	// traceback from goexit1 must hit code range of goexit
  	BYTE	$0x90	// NOP
 
-TEXT runtime·getg(SB),NOSPLIT,$0-8
-	get_tls(CX)
-	MOVQ	g(CX), AX
-	MOVQ	AX, ret+0(FP)
-	RET
-
 TEXT runtime·prefetcht0(SB),NOSPLIT,$0-8
 	MOVQ	addr+0(FP), AX
 	PREFETCHT0	(AX)
```
この差分は、x86-64アーキテクチャ向けのアセンブリファイルから`runtime·getg`関数の定義が削除されたことを示しています。以前は、このアセンブリ関数が`g`ポインタを取得する役割を担っていましたが、コンパイラが直接コードを生成するようになったため、この関数は不要になりました。他のアーキテクチャのアセンブリファイルでも同様の削除が行われています。

これらの変更により、`runtime.getg`はGoコンパイラによって完全にインライン化され、Goプログラムのパフォーマンス向上に貢献しています。

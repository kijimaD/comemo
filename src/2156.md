## 前提知識の解説

### Go言語のインターフェース

Go言語のインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは「暗黙的」に実装されます。つまり、ある型がインターフェースで定義されたすべてのメソッドを実装していれば、その型はそのインターフェースを実装していると見なされます。`implements`キーワードのような明示的な宣言は不要です。

例:
```go
type Greeter interface {
    Greet() string
}

type Person struct {
    Name string
}

func (p Person) Greet() string { // Person型はGreet()メソッドを持つため、Greeterインターフェースを実装する
    return "Hello, " + p.Name
}
```

### メソッドのレシーバ（Receiver）

Goのメソッドは、特定の型に関連付けられた関数です。メソッドを定義する際には、そのメソッドがどの型のインスタンスに対して呼び出されるかを指定する「レシーバ」を定義します。レシーバには「値レシーバ」と「ポインタレシーバ」の2種類があります。

1.  **値レシーバ (Value Receiver)**:
    `func (t MyType) MethodName() { ... }`
    この形式のメソッドは、`MyType`型の値のコピーに対して動作します。メソッド内でレシーバのフィールドを変更しても、元の値には影響しません。

2.  **ポインタレシーバ (Pointer Receiver)**:
    `func (t *MyType) MethodName() { ... }`
    この形式のメソッドは、`MyType`型へのポインタに対して動作します。メソッド内でレシーバのフィールドを変更すると、元の値も変更されます。これは、メソッドが元の値のメモリ上のアドレスを直接操作するためです。

### インターフェースとレシーバの適合性規則

Goにおいて、型がインターフェースを実装していると見なされるためのレシーバに関する重要な規則があります。

*   **値レシーバを持つメソッドのみで構成されるインターフェース**:
    インターフェースが値レシーバを持つメソッドのみを要求する場合、そのインターフェースは**値型**と**ポインタ型**の両方によって実装され得ます。
    例: `type V interface { V() }`
    `func (t T) V() {}` の場合、`T` と `*T` の両方が `V` インターフェースを満たします。これは、Goが値型の変数から値レシーバのメソッドを呼び出す際に、その値のコピーを渡すためです。また、ポインタ型の変数から値レシーバのメソッドを呼び出す際には、ポインタが指す値が自動的にデリファレンスされ、その値のコピーがメソッドに渡されます。

*   **ポインタレシーバを持つメソッドを含むインターフェース**:
    インターフェースがポインタレシーバを持つメソッドを一つでも要求する場合、そのインターフェースは**ポインタ型**によってのみ実装されます。
    例: `type P interface { P() }`
    `func (t *T) P() {}` の場合、`*T` のみが `P` インターフェースを満たします。`T` 型の変数自体は `P` インターフェースを満たしません。これは、ポインタレシーバのメソッドは、そのレシーバが指すメモリ上の値を変更する可能性があるため、Goは値型の変数からポインタレシーバのメソッドを呼び出すことを許可しないためです（ただし、値がアドレス可能であれば、コンパイラが自動的にアドレスを取得して呼び出すことは可能です）。インターフェースへの代入においては、この厳密な規則が適用されます。

この規則は、Goの型システムにおける重要な側面であり、特にインターフェースを介したポリモーフィズムを利用する際に理解しておく必要があります。

## 技術的詳細

Goのインターフェースは、内部的には「型」と「値」のペアとして表現されます。インターフェース変数に値を代入すると、そのインターフェース変数には、代入された具体的な値の型情報と、その値自体が格納されます。メソッドがインターフェースを介して呼び出される際、Goランタイムはインターフェース変数に格納されている型情報に基づいて、適切なメソッドの実装を動的にディスパッチします。

このコミットでテストされている主要な技術的詳細は、前述の「インターフェースとレシーバの適合性規則」に集約されます。特に、以下の挙動が検証されています。

1.  **値レシーバメソッドの適合性**:
    `type T int` に `func (t T) V()` という値レシーバメソッドがある場合、`T` 型の変数も `*T` 型の変数も、`V()` メソッドを要求するインターフェース（例: `type V interface { V() }`）に代入できるか。
    Goの仕様では、値レシーバのメソッドは、その型の値とポインタの両方から呼び出すことができます。インターフェースへの代入においても、この柔軟性が反映されます。

2.  **ポインタレシーバメソッドの適合性**:
    `type T int` に `func (t *T) P()` というポインタレシーバメソッドがある場合、`P()` メソッドを要求するインターフェース（例: `type P interface { P(); V() }`）に代入できるのは、`*T` 型の変数のみであり、`T` 型の変数は代入できないか。
    Goの仕様では、ポインタレシーバのメソッドは、その型のポインタからのみ呼び出すことができます。値型の変数からポインタレシーバのメソッドを呼び出すことは、その値がアドレス可能であればコンパイラが自動的にポインタに変換して呼び出しますが、インターフェースへの代入においては、より厳密な型適合性が求められます。つまり、インターフェースがポインタレシーバのメソッドを要求する場合、そのインターフェースを満たすためには、ポインタ型である必要があります。

3.  **構造体への埋め込み (Embedded Fields) とインターフェース**:
    Goの構造体は、他の型を埋め込むことができます。埋め込まれた型のメソッドは、外側の構造体のメソッドとして「昇格 (promoted)」されます。このテストでは、値型 (`S struct { T; }`) やポインタ型 (`SP struct { *T; }`) を埋め込んだ構造体が、どのようにインターフェースを実装するかを検証しています。
    - `S struct { T; }`: `S` は `T` の値レシーバメソッドとポインタレシーバメソッドの両方を昇格させます。`S` の値がアドレス可能であれば、`S` のポインタも `T` のポインタレシーバメソッドを呼び出せます。
    - `SP struct { *T; }`: `SP` は `*T` のメソッドを昇格させます。これにより、`SP` は `T` の値レシーバメソッドとポインタレシーバメソッドの両方を呼び出せるようになります。

これらのテストは、Goコンパイラがこれらの複雑な規則を正しく解釈し、適切な型チェックとメソッドディスパッチを実行できることを保証するためのものです。特に、`test/interface9.go` は、コンパイル時にエラーとなるべきケースが正しくエラーとして検出されることを確認する `errchk` テストであり、コンパイラの堅牢性を高める上で重要です。

## コアとなるコードの解説

### `test/interface8.go` の解説

このファイルは、Goのインターフェースとレシーバの挙動を網羅的にテストする主要なファイルです。

```go
package main

type T int
var nv, np int // V()とP()メソッドの呼び出し回数をカウント

func (t T) V() { // 値レシーバメソッド
    if t != 42 {
        panic(t)
    }
    nv++
}

func (t *T) P() { // ポインタレシーバメソッド
    if *t != 42 {
        panic(t, *t)
    }
    np++
}

type V interface { V() } // V()メソッドのみを要求するインターフェース
type P interface { P(); V() } // P()とV()メソッドを要求するインターフェース

type S struct { // Tを埋め込んだ構造体
    T;
}

type SP struct { // *Tを埋め込んだ構造体
    *T;
}

func main() {
    var t T;
    var v V;
    var p P;

    t = 42;

    // T型の値からメソッドを呼び出す
    t.P(); // Tはアドレス可能なので、&t.P()として呼び出される
    t.V();

    // T型の値をVインターフェースに代入
    v = t; // TはV()を持つのでOK
    v.V();

    // T型へのポインタをPインターフェースに代入
    p = &t; // *TはP()とV()を持つのでOK
    p.P();
    p.V();

    // T型へのポインタをVインターフェースに代入
    v = &t; // *TはV()を持つのでOK
    v.V();

    // p = t; // ERROR: TはP()を直接持たないため、Pインターフェースを満たさない

    // 構造体Sのテスト
    var s S;
    s.T = 42;
    s.P(); // SはTを埋め込んでいるため、TのP()メソッドが昇格される
    s.V(); // SはTを埋め込んでいるため、TのV()メソッドが昇格される

    v = s; // SはV()を持つのでOK
    s.V(); // s.V()は既に呼び出されているが、ここでは再度呼び出し

    p = &s; // *SはP()とV()を持つのでOK
    p.P();
    p.V();

    v = &s; // *SはV()を持つのでOK
    v.V();

    // p = s; // ERROR: SはP()を直接持たないため、Pインターフェースを満たさない

    // 構造体SPのテスト
    var sp SP;
    tsp := T(42) // 一時的なT型の値を作成
    sp.T = &tsp; // SPは*Tを埋め込んでいるため、*Tへのポインタを代入
    sp.P(); // SPは*Tを埋め込んでいるため、*TのP()メソッドが昇格される
    sp.V(); // SPは*Tを埋め込んでいるため、*TのV()メソッドが昇格される

    v = sp; // SPはV()を持つのでOK
    sp.V();

    p = &sp; // *SPはP()とV()を持つのでOK
    p.P();
    p.V();

    v = &sp; // *SPはV()を持つのでOK
    v.V();

    p = sp; // no error! SPは*Tを埋め込んでいるため、SP自体がPインターフェースを満たす
    p.P();
    p.V();

    // 最終的なメソッド呼び出し回数の検証
    if nv != 13 || np != 7 {
        panicln("bad count", nv, np)
    }
}
```

このテストの重要なポイントは、`nv`と`np`の最終的な値が期待通りになることを確認している点です。これは、各メソッドが正しいレシーバで、正しい回数だけ呼び出されたことを保証します。特に、`p = sp; // no error!` の行は、`SP` が `*T` を埋め込んでいるため、`SP` 自体が `P` インターフェース（ポインタレシーバメソッド `P()` を含む）を満たすという、Goの埋め込みとインターフェース適合性の複雑な挙動を示しています。

### `test/interface9.go` の解説

このファイルは、コンパイル時にエラーとなるべきインターフェースの代入を明示的にテストします。`errchk` コメントは、Goのテストフレームワークがこのファイルを実行する際に、指定された行でコンパイルエラーが発生することを期待していることを示します。

```go
package main

type T int
func (t T) V() // V()メソッドの宣言のみ
func (t *T) P() // P()メソッドの宣言のみ

type V interface { V() } // V()メソッドのみを要求
type P interface { P(); V() } // P()とV()メソッドを要求

type S struct { T; } // Tを埋め込んだ構造体
type SP struct { *T; } // *Tを埋め込んだ構造体

func main() {
    var t T;
    var v V;
    var p P;
    var s S;
    var sp SP;

    v = t; // OK: TはV()を持つのでVインターフェースを満たす
    p = t; // ERROR "is not": TはP()を直接持たないため、Pインターフェースを満たさない

    v = &t; // OK: *TはV()を持つのでVインターフェースを満たす
    p = &t; // OK: *TはP()とV()を持つのでPインターフェースを満たす

    v = s; // OK: SはTを埋め込んでいるためV()を持つのでVインターフェースを満たす
    p = s; // ERROR "is not": SはP()を直接持たないため、Pインターフェースを満たさない

    v = &s; // OK: *SはTを埋め込んでいるためV()を持つのでVインターフェースを満たす
    p = &s; // OK: *SはP()とV()を持つのでPインターフェースを満たす

    v = sp; // OK: SPは*Tを埋め込んでいるためV()を持つのでVインターフェースを満たす
    p = sp; // no error!: SPは*Tを埋め込んでいるため、SP自体がPインターフェースを満たす
    v = &sp; // OK: *SPはV()を持つのでVインターフェースを満たす
    p = &sp; // OK: *SPはP()とV()を持つのでPインターフェースを満たす
}
```

このテストの核心は、`p = t; // ERROR "is not"` と `p = s; // ERROR "is not"` の行です。これらは、値型 (`T` や `S`) がポインタレシーバメソッド (`P()`) を含むインターフェース (`P`) に直接代入できないことを示しています。Goのコンパイラは、このような不正な代入を検出し、コンパイルエラーを発生させる必要があります。

一方で、`p = sp; // no error!` は、`test/interface8.go` と同様に、`SP` が `*T` を埋め込んでいるため、`SP` 自体が `P` インターフェースを満たすという、Goの埋め込みの強力な機能を示しています。これは、`SP` の値が `*T` のメソッドを直接呼び出せるため、`P` インターフェースの要件を満たすと見なされるためです。

これらのテストは、Goのインターフェースとメソッドの適合性に関する厳密な規則を強制し、コンパイラがこれらの規則を正確に適用できることを保証するために不可欠です。

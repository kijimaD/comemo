# [インデックス 27305] ファイルの概要

このコミットは、Goツールチェーンの内部パッケージである`cmd/internal/obj`と`cmd/link`におけるオブジェクトファイルフォーマットの変更に関するものです。具体的には、Goのオブジェクトファイルがシンボルデータを格納する方法を最適化し、リンカのパフォーマンスを向上させることを目的としています。`src/cmd/internal/goobj/read.go`はオブジェクトファイルの読み込みロジックを、`src/cmd/internal/obj/objfile.go`はオブジェクトファイルの書き込みロジックを、`src/cmd/link/internal/ld/objfile.go`はリンカがオブジェクトファイルをロードするロジックをそれぞれ担当しています。

## 変更の背景

このコミットの主な目的は、Goプログラムのリンク時間を短縮し、ビルドパフォーマンスを向上させることです。以前のGoのオブジェクトファイルフォーマットでは、シンボルのメタデータ（名前、型、サイズなど）と実際のシンボルデータ（コードや初期化データなど）がファイル内でインターリーブ（混在）して配置されていました。

このような配置は、リンカがオブジェクトファイルを読み込む際に非効率なI/Oパターンを引き起こす可能性がありました。リンカが特定のシンボルのメタデータだけを必要とする場合でも、そのシンボルに付随する実際のデータも読み込まなければならないため、不要なディスクI/Oが発生していました。特に、大規模なプロジェクトや多数のオブジェクトファイルが存在する場合、この非効率性はリンク時間の増加に直結します。

コミットメッセージに示されているベンチマーク結果は、この変更が実際にリンク時間の改善に寄与していることを明確に示しています。`LinkCmdGo`と`LinkJuju`という2つのベンチマークで、それぞれ3.34%と4.30%のリンク時間の短縮が達成されています。これは、オブジェクトファイルの構造を最適化することで、リンカのI/O効率が向上した結果です。

また、コミットメッセージでは「データセクションは読み込む代わりにmmapできるかもしれない」と述べられており、将来的なさらなる最適化の可能性も示唆されています。`mmap`（メモリマップドファイル）を使用することで、ファイルの内容を直接メモリにマッピングし、OSのページング機構を利用して必要な部分だけをオンデマンドで読み込むことが可能になり、I/Oオーバーヘッドをさらに削減できる可能性があります。

## 前提知識の解説

### Goのコンパイルとリンクのプロセス

Goのビルドプロセスは、主に以下のステップで構成されます。

1.  **コンパイル**: Goソースコード（`.go`ファイル）は、Goコンパイラによってアセンブリコードに変換され、最終的にオブジェクトファイル（通常は`.o`またはGo独自の形式）が生成されます。このオブジェクトファイルには、コンパイルされた関数、グローバル変数、型情報などのシンボルと、それらに関連するデータが含まれます。
2.  **リンク**: 生成された複数のオブジェクトファイルと、標準ライブラリなどの外部ライブラリがリンカによって結合され、実行可能なバイナリファイルが作成されます。リンカは、各オブジェクトファイル内のシンボル参照を解決し、最終的なメモリレイアウトを決定し、すべてのコードとデータを一つの実行ファイルにまとめます。

### Goのオブジェクトファイルフォーマット

Goのオブジェクトファイルは、一般的なELFやMach-Oのようなシステムネイティブなフォーマットとは異なり、Go独自のフォーマットを使用しています。このフォーマットは、Goのツールチェーン（コンパイラ、リンカなど）が効率的に情報をやり取りできるように設計されています。

オブジェクトファイルには、主に以下の情報が含まれます。

*   **ヘッダ**: ファイルのバージョン、マジックナンバーなど。
*   **依存関係**: インポートされているパッケージのリスト。
*   **シンボル参照**: このオブジェクトファイルが参照する外部シンボルのリスト。
*   **シンボル定義**: このオブジェクトファイル内で定義されているシンボルのリスト。各シンボルには、名前、型、サイズ、フラグなどのメタデータと、実際のコードやデータが含まれます。
*   **PC-lineテーブル**: プログラムカウンタ（PC）とソースコードの行番号のマッピング情報。デバッグやプロファイリングに利用されます。

### シンボルデータとメタデータ

*   **シンボルメタデータ**: シンボルの名前、型、サイズ、リンケージ情報、フラグなど、シンボル自体に関する記述情報です。
*   **シンボルデータ**: シンボルが表す実際のバイナリデータです。例えば、関数シンボルであればその関数の機械語コード、変数シンボルであればその変数の初期値データなどです。

以前のフォーマットでは、これらのメタデータとデータがオブジェクトファイル内で隣接して配置されていました。

### `mmap` (Memory-mapped file)

`mmap`は、ファイルやデバイスをプロセスのアドレス空間に直接マッピングするシステムコールです。これにより、ファイルの内容を通常のメモリとしてアクセスできるようになります。ファイルI/Oを`read()`や`write()`システムコールで行う代わりに、メモリへのアクセスとして扱うことができるため、特に大きなファイルを扱う場合にI/Oの効率が向上する可能性があります。OSのページング機構がファイルの読み込みを管理するため、必要な部分だけが物理メモリにロードされ、不要な部分はディスクにスワップアウトされます。

### `s/op` (seconds per operation)

ベンチマーク結果に表示される`s/op`は「seconds per operation」の略で、1回の操作にかかる平均時間を示します。この値が小さいほど、その操作は高速であることを意味します。`delta`は変更前後の性能差をパーセンテージで示しており、負の値は性能が向上したことを意味します。`p=0.000`は統計的に有意な差があることを示し、`n`はベンチマークの実行回数を示します。

## 技術的詳細

このコミットの核心は、Goのオブジェクトファイルフォーマットを変更し、すべてのシンボルデータをオブジェクトファイル内の単一の連続したセクションに集約することです。これにより、リンカがオブジェクトファイルを読み込む際のI/Oパターンが大幅に改善され、パフォーマンスが向上します。

### オブジェクトファイルフォーマットの変更

変更後のオブジェクトファイルフォーマットの概要は以下のようになります（関連部分のみ抜粋）：

```
//	- byte 1 - version number
//	- sequence of strings giving dependencies (imported packages)
//	- empty string (marks end of sequence)
//	- sequence of symbol references used by the defined symbols
//	- byte 0xff (marks end of sequence)
//	- integer (length of following data)  <-- 新しく追加されたデータブロックの長さ
//	- data, the content of the defined symbols <-- すべてのシンボルデータがここに連続して配置される
//	- sequence of defined symbols
//	- byte 0xff (marks end of sequence)
//	- magic footer: "\xff\xffgo13ld"
```

以前はシンボルメタデータとシンボルデータがインターリーブされていましたが、この変更により、シンボル参照の後にデータブロックの長さが記述され、その後にすべてのシンボルデータが連続して配置されるようになりました。そして、その後にシンボル定義（メタデータ）が続きます。

### 書き込み側の変更 (`src/cmd/internal/obj/objfile.go`)

`Writeobjfile`関数は、オブジェクトファイルを書き出す主要な関数です。

1.  **データ長の計算**: `Writeobjfile`内で、`dataLength`という変数が導入されました。この変数は、`ctxt.Text`（コードシンボル）と`ctxt.Data`（データシンボル）に含まれるすべてのシンボルデータ（`s.P`）およびPC-lineテーブルデータ（`pc.Pcsp.P`, `pc.Pcfile.P`, `pc.Pcline.P`, `pc.Pcdata[i].P`）の合計長を計算するために使用されます。
2.  **`wrdata`関数の削除**: 以前は、シンボルデータやPC-lineテーブルデータを書き込む際に`wrdata`関数が使用されていました。この関数は、データの長さと実際のデータをセットで書き出すものでした。このコミットでは`wrdata`関数が削除され、代わりにデータブロックの長さだけを書き込むように変更されました。
3.  **データブロックの一括書き込み**: シンボル参照の書き出しが完了した後、計算された`dataLength`がオブジェクトファイルに書き込まれます。その直後に、`ctxt.Text`と`ctxt.Data`に含まれるすべてのシンボルデータとPC-lineテーブルデータが、計算された順序で連続してファイルに書き込まれます。これにより、すべてのシンボルデータがオブジェクトファイル内の単一の連続したブロックにまとめられます。
4.  **`writesym`関数の変更**: `writesym`関数は、個々のシンボルをオブジェクトファイルに書き出す役割を担います。この関数では、以前`wrdata(b, s.P)`のようにデータ本体を直接書き出していた箇所が、`wrint(b, int64(len(s.P)))`のようにデータの長さだけを書き出すように変更されました。PC-lineテーブルデータについても同様の変更が適用されています。これにより、シンボル定義（メタデータ）にはデータの長さへの参照のみが含まれ、実際のデータは前述の連続したデータブロックに格納されることになります。

### 読み込み側の変更 (`src/cmd/internal/goobj/read.go`, `src/cmd/link/internal/ld/objfile.go`)

オブジェクトファイルを読み込む側も、新しいフォーマットに対応するために変更されました。

1.  **`objReader`構造体の変更 (`goobj/read.go`)**: `objReader`構造体に`dataOffset int64`フィールドが追加されました。これは、読み込み中のオブジェクトファイル内で、現在処理しているデータブロックのオフセットを追跡するために使用されます。
2.  **データブロックの一括読み込み (`ld/objfile.go`)**: `ldobjfile`関数は、リンカがオブジェクトファイルをロードする主要な関数です。この関数内で、シンボル参照の読み込みが完了した後、`dataLength`がオブジェクトファイルから読み込まれます。次に、この`dataLength`に基づいてバイトスライスが作成され、オブジェクトファイルからその長さ分のデータが一度に読み込まれ、このバイトスライスに格納されます。これにより、すべてのシンボルデータがメモリ上の連続したブロックにロードされます。
3.  **`readData`と`rddata`関数の変更**:
    *   `src/cmd/internal/goobj/read.go`の`readData`関数は、`r.offset`と`r.skip`を使ってファイルから直接データを読み飛ばす代わりに、`r.dataOffset`を使ってデータブロック内のオフセットを管理し、`r.dataOffset`をインクリメントするように変更されました。
    *   `src/cmd/link/internal/ld/objfile.go`の`rddata`関数は、以前はファイルから直接データを読み込んでいましたが、変更後は`buf *[]byte`という引数を受け取るようになりました。この`buf`は、前述の一括読み込みでメモリにロードされたデータブロックへのポインタです。`rddata`は、この`buf`から指定された長さのデータをスライスとして切り出し、`buf`を更新して次のデータが読み込めるようにします。これにより、ファイルI/Oを伴わずにメモリ上のデータにアクセスできるようになります。
4.  **`rddataBuf`の削除 (`ld/objfile.go`)**: 以前は、`rddata`関数内で一時的なバッファ`rddataBuf`を使用してデータを読み込んでいましたが、データが一括でメモリにロードされるようになったため、このバッファは不要となり削除されました。これにより、コードが簡素化され、メモリ管理も効率化されます。
5.  **`readsym`関数の変更 (`ld/objfile.go`)**: `readsym`関数も`buf *[]byte`引数を受け取るように変更され、シンボルデータやPC-lineテーブルデータを読み込む際に、新しい`rddata`関数を介してメモリ上のデータブロックからデータを取得するようになりました。

これらの変更により、リンカはオブジェクトファイルからシンボルデータを読み込む際に、ディスクシークを最小限に抑え、連続したメモリ領域から効率的にデータを取得できるようになります。これは、特に多数の小さなデータ片が散在している場合に、I/O性能を大きく向上させる効果があります。

## コアとなるコードの解説

このコミットにおけるコアとなる変更は、オブジェクトファイル内のシンボルデータとメタデータの物理的な配置を分離し、データ部分を連続したブロックとして扱うようにした点です。

### 書き込み側 (`objfile.go`) の解説

*   **`dataLength`の計算と一括書き込み**: `Writeobjfile`関数内で、すべてのシンボルデータ（`s.P`）とPC-lineテーブルデータ（`pc.Pcsp.P`など）の合計サイズを事前に計算し、`dataLength`として記録します。その後、オブジェクトファイルにこの`dataLength`を書き込み、その直後に計算されたすべてのデータを連続して書き出します。これにより、オブジェクトファイル内のデータは物理的に連続した領域に配置されることになります。
*   **`wrdata`の削除と`writesym`の変更**: 以前は`wrdata`関数がデータの長さとデータをセットで書き込んでいましたが、この変更により`wrdata`は不要となり削除されました。代わりに、`writesym`関数では、シンボルデータやPC-lineテーブルデータの「長さ」だけを書き込むように変更されました。実際のデータは、前述の一括書き込みのステップで処理されるため、シンボル定義（メタデータ）にはデータ本体は含まれず、その長さへの参照のみが含まれることになります。

このアプローチにより、リンカはシンボルメタデータを読み込む際に、データ本体をスキップして高速に処理できるようになります。また、データ本体が必要になった場合でも、連続したブロックから効率的に読み込むことが可能になります。

### 読み込み側 (`goobj/read.go`, `ld/objfile.go`) の解説

*   **`objReader.dataOffset`の導入**: `objReader`に`dataOffset`が追加されたことで、読み込み側はデータブロック内の現在位置を正確に追跡できるようになりました。
*   **データブロックの一括読み込み**: `ldobjfile`関数では、オブジェクトファイルから`dataLength`を読み込んだ後、その長さ分のバイトスライスを確保し、ファイルからデータブロック全体を一度にメモリに読み込みます。これにより、ディスクI/Oが大幅に削減されます。
*   **`rddata`関数の変更**: 最も重要な変更点の一つは`rddata`関数の実装です。以前はファイルから直接データを読み込んでいましたが、変更後はメモリにロードされたデータブロック（`buf`）から、指定された長さのデータをスライスとして切り出すようになりました。`p := (*buf)[:n:n]`は、`buf`の先頭から`n`バイト分のスライスを作成します。`*buf = (*buf)[n:]`は、`buf`のポインタを`n`バイト分進めることで、次に`rddata`が呼び出されたときに、データブロックの次の部分からデータを読み込めるようにします。このメカニズムにより、ファイルI/Oを伴わずに、メモリ上の連続したデータから必要な部分を効率的に取得できるようになります。
*   **`rddataBuf`の削除**: データが一括でメモリにロードされるため、以前使用されていた一時バッファ`rddataBuf`は不要となり、削除されました。これにより、コードが簡素化され、メモリ管理のオーバーヘッドも削減されます。

これらの変更は、オブジェクトファイルの物理的なレイアウトを最適化し、リンカがディスクからデータを読み込む際のシーク回数を減らし、連続した読み込みを可能にすることで、I/O性能を向上させます。結果として、Goプログラムのリンク時間が短縮され、ビルドプロセス全体の効率が向上します。

## 前提知識の解説

### Goのコンパイルとリンクのプロセス

Goのビルドプロセスは、主に以下のステップで構成されます。

1.  **コンパイル**: Goソースコード（`.go`ファイル）は、Goコンパイラによってアセンブリコードに変換され、最終的にオブジェクトファイル（通常は`.o`またはGo独自の形式）が生成されます。このオブジェクトファイルには、コンパイルされた関数、グローバル変数、型情報などのシンボルと、それらに関連するデータが含まれます。
2.  **リンク**: 生成された複数のオブジェクトファイルと、標準ライブラリなどの外部ライブラリがリンカによって結合され、実行可能なバイナリファイルが作成されます。リンカは、各オブジェクトファイル内のシンボル参照を解決し、最終的なメモリレイアウトを決定し、すべてのコードとデータを一つの実行ファイルにまとめます。

### Goのオブジェクトファイルフォーマット

Goのオブジェクトファイルは、一般的なELFやMach-Oのようなシステムネイティブなフォーマットとは異なり、Go独自のフォーマットを使用しています。このフォーマットは、Goのツールチェーン（コンパイラ、リンカなど）が効率的に情報をやり取りできるように設計されています。

オブジェクトファイルには、主に以下の情報が含まれます。

*   **ヘッダ**: ファイルのバージョン、マジックナンバーなど。
*   **依存関係**: インポートされているパッケージのリスト。
*   **シンボル参照**: このオブジェクトファイルが参照する外部シンボルのリスト。
*   **シンボル定義**: このオブジェクトファイル内で定義されているシンボルのリスト。各シンボルには、名前、型、サイズ、フラグなどのメタデータと、実際のコードやデータが含まれます。
*   **PC-lineテーブル**: プログラムカウンタ（PC）とソースコードの行番号のマッピング情報。デバッグやプロファイリングに利用されます。

### シンボルデータとメタデータ

*   **シンボルメタデータ**: シンボルの名前、型、サイズ、リンケージ情報、フラグなど、シンボル自体に関する記述情報です。
*   **シンボルデータ**: シンボルが表す実際のバイナリデータです。例えば、関数シンボルであればその関数の機械語コード、変数シンボルであればその変数の初期値データなどです。

以前のフォーマットでは、これらのメタデータとデータがオブジェクトファイル内で隣接して配置されていました。

### `mmap` (Memory-mapped file)

`mmap`は、ファイルやデバイスをプロセスのアドレス空間に直接マッピングするシステムコールです。これにより、ファイルの内容を通常のメモリとしてアクセスできるようになります。ファイルI/Oを`read()`や`write()`システムコールで行う代わりに、メモリへのアクセスとして扱うことができるため、特に大きなファイルを扱う場合にI/Oの効率が向上する可能性があります。OSのページング機構がファイルの読み込みを管理するため、必要な部分だけが物理メモリにロードされ、不要な部分はディスクにスワップアウトされます。

### `s/op` (seconds per operation)

ベンチマーク結果に表示される`s/op`は「seconds per operation」の略で、1回の操作にかかる平均時間を示します。この値が小さいほど、その操作は高速であることを意味します。`delta`は変更前後の性能差をパーセンテージで示しており、負の値は性能が向上したことを意味します。`p=0.000`は統計的に有意な差があることを示し、`n`はベンチマークの実行回数を示します。

## 技術的詳細

このコミットの核心は、Goのオブジェクトファイルフォーマットを変更し、すべてのシンボルデータをオブジェクトファイル内の単一の連続したセクションに集約することです。これにより、リンカがオブジェクトファイルを読み込む際のI/Oパターンが大幅に改善され、パフォーマンスが向上します。

### オブジェクトファイルフォーマットの変更

変更後のオブジェクトファイルフォーマットの概要は以下のようになります（関連部分のみ抜粋）：

```
//	- byte 1 - version number
//	- sequence of strings giving dependencies (imported packages)
//	- empty string (marks end of sequence)
//	- sequence of symbol references used by the defined symbols
//	- byte 0xff (marks end of sequence)
//	- integer (length of following data)  <-- 新しく追加されたデータブロックの長さ
//	- data, the content of the defined symbols <-- すべてのシンボルデータがここに連続して配置される
//	- sequence of defined symbols

以前はシンボルメタデータとシンボルデータがインターリーブされていましたが、この変更により、シンボル参照の後にデータブロックの長さが記述され、その後にすべてのシンボルデータが連続して配置されるようになりました。そして、その後にシンボル定義（メタデータ）が続きます。

### 書き込み側の変更 (`src/cmd/internal/obj/objfile.go`)

`Writeobjfile`関数は、オブジェクトファイルを書き出す主要な関数です。

1.  **データ長の計算**: `Writeobjfile`内で、`dataLength`という変数が導入されました。この変数は、`ctxt.Text`（コードシンボル）と`ctxt.Data`（データシンボル）に含まれるすべてのシンボルデータ（`s.P`）およびPC-lineテーブルデータ（`pc.Pcsp.P`, `pc.Pcfile.P`, `pc.Pcline.P`, `pc.Pcdata[i].P`）の合計長を計算するために使用されます。
2.  **`wrdata`関数の削除**: 以前は、シンボルデータやPC-lineテーブルデータを書き込む際に`wrdata`関数が使用されていました。この関数は、データの長さと実際のデータをセットで書き出すものでした。このコミットでは`wrdata`関数が削除され、代わりにデータブロックの長さだけを書き込むように変更されました。
3.  **データブロックの一括書き込み**: シンボル参照の書き出しが完了した後、計算された`dataLength`がオブジェクトファイルに書き込まれます。その直後に、`ctxt.Text`と`ctxt.Data`に含まれるすべてのシンボルデータとPC-lineテーブルデータが、計算された順序で連続してファイルに書き込まれます。これにより、すべてのシンボルデータがオブジェクトファイル内の単一の連続したブロックにまとめられます。
4.  **`writesym`関数の変更**: `writesym`関数は、個々のシンボルをオブジェクトファイルに書き出す役割を担います。この関数では、以前`wrdata(b, s.P)`のようにデータ本体を直接書き出していた箇所が、`wrint(b, int64(len(s.P)))`のようにデータの長さだけを書き出すように変更されました。PC-lineテーブルデータについても同様の変更が適用されています。これにより、シンボル定義（メタデータ）にはデータの長さへの参照のみが含まれ、実際のデータは前述の連続したデータブロックに格納されることになります。

### 読み込み側の変更 (`src/cmd/internal/goobj/read.go`, `src/cmd/link/internal/ld/objfile.go`)

オブジェクトファイルを読み込む側も、新しいフォーマットに対応するために変更されました。

1.  **`objReader`構造体の変更 (`goobj/read.go`)**: `objReader`構造体に`dataOffset int64`フィールドが追加されました。これは、読み込み中のオブジェクトファイル内で、現在処理しているデータブロックのオフセットを追跡するために使用されます。
2.  **データブロックの一括読み込み (`ld/objfile.go`)**: `ldobjfile`関数は、リンカがオブジェクトファイルをロードする主要な関数です。この関数内で、シンボル参照の読み込みが完了した後、`dataLength`がオブジェクトファイルから読み込まれます。次に、この`dataLength`に基づいてバイトスライスが作成され、オブジェクトファイルからその長さ分のデータが一度に読み込まれ、このバイトスライスに格納されます。これにより、すべてのシンボルデータがメモリ上の連続したブロックにロードされます。
3.  **`readData`と`rddata`関数の変更**:
    *   `src/cmd/internal/goobj/read.go`の`readData`関数は、`r.offset`と`r.skip`を使ってファイルから直接データを読み飛ばす代わりに、`r.dataOffset`を使ってデータブロック内のオフセットを管理し、`r.dataOffset`をインクリメントするように変更されました。
    *   `src/cmd/link/internal/ld/objfile.go`の`rddata`関数は、以前はファイルから直接データを読み込んでいましたが、変更後は`buf *[]byte`という引数を受け取るようになりました。この`buf`は、前述の一括読み込みでメモリにロードされたデータブロックへのポインタです。`rddata`は、この`buf`から指定された長さのデータをスライスとして切り出し、`buf`を更新して次のデータが読み込めるようにします。これにより、ファイルI/Oを伴わずにメモリ上のデータにアクセスできるようになります。
4.  **`rddataBuf`の削除 (`ld/objfile.go`)**: 以前は、`rddata`関数内で一時的なバッファ`rddataBuf`を使用してデータを読み込んでいましたが、データが一括でメモリにロードされるようになったため、このバッファは不要となり削除されました。これにより、コードが簡素化され、メモリ管理のオーバーヘッドも削減されます。
5.  **`readsym`関数の変更 (`ld/objfile.go`)**: `readsym`関数も`buf *[]byte`引数を受け取るように変更され、シンボルデータやPC-lineテーブルデータを読み込む際に、新しい`rddata`関数を介してメモリ上のデータブロックからデータを取得するようになりました。

これらの変更により、リンカはオブジェクトファイルからシンボルデータを読み込む際に、ディスクシークを最小限に抑え、連続したメモリ領域から効率的にデータを取得できるようになります。これは、特に多数の小さなデータ片が散在している場合に、I/O性能を大きく向上させる効果があります。

## コアとなるコードの解説

このコミットにおけるコアとなる変更は、オブジェクトファイル内のシンボルデータとメタデータの物理的な配置を分離し、データ部分を連続したブロックとして扱うようにした点です。

### 書き込み側 (`objfile.go`) の解説

*   **`dataLength`の計算と一括書き込み**: `Writeobjfile`関数内で、すべてのシンボルデータ（`s.P`）とPC-lineテーブルデータ（`pc.Pcsp.P`など）の合計サイズを事前に計算し、`dataLength`として記録します。その後、オブジェクトファイルにこの`dataLength`を書き込み、その直後に計算されたすべてのデータを連続して書き出します。これにより、オブジェクトファイル内のデータは物理的に連続した領域に配置されることになります。
*   **`wrdata`の削除と`writesym`の変更**: 以前は`wrdata`関数がデータの長さとデータをセットで書き込んでいましたが、この変更により`wrdata`は不要となり削除されました。代わりに、`writesym`関数では、シンボルデータやPC-lineテーブルデータの「長さ」だけを書き込むように変更されました。実際のデータは、前述の一括書き込みのステップで処理されるため、シンボル定義（メタデータ）にはデータ本体は含まれず、その長さへの参照のみが含まれることになります。

このアプローチにより、リンカはシンボルメタデータを読み込む際に、データ本体をスキップして高速に処理できるようになります。また、データ本体が必要になった場合でも、連続したブロックから効率的に読み込むことが可能になります。

### 読み込み側 (`goobj/read.go`, `ld/objfile.go`) の解説

*   **`objReader.dataOffset`の導入**: `objReader`に`dataOffset`が追加されたことで、読み込み側はデータブロック内の現在位置を正確に追跡できるようになりました。
*   **データブロックの一括読み込み**: `ldobjfile`関数では、オブジェクトファイルから`dataLength`を読み込んだ後、その長さ分のバイトスライスを確保し、ファイルからデータブロック全体を一度にメモリに読み込みます。これにより、ディスクI/Oが大幅に削減されます。
*   **`rddata`関数の変更**: 最も重要な変更点の一つは`rddata`関数の実装です。以前はファイルから直接データを読み込んでいましたが、変更後はメモリにロードされたデータブロック（`buf`）から、指定された長さのデータをスライスとして切り出すようになりました。`p := (*buf)[:n:n]`は、`buf`の先頭から`n`バイト分のスライスを作成します。`*buf = (*buf)[n:]`は、`buf`のポインタを`n`バイト分進めることで、次に`rddata`が呼び出されたときに、データブロックの次の部分からデータを読み込めるようにします。このメカニズムにより、ファイルI/Oを伴わずに、メモリ上の連続したデータから必要な部分を効率的に取得できるようになります。
*   **`rddataBuf`の削除**: データが一括でメモリにロードされるため、以前使用されていた一時バッファ`rddataBuf`は不要となり、削除されました。これにより、コードが簡素化され、メモリ管理のオーバーヘッドも削減されます。

これらの変更は、オブジェクトファイルの物理的なレイアウトを最適化し、リンカがディスクからデータを読み込む際のシーク回数を減らし、連続した読み込みを可能にすることで、I/O性能を向上させます。結果として、Goプログラムのリンク時間が短縮され、ビルドプロセス全体の効率が向上します。

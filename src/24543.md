## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、ブロックの制御操作 (control operations) をブロックの終端でライブであると扱うように変更します。これにより、他のブロックでライブであるべき制御操作が誤って削除されることを防ぎます。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA (Static Single Assignment) 形式を使用しています。SSA形式では、各変数は一度だけ代入されるという特性を持ち、これによってデータフロー解析や最適化が容易になります。レジスタ割り当てフェーズでは、ライブ変数解析 (Live Variable Analysis) を用いて、プログラムの各ポイントでどの変数が将来使用される可能性があるか（すなわち「ライブ」であるか）を判断します。この情報は、デッドコード削除や効率的なレジスタ割り当てに不可欠です。

このコミット以前のGoコンパイラのSSAバックエンドでは、ブロックの制御操作（例えば、条件分岐の条件式やループの終了条件など）が、そのブロックの終端で「ライブ」であると正しく認識されないという問題がありました。特に、これらの制御操作の結果が次のブロックの制御フローに影響を与える場合、ライブ変数解析が不完全であると、コンパイラはそれらの操作を「デッドコード」（将来使用されないコード）と誤認し、最適化の過程で削除してしまう可能性がありました。

結果として、コンパイルされたプログラムが意図しない動作をしたり、クラッシュしたりする可能性がありました。このコミットは、このライブ変数解析の不備を修正し、制御操作が常に正しくライブであると扱われるようにすることで、コンパイラの堅牢性と生成されるコードの正確性を向上させることを目的としています。

## 前提知識の解説

### GoコンパイラとSSA形式

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA (Static Single Assignment) 形式を採用しています。SSA形式は、プログラム中の各変数が一度だけ代入されるように変換された表現であり、これによりデータフロー解析が大幅に簡素化され、より強力な最適化（例えば、共通部分式の削除、定数伝播、デッドコード削除など）が可能になります。

### ライブ変数解析 (Live Variable Analysis)

ライブ変数解析は、データフロー解析の一種であり、プログラムの特定のポイントにおいて、ある変数の値が将来の計算で利用される可能性があるかどうか（すなわち「ライブ」であるか）を決定します。変数がライブでない場合（「デッド」である場合）、その変数の値はもはや必要なく、その変数を計算する命令はデッドコードとして削除されたり、その変数が占めていたレジスタやメモリ領域が再利用されたりする可能性があります。

ライブ変数解析は通常、プログラムの制御フローグラフ (Control Flow Graph, CFG) を逆方向に辿ることで行われます。ブロックの終端でライブな変数の集合は、そのブロックのサクセッサ（後続ブロック）の開始点でライブな変数の集合と、そのブロック内で使用される変数に基づいて計算されます。

### 制御操作 (Control Operations)

制御操作とは、プログラムの実行フローを決定する命令のことです。これには、条件分岐 (if/else)、ループ (for)、関数呼び出し、return文、panic/recoverなどが含まれます。SSA形式では、これらの操作も `Value` として表現され、ブロックの `Control` フィールドに格納されることがあります。例えば、`if` 文の条件式は、そのブロックの制御操作となり、どのパスに進むかを決定します。

### レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要なフェーズの一つで、プログラム中の変数をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりも高速にアクセスできるため、効率的なレジスタ割り当てはプログラムの実行速度に大きく影響します。ライブ変数解析の結果は、レジスタ割り当てにおいて、どの変数が同時にレジスタを必要とするか（競合するか）を判断するために使用されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるライブ変数解析の精度向上にあります。具体的には、`src/cmd/compile/internal/ssa/regalloc.go` 内の `live` 関数が修正されています。

`live` 関数は、各ブロックの終端でライブな値の集合を計算する役割を担っています。以前の実装では、ブロックの `Control` フィールドに格納されている制御操作（例えば、条件分岐の条件を評価する `Value`）が、そのブロックの終端でライブであると明示的に扱われていませんでした。

問題のシナリオは以下の通りです。
1.  あるブロック `B` があり、その `Control` フィールドに `C` という `Value` が設定されているとします。`C` は、`B` の後続ブロックへの制御フローを決定します。
2.  `C` は、`B` の後続ブロックで実際に使用される（例えば、分岐命令のオペランドとして）ため、本来であれば `B` の終端で「ライブ」であるべきです。
3.  しかし、ライブ変数解析が `C` を明示的にライブセットに追加しない場合、`C` は `B` の終端でデッドであると誤認される可能性があります。
4.  この誤認により、コンパイラの最適化フェーズ（特にデッドコード削除）で `C` を計算する命令が削除されてしまい、結果としてプログラムの制御フローが壊れる、あるいは不正な動作を引き起こす可能性がありました。

このコミットでは、`regalloc.go` の `live` 関数において、各ブロック `b` を処理する際に、`b.Control` が `nil` でない場合、その `b.Control.ID` を明示的にライブセット `s` に追加するように変更されました。これにより、制御操作が常にブロックの終端でライブであると正しく認識され、誤って削除されることがなくなります。

また、`src/cmd/compile/internal/ssa/check.go` には、`checkFunc` 関数内に新しい検証ロジックが追加されました。これは、各ブロックの `Control` `Value` が、`valueMark` マップによってライブとしてマークされていることを確認するものです。このチェックは、ライブ変数解析が正しく機能していることを保証するための追加の安全策として機能します。もし制御 `Value` がライブとしてマークされていない場合、コンパイラは致命的なエラー (`f.Fatalf`) を発生させ、問題を早期に検出します。

さらに、`src/cmd/compile/internal/ssa/regalloc_test.go` に新しいテストケース `TestLiveControlOps` が追加されました。このテストは、複数のブロックにまたがる複雑な制御フローを持つ関数を構築し、レジスタ割り当てとライブネスチェックが正しく行われることを検証します。これにより、今回の修正が特定のバグシナリオを確実に捕捉し、将来のリグレッションを防ぐことができます。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/regalloc.go` の変更

`live` 関数は、ライブ変数解析の主要なロジックを含んでいます。この関数は、各ブロック `b` の終端から逆方向にライブ変数を伝播させていきます。

```go
			// Start with known live values at the end of the block
			s.clear()
			s.addAll(live[b.ID])
			if b.Control != nil {
				s.add(b.Control.ID)
			}
```

この変更は、ブロック `b` の終端でライブであると初期化される値のセット `s` に、`b.Control` が存在する場合、その `Control` `Value` のIDを明示的に追加しています。これにより、制御操作が常にライブであると認識され、デッドコード削除の対象から外れるようになります。これは、制御フローを決定する `Value` が、その決定が実際に使用される場所（通常は後続ブロックの分岐命令など）までライブである必要があるという、ライブ変数解析の基本的な要件を満たすための重要な修正です。

また、コメントの修正 `// inv: s contains the values live at the start of b (excluding phi inputs)` から `// invariant: s contains the values live at the start of b (excluding phi inputs)` は、コメントのtypo修正であり、コードの動作には影響しませんが、コードの可読性と正確性を向上させています。

### `src/cmd/compile/internal/ssa/check.go` の変更

`checkFunc` 関数は、SSA形式の関数が特定の不変条件を満たしているかを検証するためのデバッグ/チェック関数です。

```go
	for _, b := range f.Blocks {
		if b.Control != nil {
			if !valueMark[b.Control.ID] {
				f.Fatalf("control value for %s is missing: %v", b, b.Control)
			}
		}
	}
```

この追加されたループは、関数 `f` 内のすべてのブロック `b` を反復処理します。もしブロック `b` に制御 `Value` (`b.Control`) が設定されている場合、`valueMark` マップ（これはライブ変数解析の結果を保持していると推測されます）をチェックし、その制御 `Value` のIDがライブとしてマークされていることを確認します。もしマークされていない場合、それはライブ変数解析に問題があることを示唆するため、コンパイラはエラーを発生させて停止します。これは、`regalloc.go` で行われた修正が正しく機能していることを検証するための、重要なアサーションチェックです。

レジスタ割り当ては、コンパイラのバックエンドにおける重要なフェーズの一つで、プログラム中の変数をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりも高速にアクセスできるため、効率的なレジスタ割り当てはプログラムの実行速度に大きく影響します。ライブ変数解析の結果は、レジスタ割り当てにおいて、どの変数が同時にレジスタを必要とするか（競合するか）を判断するために使用されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるライブ変数解析の精度向上にあります。具体的には、`src/cmd/compile/internal/ssa/regalloc.go` 内の `live` 関数が修正されています。

`live` 関数は、各ブロックの終端でライブな値の集合を計算する役割を担っています。以前の実装では、ブロックの `Control` フィールドに格納されている制御操作（例えば、条件分岐の条件を評価する `Value`）が、そのブロックの終端でライブであると明示的に扱われていませんでした。

問題のシナリオは以下の通りです。
1.  あるブロック `B` があり、その `Control` フィールドに `C` という `Value` が設定されているとします。`C` は、`B` の後続ブロックへの制御フローを決定します。
2.  `C` は、`B` の後続ブロックで実際に使用される（例えば、分岐命令のオペランドとして）ため、本来であれば `B` の終端で「ライブ」であるべきです。
3.  しかし、ライブ変数解析が `C` を明示的にライブセットに追加しない場合、`C` は `B` の終端でデッドであると誤認される可能性があります。
4.  この誤認により、コンパイラの最適化フェーズ（特にデッドコード削除）で `C` を計算する命令が削除されてしまい、結果としてプログラムの制御フローが壊れる、あるいは不正な動作を引き起こす可能性がありました。

このコミットでは、`regalloc.go` の `live` 関数において、各ブロック `b` を処理する際に、`b.Control` が `nil` でない場合、その `b.Control.ID` を明示的にライブセット `s` に追加するように変更されました。これにより、制御操作が常にブロックの終端でライブであると正しく認識され、誤って削除されることがなくなります。

また、`src/cmd/compile/internal/ssa/check.go` には、`checkFunc` 関数内に新しい検証ロジックが追加されました。これは、各ブロックの `Control` `Value` が、`valueMark` マップによってライブとしてマークされていることを確認するものです。このチェックは、ライブ変数解析が正しく機能していることを保証するための追加の安全策として機能します。もし制御 `Value` がライブとしてマークされていない場合、コンパイラは致命的なエラー (`f.Fatalf`) を発生させ、問題を早期に検出します。

さらに、`src/cmd/compile/internal/ssa/regalloc_test.go` に新しいテストケース `TestLiveControlOps` が追加されました。このテストは、複数のブロックにまたがる複雑な制御フローを持つ関数を構築し、レジスタ割り当てとライブネスチェックが正しく行われることを検証します。これにより、今回の修正が特定のバグシナリオを確実に捕捉し、将来のリグレッションを防ぐことができます。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/regalloc.go` の変更

`live` 関数は、ライブ変数解析の主要なロジックを含んでいます。この関数は、各ブロック `b` の終端から逆方向にライブ変数を伝播させていきます。

```go
			// Start with known live values at the end of the block
			s.clear()
			s.addAll(live[b.ID])
			if b.Control != nil {
				s.add(b.Control.ID)
			}
```

この変更は、ブロック `b` の終端でライブであると初期化される値のセット `s` に、`b.Control` が存在する場合、その `Control` `Value` のIDを明示的に追加しています。これにより、制御操作が常にライブであると認識され、デッドコード削除の対象から外れるようになります。これは、制御フローを決定する `Value` が、その決定が実際に使用される場所（通常は後続ブロックの分岐命令など）までライブである必要があるという、ライブ変数解析の基本的な要件を満たすための重要な修正です。

また、コメントの修正 `// inv: s contains the values live at the start of b (excluding phi inputs)` から `// invariant: s contains the values live at the start of b (excluding phi inputs)` は、コメントのtypo修正であり、コードの動作には影響しませんが、コードの可読性と正確性を向上させています。

### `src/cmd/compile/internal/ssa/check.go` の変更

`checkFunc` 関数は、SSA形式の関数が特定の不変条件を満たしているかを検証するためのデバッグ/チェック関数です。

```go
	for _, b := range f.Blocks {
		if b.Control != nil {
			if !valueMark[b.Control.ID] {
				f.Fatalf("control value for %s is missing: %v", b, b.Control)
			}
		}
	}
```

この追加されたループは、関数 `f` 内のすべてのブロック `b` を反復処理します。もしブロック `b` に制御 `Value` (`b.Control`) が設定されている場合、`valueMark` マップ（これはライブ変数解析の結果を保持していると推測されます）をチェックし、その制御 `Value` のIDがライブとしてマークされていることを確認します。もしマークされていない場合、それはライブ変数解析に問題があることを示唆するため、コンパイラはエラーを発生させて停止します。これは、`regalloc.go` で行われた修正が正しく機能していることを検証するための、重要なアサーションチェックです。

### `src/cmd/compile/internal/ssa/regalloc_test.go` の追加

このファイルは新規追加されたテストケースです。

```go

このテストの目的は、`regalloc(f.f)`（レジスタ割り当てとライブ変数解析を実行する関数）が実行された後、`checkFunc(f.f)` がエラーを発生させずに完了することを確認することです。もし `regalloc` が制御操作を正しくライブとして扱わない場合、`checkFunc` 内の新しいアサーションが失敗し、テストが失敗するでしょう。このテストは、今回の修正が意図した通りに機能し、制御操作が誤って削除されないことを保証するための具体的なシナリオを提供します。

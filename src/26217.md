# [インデックス 26217] ファイルの概要

## コミット
このコミットは、`cmd/go` ツールにおいて、共有ライブラリのビルド時に `$prefix/...` の形式でパッケージが指定された場合の命名規則を特別に処理するように変更します。具体的には、以前の変更によって長くなりすぎていた共有ライブラリ名を、特定のパターンに対しては短く、予測可能な形式に戻すことを目的としています。

## 元コミット内容
```
cmd/go: special case shared library name when passed "$prefix/..."

Before golang.org/cl/13921, "go install -buildmode=shared prefix/..." created a
file called "libprefix.so", which was obviously a problem when prefix was
something like "." or "../". However, now it expands the ... into all the
matched packages, joins them with -, which can clearly be a very long name
indeed. Because I plan to build shared libraries for Ubuntu by running commands
exactly like "go install -buildmode=shared prefix/...", this special cases this
to produce the old behaviour (but de-relativises prefix first).

Fixes #13714

Change-Id: I4fd8d4934279f9a18cc70a13e4ef3e23f6abcb6e
Reviewed-on: https://go-review.googlesource.com/18114
Reviewed-by: Ian Lance Taylor <iant@golang.org>
```

## 変更の背景
Go 1.5以降に導入された `go install -buildmode=shared` コマンドは、Goパッケージを共有ライブラリ（Linuxでは `.so` ファイル）としてビルドする機能を提供します。これにより、複数のGoプログラムが共通のGoパッケージにリンクできるようになり、バイナリサイズやメモリフットプリントの削減が期待されます。

このコミットの背景には、共有ライブラリの命名規則に関する問題がありました。
1.  **`golang.org/cl/13921` 以前**: `go install -buildmode=shared prefix/...` は `libprefix.so` という名前の共有ライブラリを生成していました。しかし、`prefix` が `.` や `../` のような相対パスである場合、この命名は問題を引き起こす可能性がありました。
2.  **`golang.org/cl/13921` 以降**: 上記の問題を解決するためか、`golang.org/cl/13921` の変更によって、`...` はマッチする全てのパッケージに展開され、それらがハイフン (`-`) で結合されるようになりました。これにより、生成される共有ライブラリ名が非常に長くなるという新たな問題が発生しました。
3.  **本コミットの動機**: コミットの作者は、Ubuntu向けに共有ライブラリをビルドする際に `go install -buildmode=shared prefix/...` というコマンドを使用する計画があり、この際に生成される共有ライブラリ名が長すぎることを懸念していました。そのため、`prefix/...` の形式で指定された場合に限り、以前の `libprefix.so` のような短い命名規則に戻しつつ、`prefix` が相対パスであっても適切に処理（非相対化）されるようにする変更が必要となりました。

この変更は、Go issue [#13714](https://github.com/golang/go/issues/13714) で報告された「`go install -buildmode=shared prefix/...` が \"file name too long\" で失敗する可能性がある」という問題を解決するものです。

## 前提知識の解説

*   **`go install -buildmode=shared`**: Go言語のビルドコマンドの一つで、指定されたGoパッケージを共有ライブラリ（例: Linuxでは `.so`、macOSでは `.dylib`、Windowsでは `.dll`）としてコンパイルし、インストールします。これにより、複数のGoプログラムやC/C++プログラムからGoのコードを再利用できるようになります。
*   **共有ライブラリ (Shared Library)**: 複数のプログラムから共有して利用されるライブラリのことです。これにより、ディスクスペースの節約、メモリ使用量の削減、プログラムのモジュール化などが可能になります。
*   **パッケージパスと `...` (Ellipsis)**: Goのパッケージパスは、通常、`github.com/user/repo/package` のような形式で指定されます。`...` は、そのディレクトリ以下の全てのサブパッケージを意味するワイルドカードです。例えば、`prefix/...` は `prefix` ディレクトリ以下の全てのGoパッケージを指します。
*   **`libname` 関数**: `cmd/go` ツール内部で、共有ライブラリのファイル名を決定するために使用される関数です。この関数が、本コミットで変更される主要なロジックを含んでいます。
*   **`build.IsLocalImport`**: Goの `go/build` パッケージにある関数で、与えられたパスがローカルインポートパス（例: `./foo` や `../bar`）であるかどうかを判定します。
*   **`buildContext.ImportDir`**: 指定されたディレクトリのGoパッケージ情報を取得する関数です。`build.FindOnly` フラグを使用すると、パッケージの検索のみを行い、コンパイルは行いません。
*   **`filepath.Join`**: OSに依存しない形でパスを結合する関数です。
*   **`os.Getwd`**: 現在の作業ディレクトリの絶対パスを取得する関数です。

## 技術的詳細

このコミットは、`cmd/go` の `libname` 関数における共有ライブラリ名の生成ロジックを修正します。

以前の `golang.org/cl/13921` の変更により、`go install -buildmode=shared prefix/...` のようなコマンドが実行された際、`...` が展開されてマッチする全てのパッケージのインポートパスがハイフンで結合され、非常に長い共有ライブラリ名が生成される可能性がありました。これは、特にUbuntuのようなシステムで共有ライブラリを管理する際に問題となる「ファイル名が長すぎる」というエラーを引き起こす原因となっていました。

本コミットでは、この問題を解決するために、`libname` 関数に以下の特別なケース処理を追加します。

1.  **単一の引数と `strings.HasSuffix(args[0], "/...")` のチェック**: `libname` 関数に渡される引数 (`args`) が一つだけであり、かつその引数が `"/..."` で終わる場合に、この特別な処理が適用されます。これは、`go install -buildmode=shared foo/...` のようなコマンドを対象とします。
2.  **`prefix` の非相対化**:
    *   `arg := strings.TrimSuffix(args[0], "/...")` で `prefix` 部分を抽出します。
    *   `build.IsLocalImport(arg)` を使用して、抽出された `prefix` が `./` や `../` のような相対パスであるかをチェックします。
    *   もし相対パスであれば、`os.Getwd()` で現在の作業ディレクトリを取得し、`filepath.Join(cwd, arg)` で絶対パスに変換します。
    *   さらに、`buildContext.ImportDir(absolutePath, build.FindOnly)` を使用して、その絶対パスに対応するGoパッケージのインポートパスを取得します。これにより、相対パスが実際のインポートパス（例: `github.com/user/repo/foo`）に解決されます。
    *   解決されたインポートパスが空でなく、かつ `.` でない場合、そのインポートパスを新たな `arg` として使用します。
3.  **短い命名規則の適用**: 非相対化された `arg` （または元々非相対だった `prefix`）に対して、`strings.Replace(arg, "/", "-", -1)` を適用し、スラッシュをハイフンに置換します。これにより、`libprefix.so` のような短い共有ライブラリ名が生成されます。

この変更により、`prefix/...` の形式で指定された場合でも、共有ライブラリ名が不必要に長くなることを防ぎ、かつ相対パスの `prefix` も適切に処理されるようになります。

テストファイル `src/cmd/go/pkg_test.go` では、`TestSharedLibName` 関数に `rootedAt` フィールドが追加され、テスト実行時に一時的なGOPATH環境を設定し、指定されたルートディレクトリで `os.Chdir` を行うことで、相対パスのテストケースをより正確にシミュレートできるようになっています。これにより、`./...` や `../` のような相対パスが正しく非相対化され、期待される共有ライブラリ名が生成されることを検証しています。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更点
`libname` 関数は、共有ライブラリのファイル名を決定する主要なロジックを含んでいます。変更の中心は、`len(libname) == 0` （メタパッケージが指定されていない場合）のブロック内です。

*   **変更前**:
    ```go
    for _, pkg := range pkgs {
        appendName(strings.Replace(pkg.ImportPath, "/", "-", -1))
    }
    ```
    このコードは、`pkgs` リスト内の全てのパッケージのインポートパスを取得し、スラッシュをハイフンに置換して `libname` に追加していました。`prefix/...` のようなパターンが指定された場合、`pkgs` にはマッチする全てのサブパッケージが含まれるため、結果として非常に長い名前が生成されていました。

*   **変更後**:
    ```go
    if len(args) == 1 && strings.HasSuffix(args[0], "/...") {
        // Special case of "foo/..." as mentioned above.
        arg := strings.TrimSuffix(args[0], "/...")
        if build.IsLocalImport(arg) {
            cwd, _ := os.Getwd()
            bp, _ := buildContext.ImportDir(filepath.Join(cwd, arg), build.FindOnly)
            if bp.ImportPath != "" && bp.ImportPath != "." {
                arg = bp.ImportPath
            }
        }
        appendName(strings.Replace(arg, "/", "-", -1))
    } else {
        for _, pkg := range pkgs {
            appendName(strings.Replace(pkg.ImportPath, "/", "-", -1))
        }
    }
    ```
    この変更により、以下のロジックが追加されました。
    1.  `args` の数が1つであり、かつその引数が `"/..."` で終わる場合（例: `foo/...` や `./...`）、特別な処理が適用されます。
    2.  `args[0]` から `"/..."` を取り除き、`arg` 変数に `prefix` 部分（例: `foo` や `.`）を格納します。
    3.  `build.IsLocalImport(arg)` で `arg` が相対パスであるかを確認します。
    4.  もし相対パスであれば、`os.Getwd()` で現在の作業ディレクトリを取得し、`filepath.Join(cwd, arg)` で絶対パスを構築します。
    5.  `buildContext.ImportDir(absolutePath, build.FindOnly)` を呼び出して、その絶対パスに対応するGoパッケージのインポートパスを取得します。これにより、相対パスが `github.com/user/repo/foo` のような標準的なインポートパスに解決されます。
    6.  解決された `bp.ImportPath` が空でなく、かつ `.` でない場合、`arg` をそのインポートパスで上書きします。
    7.  最終的に、非相対化された（または元々非相対だった）`arg` に対して `strings.Replace(arg, "/", "-", -1)` を適用し、スラッシュをハイフンに置換して `libname` に追加します。これにより、`libfoo.so` のような短い名前が生成されます。
    8.  上記の条件に合致しない場合は、以前と同様に `pkgs` 内の全てのパッケージのインポートパスを結合するロジックが実行されます。

この変更により、`prefix/...` のような特定のパターンに対しては、共有ライブラリ名が短く、予測可能な形式で生成されるようになり、ファイル名が長すぎる問題が回避されます。

### `src/cmd/go/pkg_test.go` の変更点
テストファイルでは、`TestSharedLibName` 関数内のテストデータ構造体 `testData` に `rootedAt string` フィールドが追加されました。

*   **`rootedAt` フィールドの目的**: このフィールドは、テストケースが特定のディレクトリ構造（GOPATH内）で実行されるべきであることを示します。例えば、`rootedAt: "somelib"` の場合、テストは一時的なGOPATHの `src/somelib` ディレクトリに `os.Chdir` して実行されます。
*   **テストロジックの変更**:
    *   各テストケースの実行前に、`data.rootedAt` が設定されているかを確認します。
    *   設定されている場合、一時的なGOPATHディレクトリを作成し、その中に `src/data.rootedAt` というディレクトリ構造を作成します。
    *   `buildContext.GOPATH` を一時的なGOPATHに設定し、`os.Chdir` で `src/data.rootedAt` ディレクトリに移動します。
    *   テスト実行後、`defer` を使用して一時ディレクトリのクリーンアップと元のGOPATHおよび作業ディレクトリへの復元を行います。
*   **新しいテストケース**: `rootedAt` を使用した新しいテストケースが追加され、`./...` のような相対パスが正しく処理され、期待される短い共有ライブラリ名が生成されることを検証しています。例えば、`args: []string{"./..."}` と `rootedAt: "somelib"` のテストケースでは、期待される結果が `"somelib"` となっています。また、`args: []string{"./..."}` と `rootedAt: "gopkg.in"` のテストケースでは、期待される結果が `"gopkg.in"` となっています。

これらのテストの変更は、`build.go` で導入された相対パスの非相対化ロジックが正しく機能することを保証するために不可欠です。

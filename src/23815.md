## 元コミット内容

このコミットは、`x/tools/go/types` リポジトリで行われた複数の変更を、Go のメインリポジトリ内の `go/types` パッケージに統合するものです。具体的には、以下の変更が含まれています。

*   **`Eval` 関数への `pos` パラメータの追加と `New`, `EvalNode` 関数の削除**: これが主要な変更であり、式の評価時に正確な位置情報（`token.Pos`）を考慮に入れることで、より正確な型チェックとスコープ解決を可能にします。
*   **テストからのグローバル変数の削除**: テストの独立性と信頼性を向上させるためのクリーンアップ。
*   **`NewSignature` からの未使用の `scope` パラメータの削除**: API の簡素化と不要な情報の排除。
*   **ファイルスコープへの完全なソースファイル範囲の提供**: スコープの境界をより正確に定義し、コメントなどの非コード要素も考慮に入れることで、より堅牢な型チェックを可能にします。
*   **`resolver.go` のコメント修正**: コードの可読性と理解を向上させるためのドキュメント修正。
*   **`cmd/vet` の更新**: `go/types` パッケージの変更に合わせて、静的解析ツール `vet` を更新。
*   **不正確または欠落した位置情報に対する堅牢性の向上**: エラーハンドリングを強化し、不正な入力に対しても安定した動作を保証します。

## 変更の背景

Go の `go/types` パッケージは、Go プログラムの型チェックとセマンティック解析を行うための重要なライブラリです。このパッケージは、コンパイラ、リンター、IDE などのツールが Go コードを理解し、エラーを検出するために利用されます。

以前の `Eval` 関数は、文字列として与えられた式を評価する際に、その式がどのコンテキスト（特にどの位置）で評価されるべきかという情報が不足していました。これにより、特にスコープ解決において曖昧さや不正確さが生じる可能性がありました。例えば、同じ名前の変数が異なるスコープに存在する場合、どの変数を参照すべきかを正確に判断するのが困難になることがあります。

この問題を解決するため、`Eval` 関数に `token.Pos` 型の `pos` パラメータが追加されました。これにより、式が評価される正確なソースコード上の位置が提供され、`go/types` パッケージはより正確なスコープ解決と型チェックを実行できるようになります。

また、`New` と `EvalNode` 関数は、`Eval` 関数の新しいシグネチャと機能によって冗長になったため、削除されました。これは API の簡素化と、コードベースの一貫性を保つための変更です。

その他のクリーンアップや修正は、この主要な変更に伴うものであり、`go/types` パッケージ全体の堅牢性、正確性、保守性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

*   **Go の `go/types` パッケージ**: Go 言語の型システムをモデル化し、Go プログラムのセマンティック解析（型チェック、スコープ解決など）を行うためのライブラリです。コンパイラや静的解析ツールが Go コードを理解するために使用します。
*   **`go/ast` パッケージ**: Go ソースコードの抽象構文木（AST）を表現するためのパッケージです。Go のパーサーがソースコードを解析して AST を生成し、`go/types` パッケージはその AST を入力としてセマンティック解析を行います。
*   **`go/token` パッケージ**: ソースコード内の位置情報（ファイル、行、列など）を表現するための `token.Pos` 型を提供します。これは、エラーメッセージの表示や、特定のコード要素がどこにあるかを特定するために重要です。
*   **スコープ (Scope)**: プログラミング言語において、識別子（変数、関数、型など）が有効である範囲を指します。Go では、ブロック、関数、パッケージごとに異なるスコープが存在し、識別子の可視性が制御されます。`go/types` パッケージは、`Scope` オブジェクトを使用してこれらのスコープを管理します。
*   **`Object`**: `go/types` パッケージにおける、名前付きのエンティティ（変数、定数、関数、型など）を表すインターフェースです。各 `Object` は、その名前、型、宣言された位置などの情報を持っています。
*   **`LookupParent` メソッド**: `Scope` オブジェクトのメソッドで、現在のスコープから親スコープへと遡りながら、指定された名前の識別子を検索します。
*   **`NewSignature` 関数**: 関数のシグネチャ（引数と戻り値の型、可変長引数かどうかなど）を表現する `Signature` 型のインスタンスを作成する関数です。
*   **`cmd/vet`**: Go の静的解析ツールの一つで、疑わしいコード構造や潜在的なバグを検出します。`go/types` パッケージを利用してコードのセマンティックな側面を分析します。

## 技術的詳細

### `Eval` 関数の変更

以前の `Eval` 関数は、`Eval(str string, pkg *Package, scope *Scope)` のシグネチャを持っていました。この関数は、与えられた文字列 `str` を式として解析し、指定された `pkg` と `scope` のコンテキストで評価していました。しかし、`scope` パラメータだけでは、式がソースコードのどの「正確な位置」で評価されるべきかという情報が不足していました。

新しい `Eval` 関数は、`Eval(fset *token.FileSet, pkg *Package, pos token.Pos, expr string)` のシグネチャに変更されました。
*   `fset *token.FileSet`: ソースファイルセット。位置情報を解決するために必要です。
*   `pkg *Package`: 式が評価されるパッケージ。
*   `pos token.Pos`: 式が評価されるソースコード上の正確な位置。この `pos` が導入されたことで、`go/types` は `LookupParent` などのスコープ解決メカニズムにおいて、より正確なコンテキストで識別子を検索できるようになりました。
*   `expr string`: 評価される式を表す文字列。

この変更により、`Eval` は特定の `pos` におけるスコープを正確に特定し、その位置での識別子の可視性を考慮して式を評価できるようになります。これは、特にシャドーイング（内側のスコープで外側のスコープの識別子と同じ名前の識別子が宣言されること）が発生する場合に重要です。

### `New` および `EvalNode` 関数の削除

`New` 関数は `Eval` のラッパーとして機能し、エラー時にパニックを発生させる簡便な関数でした。`EvalNode` は `Eval` と同様に AST ノードを直接受け取る関数でした。`Eval` が `pos` パラメータを受け取るようになり、より柔軟かつ正確な評価が可能になったため、これらの関数は冗長となり削除されました。これにより、API が簡素化され、`Eval` を中心とした一貫した評価メカニズムが提供されます。

### `Scope` と `Object` の変更

*   **`Scope` 構造体の拡張**: `Scope` 構造体に `pos` と `end` フィールドが追加されました。これらはスコープのソースコード上の範囲 `[pos, end)` を表します。これにより、スコープがソースコードのどこに存在するかを正確に追跡できるようになり、`Innermost` や `Contains` といったメソッドを通じて、特定の位置がどのスコープに属するかを効率的に判断できるようになりました。
*   **`Object` インターフェースの拡張**: `Object` インターフェースに `scopePos()` と `setScopePos(pos token.Pos)` メソッドが追加されました。これにより、各 `Object`（識別子）がどの位置で宣言されたかという情報を持つことができるようになりました。これは、`LookupParent` メソッドが `pos` パラメータを受け取るようになった際に、その位置よりも前に宣言された識別子のみを考慮するために使用されます。
*   **`LookupParent` メソッドの変更**: `LookupParent(name string)` が `LookupParent(name string, pos token.Pos)` に変更されました。`pos` が有効な場合、`LookupParent` は `pos` よりも前に宣言された `Object` のみを検索対象とします。これにより、Go の言語仕様で定義されている「宣言された位置より後でなければ識別子は参照できない」というルールを正確に強制できるようになります。

### その他のクリーンアップと修正

*   **`NewSignature` の変更**: `NewSignature(scope *Scope, recv *Var, params, results *Tuple, variadic bool)` から `scope` パラメータが削除され、`NewSignature(recv *Var, params, results *Tuple, variadic bool)` となりました。これは、関数のシグネチャ自体がスコープを持つのではなく、関数が宣言されるコンテキストでスコープが管理されるべきであるという設計思想の変更を反映しています。
*   **`declare` 関数の変更**: `declare(scope *Scope, id *ast.Ident, obj Object)` が `declare(scope *Scope, id *ast.Ident, obj Object, pos token.Pos)` に変更されました。これにより、識別子が宣言される正確な位置を `Object` に関連付けることができるようになり、スコープ解決の精度が向上します。
*   **ファイルスコープの範囲の正確化**: `resolver.go` でファイルスコープを作成する際に、`*ast.File` の範囲だけでなく、`*token.File` の情報も利用して、コメントを含む完全なソースファイル範囲をスコープに設定するようになりました。これにより、スコープの境界がより正確になります。
*   **`cmd/vet` の更新**: `shadow.go` や `unused.go` など、`cmd/vet` の一部のファイルが `go/types` の変更に合わせて更新されました。特に `checkShadowing` 関数では、`LookupParent` に `obj.Pos()` を渡すことで、シャドーイングの検出がより正確になりました。

## コアとなるコードの解説

### `Eval` 関数の変更 (`src/go/types/eval.go`)

*   **シグネチャの変更**: `Eval` 関数のシグネチャが `(str string, pkg *Package, scope *Scope)` から `(fset *token.FileSet, pkg *Package, pos token.Pos, expr string)` に変更されました。これにより、評価コンテキストに `token.FileSet` と `token.Pos` が明示的に含まれるようになり、より正確な位置情報に基づいたスコープ解決が可能になります。
*   **`New` と `EvalNode` の削除**: 以前の `New` と `EvalNode` 関数は、新しい `Eval` 関数の機能によって不要になったため削除されました。これにより、API が簡素化され、`Eval` が式評価の主要なエントリポイントとなります。
*   **スコープ決定ロジックの改善**: `Eval` 関数内で、`pkg` と `pos` の値に基づいて適切なスコープを決定するロジックが追加されました。`pos.IsValid()` が `true` の場合、`pkg.scope.children` を走査し、`fscope.Innermost(pos)` を呼び出して、指定された位置 `pos` を含む最も内側のスコープを特定します。これにより、式が評価される正確なコンテキストが確立されます。
*   **`check.pos` の設定**: `NewChecker` で作成された `check` オブジェクトの `pos` フィールドに、`Eval` に渡された `pos` が設定されます。この `check.pos` は、`LookupParent` などのスコープ解決メソッドで利用され、位置情報に基づいた識別子の検索を可能にします。

### `Scope` 構造体とメソッドの変更 (`src/go/types/scope.go`)

*   **`Scope` 構造体の拡張**: `Scope` 構造体に `pos` と `end` フィールドが追加されました。これらは `token.Pos` 型で、スコープがソースコード上で占める範囲 `[pos, end)` を表します。これにより、スコープの物理的な位置を追跡できるようになります。
*   **`NewScope` 関数の変更**: `NewScope(parent *Scope, comment string)` が `NewScope(parent *Scope, pos, end token.Pos, comment string)` に変更されました。スコープの作成時にその範囲情報を指定できるようになりました。
*   **`Pos()`, `End()`, `Contains()`, `Innermost()` メソッドの追加**:
    *   `Pos()` と `End()` は、スコープの開始位置と終了位置を返します。
    *   `Contains(pos token.Pos)` は、指定された位置がこのスコープの範囲内にあるかどうかを判定します。
    *   `Innermost(pos token.Pos)` は、指定された位置を含む最も内側の（子）スコープを再帰的に検索して返します。これらのメソッドは、`Eval` 関数での正確なスコープ決定に不可欠です。
*   **`LookupParent` メソッドの変更**: `LookupParent(name string)` が `LookupParent(name string, pos token.Pos)` に変更されました。このメソッドは、指定された `pos` が有効な場合、検索対象の `Object` が `pos` よりも前に宣言されているかどうかを `obj.scopePos() <= pos` で確認します。これにより、Go の言語仕様に沿った正確な識別子解決が可能になります。

### `Object` インターフェースと `object` 構造体の変更 (`src/go/types/object.go`)

*   **`Object` インターフェースの拡張**: `Object` インターフェースに `scopePos() token.Pos` と `setScopePos(pos token.Pos)` メソッドが追加されました。これにより、すべての `Object` は、それが宣言されたスコープの開始位置を保持できるようになります。
*   **`object` 構造体の拡張**: 内部的な `object` 構造体に `scopePos_ token.Pos` フィールドが追加され、`Object` インターフェースの新しいメソッドが実装されました。これにより、`PkgName`, `Const`, `TypeName`, `Var`, `Func` などの具体的な `Object` 型が、その宣言位置のスコープ情報を保持できるようになります。

これらの変更は、`go/types` パッケージが Go 言語のセマンティクス、特にスコープと識別子の可視性をより正確にモデル化し、処理できるようにするための基盤を強化するものです。これにより、型チェックの精度が向上し、より複雑なコード構造やエッジケースに対しても堅牢な動作が期待できます。

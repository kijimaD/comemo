# [インデックス 27943] ファイルの概要

このコミットは、Go言語のリンカである `cmd/link` におけるセクションアラインメントの計算方法を改善し、並行処理を導入することでリンク時間の短縮を図るものです。具体的には、`src/cmd/link/internal/ld/data.go` ファイルが変更され、セクションごとの最大アラインメントの計算が並行して行われるようになりました。これにより、`cmd/go` のリンク時間が約1%削減される効果が報告されています。

## 変更の背景

Go言語のビルドプロセスにおいて、リンカ (`cmd/link`) はコンパイルされたオブジェクトファイルを結合し、実行可能ファイルを生成する重要な役割を担っています。このプロセスは、特に大規模なプロジェクトや多数の依存関係を持つプロジェクトにおいて、ビルド時間の大部分を占めることがあります。

本コミットの背景には、リンカのパフォーマンス最適化への継続的な取り組みがあります。セクションアラインメントの計算は、リンカが実行可能ファイルのメモリレイアウトを決定する際に必要な処理の一つであり、これまで逐次的に行われていました。この逐次処理がボトルネックとなり、リンク時間の増加に繋がっていたと考えられます。

`cmd/go` のリンク時間が1%削減されるという具体的な効果は、Go言語のツールチェイン全体の効率向上に寄与し、開発者のビルド体験を改善することを目的としています。

## 前提知識の解説

### リンカ (`cmd/link`)

Go言語のリンカ `cmd/link` は、Goコンパイラによって生成されたオブジェクトファイル（`.o` ファイル）やアーカイブファイル（`.a` ファイル）を結合し、最終的な実行可能ファイル（または共有ライブラリ）を生成するツールです。このプロセスには、シンボルの解決、再配置、そしてメモリセクションの配置などが含まれます。

### メモリセクションとアラインメント

実行可能ファイルは、コード、データ、BSS（初期化されていないデータ）などの異なる種類の情報を格納するために、複数の「セクション」に分割されます。これらのセクションは、プログラムがメモリにロードされる際に特定のメモリアドレスに配置されます。

「アラインメント（alignment）」とは、データやセクションがメモリ上で特定のバイト境界に配置されることを保証する要件です。例えば、4バイトアラインメントが必要な場合、そのデータは4の倍数のアドレスに配置されなければなりません。これは、プロセッサが特定のバイト境界に配置されたデータに効率的にアクセスできるため、パフォーマンス向上やハードウェア要件を満たすために重要です。

リンカは、各セクションに含まれるシンボル（変数や関数など）のアラインメント要件を考慮し、セクション全体がその中で最も厳しいアラインメント要件を満たすように配置します。この「最大アラインメント」の計算は、セクションの開始アドレスを決定するために不可欠です。

### 並行処理 (Concurrency)

並行処理とは、複数のタスクが同時に進行しているように見える（または実際に同時に進行する）プログラミングの概念です。Go言語はゴルーチン（goroutine）とチャネル（channel）を用いて、軽量かつ効率的な並行処理をサポートしています。本コミットでは、このGoの並行処理メカニズムを活用して、複数のセクションのアラインメント計算を同時に実行することで、処理時間の短縮を図っています。

## 技術的詳細

このコミットの主要な技術的変更点は、リンカの `dodata` 関数内で実行されるセクションアラインメント計算の並行化です。

以前の実装では、`dodata` 関数が各セクション（`.data`, `.bss`, `.noptrdata` など）を処理する際に、そのセクションに含まれるすべてのシンボルを走査し、最も大きなアラインメント値 (`maxalign` 関数) を見つけていました。この `maxalign` の呼び出しは、各セクションに対して逐次的に行われていました。

新しい実装では、以下の変更が導入されました。

1.  **`maxalign` 関数の削除**: 以前はセクションの最大アラインメントを計算するために使用されていた `maxalign` 関数が削除されました。
2.  **`dodataSect` 関数の変更**:
    *   `dodataSect` 関数は、特定のセクション (`symn`) に属するシンボルのリスト (`syms`) を処理し、ソートされたシンボルリストを返すだけでなく、そのセクションの最大アラインメント値 (`maxAlign`) も返すように変更されました。
    *   この関数内で、各シンボルのアラインメント (`symalign(symSort.lsym)`) を確認し、セクション全体の `maxAlign` を更新するロジックが追加されました。
    *   また、以前 `growdatsize` 関数で行われていたシンボルサイズのチェック（負のサイズ、大きすぎるサイズなど）も `dodataSect` 内に移動されました。
3.  **並行処理の導入**:
    *   `dodata` 関数内で、`data` マップ（セクションタイプごとのシンボルリストを保持）の各エントリに対して、`dodataSect` 関数をゴルーチンとして並行実行するようになりました。
    *   `sync.WaitGroup` を使用して、すべてのゴルーチンが完了するのを待機します。
    *   `dataMaxAlign` という新しい配列が導入され、各セクションタイプ (`obj.SXREF` はセクションタイプの列挙型) の最大アラインメントを並行処理の結果として格納します。
4.  **`growdatsize` 関数の削除と `checkdatsize` の導入**:
    *   `growdatsize` 関数は削除され、その役割は `datsize += s.Size` による単純なサイズ加算と、新しい `checkdatsize` 関数によるサイズ上限チェックに分割されました。
    *   `checkdatsize` 関数は、セクションのデータサイズが `cutoff` (2GB) を超えていないかをチェックします。これにより、以前 `growdatsize` が行っていたサイズチェックがより明確に分離されました。
5.  **セクションアラインメントの設定**:
    *   `dodata` 関数内でセクションの `Align` フィールドを設定する際に、以前は `maxalign(data[symn])` を呼び出していた箇所が、並行処理で計算された `dataMaxAlign[symn]` を参照するように変更されました。

これらの変更により、複数のセクションの最大アラインメント計算が同時に行われるため、リンカの全体的な実行時間が短縮されます。

## コアとなるコードの変更箇所

変更は `src/cmd/link/internal/ld/data.go` ファイルに集中しています。

### 削除された関数

*   `maxalign` 関数: セクションの最大アラインメントを計算する役割を担っていた。
*   `growdatsize` 関数: データサイズを増加させ、同時にサイズ上限チェックを行っていた。

### 変更された関数

*   `dodataSect` 関数:
    *   シグネチャが `func dodataSect(symn int, syms []*LSym) []*LSym` から `func dodataSect(symn int, syms []*LSym) (result []*LSym, maxAlign int32)` に変更され、ソートされたシンボルリストと最大アラインメントを返すようになった。
    *   シンボルリストを走査しながら `maxAlign` を計算するロジックが追加された。
    *   シンボルサイズのチェックロジックが `growdatsize` から移動された。
*   `dodata` 関数:
    *   `dataMaxAlign` という `[obj.SXREF]int32` 型の配列が導入された。
    *   `dodataSect` の呼び出しが `go func() { ... }()` の形式でゴルーチンとして実行され、`dataMaxAlign` に結果が格納されるようになった。
    *   各セクションの `sect.Align` の設定が、`maxalign(...)` の呼び出しから `dataMaxAlign[...]` の参照に変更された。
    *   `growdatsize` の代わりに `datsize += s.Size` と `checkdatsize(...)` が使用されるようになった。

### 新しく追加された関数

*   `checkdatsize` 関数: セクションのデータサイズが `cutoff` (2GB) を超えていないかをチェックする。

## コアとなるコードの解説

### `dodata` 関数内の並行処理部分

```go
	var dataMaxAlign [obj.SXREF]int32
	var wg sync.WaitGroup
	for symn := range data {
		symn := symn
		wg.Add(1)
		go func() {
			data[symn], dataMaxAlign[symn] = dodataSect(symn, data[symn])
			wg.Done()
		}()
	}
	wg.Wait()
```
このコードブロックは、セクションアラインメント計算の並行化の核心です。
`data` は、異なるセクションタイプ（`symn`）ごとにシンボルリストを保持するマップです。
ループ内で、各 `symn` に対して新しいゴルーチンが起動されます。
各ゴルーチンは `dodataSect` を呼び出し、そのセクションのシンボルリストを処理し、ソートされたリストと計算された最大アラインメントを返します。
返された最大アラインメントは `dataMaxAlign` 配列の対応するインデックスに格納されます。
`wg.Add(1)` と `wg.Done()` は `sync.WaitGroup` を使用した一般的な並行処理パターンで、すべてのゴルーチンが完了するまで `wg.Wait()` で待機します。これにより、後続のセクション配置処理が、すべてのアラインメント情報が揃った状態で行われることが保証されます。

### `dodataSect` 関数の変更

```go
func dodataSect(symn int, syms []*LSym) (result []*LSym, maxAlign int32) {
	// ... (既存の処理) ...

	for i, symSort := range symsSort {
		syms[i] = symSort.lsym
		align := symalign(symSort.lsym)
		if maxAlign < align {
			maxAlign = align
		}
	}

	// ... (既存の処理) ...

	return syms, maxAlign
}
```
`dodataSect` 関数は、シンボルをソートするだけでなく、その過程で各シンボルのアラインメント (`symalign`) を取得し、セクション全体の `maxAlign` を追跡・更新するようになりました。これにより、セクションの最大アラインメントの計算が、シンボルソートという既存の処理フローに統合され、効率的に行われます。

### `checkdatsize` 関数の導入

```go
const cutoff int64 = 2e9 // 2 GB (or so; looks better in errors than 2^31)

func checkdatsize(datsize int64, symn int) {
	if datsize > cutoff {
		Diag("too much data in section %v (over %d bytes)", symn, cutoff)
	}
}
```
この関数は、セクションの累積データサイズが `cutoff` (2GB) を超えた場合に診断メッセージを出力します。以前は `growdatsize` 内で行われていたこのチェックが独立した関数として切り出され、`dodata` 内の各セクション処理の最後に呼び出されるようになりました。これにより、サイズチェックのロジックが明確になり、コードの可読性が向上しています。

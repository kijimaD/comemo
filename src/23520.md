# [インデックス 23520] ファイルの概要

このコミットは、Go言語のパーサー（`go/parser`パッケージ）における不完全なセレクタ式（例: `fmt.`）の解析方法を改善するものです。以前はこのような不完全な式は`ast.BadExpr`として扱われていましたが、この変更により`fmt._`のようなブランクセレクタ式（`ast.SelectorExpr`）として解析されるようになります。これにより、部分的な構文が破棄されることを防ぎ、エラー回復ロジックが他の識別子が期待されるが発見されないケースと一貫性を持つようになります。

## 変更の背景

Go言語のパーサーは、ソースコードを解析して抽象構文木（AST）を構築する役割を担っています。このプロセスにおいて、構文エラーが発生した場合でも、可能な限り多くの情報を保持し、後続の解析やツール（IDEのコード補完、静的解析ツールなど）が機能するように、適切なエラー回復を行うことが重要です。

このコミット以前は、`fmt.`のようにセレクタの右辺（フィールド名やメソッド名）が欠落している不完全なセレクタ式に遭遇すると、パーサーは`ast.BadExpr`という特殊なASTノードを生成していました。`ast.BadExpr`は、パーサーが有効な構文を認識できなかった領域を示すために使用されます。しかし、`ast.BadExpr`は具体的な構文構造に関する情報をほとんど持たないため、この部分のコードに対しては、IDEの補完機能などがうまく働かない可能性がありました。

この変更の背景には、以下の目的があります。

1.  **部分的な構文の保持**: `fmt.`のような不完全な式でも、`fmt`という左辺が存在するという情報は保持すべきです。`BadExpr`ではこの情報が失われがちでした。
2.  **エラー回復の一貫性**: Goパーサーの他の部分では、識別子が期待されるが欠落している場合に、ブランク識別子`_`を使用してASTを構築するパターンが存在しました。不完全なセレクタ式も同様に扱うことで、パーサー全体のエラー回復ロジックの一貫性を高めます。
3.  **ツールサポートの改善**: `fmt._`として解析することで、`fmt`というパッケージ名（または変数名）が認識され、その後にセレクタが続くという構造がASTに明示されます。これにより、IDEなどのツールが、たとえ不完全なコードであっても、`fmt`パッケージのメンバーを提案するなどのより賢い補完機能を提供できるようになる可能性があります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ技術に関する基本的な知識が必要です。

### 1. Go言語のパーサー (`go/parser`パッケージ)
`go/parser`パッケージは、Go言語のソースコードを解析し、その構造を抽象構文木（AST）として表現するための標準ライブラリです。Goのコンパイラや各種開発ツール（`go vet`, `gofmt`, IDEなど）の基盤となっています。

### 2. 抽象構文木 (AST: Abstract Syntax Tree)
ASTは、プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。各ノードはソースコードの構成要素（式、文、宣言など）を表し、その子ノードはさらに詳細な構成要素を表します。Go言語では、`go/ast`パッケージでASTのノード型が定義されています。

### 3. `ast.BadExpr`
`ast.BadExpr`は、`go/ast`パッケージで定義されているASTノードの一つです。パーサーが構文エラーに遭遇し、有効なGoの構文として解析できなかった部分を表すために使用されます。`From`と`To`フィールドで、エラーが発生したソースコードの範囲を示します。これは、エラー回復の際に、これ以上解析を進められない場合に「ここからここまでが不正な構文である」とマークするために使われます。

### 4. `ast.SelectorExpr`
`ast.SelectorExpr`も`go/ast`パッケージで定義されているASTノードです。`X.Sel`の形式のセレクタ式（例: `os.Stdout`, `myVar.Method()`, `pkg.Const`) を表します。
- `X`: セレクタの左辺（例: `os`, `myVar`, `pkg`）。これは別の式（`ast.Expr`）です。
- `Sel`: セレクタの右辺（例: `Stdout`, `Method`, `Const`）。これは識別子（`ast.Ident`）です。

### 5. `ast.Ident` とブランク識別子 `_`
`ast.Ident`は、識別子（変数名、関数名、型名など）を表すASTノードです。Go言語には、値を破棄するために使用される特別な識別子であるブランク識別子`_`（アンダースコア）があります。例えば、`_ = someFunc()`のように、戻り値を無視する場合に利用されます。パーサーの文脈では、構文上識別子が必要だが、ユーザーがまだ入力していない、あるいは意図的に省略している場合に、この`_`をプレースホルダーとして利用することがあります。

### 6. Go言語のエラー回復戦略
Go言語のパーサーは、構文エラーが発生してもすぐに解析を停止せず、可能な限り解析を続行して、より多くのエラーを報告し、部分的なASTを構築しようとします。これをエラー回復（Error Recovery）と呼びます。エラー回復の目的は、ユーザーがコードを修正する際に、一度に複数のエラーメッセージを提供し、IDEなどのツールが不完全なコードでも有用な情報を提供できるようにすることです。

## 技術的詳細

このコミットの核心的な変更は、`src/go/parser/parser.go`内のセレクタ式を解析するロジックにあります。

以前のパーサーでは、`X.`のようにセレクタの左辺（`X`）は存在するものの、右辺（`Sel`）が欠落している場合、パーサーは`p.errorExpected(pos, "selector or type assertion")`を呼び出してエラーを報告し、その後`x = &ast.BadExpr{From: pos, To: p.pos}`として`ast.BadExpr`を生成していました。

この変更により、`ast.BadExpr`を生成する代わりに、以下の処理が行われるようになりました。

1.  `p.errorExpected(pos, "selector or type assertion")`を呼び出してエラーを報告する点は変わりません。これは、構文エラーが発生したことをユーザーに伝えるために必要です。
2.  しかし、`ast.BadExpr`を直接生成するのではなく、`sel := &ast.Ident{NamePos: pos, Name: "_"`というコードで、ブランク識別子`_`を表す`ast.Ident`ノードを生成します。`NamePos`は、この識別子の位置を示します。
3.  次に、`x = &ast.SelectorExpr{X: x, Sel: sel}`というコードで、既存の左辺`x`と、新しく生成したブランク識別子`sel`を組み合わせて、`ast.SelectorExpr`を構築します。

結果として、`fmt.`という入力は、AST上では`&ast.SelectorExpr{X: <fmtを表すast.Ident>, Sel: <_を表すast.Ident>}`として表現されるようになります。これは、`fmt._`という有効なGoの構文と全く同じAST構造です。

この変更の利点は、`ast.BadExpr`が持つ「この部分は不明な構文である」という情報よりも、「`fmt`という式の後にセレクタが続くが、そのセレクタ名が欠落している」という、より具体的な構文情報をASTに保持できる点です。これにより、パーサーの後の段階や、ASTを利用するツールが、より意味のある処理を行えるようになります。例えば、IDEは`fmt`の後に`_`があることを認識し、`fmt`パッケージのメンバーを補完候補として提示できるようになるかもしれません。

また、`src/go/parser/interface.go`の`ParseFile`関数内の`recover`ブロックにも小さな変更が加えられています。これは、パーサー内部で発生するパニックが`bailout`型のものであることを確認し、そうでない場合は元のパニックを再発生させるためのものです。これは、パーサーのエラー回復メカニズムの一部であり、今回のセレクタ解析の変更と直接的な関連はありませんが、パーサーの堅牢性を高めるための一般的な改善と見られます。

## コアとなるコードの解説

`src/go/parser/parser.go`の変更は、Goパーサーがセレクタ式を処理する際の挙動を根本的に変えるものです。

変更前のコード:
```go
				pos := p.pos
				p.errorExpected(pos, "selector or type assertion")
				p.next() // make progress
				x = &ast.BadExpr{From: pos, To: p.pos}
```
このコードでは、`X.`の後に識別子が見つからない場合、エラーを報告し、その部分を`ast.BadExpr`としてマークしていました。`ast.BadExpr`は、その範囲が構文的に不正であることを示すだけで、具体的な構造情報はほとんど持ちません。

変更後のコード:
```go
				pos := p.pos
				p.errorExpected(pos, "selector or type assertion")
				p.next() // make progress
				sel := &ast.Ident{NamePos: pos, Name: "_"}
				x = &ast.SelectorExpr{X: x, Sel: sel}
```
この新しいロジックでは、同じ状況でエラーを報告しつつも、`ast.BadExpr`を生成する代わりに、以下のステップでより構造的なASTノードを構築します。

1.  `sel := &ast.Ident{NamePos: pos, Name: "_"}`: ブランク識別子`_`を表す`ast.Ident`ノードを作成します。`NamePos`は、この`_`がソースコード上のどの位置に対応するかを示します。この場合、欠落した識別子が期待されていた位置です。
2.  `x = &ast.SelectorExpr{X: x, Sel: sel}`: 既存の左辺式`x`（例: `fmt`を表す`ast.Ident`）と、新しく作成したブランク識別子`sel`を組み合わせて、完全な`ast.SelectorExpr`を構築します。

この変更により、`fmt.`という不完全な入力は、`fmt._`という有効な構文と同じAST構造を持つことになります。これは、パーサーがエラー回復の際に、単に「不正な部分」とマークするのではなく、「セレクタの右辺が欠落しているが、左辺は`fmt`である」という具体的な情報をASTに埋め込むことを意味します。

このアプローチは、Goパーサーが他の場所で識別子が期待されるが欠落している場合に採用している戦略と一貫しています。例えば、変数宣言で初期値が欠落している場合などです。これにより、パーサー全体のエラー回復ロジックがより予測可能で、ツールフレンドリーになります。

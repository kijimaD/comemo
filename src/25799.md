## 変更の背景

このコミットは、Goランタイムのガベージコレクタ (GC) の `gcMarkDone` 関数におけるいくつかの改善とクリーンアップを目的としています。主な変更点は以下の3つです。

1.  **`gcMarkDone` 関数のドキュメントコメントの改善**: 関数の動作と期待されるコンテキストに関する説明がより明確にされました。特に、呼び出し元がプリエンプト可能であるべきこと、および関数内のライトバリアの許容性について追記されています。
2.  **再帰呼び出しの `goto` ステートメントへの置換**: `gcMarkDone` 内で特定の条件が満たされた場合に自身を再帰的に呼び出すロジックが、`goto` を使用したループ構造に置き換えられました。これは、スタック消費の抑制や、コードの意図をより明確にするための変更と考えられます。
3.  **`stopTheWorldWithSema` 呼び出し前のプリエンプション無効化**: GCが「Stop The World (STW)」フェーズに移行する際に `stopTheWorldWithSema` 関数を呼び出す直前に、現在のゴルーチンのプリエンプションを明示的に無効にする処理が追加されました。これは、`stopTheWorldWithSema` のドキュメントコメントに記載されている要件に合致させるための変更であり、STW処理が中断されることなく確実に実行されるようにするためのものです。

コミットメッセージには「Updates #13363, but, sadly, doesn't fix it.」とあり、この変更が既存のGC関連の問題（Issue #13363）に対する部分的な改善であり、根本的な解決には至っていないことを示唆しています。これは、GoのGCが継続的に改善されている過程の一部であり、このコミットはGCの堅牢性と正確性を高めるためのステップと位置付けられます。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション (GC) の仕組み、特にコンカレントマークフェーズとプリエンプション、そしてStop The World (STW) の概念について理解しておく必要があります。

*   **Goのガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降、GCは主に「コンカレント (concurrent)」に動作します。これは、GCの大部分がアプリケーションのゴルーチンと並行して実行されることを意味し、アプリケーションの一時停止時間（ポーズタイム）を最小限に抑えることを目的としています。GCは主に以下のフェーズで構成されます。
    *   **マークフェーズ (Mark Phase)**: ヒープ上のオブジェクトを走査し、到達可能な（まだ使用されている）オブジェクトをマークします。GoのGCでは、このフェーズの大部分がアプリケーションと並行して実行される「コンカレントマーク」です。
    *   **マークターミネーションフェーズ (Mark Termination Phase)**: コンカレントマークフェーズの最終処理を行い、次のフェーズへの移行を準備します。このフェーズは通常、短いSTWポーズを伴います。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。

*   **`gcMarkDone` 関数**: この関数は、Goのコンカレントマークフェーズにおいて、特定のP (Processor) が自身のマーク作業を完了した際に呼び出されます。その主な役割は、全てのマーク作業が完了したかどうかを確認し、必要に応じてグローバルなワークキューにローカルな作業をフラッシュしたり、GCフェーズをマークターミネーションに移行させたりすることです。

*   **プリエンプション (Preemption)**: Goランタイムのスケジューラは、実行中のゴルーチンを一時停止させ、別のゴルーチンにCPUを割り当てるメカニズムを持っています。これをプリエンプションと呼びます。これにより、長時間実行されるゴルーチンがCPUを独占するのを防ぎ、全てのゴルーチンに公平に実行機会を与え、システムの応答性を保ちます。GC作業を行うゴルーチンもプリエンプトされる可能性があります。

*   **Stop The World (STW)**: GCの特定のフェーズ（例えば、マークターミネーションの開始時やスイープの終了時）では、ヒープの状態が完全に一貫している必要があります。この一貫性を保証するため、Goランタイムは一時的に全てのアプリケーションゴルーチンを停止させます。この一時停止期間を「Stop The World (STW)」ポーズと呼びます。STWポーズはアプリケーションのレイテンシに直接影響するため、GoのGCはSTW時間を最小限に抑えるように設計されています。

*   **`stopTheWorldWithSema` 関数**: この関数は、Goランタイム内でSTWポーズを開始するために使用される内部関数です。セマフォ (`worldsema`) を利用して、複数のM (OSスレッド) が同時にSTWを開始しようとするのを防ぎ、STW処理が安全かつ一貫して行われるようにします。この関数を呼び出すゴルーチンは、STW処理中にプリエンプトされないことが期待されます。

*   **`semacquire`**: セマフォを取得するための関数です。セマフォは、共有リソースへのアクセスを制御するための同期プリミティブであり、ここでは `work.markDoneSema` というセマフォを使って `gcMarkDone` の処理を同期しています。

*   **`atomic.Xadd`**: アトミックな加算操作を行う関数です。複数のゴルーチンが同時に共有変数にアクセスして値を変更する際に、競合状態を防ぎ、正確な結果を保証するために使用されます。ここでは `work.nwait` (待機中のワーカー数) をアトミックに更新しています。

*   **`systemstack`**: 現在のゴルーチンをシステムスタックに切り替えて関数を実行するためのGoランタイムの内部関数です。これは、通常のゴルーチンのスタックとは異なる、より固定されたサイズのスタックで実行する必要がある低レベルのランタイム操作（例えば、STWの開始など）で使用されます。

*   **`getg().m.preemptoff = "gcing"`**: `getg()` は現在のゴルーチン (`g`) を取得し、`m` はそのゴルーチンが実行されているOSスレッド (`m`) を指します。`preemptoff` フィールドは、そのスレッド上で実行されているゴルーチンがプリエンプトされるべきではない理由を示す文字列です。これを設定することで、スケジューラに対して現在のゴルーチンをプリエンプトしないように指示します。`"gcing"` は、GC作業中であることを示します。

*   **ライトバリア (Write Barrier)**: コンカレントGCにおいて、アプリケーションがヒープ上のポインタを更新する際に実行される小さなコードスニペットです。これにより、GCがオブジェクトグラフを走査している最中にアプリケーションがポインタを変更しても、GCがオブジェクトを見落とすことなく、ヒープの整合性を保つことができます。

## 技術的詳細

このコミットにおける技術的な変更は、GoランタイムのGCの堅牢性と効率性を向上させるためのものです。

1.  **`gcMarkDone` のドキュメントコメント改善**:
    変更前:
    ```go
    // active work buffers in assists and background workers; however,
    // work may still be cached in per-P work buffers. In mark 2, per-P
    // caches are disabled.
    ```
    変更後:
    ```go
    // active work buffers in assists and background workers; however,
    // work may still be cached in per-P work buffers. In mark 2, per-P
    // caches are disabled.
    //
    // The calling context must be preemptible.
    //
    // Note that it is explicitly okay to have write barriers in this
    // function because completion of concurrent mark is best-effort
    // anyway. Any work created by write barriers here will be cleaned up
    // by mark termination.
    ```
    追加されたコメントは、`gcMarkDone` を呼び出すコンテキストがプリエンプト可能であるべきことを明記しています。これは、GCワーカーが長時間CPUを占有するのを防ぎ、他のアプリケーションゴルーチンが実行される機会を確保するために重要です。また、この関数内でライトバリアが実行されても問題ない理由を説明しています。コンカレントマークの完了はベストエフォートであり、ライトバリアによって生成された追加の作業はマークターミネーションフェーズで処理されるため、整合性が損なわれることはありません。

2.  **再帰呼び出しから `goto` への変更**:
    変更前:
    ```go
    	incnwait := atomic.Xadd(&work.nwait, +1)
    	if incnwait == work.nproc && !gcMarkWorkAvailable(nil) {
    		// This recursion is safe because the call
    		// can't take this same "if" branch.
    		gcMarkDone()
    	}
    ```
    変更後:
    ```go
    	incnwait := atomic.Xadd(&work.nwait, +1)
    	if incnwait == work.nproc && !gcMarkWorkAvailable(nil) {
    		// This loop will make progress because
    		// gcBlackenPromptly is now true, so it won't
    		// take this same "if" branch.
    		goto top
    	}
    ```
    `gcMarkDone` 関数内で、特定の条件 (`incnwait == work.nproc && !gcMarkWorkAvailable(nil)`) が満たされた場合に、自身を再帰的に呼び出す代わりに `goto top` を使用するように変更されました。`top:` ラベルは関数の冒頭に配置されています。
    この変更の主な理由は、再帰呼び出しがスタックを消費する可能性があるためです。特に、この条件が複数回連続して満たされるようなエッジケースでは、スタックオーバーフローのリスクが生じる可能性があります。`goto` を使用することで、スタックフレームを新たに作成することなく、関数の冒頭から処理を再開できるため、スタック消費を抑制し、より効率的なループ処理を実現します。
    新しいコメント「This loop will make progress because gcBlackenPromptly is now true, so it won't take this same "if" branch.」は、この `goto` ループが無限ループに陥らないことを保証しています。`gcBlackenPromptly` が `true` になることで、`gcMarkWorkAvailable(nil)` が最終的に `true` を返し、この `if` ブロックが実行されなくなるため、ループは必ず終了します。

3.  **`stopTheWorldWithSema` 前のプリエンプション無効化**:
    変更前:
    ```go
    	// Transition to mark termination.
    	now := nanotime()
    	work.tMarkTerm = now
    	work.pauseStart = now
    	systemstack(stopTheWorldWithSema)
    ```
    変更後:
    ```go
    	// Transition to mark termination.
    	now := nanotime()
    	work.tMarkTerm = now
    	work.pauseStart = now
    	getg().m.preemptoff = "gcing"
    	systemstack(stopTheWorldWithSema)
    ```
    マークターミネーションフェーズへの移行時に `stopTheWorldWithSema` を呼び出す直前に、`getg().m.preemptoff = "gcing"` という行が追加されました。これは、現在のゴルーチンがGC作業中であり、この重要なSTW処理中にプリエンプトされるべきではないことをGoスケジューラに明示的に伝えるためのものです。
    `stopTheWorldWithSema` は、全てのアプリケーションゴルーチンを停止させるという非常にデリケートな操作を実行します。この操作自体がプリエンプトされると、STW処理が中断され、GCの状態が不安定になったり、デッドロックが発生したりする可能性があります。`preemptoff` フラグを設定することで、STW処理が中断されることなく、一貫した状態で完了することが保証されます。これは `stopTheWorldWithSema` の内部ドキュメントコメントに記載されている要件に合致する変更であり、GCの堅牢性を高めます。

## コアとなるコードの解説

1.  **`gcMarkDone` 関数のドキュメントコメントの追加 (行 1030-1035)**:

# [インデックス 25216] ファイルの概要

このコミットは、Go言語の標準ライブラリ `mime/multipart` パッケージにおける、マルチパートメッセージの境界検出に関するエッジケースのバグを修正します。具体的には、`peekBufferSeparatorIndex` 関数が、部分的に読み込まれた境界文字列の末尾の改行文字 (`\n`) がバッファに存在しない場合に、誤って境界を見つけられないと判断し、結果として `io.ErrUnexpectedEOF` エラーを引き起こす問題を解決します。この修正により、マルチパートデータの堅牢なパースが保証されます。

## 変更の背景

このコミットは、Go言語の `mime/multipart` パッケージにおける、マルチパートメッセージのパース処理に関する特定のエッジケースのバグを修正するために行われました。このバグは、`partReader` の `Read` メソッド内で `Peek` 操作が行われる際に発生しました。

具体的には、`Peek` がバッファに `somedata\r\n--Boundary\r` のようなデータパターンを読み込んだ場合、`peekBufferSeparatorIndex` 関数が境界の末尾に必要な `\n` を見つけられず、誤って `(-1, false)` を返していました。これは以下の点で問題でした。

1.  **ドキュメントとの不一致**: `\r\n--Boundary` が見つかっているにもかかわらず、ドキュメントの意図に反して `-1` を返していました。
2.  **不正確なデータカット**: この誤った戻り値により、後続の `nCopy` 操作が `somedata\r| |\n--Boundary\r` のように不正確な位置でデータをカットしてしまい、本来の境界 (`\r\n--Boundary\r\n`) を見逃す原因となりました。

結果として、`multipart.Reader` は境界を正しく検出できず、最終的に `io.ErrUnexpectedEOF` エラーを返してしまい、マルチパートメッセージのパースが失敗していました。この問題は、Camlistore プロジェクトの issue #642 (現在はアクセス不可) で報告されていました。

## 前提知識の解説

### MIME Multipart

MIME (Multipurpose Internet Mail Extensions) Multipart は、単一のメッセージボディ内に複数の異なるデータタイプ（テキスト、画像、ファイルなど）を結合するための標準的な方法です。HTTP のフォームデータ送信（`Content-Type: multipart/form-data`）や電子メールの添付ファイルなどで広く利用されています。各データ部分は「パート」と呼ばれ、特定の「境界文字列 (boundary string)」によって区切られます。

### Go `mime/multipart` パッケージ

Go の `mime/multipart` パッケージは、MIME multipart メッセージの読み書きをサポートする標準ライブラリです。`multipart.Reader` は受信したマルチパートメッセージをパースし、各パートを個別に読み取る機能を提供します。

### 境界検出 (Boundary Detection)

マルチパートメッセージを正しくパースするためには、境界文字列を正確に検出することが不可欠です。境界文字列は通常、`--[boundary_string]` の形式で、各パートの開始を示します。メッセージの末尾には `---[boundary_string]--` が置かれます。これらの境界は、通常 `\r\n` (CRLF) で囲まれています。

### `peekBufferSeparatorIndex` 関数

`peekBufferSeparatorIndex` は `mime/multipart` パッケージ内部で使用される非公開 (unexported) 関数です。その主な役割は、バッファリングされた入力ストリーム内でマルチパートの境界セパレータを効率的に見つけることです。`multipart.Reader` が次のパートを読み進める際に、この関数を使ってバッファ内のどこに境界文字列があるかを特定し、現在のパートの終端と次のパートの開始を正確に判断します。この関数が誤ったインデックスを返すと、パース処理全体が破綻する可能性があります。

### `io.ErrUnexpectedEOF`

`io.ErrUnexpectedEOF` は、`io.Reader` インターフェースを実装する型が、期待されるデータの終端に達する前にストリームの終端に遭遇した場合に返されるエラーです。このコンテキストでは、`multipart.Reader` が境界文字列を期待しているにもかかわらず、データストリームが予期せず終了したと判断した場合に発生しました。これは、境界が正しく検出されなかったために、リーダーがデータの読み取りを継続しようとした結果として生じます。

## 技術的詳細

このバグは、`peekBufferSeparatorIndex` 関数が境界文字列の検出ロジックにおいて、バッファの境界条件を適切に処理できていなかったことに起因します。

`peekBufferSeparatorIndex` は、`bytes.IndexByte(peek, '\n')` を使用して、`peek` バッファ内に改行文字 (`\n`) が存在するかどうかを確認していました。マルチパートの境界は `\r\n--Boundary\r\n` の形式で現れるため、境界の検出には `\r\n` の両方が重要です。

問題のエッジケースは、`Peek` 操作によってバッファに `somedata\r\n--Boundary\r` のようなデータが読み込まれた場合に発生しました。このとき、境界文字列の開始 (`\r\n--Boundary`) はバッファ内に存在しますが、その直後の `\n` (つまり、`\r\n--Boundary\r\n` の最後の `\n`) がバッファの末尾を超えてまだ読み込まれていない状態でした。

元のコードでは、`if bytes.IndexByte(peek, '\n') == -1` という条件で、バッファ内に `\n` が全く見つからない場合に `return -1, false` を返していました。このロジックは、バッファに `\r\n--Boundary\r` が含まれている場合でも、最後の `\n` がないために `bytes.IndexByte` が `-1` を返し、結果として `peekBufferSeparatorIndex` が境界を見つけられなかったと誤って判断していました。

この誤った判断により、`multipart.Reader` は境界がまだ見つかっていないと認識し、不正確な `nCopy` (データのコピー量) を計算しました。これにより、本来境界として認識されるべきバイト列がデータの一部として扱われ、結果的に境界がスキップされてしまい、最終的に `io.ErrUnexpectedEOF` が発生していました。

## コアとなるコードの解説

### `src/mime/multipart/multipart.go` の変更点

変更は `peekBufferSeparatorIndex` 関数内のわずか1行です。

```go
-		return -1, false
+		return idx, false
```

この変更の意図は、`peek` バッファ内に `\n` が見つからない場合でも、`idx` 変数に既に有効な境界の開始位置が格納されている可能性があるため、その `idx` を返すようにすることです。

元のコードでは、`bytes.IndexByte(peek, '\n') == -1` の条件が真の場合、つまり `peek` バッファ内に完全な行の終端 (`\n`) が見つからない場合に、無条件に `-1` を返していました。しかし、`peekBufferSeparatorIndex` のロジックは、`peek` バッファの先頭から境界文字列 (`\r\n--Boundary`) の開始位置を `idx` に格納している可能性があります。このエッジケースでは、境界の開始は検出されているものの、その後の `\n` がバッファの末尾を超えているため、`bytes.IndexByte` が `-1` を返していました。

修正後のコードでは、`\n` が見つからない場合でも、既に計算されている `idx` を返します。これにより、`multipart.Reader` は境界が部分的に検出されたことを認識し、さらにデータを読み込んで完全な境界を検出するための適切な処理を継続できるようになります。これは、境界がバッファの途中で途切れている場合でも、その部分的な情報を利用してパース処理を進めるための重要な変更です。

### `src/mime/multipart/multipart_test.go` の変更点

テストコードの追加は、この修正の正当性を保証するために非常に重要です。

*   **`safeCount off by one` テストケース**:
    このテストケースは、`peekBufferSize` と境界文字列の長さ、`\r` の位置などを考慮して、以前のバグが再現されるような特定のサイズのマルチパートボディを意図的に構築します。これにより、`peekBufferSeparatorIndex` が `\r\n--Boundary\r` のような状況で正しく動作するかどうかを検証します。このテストは、バッファの境界で境界文字列が途切れるような「オフバイワン」エラーを捕捉することを目的としています。

*   **`TestParseAllSizes` 関数**:
    このテストはさらに包括的で、0バイトから `maxSize` (5KB) までのあらゆるサイズのファイルボディを持つマルチパートメッセージを動的に生成し、それらをパースします。この網羅的なテストにより、`peekBufferSize` のサイズに関わらず、またデータがバッファのどの位置で途切れても、`mime/multipart` パッケージが常に境界を正しく検出し、`io.ErrUnexpectedEOF` を発生させずにすべてのパートを正常に読み取れることを保証します。これは、バッファリング処理における潜在的なエッジケースを広範囲にカバーするための非常に堅牢なアプローチです。

これらのテストの追加により、修正が特定のバグを解決するだけでなく、同様のバッファリング関連のエッジケースに対しても堅牢であることが確認されます。

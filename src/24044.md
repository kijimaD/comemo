# [インデックス 24044] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/url` パッケージにおける `URL` 構造体の `RawPath` フィールドの扱いを変更するものです。具体的には、`RawPath` が本当に必要な場合にのみ設定されるようにロジックが修正され、クライアントがこのフィールドに過度に依存することを避けるよう促しています。

## 元コミット内容

`net/url` パッケージにおいて、`RawPath` フィールドは必要な場合にのみ記録されるように変更されました。

`RawPath` は `Path` の望ましいエンコーディングを示すヒントです。
`Path` が変更されたにもかかわらず `RawPath` が変更されていない場合など、`RawPath` が `Path` の有効なエンコーディングではない場合は無視されます。
また、`url` パッケージが自然に選択するエンコーディングと一致する場合、`RawPath` は無視されませんが、特に有用でもありません。
後者の場合、`RawPath` は空文字列に設定されます。
これにより、クライアントが一般的に `RawPath` の存在に依存すべきではなく、代わりに `EncodedPath` メソッドを使用すべきであるという点を強調するのに役立ちます。

この変更は、特にパースされたURLに対して `reflect.DeepEqual` を使用するテストへの影響も軽減します。

## 変更の背景

このコミットの背景には、Go言語の `net/url` パッケージにおける `URL` 構造体の `RawPath` フィールドの役割と、それに対する開発者の誤解を解消するという意図があります。

元々、`RawPath` はURL文字列から直接抽出された、パーセントエンコードされたパス部分を保持していました。しかし、`URL` 構造体には、デコードされたパスを保持する `Path` フィールドも存在します。ユーザーが `Path` フィールドを直接変更した場合、`RawPath` と `Path` の間に不整合が生じる可能性がありました。また、`RawPath` が `Path` の「自然な」エンコーディング（つまり、`url` パッケージが `Path` から自動的に生成するエンコーディング）と一致する場合、`RawPath` を保持しておくことにはほとんど意味がありませんでした。

この状況は、開発者が `RawPath` を、常に有効で信頼できるエンコード済みパスとして誤解し、`URL` 構造体の他のフィールド（特に `Path`）との整合性を考慮せずに使用してしまうリスクを生んでいました。Goの設計思想では、明確な意図と一貫性のあるAPIを提供することが重視されます。`RawPath` の曖昧な振る舞いは、この原則に反する可能性がありました。

そこで、このコミットでは `RawPath` の役割を「`Path` の望ましいエンコーディングへのヒント」と再定義し、その存在をより厳密に制御することで、開発者に `EncodedPath` メソッドの使用を促すことを目的としています。`EncodedPath` メソッドは、常に `Path` フィールドの現在の値に基づいて正しいエンコード済みパスを計算するため、より信頼性の高い方法です。

さらに、`RawPath` が常に設定されるわけではなくなることで、`reflect.DeepEqual` を使用して `URL` 構造体を比較するテストにおいて、`RawPath` の値の有無による不必要なテスト失敗を減らすという副次的な効果も期待されています。これは、テストの安定性と保守性の向上に貢献します。

## 前提知識の解説

### 1. URLの構造とパスのエンコーディング

WebにおけるURL (Uniform Resource Locator) は、リソースの場所を特定するための文字列です。一般的なURLは以下のような構造を持っています。

`scheme://user:password@host:port/path?query#fragment`

このコミットで特に重要なのは「パス (Path)」の部分です。パスはリソースの階層的な位置を示し、`/` で区切られます。URLの仕様（RFC 3986など）では、パスに含まれる特定の文字（例: スペース、日本語文字、一部の記号）は、URLとして安全に転送するために「パーセントエンコーディング」と呼ばれる形式でエンコードされる必要があります。パーセントエンコーディングでは、非ASCII文字や予約文字は `%HH` の形式（HHは文字のASCII値またはUTF-8バイト列の16進表現）に変換されます。

例: `/a b` は `/a%20b` とエンコードされます。

### 2. Go言語の `net/url` パッケージ

Go言語の `net/url` パッケージは、URLのパース、生成、およびクエリパラメータの操作を行うための機能を提供します。このパッケージの中心となるのが `URL` 構造体です。

#### `url.URL` 構造体の主要フィールド

*   **`Scheme`**: URLのスキーム（例: `http`, `https`, `ftp`）。
*   **`Host`**: ホスト名とポート番号（例: `www.example.com:8080`）。
*   **`Path`**: デコードされたパス部分。パーセントエンコーディングが解除された状態のパス文字列。
*   **`RawPath`**: エンコードされたパス部分。URL文字列から直接抽出された、パーセントエンコードされた状態のパス文字列。このコミットの主要な変更点です。
*   **`RawQuery`**: エンコードされたクエリ文字列（例: `q=foo%20bar`）。
*   **`Fragment`**: フラグメント識別子（例: `section1`）。

#### `url.URL` 構造体の主要メソッド

*   **`EscapedPath()`**: `Path` フィールドの現在の値に基づいて、適切にパーセントエンコードされたパス文字列を返します。このメソッドは、`RawPath` の値に依存せず、常に `Path` の内容から計算されます。
*   **`EncodedPath()`**: `RawPath` が設定されている場合はその値を返し、設定されていない場合は `EscapedPath()` の結果を返します。このメソッドは、`RawPath` が「ヒント」として機能する場合に、そのヒントを優先して利用するためのものです。

### 3. `reflect.DeepEqual`

Go言語の `reflect` パッケージは、実行時に型情報を調べたり、値の操作を行ったりするための機能を提供します。`reflect.DeepEqual(x, y)` 関数は、2つの値 `x` と `y` が「深く」等しいかどうかを判定します。これは、プリミティブ型だけでなく、構造体、配列、スライス、マップなどの複合型についても、その要素やフィールドが再帰的に等しいかを比較します。

テストコードで `reflect.DeepEqual` を使用してパースされた `URL` 構造体を比較する場合、`URL` 構造体のすべてのフィールド（`Path`, `RawPath`, `Scheme` など）が完全に一致する必要があります。もし `RawPath` の値が、その存在が必須ではない状況で不必要に設定されていると、`Path` の値は同じでも `RawPath` の値が異なるために `DeepEqual` が `false` を返す、というような意図しないテスト失敗を引き起こす可能性がありました。

## 技術的詳細

このコミットの技術的な核心は、`net/url` パッケージの `parse` 関数における `RawPath` の設定ロジックの変更と、それに伴う関連コードの調整です。

### `src/net/url/url.go` の変更点

以前の `parse` 関数では、URL文字列からパス部分を抽出した後、その生の文字列を無条件に `url.RawPath` に代入していました。

```go
// 変更前 (簡略化)
// ...
url.RawPath = rest // rest はURLから抽出された生のパス文字列
if url.Path, err = unescape(rest, encodePath); err != nil {
    goto Error
}
// ...
```

このコミットでは、この `RawPath` の設定ロジックが以下のように変更されました。

```go
// 変更後 (簡略化)
// ...
// url.RawPath = rest // この行が削除された
if url.Path, err = unescape(rest, encodePath); err != nil {
    goto Error
}
// RawPath is a hint as to the encoding of Path to use
// in url.EncodedPath. If that method already gets the
// right answer without RawPath, leave it empty.
// This will help make sure that people don't rely on it in general.
if url.EscapedPath() != rest && validEncodedPath(rest) {
    url.RawPath = rest
}
return url, nil
// ...
```

新しいロジックでは、`url.Path` がデコードされた後に、以下の条件が満たされた場合にのみ `url.RawPath` が元の生のパス文字列 (`rest`) に設定されます。

1.  `url.EscapedPath()` の結果が元の生のパス文字列 (`rest`) と異なること。
    *   `url.EscapedPath()` は `url.Path` の現在の値からエンコードされたパスを計算します。
    *   この条件は、`url.Path` をエンコードした結果が元の `RawPath` と異なる場合に `RawPath` を保持する意味があることを示唆しています。つまり、元の `RawPath` が `url` パッケージの「自然な」エンコーディングとは異なる、特別なエンコーディング情報を含んでいる可能性がある場合に `RawPath` を保持します。
2.  元の生のパス文字列 (`rest`) が `validEncodedPath(rest)` によって有効なエンコード済みパスであると判断されること。
    *   `validEncodedPath` 関数は、与えられた文字列がURLパスとして有効なパーセントエンコーディングを含んでいるかをチェックします。具体的には、エスケープが必要な文字がエスケープされていない場合（例: スペースが `%20` になっていない場合）は無効と判断します。このチェックは、`RawPath` が無効なエンコーディング情報を持つことを防ぎます。

これらの条件が満たされない場合、`url.RawPath` は空文字列のままとなります。これにより、`RawPath` は「`Path` の自然なエンコーディングとは異なる、特別なエンコーディング情報が元のURLに含まれていた場合」にのみ設定される「ヒント」としての役割に限定されます。

また、`validEncodedPath` 関数のコメントも修正されています。

```go
// 変更前
// It must contain any bytes that require escaping during path encoding.
// 変更後
// It must not contain any bytes that require escaping during path encoding.
```
これは、`validEncodedPath` の本来の意図（エスケープが必要なバイトを含まないこと、つまり既に適切にエンコードされていること）をより正確に反映するための修正です。

### テストコードの変更点

`src/net/http/readrequest_test.go` と `src/net/url/url_test.go` では、この `RawPath` の新しい振る舞いに合わせて、期待される `URL` 構造体の `RawPath` フィールドの値が調整されています。

*   `readrequest_test.go` では、多くのテストケースで `RawPath: "/"` のような明示的な `RawPath` の設定が削除されています。これは、これらのケースでは `url.EscapedPath()` が元のパスと一致するため、新しいロジックでは `RawPath` が空になるためです。
*   `url_test.go` では、`urltests` 配列から `RawPath: "/a%20b"` のようなエントリが削除され、`ufmt` 関数が `RawPath` を出力するように変更されています。また、`DoTest` 関数内の `RawPath` のデフォルト設定ロジックも削除されています。これにより、テストが新しい `RawPath` のセマンティクスに準拠するようになります。

これらの変更は、`RawPath` が「ヒント」であり、常に存在することを期待すべきではないというメッセージをコードとテストの両方で強化しています。

## コアとなるコードの解説

上記の `src/net/url/url.go` の変更は、`URL` 構造体のパース処理において `RawPath` フィールドがどのように設定されるかを根本的に変えています。

1.  **`url.RawPath = rest` の削除**: 以前は、URLから抽出された生のパス文字列 `rest` が無条件に `url.RawPath` に代入されていました。この行が削除されたことで、`RawPath` はデフォルトでは設定されなくなりました。

2.  **条件付き `RawPath` 設定ロジックの追加**:
    `url.Path` が `unescape` 関数によってデコードされた後、以下の条件文が追加されました。

    ```go
    if url.EscapedPath() != rest && validEncodedPath(rest) {
        url.RawPath = rest
    }
    ```

    *   `url.EscapedPath() != rest`: これは、`url.Path` を現在の `url` パッケージの標準的なルールでエンコードした結果 (`url.EscapedPath()`) が、元の生のパス文字列 (`rest`) と異なるかどうかをチェックしています。もし異なっていれば、元の `rest` には `url` パッケージが通常生成しないような、何らかの「特別な」エンコーディング情報が含まれている可能性があり、その情報を `RawPath` として保持する意味がある、と判断されます。
    *   `validEncodedPath(rest)`: この関数は、元の生のパス文字列 `rest` が、URLパスとして有効なパーセントエンコーディング規則に従っているかを検証します。例えば、エスケープが必要な文字（スペースなど）が適切に `%20` のようにエンコードされているかを確認します。このチェックにより、無効なエンコーディングを持つ文字列が `RawPath` に設定されることを防ぎます。

    この2つの条件が**両方とも**真である場合にのみ、元の生のパス文字列 `rest` が `url.RawPath` に代入されます。それ以外の場合、`url.RawPath` は空文字列のままとなります。

3.  **`validEncodedPath` のコメント修正**:
    `validEncodedPath` 関数のコメントが「`It must contain any bytes that require escaping during path encoding.`」から「`It must not contain any bytes that require escaping during path encoding.`」に修正されました。これは、この関数が「エスケープが必要なバイトを含まないこと」（つまり、既に適切にエンコードされていること）を報告するものであるという、本来の意図をより正確に表現しています。

これらの変更により、`RawPath` は単なる生のパス文字列のコピーではなく、「`Path` の自然なエンコーディングとは異なる、特別なエンコーディング情報が元のURLに含まれており、かつそのエンコーディングが有効である場合」にのみ設定される「ヒント」としての役割が明確化されました。これにより、開発者は `RawPath` の存在に依存するのではなく、常に `Path` フィールドから計算される `EncodedPath()` メソッドを使用することが推奨されるようになります。

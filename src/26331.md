## 元コミット内容

Goのビルドプロセスにおいて、デフォルトでPIE (Position-Independent Executable) が有効になっているシステムで問題が発生していました。具体的には、リンカが`-r` (部分リンク) と`-pie` (PIE生成) の両方を同時に使用できないというエラーを報告していました。この問題は、特にUbuntu Xenialのs390xアーキテクチャで顕著でしたが、将来的にはamd64アーキテクチャでもPIEがデフォルトで有効になる計画があったため、より広範な問題となる可能性がありました。

この問題を解決するためには、コンパイラに`-no-pie`フラグを`-Wl,-r`と共に渡す必要がありました。しかし、`-no-pie`フラグは比較的新しいため、すべてのコンパイラでサポートされているわけではありませんでした。そこで、このコミットでは、`-no-pie`フラグがサポートされているかどうかをテストコンパイルによって検出し、サポートされている場合にのみフラグを渡すように変更されました。

## 変更の背景

この変更の背景には、現代のオペレーティングシステムにおけるセキュリティ強化のトレンドがあります。PIE (Position-Independent Executable) は、ASLR (Address Space Layout Randomization) と組み合わせて使用されることで、メモリ上の実行可能ファイルやライブラリの配置をランダム化し、バッファオーバーフローなどのメモリ関連の脆弱性を悪用した攻撃を困難にする重要なセキュリティ機能です。

多くのLinuxディストリビューション、特にUbuntuのような主要なディストリビューションでは、セキュリティ向上のため、デフォルトでPIEを有効にする方向に進んでいます。しかし、Goのビルドシステムが内部的に使用するリンカのオプション（特に`-Wl,-r`による部分リンク）と、PIEを生成するためのオプション（`-pie`）が競合するという問題が発生しました。

具体的には、Goのビルドプロセスでは、Cgo（GoとCの相互運用機能）を使用する際に、CコードをコンパイルしてGoのオブジェクトファイルとリンクする中間ステップで、リンカに`-Wl,-r`オプションを渡して部分的なリンクを行います。この`-Wl,-r`は、複数のオブジェクトファイルを結合して、最終的な実行可能ファイルや共有ライブラリではない、再配置可能な単一のオブジェクトファイルを生成するために使用されます。

PIEがデフォルトで有効なシステムでは、リンカは暗黙的に`-pie`オプションも適用しようとします。しかし、GNU ldリンカは、`-r`（部分リンク）と`-pie`（PIE生成）を同時に指定することを許可していません。これは、部分リンクされたオブジェクトファイルは、それ自体が最終的な実行可能ファイルではないため、PIEである必要がない、あるいはPIEの概念が適用できないためと考えられます。この競合により、Goのビルドが失敗するという問題が発生していました。

このコミットは、このビルドエラーを回避し、GoがPIEがデフォルトで有効なシステムでも正しくビルドできるようにするための対応です。特に、`-no-pie`という新しいリンカフラグが導入されたことで、この問題を解決する道が開かれました。しかし、このフラグがすべての`gcc`バージョンで利用可能ではないため、そのサポートを動的に検出する必要がありました。

## 前提知識の解説

### 1. PIE (Position-Independent Executable) と ASLR (Address Space Layout Randomization)

*   **PIE (Position-Independent Executable)**: 実行可能ファイルがメモリ上の任意のアドレスにロードされても正しく実行できるようにコンパイルされた形式です。通常、プログラムは固定されたメモリアドレスを前提としてコンパイルされますが、PIEは相対アドレス指定を使用することで、この制約を取り除きます。
*   **ASLR (Address Space Layout Randomization)**: オペレーティングシステムが、実行可能ファイル、ライブラリ、ヒープ、スタックなどのメモリアドレス空間の配置をランダム化するセキュリティ技術です。PIEとASLRが組み合わされることで、攻撃者が特定のコードやデータがメモリ上のどこにあるかを予測することが非常に困難になり、Return-Oriented Programming (ROP) などの攻撃手法に対する防御が強化されます。現代のLinuxシステムでは、セキュリティ強化のためにPIEがデフォルトで有効になっていることが多いです。

### 2. `-Wl,-r` (リンカオプション)

*   `gcc`や`go tool compile`などのコンパイラコマンドにおいて、`-Wl,option`という形式は、指定された`option`をリンカ（`ld`）に直接渡すためのものです。
*   `-Wl,-r`は、リンカに`-r`オプションを渡すことを意味します。リンカの`-r`オプションは「再配置可能な出力ファイルを生成する」ことを指示します。これは、複数のオブジェクトファイル（`.o`ファイル）を結合して、最終的な実行可能ファイルや共有ライブラリではなく、それ自体が別のリンク操作の入力として使用できる単一の大きなオブジェクトファイルを生成する際に使用されます。これを「部分リンク (partial linking)」と呼びます。GoのCgoビルドプロセスでは、CコードをGoのランタイムとリンクする中間ステップでこの部分リンクが利用されます。

### 3. `-pie` (リンカオプション)

*   リンカにPIE形式の実行可能ファイルを生成するように指示するオプションです。PIEがデフォルトで有効なシステムでは、このオプションが暗黙的に適用されることがあります。

### 4. `-no-pie` (リンカオプション)

*   リンカにPIE形式の実行可能ファイルを生成しないように明示的に指示するオプションです。これは、システムがデフォルトでPIEを有効にしている場合でも、特定のビルドでPIEを無効にしたい場合に利用されます。このフラグは比較的新しい`gcc`および`ld`のバージョンで導入されました。

### 問題の核心

PIEがデフォルトで有効なシステムでは、Goのビルドプロセスが`-Wl,-r`を使用して部分リンクを行おうとすると、リンカは暗黙的に`-pie`も適用しようとします。しかし、GNU `ld`リンカは、`-r`と`-pie`を同時に使用することを許可していません。このため、「`/usr/bin/ld: -r and -pie may not be used together`」というエラーが発生し、ビルドが失敗していました。

このコミットは、この競合を解決するために、部分リンクを行う際に明示的に`-no-pie`をリンカに渡すことで、PIEの生成を抑制するようにGoのビルドツールを変更するものです。ただし、`-no-pie`フラグがすべての`gcc`バージョンでサポートされているわけではないため、そのサポートを動的にチェックするメカニズムが必要とされました。

## 技術的詳細

このコミットの技術的な核心は、`gcc`コンパイラが`-no-pie`フラグをサポートしているかどうかを動的に検出し、その結果に基づいてビルドオプションを調整する点にあります。

1.  **問題の特定**: GoのビルドシステムがCgoを使用する際、中間的なリンクステップで`-Wl,-r`（部分リンク）オプションをリンカに渡します。PIEがデフォルトで有効なLinuxシステムでは、リンカは暗黙的に`-pie`オプションも適用しようとします。しかし、GNU `ld`リンカは`-r`と`-pie`の同時使用を許可しないため、ビルドエラーが発生します。
2.  **解決策の提案**: この問題を解決するためには、部分リンクを行う際にリンカに明示的に`-no-pie`オプションを渡すことで、PIEの生成を抑制する必要があります。
3.  **互換性の問題**: `-no-pie`フラグは比較的新しい`gcc`のバージョンで導入されたため、すべての環境で利用できるわけではありません。古い`gcc`バージョンでこのフラグを渡すと、認識されないオプションとしてエラーになる可能性があります。
4.  **動的な検出メカニズム**: この互換性の問題を解決するため、Goのビルドツール（`cmd/go`）内に、`gcc`が`-no-pie`をサポートしているかどうかをテストコンパイルによって確認するロジックが導入されました。
    *   `gccSupportsNoPie()`という新しいメソッドが`builder`構造体に追加されました。
    *   このメソッドは、まず現在のOSがLinuxであるかを確認します。`-no-pie`の問題は主にLinuxシステムで発生するため、他のOSではテストをスキップします。
    *   次に、一時ディレクトリ内に「trivial.c」という空のCソースファイルを作成します。
    *   この空のCファイルを、現在の`gcc`コマンドと`-no-pie -c`オプション（コンパイルのみ、リンクはしない）を使ってコンパイルを試みます。
    *   コンパイルが成功すれば（エラーコードが`nil`であれば）、`gcc`は`-no-pie`フラグをサポートしていると判断し、`true`を返します。
    *   コンパイルが失敗すれば、サポートしていないと判断し、`false`を返します。
5.  **条件付きフラグ追加**: `gccSupportsNoPie()`の戻り値に基づいて、`ld`（リンカ）および`cgo`のビルドステップで`ldflags`に`-no-pie`が条件付きで追加されるようになりました。これにより、`-no-pie`をサポートする環境でのみこのフラグが使用され、互換性のない環境でのビルドエラーが回避されます。

このアプローチにより、Goは新しいセキュリティ機能（PIEデフォルト有効化）を採用するシステムと、古い`gcc`バージョンを使用するシステムの両方で、安定してビルドできるようになりました。

## コアとなるコードの変更箇所

変更は`src/cmd/go/build.go`ファイルに集中しています。

1.  **`gccSupportsNoPie()` メソッドの追加**:
    `builder`構造体に新しいプライベートメソッド`gccSupportsNoPie()`が追加されました。このメソッドは、現在の`gcc`が`-no-pie`フラグをサポートしているかどうかをテストコンパイルによって判断します。

    ```go
    // On systems with PIE (position independent executables) enabled by default,
    // -no-pie must be passed when doing a partial link with -Wl,-r. But -no-pie is
    // not supported by all compilers.
    func (b *builder) gccSupportsNoPie() bool {
        if goos != "linux" {
            // ... (省略: Linux以外ではテストしない)
            return false
        }
        src := filepath.Join(b.work, "trivial.c")
        if err := ioutil.WriteFile(src, []byte{}, 0666); err != nil {
            return false
        }
        cmdArgs := b.gccCmd(b.work)
        cmdArgs = append(cmdArgs, "-no-pie", "-c", "trivial.c")
        // ... (省略: buildN/buildX の処理)
        cmd := exec.Command(cmdArgs[0], cmdArgs[1:]...)
        cmd.Dir = b.work
        cmd.Env = envForDir(cmd.Dir, os.Environ())
        err := cmd.Run()
        return err == nil
    }
    ```

2.  **`ld` メソッドでの `-no-pie` の条件付き追加**:
    `gccgoToolchain`の`ld`メソッド内で、部分リンク（`-Wl,-r`）を行う際に、`b.gccSupportsNoPie()`が`true`を返す場合にのみ`ldflags`に`-no-pie`が追加されます。

    ```go
    func (tools gccgoToolchain) ld(b *builder, root *action, out string, allactions []*action) (string, []string) {
        // ...
        ldflags = append(ldflags, "-Wl,-r", "-nostdlib", "-Wl,--whole-archive", "-lgolibbegin", "-Wl,--no-whole-archive")

        if b.gccSupportsNoPie() {
            ldflags = append(ldflags, "-no-pie")
        }
        // ...
    }
    ```

3.  **`cgo` メソッドでの `-no-pie` の条件付き追加**:
    `builder`の`cgo`メソッド内でも同様に、`b.gccSupportsNoPie()`が`true`を返す場合にのみ`ldflags`に`-no-pie`が追加されます。

    ```go
    func (b *builder) cgo(p *Package, cgoExe, obj string, pcCFLAGS, pcLDFLAGS, cgofile string, outGo, outObj []string) {
        // ...
        ldflags := stringList(bareLDFLAGS, "-Wl,-r", "-nostdlib", staticLibs)

        if b.gccSupportsNoPie() {
            ldflags = append(ldflags, "-no-pie")
        }
        // ...
    }
    ```

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/go/build.go`ファイルに導入された`gccSupportsNoPie()`メソッドとその利用方法です。

### `gccSupportsNoPie()` メソッド

このメソッドは、Goのビルドシステムが使用する`gcc`コンパイラが`-no-pie`リンカフラグをサポートしているかどうかを動的に検出するために設計されています。

1.  **OSのチェック**:
    ```go
    if goos != "linux" {
        return false
    }
    ```
    このチェックは、`-no-pie`フラグの必要性が主にLinuxシステムに限定されているためです。他のOS（例えばBSD系）では、`-no-pie`をテストしようとすると、たとえ`cmd.Std*`が`nil`であってもコンソールにエラーメッセージが出力される可能性があるため、無関係なシステムでのテストを避けるために早期リターンしています。

2.  **一時ファイルの作成**:
    ```go
    src := filepath.Join(b.work, "trivial.c")
    if err := ioutil.WriteFile(src, []byte{}, 0666); err != nil {
        return false
    }
    ```
    `b.work`はビルド作業用の一時ディレクトリを指します。このディレクトリ内に`trivial.c`という名前の空のCソースファイルを作成します。このファイルは、`gcc`のコンパイルテストの対象となります。ファイルの内容は空で十分です。

3.  **コンパイルコマンドの構築**:
    ```go
    cmdArgs := b.gccCmd(b.work)
    cmdArgs = append(cmdArgs, "-no-pie", "-c", "trivial.c")
    ```
    `b.gccCmd(b.work)`は、現在のビルド環境で`gcc`を呼び出すための基本的なコマンドライン引数（`gcc`のパスやデフォルトのフラグなど）を返します。これに、テストしたいフラグである`-no-pie`と、コンパイルのみを行うための`-c trivial.c`を追加します。`-c`オプションは、リンクを行わずにオブジェクトファイル（この場合は`trivial.o`）を生成するよう`gcc`に指示します。これにより、リンカの動作ではなく、`gcc`が`-no-pie`フラグ自体を認識するかどうかをテストできます。

4.  **コマンドの実行と結果の評価**:
    ```go
    cmd := exec.Command(cmdArgs[0], cmdArgs[1:]...)
    cmd.Dir = b.work
    cmd.Env = envForDir(cmd.Dir, os.Environ())
    err := cmd.Run()
    return err == nil
    ```
    構築した`gcc`コマンドを実行します。`cmd.Dir`を作業ディレクトリに設定し、適切な環境変数を渡します。`cmd.Run()`はコマンドの実行を待ち、エラーが発生した場合は`error`を返します。`err == nil`であれば、コマンドは正常に実行された、つまり`gcc`が`-no-pie`フラグを認識し、エラーなくコンパイルできたことを意味します。この場合、メソッドは`true`を返し、`gcc`が`-no-pie`をサポートしていると判断します。エラーが発生した場合は`false`を返し、サポートしていないと判断します。

### `ld` および `cgo` メソッドでの利用

`gccSupportsNoPie()`メソッドは、`gccgoToolchain`の`ld`メソッドと`builder`の`cgo`メソッドの2箇所で利用されています。これらのメソッドは、Goのビルドプロセスにおいて、Cgoで書かれたコードやGoランタイムの一部をCコンパイラ/リンカと連携させて処理する際に呼び出されます。

```go
if b.gccSupportsNoPie() {
    ldflags = append(ldflags, "-no-pie")
}
```
このコードスニペットは、`ldflags`（リンカに渡すフラグのリスト）に`-no-pie`を追加するかどうかを、`gccSupportsNoPie()`の結果に基づいて決定しています。これにより、`-Wl,-r`オプションが使用される部分リンクの際に、PIEがデフォルトで有効なシステムであっても、リンカが`-r`と`-pie`の競合エラーを発生させることなく、ビルドが成功するようになります。

この変更により、Goのビルドシステムは、異なる`gcc`バージョンやOSのデフォルト設定（PIEの有効/無効）に対してより堅牢になり、幅広い環境での互換性が向上しました。

# [インデックス 25775] ファイルの概要

このコミットは、GoランタイムにおけるSolaris環境でのシステムコール（syscall）の挙動に関する重要な修正を含んでいます。特に、Goの内部構造である`g`（goroutine）が存在しない状況下でもシステムコールを安全に呼び出せるようにするための変更が加えられています。これにより、Cgoコールバックなどの特定のシナリオで発生していたデッドロックや無限ループの問題が解決されました。

## 元コミット内容

このコミットは、GoランタイムがSolaris上でシステムコールを呼び出す際に、現在のgoroutine（`g`）が存在しない状況でも適切に動作するようにするための変更です。主な変更点は以下の2点です。

1.  `libcall`構造体をスタック上に割り当てるように変更。これは、`nosplit`スタックのサイズが大きくなったことで可能になりました。
2.  アセンブリコード`asmsysvicall6`において、`g`が`nil`の場合に`errno`（システムコールエラーコード）の更新をスキップするロジックを追加。

これらの修正により、Solaris環境での`TestCgoCallbackGC`テストが無限ループに陥る問題が解決されました。

## 変更の背景

Goランタイムは、Cgo（GoとC言語の相互運用機能）を介してCライブラリ関数を呼び出す際に、GoのスケジューラからCのスタックに切り替える必要があります。このプロセス中に、Goのgoroutine（`g`）が一時的に存在しない状態になることがあります。特に、CgoコールバックがGoコードを呼び出すような複雑なシナリオでは、GoランタイムがCのコンテキストからシステムコールを実行しようとすることがあります。

以前の実装では、システムコールを呼び出す際に使用される`libcall`構造体が、現在の`m`（OSスレッドを表すGoランタイムの構造体）に紐付けられた領域から取得されていました。また、システムコールが失敗した場合に設定される`errno`の更新ロジックは、常に`g`が存在することを前提としていました。

しかし、`g`が存在しない状況でシステムコールが呼び出されると、`getg()`が`nil`を返すため、`libcall`の取得や`errno`の更新処理が不正なメモリアクセスを引き起こしたり、予期せぬ挙動（例えば無限ループ）に陥ったりする可能性がありました。特にSolaris環境の`TestCgoCallbackGC`テストでこの問題が顕在化し、テストがハングアップする原因となっていました。

このコミットは、これらの問題を解決し、Goランタイムがより堅牢に、かつ多様なシナリオでシステムコールを扱えるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とOSのメカニズムに関する知識が必要です。

*   **Goroutine (g)**: Goの軽量スレッドです。Goプログラムの並行処理の基本単位であり、Goスケジューラによって管理されます。各goroutineは独自のスタックを持ちます。
*   **M (Machine)**: OSスレッドを表すGoランタイムの構造体です。Goスケジューラは、`g`を`M`上で実行します。`M`はOSスレッドと1対1で対応し、Cgo呼び出しの際にはCスタックに切り替わります。
*   **P (Processor)**: 論理プロセッサを表すGoランタイムの構造体です。`P`は`M`に割り当てられ、`g`の実行に必要なリソース（例えば、実行キュー）を提供します。
*   **`nosplit`関数**: Goコンパイラディレクティブの一つで、関数がスタックを拡張しないことを保証します。これは、スタックの切り替えができない、あるいは望ましくない低レベルのランタイム関数でよく使用されます。`nosplit`関数は、呼び出し時に十分なスタック領域が確保されていることを前提とします。
*   **`libcall`構造体**: GoランタイムがCライブラリ関数（特にCgoを介した呼び出し）を実行する際に、引数や戻り値、呼び出す関数ポインタなどの情報を保持するために使用される内部構造体です。
*   **`asmcgocall`**: GoランタイムがCgoを介してC関数を呼び出すためのアセンブリルーチンです。GoのスタックからCのスタックへの切り替えなどを担当します。
*   **`errno`**: Unix系OSにおいて、システムコールがエラーを返した場合に、そのエラーの種類を示す整数値が格納されるグローバル変数（またはスレッドローカル変数）です。Goランタイムは、Cgoを介してシステムコールを呼び出した際に、この`errno`の値を適切に処理する必要があります。
*   **Cgo Callback**: CコードからGo関数を呼び出すメカニズムです。これは、GoとCの相互運用において非常に強力な機能ですが、スタック管理やgoroutineのコンテキストに関して複雑な問題を引き起こす可能性があります。
*   **スタック割り当て**: 関数が呼び出される際に、ローカル変数や引数などを格納するためにメモリ領域（スタックフレーム）が割り当てられます。Goでは、goroutineごとに可変長のスタックが割り当てられ、必要に応じて自動的に拡張されます。しかし、`nosplit`関数ではこの自動拡張が行われません。

## 技術的詳細

このコミットの技術的詳細は、主にGoランタイムのスタック管理とCgo呼び出しメカニズム、そしてSolaris固有の`errno`処理に関連しています。

1.  **`libcall`構造体のスタック割り当てへの変更**:
    *   以前の`src/runtime/os_solaris.go`では、`sysvicallN`関数群（`N`は引数の数）内で`libcall`構造体を取得する際に、`libcall := &getg().m.libcall`というコードが使われていました。これは、現在のgoroutine（`g`）が実行されているOSスレッド（`m`）に紐付けられた`libcall`構造体へのポインタを取得することを意味します。
    *   このアプローチの問題点は、Cgoコールバックなどのシナリオで`g`が`nil`（つまり、Goのgoroutineコンテキストが存在しない）の場合に、`getg()`が`nil`を返し、その結果`nil`ポインタデリファレンスが発生する可能性があったことです。
    *   今回の変更では、`libcall := &getg().m.libcall`を`var libcall libcall`に置き換えました。これにより、`libcall`構造体はヒープではなく、現在の関数のスタックフレーム上にローカル変数として割り当てられるようになります。
    *   コミットメッセージにある「The nosplit stack is now much bigger, so we can afford to allocate libcall on stack.」という記述は、この変更の前提条件を説明しています。`sysvicallN`関数群は`//go:nosplit`ディレクティブが付与されており、スタックの自動拡張が行われません。そのため、これらの関数内でローカル変数を割り当てるには、事前に十分なスタック領域が確保されている必要があります。Goランタイムの進化により、`nosplit`スタックのサイズが大きくなったため、`libcall`構造体をスタック上に安全に配置できるようになった、ということです。
    *   この変更により、`g`が`nil`であっても`libcall`構造体の割り当てに失敗することがなくなり、システムコール呼び出しの準備がより堅牢になりました。

2.  **`asmsysvicall6`における`errno`更新のスキップ**:
    *   `src/runtime/sys_solaris_amd64.s`のアセンブリコード`runtime·asmsysvicall6`は、Solaris環境でシステムコールを呼び出すための低レベルなルーチンです。このルーチンは、システムコールが完了した後に`errno`の値をGoランタイムの適切な場所に保存する役割も担っています。
    *   以前の実装では、`errno`の保存処理は常に`g`が存在することを前提としていました。具体的には、`g`レジスタ（`BX`）から`m`（`g_m(BX)`）を取得し、その`m`に紐付けられた`errno`ポインタ（`m_mOS+mOS_perrno)(BX)`）を介して`errno`を更新していました。
    *   しかし、`g == nil`の状況では、`g_m(BX)`のデリファレンスが不正なメモリアクセスを引き起こす可能性がありました。
    *   今回の修正では、`get_tls(CX)`でスレッドローカルストレージから`g`を取得した後、`CMPQ BX, $0`と`JEQ skiperrno1`（または`skiperrno2`）という命令を追加しました。これは、`g`レジスタ（`BX`）が`nil`（0）であるかどうかをチェックし、`nil`であれば`skiperrno1`（または`skiperrno2`）ラベルにジャンプして、`errno`の更新処理を完全にスキップすることを意味します。
    *   この変更により、`g`が存在しない状況でシステムコールが呼び出されても、`errno`の更新処理が安全にスキップされ、クラッシュや無限ループを防ぐことができます。`errno`は通常、現在のgoroutineに関連付けられたスレッドローカルな情報であるため、`g`が存在しない場合はその値を更新する必要がない、という判断に基づいています。

これらの変更は、GoランタイムがCgoとシステムコールを扱う際の堅牢性を高め、特にSolarisのような特定のOS環境での安定性を向上させるものです。

## コアとなるコードの解説

### `src/runtime/os_solaris.go` の変更

このファイルでは、`sysvicall0`から`sysvicall6`までの関数が変更されています。これらの関数は、引数の数が異なるCライブラリ関数を呼び出すためのGoラッパーです。

変更前:
```go
libcall := &getg().m.libcall
```
この行は、現在のgoroutine (`g`) が実行されているOSスレッド (`m`) に関連付けられた`libcall`構造体へのポインタを取得していました。`getg()`は現在のgoroutineへのポインタを返しますが、CgoコールバックなどでGoのコンテキストが完全に確立されていない場合、`getg()`は`nil`を返す可能性があります。その結果、`nil.m`のような不正なメモリアクセスが発生し、プログラムがクラッシュする原因となっていました。

変更後:
```go
var libcall libcall
```
この行は、`libcall`構造体をローカル変数として宣言しています。これにより、`libcall`は現在の関数のスタックフレーム上に直接割り当てられます。`sysvicallN`関数群は`//go:nosplit`関数であるため、スタックの自動拡張は行われませんが、コミットメッセージにあるように、`nosplit`スタックのサイズが大きくなったことで、この程度の構造体をスタックに割り当てる余裕ができたため、安全にこの変更を行うことができました。この変更により、`getg()`が`nil`を返す状況でも`libcall`構造体の初期化が安全に行えるようになり、依存関係が解消されました。

### `src/runtime/sys_solaris_amd64.s` の変更

このアセンブリファイルでは、`runtime·asmsysvicall6`という関数が変更されています。これは、Solaris/AMD64環境でのシステムコール呼び出しの低レベルな実装です。

追加されたコード:
```assembly
	CMPQ	BX, $0
	JEQ	skiperrno1
```
および
```assembly
	CMPQ	BX, $0
	JEQ	skiperrno2
```

これらの命令は、`errno`を更新する処理の直前に追加されています。
*   `get_tls(CX)`: スレッドローカルストレージから現在のgoroutine (`g`) へのポインタを`CX`レジスタにロードします。
*   `MOVQ g(CX), BX`: `CX`レジスタが指す`g`構造体のアドレスから、`g`自体へのポインタを`BX`レジスタにロードします。
*   `CMPQ BX, $0`: `BX`レジスタ（`g`へのポインタ）が`nil`（0）であるかどうかを比較します。
*   `JEQ skiperrno1` (または `skiperrno2`): もし`BX`が`nil`であれば、`skiperrno1`（または`skiperrno2`）というラベルにジャンプします。これらのラベルは、`errno`の更新処理をスキップする場所を指しています。

この変更により、`g`が存在しない状況（例えば、CgoコールバックがGoコードを呼び出し、そのGoコードがさらにシステムコールを呼び出すような、Goのスケジューラがgoroutineコンテキストを完全に確立していない状態）でシステムコールが実行された場合でも、`errno`の更新処理が安全にスキップされます。`errno`は通常、現在のgoroutineに関連付けられたスレッドローカルな情報であるため、`g`が存在しない場合はその値を更新する必要がないという設計判断に基づいています。これにより、不正なメモリアクセスや、`errno`更新ロジックが無限ループに陥る問題を回避しています。

## 変更の背景

このコミットは、Go言語の`math`パッケージに含まれる`Sqrt`関数の純粋Go実装におけるバグを修正するために行われました。具体的には、[Issue 13013](https://golang.org/issue/13013)で報告された問題に対処しています。

報告された問題は、`math.Float64frombits(uint64(2))`のような非正規化数（subnormal number）を`math.Sqrt`関数に渡すと、特に`ppc64x`のようなソフトウェア実装の`Sqrt`を使用するアーキテクチャで無限ループに陥るというものでした。これは、`Sqrt`関数内部での数値の正規化処理に欠陥があったためです。非正規化数は非常に小さい数を表現するために使用され、浮動小数点演算において特別な注意が必要となる場合があります。このバグは、特定の非常に小さい入力値に対して`Sqrt`関数が正しく終了しないという、機能上の重大な問題を引き起こしていました。

## 前提知識の解説

### 浮動小数点数とIEEE 754標準

Go言語を含む多くのプログラミング言語では、浮動小数点数の表現にIEEE 754標準を使用しています。この標準では、数を符号部、指数部、仮数部（または分数部）に分けて表現します。`float64`型は倍精度浮動小数点数に対応し、64ビットで表現されます。

### 正規化数と非正規化数（Subnormal Numbers）

*   **正規化数 (Normal Numbers)**: ほとんどの浮動小数点数は正規化数です。これらは、仮数部の最上位ビットが常に1であると暗黙的に仮定することで、表現可能な精度を最大化します。指数部は0以外の値を取ります。
*   **非正規化数 (Subnormal Numbers / Denormalized Numbers)**: 非常に0に近い数を表現するために使用されます。指数部が最小値（通常は0）を取り、仮数部の最上位ビットが0になることを許容することで、正規化数よりもさらに小さい数を表現できます。これにより、アンダーフロー（underflow）による精度損失を緩和し、「0への段階的なアンダーフロー (gradual underflow)」を可能にします。しかし、非正規化数の演算は、正規化数に比べてパフォーマンスが低下したり、特別な処理が必要になったりすることがあります。

### `math.Sqrt`関数の実装

`math.Sqrt`関数は、与えられた浮動小数点数の平方根を計算します。多くのシステムでは、この計算はハードウェアによって高速に実行されますが、一部のアーキテクチャやクロスコンパイル環境では、純粋なソフトウェア実装が使用されることがあります。純粋Go実装の`Sqrt`関数は、通常、ニュートン法などの反復アルゴリズムを用いて平方根を近似計算します。このアルゴリズムが正しく機能するためには、入力値が適切な形式（正規化された形式）であることが望ましい場合があります。

### 正規化処理

浮動小数点演算において、特に非正規化数を扱う場合、計算の前に数値を正規化する（つまり、指数部を調整して仮数部の最上位ビットを1にする）処理が必要になることがあります。これは、計算の精度を保ち、アルゴリズムが意図した通りに動作するようにするためです。

## 技術的詳細

このバグは、`src/math/sqrt.go`内の`sqrt`関数の正規化ロジックに起因していました。`sqrt`関数は、入力された`float64`値`x`を処理する際に、まずそのビット表現`ix`を取得し、指数部を抽出します。

```go
// normalize x
exp := int((ix >> shift) & mask)
if exp == 0 { // subnormal x
    for ix&1<<shift == 0 { // ここが問題の箇所
        ix <<= 1
        exp--
    }
    // ...
}
```

ここで、`exp == 0`の条件は、入力`x`が非正規化数であることを示しています。非正規化数を正規化するために、`ix`（`x`のビット表現）を左シフトし、同時に指数`exp`をデクリメントするループが実行されます。このループの目的は、`ix`の最上位ビット（`shift`で指定される位置）が1になるまでシフトを続けることです。

問題のコード`ix&1<<shift == 0`は、`1<<shift`が先に評価され、その結果と`ix`のビットAND演算が行われます。しかし、Goの演算子の優先順位では、`<<`（左シフト）は`&`（ビットAND）よりも優先順位が低いです。したがって、`ix&1<<shift`は`ix & (1 << shift)`ではなく、` (ix & 1) << shift`と解釈されていました。

`ix & 1`は`ix`の最下位ビットのみを評価し、その結果を`shift`ビット左シフトします。非正規化数の場合、`ix`の最下位ビットが0であることはよくあります。この誤った評価により、ループの条件が常に`true`となり、`ix`が左シフトされ続けても、`ix & 1`の結果は変わらず、`ix&(1<<shift)`が期待通りに`ix`の`shift`ビット目をチェックするのではなく、常に`0`を返す可能性がありました。結果として、ループが終了せず、無限ループに陥っていたのです。

## コアとなるコードの解説

### `src/math/sqrt.go`の変更

問題のあった行:
```go
for ix&1<<shift == 0 {
```
が、以下のように修正されました:
```go
for ix&(1<<shift) == 0 {
```
この修正は、ビットAND演算子`&`と左シフト演算子`<<`の優先順位に関するGo言語の仕様を正しく反映させるためのものです。括弧`(1<<shift)`を追加することで、まず`1`を`shift`ビットだけ左シフトし、その結果（つまり、`shift`ビット目だけが1であるマスク）と`ix`のビットAND演算を行うように明示的に指示しています。これにより、ループ条件が正しく`ix`の`shift`ビット目が0であるかをチェックするようになり、非正規化数の正規化処理が正しく機能し、無限ループが解消されました。

### `src/math/all_test.go`の変更

テストファイル`src/math/all_test.go`には、このバグを再現し、修正を検証するための新しいテストケースが追加されました。

```go
+	Float64frombits(2), // subnormal; see https://golang.org/issue/13013
```
この行は、`vfsqrtSC`というテストスライスに`Float64frombits(2)`という値を追加しています。`Float64frombits(2)`は、ビットパターンが`2`である`float64`値を生成します。これは非常に小さい非正規化数であり、元のバグをトリガーする入力として機能します。このテストケースの追加により、将来的に同様の回帰バグが発生しないことを保証できるようになりました。

また、`sqrtSC`スライスにも対応する期待値が追加されています。
```go
+	3.1434555694052576e-162,
```
これは、`Float64frombits(2)`の平方根の正確な値であり、修正後の`Sqrt`関数がこの非正規化数に対して正しい結果を返すことを検証します。

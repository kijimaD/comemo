# [インデックス 20590] ファイルの概要

このコミットは、Goランタイムにおける `runtime.Goexit()` 関数と `defer` ステートメントの間の相互作用に関するバグを修正するものです。具体的には、`Goexit` が呼び出された際に `defer` 関数が二重に実行される可能性があった問題を解決しています。この修正により、`defer` が既に実行を開始しているかどうかをチェックするメカニズムが導入され、重複実行が防止されます。

## 元コミット内容

`runtime: Fix interaction between Goexit and defers`

`defer` 関数を実行する際、既に実行が開始されているかどうかを確認し、二重に実行されないようにする必要がある。

Issue #8774 を修正。

## 変更の背景

このコミットは、Goランタイムにおける `runtime.Goexit()` と `defer` ステートメントの間の予期せぬ相互作用によって引き起こされるバグを修正するために導入されました。以前のランタイムでは、`Goexit` が呼び出された際に、特定の条件下で `defer` 関数が複数回実行されてしまう可能性がありました。これは、`defer` の実行状態を適切に追跡していなかったためと考えられます。

特に、Issue #8774 で報告された問題は、`panic` の処理中に `runtime.Goexit()` が呼び出された場合に、`defer` が無限ループに陥る、または二重に実行されるというものでした。このような挙動は、プログラムの予期せぬ終了やリソースの重複解放など、深刻な問題を引き起こす可能性があります。このコミットは、この不安定な挙動を解消し、`Goexit` と `defer` の相互作用をより堅牢にするために行われました。

## 前提知識の解説

### `defer` ステートメント

Go言語の `defer` ステートメントは、関数がリターンする直前（またはパニックが発生して関数が終了する直前）に、指定された関数呼び出しを延期して実行させるためのものです。`defer` された関数は、LIFO (Last-In, First-Out) の順序で実行されます。これは、リソースの解放（ファイルのクローズ、ロックの解除など）やエラーハンドリングなど、クリーンアップ処理を確実に行うために非常に有用です。

例:
```go
func readFile(filename string) {
    f, err := os.Open(filename)
    if err != nil {
        log.Fatal(err)
    }
    defer f.Close() // 関数が終了する際にf.Close()が呼び出されることを保証
    // ファイルの読み込み処理
}
```

### `runtime.Goexit()`

`runtime.Goexit()` は、現在のゴルーチンを直ちに終了させるためのGoランタイム関数です。この関数が呼び出されると、現在のゴルーチンの残りの処理はスキップされ、`defer` された関数がすべて実行された後、ゴルーチンは終了します。`Goexit` はパニックとは異なり、呼び出しスタックをアンワインドしますが、エラーを伝播させません。

重要な注意点として、`main` ゴルーチンで `runtime.Goexit()` が呼び出された場合、他のすべての非デーモンゴルーチンが終了すると、プログラム全体がデッドロックとして終了します。これは、`main` ゴルーチンが終了しても、他のゴルーチンが実行中であればプログラムは継続するため、`main` ゴルーチンが `Goexit` で終了した後に他のゴルーチンが存在しない場合、Goランタイムは「デッドロック」と判断してプログラムを終了させるためです。

### パニックとリカバリ (`panic` と `recover`)

Go言語には、プログラムの異常終了を扱うための `panic` と `recover` というメカニズムがあります。
*   **`panic`**: 実行時エラーやプログラマが意図的に発生させる例外的な状況を示すために使用されます。`panic` が発生すると、現在の関数の実行は直ちに停止し、`defer` された関数がLIFO順に実行されながら、呼び出し元の関数へとスタックを遡っていきます。
*   **`recover`**: `defer` された関数の中でしか呼び出すことができません。`recover` が呼び出されると、現在のゴルーチンで発生している `panic` を捕捉し、そのパニックの値を返します。`recover` がパニックを捕捉すると、パニックの伝播は停止し、プログラムの実行は `recover` を呼び出した `defer` 関数の次のステートメントから再開されます。これにより、プログラムのクラッシュを防ぎ、エラーハンドリングを行うことができます。

`Goexit` は `panic` とは異なり、`recover` で捕捉することはできません。`Goexit` はあくまでゴルーチンの終了を目的としており、エラー伝播のメカニズムとは異なります。

## 技術的詳細

このコミットが修正しようとしている問題は、`runtime.Goexit()` が呼び出された際に、`defer` 関数が二重に実行される可能性があった点です。Goランタイムは、`Goexit` が呼び出されると、現在のゴルーチンに登録されているすべての `defer` 関数を順次実行します。しかし、以前の実装では、`defer` 関数が実行中であるという状態を適切に管理していなかったため、同じ `defer` 関数が複数回実行される可能性がありました。

特に、`defer` 関数内で `panic` が発生し、それが `recover` されずにスタックを遡る途中で `Goexit` が呼び出されるような複雑なシナリオで、この問題が顕在化しました。`panic` 処理と `Goexit` 処理の両方が `defer` リストを走査し、実行しようとするため、`defer` の状態管理が不十分だと、既に実行を開始した `defer` が再度実行対象として認識されてしまうことがありました。

この修正の目的は、`defer` が実行を開始したことを示すフラグ (`started` フィールド) を導入し、`Goexit` が `defer` リストを処理する際に、既に `started` フラグが設定されている `defer` はスキップすることで、二重実行を防ぐことです。これにより、`Goexit` と `defer`、そして `panic`/`recover` の複雑な相互作用下でも、`defer` の実行が一度だけ保証されるようになります。

*   `if gp._defer != d` というチェックが追加され、`defer` エントリが不正な状態になっていないかを確認しています。

### `src/runtime/crash_test.go` の変更点

`Goexit` と `panic` の相互作用をテストするための新しいテストケースが多数追加されました。
*   `TestGoexitInPanic`: `panic` 中に `Goexit` が呼び出された場合の挙動をテストします。Issue #8774 の根本原因を再現するシナリオです。
*   `TestPanicAfterGoexit`: `Goexit` の後に捕捉されない `panic` が発生した場合の挙動をテストします。
*   `TestRecoveredPanicAfterGoexit`: `Goexit` の後に `panic` が発生し、それが `recover` された場合の挙動をテストします。
*   `TestRecoverBeforePanicAfterGoexit`: `recover` する `defer` と `panic` する `defer` が両方存在し、その後に `Goexit` が呼び出された場合の複雑なシナリオをテストします。

これらのテストは、`Goexit` と `defer`、`panic`、`recover` の様々な組み合わせにおいて、`defer` が正しく一度だけ実行され、プログラムが予期せぬデッドロックやクラッシュを起こさないことを検証します。

## コアとなるコードの解説

`src/runtime/panic.go` の `Goexit()` 関数内の変更は、`defer` 関数の実行ロジックをより堅牢にするためのものです。

以前の `Goexit` の `defer` 処理ループは、単に `gp._defer` が `nil` になるまで `defer` リストを線形に走査し、各 `defer` を実行していました。しかし、`panic` 処理も同様に `defer` リストを走査するため、`panic` と `Goexit` が同時に、または連続して `defer` リストを処理しようとすると、同じ `defer` が複数回実行される可能性がありました。

新しいコードでは、以下の点が改善されています。

1.  **`for {}` ループと `d == nil` チェック**:
    `for gp._defer != nil` から `for {}` に変更され、ループの先頭で `d := gp._defer` を取得し、`if d == nil { break }` でループを抜けるようになりました。これは、`gopanic` 関数と同様のパターンであり、`defer` リストの処理をより明示的に制御します。

2.  **`d.started` フラグの導入とチェック**:
    最も重要な変更は、`_defer` 構造体に `started` というブール型のフィールドが追加され、そのフィールドを利用して `defer` の実行状態を追跡するようになったことです。
    ```go
    if d.started {
        if d._panic != nil {
            d._panic.aborted = true
        }
        gp._defer = d.link
        freedefer(d)
        continue
    }
    ```
    このブロックは、現在の `defer` (`d`) が既に `started` フラグが `true` になっている場合（つまり、既に実行を開始している場合）に実行されます。この場合、その `defer` はスキップされ、リストから削除 (`gp._defer = d.link; freedefer(d)`) されます。
    `if d._panic != nil { d._panic.aborted = true }` の部分は、もしこの `defer` がパニックに関連付けられていた場合、そのパニックが `Goexit` によって中断された（`aborted`）ことをマークします。これは、パニック処理と `Goexit` 処理の間の複雑な相互作用を適切に管理するために重要です。

3.  **`d.started = true` の設定**:
    `reflectcall` で `defer` 関数が実際に呼び出される直前に `d.started = true` が設定されます。これにより、`defer` が実行を開始したことがマークされ、将来の重複実行が防止されます。

4.  **`if gp._defer != d` のチェック**:
    `reflectcall` の後に追加されたこのチェックは、`defer` 関数の実行中に `gp._defer` ポインタが予期せず変更されていないかを確認するためのものです。もし変更されていれば、それはランタイムの内部状態の破損を示唆するため、`gothrow("bad defer entry in Goexit")` で致命的なエラーを発生させます。これは、ランタイムの堅牢性を高めるための防御的なプログラミングです。

これらの変更により、`Goexit` が `defer` リストを処理する際に、各 `defer` が一度だけ実行されることが保証され、Issue #8774 で報告されたような無限ループや二重実行の問題が解決されました。

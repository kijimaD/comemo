# [インデックス 27950] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるオブジェクト割り当ての最適化に関するものです。具体的には、`src/runtime/malloc.go`と`src/runtime/mgcmark.go`の2つのファイルが変更されています。これらの変更は、GCのマークフェーズ中に新しく割り当てられるオブジェクトを「黒」（allocate-black）としてマークするプロセスの効率を向上させることを目的としています。

## コミット

このコミットは、Goランタイムの「allocate-black」メカニズムを簡素化し、最適化することを目的としています。主な変更点は、オブジェクトの割り当て時にシステムスタックへの切り替えをなくし、`bytesMarked`統計の更新方法をグローバルなアトミック操作から、P（プロセッサ）ごとのローカルな更新へと変更したことです。これにより、GCのパフォーマンスが向上し、レイテンシが削減される可能性があります。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するように設計されており、特にGo 1.5以降では、GCのストップ・ザ・ワールド（STW）時間を最小限に抑えるために、並行GCが導入されました。この並行GCの重要な側面の一つが「三色マーキング（Tri-color marking）」アルゴリズムです。

三色マーキングでは、オブジェクトは白、灰色、黒のいずれかの色でマークされます。
*   **白**: GCによってまだ発見されていないオブジェクト。最終的に回収される可能性がある。
*   **灰色**: GCによって発見されたが、そのポインタがまだスキャンされていないオブジェクト。
*   **黒**: GCによって発見され、そのポインタもすべてスキャンされたオブジェクト。

GCのマークフェーズ中に新しいオブジェクトが割り当てられると、そのオブジェクトは「黒」として割り当てられることがあります。これは「allocate-black」と呼ばれ、新しいオブジェクトがGCによって再スキャンされる必要がないようにすることで、GCの作業量を減らすための最適化です。もし新しいオブジェクトが白として割り当てられた場合、GCはそれを発見してスキャンし、黒にマークする追加の作業が必要になります。allocate-blackは、このオーバーヘッドを避けるための戦略です。

このコミット以前のallocate-blackの実装には、以下の2つの非効率性がありました。

1.  **システムスタックへの切り替え**: オブジェクトを黒として割り当てる際に、`systemstack`関数を介してシステムスタックに切り替えていました。これは、コンテキストスイッチに似た操作であり、CPUサイクルを消費し、オーバーヘッドが発生します。コミットメッセージでは「probably a historical accident」（おそらく歴史的な事故）と述べられており、この切り替えが必ずしも必要ではなかった可能性が示唆されています。
2.  **グローバルな`bytesMarked`統計のアトミック更新**: GCがマークしたバイト数を追跡するために、グローバルな`work.bytesMarked`変数を`atomic.Xadd64`（アトミック加算）で更新していました。アトミック操作は、複数のゴルーチンが同時に同じ変数にアクセスする際のデータ競合を防ぐために必要ですが、これは通常の非アトミック操作よりもコストが高く、特に競合が多い場合にはパフォーマンスのボトルネックとなる可能性があります。

コミットメッセージには「Since we're about to depend on this much more」（これからこれにもっと依存するようになるため）とあり、allocate-blackのメカニズムが将来的にさらに重要になることが示唆されています。そのため、これらの非効率性を解消し、allocate-blackのパフォーマンスを向上させることが、この変更の背景にあります。これは、GoランタイムのGCパスにおけるホットスポットを特定し、より効率的な実装に置き換えることで、全体的なGCのレイテンシとスループットを改善することを目的としています。

## 前提知識の解説

### GoランタイムのM-P-Gモデル

Goランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）という3つの主要な抽象化を使用して並行性を管理します。
*   **G (Goroutine)**: Goにおける軽量な実行単位。ユーザーが記述する並行処理のコード。
*   **P (Processor)**: ゴルーチンを実行するための論理的なコンテキスト。MとGの間の仲介役。Pはローカルな実行キューを持ち、MがPにアタッチされてゴルーチンを実行します。Pの数は`GOMAXPROCS`によって制御されます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッド。Pにアタッチされ、Pのキューからゴルーチンを取り出して実行します。

このコミットでは、Pごとの統計情報（`per-P bytes marked stat`）が言及されており、各PがGC作業を含む特定のタスクに対してローカルな状態を持つことができるというPの概念が重要になります。

### Goのガベージコレクション（GC）と三色マーキング

GoのGCは、主に「並行三色マーク・アンド・スイープ」アルゴリズムを採用しています。
*   **マークフェーズ**: ライブオブジェクト（到達可能なオブジェクト）を識別します。
    *   **三色抽象化**:
        *   **白**: まだGCによって到達可能と判断されていないオブジェクト。初期状態のすべてのオブジェクトは白。
        *   **灰色**: GCによって到達可能と判断されたが、そのオブジェクトが参照する他のオブジェクト（子）がまだスキャンされていないオブジェクト。
        *   **黒**: GCによって到達可能と判断され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みのオブジェクト。
    *   **Allocate-black**: GCのマークフェーズ中に新しく割り当てられたオブジェクトを直接黒としてマークする最適化戦略。これにより、新しく割り当てられたオブジェクトをGCが再度スキャンする必要がなくなり、GCのオーバーヘッドが削減されます。この戦略は、GCの三色不変条件（黒オブジェクトが白オブジェクトを指さない）を維持するために、ライトバリアと組み合わせて使用されます。

### `systemstack`と通常のスタック

*   **通常のスタック**: ゴルーチンがユーザーコードを実行する際に使用するスタック。動的にサイズが変更され、必要に応じて拡張・縮小されます。
*   **システムスタック (g0 stack)**: ランタイム内部の重要な処理（スケジューリング、GCの一部、シグナルハンドリング、スタックの成長処理など）を実行するために使用される特別なスタック。各OSスレッド（M）に紐付けられています。システムスタックへの切り替えは、通常のスタックでの実行とは異なるコンテキストで行われ、コンテキストの保存と復元、スタックポインタの調整など、一定のオーバーヘッドを伴います。これは、特定のランタイム処理がユーザーゴルーチンのスタックを汚染したり、スタックの拡張・縮小ロジックと競合したりするのを防ぐために使用されることがあります。システムスタックで実行されるコードは、通常、プリエンプションされません。

### `atomic.Xadd64`と`gcWork`、`bytesMarked`

*   **`atomic.Xadd64`**: `sync/atomic`パッケージで提供されるアトミック操作の一つで、64ビット整数に値をアトミックに加算します。複数のゴルーチンが同時に同じ変数にアクセスしても、データ競合が発生しないことを保証します。しかし、アトミック操作は通常の加算よりもコストが高く、特に競合が多い場合にはパフォーマンスのボトルネックになります。
*   **`gcWork`**: 各P（論理プロセッサ）に紐付けられたGC作業のコンテキスト。GCのマーキングフェーズにおける作業プールとして機能し、ライブオブジェクトを識別するタスクを管理するためのプロデューサー・コンシューマーモデルを実装しています。
*   **`bytesMarked`**: GCのマークフェーズ中に「黒」とマークされたオブジェクトの合計バイト数を追跡するための統計情報。これには、明示的にスキャンされて黒にされたオブジェクト、ポインタを含まないためすぐに黒にされる「noscan」オブジェクト、そしてGCサイクル中に黒として割り当てられたオブジェクトが含まれます。

### `//go:nosplit`ディレクティブ

`//go:nosplit`はGoコンパイラに対するディレクティブで、その関数がスタックを分割（拡張）しないことを保証します。これは、スタックの拡張が必要な場合に発生する可能性のあるプリエンプション（横取り）を防ぐために使用されます。`//go:nosplit`が指定された関数は、スタックオーバーフローチェックを省略し、スタックの成長を試みません。そのため、このディレクティブを使用する関数は非常に小さく、メモリ割り当て、パニック、ブロック、またはスタック成長を必要とするコードを呼び出すべきではありません。GCのような時間制約のあるランタイム処理では、プリエンプションを避けることで、より予測可能な実行時間と低レイテンシを実現できます。誤用するとスタックオーバーフローやメモリ破損を引き起こす可能性があるため、Goランタイムの低レベルコードでのみ使用が推奨されます。

## 技術的詳細

このコミットは、allocate-blackのプロセスにおける2つの主要な最適化を導入しています。

1.  **`systemstack`の削除**:
    以前は、`mallocgc`関数内で`gcphase == _GCmarktermination || gcBlackenPromptly`の条件が真の場合（つまり、GCのマークフェーズ中またはallocate-blackが有効な場合）、`gcmarknewobject_m`関数を`systemstack`内で呼び出していました。
    ```go
    // 変更前 (src/runtime/malloc.go)
    if gcphase == _GCmarktermination || gcBlackenPromptly {
        systemstack(func() {
            gcmarknewobject_m(uintptr(x), size, scanSize)
        })
    }
    ```
    この変更により、`systemstack`の呼び出しが削除され、`gcmarknewobject`（関数名も変更）が通常のスタックで直接呼び出されるようになりました。
    ```go
    // 変更後 (src/runtime/malloc.go)
    if gcphase == _GCmarktermination || gcBlackenPromptly {
        gcmarknewobject(uintptr(x), size, scanSize)
    }
    ```
    `systemstack`への切り替えは、コンテキストの保存と復元、スタックポインタの調整など、一定のオーバーヘッドを伴います。このオーバーヘッドを排除することで、allocate-blackのパスが高速化されます。この変更が可能になったのは、`gcmarknewobject`関数自体が`//go:nosplit`ディレクティブを持つようになったため、スタックの拡張によるプリエンプションの懸念がなくなったためと考えられます。

2.  **`bytesMarked`統計のPごとの更新**:
    以前は、`gcmarknewobject_m`関数内で、グローバルな`work.bytesMarked`変数を`atomic.Xadd64`でアトミックに更新していました。
    ```go
    // 変更前 (src/runtime/mgcmark.go)
    atomic.Xadd64(&work.bytesMarked, int64(size))
    ```
    この変更により、`atomic.Xadd64`の呼び出しが削除され、代わりに現在のP（プロセッサ）に紐付けられた`gcw`（GC Work）構造体の`bytesMarked`フィールドを直接更新するようになりました。
    ```go
    // 変更後 (src/runtime/mgcmark.go)
    gcw := &getg().m.p.ptr().gcw
    gcw.bytesMarked += uint64(size)
    ```
    各Pは自身の`gcw`構造体を持つため、この更新はローカルな操作となり、アトミック操作のようなグローバルなロックやキャッシュコヒーレンシのオーバーヘッドがなくなります。Pごとの`bytesMarked`は、後で（おそらくGCの終了時や特定の閾値に達したときに）グローバルな`work.bytesMarked`にまとめて加算される（lazily folded）ことで、グローバルな統計の正確性を保ちつつ、更新頻度を減らし、競合を緩和します。これにより、特に多数のゴルーチンが同時にオブジェクトを割り当てるような高負荷な状況でのGCのパフォーマンスが向上します。

3.  **`gcmarknewobject`関数の変更と`//go:nosplit`**:
    `gcmarknewobject_m`関数は`gcmarknewobject`にリネームされ、`//go:nosplit`ディレクティブが追加されました。
    ```go
    // 変更前 (src/runtime/mgcmark.go)
    //go:nowritebarrier
    func gcmarknewobject_m(obj, size, scanSize uintptr) {
    ```
    ```go
    // 変更後 (src/runtime/mgcmark.go)
    // This is nosplit so it can manipulate a gcWork without preemption.
    //go:nowritebarrier
    //go:nosplit
    func gcmarknewobject(obj, size, scanSize uintptr) {
    ```
    `//go:nosplit`ディレクティブは、この関数が実行中にスタックを拡張しないことをコンパイラに指示します。これにより、この関数が実行中にプリエンプションされる可能性が低くなり、`gcw`のようなGC関連の重要なデータ構造を安全かつ効率的に操作できるようになります。これは、`systemstack`を削除できた理由の一つでもあります。

これらの変更は、GoのGCがより効率的かつ低レイテンシで動作するように、ランタイムの内部パスを細かく最適化するものです。

## コアとなるコードの解説

### `src/runtime/malloc.go`の変更

*   **変更前**:
    `mallocgc`関数内で、GCのマークフェーズ中に新しいオブジェクトを割り当てる際、`gcmarknewobject_m`関数を`systemstack`クロージャ内で呼び出していました。これは、通常のゴルーチンのスタックからシステムスタックへ切り替えることを意味し、コンテキストスイッチのオーバーヘッドが発生していました。

*   **変更後**:
    `systemstack`の呼び出しが削除され、`gcmarknewobject`関数が直接呼び出されるようになりました。これにより、スタック切り替えのオーバーヘッドがなくなり、オブジェクト割り当てのパスが高速化されます。この変更は、`gcmarknewobject`関数自体が`//go:nosplit`としてマークされたことで、スタック拡張によるプリエンプションの懸念が解消されたために可能になりました。

### `src/runtime/mgcmark.go`の変更

*   **関数名の変更**:
    `gcmarknewobject_m`から`gcmarknewobject`にリネームされました。`_m`サフィックスは通常、M（OSスレッド）コンテキストで実行される関数を示す慣例であるため、`systemstack`が削除されたことでその必要がなくなったことを示唆しています。

*   **`//go:nosplit`ディレクティブの追加**:
    `gcmarknewobject`関数に`//go:nosplit`ディレクティブが追加されました。これにより、コンパイラはこの関数が実行中にスタックを拡張しないことを保証します。スタック拡張はプリエンプションを引き起こす可能性があるため、このディレクティブは、GC作業（`gcWork`の操作など）が中断されずに実行されることを保証し、GCのレイテンシを低減します。コメント`// This is nosplit so it can manipulate a gcWork without preemption.`が追加され、その理由が明確にされています。

*   **`bytesMarked`統計の更新方法の変更**:
    *   **変更前**:
        グローバルな`work.bytesMarked`変数を`atomic.Xadd64`でアトミックに更新していました。これは、複数のゴルーチンからの同時アクセスに対して安全ですが、アトミック操作のコストは通常の加算よりも高く、競合が多い場合にはパフォーマンスのボトルネックになります。

    *   **変更後**:
        現在のゴルーチン（`getg()`）が実行されているM（OSスレッド）に紐付けられたP（論理プロセッサ）の`gcw`（GC Work）構造体を取得し、そのローカルな`bytesMarked`フィールドに直接加算するようになりました。この操作はPローカルであるため、アトミック操作は不要であり、より高速に実行できます。Pごとの`bytesMarked`は、後でランタイムによってグローバルな`work.bytesMarked`に集約されます。これにより、グローバルなアトミック操作の頻度が減り、GCのパフォーマンスが向上します。

これらの変更は、GoのGCがより効率的かつ低レイテンシで動作するように、ランタイムの内部パスを細かく最適化するものです。

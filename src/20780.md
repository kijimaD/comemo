## 変更の背景

このコミットの主な背景は、Goランタイムにおける重要なバグ修正（CL 145890044: "runtime: fix stack overflow during panic"）に対して、適切なテストケースが欠如していたことです。CL 145890044は、パニック発生時にスタックオーバーフローが発生する可能性のある問題を修正しました。特に、パニック自体がスタックオーバーフローによって引き起こされた場合に、ランタイムがクラッシュする連鎖的な障害を防ぐためのものでした。

このコミットは、その修正が意図通りに機能し、特にWindows環境でCGOを介してスレッドが作成されるようなシナリオで、ハンドルリークが発生しないことを検証するためのテストを追加します。コミットメッセージの「Update #8517」は、このテストがGoの内部的な問題追跡システムにおける特定の課題（おそらくWindowsのハンドルリークに関連するもの）に対応していることを示唆しています。

Goランタイムは、効率的なメモリ管理とリソース管理を目指しており、スタックの動的な伸縮やパニック処理は、その堅牢性を保証する上で非常に重要です。このテストの追加は、Goランタイムの安定性と信頼性を高めるための継続的な取り組みの一環です。

## 前提知識の解説

### 1. Goのパニックとリカバリ

Go言語には、プログラムの異常終了を処理するための`panic`と`recover`というメカニズムがあります。`panic`は、回復不可能なエラーが発生した際にプログラムの実行を停止させ、現在のゴルーチンをアンワインド（スタックを巻き戻す）します。通常、`defer`関数内で`recover`を呼び出すことで、パニックを捕捉し、プログラムのクラッシュを防ぎ、正常な実行を再開させることができます。しかし、パニック処理自体がスタックオーバーフローなどの問題を引き起こす場合、このメカニズムが機能せず、プログラムが予期せず終了する可能性があります。

### 2. CGO

CGOは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。これにより、既存のCライブラリを利用したり、Goでは実現が難しい低レベルの操作を行ったりすることが可能になります。CGOを使用すると、GoのランタイムとCのランタイムが相互作用するため、メモリ管理やスレッド管理において複雑さが増すことがあります。特に、CコードがOSレベルのスレッドやリソース（Windowsのハンドルなど）を直接操作する場合、Goのガベージコレクタやスケジューラがそれらのリソースのライフサイクルを完全に管理できないため、リークが発生するリスクがあります。

### 3. Windowsハンドル

Windowsオペレーティングシステムでは、ファイル、レジストリキー、イベント、ミューテックス、スレッド、プロセスなどのシステムリソースは「ハンドル」と呼ばれる抽象的な識別子を介してアクセスされます。プログラムがこれらのリソースを使用する場合、対応するハンドルを取得し、使用後は明示的に解放（`CloseHandle`など）する必要があります。ハンドルが適切に解放されないと、システムリソースが枯渇し、パフォーマンスの低下やアプリケーションの不安定化につながる「ハンドルリーク」が発生します。

### 4. スタックオーバーフロー

スタックオーバーフローは、プログラムが関数呼び出しやローカル変数のために必要なスタックメモリを使い果たしたときに発生するエラーです。Goのゴルーチンは動的にスタックサイズを調整しますが、無限再帰や非常に深い関数呼び出しチェーンなどによって、スタックが割り当てられた上限を超えるとスタックオーバーフローが発生します。

## 技術的詳細

このコミットで追加されたテスト`Test8517`は、Windows環境におけるCGOとGoランタイムの相互作用、特にパニック処理中のリソース管理の堅牢性を検証することを目的としています。

テストの核心は、CGOを介してWindows APIの`CreateThread`関数を呼び出し、新しいスレッドを作成する点にあります。このスレッドは、Go側で定義されたコールバック関数`testHandleLeaksCallback`を繰り返し呼び出します。このコールバック関数は、グローバル変数`issue8517counter`をインクリメントするだけのシンプルなものです。

テストのロジックは以下の通りです。

1.  **初期ハンドル数の取得**: `processHandleCount`関数を呼び出し、テスト開始時点での現在のプロセスのハンドル数を取得します。これは`GetProcessHandleCount` Windows APIをCGO経由で呼び出すことで実現されます。
2.  **CGO関数の呼び出し**: `C.testHandleLeaks()`を呼び出します。このC関数は、新しいスレッドを作成し、そのスレッド内で`testHandleLeaksCallback`を100回呼び出します。スレッドの終了を待ってから、ハンドルを閉じます。
3.  **終了後のハンドル数の取得**: 再び`processHandleCount`関数を呼び出し、CGO呼び出し後のプロセスのハンドル数を取得します。
4.  **ハンドルリークの検証**: 取得したハンドル数を比較し、`c1 + issue8517counter <= c2`という条件をチェックします。
    *   `c1`: テスト開始前のハンドル数。
    *   `issue8517counter`: CGOスレッド内でGoのコールバックが呼び出された回数（期待されるは100）。
    *   `c2`: テスト終了後のハンドル数。

この条件は、`issue8517counter`がインクリメントされるたびに何らかのハンドルがリークしていると仮定した場合、`c2`が`c1 + issue8517counter`よりも大幅に大きくなることを期待しています。しかし、このテストの目的はリークが**ない**ことを確認することなので、`c1 + issue8517counter <= c2`という条件は、リークが許容範囲内であるか、または全くないことを検証しています。もし`c2`が`c1 + issue8517counter`よりも著しく大きければ、ハンドルリークが発生していると判断し、テストは失敗します。

このテストは、CL 145890044で修正された「パニック時のスタックオーバーフロー」が、CGOを介したスレッド作成やコールバック呼び出しといった複雑なシナリオにおいても、Windowsのハンドルリークを引き起こさないことを保証するためのものです。

## コアとなるコードの解説

### `misc/cgo/test/issue8517_windows.c`

```c
#include "windows.h"

extern void testHandleLeaksCallback(); // Go側の関数をCから呼び出すための宣言

DWORD WINAPI testHandleLeaksFunc(LPVOID lpThreadParameter)
{
	int i;
	for(i = 0; i < 100; i++) {
		testHandleLeaksCallback(); // Go側のコールバックを100回呼び出す
	}
	return 0;
}

void testHandleLeaks()
{
	HANDLE h;
	// 新しいスレッドを作成
	h = CreateThread(NULL, 0, &testHandleLeaksFunc, 0, 0, NULL);
	// スレッドの終了を待機
	WaitForSingleObject(h, INFINITE);
	// スレッドハンドルを閉じる（解放する）
	CloseHandle(h);
}
```
このCコードは、Goから`testHandleLeaks`が呼び出されると、Windows APIの`CreateThread`を使って新しいOSスレッドを生成します。このスレッドは`testHandleLeaksFunc`を実行し、その中でGo側の`testHandleLeaksCallback`関数を100回呼び出します。スレッドが終了した後、`WaitForSingleObject`でその終了を待ち、`CloseHandle`でスレッドハンドルを明示的に解放します。これにより、CGOを介して作成されたスレッドが適切にクリーンアップされることを保証します。

### `misc/cgo/test/issue8517_windows.go`

```go
package cgotest

//void testHandleLeaks(); // C言語のtestHandleLeaks関数をGoから呼び出すためのCGOディレクティブ
import "C"

import (
	"syscall"
	"testing"
	"unsafe"
)

var issue8517counter int // CGOスレッドからGoコールバックが呼び出された回数をカウント

var (
	kernel32              = syscall.MustLoadDLL("kernel32.dll")
	getProcessHandleCount = kernel32.MustFindProc("GetProcessHandleCount")
)

// processHandleCount は現在のプロセスのハンドル数を取得する
func processHandleCount(t *testing.T) int {
	const current_process = ^uintptr(0) // 現在のプロセスを表す擬似ハンドル
	var c uint32
	// GetProcessHandleCount Windows APIを呼び出す
	r, _, err := getProcessHandleCount.Call(current_process, uintptr(unsafe.Pointer(&c)))
	if r == 0 {
		t.Fatal(err) // エラーが発生したらテストを失敗させる
	}
	return int(c)
}

// test8517 はハンドルリークをテストするメイン関数
func test8517(t *testing.T) {
	c1 := processHandleCount(t) // テスト開始前のハンドル数を取得
	C.testHandleLeaks()         // CGO関数を呼び出し、Cスレッド内でGoコールバックを呼び出す
	c2 := processHandleCount(t) // CGO呼び出し後のハンドル数を取得
	// ハンドルリークがないことを検証
	// issue8517counterはCスレッドからGoコールバックが呼び出された回数（期待値は100）
	// c1 + issue8517counter <= c2 は、リークが許容範囲内であることを意味する
	if c1+issue8517counter <= c2 {
		t.Fatalf("too many handles leaked: issue8517counter=%v c1=%v c2=%v", issue8517counter, c1, c2)
	}
}

//export testHandleLeaksCallback // CGOから呼び出されるGoのコールバック関数
func testHandleLeaksCallback() {
	issue8517counter++ // カウンターをインクリメント
}
```
このGoコードは、CGOを介してC言語の`testHandleLeaks`関数を呼び出し、その前後でプロセスのハンドル数を`GetProcessHandleCount` APIを使って測定します。`testHandleLeaksCallback`は、Cスレッドから呼び出されるGo関数であり、`issue8517counter`をインクリメントします。テストの最終的なアサーションは、CGO呼び出し後にハンドル数が過度に増加していないことを確認することで、ハンドルリークがないことを検証します。

このテストは、Goランタイムがパニック処理中にCGOを介して作成されたリソース（特にWindowsハンドル）を適切に管理し、リークを防ぐ能力を保証するために不可欠です。

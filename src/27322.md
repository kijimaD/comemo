# [インデックス 27322] ファイルの概要

このコミットは、Go言語のランタイムテストスイートの一部である `test/nosplit.go` ファイルに対する変更です。`nosplit.go` は、Goコンパイラが特定の関数呼び出しに対してスタック分割（stack split）を行わないようにする `//go:nosplit` プラグマが正しく機能するかどうかを検証するためのテストを含んでいます。

## コミット

このコミットは、`s390x` アーキテクチャにおいて `nosplit` テストが正しく動作するように修正を加えるものです。具体的には、`s390x` 用のレジスタ定義を追加することで、テストの失敗を解消しています。

## 変更の背景

Go言語のランタイムには、スタックの成長（stack growth）を伴わない、非常に短いクリティカルな関数が存在します。これらの関数は、スタックの成長処理自体が行われている最中や、シグナルハンドラ内など、スタックを安全に拡張できないコンテキストで呼び出される可能性があるため、スタック分割を禁止する `//go:nosplit` プラグマが付けられます。

`test/nosplit.go` は、この `//go:nosplit` プラグマがコンパイラによって正しく解釈され、実際にスタック分割が発生しないことを検証するためのテストです。このテストは、アセンブリコードを生成し、特定のレジスタがどのように使用されているかを確認することで、`nosplit` の制約が守られているかを検証します。

`s390x` アーキテクチャ（IBM System z メインフレーム）では、他のアーキテクチャ（例: `amd64`）とは異なるレジスタセットと呼び出し規約を使用します。このコミット以前は、`test/nosplit.go` が `s390x` アーキテクチャ固有のレジスタ定義を欠いていたため、テストが正しく実行されず、失敗していました。この変更は、`s390x` 環境でのテストの信頼性を向上させるために導入されました。

## 前提知識の解説

### Goのnosplit関数

Go言語では、関数が呼び出される際に、現在のスタックフレームが十分なサイズを持っているかを確認します。もしスタックが不足している場合、ランタイムはスタックを拡張する処理（スタック分割）を行います。しかし、一部のランタイム関数、特にスタックの管理自体に関わるような低レベルの関数では、スタック分割を許可するとデッドロックや無限ループなどの問題を引き起こす可能性があります。

このような関数には、Goコンパイラに対する指示として `//go:nosplit` プラグマが付与されます。このプラグマが付与された関数は、コンパイラによってスタック分割コードが挿入されず、常に現在のスタックフレーム内で実行されることが保証されます。これは、関数が非常に小さく、スタックをほとんど消費しない場合にのみ安全です。

### s390xアーキテクチャ

`s390x` は、IBMが開発したメインフレームコンピュータのアーキテクチャである System/390 および z/Architecture の64ビット版を指します。このアーキテクチャは、高い信頼性、可用性、保守性（RAS）を特徴とし、大規模なエンタープライズシステムで広く利用されています。

`s390x` の特徴として、以下の点が挙げられます。
*   **レジスタセット**: 汎用レジスタ（General Purpose Registers, GPRs）としてR0からR15までを持ちます。Goのコンテキストでは、特定のレジスタが関数引数や戻り値、あるいは一時的な計算に使用されます。
*   **ポインタサイズ**: 64ビットアーキテクチャであるため、ポインタのサイズは8バイトです。
*   **命令セット**: CISC（Complex Instruction Set Computer）型の命令セットを持ち、強力な単一命令で複雑な操作を実行できます。

Go言語は、`s390x` を含む複数のアーキテクチャをサポートしており、各アーキテクチャの特性に合わせてコンパイラやランタイムが調整されています。

### Goのテストフレームワークとアーキテクチャ固有のテスト

Go言語には、標準ライブラリとして `testing` パッケージが提供されており、ユニットテストやベンチマークテストを簡単に記述できます。テストファイルは通常 `_test.go` というサフィックスを持ち、`go test` コマンドで実行されます。

Goのビルドシステムは、特定のファイル名パターンに基づいて、特定のOSやアーキテクチャ向けのコードを条件付きでコンパイルする機能を持っています。例えば、`_amd64.go` というファイルは `amd64` アーキテクチャでのみコンパイルされ、`_linux.go` は Linux 環境でのみコンパイルされます。

`test/nosplit.go` のように、テストコード内で `runtime.GOARCH` を使用して現在のアーキテクチャを判別し、それに応じて異なるコードパスを実行することも一般的です。これにより、アーキテクチャ固有の挙動をテストしたり、特定のアーキテクチャに合わせたテストロジックを適用したりすることが可能になります。

## 技術的詳細

`test/nosplit.go` は、`nosplit` 関数がスタック分割を行わないことを検証するために、アセンブリコードを動的に生成し、そのアセンブリコードが期待通りの挙動をするかを確認します。このテストでは、特定のレジスタがスタックポインタのチェックに使用されることを想定しています。

`s390x` アーキテクチャでは、`amd64` とは異なるレジスタが使用されます。このコミット以前は、`test/nosplit.go` 内のアーキテクチャ判別ロジックに `s390x` のケースが欠けていました。そのため、`s390x` 環境でテストが実行されると、デフォルトの `amd64` 向けのレジスタ定義（`AX` レジスタ）が適用されてしまい、`s390x` の実際のレジスタ使用状況と一致せず、テストが失敗していました。

このコミットでは、`s390x` アーキテクチャの場合に、以下の定義を追加しています。
*   `ptrSize = 8`: `s390x` は64ビットアーキテクチャであるため、ポインタサイズは8バイト（64ビット）です。
*   `#define REGISTER R10`: `s390x` において、スタックポインタのチェックや関数呼び出し規約に関連して使用される可能性のある汎用レジスタ `R10` を `REGISTER` として定義しています。これにより、生成されるアセンブリコードが `s390x` の呼び出し規約とレジスタ使用法に適合するようになります。

この変更により、`s390x` 環境で `nosplit` テストが実行された際に、正しいレジスタが参照されるようになり、テストが期待通りにパスするようになりました。

## コアとなるコードの解説

変更箇所は、`test/nosplit.go` 内の `switch runtime.GOARCH` ステートメントの中にあります。この `switch` ステートメントは、現在の実行アーキテクチャに基づいて、テストで使用するアセンブリコードの定義を調整するために使用されます。

*   `case "s390x":`: この行は、現在の実行アーキテクチャが `s390x` である場合に実行されるコードブロックを定義しています。
*   `ptrSize = 8`: `s390x` は64ビットアーキテクチャであるため、ポインタのサイズは8バイトです。この変数は、アセンブリコードの生成において、メモリアドレスの計算などに使用されます。
*   `fmt.Fprintf(&buf, "#define REGISTER R10\\n")`: この行は、動的に生成されるアセンブリコードに `#define REGISTER R10` というプリプロセッサディレクティブを追加します。これにより、アセンブリコード内で `REGISTER` というシンボルが `R10` レジスタに置き換えられます。`R10` は `s390x` アーキテクチャにおける汎用レジスタの一つであり、このテストの文脈では、スタックポインタのチェックや関数呼び出しに関連する重要なレジスタとして使用されることを示唆しています。

この追加により、`s390x` 環境で `nosplit` テストが実行される際に、アーキテクチャ固有の正しいレジスタ定義が適用され、テストが期待通りに機能するようになります。

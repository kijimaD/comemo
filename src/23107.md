# [インデックス 23107] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における、保留中のGC作業のチェックに関するバグを修正するものです。具体的には、GCワーカーを起動すべきかどうかを判断する`findRunnable`関数が、GC作業バッファ（`currentwbuf`）に存在する作業を見落とす可能性があった問題を解決します。これにより、GCが効率的に進行せず、特定のテストケースで問題が発生していました。

## 元コミット内容

Goランタイムのガベージコレクションにおいて、`findRunnable`関数がGCワーカーを起動する際に、保留中のGC作業の有無を正しくチェックできていなかった問題を修正します。

`findRunnable`は、部分的なマークワーカーを実行するかどうかを検討する際、まず作業があるかどうかを確認します。作業がない場合、ワーカーを実行してもすぐに再スケジュールされるだけなので意味がありません。しかし、これまでの`findRunnable`は`work.full`と`work.partial`のみをチェックしていました。一方、`getfull`は`m.currentwbuf`からも作業を取得できます。このため、実際には作業があるにもかかわらず、`findRunnable`がワーカーを起動しない可能性がありました。

この問題は、`test/init1.go`テストで時折発生する失敗として現れていました。このテストは、ライトバリアを実行せずに大量のメモリ割り当てを行うという点で特殊です。これにより、`currentwbuf`内のポインタが`findRunnable`が参照できる`work.partial`/`full`リストに強制的に移動されることがありませんでした。

この変更は、`findRunnable`が`currentwbuf`もチェックするようにすることで、この問題を修正します。これにより、`findRunnable`は`trygetfull`の作業の有無に関する認識と一致するようになります。

## 変更の背景

Goのガベージコレクションは、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。このGCの効率性は、GCワーカーが適切なタイミングで起動され、割り当てられたGC作業を処理できるかどうかに大きく依存します。

このコミット以前のGoランタイムでは、GCワーカーをスケジュールする`findRunnable`関数に問題がありました。`findRunnable`は、GCのマークフェーズ中に、GCワーカーが処理すべき作業（スキャンすべきオブジェクトのポインタ）があるかどうかを判断していました。しかし、その判断基準が不完全でした。

具体的には、GC作業は主に`work.full`と`work.partial`というグローバルな作業キューに格納されますが、一部の作業は各プロセッサ（P）に紐づくローカルな作業バッファである`m.currentwbuf`にも一時的に保持されます。`findRunnable`は`work.full`と`work.partial`のみをチェックし、`m.currentwbuf`の存在を考慮していませんでした。

この見落としにより、`m.currentwbuf`にGCワーカーが処理すべきポインタが存在するにもかかわらず、`findRunnable`が「作業がない」と判断し、GCワーカーを起動しないという状況が発生していました。結果として、GC作業の処理が遅延し、GCの進行が滞る可能性がありました。

特に、`test/init1.go`というテストケースでこの問題が顕在化しました。このテストは、ライトバリア（GC中にポインタの書き換えを監視するメカニズム）がほとんど実行されないような、大量のメモリ割り当てを行う特殊なシナリオを含んでいます。通常、ライトバリアが発動すると、`currentwbuf`内のポインタは`work.partial`/`full`リストにフラッシュされます。しかし、このテストではライトバリアが少ないため、`currentwbuf`にポインタが滞留しやすく、`findRunnable`がそれらを認識できないという問題が表面化したのです。

このコミットは、このようなGCの非効率性やテストの失敗を解消するために導入されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション（GC）に関するいくつかの重要な概念を理解しておく必要があります。

1.  **GoのコンカレントGC（三色マーク＆スイープ）**:
    Goは、アプリケーションの実行と並行して動作するコンカレントな三色マーク＆スイープGCを採用しています。
    *   **三色アルゴリズム**: オブジェクトを以下の3つの色で分類します。
        *   **白 (White)**: まだGCによって到達可能と判断されていないオブジェクト。初期状態ではすべてのオブジェクトが白です。
        *   **灰 (Grey)**: 到達可能と判断されたが、そのオブジェクトが参照する他のオブジェクト（子）がまだスキャンされていないオブジェクト。
        *   **黒 (Black)**: 到達可能と判断され、かつそのオブジェクトが参照するすべての子オブジェクトもスキャン済みのオブジェクト。
    *   **マークフェーズ**: GCの主要なフェーズで、ルートオブジェクト（グローバル変数、アクティブなゴルーチンのスタック変数など）から到達可能なすべてのオブジェクトを特定し、マークします。このフェーズは、ほとんどの時間をアプリケーションと並行して実行されます。
    *   **スイープフェーズ**: マークされなかった（白のままの）オブジェクトを解放し、メモリを再利用するフェーズです。

2.  **ライトバリア (Write Barrier)**:
    コンカレントGCの正確性を保証するための重要なメカニズムです。GCがマークフェーズ中に動作している間も、ユーザーのゴルーチンはポインタを書き換えることでオブジェクトグラフを変更できます。ライトバリアは、このポインタの書き換え操作を監視し、三色不変条件（黒オブジェクトが白オブジェクトを直接参照しない）が破られないようにします。もし破られそうになった場合、ライトバリアは、新しく参照される白オブジェクトを灰色にマークしたり、スキャン対象として記録したりすることで、GCがそのオブジェクトを見落とさないようにします。Go 1.8以降では、スタック再スキャンを不要にする「ハイブリッドライトバリア」が導入されています。

3.  **GC作業バッファ (`wbuf`, `currentwbuf`, `work.full`, `work.partial`)**:
    マークフェーズ中にGCワーカーが処理すべきポインタ（スキャン対象のオブジェクト）を格納するためのバッファです。
    *   **`wbuf` (Work Buffer)**: GCワーカーがスキャンすべきオブジェクトのポインタを一時的に保持するバッファの総称です。
    *   **`currentwbuf`**: 各プロセッサ（P）またはGCワーカーが現在使用しているローカルな作業バッファです。ライトバリアによって新しくスキャン対象となったポインタは、まずこの`currentwbuf`に格納されます。
    *   **`work.full` / `work.partial`**: `currentwbuf`がいっぱいになったり、特定の条件が満たされたりすると、`currentwbuf`の内容はこれらのグローバルな作業キューにフラッシュされます。`work.full`はより大きなチャンク、`work.partial`はより小さなチャンクを扱うことが多いです。GCワーカーはこれらのグローバルキューからも作業を取得します。

4.  **`findRunnable`関数とGCワーカーのスケジューリング**:
    `runtime.findRunnable`関数は、Goスケジューラの中心的な部分であり、プロセッサ（M）上で実行可能なゴルーチンを見つけてスケジュールする役割を担います。GCマークフェーズ中、`findRunnable`はGCの進行を確実にするために重要な役割を果たします。
    *   `findRunnable`は、通常のユーザーゴルーチンに加えて、GCワーカーゴルーチン（`runtime.(*gcControllerState).findRunnableGCWorker`など）のスケジュールも優先的に行います。
    *   これらのGCワーカーゴルーチンは、`wbuf`（`currentwbuf`や`work.full`/`partial`を含む）をドレインし、灰色オブジェクトをスキャンして黒にマークする作業を行います。
    *   `findRunnable`がGCワーカーのスケジュールを統合することで、GoランタイムはGC作業とアプリケーション作業を交互に実行し、GCをほとんどコンカレントに保ち、「ストップ・ザ・ワールド」の一時停止を最小限に抑えます。

このコミットは、`findRunnable`がGC作業の有無を判断する際に、`currentwbuf`に存在する作業を見落としていたという、このGCメカニズムの連携における不整合を修正するものです。

## 技術的詳細

このコミットが修正する問題は、GoランタイムのGCスケジューリングにおける「作業の可視性」の不一致に起因します。

GoのGCマークフェーズでは、GCワーカーがスキャンすべきオブジェクトのポインタを処理します。これらのポインタは、ライトバリアによって捕捉され、まず各P（プロセッサ）に紐づくローカルな作業バッファである`_p_.m.ptr().currentwbuf`に一時的に蓄積されます。`currentwbuf`がいっぱいになるか、GCワーカーが明示的にフラッシュするまで、これらのポインタはグローバルな作業キューである`work.full`や`work.partial`には移動しません。

`findRunnable`関数は、GCワーカーをスケジュールする際に、GC作業が残っているかどうかを判断するために、`work.full == 0 && work.partial == 0`という条件をチェックしていました。この条件が真であれば、「作業がない」と判断し、GCワーカーを起動せずに他のゴルーチンをスケジュールしていました。

しかし、`getfull`（GCワーカーが実際に作業を取得する関数）は、`work.full`や`work.partial`だけでなく、`_p_.m.ptr().currentwbuf`からも作業を取得できる能力を持っていました。つまり、`work.full`と`work.partial`が空であっても、`currentwbuf`に作業が残っている可能性があったのです。

この不整合が問題を引き起こしました。`findRunnable`は「作業がない」と判断してGCワーカーを起動しないにもかかわらず、実際には`currentwbuf`に未処理の作業が残っているため、GCの進行が遅延したり、特定のシナリオでGCが完了しなかったりする可能性がありました。

特に、`test/init1.go`のような、ライトバリアの発生が少ない大量割り当てテストでは、`currentwbuf`にポインタが滞留しやすくなります。通常、ライトバリアが頻繁に発生すれば、`currentwbuf`の内容は定期的にグローバルキューにフラッシュされますが、ライトバリアが少ないと、このフラッシュが起こりにくく、`currentwbuf`内の作業が`findRunnable`から「見えない」状態が長く続くことになります。これが、`test/init1.go`で時折テストが失敗する原因でした。

このコミットの修正は、`findRunnable`の作業チェックロジックを`getfull`の作業取得ロジックと一致させることで、この問題を解決します。具体的には、`findRunnable`がGC作業の有無を判断する際に、`work.full`と`work.partial`に加えて、`_p_.m.ptr().currentwbuf`もチェックするように変更されました。

これにより、`findRunnable`は`currentwbuf`に作業が残っている場合でも、それを正しく認識し、GCワーカーを適切にスケジュールできるようになります。結果として、GCの進行がよりスムーズになり、`test/init1.go`のような特殊なテストケースでもGCが正しく機能するようになります。

## コアとなるコードの解説

変更された行は、`gcControllerState`構造体の`findRunnable`メソッド内にあります。このメソッドは、GCワーカーをスケジュールすべきかどうかを判断するロジックを含んでいます。

元のコードでは、GC作業がないと判断する条件は以下の通りでした。

```go
if work.full == 0 && work.partial == 0 {
```

これは、グローバルなGC作業キューである`work.full`と`work.partial`が両方とも空である場合に、「GC作業は存在しない」と判断していました。

このコミットでは、この条件に`_p_.m.ptr().currentwbuf == 0`が追加されました。

```go
if _p_.m.ptr().currentwbuf == 0 && work.full == 0 && work.partial == 0 {
```

*   `_p_`: 現在のプロセッサ（P）を表すポインタです。
*   `_p_.m.ptr()`: 現在のPに紐づくM（マシン、OSスレッド）構造体へのポインタを取得します。
*   `currentwbuf`: M構造体内に存在する、そのMが現在使用しているローカルなGC作業バッファです。

この変更により、`findRunnable`はGC作業の有無を判断する際に、グローバルな作業キューだけでなく、各プロセッサのローカルな作業バッファである`currentwbuf`も考慮するようになりました。

新しい条件は、「`currentwbuf`も空であり、かつ`work.full`も`work.partial`も空である場合にのみ、GC作業は存在しない」と判断します。これにより、`currentwbuf`に未処理のポインタが残っている場合でも、`findRunnable`がそれを認識し、GCワーカーを適切に起動して処理を促すことができるようになります。

この修正は、GCワーカーのスケジューリングロジックを、実際にGC作業を取得するロジック（`getfull`など）と整合させることで、GCの効率性と正確性を向上させます。

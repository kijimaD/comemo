## 変更の背景

この変更は、MIME (Multipurpose Internet Mail Extensions) のヘッダーフィールドで非ASCII文字を使用するための標準であるRFC 2047「MIME (Multipurpose Internet Mail Extensions) Part Three: Message Header Extensions for Non-ASCII Text」に準拠するために行われました。RFC 2047では、エンコードされた単語（encoded-word）の各部分の最大長を75文字と推奨しています。しかし、Go言語の `mime` パッケージの実装にはバグがあり、エンコードされた単語が最大77文字まで生成されてしまう可能性がありました。この2文字の超過は、RFCの推奨事項に違反し、一部のMIMEパーサーで問題を引き起こす可能性がありました。このコミットは、この逸脱を修正し、RFC 2047の75文字の制限を厳密に遵守することを目的としています。

## 前提知識の解説

### MIME (Multipurpose Internet Mail Extensions)

MIMEは、電子メールでASCII文字以外の文字セット（日本語、中国語など）や、画像、音声、動画などの非テキストデータを扱うための標準です。MIMEは、電子メールのヘッダーと本文の構造を定義し、異なる種類のコンテンツを識別するためのメカニズムを提供します。

### RFC 2047: Message Header Extensions for Non-ASCII Text

RFC 2047は、MIMEヘッダーフィールド内で非ASCII文字を安全に表現するためのメカニズムを定義しています。これは「Encoded-Word」構文を使用します。

#### Encoded-Word 構文

Encoded-Wordは以下の形式を取ります。

`=?charset?encoding?encoded-text?=`

*   `charset`: 使用される文字セット（例: `UTF-8`, `ISO-2022-JP`）。
*   `encoding`: エンコード方式。
    *   `Q` (Quoted-Printable): テキストデータをエンコードする際に使用され、主に可読性を維持しつつ非ASCII文字を表現します。
    *   `B` (Base64): バイナリデータをエンコードする際に使用され、任意のデータをASCII文字に変換します。
*   `encoded-text`: `charset`と`encoding`に従ってエンコードされた実際のテキストデータ。

#### Encoded-Word の長さ制限

RFC 2047のセクション2には、Encoded-Wordの各部分（`=?charset?encoding?encoded-text?=` 全体）の長さが75文字を超えてはならないという推奨事項があります。もしエンコードされたテキストが長すぎて75文字の制限を超える場合、Encoded-Wordは複数の部分に分割され、それぞれが75文字の制限内でエンコードされ、スペースで区切られます。

例:
`=?UTF-8?Q?長いテキストの最初の部分?=` `=?UTF-8?Q?長いテキストの二番目の部分?=`

### Go言語の `mime` パッケージ

Go言語の標準ライブラリには、MIMEメッセージの解析と生成をサポートする `mime` パッケージが含まれています。このパッケージは、電子メールやHTTPなどのプロトコルでMIMEヘッダーを扱う際に利用されます。

## 技術的詳細

このバグは、`src/mime/encodedword.go` 内で `maxContentLen` 定数を計算する際のオフセットの誤りに起因していました。

`maxEncodedWordLen` はRFC 2047で推奨される最大長である `75` に設定されています。
`maxContentLen` は、エンコードされた単語のヘッダー (`=?charset?encoding?`) とフッター (`?=`) を除いた、`encoded-text` 部分の最大長を計算するための定数です。

Encoded-Wordの一般的な構造は `H + T + F` です。
ここで、
*   `H` はヘッダー部分 (`=?charset?encoding?`)
*   `T` はエンコードされたテキスト部分 (`encoded-text`)
*   `F` はフッター部分 (`?=`)

`charset` が `UTF-8` で `encoding` が `Q` または `B` の場合、
*   `H` の長さは `len("=?UTF-8?Q?")` または `len("=?UTF-8?B?")` であり、どちらも `10` 文字です。
*   `F` の長さは `len("?=")` であり、`2` 文字です。
したがって、`H` と `F` の合計オーバーヘッドは `10 + 2 = 12` 文字です。

RFC 2047の75文字の制限を遵守するためには、`maxContentLen` は `75 - 12 = 63` であるべきです。

しかし、バグのある以前のコードでは、`maxContentLen` は以下のように計算されていました。
```go
maxContentLen = maxEncodedWordLen - len("=?UTF-8?") - len("?=")
```
ここで、`len("=?UTF-8?")` は `9` 文字です。
したがって、`maxContentLen = 75 - 9 - 2 = 64` と計算されていました。

この `maxContentLen = 64` を使用してエンコードされた単語が生成されると、実際のヘッダー (`=?UTF-8?Q?` または `=?UTF-8?B?`) の長さが `10` 文字であるため、最終的なエンコードされた単語の長さは `10 (ヘッダー) + 64 (コンテンツ) + 2 (フッター) = 76` 文字になります。これはRFCの75文字の制限を1文字超過しています。

コミットメッセージで「77文字」と述べられているのは、おそらく `maxContentLen` の計算が `len("=?UTF-8?")` を使用し、その後にエンコーディングタイプ (`Q` または `B`) とそれに続く疑問符 (`?`) が別途追加されるようなロジックになっていたためと考えられます。
具体的には、`maxContentLen` が `75 - len("=?UTF-8?") - len("?=")` で計算され、その結果が `64` となります。
そして、エンコードされた単語を構築する際に、`=?UTF-8?` (9文字) に加えて `Q?` (2文字) がヘッダーの一部として追加され、さらにフッターの `?=` (2文字) が追加されると仮定すると、
合計の長さは `9 (=?UTF-8?) + 64 (maxContentLen) + 2 (Q?) + 2 (?=) = 77` 文字となります。
これが、コミットメッセージで言及されている「77文字」の超過のメカニズムです。

このコミットでは、`maxContentLen` の計算を修正し、ヘッダーの正確な長さを考慮するように変更しました。
```go
maxContentLen = maxEncodedWordLen - len("=?UTF-8?q?") - len("?=")
```
ここで、`len("=?UTF-8?q?")` は `10` 文字です。
したがって、新しい `maxContentLen = 75 - 10 - 2 = 63` となります。
この修正により、生成されるエンコードされた単語の最大長は `10 (ヘッダー) + 63 (コンテンツ) + 2 (フッター) = 75` 文字となり、RFC 2047の推奨事項に厳密に準拠するようになります。

## コアとなるコードの解説

### `src/mime/encodedword.go` の変更

`maxContentLen` の計算式が変更されました。
*   **変更前**: `maxEncodedWordLen - len("=?UTF-8?") - len("?=")`
    *   `len("=?UTF-8?")` は9文字。
    *   `maxContentLen` は `75 - 9 - 2 = 64` と計算されていました。
*   **変更後**: `maxEncodedWordLen - len("=?UTF-8?q?") - len("?=")`
    *   `len("=?UTF-8?q?")` は10文字。これは、`charset` と `encoding` (例: `q`) を含むヘッダーの正確な長さを反映しています。
    *   `maxContentLen` は `75 - 10 - 2 = 63` と計算されるようになりました。

この変更により、`encoded-text` 部分に割り当てられる最大文字数が1文字減少し、結果として生成されるEncoded-Word全体の長さがRFC 2047の75文字の制限に正確に収まるようになります。

### `src/mime/encodedword_test.go` の変更

`TestEncodedWordLength` 関数の追加は、この修正の検証において非常に重要です。
このテストは、`Encode` メソッドによって生成された文字列を反復処理し、スペースで区切られた各Encoded-Word部分の長さを個別にチェックします。もしどの部分でも `maxEncodedWordLen` (75) を超える長さが検出された場合、テストは失敗します。これにより、将来的に同様の長さに関する回帰バグが発生するのを防ぐことができます。

既存の `TestEncodeWord` 内のテストデータ修正は、以前のバグのある実装では許容されていたが、新しい厳密な75文字制限では長すぎると判断されるようになったケースを調整するものです。これにより、テストスイート全体が新しい仕様に準拠していることを保証します。

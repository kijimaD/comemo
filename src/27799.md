# [インデックス 27799] ファイルの概要

このコミットは、Goランタイムの`atomic`パッケージにおける`Storep1`関数が、`s390x`アーキテクチャ上で誤ってライトバリアを呼び出していた問題を修正するものです。この誤った挙動が`runtime.mapzero`関数でのパニックを引き起こしていました。修正は、`s390x`における`Storep1`からライトバリアの呼び出しを削除し、関連する`atomicstorep`関数にドキュメントを追加することで、両者の違いを明確にしています。

runtime/internal/atomic: remove write barrier from Storep1 on s390x
    
atomic.Storep1 is not supposed to invoke a write barrier (that's what
atomicstorep is for), but currently does on s390x. This causes a panic
in runtime.mapzero when it tries to use atomic.Storep1 to store what's

## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理、特にガベージコレクション（GC）におけるライトバリアの正確な適用と、特定のアーキテクチャ（s390x）でのその実装の不整合がありました。

Goのガベージコレクタは、オブジェクトがヒープ上で移動する際に、ポインタの整合性を保つためにライトバリアを使用します。ライトバリアは、ポインタが書き換えられる際に、GCがその変更を追跡し、必要に応じて古いオブジェクトをマークしたり、新しいオブジェクトを適切に処理したりするためのメカニズムです。

問題は、`runtime/internal/atomic`パッケージ内の`Storep1`関数が、`s390x`アーキテクチャにおいて、本来ライトバリアを必要としない操作であるにもかかわらず、誤ってライトバリアを呼び出していた点にありました。`Storep1`は、ポインタをアトミックにストアするための低レベルなプリミティブであり、GCの追跡対象ではないスカラー値を扱う場合など、特定のコンテキストではライトバリアを回避する必要があります。

この誤ったライトバリアの呼び出しは、`runtime.mapzero`関数内で顕在化しました。`runtime.mapzero`は、マップの初期化などでメモリをゼロクリアする際に、スカラー値をストアするために`atomic.Storep1`を使用します。このとき、`Storep1`が予期せずライトバリアを呼び出すと、GCがスカラー値をポインタとして解釈しようとし、結果としてパニック（クラッシュ）が発生していました。

したがって、この変更の目的は、`s390x`アーキテクチャにおける`Storep1`のライトバリアの誤用を修正し、Goランタイムの安定性と正確性を向上させることでした。また、`atomic.Storep1`と`atomicstorep`という類似した名前の関数間の役割の違いを明確にするために、ドキュメントの追加も行われました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とアーキテクチャに関する知識が必要です。

1.  **Goのガベージコレクション (GC) とライトバリア (Write Barrier)**:
    *   Goは並行マーク＆スイープ型のガベージコレクタを採用しています。GCは、プログラムが実行中に不要になったメモリを自動的に解放する役割を担います。
    *   **ライトバリア**は、GCが正しく動作するために不可欠なメカニズムです。プログラムがヒープ上のポインタを書き換える（ストアする）際に、GCがその変更を検知し、オブジェクトグラフの整合性を維持するために介入します。これにより、GCがオブジェクトを移動させたり、マークしたりする際に、プログラムが古いポインタを参照してしまう「stale pointer」の問題を防ぎます。
    *   ライトバリアは、通常、ポインタ型の値をヒープに書き込む際に発動します。しかし、スカラー値（整数、ブール値など）や、GCの対象外となる特定のメモリ領域への書き込みでは、ライトバリアは不要であり、むしろオーバーヘッドや誤動作の原因となることがあります。

2.  **Goの`atomic`パッケージ**:
    *   `sync/atomic`パッケージは、ミューテックスなどのロック機構を使わずに、アトミックな（不可分な）操作を提供します。これにより、複数のゴルーチンが共有データにアクセスする際の競合状態を防ぎ、パフォーマンスを向上させることができます。
    *   Goランタイム内部では、より低レベルなアトミック操作が`runtime/internal/atomic`パッケージで提供されています。これらは、GCのライトバリアとの相互作用を考慮して設計されています。
    *   `Storep1`や`atomicstorep`のような関数は、ポインタ型または`unsafe.Pointer`型の値をアトミックにストアするために使用されます。

3.  **`unsafe.Pointer`**:
    *   Goの`unsafe`パッケージは、型安全性をバイパスして、任意の型へのポインタを`unsafe.Pointer`型として扱うことを可能にします。これにより、C言語のような低レベルなメモリ操作が可能になりますが、Goの型システムやメモリモデルの保証が失われるため、非常に注意して使用する必要があります。
    *   ランタイムコードでは、メモリレイアウトを直接操作する必要があるため、`unsafe.Pointer`が頻繁に利用されます。

4.  **`s390x`アーキテクチャ**:
    *   `s390x`は、IBMのメインフレームコンピュータ（System/390およびz/Architecture）で使用される64ビット命令セットアーキテクチャです。
    *   Goはクロスプラットフォーム言語であり、様々なCPUアーキテクチャをサポートしています。各アーキテクチャには、それぞれ固有のメモリモデル、アトミック操作の実装、およびGCとの連携方法があります。このコミットは、`s390x`アーキテクチャに特有の問題を扱っています。

5.  **`runtime.mapzero`**:
    *   Goランタイム内部の関数で、マップ（`map`型）の初期化や再ハッシュなどの際に、メモリ領域をゼロクリアする役割を担います。この処理では、ポインタだけでなくスカラー値も含まれるメモリ領域を効率的に初期化する必要があります。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、Goランタイムにおけるアトミック操作とライトバリアの設計思想、および特定のアーキテクチャでのその実装の複雑さが浮き彫りになります。

Goランタイムには、ポインタをアトミックにストアするための2つの主要な関数があります。

*   `atomic.Storep1(ptr unsafe.Pointer, val unsafe.Pointer)`: この関数は、`ptr`が指すメモリ位置に`val`をアトミックにストアします。その名前が示すように、これは低レベルのアトミック操作であり、**通常はライトバリアを伴いません**。これは、GCが追跡する必要のないスカラー値や、GCのライフサイクルとは独立したメモリ領域を扱う場合に使用されます。
*   `atomicstorep(ptr unsafe.Pointer, new unsafe.Pointer)`: この関数もポインタをアトミックにストアしますが、その主な目的は、**ライトバリアを伴うストア操作**を提供することです。つまり、GCがポインタの変更を検知し、必要に応じてオブジェクトグラフを更新できるようにします。

問題は、`s390x`アーキテクチャの`runtime/internal/atomic/atomic_s390x.go`において、`Storep1`の実装が誤ってライトバリアを呼び出すようなコードになっていたことです。具体的には、`Storep1`が`*(*unsafe.Pointer)(ptr) = val`という形で直接ポインタを書き換えていましたが、この操作が`s390x`のコンテキストでライトバリアをトリガーする可能性がありました。

`runtime.mapzero`関数は、マップのメモリをゼロクリアする際に、ポインタとスカラー値が混在する可能性のあるメモリ領域を扱います。このとき、`runtime.mapzero`はスカラー値をストアするために`atomic.Storep1`を使用することを意図していました。しかし、`s390x`上で`Storep1`がライトバリアを呼び出すと、GCはスカラー値をポインタとして解釈しようとし、その結果、無効なメモリアドレスへのアクセスや、GC内部の不整合が発生し、最終的にランタイムパニックを引き起こしていました。

このコミットでは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **`s390x`における`Storep1`の実装修正**:
    `src/runtime/internal/atomic/atomic_s390x.go`内の`Storep1`関数が、`*(*unsafe.Pointer)(ptr) = val`から`*(*uintptr)(ptr) = uintptr(val)`に変更されました。
    この変更は非常に重要です。`unsafe.Pointer`を直接ストアする代わりに、`uintptr`にキャストしてからストアすることで、Goの型システムに対して「これはポインタではなく、単なるアドレス値である」という意図をより明確に伝えています。これにより、`s390x`コンパイラやランタイムがこの操作をライトバリアを伴わないスカラー値のストアとして正しく解釈するようになります。`uintptr`はポインタのアドレスを保持する整数型であり、GCの追跡対象ではありません。

2.  **`atomicstorep`のドキュメント追加**:
    `src/runtime/atomic_pointer.go`において、`atomicstorep`関数のコメントが更新されました。以前は、`atomic_pointer.go`内のコメントで「これらの関数はライトバリアチェックのためにシャドウヒープを更新しなければならない」と一般的に記述されていましたが、これは`atomicstorep`にのみ適用されるべきでした。
    新しいコメントでは、「`atomicstorep`は`*ptr = new`をアトミックに実行し、**ライトバリアを呼び出す**」と明示的に記述されています。これにより、`atomic.Storep1`と`atomicstorep`の間の重要な違い（ライトバリアの有無）が明確になり、将来的な誤用を防ぐためのドキュメントが強化されました。

これらの変更により、`s390x`アーキテクチャ上で`runtime.mapzero`が`atomic.Storep1`を使用する際に、不要なライトバリアが呼び出されることがなくなり、パニックが解消されました。

## コアとなるコードの解説

1.  **`src/runtime/atomic_pointer.go` の変更**:
    この変更は、主にドキュメンテーションの改善です。`atomicstorep`関数の新しいコメント`// atomicstorep performs *ptr = new atomically and invokes a write barrier.`は、この関数がポインタをアトミックにストアするだけでなく、**ライトバリアを伴う**ことを明確に示しています。これにより、`atomic.Storep1`（ライトバリアなし）と`atomicstorep`（ライトバリアあり）の役割の違いが、コードを読む開発者にとってより明確になりました。以前のコメントは曖昧で、`atomic.Storep1`にもライトバリアが必要であるかのような誤解を与える可能性がありました。

2.  **`src/runtime/internal/atomic/atomic_s390x.go` の変更**:
    この変更は、問題の核心を修正するものです。
    *   **変更前**: `*(*unsafe.Pointer)(ptr) = val`
        これは、`ptr`が指すメモリ位置を`unsafe.Pointer`として解釈し、そこに`val`（これも`unsafe.Pointer`）を直接ストアしていました。`s390x`アーキテクチャの特定のコンテキストでは、この操作がGoランタイムによってポインタの書き込みと解釈され、意図せずライトバリアがトリガーされていました。
    *   **変更後**: `*(*uintptr)(ptr) = uintptr(val)`
        この修正では、`val`を`uintptr`型にキャストしてからストアしています。`uintptr`はポインタのアドレスを保持する整数型であり、Goのガベージコレクタは`uintptr`型の値をポインタとして追跡しません。したがって、この変更により、`Storep1`が実行するストア操作は、GCにとって単なるスカラー値（アドレス値）の書き込みと見なされ、ライトバリアがトリガーされなくなります。これにより、`runtime.mapzero`がスカラー値をストアする際に発生していたパニックが解消されます。

この修正は、GoのメモリモデルとGCの動作を深く理解していることを示しており、特定のアーキテクチャにおける低レベルな実装の詳細が、ランタイム全体の安定性にどのように影響するかを示す良い例です。

    *   `sync/atomic`パッケージは、ミューテックスなどのロック機構を使わずに、アトミックな（不可分な）操作を提供します。これにより、複数のゴルーチンが共有データにアクセスする際の競合状態を防ぎ、パフォーマンスを向上させることができます。
    *   Goランタイム内部では、より低レベルなアトミック操作が`runtime/internal/atomic`パッケージで提供されています。これらは、GCのライトバリアとの相互作用を考慮して設計されています。
    *   `Storep1`や`atomicstorep`のような関数は、ポインタ型または`unsafe.Pointer`型の値をアトミックにストアするために使用されます。

3.  **`unsafe.Pointer`**:
    *   Goの`unsafe`パッケージは、型安全性をバイパスして、任意の型へのポインタを`unsafe.Pointer`型として扱うことを可能にします。これにより、C言語のような低レベルなメモリ操作が可能になりますが、Goの型システムやメモリモデルの保証が失われるため、非常に注意して使用する必要があります。
    *   ランタイムコードでは、メモリレイアウトを直接操作する必要があるため、`unsafe.Pointer`が頻繁に利用されます。

4.  **`s390x`アーキテクチャ**:
    *   `s390x`は、IBMのメインフレームコンピュータ（System/390およびz/Architecture）で使用される64ビット命令セットアーキテクチャです。
    *   Goはクロスプラットフォーム言語であり、様々なCPUアーキテクチャをサポートしています。各アーキテクチャには、それぞれ固有のメモリモデル、アトミック操作の実装、およびGCとの連携方法があります。このコミットは、`s390x`アーキテクチャに特有の問題を扱っています。

5.  **`runtime.mapzero`**:
    *   Goランタイム内部の関数で、マップ（`map`型）の初期化や再ハッシュなどの際に、メモリ領域をゼロクリアする役割を担います。この処理では、ポインタだけでなくスカラー値も含まれるメモリ領域を効率的に初期化する必要があります。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、Goランタイムにおけるアトミック操作とライトバリアの設計思想、および特定のアーキテクチャでのその実装の複雑さが浮き彫りになります。

Goランタイムには、ポインタをアトミックにストアするための2つの主要な関数があります。

*   `atomic.Storep1(ptr unsafe.Pointer, val unsafe.Pointer)`: この関数は、`ptr`が指すメモリ位置に`val`をアトミックにストアします。その名前が示すように、これは低レベルのアトミック操作であり、**通常はライトバリアを伴いません**。これは、GCが追跡する必要のないスカラー値や、GCのライフサイクルとは独立したメモリ領域を扱う場合に使用されます。
*   `atomicstorep(ptr unsafe.Pointer, new unsafe.Pointer)`: この関数もポインタをアトミックにストアしますが、その主な目的は、**ライトバリアを伴うストア操作**を提供することです。つまり、GCがポインタの変更を検知し、必要に応じてオブジェクトグラフを更新できるようにします。

問題は、`s390x`アーキテクチャの`runtime/internal/atomic/atomic_s390x.go`において、`Storep1`の実装が誤ってライトバリアを呼び出すようなコードになっていたことです。具体的には、`Storep1`が`*(*unsafe.Pointer)(ptr) = val`という形で直接ポインタを書き換えていましたが、この操作が`s390x`のコンテキストでライトバリアをトリガーする可能性がありました。

`runtime.mapzero`関数は、マップのメモリをゼロクリアする際に、ポインタとスカラー値が混在する可能性のあるメモリ領域を扱います。このとき、`runtime.mapzero`はスカラー値をストアするために`atomic.Storep1`を使用することを意図していました。しかし、`s390x`上で`Storep1`がライトバリアを呼び出すと、GCはスカラー値をポインタとして解釈しようとし、その結果、無効なメモリアドレスへのアクセスや、GC内部の不整合が発生し、最終的にランタイムパニックを引き起こしていました。

このコミットでは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **`s390x`における`Storep1`の実装修正**:
    `src/runtime/internal/atomic/atomic_s390x.go`内の`Storep1`関数が、`*(*unsafe.Pointer)(ptr) = val`から`*(*uintptr)(ptr) = uintptr(val)`に変更されました。
    この変更は非常に重要です。`unsafe.Pointer`を直接ストアする代わりに、`uintptr`にキャストしてからストアすることで、Goの型システムに対して「これはポインタではなく、単なるアドレス値である」という意図をより明確に伝えています。これにより、`s390x`コンパイラやランタイムがこの操作をライトバリアを伴わないスカラー値のストアとして正しく解釈するようになります。`uintptr`はポインタのアドレスを保持する整数型であり、GCの追跡対象ではありません。

2.  **`atomicstorep`のドキュメント追加**:
    `src/runtime/atomic_pointer.go`において、`atomicstorep`関数のコメントが更新されました。以前は、`atomic_pointer.go`内のコメントで「これらの関数はライトバリアチェックのためにシャドウヒープを更新しなければならない」と一般的に記述されていましたが、これは`atomicstorep`にのみ適用されるべきでした。
    新しいコメントでは、「`atomicstorep`は`*ptr = new`をアトミックに実行し、**ライトバリアを呼び出す**」と明示的に記述されています。これにより、`atomic.Storep1`と`atomicstorep`の間の重要な違い（ライトバリアの有無）が明確になり、将来的な誤用を防ぐためのドキュメントが強化されました。

これらの変更により、`s390x`アーキテクチャ上で`runtime.mapzero`が`atomic.Storep1`を使用する際に、不要なライトバリアが呼び出されることがなくなり、パニックが解消されました。

## コアとなるコードの解説

1.  **`src/runtime/atomic_pointer.go` の変更**:
    この変更は、主にドキュメンテーションの改善です。`atomicstorep`関数の新しいコメント`// atomicstorep performs *ptr = new atomically and invokes a write barrier.`は、この関数がポインタをアトミックにストアするだけでなく、**ライトバリアを伴う**ことを明確に示しています。これにより、`atomic.Storep1`（ライトバリアなし）と`atomicstorep`（ライトバリアあり）の役割の違いが、コードを読む開発者にとってより明確になりました。以前のコメントは曖昧で、`atomic.Storep1`にもライトバリアが必要であるかのような誤解を与える可能性がありました。

2.  **`src/runtime/internal/atomic/atomic_s390x.go` の変更**:
    この変更は、問題の核心を修正するものです。
    *   **変更前**: `*(*unsafe.Pointer)(ptr) = val`
        これは、`ptr`が指すメモリ位置を`unsafe.Pointer`として解釈し、そこに`val`（これも`unsafe.Pointer`）を直接ストアしていました。`s390x`アーキテクチャの特定のコンテキストでは、この操作がGoランタイムによってポインタの書き込みと解釈され、意図せずライトバリアがトリガーされていました。
    *   **変更後**: `*(*uintptr)(ptr) = uintptr(val)`
        この修正では、`val`を`uintptr`型にキャストしてからストアしています。`uintptr`はポインタのアドレスを保持する整数型であり、Goのガベージコレクタは`uintptr`型の値をポインタとして追跡しません。したがって、この変更により、`Storep1`が実行するストア操作は、GCにとって単なるスカラー値（アドレス値）の書き込みと見なされ、ライトバリアがトリガーされなくなります。これにより、`runtime.mapzero`がスカラー値をストアする際に発生していたパニックが解消されます。

この修正は、GoのメモリモデルとGCの動作を深く理解していることを示しており、特定のアーキテクチャにおける低レベルな実装の詳細が、ランタイム全体の安定性にどのように影響するかを示す良い例です。

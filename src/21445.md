# [インデックス 21445] ファイルの概要

このコミットは、GoランタイムがWindows上でクラッシュした際に、Windows Error Reporting (WER) ダイアログが表示されるのを抑制するための変更です。主にWindows固有のランタイムコードとテストファイルが影響を受けています。

具体的には、以下のファイルが変更または新規追加されています。

*   `src/runtime/export_windows_test.go`: 新規追加されたテストヘルパーファイルで、`testingWER`変数をテスト目的でエクスポートします。
*   `src/runtime/os1_windows.go`: Windows固有のOS初期化処理が含まれるファイルで、`SetErrorMode` APIのインポートと呼び出しが追加されています。
*   `src/runtime/os1_windows_386.go`: 32ビットWindowsアーキテクチャ向けのランタイム例外ハンドリングファイルで、`lastcontinuehandler`の動作が変更されています。
*   `src/runtime/os1_windows_amd64.go`: 64ビットWindowsアーキテクチャ向けのランタイム例外ハンドリングファイルで、`lastcontinuehandler`の動作が変更されています。
*   `src/runtime/syscall_windows_test.go`: Windowsシステムコール関連のテストファイルで、WERダイアログの抑制を検証するための新しいテストケースが追加されています。

## 変更の背景

このコミットの背景には、GoプログラムがWindows上でクラッシュした際に、オペレーティングシステムが提供する「Windows Error Reporting (WER)」ダイアログが自動的に表示されるという問題がありました。これは、特にバックグラウンドで動作するサーバーアプリケーションや、CI/CD環境、あるいは多数のGoプログラムが同時に実行されるような環境において、深刻な問題を引き起こす可能性がありました。

WERダイアログは、ユーザーがクラッシュ情報をMicrosoftに送信するかどうかを尋ねるもので、GUI環境では有用ですが、ヘッドレス環境や自動化された環境では、プログラムの実行をブロックし、手動での介入を必要とします。これにより、アプリケーションの可用性が低下したり、テストの自動化が妨げられたりする事態が発生していました。

Goのランタイムは、プログラムがクラッシュした際に独自のスタックトレースやデバッグ情報を出力する機能を持っています。そのため、WERダイアログはGoプログラムにとって冗長であり、むしろ望ましくない挙動でした。このコミットは、このWERダイアログの表示を抑制し、Goプログラムがクラッシュした際に、よりクリーンに、そして自動的に終了できるようにすることを目的としています。これは、GoのIssue #9121で報告された問題に対応するものです。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **Windows Error Reporting (WER)**:
    *   Windowsオペレーティングシステムに組み込まれたクラッシュレポートメカニズムです。アプリケーションがクラッシュしたり、応答しなくなったりした場合に、その情報を収集し、Microsoftに送信することをユーザーに促すダイアログを表示します。
    *   目的は、開発者がソフトウェアのバグを特定し、修正するためのデータを提供することです。
    *   しかし、サーバーアプリケーションやコマンドラインツールなど、GUIを持たないアプリケーションでは、このダイアログの表示は望ましくありません。

2.  **`SetErrorMode` API**:
    *   Windows APIの一つで、システムが特定のエラーを処理する方法を制御するために使用されます。
    *   この関数は、アプリケーションがクラッシュしたときや、ファイルが見つからないなどのクリティカルなエラーが発生したときに、エラーダイアログを表示するかどうかなどを設定できます。
    *   重要なフラグとして以下のようなものがあります:
        *   `SEM_FAILCRITICALERRORS`: システムがクリティカルなエラー（例: ドライブが見つからない）に対してエラーメッセージボックスを表示しないようにします。代わりに、エラーは呼び出しプロセスに直接返されます。
        *   `SEM_NOGPFAULTERRORBOX`: 一般保護違反（GPF）やその他のアプリケーションエラーが発生したときに、システムがエラーメッセージボックスを表示しないようにします。これがWERダイアログの抑制に直接関係します。
        *   `SEM_NOOPENFILEERRORBOX`: ファイルを開く操作が失敗したときに、システムがエラーメッセージボックスを表示しないようにします。

3.  **Goランタイムの例外ハンドリング (Windows)**:
    *   Goプログラムは、Go言語のランタイムによって管理されます。Goプログラムがパニック（Goにおけるランタイムエラー）を起こしたり、OSレベルの例外（例: アクセス違反）に遭遇したりした場合、Goランタイムはそれを捕捉し、Goのスタックトレースを出力してプログラムを終了させようとします。
    *   Windows上では、GoランタイムはOSの構造化例外ハンドリング (SEH) を利用して、これらのOSレベルの例外を捕捉します。`AddVectoredExceptionHandler`などのAPIが使用され、Goランタイム独自の例外ハンドラが登録されます。
    *   `lastcontinuehandler`は、Goランタイムが捕捉した例外を最終的に処理する部分の一つで、通常はパニック情報を出力し、プログラムを終了させる役割を担います。

4.  **`go:cgo_import_dynamic`**:
    *   Goのコンパイラディレクティブの一つで、Cgoを使用せずに動的にDLLから関数をインポートするために使用されます。これにより、Goのランタイムが直接Windows APIを呼び出すことが可能になります。

## 技術的詳細

このコミットの技術的な核心は、Goプログラムの起動時にWindowsの`SetErrorMode` APIを呼び出し、特定のフラグを設定することで、クラッシュ時のWERダイアログの表示を抑制することにあります。

具体的には、`src/runtime/os1_windows.go`の`osinit()`関数（GoランタイムのOS固有の初期化処理）内で、以下の処理が追加されています。

1.  **`SetErrorMode` APIのインポート**:
    `//go:cgo_import_dynamic runtime._SetErrorMode SetErrorMode "kernel32.dll"`
    この行により、`kernel32.dll`から`SetErrorMode`関数が動的にインポートされ、Goランタイムから呼び出せるようになります。

2.  **`SetErrorMode`の呼び出し**:
    `errormode := uint32(stdcall1(_SetErrorMode, SEM_NOGPFAULTERRORBOX))`
    `stdcall1(_SetErrorMode, uintptr(errormode)|SEM_FAILCRITICALERRORS|SEM_NOGPFAULTERRORBOX|SEM_NOOPENFILEERRORBOX)`

    *   最初の`SetErrorMode`呼び出しは、現在のエラーモードを取得するために行われます。ここでは特に`SEM_NOGPFAULTERRORBOX`フラグが渡されていますが、これは現在の設定を取得する目的で、既存のモードを上書きしないようにするためです。
    *   2番目の`SetErrorMode`呼び出しが実際の変更を行います。ここで、以下のフラグが論理和 (`|`) で結合されて設定されます。
        *   `SEM_FAILCRITICALERRORS`: クリティカルなエラーダイアログを抑制します。
        *   `SEM_NOGPFAULTERRORBOX`: 一般保護違反（GPF）などのアプリケーションエラーダイアログ（WERダイアログを含む）を抑制します。これがこのコミットの主要な目的です。
        *   `SEM_NOOPENFILEERRORBOX`: ファイルオープンエラーダイアログを抑制します。

これらのフラグを設定することで、Goプログラムがクラッシュした場合でも、WindowsはWERダイアログを表示せず、Goランタイムが制御を維持し、自身のパニック処理（スタックトレースの出力とプログラムの終了）を完了できるようになります。

また、`src/runtime/os1_windows_386.go`と`src/runtime/os1_windows_amd64.go`では、`lastcontinuehandler`関数に`testingWER`という新しいブール変数が導入されています。これは、テスト目的でWERダイアログの抑制を一時的に無効にするためのものです。`TestWERDialogue`という新しいテストケースが追加され、この変数を`true`に設定することで、意図的にWERダイアログが表示される状況をシミュレートし、その抑制が正しく機能しているかを検証します。通常実行時には`testingWER`は`false`のままであり、WERダイアログは抑制されます。

## コアとなるコードの解説

1.  **`src/runtime/os1_windows.go` の変更**:
    *   `_SetErrorMode`の動的インポートと、それに対応する`var`宣言が追加されました。これにより、GoランタイムがWindowsの`SetErrorMode`関数を呼び出す準備が整います。
    *   `SEM_FAILCRITICALERRORS`, `SEM_NOGPFAULTERRORBOX`, `SEM_NOOPENFILEERRORBOX`という定数が定義されました。これらは`SetErrorMode`関数に渡すフラグのビットマスクです。
    *   `osinit()`関数内で、`SetErrorMode`が呼び出されています。
        *   まず、`stdcall1(_SetErrorMode, SEM_NOGPFAULTERRORBOX)`で現在のエラーモードを取得しています。これは、既存の設定を尊重しつつ、新しい設定を追加するための一般的なパターンです。
        *   次に、`stdcall1(_SetErrorMode, uintptr(errormode)|SEM_FAILCRITICALERRORS|SEM_NOGPFAULTERRORBOX|SEM_NOOPENFILEERRORBOX)`で、取得した既存のモードに新しいフラグを追加して設定しています。特に`SEM_NOGPFAULTERRORBOX`が、クラッシュダイアログ（WERダイアログ）の表示を抑制する上で最も重要です。これにより、Goプログラムがクラッシュしても、Windowsは自動的にWERダイアログを表示しなくなります。

2.  **`src/runtime/os1_windows_386.go` および `src/runtime/os1_windows_amd64.go` の変更**:
    *   `testingWER`というグローバルなブール変数が追加されました。この変数は、テスト目的でWERダイアログの抑制を一時的に無効にするために使用されます。
    *   `lastcontinuehandler`関数内で、`if testingWER { return _EXCEPTION_CONTINUE_SEARCH }`という条件分岐が追加されました。
        *   `lastcontinuehandler`は、Goランタイムが処理できない例外に遭遇したときに呼び出される最終的な例外ハンドラです。通常はここでパニック情報を出力し、プログラムを終了させます。
        *   `testingWER`が`true`の場合（つまりテスト実行時）、このハンドラは例外を処理せずに`_EXCEPTION_CONTINUE_SEARCH`を返します。これは、Windowsに「この例外はまだ処理されていないので、次の例外ハンドラを探してください」と伝えることを意味します。これにより、テスト環境下ではWERダイアログが表示される挙動をシミュレートできます。
        *   通常実行時には`testingWER`は`false`のままであり、この条件は満たされないため、Goランタイムは引き続き自身のクラッシュ処理を行います。
    *   `os1_windows_amd64.go`では、`lastcontinuehandler`の戻り値の型が`uint32`から`int32`に変更されています。これは、`_EXCEPTION_CONTINUE_SEARCH`が`int32`型であるため、型の一貫性を保つための修正です。

3.  **`src/runtime/syscall_windows_test.go` の変更**:
    *   `TestWERDialogue`という新しいテスト関数が追加されました。
    *   このテストは、環境変数`TESTING_WER_DIALOGUE`が`"1"`に設定されているかどうかで動作を分岐させます。
    *   **子プロセス側**: `TESTING_WER_DIALOGUE=1`の場合、`runtime.TestingWER`を`true`に設定し、`RaiseException`というWindows APIを呼び出して意図的に例外を発生させます。このとき、`testingWER`が`true`であるため、`lastcontinuehandler`は`_EXCEPTION_CONTINUE_SEARCH`を返し、WERダイアログが表示されるはずです。しかし、テストの目的は「ダイアログが表示されないこと」を確認することなので、この子プロセスはすぐに終了します。
    *   **親プロセス側**: `TESTING_WER_DIALOGUE`が設定されていない場合、自身を子プロセスとして`TESTING_WER_DIALOGUE=1`の環境変数で実行します。そして、子プロセスの`CombinedOutput()`を呼び出し、子プロセスがWERダイアログを表示せずに正常に終了することを確認します。もしWERダイアログが表示されていれば、子プロセスはブロックされ、テストはタイムアウトするか、予期せぬエラーで失敗するでしょう。このテストは、`SetErrorMode`によるWERダイアログの抑制が正しく機能していることを検証します。

これらの変更により、GoプログラムはWindows上でより「行儀の良い」クラッシュ挙動を示すようになり、特に自動化された環境での運用が容易になりました。

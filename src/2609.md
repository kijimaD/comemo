## 元コミット内容

このコミットは、Goコンパイラ（特に6g、x86-64アーキテクチャ向け）に対する多岐にわたる改善を含んでいます。主な変更点は以下の通りです。

*   **`genwrapper`と`genembedtramp`のシグネチャ統一**: メソッドラッパーと埋め込み型トランポリンを生成する二つの関数の引数リストを統一しました。これにより、コードの整合性が向上し、保守が容易になります。
*   **`duint8`, `duint16`, `duint32`, `duint64`, `duintptr`を`gc`へ移動**: 特定のサイズの符号なし整数をデータセクションに書き込むためのヘルパー関数群を、アーキテクチャ固有のコンパイラ（6g/8g）から共通のコンパイラフロントエンド（gc）へ移動しました。これにより、コードの重複が排除され、共通ロジックが一元化されます。
*   **`genwrapper`の整理**: `genwrapper`関数の内部実装が整理され、可読性と保守性が向上しました。
*   **シグネチャリスト内の構造体フィールドシンボルに関するバグ修正**: 構造体のフィールドシンボルがシグネチャリストに現れる際のバグが修正されました。このバグはハッシュ順序に依存していたため、再現が困難でした。
*   **新しい`Type`プリントフォーマット`%#-T`の追加**: 型の文字列表現において、関数引数の名前を省略する新しい書式指定子`%#-T`が追加されました。これは、`%#T`（完全な型情報）に似ていますが、引数名を省略することで、型の比較やデバッグ出力においてより簡潔な表現を可能にします。

## 変更の背景

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われたもので、当時のGoコンパイラ（主に`gc`、`6g`、`8g`など）の成熟度を高めるための重要なステップでした。

1.  **コードベースの整理と共通化**: Goコンパイラは当初、Plan 9 C言語で書かれており、各アーキテクチャ（x86-64, x86など）ごとに異なるバックエンド（`6g`, `8g`）を持っていました。この時期は、共通のロジックを`gc`（コンパイラフロントエンド）に集約し、アーキテクチャ固有のコードを最小限に抑える努力が続けられていました。`duintxx`関数の移動はその一環です。
2.  **型システムの改善とデバッグ**: Goの型システムは、言語の安全性と表現力の核となる部分です。型の内部表現や文字列表現は、コンパイラのデバッグ、エラーメッセージの生成、そしてリフレクションなどのランタイム機能にとって非常に重要です。新しい`%#-T`フォーマットの追加は、型のデバッグ出力の柔軟性を高めることを目的としています。
3.  **メソッドディスパッチの最適化と正確性**: Goのインターフェースとメソッドは、動的なディスパッチを伴います。`genwrapper`と`genembedtramp`は、この動的なディスパッチを効率的に行うためのアセンブリコードを生成する役割を担っていました。これらの関数のシグネチャ統一やバグ修正は、メソッド呼び出しの正確性とパフォーマンスを確保するために不可欠でした。特に、埋め込み型（embedded types）のメソッド解決は複雑であり、そのためのトランポリン（`genembedtramp`）の正確な生成が求められました。
4.  **バグの修正**: ハッシュ順序に依存するバグは、再現が困難であり、コンパイラの信頼性を損なう可能性があります。このようなバグを早期に発見し修正することは、言語の安定性にとって極めて重要でした。

これらの変更は、Goコンパイラの内部構造をより堅牢で、保守しやすく、効率的なものにするための継続的な取り組みの一部でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラおよびGo言語の基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (6g/8g/gc)**:
    *   **`gc` (Go Compiler)**: Go言語の主要なコンパイラコレクションのフロントエンド部分。ソースコードの字句解析、構文解析、型チェック、中間表現（IR）の生成など、アーキテクチャ非依存の処理を担当します。
    *   **`6g` (Go Compiler for x86-64)**: `gc`のバックエンドの一つで、x86-64アーキテクチャ向けの機械語コードを生成します。
    *   **`8g` (Go Compiler for x86)**: `gc`のバックエンドの一つで、x86アーキテクチャ向けの機械語コードを生成します。
    *   当時のGoコンパイラは、Plan 9 C言語で書かれており、アセンブラコードの生成もC言語のコード内で行われることが多かったです。
*   **型システム (`Type`構造体)**:
    *   Goコンパイラ内部では、Go言語の各型が`Type`という構造体で表現されます。この構造体には、型の種類（`etype`）、サイズ、フィールド情報などが含まれます。
    *   `etype`: `Type`構造体のフィールドで、型の基本的な種類（例: `TINT`、`TFUNC`、`TSTRUCT`、`TARRAY`など）を示します。
    *   `TFIELD`: 構造体のフィールドを表す特別な型。フィールド名、型、オフセットなどを含みます。
    *   `TFUNC`: 関数型を表す。引数と戻り値の型情報を含みます。
*   **シンボル (`Sym`構造体)**:
    *   コンパイラが扱う変数名、関数名、型名などの識別子は、内部的に`Sym`（シンボル）構造体で表現されます。シンボルは、その名前、型、定義されているスコープなどの情報を持っています。
*   **メソッドディスパッチとインターフェース**:
    *   Go言語のインターフェースは、動的なメソッド呼び出しを可能にします。インターフェース型の変数に具体的な型の値が代入されると、その値のメソッドが実行時に解決されます。
    *   **`genwrapper`**: 特定の型（レシーバ型）のメソッドを呼び出すためのラッパー関数（アセンブリコード）を生成します。これは、主にインターフェースメソッドの呼び出しや、メソッド値（method value）の生成に使用されます。
    *   **`genembedtramp`**: 埋め込み型（embedded types）のメソッドを呼び出すための「トランポリン」関数（アセンブリコード）を生成します。埋め込み型を通じてアクセスされるメソッドは、レシーバのアドレスを調整する必要があるため、このトランポリンがその役割を担います。
*   **アセンブラ命令 (x86/x86-64)**:
    *   Goコンパイラは、最終的にターゲットアーキテクチャのアセンブリコードを生成します。
    *   `AMOVQ` (Move Quadword): 64ビット値を移動する命令（x86-64）。
    *   `AMOVL` (Move Long): 32ビット値を移動する命令（x86）。
    *   `AADDQ` (Add Quadword): 64ビット値を加算する命令（x86-64）。
    *   `AADDL` (Add Long): 32ビット値を加算する命令（x86）。
    *   `ATEXT`: 関数の開始を示すディレクティブ。
    *   `AJMP`: 無条件ジャンプ命令。
    *   `ARET`: 関数からのリターン命令。
    *   `ANOP`: 何もしない（No Operation）命令。
    *   `D_SP`: スタックポインタレジスタ（x86/x86-64では`RSP`/`ESP`）。
    *   `D_AX`: `AX`/`EAX`/`RAX`レジスタ。汎用レジスタとして使用されます。
    *   `D_INDIR`: 間接参照（ポインタの指すアドレス）を示す。
    *   `D_CONST`: 定数。
    *   `D_EXTERN`: 外部シンボル。
    *   `D_ADDR`: アドレス。
*   **データ定義関数**:
    *   `duintxx(Sym *s, int off, uint64 v, int wid)`: シンボル`s`のデータセクションに、オフセット`off`から`wid`バイト幅で`v`の値を書き込む関数。
    *   `dsymptr(Sym *s, int off, Sym *x, int xoff)`: シンボル`s`のデータセクションに、オフセット`off`からシンボル`x`のアドレス（`xoff`オフセット付き）をポインタとして書き込む関数。
*   **`fmt`パッケージの書式指定**:
    *   Goの`fmt`パッケージ（およびコンパイラ内部の型プリンタ）では、`%T`は型の文字列表現を出力します。
    *   `%#T`は、より詳細な（完全な）型の文字列表現を出力します。例えば、パッケージ名を含む完全修飾名など。
    *   `%#-T`は、このコミットで追加された新しいフォーマットで、`%#T`に似ていますが、関数引数の名前を省略します。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラの内部動作、特に型システム、コード生成、およびデバッグ出力の側面に関わっています。

1.  **`genwrapper`と`genembedtramp`のシグネチャ統一**:
    *   以前は、`genwrapper`と`genembedtramp`は異なる引数シグネチャを持っていました。
        *   `genembedtramp(Type *t, Sig *b)`
        *   `genwrapper(Type *rcvrtype, Type *method, Sym *newnam)`
    *   このコミットでは、両者が`genembedtramp(Type *rcvr, Type *method, Sym *newnam)`という統一されたシグネチャを持つように変更されました。
    *   `rcvr`: レシーバの型。
    *   `method`: メソッドの型情報（`TFIELD`型）。
    *   `newnam`: 生成されるラッパー/トランポリン関数の新しいシンボル名。
    *   この統一により、これらの関数を呼び出す側のコード（`dumpsigt`など）が簡素化され、コンパイラ全体の整合性が向上します。また、将来的なリファクタリングや機能追加が容易になります。

2.  **`duintxx`関数の`gc`への移動**:
    *   `duint8`, `duint16`, `duint32`, `duint64`, `duintptr`といった、特定のサイズの符号なし整数をデータセクションに書き込む関数は、元々`src/cmd/6g/gobj.c`と`src/cmd/8g/gobj.c`（アーキテクチャ固有のバックエンド）にそれぞれ実装されていました。
    *   これらの関数は、`duintxx(Sym *s, int off, uint64 v, int wid)`という共通のヘルパー関数を呼び出すだけの薄いラッパーでした。
    *   このコミットでは、これらのラッパー関数が`src/cmd/gc/obj.c`（共通のフロントエンド）に移動されました。
    *   これにより、コードの重複が解消され、各バックエンドは`duintxx`という共通のインターフェースを通じてデータ定義を行えるようになります。これは、コンパイラ設計におけるモジュール性と再利用性の向上に貢献します。

3.  **`genwrapper`の整理**:
    *   `genwrapper`関数は、メソッド呼び出しのためのアセンブリコードを生成します。このコミットでは、`src/cmd/6g/gobj.c`と`src/cmd/8g/gobj.c`の両方で、`genwrapper`の内部ロジックが整理されました。
    *   特に、アセンブリ命令の`AMOVQ`/`AMOVL`と`AADDQ`/`AADDL`を抽象化するために、`mov`と`add`という変数が導入されました。これにより、x86-64（`6g`）とx86（`8g`）で異なる命令セットを使用する際でも、コードの構造を共通化し、可読性を高めることができます。
    *   例えば、`6g`では`mov = AMOVQ; add = AADDQ;`、`8g`では`mov = AMOVL; add = AADDL;`と設定されます。

4.  **構造体フィールドシンボルに関するバグ修正**:
    *   `dsymptr`関数のシグネチャが`int dsymptr(Sym *s, int off, Sym *x)`から`int dsymptr(Sym *s, int off, Sym *x, int xoff)`に変更されました。
    *   新しい引数`xoff`は、シンボル`x`のアドレスに加算されるオフセットを指定します。
    *   この変更は、`src/cmd/gc/obj.c`の`dumpsigt`関数内で、メソッドテーブルエントリを生成する際に`dsymptr`が呼び出される箇所に影響します。
    *   以前は、`dsymptr(s, ot, b->sym)`のように呼び出されており、`b->sym`（メソッドのシンボル）のアドレスがそのまま書き込まれていました。
    *   修正後は、`dsymptr(s, ot, b->sym, 0)`と呼び出され、明示的にオフセットが0であることが示されます。
    *   コミットメッセージによると、このバグは「ハッシュ順序に依存」しており、構造体フィールドシンボルがシグネチャリストに現れる際に問題を引き起こしていました。`xoff`の導入により、アドレスの計算がより正確になり、この種のバグが解消されたと考えられます。ハッシュ順序依存のバグは、コンパイラの内部データ構造の順序が実行ごとに変わることで、特定の条件下でのみ発生するため、デバッグが非常に困難です。

5.  **新しい`Type`プリントフォーマット`%#-T`**:
    *   `src/cmd/gc/subr.c`の`Tconv`関数（型の文字列表現を生成する`fmt`パッケージのカスタムコンバータ）に、新しい書式指定子`%#-T`の処理が追加されました。
    *   `%#T`は型の完全な情報を出力しますが、`%#-T`は関数型の場合に引数名を省略します。
    *   これを実現するために、`noargnames`というグローバル変数が導入されました。`Tconv`が`%#-T`フラグ（`FmtLeft`、つまり`-`フラグ）を検出すると、`noargnames`をインクリメントし、`Tpretty`関数（型の実際の文字列表現を生成する関数）を呼び出します。`Tpretty`は、`noargnames`が設定されている場合、`TFIELD`型の引数（関数引数）の名前を出力しないように動作します。
    *   この機能は、型の比較や、引数名が重要でないデバッグ出力において、より簡潔で読みやすい出力を提供します。例えば、`func(a int, b string)`が`func(int, string)`と表示されるようになります。

### `genembedtramp`と`genwrapper`のシグネチャ統一と実装

このコミットの最も重要な変更点の一つは、`genembedtramp`と`genwrapper`という、Goのメソッドディスパッチにおいて重要な役割を果たす二つの関数のシグネチャが統一されたことです。これにより、コンパイラのコード生成ロジックがより一貫性のあるものになりました。

`genembedtramp`は、埋め込み型（embedded types）のメソッドを呼び出すためのアセンブリコード（トランポリン）を生成します。Goでは、構造体に別の構造体を埋め込むことで、埋め込まれた構造体のメソッドを外側の構造体から直接呼び出すことができます。この際、レシーバのアドレスが異なるため、アドレスを調整する処理が必要になります。`genembedtramp`が生成するコードは、このアドレス調整を行い、最終的に実際のメソッドにジャンプします。

変更後の`genembedtramp`のシグネチャは以下の通りです。

```c
void genembedtramp(Type *rcvr, Type *method, Sym *newnam)
```

*   `rcvr`: メソッドを呼び出すレシーバの型（例: 埋め込みを含む構造体の型）。
*   `method`: 呼び出されるメソッドの型情報（`TFIELD`型）。これにはメソッドのシンボル名が含まれます。
*   `newnam`: 生成されるトランポリン関数のシンボル名。

`genembedtramp`の内部では、`dotlist`というグローバル変数を使って、レシーバ型`rcvr`から`method`へのパス（フィールドの連鎖）を解決します。このパスは、アドレス調整のオフセットを計算するために使用されます。

アセンブリコード生成の核心部分は、スタック上のレシーバポインタを読み込み、必要なオフセットを加算して、最終的に実際のメソッドにジャンプする点です。

```c
    // ...
    mov = AMOVQ; // x86-64の場合
    add = AADDQ; // x86-64の場合
    loaded = 0;
    o = 0; // オフセットの合計
    for(c=d-1; c>=0; c--) { // dotlist を逆順に辿る
        f = dotlist[c].field;
        o += f->width; // フィールドの幅（オフセット）を加算
        if(!isptr[f->type->etype]) // ポインタ型でなければスキップ
            continue;

        if(!loaded) {
            loaded = 1;
            // MOVQ widthptr(SP), AX  (スタックからレシーバポインタをAXにロード)
            p = pc;
            gins(mov, N, N);
            p->from.type = D_INDIR+D_SP;
            p->from.offset = widthptr; // スタック上のレシーバポインタのオフセット
            p->to.type = D_AX;
        }

        // MOVQ o(AX), AX (AXにロードされたポインタにオフセットoを加算し、そのアドレスの値をAXにロード)
        p = pc;
        gins(mov, N, N);
        p->from.type = D_INDIR+D_AX;
        p->from.offset = o;
        p->to.type = D_AX;
    }

    if(o != 0) {
        // ADDQ $XX, AX (最終的なオフセットをAXに加算)
        p = pc;
        gins(add, N, N);
        p->from.type = D_CONST;
        p->from.offset = o;
        if(loaded)
            p->to.type = D_AX;
        else {
            p->to.type = D_INDIR+D_SP;
            p->to.offset = widthptr;
        }
    }

    if(loaded) {
        // MOVQ AX, widthptr(SP) (調整されたポインタをスタックに戻す)
        p = pc;
        gins(mov, N, N);
        p->from.type = D_AX;
        p->to.type = D_INDIR+D_SP;
        p->to.offset = widthptr;
    } else {
        // NOP (6l のバグ回避のためのパディング)
        p = pc;
        gins(ANOP, N, N);
    }

    // JMP methodsym(method->sym, ptrto(f->type)) (実際のメソッドにジャンプ)
    p = pc;
    gins(AJMP, N, N);
    p->to.type = D_EXTERN;
    p->to.sym = methodsym(method->sym, ptrto(f->type));
    pc->as = ARET; // AEND を上書き
```

このコードは、スタックからレシーバポインタを読み込み、埋め込みフィールドのオフセットを繰り返し加算して、最終的なレシーバのアドレスを計算します。そして、その調整されたアドレスをスタックに戻し、目的のメソッドにジャンプします。`mov`と`add`変数の導入により、x86-64とx86の両方で共通のロジックでコードを生成できるようになりました。

### 新しい`Type`プリントフォーマット`%#-T`

`src/cmd/gc/subr.c`の`Tconv`と`Tpretty`関数は、Goの型を文字列として表現する役割を担っています。このコミットで追加された`%#-T`フォーマットは、関数型の引数名を省略して出力する機能を提供します。

`Tconv`関数は、`fmt`パッケージのカスタムコンバータとして機能し、書式指定子（例: `%T`, `%#T`, `%#-T`）を解析します。

```c
int Tconv(Fmt *fp) {
    // ...
    sharp = (fp->flags & FmtSharp); // '#' フラグを検出
    minus = (fp->flags & FmtLeft);  // '-' フラグを検出 (これが %#-T の '-' に対応)
    fp->flags &= ~(FmtSharp|FmtLeft); // 処理後、フラグをクリア

    if(!debug['t']) {
        if(sharp)
            exporting++;
        if(minus)
            noargnames++; // '-' フラグがあれば noargnames をセット
        r = Tpretty(fp, t); // Tpretty を呼び出し
        if(sharp)
            exporting--;
        if(minus)
            noargnames--; // 処理後、noargnames をクリア
        if(r >= 0) {
            t->trecur--;
            return 0;
        }
    }
    // ...
}
```

`Tconv`は、`FmtLeft`フラグ（`%#-T`の`-`部分）がセットされている場合、グローバル変数`noargnames`をインクリメントします。そして、実際の型の文字列表現を生成する`Tpretty`関数を呼び出します。

`Tpretty`関数は、`noargnames`の値を見て、関数引数の名前を出力するかどうかを決定します。

```c
void Tpretty(Fmt *fp, Type *t) {
    // ...
    case TFUNC:
        // ...
        for(t1=getinargx(t)->type; t1; t1=t1->down) {
            if(noargnames && t1->etype == TFIELD) // noargnames がセットされており、かつ TFIELD (引数) の場合
                fmtprint(fp, "%T", t1->type); // 引数名を省略し、型のみを出力
            else
                fmtprint(fp, "%T", t1); // 通常通り引数名と型を出力
            if(t1->down)
                fmtprint(fp, ", ");
        }
        // ...
}
```

このロジックにより、`%#-T`が指定された場合、`Tpretty`は関数引数が`TFIELD`型（つまり、名前を持つ引数）であるときに、その引数名を出力せずに型情報のみを出力するようになります。これにより、`func(a int, b string)`のような型が`func(int, string)`と表示され、型の比較やデバッグ出力がより簡潔になります。

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われたもので、当時のGoコンパイラ（主に`gc`、`6g`、`8g`など）の成熟度を高めるための重要なステップでした。

2.  **型システムの改善とデバッグ**: Goの型システムは、言語の安全性と表現力の核となる部分です。型の内部表現や文字列表現は、コンパイラのデバッグ、エラーメッセージの生成、そしてリフレクションなどのランタイム機能にとって非常に重要ですす。新しい`%#-T`フォーマットの追加は、型のデバッグ出力の柔軟性を高めることを目的としています。
3.  **メソッドディスパッチの最適化と正確性**: Goのインターフェースとメソッドは、動的なディスパッチを伴います。`genwrapper`と`genembedtramp`は、この動的なディスパッチを効率的に行うためのアセンブリコードを生成する役割を担っていました。これらの関数のシグネチャ統一やバグ修正は、メソッド呼び出しの正確性とパフォーマンスを確保するために不可欠でした。特に、埋め込み型（embedded types）のメソッド解決は複雑であり、そのためのトランポリン（`genembedtramp`）の正確な生成が求められました。
4.  **バグの修正**: ハッシュ順序に依存するバグは、再現が困難であり、コンパイラの信頼性を損なう可能性があります。このようなバグを早期に発見し修正することは、言語の安定性にとって極めて重要でした。

これらの変更は、Goコンパイラの内部構造をより堅牢で、保守しやすく、効率的なものにするための継続的な取り組みの一部でした。

このコミットを理解するためには、以下のGoコンパイラおよびGo言語の基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (6g/8g/gc)**:
    *   **`gc` (Go Compiler)**: Go言語の主要なコンパイラコレクションのフロントエンド部分。ソースコードの字句解析、構文解析、型チェック、中間表現（IR）の生成など、アーキテクチャ非依存の処理を担当します。
    *   **`6g` (Go Compiler for x86-64)**: `gc`のバックエンドの一つで、x86-64アーキテクチャ向けの機械語コードを生成します。
    *   **`8g` (Go Compiler for x86)**: `gc`のバックエンドの一つで、x86アーキテクチャ向けの機械語コードを生成します。
    *   当時のGoコンパイラは、Plan 9 C言語で書かれており、アセンブラコードの生成もC言語のコード内で行われることが多かったです。
*   **型システム (`Type`構造体)**:
    *   Goコンパイラ内部では、Go言語の各型が`Type`という構造体で表現されます。この構造体には、型の種類（`etype`）、サイズ、フィールド情報などが含まれます。
    *   `etype`: `Type`構造体のフィールドで、型の基本的な種類（例: `TINT`、`TFUNC`、`TSTRUCT`、`TARRAY`など）を示します。
    *   `TFIELD`: 構造体のフィールドを表す特別な型。フィールド名、型、オフセットなどを含みます。
    *   `TFUNC`: 関数型を表す。引数と戻り値の型情報を含みます。
*   **シンボル (`Sym`構造体)**:
    *   コンパイラが扱う変数名、関数名、型名などの識別子は、内部的に`Sym`（シンボル）構造体で表現されます。シンボルは、その名前、型、定義されているスコープなどの情報を持っています。
*   **メソッドディスパッチとインターフェース**:
    *   Go言語のインターフェースは、動的なメソッド呼び出しを可能にします。インターフェース型の変数に具体的な型の値が代入されると、その値のメソッドが実行時に解決されます。
    *   **`genwrapper`**: 特定の型（レシーバ型）のメソッドを呼び出すためのラッパー関数（アセンブリコード）を生成します。これは、主にインターフェースメソッドの呼び出しや、メソッド値（method value）の生成に使用されます。
    *   **`genembedtramp`**: 埋め込み型（embedded types）のメソッドを呼び出すための「トランポリン」関数（アセンブリコード）を生成します。埋め込み型を通じてアクセスされるメソッドは、レシーバのアドレスを調整する必要があるため、このトランポリンがその役割を担います。
*   **アセンブラ命令 (x86/x86-64)**:
    *   Goコンパイラは、最終的にターゲットアーキテクチャのアセンブリコードを生成します。
    *   `AMOVQ` (Move Quadword): 64ビット値を移動する命令（x86-64）。
    *   `AMOVL` (Move Long): 32ビット値を移動する命令（x86）。
    *   `AADDQ` (Add Quadword): 64ビット値を加算する命令（x86-64）。
    *   `AADDL` (Add Long): 32ビット値を加算する命令（x86）。
    *   `ATEXT`: 関数の開始を示すディレクティブ。
    *   `AJMP`: 無条件ジャンプ命令。
    *   `ARET`: 関数からのリターン命令。
    *   `ANOP`: 何もしない（No Operation）命令。
    *   `D_SP`: スタックポインタレジスタ（x86/x86-64では`RSP`/`ESP`）。
    *   `D_AX`: `AX`/`EAX`/`RAX`レジスタ。汎用レジスタとして使用されます。
    *   `D_INDIR`: 間接参照（ポインタの指すアドレス）を示す。
    *   `D_CONST`: 定数。
    *   `D_EXTERN`: 外部シンボル。
    *   `D_ADDR`: アドレス。
*   **データ定義関数**:
    *   `duintxx(Sym *s, int off, uint64 v, int wid)`: シンボル`s`のデータセクションに、オフセット`off`から`wid`バイト幅で`v`の値を書き込む関数。
    *   `dsymptr(Sym *s, int off, Sym *x, int xoff)`: シンボル`s`のデータセクションに、オフセット`off`からシンボル`x`のアドレス（`xoff`オフセット付き）をポインタとして書き込む関数。
*   **`fmt`パッケージの書式指定**:
    *   Goの`fmt`パッケージ（およびコンパイラ内部の型プリンタ）では、`%T`は型の文字列表現を出力します。
    *   `%#T`は、より詳細な（完全な）型の文字列表現を出力します。例えば、パッケージ名を含む完全修飾名など。
    *   `%#-T`は、このコミットで追加された新しいフォーマットで、`%#T`に似ていますが、関数引数の名前を省略します。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラの内部動作、特に型システム、コード生成、およびデバッグ出力の側面に関わっています。

1.  **`genwrapper`と`genembedtramp`のシグネチャ統一**:
    *   以前は、`genwrapper`と`genembedtramp`は異なる引数シグネチャを持っていました。
        *   `genembedtramp(Type *t, Sig *b)`
        *   `genwrapper(Type *rcvrtype, Type *method, Sym *newnam)`
    *   このコミットでは、両者が`genembedtramp(Type *rcvr, Type *method, Sym *newnam)`という統一されたシグネチャを持つように変更されました。
    *   `rcvr`: メソッドを呼び出すレシーバの型。
    *   `method`: 呼び出されるメソッドの型情報（`TFIELD`型）。
    *   `newnam`: 生成されるラッパー/トランポリン関数の新しいシンボル名。
    *   この統一により、これらの関数を呼び出す側のコード（`dumpsigt`など）が簡素化され、コンパイラ全体の整合性が向上します。また、将来的なリファクタリングや機能追加が容易になります。

2.  **`duintxx`関数の`gc`への移動**:
    *   `duint8`, `duint16`, `duint32`, `duint64`, `duintptr`といった、特定のサイズの符号なし整数をデータセクションに書き込む関数は、元々`src/cmd/6g/gobj.c`と`src/cmd/8g/gobj.c`（アーキテクチャ固有のバックエンド）にそれぞれ実装されていました。
    *   これらの関数は、`duintxx(Sym *s, int off, uint64 v, int wid)`という共通のヘルパー関数を呼び出すだけの薄いラッパーでした。
    *   このコミットでは、これらのラッパー関数が`src/cmd/gc/obj.c`（共通のフロントエンド）に移動されました。
    *   これにより、コードの重複が解消され、各バックエンドは`duintxx`という共通のインターフェースを通じてデータ定義を行えるようになります。これは、コンパイラ設計におけるモジュール性と再利用性の向上に貢献します。

3.  **`genwrapper`の整理**:
    *   `genwrapper`関数は、メソッド呼び出しのためのアセンブリコードを生成します。このコミットでは、`src/cmd/6g/gobj.c`と`src/cmd/8g/gobj.c`の両方で、`genwrapper`の内部ロジックが整理されました。
    *   特に、アセンブリ命令の`AMOVQ`/`AMOVL`と`AADDQ`/`AADDL`を抽象化するために、`mov`と`add`という変数が導入されました。これにより、x86-64（`6g`）とx86（`8g`）で異なる命令セットを使用する際でも、コードの構造を共通化し、可読性を高めることができます。
    *   例えば、`6g`では`mov = AMOVQ; add = AADDQ;`、`8g`では`mov = AMOVL; add = AADDL;`と設定されます。

4.  **構造体フィールドシンボルに関するバグ修正**:
    *   `dsymptr`関数のシグネチャが`int dsymptr(Sym *s, int off, Sym *x)`から`int dsymptr(Sym *s, int off, Sym *x, int xoff)`に変更されました。
    *   新しい引数`xoff`は、シンボル`x`のアドレスに加算されるオフセットを指定します。
    *   この変更は、`src/cmd/gc/obj.c`の`dumpsigt`関数内で、メソッドテーブルエントリを生成する際に`dsymptr`が呼び出される箇所に影響します。
    *   以前は、`dsymptr(s, ot, b->sym)`のように呼び出されており、`b->sym`（メソッドのシンボル）のアドレスがそのまま書き込まれていました。
    *   修正後は、`dsymptr(s, ot, b->sym, 0)`と呼び出され、明示的にオフセットが0であることが示されます。
    *   コミットメッセージによると、このバグは「ハッシュ順序に依存」しており、構造体フィールドシンボルがシグネチャリストに現れる際に問題を引き起こしていました。`xoff`の導入により、アドレスの計算がより正確になり、この種のバグが解消されたと考えられます。ハッシュ順序依存のバグは、コンパイラの内部データ構造の順序が実行ごとに変わることで、特定の条件下でのみ発生するため、デバッグが非常に困難です。

5.  **新しい`Type`プリントフォーマット`%#-T`**:
    *   `src/cmd/gc/subr.c`の`Tconv`関数（型の文字列表現を生成する`fmt`パッケージのカスタムコンバータ）に、新しい書式指定子`%#-T`の処理が追加されました。
    *   `%#T`は型の完全な情報を出力しますが、`%#-T`は関数型の場合に引数名を省略します。
    *   これを実現するために、`noargnames`というグローバル変数が導入されました。`Tconv`が`%#-T`フラグ（`FmtLeft`、つまり`-`フラグ）を検出すると、`noargnames`をインクリメントし、`Tpretty`関数（型の実際の文字列表現を生成する関数）を呼び出します。`Tpretty`は、`noargnames`が設定されている場合、`TFIELD`型の引数（関数引数）の名前を出力しないように動作します。
    *   この機能は、型の比較や、引数名が重要でないデバッグ出力において、より簡潔で読みやすい出力を提供します。例えば、`func(a int, b string)`が`func(int, string)`と表示されるようになります。

## コアとなるコードの解説

### `genembedtramp`と`genwrapper`のシグネチャ統一と実装

このコミットの最も重要な変更点の一つは、`genembedtramp`と`genwrapper`という、Goのメソッドディスパッチにおいて重要な役割を果たす二つの関数のシグネチャが統一されたことです。これにより、コンパイラのコード生成ロジックがより一貫性のあるものになりました。

`genembedtramp`は、埋め込み型（embedded types）のメソッドを呼び出すためのアセンブリコード（トランポリン）を生成します。Goでは、構造体に別の構造体を埋め込むことで、埋め込まれた構造体のメソッドを外側の構造体から直接呼び出すことができます。この際、レシーバのアドレスが異なるため、アドレスを調整する処理が必要になります。`genembedtramp`が生成するコードは、このアドレス調整を行い、最終的に実際のメソッドにジャンプします。

変更後の`genembedtramp`のシグネチャは以下の通りです。

```c
void genembedtramp(Type *rcvr, Type *method, Sym *newnam)
```

*   `rcvr`: メソッドを呼び出すレシーバの型（例: 埋め込みを含む構造体の型）。
*   `method`: 呼び出されるメソッドの型情報（`TFIELD`型）。これにはメソッドのシンボル名が含まれます。
*   `newnam`: 生成されるトランポリン関数のシンボル名。

`genembedtramp`の内部では、`dotlist`というグローバル変数を使って、レシーバ型`rcvr`から`method`へのパス（フィールドの連鎖）を解決します。このパスは、アドレス調整のオフセットを計算するために使用されます。

アセンブリコード生成の核心部分は、スタック上のレシーバポインタを読み込み、必要なオフセットを加算して、最終的に実際のメソッドにジャンプする点です。

```c
    // ...
    mov = AMOVQ; // x86-64の場合
    add = AADDQ; // x86-64の場合
    loaded = 0;
    o = 0; // オフセットの合計
    for(c=d-1; c>=0; c--) { // dotlist を逆順に辿る
        f = dotlist[c].field;
        o += f->width; // フィールドの幅（オフセット）を加算
        if(!isptr[f->type->etype]) // ポインタ型でなければスキップ
            continue;

        if(!loaded) {
            loaded = 1;
            // MOVQ widthptr(SP), AX  (スタックからレシーバポインタをAXにロード)
            p = pc;
            gins(mov, N, N);
            p->from.type = D_INDIR+D_SP;
            p->from.offset = widthptr; // スタック上のレシーバポインタのオフセット
            p->to.type = D_AX;
        }

        // MOVQ o(AX), AX (AXにロードされたポインタにオフセットoを加算し、そのアドレスの値をAXにロード)
        p = pc;
        gins(mov, N, N);
        p->from.type = D_INDIR+D_AX;
        p->from.offset = o;
        p->to.type = D_AX;
    }

    if(o != 0) {
        // ADDQ $XX, AX (最終的なオフセットをAXに加算)
        p = pc;
        gins(add, N, N);
        p->from.type = D_CONST;
        p->from.offset = o;
        if(loaded)
            p->to.type = D_AX;
        else {
            p->to.type = D_INDIR+D_SP;
            p->to.offset = widthptr;
        }
    }

    if(loaded) {
        // MOVQ AX, widthptr(SP) (調整されたポインタをスタックに戻す)
        p = pc;
        gins(mov, N, N);
        p->from.type = D_AX;
        p->to.type = D_INDIR+D_SP;
        p->to.offset = widthptr;
    } else {
        // NOP (6l のバグ回避のためのパディング)
        p = pc;
        gins(ANOP, N, N);
    }

    // JMP methodsym(method->sym, ptrto(f->type)) (実際のメソッドにジャンプ)
    p = pc;
    gins(AJMP, N, N);
    p->to.type = D_EXTERN;
    p->to.sym = methodsym(method->sym, ptrto(f->type));
    pc->as = ARET; // AEND を上書き
```

このコードは、スタックからレシーバポインタを読み込み、埋め込みフィールドのオフセットを繰り返し加算して、最終的なレシーバのアドレスを計算します。そして、その調整されたアドレスをスタックに戻し、目的のメソッドにジャンプします。`mov`と`add`変数の導入により、x86-64とx86の両方で共通のロジックでコードを生成できるようになりました。

### 新しい`Type`プリントフォーマット`%#-T`

`src/cmd/gc/subr.c`の`Tconv`と`Tpretty`関数は、Goの型を文字列として表現する役割を担っています。このコミットで追加された`%#-T`フォーマットは、関数型の引数名を省略して出力する機能を提供します。

`Tconv`関数は、`fmt`パッケージのカスタムコンバータとして機能し、書式指定子（例: `%T`, `%#T`, `%#-T`）を解析します。

```c
int Tconv(Fmt *fp) {
    // ...
    sharp = (fp->flags & FmtSharp); // '#' フラグを検出
    minus = (fp->flags & FmtLeft);  // '-' フラグを検出 (これが %#-T の '-' に対応)
    fp->flags &= ~(FmtSharp|FmtLeft); // 処理後、フラグをクリア

    if(!debug['t']) {
        if(sharp)
            exporting++;
        if(minus)
            noargnames++; // '-' フラグがあれば noargnames をセット
        r = Tpretty(fp, t); // Tpretty を呼び出し
        if(sharp)
            exporting--;
        if(minus)
            noargnames--; // 処理後、noargnames をクリア
        if(r >= 0) {
            t->trecur--;
            return 0;
        }
    }
    // ...
}
```

`Tconv`は、`FmtLeft`フラグ（`%#-T`の`-`部分）がセットされている場合、グローバル変数`noargnames`をインクリメントします。そして、実際の型の文字列表現を生成する`Tpretty`関数を呼び出します。

`Tpretty`関数は、`noargnames`の値を見て、関数引数の名前を出力するかどうかを決定します。

```c
void Tpretty(Fmt *fp, Type *t) {
    // ...
    case TFUNC:
        // ...
        for(t1=getinargx(t)->type; t1; t1=t1->down) {
            if(noargnames && t1->etype == TFIELD) // noargnames がセットされており、かつ TFIELD (引数) の場合
                fmtprint(fp, "%T", t1->type); // 引数名を省略し、型のみを出力
            else
                fmtprint(fp, "%T", t1); // 通常通り引数名と型を出力
            if(t1->down)
                fmtprint(fp, ", ");
        }
        // ...
}
```

このロジックにより、`%#-T`が指定された場合、`Tpretty`は関数引数が`TFIELD`型（つまり、名前を持つ引数）であるときに、その引数名を出力せずに型情報のみを出力するようになります。これにより、`func(a int, b string)`のような型が`func(int, string)`と表示され、型の比較やデバッグ出力がより簡潔になります。

# [インデックス 21225] ファイルの概要

このコミットは、Goランタイムの内部ファイルである `src/runtime/proc1.go` に関連するものです。`proc1.go` は、Goランタイムの初期化プロセス、特にOSスレッド（M）の管理やスケジューラの初期設定に関連する低レベルな処理を担っています。

## コミット

```
runtime: restore error message on early needm

needm used to print an error before exiting when it was called too
early, but this error was lost in the transition to Go. Bring back
the error so we don't silently exit(1) when this happens.

Change-Id: I8086932783fd29a337d7dea31b9d6facb64cb5c1
Reviewed-on: https://go-review.googlesource.com/1226
Reviewed-by: Russ Cox <rsc@golang.org>
```

[https://github.com/golang/go/commit/76f71959c860cbd36c52d789d82914d8c2e300c9](https://github.com/golang/go/commit/76f71959c860cbd36c52d789d82914d8c2e300c9)

## 元コミット内容

このコミットの目的は、Goランタイムがまだ完全に初期化されていない段階で `needm` 関数が呼び出された際に、エラーメッセージを出力してから終了するように修正することです。以前はエラーメッセージが出力されていましたが、Goへの移行の過程でこのメッセージが失われ、サイレントにプログラムが終了（`exit(1)`）する問題が発生していました。この変更は、そのエラーメッセージを復活させることを目的としています。

## 変更の背景

Goランタイムは、プログラムの実行前に様々な初期化処理を行います。これには、メモリ管理、ガベージコレクション、スケジューラのセットアップなどが含まれます。`needm` 関数は、GoランタイムがOSスレッド（M）を必要とする際に呼び出される内部関数であり、特にCgo（GoとC言語の相互運用機能）のコールバック処理において重要な役割を果たします。

問題は、C/C++のグローバルコンストラクタなど、Goランタイムがまだ完全に初期化されていない非常に早い段階で、Cgoを介してGoの関数が呼び出される（いわゆる「cgo callback before cgo call」）場合に発生していました。このような状況では、Goのスケジューラがまだ準備できていないため、Goのコードを安全に実行できません。

以前のGoのバージョンでは、このような早期の `needm` 呼び出しが発生した場合に、エラーメッセージを標準エラー出力（stderr）に表示してからプログラムを終了していました。しかし、Goランタイムの内部実装がGo言語に移行する過程で、この重要なエラーメッセージの出力が失われてしまいました。その結果、問題が発生してもユーザーには何も表示されず、プログラムが突然終了する（`exit(1)`）という、デバッグが非常に困難な状況が生じていました。

このコミットは、このサイレントな終了という問題を解決し、開発者が早期のCgoコールバックの問題を迅速に特定できるように、エラーメッセージの出力を復活させることを目的としています。

## 前提知識の解説

### Goランタイムの初期化プロセス
Goプログラムが実行される際、`main()` 関数が呼び出される前に、Goランタイムは複雑な初期化プロセスを実行します。これには以下の主要なステップが含まれます。
1.  **低レベルな初期化**: OSスレッド（M）のセットアップ、メモリ管理（ヒープとスタック）、CPUの初期化など、OSに依存する基本的な設定が行われます。
2.  **スケジューラの初期化**: Goの並行処理を司るスケジューラ（G-M-Pモデル）が設定されます。GはGoroutine、MはOSスレッド、Pはプロセッサ（論理CPU）を表します。スケジューラは、多数のGoroutineを少数のOSスレッドに効率的にマッピングし、実行を管理します。
3.  **パッケージの初期化**: インポートされたすべてのパッケージの`init()`関数が実行されます。
これらの初期化が完了して初めて、Goのコードは安全に実行できる状態になります。

### `needm` 関数
`needm` はGoランタイムの内部関数で、Goのコードを実行するためにOSスレッド（M）が必要な場合に呼び出されます。特に、Cgoを介してCコードからGoコードが呼び出される（Cgoコールバック）際に、GoランタイムはGoroutineを実行するためにMを確保する必要があります。もしスケジューラがまだ初期化されていない段階で `needm` が呼び出されると、Goの実行環境が整っていないため、問題が発生します。

### Cgoと「cgo callback before cgo call」エラー
CgoはGoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。
*   **GoからCへの呼び出し**: GoコードがCの関数を呼び出す場合、GoのGoroutineは一時的にOSスレッドをブロックし、Cのコードを実行します。Goランタイムは、このブロックを検知して、他のGoroutineを実行するために新しいOSスレッドを起動することができます。
*   **CからGoへのコールバック**: `//export` ディレクティブを使用することで、Goの関数をC言語から呼び出せるようにエクスポートできます。
「fatal error: cgo callback before cgo call」というエラーは、C/C++の静的コンストラクタ（`main`関数が実行されるよりも非常に早い段階で実行されるコード）が、Goランタイムがまだ完全に初期化されていない状態で、エクスポートされたGo関数を呼び出そうとした場合に発生します。この状況では、Goのスケジューラやその他のランタイムコンポーネントが準備できていないため、Goコードの実行は安全ではありません。

### `exit(1)`
`exit(1)` は、プログラムが異常終了したことを示すために使用される一般的なシステムコールです。通常、`0` は正常終了を意味し、非ゼロの値はエラーを示します。このコミットの背景では、エラーメッセージなしに `exit(1)` が行われることが問題視されていました。

### `write(2)` システムコールと `unsafe.Pointer`
`write(2)` はUnix系システムにおけるシステムコールの一つで、指定されたファイルディスクリプタにデータを書き込みます。ファイルディスクリプタ `2` は通常、標準エラー出力（stderr）を指します。
`unsafe.Pointer` はGoの `unsafe` パッケージで提供される型で、任意の型のポインタを保持できます。これにより、型安全性をバイパスして、異なる型のポインタ間で変換を行ったり、ポインタ演算を行ったりすることが可能になります。Goランタイムの低レベルな部分では、OSのシステムコールを直接呼び出すために `unsafe.Pointer` が使用されることがあります。このコミットでは、バイトスライスのアドレスを `write` システムコールが期待するポインタ型に変換するために使用されています。

## 技術的詳細

このコミットは、Goランタイムの `src/runtime/proc1.go` ファイル内の `needm` 関数におけるエラーハンドリングを改善します。

`needm` 関数は、GoランタイムがOSスレッド（M）を必要とする際に呼び出されます。特に、Cgoを介してC/C++コードからGoコードが呼び出される場合（Cgoコールバック）、GoランタイムはGoroutineを実行するためにMを確保しようとします。

コミット前のコードでは、`needextram != 0` の条件が真の場合（これは、Goランタイムがまだ完全に初期化されていない、非常に早い段階でCgoコールバックが発生したことを示唆しています）、コメントアウトされた `write` システムコールの呼び出しと、その後に続く `exit(1)` がありました。コメントアウトされた行は、以前のバージョンでエラーメッセージを出力していた痕跡です。

```go
// write(2, unsafe.Pointer("fatal error: cgo callback before cgo call\n"), sizeof("fatal error: cgo callback before cgo call\n") - 1)
exit(1)
```

この状態では、エラーメッセージが出力されずにプログラムが `exit(1)` で終了するため、開発者は何が問題だったのかを把握できませんでした。

このコミットは、この問題を解決するために、コメントアウトされていた `write` システムコールの呼び出しを復活させ、さらに出力するメッセージをグローバル変数 `earlycgocallback` として定義することで、コードの可読性と保守性を向上させています。

具体的には、以下の変更が行われました。
1.  `write(2, unsafe.Pointer(&earlycgocallback[0]), int32(len(earlycgocallback)))` という行が追加されました。これは、ファイルディスクリプタ `2`（標準エラー出力）に、`earlycgocallback` バイトスライスの内容を書き込むシステムコールです。
2.  `var earlycgocallback = []byte("fatal error: cgo callback before cgo call\\n")` という新しいグローバル変数が定義されました。この変数は、出力すべきエラーメッセージをバイトスライスとして保持します。

これにより、Goランタイムがまだ初期化されていない段階でCgoコールバックが発生した場合、`"fatal error: cgo callback before cgo call\n"` というメッセージが標準エラー出力に表示され、その後プログラムが `exit(1)` で終了するようになります。これにより、開発者は問題の原因を明確に把握できるようになり、デバッグが容易になります。

`unsafe.Pointer` は、バイトスライスの先頭アドレスを `write` システムコールが期待するポインタ型に変換するために使用されています。これはGoの型安全性をバイパスする操作ですが、ランタイムの低レベルな部分でOSのシステムコールを直接扱う際には必要となる場合があります。

## コアとなるコードの解説

### `write(2, unsafe.Pointer(&earlycgocallback[0]), int32(len(earlycgocallback)))`
この行は、Goランタイムがまだ完全に初期化されていない状態で `needm` が呼び出された場合に実行されます。
*   `write`: これはGoランタイム内部で定義されている `write` システムコールへのラッパー関数です。
*   `2`: これはファイルディスクリプタで、標準エラー出力（stderr）を指します。エラーメッセージはここに書き込まれます。
*   `unsafe.Pointer(&earlycgocallback[0])`: `earlycgocallback` はバイトスライスです。`&earlycgocallback[0]` はそのバイトスライスの最初の要素のアドレスを取得します。`unsafe.Pointer` を使用することで、このアドレスを `write` システムコールが期待する汎用ポインタ型に変換しています。これにより、Goの型システムを一時的にバイパスして、低レベルなメモリ操作を可能にしています。
*   `int32(len(earlycgocallback))`: `earlycgocallback` バイトスライスの長さを `int32` 型にキャストしています。これは、`write` システムコールに書き込むバイト数を伝えます。

この行全体で、「fatal error: cgo callback before cgo call\n」というメッセージが標準エラー出力に書き込まれることになります。

### `var earlycgocallback = []byte("fatal error: cgo callback before cgo call\\n")`
この行は、Goランタイムのグローバルスコープで `earlycgocallback` という名前のバイトスライス変数を宣言し、初期化しています。
*   `[]byte`: この変数がバイトスライスであることを示します。
*   `"fatal error: cgo callback before cgo call\\n"`: この文字列リテラルがバイトスライスとして格納されます。`\n` は改行文字です。

この変数を導入することで、エラーメッセージの文字列がコード内に直接ハードコードされるのではなく、独立した変数として管理されるようになり、コードの可読性と将来的な変更の容易さが向上しています。

## 元コミット内容

Goのコンパイラとランタイムにおいて、静的なGoの名前（型名、フィールド名、メソッド名、構造体タグなど）の新しいバイトエンコーディングを導入します。このエンコーディングは、名前とオプションのタグデータをコンパクトに表現し、実行時に追加のメモリ割り当てなしでGoの文字列に変換できることを目指しています。また、Unicodeテーブルを使用せずに、その名前がエクスポートされているかどうかを記述します。

エンコーディングの詳細は `reflect/type.go` に記述されており、以下の構造を持ちます。
*   最初の1バイトはビットフィールドで、以下の情報を含みます。
    *   `1<<0`: 名前がエクスポートされているか
    *   `1<<1`: 名前の後にタグデータが続くか
    *   `1<<2`: 名前の後に `pkgPath *string` が続くか
*   次の2バイトはデータ長 `l` を示します (`uint16(data[1])<<8 | uint16(data[2])`)。
*   バイト `[3:3+l]` が文字列データです。
*   タグデータが続く場合、バイト `3+l` と `3+l+1` がタグの長さを示し、その後にタグデータが続きます。
*   インポートパスが続く場合、データの末尾に `ptrSize` バイトで `*string` 形式のインポートパスが格納されます。これは、型とは異なるパッケージで定義された具象メソッドに対してのみ設定されます。

この変更により、バイナリサイズが削減されます。
*   `cmd/go`: 164KB (1.6%)
*   `jujud`: 1.0MB (1.5%)

関連するIssueは #6853 です。

## 変更の背景

Go言語のバイナリサイズは、特に組み込みシステムやクラウド環境でのデプロイにおいて重要な考慮事項です。Goの `reflect` パッケージは、実行時に型情報を検査・操作するために広範なメタデータを使用します。このメタデータには、型名、フィールド名、メソッド名、構造体タグなどが含まれます。これらの名前が従来のGo文字列として格納される場合、文字列の長さや数に応じてバイナリサイズが肥大化する可能性があります。

特に、Goの型システムでは、エクスポートされていない（非公開の）フィールドやメソッドは、その定義元のパッケージパスと組み合わせて一意に識別される必要があります。これにより、異なるパッケージで同じ名前の非公開要素が存在しても衝突しないようになっています。しかし、このパッケージパス情報も文字列として格納されるため、さらにバイナリサイズを増加させる要因となっていました。

このコミットの背景にあるIssue #6853 は、Goのバイナリサイズを削減するための取り組みの一環として、特にリフレクション関連のメタデータにおける名前の格納方法の最適化を目的としています。従来の `*string` を直接使用する方法では、文字列ごとにポインタと文字列データが別々に存在し、メモリ効率が悪く、また文字列の比較や操作のたびにメモリ割り当てが発生する可能性がありました。

新しいエンコーディングは、これらの名前と関連するメタデータ（エクスポート状態、タグ、パッケージパス）を単一のコンパクトなバイト列として表現することで、メモリフットプリントを削減し、バイナリサイズを縮小することを目指しています。また、このバイト列からGo文字列を生成する際に、既存のメモリ領域を直接参照することで、追加のメモリ割り当てを避ける「ゼロアロケーション」を実現することも重要な目標です。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部動作と概念に関する知識が必要です。

1.  **Goのリフレクション (`reflect` パッケージ)**:
    *   Goの `reflect` パッケージは、プログラムの実行時に型情報（`Type`）、値（`Value`）、関数などを検査・操作するための機能を提供します。
    *   `reflect.Type` はGoの型の抽象表現であり、その内部には型名、フィールド、メソッドなどの詳細情報が含まれています。
    *   これらの情報は、コンパイル時に生成され、バイナリに埋め込まれます。

2.  **Goの型システムとメタデータ**:
    *   Goの各型は、ランタイム内部で `_type` (または `rtype`) という構造体で表現されます。
    *   構造体のフィールド、インターフェースのメソッド、具象型のメソッドなどには、それぞれ名前、型、パッケージパスなどのメタデータが付随します。
    *   **エクスポートされた名前と非エクスポートされた名前**: Goでは、識別子（変数、関数、型、フィールド、メソッドなど）の最初の文字が大文字であればエクスポートされ（公開）、小文字であれば非エクスポート（非公開）となります。非エクスポートされた識別子は、その定義元のパッケージ内でのみ直接アクセス可能です。
    *   **パッケージパス**: 非エクスポートされた識別子をグローバルに一意に識別するために、その識別子の名前と定義元のパッケージのインポートパスが組み合わせて使用されます。例えば、`my/package.myField` のようになります。

3.  **Goのバイナリ構造とリンカ (`cmd/link`)**:
    *   Goのコンパイラ (`cmd/compile`) は、Goのソースコードを中間表現に変換し、最終的にオブジェクトファイル（`.o`）を生成します。
    *   リンカ (`cmd/link`) は、これらのオブジェクトファイルと標準ライブラリを結合して実行可能なバイナリを生成します。
    *   この過程で、リフレクションに必要な型情報や文字列定数などもバイナリのデータセクションに配置されます。

4.  **メモリ割り当てとゼロアロケーション**:
    *   Goでは、`string` 型は読み取り専用のバイトスライスと長さを保持する構造体です。
    *   新しい文字列を生成するたびに、ヒープメモリが割り当てられる可能性があります。
    *   「ゼロアロケーション」とは、ヒープメモリの割り当てを避けることで、ガベージコレクションの負荷を減らし、パフォーマンスを向上させる最適化手法です。既存のバイトスライスを直接参照して文字列を構築できれば、新しいメモリ割り当ては不要になります。

5.  **`unsafe` パッケージ**:
    *   Goの `unsafe` パッケージは、Goの型システムを迂回してメモリを直接操作する機能を提供します。
    *   `unsafe.Pointer` は、任意の型のポインタと `uintptr` の間で変換可能であり、型安全性を損なう代わりに低レベルなメモリ操作を可能にします。
    *   このコミットでは、バイト列から直接 `string` ヘッダを構築するために `unsafe` パッケージが利用されています。

## 技術的詳細

このコミットの核心は、Goのランタイムとリフレクションシステムが使用する名前の表現方法を、従来の `*string` から、よりコンパクトで効率的なカスタムバイトエンコーディング `name` 型に置き換えることです。

### 新しい `name` 型の導入

`reflect/type.go` と `runtime/type.go` の両方に `name` という新しい構造体が導入されました。この `name` 型は、名前の文字列データ、エクスポート状態、構造体タグ、そしてオプションでパッケージパスを単一のバイト列として格納します。

`type name struct { bytes *byte }`

この `name` 型は、`*byte` ポインタを保持し、そのポインタが指すバイト列にエンコードされた名前情報が格納されます。

### エンコーディング形式

コミットメッセージに記述されているエンコーディング形式は以下の通りです。

1.  **フラグバイト (1バイト目)**:
    *   `1<<0` (ビット0): 名前がエクスポートされているか (`isExported`)。
    *   `1<<1` (ビット1): 名前の後にタグデータが続くか (`tagLen > 0`)。
    *   `1<<2` (ビット2): 名前の後にパッケージパス (`pkgPath *string`) が続くか。
    これらのフラグは、`name` 型の `data(0)` メソッドでアクセスされるバイトのビットとして格納されます。

2.  **名前の長さ (2-3バイト目)**:
    *   `uint16` で表現される名前の長さ `l`。`nameLen()` メソッドでデコードされます。

3.  **名前の文字列データ (4バイト目から `3+l` バイト目まで)**:
    *   実際の名前のバイト列。`name()` メソッドで `unsafe.Pointer` を使って直接 `string` に変換されます。

4.  **タグの長さ (オプション、`3+l` から `3+l+1` バイト目まで)**:
    *   フラグバイトのビット1がセットされている場合のみ存在。`uint16` で表現されるタグの長さ。`tagLen()` メソッドでデコードされます。

5.  **タグの文字列データ (オプション、`3+l+2` から `3+l+2+tagLen` バイト目まで)**:
    *   実際のタグのバイト列。`tag()` メソッドで `unsafe.Pointer` を使って直接 `string` に変換されます。

6.  **パッケージパス (`*string`) (オプション、末尾)**:
    *   フラグバイトのビット2がセットされている場合のみ存在。`ptrSize` バイトの領域に `*string` へのポインタが格納されます。このポインタは `round` 関数で `ptrSize` にアラインされます。`pkgPath()` メソッドでデコードされます。

### ゼロアロケーション文字列変換

`name` 型の `name()` および `tag()` メソッドは、`unsafe` パッケージを利用して、エンコードされたバイト列から直接Goの `string` を生成します。具体的には、`stringHeader` (または `stringStruct` in `runtime`) 構造体を `unsafe.Pointer` を介して操作し、バイト列の開始アドレスと長さを設定することで、新しいメモリ割り当てなしで文字列ビューを作成します。

```go
// reflect/type.go
func (n *name) name() (s string) {
	nl := n.nameLen()
	if nl == 0 {
		return ""
	}
	hdr := (*stringHeader)(unsafe.Pointer(&s)) // stringHeaderを直接操作
	hdr.Data = unsafe.Pointer(n.data(3))       // バイト列の開始アドレスを設定
	hdr.Len = nl                               // 長さを設定
	return s
}
```

### バイナリサイズ削減のメカニズム

この変更によるバイナリサイズ削減は、主に以下の理由によります。
1.  **重複する文字列の排除**: 従来の `*string` では、同じ文字列でも異なる場所で参照されると、それぞれが独立した文字列データを持つ可能性がありました。新しいエンコーディングでは、名前のバイト列は一度だけ格納され、`name` 型がそのバイト列へのポインタを持つことで、重複を排除しやすくなります。
2.  **メタデータの統合**: エクスポート状態、タグの有無、パッケージパスの有無といったメタデータが、名前のバイト列の先頭1バイトにビットフィールドとして統合されたことで、個別のフィールドやポインタが不要になり、データ構造がコンパクトになります。
3.  **ポインタの削減**: 従来の `*string` や `*pkgPath` といった複数のポインタが、`name` 型内の単一の `*byte` ポインタと、そのバイト列内のオフセットと長さで表現されるようになったため、ポインタの数が減り、ポインタが占めるメモリ領域が削減されます。

これらの最適化により、特にリフレクション情報を多く含む大規模なGoプログラムにおいて、顕著なバイナリサイズ削減が実現されました。

// name is an encoded type name with optional extra data.
//

//

### `src/cmd/compile/internal/gc/reflect.go` (名前エンコーディング関数 `dname`)

```go
// cmd/compile/internal/gc/reflect.go
// ...
// dname dumps a reflect.name for a struct field or method.
func dname(s *Sym, ot int, name, tag string, pkg *Pkg, exported bool) int {
	// ... 長さチェック ...

	// Encode name and tag. See reflect/type.go for details.
	var bits byte
	l := 1 + 2 + len(name)
	if exported {
		bits |= 1 << 0
	}
	if len(tag) > 0 {
		l += 2 + len(tag)
		bits |= 1 << 1
	}
	if pkg != nil {
		bits |= 1 << 2
	}
	b := make([]byte, l) // エンコードされたバイト列を生成
	b[0] = bits
	b[1] = uint8(len(name) >> 8)
	b[2] = uint8(len(name))
	copy(b[3:], name)
	if len(tag) > 0 {
		tb := b[3+len(name):]
		tb[0] = uint8(len(tag) >> 8)
		tb[1] = uint8(len(tag))
		copy(tb[2:], tag)
	}

	// ... pkgPath の処理とシンボルへの書き込み ...
	// 最終的に bsym (obj.LSym) にバイト列 b を格納し、そのシンボルへのポインタを返す
	return ot
}
```

## コアとなるコードの解説

### `name` 型とそのメソッド (`reflect/type.go`, `runtime/type.go`)

`name` 型は、Goのリフレクションシステムが内部的に使用する名前の新しい表現です。`bytes *byte` フィールドは、エンコードされた名前、タグ、およびオプションのパッケージパス情報を含むバイト列の先頭へのポインタです。

*   `data(off int) *byte`: `bytes` ポインタから指定されたオフセットのバイトへのポインタを返します。これにより、バイト列内の特定の部分にアクセスできます。
*   `isExported() bool`: フラグバイトのビット0をチェックし、名前がエクスポートされているかどうかを判定します。
*   `nameLen() int`, `tagLen() int`: バイト列から名前やタグの長さをデコードします。
*   `name() (s string)`, `tag() (s string)`: これらがゼロアロケーションの核心です。`unsafe.Pointer` を使用して、`name` 型が参照するバイト列の該当部分を直接Goの `string` ヘッダにマッピングします。これにより、新しい文字列データのためのメモリ割り当てなしに、既存のバイト列を文字列として扱うことができます。
*   `pkgPath() *string`: フラグバイトのビット2がセットされている場合、バイト列の末尾からパッケージパスへの `*string` ポインタをデコードして返します。

これらのメソッドにより、リフレクションシステムは効率的に名前の情報を抽出し、必要な場合にのみ文字列として利用できます。

### `dname` 関数 (`cmd/compile/internal/gc/reflect.go`)

`dname` 関数は、コンパイル時にGoの型情報から `name` 型のバイト列を生成し、それをリンカが参照できるシンボルとして出力する役割を担います。

1.  **フラグバイトの構築**: `exported` 引数、`tag` の有無、`pkg` (パッケージパス) の有無に基づいて、最初のフラグバイトを構築します。
2.  **バイト列の構築**: `name`、`tag` の長さ、およびフラグバイトに基づいて、必要なバイト列の総長 `l` を計算します。`make([]byte, l)` でバイトスライスを割り当て、フラグバイト、名前の長さ、名前データ、タグの長さ、タグデータを順番にコピーして格納します。
3.  **パッケージパスの処理**: `pkg` が `nil` でない場合（つまりパッケージパスが必要な場合）、`go.string."".methodname.%d` のようなユニークなシンボル名を生成し、そのシンボルに構築したバイト列 `b` を格納します。さらに、バイト列の末尾にパッケージパスへのポインタを追記します。
4.  **シンボルへの書き込み**: 最終的に、構築されたバイト列を含むシンボルへのポインタを `dsymptrLSym` を介して出力し、そのオフセットを返します。

この関数は、Goのコンパイラが型情報をバイナリに埋め込む際の重要なステップであり、新しいコンパクトな名前エンコーディングを実現するための中心的なロジックです。

### `method`, `imethod`, `structField` 構造体の変更

これらの構造体は、Goの型システムがメソッドや構造体フィールドのメタデータを表現するために使用されます。従来の `*string` 型の `name` や `pkgPath` フィールドが、新しい `name` 型に置き換えられました。これにより、これらの構造体自体のメモリフットプリントが削減され、リフレクションシステムが名前情報にアクセスする際の効率が向上します。

### `interfaceType`, `structType` への `pkgPath` 追加

`interfaceType` と `structType` に `pkgPath *string` フィールドが追加されたのは、インターフェースや構造体自体が定義されているパッケージのパスを明示的に保持するためです。これにより、その型に属する非エクスポートメソッドやフィールドのパッケージパスを解決する際に、より一貫性のある方法で情報を提供できるようになります。

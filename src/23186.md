# [インデックス 23186] ファイルの概要

このコミットは、GoランタイムにおけるAndroid/ARM環境での`TestNewProc0`テストの再有効化と、それに伴うヒープ破損の修正を目的としています。特に、Linux/ARM環境での`runtime.clone`システムコールがスタックポインタを不適切に設定し、関数からの戻り時にヒープを破損させる可能性があった問題に対処しています。

## 元コミット内容

Goランタイムにおいて、`TestNewProc0`テストがAndroid/ARM環境で無効化されていました。このコミットは、そのテストを再有効化し、同時にテストが失敗していた根本原因であるヒープ破損の問題を修正します。ヒープ破損は、`runtime.clone`が子プロセスのスタックポインタを不適切に設定し、関数からの戻り時にスタックの範囲外に書き込みを行おうとすることで発生していました。また、テストのポーリング間隔を短縮し、テストの実行速度を向上させています。この修正はIssue #10548に対応するものです。

## 変更の背景

Goランタイムは、新しいOSプロセス（スレッド）を作成する際に、Linuxシステムコールである`clone`を使用します。この`clone`システムコールは、新しいプロセスが実行を開始する関数（`fn`）と、その関数が使用するスタックの開始アドレスを受け取ります。

以前のGoランタイムの実装では、Linux/ARM環境において、`runtime.clone`が子プロセスのスタックポインタ（`SP`）を、割り当てられたスタック領域の末尾から4バイト手前（`child_stk-4`）に設定していました。これは、ARMアーキテクチャにおける関数呼び出し規約やスタックフレームの管理方法に起因する可能性があります。

問題は、`fn`が実行を終えて戻る際に発生しました。関数が戻り値を返す際や、特定のレジスタ（この場合は`R13`、通常はスタックポインタ）を基準としたメモリアクセスを行う際に、`4(R13)`というアドレスに書き込もうとしました。しかし、`R13`が`child_stk-4`に設定されていたため、`4(R13)`は実質的に`child_stk`、つまり割り当てられた子スタックの**直後**のアドレスを指していました。

この「割り当てられた子スタックの直後」のメモリ領域は、通常、ヒープ領域や他の重要なメモリ領域に隣接しています。そのため、このアドレスへの書き込みは、意図せずヒープを破損させたり、マップされていないメモリ領域へのアクセス（セグメンテーション違反）を引き起こしたりする可能性がありました。これが、`TestNewProc0`がAndroid/ARM環境で失敗する原因となっていました。

この問題はAndroid/ARMに特有のものではなく、Linux/ARM全般に影響する可能性がありました。テストの再有効化とヒープ破損の修正は、Goランタイムの安定性と移植性を向上させる上で不可欠でした。

また、`TestNewProc0`のテスト実行時間が長かったことも背景にあります。以前は1秒間隔でポーリングを行っていたため、テストの完了に最低でも1秒を要していました。開発サイクルを加速するため、このポーリング間隔を短縮する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

1.  **Goランタイム**: Goプログラムの実行を管理する低レベルのコンポーネントです。スケジューラ、ガベージコレクタ、システムコールインターフェースなどが含まれます。Goの並行処理モデル（ゴルーチン）を支える重要な部分です。
2.  **`runtime.clone`**: Goランタイムが新しいOSスレッド（Linuxではプロセスとスレッドは同じ`clone`システムコールで作成されることが多い）を作成するために使用する内部関数です。これはGoのユーザーレベルのゴルーチンとは異なり、OSレベルのスレッドを作成します。
3.  **スタックポインタ (Stack Pointer, SP)**: CPUのレジスタの一つで、現在の関数のスタックフレームの最上位（または最下位、アーキテクチャによる）を指します。関数呼び出しやローカル変数の割り当て、関数からの戻り時に重要な役割を果たします。ARMアーキテクチャでは、通常`R13`レジスタがスタックポインタとして使用されます。
4.  **ヒープ (Heap)**: プログラムが実行時に動的にメモリを割り当てるために使用するメモリ領域です。Goでは、ガベージコレクタがヒープ上のオブジェクトを管理します。ヒープの破損は、プログラムのクラッシュ、予期せぬ動作、セキュリティ脆弱性につながる可能性があります。
5.  **ARMアーキテクチャ**: Advanced RISC Machineの略で、モバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。ARMプロセッサは、レジスタベースの命令セットと、特定の関数呼び出し規約（ABI: Application Binary Interface）を持っています。スタックの管理方法もアーキテクチャによって異なります。
6.  **アセンブリ言語**: CPUが直接実行できる機械語命令を人間が読める形式で記述したものです。Goランタイムの低レベルな部分は、パフォーマンスやOSとの直接的なインタラクションのためにアセンブリ言語で記述されることがあります。このコミットでは、ARMアセンブリコードが変更されています。
7.  **`TestNewProc0`**: Goランタイムのテストスイートの一部で、新しいOSプロセス（スレッド）の作成に関する低レベルな動作を検証するテストです。特に、GoランタイムがOSスレッドを正しく初期化し、そのスレッドがGoのコードを実行できることを確認します。
8.  **Issue #10548**: GoプロジェクトのIssueトラッカーで報告されたバグです。このコミットが修正する具体的な問題が記述されています。

## 技術的詳細

このコミットの技術的詳細は、主にLinux/ARM環境におけるスタックポインタの管理と、それに伴うメモリ破損の問題に焦点を当てています。

Goランタイムの`runtime.clone`関数は、新しいOSスレッドを作成する際に、そのスレッドが実行を開始する関数（`fn`）と、その関数のためのスタック領域をOSに渡します。ARMアーキテクチャでは、スタックは通常、高アドレスから低アドレスに向かって成長します。

問題は、`runtime.clone`が`fn`を呼び出す前に、スタックポインタ`R13`を`child_stk-4`に設定していた点にありました。ここで`child_stk`は割り当てられたスタック領域の「最上位アドレス」（つまり、スタックが成長し始めるアドレス）を指します。通常、関数呼び出し規約では、関数が戻る際にスタックポインタを元の位置に戻すか、あるいは戻りアドレスをスタックにプッシュするなどの操作が行われます。

しかし、このケースでは、`fn`が戻った後、Goランタイムは`runtime.exit`に引数を提供するために`4(R13)`、すなわち`R13`が指すアドレスから4バイトオフセットしたアドレスに書き込もうとしました。`R13`が`child_stk-4`であったため、`4(R13)`は`child_stk`、つまり割り当てられたスタック領域の境界を越えたアドレスを指すことになります。

この「境界を越えた書き込み」は、以下のいずれかの結果を引き起こします。

1.  **ヒープ破損**: `child_stk`の直後がヒープ領域であった場合、Goランタイムのヒープ管理構造や、ヒープ上に割り当てられたデータが上書きされ、破損します。これにより、プログラムの動作が不安定になったり、クラッシュしたりします。
2.  **セグメンテーション違反 (Segmentation Fault)**: `child_stk`の直後がマップされていないメモリ領域であった場合、不正なメモリアクセスとしてOSによって検出され、プログラムはセグメンテーション違反で強制終了します。

このコミットは、`fn`が戻った直後にスタックポインタを適切に調整することで、この問題を解決しています。具体的には、`runtime.exit1`を呼び出す前に`SUB $16, R13`という命令を追加し、スタックポインタ`R13`を16バイト分減算（スタックを拡張）しています。これにより、`4(R13)`への書き込みが、割り当てられたスタック領域内の安全な場所で行われるようになります。16バイトという値は、ARMのABIにおけるスタックアライメントや、`runtime.exit1`への引数渡しに必要なスタック領域を考慮して決定されたものと考えられます。

また、`TestNewProc0`のテストコードでは、`time.NewTicker`のポーリング間隔が`1 * time.Second`から`100 * time.Millisecond`に短縮されました。これにより、テストがより迅速に結果をチェックできるようになり、テストスイート全体の実行時間が短縮されます。

### `src/runtime/norace_linux_test.go` の変更解説

このテストファイルの変更は、主にテストの実行可能性と効率性に関するものです。

1.  **テストスキップの削除**:
    ```go
    -	if runtime.GOOS == "android" && runtime.GOARCH == "arm" {
    -		// newosproc0 does not work for android/arm.
    -		// See issue 10548.
    -		t.Skipf("skipping on %v", runtime.GOOS)
    -	}
    ```
    このコードブロックは、以前はAndroid/ARM環境で`TestNewOSProc0`が既知の問題（Issue #10548）のためにスキップされるようにしていました。今回のコミットでその問題が修正されたため、このスキップロジックは不要となり削除されました。これにより、Android/ARM環境でもこの重要なテストが実行され、ランタイムの安定性が保証されるようになります。

2.  **ポーリング間隔の短縮**:
    ```go
    -	check := time.NewTicker(1 * time.Second)
    +	check := time.NewTicker(100 * time.Millisecond)
    ```
    `TestNewOSProc0`は、`newOSProcCreated`関数が実行されたことを確認するために、一定間隔でチェックを行います。以前は1秒ごとにチェックしていましたが、これを0.1秒（100ミリ秒）に短縮しました。これにより、テストがより頻繁に状態を確認できるようになり、テストが成功するまでの待機時間が短縮され、テストスイート全体の実行時間が改善されます。これは、開発者が変更を迅速に検証するために非常に重要です。

### `src/runtime/sys_linux_arm.s` の変更解説

このアセンブリファイルの変更は、ヒープ破損の根本原因を修正する、このコミットの最も重要な部分です。

```armasm
 	BL	(R0)
 
 	// It shouldn't return.  If it does, exit that thread.
+	SUB	$16, R13 // restore the stack pointer to avoid memory corruption
 	MOVW	$0, R0
 	MOVW	R0, 4(R13)
 	BL	runtime·exit1(SB)
```

-   `BL (R0)`: これは、新しく作成されたOSスレッドが実行を開始する関数（`fn`、レジスタ`R0`にそのアドレスが格納されている）へのブランチ・アンド・リンク命令です。この命令が実行されると、`fn`が呼び出されます。
-   `// It shouldn't return. If it does, exit that thread.`: このコメントは、`fn`が通常は戻らない（例えば、無限ループに入ったり、`exit`を呼び出したりするため）ことを示唆しています。しかし、もし`fn`が戻ってきてしまった場合、そのスレッドは終了する必要があります。
-   `SUB $16, R13`: これが追加された修正行です。
    -   `SUB`: 減算命令です。
    -   `$16`: 即値16です。
    -   `R13`: ARMアーキテクチャにおけるスタックポインタレジスタです。
    この命令は、スタックポインタ`R13`から16バイトを減算します。スタックは通常、高アドレスから低アドレスに向かって成長するため、スタックポインタを減算することは、スタックフレームを「拡張」することに相当します。
    この操作の目的は、`fn`が戻った後のスタックポインタの位置を調整し、次に続く`MOVW R0, 4(R13)`命令が安全なメモリ領域に書き込むようにすることです。以前は、`R13`が`child_stk-4`に設定されており、`4(R13)`は`child_stk`（割り当てられたスタックの境界外）を指していました。16バイト減算することで、`R13`は`child_stk-4-16 = child_stk-20`を指すようになり、`4(R13)`は`child_stk-16`を指すようになります。これにより、書き込みが割り当てられたスタック領域内で行われるようになり、ヒープ破損が回避されます。
-   `MOVW $0, R0` と `MOVW R0, 4(R13)`: これらの命令は、`runtime·exit1`関数に引数を渡すためのものです。`R0`レジスタに0をロードし、その値を`4(R13)`のアドレスにストアしています。このストア操作が、スタックポインタの調整によって安全に行われるようになります。
-   `BL runtime·exit1(SB)`: `runtime·exit1`関数を呼び出し、現在のスレッドを終了させます。

このアセンブリレベルの修正は、GoランタイムがOSスレッドを生成する際の低レベルなスタック管理の正確性を保証し、特定のアーキテクチャ（ARM）におけるメモリ破損という深刻なバグを解決するものです。

また、`TestNewProc0`のテスト実行時間が長かったことも背景にあります。以前は1秒間隔でポーリングを行っていたため、テストの完了に最低でも1秒を要していました。開発サイクルを加速するため、このポーリング間隔を短縮する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

1.  **Goランタイム**: Goプログラムの実行を管理する低レベルのコンポーネントです。スケジューラ、ガベージコレクタ、システムコールインターフェースなどが含まれます。Goの並行処理モデル（ゴルーチン）を支える重要な部分です。
2.  **`runtime.clone`**: Goランタイムが新しいOSスレッド（Linuxではプロセスとスレッドは同じ`clone`システムコールで作成されることが多い）を作成するために使用する内部関数です。これはGoのユーザーレベルのゴルーチンとは異なり、OSレベルのスレッドを作成します。
3.  **スタックポインタ (Stack Pointer, SP)**: CPUのレジスタの一つで、現在の関数のスタックフレームの最上位（または最下位、アーキテクチャによる）を指します。関数呼び出しやローカル変数の割り当て、関数からの戻り時に重要な役割を果たします。ARMアーキテクチャでは、通常`R13`レジスタがスタックポインタとして使用されます。
4.  **ヒープ (Heap)**: プログラムが実行時に動的にメモリを割り当てるために使用するメモリ領域です。Goでは、ガベージコレクタがヒープ上のオブジェクトを管理します。ヒープの破損は、プログラムのクラッシュ、予期せぬ動作、セキュリティ脆弱性につながる可能性があります。
5.  **ARMアーキテクチャ**: Advanced RISC Machineの略で、モバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。ARMプロセッサは、レジスタベースの命令セットと、特定の関数呼び出し規約（ABI: Application Binary Interface）を持っています。スタックの管理方法もアーキテクチャによって異なります。
6.  **アセンブリ言語**: CPUが直接実行できる機械語命令を人間が読める形式で記述したものです。Goランタイムの低レベルな部分は、パフォーマンスやOSとの直接的なインタラクションのためにアセンブリ言語で記述されることがあります。このコミットでは、ARMアセンブリコードが変更されています。
7.  **`TestNewProc0`**: Goランタイムのテストスイートの一部で、新しいOSプロセス（スレッド）の作成に関する低レベルな動作を検証するテストです。特に、GoランタイムがOSスレッドを正しく初期化し、そのスレッドがGoのコードを実行できることを確認します。
8.  **Issue #10548**: GoプロジェクトのIssueトラッカーで報告されたバグです。このコミットが修正する具体的な問題が記述されています。

## 技術的詳細

このコミットの技術的詳細は、主にLinux/ARM環境におけるスタックポインタの管理と、それに伴うメモリ破損の問題に焦点を当てています。

Goランタイムの`runtime.clone`関数は、新しいOSスレッドを作成する際に、そのスレッドが実行を開始する関数（`fn`）と、その関数のためのスタック領域をOSに渡します。ARMアーキテクチャでは、スタックは通常、高アドレスから低アドレスに向かって成長します。

問題は、`runtime.clone`が`fn`を呼び出す前に、スタックポインタ`R13`を`child_stk-4`に設定していた点にありました。ここで`child_stk`は割り当てられたスタック領域の「最上位アドレス」（つまり、スタックが成長し始めるアドレス）を指します。通常、関数呼び出し規約では、関数が戻る際にスタックポインタを元の位置に戻すか、あるいは戻りアドレスをスタックにプッシュするなどの操作が行われます。

しかし、このケースでは、`fn`が戻った後、Goランタイムは`runtime.exit`に引数を提供するために`4(R13)`、すなわち`R13`が指すアドレスから4バイトオフセットしたアドレスに書き込もうとしました。`R13`が`child_stk-4`であったため、`4(R13)`は`child_stk`、つまり割り当てられたスタック領域の境界を越えたアドレスを指すことになります。

この「境界を越えた書き込み」は、以下のいずれかの結果を引き起こします。

1.  **ヒープ破損**: `child_stk`の直後がヒープ領域であった場合、Goランタイムのヒープ管理構造や、ヒープ上に割り当てられたデータが上書きされ、破損します。これにより、プログラムの動作が不安定になったり、クラッシュしたりします。
2.  **セグメンテーション違反 (Segmentation Fault)**: `child_stk`の直後がマップされていないメモリ領域であった場合、不正なメモリアクセスとしてOSによって検出され、プログラムはセグメンテーション違反で強制終了します。

このコミットは、`fn`が戻った直後にスタックポインタを適切に調整することで、この問題を解決しています。具体的には、`runtime.exit1`を呼び出す前に`SUB $16, R13`という命令を追加し、スタックポインタ`R13`を16バイト分減算（スタックを拡張）しています。これにより、`4(R13)`への書き込みが、割り当てられたスタック領域内の安全な場所で行われるようになります。16バイトという値は、ARMのABIにおけるスタックアライメントや、`runtime.exit1`への引数渡しに必要なスタック領域を考慮して決定されたものと考えられます。

また、`TestNewProc0`のテストコードでは、`time.NewTicker`のポーリング間隔が`1 * time.Second`から`100 * time.Millisecond`に短縮されました。これにより、テストがより迅速に結果をチェックできるようになり、テストスイート全体の実行時間が短縮されます。

## コアとなるコードの解説

### `src/runtime/norace_linux_test.go` の変更解説

このテストファイルの変更は、主にテストの実行可能性と効率性に関するものです。

1.  **テストスキップの削除**:
    ```go
    -	if runtime.GOOS == "android" && runtime.GOARCH == "arm" {
    -		// newosproc0 does not work for android/arm.
    -		// See issue 10548.
    -		t.Skipf("skipping on %v", runtime.GOOS)
    -	}
    ```
    このコードブロックは、以前はAndroid/ARM環境で`TestNewOSProc0`が既知の問題（Issue #10548）のためにスキップされるようにしていました。今回のコミットでその問題が修正されたため、このスキップロジックは不要となり削除されました。これにより、Android/ARM環境でもこの重要なテストが実行され、ランタイムの安定性が保証されるようになります。

2.  **ポーリング間隔の短縮**:
    ```go
    -	check := time.NewTicker(1 * time.Second)
    +	check := time.NewTicker(100 * time.Millisecond)
    ```
    `TestNewOSProc0`は、`newOSProcCreated`関数が実行されたことを確認するために、一定間隔でチェックを行います。以前は1秒ごとにチェックしていましたが、これを0.1秒（100ミリ秒）に短縮しました。これにより、テストがより頻繁に状態を確認できるようになり、テストが成功するまでの待機時間が短縮され、テストスイート全体の実行時間が改善されます。これは、開発者が変更を迅速に検証するために非常に重要です。

### `src/runtime/sys_linux_arm.s` の変更解説

このアセンブリファイルの変更は、ヒープ破損の根本原因を修正する、このコミットの最も重要な部分です。

```armasm
 	BL	(R0)
 
 	// It shouldn't return.  If it does, exit that thread.
+	SUB	$16, R13 // restore the stack pointer to avoid memory corruption
 	MOVW	$0, R0
 	MOVW	R0, 4(R13)
 	BL	runtime·exit1(SB)
```

-   `BL (R0)`: これは、新しく作成されたOSスレッドが実行を開始する関数（`fn`、レジスタ`R0`にそのアドレスが格納されている）へのブランチ・アンド・リンク命令です。この命令が実行されると、`fn`が呼び出されます。
-   `// It shouldn't return. If it does, exit that thread.`: このコメントは、`fn`が通常は戻らない（例えば、無限ループに入ったり、`exit`を呼び出したりするため）ことを示唆しています。しかし、もし`fn`が戻ってきてしまった場合、そのスレッドは終了する必要があります。
-   `SUB $16, R13`: これが追加された修正行です。
    -   `SUB`: 減算命令です。
    -   `$16`: 即値16です。
    -   `R13`: ARMアーキテクチャにおけるスタックポインタレジスタです。
    この命令は、スタックポインタ`R13`から16バイトを減算します。スタックは通常、高アドレスから低アドレスに向かって成長するため、スタックポインタを減算することは、スタックフレームを「拡張」することに相当します。
    この操作の目的は、`fn`が戻った後のスタックポインタの位置を調整し、次に続く`MOVW R0, 4(R13)`命令が安全なメモリ領域に書き込むようにすることです。以前は、`R13`が`child_stk-4`に設定されており、`4(R13)`は`child_stk`（割り当てられたスタックの境界外）を指していました。16バイト減算することで、`R13`は`child_stk-4-16 = child_stk-20`を指すようになり、`4(R13)`は`child_stk-16`を指すようになります。これにより、書き込みが割り当てられたスタック領域内で行われるようになり、ヒープ破損が回避されます。
-   `MOVW $0, R0` と `MOVW R0, 4(R13)`: これらの命令は、`runtime·exit1`関数に引数を渡すためのものです。`R0`レジスタに0をロードし、その値を`4(R13)`のアドレスにストアしています。このストア操作が、スタックポインタの調整によって安全に行われるようになります。
-   `BL runtime·exit1(SB)`: `runtime·exit1`関数を呼び出し、現在のスレッドを終了させます。

このアセンブリレベルの修正は、GoランタイムがOSスレッドを生成する際の低レベルなスタック管理の正確性を保証し、特定のアーキテクチャ（ARM）におけるメモリ破損という深刻なバグを解決するものです。

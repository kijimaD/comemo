## 元コミット内容

`cmd/internal/gc: add missing write barrier in append(x, BigStructWithPointers)`

このコミットは、`append(x, BigStructWithPointers)` のような操作において、ライトバリアが欠落していた問題を修正します。これにより、Goのガベージコレクタがポインタを含む大きな構造体を正しく処理できるようになります。

## 変更の背景

このコミットは、Go issue #10897「CMD/GC: MEMORY CORRUPTION AT \"OPTIMIZE APPEND + WRITE BARRIER\"」を修正するために行われました。この問題は、Go 1.5の開発版において、`append` 関数がポインタを含む大きな構造体（`BigStructWithPointers`）を扱う際に、ライトバリアが適切に挿入されないことによって発生するメモリ破損バグでした。

具体的には、Camlistoreというプロジェクトの`camput`ツールで、大量のファイルをアップロードする際にランダムなクラッシュが発生するという形で顕在化しました。このクラッシュは、Goのガベージコレクタを無効化する `GOGC=off` を設定すると発生しなくなることから、GCに関連する問題であることが示唆されていました。

Goのガベージコレクタは、並行GC（Concurrent GC）を採用しており、GCが実行されている最中にもアプリケーションが動作し続けることができます。この並行性を維持するためには、アプリケーションがポインタを書き換える際に、GCにその変更を通知する「ライトバリア」という仕組みが不可欠です。ライトバリアが欠落すると、GCがオブジェクトグラフの変更を認識できず、まだ到達可能なオブジェクトを誤って回収してしまう（Use-After-Free）などのメモリ破損を引き起こす可能性があります。

`append` 関数は、スライスの容量が不足した場合に新しい基盤配列を割り当て、既存の要素をコピーしてから新しい要素を追加します。このコピーと追加の過程で、ポインタを含む構造体が移動または書き込まれる際に、ライトバリアが正しく機能しないと、GCがオブジェクトの到達可能性を誤って判断し、メモリ破損につながる可能性がありました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーキング（Tri-color marking）」アルゴリズムと「ライトバリア（Write Barrier）」を組み合わせて、並行かつ低遅延で動作するように設計されています。

*   **三色マーキング**: オブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって訪問されていないオブジェクト。最終的に回収される可能性がある。
    *   **灰 (Gray)**: GCによって訪問されたが、そのオブジェクトが参照する他のオブジェクト（子）はまだ訪問されていないオブジェクト。
    *   **黒 (Black)**: GCによって訪問され、そのオブジェクトが参照する全ての子オブジェクトも訪問されたオブジェクト。回収されない。
    GCは、ルート（スタック、グローバル変数など）から到達可能なオブジェクトを灰色にマークし、灰色オブジェクトの子を灰色にマークしながら自身を黒色にしていきます。最終的に白色のまま残ったオブジェクトが回収されます。

*   **並行GC**: GoのGCは、アプリケーションの実行と並行してマーキングフェーズの大部分を実行します。これにより、アプリケーションの一時停止（Stop The World: STW）時間を最小限に抑えます。

### ライトバリア (Write Barrier)

並行GCにおいて、アプリケーションがポインタを書き換える（例えば、オブジェクトAがオブジェクトBを参照するように変更する）と、GCがオブジェクトグラフをトラバースしている最中にその変更が発生する可能性があります。この変更がGCの認識と食い違うと、GCが誤った判断を下す可能性があります。

ライトバリアは、このような問題を解決するために導入されます。アプリケーションがヒープ上のポインタを書き換える直前に、コンパイラによって挿入される小さなコードスニペットです。このスニペットは、ポインタの変更をGCに通知し、GCがオブジェクトグラフの整合性を維持できるようにします。

GoのGCでは、Dijkstraの三色ライトバリアが採用されており、ポインタの書き込み時に、書き込まれるポインタが指すオブジェクトを灰色にマークします。これにより、GCがオブジェクトグラフをトラバースする際に、新しい参照関係を見落とすことを防ぎます。

### `append` 関数の動作

`append` 関数は、Goのスライスに要素を追加するために使用されます。スライスは、基盤となる配列への参照、長さ、容量を持つデータ構造です。

1.  **容量の確認**: `append` はまず、現在のスライスの容量が新しい要素を追加するのに十分かどうかを確認します。
2.  **再割り当て**: 容量が不足している場合、`append` はより大きな新しい基盤配列を割り当てます。この際、通常は既存の容量の2倍（または特定の閾値を超えると1.25倍）の容量を持つ配列が割り当てられます。
3.  **要素のコピー**: 古い基盤配列から新しい基盤配列へ、既存の要素がコピーされます。
4.  **要素の追加**: 新しい要素が、新しい基盤配列の末尾に追加されます。
5.  **新しいスライスの返却**: 新しい基盤配列を参照する新しいスライスヘッダが返されます。

ポインタを含む構造体（`BigStructWithPointers`）を `append` する場合、ステップ3と4でポインタがコピーまたは書き込まれるため、ライトバリアが正しく機能することが極めて重要です。

### `cmd/internal/gc` の役割

`cmd/internal/gc` は、Goコンパイラのバックエンドの一部であり、主に抽象構文木 (AST) から中間表現 (IR) を生成し、最終的に機械語コードを生成する役割を担っています。ライトバリアの挿入やスタックフレームの管理など、ランタイムとの連携に必要な低レベルのコード生成ロジックが含まれています。

## 技術的詳細

このコミットの核心は、Goコンパイラの `stkof` 関数におけるロジックの修正です。`stkof` 関数は、与えられた `Node`（コンパイラ内部の抽象構文木のノード）がスタック上に存在する場合、そのスタックポインタ (SP) からのオフセットを計算することを目的としています。このオフセット情報は、ライトバリアの挿入やその他のメモリ操作において、変数の正確な位置を特定するために重要です。

変更前の `stkof` 関数には、特に `append` 操作でポインタを含む大きな構造体が扱われる際に、スタック上のオブジェクトの位置を誤って判断する可能性がありました。これにより、ライトバリアが正しく挿入されず、GCがオブジェクトグラフの変更を追跡できなくなるという問題が発生していました。

具体的な変更点は以下の通りです。

1.  **`OINDREG` (間接レジスタ) のケースの修正**:
    変更前は、`OINDREG` のノードがスタック上にあるかどうかを判断する際に、レジスタが `Thearch.REGSP` (スタックポインタレジスタ) であるかどうかのチェックが欠落していました。この修正により、`n.Reg != int16(Thearch.REGSP)` でない場合は `-1000` (スタック上にない) を返すようになり、より正確な判断が可能になりました。

2.  **`ODOT` (構造体フィールドアクセス) および `OINDEX` (配列要素アクセス) のケースの `+1000` の導入**:
    `stkof` 関数は、スタック上のオフセットを正確に計算できない場合に `-1000` (スタック上にない) または `1000` (スタック上にあるが位置不明) を返していました。このコミットでは、`+1000` を明示的に「スタック上にあるが正確な位置は不明」という意味で使用するように変更されました。
    *   `ODOT` の場合、`n.Left` (構造体自体) のオフセットが `-1000` または `+1000` であれば、そのフィールドのオフセットも同様に不明として `off` をそのまま返します。
    *   `OINDEX` の場合、`n.Left` (配列自体) のオフセットが `-1000` または `+1000` であれば、その要素のオフセットも同様に不明として `off` をそのまま返します。さらに、配列のインデックスが定数でない場合 (`Isconst(n.Right, CTINT)` が偽の場合)、以前は `1000` を返していましたが、これを `+1000` に変更し、コメントで「スタック上にあるが正確な位置は不明」であることを明示しました。

3.  **コメントの明確化**:
    `stkof` 関数の冒頭のコメントが大幅に加筆され、関数の目的、返り値の意味 (`-1000` と `+1000`)、そして `ODOT` および `OINDEX` ケースに関する懸念（これらがオーバーラップするコピーに関与する可能性は低いのではないか、もしそうなら関数がもっと単純になるはずだ、という考察）が詳細に記述されました。これは、この関数の複雑さと、それがライトバリアの正確性に与える影響を理解する上で非常に重要です。

これらの変更により、コンパイラはスタック上のポインタを含む構造体の位置をより正確に特定できるようになり、`append` 操作中にライトバリアが適切に挿入されるようになりました。特に、`ODOT` や `OINDEX` のような複雑なメモリアクセスパターンを持つノードに対しても、スタック上の位置が不明な場合に `+1000` を返すことで、コンパイラが安全側に倒れた判断を下し、ライトバリアの挿入を確実に行うことができるようになります。

## コアとなるコードの解説

### `src/cmd/internal/gc/cgen.go` の `stkof` 関数

`stkof` 関数の変更は、Goコンパイラがスタック上のポインタを含む構造体の位置をより正確に特定し、ライトバリアを適切に挿入できるようにするために不可欠です。

*   **`OINDREG` の修正**: 以前は、レジスタがスタックポインタ (`REGSP`) でない場合でも、スタック上のオフセットを返す可能性がありました。この修正により、`REGSP` 以外のレジスタを参照している場合は確実に `-1000` (スタック上にない) を返すようになり、誤ったライトバリアの挿入や欠落を防ぎます。
*   **`ODOT` と `OINDEX` の `+1000` の明確化**: `ODOT` (構造体のフィールドアクセス) や `OINDEX` (配列の要素アクセス) の場合、その基底となるオブジェクトがスタック上にあり、かつその正確なオフセットが計算できない（例えば、配列のインデックスが実行時まで決定できない変数である場合）ことがあります。このような状況で `+1000` を返すことで、「スタック上にはあるが、正確な位置は不明」という情報をコンパイラに伝えます。これにより、コンパイラは安全側に倒れて、ライトバリアが必要な可能性があると判断し、適切なコードを生成することができます。これは、メモリ破損を防ぐ上で非常に重要な安全策です。
*   **コメントの追加**: `stkof` 関数の複雑さと、`ODOT` および `OINDEX` ケースの潜在的な影響に関する詳細なコメントは、この関数の意図と限界を明確にし、将来のメンテナンスやデバッグを容易にします。特に、これらのケースがオーバーラップするコピーに「関連しない可能性がある」という考察は、コンパイラの最適化の可能性を示唆しています。

これらの変更は、`append` 関数がポインタを含む構造体をコピーまたは移動する際に、コンパイラがその操作を正しく認識し、必要なライトバリアを挿入するための基盤となります。これにより、並行GC環境下でのメモリ破損が防止されます。

### `test/writebarrier.go` の新しいテストケース

`f15` と `f16` の追加は、このコミットが修正しようとしているバグを具体的に再現し、修正が正しく機能することを確認するためのものです。

*   **`type T1 struct { X *int }`**: ポインタ (`*int`) を一つだけ含む構造体 `T1` を定義しています。
*   **`func f15(x []T1, y T1) []T1 { return append(x, y) }`**: `T1` のスライスに `T1` 型の要素を追加する `append` 操作をテストします。
*   **`type T8 struct { X [8]*int }`**: 8つのポインタ (`*int`) を含む配列を持つ構造体 `T8` を定義しています。これは「`BigStructWithPointers`」の具体的な例として機能します。
*   **`func f16(x []T8, y T8) []T8 { return append(x, y) }`**: `T8` のスライスに `T8` 型の要素を追加する `append` 操作をテストします。

これらのテストケースでは、`append` 操作がポインタを含む構造体を扱うため、コンパイラがライトバリアを挿入する必要があります。`// ERROR "write barrier"` というコメントは、コンパイラがこの行でライトバリアを検出することを期待していることを示しています。もしライトバリアが欠落していれば、テストは失敗し、バグが再発したことを示します。これらのテストは、`stkof` 関数の修正が `append` 操作におけるライトバリアの欠落を効果的に解決したことを検証します。

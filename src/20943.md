## 変更の背景

このコミットは、Goコンパイラが特定の状況下で構造体の比較を行う際に発生していた内部コンパイラエラー（ICE）を修正するために行われました。具体的には、`switch` ステートメントの式や `case` 節で、構造体リテラルや構造体を返す関数呼び出しが使用された場合に、コンパイラが不正なASTノードに対してlvalueチェックを行い、`fatal` エラーでクラッシュするという問題がありました。

問題の根本原因は、コンパイラが比較対象の式の「実体」を正しく識別できていなかったことにあります。特に、`OCONVNOP`（型変換だが実質的に何もしない操作）ノードが介在している場合、その内部にある本来の式（lvalueであるべきもの）にアクセスする前にlvalueチェックを行ってしまい、エラーを引き起こしていました。この修正は、`OCONVNOP` ノードを適切に「剥がす」ことで、正しいノードに対してlvalueチェックとアドレス取得を行うように変更し、コンパイラの安定性を向上させます。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoコンパイラの内部構造とGo言語の概念に関する知識が必要です。

*   **Goコンパイラ (gc)**: Go言語の公式コンパイラです。ソースコードを解析し、抽象構文木（AST）を構築し、最適化を行い、最終的に実行可能なバイナリコードを生成します。
*   **抽象構文木 (AST - Abstract Syntax Tree)**: ソースコードの構文構造を木構造で表現したものです。コンパイラはASTを走査（ウォーク）しながら、型チェック、最適化、コード生成などの処理を行います。
*   **`src/cmd/gc/walk.c`**: Goコンパイラのバックエンドの一部を構成するC言語のソースファイルです。このファイルには、ASTを走査し、高レベルなGoの構文（`switch`、`for`など）をより低レベルな中間表現に変換する `walk` 関数群が含まれています。`walkcompare` 関数は、比較演算子（`==`, `!=`など）を含むASTノードを処理します。
*   **`Node`**: ASTにおける各ノードを表すデータ構造です。ノードは、変数、定数、演算子、関数呼び出し、制御構造など、プログラムのあらゆる要素に対応します。各 `Node` には、そのノードの種類を示す `op` フィールド（例: `OEQ` は等価比較、`OAS` は代入）や、子ノードへのポインタ（`left`, `right`など）が含まれます。
*   **`Type`**: Goの型システムにおける型（`int`, `string`, `struct`など）を表すデータ構造です。
*   **lvalue (左辺値)**: メモリ上の特定のアドレスを持つ式のことです。代入演算子の左辺に来ることができる式、またはアドレス演算子 `&` を適用できる式がlvalueです。比較演算子の引数も、多くの場合、そのアドレスを参照できるlvalueである必要があります。`islvalue(Node *n)` 関数は、与えられたノードがlvalueであるかを判定します。
*   **`OCONVNOP`**: ASTノードの操作コード（`op`）の一つです。これは「型変換（conversion）だが、実際には何もしない（no-operation）」ことを意味します。例えば、`type MyInt int; var x int = 10; var y MyInt = MyInt(x)` のように、基底型が同じで値の表現が変わらない型変換の場合に、コンパイラ内部で `OCONVNOP` ノードが生成されることがあります。これは、AST上は型変換が存在するが、実行時には特別なコードを生成する必要がないことを示します。
*   **`OAS` (Assignment)**: 代入操作 (`=`) を表すASTノードです。
*   **`OADDR` (Address Of)**: アドレス取得操作 (`&`) を表すASTノードです。例えば、`&x` は変数 `x` のアドレスを取得します。
*   **`temp(Type *t)`**: コンパイラが一時的に使用する変数を生成する内部関数です。
*   **`ptrto(Type *t)`**: 指定された型 `t` へのポインタ型を返す内部関数です。
*   **`typecheck(Node **np, Etype et)`**: ASTノードの型チェックを行うコンパイラ内部関数です。`Etype et` は型チェックのコンテキストを示します。
*   **`fatal(...)`**: コンパイラが回復不能なエラーに遭遇した際に、エラーメッセージを出力してコンパイルプロセスを終了させる内部関数です。
*   **Goにおける構造体の比較**: Go言語では、構造体のすべてのフィールドが比較可能な型（数値、文字列、ブール値、ポインタ、チャネル、配列、他の比較可能な構造体など）である場合、その構造体は比較可能です。比較可能な構造体は `==` 演算子や `!=` 演算子でフィールドごとに比較されます。スライス、マップ、関数を含む構造体は比較不可能です。
*   **`switch` ステートメント**: Goの制御フロー文の一つで、式の値と複数の `case` 節の値を比較し、一致する `case` ブロックを実行します。

## 技術的詳細

このコミットが修正する問題は、`walkcompare` 関数が比較演算子の引数（`n->left` と `n->right`）に対して `islvalue` チェックを行う際に、これらのノードが `OCONVNOP` ノードでラップされている場合に発生していました。

元のコードでは、`islvalue(n->left)` や `islvalue(n->right)` が直接呼び出されていました。しかし、例えば `switch T1{}` のような構造体リテラルや、`NewT1(1)` のような関数呼び出しの結果が比較対象となる場合、コンパイラ内部ではこれらの式が `OCONVNOP` ノードでラップされることがあります。`OCONVNOP` ノード自体はlvalueではないため、そのノードに対して `islvalue` を呼び出すと `false` が返され、結果として `fatal("arguments of comparison must be lvalues")` というエラーが発生し、コンパイラがクラッシュしていました。

この修正では、以下の2つの新しい `Node` ポインタ `cmpl` と `cmpr` が導入されました。

1.  `cmpl = n->left;` と `cmpr = n->right;` で、比較対象の左右のノードを初期化します。
2.  `while(cmpl != N && cmpl->op == OCONVNOP) cmpl = cmpl->left;`
    `while(cmpr != N && cmpr->op == OCONVNOP) cmpr = cmpr->left;`
    これらの `while` ループは、`cmpl` または `cmpr` が `OCONVNOP` ノードである限り、その `left` 子ノード（つまり、`OCONVNOP` がラップしている本来の式）にポインタを移動させます。これにより、`OCONVNOP` の層を剥がし、比較対象の「実体」であるノードに到達します。
3.  `islvalue(cmpl) || !islvalue(cmpr)` のlvalueチェックが、`OCONVNOP` を剥がした後の `cmpl` と `cmpr` に対して行われるようになります。これにより、正しいノードがlvalueであるかどうかが判定され、誤ったクラッシュが回避されます。
4.  一時変数 `l` と `r` に比較対象のアドレスを代入する際も、`nod(OAS, l, nod(OADDR, cmpl, N))` および `nod(OAS, r, nod(OADDR, cmpr, N))` のように、`OCONVNOP` を剥がした後の `cmpl` と `cmpr` が使用されます。これにより、正しいメモリ位置のアドレスが取得され、比較処理が正常に行われるようになります。

この変更により、コンパイラは `OCONVNOP` ノードが介在する複雑な構造体比較のシナリオでも、安定して動作するようになりました。

## コアとなるコードの解説

### `src/cmd/gc/walk.c` の変更点

`walkcompare` 関数は、Goコンパイラが比較演算子（`==`, `!=`など）を含むASTノードを処理する際に呼び出されます。

1.  **新しい変数の導入**:
    ```c
    -	Node *n, *l, *r, *call, *a, *li, *ri, *expr;
    +	Node *n, *l, *r, *call, *a, *li, *ri, *expr, *cmpl, *cmpr;
    ```
    `cmpl` (compare left) と `cmpr` (compare right) という2つの `Node` ポインタが追加されました。これらは、比較対象の左右の式から `OCONVNOP` ノードを剥がした後の「実体」のノードを指すために使用されます。

2.  **`OCONVNOP` ノードのアンラップ**:
    ```c
    +	cmpl = n->left;
    +	while(cmpl != N && cmpl->op == OCONVNOP)
    +		cmpl = cmpl->left;
    +	cmpr = n->right;
    +	while(cmpr != N && cmpr->op == OCONVNOP)
    +		cmpr = cmpr->left;
    ```
    この部分が修正の核心です。
    *   `cmpl` と `cmpr` は、それぞれ比較演算子の左辺 (`n->left`) と右辺 (`n->right`) で初期化されます。
    *   続く `while` ループは、`cmpl` または `cmpr` が `OCONVNOP` ノードである限り、そのノードの `left` 子ノード（`OCONVNOP` がラップしている本来の式）にポインタを更新し続けます。これにより、多重にネストされた `OCONVNOP` ノードもすべて剥がされ、最終的に型変換されていない本来の式ノードに到達します。

3.  **lvalue チェックの修正**:
    ```c
    -	if(!islvalue(n->left) || !islvalue(n->right)) {
    -		fatal("arguments of comparison must be lvalues");
    +	if(!islvalue(cmpl) || !islvalue(cmpr)) {
    +		fatal("arguments of comparison must be lvalues - %N %N", cmpl, cmpr);
    ```
    lvalueチェックの対象が、元の `n->left` と `n->right` から、`OCONVNOP` を剥がした後の `cmpl` と `cmpr` に変更されました。これにより、コンパイラは正しいノードに対してlvalueであるかを判定し、不適切なクラッシュを防ぎます。また、`fatal` メッセージに `cmpl` と `cmpr` の情報が追加され、デバッグ時の情報量が増えました。

4.  **アドレス取得の修正**:
    ```c
    -	a = nod(OAS, l, nod(OADDR, n->left, N));
    +	a = nod(OAS, l, nod(OADDR, cmpl, N));
    // ...
    -	a = nod(OAS, r, nod(OADDR, n->right, N));
    +	a = nod(OAS, r, nod(OADDR, cmpr, N));
    ```
    一時変数 `l` と `r` に比較対象のアドレスを代入する際も、アドレス取得操作 `OADDR` の引数が `n->left`/`n->right` から `cmpl`/`cmpr` に変更されました。これにより、`OCONVNOP` を剥がした後の本来の式のメモリ位置が正しく参照され、比較処理のための準備が適切に行われます。

### `test/fixedbugs/issue9006.go` の追加

このテストファイルは、修正されたバグを再現し、修正が正しく機能することを確認するために追加されました。

*   `T1` はシンプルな構造体、`T2` は基底型 `int` を持つカスタム型です。
*   `NewT1` と `NewT2` は、それぞれ `T1` と `T2` の値を返す関数です。
*   `main` 関数内の2つの `switch` ステートメントがポイントです。
    *   最初の `switch (T1{})` は、構造体リテラル `T1{}` を `switch` 式として使用しています。`case NewT1(1)` と `case NewT1(0)` では、構造体を返す関数呼び出しが `case` の値として使用されています。
    *   2番目の `switch T2(0)` は、カスタム型 `T2` の値を `switch` 式として使用し、`case NewT2(2)` と `case NewT2(0)` では、カスタム型を返す関数呼び出しが `case` の値として使用されています。

これらのシナリオは、コンパイラが `OCONVNOP` ノードを生成しやすく、修正前のコンパイラでは内部エラーを引き起こす可能性があったケースを網羅しています。テストは、期待される `case` ブロック（`NewT1(0)` と `NewT2(0)`）が実行され、他の `panic` が発生しないことを確認することで、コンパイラの修正が正しく機能していることを検証します。

# [インデックス 24738] ファイルの概要

`cmd/asm` のパーサーにおける潜在的な無限ループを修正するコミットです。特に ARM アーキテクチャのレジスタリストのパース処理において、閉じ括弧 `]` が欠落している場合にパーサーがハングアップする問題を解決します。

    same line are simply ignored. Only the first one is reported.

## 変更の背景

このコミットは、Go言語のアセンブラである `cmd/asm` が、特定の不正な入力に対して無限ループに陥り、ハングアップする問題を解決するために行われました。具体的には、ARM アーキテクチャのアセンブリコードでサポートされているレジスタリスト（例: `[R1,R2]`）において、閉じ括弧 `]` が欠落している場合に問題が発生していました。

パーサーは、閉じ括弧がない場合、エラーを大量に発行し、すべてのトークンを消費し尽くしていました。そして、ファイルの終端 (EOF) に達してもループを継続してしまうため、結果として無限ループに陥っていました。通常、`cmd/asm` のパーサーは、エラーが10回発生すると停止するメカニズムを持っていますが、同じ行で発生する複数のエラーは最初の1つしかカウントされないという特性がありました。このため、レジスタリストの閉じ括弧の欠落によるエラーは、常に同じ行で発生すると見なされ、エラーカウンターがインクリメントされず、無限ループを回避できませんでした。

この問題は GitHub Issue #11764 として報告されており、「cmd/asm: hang」というタイトルで、`cmd/asm` ツールが特定のプログラムを処理する際にハングアップするという内容でした。このコミットは、このハングアップ問題を修正し、パーサーの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Go言語のアセンブラ (`cmd/asm`)

Go言語は、そのコンパイラツールチェーンの一部として独自のアセンブラ `cmd/asm` を持っています。これは、Goのランタイムや特定のパフォーマンスが要求されるコード（例: 暗号化ライブラリ、システムコールラッパーなど）を記述するために使用されます。`cmd/asm` は、一般的なアセンブラとは異なる独自の構文（Plan 9アセンブラに由来）を使用しており、Goのリンカと連携して動作します。

### ARMアーキテクチャとレジスタリスト

ARM (Advanced RISC Machine) は、モバイルデバイスなどで広く使われているRISC (Reduced Instruction Set Computer) ベースのプロセッサアーキテクチャです。ARMアセンブリ言語では、複数のレジスタを一度に操作するための「レジスタリスト」という構文がサポートされています。例えば、`[R1, R2, R3]` のように角括弧 `[]` で囲んで複数のレジスタを指定します。これは、関数呼び出し時のレジスタの保存/復元（プッシュ/ポップ）などで効率的に使用されます。

### パーサーと字句解析 (Lexer/Scanner)

コンパイラやアセンブラは、ソースコードを機械が理解できる形式に変換するソフトウェアです。このプロセスは通常、以下の段階に分かれます。

1.  **字句解析 (Lexical Analysis / Scanning)**: ソースコードをトークン（意味のある最小単位、例: 識別子、キーワード、演算子、括弧など）のストリームに変換します。この処理を行うのが字句解析器（Lexer または Scanner）です。
2.  **構文解析 (Syntactic Analysis / Parsing)**: トークンのストリームが、言語の文法規則に従っているかを検証し、抽象構文木 (AST) などの構造を構築します。この処理を行うのが構文解析器（Parser）です。

本コミットで問題となっているのは、構文解析器（パーサー）がレジスタリストの構文を解析する際に、字句解析器（スキャナー）から受け取るトークンを適切に処理できないことでした。

### 無限ループ

プログラムが特定の条件を満たさない限り、同じ処理を繰り返し実行し続ける状態を無限ループと呼びます。これは通常、プログラムのバグであり、リソースの枯渇やプログラムのハングアップを引き起こします。パーサーにおける無限ループは、入力が不正な場合に、パーサーが次の有効なトークンを見つけられず、エラー回復ロジックが適切に機能しない場合に発生しやすいです。

## 技術的詳細

この問題の核心は、`cmd/asm` のパーサーがレジスタリストを解析する `registerList` 関数にありました。

1.  **既存のエラー処理の限界**: `cmd/asm` のパーサーには、エラーが多発した場合に無限ループを防ぐためのメカニズムとして、エラーカウンターがありました。しかし、このカウンターは「行ごとに最大1つのエラーしかカウントしない」というロジックを持っていました。
2.  **レジスタリストの特殊性**: レジスタリスト `[R1, R2, ...` の閉じ括弧 `]` が欠落している場合、パーサーはリスト内の各要素（レジスタ名など）を処理しようとしますが、期待される `]` が見つからないため、繰り返しエラーを生成します。これらのエラーはすべて同じ論理行で発生していると見なされるため、エラーカウンターは1回しかインクリメントされません。
3.  **トークン消費とEOF**: 閉じ括弧がないままパーサーがトークンを読み進めると、最終的にはファイルの終端 (EOF) に達します。しかし、`registerList` 関数内のループは、`]` トークンが見つかるまで継続するように設計されていたため、EOF に達してもループを抜け出す条件が満たされず、無限ループに陥ってしまっていました。パーサーは EOF を繰り返し読み込もうとし、何も進展しないままハングアップします。

このコミットは、この特定のシナリオ、つまりレジスタリストの解析中に `]` が見つからない場合に、パーサーが無限ループに陥るのを防ぐために、明示的なチェックを追加することで問題を解決しています。

## コアとなるコードの解説

`registerList` 関数は、ARMアセンブリのレジスタリスト（例: `[R0, R1, R2]`）をパースする役割を担っています。この関数は、リスト内の各レジスタまたはレジスタ範囲を処理するために `for` ループを使用しています。

変更前のコードでは、ループを抜ける条件は `]` トークンが見つかることだけでした。しかし、不正な入力（`]` が欠落している場合）では、`]` が永遠に見つからないため、パーサーは無限に次のトークンを読み込もうとし続けました。最終的に、入力の終端に達すると、`p.next()` は `scanner.EOF` トークンを返し続けますが、ループの終了条件は満たされないため、無限ループに陥っていました。

今回の修正では、この問題に対処するために以下の点が改善されました。

1.  **`ListLoop` ラベルの導入**: `for` ループに `ListLoop:` というラベルを付けることで、`break ListLoop` を使用して特定のループを明示的に終了できるようになりました。これは、複数のネストされたループがある場合に、どのループを終了させるかを明確にするために使われることがあります。このケースでは、単一のループですが、コードの意図を明確にするのに役立ちます。
2.  **`switch` ステートメントによるトークン処理の強化**:
    *   `case ']': break ListLoop` は、期待される閉じ括弧が見つかった場合にループを正常に終了させます。
    *   `case scanner.EOF: p.errorf("missing ']' in register list"); return` が最も重要な変更点です。これにより、パーサーがレジスタリストの解析中に `EOF` に達した場合、それが閉じ括弧の欠落によるものであると判断し、エラーを報告して直ちに `registerList` 関数を終了させます。これにより、`EOF` トークンを繰り返し処理しようとする無限ループが防止されます。

この修正により、`cmd/asm` は不正なレジスタリストの入力に対しても堅牢になり、ハングアップすることなく適切なエラーメッセージを出力して処理を終了できるようになりました。テストケースの追加も、この修正が意図通りに機能することを保証する上で重要な役割を果たしています。

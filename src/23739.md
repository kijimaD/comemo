# [インデックス 23739] ファイルの概要

このコミットは、Go言語の`crypto/tls`パッケージにおけるクライアント認証の挙動に関する変更です。具体的には、クライアント証明書の検証において、リーフ証明書（エンドエンティティ証明書）に明示的なクライアント認証用のExtended Key Usage (EKU) が含まれていなくても、クライアント認証を許可するように修正されました。これにより、より柔軟なクライアント証明書の運用が可能になります。

## 元コミット内容

このコミットは、`crypto/tls`パッケージにおいて、クライアント認証時に明示的なクライアント認証用Extended Key Usage (EKU) を要求しないようにするものです。

以前のGoの実装では、クライアント証明書チェーンがクライアント認証を許可していること（これは引き続き必要）に加えて、リーフ証明書自体にも明示的に`client-auth` EKUが含まれていることを強制していました。

この変更により、後者の要件が削除されます。証明書チェーン全体がクライアント認証と互換性があること（例えば、親証明書がS/MIMEなどの別の用途に限定されていないこと）は引き続き必要ですが、リーフ証明書にEKUが全く含まれていない場合でも、クライアント認証のために受け入れられるようになります。

コミットメッセージの著者であるAdam Langleyは、「すべてのクライアント証明書がその意図された目的を明示していれば素晴らしいことだが、この戦いはもはや価値があるとは思えない」と述べており、これは現実世界の証明書運用の多様性に対応するための実用的な判断であることを示唆しています。

この変更は、Issue #11087を修正するものです。

## 変更の背景

この変更の背景には、Goの`crypto/tls`パッケージが、X.509証明書のExtended Key Usage (EKU) の解釈に関して、一部のRFCの解釈と異なる、あるいは過度に厳格な挙動をしていたという問題があります。

具体的には、Goはクライアント認証を行う際に、以下の2つの条件を課していました。
1.  証明書チェーン全体がクライアント認証を許可していること。これは、チェーン内のどの証明書も、クライアント認証を禁止するようなEKUを持たないことを意味します。
2.  **リーフ証明書（エンドエンティティ証明書）に、明示的に`ExtKeyUsageClientAuth`というEKUが含まれていること。**

Issue #11087では、この2番目の要件が問題として提起されました。RFC 3280やRFC 5280といったX.509証明書に関する標準では、EKUフィールドが存在しない場合、その証明書は「あらゆる用途に利用可能」と解釈されることが一般的です。しかし、Goの`crypto/tls`は、EKUフィールドが存在しないリーフ証明書をクライアント認証に利用しようとすると、`client-auth` EKUが明示されていないという理由で認証を拒否していました。

この厳格な解釈は、一部の正当なクライアント証明書がGoのTLS実装で利用できないという互換性の問題を引き起こしていました。特に、EKUが省略されているが、チェーン全体としてはクライアント認証が許可されている証明書が、Goのサーバーでは認証に失敗するという状況が発生していました。

このコミットは、この過度に厳格な要件を緩和し、RFCの一般的な解釈に沿うことで、より多くのクライアント証明書がGoのTLS実装で正しく機能するようにすることを目的としています。

## 前提知識の解説

### TLS/SSLハンドシェイク

TLS (Transport Layer Security) は、インターネット上で安全な通信を行うためのプロトコルです。SSL (Secure Sockets Layer) はその前身です。TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行う一連のネゴシエーションプロセスです。このプロセスには、暗号スイートの選択、鍵交換、そして証明書による認証が含まれます。

### クライアント認証 (Client Authentication)

通常のTLSハンドシェイクでは、クライアントはサーバーの身元をサーバー証明書によって検証しますが、サーバーはクライアントの身元を検証しません。クライアント認証は、サーバーがクライアントの身元も検証するプロセスです。これは、サーバーがクライアント証明書を要求し、その証明書が信頼できる認証局によって発行されたものであるか、そしてその証明書がクライアント認証の目的で利用可能であるかを検証することで行われます。

### X.509証明書

X.509は、公開鍵証明書の標準フォーマットです。デジタル証明書は、公開鍵と、その公開鍵の所有者に関する情報（名前、組織など）を関連付け、信頼できる第三者（認証局、CA）によって署名されたものです。これにより、公開鍵が本当にその所有者に属していることを保証します。

### Extended Key Usage (EKU)

Extended Key Usage (EKU) は、X.509証明書の拡張フィールドの一つで、その証明書がどのような特定の目的のために利用されるべきかを示すために使用されます。例えば、サーバー認証、クライアント認証、コード署名、メール保護など、様々な用途が定義されています。EKUフィールドが存在しない場合、その証明書は通常、あらゆる用途に利用可能であると解釈されます。しかし、EKUフィールドが存在し、特定の用途がリストされている場合、その証明書はそのリストされた用途にのみ利用されるべきです。

### `x509.ExtKeyUsageClientAuth`

これはGo言語の`crypto/x509`パッケージで定義されている定数で、X.509証明書のEKUフィールドにおいて、その証明書がクライアント認証の目的で利用可能であることを示す値です。このEKUが証明書に含まれている場合、その証明書はクライアントとして自身の身元を証明するために使用できることを意味します。

## 技術的詳細

このコミットは、Goの`crypto/tls`パッケージ内のサーバーサイドハンドシェイク処理、具体的にはクライアント証明書を処理する`processCertsFromClient`関数における検証ロジックを変更します。

以前の実装では、クライアントから提示された証明書チェーンの検証後、リーフ証明書（`certs[0]`）の`ExtKeyUsage`フィールドを繰り返し処理し、`x509.ExtKeyUsageClientAuth`が明示的に含まれているかどうかを確認していました。もしこのEKUが見つからなかった場合、`ok`フラグは`false`のままで、ハンドシェイクは失敗し、`"tls: client's certificate's extended key usage doesn't permit it to be used for client authentication"`というエラーが返されていました。

このコミットでは、この明示的な`ExtKeyUsageClientAuth`のチェックを行う12行のコードブロックが完全に削除されます。

変更後も、証明書チェーン全体の検証は引き続き行われます。これは、`x509.Verify`関数が、チェーン内の各証明書がその用途（この場合はクライアント認証）に適しているかを検証するからです。例えば、中間CA証明書やルートCA証明書がクライアント認証を禁止するEKUを持っていたり、Key Usageフィールドで署名以外の用途が許可されていなかったりする場合には、`x509.Verify`がエラーを返します。

しかし、リーフ証明書に関しては、EKUフィールドが全く存在しない場合でも、`x509.Verify`は通常、その証明書を「あらゆる用途に利用可能」と判断します。したがって、このコミットによって、EKUが明示されていないリーフ証明書でも、チェーン全体の検証が成功すればクライアント認証に利用できるようになります。

この変更は、GoのTLS実装が、X.509証明書のEKUに関するRFCの一般的な解釈（EKUがない場合は汎用的に利用可能）に、より厳密に準拠するようになったことを意味します。これにより、GoのTLSサーバーは、より幅広い種類のクライアント証明書を受け入れられるようになり、相互運用性が向上します。

## コアとなるコードの解説

変更は`src/crypto/tls/handshake_server.go`ファイルの`processCertsFromClient`関数内で行われています。この関数は、クライアントから提示された証明書を処理し、検証する役割を担っています。

削除されたコードブロックは以下の部分です。

```go
		ok := false
		for _, ku := range certs[0].ExtKeyUsage {
			if ku == x509.ExtKeyUsageClientAuth {
				ok = true
				break
			}
		}
		if !ok {
			c.sendAlert(alertHandshakeFailure)
			return nil, errors.New("tls: client's certificate's extended key usage doesn't permit it to be used for client authentication")
		}
```

このコードブロックは、クライアントから受け取った証明書チェーンの最初の証明書（`certs[0]`、すなわちリーフ証明書）の`ExtKeyUsage`フィールドを検査していました。
1.  `ok := false` でフラグを初期化します。
2.  `for _, ku := range certs[0].ExtKeyUsage` ループで、リーフ証明書に含まれるすべてのExtended Key Usage (EKU) を順に確認します。
3.  `if ku == x509.ExtKeyUsageClientAuth` で、現在のEKUがクライアント認証用であるかどうかをチェックします。
4.  もしクライアント認証用EKUが見つかれば、`ok = true` に設定し、ループを`break`で抜けます。
5.  ループ終了後、`if !ok` で`ok`が`false`のまま（つまり、クライアント認証用EKUが見つからなかった場合）であれば、`c.sendAlert(alertHandshakeFailure)` でTLSアラートを送信し、`"tls: client's certificate's extended key usage doesn't permit it to be used for client authentication"` というエラーを返してハンドシェイクを中断していました。

この12行のコードが完全に削除されたことにより、リーフ証明書に明示的に`x509.ExtKeyUsageClientAuth`が含まれているかどうかのチェックは行われなくなりました。これにより、EKUフィールドが空のリーフ証明書でも、他の検証（証明書チェーンの信頼性、有効期限など）が成功すれば、クライアント認証が成功するようになります。

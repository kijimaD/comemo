# [インデックス 19780] ファイルの概要

このコミットは、Goランタイムにおけるスタックメモリの会計（`stacks_sys`）に関するバグ修正です。具体的には、解放されたスタックメモリのサイズが、そのメモリ領域（スパン）がヒープにマージされる前に正しく減算されるように修正されています。これにより、`stacks_sys`という統計値が正確に保たれるようになります。

## 変更の背景

Goランタイムは、プログラムの実行中に動的にメモリを管理します。これには、ヒープメモリ（オブジェクトが割り当てられる場所）とスタックメモリ（関数の呼び出しやローカル変数が格納される場所）の両方が含まれます。ランタイムは、これらのメモリ使用量を追跡し、`mstats`構造体を通じて様々な統計情報を提供します。`stacks_sys`は、システムからスタック用に確保されたメモリの総量を示す統計値の一つです。

このコミット以前は、スタックメモリが解放される際に、そのメモリ領域がヒープのフリーリストにマージされる処理（`MHeap_FreeSpanLocked`）の後に、`stacks_inuse`（`stacks_sys`に関連する、現在使用中のスタックメモリ量を示す内部カウンタ）が減算されていました。この順序が問題を引き起こしていました。

具体的には、`MHeap_FreeSpanLocked`が呼び出されると、解放された`MSpan`（メモリの連続したブロック）がヒープのフリーリストに統合される可能性があります。もしこの統合によって、解放されたスパンが別の既存のフリースパンと結合された場合、そのスパンのサイズは既にヒープのフリーメモリとして考慮されることになります。しかし、`stacks_inuse`の減算がその後に行われると、`stacks_inuse`が示す値が、実際にシステムに返却されたメモリ量と一致しなくなり、`stacks_sys`の会計が不正確になる可能性がありました。これは、メモリリークのように見えるか、またはメモリ使用量の統計が過大評価される原因となります。

このコミットは、この会計の不整合を修正することを目的としています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリマネージャ（ガーベージコレクタを含む）を持っています。メモリはページ単位で管理され、これらのページは`MSpan`と呼ばれる連続したブロックにまとめられます。`MSpan`は、オブジェクトの割り当てやスタックの割り当てに使用されます。

### `mheap.c`

`src/pkg/runtime/mheap.c`は、Goランタイムのヒープ管理に関連するコードが含まれるファイルです。ヒープの初期化、メモリの割り当て、解放、および`MSpan`の管理など、低レベルのメモリ操作がここで行われます。

### `MSpan`

`MSpan`は、Goランタイムのメモリ管理における基本的な単位です。これは、連続した物理メモリページのブロックを表します。`MSpan`は、オブジェクトの割り当てに使用されることもあれば、ゴルーチンのスタックとして使用されることもあります。

### `mstats`と`stacks_sys`

`mstats`は、Goランタイムのメモリ統計情報を保持するグローバル構造体です。これには、ヒープの使用量、GCの統計、そしてシステムから確保されたメモリに関する情報などが含まれます。
`stacks_sys`は`mstats`の一部であり、Goランタイムがゴルーチンのスタックのためにシステムから確保したメモリの総量を示します。これは、`mstats.stacks_inuse`という内部カウンタによって追跡されます。

### `MHeap_FreeStack`関数

`MHeap_FreeStack`関数は、ゴルーチンが終了したり、スタックが縮小されたりした際に、不要になったスタックメモリを解放するために呼び出されます。この関数は、解放されるスタックに対応する`MSpan`を受け取り、それをヒープに返却する処理を行います。

### `MHeap_FreeSpanLocked`関数

`MHeap_FreeSpanLocked`関数は、指定された`MSpan`をヒープのフリーリストに返却する役割を担います。この関数が呼び出されると、`MSpan`は適切なフリーリストに追加され、隣接するフリースパンと結合されてより大きなフリースパンを形成する可能性があります。この操作は、ヒープのロックを保持した状態で行われます。

## 技術的詳細

このコミットが修正する問題は、`MHeap_FreeStack`関数における`mstats.stacks_inuse`の減算と`MHeap_FreeSpanLocked`の呼び出し順序にありました。

元のコードでは、以下の順序で処理が行われていました。

1.  `MHeap_FreeSpanLocked(h, s);` // スパンをヒープに解放
2.  `mstats.stacks_inuse -= s->npages<<PageShift;` // `stacks_inuse`を減算

この順序の問題点は、`MHeap_FreeSpanLocked`が呼び出された時点で、解放される`s`スパンがヒープ内の他のフリースパンと結合される可能性があることです。もし結合が発生した場合、そのスパンのメモリは既にヒープのフリーメモリとして再利用可能になっています。しかし、`mstats.stacks_inuse`の減算がその後に行われるため、`stacks_inuse`が示す「使用中のスタックメモリ」の量が、実際には既に解放され、再利用可能になっているメモリを含んでしまう可能性がありました。これにより、`stacks_sys`の統計値が過大に報告されることになります。

このコミットは、この順序を逆にすることで問題を解決します。

1.  `mstats.stacks_inuse -= s->npages<<PageShift;` // `stacks_inuse`を減算
2.  `MHeap_FreeSpanLocked(h, s);` // スパンをヒープに解放

この新しい順序では、`stacks_inuse`の減算が`MSpan`がヒープにマージされる前に行われます。これにより、`stacks_inuse`は常に、実際にまだスタックとして使用されている、またはシステムに返却されていないメモリ量のみを正確に反映するようになります。`MHeap_FreeSpanLocked`が呼び出された時点でスパンが結合されたとしても、`stacks_inuse`は既に正しく更新されているため、`stacks_sys`の会計は正確に保たれます。

## コアとなるコードの解説

変更は`src/pkg/runtime/mheap.c`ファイルの`runtime·MHeap_FreeStack`関数内で行われています。

元のコードでは、以下の行がありました。

```c
	MHeap_FreeSpanLocked(h, s);
	mstats.stacks_inuse -= s->npages<<PageShift;
```

このコミットによって、これらの行の順序が入れ替えられました。

```c
	mstats.stacks_inuse -= s->npages<<PageShift;
	MHeap_FreeSpanLocked(h, s);
```

-   `mstats.stacks_inuse -= s->npages<<PageShift;`
    この行は、解放される`MSpan` `s`が持つページ数（`s->npages`）にページサイズ（`PageShift`はページサイズをバイト単位で表すためのシフト量）を掛けた値を、`mstats.stacks_inuse`から減算しています。これにより、解放されるスタックメモリのサイズが、使用中のスタックメモリの総量から差し引かれます。

-   `MHeap_FreeSpanLocked(h, s);`
    この行は、`MSpan` `s`をヒープのフリーリストに返却します。この関数が実行されると、`s`はヒープの空き領域としてマークされ、必要に応じて隣接する空きスパンと結合されます。

変更の核心は、`mstats.stacks_inuse`の減算を`MHeap_FreeSpanLocked`の呼び出しよりも前に行うことです。これにより、`stacks_inuse`の統計が、スパンがヒープにマージされ、そのメモリが再利用可能になる前に正確に更新されることが保証されます。これは、メモリ会計の正確性を保つ上で非常に重要です。

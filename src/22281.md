## 元コミット内容

`misc/ios: run lldb commands much more carefully`

このコミットは、`lldb`コマンドの実行方法をより慎重にするためのものです。具体的には、コマンドが完了し、`lldb`のプロンプトが表示されるまで待機するメカニズムを導入することで、これまでに発生していた原因不明のエラー（"spurious error"）を削減することを目指しています。

## 変更の背景

この変更の背景には、`lldb`デバッガとの非同期的なやり取りにおける信頼性の問題があります。以前の実装では、`lldb`にコマンドを送信した後、そのコマンドが完全に処理され、デバッガが次の入力を受け付ける準備ができたことを確認せずに次の操作に進んでしまうことがありました。これにより、`lldb`がまだ前のコマンドを処理している最中に次のコマンドが送信され、予期せぬエラーやデバッグセッションの不安定化を引き起こす可能性がありました。

コミットメッセージにある「spurious error」（原因不明のエラー）は、まさにこのような同期の問題に起因するものと考えられます。特に、自動化されたテストやデプロイメントスクリプトのような環境では、デバッガの応答が遅れたり、予期せぬ出力があったりすると、スクリプトが誤動作する原因となります。このコミットは、`lldb`のプロンプトを明示的に待機することで、コマンドの実行順序と完了を保証し、システムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### lldb

`lldb`は、LLVMプロジェクトの一部として開発されている高性能なデバッガです。macOSやiOS開発において、Xcodeに統合された主要なデバッガとして広く利用されています。コマンドラインインターフェースを通じて、プログラムの実行制御（ステップ実行、ブレークポイント設定）、メモリ検査、レジスタ値の表示、変数内容の確認など、多岐にわたるデバッグ機能を提供します。Go言語のクロスコンパイル環境、特にiOSのような組み込みシステムでは、`lldb`のような低レベルデバッガが、GoランタイムとOS間の相互作用をデバッグするために不可欠です。

### ios-deploy

`ios-deploy`は、iOSデバイスにアプリケーションをインストールおよびデバッグするためのコマンドラインツールです。XcodeなしでIPAファイル（iOSアプリケーションアーカイブ）をデバイスにデプロイしたり、デバッグセッションを開始したりする際に使用されます。Go言語で開発されたiOSアプリケーションのテストやデバッグにおいて、ビルドされたGoバイナリをiOSデバイスに転送し、実行可能にするために利用されます。

### Go言語のiOSクロスコンパイル

Go言語は、異なるアーキテクチャやオペレーティングシステム向けにバイナリを生成するクロスコンパイル機能を強力にサポートしています。iOS向けにGoプログラムをビルドする場合、通常は`GOOS=darwin`（macOS/iOS）と`GOARCH=arm`（ARMアーキテクチャ、iOSデバイスのCPU）を設定してコンパイルします。生成されたバイナリは、iOSアプリケーションバンドル（`.app`ディレクトリ）内に配置され、`ios-deploy`などのツールを使ってデバイスにデプロイされます。このプロセスには、GoランタイムがiOS環境で正しく動作するためのCgo（GoとC言語の相互運用）やシステムコールに関する特別な考慮事項が含まれることがあります。

### シグナルハンドリング (SIGSEGV, SIGBUS, EXC_BAD_ACCESS)

*   **SIGSEGV (Segmentation Fault)**: プログラムが不正なメモリアドレスにアクセスしようとしたときに発生するシグナルです。例えば、解放済みのメモリに書き込もうとしたり、読み取り専用のメモリ領域に書き込もうとしたりする場合に発生します。
*   **SIGBUS (Bus Error)**: プログラムが不正なメモリアクセスを行ったときに発生するシグナルですが、SIGSEGVとは異なり、通常はアラインメント違反や、物理的に存在しないアドレスへのアクセスなど、より低レベルのハードウェア関連のエラーを示します。
*   **EXC_BAD_ACCESS**: macOS/iOS環境で発生する例外の一種で、SIGSEGVやSIGBUSと同様に不正なメモリアクセスを示します。これはMachカーネルレベルの例外であり、Unixシグナルにマッピングされることがあります。

デバッガは通常、これらのシグナルが発生した際にプログラムの実行を停止し、開発者が問題の原因を調査できるようにします。このコミットでは、`lldb`に対してこれらのシグナルを捕捉してもプログラムを停止させず、デバッガが引き続き実行を許可するように設定しています（`--stop false --pass true --notify false`）。これは、Goランタイムが内部的にこれらのシグナルを処理する場合があるため、デバッガが不必要に停止するのを防ぐためです。

### `getwd`, `chdir`, `malloc`, `strcat`

これらはC言語の標準ライブラリ関数であり、GoプログラムがCgoを通じて呼び出す可能性があります。

*   **`getwd`**: 現在のワーキングディレクトリのパスを取得します。
*   **`chdir`**: 現在のワーキングディレクトリを変更します。
*   **`malloc`**: 指定されたサイズのメモリブロックを動的に割り当てます。
*   **`strcat`**: 2つの文字列を連結します。

これらの関数は、GoプログラムがiOSデバイス上でファイルシステム操作を行う際に使用されることがあります。

## 技術的詳細

このコミットの主要な技術的変更点は、`lldb`との対話における同期メカニズムの改善です。

1.  **`lldb`コマンド実行の同期化**:
    以前は、`lldb`にコマンドを送信した後、すぐに次の処理に進んでいました。この変更では、`do`関数内で`fmt.Fprintln(lldb, cmd)`でコマンドを送信した後、`waitFor(fmt.Sprintf("prompt after %q", cmd), "(lldb)")`を呼び出すようになりました。`waitFor`関数は、`lldb`の出力ストリームを監視し、`"(lldb)"`というプロンプト文字列が出現するまで待機します。これにより、各`lldb`コマンドが完全に実行され、デバッガが次のコマンドを受け付ける準備ができたことを確認してから、次の操作に進むことが保証されます。これは、特に自動化されたスクリプト環境において、デバッガとの信頼性の高い対話を実現するために非常に重要です。

2.  **パニックからの回復メカニズム (`waitPanic`)**:
    `run`関数に`defer`と`recover`を用いたパニックからの回復メカニズムが導入されました。`waitPanic`というカスタム型が定義され、`waitFor`関数内でエラーが発生した場合に`panic(waitPanic{err})`が呼び出されます。このパニックは`run`関数の`defer`ブロックで捕捉され、`waitPanic`型であればそのエラーが`run`関数の戻り値`err`に設定されます。これにより、`lldb`との対話中に発生したエラーが適切に処理され、`run`関数がエラーを返すことができるようになります。これは、`waitFor`が`do`関数内で呼び出されるようになったため、`do`関数がエラーを直接返すのではなく、パニックを通じてエラーを伝播させる設計になったことと関連しています。

3.  **`lldb`コマンドの`waitFor`呼び出しの削除**:
    いくつかの`lldb`コマンド（例: `process handle SIGUSR1`, `breakpoint set -n getwd`）の後に明示的に`waitFor`を呼び出していた箇所が削除されました。これは、`do`関数自体が内部で`waitFor`を呼び出すようになったため、冗長になったためです。これにより、コードが簡潔になり、`lldb`コマンドの実行とプロンプト待機が一貫した方法で処理されるようになりました。

4.  **ワーキングディレクトリ変更の改善**:
    以前は`chdir`の戻り値を`print`して`waitFor`で確認していましたが、`do(\`call (void)chdir($mem)\`)`に変更されました。これは、`chdir`が成功したかどうかを`lldb`の出力で確認するのではなく、`lldb`コマンドの完了（プロンプトの出現）のみを待つように変更されたことを意味します。これにより、`chdir`の成功確認がより`lldb`のプロンプトベースの同期に依存するようになりました。

5.  **SIGSEGVバックトレースの処理**:
    `SIGSEGV`発生時のバックトレース取得ロジックが変更されました。以前は`do(\`bt\`)`の後に`expr int $dummy = 1`と`print $dummy`を実行し、その結果を`waitFor`で待つという回りくどい方法でバックトレースの終了を検出していました。新しいコードでは、`fmt.Fprintln(lldb, \`bt\`)`を直接呼び出し、`waitFor("finish backtrace", "(lldb)")`で`lldb`プロンプトの出現を待つことで、バックトレースの完了をより直接的に検出するようになりました。これは、`do`関数が別のゴルーチンで実行されるため、`waitPanic`メカニズムが直接適用できないことへの対応でもあります。

## コアとなるコードの解説

### `run`関数のエラーハンドリングと`waitPanic`

`run`関数は、GoプログラムのiOS上での実行と`lldb`との対話を管理する主要な関数です。このコミットでは、`run`関数のシグネチャが`func run(bin string, args []string) (err error)`に変更され、エラーを返すようになりました。

最も重要な変更は、`defer`と`recover`を用いたパニックからの回復メカニズムの導入です。
```go
type waitPanic struct {
    err error
}
defer func() {
    if r := recover(); r != nil {
        if w, ok := r.(waitPanic); ok {
            err = w.err
            return
        }
        panic(r)
    }
}()
```
これは、`lldb`コマンドの実行をラップする`do`関数内で`waitFor`がエラーを返した場合に、そのエラーを`waitPanic`としてパニックさせるためのものです。このパニックは`run`関数の`defer`ブロックで捕捉され、`waitPanic`型であれば、その内部のエラーが`run`関数の戻り値`err`に設定されます。これにより、`lldb`との対話中に発生した同期エラーが、`run`関数の呼び出し元に適切に伝播されるようになります。`waitPanic`型でないパニックは再パニックされ、予期せぬランタイムエラーとして扱われます。

### `do`関数の変更と`lldb`コマンドの同期

`do`関数は、`lldb`にコマンドを送信するためのヘルパー関数です。
```go
do := func(cmd string) {
    fmt.Fprintln(lldb, cmd)
    if err := waitFor(fmt.Sprintf("prompt after %q", cmd), "(lldb)"); err != nil {
        panic(waitPanic{err})
    }
}
```
以前は単にコマンドを`lldb`に書き込むだけでしたが、この変更により、コマンドを送信した後に必ず`waitFor`を呼び出すようになりました。`waitFor`は、`lldb`の出力ストリームを監視し、`"(lldb)"`というプロンプト文字列が出現するまでブロックします。これにより、`lldb`が前のコマンドの処理を完了し、次のコマンドを受け付ける準備ができたことを確認してから、`do`関数が戻るようになります。この同期メカニズムは、`lldb`との対話の信頼性を大幅に向上させ、特にスクリプトによる自動化されたデバッグセッションにおいて、コマンドの順序が保証されることで「spurious error」の発生を防ぎます。`waitFor`がエラーを返した場合は、前述の`waitPanic`を発生させます。

### 冗長な`waitFor`呼び出しの削除と直接的な`fmt.Fprintln`

`do`関数が内部で`waitFor`を呼び出すようになったため、以前は`do`関数の後に明示的に`waitFor`を呼び出していた箇所（例: `process handle`や`breakpoint set`の後）が削除されました。これはコードの重複をなくし、一貫性を保つためのリファクタリングです。

また、`run`コマンドや`process continue`コマンドは、`do`関数を介さずに直接`fmt.Fprintln(lldb, ...)`で送信されるようになりました。これは、これらのコマンドの後に特定の`lldb`プロンプトを待つのではなく、より複雑な条件（例: `br getwd`のブレークポイントヒット、テストの完了）を`waitFor`で待つ必要があるためと考えられます。

### ワーキングディレクトリ変更とSIGSEGVハンドリングの改善

ワーキングディレクトリを変更する`chdir`の呼び出しは、以前は`expr int $res = (int)chdir($mem)`としてその結果を`print`し、`waitFor`で`"(int) $res = 0"`を待つことで成功を確認していました。これが`do(\`call (void)chdir($mem)\`)`に変更されました。これは、`chdir`の成功を`lldb`の出力で明示的に確認するのではなく、`do`関数による`lldb`プロンプトの待機によってコマンドの完了を間接的に確認するアプローチに変わったことを示唆しています。

`SIGSEGV`発生時のバックトレース取得ロジックも変更されました。以前の`do(\`bt\`)`の後に`expr int $dummy = 1`と`print $dummy`を実行し、その結果を`waitFor`で待つという方法は、バックトレースの終了を検出するためのハックでした。新しいコードでは、`fmt.Fprintln(lldb, \`bt\`)`を直接呼び出し、`waitFor("finish backtrace", "(lldb)")`で`lldb`プロンプトの出現を待つことで、より直接的にバックトレースの完了を検出するようになりました。この変更は、`SIGSEGV`ハンドリングが別のゴルーチンで行われるため、`do`関数が使用する`waitPanic`メカニズムが直接適用できないことへの対応でもあります。

## 元コミット内容

`misc/ios: run lldb commands much more carefully`

このコミットは、`lldb`コマンドの実行方法をより慎重にするためのものです。具体的には、コマンドが完了し、`lldb`のプロンプトが表示されるまで待機するメカニズムを導入することで、これまでに発生していた原因不明のエラー（"spurious error"）を削減することを目指しています。

## 変更の背景

この変更の背景には、`lldb`デバッガとの非同期的なやり取りにおける信頼性の問題があります。以前の実装では、`lldb`にコマンドを送信した後、そのコマンドが完全に処理され、デバッガが次の入力を受け付ける準備ができたことを確認せずに次の操作に進んでしまうことがありました。これにより、`lldb`がまだ前のコマンドを処理している最中に次のコマンドが送信され、予期せぬエラーやデバッグセッションの不安定化を引き起こす可能性がありました。

コミットメッセージにある「spurious error」（原因不明のエラー）は、まさにこのような同期の問題に起因するものと考えられます。特に、自動化されたテストやデプロイメントスクリプトのような環境では、デバッガの応答が遅れたり、予期せぬ出力があったりすると、スクリプトが誤動作する原因となります。このコミットは、`lldb`のプロンプトを明示的に待機することで、コマンドの実行順序と完了を保証し、システムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### lldb

`lldb`は、LLVMプロジェクトの一部として開発されている高性能なデバッガです。macOSやiOS開発において、Xcodeに統合された主要なデバッガとして広く利用されています。コマンドラインインターフェースを通じて、プログラムの実行制御（ステップ実行、ブレークポイント設定）、メモリ検査、レジスタ値の表示、変数内容の確認など、多岐にわたるデバッグ機能を提供します。Go言語のクロスコンパイル環境、特にiOSのような組み込みシステムでは、`lldb`のような低レベルデバッガが、GoランタイムとOS間の相互作用をデバッグするために不可欠です。

### ios-deploy

`ios-deploy`は、iOSデバイスにアプリケーションをインストールおよびデバッグするためのコマンドラインツールです。XcodeなしでIPAファイル（iOSアプリケーションアーカイブ）をデバイスにデプロイしたり、デバッグセッションを開始したりする際に使用されます。Go言語で開発されたiOSアプリケーションのテストやデバッグにおいて、ビルドされたGoバイナリをiOSデバイスに転送し、実行可能にするために利用されます。

### Go言語のiOSクロスコンパイル

Go言語は、異なるアーキテクチャやオペレーティングシステム向けにバイナリを生成するクロスコンパイル機能を強力にサポートしています。iOS向けにGoプログラムをビルドする場合、通常は`GOOS=darwin`（macOS/iOS）と`GOARCH=arm`（ARMアーキテクチャ、iOSデバイスのCPU）を設定してコンパイルします。生成されたバイナリは、iOSアプリケーションバンドル（`.app`ディレクトリ）内に配置され、`ios-deploy`などのツールを使ってデバイスにデプロイされます。このプロセスには、GoランタイムがiOS環境で正しく動作するためのCgo（GoとC言語の相互運用）やシステムコールに関する特別な考慮事項が含まれることがあります。

### シグナルハンドリング (SIGSEGV, SIGBUS, EXC_BAD_ACCESS)

*   **SIGSEGV (Segmentation Fault)**: プログラムが不正なメモリアドレスにアクセスしようとしたときに発生するシグナルです。例えば、解放済みのメモリに書き込もうとしたり、読み取り専用のメモリ領域に書き込もうとしたりする場合に発生します。
*   **SIGBUS (Bus Error)**: プログラムが不正なメモリアクセスを行ったときに発生するシグナルですが、SIGSEGVとは異なり、通常はアラインメント違反や、物理的に存在しないアドレスへのアクセスなど、より低レベルのハードウェア関連のエラーを示します。
*   **EXC_BAD_ACCESS**: macOS/iOS環境で発生する例外の一種で、SIGSEGVやSIGBUSと同様に不正なメモリアクセスを示します。これはMachカーネルレベルの例外であり、Unixシグナルにマッピングされることがあります。

デバッガは通常、これらのシグナルが発生した際にプログラムの実行を停止し、開発者が問題の原因を調査できるようにします。このコミットでは、`lldb`に対してこれらのシグナルを捕捉してもプログラムを停止させず、デバッガが引き続き実行を許可するように設定しています（`--stop false --pass true --notify false`）。これは、Goランタイムが内部的にこれらのシグナルを処理する場合があるため、デバッガが不必要に停止するのを防ぐためです。

### `getwd`, `chdir`, `malloc`, `strcat`

これらはC言語の標準ライブラリ関数であり、GoプログラムがCgoを通じて呼び出す可能性があります。

*   **`getwd`**: 現在のワーキングディレクトリのパスを取得します。
*   **`chdir`**: 現在のワーキングディレクトリを変更します。
*   **`malloc`**: 指定されたサイズのメモリブロックを動的に割り当てます。
*   **`strcat`**: 2つの文字列を連結します。

これらの関数は、GoプログラムがiOSデバイス上でファイルシステム操作を行う際に使用されることがあります。

## 技術的詳細

このコミットの主要な技術的変更点は、`lldb`との対話における同期メカニズムの改善です。

1.  **`lldb`コマンド実行の同期化**:
    以前は、`lldb`にコマンドを送信した後、すぐに次の処理に進んでいました。この変更では、`do`関数内で`fmt.Fprintln(lldb, cmd)`でコマンドを送信した後、`waitFor(fmt.Sprintf("prompt after %q", cmd), "(lldb)")`を呼び出すようになりました。`waitFor`関数は、`lldb`の出力ストリームを監視し、`"(lldb)"`というプロンプト文字列が出現するまで待機します。これにより、各`lldb`コマンドが完全に実行され、デバッガが次のコマンドを受け付ける準備ができたことを確認してから、次の操作に進むことが保証されます。これは、特に自動化されたスクリプト環境において、デバッガとの信頼性の高い対話を実現するために非常に重要です。

2.  **パニックからの回復メカニズム (`waitPanic`)**:
    `run`関数に`defer`と`recover`を用いたパニックからの回復メカニズムが導入されました。`waitPanic`というカスタム型が定義され、`waitFor`関数内でエラーが発生した場合に`panic(waitPanic{err})`が呼び出されます。このパニックは`run`関数の`defer`ブロックで捕捉され、`waitPanic`型であればそのエラーが`run`関数の戻り値`err`に設定されます。これにより、`lldb`との対話中に発生したエラーが適切に処理され、`run`関数がエラーを返すことができるようになります。これは、`waitFor`が`do`関数内で呼び出されるようになったため、`do`関数がエラーを直接返すのではなく、パニックを通じてエラーを伝播させる設計になったことと関連しています。

3.  **`lldb`コマンドの`waitFor`呼び出しの削除**:
    いくつかの`lldb`コマンド（例: `process handle SIGUSR1`, `breakpoint set -n getwd`）の後に明示的に`waitFor`を呼び出していた箇所が削除されました。これは、`do`関数自体が内部で`waitFor`を呼び出すようになったため、冗長になったためです。これにより、コードが簡潔になり、`lldb`コマンドの実行とプロンプト待機が一貫した方法で処理されるようになりました。

4.  **ワーキングディレクトリ変更の改善**:
    以前は`chdir`の戻り値を`print`して`waitFor`で確認していましたが、`do(\`call (void)chdir($mem)\`)`に変更されました。これは、`chdir`が成功したかどうかを`lldb`の出力で確認するのではなく、`lldb`コマンドの完了（プロンプトの出現）のみを待つように変更されたことを意味します。これにより、`chdir`の成功確認がより`lldb`のプロンプトベースの同期に依存するようになりました。

5.  **SIGSEGVバックトレースの処理**:
    `SIGSEGV`発生時のバックトレース取得ロジックが変更されました。以前は`do(\`bt\`)`の後に`expr int $dummy = 1`と`print $dummy`を実行し、その結果を`waitFor`で待つという回りくどい方法でバックトレースの終了を検出していました。新しいコードでは、`fmt.Fprintln(lldb, \`bt\`)`を直接呼び出し、`waitFor("finish backtrace", "(lldb)")`で`lldb`プロンプトの出現を待つことで、バックトレースの完了をより直接的に検出するようになりました。これは、`do`関数が別のゴルーチンで実行されるため、`waitPanic`メカニズムが直接適用できないことへの対応でもあります。

## コアとなるコードの解説

### `run`関数のエラーハンドリングと`waitPanic`

`run`関数は、GoプログラムのiOS上での実行と`lldb`との対話を管理する主要な関数です。このコミットでは、`run`関数のシグネチャが`func run(bin string, args []string) (err error)`に変更され、エラーを返すようになりました。

最も重要な変更は、`defer`と`recover`を用いたパニックからの回復メカニズムの導入です。
```go
type waitPanic struct {
    err error
}
defer func() {
    if r := recover(); r != nil {
        if w, ok := r.(waitPanic); ok {
            err = w.err
            return
        }
        panic(r)
    }
}()
```
これは、`lldb`コマンドの実行をラップする`do`関数内で`waitFor`がエラーを返した場合に、そのエラーを`waitPanic`としてパニックさせるためのものです。このパニックは`run`関数の`defer`ブロックで捕捉され、`waitPanic`型であれば、その内部のエラーが`run`関数の戻り値`err`に設定されます。これにより、`lldb`との対話中に発生した同期エラーが、`run`関数の呼び出し元に適切に伝播されるようになります。`waitPanic`型でないパニックは再パニックされ、予期せぬランタイムエラーとして扱われます。

### `do`関数の変更と`lldb`コマンドの同期

`do`関数は、`lldb`にコマンドを送信するためのヘルパー関数です。
```go
do := func(cmd string) {
    fmt.Fprintln(lldb, cmd)
    if err := waitFor(fmt.Sprintf("prompt after %q", cmd), "(lldb)"); err != nil {
        panic(waitPanic{err})
    }
}
```
以前は単にコマンドを`lldb`に書き込むだけでしたが、この変更により、コマンドを送信した後に必ず`waitFor`を呼び出すようになりました。`waitFor`は、`lldb`の出力ストリームを監視し、`"(lldb)"`というプロンプト文字列が出現するまでブロックします。これにより、`lldb`が前のコマンドの処理を完了し、次のコマンドを受け付ける準備ができたことを確認してから、`do`関数が戻るようになります。この同期メカニズムは、`lldb`との対話の信頼性を大幅に向上させ、特にスクリプトによる自動化されたデバッグセッションにおいて、コマンドの順序が保証されることで「spurious error」の発生を防ぎます。`waitFor`がエラーを返した場合は、前述の`waitPanic`を発生させます。

### 冗長な`waitFor`呼び出しの削除と直接的な`fmt.Fprintln`

`do`関数が内部で`waitFor`を呼び出すようになったため、以前は`do`関数の後に明示的に`waitFor`を呼び出していた箇所（例: `process handle`や`breakpoint set`の後）が削除されました。これはコードの重複をなくし、一貫性を保つためのリファクタリングです。

また、`run`コマンドや`process continue`コマンドは、`do`関数を介さずに直接`fmt.Fprintln(lldb, ...)`で送信されるようになりました。これは、これらのコマンドの後に特定の`lldb`プロンプトを待つのではなく、より複雑な条件（例: `br getwd`のブレークポイントヒット、テストの完了）を`waitFor`で待つ必要があるためと考えられます。

### ワーキングディレクトリ変更とSIGSEGVハンドリングの改善

ワーキングディレクトリを変更する`chdir`の呼び出しは、以前は`expr int $res = (int)chdir($mem)`としてその結果を`print`し、`waitFor`で`"(int) $res = 0"`を待つことで成功を確認していました。これが`do(\`call (void)chdir($mem)\`)`に変更されました。これは、`chdir`の成功を`lldb`の出力で明示的に確認するのではなく、`do`関数による`lldb`プロンプトの待機によってコマンドの完了を間接的に確認するアプローチに変わったことを示唆しています。

`SIGSEGV`発生時のバックトレース取得ロジックも変更されました。以前の`do(\`bt\`)`の後に`expr int $dummy = 1`と`print $dummy`を実行し、その結果を`waitFor`で待つという方法は、バックトレースの終了を検出するためのハックでした。新しいコードでは、`fmt.Fprintln(lldb, \`bt\`)`を直接呼び出し、`waitFor("finish backtrace", "(lldb)")`で`lldb`プロンプトの出現を待つことで、より直接的にバックトレースの完了を検出するようになりました。この変更は、`SIGSEGV`ハンドリングが別のゴルーチンで行われるため、`do`関数が使用する`waitPanic`メカニズムが直接適用できないことへの対応でもあります。

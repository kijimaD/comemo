# [インデックス 19955] ファイルの概要

このコミットは、Go言語のビルドシステム (`go/build` パッケージ) におけるインポートパスの解決ロジックを修正するものです。具体的には、`cmd/` プレフィックスを持つパッケージのインポート時に `$GOROOT/src/cmd/` 以下を探索するように変更し、`cmd/internal` のような非 `main` パッケージの利用を可能にしています。

## 変更の背景

この変更の背景には、Go言語の標準ライブラリおよびツールチェインの構造に関する進化があります。

Go 1.4リリースに向けて、Goプロジェクトでは大規模なリポジトリ構造の変更が計画されていました。これは `src/pkg` ディレクトリの廃止と、すべての標準ライブラリパッケージを `src/` 直下に移動するというものです。この変更は `golang.org/s/go14mainrepo` で議論されており、その目的の一つは、Goツールチェイン自体が使用する内部パッケージ（例えば `cmd/internal` のようなもの）をより自然に管理できるようにすることでした。

従来のGoのビルドシステムでは、`import "foo/bar"` のようなパスは通常 `$GOROOT/src/pkg/foo/bar` を探索していました。しかし、Goツールチェインのコマンド（`go build`, `go run` など）は `$GOROOT/src/cmd/` 以下に配置されており、これらのコマンドが共有する内部パッケージを持つ場合、そのインポートパスの解決が問題となっていました。例えば、`cmd/nm` コマンドが `cmd/nm/internal/objfile` のようなパッケージをインポートしようとした場合、ビルドシステムは `$GOROOT/src/pkg/cmd/nm/internal/objfile` を探しに行ってしまい、正しく解決できませんでした。

このコミットは、`src/pkg` 移行が完全に完了する前に、`cmd/` プレフィックスを持つパッケージが `$GOROOT/src/cmd/` 以下から直接インポートできるようにすることで、この問題を先行して解決し、`cmd/internal` のような内部パッケージの利用を可能にすることを目的としています。これにより、Goツールチェインの内部構造をより整理し、モジュール化を進めることができました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびGoツールチェインに関する知識が必要です。

1.  **`$GOROOT`**: Goのインストールディレクトリを指す環境変数です。Goの標準ライブラリやツールチェインのソースコードがこのディレクトリ以下に配置されています。
2.  **`go/build` パッケージ**: Goのソースコードを解析し、パッケージの依存関係を解決し、ビルドに必要な情報を取得するためのGo標準ライブラリのパッケージです。`go build` コマンドなどの基盤となっています。
3.  **パッケージのインポートパス解決**: Goでは、`import "path/to/package"` の形式でパッケージをインポートします。ビルドシステムは、このパスを基にファイルシステム上の対応するディレクトリを探します。
    *   通常、Go 1.4以前では、標準ライブラリパッケージは `$GOROOT/src/pkg/` 以下に配置されていました。
    *   ユーザーが作成したパッケージは `$GOPATH/src/` 以下に配置されます。
4.  **`cmd/` パッケージ**: Goツールチェインの実行可能コマンド（例: `go`, `gofmt`, `vet` など）のソースコードは `$GOROOT/src/cmd/` 以下に配置されています。これらのパッケージは通常 `package main` であり、実行可能なバイナリを生成します。
5.  **`internal` パッケージ**: Go 1.4で導入された、パッケージの外部からのインポートを制限するための特別なディレクトリ名です。`internal` ディレクトリ内のパッケージは、その親ディレクトリのツリー内からのみインポート可能です。例えば、`a/b/internal/c` は `a/b/d` からはインポートできますが、`a/e` からはインポートできません。このコミットは `internal` パッケージの概念が導入される前のものですが、`cmd/internal` のような構造を可能にする点で関連性があります。
6.  **`golang.org/s/go14mainrepo`**: Go 1.4におけるリポジトリ構造の変更に関する設計ドキュメントへのショートリンクです。この変更は、Goのソースコード管理とビルドプロセスを簡素化し、将来的なモジュールシステムへの移行を容易にすることを目的としていました。

## 技術的詳細

このコミットの技術的な核心は、`go/build` パッケージの `Context.Import` メソッドにおけるインポートパスの解決ロジックの変更です。

`Context.Import` メソッドは、与えられたインポートパス (`path`) と現在のソースディレクトリ (`srcDir`) を基に、対応するGoパッケージの情報を取得します。このメソッドは、Goのビルドプロセスにおいて、依存するパッケージのソースコードの場所を特定するために非常に重要です。

変更前は、`$GOROOT` 内のパッケージを探索する際、常に `$GOROOT/src/pkg/` ディレクトリをプレフィックスとしていました。

```go
// 変更前
dir := ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
```

このロジックでは、`cmd/foo/bar` のようなインポートパスが与えられた場合、`$GOROOT/src/pkg/cmd/foo/bar` を探しに行ってしまいます。しかし、Goツールチェインのコマンドに関連するパッケージは `$GOROOT/src/cmd/` 以下に直接配置されており、`src/pkg` の下にはありません。このため、`cmd/internal` のようなパッケージをインポートしようとすると、ビルドエラーが発生していました。

このコミットでは、インポートパスが `"cmd/"` で始まるかどうかをチェックする条件分岐が追加されました。

```go
// 変更後
var dir string
if strings.HasPrefix(path, "cmd/") {
    dir = ctxt.joinPath(ctxt.GOROOT, "src", path)
} else {
    dir = ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
}
```

この変更により、インポートパスが `cmd/` で始まる場合（例: `cmd/internal/objfile`）、`go/build` パッケージは `$GOROOT/src/cmd/internal/objfile` を探索するようになります。これにより、Goツールチェインの内部パッケージが正しくインポートできるようになり、コードのモジュール化と再利用が促進されます。

この変更は、Go 1.4で予定されていた `src/pkg` ディレクトリの廃止と、すべての標準ライブラリパッケージを `src/` 直下に移動する大規模なリポジトリ構造変更の「先行実装」としての側面も持っています。`src/pkg` が廃止されれば、すべてのパッケージが `src/` 直下から解決されるようになるため、この特定の `cmd/` プレフィックスの特別扱いは将来的には不要になります。しかし、このコミットは、その移行期間中に `cmd/internal` のような構造を早期に利用可能にするための実用的な解決策を提供しました。

テストケース `TestImportCmd` が追加され、`cmd/internal/objfile` のインポートが正しく解決されることを検証しています。これは、変更が意図通りに機能し、将来の回帰を防ぐための重要なステップです。

## コアとなるコードの解説

### `src/pkg/go/build/build.go` の変更

`Context.Import` メソッドは、Goのビルドコンテキスト内でパッケージをインポートする際のパス解決を担当します。

-   **変更前**:
    ```go
    dir := ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
    ```
    この行は、`$GOROOT` 内のパッケージを探す際に、常に `src/pkg` を中間パスとして含めていました。これは、Goの標準ライブラリパッケージが歴史的に `src/pkg` 以下に配置されていたためです。

-   **変更後**:
    ```go
    var dir string
    if strings.HasPrefix(path, "cmd/") {
        dir = ctxt.joinPath(ctxt.GOROOT, "src", path)
    } else {
        dir = ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
    }
    ```
    この変更により、インポートしようとしている `path` が `"cmd/"` で始まるかどうかを `strings.HasPrefix` でチェックします。
    -   もし `path` が `"cmd/"` で始まる場合（例: `cmd/internal/objfile`）、`dir` は `$GOROOT/src/` の直下に `path` を結合して構築されます。これにより、`$GOROOT/src/cmd/internal/objfile` のようなパスが正しく解決されるようになります。
    -   それ以外の場合（`cmd/` で始まらない通常の標準ライブラリパッケージなど）、`dir` は以前と同様に `$GOROOT/src/pkg/` を経由して構築されます。

この条件分岐の追加により、`go/build` パッケージは、Goツールチェインの内部パッケージが配置されている `$GOROOT/src/cmd/` ディレクトリを正しく認識し、そこからパッケージをインポートできるようになりました。

### `src/pkg/go/build/build_test.go` の変更

`TestImportCmd` という新しいテスト関数が追加されました。

```go
func TestImportCmd(t *testing.T) {
    p, err := Import("cmd/internal/objfile", "", 0)
    if err != nil {
        t.Fatal(err)
    }
    if !strings.HasSuffix(filepath.ToSlash(p.Dir), "src/cmd/internal/objfile") {
        t.Fatalf("Import cmd/internal/objfile returned Dir=%q, want %q", filepath.ToSlash(p.Dir), ".../src/cmd/internal/objfile")
    }
}
```

-   このテストは、`go/build` パッケージの `Import` 関数を呼び出し、`"cmd/internal/objfile"` というインポートパスを渡しています。
-   エラーが発生した場合はテストを失敗させます。
-   最も重要なのは、`p.Dir` (インポートされたパッケージのディレクトリパス) が `src/cmd/internal/objfile` で終わることを検証している点です。`filepath.ToSlash` は、OSに依存しないパス形式に変換するために使用されています。
-   このテストにより、`cmd/` プレフィックスを持つパッケージが `$GOROOT/src/cmd/` 以下から正しく解決されるという、このコミットの主要な機能が保証されます。

この変更は、Go 1.4で予定されていた `src/pkg` ディレクトリの廃止と、すべての標準ライブラリパッケージを `src/` 直下に移動する大規模なリポジトリ構造変更の「先行実装」としての側面も持っています。`src/pkg` が廃止されれば、すべてのパッケージが `src/` 直下から解決されるようになるため、この特定の `cmd/` プレフィックスの特別扱いは将来的には不要になります。しかし、このコミットは、その移行期間中に `cmd/internal` のような構造を早期に利用可能にするための実用的な解決策を提供しました。

テストケース `TestImportCmd` が追加され、`cmd/internal/objfile` のインポートが正しく解決されることを検証しています。これは、変更が意図通りに機能し、将来の回帰を防ぐための重要なステップです。

## コアとなるコードの解説

### `src/pkg/go/build/build.go` の変更

`Context.Import` メソッドは、Goのビルドコンテキスト内でパッケージをインポートする際のパス解決を担当します。

-   **変更前**:
    ```go
    dir := ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
    ```
    この行は、`$GOROOT` 内のパッケージを探す際に、常に `src/pkg` を中間パスとして含めていました。これは、Goの標準ライブラリパッケージが歴史的に `src/pkg` 以下に配置されていたためです。

-   **変更後**:
    ```go
    var dir string
    if strings.HasPrefix(path, "cmd/") {
        dir = ctxt.joinPath(ctxt.GOROOT, "src", path)
    } else {
        dir = ctxt.joinPath(ctxt.GOROOT, "src", "pkg", path)
    }
    ```
    この変更により、インポートしようとしている `path` が `"cmd/"` で始まるかどうかを `strings.HasPrefix` でチェックします。
    -   もし `path` が `"cmd/"` で始まる場合（例: `cmd/internal/objfile`）、`dir` は `$GOROOT/src/` の直下に `path` を結合して構築されます。これにより、`$GOROOT/src/cmd/internal/objfile` のようなパスが正しく解決されるようになります。
    -   それ以外の場合（`cmd/` で始まらない通常の標準ライブラリパッケージなど）、`dir` は以前と同様に `$GOROOT/src/pkg/` を経由して構築されます。

この条件分岐の追加により、`go/build` パッケージは、Goツールチェインの内部パッケージが配置されている `$GOROOT/src/cmd/` ディレクトリを正しく認識し、そこからパッケージをインポートできるようになりました。

### `src/pkg/go/build/build_test.go` の変更

`TestImportCmd` という新しいテスト関数が追加されました。

```go
func TestImportCmd(t *testing.T) {
    p, err := Import("cmd/internal/objfile", "", 0)
    if err != nil {
        t.Fatal(err)
    }
    if !strings.HasSuffix(filepath.ToSlash(p.Dir), "src/cmd/internal/objfile") {
        t.Fatalf("Import cmd/internal/objfile returned Dir=%q, want %q", filepath.ToSlash(p.Dir), ".../src/cmd/internal/objfile")
    }
}
```

-   このテストは、`go/build` パッケージの `Import` 関数を呼び出し、`"cmd/internal/objfile"` というインポートパスを渡しています。
-   エラーが発生した場合はテストを失敗させます。
-   最も重要なのは、`p.Dir` (インポートされたパッケージのディレクトリパス) が `src/cmd/internal/objfile` で終わることを検証している点です。`filepath.ToSlash` は、OSに依存しないパス形式に変換するために使用されています。
-   このテストにより、`cmd/` プレフィックスを持つパッケージが `$GOROOT/src/cmd/` 以下から正しく解決されるという、このコミットの主要な機能が保証されます。

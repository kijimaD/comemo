## 変更の背景

この変更は、Goのテストスイートの一部である `recover4` テストが `ppc64` および `ppc64le` アーキテクチャ上でビルドエラーまたはテスト失敗を引き起こしていた問題に対応するために行われました。コミットメッセージによると、この問題の根本原因は、Goのビルドシステムが使用する `ppc64` システムのビルド環境が64KBのページサイズを使用していることにありました。

`recover4` テストは、おそらくメモリマッピング（`mmap`）に関連する特定の動作やメモリレイアウトに依存しており、標準的な4KBページサイズとは異なる64KBページサイズ環境では正しく機能しなかったと考えられます。当時、ホストシステムのページサイズをポータブルな方法で取得する手段がなかったため、`mmap` で確保する領域（"mmap hole"）のサイズを正確に調整することが困難でした。

この問題を解決するための長期的な修正が利用可能になるまでの間、`ppc64` および `ppc64le` システムでのビルドを一時的にアンブロックするために、このテストを無効化するという暫定的な措置が取られました。これは、特定の環境でのテストの失敗が全体の開発フローを妨げないようにするための一般的なプラクティスです。

## 前提知識の解説

### Go ビルドタグ (Build Tags / Build Constraints)

Go言語には、ソースファイルのコンパイルを特定の条件に基づいて制御するための「ビルドタグ」（またはビルド制約）というメカニズムがあります。これは、ファイルの先頭に `// +build tag` の形式でコメントとして記述されます。

-   **`// +build tag1,tag2`**: `tag1` または `tag2` のいずれかが有効な場合にファイルがコンパイルされます（論理OR）。
-   **`// +build tag1 tag2`**: `tag1` と `tag2` の両方が有効な場合にファイルがコンパイルされます（論理AND）。
-   **`// +build !tag`**: `tag` が有効でない場合にファイルがコンパイルされます（論理NOT）。

これらのタグは、`go build` や `go test` などのコマンド実行時に、`-tags` フラグで指定されたタグと照合されます。また、Goツールチェーンは、オペレーティングシステム（`linux`, `windows`, `darwin` など）やアーキテクチャ（`amd64`, `arm`, `ppc64` など）に基づいて自動的にタグを適用します。

このコミットでは `// +build !ppc64,!ppc64le` が使用されており、これは「`ppc64` も `ppc64le` も有効でない場合にコンパイルする」という意味になります。

### `ppc64` および `ppc64le` アーキテクチャ

-   **`ppc64`**: IBM PowerPC 64ビットプロセッサアーキテクチャを指します。主にサーバーや高性能コンピューティング（HPC）環境で使用されます。
-   **`ppc64le`**: PowerPC 64ビットのLittle-Endian版を指します。従来のPowerPCはBig-Endianが主流でしたが、x86との互換性や特定のワークロードのためにLittle-Endian版も存在します。

これらのアーキテクチャは、メモリのページサイズやその他のシステム特性がx86_64などの一般的なアーキテクチャと異なる場合があります。

### メモリページサイズ

現代のオペレーティングシステムは、物理メモリを「ページ」と呼ばれる固定サイズのブロックに分割して管理します。仮想メモリシステムでは、仮想アドレス空間もページに分割され、これらの仮想ページが物理ページにマッピングされます。一般的なシステムでは、ページサイズは4KBですが、高性能システムや特定のアーキテクチャでは、より大きなページサイズ（例: 64KB、2MB、1GB）を使用することがあります。大きなページサイズは、TLB（Translation Lookaside Buffer）ミスを減らし、メモリ管理のオーバーヘッドを削減することで、パフォーマンスを向上させる可能性があります。

### `mmap` (Memory Map)

`mmap` は、Unix系システムコールの一つで、ファイルやデバイスをプロセスのアドレス空間にマッピングするために使用されます。これにより、ファイルの内容を通常のメモリ操作（ポインタのデリファレンスなど）で直接読み書きできるようになります。`mmap` は、共有メモリ、ファイルI/Oの高速化、動的ライブラリのロードなど、様々な用途で利用されます。`mmap` で確保されるメモリ領域は、システムのページサイズにアラインされている必要があります。

## 技術的詳細

`recover4` テストが `ppc64` および `ppc64le` 環境で失敗した原因は、これらのシステムが64KBのメモリページサイズを使用していることにありました。Goランタイムのメモリ管理、特に `mmap` を使用してメモリを確保する部分では、システムのページサイズを考慮する必要があります。

Goランタイムは、ヒープ領域やスタック領域などを管理するために `mmap` を利用します。特定のテスト（`recover4`）が、`mmap` によって確保されたメモリ領域のサイズやアラインメント、あるいはその領域内での特定のメモリ操作に依存していた可能性があります。64KBという大きなページサイズは、テストが期待するメモリレイアウトやアラインメントと合致せず、結果としてテストの失敗やクラッシュを引き起こしたと考えられます。

コミットメッセージにある「mmap hole」とは、`mmap` を使用して確保されるメモリ領域のことで、Goランタイムが特定の目的のために予約する領域を指すことがあります。この「mmap hole」のサイズを、ホストのページサイズに合わせて正確に調整する必要があったものの、当時のGoランタイムには、実行時にホストのページサイズをポータブルかつ確実に取得するメカニズムが不足していました。

このため、開発チームは、問題の根本的な解決策（ポータブルなページサイズ取得メカニズムの実装）が導入されるまでの間、影響を受けるアーキテクチャでテストを一時的に無効化するという判断を下しました。これは、CI/CDパイプラインの健全性を維持し、他の開発作業がブロックされないようにするための実用的なアプローチです。

`// +build !ppc64,!ppc64le` というビルドタグの追加は、Goツールチェーンに対して、コンパイル対象のアーキテクチャが `ppc64` または `ppc64le` のいずれかである場合、`test/recover4.go` ファイルをコンパイル対象から除外するよう指示します。これにより、これらのアーキテクチャでビルドが実行される際に、問題のあるテストコードが組み込まれることがなくなり、ビルドの成功が保証されます。

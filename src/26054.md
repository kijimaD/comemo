# [インデックス 26054] ファイルの概要

このコミットは、Goランタイムにおけるヒープのライブサイズ（`memstats.heap_live`）の過小評価を修正することを目的としています。特に、`mcache.local_cachealloc`がヒープのライブサイズを正確に反映しない場合があり、これがガベージコレクタ（GC）の動作に悪影響を与える可能性がありました。この変更により、`local_cachealloc`が廃止され、`heap_live`がより正確かつ保守的に更新されるようになります。

## 元コミット内容

```
runtime: fix (sometimes major) underestimation of heap_live

Currently, we update memstats.heap_live from mcache.local_cachealloc
whenever we lock the heap (e.g., to obtain a fresh span or to release
an unused span). However, under the right circumstances,
local_cachealloc can accumulate allocations up to the size of
the *entire heap* without flushing them to heap_live. Specifically,
since span allocations from an mcentral don't lock the heap, if a
large number of pages are held in an mcentral and the application
continues to use and free objects of that size class (e.g., the
BinaryTree17 benchmark), local_cachealloc won't be flushed until the
mcentral runs out of spans.

This is a problem because, unlike many of the memory statistics that
are purely informative, heap_live is used to determine when the
garbage collector should start and how hard it should work.

This commit eliminates local_cachealloc, instead atomically updating
heap_live directly. To control contention, we do this only when
obtaining a span from an mcentral. Furthermore, we make heap_live
conservative: allocating a span assumes that all free slots in that
span will become used and accounts for these when the span is
allocated, *before* the objects themselves are. This is important
because 1) this triggers the GC earlier than necessary rather than
potentially too late and 2) this leads to a conservative GC rate
rather than a GC rate that is potentially too low.

Alternatively, we could have flushed local_cachealloc when it passed
some threshold, but this would require determining a threshold and
would cause heap_live to underestimate the true value rather than
overestimate.

Fixes #12199.
```

## 変更の背景

Goのランタイムは、ガベージコレクタ（GC）の起動タイミングや動作強度を決定するために、`memstats.heap_live`という統計情報を使用しています。これは、GCによって「生きている」と判断されたヒープメモリの量と、それ以降に割り当てられたメモリの合計を示します。

しかし、従来のシステムでは、`mcache.local_cachealloc`というスレッドローカルなキャッシュが原因で、`heap_live`が実際の値よりも大幅に過小評価される問題がありました。`local_cachealloc`は、ヒープロックを取得する際に`heap_live`にフラッシュされることになっていましたが、特定の条件下（特に`mcentral`からのスパン割り当てがヒープロックを伴わない場合）では、このフラッシュが遅延し、`local_cachealloc`に大量の割り当てが蓄積される可能性がありました。

例えば、`BinaryTree17`のようなベンチマークでは、特定のサイズクラスのオブジェクトが頻繁に割り当てられ、解放されるサイクルが繰り返されます。この際、`mcentral`がスパンを使い切るまで`local_cachealloc`がフラッシュされず、結果として`heap_live`が実際のライブヒープサイズを大きく下回ることがありました。

`heap_live`の過小評価は、GCが遅れて起動したり、GCの動作強度が不適切になったりする原因となり、アプリケーションのパフォーマンスに悪影響を及ぼす可能性がありました。GCはメモリ使用量に基づいて動作を調整するため、不正確な`heap_live`はGCの効率を低下させ、最悪の場合、メモリ不足によるクラッシュを引き起こすことも考えられます。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの基本的な概念を理解しておく必要があります。

*   **`memstats.heap_live`**: Goランタイムが管理するヒープメモリのうち、現在「生きている」（GCによって到達可能と判断された）と見なされるバイト数を表す統計情報です。GCのトリガーや動作強度の調整に用いられる非常に重要な指標です。
*   **`mcache` (Memory Cache)**: 各P（プロセッサ、Goスケジューラにおける論理CPU）に紐付けられたスレッドローカルなメモリキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`は、`mcentral`からスパン（メモリのチャンク）を取得し、そこからオブジェクトを割り当てます。
*   **`mcache.local_cachealloc` (廃止前)**: `mcache`内で、ヒープロックを伴わずに割り当てられたバイト数を一時的に保持するカウンタでした。ヒープロックが取得される際に`memstats.heap_live`に加算される仕組みでした。
*   **`mcentral` (Memory Central)**: 特定のサイズクラス（オブジェクトのサイズ）に対応するスパンのリストを管理します。`mcache`がスパンを使い切ると、`mcentral`から新しいスパンを取得します。
*   **`mspan` (Memory Span)**: 連続したページ（OSから取得したメモリの最小単位）の集合体で、特定のサイズクラスのオブジェクトを格納するために使用されます。
*   **ガベージコレクタ (GC)**: Goの自動メモリ管理システムです。不要になったメモリを自動的に解放し、プログラマが手動でメモリを管理する手間を省きます。GCは、ヒープのライブサイズなどの統計情報に基づいて動作します。
*   **アトミック操作**: 複数のゴルーチンから同時にアクセスされる可能性のある共有変数に対して、不可分（atomic）な操作を行うことで、データ競合を防ぎ、正確性を保証する手法です。`sync/atomic`パッケージで提供される関数がこれに該当します。

## 技術的詳細

このコミットの主要な目的は、`memstats.heap_live`の過小評価を解消し、GCの精度と効率を向上させることです。そのために、以下の技術的な変更が導入されました。

1.  **`mcache.local_cachealloc`の廃止**:
    *   `mcache`構造体から`local_cachealloc`フィールドが削除されました。これにより、スレッドローカルな割り当てバイト数を一時的に保持するメカニズムがなくなります。
    *   `mallocgc`関数や`mheap`の`alloc_m`、`freeSpan`関数など、`local_cachealloc`を参照していた箇所からその更新・フラッシュ処理が削除されました。

2.  **`heap_live`の直接的かつアトミックな更新**:
    *   `heap_live`の更新は、`mcentral`からスパンを取得する際に直接行われるようになりました。これにより、割り当てが`local_cachealloc`に蓄積されることなく、よりリアルタイムに`heap_live`に反映されます。
    *   更新には`atomic.Xadd64`が使用されます。これは、複数のゴルーチンが同時に`heap_live`を更新しようとした場合でも、データ競合を起こさずに安全に加算処理を行うためのアトミック操作です。これにより、ロックの粒度を細かく保ちつつ、正確な更新が可能になります。

3.  **`heap_live`の保守的な見積もり**:
    *   スパンが割り当てられる際、そのスパン内の**全ての空きスロット**が将来的に使用されると仮定して、その分のバイト数が`heap_live`に加算されるようになりました。これは、実際にオブジェクトが割り当てられる**前**に行われます。
    *   この「保守的な」見積もりは、`heap_live`が実際のライブヒープサイズをわずかに過大評価する傾向があることを意味します。しかし、コミットメッセージで述べられているように、これは過小評価よりも望ましい結果です。
        *   **GCの早期トリガー**: `heap_live`がわずかに高めに評価されることで、GCが必要になるよりも少し早く起動する可能性があります。これは、GCが遅れて起動し、メモリ不足に陥るリスクを回避するために重要です。
        *   **保守的なGCレート**: GCの動作強度が過度に低くなることを防ぎ、より安定したGCパフォーマンスを維持します。

4.  **`mcentral.uncacheSpan`における`heap_live`の調整**:
    *   `mcentral`がスパンをキャッシュから外す際（`uncacheSpan`）、以前に保守的に加算された、まだ割り当てられていないスロット分の`heap_live`を減算する処理が追加されました。これにより、スパンが再利用される際に`heap_live`の過大評価が修正されます。

5.  **GCコントローラの改訂**:
    *   `heap_live`が変更された場合、`traceHeapAlloc()`（トレースが有効な場合）と`gcController.revise()`が呼び出されるようになりました。`gcController.revise()`は、GCの目標ヒープサイズや次のGCのタイミングを再計算するために使用され、`heap_live`の変更に迅速に対応します。

これらの変更により、`heap_live`はより正確かつ保守的に実際のライブヒープサイズを反映するようになり、GoのGCがより効率的かつ安定して動作することが期待されます。ベンチマーク結果では、一部のケースでわずかなパフォーマンス改善が見られますが、主な目的はGCの信頼性と予測可能性の向上です。

# [インデックス 22075] ファイルの概要

このコミットは、Goコマンドにおけるパッケージワイルドカード `std` の挙動を修正し、新たに `cmd` ワイルドカードを導入するものです。これにより、標準ライブラリパッケージとGoリポジトリ内のコマンドの区別が明確化され、ビルドシステムやテストスクリプトが更新されました。特に、`go install std` が標準ライブラリのみを指すようになり、コマンドを含める場合は `go install std cmd` と明示的に指定する必要が生じました。

## 変更の背景

Go言語の `go` コマンドには、特定のパッケージ群を指定するためのワイルドカードが存在します。その中でも `std` は、Goの標準ライブラリに含まれる全てのパッケージを指すものとしてドキュメントに定義されていました。しかし、歴史的にこの `std` ワイルドカードは、Goリポジトリ（`$GOROOT`）内のコマンド（例: `gofmt`, `go doc` など）も対象としていました。

Go言語の進化に伴い、Go自身で実装されるコアコマンドが増加するにつれて、この `std` の曖昧な挙動が問題となってきました。標準ライブラリとコマンドが同じワイルドカードで扱われることで、意図しないビルドやテストの実行、あるいは依存関係の混乱が生じる可能性がありました。

このコミットの主な目的は、`std` ワイルドカードの定義をそのドキュメント通りに「Go標準ライブラリのパッケージのみ」に厳密化することです。これにより、標準ライブラリとコマンドを明確に区別し、より予測可能で堅牢なビルド・テストプロセスを確立することが目指されました。

また、この変更の一環として、`race.bash` スクリプトにおける特定のコマンド（特にコンパイラ関連）のrace-enabledビルドが除外されています。これは、Goのレース検出器（Race Detector）が導入する顕著なパフォーマンスオーバーヘッド（実行時間の2倍〜20倍、メモリ使用量の5倍〜10倍）を考慮したものです。特にコンパイラのようなメモリを大量に消費するツールに対してレース検出器を有効にすると、そのオーバーヘッドがさらに大きくなり、ビルドやテストの効率が著しく低下する可能性があるため、これを回避するための措置が取られました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念とツールに関する知識が必要です。

### 1. Goのパッケージ管理とワイルドカード

Go言語では、コードはパッケージとして組織されます。`go` コマンド（`go build`, `go install`, `go test`, `go list` など）は、これらのパッケージを操作するための主要なツールです。

*   **パッケージパス**: Goのパッケージは、ファイルシステム上のパスやインポートパスによって識別されます（例: `fmt`, `net/http`, `github.com/user/repo/pkg`）。
*   **ワイルドカード**: `go` コマンドでは、複数のパッケージを一度に指定するためにワイルドカードが使用されます。
    *   **`all`**: `$GOPATH` および `$GOROOT` 内の全てのパッケージを指します。
    *   **`std`**: 歴史的にはGo標準ライブラリのパッケージとGoリポジトリ内のコマンドの両方を指していましたが、このコミットによって「Go標準ライブラリのパッケージのみ」を指すように厳密化されました。
    *   **`...` (ellipsis)**: パッケージパスの末尾に付加することで、そのディレクトリ以下の全てのサブパッケージを再帰的に含めることを意味します（例: `net/...` は `net` パッケージとその全てのサブパッケージを含みます）。
    *   **`cmd` (新規導入)**: このコミットで導入された新しいワイルドカードで、Goリポジトリ（`$GOROOT`）内のコマンド（`src/cmd` 以下にある実行可能ファイル）のみを指します。

### 2. `$GOROOT` 環境変数とGoのディレクトリ構造

`$GOROOT` は、GoのSDKがインストールされているルートディレクトリを指す環境変数です。Goのツールチェイン、コンパイラ、および標準ライブラリのソースコードがここに格納されています。

典型的な `$GOROOT` の構造は以下の通りです。
*   **`$GOROOT/bin`**: `go` コマンド自体や `gofmt` などのGoツールが格納されます。
*   **`$GOROOT/pkg`**: コンパイル済みの標準ライブラリパッケージやクロスコンパイル用のパッケージが格納されます。
*   **`$GOROOT/src`**: Go標準ライブラリのソースコードが格納されます。このディレクトリの直下には、`fmt`, `net`, `os` などの標準ライブラリパッケージのソースコードがあり、さらに `cmd` ディレクトリには `go` コマンドや `gofmt` などのGoツール自体のソースコードが含まれています。

### 3. Goのビルドシステム (`make.bash` など)

Goプロジェクトは、そのツールチェイン自体をソースコードからビルドするためのスクリプト群を持っています。`make.bash` (Unix系), `make.bat` (Windows), `make.rc` (Plan 9) などがこれにあたります。これらのスクリプトは、Goコンパイラ、リンカ、その他のツール、そして標準ライブラリをビルドし、インストールする役割を担っています。これらは通常、Goのリリースビルドや開発者がGoのソースコードを直接変更してビルドする際に使用されます。

### 4. Go Race Detector

Go Race Detectorは、Goプログラムにおけるデータ競合（data race）を検出するための強力なツールです。データ競合は、複数のゴルーチンが同期なしに同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みである場合に発生し、予測不能なプログラムの挙動を引き起こす可能性があります。

*   **動作原理**: `go build -race` のように `-race` フラグを付けてコンパイルすると、Goコンパイラは全てのメモリアクセスに計測コード（インストゥルメンテーション）を挿入します。これにより、実行時にThreadSanitizer (TSan) ランタイムライブラリがメモリアクセスのメタデータ（アクセス時刻、ゴルーチンID、メモリアドレスなど）を記録し、競合を検出します。
*   **パフォーマンスオーバーヘッド**: レース検出器は非常に有用ですが、その動作原理上、顕著なパフォーマンスオーバーヘッドを伴います。
    *   **実行時間**: 通常、2倍から20倍の実行時間の増加が見られます。
    *   **メモリ使用量**: 5倍から10倍、場合によっては20倍ものメモリ使用量の増加が見られます。これは、TSanがシャドウメモリを維持し、各メモリアドレスのメタデータを保存するためです。
*   **利用シーン**: この高いオーバーヘッドのため、レース検出器は通常、開発およびテスト段階で使用され、本番環境での利用は推奨されません。特に、コンパイラのように大量のメモリを消費するアプリケーションに対してレース検出器を有効にすると、その影響はさらに大きくなります。

## 技術的詳細

このコミットは、Goコマンドのパッケージワイルドカードのセマンティクスを明確化し、ビルドおよびテストプロセスを改善するために、複数のファイルにわたる変更を加えています。

### 1. `std` ワイルドカードの厳密化と `cmd` ワイルドカードの導入

*   **`std` の再定義**: `go` コマンドの内部ロジックにおいて、`std` ワイルドカードが `$GOROOT/src` 内の標準ライブラリパッケージのみを指すように変更されました。これまでは `src/cmd` 以下のコマンドも含まれることがありましたが、この変更により、`std` は `strings.Contains(name, ".")` や `name == "cmd"` のような条件でコマンドや外部モジュールを排除するようになりました。
*   **`cmd` の新規導入**: 新たに `cmd` ワイルドカードが導入されました。これは `$GOROOT/src/cmd` ディレクトリ以下にあるGoリポジトリのコマンド（例: `go`, `gofmt`, `vet` など）を指します。これにより、ユーザーは標準ライブラリとコマンドを個別に、または `std cmd` のように組み合わせて指定できるようになりました。

### 2. `go` コマンドの内部ロジックの変更 (`src/cmd/go/main.go`)

`src/cmd/go/main.go` は `go` コマンドの主要なロジックを実装しています。このファイルでは、`allPackages` および `matchPackages` 関数が変更され、`std` と `cmd` ワイルドカードの処理が分離されました。

*   以前は、`allPackages` 関数内で `src/cmd` ディレクトリを特別にウォークしてコマンドを収集していましたが、このロジックは削除されました。
*   代わりに、`filepath.Walk` を使用してパッケージを探索する際に、`pattern == "cmd"` の場合は探索ルートを `src/cmd` に限定し、`pattern == "std"` の場合は `cmd` ディレクトリをスキップするように変更されました。これにより、`std` と `cmd` の意味論がコードレベルで明確に分離されました。

### 3. ビルドスクリプトの更新 (`make.*`, `run.*`)

Goのビルドスクリプト (`make.bash`, `make.bat`, `make.rc`, `run.bash`, `run.bat`, `run.rc`) は、Goツールチェイン全体をビルド・インストールする際に `go install` コマンドを使用しています。

*   これらのスクリプトでは、`go install -v std` のように `std` ワイルドカードのみを指定していた箇所が、`go install -v std cmd` のように `std` と `cmd` の両方を明示的に指定するように変更されました。これにより、Goのビルドプロセスが標準ライブラリとGoリポジトリ内のコマンドの両方を確実にビルド・インストールするようになります。これは、`std` の定義が厳密化されたことによる影響を吸収するための変更です。

### 4. レース検出器関連スクリプトの変更 (`race.bash`, `race.bat`)

`race.bash` および `race.bat` は、レース検出器を有効にしてGoツールチェインをビルド・テストするためのスクリプトです。

*   これらのスクリプトから、`go install -race cmd/cgo` のような特定のコマンド（特に `cmd/cgo`）のrace-enabledビルドを明示的にインストールする行が削除されました。
*   これは、前述の通り、レース検出器がもたらす高いパフォーマンスオーバーヘッドを考慮したものです。特にコンパイラ (`cmd/cgo` はCgoのコンパイラ関連ツール) のようなメモリを大量に消費するツールに対してレース検出器を有効にすると、ビルド時間が大幅に増加し、開発効率が低下する可能性があるため、これを回避するための最適化です。

### 5. テストスクリプトの更新 (`src/cmd/go/test.bash`)

`src/cmd/go/test.bash` には、`go` コマンドの挙動を検証するためのテストが含まれています。

*   このコミットでは、`go list std` がコマンドを含まないこと、そして `go list cmd` がコマンドのみを含むことを検証する新しいテストが追加されました。これにより、`std` と `cmd` ワイルドカードの新しいセマンティクスが正しく機能していることが保証されます。

## コアとなるコードの解説

### `src/cmd/go/help.go` の変更

この変更は、`go help packages` コマンドの出力に、新しく導入された `cmd` ワイルドカードに関する説明を追加するものです。これにより、ユーザーは `cmd` がGoリポジトリ内のコマンドとその内部ライブラリに展開されることを公式ドキュメントを通じて理解できるようになります。これは、ユーザーエクスペリエンスの向上と、新しいワイルドカードの適切な利用を促進するための重要なドキュメント更新です。

### `src/cmd/go/main.go` の変更

このファイルは `go` コマンドの心臓部であり、パッケージの解決と処理を担当しています。

*   **`importPathsNoDotExpansion` 関数の変更**: この関数は、コマンドライン引数として与えられたパッケージパスを正規化し、ワイルドカードを展開する役割を担っています。変更前は `all` と `std` のみを特別扱いしていましたが、変更後は `cmd` も同様に特別扱いするようになりました。これにより、`go install cmd` のようなコマンドが正しく解釈され、`allPackages` 関数に渡されるようになります。
*   **`allPackages` および `matchPackages` 関数の変更**: これらの関数は、指定されたパターンに一致する全てのパッケージを `$GOPATH` や `$GOROOT` から見つけ出す役割を担っています。
    *   最も重要な変更は、以前 `src/cmd` ディレクトリを特別にウォークしてコマンドを収集していたロジックが削除されたことです。これは、`std` と `cmd` のセマンティクスが分離されたため、もはや必要なくなりました。
    *   代わりに、`filepath.Walk` を使用してファイルシステムを探索する際に、`pattern == "cmd"` の場合は探索の開始ルートを `src/cmd` に限定するようになりました。これにより、`cmd` ワイルドカードが `$GOROOT/src/cmd` 以下のコマンドのみを対象とすることが保証されます。
    *   また、`pattern == "std"` の場合は、パッケージ名にドットが含まれるもの（通常は外部モジュール）や、`cmd` ディレクトリ自体をスキップする条件が追加されました。これにより、`std` が純粋に標準ライブラリパッケージのみを指すように厳密化されます。この変更は、`std` の定義をドキュメントと一致させるための核心的なロジック変更です。

### ビルドスクリプト群 (`src/make.*`, `src/run.*`) の変更

これらのスクリプトは、Goのツールチェイン全体をビルド・インストールする際に使用されます。以前は `go install std` のように `std` ワイルドカードのみを指定していましたが、`std` の定義が厳密化されたため、Goリポジトリ内のコマンドがビルド対象から外れてしまう可能性がありました。

この変更により、`go install std cmd` のように `std` と `cmd` の両方を明示的に指定するようになりました。これにより、Goのビルドプロセスが標準ライブラリのパッケージとGoリポジトリ内のコマンドの両方を確実にビルド・インストールすることが保証されます。これは、`std` のセマンティクス変更に伴うビルドプロセスの整合性を保つための必須の調整です。

### レース検出器関連スクリプト (`src/race.bash`, `src/race.bat`) の変更

これらのスクリプトは、レース検出器を有効にしてGoツールチェインをビルド・テストするために使用されます。以前は `go install -race cmd/cgo` のように `cmd/cgo` を明示的にレース検出器有効でビルドしていました。

この変更では、この `go install -race cmd/cgo` の行が削除されました。これは、Goのレース検出器がもたらす高いパフォーマンスオーバーヘッドを考慮した最適化です。特に `cmd/cgo` のようなコンパイラ関連のツールは、その性質上、大量のメモリを消費し、複雑な処理を行うため、レース検出器を有効にするとビルド時間やメモリ使用量が著しく増加する可能性があります。この変更は、開発およびテストの効率を維持するために、特にパフォーマンスが重要なツールに対してレース検出器を無効にするという実用的な判断に基づいています。

### `src/cmd/go/test.bash` の変更

このテストスクリプトの変更は、`std` と `cmd` ワイルドカードの新しいセマンティクスが正しく機能していることを検証するためのものです。

*   新しく追加されたテストは、`go list std` の出力に `cmd/` で始まるパス（コマンド）が含まれていないことを確認します。
*   また、`go list cmd` の出力が `cmd/` で始まるパス（コマンド）のみを含み、それ以外のパスが含まれていないことを確認します。

これらのテストは、`go` コマンドのワイルドカード展開ロジックが意図通りに動作していることを自動的に検証し、将来の回帰を防ぐための重要な品質保証メカニズムです。

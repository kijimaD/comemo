# [インデックス 25880] ファイルの概要

このコミットは、Go言語の`archive/tar`パッケージにおける`readGNUSparseMap1x0`関数の問題を修正します。具体的には、32ビットマシンでの整数処理の不正確さ、ストリームの切り詰め検出の不備、ユーザー入力に対するメモリ割り当ての信頼性、および不正な入力によるパニックの可能性といった脆弱性に対処し、コードの堅牢性と安全性を向上させています。

## 変更の背景

このコミットは、`archive/tar`パッケージ内の`readGNUSparseMap1x0`関数が抱えていた複数の問題を解決するために行われました。これらの問題は、主に以下の4点に集約されます。

1.  **32ビット環境での64ビット整数処理の不備**: `strconv.ParseInt`の利用方法が不適切であり、特に32ビットシステム上で64ビット整数を正しく扱えない可能性がありました。これにより、大きなスパースファイル（まばらなファイル）のメタデータを正確に解析できない問題が発生していました。
2.  **ストリームの切り詰め検出の不備**: `io.ReadFull`を使用してデータを読み込む際、ファイルがブロック境界で突然終了した場合に、ストリームが切り詰められたことを適切に検出できないという問題がありました。これは、不完全なアーカイブファイルに対する堅牢性を低下させます。
3.  **`numEntries`に対する信頼性の問題**: 関数が`numEntries`（スパースエントリの数）というユーザー入力を盲目的に信頼し、それに基づいてメモリを割り当てていました。悪意のある入力が与えられた場合、過剰なメモリ割り当てを引き起こし、サービス拒否（DoS）攻撃につながる可能性がありました。
4.  **負の`numEntries`によるパニック**: `numEntries`が負の値である場合の検証が不足しており、悪意のあるスパースファイルが負の`numEntries`を指定した場合に、`make`関数（スライス作成）がパニックを引き起こす可能性がありました。

これらの問題は、関数の複雑さと境界エラーの推論の難しさから生じていました。既存の実装は理解しにくく、潜在的な脆弱性を抱えていたため、よりシンプルで堅牢なアプローチへの書き換えが必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **`archive/tar`パッケージ**: Go言語の標準ライブラリの一部で、TARアーカイブ（テープアーカイブ）ファイルの読み書きをサポートします。TARファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式です。
*   **GNU Sparse Format (PAX sparse format version 1.0)**: GNU tarが拡張したTARフォーマットの一種で、スパースファイル（ファイル内の大部分がゼロで構成されるファイル）を効率的に保存するためのメカニズムを提供します。スパースファイルは、ディスクスペースを節約するために、ゼロのブロックを実際にディスクに書き込まずに、その位置と長さをメタデータとして記録します。このフォーマットでは、スパースマップと呼ばれるメタデータがファイルデータ本体の前に格納され、オフセットとバイト数のペアでスパースエントリを記述します。
*   **`io.Reader`インターフェース**: Go言語における基本的な入力ストリームのインターフェースです。`Read`メソッドを持ち、データを読み込むための抽象化を提供します。
*   **`io.ReadFull`関数**: `io`パッケージのヘルパー関数で、指定されたバイト数だけ正確に読み込むことを保証します。指定されたバイト数に満たない場合、`io.ErrUnexpectedEOF`または他のエラーを返します。
*   **`strconv.ParseInt`関数**: 文字列を整数に変換するための関数です。基数（10進数、16進数など）とビットサイズを指定できます。ビットサイズは、結果の整数が収まる最小のビット数を指定し、オーバーフローチェックにも使用されます。
*   **`bytes.Buffer`**: 可変長のバイトシーケンスを扱うためのババッファです。`io.Reader`および`io.Writer`インターフェースを実装しており、効率的なバイト操作が可能です。特に、`ReadString`メソッドは指定されたデリミタ（区切り文字）まで読み込むのに便利です。
*   **`blockSize`**: TARアーカイブにおけるデータの最小単位で、通常は512バイトです。TARファイル内のデータは、このブロックサイズの倍数でアラインされます。
*   **スパースエントリ (sparseEntry)**: スパースファイル内で、実際にデータが存在する（またはゼロ以外のデータが存在する）領域のオフセットとバイト数を表す構造体です。

## 技術的詳細

以前の`readGNUSparseMap1x0`関数は、スパースマップの解析においていくつかの根本的な設計上の問題を抱えていました。

1.  **`strconv.ParseInt`のビットサイズ問題**: 以前の実装では`strconv.ParseInt(string(sparseHeader[:nl]), 10, 0)`のようにビットサイズに`0`を指定していました。これは、システムが提供する`int`のビットサイズ（32ビットシステムでは32ビット、64ビットシステムでは64ビット）を使用することを意味します。しかし、スパースマップのオフセットやバイト数は64ビット整数として扱われるべきであり、32ビットシステムではオーバーフローが発生し、誤った値が解析される可能性がありました。
2.  **`io.ReadFull`とブロック境界の問題**: `readDecimal`ヘルパー関数内で`io.ReadFull`を使用していました。この関数は、指定されたバイト数を読み込めなかった場合に`io.ErrUnexpectedEOF`を返しますが、TARアーカイブの特性上、スパースマップがブロック境界で正確に終了する場合、`io.ReadFull`はEOFを検出できず、不完全なデータを読み込んでしまう可能性がありました。また、`sparseHeader`バッファの管理が複雑で、ブロック単位での読み込みと改行文字の検索が入り組んでいました。
3.  **`numEntries`の信頼とメモリ割り当て**: スパースマップの最初の値である`numEntries`は、後続のスパースエントリの数を指定します。以前の実装では、この値をそのまま信頼して`make([]sparseEntry, 0, numEntries)`のようにスライスを初期化していました。もし攻撃者が非常に大きな`numEntries`を送信した場合、システムは大量のメモリを割り当てようとし、メモリ枯渇によるサービス停止を引き起こす可能性がありました。
4.  **負の`numEntries`の未検証**: `numEntries`が負の値である場合、`make`関数はパニックを引き起こします。以前の実装では、`numEntries`が負の値でないことを明示的に検証していませんでした。

新しい実装では、これらの問題を解決するために、よりシンプルで堅牢なアプローチを採用しています。

*   **`bytes.Buffer`の活用**: `bytes.Buffer`を導入し、`io.Reader`からブロック単位でデータを読み込み、バッファに蓄積します。これにより、`io.ReadFull`の直接的な使用を減らし、ストリームの管理を簡素化します。
*   **`feedTokens`ヘルパー関数**: この関数は、`bytes.Buffer`に十分な数の改行文字（トークン区切り）が含まれるまで、`io.Reader`から`blockSize`単位でデータを読み込みます。これにより、必要なデータがバッファに確実に存在することを保証し、ストリームの切り詰め検出を改善します。`io.ReadFull`が`io.EOF`を返した場合、`io.ErrUnexpectedEOF`に変換して、不完全なストリームを明確にエラーとして扱います。
*   **`nextToken`ヘルパー関数**: `bytes.Buffer.ReadString('\n')`を利用して、バッファから次の改行区切りのトークンを効率的に抽出します。これにより、以前の`readDecimal`関数で行っていた複雑なバッファ操作と改行検索が不要になります。
*   **`numEntries`の厳格な検証**: `numEntries`を解析した後、`numEntries < 0`のチェックと、`int(2*numEntries) < int(numEntries)`というオーバーフロー耐性のあるチェックを追加しています。これは、`2 * numEntries`が`int`型で表現できる最大値を超えないことを確認し、悪意のある大きな値によるメモリ割り当て攻撃を防ぎます。
*   **`strconv.ParseInt`のビットサイズ指定**: スパースエントリのオフセットとバイト数を解析する際に、`strconv.ParseInt(nextToken(), 10, 64)`のようにビットサイズを明示的に`64`に指定することで、32ビットシステムでも64ビット整数を正しく扱えるように修正されています。

これらの変更により、コードはより読みやすく、推論しやすくなり、潜在的なセキュリティ脆弱性やバグが大幅に削減されました。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の `readGNUSparseMap1x0` 関数

以前の`readGNUSparseMap1x0`関数は、`readDecimal`という内部ヘルパー関数を使って、ブロック単位でデータを読み込みながら改行文字を探し、数値を解析していました。このアプローチは、バッファ管理が複雑で、エラーハンドリングも不十分でした。

新しい実装では、以下の主要な変更が加えられています。

1.  **バッファとカウンタの導入**:
    ```go
    var cntNewline int64
    var buf bytes.Buffer
    var blk = make([]byte, blockSize)
    ```
    `cntNewline`はバッファ内の改行文字の数を追跡し、`buf`は読み込んだデータを一時的に保持する`bytes.Buffer`です。`blk`は`blockSize`単位でデータを読み込むための一時バッファです。

2.  **`feedTokens`ヘルパー関数**:
    ```go
    var feedTokens = func(cnt int64) error {
        for cntNewline < cnt {
            if _, err := io.ReadFull(r, blk); err != nil {
                if err == io.EOF {
                    err = io.ErrUnexpectedEOF
                }
                return err
            }
            buf.Write(blk)
            for _, c := range blk {
                if c == '\n' {
                    cntNewline++
                }
            }
        }
        return nil
    }
    ```
    この関数は、`buf`内に少なくとも`cnt`個の改行文字が存在するまで、`r`（入力`io.Reader`）から`blockSize`単位でデータを読み込みます。`io.ReadFull`が`io.EOF`を返した場合、`io.ErrUnexpectedEOF`に変換することで、不完全なストリームを明確にエラーとして扱います。これにより、ストリームの切り詰め検出が改善されます。

3.  **`nextToken`ヘルパー関数**:
    ```go
    var nextToken = func() string {
        cntNewline--
        tok, _ := buf.ReadString('\n')
        return tok[:len(tok)-1] // Cut off newline
    }
    ```
    この関数は、`buf`から次の改行区切りのトークンを抽出します。`bytes.Buffer.ReadString('\n')`を使用することで、改行文字までの文字列を効率的に取得できます。取得後、改行文字は削除されます。

4.  **`numEntries`の解析と検証**:
    ```go
    if err := feedTokens(1); err != nil {
        return nil, err
    }
    numEntries, err := strconv.ParseInt(nextToken(), 10, 0) // Intentionally parse as native int
    if err != nil || numEntries < 0 || int(2*numEntries) < int(numEntries) {
        return nil, ErrHeader
    }
    ```
    まず、`feedTokens(1)`を呼び出して、`numEntries`を読み込むのに十分なデータ（少なくとも1つの改行）がバッファにあることを確認します。次に、`nextToken()`で`numEntries`を解析します。ここで重要なのは、`numEntries < 0`のチェックと、`int(2*numEntries) < int(numEntries)`というオーバーフロー耐性のあるチェックが追加されたことです。これにより、悪意のある入力によるメモリ枯渇やパニックを防ぎます。`strconv.ParseInt`のビットサイズに`0`を指定しているのは、`numEntries`がスライスの長さに使われるため、Goのネイティブな`int`型に収まることを意図しているためです。

5.  **スパースエントリの解析**:
    ```go
    if err := feedTokens(2 * numEntries); err != nil {
        return nil, err
    }
    sp := make([]sparseEntry, 0, numEntries)
    for i := int64(0); i < numEntries; i++ {
        offset, err := strconv.ParseInt(nextToken(), 10, 64)
        if err != nil {
            return nil, ErrHeader
        }
        numBytes, err := strconv.ParseInt(nextToken(), 10, 64)
        if err != nil {
            return nil, ErrHeader
        }
        sp = append(sp, sparseEntry{offset: offset, numBytes: numBytes})
    }
    ```
    `numEntries`が検証された後、`2 * numEntries`個のトークン（オフセットとバイト数のペア）を読み込むのに十分なデータがあることを`feedTokens`で確認します。その後、ループ内で`nextToken()`と`strconv.ParseInt(..., 10, 64)`を使用して、各スパースエントリのオフセットとバイト数を64ビット整数として安全に解析します。

### `src/archive/tar/reader_test.go` の `TestReadGNUSparseMap1x0` 関数

テストファイルでは、`TestReadGNUSparseMap1x0`関数が完全に書き換えられ、新しい実装の堅牢性を検証するための広範なテストケースが追加されました。

以前のテストは、多数のスパースエントリを持つ単一の大きなスパースマップを生成し、その解析結果を検証するものでした。これは基本的な機能テストとしては有効でしたが、エッジケースやエラーシナリオを十分にカバーしていませんでした。

新しいテストでは、`vectors`という構造体のスライスを導入し、様々な入力データ（`input`）、期待されるスパースマップ（`sparseMap`）、読み込まれるバイト数（`cnt`）、および期待されるエラー（`err`）を定義しています。

*   空の入力、部分的な入力、ブロック境界でのEOFなど、`io.ErrUnexpectedEOF`が発生するケース。
*   不正なフォーマットの入力（改行がない、数値ではない文字が含まれるなど）で`ErrHeader`が発生するケース。
*   `numEntries`が負の値であるケース。
*   `numEntries`が非常に大きく、メモリ割り当ての検証が機能するケース。
*   複数のブロックにまたがるスパースマップの解析。

これらのテストケースにより、`readGNUSparseMap1x0`関数が様々な有効な入力と無効な入力に対して正しく動作し、期待されるエラーを返すことが保証されます。特に、`numBytes := len(v.input) - r.Len()`で実際に読み込まれたバイト数を検証している点は、ストリームの読み込みが正確に行われているかを確認する上で重要です。

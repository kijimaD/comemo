## 変更の背景

Go言語の型チェッカー (`go/types` パッケージ) は、コードのコンパイル時に型の一貫性を検証する重要な役割を担っています。しかし、以前のバージョンでは、無効な代入、特にインターフェース型への代入が失敗した場合のエラーメッセージが抽象的で、具体的な原因を特定しにくいという問題がありました。

例えば、ある具象型が特定のインターフェースを実装していないために代入が失敗した場合、単に「cannot assign X to Y」といったメッセージが表示されるだけでした。これでは、開発者はどのメソッドが不足しているのか、あるいはメソッドのシグネチャがインターフェースの定義と一致しないのかを、手動でコードを調べて確認する必要がありました。

この問題は、Go issue #10260 で報告され、より詳細なエラーメッセージが求められました。このコミットは、その要望に応える形で、インターフェースの代入失敗時に「missing method foo」や「wrong type for method bar」といった具体的な理由をエラーメッセージに含めるように `go/types` パッケージのロジックを修正しました。これにより、開発者のデバッグ体験が大幅に向上します。

## 前提知識の解説

### Goの型システムと`go/types`パッケージ

Goは静的型付け言語であり、コンパイル時に厳格な型チェックが行われます。`go/types`パッケージは、Goコンパイラの一部として、ソースコードの抽象構文木 (AST) を解析し、Go言語の型規則に従って型チェックを実行します。これには、変数の宣言、関数の呼び出し、代入、型変換などが含まれます。型チェックの目的は、プログラムが実行される前に型関連のエラーを捕捉し、プログラムの安全性と信頼性を確保することです。

### インターフェース (Interfaces)

Goのインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは「暗黙的」に実装されます。つまり、ある型がインターフェースで定義されたすべてのメソッドを実装していれば、その型はそのインターフェースを実装しているとみなされます。明示的な `implements` キーワードは不要です。

インターフェース型への代入は、Goのポリモーフィズムの根幹をなす機能です。具象型の値がインターフェース型の変数に代入されるとき、型チェッカーはその具象型がインターフェースのすべてのメソッドを正しく実装しているかを検証します。

### 代入可能性 (Assignability)

Go言語の仕様では、ある値 `x` が型 `V` を持ち、変数 `v` が型 `T` を持つ場合、`x` が `v` に代入可能であるための厳密なルールが定義されています。主なルールは以下の通りです。

1.  `V` と `T` の基底型が同一であり、かつ `V` または `T` の少なくとも一方が名前付き型でない場合。
2.  `V` と `T` が同一の型である場合。
3.  `T` がインターフェース型であり、`V` が `T` を実装している場合。
4.  `x` が事前宣言された識別子 `nil` であり、`T` がポインタ、関数、スライス、マップ、チャネル、またはインターフェース型である場合。
5.  `x` が型なしの定数であり、その値が `T` の型の値で表現可能である場合。

このコミットは、特に3番目のルール、すなわちインターフェースへの代入が失敗した場合の診断情報を改善することに焦点を当てています。

## 技術的詳細

このコミットの主要な技術的変更点は、型チェックロジック、特に代入可能性を判断する `assignableTo` 関数と、エラーを報告するメカニズムにあります。

1.  **`assignableTo` 関数のシグネチャ変更**:
    `operand` 型の `assignableTo` メソッドは、`func (x *operand) assignableTo(conf *Config, T Type) bool` から `func (x *operand) assignableTo(conf *Config, T Type, reason *string) bool` へと変更されました。
    新しい `reason *string` パラメータは、代入が失敗した場合に、その具体的な理由を文字列として格納するために使用されます。このポインタが `nil` でない場合、`assignableTo` 関数は失敗理由をこのポインタが指す文字列に書き込みます。

2.  **`assignment` 関数のシグネチャ変更と `xerrorf` の利用**:
    `Checker` 型の `assignment` メソッドも同様に、`func (check *Checker) assignment(x *operand, T Type) bool` から `func (check *Checker) assignment(x *operand, T Type, reason *string) bool` へと変更されました。
    この関数は `assignableTo` を呼び出し、その結果と `reason` を受け取ります。エラーが発生した場合、従来の `check.errorf` ではなく、新しく導入された `check.xerrorf` を使用してエラーを報告します。

3.  **新しいエラー報告関数 `xerrorf` の導入**:
    `src/go/types/errors.go` に `func (check *Checker) xerrorf(pos token.Pos, reason, format string, args ...interface{})` が追加されました。
    この関数は、`reason` 文字列が空でない場合に、元のエラーメッセージの末尾に `: %s` を追加し、`reason` をそのプレースホルダーに挿入します。これにより、エラーメッセージに詳細な理由が付加されます。

4.  **インターフェース実装チェックロジックの修正**:
    `src/go/types/operand.go` の `assignableTo` 関数内で、インターフェースへの代入チェックロジックが大幅に修正されました。
    以前は `Implements(x.typ, Ti)` を呼び出すだけでしたが、新しいロジックでは `MissingMethod(x.typ, Ti, true)` を使用します。
    `MissingMethod` 関数は、`x.typ` がインターフェース `Ti` を実装していない場合、不足しているメソッドまたは型が間違っているメソッドを返します。
    `assignableTo` は、`MissingMethod` の結果に基づいて、`reason` ポインタに「missing method M」または「wrong type for method M」といった詳細なエラー理由を設定します。

これらの変更により、型チェックの過程で代入失敗の具体的な原因が捕捉され、その情報がエラーメッセージに組み込まれるようになりました。

## コアとなるコードの解説

このコミットの核となるのは、`assignableTo` 関数と `assignment` 関数、そして新しいエラー報告メカニズム `xerrorf` の連携です。

1.  **`assignableTo` (src/go/types/operand.go)**:
    この関数は、あるオペランド `x` が特定の型 `T` に代入可能かどうかを判断します。変更前は `bool` 値のみを返していましたが、変更後は `reason *string` パラメータを受け取るようになりました。
    インターフェース型 `Ti` への代入をチェックする際、`MissingMethod(x.typ, Ti, true)` を呼び出します。この関数は、`x.typ` が `Ti` を実装していない場合、実装されていないメソッド (`m`) と、そのメソッドの型が間違っているかどうか (`wrongType`) を返します。
    もし `m` が `nil` でなければ（つまり、インターフェースが実装されていない場合）、`reason` ポインタが `nil` でないことを確認し、`wrongType` の値に応じて `*reason` に「wrong type for method M」または「missing method M」という詳細なエラー理由を設定します。そして `false` を返して代入が不可能であることを示します。

2.  **`assignment` (src/go/types/assignments.go)**:
    この関数は、具体的な代入操作を処理し、`assignableTo` を呼び出して代入可能性をチェックします。
    `reason := ""` でローカルな文字列変数を宣言し、そのアドレスを `&reason` として `assignableTo` に渡します。これにより、`assignableTo` が代入失敗の理由を `reason` 変数に書き込むことができます。
    `assignableTo` が `false` を返した場合、`x.mode != invalid` (既にエラーが報告されていない場合) を確認し、`check.errorf` の代わりに `check.xerrorf` を呼び出します。

3.  **`xerrorf` (src/go/types/errors.go)**:
    `xerrorf` は、`assignment` から渡された `reason` 文字列を受け取ります。
    もし `reason` が空でなければ、元のエラーメッセージのフォーマット文字列に `: %s` を追加し、`reason` を追加の引数として `check.err` に渡します。
    これにより、最終的なエラーメッセージは「cannot assign X to Y: missing method foo」や「cannot assign X to Y: wrong type for method bar」のようになり、開発者にとって非常に分かりやすくなります。

これらの変更は、Goの型チェッカーがより診断性の高いエラーメッセージを提供するための重要な改善であり、特にインターフェースの誤用に関するデバッグ作業を大幅に簡素化します。

## 変更の背景

Go言語の型チェッカー (`go/types` パッケージ) は、コードのコンパイル時に型の一貫性を検証する重要な役割を担っています。しかし、以前のバージョンでは、無効な代入、特にインターフェース型への代入が失敗した場合のエラーメッセージが抽象的で、具体的な原因を特定しにくいという問題がありました。

例えば、ある具象型が特定のインターフェースを実装していないために代入が失敗した場合、単に「cannot assign X to Y」といったメッセージが表示されるだけでした。これでは、開発者はどのメソッドが不足しているのか、あるいはメソッドのシグネチャがインターフェースの定義と一致しないのかを、手動でコードを調べて確認する必要がありました。

この問題は、Go issue #10260 で報告され、より詳細なエラーメッセージが求められました。このコミットは、その要望に応える形で、インターフェースの代入失敗時に「missing method foo」や「wrong type for method bar」といった具体的な理由をエラーメッセージに含めるように `go/types` パッケージのロジックを修正しました。これにより、開発者のデバッグ体験が大幅に向上します。

## 前提知識の解説

### Goの型システムと`go/types`パッケージ

Goは静的型付け言語であり、コンパイル時に厳格な型チェックが行われます。`go/types`パッケージは、Goコンパイラの一部として、ソースコードの抽象構文木 (AST) を解析し、Go言語の型規則に従って型チェックを実行します。これには、変数の宣言、関数の呼び出し、代入、型変換などが含まれます。型チェックの目的は、プログラムが実行される前に型関連のエラーを捕捉し、プログラムの安全性と信頼性を確保することです。

### インターフェース (Interfaces)

Goのインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは「暗黙的」に実装されます。つまり、ある型がインターフェースで定義されたすべてのメソッドを実装していれば、その型はそのインターフェースを実装しているとみなされます。明示的な `implements` キーワードは不要です。

インターフェース型への代入は、Goのポリモーフィズムの根幹をなす機能です。具象型の値がインターフェース型の変数に代入されるとき、型チェッカーはその具象型がインターフェースのすべてのメソッドを正しく実装しているかを検証します。

### 代入可能性 (Assignability)

Go言語の仕様では、ある値 `x` が型 `V` を持ち、変数 `v` が型 `T` を持つ場合、`x` が `v` に代入可能であるための厳密なルールが定義されています。主なルールは以下の通りです。

1.  `V` と `T` の基底型が同一であり、かつ `V` または `T` の少なくとも一方が名前付き型でない場合。
2.  `V` と `T` が同一の型である場合。
3.  `T` がインターフェース型であり、`V` が `T` を実装している場合。
4.  `x` が事前宣言された識別子 `nil` であり、`T` がポインタ、関数、スライス、マップ、チャネル、またはインターフェース型である場合。
5.  `x` が型なしの定数であり、その値が `T` の型の値で表現可能である場合。

このコミットは、特に3番目のルール、すなわちインターフェースへの代入が失敗した場合の診断情報を改善することに焦点を当てています。

## 技術的詳細

このコミットの主要な技術的変更点は、型チェックロジック、特に代入可能性を判断する `assignableTo` 関数と、エラーを報告するメカニズムにあります。

1.  **`assignableTo` 関数のシグネチャ変更**:
    `operand` 型の `assignableTo` メソッドは、`func (x *operand) assignableTo(conf *Config, T Type) bool` から `func (x *operand) assignableTo(conf *Config, T Type, reason *string) bool` へと変更されました。
    新しい `reason *string` パラメータは、代入が失敗した場合に、その具体的な理由を文字列として格納するために使用されます。このポインタが `nil` でない場合、`assignableTo` 関数は失敗理由をこのポインタが指す文字列に書き込みます。

2.  **`assignment` 関数のシグネチャ変更と `xerrorf` の利用**:
    `Checker` 型の `assignment` メソッドも同様に、`func (check *Checker) assignment(x *operand, T Type) bool` から `func (check *Checker) assignment(x *operand, T Type, reason *string) bool` へと変更されました。
    この関数は `assignableTo` を呼び出し、その結果と `reason` を受け取ります。エラーが発生した場合、従来の `check.errorf` ではなく、新しく導入された `check.xerrorf` を使用してエラーを報告します。

3.  **新しいエラー報告関数 `xerrorf` の導入**:
    `src/go/types/errors.go` に `func (check *Checker) xerrorf(pos token.Pos, reason, format string, args ...interface{})` が追加されました。
    この関数は、`reason` 文字列が空でない場合に、元のエラーメッセージの末尾に `: %s` を追加し、`reason` をそのプレースホルダーに挿入します。これにより、エラーメッセージに詳細な理由が付加されます。

4.  **インターフェース実装チェックロジックの修正**:
    `src/go/types/operand.go` の `assignableTo` 関数内で、インターフェースへの代入チェックロジックが大幅に修正されました。
    以前は `Implements(x.typ, Ti)` を呼び出すだけでしたが、新しいロジックでは `MissingMethod(x.typ, Ti, true)` を使用します。
    `MissingMethod` 関数は、`x.typ` がインターフェース `Ti` を実装していない場合、不足しているメソッドまたは型が間違っているメソッドを返します。
    `assignableTo` は、`MissingMethod` の結果に基づいて、`reason` ポインタに「missing method M」または「wrong type for method M」といった詳細なエラー理由を設定します。

これらの変更により、型チェックの過程で代入失敗の具体的な原因が捕捉され、その情報がエラーメッセージに組み込まれるようになりました。

## コアとなるコードの解説

このコミットの核となるのは、`assignableTo` 関数と `assignment` 関数、そして新しいエラー報告メカニズム `xerrorf` の連携です。

1.  **`assignableTo` (src/go/types/operand.go)**:
    この関数は、あるオペランド `x` が特定の型 `T` に代入可能かどうかを判断します。変更前は `bool` 値のみを返していましたが、変更後は `reason *string` パラメータを受け取るようになりました。
    インターフェース型 `Ti` への代入をチェックする際、`MissingMethod(x.typ, Ti, true)` を呼び出します。この関数は、`x.typ` が `Ti` を実装していない場合、実装されていないメソッド (`m`) と、そのメソッドの型が間違っているかどうか (`wrongType`) を返します。
    もし `m` が `nil` でなければ（つまり、インターフェースが実装されていない場合）、`reason` ポインタが `nil` でないことを確認し、`wrongType` の値に応じて `*reason` に「wrong type for method M」または「missing method M」という詳細なエラー理由を設定します。そして `false` を返して代入が不可能であることを示します。

2.  **`assignment` (src/go/types/assignments.go)**:
    この関数は、具体的な代入操作を処理し、`assignableTo` を呼び出して代入可能性をチェックします。
    `reason := ""` でローカルな文字列変数を宣言し、そのアドレスを `&reason` として `assignableTo` に渡します。これにより、`assignableTo` が代入失敗の理由を `reason` 変数に書き込むことができます。
    `assignableTo` が `false` を返した場合、`x.mode != invalid` (既にエラーが報告されていない場合) を確認し、`check.errorf` の代わりに `check.xerrorf` を呼び出します。

3.  **`xerrorf` (src/go/types/errors.go)**:
    `xerrorf` は、`assignment` から渡された `reason` 文字列を受け取ります。
    もし `reason` が空でなければ、元のエラーメッセージのフォーマット文字列に `: %s` を追加し、`reason` を追加の引数として `check.err` に渡します。
    これにより、最終的なエラーメッセージは「cannot assign X to Y: missing method foo」や「cannot assign X to Y: wrong type for method bar」のようになり、開発者にとって非常に分かりやすくなります。

これらの変更は、Goの型チェッカーがより診断性の高いエラーメッセージを提供するための重要な改善であり、特にインターフェースの誤用に関するデバッグ作業を大幅に簡素化します。

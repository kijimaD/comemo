## 変更の背景

このコミットは、Go言語の初期開発段階において、リンカ (`src/cmd/ld/go.c`) 内で発生していた「ダングリングポインタ」のバグを修正するために行われました。このバグは、メモリデバッグツールであるValgrindによって検出されました。

ダングリングポインタは、既に解放されたメモリ領域を指しているポインタのことで、これにアクセスすると未定義動作（プログラムのクラッシュ、データの破損、セキュリティ脆弱性など）を引き起こす可能性があります。C言語では、文字列は文字の配列として扱われ、そのメモリ管理はプログラマの責任となります。特に、関数内で一時的に作成された文字列や、スタック上に確保された文字列へのポインタを、その寿命が尽きた後も使用しようとすると、ダングリングポインタの問題が発生します。

このケースでは、`ilookup` 関数内で `name` という文字列ポインタが `x->name` に直接代入されていました。もし `name` が一時的なメモリ領域（例えば、関数の引数として渡されたスタック上の文字列や、別の関数から返された一時的なポインタ）を指していた場合、そのメモリが解放された後も `x->name` がその無効な領域を指し続けることになります。Valgrindはこのようなメモリの不正使用を検出し、開発者に問題の存在を知らせました。

## 前提知識の解説

### C言語における文字列とメモリ管理

C言語では、文字列はヌル終端された文字の配列 (`char[]` または `char*`) として扱われます。文字列を扱う際には、メモリの確保と解放をプログラマが明示的に行う必要があります。

*   **スタックとヒープ**:
    *   **スタック**: 関数呼び出しやローカル変数など、寿命が短いデータが格納される領域です。関数が終了すると、スタック上のローカル変数は自動的に解放されます。
    *   **ヒープ**: プログラムの実行中に動的にメモリを確保・解放するための領域です。`malloc` や `calloc` で確保し、`free` で解放する必要があります。ヒープに確保されたメモリは、明示的に解放されるまで有効です。
*   **文字列のコピー**: C言語では、文字列を別の変数に代入しても、文字列の内容がコピーされるわけではなく、ポインタ（メモリのアドレス）がコピーされるだけです。文字列の内容をコピーするには、`strcpy` や `strncpy`、あるいは `strdup` といった関数を使用する必要があります。

### ダングリングポインタ (Dangling Pointer)

ダングリングポインタとは、それが指していたメモリ領域が既に解放されているにもかかわらず、そのポインタ自体はまだ有効な値を保持している状態のポインタを指します。このポインタを介してメモリにアクセスしようとすると、以下のような問題が発生します。

*   **未定義動作**: プログラムのクラッシュ、予期せぬ動作、データの破損。
*   **セキュリティ脆弱性**: 攻撃者が解放されたメモリを再利用し、その領域に悪意のあるデータを書き込むことで、プログラムの制御を奪う可能性。

### `strdup` 関数

`strdup` (string duplicate) は、C標準ライブラリ（通常は `<string.h>` に含まれるが、POSIX標準でありC標準ではない）で提供される関数です。その名の通り、文字列を複製するために使用されます。

*   **機能**: 引数として与えられた文字列のコピーをヒープ上に新しく確保し、そのコピーへのポインタを返します。
*   **メモリ管理**: `strdup` は内部で `malloc` を呼び出してメモリを確保するため、`strdup` が返したポインタによって指されるメモリは、使用後に `free` 関数で明示的に解放する必要があります。
*   **利点**: 元の文字列の寿命に依存しない、独立した文字列コピーを作成できるため、ダングリングポインタの問題を防ぐのに役立ちます。

### Goリンカ (`cmd/ld`)

Go言語は、その初期段階では多くの部分がC言語で書かれていました。Goリンカ (`cmd/ld`) もその一つで、Goのソースコードをコンパイルして実行可能なバイナリを生成する過程で重要な役割を担います。リンカは、コンパイルされたオブジェクトファイルを結合し、外部ライブラリへの参照を解決し、最終的な実行ファイルを生成します。このコミットが行われた2009年当時、Go言語はまだ黎明期であり、そのツールチェインも活発に開発・改善されていました。

### Valgrind

Valgrindは、主にLinux上で動作するプロファイリングおよびメモリデバッグツールです。プログラムの実行中に発生する様々なメモリ関連のエラー（メモリリーク、無効なリード/ライト、初期化されていないメモリの使用、ダングリングポインタの使用など）を検出するのに非常に強力です。Valgrindは、プログラムのバイナリコードを動的に書き換え、メモリ操作を監視することでこれらのエラーを特定します。

## 技術的詳細

このコミットの技術的詳細は、C言語におけるメモリ管理の基本原則と、それを怠った場合に発生する問題に集約されます。

元のコード `x->name = name;` では、`ilookup` 関数内で `x` という構造体（おそらくハッシュテーブルのエントリか、シンボル情報を保持する構造体）のメンバー `name` に、引数として渡された `name` ポインタの値を直接代入していました。

ここで問題となるのは、`name` ポインタが指す文字列の「所有権」と「寿命」です。

1.  **所有権の欠如**: `x->name` は `name` が指す文字列のコピーを作成せず、単にそのアドレスを保持するだけでした。これは、`x->name` が `name` が指すメモリ領域の所有権を持たないことを意味します。
2.  **寿命の不一致**: `name` が指す文字列が、`ilookup` 関数の呼び出し元で確保された一時的なバッファや、スタック上のローカル変数であった場合、`ilookup` 関数が終了するか、呼び出し元の関数が終了すると、そのメモリ領域は解放されてしまいます。

この結果、`x->name` は解放済みのメモリ領域を指す「ダングリングポインタ」となり、後続のコードが `x->name` を介して文字列にアクセスしようとすると、未定義動作が発生します。例えば、そのメモリ領域が別のデータで上書きされていれば、`x->name` は意図しないゴミデータを読み込むことになり、プログラムのロジックが破綻する可能性があります。

この問題を解決するために、`x->name = strdup(name);` という変更が導入されました。

*   `strdup(name)` は、`name` が指す文字列の内容をヒープ上に新しくメモリを確保し、そこにコピーします。
*   そして、新しく確保されたメモリ領域へのポインタを返します。
*   この返されたポインタが `x->name` に代入されることで、`x->name` は `name` とは独立した、自身のメモリ領域を持つ文字列を指すようになります。

これにより、`name` が指す元の文字列の寿命が尽きても、`x->name` が指す文字列はヒープ上に存在し続けるため、ダングリングポインタの問題が解消されます。この修正は、リンカの安定性と信頼性を確保するために不可欠でした。

## コアとなるコードの解説

`ilookup` 関数は、おそらくGoリンカがシンボルやインポートパスなどを管理するためのハッシュテーブルのようなデータ構造 (`ihash`) に新しいエントリを追加する際に使用される関数です。`x` は新しいエントリを表す構造体であり、`name` はそのエントリに関連付けられる文字列（例えば、シンボル名やファイルパス）です。

元のコード `x->name = name;` では、`name` ポインタが指すアドレスをそのまま `x->name` にコピーしていました。これは、`name` が指す文字列の内容をコピーするのではなく、単にその場所を指すようにする操作です。

この直接代入が問題となるのは、`name` が指すメモリ領域が、`x` が使用される期間よりも短い寿命を持つ場合です。例えば、`name` が `ilookup` 関数に渡された一時的な文字列リテラルや、スタック上に確保されたバッファへのポインタであった場合、`ilookup` 関数が終了するとそのメモリは解放されます。しかし、`x` はハッシュテーブルに格納され、その後も参照され続ける可能性があります。このとき、`x->name` は既に解放されたメモリを指すダングリングポインタとなり、その後のアクセスは未定義動作を引き起こします。

修正後のコード `x->name = strdup(name);` では、`strdup` 関数が使用されています。
1.  `strdup(name)` は、`name` が指す文字列の内容を読み取ります。
2.  その内容を格納するために、ヒープ上に新しいメモリ領域を `malloc` を使って動的に確保します。
3.  元の文字列の内容を新しく確保したメモリ領域にコピーします。
4.  新しく確保されたメモリ領域の先頭アドレスを返します。

この返されたアドレスが `x->name` に代入されることで、`x->name` は `name` とは独立した、ヒープ上に存在する文字列のコピーを指すようになります。これにより、`name` の寿命が尽きても `x->name` が指す文字列は有効なままであり、ダングリングポインタの問題が完全に解消されます。この変更は、Goリンカの堅牢性を高める上で非常に重要な修正でした。

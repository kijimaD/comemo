# [インデックス 27952] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおける「浮動ゴミ推定（floating garbage estimate）」を廃止し、到達可能なヒープサイズをマーク済みヒープサイズと単純に等しいと見なすように変更します。これにより、GCトリガーの計算が簡素化され、特に高速なアロケーションを行うアプリケーションにおけるGCの挙動が改善され、ミューテーター（ユーザープログラム）の可用性が向上します。

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）における「浮動ゴミ推定」の廃止を目的としています。以前のGCトリガーの計算では、次のGCサイクル開始時の到達可能なヒープサイズを推定するために、浮動ゴミの推定値が使用されていました。この推定は、コミット `4655aad` で導入され、ヒープが実際の到達可能サイズの何倍にも膨れ上がるという悪質なフィードバックループを修正するためのものでした。

しかし、この浮動ゴミ推定にはいくつかの問題がありました。

1.  **高速なアロケーションを行うアプリケーションでの混乱**: 急速にメモリを割り当てるアプリケーションでは、この推定が容易に混乱し、正確なGCトリガーの計算を妨げていました。
2.  **トリガーコントローラーとの不整合**: 浮動ゴミ推定に基づくヒープサイズが、トリガーコントローラーがトリガー自体を計算するために使用するヒープサイズと異なっていました。この不整合により、トリガーコントローラーはGCが開始する前に終了したと誤認することが頻繁にありました。その結果、トリガーコントローラーは次のGC目標に可能な限り近い（目標の95%に制限される）トリガーを設定してしまい、GCの頻度や効率に悪影響を与えていました。
3.  **問題の解決**: 浮動ゴミ推定が元々修正しようとしていた悪質なフィードバックループは、その後の他の変更によってより適切に修正されたようで、もはや発生しないことが示唆されていました。
4.  **「allocate black」の導入**: 新しいオブジェクトをGCのマーキングフェーズ中に「黒（black）」として割り当てる「allocate black」戦略の導入により、この悪質なフィードバックループが理論上発生する可能性すらなくなりました。

これらの理由から、浮動ゴミ推定を維持するメリットがなくなり、むしろGCの挙動を複雑にし、非効率にする原因となっていました。この変更は、GCのロジックを簡素化し、より予測可能で効率的な動作を目指しています。特に、ミューテーターの可用性（ユーザープログラムが実行できる時間）を大幅に改善することが期待されています。

ベンチマーク結果によると、この変更はアロケーションが重いベンチマークで全体的なスループットをわずかに低下させるものの、ミューテーターの可用性を大幅に向上させます。具体的には、`XBenchGarbage` ベンチマークでは平均トリガーが0.95から0.7に、アクティブなGC利用率が約90%から約45%に改善されています。

このコミットは、Issue #12204 を修正し、Issue #14951 を更新します。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）に関するいくつかの重要な概念を理解しておく必要があります。

1.  **ガベージコレクション (GC)**:
    GoのGCは、プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは、並行（concurrent）、非世代別（non-generational）、非圧縮（non-compacting）のマーク＆スイープ（mark-and-sweep）アルゴリズムを採用しています。これは、アプリケーションの実行と並行して動作し、プログラムの一時停止（Stop-The-World: STW）時間を最小限に抑えるように設計されています。

2.  **マーク＆スイープ (Mark-and-Sweep)**:
    *   **マークフェーズ (Mark Phase)**: GCは、ルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを「生きている（live）」とマークします。GoのGCでは、このプロセスを「三色マーキング（Tri-color marking）」という抽象化と「ライトバリア（write barrier）」を用いて並行して行います。
        *   **白 (White)**: まだGCによって訪問されていないオブジェクト。潜在的なゴミ。
        *   **灰 (Gray)**: GCによって訪問されたが、その子（参照しているオブジェクト）がまだスキャンされていないオブジェクト。
        *   **黒 (Black)**: GCによって訪問され、そのすべての子もスキャンされマークされたオブジェクト。生きていると確定。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかった（白のままの）オブジェクトは「ゴミ（garbage）」と見なされ、メモリが解放されます。

3.  **浮動ゴミ (Floating Garbage)**:
    GoのGCはアプリケーションと並行して動作するため、GCのマークフェーズが開始された後、完了するまでの間に、アプリケーションがオブジェクトへの参照を変更し、一部のオブジェクトが到達不可能になることがあります。これらのオブジェクトは、現在のGCサイクルでは回収されず、次のサイクルで回収されることになります。これが「浮動ゴミ」です。浮動ゴミ自体はGCの並行性によって避けられない側面ですが、その量を適切に管理することが重要です。

4.  **GCトリガー (GC Trigger)**:
    GoのGCは、ヒープサイズが特定の閾値を超えたときにトリガーされます。この閾値は動的に調整され、前回のGCでマークされたヒープサイズ（到達可能なヒープサイズ）に基づいて、次のGCを開始するタイミングが決定されます。この閾値の計算には、以前は「浮動ゴミ推定」が考慮されていました。

5.  **`memstats.heap_live` と `work.bytesMarked`**:
    *   `memstats.heap_live`: 現在のライブヒープ（アプリケーションが使用していると認識しているメモリ）の推定値。
    *   `work.bytesMarked`: GCのマークフェーズで到達可能とマークされたバイト数。これは、GCサイクル終了時点での実際の到達可能ヒープサイズに非常に近い値です。

6.  **Allocate Black**:
    GoのGCにおける最適化の一つで、GCのマークフェーズ中に新しく割り当てられたオブジェクトを即座に「黒」とマークする戦略です。新しく割り当てられたオブジェクトは、それを割り当てたアプリケーションによって到達可能であるため、GCが後でその到達可能性を追跡する必要がありません。これにより、GCの作業量が減り、STWポーズが最小限に抑えられます。この戦略は、浮動ゴミの問題を軽減する効果もあります。

7.  **ミューテーターの可用性 (Mutator Availability)**:
    「ミューテーター」とは、メモリを割り当てたり、オブジェクト参照を変更したりするユーザープログラム（Goルーチン）のことです。ミューテーターの可用性とは、GCによる中断なしにユーザープログラムが実行できる時間の割合を指します。GoのGCは、このミューテーターの可用性を最大化することを目指しています。GCがCPUを多く消費したり、STWポーズが長くなったりすると、ミューテーターの可用性は低下します。

## 技術的詳細

このコミットの核心は、GoのGCが次のGCサイクルをトリガーするタイミングを決定する際に使用していた「浮動ゴミ推定」を廃止することです。

以前のGCトリガー計算では、GCサイクル開始時の到達可能なヒープサイズを推定するために、以下の複雑なロジックが使用されていました。

```go
// Compute the reachable heap size at the beginning of the
// cycle. This is approximately the marked heap size at the
// end (which we know) minus the amount of marked heap that
// was allocated after marking began (which we don't know, but
// is approximately the amount of heap that was allocated
// since marking began).
allocatedDuringCycle := memstats.heap_live - work.initialHeapLive
if memstats.heap_live < work.initialHeapLive {
    // This can happen if mCentral_UncacheSpan tightens
    // the heap_live approximation.
    allocatedDuringCycle = 0
}
if work.bytesMarked >= allocatedDuringCycle {
    memstats.heap_reachable = work.bytesMarked - allocatedDuringCycle
} else {
    // This can happen if most of the allocation during
    // the cycle never became reachable from the heap.
    // Just set the reachable heap approximation to 0 and
    // let the heapminimum kick in below.
    memstats.heap_reachable = 0
}
```

このコードは、GCサイクル中に割り当てられたメモリ量 (`allocatedDuringCycle`) を推定し、それをマークされたヒープサイズ (`work.bytesMarked`) から差し引くことで、サイクル開始時の到達可能なヒープサイズ (`memstats.heap_reachable`) を計算しようとしていました。この `allocatedDuringCycle` は、浮動ゴミの量を間接的に推定する試みでした。

しかし、コミットメッセージが指摘するように、この推定は以下の問題を引き起こしていました。

1.  **不正確さ**: 特に高速なアロケーションを行うアプリケーションでは、`memstats.heap_live` と `work.initialHeapLive` の差から `allocatedDuringCycle` を推定する方法が不正確でした。これにより、`memstats.heap_reachable` の値が実際の到達可能ヒープサイズと大きく乖離することがありました。
2.  **トリガーコントローラーの誤動作**: GCトリガーコントローラーは、この不正確な `memstats.heap_reachable` の値に基づいて次のGCトリガーを計算していました。トリガーコントローラーは、GCが非常に効率的に（あるいは開始する前に）完了したと誤認し、次のGCトリガーを可能な限り高く（目標の95%まで）設定してしまうことがありました。これは、GCが遅延し、ヒープが不必要に大きくなる原因となっていました。
3.  **「allocate black」による陳腐化**: 新しいオブジェクトを「黒」として割り当てる「allocate black」戦略が導入されたことで、GCサイクル中に割り当てられたオブジェクトは即座に到達可能とマークされるようになりました。これにより、以前の「ヒープが実際の到達可能サイズの何倍にも膨れ上がる」という悪質なフィードバックループが理論上発生しなくなりました。浮動ゴミ推定が元々解決しようとしていた問題が、より根本的な方法で解決されたため、この推定は不要になりました。

このコミットでは、上記の複雑なロジックをすべて削除し、代わりに `memstats.heap_reachable` を `work.bytesMarked` と単純に等しいと見なすように変更します。

```go
// Update the reachable heap stat.
memstats.heap_reachable = work.bytesMarked
```

この変更の技術的な影響は以下の通りです。

*   **GCトリガー計算の簡素化**: 次のGCトリガーは、GCサイクル終了時に実際にマークされたヒープサイズに基づいて、より直接的かつ正確に計算されるようになります。これにより、トリガーコントローラーの誤動作が解消されます。
*   **ミューテーターの可用性の向上**: トリガーコントローラーがより適切に動作し、GCがCPUを多く消費している場合にトリガーを低く設定するようになるため、GCの頻度が最適化され、ユーザープログラム（ミューテーター）が中断される時間が減少します。これは、アプリケーションの応答性向上に直結します。
*   **スループットへの影響**: コミットメッセージにあるベンチマーク結果が示すように、アロケーションが重いワークロードでは全体的なスループットがわずかに低下する可能性があります。これは、浮動ゴミ推定が削除されたことで、GCが以前よりもわずかに保守的に動作し、より頻繁に、あるいはより多くのメモリを回収しようとするためと考えられます。しかし、このスループットのわずかな低下は、ミューテーターの可用性の大幅な向上というメリットによって相殺されると判断されています。

この変更は、GoのGCが進化し、より堅牢で効率的なメモリ管理を実現するための重要なステップです。

## コアとなるコードの解説

変更されたコードは、`src/runtime/mgc.go` 内の `gcMark` 関数の一部です。この関数は、GCのマークフェーズが完了した後に呼び出され、次のGCサイクルに向けた統計情報を更新する役割を担っています。

変更前は、`memstats.heap_reachable` (到達可能なヒープサイズ) を計算するために、以下の複雑なロジックが使用されていました。

```go
// Compute the reachable heap size at the beginning of the
// cycle. This is approximately the marked heap size at the
// end (which we know) minus the amount of marked heap that
// was allocated after marking began (which we don't know, but
// is approximately the amount of heap that was allocated
// since marking began).
allocatedDuringCycle := memstats.heap_live - work.initialHeapLive
if memstats.heap_live < work.initialHeapLive {
    // This can happen if mCentral_UncacheSpan tightens
    // the heap_live approximation.
    allocatedDuringCycle = 0
}
if work.bytesMarked >= allocatedDuringCycle {
    memstats.heap_reachable = work.bytesMarked - allocatedDuringCycle
} else {
    // This can happen if most of the allocation during
    // the cycle never became reachable from the heap.
    // Just set the reachable heap approximation to 0 and
    // let the heapminimum kick in below.
    memstats.heap_reachable = 0
}
```

このコードブロックは、GCサイクル中に新しく割り当てられたメモリ量 (`allocatedDuringCycle`) を推定し、それを `work.bytesMarked` (マークされたヒープサイズ) から差し引くことで、GCサイクル開始時点での「真の」到達可能ヒープサイズを推定しようとしていました。これは、GCが並行して動作する間に発生する「浮動ゴミ」を考慮に入れ、次のGCトリガーをより正確に設定するための試みでした。

しかし、この推定は、特に高速なアロケーションが行われる場合に不正確になりがちでした。`memstats.heap_live` と `work.initialHeapLive` の差は、GCサイクル中に割り当てられたメモリの正確な指標ではなく、ヒープのライブ状態の近似値に過ぎませんでした。この不正確さが、GCトリガーコントローラーの誤動作を引き起こし、GCの効率を低下させていました。

このコミットでは、上記の20行近くのコードが削除され、以下の1行に置き換えられています。

```go
// Update the reachable heap stat.
memstats.heap_reachable = work.bytesMarked
```

この変更は、`memstats.heap_reachable` の値を、GCサイクル終了時に実際にマークされたバイト数である `work.bytesMarked` と単純に等しいと見なすことを意味します。

この簡素化は、以下の理由により可能かつ望ましいと判断されました。

1.  **「allocate black」の導入**: 新しいオブジェクトがGCのマークフェーズ中に「黒」として割り当てられる「allocate black」戦略が導入されたことで、GCサイクル中に割り当てられたオブジェクトは即座に到達可能とマークされるようになりました。これにより、以前の浮動ゴミ推定が対処しようとしていた「ヒープが不必要に膨れ上がる」という問題が、より根本的に解決されました。
2.  **推定の不要性**: 浮動ゴミ推定が元々修正しようとしていた問題が他の変更によって解決されたため、この複雑で不正確な推定はもはや不要になりました。
3.  **GCトリガーの改善**: `memstats.heap_reachable` を `work.bytesMarked` と直接結びつけることで、GCトリガーの計算がより直接的かつ堅牢になります。これにより、トリガーコントローラーがより適切に動作し、GCの頻度とCPU利用率が最適化され、結果としてミューテーターの可用性が向上します。

要するに、この変更はGoのGCロジックを簡素化し、より現代的なGC戦略（allocate blackなど）と整合させることで、全体的なGCのパフォーマンスとアプリケーションの応答性を向上させるものです。

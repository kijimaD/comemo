# [インデックス 26669] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における最適化に関するものです。具体的には、要素数が0または1の配列型（`[0]T`および`[1]T`）に対する比較アルゴリズムの生成を停止することで、コンパイラが生成するコードのサイズを削減し、パフォーマンスを向上させます。これらの特殊な配列型は、特に可変長引数（variadic functions）の呼び出し時に中間的に生成されることが多く、その比較処理を最適化することで、全体的なバイナリサイズと実行効率に寄与します。

## 元コミット内容

`cmd/compile: don't generate algs for [0]T and [1]T`

このコミットは、Goコンパイラが`[0]T`（要素数0の配列）と`[1]T`（要素数1の配列）の型に対して、比較アルゴリズム（`algs`）を生成しないように変更します。

*   `[0]T`型のすべての値は常に等しいです。
*   `[1]T`型の値は、その唯一の要素が等しい場合にのみ等しいです。

これらの型は、`fmt.Printf("abc")`や`fmt.Printf("%v", x)`のような可変長引数関数呼び出しの副産物として最も頻繁に現れます。

この変更により、`cmd/go`のサイズが約12KB、`golang.org/x/tools/cmd/godoc`のサイズが約22KB削減され、それぞれ約0.1%の削減となります。

この変更は、Issue #6853 と #9930 に関連しています。

## 変更の背景

Go言語では、配列は値型であり、そのサイズは型の一部です。`[0]T`や`[1]T`のような特殊な配列型は、特に可変長引数（variadic functions）のメカニズムと深く関連しています。

Goの可変長引数関数は、`func foo(args ...interface{})`のように定義されます。この`args`は実際にはスライス`[]interface{}`として関数内で扱われます。しかし、コンパイラが可変長引数呼び出しを処理する際、引数の数が0または1の場合に、最適化の一環として`[0]T`や`[1]T`のような固定サイズの配列を一時的に生成することがあります。例えば、`fmt.Printf("hello")`のように引数がない場合、`[0]interface{}`のような配列が生成され、それがスライスに変換されて関数に渡されます。同様に、`fmt.Printf("%d", 10)`のように引数が1つの場合、`[1]interface{}`のような配列が生成されます。

これらの配列型は、通常の配列と同様に比較可能ですが、その比較ロジックは非常に単純です。
*   `[0]T`型の配列は要素を持たないため、どのような`[0]T`型の値も常に等しいと見なせます。
*   `[1]T`型の配列は1つの要素しか持たないため、その配列の等価性は、含まれる唯一の要素の等価性に完全に依存します。

従来のコンパイラは、これらの自明な比較ロジックに対しても、汎用的な比較アルゴリズムを生成していました。これは不要なコードの肥大化を招き、特に多くの可変長引数関数が使用されるプログラムにおいて、バイナリサイズをわずかながら増加させていました。このコミットの目的は、これらの自明なケースをコンパイラが特別扱いし、不要な比較アルゴリズムの生成を抑制することで、生成されるバイナリのサイズを削減し、コンパイル時間や実行時の効率を向上させることにあります。

関連するIssue #6853と#9930は、コンパイラが生成するコードのサイズ削減や、特定の型に対する比較処理の最適化に関する議論を反映していると考えられます。

## 前提知識の解説

### Go言語の型システムと配列

Go言語において、配列は固定長の値型です。`[N]T`という形式で宣言され、`N`は配列の要素数、`T`は要素の型を表します。配列のサイズは型の一部であるため、`[3]int`と`[4]int`は異なる型と見なされます。

### 比較可能性 (Comparability)

Goの型には「比較可能 (comparable)」なものとそうでないものがあります。
*   数値型、文字列型、ブール型、ポインタ型、チャネル型、インターフェース型、構造体型（すべてのフィールドが比較可能な場合）、配列型（要素型が比較可能で、配列のサイズが同じ場合）は比較可能です。
*   スライス型、マップ型、関数型は比較不可能です。

比較可能な型は、`==`や`!=`演算子を使って等価性をチェックできます。

### 可変長引数 (Variadic Functions)

Goの関数は、最後の引数に`...`を付けることで可変長引数を受け取ることができます。
例: `func sum(nums ...int) int`
関数内部では、`nums`は`[]int`型のスライスとして扱われます。
`fmt.Printf`のような関数は、`...interface{}`を受け取るため、任意の型の引数を渡すことができます。

### Goコンパイラの内部構造

Goコンパイラ（`cmd/compile`）は、Goのソースコードを機械語に変換する役割を担います。このプロセスには、構文解析、型チェック、中間表現（IR）の生成、最適化、コード生成などが含まれます。
*   **`src/cmd/compile/internal/gc/subr.go`**: このファイルは、コンパイラのバックエンドにおけるサブルーチンやユーティリティ関数を定義しています。特に、型のプロパティ（比較可能性、ハッシュ可能性など）を決定するロジックが含まれることがあります。`algtype1`関数は、特定の型に対する比較アルゴリズムのタイプを決定する役割を担っています。
*   **`src/cmd/compile/internal/gc/walk.go`**: このファイルは、コンパイラの「ウォーク」フェーズに関連するコードを含んでいます。ウォークフェーズでは、抽象構文木（AST）を走査し、型チェック後の意味解析や最適化、コード生成のための準備を行います。`walkcompare`関数は、比較演算子（`==`, `!=`など）のASTノードを処理し、適切な比較コードを生成する役割を担っています。

### `algs` (Algorithms)

Goコンパイラが「algs」と呼ぶのは、特定の型に対する操作（比較、ハッシュ、ゼロ初期化、コピーなど）を実行するための内部的なアルゴリズムやコード生成ロジックを指します。これらのアルゴリズムは、コンパイラによって自動的に生成され、ランタイムで利用されます。不要な`algs`の生成を避けることは、バイナリサイズの削減に直結します。

## 技術的詳細

このコミットは、Goコンパイラの`src/cmd/compile/internal/gc/subr.go`と`src/cmd/compile/internal/gc/walk.go`の2つのファイルを変更しています。

### `src/cmd/compile/internal/gc/subr.go`の変更

`algtype1`関数は、与えられた型`t`に対して、その比較アルゴリズムのタイプを決定します。この関数は、型が比較可能であるかどうか、そしてどのように比較されるべきかを判断します。

変更前は、配列型の場合、要素型が比較可能であれば、汎用的な配列比較アルゴリズムが選択されていました。
変更後、`algtype1`関数内の配列型（`TARRAY`）を処理する`switch`文に、以下の新しいケースが追加されました。

```go
		switch t.Bound {
		case 0:
			// We checked above that the element type is comparable.
			return AMEM
		case 1:
			// Single-element array is same as its lone element.
			return a
		}
```

*   `t.Bound`は配列の要素数を表します。
*   `case 0:`: 配列の要素数が0の場合（`[0]T`）。この場合、すべての`[0]T`型の値は常に等しいため、特別な比較ロジックは不要です。`AMEM`（"always equal memory"のような意味合い）を返します。これは、メモリの内容が常に等しいと見なせることを示唆し、コンパイラがこの型の比較に対して特別なコードを生成する必要がないことを伝えます。
*   `case 1:`: 配列の要素数が1の場合（`[1]T`）。この場合、配列の等価性は、その唯一の要素の等価性に依存します。したがって、配列自体の比較アルゴリズムではなく、要素型の比較アルゴリズム（`a`で表される）を再利用するように指示します。

この変更により、`[0]T`と`[1]T`に対しては、汎用的な配列比較アルゴリズムの生成が抑制され、より効率的な（あるいは全く不要な）比較処理が選択されるようになります。

### `src/cmd/compile/internal/gc/walk.go`の変更

`walkcompare`関数は、比較演算子（`==`, `!=`など）を含むASTノードを処理し、それらをより低レベルの操作に変換します。

変更前は、配列の比較は汎用的なロジックで処理されていました。
変更後、`walkcompare`関数内の比較対象の型が配列型（`TARRAY`）である場合に、以下の新しいロジックが追加されました。

```go
	if t.Etype == TARRAY {
		// Zero- or single-element array, of any type.
		switch t.Bound {
		case 0:
			finishcompare(np, n, Nodbool(n.Op == OEQ), init)
			return
		case 1:
			l0 := Nod(OINDEX, l, Nodintconst(0))
			r0 := Nod(OINDEX, r, Nodintconst(0))
			a := Nod(n.Op, l0, r0)
			finishcompare(np, n, a, init)
			return
		}
	}
```

*   `t.Etype == TARRAY`で、比較対象が配列型であることを確認します。
*   `switch t.Bound`: 配列の要素数に応じて処理を分岐します。
*   `case 0:`: 要素数0の配列（`[0]T`）の場合。
    *   `finishcompare(np, n, Nodbool(n.Op == OEQ), init)`: `Nodbool(n.Op == OEQ)`は、比較演算子が`==`であれば`true`、`!=`であれば`false`を意味するブール定数ノードを生成します。つまり、`[0]T`型の比較は常に`true`（`==`の場合）または`false`（`!=`の場合）という定数に置き換えられます。これは、すべての`[0]T`値が等しいという事実に基づいています。
*   `case 1:`: 要素数1の配列（`[1]T`）の場合。
    *   `l0 := Nod(OINDEX, l, Nodintconst(0))`と`r0 := Nod(OINDEX, r, Nodintconst(0))`は、それぞれ左辺と右辺の配列から0番目の要素（唯一の要素）を取り出す操作を表すASTノードを生成します。
    *   `a := Nod(n.Op, l0, r0)`は、取り出された2つの要素に対して元の比較演算子（`==`または`!=`）を適用するASTノードを生成します。
    *   `finishcompare(np, n, a, init)`: この新しい要素間の比較ノード`a`を使って比較を完了させます。これにより、`[1]T`の比較は、その内部要素の比較に直接変換されます。

これらの変更により、コンパイラは`[0]T`と`[1]T`の比較を、それぞれ定数`true`/`false`または内部要素の比較に直接置き換えることができるようになり、不要な汎用比較コードの生成を完全に回避します。

### 性能への影響

この最適化は、特に`fmt.Printf`のような可変長引数関数が多用されるGoプログラムにおいて、生成されるバイナリのサイズを削減します。コミットメッセージにあるように、`cmd/go`や`golang.org/x/tools/cmd/godoc`といったツールで約0.1%のサイズ削減が確認されており、これはGoエコシステム全体で累積すると無視できない改善となります。バイナリサイズの削減は、配布サイズ、メモリ使用量、ロード時間の改善に繋がります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/subr.go` の変更点

`algtype1`関数は、Goコンパイラが特定の型に対してどのような比較アルゴリズムを使用すべきかを決定する内部関数です。この関数は、型の特性に基づいて整数値を返します。この整数値は、コンパイラがその型の比較、ハッシュ、ゼロ初期化などの操作をどのように処理するかを指示します。

変更された部分では、比較対象の型`t`が配列型（`t.Etype`が`TARRAY`）である場合に、その配列の要素数（`t.Bound`）をチェックする`switch`文が追加されています。

*   `case 0:`: `t.Bound`が`0`の場合、つまり`[0]T`のような要素数0の配列型の場合です。この場合、すべての`[0]T`型の値は常に等しいという自明な事実に基づき、`AMEM`を返します。`AMEM`は、コンパイラに対して、この型の比較は常に真であるか、あるいは比較自体が不要であることを示唆する特別な値です。これにより、コンパイラは不要な比較コードを生成する手間を省きます。
*   `case 1:`: `t.Bound`が`1`の場合、つまり`[1]T`のような要素数1の配列型の場合です。この場合、配列の等価性は、その唯一の要素の等価性に完全に依存します。したがって、`a`を返します。ここで`a`は、配列の要素型に対する比較アルゴリズムのタイプを指します。これにより、コンパイラは配列全体の比較ではなく、その内部の単一要素の比較ロジックを再利用するように指示されます。

この変更により、コンパイラは`[0]T`と`[1]T`という特殊な配列型に対して、より特化した、かつ効率的な比較処理の指示を受け取ることができるようになります。

### `src/cmd/compile/internal/gc/walk.go` の変更点

`walkcompare`関数は、Goコンパイラの「ウォーク」フェーズの一部であり、比較演算子（`==`や`!=`など）を含む抽象構文木（AST）ノードを処理します。この関数は、比較演算をより低レベルの操作に変換し、最終的に機械語コードを生成するための準備を行います。

追加されたコードブロックは、比較対象の型`t`が配列型（`t.Etype == TARRAY`）である場合に実行されます。ここでも、配列の要素数（`t.Bound`）に基づいて処理が分岐します。

*   `case 0:`: 要素数0の配列（`[0]T`）の比較の場合です。
    *   `finishcompare(np, n, Nodbool(n.Op == OEQ), init)`: この行は、比較の結果を直接ブール定数に置き換えます。`n.Op == OEQ`は、元の比較演算子が`==`であれば`true`、`!=`であれば`false`となります。つまり、`[0]T == [0]T`は常に`true`に、`[0]T != [0]T`は常に`false`にコンパイル時に解決されます。これにより、実行時に比較を行うためのコードが一切生成されなくなります。
*   `case 1:`: 要素数1の配列（`[1]T`）の比較の場合です。
    *   `l0 := Nod(OINDEX, l, Nodintconst(0))`と`r0 := Nod(OINDEX, r, Nodintconst(0))`は、それぞれ比較対象の左辺`l`と右辺`r`の配列から、インデックス`0`の要素を取り出すASTノードを生成します。`Nod(OINDEX, ...)`は配列のインデックスアクセスを表すノードです。
    *   `a := Nod(n.Op, l0, r0)`は、取り出された2つの要素`l0`と`r0`に対して、元の比較演算子`n.Op`（`==`または`!=`）を適用する新しい比較ASTノード`a`を生成します。
    *   `finishcompare(np, n, a, init)`: この新しい要素間の比較ノード`a`を使って比較処理を完了させます。これにより、`[1]T`型の配列の比較は、その内部の単一要素の比較に直接変換されます。配列のラッパーとしてのオーバーヘッドが取り除かれ、より効率的なコードが生成されます。

これらの変更は、コンパイラが`[0]T`と`[1]T`の比較を、実行時のコード生成を伴わない定数評価、またはより単純な要素間の比較に置き換えることを可能にし、結果として生成されるバイナリのサイズを削減し、実行効率を向上させます。

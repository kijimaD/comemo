## 変更の背景

このコミットの背景には、Go言語のテンプレートエンジンにおける空白文字の処理に関する特定のバグが存在していました。テンプレートエンジンは、ユーザーが定義したテンプレート文字列を解析し、データと結合して最終的な出力を生成します。この過程で、テンプレート内の特定の構文要素（例えば、アクションブロックを示す`{{...}}`や、このコミットで言及されている`{`）の前後にある空白文字をどのように扱うかは、出力の正確性に大きく影響します。

元の実装では、波括弧`{`の直前に存在する空白文字の処理に論理的な誤りがあり、意図しない挙動を引き起こしていたと考えられます。このバグは、おそらく特定のテンプレートパターンにおいて、余分な空白が出力されたり、期待される空白が削除されたりする形で顕在化していたでしょう。

この問題を修正するために、関連するテストケースがコメントアウトされていたものを有効化し、そのテストが正しくパスするようにコードの修正が行われました。テストの有効化は、バグの再現性を確認し、修正が正しく機能することを確認するための重要なステップです。

## 前提知識の解説

### Go言語のテンプレートエンジン（`text/template`の前身）

Go言語には、テキストベースの出力を生成するための強力なテンプレートエンジンが標準ライブラリとして提供されています。このコミットが作成された2009年当時、このパッケージは`src/lib/template`に位置しており、現在の`text/template`パッケージの基礎を築いたものです。

テンプレートエンジンは、主に以下の要素で構成されます。

*   **テンプレート文字列**: プレースホルダーや制御構造（条件分岐、ループなど）を含むテキスト。
*   **データ**: テンプレートに埋め込むためのGoの構造体、マップ、スライスなどの値。
*   **パーサー**: テンプレート文字列を解析し、内部的な表現（AST: 抽象構文木など）に変換する部分。
*   **エグゼキューター**: 解析されたテンプレートとデータを結合し、最終的な出力を生成する部分。

### テンプレートの構文と空白文字の扱い

Goのテンプレート構文では、アクションブロックは通常`{{`と`}}`で囲まれます。しかし、このコミットで言及されている`{`は、おそらくテンプレート内の特定のコンテキスト（例えば、構造体やマップのリテラル、あるいは特定の制御構造の開始）を示すものとして扱われていたと考えられます。

テンプレートエンジンにおける空白文字の扱いは非常に重要です。例えば、HTMLテンプレートでは、余分な空白がレンダリング結果に影響を与えることがあります。Goのテンプレートエンジンは、デフォルトで空白を保持しますが、特定の状況下ではトリミング（削除）する機能も提供しています。このコミットのバグは、この空白のトリミングまたは保持のロジックに問題があったことを示唆しています。

### `t.p`と`i`について

コミットの差分を見ると、`src/lib/template/template.go`内のコードで`t.p`と`i`という変数が使われています。これらはテンプレートのパース処理における現在の位置を示すインデックスであると推測されます。

*   `t.p`: テンプレートパーサー（`t`）が現在処理している文字列の開始位置、または以前に処理した最後の文字の次の位置を示すポインタ（インデックス）。
*   `i`: 現在走査している文字列のインデックス。

これらの変数は、テンプレート文字列を文字単位で読み込み、特定のパターン（この場合は`{`）を検出する際に使用されます。

## 技術的詳細

このコミットの技術的詳細は、`src/lib/template/template.go`内の`Loop:`ラベルを持つセクションにおける条件式の変更に集約されます。

元のコード:
```go
} else if i > t.p+1 {  // have some text accumulated so stop before '{'
    break Loop;
}
```

変更後のコード:
```go
} else if i > t.p {  // have some text accumulated so stop before '{'
    break Loop;
}
```

この変更は、テンプレートパーサーが`{`文字を検出した際に、それまでに蓄積されたテキストの処理をどこで停止するかというロジックに影響を与えます。

*   **`i > t.p+1`**: この条件は、「現在のインデックス`i`が、以前のポインタ`t.p`から2文字以上進んでいる場合」にループを中断することを意味します。これは、`t.p`と`i`の間に少なくとも2文字（例えば、1文字のテキストと1文字の空白）が存在する場合に、`{`の直前で停止するという意図があったのかもしれません。しかし、これが特定のシナリオで誤動作を引き起こしていたと考えられます。例えば、`t.p`の直後に`{`が来る場合や、`t.p`と`{`の間に1文字の空白しかない場合に、この条件が正しく評価されず、余分な文字が取り込まれてしまったり、逆に必要な文字が取り込まれなかったりする可能性がありました。

*   **`i > t.p`**: この修正後の条件は、「現在のインデックス`i`が、以前のポインタ`t.p`よりも進んでいる場合」にループを中断することを意味します。これはより一般的な条件であり、`t.p`と`i`の間に少なくとも1文字が存在すればループを中断します。この変更により、`{`の直前の空白文字の有無にかかわらず、`{`の直前でテキストの蓄積を停止するという意図がより正確に反映されるようになりました。これにより、テンプレートパーサーが`{`を正しく認識し、その前のテキストを適切に処理できるようになります。

この修正は、テンプレートパーサーが`{`文字を検出した際に、その直前のテキスト（特に空白文字）をどのように「区切り」として認識するかという、非常に細かいが重要なロジックの調整です。この調整により、テンプレートのパース結果がより予測可能になり、意図しない空白文字の挿入や削除が防がれます。

また、`src/lib/template/template_test.go`では、コメントアウトされていたテストケースが有効化されています。

元のコメントアウトされたテスト:
```go
//	&Test{
//		"{.section data}{.end} {header}\n",
//		
//		" 77\n"
//	},
```

有効化されたテスト:
```go
	&Test{
		"{.section data}{.end} {integer}\n",

		" 77\n"
	},
```

このテストケースは、`{.section data}{.end}`というテンプレート構文の後に空白があり、その後に`{integer}`という別の構文が続く場合の挙動を検証しています。元のテストでは`{header}`が使われていましたが、修正後は`{integer}`に変更されています。これは、おそらく`integer`という名前のデータフィールドが存在し、その値が`77`であることを期待しているテストです。このテストが有効化され、上記の`template.go`の修正によってパスするようになったことで、`{`の前の空白処理のバグが修正されたことが確認できます。

### `src/lib/template/template.go`の変更

この変更は、テンプレートパーサーが`{`文字を検出した際に、その直前のテキストの処理を停止する条件を修正しています。

*   **`i > t.p+1` から `i > t.p` への変更**:
    *   `t.p`は、パーサーが以前に処理したテキストの最後の位置、または現在の処理ブロックの開始位置を示します。
    *   `i`は、パーサーが現在走査している文字のインデックスです。
    *   元の条件`i > t.p+1`は、「`t.p`から2文字以上進んだ位置に`{`がある場合」にループを中断するというものでした。これは、`t.p`と`{`の間に少なくとも1文字のテキスト（または空白）があることを期待しているように見えます。しかし、これが特定のケース（例えば、`t.p`の直後に`{`が来る場合や、`t.p`と`{`の間に1文字の空白しかない場合）で誤動作を引き起こし、`{`の前の空白が正しく処理されない原因となっていました。
    *   修正後の条件`i > t.p`は、「`t.p`から1文字以上進んだ位置に`{`がある場合」にループを中断するという、より一般的な条件です。これにより、`t.p`の直後に`{`が来る場合でも、`t.p`と`{`の間に1文字の空白がある場合でも、`{`の直前でテキストの蓄積が正確に停止されるようになります。この変更によって、`{`の前の空白文字が適切に区切られ、テンプレートのパースが意図通りに行われるようになりました。

この修正は、テンプレートパーサーが`{`を「区切り文字」として認識する際のロジックを微調整し、その前のテキスト（特に空白）の取り込み範囲を正確に制御することを目的としています。

### `src/lib/template/template_test.go`の変更

このファイルでは、コメントアウトされていたテストケースが有効化され、その内容がわずかに変更されています。

*   **テストケースの有効化**:
    *   元のコードでは、特定のバグを再現する可能性のあるテストケースがコメントアウトされていました。これは、そのテストが当時の実装では失敗していたため、一時的に無効化されていたことを示唆しています。
    *   今回のコミットでこのテストが有効化されたということは、`template.go`の修正によってこのテストがパスするようになったことを意味します。これにより、バグが修正されたことの確証が得られます。

*   **テスト内容の変更**:
    *   `"{.section data}{.end} {header}\\n"` から `"{.section data}{.end} {integer}\\n"` への変更は、テスト対象のテンプレート文字列内のプレースホルダーが`header`から`integer`に変わったことを示しています。これは、テストの意図をより明確にするため、またはテストデータとの整合性を取るための変更であると考えられます。
    *   このテストケースは、`{.section data}{.end}`というブロックの後に空白文字が続き、その後に別のデータプレースホルダー（`{integer}`）が続くというシナリオを検証しています。期待される出力が`" 77\\n"`であることから、`{integer}`が`77`という値に展開され、その前に空白文字が正しく保持されることを確認していると推測されます。このテストがパスすることで、`{`の前の空白文字がテンプレートエンジンによって正しく解釈・保持されることが保証されます。

## コアとなるコードの解説

### `src/lib/template/template.go`の変更

この変更は、テンプレートパーサーが`{`文字を検出した際に、その直前のテキストの処理を停止する条件を修正しています。

*   **`i > t.p+1` から `i > t.p` への変更**:
    *   `t.p`は、パーサーが以前に処理したテキストの最後の位置、または現在の処理ブロックの開始位置を示します。
    *   `i`は、パーサーが現在走査している文字のインデックスです。
    *   元の条件`i > t.p+1`は、「`t.p`から2文字以上進んだ位置に`{`がある場合」にループを中断するというものでした。これは、`t.p`と`{`の間に少なくとも1文字のテキスト（または空白）があることを期待しているように見えます。しかし、これが特定のケース（例えば、`t.p`の直後に`{`が来る場合や、`t.p`と`{`の間に1文字の空白しかない場合）で誤動作を引き起こし、`{`の前の空白が正しく処理されない原因となっていました。
    *   修正後の条件`i > t.p`は、「`t.p`から1文字以上進んだ位置に`{`がある場合」にループを中断するという、より一般的な条件です。これにより、`t.p`の直後に`{`が来る場合でも、`t.p`と`{`の間に1文字の空白がある場合でも、`{`の直前でテキストの蓄積が正確に停止されるようになります。この変更によって、`{`の前の空白文字が適切に区切られ、テンプレートのパースが意図通りに行われるようになりました。

この修正は、テンプレートパーサーが`{`を「区切り文字」として認識する際のロジックを微調整し、その前のテキスト（特に空白）の取り込み範囲を正確に制御することを目的としています。

### `src/lib/template/template_test.go`の変更

このファイルでは、コメントアウトされていたテストケースが有効化され、その内容がわずかに変更されています。

*   **テストケースの有効化**:
    *   元のコードでは、特定のバグを再現する可能性のあるテストケースがコメントアウトされていました。これは、そのテストが当時の実装では失敗していたため、一時的に無効化されていたことを示唆しています。
    *   今回のコミットでこのテストが有効化されたということは、`template.go`の修正によってこのテストがパスするようになったことを意味します。これにより、バグが修正されたことの確証が得られます。

*   **テスト内容の変更**:
    *   `"{.section data}{.end} {header}\\n"` から `"{.section data}{.end} {integer}\\n"` への変更は、テスト対象のテンプレート文字列内のプレースホルダーが`header`から`integer`に変わったことを示しています。これは、テストの意図をより明確にするため、またはテストデータとの整合性を取るための変更であると考えられます。
    *   このテストケースは、`{.section data}{.end}`というブロックの後に空白文字が続き、その後に別のデータプレースホルダー（`{integer}`）が続くというシナリオを検証しています。期待される出力が`" 77\\n"`であることから、`{integer}`が`77`という値に展開され、その前に空白文字が正しく保持されることを確認していると推測されます。このテストがパスすることで、`{`の前の空白文字がテンプレートエンジンによって正しく解釈・保持されることが保証されます。

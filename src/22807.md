# [インデックス 22807] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/http`パッケージにおいて、HTTPトランスポート層におけるコネクションのクローズとレスポンスの受信が競合する論理的なレースコンディションを、より優雅に（gracefully）処理するための改善です。具体的には、`Transport.RoundTrip`メソッド内で発生しうる、レスポンスが保留中のラウンドトリップとコネクションクローズチャネルの競合を解消し、以前存在した100ミリ秒の不必要な遅延を排除することを目的としています。

  net/http: handle close/response race more gracefully

  There was a logical race in Transport.RoundTrip where a roundtrip with
  a pending response would race with the channel for the connection
  closing. This usually happened for responses with connection: close
  and no body.

  We handled this race by reading the close channel, setting a timer
  for 100ms and if no response was returned before then, we would then
  return an error.

  This put a lower bound on how fast a connection could fail. We couldn't
  fail a request faster than 100ms.

  Reordering the channel operations gets rid of the logical race. If
  the readLoop causes the connection to be closed, it would have put
  its response into the return channel already and we can fetch it with
  a non-blocking receive.

## 変更の背景

この変更が行われる前、Goの`net/http`パッケージの`Transport`実装には、特定の条件下でパフォーマンス上の問題を引き起こす論理的なレースコンディションが存在していました。

問題は、`Transport.RoundTrip`メソッドがHTTPリクエストを送信し、そのレスポンスを待つ際に発生しました。特に、`Connection: close`ヘッダを持つレスポンス（つまり、レスポンスの送信後にサーバーがコネクションを閉じることを示す場合）や、ボディを持たないレスポンスの場合に顕著でした。

このような状況では、`persistConn`（永続的なコネクションを管理する内部構造体）の`readLoop`ゴルーチンがレスポンスを処理し、それを`RoundTrip`ゴルーチンに送信するのと、コネクションがクローズされたことを`RoundTrip`ゴルーチンに通知するチャネル（`closech`）が競合していました。

以前の実装では、このレースコンディションを回避するために、`RoundTrip`が`closech`からの通知を先に受け取った場合、レスポンスがまだ到着していない可能性があると判断し、100ミリ秒のタイマーを設定してレスポンスの到着を待つという回避策が取られていました。もし100ミリ秒以内にレスポンスが到着しなければ、エラーとして処理されていました。

この100ミリ秒のタイマーは、コネクションが失敗するまでの最小時間を100ミリ秒に制限するという副作用をもたらしました。つまり、たとえコネクションが即座にクローズされたとしても、エラーが返されるまでに最低100ミリ秒の遅延が発生し、これが全体的なパフォーマンス、特に多数の短命なコネクションを扱う場合に悪影響を与えていました。

このコミットの目的は、この論理的なレースコンディションを根本的に解消し、不必要な100ミリ秒の遅延を排除することで、コネクションのクローズ処理をより効率的かつ即座に行えるようにすることでした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の`net/http`パッケージの内部構造と、一般的なネットワークプログラミングの概念に関する知識が必要です。

1.  **`net/http`パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
2.  **`http.Transport`**: HTTPクライアントがネットワークリクエストを行うための低レベルな実装を提供します。コネクションの確立、再利用、プロキシの処理、TLSハンドシェイクなどを担当します。通常、`http.Client`の内部で使用されます。
3.  **`persistConn`**: `http.Transport`の内部で使用される構造体で、単一のHTTP/1.1コネクション（TCPコネクション）を抽象化し、そのライフサイクル（確立、リクエストの送信、レスポンスの受信、アイドル状態での再利用、クローズ）を管理します。HTTP/1.1のKeep-Alive機能により、複数のリクエスト/レスポンスを同じTCPコネクション上で処理できます。
4.  **`readLoop`ゴルーチン**: `persistConn`の重要な部分で、バックグラウンドで動作するゴルーチンです。このゴルーチンは、基盤となるTCPコネクションからレスポンスデータを継続的に読み取り、パースし、適切な`RoundTrip`ゴルーチンにレスポンスを送信する役割を担います。コネクションがクローズされたり、エラーが発生したりした場合も、このゴルーチンが検出します。
5.  **`RoundTrip`メソッド**: `http.Transport`の主要なメソッドで、単一の`http.Request`を受け取り、対応する`http.Response`を返します。このメソッドは、`persistConn`を選択または確立し、リクエストを送信し、`readLoop`ゴルーチンからレスポンスを受け取るまで待機します。
6.  **Goのチャネル (Channels)**: ゴルーチン間で値を安全に送受信するためのGoのプリミティブです。チャネルは、ゴルーチン間の同期と通信を可能にします。
    *   **バッファなしチャネル**: 送信側が受信側が値を受け取るまでブロックし、受信側が送信側が値を送信するまでブロックします。同期的な通信に適しています。
    *   **バッファありチャネル**: 指定された数の値をバッファに格納できます。バッファが満杯になるまで送信はブロックされず、バッファが空になるまで受信はブロックされません。
7.  **Goの`select`文**: 複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行します。`select`は、非ブロッキング操作やタイムアウトの実装によく使用されます。
    *   `case <-ch:`: チャネル`ch`からの受信操作。
    *   `case ch <- val:`: チャネル`ch`への送信操作。
    *   `default:`: `select`ブロック内のどの`case`もすぐに実行できない場合に実行されます。`default`ケースが存在する場合、`select`文はブロックしません。
8.  **`Connection: close` HTTPヘッダ**: HTTPレスポンスヘッダの一つで、サーバーがレスポンスの送信後にTCPコネクションをクローズすることを示します。これは、HTTP/1.1のKeep-Aliveのデフォルト動作を上書きします。
9.  **レースコンディション (Race Condition)**: 複数の並行プロセス（この場合はゴルーチン）が共有リソース（この場合はチャネルやコネクションの状態）にアクセスし、その実行順序によって結果が非決定的に変わる状況を指します。

## 技術的詳細

このコミットの核心は、`persistConn.readLoop`と`persistConn.roundTrip`間のチャネル通信の順序とロジックを変更することで、既存の論理的なレースコンディションを解消することにあります。

### 以前のレースコンディションと100msタイマーの問題

`persistConn.readLoop`は、レスポンスを読み取ると、それを`responseAndError`構造体として`rc.ch`チャネル（`roundTrip`ゴルーチンがレスポンスを受け取るためのチャネル）に送信します。同時に、コネクションがクローズされると、`persistConn.closech`チャネルが閉じられ、`roundTrip`ゴルーチンにコネクションの終了を通知します。

問題は、`roundTrip`ゴルーチンが`select`文を使って`rc.ch`からのレスポンスと`pc.closech`からのコネクションクローズ通知の両方を待機していた点にありました。特に、`Connection: close`ヘッダを持つレスポンスやボディがないレスポンスの場合、`readLoop`はレスポンスを送信する直前または直後にコネクションをクローズすることがありました。

このとき、`select`文の非決定性により、`roundTrip`が`pc.closech`からの通知を`rc.ch`からのレスポンスよりも先に受け取ってしまう可能性がありました。もし`closech`が先に選択された場合、`roundTrip`はコネクションが死んだと判断しますが、実際には`readLoop`は既にレスポンスを`rc.ch`に送信済みであるか、送信しようとしている途中である可能性がありました。

この「コネクションは死んだが、レスポンスはまだ来るかもしれない」という状況を処理するために、以前は100ミリ秒の`time.After`タイマー（`failTicker`）が導入されていました。`closech`が選択された場合、`roundTrip`は100ミリ秒間待機し、その間に`rc.ch`からレスポンスが来ればそれを受け取り、来なければエラー（`errClosed`）を返していました。

この100ミリ秒の待機は、コネクションが実際にクローズされたにもかかわらず、エラーが即座に伝播しないというパフォーマンス上のボトルネックとなっていました。

### 変更によるレースコンディションの解消

このコミットは、以下の2つの主要な変更によってこの問題を解決します。

1.  **`readLoop`におけるチャネル送信順序の変更**:
    `src/net/http/transport.go`の`persistConn.readLoop`内で、レスポンスを`rc.ch`に送信する処理が、コネクションをアイドル状態に戻す（`pc.t.putIdleConn(pc)`）処理よりも**前**に移動されました。
    以前:
    ```go
    // ...
    if alive && !hasBody {
        alive = !pc.sawEOF &&
            pc.wroteRequest() &&
            pc.t.putIdleConn(pc)
    }
    rc.ch <- responseAndError{resp, err} // レスポンス送信がputIdleConnの後
    // ...
    ```
    変更後:
    ```go
    // ...
    rc.ch <- responseAndError{resp, err} // レスポンス送信がputIdleConnの前
    if alive && !hasBody {
        alive = !pc.sawEOF &&
            pc.wroteRequest() &&
            pc.t.putIdleConn(pc)
    }
    // ...
    ```
    この変更により、`readLoop`がコネクションをクローズする（またはアイドル状態に戻すことで、実質的に`closech`が閉じられる状況を作り出す）前に、必ずレスポンスを`rc.ch`に送信することが保証されます。コミットメッセージにあるように、「`readLoop`がコネクションをクローズする原因となる場合、それは既にレスポンスをリターンチャネルに入れているはず」という状態が作られます。

2.  **`roundTrip`における非ブロッキング受信の導入**:
    `src/net/http/transport.go`の`persistConn.roundTrip`内で、`pc.closech`が選択された場合の処理が変更されました。以前の100ミリ秒タイマー（`failTicker`）は削除され、代わりに`rc.ch`からの非ブロッキング受信が導入されました。
    以前:
    ```go
    case <-pconnDeadCh: // pc.closech
        // ...
        pconnDeadCh = nil
        failTicker = time.After(100 * time.Millisecond) // 100ms待機
    case <-failTicker:
        re = responseAndError{err: errClosed}
        break WaitResponse
    ```
    変更後:
    ```go
    case <-pc.closech:
        // ...
        // If we got a response, readLoop makes sure
        // to send it before it puts the conn and closes the channel.
        // That way, we can fetch the response, if there is one,
        // with a non-blocking receive.
        select {
        case re = <-resc: // rescはrc.chと同じ
            if fn := testHookPersistConnClosedGotRes; fn != nil {
                fn()
            }
        default: // 非ブロッキング受信
            re = responseAndError{err: errClosed}
        }
        break WaitResponse
    ```
    この変更により、`roundTrip`が`pc.closech`からの通知を受け取った場合でも、すぐにエラーを返すのではなく、まず`select`文の`default`ケースを利用して`resc`（`rc.ch`）から非ブロッキングでレスポンスを試行します。
    `readLoop`がレスポンスを先に送信しているため、もしレスポンスが既に`rc.ch`に存在すれば、この非ブロッキング受信で即座にそれを受け取ることができます。もし`rc.ch`が空であれば（つまり、本当にレスポンスが来ていないか、既に処理済みの場合）、`default`ケースが実行され、即座に`errClosed`エラーが返されます。

### テストフックの導入

`src/net/http/export_test.go`には、テスト目的で`testHookPersistConnClosedGotRes`という関数ポインタが追加されました。これは、`roundTrip`が`pc.closech`を受け取った後に、非ブロッキング受信でレスポンスを正常に取得できた場合に呼び出されるフックです。
`src/net/http/transport_test.go`には、このフックを利用した`TestTransportResponseCloseRace`という新しいテストが追加され、チャネル操作の順序変更が正しく機能し、レースコンディションが解消されたことを検証しています。このテストは、意図的にレースコンディションを発生させやすい状況を作り出し、フックが呼び出されることを確認することで、修正が有効であることを証明しています。

これらの変更により、`net/http`クライアントは、コネクションがクローズされる際に不必要な遅延なく、より迅速かつ正確にレスポンスを処理できるようになりました。

## コアとなるコードの解説

このコミットの核心的な変更は、`persistConn.readLoop`と`persistConn.roundTrip`という2つのゴルーチン間の通信プロトコルを微調整することにあります。

1.  **`persistConn.readLoop`におけるレスポンス送信の先行**:
    以前のコードでは、`readLoop`がレスポンスを`rc.ch`に送信する前に、コネクションをアイドル状態に戻す（`putIdleConn`）処理を行う可能性がありました。`putIdleConn`は、コネクションが再利用可能であればプールに戻しますが、もしコネクションがクローズされるべき状況（例: `Connection: close`ヘッダ）であれば、コネクションを閉じ、それに伴い`pc.closech`が閉じられる可能性がありました。
    この順序では、`readLoop`がレスポンスを送信する前に`pc.closech`が閉じられ、`roundTrip`が`pc.closech`からの通知を先に受け取ってしまうレースコンディションが発生しやすかったのです。
    変更後、`rc.ch <- responseAndError{resp, err}`が`putIdleConn`の呼び出しよりも**前**に移動されました。これにより、`readLoop`はコネクションの状態を変更する（そして`closech`を閉じる可能性のある）操作を行う前に、必ずレスポンスを`rc.ch`に送信することが保証されます。これは、`roundTrip`が`closech`からの通知を受け取ったとしても、`rc.ch`には既にレスポンスが準備されているという状態を作り出すための重要な変更です。

2.  **`persistConn.roundTrip`における非ブロッキング受信**:
    `roundTrip`メソッドの`select`文は、`rc.ch`からのレスポンスと`pc.closech`からのコネクションクローズ通知を同時に待機します。
    以前は、`pc.closech`が選択された場合、`roundTrip`は100ミリ秒のタイマーを設定してレスポンスの到着を待っていました。これは、`readLoop`がレスポンスを送信する前に`closech`が閉じられた場合に、レスポンスが遅れて到着する可能性を考慮したものでしたが、前述の通り不必要な遅延を生んでいました。
    変更後、`pc.closech`が選択された場合、`roundTrip`は`select`文の内部に新しい`select`ブロックを導入します。この内部`select`ブロックには、`case re = <-resc:`（`resc`は`rc.ch`と同じ）と`default:`ケースが含まれています。
    *   `case re = <-resc:`: これは`rc.ch`からの受信を試みます。もし`readLoop`が既にレスポンスを`rc.ch`に送信していれば、このケースが即座に実行され、レスポンスが取得されます。これはブロッキング操作ですが、`readLoop`が先に送信しているため、ほとんどの場合すぐに利用可能です。
    *   `default:`: もし`rc.ch`にまだレスポンスが来ていない場合（これは、`readLoop`がレスポンスを送信する前に`closech`が閉じられたという、本来解消されたはずのレースコンディションが何らかの理由で発生した場合、または`rc.ch`が既に空の場合）は、この`default`ケースが実行され、`errClosed`エラーが即座に返されます。`default`ケースがあるため、この内部`select`は決してブロックしません。

この組み合わせにより、`readLoop`がレスポンスを先に送信することを保証し、`roundTrip`がコネクションクローズ通知を受け取った場合でも、レスポンスが既にチャネルに存在するかどうかを非ブロッキングで確認できるようになりました。これにより、不必要な100ミリ秒の待機が完全に排除され、コネクションクローズ時のエラー処理が即座に行われるようになり、パフォーマンスが向上しました。

`testHookPersistConnClosedGotRes`は、この新しいロジックが正しく機能していることをテストするために導入されたフックです。`roundTrip`が`closech`を受け取った後に、非ブロッキング受信でレスポンスを正常に取得できた場合にこのフックが呼び出されることで、テストはレースコンディションが解消され、レスポンスが正しく処理されていることを検証できます。

## 変更の背景

この変更が行われる前、Goの`net/http`パッケージの`Transport`実装には、特定の条件下でパフォーマンス上の問題を引き起こす論理的なレースコンディションが存在していました。

問題は、`Transport.RoundTrip`メソッドがHTTPリクエストを送信し、そのレスポンスを待つ際に発生しました。特に、`Connection: close`ヘッダを持つレスポンス（つまり、レスポンスの送信後にサーバーがコネクションを閉じることを示す場合）や、ボディを持たないレスポンスの場合に顕著でした。

このような状況では、`persistConn`（永続的なコネクションを管理する内部構造体）の`readLoop`ゴルーチンがレスポンスを処理し、それを`RoundTrip`ゴルーチンに送信するのと、コネクションがクローズされたことを`RoundTrip`ゴルーチンに通知するチャネル（`closech`）が競合していました。

以前の実装では、このレースコンディションを回避するために、`RoundTrip`が`closech`からの通知を先に受け取った場合、レスポンスがまだ到着していない可能性があると判断し、100ミリ秒のタイマーを設定してレスポンスの到着を待つという回避策が取られていました。もし100ミリ秒以内にレスポンスが到着しなければ、エラーとして処理されていました。

この100ミリ秒のタイマーは、コネクションが失敗するまでの最小時間を100ミリ秒に制限するという副作用をもたらしました。つまり、たとえコネクションが即座にクローズされたとしても、エラーが返されるまでに最低100ミリ秒の遅延が発生し、これが全体的なパフォーマンス、特に多数の短命なコネクションを扱う場合に悪影響を与えていました。

このコミットの目的は、この論理的なレースコンディションを根本的に解消し、不必要な100ミリ秒の遅延を排除することで、コネクションのクローズ処理をより効率的かつ即座に行えるようにすることでした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の`net/http`パッケージの内部構造と、一般的なネットワークプログラミングの概念に関する知識が必要です。

1.  **`net/http`パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
2.  **`http.Transport`**: HTTPクライアントがネットワークリクエストを行うための低レベルな実装を提供します。コネクションの確立、再利用、プロキシの処理、TLSハンドシェイクなどを担当します。通常、`http.Client`の内部で使用されます。
3.  **`persistConn`**: `http.Transport`の内部で使用される構造体で、単一のHTTP/1.1コネクション（TCPコネクション）を抽象化し、そのライフサイクル（確立、リクエストの送信、レスポンスの受信、アイドル状態での再利用、クローズ）を管理します。HTTP/1.1のKeep-Alive機能により、複数のリクエスト/レスポンスを同じTCPコネクション上で処理できます。
4.  **`readLoop`ゴルーチン**: `persistConn`の重要な部分で、バックグラウンドで動作するゴルーチンです。このゴルーチンは、基盤となるTCPコネクションからレスポンスデータを継続的に読み取り、パースし、適切な`RoundTrip`ゴルーチンにレスポンスを送信する役割を担います。コネクションがクローズされたり、エラーが発生したりした場合も、このゴルーチンが検出します。
5.  **`RoundTrip`メソッド**: `http.Transport`の主要なメソッドで、単一の`http.Request`を受け取り、対応する`http.Response`を返します。このメソッドは、`persistConn`を選択または確立し、リクエストを送信し、`readLoop`ゴルーチンからレスポンスを受け取るまで待機します。
6.  **Goのチャネル (Channels)**: ゴルーチン間で値を安全に送受信するためのGoのプリミティブです。チャネルは、ゴルーチン間の同期と通信を可能にします。
    *   **バッファなしチャネル**: 送信側が受信側が値を受け取るまでブロックし、受信側が送信側が値を送信するまでブロックします。同期的な通信に適しています。
    *   **バッファありチャネル**: 指定された数の値をバッファに格納できます。バッファが満杯になるまで送信はブロックされず、バッファが空になるまで受信はブロックされません。
7.  **Goの`select`文**: 複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行します。`select`は、非ブロッキング操作やタイムアウトの実装によく使用されます。
    *   `case <-ch:`: チャネル`ch`からの受信操作。
    *   `case ch <- val:`: チャネル`ch`への送信操作。
    *   `default:`: `select`ブロック内のどの`case`もすぐに実行できない場合に実行されます。`default`ケースが存在する場合、`select`文はブロックしません。
8.  **`Connection: close` HTTPヘッダ**: HTTPレスポンスヘッダの一つで、サーバーがレスポンスの送信後にTCPコネクションをクローズすることを示します。これは、HTTP/1.1のKeep-Aliveのデフォルト動作を上書きします。
9.  **レースコンディション (Race Condition)**: 複数の並行プロセス（この場合はゴルーチン）が共有リソース（この場合はチャネルやコネクションの状態）にアクセスし、その実行順序によって結果が非決定的に変わる状況を指します。

## 技術的詳細

このコミットの核心は、`persistConn.readLoop`と`persistConn.roundTrip`間のチャネル通信の順序とロジックを変更することで、既存の論理的なレースコンディションを解消することにあります。

### 以前のレースコンディションと100msタイマーの問題

`persistConn.readLoop`は、レスポンスを読み取ると、それを`responseAndError`構造体として`rc.ch`チャネル（`roundTrip`ゴルーチンがレスポンスを受け取るためのチャネル）に送信します。同時に、コネクションがクローズされると、`persistConn.closech`チャネルが閉じられ、`roundTrip`ゴルーチンにコネクションの終了を通知します。

問題は、`roundTrip`ゴルーチンが`select`文を使って`rc.ch`からのレスポンスと`pc.closech`からのコネクションクローズ通知の両方を待機していた点にありました。特に、`Connection: close`ヘッダを持つレスポンスやボディがないレスポンスの場合、`readLoop`はレスポンスを送信する直前または直後にコネクションをクローズすることがありました。

このとき、`select`文の非決定性により、`roundTrip`が`pc.closech`からの通知を`rc.ch`からのレスポンスよりも先に受け取ってしまう可能性がありました。もし`closech`が先に選択された場合、`roundTrip`はコネクションが死んだと判断しますが、実際には`readLoop`は既にレスポンスを`rc.ch`に送信済みであるか、送信しようとしている途中である可能性がありました。

この「コネクションは死んだが、レスポンスはまだ来るかもしれない」という状況を処理するために、以前は100ミリ秒の`time.After`タイマー（`failTicker`）が導入されていました。`closech`が選択された場合、`roundTrip`は100ミリ秒間待機し、その間に`rc.ch`からレスポンスが来ればそれを受け取り、来なければエラー（`errClosed`）を返していました。

この100ミリ秒の待機は、コネクションが実際にクローズされたにもかかわらず、エラーが即座に伝播しないというパフォーマンス上のボトルネックとなっていました。

### 変更によるレースコンディションの解消

このコミットは、以下の2つの主要な変更によってこの問題を解決します。

1.  **`readLoop`におけるチャネル送信順序の変更**:
    `src/net/http/transport.go`の`persistConn.readLoop`内で、レスポンスを`rc.ch`に送信する処理が、コネクションをアイドル状態に戻す（`pc.t.putIdleConn(pc)`）処理よりも**前**に移動されました。
    以前:
    ```go
    // ...
    if alive && !hasBody {
        alive = !pc.sawEOF &&
            pc.wroteRequest() &&
            pc.t.putIdleConn(pc)
    }
    rc.ch <- responseAndError{resp, err} // レスポンス送信がputIdleConnの後
    // ...
    ```
    変更後:
    ```go
    // ...
    rc.ch <- responseAndError{resp, err} // レスポンス送信がputIdleConnの前
    if alive && !hasBody {
        alive = !pc.sawEOF &&
            pc.wroteRequest() &&
            pc.t.putIdleConn(pc)
    }
    // ...
    ```
    この変更により、`readLoop`がコネクションをクローズする（またはアイドル状態に戻すことで、実質的に`closech`が閉じられる状況を作り出す）前に、必ずレスポンスを`rc.ch`に送信することが保証されます。コミットメッセージにあるように、「`readLoop`がコネクションをクローズする原因となる場合、それは既にレスポンスをリターンチャネルに入れているはず」という状態が作られます。

2.  **`roundTrip`における非ブロッキング受信の導入**:
    `src/net/http/transport.go`の`persistConn.roundTrip`内で、`pc.closech`が選択された場合の処理が変更されました。以前の100ミリ秒タイマー（`failTicker`）は削除され、代わりに`rc.ch`からの非ブロッキング受信が導入されました。
    以前:
    ```go
    case <-pconnDeadCh: // pc.closech
        // ...
        pconnDeadCh = nil
        failTicker = time.After(100 * time.Millisecond) // 100ms待機
    case <-failTicker:
        re = responseAndError{err: errClosed}
        break WaitResponse
    ```
    変更後:
    ```go
    case <-pc.closech:
        // ...
        // If we got a response, readLoop makes sure
        // to send it before it puts the conn and closes the channel.
        // That way, we can fetch the response, if there is one,
        // with a non-blocking receive.
        select {
        case re = <-resc: // rescはrc.chと同じ
            if fn := testHookPersistConnClosedGotRes; fn != nil {
                fn()
            }
        default: // 非ブロッキング受信
            re = responseAndError{err: errClosed}
        }
        break WaitResponse
    ```
    この変更により、`roundTrip`が`pc.closech`からの通知を受け取った場合でも、すぐにエラーを返すのではなく、まず`select`文の`default`ケースを利用して`resc`（`rc.ch`）から非ブロッキングでレスポンスを試行します。
    `readLoop`がレスポンスを先に送信しているため、もしレスポンスが既に`rc.ch`に存在すれば、この非ブロッキング受信で即座にそれを受け取ることができます。もし`rc.ch`が空であれば（つまり、本当にレスポンスが来ていないか、既に処理済みの場合）、`default`ケースが実行され、即座に`errClosed`エラーが返されます。`default`ケースがあるため、この内部`select`は決してブロックしません。

### テストフックの導入

`src/net/http/export_test.go`には、テスト目的で`testHookPersistConnClosedGotRes`という関数ポインタが追加されました。これは、`roundTrip`が`pc.closech`を受け取った後に、非ブロッキング受信でレスポンスを正常に取得できた場合に呼び出されるフックです。
`src/net/http/transport_test.go`には、このフックを利用した`TestTransportResponseCloseRace`という新しいテストが追加され、チャネル操作の順序変更が正しく機能し、レースコンディションが解消されたことを検証しています。このテストは、意図的にレースコンディションを発生させやすい状況を作り出し、フックが呼び出されることを確認することで、修正が有効であることを証明しています。

これらの変更により、`net/http`クライアントは、コネクションがクローズされる際に不必要な遅延なく、より迅速かつ正確にレスポンスを処理できるようになりました。

## コアとなるコードの解説

このコミットの核心的な変更は、`persistConn.readLoop`と`persistConn.roundTrip`という2つのゴルーチン間の通信プロトコルを微調整することにあります。

1.  **`persistConn.readLoop`におけるレスポンス送信の先行**:
    以前のコードでは、`readLoop`がレスポンスを`rc.ch`に送信する前に、コネクションをアイドル状態に戻す（`putIdleConn`）処理を行う可能性がありました。`putIdleConn`は、コネクションが再利用可能であればプールに戻しますが、もしコネクションがクローズされるべき状況（例: `Connection: close`ヘッダ）であれば、コネクションを閉じ、それに伴い`pc.closech`が閉じられる可能性がありました。
    この順序では、`readLoop`がレスポンスを送信する前に`pc.closech`が閉じられ、`roundTrip`が`pc.closech`からの通知を先に受け取ってしまうレースコンディションが発生しやすかったのです。
    変更後、`rc.ch <- responseAndError{resp, err}`が`putIdleConn`の呼び出しよりも**前**に移動されました。これにより、`readLoop`はコネクションの状態を変更する（そして`closech`を閉じる可能性のある）操作を行う前に、必ずレスポンスを`rc.ch`に送信することが保証されます。これは、`roundTrip`が`closech`からの通知を受け取ったとしても、`rc.ch`には既にレスポンスが準備されているという状態を作り出すための重要な変更です。

2.  **`persistConn.roundTrip`における非ブロッキング受信**:
    `roundTrip`メソッドの`select`文は、`rc.ch`からのレスポンスと`pc.closech`からのコネクションクローズ通知を同時に待機します。
    以前は、`pc.closech`が選択された場合、`roundTrip`は100ミリ秒のタイマーを設定してレスポンスの到着を待っていました。これは、`readLoop`がレスポンスを送信する前に`closech`が閉じられた場合に、レスポンスが遅れて到着する可能性を考慮したものでしたが、前述の通り不必要な遅延を生んでいました。
    変更後、`pc.closech`が選択された場合、`roundTrip`は`select`文の内部に新しい`select`ブロックを導入します。この内部`select`ブロックには、`case re = <-resc:`（`resc`は`rc.ch`と同じ）と`default:`ケースが含まれています。
    *   `case re = <-resc:`: これは`rc.ch`からの受信を試みます。もし`readLoop`が既にレスポンスを`rc.ch`に送信していれば、このケースが即座に実行され、レスポンスが取得されます。これはブロッキング操作ですが、`readLoop`が先に送信しているため、ほとんどの場合すぐに利用可能です。
    *   `default:`: もし`rc.ch`にまだレスポンスが来ていない場合（これは、`readLoop`がレスポンスを送信する前に`closech`が閉じられたという、本来解消されたはずのレースコンディションが何らかの理由で発生した場合、または`rc.ch`が既に空の場合）は、この`default`ケースが実行され、`errClosed`エラーが即座に返されます。`default`ケースがあるため、この内部`select`は決してブロックしません。

この組み合わせにより、`readLoop`がレスポンスを先に送信することを保証し、`roundTrip`がコネクションクローズ通知を受け取った場合でも、レスポンスが既にチャネルに存在するかどうかを非ブロッキングで確認できるようになりました。これにより、不必要な100ミリ秒の待機が完全に排除され、コネクションクローズ時のエラー処理が即座に行われるようになり、パフォーマンスが向上しました。

`testHookPersistConnClosedGotRes`は、この新しいロジックが正しく機能していることをテストするために導入されたフックです。`roundTrip`が`closech`を受け取った後に、非ブロッキング受信でレスポンスを正常に取得できた場合にこのフックが呼び出されることで、テストはレースコンディションが解消され、レスポンスが正しく処理されていることを検証できます。

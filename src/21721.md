# [インデックス 21721] ファイルの概要

このコミットは、Goコンパイラツールチェーン（`cmd/6a`、`cmd/6g`、`cmd/6l`、`liblink`）における内部データ構造である`Prog`（プログラム命令）と`Addr`（アドレス/オペランド）の表現を、よりポータブルで明確なものに更新することを目的としています。具体的には、汎用的な`D_`プレフィックスを持つ定数を、`TYPE_`（アドレスの種類）や`REG_`（レジスタ）といった、より意味的に明確なプレフィックスを持つ定数に置き換える大規模なリファクタリングが行われています。これにより、コンパイラの内部コードの可読性、保守性、そして将来的な拡張性が向上します。

## 変更の背景

Go言語は、その強力なクロスコンパイル機能で知られています。これは、あるプラットフォーム（例: Windows）で別のプラットフォーム（例: Linux）向けの実行ファイルを生成できる能力を指します。このクロスコンパイルを効率的かつ堅牢に行うためには、コンパイラの内部表現が異なるアーキテクチャやオペレーティングシステム間で一貫性があり、かつ柔軟である必要があります。

このコミット以前のGoコンパイラでは、`Prog`（プログラム命令）や`Addr`（アドレス/オペランド）といった内部データ構造の型やレジスタを識別するために、`D_NONE`、`D_CONST`、`D_SP`のような汎用的な`D_`プレフィックスを持つ定数が使用されていました。これらの定数は、その用途が曖昧であったり、複数の異なる概念（例: アドレスの種類とレジスタの種類）を同じプレフィックスで表現していたりする問題がありました。

このような曖昧さは、コードの可読性を低下させ、新しいアーキテクチャのサポートやコンパイラの最適化といった将来的な変更を行う際に、意図しないバグを引き起こすリスクがありました。このコミットは、これらの内部定数を、`TYPE_`（型）や`REG_`（レジスタ）といった、よりセマンティックに明確なカテゴリに分割し、再定義することで、コンパイラの内部表現の「ポータビリティ」と「明確性」を向上させることを目的としています。これにより、コンパイラのコードベースがより理解しやすく、保守しやすくなり、将来の進化に対応しやすくなります。

## 前提知識の解説

このコミットの変更を理解するためには、以下のGoコンパイラツールチェーンの基本的な概念と内部構造に関する知識が必要です。

*   **Goコンパイラツールチェーン**:
    *   `cmd/6a` (Assembler): Goのアセンブリ言語を機械語に変換するアセンブラです。
    *   `cmd/6g` (Compiler): Goのソースコードを中間表現に変換し、最終的にアセンブリコードを生成するコンパイラです。
    *   `cmd/6l` (Linker): コンパイルされたオブジェクトファイルとライブラリを結合して実行可能ファイルを生成するリンカです。
    *   `liblink`: リンカが使用する共通のライブラリです。
    これらのツールは密接に連携し、Goプログラムのビルドプロセスを構成しています。

*   **`obj.Prog`と`obj.Addr`**:
    *   Goコンパイラのパイプラインにおいて、Goの関数はまず中間表現（IR）に変換され、その後、`obj.Prog`命令のシーケンスに変換されます。`obj.Prog`は、アセンブラが機械語に変換するための「プログラム命令」を表す構造体です。
    *   `obj.Addr`は、これらの`obj.Prog`命令のオペランド（引数）やアドレスを表す構造体です。例えば、メモリ上の位置、レジスタ、定数などが`Addr`として表現されます。これらは、Goコンパイラがコードを生成する際の「半抽象的な命令セット」の一部であり、必ずしも直接的な機械語命令にマッピングされるわけではありません。

*   **クロスコンパイル**:
    Go言語の大きな特徴の一つは、異なるオペレーティングシステムやCPUアーキテクチャ向けの実行ファイルを、現在の開発環境とは異なる環境でビルドできる「クロスコンパイル」の容易さです。これは、`GOOS`（ターゲットOS）や`GOARCH`（ターゲットアーキテクチャ）といった環境変数を設定するだけで実現できます。この機能は、Goコンパイラの内部が異なるプラットフォームの特性を抽象化し、共通の表現で処理できるような設計になっていることによって支えられています。

*   **内部定数 (`D_`, `TYPE_`, `REG_`)**:
    Goコンパイラの内部では、`Prog`や`Addr`構造体のフィールドの値を定義するために、多くの定数が使用されています。
    *   `D_`プレフィックスを持つ定数（例: `D_NONE`, `D_CONST`, `D_SP`, `D_AX`）は、以前のバージョンで使用されていた汎用的な定数です。これらは、アドレスの種類、レジスタの種類、その他の属性を区別するために使われていましたが、その命名規則は必ずしも明確ではありませんでした。
    *   このコミットでは、これらの`D_`定数が、よりセマンティックに特化した`TYPE_`プレフィックスを持つ定数（例: `TYPE_NONE`, `TYPE_CONST`, `TYPE_MEM`, `TYPE_BRANCH`）と、`REG_`プレフィックスを持つ定数（例: `REG_SP`, `REG_AX`, `REG_DI`）に置き換えられました。この変更は、コンパイラの内部コードにおける型システムとレジスタの表現をより厳密にし、コードの意図を明確にすることを目的としています。

## 技術的詳細

このコミットの核心は、Goコンパイラツールチェーン全体にわたる`Prog`および`Addr`構造体の内部表現の根本的なリファクタリングです。以前は、アドレスの種類、レジスタ、その他の属性を区別するために、`D_`プレフィックスを持つ単一のカテゴリの定数が使用されていました。しかし、これは複数の異なる概念を同じ命名規則で表現することになり、コードの意図が不明瞭になる原因となっていました。

この変更では、`D_`定数を以下の2つの明確なカテゴリに分割し、置き換えています。

1.  **`TYPE_`プレフィックスを持つ定数**: `Addr`構造体の`type`フィールドが表す「アドレスの種類」を明確に定義します。
    *   `D_NONE` → `TYPE_NONE`: オペランドが指定されていない状態。
    *   `D_CONST` → `TYPE_CONST`: オペランドが定数であることを示す。
    *   `D_BRANCH` → `TYPE_BRANCH`: オペランドが分岐先のアドレスであることを示す。
    *   `D_INDIR` → `TYPE_MEM`: オペランドがメモリ上の位置（間接参照）であることを示す。これは、以前の`D_INDIR`が単に間接参照を示すだけでなく、メモリ上のアドレスを指すことをより明確にしています。
    *   `D_ADDR` → `TYPE_ADDR`: オペランドがシンボルへのアドレスであることを示す。
    *   `D_SCONST` → `TYPE_SCONST`: オペランドが文字列定数であることを示す。
    *   `D_FCONST` → `TYPE_FCONST`: オペランドが浮動小数点定数であることを示す。

2.  **`REG_`プレフィックスを持つ定数**: `Addr`構造体の`reg`フィールドが表す「レジスタの種類」を明確に定義します。
    *   `D_SP` → `REG_SP`: スタックポインタレジスタ。
    *   `D_AX` → `REG_AX`: AXレジスタ（汎用レジスタ）。
    *   `D_DI` → `REG_DI`: DIレジスタ（汎用レジスタ、通常はデスティネーションインデックス）。
    *   `D_SI` → `REG_SI`: SIレジスタ（汎用レジスタ、通常はソースインデックス）。
    *   その他、`D_AL`, `D_CL`, `D_DX`, `D_BX`, `D_BP`, `D_R8`, `D_R9`などのレジスタ関連の`D_`定数も、それぞれ対応する`REG_`定数（例: `REG_AL`, `REG_CL`, `REG_DX`, `REG_BX`, `REG_BP`, `REG_R8`, `REG_R9`）に置き換えられています。

さらに、`Addr`構造体の`name`フィールドが表す「シンボルの種類」も明確化されています。
*   `D_AUTO` → `NAME_AUTO`: 自動変数（スタック上のローカル変数）。
*   `D_EXTERN` → `NAME_EXTERN`: 外部シンボル（グローバル変数や関数）。
*   `D_PARAM` → `NAME_PARAM`: 関数パラメータ。
*   `D_STATIC` → `NAME_STATIC`: 静的変数。

この変更は、コンパイラの字句解析器（`lex.c`）、構文解析器（`a.y`, `y.tab.c`）、コード生成器（`cgen.c`, `ggen.c`, `gsubr.c`）、オブジェクトファイル生成器（`gobj.c`）、リンカ（`6.out.h`, `asm6.c`, `list6.c`, `obj6.c`）など、Goコンパイラツールチェーンの広範な部分に影響を与えています。

このリファクタリングにより、コンパイラの内部コードはより厳密な型付けとセマンティックな分離を実現し、異なるアーキテクチャやオペレーティングシステム間での`Prog`と`Addr`の表現の一貫性を高めています。これは、Goのクロスコンパイル機能の堅牢性をさらに強化し、将来的なコンパイラの開発と保守を容易にするための重要なステップです。

## コアとなるコードの変更箇所

このコミットでは、Goコンパイラツールチェーンの複数のファイルにわたって、`D_`プレフィックスを持つ定数が`TYPE_`、`REG_`、`NAME_`プレフィックスを持つ定数に置き換えられています。以下に主要な変更箇所と、その変更がどのようなファイルに影響を与えているかを示します。

*   **`src/cmd/6a/a.y` (アセンブラのYacc定義ファイル)**:
    *   `D_NONE` → `TYPE_NONE`
    *   `D_CONST` → `TYPE_CONST`
    *   `D_BRANCH` → `TYPE_BRANCH`
    *   `D_INDIR` → `TYPE_MEM`
    *   レジスタ関連の`D_`定数（例: `D_SP`, `D_AX`） → `TYPE_REG`と`REG_`定数（例: `TYPE_REG`, `REG_SP`）
    *   シンボル関連の`D_`定数（例: `D_AUTO`, `D_EXTERN`, `D_STATIC`） → `NAME_`定数（例: `NAME_AUTO`, `NAME_EXTERN`, `NAME_STATIC`）

*   **`src/cmd/6a/lex.c` (アセンブラの字句解析器)**:
    *   `itab`配列内のレジスタやシンボルタイプ定義が、`D_`から`REG_`や`NAME_`に更新されています。

*   **`src/cmd/6a/y.tab.c` (アセンブラのYacc生成コード)**:
    *   `a.y`の変更に伴い、生成されたCコード内の定数参照が更新されています。

*   **`src/cmd/6g/cgen.c`, `src/cmd/6g/ggen.c`, `src/cmd/6g/gobj.c`, `src/cmd/6g/gsubr.c` (Goコンパイラのコード生成、オブジェクトファイル生成、サブルーチン関連)**:
    *   `Prog`や`Addr`構造体の初期化、操作、比較を行う箇所で、`D_`定数が`TYPE_`、`REG_`、`NAME_`定数に置き換えられています。
    *   特に、`agenr`関数での`Prog`の`from.type`と`from.index`の扱い、`igen`関数での`D_SP`の参照、`sgen`関数でのレジスタ定数（`D_DI`, `D_SI`, `D_CX`）の参照、`clearfat`関数での`D_DI`, `D_AX`の参照、`expandchecks`関数での`D_CONST`, `D_AX`, `D_INDIR`の参照などが変更されています。
    *   `clearp`関数での`Prog`の初期化も`TYPE_NONE`を使用するように変更されています。
    *   `appendpp`関数の引数に`freg`と`treg`が追加され、`Prog`の`from.reg`と`to.reg`が明示的に設定されるようになっています。

*   **`src/cmd/6g/gg.h` (Goコンパイラのヘッダファイル)**:
    *   `reg`配列のサイズ定義が`D_NONE`から`MAXREG`に変更され、レジスタの最大数をより適切に反映しています。

*   **`src/cmd/6l/6.out.h` (リンカの出力ヘッダ)**:
    *   `D_`定数から`TYPE_`、`REG_`、`NAME_`定数へのマッピングが定義されています。これは、リンカがコンパイラやアセンブラから受け取るオブジェクトファイルの内部構造を解釈するために必要です。

*   **`src/liblink/asm6.c`, `src/liblink/list6.c`, `src/liblink/obj6.c` (リンカのライブラリ)**:
    *   リンカが`Prog`や`Addr`構造体を処理する際に、新しい定数を使用するようにコードが更新されています。

これらの変更は、コンパイラの内部表現のセマンティックな明確性を大幅に向上させ、コードの保守性と拡張性を高めることに貢献しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`Prog`と`Addr`構造体における「型」と「レジスタ」の表現方法の分離と明確化です。

以前の`Addr`構造体には、`type`フィールドと`index`フィールドがあり、これらが`D_`プレフィックスを持つ定数で設定されていました。例えば、`D_NONE`は「型なし」を意味することもあれば、「インデックスなし」を意味することもあり、`D_SP`は「スタックポインタレジスタ」を意味することもあれば、「スタックポインタ型のアドレス」を意味することもありました。このような多義性は、コードの解釈を複雑にし、バグの温床となる可能性がありました。

このコミットでは、この曖昧さを解消するために、以下のように変更されました。

1.  **`Addr.type`のセマンティックな明確化**:
    *   `Addr.type`は、そのオペランドが「何であるか」という種類（例: 定数、メモリ参照、分岐先）を明確に表すようになりました。`D_NONE`は`TYPE_NONE`に、`D_CONST`は`TYPE_CONST`に、`D_INDIR`は`TYPE_MEM`に、`D_BRANCH`は`TYPE_BRANCH`にそれぞれ置き換えられました。これにより、`Addr.type`を見ただけで、そのオペランドがどのような性質を持つかが一目でわかるようになりました。
    *   例えば、`p->to.type = D_INDIR+D_NONE;` のような記述は、`p->to.type = TYPE_MEM;` となり、より直感的に「メモリへの間接参照」であることが伝わります。

2.  **`Addr.reg`フィールドの導入とレジスタの分離**:
    *   以前は`Addr.type`や`Addr.index`で表現されていたレジスタ情報が、新しく導入された`Addr.reg`フィールドに集約されました。そして、レジスタを識別するための定数には`REG_`プレフィックス（例: `REG_SP`, `REG_AX`, `REG_DI`）が使用されるようになりました。
    *   これにより、`Addr`構造体は、`type`フィールドでオペランドの種類を、`reg`フィールドで関連するレジスタを、それぞれ独立して表現できるようになりました。例えば、`D_SP`のような定数が、`TYPE_REG`と`REG_SP`という2つの情報に分解されることで、より詳細で正確な表現が可能になります。

3.  **`Addr.name`フィールドのシンボル種別の明確化**:
    *   `D_AUTO`, `D_EXTERN`, `D_PARAM`, `D_STATIC`といったシンボル種別を表す定数も、`NAME_AUTO`, `NAME_EXTERN`, `NAME_PARAM`, `NAME_STATIC`といった`NAME_`プレフィックスを持つ定数に置き換えられ、`Addr.name`フィールドで明確に表現されるようになりました。これにより、シンボルの種類がより明確に区別できるようになりました。

これらの変更は、コンパイラの内部コードにおける「型システム」をより厳密にし、各フィールドが持つべき意味を明確に定義しています。これにより、コンパイラの開発者は、`Prog`や`Addr`構造体を扱う際に、より正確な情報を得ることができ、誤った使い方を防ぐことができます。結果として、コードの可読性が向上し、将来的な機能追加やバグ修正が容易になるという大きなメリットがあります。特に、異なるCPUアーキテクチャやオペレーティングシステムへの対応（ポータビリティ）を考慮する上で、このような明確な内部表現は不可欠です。

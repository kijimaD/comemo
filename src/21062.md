# [インデックス 21062] ファイルの概要

このコミットは、GoランタイムのC言語からGo言語への移行プロセスの一環として、アセンブリコードの変換と改善に焦点を当てています。特に、アセンブリファイルにおけるインクルードパスの変更、スタックガード定数の命名規則の調整、`getg`関数のC言語からアセンブリへの移行、そしてアトミック操作のGoラッパーによるエスケープ解析の改善が主な内容です。

## 元コミット内容

このコミットの元の内容は、GoランタイムのアセンブリファイルをC言語からGo言語への移行に合わせて変換することです。具体的には以下の変更が含まれます。

1.  `#include "zasm_GOOS_GOARCH.h"` が `#include "go_asm.h"` および/または `#include "go_tls.h"` に変更されました。
2.  C言語の`StackGuard`がGo言語の`_StackGuard`になったことに伴い、アセンブリでの名前が `const_StackGuard` から `const__StackGuard` に変更されました。
3.  `asm_$GOARCH.s` ファイルに、以前C言語で実装されていた `getg` 関数が追加されました。
4.  名前が変更されたアトミック操作にはGoラッパーが追加され、エスケープ解析のアノテーションが正しく行われるようになりました。

## 変更の背景

このコミットは、2014年から2015年にかけて行われたGoランタイムのC言語からGo言語への大規模な書き換え（Go 1.5で完了）の一環です。この移行の主な動機は、Go言語での開発をより楽しくし、Goの専門知識をGoツール構築に活用することでした。

Goの初期バージョンでは、ランタイムの多くの部分がC言語とアセンブリで書かれていました。しかし、Go言語自体が成熟するにつれて、ランタイムをGo言語で記述することで、開発の効率性、保守性、そしてGo言語の持つ並行処理やメモリ管理の利点を最大限に引き出すことが可能になります。

このコミットは、特にアセンブリコードの側面からこの移行をサポートしています。C言語のヘッダーファイルへの依存を減らし、Goランタイムの内部構造をより直接的に反映する新しいヘッダーファイル（`go_asm.h`、`go_tls.h`）を使用することで、アセンブリコードとGoコード間の連携を強化し、ランタイム全体の整合性を高めることを目指しています。また、`getg`関数のアセンブリへの移行やアトミック操作のGoラッパーの導入は、パフォーマンスの最適化とエスケープ解析の精度向上に貢献します。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する知識が役立ちます。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのコンポーネント群です。スケジューラ、ガベージコレクタ、メモリ管理、ゴルーチン管理などが含まれます。Goランタイムは、Goプログラムが効率的かつ安全に動作するための基盤を提供します。
*   **アセンブリ言語 (Assembly Language)**: 特定のCPUアーキテクチャに特化した低レベルのプログラミング言語です。Goランタイムでは、パフォーマンスが非常に重要であったり、ハードウェアに直接アクセスする必要がある部分（例: コンテキストスイッチ、システムコール、アトミック操作）でアセンブリ言語が使用されます。
*   **ゴルーチン (Goroutine)**: Go言語の軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。GoランタイムのスケジューラがゴルーチンをOSスレッドにマッピングし、実行を管理します。
*   **`g` 構造体 (Goroutine Structure)**: 各ゴルーチンは、その状態、スタック、関連するマシン（`m`）およびプロセッサ（`p`）コンテキストに関する重要な情報を含む `g` 構造体を持っています。ランタイムは `g` 構造体を通じてゴルーチンを管理します。
*   **スレッドローカルストレージ (Thread Local Storage, TLS)**: 各スレッドが独自のデータコピーを持つことができるメモリ領域です。Goランタイムでは、現在のゴルーチン（`g`）へのポインタを効率的に取得するためにTLSが利用されることがあります。
*   **スタックガード (StackGuard)**: Goランタイムにおけるスタックオーバーフロー検出と動的なスタック拡張のための重要なメカニズムです。各ゴルーチンには `g->stackguard` フィールドがあり、これはスタックの底部から一定の距離に設定されます。関数呼び出しの前に、コンパイラは現在のスタックポインタがこの `stackguard` 値を下回っていないかチェックします。下回っている場合、スタックオーバーフローを防ぐために `morestack` 関数が呼び出され、より大きなスタックセグメントが割り当てられます。
*   **アトミック操作 (Atomic Operations)**: 複数のゴルーチン間で共有される変数を安全に操作するための低レベルで不可分な（中断されない）操作です。ミューテックスのようなロック機構を使用せずにデータ競合を防ぎ、パフォーマンスを向上させます。`sync/atomic` パッケージで提供されます。
*   **エスケープ解析 (Escape Analysis)**: Goコンパイラが行うコンパイル時の最適化です。変数がスタックに安全に割り当てられるか、それともヒープに「エスケープ」する必要があるかを決定します。スタック割り当ては高速でガベージコレクタの負担を軽減しますが、変数の寿命が関数スコープを超える場合（例: ポインタが返される、グローバル変数に格納されるなど）はヒープにエスケープします。アトミック操作でアクセスされる共有データは、通常ヒープにエスケープします。

## 技術的詳細

このコミットは、GoランタイムのC言語からGo言語への移行という大きな目標の下、アセンブリコードレベルでの複数の技術的変更を導入しています。

1.  **ヘッダーファイルの抽象化と標準化**:
    *   以前は、特定のOSとアーキテクチャに特化した `#include "zasm_GOOS_GOARCH.h"` のようなヘッダーファイルが使用されていました。これは、C言語のプリプロセッサとビルドシステムに強く依存していました。
    *   このコミットでは、これをより汎用的な `#include "go_asm.h"` および `#include "go_tls.h"` に置き換えています。
        *   `go_asm.h`: Goのビルドプロセスによって自動生成されるヘッダーファイルで、Goの型や定数のメモリレイアウトに関するシンボリック定数（構造体のフィールドオフセット、サイズなど）をアセンブリコードに提供します。これにより、アセンブリコードはGoの内部構造の変更に対してより堅牢になり、可読性も向上します。
        *   `go_tls.h`: スレッドローカルストレージ（TLS）へのアクセス、特に現在のゴルーチン（`g`）へのポインタを取得するための `get_tls` マクロを定義します。これはOSとアーキテクチャに依存しますが、アセンブリコードが `g` ポインタを効率的に取得するための標準的なインターフェースを提供します。
    *   この変更は、Goランタイムのビルドシステムとアセンブリコードの間の結合を緩め、C言語のビルドツールへの依存を減らすことを目的としています。

2.  **`StackGuard` 定数の命名変更**:
    *   `const_StackGuard` から `const__StackGuard` への変更は、C言語の命名規則からGo言語の命名規則への移行を示唆しています。Goでは、エクスポートされない識別子（パッケージ外からアクセスできないもの）は小文字で始まりますが、内部的なアセンブリ定数などでは、C言語との区別や特定の目的のためにアンダースコアが追加されることがあります。この変更は、Goランタイムの内部でC言語とGo言語のコードが混在する状況において、命名の一貫性と明確性を高めるためのものです。

3.  **`getg` 関数のアセンブリへの移行**:
    *   `getg` 関数は、現在のゴルーチン（`g`）構造体へのポインタを返すGoランタイムの非常に重要な関数です。以前はC言語で実装されていましたが、このコミットで各アーキテクチャのアセンブリファイル（`asm_$GOARCH.s`）に直接実装されるようになりました。
    *   `getg` は頻繁に呼び出されるため、そのパフォーマンスはGoプログラム全体の効率に大きく影響します。アセンブリで直接実装することで、C言語の関数呼び出しオーバーヘッドを排除し、TLSからの `g` ポインタの取得を最も効率的な機械語命令で行うことができます。
    *   現代のGoコンパイラでは、`getg()` はコンパイラの組み込み関数（intrinsic）として扱われ、コンパイラが直接最適な機械語命令を生成するため、関数呼び出しのオーバーヘッドなしに `g` ポインタを取得できます。このコミットは、その最適化の基盤を築く一歩と言えます。

4.  **アトミック操作とエスケープ解析の改善**:
    *   コミットメッセージには「The renamed atomics now have Go wrappers, to get escape analysis annotations right.」とあります。これは、アトミック操作に関連する関数がGo言語のラッパーを持つようになり、それによってコンパイラのエスケープ解析がより正確に行われるようになったことを意味します。
    *   アトミック操作は共有データに対して行われるため、通常、そのデータはヒープにエスケープする必要があります。Goラッパーが導入されることで、コンパイラはアトミック操作が関わる変数のライフタイムと共有の性質をより正確に推論できるようになります。これにより、不必要なヒープ割り当てを減らしたり、必要なヒープ割り当てが正しく行われることを保証したりして、ガベージコレクションの効率と全体的なパフォーマンスを向上させることができます。

これらの変更は、GoランタイムのC言語からの脱却を進め、Go言語の特性を最大限に活かした、より効率的で保守性の高いランタイムを構築するための重要なステップです。

## コアとなるコードの変更箇所

このコミットでは、主に`src/runtime/`ディレクトリ内の多くのアセンブリファイルが変更されています。

具体的な変更のパターンは以下の通りです。

1.  **ヘッダーファイルのインクルードパスの変更**:
    *   多くのファイルで、`#include "zasm_GOOS_GOARCH.h"` が削除され、代わりに `#include "go_asm.h"` および `#include "go_tls.h"` が追加されています。
    *   例: `src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/sys_linux_386.s` など、ほぼ全てのアセンブリファイル。

    ```diff
    --- a/src/runtime/asm_386.s
    +++ b/src/runtime/asm_386.s
    @@ -2,7 +2,8 @@
     // Use of this source code is governed by a BSD-style
     // license that can be found in the LICENSE file.

    -#include "zasm_GOOS_GOARCH.h"
    +#include "go_asm.h"
    +#include "go_tls.h"
     #include "funcdata.h"
     #include "textflag.h"
    ```

2.  **`StackGuard` 定数の命名変更**:
    *   `const_StackGuard` の参照が `const__StackGuard` に変更されています。
    *   例: `src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`

    ```diff
    --- a/src/runtime/asm_386.s
    +++ b/src/runtime/asm_386.s
    @@ -49,7 +50,7 @@ nocpuinfo:
     	// update stackguard after _cgo_init
     	MOVL	$runtime·g0(SB), CX
     	MOVL	(g_stack+stack_lo)(CX), AX
    -	ADDL	$const_StackGuard, AX
    +	ADDL	$const__StackGuard, AX
     	MOVL	AX, g_stackguard0(CX)
     	MOVL	AX, g_stackguard1(CX)
    ```

3.  **`getg` 関数の追加**:
    *   各アーキテクチャのアセンブリファイル（例: `src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s`）に `runtime·getg` 関数が追加されています。この関数はTLSから現在のゴルーチン（`g`）へのポインタを取得し、それを返します。

    ```diff
    --- a/src/runtime/asm_386.s
    +++ b/src/runtime/asm_386.s
    @@ -2290,3 +2291,10 @@ TEXT _cgo_topofstack(SB),NOSPLIT,$0
     TEXT runtime·goexit(SB),NOSPLIT,$0-0
     	BYTE	$0x90	// NOP
     	CALL	runtime·goexit1(SB)	// does not return
    +
    +TEXT runtime·getg(SB),NOSPLIT,$0-4
    +	get_tls(CX)
    +	MOVL	g(CX), AX
    +	MOVL	AX, ret+0(FP)
    +	RET
    ```

4.  **アトミック操作関数の命名変更**:
    *   `runtime·casp`, `runtime·xchgp`, `runtime·atomicstorep` といったアトミック操作に関連する関数が、`runtime·casp1`, `runtime·xchgp1`, `runtime·atomicstorep1` のように末尾に `1` が付加された名前に変更されています。これは、Goラッパーの導入に伴う内部的な名前の調整と考えられます。

    ```diff
    --- a/src/runtime/asm_386.s
    +++ b/src/runtime/asm_386.s
    @@ -502,7 +503,7 @@ cas64_fail:
     //		return 1;
     //	}else
     //		return 0;
    -TEXT runtime·casp(SB), NOSPLIT, $0-13
    +TEXT runtime·casp1(SB), NOSPLIT, $0-13
     	MOVL	ptr+0(FP), BX
     	MOVL	old+4(FP), AX
     	MOVL	new+8(FP), CX
    ```

## コアとなるコードの解説

このコミットのコアとなる変更は、GoランタイムのアセンブリコードがGo言語の内部構造とより密接に連携し、C言語への依存を減らすためのものです。

### ヘッダーファイルの変更

`#include "zasm_GOOS_GOARCH.h"` から `#include "go_asm.h"` と `#include "go_tls.h"` への変更は、Goのビルドシステムがアセンブリコードに必要な情報をよりGoらしい方法で提供するようになったことを示しています。

*   `go_asm.h` は、Goのコンパイラが生成するGoの型や定数に関するメタデータ（オフセットやサイズなど）をアセンブリコードに提供します。これにより、アセンブリコードはGoのデータ構造の内部レイアウトに直接アクセスできるようになります。例えば、`g` 構造体の特定のフィールドにアクセスするために、ハードコードされたオフセットではなく、`g_stack` のようなシンボリック定数を使用できるようになります。これは、Goの内部構造が変更された場合でも、アセンブリコードの変更を最小限に抑えるのに役立ちます。
*   `go_tls.h` は、`get_tls` マクロを提供します。このマクロは、各アーキテクチャとOSに特化した方法で、スレッドローカルストレージ（TLS）レジスタをロードします。TLSレジスタは通常、現在のゴルーチン（`g`）へのポインタを保持しています。これにより、アセンブリコードは現在のゴルーチンコンテキストに効率的にアクセスできます。

### `getg` 関数の実装

`runtime·getg` 関数の追加は、Goランタイムの重要な内部関数がC言語からアセンブリ言語に移行したことを意味します。

例えば、`src/runtime/asm_386.s` の `runtime·getg` の実装を見てみましょう。

```assembly
TEXT runtime·getg(SB),NOSPLIT,$0-4
	get_tls(CX)
	MOVL	g(CX), AX
	MOVL	AX, ret+0(FP)
	RET
```

1.  `get_tls(CX)`: `go_tls.h` で定義された `get_tls` マクロを呼び出し、現在のスレッドのTLSレジスタの内容を `CX` レジスタにロードします。このTLSレジスタは、現在のゴルーチン（`g`）構造体へのポインタを保持しています。
2.  `MOVL g(CX), AX`: `CX` レジスタが指すアドレス（`g` 構造体へのポインタ）から、`g` 構造体自体の内容を `AX` レジスタにロードします。ここで `g(CX)` は、`go_asm.h` で定義された `g` 構造体のオフセットを利用している可能性があります。
3.  `MOVL AX, ret+0(FP)`: `AX` レジスタに格納された `g` ポインタを、関数の戻り値としてスタックフレームの `ret+0(FP)` に格納します。
4.  `RET`: 関数から戻ります。

このアセンブリ実装は、C言語の関数呼び出しのオーバーヘッドなしに、現在のゴルーチンへのポインタを直接かつ高速に取得することを可能にします。これは、Goスケジューラやガベージコレクタなど、ランタイムの多くの部分で頻繁に必要とされる操作であるため、パフォーマンスにとって非常に重要です。

### `StackGuard` の命名変更

`const_StackGuard` から `const__StackGuard` への変更は、主に命名規則の統一と、C言語とGo言語のコードベースが混在する中での明確化を目的としています。機能的な変更というよりは、コードベースの整合性を高めるためのものです。

### アトミック操作の命名変更とGoラッパー

`runtime·casp` が `runtime·casp1` に変更されたように、アトミック操作に関連するアセンブリ関数がリネームされています。これは、Go言語でこれらのアトミック操作に対するラッパー関数が導入されたことを示唆しています。

Goラッパーの目的は、コンパイラがエスケープ解析をより正確に行えるようにすることです。例えば、`sync/atomic` パッケージの関数は、内部的にこれらの低レベルのアセンブリ関数を呼び出します。Goラッパーが存在することで、コンパイラはこれらの操作が共有メモリに対して行われることを認識し、関連する変数がヒープにエスケープする必要があることを正しく判断できます。これにより、ガベージコレクションの効率が向上し、不必要なヒープ割り当てが削減される可能性があります。

これらの変更は全体として、Goランタイムの内部構造をよりGo言語中心に再構築し、パフォーマンスと保守性を向上させるための基盤を強化しています。

# [インデックス 22110] ファイルの概要

このコミットでは、Go言語の標準ライブラリ`crypto/x509`パッケージ内のホスト名検証ロジックが更新されています。具体的には、`src/crypto/x509/verify.go`ファイルでワイルドカード証明書の検証ルールが変更され、`src/crypto/x509/x509_test.go`ファイルでそれに対応するテストケースが追加・修正されています。

## コミット

このコミットは、RFC 6125で規定されたワイルドカード証明書の新しいルールに準拠するために、Goの`crypto/x509`パッケージを更新するものです。これにより、ワイルドカードがパターン内の最も左のラベルでのみ許可されるようになります。これは主要なブラウザの挙動と一致させるための変更です。

## 変更の背景

この変更の背景には、TLS/SSL証明書におけるワイルドカードの取り扱いに関するセキュリティと標準化の進化があります。以前は、ワイルドカード（`*`）はドメイン名の任意の場所に配置できると解釈されることがありました。しかし、これはセキュリティ上のリスク（例えば、`*.example.com`が`sub.domain.example.com`にマッチしてしまうなど、意図しないマッチング）や、実装間の不整合を引き起こす可能性がありました。

RFC 6125は、このような問題を解決するために、ワイルドカード証明書の検証に関する明確なガイドラインを導入しました。特に、セクション6.4.3では、ワイルドカードはパターン内の最も左のラベル（例: `*.example.com`）でのみ許可されるべきであると明記されています。これは、主要なウェブブラウザ（Chrome, Firefoxなど）が既に採用していた挙動と一致させるためのものであり、相互運用性とセキュリティの向上を目的としています。

Goの`crypto/x509`パッケージは、TLS/SSL証明書の検証を行う上で重要な役割を担っています。このパッケージがRFCの最新の推奨事項と主要ブラウザの挙動に準拠することは、Goアプリケーションのセキュリティと信頼性を確保するために不可欠でした。このコミットは、その準拠を実現するためのものです。

## 前提知識の解説

*   **X.509証明書**: 公開鍵暗号基盤（PKI）で使用されるデジタル証明書の標準フォーマットです。ウェブサイトのTLS/SSL通信において、サーバーの身元を証明するために広く利用されています。証明書には、証明書が発行されたドメイン名（Common NameやSubject Alternative Name (SAN)）が含まれています。
*   **ワイルドカード証明書**: 複数のサブドメインに対して有効な単一の証明書です。例えば、`*.example.com`というワイルドカード証明書は、`www.example.com`、`blog.example.com`、`mail.example.com`など、`example.com`のすべてのサブドメインに対して有効です。ワイルドカードは通常、ドメイン名の最も左のラベルに配置されます。
*   **ホスト名検証**: クライアント（ブラウザやアプリケーション）がサーバーから受け取ったX.509証明書に記載されているドメイン名が、実際に接続しようとしているホスト名と一致するかどうかを確認するプロセスです。これは、中間者攻撃（Man-in-the-Middle attack）を防ぐために非常に重要です。
*   **RFC 6125**: "Representation and Verification of Domain-Based Application Service Identity in the Internet Public Key Infrastructure"（インターネット公開鍵基盤におけるドメインベースのアプリケーションサービス識別の表現と検証）というタイトルのRFC（Request for Comments）です。このRFCは、TLS/SSLなどのプロトコルにおいて、ドメイン名に基づいてアプリケーションサービスの身元を検証するための詳細なルールを定めています。特に、ワイルドカード証明書の取り扱いに関する厳格なルールが導入されました。このRFCは後にRFC 9525によって廃止されましたが、このコミットが作成された時点では最新の標準でした。
*   **ドメイン名のラベル**: ドメイン名はピリオド（`.`）で区切られた複数の「ラベル」で構成されます。例えば、`www.example.com`では、`www`、`example`、`com`がそれぞれラベルです。最も左のラベルは通常、ホスト名の一部を表します。

## 技術的詳細

このコミットの技術的な核心は、`src/crypto/x509/verify.go`内の`matchHostnames`関数におけるワイルドカードの処理ロジックの変更です。

変更前は、`matchHostnames`関数は、パターン内の任意の場所にあるワイルドカード（`*`）を許可していました。これは、`patternPart == "*"`という単純な条件でワイルドカードを検出していました。

変更後は、この条件に`i == 0`という制約が追加されました。`i`はドメイン名のラベルのインデックスを表し、`0`は最も左のラベルを意味します。これにより、ワイルドカードがパターン内の最初のラベル（例: `*.example.com`の`*`）である場合にのみ、ワイルドカードとして扱われるようになります。それ以外の場所（例: `sub.*.example.com`や`foo*bar.example.com`）にある`*`は、リテラルなアスタリスクとして扱われ、ワイルドカードとしての特殊な意味を持たなくなります。

この変更は、RFC 6125のセクション6.4.3で規定されている「ワイルドカードは最も左のラベルでのみ許可されるべきである」という要件を直接的に実装したものです。

また、`src/crypto/x509/x509_test.go`では、この新しいワイルドカードの挙動を検証するためのテストケースが追加・修正されています。特に、`*.*.example.com`や`*.www.*.com`のような、ワイルドカードが最も左のラベル以外にも含まれるパターンが、以前はマッチしていたものが、変更後はマッチしないようにテストが更新されています。これにより、実装がRFCの新しいルールに正しく準拠していることが保証されます。

## コアとなるコードの解説

上記のコードスニペットは、`src/crypto/x509/verify.go`ファイル内の`matchHostnames`関数の一部です。この関数は、証明書のパターン（`pattern`）と実際のホスト名（`host`）が一致するかどうかを検証します。

変更前のコードでは、`for i, patternPart := range patternParts`ループ内で、`patternPart == "*"`という条件がありました。これは、`patternParts`（ドメイン名をピリオドで分割した各ラベル）のいずれかの部分がアスタリスク（`*`）であれば、それをワイルドカードとして扱い、その部分の比較をスキップするという意味でした。これにより、`*.example.com`だけでなく、`sub.*.example.com`のようなパターンもワイルドカードとして機能する可能性がありました。

変更後のコードでは、この条件が`i == 0 && patternPart == "*"`に修正されています。
*   `i == 0`: これは、現在の`patternPart`がドメイン名の最も左のラベル（例: `www.example.com`における`www`）であるかどうかをチェックします。
*   `patternPart == "*"`: これは、そのラベルがアスタリスク（`*`）であるかどうかをチェックします。

この二つの条件がAND（`&&`）で結合されているため、ワイルドカード（`*`）は、それがドメイン名の最も左のラベルである場合にのみ、ワイルドカードとして認識され、その部分の比較がスキップされます。それ以外の位置にあるアスタリスクは、単なるリテラル文字として扱われ、ホスト名の対応するラベルと完全に一致しない限りマッチしません。

このシンプルな変更により、GoのX.509証明書検証ロジックは、RFC 6125の厳格なワイルドカードルールに準拠するようになりました。

# [インデックス 26780] ファイルの概要

このコミットは、GoプロジェクトのGitHubリポジトリにIssueテンプレートとPull Requestテンプレートを追加するものです。これにより、ユーザーやコントリビューターが問題報告やコード変更を提案する際のプロセスが標準化され、より効率的かつ質の高い情報提供が促されます。特に、Goプロジェクトのような大規模なオープンソースプロジェクトでは、貢献のガイドラインを明確にすることが重要であり、これらのテンプレートはその一環として導入されました。

## 変更の背景

オープンソースプロジェクト、特にGoのような大規模で活発なプロジェクトでは、多くのユーザーや開発者からのIssue報告やPull Request（PR）が寄せられます。これらの貢献を効率的に管理し、プロジェクトの品質を維持するためには、一貫性のある情報収集が不可欠です。

このコミットの背景には、以下の課題と目的があります。

1.  **情報不足のIssue報告**: ユーザーからのIssue報告が不完全であると、問題を再現したり、原因を特定したりするのに時間がかかります。必要な情報（Goのバージョン、OS、再現手順など）を事前に求めることで、トリアージと解決のプロセスを加速できます。
2.  **不適切なPull Request**: Goプロジェクトには独自の貢献ワークフロー（例: `go-review.googlesource.com` を介したレビュープロセス）があり、GitHubのPR機能は直接的なコード貢献には使用されません。この点を明確にすることで、コントリビューターが正しい手順を踏むように誘導し、無駄なPRの作成を防ぐことができます。
3.  **貢献プロセスの標準化**: テンプレートを導入することで、すべての貢献者が同じ形式で情報を提供するようになり、プロジェクトメンテナの負担を軽減し、コミュニケーションの効率を向上させます。
4.  **ユーザーエクスペリエンスの向上**: 貢献したいと考えるユーザーにとって、どのように情報を提供すれば良いか明確なガイドラインがあることは、貢献へのハードルを下げ、より多くの人々がプロジェクトに参加しやすくなります。

この変更は、Issue #14365 に対応するものであり、Goプロジェクトの貢献エコシステムを改善するための重要なステップでした。

## 前提知識の解説

### GitHub Issueテンプレート

GitHubのIssueテンプレートは、リポジトリの `.github/ISSUE_TEMPLATE.md` (または `.github/ISSUE_TEMPLATE/` ディレクトリ内の複数の `.md` ファイル) に配置されるMarkdownファイルです。ユーザーが新しいIssueを作成しようとすると、このテンプレートの内容が自動的にIssueの本文に表示されます。これにより、プロジェクトメンテナが問題解決に必要な特定の情報をユーザーに促すことができます。

一般的なIssueテンプレートには、以下のような項目が含まれます。

*   **再現手順**: 問題を再現するための具体的なステップ。
*   **期待される動作**: 問題が発生しない場合にどうなるべきか。
*   **実際の動作**: 実際に何が起こったか。
*   **環境情報**: 使用しているソフトウェアのバージョン、OS、ハードウェア情報など。
*   **スクリーンショットやログ**: 問題を理解するのに役立つ追加情報。

### GitHub Pull Requestテンプレート

GitHubのPull Requestテンプレートは、リポジトリの `.github/PULL_REQUEST_TEMPLATE.md` (または `.github/PULL_REQUEST_TEMPLATE/` ディレクトリ内の複数の `.md` ファイル) に配置されるMarkdownファイルです。開発者が新しいPull Requestを作成しようとすると、このテンプレートの内容がPRの本文に自動的に表示されます。これにより、PRの目的、変更内容、テスト方法など、レビューに必要な情報をコントリビューターに提供させることができます。

Goプロジェクトの場合、GitHubのPRは直接的なコード貢献には使用されず、代わりに Gerrit をベースとした `go-review.googlesource.com` が使われます。そのため、PRテンプレートは、このGo特有の貢献ワークフローをコントリビューターに案内する役割を果たします。

### Goプロジェクトの貢献ワークフロー

Goプロジェクトは、一般的なGitHubのフォーク＆プルリクエストモデルとは異なる、独自の貢献ワークフローを採用しています。主な特徴は以下の通りです。

*   **Gerritの使用**: コードレビューと変更の提出には、Gerritというコードレビューシステムが使用されます。コントリビューターは `git push` の代わりに `git-review` コマンドなどを使用して変更をGerritにアップロードします。
*   **Contributor License Agreement (CLA)**: 貢献者は、コードを提出する前にGoogleのCLAに署名する必要があります。
*   **`golang.org/doc/contribute.html`**: 公式の貢献ガイドラインが詳細に記述されており、すべての貢献者はこれを参照することが求められます。

このコミットで追加されたPRテンプレートは、このGo特有のワークフローをGitHubのユーザーに伝えるための重要なゲートウェイとなります。

## 技術的詳細

このコミットでは、Goリポジトリのルートディレクトリに `.github` ディレクトリが作成され、その中に以下の2つのファイルが追加されました。

1.  `.github/ISSUE_TEMPLATE`
2.  `.github/PULL_REQUEST_TEMPLATE`

これらのファイルは、GitHubが提供する特別な機能を利用するためのもので、リポジトリの所有者がIssueやPull Requestの作成時に表示されるデフォルトのテキストを定義することを可能にします。

### `.github/ISSUE_TEMPLATE` の内容

このファイルは、Issue報告者が提供すべき情報の構造を定義しています。具体的には、以下の質問に答えるように促しています。

*   **1. What version of Go are you using (`go version`)?**: 使用しているGoのバージョンを明確にすることで、特定のバージョンに起因するバグか、一般的な問題かを切り分けるのに役立ちます。
*   **2. What operating system and processor architecture are you using (`go env`)?**: 実行環境の情報は、OSやアーキテクチャ固有の問題を診断するために不可欠です。
*   **3. What did you do?**: 問題を再現するための具体的な手順を記述するよう求めます。`play.golang.org` を使用した実行可能な例の提供を推奨しています。これは、問題を迅速に理解し、再現するための最も効果的な方法です。
*   **4. What did you expect to see?**: 期待される動作を明確にすることで、報告者が何を問題と認識しているかを理解できます。
*   **5. What did you see instead?**: 実際に発生した動作を記述することで、期待される動作との差異を明確にし、問題の具体的な症状を把握できます。

これらの質問は、Issue報告者が網羅的かつ構造化された情報を提供することを保証し、メンテナが問題を効率的に診断・解決できるように設計されています。

### `.github/PULL_REQUEST_TEMPLATE` の内容

このファイルは、GoプロジェクトへのPull Requestに関する重要なガイドラインを提供します。

*   **Please do not send pull requests to the golang/* repositories.**：`golang/*` リポジトリへのPull Requestは直接送らないでください、という明確な指示。これは、GoプロジェクトがGitHubのPRを直接的なコード貢献の主要な手段として使用していないことを示しています。
*   **We do, however, take contributions gladly.**：しかし、貢献は喜んで受け入れます、という肯定的なメッセージ。これは、貢献を歓迎する姿勢を示しつつ、正しい方法を促すためのものです。
*   **See https://golang.org/doc/contribute.html**：Goプロジェクトへの貢献方法に関する公式ドキュメントへのリンク。これにより、コントリビューターは正しいワークフローとガイドラインを学ぶことができます。
*   **Thanks!**：感謝の言葉で締めくくられています。

このテンプレートは、Goプロジェクトの貢献ワークフローに関する誤解を防ぎ、コントリビューターを公式の貢献ガイドラインに誘導することを目的としています。

## コアとなるコードの解説

### `.github/ISSUE_TEMPLATE`

このファイルは、Issue報告者が問題を効果的に報告するために必要な情報を体系的に収集するための質問リストを提供します。各質問は、Goのバグ報告や機能リクエストにおいて特に重要な情報に焦点を当てています。

*   `1. What version of Go are you using (\`go version\`?`): Goのバージョンは、特定のバグがどのリリースで導入されたか、または修正されたかを特定するために不可欠です。`go version` コマンドの実行を促すことで、正確な情報が得られます。
*   `2. What operating system and processor architecture are you using (\`go env\`?`): OSとアーキテクチャは、環境固有の問題（例: 特定のOSでのみ発生するバグ、特定のCPUアーキテクチャでのパフォーマンス問題）を診断するために重要です。`go env` コマンドは、これらの詳細な環境情報を提供します。
*   `3. What did you do?`: 問題を再現するためのステップバイステップの指示を求めます。これは、メンテナが報告された問題を検証し、デバッグするために最も重要な情報です。`play.golang.org` の利用を推奨することで、最小限の再現可能なコード例（Minimal Reproducible Example, MRE）の提供を促し、コミュニケーションのオーバーヘッドを削減します。
*   `4. What did you expect to see?`: 期待される動作を明確にすることで、報告者の意図とシステムの動作の間のギャップを特定できます。
*   `5. What did you see instead?`: 実際に観察された動作を記述することで、問題の具体的な症状とエラーメッセージなどを把握できます。

これらの質問は、Issue報告の質を向上させ、メンテナが迅速かつ効率的に対応できるようにするためのベストプラクティスに基づいています。

### `.github/PULL_REQUEST_TEMPLATE`

このファイルは、Goプロジェクトの貢献モデルに関する重要な注意喚起とガイドラインを提供します。

*   `Please do not send pull requests to the golang/* repositories.`: これは、GoプロジェクトがGitHubのPull Request機能を、コードの直接的な変更を提案する主要なメカニズムとして使用していないことを明確に伝えています。Goプロジェクトは、Gerritを介したレビュープロセスを採用しているため、GitHubのPRは通常、コード変更の提出には使用されません。
*   `We do, however, take contributions gladly.`: この文は、前の警告が貢献を拒否するものではなく、単に正しいプロセスに従うことを求めているだけであることを明確にしています。Goプロジェクトはオープンソースであり、コミュニティからの貢献を積極的に受け入れています。
*   `See https://golang.org/doc/contribute.html`: これは、Goプロジェクトへの貢献に関する公式ドキュメントへの直接リンクです。このドキュメントには、CLAへの署名、Gerritの使用方法、コードスタイルガイドラインなど、貢献に必要なすべての情報が含まれています。このリンクを提供することで、コントリビューターは正しい手順を簡単に参照できます。
*   `Thanks!`: 丁寧な締めくくりは、プロジェクトの友好的な姿勢を示しています。

このPRテンプレートは、GitHubのPR機能の一般的な使用法とGoプロジェクトの特定の貢献ワークフローとの間のギャップを埋めるために設計されており、コントリビューターが正しいチャネルを通じて貢献できるように誘導します。

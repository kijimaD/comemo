## 元コミット内容

`cmd/link: add -extar option to set ar program for c-archive`

このコミットは、Goリンカ (`cmd/link`) に `-extar` オプションを追加し、`c-archive` ビルドモードで使用する `ar` プログラム（アーカイバ）を指定できるようにします。これは、通常とは異なるクロスコンパイル環境で `c-archive` を使用したいユーザーにとって必要となる機能です。同様の機能は環境変数でも実現可能ですが、既存の `-extld` オプション（外部リンカを指定するオプション）との類似性から `-extar` というオプション名が採用されました。

## 変更の背景

Go言語は、その強力なクロスコンパイル機能で知られています。`go build` コマンドは、`GOOS` (ターゲットOS) や `GOARCH` (ターゲットアーキテクチャ) といった環境変数を設定することで、異なるプラットフォーム向けのバイナリを簡単に生成できます。

しかし、GoプログラムをC言語のライブラリとしてビルドする `buildmode=c-archive` のような特殊なビルドモードを使用する場合、Goツールチェインは最終的なアーカイブファイル (`.a` ファイル) を作成するために、システムの `ar` コマンド（アーカイバ）に依存します。

通常の開発環境では、デフォルトの `ar` コマンドで問題ありませんが、特定のクロスコンパイル環境、特に組み込みシステムや特殊なツールチェインを使用する環境では、デフォルトの `ar` コマンドがターゲットアーキテクチャに対応していなかったり、特定のバージョンやパスの `ar` を使用する必要がある場合があります。

このコミットの背景には、このような「通常とは異なるクロスコンパイルセットアップ」において、ユーザーがGoツールチェインが使用する `ar` プログラムを明示的に制御したいというニーズがありました。既存の `-extld` オプションが外部リンカを指定するのと同様に、外部アーカイバを指定するメカニズムが求められていたのです。これにより、Goのクロスコンパイルの柔軟性がさらに高まり、より多様な開発環境に対応できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **Go言語のビルドモード (`-buildmode`)**:
    `go build` コマンドには、様々なビルドモードを指定できる `-buildmode` オプションがあります。
    *   **`exe` (デフォルト)**: 実行可能ファイルをビルドします。
    *   **`archive`**: Goパッケージをアーカイブファイル (`.a` ファイル) としてビルドします。これは他のGoプログラムからリンクされることを意図しています。
    *   **`c-archive`**: GoパッケージをC言語の静的ライブラリとしてビルドします。これにより、C/C++プログラムからGoの関数を呼び出すことができるようになります。生成されるのは `.a` ファイルと対応するヘッダファイル (`.h`) です。
    *   **`c-shared`**: GoパッケージをC言語の共有ライブラリとしてビルドします。これにより、C/C++プログラムからGoの関数を動的に呼び出すことができるようになります。生成されるのは `.so` (Linux) や `.dylib` (macOS) ファイルと対応するヘッダファイル (`.h`) です。
    *   **`shared`**: 複数のGoプログラムで共有可能なGo共有ライブラリをビルドします。
    *   **`plugin`**: Goプラグインをビルドします。

    このコミットは特に `c-archive` モードに関連しています。

2.  **`ar` コマンド (アーカイバ)**:
    `ar` は "archiver" の略で、Unix系システムで複数のファイルを1つのアーカイブファイル（通常は `.a` 拡張子を持つ静的ライブラリ）にまとめるために使用されるコマンドラインユーティリティです。C/C++のビルドプロセスでは、コンパイルされたオブジェクトファイル (`.o` ファイル) を集めて静的ライブラリを作成する際によく使われます。Goの `c-archive` ビルドモードも、最終的な静的ライブラリを生成するためにこの `ar` コマンドを利用します。

3.  **クロスコンパイル**:
    クロスコンパイルとは、あるプラットフォーム (ホスト) 上で、別のプラットフォーム (ターゲット) 向けの実行可能ファイルやライブラリをビルドすることです。例えば、macOS上でLinux ARM向けのバイナリをビルドするようなケースです。Goは `GOOS` と `GOARCH` 環境変数を設定するだけで簡単にクロスコンパイルできるため、組み込み開発やモバイル開発などで広く利用されています。

4.  **`cmd/link` (Goリンカ)**:
    `cmd/link` はGoツールチェインの一部であり、Goコンパイラによって生成されたオブジェクトファイル (`.o` ファイル) を結合して、最終的な実行可能ファイルやライブラリを生成する役割を担います。外部のC/C++コードとリンクする場合や、`c-archive` のような特殊なビルドモードを使用する場合には、外部のリンカやアーカイバと連携することもあります。

5.  **`-extld` オプション**:
    Goリンカには既に `-extld` オプションが存在します。これは、GoプログラムがCgo (GoとCの相互運用機能) を使用している場合や、特定のビルドモード (例: `c-archive`, `c-shared`) で外部のCリンカ (通常は `gcc` や `clang`) を使用する必要がある場合に、どの外部リンカを使用するかを指定するためのものです。このコミットの `-extar` は、この `-extld` と同様の目的で、外部アーカイバを指定するために導入されました。

## 技術的詳細

このコミットの技術的な核心は、Goリンカ (`cmd/link`) が `c-archive` ビルドモードで静的ライブラリを生成する際に使用する `ar` プログラムを、ユーザーがコマンドラインオプションで指定できるようにした点にあります。

以前は、Goリンカは内部的に `ar` コマンドを呼び出す際に、システムパスから見つかるデフォルトの `ar` を使用するか、あるいは特定の環境変数に依存していました。しかし、クロスコンパイル環境では、ホストシステムの `ar` がターゲットアーキテクチャのオブジェクトファイルを正しく扱えない場合や、特定のクロスコンパイルツールチェインが提供する `ar` を明示的に使用する必要がある場合があります。

新しい `-extar` オプションは、この問題を解決します。

1.  **オプションの追加**: `src/cmd/link/internal/ld/pobj.go` に `extar` という新しいフラグ変数が追加され、コマンドラインから `-extar` オプションを受け取れるようになります。
2.  **デフォルト値の設定**: `src/cmd/link/internal/ld/lib.go` 内の `archive()` 関数で、`extar` が指定されていない場合、デフォルトで `"ar"` が使用されるように設定されます。これにより、オプションが指定されない場合の既存の動作が維持されます。
3.  **`ar` コマンドの呼び出しの変更**: `archive()` 関数内で、実際に `ar` コマンドを呼び出す部分が、ハードコードされた `"ar"` から、`extar` 変数の値を使用するように変更されます。これにより、ユーザーが指定した `ar` プログラムが実行されるようになります。
4.  **ドキュメントの更新**: `src/cmd/link/doc.go` に `-extar` オプションの説明が追加され、その目的と使用法が明記されます。
5.  **テストケースの追加**: `misc/cgo/testcarchive/test.bash` に、`-extar` オプションが正しく機能するかどうかを検証する新しいテストケースが追加されます。このテストでは、カスタムの `testar` スクリプトを作成し、`-extar` でそれを指定することで、Goリンカが指定されたアーカイバを呼び出していることを確認します。

この変更により、Goの `c-archive` ビルドモードは、より多様なクロスコンパイルシナリオに対応できるようになり、開発者は特定のツールチェインの要件に合わせて `ar` プログラムを柔軟に選択できるようになります。これは、Goを組み込みシステムや特殊な環境で利用する際の障壁を低減する重要な改善です。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goリンカが外部の `ar` プログラムを呼び出すロジックにあります。

`src/cmd/link/internal/ld/lib.go` の `archive()` 関数は、`c-archive` ビルドモードで静的ライブラリを生成する際の主要な処理を担当します。この関数内で、GoのオブジェクトファイルとCgoによって生成されたオブジェクトファイルをまとめて `.a` ファイルにするために、外部の `ar` コマンドが呼び出されます。

変更前は、`ar` コマンドのパスは暗黙的にシステムの `PATH` 環境変数に依存していました。しかし、変更後は、`extar` という新しいグローバル変数が導入され、この変数の値が `ar` コマンドの実行ファイル名として使用されるようになります。

1.  **`extar` 変数の導入**: `var extar string` が追加され、コマンドラインで指定された `-extar` の値がここに格納されます。
2.  **デフォルト値の適用**: `if extar == "" { extar = "ar" }` の行は、ユーザーが `-extar` オプションを指定しなかった場合に、`extar` 変数にデフォルト値である `"ar"` を設定します。これにより、既存の動作が維持され、システムデフォルトの `ar` が使用されます。
3.  **`ar` コマンドの動的な呼び出し**: `argv := []string{extar, "-q", "-c", "-s", outfile}` の行が最も重要です。以前は `argv := []string{"ar", ...}` とハードコードされていましたが、`extar` 変数を使用するように変更されたことで、Goリンカはユーザーが `-extar` オプションで指定した任意の実行ファイルをアーカイバとして呼び出すことができるようになりました。

これにより、開発者はクロスコンパイル環境において、特定のツールチェインが提供する `ar` コマンドのパスを明示的に指定できるようになり、ビルドプロセスの柔軟性と制御性が大幅に向上します。例えば、`arm-none-eabi-ar` のようなクロスアーカイバを使用する必要がある場合に、`-ldflags="-extar=arm-none-eabi-ar"` のように指定できるようになります。

    *   **`c-archive`**: GoパッケージをC言語の静的ライブラリとしてビルドします。これにより、C/C++プログラムからGoの関数を呼び出すことができるようになります。生成されるのは `.a` ファイルと対応するヘッダファイル (`.h`) です。
    *   **`c-shared`**: GoパッケージをC言語の共有ライブラリとしてビルドします。これにより、C/C++プログラムからGoの関数を動的に呼び出すことができるようになります。生成されるのは `.so` (Linux) や `.dylib` (macOS) ファイルと対応するヘッダファイル (`.h`) です。
    *   **`shared`**: 複数のGoプログラムで共有可能なGo共有ライブラリをビルドします。
    *   **`plugin`**: Goプラグインをビルドします。

    このコミットは特に `c-archive` モードに関連しています。

2.  **`ar` コマンド (アーカイバ)**:
    `ar` は "archiver" の略で、Unix系システムで複数のファイルを1つのアーカイブファイル（通常は `.a` 拡張子を持つ静的ライブラリ）にまとめるために使用されるコマンドラインユーティリティです。C/C++のビルドプロセスでは、コンパイルされたオブジェクトファイル (`.o` ファイル) を集めて静的ライブラリを作成する際によく使われます。Goの `c-archive` ビルドモードも、最終的な静的ライブラリを生成するためにこの `ar` コマンドを利用します。

3.  **クロスコンパイル**:
    クロスコンパイルとは、あるプラットフォーム (ホスト) 上で、別のプラットフォーム (ターゲット) 向けの実行可能ファイルやライブラリをビルドすることです。例えば、macOS上でLinux ARM向けのバイナリをビルドするようなケースです。Goは `GOOS` と `GOARCH` 環境変数を設定するだけで簡単にクロスコンパイルできるため、組み込み開発やモバイル開発などで広く利用されています。

4.  **`cmd/link` (Goリンカ)**:
    `cmd/link` はGoツールチェインの一部であり、Goコンパイラによって生成されたオブジェクトファイル (`.o` ファイル) を結合して、最終的な実行可能ファイルやライブラリを生成する役割を担います。外部のC/C++コードとリンクする場合や、`c-archive` のような特殊なビルドモードを使用する場合には、外部のリンカやアーカイバと連携することもあります。

5.  **`-extld` オプション**:
    Goリンカには既に `-extld` オプションが存在します。これは、GoプログラムがCgo (GoとCの相互運用機能) を使用している場合や、特定のビルドモード (例: `c-archive`, `c-shared`) で外部のCリンカ (通常は `gcc` や `clang`) を使用する必要がある場合に、どの外部リンカを使用するかを指定するためのものです。このコミットの `-extar` は、この `-extld` と同様の目的で、外部アーカイバを指定するために導入されました。

## 技術的詳細

このコミットの技術的な核心は、Goリンカ (`cmd/link`) が `c-archive` ビルドモードで静的ライブラリを生成する際に使用する `ar` プログラムを、ユーザーがコマンドラインオプションで指定できるようにした点にあります。

以前は、Goリンカは内部的に `ar` コマンドを呼び出す際に、システムパスから見つかるデフォルトの `ar` を使用するか、あるいは特定の環境変数に依存していました。しかし、クロスコンパイル環境では、ホストシステムの `ar` がターゲットアーキテクチャのオブジェクトファイルを正しく扱えない場合や、特定のクロスコンパイルツールチェインが提供する `ar` を明示的に使用する必要がある場合があります。

新しい `-extar` オプションは、この問題を解決します。

1.  **オプションの追加**: `src/cmd/link/internal/ld/pobj.go` に `extar` という新しいフラグ変数が追加され、コマンドラインから `-extar` オプションを受け取れるようになります。
2.  **デフォルト値の設定**: `src/cmd/link/internal/ld/lib.go` 内の `archive()` 関数で、`extar` が指定されていない場合、デフォルトで `"ar"` が使用されるように設定されます。これにより、オプションが指定されない場合の既存の動作が維持されます。
3.  **`ar` コマンドの呼び出しの変更**: `archive()` 関数内で、実際に `ar` コマンドを呼び出す部分が、ハードコードされた `"ar"` から、`extar` 変数の値を使用するように変更されます。これにより、ユーザーが指定した `ar` プログラムが実行されるようになります。
4.  **ドキュメントの更新**: `src/cmd/link/doc.go` に `-extar` オプションの説明が追加され、その目的と使用法が明記されます。
5.  **テストケースの追加**: `misc/cgo/testcarchive/test.bash` に、`-extar` オプションが正しく機能するかどうかを検証する新しいテストケースが追加されます。このテストでは、カスタムの `testar` スクリプトを作成し、`-extar` でそれを指定することで、Goリンカが指定されたアーカイバを呼び出していることを確認します。

この変更により、Goの `c-archive` ビルドモードは、より多様なクロスコンパイルシナリオに対応できるようになり、開発者は特定のツールチェインの要件に合わせて `ar` プログラムを柔軟に選択できるようになります。これは、Goを組み込みシステムや特殊な環境で利用する際の障壁を低減する重要な改善です。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goリンカが外部の `ar` プログラムを呼び出すロジックにあります。

`src/cmd/link/internal/ld/lib.go` の `archive()` 関数は、`c-archive` ビルドモードで静的ライブラリを生成する際の主要な処理を担当します。この関数内で、GoのオブジェクトファイルとCgoによって生成されたオブジェクトファイルをまとめて `.a` ファイルにするために、外部の `ar` コマンドが呼び出されます。

変更前は、`ar` コマンドのパスは暗黙的にシステムの `PATH` 環境変数に依存していました。しかし、変更後は、`extar` という新しいグローバル変数が導入され、この変数の値が `ar` コマンドの実行ファイル名として使用されるようになります。

1.  **`extar` 変数の導入**: `var extar string` が追加され、コマンドラインで指定された `-extar` の値がここに格納されます。
2.  **デフォルト値の適用**: `if extar == "" { extar = "ar" }` の行は、ユーザーが `-extar` オプションを指定しなかった場合に、`extar` 変数にデフォルト値である `"ar"` を設定します。これにより、既存の動作が維持され、システムデフォルトの `ar` が使用されます。
3.  **`ar` コマンドの動的な呼び出し**: `argv := []string{extar, "-q", "-c", "-s", outfile}` の行が最も重要です。以前は `argv := []string{"ar", ...}` とハードコードされていましたが、`extar` 変数を使用するように変更されたことで、Goリンカはユーザーが `-extar` オプションで指定した任意の実行ファイルをアーカイバとして呼び出すことができるようになりました。

これにより、開発者はクロスコンパイル環境において、特定のツールチェインが提供する `ar` コマンドのパスを明示的に指定できるようになり、ビルドプロセスの柔軟性と制御性が大幅に向上します。例えば、`arm-none-eabi-ar` のようなクロスアーカイバを使用する必要がある場合に、`-ldflags="-extar=arm-none-eabi-ar"` のように指定できるようになります。

# [インデックス 23039] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の「ミューテータアシスト」メカニズムを、固定量から「比例的」なものへと変更するものです。これにより、ヒープの成長をより効果的に制御し、GCの効率を向上させることを目的としています。具体的には、ミューテータ（アプリケーションコード）がメモリを割り当てる速度に比例してGC作業を分担するようになり、GCがヒープの成長に追いつくための支援をより適切に行えるようになります。

## コミット

```
runtime: proportional mutator assist

Currently, mutator allocation periodically assists the garbage
collector by performing a small, fixed amount of scanning work.
However, to control heap growth, mutators need to perform scanning
work *proportional* to their allocation rate.

This change implements proportional mutually assists. This uses the
scan work estimate computed by the garbage collector at the beginning
of each cycle to compute how much scan work must be performed per
allocation byte to complete the estimated scan work by the time the
heap reaches the goal size. When allocation triggers an assist, it
uses this ratio and the amount allocated since the last assist to
compute the assist work, then attempts to steal as much of this work
as possible from the background collector's credit, and then performs
any remaining scan work itself.

Reviewed-on: https://go-review.googlesource.com/8836
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 元コミット内容

Goランタイムにおいて、ミューテータ（アプリケーションコード）によるメモリ割り当て時にガベージコレクタ（GC）を支援するメカニズムを、現在の固定量から比例的なものに変更します。

現状では、ミューテータのメモリ割り当ては定期的にGCを支援し、少量の固定されたスキャン作業を実行しています。しかし、ヒープの成長を制御するためには、ミューテータは自身の割り当て速度に「比例した」スキャン作業を実行する必要があります。

この変更は、比例的なミューテータアシストを実装します。これは、各GCサイクルの開始時にガベージコレクタによって計算されるスキャン作業の見積もりを使用して、ヒープが目標サイズに達するまでに推定されるスキャン作業を完了するために、割り当てバイトあたりどれだけのスキャン作業を実行する必要があるかを計算します。割り当てがアシストをトリガーすると、この比率と前回の支援以降に割り当てられた量を使用してアシスト作業を計算し、次にバックグラウンドコレクタのクレジットから可能な限り多くの作業を奪い取り、残りのスキャン作業を自身で実行します。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行と並行して動作する「並行GC」を採用しています。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。しかし、並行GCには課題があります。アプリケーション（ミューテータ）がメモリを高速に割り当て続けると、GCがその割り当て速度に追いつけなくなり、ヒープが際限なく成長してしまう可能性があります。

これを防ぐために、Goランタイムには「ミューテータアシスト」というメカニズムが導入されています。これは、ミューテータがメモリを割り当てる際に、GC作業の一部を分担させることで、GCの進行を助けるものです。このコミット以前は、このミューテータアシストは「固定量」の作業を行うものでした。つまり、ミューテータが一定量のメモリを割り当てるたびに、決まった量のGCスキャン作業を行うというものでした。

しかし、この固定量のアシストでは、ミューテータの割り当て速度が非常に速い場合、GCがヒープの成長に追いつくのに十分な支援が得られないという問題がありました。ヒープの成長を効果的に制御し、GCの効率を維持するためには、ミューテータが自身の割り当て速度に「比例して」GC作業を分担することが求められました。この「比例的ミューテータアシスト」の導入は、この課題を解決し、GCの安定性と効率を向上させるための重要な変更です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリ領域を自動的に解放し、再利用可能にするプロセスです。GoのGCは、並行（Concurrent）かつ非世代別（Non-generational）のマーク＆スイープ方式を採用しています。
*   **並行GC (Concurrent GC)**: GC作業の大部分をアプリケーションの実行と並行して行うGC方式です。これにより、GCによるアプリケーションの一時停止時間を短縮し、レイテンシを低減します。GoのGCは、主にマークフェーズを並行して実行します。
*   **ミューテータ (Mutator)**: メモリを割り当てたり、既存のメモリの内容を変更したりするアプリケーションコード（GoのGoroutine）を指します。ミューテータはヒープの状態を「変更（mutate）」するため、この名前が付けられています。
*   **ミューテータアシスト (Mutator Assist)**: 並行GCにおいて、ミューテータがメモリを割り当てる際に、GC作業の一部を分担して実行するメカニズムです。これは、GCがミューテータの割り当て速度に追いつくのを助け、ヒープの過度な成長を防ぐために重要です。ミューテータアシストは、GCのマークフェーズ中に特に重要となります。
*   **マークフェーズ (Mark Phase)**: GCの主要なフェーズの一つで、到達可能な（プログラムから参照されている）オブジェクトを特定し、マークするプロセスです。GoのGCでは、このフェーズの大部分が並行して実行されます。
*   **スキャン作業 (Scan Work)**: GCのマークフェーズにおいて、オブジェクトを走査し、そこから参照されている他のオブジェクトを特定する作業です。この作業を通じて、到達可能なオブジェクトのグラフが構築されます。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域です。Goプログラムが`make`や`new`などでメモリを確保すると、通常このヒープ領域に割り当てられます。
*   **`gcController`**: Goランタイム内部でGCの動作を制御する構造体です。GCの開始、終了、各種パラメータの計算などを行います。
*   **`g` (Goroutine)**: Goにおける軽量な実行スレッドです。各Goroutineは独自のスタックを持ち、独立して実行されます。

## 技術的詳細

このコミットの核となるのは、「比例的ミューテータアシスト」の導入です。これは、ミューテータがメモリを割り当てる際に、その割り当て量に比例したGCスキャン作業を分担させることで、ヒープの成長をより効果的に制御する仕組みです。

具体的なメカニズムは以下の通りです。

1.  **`assistRatio`の導入**: `gcControllerState`構造体に`assistRatio`という新しいフィールドが追加されました。これは、割り当てられたバイトあたりに実行すべきスキャン作業の比率を示す`float64`型の値です。
2.  **`startCycle`での`assistRatio`の計算**: 各GCサイクルの開始時（`gcControllerState.startCycle()`関数内）に、この`assistRatio`が計算されます。
    *   まず、前回のGCサイクルでマークされたバイト数（`memstats.heap_marked`）と`workRatioAvg`（スキャン作業比率の移動平均）から、今回のサイクルで予想されるスキャン作業量（`scanWorkExpected`）が計算されます。
    *   次に、ヒープの目標サイズ（`heapGoal`）が計算されます。これは、現在のマーク済みヒープサイズに`gcpercent`（GCのトリガーとなるヒープ使用率の閾値）を考慮して算出されます。
    *   `heapDistance`は、現在のライブヒープサイズから`heapGoal`までの距離を示します。この距離が小さすぎる場合や負になる場合（GC開始が遅れたり、大きな割り当てがあったりする場合）は、ゼロ除算や不適切な比率を防ぐために最小値（1MB）が設定されます。
    *   最終的に、`assistRatio`は `scanWorkExpected / heapDistance` として計算されます。これは、「ヒープが目標サイズに達するまでに、残りのヒープ距離を割り当てる間に、どれだけのスキャン作業を完了する必要があるか」という比率を表します。
3.  **`gcalloc`と`gcscanwork`の導入**: 各Goroutine（`g`構造体）に、`gcalloc`（現在のGCサイクル中に割り当てたバイト数）と`gcscanwork`（現在のGCサイクル中に実行または奪い取ったスキャン作業量）という新しいフィールドが追加されました。これらは、Goroutineごとの割り当てとGC作業の進捗を追跡するために使用されます。
4.  **`gcAssistAlloc`関数の導入**: `src/runtime/mgcmark.go`に`gcAssistAlloc`という新しい関数が追加されました。この関数は、ミューテータがメモリを割り当てるたびに呼び出されます。
    *   `gcAssistAlloc`は、まず現在のGoroutineの`gcalloc`に割り当てられたサイズを加算します。
    *   次に、`gcController.assistRatio`と`gp.gcalloc`（Goroutineが割り当てた総量）に基づいて、このGoroutineが実行すべきスキャン作業量（`scanWork`）を計算します。既に実行した`gp.gcscanwork`は差し引かれます。
    *   計算された`scanWork`が正の場合、まずバックグラウンドGCのクレジット（`gcController.bgScanCredit`）から可能な限り多くの作業を「奪い取ろう」とします。これは、バックグラウンドGCが既に実行した作業をミューテータが自分の貢献としてカウントできるため、実際のGC作業を減らすことができます。
    *   クレジットを奪い取った後も`scanWork`が残っている場合、ミューテータ自身が`gcDrainN`関数を呼び出してスキャン作業を実行します。この作業量は`gp.gcscanwork`に加算されます。
5.  **`mallocgc`の変更**: `src/runtime/malloc.go`の`mallocgc`関数（メモリ割り当てを行う主要な関数）が変更され、GCマークフェーズ中（`gcphase == _GCmark`）に`gchelpwork`の代わりに`gcAssistAlloc`を呼び出すようになりました。これにより、割り当て時に比例的なアシストがトリガーされます。

このメカニズムにより、ミューテータは自身の割り当て速度に応じてGC作業を分担するため、ヒープの成長が速いほどより多くのGC支援が行われるようになります。これにより、GCがヒープの成長に追いつきやすくなり、GCの一時停止時間を短縮し、全体的なパフォーマンスを向上させることが期待されます。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下のファイルに集中しています。

1.  **`src/runtime/malloc.go`**:
    *   `mallocgc`関数内で、GCマークフェーズ中に`gchelpwork()`の代わりに`gcAssistAlloc(size, shouldhelpgc)`が呼び出されるように変更されました。これにより、メモリ割り当て時に比例的なミューテータアシストがトリガーされるようになります。

2.  **`src/runtime/mgc.go`**:
    *   `gcControllerState`構造体に`assistRatio float64`フィールドが追加されました。
    *   `startCycle()`関数内で、`assistRatio`の計算ロジックが追加されました。これには、`scanWorkExpected`、`heapGoal`、`heapDistance`の計算が含まれます。
    *   `gc(mode int)`関数内で、マークフェーズ開始時に「mutator assists」が有効になる旨のコメントが追加されました。
    *   `gcResetGState()`関数内で、各Goroutineの`gcalloc`と`gcscanwork`が0にリセットされるようになりました。

3.  **`src/runtime/mgcmark.go`**:
    *   `gchelpwork()`関数が削除され、代わりに`gcAssistAlloc(size uintptr, allowAssist bool)`関数が新しく追加されました。
    *   `gcAssistAlloc`関数には、Goroutineごとの割り当て量（`gp.gcalloc`）の記録、必要なスキャン作業量（`scanWork`）の計算、バックグラウンドGCクレジットからの作業の奪い取り、そして残りのスキャン作業の実行ロジックが含まれています。

4.  **`src/runtime/runtime2.go`**:
    *   `g`構造体（Goroutineを表す構造体）に、`gcalloc uintptr`（現在のGCサイクル中に割り当てたバイト数）と`gcscanwork int64`（現在のGCサイクル中に実行または奪い取ったスキャン作業量）の2つのフィールドが追加されました。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

```go
type gcControllerState struct {
	// ... 既存のフィールド ...
	// assistRatio is the ratio of allocated bytes to scan work
	// that should be performed by mutator assists. This is
	// computed at the beginning of each cycle.
	assistRatio float64
}

func (c *gcControllerState) startCycle() {
	// ... 既存のロジック ...

	// Compute the expected work based on last cycle's marked bytes.
	scanWorkExpected := uint64(float64(memstats.heap_marked) * c.workRatioAvg)

	// Compute the mutator assist ratio so by the time the mutator
	// allocates the remaining heap bytes up to next_gc, it will
	// have done (or stolen) the estimated amount of scan work.
	heapGoal := memstats.heap_marked + memstats.heap_marked*uint64(gcpercent)/100
	heapDistance := int64(heapGoal) - int64(memstats.heap_live)
	if heapDistance <= 1024*1024 {
		// heapDistance can be negative if GC start is delayed
		// or if the allocation that pushed heap_live over
		// next_gc is large or if the trigger is really close
		// to GOGC. We don't want to set the assist negative
		// (or divide by zero, or set it really high), so
		// enforce a minimum on the distance.
		heapDistance = 1024 * 1024
	}
	c.assistRatio = float64(scanWorkExpected) / float64(heapDistance)
}
```
`gcControllerState`に`assistRatio`が追加され、`startCycle`でその値が計算されます。この`assistRatio`は、ミューテータがメモリを割り当てる際に、どれだけのGCスキャン作業を分担すべきかを決定するための重要な係数となります。`heapDistance`の最小値設定は、ゼロ除算や不適切な比率の計算を防ぐための堅牢性向上策です。

### `src/runtime/runtime2.go` の変更点

```go
type g struct {
	// ... 既存のフィールド ...

	// Per-G gcController state
	gcalloc    uintptr // bytes allocated during this GC cycle
	gcscanwork int64   // scan work done (or stolen) this GC cycle
}
```
各Goroutine（`g`）に`gcalloc`と`gcscanwork`が追加されました。これにより、Goroutineごとに現在のGCサイクルにおけるメモリ割り当て量と、GCスキャン作業の貢献度を追跡できるようになります。これは、比例的アシストの計算と適用に不可欠な情報です。

### `src/runtime/mgcmark.go` の変更点

```go
// gcAssistAlloc records and allocation of size bytes and, if
// allowAssist is true, may assist GC scanning in proportion to the
// allocations performed by this mutator since the last assist.
//
// It should only be called during gcphase == _GCmark.
//go:nowritebarrier
func gcAssistAlloc(size uintptr, allowAssist bool) {
	// Find the G responsible for this assist.
	gp := getg()
	if gp.m.curg != nil {
		gp = gp.m.curg
	}

	// Record allocation.
	gp.gcalloc += size

	if !allowAssist {
		return
	}

	// Compute the amount of assist scan work we need to do.
	scanWork := int64(gcController.assistRatio*float64(gp.gcalloc)) - gp.gcscanwork
	// scanWork can be negative if the last assist scanned a large
	// object and we're still ahead of our assist goal.
	if scanWork <= 0 {
		return
	}

	// Steal as much credit as we can from the background GC's
	// scan credit. This is racy and may drop the background
	// credit below 0 if two mutators steal at the same time. This
	// will just cause steals to fail until credit is accumulated
	// again, so in the long run it doesn't really matter, but we
	// do have to handle the negative credit case.
	bgScanCredit := atomicloadint64(&gcController.bgScanCredit)
	stolen := int64(0)
	if bgScanCredit > 0 {
		if bgScanCredit < scanWork {
			stolen = bgScanCredit
		} else {
			stolen = scanWork
		}
		xaddint64(&gcController.bgScanCredit, -scanWork)

		scanWork -= stolen
		gp.gcscanwork += stolen

		if scanWork == 0 {
			return
		}
	}

	// Perform assist work
	systemstack(func() {
		// drain own current wbuf first in the hopes that it
		// will be more cache friendly.
		var gcw gcWork
		gcw.initFromCache()
		startScanWork := gcw.scanWork
		gcDrainN(&gcw, scanWork)
		// Record that we did this much scan work.
		gp.gcscanwork += gcw.scanWork - startScanWork
		// TODO(austin): This is the vast majority of our
		// disposes. Instead of constantly disposing, keep a
		// per-P gcWork cache (probably combined with the
		// write barrier wbuf cache).
		gcw.dispose()
	})
}
```
`gcAssistAlloc`は、このコミットの最も重要な変更点です。メモリ割り当て時に呼び出され、Goroutineの割り当て量に基づいて必要なGCスキャン作業量を計算します。特に注目すべきは、`gcController.bgScanCredit`から作業を「奪い取る」ロジックです。これは、バックグラウンドGCが既に実行した作業をミューテータの貢献としてカウントすることで、ミューテータが実際に実行するGC作業量を最適化します。残りの作業は`gcDrainN`を呼び出してミューテータ自身が実行します。

### `src/runtime/malloc.go` の変更点

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer {
	// ... 既存のロジック ...

	if shouldtriggergc() {
		startGC(gcBackgroundMode)
	} else if gcphase == _GCmark {
		// Assist garbage collector. We delay this until the
		// epilogue so that it doesn't interfere with the
		// inner working of malloc such as mcache refills that
		// might happen while doing the gcAssistAlloc.
		gcAssistAlloc(size, shouldhelpgc)
	}

	return x
}
```
`mallocgc`における`gcAssistAlloc`の呼び出しは、Goのメモリ割り当てパスに比例的ミューテータアシストを統合するものです。これにより、すべてのメモリ割り当てがGCマークフェーズ中に適切にGC作業に貢献するようになります。`gchelpwork`から`gcAssistAlloc`への変更は、固定量のアシストから比例的アシストへの移行を明確に示しています。

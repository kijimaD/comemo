## 変更の背景

Goプログラムを動的リンク（共有ライブラリとして、または共有ライブラリを使用する実行ファイルとして）する場合、特に`ppc64le`のような特定のアーキテクチャでは、グローバル変数や関数へのアクセス方法に特別な考慮が必要です。

従来の静的リンクでは、リンカはプログラム内のすべてのシンボル（変数や関数）の最終的なアドレスを決定し、そのアドレスを直接コードに埋め込むことができます。しかし、動的リンクでは、プログラムがロードされるまで共有ライブラリ内のシンボルの正確なアドレスは分かりません。そのため、プログラムは実行時にこれらのアドレスを解決する必要があります。

`ppc64le`アーキテクチャでは、この動的解決を効率的に行うために、グローバルオフセットテーブル（GOT）とプロシージャリンケージテーブル（PLT）というメカニズムが広く利用されます。このコミット以前は、Goのツールチェインが`ppc64le`上で動的リンクを行う際に、グローバルデータへのアクセスがGOTを適切に利用していなかった可能性があります。これにより、位置独立コード（PIC）の生成が不完全になったり、動的リンクされたプログラムが正しく動作しなかったりする問題が発生していたと考えられます。

この変更の目的は、`ppc64le`アーキテクチャにおけるGoの動的リンクのサポートを強化し、グローバルデータへのアクセスがGOTを介して行われるようにすることで、より堅牢で標準に準拠した共有ライブラリおよび実行ファイルの生成を可能にすることです。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **動的リンク (Dynamic Linking)**:
    *   プログラムが実行時に必要なライブラリをロードし、リンクする方式です。これにより、ディスクスペースの節約（複数のプログラムが同じライブラリを共有できる）、メモリの節約（ライブラリのコードが一度だけメモリにロードされる）、およびライブラリの更新が容易になるという利点があります。
    *   対照的に、静的リンクでは、必要なライブラリのコードがコンパイル時に実行ファイルに直接組み込まれます。

2.  **位置独立コード (Position-Independent Code, PIC)**:
    *   メモリ上の任意のアドレスにロードされても正しく実行できるコードのことです。共有ライブラリは通常、PICとしてコンパイルされます。
    *   PICでは、絶対アドレスではなく、現在の命令ポインタからの相対オフセットを使用してデータや関数にアクセスします。

3.  **グローバルオフセットテーブル (Global Offset Table, GOT)**:
    *   動的リンクされたプログラムが、共有ライブラリ内のグローバル変数や関数にアクセスするために使用するデータ構造です。
    *   GOTは、プログラムのデータセクションに配置され、共有ライブラリ内のシンボルの実行時アドレスを格納するエントリの配列を含みます。
    *   プログラムは、直接シンボルのアドレスを参照する代わりに、GOT内の対応するエントリを間接的に参照します。動的リンカは、プログラムのロード時にGOTエントリを実際のシンボルアドレスで埋めます。

4.  **プロシージャリンケージテーブル (Procedure Linkage Table, PLT)**:
    *   共有ライブラリ内の関数を呼び出すために使用されるメカニズムです。PLTはGOTと連携して動作し、関数の遅延バインディング（関数が実際に呼び出されるまでアドレス解決を遅らせる）を可能にします。

5.  **PowerPC 64-bit Little-Endian (ppc64le) アーキテクチャ**:
    *   IBMが開発したPowerPCプロセッサの64ビット版で、リトルエンディアンバイトオーダーを使用します。
    *   `ppc64le`では、特定のレジスタ（例: `R2`）がTable of Contents (TOC) ポインタとして予約されており、グローバルデータや関数へのアクセスにTOCを介した間接参照が頻繁に用いられます。TOCは、GOTや他のグローバルデータへのオフセットを格納するテーブルです。

6.  **Goツールチェイン (`cmd/internal/obj`, `cmd/link`)**:
    *   `cmd/internal/obj`: Goのアセンブラ（`go tool asm`）のバックエンドの一部で、アセンブリコードをオブジェクトファイルに変換する役割を担います。命令のエンコード、リロケーション情報の生成などを行います。
    *   `cmd/link`: Goのリンカ（`go tool link`）のバックエンドで、オブジェクトファイルを結合して実行可能ファイルや共有ライブラリを生成します。リロケーションの解決、シンボル解決、GOT/PLTの構築などを行います。

7.  **リロケーション (Relocation)**:
    *   コンパイル時にアドレスが確定できないシンボル（例: 共有ライブラリ内のグローバル変数）について、リンカが実行時にそのアドレスを解決し、コード内の参照を修正するプロセスです。
    *   リロケーションエントリは、オブジェクトファイル内に含まれ、どの場所のコードを、どのシンボルのアドレスで、どのように修正すべきかをリンカに指示します。

## 技術的詳細

このコミットの核心は、`ppc64le`アーキテクチャにおける動的リンク時のグローバルデータアクセスを、GOTを介して行うようにGoツールチェインを修正することです。

具体的には、以下の変更が行われています。

1.  **新しいリロケーションタイプ `R_ADDRPOWER_GOT` の導入**:
    *   `src/cmd/internal/obj/link.go` に `R_ADDRPOWER_GOT` という新しいリロケーションタイプが追加されました。これは、PowerPCのD-form/DS-form命令シーケンスをリロケートする際に、シンボルのアドレスではなく、TOCからのGOTスロットのオフセットを挿入するためのものです。
    *   これにより、リンカはGOTエントリを指すようにコードを修正できるようになります。

2.  **アセンブラ定数 `C_GOTADDR` の追加**:
    *   `src/cmd/internal/obj/ppc64/a.out.go` と `src/cmd/internal/obj/ppc64/anames9.go` に `C_GOTADDR` が追加されました。これは、アセンブラがGOTアドレスを参照する際に使用する内部的な定数です。

3.  **アセンブラの命令書き換えロジックの変更 (`src/cmd/internal/obj/ppc64/asm9.go`)**:
    *   `optab` に `AMOVD, C_GOTADDR` のエントリが追加され、GOTアドレスをロードする `AMOVD` 命令の処理方法が定義されました。
    *   `aclass` 関数に `obj.NAME_GOTREF` のケースが追加され、`NAME_GOTREF` とマークされたシンボルが `C_GOTADDR` として分類されるようになりました。これは、リンカがGOTを介してアクセスすべきシンボルを識別するための重要なステップです。
    *   `asmout` 関数に新しいケース `81` が追加されました。このケースは `R_ADDRPOWER_GOT` リロケーションタイプを処理し、`ADDIS` (Add Immediate Shifted) と `AMOVD` (Move Doubleword) 命令のシーケンスを生成します。
        *   `ADDIS` は、TOCレジスタ (`R2`) を基準としてGOTスロットのアドレスの上位部分をロードします。
        *   `AMOVD` は、GOTスロットのアドレスの下位部分をロードし、最終的にGOTエントリのアドレスをレジスタに格納します。
        *   これにより、コードは直接グローバルデータのアドレスを参照するのではなく、GOT内のエントリを介して間接的に参照するようになります。

4.  **リンカの命令書き換えロジックの追加 (`src/cmd/internal/obj/ppc64/obj9.go`)**:
    *   `progedit` 関数内で、`ctxt.Flag_dynlink` が真の場合に `rewriteToUseGot` 関数が呼び出されるようになりました。これは、動的リンクが有効な場合にのみGOTを介したアクセスに書き換えることを意味します。
    *   `rewriteToUseGot` 関数が追加されました。この関数は、Goの内部的なアセンブリ命令（`obj.Prog`）を走査し、グローバルデータへのアクセスをGOTを介するように書き換えます。
        *   **`ADUFFCOPY` / `ADUFFZERO` の書き換え**: `runtime.duffcopy` や `runtime.duffzero` といったランタイム関数への呼び出しを、GOTを介して行うように変更します。具体的には、`runtime.duffxxx@GOT` をレジスタにロードし、そのレジスタを介して関数を呼び出すように命令シーケンスを生成します。
        *   **`MOVD $sym, Rx` の書き換え**: シンボルのアドレスを直接レジスタにロードする命令を、`sym@GOT` をレジスタにロードするように変更します。オフセットがある場合は、GOTからロードしたアドレスにオフセットを加算する命令も追加されます。
        *   **`MOVx sym, Ry` / `MOVx Ry, sym` の書き換え**: グローバル変数へのロード/ストア命令を、まず `sym@GOT` を一時レジスタ (`REGTMP`) にロードし、その一時レジスタを介してメモリ操作を行うように変更します。これにより、グローバル変数へのアクセスが間接化され、PICの要件を満たします。
    *   `p.From.Sym.Local = true` の設定は、特定の内部シンボルがGOTを介してアクセスされるべきではないことをリンカに伝えるために使用される可能性があります。

5.  **ELFリロケーションタイプのマッピング (`src/cmd/link/internal/ppc64/asm.go`)**:
    *   `elfreloc1` 関数に `obj.R_ADDRPOWER_GOT` のケースが追加されました。このGo内部のリロケーションタイプは、ELF標準のリロケーションタイプである `R_PPC64_GOT16_HA` (GOT High-Adjusted) と `R_PPC64_GOT16_LO_DS` (GOT Low-DS) にマッピングされます。
    *   これらのELFリロケーションタイプは、動的リンカが実行時にGOTエントリを正しく解決するために必要な情報を提供します。

これらの変更により、`ppc64le`上で動的リンクされたGoプログラムは、グローバルデータへのアクセスにGOTを適切に利用するようになり、位置独立性を確保し、動的リンクの標準的な慣行に準拠するようになります。

    	// ... 既存の処理 ...
    	if ctxt.Flag_dynlink { // 動的リンクが有効な場合のみ

    // Rewrite p, if necessary, to access global data via the global offset table.
    func rewriteToUseGot(ctxt *obj.Link, p *obj.Prog) {
    	// ADUFFCOPY/ADUFFZERO の書き換えロジック
    	if p.As == obj.ADUFFCOPY || p.As == obj.ADUFFZERO {
    		// ... runtime.duffxxx@GOT をロードし、間接呼び出しに変換 ...
    	}

    	// グローバルデータへの TYPE_ADDR アクセスの書き換え (MOVD $sym, Rx など)
    	if p.From.Type == obj.TYPE_ADDR && p.From.Name == obj.NAME_EXTERN && !p.From.Sym.Local {
    		// ... sym@GOT をロードし、必要に応じてオフセットを加算 ...
    	}

    	// グローバル変数へのロード/ストア命令の書き換え (MOVx sym, Ry / MOVx Ry, sym など)
    	var source *obj.Addr
    	if p.From.Name == obj.NAME_EXTERN && !p.From.Sym.Local {
    		source = &p.From
    	} else if p.To.Name == obj.NAME_EXTERN && !p.To.Sym.Local {
    		source = &p.To
    	} else {
    		return
    	}
    	// ... 中略 ...
    	// MOVD sym@GOT, REGTMP; MOVx (REGTMP), Ry または MOVx Ry, (REGTMP) に変換
    	p1 := obj.Appendp(ctxt, p)
    	p2 := obj.Appendp(ctxt, p1)

    	p1.As = AMOVD
    	p1.From.Type = obj.TYPE_MEM
    	p1.From.Sym = source.Sym
    	p1.From.Name = obj.NAME_GOTREF // GOT参照としてマーク
    	p1.To.Type = obj.TYPE_REG
    	p1.To.Reg = REGTMP // 一時レジスタにロード

    	p2.As = p.As
    	p2.From = p.From
    	p2.To = p.To
    	if p.From.Name == obj.NAME_EXTERN {
    		p2.From.Reg = REGTMP
    		p2.From.Name = obj.NAME_NONE
    		p2.From.Sym = nil
    	} else if p.To.Name == obj.NAME_EXTERN {
    		p2.To.Reg = REGTMP
    		p2.To.Name = obj.NAME_NONE
    		p2.To.Sym = nil
    	} else {
    		return
    	}
    	obj.Nopout(p) // 元の命令を無効化
    }

## コアとなるコードの解説

このコミットの主要な変更は、`ppc64le`アーキテクチャにおける動的リンク時のグローバルデータアクセスを、GOTを介して行うための命令書き換えとリロケーション処理の追加です。

1.  **`R_ADDRPOWER_GOT` の導入**:
    *   これはGoのアセンブラ/リンカ内部で使われる新しいリロケーションタイプです。`ppc64le`では、グローバルデータへのアクセスはTOC (Table of Contents) レジスタ (`R2`) を基準としたオフセットで行われます。`R_ADDRPOWER_GOT` は、シンボルの最終アドレスではなく、そのシンボルに対応するGOTスロットがTOCからどれだけ離れているかというオフセットをリロケーション情報として保持します。これにより、実行時に動的リンカがGOTスロットを正しいアドレスで埋めることができるようになります。

2.  **`asmout` 関数での命令生成**:
    *   `asmout` 関数は、Goのアセンブラがアセンブリ命令を機械語に変換する際に呼び出されます。`case 81` は、`R_ADDRPOWER_GOT` リロケーションが必要な場合に実行されます。
    *   ここで生成される `ADDIS` と `AMOVD` 命令のペアは、`ppc64le`でGOTエントリのアドレスをレジスタにロードするための標準的なシーケンスです。
        *   `ADDIS R_dest, R2, high_offset`: `R2` (TOCレジスタ) に `high_offset` を加算し、結果を `R_dest` に格納します。`high_offset` はGOTスロットアドレスの上位16ビットです。
        *   `AMOVD R_dest, low_offset(R_dest)`: `R_dest` の値に `low_offset` を加算したアドレスからダブルワード（8バイト）をロードし、その結果を `R_dest` に格納します。`low_offset` はGOTスロットアドレスの下位16ビットです。
    *   この2つの命令により、`R_dest` レジスタには最終的に目的のGOTスロットのアドレスが格納されます。

3.  **`rewriteToUseGot` 関数での命令書き換え**:
    *   この関数は、リンカがオブジェクトファイルを処理する際に、特定の命令パターンをGOT経由のアクセスに変換します。
    *   **`ADUFFCOPY`/`ADUFFZERO` の処理**: `runtime.duffcopy` や `runtime.duffzero` のようなランタイム関数は、動的リンク時には共有ライブラリから提供される可能性があります。これらの関数への直接呼び出しを、まず `runtime.duffxxx` のGOTエントリをレジスタ (`R12`) にロードし、そのレジスタを介して間接的に呼び出す (`BL (CTR)`) ように書き換えます。これにより、関数のアドレスが実行時に解決されます。
    *   **`MOVD $sym, Rx` の処理**: これは、シンボルのアドレスを直接レジスタにロードする命令です。動的リンクでは、シンボルのアドレスは実行時まで不明なため、この命令は `sym@GOT` (シンボルに対応するGOTエントリのアドレス) をレジスタにロードするように書き換えられます。もし元の命令にオフセットが含まれていれば、GOTからロードしたアドレスにそのオフセットを加算する命令が追加されます。
    *   **`MOVx sym, Ry` / `MOVx Ry, sym` の処理**: これは、グローバル変数 `sym` からレジスタ `Ry` へのロード、または `Ry` から `sym` へのストアを行う命令です。動的リンクでは、`sym` のアドレスは実行時まで不明なため、直接アクセスすることはできません。そこで、まず `sym@GOT` を一時レジスタ (`REGTMP`) にロードし、次にその一時レジスタをベースアドレスとして `sym` へのロード/ストア命令を実行するように書き換えます。これにより、グローバル変数へのアクセスが間接化され、位置独立性が保たれます。
    *   `obj.NAME_GOTREF` は、このシンボルがGOTを介して参照されるべきであることをリンカに伝えるためのフラグのようなものです。

4.  **`elfreloc1` 関数でのELFリロケーションマッピング**:
    *   `elfreloc1` 関数は、Go内部のリロケーションタイプをELF標準のリロケーションタイプにマッピングします。
    *   `obj.R_ADDRPOWER_GOT` は、`R_PPC64_GOT16_HA` と `R_PPC64_GOT16_LO_DS` という2つのELFリロケーションタイプに変換されます。
        *   `R_PPC64_GOT16_HA`: GOTエントリのアドレスの上位16ビットをリロケートします。
        *   `R_PPC64_GOT16_LO_DS`: GOTエントリのアドレスの下位16ビットをリロケートし、さらにDS (Doubleword-Scaled) オフセットを考慮します。
    *   これらのELFリロケーションエントリは、最終的な実行可能ファイルや共有ライブラリに埋め込まれ、プログラムがロードされる際に動的リンカによって読み取られ、GOTエントリが正しいアドレスで更新されます。

これらの変更の組み合わせにより、Goのツールチェインは`ppc64le`上で動的リンクされたプログラムが、グローバルデータにアクセスする際にGOTを適切に利用し、位置独立性を維持できるようになります。これは、Goプログラムが共有ライブラリとして機能したり、共有ライブラリに依存したりするシナリオにおいて、特に重要です。

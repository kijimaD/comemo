# [インデックス 22008] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/asm`）におけるスタックポインタ（`SP`）の参照方法に関する重要な変更を導入しています。特にARMアーキテクチャにおいて、擬似スタックポインタ`SP`を介したオフセット参照の厳格化と、実際のハードウェアスタックポインタ（ARMでは`R13`）の使用を明確に区別することを目的としています。これにより、アセンブリコードの記述における曖昧さを排除し、より堅牢なスタック操作を保証します。

## 変更の背景

Go言語のコンパイラとアセンブラは、クロスプラットフォーム対応のために、各アーキテクチャ固有のアセンブリコードを生成・処理します。この際、スタックフレーム内の変数や引数にアクセスするために、`SP`（Stack Pointer）や`FP`（Frame Pointer）といった擬似レジスタが使用されます。しかし、これらの擬似レジスタは、実際のハードウェアレジスタとしてのスタックポインタとは異なるセマンティクスを持っています。

特に、`4(SP)`のような形式で擬似スタックポインタ`SP`に直接オフセットを指定する記述は、Goのアセンブラの設計思想と合致しない場合がありました。Goのアセンブラにおける`SP`は、現在の関数のスタックフレームの「トップ」を指す擬似レジスタであり、通常は関数引数や戻り値の領域へのアクセスに使用されます。これに対し、ハードウェアのスタックポインタは、より低レベルなスタック操作（例えば、関数呼び出し時のレジスタ退避など）に用いられます。

このコミットの背景には、`4(SP)`のような記述が、特にARMアーキテクチャにおいて、擬似スタックと実際のハードウェアスタックの混同を招き、予期せぬバグや移植性の問題を引き起こす可能性があったという認識があります。386アーキテクチャでは歴史的な理由から許容されていましたが、他のアーキテクチャではこの曖昧さを排除し、より明確なスタック参照のルールを適用する必要がありました。

具体的には、擬似スタック（関数引数やローカル変数）を参照する際には、シンボル名（変数名や引数名）を明示的に指定することを強制し、純粋なオフセット参照はハードウェアスタックポインタ（ARMでは`R13`）を使用するように変更することで、コードの意図を明確にし、堅牢性を高めることが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のアセンブラに関する基本的な知識が必要です。

### Go言語のアセンブラ（cmd/asm）

Go言語は、C言語のように外部のアセンブラツール（GASなど）に依存せず、独自のクロスプラットフォームアセンブラ`cmd/asm`を持っています。このアセンブラは、Goのソースコードから生成されるアセンブリコード（`.s`ファイル）を処理し、オブジェクトファイルに変換します。`cmd/asm`は、各アーキテクチャ（amd64, arm, arm64など）の命令セットをサポートしつつ、Goランタイムの規約に合わせた擬似レジスタやシンボル解決の仕組みを提供します。

### Go言語の擬似レジスタ

Goのアセンブラには、実際のCPUレジスタとは異なる「擬似レジスタ」という概念があります。これらは、Goランタイムのメモリモデルや関数呼び出し規約を抽象化するために導入されています。主要な擬似レジスタは以下の通りです。

*   **`SP` (Stack Pointer)**:
    *   Goのアセンブラにおける`SP`は、現在の関数のスタックフレームの「トップ」を指す擬似レジスタです。
    *   `SP`からのオフセットは、通常、関数の引数や戻り値の領域、またはローカル変数へのアクセスに使用されます。
    *   例えば、`0(SP)`は関数の最初の引数、`8(SP)`は2番目の引数（64bitアーキテクチャの場合）を指すことがあります。
    *   **重要な点**: `SP`は、実際のハードウェアスタックポインタ（例えばx86の`RSP`/`ESP`やARMの`R13`）とは異なり、Goランタイムが管理する論理的なスタックフレームの概念を表します。そのため、`SP`に直接オフセットを加えて、任意のスタック上のアドレスにアクセスするような使い方は推奨されません。

*   **`FP` (Frame Pointer)**:
    *   `FP`は、現在の関数のスタックフレームの「フレームポインタ」を指す擬似レジスタです。
    *   `FP`からのオフセットは、主に呼び出し元の関数から渡された引数にアクセスするために使用されます。
    *   `0(FP)`は、現在の関数の最初の引数を指します。`name+offset(FP)`のような形式で使われ、`name`は引数のシンボル名です。

*   **`SB` (Static Base)**:
    *   `SB`は、グローバル変数や関数などの静的シンボルを参照するための擬似レジスタです。
    *   `name(SB)`のような形式で使われ、`name`はグローバルシンボル名です。

### ARMアーキテクチャのスタックポインタ（R13/SP）

ARMアーキテクチャでは、汎用レジスタ`R13`が通常、スタックポインタ（`SP`）として使用されます。これは、実際のハードウェアがスタック操作に使用するレジスタです。Goのアセンブラにおける擬似レジスタ`SP`と、ARMのハードウェアレジスタ`R13`は、名前が似ていますが、その役割とセマンティクスが異なります。

*   **Goの擬似`SP`**: Goランタイムの関数呼び出し規約に基づいた、論理的なスタックフレームの参照。
*   **ARMの`R13`**: CPUが実際にスタックのトップを追跡するために使用する物理レジスタ。

このコミットは、この2つの`SP`の概念の混同を防ぎ、アセンブリコードの記述をより厳密にすることを目的としています。

## 技術的詳細

このコミットの技術的な核心は、Goのアセンブラが擬似レジスタ`SP`を処理する方法を変更し、特定のオフセット参照を禁止することにあります。

変更前は、`4(SP)`のように、擬似レジスタ`SP`に直接数値オフセットを指定する形式が許容されていました。これは、特に386アーキテクチャでは歴史的に使用されていましたが、他のアーキテクチャでは問題を引き起こす可能性がありました。Goのアセンブラの設計では、`SP`は関数引数や戻り値、ローカル変数といった「擬似スタック」上の要素をシンボル名で参照するためのものであり、ハードウェアスタックポインタのように任意のオフセットでメモリを指す用途には適していません。

このコミットでは、`src/cmd/asm/internal/asm/parse.go`内のアセンブラのパースロジックが修正され、`SB`、`SP`、`FP`といった擬似レジスタを参照する際に、シンボル名が指定されていない`offset(PseudoRegister)`形式（例: `4(SP)`）をエラーとするようになりました。ただし、386アーキテクチャについては、既存のコードベースとの互換性を考慮し、この制限の例外としています。

新しいルールでは、擬似スタック上の要素を参照する際には、必ず`name+offset(FP)`または`name+offset(SP)`のように、シンボル名（`name`）を明示的に指定する必要があります。例えば、`p_end(SP)`や`buf(SP)`のように、定義されたシンボル名とオフセットを組み合わせる形式です。

もし、アセンブリコード内で実際のハードウェアスタックポインタからのオフセットでメモリにアクセスしたい場合は、擬似レジスタ`SP`ではなく、そのアーキテクチャの実際のハードウェアスタックポインタレジスタ（ARMでは`R13`）を直接使用するように変更されました。これにより、コードの意図が明確になり、擬似スタックとハードウェアスタックの操作が混同されることを防ぎます。

この変更は、Goのランタイム、暗号ライブラリ、同期プリミティブなど、ARMアセンブリコードを含む多くのファイルに影響を与えました。これらのファイルでは、`4(SP)`のような記述が`4(R13)`や`name+offset(FP)`、`name+offset(R13)`といった形式に修正されています。

この厳格化により、アセンブリコードの可読性と保守性が向上し、将来的なアーキテクチャ変更や最適化の際に発生しうる潜在的な問題を未然に防ぐことができます。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/parse.go` の変更

```diff
--- a/src/cmd/asm/internal/asm/parse.go
+++ b/src/cmd/asm/internal/asm/parse.go
@@ -546,6 +546,10 @@ func (p *Parser) registerIndirect(a *obj.Addr, prefix rune) {
 		// For SB, SP, and FP, there must be a name here. 0(FP) is not legal.
 		if name != "PC" && a.Name == obj.NAME_NONE {
 			p.errorf("cannot reference %s without a symbol", name)
 		}
 		p.setPseudoRegister(a, name, false, prefix)
 		return
 	}
```

このコードスニペットは、アセンブラがアドレスをパースする際のロジックの一部です。
`registerIndirect`関数は、`offset(Register)`のような間接アドレス指定を処理します。
追加された`if`文は、以下の条件をチェックします。

*   `name != "PC"`: 擬似レジスタが`PC`（プログラムカウンタ）ではないこと。`PC`は特殊なケースであり、オフセット参照が許容される場合があります。
*   `a.Name == obj.NAME_NONE`: アドレス構造体`a`の`Name`フィールドが`obj.NAME_NONE`であること。これは、シンボル名が指定されていない、つまり純粋な数値オフセット参照であることを意味します。

この両方の条件が真である場合、アセンブラは「`cannot reference %s without a symbol`」（シンボルなしで%sを参照できません）というエラーを発生させます。ここで`%s`は擬似レジスタの名前（`SB`, `SP`, `FP`）に置き換えられます。

この変更により、`0(SP)`や`4(FP)`のように、シンボル名なしで擬似レジスタに直接オフセットを指定する記述が、386以外のアーキテクチャでコンパイルエラーとなるようになります。これにより、擬似スタックの参照には必ずシンボル名を伴うというGoアセンブラの規約が強制されます。

## 変更の背景

Go言語のコンパイラとアセンブラは、クロスプラットフォーム対応のために、各アーキテクチャ固有のアセンブリコードを生成・処理します。この際、スタックフレーム内の変数や引数にアクセスするために、`SP`（Stack Pointer）や`FP`（Frame Pointer）といった擬似レジスタが使用されます。しかし、これらの擬似レジスタは、実際のハードウェアレジスタとしてのスタックポインタとは異なるセマンティクスを持っています。

特に、`4(SP)`のような形式で擬似スタックポインタ`SP`に直接オフセットを指定する記述は、Goのアセンブラの設計思想と合致しない場合がありました。Goのアセンブラにおける`SP`は、現在の関数のスタックフレームの「トップ」を指す擬似レジスタであり、通常は関数引数や戻り値の領域へのアクセスに使用されます。これに対し、ハードウェアのスタックポインタは、より低レベルなスタック操作（例えば、関数呼び出し時のレジスタ退避など）に用いられます。

このコミットの背景には、`4(SP)`のような記述が、特にARMアーキテクチャにおいて、擬似スタックと実際のハードウェアスタックの混同を招き、予期せぬバグや移植性の問題を引き起こす可能性があったという認識があります。386アーキテクチャでは歴史的な理由から許容されていましたが、他のアーキテクチャではこの曖昧さを排除し、より明確なスタック参照のルールを適用する必要がありました。

具体的には、擬似スタック（関数引数やローカル変数）を参照する際には、シンボル名（変数名や引数名）を明示的に指定することを強制し、純粋なオフセット参照はハードウェアスタックポインタ（ARMでは`R13`）を使用するように変更することで、コードの意図を明確にし、堅牢性を高めることが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のアセンブラに関する基本的な知識が必要です。

### Go言語のアセンブラ（cmd/asm）

Go言語は、C言語のように外部のアセンブラツール（GASなど）に依存せず、独自のクロスプラットフォームアセンブラ`cmd/asm`を持っています。このアセンブラは、Goのソースコードから生成されるアセンブリコード（`.s`ファイル）を処理し、オブジェクトファイルに変換します。`cmd/asm`は、各アーキテクチャ（amd64, arm, arm64など）の命令セットをサポートしつつ、Goランタイムの規約に合わせた擬似レジスタやシンボル解決の仕組みを提供します。

### Go言語の擬似レジスタ

Goのアセンブラには、実際のCPUレジスタとは異なる「擬似レジスタ」という概念があります。これらは、Goランタイムのメモリモデルや関数呼び出し規約を抽象化するために導入されています。主要な擬似レジスタは以下の通りです。

*   **`SP` (Stack Pointer)**:
    *   Goのアセンブラにおける`SP`は、現在の関数のスタックフレームの「トップ」を指す擬似レジスタです。
    *   `SP`からのオフセットは、通常、関数の引数や戻り値の領域、またはローカル変数へのアクセスに使用されます。
    *   例えば、`0(SP)`は関数の最初の引数、`8(SP)`は2番目の引数（64bitアーキテクチャの場合）を指すことがあります。
    *   **重要な点**: `SP`は、実際のハードウェアスタックポインタ（例えばx86の`RSP`/`ESP`やARMの`R13`）とは異なり、Goランタイムが管理する論理的なスタックフレームの概念を表します。そのため、`SP`に直接オフセットを加えて、任意のスタック上のアドレスにアクセスするような使い方は推奨されません。

*   **`FP` (Frame Pointer)**:
    *   `FP`は、現在の関数のスタックフレームの「フレームポインタ」を指す擬似レジスタです。
    *   `FP`からのオフセットは、主に呼び出し元の関数から渡された引数にアクセスするために使用されます。
    *   `0(FP)`は、現在の関数の最初の引数を指します。`name+offset(FP)`のような形式で使われ、`name`は引数のシンボル名です。

*   **`SB` (Static Base)**:
    *   `SB`は、グローバル変数や関数などの静的シンボルを参照するための擬似レジスタです。
    *   `name(SB)`のような形式で使われ、`name`はグローバルシンボル名です。

### ARMアーキテクチャのスタックポインタ（R13/SP）

ARMアーキテクチャでは、汎用レジスタ`R13`が通常、スタックポインタ（`SP`）として使用されます。これは、実際のハードウェアがスタック操作に使用するレジスタです。Goのアセンブラにおける擬似レジスタ`SP`と、ARMのハードウェアレジスタ`R13`は、名前が似ていますが、その役割とセマンティクスが異なります。

*   **Goの擬似`SP`**: Goランタイムの関数呼び出し規約に基づいた、論理的なスタックフレームの参照。
*   **ARMの`R13`**: CPUが実際にスタックのトップを追跡するために使用する物理レジスタ。

このコミットは、この2つの`SP`の概念の混同を防ぎ、アセンブリコードの記述をより厳密にすることを目的としています。

## 技術的詳細

このコミットの技術的な核心は、Goのアセンブラが擬似レジスタ`SP`を処理する方法を変更し、特定のオフセット参照を禁止することにあります。

変更前は、`4(SP)`のように、擬似レジスタ`SP`に直接数値オフセットを指定する形式が許容されていました。これは、特に386アーキテクチャでは歴史的に使用されていましたが、他のアーキテクチャでは問題を引き起こす可能性がありました。Goのアセンブラの設計では、`SP`は関数引数や戻り値、ローカル変数といった「擬似スタック」上の要素をシンボル名で参照するためのものであり、ハードウェアスタックポインタのように任意のオフセットでメモリを指す用途には適していません。

このコミットでは、`src/cmd/asm/internal/asm/parse.go`内のアセンブラのパースロジックが修正され、`SB`、`SP`、`FP`といった擬似レジスタを参照する際に、シンボル名が指定されていない`offset(PseudoRegister)`形式（例: `4(SP)`）をエラーとするようになりました。ただし、386アーキテクチャについては、既存のコードベースとの互換性を考慮し、この制限の例外としています。

新しいルールでは、擬似スタック上の要素を参照する際には、必ず`name+offset(FP)`または`name+offset(SP)`のように、シンボル名（`name`）を明示的に指定する必要があります。例えば、`p_end(SP)`や`buf(SP)`のように、定義されたシンボル名とオフセットを組み合わせる形式です。

もし、アセンブリコード内で実際のハードウェアスタックポインタからのオフセットでメモリにアクセスしたい場合は、擬似レジスタ`SP`ではなく、そのアーキテクチャの実際のハードウェアスタックポインタレジスタ（ARMでは`R13`）を直接使用するように変更されました。これにより、コードの意図が明確になり、擬似スタックとハードウェアスタックの操作が混同されることを防ぎます。

この変更は、Goのランタイム、暗号ライブラリ、同期プリミティブなど、ARMアセンブリコードを含む多くのファイルに影響を与えました。これらのファイルでは、`4(SP)`のような記述が`4(R13)`や`name+offset(FP)`、`name+offset(R13)`といった形式に修正されています。

この厳格化により、アセンブリコードの可読性と保守性が向上し、将来的なアーキテクチャ変更や最適化の際に発生しうる潜在的な問題を未然に防ぐことができます。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイルに集中しています。

1.  **`src/cmd/asm/internal/asm/parse.go`**:
    *   Goアセンブラのパースロジックを定義するファイルです。
    *   擬似レジスタ（`SB`, `SP`, `FP`）の参照に関する新しい検証ルールが追加されました。
    *   具体的には、`registerIndirect`関数内で、`name != "PC" && a.Name == obj.NAME_NONE`の場合に「`cannot reference %s without a symbol`」というエラーを発生させるロジックが追加されています。これは、`PC`以外の擬似レジスタをシンボル名なしで参照することを禁止するものです。

2.  **ARMアセンブリファイル群 (`.s`ファイル)**:
    *   `src/crypto/md5/md5block_arm.s`
    *   `src/crypto/rc4/rc4_arm.s`
    *   `src/crypto/sha1/sha1block_arm.s`
    *   `src/runtime/asm_arm.s`
    *   `src/runtime/sys_linux_arm.s`
    *   `src/runtime/vlop_arm.s`
    *   `src/sync/atomic/asm_linux_arm.s`
    *   これらのファイルでは、`4(SP)`のような形式のスタック参照が、`4(R13)`や`name+offset(FP)`、`name+offset(R13)`といった新しい規約に沿った形式に修正されています。例えば、`p_end(SP)`が`p_end(R13)`に、`0(FP)`が`dst+0(FP)`のように変更されています。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/parse.go` の変更

```diff
--- a/src/cmd/asm/internal/asm/parse.go
+++ b/src/cmd/asm/internal/asm/parse.go
@@ -546,6 +546,10 @@ func (p *Parser) registerIndirect(a *obj.Addr, prefix rune) {
 		// For SB, SP, and FP, there must be a name here. 0(FP) is not legal.
 		if name != "PC" && a.Name == obj.NAME_NONE {
 			p.errorf("cannot reference %s without a symbol", name)
 		}
 		p.setPseudoRegister(a, name, false, prefix)
 		return
 	}
```

このコードスニペットは、アセンブラがアドレスをパースする際のロジックの一部です。
`registerIndirect`関数は、`offset(Register)`のような間接アドレス指定を処理します。
追加された`if`文は、以下の条件をチェックします。

*   `name != "PC"`: 擬似レジスタが`PC`（プログラムカウンタ）ではないこと。`PC`は特殊なケースであり、オフセット参照が許容される場合があります。
*   `a.Name == obj.NAME_NONE`: アドレス構造体`a`の`Name`フィールドが`obj.NAME_NONE`であること。これは、シンボル名が指定されていない、つまり純粋な数値オフセット参照であることを意味します。

この両方の条件が真である場合、アセンブラは「`cannot reference %s without a symbol`」（シンボルなしで%sを参照できません）というエラーを発生させます。ここで`%s`は擬似レジスタの名前（`SB`, `SP`, `FP`）に置き換えられます。

この変更により、`0(SP)`や`4(FP)`のように、シンボル名なしで擬似レジスタに直接オフセットを指定する記述が、386以外のアーキテクチャでコンパイルエラーとなるようになります。これにより、擬似スタックの参照には必ずシンボル名を伴うというGoアセンブラの規約が強制されます。

# [インデックス 26650] ファイルの概要

このコミットは、Goランタイムが`libc`の`mmap`システムコールを呼び出す際に、`amd64`アーキテクチャのProcedure Call Standard (psABI) に準拠したスタックポインタ (SP) のアライメントを保証するための修正です。具体的には、`_cgo_mmap`を呼び出す前にスタックを16バイト境界にアライメントし、呼び出し後に元に戻す処理を追加しています。これにより、`libc`関数との互換性と安定性が向上します。

## 変更の背景

この変更の背景には、GoランタイムがC言語のライブラリ関数（特に`libc`の`mmap`）を呼び出す際のスタックアライメントの不整合がありました。`amd64`アーキテクチャでは、System V Application Binary Interface (psABI) という標準が定められており、これには関数呼び出し時のスタックポインタ (SP) のアライメントに関する厳格な要件が含まれています。具体的には、`CALL`命令が実行される直前には、SPが16バイト境界にアライメントされている必要があります。

Goランタイムは、`cgo`が使用されている場合に、メモリマッピングのシステムコール（`mmap`）を直接実行する代わりに、`_cgo_mmap`という内部変数を通じてC言語の`mmap`実装を呼び出すことがあります。これは、メモリサニタイザーなどのツールがCコードのメモリ操作をインターセプトできるようにするために重要です。

しかし、修正前の`runtime·callCgoMmap`関数は、`_cgo_mmap`を呼び出す前にSPの16バイトアライメントを保証していませんでした。`CALL`命令自体はリターンアドレス（8バイト）をスタックにプッシュするため、呼び出し直前のSPが16バイトアライメントされていなければ、呼び出されたC関数内部ではSPが正しくアライメントされず、予期せぬ動作やクラッシュ（セグメンテーション違反など）を引き起こす可能性がありました。特に、SIMD命令（SSE/AVXなど）を使用するC関数は、16バイト以上の厳密なメモリアライメントを要求することが多く、アライメント違反はパフォーマンスの低下やプログラムの誤動作に直結します。

このコミットは、このスタックアライメントの不整合を解消し、Goランタイムが`libc`関数を安全かつ標準に準拠した形で呼び出せるようにすることを目的としています。

## 前提知識の解説

1.  **amd64 (x86-64) psABI (Procedure Call Standard for the AMD64 Architecture)**:
    *   `amd64`アーキテクチャにおける関数呼び出し規約の標準です。LinuxやmacOSなどのUnix系システムで広く採用されています。
    *   この規約は、レジスタの使用方法、引数の渡し方、スタックフレームの構造、そしてスタックポインタのアライメントなど、関数間のインターフェースを定義しています。
    *   **スタックアライメントの要件**: `CALL`命令が実行される直前には、スタックポインタ (RSP) が16バイト境界にアライメントされている必要があります。つまり、RSPのアドレスは16の倍数でなければなりません。
    *   `CALL`命令は、リターンアドレス（8バイト）をスタックにプッシュします。そのため、呼び出された関数に入った直後には、RSPは8バイトアライメント（`RSP % 16 == 8`）になります。呼び出された関数がさらに別の関数を呼び出す場合や、16バイトアライメントを要求するデータ（SIMD命令のオペランドなど）を使用する場合は、関数内でSPを再度16バイトアライメントに調整する必要があります。

2.  **スタックポインタ (SP/RSP)**:
    *   プログラムの実行中に、ローカル変数、関数引数、リターンアドレスなどが格納されるスタックメモリの最上位を指すレジスタです。
    *   `amd64`では、スタックは高アドレスから低アドレスに向かって成長します。

3.  **`mmap`システムコール**:
    *   メモリをファイルやデバイスにマッピングしたり、匿名メモリ領域を確保したりするためのシステムコールです。OSからメモリを割り当てる際に使用されます。
    *   Goランタイムは、自身のメモリ管理のために`mmap`を内部的に利用します。

4.  **`cgo`**:
    *   GoプログラムからC言語のコードを呼び出すためのGoの機能です。
    *   `cgo`を使用すると、GoとCの間でデータを受け渡ししたり、Cライブラリの関数をGoから直接呼び出したりできます。
    *   `cgo`が有効な場合、Goランタイムは特定のシステムコール（`mmap`など）をC言語のラッパー関数経由で呼び出すことがあります。これは、C言語のツール（メモリサニタイザーなど）がこれらのシステムコールをインターセプトできるようにするためです。

5.  **`_cgo_mmap`**:
    *   Goランタイム内部で使用される変数で、`cgo`が有効な場合にC言語の`mmap`実装へのポインタを保持します。
    *   Goランタイムが`mmap`システムコールを実行する必要があるが、`cgo`が有効な場合は、直接システムコールを発行する代わりに、この`_cgo_mmap`を通じてC言語の`mmap`ラッパーを呼び出します。

6.  **アセンブリ言語 (`.s`ファイル)**:
    *   Goランタイムの低レベルな処理（システムコール、コンテキストスイッチ、スタック管理など）は、特定のアーキテクチャ向けにアセンブリ言語で記述されています。
    *   `src/runtime/sys_linux_amd64.s`は、Linux `amd64`環境におけるランタイムのシステムコール関連のアセンブリコードを含んでいます。

## 技術的詳細

このコミットは、`src/runtime/sys_linux_amd64.s`ファイル内の`runtime·callCgoMmap`というアセンブリ関数に修正を加えています。この関数は、Goランタイムが`_cgo_mmap`を通じてC言語の`mmap`関数を呼び出すためのラッパーです。

修正の核心は、`_cgo_mmap`を呼び出す直前にスタックポインタ (SP) を`amd64 psABI`の要件に従って16バイト境界にアライメントすることです。

1.  **スタックフレームサイズの変更**:
    *   `TEXT runtime·callCgoMmap(SB),NOSPLIT,$0` から `TEXT runtime·callCgoMmap(SB),NOSPLIT,$16` へ変更されています。
    *   `$0`は、この関数が自身のスタックフレームにローカル変数やレジスタ退避のために0バイトを割り当てることを意味していました。`$16`に変更することで、この関数が自身のスタックフレームに16バイトを割り当てることを示唆しています。これは、スタックアライメントのための領域を確保するためです。

2.  **スタックアライメントの調整**:
    *   `MOVQ SP, BX`: 現在のスタックポインタ (SP) の値を`BX`レジスタに一時的に保存します。これは、`_cgo_mmap`呼び出し後に元のSPに戻すために必要です。
    *   `ANDQ $~15, SP`: `SP`レジスタの値を`~15`（ビットマスクで下位4ビットをクリア、つまり16の倍数にする）と論理AND演算します。これにより、`SP`は強制的に16バイト境界にアライメントされます。例えば、SPが`0x...08`であれば`0x...00`に、`0x...10`であれば`0x...10`になります。
    *   `MOVQ BX, 0(SP)`: 一時保存しておいた元の`SP`の値を、新しくアライメントされた`SP`が指すアドレス（つまりスタックの最上位）にプッシュします。これにより、`_cgo_mmap`呼び出し後に元のSPを復元するための情報がスタックに保存されます。
    *   `CALL AX`: `AX`レジスタに格納されている`_cgo_mmap`のアドレスを呼び出します。この`CALL`命令が実行される直前には、`SP`は16バイトアライメントされています。`CALL`命令はリターンアドレスをプッシュするため、`_cgo_mmap`関数に入った直後には`SP`は8バイトアライメントになりますが、これは`psABI`の要件を満たしています（呼び出し直前が16バイトアライメントであれば、呼び出し先では8バイトオフセットが許容される）。
    *   `MOVQ 0(SP), SP`: `_cgo_mmap`からのリターン後、スタックの最上位に保存しておいた元の`SP`の値を`SP`レジスタに戻します。これにより、`_cgo_mmap`呼び出し前のスタック状態が復元されます。

この一連の操作により、`_cgo_mmap`（そしてそれが呼び出す`libc mmap`）は、`amd64 psABI`に準拠したスタック環境で実行されることが保証され、Cライブラリとの安全な相互運用が可能になります。

## コアとなるコードの解説

*   **`TEXT runtime·callCgoMmap(SB),NOSPLIT,$16`**:
    *   `TEXT`はアセンブリ関数の定義を開始します。
    *   `runtime·callCgoMmap(SB)`は、Goランタイム内の`callCgoMmap`関数を指します。`SB`はシンボルベースを意味します。
    *   `NOSPLIT`は、この関数がスタックを拡張しないことを示します。
    *   `$16`は、この関数が自身のスタックフレームに16バイトのローカルスタック領域を割り当てることを宣言しています。これは、スタックアライメントのために元のSP値を一時的に保存するのに使われます。

*   **`MOVQ SP, BX`**:
    *   現在のスタックポインタ`SP`の値を`BX`レジスタに移動（コピー）します。`BX`は汎用レジスタであり、一時的な値の保存に適しています。

*   **`ANDQ $~15, SP // alignment as per amd64 psABI`**:
    *   `SP`レジスタの値を`~15`（`0xFFFFFFFFFFFFFFF0`）とビット単位の論理AND演算を行います。
    *   この操作により、`SP`の下位4ビットがクリアされ、`SP`の値が最も近い16の倍数（16バイト境界）に切り捨てられます。
    *   コメントにある通り、これは`amd64 psABI`のスタックアライメント要件を満たすための処理です。

*   **`MOVQ BX, 0(SP)`**:
    *   `BX`レジスタに保存しておいた元の`SP`の値を、新しくアライメントされた`SP`が指すアドレス（`0(SP)`）に格納します。
    *   これにより、`_cgo_mmap`呼び出し後に元のスタックポインタを復元するための情報がスタックにプッシュされます。

*   **`CALL AX`**:
    *   `AX`レジスタに格納されているアドレス（この場合は`_cgo_mmap`のアドレス）にある関数を呼び出します。
    *   この命令が実行される直前には、`SP`は16バイトアライメントされています。

*   **`MOVQ 0(SP), SP`**:
    *   `_cgo_mmap`からのリターン後、スタックの最上位（`0(SP)`）に保存しておいた元の`SP`の値を`SP`レジスタに復元します。
    *   これにより、`_cgo_mmap`呼び出しによって変更されたスタックポインタが、呼び出し前の状態に戻されます。

これらの変更により、`runtime·callCgoMmap`は`_cgo_mmap`を呼び出す際に`amd64 psABI`のスタックアライメント要件を遵守し、C言語の`mmap`関数との安全で正しい連携を保証します。

## 変更の背景

このコミットの主な背景は、Goコンパイラが生成する機械語コードのパフォーマンス向上と、既存の最適化ロジックにおける潜在的なバグの修正です。

1.  **ストア操作の最適化**: 現代のCPUは、小さなサイズのメモリ書き込み（例: 1バイトずつ）を複数回行うよりも、大きなサイズのメモリ書き込み（例: 8バイトまとめて）を1回行う方が効率的です。これは、CPUのキャッシュラインやバス幅の利用効率が向上するためです。GoコンパイラのSSAバックエンドでは、バイト単位のストアが連続して行われるパターンを検出し、それをより大きなワード（2バイト）、ダブルワード（4バイト）、クアッドワード（8バイト）のストアに結合することで、生成されるコードの実行速度を向上させることを目指しています。

2.  **`clobber()`関数の導入**: ストア結合のような最適化を行う際、コンパイラは元の小さなストア操作が最適化後に不要になることを保証する必要があります。もし元の操作が他の場所でまだ使用されている場合、それを削除したり変更したりするとプログラムの動作が変わってしまう可能性があります。`clobber()`関数は、特定の値が最適化によって「無効化」され、それ以降は使用されないことを明示的にマークするために導入されました。これにより、コンパイラは安全にリライト（書き換え）を実行し、デッドコード（不要になったコード）を削除できるようになります。

3.  **ロード操作のバグ修正 (Fixes #14267)**: コミットメッセージには「Fix bug in loads where all intermediate values depending on a small load (not just the load itself) must have no other uses. We really need the small load to be dead after the rewrite..」とあります。これは、小さなサイズのロード操作（例: 1バイトの読み込み）が最適化される際に、そのロード結果に依存する全ての中間値が、最適化後に完全にデッド（未使用）になることを保証する必要があるという問題を示しています。もし中間値が他の場所で使われていると、最適化によってそのロードが変更された場合に、誤った値が伝播する可能性があります。このバグは、特に並行処理環境やアトミック操作において、データの整合性に関わる深刻な問題を引き起こす可能性がありました。`clobber()`の導入は、このロードに関するバグ修正にも寄与しています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現であるSSA（Static Single Assignment）形式に変換します。SSA形式は、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化されます。

*   **値 (Value)**: SSAグラフのノードであり、計算結果やメモリ操作などを表します。各値は一意であり、一度だけ定義されます。
*   **オペレーション (Operation)**: 値が実行する具体的な操作（例: 加算、ロード、ストア）。
*   **引数 (Args)**: 値が依存する他の値。
*   **使用回数 (Uses)**: ある値が他のいくつの値の引数として使われているかを示すカウンタ。`Uses == 1`は、その値が一度だけ使用されていることを意味し、最適化の機会を示唆します。
*   **メモリ (Memory)**: SSAでは、メモリの状態も`TypeMem`という特殊な値として扱われます。メモリへの書き込み（ストア）は新しい`TypeMem`値を生成し、メモリからの読み込み（ロード）はその時点の`TypeMem`値に依存します。これにより、メモリ操作の順序と依存関係が明示的に表現されます。

### コンパイラ最適化におけるストアの結合

ストアの結合は、コンパイラのバックエンドで行われる重要な最適化の一つです。

*   **目的**: 複数の隣接する小さなメモリ書き込み操作を、より少ない回数の大きなメモリ書き込み操作に変換することで、実行効率を向上させます。
*   **例**:
    ```go
    var arr [4]byte
    arr[0] = 0x11
    arr[1] = 0x22
    arr[2] = 0x33
    arr[3] = 0x44
    ```
    このようなコードは、コンパイラによって以下のような単一の4バイトストアに変換される可能性があります。
    ```assembly
    MOV DWORD PTR [arr], 0x44332211
    ```
    （エンディアンに依存しますが、概念としてはこのようになります。）
*   **安全性**: この最適化は、元の小さなストア操作が他の場所で読み取られたり、他の操作に影響を与えたりしない場合にのみ安全に適用できます。

### `clobber`の概念

コンパイラ最適化の文脈における「clobber」は、「破壊する」「上書きする」といった意味合いで使われます。GoのSSAリライトルールでは、`clobber()`関数は特定の値が最適化によって「消費され、もはや有効ではない」ことをマークするために使用されます。

*   **役割**: リライトルールが適用され、元のSSA値が新しい、より最適化されたSSA値に置き換えられる際、元の値は「デッド」になるべきです。`clobber(v)`は、値`v`を`OpInvalid`（無効なオペレーション）にリセットし、その使用カウントを実質的にゼロにする効果があります。これにより、コンパイラのデッドコード削除フェーズで、その値が安全に削除されることが保証されます。
*   **`Uses == 1`との連携**: 多くの最適化ルールは、`x.Uses == 1`という条件を含みます。これは、値`x`が一度しか使われていない場合にのみ最適化を適用するという意味です。`clobber(x)`をこの条件と組み合わせることで、`x`がその最適化ルールによって「消費」され、それ以降は使われないことをより厳密に保証できます。

### ロードとストア操作

*   **ロード (Load)**: メモリからデータを読み込む操作。`MOVBload` (バイトロード), `MOVWload` (ワードロード), `MOVLload` (ロングワードロード), `MOVQload` (クアッドワードロード) などがあります。
*   **ストア (Store)**: メモリにデータを書き込む操作。`MOVBstore` (バイトストア), `MOVWstore` (ワードストア), `MOVLstore` (ロングワードストア), `MOVQstore` (クアッドワードストア) などがあります。
*   **インデックス付きロード/ストア**: `MOVBloadidx1`のように、ベースアドレスにインデックスを加えてアクセスする操作。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおけるAMD64アーキテクチャ向けのリライトルールに焦点を当てています。

### 1. ストア結合の最適化

`src/cmd/compile/internal/ssa/gen/AMD64.rules`および`src/cmd/compile/internal/ssa/rewriteAMD64.go`に、バイトストアをワードストア、ロングワードストア、クアッドワードストアに結合する新しいリライトルールが多数追加されています。

**例: 連続するバイトストアをワードストアに結合**

```
(MOVBstore [i] {s} p (SHRQconst [8] w) x:(MOVBstore [i-1] {s} p w mem))
  && x.Uses == 1
  && clobber(x)
  -> (MOVWstore [i-1] {s} p w mem)
```
このルールは、以下のようなパターンを検出します。
*   アドレス`i`に`w`の8ビット右シフト値をストアする`MOVBstore`。
*   その直前（`mem`引数で示されるメモリ状態）に、アドレス`i-1`に`w`をストアする`MOVBstore` `x`が存在する。
*   `x`が一度しか使用されていない (`x.Uses == 1`)。
*   `x`が`clobber`される（無効化される）。

これらの条件が満たされる場合、2つの`MOVBstore`を1つの`MOVWstore`（ワードストア）に結合します。これにより、2回のバイト書き込みが1回のワード書き込みに置き換えられ、効率が向上します。同様のルールが、定数ストア (`MOVBstoreconst`) やインデックス付きストア (`MOVBstoreidx1`)、さらに大きな幅（MOVLstore, MOVQstore）に対しても追加されています。

### 2. `clobber()`関数の導入

`src/cmd/compile/internal/ssa/rewrite.go`に`clobber()`関数が追加されました。

```go
// clobber invalidates v.  Returns true.
// clobber is used by rewrite rules to:
//   A) make sure v is really dead and never used again.
//   B) decrement use counts of v's args.
func clobber(v *Value) bool {
	v.reset(OpInvalid)
	// Note: leave v.Block intact.  The Block field is used after clobber.
	return true
}
```
この関数は、引数として渡されたSSA値`v`のオペレーションを`OpInvalid`に設定します。これにより、`v`は無効な値としてマークされ、コンパイラの後続のフェーズでデッドコードとして認識され、削除される準備が整います。`clobber()`は常に`true`を返すため、リライトルールの条件式内で簡単に使用できます。

### 3. ロード最適化ルールの修正と`clobber()`の適用

既存のロード最適化ルール（例: `MOVBQSX`や`MOVBQZX`などの符号拡張/ゼロ拡張ロード）にも`clobber(x)`条件が追加されています。

**例: `MOVBQSX`ロードのルール修正**

変更前:
```
(MOVBQSX x:(MOVBload [off] {sym} ptr mem)) && x.Uses == 1 -> @x.Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)
```
変更後:
```
(MOVBQSX x:(MOVBload [off] {sym} ptr mem)) && x.Uses == 1 && clobber(x) -> @x.Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)
```
この変更は、元の`MOVBload`値`x`が、`MOVBQSXload`というより最適化されたロードに置き換えられた後、完全にデッドになることを`clobber(x)`によって保証します。これにより、元のロード`x`やそれに依存する中間値が、意図せず他の場所で再利用されることを防ぎ、特にIssue #14267で指摘されたようなバグを防ぎます。

また、バイトロードをワード、ロングワード、クアッドワードロードに結合するルールにも`clobber`が追加されています。これは、`encoding/binary.LittleEndian`のようなバイト列から整数を構築するパターンを最適化するものです。

**例: 2つのバイトロードを1つのワードロードに結合**

```
(ORW                  x0:(MOVBload [i]   {s} p mem)
    s0:(SHLWconst [8] x1:(MOVBload [i+1] {s} p mem)))
  && x0.Uses == 1
  && x1.Uses == 1
  && s0.Uses == 1
  && mergePoint(b,x0,x1) != nil
  && clobber(x0)
  && clobber(x1)
  && clobber(s0)
  -> @mergePoint(b,x0,x1) (MOVWload [i] {s} p mem)
```
このルールでは、`x0`, `x1` (元のバイトロード) および`s0` (シフト操作) の全てが`clobber`されることで、これらの値が最適化後に完全に無効化され、安全に`MOVWload`に置き換えられることが保証されます。

### 4. `dupLoad.go`のテストケース

`src/cmd/compile/internal/gc/testdata/dupLoad.go`には、ロードに関するバグを再現し、修正を検証するためのテストケースが追加されています。`read1`と`read2`関数は、それぞれ異なるバイト位置から読み込み、それを結合して`uint16`を生成するパターンを示しています。`main1`と`main2`は、これらの関数を並行して実行し、データの整合性が保たれることを確認します。このテストは、小さなロードが最適化された際に、その中間値が正しく処理されることを保証するために重要です。

## コアとなるコードの解説

### `clobber`関数の役割

`clobber`関数は、SSAリライトルールが適用された際に、元のSSA値が「デッド」であることを明示的にマークするために導入されました。SSAでは、各値は一度だけ定義されますが、最適化によってある値が別の値に置き換えられることがあります。このとき、元の値がもはや必要ないことをコンパイラに伝える必要があります。`clobber(v)`を呼び出すことで、`v`のオペレーションが`OpInvalid`に設定され、その値が後続のデッドコード削除フェーズで安全に除去されるようになります。

### リライトルールにおける`clobber(x)`の追加

既存のロード最適化ルールや新しく追加されたストア結合ルールにおいて、条件式に`&& clobber(x)`が追加されたことは非常に重要です。

*   **安全性と正確性の向上**: `x.Uses == 1`という条件だけでは、`x`がそのルールによって消費された後、`x`に依存する他の値がまだ存在しないことを完全に保証できませんでした。特に、`x`が中間的な計算結果であり、その結果がさらに別の場所で使われている場合、`x`を単純に置き換えると問題が発生する可能性がありました。`clobber(x)`を追加することで、`x`がリライトによって無効化され、その使用カウントが適切に処理されるため、元の値が「デッド」であることがより厳密に保証されます。これにより、最適化がプログラムのセマンティクスを破壊することなく、安全に実行できるようになります。
*   **デッドコード削除の促進**: `clobber`された値は`OpInvalid`となるため、コンパイラのデッドコード削除パスで効率的に除去されます。これにより、生成される機械語コードから不要な命令が削減され、コードサイズと実行速度の両面でメリットがあります。
*   **Issue #14267の修正**: ロードに関するバグは、まさに「小さなロードに依存する全ての中間値が他の用途を持たないこと」を保証する必要があるという問題でした。`clobber()`の導入と、ロード最適化ルールへのその適用は、この厳密な保証を提供し、バグを修正する上で中心的な役割を果たします。

### ストア結合ルールの動作

新しく追加されたストア結合ルールは、連続するバイトストアをより大きなストアに変換します。例えば、メモリ上の隣接する2バイトにそれぞれ値を書き込む2つの`MOVBstore`操作があった場合、これらを1つの`MOVWstore`操作に変換します。この際、元の2つの`MOVBstore`操作は`clobber`され、新しい`MOVWstore`がそれらを置き換えます。これにより、メモリへのアクセス回数が減り、CPUの効率的なメモリ操作が可能になります。

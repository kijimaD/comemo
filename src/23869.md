# [インデックス 23869] ファイルの概要

このコミットは、Go言語の標準ライブラリ `encoding/json` パッケージ内のJSONスキャナーにおける不要なメモリ割り当てを削減することを目的としています。具体的には、`nextValue()` 関数がJSON構造のサブスキャンを行う際に、本来エラーではない状況で誤ってエラーメッセージのためのメモリを割り当ててしまう問題を解決しています。これにより、特に特定のJSON構造のデコード性能が向上しています。

## コミット

```
encoding/json: Remove extra allocation in scanner.

When the scanner receives a non-whitespace character in stateEndTop,
it creates an error message and caches it to return on the next
transition. nextValue() uses the scanner to sub-scan for a value
inside a larger JSON structure. Since stateEndTop is triggered
*after* the ending byte, whatever character immediately follows the
sub-value gets pulled into the scanner's state machine as well.
Even though it is not used and doesn't cause an error, it does
cause the state machine to allocate an error that will never be used.

The fix is to probe the state machine with whitespace after
scanEndObject or scanEndArray to see whether the next character would
result in a scanEnd state transition. If so, we can return right
away without processing the next character and avoid triggering
an allocation.
```

## 変更の背景

Goの `encoding/json` パッケージは、JSONデータのエンコードとデコードを扱うための標準ライブラリです。このパッケージの内部には、JSON文字列を解析するためのステートマシンベースのスキャナーが存在します。

`nextValue()` 関数は、より大きなJSON構造の一部として、特定のJSON値（オブジェクト、配列、文字列など）をサブスキャンするために使用されます。このスキャナーは、JSON値の終端を検出した後、`stateEndTop` という状態に遷移します。問題は、この `stateEndTop` 状態で、JSON値の直後に非空白文字が続く場合に発生していました。

通常、JSON値の後に非空白文字が続くのは構文エラーですが、`nextValue()` がサブスキャンを行う場合、その非空白文字は親のJSON構造の一部であり、サブスキャンにとっては「次の文字」に過ぎません。しかし、スキャナーはこれをエラーと誤解し、エラーメッセージを生成してキャッシュしていました。このエラーメッセージは実際には使用されないにもかかわらず、メモリ割り当て（アロケーション）が発生していました。

この不要なアロケーションは、特にJSONのデコード処理が頻繁に行われるアプリケーションにおいて、パフォーマンスのオーバーヘッドとなっていました。コミットメッセージに記載されているベンチマーク結果 (`BenchmarkIssue10335` でアロケーションが63.64%削減) が示すように、この問題は無視できないものでした。この変更は、この無駄なメモリ割り当てを排除し、JSONデコードの効率を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **JSON (JavaScript Object Notation)**: 軽量なデータ交換フォーマット。キーと値のペアの集まり（オブジェクト）と、順序付けられた値のリスト（配列）を基本構造とします。
2.  **Go `encoding/json` パッケージ**: Go言語でJSONデータを扱うための標準ライブラリ。`json.Marshal` でGoのデータ構造をJSONに変換（エンコード）し、`json.Unmarshal` でJSONをGoのデータ構造に変換（デコード）します。
3.  **JSONスキャナー**: `encoding/json` パッケージの内部で、入力されたJSONバイト列を解析し、その構造を識別する役割を担うコンポーネントです。これは通常、ステートマシンとして実装されており、入力文字に応じて状態を遷移させながらJSONのトークン（文字列、数値、ブール値、null、オブジェクトの開始/終了、配列の開始/終了など）を認識します。
4.  **ステートマシン**: 有限個の状態を持ち、現在の状態と入力イベントに基づいて次の状態に遷移する抽象機械。JSONスキャナーでは、各文字が入力イベントとなり、JSONの構文規則に従って状態が変化します。
5.  **`scanner` 構造体**: `encoding/json` パッケージ内のスキャナーの実装を表す構造体。現在のスキャン状態やエラー情報などを保持します。
6.  **`nextValue()` 関数**: `encoding/json` パッケージ内で使用される内部関数で、JSONバイト列から次のJSON値（オブジェクト、配列、文字列など）を抽出する役割を担います。これは、より大きなJSON構造の一部を解析する「サブスキャン」のシナリオで特に重要です。
7.  **スキャナーの状態定数**:
    *   `scanEndTop`: JSON値の解析が完了し、トップレベルのJSON構造の終端に達したことを示す状態。
    *   `scanEndObject`: JSONオブジェクトの終端（`}`）を検出した後の状態。
    *   `scanEndArray`: JSON配列の終端（`]`）を検出した後の状態。
    *   `scanEnd`: JSON値の解析が正常に完了したことを示す最終状態。
    *   `scanError`: スキャン中にエラーが発生したことを示す状態。
8.  **メモリ割り当て (Allocation)**: プログラムが実行時にメモリを要求し、OSから割り当てられる操作。Goではガベージコレクションによって不要なメモリは自動的に解放されますが、不要なアロケーションはガベージコレクションの頻度を増やし、アプリケーションのパフォーマンスに影響を与える可能性があります。

## 技術的詳細

このコミットが解決しようとしている問題は、`encoding/json` スキャナーの `nextValue()` 関数が、JSON構造のサブスキャンを行う際に発生する特定のシナリオにおける不要なエラーオブジェクトの割り当てです。

`nextValue()` 関数は、与えられたバイト列から単一のJSON値を解析します。解析が完了すると、スキャナーは `scanEndObject` または `scanEndArray` のような終端状態に達します。しかし、この関数がより大きなJSONドキュメントの一部を解析している場合、抽出されたJSON値の直後には、親のJSON構造の一部である別の文字（例えば、オブジェクト内の次のキーの開始を示す `,` や、親オブジェクトの終了を示す `}` など）が続くことがあります。

コミット前の実装では、スキャナーが `scanEndObject` や `scanEndArray` の状態に達した後、次の文字を読み込み、それが非空白文字であると `stateEndTop` に遷移し、そこでエラーメッセージを生成してキャッシュしていました。これは、トップレベルのJSONドキュメントの終端で非空白文字が続く場合は確かにエラーですが、`nextValue()` がサブスキャンを行っている場合は、その文字はエラーではなく、単に親のJSON構造の一部であるため、このエラーメッセージは決して使用されません。しかし、エラーメッセージの生成とキャッシュのためにメモリが割り当てられていました。

このコミットの修正は、この不要なアロケーションを回避するために、`scanEndObject` または `scanEndArray` の状態に達した直後に、スキャナーに対して「空白文字」をプローブ（試行的に与える）するという巧妙な手法を導入しています。

具体的には、以下のロジックが追加されました。
1.  スキャナーが `scanEndObject` または `scanEndArray` の状態に遷移したことを検出する。
2.  この時点で、スキャナーの `step` メソッドに仮の空白文字 (`' '`) を与えて、次の状態遷移をシミュレートする。
3.  もしこのシミュレーションの結果、スキャナーが `scanEnd` 状態に遷移するならば、それは現在のJSON値の解析が完全に終了し、次の文字が何であれ、このサブスキャンは完了したと判断できる。
4.  この場合、`nextValue()` は直ちに現在のJSON値のバイト列と残りのバイト列を返して終了する。これにより、実際の次の文字がスキャナーに渡される前に処理が中断され、`stateEndTop` での不要なエラーアロケーションが回避されます。

この変更により、スキャナーは実際にエラーが発生するまでエラーオブジェクトを割り当てなくなり、特にネストされたJSON構造のデコードにおいて、メモリ使用量とガベージコレクションの負荷が軽減され、パフォーマンスが向上します。ベンチマーク結果の `BenchmarkIssue10335` の `allocs` と `bytes` の大幅な削減が、この最適化の効果を明確に示しています。

## コアとなるコードの解説

`src/encoding/json/scanner.go` の変更点に注目します。

元のコードでは、`if v >= scanEnd` という条件で、スキャナーが `scanEnd` 以上の状態（つまり、JSON値の終端に達したか、エラーが発生したか）になった場合に処理を行っていました。
変更後のコードでは、この条件が `if v >= scanEndObject` に変更されています。これは、`scanEndObject` や `scanEndArray` の状態に達した時点で、特定の最適化ロジックを適用するためです。

新しい `switch v` ブロック内で、`case scanEndObject, scanEndArray:` が追加されています。
このケースでは、以下の重要なロジックが実行されます。

```go
				if scan.step(scan, ' ') == scanEnd {
					return data[:i+1], data[i+1:], nil
				}
```

*   `scan.step(scan, ' ')`: ここが「プローブ」の核心です。スキャナーの `step` メソッドに、実際の次の文字ではなく、仮の空白文字 (`' '`) を与えて呼び出しています。
*   `== scanEnd`: もし、この空白文字を処理した結果、スキャナーが `scanEnd` 状態に遷移するならば、それは現在のJSON値の解析が正常に完了したことを意味します。JSONの構文規則では、値の後に空白文字が続くことは許容されており、その後に続く文字が何であれ、現在の値の解析は完了していると判断できます。
*   `return data[:i+1], data[i+1:], nil`: この条件が真の場合、`nextValue()` 関数は直ちに現在のJSON値（`data[:i+1]`）と残りのバイト列（`data[i+1:]`）を返して終了します。これにより、実際の次の文字がスキャナーに渡されることがなくなり、`stateEndTop` での不要なエラーアロケーションが回避されます。

この変更により、スキャナーはJSON値の終端を検出した直後に、次の文字が空白文字であるかのように振る舞いをシミュレートし、その結果に基づいて早期にリターンすることで、無駄なエラーオブジェクトの生成を防いでいます。

`src/encoding/json/bench_test.go` に追加された `BenchmarkIssue10335` は、この最適化の効果を具体的に示すためのものです。
`j := []byte(`{"a":{ }}`)` というJSON文字列は、空のオブジェクト `{}` がネストされており、この空のオブジェクトのデコード時に、`nextValue()` がサブスキャンを行い、その直後に親オブジェクトの `}` が続くという、まさにこのコミットが解決するシナリオを再現しています。`b.ReportAllocs()` を使用することで、このベンチマークはメモリ割り当ての回数を報告し、最適化の効果を定量的に評価できるようにしています。

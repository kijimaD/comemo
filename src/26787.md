# [インデックス 26787] ファイルの概要

このコミットはGoランタイムのスケジューラにおける`dropg`関数の挙動を修正するものです。具体的には、`g` (goroutine) と `m` (OSスレッド) の関連付けを解除する際に、`m.lockedg`が設定されているかどうかに関わらず、常に`m.curg`を`nil`に設定するように変更しています。これにより、`lockedg`を持つ`m`と持たない`m`の間で`g/m`の関連付け解除の挙動が統一され、スケジューラの健全性チェックやデバッグ時の混乱が解消されます。

## 変更の背景

Goランタイムのスケジューラでは、`g` (goroutine) と `m` (OSスレッド) の関連付けを管理しています。`dropg`関数は、現在実行中のgoroutineがOSスレッドから切り離される際に呼び出され、`m.curg` (現在のOSスレッドが実行しているgoroutine) を`nil`に設定することで関連付けを解除します。

しかし、このコミット以前の`dropg`関数には、`m.lockedg`が設定されている場合（つまり、特定のgoroutineにロックされたOSスレッドの場合）には`m.curg`の関連付け解除を行わないという特殊なロジックが存在しました。コミットメッセージによると、この区別は不要であり、いくつかの問題を引き起こしていました。

1.  **誤解の招き**: `lockedg`の有無で挙動が異なることが、この区別が何らかの理由で必要であるという誤った認識を生じさせていました。
2.  **健全性チェックの妨げ**: `execute`関数でgoroutineが再開される際に`g/m`の関連付けが再確立されますが、その前に`g/m`が「関連付け解除されている」ことを前提とする健全性チェックやクロスチェックがある場合、`lockedg`を持つ`m`ではこのチェックが失敗する可能性がありました。コミットの作者であるDmitry Vyukov氏は、レース検出器の変更中にこの問題に遭遇したと述べています。特に、goroutineがデスケジュールされ、スケジューラコードが実行される際、通常`m.curg`は`nil`になるべきですが、`lockedg`を持つ`m`ではそうならないことがありました。

これらの問題を解決し、スケジューラのロジックを簡素化し、一貫性を持たせるために、`lockedg`の有無に関わらず常に`m.curg`を`nil`に設定する変更が提案されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラにおける以下の概念を理解しておく必要があります。

*   **Goroutine (g)**: Go言語における軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のgoroutineを同時に実行できます。
*   **Machine (m)**: OSスレッドを表します。Goランタイムは、OSスレッド上でgoroutineを実行します。
*   **Processor (p)**: 論理プロセッサを表します。Goスケジューラは、`p`を介して`g`を`m`に割り当てます。`p`は、`g`を実行するためのコンテキスト（スケジューラキュー、ローカルランキューなど）を提供します。
*   **M:Nスケジューリング**: Goランタイムは、M個のgoroutineをN個のOSスレッドにマッピングするM:Nスケジューリングモデルを採用しています。
*   **`m.curg`**: 現在そのOSスレッド (`m`) で実行されているgoroutine (`g`) へのポインタです。
*   **`m.lockedg`**: 特定のgoroutineがOSスレッドに「ロック」されている場合に設定されるポインタです。これは、Cgo呼び出しや特定のシステムコールなど、OSスレッドが特定のgoroutineに専有される必要がある場合に発生します。`lockedg`が設定されている間、そのOSスレッドは他のgoroutineを実行できません。
*   **`dropg()`**: 現在実行中のgoroutineがOSスレッドから切り離される際に呼び出されるランタイム関数です。例えば、goroutineがブロックされたり、スケジューラに制御を戻したりする場合に利用されます。この関数は、`m.curg`を`nil`に設定することで、OSスレッドとgoroutineの関連付けを解除します。
*   **`execute()`**: スケジューラが新しいgoroutineをOSスレッドに割り当てて実行を開始する際に呼び出されるランタイム関数です。この関数は、`m.curg`を新しいgoroutineに設定し、`g/m`の関連付けを確立します。

## 技術的詳細

変更前の`dropg`関数は以下のようになっていました。

```go
func dropg() {
	_g_ := getg()

	if _g_.m.lockedg == nil { // ここで条件分岐
		_g_.m.curg.m = nil
		_g_.m.curg = nil
	}
}
```

このコードでは、`_g_.m.lockedg`が`nil`でない場合（つまり、現在のOSスレッドが特定のgoroutineにロックされている場合）、`_g_.m.curg.m = nil`と`_g_.m.curg = nil`の行が実行されませんでした。これは、`lockedg`を持つ`m`は常に同じ`g`を実行し続けるため、`dropg`が呼ばれても`m.curg`を`nil`にする必要がない、あるいは`execute`で再割り当てされる際に自動的に上書きされるため問題ない、という考えがあったのかもしれません。

しかし、コミットメッセージが指摘するように、`execute`関数は常に`g/m`の関連付けを再確立します。つまり、`dropg`が呼ばれた後に`execute`が呼ばれるのであれば、`dropg`で`m.curg`を`nil`に設定するかどうかは、最終的な`g/m`の関連付けには影響しません。

この「不要な区別」が問題となるのは、スケジューラの内部状態の整合性をチェックするようなコードや、デバッグ時に`m.curg`が`nil`であることを期待するような状況です。例えば、`execute`が`g/m`を再関連付ける前に、`m.curg`が`nil`であることをアサートするようなチェックがあった場合、`lockedg`を持つ`m`ではこのアサートが失敗してしまいます。これは、`m.curg`が`nil`でないにもかかわらず、その`g`が実際には実行されていない（デスケジュールされている）という矛盾した状態を示唆するため、混乱を招きます。

このコミットは、この条件分岐を削除し、`lockedg`の有無に関わらず常に`m.curg`を`nil`に設定するように変更することで、この問題を解決しています。

変更後の`dropg`関数は以下のようになります。

```go
func dropg() {
	_g_ := getg()

	_g_.m.curg.m = nil // 条件分岐なしで常に実行
	_g_.m.curg = nil   // 条件分岐なしで常に実行
}
```

これにより、`dropg`が呼び出された際には、OSスレッドとgoroutineの関連付けが常に明確に解除されるようになります。これは、スケジューラの内部状態の一貫性を高め、将来的なデバッグやランタイムの変更を容易にする効果があります。

## コアとなるコードの解説

変更は`dropg`関数内の`if _g_.m.lockedg == nil`という条件分岐を削除し、その内部にあった`_g_.m.curg.m = nil`と`_g_.m.curg = nil`の2行を無条件に実行するようにした点です。

*   `_g_ := getg()`: 現在実行中のgoroutine (`g`) を取得します。Goランタイムの内部では、`g`構造体が現在の実行コンテキストを保持しています。
*   `_g_.m`: 現在のgoroutineが実行されているOSスレッド (`m`) を指します。
*   `_g_.m.curg`: 現在のOSスレッド (`m`) が実行しているgoroutine (`g`) へのポインタです。
*   `_g_.m.curg.m = nil`: `g`から`m`への逆参照を`nil`に設定します。これにより、goroutineがどのOSスレッドにも関連付けられていない状態になります。
*   `_g_.m.curg = nil`: `m`から`g`への参照を`nil`に設定します。これにより、OSスレッドがどのgoroutineも実行していない状態になります。

この変更により、`dropg`が呼び出されると、そのOSスレッドは現在実行中のgoroutineとの関連付けを完全に解除します。`lockedg`の有無による特殊な挙動がなくなることで、スケジューラの状態管理が一貫し、より予測可能になります。これは、特にランタイムのデバッグや、レース検出器のような複雑なツールを開発する際に、状態の推論を容易にする上で重要です。

# [インデックス 21318] ファイルの概要

このコミットは、Go言語の `encoding/base64` パッケージに、パディングなしのBase64エンコーディングのサポートを追加し、既存のテストスイートを拡張してすべてのエンコーディングタイプを網羅するように改善したものです。これにより、特定のアプリケーション要件やRFC 4648に準拠した、より柔軟なBase64処理が可能になりました。

## コミット

```
encoding/base64: add unpadded encodings, and test all encodings.

Some applications use unpadded base64 format, omitting the trailing
'=' padding characters from the standard base64 format, either to
minimize size or (more justifiably) to avoid use of the '=' character.
Unpadded flavors are standard and documented in section 3.2 of RFC 4648.

To support these unpadded flavors, this change adds two predefined
encoding variables, RawStdEncoding and RawURLEncoding, for unpadded
encodings using the standard and URL character set, respectively.
The change also adds a function WithPadding() to customize the padding
character or disable padding in a custom Encoding.

Finally, I noticed that the existing base64 test-suite was only
exercising the StdEncoding, and not referencing URLEncoding at all.
This change adds test-suite functionality to exercise all four encodings
(the two existing ones and the two new unpadded flavors),
although it still doesn't run *every* test on all four encodings.

Naming: I used the "Raw" prefix because it's more concise than "Unpadded"
and seemed just as expressive, but I have no strong preferences here.
Another short alternative prefix would be "Min" ("minimal" encoding).
```

## 変更の背景

Base64エンコーディングは、バイナリデータをASCII文字列形式に変換するための一般的な手法です。しかし、標準的なBase64エンコーディングでは、エンコードされた出力が4文字の倍数になるように、末尾にパディング文字（通常は`=`）が追加されます。

このパディングは、デコード時にデータの完全性を保証するために重要ですが、一部のアプリケーションでは問題となる場合があります。例えば、URLやファイル名にBase64エンコードされたデータを使用する場合、`=`文字は特別な意味を持つため、エンコードされた文字列がURLの一部として正しく解釈されない可能性があります。また、データサイズを最小限に抑えたい場合にも、パディング文字は不要なオーバーヘッドとなります。

RFC 4648（"The Base16, Base32, and Base64 Data Encodings"）のセクション3.2では、パディングを省略したBase64形式が標準として定義されており、多くのシステムで利用されています。このコミットは、Go言語の `encoding/base64` パッケージが、このようなパディングなしのBase64形式をネイティブにサポートすることで、他のシステムとの相互運用性を向上させ、開発者が手動でパディングの処理を行う必要をなくすことを目的としています。

また、既存のテストスイートが `StdEncoding` のみしかテストしておらず、`URLEncoding` を含め、他のエンコーディングタイプが十分に検証されていないという問題も認識されていました。このコミットは、新しいパディングなしのエンコーディングだけでなく、既存の `URLEncoding` も含め、すべてのエンコーディングタイプが適切にテストされるように、テストカバレッジを改善することも目的としています。

## 前提知識の解説

### Base64エンコーディング

Base64は、バイナリデータをASCII文字列のサブセットに変換するエンコーディングスキームです。主に、バイナリデータをテキストベースのプロトコル（例: 電子メール、HTTP）で安全に転送するために使用されます。Base64は、入力の3バイトを4つの6ビットグループに分割し、それぞれを64文字のアルファベット（A-Z, a-z, 0-9, +, /）のいずれかにマッピングします。

### Base64のパディング

Base64エンコーディングでは、入力データのバイト数が3の倍数でない場合、出力が4文字の倍数になるようにパディングが行われます。これは、エンコードされた文字列の長さを固定し、デコード時に元のバイト数を正確に復元するために必要です。パディングには通常、`=`文字が使用されます。

*   入力が3バイトの倍数の場合: パディングなし。
*   入力が3バイトの倍数 + 1バイトの場合: 2つの`=`でパディングされます（例: `A` -> `QQ==`）。
*   入力が3バイトの倍数 + 2バイトの場合: 1つの`=`でパディングされます（例: `AB` -> `QUI=`）。

### RFC 4648

RFC 4648は、Base16、Base32、Base64のデータエンコーディングを定義するIETF（Internet Engineering Task Force）の標準ドキュメントです。このRFCは、これらのエンコーディングスキームの標準的な実装方法と、パディングの有無を含む様々なバリエーションについて記述しています。特に、セクション3.2では、パディングを省略したBase64形式が言及されており、これは「unpadded Base64」または「raw Base64」として知られています。

### Go言語の `encoding/base64` パッケージ

Go言語の標準ライブラリには、Base64エンコーディングとデコーディングを扱う `encoding/base64` パッケージが含まれています。このパッケージは、`StdEncoding`（標準Base64）と `URLEncoding`（URLおよびファイル名に適したBase64）を提供しています。これまでは、これらのエンコーディングはデフォルトでパディングを使用する形式でした。

## 技術的詳細

このコミットは、Go言語の `encoding/base64` パッケージに以下の主要な変更を導入しました。

1.  **パディング文字のカスタマイズと無効化**:
    *   `Encoding` 構造体に `padChar rune` フィールドが追加されました。これにより、エンコーディングが使用するパディング文字を内部的に保持できるようになります。
    *   `StdPadding` (`=`) と `NoPadding` (`-1`) という新しい `rune` 定数が導入されました。`NoPadding` はパディングを無効にするための特別な値です。
    *   `WithPadding(padding rune) *Encoding` メソッドが `Encoding` 型に追加されました。このメソッドは、既存の `Encoding` オブジェクトを基に、指定されたパディング文字（または `NoPadding`）を持つ新しい `Encoding` オブジェクトを返します。これにより、開発者は既存のエンコーディングを簡単にカスタマイズして、パディングの有無や種類を変更できるようになりました。

2.  **パディングなしのエンコーディングの追加**:
    *   `RawStdEncoding` と `RawURLEncoding` という2つの新しいグローバルな `Encoding` 変数が追加されました。
    *   `RawStdEncoding` は `StdEncoding.WithPadding(NoPadding)` を呼び出すことで作成され、標準の文字セットを使用しつつパディングを省略します。
    *   `RawURLEncoding` は `URLEncoding.WithPadding(NoPadding)` を呼び出すことで作成され、URLセーフな文字セットを使用しつつパディングを省略します。
    *   これらの新しいエンコーディングは、RFC 4648のセクション3.2で定義されているパディングなしのBase64形式に準拠しています。

3.  **エンコード/デコードロジックの変更**:
    *   `Encoding` 型の `Encode` メソッドが、`padChar` フィールドの値に基づいてパディングを行うかどうかを条件分岐するようになりました。`NoPadding` が設定されている場合、末尾の`=`文字は追加されません。
    *   `Encoding` 型の `decode` メソッドも、`padChar` フィールドを考慮してパディング文字を処理するように変更されました。これにより、パディングなしの入力も正しくデコードできるようになりました。
    *   `EncodedLen` および `DecodedLen` メソッドも、`padChar` が `NoPadding` の場合に異なる計算ロジックを使用するように更新されました。これにより、パディングの有無に応じて正確なエンコード/デコード後の長さを計算できます。

4.  **テストスイートの改善**:
    *   `src/encoding/base64/base64_test.go` に、`encodingTest` 構造体と `encodingTests` スライスが追加されました。これにより、`StdEncoding`、`URLEncoding`、`RawStdEncoding`、`RawURLEncoding`、およびカスタムパディングを持つエンコーディング（`funnyEncoding`）を含む、複数のエンコーディングタイプに対してテストを簡単に実行できるようになりました。
    *   `TestEncode` および `TestDecode` 関数が、`encodingTests` スライスをループ処理し、各エンコーディングタイプに対してテストを実行するように修正されました。これにより、既存の `StdEncoding` だけでなく、すべてのエンコーディングが適切に機能することを検証できるようになりました。

これらの変更により、Go言語の `encoding/base64` パッケージは、より広範なBase64エンコーディングのユースケースに対応できるようになり、特にパディングなしの形式を必要とするアプリケーションにとって非常に有用な機能強化となりました。

## コアとなるコードの解説

### `Encoding` 構造体とパディングの管理

`Encoding` 構造体に `padChar rune` フィールドが追加されたことで、各エンコーディングインスタンスが独自のパディング文字を持つことができるようになりました。これにより、標準の`=`だけでなく、`NoPadding`（パディングなし）や、`funnyEncoding` のようなカスタムパディング文字（例: `@`）もサポート可能になります。

`StdPadding` と `NoPadding` 定数は、パディングの意図を明確にするためのものです。特に `NoPadding` は、パディングを完全に無効にするという明確なシグナルとして機能します。

### `WithPadding` メソッド

このメソッドは、既存の `Encoding` オブジェクトのコピーを作成し、その `padChar` フィールドを引数で指定された値に設定して返します。これは、Go言語におけるイミュータブルなオブジェクトの操作パターンに沿っており、既存のエンコーディングを変更せずに新しいバリエーションを作成する安全な方法を提供します。例えば、`StdEncoding.WithPadding(NoPadding)` とすることで、標準のBase64エンコーディングの文字セットを維持しつつ、パディングを省略した新しいエンコーディングを簡単に生成できます。

### `RawStdEncoding` と `RawURLEncoding`

これらの新しいグローバル変数は、開発者がパディングなしのBase64エンコーディングをすぐに利用できるようにするためのものです。これらは `WithPadding(NoPadding)` を使用して既存の標準エンコーディングから派生しており、RFC 4648のセクション3.2で定義されている形式に直接対応します。これにより、URLセーフなパディングなしのBase64や、一般的なパディングなしのBase64を扱う際に、手動でパディングを処理する手間が省けます。

### `Encode` メソッドの変更

`Encode` メソッド内のパディングロジックは、`enc.padChar` の値に基づいて条件分岐するようになりました。これにより、`NoPadding` が設定されているエンコーディングでは、エンコードされた出力の末尾に`=`文字が追加されなくなります。これは、出力のサイズを最小化したり、`=`文字が問題となる環境でBase64を使用したりする場合に不可欠な変更です。

### `decode` メソッドの変更

`decode` メソッドも同様に、`enc.padChar` を参照してパディング文字を処理します。これにより、パディングなしの入力文字列が与えられた場合でも、デコード処理が正しく行われるようになります。特に、入力の末尾にパディング文字がない場合でも、部分的な量子（quantum）を正しく解釈できるようになりました。

### `EncodedLen` と `DecodedLen` メソッドの変更

これらのメソッドは、エンコードまたはデコード後のデータの長さを計算します。パディングの有無によって計算式が異なるため、`enc.padChar == NoPadding` の条件に基づいて適切な計算ロジックが適用されるようになりました。これにより、パディングなしのBase64文字列の長さが正確に予測できるようになり、バッファの割り当てなどが最適化されます。

### テストスイートの改善

`encodingTest` 構造体と `encodingTests` スライスは、テストの網羅性を大幅に向上させます。これにより、新しい `RawStdEncoding` や `RawURLEncoding` だけでなく、既存の `URLEncoding` やカスタムパディングを持つエンコーディングも、同じテストフレームワークで検証できるようになりました。これは、コードの品質と信頼性を高める上で非常に重要です。

# [インデックス 22021] ファイルの概要

このコミットは、Go言語のツールチェインに含まれるアセンブラ（`cmd/9a` および `cmd/new9a`）におけるシンボル処理のバグ修正に関するものです。具体的には、アセンブラが特定の静的シンボル（特に名前に`<`と`>`を含むもの）に対して、正しく「静的」フラグを設定していなかった問題に対処しています。この修正により、アセンブラが生成するオブジェクトファイル内のシンボル情報が正確になり、リンカがこれらのシンボルを正しく処理できるようになります。

変更されたファイルは以下の通りです。
- `src/cmd/9a/a.y`: 古いアセンブラ (`9a`) のYacc/Bison文法定義ファイル。
- `src/cmd/9a/y.tab.c`: `src/cmd/9a/a.y` から生成されたC言語のパーサーコード。
- `src/cmd/new9a/a.y`: 新しいアセンブラ (`new9a`) のYacc/Bison文法定義ファイル（Go言語で記述されたパーサーの元となる）。
- `src/cmd/new9a/y.go`: `src/cmd/new9a/a.y` から生成されたGo言語のパーサーコード。

これらのファイルは、アセンブラがソースコードを解析し、シンボルを識別・登録するロジックを定義しています。

## 変更の背景

この変更は、Go言語のコンパイルプロセスにおけるアセンブラの挙動に関するバグ修正です。Goのツールチェインには、Go言語で書かれたコードを最終的な実行可能ファイルに変換する際に使用されるアセンブラが含まれています。このアセンブラは、特にGoのランタイムや標準ライブラリの一部で手書きのアセンブリコードを処理するために利用されます。

問題は、アセンブラ（`cmd/9a` および `cmd/new9a`）が、特定の種類のシンボル、特に名前に山括弧（`<`と`>`）を含むシンボルを処理する際に、「静的 (static)」ビットを正しく設定していなかったという「見落とし (oversight)」にありました。Goの内部では、メソッド値、クロージャ、型情報など、コンパイラが生成する特定のエンティティに対して、このような山括弧を含むシンボル名が使用されることがあります。

シンボルが「静的」であるという情報は、リンカが最終的な実行可能ファイルを生成する際に非常に重要です。静的シンボルは通常、その定義が単一のオブジェクトファイル内に閉じているか、あるいは特定のリンケージ特性を持つことを示します。このビットが正しく設定されていないと、リンカがシンボルを誤って解釈し、結果としてリンクエラー、不正な実行時動作、または最適化の機会の損失につながる可能性がありました。

このコミットは、このアセンブラの不正確な挙動を修正し、Goプログラムのビルドプロセスにおける堅牢性と正確性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. Goのツールチェインとアセンブラ (`cmd/9a`, `cmd/new9a`)

Go言語のソースコードは、`go build`コマンドによってコンパイルされ、実行可能ファイルが生成されます。このプロセスは複数の段階から成り立っており、その一部としてアセンブラが使用されます。

*   **`cmd/9a`**: これはGoの初期のバージョンで使用されていたアセンブラで、Plan 9オペレーティングシステムのアセンブラ設計に強く影響を受けています。Goのコンパイラは、Goのソースコードを中間表現に変換した後、必要に応じてアセンブリコードを生成し、`9a`のようなアセンブラがそれを機械語に変換します。
*   **`cmd/new9a`**: `9a`の後継として開発された、Go言語で書かれた新しいアセンブラです。機能的には`9a`と類似していますが、Go言語で実装されているため、Goのツールチェインとの統合がよりスムーズになっています。このコミットは、両方のアセンブラに共通するロジックの修正を含んでいます。

### 2. Plan 9アセンブラの記法とGoへの影響

Goのアセンブラは、AT&T構文やIntel構文とは異なる、Plan 9アセンブラの独特な記法を採用しています。この記法は、レジスタのプレフィックスがない、ソースとデスティネーションの順序が逆（デスティネーションが先）であるなど、いくつかの特徴があります。Goの内部では、このPlan 9スタイルのアセンブラが、ランタイムの低レベルな部分や、特定のプラットフォーム固有の最適化のために利用されています。

### 3. シンボルと静的シンボル

プログラムにおいて、シンボルとは変数、関数、ラベルなどの名前付きエンティティを指します。コンパイルおよびリンクの過程で、これらのシンボルはメモリ上の特定のアドレスに関連付けられます。

*   **シンボルテーブル**: コンパイラやアセンブラは、ソースコード内で見つかったシンボルとその属性（型、スコープ、アドレスなど）を記録するシンボルテーブルを生成します。
*   **静的シンボル (Static Symbols)**: 一般的に、静的シンボルは、その定義が単一のコンパイル単位（例：オブジェクトファイル）に限定されるか、または特定の内部リンケージを持つシンボルを指します。C言語における`static`キーワードで宣言された変数や関数がこれに該当します。Goの文脈では、パッケージレベルの変数や関数、あるいはコンパイラが内部的に生成する特定のエンティティが静的シンボルとして扱われることがあります。リンカは、静的シンボルを外部から参照できないようにしたり、重複する定義を許可したりするなど、その特性に基づいて異なる処理を行います。

### 4. `linklookup`関数

コミットの変更点に登場する`linklookup`関数は、アセンブラやリンカの内部でシンボルを管理するために使用される関数です。その名前が示す通り、「リンク時にシンボルを検索（lookup）する」役割を担っています。この関数は、シンボル名を受け取り、そのシンボルが既にシンボルテーブルに存在するかどうかを確認し、存在しない場合は新しく作成して登録します。

この関数の引数には、シンボル名に加えて、シンボルの属性（例えば、静的であるかどうか）を示すフラグが渡されることが一般的です。今回のコミットでは、このフラグの値が`0`から`1`に変更されています。これは、特定のシンボルに対して「静的」という属性を明示的に設定するための変更であると推測されます。

### 5. Yacc/Bison (`.y`ファイル) と生成されるパーサー (`.tab.c`, `.go`ファイル)

*   **Yacc (Yet Another Compiler Compiler) / Bison**: これらは、文法定義ファイル（通常`.y`拡張子を持つ）から、C言語などのプログラミング言語で書かれた構文解析器（パーサー）を自動生成するツールです。アセンブラのようなツールは、入力されたアセンブリコードの構文を解析するためにパーサーを必要とします。
*   **`.y`ファイル**: アセンブラの文法規則と、各規則が認識されたときに実行されるアクション（セマンティックアクション）が定義されています。
*   **`.tab.c` / `.go`ファイル**: `.y`ファイルからYacc/Bison（またはそのGo言語版ツール）によって生成される実際のパーサーコードです。このコードには、文法規則に基づいて入力を解析し、定義されたアクションを実行するためのロジックが含まれています。今回の変更は、`.y`ファイル内のアクション定義を変更し、それが生成される`.tab.c`や`.go`ファイルに反映されることで実現されています。

### 6. 山括弧 (`<>`) を含むシンボル

Goのコンパイラやランタイムは、内部的に特定の目的のために特殊なシンボル名を使用します。山括弧（`<`と`>`）で囲まれたシンボル名は、Goのソースコードには直接現れない、コンパイラが生成する内部的なシンボルを示す一般的な慣習です。例えば、メソッド値（`T.Method`のような形式で関数として扱われるメソッド）、クロージャ（匿名関数）、または特定の型情報に関連するシンボルなどがこれに該当することがあります。これらのシンボルは、Goの実行時型情報（RTTI）やガベージコレクション、インターフェースの実装など、ランタイムの複雑な機能の基盤となっています。

## 技術的詳細

このコミットの核心は、Goアセンブラがシンボルを処理する際の`linklookup`関数の呼び出し方における、特定の引数の値の変更です。

### 問題点

アセンブラ（`cmd/9a`と`cmd/new9a`）は、アセンブリコードを解析し、シンボルを識別してシンボルテーブルに登録する際に、`linklookup`関数を使用します。コミットメッセージによると、「`9a`における見落とし：山括弧（`<`と`>`）を持つシンボルに対して、アセンブラが静的ビットを設定していなかった」という問題がありました。

これは、例えばGoのコンパイラが生成する内部的なシンボル（例: `go.itab.*` や `type.*` など、あるいは特定のクロージャやメソッド値に関連するシンボル）が、アセンブリコード内で山括弧を含む形式で参照される場合、アセンブラがそれらを正しく「静的」としてマークしていなかったことを意味します。

シンボルが静的であるという情報は、リンカがそのシンボルをどのように扱うべきかを決定するために不可欠です。静的ビットが設定されていないと、リンカはこれらのシンボルを外部リンケージを持つものとして誤って解釈したり、あるいはシンボル解決の際に予期せぬ問題を引き起こしたりする可能性がありました。これは、最終的な実行可能ファイルの動作に影響を与えたり、ビルドエラーの原因となったりする潜在的なバグでした。

### 修正内容

修正は非常にシンプルで、`linklookup`関数を呼び出す際の最後の引数を`0`から`1`に変更することです。

変更前:
`linklookup(ctxt, $1->name, 0)`
`obj.Linklookup(asm.Ctxt, $1.Name, 0)`

変更後:
`linklookup(ctxt, $1->name, 1)`
`obj.Linklookup(asm.Ctxt, $1.Name, 1)`

この最後の引数は、シンボルの属性（この場合は「静的」であるかどうか）を示すフラグであると推測されます。`0`は「非静的」または「外部リンケージ」、`1`は「静的」または「内部リンケージ」を示すものと考えられます。この変更により、山括弧を持つシンボルが`linklookup`によって処理される際に、正しく静的ビットが設定されるようになります。

### 変更が適用される場所

この変更は、アセンブラの文法定義ファイル（`a.y`）とその生成物（`y.tab.c`、`y.go`）内の、シンボル名を処理する部分に適用されています。具体的には、`name:`という文法規則に関連するセマンティックアクション内で、シンボルが`NAME_STATIC`として識別される場合に`linklookup`が呼び出される箇所が修正されています。

*   `a.y`ファイルでは、`name:`という規則の定義内で、`NAME_STATIC`タイプのシンボルに対して`linklookup`が呼び出される部分が変更されています。
*   `y.tab.c`と`y.go`は、それぞれ`a.y`から生成されたC言語とGo言語のパーサーコードであり、`yyreduce`関数内の対応する箇所が変更されています。これは、パーサーが`name`規則を認識した際に実行されるアクションに修正が加えられたことを意味します。

この修正により、Goのコンパイラが生成する内部的な静的シンボルが、アセンブラによって正しく処理され、リンカに適切な情報が渡されるようになります。これにより、Goプログラムのビルドの信頼性が向上します。

## コアとなるコードの解説

上記のコードスニペットは、アセンブラのパーサーがシンボル名を処理する際のロジックを示しています。

*   **`name:` 規則**: これはYacc/Bisonの文法定義における規則の一つで、アセンブリコード内のシンボル名をどのように解析するかを定義しています。この規則の内部で、シンボルがメモリ参照（`TYPE_MEM`）であり、かつ静的（`NAME_STATIC`）であると判断された場合のアクションが記述されています。
*   **`$$ = nullgen;`**: これは、パーサーがこの規則を処理した結果として生成される値（セマンティック値）を初期化しています。
*   **`$$.type = TYPE_MEM;` / `$$.Type = obj.TYPE_MEM;`**: シンボルがメモリ参照であることを示します。
*   **`$$.name = NAME_STATIC;` / `$$.Name = obj.NAME_STATIC;`**: シンボルが静的であることを示します。これは、Goの内部的なシンボル（特に山括弧を含むもの）がこのカテゴリに分類されることを意味します。
*   **`$$.sym = linklookup(ctxt, $1->name, 0);` (変更前)**
*   **`$$.sym = linklookup(ctxt, $1->name, 1);` (変更後)**
    *   `linklookup` (または `obj.Linklookup` for `new9a`) は、シンボルテーブル内で`$1->name`（または`$1.Name`）で指定されたシンボル名を検索または登録する関数です。
    *   `ctxt` (または `asm.Ctxt`) は、コンテキスト情報（例えば、現在のオブジェクトファイルやリンカの状態）を保持するオブジェクトです。
    *   `$1->name` (または `$1.Name`) は、解析されたシンボル名自体を指します。
    *   **最後の引数 `0` から `1` への変更**: これがこのコミットの最も重要な部分です。この引数は、`linklookup`関数に対して、シンボルが静的であるという追加情報を提供します。`0`は「非静的」または「デフォルトのリンケージ」を意味し、`1`は「静的」または「内部リンケージ」を意味すると考えられます。この変更により、山括弧を持つ静的シンボルが正しく静的としてマークされ、リンカがそれらを適切に処理できるようになります。
*   **`$$.offset = $4;`**: シンボルのオフセット（メモリ上の位置）を設定します。

要するに、このコードはアセンブラがアセンブリコード内のシンボル定義を解析し、そのシンボルが静的であると判断した場合に、`linklookup`関数を呼び出してシンボルテーブルに登録する際の「静的」フラグを修正しています。これにより、Goの内部的な静的シンボルが、ビルドプロセス全体で正しく扱われるようになります。

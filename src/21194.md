このコミットは、Goリンカー (`cmd/ld`) におけるリンクモードの決定ロジックを修正し、特に `runtime/cgo` パッケージのインポート判断が正しく行われるようにすることを目的としています。既存のコードでは、リンクモードが最終的に決定される前に `runtime/cgo` のインポート有無がチェックされており、これがAndroidのような特定のプラットフォームで問題を引き起こす可能性がありました。この変更により、リンクモードの決定が `runtime/cgo` のインポートチェックよりも先行するようにコードの順序が調整され、リンカーの動作の堅牢性が向上しました。

## 変更の背景

このコミットの背景には、GoプログラムがC言語のコードと連携するための `cgo` 機能と、Goリンカーの動作に関する問題がありました。コミットメッセージによると、作者はiOSへのGoのポーティング作業中にこの問題を発見しました。既存のリンカーのロジックでは、`linkmode` (リンクモード) の最終的な決定が、`runtime/cgo` パッケージがインポートされているかどうかのチェックよりも後に行われていました。

特にAndroidのようなプラットフォームでは、`cgo` を使用する場合、リンカーは強制的に `LinkExternal` モードで動作する必要があります。しかし、`linkmode` がまだ `LinkAuto` の状態であるにもかかわらず `runtime/cgo` のインポート有無がチェックされると、リンカーが誤った判断を下し、結果としてリンクエラーや予期せぬ動作を引き起こす可能性がありました。コミットメッセージの「Frankly, I don't understand how the current code could possibly work except when every android program is using cgo.」という記述は、このロジックの欠陥が、Android上で `cgo` を使用しないプログラムのリンクを困難にしていたことを示唆しています。

この変更は、リンカーが `runtime/cgo` のインポート有無に基づいて適切な処理を行う前に、`linkmode` が常に正しい最終状態になっていることを保証することで、この問題を解決しようとしています。

## 前提知識の解説

このコミットを理解するためには、以下のGoのビルドシステムとリンカーに関する知識が必要です。

*   **Goリンカー (`cmd/ld`)**: Go言語のコンパイラツールチェーンの一部であり、コンパイルされたGoのオブジェクトファイルと必要なライブラリを結合して実行可能ファイルを生成する役割を担います。
*   **`cgo`**: GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムを提供するGoの機能です。`cgo` を使用すると、既存のCライブラリを利用したり、OS固有のAPIにアクセスしたりすることが可能になります。
*   **`runtime/cgo` パッケージ**: `cgo` 機能が有効になっているGoプログラムに自動的にインポートされる内部パッケージです。このパッケージは、GoとCの間の呼び出し規約やメモリ管理の橋渡しを行います。
*   **リンクモード (`linkmode`)**: Goリンカーが実行可能ファイルを生成する際に使用するリンク方式を指します。主なモードは以下の通りです。
    *   **`LinkInternal` (内部リンク)**: Goリンカーがすべての依存関係を自身で解決し、単一の静的バイナリを生成するモードです。Goの標準的なビルドでよく使用されます。
    *   **`LinkExternal` (外部リンク)**: Goリンカーが最終的なリンク処理をシステムのCリンカー (例: `gcc` や `clang`) に委譲するモードです。`cgo` を使用する場合や、特定のシステムライブラリにリンクする必要がある場合に用いられます。外部リンカーは、C++の機能（グローバルコンストラクタ/デストラクタ、例外処理など）や、複雑なシステムライブラリのリンクを処理するのに適しています。
    *   **`LinkAuto` (自動リンク)**: リンカーが状況に応じて `LinkInternal` または `LinkExternal` を自動的に選択するモードです。通常、`cgo` が使用されている場合は `LinkExternal` が選択されます。
*   **Android/iOSポーティング**: Go言語のプログラムをAndroidやiOSといったモバイルプラットフォームで動作させるための移植作業です。これらのプラットフォームでは、GoコードがネイティブのUIフレームワークやシステムサービスと連携する必要があるため、`cgo` を介したC/Objective-C/Swiftとの相互運用が不可欠となることが多いです。`gomobile` ツールなどがこのプロセスを支援します。

## 技術的詳細

このコミットの技術的な核心は、Goリンカー (`cmd/ld`) の `loadlib` 関数内のコードブロックの順序変更にあります。`loadlib` 関数は、リンカーがライブラリをロードし、リンクモードを決定する主要な部分です。

変更前のコードでは、以下の順序で処理が行われていました。

1.  ロードされたライブラリの中に `runtime/cgo` が含まれているか (`iscgo`) をチェックする。
2.  `linkmode` が `LinkAuto` の場合、`iscgo` の値と `externalobj` (外部オブジェクトが存在するか) に基づいて `linkmode` を `LinkExternal` または `LinkInternal` に設定する。
3.  Android向けの場合は、`linkmode` を強制的に `LinkExternal` に設定する。
4.  `linkmode == LinkExternal` かつ `!iscgo` (cgoを使用していない) の場合の特別な処理。このブロックは、`runtime/cgo` のインポート有無に依存して、スタートアップコードの動作を決定します。

問題は、ステップ4の `if(linkmode == LinkExternal && !iscgo)` の条件が評価される時点で、`linkmode` がまだ最終的な状態にない可能性があったことです。特に、Androidプラットフォームでは `linkmode` が強制的に `LinkExternal` に設定されるロジックがステップ2と3の後にありました。もし `linkmode` が `LinkAuto` のままでステップ4の条件が評価されると、リンカーは `cgo` を使用していないにもかかわらず `LinkExternal` モードでのリンクを試みたり、あるいはその逆の誤った判断を下す可能性がありました。

このコミットは、`linkmode` の最終決定ロジック（`LinkAuto` から `LinkExternal`/`LinkInternal` への変換、およびAndroidでの強制 `LinkExternal` 設定）を、`runtime/cgo` のインポート有無に基づく条件分岐の**前**に移動させました。これにより、`if(linkmode == LinkExternal && !iscgo)` のような条件が評価される際には、`linkmode` が常にその最終的かつ正しい値を持っていることが保証されます。

この修正は、特にモバイルプラットフォーム（AndroidやiOS）での `cgo` を使用しないGoプログラムのビルドの信頼性を向上させます。`cgo` を使用しないプログラムでも、リンカーが `LinkExternal` モードを誤って選択したり、`runtime/cgo` のインポートに関する誤った仮定に基づいて動作したりするのを防ぎます。

## コアとなるコードの変更箇所

変更は `src/cmd/ld/lib.c` ファイルの `loadlib` 関数内で行われています。

具体的には、以下のコードブロックが移動されました。

```c
if(linkmode == LinkAuto) {
	if(iscgo && externalobj)
		linkmode = LinkExternal;
	else
		linkmode = LinkInternal;

	// Force external linking for android.
	if(strcmp(goos, "android") == 0)
		linkmode = LinkExternal;
}
```

このブロックは、元々 `if(linkmode == LinkExternal && !iscgo)` の条件分岐の**後**にありましたが、コミットによってその**前**に移動されました。

## コアとなるコードの解説

移動されたコードブロックは、リンカーの `linkmode` 変数を最終的に決定する役割を担っています。

*   `if(linkmode == LinkAuto)`: 現在のリンクモードが自動選択 (`LinkAuto`) に設定されている場合にのみ、以下のロジックが実行されます。
*   `if(iscgo && externalobj) linkmode = LinkExternal; else linkmode = LinkInternal;`:
    *   `iscgo`: `runtime/cgo` パッケージがインポートされているかどうかを示すフラグ。
    *   `externalobj`: 外部オブジェクトファイル（C/C++など）が存在するかどうかを示すフラグ。
    *   もし `cgo` が使用されており、かつ外部オブジェクトファイルが存在する場合は、`linkmode` を `LinkExternal` に設定します。これは、`cgo` が外部リンカーとの連携を必要とすることが多いためです。
    *   それ以外の場合は、`linkmode` を `LinkInternal` に設定します。
*   `if(strcmp(goos, "android") == 0) linkmode = LinkExternal;`:
    *   現在のターゲットOSがAndroidである場合、`linkmode` を強制的に `LinkExternal` に設定します。これは、Androidプラットフォームの特性上、Goプログラムがネイティブコードと連携するために外部リンカーが必須となるためです。

このブロックを `runtime/cgo` のインポート有無に基づく条件分岐の前に配置することで、リンカーは `cgo` 関連の判断を行う際に、既にプラットフォーム固有の要件（例: Androidでの強制外部リンク）が考慮された、確定済みの `linkmode` を参照できるようになります。これにより、リンカーの動作がより予測可能で堅牢になります。

# [インデックス 24256] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における関数値シンボルの定義方法に関する変更です。特に、実装を持たない関数宣言が共有ライブラリを破損させる問題に対処し、シンボルが宣言時に適切に定義されるようにすることで、共有ライブラリの堅牢性を向上させています。

## 元コミット内容

`cmd/compile: define func value symbols at declaration`

このコミットは、Goコンパイラが関数値シンボルを宣言時に定義するように変更するものです。これは主にRuss Cox氏による`https://golang.org/cl/12145`の変更に基づいていますが、実装を持たない関数宣言が共有ライブラリを破損させるという問題に対処するための追加修正が含まれています。また、この問題を確認するためのテストケースも追加されています。

この変更は、`Fixes #11480` に関連しています。

## 変更の背景

Go言語は、その設計思想として静的リンクを強く推奨しており、デフォルトではGoプログラムは全ての依存関係（Goランタイム、標準ライブラリ、モジュールなど）を単一の実行可能ファイルに含めてコンパイルされます。これにより、高い移植性とデプロイの容易さが実現されます。

しかし、`cgo`を使用してC言語の関数を呼び出す場合や、`buildmode=c-shared`や`buildmode=shared`といったビルドモードで明示的に共有ライブラリを生成する場合には、動的リンクが必要となります。動的リンクされたプログラムやライブラリは、実行時に外部のシンボル（関数や変数など）を解決する必要があります。

このコミットが修正しようとしている問題は、「実装を持たない関数宣言が共有ライブラリを破損させる」という点にあります。これは、Goコンパイラが共有ライブラリを生成する際に、関数が宣言されているにもかかわらず、その実装が提供されていない場合に、リンカがそのシンボルを解決できずにエラーとなる、あるいは不正な状態になることを示唆しています。特に、`cgo`を介してGoの関数がCのコードから呼び出されるようなシナリオや、Goの共有ライブラリが他のGoプログラムから利用されるシナリオで問題が発生したと考えられます。

Goコンパイラは、プログラム内の識別子（関数名、変数名など）に関する情報をシンボルテーブルに格納します。このシンボルテーブルは、コンパイルおよびリンクプロセスにおいて、エラーチェック、スコープ管理、コード最適化に不可欠です。実装のない関数宣言に対してシンボルが適切に定義されない場合、共有ライブラリの生成時にリンカが期待するシンボル情報が不足し、結果としてライブラリが正しく機能しない、あるいはビルドに失敗する原因となります。

このコミットは、このような状況を防ぐために、関数が宣言された時点でそのシンボルが適切に定義されるようにコンパイラの挙動を変更することで、共有ライブラリの堅牢性と互換性を向上させることを目的としています。

## 前提知識の解説

### 1. Go言語のコンパイルとリンク

*   **静的リンク (Static Linking)**: Goのデフォルトの挙動です。全てのコード（Goランタイム、標準ライブラリ、依存モジュール）が単一の実行可能ファイルにまとめられます。これにより、実行時に外部ライブラリを必要とせず、高い移植性を持ちます。
*   **動的リンク (Dynamic Linking)**: 特定のシナリオ（`cgo`の使用、`buildmode`オプションによる共有ライブラリの生成）で発生します。この場合、実行可能ファイルは、実行時にシステム上の共有ライブラリ（例: `libc`）やGoが生成した共有ライブラリにリンクされます。
*   **シンボル (Symbol)**: プログラム内の関数、変数、型などの識別子を指します。コンパイラとリンカは、これらのシンボルを使用して、コード内の参照を実際のメモリ上のアドレスに解決します。
*   **シンボルテーブル (Symbol Table)**: コンパイラがプログラムのコンパイル中に作成するデータ構造で、シンボルとその属性（型、スコープ、アドレスなど）を記録します。リンカはこれを利用して、異なるオブジェクトファイルやライブラリ間の参照を解決します。

### 2. 共有ライブラリ (Shared Libraries)

共有ライブラリ（Linuxでは`.so`、Windowsでは`.dll`、macOSでは`.dylib`）は、複数のプログラムで共有されるコードの集合です。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が可能になります。

共有ライブラリが正しく機能するためには、そのライブラリがエクスポートする全ての関数や変数のシンボルが、ライブラリのビルド時に適切に定義され、リンカによって解決可能である必要があります。もし宣言されているにもかかわらず実装がない関数があると、そのシンボルは未解決となり、ライブラリのロードやリンクに失敗する原因となります。

### 3. `cgo`

`cgo`は、GoプログラムからC言語のコードを呼び出すためのGoの機能です。`cgo`を使用すると、GoのビルドプロセスはCコンパイラとリンカを呼び出し、結果としてGoプログラムはCライブラリに動的にリンクされることが多くなります。このため、`cgo`を使用するGoプログラムは、デフォルトの静的リンクではなく、動的リンクの特性を持つことになります。

### 4. `cmd/compile`と`gc`パッケージ

`cmd/compile`はGo言語の公式コンパイラです。その内部には、コンパイルの各ステージを処理するパッケージ群が含まれており、`internal/gc`はその中核をなすパッケージの一つで、Goソースコードの解析、型チェック、中間表現への変換、コード生成などを担当します。このコミットは、`internal/gc`パッケージ内の`closure.go`と`dcl.go`というファイルに変更を加えており、これはコンパイラの宣言処理とクロージャ処理の段階でシンボル定義の挙動を調整していることを示しています。

## 技術的詳細

このコミットの核心は、Goコンパイラが関数シンボルを「宣言時」に定義するように変更することです。以前は、関数が宣言されても、その実装が実際にコンパイルされるまで、対応するシンボルが完全に定義されないケースがあった可能性があります。これが、特に共有ライブラリの文脈で問題を引き起こしていました。

共有ライブラリは、外部から参照される可能性のある全てのシンボルについて、その定義（実装）を持っていることを期待します。もし、Goのコードで関数が宣言されているが、何らかの理由でその実装が提供されていない場合（例えば、アセンブリで実装されることを期待しているが、まだそのアセンブリコードがリンクされていない場合など）、リンカはその未定義のシンボルを見つけてエラーを報告するか、あるいは不完全なライブラリを生成してしまう可能性があります。

このコミットでは、`src/cmd/compile/internal/gc/dcl.go`内の`funchdr`関数（関数ヘッダを処理する部分）と、`makefuncsym`関数（関数シンボルを作成する部分）に修正が加えられています。

具体的には、`funchdr`関数内で、`importpkg == nil`（つまり、現在のパッケージ内で宣言されている関数）かつ`n.Func.Nname != nil`（関数名が有効である）場合に、`makefuncsym(n.Func.Nname.Sym)`を呼び出すように変更されています。これにより、関数の宣言が処理される段階で、その関数に対応するシンボルが確実に作成・定義されるようになります。

また、`src/cmd/compile/internal/gc/closure.go`内の`makeclosure`関数（クロージャを生成する部分）でも同様に、クロージャの関数シンボルが宣言時に定義されるように`makefuncsym`が呼び出されています。

`makefuncsym`関数自体も変更されており、`funcsym`関数を呼び出してシンボルを取得した後、`s1.Def = newfuncname(s1)`と`s1.Def.Func.Shortname = newname(s)`によってシンボルの定義情報を設定し、`funcsyms`リストに追加しています。これにより、シンボルが単に存在するというだけでなく、その定義がコンパイラ内部で適切に表現されるようになります。

この変更により、Goコンパイラは、共有ライブラリをビルドする際に、宣言された全ての関数に対して適切なシンボル情報を生成できるようになり、リンカが未定義シンボルで失敗するリスクが低減されます。

テストケースとして追加された`misc/cgo/testshared/src/dep/asm.s`、`misc/cgo/testshared/src/dep/gccgo.go`、`misc/cgo/testshared/src/dep/stubs.go`は、アセンブリで実装される関数（`ImplementedInAsm`）の宣言と、その利用をシミュレートしています。特に`stubs.go`では、`func ImplementedInAsm()`という実装のない宣言があり、これが共有ライブラリの文脈で問題を引き起こす可能性があったことを示唆しています。このテストケースは、今回の修正がこのようなシナリオで正しく機能することを確認するために導入されました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/dcl.go` の変更

*   **`funchdr` 関数内の `makefuncsym` 呼び出しの追加**:
    *   `funchdr`は、Goコンパイラが関数のヘッダ（宣言部分）を処理する際に呼び出される関数です。
    *   追加された`if importpkg == nil && n.Func.Nname != nil`の条件は、現在のパッケージ内で宣言されている（インポートされたものではない）かつ有効な名前を持つ関数に対してのみ処理を行うことを意味します。
    *   この条件が満たされた場合、`makefuncsym(n.Func.Nname.Sym)`が呼び出されます。これにより、関数の宣言が解析された時点で、その関数に対応するシンボルが確実に作成・定義されるようになります。以前は、この段階でシンボルが完全に定義されないことがあり、特に実装のない関数宣言が問題を引き起こしていました。

*   **`makefuncsym` 関数の新規追加と`funcsym`からのロジック移動**:
    *   `makefuncsym`は、特定のシンボル`s`に対して関数シンボルを生成し、`funcsyms`リストに追加する役割を担います。
    *   `funcsym`関数から、実際にシンボルを定義し`funcsyms`リストに追加するロジックが`makefuncsym`に移動されました。これにより、関数シンボルの定義プロセスがより明確に分離され、`funchdr`や`makeclosure`のような場所から一貫して呼び出せるようになりました。
    *   `isblanksym(s)`のチェックは、ブランク識別子（`_`）のシンボルを処理しないためのものです。
    *   `compiling_runtime != 0 && s.Name == "getg"`のチェックは、`runtime.getg()`が特別な関数であり、通常の関数シンボルとして扱われないようにするための例外処理です。

### `src/cmd/compile/internal/gc/closure.go` の変更

*   **`makeclosure` 関数内の `makefuncsym` 呼び出しの追加**:
    *   `makeclosure`は、Goコンパイラがクロージャ（匿名関数）を生成する際に呼び出される関数です。
    *   クロージャもまた関数であるため、そのシンボルが宣言時に適切に定義される必要があります。
    *   `makefuncsym(xfunc.Func.Nname.Sym)`の追加により、クロージャのシンボルも`funchdr`で処理される通常の関数と同様に、宣言時に定義されることが保証されます。

### テストケースの追加 (`misc/cgo/testshared/src/dep/asm.s`, `misc/cgo/testshared/src/dep/stubs.go`, `misc/cgo/testshared/src/dep/gccgo.go`, `misc/cgo/testshared/src/exe/exe.go`)

*   これらのファイルは、`ImplementedInAsm`という関数を例にとり、その宣言と実装が異なるファイルに存在する場合の共有ライブラリの挙動をテストするために追加されました。
*   `stubs.go`では`func ImplementedInAsm()`と宣言のみが行われ、実装は`asm.s`（アセンブリ）または`gccgo.go`（gccgoビルドの場合）で提供されます。
*   `exe.go`では、この`ImplementedInAsm`関数が`defer`文で呼び出されています。
*   このテストケースは、実装のない関数宣言が共有ライブラリのビルド時に問題を引き起こすシナリオを再現し、今回の修正がその問題を解決することを確認するために重要です。

これらの変更により、Goコンパイラは、関数が宣言された時点でそのシンボルをより早期かつ確実に定義するようになり、特に共有ライブラリを生成する際のリンカエラーや不正な挙動を防ぐことができます。

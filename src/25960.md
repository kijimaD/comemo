# [インデックス 25960] ファイルの概要

このコミットは、Goランタイムにおけるシグナルハンドリングのロジックに存在する整数比較のバグを修正するものです。具体的には、`sig`変数が符号なし整数であるにもかかわらず、`sig - 1 >= 0`という条件でシグナル番号の有効性をチェックしていたため、常に真となってしまう問題を解決しています。この修正により、シグナル番号が0の場合に発生しうる不正な配列アクセスを防ぎ、シグナルブロック処理の堅牢性を向上させています。

## 変更の背景

この変更は、Goランタイムのシグナルハンドリングにおける潜在的なバグを修正するために行われました。Goのランタイムは、OSからのシグナル（例えば、`SIGINT`や`SIGTERM`など）を適切に処理し、Goプログラムの実行を制御します。シグナルは通常1以上の整数で表現されますが、Goランタイム内部でシグナル番号を扱う際に、`sig`変数が符号なし整数型として定義されていました。

問題は、シグナル番号`sig`から1を引いた値`b`が0以上であるかをチェックする`b >= 0`という条件にありました。`sig`が符号なし整数であるため、`sig - 1`という演算は、`sig`が0の場合にアンダーフローを起こし、非常に大きな正の数（例えば、`uintptr`の最大値）になります。結果として、`sig - 1 >= 0`という条件は`sig`がどのような値であっても常に真となってしまい、シグナル番号が0の場合でも条件が満たされてしまうという論理的な誤りがありました。

シグナル番号0は通常、有効なシグナルとしては扱われません。このバグにより、無効なシグナル番号（0）が渡された場合に、`sigBlocked`という配列に対して不正なインデックスアクセスが発生する可能性がありました。これは、プログラムのクラッシュや予期せぬ動作につながる重大な問題です。この問題はGoのIssue #11281として報告され、このコミットで修正されました。

## 前提知識の解説

### 1. シグナル (Signals)

オペレーティングシステムにおいて、シグナルはプロセスに対して非同期的にイベントを通知するメカニズムです。例えば、ユーザーがCtrl+Cを押すと`SIGINT`シグナルがプロセスに送られ、プロセスは通常終了します。他にも、`SIGTERM`（終了要求）、`SIGKILL`（強制終了）、`SIGSEGV`（セグメンテーション違反）など、様々なシグナルがあります。Goランタイムはこれらのシグナルを捕捉し、Goプログラム内で適切に処理するための仕組みを提供しています。

### 2. 符号なし整数 (Unsigned Integers)

符号なし整数は、負の値を表現できない整数型です。その代わりに、表現できる値の範囲がすべて非負の数に割り当てられます。例えば、8ビットの符号なし整数は0から255までの値を表現できます。

### 3. 整数アンダーフロー (Integer Underflow)

符号なし整数に対して、その最小値（通常は0）よりも小さい値を表現しようとすると、アンダーフローが発生します。多くのプログラミング言語やCPUアーキテクチャでは、符号なし整数がアンダーフローすると、その型の最大値にラップアラウンドします。例えば、8ビットの符号なし整数で0から1を引くと、255になります。

### 4. Goランタイムのシグナルハンドリング

Goランタイムは、OSからのシグナルをGoのgoroutineにディスパッチする独自のシグナルハンドリング機構を持っています。`src/runtime/signal1_unix.go`のようなファイルは、Unix系システムにおけるシグナル処理の低レベルな部分を扱います。`sigBlocked`のようなデータ構造は、どのシグナルが現在ブロックされているか（つまり、ランタイムがそのシグナルを無視するか、特別な処理をするか）を管理するために使用されます。

### 5. `select`ステートメントとチャネル

Goの`select`ステートメントは、複数の通信操作（チャネルの送受信）を待機し、準備ができた操作のいずれかを実行するために使用されます。このコミットのコードスニペットでは、`enableSigChan`と`disableSigChan`というチャネルからシグナル番号を受け取っています。これらは、ランタイムが特定のシグナルをブロックしたり、ブロック解除したりする指示を受け取るために使われます。

## 技術的詳細

このコミットの核心は、符号なし整数`sig`の特性を誤解した比較演算の修正です。

元のコードでは、`sig`から1を引いた結果を`b`に代入し、その`b`が0以上であるかをチェックしていました。
`if b := sig - 1; b >= 0 { ... }`

ここで、`sig`が`uintptr`のような符号なし整数型であると仮定します。
- `sig`が1以上の値の場合: `sig - 1`は0以上の値となり、`b >= 0`は真となります。これは期待通りの動作です。
- `sig`が0の場合: `sig - 1`は符号なし整数のアンダーフローを引き起こし、`uintptr`の最大値（例えば`0xFFFFFFFFFFFFFFFF`）のような非常に大きな正の数になります。この場合も`b >= 0`は真となってしまいます。

この「常に真」となる問題により、`sig`が0であっても条件が通過し、`sigBlocked[b/32]`のような配列アクセスが行われる可能性がありました。シグナル番号0は通常有効なシグナルではないため、`sigBlocked`配列の範囲外アクセスを引き起こす可能性があり、これはランタイムのクラッシュやセキュリティ上の脆弱性につながりかねません。

修正後のコードでは、`b := sig - 1`という代入はそのままですが、条件式が`sig > 0`に変更されています。
`if b := sig - 1; sig > 0 { ... }`

この変更により、以下のようになります。
- `sig`が1以上の値の場合: `sig > 0`は真となり、期待通りの動作です。
- `sig`が0の場合: `sig > 0`は偽となり、`if`ブロック内のコードは実行されません。これにより、シグナル番号0に対する不正な処理が回避されます。

この修正は、シグナル番号が有効な範囲（通常1以上）であることを保証するための、より正確なチェックを導入しています。`sigBlocked`配列は、シグナル番号をビットマップ形式で管理するためのものであり、インデックス`b`はシグナル番号`sig`に対応するビットの位置を計算するために使われます。したがって、`b`が有効な範囲内にあることを保証することが重要です。

## コアとなるコードの変更箇所

変更は`src/runtime/signal1_unix.go`ファイル内の`ensureSigM`関数にあります。

```diff
--- a/src/runtime/signal1_unix.go
+++ b/src/runtime/signal1_unix.go
@@ -228,11 +228,11 @@ func ensureSigM() {
 		for {
 			select {
 			case sig := <-enableSigChan:
-				if b := sig - 1; b >= 0 {
+				if b := sig - 1; sig > 0 {
 					sigBlocked[b/32] &^= (1 << (b & 31))
 				}
 			case sig := <-disableSigChan:
-				if b := sig - 1; b >= 0 {
+				if b := sig - 1; sig > 0 {
 					sigBlocked[b/32] |= (1 << (b & 31))
 				}
 			}
```

## コアとなるコードの解説

`ensureSigM`関数は、Goランタイムがシグナルを処理するために使用する特別なM (Machine) スレッドが適切に動作していることを保証する役割を担っています。この関数内の`for`ループと`select`ステートメントは、`enableSigChan`と`disableSigChan`という2つのチャネルからのイベントを待機しています。

- `case sig := <-enableSigChan:`: このケースは、特定のシグナルをブロック解除（有効化）する要求が来たときに実行されます。
- `case sig := <-disableSigChan:`: このケースは、特定のシグナルをブロック（無効化）する要求が来たときに実行されます。

どちらのケースでも、`sig`という変数にシグナル番号が格納されます。
変更された行は以下の部分です。

**変更前:**
```go
if b := sig - 1; b >= 0 {
    sigBlocked[b/32] &^= (1 << (b & 31))
}
```
**変更後:**
```go
if b := sig - 1; sig > 0 {
    sigBlocked[b/32] &^= (1 << (b & 31))
}
```
そして、`disableSigChan`のケースでも同様の変更が適用されています。

`b := sig - 1`は、シグナル番号`sig`を0ベースのインデックスに変換しています。例えば、シグナル番号1（`SIGHUP`など）はインデックス0に対応します。
`sigBlocked`は、シグナルブロック状態を管理するためのビットマップ配列です。
- `b/32`: `b`番目のシグナルが`sigBlocked`配列のどの要素に格納されているかを計算します。各要素が32ビットの整数であると仮定しています。
- `b & 31`: `b`番目のシグナルが、その配列要素内のどのビットに対応するかを計算します（`b % 32`と同じ）。
- `(1 << (b & 31))`: 対応するビット位置に1がセットされたマスクを作成します。

`enableSigChan`のケースでは、`&^=`演算子（ビットクリア）を使って、`sigBlocked`配列の対応するビットをクリアし、シグナルをブロック解除します。
`disableSigChan`のケースでは、`|=`演算子（ビットセット）を使って、`sigBlocked`配列の対応するビットをセットし、シグナルをブロックします。

この修正により、`sig`が0の場合にこれらのビット操作が実行されることがなくなり、`sigBlocked`配列への不正なアクセスが防止されます。

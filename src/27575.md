## 元コミット内容

このコミットは、Goの `syscall` パッケージにIBMのs390xアーキテクチャのサポートを追加します。主な変更点は以下の通りです。

1.  **`char` 型の符号問題への対応**: s390xでは `char` 型がデフォルトで符号なしですが、Goの `syscall` パッケージでは `RawSockaddr.Data` や `RawSockaddrUnix.Path` のようなフィールドで符号付きの `int8` を期待する場合があります。既存の `gccgo` APIとの互換性を保つため、これらのフィールドを明示的に符号付きとして扱います。
2.  **`PtraceRegs` フィールドのエクスポート**: s390x固有の `PtraceRegs` 構造体のフィールド型を、他のプラットフォームのAPIに影響を与えることなくエクスポートするために、`mkall.sh` スクリプトに `mkpost.go` という新しい後処理ステップを追加します。
3.  **生成コードのクリーンアップ**: `mkpost.go` は、`cgo -godefs` によって生成される `Pad_cgo*` や `X_*` といった不要なパディングフィールドをクリーンアップし、`gccgo` APIとの整合性を高めます。

## 変更の背景

Go言語はクロスプラットフォーム対応を重視しており、様々なCPUアーキテクチャやオペレーティングシステムで動作するように設計されています。s390xはIBMのメインフレームで利用される重要なアーキテクチャであり、Goがこの環境でネイティブに動作するためには、低レベルのシステムコールインターフェースを適切に実装する必要があります。

このコミットの背景には、主に以下の課題がありました。

*   **アーキテクチャ固有の型定義の差異**: C言語の `char` 型の符号の有無は、アーキテクチャによって異なります。s390xでは `unsigned char` がデフォルトであるため、Goの `syscall` パッケージが期待する型（通常は `int8`）と不一致が生じ、データ解釈に問題が発生する可能性がありました。
*   **既存の `gccgo` APIとの互換性**: s390x向けの `gccgo` (GCCベースのGoコンパイラ) は既に公開されており、そのAPIとの互換性を維持することが重要でした。安易な変更は、既存のs390x上のGoプロジェクトを破壊する恐れがありました。
*   **`cgo -godefs` の出力調整**: `cgo -godefs` はCの構造体定義からGoの構造体定義を自動生成するツールですが、生成されるコードにはプラットフォーム固有の調整が必要な場合があります。特に、`PtraceRegs` のようなデバッグ関連の構造体は、アーキテクチャによって内部表現が大きく異なるため、手動での調整や後処理が必要でした。

これらの課題を解決し、s390x上でのGoの `syscall` パッケージの堅牢性と互換性を確保するために、本コミットが導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. s390x アーキテクチャ

IBM System/390 (S/390) およびその後継である z/Architecture の64ビット版を指します。IBMのメインフレームコンピュータで利用されるRISCベースの命令セットアーキテクチャです。特徴としては、強力なI/O処理能力、信頼性、可用性、保守性 (RAS) が挙げられます。Go言語のようなモダンな言語がメインフレーム環境で動作することは、エンタープライズ分野でのGoの適用範囲を広げる上で重要です。

### 2. Go言語の `syscall` パッケージ

`syscall` パッケージは、Goプログラムからオペレーティングシステムの低レベルなシステムコールにアクセスするためのインターフェースを提供します。ファイル操作、プロセス管理、ネットワーク通信など、OSカーネルが提供する機能を利用するために使われます。このパッケージは、OSやアーキテクチャごとに異なるシステムコールの詳細を抽象化し、Goプログラムから一貫した方法でアクセスできるようにしますが、その内部では各プラットフォーム固有の実装が必要です。

### 3. `cgo` と `go tool cgo -godefs`

*   **`cgo`**: GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cのライブラリを利用したり、OSの低レベルな機能にアクセスしたりする際に使用されます。
*   **`go tool cgo -godefs`**: `cgo` ツールの一部で、C言語のヘッダーファイルからGo言語の構造体定義を自動生成するために使用されます。これにより、Cの構造体をGoのコードで安全に扱うための型バインディングが作成されます。例えば、OSのシステムコールが使用するCの構造体（`struct stat` など）をGoの `syscall` パッケージで利用可能にするために使われます。

### 4. `mkall.sh` スクリプト

Goの `syscall` パッケージのソースコードディレクトリ (`src/syscall`) に存在するシェルスクリプトです。このスクリプトは、様々なアーキテクチャとOSの組み合わせ (`GOOS`/`GOARCH`) に対して、`syscall` パッケージが必要とする定数、エラーコード、システムコール番号、型定義などを自動生成するために使用されます。具体的には、`mksysnum_linux.pl` や `go tool cgo -godefs` などのツールを呼び出して、`zerrors_*.go`, `zsyscall_*.go`, `zsysnum_*.go`, `ztypes_*.go` といったファイルを生成します。

### 5. `PtraceRegs` 構造体

`PtraceRegs` は、`ptrace` システムコール（プロセスをトレース・デバッグするためのシステムコール）で使用される構造体で、トレース対象プロセスのCPUレジスタの状態を保持します。この構造体の具体的な定義は、CPUアーキテクチャによって大きく異なります。デバッガやプロファイラのようなツールが、プロセスの実行状態を検査・変更するために利用します。

## 技術的詳細

このコミットの技術的詳細は、s390xアーキテクチャの特性とGoの `syscall` パッケージのコード生成プロセスに深く関連しています。

### 1. `char` 型の符号問題と `gccgo` 互換性

s390xのCコンパイラでは、`char` 型がデフォルトで `unsigned char` として扱われます。これは、他の多くのアーキテクチャ（x86-64など）で `signed char` がデフォルトであることと異なります。Goの `syscall` パッケージでは、`RawSockaddr.Data` や `RawSockaddrUnix.Path` のようなバイト列を扱うフィールドで、Cの `char` に対応するGoの型として `int8` (符号付き8ビット整数) を期待することが一般的です。

この不一致を解決するために、`cgo -godefs` が生成するGoの型定義を後処理する `mkpost.go` スクリプトが導入されました。`mkpost.go` は、`RawSockaddr.Data` フィールドの型が `[14]uint8` となっている場合、これを `[14]int8` に強制的に変更します。これにより、Goの `syscall` パッケージが期待する型とs390xの `gccgo` APIが使用する型との整合性が保たれ、既存のプロジェクトが壊れるのを防ぎます。`gccgo` APIとの互換性は、Goエコシステム全体の一貫性を保つ上で非常に重要です。

### 2. `mkpost.go` による後処理の導入

`mkall.sh` スクリプトは、`syscall` パッケージのプラットフォーム固有のファイルを生成する中心的な役割を担っています。このコミットでは、`linux_s390x` のケースにおいて、`mktypes` コマンド（`go tool cgo -godefs` を実行する部分）の出力が直接ファイルに書き込まれるのではなく、新しく追加された `mkpost.go` スクリプトにパイプで渡されるように変更されました。

具体的には、`mkall.sh` の以下の行が変更されました。

```diff
- if [ -n "$mktypes" ]; then echo "$mktypes types_$GOOS.go |gofmt >ztypes_$GOOSARCH.go"; fi
+ if [ -n "$mktypes" ]; then echo "$mktypes types_$GOOS.go |go run mkpost.go >ztypes_$GOOSARCH.go"; fi
```

この変更により、`go tool cgo -godefs types_linux.go` の出力が `mkpost.go` に渡され、`mkpost.go` がその内容を修正してから最終的な `ztypes_linux_s390x.go` ファイルに書き出すというワークフローが確立されました。

`mkpost.go` スクリプトは、以下の処理を行います。

*   **`PtraceRegs` フィールドのエクスポート**: s390xの場合、`PtraceRegs` 構造体内の `ptracePsw`, `ptraceFpregs`, `ptracePer` といったフィールド名を正規表現 (`ptrace(Psw|Fpregs|Per)`) を使って `Ptrace$1` の形式に変換し、Goのエクスポートルール（大文字で始まる）に適合させます。これにより、これらのフィールドがGoのコードからアクセス可能になります。
*   **不要なフィールドのクリーンアップ**: `cgo -godefs` は、Cの構造体のアライメント要件を満たすために `Pad_cgo_...` のようなパディングフィールドを挿入したり、Cの内部的な `X_...` フィールドを生成したりすることがあります。これらはGoのAPIとしては不要であり、`gccgo` APIにも存在しないため、`mkpost.go` はこれらのフィールドをGoのブランク識別子 (`_`) に置き換えて削除します。これにより、生成されるGoのAPIがよりクリーンで、`gccgo` との整合性が高まります。
*   **`RawSockaddr.Data` の型強制**: 前述の通り、`RawSockaddr.Data` の型を `[14]uint8` から `[14]int8` に変更します。
*   **`gofmt` 適用**: 最終的な出力は `go/format` パッケージによって `gofmt` され、Goの標準的なコーディングスタイルに準拠します。
*   **ヘッダーへのコマンド追記**: 生成されたファイルのヘッダーコメントに、`go run mkpost.go` が実行されたことを示す情報を追記し、ファイルの生成元を明確にします。

### 3. s390x固有のシステムコール実装

`src/syscall/syscall_linux_s390x.go` ファイルは、s390xアーキテクチャに特化したシステムコールラッパーとヘルパー関数を提供します。

*   **`mmap` の実装**: s390x Linuxでは、`mmap` システムコールが引数を構造体で渡す古いインターフェースを使用します。このファイルでは、`mmap_args` という配列に引数を格納し、`SYS_MMAP` システムコールを呼び出すことで、このインターフェースに対応しています。
*   **`socketcall` の利用**: s390x Linuxでは、ほとんどのソケット関連システムコールが `socketcall` という単一のシステムコールを介して間接的に呼び出されます。これは、複数のソケット関連システムコールを一つのエントリポイントで処理するためのメカニズムです。`socketcall` 関数は、実際のソケット操作の種類を示す `call` パラメータと、その操作に必要な引数を可変長引数として受け取ります。このファイルでは、`accept`, `bind`, `connect`, `socket`, `getsockopt`, `setsockopt`, `recvfrom`, `sendto`, `recvmsg`, `sendmsg`, `Listen`, `Shutdown` などのGoの `syscall` 関数が、内部的に `socketcall` または `rawsocketcall` を呼び出すように実装されています。
*   **`PtraceRegs` のメソッド**: `PtraceRegs` 構造体に対して `PC()` と `SetPC()` メソッドが追加され、プログラムカウンタの取得と設定が可能になっています。これはデバッグツールにとって重要な機能です。

### 4. `types_linux.go` の変更

`types_linux.go` は、Linuxシステムコールで使用されるCの型定義をGoの型にマッピングするためのファイルです。このコミットでは、s390x固有の変更が加えられました。

*   **`sun_path` の符号**: `struct my_sockaddr_un` の `sun_path` フィールドの定義に `__s390x__` が追加され、ARMおよびPowerPCと同様に、s390xでも `signed char sun_path[108]` が使用されるように変更されました。これにより、`char` の符号問題に対応しています。
*   **`PtraceRegs` 関連の型定義**: s390xの場合に `PtraceRegs` が `struct _user_regs_struct` に、そして `ptracePsw`, `ptraceFpregs`, `ptracePer` がそれぞれ `struct _user_psw_struct`, `struct _user_fpregs_struct`, `struct _user_per_struct` にマッピングされるように条件付きで型定義が追加されました。これにより、s390xの `ptrace` 関連の構造体がGoから適切に扱えるようになります。

### 5. 自動生成ファイル群

`zerrors_linux_s390x.go`, `zsyscall_linux_s390x.go`, `zsysnum_linux_s390x.go`, `ztypes_linux_s390x.go` は、`mkall.sh` スクリプトによって自動生成されるファイルです。

*   **`zerrors_linux_s390x.go`**: s390x Linuxシステムで定義されている様々なエラーコードや定数（`AF_ALG`, `ETH_P_IP`, `SOCK_STREAM` など）をGoの定数として定義します。
*   **`zsyscall_linux_s390x.go`**: s390x Linuxのシステムコールに対応するGoの関数スタブを定義します。これらの関数は、実際のシステムコールを呼び出すための低レベルなアセンブリコードにリンクされます。
*   **`zsysnum_linux_s390x.go`**: s390x Linuxのシステムコール番号をGoの定数として定義します（例: `SYS_READ`, `SYS_WRITE`）。
*   **`ztypes_linux_s390x.go`**: `cgo -godefs` と `mkpost.go` によって生成された、s390x Linux固有のGoの型定義を含みます。これには、`Stat_t`, `Timeval`, `Rlimit`, `RawSockaddr` など、システムコールで使用される様々な構造体が含まれます。

これらの自動生成ファイルは、s390xアーキテクチャ上でGoの `syscall` パッケージが正しく機能するために不可欠な、プラットフォーム固有の詳細をカプセル化しています。

2.  **`src/syscall/mkpost.go`**:
    *   新しく追加されたGoスクリプト。
    *   `os.Stdin` から `cgo -godefs` の出力を読み込む。
    *   `GOARCH` が `s390x` かつ `GOOS` が `linux` の場合に、以下の正規表現置換を実行。
        *   `ptrace(Psw|Fpregs|Per)` を `Ptrace$1` に変換（`PtraceRegs` フィールドのエクスポート）。
        *   `Pad_cgo[A-Za-z0-9_]*` を `_` に変換（パディングフィールドの削除）。
        *   `X_[A-Za-z0-9_]*` を `_` に変換（不要なフィールドの削除）。
        *   `(Data\\s+\\[14\\])uint8` を `${1}int8` に変換（`RawSockaddr.Data` の型強制）。
    *   `go/format` でコードをフォーマット。
    *   ヘッダーに `go run mkpost.go` の情報を追記。

    ```go
    // Copyright 2016 The Go Authors. All rights reserved.
    // Use of this source code is governed by a BSD-style
    // license that can be found in the LICENSE file.

    // +build ignore

    // mkpost processes the output of cgo -godefs to
    // modify the generated types. It is used to clean up
    // the syscall API in an architecture specific manner.
    //
    // mkpost is run after cgo -godefs by mkall.sh.
    package main

    import (
    	"fmt"
    	"go/format"
    	"io/ioutil"
    	"log"
    	"os"
    	"regexp"
    )

    func main() {
    	b, err := ioutil.ReadAll(os.Stdin)
    	if err != nil {
    		log.Fatal(err)
    	}
    	s := string(b)

    	goarch := os.Getenv("GOARCH")
    	goos := os.Getenv("GOOS")
    	if goarch == "s390x" && goos == "linux" {
    		// Export the types of PtraceRegs fields.
    		re := regexp.MustCompile("ptrace(Psw|Fpregs|Per)")
    		s = re.ReplaceAllString(s, "Ptrace$1")

    		// Replace padding fields inserted by cgo with blank identifiers.
    		re = regexp.MustCompile("Pad_cgo[A-Za-z0-9_]*")
    		s = re.ReplaceAllString(s, "_")

    		// Replace other unwanted fields with blank identifiers.
    		re = regexp.MustCompile("X_[A-Za-z0-9_]*")
    		s = re.ReplaceAllString(s, "_")

    		// Force the type of RawSockaddr.Data to [14]int8 to match
    		// the existing gccgo API.
    		re = regexp.MustCompile("(Data\\s+\\[14\\])uint8")
    		s = re.ReplaceAllString(s, "${1}int8")
    	}

    	// gofmt
    	b, err = format.Source([]byte(s))
    	if err != nil {
    		log.Fatal(err)
    	}

    	// Append this command to the header to show where the new file
    	// came from.
    	re := regexp.MustCompile("(cgo -godefs [a-zA-Z0-9_]+\\.go.*)")
    	s = re.ReplaceAllString(string(b), "$1 | go run mkpost.go")

    	fmt.Print(s)
    }
    ```

### `mkall.sh` の役割

`mkall.sh` は、Goの `syscall` パッケージが様々なプラットフォームで動作するために必要な、低レベルなOSインターフェースのバインディングを生成するオーケストレーターです。s390xのサポートを追加するにあたり、このスクリプトに `linux_s390x` のエントリが追加されました。これにより、`GOOS=linux GOARCH=s390x` の環境でビルドする際に、s390x固有のファイルが生成されるようになります。

最も重要な変更は、`mktypes` の実行方法です。通常、`go tool cgo -godefs types_linux.go` の出力は直接 `ztypes_linux_s390x.go` に書き込まれますが、s390xではこの出力が `mkpost.go` にパイプで渡されるようになりました。これは、`cgo -godefs` が生成するコードがs390xの特定の要件（`char` の符号、`PtraceRegs` のフィールド名、不要なパディング）を完全に満たさないため、追加の修正が必要であることを意味します。

### `mkpost.go` の重要性

`mkpost.go` は、`cgo -godefs` の「生」の出力を、Goの `syscall` パッケージのAPI規約とs390xの `gccgo` APIとの互換性に適合させるための「調整レイヤー」として機能します。

*   **`PtraceRegs` フィールドのエクスポート**: `ptracePsw` のようなフィールドが `PtracePsw` に変更されることで、Goの命名規則に従い、これらのフィールドがパッケージ外部からアクセス可能になります。これは、デバッグツールなどがs390x上でレジスタ情報を正しく読み書きするために不可欠です。
*   **パディングと不要なフィールドの削除**: `Pad_cgo*` や `X_*` フィールドは、Cの構造体のアライメントや内部実装の詳細であり、Goのユーザーには無関係です。これらを `_` (ブランク識別子) に置き換えることで、生成されるGoのAPIが簡潔になり、Goのコードからこれらの内部的な詳細が誤って参照されることを防ぎます。また、`gccgo` APIとの整合性も向上します。
*   **`RawSockaddr.Data` の型強制**: s390xの `char` のデフォルトが `unsigned` であることによる問題を、`uint8` から `int8` への明示的な型変換で解決します。これは、Goの `syscall` パッケージがネットワークアドレスなどのバイト列を扱う際に、符号付きバイトを期待する場面があるためです。この変更は、Goの `syscall` パッケージがs390x上でネットワーク通信を正しく処理するために重要です。

この後処理ステップは、Goのクロスプラットフォーム対応において、特定のアーキテクチャの癖や既存のツールチェーン（`gccgo`）との互換性を吸収するための柔軟なアプローチを示しています。

### `syscall_linux_s390x.go` の実装詳細

このファイルは、s390x Linuxにおけるシステムコール呼び出しの具体的な実装を提供します。

*   **`mmap` の特殊性**: `mmap` システムコールが引数を構造体で渡す必要があるというs390xの特性に対応するため、`mmap_args` というGoの配列に引数をパックし、その配列へのポインタをシステムコールに渡しています。これは、他のアーキテクチャで直接引数を渡す方法とは異なります。
*   **`socketcall` の利用**: s390xでは、ソケット関連の操作が `socketcall` という単一のシステムコールを介して行われるため、Goの各ソケット関数（`accept`, `bind` など）は、適切な `_SOCKET`, `_BIND` などの定数と引数を `socketcall` に渡すように実装されています。これにより、GoのソケットAPIがs390x上で正しく機能します。
*   **`PtraceRegs` メソッド**: `PC()` と `SetPC()` メソッドは、`PtraceRegs` 構造体内の `Psw.Addr` フィールドを直接操作します。`Psw` (Program Status Word) はs390xのCPUレジスタの一部であり、プログラムカウンタ（次に実行される命令のアドレス）を保持します。これらのメソッドは、デバッガがプロセスの実行フローを制御するために使用されます。

これらの実装は、s390xの低レベルなOSインターフェースのセマンティクスをGoの `syscall` パッケージの抽象化に適合させるための具体的な努力を示しています。

Go言語はクロスプラットフォーム対応を重視しており、様々なCPUアーキテクチャやオペレーティングシステムで動作するように設計されています。s390xはIBMのメインフレームで利用される重要なアーキテクチャであり、Goがこの環境でネイティブに動作するためには、低レベルのシステムコールインターフェースを適切に実装する必要があります。

このコミットの背景には、主に以下の課題がありました。

*   **アーキテクチャ固有の型定義の差異**: C言語の `char` 型の符号の有無は、アーキテクチャによって異なります。s390xでは `unsigned char` がデフォルトであるため、Goの `syscall` パッケージが期待する型（通常は `int8`）と不一致が生じ、データ解釈に問題が発生する可能性がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. s390x アーキテクチャ

IBM System/390 (S/390) およびその後継である z/Architecture の64ビット版を指します。IBMのメインフレームコンピュータで利用されるRISCベースの命令セットアーキテクチャです。特徴としては、強力なI/O処理能力、信頼性、可用性、保守性 (RAS) が挙げられます。Go言語のようなモダンな言語がメインフレーム環境で動作することは、エンタープライズ分野でのGoの適用範囲を広げる上で重要です。

### 2. Go言語の `syscall` パッケージ

`syscall` パッケージは、Goプログラムからオペレーティングシステムの低レベルなシステムコールにアクセスするためのインターフェースを提供します。ファイル操作、プロセス管理、ネットワーク通信など、OSカーネルが提供する機能を利用するために使われます。このパッケージは、OSやアーキテクチャごとに異なるシステムコールの詳細を抽象化し、Goプログラムから一貫した方法でアクセスできるようにしますが、その内部では各プラットフォーム固有の実装が必要です。

### 3. `cgo` と `go tool cgo -godefs`

*   **`cgo`**: GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cのライブラリを利用したり、OSの低レベルな機能にアクセスしたりする際に使用されます。
*   **`go tool cgo -godefs`**: `cgo` ツールの一部で、C言語のヘッダーファイルからGo言語の構造体定義を自動生成するために使用されます。これにより、Cの構造体をGoのコードで安全に扱うための型バインディングが作成されます。例えば、OSのシステムコールが使用するCの構造体（`struct stat` など）をGoの `syscall` パッケージで利用可能にするために使われます。

### 4. `mkall.sh` スクリプト

Goの `syscall` パッケージのソースコードディレクトリ (`src/syscall`) に存在するシェルスクリプトです。このスクリプトは、様々なアーキテクチャとOSの組み合わせ (`GOOS`/`GOARCH`) に対して、`syscall` パッケージが必要とする定数、エラーコード、システムコール番号、型定義などを自動生成するために使用されます。具体的には、`mksysnum_linux.pl` や `go tool cgo -godefs` などのツールを呼び出して、`zerrors_*.go`, `zsyscall_*.go`, `zsysnum_*.go`, `ztypes_*.go` といったファイルを生成します。

### 5. `PtraceRegs` 構造体

`PtraceRegs` は、`ptrace` システムコール（プロセスをトレース・デバッグするためのシステムコール）で使用される構造体で、トレース対象プロセスのCPUレジスタの状態を保持します。この構造体の具体的な定義は、CPUアーキテクチャによって大きく異なります。デバッガやプロファイラのようなツールが、プロセスの実行状態を検査・変更するために利用します。

## 技術的詳細

このコミットの技術的詳細は、s390xアーキテクチャの特性とGoの `syscall` パッケージのコード生成プロセスに深く関連しています。

### 1. `char` 型の符号問題と `gccgo` 互換性

s390xのCコンパイラでは、`char` 型がデフォルトで `unsigned char` として扱われます。これは、他の多くのアーキテクチャ（x86-64など）で `signed char` がデフォルトであることと異なります。Goの `syscall` パッケージでは、`RawSockaddr.Data` や `RawSockaddrUnix.Path` のようなバイト列を扱うフィールドで、Cの `char` に対応するGoの型として `int8` (符号付き8ビット整数) を期待することが一般的です。

この不一致を解決するために、`cgo -godefs` が生成するGoの型定義を後処理する `mkpost.go` スクリプトが導入されました。`mkpost.go` は、`RawSockaddr.Data` フィールドの型が `[14]uint8` となっている場合、これを `[14]int8` に強制的に変更します。これにより、Goの `syscall` パッケージが期待する型とs390xの `gccgo` APIが使用する型との整合性が保たれ、既存のプロジェクトが壊れるのを防ぎます。`gccgo` APIとの互換性は、Goエコシステム全体の一貫性を保つ上で非常に重要です。

### 2. `mkpost.go` による後処理の導入

`mkall.sh` スクリプトは、`syscall` パッケージのプラットフォーム固有のファイルを生成する中心的な役割を担っています。このコミットでは、`linux_s390x` のケースにおいて、`mktypes` コマンド（`go tool cgo -godefs` を実行する部分）の出力が直接ファイルに書き込まれるのではなく、新しく追加された `mkpost.go` スクリプトにパイプで渡されるように変更されました。

具体的には、`mkall.sh` の以下の行が変更されました。

```diff
- if [ -n "$mktypes" ]; then echo "$mktypes types_$GOOS.go |gofmt >ztypes_$GOOSARCH.go"; fi
+ if [ -n "$mktypes" ]; then echo "$mktypes types_$GOOS.go |go run mkpost.go >ztypes_$GOOSARCH.go"; fi
```

この変更により、`go tool cgo -godefs types_linux.go` の出力が `mkpost.go` に渡され、`mkpost.go` がその内容を修正してから最終的な `ztypes_linux_s390x.go` ファイルに書き出すというワークフローが確立されました。

`mkpost.go` スクリプトは、以下の処理を行います。

*   **`PtraceRegs` フィールドのエクスポート**: s390xの場合、`PtraceRegs` 構造体内の `ptracePsw`, `ptraceFpregs`, `ptracePer` といったフィールド名を正規表現 (`ptrace(Psw|Fpregs|Per)`) を使って `Ptrace$1` の形式に変換し、Goのエクスポートルール（大文字で始まる）に適合させます。これにより、これらのフィールドがGoのコードからアクセス可能になります。
*   **不要なフィールドのクリーンアップ**: `cgo -godefs` は、Cの構造体のアライメント要件を満たすために `Pad_cgo_...` のようなパディングフィールドを挿入したり、Cの内部的な `X_...` フィールドを生成したりすることがあります。これらはGoのAPIとしては不要であり、`gccgo` APIにも存在しないため、`mkpost.go` はこれらのフィールドをGoのブランク識別子 (`_`) に置き換えて削除します。これにより、生成されるGoのAPIがよりクリーンで、`gccgo` との整合性が高まります。
*   **`RawSockaddr.Data` の型強制**: 前述の通り、`RawSockaddr.Data` の型を `[14]uint8` から `[14]int8` に変更します。
*   **`gofmt` 適用**: 最終的な出力は `go/format` パッケージによって `gofmt` され、Goの標準的なコーディングスタイルに準拠します。
*   **ヘッダーへのコマンド追記**: 生成されたファイルのヘッダーコメントに、`go run mkpost.go` が実行されたことを示す情報を追記し、ファイルの生成元を明確にします。

### 3. s390x固有のシステムコール実装

`src/syscall/syscall_linux_s390x.go` ファイルは、s390xアーキテクチャに特化したシステムコールラッパーとヘルパー関数を提供します。

*   **`mmap` の実装**: s390x Linuxでは、`mmap` システムコールが引数を構造体で渡す古いインターフェースを使用します。このファイルでは、`mmap_args` という配列に引数を格納し、`SYS_MMAP` システムコールを呼び出すことで、このインターフェースに対応しています。
*   **`socketcall` の利用**: s390x Linuxでは、ほとんどのソケット関連システムコールが `socketcall` という単一のシステムコールを介して間接的に呼び出されます。これは、複数のソケット関連システムコールを一つのエントリポイントで処理するためのメカニズムです。`socketcall` 関数は、実際のソケット操作の種類を示す `call` パラメータと、その操作に必要な引数を可変長引数として受け取ります。このファイルでは、`accept`, `bind`, `connect`, `socket`, `getsockopt`, `setsockopt`, `recvfrom`, `sendto`, `recvmsg`, `sendmsg`, `Listen`, `Shutdown` などのGoの `syscall` 関数が、内部的に `socketcall` または `rawsocketcall` を呼び出すように実装されています。
*   **`PtraceRegs` のメソッド**: `PtraceRegs` 構造体に対して `PC()` と `SetPC()` メソッドが追加され、プログラムカウンタの取得と設定が可能になっています。これはデバッグツールにとって重要な機能です。

これらの実装は、s390xの低レベルなOSインターフェースのセマンティクスをGoの `syscall` パッケージの抽象化に適合させるための具体的な努力を示しています。

### 4. `types_linux.go` の変更

`types_linux.go` は、Linuxシステムコールで使用されるCの型定義をGoの型にマッピングするためのファイルです。このコミットでは、s390x固有の変更が加えられました。

*   **`sun_path` の符号**: `struct my_sockaddr_un` の `sun_path` フィールドの定義に `__s390x__` が追加され、ARMおよびPowerPCと同様に、s390xでも `signed char sun_path[108]` が使用されるように変更されました。これにより、`char` の符号問題に対応しています。
*   **`PtraceRegs` 関連の型定義**: s390xの場合に `PtraceRegs` が `struct _user_regs_struct` に、そして `ptracePsw`, `ptraceFpregs`, `ptracePer` がそれぞれ `struct _user_psw_struct`, `struct _user_fpregs_struct`, `struct _user_per_struct` にマッピングされるように条件付きで型定義が追加されました。これにより、s390xの `ptrace` 関連の構造体がGoから適切に扱えるようになります。

### 5. 自動生成ファイル群

`zerrors_linux_s390x.go`, `zsyscall_linux_s390x.go`, `zsysnum_linux_s390x.go`, `ztypes_linux_s390x.go` は、`mkall.sh` スクリプトによって自動生成されるファイルです。

*   **`zerrors_linux_s390x.go`**: s390x Linuxシステムで定義されている様々なエラーコードや定数（`AF_ALG`, `ETH_P_IP`, `SOCK_STREAM` など）をGoの定数として定義します。
*   **`zsyscall_linux_s390x.go`**: s390x Linuxのシステムコールに対応するGoの関数スタブを定義します。これらの関数は、実際のシステムコールを呼び出すための低レベルなアセンブリコードにリンクされます。
*   **`zsysnum_linux_s390x.go`**: s390x Linuxのシステムコール番号をGoの定数として定義します（例: `SYS_READ`, `SYS_WRITE`）。
*   **`ztypes_linux_s390x.go`**: `cgo -godefs` と `mkpost.go` によって生成された、s390x Linux固有のGoの型定義を含みます。これには、`Stat_t`, `Timeval`, `Rlimit`, `RawSockaddr` など、システムコールで使用される様々な構造体が含まれます。

これらの自動生成ファイルは、s390xアーキテクチャ上でGoの `syscall` パッケージが正しく機能するために不可欠な、プラットフォーム固有の詳細をカプセル化しています。

## コアとなるコードの解説

このコミットの核心は、s390xアーキテクチャの特殊性をGoの `syscall` パッケージに透過的に統合するための、巧妙なコード生成と後処理のメカニズムにあります。

### `mkall.sh` の役割

`mkall.sh` は、Goの `syscall` パッケージが様々なプラットフォームで動作するために必要な、低レベルなOSインターフェースのバインディングを生成するオーケストレーターです。s390xのサポートを追加するにあたり、このスクリプトに `linux_s390x` のエントリが追加されました。これにより、`GOOS=linux GOARCH=s390x` の環境でビルドする際に、s390x固有のファイルが生成されるようになります。

最も重要な変更は、`mktypes` の実行方法です。通常、`go tool cgo -godefs types_linux.go` の出力は直接 `ztypes_linux_s390x.go` に書き込まれますが、s390xではこの出力が `mkpost.go` にパイプで渡されるようになりました。これは、`cgo -godefs` が生成するコードがs390xの特定の要件（`char` の符号、`PtraceRegs` のフィールド名、不要なパディング）を完全に満たさないため、追加の修正が必要であることを意味します。

### `mkpost.go` の重要性

`mkpost.go` は、`cgo -godefs` の「生」の出力を、Goの `syscall` パッケージのAPI規約とs390xの `gccgo` APIとの互換性に適合させるための「調整レイヤー」として機能します。

*   **`PtraceRegs` フィールドのエクスポート**: `ptracePsw` のようなフィールドが `PtracePsw` に変更されることで、Goの命名規則に従い、これらのフィールドがパッケージ外部からアクセス可能になります。これは、デバッグツールなどがs390x上でレジスタ情報を正しく読み書きするために不可欠です。
*   **パディングと不要なフィールドの削除**: `Pad_cgo*` や `X_*` フィールドは、Cの構造体のアライメントや内部実装の詳細であり、Goのユーザーには無関係です。これらを `_` (ブランク識別子) に置き換えることで、生成されるGoのAPIが簡潔になり、Goのコードからこれらの内部的な詳細が誤って参照されることを防ぎます。また、`gccgo` APIとの整合性も向上します。
*   **`RawSockaddr.Data` の型強制**: s390xの `char` のデフォルトが `unsigned` であることによる問題を、`uint8` から `int8` への明示的な型変換で解決します。これは、Goの `syscall` パッケージがネットワークアドレスなどのバイト列を扱う際に、符号付きバイトを期待する場面があるためです。この変更は、Goの `syscall` パッケージがs390x上でネットワーク通信を正しく処理するために重要です。

この後処理ステップは、Goのクロスプラットフォーム対応において、特定のアーキテクチャの癖や既存のツールチェーン（`gccgo`）との互換性を吸収するための柔軟なアプローチを示しています。

### `syscall_linux_s390x.go` の実装詳細

このファイルは、s390x Linuxにおけるシステムコール呼び出しの具体的な実装を提供します。

*   **`mmap` の特殊性**: `mmap` システムコールが引数を構造体で渡す必要があるというs390xの特性に対応するため、`mmap_args` というGoの配列に引数をパックし、その配列へのポインタをシステムコールに渡しています。これは、他のアーキテクチャで直接引数を渡す方法とは異なります。
*   **`socketcall` の利用**: s390xでは、ソケット関連の操作が `socketcall` という単一のシステムコールを介して行われるため、Goの各ソケット関数（`accept`, `bind` など）は、適切な `_SOCKET`, `_BIND` などの定数と引数を `socketcall` に渡すように実装されています。これにより、GoのソケットAPIがs390x上で正しく機能します。
*   **`PtraceRegs` メソッド**: `PC()` と `SetPC()` メソッドは、`PtraceRegs` 構造体内の `Psw.Addr` フィールドを直接操作します。`Psw` (Program Status Word) はs390xのCPUレジスタの一部であり、プログラムカウンタ（次に実行される命令のアドレス）を保持します。これらのメソッドは、デバッガがプロセスの実行フローを制御するために使用されます。

これらの実装は、s390xの低レベルなOSインターフェースのセマンティクスをGoの `syscall` パッケージの抽象化に適合させるための具体的な努力を示しています。

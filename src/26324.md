# [インデックス 26324] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるワークバッファの共有メカニズムを改善し、GCの効率を向上させるものです。特に、GCアシスト（アプリケーションコードがGCを手伝う処理）がワークバッファを占有し、他のGCワーカーが利用できる作業が不足する問題を解決します。これにより、GCのパフォーマンスが大幅に改善され、特定のベンチマークで39%の時間短縮が達成されました。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。GCのマークフェーズでは、到達可能なオブジェクトを特定するためにヒープを走査し、その作業は「ワークバッファ」と呼ばれるデータ構造に格納されます。これらのワークバッファは、複数のGCワーカー（ゴルーチン）によって共有され、並行して処理されます。

以前の実装では、GCワークバッファのバランシング（つまり、ワークバッファをグローバルなキューと各プロセッサ（P）のローカルキャッシュ間で適切に分配する処理）は、主にバックグラウンドワーカーやアイドル状態のワーカーによってのみ行われていました。しかし、GCアシスト（アプリケーションのゴルーチンが、GCの進行が遅れている場合にGC作業の一部を肩代わりするメカニズム）は、このバランシング処理に積極的に参加していませんでした。

この「見落とし」により、GCアシストが多用されるようなワークロード（例えば、大量のオブジェクトを短期間に割り当てるプログラム）では、アシストが大量のワークバッファを各Pのローカルキャッシュに保持したままになりがちでした。その結果、グローバルなワークバッファリストが空になりやすくなり、他のGCワーカーや、さらにGCアシスト自身も、作業を見つけられずにブロックしたり、終了したりする可能性が高まりました。これはシステム全体の速度低下を引き起こし、特にCL 15893で導入された変更によって顕在化したパフォーマンスの回帰（リグレッション）として観測されていました。

このコミットは、この問題を解決し、GCアシストがより積極的にワークバッファの共有に参加することで、GCの効率と全体的なアプリケーションのパフォーマンスを向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

GoのGCは、Stop-The-World (STW) フェーズを最小限に抑えるために、コンカレント（並行）かつインクリメンタル（漸進的）なマーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGC作業の大部分を行うことで、アプリケーションの一時停止時間を短縮し、レイテンシを低減することを目的としています。

### GCの「マークフェーズ」

GCの主要なフェーズの一つが「マークフェーズ」です。このフェーズでは、GCはルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを特定し、「マーク」します。マークされなかったオブジェクトは、その後のスイープフェーズで解放されます。マーク作業は、ヒープ上のオブジェクトを走査し、参照をたどることで行われます。

### GCワークバッファ (work buffers) の役割

マークフェーズにおいて、GCワーカーはヒープを走査し、発見したポインタ（参照）を一時的に保存する必要があります。この一時保存に使われるのが「ワークバッファ」です。ワークバッファは、ポインタのキューとして機能し、GCワーカーが処理すべきオブジェクトのリストを保持します。これにより、GCワーカーは効率的に作業を分担し、並行してヒープを走査できます。ワークバッファは、各P（プロセッサ）にローカルにキャッシュされるものと、グローバルな共有リストに置かれるものがあります。

### GoランタイムにおけるP (Processor) の概念

Goランタイムは、OSのスレッド（M: Machine）上でGoのゴルーチン（G: Goroutine）をスケジュールするために、抽象的な「プロセッサ」（P: Processor）の概念を使用します。Pは、MがGを実行するために必要なリソース（スケジューラキュー、メモリキャッシュなど）を提供します。各Pは、GCワークバッファのようなローカルなリソースを持つことができます。

### GCにおける「アシスト (assists)」と「バックグラウンド/アイドルワーカー (background/idle workers)」

*   **GCアシスト (GC assists)**: アプリケーションのゴルーチンがメモリ割り当てを行おうとした際に、GCの進行が遅れていると判断された場合、そのゴルーチンはGC作業の一部を「アシスト」として実行します。これは、GCがアプリケーションのメモリ割り当て要求に追いつくのを助け、STWフェーズを回避するための重要なメカニズムです。アシストは、アプリケーションの実行パス上で同期的にGC作業を行います。
*   **バックグラウンド/アイドルワーカー (background/idle workers)**: これらは、アプリケーションの実行とは独立して、バックグラウンドでGC作業を行う専用のゴルーチンです。システムがアイドル状態のときや、GCが必要なときに積極的にGC作業を進めます。

### ワークバッファの「バランシング」の重要性

ワークバッファのバランシングは、GCワーカー間で作業負荷を均等に分散するために不可欠です。もし一部のワーカーが大量のワークバッファを抱え込み、他のワーカーが作業を見つけられない場合、GCの並行性が損なわれ、効率が低下します。グローバルなワークバッファリストが枯渇すると、ワーカーは作業を待つか、終了せざるを得なくなり、GCの進行が遅れます。適切なバランシングは、常に利用可能な作業があることを保証し、GCワーカーの稼働率を最大化します。

## 技術的詳細

このコミットの核心は、`src/runtime/mgcmark.go` 内の `gcDrain` 関数におけるワークバッファのバランシングロジックの変更です。`gcDrain` 関数は、GCワーカーがワークバッファからオブジェクトを処理する主要なループを含んでいます。

以前の実装では、`gcDrain` 内のワークバッファのバランシング（`gcw.balance()` の呼び出し）は、主に「他のPがポインタを欲しがっている場合 (`work.nwait > 0`)」かつ「グローバルなワークバッファリストが満杯でない場合 (`work.full == 0`)」という条件でのみ行われていました。この条件は、バックグラウンドワーカーやアイドルワーカーには適切でしたが、GCアシストには不十分でした。GCアシストは、自身のPのローカルキャッシュにワークバッファを保持し続ける傾向があり、グローバルリストが空になっても、`work.nwait > 0` の条件が満たされない限り、バランシングを行いませんでした。

新しい実装では、この条件が緩和され、**グローバルなワークバッファリストが空である場合 (`work.full == 0`)**、GCアシストも積極的に `gcw.balance()` を呼び出すようになりました。これにより、アシストがローカルに保持しているワークバッファの一部をグローバルリストに解放し、他のワーカーが利用できるようにします。

この変更の意図は、ワーカーが作業を待つまで待つのではなく、**グローバルキューに常に作業が利用可能である状態を維持する**ことです。コミットメッセージにあるように、「ワーカーが待っているかどうかをチェックするよりも、作業を常に利用可能にしておく方が良い」という思想に基づいています。これにより、たとえO(log(_WorkbufSize))の不要なバランシングが発生したとしても、ワーカーがブロックする可能性を減らし、GCの全体的なスループットを向上させます。

結果として、GCアシストがワークバッファを占有する問題が解消され、GCワーカー間の作業共有がより効率的に行われるようになります。これにより、GCの進行がスムーズになり、アプリケーションの実行が中断される時間が短縮され、特にメモリ割り当てが頻繁に行われるワークロードでのパフォーマンスが大幅に改善されます。

## コアとなるコードの解説

このコミットでは、主に `src/runtime/mgcmark.go` ファイル内の `gcDrain` 関数と `gcDrainN` 関数が変更されています。

1.  **タイプミス修正**:
    *   `preemtible` が `preemptible` に修正されています。これは機能的な変更ではなく、単なるスペルミス修正です。

2.  **`gcDrain` 関数内のワークバッファバランシングロジックの変更**:
    *   変更前:
        ```go
        // If another proc wants a pointer, give it some.
        if work.nwait > 0 && work.full == 0 {
            gcw.balance()
        }
        ```
        この条件は、「他のプロセッサがポインタを待っている (`work.nwait > 0`)」**かつ**「グローバルなワークバッファリストが満杯でない (`work.full == 0`)」場合にのみ、現在のGCワーカーが自身のワークバッファをグローバルリストにバランス（共有）することを意味していました。GCアシストの場合、`work.nwait > 0` の条件が満たされにくく、ローカルにワークバッファを保持し続ける傾向がありました。
    *   変更後:
        ```go
        // Try to keep work available on the global queue. We used to
        // check if there were waiting workers, but it's better to
        // just keep work available than to make workers wait. In the
        // worst case, we'll do O(log(_WorkbufSize)) unnecessary
        // balances.
        if work.full == 0 {
            gcw.balance()
        }
        ```
        新しい条件は、「グローバルなワークバッファリストが満杯でない (`work.full == 0`)」場合に、現在のGCワーカーが自身のワークバッファをグローバルリストにバランスすることを意味します。`work.nwait > 0` の条件が削除されたことで、他のワーカーが明示的に作業を待っているかどうかに関わらず、グローバルリストが空になりそうであれば、積極的にワークバッファを共有するようになりました。これにより、GCアシストもこの新しいロジックに従い、より早くワークバッファを共有するようになります。コメントにもあるように、これはワーカーが待つことを避けるために、グローバルキューに常に作業がある状態を維持することを目的としています。

3.  **`gcDrainN` 関数内のワークバッファバランシングの追加**:
    *   `gcDrainN` 関数は、特定の量のスキャン作業を完了するまでGC作業を行う関数です。この関数内にも、`gcDrain` と同様のバランシングロジックが追加されました。
    *   追加されたコード:
        ```go
        // See gcDrain comment.
        if work.full == 0 {
            gcw.balance()
        }
        ```
        これにより、`gcDrainN` を実行しているワーカーも、グローバルなワークバッファリストが空になりそうであれば、積極的にワークバッファを共有するようになります。これは、`gcDrain` で行われた変更と同じ理由と目的を持っています。

これらの変更により、GCアシストを含むすべてのGCワーカーが、グローバルなワークバッファリストの枯渇を防ぐために、より積極的にワークバッファを共有するようになります。これにより、GCワーカー間の作業の受け渡しがスムーズになり、GCの並行性が向上し、全体的なGCの効率が改善されます。

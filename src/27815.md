## 変更の背景

`src/net/mockserver_test.go` 内の `newLocalPacketListener` 関数は、テスト目的でローカルのパケットリスナーを作成するために使用されます。この関数は `network` 引数を受け取り、それに基づいて適切な `net.ListenPacket` 呼び出しを行うことを意図していました。

しかし、変更前の実装では、`"udp"`、`"udp4"`、`"udp6"` の3つのネットワークタイプが `switch` ステートメントの単一の `case "udp", "udp4", "udp6":` ブロックで処理されていました。この実装では、`network` 引数が `"udp4"` または `"udp6"` であった場合でも、最初に `supportsIPv4` が `true` であれば `ListenPacket("udp4", ...)` が呼ばれ、そうでなければ `supportsIPv6` が `true` であれば `ListenPacket("udp6", ...)` が呼ばれるというロジックになっていました。

この問題は、呼び出し元が明示的に `"udp6"` を要求しているにもかかわらず、システムがIPv4をサポートしているために `ListenPacket("udp4", ...)` が作成されてしまう、といった意図しない動作を引き起こす可能性がありました。これにより、特定のIPバージョンに限定したテストシナリオが正しく実行できないという問題が生じていました。このコミットは、この `network` 引数の処理の不正確さを修正し、呼び出し元の意図通りに特定のIPバージョンでリスナーが作成されるようにすることを目的としています。

## 前提知識の解説

*   **Go言語の `net` パッケージ**: Go言語の標準ライブラリの一部で、ネットワークI/O機能を提供します。TCP/IP、UDP、Unixドメインソケットなど、様々なネットワークプロトコルを扱うためのインターフェースと実装が含まれています。
*   **`net.PacketConn` インターフェース**: パケット指向のネットワーク接続を表すインターフェースです。UDPソケットなどがこれに該当し、接続を確立せずに個々のデータグラム（パケット）を送受信します。
*   **`net.ListenPacket(network, address string) (PacketConn, error)` 関数**: 指定されたネットワークプロトコルとローカルアドレスでパケットリスナーを起動する関数です。成功すると `PacketConn` インターフェースを実装するオブジェクトを返します。
    *   `network` 引数: 使用するネットワークプロトコルを指定します。
        *   `"udp"`: UDPプロトコルを使用します。Goランタイムは、システム設定とアドレスの性質に基づいてIPv4またはIPv6のいずれかを選択しようとします。デュアルスタック対応が期待されます。
        *   `"udp4"`: UDP over IPv4プロトコルを明示的に使用します。IPv4アドレスのみにバインドまたは接続します。
        *   `"udp6"`: UDP over IPv6プロトコルを明示的に使用します。IPv6アドレスのみにバインドまたは接続します。
    *   `address` 引数: リッスンするローカルネットワークアドレスを指定します。例えば、`"127.0.0.1:0"` はIPv4のループバックアドレスの任意のポート、`"[::1]:0"` はIPv6のループバックアドレスの任意のポートを意味します。ポート番号に `0` を指定すると、OSが利用可能なポートを自動的に割り当てます。
*   **IPv4とIPv6**: インターネットプロトコルのバージョンです。IPv4は32ビットアドレスを使用し、IPv6は128ビットアドレスを使用します。両者は互換性がなく、異なるネットワークスタックで処理されます。
*   **ループバックアドレス**: `127.0.0.1` (IPv4) および `::1` (IPv6) は、自身のマシンを指す特殊なIPアドレスです。主にローカルでのテストやプロセス間通信に使用されます。
*   **`supportsIPv4` / `supportsIPv6`**: これらの変数は、実行環境がそれぞれIPv4またはIPv6をサポートしているかどうかを示すブール値であると推測されます。テスト環境のセットアップ時にこれらの値が決定され、利用可能なIPバージョンに基づいてリスナーを作成する際の条件分岐に使用されます。

## 技術的詳細

変更前の `newLocalPacketListener` 関数は、`network` 引数として `"udp"`、`"udp4"`、`"udp6"` のいずれを受け取っても、最初の `switch` ケース `case "udp", "udp4", "udp6":` に入っていました。このブロック内では、まず `supportsIPv4` をチェックし、`true` であれば `ListenPacket("udp4", ...)` を呼び出していました。`supportsIPv4` が `false` の場合にのみ `supportsIPv6` をチェックし、`true` であれば `ListenPacket("udp6", ...)` を呼び出すというロジックでした。

このロジックの問題点は以下の通りです。
1.  **`"udp4"` の場合**: 呼び出し元が明示的にIPv4を要求しているため、`ListenPacket("udp4", ...)` が呼ばれるのは正しい動作です。
2.  **`"udp6"` の場合**: 呼び出し元が明示的にIPv6を要求しているにもかかわらず、もしシステムがIPv4をサポートしていれば（`supportsIPv4` が `true`）、誤って `ListenPacket("udp4", ...)` が呼び出されてしまいます。これは、IPv6専用のテストケースを意図通りに実行できない原因となります。
3.  **`"udp"` の場合**: `"udp"` はデュアルスタックを意図しているか、システムが最適なものを選択することを期待しますが、この実装ではまずIPv4を優先し、IPv4が利用できない場合にのみIPv6にフォールバックするという、特定の順序での選択が行われていました。これは必ずしも `"udp"` の一般的な期待と一致しない場合があります。

このコミットによる修正は、`switch` ステートメントを細分化し、`"udp"`、`"udp4"`、`"udp6"` の各ケースを独立して処理するように変更しました。
*   `"udp"` のケースでは、引き続き `supportsIPv4` を優先し、次に `supportsIPv6` を試みるロジックを維持します。これは、`"udp"` が特定のIPバージョンを強制しないため、システムが利用可能なものを選択するという意図に沿っています。
*   `"udp4"` のケースでは、明示的に `ListenPacket("udp4", ...)` を呼び出すようにします。
*   `"udp6"` のケースでは、明示的に `ListenPacket("udp6", ...)` を呼び出すようにします。

これにより、`newLocalPacketListener` 関数は、`network` 引数で指定されたIPバージョンに厳密に従ってパケットリスナーを作成するようになり、テストの正確性と信頼性が向上しました。

## コアとなるコードの解説

変更は `src/net/mockserver_test.go` ファイル内の `newLocalPacketListener` 関数に集中しています。

*   **変更前**:
    ```go
    	switch network {
    	case "udp", "udp4", "udp6":
    		if supportsIPv4 {
    			return ListenPacket("udp4", "127.0.0.1:0")
    		}
    		if supportsIPv6 {
    			return ListenPacket("udp6", "[::1]:0")
    		}
    ```
    この部分では、`"udp"`、`"udp4"`、`"udp6"` のいずれが `network` 引数として渡されても、同じコードブロックが実行されていました。まず `supportsIPv4` を確認し、IPv4が利用可能であれば `udp4` リスナーを作成します。IPv4が利用できない場合にのみ `supportsIPv6` を確認し、`udp6` リスナーを作成します。このロジックは、`"udp6"` が明示的に要求された場合でも、IPv4が利用可能であれば `udp4` リスナーが作成されてしまうという問題がありました。

*   **変更後**:
    ```go
    	switch network {
    	case "udp":
    		if supportsIPv4 {
    			return ListenPacket("udp4", "127.0.0.1:0")
    		}
    		if supportsIPv6 {
    			return ListenPacket("udp6", "[::1]:0")
    		}
    	case "udp4":
    		if supportsIPv4 {
    			return ListenPacket("udp4", "127.0.0.1:0")
    		}
    	case "udp6":
    		if supportsIPv6 {
    			return ListenPacket("udp6", "[::1]:0")
    		}
    ```
    `switch` ステートメントが3つの独立した `case` ブロックに分割されました。
    *   `case "udp":` ブロックは変更前と同じロジックを維持します。これは、`"udp"` が特定のIPバージョンを強制しないため、システムが利用可能なものを選択するという意図に沿っています。
    *   `case "udp4":` ブロックは、`network` が `"udp4"` の場合にのみ実行されます。このブロックでは、`supportsIPv4` が `true` であれば、明示的に `ListenPacket("udp4", "127.0.0.1:0")` を呼び出します。これにより、IPv4リスナーの作成が保証されます。
    *   `case "udp6":` ブロックは、`network` が `"udp6"` の場合にのみ実行されます。このブロックでは、`supportsIPv6` が `true` であれば、明示的に `ListenPacket("udp6", "[::1]:0")` を呼び出します。これにより、IPv6リスナーの作成が保証されます。

この修正により、`newLocalPacketListener` 関数は、`network` 引数で指定されたネットワークタイプ（特にIPv4またはIPv6）に厳密に従って動作するようになり、テストの意図が正確に反映されるようになりました。

# [インデックス 2738] ファイルの概要

このコミットは、Go言語の初期の式評価器（`usr/austin/eval` パッケージ内）において、単項演算子および二項演算子を網羅的に実装したものです。具体的には、算術演算子、ビット演算子、論理演算子など、Go言語がサポートする主要な演算子の評価ロジックが追加・整理されています。これにより、式評価器がより広範なGoの式を正確に解釈し、実行できるようになりました。

## 変更の背景

このコミットは、Go言語の初期開発段階における式評価器（`usr/austin/eval` パッケージ）の機能拡張の一環として行われました。当時のGo言語はまだ仕様が固まっておらず、コンパイラやツールチェインも発展途上でした。式評価器は、デバッガやインタプリタ、あるいはコンパイル時の定数評価など、様々な場面で必要となる基本的なコンポーネントです。

このコミット以前は、式評価器がサポートする単項および二項演算子の種類が限られていたと考えられます。そのため、より複雑な式や、Go言語の仕様で定義される全ての演算子を正確に処理するためには、これらの演算子の評価ロジックを網羅的に実装する必要がありました。特に、数値型だけでなく、ブール型や文字列型、ポインタ型など、Goが持つ多様な型に対する演算のセマンティクスを正しく反映させることが求められました。

また、`gen.py genOps`というコメントから、これらの演算子生成ロジックがスクリプトによって自動生成されたものであることが示唆されており、これは開発効率の向上と、将来的な演算子追加・変更への対応を容易にするための設計判断であったと考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/インタプリタの基本的な概念が必要です。

1.  **Go言語の型システム**: Go言語は静的型付け言語であり、`int`, `uint`, `float64`, `bool`, `string`, `pointer` など、多様な組み込み型を持ちます。また、`ideal` 型（型付けされていない定数）の概念も重要です。`ideal` 型は、コンパイル時に具体的な型に変換されるまで、より広い精度を持つことができます。
2.  **抽象構文木 (AST: Abstract Syntax Tree)**: プログラムのソースコードを解析して得られる、構文構造を木構造で表現したものです。Go言語の`go/ast`パッケージがこれに該当します。`ast.UnaryExpr`や`ast.BinaryExpr`は、それぞれ単項演算子と二項演算子を含む式を表します。
3.  **トークン (Token)**: ソースコードを字句解析（スキャン）した結果得られる、意味を持つ最小単位です。`token.ADD`（+）、`token.SUB`（-）、`token.NOT`（!）、`token.SHL`（<<）などが演算子を表すトークンです。
4.  **式評価器 (Expression Evaluator)**: ASTで表現された式を解釈し、その結果の値を計算するコンポーネントです。このコミットでは、`exprCompiler`という構造体がその役割を担っています。
5.  **型チェック (Type Checking)**: 式の各部分がGo言語の型規則に適合しているかを確認するプロセスです。例えば、`+`演算子は数値型または文字列型にのみ適用可能であり、ブール型には適用できません。
6.  **コード生成 (Code Generation)**: 式評価器の場合、ASTを直接実行可能な内部表現（この場合はGoの関数リテラル）に変換するプロセスを指します。このコミットでは、`evalBool`, `evalUint`, `evalInt` などの関数フィールドに、具体的な評価ロジックを持つ関数を割り当てることで、コード生成を行っています。
7.  **`bignum` パッケージ**: Go言語の初期には、任意精度整数（`bignum.Integer`）や任意精度有理数（`bignum.Rational`）を扱うための`bignum`パッケージが存在しました。これは、`ideal` 型の定数評価において、オーバーフローを気にせずに計算を行うために使用されました。

## 技術的詳細

このコミットは、`usr/austin/eval`パッケージ内の式評価器の核となる`exprCompiler`構造体に、Go言語の全ての単項および二項演算子を処理する機能を追加しています。

主要な変更点は以下の通りです。

1.  **`Type` インターフェースの拡張**: `usr/austin/eval/decls.go`において、`Type`インターフェースに`isBoolean() bool`メソッドが追加されました。これにより、型チェック時に特定の型がブール型であるかを効率的に判定できるようになりました。`usr/austin/eval/type.go`では、`commonType`の`isBoolean()`が`false`を返し、`boolType`の`isBoolean()`が`true`を返すように実装されています。

2.  **演算子ジェネレータの導入**: `usr/austin/eval/expr.go`の`exprCompiler`構造体に、`genIdentOp`, `genStarOp`, `genUnaryOpNeg`, `genUnaryOpNot`, `genUnaryOpXor`, `genBinOpAdd`など、各演算子に対応する`gen`プレフィックスの付いたメソッドが多数追加されました。これらのメソッドは、特定の型のオペランドに対して、その演算を実行するためのGoの関数リテラル（クロージャ）を生成し、`exprCompiler`の`eval*`フィールド（例: `evalBool`, `evalUint`, `evalInt`）に割り当てます。これにより、式の評価時に適切な型に応じた演算が実行されるようになります。

3.  **`DoUnaryExpr` および `DoBinaryExpr` のロジック強化**:
    *   `DoUnaryExpr` (単項演算子処理) では、`token.ADD`, `token.SUB`, `token.NOT`, `token.XOR`, `token.AND` (アドレス取得) などの単項演算子に対する型チェックロジックが追加されました。例えば、`!` (NOT) 演算子はブール型にのみ適用可能であることなどがチェックされます。その後、対応する`genUnaryOp*`メソッドを呼び出して評価ロジックを生成します。
    *   `DoBinaryExpr` (二項演算子処理) では、`token.ADD`, `token.SUB`, `token.MUL`, `token.QUO`, `token.REM`, `token.AND`, `token.OR`, `token.XOR`, `token.AND_NOT`, `token.SHL`, `token.SHR` など、Go言語の全ての二項演算子に対する型チェックと評価ロジックの生成が実装されました。特に、シフト演算子 (`<<`, `>>`) の右オペランドが`uint`型であるべきというGoの仕様に合わせた型変換ロジックや、`ideal`型（型付けされていない定数）の扱いに関する複雑なルールが組み込まれています。

4.  **自動生成コードの統合**: コミットの差分を見ると、`expr.go`の末尾に`/* Operator generators Everything below here is MACHINE GENERATED by gen.py genOps */`というコメントとともに、大量の`gen*Op`関数が追加されています。これは、これらの関数が手書きではなく、`gen.py`というスクリプトによって自動生成されたものであることを示しています。これにより、各型と各演算子の組み合わせに対する冗長なコードを効率的に生成し、保守性を高めています。`bignum`パッケージを使用した`ideal`型に対する演算もここで実装されています。

この実装は、Go言語の型システムと演算子のセマンティクスを、式評価器のレベルで忠実に再現しようとする初期の試みであり、特に`ideal`型やシフト演算子の型変換ルールなど、Go言語のユニークな特徴を考慮に入れている点が重要です。

## 変更の背景

このコミットは、Go言語の初期開発段階における式評価器（`usr/austin/eval` パッケージ）の機能拡張の一環として行われました。当時のGo言語はまだ仕様が固まっておらず、コンパイラやツールチェインも発展途上でした。式評価器は、デバッガやインタプリタ、あるいはコンパイル時の定数評価など、様々な場面で必要となる基本的なコンポーネントです。

このコミット以前は、式評価器がサポートする単項および二項演算子の種類が限られていたと考えられます。そのため、より複雑な式や、Go言語の仕様で定義される全ての演算子を正確に処理するためには、これらの演算子の評価ロジックを網羅的に実装する必要がありました。特に、数値型だけでなく、ブール型や文字列型、ポインタ型など、Goが持つ多様な型に対する演算のセマンティクスを正しく反映させることが求められました。

また、`gen.py genOps`というコメントから、これらの演算子生成ロジックがスクリプトによって自動生成されたものであることが示唆されており、これは開発効率の向上と、将来的な演算子追加・変更への対応を容易にするための設計判断であったと考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/インタプリタの基本的な概念が必要です。

1.  **Go言語の型システム**: Go言語は静的型付け言語であり、`int`, `uint`, `float64`, `bool`, `string`, `pointer` など、多様な組み込み型を持ちます。また、`ideal` 型（型付けされていない定数）の概念も重要です。`ideal` 型は、コンパイル時に具体的な型に変換されるまで、より広い精度を持つことができます。
2.  **抽象構文木 (AST: Abstract Syntax Tree)**: プログラムのソースコードを解析して得られる、構文構造を木構造で表現したものです。Go言語の`go/ast`パッケージがこれに該当します。`ast.UnaryExpr`や`ast.BinaryExpr`は、それぞれ単項演算子と二項演算子を含む式を表します。
3.  **トークン (Token)**: ソースコードを字句解析（スキャン）した結果得られる、意味を持つ最小単位です。`token.ADD`（+）、`token.SUB`（-）、`token.NOT`（!）、`token.SHL`（<<）などが演算子を表すトークンです。
4.  **式評価器 (Expression Evaluator)**: ASTで表現された式を解釈し、その結果の値を計算するコンポーネントです。このコミットでは、`exprCompiler`という構造体がその役割を担っています。
5.  **型チェック (Type Checking)**: 式の各部分がGo言語の型規則に適合しているかを確認するプロセスです。例えば、`+`演算子は数値型または文字列型にのみ適用可能であり、ブール型には適用できません。
6.  **コード生成 (Code Generation)**: 式評価器の場合、ASTを直接実行可能な内部表現（この場合はGoの関数リテラル）に変換するプロセスを指します。このコミットでは、`evalBool`, `evalUint`, `evalInt` などの関数フィールドに、具体的な評価ロジックを持つ関数を割り当てることで、コード生成を行っています。
7.  **`bignum` パッケージ**: Go言語の初期には、任意精度整数（`bignum.Integer`）や任意精度有理数（`bignum.Rational`）を扱うための`bignum`パッケージが存在しました。これは、`ideal` 型の定数評価において、オーバーフローを気にせずに計算を行うために使用されました。

## 技術的詳細

このコミットは、`usr/austin/eval`パッケージ内の式評価器の核となる`exprCompiler`構造体に、Go言語の全ての単項および二項演算子を処理する機能を追加しています。

主要な変更点は以下の通りです。

1.  **`Type` インターフェースの拡張**: `usr/austin/eval/decls.go`において、`Type`インターフェースに`isBoolean() bool`メソッドが追加されました。これにより、型チェック時に特定の型がブール型であるかを効率的に判定できるようになりました。`usr/austin/eval/type.go`では、`commonType`の`isBoolean()`が`false`を返し、`boolType`の`isBoolean()`が`true`を返すように実装されています。

2.  **演算子ジェネレータの導入**: `usr/austin/eval/expr.go`の`exprCompiler`構造体に、`genIdentOp`, `genStarOp`, `genUnaryOpNeg`, `genUnaryOpNot`, `genUnaryOpXor`, `genBinOpAdd`など、各演算子に対応する`gen`プレフィックスの付いたメソッドが多数追加されました。これらのメソッドは、特定の型のオペランドに対して、その演算を実行するためのGoの関数リテラル（クロージャ）を生成し、`exprCompiler`の`eval*`フィールド（例: `evalBool`, `evalUint`, `evalInt`）に割り当てます。これにより、式の評価時に適切な型に応じた演算が実行されるようになります。

3.  **`DoUnaryExpr` および `DoBinaryExpr` のロジック強化**:
    *   `DoUnaryExpr` (単項演算子処理) では、`token.ADD`, `token.SUB`, `token.NOT`, `token.XOR`, `token.AND` (アドレス取得) などの単項演算子に対する型チェックロジックが追加されました。例えば、`!` (NOT) 演算子はブール型にのみ適用可能であることなどがチェックされます。その後、対応する`genUnaryOp*`メソッドを呼び出して評価ロジックを生成します。
    *   `DoBinaryExpr` (二項演算子処理) では、`token.ADD`, `token.SUB`, `token.MUL`, `token.QUO`, `token.REM`, `token.AND`, `token.OR`, `token.XOR`, `token.AND_NOT`, `token.SHL`, `token.SHR` など、Go言語の全ての二項演算子に対する型チェックと評価ロジックの生成が実装されました。特に、シフト演算子 (`<<`, `>>`) の右オペランドが`uint`型であるべきというGoの仕様に合わせた型変換ロジックや、`ideal`型（型付けされていない定数）の扱いに関する複雑なルールが組み込まれています。

4.  **自動生成コードの統合**: コミットの差分を見ると、`expr.go`の末尾に`/* Operator generators Everything below here is MACHINE GENERATED by gen.py genOps */`というコメントとともに、大量の`gen*Op`関数が追加されています。これは、これらの関数が手書きではなく、`gen.py`というスクリプトによって自動生成されたものであることを示しています。これにより、各型と各演算子の組み合わせに対する冗長なコードを効率的に生成し、保守性を高めています。`bignum`パッケージを使用した`ideal`型に対する演算もここで実装されています。

この実装は、Go言語の型システムと演算子のセマンティクスを、式評価器のレベルで忠実に再現しようとする初期の試みであり、特に`ideal`型やシフト演算子の型変換ルールなど、Go言語のユニークな特徴を考慮に入れている点が重要です。

## コアとなるコードの変更箇所

このコミットの主要な変更は以下のファイルに集中しています。

*   **`usr/austin/eval/decls.go`**:

    *   `DoIdent`, `DoStarExpr`, `DoUnaryExpr`, `DoBinaryExpr` メソッド内の演算子処理ロジックが大幅に拡張・修正されました。特に、型チェックと、対応する`gen*Op`メソッドの呼び出しが追加されています。

## コアとなるコードの解説

このコミットの核心は、`exprCompiler`がASTノードを走査する際に、各演算子ノード（`ast.UnaryExpr`や`ast.BinaryExpr`）に対して、その演算を実行するための具体的なGo関数（クロージャ）を動的に生成し、`exprCompiler`自身のフィールドに割り当てる点にあります。

例えば、`expr.go`の`DoUnaryExpr`メソッドでは、単項演算子`x.Op`の種類に応じて型チェックを行い、その後、以下のような`genUnaryOp*`メソッドを呼び出します。

```go
func (a *exprCompiler) genUnaryOpNeg(v *exprCompiler) {
	switch _ := v.t.literal().(type) {
	case *uintType:
		vf := v.asUint();
		a.evalUint = func(f *Frame) uint64 { return -vf(f) };
	case *intType:
		vf := v.asInt();
		a.evalInt = func(f *Frame) int64 { return -vf(f) };
	// ... 他の型に対する処理 ...
	default:
		log.Crashf("unexpected operand type %v at %v", v.t.literal(), a.pos);
	}
}
```

この`genUnaryOpNeg`関数は、オペランド`v`の型（`v.t`）に応じて異なる`func`リテラルを`a.evalUint`や`a.evalInt`といったフィールドに割り当てます。これにより、`exprCompiler`が最終的に生成する`Expr`オブジェクトは、その式が評価される際に、適切な型の値に対して正しい演算を実行する関数を持つことになります。

二項演算子についても同様で、`genBinOpAdd`などの関数が、左右のオペランドの型に基づいて`+`演算を実行する関数を生成します。特に、`idealIntType`や`idealFloatType`といった`ideal`型に対しては、`bignum`パッケージの任意精度演算関数（`Add`, `Sub`, `Mul`, `Quo`, `Rem`, `And`, `Or`, `Xor`など）が使用され、コンパイル時の定数評価の精度を保証しています。

シフト演算子 (`<<`, `>>`) の処理は特に複雑で、Goの仕様に従い、右オペランドが`uint`型であること、または`uint`型に安全に変換できる`ideal`型であることを厳密にチェックし、必要に応じて型変換を行います。

このアプローチは、各演算子と型の組み合わせごとに専用の評価ロジックを生成することで、実行時のオーバーヘッドを最小限に抑えつつ、Go言語の厳密な型規則と演算セマンティクスを遵守することを目的としています。

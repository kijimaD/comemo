# [インデックス 15256] ファイルの概要

このコミットは、Go言語のパーサーパッケージ `go/parser` におけるエラー報告の挙動を改善するためのクリーンアップと修正を含んでいます。特に、以前の変更 (CL 7307085) で導入された `AllErrors` フラグの利用を適切化し、デフォルトのエラー報告において「偽のエラー（spurious errors）」を排除することで、より有用で簡潔なエラーメッセージを提供することを目的としています。

## 元コミット内容

このコミットは、Go言語のパーサー (`go/parser`) におけるエラー処理の改善を目的としています。主な変更点は以下の通りです。

1.  **`AllErrors` フラグの適切な利用**: 以前の変更 (CL 7307085) で導入された `AllErrors` フラグを、`gofmt` や `gotype` といったツールで適切に利用するように修正しました。これにより、これらのツールがパーサーからすべてのエラーを受け取るかどうかの挙動を制御できるようになります。
2.  **偽のエラー (Spurious Errors) の排除**: `AllErrors` フラグが設定されていない場合（デフォルトの挙動）、パーサーがエラーリストにエラーを追加する前に、同じ行で既に報告されたエラーを破棄するロジックが追加されました。これは、一つの構文エラーが原因で、その後の解析が混乱し、多数の無関係なエラー（偽のエラー）が報告されるのを防ぐためです。コミットメッセージには「偽のエラーを報告すると、結局のところ、情報量の少ないエラーが多すぎることになる」と明記されており、ユーザーにとってより分かりやすいエラー報告を目指しています。

## 変更の背景

Go言語のコンパイラやツールチェーンにおいて、ソースコードの解析（パース）は非常に重要なステップです。パーサーはコードの構文をチェックし、エラーがあればそれを報告します。しかし、初期のパーサーの実装では、一つの小さな構文エラーが連鎖的に多数の追加エラーを引き起こす「偽のエラー（spurious errors）」を報告することがありました。例えば、セミコロンの欠落や括弧の閉じ忘れが原因で、その後のコードがすべて不正であるかのように見え、大量のエラーメッセージが出力されるといったケースです。

このような偽のエラーは、開発者にとって真の問題を特定することを困難にし、エラーメッセージの有用性を低下させます。このコミットは、以前の変更 (CL 7307085) で導入された `AllErrors` フラグ（すべてのエラーを報告するかどうかを制御する）を基盤として、デフォルトのパーサーの挙動を改善し、偽のエラーを積極的に排除することで、よりクリーンで実用的なエラー報告を実現することを目的としています。これにより、開発者は本当に修正すべきエラーに集中できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておくことが役立ちます。

*   **Go言語のパーサー (`go/parser` パッケージ)**:
    Go言語の標準ライブラリの一部であり、Goのソースコードを解析して抽象構文木 (AST: Abstract Syntax Tree) を構築する機能を提供します。ASTは、コンパイラや静的解析ツールがコードの構造を理解し、処理するために使用するデータ構造です。`go/parser` は、構文エラーを検出した場合にそれを報告する役割も担います。

*   **抽象構文木 (AST)**:
    ソースコードの構造を木構造で表現したものです。例えば、`a + b` という式は、ルートノードが加算演算子、その子ノードが変数 `a` と `b` といった形で表現されます。パーサーはソースコードを読み込み、このASTを生成します。

*   **`token.Pos` と `scanner.ErrorList`**:
    *   `token.Pos`: Go言語のソースコード内の特定の位置（ファイル名、行番号、列番号）を表す型です。エラーメッセージの場所を正確に指し示すために使用されます。
    *   `scanner.ErrorList`: 複数のエラーを格納し、管理するためのGoの標準的なエラー型です。パーサーが複数の構文エラーを検出した場合、これにエラーを追加していきます。

*   **ビットフラグ (Bit Flags)**:
    複数のブール値（真/偽）の状態を単一の整数値で表現するプログラミング手法です。各ビットが特定のオプションのオン/オフに対応します。`go/parser` パッケージでは、`parser.Mode` 型がビットフラグとして定義されており、パーサーの挙動（例: コメントをパースするか、特定のエラーを報告するかなど）を制御するために使用されます。例えば、`parser.ParseComments` や `parser.AllErrors` は、それぞれ特定のビットに対応するフラグです。

*   **偽のエラー (Spurious Errors)**:
    プログラミング言語のパーサーにおいて、一つの真のエラー（例えば、構文の誤り）が原因で、その後のコード解析が混乱し、実際には存在しないか、あるいは真のエラーに起因する二次的な多数のエラーが報告されてしまう現象を指します。これらのエラーは「偽の」または「誤った」エラーと呼ばれ、開発者が根本原因を特定するのを妨げることがあります。このコミットの主要な目的の一つは、この種の偽のエラーを減らすことです。

## 技術的詳細

このコミットの技術的な核心は、`go/parser` パッケージの `parser` 構造体内の `error` メソッドの変更にあります。このメソッドは、パーサーが構文エラーを検出した際に呼び出され、エラーを内部のエラーリストに追加する役割を担っています。

変更前は、`SpuriousErrors` フラグ（後に `AllErrors` のエイリアスとなる）が設定されていない場合、エラーリストの長さが10を超えるとパースを中断していました。これは、あまりにも多くのエラーが報告されるのを防ぐための基本的なメカニズムでした。

変更後、`error` メソッドはより洗練されたロジックを持つようになりました。

1.  **`AllErrors` フラグの利用**: `p.mode&SpuriousErrors == 0` のチェックが `p.mode&AllErrors == 0` に置き換えられました。これは、新しい `AllErrors` フラグを直接参照するようにコードを更新したものです。
2.  **偽のエラーの排除ロジック**: `AllErrors` フラグが設定されていない場合（つまり、デフォルトの挙動の場合）に、以下の新しいチェックが導入されました。
    ```go
    if n > 0 && p.errors[n-1].Pos.Line == epos.Line {
        return // discard - likely a spurious error
    }
    ```
    このコードは、現在報告しようとしているエラー (`epos`) が、既にエラーリストに記録されている最後のエラー (`p.errors[n-1]`) と**同じ行**で発生している場合、そのエラーを破棄します。これは、一つの行における構文エラーが原因で、パーサーがその行の複数の場所でエラーを報告してしまう「偽のエラー」を効果的に排除するためのメカニズムです。例えば、`func main() {` の後に `}` がない場合、その行の複数のトークンに対してエラーが報告される可能性がありますが、このロジックにより最初の有用なエラーのみが保持され、残りは破棄されます。
3.  **エラー数制限の適用**: エラー数が10を超えた場合にパースを中断するロジック (`if n > 10 { panic(bailout{}) }`) は引き続き存在しますが、これも `AllErrors` フラグが設定されていない場合にのみ適用されるようになりました。これにより、`AllErrors` が設定されている場合は、エラーの数に関わらずすべてのエラーが報告されることが保証されます。

この変更により、`go/parser` はデフォルトでより「賢く」エラーを報告するようになり、開発者にとってのエラーメッセージのノイズが大幅に削減されます。`AllErrors` フラグを明示的に設定することで、すべてのエラー（偽のエラーも含む）を詳細に取得することも可能です。

また、`src/cmd/gofmt/gofmt.go` と `src/pkg/exp/gotype/gotype.go` では、コマンドラインオプション `-e` の意味が「すべてのエラーを報告する（異なる行の最初の10個だけでなく）」とより明確に記述され、内部的には `parser.SpuriousErrors` から `parser.AllErrors` フラグを使用するように更新されています。これは、この新しいエラー報告の挙動をユーザーインターフェースに反映させたものです。

`src/pkg/go/parser/error_test.go` と `src/pkg/go/types/check_test.go` では、テストコードが `parser.AllErrors` フラグを明示的に使用するように変更されています。これにより、テストがパーサーのすべてのエラー報告能力を検証できるようになり、この変更が意図通りに機能していることを保証します。

## コアとなるコードの解説

上記の `error` メソッドの変更は、Goパーサーのエラー報告戦略の核心をなしています。

1.  **`epos := p.file.Position(pos)`**:
    まず、`token.Pos` 型の `pos`（エラーが発生したソースコード上の抽象的な位置）を、より具体的なファイル、行、列の情報を含む `token.Position` 型の `epos` に変換しています。これにより、エラーの発生位置を正確に特定できます。

2.  **`if p.mode&AllErrors == 0`**:
    この条件は、パーサーが `AllErrors` フラグ（またはそのエイリアスである `SpuriousErrors`）が設定されていない「デフォルト」モードで動作しているかどうかをチェックします。`AllErrors` フラグが設定されている場合、パーサーはすべてのエラーを報告するため、以下の偽のエラー排除ロジックはスキップされます。

3.  **`n := len(p.errors)`**:
    現在までに記録されているエラーの数を取得します。

4.  **`if n > 0 && p.errors[n-1].Pos.Line == epos.Line`**:
    これが偽のエラーを排除するための主要なロジックです。
    *   `n > 0`: 既に少なくとも1つのエラーが記録されていることを確認します。
    *   `p.errors[n-1].Pos.Line == epos.Line`: 現在報告しようとしているエラー (`epos`) の行番号が、既に記録されている最後のエラー (`p.errors[n-1]`) の行番号と**同じ**であるかをチェックします。
    *   もしこの条件が真であれば、`return` ステートメントが実行され、現在のエラーはエラーリストに追加されずに破棄されます。これは、同じ行で発生した複数のエラーのうち、最初の有用なエラーのみを保持し、その後の重複または派生的なエラーを「偽のエラー」として無視するためです。

5.  **`if n > 10`**:
    この条件は、エラーの数が10を超えた場合に `panic(bailout{})` を発生させ、パース処理を中断します。これは、あまりにも多くのエラーが報告されるのを防ぐための「早期終了」メカニズムです。この制限は、`AllErrors` フラグが設定されていない場合にのみ適用されます。

6.  **`p.errors.Add(epos, msg)`**:
    上記の偽のエラー排除ロジックを通過した場合、エラーの `token.Position` (`epos`) とエラーメッセージ (`msg`) がパーサーのエラーリスト (`p.errors`) に追加されます。

この変更により、Goパーサーはデフォルトで、より簡潔で、開発者にとって本当に重要なエラーに焦点を当てたエラー報告を行うようになります。

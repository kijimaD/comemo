# [インデックス 23512] ファイルの概要

このコミットは、Goコンパイラの内部コードジェネレータ（`cmd/internal/gc`）における、ARMアーキテクチャ上での64ビット定数のスライス操作（`cgen_slice`）の取り扱いに関するバグ修正です。具体的には、32ビットアーキテクチャであるARMにおいて、スライス操作のインデックスとして64ビット定数が使用された際に、正しく境界チェックが行われない可能性があった問題を解決します。

## 変更の背景

Go言語のコンパイラ（`cmd/internal/gc`）は、ソースコードを各ターゲットアーキテクチャの機械語に変換する役割を担っています。この過程で、スライス操作（例: `s[i:j:k]`）は、配列の境界チェックやポインタの計算など、様々な低レベルな処理に変換されます。

問題は、32ビットアーキテクチャであるARMにおいて、スライスのインデックス（`i`, `j`, `k`）として64ビットの定数が与えられた場合に発生しました。Go言語の型システムでは、`int`型は通常32ビットまたは64ビットのいずれかですが、定数式はより広い範囲の値を表現できます。32ビットアーキテクチャでは、レジスタサイズが32ビットであるため、64ビット定数を直接扱う際に特別な注意が必要です。

このコミットが修正しようとしているのは、`cgen_slice`関数内でスライスの境界チェックを行う際に、64ビット定数が正しく32ビット値として扱われず、結果として境界チェックが誤って行われる、あるいは完全にスキップされる可能性があった点です。特に、`ginscmp`というアーキテクチャ固有の比較命令生成関数が関与していることが示唆されており、386アーキテクチャではこの問題が発生しないと明記されています。

コミットメッセージに記載されている「Fixes #10843」は、GoのIssueトラッカーにおける特定のバグ報告を指していますが、現在のWeb検索ではその詳細を特定できませんでした。しかし、コミット内容から、この問題がスライス操作における潜在的なメモリ安全性違反（out-of-boundsアクセス）につながる可能性のある重要なバグであったことが推測されます。

## 前提知識の解説

*   **Goコンパイラ (`cmd/internal/gc`)**: Go言語の公式コンパイラの一部で、Goのソースコードを中間表現に変換し、最終的に各ターゲットアーキテクチャの機械語にコンパイルする役割を担います。`cgen.go`ファイルは、コード生成（code generation）のフェーズに関連する処理を含んでいます。
*   **スライス (`slice`)**: Go言語の組み込み型で、可変長シーケンスを表現します。内部的には、基盤となる配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。スライス操作（例: `a[low:high]`）は、新しいスライスを生成したり、既存のスライスの部分を参照したりするために使われます。
*   **`cgen_slice` 関数**: Goコンパイラのコード生成フェーズにおいて、スライス操作（`slice`式）を処理する関数です。この関数は、スライスのインデックスの境界チェックや、新しいスライスヘッダの構築などを行います。
*   **`ginscmp`**: Goコンパイラのバックエンドで、特定のアーキテクチャ（この場合はARM）向けに比較命令を生成するための内部関数です。異なるアーキテクチャでは、比較命令の生成方法やレジスタの扱いが異なるため、このようなアーキテクチャ固有の関数が存在します。
*   **64ビット定数と32ビットアーキテクチャ**: 32ビットアーキテクチャ（例: ARMv7）では、CPUのレジスタが32ビット幅です。しかし、Go言語の定数式は、例えば`1 << 32`のような64ビットの値を表現できます。これらの64ビット定数を32ビットレジスタで扱う場合、通常は複数のレジスタを使用したり、特別な命令を使ったりする必要があります。このコミットの文脈では、64ビット定数が32ビット値として誤って解釈され、比較が正しく行われない問題が指摘されています。
*   **`Mpint`**: Goコンパイラ内部で多倍長整数（multi-precision integer）を扱うための型です。定数式は、通常の`int`型や`int64`型で表現できる範囲を超える可能性があるため、`Mpint`のような型で表現されます。
*   **`Mpgetfix`**: `Mpint`型の値を固定幅の整数（例: `int64`）に変換する関数です。
*   **`mpcmpfixc`**: `Mpint`型の値と固定幅の定数を比較する関数です。
*   **`Ctxt.Arch.Regsize`**: 現在コンパイルしているターゲットアーキテクチャのレジスタサイズ（バイト単位）を示すコンパイラコンテキストのフィールドです。ARMv7のような32ビットアーキテクチャでは`4`（バイト）になります。
*   **`indexRegType`**: スライスのインデックスに使用されるレジスタの型を定義するコンパイラ内部の型です。通常、これはポインタサイズと同じになります。
*   **`Fatal("missed slice out of bounds check")`**: コンパイラが内部で致命的なエラーを検出した場合に呼び出される関数です。このメッセージは、スライスの境界チェックが何らかの理由で見落とされたことを示しており、非常に深刻な問題です。

## 技術的詳細

このコミットの核心は、32ビットアーキテクチャ（特にARM）上で`cgen_slice`関数がスライスのインデックスとして64ビット定数を扱う際の挙動を修正することにあります。

Goコンパイラでは、スライスのインデックス`i`, `j`, `k`は、`indexRegType`という型で表現されます。これは通常、ターゲットアーキテクチャのポインタサイズと同じ幅を持ちます。32ビットアーキテクチャでは、`indexRegType`は32ビット幅です。

しかし、Goの定数式は、例えば`1 << 32`のように、32ビットでは表現できない64ビットの値を生成することが可能です。このような64ビット定数がスライスのインデックスとして使用された場合、`cgen_slice`内の`compare`関数（スライスの境界チェックを行うためのヘルパー関数）が問題を引き起こしていました。

`compare`関数は、`Thearch.Ginscmp`を使用して2つのノード（`n1`, `n2`）を比較し、境界外アクセスが発生した場合にパニックを生成するコードを生成します。ここで`n1`が64ビット定数である場合、`ginscmp`に渡される前に、その値が32ビットレジスタに収まるように適切に処理される必要がありました。

修正前のコードでは、`n1`が64ビット定数であっても、32ビットアーキテクチャ上でそれが32ビット値として扱われることを前提としていました。しかし、`Mpint`で表現される64ビット定数が`1 << 31`（32ビット符号付き整数の最大値+1）以上の値を持つ場合、それは32ビット符号付き整数としては負の値として解釈されるか、あるいはオーバーフローしてしまい、正しい比較が行われませんでした。これにより、本来パニックすべき境界外アクセスが検出されずに、不正なメモリアクセスが発生する可能性がありました。

このコミットでは、`compare`関数内に以下のロジックを追加することでこの問題を解決しています。

1.  **アーキテクチャと型のチェック**: まず、現在のアーキテクチャのレジスタサイズが4バイト（32ビット）であり、かつ比較対象のノード`n1`の型が64ビットであるかをチェックします。
2.  **64ビット定数の値チェック**: `n1`が64ビット定数である場合、その値が`1 << 31`以上であるかを`mpcmpfixc`関数を使って確認します。これは、32ビット符号付き整数で表現できない大きな正の数であるかをチェックするものです。
3.  **致命的エラーの検出**: もし`n1`が32ビットアーキテクチャ上で`1 << 31`以上の64ビット定数であり、かつそれがスライスのインデックスとして使われている場合、これは「missed slice out of bounds check」（スライスの境界チェックの見落とし）という致命的なエラーとして扱われます。これは、コンパイラがこのような状況を正しく処理できていないことを意味し、即座にコンパイルを停止させます。
4.  **32ビット値への変換**: エラーではない場合（つまり、64ビット定数だが32ビットで表現可能な範囲内である場合）、`Mpgetfix`を使って`n1`の`Mpint`値を32ビットの固定幅整数に変換し、新しい定数ノード`tmp`を作成します。そして、この`tmp`ノードを`n1`の代わりに`ginscmp`に渡します。これにより、`ginscmp`は常に32ビットの値を比較することになり、正しいコードが生成されます。

この修正により、32ビットARMアーキテクチャ上で64ビット定数がスライスのインデックスとして使用された場合でも、コンパイラがその値を正しく扱い、適切な境界チェックコードを生成するか、あるいはコンパイル時に問題を検出してエラーを報告するようになります。

## コアとなるコードの解説

追加されたコードブロックは、`cgen_slice`関数内で定義されている`compare`という無名関数の中にあります。この`compare`関数は、スライスのインデックス`n1`と境界値`n2`を比較し、境界チェックのコードを生成する役割を担っています。

1.  `if Ctxt.Arch.Regsize == 4 && Is64(n1.Type) { ... }`
    *   この条件は、現在のターゲットアーキテクチャが32ビット（レジスタサイズが4バイト）であり、かつ比較対象のノード`n1`が64ビット型である場合にのみ、以下の処理を実行することを示しています。これは、問題が32ビットアーキテクチャ上の64ビット定数に特化しているためです。
    *   `Ctxt.Arch.Regsize == 4`: コンパイラが32ビットアーキテクチャ（例: ARMv7）をターゲットにしていることを確認します。
    *   `Is64(n1.Type)`: `n1`が64ビット整数型（例: `int64`, `uint64`）であることを確認します。

2.  `if mpcmpfixc(n1.Val.U.(*Mpint), 1<<31) >= 0 { Fatal("missed slice out of bounds check") }`
    *   この行は、`n1`が定数であり、その値が`1 << 31`（32ビット符号付き整数の最大値+1）以上であるかをチェックします。
    *   `n1.Val.U.(*Mpint)`: `n1`が定数ノードである場合、その値は`Mpint`型として格納されています。これを取得します。
    *   `mpcmpfixc(..., 1<<31) >= 0`: `n1`の`Mpint`値と`1 << 31`を比較します。もし`n1`の値が`1 << 31`以上であれば、それは32ビット符号付き整数では表現できない大きな正の数です。
    *   `Fatal("missed slice out of bounds check")`: この条件が真の場合、コンパイラは致命的なエラーを発生させます。これは、32ビットアーキテクチャ上で32ビットレジスタに収まらない64ビット定数がスライスのインデックスとして使われ、かつその値が境界チェックのロジックで正しく扱えないことを意味します。このような状況は、コンパイラのバグであり、実行時に不正なメモリアクセスを引き起こす可能性があるため、コンパイルを中止して開発者に問題を知らせるのが最善です。

3.  `var tmp Node`
    *   新しい`Node`型の変数`tmp`を宣言します。これは、64ビット定数を32ビット値として表現するための新しいノードを作成するために使用されます。

4.  `Nodconst(&tmp, indexRegType, Mpgetfix(n1.Val.U.(*Mpint)))`
    *   `tmp`ノードを定数ノードとして初期化します。
    *   `indexRegType`: `tmp`ノードの型をスライスのインデックスレジスタの型に設定します（32ビットアーキテクチャでは32ビット）。
    *   `Mpgetfix(n1.Val.U.(*Mpint))`: `n1`の`Mpint`値を、`indexRegType`に適合する固定幅の整数（この場合は32ビット整数）に変換して取得します。これにより、`n1`の64ビット定数から、32ビットで表現可能な部分が抽出されます。

5.  `n1 = &tmp`
    *   元の`n1`ノードを、新しく作成した32ビット定数ノード`tmp`で置き換えます。これにより、`Thearch.Ginscmp`関数には常に32ビットの定数ノードが渡されるようになり、32ビットアーキテクチャ上で正しく比較命令が生成されるようになります。

この一連の変更により、Goコンパイラは32ビットアーキテクチャ上で64ビット定数がスライスのインデックスとして使用された場合でも、その値を安全かつ正確に処理できるようになり、潜在的なメモリ安全性問題を回避します。

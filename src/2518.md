## 変更の背景

このコミットは、Go言語の初期開発段階におけるコードベースの整理とリファクタリングの一環として行われたと考えられます。コミットメッセージが「dreg」（残りかす、不要物）と非常に簡潔であることから、`src/pkg/os/proc_linux.go`ファイルがもはやGoランタイムの設計において必要とされなくなった、あるいはその機能が他のより適切な場所へ統合・移動されたことを示唆しています。

Go言語の初期は、様々なOS固有の実装が試行錯誤され、その後に共通化されたり、より洗練された抽象化レイヤーの下に隠蔽されたりする過程がありました。`proc_linux.go`のようなファイルは、当初はLinuxシステムコールを直接扱うための場所として存在していたものの、Goのクロスプラットフォーム対応やランタイムの内部構造の成熟に伴い、その役割を終えたと推測されます。特に、`os`パッケージの役割はOSに依存しない汎用的なインターフェースを提供することであり、特定のOSの低レベルな実装は`syscall`パッケージやランタイム内部で処理されることが一般的です。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念とパッケージに関する知識が必要です。

*   **`os`パッケージ**: Go言語の標準ライブラリの一部で、オペレーティングシステムとの相互作用（ファイル操作、プロセス管理、環境変数、コマンドライン引数など）のための汎用的なインターフェースを提供します。OSに依存しない形でこれらの機能を利用できるように設計されています。
*   **`syscall`パッケージ**: 低レベルなシステムコールへのアクセスを提供します。OS固有の機能や、`os`パッケージでは抽象化しきれない詳細な制御が必要な場合に使用されます。プラットフォームごとに異なる実装を持つことが多く、通常は直接アプリケーションコードから利用するよりも、標準ライブラリの内部で利用されることが多いです。
*   **Goランタイム**: Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューラ、システムコールインターフェースなど、プログラムの実行に必要な低レベルな機能を提供します。コマンドライン引数（`os.Args`）や環境変数（`os.Environ`）の初期化もランタイムの役割の一部です。
*   **`os.Args`と`os.Environ`**: Goプログラムが起動される際に、コマンドライン引数と環境変数はランタイムによって初期化され、それぞれ`os.Args`（`[]string`型）と`os.Environ`（`[]string`型）として`os`パッケージを通じて利用可能になります。
*   **`os.Exit`**: プログラムを終了させるための関数です。引数として終了コード（整数）を取り、通常0は成功、非ゼロはエラーを示します。内部的にはOSの終了システムコールを呼び出します。
*   **`syscall.SYS_EXIT_GROUP`**: Linuxシステムコールの一つで、プロセスグループ全体を終了させるために使用されます。`exit()`システムコールが単一のスレッドを終了させるのに対し、`exit_group()`はマルチスレッドプログラム全体を終了させるために推奨されます。Goランタイムはマルチスレッドで動作するため、プログラム全体の終了には`exit_group`が適切です。

## 技術的詳細

削除された`src/pkg/os/proc_linux.go`ファイルの内容は以下の通りでした。

```go
// Copyright 2009 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package os

import (
	"os";
	"syscall";
)

var Args []string;	// provided by runtime
var Envs []string;	// provided by runtime

// Exit causes the current program to exit with the given status code.
// Conventionally, code zero indicates success, non-zero an error.
func Exit(code int) {
	syscall.Syscall(syscall.SYS_EXIT_GROUP, int64(code), 0, 0)
}
```

このファイルは、`os`パッケージの一部として、Linux環境におけるプロセス関連の非常に基本的な機能を提供していました。

1.  **`Args`と`Envs`変数の宣言**:
    `var Args []string`と`var Envs []string`は、それぞれコマンドライン引数と環境変数を保持するためのスライスとして宣言されていました。コメントには「provided by runtime」とあり、これらの変数の実際の値はGoランタイムによって初期化されることが示されています。
    初期のGoでは、これらの変数がOS固有のファイルで宣言されていた可能性がありますが、最終的には`os`パッケージのより汎用的な部分、あるいはランタイムの内部で直接管理されるようになりました。`os.Args`と`os.Environ`は、現在では`os`パッケージの公開APIとして提供されていますが、その実体はランタイムが管理しています。

2.  **`Exit`関数の実装**:
    `func Exit(code int)`は、プログラムを終了させるための関数です。その実装は`syscall.Syscall(syscall.SYS_EXIT_GROUP, int64(code), 0, 0)`となっており、Linuxの`exit_group`システムコールを直接呼び出していました。
    これは、Goプログラムがマルチスレッドで動作する（特にGoルーチンがOSスレッドにマッピングされる）ため、単一の`exit`システムコールではなく、プロセスグループ全体を終了させる`exit_group`を使用することが適切であるという設計判断に基づいています。
    この`Exit`関数の実装も、最終的には`os`パッケージのより汎用的な部分に移動されたか、あるいはランタイム内部で抽象化され、OS固有の`syscall`の直接呼び出しが`os`パッケージの公開APIから隠蔽される形になったと考えられます。これにより、`os.Exit`はどのOSでも同じように動作するようになり、内部的なOS依存性はランタイムが吸収する形になりました。

このファイルの削除は、Goランタイムが成熟し、OS固有の低レベルな実装がより抽象化されたレイヤーに統合されたことを明確に示しています。これにより、`os`パッケージは真にクロスプラットフォームなインターフェースとして機能するようになり、開発者はOSの違いを意識することなくプロセス関連の操作を行えるようになりました。

## コアとなるコードの解説

`src/pkg/os/proc_linux.go`ファイルの削除は、GoランタイムがLinux環境でプロセスを扱う方法の根本的な変更を意味します。このファイルが提供していた`Args`、`Envs`、`Exit`といった機能は、Goプログラムの実行において非常に基本的な要素です。

このファイルの削除が意味するのは、これらの機能がもはやLinux固有のファイルで直接実装される必要がなくなったということです。考えられる理由はいくつかあります。

1.  **汎用的な実装への移行**: `Args`、`Envs`、`Exit`のような機能は、ほとんどのオペレーティングシステムで共通の概念です。Goの設計思想として、可能な限りOSに依存しないコードを書くことが推奨されます。したがって、これらの機能のOS固有の実装が、より汎用的なコードパスに統合された可能性が高いです。例えば、ランタイムのコア部分でOSの差異を吸収し、`os`パッケージからは共通のインターフェースを提供するようになった、といった変更が考えられます。
2.  **ランタイム内部への隠蔽**: `syscall.Syscall`を直接呼び出すような低レベルな操作は、`os`パッケージのような高レベルなAPIからは隠蔽されるべきです。これらの機能はGoランタイムの内部で処理され、`os`パッケージはランタイムが提供する抽象化されたインターフェースを利用する形になったと推測されます。これにより、`os`パッケージのコードはよりクリーンになり、OS固有の複雑さから解放されます。
3.  **初期の試行錯誤の残骸**: Go言語の初期段階では、様々な実装アプローチが試されました。`proc_linux.go`は、その過程で一時的に存在したLinux固有の実装の「残りかす」（dreg）であり、より良い設計が確立されたことで削除された、という可能性も十分にあります。

この削除により、Goの`os`パッケージはより一貫性のあるクロスプラットフォームなAPIを提供できるようになり、内部の実装はよりモジュール化され、保守性が向上したと考えられます。

runtime: fix freed page accounting in mHeap_ReclaimList

mHeap_ReclaimList is asked to reclaim at least npages pages, but it
counts the number of spans reclaimed, not the number of pages

## 変更の背景

このコミットは、Goランタイムのメモリ管理におけるバグ修正を目的としています。具体的には、`mHeap_ReclaimList`関数が、要求されたページ数ではなく、回収されたスパンの数を誤ってカウントしていた問題に対処しています。

`mHeap_ReclaimList`は、少なくとも`npages`（指定されたページ数）を回収するように求められます。しかし、以前の実装では、回収されたスパンの数をカウントしていました。1つのスパンには複数のページが含まれるため、回収されたスパンの数でカウントすると、実際に回収されたページ数よりも少ない値がカウントされてしまいます。これにより、`mHeap_ReclaimList`は、呼び出し元が意図したよりも多くのメモリを回収しようとしてしまい、結果として大きなメモリ割り当てが遅延するという問題が発生していました。

コミットメッセージには「Fixes #9048」と記載されており、この変更が特定のバグ報告（Issue 9048）に対応するものであることを示唆しています。ただし、公開されているGoのIssueトラッカーで直接このIssueを見つけることはできませんでした。これは、Issueが非常に古いか、内部的なトラッカーに存在していた可能性を示唆しています。

この問題は、メモリの過剰な回収が、特に大きなメモリブロックを必要とするアプリケーションのパフォーマンスに悪影響を与える可能性があるため、修正が必要でした。

## 前提知識の解説

Goランタイムのメモリ管理は、ヒープ（heap）と呼ばれる領域を管理し、プログラムが動的にメモリを割り当てる際に使用します。このメモリ管理は、ガベージコレクション（GC）と密接に関連しています。

*   **ヒープ (Heap)**: Goプログラムが実行時に動的にメモリを割り当てる主要な領域です。
*   **mHeap**: Goランタイムにおけるヒープ全体の管理構造体です。メモリの割り当て、解放、ガベージコレクションの調整などを行います。
*   **mSpan**: ヒープは、`mSpan`と呼ばれる連続したページ（通常は8KB）のチャンクに分割されます。`mSpan`は、特定のサイズのオブジェクトを格納するために使用されるか、または大きなオブジェクトのために複数のページを結合して使用されます。各`mSpan`は、それが管理するページの数（`npages`）を持っています。
*   **ページ (Page)**: メモリ管理の最小単位であり、通常は4KBまたは8KBの固定サイズです。Goランタイムでは、これらのページを`mSpan`にまとめて管理します。
*   **ガベージコレクション (Garbage Collection, GC)**: Goのランタイムは自動的に不要になったメモリを回収します。GCは、プログラムが使用しなくなったオブジェクトを特定し、それらが占めていたメモリを再利用可能にします。
*   **メモリの再利用 (Reclamation)**: GCによって不要と判断されたメモリは、将来の割り当てのために再利用可能な状態にされます。`mHeap_ReclaimList`のような関数は、この再利用プロセスの一部として機能します。
*   **スイープ (Sweep)**: ガベージコレクションのフェーズの一つで、マークされたオブジェクト以外のメモリを解放し、再利用可能な状態にするプロセスです。`mSpan_Sweep`関数は、特定のスパンに対してこのスイープ処理を実行します。

## 技術的詳細

このコミットが修正する問題は、`mHeap_ReclaimList`関数における「解放されたページ数の誤った計上」です。

`mHeap_ReclaimList`の目的は、指定された`npages`（ページ数）以上のメモリを回収することです。この関数は、ヒープから回収可能な`mSpan`を探索し、それらをスイープして再利用可能な状態にします。

問題は、以前の実装では、`mSpan_Sweep`が呼び出された後に、回収されたメモリの量を`n++`という形でカウントしていた点にあります。これは、回収された「スパンの数」を1つずつ増やしていることを意味します。しかし、各`mSpan`は1ページだけでなく、複数のページ（`s.npages`）で構成されている場合があります。

したがって、`n++`というカウント方法は、実際に回収された「ページ数」を過小評価していました。例えば、`mHeap_ReclaimList`が100ページを回収するように要求された場合、以前の実装では100個のスパンを回収しようとしました。しかし、もし各スパンが平均して4ページを持っていたとすると、実際には400ページが回収されてしまうことになります。

この過小評価により、`mHeap_ReclaimList`は、要求された`npages`に到達したと誤って判断するまでに、必要以上に多くのスパンをスイープし、結果として必要以上に多くのメモリを回収してしまっていました。この「過剰な回収」は、特に大きなメモリ割り当てを必要とする操作において、メモリの再利用が遅延し、パフォーマンスの低下を引き起こす可能性がありました。

コミットメッセージにある「It is undercounting the number of pages reclaimed.」という記述は、この過小評価の問題を明確に指摘しています。そして、「forcing more reclamation than was intended by the caller, which delays large allocations.」という記述は、その結果として生じるパフォーマンスへの悪影響を説明しています。

変更前は、`mSpan_Sweep`が成功した場合（つまり、スパンがスイープされ、再利用可能になった場合）、単に`n++`としていました。これは、回収されたスパンの数をカウントしているだけであり、そのスパンが実際に何ページで構成されているかを考慮していませんでした。コメントにも明示的に「It is undercounting the number of pages reclaimed.」と書かれており、この問題が認識されていたことがわかります。また、「Note that if we want to add the true count of s's pages, we must record that before calling mSpan_Sweep, because if mSpan_Sweep returns true the span has been」というコメントは、`mSpan_Sweep`がスパンの状態を変更する可能性があるため、正確なページ数を取得するためにはスイープ前に`s.npages`を保存する必要があることを示唆しています。

```go

				n += snpages
			}

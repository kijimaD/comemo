# [インデックス 22791] ファイルの概要

このコミットは、Goリンカー (`cmd/internal/ld`) における共有ライブラリ生成のフラグ体系を再構築するものです。既存の `-shared` フラグを、より明確で将来的な拡張性を持つ `-buildmode=c-shared` へと移行し、`-shared` は互換性のためにエイリアスとして残されています。これにより、Goの「実行モード (Go Execution Modes)」という概念が導入され、リンカーの挙動がより体系的に管理されるようになります。

## 変更の背景

この変更の主な背景には、Go言語のビルドシステムにおける「共有」という概念の曖昧さと、将来的な「Go実行モード (Go Execution Modes)」の導入計画があります。

Goリンカーは、特定のプラットフォームにおいて `-shared` フラグをサポートしていました。このフラグは、Goコードを共有ライブラリとしてビルドする際に使用され、C言語から呼び出し可能な形式（C-callable shared library）を生成する機能を持っていました。しかし、Goの進化に伴い、様々なビルドモード（例: プラグイン、WebAssemblyなど）が検討される中で、「shared」という用語が複数の異なる意味合いで使われるようになり、その意味が過負荷（overloaded）になっていました。

具体的には、Go 1.5で導入された `c-shared` ビルドモードは、GoパッケージをC言語から利用可能な共有ライブラリとしてコンパイルすることを目的としています。これは、Goの強力な並行処理やパフォーマンスを他の言語のアプリケーションに組み込むための重要な機能です。この新しいビルドモードの導入に際し、既存の `-shared` フラグが指す意味と、新しい `c-shared` の意味が重複し、混乱を招く可能性がありました。

このコミットは、このような混乱を解消し、リンカーのオプションをより体系的に整理するために行われました。`-shared` フラグを廃止し、より汎用的な `-buildmode` フラグを導入することで、将来的に追加される可能性のある様々なビルドモードを統一的なインターフェースで管理できるようにしています。Go 1.4でリンカーが `-shared` をサポートしていたため、後方互換性を保つために `-shared` は `-buildmode=c-shared` のエイリアスとして残されています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびリンカーに関する前提知識が必要です。

*   **Goリンカー (`cmd/internal/ld`)**: Goコンパイラツールチェーンの一部であり、Goのソースコードから実行可能ファイルやライブラリを生成する役割を担います。Goのランタイム、標準ライブラリ、ユーザーコードなどを結合し、最終的なバイナリを作成します。
*   **共有ライブラリ (Shared Library)**: 複数のプログラムから共有して利用できるライブラリのことです。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化などが可能になります。C言語の文脈では `.so` (Linux), `.dll` (Windows), `.dylib` (macOS) などの形式で提供されます。
*   **`c-shared` ビルドモード**: Go 1.5で導入されたビルドモードの一つで、GoのパッケージをC言語から呼び出し可能な共有ライブラリとしてコンパイルします。これにより、Goで書かれたロジックをC、Python、Javaなどの他の言語のアプリケーションから利用できるようになります。`go build -buildmode=c-shared` コマンドで利用されます。このモードでビルドされたライブラリは、Goランタイムを内包し、Cのヘッダーファイルも生成されます。
*   **`Flag_shared` (旧フラグ)**: このコミット以前にリンカーで使用されていた内部フラグで、共有ライブラリをビルドするかどうかを制御していました。このフラグは整数型で、0以外の場合に共有ライブラリビルドモードが有効になるという慣習的な使われ方をしていました。
*   **`Buildmode` (新フラグ)**: このコミットで導入された新しい型で、Goのビルドモードを明示的に表現するための列挙型です。`BuildmodeExe` (通常の実行可能ファイル) と `BuildmodeCShared` (C-callable共有ライブラリ) などの値を取ります。これにより、リンカーの挙動がより明確に定義されます。
*   **`INITENTRY`**: Goプログラムのエントリポイント（初期化関数）の名前を指すリンカー内部の定数です。通常の実行可能ファイルと共有ライブラリでは、このエントリポイントの名前が異なります。
*   **`R_TLS` (Thread Local Storage Relocation)**: スレッドローカルストレージ (TLS) に関連する再配置タイプです。TLSは、各スレッドが独自のデータを持つことを可能にするメカニズムで、共有ライブラリの文脈で重要になることがあります。
*   **`Linkmode`**: リンカーのリンクモードを制御するフラグです。`LinkInternal` はGoリンカーが完全に内部でリンク処理を行うことを意味し、`LinkExternal` は外部リンカー（例: GCC）を使用することを意味します。共有ライブラリのビルドでは、通常、外部リンカーが必要となります。

## 技術的詳細

このコミットの技術的な核心は、Goリンカー内部で共有ライブラリビルドモードを制御するメカニズムを、従来の `Flag_shared` という単純な整数フラグから、より構造化された `Buildmode` 型へと移行した点にあります。

1.  **`BuildMode` 型の導入**:
    `src/cmd/internal/ld/lib.go` に `BuildMode` という新しい型が定義されました。これは `uint8` を基盤とする列挙型で、以下の定数を持ちます。
    *   `BuildmodeExe`: 通常の実行可能ファイルをビルドするモード。
    *   `BuildmodeCShared`: C言語から呼び出し可能な共有ライブラリをビルドするモード。
    この型には、コマンドライン引数から値を設定するための `Set(s string) error` メソッドと、文字列表現を返す `String() string` メソッドが実装されています。`Set` メソッドでは、`c-shared` モードが `amd64` および `arm` アーキテクチャでのみサポートされるという制約もチェックされます。

2.  **`Flag_shared` から `Buildmode` への置き換え**:
    リンカーコードベース全体で、`Flag_shared != 0` という条件式が `Buildmode == BuildmodeCShared` に置き換えられました。これにより、リンカーの挙動がどのビルドモードに依存しているかが明確になります。影響を受けたファイルは `src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/6l/obj.go`, `src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`, `src/cmd/internal/ld/go.go`, `src/cmd/internal/ld/lib.go` です。

3.  **`-buildmode` コマンドラインフラグの追加**:
    `src/cmd/internal/ld/pobj.go` の `Ldmain` 関数内で、`flag.Var(&Buildmode, "buildmode", "build mode to use")` という行が追加され、リンカーが `-buildmode` コマンドライン引数を受け入れるようになりました。これにより、ユーザーは `go build -buildmode=c-shared` のように、明示的にビルドモードを指定できるようになります。

4.  **`-shared` フラグのエイリアス化と互換性**:
    Go 1.4で `-shared` フラグが導入されていたため、後方互換性を維持するために、`-shared` フラグは `-buildmode=c-shared` のエイリアスとして機能するように変更されました。
    `src/cmd/internal/ld/pobj.go` では、`flagShared` という一時的な変数が導入され、`-shared` フラグの値を捕捉します。`Ldmain` の初期化段階で、もし `flagShared` が設定されており、かつ `Buildmode` がまだ `BuildmodeExe` (デフォルト) のままであれば、`Buildmode` を `BuildmodeCShared` に設定します。もし `-shared` と `-buildmode` が矛盾する形で指定された場合は、エラー (`Diag`) を出力して終了します。

5.  **`INITENTRY` の決定ロジックの変更**:
    `src/cmd/internal/ld/lib.go` の `libinit` 関数内で、`INITENTRY` の決定ロジックが `Flag_shared` から `Buildmode` の `switch` 文に変更されました。これにより、ビルドモードに応じて適切なエントリポイント名が設定されます。
    *   `BuildmodeCShared` の場合: `_rt0_%s_%s_lib` (共有ライブラリ用)
    *   `BuildmodeExe` の場合: `_rt0_%s_%s` (実行可能ファイル用)

6.  **リンカーオプションの調整**:
    `src/cmd/internal/ld/lib.go` の `hostlink` 関数では、`Flag_shared != 0` の条件が `Buildmode == BuildmodeCShared` に変更され、共有ライブラリビルド時に `-Wl,-Bsymbolic` や `-shared` といった外部リンカーオプションが適切に渡されるようになっています。

これらの変更により、Goリンカーのビルドモード管理がより堅牢で拡張性の高いものとなり、将来的なGoのビルドシステム開発の基盤が強化されました。

// A BuildMode indicates the sort of object we are building:
//   "exe": build a main package and everything it imports into an executable.
//   "c-shared": build a main package, plus all packages that it imports, into a
//     single C shared library. The only callable symbols will be those functions
// //     marked as exported.
type BuildMode uint8

const (
	BuildmodeExe BuildMode = iota
	BuildmodeCShared
)

func (mode *BuildMode) Set(s string) error {
	switch s {
	default:
		return errors.New("invalid mode")
	case "exe":
		*mode = BuildmodeExe
	case "c-shared":
		goarch := obj.Getgoarch()
		if goarch != "amd64" && goarch != "arm" {
			return fmt.Errorf("not supported on %s", goarch)
		}
		*mode = BuildmodeCShared
	}
	return nil
}

func (mode *BuildMode) String() string {
	switch *mode {
	case BuildmodeExe:
		return "exe"
	case BuildmodeCShared:
		return "c-shared"
	}
	return fmt.Sprintf("BuildMode(%d)", uint8(*mode))
}

## 変更の背景

この変更の主な背景には、Go言語のビルドシステムにおける「共有」という概念の曖昧さと、将来的な「Go実行モード (Go Execution Modes)」の導入計画があります。

Goリンカーは、特定のプラットフォームにおいて `-shared` フラグをサポートしていました。このフラグは、Goコードを共有ライブラリとしてビルドする際に使用され、C言語から呼び出し可能な形式（C-callable shared library）を生成する機能を持っていました。しかし、Goの進化に伴い、様々なビルドモード（例: プラグイン、WebAssemblyなど）が検討される中で、「shared」という用語が複数の異なる意味合いで使われるようになり、その意味が過負荷（overloaded）になっていました。

具体的には、Go 1.5で導入された `c-shared` ビルドモードは、GoパッケージをC言語から利用可能な共有ライブラリとしてコンパイルすることを目的としています。これは、Goの強力な並行処理やパフォーマンスを他の言語のアプリケーションに組み込むための重要な機能です。この新しいビルドモードの導入に際し、既存の `-shared` フラグが指す意味と、新しい `c-shared` の意味が重複し、混乱を招く可能性がありました。

このコミットは、このような混乱を解消し、リンカーのオプションをより体系的に整理するために行われました。`-shared` フラグを廃止し、より汎用的な `-buildmode` フラグを導入することで、将来的に追加される可能性のある様々なビルドモードを統一的なインターフェースで管理できるようにしています。Go 1.4でリンカーが `-shared` をサポートしていたため、後方互換性を保つために `-shared` は `-buildmode=c-shared` のエイリアスとして残されています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびリンカーに関する前提知識が必要です。

*   **Goリンカー (`cmd/internal/ld`)**: Goコンパイラツールチェーンの一部であり、Goのソースコードから実行可能ファイルやライブラリを生成する役割を担います。Goのランタイム、標準ライブラリ、ユーザーコードなどを結合し、最終的なバイナリを作成します。
*   **共有ライブラリ (Shared Library)**: 複数のプログラムから共有して利用できるライブラリのことです。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化などが可能になります。C言語の文脈では `.so` (Linux), `.dll` (Windows), `.dylib` (macOS) などの形式で提供されます。
*   **`c-shared` ビルドモード**: Go 1.5で導入されたビルドモードの一つで、GoのパッケージをC言語から呼び出し可能な共有ライブラリとしてコンパイルします。これにより、Goで書かれたロジックをC、Python、Javaなどの他の言語のアプリケーションから利用できるようになります。`go build -buildmode=c-shared` コマンドで利用されます。このモードでビルドされたライブラリは、Goランタイムを内包し、Cのヘッダーファイルも生成されます。
*   **`Flag_shared` (旧フラグ)**: このコミット以前にリンカーで使用されていた内部フラグで、共有ライブラリをビルドするかどうかを制御していました。このフラグは整数型で、0以外の場合に共有ライブラリビルドモードが有効になるという慣習的な使われ方をしていました。
*   **`Buildmode` (新フラグ)**: このコミットで導入された新しい型で、Goのビルドモードを明示的に表現するための列挙型です。`BuildmodeExe` (通常の実行可能ファイル) と `BuildmodeCShared` (C-callable共有ライブラリ) などの値を取ります。これにより、リンカーの挙動がより明確に定義されます。
*   **`INITENTRY`**: Goプログラムのエントリポイント（初期化関数）の名前を指すリンカー内部の定数です。通常の実行可能ファイルと共有ライブラリでは、このエントリポイントの名前が異なります。
*   **`R_TLS` (Thread Local Storage Relocation)**: スレッドローカルストレージ (TLS) に関連する再配置タイプです。TLSは、各スレッドが独自のデータを持つことを可能にするメカニズムで、共有ライブラリの文脈で重要になることがあります。
*   **`Linkmode`**: リンカーのリンクモードを制御するフラグです。`LinkInternal` はGoリンカーが完全に内部でリンク処理を行うことを意味し、`LinkExternal` は外部リンカー（例: GCC）を使用することを意味します。共有ライブラリのビルドでは、通常、外部リンカーが必要となります。

## 技術的詳細

このコミットの技術的な核心は、Goリンカー内部で共有ライブラリビルドモードを制御するメカニズムを、従来の `Flag_shared` という単純な整数フラグから、より構造化された `Buildmode` 型へと移行した点にあります。

1.  **`BuildMode` 型の導入**:
    `src/cmd/internal/ld/lib.go` に `BuildMode` という新しい型が定義されました。これは `uint8` を基盤とする列挙型で、以下の定数を持ちます。
    *   `BuildmodeExe`: 通常の実行可能ファイルをビルドするモード。
    *   `BuildmodeCShared`: C言語から呼び出し可能な共有ライブラリをビルドするモード。
    この型には、コマンドライン引数から値を設定するための `Set(s string) error` メソッドと、文字列表現を返す `String() string` メソッドが実装されています。`Set` メソッドでは、`c-shared` モードが `amd64` および `arm` アーキテクチャでのみサポートされるという制約もチェックされます。

2.  **`Flag_shared` から `Buildmode` への置き換え**:
    リンカーコードベース全体で、`Flag_shared != 0` という条件式が `Buildmode == BuildmodeCShared` に置き換えられました。これにより、リンカーの挙動がどのビルドモードに依存しているかが明確になります。影響を受けたファイルは `src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/6l/obj.go`, `src/cmd/internal/ld/data.go`, `src/cmd/internal/ld/elf.go`, `src/cmd/internal/ld/go.go`, `src/cmd/internal/ld/lib.go` です。

3.  **`-buildmode` コマンドラインフラグの追加**:
    `src/cmd/internal/ld/pobj.go` の `Ldmain` 関数内で、`flag.Var(&Buildmode, "buildmode", "build mode to use")` という行が追加され、リンカーが `-buildmode` コマンドライン引数を受け入れるようになりました。これにより、ユーザーは `go build -buildmode=c-shared` のように、明示的にビルドモードを指定できるようになります。

4.  **`-shared` フラグのエイリアス化と互換性**:
    Go 1.4で `-shared` フラグが導入されていたため、後方互換性を維持するために、`-shared` フラグは `-buildmode=c-shared` のエイリアスとして機能するように変更されました。
    `src/cmd/internal/ld/pobj.go` では、`flagShared` という一時的な変数が導入され、`-shared` フラグの値を捕捉します。`Ldmain` の初期化段階で、もし `flagShared` が設定されており、かつ `Buildmode` がまだ `BuildmodeExe` (デフォルト) のままであれば、`Buildmode` を `BuildmodeCShared` に設定します。もし `-shared` と `-buildmode` が矛盾する形で指定された場合は、エラー (`Diag`) を出力して終了します。

5.  **`INITENTRY` の決定ロジックの変更**:
    `src/cmd/internal/ld/lib.go` の `libinit` 関数内で、`INITENTRY` の決定ロジックが `Flag_shared` から `Buildmode` の `switch` 文に変更されました。これにより、ビルドモードに応じて適切なエントリポイント名が設定されます。
    *   `BuildmodeCShared` の場合: `_rt0_%s_%s_lib` (共有ライブラリ用)
    *   `BuildmodeExe` の場合: `_rt0_%s_%s` (実行可能ファイル用)

6.  **リンカーオプションの調整**:
    `src/cmd/internal/ld/lib.go` の `hostlink` 関数では、`Flag_shared != 0` の条件が `Buildmode == BuildmodeCShared` に変更され、共有ライブラリビルド時に `-Wl,-Bsymbolic` や `-shared` といった外部リンカーオプションが適切に渡されるようになっています。

これらの変更により、Goリンカーのビルドモード管理がより堅牢で拡張性の高いものとなり、将来的なGoのビルドシステム開発の基盤が強化されました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下の通りです。

## コアとなるコードの解説

### `src/cmd/internal/ld/lib.go` における `BuildMode` 型の定義と利用

```go
// A BuildMode indicates the sort of object we are building:
//   "exe": build a main package and everything it imports into an executable.
//   "c-shared": build a main package, plus all packages that it imports, into a
//     single C shared library. The only callable symbols will be those functions
// //     marked as exported.
type BuildMode uint8

const (
	BuildmodeExe BuildMode = iota
	BuildmodeCShared
)

func (mode *BuildMode) Set(s string) error {
	switch s {
	default:
		return errors.New("invalid mode")
	case "exe":
		*mode = BuildmodeExe
	case "c-shared":
		goarch := obj.Getgoarch()
		if goarch != "amd64" && goarch != "arm" {
			return fmt.Errorf("not supported on %s", goarch)
		}
		*mode = BuildmodeCShared
	}
	return nil
}

func (mode *BuildMode) String() string {
	switch *mode {
	case BuildmodeExe:
		return "exe"
	case BuildmodeCShared:
		return "c-shared"
	}
	return fmt.Sprintf("BuildMode(%d)", uint8(*mode))
}

// ... (中略) ...

var (
	// ... (中略) ...
	Buildmode          BuildMode // Flag_shared の代わりに導入
	// ... (中略) ...
)

// ... (中略) ...

func libinit() {
	// ... (中略) ...
	if INITENTRY == "" {
		switch Buildmode { // Flag_shared から Buildmode に変更
		case BuildmodeCShared:
			INITENTRY = fmt.Sprintf("_rt0_%s_%s_lib", goarch, goos)
		case BuildmodeExe:
			INITENTRY = fmt.Sprintf("_rt0_%s_%s", goarch, goos)
		default:
			Diag("unknown INITENTRY for buildmode %v", Buildmode)
		}
	}
	// ... (中略) ...
}

// ... (中略) ...

func loadlib() {
	if Buildmode == BuildmodeCShared { // Flag_shared から Buildmode に変更
		s := Linklookup(Ctxt, "runtime.islibrary", 0)
		s.Dupok = 1
		Adduint8(Ctxt, s, 1)
	}
	// ... (中略) ...
	if Buildmode == BuildmodeExe && havedynamic == 0 && HEADTYPE != Hdarwin && HEADTYPE != Hsolaris { // Flag_shared から Buildmode に変更
		Debug['d'] = 1
	}
	// ... (中略) ...
}

// ... (中略) ...

func hostlink() {
	// ... (中略) ...
	if Buildmode == BuildmodeCShared { // Flag_shared から Buildmode に変更
		argv = append(argv, "-Wl,-Bsymbolic")
		argv = append(argv, "-shared")
	}
	// ... (中略) ...
}
```
このコードは、Goリンカーがビルドモードをどのように認識し、それに基づいて異なる挙動をするかを定義しています。`BuildMode` 型は、リンカーが生成する出力の種類（実行可能ファイルか共有ライブラリか）を明確に区別するためのものです。`Set` メソッドはコマンドライン引数からモードを設定し、`String` メソッドはデバッグやエラーメッセージのためにモードの文字列表現を提供します。`libinit`, `loadlib`, `hostlink` 関数では、従来の `Flag_shared` のチェックが `Buildmode == BuildmodeCShared` に置き換えられ、ビルドモードに応じた初期化エントリポイントの選択、ランタイムライブラリの挙動調整、外部リンカーへのフラグ渡しが行われます。

### `src/cmd/internal/ld/pobj.go` におけるフラグ処理

```go
func Ldmain() {
	// ... (中略) ...
	obj.Flagcount("Z", "clear stack frame on entry", &Debug['Z'])
	obj.Flagcount("a", "disassemble output", &Debug['a'])
	flag.Var(&Buildmode, "buildmode", "build mode to use") // -buildmode フラグの登録
	obj.Flagcount("c", "dump call graph", &Debug['c'])
	// ... (中略) ...
	var flagShared int // -shared フラグの値を一時的に保持する変数
	if Thearch.Thechar == '5' || Thearch.Thechar == '6' {
		obj.Flagcount("shared", "generate shared object (implies -linkmode external)", &flagShared) // -shared フラグの登録
	}
	// ... (中略) ...
	startProfile()
	Ctxt.Bso = &Bso
	Ctxt.Debugvlog = int32(Debug['v'])
	if flagShared != 0 { // -shared が指定された場合の処理
		if Buildmode == BuildmodeExe { // -buildmode がデフォルト (exe) の場合
			Buildmode = BuildmodeCShared // Buildmode を c-shared に設定
		} else if Buildmode != BuildmodeCShared { // -buildmode が c-shared 以外で指定されている場合 (矛盾)
			Diag("-shared and -buildmode=%s are incompatible\n", Buildmode.String())
			Errorexit()
		}
	}
	// ... (中略) ...
}
```
`Ldmain` 関数はリンカーのメインエントリポイントです。ここで、新しい `-buildmode` フラグが `flag.Var` を使って登録されます。これにより、Goの標準的なフラグパーシングメカニズムを通じて `Buildmode` 変数に値が設定されるようになります。また、後方互換性のために、従来の `-shared` フラグも `flagShared` 変数に登録されます。`flagShared` が非ゼロ（つまり `-shared` が指定された）場合、現在の `Buildmode` の値がチェックされます。もし `Buildmode` がまだデフォルトの `BuildmodeExe` であれば、`BuildmodeCShared` に上書きされます。しかし、もし `Buildmode` が既に `BuildmodeCShared` 以外の値に設定されている場合は、`-shared` と `-buildmode` の指定が矛盾していると判断され、エラーが発生します。このロジックにより、`-shared` が `-buildmode=c-shared` のエイリアスとして機能しつつ、矛盾するフラグ指定を防ぐことができます。

### 各アーキテクチャ固有のリンカーファイルにおける変更

`src/cmd/5l/asm.go`, `src/cmd/6l/asm.go`, `src/cmd/6l/obj.go` など、各アーキテクチャ（例: ARM, x86-64）固有のリンカーファイルでは、TLS再配置やリンクモードの決定など、共有ライブラリビルドに関連する部分で `ld.Flag_shared` の参照が `ld.Buildmode == ld.BuildmodeCShared` に変更されています。これは、リンカーの低レベルな部分においても、新しい `Buildmode` 型が統一的に利用されるようになったことを示しています。

例 (`src/cmd/5l/asm.go`):
```go
func elfreloc1(r *ld.Reloc, sectoff int64) int {
	// ... (中略) ...
	case ld.R_TLS:
		if r.Siz == 4 {
			if ld.Buildmode == ld.BuildmodeCShared { // ld.Flag_shared から変更
				ld.Thearch.Lput(ld.R_ARM_TLS_IE32 | uint32(elfsym)<<8)
			} else {
				ld.Thearch.Lput(ld.R_ARM_TLS_LE32 | uint32(elfsym)<<8)
			}
		}
	// ... (中略) ...
}
```
この変更は、リンカーがTLS再配置を行う際に、ビルドモードが `c-shared` であるかどうかを正確に判断し、それに応じて適切な再配置タイプ（例: `R_ARM_TLS_IE32` vs `R_ARM_TLS_LE32`）を選択することを保証します。

# [インデックス 23354] ファイルの概要

このコミットは、Go言語の `html/template` パッケージにおけるパイプラインサニタイゼーションのバグ修正に関するものです。具体的には、テンプレートのパイプライン処理において、コマンドの最初のオペランドがメソッド呼び出しである場合にパニックが発生する問題を解決します。

## 元コミット内容

`html/template` パッケージにおいて、パイプラインのサニタイゼーション処理が修正されました。既存のサニタイザーが存在しない場合に、パイプラインにサニタイザーが挿入される際、コードは各コマンドの最初のオペランドが関数識別子であると仮定していました。しかし、これは誤りであり、メソッドである可能性もあります。この誤った仮定により、`{{1|print 2|.f 3}}` のようなテンプレートでパニックが発生していました。このコミットでは、識別子のみがサニタイザーと比較されるように、追加の型アサーションが導入されました。これにより、Issue #10673 が修正されました。

## 変更の背景

Go言語の `html/template` パッケージは、Webアプリケーションにおけるクロスサイトスクリプティング (XSS) 攻撃を防ぐために設計されています。このパッケージは、テンプレートの出力内容を自動的にエスケープ（サニタイズ）することで、悪意のあるスクリプトがブラウザで実行されるのを防ぎます。

サニタイゼーションは、テンプレートのパイプライン処理中に特定の関数（サニタイザー）を挿入することで行われます。例えば、`{{. | html}}` のように明示的に `html` 関数を呼び出すこともできますが、`html/template` は必要に応じて自動的にサニタイザーを挿入します。

この自動挿入ロジックにおいて、既存のサニタイザーが冗長であるかどうかを判断する部分にバグがありました。具体的には、パイプライン内のコマンドの最初のオペランドが常に「関数識別子」であると仮定していました。しかし、Goのテンプレートでは、`.f` のようにレシーバーを持つ「メソッド呼び出し」も最初のオペランドになり得ます。この仮定の誤りにより、メソッド呼び出しが来た場合に型アサーションが失敗し、ランタイムパニックを引き起こしていました。

この問題は、Issue #10673 として報告され、本コミットによって修正されました。

## 前提知識の解説

### Go言語の `html/template` パッケージ

`html/template` は、Go標準ライブラリの一部で、HTML出力を安全に生成するためのテンプレートエンジンです。主な目的は、ユーザー入力やデータベースからのデータがHTMLに埋め込まれる際に、XSS攻撃を防ぐことです。これは、出力されるコンテンツの種類（HTML、URL、JavaScriptなど）に応じて適切なエスケープ処理を自動的に適用することで実現されます。

### テンプレートのパイプライン

Goのテンプレートでは、Unixのパイプラインのように、複数のコマンドを `|` 演算子で連結できます。例えば、`{{.Name | html | urlquery}}` は、`.Name` の値を `html` 関数に渡し、その結果を `urlquery` 関数に渡します。

### `parse.CommandNode` と `parse.IdentifierNode`

`html/template` パッケージは、テンプレート文字列を解析して抽象構文木 (AST) を構築します。
- `parse.CommandNode`: テンプレート内のコマンド（例: `print 2` や `.f 3`）を表すノードです。コマンドは複数のオペランドを持つことができます。
- `parse.IdentifierNode`: 識別子（変数名、関数名など）を表すノードです。例えば、`print` は関数識別子です。
- `parse.FieldNode`: `.f` のように、レシーバー（`.`）に続くフィールドやメソッドを表すノードです。

問題の核心は、`appendCmd` 関数が `cmds[n-1].Args[0]` と `cmd.Args[0]` を `*parse.IdentifierNode` に型アサートしようとしていた点です。メソッド呼び出しの場合、これは `*parse.FieldNode` になるため、型アサーションが失敗し、パニックを引き起こしていました。

### サニタイザーの冗長性チェック

`html/template` は、不必要なサニタイザーの挿入を避けるために、既に適切なサニタイザーが存在するかどうかをチェックします。例えば、`{{. | html | html}}` のように `html` 関数が二重に適用される場合、2番目の `html` は冗長と判断され、挿入がスキップされることがあります。この冗長性チェックのロジックが、今回のバグの原因となっていました。

## 技術的詳細

`html/template` パッケージの `escape.go` ファイルには、テンプレートのサニタイゼーションロジックが含まれています。特に `appendCmd` 関数は、パイプラインに新しいコマンドを追加する際に、既存のコマンドとの間でサニタイザーが冗長でないかをチェックする役割を担っています。

問題のコードは以下の部分でした（修正前）：

```go
func appendCmd(cmds []*parse.CommandNode, cmd *parse.CommandNode) []*parse.CommandNode {
	if n := len(cmds); n != 0 {
		last, ok := cmds[n-1].Args[0].(*parse.IdentifierNode)
		next, _ := cmd.Args[0].(*parse.IdentifierNode)
		if ok && redundantFuncs[last.Ident][next.Ident] {
			return cmds
		}
	}
	// ...
}
```

ここで、`cmds[n-1].Args[0]` と `cmd.Args[0]` は、それぞれパイプラインの最後のコマンドと新しいコマンドの最初のオペランドを指します。このコードは、これらのオペランドが `*parse.IdentifierNode` であると仮定し、`last` と `next` に型アサートしています。

しかし、テンプレートのパイプラインでは、例えば `{{.X | print 2 | .f 3}}` のように、`.f` のようなメソッド呼び出しがコマンドの最初のオペランドになることがあります。`parse.FieldNode` は `parse.IdentifierNode` ではないため、`cmds[n-1].Args[0].(*parse.IdentifierNode)` や `cmd.Args[0].(*parse.IdentifierNode)` の型アサーションが失敗し、`ok` が `false` になるか、あるいは `next` のアサーションが失敗して `next` が `nil` になります。

特に、`next, _ := cmd.Args[0].(*parse.IdentifierNode)` の行では、2番目の戻り値（成功を示すブール値）が破棄されています。もし `cmd.Args[0]` が `*parse.IdentifierNode` でない場合、`next` は `nil` になります。その後の `redundantFuncs[last.Ident][next.Ident]` の評価で `next.Ident` にアクセスしようとすると、`nil` ポインタデリファレンスが発生し、ランタイムパニックを引き起こします。

このコミットは、この問題を解決するために、`next` の型アサーションの成功も `okNext` という変数で明示的にチェックするように変更しました。

## コアとなるコードの解説

変更の核心は、`next` 変数への型アサーションの結果を明示的にチェックする `okNext` 変数を導入した点です。

修正前:
```go
last, ok := cmds[n-1].Args[0].(*parse.IdentifierNode)
next, _ := cmd.Args[0].(*parse.IdentifierNode) // ここで2番目の戻り値が破棄されている
if ok && redundantFuncs[last.Ident][next.Ident] {
    // ...
}
```
このコードでは、`next` への型アサーションが失敗した場合（つまり `cmd.Args[0]` が `*parse.IdentifierNode` でない場合）、`next` は `nil` になります。その後の `redundantFuncs[last.Ident][next.Ident]` の評価で `next.Ident` にアクセスしようとすると、`nil` ポインタデリファレンスが発生し、パニックを引き起こします。

修正後:
```go
last, okLast := cmds[n-1].Args[0].(*parse.IdentifierNode)
next, okNext := cmd.Args[0].(*parse.IdentifierNode) // 2番目の戻り値 (okNext) を取得
if okLast && okNext && redundantFuncs[last.Ident][next.Ident] {
    // ...
}
```
この修正により、`redundantFuncs` マップにアクセスする前に、`last` と `next` の両方が `*parse.IdentifierNode` であることが `okLast && okNext` という条件で保証されます。もしどちらか一方が `*parse.IdentifierNode` でない場合、`okLast && okNext` は `false` となり、`redundantFuncs` へのアクセスは行われません。これにより、`nil` ポインタデリファレンスによるパニックが回避され、メソッド呼び出しが最初のオペランドであるパイプラインでも安全に処理されるようになりました。

また、`escape_test.go` には、この修正を検証するための新しいテストケースが追加されています。
```go
		{
			"{{.X | print 2 | .f 3}}",
			".X | print 2 | .f 3 | urlquery | html",
			[]string{"urlquery", "html"},
		},
		{
			"{{.X | html | print 2 | .f 3}}",
			".X | urlquery | html | print 2 | .f 3",
			[]string{"urlquery", "html"},
		},
```
これらのテストケースは、メソッド呼び出し (`.f 3`) を含むパイプラインが正しくサニタイズされることを確認しています。

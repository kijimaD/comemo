このコミットは、Goの標準ライブラリ `net/http` パッケージのテストコードにおける重要な改善を導入しています。具体的には、これまで非公式な「ハック」として利用されてきた `z_last_test.go` というファイル名によるテスト実行順序の制御を廃止し、Goの `testing` パッケージが提供する公式な `TestMain` 関数に置き換えるものです。これにより、テストスイート全体の実行前後に、より堅牢かつイディオム的な方法でセットアップやティアダウン、特にゴルーチンリークのチェックを行うことが可能になりました。

## 変更の背景

Goのテストフレームワークでは、通常、テストファイルはファイル名の辞書順に実行されます。この特性を利用して、特定のテスト（この場合はゴルーチンリークのチェック）を他のすべてのテストの後に実行させるために、`z_last_test.go` のようにファイル名の先頭に `z_` を付けるという非公式な「ハック」が用いられていました。これは、すべてのテストが完了した後にシステムの状態（特に残存するゴルーチン）を検証するために必要でした。

しかし、このようなファイル名に依存したテスト順序の制御は、Goのテストの設計思想（テストは独立しているべき）に反し、非イディオム的であり、将来的な変更に対して脆弱でした。Go 1.4で `testing.Main` 関数が導入されたことで、パッケージレベルでのテストのセットアップとティアダウンを公式かつ堅牢な方法で制御する手段が提供されました。このコミットは、この新しいイディオム的なアプローチを採用し、既存の「ハック」をより適切な方法に置き換えることを目的としています。これにより、テストコードの可読性、保守性、そして信頼性が向上します。

## 前提知識の解説

### Goのテストの仕組み

Go言語には、標準ライブラリとして強力なテストフレームワークが組み込まれています。
*   **テストファイルの命名規則**: テストコードは、テスト対象のGoファイルと同じディレクトリに配置され、ファイル名が `_test.go` で終わる必要があります（例: `my_package_test.go`）。
*   **テスト関数の命名規則**: テストファイル内で、`func TestXxx(*testing.T)` の形式で定義された関数がテスト関数として認識されます。`Xxx` は大文字で始まる任意の名前です。
*   **テストの実行**: `go test` コマンドを実行すると、カレントディレクトリまたは指定されたパッケージ内のすべてのテストファイルがコンパイルされ、テスト関数が実行されます。デフォルトでは、テストは並行して実行される可能性があります。
*   **テストの順序**: `go test` は、テストファイルをファイル名の辞書順に処理しますが、個々のテスト関数が実行される順序は保証されません（並行実行されるため）。

### `testing.Main` 関数 (`func TestMain(m *testing.M)`)

Go 1.4で導入された `TestMain` 関数は、パッケージ内のすべてのテストの実行を制御するための特別なエントリポイントです。
*   **役割**: `_test.go` ファイル内に `func TestMain(m *testing.M)` が定義されている場合、`go test` コマンドは通常のテスト関数を直接実行する代わりに、まずこの `TestMain` 関数を呼び出します。
*   **セットアップとティアダウン**: `TestMain` 関数内で、`m.Run()` を呼び出すことで実際のテストが実行されます。`m.Run()` の呼び出し前にはパッケージ全体のセットアップ処理を、呼び出し後にはティアダウン処理を記述できます。これにより、データベース接続の確立やクリーンアップ、一時ファイルの作成と削除など、テスト全体で共有されるリソースの管理を効率的に行えます。
*   **終了コード**: `m.Run()` はテストの実行結果を示す終了コード（すべてのテストが成功すれば0、失敗があれば非0）を返します。`TestMain` 関数は、この戻り値を `os.Exit()` に渡してプログラムを終了させる必要があります。これにより、`go test` コマンドがテストの成功/失敗を正しく判断できます。
*   **用途**: 主に、テスト環境の準備、リソースの初期化と解放、そして今回のコミットのように、テスト実行後に特定の状態（例: ゴルーチンリーク）をチェックするために使用されます。

### ゴルーチンリーク

*   **定義**: ゴルーチンリークとは、プログラムの実行が終了した後も、本来終了すべきゴルーチンが終了せずにメモリ上に残り続けてしまう現象を指します。これは、ゴルーチンがブロックされたままになったり、チャネルからの受信を待ち続けたり、無限ループに陥ったりすることで発生します。
*   **問題点**: ゴルーチンリークは、メモリやその他のリソースを消費し続け、アプリケーションのパフォーマンス低下、リソース枯渇、最終的にはクラッシュにつながる可能性があります。
*   **テストにおける重要性**: 特に長期稼働するサーバーアプリケーションなどでは、ゴルーチンリークは深刻な問題となるため、テスト段階でこれを検出することが非常に重要です。テストスイートの実行後に残存するゴルーチンをチェックすることで、予期せぬリークを早期に発見できます。

### `z_last_test.go` ハック

これは、Goのテストフレームワークのファイル名による辞書順ソートの特性を悪用した非公式な手法です。
*   **目的**: 特定のテストファイル（この場合は `z_last_test.go`）を、他のすべてのテストファイルの後に実行させることを目的としていました。
*   **仕組み**: ファイル名の先頭に `z_` を付けることで、そのファイルが辞書順で最後に位置するようにし、結果として `go test` がそのファイルを最後に処理するように仕向けます。
*   **問題点**:
    *   **非イディオム的**: Goのテストの設計思想に反し、テストの独立性を損ないます。
    *   **脆弱性**: ファイル名に依存するため、リファクタリングやファイル名の変更によって容易に壊れる可能性があります。
    *   **可読性の低下**: コードの意図がファイル名に隠蔽され、理解しにくくなります。

## 技術的詳細

このコミットの技術的詳細は、主に `z_last_test.go` ファイルを `main_test.go` にリネームし、その内容を `TestMain` 関数と `goroutineLeaked` 関数に再構築した点にあります。

1.  **ファイルのリネーム**:
    *   `src/net/http/z_last_test.go` が `src/net/http/main_test.go` にリネームされました。
    *   このリネームは、ファイル名によるテスト順序制御の「ハック」を廃止し、`TestMain` 関数がGoのテストランナーによって自動的に検出されるようにするためのものです。`TestMain` 関数は、どの `_test.go` ファイルに存在しても、パッケージ内で一つだけ定義されていればテスト実行のエントリポイントとなります。

2.  **`TestMain` 関数の導入**:
    *   新しい `main_test.go` ファイルに `func TestMain(m *testing.M)` が追加されました。
    *   この関数は、`m.Run()` を呼び出すことで `net/http` パッケージ内のすべてのテストを実行します。
    *   `m.Run()` が返した結果コード `v` を受け取り、テストがすべて成功した場合（`v == 0`）にのみ `goroutineLeaked()` 関数を呼び出してゴルーチンリークをチェックします。
    *   もしリークが検出された場合、`os.Exit(1)` を呼び出してテスト全体を失敗として終了させます。
    *   リークがなければ、またはテスト自体が失敗した場合は、`os.Exit(v)` を呼び出して `m.Run()` の結果をそのまま反映させます。

3.  **`TestGoroutinesRunning` から `goroutineLeaked` へのリファクタリング**:
    *   以前 `z_last_test.go` にあった `func TestGoroutinesRunning(t *testing.T)` は、`func goroutineLeaked() bool` という非エクスポート関数にリファクタリングされました。
    *   この関数は、`interestingGoroutines()` を呼び出して現在実行中の「興味深い」ゴルーチン（テストに関連する可能性のあるゴルーチン）のリストを取得します。
    *   `testing.Short()` モード（`go test -short`）では、ゴルーチンリークチェックをスキップします。これは、`short` モードが高速なテスト実行を目的としているため、時間のかかるリークチェックは省略されるべきという判断に基づいています。
    *   取得したゴルーチンの数が0でなければ、標準エラー出力にリークしているゴルーチンのスタックトレースとインスタンス数を出力し、`true` を返してリークがあったことを示します。

4.  **`interestingGoroutines()` の改善**:
    *   `interestingGoroutines()` 関数は、`runtime.Stack` を使用してすべてのゴルーチンのスタックトレースを取得し、テストとは無関係なバックグラウンドゴルーチン（例: `runtime.goexit`, `runtime.gc`, `runtime.MHeap_Scavenger` など）を除外するフィルタリングロジックを含んでいます。
    *   このコミットでは、フィルタリング条件に `strings.Contains(stack, "net/http_test.interestingGoroutines")` が追加されました。これは、`interestingGoroutines` 関数自体が実行中に生成するゴルーチン（もしあれば）を、リークとして誤検出しないようにするための重要な改善です。これにより、自己参照による誤検出を防ぎ、より正確なリークチェックが可能になります。

これらの変更により、ゴルーチンリークのチェックがテストスイートのライフサイクルに適切に統合され、より信頼性の高いテスト結果が得られるようになりました。

## コアとなるコードの解説

このコミットの核心は、`TestMain` 関数の導入と、それに伴うゴルーチンリークチェックのロジックの変更です。

### `TestMain` 関数の解説

```go
func TestMain(m *testing.M) {
	v := m.Run()
	if v == 0 && goroutineLeaked() {
		os.Exit(1)
	}
	os.Exit(v)
}
```

*   `func TestMain(m *testing.M)`: この関数は、`net/http` パッケージ内のすべてのテストが実行される前に、Goのテストランナーによって自動的に呼び出されるエントリポイントです。`*testing.M` 型の引数 `m` は、テストの実行を制御するためのメソッドを提供します。
*   `v := m.Run()`: ここで、パッケージ内のすべてのテスト（`TestXxx` 関数やベンチマークなど）が実行されます。`m.Run()` は、すべてのテストが成功した場合は `0` を、一つでも失敗した場合は非ゼロの値を返します。この戻り値は変数 `v` に格納されます。
*   `if v == 0 && goroutineLeaked()`:
    *   `v == 0`: これは、`m.Run()` によって実行されたすべてのテストが成功したかどうかをチェックします。ゴルーチンリークのチェックは、テスト自体が成功した場合にのみ意味があります。テストが失敗している場合、その失敗がより根本的な問題を示している可能性があり、ゴルーチンリークのチェックは二次的なものとなります。
    *   `goroutineLeaked()`: この関数は、後述するように、テスト実行後に不要なゴルーチンが残っていないか（リークしていないか）をチェックします。リークが検出された場合、`true` を返します。
    *   この `if` 文は、「すべてのテストが成功し、かつゴルーチンリークが検出された場合」という条件を意味します。
*   `os.Exit(1)`: 上記の条件が真（テスト成功かつリークあり）の場合、`os.Exit(1)` が呼び出されます。これは、プログラムを終了コード `1` で終了させることを意味し、`go test` コマンドに対して「テストが失敗した」と伝えます。これにより、ゴルーチンリークもテスト失敗として扱われるようになります。
*   `os.Exit(v)`: `if` 文の条件が偽の場合（テストが失敗したか、リークがなかった場合）、`os.Exit(v)` が呼び出されます。これは、`m.Run()` が返した元の終了コード `v` をそのまま使用してプログラムを終了させます。これにより、テストの成功または失敗が適切に報告されます。

### `goroutineLeaked` 関数の解説

```go
func goroutineLeaked() bool {
	if testing.Short() {
		// not counting goroutines for leakage in -short mode
		return false
	}
	gs := interestingGoroutines()

	n := 0
	stackCount := make(map[string]int)
	for _, g := range gs {
		stackCount[g]++
		n++
	}

	if n == 0 {
		return false
	}
	fmt.Fprintf(os.Stderr, "Too many goroutines running after net/http test(s).\n")
	for stack, count := range stackCount {
		fmt.Fprintf(os.Stderr, "%d instances of:\n%s", count, stack)
	}
	return true
}
```

*   `if testing.Short()`: `go test -short` コマンドでテストが実行された場合、この条件が真となります。`short` モードは、テストを高速に実行するためのものであり、ゴルーチンリークチェックのような時間のかかる処理はスキップされるべきです。この場合、関数は `false` を返し、リークがないものとして扱われます。
*   `gs := interestingGoroutines()`: `interestingGoroutines()` 関数を呼び出し、テストに関連する可能性のあるゴルーチンのスタックトレースのリストを取得します。この関数は、Goランタイムの内部ゴルーチンなど、テストとは無関係なゴルーチンを除外するロジックを含んでいます。
*   `n := 0; stackCount := make(map[string]int)`: `n` はリークしているゴルーチンの総数をカウントし、`stackCount` は各スタックトレースの出現回数をカウントするためのマップです。
*   `for _, g := range gs`: 取得した各ゴルーチンのスタックトレースについてループ処理を行います。
    *   `stackCount[g]++`: 同じスタックトレースを持つゴルーチンの数をインクリメントします。
    *   `n++`: リークしているゴルーチンの総数をインクリメントします。
*   `if n == 0`: リークしているゴルーチンが一つもなければ、`false` を返してリークがないことを示します。
*   `fmt.Fprintf(os.Stderr, ...)`: リークが検出された場合、標準エラー出力に警告メッセージと、リークしている各ゴルーチンのスタックトレースおよびそのインスタンス数を出力します。これにより、開発者はどのゴルーチンがリークしているかを特定しやすくなります。
*   `return true`: リークが検出されたことを示します。

この変更により、`net/http` パッケージのテストは、より現代的で堅牢な方法でゴルーチンリークを検出し、テストスイート全体の品質を向上させることができました。

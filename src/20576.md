## 変更の背景

このコミットの主な目的は、GoプログラムがWindows上で`OutputDebugString`関数を使用してデバッグメッセージを出力する際に、デバッガがそのメッセージを適切に捕捉できるようにすることです。

以前のGoランタイムのVEH (Vectored Exception Handler) 実装では、`OutputDebugString`が内部的に発生させる`DBG_PRINTEXCEPTION_C`例外（例外コード`0x40010006`）を「処理済み」としてマークしていました。これにより、デバッガがこの例外を捕捉できなくなり、結果として`OutputDebugString`によって送信されたデバッグメッセージがデバッガの出力ウィンドウに表示されないという問題が発生していました。

コミットメッセージによると、この「処理済み」とマークする挙動は、クラッシュを防ぐためのものとコメントされていましたが、コミッタはテストを追加してもクラッシュが発生しないことを確認しました。そのため、この不要な処理を削除し、デバッガが`OutputDebugString`のメッセージを正しく受信できるようにすることが決定されました。

また、この変更は、GoランタイムのVEHハンドラを簡素化し、当時存在した「issue 8006」の修正に向けた準備の一環でもありました。issue 8006の具体的な内容は不明ですが、VEHハンドラに関連する問題であったと推測されます。

## 前提知識の解説

### 1. Windowsのデバッグと`OutputDebugString`

Windowsアプリケーションは、デバッグ情報をデバッガに送信するために`OutputDebugString`というAPI関数を使用できます。この関数は、文字列をデバッガの出力ウィンドウに表示するために設計されています。

`OutputDebugString`が呼び出されると、内部的には`DBG_PRINTEXCEPTION_C`（またはそのワイド文字版`DBG_PRINTEXCEPTION_WIDE_C`）という特定の例外が生成されます。この例外は、通常、アタッチされたデバッガによって捕捉され、デバッガはその例外から文字列を抽出し、ユーザーに表示します。デバッガがアタッチされていない場合、この例外は通常無視されるか、アプリケーションのデフォルトの例外ハンドラに渡されます。

### 2. Windowsの例外処理 (SEHとVEH)

Windowsオペレーティングシステムには、プログラム実行中に発生するエラーや予期せぬイベント（例外）を処理するためのメカニズムがいくつかあります。

*   **Structured Exception Handling (SEH)**: これはWindowsのネイティブな例外処理メカニズムで、C/C++言語の`__try`/`__except`/`__finally`ブロックに似ています。SEHハンドラは、特定のコードブロックや関数スコープ内で例外を捕捉します。例外が発生すると、システムはコールスタックを遡り、適切なSEHハンドラを探します。

*   **Vectored Exception Handling (VEH)**: VEHはWindows XPで導入された、SEHを補完するより強力な例外処理メカニズムです。SEHがコールスタックのフレームに紐付けられるのに対し、VEHハンドラはプロセス全体にわたって登録されます。例外が発生すると、デバッガが最初の通知を受け取った後、SEHハンドラが呼び出される前に、登録されたVEHハンドラが呼び出されます。これにより、アプリケーションは例外がどこで発生したかに関わらず、グローバルに例外を監視・処理することができます。VEHハンドラは、例外を処理したことをシステムに通知することも、他のハンドラに処理を委ねることも可能です。

### 3. `DBG_PRINTEXCEPTION_C` (例外コード `0x40010006`)

これは、`OutputDebugString`関数がデバッガにメッセージを送信するために内部的に使用する特定の例外コードです。この例外は、デバッガがアタッチされている場合にのみ意味を持ち、デバッガがこの例外を捕捉して処理することで、デバッグ文字列がユーザーに表示されます。

## 技術的詳細

このコミットは、GoランタイムがWindows上で例外を処理する方法、特にVEHハンドラが`DBG_PRINTEXCEPTION_C`例外をどのように扱うかという点に焦点を当てています。

Goランタイムは、WindowsのVEHメカニズムを利用して、Goプログラム内で発生する様々な例外（例えば、不正なメモリアクセスなど）を捕捉し、Goのランタイムパニックやクラッシュレポートに変換します。このVEHハンドラは、`runtime·sighandler`という関数で実装されています。

以前の実装では、`runtime·sighandler`内で、例外コードが`DBG_PRINTEXCEPTION_C`である場合に、その例外を即座に「処理済み」（戻り値`-1`）としてマークしていました。コミットメッセージのコメントによると、これは「プログラムのクラッシュを防ぐため」とされていましたが、コミッタの検証により、この処理がなくてもクラッシュしないことが判明しました。

この「処理済み」とマークする挙動は、デバッガが`DBG_PRINTEXCEPTION_C`例外を捕捉する機会を奪っていました。デバッガは、この例外を捕捉することで`OutputDebugString`からのメッセージを読み取るため、Goランタイムがこの例外を横取りして処理済みとしてしまうと、デバッガはメッセージを表示できなくなります。

このコミットは、この不要な処理を削除することで、Goプログラムが`OutputDebugString`を使用した場合に、デバッガがそのメッセージを正しく受信し、表示できるようにします。これにより、Goプログラムのデバッグ体験が向上します。

また、この変更は、VEHハンドラのコードを簡素化し、将来的に「issue 8006」を修正するための準備でもあります。VEHハンドラから特定の例外処理ロジックを削除することで、コードの可読性と保守性が向上し、今後の変更が容易になります。

## コアとなるコードの変更箇所

変更は主に以下の2つのファイルで行われています。これらはGoランタイムのWindows固有の例外ハンドラの実装です。

1.  `src/runtime/os_windows_386.c` (32ビット版Windowsランタイム)
2.  `src/runtime/os_windows_amd64.c` (64ビット版Windowsランタイム)
3.  `src/runtime/syscall_windows_test.go` (テストファイルの追加)

具体的な変更内容は、`DBG_PRINTEXCEPTION_C`の定義と、その例外を処理する条件分岐の削除です。

**削除されたコード:**

```c
#define DBG_PRINTEXCEPTION_C 0x40010006

// ... (runtime·sighandler 関数内)
if(info->ExceptionCode == DBG_PRINTEXCEPTION_C) {
    // This exception is intended to be caught by debuggers.
    // There is a not-very-informational message like
    // "Invalid parameter passed to C runtime function"
    // sitting at info->ExceptionInformation[0] (a wchar_t*),
    // with length info->ExceptionInformation[1].
    // The default behavior is to ignore this exception,
    // but somehow returning 0 here (meaning keep going)
    // makes the program crash instead. Maybe Windows has no
    // other handler registered? In any event, ignore it.
    return -1;
}
```

**追加されたコード:**

`src/runtime/syscall_windows_test.go` に`TestOutputDebugString`という新しいテスト関数が追加されました。

```go
func TestOutputDebugString(t *testing.T) {
	d := GetDLL(t, "kernel32.dll")
	p := syscall.StringToUTF16Ptr("testing OutputDebugString")
	d.Proc("OutputDebugStringW").Call(uintptr(unsafe.Pointer(p)))
}
```

## コアとなるコードの解説

### 削除されたコードの解説

`src/runtime/os_windows_386.c` および `src/runtime/os_windows_amd64.c` から削除されたコードは、GoランタイムのVEHハンドラである`runtime·sighandler`関数の一部でした。

*   `#define DBG_PRINTEXCEPTION_C 0x40010006`: これは`OutputDebugString`が生成する特定の例外コードを定義していました。
*   `if(info->ExceptionCode == DBG_PRINTEXCEPTION_C) { ... return -1; }`: この条件分岐が、問題の核心でした。`info->ExceptionCode`が`DBG_PRINTEXCEPTION_C`と一致した場合、ハンドラは即座に`-1`を返していました。WindowsのVEHハンドラにおいて、戻り値`-1`は「例外が処理されたため、これ以上他のハンドラに渡す必要はない」ことを意味します。これにより、デバッガがこの例外を捕捉する機会が失われ、`OutputDebugString`からのメッセージが表示されなくなっていました。
    コメントには「プログラムのクラッシュを防ぐため」とありましたが、コミッタのテストにより、この処理がなくてもクラッシュしないことが確認されたため、このブロックは完全に削除されました。

### 追加されたテストコードの解説

`src/runtime/syscall_windows_test.go` に追加された`TestOutputDebugString`関数は、この変更が意図通りに機能することを確認するためのものです。

*   `d := GetDLL(t, "kernel32.dll")`: `kernel32.dll`はWindowsのコアシステムライブラリであり、`OutputDebugStringW`関数が含まれています。この行は、そのDLLへのハンドルを取得します。
*   `p := syscall.StringToUTF16Ptr("testing OutputDebugString")`: `OutputDebugStringW`はワイド文字（UTF-16）の文字列ポインタを引数として受け取ります。この行は、テスト用の文字列をUTF-16に変換し、そのポインタを取得します。
*   `d.Proc("OutputDebugStringW").Call(uintptr(unsafe.Pointer(p)))`: この行が実際に`OutputDebugStringW`関数を呼び出します。`Call`メソッドは、指定された引数でDLL内のプロシージャ（関数）を実行します。

このテストは、`OutputDebugStringW`が呼び出されたときに、デバッガがアタッチされていればそのメッセージが捕捉されることを期待しています。VEHハンドラから`DBG_PRINTEXCEPTION_C`の処理が削除されたことで、このテストは成功するようになりました。

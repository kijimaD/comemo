# [インデックス 23365] ファイルの概要

## コミット

このコミットは、GoランタイムにおけるCPUプロファイリングの精度と有用性を向上させることを目的としています。具体的には、`g0`（システムゴルーチン）上で実行されるコードのプロファイリングを可能にし、`systemstack`への切り替えを伴うスタックトレースバックの課題を解決します。これにより、ランタイム内部の処理がCPU時間をどのように消費しているかをより正確に把握できるようになります。

## 変更の背景

GoのCPUプロファイリングは、アプリケーションのパフォーマンスボトルネックを特定する上で非常に強力なツールです。しかし、このコミット以前は、Goランタイムの内部処理、特に`g0`（システムゴルーチン）上で実行されるコードのプロファイリングには限界がありました。

`g0`は、Goランタイムがスケジューリング、ガベージコレクション、システムコール処理などの低レベルなタスクを実行するために使用する特別なゴルーチンです。ユーザーゴルーチンがシステムコールを行う際などには、実行コンテキストがユーザーゴルーチンから`g0`へと切り替わります。この切り替えは`systemstack`と呼ばれる専用のスタック上で行われます。

従来のプロファイリングメカニズムでは、`systemstack`上でのスタックトレースバックが困難でした。特に、`gogo`のようなゴルーチンコンテキストスイッチを行う関数や、`systemstack`への切り替え中にプロファイリング信号（`SIGPROF`など）が到着した場合、スタックの状態が不安定になり、正確な呼び出し履歴を遡ることができませんでした。このため、ランタイムがCPU時間を消費している部分がプロファイルに現れず、プロファイリングデータが不完全になるという問題がありました（Issue #10609）。

このコミットは、`systemstack`上で実行されるコードのスタック情報が利用可能になったことを受けて、`gentraceback`関数を改良し、`systemstack`への切り替えを適切に処理することで、`g0`上でのプロファイリングを可能にし、CPUプロファイルの有用性を高めることを目的としています。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念とプロファイリングの基礎知識が不可欠です。

*   **Goランタイム (Go Runtime):** Goプログラムの実行を管理する中核部分です。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル通信、システムコールインターフェースなど、Goプログラムの低レベルな動作のほとんどを担っています。
*   **Goroutine (ゴルーチン):** Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。ユーザーが記述するGoコードは、通常これらのゴルーチン上で実行されます。
*   **g0 (システムゴルーチン):** 各OSスレッド（GoランタイムではM: Machineと呼ばれる）に一つずつ関連付けられている特別なゴルーチンです。ユーザーゴルーチンとは異なり、ランタイムの内部処理（スケジューラの実行、ガベージコレクションの補助、システムコールへの移行など）のために予約されています。ユーザーコードが直接`g0`上で実行されることはありませんが、ユーザーゴルーチンがシステムコールを発行する際などには、`g0`にコンテキストが切り替わります。
*   **systemstack:** `g0`が使用する専用のスタックです。ユーザーゴルーチンが使用するスタックとは独立しており、ランタイムの重要な処理が実行される際に利用されます。これにより、ユーザーゴルーチンのスタックオーバーフローなどからランタイムの安定性を保護します。
*   **CPUプロファイリング (CPU Profiling):** プログラムがCPU時間をどこで消費しているかを分析する手法です。Goでは`pprof`ツールが広く利用されます。CPUプロファイリングは通常、一定の時間間隔（例: 100Hz）で実行中のプログラムのスタックトレースをサンプリングし、どの関数が呼び出し履歴に多く出現するかを統計的に集計することで、CPU使用率の高いコードパスを特定します。
*   **スタックトレース (Stack Trace) / スタックアンワインド (Stack Unwinding):** プログラムの実行中に、現在実行中の関数からその関数を呼び出した関数、さらにその呼び出し元へと、関数の呼び出し履歴を遡って取得するプロセスです。CPUプロファイリングでは、サンプリング時にこのスタックトレースを取得し、どの関数がCPUを占有しているかを判断します。
*   **`gentraceback`関数:** Goランタイムの内部関数で、与えられたプログラムカウンタ（PC）とスタックポインタ（SP）からスタックトレースを生成する役割を担います。
*   **`gogo`関数:** Goランタイムの内部で、ゴルーチン間のコンテキストスイッチを行うために使用されるアセンブリ言語で書かれた関数です。スタックポインタやプログラムカウンタを直接操作します。
*   **`funcPC`関数:** Goランタイムの内部関数で、特定の関数のエントリポイントのプログラムカウンタ（PC）を取得します。

## 技術的詳細

このコミットの核心は、GoランタイムのCPUプロファイリングが`g0`（システムゴルーチン）上で実行されるコードを正確に捕捉できるようにすることです。

**以前の課題とアプローチ:**
以前のGoランタイムでは、CPUプロファイリングのサンプリング時に`g0`上で実行されているコードのスタックトレースを正確に取得することが困難でした。特に、`gogo`関数のようなゴルーチンコンテキストスイッチを行う関数内でプロファイリング信号が到着した場合、スタックの状態が一時的に不安定になるため、`gentraceback`が正しいスタックトレースを生成できませんでした。
この問題を回避するため、`src/runtime/proc1.go`の`sigprof`関数内には、`gogo`関数のサイズを`_RuntimeGogoBytes`というアーキテクチャ依存の定数で定義し、現在のプログラムカウンタ（PC）がその範囲内にある場合はトレースバックをスキップするという、ややハック的なロジックが存在していました。このアプローチは、`gogo`関数のサイズが変更されるたびに定数を更新する必要があり、保守が難しいという問題がありました。また、`systemstack`自体でのプロファイリングは十分に考慮されていませんでした。

**このコミットによる改善点:**

1.  **`systemstack`上でのスタック情報利用の実現:**
    このコミットの前提として、「`systemstack`上で実行されているコードのスタック情報が利用可能になった」という重要な変更があります。これにより、`g0`上での実行であっても、スタックの状態をより正確に把握できるようになりました。

2.  **`gentraceback`の`systemstack`スイッチ対応:**
    最も重要な変更は、`gentraceback`関数が`systemstack`への切り替えを適切に「飛び越える」ロジックが追加されたことです。これにより、`g0`上でプロファイリング信号が捕捉された場合でも、その`g0`を呼び出した元のユーザーゴルーチン（`curg`）のスタックにまで遡ってトレースバックを継続できるようになります。これは、ランタイム内部の処理がどのユーザーゴルーチンのためにCPU時間を消費しているかを正確に特定するために不可欠です。

3.  **`_RuntimeGogoBytes`の廃止と`setsSP`関数の導入:**
    `gogo`関数のサイズをハードコードする`_RuntimeGogoBytes`定数（およびそれに関連するテスト`TestRuntimeGogoBytes`）は削除されました。代わりに、`setsSP`という新しいヘルパー関数が導入されました。
    `setsSP`関数は、与えられたPCが`gogo`, `systemstack`, `mcall`, `morestack`といった、スタックポインタ（SP）を絶対値で設定する可能性のある関数を指すかどうかを判定します。これらの関数はスタックの構造を大きく変更するため、プロファイリング信号がこれらの関数内で到着した場合、スタックトレースバックの開始点としては不適切である可能性が高いです。`sigprof`関数は、`setsSP`が`true`を返す場合、一時的にトレースバックをスキップすることで、不正なスタックトレースの生成を防ぎます。

4.  **`_TraceJumpStack`フラグの導入:**
    `src/runtime/runtime2.go`に`_TraceJumpStack`という新しいフラグが追加されました。このフラグは`gentraceback`関数に渡され、`systemstack`からのスタックジャンプを試みるべきかどうかを指示します。`gentraceback`はこのフラグと現在の実行コンテキスト（`g0`上で`systemstack`関数が実行されており、かつユーザーゴルーチンが存在する場合）をチェックし、必要に応じて`g0`のスタックからユーザーゴルーチンのスタックへと論理的に接続します。

これらの変更により、GoのCPUプロファイリングは、ユーザーコードだけでなく、ランタイムの内部処理、特に`g0`が関与する部分についても、より包括的で正確な情報を提供するようになりました。これにより、Goアプリケーションのパフォーマンスチューニングにおいて、より深い洞察を得ることが可能になります。

## コアとなるコードの解説

### `src/runtime/proc1.go`における`sigprof`関数の変更

`sigprof`関数は、CPUプロファイリングのためにOSから`SIGPROF`シグナルを受け取った際に呼び出されるハンドラです。この関数内でスタックトレースバックを行うかどうかの判断ロジックが変更されました。

```go
// 変更前:
// 	gogo := funcPC(gogo)
// 	if gp == nil || gp != mp.curg ||
// 		sp < gp.stack.lo || gp.stack.hi < sp ||
// 		(gogo <= pc && pc < gogo+_RuntimeGogoBytes) {
// 		traceback = false
// 	}

// 変更後:
	if gp == nil || sp < gp.stack.lo || gp.stack.hi < sp || setsSP(pc) {
		traceback = false
	}
```
この変更により、`_RuntimeGogoBytes`を使った`gogo`関数のPC範囲チェックが、新しく導入された`setsSP(pc)`関数によるチェックに置き換えられました。`setsSP(pc)`は、現在のPCがスタックポインタを直接操作する可能性のある関数（`gogo`, `systemstack`, `mcall`, `morestack`）を指す場合に`true`を返します。これにより、より汎用的かつ堅牢な方法で、スタックトレースバックが不安定になる可能性のある状況を検出できるようになりました。

また、`gentraceback`の呼び出しも変更されています。

```go
// 変更前:
// 	if traceback {
// 		n = gentraceback(pc, sp, lr, gp, 0, &stk[0], len(stk), nil, nil, _TraceTrap)
// 	}

// 変更後:
	if mp.ncgo > 0 && mp.curg != nil && mp.curg.syscallpc != 0 && mp.curg.syscallsp != 0 {
		// Cgo, we can't unwind and symbolize arbitrary C code,
		// so instead collect Go stack that leads to the cgo call.
		// This is especially important on windows, since all syscalls are cgo calls.
		n = gentraceback(mp.curg.syscallpc, mp.curg.syscallsp, 0, mp.curg, 0, &stk[0], len(stk), nil, nil, 0)
	} else if traceback {
		n = gentraceback(pc, sp, lr, gp, 0, &stk[0], len(stk), nil, nil, _TraceTrap|_TraceJumpStack)
	}
```
`traceback`が`true`の場合の`gentraceback`呼び出しに、新しいフラグ`_TraceJumpStack`が追加されました。このフラグは、`gentraceback`に対して`systemstack`からのスタックジャンプを試みるよう指示します。これにより、`g0`上でプロファイリングされた場合でも、ユーザーゴルーチンのスタックに接続して完全なトレースバックを生成できるようになります。

### `src/runtime/proc1.go`における`setsSP`関数の追加

```go
func setsSP(pc uintptr) bool {
	f := findfunc(pc)
	if f == nil {
		// couldn't find the function for this PC,
		// so assume the worst and stop traceback
		return true
	}
	switch f.entry {
	case gogoPC, systemstackPC, mcallPC, morestackPC:
		return true
	}
	return false
}
```
この`setsSP`関数は、与えられたプログラムカウンタ`pc`が、スタックポインタ（SP）を絶対値で設定する可能性のある特定のランタイム関数（`gogo`, `systemstack`, `mcall`, `morestack`）のエントリポイントを指しているかどうかをチェックします。これらの関数はスタックの構造を大きく変更するため、これらの関数内でプロファイリング信号が到着した場合、スタックトレースバックの信頼性が低下する可能性があります。`setsSP`が`true`を返す場合、`sigprof`はトレースバックを一時的に無効にし、安全な状態でのみトレースバックを試みるようにします。

### `src/runtime/traceback.go`における`gentraceback`関数の変更

`gentraceback`関数は、スタックトレースバックの実際の処理を行います。このコミットでは、`_TraceJumpStack`フラグと`systemstack`からのジャンプロジックが追加されました。

```go
// 変更前:
// 	if frame.fp == 0 {
// 		frame.fp = frame.sp + uintptr(funcspdelta(f, frame.pc))

// 変更後:
	if frame.fp == 0 {
		// We want to jump over the systemstack switch. If we're running on the
		// g0, this systemstack is at the top of the stack.
		// if we're not on g0 or there's a no curg, then this is a regular call.
		sp := frame.sp
		if flags&_TraceJumpStack != 0 && f.entry == systemstackPC && gp == g.m.g0 && gp.m.curg != nil {
			sp = gp.m.curg.sched.sp
		}
		frame.fp = sp + uintptr(funcspdelta(f, frame.pc))
```
この変更は、`gentraceback`がフレームポインタ（`frame.fp`）を計算する際に適用されます。
`flags&_TraceJumpStack != 0`：`_TraceJumpStack`フラグが設定されていることを確認します。
`f.entry == systemstackPC`：現在の関数が`systemstack`関数であることを確認します。
`gp == g.m.g0`：現在のゴルーチンが`g0`（システムゴルーチン）であることを確認します。
`gp.m.curg != nil`：`g0`が現在実行中のユーザーゴルーチン（`curg`）を持っていることを確認します。

これらの条件がすべて満たされる場合、つまり`g0`上で`systemstack`関数が実行されており、`_TraceJumpStack`フラグが有効な場合、`frame.sp`の代わりに`gp.m.curg.sched.sp`（現在のユーザーゴルーチンのスタックポインタ）が使用されます。これにより、`g0`のスタックから、`g0`を呼び出したユーザーゴルーチンのスタックへと論理的にジャンプし、ユーザーゴルーチン側のスタックトレースを継続して取得できるようになります。これは、`g0`がどのユーザーゴルーチンのために作業しているかをプロファイル上で正確に表現するために非常に重要です。

## 変更の背景

Go言語の初期のビルドシステムは、各パッケージの`Makefile`内でコンパイラ、アセンブラ、リンカといったビルドツールに関する詳細な定義を直接持っていました。これは、新しいアーキテクチャやオペレーティングシステムをサポートする際に、すべての`Makefile`を個別に更新する必要があるという問題を引き起こしていました。また、パッケージのインストールパスも`$(GOROOT)/pkg$D/`のように、`$D`という変数に依存しており、これも柔軟性に欠ける点でした。

このコミットの背景には、Goのビルドシステムをよりスケーラブルで保守しやすいものにするという明確な意図があります。具体的には、以下の課題を解決しようとしています。

1.  **ビルドツールの定義の一元化**: 各`Makefile`に散らばっていたアーキテクチャ固有のビルドツール定義を共通のファイルに集約することで、変更や追加が容易になります。
2.  **パッケージインストールパスの標準化**: `GOOS`（オペレーティングシステム）と`GOARCH`（アーキテクチャ）に基づいてパッケージがインストールされるようにパスを標準化することで、クロスコンパイルのサポートを強化し、異なる環境でのビルド成果物の管理を簡素化します。
3.  **アセンブラ/アーカイバの変更**: `6ar`のような特定のツール名から、より汎用的な`gopack`への移行は、ビルドツールの抽象化と将来的な柔軟性向上を目指しています。

これらの変更は、Go言語が多様なプラットフォームで動作することを目標としていた初期段階において、ビルドシステムの基盤を固める上で不可欠なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての基本的な知識が必要です。

*   **Makefileとmake**: `Makefile`は、`make`ユーティリティがプログラムのコンパイルやインストールなどのタスクを自動化するために使用するスクリプトファイルです。依存関係に基づいてコマンドを実行し、プロジェクトのビルドプロセスを管理します。
*   **Go言語のビルドシステム**: Go言語は、独自のビルドツールチェーンを持っています。初期のGoでは、C言語のツールチェーン（`gcc`など）と連携しつつ、Go独自のコンパイラ（`6g`, `8g`, `5g`など、数字はターゲットアーキテクチャのビット数を表す）やアセンブラ（`6a`, `8a`, `5a`）、リンカ（`6l`, `8l`, `5l`）を使用していました。
*   **`GOROOT`**: Goのインストールディレクトリのルートパスを示す環境変数です。Goのソースコード、コンパイル済みパッケージ、ツールなどがこのディレクトリ以下に配置されます。
*   **`GOOS`と`GOARCH`**: これらはGoの環境変数で、それぞれターゲットのオペレーティングシステム（例: `linux`, `windows`, `darwin`）とアーキテクチャ（例: `amd64`, `386`, `arm`）を指定します。Goのクロスコンパイルにおいて非常に重要です。
*   **`gopack`**: Goの初期のビルドツールの一つで、コンパイルされたオブジェクトファイル（`.a`ファイル）をアーカイブ（ライブラリ）にまとめる役割を担っていました。これはC言語における`ar`コマンドに相当します。
*   **チェンジリスト (CL)**: Goプロジェクトでは、変更はチェンジリストとして提出され、レビューを経てコミットされます。`CL 29923`はこのコミットの元となった変更提案を指します。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムにおける「設定の集中化」と「プラットフォーム抽象化の強化」にあります。

以前の`Makefile`では、各パッケージが自身のビルドに必要なコンパイラ（`GC`）、アセンブラ（`AS`）、リンカ（`LD`）、アーカイバ（`AR`）といったツールを、ターゲットアーキテクチャ（`GOARCH`）に応じて個別に定義していました。例えば、`O_arm=5`, `O_amd64=6`, `O_386=8`といった変数を使って、アーキテクチャごとに異なるツール（例: `5g`, `6g`, `8g`）を呼び出していました。

このコミットでは、これらの冗長な定義を削除し、代わりに`include $(GOROOT)/src/Make.$(GOARCH)`という行を導入しています。これにより、各`Makefile`は、`GOROOT`ディレクトリ内の`src/Make.$(GOARCH)`ファイルから、現在のターゲットアーキテクチャに応じた共通のビルドツール定義を読み込むようになります。この共通ファイルには、`GC`, `CC`, `AS`などの変数が適切に設定されており、各パッケージの`Makefile`はこれらの共通定義を利用するだけでよくなります。

また、アーカイバの指定が`AR=6ar`のような具体的なツール名から`AR=gopack`へと変更されています。これは、Goのビルドツールチェーンが進化し、より汎用的な`gopack`コマンドが導入されたことを示唆しています。`gopack`は、Goのオブジェクトファイルをまとめてライブラリ（`.a`ファイル）を作成するためのツールであり、特定のアーキテクチャに依存しないインターフェースを提供します。

さらに、コンパイル済みパッケージのインストールパスも変更されました。以前は`$(GOROOT)/pkg$D/`という形式でしたが、これは`$(GOROOT)/pkg/$(GOOS)_$(GOARCH)$D/`へと変更されています。この新しいパスは、オペレーティングシステム（`GOOS`）とアーキテクチャ（`GOARCH`）を明示的に含んでおり、異なるプラットフォーム向けのビルド成果物が衝突することなく、より整理された形で管理されることを可能にします。これは、Goのクロスコンパイル機能の基盤を強化する上で重要な変更です。

これらの変更により、Goのビルドシステムは、新しいアーキテクチャのサポートやビルドツールの更新がはるかに容易になり、全体としての保守性と拡張性が大幅に向上しました。

## コアとなるコードの変更箇所

このコミットは、`src/lib`以下の多数のパッケージの`Makefile`に同様の変更を加えています。以下に、代表的な変更パターンを示します。

**変更前:**

```makefile
# src/lib/bignum/Makefile の一部 (変更前)
D=

O_arm=5
O_amd64=6
O_386=8
OS=568vq

O=$(O_$(GOARCH))
GC=$(O)g -I_obj
CC=$(O)c -FVw
AS=$(O)a
AR=6ar

# ...

install: packages
	test -d $(GOROOT)/pkg && mkdir -p $(GOROOT)/pkg$D
	cp _obj$D/bignum.a $(GOROOT)/pkg$D/bignum.a
```

**変更後:**

```makefile
# src/lib/bignum/Makefile の一部 (変更後)
D=

include $(GOROOT)/src/Make.$(GOARCH)
AR=gopack

# ...

install: packages
	test -d $(GOROOT)/pkg && mkdir -p $(GOROOT)/pkg/$(GOOS)_$(GOARCH)$D
	cp _obj$D/bignum.a $(GOROOT)/pkg/$(GOOS)_$(GOARCH)$D/bignum.a
```

このパターンは、`src/lib`以下のほぼすべての`Makefile`に適用されています。

## コアとなるコードの解説

変更の核心は以下の3点です。

1.  **ビルドツール定義の削除と共通ファイルのインクルード**:
    *   `O_arm=5`, `O_amd64=6`, `O_386=8`, `OS=568vq`, `O=$(O_$(GOARCH))`, `GC=$(O)g -I_obj`, `CC=$(O)c -FVw`, `AS=$(O)a`といった、アーキテクチャ固有のコンパイラ、アセンブラ、リンカの定義が各`Makefile`から削除されました。
    *   代わりに、`include $(GOROOT)/src/Make.$(GOARCH)`という行が追加されました。これにより、ビルド時に`GOROOT/src`ディレクトリにある、現在のターゲットアーキテクチャ（例: `Make.amd64`, `Make.386`）に対応する共通の`Makefile`スニペットが読み込まれます。この共通ファイルが、`GC`, `CC`, `AS`などの変数を一元的に定義する役割を担います。これにより、各パッケージの`Makefile`はこれらの詳細を知る必要がなくなり、簡潔になります。

2.  **アーカイバの変更**:
    *   `AR=6ar`という行が`AR=gopack`に変更されました。`6ar`はPlan 9由来のツールで、特定のアーキテクチャ（この場合はamd64）に特化したアーカイバでしたが、`gopack`はGoのビルドシステム内でより汎用的に使用されるアーカイバです。この変更は、GoのビルドツールチェーンがよりGoネイティブなツールへと移行していることを示しています。

3.  **インストールパスの変更**:
    *   `$(GOROOT)/pkg$D/`というパッケージインストールパスが、`$(GOROOT)/pkg/$(GOOS)_$(GOARCH)$D/`に変更されました。
        *   `$D`は、パッケージのサブディレクトリパス（例: `/container/` for `container/list`）を表す変数です。
        *   新しいパスには、`$(GOOS)`（ターゲットOS）と`$(GOARCH)`（ターゲットアーキテクチャ）が明示的に含まれています。これにより、例えばLinux/amd64向けのパッケージは`$(GOROOT)/pkg/linux_amd64/`以下に、Windows/386向けのパッケージは`$(GOROOT)/pkg/windows_386/`以下にインストールされるようになります。この変更は、異なるOSやアーキテクチャ向けのビルド成果物を明確に分離し、クロスコンパイル環境での管理を容易にするためのものです。

これらの変更は、Goのビルドシステムが初期の試行錯誤の段階から、より堅牢でスケーラブルな構造へと進化していく過程を示しています。

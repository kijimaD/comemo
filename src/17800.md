## 元コミット内容

`cmd/cgo: fix Xcode 5 incompatibility for #defined expressions`

このコミットは、`#define`された式に対するXcode 5の非互換性を修正します。
Clangが常に警告を出すようなコード（例: `"1;"`というステートメント）を与えることで、Clangが常に非ゼロのステータスで終了するようにします。
これにより、Issue #6128が修正されます。

## 変更の背景

Go言語の`cgo`ツールは、GoプログラムからC言語のコードを呼び出すためのブリッジを提供します。このツールは、C言語のヘッダファイルを解析するためにClangコンパイラを内部的に利用しています。

問題は、Xcode 5に同梱されているClangコンパイラの挙動変更に起因します。以前のバージョンのClangでは、`#define`された式が未使用であっても、それに関連する警告を生成していました。しかし、Xcode 5のClang（具体的には、[http://llvm.org/viewvc/llvm-project?view=revision&revision=172696](http://llvm.org/viewvc/llvm-project?view=revision&revision=172696) のリビジョンで導入された変更）では、`#define`された式が未使用の場合に警告を抑制するようになりました。

`cgo`は、C言語のシンボル（変数、関数、マクロなど）の種類（式なのか、型なのかなど）を推測するために、ClangにCコードの一部を渡し、その出力（特に警告）を解析していました。Clangが警告を生成しない場合、`cgo`はシンボルの種類を正しく推測できず、結果としてコンパイルエラーや誤ったコード生成を引き起こす可能性がありました。

特に、`#define`されたシンボルがすべて式である場合、Clangは警告を一切出力せず、正常終了してしまいます。`cgo`はClangの終了ステータスや出力される警告を基にシンボルの種類を判断しているため、警告が出ないことで、`cgo`がシンボルを正しく識別できなくなるという問題が発生しました。

この問題は、GoのIssue #6128として報告されました。

## 前提知識の解説

*   **cgo**: Go言語のツールチェーンの一部で、GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を利用したりするための機能を提供します。`import "C"`という特殊なインポート文を使用することで、C言語のコードをGoプログラムに組み込むことができます。
*   **Clang**: LLVMプロジェクトの一部であるC、C++、Objective-C、Objective-C++コンパイラです。AppleのXcode開発環境で広く使用されています。`cgo`は内部的にClang（またはGCC）を呼び出してC言語のコードを解析します。
*   **`#define`**: C言語のプリプロセッサディレクティブの一つで、マクロを定義するために使用されます。これにより、コード内の特定の文字列を別の文字列に置換することができます。例えば、`#define X 0x1`は、コード中の`X`を`0x1`に置換します。
*   **プリプロセッサ**: コンパイルの前にソースコードを処理するプログラムです。`#define`などのプリプロセッサディレクティブを解釈し、ソースコードを変換します。
*   **警告 (Warning)**: コンパイラがコード内で潜在的な問題や非推奨の構文を見つけた場合に生成するメッセージです。警告は通常、コンパイルを中断させませんが、プログラムの動作に影響を与える可能性があります。
*   **終了ステータス (Exit Status)**: プログラムが終了する際にオペレーティングシステムに返す数値です。通常、0は成功を示し、非ゼロの値はエラーや異常終了を示します。`cgo`はClangの終了ステータスをチェックして、Cコードの解析が成功したかどうかを判断します。
*   **`golang.org/issue/6128`**: このコミットが修正するGo言語のバグトラッカー上の特定の課題（Issue）です。

## 技術的詳細

`cgo`は、C言語のヘッダファイルやCコードの断片をClangに渡し、その出力を解析することで、GoコードからCのシンボルにアクセスするための情報を収集します。このプロセスの一部として、`cgo`はClangが生成する警告を利用して、特定のCシンボルが式であるか、型であるかなどを推測していました。

Xcode 5に同梱されたClangの変更により、`#define`された式が未使用の場合に警告が抑制されるようになりました。これは、Clangの最適化や警告のノイズを減らすための改善でしたが、`cgo`にとっては予期せぬ副作用をもたらしました。

具体的には、`cgo`がClangに渡すCコードの断片が、すべて`#define`された式（例: `#define X 1`）のみを含んでいた場合、Clangは警告を一切出力せず、正常終了してしまいます。`cgo`はClangが警告を出すことを期待しており、警告が出ない場合はシンボルの種類を正しく判断できませんでした。

このコミットの解決策は、Clangが常に何らかの警告を生成するように、意図的に警告を誘発するコードを挿入することです。挿入されるコードは`"1;"`というステートメントです。このステートメントは、C言語では有効な式ですが、通常は副作用がなく、単独で存在すると「未使用の式」として警告の対象となります。

この「未使用の式」警告は、Clangのバージョンアップによって抑制される可能性が低い、普遍的な警告であると判断されました。これにより、Clangが常に何らかの警告を生成し、`cgo`がその出力を解析してシンボルの種類を正しく推測できるようになります。たとえClangが将来的にさらに「壊れた」挙動を示したとしても、この警告によって`cgo`は異常を検知できるようになります。

## コアとなるコードの解説

`src/cmd/cgo/gcc.go`ファイルの`guessKinds`関数は、C言語のシンボルの種類を推測する役割を担っています。この関数内で、Clangに渡すCコードの文字列を構築しています。

変更点として、以下の行が追加されました。

```go
	// For a #defined expression, clang silences the warning about "unused expression".
	// http://llvm.org/viewvc/llvm-project?view=revision&revision=172696
	// Silencing the warning is not a big deal, because our default assumption is that
	// (in the absence of other evidence) names are expressions.
	// However, if all the C names we are investigating are #defined expressions,
	// clang will print no warnings at all and then exit successfully.
	// We want clang to print warnings, so seed the code with a function
	// that is guaranteed to provoke a warning (that we will ignore).
	// This way, if clang becomes even more broken, we\'ll find out.
	// See golang.org/issue/6128.
	fmt.Fprintf(&b, "1;\\n")
```

このコードブロックは、`b`という`bytes.Buffer`にCコードの文字列を追加しています。`fmt.Fprintf(&b, "1;\\n")`という行が追加された主要な変更です。

*   `fmt.Fprintf(&b, "1;\\n")`: これは、C言語のコードとして`1;`というステートメントを挿入します。C言語では、`1`は整数リテラルであり、`1;`は有効な式ステートメントです。しかし、この式には副作用がなく、その値も使用されないため、多くのコンパイラ（Clangを含む）は「未使用の式」として警告を生成します。

この変更の意図は、コメントに詳細に記述されています。

1.  **Clangの挙動変更の認識**: Clangが`#define`された式に対する「未使用の式」警告を抑制するようになったことを認識しています。
2.  **デフォルトの仮定**: `cgo`は、他の証拠がない限り、名前が式であるとデフォルトで仮定しているため、警告が抑制されてもそれ自体は大きな問題ではないと述べています。
3.  **問題の核心**: しかし、調査対象のC名がすべて`#define`された式である場合、Clangは警告を一切出力せず、正常終了してしまうことが問題であると指摘しています。
4.  **警告の必要性**: `cgo`はClangに警告を出力してほしいと考えているため、無視されることが保証されている警告を誘発するコードを挿入します。
5.  **将来への備え**: この方法により、Clangが将来的にさらに「壊れた」挙動を示した場合でも、`cgo`がそれを検知できるようになります。
6.  **関連Issue**: `golang.org/issue/6128`がこの問題に関連していることを明記しています。

`misc/cgo/test/issue6128.go`のテストファイルは、`#define X 0x1`のようなマクロ定義を含むCコードを`cgo`経由でGoから利用するシナリオをテストしています。このテストは、修正が正しく機能し、`cgo`がXcode 5環境でも`#define`された式を正しく処理できることを保証します。

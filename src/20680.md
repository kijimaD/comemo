# [インデックス 20680] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `Transport.CloseIdleConnections` メソッドの挙動を改善するものです。具体的には、`CloseIdleConnections` が呼び出された際に、既に確立されているアイドル状態のコネクションだけでなく、現在進行中のダイヤル（接続確立処理）が完了した際にも、そのコネクションがアイドル状態であれば即座にクローズされるように変更を加えます。これにより、リソースリークの可能性を低減し、`http.Client` のシャットダウン時の挙動をより予測可能にします。

    net/http: make Transport.CloseIdleConnections also close pending dials

    See comment 4 of https://code.google.com/p/go/issues/detail?id=8483#c4:

    "So if a user creates a http.Client, issues a bunch of
    requests and then wants to shutdown it and all opened connections;
    what is she intended to do? The report suggests that just waiting for
    all pending requests and calling CloseIdleConnections won't do, as
    there can be new racing connections. Obviously she can't do what
    you've done in the test, as it uses the unexported function.  If this
    happens periodically, it can lead to serious resource leaks (the
    transport is also preserved alive).  Am I missing something?"

    This CL tracks the user's intention to close all idle
    connections (CloseIdleConnections sets it true; and making a
    new request sets it false). If a pending dial finishes and
    nobody wants it, before it's retained for a future caller, the
    "wantIdle" bool is checked and it's closed if the user has
    called CloseIdleConnections without a later call to make a new
    request.

## 変更の背景

この変更は、Go issue #8483 で報告された問題に対応するものです。ユーザーが `http.Client` を作成し、多数のリクエストを発行した後、そのクライアントとそれに伴う全てのオープンなコネクションをシャットダウンしたい場合に、既存の `Transport.CloseIdleConnections()` メソッドだけでは不十分であるという問題が指摘されました。

具体的には、`CloseIdleConnections()` は既にアイドル状態にあるコネクションをクローズしますが、その呼び出し中に新たな接続確立処理（ダイヤル）が開始され、それが完了した際にアイドル状態になった場合、そのコネクションは `CloseIdleConnections()` の影響を受けずに残ってしまう可能性がありました。これにより、特に短命な `http.Client` インスタンスを頻繁に作成・破棄するようなシナリオにおいて、リソースリーク（ソケットやファイルディスクリプタの枯渇など）が発生する懸念がありました。

このコミットは、ユーザーが `CloseIdleConnections()` を呼び出した意図（「もうアイドルコネクションは不要である」という意図）を `Transport` が認識し、その後に完了したダイヤルによって生成されたアイドルコネクションも適切にクローズされるようにすることで、この問題を解決しようとしています。

## 前提知識の解説

このコミットを理解するためには、Go言語の `net/http` パッケージにおける `http.Client` と `Transport` の役割、およびHTTPコネクションの管理について基本的な知識が必要です。

1.  **`http.Client`**: Go言語でHTTPリクエストを行うための高レベルなインターフェースを提供します。通常、アプリケーション内で一度作成し、複数のリクエストで再利用することが推奨されます。
2.  **`http.Transport`**: `http.Client` の内部で実際にHTTPリクエストの送受信、コネクションの確立・管理、TLSハンドシェイクなどを担当する低レベルなコンポーネントです。`Transport` は、パフォーマンス向上のためにHTTP/1.xの「Keep-Alive」機能を利用して、一度確立したTCPコネクションを再利用します。これにより、新しいリクエストごとにTCPハンドシェイクやTLSハンドシェイクを行うオーバーヘッドを削減できます。
3.  **アイドルコネクション (Idle Connections)**: Keep-Alive機能により、HTTPリクエストの処理が完了した後も、将来のリクエストのために開いたまま維持されるコネクションのことです。`Transport` はこれらのアイドルコネクションをプール（キャッシュ）します。
4.  **`CloseIdleConnections()`**: `Transport` のメソッドで、現在プールされているアイドル状態のコネクションを全てクローズします。これは、クライアントがもう使われない場合や、リソースを解放したい場合に呼び出されます。
5.  **ダイヤル (Dial)**: TCPコネクションを確立するプロセスを指します。`Transport` は必要に応じて新しいコネクションをダイヤルします。
6.  **リソースリーク**: プログラムが使用したリソース（メモリ、ファイルディスクリプタ、ネットワークソケットなど）を適切に解放せず、それらが蓄積されてシステムのリソースを枯渇させてしまう問題です。

このコミットの核心は、`CloseIdleConnections()` が呼び出された「後」に、新たなダイヤルが完了してアイドル状態になったコネクションの扱いです。以前は、`CloseIdleConnections()` が呼び出された時点でのアイドルコネクションしかクローズされず、その後に確立されたコネクションは対象外でした。

## 技術的詳細

このコミットは、`net/http.Transport` 構造体に `wantIdle` という新しいブーリアンフィールドを追加することで、ユーザーの「アイドルコネクションをクローズしたい」という意図を永続的に追跡します。

1.  **`Transport.CloseIdleConnections()` の変更**:
    *   このメソッドが呼び出されると、既存のアイドルコネクションをクローズするだけでなく、`t.wantIdle = true` を設定します。これにより、`Transport` は「ユーザーがアイドルコネクションを望んでいない」という状態を記憶します。
2.  **`Transport.putIdleConn()` の変更**:
    *   `putIdleConn` は、コネクションがアイドル状態になり、プールに戻される際に呼び出されるメソッドです。
    *   このメソッド内で、`t.wantIdle` の値がチェックされるようになります。
    *   もし `t.wantIdle` が `true` であれば、つまり `CloseIdleConnections()` が以前に呼び出されており、かつその後に新しいリクエストが発行されていない場合、`putIdleConn` はそのコネクションをプールに追加せず、即座にクローズします (`pconn.close()`)。そして `false` を返して、コネクションがプールされなかったことを示します。
3.  **`Transport.getIdleConnCh()` の変更**:
    *   このメソッドは、新しいリクエストのためにアイドルコネクションを取得しようとする際に呼び出されます。
    *   このメソッドが呼び出されると、`t.wantIdle = false` が設定されます。これは、新しいリクエストが発行されたということは、ユーザーが再びコネクションを必要としている可能性があり、`CloseIdleConnections()` の意図が一時的に解除されたと見なすためです。

このメカニズムにより、`CloseIdleConnections()` が呼び出された後でも、その後に完了したダイヤルによって生成されたコネクションが誤ってアイドルプールに保持されることを防ぎ、即座にクローズされるようになります。これにより、リソースリークの懸念が解消されます。

## コアとなるコードの解説

このコミットの核心は、`Transport` の状態管理に `wantIdle` という新しいフラグを導入した点です。

*   **`wantIdle` フラグ**: このブーリアン値は、ユーザーが `CloseIdleConnections()` を呼び出したことによって、`Transport` が「アイドルコネクションを望んでいない」状態にあることを示します。
    *   `CloseIdleConnections()` が呼び出されると `true` に設定されます。これは、既存のアイドルコネクションをクローズするだけでなく、将来的にアイドルになる可能性のあるコネクションもクローズしたいというユーザーの意図を記録します。
    *   新しいリクエストが `Transport` を通じて行われる（具体的には `getIdleConnCh` が呼び出される）と `false` にリセットされます。これは、ユーザーが再びコネクションを必要としているため、アイドルコネクションのクローズ意図が一時的に解除されたと見なすためです。

*   **`putIdleConn` の変更**: この関数は、使用済みのコネクションをアイドルプールに戻す役割を担います。変更後、コネクションがプールに戻される直前に `wantIdle` フラグがチェックされます。もし `wantIdle` が `true` であれば、そのコネクションはプールに戻されずに即座にクローズされます。これにより、`CloseIdleConnections()` が呼び出された後に、新たなダイヤルによって確立されたコネクションがアイドル状態になったとしても、それがプールに残り続けることを防ぎます。

この変更により、`CloseIdleConnections()` は単に既存のアイドルコネクションをクリーンアップするだけでなく、その後のコネクションライフサイクルにも影響を与え、より堅牢なリソース管理を実現しています。

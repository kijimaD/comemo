# [インデックス 20048] ファイルの概要

このコミットは、Go言語のリンカ (`liblink`) において、`power64` アーキテクチャ向けにスタック分割機能を一時的に無効化する変更です。これは、`power64` へのGoの移植作業の初期段階における暫定的な対応と考えられます。

## 変更の背景

このコミットは、Go言語の `power64` (PowerPC 64-bit) アーキテクチャへの移植作業の一環として行われました。コミットメッセージの `[dev.power64]` というプレフィックスと、コミット日付が2014年8月であることから、これはGo 1.5で `ppc64` の公式サポートが開始される（2015年8月）よりも前の、開発初期段階での変更であることがわかります。

当時のGoランタイムは、ゴルーチンのスタック管理に「セグメントスタック (segmented stacks)」と呼ばれる方式を採用していました。これは、スタックが不足した際に新しいメモリセグメントを割り当ててスタックを「分割」し、複数のセグメントにまたがってスタックを拡張する仕組みです。しかし、このセグメントスタック方式には、特にスタックの頻繁な拡張と縮小が発生する際に「ホットスプリット問題 (hot split problem)」と呼ばれるパフォーマンス上の課題がありました。

`power64` のような新しいアーキテクチャへの移植では、Goランタイムの低レベルな部分、特にスタック管理や関数呼び出し規約 (ABI) の実装が複雑になります。このコミットでスタック分割を一時的に無効化したのは、おそらく `power64` 環境でのセグメントスタックの実装に何らかの問題（バグ、パフォーマンスボトルネック、ABIの不整合など）があったため、まずは基本的な実行を可能にするための暫定的な措置であったと考えられます。`// TODO(minux)` というコメントからも、これが一時的な回避策であり、後で適切な解決策が実装される予定であったことが伺えます。

Go 1.4（2014年12月リリース）以降、Goランタイムはセグメントスタックから「連続スタック (contiguous stacks)」と「スタックコピー (stack copying)」方式に移行し、ホットスプリット問題を解決しました。このコミットは、その移行期よりも前の、セグメントスタックが主流であった時期の `power64` 移植における課題を示しています。

## 前提知識の解説

### Go言語のスタック管理とゴルーチン

Go言語は軽量な並行処理単位である「ゴルーチン (goroutine)」を特徴としています。各ゴルーチンは独自のスタックを持ち、このスタックは必要に応じて動的にサイズが変更されます。

*   **初期スタックサイズ**: ゴルーチンは非常に小さな初期スタックサイズ（Go 1.20では通常2KB）で開始されます。これにより、多数のゴルーチンを効率的に生成できます。
*   **動的なスタックの伸縮**: ゴルーチンのスタックは固定サイズではなく、関数呼び出しの深さに応じて動的に拡張・縮小します。

### スタック分割 (Segmented Stacks)

このコミットが作成された2014年時点のGoランタイムでは、スタックの拡張に「セグメントスタック」という手法が用いられていました。

1.  **スタックオーバーフローの検出**: 各関数のプロローグ（開始部分）には、現在のスタックフレームが残りのスタック領域に収まるかをチェックするコードが挿入されていました。
2.  **`morestack` 関数の呼び出し**: スタック領域が不足すると判断された場合、ランタイムの `morestack` 関数が呼び出されます。
3.  **新しいセグメントの割り当て**: `morestack` は、新しいメモリセグメントを割り当て、既存のスタックセグメントとリンクさせます。これにより、論理的には連続したスタックが、物理的には複数の不連続なメモリセグメントに分散して存在することになります。
4.  **実行の再開**: 新しいセグメント上で関数の実行が再開されます。

この方式は、スタックの初期サイズを小さく保ちつつ、必要に応じて拡張できるという利点がありましたが、セグメント間の切り替えや、頻繁なスタックの伸縮によるセグメントの割り当て・解放がパフォーマンスオーバーヘッドとなる「ホットスプリット問題」を抱えていました。

### `liblink` (Goリンカ)

`liblink` はGo言語のリンカであり、コンパイラによって生成されたオブジェクトファイル（機械語コード）を結合し、実行可能なバイナリを生成する役割を担っています。スタック分割（またはスタックコピー）のためのコード（例えば、関数のプロローグにスタックチェックを挿入する部分や、`morestack` 関数への呼び出しを生成する部分）は、リンカまたはコンパイラによって処理されます。

### `obj9.c`

Goのツールチェインでは、特定のアーキテクチャを識別するために数字が使われることがあります。例えば、`6g` はamd64コンパイラ、`8g` は386コンパイラ、`9g` はppc64コンパイラを指すことがありました。したがって、`src/liblink/obj9.c` は、リンカのPowerPC 64-bit (ppc64) アーキテクチャ固有のバックエンド、特にオブジェクトファイルの処理やコード生成に関連する部分であると推測されます。このファイル内の `stacksplit` 関数は、PowerPCアーキテクチャにおけるスタック分割のロジックを実装していたと考えられます。

### `dev.power64`

これは、Go言語の `power64` アーキテクチャへの移植作業のための開発ブランチまたはコンテキストを示しています。新しいアーキテクチャへの移植は、コンパイラ、アセンブラ、リンカ、ランタイムなど、Goツールチェインの多くの部分にわたる大規模な作業であり、段階的に進められます。

## 技術的詳細

このコミットは、`src/liblink/obj9.c` ファイル内の `stacksplit` 関数に、以下の変更を加えることで、`power64` アーキテクチャにおけるスタック分割のロジックを無効化しています。

```c
static Prog*
stacksplit(Link *ctxt, Prog *p, int32 framesize, int noctxt)
{
	// TODO(minux)
	return p;
	// ... 既存のスタック分割ロジック ...
}
```

通常、`stacksplit` 関数は、スタックの拡張が必要な場合に `morestack` 関数への呼び出しを挿入したり、スタックチェックのコードを生成したりする役割を担っていました。しかし、この変更により、関数が呼び出されるとすぐに引数 `p` をそのまま返しています。これは、`stacksplit` 関数が本来行うべきスタック分割のためのコード生成やロジックの適用を一切行わないことを意味します。

この「無効化」は、`power64` アーキテクチャへのGoの移植作業において、セグメントスタックの実装がまだ安定していないか、あるいは特定の条件下で問題を引き起こしていたため、一時的にその機能をバイパスすることで、他の部分の開発やデバッグを進めるための措置であったと推測されます。

考えられる具体的な問題点としては、以下のようなものが挙げられます。

*   **ABIの不整合**: PowerPCの関数呼び出し規約 (ABI) と、Goランタイムが期待するスタックフレームの構造やレジスタの使用方法との間に不整合があった可能性。
*   **ランタイムのバグ**: `power64` 環境でのスタック拡張・縮小処理、特に `morestack` 関数や関連するアセンブリコードにバグがあった可能性。
*   **パフォーマンス問題**: `power64` 環境でセグメントスタックの切り替えが極端に遅い、またはリソースを大量に消費するなどのパフォーマンス上の問題があった可能性。
*   **デバッグの簡素化**: スタック分割の複雑なロジックを一時的に無効にすることで、他の部分（例えば、基本的な関数呼び出し、レジスタの割り当て、ガベージコレクションなど）のデバッグを容易にする目的。

`// TODO(minux)` というコメントは、この変更が永続的なものではなく、将来的に適切なスタック管理メカニズムが `power64` 向けに実装されることを示唆しています。実際に、Go 1.4でセグメントスタックから連続スタックへの移行が行われたことで、この一時的な無効化は不要になったと考えられます。

## コアとなるコードの解説

`stacksplit` 関数は、Goのリンカがスタック分割ロジックを適用するために呼び出す関数です。この関数は、リンカのコンテキスト (`ctxt`)、現在のプログラム命令 (`p`)、フレームサイズ (`framesize`)、およびコンテキストなしフラグ (`noctxt`) を引数として受け取ります。

変更前は、この関数内でスタックの拡張が必要な場合に、スタックチェック命令や `morestack` 関数へのジャンプ命令などを生成する複雑なロジックが実行されていました。

しかし、このコミットでは、関数の冒頭に以下の3行が追加されています。

1.  `// TODO(minux)`: これは開発者向けのコメントで、このコードが一時的なものであり、後で修正が必要であることを示しています。`minux` はコミットの作者である Shenghou Ma のハンドル名です。
2.  `return p;`: この行が最も重要です。関数が受け取ったプログラム命令 `p` を、何の変更も加えずにそのまま返しています。これにより、`stacksplit` 関数が本来行うべきスタック分割のためのコード生成やロジックの適用が完全にスキップされます。

結果として、`power64` アーキテクチャ向けのバイナリでは、このリンカの変更が適用された期間中、スタックが動的に拡張されるための仕組みが機能しなくなります。これは、スタックオーバーフローが発生しやすくなることを意味しますが、移植作業の初期段階では、スタック管理の複雑な問題を一時的に回避し、他の部分の動作確認を優先するための実用的な選択であったと考えられます。

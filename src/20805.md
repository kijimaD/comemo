# [インデックス 20805] ファイルの概要

このコミットは、Goコンパイラ (`cmd/gc`) およびランタイムにおいて、2ワード、3ワード、4ワードのデータに対するライトバリア処理を最適化するためのものです。具体的には、これらのサイズのデータ割り当て時に発生するライトバリアのオーバーヘッドを削減するため、汎用的な `memmove` ベースの `writebarrierfat` ルーチンではなく、サイズに特化した `writebarrierfat2`, `writebarrierfat3`, `writebarrierfat4` という新しいライトバリア関数を導入しています。これにより、Goプログラムのパフォーマンス、特にガベージコレクションに関連するオーバーヘッドが改善されます。

## 元コミット内容

このコミットは、Goコンパイラが生成するコードにおいて、2ワード、3ワード、および4ワードの値を割り当てる際のライトバリア処理を最適化することを目的としています。以前は、これらのサイズのデータにポインタが含まれる場合、汎用的な `writebarrierfat` ルーチンが呼び出され、その中で `memmove` が使用されていました。しかし、少量のデータに対して `memmove` を呼び出すことはオーバーヘッドが大きいため、このコミットでは、コピーされるデータの量に特化した `writebarrierfat2`, `writebarrierfat3`, `writebarrierfat4` という新しいライトバリア関数を導入し、これらを代わりに呼び出すように変更しています。これにより、多くのベンチマークでパフォーマンスの向上が見られます。

## 変更の背景

Goのガベージコレクション (GC) は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。GoのGCはコンカレントGCであり、プログラムの実行と並行してGCが動作します。この並行性を維持しつつ、GCがメモリの状態を正確に把握するために「ライトバリア (Write Barrier)」という仕組みが導入されています。

ライトバリアは、ポインタの書き込み（あるポインタが指すオブジェクトを別のオブジェクトに書き換えるなど）が行われる際に、GCがその変更を追跡できるようにするためのフックです。これにより、GCがオブジェクトグラフを走査している最中にポインタが変更されても、GCが誤って到達可能なオブジェクトを解放してしまうことを防ぎます。

このコミットが作成された時点では、2ワード、3ワード、4ワードといった比較的小さなサイズの複合型（例えば、構造体や配列）の割り当てでポインタが含まれる場合、コンパイラは汎用的な `writebarrierfat` というランタイム関数を呼び出していました。この `writebarrierfat` 関数は、内部で `memmove` を使用してデータをコピーしていました。

しかし、`memmove` は任意のサイズのメモリブロックを効率的にコピーするために設計された汎用的な関数であり、その呼び出しには一定のオーバーヘッドが伴います。特に、2ワード（16バイト）、3ワード（24バイト）、4ワード（32バイト）といった非常に小さなデータブロックをコピーするたびに `memmove` を呼び出すことは、そのオーバーヘッドがコピー自体のコストを上回る可能性があり、パフォーマンスのボトルネックとなっていました。

この非効率性を解消し、Goプログラムの実行速度を向上させることが、このコミットの主要な背景です。特定のサイズに特化したライトバリア関数を導入することで、`memmove` の汎用的なオーバーヘッドを回避し、より直接的かつ効率的なメモリコピーを実現することを目指しました。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、主に「三色マーク＆スイープ」アルゴリズムをベースにしたコンカレントGCです。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑えることを目指しています。

*   **三色マーク＆スイープ**: オブジェクトを白、灰、黒の3色でマークし、到達可能性を判断します。
    *   **白**: まだGCによって走査されていないオブジェクト。最終的に到達不可能と判断されれば解放されます。
    *   **灰**: GCによって走査中だが、そのオブジェクトが参照する他のオブジェクトはまだ走査されていない状態。
    *   **黒**: GCによって走査済みで、そのオブジェクトが参照する全てのオブジェクトも走査済みである状態。
*   **コンカレントGC**: アプリケーションのゴルーチンとGCゴルーチンが並行して動作します。これにより、GCによるアプリケーションの停止時間を短縮します。
*   **ライトバリア (Write Barrier)**: コンカレントGCの正確性を保証するために不可欠なメカニズムです。アプリケーションのゴルーチンがヒープ上のポインタを書き換える際に、GCがその変更を検知し、オブジェクトグラフの整合性を保つための処理がライトバリアです。具体的には、ポインタの書き込みが行われる前に、元のポインタが指していたオブジェクトや、新しく書き込まれるポインタが指すオブジェクトを「灰色のオブジェクト」としてマークするなどの処理が行われます。これにより、GCがオブジェクトグラフを走査している最中にポインタが変更されても、到達可能なオブジェクトが誤って回収されることを防ぎます。ライトバリアは、GCのオーバーヘッドの主要な要因の一つとなることがあります。

### `memmove`

`memmove` は、C言語の標準ライブラリ関数の一つで、指定されたメモリ領域から別のメモリ領域へバイト列をコピーします。`memcpy` と異なり、コピー元とコピー先のメモリ領域が重なっていても正しく動作することが保証されています。

Goのランタイムでは、C言語で書かれた部分や、アセンブリ言語で書かれた部分で `memmove` に相当する低レベルのメモリコピー操作が頻繁に利用されます。この関数は汎用性が高く、任意のサイズのデータを効率的にコピーできるように最適化されていますが、その汎用性ゆえに、非常に小さなデータをコピーする際には、関数呼び出しのオーバーヘッドや、コピーサイズを動的に判断するためのロジックが、実際のデータコピーにかかる時間よりも大きくなることがあります。

### Goのコンパイラ (`cmd/gc`)

`cmd/gc` はGo言語の公式コンパイラです。Goのソースコードを読み込み、抽象構文木 (AST) を構築し、型チェック、最適化、そして最終的にアセンブリコードまたはオブジェクトコードを生成します。このコンパイラは、ガベージコレクションのためのライトバリア呼び出しを、ポインタの書き込みが行われる箇所に自動的に挿入する役割も担っています。

### Goのランタイム (`src/runtime`)

`src/runtime` はGoプログラムの実行を支える中核部分であり、Go言語で書かれたコードとアセンブリ言語で書かれたコードで構成されています。ガベージコレクタ、スケジューラ、メモリ管理、チャネル操作、ゴルーチン管理など、Go言語の並行処理モデルやメモリモデルを実現するための低レベルな機能がここに実装されています。ライトバリア関数もこのランタイムの一部として提供されます。

### セグメントスタック (Segmented Stacks)

セグメントスタックは、Go 1.3以前のGoランタイムで採用されていたスタック管理方式です。ゴルーチンのスタックサイズが動的に増減する際に、連続したメモリ領域を確保するのではなく、必要に応じて小さなセグメントを割り当て、それらをリンクしてスタックを構成する方式でした。これにより、スタックオーバーフローを避けるために大きなスタックを事前に確保する必要がなく、メモリ効率が良いという利点がありました。

しかし、セグメントスタックにはいくつかの欠点がありました。特に、スタックの拡張や縮小（スタックの「スプリット」や「グロー」）が発生する際に、セグメント間のリンクを更新したり、新しいセグメントを割り当てたりするオーバーヘッドがありました。また、スタックのセグメントが連続していないため、C言語とのFFI (Foreign Function Interface) 呼び出しが複雑になるという問題もありました。

Go 1.3で、セグメントスタックは「連続スタック (Contiguous Stacks)」に置き換えられました。連続スタックでは、スタックは単一の連続したメモリブロックとして確保され、必要に応じてそのブロック全体がより大きなブロックにコピーされることで拡張されます。これにより、スタック操作のオーバーヘッドが削減され、C言語との連携も容易になりました。

このコミットメッセージでセグメントスタックが言及されているのは、「（ライトバリア関数の）現在の3つの関数は3+7+15=25になるが、それでも大きな負担ではない（セグメントスタックを廃止した際に、それよりも多くの `morestack` 関数を削除した）」という文脈で、過去の大きな変更と比較して、今回の変更が複雑さやオーバーヘッドの点で小さいことを強調するためです。

## 技術的詳細

このコミットの核心は、Goのライトバリア処理におけるパフォーマンスのボトルネックを解消することにあります。

### `writebarrierfat` の問題点と特化関数の導入

以前のGoランタイムでは、ポインタを含む2ワード、3ワード、4ワードの複合型（例えば、`struct { *int; int }` や `[3]*byte` など）を割り当てる際、コンパイラは汎用的な `writebarrierfat` ランタイム関数を呼び出していました。この関数は、コピー対象のデータの型情報 (`typ`) と、コピー元 (`src`) およびコピー先 (`dst`) のポインタを受け取り、内部で `memmove(dst, src, typ.size)` のように `memmove` を呼び出してデータをコピーしていました。

`memmove` は非常に最適化されたメモリコピー関数ですが、関数呼び出しのオーバーヘッド、コピーサイズを動的に決定するロジック、そして汎用的な実装ゆえのキャッシュ効率の悪さなどが、特に小さなデータ（数ワード程度）のコピーにおいては無視できないコストとなっていました。

この問題を解決するため、このコミットでは以下の3つの新しいライトバリア関数を導入しました。

*   `writebarrierfat2`: 2ワードのデータコピーに特化
*   `writebarrierfat3`: 3ワードのデータコピーに特化
*   `writebarrierfat4`: 4ワードのデータコピーに特化

これらの関数は、コピーするワード数が固定されているため、`memmove` のような汎用的な関数呼び出しを避け、直接的なメモリコピー命令（例えば、アセンブリレベルでの `MOV` 命令のシーケンス）を生成することで、オーバーヘッドを大幅に削減します。

### ポインタの有無と将来の拡張

コミットメッセージには「Today the write barrier does not care which words are pointers, so size alone is enough to distinguish the cases. If we keep these distinctions in Go 1.5 we will need to expand them for all the pointer-vs-scalar possibilities, so the current 3 functions will become 3+7+15 = 25」とあります。

これは、このコミットが作成された時点（Go 1.4リリース前）では、ライトバリアはコピーされるデータブロック内にポインタが含まれているかどうかのみを気にし、どのワードがポインタであるかまでは区別していなかったことを意味します。そのため、2ワード、3ワード、4ワードのデータであれば、そのサイズだけで適切な特化関数を呼び出すことができました。

しかし、Go 1.5以降でライトバリアの粒度をさらに細かくし、データブロック内のどのワードがポインタであるかを区別する必要が生じた場合、各サイズ（2, 3, 4ワード）に対して、ポインタとスカラー（非ポインタ）のあらゆる組み合わせに対応する特化関数が必要になる可能性が示唆されています。

*   **2ワード**: 2つのワードがあり、それぞれがポインタかスカラーかの2通り。`2^2 = 4` 通りの組み合わせ。ただし、ポインタが含まれない場合はライトバリア不要なので、ポインタが1つ以上含まれる `2^2 - 1 = 3` 通り。既存の `writebarrierfat2` に加えて、ポインタの配置に応じた3つのバリア関数が必要になる。
*   **3ワード**: `2^3 = 8` 通りの組み合わせ。ポインタが1つ以上含まれる `2^3 - 1 = 7` 通り。
*   **4ワード**: `2^4 = 16` 通りの組み合わせ。ポインタが1つ以上含まれる `2^4 - 1 = 15` 通り。

合計で `3 + 7 + 15 = 25` の特化関数が必要になる可能性が示されています。コミットメッセージでは、これは「まだ大きな負担ではない」と述べられており、Go 1.3でセグメントスタックを廃止した際に削除された `morestack` 関数群の数と比較して、この程度の関数増加は許容範囲であるという見解が示されています。これは、将来的なGCの進化を見据えた上での設計判断を示唆しています。

## 変更の背景

Goのガベージコレクション (GC) は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。GoのGCはコンカレントGCであり、プログラムの実行と並行してGCが動作します。この並行性を維持しつつ、GCがメモリの状態を正確に把握するために「ライトバリア (Write Barrier)」という仕組みが導入されています。

ライトバリアは、ポインタの書き込み（あるポインタが指すオブジェクトを別のオブジェクトに書き換えるなど）が行われる際に、GCがその変更を追跡できるようにするためのフックです。これにより、GCがオブジェクトグラフを走査している最中にポインタが変更されても、GCが誤って到達可能なオブジェクトを解放してしまうことを防ぎます。

このコミットが作成された時点では、2ワード、3ワード、4ワードといった比較的小さなサイズの複合型（例えば、構造体や配列）の割り当てでポインタが含まれる場合、コンパイラは汎用的な `writebarrierfat` というランタイム関数を呼び出していました。この `writebarrierfat` 関数は、内部で `memmove` を使用してデータをコピーしていました。

しかし、`memmove` は任意のサイズのメモリブロックを効率的にコピーするために設計された汎用的な関数であり、その呼び出しには一定のオーバーヘッドが伴います。特に、2ワード（16バイト）、3ワード（24バイト）、4ワード（32バイト）といった非常に小さなデータブロックをコピーするたびに `memmove` を呼び出すことは、そのオーバーヘッドがコピー自体のコストを上回る可能性があり、パフォーマンスのボトルネックとなっていました。

この非効率性を解消し、Goプログラムの実行速度を向上させることが、このコミットの主要な背景です。特定のサイズに特化したライトバリア関数を導入することで、`memmove` の汎用的なオーバーヘッドを回避し、より直接的かつ効率的なメモリコピーを実現することを目指しました。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、主に「三色マーク＆スイープ」アルゴリズムをベースにしたコンカレントGCです。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑えることを目指しています。

*   **三色マーク＆スイープ**: オブジェクトを白、灰、黒の3色でマークし、到達可能性を判断します。
    *   **白**: まだGCによって走査されていないオブジェクト。最終的に到達不可能と判断されれば解放されます。
    *   **灰**: GCによって走査中だが、そのオブジェクトが参照する他のオブジェクトはまだ走査されていない状態。
    *   **黒**: GCによって走査済みで、そのオブジェクトが参照する全てのオブジェクトも走査済みである状態。
*   **コンカレントGC**: アプリケーションのゴルーチンとGCゴルーチンが並行して動作します。これにより、GCによるアプリケーションの停止時間を短縮します。
*   **ライトバリア (Write Barrier)**: コンカレントGCの正確性を保証するために不可欠なメカニズムです。アプリケーションのゴルーチンがヒープ上のポインタを書き換える際に、GCがその変更を検知し、オブジェクトグラフの整合性を保つための処理がライトバリアです。具体的には、ポインタの書き込みが行われる前に、元のポインタが指していたオブジェクトや、新しく書き込まれるポインタが指すオブジェクトを「灰色のオブジェクト」としてマークするなどの処理が行われます。これにより、GCがオブジェクトグラフを走査している最中にポインタが変更されても、到達可能なオブジェクトが誤って回収されることを防ぎます。ライトバリアは、GCのオーバーヘッドの主要な要因の一つとなることがあります。

### `memmove`

`memmove` は、C言語の標準ライブラリ関数の一つで、指定されたメモリ領域から別のメモリ領域へバイト列をコピーします。`memcpy` と異なり、コピー元とコピー先のメモリ領域が重なっていても正しく動作することが保証されています。

Goのランタイムでは、C言語で書かれた部分や、アセンブリ言語で書かれた部分で `memmove` に相当する低レベルのメモリコピー操作が頻繁に利用されます。この関数は汎用性が高く、任意のサイズのデータを効率的にコピーできるように最適化されていますが、その汎用性ゆえに、非常に小さなデータをコピーする際には、関数呼び出しのオーバーヘッドや、コピーサイズを動的に判断するためのロジックが、実際のデータコピーにかかる時間よりも大きくなることがあります。

### Goのコンパイラ (`cmd/gc`)

`cmd/gc` はGo言語の公式コンパイラです。Goのソースコードを読み込み、抽象構文木 (AST) を構築し、型チェック、最適化、そして最終的にアセンブリコードまたはオブジェクトコードを生成します。このコンパイラは、ガベージコレクションのためのライトバリア呼び出しを、ポインタの書き込みが行われる箇所に自動的に挿入する役割も担っています。

### Goのランタイム (`src/runtime`)

`src/runtime` はGoプログラムの実行を支える中核部分であり、Go言語で書かれたコードとアセンブリ言語で書かれたコードで構成されています。ガベージコレクタ、スケジューラ、メモリ管理、チャネル操作、ゴルーチン管理など、Go言語の並行処理モデルやメモリモデルを実現するための低レベルな機能がここに実装されています。ライトバリア関数もこのランタイムの一部として提供されます。

### セグメントスタック (Segmented Stacks)

セグメントスタックは、Go 1.3以前のGoランタイムで採用されていたスタック管理方式です。ゴルーチンのスタックサイズが動的に増減する際に、連続したメモリ領域を確保するのではなく、必要に応じて小さなセグメントを割り当て、それらをリンクしてスタックを構成する方式でした。これにより、スタックオーバーフローを避けるために大きなスタックを事前に確保する必要がなく、メモリ効率が良いという利点がありました。

しかし、セグメントスタックにはいくつかの欠点がありました。特に、スタックの拡張や縮小（スタックの「スプリット」や「グロー」）が発生する際に、セグメント間のリンクを更新したり、新しいセグメントを割り当てたりするオーバーヘッドがありました。また、スタックのセグメントが連続していないため、C言語とのFFI (Foreign Function Interface) 呼び出しが複雑になるという問題もありました。

Go 1.3で、セグメントスタックは「連続スタック (Contiguous Stacks)」に置き換えられました。連続スタックでは、スタックは単一の連続したメモリブロックとして確保され、必要に応じてそのブロック全体がより大きなブロックにコピーされることで拡張されます。これにより、スタック操作のオーバーヘッドが削減され、C言語との連携も容易になりました。

このコミットメッセージでセグメントスタックが言及されているのは、「（ライトバリア関数の）現在の3つの関数は3+7+15=25になるが、それでも大きな負担ではない（セグメントスタックを廃止した際に、それよりも多くの `morestack` 関数を削除した）」という文脈で、過去の大きな変更と比較して、今回の変更が複雑さやオーバーヘッドの点で小さいことを強調するためです。

## 技術的詳細

このコミットの核心は、Goのライトバリア処理におけるパフォーマンスのボトルネックを解消することにあります。

### `writebarrierfat` の問題点と特化関数の導入

以前のGoランタイムでは、ポインタを含む2ワード、3ワード、4ワードの複合型（例えば、`struct { *int; int }` や `[3]*byte` など）を割り当てる際、コンパイラは汎用的な `writebarrierfat` ランタイム関数を呼び出していました。この関数は、コピー対象のデータの型情報 (`typ`) と、コピー元 (`src`) およびコピー先 (`dst`) のポインタを受け取り、内部で `memmove(dst, src, typ.size)` のように `memmove` を呼び出してデータをコピーしていました。

`memmove` は非常に最適化されたメモリコピー関数ですが、関数呼び出しのオーバーヘッド、コピーサイズを動的に決定するロジック、そして汎用的な実装ゆえのキャッシュ効率の悪さなどが、特に小さなデータ（数ワード程度）のコピーにおいては無視できないコストとなっていました。

この問題を解決するため、このコミットでは以下の3つの新しいライトバリア関数を導入しました。

*   `writebarrierfat2`: 2ワードのデータコピーに特化
*   `writebarrierfat3`: 3ワードのデータコピーに特化
*   `writebarrierfat4`: 4ワードのデータコピーに特化

これらの関数は、コピーするワード数が固定されているため、`memmove` のような汎用的な関数呼び出しを避け、直接的なメモリコピー命令（例えば、アセンブリレベルでの `MOV` 命令のシーケンス）を生成することで、オーバーヘッドを大幅に削減します。

### ポインタの有無と将来の拡張

コミットメッセージには「Today the write barrier does not care which words are pointers, so size alone is enough to distinguish the cases. If we keep these distinctions in Go 1.5 we will need to expand them for all the pointer-vs-scalar possibilities, so the current 3 functions will become 3+7+15 = 25」とあります。

これは、このコミットが作成された時点（Go 1.4リリース前）では、ライトバリアはコピーされるデータブロック内にポインタが含まれているかどうかのみを気にし、どのワードがポインタであるかまでは区別していなかったことを意味します。そのため、2ワード、3ワード、4ワードのデータであれば、そのサイズだけで適切な特化関数を呼び出すことができました。

しかし、Go 1.5以降でライトバリアの粒度をさらに細かくし、データブロック内のどのワードがポインタであるかを区別する必要が生じた場合、各サイズ（2, 3, 4ワード）に対して、ポインタとスカラー（非ポインタ）のあらゆる組み合わせに対応する特化関数が必要になる可能性が示唆されています。

*   **2ワード**: 2つのワードがあり、それぞれがポインタかスカラーかの2通り。`2^2 = 4` 通りの組み合わせ。ただし、ポインタが含まれない場合はライトバリア不要なので、ポインタが1つ以上含まれる `2^2 - 1 = 3` 通り。既存の `writebarrierfat2` に加えて、ポインタの配置に応じた3つのバリア関数が必要になる。
*   **3ワード**: `2^3 = 8` 通りの組み合わせ。ポインタが1つ以上含まれる `2^3 - 1 = 7` 通り。
*   **4ワード**: `2^4 = 16` 通りの組み合わせ。ポインタが1つ以上含まれる `2^4 - 1 = 15` 通り。

合計で `3 + 7 + 15 = 25` の特化関数が必要になる可能性が示されています。コミットメッセージでは、これは「まだ大きな負担ではない」と述べられており、Go 1.3でセグメントスタックを廃止した際に削除された `morestack` 関数群の数と比較して、この程度の関数増加は許容範囲であるという見解が示されています。これは、将来的なGCの進化を見据えた上での設計判断を示唆しています。

## コアとなるコードの解説

このコミットのコード変更は、Goコンパイラとランタイムの密接な連携によって実現されています。

1.  **ランタイム関数の宣言 (`src/cmd/gc/builtin.c`, `src/cmd/gc/runtime.go`)**:
    まず、新しい特化ライトバリア関数 (`writebarrierfat2`, `writebarrierfat3`, `writebarrierfat4`) がGoコンパイラに認識されるように、`builtin.c` (C言語で書かれたコンパイラ内部の定義) と `runtime.go` (Go言語で書かれたランタイム関数のGo側宣言) の両方で宣言されます。これにより、コンパイラはこれらの関数を通常のGo関数として扱えるようになります。

2.  **コンパイラによるライトバリア挿入ロジックの変更 (`src/cmd/gc/walk.c`)**:
    Goコンパイラの `walk.c` 内にある `applywritebarrier` 関数は、Goソースコード中のポインタ書き込み箇所を検出し、適切なライトバリア関数呼び出しを挿入する役割を担っています。
    このコミットでは、`applywritebarrier` 関数に新しい条件分岐が追加されました。具体的には、割り当てられるデータの型 (`t`) のサイズ (`t->width`) をチェックし、それが2ワード、3ワード、または4ワードのポインタサイズに相当する場合、それぞれに対応する特化ライトバリア関数 (`writebarrierfat2`, `writebarrierfat3`, `writebarrierfat4`) を呼び出すように変更されました。
    これにより、コンパイラは、以前は一律に `writebarrierfat` を呼び出していた小さな複合型の割り当てに対して、より効率的な特化関数を選択できるようになります。この選択はコンパイル時に行われるため、実行時のオーバーヘッドが削減されます。

3.  **ランタイムでの特化ライトバリア関数の実装 (`src/runtime/mgc0.go`)**:
    最後に、`src/runtime/mgc0.go` にて、`writebarrierfat2`, `writebarrierfat3`, `writebarrierfat4` の実際のGo言語による実装が提供されます。これらの関数は、`memmove` のような汎用的なメモリコピー関数を呼び出す代わりに、直接 `uintptr` 配列の要素をコピーするシンプルなロジックを持っています。
    `//go:nosplit` ディレクティブが付与されていることで、これらの関数が呼び出されてもスタックの拡張チェックや処理が行われず、非常に高速に実行されることが保証されます。これは、ライトバリアが頻繁に呼び出される性質上、パフォーマンスにとって極めて重要です。

これらの変更が連携することで、Goコンパイラは特定のサイズのポインタを含むデータ割り当てに対して、より効率的なランタイム関数を生成するようになり、結果としてガベージコレクションのオーバーヘッドが削減され、Goプログラム全体のパフォーマンスが向上します。

# [インデックス 24087] ファイルの概要

このコミットは、Goランタイムにおいて、データ競合検出モード（`-race`モード）で実行される際のゴルーチンスケジューリングにランダム性を導入するものです。これにより、特定のスケジューリング順序に依存する潜在的なバグを早期に発見しやすくすることを目的としています。

## 変更の背景

Go 1.5では、Goスケジューラの内部的な変更により、ゴルーチンのスケジューリング順序が以前のバージョンと異なりました。この変更は、多くの既存のテストが特定の（そして意図しない）スケジューリング順序に依存していたために、それらのテストを壊す結果となりました。これは、テストが並行処理の非決定性を適切に扱っておらず、暗黙的に特定の実行順序を仮定していたことを示しています。

このような「潜在的なスケジューリング順序への依存」は、Goランタイムの将来のバージョンでスケジューラが再び変更された際に、同様の問題を引き起こす可能性があります。特に、データ競合検出モード（`-race`）は、並行処理における問題を発見するための強力なツールですが、決定的なスケジューリングでは、特定の競合条件が常に同じ順序で発生しない限り、検出が困難になることがあります。

このコミットの目的は、Go 1.5のリリースに向けて、`-race`モードでのスケジューリングに意図的にランダム性を導入することです。これにより、テストやアプリケーションが特定のスケジューリング順序に依存している場合に、その依存性をより高い確率で露呈させ、開発者が修正できるように促します。Go 1.6以降でスケジューラがさらに変更されたとしても、このようなランダム化によって、スケジューリング順序に依存するバグが表面化しやすくなり、より堅牢な並行コードの作成に貢献することが期待されます。

## 前提知識の解説

### ゴルーチン (Goroutine)

Goにおけるゴルーチンは、軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千、数万のゴルーチンを同時に実行することが可能です。ゴルーチンはGoランタイムによって管理され、GoスケジューラがOSスレッド上でゴルーチンを多重化して実行します。

### Goスケジューラ

Goスケジューラは、ゴルーチンをOSスレッドにマッピングし、実行を管理するランタイムの一部です。M:Nスケジューリングモデルを採用しており、M個のゴルーチンをN個のOSスレッド（通常は`GOMAXPROCS`で指定された論理CPUの数）上で実行します。スケジューラは、ゴルーチンがブロックされたり、タイムスライスを使い果たしたりしたときに、別の実行可能なゴルーチンに切り替えます。この切り替えの順序は、通常は決定論的ですが、特定の条件下では非決定論的になることもあります。

### データ競合 (Data Race) と Go Race Detector

データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生する並行処理のバグです。データ競合はプログラムの動作を予測不能にし、デバッグを非常に困難にします。

Goには、データ競合を検出するための組み込みツールである「Race Detector」があります。これは、プログラムを`-race`フラグ付きでビルド・実行することで有効になります。Race Detectorは、実行時にメモリアクセスを監視し、データ競合のパターンを検出すると警告を出力します。しかし、Race Detectorは実行されたコードパスのみを監視するため、特定のスケジューリング順序でしか発生しないデータ競合は、その順序がたまたま発生しない限り検出できません。

### スケジューリングの決定論性と非決定論性

*   **決定論的スケジューリング**: 特定の入力と環境条件下で、常に同じゴルーチン実行順序を生成するスケジューリングです。テストの再現性を高める利点がありますが、特定の実行順序でしか発生しないバグ（データ競合など）を隠蔽する可能性があります。
*   **非決定論的スケジューリング**: 実行ごとにゴルーチンの実行順序が変わりうるスケジューリングです。これにより、決定論的スケジューリングでは見過ごされがちな、スケジューリング順序に依存するバグを露呈させる可能性が高まります。

このコミットは、`-race`モードにおいて意図的に非決定論的スケジューリングを導入することで、Race Detectorの検出能力を向上させようとするものです。

## 技術的詳細

このコミットは、Goランタイムのスケジューリングロジックにランダム性を導入することで、`-race`モードでのデータ競合検出能力を向上させます。主な変更点は、`src/runtime/proc1.go`内のゴルーチンをローカル実行キューに入れる関数`runqput`と、グローバル実行キューからゴルーチンをバッチで取得する際に使用される`runqputslow`にあります。

### `randomizeScheduler`定数

```go
const randomizeScheduler = raceenabled
```
`randomizeScheduler`という新しい定数が導入され、これが`raceenabled`（Goのビルド時に`-race`フラグが指定された場合に`true`となるコンパイル時定数）に設定されます。これにより、スケジューラのランダム化は`-race`モードでのみ有効になり、通常の実行パフォーマンスには影響を与えません。

### `runqput`関数におけるランダム化

`runqput`関数は、実行可能なゴルーチンを現在のP（プロセッサ、OSスレッドに相当）のローカル実行キューに入れる役割を担います。この関数には`next`というブール引数があり、これが`true`の場合、ゴルーチンはPの`runnext`スロット（次に実行される可能性が高いゴルーチンを保持する特別なスロット）に配置されます。`false`の場合、ゴルーチンはキューの末尾に追加されます。

変更後の`runqput`関数では、`randomizeScheduler`が`true`（つまり`-race`モード）で、かつ`next`が`true`の場合に、`fastrand1()%2 == 0`という条件で50%の確率で`next`を`false`に設定します。
```go
	if randomizeScheduler && next && fastrand1()%2 == 0 {
		next = false
	}
```
これは、本来`runnext`スロットに配置されてすぐに実行されるはずだったゴルーチンが、ランダムにローカルキューの末尾に回される可能性があることを意味します。これにより、ゴルーチンの実行順序に不確実性が導入されます。

### `runqputslow`関数におけるランダム化

`runqputslow`関数は、ローカル実行キューが満杯になった際に、ゴルーチンをグローバル実行キューに移動させる処理の一部として、バッチ処理を行います。また、グローバルキューからゴルーチンをローカルキューに補充する際にも関連します。

この関数内で、グローバルキューから取得したゴルーチンのバッチ（`batch`スライス）をローカルキューに入れる直前に、以下のランダム化処理が追加されました。
```go
	if randomizeScheduler {
		for i := uint32(1); i <= n; i++ {
			j := fastrand1() % (i + 1)
			batch[i], batch[j] = batch[j], batch[i]
		}
	}
```
このコードは、Fisher-Yatesシャッフルアルゴリズムに似た方法で、`batch`スライス内のゴルーチンの順序をランダムに入れ替えます。`fastrand1()`は高速な擬似乱数生成関数です。これにより、グローバルキューからローカルキューに補充されるゴルーチンの順序がランダムになり、さらにスケジューリングの非決定性が高まります。

### `sched_test.go`の追加

このコミットでは、`src/runtime/race/sched_test.go`という新しいテストファイルも追加されています。このテストは、スケジューリングのランダム性が実際に機能していることを検証するためのものです。

`TestRandomScheduling`テストは、`GOMAXPROCS=1`（スケジューラが最も決定論的になりやすい設定）で実行されるように設定されています。このテストは、N個のゴルーチンを起動し、それぞれがチャネルに自身のインデックスを送信するようにします。そして、チャネルからN個の値をN回読み取り、その順序を記録します。

もしスケジューリングが完全に決定論的であれば、N回の試行すべてで同じ順序のシーケンスが得られるはずです。しかし、ランダム化が導入されているため、異なる実行順序が少なくとも1回は発生することが期待されます。テストは、もしすべての試行で同じ順序が得られた場合、`t.Fatalf`を呼び出して失敗させます。これは、「一貫したゴルーチン実行順序」が検出されたことを意味し、ランダム化が機能していないことを示します。

## コアとなるコードの解説

### `src/runtime/proc1.go`の変更点

1.  **`randomizeScheduler`定数の導入**:
    ```go
    const randomizeScheduler = raceenabled
    ```
    この行は、スケジューラのランダム化機能が、Goプログラムが`-race`フラグ付きでビルドされた場合にのみ有効になるように制御します。`raceenabled`はコンパイル時定数であり、`-race`が指定されていれば`true`、そうでなければ`false`となります。これにより、ランダム化によるオーバーヘッドが、データ競合検出が必要な場合に限定されます。

2.  **`runqput`関数内のランダム化**:
    ```go
    	if randomizeScheduler && next && fastrand1()%2 == 0 {
    		next = false
    	}
    ```
    `runqput`関数は、実行可能なゴルーチンをPのローカル実行キューに追加します。`next`引数が`true`の場合、ゴルーチンはPの`runnext`スロットに配置され、次に実行される可能性が高まります。この変更では、`-race`モードが有効で、かつゴルーチンが`runnext`スロットに配置される予定だった場合に、50%の確率で`next`を`false`に上書きします。`fastrand1()`はGoランタイム内部で使われる高速な擬似乱数ジェネレータです。
    この結果、本来すぐに実行されるはずだったゴルーチンが、ローカルキューの末尾に回される可能性が生じ、スケジューリングの順序に意図的な非決定性が導入されます。これにより、特定のゴルーチンが常に優先的に実行されるという暗黙の仮定に依存するコードのバグが露呈しやすくなります。

3.  **`runqputslow`関数内のバッチシャッフル**:
    ```go
    	if randomizeScheduler {
    		for i := uint32(1); i <= n; i++ {
    			j := fastrand1() % (i + 1)
    			batch[i], batch[j] = batch[j], batch[i]
    		}
    	}
    ```
    `runqputslow`関数は、ローカル実行キューが満杯になった際や、グローバル実行キューからゴルーチンを補充する際に、複数のゴルーチンをバッチとして処理します。このコードブロックは、`-race`モードが有効な場合に、`batch`スライス内のゴルーチンの順序をランダムにシャッフルします。
    これはFisher-Yatesシャッフルアルゴリズムの変種であり、`batch`内のゴルーチンがランダムな順序で処理されることを保証します。これにより、グローバルキューからローカルキューへのゴルーチンの補充順序が非決定論的になり、さらにスケジューリングのランダム性が強化されます。これは、特に多数のゴルーチンが同時に実行可能になった場合に、その実行順序の多様性を高める効果があります。

この新しいテストファイルは、スケジューラのランダム化が期待通りに機能していることを検証するために追加されました。

2.  **`TestRandomScheduling`関数**:

    ```go
    }
    ```
    *   `defer runtime.GOMAXPROCS(runtime.GOMAXPROCS(1))`: この行は、テストの実行中に`GOMAXPROCS`を1に設定します。`GOMAXPROCS=1`は、Goスケジューラが最も決定論的な動作をする傾向がある設定であり、ランダム化の効果を最も明確に検出するために意図的に選択されています。
    *   テストは、N個（ここでは10個）のゴルーチンを起動し、それぞれが自身のインデックスをバッファ付きチャネル`c`に送信します。
    *   その後、チャネルからN個の値を読み取り、その順序を`row`スライスに記録します。このプロセスをN回繰り返して、`out`という二次元スライスにすべての実行順序の記録を保存します。
    *   最後に、`out[0]`（最初の実行で得られた順序）と、それ以降のすべての`out[i]`を比較します。もし、`out[0]`と異なる順序が一つでも見つかれば、それはスケジューリングにランダム性が導入されたことを意味するため、テストは成功とみなされ、`return`で終了します。
    *   もし、すべての`out[i]`が`out[0]`と完全に一致した場合（つまり、N回の試行すべてで同じ実行順序が得られた場合）、それはランダム化が機能していないことを意味します。この場合、`t.Fatalf`が呼び出され、テストは失敗します。これにより、スケジューラのランダム化が期待通りに動作していることを保証します。

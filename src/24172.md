# [インデックス 24172] ファイルの概要

このコミットは、Goランタイムの`cmd/internal/obj`パッケージにおける、プロローグ処理中のPC（プログラムカウンタ）/SP（スタックポインタ）情報の不正確さを修正するものです。具体的には、`morestack`呼び出しが関数のプロローグの最後に移動された際に、スタックトレース情報が正しく更新されず、トレースバックが混乱する問題に対処しています。

## 変更の背景

Goランタイムでは、各Goルーチンに割り当てられたスタックが不足した場合に、より大きなスタックに切り替える「スタック拡張」のメカニズムがあります。このスタック拡張は、`morestack`という関数への呼び出しによってトリガーされます。

以前の変更で、この`morestack`への呼び出しが、関数のプロローグ（関数が実行される前に実行される初期設定コード）のより「下部」に移動されました。この移動自体は、特定の最適化やコード生成の都合によるものと考えられます。

しかし、この`morestack`呼び出しの移動に伴い、Goランタイムがスタックトレースを生成するために使用するPC（プログラムカウンタ）とSP（スタックポインタ）のテーブルが適切に更新されませんでした。その結果、`morestack`呼び出しを介したトレースバック（例えば、スタックオーバーフローやパニック発生時）が必要になった場合、ランタイムはスタックの状態を正しく解釈できず、`morestack`の場所でトレースバックが停止してしまうという問題が発生しました。これはデバッグやエラー解析において重大な問題となります。

このコミットは、この不整合を解消し、`morestack`呼び出しの位置変更後もPC/SPテーブルが正確なスタックフレーム情報を提供するように修正することを目的としています。

## 前提知識の解説

### Goのスタック管理と`morestack`

Goは、可変サイズのスタックを使用します。これは、Goルーチンが最初に小さなスタックで開始し、必要に応じてスタックを拡張できることを意味します。スタックが不足しそうになると、コンパイラによって生成されたコードが`morestack`というランタイム関数を呼び出します。`morestack`は、より大きなスタックを割り当て、現在のスタックの内容を新しいスタックにコピーし、新しいスタックで実行を再開します。このプロセスは、Goの効率的な並行処理を支える重要なメカニズムの一つです。

### 関数のプロローグとエピローグ

コンパイラは、各関数に対してプロローグとエピローグという特別なコードシーケンスを生成します。
*   **プロローグ**: 関数が呼び出された直後に実行されるコードです。これには、スタックフレームのセットアップ（ローカル変数のためのスペース確保、レジスタの保存など）、スタック拡張チェック（`morestack`呼び出し）などが含まれます。
*   **エピローグ**: 関数がリターンする直前に実行されるコードです。これには、スタックフレームの解放、保存されたレジスタの復元、呼び出し元へのリターンなどが含まれます。

### PC/SPテーブルとスタックトレース

Goランタイムは、ガベージコレクション、デバッグ、パニック時のスタックトレース生成などのために、実行中のGoルーチンのスタックの状態を正確に知る必要があります。この情報を提供するために、コンパイラは各関数のPC（プログラムカウンタ）とSP（スタックポインタ）に関するメタデータテーブルを生成します。

*   **PC (Program Counter)**: 現在実行中の命令のアドレスを示します。
*   **SP (Stack Pointer)**: 現在のスタックフレームの最上位（または最下位、アーキテクチャによる）のアドレスを示します。

PC/SPテーブルは、特定のPC値（コード内の位置）において、SPがどの程度調整されたか（スタックフレームのサイズ）を記録します。これにより、ランタイムは任意のPC値からスタックを「巻き戻し」（unwind）て、呼び出しチェーンを再構築し、各スタックフレームの情報を取得できます。これは、特にガベージコレクタがスタック上のポインタをスキャンする際や、デバッガが変数の値を見る際に不可欠です。

### `obj.ANOP`と`Spadj`

Goのコンパイラバックエンド（`cmd/internal/obj`）では、アセンブリコードを生成する際に、命令を表す`obj.Prog`構造体を使用します。
*   `obj.ANOP` (No Operation): 何も実行しない命令を表します。これは、実際の機械語命令を生成しないが、コンパイラが内部的に特定の情報を記録するために使用されることがあります。
*   `Spadj` (Stack Adjustment): `obj.Prog`構造体のフィールドで、この命令が実行されたときにスタックポインタがどれだけ調整されるか（スタックフレームのサイズ変更）を示します。これは、PC/SPテーブルの生成において重要な情報となります。

## 技術的詳細

問題の核心は、`morestack`呼び出しがプロローグ内で移動されたにもかかわらず、その移動によって生じるスタックポインタの調整がPC/SPテーブルに正しく反映されていなかった点にあります。

通常、関数が呼び出されると、プロローグでスタックフレームが設定され、SPが調整されます。このSPの調整量は、PC/SPテーブルに記録され、特定のPC（命令アドレス）に対応するSPのオフセットが示されます。これにより、ランタイムはスタックトレース時に、どのPCでSPがどの値であったかを正確に判断できます。

`morestack`呼び出しがプロローグの「下部」に移動したということは、スタックフレームのセットアップが完了した後に`morestack`が呼び出される可能性があることを意味します。もし`morestack`が呼び出される前にスタックフレームが既に設定されている場合、その時点でのSPの調整量がPC/SPテーブルに正しく記録されている必要があります。しかし、この情報が欠落していたため、`morestack`が呼び出された時点でのスタックの状態がランタイムには不明瞭となり、トレースバックがそこで途切れてしまっていたのです。

このコミットは、`obj.ANOP`命令を挿入し、その`Spadj`フィールドに適切なスタック調整量（`framesize`）を設定することで、このPC/SPテーブルの不整合を解消します。`ANOP`命令は実際のコードには影響を与えませんが、コンパイラがPC/SPテーブルを生成する際に、その位置でのスタックポインタの調整を正確に記録するためのマーカーとして機能します。

具体的には、`morestack`呼び出しの直前でスタックフレームが設定されたことを示す`Spadj = -framesize`の`ANOP`を挿入し、`morestack`からのリターンパス（またはジャンプ先）の直後でスタックフレームが解放されたことを示す`Spadj = +framesize`の`ANOP`を挿入することで、`morestack`呼び出しの前後でスタックポインタがどのように変化するかをPC/SPテーブルに明示的に伝えています。

## コアとなるコードの解説

各アーキテクチャの`stacksplit`関数（スタック拡張チェックのコードを生成する部分）において、以下の変更が加えられています。

1.  **スタックフレーム確保前の`ANOP`挿入**:
    `for last = ctxt.Cursym.Text; last.Link != nil; last = last.Link {}` ループの直後、つまり関数のプロローグの初期段階で、新しい`obj.Prog` (`spfix`) が作成され、`last`（現在の命令リストの最後）にアペンドされます。
    *   `spfix.As = obj.ANOP`: この命令は実際の機械語コードを生成しません。
    *   `spfix.Spadj = -framesize`: ここが重要です。`framesize`は、この関数が使用するスタックフレームの合計サイズを示します。`-framesize`は、スタックポインタが`framesize`分だけ減少（スタックが拡張）したことを意味します。これにより、PC/SPテーブルは、この`ANOP`の位置でスタックフレームが確保されたことを正確に記録できます。
    *   続く`movw` (ARM/ARM64) や `call` (x86) 命令は、この新しく挿入された`spfix`の後にアペンドされるように変更されています (`obj.Appendp(ctxt, spfix)`).

2.  **スタックフレーム解放後の`ANOP`挿入**:
    `morestack`呼び出しからのリターンパス（またはジャンプ命令`jmp`）の直後にも、同様に`obj.ANOP`命令が挿入されます。
    *   `spfix = obj.Appendp(ctxt, b)` (ARM/ARM64) または `spfix = obj.Appendp(ctxt, jmp)` (x86): `b`や`jmp`は`morestack`へのジャンプ命令またはその後の命令です。
    *   `spfix.As = obj.ANOP`: 同様に、実際のコードは生成されません。
    *   `spfix.Spadj = +framesize`: ここでは`+framesize`が設定されています。これは、スタックポインタが`framesize`分だけ増加（スタックが解放）したことを意味します。これにより、PC/SPテーブルは、この位置でスタックフレームが解放されたことを正確に記録できます。

これらの変更により、`morestack`呼び出しの前後でスタックポインタがどのように変化するかという情報が、`obj.ANOP`命令の`Spadj`フィールドを通じてPC/SPテーブルに明示的に提供されるようになります。結果として、ランタイムは`morestack`を介したスタックトレースを正確に生成できるようになり、デバッグやエラー解析の信頼性が向上します。

x86の変更箇所にあるコメント `// Explain to PC-line tables that there is no frame here.` は、この`ANOP`がPC/SPテーブルに対して、この時点ではまだスタックフレームが完全に設定されていない（または、`morestack`呼び出しの前後で一時的にフレームがない状態になる）ことを伝える役割を果たすことを明確に示しています。

## 元コミット内容

Goコンパイラの `cmd/compile/internal/gc` パッケージから、残っていた `Nod(OXXX, ...)` の使用箇所のほとんどを削除する。パフォーマンスの改善は、完全に `func temp(*Type)` の変更によるものであり、その他のクリーンアップは予想通り効果がない。

残りの `Nod(OXXX, ...)` の使用箇所は、変更に非常に敏感であるため、後続のCL（Change List）で対応する予定である。

`benchstat` の結果は以下の通り：
- `Template`, `GoTypes`, `Compiler` の各ベンチマークにおいて、`time/op` はほぼ変化なし。
- `alloc/op` (メモリ割り当て量) は、`Template` で -0.35%、`GoTypes` で -0.38%、`Compiler` で -0.38% 削減。
- `allocs/op` (割り当て回数) は、`Template` で -0.30%、`GoTypes` で -0.31%、`Compiler` で -0.34% 削減。

## 変更の背景

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築し、それを中間表現に変換し、最終的に機械語を生成します。この過程で、ASTノードの生成と操作は頻繁に行われます。

以前のGoコンパイラでは、ASTノードを生成するために `Nod(OXXX, ...)` というヘルパー関数が広く使われていました。この関数は、新しい `Node` 構造体をヒープ上に割り当て、指定された操作タイプ（`OXXX`）や子ノードで初期化する役割を担っていました。しかし、ヒープアロケーションはガベージコレクション（GC）の負荷を増加させ、コンパイラの実行速度に影響を与える可能性があります。

このコミットの背景には、Goコンパイラのパフォーマンス最適化、特にメモリ使用量の削減とGC負荷の軽減という継続的な取り組みがあります。`Nod` 関数を直接呼び出す代わりに、既存の `Node` 構造体をコピーしたり、スタック上に新しい `Node` を作成してそのアドレスを渡したりすることで、ヒープアロケーションを回避または削減できる場合があります。これにより、コンパイラの実行がより高速になり、メモリフットプリントが小さくなることが期待されます。

コミットメッセージで「パフォーマンスの改善は、完全に `func temp(*Type)` の変更によるもの」と明記されていることから、一時変数の生成がコンパイラのメモリ割り当てにおいて重要なボトルネックの一つであったことが示唆されます。`Nod` の使用箇所を減らすことで、コンパイラのコードベースを簡素化し、より効率的なASTノード管理パターンへと移行する意図もあります。

## 前提知識の解説

### Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、複数のステージで構成されています。`cmd/compile/internal/gc` パッケージは、Goコンパイラのフロントエンドおよび中間部分を担っています。主な役割は以下の通りです。

1.  **字句解析 (Lexing)**: ソースコードをトークンに分割します。
2.  **構文解析 (Parsing)**: トークン列から抽象構文木（AST）を構築します。
3.  **型チェック (Type Checking)**: ASTの各ノードの型を解決し、型の一貫性を検証します。
4.  **中間表現への変換 (IR Generation)**: ASTを、より低レベルな中間表現（SSA: Static Single Assignment formなど）に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。

このコミットが影響するのは、主にASTの構築と操作の段階です。

### 抽象構文木 (AST: Abstract Syntax Tree)

ASTは、プログラミング言語のソースコードの抽象的な構文構造を木構造で表現したものです。各ノードは、変数宣言、関数呼び出し、演算子などのコードの構成要素を表します。コンパイラはASTを走査し、コードの意味を理解し、変換や最適化を行います。

例えば、`x = a + b` というコードは、以下のようなASTで表現されることがあります。

```
      =
     / \
    x   +
       / \
      a   b
```

### `Node` 構造体

GoコンパイラにおけるASTの各ノードは、`Node` という構造体で表現されます。この構造体は、ノードの操作タイプ（`Op`）、型情報（`Type`）、子ノード（`Left`, `Right`, `List`, `Rlist`）、シンボル情報（`Sym`）、ソースコード上の位置（`Lineno`）など、様々なフィールドを持ちます。

```go
// 簡略化されたNode構造体のイメージ
type Node struct {
    Op      Op      // ノードの操作タイプ (例: OADD, OCALL, OLITERAL)
    Type    *Type   // ノードの型
    Left    *Node   // 左の子ノード
    Right   *Node   // 右の子ノード
    List    Nodes   // 子ノードのリスト
    Rlist   Nodes   // 別の種類の子ノードのリスト
    Sym     *Sym    // シンボル情報 (変数名、関数名など)
    Lineno  int32   // ソースコード上の行番号
    Orig    *Node   // 元のノードへのポインタ (最適化などでノードが変換された場合)
    // ... その他多くのフィールド
}
```

### `Nod(OXXX, ...)` 関数

`Nod` 関数は、Goコンパイラで新しい `Node` を作成するためのヘルパー関数でした。`OXXX` は `Node` の `Op` フィールドに設定される操作タイプ（例: `OADD` は加算、`OLITERAL` はリテラル値）を表します。

```go
// 以前のNod関数の呼び出しイメージ
// 新しいNodeをヒープに割り当て、初期化する
newNode := Nod(OADD, leftNode, rightNode)
```

この関数は、内部で `new(Node)` を呼び出してヒープアロケーションを行い、新しい `Node` 構造体へのポインタを返していました。このコミットでは、このような明示的なヒープアロケーションを減らすために、`Nod` の使用を避ける変更が行われています。

### `func temp(*Type)` 関数

`temp` 関数は、コンパイラが一時変数を必要とするときに、その一時変数を表す `Node` を生成するために使用されます。例えば、複雑な式の中間結果を保持するためなどに一時変数が導入されます。

```go
// 以前のtemp関数の呼び出しイメージ
// 型tの一時変数を表すNodeを生成
tmpVarNode := temp(someType)
```

この関数も以前は `Nod(OXXX, ...)` を内部で呼び出していましたが、このコミットでその実装が変更され、ヒープアロケーションを削減するように最適化されました。コミットメッセージがこの関数の変更がパフォーマンス改善の主要因であると述べているのは、コンパイル中に非常に多くの（数百万単位の）一時変数が生成されるため、その生成コストが全体に大きく影響するためです。

### `benchstat` ツール

`benchstat` は、Goのベンチマーク結果を比較し、統計的に有意な差があるかどうかを判断するためのツールです。`go test -bench .` コマンドで生成されたベンチマーク結果ファイル（例: `/tmp/old.txt`, `/tmp/new.txt`）を引数として与えることで、実行時間 (`time/op`)、メモリ割り当て量 (`alloc/op`)、メモリ割り当て回数 (`allocs/op`) などのメトリクスについて、変更前後の統計的な比較結果を出力します。

-   `delta`: 変更による差分。`~` は統計的に有意な差がないことを示し、`+X%` や `-X%` は有意な増加または減少を示します。
-   `p`: p値。統計的仮説検定において、帰無仮説（差がない）が正しい場合に、観測されたデータまたはそれよりも極端なデータが得られる確率。一般的に `p < 0.05` であれば、統計的に有意な差があると判断されます。
-   `n`: 測定回数。

このコミットの `benchstat` 結果では、`time/op` には有意な差が見られませんが、`alloc/op` と `allocs/op` には有意な減少（約 -0.3% から -0.4%）が見られます。これは、メモリ割り当ての効率が改善されたことを明確に示しています。

## 技術的詳細

このコミットの主要な技術的変更は、Goコンパイラ内でASTノードを生成する際のヒープアロケーションを削減することにあります。具体的には、`Nod(OXXX, nil, nil)` のような明示的なヒープアロケーションを伴う関数呼び出しを、スタックアロケーションや既存の構造体のコピーを利用するパターンに置き換えています。

### `Nod(OXXX, ...)` からの移行パターン

変更の核心は、新しい `Node` を作成する際に、`Nod` 関数を呼び出す代わりに、以下のいずれかのパターンを使用することです。

1.  **既存の `Node` 構造体の値コピーとポインタの再割り当て**:
    ```go
    // 変更前:
    // nn := Nod(OXXX, nil, nil)
    // *nn = *n
    // n = nn

    // 変更後:
    nn := *n // nが指すNode構造体の内容をnnに値コピー（スタック上に作成）
    n = &nn  // nを新しく作成したnnのアドレスに再割り当て
    ```
    このパターンでは、元の `n` が指していた `Node` の内容を新しい `Node` `nn` にコピーします。`nn` は通常、スタック上に割り当てられるため、ヒープアロケーションが回避されます。その後、`n` はこの新しい `nn` のアドレスを指すように更新されます。

2.  **`var Node` 宣言とポインタ渡し**:
    ```go
    // 変更前:
    // n := Nod(OXXX, nil, nil)
    // Tempname(n, t)

    // 変更後:
    var n Node // スタック上にNode構造体を宣言
    Tempname(&n, t) // そのアドレスを関数に渡す
    ```
    このパターンは、特に `func temp(*Type)` の変更で見られます。`Node` 構造体を直接スタック上に宣言し、そのアドレスを `Tempname` のようなヘルパー関数に渡すことで、ヒープアロケーションなしで `Node` を初期化・利用します。

### `Node.Orig` フィールドの更新

多くの箇所で、`Node` 構造体の `Orig` フィールドの更新方法も変更されています。

```go
// 変更前:
// nl := Nod(OXXX, nil, nil)
// *nl = *s[i1]
// nl.Orig = nl // nl自身を指す

// 変更後:
nl := *s[i1] // 値コピー
nl.Orig = &nl // 新しくコピーしたnlのアドレスを指す
```
`Orig` フィールドは、最適化や変換によってノードが変更された場合に、元のノードへの参照を保持するために使用されます。以前は `Nod` で作成されたヒープ上のノード自身を指していましたが、値コピーを行った場合は、コピーされた新しい構造体のアドレスを指すように変更する必要があります。これにより、ノードの履歴が正しく追跡されます。

### `func temp(*Type)` の最適化

`func temp(*Type)` は、一時変数を表す `Node` を生成する関数です。この関数はコンパイル中に頻繁に呼び出されるため、ここでのアロケーション削減は全体的なパフォーマンスに大きな影響を与えます。

```go
// 変更前 (src/cmd/compile/internal/gc/gen.go):
// func temp(t *Type) *Node {
// 	n := Nod(OXXX, nil, nil)
// 	Tempname(n, t)
// 	n.Sym.Def.Used = true
// 	return n.Orig
// }

// 変更後 (src/cmd/compile/internal/gc/gen.go):
func temp(t *Type) *Node {
	var n Node // Node構造体をスタック上に直接宣言
	Tempname(&n, t) // nのアドレスを渡して初期化
	n.Sym.Def.Used = true
	return n.Orig
}
```
この変更により、`temp` 関数内で `Nod` を呼び出すことによるヒープアロケーションが完全に排除され、代わりにスタックアロケーションが利用されるようになりました。これにより、一時変数の生成コストが大幅に削減され、`benchstat` の結果に示されるメモリ割り当て量と回数の減少に直接貢献しています。

### パフォーマンスへの影響

`benchstat` の結果が示すように、この変更は実行時間（`time/op`）には大きな影響を与えませんでしたが、メモリ割り当て量（`alloc/op`）と割り当て回数（`allocs/op`）を約0.3%〜0.4%削減しました。これは、コンパイラが実行中に生成するオブジェクトの総数を減らし、ガベージコレクタが処理する必要のあるメモリ量を削減したことを意味します。このような小さな改善の積み重ねが、大規模なプロジェクトのコンパイル時間やリソース使用量に長期的に良い影響を与えます。

## コアとなるコードの解説

### `Node` の値コピーとポインタの再割り当て

多くの変更箇所、例えば `const.go` の `convlit1` や `defaultlit` 関数、`dcl.go` の `funcargs` 関数、`export.go` の `importconst` 関数、`inl.go` の `inlcopy` 関数、`order.go` の `ordercheapexpr` や `ordersafeexpr` 関数、`racewalk.go` の `instrument` 関数、`subr.go` の `treecopy` や `substArgTypes` 関数では、以下のパターンが適用されています。

**変更前:**
```go
nn := Nod(OXXX, nil, nil) // ヒープに新しいNodeを割り当て、ポインタnnを得る
*nn = *n                  // nが指すNodeの内容を、新しく割り当てたNodeにコピー
n = nn                    // nを新しいNodeのポインタに更新
```
このコードは、`Nod` 関数によってヒープアロケーションを発生させます。

**変更後:**
```go
nn := *n // nが指すNodeの内容を、スタック上に新しいNode構造体として値コピー
n = &nn  // nを、スタック上の新しいNode構造体のアドレスに更新
```
この変更により、`Nod` 関数によるヒープアロケーションが不要になります。`nn` はスタック上に作成されるため、関数スコープを抜けると自動的に解放され、ガベージコレクションの対象になりません。これにより、メモリ割り当ての回数と量が削減されます。

また、`Node.Orig` フィールドの更新も重要です。
**変更前:** `nl.Orig = nl`
**変更後:** `nl.Orig = &nl`
これは、`nl` がヒープ上のポインタからスタック上の値に変わったため、`Orig` フィールドもその新しいアドレスを指すように修正する必要があるためです。これにより、ノードの変換履歴が正しく保持されます。

### `func temp(*Type)` の変更

`src/cmd/compile/internal/gc/gen.go` にある `func temp(*Type)` の変更は、このコミットにおけるパフォーマンス改善の主要因です。

**変更前:**
```go
func temp(t *Type) *Node {
	n := Nod(OXXX, nil, nil) // ここでヒープアロケーションが発生
	Tempname(n, t)
	n.Sym.Def.Used = true
	return n.Orig

## 前提知識の解説

### Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、複数のステージで構成されています。`cmd/compile/internal/gc` パッケージは、Goコンパイラのフロントエンドおよび中間部分を担っています。主な役割は以下の通りです。

1.  **字句解析 (Lexing)**: ソースコードをトークンに分割します。
2.  **構文解析 (Parsing)**: トークン列から抽象構文木（AST）を構築します。
3.  **型チェック (Type Checking)**: ASTの各ノードの型を解決し、型の一貫性を検証します。
4.  **中間表現への変換 (IR Generation)**: ASTを、より低レベルな中間表現（SSA: Static Single Assignment formなど）に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。

このコミットが影響するのは、主にASTの構築と操作の段階です。

### 抽象構文木 (AST: Abstract Syntax Tree)

ASTは、プログラミング言語のソースコードの抽象的な構文構造を木構造で表現したものです。各ノードは、変数宣言、関数呼び出し、演算子などのコードの構成要素を表します。コンパイラはASTを走査し、コードの意味を理解し、変換や最適化を行います。

例えば、`x = a + b` というコードは、以下のようなASTで表現されることがあります。

```
      =
     / \
    x   +
       / \
      a   b
```

### `Node` 構造体

GoコンパイラにおけるASTの各ノードは、`Node` という構造体で表現されます。この構造体は、ノードの操作タイプ（`Op`）、型情報（`Type`）、子ノード（`Left`, `Right`, `List`, `Rlist`）、シンボル情報（`Sym`）、ソースコード上の位置（`Lineno`）など、様々なフィールドを持ちます。

```go
// 簡略化されたNode構造体のイメージ
type Node struct {
    Op      Op      // ノードの操作タイプ (例: OADD, OCALL, OLITERAL)
    Type    *Type   // ノードの型
    Left    *Node   // 左の子ノード
    Right   *Node   // 右の子ノード
    List    Nodes   // 子ノードのリスト
    Rlist   Nodes   // 別の種類の子ノードのリスト
    Sym     *Sym    // シンボル情報 (変数名、関数名など)
    Lineno  int32   // ソースコード上の行番号
    Orig    *Node   // 元のノードへのポインタ (最適化などでノードが変換された場合)
    // ... その他多くのフィールド
}
```

### `Node` の値コピーとポインタの再割り当て

多くの変更箇所、例えば `const.go` の `convlit1` や `defaultlit` 関数、`dcl.go` の `funcargs` 関数、`export.go` の `importconst` 関数、`inl.go` の `inlcopy` 関数、`order.go` の `ordercheapexpr` や `ordersafeexpr` 関数、`racewalk.go` の `instrument` 関数、`subr.go` の `treecopy` や `substArgTypes` 関数では、以下のパターンが適用されています。

**変更前:**
```go
nn := Nod(OXXX, nil, nil) // ヒープに新しいNodeを割り当て、ポインタnnを得る
*nn = *n                  // nが指すNodeの内容を、新しく割り当てたNodeにコピー
n = nn                    // nを新しいNodeのポインタに更新
```
このコードは、`Nod` 関数によってヒープアロケーションを発生させます。

**変更後:**
```go
nn := *n // nが指すNodeの内容を、スタック上に新しいNode構造体として値コピー
n = &nn  // nを、スタック上の新しいNode構造体のアドレスに更新
```
この変更により、`Nod` 関数によるヒープアロケーションが不要になります。`nn` はスタック上に作成されるため、関数スコープを抜けると自動的に解放され、ガベージコレクションの対象になりません。これにより、メモリ割り当ての回数と量が削減されます。

また、`Node.Orig` フィールドの更新も重要です。
**変更前:** `nl.Orig = nl`
**変更後:** `nl.Orig = &nl`
これは、`nl` がヒープ上のポインタからスタック上の値に変わったため、`Orig` フィールドもその新しいアドレスを指すように修正する必要があるためです。これにより、ノードの変換履歴が正しく保持されます。

### `func temp(*Type)` の変更

`src/cmd/compile/internal/gc/gen.go` にある `func temp(*Type)` の変更は、このコミットにおけるパフォーマンス改善の主要因です。

**変更前:**
```go
func temp(t *Type) *Node {
	n := Nod(OXXX, nil, nil) // ここでヒープアロケーションが発生
	Tempname(n, t)
	n.Sym.Def.Used = true
	return n.Orig
}
```
`temp` 関数は、コンパイル中に一時変数を表す `Node` を頻繁に生成します。以前の実装では、`Nod` を呼び出すたびにヒープアロケーションが発生していました。

**変更後:**
```go
func temp(t *Type) *Node {
	var n Node // Node構造体をスタック上に直接宣言
	Tempname(&n, t) // nのアドレスを渡して初期化
	n.Sym.Def.Used = true
	return n.Orig
}
```
この変更により、`n` はスタック上に直接割り当てられるため、ヒープアロケーションが完全に回避されます。`Tempname` 関数は `*Node` を引数に取るため、`&n` としてアドレスを渡すことで、スタック上の `Node` を初期化できます。これにより、一時変数の生成に伴うメモリ割り当てのオーバーヘッドが大幅に削減され、コンパイラの全体的なメモリ効率が向上します。

これらの変更は、Goコンパイラがより効率的にメモリを使用し、ガベージコレクションの負担を軽減するための重要なステップです。

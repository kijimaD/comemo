# [インデックス 20403] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャのソフトウェア浮動小数点演算処理中に発生するnilポインタのロード/ストア操作を安全にハンドリングするための修正です。特に、Cコードやアセンブリコードがスタック上に存在し、レジスタの状態が不明な状況で直接パニックを発生させることによる問題を回避します。

## 元コミット内容

このコミットは、GoランタイムがARMアーキテクチャ上でソフトウェア浮動小数点演算を実行する際に、nilポインタのロード（読み込み）またはストア（書き込み）が発生した場合の挙動を修正するものです。

従来のGoランタイムでは、nilポインタのデリファレンス（参照外し）は通常、SIGSEGV（セグメンテーション違反）シグナルをトリガーし、Goのパニックメカニズムによって処理されます。しかし、ARMのソフトウェア浮動小数点コードの特定のコンテキスト（特にCコードとアセンブリコードが混在するスタックフレーム）では、この通常のパニック処理が問題を引き起こす可能性がありました。

具体的には、ソフトウェア浮動小数点コードが実行されている最中にnilポインタデリファレンスが発生すると、スタック上にはGoのランタイムコードだけでなく、C言語で書かれた部分やアセンブリ言語で書かれた部分のスタックフレームが混在しています。この状況で通常のパニック処理を開始しようとすると、レジスタの状態（特にどのレジスタがポインタを保持しているか）が不明瞭であるため、Goのガベージコレクタがポインタを正しく識別できず、クラッシュや不正なメモリアクセスを引き起こす可能性がありました。

このコミットは、このような危険な状況を回避するため、nilポインタのロード/ストアを明示的に検出し、Cコードやアセンブリコードのコンテキストから安全に抜け出し、`sigpanic`（Goのパニック処理を開始する関数）を呼び出すための特別なスタブ（`_sfloatpanic`）に制御を移すように変更しています。これにより、Goのパニック処理が安全な環境で開始され、プログラムの安定性が向上します。

また、この修正は`GOARM=5`ビルドの問題を解決すると明記されており、特定のARMv5アーキテクチャ向けのビルド環境で発生していた問題を解消するものです。

## 変更の背景

Go言語は、クロスプラットフォーム対応を重視しており、ARMアーキテクチャもその対象です。ARMプロセッサには、ハードウェア浮動小数点ユニット（FPU）を搭載していない、あるいは搭載していても特定の命令セット（例: ARMv5）ではGoランタイムがハードウェアFPUを直接利用できない場合があります。このような環境では、浮動小数点演算をソフトウェアでエミュレートする必要があります。これが「ソフトウェア浮動小数点」です。

Goランタイムのソフトウェア浮動小数点処理は、パフォーマンスを最適化するためにC言語とアセンブリ言語で記述されています。これらの低レベル言語で書かれたコードは、Goの通常のランタイムとは異なるスタックフレーム構造やレジスタ使用規則を持つことがあります。

問題は、Goプログラムがnilポインタをデリファレンスしようとしたときに発生します。Goでは、nilポインタデリファレンスはランタイムパニックを引き起こす設計になっています。これは通常、オペレーティングシステムがSIGSEGVシグナルをプロセスに送信することで検出されます。Goランタイムはこのシグナルを捕捉し、パニック処理を開始します。

しかし、ARMのソフトウェア浮動小数点コードの実行中にSIGSEGVが発生した場合、以下のような特有の問題がありました。

1.  **スタックの複雑性**: ソフトウェア浮動小数点コードの実行中は、Goの関数呼び出し規約とは異なるC言語やアセンブリ言語のスタックフレームが混在しています。Goのパニック処理は、スタックをウォークしてGoのスタックフレームを解析し、レジスタに保存されているポインタを特定する必要があります。この混在したスタック構造では、正確なスタックウォークが困難になります。
2.  **レジスタの状態の不明瞭さ**: アセンブリコードのフレームには、多くのレジスタが保存されていますが、Goランタイムがどのレジスタが有効なポインタを保持しているかを正確に判断することは非常に困難です。誤った判断は、ガベージコレクタが不正なメモリをスキャンしたり、有効なポインタを見逃したりする原因となり、結果としてクラッシュやメモリ破損につながります。
3.  **安全なパニック開始の必要性**: 上記の理由から、ソフトウェア浮動小数点コードの実行中に直接パニック処理を開始することは危険でした。Goランタイムは、パニック処理を開始する前に、安全なGoのコンテキストに制御を戻す必要がありました。

このコミットは、これらの問題を解決し、ARMソフトウェア浮動小数点環境でのnilポインタデリファレンスを安全かつ予測可能な方法で処理するためのメカニズムを導入しています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するGo言語の不可欠な部分です。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、スタック管理、プリミティブな同期メカニズム、そしてパニック処理などが含まれます。Goプログラムは、コンパイル時にGoランタイムとリンクされ、ランタイムの機能を利用して実行されます。

### ARMアーキテクチャ

ARM (Advanced RISC Machine) は、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのプロセッサアーキテクチャです。GoはARMプロセッサをサポートしており、様々なARMベースのデバイスでGoプログラムを実行できます。ARMプロセッサには、ハードウェア浮動小数点ユニット（FPU）の有無や、サポートする命令セット（例: ARMv5, ARMv7, ARMv8）によって多くのバリエーションがあります。

### ソフトウェア浮動小数点 (Software Floating Point)

一部のARMプロセッサや古いARMアーキテクチャ（例: ARMv5）では、ハードウェアFPUが搭載されていないか、GoランタイムがハードウェアFPUを直接利用できない場合があります。このような場合、浮動小数点演算（加算、減算、乗算、除算など）は、プロセッサの整数演算命令とソフトウェアロジックを組み合わせてエミュレートされます。これをソフトウェア浮動小数点と呼びます。ソフトウェア浮動小数点演算は、ハードウェアFPUを使用する場合に比べて一般的に低速ですが、FPUを持たないシステムでも浮動小数点演算を可能にします。

### nilポインタデリファレンス (Nil Pointer Dereferencing)

Goにおいて、`nil`はポインタのゼロ値であり、何も指していないことを意味します。`nil`ポインタをデリファレンスしようとすると（つまり、`nil`ポインタが指すメモリ位置にアクセスしようとすると）、ランタイムエラーが発生します。これは通常、オペレーティングシステムによってSIGSEGV（セグメンテーション違反）シグナルとして検出され、Goランタイムがこれを捕捉してパニックを引き起こします。

### Goのパニックとリカバリ (Panic and Recover)

Goには、プログラムの異常終了を処理するための`panic`と`recover`という組み込み関数があります。
-   `panic`: プログラムの実行を停止し、現在のゴルーチンのスタックをアンワインド（巻き戻し）します。この過程で、`defer`関数が実行されます。
-   `recover`: `panic`によって引き起こされたパニックを捕捉し、パニックからの回復を試みます。`recover`は`defer`関数内でしか有効ではありません。

Goランタイムは、nilポインタデリファレンスのような特定のランタイムエラーを検出すると、内部的にパニックを発生させます。

### シグナルハンドリング (Signal Handling)

オペレーティングシステムは、プログラムの実行中に発生する特定のイベント（例: メモリアクセス違反、割り込み）をシグナルとしてプロセスに通知します。SIGSEGV（Segmentation Violation）は、プログラムがアクセス権のないメモリ領域にアクセスしようとしたり、存在しないメモリ領域にアクセスしようとしたりした場合に発生するシグナルです。Goランタイムは、これらのシグナルを捕捉し、Goのパニックメカニズムに変換するシグナルハンドラを持っています。

### アセンブリコードとCコードの相互作用

Goランタイムの低レベル部分は、パフォーマンスや特定のハードウェア機能へのアクセスを目的として、C言語やアセンブリ言語で書かれています。これらのコードは、Go言語で書かれたコードとは異なる関数呼び出し規約やスタックフレーム構造を持つことがあります。Goランタイムは、GoコードとC/アセンブリコードの間で安全に制御をやり取りするためのメカニズム（例: `runtime·onM`）を提供しています。

## 技術的詳細

このコミットの技術的詳細を理解するためには、GoランタイムがARMのソフトウェア浮動小数点命令をどのようにエミュレートしているか、そしてnilポインタデリファレンスをどのように検出して処理しているかを掘り下げる必要があります。

### ソフトウェア浮動小数点エミュレーション (`stepflt`関数)

`src/pkg/runtime/softfloat_arm.c`ファイルには、ARMの浮動小数点命令をソフトウェアでエミュレートするためのCコードが含まれています。このコードの中心となるのが`stepflt`関数です。

`stepflt`関数は、ARMの浮動小数点命令を解析し、その命令がメモリのロード（読み込み）またはストア（書き込み）操作であるかどうかを判断します。もしロード/ストア命令であれば、その命令がアクセスしようとしているメモリアドレスを計算します。

このコミットでは、`stepflt`関数内のロード/ストア処理にnilポインタデリファレンス検出ロジックが追加されました。

```c
#define FAULT (0x80000000U) // impossible PC offset
// ...
stage1: // load/store regn is cpureg, regm is 8bit offset

    case 0xed900a00:    // single load
        addr = (uint32*)(regs[regn] + regm);
        if((uintptr)addr < 4096) { // ここでnilポインタデリファレンスを検出
            if(trace)
                runtime·printf("*** load @%p => fault\n", addr);
            return FAULT; // FAULTを返す
        }
        m->freglo[regd] = addr[0];
// ... (同様のチェックが他のロード/ストアケースにも追加)
```

ここで重要なのは、`if((uintptr)addr < 4096)`というチェックです。これは、Goランタイムがnilポインタデリファレンスを検出するための一般的なヒューリスティックです。多くのオペレーティングシステムでは、アドレス空間の最下位ページ（通常は0から4095バイト）はマップされておらず、アクセスするとSIGSEGVが発生します。したがって、計算されたアドレスがこの「ゼロページ」内にある場合、それはnilポインタデリファレンスであると見なされます。

もしnilポインタデリファレンスが検出された場合、`stepflt`関数は特別な値`FAULT`（`0x80000000U`）を返します。この値は、通常の命令の長さ（ワード数）としてはありえないオフセットであり、呼び出し元に「フォルトが発生した」ことを通知する役割を果たします。

### `sfloat2`関数とパニック処理の連携

`stepflt`関数を呼び出すのは`sfloat2`関数です。`sfloat2`は、ソフトウェア浮動小数点命令の実行ループを管理します。

```c
static void
sfloat2(void)
{
    uint32 *pc;
    Sfregs *regs;
    int32 skip;
    bool first;
    
    pc = g->m->ptrarg[0];
    regs = g->m->ptrarg[1];
    g->m->ptrarg[0] = nil;
    g->m->ptrarg[1] = nil;

    first = true;
    while(skip = stepflt(pc, (uint32*)&regs->r0)) { // stepfltの戻り値をチェック
        first = false;
        if(skip == FAULT) { // FAULTが返された場合
            // Encountered bad address in store/load.
            // Record signal information and return to assembly
            // trampoline that fakes the call.
            enum { SIGSEGV = 11 };
            curg = g->m->curg;
            curg->sig = SIGSEGV; // SIGSEGVシグナル情報を記録
            curg->sigcode0 = 0;
            curg->sigcode1 = 0;
            curg->sigpc = (uint32)pc; // フォルト発生時のPCを記録
            pc = (uint32*)_sfloatpanic; // _sfloatpanicへのジャンプを準備
            break; // ループを抜ける
        }
        pc += skip; // 通常の命令実行
    }
    if(first) {
        runtime·printf("sfloat2 %p %x\n", pc, *pc);
        fabort(); // not ok to fail first instruction
    }
        
    g->m->ptrarg[0] = pc; // 最終的なPCを保存
}
```

`sfloat2`関数は、`stepflt`が`FAULT`を返した場合、通常の命令処理を中断します。そして、現在のゴルーチン（`curg`）のシグナル情報（`sig`, `sigcode0`, `sigcode1`, `sigpc`）を、あたかもSIGSEGVシグナルがOSから送られてきたかのように設定します。

最も重要な変更は、`pc = (uint32*)_sfloatpanic;`という行です。これは、`sfloat2`関数が終了し、呼び出し元（`runtime·_sfloat2`）に戻った際に、通常の命令の次のアドレスに進むのではなく、特別に用意されたアセンブリ関数`_sfloatpanic`にジャンプするように制御フローを変更します。

### `_sfloatpanic`アセンブリトランポリン

`src/pkg/runtime/vlop_arm.s`ファイルには、新しく追加されたアセンブリ関数`_sfloatpanic`があります。これは「トランポリン」として機能します。

```assembly
// trampoline for _sfloat2 panic.
// _sfloat2 instructs _sfloat to return here.
// We need to push a fake saved LR onto the stack,
// load the signal fault address into LR, and jump
// to the real sigpanic.
// This simulates what sighandler does for a memory fault.
TEXT _sfloatpanic(SB),NOSPLIT,$-4
    MOVW    $0, R0
    MOVW.W  R0, -4(R13) // フェイクのLRをスタックにプッシュ
    MOVW    g_sigpc(g), LR // sigpcをLRにロード
    B   runtime·sigpanic(SB) // sigpanicへジャンプ
```

`_sfloatpanic`の役割は以下の通りです。

1.  **フェイクのLRプッシュ**: `MOVW.W R0, -4(R13)`は、スタックにダミーの値（0）をプッシュします。これは、通常の関数呼び出しでリターンアドレス（LR: Link Register）がスタックに保存されるのを模倣しています。これにより、`sigpanic`がスタックをウォークする際に、期待されるスタックフレーム構造を維持します。
2.  **`sigpc`をLRにロード**: `MOVW g_sigpc(g), LR`は、`sfloat2`で設定されたフォルト発生時のプログラムカウンタ（`sigpc`）をLRレジスタにロードします。これは、`sigpanic`がパニックの原因となった命令のアドレスを正確に特定できるようにするためです。
3.  **`sigpanic`へのジャンプ**: `B runtime·sigpanic(SB)`は、Goランタイムの実際のパニック処理を開始する`sigpanic`関数に無条件ジャンプします。

この一連のメカニズムにより、ソフトウェア浮動小数点コード内でnilポインタデリファレンスが発生した場合でも、OSからのSIGSEGVシグナルを待つことなく、Goランタイムが自律的にそれを検出し、安全な方法で`sigpanic`を呼び出すことができます。これにより、Cコードやアセンブリコードが混在する複雑なスタックコンテキストでのパニック処理の不安定性が回避されます。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の2つのファイルにあります。

1.  `src/pkg/runtime/softfloat_arm.c`:
    *   `FAULT`マクロの追加: `0x80000000U`という特殊な値を定義し、nilポインタデリファレンスを示すために使用します。
    *   `stepflt`関数内のロード/ストア命令処理にnilポインタチェック（`if((uintptr)addr < 4096)`）を追加。このチェックが真の場合、`FAULT`を返します。
    *   `sfloat2`関数内で`stepflt`の戻り値が`FAULT`であるかをチェックし、その場合は現在のゴルーチンのシグナル情報を設定し、`_sfloatpanic`へのジャンプを準備します。
    *   `runtime·_sfloat2`関数と`sfloat2`関数の引数名が`lr`から`pc`に変更されていますが、これは意味的な変更であり、機能的な変更ではありません。

2.  `src/pkg/runtime/vlop_arm.s`:
    *   `_sfloatpanic`という新しいアセンブリ関数が追加されました。この関数は、`sfloat2`から制御を受け取り、フェイクのスタックフレームを構築し、`sigpanic`関数にジャンプします。

## コアとなるコードの解説

### `src/pkg/runtime/softfloat_arm.c`の変更点

#### `FAULT`マクロの追加

```c
#define FAULT (0x80000000U) // impossible PC offset
```
このマクロは、`stepflt`関数が命令の長さを返す代わりに、nilポインタデリファレンスが発生したことを示すために使用される特殊な値です。`0x80000000U`は、通常のARM命令の長さとしてはありえない大きな値であり、エラー状態を明確に区別できます。

#### `stepflt`関数内のnilポインタチェック

```c
// 例: single loadの場合
case 0xed900a00:    // single load
    addr = (uint32*)(regs[regn] + regm);
    if((uintptr)addr < 4096) { // アドレスがゼロページ内にあるかチェック
        if(trace)
            runtime·printf("*** load @%p => fault\\n", addr);
        return FAULT; // FAULTを返してエラーを通知
    }
    m->freglo[regd] = addr[0];
```
このコードは、ARMの浮動小数点ロード/ストア命令がアクセスしようとしているメモリアドレス`addr`を計算した後、そのアドレスが`4096`（通常、OSがマップしないゼロページの上限）未満であるかどうかをチェックします。もしアドレスがこの範囲内であれば、それはnilポインタデリファレンスであると判断し、`FAULT`を返します。これにより、OSのシグナルハンドラを介さずに、Goランタイムが早期にnilポインタデリファレンスを検出できます。

#### `sfloat2`関数内の`FAULT`ハンドリング

```c
while(skip = stepflt(pc, (uint32*)&regs->r0)) {
    first = false;
    if(skip == FAULT) { // stepfltがFAULTを返した場合
        // シグナル情報を設定
        enum { SIGSEGV = 11 };
        curg = g->m->curg;
        curg->sig = SIGSEGV;
        curg->sigcode0 = 0;
        curg->sigcode1 = 0;
        curg->sigpc = (uint32)pc; // フォルト発生時のPCを記録
        pc = (uint32*)_sfloatpanic; // _sfloatpanicへのジャンプを指示
        break; // ループを終了
    }
    pc += skip; // 通常の命令実行
}
```
`sfloat2`関数は、`stepflt`の戻り値を継続的にチェックします。もし`stepflt`が`FAULT`を返した場合、`sfloat2`は通常の命令処理を停止し、現在のゴルーチン（`curg`）のシグナル関連フィールドを、あたかもSIGSEGVシグナルが受信されたかのように設定します。そして、最も重要なのは、`pc`（プログラムカウンタ）を`_sfloatpanic`関数のアドレスに設定することです。これにより、`sfloat2`が終了して呼び出し元に戻った際に、`_sfloatpanic`が実行されるようになります。

### `src/pkg/runtime/vlop_arm.s`の変更点

#### `_sfloatpanic`アセンブリ関数の追加

```assembly
TEXT _sfloatpanic(SB),NOSPLIT,$-4
    MOVW    $0, R0
    MOVW.W  R0, -4(R13) // スタックにダミーのリターンアドレスをプッシュ
    MOVW    g_sigpc(g), LR // g->sigpcの値をLRレジスタにロード
    B   runtime·sigpanic(SB) // runtime·sigpanicへジャンプ
```
このアセンブリコードは、`sfloat2`から制御が移されたときに実行される「トランポリン」です。
1.  `MOVW $0, R0` と `MOVW.W R0, -4(R13)`: これは、スタックにダミーの値をプッシュすることで、`sigpanic`が期待するスタックフレームの構造を模倣します。特に、リターンアドレス（LR）がスタックに保存されているかのように見せかけます。これは、`sigpanic`がスタックをウォークしてパニックの原因を特定する際に、正しいコンテキストを認識できるようにするために重要です。
2.  `MOVW g_sigpc(g), LR`: `g`は現在のゴルーチン構造体へのポインタです。`g_sigpc(g)`は、`sfloat2`で設定された、nilポインタデリファレンスが発生した命令のアドレス（プログラムカウンタ）を指します。このアドレスをLR（Link Register）にロードすることで、`sigpanic`はパニックの原因となった正確な命令位置を特定できます。
3.  `B runtime·sigpanic(SB)`: 最後に、無条件分岐命令`B`を使って、Goランタイムの実際のパニック処理を開始する`runtime·sigpanic`関数にジャンプします。

この`_sfloatpanic`トランポリンは、ソフトウェア浮動小数点コードの複雑なコンテキストから、Goの通常のパニック処理フローへと安全に移行させるための重要な橋渡し役を果たします。これにより、レジスタの状態が不明瞭なC/アセンブリコードのスタックフレーム上で直接パニック処理を開始する危険性を回避し、Goのパニック処理が安定した環境で実行されることを保証します。

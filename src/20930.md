# [インデックス 20930] ファイルの概要

このコミットは、Goコンパイラツールチェーンの一部である`9a`アセンブラにおける、4引数を持つ命令の生成に関するバグ修正です。具体的には、`src/cmd/9a/lex.c`ファイル内の`outgcode`関数における引数の解釈ミスを修正しています。

## 元コミット内容

このコミットは、`9a`アセンブラが4つの引数を持つ命令を生成する際に、引数の順序が誤っていた問題を修正します。具体的には、`outgcode`関数において、`to`フィールドと`from3`フィールドに割り当てる引数が入れ替わっていました。これは、`a.y`（アセンブラの文法定義ファイル）での引数順序は正しかったものの、`outgcode`関数内での引数の解釈が異なっていたためです。この問題は、これまで手書きのアセンブリコードでこれらの「より曖昧な」操作が使用されていなかったため、顕在化していませんでした。

## 変更の背景

Goコンパイラツールチェーンは、Go言語のソースコードを最終的に実行可能なバイナリに変換する一連のツールです。このプロセスには、Goコードを中間表現に変換し、その後、ターゲットアーキテクチャのネイティブアセンブリコードに変換するステップが含まれます。`9a`は、Plan 9アセンブラのGoポートであり、Goのツールチェーンにおいて、特定のアーキテクチャ（この場合はPowerPC 64-bit、`dev.power64`ブランチで作業されていたため）向けのアセンブリコードを生成する役割を担っていました。

このコミットの背景には、Goコンパイラが生成するアセンブリコード、または手書きのアセンブリコードが、特定の命令セット（この場合は4引数命令）を正しく利用できていなかったという問題があります。アセンブラが命令の引数を誤って解釈すると、生成される機械語コードが意図したものと異なり、プログラムの誤動作やクラッシュにつながる可能性があります。

コミットメッセージにある「This hadn't come up because we hadn't used these more obscure operations in any hand-written assembly until now.」という記述は、このバグが、これまでGoの標準ライブラリやランタイムで広く使われていなかった、特定の複雑なアセンブリ命令の使用が始まったことで初めて発見されたことを示唆しています。これは、新しいアーキテクチャサポート（PowerPC 64-bit）や、特定の最適化のために、より低レベルなアセンブリコードが導入された結果であると考えられます。

## 前提知識の解説

*   **Goコンパイラツールチェーン**: Go言語のソースコードをコンパイルし、実行可能なバイナリを生成するための一連のツール群です。これには、コンパイラ（`go tool compile`）、アセンブラ（`go tool asm`、以前は`8a`, `6a`, `5a`, `9a`などアーキテクチャごとに分かれていた）、リンカ（`go tool link`）などが含まれます。
*   **`9a`**: Goの初期のツールチェーンにおける、PowerPC 64-bitアーキテクチャ向けのアセンブラです。Goのツールチェーンは、Plan 9オペレーティングシステムのアセンブラ設計思想を継承しており、各アーキテクチャ向けのアセンブラは数字と`a`の組み合わせで命名されていました（例: `8a`はx86、`6a`はamd64、`5a`はARM）。現在では、`go tool asm`として統合されていますが、内部的にはこれらのアセンブラのロジックが使われています。
*   **アセンブラ**: アセンブリ言語で書かれたプログラムを機械語（CPUが直接実行できる形式）に変換するプログラムです。アセンブリ言語は、CPUの命令セットに1対1で対応する低レベルなプログラミング言語であり、レジスタ、メモリ、命令のオペランド（引数）などを直接操作します。
*   **オペランド (Operand)**: アセンブリ命令が操作する対象となるデータやアドレスのことです。命令によっては、1つ、2つ、3つ、あるいはそれ以上のオペランドを取ることがあります。例えば、`ADD R1, R2, R3`という命令では、R1, R2, R3がオペランドであり、R2とR3の内容を足し算してR1に格納する、といった意味になります。
*   **`lex.c`**: 通常、コンパイラやアセンブラのフロントエンドにおける字句解析（lexical analysis）を担当する部分のソースファイル名として使われます。字句解析は、ソースコードをトークン（意味のある最小単位）のストリームに分解するプロセスです。しかし、この文脈では、アセンブリ命令の内部表現を生成するロジックが含まれているようです。
*   **`a.y`**: `yacc` (Yet Another Compiler Compiler) または`bison`などのパーサジェネレータで使われる文法定義ファイルです。アセンブラの場合、アセンブリ言語の構文規則が定義されており、パーサがアセンブリコードを解析して、命令とそのオペランドを識別するために使用されます。
*   **`outgcode`関数**: この関数は、アセンブリ命令の内部表現を構築し、それをリンカが処理できる形式で出力する役割を担っていると推測されます。`g1`, `g2`, `g3`といった引数は、アセンブリ命令のオペランド（ソース、デスティネーション、追加のオペランドなど）に対応するアドレス構造体であると考えられます。

## 技術的詳細

このバグは、`outgcode`関数がアセンブリ命令のオペランドを内部データ構造にマッピングする際の論理的な誤りに起因していました。

アセンブリ命令は、通常、複数のオペランドを持ちます。例えば、`ADD dest, src1, src2` のように、デスティネーションと2つのソースオペランドを持つ命令があります。Goのアセンブラでは、これらのオペランドは`Prog`構造体（アセンブリ命令の内部表現）のフィールドに格納されます。このコミットで問題となったのは、4つの引数を持つ命令（例えば、`ADD R1, R2, R3, R4`のような、より複雑な命令）を処理する際の`Prog`構造体へのマッピングでした。

コミットメッセージによると、`outgcode`関数は以下のような引数を受け取っていました（簡略化された表現）：
`outgcode(..., Addr *g1, int reg, Addr *g2, Addr *g3)`

そして、バグのあるコードでは、これらの引数を`Prog`構造体のフィールドに以下のように割り当てていました：
```c
p->from = *g1;
p->reg = reg;
p->to = *g2;   // ここが問題
p->from3 = *g3; // ここが問題
```

ここで、`p->to`は命令のデスティネーションオペランドを、`p->from3`は3番目のソースオペランド（または4番目のオペランド）を意味すると考えられます。

問題は、`a.y`（アセンブラの文法定義）では、引数の順序が`g2`が`from3`に、`g3`が`to`に対応するように意図されていたにもかかわらず、`outgcode`関数内ではその逆になっていたことです。つまり、`g2`と`g3`の役割が入れ替わっていたのです。

この結果、4引数命令を生成しようとすると、3番目のオペランドと4番目のオペランドが入れ替わってしまい、誤った機械語コードが生成されていました。このバグがこれまで発見されなかったのは、Goのコンパイラやランタイムが、これらの特定の4引数命令を、手書きのアセンブリコードで積極的に使用していなかったためです。新しい最適化や特定のアーキテクチャ（PowerPC 64-bit）のサポートが進むにつれて、これらの「より曖昧な」命令が使われるようになり、バグが顕在化したと考えられます。

修正は非常にシンプルで、`outgcode`関数内で`g2`と`g3`の割り当てを入れ替えることで、`a.y`で定義された正しい引数順序と一致させました。

    *   `p->from3 = *g3;`: `outgcode`関数の第5引数`g3`が、`Prog`構造体の`from3`フィールド（3番目のソースオペランド）に割り当てられていました。

*   **変更後**:
    *   `p->from3 = *g2;`: `outgcode`関数の第4引数`g2`が、`Prog`構造体の`from3`フィールドに割り当てられるようになりました。

## コアとなるコードの解説

変更されたのは以下の2行です。

```c
-	p->to = *g2;
-	p->from3 = *g3;
+	p->from3 = *g2;
+	p->to = *g3;
```

*   **変更前**:
    *   `p->to = *g2;`: `outgcode`関数の第4引数`g2`が、`Prog`構造体の`to`フィールド（デスティネーションオペランド）に割り当てられていました。
    *   `p->from3 = *g3;`: `outgcode`関数の第5引数`g3`が、`Prog`構造体の`from3`フィールド（3番目のソースオペランド）に割り当てられていました。

*   **変更後**:
    *   `p->from3 = *g2;`: `outgcode`関数の第4引数`g2`が、`Prog`構造体の`from3`フィールドに割り当てられるようになりました。
    *   `p->to = *g3;`: `outgcode`関数の第5引数`g3`が、`Prog`構造体の`to`フィールドに割り当てられるようになりました。

この変更により、`outgcode`関数が受け取る`g2`と`g3`の引数が、`Prog`構造体の`from3`と`to`フィールドにそれぞれ正しくマッピングされるようになり、4引数命令のオペランド順序の誤りが修正されました。

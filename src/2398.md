# [インデックス 2398] ファイルの概要

このコミットは、Go言語のビルドシステムにおけるMakefileとスクリプトの構造を再編成し、アーキテクチャ固有のツールプレフィックス（例: `6g`, `8g`）のロジックを共通化し、ハードコードされたパスを排除することを目的としています。これにより、ビルドシステムの柔軟性と保守性が向上し、特にクロスコンパイルのシナリオにおいて、よりクリーンで拡張性の高いアプローチが実現されています。

## 変更の背景

Go言語の初期のビルドシステムは、特定のアーキテクチャ（例: `amd64`, `386`, `arm`）に対応するコンパイラ (`6g`, `8g`, `5g`) やリンカ (`6l`, `8l`, `5l`) のツール名をスクリプトやMakefile内で直接指定（ハードコード）していました。これは、新しいアーキテクチャの追加やツール名の変更があった場合に、多くのファイルを修正する必要があるという保守性の問題を引き起こしていました。

このコミットの背景には、以下の課題意識があったと考えられます。

1.  **ハードコードされたツール名の問題**: `6g`や`6l`といったツール名が直接スクリプトに埋め込まれていると、アーキテクチャが変更されたり、将来的にツール名が変更されたりした場合に、広範囲にわたる修正が必要となる。
2.  **アーキテクチャ固有のロジックの分散**: 各スクリプトやMakefileが、`GOARCH`環境変数に基づいて`O`（オブジェクトファイル接尾辞やツールプレフィックス）を決定するロジックをそれぞれ持っているため、重複が多く、一貫性のない実装になりがちである。
3.  **クロスコンパイルの複雑さ**: 異なるアーキテクチャ向けにビルドを行う際、ツール名の切り替えが手動または複雑なスクリプトロジックに依存していると、ビルドプロセスが煩雑になる。

これらの問題を解決し、ビルドシステムをよりモジュール化され、柔軟で、将来の変更に強いものにするために、共通のロジックを外部ファイルに切り出す必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Go言語のビルドツールチェーン**:
    *   **`g`系ツール**: Go言語の初期のコンパイラ、アセンブラ、リンカは、ターゲットアーキテクチャを示す数字とツールの種類を示す文字の組み合わせで命名されていました。
        *   `6g`: `amd64` (64-bit Intel/AMD) 用のGoコンパイラ
        *   `8g`: `386` (32-bit Intel/AMD) 用のGoコンパイラ
        *   `5g`: `arm` 用のGoコンパイラ
        *   同様に、`6l`, `8l`, `5l` はリンカ、`6a`, `8a`, `5a` はアセンブラを指します。
    *   これらのツールは、Goのソースコードをコンパイルし、実行可能ファイルを生成するために使用されます。
2.  **`GOARCH`環境変数**: Goのビルドシステムで使用される環境変数で、ターゲットとするCPUアーキテクチャ（例: `amd64`, `386`, `arm`）を指定します。
3.  **`GOROOT`環境変数**: Goのインストールディレクトリのルートパスを指定する環境変数です。Goのツールや標準ライブラリのソースコードが配置されています。
4.  **Makefile**: ビルドプロセスを自動化するためのファイルです。依存関係とコマンドを定義し、ソースコードのコンパイル、リンク、テストなどのタスクを実行します。
5.  **シェルスクリプト (`.bash`や実行可能スクリプト)**: コマンドのシーケンスを自動化するために使用されるスクリプトです。このコミットでは、ビルドやテストの補助スクリプトが対象となっています。
6.  **`source`コマンド (または`.`コマンド)**: シェルスクリプト内で別のスクリプトファイルを読み込み、そのスクリプト内の変数を現在のシェル環境にインポートするために使用されます。これにより、共通の設定や関数を複数のスクリプトで共有できます。
7.  **`O`変数**: このコミットでは、`O`はオブジェクトファイルの接尾辞（例: `.6`、`.8`、`.5`）や、ツール名のプレフィックス（例: `6`、`8`、`5`）として使われる共通の識別子を指します。

## 技術的詳細

このコミットの核心は、Goビルドシステムにおけるアーキテクチャ固有のツール名とオブジェクトファイル接尾辞の管理方法を中央集権化し、抽象化することにあります。

以前は、各スクリプトやMakefileが`GOARCH`環境変数に基づいて、以下のようなロジックでツール名や接尾辞を決定していました。

```bash
case "$GOARCH" in
amd64)  O=6;;
arm)    O=5;;
386)    O=8;;
*)      echo 'unknown $GOARCH' 1>&2
        exit 1
esac
GC=${GC:-${O}g}
GL=${GL:-${O}l}
```

このコミットでは、このロジックを`src/Make.$GOARCH`という形式の新しいファイル群に集約します。

*   `src/Make.386`:
    ```makefile
    O=8
    AS=${O}a
    CC=${O}c
    GC=${O}g
    LD=${O}l
    ```
*   `src/Make.amd64`:
    ```makefile
    O=6
    AS=${O}a
    CC=${O}c
    GC=${O}g
    LD=${O}l
    ```
*   `src/Make.arm`:
    ```makefile
    O=5
    AS=${O}a
    CC=${O}c
    GC=${O}g
    LD=${O}l
    ```

これにより、各スクリプトやMakefileは、`GOARCH`の値に応じて適切な`Make.$GOARCH`ファイルを`source`コマンド（または`include`ディレクティブ）で読み込むだけで、`O`, `AS`, `CC`, `GC`, `LD`といった変数を自動的に設定できるようになります。

例えば、`doc/progs/run`スクリプトでは、以前は`rm -f *.6`のようにハードコードされていた部分が`rm -f *.$O`となり、`6g $i`が`$GC $i`に、`6l $1.6`が`$LD $1.$O`に置き換えられています。これにより、スクリプト自体は特定のアーキテクチャに依存せず、`GOARCH`環境変数によって動的にツールが選択されるようになります。

また、`src/cmd/ld/go.c`におけるエラーメッセージの出力も改善されています。以前は`fprintf(2, "6l: ...")`のようにリンカ名がハードコードされていましたが、`fprintf(2, "%s: ...", argv0)`と変更され、実行中のプログラム名（`argv0`）が動的に使用されるようになりました。これは、エラーメッセージの汎用性を高め、どのツールがエラーを出力したかをより正確に伝えるための変更です。

この変更は、Goのビルドシステムがより洗練され、将来の拡張性に対応できる基盤を築く上で重要なステップでした。

## コアとなるコードの解説

このコミットの最も重要な変更は、ビルドツールのプレフィックスとオブジェクトファイル拡張子を、アーキテクチャごとに独立したファイル（`src/Make.386`, `src/Make.amd64`, `src/Make.arm`）に定義したことです。

例えば、`src/Make.amd64`の内容を見てみましょう。

```makefile
# Copyright 2009 The Go Authors. All rights reserved.
# Use of this source code is governed by a BSD-style
# license that can be found in the LICENSE file.

O=6
AS=${O}a
CC=${O}c
GC=${O}g
LD=${O}l
```

ここで、
*   `O=6`: `amd64`アーキテクチャの場合、オブジェクトファイルの接尾辞やツール名のプレフィックスとして`6`を使用することを定義しています。
*   `AS=${O}a`: アセンブラは`6a`となることを定義しています。
*   `CC=${O}c`: Cコンパイラは`6c`となることを定義しています。
*   `GC=${O}g`: Goコンパイラは`6g`となることを定義しています。
*   `LD=${O}l`: リンカは`6l`となることを定義しています。

これらの定義ファイルは、各ビルドスクリプトやMakefileで`source`コマンド（シェルスクリプトの場合）や`include`ディレクティブ（Makefileの場合）を使って読み込まれます。

例: `doc/progs/run`スクリプトの変更点

変更前:
```bash
rm -f *.6
6g $i
6l $1.6
```

変更後:
```bash
. $GOROOT/src/Make.$GOARCH # ここでMake.amd64などが読み込まれる
if [ -z "$O" ]; then
    echo 'missing $O - maybe no Make.$GOARCH?' 1>&2
    exit 1
fi
rm -f *.$O # $Oが6であれば、*.6が削除される
$GC $i     # $GCが6gであれば、6g $iが実行される
$LD $1.$O  # $LDが6l、$Oが6であれば、6l $1.6が実行される
```

この変更により、スクリプト自体は`6g`や`6l`といった具体的なツール名を知る必要がなくなり、`$GC`や`$LD`といった抽象化された変数を通じてツールを呼び出すことができます。これにより、ビルドシステムは特定のアーキテクチャに縛られず、`GOARCH`環境変数を変更するだけで、異なるアーキテクチャ向けのビルドツールを透過的に使用できるようになります。これは、Goのクロスコンパイル能力を支える重要な基盤の一つです。

また、`src/cmd/ld/go.c`におけるエラーメッセージの変更も注目に値します。

変更前:
```c
fprintf(2, "6l: too much pkg data in %s\\n", filename);
```

変更後:
```c
fprintf(2, "%s: too much pkg data in %s\\n", argv0, filename);
```

`argv0`はC言語のプログラムにおいて、実行されたプログラム自身の名前を格納する変数です。この変更により、エラーメッセージは`6l: ...`ではなく、例えば`ld: ...`のように、実際に実行されているリンカの名前を動的に表示するようになります。これは、ユーザーがどのツールからのエラーメッセージであるかをより明確に理解するのに役立ちます。

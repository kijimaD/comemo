## 変更の背景

このコミットは、`net/http/fcgi` パッケージ内の `TestChildServeCleansUp` というテストが、複数回連続して実行された場合にデッドロックを起こす問題を修正するために行われました。

問題の根本原因は、テスト内で使用される入力データが、テスト実行中に変更（mutate）されてしまうことにありました。Goのテストフレームワークでは、テスト関数が複数回実行されることがあります（例えば、`go test` コマンドを複数回実行したり、特定のテストを繰り返し実行する設定にしたりする場合）。理想的には、各テスト実行は独立しており、以前の実行が次の実行に影響を与えないべきです。

しかし、このテストでは、`bytes.NewBuffer(tt.input)` のように、テストケースの入力データ `tt.input` を直接 `bytes.Buffer` に渡していました。`bytes.Buffer` は内部的にスライスを参照し、そのスライスに対して書き込み操作を行うと、元のスライスの内容が変更される可能性があります。この場合、`nopWriteCloser` が `bytes.Buffer` をラップしており、その `Write` メソッドが `bytes.Buffer` に書き込むことで、元の `tt.input` が変更されてしまっていたと考えられます。

その結果、1回目のテスト実行では問題なくパスしますが、`tt.input` が変更された状態で2回目のテストが開始されると、期待される入力データが提供されず、テストロジックが不正な状態に陥り、最終的に「`fatal error: all goroutines are asleep - deadlock!`」というデッドロックエラーが発生していました。これは、テストが冪等性（何度実行しても同じ結果になる性質）を持たないという、テストとしては非常に望ましくない状態でした。

このコミットは、このデータ破壊を防ぎ、テストが複数回実行されても常に正しい結果を返すようにするために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Go言語のテスト**:
    *   Go言語には標準でテストフレームワークが組み込まれており、`go test` コマンドで実行します。
    *   テストファイルは通常、テスト対象のファイルと同じディレクトリに `_test.go` サフィックスを付けて配置されます。
    *   テスト関数は `Test` で始まり、`*testing.T` 型の引数を取ります（例: `func TestMyFunction(t *testing.T)`）。
    *   テストは並行して実行されることがあり、また、同じテスト関数が複数回実行されることもあります。そのため、テストは互いに独立しており、副作用がないように設計されるべきです。

2.  **`net/http/fcgi` パッケージ**:
    *   このパッケージは、Goの `net/http` パッケージとFastCGIプロトコルを統合するためのものです。
    *   FastCGIは、Webサーバー（Nginx, Apacheなど）とアプリケーション（Goプログラムなど）が通信するためのプロトコルです。WebサーバーはFastCGIリクエストをアプリケーションに渡し、アプリケーションはFastCGIレスポンスを返します。
    *   `fcgi` パッケージは、Goの `http.Handler` をFastCGIアプリケーションとして動作させるための機能を提供します。

3.  **`bytes.Buffer`**:
    *   `bytes.Buffer` は、可変長のバイトシーケンスを扱うためのバッファです。
    *   `bytes.NewBuffer(buf []byte)` は、既存のバイトスライス `buf` を初期データとして新しい `Buffer` を作成します。**重要な点として、このコンストラクタは `buf` のコピーを作成せず、`buf` を直接参照します。** したがって、`Buffer` への書き込み操作が、元の `buf` スライスの内容を変更する可能性があります。

4.  **`io.Writer` インターフェース**:
    *   Goの標準ライブラリ `io` パッケージで定義されているインターフェースで、`Write([]byte) (n int, err error)` メソッドを持つ型がこのインターフェースを満たします。
    *   データを受け取り、どこかに出力する（ファイル、ネットワーク、メモリバッファなど）ための抽象化を提供します。
    *   このコミットでは、`nopWriteCloser` というカスタム型が `io.Writer` インターフェース（および `io.Closer`）を満たしており、内部で `bytes.Buffer` を使用してデータを処理しています。

5.  **スライスと配列のコピー**:
    *   Goのスライスは、基になる配列への参照です。スライスを別の変数に代入しても、同じ基になる配列を指します。
    *   スライスの内容を完全に独立した新しいスライスにコピーするには、`copy(dst, src)` 関数を使用するか、`make` で新しいスライスを作成してからループで要素をコピーする必要があります。

## 技術的詳細

この問題の核心は、Goにおけるスライスの参照渡しと、`bytes.NewBuffer` の動作にあります。

`TestChildServeCleansUp` テスト関数は、`cleanUpTests` というテストケースのスライスをイテレートします。各テストケース `tt` には `input` というバイトスライスが含まれています。

元のコードでは、以下の行がありました。

```go
rc := nopWriteCloser{bytes.NewBuffer(tt.input)}
```

ここで `tt.input` は `[]byte` 型です。`bytes.NewBuffer(tt.input)` は、`tt.input` が指す基になる配列を直接参照する `bytes.Buffer` を作成します。

`nopWriteCloser` は `io.Writer` インターフェースを実装しており、その `Write` メソッドは内部の `bytes.Buffer` にデータを書き込みます。この書き込み操作は、`bytes.Buffer` が参照している `tt.input` の基になる配列の内容を直接変更してしまいます。

例えば、`tt.input` が `[]byte{'a', 'b', 'c'}` であったとします。1回目のテスト実行で `nopWriteCloser` がこのバッファに何かを書き込むと、`tt.input` が指すメモリ領域の内容が変更され、例えば `[]byte{'x', 'y', 'z'}` のようになる可能性があります。

テストが完了し、2回目のループで同じ `tt`（つまり同じ `tt.input`）が使用されると、`tt.input` はすでに変更された状態になっています。これにより、テストの前提条件が崩れ、予期せぬ動作（この場合はデッドロック）が発生しました。

この問題を解決するために、コミットでは `tt.input` の**ディープコピー**を作成するというアプローチが取られました。

```go
input := make([]byte, len(tt.input))
copy(input, tt.input)
rc := nopWriteCloser{bytes.NewBuffer(input)}
```

この変更により、以下のようになります。
1.  `make([]byte, len(tt.input))` で、元の `tt.input` と同じ長さの新しいバイトスライス `input` がメモリ上に確保されます。
2.  `copy(input, tt.input)` で、`tt.input` の内容が新しく作成された `input` スライスにバイトごとにコピーされます。これにより、`input` は `tt.input` とは完全に独立したデータのコピーとなります。
3.  `bytes.NewBuffer(input)` は、この新しくコピーされた `input` スライスを参照する `bytes.Buffer` を作成します。

この修正により、`nopWriteCloser` が `bytes.Buffer` に書き込みを行っても、それは `input` スライスの内容を変更するだけであり、元の `tt.input` スライスには一切影響を与えません。したがって、テストが何回実行されても、各実行は常に `cleanUpTests` で定義されたオリジナルの `tt.input` のクリーンなコピーを受け取ることが保証され、テストの冪等性が保たれます。

これは、テストの信頼性を確保し、テストが環境や実行順序に依存しないようにするための基本的なプラクティスを示しています。特に、共有される可能性のある入力データや状態を扱う際には、意図しない副作用を防ぐためにデータのコピーを検討することが重要です。

例えば、`tt.input` が `[]byte{'a', 'b', 'c'}` であったとします。1回目のテスト実行で `nopWriteCloser` がこのバッファに何かを書き込むと、`tt.input` が指すメモリ領域の内容が変更され、例えば `[]byte{'x', 'y', 'z'}` のようになる可能性があります。

テストが完了し、2回目のループで同じ `tt`（つまり同じ `tt.input`）が使用されると、`tt.input` はすでに変更された状態になっています。これにより、テストの前提条件が崩れ、予期せぬ動作（この場合はデッドロック）が発生しました。

この問題を解決するために、コミットでは `tt.input` の**ディープコピー**を作成するというアプローチが取られました。

```go
input := make([]byte, len(tt.input))
copy(input, tt.input)
rc := nopWriteCloser{bytes.NewBuffer(input)}
```

この変更により、以下のようになります。
1.  `make([]byte, len(tt.input))` で、元の `tt.input` と同じ長さの新しいバイトスライス `input` がメモリ上に確保されます。
2.  `copy(input, tt.input)` で、`tt.input` の内容が新しく作成された `input` スライスにバイトごとにコピーされます。これにより、`input` は `tt.input` とは完全に独立したデータのコピーとなります。
3.  `bytes.NewBuffer(input)` は、この新しくコピーされた `input` スライスを参照する `bytes.Buffer` を作成します。

この修正により、`nopWriteCloser` が `bytes.Buffer` に書き込みを行っても、それは `input` スライスの内容を変更するだけであり、元の `tt.input` スライスには一切影響を与えません。したがって、テストが何回実行されても、各実行は常に `cleanUpTests` で定義されたオリジナルの `tt.input` のクリーンなコピーを受け取ることが保証され、テストの冪等性が保たれます。

これは、テストの信頼性を確保し、テストが環境や実行順序に依存しないようにするための基本的なプラクティスを示しています。特に、共有される可能性のある入力データや状態を扱う際には、意図しない副作用を防ぐためにデータのコピーを検討することが重要です。

## コアとなるコードの解説

変更は `src/net/http/fcgi/fcgi_test.go` ファイルの `TestChildServeCleansUp` 関数内で行われています。

**変更前:**

```go
rc := nopWriteCloser{bytes.NewBuffer(tt.input)}
```

この行では、テストケース `tt` の `input` フィールド（バイトスライス）を直接 `bytes.NewBuffer` に渡していました。前述の通り、`bytes.NewBuffer` は渡されたスライスの基になる配列への参照を持つため、`nopWriteCloser` を通じた `bytes.Buffer` への書き込みが、元の `tt.input` の内容を破壊していました。

**変更後:**

```go
input := make([]byte, len(tt.input))
copy(input, tt.input)
rc := nopWriteCloser{bytes.NewBuffer(input)}
```

この3行が修正の核心です。

1.  `input := make([]byte, len(tt.input))`
    *   `len(tt.input)` は元の `tt.input` スライスの長さを取得します。
    *   `make([]byte, length)` は、指定された長さの新しいバイトスライスをメモリ上に割り当て、そのスライスを `input` 変数に代入します。この時点では、`input` スライスはゼロ値（バイトスライスの場合、各要素は `0`）で初期化されています。

2.  `copy(input, tt.input)`
    *   Goの組み込み関数 `copy` を使用して、`tt.input` スライスの内容を、新しく作成された `input` スライスにコピーします。
    *   これにより、`input` は `tt.input` とは完全に独立した、同じ内容を持つ新しいバイトスライスとなります。

3.  `rc := nopWriteCloser{bytes.NewBuffer(input)}`
    *   `bytes.NewBuffer` に、元の `tt.input` ではなく、そのコピーである `input` スライスを渡します。
    *   これにより、`nopWriteCloser` が内部の `bytes.Buffer` に書き込みを行っても、それは `input` スライスの内容のみを変更し、元のテストケースデータ `tt.input` には影響を与えなくなります。

この修正により、`TestChildServeCleansUp` テストは冪等性を獲得し、複数回実行されても安定して動作するようになりました。これは、テストの信頼性と再現性を確保する上で非常に重要な変更です。

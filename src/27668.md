## 元コミット内容

このコミットは、Goランタイムのロックフリースタック（`lfstack`）を操作する`lfstackPack`と`lfstackUnpack`関数の実装を、単一のファイルに統合することを目的としています。以前は、これらの関数は32ビット、64ビット、およびAMD64アーキテクチャ向けに個別のファイル（`lfstack_32bit.go`, `lfstack_64bit.go`, `lfstack_amd64.go`）に分かれて実装されていました。

コミットメッセージの要点は以下の通りです。

*   `lfstackPack`と`lfstackUnpack`の残りの実装を1つのファイルにマージする。
*   `unsafe.Sizeof(uintptr(0)) == 4`という定数比較はコンパイル時に解決されるため、不要な分岐はコンパイル時に削除される。
*   Dmitry氏の確認により、ユーザーモードポインタの上位17ビットはゼロになるため、AMD64でのアンパック時に符号拡張（sign extend）の必要がないことが判明。これにより、AMD64も他の64ビットアーキテクチャと同じ実装を再利用できる。

## 変更の背景

Goランタイムの内部では、ガベージコレクションやスケジューラなどの低レベルな処理で、ロックフリーデータ構造が頻繁に利用されます。ロックフリースタックはその一つであり、複数のゴルーチンが同時にアクセスしても競合状態に陥らないように設計されています。

`lfstackPack`と`lfstackUnpack`関数は、このロックフリースタックのノード（`lfnode`）のポインタとカウンタを、単一の`uint64`値にパック（結合）したり、その逆のアンパック（分離）したりするために使用されます。これは、Compare-And-Swap (CAS) 操作などのアトミック操作で、ポインタとカウンタを同時に更新する必要がある場合に特に重要です。ポインタとカウンタを1つの値にまとめることで、CAS操作を一度で実行でき、ABA問題の発生を抑制しつつ、効率的なロックフリー操作を実現します。

以前は、異なるCPUアーキテクチャ（32ビット、64ビット、特にAMD64）のメモリレイアウトやポインタの特性の違いに対応するため、これらの関数が個別のファイルに実装されていました。しかし、これはコードの重複と保守の複雑さにつながります。このコミットの背景には、これらのアーキテクチャ固有の差異をよりスマートに吸収し、コードベースを簡素化したいという意図があります。特に、AMD64におけるユーザーモードポインタの特性に関する新たな知見が、この統合を可能にする重要な要素となりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **ロックフリーデータ構造 (Lock-Free Data Structures)**:
    複数のスレッド（Goにおいてはゴルーチン）が同時にアクセスしても、ミューテックスなどのロック機構を使用せずに、正しい操作を保証するデータ構造です。これにより、ロックの競合によるパフォーマンス低下やデッドロックのリスクを回避できます。ロックフリーデータ構造の実装には、通常、アトミック操作（CAS: Compare-And-Swapなど）が用いられます。

2.  **Compare-And-Swap (CAS) 操作**:
    メモリ上の特定のアドレスにある値が期待する値と一致する場合にのみ、その値を新しい値にアトミックに更新する操作です。この操作は不可分であり、他のスレッドからの干渉を受けません。ロックフリーアルゴリズムの基盤となります。

3.  **ABA問題 (ABA Problem)**:
    ロックフリーアルゴリズムで発生しうる問題の一つです。CAS操作において、あるメモリ位置の値がAからBに変化し、その後再びAに戻った場合、CAS操作は値が変更されていないと誤認してしまう可能性があります。これを防ぐために、ポインタと一緒にカウンタ（またはタグ）を格納し、値が変更されるたびにカウンタをインクリメントする手法がよく用いられます。これにより、値がAに戻ってもカウンタが異なるため、CAS操作は失敗し、ABA問題を回避できます。

4.  **`unsafe.Pointer` と `uintptr`**:
    *   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムを迂回して、メモリを直接操作するために使用されます。ガベージコレクタは`unsafe.Pointer`が指すメモリを追跡しません。
    *   `uintptr`: ポインタの値を整数として表現する型です。`unsafe.Pointer`と相互変換が可能ですが、`uintptr`はポインタではないため、ガベージコレクタは`uintptr`が指すメモリを追跡しません。これらの型は、低レベルなシステムプログラミングや、Goの型システムでは表現できない操作（例: ポインタ演算、メモリレイアウトの操作）を行う際に利用されます。

5.  **ポインタパッキング (Pointer Packing)**:
    複数の情報を1つのワード（例: `uint64`）に詰め込む技術です。このコミットの場合、ロックフリースタックのノードへのポインタと、ABA問題対策のためのカウンタを1つの`uint64`値にパックしています。これにより、CAS操作を1回で実行できるようになります。ポインタは通常、メモリのアライメント制約により下位ビットが常にゼロになるため、その空いたビット空間をカウンタに利用できます。また、仮想アドレス空間の制約により、上位ビットが常にゼロになることも利用されます。

6.  **アーキテクチャ固有のメモリレイアウト**:
    CPUアーキテクチャによって、仮想アドレス空間のサイズやポインタの表現方法が異なります。例えば、32ビットシステムではポインタは32ビット、64ビットシステムではポインタは64ビットです。しかし、64ビットシステムであっても、実際に使用される仮想アドレス空間は64ビット全てではなく、例えば48ビットや40ビットに制限されていることがあります。残りの上位ビットは、通常、符号拡張（sign extension）のために使用されたり、単にゼロであったりします。このコミットでは、AMD64のユーザーモードポインタが上位17ビットでゼロになるという特性が利用されています。

## 技術的詳細

このコミットの核心は、`lfstackPack`と`lfstackUnpack`関数を単一の`lfstack.go`ファイルに統合し、アーキテクチャ間の差異をコンパイル時定数と特定のアーキテクチャ特性の利用によって吸収することです。

1.  **コンパイル時分岐による32ビット/64ビット対応**:
    `unsafe.Sizeof(uintptr(0)) == 4`という条件式が導入されています。`uintptr(0)`はゼロ値の`uintptr`型であり、そのサイズは実行環境のポインタサイズに依存します。
    *   32ビットシステムでは`unsafe.Sizeof(uintptr(0))`は4バイト（32ビット）になります。
    *   64ビットシステムでは`unsafe.Sizeof(uintptr(0))`は8バイト（64ビット）になります。
    この比較はコンパイル時に定数として評価されるため、コンパイラは不要な分岐を最適化によって削除（dead code elimination）し、結果として各アーキテクチャに最適化されたコードが生成されます。これにより、実行時のオーバーヘッドなしに、単一のソースファイルで複数のアーキテクチャに対応できます。

2.  **ポインタとカウンタのパッキング/アンパッキングロジック**:
    *   **32ビットシステム (`unsafe.Sizeof(uintptr(0)) == 4` の場合)**:
        *   `lfstackPack`: `uintptr(unsafe.Pointer(node))`を32ビット左シフトし、`uint64(cnt)`とOR演算で結合します。これにより、上位32ビットにポインタ、下位32ビットにカウンタが格納されます。
        *   `lfstackUnpack`: `val >> 32`で上位32ビットを取り出し、それを`uintptr`にキャストして`lfnode`ポインタに戻します。
        これは、32ビットシステムではポインタが32ビット幅であるため、`uint64`の半分をポインタに、残りの半分をカウンタに割り当てることが可能だからです。

    *   **64ビットシステム (それ以外の場合)**:
        *   `addrBits`と`cntBits`という定数が定義されています。
            *   `addrBits = 48`: 仮想アドレス空間が48ビットであることを想定しています。これは、多くの64ビットシステム（PPC64, MIPS64, AMD64など）で実際に使用されるユーザーモードアドレス空間のサイズを反映しています。
            *   `cntBits = 64 - addrBits + 3`: カウンタに割り当てるビット数です。`64 - 48 = 16`ビットがアドレスの上位から利用可能で、さらにポインタのアライメント（通常8バイトアライメント、つまり下位3ビットが常にゼロ）を利用して下位3ビットもカウンタに利用できるため、合計`16 + 3 = 19`ビットがカウンタに割り当てられます。
        *   `lfstackPack`: `uintptr(unsafe.Pointer(node))`を`(64 - addrBits)`ビット左シフトし、`uint64(cnt&(1<<cntBits-1))`とOR演算で結合します。
            *   `uintptr(unsafe.Pointer(node)))<<(64-addrBits)`: ポインタを左シフトして、カウンタ用のビット空間を確保します。例えば`addrBits=48`の場合、`64-48=16`ビット左シフトされ、ポインタは上位48ビットに配置されます。
            *   `uint64(cnt&(1<<cntBits-1))`: カウンタ値を`cntBits`でマスクし、カウンタ用のビット空間に収まるようにします。
        *   `lfstackUnpack`: `val >> cntBits << 3`でポインタ部分を取り出します。
            *   `val >> cntBits`: パックされた値からカウンタ部分を右シフトで取り除きます。
            *   `<< 3`: ポインタが8バイトアライメントされていることを利用し、アンパック時に失われた下位3ビットを復元します。これにより、正しいポインタ値が得られます。

3.  **AMD64の特殊な扱いと統合**:
    コミットメッセージで特に言及されているのがAMD64アーキテクチャです。AMD64では、仮想アドレスは通常48ビットですが、64ビットレジスタにロードされる際に符号拡張（sign extension）されます。つまり、48ビット目の最上位ビットが64ビット目までコピーされます。
    以前の`lfstack_amd64.go`では、この符号拡張された部分を考慮して、ポインタを16ビット左シフトして符号拡張部分を排除し、下位ビットをカウンタに利用していました。
    しかし、Dmitry氏の確認により、「ユーザーモードポインタの上位17ビットはゼロになる」という事実が判明しました。これは、ユーザー空間のアドレスが特定の範囲に限定されており、その範囲では符号拡張が実質的に不要であることを意味します。この知見により、AMD64は他の64ビットアーキテクチャ（PPC64, MIPS64など）と同じ`addrBits=48`の汎用64ビット実装をそのまま利用できるようになり、個別の実装が不要になりました。これにより、`lfstack_amd64.go`ファイルが削除され、コードの重複がさらに削減されました。

## コアとなるコードの変更箇所

`src/runtime/lfstack.go`に以下のコードが追加され、既存のアーキテクチャ固有ファイルが削除されました。

```go
// src/runtime/lfstack.go に追加されたコード
const (
	addrBits = 48
	cntBits  = 64 - addrBits + 3
)

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	if unsafe.Sizeof(uintptr(0)) == 4 {
		// On 32-bit systems, the stored uint64 has a 32-bit pointer and 32-bit count.
		return uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)
	}
	// On ppc64, Linux limits the user address space to 46 bits (see
	// TASK_SIZE_USER64 in the Linux kernel).  This has grown over time,
	// so here we allow 48 bit addresses.
	//
	// On mips64, Linux limits the user address space to 40 bits (see
	// TASK_SIZE64 in the Linux kernel).  This has grown over time,
	// so here we allow 48 bit addresses.
	//
	// On AMD64, virtual addresses are 48-bit numbers sign extended to 64.
	// We shift the address left 16 to eliminate the sign extended part and make
	// room in the bottom for the count.
	//
	// In addition to the 16 bits taken from the top, we can take 3 from the
	// bottom, because node must be pointer-aligned, giving a total of 19 bits
	// of count.
	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
}

func lfstackUnpack(val uint64) *lfnode {
	if unsafe.Sizeof(uintptr(0)) == 4 {
		return (*lfnode)(unsafe.Pointer(uintptr(val >> 32)))
	}
	return (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
}
```

削除されたファイル:
*   `src/runtime/lfstack_32bit.go`
*   `src/runtime/lfstack_64bit.go`
*   `src/runtime/lfstack_amd64.go`

## コアとなるコードの解説

追加された`lfstackPack`と`lfstackUnpack`関数は、Goのランタイムがロックフリースタックを効率的に管理するために使用する、ポインタとカウンタの結合・分離ロジックを実装しています。

### `lfstackPack(node *lfnode, cnt uintptr) uint64`

この関数は、ロックフリースタックのノードへのポインタ`node`と、ABA問題対策用のカウンタ`cnt`を、単一の`uint64`値にパックします。

*   **32ビットシステムの場合 (`unsafe.Sizeof(uintptr(0)) == 4`)**:
    `uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)`
    `node`ポインタを`uintptr`に変換し、それを32ビット左シフトして`uint64`の上位32ビットに配置します。そして、カウンタ`cnt`を下位32ビットに配置するためにOR演算で結合します。これにより、1つの`uint64`値にポインタとカウンタが効率的に格納されます。

*   **64ビットシステムの場合 (それ以外)**:
    `uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))`
    `node`ポインタを`uintptr`に変換し、`(64 - addrBits)`ビット左シフトします。`addrBits`は48なので、16ビット左シフトされます。これにより、ポインタは`uint64`の上位48ビットに配置され、下位16ビットがカウンタ用に空けられます。
    `cnt&(1<<cntBits-1)`は、カウンタ`cnt`を`cntBits`（19ビット）の範囲に収まるようにマスクします。このマスクされたカウンタ値が、ポインタが占有しない下位ビット空間にOR演算で結合されます。
    この実装では、ポインタのアライメント（通常8バイトアライメント）により、ポインタの下位3ビットが常にゼロであることを利用し、カウンタにさらに3ビットを追加しています。

### `lfstackUnpack(val uint64) *lfnode`

この関数は、パックされた`uint64`値`val`から、元の`lfnode`ポインタを復元します。

*   **32ビットシステムの場合 (`unsafe.Sizeof(uintptr(0)) == 4`)**:
    `(*lfnode)(unsafe.Pointer(uintptr(val >> 32)))`
    パックされた`val`を32ビット右シフトすることで、上位32ビットに格納されていたポインタ値を取り出します。これを`uintptr`にキャストし、さらに`unsafe.Pointer`を介して`*lfnode`型に戻します。

*   **64ビットシステムの場合 (それ以外)**:
    `(*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))`
    パックされた`val`から、まず`cntBits`（19ビット）分右シフトしてカウンタ部分を取り除きます。これにより、ポインタ値が`uint64`の下位から始まる形になります。
    次に、`<< 3`（3ビット左シフト）を行うことで、ポインタのアライメントによって失われた下位3ビットを復元し、正しいポインタ値を得ます。これを`uintptr`にキャストし、`unsafe.Pointer`を介して`*lfnode`型に戻します。

これらの変更により、Goランタイムは、異なるアーキテクチャ間でロックフリースタックのポインタパッキングロジックを単一の、より簡潔で保守しやすいコードベースで管理できるようになりました。

## 変更の背景

Goランタイムの内部では、ガベージコレクションやスケジューラなどの低レベルな処理で、ロックフリーデータ構造が頻繁に利用されます。ロックフリースタックはその一つであり、複数のゴルーチンが同時にアクセスしても競合状態に陥らないように設計されています。

`lfstackPack`と`lfstackUnpack`関数は、このロックフリースタックのノード（`lfnode`）のポインタとカウンタを、単一の`uint64`値にパック（結合）したり、その逆のアンパック（分離）したりするために使用されます。これは、Compare-And-Swap (CAS) 操作などのアトミック操作で、ポインタとカウンタを同時に更新する必要がある場合に特に重要です。ポインタとカウンタを1つの値にまとめることで、CAS操作を一度で実行でき、ABA問題の発生を抑制しつつ、効率的なロックフリー操作を実現します。

以前は、異なるCPUアーキテクチャ（32ビット、64ビット、特にAMD64）のメモリレイアウトやポインタの特性の違いに対応するため、これらの関数が個別のファイルに実装されていました。しかし、これはコードの重複と保守の複雑さにつながります。このコミットの背景には、これらのアーキテクチャ固有の差異をよりスマートに吸収し、コードベースを簡素化したいという意図があります。特に、AMD64におけるユーザーモードポインタの特性に関する新たな知見が、この統合を可能にする重要な要素となりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **ロックフリーデータ構造 (Lock-Free Data Structures)**:
    複数のスレッド（Goにおいてはゴルーチン）が同時にアクセスしても、ミューテックスなどのロック機構を使用せずに、正しい操作を保証するデータ構造です。これにより、ロックの競合によるパフォーマンス低下やデッドロックのリスクを回避できます。ロックフリーデータ構造の実装には、通常、アトミック操作（CAS: Compare-And-Swapなど）が用いられます。

2.  **Compare-And-Swap (CAS) 操作**:
    メモリ上の特定のアドレスにある値が期待する値と一致する場合にのみ、その値を新しい値にアトミックに更新する操作です。この操作は不可分であり、他のスレッドからの干渉を受けません。ロックフリーアルゴリズムの基盤となります。

3.  **ABA問題 (ABA Problem)**:
    ロックフリーアルゴリズムで発生しうる問題の一つです。CAS操作において、あるメモリ位置の値がAからBに変化し、その後再びAに戻った場合、CAS操作は値が変更されていないと誤認してしまう可能性があります。これを防ぐために、ポインタと一緒にカウンタ（またはタグ）を格納し、値が変更されるたびにカウンタをインクリメントする手法がよく用いられます。これにより、値がAに戻ってもカウンタが異なるため、CAS操作は失敗し、ABA問題を回避できます。

4.  **`unsafe.Pointer` と `uintptr`**:
    *   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムを迂回して、メモリを直接操作するために使用されます。ガベージコレクタは`unsafe.Pointer`が指すメモリを追跡しません。
    *   `uintptr`: ポインタの値を整数として表現する型です。`unsafe.Pointer`と相互変換が可能ですが、`uintptr`はポインタではないため、ガベージコレクタは`uintptr`が指すメモリを追跡しません。これらの型は、低レベルなシステムプログラミングや、Goの型システムでは表現できない操作（例: ポインタ演算、メモリレイアウトの操作）を行う際に利用されます。

5.  **ポインタパッキング (Pointer Packing)**:
    複数の情報を1つのワード（例: `uint64`）に詰め込む技術です。このコミットの場合、ロックフリースタックのノードへのポインタと、ABA問題対策のためのカウンタを1つの`uint64`値にパックしています。これにより、CAS操作を1回で実行できるようになります。ポインタは通常、メモリのアライメント制約により下位ビットが常にゼロになるため、その空いたビット空間をカウンタに利用できます。また、仮想アドレス空間の制約により、上位ビットが常にゼロになることも利用されます。

6.  **アーキテクチャ固有のメモリレイアウト**:
    CPUアーキテクチャによって、仮想アドレス空間のサイズやポインタの表現方法が異なります。例えば、32ビットシステムではポインタは32ビット、64ビットシステムではポインタは64ビットです。しかし、64ビットシステムであっても、実際に使用される仮想アドレス空間は64ビット全てではなく、例えば48ビットや40ビットに制限されていることがあります。残りの上位ビットは、通常、符号拡張（sign extension）のために使用されたり、単にゼロであったりします。このコミットでは、AMD64のユーザーモードポインタが上位17ビットでゼロになるという特性が利用されています。

## 技術的詳細

このコミットの核心は、`lfstackPack`と`lfstackUnpack`関数を単一の`lfstack.go`ファイルに統合し、アーキテクチャ間の差異をコンパイル時定数と特定のアーキテクチャ特性の利用によって吸収することです。

1.  **コンパイル時分岐による32ビット/64ビット対応**:
    `unsafe.Sizeof(uintptr(0)) == 4`という条件式が導入されています。`uintptr(0)`はゼロ値の`uintptr`型であり、そのサイズは実行環境のポインタサイズに依存します。
    *   32ビットシステムでは`unsafe.Sizeof(uintptr(0))`は4バイト（32ビット）になります。
    *   64ビットシステムでは`unsafe.Sizeof(uintptr(0))`は8バイト（64ビット）になります。
    この比較はコンパイル時に定数として評価されるため、コンパイラは不要な分岐を最適化によって削除（dead code elimination）し、結果として各アーキテクチャに最適化されたコードが生成されます。これにより、実行時のオーバーヘッドなしに、単一のソースファイルで複数のアーキテクチャに対応できます。

2.  **ポインタとカウンタのパッキング/アンパッキングロジック**:
    *   **32ビットシステム (`unsafe.Sizeof(uintptr(0)) == 4` の場合)**:
        *   `lfstackPack`: `uintptr(unsafe.Pointer(node))`を32ビット左シフトし、`uint64(cnt)`とOR演算で結合します。これにより、上位32ビットにポインタ、下位32ビットにカウンタが格納されます。
        *   `lfstackUnpack`: `val >> 32`で上位32ビットを取り出し、それを`uintptr`にキャストして`lfnode`ポインタに戻します。
        これは、32ビットシステムではポインタが32ビット幅であるため、`uint64`の半分をポインタに、残りの半分をカウンタに割り当てることが可能だからです。

    *   **64ビットシステム (それ以外の場合)**:
        *   `addrBits`と`cntBits`という定数が定義されています。
            *   `addrBits = 48`: 仮想アドレス空間が48ビットであることを想定しています。これは、多くの64ビットシステム（PPC64, MIPS64, AMD64など）で実際に使用されるユーザーモードアドレス空間のサイズを反映しています。
            *   `cntBits = 64 - addrBits + 3`: カウンタに割り当てるビット数です。`64 - 48 = 16`ビットがアドレスの上位から利用可能で、さらにポインタのアライメント（通常8バイトアライメント、つまり下位3ビットが常にゼロ）を利用して下位3ビットもカウンタに利用できるため、合計`16 + 3 = 19`ビットがカウンタに割り当てられます。
        *   `lfstackPack`: `uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))`
            *   `uintptr(unsafe.Pointer(node)))<<(64-addrBits)`: ポインタを左シフトして、カウンタ用のビット空間を確保します。例えば`addrBits=48`の場合、`64-48=16`ビット左シフトされ、ポインタは上位48ビットに配置されます。
            *   `uint64(cnt&(1<<cntBits-1))`: カウンタ値を`cntBits`でマスクし、カウンタ用のビット空間に収まるようにします。
        *   `lfstackUnpack`: `(*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))`
            *   `val >> cntBits`: パックされた値からカウンタ部分を右シフトで取り除きます。
            *   `<< 3`: ポインタが8バイトアライメントされていることを利用し、アンパック時に失われた下位3ビットを復元します。これにより、正しいポインタ値が得られます。

3.  **AMD64の特殊な扱いと統合**:
    コミットメッセージで特に言及されているのがAMD64アーキテクチャです。AMD64では、仮想アドレスは通常48ビットですが、64ビットレジスタにロードされる際に符号拡張（sign extension）されます。つまり、48ビット目の最上位ビットが64ビット目までコピーされます。
    以前の`lfstack_amd64.go`では、この符号拡張された部分を考慮して、ポインタを16ビット左シフトして符号拡張部分を排除し、下位ビットをカウンタに利用していました。
    しかし、Dmitry氏の確認により、「ユーザーモードポインタの上位17ビットはゼロになる」という事実が判明しました。これは、ユーザー空間のアドレスが特定の範囲に限定されており、その範囲では符号拡張が実質的に不要であることを意味します。この知見により、AMD64は他の64ビットアーキテクチャ（PPC64, MIPS64など）と同じ`addrBits=48`の汎用64ビット実装をそのまま利用できるようになり、個別の実装が不要になりました。これにより、`lfstack_amd64.go`ファイルが削除され、コードの重複がさらに削減されました。

## コアとなるコードの変更箇所

`src/runtime/lfstack.go`に以下のコードが追加され、既存のアーキテクチャ固有ファイルが削除されました。

```go
// src/runtime/lfstack.go に追加されたコード
const (
	addrBits = 48
	cntBits  = 64 - addrBits + 3
)

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	if unsafe.Sizeof(uintptr(0)) == 4 {
		// On 32-bit systems, the stored uint64 has a 32-bit pointer and 32-bit count.
		return uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)
	}
	// On ppc64, Linux limits the user address space to 46 bits (see
	// TASK_SIZE_USER64 in the Linux kernel).  This has grown over time,
	// so here we allow 48 bit addresses.
	//
	// On mips64, Linux limits the user address space to 40 bits (see
	// TASK_SIZE64 in the Linux kernel).  This has grown over time,
	// so here we allow 48 bit addresses.
	//
	// On AMD64, virtual addresses are 48-bit numbers sign extended to 64.
	// We shift the address left 16 to eliminate the sign extended part and make
	// room in the bottom for the count.
	//
	// In addition to the 16 bits taken from the top, we can take 3 from the
	// bottom, because node must be pointer-aligned, giving a total of 19 bits
	// of count.
	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
}

func lfstackUnpack(val uint64) *lfnode {
	if unsafe.Sizeof(uintptr(0)) == 4 {
		return (*lfnode)(unsafe.Pointer(uintptr(val >> 32)))
	}
	return (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
}
```

削除されたファイル:
*   `src/runtime/lfstack_32bit.go`
*   `src/runtime/lfstack_64bit.go`
*   `src/runtime/lfstack_amd64.go`

## コアとなるコードの解説

追加された`lfstackPack`と`lfstackUnpack`関数は、Goのランタイムがロックフリースタックを効率的に管理するために使用する、ポインタとカウンタの結合・分離ロジックを実装しています。

### `lfstackPack(node *lfnode, cnt uintptr) uint64`

この関数は、ロックフリースタックのノードへのポインタ`node`と、ABA問題対策用のカウンタ`cnt`を、単一の`uint64`値にパックします。

*   **32ビットシステムの場合 (`unsafe.Sizeof(uintptr(0)) == 4`)**:
    `uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)`
    `node`ポインタを`uintptr`に変換し、それを32ビット左シフトして`uint64`の上位32ビットに配置します。そして、カウンタ`cnt`を下位32ビットに配置するためにOR演算で結合します。これにより、1つの`uint64`値にポインタとカウンタが効率的に格納されます。

*   **64ビットシステムの場合 (それ以外)**:
    `uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))`
    `node`ポインタを`uintptr`に変換し、`(64 - addrBits)`ビット左シフトします。`addrBits`は48なので、16ビット左シフトされます。これにより、ポインタは`uint64`の上位48ビットに配置され、下位16ビットがカウンタ用に空けられます。
    `cnt&(1<<cntBits-1)`は、カウンタ`cnt`を`cntBits`（19ビット）の範囲に収まるようにマスクします。このマスクされたカウンタ値が、ポインタが占有しない下位ビット空間にOR演算で結合されます。
    この実装では、ポインタのアライメント（通常8バイトアライメント）により、ポインタの下位3ビットが常にゼロであることを利用し、カウンタにさらに3ビットを追加しています。

### `lfstackUnpack(val uint64) *lfnode`

この関数は、パックされた`uint64`値`val`から、元の`lfnode`ポインタを復元します。

*   **32ビットシステムの場合 (`unsafe.Sizeof(uintptr(0)) == 4`)**:
    `(*lfnode)(unsafe.Pointer(uintptr(val >> 32)))`
    パックされた`val`を32ビット右シフトすることで、上位32ビットに格納されていたポインタ値を取り出します。これを`uintptr`にキャストし、さらに`unsafe.Pointer`を介して`*lfnode`型に戻します。

*   **64ビットシステムの場合 (それ以外)**:
    `(*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))`
    パックされた`val`から、まず`cntBits`（19ビット）分右シフトしてカウンタ部分を取り除きます。これにより、ポインタ値が`uint64`の下位から始まる形になります。
    次に、`<< 3`（3ビット左シフト）を行うことで、ポインタのアライメントによって失われた下位3ビットを復元し、正しいポインタ値を得ます。これを`uintptr`にキャストし、`unsafe.Pointer`を介して`*lfnode`型に戻します。

これらの変更により、Goランタイムは、異なるアーキテクチャ間でロックフリースタックのポインタパッキングロジックを単一の、より簡潔で保守しやすいコードベースで管理できるようになりました。

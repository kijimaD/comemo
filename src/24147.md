# [インデックス 24147] ファイルの概要

このコミットは、Go言語の公式ドキュメントである `doc/asm.html` を更新し、Goアセンブラのアーキテクチャ固有の情報を改善することを目的としています。特に、アセンブラ命令の定義の参照方法、x86およびARMアーキテクチャにおけるアドレッシングモードの詳細、そして`g`および`m`構造体へのアクセス方法に関する記述が更新されました。また、ARM64とPPC64アーキテクチャのドキュメントがまだ不完全であることを明記し、今後の改善点としています。

## 変更の背景

Go言語のランタイムや一部の標準ライブラリは、パフォーマンスが要求される箇所でGoアセンブラ（Plan 9アセンブラの派生）を使用しています。このアセンブラの構文やアーキテクチャ固有の動作を理解することは、Goの低レベルな挙動をデバッグしたり、最適化されたコードを書いたりする上で不可欠です。

しかし、以前の`doc/asm.html`ドキュメントは、アセンブラ命令の定義を見つける方法が古くなっていたり、特定のアドレッシングモードに関する詳細な説明が不足していたりしました。特に、命令セットの参照先がGoのツールチェーンの進化に合わせて更新されていませんでした。

このコミットは、これらの問題を解決し、Goアセンブラに関するドキュメントの正確性と網羅性を向上させることを目的としています。これにより、開発者がGoアセンブリコードをより容易に理解し、記述できるようになることが期待されます。また、ARM64やPPC64といった比較的新しいアーキテクチャのドキュメントが不足している現状を認識し、今後の課題として明示しています。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下の概念について基本的な知識があると役立ちます。

*   **Goアセンブラ (Plan 9アセンブラ)**: Go言語で使用されるアセンブラは、一般的なIntel構文やAT&T構文とは異なる独自の構文（Plan 9アセンブラ由来）を持っています。レジスタの命名規則（例: `AX`, `CX`ではなく`AX`, `BX`など）、命令のオペランドの順序（左から右へデータが流れる）、擬似レジスタ（`SP`, `FP`, `SB`など）の使用が特徴です。
*   **Goランタイム**: Goプログラムの実行を管理する低レベルなシステムです。これには、ゴルーチン（goroutine）のスケジューリング、ガベージコレクション、メモリ管理、システムコールインターフェースなどが含まれます。Goランタイムの多くの部分は、パフォーマンスのためにアセンブリ言語で書かれています。
*   **`g` と `m` 構造体**: Goランタイムにおける中心的なデータ構造です。
    *   `g` (goroutine): Goの軽量スレッドであるゴルーチンを表す構造体です。各ゴルーチンは独自のスタックを持ち、`g`構造体にはそのゴルーチンの状態（スタックポインタ、スケジューリング情報など）が格納されます。
    *   `m` (machine): OSスレッドを表す構造体です。Goランタイムは複数のOSスレッドを利用してゴルーチンを実行します。`m`構造体には、そのOSスレッドに関連する情報（現在のゴルーチン`g`へのポインタ、スケジューラ情報など）が格納されます。
    アセンブリコードでは、現在のゴルーチンやOSスレッドの情報を取得するために、これらの構造体へのポインタを頻繁に操作します。
*   **`cmd/internal/obj` パッケージ**: Goコンパイラツールチェーンの一部であり、アセンブラの命令定義、オブジェクトファイルの生成、およびアーキテクチャ固有のコード生成ロジックが含まれています。Goアセンブラの命令セットは、このパッケージ内のGoソースファイルで定義されています。
*   **アトミック操作**: 複数のCPUコアやスレッドから同時にアクセスされても、その操作が中断されずに完全に実行されることを保証する操作です。メモリの読み書きにおいて、競合状態を防ぎ、データの一貫性を保つために重要です。アトミック操作は通常、ハードウェアの特別な命令を利用して実装されます。
*   **メモリのアラインメント**: データがメモリ上で特定のバイト境界（例: 4バイト、8バイト）に配置されることを指します。多くの場合、CPUはアラインされたデータへのアクセスの方が高速であり、アラインされていないデータへのアクセスはパフォーマンスの低下や、場合によってはハードウェア例外（クラッシュ）を引き起こす可能性があります。

## 技術的詳細

このコミットは、`doc/asm.html`の複数のセクションにわたって、Goアセンブラの利用に関する重要な更新と明確化を行っています。

1.  **命令セットの参照方法の変更**:
    *   以前は、特定のアーキテクチャ（例: 32-bit Intel x86）の命令セットを確認するには、リンカのヘッダーファイル（例: `$GOROOT/src/cmd/8l/8.out.h`）を参照するように指示されていました。このファイルはC言語の`enum`で命令を定義していました。
    *   このコミットでは、参照先を`src/cmd/internal/obj/arm/a.out.go`（ARMの場合）や`cmd/internal/obj/x86/a.out.go`（x86/amd64の場合）に変更しています。これは、Goのアセンブラツールチェーンの内部構造が進化し、命令定義が`cmd/internal/obj`パッケージ内のGoソースファイル（`const`宣言）に統合されたことを示唆しています。これにより、Go開発者はGoのソースコード内で命令定義を直接確認できるようになり、より一貫性のある参照方法が提供されます。
    *   命令名の命名規則（`A`で始まる定数、例: `AAND`）と、それが実際のアセンブリ命令（`A`なし、例: `AND`）にどのように対応するかの説明が更新され、より明確になりました。

2.  **`g` と `m` 構造体へのアクセス方法の明確化**:
    *   32-bit Intel 386および64-bit Intel 386 (amd64) アーキテクチャにおいて、Goランタイムの`g`（ゴルーチン）および`m`（OSスレッド）構造体へのポインタをアセンブリコードから取得する方法が再確認されました。
    *   `get_tls(CX)`マクロを使用してスレッドローカルストレージ（TLS）から現在の`g`ポインタを取得し、そこから`g.m`（`g_m(AX)`）を介して`m`ポインタを取得する一連の命令（`MOVL`/`MOVQ`）が示されています。これはGoランタイムのアセンブリコードで頻繁に使用されるパターンです。
    *   `#include "zasm_GOOS_GOARCH.h"`の代わりに`#include "go_asm.h"`を使用するように変更され、アセンブリコードのインクルードメカニズムが簡素化された可能性があります。

3.  **アドレッシングモードの詳細な追加**:
    *   x86アーキテクチャ向けに、` (DI)(BX*2)`（レジスタ間接＋インデックスレジスタ*スケール）や`64(DI)(BX*2)`（ベース＋レジスタ間接＋インデックスレジスタ*スケール）といった複雑なアドレッシングモードの例が追加されました。これにより、Goアセンブラがサポートするx86のアドレッシングモードの多様性が示されます。
    *   ARMアーキテクチャ向けに、`R0->16`（算術右シフト）、`R0>>16`（論理右シフト）、`R0<<16`（左シフト）、`R0@>16`（右ローテート）といったシフト操作を含むアドレッシングモードの例が追加されました。また、シフト量がレジスタで指定される場合（例: `R0<<R1`）も示されています。これは、ARMプロセッサの強力なバレルシフタ機能をGoアセンブラでどのように利用できるかを示しています。
    *   ARMの複数レジスタ命令におけるレジスタリストの指定方法（例: `[R0,g,R12-R15]`）も追加されました。
    *   PPC64アーキテクチャ向けに、` (R5)(R6*1)`というスケーリングされたアドレッシングモードの例が追加されましたが、x86とは異なり、スケールは`1`のみが許可されることが明記されています。

4.  **`runtime·atomicload64`関数のアセンブリコード例の更新**:
    *   このセクションでは、64ビットのアトミックロード関数`atomicload64`のx86アセンブリ実装例が更新されました。
    *   特に重要な変更は、`ptr`が8バイト境界にアラインされているかどうかのチェックが追加された点です。
        ```asm
        TESTL	$7, AX
        JZ	2(PC)
        MOVL	0, AX // crash with nil ptr deref
        ```
        このコードは、`ptr`（`AX`レジスタに格納されている）の下位3ビットをテストし（`$7`はバイナリで`0111`）、結果がゼロでない（つまり、アドレスが8の倍数でない）場合に、`MOVL 0, AX`を実行して`AX`をゼロに設定します。これにより、続く`MOVQ (%EAX), %MM0`命令がnilポインタ逆参照を引き起こし、プログラムがクラッシュします。これは、アラインされていないアドレスでのアトミック操作が未定義の動作を引き起こす可能性があるため、問題を早期に検出して開発者に通知するための堅牢性向上策です。

5.  **ARM64とPPC64のドキュメント不足の明記**:
    *   ARM64とPPC64のセクションには「TODO」が追加され、これらのアーキテクチャに関する詳細なドキュメントがまだ不足していることが明示されました。これは、今後のドキュメント改善の方向性を示しています。

## コアとなるコードの解説

このコミットの「コアとなるコード」は、Goアセンブラのドキュメントである`doc/asm.html`のテキストコンテンツそのものです。変更の大部分は、既存の記述の修正、新しい情報の追加、および説明の明確化にあります。

最も技術的に重要な変更点の一つは、`runtime·atomicload64`関数のアセンブリコード例に追加されたアラインメントチェックです。

```html
<pre>
TEXT runtime·atomicload64(SB), NOSPLIT, $0-12
 	MOVL	ptr+0(FP), AX
+	TESTL	$7, AX
+	JZ	2(PC)
+	MOVL	0, AX // crash with nil ptr deref
 	LEAL	ret_lo+4(FP), BX
 	// MOVQ (%EAX), %MM0
 	BYTE $0x0f; BYTE $0x6f; BYTE $0x00
 	// MOVQ %MM0, 0(%EBX)
 	BYTE $0x0f; BYTE $0x7f; BYTE $0x03
 	// EMMS
 	BYTE $0x0F; BYTE $0x77
 	RET
</pre>
```

このコードスニペットの追加された行は以下の通りです。

*   `MOVL ptr+0(FP), AX`: 関数引数`ptr`のアドレスを`AX`レジスタにロードします。
*   `TESTL $7, AX`: `AX`レジスタの値（`ptr`のアドレス）と即値`7`（バイナリで`00000111`）のビットごとのAND演算を実行し、結果に基づいてフラグを設定します。この操作は、`ptr`のアドレスが8の倍数であるかどうか（つまり、下位3ビットがすべてゼロであるかどうか）を効率的にチェックします。
*   `JZ 2(PC)`: 直前の`TESTL`命令の結果、ゼロフラグ（ZF）がセットされている場合（つまり、`ptr`のアドレスが8の倍数である場合）、プログラムカウンタ（PC）を2バイト進めます。これにより、次の2つの命令（`MOVL 0, AX`）がスキップされます。
*   `MOVL 0, AX // crash with nil ptr deref`: `TESTL`の結果、ゼロフラグがセットされていない場合（つまり、`ptr`のアドレスが8の倍数でない場合）、`AX`レジスタに`0`をロードします。これにより、`AX`はnilポインタとなり、続く`MOVQ (%EAX), %MM0`命令がnilポインタ逆参照を引き起こし、プログラムがクラッシュします。これは、アラインメント違反を早期に検出し、未定義の動作を防ぐための意図的なクラッシュメカニズムです。

この変更は、アトミック操作が正しく機能するために、対象となるメモリが適切にアラインされている必要があるという重要な制約を強調しています。アラインメント違反は、特に異なるアーキテクチャやコンパイラ設定において、予測不能なバグやパフォーマンスの問題を引き起こす可能性があるため、このような明示的なチェックはコードの堅牢性を高めます。

その他の変更は、主にGoアセンブラの構文、命令セットの参照方法、およびアーキテクチャ固有のアドレッシングモードに関する説明を更新し、より正確で理解しやすいドキュメントを提供することに貢献しています。

# [インデックス 25187] ファイルの概要

このコミットは、GoコンパイラのPPC64アーキテクチャ向けバックエンドにおける、非リーフ（non-leaf）な生成メソッドのエピローグ処理に関するバグを修正するものです。具体的には、`duffzero`という高速なメモリゼロクリアルーチンが、特定の条件下でリンクレジスタ（LR）を誤って上書きしてしまう問題に対処し、その結果として一時的に無効化されていた`duffzero`を再び有効にすることを目的としています。

変更されたファイルは以下の3つです。

*   `src/cmd/compile/internal/ppc64/ggen.go`: GoコンパイラのPPC64バックエンドにおけるコード生成の一部で、`duffzero`の使用条件を制御していました。
*   `src/cmd/internal/obj/ppc64/obj9.go`: GoアセンブラのPPC64バックエンドの一部で、関数のエピローグ処理、特に戻りアドレスの処理を担っています。
*   `test/fixedbugs/issue12108.go`: このコミットで修正されるバグ（Issue 12108）を再現し、修正を検証するための新しいテストケースです。

## 変更の背景

このコミットの背景には、GoコンパイラがPPC64アーキテクチャ向けに生成するコードにおいて、`duffzero`という最適化されたメモリゼロクリアルーチンが原因で発生していた問題があります。

`duffzero`は、大きなメモリ領域を効率的にゼロクリアするために使用されるアセンブリレベルの最適化手法です。しかし、PPC64アーキテクチャ上の非リーフ（つまり、他の関数を呼び出す）な生成メソッドにおいて、`duffzero`が誤ってリンクレジスタ（LR）の内容を上書きしてしまうというバグが存在していました。リンクレジスタは、関数呼び出し後に元の呼び出し元に戻るためのアドレスを保持する非常に重要なレジスタです。これが上書きされると、関数からの復帰が不正なアドレスに行われ、プログラムのクラッシュや予期せぬ動作を引き起こします。

この問題のため、Goコンパイラは一時的にPPC64上で`duffzero`の使用を無効化していました。具体的には、`src/cmd/compile/internal/ppc64/ggen.go`内の`duffzero`を呼び出す条件式に`false &&`というプレフィックスを付けることで、コンパイル時に`duffzero`のコードが生成されないようにしていました。

Issue #12108 はこの問題を追跡しており、このコミットは、`src/cmd/internal/obj/ppc64/obj9.go`におけるエピローグ処理の修正を通じて、リンクレジスタの保護を強化し、`duffzero`を安全に再有効化できるようにすることで、このバグを解決します。これにより、PPC64上でのGoプログラムのパフォーマンスが向上することが期待されます。

## 前提知識の解説

### PPC64アーキテクチャ

PPC64（PowerPC 64-bit）は、IBMによって開発されたRISC（Reduced Instruction Set Computer）アーキテクチャの一種です。Go言語は、様々なCPUアーキテクチャをサポートしており、PPC64もその一つです。PPC64プロセッサは、汎用レジスタ（GPRs）、浮動小数点レジスタ（FPRs）、特殊目的レジスタ（SPRs）などを持っています。

*   **リンクレジスタ (Link Register, LR)**: PPC64アーキテクチャにおいて、LRは関数呼び出し時に呼び出し元に戻るためのアドレス（リターンアドレス）を格納するために使用される特殊目的レジスタです。関数が別の関数を呼び出す際、呼び出し元の次の命令のアドレスがLRに保存されます。呼び出された関数は、処理を終えるとLRに格納されたアドレスに分岐することで、呼び出し元に制御を戻します。非リーフ関数（他の関数を呼び出す関数）では、LRの内容が上書きされる可能性があるため、スタックに保存・復元する必要があります。

### Goコンパイラ (cmd/compile)

`cmd/compile`はGo言語のコンパイラ本体です。ソースコードを中間表現に変換し、最終的に各ターゲットアーキテクチャ（例: amd64, arm64, ppc64）の機械語コードに変換するバックエンドを持っています。
*   `src/cmd/compile/internal/ppc64/ggen.go`: このファイルは、PPC64アーキテクチャ向けのコード生成ロジックの一部を含んでいます。特に、メモリのゼロクリアなどの低レベルな操作に関するコード生成を担当することがあります。

### Goアセンブラ (cmd/internal/obj)

`cmd/internal/obj`はGo言語のアセンブラであり、コンパイラが生成したアセンブリ命令を機械語に変換したり、リンカが使用するオブジェクトファイルを生成したりします。また、コンパイラのバックエンドが生成するアセンブリコードの最適化や変換も行います。
*   `src/cmd/internal/obj/ppc64/obj9.go`: このファイルは、PPC64アーキテクチャ向けのアセンブラのバックエンド処理を含んでいます。関数のプロローグ（開始処理）やエピローグ（終了処理）の生成、命令の変換など、低レベルなコード操作を行います。

### エピローグ (Epilogue)

エピローグは、関数の実行が終了する直前に行われる一連の処理です。主な目的は、関数が使用したスタックフレームを解放し、呼び出し元に制御を安全に戻すことです。これには、スタックポインタの調整、保存されたレジスタ（特にリンクレジスタ）の復元、そしてリターンアドレスへの分岐などが含まれます。

### リーフ関数 (Leaf function) と 非リーフ関数 (Non-leaf function)

*   **リーフ関数**: 実行中に他の関数を一切呼び出さない関数を指します。リーフ関数は、リンクレジスタをスタックに保存する必要がないため、エピローグ処理が簡素化されることがあります。
*   **非リーフ関数**: 実行中に他の関数を呼び出す関数を指します。非リーフ関数は、自身が別の関数を呼び出す際にリンクレジスタが上書きされるため、呼び出し前にLRの値をスタックに保存し、関数終了時にスタックから復元する必要があります。

### Duff's Device (Duffzero)

Duff's Deviceは、C言語のプログラマであるTom Duffが考案した、ループアンローリング（ループ展開）を効率的に行うためのテクニックです。特に、メモリのコピーやゼロクリアといった単純な操作を高速化するためにアセンブリ言語レベルで実装されることがあります。Go言語のランタイムでは、`duffzero`として、大きなメモリ領域を高速にゼロクリアするために使用されています。これは、特定のサイズごとにジャンプテーブルを利用してループを部分的に展開し、CPUのパイプライン効率を最大化することで、通常のループよりも高速な処理を実現します。

`duffzero`のような低レベルな最適化ルーチンは、直接レジスタを操作するため、アーキテクチャ固有のレジスタ使用規約（ABI）や、リンクレジスタの保存・復元ルールに厳密に従う必要があります。もし`duffzero`がLRを誤って上書きした場合、関数からの不正な復帰を引き起こす可能性があります。

### テールコール (Tail call)

テールコールは、関数の最後の操作が別の関数呼び出しである場合に適用される最適化手法です。この最適化が適用されると、呼び出し元の関数はスタックフレームを構築せずに、直接呼び出される関数に制御を移すことができます。これにより、スタックの使用量を削減し、パフォーマンスを向上させることができます。しかし、テールコール最適化は、デバッグを困難にしたり、特定のアーキテクチャやコンパイラの実装によっては複雑なレジスタ管理を必要としたりする場合があります。

## 技術的詳細

このコミットは、PPC64アーキテクチャにおけるGoコンパイラのコード生成とアセンブラの連携に関する深い理解を必要とする問題に対処しています。

問題の核心は、`duffzero`が非リーフな生成メソッド内で使用された際に、リンクレジスタ（LR）を誤って上書きしてしまうことにありました。通常、非リーフ関数は、自身が他の関数を呼び出す前にLRをスタックに保存し、関数終了時に復元することで、呼び出し元への正しい復帰を保証します。しかし、`duffzero`のような最適化されたアセンブリルーチンが、このLRの保存・復元メカニズムと衝突し、LRを破壊してしまうケースがあったと考えられます。

具体的には、`ggen.go`内のコメントに「If DUFFZERO is used inside a tail call (see genwrapper) it will overwrite the link register.」とあるように、`duffzero`がテールコールのような状況で使われるとLRを上書きする可能性が指摘されていました。このため、一時的に`duffzero`の使用が停止されていました。

このコミットでは、`obj9.go`におけるエピローグ処理、特に`ABR`（Absolute Branch）命令の生成ロジックが修正されています。`ABR`命令は、指定されたアドレスに無条件に分岐する命令です。関数のエピローグでは、この命令を使ってLRに格納されたリターンアドレスに分岐することで、呼び出し元に制御を戻します。

修正前は、リーフ関数と非リーフ関数でLRへの分岐処理が不適切に扱われる可能性がありました。特に、`p.To.Sym != nil`という条件（これは`retjmp`、つまり特定のシンボルへのジャンプを意味する）が考慮されていましたが、非リーフ関数におけるLRの正しい復元と分岐のロジックが不十分でした。

このコミットでは、`retTarget`という変数を導入し、分岐先がシンボルであるか（`retjmp`）そうでないか（通常のLRへの復帰）を明確に区別しています。そして、非リーフ関数（`cursym.Text.Mark&LEAF != 0`が偽の場合）のエピローグにおいて、`ABR`命令の分岐先を、`retTarget`が存在すればそのシンボルに、存在しなければ`REG_LR`（リンクレジスタ）に設定するように変更されました。これにより、非リーフ関数が`duffzero`のようなルーチンを呼び出した後でも、リンクレジスタが正しく復元され、適切なリターンアドレスに分岐できるようになります。

`ggen.go`の変更は、この`obj9.go`での修正が完了したことを受けて、`duffzero`を無効化していた`false &&`の条件を削除し、`duffzero`の最適化を再び有効にするものです。

## コアとなるコードの解説

このコミットの核となる修正は、PPC64アーキテクチャにおける関数のエピローグ処理、特に`ABR`（Absolute Branch）命令の分岐先決定ロジックの改善にあります。

`src/cmd/internal/obj/ppc64/obj9.go`の変更は、`preprocess`関数内で、関数のエピローグにおける戻り処理をより堅牢にするものです。
以前は、`p.To.Sym != nil`という条件で`retjmp`（特定のシンボルへのジャンプ）を処理していましたが、これがリーフ関数と非リーフ関数、特に`duffzero`のような最適化ルーチンが関与する場合に、リンクレジスタ（LR）の正しい扱いを妨げていました。

新しいコードでは、まず`retTarget := p.To.Sym`として、元の命令がシンボルへの分岐を意図していたかどうかを`retTarget`変数に保存します。
そして、`ABR`命令を生成する際に、以下のロジックで分岐先を決定します。

1.  **リーフ関数（`cursym.Text.Mark&LEAF != 0`）の場合**:
    *   `retTarget == nil`（通常の関数復帰）であれば、`p.To.Type = obj.TYPE_REG`および`p.To.Reg = REG_LR`を設定し、LRに格納されたアドレスに分岐します。
    *   `retTarget != nil`（特定のシンボルへのジャンプ）であれば、`p.To.Type = obj.TYPE_BRANCH`および`p.To.Sym = retTarget`を設定し、そのシンボルに分岐します。
    この変更により、リーフ関数であっても、`retjmp`のような特殊なケースでLRを誤って使用するのではなく、適切な分岐先を選択できるようになります。

2.  **非リーフ関数（`cursym.Text.Mark&LEAF == 0`）の場合**:
    *   同様に、`retTarget == nil`であれば`REG_LR`に、`retTarget != nil`であれば`retTarget`シンボルに分岐するように設定されます。
    非リーフ関数は、自身が他の関数を呼び出すため、呼び出し前にLRをスタックに保存し、エピローグで復元する必要があります。この修正は、LRが正しく復元された後に、そのLRの値（または`retTarget`で指定されたシンボル）に安全に分岐することを保証します。これにより、`duffzero`がLRを一時的に上書きしたとしても、エピローグで正しいLRの値が復元され、プログラムが正常に呼び出し元に戻れるようになります。

`src/cmd/compile/internal/ppc64/ggen.go`の変更は、この`obj9.go`でのエピローグ処理の修正が完了し、`duffzero`が安全に使用できるようになったことを受けて行われました。以前は`false &&`という条件で`duffzero`のコード生成を意図的に無効化していましたが、このプレフィックスを削除することで、コンパイラは再び`duffzero`の最適化を利用してメモリゼロクリアを行うようになります。

結果として、このコミットはPPC64アーキテクチャにおけるGoプログラムの正確性とパフォーマンスの両方を向上させます。

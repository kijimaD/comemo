## 変更の背景

この変更の背景には、HTTP/2プロトコルの導入と普及があります。Go言語の `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供しており、HTTP/1.xだけでなくHTTP/2もサポートしています。リダイレクト処理はHTTP通信において非常に一般的な操作であり、クライアントがリダイレクトレスポンスを受け取った際に、そのレスポンスボディを適切に処理（通常は破棄）し、新しいURLにリクエストを再送信する必要があります。

HTTP/1.xとHTTP/2では、プロトコルの動作にいくつかの違いがあります。特に、HTTP/2は単一のTCP接続上で複数のリクエストとレスポンスを多重化（multiplexing）する能力を持っています。このようなプロトコルの違いが、リダイレクト時のボディ処理に予期せぬ影響を与える可能性がないかを検証することは重要です。

既存の `TestClientRedirectEatsBody` テストはHTTP/1.xの動作を検証していましたが、HTTP/2環境下でも同様の挙動が保証されることを確認するため、このテストをHTTP/2モードでも実行できるように拡張する必要がありました。これにより、Goの `net/http` クライアントが、どのHTTPプロトコルを使用しているかに関わらず、リダイレクトを安全かつ正しく処理できることが保証されます。

## 前提知識の解説

### HTTP/1.xとHTTP/2

*   **HTTP/1.x**: 広く普及しているHTTPの初期バージョン。リクエストごとに新しいTCP接続を確立するか、Keep-Aliveヘッダーを使用して単一接続で複数のリクエストを順次処理します。ヘッダーはテキストベースで冗長になりがちです。
*   **HTTP/2**: HTTP/1.xのパフォーマンス上の課題を解決するために設計された新しいプロトコル。
    *   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が軽減されます。
    *   **ヘッダー圧縮 (Header Compression)**: HPACK形式を使用してヘッダーを効率的に圧縮し、帯域幅の使用量を削減します。
    *   **サーバープッシュ (Server Push)**: クライアントが要求する前に、サーバーがリソースをプッシュできます。
    *   **バイナリフレーミング (Binary Framing)**: メッセージがバイナリ形式でエンコードされ、解析が高速化されます。

### HTTPリダイレクト

HTTPリダイレクトは、クライアントが要求したリソースが別の場所に移動したことをサーバーがクライアントに伝えるメカニズムです。サーバーは `Location` ヘッダーと3xxステータスコード（例: `302 Found`, `301 Moved Permanently`）を含むレスポンスを返します。クライアントは `Location` ヘッダーで指定された新しいURLに自動的にリクエストを再送信します。

「リダイレクト時にボディを食べる (Redirect Eats Body)」とは、リダイレクトレスポンス（例: `302 Found`）にボディが含まれている場合、クライアントはそのボディを読み取って処理するのではなく、単に破棄して次のリダイレクト先へのリクエストに進むべきであるという挙動を指します。これは、リダイレクトレスポンスのボディが通常、ユーザーには表示されない情報であり、不必要にリソースを消費したり、セキュリティ上の問題を引き起こしたりするのを防ぐためです。

### Go `net/http` パッケージ

Go言語の標準ライブラリに含まれる `net/http` パッケージは、HTTPクライアントとサーバーを構築するための強力な機能を提供します。これには、リクエストの送信、レスポンスの受信、ヘッダーの処理、リダイレクトの自動追跡などが含まれます。

### `httptest.NewServer` と `newClientServerTest`

*   `httptest.NewServer`: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ関数です。通常、ローカルホストのランダムなポートでサーバーを起動し、テスト対象のHTTPクライアントが接続できるようにします。これは主にHTTP/1.xのテストに使用されます。
*   `newClientServerTest`: このコミットで導入された（または既存の）ヘルパー関数で、HTTP/1.xとHTTP/2の両方でテストサーバーとクライアントを設定するために使用されます。`h2` パラメータを受け取ることで、HTTP/2モードでのテストを容易にします。

## 技術的詳細

このコミットの主要な技術的変更点は、既存のテストロジックを共通のヘルパー関数 `testClientRedirectEatsBody` に抽出し、そのヘルパー関数がHTTP/1.xとHTTP/2の両方のモードで実行できるようにしたことです。

1.  **テストロジックの共通化**: 元々 `TestClientRedirectEatsBody` という単一のテスト関数内にあったリダイレクト処理の検証ロジックが、`testClientRedirectEatsBody(t *testing.T, h2 bool)` という新しい関数に移動されました。この関数は `h2` というブール値の引数を受け取り、HTTP/2モードでテストを実行するかどうかを制御します。
2.  **HTTP/1.xとHTTP/2のテストケースの分離**:
    *   `TestClientRedirectEatsBody_h1(t *testing.T)`: この新しいテスト関数は `testClientRedirectEatsBody(t, false)` を呼び出し、HTTP/1.xモードでリダイレクトテストを実行します。
    *   `TestClientRedirectEatsBody_h2(t *testing.T)`: この新しいテスト関数は `testClientRedirectEatsBody(t, true)` を呼び出し、HTTP/2モードでリダイレクトテストを実行します。
3.  **テストサーバーとクライアントのセットアップの抽象化**: `newClientServerTest(t, h2, HandlerFunc(...))` というヘルパー関数が導入されています（または既存のものが利用されています）。この関数は、`h2` パラメータに基づいてHTTP/1.xまたはHTTP/2のテストサーバーとクライアントをセットアップします。これにより、テストコードがプロトコル固有のセットアップ詳細から解放され、より簡潔になります。
    *   `cst := newClientServerTest(t, h2, HandlerFunc(...))` でテスト環境を構築し、`defer cst.close()` でクリーンアップします。
    *   クライアントのリクエストは `cst.c.Get(cst.ts.URL)` を通じて行われます。ここで `cst.c` は設定されたHTTPクライアント、`cst.ts.URL` はテストサーバーのURLです。

この構造により、同じリダイレクト処理の検証ロジックを再利用しつつ、異なるHTTPプロトコル環境下での動作を網羅的にテストすることが可能になります。

## コアとなるコードの解説

1.  **`TestClientRedirectEatsBody_h1` と `TestClientRedirectEatsBody_h2` の追加**:
    *   `TestClientRedirectEatsBody_h1(t *testing.T)` は、HTTP/1.xモードでリダイレクトテストを実行するためのエントリポイントです。`testClientRedirectEatsBody(t, false)` を呼び出し、`h2` フラグを `false` に設定してHTTP/1.xの動作を指示します。
    *   `TestClientRedirectEatsBody_h2(t *testing.T)` は、HTTP/2モードでリダイレクトテストを実行するためのエントリポイントです。`testClientRedirectEatsBody(t, true)` を呼び出し、`h2` フラグを `true` に設定してHTTP/2の動作を指示します。

2.  **`testClientRedirectEatsBody(t *testing.T, h2 bool)` 関数の導入**:
    *   この関数は、実際のリダイレクトテストロジックをカプセル化します。`h2` 引数によって、HTTP/1.xとHTTP/2のどちらのプロトコルでテストを実行するかを制御します。
    *   `defer afterTest(t)`: テスト後のクリーンアップ処理を保証します。
    *   `saw := make(chan string, 2)`: リクエストがサーバーに到達したことを記録するためのチャネルです。
    *   `cst := newClientServerTest(t, h2, HandlerFunc(...))`: ここが重要な変更点です。`httptest.NewServer` の代わりに `newClientServerTest` ヘルパー関数が使用されています。この関数は `h2` フラグに基づいて、HTTP/1.xまたはHTTP/2をサポートするテストサーバー (`cst.ts`) と、それに対応するクライアント (`cst.c`) をセットアップします。
        *   `HandlerFunc(func(w ResponseWriter, r *Request) { ... })`: テストサーバーがリクエストを受け取った際のハンドラです。
            *   `saw <- r.RemoteAddr`: リクエスト元のリモートアドレスをチャネルに送信します。
            *   `if r.URL.Path == "/" { Redirect(w, r, "/foo", StatusFound) }`: ルートパスへのリクエストに対して、`/foo` への `302 Found` リダイレクトを返します。このリダイレクトレスポンスにはボディが含まれる可能性があります。
    *   `defer cst.close()`: テストサーバーとクライアントのリソースを適切にクリーンアップします。
    *   `res, err := cst.c.Get(cst.ts.URL)`: セットアップされたクライアント (`cst.c`) を使用して、テストサーバー (`cst.ts.URL`) にGETリクエストを送信します。これにより、リダイレクト処理がトリガーされます。
    *   以降のコード（変更差分には含まれていませんが、元のテストロジックから引き継がれる部分）で、リダイレクトが正しく処理され、リダイレクトレスポンスのボディが「食べられた」（破棄された）ことが検証されます。

この変更により、Goの `net/http` クライアントが、HTTP/1.xとHTTP/2の両方の環境で、リダイレクト時にレスポンスボディを適切に無視する挙動を確実にテストできるようになりました。

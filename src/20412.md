# [インデックス 20412] ファイルの概要

このコミットは、GoランタイムにおけるSolarisシステムコール実装の重要な変更を示しています。具体的には、`syscall_solaris.goc`というCとGoの混合コードで書かれたファイルを廃止し、その機能を純粋なGoコード（`syscall_solaris.go`）と、Cライブラリ関数へのシンボル解決を行うための新しいCファイル（`syscall_solaris.c`）、そしてアセンブリ言語によるGoとCの間の橋渡し（`thunk_solaris_amd64.s`）に置き換えるものです。これにより、GoランタイムのCコード依存性を減らし、Go 1.4で進められたランタイムのGo言語化の一環として、保守性と移植性の向上を目指しています。

+func syscall_sysvicall6(fn, nargs, a1, a2, a3, a4, a5, a6 uintptr) (r1, r2, err uintptr) {
+	call := libcall{
+		fn:   unsafe.Pointer(fn),
+		n:    nargs,
+		args: unsafe.Pointer(&a1),
+	}
+	entersyscallblock()
+	asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(&call))
+	exitsyscall()
+	return call.r1, call.r2, call.err

## 変更の背景

このコミットは、Go言語のランタイムがC言語のコードに依存する部分を減らし、よりGo言語で記述されたコードに移行するという、Go 1.4リリースにおける主要な取り組みの一環です。Goの初期のランタイムは、ガベージコレクション、並行処理、メモリ管理といった重要な機能のためにC言語とアセンブリ言語に大きく依存していました。特に、オペレーティングシステムとの低レベルな相互作用、すなわちシステムコールはC言語で実装されていました。

`syscall_solaris.goc`ファイルは、GoとCのコードを混在させるための特殊な形式であり、Solarisシステムにおけるシステムコールを扱うために使用されていました。しかし、このような混合コードは、Goランタイムの全体的な保守性、移植性、そしてガベージコレクタの精度向上を妨げる要因となっていました。

Go 1.4では、ランタイムの大部分をCからGoへ書き換えるという大きな変更が行われました。これにより、より正確なガベージコレクタの実装が可能になり、Goコンパイラの最適化能力を最大限に活用することでパフォーマンスの向上も期待されました。このコミットは、Solarisプラットフォームにおけるシステムコール実装をこのGo言語化の潮流に乗せるものであり、`syscall_solaris.goc`を廃止し、Go言語で書かれた新しい実装に置き換えることで、ランタイムのC依存性をさらに低減することを目的としています。

## 前提知識の解説

このコミットの理解を深めるために、以下の概念について解説します。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するGo言語のコア部分です。ガベージコレクション、ゴルーチンのスケジューリング、メモリ管理、システムコールとの連携など、プログラムの動作に不可欠な低レベルな機能を提供します。Go 1.4以降、その多くがGo言語自体で記述されるようになりました。

*   **システムコール (Syscalls)**: オペレーティングシステム (OS) が提供するサービスをプログラムが利用するためのインターフェースです。ファイルI/O、プロセス管理、ネットワーク通信など、OSカーネルの機能にアクセスするために不可欠です。GoプログラムがOSと対話する際には、内部的にシステムコールが発行されます。

*   **`cgo`と`.goc`ファイル**: `cgo`はGoプログラムからC言語のコードを呼び出すためのGoのツールです。GoのコードとCのコードを連携させるために使用されます。`.goc`ファイルは、GoとCのコードを一つのファイルに混在させるための特殊なファイル形式で、Goの初期のバージョンで低レベルなOSインタラクションなどに用いられていました。しかし、GoランタイムのGo言語化の進展に伴い、その使用は段階的に廃止されていきました。

*   **Solaris OS**: Sun Microsystems（現在はOracleが所有）によって開発されたUNIXベースのオペレーティングシステムです。Goは公式にSolaris 11以降の`amd64`アーキテクチャをサポートしています。このコミットは、GoがSolaris環境で効率的に動作するための基盤の一部を形成しています。

*   **アセンブリ言語 (Assembly Language) とGo**: Goのランタイムや一部の低レベルな操作では、パフォーマンスの最適化やOSとの直接的なインターフェースのためにアセンブリ言語が使用されることがあります。GoとCの間のコンテキストスイッチや、特定のCPU命令へのアクセスが必要な場合に利用されます。

*   **`dynimport` pragma**: Goコンパイラに対する特殊な指示（プラグマ）の一つで、C言語の共有ライブラリから動的にシンボル（関数や変数）をインポートするために使用されます。これは、`//go:cgo_import_dynamic`というGoのプラグマの別名であり、Goプログラムが実行時に外部のCライブラリの関数を呼び出す際に、その関数のアドレスを解決するために利用されます。

*   **`runtime.cgocall` と `runtime.asmcgocall`**: Goの`cgo`メカニズムにおいて、GoコードからCコードを呼び出す際に使用されるランタイム関数です。
    *   `runtime.cgocall`: GoからCへの呼び出しを調整する高レベルなGoランタイム関数です。ゴルーチンをOSスレッドにロックし、GoスケジューラにCコードの実行を通知（`entersyscall`）し、C関数が完了した後にクリーンアップ（`exitsyscall`）を行います。
    *   `runtime.asmcgocall`: アセンブリ言語で実装された関数で、GoとCの実行コンテキストを切り替える低レベルな詳細を処理します。GoのゴルーチンのスタックからOSスレッドに割り当てられた`g0`スタック（Cコードの実行に安全なスタック）への切り替えを行い、C関数を呼び出し、完了後にGoスタックに戻ります。これらの関数は、GoとCの間のコンテキストスイッチのオーバーヘッドを伴います。

*   **`//go:nosplit`**: Goコンパイラに対するプラグマの一つで、関数がスタックを拡張しないことを保証します。システムコールのような低レベルな関数では、スタックの拡張が予期せぬ問題を引き起こす可能性があるため、この指示が使われます。

## 技術的詳細

このコミットの技術的な核心は、Solarisシステムコールを扱うためのGoランタイムの内部実装を、C言語とGoの混合コード（`.goc`ファイル）から、より純粋なGo言語ベースの構造へと移行した点にあります。

1.  **`syscall_solaris.goc`の廃止と置き換え**:
    *   従来の`src/pkg/runtime/syscall_solaris.goc`は削除されました。このファイルは、CのプリプロセッサディレクティブとGoのコードが混在しており、Goのビルドシステムやランタイムの進化において複雑さの原因となっていました。
    *   その機能は主に`src/pkg/runtime/syscall_solaris.go`に移行されました。この新しいGoファイルは、SolarisのシステムコールをGoの関数としてラップし、Goランタイムがこれらのシステムコールを呼び出すためのインターフェースを提供します。

2.  **Cライブラリ関数の動的インポート (`syscall_solaris.c`)**:
    *   `src/pkg/runtime/syscall_solaris.c`という新しいCファイルが導入されました。このファイルは、GoランタイムがSolarisの標準Cライブラリ（`libc.so`）から動的にインポートする必要があるシステムコール関数（例: `chdir`, `close`, `execve`, `wait4`など）を宣言しています。
    *   `#pragma dynimport`ディレクティブが使用されており、これはGoコンパイラに対して、指定されたCライブラリ関数を動的にリンクするように指示します。これにより、Goコードは直接Cライブラリの関数ポインタを参照できるようになります。

3.  **アセンブリによるGoとCの橋渡し (`thunk_solaris_amd64.s`)**:
    *   `src/pkg/runtime/thunk_solaris_amd64.s`という新しいアセンブリファイルが追加されました。このファイルは、`syscall_solaris.c`で宣言されたCライブラリ関数へのジャンプテーブル（または「サンク」）を提供します。
    *   Goのコードが`libc_chdir`のようなCライブラリ関数を呼び出す際、実際にはこのアセンブリコードを経由して、対応するCライブラリ関数のエントリポイントへジャンプします。これにより、GoのランタイムはCライブラリ関数を直接呼び出すことができます。

4.  **Go言語でのシステムコールラッパーの実装 (`syscall_solaris.go`)**:
    *   `syscall_solaris.go`では、`libc_chdir`などのCライブラリ関数へのポインタが`uintptr`型で宣言されています。
    *   `libcall`構造体と`asmcgocall`関数が、GoからC関数を呼び出すための汎用的なメカニズムとして使用されています。`libcall`は呼び出すC関数のポインタ、引数の数、引数へのポインタを保持します。
    *   `asmcgocall`は、GoのスタックからCのスタックへの切り替え、C関数の実行、そして結果のGoへの戻りをアセンブリレベルで処理します。
    *   多くのシステムコールラッパー関数（例: `syscall_chdir`, `syscall_execve`）には`//go:nosplit`プラグマが付与されています。これは、これらの関数がスタックを拡張しないことを保証し、システムコール実行中のスタック管理の複雑さを軽減します。
    *   `entersyscallblock()`と`exitsyscall()`は、Goスケジューラに対して、システムコールが開始されることと終了することを通知します。これにより、Goランタイムはシステムコール中のゴルーチンの状態を適切に管理し、他のゴルーチンの実行をブロックしないようにします。

5.  **`syscall`パッケージの変更 (`asm_solaris_amd64.s`, `so_solaris.go`)**:
    *   `src/pkg/syscall/asm_solaris_amd64.s`が修正され、`syscall`パッケージの関数が、新しい`runtime`パッケージ内のGoで実装されたシステムコールラッパー関数（例: `runtime·syscall_chdir`）にジャンプするように変更されました。これにより、`syscall`パッケージのユーザーは、内部実装がGoに移行したことを意識することなく、引き続きシステムコールを利用できます。
    *   `src/pkg/syscall/so_solaris.go`のコメントが更新され、システムコールが`syscall_solaris.goc`ではなく`asm_solaris_amd64.s`で実装されていることが示されました。

この変更により、GoランタイムはSolarisシステムコールをよりGoらしい方法で扱うことができるようになり、将来的なGoランタイムの改善や他のプラットフォームへの移植が容易になります。

    *   `syscall_solaris.c`で宣言されたCライブラリ関数へのジャンプを行うアセンブリサンク（thunk）が定義されています。Goコードが`runtime·libc_chdir`のようなシンボルを呼び出すと、このアセンブリコードが対応するCライブラリ関数へ制御を移します。

5.  **`src/pkg/syscall/asm_solaris_amd64.s` (変更)**:
    *   `syscall`パッケージ内のアセンブリ関数（例: `·chdir`, `·close`）が、新しい`runtime`パッケージ内のGoで実装された対応するシステムコールラッパー関数（例: `runtime·syscall_chdir`）にジャンプするように変更されました。これにより、`syscall`パッケージの公開APIは維持されつつ、その内部実装がGoランタイムの新しいGoコードに委譲されます。

6.  **`src/pkg/syscall/so_solaris.go` (変更)**:
    *   コメントが更新され、システムコールの実装が`syscall_solaris.goc`から`asm_solaris_amd64.s`に移行したことが反映されました。

これらの変更により、Solarisにおけるシステムコール処理の大部分がGo言語で記述されるようになり、GoランタイムのC言語依存性が大幅に削減されました。

## コアとなるコードの解説

`src/pkg/runtime/syscall_solaris.go`がこのコミットの核心であり、Go言語でシステムコールをラップする方法を示しています。

```go
package runtime

import "unsafe"

var (
	libc_chdir,
	libc_chroot,
	// ... (他のlibc関数へのポインタ)
	libc_write,
	pipe1 libcFunc
)

//go:nosplit
func syscall_sysvicall6(fn, nargs, a1, a2, a3, a4, a5, a6 uintptr) (r1, r2, err uintptr) {
	call := libcall{
		fn:   unsafe.Pointer(fn),
		n:    nargs,
		args: unsafe.Pointer(&a1),
	}
	entersyscallblock() // システムコールブロックに入ることをスケジューラに通知
	asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(&call)) // アセンブリ経由でC関数を呼び出し
	exitsyscall()       // システムコールブロックから出ることをスケジューラに通知
	return call.r1, call.r2, call.err
}

//go:nosplit
func syscall_chdir(path uintptr) (err uintptr) {
	call := libcall{
		fn:   unsafe.Pointer(&libc_chdir), // libc_chdirへのポインタ
		n:    1,                           // 引数の数
		args: unsafe.Pointer(&path),       // 引数へのポインタ
	}
	asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(&call))
	return call.err
}

// ... (他のシステムコールラッパー関数)
```

*   **`var (...)` ブロック**: `libc_chdir`などの変数は、`src/pkg/runtime/syscall_solaris.c`で`#pragma dynimport`によって動的にインポートされるCライブラリ関数のエントリポイント（アドレス）を保持するための`uintptr`型の変数です。Goコードはこれらの変数を通じてC関数を間接的に呼び出します。

*   **`syscall_sysvicall6` 関数**:
    *   これは、GoからC関数を呼び出すための汎用的なラッパーです。`fn`は呼び出すC関数のアドレス、`nargs`は引数の数、`a1`から`a6`は引数です。
    *   `libcall`構造体は、C関数呼び出しに必要な情報をカプセル化します。
    *   `entersyscallblock()`と`exitsyscall()`は、Goランタイムのスケジューラと連携し、システムコールが開始される前と終了した後に適切な処理（例: ゴルーチンのOSスレッドへの固定、GCの停止など）を行うために呼び出されます。これにより、システムコールがGoのスケジューリングやガベージコレクションに悪影響を与えないようにします。
    *   `asmcgocall`は、アセンブリ言語で実装された低レベルな関数で、GoのスタックからCのスタックへの切り替え、C関数の実行、そして結果のGoへの戻りを担当します。

*   **`syscall_chdir` 関数**:
    *   これは、`chdir`システムコール（ディレクトリ変更）をGoから呼び出すための具体的なラッパー関数です。
    *   `libcall`構造体を初期化し、`libc_chdir`（Cライブラリの`chdir`関数のアドレス）と引数（`path`）を設定します。
    *   `asmcgocall`を呼び出して、実際のC関数呼び出しを実行します。
    *   `//go:nosplit`プラグマは、この関数が実行中にGoのスタックを拡張しないことを保証します。これは、システムコールのような低レベルな操作では、スタックの動的な変更が問題を引き起こす可能性があるため重要です。

この構造により、GoランタイムはC言語のコードを直接埋め込むことなく、SolarisのシステムコールをGo言語から安全かつ効率的に呼び出すことが可能になります。

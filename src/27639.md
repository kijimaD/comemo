## 変更の背景
このコミットの主な目的は、Goランタイムにおける64ビットアーキテクチャ向けのロックフリースタック（lfstack）の実装を統合し、コードの重複を削減し、保守性を向上させることです。これまで、異なる64ビットアーキテクチャ（例: arm64, mips64, ppc64）ごとにほぼ同一の`lfstack`実装ファイルが存在していました。これらのファイルは、ポインタとカウンタを単一の64ビットワードにパック/アンパックするためのロジックを共有していましたが、それぞれが独自のビルドタグを持っていました。

この重複を解消し、共通のコードベースを維持するために、これらの実装を一つの汎用的な`lfstack_64bit.go`ファイルに集約することが決定されました。これにより、将来的な変更やバグ修正が容易になり、コードベース全体の複雑さが軽減されます。コミットメッセージには、`lfstack_amd64.go`も同様に統合される可能性があるが、わずかに異なるため後続のコミットで対応すると記載されており、段階的なリファクタリングのアプローチが示唆されています。

## 前提知識の解説

### ロックフリースタック (Lock-Free Stack)
ロックフリーデータ構造は、複数のゴルーチン（またはスレッド）が同時にアクセスしても、ミューテックスなどのロック機構を使用せずに正しく動作するように設計されたデータ構造です。これにより、ロックの競合による性能低下を防ぎ、システムの並行性を高めることができます。スタックはLIFO（Last-In, First-Out）の原則に従うデータ構造であり、ロックフリースタックは、`Push`（要素の追加）や`Pop`（要素の削除）操作がアトミックに行われることを保証します。

ロックフリーアルゴリズムでは、一般的にCompare-And-Swap (CAS) などのアトミック操作が用いられます。しかし、CAS操作だけでは「ABA問題」という特定の競合状態が発生する可能性があります。ABA問題とは、ある値がAからBに変化し、その後再びAに戻った場合、CAS操作がその変化を検出できないという問題です。ロックフリースタックでは、このABA問題を回避するために、ポインタと一緒に「カウンタ」を組み合わせた64ビットワードを使用することが一般的です。ポインタが指すアドレスだけでなく、そのポインタが何回更新されたかを示すカウンタも一緒にアトミックに更新することで、ABA問題を検出・回避します。

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する重要なコンポーネントです。これには、ゴルーチン（軽量スレッド）のスケジューリング、ガベージコレクション（GC）、メモリ割り当て、チャネル通信、および低レベルのシステムコールインターフェースなどが含まれます。Goランタイムは、Goプログラムが効率的かつ並行に動作するための基盤を提供します。ロックフリースタックのようなデータ構造は、ランタイム内部でゴルーチンのスケジューリングやメモリ管理などのクリティカルな部分で利用され、高いパフォーマンスとスケーラビリティを実現しています。

### ビルドタグ (Build Tags)
Go言語では、ソースコードファイルに特別なコメント行を追加することで、特定の条件に基づいてファイルをコンパイルに含めるか除外するかを制御できます。これを「ビルドタグ」と呼びます。`// +build <tag>` の形式で記述され、複数のタグをスペースで区切って指定したり、カンマで区切ってOR条件を表したりできます。このコミットでは、`// +build ppc64 ppc64le` のような行が `// +build arm64 mips64 mips64le ppc64 ppc64le` に変更されており、これにより`lfstack_64bit.go`ファイルがより多くの64ビットアーキテクチャでコンパイルされるようになります。

### `lfnode`, `lfstackPack`, `lfstackUnpack`, `addrBits`, `cntBits`
*   **`lfnode`**: ロックフリースタックの各要素（ノード）を表す構造体です。通常、次のノードへのポインタと、そのノードが保持するデータを含みます。
*   **`lfstackPack`**: `*lfnode`型のポインタと`uintptr`型のカウンタを結合し、単一の`uint64`値にパックする関数です。このパックされた値は、アトミックなCAS操作などで使用されます。
*   **`lfstackUnpack`**: `lfstackPack`によってパックされた`uint64`値から、元の`*lfnode`ポインタとカウンタを抽出する関数です。
*   **`addrBits`**: 64ビットワードのうち、アドレス（ポインタ）部分に割り当てるビット数を定義する定数です。このコミットでは`48`に設定されています。これは、多くの64ビットシステムでユーザー空間のアドレスが64ビットすべてを使用せず、上位ビットが未使用であるという事実に基づいています（例: Linuxカーネルの`TASK_SIZE_USER64`や`TASK_SIZE64`）。
*   **`cntBits`**: 64ビットワードのうち、カウンタ部分に割り当てるビット数を定義する定数です。`64 - addrBits + 3`と計算されます。`+3`は、ポインタがアラインされている（通常8バイトアライン）ため、下位3ビットが常に0であることを利用して、その3ビットもカウンタとして再利用できることを意味します。これにより、カウンタの表現可能な範囲が広がります。

4.  **コメントの追加**:
    `lfstack_64bit.go`には、`mips64`におけるLinuxのユーザーアドレス空間の制限（40ビットだが、48ビットを許容）に関するコメントが追加されました。これは、このファイルがカバーするアーキテクチャの範囲が広がったことに伴い、より包括的な情報を提供するものです。

この統合は、GoランタイムのコードベースをよりDRY（Don't Repeat Yourself）にし、将来的なメンテナンスコストを削減するための重要なステップです。`lfstack_amd64.go`がこの統合に含まれていないのは、その実装が他の64ビットアーキテクチャと比べてわずかに異なるためであり、これは慎重なリファクタリングアプローチを示しています。

## コアとなるコードの解説

統合された`lfstack_64bit.go`ファイルに含まれる`lfstackPack`と`lfstackUnpack`関数は、Goランタイムのロックフリースタック実装において、ポインタとカウンタを単一の`uint64`値に効率的に格納し、またそこから復元するための中心的な役割を担います。これは、アトミックなCAS (Compare-And-Swap) 操作でポインタとカウンタを同時に更新するために不可欠です。

```go
// +build arm64 mips64 mips64le ppc64 ppc64le

package runtime

import "unsafe"

// On ppc64, Linux limits the user address space to 48 bits (see
// TASK_SIZE_USER64 in the Linux kernel).  This has grown over time,
// so here we allow 48 bit addresses.
//
// On mips64, Linux limits the user address space to 40 bits (see
// TASK_SIZE64 in the Linux kernel).  This has grown over time,
// so here we allow 48 bit addresses.
//
// In addition to the 16 bits taken from the top, we can take 3 from the
// bottom, because node must be pointer-aligned, giving a total of 19 bits
// of count.
const (
	addrBits = 48
	cntBits  = 64 - addrBits + 3
)

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
}

func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr) {
	node = (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
	cnt = uintptr(val & (1<<cntBits - 1))
	return
}
```

### 定数 `addrBits` と `cntBits`

*   **`addrBits = 48`**:
    これは、64ビットのワードのうち、ポインタのアドレス部分に割り当てられるビット数を示します。多くの64ビットシステムでは、ユーザー空間のアドレスは実際には64ビットすべてを使用せず、上位ビットが常に0であるか、特定の範囲に制限されています。例えば、Linuxカーネルの`TASK_SIZE_USER64`や`TASK_SIZE64`は、ユーザープロセスがアクセスできるアドレス空間の上限を定義しており、これが48ビットに収まることが多いです。これにより、残りの`64 - 48 = 16`ビットをカウンタのために利用できることになります。

*   **`cntBits = 64 - addrBits + 3`**:
    カウンタに割り当てられるビット数です。`64 - addrBits`はアドレスの上位ビットから得られる16ビットです。これに`+3`が加算されています。この`+3`は、`node`（ポインタ）が常にポインタアラインされている（例えば、64ビットシステムでは8バイトアライン）という事実を利用しています。8バイトアラインされたアドレスは、常に下位3ビットが0になります。したがって、これらの下位3ビットもカウンタとして再利用できるため、カウンタの合計ビット数は`16 + 3 = 19`ビットとなります。19ビットのカウンタは`2^19 = 524,288`までの値を表現でき、ABA問題を効果的に防ぐのに十分な範囲を提供します。

### 関数 `lfstackPack`

`func lfstackPack(node *lfnode, cnt uintptr) uint64`

この関数は、`*lfnode`型のポインタ`node`と`uintptr`型のカウンタ`cnt`を受け取り、これらを単一の`uint64`値にパックします。

1.  `uintptr(unsafe.Pointer(node))`: `*lfnode`ポインタを`uintptr`（符号なし整数）に変換し、そのアドレス値を取得します。
2.  `<<(64-addrBits)`: 取得したアドレス値を左に`64 - addrBits`ビット（この場合`64 - 48 = 16`ビット）シフトします。これにより、アドレス値が`uint64`の上位48ビットに配置され、下位16ビットが空きます。
3.  `uint64(cnt&(1<<cntBits-1))`: カウンタ`cnt`から、`cntBits`で定義されたビット数（19ビット）だけを抽出します。`1<<cntBits-1`は、`cntBits`個の1が並んだビットマスクを生成します（例: `cntBits=19`なら`0x7FFFF`）。`&`演算子でこのマスクを適用することで、カウンタの関連するビットのみが保持されます。
4.  `|`: シフトされたアドレス値とマスクされたカウンタ値をビットOR演算で結合します。これにより、アドレスが上位48ビットに、カウンタが下位19ビット（アドレスの下位3ビットを含む）に格納された単一の`uint64`値が生成されます。

### 関数 `lfstackUnpack`

`func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr)`

この関数は、`lfstackPack`によってパックされた`uint64`値`val`を受け取り、元の`*lfnode`ポインタとカウンタを復元します。

1.  **ポインタの復元**:
    *   `val >> cntBits`: `val`を右に`cntBits`ビット（19ビット）シフトします。これにより、カウンタ部分が取り除かれ、アドレス部分が`uint64`の下位に移動します。
    *   `<< 3`: その結果を左に3ビットシフトします。これは、`lfstackPack`でカウンタのために利用されたアドレスの下位3ビットを元に戻す操作です。これにより、元のポインタアドレスが復元されます。
    *   `uintptr(...)`: 復元されたアドレス値を`uintptr`に変換します。
    *   `(*lfnode)(unsafe.Pointer(...))`: `uintptr`を`unsafe.Pointer`を介して`*lfnode`ポインタに型変換します。

2.  **カウンタの復元**:
    *   `val & (1<<cntBits - 1)`: `val`に対して、`cntBits`で定義されたビット数（19ビット）のマスクを適用します。これにより、`val`の下位19ビット（カウンタ部分）のみが抽出されます。
    *   `uintptr(...)`: 抽出されたカウンタ値を`uintptr`に型変換します。

これらの関数は、Goランタイムがロックフリースタックを効率的かつ安全に操作するための基盤を提供し、特にABA問題の回避に貢献します。

# [インデックス 27948] ファイルの概要

このコミットは、Go言語のテストフレームワークにおいて、`go test -run` および `go test -bench` コマンドがサブテストやサブベンチマークをマッチングする際の正規表現の挙動を改善するものです。特に、サブテスト名にスラッシュ (`/`) が含まれる場合に、より直感的で堅牢なマッチングを可能にするための変更が導入されました。これにより、`go test` が出力するテスト/ベンチマーク識別子をそのままコピー＆ペーストしてフィルタリングできるようになります。

## コミット

```
testing: add matching of subtest

Allows passing regexps per subtest to --test.run and --test.bench

Note that the documentation explicitly states that the split regular
expressions match the correpsonding parts (path components) of
the bench/test identifier. This is intended and slightly different
from the i'th RE matching the subtest/subbench at the respective
level. Picking this semantics allows guaranteeing that a test or
benchmark identifier as printed by go test can be passed verbatim
(possibly quoted) to, respectively, -run or -bench: subtests and
subbenches might have a '/' in their name, causing a misaligment if
their ID is passed to -run or -bench as is.
This semantics has other benefits, but this is the main motivation.
```

## 変更の背景

Goのテストフレームワークでは、`go test -run <regexp>` や `go test -bench <regexp>` コマンドを使用して、特定のテストやベンチマークを実行できます。Go 1.7で導入されたサブテスト/サブベンチマーク機能により、テスト名が `ParentTest/SubTestName` のような階層構造を持つようになりました。

しかし、従来の正規表現マッチングでは、サブテスト名自体にスラッシュ (`/`) が含まれている場合に問題が発生する可能性がありました。例えば、`TestFoo/bar/baz` というサブテストがあった場合、ユーザーが `-run "TestFoo/bar/baz"` と指定しても、内部的なマッチングロジックがスラッシュを階層の区切りと誤解し、意図しない結果を招くことがありました。

このコミットの主な動機は、`go test` が出力するテストまたはベンチマークの識別子（例: `TestFoo/bar/baz`）を、ユーザーが `-run` や `-bench` フラグにそのまま（必要に応じて引用符で囲んで）渡せるようにすることです。これにより、ユーザーはテスト結果からコピーした名前を直接使用して、特定のサブテストを再実行できるようになり、開発者の利便性が大幅に向上します。この問題は `golang.go#15126` で報告されていました。

## 前提知識の解説

### Goのテストとベンチマーク

Go言語には、標準ライブラリ `testing` パッケージによる強力なテストおよびベンチマーク機能が組み込まれています。
*   **テスト関数**: `func TestXxx(t *testing.T)` の形式で定義され、`go test` コマンドで実行されます。
*   **ベンチマーク関数**: `func BenchmarkXxx(b *testing.B)` の形式で定義され、`go test -bench .` コマンドで実行されます。
*   **サブテスト/サブベンチマーク**: `t.Run("SubTestName", func(t *testing.T) { ... })` や `b.Run("SubBenchName", func(b *testing.B) { ... })` を使用して、テストやベンチマークを階層的に構成できます。これにより、関連するテストをグループ化し、より詳細な制御が可能になります。サブテストの完全な識別子は、親テスト名とサブテスト名をスラッシュで連結した形式（例: `TestParent/SubChild`）になります。

### `go test -run` と `go test -bench`

これらのコマンドは、実行するテストやベンチマークをフィルタリングするために正規表現を使用します。
*   `-run <regexp>`: 指定された正規表現にマッチするテスト関数およびサブテストのみを実行します。
*   `-bench <regexp>`: 指定された正規表現にマッチするベンチマーク関数およびサブベンチマークのみを実行します。

### 正規表現 (Regular Expressions)

正規表現は、文字列のパターンを記述するための強力なツールです。Goの `regexp` パッケージは、RE2構文をサポートしており、効率的なパターンマッチングを提供します。
このコミットでは、特に正規表現の構文要素（`[`, `]`, `(`, `)`, `\`）がスラッシュ (`/`) と組み合わされた場合に、どのようにパターンを分割するかが重要になります。

## 技術的詳細

この変更の核心は、`go test -run` や `go test -bench` に渡される正規表現パターンを、トップレベルのスラッシュ (`/`) で分割し、それぞれの部分がテスト/ベンチマーク識別子の対応する「パスコンポーネント」にマッチするようにすることです。

具体的には、以下の点が技術的な詳細として挙げられます。

1.  **正規表現の分割ロジック**:
    *   新しい `splitRegexp` 関数が `src/testing/match.go` に追加されました。この関数は、入力された正規表現文字列をトップレベルのスラッシュ (`/`) で分割します。
    *   「トップレベル」とは、正規表現のグループ化（`(` と `)`）や文字クラス（`[` と `]`）の内部にないスラッシュを意味します。これにより、例えば `TestFoo/(bar/baz)` のようなパターンが `TestFoo` と `(bar/baz)` に分割されず、`TestFoo/(bar/baz)` 全体が1つのコンポーネントとして扱われるようになります。
    *   バックスラッシュ (`\`) によるエスケープも考慮され、`\/` のようなエスケープされたスラッシュは分割の対象外となります。
    *   このロジックは、正規表現の構文解析を模倣し、括弧やブラケットのネストレベルを追跡することで実現されています。

2.  **`matcher` 構造体の変更**:
    *   `src/testing/match.go` の `matcher` 構造体の `filter` フィールドが、単一の文字列から `[]string` (文字列スライス) に変更されました。これは、分割された複数の正規表現パターンを保持するためです。

3.  **マッチングロジックの更新**:
    *   `matcher.fullName` メソッドが変更され、テスト/ベンチマークの完全な名前（例: `TestParent/SubChild/GrandChild`）をスラッシュで分割し、それぞれのコンポーネントに対して `matcher` の `filter` スライス内の対応する正規表現をマッチングするようになりました。
    *   例えば、`-run "TestA/SubB"` というパターンが与えられた場合、`splitRegexp` は `["TestA", "SubB"]` を返します。`matcher.fullName` は、テスト名 `TestA/SubB/SubC` を `["TestA", "SubB", "SubC"]` に分割し、`TestA` が `filter[0]` (`TestA`) に、`SubB` が `filter[1]` (`SubB`) にマッチするかを個別に確認します。

4.  **ドキュメントの更新**:
    *   `src/cmd/go/alldocs.go` と `src/cmd/go/test.go` の `go help test` の出力が更新され、`-bench` と `-run` フラグが「トップレベルのスラッシュ (`/`) で分割され、それぞれの部分がベンチマーク/テスト識別子の対応する部分にマッチする」という新しい挙動を明確に説明するようになりました。

この変更により、ユーザーはサブテスト名にスラッシュが含まれていても、`go test` が出力する名前をそのまま使用してフィルタリングできるようになり、より直感的で予測可能な挙動が実現されます。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/testing/match.go` に追加された `splitRegexp` 関数と、それを利用するように変更された `matcher` 構造体のロジックです。

### `splitRegexp` 関数の解説

```go
func splitRegexp(s string) []string {
	a := make([]string, 0, strings.Count(s, "/"))
	cs := 0 // character class nesting level (for '[')
	cp := 0 // parenthesis nesting level (for '(')
	for i := 0; i < len(s); {
		switch s[i] {
		case '[':
			cs++
		case ']':
			if cs--; cs < 0 { // An unmatched ']' is legal.
				cs = 0
			}
		case '(':
			if cs == 0 { // Only count if not inside a character class
				cp++
			}
		case ')':
			if cs == 0 { // Only count if not inside a character class
				cp--
			}
		case '\\': // Escape character
			i++ // Skip next character
		case '/':
			if cs == 0 && cp == 0 { // Only split if not inside character class or parenthesis
				a = append(a, s[:i])
				s = s[i+1:]
				i = 0 // Reset index for the new string
				continue
			}
		}
		i++
	}
	return append(a, s) // Append the last part
}
```

この関数は、正規表現パターン文字列 `s` を受け取り、トップレベルのスラッシュ (`/`) で分割された文字列のスライスを返します。

*   `cs` (character class nesting level): `[` と `]` のネストレベルを追跡します。`[` が見つかるとインクリメントされ、`]` が見つかるとデクリメントされます。
*   `cp` (parenthesis nesting level): `(` と `)` のネストレベルを追跡します。`(` が見つかるとインクリメントされ、`)` が見つかるとデクリメントされます。ただし、文字クラスの内部にある場合はカウントしません。
*   ループは文字列 `s` を1文字ずつ走査します。
*   `\` (バックスラッシュ) が見つかった場合、次の文字はエスケープされているとみなし、その文字をスキップします。これにより、`\/` のようなエスケープされたスラッシュが分割の対象とならないようにします。
*   `/` が見つかった場合、`cs` と `cp` が両方とも `0` であれば（つまり、文字クラスや括弧の内部にないトップレベルのスラッシュであれば）、その位置で文字列を分割し、現在の部分を結果スライス `a` に追加します。そして、残りの文字列を新しい `s` として設定し、インデックス `i` をリセットして次の部分の処理を開始します。
*   ループが終了した後、最後に残った文字列の部分を `a` に追加して返します。

このロジックにより、`TestFoo/[a-z]/bar` のようなパターンは `TestFoo` と `[a-z]` と `bar` に分割され、`TestFoo/(a|b)/bar` のようなパターンは `TestFoo` と `(a|b)` と `bar` に分割されます。これにより、正規表現の構文を尊重しつつ、テスト識別子の階層構造に合わせた分割が可能になります。

### `matcher.fullName` の変更点の解説

変更後の `matcher.fullName` は、以下のロジックでマッチングを行います。

```go
func (m *matcher) fullName(c *common, subname string) (name string, ok bool) {
	// ... (既存のロック処理など) ...

	// We check the full array of paths each time to allow for the case that
	// a pattern contains a '/'.
	for i, s := range strings.Split(name, "/") { // テスト/ベンチマーク名をスラッシュで分割
		if i >= len(m.filter) { // 分割された正規表現の数を超えたら、残りの部分はマッチング不要
			break
		}
		if ok, _ := m.matchFunc(m.filter[i], s); !ok { // 各部分を対応する正規表現でマッチング
			return name, false // 一つでもマッチしなければ失敗
		}
	}
	return name, true // 全てマッチすれば成功
}
```

*   `strings.Split(name, "/")` を使用して、テスト/ベンチマークの完全な識別子（例: `TestParent/SubChild`）をスラッシュで分割します。
*   分割された各コンポーネント（例: `TestParent`, `SubChild`）に対して、`m.filter` スライスに格納されている対応する正規表現（`m.filter[i]`）を使用してマッチングを行います。
*   もし、テスト識別子のコンポーネント数が `m.filter` の正規表現の数を超えた場合、残りのコンポーネントは自動的にマッチするとみなされます（`break` してループを抜ける）。これは、例えば `-run "TestA"` と指定した場合に `TestA/SubB` もマッチさせる挙動に対応します。
*   いずれかのコンポーネントが対応する正規表現にマッチしなかった場合、`fullName` は `false` を返します。
*   すべてのコンポーネントがマッチした場合、`true` を返します。

この新しいロジックにより、ユーザーが `-run "TestFoo/bar/baz"` と指定した場合、`TestFoo` は最初の正規表現に、`bar` は2番目の正規表現に、`baz` は3番目の正規表現にそれぞれマッチングされるようになります。これにより、サブテスト名にスラッシュが含まれていても、意図した通りのフィルタリングが可能になります。

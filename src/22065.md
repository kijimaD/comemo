# [インデックス 22065] ファイルの概要

このコミットは、Goのアセンブラ (`cmd/asm`) のビルドプロセスにおける、壊れたエンドツーエンドテストを修正することを目的としています。

## 変更の背景

この変更の背景には、Go言語のツールチェイン、特にアセンブラ (`cmd/asm`) のテストインフラストラクチャにおける特定の課題がありました。`cmd/asm` はGoプログラムが利用するアセンブリコードを処理するための重要なコンポーネントであり、その正確性はGoプログラム全体の動作に直結します。

コミットメッセージにある「broken end to end test」という記述は、アセンブラの出力結果を検証するテストが、何らかの理由で期待通りに動作していなかったことを示唆しています。特に、`src/cmd/asm/internal/asm/testdata/arm.s` というARMアセンブリのテストファイルと、その期待される出力結果を記述した `src/cmd/asm/internal/asm/testdata/arm.out` ファイルが関係しています。

問題の核心は、`MRC` (Move to ARM Register from Coprocessor) 命令の出力形式が、ビルドを実行するマシンのアーキテクチャ（32ビットまたは64ビット）によって異なっていた点にあります。エンドツーエンドテストでは、アセンブラが生成した出力と `arm.out` に記述された期待される出力を比較します。この比較において、`MRC` 命令の出力形式の差異が原因で不一致が生じ、テストが失敗していました。

この不整合を解消し、ビルドプロセスを正常化するために、一時的な措置として `MRC` 命令のテストを無効化し、それに伴い `arm.out` ファイル内の行番号の参照を調整する必要がありました。これは、根本的な解決（32ビットと64ビット環境での`MRC`命令の出力形式の統一）が行われるまでの暫定的な対応と考えられます。

## 前提知識の解説

### Goの`cmd/asm`

`cmd/asm` はGo言語のツールチェインの一部であり、Goプログラムが利用するアセンブリコードをアセンブル（機械語に変換）するためのアセンブラです。Go言語は、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある場合に、Goのアセンブリ言語（Plan 9アセンブリに似た独自の構文を持つ）を使用します。`cmd/asm` は、これらのアセンブリソースファイルをオブジェクトファイルに変換する役割を担います。

### ARMアーキテクチャ

ARM (Advanced RISC Machine) は、組み込みシステム、モバイルデバイス（スマートフォン、タブレット）、IoTデバイスなどで広く使用されているRISC (Reduced Instruction Set Computer) プロセッサアーキテクチャです。低消費電力と高性能を両立させる設計が特徴です。ARMプロセッサは、汎用レジスタ、コプロセッサ、特定の命令セットなど、独自のアーキテクチャ的特徴を持っています。

### `MRC`命令 (Move to ARM Register from Coprocessor)

`MRC` はARMアーキテクチャにおける命令の一つで、「Move to ARM Register from Coprocessor」の略です。この命令は、ARMプロセッサの汎用レジスタとコプロセッサのレジスタ間でデータを転送するために使用されます。

*   **コプロセッサ**: ARMアーキテクチャでは、メインのCPUコアとは別に、特定の機能（浮動小数点演算、メモリ管理、システム制御など）を高速化するための専用の処理ユニットを「コプロセッサ」と呼びます。
*   **CP15 (System Control Coprocessor)**: 特に重要なコプロセッサの一つがCP15です。CP15は、メモリ管理ユニット (MMU)、キャッシュ制御、システムレジスタへのアクセスなど、システムレベルの制御機能を提供します。`MRC`命令は、CP15のようなコプロセッサからシステムの状態や設定情報を読み出す際によく使用されます。例えば、キャッシュの状態を読み取ったり、MMUの設定を確認したりするために使われます。

`MRC`命令の構文は通常、`MRC{cond} p#, opc1, Rd, Cn, Cm{, opc2}` のようになります。ここで、`p#` はコプロセッサ番号（例: `p15`）、`opc1` と `opc2` はコプロセッサ固有の操作コード、`Rd` はARM汎用レジスタ、`Cn` と `Cm` はコプロセッサレジスタを示します。

### エンドツーエンドテスト

エンドツーエンドテスト (End-to-End Testing, E2E Testing) は、ソフトウェアシステム全体が、ユーザーの視点から期待通りに動作するかどうかを検証するテスト手法です。これは、個々のコンポーネントやモジュールが正しく機能するかを検証する単体テストや結合テストとは異なり、システム全体のフロー（ユーザーインターフェースからデータベース、外部サービス連携まで）を網羅的にテストします。

`cmd/asm` の文脈では、アセンブラがアセンブリコードを正しく機械語に変換し、その結果が期待される出力と一致するかどうかを検証するプロセスがエンドツーエンドテストに該当します。このテストが失敗するということは、アセンブラの出力に問題があるか、テストの期待値が現在の環境と合致していないことを意味します。

## 技術的詳細

このコミットの技術的詳細は、主にGoのアセンブラ (`cmd/asm`) がARMアーキテクチャ向けのアセンブリコードを処理する際の、`MRC`命令の出力形式に関する問題に集約されます。

Goのアセンブラは、アセンブリソースファイル (`.s` 拡張子) を読み込み、それを機械語に変換してオブジェクトファイル (`.out` 拡張子) を生成します。このオブジェクトファイルには、アセンブルされた命令のバイナリ表現や、デバッグ情報などが含まれます。エンドツーエンドテストでは、`arm.s` をアセンブルして生成された `arm.out` の内容が、事前に用意された `arm.out` (期待される出力) と完全に一致するかどうかを比較します。

問題となったのは、`MRC`命令のテキスト表現、特にそのオペランドの表示形式が、アセンブラが動作する環境のビット幅（32ビットまたは64ビット）によって異なっていたことです。アセンブリ命令のテキスト表現は、デバッグや解析の際に人間が読みやすいように整形されますが、この整形ルールが環境によって異なると、テストの比較が失敗します。

元の `arm.s` ファイルには、以下のような `MRC` 命令のテストコードが含まれていました（コメントアウトされていますが、その存在が問題を示唆しています）：

```go
// TODO: Representation in printout differs between 32- and 64-bit machines.
// Fix the output in obj/arm and restore this.
// MRC.S	4, 6, R1, C2, C3, 7
```

このコメントは、`MRC`命令の出力形式が32ビットと64ビットのマシンで異なり、それが原因でテストが壊れていることを明確に示しています。アセンブラの出力が環境によって変わることは、クロスコンパイル環境や異なる開発環境でのビルドの再現性を損なうため、非常に厄介な問題です。

このコミットでは、根本的な解決策（`MRC`命令の出力形式を統一する）がまだ実装されていないため、一時的な回避策として、`MRC`命令のテストを完全に無効化しています。具体的には、`arm.out` から `MRC` 命令に関連する行を削除し、`arm.s` からも関連するコメントを更新しています。これにより、テストの比較対象から問題のある行が除外され、テストがパスするようになります。

また、`arm.out` ファイル内の行番号が調整されているのは、`MRC`命令に関連する行が削除されたことで、その後の命令の行番号がずれてしまったためです。テストの比較は厳密に行われるため、このような行番号のずれもテスト失敗の原因となります。

## コアとなるコードの解説

このコミットのコアとなる変更は、`MRC`命令のテストを一時的に無効化することによって、壊れていたエンドツーエンドテストを修正した点にあります。

`arm.s` ファイル内の `MRC` 命令は、元々コメントアウトされていましたが、その上の `TODO` コメントが示すように、アセンブラの出力が32ビットと64ビットの環境で異なるという問題がありました。この問題は、アセンブラが生成する `arm.out` ファイルの内容に影響を与え、テストの比較が失敗する原因となっていました。

具体的には、`arm.out` から `MRC` 命令に関連する行を削除することで、アセンブラの出力と期待される出力との間の不一致を解消しています。これにより、テストは`MRC`命令の出力形式の差異に影響されなくなり、ビルドが正常に完了するようになります。

`arm.s` のコメント変更は、この問題がまだ未解決であり、将来的に`MRC`命令の出力形式が統一された際に、このテストを再度有効化する必要があることを開発者に示唆しています。これは、一時的な回避策であることを明確にするための重要な情報です。

この変更は、Goのツールチェインの安定性を維持し、開発者が異なる環境でGoコードをビルドする際の信頼性を確保するために行われました。

## 技術的詳細

このコミットの技術的詳細は、主にGoのアセンブラ (`cmd/asm`) がARMアーキテクチャ向けのアセンブリコードを処理する際の、`MRC`命令の出力形式に関する問題に集約されます。

Goのアセンブラは、アセンブリソースファイル (`.s` 拡張子) を読み込み、それを機械語に変換してオブジェクトファイル (`.out` 拡張子) を生成します。このオブジェクトファイルには、アセンブルされた命令のバイナリ表現や、デバッグ情報などが含まれます。エンドツーエンドテストでは、`arm.s` をアセンブルして生成された `arm.out` の内容が、事前に用意された `arm.out` (期待される出力) と完全に一致するかどうかを比較します。

問題となったのは、`MRC`命令のテキスト表現、特にそのオペランドの表示形式が、アセンブラが動作する環境のビット幅（32ビットまたは64ビット）によって異なっていたことです。アセンブリ命令のテキスト表現は、デバッグや解析の際に人間が読みやすいように整形されますが、この整形ルールが環境によって異なると、テストの比較が失敗します。

元の `arm.s` ファイルには、以下のような `MRC` 命令のテストコードが含まれていました（コメントアウトされていますが、その存在が問題を示唆しています）：

```go
// TODO: Representation in printout differs between 32- and 64-bit machines.
// Fix the output in obj/arm and restore this.
// MRC.S	4, 6, R1, C2, C3, 7
```

このコメントは、`MRC`命令の出力形式が32ビットと64ビットのマシンで異なり、それが原因でテストが壊れていることを明確に示しています。アセンブラの出力が環境によって変わることは、クロスコンパイル環境や異なる開発環境でのビルドの再現性を損なうため、非常に厄介な問題です。

このコミットでは、根本的な解決策（`MRC`命令の出力形式を統一する）がまだ実装されていないため、一時的な回避策として、`MRC`命令のテストを完全に無効化しています。具体的には、`arm.out` から `MRC` 命令に関連する行を削除し、`arm.s` からも関連するコメントを更新しています。これにより、テストの比較対象から問題のある行が除外され、テストがパスするようになります。

また、`arm.out` ファイル内の行番号が調整されているのは、`MRC`命令に関連する行が削除されたことで、その後の命令の行番号がずれてしまったためです。テストの比較は厳密に行われるため、このような行番号のずれもテスト失敗の原因となります。

1.  `src/cmd/asm/internal/asm/testdata/arm.out`
2.  `src/cmd/asm/internal/asm/testdata/arm.s`

## コアとなるコードの解説

このコミットのコアとなる変更は、`MRC`命令のテストを一時的に無効化することによって、壊れていたエンドツーエンドテストを修正した点にあります。

`arm.s` ファイル内の `MRC` 命令は、元々コメントアウトされていましたが、その上の `TODO` コメントが示すように、アセンブラの出力が32ビットと64ビットの環境で異なるという問題がありました。この問題は、アセンブラが生成する `arm.out` ファイルの内容に影響を与え、テストの比較が失敗する原因となっていました。

具体的には、`arm.out` から `MRC` 命令に関連する行を削除することで、アセンブラの出力と期待される出力との間の不一致を解消しています。これにより、テストは`MRC`命令の出力形式の差異に影響されなくなり、ビルドが正常に完了するようになります。

`arm.s` のコメント変更は、この問題がまだ未解決であり、将来的に`MRC`命令の出力形式が統一された際に、このテストを再度有効化する必要があることを開発者に示唆しています。これは、一時的な回避策であることを明確にするための重要な情報です。

この変更は、Goのツールチェインの安定性を維持し、開発者が異なる環境でGoコードをビルドする際の信頼性を確保するために行われました。

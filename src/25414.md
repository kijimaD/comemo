# [インデックス 25414] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9オペレーティングシステム上でのシグナルハンドラ内での浮動小数点演算の使用に関するバグ修正を扱っています。具体的には、メモリプロファイリングのための`nextSample`関数がシグナルハンドラ内で呼び出された際に発生する問題を解決します。

    runtime: don't use FP when calling nextSample in the Plan 9 sighandler
    
    In the Go signal handler on Plan 9, when a signal with

    printing the stack trace.

    startpanic_m. In the startpanic_m function, we call
    allocmcache to allocate _g_.m.mcache. The problem is

    point operation to return a sampling point for heap profiling.

    signal handler.

    called when in the Plan 9 signal handler, which is

## 元コミット内容

GoのPlan 9向けシグナルハンドラにおいて、`_SigThrow`フラグを持つシグナルが受信されると、スタックトレースを出力する前に`startpanic`関数が呼び出されます。この`startpanic`は`systemstack`を介して`startpanic_m`を呼び出し、さらに`allocmcache`を呼び出して`_g_.m.mcache`を割り当てます。問題は、`allocmcache`がヒーププロファイリングのためのサンプリングポイントを返す`nextSample`関数を呼び出す点にありました。`nextSample`は浮動小数点演算を使用しますが、Plan 9のシグナルハンドラ内では浮動小数点演算がサポートされていませんでした。

このコミットは、`nextSample`と類似しているものの浮動小数点演算を避ける新しい関数`nextSampleNoFP`を追加することでこの問題を解決します。`nextSample`は、Plan 9のシグナルハンドラ内で実行されている場合にのみ`nextSampleNoFP`を呼び出すように変更されました。

## 変更の背景

Goランタイムは、プログラムの異常終了時や特定のシグナル受信時に、スタックトレースの出力やパニック処理を行います。この処理は、オペレーティングシステム（OS）のシグナルハンドラ内で実行されることがよくあります。Plan 9というOSでは、シグナルハンドラの実行環境に特定の制約があり、特に浮動小数点演算が許可されていませんでした。

Goのメモリプロファイリング機能は、ヒープ割り当ての統計を収集するために、一定の確率でサンプリングを行います。このサンプリングのタイミングを決定するために`nextSample`関数が使用され、その内部で乱数生成と指数分布の計算のために浮動小数点演算が用いられていました。

問題は、Goプログラムがパニック状態に陥り、その処理がPlan 9のシグナルハンドラ内で実行される際に発生しました。パニック処理の一環としてメモリ割り当てが行われ、その過程で`allocmcache`が`nextSample`を呼び出します。このとき、シグナルハンドラ内で浮動小数点演算が実行されてしまい、Plan 9の制約に違反し、プログラムがクラッシュするというバグがありました。

このコミットは、Plan 9のシグナルハンドラという特殊なコンテキストにおいて、浮動小数点演算を安全に回避しつつ、メモリプロファイリングの機能を維持するための修正です。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、シグナルハンドリングなどを担当します。
*   **シグナルハンドラ (Signal Handler)**: オペレーティングシステムがプログラムにシグナル（イベント通知）を送信した際に、そのシグナルを処理するために実行される特別な関数です。例えば、プログラムの異常終了（セグメンテーション違反など）や、Ctrl+Cによる割り込みなどがシグナルとして扱われます。シグナルハンドラは、通常のプログラム実行とは異なる、非常に制約の多い環境で実行されることが一般的です。
*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステム。Unixの概念をさらに推し進めた設計思想を持ち、ファイルシステムを中心としたリソース管理が特徴です。シグナルハンドラの設計もUnix系OSとは異なる場合があります。
*   **`_SigThrow` フラグ**: Goランタイム内部で使用されるシグナルに関するフラグの一つで、Goのパニック機構と関連しています。このフラグが設定されたシグナルは、Goランタイムがパニック状態に移行するきっかけとなることを示唆します。
*   **`startpanic` / `systemstack` / `startpanic_m`**: Goランタイムにおけるパニック処理の内部関数群です。`startpanic`はパニック処理を開始し、`systemstack`は現在のゴルーチンスタックからシステムスタックに切り替える役割を持ちます。`startpanic_m`は、システムスタック上でパニック処理の具体的なステップを実行します。
*   **`allocmcache`**: Goランタイムのメモリ管理において、Mキャッシュ（Memory Cache）を割り当てる関数です。Mキャッシュは、各M（OSスレッド）がP（プロセッサ）に紐付けられた際に、Pが管理するローカルなメモリキャッシュを指します。これにより、ロック競合を減らし、メモリ割り当ての効率を高めます。
*   **ヒーププロファイリング (Heap Profiling)**: プログラムがヒープメモリをどのように使用しているかを分析する手法です。Goでは、`runtime/pprof`パッケージを通じてヒーププロファイリング機能が提供されており、メモリリークの特定やメモリ使用量の最適化に役立ちます。`nextSample`関数は、このプロファイリングのために、どのメモリ割り当てをサンプリングするかを確率的に決定します。
*   **`MemProfileRate`**: Goのメモリプロファイリングにおけるサンプリングレートを制御するランタイム変数です。この値が大きいほど、より多くのメモリ割り当てがプロファイリングの対象となります。
*   **浮動小数点演算 (Floating Point Operations)**: 小数点を含む数値を扱うための演算です。CPUの浮動小数点ユニット（FPU）によって処理されます。シグナルハンドラのような低レベルのコンテキストでは、FPUの状態が不安定であったり、FPUの使用が許可されていなかったりする場合があります。

## 技術的詳細

この問題の核心は、Plan 9のシグナルハンドラが浮動小数点演算を安全に実行できないというOSレベルの制約と、Goランタイムのメモリプロファイリング機能が浮動小数点演算に依存しているという実装の詳細の衝突にありました。

Goの`nextSample`関数は、`MemProfileRate`に基づいて、次にメモリ割り当てをサンプリングするまでのバイト数を決定します。この計算には、乱数（`fastrand1()`）と対数関数（`math.Log`）を用いた指数分布のサンプリングが含まれており、これらが浮動小数点演算を必要とします。

```go
// func nextSample() int32 {
//     // ...
//     qlog := math.Log(float64(fastrand1()) / (1<<32 - 1))
//     // ...
//     return int32(qlog*(minusLog2*float64(period))) + 1
// }
```

Plan 9のシグナルハンドラ内でパニックが発生し、`startpanic` -> `systemstack` -> `startpanic_m` -> `allocmcache` の呼び出しパスを経て`nextSample`が実行されると、この浮動小数点演算が原因でクラッシュが発生していました。シグナルハンドラは、割り込みによって非同期に実行されるため、通常のプログラム実行とは異なるCPUの状態（特にFPUの状態）で動作することがあり、浮動小数点レジスタのコンテキスト保存・復元が適切に行われない場合や、そもそもFPUの使用が禁止されている場合があります。

このコミットでは、この問題を解決するために、`nextSample`関数にOSと実行コンテキストのチェックを追加しました。
1.  `GOOS == "plan9"`: 現在のOSがPlan 9であるかを確認します。
2.  `g := getg(); g == g.m.gsignal`: 現在実行中のゴルーチン`g`が、シグナルハンドラ用のゴルーチン`g.m.gsignal`であるかを確認します。

これらの条件が両方とも真である場合、つまりPlan 9のシグナルハンドラ内で実行されている場合にのみ、新しく導入された`nextSampleNoFP`関数が呼び出されます。

`nextSampleNoFP`は、浮動小数点演算を使用しない、より単純なサンプリングロジックを提供します。

```go
// func nextSampleNoFP() int32 {
//     rate := MemProfileRate
//     if rate > 0x3fffffff {
//         rate = 0x3fffffff
//     }
//     if rate != 0 {
//         return int32(int(fastrand1()) % (2 * rate))
//     }
//     return 0
// }
```

この実装では、`fastrand1()`で生成された乱数を`2 * rate`で割った余りを使用することで、浮動小数点演算を完全に回避しています。これにより、Plan 9のシグナルハンドラ内でも安全にメモリプロファイリングのサンプリングポイントを決定できるようになりました。サンプリングの精度は若干低下する可能性がありますが、クラッシュを回避できることのメリットが上回ります。

## コアとなるコードの解説

*   **`nextSample()` 関数内の変更**:
    *   `if GOOS == "plan9"`: コンパイル時に定義される`GOOS`定数を用いて、現在のビルドターゲットがPlan 9であるかをチェックします。これにより、Plan 9以外のOSではこの特殊なロジックが実行されないようにします。
    *   `if g := getg(); g == g.m.gsignal`: `getg()`は現在のゴルーチン構造体へのポインタを返します。`g.m.gsignal`は、現在のM（OSスレッド）に紐付けられたシグナルハンドラ用のゴルーチンを指します。この比較により、コードがシグナルハンドラのコンテキストで実行されているかを正確に判断します。
    *   `return nextSampleNoFP()`: 上記の条件が満たされた場合、浮動小数点演算を含まない`nextSampleNoFP`関数を呼び出して、サンプリングポイントを決定します。

*   **`nextSampleNoFP()` 関数の追加**:
    *   この関数は、`nextSample`の代替として、浮動小数点演算なしでサンプリングポイントを計算します。
    *   `rate := MemProfileRate`: メモリプロファイリングのサンプリングレートを取得します。
    *   `if rate > 0x3fffffff { rate = 0x3fffffff }`: `2 * rate`がオーバーフローしないように、`rate`の最大値を制限します。
    *   `if rate != 0 { return int32(int(fastrand1()) % (2 * rate)) }`: `MemProfileRate`が0でない場合（プロファイリングが有効な場合）、`fastrand1()`で生成された擬似乱数を`2 * rate`で割った余りをサンプリングポイントとして返します。これは、単純なモジュロ演算によるサンプリングであり、浮動小数点演算を必要としません。
    *   `return 0`: `MemProfileRate`が0の場合（プロファイリングが無効な場合）、0を返します。

この変更により、GoランタイムはPlan 9のシグナルハンドラ内での浮動小数点演算の制約を尊重しつつ、メモリプロファイリングの基本的な機能を維持できるようになりました。これは、特定のOS環境における低レベルな制約と、Goランタイムの高度な機能との間のバランスを取るための典型的な修正例と言えます。

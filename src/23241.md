## 変更の背景

Goのガベージコレクター（GC）は、アプリケーションのパフォーマンスに大きな影響を与える重要なコンポーネントです。特に、Go 1.5で導入された並行GCは、GCポーズタイムを大幅に削減することを目的としていました。しかし、GCの内部動作、特にGCがいつ開始され、どのようにヒープの成長を制御するかの「ペース調整（pacing）」のロジックは複雑です。

この複雑なロジックを理解し、デバッグするためには、GCコントローラーの内部状態を可視化する手段が不可欠でした。このコミットは、GCコントローラーがどのようにヒープの使用状況を監視し、次のGCサイクルをいつトリガーするかを決定しているかを、開発者が詳細に追跡できるようにするためのものです。これにより、GCのパフォーマンス問題の診断や、GCアルゴリズム自体の改善に役立つ情報を提供します。

## 前提知識の解説

### Goのガベージコレクター (GC)

GoのGCは、不要になったメモリを自動的に解放するシステムです。Go 1.5以降、GoのGCは「並行（concurrent）」かつ「非世代別（non-generational）」のマーク＆スイープGCを採用しています。

*   **並行GC**: アプリケーションの実行と並行してGCの大部分の作業（マークフェーズ）が行われます。これにより、GCがアプリケーションの実行を停止させる時間（ポーズタイム）が大幅に短縮されます。
*   **マーク＆スイープ**:
    *   **マークフェーズ**: プログラムがアクセス可能なオブジェクト（ライブオブジェクト）を特定し、マークします。
    *   **スイープフェーズ**: マークされなかったオブジェクト（デッドオブジェクト）が占めるメモリを解放し、再利用可能にします。

### GCコントローラー (Pacer)

GCコントローラー、またはGCペーサーは、GoランタイムのGCの心臓部とも言えるコンポーネントです。その主な役割は以下の通りです。

1.  **GCトリガーの決定**: 次のGCサイクルをいつ開始するかを決定します。これは、前回のGCでマークされたヒープサイズ（`heap_marked`）と、GC目標（`next_gc`）に基づいて行われます。GC目標は、GCが完了した後にヒープがどの程度成長したら次のGCを開始するかを示す値です。
2.  **ヒープ成長の制御**: アプリケーションのメモリ割り当てパターンに基づいて、ヒープの成長率を調整し、GCが効率的に動作するようにします。目標は、GC作業がアプリケーションの実行と並行して完了するように、適切なタイミングでGCを開始することです。
3.  **スキャンワークの調整**: GCが実行するスキャン作業の量を調整し、アプリケーションのスループットへの影響を最小限に抑えつつ、GCを時間内に完了させます。

### `GODEBUG` フラグ

`GODEBUG`は、Goプログラムのランタイム動作を制御するための環境変数です。特定のデバッグ情報を出力したり、ランタイムの挙動を変更したりするために使用されます。例えば、`GODEBUG=gctrace=1`を設定すると、GCの実行に関する詳細なトレース情報が出力されます。このコミットでは、`gcpacertrace`という新しいフラグが追加され、GCコントローラーの内部状態をトレースできるようになります。

## 技術的詳細

このコミットは、`gcControllerState`構造体の`endCycle`メソッドにデバッグ出力ロジックを追加します。`endCycle`メソッドは、並行GCサイクルのマークフェーズが終了した後に呼び出され、GCコントローラーの状態を更新する役割を担っています。

追加されたデバッグ出力は、GoのGCペーサーの設計ドキュメント（Go 1.5 concurrent GC pacingなど）で定義されている主要な変数に基づいています。これらの変数は、GCのトリガー、ヒープの成長、およびGC作業のペース調整を理解するために不可欠です。

出力される主な変数は以下の通りです。

*   `H_m_prev`: 前回のGCでマークされたヒープのサイズ。
*   `h_t`: 現在のトリガー比率。これは、前回のGCでマークされたヒープサイズに対して、次のGCが開始されるまでにヒープがどれだけ成長できるかを示す比率です。
*   `H_T`: 次のGCが開始されるべきヒープの目標サイズ（`memstats.next_gc`）。
*   `h_a`: 実際の成長比率。前回のGCから現在までのヒープの実際の成長比率。
*   `H_a`: 現在のライブヒープサイズ（`memstats.heap_live`）。
*   `h_g`: 目標成長比率。GCコントローラーが目指すヒープの成長比率。
*   `H_g`: 目標ヒープサイズ。`H_m_prev * (1 + h_g)`で計算される、目標成長比率に基づいたヒープサイズ。
*   `u_a`: 実際の利用率。GCがヒープをどれだけ効率的に利用しているかを示す。
*   `u_g`: GC目標利用率。GCコントローラーが目指すヒープの利用率。
*   `W_a`: 実際のスキャンワーク量。GCが実行したスキャン作業の総量。
*   `w_a`: 実際のワーク比率。GCが実行したスキャンワークと、GCが完了するまでに必要な総ワークの比率。
*   `w_ewma`: ワーク比率の指数移動平均（EWMA）。GC作業の変動を平滑化するために使用されます。
*   `goalΔ`: `goalGrowthRatio - h_t`。目標成長比率と現在のトリガー比率の差。
*   `actualΔ`: `h_a - h_t`。実際の成長比率と現在のトリガー比率の差。
*   `u_a/u_g`: 実際の利用率と目標利用率の比率。

これらの値を出力することで、開発者はGCコントローラーがどのように意思決定を行い、ヒープの成長を制御しているかを詳細に分析できます。例えば、`goalΔ`や`actualΔ`を見ることで、GCが目標とする成長率に対して、実際にどれだけヒープが成長しているか、あるいはトリガー比率が適切に調整されているかを評価できます。

*   `w_a`: 実際のワーク比率。GCが実行したスキャンワークと、GCが完了するまでに必要な総ワークの比率。
*   `w_ewma`: ワーク比率の指数移動平均（EWMA）。GC作業の変動を平滑化するために使用されます。
*   `goalΔ`: `goalGrowthRatio - h_t`。目標成長比率と現在のトリガー比率の差。
*   `actualΔ`: `h_a - h_t`。実際の成長比率と現在のトリガー比率の差。
*   `u_a/u_g`: 実際の利用率と目標利用率の比率。

これらの値を出力することで、開発者はGCコントローラーがどのように意思決定を行い、ヒープの成長を制御しているかを詳細に分析できます。例えば、`goalΔ`や`actualΔ`を見ることで、GCが目標とする成長率に対して、実際にどれだけヒープが成長しているか、あるいはトリガー比率が適切に調整されているかを評価できます。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

*   `h_t := c.triggerRatio // For debugging`
    *   `endCycle`メソッドの冒頭で、現在のトリガー比率`c.triggerRatio`を`h_t`という変数に保存しています。これは、デバッグ出力の際に、この時点での`triggerRatio`の値を参照できるようにするためです。

*   `if debug.gcpacertrace > 0 { ... }` ブロックの追加
    *   この`if`ブロックが、GCコントローラーの状態を詳細に出力する主要な部分です。
    *   `debug.gcpacertrace`は、`GODEBUG=gcpacertrace=1`のように設定することで有効になるフラグです。このフラグが0より大きい場合にのみ、以下のデバッグ出力が実行されます。
    *   ブロック内では、GCペーサーの設計ドキュメントで定義されている様々なメトリクス（`H_m_prev`, `H_T`, `h_a`, `H_a`, `h_g`, `H_g`, `u_a`, `u_g`, `W_a`, `w_a`, `w_ewma`）が計算または取得されます。
    *   `H_g`は、`H_m_prev`（前回のGCでマークされたヒープサイズ）と`h_g`（目標成長比率）に基づいて計算される目標ヒープサイズです。
    *   最後に、`print`関数を使用して、これらの変数の値が`pacer:`というプレフィックスとともに標準エラー出力に書き出されます。これにより、GCサイクルの終了時にGCコントローラーの「スナップショット」が提供されます。
    *   `goalΔ`, `actualΔ`, `u_a/u_g`といった派生的な値も計算され、出力されます。これらは、GCコントローラーの目標と実際のパフォーマンスとの間の差を直接的に示し、GCのチューニングやデバッグに役立ちます。

### `src/runtime/runtime1.go` の変更点

*   `var debug struct { ... }` に `gcpacertrace int32` の追加
    *   `debug`構造体は、様々なランタイムデバッグフラグを保持しています。ここに`gcpacertrace`という新しいフィールドが`int32`型で追加されました。これにより、`GODEBUG`環境変数を通じてこのフラグを制御できるようになります。

*   `var dbgvars = []dbgVar{ ... }` に `{"gcpacertrace", &debug.gcpacertrace},` の追加
    *   `dbgvars`配列は、`GODEBUG`環境変数を解析する際に使用される、フラグ名とそれに対応する`debug`構造体内のフィールドへのポインタのマッピングを定義しています。
    *   この行の追加により、`GODEBUG=gcpacertrace=...`という形式で`gcpacertrace`フラグの値を設定できるようになります。

これらの変更により、Goランタイムのユーザーは、`GODEBUG=gcpacertrace=1`を設定することで、GCコントローラーの内部状態を詳細に監視し、GCの動作をより深く理解できるようになります。

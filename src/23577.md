## 元コミット内容

`cmd/internal/obj: make arm64 use RegTo2 instead of a full fledged Addr To2`

このコミットは、Goコンパイラの内部パッケージである`cmd/internal/obj`において、ARM64アーキテクチャの命令表現を改善するものです。具体的には、命令を表す`Prog`構造体において、汎用的な`Addr`型の`To2`フィールドの代わりに、レジスタ専用の`RegTo2`フィールドを使用するように変更します。これにより、`Prog`構造体のサイズがAMD64アーキテクチャ上で448バイトから376バイトに削減されます。

この変更の根拠として、現代のほとんどのアーキテクチャでは、レジスタではない2つの異なる宛先に書き込む命令は存在しないという事実が挙げられています（x86でさえそのような命令は持っていません）。したがって、`To2`がレジスタである場合に限定することで、より正確で効率的な表現が可能になります。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現として`Prog`（Program instructionの略）構造体を使用します。この`Prog`構造体は、アセンブリ命令のオペランド（操作対象）を表現するために`Addr`（Addressの略）構造体を含んでいます。

従来の`Prog`構造体には、`From`、`To`、そして`To2`という3つの`Addr`型フィールドがありました。`To2`は、一部の命令（特にARM64の`STLXR`のような排他ストア命令）で必要とされる、2つ目の書き込み先オペランドを表現するために使用されていました。しかし、コミットメッセージが指摘するように、現代のCPUアーキテクチャにおいて、レジスタではないメモリ位置に同時に2つの異なる書き込みを行う命令は非常に稀です。ほとんどの場合、2つ目の書き込み先が指定される場合、それはレジスタであることが一般的です。

この状況において、`To2`が汎用的な`Addr`型であることは、不要なメモリ消費と、命令のセマンティクスに対する誤解を招く可能性がありました。`Addr`構造体は、レジスタ、メモリ、定数など、様々な種類のアドレス指定モードを表現できるため、その分サイズが大きくなります。`To2`が常にレジスタであるべきであるならば、`Addr`型全体を持つ必要はなく、レジスタ番号だけを保持する方が効率的です。

このコミットは、この非効率性を解消し、`Prog`構造体のサイズを削減することで、コンパイラのメモリ使用量を最適化し、パフォーマンスを向上させることを目的としています。

## 前提知識の解説

### Goコンパイラの構造 (`cmd/internal/obj`)

Goコンパイラは複数のステージで動作し、`cmd/internal/obj`パッケージは、アセンブラとリンカの共通のオブジェクトファイルフォーマットと命令表現を定義する重要な部分です。このパッケージは、Goのソースコードが最終的な機械語に変換される過程で、アーキテクチャ固有のアセンブリ命令を抽象化して表現するために使用されます。

### `Prog`構造体

`Prog`構造体は、Goコンパイラ内部で単一のアセンブリ命令を表現するために使用される中心的なデータ構造です。これには、命令の種類（オペコード）、ソースオペランド、デスティネーションオペランド、およびその他の命令固有のメタデータが含まれます。

```go
type Prog struct {
    // ... 既存のフィールド ...
    From     Addr
    From3    Addr // 3番目のソースオペランド (稀に使用)
    To       Addr
    // To2      Addr // 削除されるフィールド
    // ... その他のフィールド ...
    Reg      int16 // 汎用レジスタオペランド
    RegTo2   int16 // 新しく追加される2番目のレジスタ出力オペランド
    // ... その他のフィールド ...
}
```

### `Addr`構造体

`Addr`構造体は、アセンブリ命令のオペランド（アドレス指定モード）を表現するために使用されます。これには、オペランドのタイプ（レジスタ、メモリ、定数など）、レジスタ番号、オフセット、シンボルなどの情報が含まれます。`Addr`は比較的大きな構造体であり、様々なアドレス指定モードをサポートするために多くのフィールドを持っています。

```go
type Addr struct {
    Type     int18 // オペランドのタイプ (TYPE_REG, TYPE_MEM, TYPE_CONSTなど)
    Reg      int16 // レジスタ番号
    Offset   int64 // メモリオフセット
    Sym      *LSym // シンボル
    // ... その他のフィールド ...
}
```

### ARM64アーキテクチャと`STLXR`命令

ARM64は、モバイルデバイスやサーバーなどで広く使用されている64ビットRISCアーキテクチャです。`STLXR`（Store-Exclusive Register）命令は、ARM64の排他アクセス命令セットの一部です。これは、マルチコアプロセッサ環境でのアトミック操作（不可分操作）を実装するために使用されます。

`STLXR`命令は、指定されたアドレスに値をストアし、その操作が排他的に成功したかどうかを示すステータスをレジスタに書き込みます。つまり、この命令は2つの出力を持つと考えることができます。1つはメモリへの書き込み、もう1つはステータスレジスタへの書き込みです。このコミットの文脈では、`To2`がこのステータスレジスタを指すことになります。

### メモリフットプリントの削減

`Prog`構造体のサイズを削減することは、コンパイラのパフォーマンスにとって重要です。コンパイル中に数百万もの`Prog`構造体が生成される可能性があるため、各`Prog`構造体のサイズが小さくなればなるほど、メモリ使用量が減り、キャッシュ効率が向上し、結果としてコンパイル時間が短縮されます。

## 技術的詳細

このコミットの核心は、`Prog`構造体から`Addr`型の`To2`フィールドを削除し、代わりに`int16`型の`RegTo2`フィールドを追加することです。

*   **`Addr`から`int16`への変更の理由**:
    *   `Addr`構造体は、オペランドのタイプ、レジスタ番号、オフセット、シンボルなど、多くの情報を保持するため、比較的大きなサイズ（例えば、AMD64上で24バイト程度）を持ちます。
    *   一方、`int16`は2バイトの整数型であり、レジスタ番号（通常は0から31または63の範囲）を表現するには十分です。
    *   コミットメッセージが指摘するように、`To2`が使用されるほとんどのケース（特にARM64の`STLXR`命令）では、そのオペランドは常にレジスタです。したがって、`Addr`の全ての情報を保持する必要はなく、レジスタ番号のみを保持すれば十分です。

*   **メモリ削減効果**:
    *   `Prog`構造体から`Addr`（約24バイト）を削除し、`int16`（2バイト）を追加することで、`Prog`構造体全体のサイズが約22バイト削減されます。
    *   コミットメッセージでは、AMD64上で`Prog`構造体のサイズが448バイトから376バイトに削減されたと述べられています。これは、`Prog`構造体内の他のフィールドのパディングやアライメントの影響も考慮した結果と考えられます。この削減は、コンパイル時のメモリ使用量に大きな影響を与えます。

*   **セマンティクスの明確化**:
    *   `To2`が`Addr`型であると、理論的にはレジスタ以外の任意のアドレス指定モード（例えば、メモリ位置）を表現できることになります。しかし、実際にはそのような命令は存在しないため、これは誤解を招く可能性がありました。
    *   `RegTo2`という名前の`int16`フィールドにすることで、このオペランドが常にレジスタであることをコードの型システムレベルで強制し、セマンティクスをより明確にします。これにより、コンパイラのコードの健全性が向上します。

## コアとなるコードの解説

この変更の最も重要な部分は、`Prog`構造体の定義変更です。

`src/cmd/internal/obj/link.go`における`Prog`構造体の変更は、Goコンパイラの命令表現の根本的な改善を示しています。

*   **`To2 Addr`の削除**: 汎用的な`Addr`構造体は、レジスタ、メモリ、定数など、様々なオペランドタイプを表現できます。しかし、2番目の出力オペランド（`To2`）が実際にレジスタである場合にのみ使用されるという事実に基づき、この汎用性は不要と判断されました。`Addr`構造体は複数のフィールドを持つため、その分メモリを消費します。
*   **`RegTo2 int16`の追加**: `int16`型は、レジスタ番号（通常は小さな整数値）を効率的に格納できます。これにより、`Prog`構造体のメモリフットプリントが大幅に削減されます。`int16`という型は、このオペランドがレジスタであることを明確に示し、コンパイラのコードがより堅牢になります。

他のファイルでの変更は、この`Prog`構造体の変更に合わせたものです。

*   `src/cmd/asm/internal/asm/asm.go`では、アセンブラがソースコードを解析して`Prog`構造体を構築する際に、ARM64の`STLXR`命令に対して、3番目のオペランドがレジスタであることを検証し、そのレジスタ番号を新しい`RegTo2`フィールドに格納するように修正されています。これにより、不正なオペランド指定がコンパイル時に検出されるようになります。
*   `src/cmd/compile/internal/arm64/peep.go`や`src/cmd/internal/obj/arm64/asm7.go`では、ARM64アーキテクチャ固有のコード生成や最適化のロジックが、`To2`の代わりに`RegTo2`を使用するように更新されています。これは、`Prog`構造体の新しい定義に準拠するための直接的な変更です。
*   `src/cmd/internal/obj/util.go`の`Prog.String()`メソッドの変更は、デバッグやログ出力の際に、新しい`RegTo2`フィールドの内容が正しく表示されるようにするためのものです。
*   `src/cmd/internal/obj/x86/obj6.go`の変更は、x86アーキテクチャのコードから、もはや存在しない`To2`フィールドへの参照を削除するクリーンアップです。

これらの変更は、Goコンパイラの内部表現をより効率的かつ正確にし、特にARM64のような特定のアーキテクチャの特性を考慮に入れた最適化の一環です。

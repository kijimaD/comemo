# [インデックス 26038] ファイルの概要

このコミットは、Go言語の `net` パッケージにおける `LookupPort` 関数の挙動を修正するものです。具体的には、`LookupPort` 関数に空のサービス文字列が渡された場合に、ポート番号として `0` を返すように変更し、この「レガシーな挙動」を明示的にロックインします。これにより、Issue 13610で報告された、空のサービス文字列が与えられた際の予期せぬエラーや挙動が解消されます。

## 変更の背景

Go言語の `net` パッケージに含まれる `LookupPort` 関数は、指定されたネットワークプロトコル（例: "tcp", "udp"）とサービス名（例: "http", "ssh"）に基づいて、対応するポート番号を検索する機能を提供します。しかし、この関数に空のサービス文字列 `""` が渡された場合、その挙動は明確に定義されておらず、実装によっては予期せぬエラーを返したり、無効なポート解決を試みたりする可能性がありました。

この問題は、GoのIssueトラッカーでIssue 13610として報告されました。報告によると、空のサービス文字列が渡された際に `LookupPort` がエラーを返すことがあり、これはユーザーが `0` を期待するシナリオ（例: 任意のポートを意味する場合）と矛盾していました。このコミットは、この曖昧な挙動を解消し、空のサービス文字列に対しては一貫してポート `0` を返すようにすることで、関数の信頼性と予測可能性を向上させることを目的としています。

## 前提知識の解説

### Go言語の `net` パッケージ

`net` パッケージは、Go言語におけるネットワークI/Oのプリミティブインターフェースを提供します。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルを扱うための機能が含まれており、ネットワーク接続の確立、データの送受信、DNSルックアップなどが可能です。

### `net.LookupPort` 関数

`func LookupPort(network, service string) (port int, err error)`

この関数は、指定された `network` タイプ（例: "tcp", "udp", "tcp4", "tcp6", "udp4", "udp6"）と `service` 名（例: "http", "ftp", "domain"）に対応するポート番号を検索します。サービス名は通常、`/etc/services` ファイルやIANA (Internet Assigned Numbers Authority) によって定義された標準的なサービス名に対応します。例えば、`LookupPort("tcp", "http")` は通常 `80` を返します。

### サービス名とポート番号

インターネット上の多くのサービスは、特定のポート番号を使用するように標準化されています。例えば、HTTPはポート80、HTTPSはポート443、SSHはポート22を使用します。これらのサービスは、人間が覚えやすいサービス名（例: "http"）と、コンピュータが通信に使うポート番号（例: 80）で関連付けられています。`LookupPort` はこの関連付けを解決する役割を担います。

### Issue 13610

このコミットが修正する具体的な問題は、GoのIssue 13610で議論されました。このIssueでは、`net.LookupPort` に空のサービス文字列 `""` を渡すと、`lookupPort` 関数が内部で `getaddrinfo` を呼び出し、結果としてエラーを返すことが報告されました。しかし、多くのユーザーは空のサービス文字列を「任意のポート」や「ポート0」として解釈することを期待しており、この挙動は直感的ではありませんでした。このコミットは、この期待される挙動に合わせて `LookupPort("")` が `0` を返すように変更します。

## 技術的詳細

`net.LookupPort` 関数は、内部でサービス名をポート番号に変換するためにいくつかのステップを踏みます。

1.  **数値ポートの直接解析**: まず、サービス文字列が直接数値として解釈できるか (`dtoi` 関数などを使用して) 試みます。例えば、`"80"` は `80` に変換されます。
2.  **システムサービスファイルの検索**: 数値として解釈できない場合、システムに設定されているサービスファイル（Unix系OSでは通常 `/etc/services`）を検索して、サービス名に対応するポート番号を見つけようとします。これは `lookupPort` 関数が担当します。
3.  **DNS SRVレコードの検索**: さらに複雑なケースでは、DNSのSRVレコードを使用してサービス情報を解決することもありますが、`LookupPort` の直接的な挙動としては一般的ではありません。

このコミット以前は、空のサービス文字列 `""` が与えられた場合、上記のステップ1では数値として解釈できず、ステップ2の `lookupPort` が呼び出されていました。`lookupPort` は空のサービス名に対して有効なポートを見つけることができず、結果としてエラーを返していました。

このコミットでは、`LookupPort` 関数の冒頭に以下のチェックを追加することで、この問題を解決しています。

```go
if service == "" {
    // Lock in the legacy behavior that an empty string
    // means port 0. See Issue 13610.
    return 0, nil
}
```

この変更により、`service` が空文字列である場合は、他のポート解決ロジックをスキップして即座に `0` と `nil` エラーを返します。これは、空のサービス文字列が「ポート0」を意味するという、以前から一部で期待されていた「レガシーな挙動」を明示的に採用し、将来にわたってこの挙動を保証するためのものです。

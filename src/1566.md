## コミット

このコミットは、Go言語に`defer`ステートメントを導入するためのものです。`defer`は、関数がリターンする直前に実行される関数呼び出しをスケジュールするために使用されます。これにより、リソースの解放（ファイルクローズ、ロック解除など）を確実に行うことができます。

## 変更の背景

このコミットが行われた2009年1月は、Go言語がまだ一般に公開される前の非常に初期の段階でした。Go言語の設計目標の一つに、シンプルさと効率性がありました。従来のプログラミング言語では、リソースの確保と解放のペア（例: ファイルを開く/閉じる、ロックを取得する/解放する）を適切に管理することが、エラー処理やコードの複雑さを増大させる要因となっていました。特に、複数のリターンパスがある関数では、すべてのパスでリソースが確実に解放されるようにコードを書くのは困難であり、バグの温床となりがちでした。

`defer`ステートメントは、このような問題を解決するためにGo言語に導入されました。`defer`を使用することで、リソースの確保直後にその解放処理を記述することができ、コードの可読性を高め、リソースリークやデッドロックといったバグのリスクを大幅に低減します。これにより、開発者はリソース管理の煩雑さから解放され、より本質的なロジックに集中できるようになります。

## 前提知識の解説

### `defer`ステートメントとは

Go言語の`defer`ステートメントは、そのステートメントを含む関数が実行を終了する直前（`return`ステートメントが実行される直前、またはパニックが発生して関数が異常終了する直前）に、指定された関数呼び出しをスケジュールするものです。

`defer`の主な特徴は以下の通りです。

1.  **実行タイミング**: `defer`された関数は、それを囲む関数がリターンする直前に、LIFO（Last-In, First-Out）の順序で実行されます。つまり、複数の`defer`ステートメントがある場合、最後に`defer`されたものが最初に実行されます。
2.  **引数の評価**: `defer`ステートメントの引数（関数呼び出しの引数）は、`defer`ステートメントが実行された時点（つまり、関数が`defer`された時点）で評価されます。これは、`defer`された関数が実際に実行される時点ではありません。
3.  **用途**:
    *   **リソースの解放**: ファイルのクローズ、データベース接続のクローズ、ミューテックスのアンロックなど、確保したリソースを確実に解放するために使用されます。
    *   **トレース/ロギング**: 関数の開始と終了をログに記録する際に、関数の終了時にログを出力するために使用できます。
    *   **パニックからの回復**: `recover`関数と組み合わせて、パニックが発生した際にプログラムのクラッシュを防ぎ、回復処理を行うために使用されます。

### Go言語のパーサー、スキャナー、プリンター

Go言語のコンパイラは、ソースコードを機械語に変換する過程で、いくつかの段階を経ます。このコミットで変更されている`parser.go`、`scanner.go`、`printer.go`は、その初期段階で重要な役割を担います。

*   **スキャナー (Lexer)**: ソースコードを読み込み、意味のある最小単位である「トークン」（キーワード、識別子、演算子、リテラルなど）に分割します。例えば、`defer`という文字列を`DEFER`というトークンとして認識します。
*   **パーサー (Parser)**: スキャナーが生成したトークンのストリームを受け取り、Go言語の文法規則に従って、それらを抽象構文木（AST: Abstract Syntax Tree）と呼ばれるツリー構造に変換します。ASTは、プログラムの構造を表現したものです。パーサーは、`defer`キーワードの後に続く式が、`defer`ステートメントの文法規則に合致するかどうかを検証します。
*   **プリンター (Printer)**: 抽象構文木（AST）を受け取り、それを人間が読める形式のソースコードに変換します。これは、コンパイラがエラーメッセージを生成したり、`go fmt`のようなツールがコードを整形したりする際に使用されます。

これらのコンポーネントは、新しい言語機能（この場合は`defer`）をGo言語に追加する際に、その機能が正しく認識され、解析され、表現されるようにするために、必ず変更が必要となります。

## 技術的詳細

このコミットにおける`defer`ステートメントの導入は、Go言語の構文解析とコード生成のパイプラインに深く関わる変更です。

1.  **スキャナー層 (`scanner.go`)**:
    *   `DEFER`という新しいトークンが定数として追加されました。これにより、スキャナーはソースコード中の`defer`というキーワードを、特定の意味を持つトークンとして識別できるようになります。
    *   `TokenString`関数に`DEFER`トークンに対応する文字列`"defer"`が追加され、トークンを文字列表現に変換できるようになりました。

2.  **パーサー層 (`parser.go`)**:
    *   `ParseGoStat`関数が`ParseInvocationStat`というより汎用的な関数にリファクタリングされました。これは、`go`ステートメントと`defer`ステートメントが、どちらもキーワードの後に式が続くという類似した構文を持つためです。
    *   `ParseInvocationStat`は、引数としてキーワード（`Scanner.GO`または`Scanner.DEFER`）を受け取るようになりました。これにより、同じロジックで両方のステートメントを解析できます。
    *   `ParseStatement`関数内の`switch`文に`Scanner.DEFER`が追加され、`defer`キーワードが検出された場合に`ParseInvocationStat`が呼び出されるようになりました。これは、パーサーが`defer`ステートメントを認識し、適切な解析パスにディスパッチするためのエントリポイントです。
    *   `AST.NewStat(P.pos, keyword)`により、`defer`ステートメントを表す新しい抽象構文木ノードが作成されます。このノードは、`defer`キーワードの位置情報と、それが`defer`ステートメントであることを示す`keyword`（`Scanner.DEFER`）を保持します。

3.  **プリンター層 (`printer.go`)**:
    *   `Stat`関数内の`switch`文に`Scanner.DEFER`が追加されました。これにより、プリンターはAST内の`defer`ステートメントノードを認識し、対応する`defer`キーワードをソースコードとして出力できるようになります。
    *   `P.Token(s.Pos, s.Tok)`は、`defer`キーワード自体を出力します。
    *   `if s.Expr != nil { P.separator = blank; P.Expr(s.Expr); }`の部分は、`defer`キーワードの後に続く式（`defer`される関数呼び出し）を整形して出力します。

4.  **テストコード (`selftest2.go`, `test.sh`)**:
    *   `selftest2.go`に`defer println(i, x);`という行が追加され、`defer`ステートメントの基本的な動作（ループ内で`defer`された関数が、ループ終了後にLIFO順で実行されること）を検証するようになりました。
    *   `test.sh`に`bug133.go`という新しいテストケースが追加された可能性があります。これは、`defer`に関連する特定のバグやエッジケースをテストするために導入されたものと考えられます。

これらの変更は、Go言語のコンパイラが`defer`という新しい言語機能を正しく理解し、処理し、そして最終的に実行可能なバイナリに変換するための基盤を構築しています。

## コアとなるコードの解説

### `parser.go`の変更

*   **`ParseGoStat`から`ParseInvocationStat`へのリファクタリング**:
    *   元の`ParseGoStat`関数は、`go`キーワードに続く式を解析するためのものでした。
    *   `defer`ステートメントも`defer`キーワードに続く式を解析するため、両者の構文が類似していることから、共通の解析ロジックを持つ`ParseInvocationStat`関数に統合されました。
    *   `ParseInvocationStat`は`keyword`引数を受け取ることで、`go`と`defer`のどちらのステートメントを解析しているかを区別し、適切なASTノードを作成できるようになりました。
    *   `P.Expect(keyword)`は、現在のトークンが期待されるキーワード（`go`または`defer`）であることを検証します。
*   **`ParseStatement`の`switch`文の更新**:
    *   `case Scanner.GO:`の行が`case Scanner.GO, Scanner.DEFER:`に変更されました。これにより、パーサーは`go`トークンだけでなく、新しく追加された`DEFER`トークンもステートメントの開始として認識し、`ParseInvocationStat`関数に処理を委譲するようになりました。

これらの変更により、パーサーは`defer`ステートメントの構文を正しく解析し、抽象構文木（AST）内にその存在を表現できるようになります。

### `printer.go`の変更

*   **`Stat`関数の`switch`文の更新**:
    *   `case Scanner.GO, Scanner.RETURN, ...:`の行に`Scanner.DEFER`が追加されました。
    *   これにより、プリンターはASTを走査する際に`DEFER`トークンを持つステートメントノードを認識し、そのノードに対応する`defer`キーワードとそれに続く式を整形して出力するロジックが適用されるようになりました。
    *   `P.Token(s.Pos, s.Tok)`は、`defer`キーワード自体をソースコードとして出力します。
    *   `if s.Expr != nil { ... P.Expr(s.Expr); }`は、`defer`される関数呼び出しの式を整形して出力します。

この変更により、`defer`ステートメントを含むGoコードが正しく整形され、出力されるようになります。

### `scanner.go`の変更

*   **`DEFER`定数の追加**:
    *   `const`ブロックに`DEFER;`が追加されました。これは、`defer`キーワードに対応する新しいトークンタイプを定義しています。
*   **`TokenString`関数の更新**:
    *   `case DEFER: return "defer";`が追加されました。これにより、`DEFER`トークンが文字列`"defer"`として表現されるようになり、デバッグやエラーメッセージの生成に役立ちます。

これらの変更は、スキャナーがソースコード中の`defer`という文字列を、コンパイラが理解できる内部的なトークンとして認識するための基盤を確立します。

### `selftest2.go`の変更

*   `for i, x = range m { println(i, x); }`の行が`for i, x = range m { defer println(i, x); }`に変更されました。
*   この変更は、`defer`ステートメントがループ内でどのように振る舞うか（各イテレーションで`defer`された関数が、ループ終了後にLIFO順で実行されること）をテストするための具体的な使用例を示しています。これは、`defer`の重要なセマンティクスの一つであり、その正しい実装を検証するために不可欠です。

### `test.sh`の変更

*   `bug133.go`がテスト対象のファイルリストに追加されました。
*   これは、`defer`ステートメントの導入に伴い、発見された可能性のある新しいバグや、`defer`の特定の挙動を検証するためのテストケースが追加されたことを示唆しています。

これらのコード変更は、Go言語に`defer`ステートメントを完全に統合し、その構文解析、セマンティクス、およびテストカバレッジを確保するための包括的なアプローチを示しています。

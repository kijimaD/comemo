# [インデックス 2534] ファイルの概要

このコミットは、Goコンパイラ（`gc`）におけるバグ「bug165」を修正するものです。具体的には、前方宣言された型がマップのキーとして使用された際に、コンパイラがその型を不適切に「無効なマップキー型」と判断してしまう問題を解決します。この修正により、型の完全な定義が完了するまでマップキーの妥当性チェックを遅延させるメカニズムが導入され、自己参照的なインターフェース型がマップキーとして正しく扱われるようになります。

## 変更の背景

Go言語の初期段階において、コンパイラ（`gc`）は型の前方宣言とマップキーの妥当性チェックの相互作用において問題を抱えていました。特に、インターフェース型が自身の定義内でマップのキーとして使用されるような自己参照的なシナリオで、コンパイラが型が完全に解決される前にマップキーの比較可能性をチェックしようとし、誤ってエラーを報告していました。

例えば、`type I interface { m(map[I] bool) }` のような定義では、インターフェース`I`がまだ完全に定義されていない段階で`map[I]bool`という形でキーとして参照されます。Goの仕様では、インターフェース型は、その動的な型が比較可能であればマップキーとして有効です。しかし、コンパイラがこの「動的な型」の情報を得る前にチェックを実行してしまうと、不適切なエラーが発生していました。

このバグ（bug165）は、このような状況下でのコンパイルエラーを修正し、Goの型システムが意図する柔軟性を正しくサポートするために導入されました。

## 前提知識の解説

### Goの型システムとマップのキー型

Go言語のマップ（`map[KeyType]ValueType`）は、キーとして使用できる型に制約があります。マップのキー型は「比較可能（comparable）」でなければなりません。これは、マップがキーの等価性を判断するためにキーを比較する必要があるためです。

*   **比較可能な型**: 数値型、文字列型、ブール型、ポインタ型、チャネル型、インターフェース型（動的な型が比較可能であれば）、構造体型（すべてのフィールドが比較可能であれば）、配列型（すべての要素が比較可能であれば）。
*   **比較不可能な型**: スライス型、マップ型、関数型。これらの型は、Goの言語仕様上、等価性を定義できないため、マップのキーにはなれません。

### Goコンパイラ（`gc`）の型処理

Goコンパイラ`gc`は、ソースコードを解析し、型情報を構築・解決する複雑なプロセスを持っています。

*   **`Type`構造体**: コンパイラ内部では、すべての型は`Type`という構造体で表現されます。この構造体には、型の種類（`etype`）、要素型（`type`）、フィールド（`field`）、メソッド（`method`）など、型に関する詳細な情報が含まれています。
*   **前方宣言（Forward Declaration）**: Goでは、型が完全に定義される前にその型を参照する場合があります。例えば、相互に参照し合う構造体やインターフェースの定義です。コンパイラはこのような前方参照を一時的に`TFORW`（Forward Type）としてマークし、後で実際の型定義が解決されたときに更新します。
*   **`updatetype`関数**: この関数は、前方宣言されていた型が最終的にその完全な定義を受け取ったときに呼び出されます。`TFORW`状態の`Type`構造体を、実際の型情報で更新する役割を担います。
*   **`maptype`関数**: この関数は、`map[KeyType]ValueType`のようなマップ型がコンパイラによって構築される際に呼び出されます。このとき、`KeyType`がGoのマップキーの制約（比較可能であること）を満たしているかをチェックします。
*   **`algtype`関数と`ANOEQ`**: `algtype`は、与えられた型がどのような比較アルゴリズムを持つかを判断するコンパイラ内部の関数です。`ANOEQ`は「No Equality」（等価性なし）を意味し、その型が比較不可能であることを示します。

## 技術的詳細

このコミットは、Goコンパイラがマップキーの妥当性チェックを行うタイミングを最適化することで、前方宣言された型がマップキーとして使用される際の誤ったエラー報告を修正します。

1.  **`Type`構造体への`maplineno`フィールドの追加**:
    `src/cmd/gc/go.h`において、`Type`構造体に`int32 maplineno`という新しいフィールドが追加されました。このフィールドの目的は、前方宣言された型（`TFORW`）がマップのキーとして初めて使用されたソースコード上の行番号を記録することです。これにより、コンパイラは型がまだ不完全な状態であっても、その型がマップキーとして参照された事実を記憶し、後で完全な型情報が利用可能になった時点で再チェックを行うための「リマインダー」として機能します。

2.  **`maptype`関数の変更（チェックの遅延）**:
    `src/cmd/gc/subr.c`内の`maptype`関数は、マップ型が構築される際にキー型の妥当性を検証します。
    *   変更前は、キー型が比較不可能（`algtype(key) == ANOEQ`）であると判断されると、即座にエラー（`yyerror`）を報告していました。
    *   変更後は、キー型が比較不可能であり、かつその型が前方宣言された型（`key->etype == TFORW`）である場合に、エラーを即座に報告するのではなく、チェックを遅延させるロジックが追加されました。具体的には、`key->maplineno`がまだ設定されていない場合（つまり、その型がマップキーとして前方参照されたのが初めての場合）、現在のソースコードの行番号（`lineno`）を`key->maplineno`に記録します。これにより、型が完全に定義されるまで、この特定のマップキーの妥当性チェックが保留されます。`maplineno`が既に設定されている場合は、最初の参照箇所のエラーのみを報告するという方針に基づき、更新は行われません。

3.  **`updatetype`関数の変更（遅延チェックの実行）**:
    `src/cmd/gc/dcl.c`内の`updatetype`関数は、前方宣言されていた型がその完全な定義を受け取ったときに呼び出されます。
    *   この関数は、型の定義が更新された後、`n->maplineno`がゼロでないかどうかを確認します。`n->maplineno`がゼロでなければ、それはこの型が以前にマップキーとして前方参照され、その時点ではチェックが遅延されたことを意味します。
    *   その場合、`updatetype`は現在の`lineno`を一時的に保存し、`n->maplineno`に記録されていた行番号を現在の`lineno`として設定します。そして、`maptype(n, types[TBOOL])`を呼び出して、型`n`がマップキーとして有効であるかどうかのチェックを再実行します。この再チェックは、型`n`が完全に定義された状態で行われるため、正確な妥当性判断が可能になります。チェックが完了した後、`lineno`は元の値に戻されます。
    *   このメカニズムにより、コンパイラは型定義の完全なコンテキストが利用可能になった時点で、マップキーの制約を正確に適用できるようになり、`type I interface { m(map[I] bool) }` のような有効な自己参照型定義が正しくコンパイルされるようになります。同時に、`type S struct { m map[S] bool }` のように、比較不可能な構造体型が自己参照的にマップキーとして使用される場合は、型が完全に定義された後も`algtype(S) == ANOEQ`が真となるため、適切なエラーが報告されます。

## コアとなるコードの解説

### `Type`構造体への`maplineno`追加

`Type`構造体に`maplineno`が追加されたことで、Goコンパイラは型定義のライフサイクルを通じて、その型がマップキーとして前方参照された事実と、その参照が発生したソースコード上の位置を記憶できるようになりました。これにより、型が完全に解決されるまで、厳密なマップキーの妥当性チェックを保留することが可能になります。これは、特に循環的な型定義や相互参照を持つ型定義において、コンパイラがより柔軟かつ正確に型を処理するために不可欠な情報となります。

### `maptype`関数内の変更

`maptype`関数内の変更は、マップキーの型チェックの「早期終了」ロジックを修正します。以前は、比較不可能な型がキーとして渡されるとすぐにエラーを報告していましたが、前方宣言された型（`TFORW`）の場合は、その型がまだ完全に定義されていない可能性があるため、エラー報告を遅らせるように変更されました。代わりに、`maplineno`に現在の行番号を記録し、後で再チェックするためのマーカーとします。この変更により、コンパイラは、型がまだ不完全な状態であっても、その型がマップキーとして使用される可能性を認識し、適切なタイミングで最終的な検証を行うことができるようになります。

### `updatetype`関数内の変更

`updatetype`関数内の変更は、型が完全に定義された後の「後処理」ステップです。`maplineno`が設定されている場合、それはこの型が以前にマップキーとして使用され、その時点では前方宣言状態であったことを意味します。`updatetype`は、型が完全に定義された後、`maplineno`に記録された行番号を一時的に使用して`maptype`を再呼び出しします。この再呼び出しにより、型が完全に解決された状態でのマップキーの妥当性チェックが実行され、もし型が依然としてマップキーとして無効であれば、適切なエラーが報告されます。このメカニズムにより、コンパイラは型定義の完全なコンテキストが利用可能になった時点で、マップキーの制約を正確に適用できるようになります。

### テストケースの変更

`test/bugs/bug165.go`が`test/fixedbugs/bug165.go`にリネームされ、テスト内容も更新されました。
*   `type I interface { m(map[I] bool) }` のようなインターフェースの自己参照型が、マップキーとして使用されてもエラーにならないことを確認するテストが追加されました。これは、インターフェースの動的な型が比較可能であればマップキーとして有効であるというGoの仕様に合致します。
*   `type S struct { m map[S] bool }` のような構造体の自己参照型が、マップキーとして使用された場合にエラーになることを確認するテストも追加されました。構造体自体は比較可能ですが、そのフィールドにマップが含まれるため、構造体全体としては比較不可能となり、マップキーとしては無効です。このテストは、コンパイラがこのケースを正しく検出することを確認します。

これらの変更により、Goコンパイラは前方宣言された型とマップキーの制約をより正確に処理できるようになり、言語仕様に準拠した振る舞いを実現しています。

## 変更の背景

Go言語の`flag`パッケージは、コマンドライン引数を解析するための標準的な方法を提供します。`FlagSet`構造体は、フラグの定義と解析を管理し、エラーが発生した場合の挙動を`ErrorHandling`という列挙型で制御します。この`ErrorHandling`には、`ContinueOnError`、`ExitOnError`、`PanicOnError`の3つのモードがあります。

コミットメッセージが指摘するように、特に`ContinueOnError`の挙動は開発者にとって混乱を招きやすいものでした。その名前から「エラーが発生してもフラグの解析を続行する」と誤解されがちですが、実際には「エラーを検出した時点でフラグ解析を中止し、エラーを返してプログラムの実行自体は継続させる」という挙動をします。つまり、「解析を継続する」のではなく、「プログラムの実行を継続する」という意味合いが強かったのです。

この曖昧さが原因で、開発者が意図しないエラーハンドリングロジックを実装したり、フラグ解析の挙動を誤解したりする可能性がありました。このコミットは、このような混乱を解消し、各`ErrorHandling`定数の実際の挙動を明確に文書化することで、`flag`パッケージの使いやすさと堅牢性を向上させることを目的としています。

## 前提知識の解説

### Go言語の`flag`パッケージ

`flag`パッケージは、Goプログラムがコマンドライン引数を解析し、フラグとして定義されたオプションを処理するための機能を提供します。これにより、ユーザーはプログラムの実行時に様々な設定を柔軟に指定できます。

-   **`flag.Parse()`**: グローバルな`FlagSet`（デフォルトの`FlagSet`）を使用してコマンドライン引数を解析します。
-   **`flag.FlagSet`**: 複数のフラグをグループ化し、独立して管理するための構造体です。独自の`FlagSet`を作成することで、異なるコンテキストでフラグを定義・解析できます。
-   **フラグの定義**: `flag.String()`, `flag.Int()`, `flag.Bool()`などの関数を使って、フラグの名前、デフォルト値、説明を指定してフラグを定義します。

### `ErrorHandling`列挙型

`FlagSet`は、フラグ解析中にエラーが発生した場合の挙動を制御するために`ErrorHandling`という型を使用します。これは以下の3つの定数で構成されます。

1.  **`ContinueOnError`**:
    *   **変更前の一般的な理解（誤解）**: エラーが発生してもフラグの解析を続行する。
    *   **実際の挙動**: エラーを検出した時点でフラグの解析を中止し、`FlagSet.Parse()`（または`flag.Parse()`）がエラー値を返します。プログラムは終了せず、呼び出し元がエラーを処理できます。このモードは、エラーが発生してもプログラム自体は終了させずに、エラー情報を取得して後続の処理を決定したい場合に利用されます。
2.  **`ExitOnError`**:
    *   **挙動**: エラーが発生した場合、使用方法メッセージを標準エラー出力に表示し、`os.Exit(2)`を呼び出してプログラムを終了します。これは`FlagSet`のデフォルトの挙動です。
3.  **`PanicOnError`**:
    *   **挙動**: エラーが発生した場合、パニック（panic）を発生させます。これは、回復不可能なエラーとしてプログラムを即座に停止させたい場合や、テスト中に予期せぬフラグエラーを検出したい場合などに使用されます。

このコミットは、特に`ContinueOnError`の「実際の挙動」を明確にすることで、開発者がこれらのエラーハンドリングモードをより適切に選択・利用できるようにすることを目的としています。

## 技術的詳細

このコミットの技術的な変更は、`src/flag/flag.go`ファイル内の`ErrorHandling`列挙型の定数定義に、インラインコメントを追加することに集約されます。

具体的には、以下の変更が行われました。

-   `ErrorHandling`型の定義に対するコメントが、より具体的な説明に更新されました。
    -   変更前: `// ErrorHandling defines how to handle flag parsing errors.`
    -   変更後: `// ErrorHandling defines how FlagSet.Parse behaves if the parse fails.`
    -   これにより、`ErrorHandling`が`FlagSet.Parse`メソッドのエラー時の挙動を定義するものであることが明確になりました。
-   各定数（`ContinueOnError`、`ExitOnError`、`PanicOnError`）に、その挙動を簡潔に説明するコメントが追加されました。
    -   `ContinueOnError`: `// Return a descriptive error.` (記述的なエラーを返す。)
    -   `ExitOnError`: `// Call os.Exit(2).` (`os.Exit(2)`を呼び出す。)
    -   `PanicOnError`: `// Call panic with a descriptive error.` (記述的なエラーでパニックを呼び出す。)

これらのコメントは、Goのコードベースにおける自己文書化の原則に従い、コードを読むだけでその挙動を理解できるようにするためのものです。特に`ContinueOnError`については、その名前が持つ潜在的な誤解を解消し、実際に何が起こるのかを明確にすることで、開発者がこのエラーハンドリングモードを正しく利用できるようになります。

この変更は、GoのAPI設計における「明確さ」と「使いやすさ」を重視する哲学を反映しています。小さな変更ですが、ライブラリの利用者が直感的に挙動を理解できるようになるため、バグの発生を減らし、コードの品質を向上させる効果が期待できます。

## コアとなるコードの解説

上記のdiffは、`src/flag/flag.go`ファイルにおける変更を示しています。

1.  **`type ErrorHandling int` のコメント変更**:
    -   `- // ErrorHandling defines how to handle flag parsing errors.`
    -   `+ // ErrorHandling defines how FlagSet.Parse behaves if the parse fails.`
    -   `ErrorHandling`型自体の説明が、「フラグ解析エラーをどのように処理するか」から「`FlagSet.Parse`が解析に失敗した場合にどのように振る舞うか」へと、より具体的なメソッドの挙動に焦点を当てるように変更されました。これにより、この型が`FlagSet.Parse`のコンテキストで最も関連性が高いことが明確になります。

2.  **`const` ブロックの新しいコメント**:
    -   `+ // These constants cause FlagSet.Parse to behave as described if the parse fails.`
    -   `const`ブロックの直前に新しいコメントが追加され、これから定義される定数群が`FlagSet.Parse`のエラー時の挙動を制御するものであることが明示されました。これは、続く各定数のコメントの導入部として機能します。

3.  **各`ErrorHandling`定数へのインラインコメント追加**:
    -   `ContinueOnError ErrorHandling = iota // Return a descriptive error.`
        -   `ContinueOnError`の行に「記述的なエラーを返す」というコメントが追加されました。これは、このモードがエラーを検出した時点で解析を停止し、エラー値を呼び出し元に返すことを明確に示しています。これにより、「解析を継続する」という誤解が解消されます。
    -   `ExitOnError                          // Call os.Exit(2).`
        -   `ExitOnError`の行に「`os.Exit(2)`を呼び出す」というコメントが追加されました。これは、このモードがプログラムを終了させることを明確に示しています。
    -   `PanicOnError                         // Call panic with a descriptive error.`
        -   `PanicOnError`の行に「記述的なエラーでパニックを呼び出す」というコメントが追加されました。これは、このモードがパニックを発生させることを明確に示しています。

これらの変更は、Goのコードベースにおける自己文書化の原則に則り、コードを読むだけでその挙動を理解できるようにするためのものです。特に`ContinueOnError`のコメントは、その名前が持つ潜在的な誤解を解消し、開発者がこのエラーハンドリングモードを正しく利用できるようになるための重要な改善です。

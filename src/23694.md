## 元コミット内容

このコミットは、`go test`コマンドに`-test.count`フラグを追加し、テストおよびベンチマークを複数回実行する機能を提供します。

具体的には、以下のように使用できます。

```bash
% go test -run XXX -bench . -count 3
```

上記のコマンドは、ベンチマークを3回実行します。出力例を見ると、各ベンチマークが3回ずつ実行され、それぞれの結果が表示されていることがわかります。

また、`-cpu`フラグが設定されている場合、各テストは`-cpu`で指定された各CPU値に対して`n`回実行されます。ただし、`Example`関数は常に1回のみ実行されます。

この機能は、`r` (Rob Pike) によって提案された元の変更（CL 10663）に基づいています。

## 変更の背景

Goのテストフレームワークにおいて、テストやベンチマークの実行は通常1回です。しかし、ソフトウェア開発においては、以下のような状況でテストやベンチマークを複数回実行したいというニーズがあります。

1.  **Flaky Test（不安定なテスト）の検出**: 特定の条件下でのみ失敗するテスト（Flaky Test）は、CI/CDパイプラインの信頼性を低下させます。複数回実行することで、これらの不安定なテストを早期に発見し、修正する機会を得られます。
2.  **ベンチマークの安定性評価**: ベンチマークの結果は、システムの負荷状況や環境要因によって変動することがあります。複数回実行し、その結果を比較することで、ベンチマークの安定性や信頼性を評価し、より正確な性能測定を行うことができます。
3.  **並行処理のテスト**: ゴルーチンやチャネルを用いた並行処理のテストでは、実行順序の非決定性により、まれにデッドロックや競合状態が発生することがあります。複数回実行することで、これらの潜在的な問題を顕在化させやすくなります。

このコミットは、これらの課題に対応するため、`go test`コマンドにシンプルかつ効果的なメカニズムを提供することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のテストに関する基本的な知識が必要です。

*   **`go test`コマンド**: Go言語の標準的なテスト実行ツールです。`go test`コマンドは、カレントディレクトリまたは指定されたパッケージ内のテストファイル（`_test.go`で終わるファイル）をコンパイルし、テスト関数（`TestXxx`）、ベンチマーク関数（`BenchmarkXxx`）、および例関数（`ExampleXxx`）を実行します。
*   **テスト関数 (`TestXxx`)**: `func TestXxx(t *testing.T)`というシグネチャを持つ関数で、ユニットテストや結合テストを記述するために使用されます。
*   **ベンチマーク関数 (`BenchmarkXxx`)**: `func BenchmarkXxx(b *testing.B)`というシグネチャを持つ関数で、コードの性能を測定するために使用されます。`b.N`回ループを実行し、その平均実行時間を測定します。
*   **`testing`パッケージ**: Goの標準ライブラリに含まれるパッケージで、テスト、ベンチマーク、および例を記述するための機能を提供します。`*testing.T`や`*testing.B`などの型が定義されています。
*   **`flag`パッケージ**: コマンドライン引数を解析するためのGoの標準ライブラリパッケージです。`go test`コマンドの`-test.v`や`-test.run`などのフラグは、このパッケージによって処理されます。
*   **`GOMAXPROCS`環境変数と`-cpu`フラグ**: `GOMAXPROCS`は、同時に実行できるOSスレッドの最大数を制御する環境変数です。Go 1.5以降、デフォルトは利用可能なCPUコア数になりました。`go test`の`-cpu`フラグは、ベンチマークを特定の`GOMAXPROCS`値で実行するために使用されます。例えば、`-cpu 1,4`と指定すると、`GOMAXPROCS=1`と`GOMAXPROCS=4`の両方でベンチマークが実行されます。

## 技術的詳細

このコミットの技術的な核心は、`go test`コマンドのフラグ処理と、`testing`パッケージ内でのテスト実行ロジックの変更にあります。

1.  **フラグの定義と伝播**:
    *   `src/cmd/go/alldocs.go`と`src/cmd/go/test.go`：`go test`コマンドのヘルプメッセージに`-count`フラグの説明が追加されます。これにより、ユーザーは新しいフラグの存在とその使い方を認識できます。
    *   `src/cmd/go/testflag.go`：`testFlagDefn`スライスに`{name: "count", passToTest: true}`が追加されます。これは、`go test`コマンドが受け取った`-count`フラグを、実際にテストを実行するプロセス（`go test`が生成するテストバイナリ）に渡す必要があることを示します。`passToTest: true`は、このフラグがテストバイナリに直接渡されるべきであることを意味します。
    *   `src/testing/testing.go`：`testing`パッケージ内で、`count = flag.Uint("test.count", 1, "run tests and benchmarks `n` times")`として、`-test.count`フラグが定義されます。`flag.Uint`を使用することで、フラグの値が符号なし整数として扱われ、デフォルト値は1（つまり、1回実行）に設定されます。

2.  **テスト実行ロジックの変更**:
    *   `src/testing/testing.go`内の`parseCpuList()`関数が変更されます。この関数は、`-cpu`フラグが指定された場合に、どの`GOMAXPROCS`値でテストを実行するかを決定するリスト（`cpuList`）を生成します。
    *   変更前は、`cpuList`に各CPU値が1回ずつ追加されていました。
    *   変更後は、`for i := uint(0); i < *count; i++`というループが導入され、`-test.count`で指定された回数だけ、各CPU値が`cpuList`に追加されるようになります。
    *   これにより、`-cpu`と`-count`が同時に指定された場合、例えば`-cpu 1,4 -count 3`であれば、`GOMAXPROCS=1`で3回、`GOMAXPROCS=4`で3回、合計6回のテスト実行がスケジュールされることになります。
    *   `-cpu`フラグが指定されていない場合（`cpuList == nil`のケース）も同様に、デフォルトの`GOMAXPROCS`値が`-count`回だけ`cpuList`に追加されます。

この変更により、`testing`パッケージは、`cpuList`に基づいてテストを繰り返し実行する既存のメカニズムを再利用しつつ、`-count`フラグの機能を実現しています。

## コアとなるコードの解説

`src/testing/testing.go`の変更がこのコミットの機能の中核をなしています。

1.  **`count`フラグの定義**:
    ```go
    count = flag.Uint("test.count", 1, "run tests and benchmarks `n` times")
    ```
    ここで、`testing`パッケージは`flag`パッケージを使用して`-test.count`という新しいコマンドラインフラグを登録しています。
    *   `"test.count"`: フラグの名前です。`go test`コマンドから渡される際には、`go test -count N`のように指定されますが、テストバイナリ内部では`test.count`として認識されます。
    *   `1`: フラグのデフォルト値です。`-count`が指定されない場合、テストは1回だけ実行されます。
    *   `"run tests and benchmarks `n` times"`: フラグの短い説明です。

2.  **`parseCpuList()`関数の変更**:
    この関数は、`-cpu`フラグが指定された場合に、テストを実行する`GOMAXPROCS`値のリストを構築します。
    変更前は、`-cpu 1,4`と指定された場合、`cpuList`には`[1, 4]`のように各CPU値が1回ずつ追加されていました。
    変更後は、以下のループが導入されました。
    ```go
    for i := uint(0); i < *count; i++ {
        cpuList = append(cpuList, cpu)
    }
    ```
    このループは、`-test.count`で指定された回数だけ、現在の`cpu`値（またはデフォルトの`GOMAXPROCS`値）を`cpuList`に追加します。
    例えば、`-cpu 1 -count 3`の場合、`cpuList`は`[1, 1, 1]`となります。
    `testing`パッケージの内部ロジックは、この`cpuList`の各要素に対してテストスイート全体を1回実行します。したがって、`cpuList`に同じCPU値が複数回含まれることで、テストスイート全体が複数回実行されるという効果が得られます。

この巧妙な変更により、既存のテスト実行メカニズムを大きく変更することなく、`-count`フラグの機能が実現されています。

## 元コミット内容

このコミットは、`go test`コマンドに`-test.count`フラグを導入し、テストおよびベンチマークを複数回実行する機能を追加します。

**使用例:**

```bash
% go test -run XXX -bench . -count 3
```

上記のコマンドは、指定されたベンチマークを3回実行します。出力例からもわかるように、各ベンチマークは指定された回数だけ繰り返し実行され、それぞれの結果が表示されます。

**`-cpu`フラグとの連携:**

もし`-cpu`フラグが同時に設定されている場合、各テストは`-cpu`で指定された各CPU値に対して`n`回（`-count`で指定された回数）実行されます。例えば、`-cpu 1,4 -count 3`と指定すると、`GOMAXPROCS=1`の環境で3回、`GOMAXPROCS=4`の環境で3回、合計6回のテスト実行が行われます。

ただし、`Example`関数（`func ExampleXxx()`）は、このフラグの影響を受けず、常に1回のみ実行されます。

この機能は、Rob Pike氏（`r`）による元の変更提案（CL 10663）に基づいて実装されました。

## 変更の背景

Go言語のテストフレームワークは、シンプルさと効率性を重視していますが、特定のシナリオではテストやベンチマークの単一実行では不十分な場合があります。このコミットは、以下の開発者のニーズに応えるために導入されました。

1.  **不安定なテスト（Flaky Tests）の特定**:
    テストが常に同じ結果を返すとは限りません。環境要因、並行処理のタイミング、外部サービスへの依存などにより、ごくまれに失敗する「不安定なテスト」が存在します。これらのテストは、CI/CDパイプラインの信頼性を損ない、開発者の生産性を低下させます。`-test.count`フラグを使用することで、テストを繰り返し実行し、不安定な挙動を早期に露呈させ、修正を促すことができます。

2.  **ベンチマーク結果の信頼性向上**:
    ベンチマークは、コードの性能を測定するために使用されますが、実行環境のノイズ（OSのスケジューリング、他のプロセスの影響など）によって結果が変動することがあります。複数回ベンチマークを実行し、その結果の平均値やばらつきを分析することで、より信頼性の高い性能評価が可能になります。

3.  **並行処理のデバッグ**:
    Goのゴルーチンとチャネルは強力な並行処理プリミティブを提供しますが、競合状態（race conditions）やデッドロックなどの問題は、特定の実行タイミングでのみ発生することがあります。テストを複数回実行することで、これらの非決定的なバグが顕在化する可能性が高まります。

この機能は、開発者がより堅牢で高性能なGoアプリケーションを構築するための重要なツールとなります。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下のGo言語のテストおよび関連する概念についての知識が不可欠です。

*   **`go test`コマンド**:
    Go言語のビルドシステムに統合されたテスト実行ツールです。`_test.go`で終わるファイル内の`TestXxx`、`BenchmarkXxx`、`ExampleXxx`関数を自動的に発見し、実行します。様々なコマンドラインフラグ（例: `-v`で詳細出力、`-run`で特定のテストの実行、`-bench`でベンチマークの実行）をサポートしています。

*   **`testing`パッケージ**:
    Goの標準ライブラリの一部であり、テスト、ベンチマーク、および例を記述するためのAPIを提供します。
    *   `*testing.T`: テスト関数に渡される型で、テストの失敗報告、ログ出力、ヘルパー関数の呼び出しなどに使用されます。
    *   `*testing.B`: ベンチマーク関数に渡される型で、ベンチマークの実行回数（`b.N`）の制御、タイマーの開始/停止、メモリ割り当ての測定などに使用されます。

*   **`flag`パッケージ**:
    Goの標準ライブラリに含まれるパッケージで、コマンドライン引数を解析し、プログラム内で利用可能な変数にバインドするために使用されます。`go test`コマンド自体も、内部でこのパッケージを利用して様々なフラグを処理しています。このコミットでは、`testing`パッケージが自身のフラグ（`-test.count`など）を定義するために`flag`パッケージを使用しています。

*   **`GOMAXPROCS`環境変数と`-cpu`フラグ**:
    *   `GOMAXPROCS`は、Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数です。Go 1.5以降、デフォルト値は利用可能なCPUコア数に設定されています。
    *   `go test`コマンドの`-cpu`フラグは、ベンチマークを特定の`GOMAXPROCS`値のセットで実行するために使用されます。例えば、`go test -bench . -cpu 1,2,4`と指定すると、ベンチマークは`GOMAXPROCS=1`、`GOMAXPROCS=2`、`GOMAXPROCS=4`の各設定で実行され、並行処理の性能特性を異なるCPU環境で評価できます。

これらの知識は、`-test.count`フラグがどのように`go test`コマンドの既存の機能と統合され、テスト実行の挙動に影響を与えるかを理解する上で重要です。

## 技術的詳細

このコミットの技術的な実装は、`go test`コマンドのフロントエンド（`cmd/go`パッケージ）と、実際のテスト実行ロジックを担う`testing`パッケージの両方に変更を加えています。

1.  **`go test`コマンドライン引数の処理 (`cmd/go`パッケージ)**:
    *   **ドキュメントの更新**: `src/cmd/go/alldocs.go`と`src/cmd/go/test.go`において、`go test`コマンドのヘルプメッセージに`-count n`フラグの説明が追加されました。これにより、ユーザーは`go help test`を実行した際に、この新しいフラグの存在と基本的な使い方を知ることができます。
    *   **フラグの伝播設定**: `src/cmd/go/testflag.go`内の`testFlagDefn`スライスに、`{name: "count", passToTest: true}`というエントリが追加されました。これは非常に重要な変更です。`go test`コマンドは、実際にはテストコードをコンパイルして独立したテストバイナリを生成し、そのバイナリを実行します。`passToTest: true`という設定は、`go test`コマンドが受け取った`-count`フラグとその値を、生成されたテストバイナリにコマンドライン引数として渡す必要があることを示します。これにより、テストバイナリ自身が`-test.count`フラグを認識し、その値に基づいて動作できるようになります。

2.  **テスト実行ロジックの変更 (`testing`パッケージ)**:
    *   **`-test.count`フラグの定義**: `src/testing/testing.go`内で、`testing`パッケージ自身が`flag.Uint("test.count", 1, "run tests and benchmarks `n` times")`を呼び出して、`-test.count`というコマンドラインフラグを定義しています。`flag.Uint`は、フラグの値が符号なし整数であることを示し、デフォルト値は`1`に設定されています。これは、`-count`が指定されない限り、テストは通常通り1回だけ実行されることを意味します。
    *   **`parseCpuList()`関数の変更**: この関数は、`-cpu`フラグが指定された場合に、テストスイートを実行する`GOMAXPROCS`値のリスト（`cpuList`）を構築する役割を担っています。
        *   変更前は、`-cpu 1,4`のように指定された場合、`cpuList`には`[1, 4]`のように各CPU値が1回ずつ追加されていました。
        *   変更後は、以下のコードが導入されました。
            ```go
            for i := uint(0); i < *count; i++ {
                cpuList = append(cpuList, cpu)
            }
            ```
            このループは、`-test.count`で指定された回数（`*count`）だけ、現在の`cpu`値（または`-cpu`が指定されていない場合のデフォルト`GOMAXPROCS`値）を`cpuList`に追加します。
            例えば、`-cpu 1 -count 3`と指定された場合、`cpuList`は`[1, 1, 1]`となります。
            `testing`パッケージの内部では、この`cpuList`の各要素に対してテストスイート全体（すべての`TestXxx`、`BenchmarkXxx`）が1回ずつ実行される既存のメカニズムがあります。したがって、`cpuList`に同じCPU値が複数回追加されることで、テストスイート全体が複数回実行されるという効果が実現されます。

この設計は、既存のテスト実行ループを再利用しつつ、新しい`-test.count`フラグの機能を追加するという、効率的かつ影響範囲の少ない方法で実装されています。

## コアとなるコードの解説

このコミットの機能を実現する上で最も重要な変更は、`src/testing/testing.go`ファイル内の以下の部分です。

1.  **`count`フラグの定義**:
    ```go
    count = flag.Uint("test.count", 1, "run tests and benchmarks `n` times")
    ```
    この行は、`testing`パッケージが自身のコマンドラインフラグとして`-test.count`を登録していることを示します。
    *   `"test.count"`: フラグの内部名です。`go test -count N`のように`go test`コマンドに渡された引数は、テストバイナリ内部では`test.count`として解釈されます。
    *   `1`: このフラグのデフォルト値です。もしユーザーが`-count`フラグを指定しなかった場合、`count`変数の値は`1`となり、テストは通常通り1回だけ実行されます。
    *   `"run tests and benchmarks `n` times"`: このフラグの目的を説明する短い文字列です。

2.  **`parseCpuList()`関数の変更**:
    `parseCpuList()`関数は、`go test`コマンドに`-cpu`フラグが指定された際に、どの`GOMAXPROCS`値でテストを実行すべきかを決定する`cpuList`というスライスを構築します。この`cpuList`の各要素に対して、テストスイート全体が一度実行されるという`testing`パッケージの既存の動作を利用しています。

    変更前は、`-cpu 1,4`と指定された場合、`cpuList`は`[1, 4]`となり、テストスイートは`GOMAXPROCS=1`と`GOMAXPROCS=4`でそれぞれ1回ずつ実行されていました。

    変更後は、以下のループが導入されました。
    ```go
    for i := uint(0); i < *count; i++ {
        cpuList = append(cpuList, cpu)
    }
    ```
    このループは、`-test.count`フラグで指定された回数（`*count`は`count`変数の値、つまりユーザーが`-count`に指定した数値）だけ、現在の`cpu`値（`-cpu`フラグで指定された値、またはデフォルトの`GOMAXPROCS`値）を`cpuList`に追加します。

    **例**:
    *   `go test -cpu 1 -count 3`の場合: `parseCpuList()`は`cpuList`に`1`を3回追加し、`cpuList`は`[1, 1, 1]`となります。結果として、テストスイートは`GOMAXPROCS=1`の環境で3回実行されます。
    *   `go test -cpu 1,4 -count 2`の場合: `cpuList`は`[1, 1, 4, 4]`のようになります。テストスイートは`GOMAXPROCS=1`で2回、`GOMAXPROCS=4`で2回実行されます。

    この変更により、`testing`パッケージは、既存のテスト実行メカニズムを大きく変更することなく、`-test.count`フラグによってテストやベンチマークの実行回数を制御できるようになりました。これは、既存のコードベースの再利用と、新しい機能の効率的な統合の良い例と言えます。

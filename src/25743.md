## 変更の背景

Go言語の `go` および `defer` ステートメントは、関数呼び出しを引数として受け取ります。しかし、プログラマが誤ってその関数呼び出しを括弧で囲んでしまうことがあります。例えば、`go (f())` や `defer (g())` のような記述です。

このコミット以前は、このようなコードに対してコンパイラは「argument to go/defer must be function call」（`go`/`defer` の引数は関数呼び出しでなければなりません）という一般的なエラーメッセージを出力していました。このメッセージは、括弧が問題であるという直接的な情報を含んでおらず、プログラマが問題の原因を特定するのに時間がかかる可能性がありました。

この変更の背景には、ユーザーエクスペリエンスの向上、特にコンパイラのエラーメッセージの明確化があります。より具体的で分かりやすいエラーメッセージを提供することで、開発者はコードの誤りを迅速に特定し、修正できるようになります。この特定のケースでは、括弧の使用が構文的に誤りであるという点を明確に伝えることが目的でした。

## 前提知識の解説

### Go言語の `go` および `defer` ステートメント

*   **`go` ステートメント**: Go言語の並行処理の根幹をなす機能です。`go` キーワードの後に続く関数呼び出しを、新しいゴルーチン（軽量な実行スレッド）として非同期に実行します。
    例: `go myFunction()`
*   **`defer` ステートメント**: `defer` キーワードの後に続く関数呼び出しを、その関数がリターンする直前に実行するようにスケジュールします。主にリソースの解放（ファイルのクローズ、ロックの解除など）に使用されます。
    例: `defer file.Close()`

これらのステートメントは、引数として「関数呼び出し」を期待します。つまり、`myFunction()` のように、関数名とその引数リストが続く形式である必要があります。`myFunction` のように関数名だけを渡したり、`(myFunction())` のように括弧で囲んだりすることは、Goの構文規則上、許可されていません。

### Goコンパイラ (`gc`) の概要

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。`gc` はGo言語で書かれており、複数のステージ（字句解析、構文解析、型チェック、最適化、コード生成など）を経てコンパイルを行います。

*   **構文解析 (Parsing)**: ソースコードを読み込み、Go言語の文法規則に従って抽象構文木 (AST: Abstract Syntax Tree) を構築するプロセスです。ASTは、プログラムの構造を木構造で表現したものです。
*   **抽象構文木 (AST)**: プログラムのソースコードの抽象的な構文構造を、プログラミング言語の構文の各要素に対応するノードを持つツリーとして表現したものです。例えば、関数呼び出しは `OCALL` ノード、括弧で囲まれた式は `OPAREN` ノードとして表現されます。
*   **エラーハンドリング**: コンパイラは、構文エラーや型エラーなど、ソースコード内の問題を発見した際に、適切なエラーメッセージを生成してユーザーに報告します。`Yyerror` は、Goコンパイラ内でエラーメッセージを出力するための関数の一つです。

### `parser.go` と `pseudocall` 関数

`src/cmd/compile/internal/gc/parser.go` は、Goコンパイラの構文解析器の一部です。このファイルには、Go言語の構文を解析し、ASTを構築するためのロジックが含まれています。

`pseudocall` 関数は、`go` および `defer` ステートメントの引数を解析するために使用される内部関数です。これらのステートメントは、通常の関数呼び出しとは異なる特別な処理を必要とするため、このような専用の関数が用意されています。この関数は、引数として与えられた式が有効な関数呼び出しであるかを検証し、そうでない場合はエラーを報告します。

## 技術的詳細

このコミットの核心は、`parser.go` 内の `pseudocall` 関数のロジック変更にあります。

変更前は、`pseudocall` 関数は `p.pexpr(true /* keep_parens */)` を呼び出して式を解析していました。`pexpr` は式を解析する関数で、`keep_parens` 引数が `true` の場合、括弧をASTノードとして保持します。その後、解析された式のASTノード `x` の `Op` (Operation) が `OCALL` (関数呼び出し) でない場合に、一律に「argument to go/defer must be function call」というエラーを出力していました。

このアプローチの問題点は、`go (f())` のようなコードの場合、`f()` 自体は `OCALL` ですが、全体としては `(f())` という「括弧で囲まれた式」として解析され、AST上では `OPAREN` ノードの下に `OCALL` ノードがぶら下がる形になります。しかし、`pseudocall` が受け取る `x` は最上位の `OPAREN` ノードであるため、`x.Op != OCALL` の条件に合致し、一般的なエラーメッセージが出力されていました。

変更後は、`pseudocall` 関数は `p.pexpr(true)` で式を解析した後、`switch` ステートメントを使用して `x.Op` の種類をより詳細にチェックするようになりました。

1.  **`case OCALL:`**: 式が直接関数呼び出し (`OCALL`) であれば、それは有効な引数なので `x` を返します。
2.  **`case OPAREN:`**: 式が括弧で囲まれた式 (`OPAREN`) であれば、`Yyerror("expression in go/defer must not be parenthesized")` という新しいエラーメッセージを出力します。これにより、括弧が問題であることを明確に伝えます。
3.  **`default:`**: 上記のいずれでもない場合（例えば、単なる変数名 `F` など）、以前と同様に `Yyerror("expression in go/defer must be function call")` というエラーメッセージを出力します。これは、式が関数呼び出しの形式ではないことを示します。

この変更により、コンパイラは `go (f())` のようなケースを `OPAREN` として識別し、より具体的なエラーメッセージを提供できるようになりました。また、`go F` のようなケースでは、引き続き「must be function call」というメッセージが出力され、適切なエラーハンドリングが維持されています。

テストファイル `test/fixedbugs/issue4468.go` の変更も重要です。このファイルは、このコミットが修正しようとしている特定のバグや改善点をテストするために追加または修正されたものです。新しいテストケース `go (F)` や `defer (F())` が追加され、それぞれが期待されるエラーメッセージ（`"must be function call|must not be parenthesized"`）を生成するかどうかを検証しています。`|` は、コンパイラのバージョンや最適化の段階によってどちらかのエラーメッセージが出力される可能性があることを示唆しています。

### `src/cmd/compile/internal/gc/parser.go` の変更

1.  **`x := p.pexpr(true) // keep_parens so we can report error below`**:
    `pexpr(true)` の呼び出しは変更されていません。これは、式を解析する際に括弧の情報をASTノードとして保持することを意味します。これにより、後で括弧が存在したかどうかを `OPAREN` ノードとして識別できます。

2.  **`switch x.Op { ... }`**:
    以前の `if x.Op != OCALL` という単純なチェックが、`switch` ステートメントによるより詳細なパターンマッチングに置き換えられました。

    *   **`case OCALL:`**:
        解析された式 `x` が `OCALL` (関数呼び出し) ノードである場合、それは `go` または `defer` の有効な引数であるため、そのまま `x` を返します。これは期待される正常なケースです。

    *   **`case OPAREN:`**:
        解析された式 `x` が `OPAREN` (括弧で囲まれた式) ノードである場合、これは `go (f())` や `defer (f)` のように、関数呼び出しが不必要に括弧で囲まれている状況を意味します。Go言語の構文では、`go` や `defer` の引数に括弧は不要であり、むしろ誤りです。
        このケースでは、`Yyerror("expression in go/defer must not be parenthesized")` という新しい、より具体的なエラーメッセージが出力されます。これにより、プログラマは括弧が問題の原因であることを直接理解できます。
        `// already progressed, no need to advance` というコメントは、`Yyerror` が呼び出された時点でパーサーの状態が適切に進んでいるため、追加のトークン消費などの処理は不要であることを示唆しています。

    *   **`default:`**:
        `OCALL` でも `OPAREN` でもない場合、例えば `go F` のように単に関数名が与えられた場合などがこれに該当します。この場合、引数は関数呼び出しの形式ではないため、以前と同じ `Yyerror("expression in go/defer must be function call")` というエラーメッセージが出力されます。これは、引数が関数呼び出しの形式であるべきだという一般的なエラーを維持します。
        ここでも `// already progressed, no need to advance` というコメントがあります。

3.  **`return nil`**:
    エラーが発生した場合、`pseudocall` 関数は `nil` を返すようになりました。これは、無効なASTノードを返さないことで、後続のコンパイルステージでの不整合やクラッシュを防ぐための標準的なエラー処理パターンです。

このアプローチの問題点は、`go (f())` のようなコードの場合、`f()` 自体は `OCALL` ですが、全体としては `(f())` という「括弧で囲まれた式」として解析され、AST上では `OPAREN` ノードの下に `OCALL` ノードがぶら下がる形になります。しかし、`pseudocall` が受け取る `x` は最上位の `OPAREN` ノードであるため、`x.Op != OCALL` の条件に合致し、一般的なエラーメッセージが出力されていました。

変更後は、`pseudocall` 関数は `p.pexpr(true)` で式を解析した後、`switch` ステートメントを使用して `x.Op` の種類をより詳細にチェックするようになりました。

1.  **`case OCALL:`**: 式が直接関数呼び出し (`OCALL`) であれば、それは有効な引数なので `x` を返します。
2.  **`case OPAREN:`**: 式が括弧で囲まれた式 (`OPAREN`) であれば、`Yyerror("expression in go/defer must not be parenthesized")` という新しいエラーメッセージを出力します。これにより、括弧が問題であることを明確に伝えます。
3.  **`default:`**: 上記のいずれでもない場合（例えば、単なる変数名 `F` など）、以前と同様に `Yyerror("expression in go/defer must be function call")` というエラーメッセージを出力します。これは、式が関数呼び出しの形式ではないことを示します。

この変更により、コンパイラは `go (f())` のようなケースを `OPAREN` として識別し、より具体的なエラーメッセージを提供できるようになりました。また、`go F` のようなケースでは、引き続き「must be function call」というメッセージが出力され、適切なエラーハンドリングが維持されます。

テストファイル `test/fixedbugs/issue4468.go` の変更も重要です。このファイルは、このコミットが修正しようとしている特定のバグや改善点をテストするために追加または修正されたものです。新しいテストケース `go (F)` や `defer (F())` が追加され、それぞれが期待されるエラーメッセージ（`"must be function call|must not be parenthesized"`）を生成するかどうかを検証しています。`|` は、コンパイラのバージョンや最適化の段階によってどちらかのエラーメッセージが出力される可能性があることを示唆しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go` の変更

`pseudocall` 関数の変更は以下の通りです。

1.  **`x := p.pexpr(true) // keep_parens so we can report error below`**:
    `pexpr(true)` の呼び出しは変更されていません。これは、式を解析する際に括弧の情報をASTノードとして保持することを意味します。これにより、後で括弧が存在したかどうかを `OPAREN` ノードとして識別できます。

2.  **`switch x.Op { ... }`**:
    以前の `if x.Op != OCALL` という単純なチェックが、`switch` ステートメントによるより詳細なパターンマッチングに置き換えられました。

    *   **`case OCALL:`**:
        解析された式 `x` が `OCALL` (関数呼び出し) ノードである場合、それは `go` または `defer` の有効な引数であるため、そのまま `x` を返します。これは期待される正常なケースです。

    *   **`case OPAREN:`**:
        解析された式 `x` が `OPAREN` (括弧で囲まれた式) ノードである場合、これは `go (f())` や `defer (f)` のように、関数呼び出しが不必要に括弧で囲まれている状況を意味します。Go言語の構文では、`go` や `defer` の引数に括弧は不要であり、むしろ誤りです。
        このケースでは、`Yyerror("expression in go/defer must not be parenthesized")` という新しい、より具体的なエラーメッセージが出力されます。これにより、プログラマは括弧が問題の原因であることを直接理解できます。
        `// already progressed, no need to advance` というコメントは、`Yyerror` が呼び出された時点でパーサーの状態が適切に進んでいるため、追加のトークン消費などの処理は不要であることを示唆しています。

    *   **`default:`**:
        `OCALL` でも `OPAREN` でもない場合、例えば `go F` のように単に関数名が与えられた場合などがこれに該当します。この場合、引数は関数呼び出しの形式ではないため、以前と同じ `Yyerror("expression in go/defer must be function call")` というエラーメッセージが出力されます。これは、引数が関数呼び出しの形式であるべきだという一般的なエラーを維持します。
        ここでも `// already progressed, no need to advance` というコメントがあります。

3.  **`return nil`**:
    エラーが発生した場合、`pseudocall` 関数は `nil` を返すようになりました。これは、無効なASTノードを返さないことで、後続のコンパイルステージでの不整合やクラッシュを防ぐための標準的なエラー処理パターンです。

### `test/fixedbugs/issue4468.go` の変更

テストファイルでは、新しいエラーメッセージの動作を検証するために、以下のテストケースが追加されました。

*   `go F` と `defer F`: これらは以前から「must be function call」エラーを発生させるケースであり、変更後も同じエラーが期待されます。
*   `go (F)` と `defer (F)`: 関数名 `F` が括弧で囲まれているケースです。これは `OPAREN` ノードとして解析され、新しいエラーメッセージ「must not be parenthesized」または「must be function call」のいずれか（コンパイラの内部状態や解析順序による）が期待されます。
*   `go (F())` と `defer (F())`: 関数呼び出し `F()` が括弧で囲まれているケースです。これも `OPAREN` ノードとして解析され、同様に新しいエラーメッセージが期待されます。

これらのテストケースは、`go` および `defer` ステートメントの引数として括弧が使用された場合に、コンパイラが正しくエラーを検出し、適切なメッセージを出力することを確認します。`// ERROR "..."` コメントは、コンパイラがその行で指定されたエラーメッセージ（またはその一部）を出力することを期待していることを示します。`|` は、複数の可能性のあるエラーメッセージのいずれかがマッチすれば良いことを意味します。

## 変更の背景

Go言語のチャネルは、ゴルーチン間の安全な通信と同期のための主要なプリミティブです。特に「同期チャネル」（バッファサイズが0のチャネル）は、送信操作が対応する受信操作が完了するまでブロックするという厳格な保証を提供します。この特性は、並行処理におけるデッドロックの回避や、イベントの順序付け、リソースの同期など、多くの並行プログラミングパターンにおいて不可欠です。

しかし、このコミットが作成された時点（2009年）では、Go言語の代替コンパイラである `gccgo` において、この同期チャネルの「送信が受信を待つ」という保証が正しく実装されていませんでした。つまり、`gccgo` でコンパイルされたプログラムでは、同期チャネルへの送信が、受信側が値を受け取る前に完了してしまう可能性があり、これによりプログラムのロジックが破綻したり、競合状態が発生したりする危険性がありました。

このコミットの目的は、この `gccgo` のバグを修正し、Go言語の仕様に準拠したチャネルの同期動作を保証することです。そのために、この特定のバグを再現し、修正が正しく適用されたことを検証するための自動テスト `bug147.go` が追加されました。これにより、将来的に同様の回帰が発生することを防ぎ、Goプログラムの移植性と信頼性を高めることができます。

## 前提知識の解説

### Go言語のチャネル

Go言語のチャネルは、ゴルーチン（軽量スレッド）間で値を安全に受け渡しするための通信メカニズムです。チャネルは型付けされており、特定の型の値のみを送信・受信できます。

チャネルには大きく分けて2種類あります。

1.  **非同期チャネル（バッファ付きチャネル）**: `make(chan Type, capacity)` のように、バッファサイズを指定して作成します。バッファが満杯でない限り、送信操作はブロックしません。バッファが空でない限り、受信操作はブロックしません。
2.  **同期チャネル（バッファなしチャネル）**: `make(chan Type)` のように、バッファサイズを0または省略して作成します。これがこのコミットの主題です。

### 同期チャネルの特性

同期チャネルの最も重要な特性は、**送信操作 (`ch <- value`) は、その値が別のゴルーチンによって受信されるまでブロックする**という点です。同様に、**受信操作 (`<-ch`) は、値がチャネルに送信されるまでブロックする**という点です。

この「同期」の性質は、送信側と受信側が「ハンドシェイク」を行うようなものです。両者が同時に準備ができて初めて値の受け渡しが行われ、その間、両方のゴルーチンはブロックされます。これにより、明示的なロックやミューテックスを使用することなく、ゴルーチン間の同期と順序付けを保証できます。

### `gccgo`

`gccgo` は、GCC（GNU Compiler Collection）のフロントエンドとして実装されたGo言語のコンパイラです。Go言語の公式コンパイラである `gc` とは異なる実装であり、GoプログラムをGCCの最適化パイプラインを通じてコンパイルできるという特徴があります。歴史的に、`gccgo` は `gc` コンパイラに比べて開発が遅れることがあり、Go言語の新しい機能やランタイムの挙動が `gc` と完全に一致しないケースが稀に発生していました。このコミットで修正されたバグも、そうした `gccgo` の実装上の差異に起因するものです。

### 並行処理と競合状態

並行処理では、複数の処理が同時に実行されます。この際、共有リソース（この場合は `count` 変数）へのアクセスが適切に同期されていないと、「競合状態（Race Condition）」が発生する可能性があります。競合状態とは、複数のゴルーチンが同時に共有リソースにアクセスし、その結果が実行のタイミングに依存してしまう状態を指します。同期チャネルの「送信が受信を待つ」という保証が破られると、意図しないタイミングで処理が進んでしまい、このような競合状態や不正なプログラム動作を引き起こす原因となります。

## 技術的詳細

`bug147.go` テストは、同期チャネルの動作を検証するために、非常に巧妙な方法を使用しています。

1.  **`count` 変数の導入**: `count` という整数変数が導入され、チャネルの送信・受信のタイミングを追跡するために使用されます。
2.  **ゴルーチンの起動**: メインゴルーチンとは別に、チャネル `c` を引数として受け取る匿名ゴルーチンが起動されます。
3.  **ゴルーチン内の処理**:
    *   `<-c;`: 最初の受信操作。ここでゴルーチンはブロックし、メインゴルーチンからの最初の送信を待ちます。
    *   `count++;`: 受信が完了した後、`count` をインクリメントします。
    *   `time.Sleep(1000000);`: 意図的に長いスリープを挿入します。これは、もし同期チャネルの送信が受信を待たない場合、このスリープ中にメインゴルーチンが次の送信を完了してしまう可能性があることをシミュレートするためです。
    *   `count++;`: スリープ後、`count` を再度インクリメントします。
    *   `<-c;`: 2回目の受信操作。ここでゴルーチンはブロックし、メインゴルーチンからの2回目の送信を待ちます。
4.  **メインゴルーチン内の処理**:
    *   `c <- 1;`: 最初の送信操作。同期チャネルであるため、この送信は匿名ゴルーチンが `<-c` で値を受け取るまでブロックします。
    *   `c <- 2;`: 2回目の送信操作。同様に、匿名ゴルーチンが2回目の `<-c` で値を受け取るまでブロックします。
5.  **検証**:
    *   `if count != 2 { panicln("synchronous send did not wait") }`: 最終的に `count` の値が `2` であることを検証します。

**なぜ `count == 2` が期待されるのか？**

*   `c <- 1;` が実行されると、メインゴルーチンはブロックします。
*   匿名ゴルーチンが `<-c;` で `1` を受信し、`count` が `1` になります。
*   匿名ゴルーチンは `time.Sleep(1000000);` でスリープします。
*   **同期チャネルの正しい動作であれば、メインゴルーチンはまだ最初の `c <- 1` でブロックしたままです。** 匿名ゴルーチンがスリープを終え、`count` が `2` になり、2回目の `<-c;` に到達するまで、メインゴルーチンは次の `c <- 2;` を実行できません。
*   匿名ゴルーチンが2回目の `<-c;` に到達すると、メインゴルーチンの `c <- 2;` が実行され、メインゴルーチンはブロックを解除します。
*   匿名ゴルーチンが `2` を受信し、テストが終了します。

もし `gccgo` のバグが存在し、同期チャネルの送信が受信を待たなかった場合、メインゴルーチンは匿名ゴルーチンが `time.Sleep` 中であっても `c <- 2;` を実行してしまう可能性があります。この場合、匿名ゴルーチンが `count++` を2回実行する前に、メインゴルーチンが `c <- 2` を完了し、`count` の最終的な値が `2` にならない（例えば `1` のままになる）といった状況が発生し、テストが `panicln` を引き起こすことになります。

このテストは、`time.Sleep` を挟むことで、送信と受信の間の時間的な隔たりを作り出し、その間も送信側がブロックし続けることを強制的に検証しています。

## コアとなるコードの変更箇所

このコミットによって追加された唯一のファイルは `test/fixedbugs/bug147.go` です。

```go
// $G $D/$F.go && $L $F.$A && ./$A.out || echo BUG: bug147

// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main
import "time"
func main() {
	var count int;
	c := make(chan byte);
	go func(c chan byte) {
		<-c;
		count++;
		time.Sleep(1000000);
		count++;
		<-c;
	} (c);
	c <- 1;
	c <- 2;
	if count != 2 { panicln("synchronous send did not wait") }
}
```

## コアとなるコードの解説

*   `// $G $D/$F.go && $L $F.$A && ./$A.out || echo BUG: bug147`: これはGoのテストスクリプトが使用するコメント行で、このファイルがどのようにコンパイル・実行されるべきか、そしてテストが失敗した場合に `BUG: bug147` と出力されることを示しています。
*   `package main` と `import "time"`: 実行可能なプログラムであることを示し、`time` パッケージをインポートして `time.Sleep` 関数を使用します。
*   `func main() { ... }`: プログラムのエントリポイントです。
*   `var count int;`: `count` という名前の整数変数を宣言し、初期値は `0` です。この変数は、チャネルの受信が完了した回数を追跡するために使用されます。
*   `c := make(chan byte);`: バッファサイズが `0` の同期チャネル `c` を作成します。このチャネルは `byte` 型の値を送受信します。
*   `go func(c chan byte) { ... } (c);`: 新しいゴルーチンを起動します。このゴルーチンは匿名関数として定義され、チャネル `c` を引数として受け取ります。
    *   `<-c;`: 匿名ゴルーチンはここでブロックし、チャネル `c` から値が送信されるのを待ちます。
    *   `count++;`: 値を受信した後、`count` を `1` にインクリメントします。
    *   `time.Sleep(1000000);`: 匿名ゴルーチンはここで1ミリ秒（1,000,000ナノ秒）スリープします。これは、メインゴルーチンが次の送信を試みる前に、匿名ゴルーチンが確実にこのスリープに入るようにするためのものです。
    *   `count++;`: スリープ後、`count` を `2` にインクリメントします。
    *   `<-c;`: 匿名ゴルーチンは再びここでブロックし、チャネル `c` から次の値が送信されるのを待ちます。
*   `c <- 1;`: メインゴルーチンはチャネル `c` に `1` を送信します。同期チャネルの性質上、この操作は匿名ゴルーチンが `1` を受信するまでブロックします。
*   `c <- 2;`: メインゴルーチンはチャネル `c` に `2` を送信します。同様に、この操作は匿名ゴルーチンが `2` を受信するまでブロックします。
*   `if count != 2 { panicln("synchronous send did not wait") }`: 最後に、`count` の値が `2` であることを検証します。もし `count` が `2` でなければ、それは同期チャネルの送信が受信を待たなかったことを意味し、プログラムは `panicln` を呼び出してエラーメッセージを出力し、テストは失敗します。

このテストは、`count` 変数のインクリメントと `time.Sleep` の配置によって、同期チャネルの「送信が受信を待つ」という厳密な保証が破られていないかを効果的にチェックしています。

# [インデックス 26002] ファイルの概要

このコミットは、Go言語のネットワークパッケージ（`net`）およびWindowsシステムコール（`internal/syscall/windows`）における、ネットワークインターフェースおよびアドレスの識別に関する複数のバグを修正するものです。特に、Windows APIの誤用と`GetAdapterAddresses`関数からの戻り値の不適切な処理が原因で発生していた問題を解決し、Go 1.5から1.5.2までのバージョンで存在したネットワーク機能情報の不正確さを改善します。

## 元コミット内容

`net, internal/syscall/windows: fix interface and address identification on windows`

Go 1.5から1.5.2までの現在の実装は、Windows APIを誤用し、Windows上の`GetAdapterAddresses`からの戻り値を誤って処理していました。この変更は、インターフェースおよびインターフェースアドレスのパーサーを再調整することにより、ネットワーク機能情報に関連する様々な問題を修正します。

以下のIssueを更新します: #5395, #10530, #12301, #12551, #13542。
以下のIssueを修正します: #12691, #12811, #13476, #13544。

また、`net_windows_test.go`内の脆弱なスクリーン・スクレイピング・テストケースも修正します。

レビューアへの追加情報:

上記のほとんどすべての問題は同じ根本原因、つまりWindows APIの誤解にあるようです。MSDNの情報に対する私の解釈が正しければ、現在の実装には以下のバグが含まれています。

- `SIO_GET_INTERFACE_LIST`はIPv6には使用すべきではありません。`SIO_GET_INTERFACE_LIST`の動作はカーネルによって異なり、Windows XP SP2のような古いカーネルではIPv6で正しく動作しない可能性があります。残念ながらMSDNには`SIO_GET_INTERFACE_LIST`の詳細な説明はありませんが、インターネット上の情報がそう示唆しています。
- 固定サイズの領域で`IP_ADAPTER_ADDRESSES`構造体を取得すると、IPv6を使用している場合に機能しない可能性があります。IPv6は様々なアドレススコープに対して大量のインターフェースアドレスを生成するため、領域を適切に調整する必要があります。
- `IP_ADAPTER_ADDRESSES`構造体の`PhysicalAddress`フィールドには余分なスペースが含まれる場合があります。`IP_ADAPTER_ADDRESS`構造体の`PhysicalAddressLength`フィールドを無視することはできません。
- `IP_ADAPTER_ADDRESSES`構造体の`Flags`フィールドは、管理上および運用上のステータスを表すものではありません。これは単にWindowsネットワークアダプターの設定を表すものです。
- `IP_ADAPTER_ADDRESSES`構造体の`MTU`フィールドは、64ビットプラットフォームで`uint32(-1)`を持つ場合があります。この値を適切に整数に変換する必要があります。
- `IP_ADAPTER_ADDRESSES`構造体の`IfType`フィールドはビットフィールドではありません。このフィールドに対するビットワイズ操作は完全に間違っています。
- `IP_ADAPTER_ADDRESSES`構造体の`OperStatus`フィールドはビットフィールドではありません。このフィールドに対するビットワイズ操作は完全に間違っています。
- `IP_ADAPTER_ADDRESSES`構造体の`IPv6IfIndex`フィールドは`IfIndex`フィールドの代替に過ぎません。`IfIndex`よりも`IPv6IfIndex`を優先することはできません。
- Windows XP、2003サーバー以前のOSでは、`IP_ADAPTER_UNICAST_ADDRESS`構造体の`OnLinkPrefixLength`フィールドが設定されません。古いカーネルではこのフィールドに依存することはできません。代わりに`IP_ADAPTER_ADDRESSES`構造体の`FirstPrefix`フィールドと`IP_ADAPTER_PREFIX`構造体を使用できます。
- `IP_ADAPTER_{UNICAST,ANYCAST,MULTICAST}_ADDRESS`構造体の`Length`フィールドは、アドレスプレフィックス長を表すものではありません。これは単にソケットアドレス長を表すものです。

## 変更の背景

Go言語のネットワークパッケージは、オペレーティングシステム固有のネットワークインターフェース情報を取得するために、各OSのシステムコールを利用しています。Windows環境においては、`iphlpapi.dll`が提供する`GetAdaptersAddresses`関数が主要な情報源となります。しかし、Go 1.5から1.5.2までの実装では、この`GetAdaptersAddresses`関数および関連するWindows APIの利用方法に複数の誤りがありました。

具体的には、以下のような問題が報告されていました。

1.  **不正確なネットワークインターフェース情報の取得**: インターフェースのMTU、物理アドレス、フラグ（アップ/ダウン、ループバック、ブロードキャストなど）が正しく取得されない、または誤って解釈される。
2.  **IPv6アドレスの不正確なプレフィックス長**: IPv6アドレスのサブネットマスク（プレフィックス長）が正しく計算されない。特にWindows XPやWindows Server 2003のような古いOSでは、`OnLinkPrefixLength`フィールドが利用できないため、問題が顕著でした。
3.  **バッファオーバーフローの可能性**: `GetAdapterAddresses`関数は、必要なバッファサイズが不足している場合に`ERROR_BUFFER_OVERFLOW`を返すことがあります。既存の実装では、このバッファサイズ調整が不適切で、特にIPv6アドレスが多数存在する環境で問題が発生しやすかった。
4.  **テストの脆弱性**: ネットワークインターフェース情報を取得するテストが、環境に依存する「スクリーン・スクレイピング」手法に頼っており、不安定でした。

これらの問題は、GoアプリケーションがWindows上でネットワークインターフェース情報を正確に取得できないという、深刻なバグにつながっていました。例えば、特定のインターフェースにバインドしようとしたり、ネットワーク構成を分析したりする際に、誤った情報に基づいて動作してしまう可能性がありました。このコミットは、これらの根本的な原因を特定し、Windows APIの正しい利用方法に基づいて実装を修正することで、Goのネットワークパッケージの堅牢性と正確性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のWindowsネットワークAPIと関連する概念についての知識が必要です。

1.  **`GetAdaptersAddresses`関数**:
    *   Windows IP Helper APIの一部で、ローカルコンピュータに構成されているネットワークアダプターに関する詳細な情報を取得するために使用されます。
    *   `IP_ADAPTER_ADDRESSES`構造体のリンクリストを返します。この構造体には、アダプター名、説明、MACアドレス、MTU、インターフェースタイプ、運用ステータス、そしてそのアダプターに関連付けられたIPアドレス（ユニキャスト、エニーキャスト、マルチキャスト）のリストなどが含まれます。
    *   この関数は、必要なバッファサイズが不足している場合、`ERROR_BUFFER_OVERFLOW`を返して、必要なサイズを`SizePointer`引数に設定します。呼び出し元はこのサイズを使ってより大きなバッファを再割り当てし、関数を再呼び出しする必要があります。
    *   `GAA_FLAG_INCLUDE_PREFIX`フラグを指定すると、`IP_ADAPTER_PREFIX`構造体のリストも取得でき、これはアドレスのプレフィックス情報を提供します。

2.  **`IP_ADAPTER_ADDRESSES`構造体**:
    *   個々のネットワークアダプターに関する情報を格納する主要な構造体です。
    *   `IfIndex`と`Ipv6IfIndex`: インターフェースのインデックス。IPv6IfIndexはIPv6アドレスを持つインターフェースのインデックスですが、多くの場合IfIndexと同じか代替として使用されます。
    *   `PhysicalAddress`と`PhysicalAddressLength`: アダプターのMACアドレスとその長さ。`PhysicalAddress`フィールドは可変長であるため、`PhysicalAddressLength`を正確に参照する必要があります。
    *   `Mtu`: 最大転送単位。
    *   `IfType`: インターフェースのタイプ（例: イーサネット、ループバック、PPPなど）。これはビットフィールドではなく、単一の値を持ちます。
    *   `OperStatus`: インターフェースの現在の運用ステータス（例: アップ、ダウン）。これもビットフィールドではありません。
    *   `FirstUnicastAddress`, `FirstAnycastAddress`, `FirstMulticastAddress`, `FirstPrefix`: それぞれユニキャスト、エニーキャスト、マルチキャストアドレス、およびプレフィックスのリンクリストへのポインタ。
    *   `OnLinkPrefixLength` (in `IP_ADAPTER_UNICAST_ADDRESS`): Windows Vista以降で利用可能なフィールドで、ユニキャストIPアドレスのオンリンクプレフィックス長（サブネットマスクのビット数）を示します。Windows XPや2003 Serverではこのフィールドは設定されません。

3.  **`IP_ADAPTER_PREFIX`構造体**:
    *   `GetAdaptersAddresses`関数が`GAA_FLAG_INCLUDE_PREFIX`フラグと共に呼び出された場合に返される、IPアドレスプレフィックス情報を格納する構造体です。
    *   `PrefixLength`: プレフィックス長（サブネットマスクのビット数）を直接提供します。これは古いWindowsバージョンで`OnLinkPrefixLength`の代替として使用できます。

4.  **`SIO_GET_INTERFACE_LIST` IOCTL**:
    *   ソケットI/Oコントロールコマンドの一つで、システム上のインターフェースのリストを取得するために使用されます。
    *   コミットメッセージで指摘されているように、IPv6に対しては信頼性が低い、または正しく動作しない可能性があります。`GetAdaptersAddresses`がより推奨される方法です。

5.  **Go言語の`net`パッケージ**:
    *   Goプログラムがネットワークインターフェースやアドレス情報を扱うための標準ライブラリです。`net.Interfaces()`や`net.Interface.Addrs()`などの関数を提供します。これらの関数は内部的にOS固有のシステムコールを呼び出します。

これらのAPIと構造体の詳細な動作、特に異なるWindowsバージョン間での挙動の違いを理解することが、このコミットの修正内容を把握する上で重要です。

## 技術的詳細

このコミットの技術的詳細は、主にWindows APIの正確な利用と、それによって得られるネットワークインターフェース情報の適切な解析に焦点を当てています。

1.  **`GetAdaptersAddresses`のバッファ管理の改善**:
    *   以前の実装では、`IP_ADAPTER_ADDRESSES`構造体を格納するためのバッファサイズを固定値（15KB）で初期化し、`ERROR_BUFFER_OVERFLOW`が発生した場合にのみ再試行していました。しかし、IPv6アドレスが多数存在する環境では、この固定サイズでは不十分であり、再試行ロジックも不完全でした。
    *   新しい`adapterAddresses`関数では、推奨される初期サイズ（15KB）でバッファを確保し、`GetAdaptersAddresses`が`ERROR_BUFFER_OVERFLOW`を返した場合、関数が要求する正確なサイズ（`l`変数に格納される）でバッファを再割り当てし、再試行するロバストなメカニズムを導入しています。これにより、あらゆるネットワーク構成で確実にアダプター情報を取得できるようになりました。

2.  **Windowsバージョンの検出とAPIの互換性**:
    *   `IP_ADAPTER_UNICAST_ADDRESS`構造体の`OnLinkPrefixLength`フィールドはWindows Vista以降で導入されました。Windows XPや2003 Serverではこのフィールドが利用できません。
    *   `probeWindowsIPStack`関数が追加され、`syscall.GetVersion()`を使用してOSのメジャーバージョンをチェックし、Windows Vista以降であるかどうか（`supportsVistaIP`）を判定します。
    *   この`supportsVistaIP`フラグに基づいて、アドレスのプレフィックス長を決定するロジックが分岐されます。古いOSでは`IP_ADAPTER_PREFIX`構造体からプレフィックス長を導出する新しいメカニズムが使用されます。

3.  **インターフェース情報の正確な解析**:
    *   **`IfIndex`と`IPv6IfIndex`**: 以前は`IPv6IfIndex`が0でない場合に`IfIndex`よりも優先されていましたが、コミットメッセージで指摘されているように、`IPv6IfIndex`は`IfIndex`の代替に過ぎません。新しいコードでは、`IfIndex`が0の場合にのみ`IPv6IfIndex`を使用するように修正されています。
    *   **`PhysicalAddress`**: `IP_ADAPTER_ADDRESSES`構造体の`PhysicalAddress`フィールドは、`PhysicalAddressLength`で示される長さのバイト配列です。以前は配列全体をそのまま使用していましたが、余分なスペースが含まれる可能性があったため、`PhysicalAddressLength`に基づいて正確な長さのバイトスライスをコピーするように修正されました。
    *   **`MTU`**: `MTU`フィールドが64ビットプラットフォームで`uint32(-1)`を返す可能性がある問題に対応するため、この値が検出された場合は`-1`として扱うように修正されました。
    *   **`IfType`と`OperStatus`の誤解の修正**: コミットメッセージで強調されているように、これらのフィールドはビットフィールドではありません。以前のコードでビットワイズ操作が行われていた場合、それは誤りでした。このコミットでは、`IfType`と`OperStatus`の値を直接比較し、それに基づいてGoの`net.Interface`構造体の`Flags`フィールド（`FlagUp`, `FlagLoopback`, `FlagBroadcast`, `FlagMulticast`, `FlagPointToPoint`）を適切に設定するようにロジックが変更されました。特に、`IfType`に基づいてインターフェースの特性（ブロードキャスト、マルチキャスト、ポイントツーポイント、ループバック）を推測するロジックが導入されました。
    *   **`SIO_GET_INTERFACE_LIST`の廃止**: IPv6での信頼性の問題から、`getInterfaceInfos`関数（内部で`SIO_GET_INTERFACE_LIST`を使用）が削除され、`GetAdaptersAddresses`からの情報のみを使用するように統一されました。

4.  **アドレスプレフィックス長の計算ロジック**:
    *   Windows XP/2003 Serverで`OnLinkPrefixLength`が利用できない問題に対応するため、`addrPrefixTable`と`addrPrefixLen`という新しいヘルパー関数が導入されました。
    *   `addrPrefixTable`は、`IP_ADAPTER_ADDRESSES`構造体の`FirstPrefix`リンクリストを走査し、`IP_ADAPTER_PREFIX`構造体からIPv4およびIPv6のプレフィックス情報を抽出します。
    *   `addrPrefixLen`は、与えられたIPアドレスが属する最も具体的なプレフィックス長を、抽出されたプレフィックスリストから線形探索で決定します。これは、古いOSでの正確なサブネットマスクの取得を可能にします。

これらの変更により、GoのネットワークパッケージはWindows環境において、より正確で堅牢なネットワークインターフェースおよびアドレス情報を提供できるようになりました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に`src/net/interface_windows.go`ファイルに集中しています。

1.  **`src/net/interface_windows.go`**:
    *   `getAdapters()`関数と`getInterfaceInfos()`関数が削除されました。
    *   `supportsVistaIP`グローバル変数と`probeWindowsIPStack()`関数が追加され、Windows Vista以降のIPスタックサポートを検出します。
        ```go
        var supportsVistaIP bool

        func init() {
        	supportsVistaIP = probeWindowsIPStack()
        }

        func probeWindowsIPStack() (supportsVistaIP bool) {
        	v, err := syscall.GetVersion()
        	if err != nil {
        		return true // Windows 10 and above will deprecate this API
        	}
        	if byte(v) < 6 { // major version of Windows Vista is 6
        		return false
        	}
        	return true
        }
        ```
    *   `adapterAddresses()`関数が新しく追加され、`GetAdaptersAddresses`を呼び出して`IP_ADAPTER_ADDRESSES`のリストを動的に取得します。バッファオーバーフローを適切に処理します。
        ```go
        func adapterAddresses() ([]*windows.IpAdapterAddresses, error) {
        	var b []byte
        	l := uint32(15000) // recommended initial size
        	for {
        		b = make([]byte, l)
        		err := windows.GetAdaptersAddresses(syscall.AF_UNSPEC, windows.GAA_FLAG_INCLUDE_PREFIX, 0, (*windows.IpAdapterAddresses)(unsafe.Pointer(&b[0])), &l)
        		if err == nil {
        			if l == 0 {
        				return nil, nil
        			}
        			break
        		}
        		if err.(syscall.Errno) != syscall.ERROR_BUFFER_OVERFLOW {
        			return nil, os.NewSyscallError("getadaptersaddresses", err)
        		}
        		if l <= uint32(len(b)) { // Avoid infinite loop if l doesn't grow
        			return nil, os.NewSyscallError("getadaptersaddresses", err)
        		}
        	}
        	var aas []*windows.IpAdapterAddresses
        	for aa := (*windows.IpAdapterAddresses)(unsafe.Pointer(&b[0])); aa != nil; aa = aa.Next {
        		aas = append(aas, aa)
        	}
        	return aas, nil
        }
        ```
    *   `interfaceTable`関数が大幅に書き直され、`adapterAddresses()`からの情報を使用して`net.Interface`構造体を構築します。`IfType`と`OperStatus`に基づいて`Flags`を設定するロジックが修正されました。

        // 変更後の interfaceTable の一部抜粋
        func interfaceTable(ifindex int) ([]Interface, error) {
        	aas, err := adapterAddresses()
        	if err != nil {
        		return nil, err
        	}
        	var ift []Interface
        	for _, aa := range aas {

        		if index == 0 { // ipv6IfIndex is a sustitute for ifIndex
        			index = aa.Ipv6IfIndex
        		}

        			ifi := Interface{
        				Index: int(index),
        				Name:  syscall.UTF16ToString((*(*[10000]uint16)(unsafe.Pointer(aa.FriendlyName)))[:]),
        			}
        			if aa.OperStatus == windows.IfOperStatusUp {
        				ifi.Flags |= FlagUp
        			}
        			// ... IfTypeに基づくFlagsの設定ロジック ...
        			if aa.Mtu == 0xffffffff {
        				ifi.MTU = -1
        			} else {
        				ifi.MTU = int(aa.Mtu)
        			}
        			if aa.PhysicalAddressLength > 0 {
        				ifi.HardwareAddr = make(HardwareAddr, aa.PhysicalAddressLength)
        				copy(ifi.HardwareAddr, aa.PhysicalAddress[:])
        			}
        			ift = append(ift, ifi)
        			if ifindex == ifi.Index {
        				break
        			}
        		}
        	}
        	return ift, nil
        }

        	if err != nil {
        		return nil, err

        					} else {

        					}
        					// ... IPNetの構築 ...
        				}
        			}

        	}

## コアとなるコードの解説

このコミットの核心は、Windowsのネットワークインターフェース情報を取得する際のGoの`net`パッケージの信頼性と正確性を根本的に改善した点にあります。

1.  **`adapterAddresses()`関数による堅牢な情報取得**:
    *   以前の`getAdapters()`関数は、`GetAdapterAddresses`のバッファ管理を誤っていました。特にIPv6環境では、多数のアドレスが存在するため、固定サイズのバッファではすぐにオーバーフローし、情報の取得に失敗する可能性がありました。
    *   新しい`adapterAddresses()`関数は、`GetAdapterAddresses`が返す`ERROR_BUFFER_OVERFLOW`エラーを適切に処理し、必要なサイズにバッファを動的に拡張して再試行するロジックを実装しています。これにより、どのようなネットワーク構成であっても、すべてのアダプター情報を確実に取得できるようになりました。これは、Windows APIの推奨される利用パターンに厳密に従ったものです。

2.  **Windowsバージョンに応じたプレフィックス長計算の適応**:
    *   `IP_ADAPTER_UNICAST_ADDRESS`構造体の`OnLinkPrefixLength`フィールドは、IPv6アドレスのプレフィックス長を直接提供しますが、これはWindows Vista以降でしか利用できません。Windows XPや2003 Serverのような古いOSでは、このフィールドは常に0でした。
    *   `supportsVistaIP`フラグの導入により、Goは実行中のWindowsのバージョンを検出し、それに応じてプレフィックス長の計算方法を切り替えます。
    *   古いWindowsバージョンでは、`IP_ADAPTER_ADDRESSES`構造体に含まれる`FirstPrefix`リンクリストを走査し、`IP_ADAPTER_PREFIX`構造体からプレフィックス長を取得する`addrPrefixTable`と`addrPrefixLen`関数が使用されます。これにより、古いOSでも正確なサブネットマスク情報を提供できるようになりました。これは、APIの互換性の問題を巧みに解決する重要な変更です。

3.  **`net.Interface`構造体への正確なマッピング**:
    *   `interfaceTable`関数は、`adapterAddresses()`から取得した生データ（`IP_ADAPTER_ADDRESSES`構造体）をGoの`net.Interface`構造体にマッピングする役割を担います。
    *   このマッピングロジックが大幅に改善されました。例えば、`PhysicalAddress`の長さが`PhysicalAddressLength`フィールドによって正確に指定されるように修正され、`MTU`の`uint32(-1)`という特殊な値が適切に処理されるようになりました。
    *   最も重要なのは、`IfType`と`OperStatus`フィールドがビットフィールドではないという理解に基づき、`net.Interface`の`Flags`フィールド（`FlagUp`, `FlagLoopback`, `FlagBroadcast`など）が正しく設定されるようになった点です。以前はこれらのフィールドに対して誤ったビットワイズ操作が行われていた可能性がありましたが、新しい実装では、`IfType`の値に基づいてインターフェースの特性を推測し、適切なフラグを設定します。これにより、Goアプリケーションが取得するインターフェースの特性が、Windowsの実際の状態と一致するようになりました。

これらの変更は、GoのネットワークパッケージがWindows環境でより信頼性の高いネットワーク情報を提供するための基盤を築き、多くの既存のバグを解決しました。

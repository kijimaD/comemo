# [インデックス 23218] ファイルの概要

このコミットは、Go言語のツールチェインにおける`cmd/go`と`cmd/cgo`の2つの主要なファイルを変更しています。

- `src/cmd/cgo/out.go`: `cgo`ツールがCコードを生成する際の挙動、特に`gccgo`バックエンドを使用する場合のエクスポート関数の生成ロジックを修正しています。
- `src/cmd/go/build.go`: `go`コマンドのビルドロジック、特に`gccgo`ツールチェインで`-buildmode=c-archive`を使用する際のリンカフラグ、スタック分割の扱い、および`CgoLDFLAGS`の処理方法を調整しています。

## 変更の背景

このコミットの主な背景は、Go言語の`gccgo`コンパイラバックエンドにおいて、`-buildmode=c-archive`のサポートを拡張することにあります。

元々、Goの標準コンパイラ（`gc`）では、`http://golang.org/cl/8094`で`-buildmode=c-archive`のサポートが導入されました。これは、GoのコードをC言語から呼び出し可能なスタティックライブラリとしてビルドする機能です。しかし、この機能は`gccgo`には適用されていませんでした。

`gccgo`は、Go言語のコードをGCC（GNU Compiler Collection）のフロントエンドとしてコンパイルするもので、`gc`とは異なるランタイムとリンケージの特性を持っています。特に、`gc`が`runtime/cgo`パッケージを通じて`runtime_iscgo`変数を設定するのに対し、`gccgo`にはこれに相当するパッケージがありませんでした。そのため、`cgo`を使用するGoプログラムが`gccgo`でビルドされた際に、ランタイムがCgoが使用されていることを正しく認識できない問題がありました。

また、`-buildmode=c-archive`でGoオブジェクトをリンクする際に、`-r`リンカフラグ（再配置可能な出力ファイルを生成）が使用されますが、これにはスタックの扱いに関する特定の要件がありました。特に、`386`および`amd64`アーキテクチャでは、Cコードのコンパイル時に`-fsplit-stack`フラグが必要となることが判明しました。これは、Goのスタック管理とCのスタック管理の間の互換性を確保し、不必要なスタック分割を減らすためです。

さらに、`gccgo`は`gc`とは異なり、`runtime/cgo`パッケージを使用しないため、標準パッケージの`CgoLDFLAGS`（Cgoリンカフラグ）が`gccgo`のビルドプロセスに誤って適用されることを避ける必要がありました。これらの背景から、`gccgo`における`-buildmode=c-archive`の完全なサポートと、それに伴う`cgo`および`go`ツールの挙動の調整が必要となりました。

## 前提知識の解説

### Go言語のコンパイラバックエンド (`gc`と`gccgo`)

Go言語には主に2つのコンパイラバックエンドが存在します。

-   **`gc` (Go Compiler)**: Goプロジェクトの公式かつデフォルトのコンパイラです。Go言語で書かれており、Goのランタイムと密接に統合されています。高速なコンパイルと最適化が特徴です。
-   **`gccgo`**: GCC（GNU Compiler Collection）の一部として実装されたGo言語のフロントエンドです。GoのコードをGCCの中間表現に変換し、GCCの最適化パスとコード生成バックエンドを利用します。これにより、GCCがサポートする多様なアーキテクチャやプラットフォームでGoコードをコンパイルできる利点があります。しかし、`gc`とは異なるランタイム（libgo）を使用し、Cgoの統合方法も異なります。

### `cgo`

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoツールです。GoとCの間の相互運用性を提供します。`cgo`を使用すると、Goのソースコード内にCのコードを直接記述し、Goのビルドプロセスの一部としてCコンパイラとリンカを呼び出すことができます。

### `-buildmode=c-archive`

Go 1.4で導入されたビルドモードの一つです。このモードを使用すると、GoのパッケージをC言語からリンク可能なスタティックライブラリ（`.a`ファイル）としてビルドできます。これにより、既存のC/C++プロジェクトにGoの機能を組み込むことが可能になります。生成されるアーカイブファイルには、Goのランタイムと指定されたGoパッケージのコンパイル済みコードが含まれます。

### `runtime_iscgo`

Goランタイム内部で使用される変数で、現在のプログラムが`cgo`を使用しているかどうかを示すフラグです。`gc`コンパイラの場合、`runtime/cgo`パッケージがインポートされると、この変数が設定され、ランタイムがCgo関連の初期化や処理を行うべきであることを示します。`gccgo`の場合、`runtime/cgo`のような特定のパッケージに依存せず、Cgoが使用されていることをランタイムに伝える別のメカニズムが必要です。

### `-fsplit-stack`

GCCコンパイラ（およびClang）のオプションの一つです。このフラグは、関数呼び出しごとにスタックを動的に拡張できるように、スタックを小さなチャンクに分割するコードを生成するようコンパイラに指示します。これにより、非常に深い再帰呼び出しや大きなスタックフレームを持つ関数でも、スタックオーバーフローのリスクを軽減し、メモリ使用量を効率化できます。Goのランタイムは独自のスタック管理メカニズムを持っているため、Cgoを介してCコードとGoコードが相互作用する場合、スタックの互換性を確保するためにこのオプションが重要になることがあります。

### `-Wl,--whole-archive` と `-Wl,--no-whole-archive`

これらはリンカ（通常は`ld`）に渡されるオプションで、`-Wl,`は続く文字列をリンカオプションとして解釈するようコンパイラに指示します。

-   **`--whole-archive`**: このオプションとそれに続くアーカイブファイル（`.a`）の間にあるすべてのオブジェクトファイルを、たとえ参照されていなくても強制的にリンクに含めるようリンカに指示します。通常、リンカはアーカイブファイルから、プログラムが明示的に参照するシンボルを定義しているオブジェクトファイルのみを抽出してリンクします。
-   **`--no-whole-archive`**: `--whole-archive`の効果を打ち消し、通常のリンキング動作に戻します。

これらは、ライブラリ内の初期化コードなど、直接参照されないが実行時に必要となるコードを確実にリンクに含めるために使用されます。

### `ar` コマンド

`ar`は「archiver」の略で、複数のファイルを単一のアーカイブファイル（通常は`.a`拡張子を持つ）にまとめるためのUnix系システムコマンドです。主にスタティックライブラリの作成に使用されます。リンカはこれらのアーカイブファイルから必要なオブジェクトファイルを抽出して最終的な実行可能ファイルを生成します。

## 技術的詳細

このコミットは、`gccgo`における`-buildmode=c-archive`のサポートを、以下の主要な技術的変更によって実現しています。

1.  **`runtime_iscgo`の`gccgo`対応**:
    -   `src/cmd/cgo/out.go`において、`gccgo`用の`_cgo_export.c`ファイルに`gccgoExportFileProlog`という新しいCコードのプロローグが追加されました。
    -   このプロローグには、`runtime_iscgo`という`_Bool`型の外部変数（`__attribute__ ((weak))`で弱参照として宣言）と、`GoInit`というコンストラクタ関数（`__attribute__ ((constructor))`）が含まれています。
    -   `GoInit`関数は、プログラムの起動時に自動的に実行され、`&runtime_iscgo`が有効な場合（つまり、`runtime_iscgo`シンボルが存在する場合）に`runtime_iscgo = 1`を設定します。これにより、`gccgo`ランタイムがCgoを使用していることを正しく認識できるようになります。弱参照を使用することで、古いバージョンの`gccgo`との互換性も保たれています。
    -   また、`_cgo_wait_runtime_init_done()`という弱参照の外部関数が追加され、Cgoエクスポート関数が呼び出される前にランタイムの初期化完了を待機するロジックが追加されました。これは、Goランタイムが完全に初期化される前にCgo経由でGo関数が呼び出されることによる潜在的な問題を回避するためです。

2.  **`-buildmode=c-archive`のリンキングロジック (`gccgo`)**:
    -   `src/cmd/go/build.go`の`gccgoToolchain.ld`関数が大幅に修正されました。
    -   `-buildmode=c-archive`の場合、Goのオブジェクトファイルを単一の`.o`ファイルにリンクするために、リンカに`-Wl,-r`（再配置可能な出力ファイルを生成）と`-nostdlib`（標準ライブラリをリンクしない）が渡されます。
    -   特に重要なのは、`-lgolibbegin`ライブラリを`-Wl,--whole-archive`と`-Wl,--no-whole-archive`で囲んでリンクしている点です。`-lgolibbegin`はGoランタイムの初期化コードを含んでいますが、直接参照されるシンボルを定義しないため、`--whole-archive`を使用しないとリンカによって除外されてしまう可能性があります。これにより、Goランタイムの初期化が確実に行われるようになります。
    -   生成されるのはオブジェクトファイルであるため、ビルドID（`--build-id`）は不要であり、`b.disableBuildID(ldflags)`を呼び出してビルドIDの生成を抑制しています。
    -   最終的に、Goのオブジェクトファイルがリンクされた`.o`ファイルが生成された後、`ar rc realOut out`コマンドを使用して、この`.o`ファイルを指定された出力ファイル名（`realOut`）のアーカイブファイル（`.a`）に格納します。

3.  **`-fsplit-stack`の適用**:
    -   `src/cmd/go/build.go`の`gccgoToolchain.cc`関数（Cコードのコンパイル）と`builder.cgo`関数（Cgoが生成するCコードのコンパイル）において、`386`および`amd64`アーキテクチャの場合に`-fsplit-stack`フラグがCコンパイラに渡されるようになりました。
    -   これは、`-r`リンカフラグを使用する際に必要であり、GoとCのスタック管理の間の互換性を確保し、不必要なスタック分割を減らす目的があります。

4.  **`CgoLDFLAGS`のフィルタリング**:
    -   `src/cmd/go/build.go`の`gccgoToolchain.ld`関数において、標準パッケージ（`a.p.Standard`が`true`）からの`CgoLDFLAGS`が収集されないように変更されました。
    -   これは、`gccgo`が`runtime/cgo`パッケージを使用しないため、そのパッケージに含まれる`CgoLDFLAGS`が`gccgo`のビルドプロセスに誤って影響を与えることを避けるためです。

これらの変更により、`gccgo`ユーザーはGoコードをC言語から呼び出し可能なスタティックライブラリとしてビルドできるようになり、`gccgo`とCgoの統合がより堅牢になりました。

### `src/cmd/cgo/out.go`の変更

-   **`gccgoExportFileProlog`の追加**:
    -   `_cgo_export.c`ファイル（Cgoが生成するC言語のソースファイル）の冒頭に、`gccgoExportFileProlog`という定数文字列の内容が追加されるようになりました。
    -   このプロローグには、`runtime_iscgo`という`_Bool`型の外部変数（`__attribute__ ((weak))`で弱参照）と、`GoInit`というコンストラクタ関数（`__attribute__ ((constructor))`）の宣言と定義が含まれています。
    -   `GoInit`関数は、プログラム起動時に自動的に実行され、`runtime_iscgo`変数が存在すれば（`&runtime_iscgo`でアドレスが取得できれば）、その値を`1`に設定します。これにより、`gccgo`ランタイムがCgoが使用されていることを認識し、適切な初期化処理を行うことができるようになります。弱参照を使用することで、`runtime_iscgo`シンボルが存在しない古い`gccgo`バージョンとの互換性も維持されます。
    -   また、`_cgo_wait_runtime_init_done()`という弱参照の外部関数も宣言されており、Cgoエクスポート関数が呼び出される前にランタイムの初期化完了を待機するロジックが追加されています。これは、Goランタイムが完全に初期化される前にCgo経由でGo関数が呼び出されることによる競合状態やクラッシュを防ぐための安全策です。

### `src/cmd/go/build.go`の変更

-   **`CgoLDFLAGS`のフィルタリング**:
    -   `gccgoToolchain.ld`関数内で、`allactions`（ビルド対象のすべてのアクション）をループする際に、`a.p.Standard`（標準パッケージかどうか）をチェックする条件が追加されました。
    -   `gccgo`は`runtime/cgo`パッケージを使用しないため、`runtime/cgo`のような標準パッケージから提供される`CgoLDFLAGS`が`gccgo`のビルドに誤って適用されるのを防ぐために、標準パッケージの`CgoLDFLAGS`は収集されなくなりました。

-   **`-buildmode=c-archive`のリンキングロジックの追加**:
    -   `ldBuildmode == "c-archive"`の場合の新しいリンキングロジックが`gccgoToolchain.ld`関数内の`switch`文に追加されました。
    -   Goのオブジェクトファイルを単一の`.o`ファイルにリンクするために、リンカに`-Wl,-r`（再配置可能な出力ファイルを生成）と`-nostdlib`（標準ライブラリをリンクしない）が渡されます。
    -   `-lgolibbegin`ライブラリは、`-Wl,--whole-archive`と`-Wl,--no-whole-archive`で囲まれてリンクされます。これは、`libgolibbegin`がGoランタイムの初期化コードを含んでいるものの、直接参照されるシンボルを定義しないため、リンカがその内容を削除してしまうのを防ぐためです。これにより、Goランタイムの初期化が確実に実行されます。
    -   生成されるのは実行可能ファイルではなくオブジェクトファイルであるため、`b.disableBuildID(ldflags)`を呼び出してビルドIDの生成を抑制しています。
    -   最終的に、Goのオブジェクトファイルがリンクされた中間`.o`ファイルが生成された後、`ar rc realOut out`コマンドが実行され、この中間`.o`ファイルが最終的なアーカイブファイル（`.a`）にまとめられます。

-   **`-fsplit-stack`の適用**:
    -   `gccgoToolchain.cc`関数（Cコードのコンパイル）と`builder.cgo`関数（Cgoが生成するCコードのコンパイル）において、ターゲットアーキテクチャが`386`または`amd64`の場合に、Cコンパイラに`-fsplit-stack`フラグが追加されるようになりました。
    -   これは、Goのスタック管理とCのスタック管理の間の互換性を確保し、特に`-r`リンカフラグを使用する際に発生しうるスタック関連の問題を回避するために重要です。

-   **`disableBuildID`ヘルパー関数の追加**:
    -   `builder`構造体に`disableBuildID`という新しいヘルパー関数が追加されました。
    -   この関数は、リンカフラグのリストを受け取り、`goos`（オペレーティングシステム）が`android`, `dragonfly`, `linux`, `netbsd`のいずれかである場合に、`-Wl,--build-id=none`フラグを追加します。
    -   これは、一部のシステム（例: Ubuntu）でデフォルトでビルドIDが生成されるのを防ぐためのもので、実行可能ファイルや共有ライブラリではなくオブジェクトファイルを生成する際に不要なビルドIDを抑制します。

これらの変更により、`gccgo`コンパイラを使用するGoプロジェクトでも、GoコードをC言語から呼び出し可能なスタティックライブラリとしてビルドする機能が完全にサポートされ、Cgoとの連携がよりスムーズかつ堅牢になりました。

## 変更の背景

デバッグはソフトウェア開発において不可欠なプロセスであり、デバッガがソースコードの正確な位置を特定できることはその効率に直結します。コンパイラは、ソースコードを機械語に変換する際に、デバッグ情報と呼ばれるメタデータを生成します。このデバッグ情報には、機械語のアドレスと元のソースコードのファイル名、行番号、列番号とのマッピングが含まれており、これを「ラインテーブル」と呼びます。

Go言語の `debug/dwarf` パッケージは、GoプログラムがELF形式などの実行ファイルに埋め込まれたDWARFデバッグ情報を読み取るための機能を提供します。このパッケージのラインテーブルリーダーが正確に機能することは、Goのデバッガがユーザーに正しいソースコードのコンテキストを提供するために極めて重要です。

このコミットは、`debug/dwarf` パッケージのラインテーブルリーダーの正確性を検証するために、包括的な単体テストを追加することを目的としています。異なるコンパイラ（GCCとClang）で生成されたELFバイナリを使用し、それらのバイナリから `readelf` ツールで抽出した既知の正しいラインテーブル情報と、Goのラインテーブルリーダーが解析した結果を比較することで、実装の堅牢性を保証します。これにより、Goのデバッグツールが様々な環境で生成されたバイナリに対しても信頼性の高いデバッグ情報を提供できるようになります。

## 前提知識の解説

### DWARF (Debugging With Arbitrary Record Formats)

DWARFは、コンパイラが生成するデバッグ情報の標準フォーマットです。プログラムのソースコードとコンパイルされたバイナリコードとの間のマッピングを提供し、デバッガがソースレベルでのデバッグを可能にするために使用されます。DWARF情報には、変数、型、関数、ソースファイル、行番号などの詳細が含まれます。

### DWARF ラインテーブル

DWARFラインテーブルは、DWARFデバッグ情報の一部であり、機械語の命令アドレスと、それに対応するソースコードのファイル名、行番号、列番号とのマッピングを定義します。デバッガは、このラインテーブルを使用して、プログラムの実行中に現在の命令がソースコードのどの位置にあるかを特定し、ユーザーに表示します。また、ブレークポイントの設定やステップ実行の際にも利用されます。ラインテーブルは通常、実行ファイル内の `.debug_line` セクションに格納されます。

### ELF (Executable and Linkable Format)

ELFは、Unix系オペレーティングシステム（Linuxなど）で広く使用されている、実行可能ファイル、オブジェクトコード、共有ライブラリ、コアダンプの標準ファイルフォーマットです。ELFファイルは、プログラムのコード、データ、メタデータなど、様々なセクションで構成されます。DWARFデバッグ情報は、通常、ELFファイル内の特定の `.debug_` プレフィックスを持つセクション（例: `.debug_info`, `.debug_line`）に埋め込まれます。

### `readelf` ツール

`readelf` は、ELF形式のバイナリファイルの内容を表示するためのGNU Binutilsの一部であるコマンドラインツールです。特に、デバッグ情報（DWARF）を含む様々なセクションの内容を解析し、人間が読める形式で出力する機能があります。
このコミットでは、`readelf --debug-dump=rawline,decodedline` コマンドを使用して、ELFバイナリからDWARFラインテーブルの生データとデコードされたデータを抽出し、Goのラインテーブルリーダーの出力と比較するための「正解」データとして利用しています。

### Go `debug/dwarf` パッケージ

Go言語の標準ライブラリに含まれる `debug/dwarf` パッケージは、GoプログラムからDWARFデバッグ情報にアクセスするためのインターフェースを提供します。このパッケージは、`debug/elf`、`debug/macho`、`debug/pe` などの他の `debug` パッケージを通じて、実行ファイルからDWARFデータを読み込み、解析することができます。これにより、Goで書かれたデバッガやプロファイラなどのツールが、コンパイルされたプログラムの内部構造を理解し、ソースレベルでの情報を提供することが可能になります。

## 技術的詳細

このコミットで追加されたテストは、`debug/dwarf` パッケージのラインテーブルリーダーが、異なるコンパイラ（GCCとClang）によって生成されたELFバイナリからDWARFラインテーブルを正確に解析できることを検証します。テストの核心は、Goのリーダーが解析した結果と、`readelf` ツールが生成する既知の正しいラインテーブル情報を比較することにあります。

### `LineEntry` 構造体

`LineEntry` 構造体は、DWARFラインテーブルの各エントリを表します。これは、特定の機械語アドレスに対応するソースコードの位置情報を含みます。

```go
type LineEntry struct {
	Address       uint64    // 機械語命令のアドレス
	File          *LineFile // ソースファイル情報へのポインタ
	Line          int       // ソースコードの行番号
	Column        int       // ソースコードの列番号
	IsStmt        bool      // ステートメントの開始位置であるか (ブレークポイント推奨位置)
	BasicBlock    bool      // 基本ブロックの開始であるか
	PrologueEnd   bool      // プロローグの終了であるか
	EpilogueBegin bool      // エピローグの開始であるか
	EndSequence   bool      // シーケンスの終了であるか
	Discriminator uint64    // 最適化されたコードで同じ行の異なる基本ブロックを区別するための識別子
}
```

### `LineFile` 構造体

`LineFile` 構造体は、ソースファイルに関する情報を含みます。

```go
type LineFile struct {
	Name string // ファイルの絶対パス
}
```

### テストの仕組み

1.  **テストバイナリの生成**:
    *   `line1.c`, `line1.h`, `line2.c` というシンプルなC言語のソースファイルが用意されています。
    *   これらのソースファイルは、GCC (Ubuntu 4.8.2) と Clang (Ubuntu 3.4) を使用して、デバッグ情報 (`-g` フラグ) 付きでELFバイナリ (`line-gcc.elf`, `line-clang.elf`) としてコンパイルされます。

2.  **期待値の定義**:
    *   `TestLineELFGCC` と `TestLineELFClang` 関数では、それぞれのコンパイラで生成されたバイナリに対して、`readelf --debug-dump=rawline,decodedline` の出力に基づいて手動で作成された `[]LineEntry` スライスの `want` 変数が定義されています。これが、Goのラインテーブルリーダーが返す「べき」正しいラインテーブル情報です。

3.  **ラインテーブルの読み取りと比較**:
    *   `testLineTable` ヘルパー関数が、ELFバイナリからDWARFデータを読み込み、`d.LineReader(cu)` を使用してラインリーダーを取得します。
    *   `lr.Next(&line)` を繰り返し呼び出すことで、ラインテーブルの各エントリを読み取り、`got` スライスに格納します。
    *   最終的に、`compareLines(got, want)` 関数を使用して、Goのリーダーが解析した `got` スライスと、`readelf` に基づく `want` スライスが一致するかどうかを検証します。

### `LineReader` の機能テスト (`TestLineSeek`)

`TestLineSeek` 関数は、`LineReader` のより高度な機能である `Tell()`, `Reset()`, `Seek()`, `SeekPC()` メソッドの正確性を検証します。

*   **`Tell()`**: 現在のラインテーブルリーダーの位置を `LineReaderPos` 型で返します。これにより、後でその位置に戻ることができます。
*   **`Reset()`**: ラインリーダーをラインテーブルの最初の位置にリセットします。
*   **`Seek(pos LineReaderPos)`**: 以前 `Tell()` で取得した位置にラインリーダーを移動させます。これにより、ラインテーブル内を自由に移動できます。
*   **`SeekPC(pc uint64, line *LineEntry)`**: 指定されたプログラムカウンタ (PC) アドレス `pc` に対応するラインエントリを検索し、`line` に格納します。これは、デバッガが特定の命令アドレスに対応するソースコードの行を迅速に特定するために非常に重要な機能です。テストでは、各ラインエントリのアドレス範囲を網羅的にチェックし、正しい `LineEntry` が返されることを確認しています。

これらのテストは、Goの `debug/dwarf` パッケージが、様々なコンパイラや複雑なラインテーブル構造に対しても、正確かつ効率的にデバッグ情報を提供できることを保証するための重要な基盤となります。

このファイルは、DWARFラインテーブルリーダーのテストロジックを含んでいます。

#### `TestLineELFGCC` および `TestLineELFClang`

これらのテスト関数は、GCCとClangでそれぞれ生成されたELFバイナリからラインテーブルを読み取り、事前に `readelf` の出力に基づいて作成された期待値 (`want` スライス) と比較します。

```go
	//   # gcc -g -o line-gcc.elf line*.c

	// Line table based on readelf --debug-dump=rawline,decodedline
	want := []LineEntry{
		// ... 期待されるLineEntryのリスト ...
	}

	testLineTable(t, want, elfData(t, "testdata/line-gcc.elf"))

```

`want` スライスには、各 `LineEntry` の `Address`, `File`, `Line`, `IsStmt`, `Discriminator` (GCCの場合) などのフィールドが正確に定義されています。`File` フィールドは、`LineFile` 構造体へのポインタであり、ソースファイルのパスを含みます。

#### `compareLines` および `dumpLines`

*   `compareLines(a, b []LineEntry) bool`: 2つの `LineEntry` スライスが等しいかどうかを比較します。`EndSequence` の場合や `File.Name` の比較など、特定のフィールドの比較ロジックが含まれています。
*   `dumpLines(t *testing.T, lines []LineEntry)`: テスト失敗時に、比較のために `LineEntry` スライスを整形してログに出力するヘルパー関数です。

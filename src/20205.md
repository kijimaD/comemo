# [インデックス 20205] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）における`select`ステートメントのチャネル評価順序に関するバグを修正するものです。具体的には、`select`ステートメント内の受信チャネルの式が、ソースコードに記述された順序で厳密に評価されるようにし、パニック発生時の挙動が予測可能になるように変更されました。

## コミット

```
commit 20e97677fd61dbdca128e9628e28327988c39bb4
Author: Russ Cox <rsc@golang.org>
Date:   Mon Aug 25 07:05:45 2014 -0400

    cmd/gc: fix order of channel evaluation of receive channels
    
    Normally, an expression of the form x.f or *y can be reordered
    with function calls and communications.
    
    Select is stricter than normal: each channel expression is evaluated
    in source order. If you have case <-x.f and case <-foo(), then if the
    evaluation of x.f causes a panic, foo must not have been called.
    (This is in contrast to an expression like x.f + foo().)
    
    Enforce this stricter ordering.
    
    Fixes #8336.
    
    LGTM=dvyukov
    R=golang-codereviews, dvyukov
    CC=golang-codereviews, r
    https://golang.org/cl/126570043
```

## 元コミット内容

通常のGoの式評価では、`x.f`や`*y`のような式は、関数呼び出しやチャネル通信と再順序付けされる可能性があります。しかし、`select`ステートメントはより厳密な評価順序を持ちます。`select`内の各チャネル式は、ソースコードに記述された順序で評価される必要があります。例えば、`case <-x.f`と`case <-foo()`というケースがある場合、もし`x.f`の評価がパニックを引き起こすなら、`foo()`は呼び出されてはなりません。このコミットは、この厳密な順序付けを強制することを目的としています。

## 変更の背景

Go言語の`select`ステートメントは、複数のチャネル操作を同時に待ち受けるための強力な構文です。その動作はGo言語仕様によって厳密に定義されています。通常のGoの式評価では、コンパイラはプログラムの観測可能な動作を変更しない限り、式の評価順序を最適化のために再順序付けすることが許されています。例えば、`a() + b()`のような式では、`a()`と`b()`のどちらが先に評価されるかは保証されません。

しかし、`select`ステートメントのチャネル式には、この通常のルールとは異なる、より厳密な評価順序の要件があります。具体的には、`select`ステートメント内の各チャネル式（例: `<-ch`、`ch <- val`）は、ソースコードに記述された順序で評価されなければなりません。この厳密な順序付けは、特にチャネル式の評価中にパニックが発生した場合に重要になります。

このコミット以前は、Goコンパイラ（`cmd/gc`）がこの`select`の厳密な評価順序を完全に強制できていませんでした。特に、`x.f`のようなポインタのフィールドアクセスや、`*y`のような間接参照を含むチャネル式が、コンパイラの最適化によって再順序付けされる可能性がありました。これにより、例えば`case <-x.c`（`x`が`nil`の場合パニック）と`case <-foo()`という`select`があった場合、`x.c`の評価がパニックを引き起こす前に`foo()`が呼び出されてしまうという、予期せぬ動作が発生する可能性がありました。これは、Go言語仕様が意図する`select`の動作、すなわち「`x.c`の評価がパニックを引き起こすなら、`foo()`は呼び出されてはならない」という原則に反します。

この問題は、GoのIssue #8336として報告され、このコミットによって修正されました。この修正は、`select`ステートメントの信頼性と予測可能性を保証するために不可欠でした。

## 前提知識の解説

### Goの`select`ステートメントの動作

`select`ステートメントは、複数の通信操作（チャネルの送受信）を同時に待ち受けるためのGoの制御構造です。
*   `select`は、いずれかのケースが準備できるまでブロックします。
*   複数のケースが準備できた場合、`select`はそれらのうちの1つをランダムに選択して実行します。選択の順序は保証されません。
*   `default`ケースが存在する場合、どのケースも準備できていないときに`default`ケースが即座に実行されます。
*   各`case`内のチャネル式（例: `ch`、`ch <- val`の`ch`や`val`）は、`select`ステートメントに入ったときに、ソースコードに記述された順序で一度だけ評価されます。

### Goにおける式の評価順序と再順序付け

Go言語では、式の評価順序は通常、言語仕様によって厳密に定義されています。しかし、コンパイラは、プログラムの観測可能な動作（observable behavior）を変更しない限り、式の評価順序を最適化のために再順序付け（reordering）することが許されています。観測可能な動作とは、プログラムの外部から見える副作用（例: 関数呼び出し、チャネル通信、パニック）を指します。

例えば、`f() + g()`という式では、`f()`と`g()`のどちらが先に実行されるかは保証されません。これは、両者の関数呼び出しが独立しており、その結果が足し算に影響を与えるだけで、外部から見える副作用の順序が重要でないためです。

### パニックとリカバリ

Goには、実行時エラーを処理するための`panic`と`recover`というメカニズムがあります。
*   `panic`は、通常のプログラムフローを中断し、現在のゴルーチンを停止させます。
*   `recover`は、`defer`関数内で呼び出されることで、パニックから回復し、プログラムの実行を継続させることができます。
`panic`は、プログラムの異常終了を示すものであり、その発生タイミングはプログラムの観測可能な動作の一部と見なされます。

### チャネル操作

Goのチャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネル操作（送信`ch <- val`と受信`<-ch`）は、同期的な通信であり、Goの並行処理の根幹をなします。チャネル操作は副作用を持つため、その評価順序は重要です。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラ（`cmd/gc`）が`select`ステートメントのチャネル式を処理する方法にあります。Go言語仕様では、`select`内のチャネル式はソースコード順に評価されると規定されています。これは、通常の式評価における再順序付けの可能性とは対照的です。

問題は、`x.f`のようなフィールドアクセスや`*y`のような間接参照を含むチャネル式が、コンパイラの最適化フェーズで「巻き上げ（hoisting）」され、`select`ステートメントの他のチャネル式の評価よりも前に実行されてしまう可能性があったことです。例えば、`case <-x.c`というケースで`x`が`nil`の場合、`x.c`の評価はパニックを引き起こします。もしこの`x.c`の評価が、`select`内の別のケース（例: `case <-foo()`）のチャネル式よりも前に、かつソースコードの順序を無視して実行されてしまうと、`foo()`が呼び出されるべきではない状況で呼び出されてしまうという問題が発生します。

このコミットは、この問題を解決するために、`select`ステートメント内のチャネル式、特に受信チャネルの式が、常に一時変数にコピー（hoist）されるように変更しました。これにより、これらの式の評価が`select`の他のチャネル式の評価よりも前に、かつソースコードの順序を無視して再順序付けされることを防ぎます。

具体的には、`src/cmd/gc/order.c`内の`orderstmt`関数が修正されました。この関数は、GoのAST（抽象構文木）を走査し、式の評価順序を決定する役割を担っています。`select`ステートメントの処理において、受信チャネルの式（`r->right->left`）が単なる名前（`ONAME`）でない場合（つまり、`x.c`のような複合式の場合）、その式全体が`ordercopyexpr`関数によって一時変数にコピーされます。この一時変数へのコピーは、式の評価を強制的にその時点で行わせる効果があり、後続の最適化による再順序付けを防ぎます。

この変更により、`select`ステートメントのチャネル式の評価は、Go言語仕様に厳密に準拠し、パニック発生時の挙動が予測可能かつ一貫性のあるものとなりました。

## コアとなるコードの解説

### `src/cmd/gc/order.c`の変更

`order.c`は、Goコンパイラのバックエンドの一部であり、ASTノードを線形化し、式の評価順序を決定する役割を担っています。このファイル内の`orderstmt`関数は、`select`ステートメントの処理を担当する部分です。

追加されたコメントは、`select`の評価順序が通常の式よりも厳密であることを明確に示しています。特に、`p.c`のような式でさえ一時変数に「巻き上げ（hoisted）」る必要があると述べています。これは、`p`が`nil`の場合に発生するパニックのタイミングが、他のチャネル式の評価順序に影響を与えないようにするためです。

重要な変更は、`orderstmt`関数内の`select`ケースを処理するループの中にあります。

```c
					orderexpr(&r->right->left, order);
					if(r->right->left->op != ONAME)
						r->right->left = ordercopyexpr(r->right->left, r->right->left->type, order, 0);
```

*   `r->right->left`は、`case <-c`のような受信操作におけるチャネル式`c`を表します。
*   `orderexpr(&r->right->left, order);`は、まずこのチャネル式を通常の順序付けルールに従って処理します。
*   `if(r->right->left->op != ONAME)`: この条件は、チャネル式が単なる変数名（`ONAME`）ではない場合、つまり`x.c`のような複合式である場合に真となります。単なる変数名であれば、その評価はすでに完了しているか、再順序付けの懸念が少ないため、特別な処理は不要です。
*   `r->right->left = ordercopyexpr(r->right->left, r->right->left->type, order, 0);`: この行がこのコミットの核心です。`ordercopyexpr`関数は、与えられた式（`r->right->left`）を評価し、その結果を新しい一時変数に格納します。そして、元の式ノードをこの一時変数を参照するノードに置き換えます。これにより、複合チャネル式（例: `x.c`）の評価が、`select`ステートメントの他のチャネル式の評価よりも前に、かつソースコードの順序に従って強制的に行われるようになります。もし`x`が`nil`であれば、この時点でパニックが発生し、`select`内の後続のチャネル式（例: `foo()`）は評価されなくなります。

この修正により、`select`ステートメントのチャネル式の評価順序がGo言語仕様に厳密に準拠し、パニック発生時の挙動が予測可能になりました。

### `test/fixedbugs/issue8336.go`の追加

このテストファイルは、修正されたバグを具体的に再現し、修正が正しく機能することを確認するために追加されました。

```go
package main

type X struct {
	c chan int
}

func main() {
	defer func() {
		recover()
	}()
	var x *X
	select {
	case <-x.c: // should fault and panic before foo is called
	case <-foo():
	}
}

func foo() chan int {
	println("BUG: foo must not be called")
	return make(chan int)
}
```

*   `X`という構造体が定義され、その中にチャネル`c`が含まれています。
*   `main`関数内で、`x`という`*X`型の変数が`nil`で宣言されます。
*   `defer func() { recover() }()`は、パニックが発生してもプログラムがクラッシュしないようにするためのものです。これにより、テストの実行を継続し、`println`が呼び出されるかどうかを確認できます。
*   `select`ステートメントには2つのケースがあります。
    *   `case <-x.c:`: `x`は`nil`なので、`x.c`にアクセスしようとすると`nil`ポインタデリファレンスによるパニックが発生します。
    *   `case <-foo():`: `foo()`関数は`"BUG: foo must not be called"`という文字列を出力し、新しいチャネルを返します。
*   このテストの意図は、`x.c`の評価がパニックを引き起こす前に`foo()`が呼び出されてはならない、というものです。修正前は、コンパイラの最適化によって`foo()`が先に評価されてしまい、`"BUG: foo must not be called"`が出力される可能性がありました。修正後は、`x.c`の評価が強制的に先に行われ、パニックが発生するため、`foo()`は呼び出されず、`"BUG: foo must not be called"`は出力されません。これにより、`select`の厳密な評価順序が正しく適用されていることが確認できます。

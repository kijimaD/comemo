# [インデックス 24215] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージにおける、HTTP/1.1 の `Expect: 100-continue` ヘッダを伴うリクエスト処理に関するバグ修正です。具体的には、`Expect: 100-continue` ヘッダを持つリクエストが送信され、サーバー側のハンドラがリクエストボディを完全に読み込まなかった場合に、そのコネクションを再利用しないように変更することで、コネクションの状態が不明になる問題を解決しています。

## 元コミット内容

`net/http: don't reuse conns after incomplete 100-continue requests`

このコミットは、`Expect: 100-continue` ヘッダを持つHTTPリクエストにおいて、ハンドラがリクエストボディをEOF（End Of File）まで読み込まなかった場合に、そのコネクションを再利用しないようにするものです。これにより、コネクションが不明な状態になることを防ぎます。

## 変更の背景

HTTP/1.1では、クライアントが大きなリクエストボディを送信する前に、サーバーがそのリクエストを受け入れる準備ができているかを確認するために `Expect: 100-continue` ヘッダを使用できます。クライアントはまずヘッダのみを送信し、サーバーが `100 Continue` レスポンスを返した場合にのみ、残りのリクエストボディを送信します。これにより、サーバーがリクエストを拒否する場合に、無駄なデータ転送を防ぐことができます。

しかし、このメカニズムには潜在的な問題があります。サーバーが `100 Continue` を返した後、クライアントがリクエストボディを送信しますが、サーバー側のハンドラが何らかの理由でそのボディを完全に読み込まない（EOFに到達しない）ことがあります。この場合、コネクションの入力バッファには未読のデータが残っている可能性があり、そのコネクションを再利用すると、次のリクエストがこの未読データから始まってしまい、プロトコル違反やデータ破損を引き起こす可能性があります。

特に、一部のHTTPクライアントは、サーバーが `100 Continue` をサポートしていない可能性を考慮し、一定時間内に `100 Continue` レスポンスが来ない場合でも、リクエストボディを送信し始めることがあります。この挙動と、サーバー側がボディを完全に読み込まないケースが組み合わさると、コネクションの状態がさらに複雑になり、予測不能な動作につながる可能性がありました。

このコミットは、Goの `net/http` パッケージがこのような状況でコネクションを安全に処理できるようにするための修正であり、Issue 11549で報告された問題を解決します。

## 前提知識の解説

### HTTP/1.1 `Expect: 100-continue`

- **目的**: クライアントが大きなリクエストボディを送信する前に、サーバーがそのリクエストを受け入れる準備ができているかを確認するためのメカニズム。
- **動作**:
    1.  クライアントは `Expect: 100-continue` ヘッダを含むリクエストヘッダのみを送信します。
    2.  サーバーは、リクエストヘッダを検証し、リクエストを受け入れる準備ができていれば `100 Continue` ステータスコードを返します。
    3.  クライアントは `100 Continue` を受け取った後、リクエストボディを送信します。
    4.  もしサーバーがリクエストを拒否する場合（例: `401 Unauthorized` や `403 Forbidden`）、クライアントはリクエストボディを送信せずに処理を中止できます。
- **問題点**: クライアントが `100 Continue` を待たずにボディを送信し始めるタイムアウト機構を持つ場合や、サーバーがボディを完全に読み込まない場合に、コネクションの状態が不明瞭になることがあります。

### TCPコネクションの再利用 (Keep-Alive)

- **目的**: HTTP/1.1では、複数のリクエスト/レスポンスサイクルで同じTCPコネクションを再利用する「Keep-Alive」がデフォルトで有効です。これにより、新しいコネクションを確立するオーバーヘッド（TCPハンドシェイク、TLSハンドシェイクなど）を削減し、パフォーマンスを向上させます。
- **条件**: コネクションを再利用するためには、両端（クライアントとサーバー）が現在のリクエスト/レスポンスの境界を明確に認識している必要があります。特に、サーバーは現在のリクエストボディの終わり（EOF）を正確に知る必要があります。
- **問題点**: `Expect: 100-continue` のシナリオで、サーバーがリクエストボディをEOFまで読み込まなかった場合、コネクションの入力ストリームにはまだデータが残っている可能性があります。この状態でコネクションを再利用すると、次のリクエストのヘッダが、前のリクエストの未読ボディの一部として解釈されてしまう危険性があります。

### `io.Reader` と `io.EOF`

- Go言語では、データの読み込みは `io.Reader` インターフェースを通じて行われます。
- `Read` メソッドは、読み込むデータがない場合に `io.EOF` エラーを返します。これは、ストリームの終端に達したことを示します。
- HTTPリクエストボディを完全に読み込むことは、`io.EOF` が返されるまで `Read` を呼び出し続けることを意味します。

## 技術的詳細

このコミットの技術的な核心は、`net/http` パッケージ内の `expectContinueReader` 構造体と、`server.go` 内のコネクション処理ロジックの変更にあります。

1.  **`expectContinueReader` への `sawEOF` フィールドの追加**:
    -   `expectContinueReader` は、`Expect: 100-continue` ヘッダを持つリクエストのボディをラップする `io.ReadCloser` の実装です。
    -   このコミットでは、`expectContinueReader` に `sawEOF bool` という新しいフィールドが追加されました。このフィールドは、リクエストボディの読み込み中に `io.EOF` が検出されたかどうかを追跡します。

2.  **`Read` メソッドでの `sawEOF` の設定**:
    -   `expectContinueReader` の `Read` メソッド内で、基になる `readCloser` からの読み込みが `io.EOF` を返した場合に、`ecr.sawEOF` が `true` に設定されるようになりました。これにより、ボディが完全に読み込まれたかどうかの状態が保持されます。

3.  **コネクション再利用ロジックの変更**:
    -   `server.go` 内の `(*conn).serve` メソッド（またはそれに相当するリクエスト処理の終端）において、レスポンスを送信する直前に、コネクションを再利用するかどうかの判断ロジックが追加されました。
    -   具体的には、現在のリクエストのボディが `*expectContinueReader` 型であり、かつ `ecr.sawEOF` が `false` の場合（つまり、`Expect: 100-continue` リクエストであったにもかかわらず、ボディがEOFまで読み込まれなかった場合）、`w.closeAfterReply` が `true` に設定されます。
    -   `w.closeAfterReply = true` は、現在のレスポンスを送信した後、このTCPコネクションを閉じることをサーバーに指示します。これにより、不明な状態のコネクションが次のリクエストで再利用されることが防止されます。

この変更により、サーバーは `Expect: 100-continue` リクエストのボディが完全に消費されなかった場合に、安全のためにコネクションを閉じ、次のリクエストがクリーンな状態の新しいコネクションで処理されることを保証します。

## コアとなるコードの解説

### `src/net/http/server.go` の変更点

1.  **`expectContinueReader` 構造体への `sawEOF` フィールドの追加**:
    ```go
    type expectContinueReader struct {
        resp       *response
        readCloser io.ReadCloser
        closed     bool
        sawEOF     bool // 追加されたフィールド
    }
    ```
    この `sawEOF` フィールドは、`expectContinueReader` がラップしているリクエストボディの `io.ReadCloser` から `io.EOF` が返されたかどうかを記録します。

2.  **`expectContinueReader.Read` メソッドの変更**:
    ```go
    func (ecr *expectContinueReader) Read(p []byte) (n int, err error) {
        // ... (既存の100 Continueレスポンス送信ロジック) ...
        n, err = ecr.readCloser.Read(p)
        if err == io.EOF {
            ecr.sawEOF = true // EOFが検出されたらフラグを立てる
        }
        return
    }
    ```
    `Read` メソッドが基になるリーダーからデータを読み込む際に、`io.EOF` エラーが発生した場合に `ecr.sawEOF` を `true` に設定します。これにより、リクエストボディが完全に読み込まれたかどうかの状態が `expectContinueReader` オブジェクト内に保持されます。

3.  **コネクションクローズロジックの追加**:
    ```go
    // If the client wanted a 100-continue but we never sent it to
    // them (or, more strictly: we never finished reading their
    // request body), don't reuse this connection because it's now
    // in an unknown state: we might be sending this response at
    // the same time the client is now sending its request body
    // after a timeout.  (Some HTTP clients send Expect:
    // 100-continue but knowing that some servers don't support
    // it, the clients set a timer and send the body later anyway)
    // If we haven't seen EOF, we can't skip over the unread body
    // because we don't know if the next bytes on the wire will be
    // the body-following-the-timer or the subsequent request.
    // See Issue 11549.
    if ecr, ok := w.req.Body.(*expectContinueReader); ok && !ecr.sawEOF {
        w.closeAfterReply = true
    }
    ```
    このコードブロックは、レスポンスを書き込む直前に実行されます。
    -   `if ecr, ok := w.req.Body.(*expectContinueReader); ok`: 現在のリクエストボディが `expectContinueReader` 型であるか（つまり、`Expect: 100-continue` ヘッダを持つリクエストであったか）を確認します。
    -   `&& !ecr.sawEOF`: かつ、その `expectContinueReader` が `io.EOF` を検出していなかった場合（つまり、リクエストボディが完全に読み込まれていなかった場合）に条件が真となります。
    -   `w.closeAfterReply = true`: 上記の条件が真の場合、`w.closeAfterReply` フラグを `true` に設定します。このフラグが `true` に設定されると、現在のレスポンスがクライアントに送信された後、サーバーはこのTCPコネクションを閉じます。これにより、未読のデータが残っている可能性のあるコネクションが再利用されることを防ぎ、プロトコルの整合性を保ちます。

### `src/net/http/serve_test.go` の変更点

`TestIssue11549_Expect100` という新しいテストケースが追加されました。
このテストは、以下のシナリオをシミュレートします。
1.  `Expect: 100-continue` ヘッダを持つ `PUT /readbody` リクエストを送信。このリクエストのボディはハンドラによって完全に読み込まれます (`ioutil.ReadAll(r.Body)`)。
2.  `Expect: 100-continue` ヘッダを持つ `PUT /noreadbody` リクエストを送信。このリクエストのボディはハンドラによって**読み込まれません**。
3.  その後、`GET /should-be-ignored` リクエストが続くようにバイト列を準備します。これは、前のリクエストのボディが完全に読み込まれなかった場合に、この `GET` リクエストが誤って前のリクエストのボディの一部として解釈される可能性をテストするためです。

テストの期待値は以下の通りです。
-   `numReq != 2`: 処理されたリクエストの数が2であることを確認します。これは、`PUT /readbody` と `PUT /noreadbody` の2つのリクエストが正しく処理され、`GET /should-be-ignored` が無視されることを意味します。
-   `!strings.Contains(buf.String(), "Connection: close\\r\\n")`: レスポンスに `Connection: close` ヘッダが含まれていることを確認します。これは、`PUT /noreadbody` の後にコネクションが閉じられたことを示します。

このテストは、`Expect: 100-continue` リクエストでボディが完全に読み込まれなかった場合に、コネクションが正しく閉じられ、後続のデータが誤って解釈されないことを検証しています。

## 変更の背景

この変更は、以前のコミット `85e7bee` によって導入されたバグを修正するために行われました。`85e7bee` は、マップのキーと値がポインタを含まない型である場合に、そのマップバケットをガベージコレクタがスキャンする必要がない「noscan」としてマークする最適化を導入しました。これはGCの効率を向上させるための重要な最適化です。

しかし、この最適化には見落としがありました。Goのマップは、キーや値のサイズが大きい場合、それらをバケット内に直接格納するのではなく、ヒープ上の別の場所に「アウトライン」として格納し、バケット内にはそのデータへのポインタを持つことがあります。つまり、キーや値の型自体がポインタを含まなくても、そのサイズが大きいために内部的にポインタが生成されるケースが存在します。

`85e7bee` の実装では、この「アウトライン」ストレージの可能性が考慮されていなかったため、実際にはポインタを含んでいるにもかかわらず、マップバケットが誤って「noscan」とマークされていました。これにより、ガベージコレクタがこれらのポインタを認識できず、参照されているオブジェクトが誤って回収されてしまう可能性があり、プログラムのクラッシュやデータ破損につながる深刻なバグでした。

このコミットは、この問題を解決するために、マップバケットを「noscan」とマークする際に、キーと値の型がポインタを含まないことに加えて、そのサイズがインラインで格納できる最大サイズ (`MAXKEYSIZE`/`MAXVALSIZE`) を超えていないかどうかもチェックするように変更しました。

## 前提知識の解説

### Goのガベージコレクション (GC) の基本

Go言語は、自動メモリ管理のためにトレース型ガベージコレクタを採用しています。GCの主な目的は、プログラムがもはや到達できない（参照されていない）メモリを自動的に解放し、メモリリークを防ぐことです。GoのGCは、並行マーク＆スイープ方式をベースにしており、プログラムの実行と並行して動作することで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えるように設計されています。

GCがメモリを解放するためには、まず「到達可能な」オブジェクトを特定する必要があります。これは、プログラムのルート（グローバル変数、スタック上の変数、レジスタなど）から開始して、そこから参照されているすべてのオブジェクトをたどっていく（マークする）ことで行われます。マークされなかったオブジェクトは到達不可能と判断され、スイープフェーズで解放されます。

### Goのマップ (map) の内部構造

Goのマップ (`map`) はハッシュテーブルとして実装されています。内部的には、`hmap` 構造体がマップのメタデータを管理し、`bmap` (bucket map) と呼ばれるバケットの配列が実際のキーと値のペアを格納します。

*   **バケット (`bmap`)**: 各バケットは、複数のキーと値のペアを格納できる固定サイズの構造体です。衝突が発生した場合（異なるキーが同じバケットにハッシュされる場合）、バケットは連結リストのようにオーバーフローバケットを指すポインタ (`overflow`) を持ち、追加のペアを格納します。
*   **オーバーフローバケット**: バケットが満杯になった場合に、追加のキーと値のペアを格納するために動的に割り当てられるバケットです。これらのオーバーフローバケットは、元のバケットからポインタで参照されます。

### "noscan" の概念とGCにおけるその重要性

GoのGCは、メモリ領域をスキャンしてポインタを探し、到達可能なオブジェクトをマークします。しかし、すべてのメモリ領域がポインタを含むわけではありません。例えば、`int` や `float64` のようなプリミティブ型のみを格納する構造体や配列は、ポインタを含みません。

「noscan」とは、特定のメモリ領域（この場合はマップバケット）がポインタを一切含まないことをGCに伝えるためのマークです。GCは「noscan」とマークされた領域をスキャンする必要がないため、GCの作業量を大幅に削減し、パフォーマンスを向上させることができます。これは、特に大量のデータが格納されるマップにおいて重要な最適化となります。

### Goにおける値の「インライン」と「アウトライン」ストレージ

Goのコンパイラとランタイムは、データがメモリにどのように配置されるかを決定します。
*   **インライン (Inline) ストレージ**: データが、それを格納する構造体や配列のメモリ領域内に直接配置されることを指します。例えば、小さな構造体やプリミティブ型の配列は、通常、インラインで格納されます。
*   **アウトライン (Outline) ストレージ**: データが、それを格納する構造体や配列のメモリ領域とは別のヒープ上の場所に割り当てられ、元の場所からはそのデータへのポインタを介して参照されることを指します。これは、主にデータが大きすぎる場合や、可変長である場合（例: スライス、文字列、インターフェース値の動的な部分）に発生します。

マップのキーや値の場合、そのサイズが一定の閾値（`MAXKEYSIZE` や `MAXVALSIZE`）を超えると、バケット内に直接格納するのではなく、ヒープにアウトラインで割り当てられ、バケット内にはそのアウトラインデータへのポインタが格納されます。このポインタはGCのスキャン対象となるべきものです。

## 技術的詳細

このコミットの技術的詳細は、マップバケットの「noscan」属性を決定するロジックに、キーと値のサイズチェックを追加した点にあります。

以前の実装では、マップのキー型 (`ktyp`) と値型 (`etyp`) がそれぞれポインタを含まない (`kindNoPointers` フラグがセットされている) 場合に、マップバケット全体がポインタを含まない (`kindNoPointers`) と判断していました。

しかし、前述の通り、キーや値のサイズが大きい場合、それらはバケットのメモリ領域外に「アウトライン」として格納され、バケット内にはそのアウトラインデータへのポインタが保持されます。このポインタはGCによってスキャンされる必要があります。

このコミットでは、この問題を解決するために、以下の2つの場所でサイズチェックを追加しています。

1.  **`src/cmd/gc/reflect.c` (コンパイラ)**:
    コンパイラがマップのバケット型を生成する際に、`mapbucket` 関数内でバケットがポインタを持つかどうかを判断します。
    変更前: `!haspointers(t->type) && !haspointers(t->down)`
    変更後: `!haspointers(t->type) && !haspointers(t->down) && t->type->width <= MAXKEYSIZE && t->down->width <= MAXVALSIZE`
    ここで `t->type` はキーの型、`t->down` は値の型を指します。`width` は型のサイズ（バイト単位）です。`MAXKEYSIZE` と `MAXVALSIZE` は、それぞれキーと値がインラインで格納される最大サイズを定義する定数です。この変更により、キーと値がポインタを含まない型であることに加えて、そのサイズがインラインで格納できる範囲内である場合にのみ、バケットが「noscan」とマークされるようになりました。

2.  **`src/reflect/type.go` (リフレクション)**:
    リフレクションパッケージでも、マップのバケット型を生成する際に同様のロジックが使用されます。
    変更前: `if ktyp.kind&kindNoPointers != 0 && etyp.kind&kindNoPointers != 0`
    変更後: `if ktyp.kind&kindNoPointers != 0 && etyp.kind&kindNoPointers != 0 && ktyp.size <= maxKeySize && etyp.size <= maxValSize`
    `ktyp.size` と `etyp.size` はそれぞれキーと値のサイズです。`maxKeySize` と `maxValSize` は、`MAXKEYSIZE` と `MAXVALSIZE` に対応する定数です。ここでも、キーと値のサイズがインラインで格納できる閾値を超えていないかを確認することで、誤った「noscan」マークを防ぎます。

これらの変更により、マップのキーや値がポインタを含まない型であっても、そのサイズが大きいためにアウトラインストレージが使用され、結果としてバケットがポインタを持つ場合には、GCが正しくそのバケットをスキャンするようになります。

また、`src/runtime/hashmap.go` のコメントも更新され、`hmap` 構造体の `noscan` に関する説明に「and are inline」という文言が追加され、この変更の意図が明確化されています。

さらに、`src/runtime/map_test.go` には、大きなキーや値を持つマップが正しく動作し、GC後もデータが破損しないことを確認するための新しいテストケース (`TestMapLargeKeyNoPointer` と `TestMapLargeValNoPointer`) が追加されました。これらのテストは、このバグが修正されたことを検証する上で非常に重要です。

## 変更の背景

この変更は、以前のコミット `85e7bee` によって導入されたバグを修正するために行われました。`85e7bee` は、マップのキーと値がポインタを含まない型である場合に、そのマップバケットをガベージコレクタがスキャンする必要がない「noscan」としてマークする最適化を導入しました。これはGCの効率を向上させるための重要な最適化です。

しかし、この最適化には見落としがありました。Goのマップは、キーや値のサイズが大きい場合、それらをバケット内に直接格納するのではなく、ヒープ上の別の場所に「アウトライン」として格納し、バケット内にはそのデータへのポインタを持つことがあります。つまり、キーや値の型自体がポインタを含まなくても、そのサイズが大きいために内部的にポインタが生成されるケースが存在します。

`85e7bee` の実装では、この「アウトライン」ストレージの可能性が考慮されていなかったため、実際にはポインタを含んでいるにもかかわらず、マップバケットが誤って「noscan」とマークされていました。これにより、ガベージコレクタがこれらのポインタを認識できず、参照されているオブジェクトが誤って回収されてしまう可能性があり、プログラムのクラッシュやデータ破損につながる深刻なバグでした。

このコミットは、この問題を解決するために、マップバケットを「noscan」とマークする際に、キーと値の型がポインタを含まないことに加えて、そのサイズがインラインで格納できる最大サイズ (`MAXKEYSIZE`/`MAXVALSIZE`) を超えていないかどうかもチェックするように変更しました。

## 前提知識の解説

### Goのガベージコレクション (GC) の基本

Go言語は、自動メモリ管理のためにトレース型ガベージコレクタを採用しています。GCの主な目的は、プログラムがもはや到達できない（参照されていない）メモリを自動的に解放し、メモリリークを防ぐことです。GoのGCは、並行マーク＆スイープ方式をベースにしており、プログラムの実行と並行して動作することで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えるように設計されています。

GCがメモリを解放するためには、まず「到達可能な」オブジェクトを特定する必要があります。これは、プログラムのルート（グローバル変数、スタック上の変数、レジスタなど）から開始して、そこから参照されているすべてのオブジェクトをたどっていく（マークする）ことで行われます。マークされなかったオブジェクトは到達不可能と判断され、スイープフェーズで解放されます。

### Goのマップ (map) の内部構造

Goのマップ (`map`) はハッシュテーブルとして実装されています。内部的には、`hmap` 構造体がマップのメタデータを管理し、`bmap` (bucket map) と呼ばれるバケットの配列が実際のキーと値のペアを格納します。

*   **バケット (`bmap`)**: 各バケットは、複数のキーと値のペアを格納できる固定サイズの構造体です。衝突が発生した場合（異なるキーが同じバケットにハッシュされる場合）、バケットは連結リストのようにオーバーフローバケットを指すポインタ (`overflow`) を持ち、追加のペアを格納します。
*   **オーバーフローバケット**: バケットが満杯になった場合に、追加のキーと値のペアを格納するために動的に割り当てられるバケットです。これらのオーバーフローバケットは、元のバケットからポインタで参照されます。

### "noscan" の概念とGCにおけるその重要性

GoのGCは、メモリ領域をスキャンしてポインタを探し、到達可能なオブジェクトをマークします。しかし、すべてのメモリ領域がポインタを含むわけではありません。例えば、`int` や `float64` のようなプリミティブ型のみを格納する構造体や配列は、ポインタを含みません。

「noscan」とは、特定のメモリ領域（この場合はマップバケット）がポインタを一切含まないことをGCに伝えるためのマークです。GCは「noscan」とマークされた領域をスキャンする必要がないため、GCの作業量を大幅に削減し、パフォーマンスを向上させることができます。これは、特に大量のデータが格納されるマップにおいて重要な最適化となります。

### Goにおける値の「インライン」と「アウトライン」ストレージ

Goのコンパイラとランタイムは、データがメモリにどのように配置されるかを決定します。
*   **インライン (Inline) ストレージ**: データが、それを格納する構造体や配列のメモリ領域内に直接配置されることを指します。例えば、小さな構造体やプリミティブ型の配列は、通常、インラインで格納されます。
*   **アウトライン (Outline) ストレージ**: データが、それを格納する構造体や配列のメモリ領域とは別のヒープ上の場所に割り当てられ、元の場所からはそのデータへのポインタを介して参照されることを指します。これは、主にデータが大きすぎる場合や、可変長である場合（例: スライス、文字列、インターフェース値の動的な部分）に発生します。

マップのキーや値の場合、そのサイズが一定の閾値（`MAXKEYSIZE` や `MAXVALSIZE`）を超えると、バケット内に直接格納するのではなく、ヒープにアウトラインで割り当てられ、バケット内にはそのアウトラインデータへのポインタが格納されます。このポインタはGCのスキャン対象となるべきものです。

## 技術的詳細

このコミットの技術的詳細は、マップバケットの「noscan」属性を決定するロジックに、キーと値のサイズチェックを追加した点にあります。

以前の実装では、マップのキー型 (`ktyp`) と値型 (`etyp`) がそれぞれポインタを含まない (`kindNoPointers` フラグがセットされている) 場合に、マップバケット全体がポインタを含まない (`kindNoPointers`) と判断していました。

しかし、前述の通り、キーや値のサイズが大きい場合、それらはバケットのメモリ領域外に「アウトライン」として格納され、バケット内にはそのアウトラインデータへのポインタが保持されます。このポインタはGCによってスキャンされる必要があります。

このコミットでは、この問題を解決するために、以下の2つの場所でサイズチェックを追加しています。

1.  **`src/cmd/gc/reflect.c` (コンパイラ)**:
    コンパイラがマップのバケット型を生成する際に、`mapbucket` 関数内でバケットがポインタを持つかどうかを判断します。
    変更前: `!haspointers(t->type) && !haspointers(t->down)`
    変更後: `!haspointers(t->type) && !haspointers(t->down) && t->type->width <= MAXKEYSIZE && t->down->width <= MAXVALSIZE`
    ここで `t->type` はキーの型、`t->down` は値の型を指します。`width` は型のサイズ（バイト単位）です。`MAXKEYSIZE` と `MAXVALSIZE` は、それぞれキーと値がインラインで格納される最大サイズを定義する定数です。この変更により、キーと値がポインタを含まない型であることに加えて、そのサイズがインラインで格納できる範囲内である場合にのみ、バケットが「noscan」とマークされるようになりました。

2.  **`src/reflect/type.go` (リフレクション)**:
    リフレクションパッケージでも、マップのバケット型を生成する際に同様のロジックが使用されます。
    変更前: `if ktyp.kind&kindNoPointers != 0 && etyp.kind&kindNoPointers != 0`
    変更後: `if ktyp.kind&kindNoPointers != 0 && etyp.kind&kindNoPointers != 0 && ktyp.size <= maxKeySize && etyp.size <= maxValSize`
    `ktyp.size` と `etyp.size` はそれぞれキーと値のサイズです。`maxKeySize` と `maxValSize` は、`MAXKEYSIZE` と `MAXVALSIZE` に対応する定数です。ここでも、キーと値のサイズがインラインで格納できる閾値を超えていないかを確認することで、誤った「noscan」マークを防ぎます。

これらの変更により、マップのキーや値がポインタを含まない型であっても、そのサイズが大きいためにアウトラインストレージが使用され、結果としてバケットがポインタを持つ場合には、GCが正しくそのバケットをスキャンするようになります。

また、`src/runtime/hashmap.go` のコメントも更新され、`hmap` 構造体の `noscan` に関する説明に「and are inline」という文言が追加され、この変更の意図が明確化されています。

さらに、`src/runtime/map_test.go` には、大きなキーや値を持つマップが正しく動作し、GC後もデータが破損しないことを確認するための新しいテストケース (`TestMapLargeKeyNoPointer` と `TestMapLargeValNoPointer`) が追加されました。これらのテストは、このバグが修正されたことを検証する上で非常に重要です。

## コアとなるコードの解説

### `src/cmd/gc/reflect.c` の変更

このファイルはGoコンパイラの一部であり、Goの型情報（特にリフレクションで使用される情報）を生成する役割を担っています。`mapbucket` 関数は、マップのバケット型に関する情報を設定する際に呼び出されます。

変更前は、マップのキー型 (`t->type`) と値型 (`t->down`) がポインタを含まない (`!haspointers(...)`) 場合に、バケット全体がポインタを含まない (`bucket->haspointers = 1`) とマークされていました。

変更後は、この条件に加えて、キーのサイズ (`t->type->width`) が `MAXKEYSIZE` 以下であり、値のサイズ (`t->down->width`) が `MAXVALSIZE` 以下であるという条件が追加されました。
`MAXKEYSIZE` と `MAXVALSIZE` は、マップのキーと値がバケット内にインラインで格納される最大サイズを定義する定数です。これらのサイズを超えると、キーや値はヒープにアウトラインで割り当てられ、バケット内にはそのデータへのポインタが格納されるため、バケットはポインタを持つと見なされるべきです。

この修正により、コンパイラが生成する型情報において、マップバケットのポインタの有無がより正確に反映されるようになり、GCが誤って「noscan」と判断することを防ぎます。

### `src/reflect/type.go` の変更

このファイルはGoのリフレクションパッケージの一部であり、Goの型システムをランタイムで表現します。`bucketOf` 関数は、リフレクションを通じてマップのバケット型を取得する際に使用されます。

ここでも、`src/cmd/gc/reflect.c` と同様のロジックが適用されています。変更前は、キー型 (`ktyp`) と値型 (`etyp`) がポインタを含まない (`kindNoPointers != 0`) 場合に、バケットがポインタを含まない (`kind = kindNoPointers`) とマークされていました。

変更後は、キーのサイズ (`ktyp.size`) が `maxKeySize` 以下であり、値のサイズ (`etyp.size`) が `maxValSize` 以下であるという条件が追加されました。
`maxKeySize` と `maxValSize` は、`src/cmd/gc/reflect.c` の `MAXKEYSIZE` と `MAXVALSIZE` に対応する定数です。

この変更により、リフレクションシステムがマップバケットのポインタの有無を正確に判断できるようになり、GCの動作に一貫性をもたらします。

### `src/runtime/hashmap.go` の変更

このファイルはGoランタイムのハッシュマップ実装のコア部分です。このファイルへの変更はコードロジックの変更ではなく、コメントの修正です。

`hmap` 構造体のコメントにおいて、マップバケットが「noscan」とマークされる条件の説明に「and are inline」という文言が追加されました。これは、キーと値がポインタを含まないだけでなく、バケット内にインラインで格納されている場合にのみ「noscan」となるという、このコミットの修正内容を反映し、ドキュメントの正確性を向上させています。

### `src/runtime/map_test.go` の変更

このファイルには、Goのマップの動作を検証するためのテストが含まれています。このコミットでは、以下の2つの新しいテスト関数が追加されました。

*   **`TestMapLargeKeyNoPointer`**:
    このテストは、キーがポインタを含まないが、そのサイズが大きいためにアウトラインで格納されるようなマップのケースを検証します。具体的には、`[64]int` のような大きな配列をキーとして使用し、マップへの挿入、GCの実行、そしてその後の値の取得が正しく行われることを確認します。もしバグが修正されていなければ、GCによってキーが誤って回収され、マップが破損する可能性があります。

*   **`TestMapLargeValNoPointer`**:
    このテストは、値がポインタを含まないが、そのサイズが大きいためにアウトラインで格納されるようなマップのケースを検証します。同様に、`[64]int` のような大きな配列を値として使用し、マップへの挿入、GCの実行、そしてその後の値の取得が正しく行われることを確認します。

これらのテストは、このコミットによって修正されたバグが実際に解決されたことを保証し、将来的な回帰を防ぐための重要な安全網となります。

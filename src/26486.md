## 変更の背景

この変更の背景には、Go 1.5 における `c-archive` および `c-shared` ビルドモードで生成されたライブラリが、ホストアプリケーション（C/C++など）のシグナルハンドリングと競合する可能性があったという問題があります。

Go 1.5 では、Go のアーカイブまたは共有ライブラリが、ほとんどのシグナルに対して独自のシグナルハンドラをインストールしていました。これは、Go ランタイムが自身の内部的な処理（例えば、goroutine のスケジューリング、ガベージコレクション、パニック処理など）のためにシグナルを利用するためです。しかし、Go のライブラリが C/C++ アプリケーションに組み込まれる場合、ホストアプリケーションも独自のシグナルハンドラを設定していることがよくあります。

両者が独立してシグナルハンドラを設定しようとすると、どちらかのハンドラが上書きされたり、意図しない挙動を引き起こしたりする可能性がありました。特に、Go ランタイムが捕捉するシグナルが、ホストアプリケーションにとって重要なシグナル（例えば、`SIGINT` や `SIGTERM` など、プログラムの正常終了を促すシグナル）であった場合、ホストアプリケーションの期待する動作が妨げられることになります。

Go 1.6 では、この競合を緩和し、Go ライブラリがホストアプリケーションのシグナルハンドリングに与える影響を最小限に抑えるために、シグナルハンドリングの戦略が見直されました。Go ランタイムが本当に必要とするシグナルのみを捕捉するように変更することで、より協調的な動作を目指しました。

## 前提知識の解説

### Goのビルドモード (`-buildmode=c-archive`, `-buildmode=c-shared`)

Go は、Go プログラムを通常の実行可能ファイルとしてビルドするだけでなく、他の言語（主に C/C++）から利用できるライブラリとしてビルドする機能を提供しています。

*   **`-buildmode=c-archive`**: このモードでビルドすると、Go のコードが静的ライブラリ（通常は `.a` ファイル）としてコンパイルされます。このアーカイブは、C/C++ プロジェクトにリンクされ、Go の関数を C の関数として呼び出すことができます。Go のランタイムと依存関係はすべてこのアーカイブにバンドルされます。
*   **`-buildmode=c-shared`**: このモードでビルドすると、Go のコードが共有ライブラリ（通常は `.so` ファイルや `.dylib` ファイル）としてコンパイルされます。この共有ライブラリは、C/C++ プロジェクトから動的にロードされ、Go の関数を C の関数として呼び出すことができます。静的ライブラリと同様に、Go のランタイムと依存関係が含まれます。

これらのビルドモードは、既存の C/C++ コードベースに Go の高性能な機能や並行処理を組み込む際に非常に有用です。

### シグナルハンドリング

オペレーティングシステムにおける**シグナル**とは、プロセスに対して非同期的に発生するイベントを通知するソフトウェア割り込みの一種です。シグナルは、エラー状態（例: 無効なメモリアクセス）、外部イベント（例: ユーザーが Ctrl+C を押す）、または他のプロセスからの通信など、様々な理由で生成されます。

一般的なシグナルの例:
*   `SIGINT` (Interrupt): ユーザーがプログラムを中断しようとしたとき（例: Ctrl+C）。
*   `SIGTERM` (Terminate): プログラムを正常に終了させるよう要求するとき。
*   `SIGKILL` (Kill): プログラムを強制終了するとき（捕捉・無視不可）。
*   `SIGSEGV` (Segmentation Violation): 無効なメモリアクセスが発生したとき。
*   `SIGBUS` (Bus Error): ハードウェアエラー（例: アラインメント違反）が発生したとき。
*   `SIGFPE` (Floating-Point Exception): 浮動小数点演算エラー（例: ゼロ除算）が発生したとき。

プロセスは、特定のシグナルを受信したときに実行される**シグナルハンドラ**を登録できます。シグナルハンドラは、シグナルを捕捉し、デフォルトの動作（例: プログラムの終了）をオーバーライドして、カスタムの処理（例: リソースのクリーンアップ、エラーログの記録）を実行するために使用されます。

### Goランタイムとシグナル

Go ランタイムは、その内部動作のためにシグナルを多用します。例えば、Go のスケジューラは `SIGURG` や `SIGPROF` などのシグナルを利用して goroutine のプリエンプション（横取り）を実現したり、プロファイリング情報を収集したりします。また、Go のパニックメカニズムは、`SIGSEGV` や `SIGBUS` といった同期シグナルを捕捉して、Go のスタックトレースを出力し、プログラムをより優雅に終了させるために利用します。

### C/Go相互運用におけるシグナルハンドリングの課題

Go のライブラリが C/C++ アプリケーションに組み込まれる場合、シグナルハンドリングは複雑な問題を引き起こす可能性があります。
*   **競合**: ホストの C/C++ アプリケーションと Go ランタイムの両方が同じシグナルに対してハンドラを設定しようとすると、どちらかのハンドラが意図せず上書きされ、予期しない動作やクラッシュにつながる可能性があります。
*   **期待される動作の不一致**: ホストアプリケーションは特定のシグナルに対して特定の動作を期待しているかもしれませんが、Go ランタイムがそのシグナルを捕捉して独自の処理を行うことで、ホストアプリケーションの期待が裏切られることがあります。例えば、ホストアプリケーションが `SIGINT` を捕捉してクリーンアップ処理を行いたいのに、Go ライブラリがそれを捕捉して別の動作をしてしまう、といったケースです。
*   **デバッグの困難さ**: シグナルハンドリングの競合は、デバッグを非常に困難にします。どちらのコードベースがシグナルを処理しているのか、なぜ期待通りの動作をしないのかを特定するのが難しくなります。

## 技術的詳細

### Go 1.5での挙動

Go 1.5 では、`c-archive` または `c-shared` モードでビルドされた Go ライブラリは、Go ランタイムの要件に基づいて「ほとんどのシグナル」に対してシグナルハンドラをインストールしていました。これは、Go ランタイムが自身の内部的な整合性を保ち、パニックなどのエラーを適切に処理するために必要な措置でした。しかし、前述の通り、これはホストの C/C++ アプリケーションとの間でシグナルハンドリングの競合を引き起こす可能性がありました。

### Go 1.6での変更点

Go 1.6 では、この挙動が大幅に変更されました。Go のアーカイブまたは共有ライブラリは、ホストアプリケーションとの競合を避けるため、シグナルハンドラのインストールを最小限に抑えるようになりました。具体的には、Go 1.6 では、Go コード内のランタイムパニックを処理するために必要な**同期シグナル**のみにシグナルハンドラをインストールします。

これらの同期シグナルは以下の通りです。
*   `SIGBUS` (Bus Error)
*   `SIGFPE` (Floating-Point Exception)
*   `SIGSEGV` (Segmentation Violation)

### なぜこれらのシグナルに限定されたのか

この変更の鍵は「同期シグナル」という点にあります。
*   **同期シグナル**: プログラムの実行中に、CPU が直接検出するエラー（例: 無効なメモリアクセス、ゼロ除算）によって生成されるシグナルです。これらは、特定の命令の実行結果として同期的に発生します。`SIGBUS`, `SIGFPE`, `SIGSEGV` は典型的な同期シグナルです。Go ランタイムは、これらのシグナルを捕捉することで、Go コード内で発生したこれらのエラーを Go のパニックメカニズムに変換し、Go のスタックトレースを出力して、より制御された形でプログラムを終了させることができます。これは Go の堅牢性にとって不可欠です。
*   **非同期シグナル**: プログラムの実行とは独立して、外部イベント（例: ユーザー入力、タイマー、他のプロセスからの通知）によって生成されるシグナルです。`SIGINT`, `SIGTERM`, `SIGHUP` などがこれに該当します。Go 1.6 では、これらの非同期シグナルに対するハンドラのインストールを停止しました。これにより、ホストの C/C++ アプリケーションがこれらのシグナルを自由に処理できるようになり、Go ライブラリとの競合が大幅に減少します。

この戦略により、Go ランタイムは自身のパニック処理に必要な最小限のシグナルハンドリングを維持しつつ、ホストアプリケーションが他のシグナルを適切に管理できる柔軟性を提供します。

### `os/signal` パッケージへの言及

ドキュメントの変更では、`os/signal` パッケージへの参照も含まれています。これは、Go 開発者が Go プログラム内でシグナルを明示的に処理する必要がある場合に、このパッケージを使用できることを示唆しています。`os/signal` パッケージは、Go プログラムが特定のシグナルを捕捉したり、シグナルを無視したり、シグナルハンドラを設定したりするための機能を提供します。Go ライブラリがホストアプリケーションに組み込まれる場合でも、Go 側で特定のシグナルを処理したい場合は、このパッケージを利用することになります。

## コアとなるコードの解説

追加された HTML コードは、Go 1.6 のリリースノートの一部として、`c-archive` および `c-shared` ビルドモードを使用する開発者に対して、シグナルハンドリングの変更点を明確に伝えています。

*   最初の文では、`c-archive` または `c-shared` を使用してアーカイブまたは共有ライブラリをビルドする際のシグナルハンドリングが変更されたことを明記しています。
*   次に、Go 1.5 では Go ライブラリが「ほとんどのシグナル」に対してハンドラをインストールしていたことを説明し、以前の挙動を明確にしています。
*   そして、Go 1.6 では「Go コード内のランタイムパニックを処理するために必要な同期シグナル（SIGBUS, SIGFPE, SIGSEGV）のみ」にハンドラをインストールするようになったという、新しい挙動を詳細に説明しています。
*   最後に、`os/signal` パッケージへのリンクを提供し、より詳細な情報が必要な場合に参照できるようにしています。

このドキュメントの追加により、Go 1.5 から Go 1.6 へ移行する開発者が、Go ライブラリを C/C++ アプリケーションに組み込む際に発生する可能性のあるシグナルハンドリングの挙動変更について、事前に認識し、必要に応じてコードを調整できるようになります。

## 変更の背景

ソフトウェアプロジェクトにおいて、ユーザーからのバグ報告や機能要望は開発プロセスにおいて非常に重要です。しかし、報告内容が不明確であったり、再現手順が不足していたりすると、開発者は問題の特定や解決に多くの時間を費やすことになります。GitHubのIssueテンプレートは、ユーザーがIssueを報告する際に必要な情報を構造化して提供することを促すための強力なツールです。

このコミットの背景には、Goプロジェクトにおいて、より質の高いIssue報告を奨励し、開発効率を向上させたいという意図があります。特に、バグ報告においては、問題を再現できる最小限のコード例（再現レシピ）が不可欠です。以前のテンプレートでは、`play.golang.org`の使用を推奨していましたが、より一般的な「再現レシピ」の提供の重要性を強調し、さらに「完全な実行可能プログラム」も良い選択肢であることを明示することで、ユーザーがより多様な形式で再現例を提供できるように促しています。これにより、開発者はIssueの根本原因を迅速に特定し、修正に取り掛かることができるようになります。

## 前提知識の解説

### GitHub Issueテンプレート

GitHub Issueテンプレートは、GitHubリポジトリの`.github`ディレクトリ内に配置される特別なMarkdownファイルです。これらのテンプレートを使用することで、プロジェクトのメンテナーは、ユーザーが新しいIssueを作成する際に表示されるデフォルトのコンテンツを定義できます。これにより、ユーザーはIssueの種類（バグ報告、機能要望、質問など）に応じて、必要な情報を漏れなく、かつ一貫した形式で提供するよう促されます。

Issueテンプレートの主な利点は以下の通りです。

*   **情報の標準化**: 報告されるIssueの形式と内容を統一し、必要な情報が常に含まれるようにします。
*   **効率の向上**: 開発者がIssueの内容を理解し、再現するまでの時間を短縮します。
*   **ユーザー体験の改善**: ユーザーがIssueを報告する際に、どのような情報が必要かを明確に示し、報告プロセスをガイドします。
*   **コミュニケーションの促進**: 開発者とユーザー間のコミュニケーションを円滑にし、誤解を減らします。

Goプロジェクトでは、このテンプレートを利用して、ユーザーに特定の質問に答えさせたり、再現手順や期待される動作、実際の動作などを記述させたりすることで、Issueの品質を維持しています。

### `play.golang.org`

`play.golang.org`は、Go言語の公式ウェブサイトが提供するオンラインのGoコード実行環境です。このプラットフォームは、Goコードをブラウザ上で記述、実行、共有できるため、Go言語の学習、簡単なコードスニペットのテスト、そしてバグ報告における再現コードの共有に広く利用されています。

`play.golang.org`の主な特徴は以下の通りです。

*   **手軽な実行**: Goコンパイラや実行環境をローカルにセットアップすることなく、Goコードを即座に実行できます。
*   **共有機能**: 作成したコードスニペットは一意のURLで共有できるため、他のユーザーと簡単にコードを共有し、共同でデバッグやレビューを行うことができます。これは、Issue報告において再現コードを提示する際に非常に便利です。
*   **バージョン管理**: 特定のGoバージョンでコードを実行できるため、バージョン間の挙動の違いを確認する際にも役立ちます。

このコミットでは、`play.golang.org`が再現例を提供する「最良の」方法であると引き続き推奨しつつ、他の形式での再現例の提供も許容するよう指示を調整しています。

## 技術的詳細

このコミットは、GoプロジェクトのGitHubリポジトリにおけるIssueテンプレートファイルである`.github/ISSUE_TEMPLATE`の内容を修正しています。変更の目的は、ユーザーがIssueを報告する際に、問題の再現方法に関するより明確で柔軟な指示を提供することです。

具体的には、Issueテンプレートの「3. What did you do?」（何を行いましたか？）というセクションの指示が変更されました。

**変更前:**

```markdown
3. What did you do?
-(Use play.golang.org to provide a runnable example, if possible.)
```

この指示は、可能であれば`play.golang.org`を使用して実行可能な例を提供するよう求めていました。これは良い出発点ですが、すべてのシナリオで`play.golang.org`が最適であるとは限りません。例えば、ファイルシステムへのアクセスが必要な場合や、特定の外部ライブラリに依存する場合など、`play.golang.org`では再現が難しいケースも存在します。

**変更後:**

```markdown
3. What did you do?
+If possible, provide a recipe for reproducing the error.
+A complete runnable program is good.
+A link on play.golang.org is best.
```

この新しい指示は、以下の点で改善されています。

1.  **「再現レシピ」の強調**: 「If possible, provide a recipe for reproducing the error.」（可能であれば、エラーを再現するためのレシピを提供してください。）という文言が追加されました。これは、`play.golang.org`に限定せず、問題を再現するための具体的な手順やコードスニペット全般を指します。これにより、ユーザーはより広範な方法で再現情報を提供できるようになります。
2.  **「完全な実行可能プログラム」の許容**: 「A complete runnable program is good.」（完全な実行可能プログラムは良いです。）という文言が追加されました。これは、`play.golang.org`で提供できないような複雑なケースや、複数のファイルにまたがるようなケースでも、完全なGoプログラムとして提供することが許容され、推奨されることを示しています。これは、特に大規模なバグや特定の環境に依存するバグの報告において有用です。
3.  **`play.golang.org`の最良の選択肢としての位置づけ**: 「A link on play.golang.org is best.」（`play.golang.org`へのリンクが最良です。）という文言は維持され、`play.golang.org`が依然として再現例を提供する上で最も推奨される、手軽で効果的な方法であることを明確にしています。

これらの変更により、ユーザーはIssue報告時に、状況に応じて最も適切な形式で再現情報を提供できるようになり、結果としてIssueの品質と開発者のデバッグ効率が向上することが期待されます。

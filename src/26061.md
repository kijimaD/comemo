# [インデックス 26061] ファイルの概要

このコミットは、Goの`net/http`パッケージにおける`CloseNotifier`インターフェースの実装を再構築し、その動作に関するドキュメントを明確化することを目的としています。これにより、以前の曖昧な仕様が改善され、`CloseNotifier`とHTTP/1.1パイプライン処理、および`Hijacker`インターフェースとの間の既存のバグが修正されました。

Author: Brad Fitzpatrick <bradfitz@golang.org>
Date:   Tue Dec 1 19:07:41 2015 +0000

    net/http: rework CloseNotifier implementation, clarify expectations in docs
    
    CloseNotifier wasn't well specified previously. This CL simplifies its
    implementation, clarifies the public documentation on CloseNotifier,
    clarifies internal documentation on conn, and fixes two CloseNotifier
    bugs in the process.
    
    The main change, though, is tightening the rules and expectations for using
    CloseNotifier:
    
    * the caller must consume the Request.Body first (old rule, unwritten)
    * the received value is the "true" value (old rule, unwritten)
    * no promises for channel sends after Handler returns (old rule, unwritten)
    * a subsequent pipelined request fires the CloseNotifier (new behavior;
      previously it never fired and thus effectively deadlocked as in #13165)
    * advise that it should only be used without HTTP/1.1 pipelining (use HTTP/2
      or non-idempotent browsers). Not that browsers actually use pipelining.
    
    The main implementation change is that each Handler now gets its own
    CloseNotifier channel value, rather than sharing one between the whole
    conn. This means Handlers can't affect subsequent requests. This is
    how HTTP/2's Server works too. The old docs never clarified a behavior
    either way. The other side effect of each request getting its own
    CloseNotifier channel is that one handler can't "poison" the
    underlying conn preventing subsequent requests on the same connection
    from using CloseNotifier (this is #9763).
    
    In the old implementation, once any request on a connection used
    ClosedNotifier, the conn's underlying bufio.Reader source was switched
    from the TCPConn to the read side of the pipe being fed by a
    never-ending copy. Since it was impossible to abort that never-ending
    copy, we could never get back to a fresh state where it was possible
    to return the underlying TCPConn to callers of Hijack. Now, instead of
    a never-ending Copy, the background goroutine doing a Read from the
    TCPConn (or *tls.Conn) only reads a single byte. That single byte
    can be in the request body, a socket timeout error, io.EOF error, or
    the first byte of the second body. In any case, the new *connReader
    type stitches sync and async reads together like an io.MultiReader. To
    clarify the flow of Read data and combat the complexity of too many
    wrapper Reader types, the *connReader absorbs the io.LimitReader
    previously used for bounding request header reads.  The
    liveSwitchReader type is removed. (an unused switchWriter type is also
    removed)
    
    Many fields on *conn are also documented more fully.
    
    Fixes #9763 (CloseNotify + Hijack together)
    Fixes #13165 (deadlock with CloseNotify + pipelined requests)

## 元コミット内容

このコミットは、`net/http`パッケージの`CloseNotifier`インターフェースの実装を再構築し、そのドキュメントを明確化します。以前の`CloseNotifier`は仕様が不明確であり、この変更によって実装が簡素化され、公開ドキュメントおよび`conn`構造体に関する内部ドキュメントが明確化され、同時に2つの`CloseNotifier`関連のバグが修正されました。

主な変更点は、`CloseNotifier`を使用する際のルールと期待される動作を厳格化したことです。具体的には以下の点が挙げられます。

*   呼び出し元は`Request.Body`を最初に消費する必要がある（以前からの暗黙のルール）。
*   受信される値は「真」の値である（以前からの暗黙のルール）。
*   ハンドラが戻った後、チャネル送信の保証はない（以前からの暗黙のルール）。
*   後続のパイプラインリクエストが`CloseNotifier`を発火させる（新しい動作。以前は発火せず、#13165のようにデッドロックを引き起こす可能性があった）。
*   HTTP/1.1パイプライン処理なしでのみ使用することを推奨（HTTP/2または非冪等なブラウザを使用）。

実装面での主要な変更は、各ハンドラが接続全体で共有されるのではなく、独自の`CloseNotifier`チャネル値を持つようになったことです。これにより、あるハンドラが後続のリクエストに影響を与えることがなくなります。これはHTTP/2のサーバーの動作と同様です。また、この変更により、あるハンドラが`CloseNotifier`を使用したことで、同じ接続上の後続のリクエストが`CloseNotifier`を使用できなくなるという「汚染」問題（#9763）も解決されます。

以前の実装では、接続上のいずれかのリクエストが`CloseNotifier`を使用すると、`conn`の基盤となる`bufio.Reader`のソースがTCPConnから、無限コピーによって供給されるパイプの読み取り側に切り替わっていました。この無限コピーを中断する方法がなかったため、`Hijack`の呼び出し元に基盤となるTCPConnを返すことができませんでした。新しい実装では、無限コピーの代わりに、TCPConn（または`*tls.Conn`）からの読み取りを行うバックグラウンドゴルーチンが単一バイトのみを読み取ります。この単一バイトは、リクエストボディ、ソケットタイムアウトエラー、`io.EOF`エラー、または2番目のボディの最初のバイトである可能性があります。いずれの場合も、新しい`*connReader`型が同期読み取りと非同期読み取りを`io.MultiReader`のように結合します。読み取りデータの流れを明確にし、過剰なラッパー`Reader`型の複雑さを解消するため、`*connReader`は以前リクエストヘッダーの読み取り制限に使用されていた`io.LimitReader`の機能を吸収します。`liveSwitchReader`型は削除され、未使用の`switchWriter`型も削除されました。

また、`*conn`構造体の多くのフィールドがより詳細に文書化されています。

このコミットは、以下の問題を修正します。
*   #9763 (`CloseNotify`と`Hijack`の同時使用に関する問題)
*   #13165 (`CloseNotify`とパイプラインリクエストによるデッドロック)

## 変更の背景

このコミットが行われた背景には、Goの`net/http`パッケージにおける`CloseNotifier`インターフェースの既存の設計と実装に起因するいくつかの問題がありました。

1.  **不明確な仕様と期待される動作**: `CloseNotifier`は、クライアントが接続を切断した際にハンドラに通知するためのメカニズムですが、その正確な動作、特に`Request.Body`の消費タイミング、チャネルの送信保証、HTTP/1.1パイプライン処理との相互作用について、公式なドキュメントや内部的な取り決めが不足していました。これにより、開発者が`CloseNotifier`を誤用したり、予期せぬ動作に遭遇したりする可能性がありました。

2.  **HTTP/1.1パイプライン処理とのデッドロック (#13165)**: 以前の実装では、HTTP/1.1パイプライン処理が使用された場合、最初のハンドラが`CloseNotifier`を呼び出しても、後続のパイプラインリクエストが到着してもチャネルが発火しないという問題がありました。これは、`CloseNotifier`が接続全体で共有される単一のチャネルに依存していたため、後続のリクエストがそのチャネルの状態を適切に更新できなかったことに起因します。結果として、ハンドラが`CloseNotifier`チャネルからの通知を待ち続けることで、デッドロックが発生していました。

3.  **`CloseNotifier`と`Hijack`の非互換性 (#9763)**: `Hijacker`インターフェースは、HTTPハンドラが基盤となるTCP接続を直接制御できるようにする強力な機能です。しかし、以前の`CloseNotifier`の実装では、一度`CloseNotifier`が使用されると、接続の読み取りソースが`io.Pipe`に切り替わり、そのパイプからの無限コピーが開始されていました。この状態では、元のTCP接続を`Hijack`経由で返すことが不可能になり、`CloseNotifier`と`Hijack`を同じ接続上で使用するとエラーが発生するか、予期せぬ動作を引き起こしていました。これは、`CloseNotifier`が接続の状態を不可逆的に変更してしまうためです。

4.  **接続状態の「汚染」**: `CloseNotifier`が接続全体で共有されていたため、あるリクエストのハンドラが`CloseNotifier`を使用すると、同じ接続上の後続のリクエストのハンドラが`CloseNotifier`を正しく使用できなくなる可能性がありました。これは、接続の状態が前のリクエストによって「汚染」されることを意味します。

これらの問題を解決し、`net/http`パッケージの堅牢性と予測可能性を高めるために、`CloseNotifier`の実装の根本的な見直しとドキュメントの明確化が必要とされました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識が必要です。

1.  **HTTP/1.1 プロトコル**:
    *   **リクエスト/レスポンスサイクル**: クライアントがリクエストを送信し、サーバーがレスポンスを返す基本的な流れ。
    *   **Keep-Alive接続**: 複数のリクエスト/レスポンスを単一のTCP接続上で処理することで、接続確立のオーバーヘッドを削減するメカニズム。
    *   **パイプライン処理 (Pipelining)**: HTTP/1.1の機能の一つで、クライアントが前のレスポンスを待たずに複数のリクエストを連続して送信できる仕組み。ただし、実際にはブラウザでの実装は少なく、広く使われている機能ではありません。このコミットでは、このパイプライン処理が`CloseNotifier`に与える影響が重要になります。
    *   **冪等性 (Idempotency)**: 同じリクエストを複数回実行しても、サーバーの状態が初回実行時と同じ結果になる特性。GETリクエストは通常冪等ですが、POSTリクエストは非冪等です。

2.  **Goの`net/http`パッケージ**:
    *   **`http.Handler`インターフェース**: `ServeHTTP(ResponseWriter, *Request)`メソッドを持つインターフェースで、HTTPリクエストを処理するための基本的な単位です。
    *   **`http.ResponseWriter`インターフェース**: HTTPレスポンスをクライアントに書き込むためのインターフェース。
    *   **`http.Request`構造体**: クライアントからのHTTPリクエストを表す構造体。`Body`フィールドはリクエストボディを読み取るための`io.ReadCloser`です。
    *   **`http.CloseNotifier`インターフェース**: `CloseNotify() <-chan bool`メソッドを持つインターフェース。`http.ResponseWriter`がこのインターフェースを実装している場合、クライアントが接続を切断した際にチャネルに値が送信され、ハンドラがその通知を受け取ることができます。これにより、長時間実行される処理中にクライアントが切断した場合に、サーバー側で処理を中断するなどの対応が可能になります。
    *   **`http.Hijacker`インターフェース**: `Hijack() (net.Conn, *bufio.ReadWriter, error)`メソッドを持つインターフェース。`http.ResponseWriter`がこれを実装している場合、ハンドラはHTTPサーバーの制御をバイパスし、基盤となるTCP接続を直接操作できるようになります。これはWebSocketのようなプロトコルや、カスタムプロトコルを実装する際に使用されます。

3.  **GoのI/Oプリミティブ**:
    *   **`io.Reader` / `io.Writer`**: データの読み書きを行うための基本的なインターフェース。
    *   **`bufio.Reader` / `bufio.Writer`**: バッファリングされたI/Oを提供する構造体。効率的な読み書きのために使用されます。
    *   **`io.LimitedReader`**: 指定されたバイト数までしか読み取れない`Reader`のラッパー。リクエストヘッダーのサイズ制限などに利用されます。
    *   **`io.Pipe`**: 読み書きが同期的に行われるインメモリパイプ。ゴルーチン間でデータをやり取りする際に使用されます。

4.  **Goの並行処理**:
    *   **ゴルーチン (Goroutine)**: Goの軽量なスレッド。並行処理を実現するために使用されます。
    *   **チャネル (Channel)**: ゴルーチン間でデータを安全にやり取りするための通信メカニズム。
    *   **`sync.Mutex`**: 共有リソースへのアクセスを排他的に制御するためのミューテックス。競合状態（Race Condition）を防ぎます。

これらの概念を理解することで、`CloseNotifier`の再設計がなぜ必要だったのか、そして新しい実装がどのようにこれらの問題を解決しているのかを深く把握することができます。

## 技術的詳細

このコミットにおける`CloseNotifier`の実装の再構築は、主に以下の技術的詳細と変更点を含んでいます。

1.  **`CloseNotifier`のセマンティクスの明確化と厳格化**:
    *   **リクエストボディの消費**: `CloseNotifier`を使用する前に、`Request.Body`を完全に読み取る必要があるというルールが明示されました。これは以前から暗黙の了解でしたが、ドキュメントで明確にされました。
    *   **チャネル送信の保証**: ハンドラがリターンした後、`CloseNotifier`チャネルに値が送信される保証はないと明記されました。これは、ハンドラのライフサイクルと接続のライフサイクルが異なるため、ハンドラが終了した後に接続が切断されても、その通知がハンドラに届くとは限らないことを意味します。
    *   **HTTP/1.1パイプライン処理への対応**: 以前はパイプラインリクエストが`CloseNotifier`をデッドロックさせていましたが、新しい動作では後続のパイプラインリクエストが到着すると、最初のハンドラの`CloseNotifier`チャネルが発火するようになりました。ただし、HTTP/1.1パイプライン処理はブラウザではほとんど使用されないため、HTTP/2または非冪等なリクエスト（POSTなど）での使用が推奨されています。

2.  **`CloseNotifier`のスコープ変更**:
    *   **接続ごとの共有からリクエストごとの独立へ**: 以前は、`CloseNotifier`チャネルは`conn`構造体全体で共有されていました。このコミットの最も重要な変更点の一つは、各`http.Handler`が独自の`CloseNotifier`チャネル値を持つようになったことです。これにより、あるハンドラが`CloseNotifier`を使用しても、同じ接続上の後続のリクエストのハンドラに影響を与えることがなくなりました。これはHTTP/2サーバーの動作と一致しており、接続の「汚染」問題（#9763）を解決します。

3.  **`connReader`型の導入とI/O処理の改善**:
    *   **`io.LimitReader`機能の吸収**: 以前は、リクエストヘッダーのサイズ制限のために`io.LimitReader`が使用されていましたが、新しい`*connReader`型がこの機能を吸収しました。これにより、複数の`Reader`ラッパーが連鎖する複雑さが軽減され、I/Oスタックが簡素化されます。
    *   **同期読み取りと非同期読み取りの統合**: `connReader`は、`io.MultiReader`のように同期読み取りと非同期読み取りを結合する役割を担います。
    *   **バックグラウンド読み取りの変更**: 以前の`CloseNotifier`の実装では、`io.Pipe`と`io.CopyBuffer`を使った無限コピーがバックグラウンドで行われていました。これが`Hijack`との非互換性の原因でした。新しい実装では、`connReader`内のバックグラウンドゴルーチンが、基盤となる`net.Conn`（または`*tls.Conn`）から**単一バイト**のみを読み取るように変更されました。
        *   この単一バイトの読み取りは、リクエストボディの一部、ソケットタイムアウトエラー、`io.EOF`、または後続のパイプラインリクエストの最初のバイトである可能性があります。
        *   この変更により、バックグラウンド読み取りが接続の状態をロックすることなく、`CloseNotifier`の通知トリガーとして機能できるようになりました。
        *   `Hijack`が呼び出された場合でも、基盤となる`net.Conn`が`io.Pipe`に切り替わっていないため、正しく接続を返すことが可能になりました。

4.  **不要な型の削除**:
    *   `liveSwitchReader`型と`switchWriter`型が削除されました。これらは以前の`CloseNotifier`の実装に関連するもので、`connReader`の導入により不要になりました。

5.  **`conn`構造体のドキュメント強化**:
    *   `conn`構造体の各フィールドについて、より詳細な説明が追加され、内部的な理解が深まりました。

これらの変更により、`CloseNotifier`はより堅牢で予測可能な動作をするようになり、`net/http`パッケージ全体の信頼性が向上しました。特に、`Hijack`との互換性問題とパイプライン処理によるデッドロック問題が解決されたことは大きな進歩です。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、`src/net/http/server.go`と`src/net/http/serve_test.go`に集中しています。

### `src/net/http/server.go`

1.  **`CloseNotifier`インターフェースのドキュメント更新**:
    *   `CloseNotify()`メソッドのコメントが大幅に加筆修正され、`Request.Body`の完全な読み取りが必要であること、ハンドラが戻った後のチャネル送信の保証がないこと、HTTP/1.1パイプライン処理時の動作、およびHTTP/2または非冪等なメソッドでの使用推奨が明記されました。

2.  **`conn`構造体の変更**:
    *   `remoteAddr`, `server`, `rwc`, `tlsState`, `werr`などのフィールドに詳細なコメントが追加され、その役割が明確化されました。
    *   `sr liveSwitchReader`フィールドが削除され、代わりに`r *connReader`が追加されました。
    *   `lr *io.LimitedReader`フィールドが削除されました。
    *   `buf *bufio.ReadWriter`フィールドが削除され、代わりに`bufr *bufio.Reader`と`bufw *bufio.Writer`が追加されました。
    *   `clientGone bool`と`closeNotifyc chan bool`フィールドが削除されました。
    *   `mu sync.Mutex`のガード対象が明確化されました。
    *   `response`構造体に`closeNotifyCh <-chan bool`フィールドが追加され、`conn.mu`によってガードされるようになりました。

3.  **`conn.hijack()`メソッドの変更**:
    *   メソッド名が`conn.hijackLocked()`に変更され、`c.mu`が保持されている必要があることが示唆されました。
    *   以前存在した`c.closeNotifyc != nil`の場合のエラーチェックが削除されました。これは、`CloseNotifier`が接続全体ではなくリクエストごとに管理されるようになったため、`Hijack`との非互換性が解消されたためです。
    *   `buf = c.buf`の代わりに`buf = bufio.NewReadWriter(c.bufr, bufio.NewWriter(rwc))`が使用されるようになりました。

4.  **`conn.closeNotify()`メソッドの削除**:
    *   このメソッドは完全に削除され、`CloseNotifier`のロジックは`response.CloseNotify()`に移動されました。

5.  **`liveSwitchReader`型と`switchWriter`型の削除**:
    *   これらの型は、新しい`connReader`の導入により不要になったため、コードベースから削除されました。

6.  **`connReader`型の追加**:
    *   `connReader`という新しい構造体が追加されました。
    *   フィールド: `r io.Reader`, `remain int64`, `ch chan readResult`。
    *   メソッド: `setReadLimit`, `setInfiniteReadLimit`, `hitReadLimit`, `Read`, `startBackgroundRead`, `closeNotifyAwaitActivityRead`。
    *   この型は、`io.LimitedReader`の機能と、`CloseNotifier`のためのバックグラウンドでの単一バイト読み取りを統合します。

7.  **`Server.newConn()`関数の変更**:
    *   `conn`の初期化ロジックが簡素化され、`connReader`, `bufio.Reader`, `bufio.Writer`の初期化は`conn.serve()`メソッド内に移動されました。

8.  **`conn.readRequest()`メソッドの変更**:
    *   `c.lr.N`による読み取り制限の管理が、`c.r.setReadLimit()`と`c.r.hitReadLimit()`を使用するように変更されました。
    *   `c.bufr`（新しい`bufio.Reader`）がリクエストの読み取りに使用されるようになりました。

9.  **`response.CloseNotify()`メソッドの追加と実装**:
    *   このメソッドは、`CloseNotifier`インターフェースの実装を提供します。
    *   `conn.mu`による排他制御が行われます。
    *   `closeNotifyCh`が既に存在する場合はそれを返します。
    *   新しいチャネルを作成し、`closeNotifyCh`に設定します。
    *   `conn.hijackedv`がtrueの場合（Hijack済みの場合）は、値が送信されないチャネルを返します。
    *   `c.bufr.Buffered() > 0`の場合（パイプラインリクエストや未読のリクエストボディデータがある場合）は、`notify()`を即座に呼び出してチャネルに値を送信します。
    *   それ以外の場合は、`c.r.startBackgroundRead(notify)`を呼び出してバックグラウンドで単一バイト読み取りを開始し、アクティビティがあった場合にチャネルに通知します。

10. **`conn.serve()`メソッドの変更**:
    *   `connReader`, `bufio.Reader`, `bufio.Writer`の初期化がここで行われるようになりました。

## コアとなるコードの解説

このコミットの核心は、`net/http`パッケージにおける`CloseNotifier`の動作をより堅牢で予測可能なものにするための、`conn`構造体と関連するI/O処理の再設計にあります。

### `connReader`の役割

以前の`net/http`サーバーのI/Oスタックは、`io.LimitReader`や`liveSwitchReader`など、複数の`Reader`ラッパーが複雑に絡み合っていました。特に`CloseNotifier`が使用されると、基盤となる`net.Conn`からの読み取りが`io.Pipe`に切り替わり、バックグラウンドで無限コピーが実行されるという、`Hijack`との非互換性を生む原因となっていました。

新しい`connReader`型は、この複雑さを解消し、以下の主要な機能を提供します。

1.  **`io.LimitReader`機能の吸収**: `connReader`は`remain`フィールドを持ち、`setReadLimit`メソッドで読み取り可能なバイト数を制限できます。これにより、リクエストヘッダーのサイズ制限など、以前`io.LimitReader`が担っていた役割を`connReader`自身が果たせるようになります。
2.  **同期/非同期読み取りの統合**: `connReader`の`Read`メソッドは、通常の同期的な読み取りパスを提供します。しかし、`CloseNotifier`がアクティブな場合、`startBackgroundRead`メソッドが呼び出され、バックグラウンドゴルーチンで`closeNotifyAwaitActivityRead`が実行されます。
    *   `closeNotifyAwaitActivityRead`は、基盤となる`cr.r`（通常は`net.Conn`）から**単一バイト**のみを読み取ろうとします。
    *   この読み取りはブロックされる可能性がありますが、`cr.ch`チャネルを通じて結果を`connReader`の`Read`メソッドに伝えます。
    *   もし`Read`メソッドが呼び出された際に`cr.ch`に結果が既に存在する場合、その結果が優先的に使用されます。これにより、`CloseNotifier`のバックグラウンド読み取りと、通常のHTTPリクエストの読み取りがスムーズに連携します。
    *   この単一バイト読み取りの戦略は、以前の無限コピーとは異なり、接続の状態を不可逆的に変更しないため、`Hijack`との互換性が保たれます。

### `response.CloseNotify()`の実装

`CloseNotifier`インターフェースの実装は、`conn`構造体から`response`構造体に移されました。これにより、`CloseNotifier`のチャネルが接続全体ではなく、**各HTTPリクエストのハンドラに固有**のものとなります。

1.  **リクエストごとのチャネル**: `response`構造体内の`closeNotifyCh <-chan bool`フィールドが、各リクエストの`CloseNotifier`チャネルを保持します。これにより、あるハンドラが`CloseNotifier`を使用しても、他のハンドラに影響を与えることがなくなります。
2.  **`conn.mu`による保護**: `response.CloseNotify()`メソッドは、`w.conn.mu`ミューテックスによって保護されます。これにより、チャネルの作成や状態の変更が並行処理において安全に行われます。
3.  **パイプラインリクエストへの対応**:
    *   `if c.bufr.Buffered() > 0`のチェックが重要です。これは、`bufio.Reader`にまだ読み取られていないデータが残っているかどうかを確認します。
    *   もしデータが残っている場合、それは後続のパイプラインリクエストのヘッダーであるか、または前のリクエストボディの未読データである可能性があります。いずれにせよ、クライアントが接続を切断したと見なすことができるため、`notify()`関数を即座に呼び出して`CloseNotifier`チャネルに値を送信します。これにより、#13165のデッドロック問題が解決されます。
4.  **バックグラウンド読み取りの開始**: `c.bufr.Buffered() == 0`の場合、つまりバッファにデータがない場合は、`c.r.startBackgroundRead(notify)`を呼び出して、`connReader`にバックグラウンドでの単一バイト読み取りを開始させます。この読み取りが完了するか、エラーが発生すると`notify()`が呼び出され、`CloseNotifier`チャネルに通知が送られます。
5.  **`Hijack`との互換性**: `if w.conn.hijackedv`のチェックにより、既に`Hijack`された接続に対して`CloseNotifier`が呼び出された場合でも、エラーを発生させることなく、値が送信されないチャネルを返します。これは、`Hijack`が接続の制御を完全にハンドラに渡すため、`CloseNotifier`の通知メカニズムが機能しなくなることを意味しますが、以前のような非互換性によるパニックやエラーは回避されます。

これらの変更により、`CloseNotifier`はより明確なセマンティクスを持ち、HTTP/1.1パイプライン処理や`Hijack`といった高度な機能との相互運用性が大幅に向上しました。

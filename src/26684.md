## 元コミット内容

このコミットは、GoコンパイラのSSA（Static Single Assignment）形式における共通部分式除去（CSE）パスが、交換法則が成り立つ演算（例: `a + b` と `b + a`）をより効果的に処理できるようにするためのものです。具体的には、交換法則が成り立つ二項演算のオペランドを正規の順序（canonical way）に並べ替えることで、オペランドの順序が異なるだけの同じ式をCSEが認識し、冗長な計算を排除できるようにします。

この変更により、`pkg/tool/linux_amd64/*` のコンパイル済みバイナリサイズが約14KB（約0.015%）削減されました。

コミットメッセージでは、`Leq`（Less than or equal）や `Geq`（Greater than or equal）のような比較演算に対しても同様の試みが行われたが、`lowered cse` パスを混乱させ、`IsInBounds` から冗長な比較を除去できなくなるため、結果が良くなかったと述べられています。これは、比較演算が必ずしも厳密な意味で交換法則を満たすわけではない（例: `a <= b` と `b <= a` は異なる意味を持つ）こと、またはコンパイラのより低レベルの最適化パスとの相互作用が複雑であることを示唆しています。

## 変更の背景

コンパイラ最適化の一つである共通部分式除去（CSE）は、プログラム内で複数回計算される同じ式を一度だけ計算し、その結果を再利用することで、実行速度の向上やコードサイズの削減を目指します。しかし、従来のCSEでは、`a + b` と `b + a` のように、オペランドの順序が異なるだけで意味的には同じである式を、異なる式として扱ってしまう問題がありました。

これは、コンパイラが式の「形」に基づいて共通部分を識別するため、オペランドの順序が異なると、たとえ数学的には同じ結果になるとしても、異なる内部表現として扱われてしまうためです。このコミットは、この問題を解決し、交換法則が成り立つ演算に対してより積極的なCSEを可能にすることで、コンパイラが生成するコードの効率をさらに高めることを目的としています。

特に、GoコンパイラのSSAバックエンドは、プログラムをSSA形式に変換し、その上で様々な最適化を適用します。この段階で交換法則を考慮に入れることで、より多くの最適化機会を捉えることができます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。

例えば、以下のコードがあるとします。

```go
x = a + b
y = x * 2
x = c + d
z = x * 2
```

これをSSA形式に変換すると、以下のようになります。

```go
x1 = a + b
y1 = x1 * 2
x2 = c + d
z1 = x2 * 2
```

このように、変数のバージョン管理を行うことで、どの `x` がどの `x` を指しているのかが明確になります。Goコンパイラも、最適化の段階でプログラムをSSA形式に変換します。

### 2. 共通部分式除去 (CSE: Common Subexpression Elimination)

CSEは、コンパイラ最適化の基本的な手法の一つで、プログラム内で同じ値が複数回計算されている場合、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

例:
```go
result1 = (a + b) * c
result2 = (a + b) * d
```

この場合、`(a + b)` は共通部分式です。CSEを適用すると、以下のようになります。

```go
temp = a + b
result1 = temp * c
result2 = temp * d
```

これにより、`a + b` の計算が一度で済み、効率が向上します。

### 3. 交換法則 (Commutative Property)

数学における交換法則とは、二項演算においてオペランドの順序を入れ替えても結果が変わらない性質を指します。

例:
*   加算: `a + b = b + a`
*   乗算: `a * b = b * a`
*   論理積 (AND): `a & b = b & a`
*   論理和 (OR): `a | b = b | a`
*   排他的論理和 (XOR): `a ^ b = b ^ a`
*   等価比較: `a == b = b == a`

CSEのような最適化では、これらの交換法則が成り立つ演算において、オペランドの順序が異なるだけの式を同じものとして認識できると、より多くの最適化機会が生まれます。

### 4. Canonical Ordering (正規順序付け)

正規順序付けとは、複数の同等な表現の中から、特定の基準に基づいて一意の表現を選択するプロセスです。CSEの文脈では、交換法則が成り立つ演算のオペランドを、常に同じ順序（例えば、IDが小さい方を常に最初のオペランドにする）に並べ替えることを指します。これにより、`a + b` と `b + a` が内部的には `min(a,b) + max(a,b)` のような一意の表現として扱われ、CSEがこれらを同じ式として認識できるようになります。

### 5. Goコンパイラの `cmd/compile/internal/ssa` パッケージ

`cmd/compile/internal/ssa` は、Goコンパイラのバックエンドの一部であり、GoのソースコードをSSA形式に変換し、その上で様々な最適化を行う役割を担っています。このパッケージには、SSA形式の値を表現する `Value` 型、演算の種類を定義する `Op` 型、そして最適化パス（例: CSE）の実装が含まれています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるCSEパスが、交換法則が成り立つ演算のオペランドの順序を正規化することで、より効果的に機能するようにすることです。

従来のCSEでは、`x + y` と `y + x` は異なる式として扱われていました。これは、コンパイラが式の構造を比較する際に、オペランドの順序も考慮に入れていたためです。しかし、加算のような交換法則が成り立つ演算では、オペランドの順序は結果に影響しません。したがって、これらを同じ式として扱うことで、冗長な計算を排除できる可能性が高まります。

この問題を解決するために、以下の変更が導入されました。

1.  **演算の交換法則属性の追加**: `src/cmd/compile/internal/ssa/op.go` および `src/cmd/compile/internal/ssa/gen/genericOps.go` に、各演算が交換法則を持つかどうかを示す `commutative` フラグが追加されました。`Add`、`Mul`、`And`、`Or`、`Xor`、`Eq`、`Neq` などの二項演算に対してこのフラグが `true` に設定されます。
2.  **CSEパスでのオペランド正規化**: `src/cmd/compile/internal/ssa/cse.go` のCSEパスにおいて、`commutative` フラグが `true` の二項演算（オペランドが2つの演算）が見つかった場合、そのオペランドの順序を正規化するロジックが追加されました。具体的には、オペランドのID（SSA形式における値の一意な識別子）を比較し、IDが小さい方を常に最初のオペランドとして配置するように並べ替えます。

この正規化により、`v1 + v2` と `v2 + v1` のような式は、CSEパスに到達する前に `min(v1, v2) + max(v1, v2)` のような一意の表現に変換されます。その結果、CSEはこれらを同じ共通部分式として認識し、冗長な計算を排除できるようになります。

コミットメッセージで言及されている `Leq` や `Geq` のような比較演算で同様の試みが失敗した理由は、これらの演算が厳密には交換法則を持たないため、単純なオペランドの並べ替えが意味論的な変更を引き起こすか、あるいはコンパイラの他の最適化パス（`lowered cse`）との相互作用で予期せぬ悪影響を及ぼしたためと考えられます。例えば、`a <= b` と `b <= a` は異なる条件を表します。また、`IsInBounds` のような特定のコンテキストでは、比較の順序が重要になる場合があります。

この変更は、コンパイラがより賢く最適化を行うための重要なステップであり、最終的に生成されるバイナリの効率向上に貢献します。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/cmd/compile/internal/ssa/cse.go` 内の `cse` 関数に追加された以下のコードブロックです。

```go
if opcodeTable[v.Op].commutative && len(v.Args) == 2 && v.Args[1].ID < v.Args[0].ID {
	// Order the arguments of binary commutative operations.
	v.Args[0], v.Args[1] = v.Args[1], v.Args[0]
}
```

このコードは、SSA形式の各 `Value` (`v`) を処理する際に実行されます。

1.  **`opcodeTable[v.Op].commutative`**:
    *   `v.Op` は現在の `Value` が表す演算の種類（例: `Add8`, `Mul64` など）です。
    *   `opcodeTable` は、Goコンパイラが持つすべてのSSA演算に関するメタデータ（`opInfo` 構造体）を格納するテーブルです。
    *   この条件は、現在の演算が交換法則を持つかどうかをチェックします。`genericOps.go` および `opGen.go` の変更により、加算、乗算、ビット演算、等価比較などの演算には `commutative: true` が設定されています。

2.  **`len(v.Args) == 2`**:
    *   この条件は、現在の演算が二項演算（2つのオペランドを持つ演算）であることを確認します。交換法則は通常、二項演算に適用されるため、このチェックは重要です。

3.  **`v.Args[1].ID < v.Args[0].ID`**:
    *   `v.Args` は、現在の `Value` のオペランド（引数）のリストです。
    *   `v.Args[0]` は最初のオペランド、`v.Args[1]` は2番目のオペランドです。
    *   `ID` は、SSA形式における各 `Value` に割り当てられる一意の識別子です。
    *   この条件は、2番目のオペランドのIDが最初のオペランドのIDよりも小さい場合に `true` となります。これは、オペランドを「正規の順序」に並べ替えるための基準として使用されます。具体的には、IDが小さいオペランドを常に `v.Args[0]` に、IDが大きいオペランドを常に `v.Args[1]` に配置するようにします。

4.  **`v.Args[0], v.Args[1] = v.Args[1], v.Args[0]`**:
    *   上記の条件がすべて `true` の場合、この行が実行され、オペランドの順序が入れ替えられます。これにより、`v.Args[0]` にはIDが小さい方のオペランドが、`v.Args[1]` にはIDが大きい方のオペランドが格納されることになります。

この正規化ステップは、CSEパスの非常に早い段階で実行されます。これにより、例えば `v1 + v2` と `v2 + v1` という2つの異なる `Value` が存在しても、CSEパスがそれらを処理する前に、両方とも `min(v1, v2) + max(v1, v2)` のような正規化された形式に変換されます。結果として、CSEはこれらを同じ共通部分式として認識し、一方の計算を削除してもう一方の結果を再利用できるようになります。

この変更は、コンパイラの最適化能力を向上させ、生成されるコードの効率を高めるための、シンプルでありながら効果的な手法です。

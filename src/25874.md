## 変更の背景

このコミットは、Go言語の `mime` パッケージにおけるメディアタイプパラメータ値の解析に関する長年のバグを修正するものです。具体的には、メディアタイプパラメータの値がシングルクォートで囲まれている場合でも、ダブルクォートで囲まれている場合と同様に有効な値として扱われてしまうという問題がありました。

このバグは、2011年4月に `git rev 90e4ece3` (https://golang.org/cl/4430049) で導入されました。当時、`http://greenbytes.de/tech/tc2231/` から追加のテストケースを実装する際に、`attwithfntokensq` というテストの期待値を誤って解釈したことが原因でした。

MIMEの仕様（RFC 2045など）では、メディアタイプパラメータの値はダブルクォートで囲むか、またはトークン（引用符なしの文字列）として表現されることが規定されています。シングルクォートで囲む形式は、どの既知の仕様にも存在せず、既存のソフトウェアもそのような形式を生成したり期待したりすることはありません。

この誤った挙動は、`a=', b='` のような文字列が与えられた場合に解析の曖昧さを引き起こす可能性がありました。この文字列は、「キー `a` と `b` がそれぞれ値 `'` を持つ」と解釈することも、「キー `a` が値 `', b=` を持つ」と解釈することもできてしまいます。このような曖昧さは、セキュリティ上の脆弱性や予期せぬ動作につながる可能性があるため、修正が必要でした。

この修正は、Issue #11291 に対応するものです。

## 前提知識の解説

### MIMEメディアタイプ (Media Type)

MIME (Multipurpose Internet Mail Extensions) メディアタイプは、インターネット上で転送されるデータの種類を識別するための標準的な方法です。HTTPヘッダーの `Content-Type` フィールドなどで使用され、例えば `text/html` はHTMLドキュメント、`image/jpeg` はJPEG画像を表します。

メディアタイプは通常、`type/subtype` の形式で構成されます。

### メディアタイプパラメータ (Media Type Parameters)

メディアタイプには、追加情報を提供するためのパラメータを含めることができます。これらは `attribute=value` の形式で、セミコロンで区切られてメディアタイプに付加されます。例えば、`text/plain; charset=utf-8` では、`charset=utf-8` がパラメータであり、`charset` が属性名、`utf-8` が値です。

### RFC 2045: MIME Part 1: Format of Internet Message Bodies

RFC 2045は、MIMEメッセージの基本的なフォーマットを定義しています。メディアタイプパラメータの引用符に関する主要なルールは以下の通りです。

- **構文**: パラメータは `attribute=value` の形式です。
- **値の形式**: パラメータの値は、以下のいずれかです。
    - **トークン (token)**: スペース、制御文字、および特定の特殊文字（`tspecials`）を含まないUS-ASCII文字のシーケンスです。引用符は不要です。
    - **引用符付き文字列 (quoted-string)**: ダブルクォート (`"`) で囲まれた文字列です。ダブルクォート自体は値の一部ではなく、区切り文字として機能します。引用符付き文字列内では、バックスラッシュ (`\`) を使ってダブルクォートやバックスラッシュ自体をエスケープできます。
- **等価性**: トークンとして表現できる値は、ダブルクォートで囲んでも意味は変わりません。例: `charset=us-ascii` と `charset="us-ascii"` は等価です。

**RFC 2045では、シングルクォートでパラメータ値を囲むことは許可されていません。**

### RFC 2231: MIME Parameter Value and Encoded Word Extensions

RFC 2231は、RFC 2045のパラメータ値に関するいくつかの制限（US-ASCII以外の文字セットのサポート、長いパラメータ値の扱いなど）を解決するために導入された拡張仕様です。

RFC 2231では、拡張パラメータの構文が導入され、パラメータ名にアスタリスク (`*`) を付加することで、文字セット、言語、およびエンコーディング情報を含むことができるようになりました。例えば、`filename*=utf-8'en'foo%20bar.txt` のような形式です。

この拡張構文では、値の内部にシングルクォート (`'`) が文字セットと言語タグの区切り文字として使用されますが、**パラメータ値全体をシングルクォートで囲むことを許可するものではありません**。このコミットで問題となっているのは、RFC 2045の `quoted-string` の文脈で、ダブルクォートの代わりにシングルクォートが使われてしまうケースです。

## 技術的詳細

`mime` パッケージの `consumeValue` 関数は、メディアタイプパラメータの値を解析する役割を担っています。この関数は、入力文字列が引用符で始まっているかどうかを判断し、それに応じて引用符付き文字列として解析するか、またはトークンとして解析するかを決定します。

元のコードでは、`if !strings.HasPrefix(v, `"`) && !strings.HasPrefix(v, `'`)` という条件で、文字列がダブルクォート (`"`) またはシングルクォート (`'`) のいずれでも始まっていない場合にトークンとして処理していました。これは、文字列がどちらかの引用符で始まっている場合は、引用符付き文字列として解析しようとすることを意味します。

このロジックの問題点は、シングルクォートで始まる文字列も有効な引用符付き文字列として扱ってしまっていたことです。MIMEの仕様ではダブルクォートのみが引用符として認められているため、これは仕様違反です。

さらに深刻な問題は、コミットメッセージで指摘されている解析の曖昧さです。例えば、`Content-Type: text/plain; a=', b='` のようなヘッダーが与えられた場合を考えます。

1.  **現在の（バグのある）実装**: `a` の値がシングルクォートで囲まれた文字列として解析され、値は `', b=` となる可能性があります。この場合、`b` は別のパラメータとして認識されません。
2.  **正しい実装**: シングルクォートは引用符として認識されないため、`a` の値はトークンとして `',` と解析され、その後に `b='` という別のパラメータが続くことになります。

この曖昧さは、悪意のある入力によって意図しない解釈を引き起こし、アプリケーションのロジックに影響を与える可能性があります。例えば、ファイル名やコンテンツタイプに基づいて処理を分岐するようなシステムでは、予期せぬ動作やセキュリティ上の問題につながる恐れがあります。

このコミットは、この曖昧さを排除し、MIMEの仕様に厳密に従うことで、堅牢性とセキュリティを向上させることを目的としています。

## コアとなるコードの解説

### `src/mime/mediatype.go` の変更

1.  **引用符のチェックの変更**:
    元のコード: `if !strings.HasPrefix(v, `"`) && !strings.HasPrefix(v, `'`)`
    変更後:
    ```go
    if v == "" {
        return
    }
    if v[0] != '"' {
        return consumeToken(v)
    }
    ```
    この変更により、`consumeValue` 関数は、入力文字列 `v` が空でないことを確認した後、**先頭文字がダブルクォート (`"`) でない場合のみ** `consumeToken` 関数を呼び出すようになりました。これにより、シングルクォート (`'`) で始まる文字列は、もはや引用符付き文字列として特別扱いされず、通常のトークンとして解析されるようになります。これは、MIMEの仕様に合致する動作です。

2.  **`leadQuote` 変数の削除**:
    元のコードでは、`leadQuote := rune(v[0])` で先頭の引用符（ダブルクォートまたはシングルクォート）を記憶し、ループ内で `r == leadQuote` で閉じ引用符をチェックしていました。シングルクォートが引用符として扱われなくなったため、この `leadQuote` 変数は不要になり、削除されました。

3.  **閉じ引用符のチェックの変更**:
    元のコード: `case r == leadQuote:`
    変更後: `case r == '"':`
    これにより、引用符付き文字列の解析中に、閉じ引用符として認識されるのは**ダブルクォート (`"`) のみ**となりました。シングルクォートは、引用符付き文字列内の通常の文字として扱われます。

これらの変更により、`consumeValue` 関数はMIMEの仕様に厳密に従い、ダブルクォートで囲まれた文字列のみを引用符付き文字列として解析し、それ以外の文字列はトークンとして解析するようになりました。

### `src/mime/mediatype_test.go` の変更

1.  **シングルクォートテストケースの期待値の変更**:
    元のテストケース:
    ```go
    {`attachment; filename='foo.html'`,
        "attachment",
        m("filename", "foo.html")},
    ```
    変更後:
    ```go
    {`attachment; filename='foo.html'`,
        "attachment",
        m("filename", "'foo.html'")},
    ```
    この変更は、`filename='foo.html'` という入力が与えられた場合、`filename` パラメータの値がもはや `foo.html` とは解析されず、シングルクォートを含んだ `'foo.html'` という文字列全体が値として扱われることを示しています。これは、シングルクォートが引用符として機能しなくなった結果です。

2.  **新しいテストケースの追加**:
    ```go
    {"foo/bar", map[string]string{"0": "'", "9": "'"}, "foo/bar; 0='; 9='"},
    ```
    このテストケースは、パラメータ値にシングルクォートが含まれるが、それが引用符として機能しない場合の挙動を検証しています。`0='` と `9='` は、それぞれ値がシングルクォートであるトークンとして正しくフォーマットされることを確認しています。

これらのテストケースの変更は、`mediatype.go` で行われた解析ロジックの変更が意図した通りに機能し、MIMEの仕様に準拠していることを確認するために不可欠です。

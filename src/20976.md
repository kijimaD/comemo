# [インデックス 20976] ファイルの概要

このコミットは、Goコンパイラ（`9g`）がPowerPC 64-bit (power64x) アーキテクチャ向けに生成するコードにおける、`clearfat` 関数でのメモリゼロ初期化の不具合を修正するものです。具体的には、大きな構造体や配列をゼロ初期化する際に、一部のメモリ領域が適切にゼロクリアされない「under-zeroing」という問題が発生していました。この修正により、PowerPC 64-bit環境でのGoプログラムのメモリ安全性が向上します。

## コミット

```
commit 6e86003651be7feb6da46360d6c411ff1c29b7f5
Author: Austin Clements <austin@google.com>
Date:   Fri Oct 31 11:08:27 2014 -0400

    [dev.power64] 9g: fix under-zeroing in clearfat

    All three cases of clearfat were wrong on power64x.

    The cases that handle 1032 bytes and up and 32 bytes and up
    both use MOVDU (one directly generated in a loop and the other
    via duffzero), which leaves the pointer register pointing at
    the *last written* address.  The generated code was not
    accounting for this, so the byte fill loop was re-zeroing the
    last zeroed dword, rather than the bytes following the last
    zeroed dword.  Fix this by simply adding an additional 8 byte
    offset to the byte zeroing loop.

    The case that handled under 32 bytes was also wrong.  It
    didn't update the pointer register at all, so the byte zeroing
    loop was simply re-zeroing the beginning of region.  Again,
    the fix is to add an offset to the byte zeroing loop to
    account for this.
```

## 変更の背景

Go言語では、新しい変数や構造体が宣言された際に、そのメモリ領域が自動的にゼロ値で初期化されることが保証されています。これはGoのメモリ安全性を高める重要な特性の一つです。このゼロ初期化処理は、コンパイラによって生成されるコードや、Goランタイム内の特定の関数によって行われます。

`clearfat` 関数は、特に大きな構造体や配列、あるいはスタック上のオブジェクトなど、特定のメモリ領域を効率的にゼロ初期化するためにGoコンパイラ（`9g`、PowerPC 64-bitアーキテクチャ向け）が利用する内部関数です。

PowerPC 64-bit (power64x) アーキテクチャにおいて、この `clearfat` 関数の実装にバグが存在していました。具体的には、メモリをゼロクリアする際に、ポインタレジスタの更新方法に誤りがあり、結果として指定されたメモリ領域の一部がゼロ初期化されずに残ってしまう「under-zeroing」という問題が発生していました。これは、Goのメモリ安全性の保証を破る可能性があり、未初期化のメモリ内容がプログラムの動作に影響を与えるという潜在的なバグを引き起こす恐れがありました。

この問題は、特に`MOVDU`命令や`duffzero`ルーチンがポインタレジスタを更新する挙動と、その後のバイト単位のゼロクリア処理との間の不整合によって引き起こされていました。このコミットは、この不整合を解消し、PowerPC 64-bit環境でのGoプログラムの堅牢性と安全性を確保するために行われました。

## 前提知識の解説

### Go言語のメモリ管理とゼロ初期化

Go言語は、変数が宣言されると自動的にその型のゼロ値で初期化されるという特徴を持っています。例えば、`int`型は`0`、`string`型は`""`、ポインタ型は`nil`で初期化されます。これは、C/C++のような言語で起こりうる未初期化変数の使用によるバグを防ぐ上で非常に重要です。このゼロ初期化は、コンパイラが生成するコードやランタイムのサポートによって実現されます。

### `clearfat` 関数

`clearfat` は、Goコンパイラ（特に`9g`、PowerPC 64-bitアーキテクチャ向け）が、大きな構造体や配列、あるいはスタック上のオブジェクトなどのメモリ領域を効率的にゼロ初期化するために使用する内部関数です。この関数は、指定されたメモリブロックをゼロで埋める役割を担います。通常、これはアセンブリ言語で実装され、特定のアーキテクチャの特性（レジスタ、命令セットなど）を最大限に活用して高速化されます。

### PowerPC 64-bit (power64x) アーキテクチャ

PowerPCは、IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。power64xは、その64ビット版を指します。Go言語は、様々なアーキテクチャをサポートしており、PowerPCもその一つです。PowerPCアーキテクチャには、汎用レジスタ（GPRs）、浮動小数点レジスタ（FPRs）などがあり、命令セットにはロード/ストア命令、算術/論理命令などが含まれます。

*   **レジスタ**: PowerPCの汎用レジスタは通常R0からR31まであり、データやアドレスを保持します。
*   **`MOVDU` 命令**: PowerPCのアセンブリ命令の一つで、"Move Doubleword with Update" を意味します。この命令は、指定されたレジスタの内容をメモリにストアし、同時にベースレジスタ（ポインタとして使用されるレジスタ）を更新して、書き込みが行われた次のアドレスを指すようにします。これは、ループ内で連続的にメモリを操作する際に、ポインタを自動的にインクリメントするのに便利です。

### Duff's Device (`duffzero`)

Duff's Deviceは、C言語のプログラマであるTom Duffが考案した、ループアンローリング（loop unrolling）と`switch`文のフォールスルー（fall-through）を組み合わせた最適化手法です。これにより、ループのオーバーヘッドを削減し、高速なメモリコピーや初期化を実現できます。

Goランタイムでは、このDuff's Deviceの概念を応用して、`duffzero`というルーチンが実装されています。これは、大量のメモリ領域を効率的にゼロ初期化するためにアセンブリ言語で書かれたルーチンです。`duffzero`は、通常、`MOVDU`のような命令を内部で利用し、ポインタを効率的に進めながらメモリをゼロで埋めていきます。

### アセンブリ言語とポインタ操作

アセンブリ言語は、CPUが直接実行できる機械語に非常に近い低レベルのプログラミング言語です。Goランタイムのパフォーマンスが重要な部分は、しばしばアセンブリ言語で記述されます。アセンブリ言語では、メモリのアドレスを直接操作するためにポインタ（レジスタに格納されたアドレス）が頻繁に用いられます。メモリをゼロ初期化する際には、ポインタを適切なオフセットで進めながら、メモリの各ワードやバイトにゼロを書き込んでいきます。ポインタの更新が正しく行われないと、メモリ領域の一部がスキップされたり、同じ場所が何度も書き込まれたりする問題が発生します。

## 技術的詳細

このコミットが修正する問題は、`clearfat` 関数がPowerPC 64-bitアーキテクチャでメモリをゼロ初期化する際のポインタレジスタの不適切な更新に起因していました。`clearfat` は、ゼロ初期化するメモリ領域のサイズに応じて、主に以下の3つのケースで処理を分岐していました。

1.  **1032バイト以上の場合**: このケースでは、大きなブロックを効率的にゼロ初期化するために、`MOVDU`命令を直接使用したループが生成されます。
2.  **32バイト以上1032バイト未満の場合**: このケースでは、`duffzero`ルーチンが利用されます。`duffzero`も内部で`MOVDU`命令を多用して高速なゼロ初期化を行います。
3.  **32バイト未満の場合**: このケースでは、より小さな領域をバイト単位でゼロ初期化するループが使用されます。

問題は、上記1と2のケースで`MOVDU`命令（または`duffzero`経由での`MOVDU`）が使用された際に発生しました。`MOVDU`命令は、データをメモリに書き込んだ後、**ポインタレジスタを書き込みが行われたアドレスの次のアドレスではなく、書き込みが行われたアドレス自体（つまり、最後に書き込まれたダブルワードの開始アドレス）を指すように更新する**という特性を持っていました。

この挙動が問題でした。なぜなら、`clearfat`のコードは、`MOVDU`や`duffzero`によるダブルワード（8バイト）単位のゼロ初期化が完了した後、残りのバイト（8バイト未満の端数）をバイト単位でゼロ初期化するループに移行する際に、ポインタレジスタが「最後に書き込まれたダブルワードの**次の**アドレス」を指していると誤解していたためです。

結果として、バイト単位のゼロ初期化ループが開始されると、ポインタは既にゼロ初期化された最後のダブルワードの開始アドレスを指しているため、そのダブルワードが再度ゼロ初期化されるか、あるいはその後のバイトがスキップされてしまう「under-zeroing」が発生していました。つまり、本来ゼロにすべきメモリ領域の一部が、ゼロにされずに残ってしまう状態でした。

32バイト未満のケースでも同様の問題がありました。このケースでは、ポインタレジスタが全く更新されず、バイト単位のゼロ初期化ループが常に領域の先頭を再ゼロ初期化してしまうため、やはり「under-zeroing」が発生していました。

この修正は、これらの問題を解決するために、バイト単位のゼロ初期化ループを開始する前に、ポインタレジスタに適切なオフセット（8バイト、またはそれまでのゼロ初期化された総バイト数）を追加することで、ポインタが正しく未初期化の領域の先頭を指すように調整しています。これにより、すべてのメモリ領域が確実にゼロ初期化されるようになります。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の3つのファイルにわたります。

1.  **`src/cmd/9g/ggen.c`**: GoコンパイラのPowerPC 64-bitバックエンドにおける`clearfat`関数の実装。ここでゼロ初期化ロジックが修正されました。
    *   `uint64 w, c, q, t;` の行に `boff` (byte offset) 変数が追加されました。
    *   1032バイト以上のケースと32バイト以上のケースで、`boff = 8;` が追加されました。これは、`MOVDU`または`duffzero`がポインタを最後に書き込まれたダブルワードの開始アドレスに設定するため、バイト単位のゼロ初期化ループの開始位置を8バイト進める必要があることを示しています。
    *   32バイト未満のケースでは、ループの後に `boff = 8*q;` が追加されました。これは、ダブルワード単位のゼロ初期化が行われなかった場合でも、それまでに処理されたバイト数（`8*q`）をオフセットとして加算する必要があるためです。
    *   バイト単位のゼロ初期化ループ (`for(t = 0; t < c; t++)`) の中で、`p->to.offset = t;` が `p->to.offset = t+boff;` に変更されました。これにより、バイト単位のゼロ初期化が正しい開始位置から行われるようになります。

2.  **`src/runtime/asm_power64x.s`**: PowerPC 64-bitアーキテクチャ向けのアセンブリ言語ランタイムコード。
    *   `TEXT runtime·duffzero(SB), NOSPLIT, $-8-0` のコメントが修正されました。
        *   変更前: `// R3 is updated as a side effect.`
        *   変更後: `// On return, R3 points to the last zeroed dword.`
        このコメントの変更は、`duffzero`ルーチンがR3レジスタをどのように更新するかについての正確な説明を提供し、`ggen.c`での修正の根拠を明確にしています。

3.  **`test/clearfat.go`**: `clearfat`関数の修正を検証するための新しいテストファイル。
    *   このテストは、様々なサイズの構造体や配列をゼロ初期化し、その後にメモリ内容がすべてゼロになっていることを確認することで、`clearfat`の動作が正しいことを検証します。
    *   `poison`関数でスタック領域を`0xff`で埋め、`clearfat`がその領域をゼロクリアできるかをチェックします。
    *   `ntest`定数（1100）により、1バイトから1100バイトまでの様々なサイズのオブジェクトに対してテストが実行されます。

## コアとなるコードの解説

### `src/cmd/9g/ggen.c` の変更

`ggen.c`の`clearfat`関数は、Goコンパイラが生成するゼロ初期化コードのロジックを定義しています。

```c
void
clearfat(Node *nl)
{
	uint64 w, c, q, t, boff; // boff変数の追加
	Node dst, end, r0, *f;
	Prog *p, *pl;

    // ... (中略) ...

	if (q >= 128) { // 1032バイト以上 (128 * 8バイト = 1024バイト + α)
		// ... (MOVDUを直接使用したループ) ...
		regfree(&end);
		// The loop leaves R3 on the last zeroed dword
		boff = 8; // MOVDUが最後に書き込んだダブルワードの開始を指すため、8バイトのオフセットが必要
	} else if(q >= 4) { // 32バイト以上 (4 * 8バイト = 32バイト)
		// ... (duffzeroの呼び出し) ...
		// duffzero leaves R3 on the last zeroed dword
		boff = 8; // duffzeroも同様に最後に書き込んだダブルワードの開始を指すため、8バイトのオフセットが必要
	} else { // 32バイト未満
		for(t = 0; t < q; t++) {
			p = gins(AMOVD, &r0, &dst);
			p->to.type = D_OREG;
			p->to.offset = 8*t; // ダブルワード単位のゼロ初期化
		}
		boff = 8*q; // ダブルワード単位で処理された総バイト数をオフセットとする
	}

	for(t = 0; t < c; t++) { // 残りのバイトをゼロ初期化するループ
		p = gins(AMOVB, &r0, &dst);
		p->to.type = D_OREG;
		p->to.offset = t+boff; // ここでboffを加算し、正しい開始位置からバイト単位のゼロ初期化を行う
	}
	reg[REGRT1]--;
}
```

この変更の核心は、`boff` (byte offset) 変数の導入と、バイト単位のゼロ初期化ループにおけるオフセットの適用です。

*   `boff` は、ダブルワード単位のゼロ初期化（`MOVDU`または`duffzero`による）が完了した後に、ポインタが実際にどこを指しているか、そしてバイト単位のゼロ初期化をどこから開始すべきかを調整するためのオフセットを保持します。
*   `MOVDU`や`duffzero`がポインタを「最後に書き込まれたダブルワードの開始アドレス」に設定するという特性を考慮し、`boff`に`8`（1ダブルワードのサイズ）を設定することで、バイト単位のゼロ初期化がその次のアドレスから開始されるようにします。
*   32バイト未満のケースでは、ダブルワード単位のゼロ初期化がループで行われるため、`boff`は`8*q`（`q`はダブルワードの数）となり、これまでのゼロ初期化された総バイト数を表します。
*   最終的に、バイト単位のゼロ初期化ループでは、`p->to.offset = t+boff;` とすることで、`boff`によって計算された正しい開始位置から、残りのバイトが確実にゼロ初期化されるようにしています。

### `src/runtime/asm_power64x.s` の変更

`duffzero`ルーチンのコメント修正は、このルーチンがR3レジスタをどのように更新するかについての正確なドキュメントを提供します。

```assembly
// in ../../cmd/9g/ggen.c:/^clearfat.
// R0: always zero
// R3 (aka REGRT1): ptr to memory to be zeroed - 8
// On return, R3 points to the last zeroed dword. // 変更されたコメント
TEXT runtime·duffzero(SB), NOSPLIT, $-8-0
	MOVDU	R0, 8(R3)
	MOVDU	R0, 8(R3)
    // ... (duffzeroの本体) ...
```

このコメントは、`duffzero`が実行された後、R3レジスタが「最後にゼロ初期化されたダブルワードの開始アドレス」を指していることを明確にしています。この情報は、`ggen.c`で`boff`を計算する際の重要な前提となります。

### `test/clearfat.go` の追加

このテストファイルは、Goのテストフレームワークを利用して、`clearfat`関数の修正が正しく機能していることを検証します。

```go
package main

import (
	"bytes"
	"fmt"
	"strconv"
	"strings"
)

const ntest = 1100 // 1バイトから1100バイトまでテスト

func main() {
	var decls, calls bytes.Buffer

	for i := 1; i <= ntest; i++ {
		s := strconv.Itoa(i)
		decls.WriteString(strings.Replace(decl, "$", s, -1))
		calls.WriteString(strings.Replace("poison$()\n\tclearfat$()\n\t", "$", s, -1))
	}

	program = strings.Replace(program, "$DECLS", decls.String(), 1)
	program = strings.Replace(program, "$CALLS", calls.String(), 1)
	fmt.Print(program)
}

var program = `package main

var count int

$DECLS

func main() {
	$CALLS
	if count != 0 {
		println("failed", count, "case(s)")
	}
}
`

const decl = `
func poison$() {
	// Grow and poison the stack space that will be used by clearfat$
	var t [2*$]byte
	for i := range t {
		t[i] = 0xff // メモリを0xffで埋める（毒を入れる）
	}
}

func clearfat$() {
	var t [$]byte // clearfatによってゼロ初期化される変数

	for _, x := range t {
		if x != 0 { // ゼロ初期化されているかチェック
//			println("clearfat$: index", i, "expected 0, got", x)
			count++ // ゼロでなければカウントを増やす
			break
		}
	}
}
`
```

このテストは、Goの`go test`コマンドで実行されるように設計されています。

1.  `main`関数内で、`ntest`（1100）回ループし、各サイズ（1バイトから1100バイト）に対応する`poison`関数と`clearfat`関数の呼び出しを動的に生成します。
2.  `poison`関数は、`clearfat`が使用する予定のスタック領域を`0xff`（すべてのビットが1）で埋めます。これは、メモリがゼロ初期化されていない場合に、その「毒」が残っていることを検出するためのものです。
3.  `clearfat`関数（テスト対象）は、`var t [$]byte`という形で、指定されたサイズのバイト配列を宣言します。Goの仕様により、この配列はゼロ初期化されるはずです。
4.  その後のループで、`t`の各バイトが本当に`0`になっているかを確認します。もし`0`でなければ、`count`変数をインクリメントし、テストが失敗したことを示します。
5.  `main`関数は、すべてのテストケースが完了した後、`count`が`0`であることを確認します。`count`が`0`でなければ、ゼロ初期化が不完全であったことを意味し、テストは失敗します。

このテストは、`clearfat`関数が様々なサイズのメモリ領域を確実にゼロ初期化できることを、実際のGoコンパイラとランタイムの挙動を通じて検証する、非常に効果的な回帰テストとなっています。

# [インデックス 22176] ファイルの概要

このコミットは、GoランタイムのPlan 9オペレーティングシステムにおけるメモリ管理のバグ修正と改善に関するものです。具体的には、Plan 9環境でのメモリ解放の不備を解消し、より堅牢なメモリ割り当て・解放メカニズムを導入しています。

## コミット

このコミットは、GoランタイムのPlan 9向けメモリ管理コンポーネントを修正し、以前の不適切なメモリ解放の挙動を改善します。以前のシステムでは、最後に割り当てられたブロックしか適切に解放できませんでしたが、この変更により、コalescing（結合）とsplitting（分割）の機能を備えたKernighan & Ritchie (K&R) メモリ割り当てアルゴリズムのバリアントが導入されました。

主な変更点は以下の通りです。
- 割り当てられたブロックの先頭にヘッダーを付加しない。これは、`sysFree`呼び出し時に常にサイズが指定されるためです。
- フリーリストが循環リストではなく、nil終端リストになりました。

この変更は、以下のIssueを修正します: #9736, #9803, #9952。

## 変更の背景

GoランタイムのPlan 9向けメモリ割り当てメカニズムには、深刻な問題がありました。以前の実装では、`sysFree`関数が最後に割り当てられたメモリブロックしか適切に解放できないという制約がありました。これは、メモリリークやメモリの断片化を引き起こし、GoプログラムがPlan 9環境で安定して動作することを妨げる可能性がありました。特に、異なるサイズのブロックが頻繁に割り当てられ、解放されるようなシナリオでは、利用可能なメモリが枯渇しやすくなるという問題がありました。

この問題に対処するため、より汎用的で効率的なメモリ管理戦略が必要とされました。具体的には、解放されたメモリブロックを再利用し、隣接するフリーブロックを結合（coalescing）して大きなフリーブロックを形成する機能、そして要求されたサイズよりも大きなフリーブロックを分割（splitting）して効率的に利用する機能が求められました。

## 前提知識の解説

### Plan 9オペレーティングシステム

Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの概念をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルシステムとして表現するという哲学を持っています。メモリ管理においても、Unix系の`sbrk`のようなシステムコールを通じて、プロセスが自身のデータセグメントのサイズを増減させることでメモリを要求する方式が一般的です。Plan 9のメモリ管理は、Unixライクなシステムコールを介して行われることが多く、このコミットで修正される`sbrk`の利用はその典型です。

### Kernighan & Ritchie (K&R) メモリ割り当てアルゴリズム

KernighanとRitchieの著書「プログラミング言語C」で紹介されたメモリ割り当てアルゴリズムは、シンプルながらも効率的なフリーリストベースのメモリ管理手法です。基本的な考え方は以下の通りです。

1.  **フリーリスト**: 利用可能なメモリブロックを連結リスト（フリーリスト）として管理します。各ブロックは、そのサイズと次のフリーブロックへのポインタを持ちます。
2.  **割り当て (Allocation)**: メモリ要求があった場合、フリーリストを走査し、要求されたサイズ以上の最初のブロックを見つけます。
    *   **分割 (Splitting)**: 見つかったブロックが要求サイズよりも十分に大きい場合、そのブロックを要求サイズの部分と残りのフリー部分に分割します。要求サイズの部分を返し、残りのフリー部分をフリーリストに残します。
    *   **そのまま使用**: 見つかったブロックが要求サイズとほぼ同じ場合、そのブロック全体を返します。
3.  **解放 (Freeing)**: 解放されたメモリブロックは、フリーリストに挿入されます。
    *   **結合 (Coalescing)**: 解放されたブロックが、フリーリスト内の隣接するブロックと物理的に連続している場合、それらを結合してより大きな単一のフリーブロックを形成します。これにより、メモリの断片化を防ぎ、将来の大きな割り当て要求に対応しやすくなります。

K&Rアロケータは、そのシンプルさから多くのシステムでベースとして採用されていますが、実際のシステムではパフォーマンスや断片化対策のために様々な最適化が施されます。このコミットでは、GoランタイムのPlan 9向けにこのK&Rアロケータのバリアントを実装しています。

### `sbrk`システムコール

`sbrk`は、Unix系システムでプロセスのアドレス空間の「ブレーク」位置（データセグメントの末尾）を変更するために使用されるシステムコールです。`sbrk(increment)`を呼び出すと、ブレーク位置が`increment`バイトだけ増加し、その結果として新しいメモリ領域がプロセスに割り当てられます。`sbrk(0)`は現在のブレーク位置を返します。このコミットの以前の実装では、`sbrk`を直接使用してメモリを割り当て、解放時には`sbrk`を逆方向に呼び出すことで、最後に割り当てられたブロックのみを解放していました。

### Goの低レベルメモリ操作

*   **`unsafe.Pointer`**: Goの型システムをバイパスして、任意の型のポインタを表現できる特殊な型です。C言語の`void*`に似ており、低レベルのメモリ操作やシステムコールとの連携で利用されます。
*   **`uintptr`**: ポインタを保持できる整数型です。ポインタ演算を行う際に`unsafe.Pointer`と組み合わせて使用されます。
*   **`memclr(ptr, size)`**: 指定されたメモリ領域をゼロで埋めるGoランタイムの内部関数です。セキュリティや初期化のために使用されます。
*   **`add(ptr, offset)`**: `unsafe.Pointer`にオフセットを加算するGoランタイムの内部関数です。ポインタ演算を安全に行うために使用されます。
*   **`lock(&mutex)` / `unlock(&mutex)`**: ミューテックス（排他ロック）を使用して、共有リソースへのアクセスを同期するためのGoランタイムの内部関数です。メモリ割り当てのようなクリティカルセクションでは、競合状態を防ぐためにロックが必要です。
*   **`xadd64(ptr, delta)`**: アトミックに64ビット整数に値を加算するGoランタイムの内部関数です。統計情報の更新など、並行処理環境での安全なカウンタ操作に使用されます。
*   **`throw(message)`**: Goランタイムの内部関数で、致命的なエラーが発生した場合にプログラムを終了させます。

## 技術的詳細

このコミットは、`src/runtime/mem_plan9.go`ファイルに大幅な変更を加え、Plan 9環境におけるGoランタイムのメモリ割り当てと解放のロジックを根本的に改善しています。

### 新しいメモリ管理構造体 `memHdr`

```go
type memHdr struct {
	next *memHdr
	size uintptr
}
```
この構造体は、フリーリスト内の各メモリブロックのヘッダーとして機能します。
- `next`: フリーリスト内の次のフリーブロックへのポインタ。
- `size`: このフリーブロックのサイズ（バイト単位）。

### フリーリスト `memFreelist`

```go
var memFreelist *memHdr // sorted in ascending order
```
これは、利用可能なフリーメモリブロックを管理する単方向連結リストの先頭ポインタです。コメントにあるように、リストはアドレスの昇順にソートされます。これにより、隣接するブロックの結合（coalescing）が効率的に行えます。

### `memAlloc(n uintptr) unsafe.Pointer` 関数

この関数は、`n`バイトのメモリを割り当てるための新しいロジックを実装しています。
1.  `n = memRound(n)`: 要求されたサイズ`n`をページサイズ（`_PAGESIZE`）の倍数に丸めます。これは、OSからのメモリ割り当てがページ単位で行われるためです。
2.  フリーリストの走査: `memFreelist`を走査し、要求されたサイズ`n`以上のフリーブロックを探します。
    *   **完全一致**: `p.size == n`の場合、そのブロックをフリーリストから削除し、そのまま返します。
    *   **分割 (Splitting)**: `p.size > n`の場合、見つかったブロック`p`を`n`バイト分だけ縮小し、縮小されたブロックの末尾（元のブロックの`n`バイト目から）を新しい割り当て済みブロックとして返します。この際、`p`のサイズを`n`だけ減らし、返されるポインタ`p`を`add(unsafe.Pointer(p), p.size)`で計算し直しています。これは、ヘッダーを割り当て済みブロックの先頭に置かないという設計思想によるものです。
3.  **`sbrk`へのフォールバック**: フリーリストに適切なブロックが見つからない場合、`sbrk(n)`を呼び出してOSから新しいメモリを要求します。

### `memFree(ap unsafe.Pointer, n uintptr)` 関数

この関数は、`ap`で始まる`n`バイトのメモリブロックを解放し、フリーリストに戻します。
1.  `n = memRound(n)`: 解放されるサイズ`n`をページサイズに丸めます。
2.  `memclr(ap, n)`: 解放されるメモリ領域をゼロクリアします。これはセキュリティ上の理由やデバッグのために行われることがあります。
3.  `bp := (*memHdr)(ap)`: 解放されるブロックのポインタ`ap`を`memHdr`型にキャストし、`bp`とします。この`bp`が新しいフリーブロックのヘッダーとなります。
4.  `bp.size = n`: 新しいフリーブロックのサイズを設定します。
5.  **フリーリストへの挿入と結合 (Coalescing)**:
    *   **空のフリーリスト**: `memFreelist`が`nil`の場合、`bp`が唯一のフリーブロックとしてリストの先頭になります。
    *   **リストの先頭への挿入**: `bpn < uintptr(unsafe.Pointer(p))` (つまり、`bp`のアドレスが現在の`memFreelist`の先頭よりも小さい) 場合、`bp`を新しい先頭として挿入します。この際、`bp`が元の先頭ブロック`p`と隣接しているか（`bpn+bp.size == uintptr(unsafe.Pointer(p))`）をチェックし、隣接していれば結合します。
    *   **リストの中間または末尾への挿入**: フリーリストを走査し、`bp`を適切な位置に挿入します。挿入位置は、`bp`のアドレスが`p`のアドレスより大きく、かつ`p.next`のアドレスより小さい場所です。挿入後、`bp`が`p.next`と隣接しているか、または`p`が`bp`と隣接しているかをチェックし、隣接していれば結合します。

### `memCheck()` 関数

`memDebug`が`true`の場合にのみ実行されるデバッグ関数です。フリーリストの整合性をチェックします。
- 無限ループの検出 (`p == p.next`)
- リストの順序のチェック (`p > p.next`)
- ブロックの重複の検出 (`p + p.size > p.next`)
- 解放されたメモリがゼロクリアされているかのチェック

### `sysAlloc`, `sysFree`, `sysReserve` の変更

これらのGoランタイムのシステムコールラッパーは、新しい`memAlloc`と`memFree`関数を使用するように変更されました。
- `sysAlloc`: `sbrk`を直接呼び出す代わりに、`memAlloc`を呼び出すようになりました。ロックと`memCheck`の呼び出しも追加されています。
- `sysFree`: 以前の単純な`sbrk`ベースの解放ロジックが削除され、`memFree`を呼び出すようになりました。ロックと`memCheck`の呼び出しも追加されています。
- `sysReserve`: `sbrk`を直接呼び出す代わりに、`memAlloc`を呼び出すようになりました。ロックと`memCheck`の呼び出しも追加されています。

これにより、Plan 9におけるGoランタイムのメモリ管理が、より洗練されたK&Rベースのアロケータによって行われるようになり、メモリの再利用と断片化対策が強化されました。

## コアとなるコードの解説

このコミットの核心は、`memAlloc`と`memFree`関数によって実装されたK&Rスタイルのメモリ割り当て・解放アルゴリズムです。

### `memAlloc` の詳細な動作

`memAlloc`関数は、要求されたサイズ`n`に対して、フリーリスト`memFreelist`から最適なメモリブロックを見つけ、必要に応じて分割して返します。

1.  **サイズ調整**: `n = memRound(n)`により、要求サイズがページ境界にアラインされます。これは、OSがページ単位でメモリを管理するため、効率的な割り当てと解放のために重要です。
2.  **フリーリスト検索**: `for p := memFreelist; p != nil; p = p.next` ループでフリーリストを走査します。`prevp`は現在の`p`の前の要素を追跡し、リストからの削除や挿入を容易にします。
3.  **ブロックの適合**: `if p.size >= n` で、現在のフリーブロック`p`が要求サイズ`n`を満たすかチェックします。
    *   **完全一致 (`p.size == n`)**:
        *   この場合、ブロック`p`全体が割り当てられます。
        *   `prevp != nil` (つまり、`p`がフリーリストの先頭ではない) なら、`prevp.next = p.next` で`p`をリストから削除します。
        *   `prevp == nil` (つまり、`p`がフリーリストの先頭である) なら、`memFreelist = p.next` で`p`を新しい先頭に設定します。
    *   **部分一致（分割） (`p.size > n`)**:
        *   ブロック`p`は要求サイズ`n`よりも大きいので、分割されます。
        *   `p.size -= n` で、元のブロック`p`のサイズを`n`だけ減らします。これにより、`p`は残りのフリー部分を表すようになります。
        *   `p = (*memHdr)(add(unsafe.Pointer(p), p.size))` で、返されるポインタ`p`を計算します。これは、元のブロック`p`の末尾から`n`バイト分を切り出した部分の先頭アドレスを指します。このアドレスは、割り当てられたブロックの先頭であり、このコミットの設計思想である「割り当てられたブロックの先頭にヘッダーを置かない」に従っています。
        *   `memclr(unsafe.Pointer(p), unsafe.Sizeof(memHdr{}))` で、返されるメモリ領域の先頭（ただし、これは割り当てられたブロックの先頭であり、ヘッダーではない）をゼロクリアします。これは、デバッグやセキュリティのために行われる可能性があります。
4.  **`sbrk`へのフォールバック**: フリーリストに適切なブロックが見つからなかった場合、`sbrk(n)`を呼び出してOSから直接新しいメモリを要求します。これは、システムがより多くのメモリを必要としているか、フリーリストが断片化している場合に発生します。

### `memFree` の詳細な動作

`memFree`関数は、解放されたメモリブロック`ap`をフリーリストに挿入し、隣接するフリーブロックと結合（coalescing）します。

1.  **サイズ調整とゼロクリア**: `n = memRound(n)` でサイズを丸め、`memclr(ap, n)` でメモリ領域をゼロクリアします。
2.  **`memHdr`の準備**: `bp := (*memHdr)(ap)` で解放されたブロックの先頭を`memHdr`として扱います。`bp.size = n` でそのサイズを設定します。
3.  **フリーリストへの挿入**:
    *   **空のリスト**: `if memFreelist == nil` の場合、`bp`が唯一のフリーブロックとして`memFreelist`に設定されます。
    *   **リストの先頭への挿入**: `if bpn < uintptr(unsafe.Pointer(p))` (解放されるブロックのアドレスが現在のフリーリストの先頭ブロックのアドレスより小さい) の場合、`bp`を新しい先頭として挿入します。
        *   **先頭ブロックとの結合**: `if bpn+bp.size == uintptr(unsafe.Pointer(p))` (解放されるブロックが元の先頭ブロックと物理的に隣接している) の場合、両者を結合し、`bp`のサイズを増やし、`bp.next`を元の先頭ブロックの次の要素に設定します。
        *   **結合なし**: 隣接していない場合、`bp.next = p` で`bp`を先頭に挿入します。
    *   **リストの中間または末尾への挿入**: `for ; p.next != nil; p = p.next` ループで、`bp`を挿入すべき適切な位置（`p`と`p.next`の間）を探します。
        *   **`bp`と`p.next`の結合**: `if bpn+bp.size == uintptr(unsafe.Pointer(p.next))` (解放されるブロックが`p.next`と隣接している) の場合、両者を結合し、`bp`のサイズを増やし、`bp.next`を`p.next.next`に設定します。
        *   **`p`と`bp`の結合**: `if uintptr(unsafe.Pointer(p))+p.size == bpn` (現在のブロック`p`が解放されるブロック`bp`と隣接している) の場合、両者を結合し、`p`のサイズを増やし、`p.next`を`bp.next`に設定します。
        *   **結合なし**: どちらとも隣接していない場合、`bp.next = p.next` と `p.next = bp` で`bp`を`p`の次に挿入します。

この結合ロジックにより、メモリの断片化が抑制され、大きな連続したメモリブロックが再利用可能になります。

## 元コミット内容

このコミットは、Go言語の標準ライブラリである`crypto/tls`パッケージにおける変更です。主な目的は、TLSハンドシェイク中に発生するデジタル署名と暗号文の復号操作を、具体的な鍵の実装（例: `*ecdsa.PrivateKey`や`*rsa.PrivateKey`）に直接依存するのではなく、`crypto.Signer`および`crypto.Decrypter`という抽象的なインターフェースを介して行うように修正することです。

これは、以前のコミット `https://go-review.googlesource.com/#/c/3900/` の後続作業として位置づけられています。その先行コミットでは、`crypto.Decrypter`インターフェースが導入され、RSA鍵に対してその実装が提供されました。今回のコミットは、そのインターフェースを実際に`crypto/tls`パッケージ内で活用し、さらに`crypto.Signer`インターフェースも同様に利用することで、鍵操作の抽象化をより一層進めるものです。

## 変更の背景

この変更の背景には、Go言語の暗号ライブラリにおけるセキュリティと柔軟性の向上が挙げられます。従来のGoの暗号操作では、秘密鍵が特定の構造体（例: `*rsa.PrivateKey`, `*ecdsa.PrivateKey`）としてメモリ上に存在することを前提としていました。しかし、現実のシステムでは、秘密鍵はハードウェアセキュリティモジュール（HSM）やクラウドの鍵管理サービス（KMS）など、よりセキュアな環境に格納され、直接アクセスできない場合があります。

`crypto.Signer`と`crypto.Decrypter`インターフェースの導入は、このような外部の鍵管理システムとの連携を容易にし、秘密鍵の実装詳細を抽象化することを目的としています。これにより、アプリケーションは秘密鍵がどこに、どのように格納されているかを意識することなく、署名や復号といった暗号操作を実行できるようになります。

先行コミット `https://go-review.googlesource.com/#/c/3900/` で`crypto.Decrypter`が導入され、RSA鍵の復号に利用可能になりました。今回のコミットは、そのインターフェースを`crypto/tls`に適用し、さらに署名操作についても`crypto.Signer`インターフェースを導入・適用することで、TLSハンドシェイク全体における鍵操作の抽象化を完成させるものです。これにより、TLSサーバーがHSMに格納された鍵を使用するようなシナリオが、より容易に実現できるようになります。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上でデータを安全にやり取りするための暗号化プロトコルです。ウェブサイトのHTTPS通信などで広く利用されています。TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行う一連のネゴシエーションプロセスです。このプロセスには、サーバー認証、鍵交換、暗号スイートの選択などが含まれます。

### デジタル署名

デジタル署名は、メッセージの送信者の身元を証明し、メッセージが改ざんされていないことを保証するための技術です。送信者は秘密鍵でメッセージのハッシュ値を署名し、受信者は公開鍵でその署名を検証します。TLSハンドシェイクでは、サーバーが自身の身元を証明するためにデジタル署名を使用します。

### 非対称暗号（公開鍵暗号）

公開鍵暗号は、公開鍵と秘密鍵のペアを使用する暗号方式です。公開鍵は誰でも利用できますが、秘密鍵は所有者のみが保持します。
- **暗号化**: 公開鍵で暗号化されたデータは、対応する秘密鍵でのみ復号できます。
- **デジタル署名**: 秘密鍵で署名されたデータは、対応する公開鍵で検証できます。

### RSA (Rivest–Shamir–Adleman)

RSAは、最も広く使用されている公開鍵暗号アルゴリズムの一つです。暗号化、デジタル署名、鍵交換などに利用されます。

### ECDSA (Elliptic Curve Digital Signature Algorithm)

ECDSAは、楕円曲線暗号に基づくデジタル署名アルゴリズムです。RSAと比較して、同等のセキュリティレベルをより短い鍵長で実現できるため、効率的です。

### `crypto.Signer`インターフェース

Go言語の`crypto`パッケージで定義されているインターフェースで、デジタル署名操作を行うための抽象化を提供します。
```go
type Signer interface {
    // Public returns the public key corresponding to the opaque private key.
    Public() PublicKey

    // Sign signs digest with the private key, possibly using randomness from rand.
    // The opts argument is optional and contains options for the signing operation.
    Sign(rand io.Reader, digest []byte, opts SignerOpts) (signature []byte, err error)
}
```
このインターフェースを実装することで、実際の秘密鍵がメモリ上に直接存在しなくても（例: HSM内にある場合）、署名操作を実行できるようになります。`*rsa.PrivateKey`や`*ecdsa.PrivateKey`は、この`Signer`インターフェースを実装しています。

### `crypto.Decrypter`インターフェース

Go言語の`crypto`パッケージで定義されているインターフェースで、非対称暗号の復号操作を行うための抽象化を提供します。
```go
type Decrypter interface {
    // Public returns the public key corresponding to the opaque private key.
    Public() PublicKey

    // Decrypt decrypts ciphertext with the private key.
    // The opts argument is optional and contains options for the decryption operation.
    Decrypt(rand io.Reader, msg []byte, opts DecrypterOpts) (plaintext []byte, err error)
}
```
このインターフェースを実装することで、秘密鍵が直接アクセスできない環境でも復号操作を実行できるようになります。`*rsa.PrivateKey`は、この`Decrypter`インターフェースを実装しています。

## 技術的詳細

このコミットの技術的詳細は、`crypto/tls`パッケージ内のサーバーサイドハンドシェイクロジックと鍵交換ロジックにおける、秘密鍵の利用方法の変更に集約されます。

1.  **`crypto/tls/common.go`の`Certificate`構造体**:
    `PrivateKey`フィールドのコメントが更新され、サーバー側の鍵が`crypto.Decrypter`または`crypto.Signer`インターフェースを実装する必要があることが明記されました。これにより、より抽象的なインターフェースの使用が推奨されます。

2.  **`crypto/tls/handshake_server.go`の`serverHandshakeState`構造体**:
    -   `rsaOk`, `signOk`, `decryptOk`という新しいブール型フィールドが追加されました。これらは、サーバーの秘密鍵がそれぞれRSA鍵、`crypto.Signer`インターフェース、`crypto.Decrypter`インターフェースをサポートしているかどうかを示すフラグです。
    -   ハンドシェイクの初期化段階で、`hs.cert.PrivateKey`が`crypto.Signer`または`crypto.Decrypter`インターフェースを実装しているかどうかがチェックされ、対応する`signOk`や`decryptOk`フラグが設定されます。また、`Public()`メソッドから取得できる公開鍵の型（ECDSAまたはRSA）に基づいて、`ecdsaOk`や`rsaOk`フラグも更新されます。これにより、ハンドシェイクの早い段階で、利用可能な鍵操作の能力が判別されます。

3.  **`crypto/tls/handshake_server.go`の`setCipherSuite`関数（旧`tryCipherSuite`）**:
    -   関数名が`tryCipherSuite`から`setCipherSuite`に変更され、`*Conn`のメソッドから`*serverHandshakeState`のメソッドに変更されました。これにより、ハンドシェイクの状態に直接アクセスできるようになりました。
    -   引数から`ellipticOk`と`ecdsaOk`が削除され、代わりに`serverHandshakeState`の新しいフラグ（`hs.ellipticOk`, `hs.signOk`, `hs.ecdsaOk`, `hs.rsaOk`, `hs.decryptOk`）が利用されるようになりました。
    -   暗号スイートの選択ロジックが更新され、選択された暗号スイートがECDHE（Elliptic Curve Diffie-Hellman Ephemeral）ベースである場合、`hs.ellipticOk`と`hs.signOk`が真であることを確認します。さらに、ECDSAベースのECDHEスイートの場合は`hs.ecdsaOk`が、RSAベースのECDHEスイートの場合は`hs.rsaOk`が真であることを確認します。
    -   非ECDHE（つまりRSA鍵交換）の暗号スイートの場合、`hs.decryptOk`と`hs.rsaOk`が真であることを確認します。これは、クライアントから送られてくるPre-Master Secretを復号するために、サーバーのRSA秘密鍵が`crypto.Decrypter`インターフェースを実装している必要があるためです。
    -   これにより、選択された暗号スイートが、サーバーが持つ秘密鍵の能力と正確に一致しているかどうかが、より厳密にチェックされるようになりました。

4.  **`crypto/tls/key_agreement.go`の鍵交換ロジック**:
    -   **RSA鍵交換の復号**: `rsaKeyAgreement.processClientKeyExchange`関数において、クライアントから送られてきた暗号化されたPre-Master Secretの復号に、`cert.PrivateKey.(*rsa.PrivateKey)`への直接キャストではなく、`cert.PrivateKey.(crypto.Decrypter)`インターフェースが利用されるようになりました。具体的には、`priv.Decrypt(config.rand(), ciphertext, &rsa.PKCS1v15DecryptOptions{SessionKeyLen: 48})`が呼び出されます。これにより、秘密鍵がHSMなどに格納されている場合でも、復号操作が可能になります。
    -   **ECDHE鍵交換の署名**: `ecdheKeyAgreement.generateServerKeyExchange`関数において、サーバー鍵交換メッセージの署名に、`cert.PrivateKey.(*ecdsa.PrivateKey)`や`cert.PrivateKey.(*rsa.PrivateKey)`への直接キャストではなく、`cert.PrivateKey.(crypto.Signer)`インターフェースが利用されるようになりました。具体的には、`priv.Sign(config.rand(), digest, hashFunc)`が呼び出されます。これにより、署名操作も抽象化され、鍵の実装詳細に依存しなくなります。

これらの変更により、`crypto/tls`パッケージは、秘密鍵の具体的な実装に直接依存することなく、`crypto.Signer`と`crypto.Decrypter`インターフェースを介して暗号操作を実行できるようになり、鍵管理の柔軟性とセキュリティが大幅に向上しました。

## コアとなるコードの解説

### `src/crypto/tls/common.go`

-   `Certificate`構造体の`PrivateKey`フィールドのコメントが更新されました。これは、サーバーの秘密鍵が`crypto.Decrypter`または`crypto.Signer`インターフェースを実装する必要があることを明確に示しています。これにより、コードの意図がより明確になり、将来的な拡張性も考慮されています。

-   `serverHandshakeState`構造体に`rsaOk`, `signOk`, `decryptOk`という新しいフラグが追加されました。これらは、ハンドシェイクの初期段階で、サーバーの秘密鍵がどの暗号操作（RSA、署名、復号）をサポートしているかを効率的に判断するために使用されます。
-   `hs.cert.PrivateKey`が`crypto.Signer`または`crypto.Decrypter`インターフェースを実装しているかどうかの型アサーションが追加されました。これにより、秘密鍵がこれらのインターフェースをサポートしている場合、対応するフラグが設定されます。また、`Public()`メソッドから取得した公開鍵の型に基づいて、`ecdsaOk`や`rsaOk`も適切に設定されます。これにより、具体的な鍵タイプに依存せず、インターフェースの能力に基づいて処理を分岐できるようになります。
-   `tryCipherSuite`関数が`setCipherSuite`に改名され、`*Conn`のメソッドから`*serverHandshakeState`のメソッドに変更されました。これにより、関数がハンドシェイクの状態に直接アクセスできるようになり、引数の数を減らすことができます。
-   `setCipherSuite`関数内の暗号スイート選択ロジックが大幅に修正されました。以前は`ellipticOk`と`ecdsaOk`というブール値に直接依存していましたが、変更後は`hs.ellipticOk`, `hs.signOk`, `hs.ecdsaOk`, `hs.rsaOk`, `hs.decryptOk`といった`serverHandshakeState`の新しいフラグを組み合わせて、より詳細かつ柔軟なチェックを行うようになりました。これにより、選択された暗号スイートが、サーバーの秘密鍵が提供する実際の暗号機能と正確に一致していることを保証します。特に、ECDHEスイートの場合は署名能力（`signOk`）と鍵タイプ（`ecdsaOk`または`rsaOk`）を、非ECDHE（RSA鍵交換）スイートの場合は復号能力（`decryptOk`）とRSA鍵タイプ（`rsaOk`）を厳密にチェックします。

### `src/crypto/tls/key_agreement.go`

-   `rsaKeyAgreement.processClientKeyExchange`関数において、クライアントから送られてきたPre-Master Secretの復号処理が変更されました。以前は`cert.PrivateKey.(*rsa.PrivateKey)`と直接型アサーションしていましたが、新しいコードでは`cert.PrivateKey.(crypto.Decrypter)`インターフェースを使用します。これにより、`Decrypt`メソッドを呼び出すことで、秘密鍵の実装詳細を隠蔽しつつ復号操作を実行できます。
-   `ecdheKeyAgreement.generateServerKeyExchange`関数において、サーバー鍵交換メッセージの署名処理が変更されました。以前は`cert.PrivateKey.(*ecdsa.PrivateKey)`や`cert.PrivateKey.(*rsa.PrivateKey)`と直接型アサーションしていましたが、新しいコードでは`cert.PrivateKey.(crypto.Signer)`インターフェースを使用します。これにより、`Sign`メソッドを呼び出すことで、秘密鍵の実装詳細を隠蔽しつつ署名操作を実行できます。また、ECDSA署名の場合の`asn1.Marshal`によるエンコードも`crypto.Signer`の`Sign`メソッド内で処理されるため、コードが簡潔になりました。

これらの変更は、GoのTLS実装が、より抽象的な暗号インターフェースを活用することで、鍵管理の柔軟性を高め、HSMなどの外部デバイスとの連携を容易にするための重要なステップです。

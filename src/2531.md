## 変更の背景

このコミットは2009年、Go言語がまだ活発に開発されていた初期段階に行われました。当時のGoのパッケージ管理は主に `GOPATH` 環境変数に依存しており、モジュールシステムはまだ存在していませんでした（Goモジュールは2018年のGo 1.11で導入）。

初期のGoでは、パッケージのインポートパスの解決において、ローカルディレクトリ内のパッケージと、GOPATH内の他の場所にあるパッケージ、あるいは標準ライブラリのパッケージとの間で曖昧さが発生する可能性がありました。例えば、`import "file"` のような記述があった場合、それが現在のディレクトリにある `file` パッケージを指すのか、それともGOPATH内のどこかにある `file` パッケージを指すのか、あるいは標準ライブラリの `file` パッケージ（もし存在すれば）を指すのかが、ツールチェインにとって常に明確ではありませんでした。

この曖昧さを解消し、ローカルパッケージへのインポートを明示的にするために、Russ Cox氏はこのコミットで `./` プレフィックスの導入を行いました。`import "./file"` と記述することで、コンパイラやビルドツールは「現在のディレクトリ（またはそのサブディレクトリ）にある `file` パッケージをインポートする」という意図を明確に理解できるようになります。これにより、ビルドの堅牢性が向上し、予期せぬパッケージの解決ミスを防ぐことが目的でした。

## 前提知識の解説

### Goのパッケージとインポートシステム

Go言語は、コードをパッケージという単位で整理します。パッケージは関連する機能の集合であり、再利用可能なコードの基本単位です。他のパッケージの機能を利用するには、`import` ステートメントを使用してそのパッケージをインポートする必要があります。

Goのインポートパスは、大きく分けて以下の2種類があります。

1.  **標準ライブラリパッケージ**: Goのインストールに含まれる組み込みパッケージ（例: `"fmt"`, `"os"`, `"net/http"`）。これらは通常、パッケージ名のみでインポートされます。
2.  **外部パッケージ/ローカルパッケージ**: ユーザーが作成したパッケージや、サードパーティ製のパッケージ。これらは通常、GOPATH（Go 1.11以前）またはGoモジュール（Go 1.11以降）の規則に従って解決されます。

### GOPATH (Go 1.11以前のパッケージ管理)

このコミットが行われた2009年当時、Goのパッケージ管理は `GOPATH` 環境変数に大きく依存していました。`GOPATH` は、Goのワークスペースのルートディレクトリを指定し、その中に `src`、`pkg`、`bin` の3つのサブディレクトリを持つことが一般的でした。

*   `$GOPATH/src`: すべてのGoソースコードがここに配置されます。プロジェクトやパッケージは、このディレクトリからの相対パスで管理されます。
*   `$GOPATH/pkg`: コンパイル済みのパッケージオブジェクトが保存されます。
*   `$GOPATH/bin`: コンパイル済みの実行可能ファイルが保存されます。

パッケージをインポートする際、Goツールチェインは `$GOPATH/src` からの相対パスでパッケージを探します。例えば、`$GOPATH/src/github.com/user/repo/mypackage` にあるパッケージは `import "github.com/user/repo/mypackage"` としてインポートされました。

### 相対インポートと絶対インポート

*   **絶対インポート**: `import "fmt"` や `import "github.com/user/repo/mypackage"` のように、GOPATHのルートからの完全なパス、または標準ライブラリのパッケージ名で指定する形式です。これはGoの推奨されるインポート方法であり、パッケージの場所が一意に定まります。
*   **相対インポート**: `import "./mypackage"` のように、現在のファイルからの相対パスでパッケージを指定する形式です。このコミット以前は、`import "mypackage"` のように `./` なしでローカルパッケージをインポートできるケースがあったと考えられますが、このコミットによって `./` を明示することが求められるようになりました。Go 1.0以降、相対インポートは非推奨となり、Goモジュール時代にはほとんど使われなくなりましたが、このコミット当時はまだその過渡期にありました。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムとコンパイラが、インポートパスをどのように解釈するかという点にあります。

### `./` の導入がインポート解決に与える影響

`import "./package_name"` という形式は、Goツールチェインに対して「現在のソースファイルが存在するディレクトリ、またはそのサブディレクトリにある `package_name` というパッケージを探しなさい」という明確な指示を与えます。

この変更以前は、`import "package_name"` と書かれた場合、Goツールチェインは以下の順序でパッケージを探索していた可能性があります（正確な探索順序は当時の実装に依存しますが、一般的なパターンとして）：

1.  標準ライブラリのパッケージ
2.  GOPATH内のパッケージ
3.  現在のディレクトリ内のパッケージ

この探索順序では、もし標準ライブラリやGOPATH内に現在のディレクトリ内のパッケージと同じ名前のパッケージが存在した場合、意図しないパッケージがインポートされてしまう「名前の衝突」が発生するリスクがありました。

`./` を明示的に追加することで、この探索順序における曖昧さが解消されます。`./` が付いている場合は、まず現在のディレクトリからの相対パスでパッケージを探索し、それ以外の場合は標準ライブラリやGOPATHからの探索を行う、といった明確なルールを確立できます。これにより、開発者はローカルパッケージへの参照を意図的に行っていることをコード上で表現できるようになり、ビルドシステムもその意図を正確に解釈できるようになります。

### `.` ではなく `./` なのか

Go言語の設計思想として、明示性と簡潔さのバランスが重視されます。`import "."` は、現在のパッケージのシンボルを修飾なしで直接利用できるようにする特殊なインポートですが、これは通常、テストコードなどで限定的に使用されます。一般的なパッケージのインポートでは、パッケージ名をプレフィックスとして使用することで、どのパッケージのどのシンボルを使っているのかを明確にするのがGoの慣習です。

`./` は、現在のディレクトリからの相対パスを示す標準的なファイルシステム表記であり、これをインポートパスに適用することで、ローカルファイルシステム上のパッケージを参照していることを直感的に理解できます。これは、Goのインポートパスがファイルシステム上のパスと密接に関連しているという設計原則とも一致します。

### `gobuild` コマンドへの影響

コミットの差分には `src/cmd/gobuild/` 以下のファイルが含まれています。`gobuild` は、Goの初期のビルドツールの一つであり、現在の `go build` コマンドの前身のような役割を担っていたと考えられます。

`gobuild` 関連のファイル (`gobuild.go`, `main.go`, `makefile.go`) の変更は、`gobuild` 自身が他の `gobuild` パッケージ（おそらく内部ヘルパーパッケージ）をインポートする際に、`import "gobuild"` から `import "./gobuild"` へと修正されていることを示しています。これは、`gobuild` ツール自身が、この新しいインポートルールに従うように更新されたことを意味します。つまり、この変更はGoのツールチェインの内部にも適用され、一貫したインポート解決の挙動を保証しようとしていたことが伺えます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、Goソースコード内の `import` ステートメントにおいて、ローカルパッケージへの参照に `./` プレフィックスを追加する点です。

具体的な変更パターンは以下の通りです。

```diff
--- a/path/to/file.go
+++ b/path/to/file.go
@@ -X,Y +X,Y @@
 package main
 
 import (
-	"package_name";
+	"./package_name";
 	// ...
 )
```

いくつかのファイルでは、`import "package_name"` が `import "./package_name"` に変更されています。

例:

*   `doc/progs/cat.go`: `import "file"` が `import "./file"` に変更。
*   `src/cmd/gobuild/gobuild.go`: `import "gobuild"` が `import "./gobuild"` に変更。
*   `test/fixedbugs/bug083.dir/bug1.go`: `import "bug0"` が `import "./bug0"` に変更。

また、`src/cmd/gobuild/main.go` では、単一のインポートステートメントが簡潔な形式に変更されています。

```diff
--- a/src/cmd/gobuild/main.go
+++ b/src/cmd/gobuild/main.go
@@ -4,9 +4,7 @@
 
 package main
 
-import (
-	"gobuild";
-)
+import "./gobuild";
 
 func main() {
 	gobuild.Main();
```

これは、`import` ブロックから単一行の `import "./gobuild";` へと変更されたもので、機能的な変更というよりはコードスタイルの調整ですが、ここでも `./` が追加されている点が重要です。

## コアとなるコードの解説

変更された各ファイルは、Goのプログラム、テストケース、またはビルドツールの一部です。これらのファイルは、それぞれが依存するローカルパッケージをインポートしていました。

例えば、`doc/progs/cat.go` は `file` パッケージをインポートしています。この `file` パッケージは、おそらく `doc/progs/` ディレクトリ内、またはそのサブディレクトリに存在していたと考えられます。変更前は `import "file"` と記述されていましたが、このコミットにより `import "./file"` と修正されました。これにより、`cat.go` が現在のディレクトリにある `file` パッケージを明示的に参照していることが明確になります。

同様に、`src/cmd/gobuild/gobuild.go` や `src/cmd/gobuild/makefile.go` が `gobuild` パッケージをインポートする際も、`import "gobuild"` から `import "./gobuild"` へと変更されています。これは、`gobuild` コマンド自体が、自身の内部で定義されたヘルパーパッケージをインポートする際に、この新しいルールに従うように修正されたことを示しています。これにより、`gobuild` のビルドプロセスがより堅牢になり、内部パッケージの解決が意図通りに行われるようになります。

`test/fixedbugs/` ディレクトリ内のテストケースも同様に修正されています。これらのテストは、特定のバグを再現するために作成されたものであり、ローカルに定義された `bug0` や `bug1` といったパッケージをインポートしています。これらのインポートパスに `./` を追加することで、テストの意図が明確になり、Goツールチェインがテスト対象のローカルパッケージを正しく解決できるようになります。

この変更は、Go言語の初期段階におけるパッケージインポートのセマンティクスを確立し、ローカルパッケージの参照方法を標準化する上で重要な一歩でした。これにより、開発者はより予測可能で堅牢なビルドプロセスを享受できるようになりました。

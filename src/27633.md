# [インデックス 27633] ファイルの概要

このコミットは、Go言語の `reflect` パッケージに s390x アーキテクチャのサポートを追加するものです。具体的には、`reflect.MakeFunc` および `reflect.Value.Call` の内部実装に必要なアセンブリコードを s390x 向けに提供します。これにより、s390x 環境で Go のリフレクション機能が正しく動作するようになります。

## コミット

`reflect` パッケージに s390x (IBM Z および LinuxONE プロセッサ) のサポートを追加します。これは、`makeFuncStub` と `methodValueCall` という2つの重要なアセンブリ関数を `src/reflect/asm_s390x.s` ファイルに実装することで実現されます。これらの関数は、Go のリフレクションメカニズムにおいて、動的に生成された関数やメソッドの呼び出しを処理するために不可欠です。

## 変更の背景

Go言語はクロスプラットフォーム対応を重視しており、様々なCPUアーキテクチャ上で動作するように設計されています。s390x は IBM のメインフレームコンピュータで使用される64ビットアーキテクチャであり、エンタープライズ環境で重要な役割を担っています。Go の `reflect` パッケージは、実行時に型情報を検査したり、動的に関数を呼び出したり、構造体のフィールドにアクセスしたりする強力な機能を提供します。

しかし、`reflect` パッケージの特定の機能、特に `reflect.MakeFunc` (任意の関数シグネチャを持つ新しい関数を動的に作成する) や `reflect.Value.Call` (リフレクションを通じて関数やメソッドを呼び出す) は、低レベルのアセンブリコードに依存しています。これは、Go のランタイムが、異なる呼び出し規約やスタックフレームの管理方法を持つ様々なアーキテクチャ上で、動的に生成されたコードと Go の通常のコードの間で引数や戻り値を正しく受け渡しする必要があるためです。

このコミット以前は、s390x アーキテクチャではこれらのリフレクション機能が完全にサポートされていなかった可能性があります。このコミットは、s390x 上で Go のリフレクション機能が期待通りに動作するための基盤となるアセンブリコードを提供し、s390x 環境での Go の実用性を向上させることを目的としています。

## 前提知識の解説

### Go言語のリフレクション (reflectパッケージ)

Go の `reflect` パッケージは、プログラムが自身の構造を検査し、実行時に値を操作する能力を提供します。主な機能は以下の通りです。
*   **型の検査**: `reflect.TypeOf` を使用して変数の動的な型情報を取得できます。
*   **値の操作**: `reflect.ValueOf` を使用して変数の動的な値を取得し、その値を操作できます。
*   **動的な関数呼び出し**: `reflect.Value.Call` を使用して、実行時に任意の関数やメソッドを呼び出すことができます。これは、引数の型や数が事前に分からない場合に特に有用です。
*   **動的な関数生成**: `reflect.MakeFunc` を使用して、指定された関数シグネチャを持つ新しい関数を動的に作成し、その関数が呼び出されたときに特定の処理を実行させることができます。

これらの動的な関数呼び出しや生成のメカニズムは、Go のコンパイラが生成する静的な関数呼び出しとは異なり、実行時に引数の型変換やスタックフレームの調整を行う必要があります。このため、各アーキテクチャ固有のアセンブリコードが必要となります。

### s390x アーキテクチャ

s390x は、IBM のメインフレームコンピュータ (IBM Z および LinuxONE) で使用される64ビット命令セットアーキテクチャです。特徴としては、以下の点が挙げられます。
*   **レジスタ**: 汎用レジスタ (R0-R15) や浮動小数点レジスタなどがあります。
*   **呼び出し規約**: 関数呼び出し時の引数の渡し方や戻り値の受け取り方、スタックフレームの管理方法などが定義されています。これは他のアーキテクチャ (x86-64, ARM64など) とは異なります。
*   **システムプログラミング**: メインフレーム環境での高い信頼性、可用性、セキュリティをサポートするための特殊な命令や機能が含まれています。

Go のランタイムは、これらのアーキテクチャ固有の特性を考慮して、アセンブリコードを記述する必要があります。

### Goのアセンブリ言語

Go は、Go言語自体で書かれたコードと、Go のアセンブリ言語で書かれたコードを組み合わせることができます。Go のアセンブリ言語は、Plan 9 アセンブラの文法に基づいており、一般的なアセンブリ言語とは異なる独自の記法を持ちます。
*   `TEXT` ディレクティブ: 関数の定義に使用されます。`TEXT ·makeFuncStub(SB),(NOSPLIT|WRAPPER),$16` のように記述され、関数名、シンボルベース (SB)、フラグ (NOSPLIT, WRAPPER)、スタックフレームサイズなどを指定します。
*   `MOVD`: 64ビットデータを移動する命令 (s390x の場合)。
*   `BL`: 分岐してリンクする命令 (関数呼び出し)。
*   `RET`: 関数から戻る命令。
*   `R0-R15`: s390x の汎用レジスタ。
*   `FP`: フレームポインタ。
*   `SB`: 静的ベースポインタ。

## 技術的詳細

このコミットで追加された `src/reflect/asm_s390x.s` ファイルは、s390x アーキテクチャにおける `reflect` パッケージの低レベルな動作を定義します。特に、`reflect.MakeFunc` と `reflect.Value.Call` が内部的に使用する2つのアセンブリ関数 `makeFuncStub` と `methodValueCall` を実装しています。

これらの関数は、Go のランタイムが動的に生成した関数やメソッドを呼び出す際に、以下の役割を担います。

1.  **引数の準備**: Go のリフレクションは、引数を `[]reflect.Value` のスライスとして受け取ります。しかし、実際に関数を呼び出す際には、これらの値をターゲット関数の呼び出し規約に従ってレジスタやスタックに配置する必要があります。アセンブリスタブは、この変換処理の一部を担います。
2.  **ランタイムへのコールバック**: アセンブリスタブは、引数を準備した後、Go のランタイム内のヘルパー関数 (`callReflect` や `callMethod`) を呼び出します。これらのヘルパー関数は、`reflect.Value` から実際の引数値を抽出し、ターゲット関数を呼び出し、戻り値を `reflect.Value` にラップし直す役割を担います。
3.  **スタックフレームの管理**: 関数呼び出し時には、新しいスタックフレームが設定され、戻り時には元のスタックフレームに戻る必要があります。アセンブリコードは、このスタックフレームのセットアップとクリーンアップを適切に行います。

s390x の呼び出し規約では、引数は通常レジスタ (R2-R6) やスタックに渡されます。戻り値もレジスタ (R2) で返されます。`makeFuncStub` と `methodValueCall` は、これらの規約に従って、`reflect` パッケージが提供する汎用的な引数フレーム (`argframe`) からデータを抽出し、ランタイムのヘルパー関数に渡すための橋渡しをします。

`$16` は、これらのスタブ関数が使用するスタックフレームのサイズを示しています。`NOSPLIT` は、この関数がスタックを分割しないことを示し、`WRAPPER` は、この関数が他の関数をラップする目的で使用されることを示します。`NO_LOCAL_POINTERS` は、この関数がローカルポインタを持たないことを示し、ガベージコレクタの負担を軽減します。

#include "textflag.h"

// makeFuncStub は MakeFunc によって返される関数のコード部分です。

	RET

## コアとなるコードの解説

このアセンブリコードは、s390x アーキテクチャにおける Go のリフレクション機能の心臓部を構成します。

### `makeFuncStub`

*   `TEXT ·makeFuncStub(SB),(NOSPLIT|WRAPPER),$16`: `makeFuncStub` という名前の関数を定義します。`SB` はシンボルベース、`NOSPLIT` はスタックを分割しないことを示し、`WRAPPER` は他の関数をラップする目的であることを示します。`$16` はこの関数が使用するスタックフレームのサイズが16バイトであることを意味します。
*   `NO_LOCAL_POINTERS`: この関数がローカルポインタを持たないことをガベージコレクタに伝えます。
*   `MOVD R12, 8(R15)`: レジスタ `R12` の内容を、`R15` (スタックポインタ) から8バイトオフセットしたメモリ位置に格納します。`R12` は通常、Go の関数呼び出し規約において、`g` (現在のゴルーチン構造体へのポインタ) を保持するために使用されます。この操作は、`callReflect` が `g` ポインタにアクセスできるように、スタックフレームに保存している可能性があります。
*   `MOVD $argframe+0(FP), R3`: `argframe` のアドレスをレジスタ `R3` にロードします。`argframe` は、`reflect` パッケージが動的に呼び出す関数の引数を格納するために使用するメモリ領域です。`FP` はフレームポインタであり、現在のスタックフレームの基準点となります。`R3` は s390x の呼び出し規約で最初の引数を渡すレジスタとしてよく使われます。
*   `MOVD R3, 16(R15)`: `R3` の内容 (つまり `argframe` のアドレス) を、`R15` (スタックポインタ) から16バイトオフセットしたメモリ位置に格納します。これは、`callReflect` 関数への引数として `argframe` のアドレスを渡すための準備です。
*   `BL ·callReflect(SB)`: `callReflect` という Go ランタイム関数を呼び出します。`BL` は "Branch and Link" 命令で、呼び出し元の戻りアドレスをリンクレジスタに保存し、指定されたアドレスに分岐します。`callReflect` は、`reflect.MakeFunc` によって生成された関数が実際に呼び出されたときに、引数の処理、ターゲット関数の呼び出し、戻り値の処理を行う Go のヘルパー関数です。
*   `RET`: 関数から戻ります。

### `methodValueCall`

`methodValueCall` は `makeFuncStub` と非常に似た構造をしています。
*   `TEXT ·methodValueCall(SB),(NOSPLIT|WRAPPER),$16`: `methodValueCall` という名前の関数を定義します。
*   `NO_LOCAL_POINTERS`: 同上。
*   `MOVD R12, 8(R15)`: 同上。
*   `MOVD $argframe+0(FP), R3`: 同上。
*   `MOVD R3, 16(R15)`: 同上。
*   `BL ·callMethod(SB)`: `callMethod` という Go ランタイム関数を呼び出します。`callMethod` は、`reflect.Value.Call` を通じてメソッドが呼び出されたときに、引数の処理、ターゲットメソッドの呼び出し、戻り値の処理を行う Go のヘルパー関数です。
*   `RET`: 関数から戻ります。

これらのアセンブリスタブは、Go のリフレクション機能が s390x 上で動作するために不可欠な、Go のランタイムと動的に生成されたコード間の低レベルなインターフェースを提供します。

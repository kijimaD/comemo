# [インデックス 20663] ファイルの概要

このコミットは、Goリンカー（`cmd/ld`）におけるバグ修正に関するものです。具体的には、`-X`リンカーオプションを使用してプログラム内で使用されていないシンボルを参照した場合に発生する「missing Go type information」エラーを解決します。リンカーが`-X`オプションによって作成されたシンボルを自動的に到達可能とマークしないようにすることで、この問題が修正されます。

## 変更の背景

このコミットは、Goリンカーの`-X`オプションの挙動に関連するバグ（Issue #8821）を修正するために導入されました。

**問題の概要:**
Goのビルドプロセスにおいて、`-ldflags="-X importpath.name=value"`という形式で`-X`オプションを使用すると、コンパイル時に指定した文字列変数の値を埋め込むことができます。これは、バージョン情報やビルド時刻などのメタデータをバイナリに含める際によく利用されます。

しかし、この`-X`オプションが参照するシンボル（変数）が、プログラムのコード内で実際に使用されていない場合、Goリンカーが「missing Go type information」（Goの型情報が見つかりません）というエラーを報告するというバグが存在しました。

**バグの原因:**
リンカーは、`-X`オプションによって新しい文字列データシンボルを作成し、それを参照するシンボル（例えば`main.Version`）を生成します。従来のリンカーの挙動では、`addstrdata`のような関数がシンボルを処理する際に、そのシンボルを自動的に「到達可能（reachable）」とマークしていました。

「到達可能」とは、リンカーが最終的なバイナリに含めるべきコードやデータを決定する際に使用する概念です。リンカーはプログラムのエントリポイント（通常は`main`関数）からシンボルグラフを走査し、参照されているすべてのシンボルを到達可能とマークします。到達可能とマークされなかったシンボルは、デッドコード（不要なコード）として最終バイナリから削除されます。

問題は、`-X`オプションで指定されたシンボルが、たとえプログラム内で使用されていなくても、`addstrdata`によって自動的に到達可能とマークされてしまう点にありました。使用されていないシンボルが到達可能とマークされると、リンカーはそれらのシンボルに対して型情報を解決しようとしますが、実際にコードから参照されていないため、必要な型情報が不足していると判断し、エラーを発生させていました。

このコミットは、`-X`オプションによって作成されるシンボルが、そのシンボルが実際にコード内で使用されているかどうかにかかわらず、自動的に到達可能とマークされるべきではないという認識に基づいています。

## 前提知識の解説

### Goリンカー (`cmd/ld`)

Goのビルドシステムにおいて、`cmd/ld`はGoプログラムを最終的な実行可能バイナリにリンクする役割を担うリンカーです。コンパイラ（`cmd/compile`）が生成したオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、必要なライブラリやランタイムコードを含めて、実行可能な形式に変換します。リンカーの主な機能には、シンボル解決、アドレス割り当て、デッドコード排除などがあります。

### `-X` オプション (Build-time variable injection)

Goリンカーの`-X`オプションは、ビルド時にGoプログラム内の文字列変数の値を変更するために使用されます。これは、`go build`、`go run`、`go install`コマンドの`-ldflags`引数を通じて渡されます。

**構文:**
`go build -ldflags="-X importpath.name=value"`

*   `importpath`: 変数が宣言されているパッケージの完全なインポートパス（例: `main`、`github.com/user/repo/pkg`）。
*   `name`: 値を設定したい文字列変数の名前。
*   `value`: 変数に割り当てる文字列値。

**使用例:**
アプリケーションのバージョン情報をバイナリに埋め込む場合などによく使われます。

```go
// main.go
package main

import "fmt"

var Version string // この変数の値をビルド時に設定したい

func main() {
    fmt.Printf("Application Version: %s\n", Version)
}
```

ビルドコマンド:
`go build -ldflags="-X main.Version=1.0.0"`

これにより、実行時に`Application Version: 1.0.0`と出力されます。
`-X`オプションは、ソースコードを変更せずにビルドごとの動的な情報をバイナリに含める非常に便利な方法です。

### 到達可能なシンボル (Reachable Symbols) とデッドコード排除 (Dead Code Elimination)

Goリンカーは、最終的な実行可能バイナリのサイズを最適化するために、デッドコード排除（DCE）というプロセスを実行します。DCEの目的は、プログラム内で決して実行されない、または参照されないコードやデータをバイナリから削除することです。

リンカーは、プログラムのエントリポイント（通常は`main`関数）から開始し、そこから直接的または間接的に参照されるすべてのシンボル（関数、変数、型など）を「到達可能（reachable）」とマークします。このプロセスはシンボルグラフの走査として知られています。走査が完了した後、到達可能とマークされなかったシンボルはデッドコードと見なされ、最終バイナリには含まれません。

シンボルが「到達可能」であるとマークされることは、リンカーがそのシンボルに関連するすべての情報（例えば型情報）を処理し、バイナリに含める必要があることを意味します。もしシンボルが不必要に到達可能とマークされると、リンカーは存在しない、または不要な型情報を解決しようとし、結果として「missing Go type information」のようなエラーを引き起こす可能性があります。

### 「missing Go type information」エラー

このエラーは、Goリンカーが特定のシンボルに必要な型情報を見つけられない場合に発生します。これは通常、リンカーがシンボルを処理しようとしているにもかかわらず、そのシンボルがコンパイル時に完全な型情報を持っていないか、またはリンカーがその型情報を正しく解決できない場合に起こります。

本コミットの文脈では、`-X`オプションによって注入された文字列シンボルが、プログラムの他の部分から実際に参照されていないにもかかわらず、リンカーによって「到達可能」と誤ってマークされたために発生していました。リンカーは到達可能とマークされたシンボルに対して型情報を期待しますが、使用されていない`-X`シンボルには完全な型情報が関連付けられていないため、このエラーが発生していました。

## 技術的詳細

このコミットの技術的な核心は、Goリンカーがシンボルの「到達可能性（reachable）」フラグをどのように管理するかという点にあります。

Goリンカーの内部では、`LSym`構造体が各シンボルを表し、その中に`reachable`という`uchar`型のフィールドがあります。このフィールドは、そのシンボルが最終的なバイナリに含められるべきかどうかを示すフラグです。

### `src/cmd/ld/data.c` の変更

`addstrdata`関数は、`-X`オプションによって注入されるような文字列データをリンカーのシンボルテーブルに追加するために使用されます。変更前は、この関数内で`addaddr`や`adduint32`などの操作が行われると、それらの操作が内部的に関連するシンボル（この場合は`s`と`sp`）を自動的に到達可能（`reachable = 1`）とマークしていました。

問題は、`-X`オプションで指定されたシンボルが、たとえプログラムのどこからも参照されていなくても、`addstrdata`が呼び出されることで強制的に到達可能とマークされてしまうことでした。これにより、リンカーは使用されていないシンボルに対しても型情報を解決しようとし、「missing Go type information」エラーが発生していました。

このコミットでは、`addstrdata`関数内で、シンボル`s`の既存の`reachable`状態を一時的に`reachable`変数に保存し、関数内の操作（`addaddr`など）がシンボルの`reachable`フラグを変更した後で、元の`reachable`状態を`s->reachable`と`sp->reachable`に復元するように変更されました。

```c
// 変更前:
// in case reachability has already been computed
// sp->reachable = s->reachable;

// 変更後:
uchar reachable; // 新しく追加された変数
// ...
reachable = s->reachable; // sの現在のreachable状態を保存
// ...
// addstring, addaddr, etc., mark the symbols as reachable.
// In this case that is not necessarily true, so stick to what
// we know before entering this function.
s->reachable = reachable;   // sのreachable状態を元の値に戻す
sp->reachable = reachable;  // spのreachable状態も元の値に戻す
```

この変更により、`-X`オプションによって作成されたシンボルが、`addstrdata`関数内の副作用によって不必要に到達可能とマークされることがなくなりました。シンボルが実際にプログラムの他の部分から参照されている場合にのみ、リンカーの通常の到達可能性解析によって到達可能とマークされるようになります。

### `src/cmd/ld/lib.c` の変更

`lib.c`の変更は、`runtime/cgo`という特定の文字列シンボルに関するものです。このシンボルは、Cgo（GoとCの相互運用機能）を使用するGoプログラムにおいて、ランタイムがCgo関連の情報を処理するために常に必要とされます。

変更前は、`addstrdata(cgostrsym, "runtime/cgo");`の呼び出し後に`linklookup(ctxt, cgostrsym, 0)->type = SRODATA;`という行がありましたが、この行では`reachable`フラグが明示的に設定されていませんでした。

変更後、`addstrdata`の呼び出し前に`s->reachable = 1;`という行が追加されました。

```c
// 変更前:
// addstrdata(cgostrsym, "runtime/cgo");
// linklookup(ctxt, cgostrsym, 0)->type = SRODATA;

// 変更後:
s = linklookup(ctxt, cgostrsym, 0); // シンボルを取得
s->type = SRODATA;                  // 型を設定
s->reachable = 1;                   // 明示的に到達可能とマーク
addstrdata(cgostrsym, "runtime/cgo"); // 文字列データを追加
```

この変更は、`runtime/cgo`シンボルが常に必要とされるため、リンカーがデッドコード排除の対象としないように、明示的に到達可能とマークすることを保証します。これは、`data.c`の変更によって`addstrdata`がシンボルを自動的に到達可能とマークしなくなったことへの対応でもあります。`runtime/cgo`は常に必要なので、明示的に到達可能にする必要があります。

### `test/linkx.go` の変更

テストファイル`test/linkx.go`は、`-X`オプションの挙動をテストするためのものです。このコミットでは、新しいテストケースが追加されました。

変更前:
`// $G $D/$F.go && $L -X main.tbd hello -X main.overwrite trumped $F.$A && ./$A.out`

変更後:
`// $G $D/$F.go && $L -X main.tbd hello -X main.overwrite trumped -X main.nosuchsymbol neverseen $F.$A && ./$A.out`

追加された`-X main.nosuchsymbol neverseen`は、プログラムのソースコードには存在しないシンボルを`-X`オプションで参照するケースをシミュレートしています。このテストケースは、このような未使用のシンボルを参照しても「missing Go type information」エラーが発生しないことを検証するために追加されました。

## コアとなるコードの解説

### `src/cmd/ld/data.c` の `addstrdata` 関数における変更

この変更は、`addstrdata`関数がシンボルを処理する際の「到達可能性」の副作用を管理するためのものです。

1.  **`uchar reachable;` の追加**:
    `addstrdata`関数の冒頭に、`uchar`型のローカル変数`reachable`が追加されました。これは、シンボル`s`の既存の到達可能性状態を一時的に保存するために使用されます。

2.  **`reachable = s->reachable;`**:
    `linklookup`によってシンボル`s`が取得された直後、そのシンボルの現在の`reachable`フラグの値が`reachable`変数に保存されます。これは、`addaddr`や`adduint32`などの後続の操作が`s->reachable`の値を変更する可能性があるため、元の状態を保持するためです。

3.  **`s->reachable = reachable;` および `sp->reachable = reachable;`**:
    `addaddr`や`adduint32`などの操作が完了した後、保存しておいた`reachable`変数の値が、シンボル`s`と`sp`の`reachable`フラグに再度割り当てられます。
    コメントで示されているように、`addstring`, `addaddr`などの関数は、内部的にシンボルを到達可能とマークする傾向があります。しかし、`-X`オプションによって追加されるシンボルの場合、それが実際にコードから参照されているとは限らないため、自動的に到達可能とマークされるべきではありません。この変更により、`addstrdata`関数が呼び出される前のシンボルの到達可能性状態が維持され、不必要な到達可能性マークが回避されます。これにより、未使用の`-X`シンボルがリンカーによって誤って処理されることがなくなり、「missing Go type information」エラーが解決されます。

### `src/cmd/ld/lib.c` の `loadlib` 関数における変更

この変更は、`runtime/cgo`という特定の文字列シンボルが常に到達可能であることを保証するためのものです。

1.  **`s = linklookup(ctxt, cgostrsym, 0);`**:
    `cgostrsym`（"go.string.\"runtime/cgo\""）に対応するシンボル`s`を取得します。

2.  **`s->type = SRODATA;`**:
    シンボルの型を`SRODATA`（読み取り専用データ）に設定します。これは、文字列リテラルが通常格納されるセクションです。

3.  **`s->reachable = 1;`**:
    最も重要な変更点として、シンボル`s`の`reachable`フラグが明示的に`1`（到達可能）に設定されます。
    これは、`runtime/cgo`シンボルがCgoを使用するGoプログラムにとって常に不可欠であるため、リンカーがデッドコード排除の対象としないようにするためです。`data.c`の変更により`addstrdata`がシンボルを自動的に到達可能とマークしなくなったため、この明示的な設定が必要になりました。

### `test/linkx.go` の変更

このテストファイルの変更は、修正が正しく機能することを確認するためのものです。

1.  **`-X main.nosuchsymbol neverseen` の追加**:
    リンカーコマンドラインに`-X main.nosuchsymbol neverseen`が追加されました。
    `main.nosuchsymbol`は、`linkx.go`のソースコード内には存在しない変数です。このテストケースは、プログラム内で宣言されていないシンボルを`-X`オプションで参照した場合でも、リンカーがエラーを発生させずに正常にリンクできることを検証します。これは、まさにこのコミットが修正しようとしている「未使用の`-X`シンボルが型情報エラーを引き起こす」というバグのシナリオをカバーしています。

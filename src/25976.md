# [インデックス 25976] ファイルの概要

このコミットは、Go言語の`if`ステートメントにおける`else`ブランチの構文解析と型チェックを厳格化し、不正な`else`ブランチをエラーとして報告するように変更するものです。これにより、Goの構文規則がより厳密に適用され、コードの堅牢性が向上します。

## コミット

go/parser, go/types: report invalid else branch in if statements

## 変更の背景

Go言語の`if`ステートメントの`else`ブランチは、その後に続くステートメントが`if`ステートメント自身であるか、またはブロックステートメント（`{ ... }`）であるという特定の構文規則を持っています。しかし、過去にはこの規則が`go/parser`によって十分に厳密に強制されておらず、`else`の後に任意のステートメントが続くような不正な構文が、少なくとも構文解析の段階では許容されてしまう可能性がありました。

このコミットは、Issue #13475で報告された問題を解決するために導入されました。この問題は、`else`の後にセミコロン（`;`）や`defer`文のような不正なステートメントが続く場合に、`go/parser`がエラーを報告せず、`go/types`が型チェックを行う際に初めてエラーが検出されるというものでした。このような挙動は、開発者にとって混乱を招く可能性があり、より早い段階で構文エラーを検出することが望ましいとされました。

したがって、この変更の主な目的は、`go/parser`と`go/types`の両方で`if`ステートメントの`else`ブランチの構文規則を厳格に適用し、不正な構文を早期にエラーとして報告することで、Goコードの品質と一貫性を向上させることにあります。また、古い構文を許容していた`gofmt`のテストを削除することで、現在のGoの構文規則への完全な移行を反映しています。

## 前提知識の解説

このコミットの理解には、以下のGo言語の概念とツールに関する知識が役立ちます。

*   **Go言語のif文**:
    Go言語の`if`ステートメントは、条件に基づいてコードブロックを実行するために使用されます。基本的な構文は以下の通りです。

    ```go
    if condition {
        // conditionがtrueの場合に実行されるコード
    } else if anotherCondition {
        // anotherConditionがtrueの場合に実行されるコード
    } else {
        // どの条件もtrueでない場合に実行されるコード
    }
    ```
    重要なのは、`else`の後に続くのは、別の`if`ステートメント（`else if`）か、または波括弧で囲まれたブロックステートメント（`{ ... }`）でなければならないという規則です。`else`の後に単一のステートメントを直接記述することはできません。

*   **AST (Abstract Syntax Tree - 抽象構文木)**:
    ASTは、ソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラやリンター、コードフォーマッタなどのツールは、ソースコードを直接操作するのではなく、まずソースコードをASTに変換し、そのASTを解析・操作することで様々な処理を行います。Go言語では、`go/ast`パッケージがASTのデータ構造を定義しています。

*   **`go/parser`パッケージ**:
    `go/parser`パッケージは、Goのソースコードを解析し、ASTを生成する役割を担っています。このパッケージは、Goの構文規則に従ってソースコードを読み込み、その構造を`go/ast`パッケージで定義されたASTノードの集合として表現します。構文エラーがある場合、`go/parser`はエラーを報告します。

*   **`go/types`パッケージ**:
    `go/types`パッケージは、Goプログラムの型チェックとセマンティック解析を行う役割を担っています。`go/parser`によって生成されたASTを受け取り、変数や関数の型が正しく使用されているか、インターフェースの実装が正しいか、スコープ規則が守られているかなどを検証します。このパッケージは、プログラムの意味的な正当性を保証するために不可欠です。

*   **`go/printer`パッケージ**:
    `go/printer`パッケージは、ASTをGoのソースコードとして整形して出力する役割を担っています。これは、`gofmt`のようなツールで利用され、一貫したコーディングスタイルを適用するために使用されます。

*   **`gofmt`ツール**:
    `gofmt`は、Go言語の公式なコードフォーマッタです。Goのソースコードを解析し、Goの標準的なコーディングスタイルに自動的に整形します。これにより、Goコミュニティ全体で一貫したコードスタイルが維持され、可読性が向上します。`gofmt`は内部的に`go/parser`でASTを生成し、`go/printer`で整形されたコードを出力します。

## 技術的詳細

このコミットは、Go言語の`if`ステートメントの`else`ブランチの処理を、`go/parser`と`go/types`の両方で強化しています。

1.  **`go/parser`における構文解析の厳格化**:
    以前の`go/parser`は、`else`キーワードの後に続くステートメントの種類について、現在よりも緩やかな解釈をしていました。この変更により、`parser.go`内の`parseIfStmt`関数が修正され、`else`の後に続くトークンを`switch`文で明示的にチェックするようになりました。
    *   `token.IF`の場合: `else if`の形式として、`parseIfStmt()`を再帰的に呼び出します。
    *   `token.LBRACE`の場合: `else { ... }`の形式として、`parseBlockStmt()`を呼び出します。
    *   上記以外の場合: `p.errorExpected(p.pos, "if statement or block")`を呼び出し、「ifステートメントまたはブロックが期待されます」というエラーを報告します。これにより、`else ;`や`else defer f()`のような不正な構文が、構文解析の段階で即座にエラーとして検出されるようになります。

2.  **`go/types`におけるASTの再検証**:
    `go/parser`が構文解析の段階でエラーを報告するようになった一方で、ASTはプログラムの他の部分で変更される可能性があり、その結果として`else`ブランチが不正な状態になることも考えられます。`go/types`パッケージは、このような状況にも対応するため、`stmt.go`内の`stmt`関数（`if`ステートメントの処理部分）に再検証ロジックを追加しました。
    *   `s.Else`（`else`ブランチを表すASTノード）の型を`switch`文でチェックします。
    *   `nil`または`*ast.BadStmt`の場合: これは有効な状態か、または`go/parser`によって既にエラーが報告されている状態なので、特別な処理は不要です。
    *   `*ast.IfStmt`または`*ast.BlockStmt`の場合: これは有効な`else if`または`else { ... }`の形式なので、`check.stmt(inner, s.Else)`を呼び出して型チェックを続行します。
    *   上記以外の場合: `check.error(s.Else.Pos(), "invalid else branch in if statement")`を呼び出し、「ifステートメントのelseブランチが不正です」というエラーを報告します。これにより、`go/parser`をすり抜けた、あるいはASTが後から不正に改変された場合でも、`go/types`がセマンティックなエラーとして検出できるようになります。

3.  **`gofmt`のテスト削除**:
    `src/cmd/gofmt/testdata/old.golden`と`src/cmd/gofmt/testdata/old.input`の2つのテストファイルが削除されました。これらのファイルは、`else`の後に単一のステートメントが続く古いスタイルの`if`ステートメントが`gofmt`によって正しく整形されることを検証するためのものでした。Go言語の構文が現在の形式に移行して久しいことから、これらの古い構文をサポートする必要がなくなり、関連するテストも不要と判断されました。

4.  **`go/printer`へのコメント追加**:
    `src/go/printer/nodes.go`内の`stmt`関数（`if`ステートメントの`else`ブランチを処理する部分）にコメントが追加されました。このコメントは、`else`ブランチが`*ast.BlockStmt`や`*ast.IfStmt`ではない場合に、それが「不正に構築されたAST」であることを明記しています。`go/printer`は、このような不正なASTであっても、エラーを発生させずに印刷を試みることを示しています。これは、`go/parser`や`go/types`がエラーを報告する一方で、`go/printer`は可能な限り出力を行うという役割分担を明確にするものです。

5.  **`go/parser`のテスト追加**:
    `src/go/parser/short_test.go`に、Issue #13475に関連する新しい無効なテストケースが追加されました。具体的には、`if true {} else ;`と`if true {} else defer f()`という構文が、`go/parser`によって「expected if statement or block」（ifステートメントまたはブロックが期待されます）というエラーとして正しく検出されることを検証しています。

これらの変更により、Go言語の`if`ステートメントの`else`ブランチに関する構文規則がより厳密に強制され、開発者はより早期に構文エラーを検出できるようになります。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更

`parseIfStmt`関数は、`if`ステートメントの構文解析を担当します。変更前は、`else`キーワードの後に`p.parseStmt()`を呼び出して、任意のステートメントを`else`ブランチとして受け入れていました。

変更後は、`else`の後に続くトークンを`switch p.tok`でチェックし、Go言語の厳密な構文規則を適用しています。
*   `case token.IF:`: `else if`のケースです。`parseIfStmt()`を再帰的に呼び出すことで、ネストされた`if`ステートメントを正しく処理します。
*   `case token.LBRACE:`: `else { ... }`のケースです。`parseBlockStmt()`を呼び出してブロックステートメントを解析します。その後、`p.expectSemi()`でセミコロンを期待します。
*   `default:`: 上記のいずれでもない場合、不正な構文と判断されます。`p.errorExpected(p.pos, "if statement or block")`を呼び出してエラーを報告し、`&ast.BadStmt{From: p.pos, To: p.pos}`という`BadStmt`ノードを`else_`に割り当てます。`BadStmt`は、構文エラーが発生したことを示すASTノードであり、後続の処理がクラッシュしないようにするためのプレースホルダーとして機能します。

この変更により、`else`の後に`if`ステートメントまたはブロックステートメント以外のものが来た場合、構文解析の段階でエラーが報告されるようになり、開発者はより早期に問題を特定できます。

### `src/go/types/stmt.go` の変更

`stmt`関数は、Goプログラムの型チェックとセマンティック解析を行います。特に、`if`ステートメントの処理において、`else`ブランチの妥当性を再検証するロジックが追加されました。

変更前は、`if s.Else != nil`という単純なチェックで`else`ブランチの存在を確認し、存在すれば`check.stmt(inner, s.Else)`を呼び出して型チェックを行っていました。これは、`go/parser`が不正な`else`ブランチを許容していた場合、`go/types`がその不正なASTを処理しようとすることを意味します。

変更後は、`switch s.Else.(type)`を使用して`else`ブランチのASTノードの具体的な型をチェックしています。
*   `case nil, *ast.BadStmt:`: `else`ブランチが存在しない場合（`nil`）か、`go/parser`によって既にエラーが報告され`BadStmt`が設定されている場合です。これらのケースは有効であるか、既に処理済みであるため、追加のエラー報告は不要です。
*   `case *ast.IfStmt, *ast.BlockStmt:`: `else`ブランチが`if`ステートメント（`else if`）またはブロックステートメント（`else { ... }`）である場合です。これはGoの構文規則に合致するため、`check.stmt(inner, s.Else)`を呼び出して型チェックを続行します。
*   `default:`: 上記のいずれでもない場合、`else`ブランチが不正な型を持っていると判断されます。`check.error(s.Else.Pos(), "invalid else branch in if statement")`を呼び出して、「ifステートメントのelseブランチが不正です」というエラーを報告します。このチェックは、`go/parser`が不正なASTを生成しなかったとしても、ASTが外部で（例えば、プログラムによるASTの操作によって）不正に改変された場合に備えて重要です。

この変更により、`go/types`は`else`ブランチのセマンティックな妥当性をより厳密に検証し、不正な構造を確実にエラーとして報告できるようになりました。

### `src/cmd/gofmt/testdata/old.golden` および `src/cmd/gofmt/testdata/old.input` の削除

これらのファイルは、`gofmt`が古いスタイルの`if`ステートメント（`else`の後に単一のステートメントが続く形式）を正しく整形できることをテストするためのものでした。Go言語の構文が進化し、この古い形式がもはや有効ではないため、これらのテストは不要となり削除されました。これは、Go言語のツールチェーンが最新の構文規則に完全に準拠していることを示しています。

### `src/go/parser/short_test.go` の変更

`invalids`配列は、`go/parser`がエラーを報告すべき不正なGoコードスニペットのリストです。Issue #13475で報告された問題に対応するため、以下の2つの新しいテストケースが追加されました。

*   `` `package p; func f() { if true {} else ; /* ERROR "expected if statement or block" */ }` ``
*   `` `package p; func f() { if true {} else defer /* ERROR "expected if statement or block" */ f() }` ``

これらのテストケースは、`else`の後にセミコロンや`defer`ステートメントのような不正な要素が続く場合に、`go/parser`が「expected if statement or block」という適切なエラーメッセージを生成することを検証します。これにより、`go/parser`の厳格化された構文解析が正しく機能していることが保証されます。

### `src/go/printer/nodes.go` の変更

`stmt`関数は、ASTノードをGoのソースコードとして印刷する役割を担っています。`if`ステートメントの`else`ブランチを処理する部分にコメントが追加されました。

```go
				// This can only happen with an incorrectly
				// constructed AST. Permit it but print so
				// that it can be parsed without errors.
```

このコメントは、`else`ブランチが`*ast.BlockStmt`や`*ast.IfStmt`ではない`default`ケースに到達した場合、それは「不正に構築されたAST」であることを明確にしています。`go/parser`や`go/types`がこのような不正なASTに対してエラーを報告する一方で、`go/printer`は可能な限りそのASTを印刷しようとします。これは、`go/printer`がコードの整形と出力に特化しており、構文やセマンティックなエラーチェックは他のツールに任せるという役割分担を示しています。`go/printer`がエラーを発生させずに印刷することで、不正なASTであっても、その構造を視覚的に確認できるという利点があります。

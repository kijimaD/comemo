# [インデックス 21341] ファイルの概要

## 変更の背景

このコミットの背景には、Go言語のリンカ `cmd/9l` がPowerPCアーキテクチャ向けのリロケーションタイプ `R_CALLPOWER` を処理する際に発生するエラーメッセージの改善があります。以前のリンカは、リロケーションが正しくアラインされていない場合や、オフセットが大きすぎる場合に、エラーメッセージにシンボルの名前 (`s->name`) のみを含んでいました。しかし、これだけでは問題の特定が困難な場合がありました。

特に、リロケーションがアラインされていないエラー (`t & 3`) や、リロケーションのオフセットが大きすぎるエラー (`t << 6 >> 6 != t`) は、特定の命令のアドレス計算に関連しており、シンボル名だけでなく、そのシンボルからのオフセット情報 (`r->off`) も含めることで、開発者が問題の発生箇所をより正確に特定できるようになります。

また、オフセットが大きすぎるエラーについては、32MBを超えるテキストセクションを持つプログラムで発生する可能性が示唆されており、将来的に「コールトランポリン」を追加することでこの問題を解決する可能性が `TODO` コメントとして追記されています。これは、リンカがより大きなプログラムを扱えるようにするための将来的な改善点を示唆しています。

## 前提知識の解説

*   **`cmd/9l`**: Go言語の初期のリンカです。現在は `cmd/link` に統合されていますが、このコミットが作成された時点ではまだ使用されていました。リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o` ファイル）を結合し、実行可能なバイナリを生成するツールです。この過程で、未解決のシンボル参照（関数呼び出しや変数アクセスなど）を解決し、正しいメモリアドレスに置き換える「リロケーション」を行います。
*   **リロケーション (Relocation)**: プログラム内のシンボル（関数や変数）が最終的にメモリ上のどこに配置されるか分からない状態でコンパイルされたコードを、リンカが実際のメモリアドレスに「再配置」するプロセスです。これにより、プログラムは正しく実行できるようになります。リロケーションには様々なタイプがあり、それぞれ異なる方法でアドレス解決を行います。
*   **`R_CALLPOWER`**: PowerPCアーキテクチャに特化したリロケーションタイプの一つです。これは、PowerPCの関数呼び出し命令に関連するアドレス解決を扱います。PowerPCの命令セットやアドレッシングモードの特性上、関数呼び出しのターゲットアドレスを正確に計算し、命令をパッチするためにこのリロケーションタイプが使用されます。
*   **`LSym`**: リンカが扱うシンボル（関数、変数など）を表す内部データ構造です。`s->name` はシンボルの名前、`s->value` はシンボルのアドレス（またはオフセット）を示します。
*   **`Reloc`**: リロケーションエントリを表す内部データ構造です。`r->sym` はリロケーションが参照するシンボル、`r->add` はリロケーションの加算値、`r->off` はリロケーションが適用される命令のシンボルからのオフセットを示します。
*   **`symaddr(r->sym)`**: `r->sym` が指すシンボルの最終的なアドレスを計算する関数です。
*   **`ctxt->diag`**: リンカのコンテキストオブジェクト `ctxt` の診断メッセージ出力関数です。エラーや警告メッセージをユーザーに表示するために使用されます。
*   **アラインメント (Alignment)**: メモリアクセスの効率を向上させるために、データや命令が特定のバイト境界に配置されることを指します。PowerPCのような一部のアーキテクチャでは、命令が特定のバイト境界（例えば4バイト境界）にアラインされている必要があります。アラインメントが守られていない場合、パフォーマンスの低下や、場合によってはプログラムのクラッシュを引き起こす可能性があります。
*   **コールトランポリン (Call Trampoline)**: 特定のアーキテクチャ（特にジャンプ命令の範囲が限られている場合）で、遠く離れた関数を呼び出すために使用される小さなコードスニペットです。直接ジャンプできない場合、トランポリンが中間地点として機能し、そこから目的の関数へジャンプします。これは、32MBを超えるテキストセクションを持つプログラムで、通常の呼び出し命令のオフセットが足りなくなる場合に必要となることがあります。

## 技術的詳細

このコミットで変更されているのは、`src/cmd/9l/asm.c` 内の `archreloc` 関数です。この関数は、特定のリロケーションタイプ（この場合は `R_CALLPOWER`）を処理し、シンボルのアドレスを解決して、命令内の対応するフィールドを更新します。

変更の対象となっているのは、`R_CALLPOWER` リロケーションにおける2つのエラーチェックです。

1.  **アラインメントチェック**:
    ```c
    t = symaddr(r->sym) + r->add - (s->value + r->off);
    if(t & 3)
        ctxt->diag("relocation for %s is not aligned: %lld", s->name, t);
    ```
    このコードは、計算されたオフセット `t` が4の倍数であるか（つまり、下位2ビットが0であるか）をチェックしています。`t & 3` は `t` を4で割った余りを計算するのと同じです。もし余りが0でなければ、アラインメントエラーが発生します。
    変更前はエラーメッセージが `relocation for %s is not aligned: %lld` でしたが、変更後は `relocation for %s+%d is not aligned: %lld` となり、`r->off` (リロケーションのオフセット) が追加されました。これにより、どのシンボルのどの位置でアラインメント問題が発生したかがより明確になります。

2.  **オフセットサイズチェック**:
    ```c
    if(t << 6 >> 6 != t)
        ctxt->diag("relocation for %s is too big: %lld", s->name, t);
    ```
    このコードは、計算されたオフセット `t` がPowerPCの呼び出し命令で表現できる範囲内にあるかをチェックしています。`t << 6 >> 6` は、`t` を左に6ビットシフトし、その後右に6ビットシフトすることで、`t` の上位6ビットを切り捨てる操作です。もしこの操作の結果が元の `t` と異なる場合、それは `t` が表現可能な範囲を超えていることを意味します。これは通常、ジャンプ命令のオフセットフィールドが限られたビット数しか持たないために発生します。
    変更前はエラーメッセージが `relocation for %s is too big: %lld` でしたが、変更後は `relocation for %s+%d is too big: %lld` となり、ここでも `r->off` が追加されました。
    さらに、このエラーメッセージの下に `// TODO(austin) This can happen if text > 32M. // Add a call trampoline to .text in that case.` という `TODO` コメントが追加されました。これは、テキストセクションのサイズが32MBを超えるとこの問題が発生する可能性があり、その解決策としてコールトランポリンの導入が検討されていることを示しています。

これらの変更は、リンカが生成するエラーメッセージの診断能力を向上させ、開発者がリロケーション関連の問題をデバッグする際の効率を高めることを目的としています。

## コアとなるコードの解説

変更は `archreloc` 関数内の2つの `ctxt->diag` 呼び出しに集中しています。

1.  **アラインメントエラーメッセージの変更**:
    *   変更前: `ctxt->diag("relocation for %s is not aligned: %lld", s->name, t);`
    *   変更後: `ctxt->diag("relocation for %s+%d is not aligned: %lld", r->sym->name, r->off, t);`
    `s->name` が `r->sym->name` に変更され、さらに `%d` と `r->off` が追加されました。これにより、エラーメッセージにリロケーションが適用されるシンボル名とそのシンボルからのオフセットが明示的に含まれるようになり、問題の発生源をより正確に特定できるようになりました。

2.  **オフセットサイズエラーメッセージの変更**:
    *   変更前: `ctxt->diag("relocation for %s is too big: %lld", s->name, t);`
    *   変更後: `ctxt->diag("relocation for %s+%d is too big: %lld", r->sym->name, r->off, t);`
    こちらも同様に、`s->name` が `r->sym->name` に変更され、`%d` と `r->off` が追加されました。
    さらに、この行の直前に以下の `TODO` コメントが追加されました。
    ```c
    // TODO(austin) This can happen if text > 32M.
    // Add a call trampoline to .text in that case.
    ```
    このコメントは、テキストセクションが32MBを超える場合にこのエラーが発生する可能性があり、その解決策としてコールトランポリンの追加が検討されていることを示しています。これは、リンカの将来的なスケーラビリティに関する重要な情報を提供しています。

これらの変更は、Goリンカのエラー報告の品質を向上させ、特にPowerPCアーキテクチャにおけるリロケーション関連のデバッグを容易にすることを目的としています。

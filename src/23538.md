## 変更の背景

この変更は、Goのビルドシステム上で`TestDialerDualStack`テストがパニックを起こすという問題に対応するために行われました。具体的には、以下のビルドログで報告されたクラッシュが原因です。

[http://build.golang.org/log/e5843777df400868ce708b7f00c50dc32c2ec478](http://build.golang.org/log/e5843777df400868ce708b7f00c50dc32c2ec478)

このパニックは、`newDualStackServer`関数内でデュアルスタックリスナーを初期化する際に、エラーが発生した場合のクリーンアップ処理に不備があったために発生しました。一部のリスナーは正常に開かれたものの、その後のリスナーのオープンに失敗した場合、エラーハンドリングルーチンがまだ開かれていない（または初期化に失敗した）リスナーに対しても`Close()`を呼び出そうとし、結果としてパニックを引き起こしていました。

## 前提知識の解説

### Goの`net`パッケージ
Go言語の`net`パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルを扱うための機能が含まれています。

### デュアルスタックリスナー (Dual-Stack Listener)
デュアルスタックリスナーとは、単一のソケットでIPv4とIPv6の両方からの接続を受け入れることができるリスナーのことです。これにより、アプリケーションはIPv4とIPv6の両方のクライアントに対応するために、別々のリスナーを立てる必要がなくなります。Goの`net`パッケージでは、適切なアドレスとネットワークタイプを指定することで、デュアルスタックリスナーを簡単に作成できます。

### `net.Listen`関数
`net.Listen(network, address string)`関数は、指定されたネットワークアドレスでローカルネットワークリスナーを宣言します。
- `network`: "tcp", "tcp4", "tcp6", "udp", "udp4", "udp6", "unix", "unixgram", "unixpacket" など。
- `address`: ネットワークアドレス。例えば、"localhost:8080" や "[::1]:8080" など。

### `net.Listener.Close()`メソッド
`net.Listener`インターフェースは`Close()`メソッドを持ち、リスナーを閉じ、それ以上新しい接続を受け入れないようにします。既に閉じられたリスナーに対して`Close()`を呼び出すと、通常はエラーが返されるか、あるいは何もしない実装になっていることが多いですが、Goのテスト環境では、未初期化のリスナーや無効なリスナーに対して`Close()`を呼び出すとパニックを引き起こす可能性があります。

### `JoinHostPort`関数
`net.JoinHostPort(host, port string)`関数は、ホストとポートをネットワークアドレス文字列に結合します。これは、IPv6アドレスを角括弧で囲むなど、正しい形式を保証するために使用されます。

### Goにおける`panic`
Goにおける`panic`は、プログラムの実行を中断するランタイムエラーです。通常、回復不可能なエラーやプログラマーの論理的な誤りを示すために使用されます。`panic`が発生すると、現在のゴルーチンの通常の実行フローは停止し、遅延関数（`defer`）が実行され、その後、呼び出しスタックをアンワインドしていきます。最終的に、`recover`が呼び出されない限り、プログラムはクラッシュします。

## 技術的詳細

`src/net/mockserver_test.go`内の`newDualStackServer`関数は、デュアルスタックサーバーをセットアップするために複数のリスナーを作成します。この関数は、`dss.lns`というスライスに定義された複数の`streamListener`構造体（ネットワークタイプとアドレス情報を持つ）をループ処理し、それぞれに対して`net.Listen`を呼び出してリスナーを生成します。

```go
func newDualStackServer(lns []streamListener) (*dualStackServer, error) {
	dss := &dualStackServer{lns: lns}
	// ... (ポート割り当てなどの初期化)

	for i := range dss.lns {
		ln, err := Listen(dss.lns[i].network, JoinHostPort(dss.lns[i].address, dss.port))
		if err != nil {
			// エラー発生時のクリーンアップ処理
			for _, ln := range dss.lns { // 変更前: ここが問題
				ln.Listener.Close()
			}
			return nil, err
		}
		dss.lns[i].Listener = ln // 正常に開かれたリスナーをスライスに格納
	}
	return dss, nil
}
```

問題は、`for i := range dss.lns`ループ内で`Listen`呼び出しがエラーを返した場合のクリーンアップ処理にありました。エラーが発生すると、関数はそれまでに開かれたリスナーをすべて閉じようとします。しかし、変更前のコードでは、クリーンアップループが`for _, ln := range dss.lns`となっていました。

この`dss.lns`スライスは、`newDualStackServer`関数に渡された初期の`streamListener`のリストであり、`Listen`が成功した場合にのみ`ln.Listener`フィールドが実際の`net.Listener`インスタンスで更新されます。

もしループの途中で`Listen`がエラーを返した場合、`i`番目以降の`dss.lns`内の要素の`Listener`フィールドはまだ`nil`（またはゼロ値）のままです。この状態で`for _, ln := range dss.lns`を使ってスライス全体をイテレートし、`ln.Listener.Close()`を呼び出そうとすると、`nil`ポインタに対してメソッドを呼び出すことになり、Goランタイムがパニックを引き起こします。

このパニックは、特にテスト環境でネットワーク設定が不安定な場合や、特定のアドレスでのリスニングに失敗した場合に顕在化しました。

- **変更前**: `for _, ln := range dss.lns`
  - これは`dss.lns`スライス全体をイテレートします。前述の通り、`i`番目以降の要素の`Listener`フィールドは`nil`である可能性があり、`nil.Close()`を呼び出してパニックを引き起こします。

  - この変更により、クリーンアップループは`dss.lns`スライスの`0`から`i-1`までの要素のみをイテレートするようになります。
  - `dss.lns[:i]`は、スライスの最初の`i`個の要素を含む新しいスライス（スライスヘッダ）を作成します。
  - `i`は、`Listen`呼び出しがエラーを返した時点のインデックスです。したがって、`i`より前のインデックスのリスナーは正常に開かれ、`dss.lns[j].Listener`（`j < i`）には有効な`net.Listener`インスタンスが格納されています。

この修正は、エラーハンドリングにおける「既に成功した部分のクリーンアップ」という一般的なプログラミングパターンを正しく適用したものです。

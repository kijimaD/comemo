# [インデックス 23720] ファイルの概要

このコミットは、Go言語のテストスイートの一部である `test/nosplit.go` ファイルに対する変更です。`nosplit.go` は、Goランタイムの低レベルな部分で使用される「nosplit」関数（スタックの拡張を許可しない関数）の挙動をテストするために用いられます。これらの関数は、スタックの境界チェックを省略することで、パフォーマンスが要求されるクリティカルなパスや、スタックの拡張自体が不可能な状況（例えば、スタックの拡張処理自体を実装する際）で利用されます。このファイルは、異なるアーキテクチャ（GOARCH）向けにアセンブリコードを動的に生成し、`nosplit` 関数の呼び出し規約やスタックフレームの整合性を検証します。

## コミット

このコミットは、`GOARCH=ppc64` および `GOARCH=ppc64le` アーキテクチャにおけるビルドの問題を修正することを目的としています。具体的には、`test/nosplit.go` 内でPowerPC 64-bitアーキテクチャ向けに生成されるアセンブリコードの定義から、不要な `#define RET RETURN` マクロを削除しています。これにより、これらのアーキテクチャでのテストビルドが正常に完了するようになります。

## 変更の背景

Go言語は、様々なCPUアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたコードを生成する必要があります。特に、Goランタイムの低レベルな部分（スケジューラ、ガベージコレクタ、スタック管理など）は、アセンブリ言語で記述されることが多く、アーキテクチャ固有の呼び出し規約やレジスタの使用法に厳密に従う必要があります。

`test/nosplit.go` は、これらの低レベル関数、特にスタック拡張を行わない `nosplit` 関数が正しく動作するかを検証するためのテストです。このテストは、Goのビルドシステムが提供する`goarch`変数に基づいて、ターゲットアーキテクチャ向けのアセンブリコードスニペットを動的に生成します。

`ppc64` (PowerPC 64-bit big-endian) および `ppc64le` (PowerPC 64-bit little-endian) アーキテクチャにおいて、このテストのビルドが失敗していました。これは、`test/nosplit.go` が生成するアセンブリコードの一部が、これらのアーキテクチャの期待する形式と合致していなかったためと考えられます。具体的には、`#define RET RETURN` というマクロ定義が問題を引き起こしていました。このマクロは、特定のアーキテクチャでは不要であるか、あるいは既存の定義と衝突していた可能性があります。このコミットは、このビルドエラーを解消し、PowerPC 64-bit環境でのGoの安定性と互換性を向上させるために行われました。

## 前提知識の解説

### `GOARCH=ppc64/ppc64le`

*   **PowerPC (PPC)**: IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。高性能コンピューティング、組み込みシステム、ゲーム機など、幅広い分野で使用されてきました。
*   **ppc64**: PowerPC 64-bitアーキテクチャを指します。通常、ビッグエンディアン（Big-Endian）形式でデータを扱います。ビッグエンディアンでは、データの最上位バイトがメモリアドレスの最も小さい位置に格納されます。
*   **ppc64le**: PowerPC 64-bitリトルエンディアン（Little-Endian）アーキテクチャを指します。リトルエンディアンでは、データの最下位バイトがメモリアドレスの最も小さい位置に格納されます。現代の多くのシステム（x86など）はリトルエンディアンを採用しており、互換性のためにPowerPCもリトルエンディアンモードをサポートしています。
*   **Go言語におけるサポート**: Go言語は、これらのPowerPC 64-bitアーキテクチャをサポートしており、クロスコンパイルによってこれらのプラットフォーム向けのバイナリを生成できます。

### `nosplit` 関数

Goランタイムには、通常のGo関数とは異なる特別な関数が存在します。その一つが「nosplit」関数です。
*   **スタック拡張**: 通常のGo関数は、実行中にスタックが不足した場合、自動的にスタックを拡張するメカニズム（スタックチェックとスタックコピー）を持っています。これにより、プログラマはスタックサイズを意識することなく再帰呼び出しなどを行うことができます。
*   **`nosplit` の目的**: `nosplit` 関数は、このスタック拡張メカニズムを無効にした関数です。つまり、`nosplit` 関数はスタックチェックを行わず、スタックが不足しても拡張されません。
*   **使用される場面**:
    *   **ランタイムの低レベルコード**: Goランタイム自体がスタック拡張のメカニズムを実装しているため、その実装中にスタック拡張が発生すると無限ループやデッドロックに陥る可能性があります。そのため、スタック拡張処理自体や、ガベージコレクタ、スケジューラなどの非常に低レベルでクリティカルなコードパスでは `nosplit` 関数が使用されます。
    *   **パフォーマンスが要求されるコード**: スタックチェックのオーバーヘッドを完全に排除したい場合にも使用されることがありますが、これは非常に稀で、通常はランタイム内部での利用が主です。
*   **`test/nosplit.go` の役割**: このファイルは、`nosplit` 関数が正しくコンパイルされ、期待される挙動（スタック拡張が行われないこと、呼び出し規約が守られることなど）を示すことを検証するためのテストコードを生成します。異なるアーキテクチャで `nosplit` 関数のアセンブリコードがどのように生成されるかをテストすることは、Goランタイムの移植性と安定性を保証する上で非常に重要です。

### アセンブリマクロ (`#define CALL BL`, `#define REGISTER (CTR)`, `#define RET RETURN`)

Goのアセンブリコードは、Go独自の擬似アセンブリ構文を使用しますが、C言語のプリプロセッサのようなマクロ定義も利用されることがあります。
*   **`#define`**: C言語のプリプロセッサディレクティブで、シンボルを定義するために使用されます。ここでは、アセンブリコード内で共通の操作を抽象化するために使われています。
*   **`CALL BL`**: PowerPCアーキテクチャにおける関数呼び出し命令の一つです。`BL` (Branch with Link) は、指定されたアドレスに分岐し、現在の命令の次のアドレスをリンクレジスタ (LR) に保存します。これにより、関数からの戻りアドレスが保持されます。
*   **`REGISTER (CTR)`**: PowerPCアーキテクチャには、特定の目的を持つ特殊レジスタがいくつかあります。`CTR` (Count Register) は、ループカウンタや分岐ターゲットアドレスの保持など、様々な用途で使用されるレジスタです。ここでは、おそらく関数呼び出しや戻りの際に使用されるレジスタを抽象化するために定義されています。
*   **`RET RETURN`**: これは、関数からの戻り操作を抽象化しようとしたマクロです。しかし、PowerPCのアセンブリでは、通常 `BLR` (Branch to Link Register) 命令が関数からの戻りに使用されます。`RETURN` というシンボルがPowerPCのアセンブリ言語で特別な意味を持つか、あるいはGoのアセンブラが内部的に `RETURN` を特定の命令に変換するのか、または単に他のアーキテクチャとの互換性のために定義されたがPowerPCでは不要だったのか、といった背景が考えられます。このコミットでは、`ppc64/ppc64le` においてこの `RET RETURN` の定義がビルドエラーの原因となっていたため削除されました。

## 技術的詳細

このコミットの技術的な核心は、PowerPC 64-bitアーキテクチャ（`ppc64`および`ppc64le`）におけるGoのアセンブリコード生成の正確性に関するものです。`test/nosplit.go` は、Goのテストフレームワークの一部として、特定のアーキテクチャ向けにアセンブリコードを動的に生成し、そのコードがGoのランタイム規約（特に`nosplit`関数の呼び出し規約）に準拠しているかを検証します。

問題は、`ppc64`および`ppc64le`の場合に、生成されるアセンブリコードに `#define RET RETURN` という行が含まれていたことです。Goのアセンブラ（`cmd/asm`）は、各アーキテクチャのアセンブリ言語の構文とセマンティクスを理解しています。`RETURN`というシンボルは、Goのアセンブラが特定のアーキテクチャで関数からの戻りを示すために内部的に使用するキーワードである可能性があります。

PowerPCアーキテクチャでは、関数からの戻りには通常、リンクレジスタ（LR）に保存されたアドレスへの分岐命令である `BLR` が使用されます。もし `RETURN` がGoのアセンブラにとって特別な意味を持つキーワードである場合、`#define RET RETURN` と定義してしまうと、`RET` を使用した箇所が `RETURN` に展開され、Goのアセンブラが期待するPowerPCのアセンブリ構文と衝突するか、あるいは二重定義のような形でエラーを引き起こしていたと考えられます。

例えば、Goのアセンブラが `RET` という命令を `BLR` に変換するような内部ロジックを持っていたとして、そこに `#define RET RETURN` が存在すると、`RET` が `RETURN` に展開され、さらに `RETURN` が `BLR` に変換される、といった複雑な（そしておそらく誤った）解釈が生じる可能性があります。あるいは、`RETURN` 自体がPowerPCのアセンブリ言語では有効な命令やシンボルとして認識されず、プリプロセッサによる展開後にアセンブラが構文エラーを報告していた可能性もあります。

このコミットは、`ppc64`および`ppc64le`アーキテクチャにおいて、`RET` マクロが不要であるか、あるいは誤った定義であったことを示唆しています。`BL` (Branch with Link) や `CTR` (Count Register) の定義は残されていることから、これらのマクロはPowerPCのアセンブリコード生成において依然として有効かつ必要であると考えられます。`RET RETURN` の削除は、PowerPCのアセンブリコード生成プロセスにおける冗長性または誤りを修正し、ビルドエラーを解消するための直接的な解決策です。

## コアとなるコードの解説

変更は `test/nosplit.go` ファイルの252行目付近にあります。
このコードスニペットは、Goのテスト実行時に、現在のターゲットアーキテクチャ (`goarch`) に応じて、アセンブリコードのテンプレートに埋め込むためのマクロ定義を生成しています。

*   `switch goarch { ... }` ブロック内で、`goarch` が `"ppc64"` または `"ppc64le"` の場合に実行されるケースが変更されています。
*   変更前は、`fmt.Fprintf` を使って以下の3つのマクロがバッファ (`buf`) に書き込まれていました。
    *   `#define CALL BL`
    *   `#define REGISTER (CTR)`
    *   `#define RET RETURN`
*   変更後は、`#define RET RETURN` の部分が削除され、以下の2つのマクロのみが書き込まれるようになりました。
    *   `#define CALL BL`
    *   `#define REGISTER (CTR)`

この変更により、`ppc64` および `ppc64le` アーキテクチャ向けのアセンブリコード生成時に、`RET` マクロが定義されなくなります。前述の技術的詳細で説明したように、この `RET RETURN` の定義がPowerPC 64-bit環境でのGoのアセンブラにとって問題を引き起こしていたため、その削除がビルドエラーの解決に繋がりました。

この修正は、GoランタイムがPowerPC 64-bitアーキテクチャ上で正しくビルドされ、`nosplit` 関数のテストが正常に実行されることを保証するために不可欠です。

*   **`RET RETURN`**: これは、関数からの戻り操作を抽象化しようとしたマクロです。しかし、PowerPCのアセンブリでは、通常 `BLR` (Branch to Link Register) 命令が関数からの戻りに使用されます。`RETURN` というシンボルがPowerPCのアセンブリ言語で特別な意味を持つか、あるいはGoのアセンブラが内部的に `RETURN` を特定の命令に変換するのか、または単に他のアーキテクチャとの互換性のために定義されたがPowerPCでは不要だったのか、といった背景が考えられます。このコミットでは、`ppc64/ppc64le` においてこの `RET RETURN` の定義がビルドエラーの原因となっていたため削除されました。

## 技術的詳細

このコミットの技術的な核心は、PowerPC 64-bitアーキテクチャ（`ppc64`および`ppc64le`）におけるGoのアセンブリコード生成の正確性に関するものです。`test/nosplit.go` は、Goのテストフレームワークの一部として、特定のアーキテクチャ向けにアセンブリコードを動的に生成し、そのコードがGoのランタイム規約（特に`nosplit`関数の呼び出し規約）に準拠しているかを検証します。

問題は、`ppc64`および`ppc64le`の場合に、生成されるアセンブリコードに `#define RET RETURN` という行が含まれていたことです。Goのアセンブラ（`cmd/asm`）は、各アーキテクチャのアセンブリ言語の構文とセマンティクスを理解しています。`RETURN`というシンボルは、Goのアセンブラが特定のアーキテクチャで関数からの戻りを示すために内部的に使用するキーワードである可能性があります。

PowerPCアーキテクチャでは、関数からの戻りには通常、リンクレジスタ（LR）に保存されたアドレスへの分岐命令である `BLR` が使用されます。もし `RETURN` がGoのアセンブラにとって特別な意味を持つキーワードである場合、`#define RET RETURN` と定義してしまうと、`RET` を使用した箇所が `RETURN` に展開され、Goのアセンブラが期待するPowerPCのアセンブリ構文と衝突するか、あるいは二重定義のような形でエラーを引き起こしていたと考えられます。

例えば、Goのアセンブラが `RET` という命令を `BLR` に変換するような内部ロジックを持っていたとして、そこに `#define RET RETURN` が存在すると、`RET` が `RETURN` に展開され、さらに `RETURN` が `BLR` に変換される、といった複雑な（そしておそらく誤った）解釈が生じる可能性があります。あるいは、`RETURN` 自体がPowerPCのアセンブリ言語では有効な命令やシンボルとして認識されず、プリプロセッサによる展開後にアセンブラが構文エラーを報告していた可能性もあります。

このコミットは、`ppc64`および`ppc64le`アーキテクチャにおいて、`RET` マクロが不要であるか、あるいは誤った定義であったことを示唆しています。`BL` (Branch with Link) や `CTR` (Count Register) の定義は残されていることから、これらのマクロはPowerPCのアセンブリコード生成において依然として有効かつ必要であると考えられます。`RET RETURN` の削除は、PowerPCのアセンブリコード生成プロセスにおける冗長性または誤りを修正し、ビルドエラーを解消するための直接的な解決策です。

## コアとなるコードの解説

変更は `test/nosplit.go` ファイルの252行目付近にあります。
このコードスニペットは、Goのテスト実行時に、現在のターゲットアーキテクチャ (`goarch`) に応じて、アセンブリコードのテンプレートに埋め込むためのマクロ定義を生成しています。

*   `switch goarch { ... }` ブロック内で、`goarch` が `"ppc64"` または `"ppc64le"` の場合に実行されるケースが変更されています。
*   変更前は、`fmt.Fprintf` を使って以下の3つのマクロがバッファ (`buf`) に書き込まれていました。
    *   `#define CALL BL`
    *   `#define REGISTER (CTR)`
    *   `#define RET RETURN`
*   変更後は、`#define RET RETURN` の部分が削除され、以下の2つのマクロのみが書き込まれるようになりました。
    *   `#define CALL BL`
    *   `#define REGISTER (CTR)`

この変更により、`ppc64` および `ppc64le` アーキテクチャ向けのアセンブリコード生成時に、`RET` マクロが定義されなくなります。前述の技術的詳細で説明したように、この `RET RETURN` の定義がPowerPC 64-bit環境でのGoのアセンブラにとって問題を引き起こしていたため、その削除がビルドエラーの解決に繋がりました。

この修正は、GoランタイムがPowerPC 64-bitアーキテクチャ上で正しくビルドされ、`nosplit` 関数のテストが正常に実行されることを保証するために不可欠です。

# [インデックス 20722] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における「スキャンとマーク」フェーズの大規模なリファクタリングを目的としています。特に、並行GC（Concurrent GC）とライトバリア（Write Barrier）の共通基盤を構築し、スキャンとマークのフェーズを分離することで、スタックのスキャンをオブジェクトを「黒くする」（マークする）ことなく実行できるように変更されています。これにより、コストの高いライトバリアコードの導入を遅らせることが可能になり、GCの効率化と停止時間の削減に寄与します。

## 元コミット内容

このコミットの元の内容は、Goランタイムのガベージコレクションにおけるスキャンとマークのフェーズをリファクタリングすることです。主な目的は、並行GC、特にライトバリアが共通のインフラストラクチャを共有できるようにすることです。スキャンとマークのフェーズが分離されたことで、オブジェクトを即座に「黒くする」（到達可能としてマークする）ことなくスタックをスキャンできるようになります。これにより、高コストなライトバリアコードの導入を遅らせることが可能になります。

## 変更の背景

Goの初期のガベージコレクションは、プログラムの実行を完全に停止させる「Stop-The-World (STW)」方式を採用していました。これはGCの実行中にアプリケーションが一時停止するため、特に大規模なアプリケーションや低レイテンシが求められるシステムでは、ユーザー体験に悪影響を与える可能性がありました。

このコミットが行われた背景には、GoのGCをより並行性の高いものへと進化させるという明確な目標がありました。並行GCは、GCの作業の一部をアプリケーションの実行と並行して行うことで、STWポーズの時間を大幅に削減することを目指します。

並行GCを実現するためには、GCがオブジェクトグラフを走査している間に、アプリケーション（ミューテーター）がポインタを変更する可能性を考慮する必要があります。このポインタの変更を追跡し、GCの正確性を保証するために導入されるのが「ライトバリア」です。しかし、ライトバリアは実行時にオーバーヘッドを発生させるため、その導入タイミングや実装の効率性が重要になります。

このコミットは、スキャンとマークのフェーズをより細かく分離し、`Workbuf`や`Markbits`といった新しいデータ構造を導入することで、並行GCとライトバリアのためのより堅牢で効率的な基盤を築こうとしています。特に、スタックのスキャンをオブジェクトの即時マークなしに行えるようにすることで、ライトバリアの適用を遅らせ、全体的なパフォーマンスを向上させる狙いがあります。

## 前提知識の解説

このコミットを理解するためには、以下のガベージコレクションに関する基本的な概念とGoランタイムの内部構造に関する知識が必要です。

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはや使用されていない（到達不可能になった）ものを自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークのリスクを低減できます。

GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
1.  **マークフェーズ (Mark Phase)**: プログラムのルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めるメモリ領域を解放し、再利用可能にします。

### Stop-The-World (STW)

STWは、GCの特定のフェーズにおいて、アプリケーションの実行を完全に停止させる期間を指します。この期間中、アプリケーションは一切処理を進めることができません。STWポーズはGCの正確性を保証するために必要ですが、その時間が長くなるとアプリケーションの応答性に悪影響を与えます。GoのGCは、このSTWポーズを最小限に抑えるように進化してきました。

### 並行GC (Concurrent GC)

並行GCは、GCの作業の一部をアプリケーションの実行と並行して行うことで、STWポーズの時間を短縮する手法です。これにより、GCが実行されている間もアプリケーションは処理を継続できるため、レイテンシの改善が期待できます。並行GCでは、GCがオブジェクトグラフを走査している間にアプリケーションがポインタを変更する可能性があるため、その変更を追跡するメカニズムが必要になります。

### ライトバリア (Write Barrier)

ライトバリアは、並行GCにおいて、ミューテーター（アプリケーションコード）がヒープ上のポインタを更新する際に実行される小さなコードスニペットです。その目的は、GCがオブジェクトグラフを走査している最中にポインタが変更され、GCが見落とす可能性のあるオブジェクト（「灰色」から「黒」への変更など）を適切に追跡することです。ライトバリアにはいくつかの種類がありますが、一般的にはポインタの書き込み時に古い値や新しい値を記録することで、GCの正確性を保証します。ライトバリアはオーバーヘッドを伴うため、その設計と実装はGCのパフォーマンスに大きく影響します。

### オブジェクトの色付け (Coloring)

マーク＆スイープGCでは、オブジェクトの状態を色で表現することがあります。
*   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GC開始時にはすべてのオブジェクトが白。
*   **灰色 (Grey)**: GCによって到達可能とマークされたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていない状態。
*   **黒 (Black)**: GCによって到達可能とマークされ、かつそのオブジェクトが参照するすべてのオブジェクトもスキャンが完了した状態。

並行GCでは、ミューテーターがポインタを更新することでオブジェクトの色が変化する可能性があり、これをライトバリアで適切に処理する必要があります。

### Goランタイムのメモリ管理

Goランタイムは独自のメモリ管理システムを持っています。
*   **ヒープ (Heap)**: プログラムが動的に確保するメモリ領域。GCの主な対象。
*   **スタック (Stack)**: 関数の呼び出しやローカル変数を格納するメモリ領域。Goのスタックは動的に伸縮します。
*   **`MSpan`**: ヒープメモリを管理するための構造体。連続したページ（Page）の集合を表します。
*   **`MCache`**: 各P（プロセッサ、OSスレッドに相当）が持つローカルなメモリキャッシュ。GC作業バッファもここに格納されます。

## 技術的詳細

このコミットの技術的詳細は、Goの並行GCの実現に向けた重要なステップを示しています。

### スキャンとマークフェーズの分離と新しいGCフェーズ

従来のマークフェーズでは、オブジェクトをスキャンしながら同時にマーク（黒くする）していました。このコミットでは、このプロセスをより細分化し、以下の新しいGCフェーズが導入されています。

*   **`GCscan`**: このフェーズでは、主にスタックやグローバル変数から到達可能なオブジェクトをスキャンし、それらを「灰色」としてマークします。重要なのは、この段階ではオブジェクトを「黒くする」ことなく、スキャンされたポインタを`Workbuf`にキューイングする点です。これにより、スタックのスキャン中にミューテーターがポインタを更新しても、ライトバリアの介入を最小限に抑えることができます。
*   **`GCmark`**: `GCscan`フェーズで収集された「灰色」のオブジェクトを`Workbuf`から取り出し、それらが参照するオブジェクトを再帰的にスキャンし、マーク（黒くする）します。このフェーズは並行して実行され、ミューテーターもGC作業に協力（ヘルプ）することができます。
*   **`GCmarktermination`**: マークフェーズの終了を検出するフェーズです。すべての到達可能なオブジェクトがマークされ、GC作業が完了したことを確認します。このフェーズでは、新しいオブジェクトの割り当ては「黒」として行われ、GCヘルパーもGC作業を継続します。

このフェーズの分離により、特にスタックのスキャンをより効率的に、かつSTWポーズを短くして実行できるようになります。

### `Workbuf`と`MCache`の役割強化

`Workbuf`は、GCがスキャンすべきオブジェクト（灰色オブジェクト）を一時的に保持するためのバッファです。このコミットでは、`MCache`（各Pのローカルキャッシュ）が`Workbuf`を直接保持するように変更され、GC作業の効率的な管理とP間の作業分散を可能にしています。

*   **`MCache.gcworkbuf`**: `void*`から`Workbuf*`に変更され、GC作業バッファが型安全に管理されるようになりました。
*   **`getpartial` / `putpartial`**: 新たに導入されたこれらの関数は、Pのローカルな`MCache`から部分的に使用された`Workbuf`を取得・解放するためのものです。これにより、GC作業の粒度を細かくし、Pが自身の作業を効率的に管理できるようになります。
*   **`getempty` / `putempty`**: 空の`Workbuf`の取得と解放を管理します。
*   **`getfull`**: グローバルな`work.full`リストから、他のPによって満たされた`Workbuf`を取得します。これは、複数のGCヘルパーが協調して作業を進めるための重要なメカニズムであり、GCの終了条件の検出にも利用されます。

### `Markbits`構造体の導入とGCビットマップの操作

`Markbits`構造体は、GCビットマップから特定のオブジェクトに関するマーク情報を効率的に抽出するための新しい抽象化です。

```c
typedef struct Markbits Markbits;
struct Markbits {
	byte *bitp; // pointer to the byte holding xbits
 	byte shift; // bits xbits needs to be shifted to get bits
	byte xbits; // byte holding all the bits from *bitp
	byte bits;  // bits relevant to corresponding slot.
};
```

*   `bitp`: GCビットマップ内の、対象オブジェクトのマーク情報を含むバイトへのポインタ。
*   `shift`: `*bitp`から対象オブジェクトのビットを抽出するためのシフト量。
*   `xbits`: `*bitp`の生の値。
*   `bits`: 対象オブジェクトに関連する実際のGCビット（マーク済み、ポインタの有無など）。

この構造体と関連する関数（`slottombits`, `objectstart`, `greyobject`）により、GCはヒープ上の任意のアドレスからオブジェクトの開始位置を特定し、そのマーク情報を効率的に読み書きできるようになります。

*   **`inheap(byte *b)`**: 与えられたアドレス`b`がGoのヒープ内に存在するかどうかをチェックします。これは、無効なポインタをGCが処理しようとするのを防ぐために重要です。
*   **`slottombits(byte *obj, Markbits *mbits)`**: オブジェクトのアドレスから、対応するGCビットマップのバイトとシフト量を計算し、`Markbits`構造体に格納します。
*   **`objectstart(byte *b, Markbits *mbits)`**: ヒープ内の任意のアドレス`b`から、そのアドレスが属するオブジェクトの開始アドレスを特定し、関連する`Markbits`情報を取得します。これは、オブジェクトの内部ポインタからでもそのオブジェクトのベースアドレスを特定できることを意味します。
*   **`greyobject(byte *obj, Markbits *mbits, Workbuf *wbuf)`**: オブジェクトがまだマークされていない場合、それをマークし（灰色にする）、`Workbuf`にキューイングします。この関数は、並行GCにおけるオブジェクトのマーク処理の中心的な部分です。アトミック操作（`runtime·atomicor8`）を使用して、複数のPが同時に同じオブジェクトをマークしようとした場合の競合を安全に解決します。
*   **`scanobject(byte *b, uintptr n, byte *ptrmask, Workbuf *wbuf)`**: 指定されたメモリブロック`b`をスキャンし、そこに含まれるポインタを識別して`greyobject`を呼び出し、`Workbuf`に追加します。`ptrmask`が`nil`の場合、GCビットマップを参照してポインタを特定します。

### `scanblock`関数のリファクタリング

`scanblock`関数は、GCのマークフェーズにおいて、オブジェクトをスキャンし、そこから見つかったポインタを処理する中心的な関数です。このコミットでは、`scanblock`が`scanobject`と`Workbuf`管理関数（`getpartial`, `putpartial`, `getfull`）を組み合わせて使用するように大幅にリファクタリングされています。

*   `scanblock`は、初期のオブジェクトスキャン（`scanobject`）を行った後、`Workbuf`にキューイングされたオブジェクトを再帰的に処理するループに入ります。
*   `keepworking`フラグは、GCヘルパーが作業を継続すべきかどうかを制御します。
*   `getfull`は、すべてのGCヘルパーが作業を探している状態（GCの終了条件）を検出するためのバリアとしても機能します。

### スタックのスキャンとライトバリアの遅延

このコミットの重要な成果の一つは、スタックのスキャン方法の変更です。

*   `markroot`関数内で、ゴルーチン（G）のスタックをスキャンする際に、`scanstack(gp)`が直接呼び出されるのではなく、`runtime·gcphasework(G *gp)`を通じて`GCscan`フェーズで実行されるようになりました。
*   これにより、スタック上のオブジェクトを即座に「黒くする」ことなくスキャンし、ポインタを`Workbuf`にキューイングできるようになります。
*   この「黒くしない」スキャンは、ライトバリアの導入を遅らせることを可能にします。スタックはGCのルートであり、その内容は頻繁に変化する可能性があります。スタックのスキャンとマークを分離することで、GCがスタックを走査している間にミューテーターがポインタを更新しても、ライトバリアの介入を最小限に抑え、オーバーヘッドを削減できます。

## コアとなるコードの解説

### `Markbits`構造体と関連関数 (`slottombits`, `objectstart`, `greyobject`)

このコミットの核心的な変更の一つは、GCビットマップの操作を抽象化する`Markbits`構造体の導入です。

```c
// src/runtime/mgc0.c
typedef struct Markbits Markbits;
struct Markbits {
	byte *bitp; // pointer to the byte holding xbits
 	byte shift; // bits xbits needs to be shifted to get bits
	byte xbits; // byte holding all the bits from *bitp
	byte bits;  // bits relevant to corresponding slot.
};

// slottombits: オブジェクトのアドレスからMarkbits情報を計算
static void
slottombits(byte *obj, Markbits *mbits)
{
	uintptr off;
	off = (uintptr*)((uintptr)obj&~(PtrSize-1)) - (uintptr*)runtime·mheap.arena_start;
	mbits->bitp = runtime·mheap.arena_start - off/wordsPerBitmapByte - 1;
	mbits->shift = (off % wordsPerBitmapByte) * gcBits;
	mbits->xbits = *mbits->bitp;
	mbits->bits = (mbits->xbits >> mbits->shift) & bitMask;
}

// objectstart: ヒープ内の任意のアドレスからオブジェクトの開始アドレスとMarkbits情報を取得
static byte*
objectstart(byte *b, Markbits *mbits)
{
    // ... (オブジェクトの開始アドレスを特定するロジック) ...
    slottombits(obj, mbits); // 特定したオブジェクトの開始アドレスでMarkbitsを更新
    return obj;
}

// greyobject: オブジェクトをマークし、Workbufにキューイング
static Workbuf*
greyobject(byte *obj, Markbits *mbits, Workbuf *wbuf)
{
	// objが既にマーク済みなら何もしない
	if((mbits->bits&bitMarked) != 0)
		return wbuf;

	// オブジェクトをマークする（アトミック操作または非アトミック操作）
	if((mbits->xbits&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)) ||
				work.nproc == 1)
		*mbits->bitp = mbits->xbits | (bitMarked<<mbits->shift);
	else
		runtime·atomicor8(mbits->bitp, bitMarked<<mbits->shift);
	
	// noscanオブジェクト（ポインタを含まないオブジェクト）ならスキャン不要
	if(((mbits->xbits>>(mbits->shift+2))&BitsMask) == BitsDead)
		return wbuf;

	// Workbufが満杯なら新しい空のWorkbufを取得
	if(wbuf->nobj >= nelem(wbuf->obj)) {
		wbuf = getempty(wbuf);
	}

	// オブジェクトをWorkbufに追加
	wbuf->obj[wbuf->nobj] = obj;
	wbuf->nobj++;
	return wbuf;                    
}
```

*   `slottombits`は、与えられたオブジェクトのアドレスから、GCビットマップ内の対応するバイトポインタ（`bitp`）とビットシフト量（`shift`）を計算します。これにより、GCビットマップの特定のビットに効率的にアクセスできます。
*   `objectstart`は、ヒープ内の任意のアドレス（オブジェクトの途中を指す可能性もある）から、そのアドレスが属するオブジェクトの実際の開始アドレスを特定します。これは、GCがポインタをたどる際に、常にオブジェクトの先頭から情報を取得できるようにするために重要です。
*   `greyobject`は、GCのマーク処理の中心です。まだマークされていないオブジェクトを受け取り、それを「マーク済み」としてビットマップに記録します。この際、並行性を考慮してアトミック操作（`runtime·atomicor8`）を使用する場合があります。マークされたオブジェクトは、後でスキャンするために`Workbuf`にキューイングされます。`BitsDead`（noscanオブジェクト）の場合は、ポインタを含まないためスキャンをスキップします。

### `scanblock`関数のリファクタリング

`scanblock`は、メモリブロックをスキャンし、そこから見つかったポインタを処理する主要な関数です。

```c
// src/runtime/mgc0.c
static void
scanblock(byte *b, uintptr n, byte *ptrmask)
{
	Workbuf *wbuf;
	bool keepworking;

	wbuf = getpartial(); // PのローカルMCacheからWorkbufを取得
	if(b != nil) {
		wbuf = scanobject(b, n, ptrmask, wbuf); // 初期ブロックをスキャン
		if(runtime·gcphase == GCscan) { // GCscanフェーズなら、ここで終了
			putpartial(wbuf);
			return;
		}
	}

	keepworking = b == nil; // bがnilなら、グローバルキューから作業を取得し続ける

	for(;;) {
		if(wbuf->nobj == 0) { // Workbufが空なら
			if(!keepworking) { // 作業を継続する必要がなければ終了
				putempty(wbuf);
				return;
			}
			wbuf = getfull(wbuf); // グローバルキューから満杯のWorkbufを取得
			if(wbuf == nil) // 作業がなければ終了
				return;
		}

		// 他のプロセッサがポインタを欲しがっている場合、一部を渡す
		if(work.nwait > 0 && wbuf->nobj > 4 && work.full == 0) {
			wbuf = handoff(wbuf);
		}

		--wbuf->nobj; // Workbufからオブジェクトを取り出す
		b = wbuf->obj[wbuf->nobj];
		wbuf = scanobject(b, runtime·mheap.arena_used - b, nil, wbuf); // 取り出したオブジェクトをスキャン
	}
}
```

*   `scanblock`は、まずPのローカルな`MCache`から`Workbuf`を取得します。
*   もし初期のブロック`b`が与えられていれば、`scanobject`を呼び出してそのブロックをスキャンします。
*   `GCscan`フェーズの場合、初期スキャンが完了したら`putpartial`で`Workbuf`を戻し、関数を終了します。これは、`GCscan`がスタックのスキャンに特化しており、オブジェクトの再帰的なスキャンは後のフェーズで行われることを示しています。
*   メインのループでは、`Workbuf`が空になった場合、`getfull`を呼び出してグローバルキューから満杯の`Workbuf`を取得します。これは、他のGCヘルパーが生成した作業を取り込むためです。`getfull`は、すべてのGCヘルパーが作業を探している状態（GCの終了条件）を検出するバリアとしても機能します。
*   `Workbuf`からオブジェクトを取り出し、`scanobject`を呼び出してそのオブジェクトをスキャンし、そこから見つかったポインタを再び`Workbuf`にキューイングします。このプロセスが繰り返され、到達可能なすべてのオブジェクトがスキャンされます。

### GCフェーズの変更 (`runtime.h`と`mgc0.c`)

`src/runtime/runtime.h`で定義されるGCフェーズの`enum`に、`GCscan`と`GCmarktermination`が追加されました。

```c

	GCoff = 0,		// stop and start	no wb
	GCquiesce, 		// stop and start	no wb
	GCstw, 			// stop the ps		nop
	GCscan,			// scan the stacks prior to marking
	GCmark,			// mark use wbufs from GCscan and globals, scan the stacks, then go to GCtermination
	GCmarktermination,	// mark termination detection. Allocate black, Ps help out GC
	GCsweep,		// stop and start	nop
};

```c
// src/runtime/mgc0.c
void runtime·gcphasework(G *gp)
{
	switch(runtime·gcphase) {
	// ... 既存のフェーズ ...
	case GCscan:
		// scan the stack, mark the objects, put pointers in work buffers
		// hanging off the P where this is being run.
		scanstack(gp); // スタックをスキャンし、Workbufにポインタを追加
		break;
	case GCmark:
	case GCmarktermination:
		// ...
		scanstack(gp); // スタックをスキャン
		// scanstack will call shade which will populate
		// the Workbuf.
		// emptywbuf(gp) will empty it before returning
		break;
	}
	gp->gcworkdone = true;
}
```

*   `GCscan`フェーズでは、`scanstack(gp)`が呼び出され、ゴルーチン`gp`のスタックがスキャンされます。この際、オブジェクトは即座に黒くされず、ポインタは`Workbuf`にキューイングされます。
*   `GCmark`と`GCmarktermination`フェーズでも`scanstack(gp)`が呼び出されますが、これは主にGCヘルパーがスタックをスキャンして`Workbuf`を埋める役割を担います。

これらの変更により、GoのGCはより段階的かつ並行的に動作するようになり、特にSTWポーズの削減に貢献します。

## 変更の背景

Goの初期のガベージコレクションは、プログラムの実行を完全に停止させる「Stop-The-World (STW)」方式を採用していました。これはGCの実行中にアプリケーションが一時停止するため、特に大規模なアプリケーションや低レイテンシが求められるシステムでは、ユーザー体験に悪影響を与える可能性がありました。

このコミットが行われた背景には、GoのGCをより並行性の高いものへと進化させるという明確な目標がありました。並行GCは、GCの作業の一部をアプリケーションの実行と並行して行うことで、STWポーズの時間を大幅に削減することを目指します。

並行GCを実現するためには、GCがオブジェクトグラフを走査している間に、アプリケーション（ミューテーター）がポインタを変更する可能性を考慮する必要があります。このポインタの変更を追跡し、GCの正確性を保証するために導入されるのが「ライトバリア」です。しかし、ライトバリアは実行時にオーバーヘッドを発生させるため、その導入タイミングや実装の効率性が重要になります。

このコミットは、スキャンとマークのフェーズをより細かく分離し、`Workbuf`や`Markbits`といった新しいデータ構造を導入することで、並行GCとライトバリアのためのより堅牢で効率的な基盤を築こうとしています。特に、スタックのスキャンをオブジェクトの即時マークなしに行えるようにすることで、ライトバリアの適用を遅らせ、全体的なパフォーマンスを向上させる狙いがあります。

## 前提知識の解説

このコミットを理解するためには、以下のガベージコレクションに関する基本的な概念とGoランタイムの内部構造に関する知識が必要です。

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはや使用されていない（到達不可能になった）ものを自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークのリスクを低減できます。

GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
1.  **マークフェーズ (Mark Phase)**: プログラムのルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めるメモリ領域を解放し、再利用可能にします。

### Stop-The-World (STW)

STWは、GCの特定のフェーズにおいて、アプリケーションの実行を完全に停止させる期間を指します。この期間中、アプリケーションは一切処理を進めることができません。STWポーズはGCの正確性を保証するために必要ですが、その時間が長くなるとアプリケーションの応答性に悪影響を与えます。GoのGCは、このSTWポーズを最小限に抑えるように進化してきました。

### 並行GC (Concurrent GC)

並行GCは、GCの作業の一部をアプリケーションの実行と並行して行うことで、STWポーズの時間を短縮する手法です。これにより、GCが実行されている間もアプリケーションは処理を継続できるため、レイテンシの改善が期待できます。並行GCでは、GCがオブジェクトグラフを走査している間にアプリケーションがポインタを変更する可能性があるため、その変更を追跡するメカニズムが必要になります。

### ライトバリア (Write Barrier)

ライトバリアは、並行GCにおいて、ミューテーター（アプリケーションコード）がヒープ上のポインタを更新する際に実行される小さなコードスニペットです。その目的は、GCがオブジェクトグラフを走査している最中にポインタが変更され、GCが見落とす可能性のあるオブジェクト（「灰色」から「黒」への変更など）を適切に追跡することです。ライトバリアにはいくつかの種類がありますが、一般的にはポインタの書き込み時に古い値や新しい値を記録することで、GCの正確性を保証します。ライトバリアはオーバーヘッドを伴うため、その設計と実装はGCのパフォーマンスに大きく影響します。

### オブジェクトの色付け (Coloring)

マーク＆スイープGCでは、オブジェクトの状態を色で表現することがあります。
*   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GC開始時にはすべてのオブジェクトが白。
*   **灰色 (Grey)**: GCによって到達可能とマークされたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていない状態。
*   **黒 (Black)**: GCによって到達可能とマークされ、かつそのオブジェクトが参照するすべてのオブジェクトもスキャンが完了した状態。

並行GCでは、ミューテーターがポインタを更新することでオブジェクトの色が変化する可能性があり、これをライトバリアで適切に処理する必要があります。

### Goランタイムのメモリ管理

Goランタイムは独自のメモリ管理システムを持っています。
*   **ヒープ (Heap)**: プログラムが動的に確保するメモリ領域。GCの主な対象。
*   **スタック (Stack)**: 関数の呼び出しやローカル変数を格納するメモリ領域。Goのスタックは動的に伸縮します。
*   **`MSpan`**: ヒープメモリを管理するための構造体。連続したページ（Page）の集合を表します。
*   **`MCache`**: 各P（プロセッサ、OSスレッドに相当）が持つローカルなメモリキャッシュ。GC作業バッファもここに格納されます。

## 技術的詳細

このコミットの技術的詳細は、Goの並行GCの実現に向けた重要なステップを示しています。

### スキャンとマークフェーズの分離と新しいGCフェーズ

従来のマークフェーズでは、オブジェクトをスキャンしながら同時にマーク（黒くする）していました。このコミットでは、このプロセスをより細分化し、以下の新しいGCフェーズが導入されています。

*   **`GCscan`**: このフェーズでは、主にスタックやグローバル変数から到達可能なオブジェクトをスキャンし、それらを「灰色」としてマークします。重要なのは、この段階ではオブジェクトを「黒くする」ことなく、スキャンされたポインタを`Workbuf`にキューイングする点です。これにより、スタックのスキャン中にミューテーターがポインタを更新しても、ライトバリアの介入を最小限に抑えることができます。
*   **`GCmark`**: `GCscan`フェーズで収集された「灰色」のオブジェクトを`Workbuf`から取り出し、それらが参照するオブジェクトを再帰的にスキャンし、マーク（黒くする）します。このフェーズは並行して実行され、ミューテーターもGC作業に協力（ヘルプ）することができます。
*   **`GCmarktermination`**: マークフェーズの終了を検出するフェーズです。すべての到達可能なオブジェクトがマークされ、GC作業が完了したことを確認します。このフェーズでは、新しいオブジェクトの割り当ては「黒」として行われ、GCヘルパーもGC作業を継続します。

このフェーズの分離により、特にスタックのスキャンをより効率的に、かつSTWポーズを短くして実行できるようになります。

### `Workbuf`と`MCache`の役割強化

`Workbuf`は、GCがスキャンすべきオブジェクト（灰色オブジェクト）を一時的に保持するためのバッファです。このコミットでは、`MCache`（各Pのローカルキャッシュ）が`Workbuf`を直接保持するように変更され、GC作業の効率的な管理とP間の作業分散を可能にしています。

*   **`MCache.gcworkbuf`**: `void*`から`Workbuf*`に変更され、GC作業バッファが型安全に管理されるようになりました。
*   **`getpartial` / `putpartial`**: 新たに導入されたこれらの関数は、Pのローカルな`MCache`から部分的に使用された`Workbuf`を取得・解放するためのものです。これにより、GC作業の粒度を細かくし、Pが自身の作業を効率的に管理できるようになります。
*   **`getempty` / `putempty`**: 空の`Workbuf`の取得と解放を管理します。
*   **`getfull`**: グローバルな`work.full`リストから、他のPによって満たされた`Workbuf`を取得します。これは、複数のGCヘルパーが協調して作業を進めるための重要なメカニズムであり、GCの終了条件の検出にも利用されます。

### `Markbits`構造体の導入とGCビットマップの操作

`Markbits`構造体は、GCビットマップから特定のオブジェクトに関するマーク情報を効率的に抽出するための新しい抽象化です。

```c
typedef struct Markbits Markbits;
struct Markbits {
	byte *bitp; // pointer to the byte holding xbits
 	byte shift; // bits xbits needs to be shifted to get bits
	byte xbits; // byte holding all the bits from *bitp
	byte bits;  // bits relevant to corresponding slot.
};
```

*   `bitp`: GCビットマップ内の、対象オブジェクトのマーク情報を含むバイトへのポインタ。
*   `shift`: `*bitp`から対象オブジェクトのビットを抽出するためのシフト量。
*   `xbits`: `*bitp`の生の値。
*   `bits`: 対象オブジェクトに関連する実際のGCビット（マーク済み、ポインタの有無など）。

この構造体と関連する関数（`slottombits`, `objectstart`, `greyobject`）により、GCはヒープ上の任意のアドレスからオブジェクトの開始位置を特定し、そのマーク情報を効率的に読み書きできるようになります。

*   **`inheap(byte *b)`**: 与えられたアドレス`b`がGoのヒープ内に存在するかどうかをチェックします。これは、無効なポインタをGCが処理しようとするのを防ぐために重要です。
*   **`slottombits(byte *obj, Markbits *mbits)`**: オブジェクトのアドレスから、対応するGCビットマップのバイトとシフト量を計算し、`Markbits`構造体に格納します。
*   **`objectstart(byte *b, Markbits *mbits)`**: ヒープ内の任意のアドレス`b`から、そのアドレスが属するオブジェクトの開始アドレスを特定し、関連する`Markbits`情報を取得します。これは、オブジェクトの内部ポインタからでもそのオブジェクトのベースアドレスを特定できることを意味します。
*   **`greyobject(byte *obj, Markbits *mbits, Workbuf *wbuf)`**: オブジェクトがまだマークされていない場合、それをマークし（灰色にする）、`Workbuf`にキューイングします。この関数は、並行GCにおけるオブジェクトのマーク処理の中心的な部分です。アトミック操作（`runtime·atomicor8`）を使用して、複数のPが同時に同じオブジェクトをマークしようとした場合の競合を安全に解決します。
*   **`scanobject(byte *b, uintptr n, byte *ptrmask, Workbuf *wbuf)`**: 指定されたメモリブロック`b`をスキャンし、そこに含まれるポインタを識別して`greyobject`を呼び出し、`Workbuf`に追加します。`ptrmask`が`nil`の場合、GCビットマップを参照してポインタを特定します。

### `scanblock`関数のリファクタリング

`scanblock`は、メモリブロックをスキャンし、そこから見つかったポインタを処理する主要な関数です。このコミットでは、`scanblock`が`scanobject`と`Workbuf`管理関数（`getpartial`, `putpartial`, `getfull`）を組み合わせて使用するように大幅にリファクタリングされています。

```c
// src/runtime/mgc0.c
static void
scanblock(byte *b, uintptr n, byte *ptrmask)
{
	Workbuf *wbuf;
	bool keepworking;

	wbuf = getpartial(); // PのローカルMCacheからWorkbufを取得
	if(b != nil) {
		wbuf = scanobject(b, n, ptrmask, wbuf); // 初期ブロックをスキャン
		if(runtime·gcphase == GCscan) { // GCscanフェーズなら、ここで終了
			putpartial(wbuf);
			return;
		}
	}

	keepworking = b == nil; // bがnilなら、グローバルキューから作業を取得し続ける

	for(;;) {
		if(wbuf->nobj == 0) { // Workbufが空なら
			if(!keepworking) { // 作業を継続する必要がなければ終了
				putempty(wbuf);
				return;
			}
			wbuf = getfull(wbuf); // グローバルキューから満杯のWorkbufを取得
			if(wbuf == nil) // 作業がなければ終了
				return;
		}

		// 他のプロセッサがポインタを欲しがっている場合、一部を渡す
		if(work.nwait > 0 && wbuf->nobj > 4 && work.full == 0) {
			wbuf = handoff(wbuf);
		}

		--wbuf->nobj; // Workbufからオブジェクトを取り出す
		b = wbuf->obj[wbuf->nobj];
		wbuf = scanobject(b, runtime·mheap.arena_used - b, nil, wbuf); // 取り出したオブジェクトをスキャン
	}
}
```

*   `scanblock`は、まずPのローカルな`MCache`から`Workbuf`を取得します。
*   もし初期のブロック`b`が与えられていれば、`scanobject`を呼び出してそのブロックをスキャンします。
*   `GCscan`フェーズの場合、初期スキャンが完了したら`putpartial`で`Workbuf`を戻し、関数を終了します。これは、`GCscan`がスタックのスキャンに特化しており、オブジェクトの再帰的なスキャンは後のフェーズで行われることを示しています。
*   メインのループでは、`Workbuf`が空になった場合、`getfull`を呼び出してグローバルキューから満杯の`Workbuf`を取得します。これは、他のGCヘルパーが生成した作業を取り込むためです。`getfull`は、すべてのGCヘルパーが作業を探している状態（GCの終了条件）を検出するバリアとしても機能します。
*   `Workbuf`からオブジェクトを取り出し、`scanobject`を呼び出してそのオブジェクトをスキャンし、そこから見つかったポインタを再び`Workbuf`にキューイングします。このプロセスが繰り返され、到達可能なすべてのオブジェクトがスキャンされます。

### GCフェーズの変更 (`runtime.h`と`mgc0.c`)

`src/runtime/runtime.h`で定義されるGCフェーズの`enum`に、`GCscan`と`GCmarktermination`が追加されました。

```c
// src/runtime/runtime.h
enum {                               // Action               WB installation
	GCoff = 0,		// stop and start	no wb
	GCquiesce, 		// stop and start	no wb
	GCstw, 			// stop the ps		nop
	GCscan,			// scan the stacks prior to marking
	GCmark,			// mark use wbufs from GCscan and globals, scan the stacks, then go to GCtermination
	GCmarktermination,	// mark termination detection. Allocate black, Ps help out GC
	GCsweep,		// stop and start	nop
};
```

そして、`src/runtime/mgc0.c`の`runtime·gcphasework`関数で、これらの新しいフェーズが処理されます。

```c
// src/runtime/mgc0.c
void runtime·gcphasework(G *gp)
{
	switch(runtime·gcphase) {
	// ... 既存のフェーズ ...
	case GCscan:
		// scan the stack, mark the objects, put pointers in work buffers
		// hanging off the P where this is being run.
		scanstack(gp); // スタックをスキャンし、Workbufにポインタを追加
		break;
	case GCmark:
	case GCmarktermination:
		// ...
		scanstack(gp); // スタックをスキャン
		// scanstack will call shade which will populate
		// the Workbuf.
		// emptywbuf(gp) will empty it before returning
		break;
	}
	gp->gcworkdone = true;
}
```

*   `GCscan`フェーズでは、`scanstack(gp)`が呼び出され、ゴルーチン`gp`のスタックがスキャンされます。この際、オブジェクトは即座に黒くされず、ポインタは`Workbuf`にキューイングされます。
*   `GCmark`と`GCmarktermination`フェーズでも`scanstack(gp)`が呼び出されますが、これは主にGCヘルパーがスタックをスキャンして`Workbuf`を埋める役割を担います。

これらの変更により、GoのGCはより段階的かつ並行的に動作するようになり、特にSTWポーズの削減に貢献します。

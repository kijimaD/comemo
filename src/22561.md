## 変更の背景
このコミットは、Go言語のランタイムがWindows/386（32ビットWindows）環境で外部リンキングをより適切にサポートするための準備として行われました。コミットメッセージにある通り、「windows/386も外部名にアンダースコアプレフィックスを必要とする」という、特定のプラットフォームにおけるリンキング規則への対応が主な目的です。

具体的には、32ビットWindows環境のCコンパイラ（MinGWなどで使用されるものを含む）は、`__cdecl`呼び出し規約を使用するC関数に対して、リンカーがシンボル名に先頭アンダースコア（`_`）を付加する慣習があります。これは、リンキングプロセスを円滑に進めるための名前修飾（name mangling）の一部です。GoプログラムがC言語で書かれたライブラリと連携する場合や、Goの関数が外部のCコードから呼び出される場合、Goのシンボル名がこのWindowsのリンキング規則に準拠している必要があります。

この変更は、Goの`main`関数（プログラムのエントリポイント）のシンボル名を、Windows/386環境で外部リンカーが期待する`_main`という形式に合わせることで、GoとC言語間の相互運用性（FFI: Foreign Function Interface）を向上させるための基盤を構築しています。これにより、Goプログラムが外部のCライブラリをよりシームレスに利用できるようになり、またGoの関数をCから呼び出す際の互換性も確保されます。

## 前提知識の解説
*   **リンキング (Linking)**: コンパイルされた複数のオブジェクトファイルやライブラリを結合し、最終的に実行可能なプログラムを生成するプロセスです。リンカーは、プログラム内の関数や変数の参照（シンボル）を解決し、それらがメモリ上のどこに配置されるかを決定します。
*   **シンボル (Symbol)**: プログラム内で定義された関数名、変数名、またはその他のコードやデータの参照可能な名前です。リンカーはこれらのシンボルを使って、異なるコンパイル単位（オブジェクトファイル）間で定義された要素を参照します。
*   **外部リンキング (External Linking)**: GoプログラムがC/C++などの他の言語で書かれたライブラリと連携したり、Goプログラム自体が他の言語から呼び出されることを可能にする機能です。これには、異なるコンパイラやリンカーが生成するシンボル名の規則を理解し、適切に変換する必要があります。Goでは主に`cgo`ツールを通じてこの機能が提供されます。
*   **シンボル名の修飾 (Name Decoration / Name Mangling)**: コンパイラやリンカーが、プログラミング言語のシンボル（関数名、変数名など）を、リンカーが処理できる一意の形式に変換するプロセスです。特にC++では、関数オーバーロードなどを区別するために複雑なマングリングが行われます。C言語やGo言語では比較的単純ですが、プラットフォームやABI（Application Binary Interface）によって特定のプレフィックス（例: アンダースコア）が付加されることがあります。
*   **ABI (Application Binary Interface)**: オペレーティングシステムとプログラム、またはプログラムの異なるモジュール間で、バイナリレベルでの互換性を定義する一連の規則です。これには、関数呼び出し規約（引数の渡し方、戻り値の受け取り方）、データ型のメモリ配置、シンボル名の修飾規則などが含まれます。ABIは、異なるコンパイラでコンパイルされたコードが互いに連携できるようにするために重要です。
*   **Windows/386 (x86)**: Windowsオペレーティングシステムが動作するIntel 80386互換の32ビットアーキテクチャを指します。この環境では、C言語の呼び出し規約（例: `__cdecl`, `__stdcall`）やリンキング規則が、シンボル名に特定のプレフィックスを要求することが一般的です。特に、`_`（アンダースコア）が関数名の前に付加されることがよくあります。これは、32ビットWindowsのC ABIの特性です。64ビットWindowsでは通常、このアンダースコアプレフィックスは使用されません。
*   **`rt0_windows_386.s`**: Goランタイムの初期化コードの一部で、Windows/386アーキテクチャ向けのスタートアップルーチンをアセンブリ言語で記述したファイルです。プログラムが実行を開始する際に最初に実行されるコードであり、Goランタイムの初期化や`main`関数の呼び出しなどを行います。
*   **`main`関数と`_main`関数**: C言語の慣習では、プログラムのエントリポイントは通常`main`という名前の関数です。しかし、32ビットWindowsのリンカーや特定の呼び出し規約では、この`main`関数がリンキング時に`_main`として扱われることがあります。これは、リンカーがシンボルを解決する際に、特定のプラットフォーム固有のABI規則に従うためです。

## 技術的詳細
このコミットは、GoランタイムがWindows/386環境で外部リンキングをサポートする上で、シンボル名の互換性問題を解決するためのものです。

32ビットWindows環境では、C言語のコンパイラ（例えばGCCベースのMinGWなど）が生成するオブジェクトファイルにおいて、`__cdecl`呼び出し規約を使用するグローバル関数シンボルには、慣習的に先頭にアンダースコア（`_`）が付加されます。例えば、C言語で定義された`myFunction`という関数は、コンパイル後のオブジェクトファイルでは`_myFunction`というシンボル名でエクスポートされます。リンカーは、この修飾されたシンボル名を用いて関数呼び出しを解決します。

Goのランタイムは、プログラムのエントリポイントとして内部的に`main`というシンボルを使用しています。しかし、Goプログラムが外部のCライブラリとリンクする場合、またはGoの関数が外部のCコードから呼び出される場合、WindowsのリンカーはGoの`main`シンボルを`_main`として期待する可能性があります。もしGoのランタイムが`main`というシンボル名でエクスポートし、外部リンカーが`_main`を期待すると、シンボル解決の不一致が発生し、リンクエラーや実行時エラーにつながる可能性があります。

このコミットでは、`src/runtime/rt0_windows_386.s`ファイル内のアセンブリコードを変更することで、この問題を解決しています。具体的には、Goランタイムが内部的に使用する`main`シンボルを`_main`に変更しています。

*   `JMP main(SB)` を `JMP _main(SB)` に変更: これは、Goランタイムの初期エントリポイントから、実際のGoプログラムの初期化処理を行う関数へのジャンプ命令です。この変更により、ジャンプ先が`_main`というシンボル名に変わります。
*   `TEXT main(SB),NOSPLIT,$0` を `TEXT _main(SB),NOSPLIT,$0` に変更: これは、Goランタイムの`main`関数の定義です。この変更により、この関数のシンボル名自体が`_main`に変更されます。

これらの変更により、GoのランタイムがWindows/386環境で生成する実行ファイルは、外部リンカーが期待するシンボル名規則（特に`_main`）に準拠するようになります。これにより、GoプログラムがCライブラリを呼び出したり、Goの関数をCから呼び出したりする際に、シンボル解決の互換性が確保され、外部リンキングが円滑に行えるようになります。

この変更は、Goのクロスコンパイル能力と、異なる言語間での相互運用性（FFI）を向上させるための重要な基盤となります。特に、Windows環境でのGoアプリケーションの開発において、C/C++で書かれた既存のライブラリ資産を活用する道を開くものです。`cgo`ツールは、このようなプラットフォーム固有のシンボル名修飾を自動的に処理しますが、ランタイム自体がこの規則に準拠することで、より堅牢な外部リンキングが可能になります。

## コアとなるコードの変更箇所
`src/runtime/rt0_windows_386.s`ファイルにおいて、以下の2箇所が変更されています。

1.  `JMP main(SB)` が `JMP _main(SB)` に変更。
2.  `TEXT main(SB),NOSPLIT,$0` が `TEXT _main(SB),NOSPLIT,$0` に変更。

## コアとなるコードの解説
`src/runtime/rt0_windows_386.s`は、GoプログラムがWindows/386環境で起動する際のエントリポイントとなるアセンブリコードです。このファイルは、OSから最初に制御を受け取り、Goランタイムの初期化に必要な準備を行い、最終的にGoの`main`関数（このコミット後は`_main`）に制御を渡す役割を担っています。

*   **`TEXT _rt0_386_windows(SB),NOSPLIT,$12`**:
    *   これは、GoプログラムがOSから最初に制御を受け取る関数（エントリポイント）の定義です。
    *   `TEXT`はアセンブリ言語で関数を定義するためのディレクティブです。
    *   `_rt0_386_windows`は、この関数の名前です。
    *   `SB`はStatic Baseを意味し、グローバルシンボルを参照する際に使用されます。
    *   `NOSPLIT`は、この関数がスタックフレームを必要としないことを示します。
    *   `$12`は、この関数のスタックフレームサイズが12バイトであることを示します。
    *   この関数は、Goランタイムの初期化に必要なレジスタの設定やスタックの準備などを行います。

*   **`JMP main(SB)` から `JMP _main(SB)` への変更**:
    *   `JMP`はアセンブリ言語のジャンプ命令で、指定されたアドレスにプログラムの実行フローを移します。
    *   変更前は`main(SB)`というシンボルにジャンプしていました。これはGoランタイムの内部的な`main`関数を指します。
    *   変更後は`_main(SB)`というシンボルにジャンプするようになります。
    *   この変更は、OSからの初期エントリポイントである`_rt0_386_windows`から、Goランタイムの実際の初期化処理を行う`main`関数（変更後は`_main`）へ制御を移す役割を果たしています。Windows/386のリンキング規則に合わせ、`main`シンボルを`_main`として参照するようになります。

*   **`TEXT main(SB),NOSPLIT,$0` から `TEXT _main(SB),NOSPLIT,$0` への変更**:
    *   変更前は`main(SB)`というシンボル名で関数が定義されていました。
    *   変更後は`_main(SB)`というシンボル名で関数が定義されるようになります。
    *   この関数は、最終的に`JMP runtime·rt0_go(SB)`という命令を実行し、Goランタイムのより詳細な初期化プロセス（ガベージコレクションの初期化、スケジューラの起動など）を開始する`runtime·rt0_go`関数に制御を渡します。
    *   この変更により、Goランタイムの内部的なエントリポイントのシンボル名が、Windows/386のリンキング規則に準拠する`_main`に統一されます。

これらの変更は、GoプログラムがWindows/386環境で外部リンキングを円滑に行うために、シンボル名の互換性を確保することを目的としています。これにより、Goの実行ファイルが外部のC/C++ライブラリと正しくリンクできるようになり、また外部からGoの関数を呼び出す際のシンボル解決の問題が解消されます。

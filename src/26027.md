## 変更の背景

Go言語のガベージコレクタは、並行マーク・アンド・スイープ方式を採用しており、プログラムの実行と並行してガベージコレクション（GC）を行います。この並行GCの正確性を保証するために、「ライトバリア（Write Barrier）」というメカニズムが非常に重要になります。

ライトバリアは、ヒープ上のポインタが変更される際に、GCがオブジェクトの参照関係を正しく追跡できるようにするためのフックです。特に、GCがマークフェーズにある間にプログラムがポインタを書き換えると、GCがまだマークしていないオブジェクトへの参照が失われ、誤って回収されてしまう（Dangling Pointer）可能性があります。これを防ぐために、ポインタの書き込み時にライトバリアが発動し、GCにその変更を通知したり、必要なオブジェクトをマークしたりします。

このコミット以前は、Goコンパイラにおいて、関数の戻り値がヒープにエスケープする（つまり、スタックではなくヒープに割り当てられる）場合、その戻り値を結果パラメータにコピーする際にライトバリアが適切に挿入されていませんでした。結果パラメータがヒープにエスケープしている場合、そのパラメータへの書き込みはヒープへのポインタ書き込みと見なされるため、ライトバリアが必要となります。この欠落は、特定の条件下でガベージコレクタの不正確な動作を引き起こし、メモリ破損やクラッシュにつながる可能性がありました。

`Fixes #13587` と記載されていますが、Goの公式イシュートラッカーでこの番号の具体的なイシューを見つけることはできませんでした。しかし、コミットメッセージから、この変更がガベージコレクションの正確性に関わる重要なバグ修正であったことは明らかです。

## 前提知識の解説

### 1. Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク・アンド・スイープ（Tri-color Mark-and-Sweep）」アルゴリズムをベースにしています。

*   **三色抽象化**:
    *   **白 (White)**: GCによってまだ発見されていないオブジェクト、または回収対象のオブジェクト。
    *   **灰 (Gray)**: GCによって発見されたが、その参照先（子オブジェクト）がまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって発見され、その参照先もすべてスキャンされたオブジェクト。回収対象ではない。
*   **マークフェーズ**: GCはルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトをスキャンし、白から灰、灰から黒へと色を塗っていきます。
*   **スイープフェーズ**: マークされなかった白いオブジェクト（到達不可能なオブジェクト）をメモリから解放します。
*   **並行GC**: GoのGCは、プログラムの実行と並行してマークフェーズの大部分を実行します。これにより、プログラムの一時停止時間（Stop-The-World, STW）を最小限に抑えます。

### 2. ライトバリア (Write Barrier)

並行GCにおいて、プログラムがヒープ上のポインタを書き換える際に、GCの正確性を保証するためのメカニズムです。

*   **目的**: GCがオブジェクトグラフをスキャンしている最中に、プログラムがポインタを書き換えることで、GCがまだマークしていないオブジェクトへの参照が失われる「Dangling Pointer」問題を防ぎます。
*   **動作**: ポインタの書き込み操作（例: `*ptr = new_value`）が行われる直前または直後に、GCランタイムのフックが呼び出されます。このフックは、書き込まれる値（`new_value`）がGCによってマークされていることを確認したり、必要に応じてマークしたりします。GoのGCでは、一般的に「Dijkstraのライトバリア」の変種が使用され、新しいポインタが指すオブジェクトを灰色にマークします。

### 3. エスケープ解析 (Escape Analysis)

Goコンパイラが行う最適化の一つで、変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを決定します。

*   **スタック**: 関数の呼び出し時に確保され、関数が終了すると自動的に解放されるメモリ領域。高速で、GCの対象外。
*   **ヒープ**: プログラム実行中に動的に確保・解放されるメモリ領域。GCの対象。
*   **エスケープ**: 変数がその変数を宣言したスコープ（関数）の寿命を超えて参照される可能性がある場合、その変数はヒープに「エスケープ」すると判断されます。例えば、関数の戻り値としてポインタが返される場合や、グローバル変数に代入される場合などです。
*   **重要性**: エスケープ解析は、不要なヒープ割り当てを減らし、GCの負荷を軽減することで、プログラムのパフォーマンスを向上させます。

### 4. 戻り値と結果パラメータ

Goの関数は、名前付きの戻り値を持つことができます。

```go
func F() (err error) {
    // err は F の結果パラメータであり、関数内で変数として扱える
    err = errors.New("some error")
    return // err の現在の値が戻り値となる
}
```
この `err` のような結果パラメータは、関数内で通常の変数として扱われます。もしこの `err` がヒープにエスケープするとコンパイラが判断した場合、その `err` への代入（例: `err = errors.New("some error")`）は、ヒープ上のポインタへの書き込みと見なされるため、ライトバリアが必要になります。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのコード生成フェーズにおけるライトバリアの挿入ロジックにあります。

Goコンパイラは、ソースコードを抽象構文木（AST）に変換し、その後、中間表現（IR）を経て、最終的に機械語コードを生成します。この過程で、エスケープ解析が行われ、どの変数がヒープに割り当てられるべきかが決定されます。

問題となっていたのは、`return` ステートメントの処理です。Goの関数が値を返す際、その戻り値は一時的に保持され、最終的に呼び出し元に渡されます。名前付きの結果パラメータがある場合、`return` ステートメントは、結果パラメータの現在の値を戻り値として使用します。

コンパイラは、`return` ステートメントを内部的に一連の代入操作として扱います。例えば、`return expr` は、`result_param = expr; goto end_of_function;` のような形に変換されます。ここで、もし `result_param` がエスケープ解析によってヒープに割り当てられていると判断された場合、`result_param = expr` という代入は、ヒープ上のポインタへの書き込みとなります。

このコミット以前は、この `result_param = expr` のような代入に対して、ライトバリアが適切に挿入されていませんでした。特に、`expr` が新しいオブジェクトを生成し、そのポインタが `result_param` に代入されるようなケースで問題が発生しました。GCがマークフェーズ中にこの代入が行われると、`expr` が指す新しいオブジェクトがGCによってマークされる前に `result_param` に代入され、GCがそのオブジェクトを見落とす可能性がありました。

この修正は、`walkstmt` 関数内で `return` ステートメントを処理する際に、戻り値のリスト（`n.List`）をイテレートし、それぞれの戻り値に対して `applywritebarrier` を呼び出すことで、この問題を解決しています。これにより、ヒープにエスケープした結果パラメータへの代入がライトバリアによって保護され、GCの正確性が保証されるようになりました。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/walk.go` は、Goコンパイラの「ウォーク（walk）」フェーズを担当するファイルです。このフェーズでは、ASTを走査し、最適化やコード変換を行います。

変更が加えられたのは `walkstmt` 関数内の `case ORETURN:` ブロックです。
`walkstmt` 関数は、各ステートメントノードを処理します。`ORETURN` は `return` ステートメントを表します。

1.  `ll := ascompatee(n.Op, rl, n.List, &n.Ninit)`:
    *   `ascompatee` 関数は、`return` ステートメントの戻り値を、対応する結果パラメータへの代入として表現するノードリストを生成します。`n.List` は `return` ステートメントの引数リスト（例: `return a, b` の `a, b`）です。`rl` は関数の結果パラメータのリストです。
    *   この行で、`return` ステートメントが、結果パラメータへの暗黙的な代入のシーケンスに変換されます。

2.  `n.List = reorder3(ll)`:
    *   `reorder3` 関数は、生成された代入ノードのリストを最適化し、実行順序を調整します。

3.  **追加されたコード**:
    ```go
    for lr := n.List; lr != nil; lr = lr.Next {
        lr.N = applywritebarrier(lr.N, &n.Ninit)
    }
    ```
    *   このループは、`ascompatee` によって生成され、`reorder3` によって並べ替えられた、結果パラメータへの各代入ノード（`lr.N`）をイテレートします。
    *   `applywritebarrier(lr.N, &n.Ninit)` が呼び出されます。この関数は、与えられたノード `lr.N` がポインタの書き込み操作である場合、その操作の前にライトバリアを挿入するようにコンパイラに指示します。`n.Ninit` は、ステートメントの初期化リストであり、ライトバリアのコードが挿入される場所を示します。
    *   これにより、`return` ステートメントによって行われる、ヒープにエスケープした結果パラメータへのすべての代入が、ライトバリアによって適切に保護されるようになります。

### テストファイル `test/fixedbugs/issue13587.go` の解説

この新しいテストファイルは、修正が正しく機能することを確認するために追加されました。

```go
// errorcheck -0 -l -d=wb

package issue13587

import "errors"

func escape(p *error)

func F() (err error) {
	escape(&err)
	return errors.New("error") // ERROR "write barrier"
}
```

*   `// errorcheck -0 -l -d=wb`: これはコンパイラテストのディレクティブです。
    *   `-0`: 最適化を無効にします。
    *   `-l`: インライン化を無効にします。
    *   `-d=wb`: ライトバリアのデバッグ情報を出力するようにコンパイラに指示します。
*   `func escape(p *error)`: この関数は、`err` 変数のアドレスを引数として受け取ります。これにより、コンパイラは `err` が関数 `F` のスコープを超えて参照される可能性があると判断し、`err` をヒープにエスケープさせます。
*   `func F() (err error) { ... }`: 名前付き戻り値 `err` を持つ関数です。
*   `escape(&err)`: `err` のアドレスを `escape` 関数に渡すことで、`err` がヒープにエスケープするように強制します。
*   `return errors.New("error")`: ここで、新しい `error` オブジェクトが作成され、そのポインタがヒープにエスケープした `err` 変数に代入されます。
*   `// ERROR "write barrier"`: このコメントは、コンパイラがこの行でライトバリアを挿入すること（または、ライトバリアのデバッグ出力にその旨が表示されること）を期待していることを示します。もしライトバリアが挿入されていなければ、テストは失敗します。

このテストは、ヒープにエスケープした結果パラメータへの戻り値の代入に対して、ライトバリアが正しく適用されることを検証するものです。

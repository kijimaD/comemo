# [インデックス 28072] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile`) におけるガベージコレクション (GC) のライブネス情報シンボル (`gclocals` および `gcargs`) の重複排除に関する改善を導入しています。これまでリンカで行われていた重複排除の一部をコンパイラ側で先行して行うことで、リンカの負荷を軽減し、全体的なコンパイルプロセスの効率化を図っています。

## 元コミット内容

このコミットは、Goコンパイラが生成する `gclocals` シンボルの重複を、リンカだけでなくコンパイラ自身でも排除するように変更します。これにより、リンカの作業負荷が軽減されます。

具体的には、`src/cmd/compile/internal/gc/pgen.go` から `gcsymdup` 関数とその呼び出しを削除し、`src/cmd/compile/internal/gc/plive.go` の `onebitwritesymbol` 関数内に同様の重複排除ロジックを移動・統合しています。また、`src/cmd/compile/internal/gc/ssa.go` からも `gcsymdup` の呼び出しが削除されています。

## 変更の背景

Goのコンパイルプロセスでは、ガベージコレクションのために、関数の引数 (`gcargs`) やローカル変数 (`gclocals`) のライブネス情報（どの時点でどの変数が生きているか）を記述したシンボルが生成されます。これらのシンボルは、同じライブネスパターンを持つ場合でも、コンパイラによって重複して生成されることがありました。

コミットメッセージによると、`runtime.a` のようなライブラリでは、全シンボル13769個のうち2425個がこれらの重複した `gclocals` シンボルであったと報告されています。これまでは、リンカが最終的にこれらの重複を排除していましたが、コンパイラが大量の重複シンボルを生成することは、リンカにとって不必要な作業負荷となっていました。

この変更の目的は、重複排除のプロセスをコンパイルのより早い段階（シンボルが生成される際）に移動させることで、リンカの負担を軽減し、コンパイル全体の効率を向上させることです。これにより、中間生成物（オブジェクトファイル）のサイズが削減され、リンカの処理速度が向上する可能性があります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールです。このプロセス中に、ガベージコレクションに必要なメタデータも生成します。
*   **Goリンカ (`cmd/link`)**: コンパイラが生成したオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成するツールです。この過程で、シンボルの解決や重複排除が行われます。
*   **ガベージコレクション (GC)**: プログラムが使用しなくなったメモリを自動的に解放する仕組みです。GoのGCは、正確なGC (precise GC) であり、どのメモリ領域がポインタを含んでいるかを正確に知る必要があります。
*   **ライブネス情報**: GCが正しく動作するために不可欠な情報です。特定のプログラム実行ポイントにおいて、どの変数がまだ使用される可能性があるか（「生きている」か）を示します。
*   **`gclocals` シンボル**: 関数のローカル変数のライブネス情報を示すシンボルです。各関数には、そのローカル変数のライブネスパターンを記述したビットマップが関連付けられます。
*   **`gcargs` シンボル**: 関数の引数のライブネス情報を示すシンボルです。
*   **シンボルの重複排除 (De-duplication)**: 同じ内容を持つシンボルが複数存在する場合に、それらを一つにまとめるプロセスです。これにより、バイナリサイズを削減し、リンカの処理を高速化できます。
*   **MD5ハッシュ**: データのハッシュ値を計算するアルゴリズムの一つです。このコミットでは、シンボルの内容が同じかどうかを効率的に比較するために使用されています。
*   **`obj.Dupok`**: Goのオブジェクトファイルフォーマットにおけるシンボルフラグの一つで、このシンボルが重複しても問題ないことをリンカに伝えます。リンカは `Dupok` が設定されたシンボルの中から一つを選んで使用します。
*   **`Ctxt.Hash`**: コンパイラ内部でシンボルを管理するためのハッシュマップです。シンボル名とバージョンをキーとして、対応するリンカシンボル (`obj.LSym`) を格納します。

## 技術的詳細

このコミットの核心は、`gclocals` および `gcargs` シンボルの重複排除ロジックを、リンカからコンパイラのより深い部分へ移動させた点にあります。

以前のコンパイラでは、`gcsymdup` 関数が `pgen.go` に存在し、`genlegacy` 関数や `genssa` 関数内で `gclocals` および `gcargs` シンボルに対して呼び出されていました。この `gcsymdup` 関数は、シンボルの内容（バイト列 `ls.P`）のMD5ハッシュを計算し、そのハッシュ値を使ってシンボル名を `gclocals·%x` の形式にリネームし、`ls.Dupok = true` を設定していました。これにより、リンカは同じMD5ハッシュを持つシンボルを重複として扱い、一つにまとめることができました。

しかし、このアプローチでは、コンパイラはまず重複したシンボルを生成し、それらをオブジェクトファイルに書き出し、その後リンカがそれらを読み込んで重複排除するという二段階のプロセスを踏んでいました。

今回の変更では、`gcsymdup` 関数自体が削除され、そのロジックが `plive.go` 内の `onebitwritesymbol` 関数に移動されました。`onebitwritesymbol` は、GCライブネスビットマップを実際に書き込む際に呼び出される関数です。

新しいロジックでは、`onebitwritesymbol` がシンボルを受け取ると、以下の処理を行います。
1.  シンボルの内容 (`ls.P`) のMD5ハッシュを計算し、それを用いてシンボル名を `gclocals·%x` の形式に設定します。
2.  `ls.Dupok = true` を設定し、リンカに重複を許可することを伝えます。
3.  `Ctxt.Hash` マップをチェックし、同じ名前とバージョンを持つシンボルが既に存在するかどうかを確認します。
    *   もし存在すれば、現在のシンボル (`sym.Lsym`) を既存のシンボルに置き換えます。これにより、物理的に同じ内容のシンボルが複数生成されることを防ぎます。
    *   存在しない場合は、現在のシンボルを `Ctxt.Hash` に追加し、通常通りグローバルシンボルとして書き出します。

この変更により、コンパイラはシンボルを生成する段階で、既に同じ内容のシンボルが生成されていないかをチェックし、もしあれば既存のシンボルを再利用するようになります。これにより、オブジェクトファイルに書き出されるシンボルの数が減り、リンカが処理するシンボルの数も削減されます。結果として、コンパイル時間の短縮や中間ファイルのサイズの削減が期待できます。

*   `genssa` 関数内での `gcsymdup(gcargs)` および `gcsymdup(gclocals)` の呼び出し削除。

## コアとなるコードの解説

変更の核となるのは `src/cmd/compile/internal/gc/plive.go` の `onebitwritesymbol` 関数内の以下の追加コードです。

```go
	ls := Linksym(sym)
	ls.Name = fmt.Sprintf("gclocals·%x", md5.Sum(ls.P))
	ls.Dupok = true
	sv := obj.SymVer{ls.Name, 0}
	ls2, ok := Ctxt.Hash[sv]
	if ok {
		sym.Lsym = ls2
	} else {
		Ctxt.Hash[sv] = ls
		ggloblsym(sym, int32(off), obj.RODATA)
	}
```

1.  `ls := Linksym(sym)`: 現在処理しているシンボル `sym` に対応するリンカシンボル (`obj.LSym`) を取得します。
2.  `ls.Name = fmt.Sprintf("gclocals·%x", md5.Sum(ls.P))`: リンカシンボルの名前を、その内容 (`ls.P`、つまりライブネスビットマップのバイト列) のMD5ハッシュ値に基づいた形式に設定します。これにより、内容が同じシンボルは同じ名前を持つことになります。
3.  `ls.Dupok = true`: このシンボルが重複してもリンカがエラーとせず、重複排除の対象とすることを明示します。
4.  `sv := obj.SymVer{ls.Name, 0}`: シンボル名とバージョン（ここでは0）を組み合わせたキーを作成します。
5.  `ls2, ok := Ctxt.Hash[sv]`: コンパイラが保持するハッシュマップ `Ctxt.Hash` を検索し、同じ名前（つまり同じ内容）のシンボルが既に登録されているかを確認します。
6.  `if ok { sym.Lsym = ls2 }`: もし同じ名前のシンボル `ls2` が既に存在すれば、現在処理中のシンボル `sym` のリンカシンボルを、既存の `ls2` に置き換えます。これにより、新しい重複シンボルを生成する代わりに、既存のシンボルを指すようにします。
7.  `else { Ctxt.Hash[sv] = ls; ggloblsym(sym, int32(off), obj.RODATA) }`: 既存のシンボルが存在しない場合、現在のシンボル `ls` を `Ctxt.Hash` に登録し、`ggloblsym` を呼び出してグローバルシンボルとしてオブジェクトファイルに書き出す準備をします。

このロジックにより、コンパイラはライブネスビットマップを生成する時点で、その内容が既に生成された他のビットマップと同一であれば、新しいシンボルを生成せずに既存のシンボルを再利用するようになります。これにより、オブジェクトファイル内の重複シンボルが大幅に削減され、リンカの処理が効率化されます。

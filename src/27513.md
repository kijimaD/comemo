# [インデックス 27513] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTP/2のアップグレードリクエスト、特にクライアントプリフェース（"PRI * HTTP/2.0\\r\\n\\r\\nSM\\r\\n\\r\\n"）をハンドラが処理できるようにするための変更です。これにより、GoのHTTPサーバーがHTTP/2の直接接続（h2c）をより適切にサポートできるようになります。

    net/http: allow Handlers to handle http2 upgrade PRI requests

    The http2 spec defines a magic string which initates an http2 session:

        "PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n"

    It was intentionally chosen to kinda look like an HTTP request, but
    just different enough to break things not ready for it. This change
    makes Go ready for it.

    Notably: Go now accepts the request header (the prefix "PRI *"
    HTTP/2.0\r\n\r\n") as a valid request, even though it doesn't have a
    Host header. But we now mark it as "Connection: close" and teach the
    Server to never read a second request from the connection once that's
    seen. If the http.Handler wants to deal with the upgrade, it has to
    hijack the request, read out the "body", compare it against
    "SM\r\n\r\n", and then speak http2. One of the new tests demonstrates
    that hijacking.

    Updates #14141 (h2c)

## 元コミット内容

Goの`net/http`パッケージにおいて、HTTP/2のアップグレードリクエストである「PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n」というマジック文字列をハンドラが処理できるようにする変更。このマジック文字列はHTTP/2セッションを開始するために定義されており、通常のHTTPリクエストとは異なる形式を持つため、既存のHTTPサーバーでは問題となる可能性があった。このコミットにより、Goのサーバーはこの特殊なリクエストを有効なものとして認識し、`Host`ヘッダがない場合でも受け入れるようになる。ただし、このリクエストは`Connection: close`として扱われ、サーバーは一度このリクエストを処理したら、そのコネクションから2番目のリクエストを読み込まないようにする。ハンドラがHTTP/2へのアップグレードを処理したい場合は、コネクションをハイジャックし、残りの「SM\r\n\r\n」というボディを読み取り、その後HTTP/2プロトコルで通信する必要がある。

## 変更の背景

HTTP/2プロトコルは、既存のHTTP/1.xプロトコルとは異なるバイナリフレーミング層を使用しており、セッションの開始方法も複数存在します。その一つが、HTTP/1.xのコネクション上でHTTP/2にアップグレードする「h2c (HTTP/2 Cleartext)」と呼ばれるメカニズムです。h2cでは、クライアントがサーバーに対して特別な「クライアントプリフェース」と呼ばれるマジック文字列を送信することで、HTTP/2セッションの開始を試みます。

このマジック文字列は、`"PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n"`という形式をしており、これは意図的に通常のHTTP/1.xリクエストに似せつつも、既存のパーサーが誤って解釈しないように設計されています。しかし、この形式はいくつかの点で通常のHTTP/1.xリクエストの要件を満たしません。特に、`Host`ヘッダが存在しない点が問題となります。

Goの`net/http`サーバーは、HTTP/1.1以降のリクエストに対して`Host`ヘッダの存在を必須としていました。そのため、このHTTP/2クライアントプリフェースが送信されると、サーバーはこれを不正なリクエストとして拒否してしまう可能性がありました。このコミットの背景には、GoのHTTPサーバーがh2cを適切にサポートし、HTTP/2クライアントプリフェースを正しく処理できるようにするという目的があります。これにより、GoアプリケーションがHTTP/2の恩恵をより広範に受けられるようになります。

## 前提知識の解説

### HTTP/2 (Hypertext Transfer Protocol Version 2)
HTTP/2は、HTTP/1.xのセマンティクスを維持しつつ、パフォーマンスを向上させるために設計されたプロトコルです。主な特徴として、バイナリフレーミング、多重化（Multiplexing）、ヘッダ圧縮（HPACK）、サーバープッシュなどがあります。これにより、複数のリクエストとレスポンスを同時に処理し、ネットワークの効率を向上させることができます。

### HTTP/2 クライアントプリフェース (Client Preface)
HTTP/2セッションを開始するための特別なシーケンスです。特に、TLSを使用しないHTTP/2接続（h2c）の場合にクライアントがサーバーに送信します。これは24オクテットのマジック文字列で構成されており、以下の2つの部分からなります。
1.  **接続プリフェース (Connection Preface)**: `"PRI * HTTP/2.0\r\n\r\n"`
    これはHTTP/1.1のリクエストラインに似ていますが、`Method`が`PRI`、`Request-Target`が`*`、`HTTP-Version`が`HTTP/2.0`という特殊な形式です。この部分の後に、HTTP/1.xのヘッダブロックが続くかのように見えますが、実際には空のヘッダブロックが続きます。
2.  **設定フレーム (SETTINGS frame)**: `SM\r\n\r\n`
    これはHTTP/2の最初のフレームであり、バイナリ形式でエンコードされた`SETTINGS`フレームです。

この全体のマジック文字列は、既存のHTTP/1.xサーバーがこれを通常のHTTPリクエストとして解釈しないように、しかしHTTP/1.xのパーサーが完全に壊れないように巧妙に設計されています。

### h2c (HTTP/2 Cleartext)
TLSを使用しないHTTP/2接続を指します。通常、HTTP/2はTLS上で動作するh2が一般的ですが、h2cは既存のHTTP/1.1コネクションをHTTP/2にアップグレードするか、直接HTTP/2クライアントプリフェースを送信することで開始されます。このコミットは、後者の直接接続のシナリオに対応するためのものです。

### `net/http.Hijacker` インターフェース
Goの`net/http`パッケージにおいて、`http.ResponseWriter`が実装できるインターフェースです。`Hijack()`メソッドを提供し、これによりHTTPハンドラは基盤となるTCPコネクションを直接制御できるようになります。これは、WebSocketや、今回のHTTP/2アップグレードのようなプロトコル切り替えが必要な場合に非常に有用です。ハンドラがコネクションをハイジャックすると、`net/http`サーバーはそれ以降そのコネクションの管理から手を引きます。

## 技術的詳細

このコミットの主要な技術的変更点は、`net/http`サーバーがHTTP/2クライアントプリフェースを特殊なケースとして認識し、適切に処理するように修正されたことです。

1.  **`PRI * HTTP/2.0` リクエストの認識**:
    *   `src/net/http/request.go`に`isH2Upgrade()`メソッドが追加されました。このメソッドは、リクエストの`Method`が`"PRI"`、`URL.Path`が`"*"`、`Header`が空、`Proto`が`"HTTP/2.0"`である場合に`true`を返します。これはまさにHTTP/2クライアントプリフェースの最初の部分を識別するためのものです。
    *   `readRequest`関数内で`isH2Upgrade()`が呼び出され、HTTP/2アップグレードリクエストであると判断された場合、`req.ContentLength`が`-1`（不明な長さ）に設定され、`req.Close`が`true`に設定されます。`req.Close = true`は、サーバーがこのリクエストの処理後にコネクションを閉じるべきであることを示します。これは、ハンドラがコネクションをハイジャックしない限り、サーバーが誤って後続のデータをHTTP/1.xリクエストとして解釈するのを防ぐための重要な措置です。

2.  **`Host`ヘッダの要件の緩和**:
    *   `src/net/http/server.go`の`conn.readRequest()`メソッド内で、HTTP/1.1以降のリクエストに対する`Host`ヘッダの必須チェックが修正されました。`isH2Upgrade`が`true`の場合、`Host`ヘッダがなくても`badRequestError`を返さないように変更されています。これにより、`Host`ヘッダを持たないHTTP/2クライアントプリフェースが有効なリクエストとして受け入れられるようになります。

3.  **コネクションのクローズ動作**:
    *   `src/net/http/server.go`の`conn.readRequest()`内で、`isH2Upgrade`が`true`の場合、レスポンスライター`w`の`closeAfterReply`が`true`に設定されます。これは、レスポンスが送信された後にコネクションが閉じられることを保証します。これは、ハンドラがコネクションをハイジャックしない場合に、サーバーがそのコネクションを再利用しようとしないようにするためのものです。

4.  **ハンドラによるハイジャックのサポート**:
    *   この変更により、`http.Handler`は`Hijacker`インターフェースを使用してコネクションをハイジャックし、HTTP/2クライアントプリフェースの残りの部分（`SM\r\n\r\n`）を読み取り、その後HTTP/2プロトコルで通信を開始できるようになります。新しいテストケース`TestServerHandlersCanHandleH2PRI`が追加され、このハイジャックのシナリオが実証されています。

## コアとなるコードの変更箇所

### `src/net/http/request.go`
```go
// isH2Upgrade reports whether r represents the http2 "client preface"
// magic string.
func (r *Request) isH2Upgrade() bool {
	return r.Method == "PRI" && len(r.Header) == 0 && r.URL.Path == "*" && r.Proto == "HTTP/2.0"
}

// ... (readRequest function within the same file)
if req.isH2Upgrade() {
	// Because it's neither chunked, nor declared:
	req.ContentLength = -1

	// We want to give handlers a chance to hijack the
	// connection, but we need to prevent the Server from
	// dealing with the connection further if it's not
	// hijacked. Set Close to ensure that:
	req.Close = true
}
```

### `src/net/http/server.go`
```go
func (c *conn) readRequest() (w *response, err error) {
	// ...
	isH2Upgrade := req.isH2Upgrade()
	if req.ProtoAtLeast(1, 1) && (!haveHost || len(hosts) == 0) && !isH2Upgrade {
		return nil, badRequestError("missing required Host header")
	}
	// ...
	if isH2Upgrade {
		w.closeAfterReply = true
	}
	// ...
}
```

### `src/net/http/readrequest_test.go`
HTTP/2クライアントプリフェースを有効なリクエストとして認識するための新しいテストケースが`reqTests`に追加されました。

### `src/net/http/serve_test.go`
*   `TestHTTP2UpgradeClosesConnection`: HTTP/2アップグレードリクエストが処理された後にコネクションが閉じられることを確認するテスト。
*   `TestServerValidatesHostHeader`: `Host`ヘッダの検証において、HTTP/2アップグレードリクエストが例外として扱われることを確認するテスト。
*   `TestServerHandlersCanHandleH2PRI`: ハンドラが`Hijack`を使用してHTTP/2クライアントプリフェースを処理できることを実証するテスト。

## コアとなるコードの解説

### `isH2Upgrade()` メソッド (`src/net/http/request.go`)
この新しいメソッドは、受信した`http.Request`オブジェクトがHTTP/2クライアントプリフェースの最初の部分（`PRI * HTTP/2.0\r\n\r\n`）に合致するかどうかを厳密にチェックします。`Method`が`"PRI"`、`URL.Path`が`"*"`、`Header`マップが空、そして`Proto`が`"HTTP/2.0"`であるという条件を全て満たす場合に`true`を返します。これにより、サーバーは通常のHTTP/1.xリクエストとHTTP/2アップグレードリクエストを明確に区別できるようになります。

### `readRequest` 関数内の変更 (`src/net/http/request.go`)
`isH2Upgrade()`が`true`を返した場合、`req.ContentLength`が`-1`に設定されます。これは、このリクエストにはHTTP/1.xのセマンティクスにおける「ボディ」が存在しないか、その長さが不明であることを示します。また、`req.Close`が`true`に設定されることで、このリクエストが処理された後、サーバーがこのコネクションを閉じるべきであるというシグナルを送ります。これは、ハンドラがコネクションをハイジャックしてHTTP/2プロトコルに切り替えない限り、サーバーがこのコネクションを再利用して後続のデータをHTTP/1.xリクエストとして誤って解釈するのを防ぐための安全策です。

### `conn.readRequest()` 関数内の変更 (`src/net/http/server.go`)
この関数は、クライアントからのリクエストを読み込み、`http.Request`オブジェクトを構築するサーバー側の主要なロジックを含んでいます。
1.  `isH2Upgrade := req.isH2Upgrade()`: まず、リクエストがHTTP/2アップグレードリクエストであるかを判定します。
2.  `if req.ProtoAtLeast(1, 1) && (!haveHost || len(hosts) == 0) && !isH2Upgrade`: `Host`ヘッダの検証ロジックが変更されました。以前はHTTP/1.1以降のリクエストで`Host`ヘッダがない場合はエラーとされていましたが、`!isH2Upgrade`という条件が追加されたことで、HTTP/2アップグレードリクエストの場合は`Host`ヘッダがなくてもエラーとはなりません。これは、HTTP/2クライアントプリフェースが`Host`ヘッダを持たないという仕様に対応するための重要な修正です。
3.  `if isH2Upgrade { w.closeAfterReply = true }`: HTTP/2アップグレードリクエストの場合、レスポンスライター`w`の`closeAfterReply`フラグが`true`に設定されます。これは、サーバーがこのリクエストに対するレスポンスを送信した後、基盤となるTCPコネクションを閉じるべきであることを示します。これにより、ハンドラがコネクションをハイジャックしてプロトコルを切り替える機会を与えつつ、ハイジャックされなかった場合にはコネクションが適切に終了されることが保証されます。

これらの変更により、Goの`net/http`サーバーは、HTTP/2クライアントプリフェースを通常のHTTP/1.xリクエストとは異なる特殊なリクエストとして認識し、ハンドラが`Hijack`メカニズムを通じてHTTP/2セッションを開始するための道を開きます。

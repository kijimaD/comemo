# [インデックス 2308] ファイルの概要

このコミットは、Go言語の386アーキテクチャ向けコンパイラである`8g`において、基本的な"Hello, World!"プログラムが再び動作するように修正するものです。主な変更点は、文字列リテラルの内部表現と処理方法の変更、関連するコンパイラ内部ファイルの名称変更、および`6g`（AMD64アーキテクチャ向けコンパイラ）とのコードベースの同期です。これにより、`8g`コンパイラが正しく文字列データを生成し、実行可能ファイルに埋め込むことができるようになります。

## 変更の背景

このコミットが行われた2009年5月は、Go言語がまだ一般に公開される前の初期開発段階にありました。当時のGoコンパイラは、複数のアーキテクチャ（例: 386、AMD64）をサポートするために、それぞれ`8g`、`6g`といった名称で開発されていました。

"Hello, World!"プログラムは、プログラミング言語の基本的な機能（文字列リテラル、標準出力への書き込み、実行可能ファイルの生成）が正しく動作するかを確認するための、最も単純かつ重要なテストケースです。このコミットのタイトル「8g: hello world works again」が示すように、`8g`コンパイラで"Hello, World!"が動作しないという問題が発生していました。これは、コンパイラが文字列リテラルを正しく処理し、実行ファイルに埋め込むことができていなかったためと考えられます。

変更の背景には、以下の要因が考えられます。

1.  **文字列リテラル処理の不整合**: `8g`と`6g`の間で文字列リテラルの内部表現や処理ロジックに差異が生じており、`8g`側で問題が発生していた。
2.  **コードベースの同期**: `6g`コンパイラでは既に動作していた機能が`8g`に反映されていなかったため、`6g`の最新の変更（特に文字列処理関連）を`8g`に「コピー＆ペースト」で適用する必要があった。これは、初期のGoコンパイラ開発において、アーキテクチャ固有のコードと共通コードの分離がまだ完全ではなかったことを示唆しています。
3.  **ファイル構造の整理**: コンパイラ内部のファイル名が、より一貫性のある命名規則（例: `align.c`から`galign.c`のように、`g`プレフィックスを追加）に変更され、コードベース全体の整理が進められていた。

このコミットは、`8g`コンパイラの基本的な健全性を回復し、Go言語の初期開発における重要なマイルストーンの一つと言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの初期設計と関連する概念について知っておく必要があります。

### 1. Goコンパイラ (`gc`, `8g`, `6g`) の役割と歴史的背景

*   **`gc` (Go Compiler)**: Go言語の公式コンパイラ群の総称です。初期のGoコンパイラは、Plan 9 Cコンパイラをベースにしていました。
*   **`8g`**: 386（Intel 32-bit）アーキテクチャ向けのGoコンパイラを指します。Go言語の初期には、異なるCPUアーキテクチャごとに独立したコンパイラバイナリが存在しました。
*   **`6g`**: AMD64（Intel 64-bit）アーキテクチャ向けのGoコンパイラを指します。
*   **コンパイラの役割**: Goソースコードを読み込み、抽象構文木（AST）を構築し、中間表現（IR）に変換し、最終的にターゲットアーキテクチャの機械語コードを生成します。この過程で、文字列リテラルなどの定数データも実行ファイル内の適切なセクションに配置されます。

### 2. Goの文字列リテラルの内部表現

Go言語の文字列は、不変のバイトスライスとして扱われます。内部的には、文字列はポインタと長さのペアで表現されます。

```go
type stringStruct struct {
    str unsafe.Pointer // 文字列データの先頭へのポインタ
    len int            // 文字列の長さ（バイト数）
}
```

コンパイラは、ソースコード中の文字列リテラル（例: `"Hello, World!"`）を、実行ファイルのデータセクションに配置し、そのアドレスと長さを参照するコードを生成します。

### 3. コンパイラのデータセクションとテキストセクション

実行可能ファイルは、通常、複数のセクションに分かれています。

*   **テキストセクション (Text Segment)**: 実行可能な機械語コードが格納されます。
*   **データセクション (Data Segment)**: 初期化されたグローバル変数や静的変数、文字列リテラルなどのデータが格納されます。

コンパイラは、コード生成中にこれらのセクションを適切に管理し、データとコードを正しい場所に配置する必要があります。

### 4. `Makefile`、`.h`、`.c` ファイルの役割

*   **`Makefile`**: ビルドプロセスを自動化するための設定ファイルです。どのソースファイルをコンパイルし、どのようにリンクするかを定義します。このコミットでは、ファイル名変更に伴い、コンパイル対象のオブジェクトファイル名が更新されています。
*   **`.h` (ヘッダーファイル)**: C言語の慣習で、関数プロトタイプ、構造体定義、マクロなどが宣言されます。コンパイラの異なるモジュール間で共有される定義が含まれます。
*   **`.c` (ソースファイル)**: C言語のソースコードが含まれます。コンパイラの具体的なロジックが実装されています。

### 5. `Prog` 構造体

Goコンパイラのバックエンドでは、機械語命令を表現するために`Prog`（Program）構造体が使用されます。これは、アセンブリ命令のオペコード、オペランド、リンク情報などを含む、命令のリストを構築するための基本的な単位です。

### `src/cmd/8g/gobj.c` (旧 `obj.c`)

    *   `text()`が呼び出されると、元の`pc`に戻り、コード生成が再開されます。
    *   これにより、文字列リテラルなどのデータがコードの途中に誤って埋め込まれることを防ぎ、データセクションにまとめて配置されるようになります。

*   **`datagostring`関数の追加**:

    *   まず、`datastring`を呼び出して実際の文字列バイトデータを生成し、そのアドレスを取得します。

## コアとなるコードの解説

### `datastring`関数の解説 (抜粋と要点)

```c
// src/cmd/8g/gobj.c
void
datastring(char *s, int len, Addr *a)
{
    // ... (初期化部分省略) ...

    // huge strings are made static to avoid long names.
    // 長い文字列は匿名で静的なシンボルとして生成
    if(len > 100) {
        snprint(namebuf, sizeof(namebuf), ".string.%d", gen++);
        ao.sym = lookup(namebuf);
        ao.type = D_STATIC;
    } else {
        // small strings get named by their contents,
        // so that multiple modules using the same string
        // can share it.
        // 短い文字列は内容に基づいて名前が付けられ、外部シンボルとして生成（重複排除のため）
        if(len > 0 && s[len-1] == '\0')
            len--; // 終端NULL文字を考慮
        tmp.lit.len = len;
        memmove(tmp.lit.s, s, len);
        tmp.lit.s[len] = '\0'; // NULL終端
        len++;
        snprint(namebuf, sizeof(namebuf), "\"%Z\"", &tmp.lit);
        ao.sym = pkglookup(namebuf, "string"); // パッケージスコープでシンボルを検索/作成
        ao.type = D_EXTERN;
    }
    *a = ao; // 生成されたアドレス情報を呼び出し元に返す

    // only generate data the first time.
    // 初回のみデータを生成（重複排除）
    if(ao.sym->uniq)
        return;
    ao.sym->uniq = 1; // 生成済みフラグを設定

    data(); // データセクション生成モードに切り替え
    for(w=0; w<len; w+=8) { // 8バイトずつデータを書き込み
        p = pc;
        gins(ADATA, N, N); // DATA命令を生成
        p->from = ao;
        p->from.offset = w; // オフセットを設定

        // ... (データ内容のコピーと設定) ...
    }
    p = pc;
    ggloblsym(ao.sym, len, ao.type == D_EXTERN); // グローバルシンボルとして登録
    if(ao.type == D_STATIC)
        p->from.type = D_STATIC;
    text(); // テキストセクション生成モードに戻す
}
```
この関数は、与えられたバイト列`s`と長さ`len`を、実行ファイルのデータセクションに配置します。
*   **文字列の命名と型**: 文字列の長さによって、生成されるシンボルの種類が変わります。長い文字列は`.string.N`のような匿名で静的なシンボルとして扱われ、短い文字列は内容のハッシュ値などに基づいて名前が付けられた外部シンボルとして扱われます。これにより、短い文字列リテラルは複数のモジュール間で共有され、バイナリサイズを削減できます。
*   **重複排除**: `ao.sym->uniq = 1;`というフラグを使って、同じ文字列データが複数回生成されるのを防ぎます。一度生成された文字列は、そのシンボルが`uniq`フラグを持つため、再生成されません。
*   **`data()`と`text()`の利用**: `data()`を呼び出してデータセクションへの書き込みモードに切り替え、文字列データを`ADATA`命令として生成します。データ生成が完了したら`text()`を呼び出して、通常のコード生成モードに戻します。これにより、データとコードが明確に分離されます。

### `data()`と`text()`関数の解説

```c
// src/cmd/8g/gobj.c
static Prog *strdat;  // データセクションの開始点
static Prog *estrdat; // データセクションの終了点
static int gflag;     // デバッグフラグの保存用
static Prog *savepc;  // テキストセクションの現在のpcを保存用

static void
data(void)
{
    gflag = debug['g']; // デバッグフラグを保存
    debug['g'] = 0;     // データ生成中はデバッグ出力を抑制

    if(estrdat == nil) {
        strdat = mal(sizeof(*pc)); // 初回呼び出し時にデータセクションの開始点を確保
        clearp(strdat);
        estrdat = strdat;
    }
    if(savepc)
        fatal("data phase error"); // ネストされたdata()呼び出しはエラー
    savepc = pc; // 現在のpc（テキストセクションの命令ポインタ）を保存
    pc = estrdat; // pcをデータセクションの末尾に設定
}

static void
text(void)
{
    if(!savepc)
        fatal("text phase error"); // data()が呼び出されていないのにtext()はエラー
    debug['g'] = gflag; // デバッグフラグを元に戻す
    estrdat = pc; // データセクションの終了点を現在のpcに設定
    pc = savepc;  // pcを保存しておいたテキストセクションの命令ポインタに戻す
    savepc = nil; // 保存用ポインタをクリア
}
```
これらの関数は、コンパイラのコード生成フェーズにおいて、データ（静的変数、文字列リテラルなど）と実行可能コード（命令）を異なるセクションに適切に配置するための状態管理を行います。
*   `data()`: 現在のコード生成コンテキスト（`pc`）を保存し、`pc`をデータセクションの末尾に切り替えます。これにより、以降の`gins`（命令生成）呼び出しはデータセクションにデータを追加するようになります。
*   `text()`: データセクションへの書き込みを終了し、保存しておいたコード生成コンテキスト（`pc`）に戻します。これにより、以降の`gins`呼び出しはテキストセクションに命令を追加するようになります。
このメカニズムにより、コンパイラはデータとコードを混在させることなく、構造化された実行ファイルを生成できます。

### `datagostring`関数の解説 (抜粋と要点)

```c
// src/cmd/8g/gobj.c
void
datagostring(Strlit *sval, Addr *a)
{
    // ... (初期化部分省略) ...

    // $string len+ptr
    // 文字列データ本体を生成し、そのアドレスapを取得
    datastring(sval->s, sval->len, &ap);
    ap.index = ap.type; // アドレスの型を設定
    ap.type = D_ADDR;   // アドレス型としてマーク
    ap.etype = TINT32;  // 型は32ビット整数（ポインタサイズ）

    if(ap.index == D_STATIC) {
        // huge strings are made static to avoid long names
        // 長い文字列の場合、Go文字列構造体も静的シンボルとして生成
        snprint(namebuf, sizeof(namebuf), ".gostring.%d", ++gen);
        ao.sym = lookup(namebuf);
        ao.type = D_STATIC;
    } else {
        // small strings get named by their contents,
        // so that multiple modules using the same string
        // can share it.
        // 短い文字列の場合、Go文字列構造体も内容に基づいて名前が付けられた外部シンボルとして生成
        snprint(namebuf, sizeof(namebuf), "\"%Z\"", sval);
        ao.sym = pkglookup(namebuf, "go.string");
        ao.type = D_EXTERN;

    if(ao.sym->uniq)
        return; // 重複排除
    ao.sym->uniq = 1;

    data(); // データセクション生成モードに切り替え
    // DATA gostring, wp, $cstring
    // Go文字列構造体のポインタ部分を生成
    p = pc;
    gins(ADATA, N, N);
    p->from = ao;
    p->from.scale = wp; // ポインタの幅
    p->to = ap;         // 文字列データ本体のアドレス

    // DATA gostring+wp, wi, $len
    // Go文字列構造体の長さ部分を生成
    p = pc;
    gins(ADATA, N, N);
    p->from = ao;
    p->from.offset = wp; // ポインタの幅分オフセット
    p->from.scale = wi;  // 長さの幅
    p->to = ac;
    p->to.offset = sval->len; // 文字列の長さ

    p = pc;
    ggloblsym(ao.sym, types[TSTRING]->width, ao.type == D_EXTERN); // グローバルシンボルとして登録
    if(ao.type == D_STATIC)
        p->from.type = D_STATIC;
    text(); // テキストセクション生成モードに戻す
}
```
この関数は、Go言語の`string`型（ポインタと長さのペア）を表現するデータ構造をデータセクションに生成します。
*   **二段階のデータ生成**: まず`datastring`を呼び出して、実際の文字列バイトデータ（例: "Hello, World!"のバイト列）をデータセクションに配置します。次に、その文字列データへのポインタと文字列の長さを格納する別のデータ構造（Goの`string`型に対応）をデータセクションに配置します。

これらの変更により、`8g`コンパイラはGoの文字列リテラルを、Goのランタイムが期待する形式で、かつ効率的に（重複排除を行いつつ）実行ファイルに埋め込むことができるようになり、"Hello, World!"プログラムが正しく動作するようになりました。

```c

void
datastring(char *s, int len, Addr *a)
{
    // ... (初期化部分省略) ...

    // huge strings are made static to avoid long names.
    // 長い文字列は匿名で静的なシンボルとして生成
    if(len > 100) {
        snprint(namebuf, sizeof(namebuf), ".string.%d", gen++);
        ao.sym = lookup(namebuf);
        ao.type = D_STATIC;
    } else {
        // small strings get named by their contents,
        // so that multiple modules using the same string
        // can share it.
        // 短い文字列は内容に基づいて名前が付けられ、外部シンボルとして生成（重複排除のため）
        if(len > 0 && s[len-1] == '\0')
            len--; // 終端NULL文字を考慮
        tmp.lit.len = len;
        memmove(tmp.lit.s, s, len);
        tmp.lit.s[len] = '\0'; // NULL終端
        len++;
        snprint(namebuf, sizeof(namebuf), "\"%Z\"", &tmp.lit);
        ao.sym = pkglookup(namebuf, "string"); // パッケージスコープでシンボルを検索/作成
        ao.type = D_EXTERN;
    }
    *a = ao; // 生成されたアドレス情報を呼び出し元に返す

    // only generate data the first time.
    // 初回のみデータを生成（重複排除）
    if(ao.sym->uniq)
        return;
    ao.sym->uniq = 1; // 生成済みフラグを設定

    data(); // データセクション生成モードに切り替え
    for(w=0; w<len; w+=8) { // 8バイトずつデータを書き込み
        p = pc;
        gins(ADATA, N, N); // DATA命令を生成
        p->from = ao;
        p->from.offset = w; // オフセットを設定

        // ... (データ内容のコピーと設定) ...
    }
    p = pc;
    ggloblsym(ao.sym, len, ao.type == D_EXTERN); // グローバルシンボルとして登録
    if(ao.type == D_STATIC)
        p->from.type = D_STATIC;
    text(); // テキストセクション生成モードに戻す
}
```
この関数は、与えられたバイト列`s`と長さ`len`を、実行ファイルのデータセクションに配置します。
*   **文字列の命名と型**: 文字列の長さによって、生成されるシンボルの種類が変わります。長い文字列は`.string.N`のような匿名で静的なシンボルとして扱われ、短い文字列は内容のハッシュ値などに基づいて名前が付けられた外部シンボルとして扱われます。これにより、短い文字列リテラルは複数のモジュール間で共有され、バイナリサイズを削減できます。
*   **重複排除**: `ao.sym->uniq = 1;`というフラグを使って、同じ文字列データが複数回生成されるのを防ぎます。一度生成された文字列は、そのシンボルが`uniq`フラグを持つため、再生成されません。
*   **`data()`と`text()`の利用**: `data()`を呼び出してデータセクションへの書き込みモードに切り替え、文字列データを`ADATA`命令として生成します。データ生成が完了したら`text()`を呼び出して、通常のコード生成モードに戻します。これにより、データとコードが明確に分離されます。

### `data()`と`text()`関数の解説

```c
// src/cmd/8g/gobj.c
static Prog *strdat;  // データセクションの開始点
static Prog *estrdat; // データセクションの終了点
static int gflag;     // デバッグフラグの保存用
static Prog *savepc;  // テキストセクションの現在のpcを保存用

static void
data(void)
{
    gflag = debug['g']; // デバッグフラグを保存
    debug['g'] = 0;     // データ生成中はデバッグ出力を抑制

    if(estrdat == nil) {
        strdat = mal(sizeof(*pc)); // 初回呼び出し時にデータセクションの開始点を確保
        clearp(strdat);
        estrdat = strdat;
    }
    if(savepc)
        fatal("data phase error"); // ネストされたdata()呼び出しはエラー
    savepc = pc; // 現在のpc（テキストセクションの命令ポインタ）を保存
    pc = estrdat; // pcをデータセクションの末尾に設定
}

static void
text(void)
{
    if(!savepc)
        fatal("text phase error"); // data()が呼び出されていないのにtext()はエラー
    debug['g'] = gflag; // デバッグフラグを元に戻す
    estrdat = pc; // データセクションの終了点を現在のpcに設定
    pc = savepc;  // pcを保存しておいたテキストセクションの命令ポインタに戻す
    savepc = nil; // 保存用ポインタをクリア
}
```
これらの関数は、コンパイラのコード生成フェーズにおいて、データ（静的変数、文字列リテラルなど）と実行可能コード（命令）を異なるセクションに適切に配置するための状態管理を行います。
*   `data()`: 現在のコード生成コンテキスト（`pc`）を保存し、`pc`をデータセクションの末尾に切り替えます。これにより、以降の`gins`（命令生成）呼び出しはデータセクションにデータを追加するようになります。
*   `text()`: データセクションへの書き込みを終了し、保存しておいたコード生成コンテキスト（`pc`）に戻します。これにより、以降の`gins`呼び出しはテキストセクションに命令を追加するようになります。
このメカニズムにより、コンパイラはデータとコードを混在させることなく、構造化された実行ファイルを生成できます。

### `datagostring`関数の解説 (抜粋と要点)

```c
// src/cmd/8g/gobj.c
void
datagostring(Strlit *sval, Addr *a)
{
    // ... (初期化部分省略) ...

    // $string len+ptr
    // 文字列データ本体を生成し、そのアドレスapを取得
    datastring(sval->s, sval->len, &ap);
    ap.index = ap.type; // アドレスの型を設定
    ap.type = D_ADDR;   // アドレス型としてマーク
    ap.etype = TINT32;  // 型は32ビット整数（ポインタサイズ）

    if(ap.index == D_STATIC) {
        // huge strings are made static to avoid long names
        // 長い文字列の場合、Go文字列構造体も静的シンボルとして生成
        snprint(namebuf, sizeof(namebuf), ".gostring.%d", ++gen);
        ao.sym = lookup(namebuf);
        ao.type = D_STATIC;
    } else {
        // small strings get named by their contents,
        // so that multiple modules using the same string
        // can share it.
        // 短い文字列の場合、Go文字列構造体も内容に基づいて名前が付けられた外部シンボルとして生成
        snprint(namebuf, sizeof(namebuf), "\"%Z\"", sval);
        ao.sym = pkglookup(namebuf, "go.string");
        ao.type = D_EXTERN;
    }

    *a = ao; // 生成されたGo文字列構造体のアドレス情報を呼び出し元に返す
    if(ao.sym->uniq)
        return; // 重複排除
    ao.sym->uniq = 1;

    data(); // データセクション生成モードに切り替え
    // DATA gostring, wp, $cstring
    // Go文字列構造体のポインタ部分を生成
    p = pc;
    gins(ADATA, N, N);
    p->from = ao;
    p->from.scale = wp; // ポインタの幅
    p->to = ap;         // 文字列データ本体のアドレス

    // DATA gostring+wp, wi, $len
    // Go文字列構造体の長さ部分を生成
    p = pc;
    gins(ADATA, N, N);
    p->from = ao;
    p->from.offset = wp; // ポインタの幅分オフセット
    p->from.scale = wi;  // 長さの幅
    p->to = ac;
    p->to.offset = sval->len; // 文字列の長さ

    p = pc;
    ggloblsym(ao.sym, types[TSTRING]->width, ao.type == D_EXTERN); // グローバルシンボルとして登録
    if(ao.type == D_STATIC)
        p->from.type = D_STATIC;
    text(); // テキストセクション生成モードに戻す
}
```
この関数は、Go言語の`string`型（ポインタと長さのペア）を表現するデータ構造をデータセクションに生成します。
*   **二段階のデータ生成**: まず`datastring`を呼び出して、実際の文字列バイトデータ（例: "Hello, World!"のバイト列）をデータセクションに配置します。次に、その文字列データへのポインタと文字列の長さを格納する別のデータ構造（Goの`string`型に対応）をデータセクションに配置します。
*   **シンボルの命名と重複排除**: `datastring`と同様に、Go文字列構造体自体も長さや内容に基づいて命名され、`ao.sym->uniq`フラグによって重複排除されます。
*   **`ADATA`命令**: `gins(ADATA, N, N)`を使って、Go文字列構造体のポインタ部分と長さ部分をデータセクションに書き込みます。

これらの変更により、`8g`コンパイラはGoの文字列リテラルを、Goのランタイムが期待する形式で、かつ効率的に（重複排除を行いつつ）実行ファイルに埋め込むことができるようになり、"Hello, World!"プログラムが正しく動作するようになりました。

# [インデックス 22729] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）トレース機能（`gctrace`）の出力を拡張し、マーク済みヒープサイズを報告するように変更します。これにより、GCサイクルの各段階におけるヒープの状態をより詳細に把握できるようになり、Goアプリケーションのメモリ使用状況とGCのパフォーマンス分析が向上します。

## 元コミット内容

このコミットは、`GODEBUG`環境変数で`gctrace`オプションが有効になっている場合に、Goランタイムのガベージコレクション（GC）トレース出力に「マーク済みヒープサイズ」を追加することを目的としています。これにより、GCサイクル開始時のヒープサイズ、スイープ前のGCサイクル終了時のヒープサイズに加えて、次のGCサイクルまで保持されるヒープの量を示すマーク済みヒープサイズが報告されるようになります。

## 変更の背景

Goのガベージコレクタは、アプリケーションのメモリ管理において重要な役割を果たします。`gctrace`は、GCの動作をデバッグし、パフォーマンスを分析するための強力なツールです。しかし、このコミット以前の`gctrace`の出力では、GCサイクル開始時と終了時のヒープサイズは提供されていましたが、GCによって「生きている」と判断され、次のサイクルまで保持されるオブジェクトが占めるヒープの正確なサイズ（マーク済みヒープサイズ）は直接報告されていませんでした。

この情報がないと、開発者はGCがどれだけのメモリを実際に解放できたのか、あるいはどれだけのメモリがまだ使用中であるのかを正確に把握することが困難でした。特に、メモリリークの疑いがある場合や、GCの効率を最適化しようとする際には、マーク済みヒープサイズは非常に重要な指標となります。このコミットは、この不足している情報を提供することで、`gctrace`の有用性を高め、Goアプリケーションのメモリプロファイリングとデバッグをより効果的にすることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goは、並行（Concurrent）、非世代別（Non-generational）、トライカラー（Tri-color）のマーク＆スイープ（Mark-and-Sweep）方式のガベージコレクタを採用しています。

*   **マークフェーズ (Mark Phase)**: このフェーズでは、GCはプログラムのルート（グローバル変数、ゴルーチンのスタック上のローカル変数など）から参照をたどり、現在使用されているすべてのオブジェクト（「生きている」オブジェクト）を識別し、マークします。GoのGCは、このマークフェーズの大部分をアプリケーションの実行と並行して行います（並行マーク）。
*   **スイープフェーズ (Sweep Phase)**: マークフェーズの完了後、GCはマークされなかったオブジェクト（「死んでいる」オブジェクト）が占めるメモリを解放し、再利用可能な状態にします。このフェーズも一部並行して行われます。
*   **Stop-the-World (STW)**: GoのGCは並行性を重視していますが、完全にSTWがないわけではありません。GCの特定の短い期間（例えば、マークフェーズの開始時と終了時）には、アプリケーションの実行が一時的に停止されます。これをSTWと呼びます。GoのGCは、このSTWポーズを非常に短く抑えるように設計されています（通常、マイクロ秒からミリ秒単位）。
*   **ヒープサイズ**: Goプログラムが動的に確保するメモリ領域をヒープと呼びます。GCはヒープ上のオブジェクトを管理します。

### `gctrace`

`gctrace`は、Goランタイムのデバッグオプションの一つで、`GODEBUG=gctrace=1`のように環境変数を設定することで有効にできます。有効にすると、GCサイクルが完了するたびに、GCの動作に関する詳細な情報が標準エラー出力に1行で出力されます。

一般的な`gctrace`の出力形式は以下のようになります（Goのバージョンによって多少異なる場合があります）：

```
gc # @#s #%: #+...+# ms clock, #+...+# ms cpu, #->#-># MB, # MB goal, # P
```

各フィールドの意味は以下の通りです：

*   `gc #`: GCの実行回数。
*   `@#s`: プログラム開始からの経過時間（秒）。
*   `#%`: プログラム実行時間全体に対するGCに費やされた時間の割合。
*   `#+...+# ms clock`: GCの各フェーズにかかった実時間（ウォールクロック時間）。通常、STWスイープ終了、並行マーク、STWマーク終了などのフェーズが含まれます。
*   `#+...+# ms cpu`: GCの各フェーズにかかったCPU時間。
*   `#->#-># MB`: GCサイクル中のヒープサイズ（MB単位）。
    *   最初の数値: GC開始時のヒープサイズ。
    *   2番目の数値: マークフェーズ後のヒープサイズ（このコミット以前はスイープ前のヒープサイズ）。
    *   3番目の数値: スイープ後のライブヒープサイズ（このコミットで追加される「マーク済みヒープサイズ」に相当）。
*   `# MB goal`: 次のGCサイクルで目標とするヒープサイズ。
*   `# P`: Goランタイムが使用している論理プロセッサの数（`GOMAXPROCS`）。

このコミット以前は、`#->#-># MB`の部分は`#-># MB`のように2つの数値しか表示されず、マーク済みヒープサイズは直接報告されていませんでした。

## 技術的詳細

このコミットの主要な変更点は、`src/runtime/mgc.go`ファイル内の`gc`関数にあります。この関数はGoランタイムのガベージコレクションの主要なロジックを担っています。

具体的には、以下の点が変更されています。

1.  **新しいヒープサイズ変数の追加**:
    `gc`関数内で、GCサイクル中のヒープサイズを記録するための変数として、`heap0`と`heap1`に加えて`heap2`という`uint64`型の変数が追加されました。
    *   `heap0`: GCサイクル開始時のヒープサイズを格納します。
    *   `heap1`: スイープ前のGCサイクル終了時のヒープサイズを格納します。
    *   `heap2`: 新たに、マークフェーズで「生きている」とマークされたオブジェクトが占めるヒープサイズ（マーク済みヒープサイズ）を格納します。

2.  **`heap2`への値の代入**:
    `gcMark`関数（マークフェーズを実行する関数）の呼び出し後、`debug.gctrace > 0`（`gctrace`が有効な場合）の条件分岐内で、`heap2 = work.bytesMarked`という行が追加されました。
    *   `work.bytesMarked`は、マークフェーズ中にマークされたバイト数、つまり「生きている」と判断されたオブジェクトの合計サイズを保持する変数です。この値を`heap2`に代入することで、マーク済みヒープサイズが記録されます。

3.  **`gctrace`出力フォーマットの変更**:
    `gctrace`の出力を行う`print`文において、ヒープサイズを表示する部分のフォーマットが変更されました。
    変更前: `heap0>>20, "->", heap1>>20, " MB, "`
    変更後: `heap0>>20, "->", heap1>>20, "->", heap2>>20, " MB, "`
    これにより、GC開始時 (`heap0`) -> スイープ前 (`heap1`) -> マーク済み (`heap2`) の3つのヒープサイズがMB単位で表示されるようになります。

4.  **コメントの削除**:
    以前のコードにあった`// TODO(austin): Marked heap size at end`というコメントが削除されました。これは、このコミットによってマーク済みヒープサイズの報告が実装されたため、不要になったことを示しています。

これらの変更により、`gctrace`の出力はより詳細になり、GCの動作を分析する際に、実際にどれだけのメモリが解放され、どれだけのメモリが保持されたのかを明確に区別できるようになりました。

## コアとなるコードの解説

### `src/runtime/mgc.go`

このファイルはGoランタイムのガベージコレクタの主要な実装を含んでいます。

*   **`var heap0, heap1, heap2 uint64` の追加**:
    `gc`関数の冒頭で、GCサイクル中のヒープサイズを追跡するための3つの`uint64`型変数が宣言されています。
    *   `heap0`: GC開始時のヒープサイズ。
    *   `heap1`: マークフェーズ終了後、スイープ開始前のヒープサイズ。
    *   `heap2`: 新たに追加された変数で、マークフェーズで「生きている」と判断されたオブジェクトが占めるヒープサイズ（マーク済みヒープサイズ）を格納します。

*   **`if debug.gctrace > 0 { heap2 = work.bytesMarked }` の追加**:
    `gcMark`関数（GCのマークフェーズを実行する）の呼び出し直後に、このコードブロックが追加されました。
    `debug.gctrace > 0`は、`gctrace`デバッグオプションが有効になっているかどうかをチェックします。
    `work.bytesMarked`は、GCのマークフェーズ中に「生きている」とマークされたオブジェクトの合計バイト数を保持するグローバルなカウンタです。この値が`heap2`に代入されることで、マーク済みヒープサイズが記録されます。

*   **`// TODO(austin): Marked heap size at end` コメントの削除**:
    以前のコードにあったこのコメントは、マーク済みヒープサイズの報告がこのコミットで実装されたため、不要となり削除されました。

*   **`print` 文の変更**:
    `gctrace`の出力を行う`print`文のフォーマットが変更されました。
    変更前は`heap0`と`heap1`の2つのヒープサイズのみが表示されていましたが、変更後は`heap0`, `heap1`, `heap2`の3つのヒープサイズが`->`で区切られて表示されるようになりました。
    `heap0>>20`, `heap1>>20`, `heap2>>20`は、バイト単位のヒープサイズを20ビット右シフト（つまり1024 * 1024 = 1MBで割る）することで、MB単位に変換して表示しています。

これらの変更により、`gctrace`の出力は、GCサイクル開始時のヒープ、スイープ前のヒープ、そして実際に保持される（マークされた）ヒープという3つの重要なヒープサイズを明確に区別して表示するようになり、GCの動作をより深く理解するための貴重な情報を提供します。

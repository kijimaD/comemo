# [インデックス 24670] ファイルの概要

このコミットは、Goランタイムの`cgo`関連アセンブリファイルから、未使用の`__stack_chk_fail_local`シンボルを削除するものです。具体的には、`src/runtime/cgo/gcc_386.S`、`src/runtime/cgo/gcc_arm.S`、`src/runtime/cgo/gcc_arm64.S`、`src/runtime/cgo/gcc_ppc64x.S`の4つのファイルが変更され、合計18行が削除されました。

## コミット

Goランタイムの`cgo`コンポーネントにおいて、`__stack_chk_fail_local`というシンボルが複数のアーキテクチャ向けのアセンブリファイル内で定義されていましたが、実際にはどこからも使用されていませんでした。この未使用のシンボルが、特定の環境下でリンカによる重複シンボルエラーを引き起こす原因となっていました。本コミットは、この問題に対処するため、該当する`__stack_chk_fail_local`の定義を全てのアセンブリファイルから削除します。これにより、リンカエラーの解消とコードベースの整理が図られます。

## 変更の背景

この変更の主な背景は、Goプログラムをビルドする際に発生していた「重複シンボルエラー」です。具体的には、`golang/go#9327`で報告された問題に対処するために行われました。

`__stack_chk_fail_local`というシンボルは、スタック破壊保護（Stack Smashing Protection, SSP）に関連する関数で、通常はコンパイラ（GCCなど）によって生成されるコードがスタックオーバーフローを検出した際に呼び出されます。Goの`cgo`（C言語との相互運用機能）は、Cコードをコンパイル・リンクする際に、システムが提供するライブラリ（例: `libc`や`libssp`）と連携します。

問題は、Goランタイムの`cgo`関連アセンブリファイル（`gcc_386.S`など）が、この`__stack_chk_fail_local`シンボルを独自に定義していたにもかかわらず、Goランタイムのコード内では実際にはどこからも使用されていなかった点にありました。一方で、システムが提供するライブラリも同じシンボルを定義している場合があり、これによりリンカが「同じ名前のシンボルが複数存在するため、どちらを使用すべきか判断できない」という重複シンボルエラーを報告していました。

このコミットは、Goランタイム側で不要な`__stack_chk_fail_local`の定義を削除することで、システムライブラリとのシンボル衝突を回避し、ビルドエラーを解消することを目的としています。

## 前提知識の解説

### 1. cgo (C Foreign Function Interface for Go)

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。Goはシステムプログラミング言語ですが、既存のCライブラリ資産を活用したい場合や、特定の低レベル操作をCで行いたい場合に`cgo`が利用されます。`cgo`を使用すると、Goのビルドプロセス中にCコンパイラ（通常はGCC）が呼び出され、CコードがコンパイルされてGoの実行可能ファイルにリンクされます。

### 2. スタック破壊保護 (Stack Smashing Protection, SSP)

スタック破壊保護（Stack Smashing Protection, SSP）は、スタックベースのバッファオーバーフロー攻撃を防ぐためのセキュリティ機構です。これは「スタックカナリア（Stack Canary）」とも呼ばれます。
コンパイラ（GCCなど）は、関数のプロローグ（開始部分）で、リターンアドレスの前にランダムな値（カナリア）をスタックに配置します。関数のエピローグ（終了部分）では、このカナリアの値が変更されていないかチェックします。もし値が変更されていれば、バッファオーバーフローが発生したと判断し、プログラムを異常終了させます。この異常終了処理を行う関数が`__stack_chk_fail`や`__stack_chk_fail_local`です。

### 3. `__stack_chk_fail` と `__stack_chk_fail_local`

*   **`__stack_chk_fail`**: スタック破壊が検出された際に呼び出される標準的な関数です。通常、`libc`などのシステムライブラリによって提供され、エラーメッセージを出力してプログラムを終了させます。
*   **`__stack_chk_fail_local`**: これは`__stack_chk_fail`のローカル版、または特定のコンパイラや環境で内部的に使用されるバリアントです。GCCなどのコンパイラが、特定の最適化やリンキングの都合上、`__stack_chk_fail`の代わりに`__stack_chk_fail_local`への呼び出しを生成することがあります。このシンボルも、通常はシステムライブラリの一部として提供されるか、コンパイラが生成する補助コードに含まれます。

### 4. アセンブリファイル (`.S`)

`.S`拡張子を持つファイルは、アセンブリ言語のソースコードファイルです。Goランタイムは、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある部分でアセンブリ言語を使用します。`cgo`のコンテキストでは、GoとCの間でスタックフレームやレジスタの状態を適切に切り替えるための「クロスコール」処理などがアセンブリで記述されることがあります。これらのファイルは、特定のCPUアーキテクチャ（例: `386`、`arm`、`arm64`、`ppc64x`）に特化しています。

### 5. リンカ (Linker)

リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o`ファイル）やライブラリを結合し、最終的な実行可能ファイルや共有ライブラリを作成するツールです。リンカの主な役割の一つは、プログラム内で参照されているシンボル（関数名や変数名）の定義を、適切なオブジェクトファイルやライブラリから見つけて解決することです。もし同じシンボルが複数の場所で定義されている場合、リンカは「重複シンボルエラー」を報告し、ビルドを停止します。

## 技術的詳細

このコミットで削除された`__stack_chk_fail_local`の定義は、Goランタイムの`cgo`関連アセンブリファイル（`gcc_386.S`、`gcc_arm.S`、`gcc_arm64.S`、`gcc_ppc64x.S`）内に存在していました。これらの定義は、各アーキテクチャのアセンブリ言語で書かれており、`EXT(__stack_chk_fail_local):`というラベルでシンボルを公開し、その直後に無限ループ（`jmp 1b`や`b 1b`）を実装していました。これは、もしこの関数が呼び出された場合にプログラムがハングアップするように見せかける、一種のプレースホルダーまたはデバッグ用の実装であったと考えられます。

しかし、コミットメッセージにあるように、Goランタイムのコードベース内でこの`__stack_chk_fail_local`が実際に使用されている箇所は見つかりませんでした。これは、Goランタイムがスタック破壊保護を独自に実装しているか、あるいは`cgo`のコンテキストでこの特定のシンボルがGo側から呼び出される必要がなかったためと考えられます。

問題は、GoのビルドシステムがCコンパイラ（GCC）を使用して`cgo`関連のコードをコンパイルする際に、システムが提供するライブラリ（例: `glibc`や`musl`などのCライブラリ、または`libssp`などのスタック破壊保護ライブラリ）も`__stack_chk_fail_local`を定義している場合があることです。Goランタイムのアセンブリファイルとシステムライブラリの両方が同じシンボルを定義していると、リンカはどちらの定義を使用すべきか判断できず、重複シンボルエラー（`duplicate symbol` error）を発生させ、ビルドが失敗していました。

このコミットは、Goランタイム側で不要な`__stack_chk_fail_local`の定義を削除することで、このシンボル衝突の問題を根本的に解決します。これにより、Goのビルドプロセスがより堅牢になり、様々な環境での互換性が向上します。特に、32ビットアーキテクチャや`musl`ベースのLinuxディストリビューション（例: Alpine Linux）など、リンカの挙動が異なる環境でこの問題が顕著に発生していました。

## コアとなるコードの解説

削除されたコードブロックは、各アーキテクチャのアセンブリ言語で`__stack_chk_fail_local`というシンボルを定義していました。

例として、`gcc_386.S`の削除された部分を見てみましょう。

```assembly
.globl EXT(__stack_chk_fail_local)
EXT(__stack_chk_fail_local):
1:
	jmp 1b
```

*   `.globl EXT(__stack_chk_fail_local)`: これは、`__stack_chk_fail_local`というシンボルをグローバルに公開することをリンカに指示するディレクティブです。`EXT`マクロは、Goのビルドシステムが使用するシンボル命名規則に合わせて、シンボル名を適切に装飾するために使用されます。
*   `EXT(__stack_chk_fail_local):`: ここで`__stack_chk_fail_local`というラベルが定義され、このアドレスが関数のエントリポイントとなります。
*   `1:`: これはローカルラベルで、この行の次の命令への参照として使用されます。
*   `jmp 1b`: これは「後方へのジャンプ」命令で、`1:`ラベルにジャンプします。結果として、この関数が呼び出されると無限ループに陥り、プログラムがハングアップします。他のアーキテクチャ（ARM, ARM64, PPC64x）でも同様に、`b 1b`（ブランチ命令）を使って無限ループを実装していました。

このコードは、`__stack_chk_fail_local`が呼び出された場合にプログラムを停止させるための非常に単純な実装でした。しかし、Goランタイムのコードベース内でこの関数が実際に呼び出される箇所がなかったため、この定義は冗長であり、システムライブラリが提供する同名のシンボルとの衝突を引き起こしていました。

このコミットは、この未使用かつ衝突の原因となっていたアセンブリコードを削除することで、Goのビルドプロセスにおけるリンカエラーを解消し、Goランタイムの`cgo`コンポーネントの堅牢性と互換性を向上させました。

## 変更の背景

Goのガベージコレクション（GC）は、並行実行されるプログラム（ミューテーター）と同時に動作するように設計されています。この並行GCの正確性を保証するために「ライトバリア（Write Barrier）」というメカニズムが導入されています。ライトバリアは、ポインタの書き込み操作が行われる際に特定の処理を挿入することで、GCがオブジェクトグラフの変更を正しく追跡できるようにします。

しかし、Goランタイムの非常に低レベルな部分、特にスケジューラやGC自体の一部では、ライトバリアの実行が不適切または不可能である場合があります。例えば、ライトバリアは通常、アクティブな`P`（プロセッサコンテキスト）を必要としますが、`P`が利用できない状況で実行される関数では問題が生じます。このような状況に対応するため、Goコンパイラには`//go:nowritebarrier`というディレクティブが用意されています。これは、その直後に続く関数がライトバリアを含まないことをコンパイラに保証させるためのアノテーションです。もしライトバリアが含まれていれば、コンパイル時にエラーが発生します。

このコミットの背景にある問題は、`gcmarkwb_m`関数に`go:nowritebarrier`アノテーションを適用する際に、そのアノテーションがコメント行に誤って記述されていたことです。コンパイラはコメント内のディレクティブを認識しないため、`gcmarkwb_m`関数は意図せずライトバリアのチェックから除外されていませんでした。この修正は、この誤った配置を訂正し、コンパイラが正しく`go:nowritebarrier`ディレクティブを適用できるようにすることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、**三色マーキングアルゴリズム**をベースとした並行マーク＆スイープ方式を採用しています。
*   **白 (White) オブジェクト**: まだGCによって訪問されていないオブジェクト。回収候補。
*   **灰 (Grey) オブジェクト**: GCによって訪問されたが、その参照先（子オブジェクト）がまだスキャンされていないオブジェクト。
*   **黒 (Black) オブジェクト**: GCによって訪問され、その参照先もすべてスキャンされたオブジェクト。回収対象外。

GCはプログラムの実行と並行して動作し、アプリケーション（ミューテーター）がオブジェクトグラフを変更する可能性があります。この並行性の中で、「黒オブジェクトが白オブジェクトを参照してはならない」という重要な不変条件を維持する必要があります。

### ライトバリア (Write Barrier)

この不変条件を維持するために導入されるのがライトバリアです。ライトバリアは、ポインタの書き込み操作（例: `obj.field = new_ptr`）が行われる際に、コンパイラによって自動的に挿入される小さなコードスニペットです。Goでは主に**挿入ライトバリア**が使用されます。

挿入ライトバリアの動作は以下の通りです。
1.  もし黒オブジェクトに白オブジェクトへのポインタが割り当てられようとした場合、
2.  その白オブジェクトは直ちに灰オブジェクトとしてマークされます。

これにより、新しく参照されたオブジェクトが誤って回収されることを防ぎ、GCによって確実にスキャンされるようになります。ライトバリアは、GCの一時停止時間（Stop-The-World, STW）を最小限に抑え、アプリケーションのレイテンシを向上させる上で重要な役割を果たします。

### `//go:nowritebarrier` ディレクティブ

`//go:nowritebarrier`は、Goコンパイラに対する特殊なアノテーション（ディレクティブ）であり、主にGoランタイムの内部コードで使用されます。このディレクティブの目的は以下の通りです。

*   **ライトバリアの不在を表明**: このディレクティブが直後に続く関数には、ライトバリアが含まれていないことをコンパイラに保証させます。もし関数内にライトバリアが生成されるようなポインタ書き込み操作があれば、コンパイル時にエラーが発生します。これはライトバリアの生成を抑制するものではなく、あくまで「ライトバリアがないはずだ」というアサーション（表明）です。
*   **使用される文脈**: Goランタイムの非常にデリケートな部分、特にスケジューラやGCの内部処理で利用されます。これらの関数は、`P`（プロセッサコンテキスト）が利用できない状態や、GCの整合性を損なう可能性のある状況で実行されることがあります。このような状況でライトバリアが実行されると、デッドロック、無限ループ、またはGCの状態の破損といった深刻な問題を引き起こす可能性があります。
*   **`//go:nowritebarrierrec`との違い**: `//go:nowritebarrierrec`という関連するディレクティブもあります。これは、アノテーションされた関数とその関数が推移的に呼び出すすべての関数（`//go:yeswritebarrierrec`ディレクティブに遭遇するまで）にライトバリアが含まれないことを表明します。`//go:nowritebarrier`は、ライトバリアを避けることが有益だが、必ずしも正確性のために不可欠ではない状況で使用されるのに対し、`//go:nowritebarrierrec`はランタイムの整合性にとって不可欠な場合に用いられることが多いです。

例えば、`src/runtime/runtime2.go`の`setMNoWB`関数や`src/runtime/proc.go`の`newosproc`関数などは、`P`が利用できない状況で動作するため、`//go:nowritebarrier`でマークされています。`g`（ゴルーチン）、`m`（OSスレッド）、`p`（プロセッサ）といったオブジェクト自体はヒープに割り当てられますが、決して解放されないため、ランタイムはこれらのオブジェクトを操作する低レベルのスケジューラコードでライトバリアを回避することができます。

## 技術的詳細

このコミットで修正されているのは、`src/runtime/mbarrier.go`内の`gcmarkwb_m`関数に対する`go:nowritebarrier`アノテーションの配置ミスです。

`gcmarkwb_m`関数は、GCのマークフェーズ中にポインタの書き込みバリアとして機能する関数です。この関数自体は、GCの内部処理の一部として、特定の条件下でライトバリアを無効にする必要がある文脈で呼び出される可能性があります。そのため、この関数自体がライトバリアを含まないことをコンパイラに保証させるために`go:nowritebarrier`ディレクティブが適用されていました。

しかし、元のコードでは、`go:nowritebarrier`ディレクティブが以下のようにコメント行の途中に記述されていました。

```go
// stack frames that have not been active. go:nowritebarrier
func gcmarkwb_m(slot *uintptr, ptr uintptr) {
```

Goコンパイラは、`//go:`で始まるディレクティブを認識しますが、それがコメント行の途中に埋め込まれている場合、正しく解釈できないことがあります。ディレクティブは通常、単独のコメント行として、またはコード行の直前に配置される必要があります。この誤った配置により、コンパイラは`gcmarkwb_m`関数に対して`go:nowritebarrier`のチェックを適用せず、意図しないライトバリアが関数内に存在してもコンパイルエラーを検出できませんでした。

このコミットは、`go:nowritebarrier`ディレクティブをコメント行から分離し、`gcmarkwb_m`関数の定義の直前の独立したコメント行として配置することで、この問題を解決しています。

```go
// stack frames that have not been active.
//go:nowritebarrier
func gcmarkwb_m(slot *uintptr, ptr uintptr) {
```

これにより、コンパイラは`gcmarkwb_m`関数がライトバリアを含まないことを正しく検証できるようになり、GoランタイムのGCメカニズムの堅牢性が向上します。

## コアとなるコードの解説

変更は`src/runtime/mbarrier.go`ファイルの86行目付近にあります。

-   **`- stack frames that have not been active. go:nowritebarrier`**:
    元のコードでは、`go:nowritebarrier`ディレクティブが、その前のコメント行の末尾に結合されていました。この形式では、Goコンパイラはこれを有効なディレクティブとして認識できませんでした。

-   **`+ stack frames that have not been active.`**:
    まず、元のコメント行から`go:nowritebarrier`の部分が削除され、純粋なコメントとして残されます。

-   **`+//go:nowritebarrier`**:
    次に、`gcmarkwb_m`関数の定義の直前に、`//go:nowritebarrier`が独立した行として追加されます。この配置により、Goコンパイラはこのディレクティブを正しく認識し、`gcmarkwb_m`関数がライトバリアを含まないことを検証するようになります。

この修正は、機能的な動作を変更するものではなく、コンパイラディレクティブの構文的な正確性を保証し、開発者が意図した通りのコンパイル時チェックが適用されるようにするためのものです。これにより、将来的に`gcmarkwb_m`関数に誤ってライトバリアが導入された場合に、コンパイルエラーとして早期に検出できるようになります。

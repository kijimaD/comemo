# [インデックス 23340] ファイルの概要

## コミット
`runtime: check consistency of all module data objects`

このコミットは、Goランタイムがロードされたすべてのモジュールデータオブジェクトの整合性を検証するように変更します。以前は、ランタイム自身が属するモジュールデータオブジェクトのみがチェックされていましたが、この変更により、システム内のすべてのモジュールデータオブジェクトに対して整合性チェックが拡張されます。具体的には、関数テーブル（`functab`）がプログラムカウンタ（PC）によって正しくソートされているかなどの検証が行われます。

## 変更の背景
Goランタイムは、プログラムの実行中にロードされるコードモジュールに関するメタデータ（関数情報、型情報など）を管理するために`moduledata`構造体を使用します。以前の実装では、ランタイムの初期化時に、ランタイム自体が属するメインの`moduledata`オブジェクトの整合性のみを検証していました。しかし、Goプログラムは動的にロードされるプラグインや共有ライブラリなど、複数の`moduledata`オブジェクトを持つ可能性があります。

もし、これらの追加の`moduledata`オブジェクトのいずれかが破損している場合（例えば、関数テーブルが正しくソートされていないなど）、ランタイムが誤動作したり、クラッシュしたりする可能性があります。このような問題は、スタックトレースの誤り、デバッグ情報の欠落、さらにはプログラムのクラッシュに直結します。このコミットは、このような潜在的な問題を早期に発見し、システムの堅牢性を向上させるために、すべてのロードされた`moduledata`オブジェクトに対して整合性チェックを拡張することを目的としています。これにより、デバッグが容易になり、より安定した実行環境が提供されます。

## 前提知識の解説

### Goランタイム
Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、スタック管理、ゴルーチン管理など、Go言語の多くの重要な機能を提供します。ランタイムは、Goプログラムが効率的かつ安全に動作するための基盤となります。

### `moduledata`構造体
`moduledata`はGoランタイム内部で使用される重要なデータ構造で、ロードされたGoモジュール（実行可能ファイルや共有ライブラリなど）に関するメタデータを保持します。これには、以下のような情報が含まれます。
-   **`pclntable`**: プログラムカウンタ（PC）と行番号、関数名などのマッピング情報を含むテーブル。デバッグ情報やスタックトレースの生成に利用されます。
-   **`ftab`**: 関数テーブル。各関数の開始PCと、`pclntable`内の対応するエントリへのオフセットを格納します。このテーブルはPCアドレスでソートされていることが厳密に要求されます。
-   **`minpc`, `maxpc`**: このモジュールがカバーするPCアドレスの最小値と最大値。
-   **`next`**: 複数のモジュールがロードされている場合に、次の`moduledata`オブジェクトへのポインタ。これにより、ランタイムはリンクされたリストのようにすべてのロードされたモジュールを走査できます。

### 関数テーブル（`functab`）の整合性
`functab`は、プログラムカウンタ（PC）から関数情報を効率的に検索するために使用されます。このテーブルは、PCアドレスの昇順でソートされていることが厳密に要求されます。もしソート順が崩れている場合、ランタイムは正しい関数情報を特定できなくなり、スタックトレースの誤り、デバッグ情報の欠落、さらにはプログラムのクラッシュにつながる可能性があります。これは、Goの反射（reflection）機能やプロファイリングツールにとっても極めて重要です。

### プログラムカウンタ（PC）
プログラムカウンタは、CPUが次に実行する命令のアドレスを指すレジスタです。Goランタイムでは、PC値を使用して、現在実行中のコードがどの関数に属するかを特定します。これは、エラー発生時のスタックトレース生成や、デバッガがコードの実行位置を特定する際に不可欠な情報です。

## 技術的詳細

この変更の核心は、`symtab.go`ファイル内の`moduledataverify`関数の導入と、既存の検証ロジックの汎用化です。これにより、Goランタイムは、メインモジュールだけでなく、動的にロードされた可能性のあるすべてのモジュールに対しても、その内部データ構造が正しく構築され、ソートされていることを保証できるようになります。

1.  **`symtabverify`から`moduledataverify1`へのリネームと汎用化**:
    -   元の`symtabverify`関数は、`firstmoduledata`というグローバル変数に直接アクセスして、メインモジュールの整合性をチェックしていました。
    -   この関数は`moduledataverify1(datap *moduledata)`にリネームされ、引数として`*moduledata`を受け取るようになりました。これにより、任意の`moduledata`オブジェクトに対して同じ検証ロジックを適用できるようになります。
    -   関数内の`firstmoduledata`への参照はすべて、引数`datap`への参照に置き換えられました。これにより、コードの再利用性が高まり、特定のモジュールデータオブジェクトに依存しない汎用的なチェックが可能になります。

2.  **新しい`moduledataverify`関数の導入**:
    -   この新しい関数は、`firstmoduledata`から始まり、各`moduledata`構造体の`next`ポインタをたどって、ロードされているすべての`moduledata`オブジェクトをイテレートします。
    -   イテレーションごとに、現在の`moduledata`オブジェクトを引数として`moduledataverify1`を呼び出し、その整合性を検証します。このループは、Goプログラムが複数のモジュール（例えば、メインの実行可能ファイルとプラグインとしてロードされた共有ライブラリ）で構成されている場合に特に重要です。

3.  **`schedinit`の変更**:
    -   `proc1.go`内の`schedinit`関数は、Goランタイムの初期化シーケンスの一部であり、プログラムが実行を開始する前に様々なランタイムコンポーネントをセットアップします。
    -   以前は`symtabverify()`を直接呼び出していましたが、この変更により`moduledataverify()`を呼び出すように変更されました。これにより、ランタイムの初期化時に、メインモジュールだけでなく、すべてのロードされたモジュールデータオブジェクトの整合性チェックが実行されるようになります。これは、プログラムの実行開始前に潜在的な問題を早期に発見するための重要なステップです。

これらの変更により、Goランタイムの堅牢性が大幅に向上し、予期せぬ動作やクラッシュのリスクが低減されます。特に、動的にロードされるコードの増加に伴い、このような包括的な整合性チェックはシステムの安定性を維持するために不可欠です。

## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムが複数のコードモジュール（例えば、メインの実行可能ファイルと動的にロードされたプラグイン）を扱う際の堅牢性を高めることにあります。

1.  **`moduledataverify`関数の導入**:
    -   この関数は、Goプログラムにロードされているすべての`moduledata`オブジェクトを走査する役割を担います。
    -   `firstmoduledata`は、Goランタイムが認識する最初の（通常はメインの）モジュールデータオブジェクトへのグローバルポインタです。
    -   各`moduledata`構造体には`next`フィールドがあり、これによりランタイムはリンクされたリストのようにすべてのモジュールデータオブジェクトをたどることができます。
    -   このループにより、システム内のすべてのモジュールが検証の対象となります。これにより、メインモジュール以外の動的にロードされたモジュールについても、その内部構造が正しく設定されていることが保証されます。

2.  **`moduledataverify1(datap *moduledata)`関数の汎用化**:
    -   この関数は、個々の`moduledata`オブジェクトの整合性チェックを実行します。
    -   **`pclntable`ヘッダーの検証**: `pcln`および`pcln32`変数を通じて、`pclntable`のヘッダーが期待されるマジックナンバー（`0xfffffffb`）、PC量子（`_PCQuantum`）、およびポインタサイズ（`ptrSize`）と一致するかを確認します。これは、`pclntable`が正しく初期化され、破損していないことを保証するための基本的なチェックです。もしヘッダーが不正であれば、`throw("invalid function symbol table\\n")`によってランタイムパニックが発生します。
    -   **`ftab`のソート順の検証**: `ftab`（関数テーブル）は、PCアドレスの昇順でソートされている必要があります。このループは、`ftab`内の連続するエントリ`datap.ftab[i].entry`と`datap.ftab[i+1].entry`を比較し、前のエントリのPCが次のエントリのPCよりも大きい場合にエラーを`throw`します。これは、`ftab`の最も重要な整合性要件の一つであり、効率的なPC-to-functionマッピングを可能にします。
    -   **`minpc`と`maxpc`の検証**: `datap.minpc`が`ftab`の最初のエントリのPCと一致し、`datap.maxpc`が`ftab`の最後のエントリのPCと一致するかを確認します。これにより、モジュールのPC範囲が正しく設定されていることを保証し、ランタイムがモジュール内のコードアドレスを正確に識別できるようにします。

これらのチェックは、Goランタイムが関数呼び出しの解決、スタックトレースの生成、デバッグ情報の提供などを正確に行うために不可欠です。すべてのモジュールに対してこれらのチェックを適用することで、Goプログラム全体の信頼性と安定性が向上します。

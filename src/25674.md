## 元コミット内容

このコミットは、Goコンパイラのパーサーにおけるクリーンアップ作業の第3弾です。具体的には、`dotname`（ドット付きの名前、例: `pkg.Symbol` や `struct.Field`）の機能を、これまで3箇所でインライン展開されていたものを、独立した関数として切り出すことでリファクタリングを行いました。

## 変更の背景

Goコンパイラのコードベースは、そのパフォーマンスと正確性を維持するために、常に整理され、最適化されています。このコミットの背景には、コードの重複を排除し、保守性を向上させるという一般的なソフトウェアエンジニアリングの原則があります。

`dotname` の処理ロジックがパーサー内の複数の場所でインライン展開されていると、以下のような問題が発生します。

1.  **コードの重複**: 同じロジックが複数回記述されるため、コード量が増加し、見通しが悪くなります。
2.  **保守性の低下**: `dotname` の処理に変更が必要になった場合、すべてのインライン展開された箇所を修正する必要があり、修正漏れやバグの発生リスクが高まります。
3.  **可読性の低下**: 複雑なロジックがパーサーの主要な処理フローの中に埋め込まれることで、コードの意図を理解しにくくなります。

これらの問題を解決するため、共通の `dotname` 処理を独立した関数として抽出し、その関数を呼び出す形にすることで、コードの再利用性を高め、保守性と可読性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの基本的な構造と、特にパーサーの役割に関する知識が必要です。

*   **Goコンパイラ (`cmd/compile`)**: Go言語の公式コンパイラは `cmd/compile` パッケージに実装されています。これは、Goのソースコードを機械語に変換する一連のプロセス（字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成）を管理します。
*   **パーサー (`parser.go`)**: コンパイラの「構文解析」フェーズを担当します。字句解析器（lexer）が生成したトークン列を読み込み、Go言語の文法規則（Go言語仕様）に従って、プログラムの構造を表現する抽象構文木（AST: Abstract Syntax Tree）を構築します。
*   **抽象構文木 (AST)**: ソースコードの構造を木構造で表現したものです。各ノードはプログラムの構成要素（変数宣言、関数呼び出し、演算子など）を表します。コンパイラの後のフェーズ（意味解析、コード生成など）は、このASTを基に進められます。
*   **`Node` 構造体**: Goコンパイラ内部では、ASTの各要素を `Node` 構造体で表現します。`Node` は、その種類（`Op` フィールド）、関連するシンボル、型情報、子ノードへのポインタなど、様々な情報を含みます。
*   **`dotname`**: Go言語における「ドット付きの名前」を指します。これは主に以下の2つの文脈で現れます。
    *   **パッケージ修飾子**: `fmt.Println` のように、パッケージ名に続いてドットと識別子が続く形式。`fmt` はパッケージ、`Println` はそのパッケージ内のシンボルです。
    *   **セレクタ**: `obj.Field` や `obj.Method()` のように、構造体やインターフェースのフィールドやメソッドにアクセスする形式。`obj` は式、`Field` や `Method` はそのメンバーです。
*   **`OPACK`**: `Node.Op` フィールドの値の一つで、ノードがパッケージを表すことを示します。例えば、`fmt.Println` の `fmt` の部分は `OPACK` ノードとしてASTに表現されます。
*   **`OXDOT`**: `Node.Op` フィールドの値の一つで、ノードがドット演算子（セレクタ）を表すことを示します。`fmt.Println` 全体や `obj.Field` 全体は `OXDOT` ノードとしてASTに表現されます。`OXDOT` ノードは通常、左の子ノードにドットの左側の式（例: `fmt` や `obj`）、右の子ノードにドットの右側の識別子（例: `Println` や `Field`）を持ちます。
*   **`p.sym()`**: パーサーのメソッドで、現在のトークンがシンボル（識別子）であると期待し、そのシンボルに対応する `Node` を返します。
*   **`restrictlookup(sel.Name, pkg.Name.Pkg)`**: パッケージスコープでのシンボル解決を行う関数です。`pkg.Name.Pkg` で指定されたパッケージ内で `sel.Name` という名前のシンボルを探します。これは、`fmt.Println` のようなパッケージ修飾された名前を解決する際に使用されます。
*   **`oldname(s)` / `newname(sel)`**: ASTノードを生成または変換するヘルパー関数です。`oldname` は既存のシンボルからノードを作成し、`newname` は新しい識別子からノードを作成します。
*   **`p.trace()` / `Debug['x']`**: Goコンパイラにはデバッグ用のトレース機能が組み込まれています。`trace` が有効で、特定のデバッグフラグ（この場合は `'x'`）が設定されている場合に、関数の呼び出しや終了をログに出力します。これはコンパイラの動作を追跡し、デバッグするのに役立ちます。

## 技術的詳細

このコミットの主要な技術的変更は、`dotname` 処理の共通化です。以前は、`parser.go` 内の複数の場所（特に式解析に関連する部分）で、ドット演算子（`.`）に続く識別子を処理するロジックが重複して記述されていました。このロジックは、左側のオペランドがパッケージであるか、それ以外の式であるかによって異なる処理を行う必要がありました。

具体的には、以下のパターンを処理していました。

1.  `package.Symbol`: 左側のオペランドがパッケージ (`OPACK` ノード) の場合、そのパッケージ内でシンボルをルックアップし、対応するノードを返します。
2.  `expression.Field`: 左側のオペランドがパッケージではない式の場合、ドット演算子 (`OXDOT`) を表すノードを生成し、左の子に式、右の子にフィールド名（識別子）を設定します。

この共通のロジックが、`parser` 構造体の新しいメソッド `new_dotname` として抽出されました。

**`new_dotname` 関数の役割**:
`new_dotname` 関数は、左側のオペランドを表す `pkg *Node` を引数として受け取ります。関数内部では、まずドットの右側の識別子を `p.sym()` で取得します。次に、`pkg.Op` が `OPACK` であるかどうかをチェックし、それに応じてパッケージスコープでのシンボル解決を行うか、`OXDOT` ノードを生成するかを決定します。

**変更の影響**:
このリファクタリングにより、パーサーのコードはよりDRY (Don't Repeat Yourself) になり、`dotname` 処理のロジックが単一の場所で管理されるようになりました。これにより、将来的な変更やバグ修正が容易になり、コードの品質が向上します。

また、`syntax_error` 関数と新しく追加された `new_dotname` 関数にデバッグ用のトレースコードが追加されています。これは、コンパイラの開発者がパーサーの動作をデバッグする際に、これらの重要な関数がいつ呼び出され、どのような引数で実行されたかを追跡できるようにするためのものです。

## コアとなるコードの解説

このコミットの核となる変更は、`parser` 構造体に新しく追加された `new_dotname` メソッドです。

```go
// go.y:dotname (partial)
func (p *parser) new_dotname(pkg *Node) *Node {
	if trace && Debug['x'] != 0 {
		defer p.trace("new_dotname")()
	}

	sel := p.sym() // ドットの右側の識別子（セレクタ）を取得
	if pkg.Op == OPACK { // 左側のオペランドがパッケージの場合
		s := restrictlookup(sel.Name, pkg.Name.Pkg) // パッケージ内でシンボルをルックアップ
		pkg.Used = true // パッケージが使用されたことをマーク
		return oldname(s) // 解決されたシンボルに対応するノードを返す
	}
	// 左側のオペランドがパッケージではない式の場合
	return Nod(OXDOT, pkg, newname(sel)) // OXDOTノードを生成し、左の子に式、右の子にセレクタを設定
}
```

この `new_dotname` 関数は、Go言語の構文解析において `.` (ドット) 演算子を処理する共通ロジックをカプセル化しています。

1.  **`sel := p.sym()`**: まず、ドットの後に続く識別子（セレクタ、例えば `fmt.Println` の `Println` や `obj.Field` の `Field`）をパーサーの `sym()` メソッドを使って取得します。
2.  **`if pkg.Op == OPACK`**: 引数 `pkg` はドットの左側の式（またはパッケージ名）を表すASTノードです。この条件は、左側のオペランドがパッケージ (`OPACK` ノード) であるかどうかをチェックします。
    *   もし `pkg` がパッケージであれば、それは `package.Symbol` の形式です。この場合、`restrictlookup` 関数を使って、`pkg.Name.Pkg` で指定されたパッケージ内で `sel.Name` というシンボルを検索し、そのシンボルに対応するノードを `oldname(s)` で返します。`pkg.Used = true` は、このパッケージがコード内で実際に使用されたことをマークします。
    *   もし `pkg` がパッケージでなければ、それは `expression.Field` や `expression.Method` のようなセレクタの形式です。この場合、`Nod(OXDOT, pkg, newname(sel))` を呼び出して `OXDOT` (ドット演算子) ノードを生成します。この `OXDOT` ノードは、左の子に `pkg` (ドットの左側の式)、右の子に `newname(sel)` (ドットの右側のセレクタ名) を持ちます。

この `new_dotname` 関数が導入されたことで、以前はパーサー内の3つの異なる場所で重複して記述されていた上記のロジックが、この単一の関数呼び出しに置き換えられました。これにより、コードの重複が解消され、パーサーのコードベース全体がより簡潔で理解しやすくなりました。

また、`syntax_error` 関数にデバッグ用のトレースが追加されたことも注目すべき点です。これは、コンパイラの開発者が構文エラーが発生した際のパーサーの内部状態をより詳細に把握できるようにするためのもので、デバッグ作業の効率化に貢献します。

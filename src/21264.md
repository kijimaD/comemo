# [インデックス 21264] ファイルの概要

このコミットは、Goランタイムのメモリ管理における重要な改善を導入しています。具体的には、初期アリーナの仮想メモリ予約が失敗した場合に、より小さなアリーナサイズで再試行するメカニズムを追加することで、特にAndroid Lのような、他のランタイム（ARTなど）が積極的に仮想メモリを予約する環境でのGoプログラムの起動の信頼性を向上させています。

## 変更の背景

このコミットの背景には、Goプログラムが起動時に仮想メモリ領域を予約する際の問題がありました。特に、Android Lのような環境では、ART（Android Runtime）が非常に積極的に仮想メモリを予約するため、Goランタイムが初期アリーナ（メモリヒープの主要部分）を予約しようとしたときに、十分な連続した仮想アドレス空間を確保できないことがありました。これにより、Goプログラムの起動が失敗する可能性がありました。

この問題は、Goランタイムが最初に大きな仮想メモリ領域（例えば512MB）を予約しようとし、それが失敗した場合に、代替手段なしで終了してしまうことに起因していました。このコミットは、この問題を解決するために、予約が失敗した場合に、より小さなアリーナサイズ（例えば256MB）で再試行するロジックを導入しています。これにより、仮想メモリの競合が激しい環境でも、Goプログラムがより確実に起動できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムのメモリ管理に関する基本的な概念を理解しておく必要があります。

*   **Goランタイムのメモリ管理**: Goは独自のメモリマネージャとガベージコレクタを持っています。プログラムがメモリを要求すると、GoランタイムはOSから仮想メモリを確保し、それを管理します。
*   **アリーナ (Arena)**: Goランタイムがヒープとして使用するためにOSから予約する連続した仮想メモリ領域のことです。Goのオブジェクトは、このアリーナ内に割り当てられます。
*   **`mallocinit()`**: Goプログラムの起動時に呼び出されるランタイムの初期化関数の一つで、メモリヒープの初期化を担当します。この関数内で、アリーナの仮想メモリ予約が行われます。
*   **`sysReserve()`**: OSに対して仮想メモリ領域を予約するランタイム内部の関数です。これは、実際にメモリをコミット（物理メモリと関連付ける）するのではなく、単にアドレス空間を確保するだけです。
*   **`mheap`**: Goランタイムのグローバルなヒープ構造体です。アリーナの開始アドレス (`arena_start`) や終了アドレス (`arena_end`) などの情報を含みます。
*   **`mspan`**: Goランタイムのメモリ管理の基本単位の一つで、連続したページ（通常は8KB）の集合です。オブジェクトは`mspan`から割り当てられます。
*   **`bitmap`**: アリーナ内のメモリブロックが使用されているかどうかを追跡するためのビットマップです。
*   **`_PageSize`**: OSのページサイズ（通常は4KBまたは8KB）を表す定数です。メモリの割り当てはページ単位で行われます。
*   **`_MaxMem`**: 64ビットシステムにおける最大仮想メモリサイズ（通常は128TB）です。
*   **`_MaxArena32`**: 32ビットシステムにおける最大アリーナサイズ（通常は2GB）です。
*   **仮想メモリ (Virtual Memory)**: OSが提供する抽象化されたメモリ空間です。プログラムは仮想アドレスを使用し、OSがそれを物理アドレスにマッピングします。仮想メモリの予約は、物理メモリを消費せずにアドレス空間を確保する操作です。

## 技術的詳細

このコミットは、`src/runtime/malloc1.go`ファイルの`mallocinit`関数内のメモリ予約ロジックを変更しています。

変更前は、32ビットシステムにおいて、Goランタイムはまず512MBの初期アリーナを予約しようとします。この予約が`sysReserve`によって失敗した場合、Goランタイムは`gothrow`を呼び出してパニックを起こし、プログラムが終了していました。

変更後は、`arenaSizes`というスライスが導入され、複数のアリーナサイズ（最初は512MB、次に256MB）が定義されています。`mallocinit`関数は、これらのサイズを順番に試行するループを持つようになりました。

具体的には、以下のステップでメモリ予約を試みます。

1.  **初期アリーナサイズの設定**: `arenaSizes`スライスから最初のアリーナサイズ（512MB）を取得します。
2.  **`bitmapSize`と`spansSize`の計算**: 選択された`arenaSize`に基づいて、`bitmap`と`mspan`に必要なサイズを計算します。
3.  **`limit`の考慮**: もしメモリ制限（`limit`）が設定されている場合、`arenaSize`、`bitmapSize`、`spansSize`の合計が`limit`を超えないように調整します。これにより、メモリ制限内でアリーナが収まるようにします。
4.  **`spansSize`のページアラインメント**: `spansSize`をページサイズに丸めます。
5.  **予約アドレスの決定**: `sysReserve`に渡す仮想アドレスのヒントを計算します。これは、実行バイナリの末尾から少し離れた場所（1/4 MB）から開始し、MB境界に丸められます。これは、OSが予約アドレスを調整する際のバグ（特にQEMUのようなエミュレータでの問題）を回避するためです。
6.  **`pSize`の計算**: `bitmapSize`、`spansSize`、`arenaSize`、および追加のページサイズを合計して、予約する仮想メモリの総サイズ`pSize`を計算します。
7.  **`sysReserve`の呼び出し**: 計算されたアドレス`p`とサイズ`pSize`で`sysReserve`を呼び出し、仮想メモリを予約します。
8.  **予約の成否判定と再試行**:
    *   `sysReserve`が成功し、`p`が0以外の場合、ループを抜けて初期化を続行します。
    *   `sysReserve`が失敗し、`p`が0の場合、ループの次のイテレーションに進み、`arenaSizes`スライスから次のより小さなアリーナサイズ（256MB）を試行します。
9.  **最終的な失敗**: すべてのアリーナサイズを試しても予約が成功しない場合、`gothrow("runtime: cannot reserve arena virtual address space")`を呼び出してパニックを起こします。

この変更により、Goランタイムは、最初に大きなアリーナを予約できなかった場合でも、より小さなアリーナで再試行することで、起動の成功率を高めることができます。これは、特に仮想メモリが断片化している、または他のプロセスによって大量に消費されている環境で有効です。

## コアとなるコードの解説

このコミットの主要な変更点は、32ビットシステムにおける初期アリーナの仮想メモリ予約のロバスト性を高めることです。

1.  **変数名の変更**:
    *   `arena_size`, `bitmap_size`, `spans_size`, `p_size` といった変数名が、Goの命名規則に合わせて `arenaSize`, `bitmapSize`, `spansSize`, `pSize` に変更されています。これは機能的な変更ではなく、コードの可読性と一貫性を向上させるためのものです。

2.  **`arenaSizes` スライスの導入**:
    *   新たに `arenaSizes := []uintptr{512 << 20, 256 << 20}` というスライスが導入されました。これは、初期アリーナとして試行する仮想メモリサイズの候補リストです。`512 << 20` は512MB、`256 << 20` は256MBを意味します。

3.  **予約試行ループの追加**:
    *   以前は単一の`sysReserve`呼び出しで予約を試みていましたが、変更後は `for _, arenaSize := range arenaSizes` ループが追加されました。このループにより、Goランタイムはまず512MBのアリーナを予約しようとし、それが失敗した場合は256MBのアリーナを予約しようとします。
    *   ループ内で、選択された `arenaSize` に基づいて `bitmapSize` と `spansSize` が再計算されます。
    *   `sysReserve` の呼び出しもループ内に移動し、予約が成功 (`p != 0`) した場合は `break` でループを抜けます。これにより、最初のアリーナサイズで成功すれば、それ以上小さなサイズを試す必要がなくなります。

4.  **コメントの追加**:
    *   「If we fail to allocate, try again with a smaller arena. This is necessary on Android L where we share a process with ART, which reserves virtual memory aggressively.」というコメントが追加され、この変更の具体的な背景と目的（Android LでのARTとの仮想メモリ競合問題の解決）が明確に示されています。

これらの変更により、Goランタイムは、仮想メモリの予約が困難な環境（特にAndroid L）でも、より柔軟に対応し、プログラムの起動失敗を減らすことができるようになりました。これは、Goアプリケーションの移植性と信頼性を向上させる上で重要な改善です。

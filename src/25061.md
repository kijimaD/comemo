# [インデックス 25061] ファイルの概要

このコミットは、Go言語の標準ライブラリ`bufio`パッケージ内の`Scanner`型におけるバッファ拡張時の整数オーバーフロー計算の不具合を修正するものです。具体的には、`Scanner`が内部バッファを2倍に拡張しようとする際に、その計算結果が`int`型の最大値を超えてしまう可能性があり、その結果として不正なバッファサイズが設定されることを防ぐための変更が加えられました。

## 変更の背景

Goの`bufio.Scanner`は、入力ストリームを効率的に読み込み、行や単語などのトークンに分割するために使用されます。この`Scanner`は内部的にバッファを保持しており、現在のバッファサイズではトークンを格納しきれない場合に、バッファを拡張するロジックを持っています。一般的なバッファ拡張戦略として、現在のバッファサイズを2倍にするという方法が用いられます。

このコミットが修正しようとしている問題は、この「バッファサイズを2倍にする」という算術演算自体が整数オーバーフローを引き起こす可能性があったことです。Go言語の`int`型は、その実行環境のアーキテクチャ（32ビットまたは64ビット）に依存する固定ビット幅の符号付き整数であり、デフォルトでは算術オーバーフローチェックを行いません。

もし`len(s.buf)`（現在のバッファ長）が`int`型の最大値の半分よりも大きい場合、`len(s.buf) * 2`という計算は`int`型の最大値を超えてしまい、結果として予期せぬ小さな値（ラップアラウンド）になる可能性があります。このような不正な`newSize`が計算されると、`Scanner`は意図しない小さなバッファを割り当てようとしたり、その他の未定義の動作を引き起こす可能性がありました。

コミットメッセージにある「I was being too clever, as usual. Write the obvious code to make sure that when we grow the buffer we don't overflow.」というRob Pike氏のコメントは、以前のオーバーフロー対策が不十分であったか、あるいは意図した通りに機能していなかったことを示唆しています。この変更は、バッファ拡張時の算術オーバーフローを明示的に検出し、安全に処理することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と`bufio.Scanner`の内部動作に関する知識が必要です。

1.  **Goの`int`型と整数オーバーフロー**:
    *   Goの`int`型は、符号付き整数であり、そのサイズはコンパイルされるシステムに依存します（通常32ビットまたは64ビット）。
    *   Goの算術演算は、C言語などと同様に、デフォルトでは整数オーバーフローをチェックしません。例えば、`int`の最大値に1を加算すると、最小値にラップアラウンドするなどの予期せぬ結果が生じます。
    *   このため、大きな数値を扱う際や、バッファサイズ計算のように乗算を行う際には、明示的なオーバーフローチェックが必要になることがあります。

2.  **`bufio.Scanner`の基本**:
    *   `bufio.Scanner`は、`io.Reader`からデータを読み込み、定義された区切り文字（デフォルトでは改行）に基づいてトークン（文字列）を抽出するための便利なインターフェースを提供します。
    *   内部的には、読み込んだデータを保持するためのバイトスライス（バッファ）を使用します。

3.  **`bufio.Scanner`のバッファ拡張**:
    *   `Scanner`は、現在のバッファにトークン全体が収まらない場合、より大きなバッファを確保しようとします。
    *   一般的な戦略として、新しいバッファサイズは現在のバッファサイズの2倍として計算されます (`newSize := len(s.buf) * 2`)。
    *   `Scanner`には`maxTokenSize`という設定があり、これは`Scanner`が処理できる単一トークンの最大サイズを制限します。このサイズを超過するトークンが見つかった場合、`bufio.ErrTooLong`エラーが返されます。

4.  **`int(^uint(0) >> 1)`イディオム**:
    *   このGoのイディオムは、現在のシステムにおける`int`型の最大正の値、すなわち`math.MaxInt`を取得するために使用されます。
    *   `uint(0)`: 符号なし整数0。
    *   `^uint(0)`: ビットごとのNOT演算。これにより、すべてのビットが1に設定された`uint`の最大値（例: 64ビットシステムでは`math.MaxUint64`）が得られます。
    *   `>> 1`: 1ビット右シフト。これにより、`uint`の最大値が2で割られ、`int`の最大正の値が得られます。これは、符号なし整数の最大値の半分が、符号付き整数の最大値に相当するためです（最上位ビットが符号ビットとして使用されるため）。

## 技術的詳細

このコミットの技術的な核心は、`bufio.Scanner`の`Scan()`メソッドにおけるバッファ拡張ロジックの堅牢性を向上させることにあります。

以前の実装では、`Scanner.Buffer()`メソッド内で`maxTokenSize`を`int`型の最大値でクランプする（`if max > maxInt { max = maxInt }`）ことで、間接的にオーバーフローを防ごうとする試みがありました。しかし、このアプローチは不十分でした。なぜなら、`newSize`の計算は`len(s.buf) * 2`に基づいて行われ、`maxTokenSize`の値がどうであれ、`len(s.buf)`自体が十分に大きければ、この乗算がオーバーフローする可能性があったからです。

新しい実装では、`Scan()`メソッド内で`newSize`を計算する直前に、以下の明示的なオーバーフローチェックが導入されました。

```go
const maxInt = int(^uint(0) >> 1)
if len(s.buf) >= s.maxTokenSize || len(s.buf) > maxInt/2 {
    s.setErr(ErrTooLong)
    return false
}
newSize := len(s.buf) * 2
```

この変更のポイントは以下の通りです。

1.  **`maxInt`の局所化**: `maxInt`定数が`Scan()`メソッド内に定義されました。これにより、この定数が使用される文脈が明確になり、他の場所での誤用を防ぎます。
2.  **算術オーバーフローの直接チェック**: `len(s.buf) > maxInt/2`という条件が追加されました。これは、現在のバッファ長`len(s.buf)`が`int`型の最大値の半分を超えているかどうかをチェックします。もし超えている場合、`len(s.buf) * 2`という計算は確実に`int`型の最大値を超えてオーバーフローするため、`ErrTooLong`エラーを発生させて`Scan()`を終了します。これにより、不正な`newSize`が計算されることを未然に防ぎます。
3.  **`maxTokenSize`チェックとの統合**: `len(s.buf) >= s.maxTokenSize`という既存のチェックと`len(s.buf) > maxInt/2`が論理OR (`||`) で結合されました。これは、バッファが`maxTokenSize`を超えた場合、またはバッファ拡張の乗算がオーバーフローする場合のいずれかにおいて、`ErrTooLong`を返すことを意味します。
4.  **`Buffer()`メソッドからの冗長なコードの削除**: `Scanner.Buffer()`メソッドにあった`maxInt`の定義と`if max > maxInt { max = maxInt }`というロジックは、`Scan()`メソッドでより直接的かつ正確なオーバーフローチェックが導入されたため、冗長となり削除されました。これにより、コードの重複が解消され、ロジックが簡素化されました。

この修正により、`bufio.Scanner`は、非常に大きなトークンを処理しようとした際に、バッファ拡張の算術計算自体がオーバーフローするリスクから保護され、より堅牢になりました。

## コアとなるコードの解説

### `Scanner.Scan()` メソッド内の変更

```go
 			// Guarantee no overflow in the multiplication below.
 			const maxInt = int(^uint(0) >> 1)
 			if len(s.buf) >= s.maxTokenSize || len(s.buf) > maxInt/2 {
 				s.setErr(ErrTooLong)
 				return false
 			}
 			newSize := len(s.buf) * 2
```

*   **`const maxInt = int(^uint(0) >> 1)`**: ここで、現在のシステムにおける`int`型の最大正の値が`maxInt`として定義されます。これは、後続のオーバーフローチェックの基準となります。
*   **`if len(s.buf) >= s.maxTokenSize || len(s.buf) > maxInt/2`**:
    *   `len(s.buf) >= s.maxTokenSize`: これは既存のチェックで、現在のバッファ長が`Scanner`が許容する最大トークンサイズを超えている場合に`ErrTooLong`を返します。
    *   `len(s.buf) > maxInt/2`: これが新たに追加されたオーバーフローチェックです。もし現在のバッファ長が`int`型の最大値の半分を超えている場合、次の行で行われる`len(s.buf) * 2`の計算は確実に`int`型のオーバーフローを引き起こします。この条件が真であれば、`s.setErr(ErrTooLong)`を呼び出してエラーを設定し、`false`を返して`Scan()`の処理を中断します。これにより、不正な`newSize`が計算され、その後のメモリ割り当てで問題が発生するのを防ぎます。
*   **`newSize := len(s.buf) * 2`**: 上記のチェックを通過した場合のみ、安全にバッファサイズを2倍にする計算が実行されます。

### `Scanner.Buffer()` メソッド内の変更

```diff
-\t// Guarantee no overflow: we multiply len(s.buf) by two in Scan,\n-\t// but only if it exceeds maxTokenSize.\n-\tconst maxInt = int(^uint(0) >> 1)\n-\tif max > maxInt {\n-\t\tmax = maxInt\n-\t}\n \ts.maxTokenSize = max
```

*   以前は、`Scanner.Buffer()`メソッド内で`maxTokenSize`を`maxInt`でクランプするロジックが存在しました。これは、`Scan()`メソッドでのバッファ拡張時の乗算オーバーフローを間接的に防ぐことを意図していたと考えられます。
*   しかし、`Scan()`メソッド内で直接的な算術オーバーフローチェックが導入されたため、この`Buffer()`メソッド内のロジックは冗長となり、削除されました。これにより、オーバーフロー対策のロジックが一箇所に集約され、コードの可読性と保守性が向上しました。

## 元コミット内容

このコミットの目的は、Goランタイムにおいて、いくつかのデッドポインタ（もはや有効なオブジェクトを指していないポインタ）をゼロ化することです。

主な変更点は以下の通りです。
*   チャネル操作において、クローズされたチャネルでパニックが発生した場合に、`gp.waiting`（goroutineが待機している状態を示すポインタ）のゼロ化が見落とされていた点を修正します。
*   `m.morebuf.g`（スタック拡張に関連するバッファ内のgoroutineポインタ）がゼロ化されていなかった点を修正します。後者については、直接的な問題を引き起こすとは予想されていないものの、念のための対応です。

## 変更の背景

Goランタイムは、ガベージコレクション（GC）によってメモリを自動的に管理します。GCは、到達可能なオブジェクトを特定し、それ以外のメモリを解放することで機能します。このプロセスにおいて、デッドポインタ（もはや有効なオブジェクトを指していないポインタ）がメモリ上に残っていると、GCが誤ってそれらを有効な参照と判断し、本来解放されるべきメモリを保持し続けてしまう可能性があります。これはメモリリークや、最悪の場合、不正なメモリアクセスによるクラッシュを引き起こす原因となり得ます。

このコミットは、このような潜在的な問題を未然に防ぐための保守的な改善です。特に、チャネルのパニック時やスタック拡張といった、通常とは異なるコードパスにおいて、ポインタが適切にゼロ化されないケースが存在したため、それらを修正することでランタイムの堅牢性とメモリ安全性を向上させています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する中核部分です。これには、goroutineのスケジューリング、ガベージコレクション、チャネル操作、メモリ管理などが含まれます。Goプログラムは、OSのスレッド上で直接実行されるのではなく、ランタイムが管理する軽量なgoroutineとして実行されます。

*   **goroutine (G)**: Goにおける軽量な実行単位であり、OSのスレッドよりもはるかに少ないリソースで作成・管理されます。Goランタイムのスケジューラによって、複数のgoroutineが少数のOSスレッド上で多重化されて実行されます。各goroutineは`G`構造体によって表現され、その状態（実行中、待機中、実行可能など）やスタック情報などが含まれます。

*   **`gp.waiting`**: `G`構造体（goroutine）のフィールドの一つで、goroutineがチャネル操作（送受信）などでブロックされ、待機状態になった際に、その待機情報を保持する`sudog`構造体へのポインタです。goroutineが待機状態から解放されると、このポインタは`nil`にゼロ化されるべきです。

*   **`m.morebuf.g`**: GoランタイムのM (Machine) 構造体（OSスレッドを表す）のフィールドです。`morebuf`は、スタックの拡張や縮小などの操作時に一時的に使用されるバッファに関連する情報を持つ構造体です。`morebuf.g`は、このバッファに関連するgoroutineへのポインタを保持します。スタック操作が完了した後、このポインタもゼロ化されることが望ましいです。

*   **ゼロ化 (Zeroing)**: メモリ上のポインタやデータ領域を、`nil`（Goにおけるゼロ値）やゼロビットで上書きする操作です。これは、以下のような目的で行われます。
    *   **メモリ安全性の向上**: 古い、無効なポインタが残ることを防ぎ、ガベージコレクタが誤ってそれらを有効な参照と判断するのを防ぎます。
    *   **メモリリークの防止**: 不要になったオブジェクトへの参照が残ることで、GCがそのオブジェクトを回収できなくなる「ポインタリーク」を防ぎます。
    *   **デバッグの容易化**: デバッグ時に、無効なポインタが指す不正なメモリ内容によって混乱するのを防ぎます。

*   **チャネル (Channel)**: goroutine間で値を安全に送受信するためのGoの組み込み機能です。チャネルは、同期的な通信（バッファなしチャネル）と非同期的な通信（バッファありチャネル）の両方をサポートします。チャネル操作中にgoroutineがブロックされることがあります。

*   **`sudog`**: `s`udogは、`s`ingle `u`ser `dog`の略で、チャネル操作などでブロックされたgoroutineの待機情報を表現するためにGoランタイムが内部的に使用する構造体です。`sudog`は、待機しているgoroutine、チャネル、送受信するデータなどの情報を含みます。

*   **`goparkunlock`**: goroutineをパーク（待機）状態にするGoランタイムの内部関数です。この関数が呼び出されると、現在のgoroutineは実行を中断し、指定されたロックを解放して、スケジューラによって別のgoroutineが実行されるのを待ちます。

*   **`gothrow`**: Goランタイムの内部関数で、致命的なエラーが発生した場合にパニックを引き起こし、プログラムを終了させます。

## 技術的詳細

このコミットは、Goランタイムのメモリ管理と堅牢性に関する細かな改善です。主な焦点は、特定の条件下でデッドポインタが適切にゼロ化されないという潜在的な問題に対処することです。

1.  **`gp.waiting`のゼロ化の修正**:
    *   Goのチャネル操作（`chansend`と`chanrecv`）では、goroutineがチャネルの準備ができるまで待機することがあります。この待機状態は`gp.waiting`ポインタによって管理されます。
    *   コミットメッセージによると、「クローズされたチャネルでパニックが発生した場合に、`gp.waiting`のゼロ化が見落とされていた」とのことです。これは、通常のエラーハンドリングパスや正常な終了パスではゼロ化が行われるものの、予期せぬパニックパスではその処理がスキップされる可能性があったことを示唆しています。
    *   `gp.waiting`がゼロ化されないと、そのポインタが古い`sudog`構造体を指したままになり、ガベージコレクタがその`sudog`を「到達可能」と誤認し、メモリを解放できなくなる可能性があります。これはメモリリークにつながるだけでなく、デバッグ時に混乱を招く原因にもなります。
    *   このコミットでは、`goparkunlock`（goroutineを待機状態から復帰させる関数）の直後に`gp.waiting = nil`を配置することで、goroutineが待機状態から解放された直後に、どのような状況であっても`gp.waiting`が確実にゼロ化されるように変更されています。これにより、パニックパスを含むすべてのケースでメモリの整合性が保たれます。

2.  **`m.morebuf.g`のゼロ化の追加**:
    *   `m.morebuf.g`は、Goランタイムがgoroutineのスタックを拡張する際に使用される一時的なバッファに関連するgoroutineポインタです。
    *   コミットメッセージでは、「後者（`m.morebuf.g`のゼロ化）は直接的な問題を引き起こすとは予想されていないが、念のため」と述べられています。これは、このポインタが通常は短命であり、GCが誤って参照する可能性は低いものの、将来的な変更や特定のコーナーケースで問題が発生するリスクを排除するための予防的な措置であることを意味します。
    *   スタック拡張処理が完了した後、このポインタが古いgoroutineを指したまま残ることを防ぐために、明示的に`nil`に設定されます。これにより、ランタイムの内部状態がよりクリーンに保たれ、潜在的なバグのリスクがさらに低減されます。

これらの変更は、Goランタイムの内部的な堅牢性とメモリ安全性を高めるための、細かではあるが重要な改善です。デッドポインタのゼロ化は、ガベージコレクタの効率を向上させ、メモリリークや不正なメモリ参照といった深刻な問題を防ぐ上で不可欠なプラクティスです。

## コアとなるコードの解説

### `src/runtime/chan.go` の変更

`chansend` および `chanrecv` 関数は、それぞれチャネルへの送信と受信を処理します。これらの関数内でgoroutineがブロックされる場合、`gp.waiting` ポインタが使用されます。

**変更前 (`chansend` の一部):**

```go
		if mysg != gp.waiting {
			gothrow("G waiting list is corrupted!")
		}
		gp.waiting = nil
		releasereadog(mysg) // この行は変更なし
		return true
	}
```

**変更後 (`chansend` の一部):**

```go
		// someone woke us up.
		if mysg != gp.waiting {
			gothrow("G waiting list is corrupted!")
		}
		gp.waiting = nil // ここに移動・追加
		if gp.param == nil {
			if c.closed == 0 {
				gothrow("chansend: spurious wakeup")
			}
			// Channel is already closed.
		}
		// ... (mysg.releasetime > 0 のブロックは変更なし)
		releasereadog(mysg) // この行は変更なし
		return true
	}
```

同様の変更が `chanrecv` 関数にも適用されています。

**解説:**
この変更の核心は、`gp.waiting = nil` の行が `goparkunlock` (goroutineが待機状態から復帰する直前) の直後に移動または追加されたことです。
変更前は、`gp.waiting = nil` の前にいくつかの条件分岐が存在していました。特に、チャネルがクローズされてパニックが発生するようなエッジケースでは、このゼロ化の処理がスキップされる可能性がありました。
変更後は、goroutineが待機状態から復帰した直後、つまり `goparkunlock` が完了した直後に `gp.waiting` が確実に `nil` に設定されるようになりました。これにより、どのような状況（正常な復帰、パニックによる復帰など）であっても、デッドポインタが残ることを防ぎ、メモリの整合性が向上します。`mysg != gp.waiting` のチェックは、`gp.waiting` が正しく設定されているかどうかの整合性チェックであり、その後にゼロ化が行われることで、より安全な状態遷移が保証されます。

### `src/runtime/stack.c` の変更

`runtime·newstack` 関数は、goroutineのスタックが不足し、拡張が必要になった際に呼び出されるGoランタイムの内部関数です。

**変更前 (`runtime·newstack` の一部):**

```c
	g->m->morebuf.pc = (uintptr)nil;
	g->m->morebuf.lr = (uintptr)nil;
	g->m->morebuf.sp = (uintptr)nil;
	// g->m->morebuf.g はゼロ化されていない
```

**変更後 (`runtime·newstack` の一部):**

```c
	g->m->morebuf.pc = (uintptr)nil;
	g->m->morebuf.lr = (uintptr)nil;
	g->m->morebuf.sp = (uintptr)nil;
	g->m->morebuf.g = (G*)nil; // この行が追加された

	runtime·casgstatus(gp, Grunning, Gwaiting);
	gp->waitreason = runtime·gostringnocopy((byte*)"stack growth");
```

**解説:**
この変更により、`runtime·newstack` 関数内で、`g->m->morebuf.g` ポインタが明示的に `nil` にゼロ化されるようになりました。`morebuf` はスタック拡張処理中に一時的に使用されるバッファであり、その中に含まれる `g` ポインタも、処理が完了した後は不要になります。
このゼロ化は、`morebuf.g` が古い、無効な `G` 構造体を指したままになることを防ぎます。コミットメッセージにあるように、このポインタが問題を引き起こす可能性は低いとされていますが、予防的な措置としてゼロ化することで、ランタイムの内部状態をよりクリーンに保ち、潜在的なメモリ関連のバグのリスクをさらに低減します。

これらの変更は、Goランタイムのメモリ管理における細部へのこだわりを示しており、システムの安定性と信頼性を高める上で重要な役割を果たします。

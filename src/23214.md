# [インデックス 23214] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ (GC) におけるデバッグ関数 `gcDumpObject` のバグを修正します。具体的には、`gcDumpObject` がヒープ以外のポインタを処理しようとした際に発生するパニックを防ぐための変更です。

## コミット

```
runtime: fix gcDumpObject on non-heap pointers

gcDumpObject is used to print the source and destination objects when
checkmark find a missing mark. However, gcDumpObject currently assumes
the given pointer will point to a heap object. This is not true of the
source object during root marking and may not even be true of the
destination object in the limited situations where the heap points
back in to the stack.

If the pointer isn't a heap object, gcDumpObject will attempt an
out-of-bounds access to h_spans. This will cause a panicslice, which
will attempt to construct a useful panic message. This will cause a
string allocation, which will lead mallocgc to panic because the GC is
in mark termination (checkmark only happens during mark termination).

Fix this by checking that the pointer points into the heap arena
before attempting to use it as an arena pointer.

Reviewed-on: https://go-review.googlesource.com/9498
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goのガベージコレクタ (GC) は、メモリリークを防ぎ、メモリ管理を自動化する重要なコンポーネントです。GCのデバッグプロセスにおいて、`gcDumpObject` という関数が、マークフェーズ中に「マークされていないオブジェクト」が発見された際に、そのオブジェクトの情報をダンプするために使用されます。

しかし、この `gcDumpObject` 関数には問題がありました。それは、引数として渡されるポインタが常にヒープ上のオブジェクトを指していると仮定していた点です。実際には、ルートマーキング（GCがプログラムのルートから到達可能なオブジェクトをマークするプロセス）中に、ソースオブジェクトがヒープ上ではない（例えばスタック上にある）場合があります。また、稀なケースではありますが、ヒープ上のオブジェクトがスタック上のオブジェクトを指している場合、デスティネーションオブジェクトもヒープ外である可能性がありました。

このような非ヒープポインタが `gcDumpObject` に渡されると、関数内でヒープ関連のデータ構造 (`h_spans` など) へのアクセスを試み、結果として範囲外アクセス (out-of-bounds access) が発生し、`panicslice` というパニックを引き起こしていました。さらに深刻な問題は、このパニックメッセージを構築する際に文字列の割り当てが必要となり、それが `mallocgc` (Goランタイムのメモリ割り当て関数) を呼び出すことでした。GCがマーク終了フェーズ（`checkmark` が実行されるフェーズ）にある最中に `mallocgc` が呼ばれると、GCの整合性が崩れるため、`mallocgc` 自体がパニックするという、二重のパニック状態に陥っていました。

この連鎖的なパニックは、GCのデバッグを極めて困難にし、ランタイムの安定性にも影響を与える可能性がありました。このコミットは、この根本原因を修正し、`gcDumpObject` が非ヒープポインタを安全に処理できるようにすることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。これは、オブジェクトを白（未訪問）、灰色（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類し、到達可能なオブジェクトをマークしていく方式です。

*   **マークフェーズ (Mark Phase)**: GCのルート（グローバル変数、スタック上の変数など）から開始し、到達可能なすべてのオブジェクトをマークします。このフェーズ中に、オブジェクトがマークされているかどうかのチェックが行われます。
*   **マーク終了フェーズ (Mark Termination Phase)**: マークフェーズの終了を処理し、次のフェーズへの移行準備を行います。このフェーズ中に `checkmark` のような整合性チェックが行われることがあります。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不能な）オブジェクトを解放し、メモリを再利用可能にします。

### `gcDumpObject` 関数

`gcDumpObject` は、Goランタイムの内部デバッグ関数です。GCのマークフェーズ中に、何らかの理由でオブジェクトのマークが欠落していることが検出された場合（例えば、`checkmark` が異常を検出した場合）、そのオブジェクトのメモリ内容や関連情報を標準出力にダンプするために使用されます。これは、GCのバグを特定し、修正するために非常に重要な情報を提供します。

### ヒープ (Heap) とスタック (Stack)

Goプログラムでは、メモリは主に以下の2つの領域に分けられます。

*   **ヒープ (Heap)**: プログラム実行中に動的に割り当てられるメモリ領域です。`make` や `new` で作成されるオブジェクト、あるいは関数間で共有される可能性のある大きなデータ構造などがヒープに割り当てられます。GCの主な管理対象はこのヒープ領域です。
*   **スタック (Stack)**: 関数の呼び出しごとに割り当てられるメモリ領域です。ローカル変数や関数の引数などがスタックに割り当てられます。関数呼び出しが終了すると、その関数のスタックフレームは解放されます。スタックは通常、GCの直接的な管理対象ではありませんが、GCはスタック上のポインタをスキャンして、ヒープ上のオブジェクトへの参照を見つけます（ルートマーキング）。

### `mheap_` と `arena_start`, `arena_used`

Goランタイムは、独自のメモリ管理システムを持っています。`mheap_` は、Goランタイムが管理するグローバルなヒープ構造体です。この構造体には、ヒープ領域の開始アドレス (`arena_start`) と使用中のヒープ領域の終了アドレス (`arena_used`) など、ヒープに関する重要な情報が含まれています。これらの値は、特定のポインタがGoランタイムによって管理されているヒープ領域内にあるかどうかを判断するために使用されます。

### `panicslice` と `mallocgc`

*   **`panicslice`**: Goランタイム内部で、スライス操作（インデックスアクセスなど）が範囲外で行われた場合に発生するパニックです。このパニックが発生すると、ランタイムはエラーメッセージを生成しようとします。
*   **`mallocgc`**: Goランタイムの内部メモリ割り当て関数です。ユーザーコードが `make` や `new` を使用してメモリを割り当てる際、最終的にこの関数が呼び出されます。GCがアクティブな（特にマーク終了フェーズのような重要な）期間中に `mallocgc` が呼び出されると、GCの内部状態が不安定になる可能性があるため、通常は禁止されています。

## 技術的詳細

このコミットが修正する問題は、`gcDumpObject` 関数が、渡されたポインタが常にGoランタイムの管理するヒープ領域内にあると誤って仮定していたことに起因します。

`gcDumpObject` は、ポインタ `obj` を受け取ると、そのポインタが指すメモリページに関する情報を取得するために、ヒープの内部構造 (`mheap_` の `h_spans` など) を参照しようとします。この処理は、ポインタがヒープ内にあることを前提としています。

しかし、GCのルートマーキング中には、スタック上のオブジェクトがソースポインタとして `gcDumpObject` に渡されることがあります。また、ヒープ上のオブジェクトがスタック上のオブジェクトを指しているような特殊な状況では、デスティネーションポインタもスタック上にある可能性があります。

このような非ヒープポインタが `gcDumpObject` に渡されると、`obj` のアドレスに基づいて `mheap_` の内部構造を計算しようとしますが、`obj` がヒープ範囲外であるため、`h_spans` などの配列に対して範囲外アクセスが発生します。これにより、Goランタイムは `panicslice` という内部パニックを引き起こします。

さらに悪いことに、この `panicslice` が発生すると、Goランタイムはパニックメッセージを生成しようとします。パニックメッセージの生成には、通常、文字列の割り当てが必要となり、そのために `mallocgc` が呼び出されます。しかし、この問題が発生する `checkmark` はGCのマーク終了フェーズ中に実行されます。GCがマーク終了フェーズにある間は、GCの整合性を保つために `mallocgc` によるメモリ割り当ては厳しく制限されています。したがって、このタイミングで `mallocgc` が呼び出されると、`mallocgc` 自体がパニックするという、いわゆる「パニック中のパニック」が発生し、ランタイムがクラッシュする原因となっていました。

このコミットは、`gcDumpObject` の冒頭で、渡されたポインタ `obj` が実際にGoランタイムの管理するヒープ領域内にあるかどうかを `mheap_.arena_start` と `mheap_.arena_used` を使ってチェックすることで、この問題を解決します。ヒープ領域外のポインタであれば、エラーメッセージを出力してすぐにリターンすることで、範囲外アクセスとそれに続く連鎖的なパニックを防ぎます。

## コアとなるコードの解説

追加されたコードは以下の `if` 文です。

```go
if obj < mheap_.arena_start || obj >= mheap_.arena_used {
	print(label, "=", hex(obj), " is not a heap object\n")
	return
}
```

この `if` 文は、`gcDumpObject` 関数が受け取ったポインタ `obj` が、Goランタイムが管理するヒープ領域の範囲内にあるかどうかをチェックしています。

*   `mheap_.arena_start`: Goランタイムが管理するヒープ領域の開始アドレスです。
*   `mheap_.arena_used`: Goランタイムが現在使用しているヒープ領域の終了アドレス（の次）です。

条件式 `obj < mheap_.arena_start || obj >= mheap_.arena_used` は、`obj` がヒープ領域の開始アドレスよりも小さいか、または使用中のヒープ領域の終了アドレス以上である場合に真となります。これはつまり、`obj` がGoランタイムのヒープ領域外を指していることを意味します。

もし `obj` がヒープ領域外を指している場合、関数は以下の処理を行います。

1.  `print(label, "=", hex(obj), " is not a heap object\n")`: デバッグ情報として、`obj` がヒープオブジェクトではないことを示すメッセージを標準出力に出力します。`label` は呼び出し元から渡される識別子、`hex(obj)` はポインタのアドレスを16進数で表示したものです。
2.  `return`: 関数を即座に終了します。これにより、`obj` がヒープポインタであると仮定して行われる後続の処理（`h_spans` へのアクセスなど）がスキップされ、範囲外アクセスによる `panicslice` の発生を防ぎます。

このシンプルなチェックを追加することで、`gcDumpObject` は非ヒープポインタを安全に処理できるようになり、GCのデバッグ中に発生していた連鎖的なパニックが解消されます。これにより、Goランタイムの安定性が向上し、GC関連のバグの特定と修正がより容易になります。

# [インデックス 2198] ファイルの概要

このコミットは、Go言語の標準ライブラリである`os`パッケージに、ハードリンクの作成、シンボリックリンクの作成、およびシンボリックリンクの読み取りを行うための新しい関数`os.Link`、`os.Symlink`、`os.Readlink`を追加するものです。これにより、Goプログラムからファイルシステムのリンク操作を直接行えるようになります。

## 変更の背景

このコミットは、Go言語がまだ初期開発段階にあった2009年に行われました。当時のGo言語の標準ライブラリは、ファイルシステム操作に関する基本的な機能しか提供していませんでした。Unix系システムにおいて、ハードリンクやシンボリックリンクはファイルシステムを柔軟に操作するための重要な機能であり、多くのシステムプログラミングにおいて不可欠です。

Go言語がシステムプログラミング言語としての地位を確立していく上で、これらの基本的なファイルシステム操作APIの欠如は、開発者がGoでより複雑なツールやアプリケーションを構築する際の障壁となっていました。このコミットは、`os`パッケージにこれらのリンク操作機能を追加することで、Go言語のファイルシステム操作能力を向上させ、より幅広いシステムプログラミングのユースケースに対応できるようにすることを目的としています。

特に、`os.Link`（ハードリンク）、`os.Symlink`（シンボリックリンク）、`os.Readlink`（シンボリックリンクの読み取り）は、既存のUnixシステムコールに直接対応するものであり、Goプログラムがこれらの低レベルなファイルシステム機能を利用できるようにするための基盤を築きました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **ハードリンク (Hard Link)**:
    *   ハードリンクは、同じiノード（inode）を指す複数のディレクトリエントリです。iノードはファイルシステム上の実際のデータブロックを指すメタデータ構造です。
    *   つまり、複数のファイル名が同じファイルデータ（iノード）を共有している状態です。
    *   ハードリンクを作成しても、ディスク上のファイルデータが複製されるわけではありません。
    *   元のファイルを削除しても、他のハードリンクが存在する限り、ファイルデータは削除されません。すべてのハードリンクが削除されたときに初めて、ファイルデータが解放されます。
    *   異なるファイルシステムパーティションをまたいで作成することはできません。
    *   ディレクトリに対してハードリンクを作成することはできません（通常）。

2.  **シンボリックリンク (Symbolic Link / Soft Link)**:
    *   シンボリックリンクは、別のファイルやディレクトリへのパスを格納する特殊なファイルです。
    *   これは、WindowsのショートカットやmacOSのエイリアスに似ていますが、より低レベルなファイルシステム機能です。
    *   シンボリックリンクは独自のiノードを持ち、そのデータブロックには参照先のパスが文字列として保存されています。
    *   参照先のファイルやディレクトリが削除されると、シンボリックリンクは「壊れたリンク」（dangling link）となり、参照できなくなります。
    *   異なるファイルシステムパーティションをまたいで作成できます。
    *   ディレクトリに対しても作成できます。

3.  **`os`パッケージ**:
    *   Go言語の標準ライブラリの一部で、オペレーティングシステム（OS）の機能にアクセスするための汎用的なインターフェースを提供します。
    *   ファイル操作、ディレクトリ操作、プロセス管理、環境変数など、OSレベルの機能を提供します。
    *   このコミット以前は、リンク操作に関する直接的なAPIは提供されていませんでした。

4.  **`syscall`パッケージ**:
    *   Go言語の標準ライブラリの一部で、低レベルなシステムコールに直接アクセスするためのインターフェースを提供します。
    *   OS固有のシステムコール（例: `link(2)`、`symlink(2)`、`readlink(2)`）をGoから呼び出すためのラッパーを提供します。
    *   `os`パッケージの多くの関数は、内部的に`syscall`パッケージの機能を利用して実装されています。

5.  **エラーハンドリング (`Error`型と`ErrnoToError`)**:
    *   Go言語では、エラーは戻り値として明示的に扱われます。
    *   このコミット当時のGoでは、`os`パッケージのエラーは`Error`インターフェース（後に`error`インターフェースに統合）を通じて返されていました。
    *   `syscall`パッケージから返されるシステムコールエラーは通常、数値の`errno`（エラー番号）として表現されます。`ErrnoToError`関数は、この`errno`をGoの`Error`型に変換するためのユーティリティ関数です。

## 技術的詳細

このコミットの技術的な核心は、Unix系OSが提供する`link(2)`、`symlink(2)`、`readlink(2)`システムコールをGo言語の`os`パッケージから利用可能にすることです。

1.  **`os.Link(oldpath, newpath string) Error`**:
    *   `oldpath`で指定された既存のファイルへのハードリンクを`newpath`に作成します。
    *   内部的には、`syscall.Link(oldpath, newpath)`を呼び出しています。
    *   `syscall.Link`は、OSの`link(2)`システムコールを直接呼び出し、成功時には0、失敗時にはエラー番号を返します。
    *   返されたエラー番号は`ErrnoToError`によって`os.Error`型に変換され、呼び出し元に返されます。

2.  **`os.Symlink(oldpath, newpath string) Error`**:
    *   `oldpath`で指定されたファイルまたはディレクトリへのシンボリックリンクを`newpath`に作成します。
    *   内部的には、`syscall.Symlink(oldpath, newpath)`を呼び出しています。
    *   `syscall.Symlink`は、OSの`symlink(2)`システムコールを直接呼び出し、成功時には0、失敗時にはエラー番号を返します。
    *   返されたエラー番号は`ErrnoToError`によって`os.Error`型に変換され、呼び出し元に返されます。

3.  **`os.Readlink(path string) (string, Error)`**:
    *   `path`で指定されたシンボリックリンクが指すパスを読み取ります。
    *   内部的には、`syscall.Readlink(path, buf, len)`を呼び出しています。
    *   `readlink(2)`システムコールは、リンクが指すパスをバッファに書き込み、書き込まれたバイト数を返します。パスの長さが不明な場合があるため、この関数は可変長のバッファを効率的に扱うためのループを含んでいます。
    *   最初は128バイトのバッファで試行し、パスがバッファに収まらない場合はバッファサイズを倍にして再試行します。これは、`readlink(2)`がバッファサイズが不足している場合でもエラーを返さず、書き込まれたバイト数を返すという特性を利用した一般的なパターンです。
    *   `syscall.Readlink`は、OSの`readlink(2)`システムコールを直接呼び出します。
    *   成功した場合は読み取ったパスの文字列と`nil`エラーを返し、失敗した場合は空文字列と`os.Error`型のエラーを返します。

このコミットでは、`src/lib/syscall/file_darwin.go`と`src/lib/syscall/file_linux.go`に、それぞれのOS向けの`Link`、`Symlink`、`Readlink`システムコールラッパーが追加されています。これらは`Syscall`関数（Goの低レベルなシステムコール呼び出しメカニズム）を使用して、C言語の対応するシステムコールを呼び出しています。`StringBytePtr`はGoの文字列をC言語のバイトポインタに変換するためのヘルパー関数です。

また、`src/lib/os/os_test.go`には、これらの新機能が正しく動作するかを確認するためのテストケースが追加されています。特に、`TestHardLink`、`TestSymLink`、`TestLongSymlink`は、それぞれのリンク作成と読み取りのシナリオをカバーしており、リンクの特性（iノードの一致、シンボリックリンクの参照先、長いパスの処理など）を検証しています。

## コアとなるコードの解説

### `src/lib/os/file.go`

```go
// Link creates a hard link.
func Link(oldpath, newpath string) Error {
	r, e := syscall.Link(oldpath, newpath);
	return ErrnoToError(e);
}

// Symlink creates a symbolic link.
func Symlink(oldpath, newpath string) Error {
	r, e := syscall.Symlink(oldpath, newpath);
	return ErrnoToError(e);
}

// Readlink reads the contents of a symbolic link: the destination of
// the link.  It returns the contents and an Error, if any.
func Readlink(path string) (string, Error) {
	for len := int64(128); ; len *= 2 {
		b := make([]byte, len);
		r, e := syscall.Readlink(path, &b[0], len);
		if r == -1 {
			return "", ErrnoToError(e);
		} else if r < len {
			return string(b[0:r]), nil;
		}
	}
	// Silence 6g.
	return "", nil; // unreachable
}
```
*   `Link`と`Symlink`は非常にシンプルで、それぞれ対応する`syscall`パッケージの関数を呼び出し、その結果のエラーを`ErrnoToError`で変換して返しています。
*   `Readlink`はより複雑で、`readlink`システムコールがバッファの長さを必要とするため、適切なバッファサイズを見つけるためのループを実装しています。最初は128バイトのバッファで試行し、もしパスがバッファに収まらない（`r == len`）場合は、バッファサイズを倍にして再試行します。`r == -1`はシステムコールエラーを示し、`r < len`はパス全体がバッファに収まったことを示します。

### `src/lib/syscall/file_darwin.go` および `src/lib/syscall/file_linux.go` (共通の構造)

```go
func Link(oldpath, newpath string) (ret int64, errno int64) {
	oldbuf := StringBytePtr(oldpath);
	newbuf := StringBytePtr(newpath);
	r1, r2, err := Syscall(SYS_LINK, int64(uintptr(unsafe.Pointer(oldbuf))), int64(uintptr(unsafe.Pointer(newbuf))), 0);
	return r1, err;
}

func Symlink(oldpath, newpath string) (ret int64, errno int64) {
	oldbuf := StringBytePtr(oldpath);
	newbuf := StringBytePtr(newpath);
	r1, r2, err := Syscall(SYS_SYMLINK, int64(uintptr(unsafe.Pointer(oldbuf))), int64(uintptr(unsafe.Pointer(newbuf))), 0);
	return r1, err;
}

func Readlink(path string, buf *byte, nbytes int64) (ret int64, errno int64) {
	pathbuf := StringBytePtr(path);
	r1, r2, err := Syscall(SYS_READLINK, int64(uintptr(unsafe.Pointer(pathbuf))), int64(uintptr(unsafe.Pointer(buf))), nbytes);
	return r1, err;
}
```
*   これらのファイルでは、各OSのシステムコール番号（`SYS_LINK`, `SYS_SYMLINK`, `SYS_READLINK`）を使用して、`Syscall`関数を介して実際のシステムコールを呼び出しています。
*   `StringBytePtr`はGoの文字列をCスタイルのヌル終端バイト配列ポインタに変換し、システムコールに渡せるようにします。
*   `unsafe.Pointer`と`uintptr`は、Goの型システムをバイパスしてメモリを直接操作するためのもので、低レベルなシステムコールインターフェースでよく使用されます。

### `src/lib/os/os_test.go`

テストコードは、`os.Link`, `os.Symlink`, `os.Readlink`が期待通りに動作するかを検証しています。
*   `TestHardLink`:
    *   一時ファイルを作成し、それに対してハードリンクを作成します。
    *   `Stat`関数を使用して、元のファイルとハードリンクのiノード番号とデバイスIDが一致することを確認し、ハードリンクが正しく作成されたことを検証します。
*   `TestSymLink`:
    *   一時ファイルを作成し、それに対してシンボリックリンクを作成します。
    *   `Stat`と`Lstat`（リンク自体をstatする）を使い分け、シンボリックリンクが正しく作成され、かつそれがシンボリックリンクとして認識されることを確認します。
    *   `Readlink`を使用して、シンボリックリンクが指すパスが元のファイルパスと一致することを確認します。
    *   シンボリックリンクを介して元のファイルを開けることも検証します。
*   `TestLongSymlink`:
    *   非常に長い文字列をターゲットとするシンボリックリンクを作成し、`Readlink`が長いパスも正しく読み取れることを検証します。これは`Readlink`のバッファ拡張ロジックのテストにもなります。

これらのテストは、新しく追加されたAPIがGoのファイルシステム操作のセマンティクスに沿って正しく機能することを保証しています。

# [インデックス 24844] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/internal/ld`）が共有ライブラリを生成する際に、読み取り専用の再配置データを`.data.rel.ro`セクションに配置するように変更するものです。これにより、Goが生成する共有ライブラリが、テキストセグメントに対する再配置（TEXTREL）を持つことによってプロセス間で共有できないという問題を解決し、より効率的でセキュアな共有ライブラリの生成を可能にします。

## 変更の背景

Go言語は、その設計上、静的リンクを基本としていますが、Cgoを介して共有ライブラリ（`c-shared`ビルドモード）や、Go自身の共有ライブラリ（`shared`ビルドモード）を生成する機能も提供しています。しかし、このコミット以前のGoリンカが生成する共有ライブラリには、重大な問題がありました。それは、**TEXTREL（テキスト再配置）**と呼ばれる、コードセグメント（通常は読み取り専用であるべき領域）に対する再配置情報が含まれてしまうことでした。

TEXTRELが存在すると、以下のような問題が発生します。

1.  **メモリ効率の低下**: 共有ライブラリの最大の利点の一つは、複数のプロセスが同じコードセグメントをメモリ上で共有できることです。しかし、TEXTRELが存在すると、動的リンカがライブラリをロードする際に、コードセグメントを書き込み可能にする必要があります。これにより、コードセグメントがプロセス間で共有できなくなり、各プロセスが独自のコピーを持つことになり、メモリ使用量が増加します。
2.  **パフォーマンスの低下**: 動的リンカがTEXTRELを解決するために、ロード時にコードセグメントを書き換えなければならないため、ライブラリのロード時間が長くなります。
3.  **セキュリティリスク**: コードセグメントが一時的に書き込み可能になることで、攻撃者がその期間中にコードを改ざんする機会が生まれ、セキュリティ上の脆弱性につながる可能性があります。

このコミットは、Goが生成する共有ライブラリからTEXTRELを排除し、真に共有可能で、より効率的かつセキュアなライブラリを実現することを目的としています。具体的には、再配置が必要な読み取り専用データを、動的リンカが特別に扱う`.data.rel.ro`セクションに移動させることでこの問題を解決します。

## 前提知識の解説

### 共有ライブラリ (Shared Libraries)
共有ライブラリは、複数の実行可能ファイルや他のライブラリによって共有されるコードとデータを含むファイルです。これにより、ディスクスペースの節約、メモリ使用量の削減、プログラムのモジュール化といった利点があります。Linuxでは`.so`（Shared Object）、Windowsでは`.dll`（Dynamic Link Library）、macOSでは`.dylib`という拡張子が一般的です。

### 再配置 (Relocations)
プログラムがコンパイルされ、リンクされる際、コードやデータ内のアドレスは、最終的にメモリにロードされる際のアドレスとは異なる場合があります。再配置とは、プログラムがメモリにロードされる際に、これらのアドレスを実際のメモリ上の位置に合わせて修正するプロセスです。動的リンカ（Dynamic Linker）がこの処理を担当します。

### TEXTREL (テキスト再配置)
TEXTRELは、実行可能コードを含むテキストセグメント（`.text`セクションなど）に対する再配置を指します。通常、テキストセグメントは実行中に変更されないように読み取り専用としてマークされます。TEXTRELが存在すると、動的リンカはテキストセグメントを一時的に書き込み可能にして再配置を実行する必要があり、これは前述の通り、メモリ効率、パフォーマンス、セキュリティの観点から望ましくありません。

### 位置独立コード (Position-Independent Code, PIC)
PICは、メモリ上の任意のアドレスにロードされても正しく実行されるように設計されたコードです。共有ライブラリは通常、PICとしてコンパイルされます。PICは、絶対アドレスではなく、相対アドレス指定やグローバルオフセットテーブル（GOT）、プロシージャリンケージテーブル（PLT）などのメカニズムを使用して、コードがどこにロードされても正しくデータや関数にアクセスできるようにします。これにより、TEXTRELを回避し、コードセグメントの共有を可能にします。

### RELRO (Read-Only Relocations) と `.data.rel.ro` セクション
RELROは、共有ライブラリや実行可能ファイルのセキュリティを強化するための技術です。これは、再配置が必要な読み取り専用データを、動的リンカが再配置を適用した後に読み取り専用として保護するメカニズムです。

*   **`.data.rel.ro`セクション**: このセクションは、定数として宣言されているが、実行時に動的リンカによる再配置が必要なグローバル変数を格納するために使用されます。例えば、`const`ポインタが別のグローバル変数や関数のアドレスを指す場合などです。
*   **動作原理**:
    1.  コンパイル時、再配置が必要な読み取り専用データは`.data.rel.ro`セクションに配置されます。
    2.  ロード時、このセクションは一時的に書き込み可能として扱われ、動的リンカが再配置を適用します。
    3.  再配置が完了した後、動的リンカは`mprotect`システムコールなどを使用して、`.data.rel.ro`セクションを含むメモリページを読み取り専用に設定します。

これにより、再配置後のデータが改ざんされるのを防ぎ、セキュリティを向上させます。

### ELF (Executable and Linkable Format)
ELFは、Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイルフォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、および様々なセクション（`.text`, `.data`, `.rodata`, `.bss`など）で構成されます。

### Goリンカ (`cmd/link`)
Go言語のツールチェーンの一部であり、Goのソースコードから実行可能ファイルやライブラリを生成する役割を担います。Goのリンカは、C/C++のリンカとは異なり、多くの処理を独自に行う特徴があります。

## 技術的詳細

このコミットの核心は、Goリンカが共有ライブラリを生成する際の、読み取り専用データの扱いを変更することにあります。従来のGoリンカは、再配置が必要な読み取り専用データを、システムリンカが期待する`.rodata`セクションに配置していました。しかし、`.rodata`セクションは通常、完全に読み取り専用であり、再配置によって書き換えられることを想定していません。これがTEXTREL問題の一因となっていました。

この変更では、以下の主要なメカニズムが導入されています。

1.  **新しいシンボルタイプ `SXXXRELRO` の導入**:
    `src/cmd/internal/obj/link.go`に、既存の読み取り専用データ型（`STYPE`, `SSTRING`, `SGOSTRING`, `SGCBITS`, `SRODATA`, `SFUNCTAB`）に対応する新しい型として、`STYPERELRO`, `SSTRINGRELRO`, `SGOSTRINGRELRO`, `SGCBITSRELRO`, `SRODATARELRO`, `SFUNCTABRELRO`が追加されました。これらの新しい型は、再配置が必要な読み取り専用データを識別するために使用されます。

2.  **`UseRelro()` 関数の導入**:
    `src/cmd/link/internal/ld/lib.go`に`UseRelro()`関数が追加されました。この関数は、現在のビルドモードが`BuildmodeCShared`または`BuildmodeShared`であり、かつターゲットシステムがELF形式を使用している場合に`true`を返します。これにより、RELROメカニズムを適用するかどうかをリンカが判断できるようになります。

3.  **`dodata()` 関数でのデータ型昇格**:
    `src/cmd/link/internal/ld/data.go`の`dodata()`関数が変更され、`UseRelro()`が`true`の場合に、再配置を持つ読み取り専用データ（`obj.STYPE`から`obj.SFUNCTAB`までの型、および`obj.SGOSTRING`）の型を、対応する`SXXXRELRO`型に昇格させるロジックが追加されました。これにより、これらのデータが特別なセクションに配置される準備が整います。

4.  **`.data.rel.ro` セクションの生成**:
    `dodata()`関数内で、`UseRelro()`が`true`の場合に、`.data.rel.ro`という名前の新しいセクションが追加されます。このセクションには、型が`SXXXRELRO`に昇格されたデータが格納されます。このセクションは、動的リンカが再配置を適用できるように、一時的に書き込み可能（パーミッション`06`）としてマークされます。再配置完了後、動的リンカによって読み取り専用に保護されます。

5.  **セクション名の変更**:
    `src/cmd/link/internal/ld/elf.go`および`src/cmd/link/internal/ld/data.go`において、`typelink`, `gosymtab`, `gopclntab`といったセクション名が、`UseRelro()`が`true`の場合に`.data.rel.ro.typelink`のように`.data.rel.ro`プレフィックスを持つように変更されました。これにより、これらのセクションもRELROメカニズムの恩恵を受けられるようになります。

6.  **リンカフラグの追加**:
    `src/cmd/link/internal/ld/lib.go`の`hostlink()`関数において、`UseRelro()`が`true`の場合に、外部リンカに対して`-Wl,-z,relro`フラグが渡されるようになりました。このフラグは、GNUリンカに対してRELROを有効にするよう指示するものです。

これらの変更により、Goリンカは、再配置が必要な読み取り専用データを、システムリンカが適切に処理できる`.data.rel.ro`セクションに配置するようになり、TEXTRELの問題を根本的に解決します。結果として、Goが生成する共有ライブラリは、より効率的でセキュアになり、プロセス間で真に共有可能になります。

## コアとなるコードの解説

### `src/cmd/internal/obj/link.go` における新しいシンボルタイプ

```go
const (
	Sxxx = iota
	STEXT
	SELFRXSECT
	// ... 既存の型 ...
	SRODATA
	SFUNCTAB

	// Types STYPE-SFUNCTAB above are written to the .rodata section by default.
	// When linking a shared object, some conceptually "read only" types need to
	// be written to by relocations and putting them in a section called
	// ".rodata" interacts poorly with the system linkers. The GNU linkers
	// support this situation by arranging for sections of the name
	// ".data.rel.ro.XXX" to be mprotected read only by the dynamic linker after
	// relocations have applied, so when the Go linker is creating a shared
	// object it checks all objects of the above types and bumps any object that
	// has a relocation to it to the corresponding type below, which are then
	// written to sections with appropriate magic names.
	STYPERELRO
	SSTRINGRELRO
	SGOSTRINGRELRO
	SGOFUNCRELRO
	SGCBITSRELRO
	SRODATARELRO
	SFUNCTABRELRO

	STYPELINK
	// ... 続く型 ...
)
```
このコードは、Goリンカが内部的に使用するシンボルタイプを定義しています。`SRODATA`や`SFUNCTAB`などの既存の読み取り専用データ型に加えて、`STYPERELRO`などの新しい`SXXXRELRO`型が導入されました。コメントにあるように、これらの新しい型は、共有オブジェクトをリンクする際に、再配置が必要な「概念的に読み取り専用」のデータを識別するために使用されます。これにより、これらのデータはシステムリンカが認識する特別なセクション（`.data.rel.ro.XXX`）に配置され、動的リンカによって再配置後に読み取り専用として保護されるようになります。

### `src/cmd/link/internal/ld/lib.go` における `UseRelro()` 関数

```go
// UseRelro returns whether to make use of "read only relocations" aka
// relro.
func UseRelro() bool {
	return (Buildmode == BuildmodeCShared || Buildmode == BuildmodeShared) && Iself
}
```
`UseRelro()`関数は、現在のビルド設定に基づいてRELROメカニズムを使用すべきかどうかを判断します。`BuildmodeCShared`または`BuildmodeShared`（Cgoを介した共有ライブラリまたはGo自身の共有ライブラリをビルドする場合）であり、かつターゲットシステムがELF形式（`Iself`が`true`）である場合に`true`を返します。この関数は、リンカの様々な箇所でRELRO関連の処理を条件分岐させるために使用されます。

### `src/cmd/link/internal/ld/data.go` における `dodata()` の変更

```go
func dodata() {
	// ... 既存の処理 ...

	if UseRelro() {
		// "read only" data with relocations needs to go in its own section
		// when building a shared library. We do this by boosting objects of
		// type SXXX with relocations to type SXXXRELRO.
		for s := datap; s != nil; s = s.Next {
			if (s.Type >= obj.STYPE && s.Type <= obj.SFUNCTAB && len(s.R) > 0) || s.Type == obj.SGOSTRING {
				s.Type += (obj.STYPERELRO - obj.STYPE)
				if s.Outer != nil {
					s.Outer.Type = s.Type
				}
			}
		}
		// ... 型の一貫性チェック ...
	}

	// ... 既存の処理 ...

	// There is some data that are conceptually read-only but are written to by
	// relocations. On GNU systems, we can arrange for the dynamic linker to
	// mprotect sections after relocations are applied by giving them write
	// permissions in the object file and calling them ".data.rel.ro.FOO". We
	// divide the .rodata section between actual .rodata and .data.rel.ro.rodata,
	// but for the other sections that this applies to, we just write a read-only
	// .FOO section or a read-write .data.rel.ro.FOO section depending on the
	// situation.
	// TODO(mwhudson): It would make sense to do this more widely, but it makes
	// the system linker segfault on darwin.
	relro_perms := 04
	relro_prefix := ""

	if UseRelro() {
		relro_perms = 06
		relro_prefix = ".data.rel.ro"
		/* data only written by relocations */
		sect = addsection(segro, ".data.rel.ro", 06) // 新しい .data.rel.ro セクションの追加
		// ... .data.rel.ro セクションへのデータ配置 ...
	}

	/* typelink */
	sect = addsection(segro, relro_prefix+".typelink", relro_perms) // セクション名の変更
	// ... 続くセクションの処理 ...
}
```
`dodata()`関数は、Goリンカがデータセクションを構築する主要な場所です。
最初の`if UseRelro()`ブロックでは、再配置を持つ読み取り専用データの型を`SXXXRELRO`に「昇格」させています。これは、これらのデータが通常の`.rodata`セクションではなく、特別なRELROセクションに配置されるべきであることをリンカに伝えるための重要なステップです。
次の`if UseRelro()`ブロックでは、実際に`.data.rel.ro`という名前の新しいセクションが追加されます。このセクションは、動的リンカが再配置を適用できるように、一時的に書き込み可能（パーミッション`06`）として作成されます。そして、`relro_prefix`が設定され、後続の`.typelink`、`.gosymtab`、`.gopclntab`などのセクション名にこのプレフィックスが付加されることで、これらのセクションもRELROの恩恵を受けられるようになります。

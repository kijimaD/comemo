## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）における重要なバグを修正し、関連するテストカバレッジを向上させることを目的としています。

主な問題は、`getgcmask`関数内で`bv.data`というビットベクトルデータ構造を扱う際のオフセット計算の誤りにありました。`bv.data`は`uint32`の配列として定義されているにもかかわらず、コードがバイト配列であるかのようにオフセットを計算していたため、GCがオブジェクト内のポインタを正しく識別できない可能性がありました。これは、GCがメモリを正確にスキャンし、到達可能なオブジェクトを特定するために不可欠なポインタマスクの生成に直接影響します。誤ったポインタマスクは、本来回収されるべきでないメモリが回収されたり（use-after-free）、逆に回収されるべきメモリが回収されずにメモリリークを引き起こしたりする原因となります。

また、このコミットではスタック上のオブジェクトに対するGC情報のテストが不足していることも認識され、そのカバレッジを向上させるためのテストケースが追加されました。スタックはプログラム実行中に頻繁に利用されるメモリ領域であり、ここに配置されるオブジェクトのGC情報が正確であることは、ランタイムの安定性と正確性にとって極めて重要です。

この修正は、GoランタイムのGCの正確性と堅牢性を高める上で不可欠なものでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクションに関する概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

Goのガベージコレクションは、プログラムが動的に確保したメモリのうち、もはや到達不可能になったものを自動的に解放する仕組みです。GoのGCは並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。

-   **マークフェーズ**: GCはルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
-   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能なオブジェクト）のメモリを解放し、再利用可能な状態にします。

GCが正しく動作するためには、オブジェクト内のどの部分がポインタであり、どの部分が非ポインタデータであるかを正確に知る必要があります。これを「ポインタマスク」または「GC情報」と呼びます。

### ポインタマスク (GC情報)

Goのランタイムは、各型（struct、arrayなど）について、そのインスタンス内のどのオフセットにポインタが含まれているかを示すビットマスク（またはバイトマスク）を生成します。GCはこのマスクを使用して、オブジェクトをスキャンする際にポインタを識別し、それらが指すオブジェクトをマークします。

-   **`bv.data`**: ビットベクトル（Bit Vector）のデータ部分を指します。Goランタイムでは、GC情報を効率的に表現するためにビットベクトルが使用されます。この`bv.data`は、通常、`uint32`の配列として実装され、各ビットが特定のメモリ位置がポインタであるか否かを示します。
-   **`getgcmask`関数**: この関数は、特定のメモリ領域（例えば、スタックフレームやヒープオブジェクト）に対応するGCポインタマスクを取得する役割を担います。GCがメモリをスキャンする際に、この関数が提供するマスクに基づいてポインタを識別します。

### GC情報におけるビットの種類

`src/pkg/runtime/gcinfo_test.go`や関連するGCコードでは、ポインタマスクの各バイト（またはビット）がオブジェクトの特定のオフセットにおけるデータの種類を示します。

-   **`BitsPointer`**: その位置にポインタが存在することを示します。GCはこのポインタを辿って、参照先のオブジェクトをマークします。
-   **`BitsScalar`**: その位置にポインタではないスカラー値（整数、浮動小数点数など）が存在することを示します。GCはこの部分をスキャンしません。
-   **`BitsDead`**: その位置が未使用または無効なデータであることを示します。スタック上では、この領域は通常、ポインタを含まないスカラー値として扱われます。
-   **`BitsMultiWord`**: 複数のワードにまたがるデータ構造の開始を示します。
-   **`BitsSlice`**: スライス型であることを示します。スライスは内部的にポインタ、長さ、容量を持つため、GCはこれらを適切に処理する必要があります。
-   **`BitsString`**: 文字列型であることを示します。文字列も内部的にポインタと長さを持つため、GCはこれらを適切に処理する必要があります。

### スタックGC情報

Goの関数呼び出しでは、ローカル変数や引数がスタックに割り当てられます。これらのスタック上の変数にもポインタが含まれる場合があり、GCはスタックをスキャンして到達可能なオブジェクトをマークする必要があります。スタック上のオブジェクトのGC情報が正確であることは、プログラムの正確な動作とメモリ安全性を保証するために不可欠です。

## 技術的詳細

このコミットの核心は、`src/pkg/runtime/mgc0.c`内の`runtime·getgcmask`関数における`bv.data`のオフセット計算の誤りを修正することです。

元のコードでは、`bv.data`が`uint32`の配列であるにもかかわらず、オフセット計算がバイト配列を前提としていました。具体的には、`bv.data[off/PointersPerByte]`のような計算が行われていましたが、これは`bv.data`がバイトの配列である場合にのみ正しいです。`bv.data`が`uint32`の配列である場合、各`uint32`は32ビット、つまり4バイトを表します。したがって、ビットオフセットを`uint32`のインデックスに変換するには、ビットオフセットを32で割る必要があります。

修正前:
`bits = (bv.data[off/PointersPerByte] >> ((off%PointersPerByte)*BitsPerPointer))&BitsMask;`

修正後:
`bits = (bv.data[off*BitsPerPointer/32] >> ((off*BitsPerPointer)%32))&BitsMask;`

この修正により、`off`（ポインタのワードオフセット）が`bv.data`内の正しい`uint32`要素を指し、その`uint32`内の正しいビット位置からポインタマスク情報が抽出されるようになります。`off*BitsPerPointer`はビット単位のオフセットを表し、これを32で割ることで`uint32`配列のインデックスが得られ、32で割った余りを取ることで`uint32`内のビットオフセットが得られます。

また、`src/pkg/runtime/gcinfo_test.go`では、スタック上のオブジェクトに対するGC情報が正しく生成されていることを検証するための新しいテストケースが追加されました。これまでのテストは主にヒープ、データ、BSSセグメントのオブジェクトに焦点を当てていましたが、スタック上のオブジェクトもGCの対象となるため、その正確性を保証するためのテストが不可欠でした。

`nonStackInfo`というヘルパー関数が導入され、スタック以外のオブジェクトのGC情報において`BitsDead`が`BitsScalar`に置き換えられるというGoランタイムの特定の挙動をシミュレートしています。これは、スタック上では`BitsDead`がそのままの意味を持つ一方で、ヒープやデータセグメントでは`BitsDead`が実質的にスカラー値として扱われるというGCの内部的な最適化や設計の違いを反映しています。この関数を使うことで、スタックと非スタックのGC情報の違いをテストで適切に扱うことができます。

## コアとなるコードの解説

### `src/pkg/runtime/gcinfo_test.go`の変更点

1.  **スタックGC情報のテスト追加**:
    `TestGCInfo`関数内に、`new(Type)`を使ってスタックに割り当てられたオブジェクト（実際にはヒープにエスケープされる可能性もありますが、ここではスタック上のオブジェクトのGC情報が正しく扱われることを意図しています）に対する`verifyGCInfo`呼び出しが追加されました。これにより、スタック上のポインタマスクの正確性が検証されます。

    ```go
    	verifyGCInfo(t, "stack ScalarPtr", new(ScalarPtr), infoScalarPtr)
    	verifyGCInfo(t, "stack PtrScalar", new(PtrScalar), infoPtrScalar)
    	verifyGCInfo(t, "stack Complex", new(Complex), infoComplex())
    	verifyGCInfo(t, "stack string", new(string), infoString)
    	verifyGCInfo(t, "stack eface", new(interface{}), infoEface)
    ```

2.  **`nonStackInfo`ヘルパー関数の導入**:
    この新しい関数は、スタック以外のメモリ領域（BSS、データ、ヒープ）におけるGC情報の特性を考慮するためのものです。GoランタイムのGCでは、スタック上の`BitsDead`（未使用/無効なデータ）はそのまま`BitsDead`として扱われますが、スタック以外の領域では`BitsDead`が`BitsScalar`（ポインタではないスカラー値）として解釈される場合があります。`nonStackInfo`は、この変換をシミュレートし、テストが期待するポインタマスクを生成します。

    ```go
    func nonStackInfo(mask []byte) []byte {
    	// BitsDead is replaced with BitsScalar everywhere except stacks.
    	mask1 := make([]byte, len(mask))
    	mw := false // Multi-word flag
    	for i, v := range mask {
    		if !mw && v == BitsDead {
    			v = BitsScalar // BitsDeadをBitsScalarに変換
    		}
    		mw = !mw && v == BitsMultiWord // Multi-wordの開始を検出
    		mask1[i] = v
    	}
    	return mask1
    }
    ```
    この関数は、`BitsMultiWord`のフラグ`mw`を使って、複数ワードにまたがるデータ構造の処理を考慮しています。`BitsDead`が`BitsScalar`に変換されるのは、`mw`が`false`の場合、つまり単一ワードのデータの場合に限られます。

3.  **既存のテストの更新**:
    BSS、データ、ヒープのテストケースで、`infoScalarPtr`などの元のGC情報マスクが`nonStackInfo`関数を通して渡されるように変更されました。これにより、スタック以外の領域における`BitsDead`の挙動がテストで正しく考慮されるようになります。

    ```diff
    -	verifyGCInfo(t, "bss ScalarPtr", &bssScalarPtr, infoScalarPtr)
    +	verifyGCInfo(t, "bss ScalarPtr", &bssScalarPtr, nonStackInfo(infoScalarPtr))
    // ...
    -		verifyGCInfo(t, "heap ScalarPtr", escape(new(ScalarPtr)), infoScalarPtr)
    +		verifyGCInfo(t, "heap ScalarPtr", escape(new(ScalarPtr)), nonStackInfo(infoScalarPtr))
    ```

4.  **`infoComplex`関数の更新**:
    `infoComplex`関数内で生成されるポインタマスクにおいて、一部の`BitsScalar`が`BitsDead`に変更されました。これは、特定のアーキテクチャ（`386`, `amd64`, `amd64p32`）において、複合型（`Complex`）のGC情報がより正確に表現されるように調整されたものです。この変更は、`getgcmask`の修正と合わせて、GC情報の正確性を全体的に向上させます。

    ```diff
    -			BitsScalar, BitsScalar, BitsScalar, BitsScalar,
    +			BitsDead, BitsScalar, BitsScalar, BitsScalar,
    ```

### `src/pkg/runtime/mgc0.c`の変更点

`runtime·getgcmask`関数内のビットベクトル`bv.data`からのビット抽出ロジックが修正されました。

```diff
--- a/src/pkg/runtime/mgc0.c
+++ b/src/pkg/runtime/mgc0.c
@@ -2087,7 +2087,7 @@ runtime·getgcmask(byte *p, Type *t, byte **mask, uintptr *len)
 		*mask = runtime·mallocgc(*len, nil, 0);
 		for(i = 0; i < n; i += PtrSize) {
 			off = (p+i-frame.varp+size)/PtrSize;
-			bits = (bv.data[off/PointersPerByte] >> ((off%PointersPerByte)*BitsPerPointer))&BitsMask;
+			bits = (bv.data[off*BitsPerPointer/32] >> ((off*BitsPerPointer)%32))&BitsMask;
 			(*mask)[i/PtrSize] = bits;
 		}
 	}
```

-   **`off`**: これは、GC対象のメモリ領域内でのポインタのワードオフセットです。
-   **`BitsPerPointer`**: 1つのポインタが占めるビット数（通常は32ビットまたは64ビット）。
-   **`bv.data`**: `uint32`の配列です。

修正前の`off/PointersPerByte`は、`bv.data`がバイト配列であるかのようにインデックスを計算していました。しかし、`bv.data`は`uint32`の配列であるため、各要素は32ビットを表します。

修正後の`off*BitsPerPointer/32`は、`off`ワードオフセットに対応するビットオフセットを計算し（`off*BitsPerPointer`）、それを32で割ることで、`bv.data`配列内の正しい`uint32`要素のインデックスを正確に特定します。

同様に、`((off%PointersPerByte)*BitsPerPointer)`は`uint32`内のビットオフセットを誤って計算していましたが、`((off*BitsPerPointer)%32)`は、`off`ワードオフセットに対応するビットオフセットを32で割った余りを取り、`uint32`内の正しいビット位置を特定します。

この修正により、`getgcmask`関数は`bv.data`からポインタマスク情報を正確に抽出し、GCがメモリを正しくスキャンできるようになります。

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）における重要なバグを修正し、関連するテストカバレッジを向上させることを目的としています。

主な問題は、`getgcmask`関数内で`bv.data`というビットベクトルデータ構造を扱う際のオフセット計算の誤りにありました。`bv.data`は`uint32`の配列として定義されているにもかかわらず、コードがバイト配列であるかのようにオフセットを計算していたため、GCがオブジェクト内のポインタを正しく識別できない可能性がありました。これは、GCがメモリを正確にスキャンし、到達可能なオブジェクトを特定するために不可欠なポインタマスクの生成に直接影響します。誤ったポインタマスクは、本来回収されるべきでないメモリが回収されたり（use-after-free）、逆に回収されるべきメモリが回収されずにメモリリークを引き起こしたりする原因となります。

また、このコミットではスタック上のオブジェクトに対するGC情報のテストが不足していることも認識され、そのカバレッジを向上させるためのテストケースが追加されました。スタックはプログラム実行中に頻繁に利用されるメモリ領域であり、ここに配置されるオブジェクトのGC情報が正確であることは、ランタイムの安定性と正確性にとって極めて重要です。

この修正は、GoランタイムのGCの正確性と堅牢性を高める上で不可欠なものでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクションに関する概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

Goのガベージコレクションは、プログラムが動的に確保したメモリのうち、もはや到達不可能になったものを自動的に解放する仕組みです。GoのGCは並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。

-   **マークフェーズ**: GCはルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
-   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能なオブジェクト）のメモリを解放し、再利用可能な状態にします。

GCが正しく動作するためには、オブジェクト内のどの部分がポインタであり、どの部分が非ポインタデータであるかを正確に知る必要があります。これを「ポインタマスク」または「GC情報」と呼びます。

### ポインタマスク (GC情報)

Goのランタイムは、各型（struct、arrayなど）について、そのインスタンス内のどのオフセットにポインタが含まれているかを示すビットマスク（またはバイトマスク）を生成します。GCはこのマスクを使用して、オブジェクトをスキャンする際にポインタを識別し、それらが指すオブジェクトをマークします。

-   **`bv.data`**: ビットベクトル（Bit Vector）のデータ部分を指します。Goランタイムでは、GC情報を効率的に表現するためにビットベクトルが使用されます。この`bv.data`は、通常、`uint32`の配列として実装され、各ビットが特定のメモリ位置がポインタであるか否かを示します。
-   **`getgcmask`関数**: この関数は、特定のメモリ領域（例えば、スタックフレームやヒープオブジェクト）に対応するGCポインタマスクを取得する役割を担います。GCがメモリをスキャンする際に、この関数が提供するマスクに基づいてポインタを識別します。

### GC情報におけるビットの種類

`src/pkg/runtime/gcinfo_test.go`や関連するGCコードでは、ポインタマスクの各バイト（またはビット）がオブジェクトの特定のオフセットにおけるデータの種類を示します。

-   **`BitsPointer`**: その位置にポインタが存在することを示します。GCはこのポインタを辿って、参照先のオブジェクトをマークします。
-   **`BitsScalar`**: その位置にポインタではないスカラー値（整数、浮動小数点数など）が存在することを示します。GCはこの部分をスキャンしません。
-   **`BitsDead`**: その位置が未使用または無効なデータであることを示します。スタック上では、この領域は通常、ポインタを含まないスカラー値として扱われます。
-   **`BitsMultiWord`**: 複数のワードにまたがるデータ構造の開始を示します。
-   **`BitsSlice`**: スライス型であることを示します。スライスは内部的にポインタ、長さ、容量を持つため、GCはこれらを適切に処理する必要があります。
-   **`BitsString`**: 文字列型であることを示します。文字列も内部的にポインタと長さを持つため、GCはこれらを適切に処理する必要があります。

### スタックGC情報

Goの関数呼び出しでは、ローカル変数や引数がスタックに割り当てられます。これらのスタック上の変数にもポインタが含まれる場合があり、GCはスタックをスキャンして到達可能なオブジェクトをマークする必要があります。スタック上のオブジェクトのGC情報が正確であることは、プログラムの正確な動作とメモリ安全性を保証するために不可欠です。

## 技術的詳細

このコミットの核心は、`src/pkg/runtime/mgc0.c`内の`runtime·getgcmask`関数における`bv.data`のオフセット計算の誤りを修正することです。

元のコードでは、`bv.data`が`uint32`の配列であるにもかかわらず、オフセット計算がバイト配列を前提としていました。具体的には、`bv.data[off/PointersPerByte]`のような計算が行われていましたが、これは`bv.data`がバイトの配列である場合にのみ正しいです。`bv.data`が`uint32`の配列である場合、各`uint32`は32ビット、つまり4バイトを表します。したがって、ビットオフセットを`uint32`のインデックスに変換するには、ビットオフセットを32で割る必要があります。

修正前:
`bits = (bv.data[off/PointersPerByte] >> ((off%PointersPerByte)*BitsPerPointer))&BitsMask;`

修正後:
`bits = (bv.data[off*BitsPerPointer/32] >> ((off*BitsPerPointer)%32))&BitsMask;`

この修正により、`off`（ポインタのワードオフセット）が`bv.data`内の正しい`uint32`要素を指し、その`uint32`内の正しいビット位置からポインタマスク情報が抽出されるようになります。`off*BitsPerPointer`はビット単位のオフセットを表し、これを32で割ることで`uint32`配列のインデックスが得られ、32で割った余りを取ることで`uint32`内のビットオフセットが得られます。

また、`src/pkg/runtime/gcinfo_test.go`では、スタック上のオブジェクトに対するGC情報が正しく生成されていることを検証するための新しいテストケースが追加されました。これまでのテストは主にヒープ、データ、BSSセグメントのオブジェクトに焦点を当てていましたが、スタック上のオブジェクトもGCの対象となるため、その正確性を保証するためのテストが不可欠でした。

`nonStackInfo`というヘルパー関数が導入され、スタック以外のオブジェクトのGC情報において`BitsDead`が`BitsScalar`に置き換えられるというGoランタイムの特定の挙動をシミュレートしています。これは、スタック上では`BitsDead`がそのままの意味を持つ一方で、ヒープやデータセグメントでは`BitsDead`が実質的にスカラー値として扱われるというGCの内部的な最適化や設計の違いを反映しています。この関数を使うことで、スタックと非スタックのGC情報の違いをテストで適切に扱うことができます。

## コアとなるコードの解説

### `src/pkg/runtime/gcinfo_test.go`の変更点

1.  **スタックGC情報のテスト追加**:
    `TestGCInfo`関数内に、`new(Type)`を使ってスタックに割り当てられたオブジェクト（実際にはヒープにエスケープされる可能性もありますが、ここではスタック上のオブジェクトのGC情報が正しく扱われることを意図しています）に対する`verifyGCInfo`呼び出しが追加されました。これにより、スタック上のポインタマスクの正確性が検証されます。

    ```go
    	verifyGCInfo(t, "stack ScalarPtr", new(ScalarPtr), infoScalarPtr)
    	verifyGCInfo(t, "stack PtrScalar", new(PtrScalar), infoPtrScalar)
    	verifyGCInfo(t, "stack Complex", new(Complex), infoComplex())
    	verifyGCInfo(t, "stack string", new(string), infoString)
    	verifyGCInfo(t, "stack eface", new(interface{}), infoEface)
    ```

2.  **`nonStackInfo`ヘルパー関数の導入**:
    この新しい関数は、スタック以外のメモリ領域（BSS、データ、ヒープ）におけるGC情報の特性を考慮するためのものです。GoランタイムのGCでは、スタック上の`BitsDead`（未使用/無効なデータ）はそのまま`BitsDead`として扱われますが、スタック以外の領域では`BitsDead`が`BitsScalar`（ポインタではないスカラー値）として解釈される場合があります。`nonStackInfo`は、この変換をシミュレートし、テストが期待するポインタマスクを生成します。

    ```go
    func nonStackInfo(mask []byte) []byte {
    	// BitsDead is replaced with BitsScalar everywhere except stacks.
    	mask1 := make([]byte, len(mask))
    	mw := false // Multi-word flag
    	for i, v := range mask {
    		if !mw && v == BitsDead {
    			v = BitsScalar // BitsDeadをBitsScalarに変換
    		}
    		mw = !mw && v == BitsMultiWord // Multi-wordの開始を検出
    		mask1[i] = v
    	}
    	return mask1
    }
    ```
    この関数は、`BitsMultiWord`のフラグ`mw`を使って、複数ワードにまたがるデータ構造の処理を考慮しています。`BitsDead`が`BitsScalar`に変換されるのは、`mw`が`false`の場合、つまり単一ワードのデータの場合に限られます。

3.  **既存のテストの更新**:
    BSS、データ、ヒープのテストケースで、`infoScalarPtr`などの元のGC情報マスクが`nonStackInfo`関数を通して渡されるように変更されました。これにより、スタック以外の領域における`BitsDead`の挙動がテストで正しく考慮されるようになります。

    ```diff
    -	verifyGCInfo(t, "bss ScalarPtr", &bssScalarPtr, infoScalarPtr)
    +	verifyGCInfo(t, "bss ScalarPtr", &bssScalarPtr, nonStackInfo(infoScalarPtr))
    // ...
    -		verifyGCInfo(t, "heap ScalarPtr", escape(new(ScalarPtr)), infoScalarPtr)
    +		verifyGCInfo(t, "heap ScalarPtr", escape(new(ScalarPtr)), nonStackInfo(infoScalarPtr))
    ```

4.  **`infoComplex`関数の更新**:
    `infoComplex`関数内で生成されるポインタマスクにおいて、一部の`BitsScalar`が`BitsDead`に変更されました。これは、特定のアーキテクチャ（`386`, `amd64`, `amd64p32`）において、複合型（`Complex`）のGC情報がより正確に表現されるように調整されたものです。この変更は、`getgcmask`の修正と合わせて、GC情報の正確性を全体的に向上させます。

    ```diff
    -			BitsScalar, BitsScalar, BitsScalar, BitsScalar,
    +			BitsDead, BitsScalar, BitsScalar, BitsScalar,
    ```

### `src/pkg/runtime/mgc0.c`の変更点

`runtime·getgcmask`関数内のビットベクトル`bv.data`からのビット抽出ロジックが修正されました。

```diff
--- a/src/pkg/runtime/mgc0.c
+++ b/src/pkg/runtime/mgc0.c
@@ -2087,7 +2087,7 @@ runtime·getgcmask(byte *p, Type *t, byte **mask, uintptr *len)
 		*mask = runtime·mallocgc(*len, nil, 0);
 		for(i = 0; i < n; i += PtrSize) {
 			off = (p+i-frame.varp+size)/PtrSize;
-			bits = (bv.data[off/PointersPerByte] >> ((off%PointersPerByte)*BitsPerPointer))&BitsMask;
+			bits = (bv.data[off*BitsPerPointer/32] >> ((off*BitsPerPointer)%32))&BitsMask;
 			(*mask)[i/PtrSize] = bits;
 		}
 	}
```

-   **`off`**: これは、GC対象のメモリ領域内でのポインタのワードオフセットです。
-   **`BitsPerPointer`**: 1つのポインタが占めるビット数（通常は32ビットまたは64ビット）。
-   **`bv.data`**: `uint32`の配列です。

修正前の`off/PointersPerByte`は、`bv.data`がバイト配列であるかのようにインデックスを計算していました。しかし、`bv.data`は`uint32`の配列であるため、各要素は32ビットを表します。

修正後の`off*BitsPerPointer/32`は、`off`ワードオフセットに対応するビットオフセットを計算し（`off*BitsPerPointer`）、それを32で割ることで、`bv.data`配列内の正しい`uint32`要素のインデックスを正確に特定します。

同様に、`((off*BitsPerPointer)%32)`は、`off`ワードオフセットに対応するビットオフセットを32で割った余りを取り、`uint32`内の正しいビット位置を特定します。

この修正により、`getgcmask`関数は`bv.data`からポインタマスク情報を正確に抽出し、GCがメモリを正しくスキャンできるようになります。

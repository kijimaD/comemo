## 変更の背景

Go言語では、プログラムのパフォーマンスを最適化するために、コンパイラが「エスケープ解析 (Escape Analysis)」と呼ばれるプロセスを実行します。これは、変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定する静的解析です。スタック割り当ては高速であり、ガベージコレクション（GC）のオーバーヘッドを発生させないため、可能な限りスタック割り当てが望ましいとされています。

しかし、エスケープ解析が不正確であると、本来スタックに割り当てられるべき変数が誤ってヒープに割り当てられてしまう「誤検知 (false positive)」が発生することがあります。これは、GCの負荷を増やし、プログラムの実行速度を低下させる原因となります。特に、関数のパラメータは、そのライフタイムが関数の実行スコープに限定されることが多いため、スタックに割り当てられることが期待されます。

このコミットは、関数のパラメータに関するエスケープ解析の誤検知を特定し、修正するための包括的なテストケースを追加することで、Goコンパイラのエスケープ解析の堅牢性と正確性を向上させることを目的としています。これにより、より効率的なメモリ管理と、結果としてGoプログラムのパフォーマンス向上に貢献します。

## 前提知識の解説

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラが変数のメモリ割り当て場所（スタックかヒープか）を決定するために行う最適化手法です。

*   **スタック (Stack)**: 関数呼び出しごとに割り当てられるメモリ領域で、関数の実行が終了すると自動的に解放されます。高速で、GCの対象外です。ローカル変数や関数の引数など、ライフタイムが短いデータに適しています。
*   **ヒープ (Heap)**: プログラム全体で共有されるメモリ領域で、ガベージコレクタによって管理されます。スタックに比べて割り当て・解放のコストが高く、GCの対象となります。ライフタイムが関数スコープを超えるデータ（例: グローバル変数、関数から返されるポインタ、別のゴルーチンに渡されるデータ）に適しています。

変数が「エスケープする (escape)」とは、その変数のライフタイムが現在のスコープ（通常は関数）を超えてしまうことを意味します。エスケープ解析は、変数がエスケープするかどうかを判断し、エスケープする場合はヒープに割り当て、そうでない場合はスタックに割り当てます。

**変数がヒープにエスケープする主なシナリオ:**

1.  **ポインタが関数から返される場合**: 関数内で作成されたローカル変数のアドレスが関数から返される場合、その変数は関数終了後も参照され続ける可能性があるため、ヒープにエスケープします。
2.  **変数がグローバル変数やヒープ上のデータ構造に格納される場合**: ローカル変数の値やアドレスが、グローバル変数やヒープに割り当てられた構造体のフィールドに代入される場合、その変数はエスケープします。
3.  **変数が別のゴルーチンに渡される場合**: ゴルーチンは非同期に実行されるため、変数のライフタイムが現在の関数のライフタイムを超える可能性があります。
4.  **インターフェース型への変換**: 特定の条件下で、具象型がインターフェース型に変換される際に、その基になる値がヒープにエスケープすることがあります。
5.  **コンパイラがライフタイムを特定できない場合**: コンパイラが変数の正確なライフタイムを静的に判断できない場合、安全のためにヒープに割り当てられることがあります。

### 誤検知 (False Positive)

エスケープ解析における「誤検知」とは、実際にはスタックに割り当てることが可能な変数を、コンパイラが誤ってヒープに割り当ててしまう状況を指します。これは、コンパイラの解析能力の限界や、特定のコードパターンに対する最適化の不足によって発生します。誤検知は、不必要なヒープ割り当てとGCオーバーヘッドを引き起こし、プログラムのパフォーマンスを低下させるため、Goコンパイラの開発において重要な改善点となります。

このコミットで追加されたテストは、特に「False positives (var incorrectly escapes) are marked with BAD.」とあるように、このような誤検知のケースを意図的に作り出し、コンパイラが正しく「エスケープしない」と判断できるかを検証しています。

## 技術的詳細

このコミットで追加された `test/escape_param.go` ファイルは、Goコンパイラのエスケープ解析が関数のパラメータをどのように扱うかを詳細にテストするためのものです。このテストファイルは、`errorcheck` ツールと `-0 -m -l` フラグを使用してコンパイル時のエスケープ解析の診断メッセージをチェックします。

*   `-0`: 最適化レベル0（最適化を無効にする）
*   `-m`: エスケープ解析の診断メッセージを表示する
*   `-l`: インライン化を無効にする

テストの基本的なアプローチは、様々なパターンでポインタを関数パラメータとして渡し、そのポインタがヒープにエスケープするかどうかを `// ERROR` コメントでアノテーションすることです。`// ERROR` コメントは、その行で期待されるエスケープ解析の診断メッセージを示します。

特に注目すべきは、ファイル冒頭のコメント「In this test almost everything is BAD except the simplest cases where input directly flows to output.」です。これは、このテストの多くのケースが、本来エスケープすべきではない変数が誤ってエスケープしてしまう「誤検知 (false positive)」のシナリオを意図的に作成していることを示唆しています。これらの「BAD」とマークされたケースは、コンパイラがエスケープ解析を改善すべき領域を示しています。

テストケースは、以下のような様々なポインタのフローパターンを網羅しています。

*   `in -> out`: 入力パラメータが直接戻り値として返されるケース。
*   `in, in -> out, out`: 複数の入力パラメータが複数の戻り値として返されるケース。
*   `in -> other in`: 入力パラメータが別の入力パラメータを介して間接的に参照されるケース。
*   `in -> in`: 入力パラメータが構造体のフィールドとして扱われるケース。
*   `in -> rcvr`: メソッドのレシーバとしてパラメータが扱われるケース。
*   `in -> heap`: 入力パラメータが直接 `sink` 変数（グローバルな `interface{}` 型の変数で、ヒープへのエスケープを強制するために使用される）に代入されることで、ヒープへのエスケープが強制されるケース。
*   `*in -> heap`, `**in -> heap`: 多重ポインタのデリファレンスがヒープへのエスケープを引き起こすケース。
*   `*in -> out`, `**in -> out`: 多重ポインタのデリファレンスが戻り値として返されるケース。
*   `&in -> out`: パラメータのアドレスが返されるケース。
*   `&in -> rcvr`: パラメータのアドレスがメソッドのレシーバに格納されるケース。
*   `in -> value rcvr`: 値レシーバのメソッドでパラメータが扱われるケース。

これらのテストケースは、Goコンパイラのエスケープ解析が、ポインタの複雑なフローや間接参照、構造体やメソッドのレシーバといった様々な状況下で、パラメータのライフタイムを正確に追跡できるかを検証するために設計されています。

## コアとなるコードの解説

`test/escape_param.go` ファイルは、Goのエスケープ解析の挙動を検証するための様々な関数とそれらを呼び出す `caller` 関数で構成されています。各テスト関数は、特定のポインタのフローパターンを表現し、その結果として期待されるエスケープ解析の診断メッセージが `// ERROR` コメントで記述されています。

ファイル内で共通して使用されている `var sink interface{}` は、変数をヒープにエスケープさせるためのトリックです。`sink = someVar` のように `sink` に値を代入すると、`someVar` はグローバルなインターフェース変数に格納されるため、そのライフタイムが現在の関数スコープを超え、ヒープにエスケープすることが強制されます。

以下に、いくつかの代表的なテストケースとその意図を解説します。

### `param0(p *int) *int` (in -> out)

```go
func param0(p *int) *int { // ERROR "leaking param: p to result ~r1$"
	return p
}

func caller0a() {
	i := 0
	_ = param0(&i) // ERROR "caller0a &i does not escape$"
}

func caller0b() {
	i := 0            // ERROR "moved to heap: i$"
	sink = param0(&i) // ERROR "&i escapes to heap$" "param0(&i) escapes to heap"
}
```

*   `param0`: パラメータ `p` がそのまま戻り値として返されるため、`p` はエスケープします。
*   `caller0a`: `param0(&i)` の結果がどこにも代入されないため、`i` はエスケープしません。
*   `caller0b`: `param0(&i)` の結果が `sink` に代入されるため、`i` はヒープにエスケープします。

### `param2(p1 *int, p2 **int)` (in -> other in)

```go
func param2(p1 *int, p2 **int) { // ERROR "leaking param: p1$" "param2 p2 does not escape$"
	*p2 = p1
}

func caller2a() {
	i := 0 // ERROR "moved to heap: i$"
	var p *int
	param2(&i, &p) // ERROR "&i escapes to heap$" "caller2a &p does not escape$"
	_ = p
}
```

*   `param2`: `p1` が `*p2` を介して間接的に参照され、`p2` が指す先に `p1` が代入されます。この場合、`p1` はエスケープします。
*   `caller2a`: `&i` が `param2` に渡され、`p` に代入されます。`p` はその後 `_ = p` で参照されるだけなので、`&p` 自体はエスケープしませんが、`i` はヒープに移動します。

### `param5(i *int)` (in -> heap)

```go
func param5(i *int) { // ERROR "leaking param: i$"
	sink = i // ERROR "i escapes to heap$"
}

func caller5() {
	i := 0     // ERROR "moved to heap: i$"
	param5(&i) // ERROR "&i escapes to heap$"
}
```

*   `param5`: パラメータ `i` が直接 `sink` に代入されるため、`i` はヒープにエスケープします。
*   `caller5`: ローカル変数 `i` のアドレスが `param5` に渡され、結果として `i` はヒープに移動します。

これらのテストケースは、Goコンパイラがポインタのデリファレンス、構造体への埋め込み、メソッドレシーバ、グローバル変数への代入など、様々な状況下でパラメータのライフタイムを正確に追跡し、不必要なヒープ割り当てを避けることができるかを検証するためのものです。`// BAD` コメントは、現在のコンパイラの実装では誤検知が発生する可能性のあるケースを示しており、今後の改善の余地があることを示唆しています。

## 元コミット内容

`net`パッケージにおいて、有効なDNS応答がタイムアウトするまで待機し続けるように変更されました。これにより、不正なUDPパケットによるサービス拒否攻撃が防止されます。この変更はIssue #13281を修正するものです。

## 変更の背景

DNS（Domain Name System）はインターネットの根幹をなすサービスであり、ドメイン名をIPアドレスに変換する役割を担っています。DNSクエリは通常UDPプロトコルを介して行われますが、UDPはコネクションレスであるため、送信元IPアドレスの偽装が容易です。この特性を悪用し、攻撃者は不正なDNS応答パケットを送信することで、正当なDNSクライアントの処理を妨害したり、誤った情報を注入したりする可能性があります。

このコミットが行われる前は、Goの`net`パッケージのDNSクライアントは、DNSクエリを送信した後、最初に受信した応答パケットを無条件に処理しようとしていました。もしこの最初のパケットが不正なものであった場合（例えば、クエリIDが一致しない、フォーマットが不正など）、クライアントはそのパケットを処理できずにエラーを返し、正当な応答が届く前に処理を終了してしまう可能性がありました。

このような挙動は、特にサービス拒否（DoS）攻撃に対して脆弱性をもたらします。攻撃者が大量の不正なUDPパケットをDNSクライアントに送りつけることで、クライアントが正当なDNSサーバーからの応答を受け取れなくなり、結果として名前解決ができなくなる、というシナリオが考えられます。コミットメッセージにある「bogus UDP packets（不正なUDPパケット）」による「denial of service attacks（サービス拒否攻撃）」を防ぐことが、この変更の主要な動機です。

## 前提知識の解説

### DNS (Domain Name System)

*   **役割**: ドメイン名（例: `www.example.com`）をIPアドレス（例: `93.184.216.34`）に変換する分散型データベースシステム。
*   **プロトコル**: 主にUDPポート53を使用しますが、応答が大きすぎる場合やゾーン転送にはTCPポート53も使用されます。
*   **DNSメッセージ構造**:
    *   **ヘッダ**: 12バイト。クエリID、フラグ（応答/クエリ、権威、切り詰めなど）、質問数、回答数などが含まれます。
    *   **質問セクション**: クエリ対象のドメイン名、クエリタイプ（Aレコード、AAAAレコードなど）、クエリクラス（INなど）が含まれます。
    *   **回答セクション**: 質問に対する回答（IPアドレスなど）が含まれます。
    *   **権威セクション**: 権威サーバーの情報が含まれます。
    *   **追加セクション**: 追加情報が含まれます。
*   **クエリID (ID)**: DNSヘッダに含まれる16ビットの識別子。クライアントがクエリを送信する際に生成し、DNSサーバーはそのIDを応答に含めて返します。クライアントはこのIDを使って、どのクエリに対する応答であるかを識別します。

### サービス拒否 (DoS) 攻撃

*   **概要**: 標的となるシステムやネットワークリソースに対して、過剰な負荷をかけたり、不正なトラフィックを送りつけたりすることで、正当なユーザーからのサービス利用を妨害する攻撃。
*   **DNSにおけるDoS**: DNSクライアントが不正な応答パケットによって処理を妨害され、名前解決ができなくなることで、アプリケーションやサービスが機能停止に陥る可能性があります。

### Goの`net`パッケージ

Go言語の標準ライブラリに含まれるネットワーク機能を提供するパッケージです。TCP/UDP通信、IPアドレスの解決、DNSルックアップなど、様々なネットワーク関連の機能を提供します。

## 技術的詳細

このコミットの核心は、DNS応答の検証ロジックを強化し、不正な応答を無視して有効な応答を待ち続けるメカニズムを導入した点にあります。

以前の実装では、UDPベースのDNS通信において、`UDPConn.readDNSResponse()` メソッドが単一のUDPパケットを読み込み、その内容をDNSメッセージとしてアンパックし、すぐに返していました。この際、メッセージのIDが元のクエリと一致するかどうかのチェックは、`exchange`関数内で`in.id != out.id`として行われていましたが、不正なフォーマットのパケットや、IDが一致しないパケットを受信した場合、すぐにエラーとして処理されていました。

新しい実装では、`dnsRoundTripUDP`という新しいヘルパー関数が導入されました。この関数は、UDPコネクション（`io.ReadWriter`インターフェースを満たすもの）とDNSクエリメッセージを受け取り、有効なDNS応答メッセージを返す役割を担います。

`dnsRoundTripUDP`の主要な変更点は以下の通りです。

1.  **ループによる応答待機**: `for {}` ループを導入し、タイムアウトが発生するか、有効な応答が受信されるまで、UDPパケットの読み込みを継続します。
2.  **応答の検証**: 受信したUDPパケットを`dnsMsg`としてアンパックした後、以下の2つの重要な検証を行います。
    *   `!resp.Unpack(b[:n])`: 受信したバイト列が有効なDNSメッセージとしてアンパックできるか。
    *   `!resp.IsResponseTo(query)`: 受信した応答が、現在送信しているクエリに対する有効な応答であるか。
3.  **不正な応答の無視**: 上記の検証のいずれかが失敗した場合、つまりパケットが不正なフォーマットであるか、または現在のクエリに対する応答ではないと判断された場合、そのパケットは「悪意のある偽造試行（malicious forgery attempts）」として無視され、ループの次のイテレーションに進みます。これにより、クライアントは不正なパケットに惑わされることなく、正当なDNSサーバーからの応答を待ち続けることができます。
4.  **`IsResponseTo`メソッドの導入**: `dnsmsg.go`に`IsResponseTo`という新しいメソッドが追加されました。このメソッドは、受信したDNSメッセージが特定のクエリに対する有効な応答であるかを厳密にチェックします。具体的には、以下の条件をすべて満たす必要があります。
    *   メッセージが応答フラグ（`response`フィールド）を持っていること。
    *   メッセージIDがクエリのIDと一致すること。
    *   質問セクションの数がクエリの質問セクションの数と一致すること。
    *   各質問のドメイン名、クエリタイプ、クエリクラスがクエリのそれらと一致すること（`equalASCIILabel`関数でドメイン名の比較を行う）。

この変更により、GoのDNSクライアントは、不正なUDPパケットが送信されても、それを適切にフィルタリングし、タイムアウト期間内であれば正当な応答を待ち続けることができるようになります。これにより、不正なパケットによる一時的なサービス拒否攻撃に対する耐性が大幅に向上しました。

TCPベースのDNS通信（`dnsRoundTripTCP`）についても、同様に`IsResponseTo`メソッドによる応答検証が追加され、不正な応答を検出した場合はエラーを返すようになりました。ただし、TCPはコネクション指向であるため、UDPのような「不正なパケットを無視して待ち続ける」というロジックは必要ありません。TCPでは、不正な応答は通常、接続の切断やプロトコルエラーとして扱われるためです。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/net/dnsclient_unix.go`内の`dnsRoundTripUDP`関数と、`src/net/dnsmsg.go`内の`IsResponseTo`メソッドの導入です。

### `dnsRoundTripUDP`関数

```go
func dnsRoundTripUDP(c io.ReadWriter, query *dnsMsg) (*dnsMsg, error) {
	b, ok := query.Pack()
	if !ok {
		return nil, errors.New("cannot marshal DNS message")
	}
	if _, err := c.Write(b); err != nil {
		return nil, err
	}

	b = make([]byte, 512) // see RFC 1035
	for { // ここが重要な変更点：有効な応答を待ち続けるループ
		n, err := c.Read(b)
		if err != nil {
			return nil, err
		}
		resp := &dnsMsg{}
		if !resp.Unpack(b[:n]) || !resp.IsResponseTo(query) { // 不正な応答を検出
			// Ignore invalid responses as they may be malicious
			// forgery attempts. Instead continue waiting until
			// timeout. See golang.org/issue/13281.
			continue // 不正な応答は無視して次のパケットを待つ
		}
		return resp, nil // 有効な応答が見つかったら返す
	}
}
```

この関数は、DNSクエリをUDPで送信し、その応答を受信するロジックをカプセル化しています。特に注目すべきは`for {}`ループです。このループは、`c.Read(b)`でUDPパケットを繰り返し読み込みます。読み込んだパケットが`resp.Unpack(b[:n])`でDNSメッセージとして正常に解析できない場合、または`resp.IsResponseTo(query)`が`false`を返した場合（つまり、現在のクエリに対する有効な応答ではない場合）、`continue`文によってそのパケットは破棄され、次のパケットの読み込みに移ります。この処理は、コネクションのタイムアウトが発生するまで継続されます。これにより、攻撃者が送信する不正なパケットによって、正当なDNSサーバーからの応答が処理される機会が失われることを防ぎます。

### `IsResponseTo`メソッド

```go
func (m *dnsMsg) IsResponseTo(query *dnsMsg) bool {
	if !m.response { // 応答フラグが立っているか
		return false
	}
	if m.id != query.id { // クエリIDが一致するか
		return false
	}
	if len(m.question) != len(query.question) { // 質問数が一致するか
		return false
	}
	for i, q := range m.question {
		q2 := query.question[i]
		// 質問のドメイン名、タイプ、クラスが一致するか
		if !equalASCIILabel(q.Name, q2.Name) || q.Qtype != q2.Qtype || q.Qclass != q2.Qclass {
			return false
		}
	}
	return true // すべての条件を満たせば有効な応答
}
```

このメソッドは、受信したDNSメッセージ`m`が、元のクエリメッセージ`query`に対する正当な応答であるかを厳密に判断します。単にメッセージIDが一致するだけでなく、応答フラグが立っていること、質問の数が一致すること、そして各質問のドメイン名、タイプ、クラスがすべて一致することを検証します。これにより、単なるIDの偽装だけでなく、質問内容を偽装した応答に対しても高いレベルで防御できるようになります。

これらの変更により、Goの`net`パッケージは、DNS名前解決の堅牢性とセキュリティを向上させ、特にUDPベースのDNS通信におけるサービス拒否攻撃に対する耐性を強化しました。

## 元コミット内容

このコミットの目的は、GoランタイムにDarwinオペレーティングシステムとARMアーキテクチャの組み合わせ（darwin/arm）に対するサポートを追加することです。

## 変更の背景

2014年当時、ARMアーキテクチャはモバイルデバイス（特にAppleのiPhoneやiPad）で広く採用されており、その重要性が増していました。Go言語がこれらのプラットフォームで動作するためには、GoランタイムがDarwinカーネルとARMプロセッサの組み合わせに特化した低レベルのインターフェースを提供する必要がありました。

このコミットは、Go言語のエコシステムを拡張し、開発者がARMベースのAppleデバイス向けにGoアプリケーションをコンパイル・実行できるようにするための基盤を構築するものです。これにより、Go言語の適用範囲がサーバーサイドやデスクトップ環境だけでなく、モバイルや組み込みシステムにも広がる可能性が開かれました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の技術的な概念を把握しておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。Goランタイムは、ガベージコレクション、goroutineスケジューリング、チャネル通信、システムコールインターフェースなど、Go言語の並行処理モデルとメモリ管理を支える重要な機能を提供します。OSやアーキテクチャに依存する部分は、ランタイム内で抽象化され、各プラットフォーム向けに実装されます。

*   **ARMアーキテクチャ (ARM Architecture)**: ARM（Advanced RISC Machine）は、モバイルデバイス、組み込みシステム、最近ではサーバーやデスクトップPCでも広く使用されているRISC（Reduced Instruction Set Computer）ベースのCPUアーキテクチャです。x86アーキテクチャとは異なり、命令セット、レジスタの構成、関数呼び出し規約などが異なります。Goランタイムは、特定のARM命令セット（例：ARMv7）とABI（Application Binary Interface）に準拠してコードを生成し、OSと対話する必要があります。

*   **Darwin**: AppleのmacOSおよびiOSの基盤となっているUnix系オペレーティングシステムカーネルです。MachマイクロカーネルとBSDレイヤー（POSIX互換性を提供）から構成されています。Darwinは、システムコール、シグナル処理、メモリ管理、スレッド管理など、OS固有のサービスを提供します。Goランタイムは、これらのDarwin固有のAPIを介してOSと対話します。

*   **システムコール (System Calls)**: ユーザー空間で実行されるプログラムが、ファイルI/O、メモリ管理、プロセス制御、ネットワーク通信など、カーネルが提供する特権的なサービスを利用するためのインターフェースです。各OSは独自のシステムコール番号と呼び出し規約を持っています。ARMアーキテクチャでは、通常、特定のレジスタにシステムコール番号と引数を設定し、`SWI`（Software Interrupt）命令などの特別な命令を実行することでカーネルに制御を渡します。

*   **シグナル処理 (Signal Handling)**: オペレーティングシステムがプロセスに対して非同期イベント（例：プログラムのエラー、外部からの割り込み、タイマーイベントなど）を通知するメカニズムです。プロセスは、特定のシグナルを受信した際に実行される「シグナルハンドラ」を登録できます。Goランタイムは、プログラムのクラッシュ（例：セグメンテーション違反）や割り込み（例：Ctrl+C）を適切に処理するために、独自のシグナルハンドラを設定します。シグナルハンドラが実行される際のスタックの状態やレジスタのコンテキスト（`ucontext`、`mcontext`）はOSによって異なります。

*   **スタック管理 (Stack Management)**: プログラムの実行中に、関数のローカル変数、引数、リターンアドレスなどを一時的に格納するメモリ領域です。Goランタイムは、各goroutineに独自のスタックを割り当て、必要に応じてスタックを動的に拡張・縮小する「可変スタック」の仕組みを持っています。OSがシグナルハンドリングなどのために予約するスタック領域（「システムスタック」または「シグナルスタック」）も考慮に入れる必要があります。

*   **スレッドローカルストレージ (Thread Local Storage, TLS)**: 各スレッドが独自のデータを保持できるメモリ領域です。Goランタイムでは、現在のgoroutineのポインタやM（Machine）構造体へのポインタなど、スレッド固有の情報を格納するためにTLSが利用されます。ARMアーキテクチャでは、TLSベースポインタを読み出すための特別な命令（CP15レジスタの読み出しなど）が存在します。

## 技術的詳細

このコミットは、GoランタイムがDarwin/ARM環境で動作するために必要な低レベルのインターフェースを実装しています。

1.  **Darwin/ARM固有の定数とデータ構造の定義 (`src/runtime/defs_darwin_arm.go`)**:
    *   このファイルは、Darwin/ARM環境でGoランタイムがOSと対話するために必要なシステムコール関連の定数（例: `_PROT_READ`, `_MAP_ANON`, `_EINTR` など）や、OS固有のデータ構造（`machbody`, `machheader`, `stackt`, `sigactiont`, `siginfo`, `timeval`, `itimerval`, `timespec`, `floatstate32`, `regs32`, `exceptionstate32`, `mcontext32`, `ucontext`, `keventt` など）を定義しています。
    *   特に、`mcontext32` と `ucontext` は、シグナルハンドラが呼び出された際に、CPUのレジスタ状態やスタック情報などの実行コンテキストを保存・復元するために不可欠な構造体です。ARMアーキテクチャの32ビットレジスタ構成に合わせて定義されています。
    *   コメントにあるように、`cgo` が一部のDarwin/ARM構造体を自動生成できないため、手動で定義されています。これは、OSのABI（Application Binary Interface）に厳密に準拠する必要があるためです。

2.  **OS固有のランタイム関数の実装 (`src/runtime/os_darwin_arm.go`)**:
    *   `cputicks()` 関数は、CPUのティック数を返すためのもので、プロファイラや乱数生成のシードとして使用されます。ここでは `nanotime()` を使用していますが、これはCPUティックの近似値であり、より良いエントロピーが必要であるというTODOコメントがあります。
    *   `checkgoarm()` は、ARM固有のチェックを行うためのプレースホルダ関数です。

3.  **ランタイムのエントリポイント (`src/runtime/rt0_darwin_arm.s`)**:
    *   `_rt0_arm_darwin` は、Goプログラムが起動した際のエントリポイントとなるアセンブリコードです。OSから渡される引数（`argc`, `argv`）を処理し、Goランタイムの初期化関数である `runtime·rt0_go` を呼び出します。これは、GoプログラムがC言語の `main` 関数のように動作を開始するためのブートストラップコードです。

4.  **シグナル処理の実装 (`src/runtime/signal_darwin_arm.go`)**:
    *   `sigctxt` 構造体は、シグナルハンドラ内でCPUレジスタにアクセスするためのヘルパーを提供します。これにより、シグナル発生時のプログラムカウンタ（PC）、スタックポインタ（SP）、その他のレジスタの値を読み書きできます。
    *   `regs()` メソッドは、`ucontext` 構造体内の `mcontext` からレジスタ情報 (`regs32`) を取得します。
    *   `set_pc`, `set_sp`, `set_lr` などのメソッドは、シグナルハンドラから復帰する際に、プログラムの実行フローを制御するためにレジスタの値を変更するために使用されます。

5.  **スタック定義の更新 (`src/runtime/stack.h`, `src/runtime/stack2.go`)**:
    *   `src/runtime/stack.h` では、`StackSystem` の定義に `GOOS_darwin` と `GOARCH_arm` の組み合わせが追加され、`STACKSYSTEM` が `1024` に設定されています。これは、Darwin/ARM環境でOSがシグナルハンドリングなどのために予約するスタック領域を考慮したものです。
    *   `src/runtime/stack2.go` では、Goのスタックシステムサイズを計算する `_StackSystem` 定数に `goos_darwin*goarch_arm*1024` が追加されています。これにより、GoランタイムがOS固有のスタック要件を満たすように、各goroutineのスタックに十分なガード領域が確保されます。

6.  **システムコールインターフェースの実装 (`src/runtime/sys_darwin_arm.s`)**:
    *   このファイルは、Darwin/ARM環境におけるGoランタイムのシステムコール呼び出しを実装する最も重要な部分です。
    *   `SYS_exit`, `SYS_read`, `SYS_write`, `SYS_open`, `SYS_mmap`, `SYS_munmap`, `SYS_sigaction`, `SYS_sigprocmask`, `SYS_gettimeofday`, `SYS_kqueue`, `SYS_kevent` など、Goランタイムが使用する主要なシステムコールのラッパー関数がアセンブリで記述されています。
    *   Darwin/ARMでは、システムコールは通常、システムコール番号を `R12` レジスタに設定し、引数を `R0` から `R6` レジスタに渡し、`SWI 0x80` 命令を実行することで呼び出されます。
    *   `runtime·sigtramp` は、OSからシグナルを受信した際に最初に実行されるアセンブリコードです。Darwin/ARMでは、シグナルハンドラがメインスタックで実行される可能性があるため、`sigtramp` は現在のgoroutineのコンテキストを保存し、Goランタイムが管理するシグナルスタック（`m_gsignal`）に切り替えてから、Goのシグナルハンドラを呼び出します。これにより、Goのスタック管理とシグナル処理がOSの動作と整合するように調整されます。シグナルハンドラからの復帰時には、`SYS_sigreturn` システムコールを呼び出して元のコンテキストに戻ります。
    *   `runtime·bsdthread_create` や `runtime·bsdthread_register` は、Darwinの`bsdthread` APIを使用して、Goランタイムが管理するスレッド（M）をOSスレッドとして登録・作成するためのものです。

7.  **スレッドローカルストレージ (TLS) の実装 (`src/runtime/tls_arm.s`)**:
    *   このファイルは、ARMアーキテクチャにおけるTLSの読み書きを実装しています。Goランタイムは、現在のgoroutineのポインタ（`g`）をTLSに格納し、必要に応じてアクセスします。
    *   `MRC 15, 0, R0, C13, C0, 3` 命令は、ARMのCP15コプロセッサレジスタからTLSベースポインタを読み出すために使用されます。
    *   `BIC $3, R0` という命令は、Darwin/ARM環境でTLSベースポインタが4バイトアラインされていない可能性があるため、下位2ビットをクリアしてアラインメントを強制するために追加されています。これは、ポインタの計算やメモリアクセスが正しく行われるようにするための重要な修正です。
    *   `GOOS_darwin` が定義されている場合に `TLSG_IS_VARIABLE` マクロが有効になり、`runtime.tlsg` が通常の変数として扱われることを示しています。

これらの変更は、GoランタイムがDarwin/ARMの低レベルなOSインターフェースとARMプロセッサの特性を正確に理解し、それらに適応することで、Goプログラムがこの新しいプラットフォームで安定して動作することを可能にしています。

**`src/runtime/sys_darwin_arm.s` からの抜粋（システムコール呼び出しの例と `sigtramp` の一部）**:

```asm
TEXT runtime·write(SB),NOSPLIT,$0
	MOVW	fd+0(FP), R0
	MOVW	p+4(FP), R1
	MOVW	n+8(FP), R2
	MOVW	$SYS_write, R12
	SWI	$0x80
	MOVW	R0, ret+12(FP)
	RET

TEXT runtime·sigtramp(SB),NOSPLIT,$0
	// this might be called in external code context,
	// where g is not set.
	// first save R0, because runtime·load_g will clobber it
	MOVM.DB.W [R0], (R13)
	MOVB	runtime·iscgo(SB), R0
	CMP 	$0, R0
	BL.NE	runtime·load_g(SB)

	CMP 	$0, g
	BNE 	cont
	// ... (省略) ...
cont:
	// Restore R0
	MOVM.IA.W (R13), [R0]

	// NOTE: some Darwin/ARM kernels always use the main stack to run the
	// signal handler. We need to switch to gsignal ourselves.
	MOVW	g_m(g), R11
	MOVW	m_gsignal(R11), R5
	MOVW	(g_stack+stack_hi)(R5), R6
	SUB		$28, R6

	// copy arguments for call to sighandler
	MOVW	R2, 4(R6) // signal num
	MOVW	R3, 8(R6) // signal info
	MOVW	g, 16(R6) // old_g
	MOVW    -4(FP), R4
	MOVW	R4, 12(R6) // context

	// Backup ucontext and infostyle
	MOVW    R4, 20(R6)
	MOVW    R1, 24(R6)

	// switch stack and g
	MOVW	R6, R13 // sigtramp can not re-entrant, so no need to back up R13.
	MOVW	R5, g

	BL	(R0)

	// call sigreturn
	MOVW	20(R13), R0	// saved ucontext
	MOVW	24(R13), R1	// saved infostyle
ret:
	MOVW	$SYS_sigreturn, R12 // sigreturn(ucontext, infostyle)
	SWI	$0x80
```

## コアとなるコードの解説

1.  **`src/runtime/defs_darwin_arm.go` のデータ構造**:
    *   `ucontext` と `mcontext32` は、Unix系OSにおけるシグナル処理の標準的なメカニズムの一部です。シグナルが発生すると、OSは現在のCPUの状態（レジスタの値など）を `mcontext` に保存し、スタック情報やシグナルマスクなどを含むより広範なコンテキストを `ucontext` に格納して、シグナルハンドラに渡します。
    *   これらの構造体を正確に定義することは、Goランタイムがシグナルハンドラ内でCPUの状態を読み取り、必要に応じて変更し、シグナル処理後に元の実行フローに正しく戻るために不可欠です。ARMの32ビットレジスタセットに合わせて `regs32` が定義されている点も重要です。

2.  **`src/runtime/sys_darwin_arm.s` のシステムコールと `sigtramp`**:
    *   **システムコールラッパー**: `runtime·write` のような関数は、Goの内部関数がOSの `write` システムコールを呼び出すための橋渡しをします。ARMの呼び出し規約に従い、引数をレジスタ（`R0`, `R1`, `R2`）に配置し、システムコール番号を `R12` に設定した後、`SWI 0x80` 命令を実行してカーネルに制御を渡します。このアセンブリコードは、GoランタイムがOSのサービスを利用するための低レベルなインターフェースを直接提供します。
    *   **`runtime·sigtramp`**: これはシグナル処理の核心部分です。Darwin/ARMでは、OSがシグナルハンドラを呼び出す際に、必ずしもGoランタイムが期待するスタック（goroutineスタック）上で実行されるとは限りません。特に、OSがメインスタックでシグナルハンドラを実行する場合があります。
        *   `sigtramp` は、まずOSから渡されたコンテキスト（シグナル番号、シグナル情報、`ucontext`）を保存します。
        *   次に、現在のGoランタイムのM（Machine）構造体から、シグナル処理専用のスタック（`m_gsignal`）に切り替えます。これにより、Goのシグナルハンドラが安全に実行できる環境が整います。
        *   スタックと現在のgoroutine (`g`) のコンテキストを切り替えた後、Goで実装された実際のシグナルハンドラ（`BL (R0)` で呼び出される）に制御を渡します。
        *   シグナルハンドラが完了すると、`sigtramp` は保存しておいた元のコンテキストとスタックに戻り、`SYS_sigreturn` システムコールを呼び出してOSに制御を返します。このスタック切り替えロジックは、Goの並行処理モデルとOSのシグナル処理メカニズムを調和させる上で非常に重要です。

3.  **`src/runtime/tls_arm.s` のTLSアラインメント調整**:
    *   `MRC 15, 0, R0, C13, C0, 3` は、ARMアーキテクチャでTLSベースポインタを読み出すための特殊な命令です。このポインタは、スレッドローカル変数へのアクセスに使用されます。
    *   `BIC $3, R0` 命令は、読み出したTLSベースポインタの最下位2ビットをクリア（ビットAND NOT）します。これは、Darwin/ARM環境では、OSが返すTLSベースポインタが必ずしも4バイト境界にアラインされているとは限らないためです。Goランタイムは、ポインタ演算やメモリアクセスを効率的かつ安全に行うために、4バイトアラインメントを前提とすることが多いため、このアラインメント調整は潜在的なクラッシュや不正なメモリアクセスを防ぐ上で不可欠な修正です。

これらのコード変更は、GoランタイムがDarwin/ARMという特定のOSとアーキテクチャの組み合わせの特性（システムコール規約、シグナル処理の挙動、TLSの扱いなど）を深く理解し、それらに適応するための低レベルな実装を示しています。

# [インデックス 24019] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるライブヒープの会計処理に関するバグを修正するものです。具体的には、`checkmark`フェーズや`gctrace=2`オプションが有効な場合に、GCのマーク状態が適切にリセットされず、GCコントローラがヒープサイズを誤認識し、不必要に新しいGCサイクルを即座に開始してしまう問題を解決します。この修正は、マーク状態のリセット処理を`gcResetMarkState`という新しい関数に切り出し、必要なすべてのマーク処理の前に呼び出すことで実現されています。

## 元コミット内容

Goランタイムにおいて、`checkmark`マーク処理および`gctrace=2`による追加マーク処理の前に、ライブヒープの会計状態がリセットされていませんでした。この結果、これらの機能が有効になっている場合、GC終了時にライブヒープが0バイトであると誤って認識され、実際のヒープサイズに関わらずGCコントローラが直ちに新しいGCを開始してしまう問題が発生していました。

この問題は、マーク状態のリセット処理を関数として切り出し、可能な3つのマーク処理すべて（通常のGCマーク、`checkmark`マーク、`gctrace=2`マーク）の前に呼び出すことで修正されます。

この新しい関数は`gcResetGState`と統合されるべきですが、それには追加のクリーンアップが必要なため、現在のフリーズ期間後に行われる予定です。このクリーンアップについては、Issue #11427が起票されています。

このコミットはIssue #10492を修正します。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作するコンカレントGCを採用しています。GCは主に「マーク」と「スイープ」のフェーズに分かれます。マークフェーズでは、到達可能なオブジェクトを識別し、スイープフェーズでは到達不能なオブジェクトが解放されます。

このコミットが修正する問題は、GCのマークフェーズに関連するライブヒープの会計処理の不正確さにありました。具体的には、以下のシナリオで問題が発生していました。

1.  **`checkmark`マーク**: これは、コンカレントGCの正確性を検証するために行われる追加のマークフェーズです。コンカレントマーク中に見落としがないかを確認するために、GCの最後にStop-The-World (STW) フェーズで実行されます。
2.  **`gctrace=2`による追加マーク**: `gctrace`はGCのデバッグ情報を出力するためのオプションです。`gctrace=2`を設定すると、GCの実行中に詳細な情報が出力され、これには追加のマーク処理が含まれることがあります。

これらの追加のマーク処理の前に、GCが内部的に使用するライブヒープの統計情報（`work.bytesMarked`や`work.initialHeapLive`など）が適切にリセットされていませんでした。その結果、これらのマーク処理が実行されると、GCはライブヒープが0バイトであると誤って計算してしまいました。

GoのGCコントローラは、ヒープのライブサイズに基づいて次のGCのタイミングを決定します。ライブヒープが0バイトであると誤認識されると、GCコントローラはヒープが非常に小さいと判断し、すぐに次のGCサイクルを開始してしまいます。これは、実際のヒープサイズが大きくても発生するため、不必要なGCが頻繁に発生し、アプリケーションのパフォーマンスに悪影響を及ぼす可能性がありました。

このコミットは、この誤った会計処理を修正し、GCコントローラが常に正確なライブヒープ情報に基づいて動作するようにすることで、GCの効率性と安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと関連する概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが動的に確保したメモリ領域のうち、もはや使用されない（到達不能な）ものを自動的に解放する仕組みです。Goはトレース型GCの一種であるマーク＆スイープ方式を採用しています。
*   **マーク＆スイープ (Mark & Sweep)**:
    *   **マークフェーズ**: GCルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを「ライブ」（使用中）としてマークします。GoのGCは、このマークフェーズの大部分をアプリケーションの実行と並行して（コンカレントに）行います。
    *   **スイープフェーズ**: マークされなかった（到達不能な）オブジェクトが「デッド」（未使用）と判断され、そのメモリ領域が解放され、再利用可能になります。
*   **コンカレントGC (Concurrent GC)**: GoのGCは、アプリケーションの実行と並行してマークフェーズの大部分を実行します。これにより、アプリケーションの一時停止時間（Stop-The-World, STW）を最小限に抑え、レイテンシを改善します。
*   **Stop-The-World (STW)**: GCの特定の短い期間、すべてのアプリケーションゴルーチンが一時停止される状態です。GoのGCはSTW期間を極力短くするように設計されていますが、GCルートの特定やマークフェーズの最終処理、スイープの準備など、一部の重要な処理はSTW中に行われます。
*   **`memstats.heap_live`**: Goランタイムが管理するメモリ統計情報の一部で、現在ライブ（使用中）と認識されているヒープメモリのバイト数を示します。GCコントローラはこの値などを参照して、次のGCのトリガータイミングを決定します。
*   **GCコントローラ**: Goランタイム内でGCの実行を制御するロジックです。ヒープの使用量やGCの頻度などを監視し、適切なタイミングでGCサイクルを開始します。
*   **`gctrace`**: Goプログラムの実行時に`GODEBUG=gctrace=1`または`gctrace=2`環境変数を設定することで、GCの動作に関する詳細なログを出力できます。`gctrace=2`はより詳細なデバッグ情報を提供し、追加のGCマーク処理をトリガーすることがあります。
*   **`work.bytesMarked`**: GCのマークフェーズ中にマークされたバイト数を追跡する内部変数です。
*   **`work.initialHeapLive`**: GCサイクル開始時のライブヒープサイズを記録する内部変数です。

これらの内部変数が正しくリセットされないと、GCコントローラが誤った情報に基づいて動作し、GCの効率が低下する原因となります。

## 技術的詳細

このコミットの技術的な核心は、Goのガベージコレクションにおけるライブヒープの正確な追跡と、それに基づくGCコントローラの適切な動作を保証することにあります。

問題の根源は、GCのマークフェーズが複数回実行される可能性があるにもかかわらず、その都度ライブヒープの会計状態が適切に初期化されていなかった点にあります。

1.  **通常のGCサイクル**: GoのコンカレントGCは、まずコンカレントマークフェーズを実行し、その後STWマークターミネーションフェーズでマークを完了します。この一連の処理の開始時には、ライブヒープの会計状態がリセットされることが期待されます。
2.  **`checkmark`**: これは、GCのデバッグや検証のために使用される特別なマークフェーズです。通常のGCマークが完了した後、STW中に再度マーク処理を実行し、コンカレントマーク中に見落としがなかったかを確認します。この`checkmark`の前に、ライブヒープの会計状態がリセットされていなかったため、前回のマーク処理の結果が残ってしまい、`checkmark`がライブヒープを0バイトと誤認識する原因となっていました。
3.  **`gctrace=2`**: このデバッグオプションが有効な場合、Goランタイムは追加のマーク処理を実行することがあります。これも`checkmark`と同様に、その前に会計状態がリセットされていなかったため、同様の誤認識を引き起こしていました。

これらの誤認識により、`memstats.heap_live`が不正確な値（0バイト）を報告し、GCコントローラはヒープが空であると判断して、すぐに次のGCサイクルを開始してしまいます。これは、アプリケーションがまだ十分なメモリを持っているにもかかわらず、不必要なGCオーバーヘッドを発生させることになります。

この修正では、`work.bytesMarked`と`work.initialHeapLive`という2つの重要な内部変数のリセット処理を`gcResetMarkState()`という新しい関数にカプセル化しました。そして、この関数を以下の3つの主要なマーク処理の直前に呼び出すように変更しました。

*   通常のGCサイクルの開始時 (`func gc(mode int)`)
*   `checkmark`の開始時 (`initCheckmarks()`)
*   `gctrace=2`による追加マーク処理の開始時

これにより、各マーク処理が常にクリーンな状態からライブヒープの会計を開始できるようになり、GCコントローラが正確な情報に基づいて動作するようになります。結果として、不必要なGCの連鎖が解消され、GCの効率とアプリケーションのパフォーマンスが向上します。

コミットメッセージには、`gcResetMarkState`を`gcResetGState`と統合すべきであるというTODOコメントが含まれています。これは、両者がGCの状態リセットに関連する処理であるため、将来的にコードの整理と簡素化を図るための計画です。Issue #11427で追跡されています。

## コアとなるコードの解説

このコミットの主要な変更は、`gcResetMarkState()`という新しい関数の導入と、その関数が`gc`関数内の複数の箇所で呼び出されるようになった点です。

1.  **`gcResetMarkState()` 関数の追加**:
    ```go
    // gcResetMarkState resets state prior to marking (concurrent or STW).
    //
    // TODO(austin): Merge with gcResetGState. See issue #11427.
    func gcResetMarkState() {
    	work.bytesMarked = 0
    	work.initialHeapLive = memstats.heap_live
    }
    ```
    この新しい関数は、GCのマークフェーズが開始される前に、ライブヒープの会計に関連する2つの重要な内部変数をリセットします。
    *   `work.bytesMarked = 0`: これは、現在のGCサイクルでマークされたバイト数を追跡する変数です。新しいマークフェーズが始まる前に0にリセットすることで、そのフェーズでのマーク量を正確に計測できるようにします。
    *   `work.initialHeapLive = memstats.heap_live`: これは、GCサイクル開始時のライブヒープサイズを記録する変数です。これもリセットすることで、各マークフェーズが独立してライブヒープの初期状態を把握できるようにします。

2.  **`gc` 関数内での `gcResetMarkState()` の呼び出し**:
    *   **通常のGCサイクルの開始時**:
        ```diff
        -\twork.bytesMarked = 0
        -\twork.initialHeapLive = memstats.heap_live
        +\tgcResetMarkState()
        ```
        `gc`関数の冒頭で、以前は直接行われていた`work.bytesMarked`と`work.initialHeapLive`のリセットが、`gcResetMarkState()`の呼び出しに置き換えられました。これにより、通常のGCマークフェーズが始まる前に状態が適切に初期化されます。

    *   **`checkmark` の開始時**:
        ```diff
        \t\t\tgcResetGState() // Rescan stacks
        +\t\t\tgcResetMarkState()
        \t\t\tinitCheckmarks()
        ```
        `checkmark`処理（コンカレントマークの検証のための追加マーク）が始まる直前にも`gcResetMarkState()`が呼び出されるようになりました。これにより、`checkmark`が独立したマークフェーズとして、クリーンな状態からライブヒープの会計を開始できます。

    *   **`gctrace=2` による追加マーク処理の開始時**:
        ```diff
        \t\t\tgcResetGState()
        +\t\t\tgcResetMarkState()
        \t\t\tfinishsweep_m()
        ```
        `gctrace=2`が有効な場合に実行される追加のマーク処理の直前にも`gcResetMarkState()`が呼び出されます。これも`checkmark`と同様に、この追加マークが正確なライブヒープ情報を報告できるようにするためです。

これらの変更により、GoのGCは、通常のGCサイクル、`checkmark`、`gctrace=2`による追加マークのいずれにおいても、ライブヒープの会計状態を常に正確に初期化するようになります。これにより、GCコントローラが誤った情報に基づいて不必要なGCをトリガーする問題が解消され、GCの動作がより予測可能で効率的になります。

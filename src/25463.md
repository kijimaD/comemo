# [インデックス 25463] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net` パッケージにおけるネットワーク接続確立（`Dial`）およびリッスン（`Listen`, `ListenPacket`）関数が、無効なポート番号に対して常に失敗するように挙動を変更するものです。これまでは、特定のデバッグ設定（`GODEBUG=netdns`）によっては無効なポート番号がエラーとならずに処理されてしまう可能性がありましたが、この変更によりその挙動が修正され、より堅牢なエラーハンドリングが実現されます。

## コミット

`net: make Dial, Listen{,Packet} for TCP/UDP with invalid port fail`

## 変更の背景

このコミットの主な背景には、Goの `net` パッケージにおけるポート番号の扱いの曖昧さがありました。特に、`Dial`、`Listen`、`ListenPacket` といったネットワーク操作関数が、無効なポート番号（例えば負の値や65535を超える値）を受け取った際に、一貫性のない挙動を示すことが問題となっていました。

具体的には、以下の点が挙げられます。

1.  **`GODEBUG=netdns` の影響**: `GODEBUG=netdns` という環境変数が設定されている場合、ポート番号の解決ロジックが変更され、無効なポート番号がエラーとして適切に処理されないケースがありました。これにより、開発者が意図しないポートで接続が試みられたり、リッスンが開始されたりする可能性がありました。
2.  **`cgoLookupPort` の挙動**: `cgoLookupPort` は、Cgoを介してシステムのポート解決機能を利用する際に使用される関数です。一部のプラットフォームでは、範囲外の数値リテラルがポート番号として与えられた場合、エラーを返さずに0または65535といった境界値を返してしまうことがありました。これは、無効な入力がサイレントに有効な値に変換されてしまうというセキュリティ上および信頼性上の問題を引き起こす可能性がありました。
3.  **一貫性の欠如**: ネットワークプログラミングにおいて、無効な入力は明確なエラーとして扱われるべきです。しかし、上記のような状況では、無効なポート番号がエラーとならずに処理されてしまい、アプリケーションの予期せぬ動作や脆弱性につながる恐れがありました。

これらの問題を解決し、`net` パッケージの堅牢性と信頼性を向上させるため、このコミットでは無効なポート番号が常にエラーとなるように修正が加えられました。これは、[Issue #11715](https://github.com/golang/go/issues/11715) で報告された問題への対応でもあります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **TCP/UDPポート番号**:
    *   TCP (Transmission Control Protocol) および UDP (User Datagram Protocol) は、インターネットプロトコルスイートの主要なトランスポート層プロトコルです。
    *   ポート番号は、IPアドレスと組み合わせて、特定のプロセスやサービスを識別するために使用されます。
    *   ポート番号は0から65535までの範囲の16ビットの符号なし整数です。
        *   0-1023: Well-known ports (予約済みポート、例: HTTP 80, HTTPS 443)
        *   1024-49151: Registered ports (登録済みポート)
        *   49152-65535: Dynamic/Private ports (動的/プライベートポート)
    *   この範囲外のポート番号は無効と見なされます。

2.  **Go `net` パッケージ**:
    *   Go言語の `net` パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。
    *   `Dial`: 指定されたネットワークアドレスへの接続を確立するために使用されます。例: `net.Dial("tcp", "localhost:8080")`
    *   `Listen`: 指定されたネットワークアドレスで着信接続をリッスンするために使用されます。例: `net.Listen("tcp", ":8080")`
    *   `ListenPacket`: 指定されたネットワークアドレスで着信パケットをリッスンするために使用されます。例: `net.ListenPacket("udp", ":1234")`
    *   `SplitHostPort`: "host:port" 形式の文字列をホストとポートに分割するユーティリティ関数です。
    *   `LookupPort`: ネットワークサービス名（例: "http"）またはポート番号の文字列表現を、対応する整数ポート番号に解決する関数です。

3.  **`GODEBUG` 環境変数**:
    *   `GODEBUG` はGoランタイムのデバッグオプションを設定するための環境変数です。
    *   `GODEBUG=netdns=1` のように設定することで、`net` パッケージのDNSルックアップの挙動をデバッグ目的で変更できます。このコミット以前は、この設定がポート解決の挙動にも影響を与え、無効なポートがエラーとならない原因の一つとなっていました。

4.  **`cgoLookupPort`**:
    *   Goの `net` パッケージは、DNSルックアップやサービス名からポート番号への解決に、Cgoを介してOSのネイティブ機能（例: `getservbyname`）を利用することがあります。
    *   `cgoLookupPort` は、このようなCgoベースのポート解決を行う内部関数の一つです。この関数が、一部のプラットフォームで範囲外のポート番号リテラルに対して誤った値を返す可能性がありました。

5.  **`dtoi` 関数**:
    *   `dtoi` (decimal to integer) は、文字列から整数を解析するための内部ユーティリティ関数です。このコミットでは、ポート番号の解析において、負の数や非常に大きな数を適切に処理できるように修正が加えられています。

## 技術的詳細

このコミットの技術的な核心は、ポート番号の解析と検証ロジックを `net` パッケージ内で一元化し、堅牢化することにあります。

1.  **`src/net/port.go` の削除と `LookupPort` への統合**:
    *   以前は `src/net/port.go` に `parsePort` という関数が存在し、ポート番号の解析と検証を行っていました。
    *   このコミットでは `src/net/port.go` ファイル自体が削除され、`parsePort` の機能は `src/net/lookup.go` 内の `LookupPort` 関数に統合されました。これにより、ポート解決のロジックが `LookupPort` に集約され、一貫性が向上します。

2.  **`LookupPort` におけるポート範囲検証の強化**:
    *   `src/net/lookup.go` の `LookupPort` 関数が大幅に修正されました。
    *   変更前は、`dtoi` で数値として解析できた場合、その値がそのまま返される可能性がありました。
    *   変更後、`LookupPort` はまず `dtoi` を使ってサービス名が数値リテラルであるかを試みます。
    *   数値リテラルとして解析された場合でも、その値が `0` から `65535` の有効なポート範囲内にあるかを厳密にチェックするようになりました。
    *   範囲外の値（負の数や65535を超える数）が検出された場合、`&AddrError{Err: "invalid port", Addr: service}` というエラーを返すようになりました。これにより、無効なポート番号がアプリケーションレベルで明確にエラーとして扱われることが保証されます。
    *   サービス名が数値リテラルでない場合は、引き続き `lookupPort` (CgoまたはGoネイティブのサービスルックアップ) を呼び出して解決を試みます。

3.  **`dtoi` 関数での負の数とオーバーフローの処理**:
    *   `src/net/parse.go` の `dtoi` 関数が修正され、負の数を適切に処理できるようになりました。文字列が `-` で始まる場合、負のフラグを立てて処理し、最終的に結果を負の値にします。
    *   また、`dtoi` は `big` (0xFFFFFF) という定数を使ってオーバーフローをチェックしていましたが、このチェックも負の数に対応するように調整されました。これにより、非常に大きな数値リテラルや負の数値リテラルが `dtoi` で解析される際に、より正確な結果またはエラーが返されるようになります。

4.  **テストケースの追加**:
    *   `src/net/error_test.go`、`src/net/parse_test.go`、`src/net/port_test.go` に、無効なポート番号（例: "-1", "123456789"）に対する新しいテストケースが追加されました。
    *   これらのテストは、`Dial`、`Listen`、`ListenPacket`、`LookupPort`、`dtoi` が無効なポートに対して期待通りにエラーを返すことを検証します。特に、`DialError` と `ListenError` のテストでは、`OpError` や `SyscallError` のラップを解除して、根本的なエラーが `errOpNotSupported` でないことを確認するロジックが追加されています。これは、OSによっては無効なポートが「操作がサポートされていません」のような一般的なエラーとして報告される可能性があるため、より具体的な「無効なポート」エラーを期待していることを示しています。

これらの変更により、`net` パッケージはポート番号の検証に関してより予測可能で安全な挙動を提供するようになります。

## コアとなるコードの解説

このコミットの主要な変更は、ポート番号の解析と検証を `LookupPort` 関数に集約し、そのロジックを強化した点にあります。

1.  **`src/net/ipsock.go` の変更**:
    *   `internetAddrList` 関数は、ネットワークアドレスを解析してIPアドレスとポート番号のリストを生成する内部関数です。
    *   以前は `parsePort` を呼び出してポート番号を解析していましたが、このコミットにより `LookupPort` を呼び出すように変更されました。これは、ポート解析の責任を `LookupPort` に完全に移譲し、一貫した検証ロジックを適用するための重要なステップです。

2.  **`src/net/lookup.go` の `LookupPort` の変更**:
    *   この関数は、サービス名（例: "http"）または数値文字列（例: "8080"）からポート番号を解決する役割を担います。
    *   **数値リテラルの直接解析と検証**: まず `dtoi(service, 0)` を呼び出して、`service` 文字列が直接ポート番号の数値リテラルであるかを試みます。
        *   `dtoi` が成功した場合でも、その `port` の値が `0` から `65535` の有効な範囲内にあるかを `if 0 > port || port > 65535` で厳密にチェックします。範囲外であれば、`&AddrError{Err: "invalid port", Addr: service}` という具体的なエラーを返します。これにより、`cgoLookupPort` が誤った値を返す可能性のあるシナリオや、`GODEBUG=netdns` の影響下での不適切な挙動が防止されます。
    *   **サービスルックアップへのフォールバック**: `dtoi` が失敗した場合（つまり、`service` が数値リテラルではない場合、例えば "http" のようなサービス名の場合）、または `dtoi` がオーバーフローを示す特別な値 (`big` または `-big`) を返した場合、`lookupPort(network, service)` を呼び出して、OSのサービスデータベースやDNS SRVレコードなどからポート番号を解決しようとします。このフォールバックロジックは以前から存在していましたが、数値リテラルに対する厳密な検証が先行することで、より安全な処理フローが確立されました。

3.  **`src/net/parse.go` の `dtoi` の変更**:
    *   `dtoi` 関数は、文字列から10進数整数を解析する内部ヘルパーです。
    *   **負の数処理**: 文字列の先頭が `-` であるかをチェックし、`neg` フラグを立てて負の数を正しく処理できるようにしました。これにより、"-1" のような入力が `dtoi` で適切に解析され、その後の `LookupPort` で無効なポートとして検出されるようになります。
    *   **オーバーフロー処理の改善**: `n >= big` のオーバーフローチェックにおいて、負の数である場合は `-big` を返すように修正されました。これにより、非常に大きな負の数値リテラルも適切にオーバーフローとして扱われます。

これらの変更により、Goの `net` パッケージは、ポート番号の入力に対してより堅牢で予測可能なエラーハンドリングを提供するようになり、開発者が無効なポート番号を誤って使用するリスクが低減されます。

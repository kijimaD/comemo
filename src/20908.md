# [インデックス 20908] ファイルの概要

このコミットは、Go言語のリンカーの一部である`src/liblink/obj9.c`ファイルに対する修正です。`obj9.c`は、Goプログラムのコンパイルおよびリンクプロセスにおいて、特にスタック管理、中でもスタック分割（stack splitting）のロジックを扱う重要な部分です。このファイルは、GoランタイムがGoルーチンのスタックサイズを動的に調整し、必要に応じて拡張するための命令シーケンスを生成する役割を担っています。

## コミット

このコミットは、Goランタイムのスタック分割ロジックにおけるバグを修正するものです。具体的には、非常に大きなスタックを必要とするケース（"really-big-stack case"）において、スタックプリエンプション（stack preempt）時の分岐ターゲットが失われる問題に対処しています。この問題は、無限ループを引き起こす可能性がありました。修正は、失われた分岐ターゲットを正しく復元することによって行われました。

## 変更の背景

Goランタイムは、Goルーチンのスタックを動的に拡張する「スタック分割（stack splitting）」というメカニズムを採用しています。これは、初期のスタックサイズを小さく保ち、必要に応じて拡張することでメモリ効率を高めるための重要な機能です。しかし、このメカニズムには複雑な側面があり、特にスタックが非常に大きくなるケース（"really-big-stack case"）や、ガーベージコレクションやスケジューリングのためにGoルーチンを一時停止させる「スタックプリエンプション（stack preemption）」の際に問題が発生することがあります。

このコミットの背景にある問題は、最近のコミットによって`splitstack`関数内で、特定の条件下で分岐ターゲットが失われるバグが導入されたことです。具体的には、スタックが非常に大きい場合にスタックプリエンプションが発生すると、リンカーが生成するアセンブリコード内の条件分岐命令が正しいジャンプ先を見失い、結果として無限ループに陥るという深刻な問題を引き起こしていました。この無限ループは、Goルーチンがスタックを拡張しようとする際に、`runtime.morestack`関数への呼び出しが正しく行われず、スタックチェックが常に失敗し続けるために発生しました。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムおよびリンカーに関する前提知識が役立ちます。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する中核部分です。スケジューリング、ガーベージコレクション、メモリ管理、スタック管理など、Go言語の並行性モデルと効率的な実行を支える多くの低レベルな機能を提供します。
*   **スタック (Stack)**: プログラム実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどを一時的に格納するために使用されるメモリ領域です。Goルーチンごとに独自のスタックを持ちます。
*   **スタック分割 (Stack Splitting)**: Go言語の重要な特徴の一つで、Goルーチンのスタックサイズを動的に調整するメカニズムです。Goルーチンは小さなスタックで開始し、関数呼び出しによってスタックが不足しそうになると、ランタイムが自動的にスタックを拡張します。これは、スタックの先頭に配置された「スタックガード（Stack Guard）」と呼ばれる特別な値と現在のスタックポインタを比較することで検出されます。スタックガードを超えてスタックを使用しようとすると、`runtime.morestack`関数が呼び出され、より大きなスタックへの切り替えが行われます。
*   **スタックガード (Stack Guard)**: 各Goルーチンのスタックの境界を示す値です。関数呼び出しのプロローグで、現在のスタックポインタがスタックガードを超えていないかチェックされます。これにより、スタックオーバーフローを検出し、スタック拡張のトリガーとなります。
*   **スタックプリエンプション (Stack Preemption)**: Goランタイムが、実行中のGoルーチンを安全なポイントで一時停止させるメカニズムです。これは主にガーベージコレクションのマークフェーズや、長時間実行されているGoルーチンがスケジューラに制御を戻す必要がある場合（協調的プリエンプション）に利用されます。スタックプリエンプションは、スタックガードの値を一時的に変更することでトリガーされます。Goルーチンがスタックチェックを行う際に、変更されたスタックガード値と現在のスタックポインタを比較し、プリエンプションが必要であると判断すると、`runtime.morestack`（または関連するプリエンプションハンドラ）が呼び出されます。
*   **`liblink`**: Goツールチェインの一部であるリンカーのライブラリです。コンパイラによって生成されたオブジェクトファイルを結合し、実行可能なバイナリを生成する役割を担います。このプロセスには、アセンブリコードの生成、シンボルの解決、そしてスタック分割のようなランタイムサポートコードの挿入が含まれます。
*   **`obj9.c`**: `liblink`ディレクトリ内のソースファイルの一つで、主にPlan 9アーキテクチャ（Goのコンパイラ・リンカーの設計思想の基盤）におけるオブジェクトファイルの生成と、特にスタック分割に関連するアセンブリ命令の生成ロジックを含んでいます。`stacksplit`関数はこのファイル内で定義されています。
*   **`Prog`構造体**: Goリンカーが内部的にアセンブリ命令を表現するために使用するデータ構造です。各`Prog`インスタンスは、命令の種類（`as`フィールド）、オペランド（`from`, `to`フィールド）、そして条件分岐命令の場合には分岐ターゲットとなる別の`Prog`インスタンスへのポインタ（`pcond`フィールド）など、命令に関する詳細な情報を含みます。

## 技術的詳細

このコミットが修正する問題は、`src/liblink/obj9.c`内の`stacksplit`関数に起因します。この関数は、Goルーチンのスタックが不足した場合にスタックを拡張するためのアセンブリコードシーケンスを生成します。

`stacksplit`関数は、スタックの現在の使用量と必要なフレームサイズに基づいて、いくつかのケースを処理します。問題が発生したのは、`framesize`が`StackBig`（非常に大きなスタック）を超える場合のロジックです。このケースでは、スタックプリエンプションのチェックも同時に行われます。

スタックプリエンプションは、`g->stackguard0`（通常のスタックガード）と`g->stackguard1`（プリエンプション用のスタックガード）の比較によってトリガーされます。プリエンプションが必要な場合、リンカーは以下のようなアセンブリ命令シーケンスを生成します（簡略化）：

1.  `CMP`命令: `g->stackguard0`と現在のスタックポインタを比較。
2.  `JMP`命令（条件付き分岐）: 比較結果に基づいて、スタックが足りないか、プリエンプションが必要な場合に特定の命令にジャンプ。
3.  `MOVD`命令: `StackPreempt`定数をレジスタにロード。
4.  `BL`命令: `runtime.morestack`関数を呼び出す。

問題は、`StackPreempt`のケースで生成される条件分岐命令（`ABEQ`）の分岐ターゲットが正しく設定されていなかったことにありました。リンカーは、条件分岐命令のターゲットを`Prog`構造体の`pcond`フィールドに設定する必要があります。しかし、以前のコードでは、`ABEQ`命令の直前の命令を指すポインタを保持する変数`q`が正しく更新されていなかったため、`ABEQ`命令の`pcond`フィールドが`nil`のままになっていました。

具体的には、`stacksplit`関数内で、`framesize <= StackSmall`（小さなスタック）と`framesize <= StackBig`（中程度のスタック）のケースでは、`q1`という変数が分岐ターゲットのポインタを保持し、その`pcond`フィールドが適切に設定されていました。しかし、`framesize > StackBig`（大きなスタック）のケースでスタックプリエンプションのロジックが追加された際、`q`という新しい変数が導入されましたが、この`q`が`ABEQ`命令の直前の命令を正しく参照し、その`pcond`フィールドを`runtime.morestack`への`BL`命令に設定するロジックが欠けていました。

結果として、`ABEQ`命令はどこにもジャンプせず、無限ループに陥るか、予期せぬ動作を引き起こしていました。

このコミットは、この`q`変数の取り扱いを修正することで問題を解決しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`stacksplit`関数における`Prog`ポインタ`q`の導入と、その適切な利用です。

1.  **`Prog *q, *q1;`**:
    *   以前は`Prog *q1;`のみが宣言されていました。この変更により、`q`という新しい`Prog`ポインタが追加されました。`q`は、スタックプリエンプションのケースで生成される条件分岐命令（`ABEQ`）の直前の命令を指すために使用されます。

2.  **`q = nil;`**:
    *   `stacksplit`関数の冒頭で、新しく導入された`q`ポインタが`nil`に初期化されます。これは、`q`が特定の条件（`StackPreempt`ケース）でのみ使用されるため、それ以外のケースでは`nil`であることを保証するためです。

3.  **`q = p = appendp(ctxt, p);`**:
    *   この行は、`framesize > StackBig`かつ`StackPreempt`が設定されている場合に実行されるブロック内にあります。
    *   以前は単に`p = appendp(ctxt, p);`でした。`appendp`関数は、新しい`Prog`命令を生成し、それをリンクリストに追加して、その新しい命令へのポインタを返します。
    *   この変更により、`ABEQ`命令が生成される直前の命令（`MOVD`命令で`StackPreempt`定数をロードする命令）へのポインタが`q`に保存されるようになりました。これにより、後続のステップでこの`q`が指す命令の`pcond`フィールドを正しく設定できるようになります。

4.  **`if(q) q->pcond = p;`**:
    *   この行は、`BL runtime.morestack(SB)`命令が生成される直前に追加されました。
    *   `q`が`nil`でない場合（つまり、`StackPreempt`のケースで`q`が前の命令を指している場合）、`q`が指す命令（`ABEQ`命令の直前の`MOVD`命令）の`pcond`フィールドが、現在の`p`（`BL runtime.morestack(SB)`命令）に設定されます。
    *   これにより、`ABEQ`命令が正しく`runtime.morestack`への呼び出しにジャンプするようになり、スタックプリエンプション時の無限ループが解消されます。

これらの変更により、Goリンカーはスタックプリエンプションをトリガーするアセンブリコードを正しく生成できるようになり、特に大きなスタックを使用するGoルーチンがプリエンプションされた際に、無限ループに陥ることなく`runtime.morestack`を呼び出してスタックを安全に処理できるようになりました。

# [インデックス 20535] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）における重要な変更を導入し、アセンブリ言語で記述された関数がGoのランタイムとどのように連携するかを改善します。特に、Goの関数プロトタイプ情報（引数のスタックマップ情報を含む）の扱いを自動化することで、コードの簡素化と特定のビルドエラーの修正を目指しています。

## 元コミット内容

このコミットは、Goリンカ（`liblink`）の動作を変更し、名前が `·` (中点) で始まるアセンブリ関数に対して、デフォルトでGoのプロトタイプ情報（特に引数のスタックマップ情報）を付与するようにします。これにより、Goから呼び出されるアセンブリ関数が、Goのガベージコレクション（GC）に必要なスタック情報を持つことが保証されます。

もし関数がGoから呼び出されず、Goプロトタイプ情報が不要な場合は、`name<>(SB)` の形式を使用してファイルローカルなシンボルとして定義することで、この自動付与の対象外とすることができます。

この変更は、`sync/atomic.StoreUint32` のような関数に引数のスタックマップ情報を提供することで、当時のBSDビルドの失敗を修正することを目的としています。

## 変更の背景

この変更の主な背景は、Goのランタイムとアセンブリコード間の連携における、スタックマップ情報の欠如による問題の解決です。特に、`sync/atomic` パッケージのような低レベルのアセンブリ関数が、Goのガベージコレクタが正しく動作するために必要な引数のスタックマップ情報を持っていなかったことが原因で、BSD環境でのビルドが失敗していました。

Goのガベージコレクタは、スタック上のどの値がポインタであるかを正確に識別する必要があります。アセンブリ関数がGoの規約に従って引数を扱う場合でも、リンカがその関数の引数レイアウトに関するメタデータ（スタックマップ）を持っていなければ、GCはスタック上のポインタを正しく追跡できません。

以前は、アセンブリ関数に `GO_ARGS` ディレクティブを明示的に記述することで、リンカにGoプロトタイプ情報を付与するよう指示していました。しかし、多くのランタイムやシステムコール関連のアセンブリ関数はGoの内部的な規約に従っており、`GO_ARGS` を明示的に記述するのは冗長であり、記述漏れによる問題を引き起こす可能性がありました。

このコミットは、`·` プレフィックスを持つ関数をGoの内部関数とみなし、自動的に必要なスタックマップ情報を付与することで、この問題を体系的に解決し、コードの保守性を向上させます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部動作に関する知識が必要です。

1.  **Goアセンブリ言語 (`.s` ファイル)**: Goは、パフォーマンスが重要な部分や、OSとの低レベルなインタラクション（システムコールなど）のために、独自のPlan 9アセンブリ構文を使用します。これらのファイルは、Goのコンパイラによって生成されるオブジェクトファイルにリンクされます。
2.  **Goリンカ (`liblink`)**: Goツールチェーンの一部であり、コンパイルされたGoコードとアセンブリコードを結合し、実行可能ファイルを生成する役割を担います。リンカは、シンボル解決、アドレスの再配置、そしてGoランタイムが必要とするメタデータ（スタックマップなど）の埋め込みを行います。
3.  **Goのガベージコレクション (GC) とスタックマップ**: Goは、正確な（precise）ガベージコレクションを採用しています。これは、GCがメモリ上のどの値がポインタであるかを正確に識別できることを意味します。特に、ゴルーチンのスタック上にあるポインタを識別するために「スタックマップ」というメタデータを使用します。スタックマップは、特定のプログラムカウンタ（PC）におけるスタックフレームのレイアウト（どのオフセットにポインタがあるか）を記述します。GCはこれを利用して、スタック上のポインタをたどり、到達可能なオブジェクトをマークします。
4.  **`GO_ARGS` ディレクティブ (旧来)**: 以前のGoアセンブリでは、Goの関数プロトタイプを持つアセンブリ関数に対して、リンカにその旨を伝えるために `GO_ARGS` ディレクティブを明示的に記述する必要がありました。これにより、リンカはその関数の引数に関するスタックマップ情報を生成し、実行可能ファイルに埋め込みました。
5.  **`·` (中点) シンボル**: Goの内部では、`runtime·` や `syscall·` のように、パッケージ名と関数名の間に `·` (中点) を使用して、内部的なシンボルやアセンブリ関数を表現する慣習があります。これは、Goのソースコードから直接参照できない、低レベルな実装の詳細を示すことが多いです。
6.  **`name<>(SB)` シンボル**: Goアセンブリにおけるシンボル定義の構文で、`name<>(SB)` は、そのシンボルがファイルローカルであることを示します。これは、他のファイルから参照されることを意図しない関数やデータに使用され、リンカがGoプロトタイプ情報を自動的に付与する対象外とすることができます。

## 技術的詳細

このコミットの核心は、Goリンカの `liblink` が、アセンブリ関数名の `·` プレフィックスを、その関数がGoのプロトタイプを持つことを示す暗黙的なシグナルとして扱うようになった点です。

具体的には、`src/liblink/objfile.c` 内の `writeobj` 関数が変更されました。この関数は、オブジェクトファイルを書き出す際に、Goの関数に関するメタデータを処理します。変更点では、リンカがすべてのテキストシンボル（関数）を走査し、その名前が `·` で始まるかどうかをチェックします。

名前が `·` で始まる関数が見つかった場合、リンカはその関数が `FUNCDATA_ArgsPointerMaps` という種類の関数データを持っているかを確認します。`FUNCDATA_ArgsPointerMaps` は、その関数の引数領域におけるポインタの配置を示すスタックマップ情報への参照です。もしこの情報がまだ付与されていない場合、リンカは自動的に `AFUNCDATA` 命令を生成し、`FUNCDATA_ArgsPointerMaps` をその関数に関連付けます。この `AFUNCDATA` 命令は、`s->name.args_stackmap` という形式のシンボルを参照します。このシンボルは、コンパイラが生成した、その関数の引数スタックマップデータの実体です。

この自動化により、`src/runtime` や `src/syscall` ディレクトリ内の多くのアセンブリファイルから、冗長な `GO_ARGS` ディレクティブを削除することが可能になりました。これにより、アセンブリコードが簡素化され、開発者が明示的に `GO_ARGS` を記述し忘れることによる潜在的なバグが減少します。

結果として、`sync/atomic.StoreUint32` のような関数が、Goのガベージコレクタが正しく動作するために必要な引数スタックマップ情報を確実に持つようになり、BSD環境でのビルド失敗が解消されました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/liblink/objfile.c`**: リンカのオブジェクトファイル書き出しロジック。Goプロトタイプ情報の自動付与に関する新しいロジックが追加されました。
*   **`src/runtime/asm_*.s`**: Goランタイムのアセンブリファイル。`·` プレフィックスを持つ関数から `GO_ARGS` ディレクティブが削除されました。
*   **`src/syscall/asm_*.s`**: システムコール関連のアセンブリファイル。同様に、`GO_ARGS` ディレクティブが削除されました。
*   **`test/nosplit.go`**: テストスイート。この変更の動作を検証するための調整が行われました。

## コアとなるコードの解説

### `src/liblink/objfile.c` の変更

`writeobj` 関数内に新しいループが追加されました。

```c
 	// Add reference to Go arguments for C or assembly functions without them.
 	for(s = text; s != nil; s = s->next) {
 		if(strncmp(s->name, "\"\\\"\\\".", 3) != 0)
 			continue;
 		found = 0;
 		for(p = s->text; p != nil; p = p->link) {
 			if(p->as == ctxt->arch->AFUNCDATA && p->from.type == ctxt->arch->D_CONST && p->from.offset == FUNCDATA_ArgsPointerMaps) {
 				found = 1;
 				break;
 			}
 		}
 		if(!found) {
 			p = appendp(ctxt, s->text);
 			p->as = ctxt->arch->AFUNCDATA;
 			p->from.type = ctxt->arch->D_CONST;
 			p->from.offset = FUNCDATA_ArgsPointerMaps;
 			p->to.type = ctxt->arch->D_EXTERN;
 			p->to.sym = linklookup(ctxt, smprint("%s.args_stackmap", s->name), s->version);
 		}
 	}
```

このコードブロックは以下の処理を行います。

1.  `for(s = text; s != nil; s = s->next)`: すべてのテキストシンボル（関数）を走査します。
2.  `if(strncmp(s->name, "\"\\\"\\\".", 3) != 0) continue;`: シンボル名が `·` (中点) で始まるかどうかをチェックします。C言語の文字列リテラルでは、`·` は `\"\\\".` と表現されます。この条件に合致しない関数はスキップされます。
3.  `for(p = s->text; p != nil; p = p->link)`: 現在の関数 `s` の命令リストを走査し、既に `FUNCDATA_ArgsPointerMaps` が付与されているかを確認します。
4.  `if(!found)`: もし `FUNCDATA_ArgsPointerMaps` が見つからなかった場合、リンカは新しい命令を関数 `s` の先頭に追加します。
    *   `p->as = ctxt->arch->AFUNCDATA;`: 命令の種類を `AFUNCDATA` (関数データ) に設定します。
    *   `p->from.type = ctxt->arch->D_CONST; p->from.offset = FUNCDATA_ArgsPointerMaps;`: この関数データが引数ポインタマップに関するものであることを指定します。
    *   `p->to.type = ctxt->arch->D_EXTERN; p->to.sym = linklookup(ctxt, smprint("%s.args_stackmap", s->name), s->version);`: この関数データが、`s->name.args_stackmap` という名前の外部シンボル（コンパイラが生成した実際のスタックマップデータ）を参照するように設定します。

この変更により、`·` プレフィックスを持つアセンブリ関数は、明示的な `GO_ARGS` ディレクティブがなくても、Goのガベージコレクタが必要とする引数スタックマップ情報を自動的に持つようになります。

### アセンブリファイルの変更 (`src/runtime/*.s`, `src/syscall/*.s`)

多くのGoランタイムおよびシステムコールのアセンブリファイルから、以下のような行が削除されました。

```assembly
-	GO_ARGS
```

例えば、`src/runtime/asm_386.s` の `runtime·asmcgocall` 関数は、`TEXT runtime·asmcgocall(SB),NOSPLIT,$0-8` から `TEXT ·asmcgocall(SB),NOSPLIT,$0-8` に変更され、同時に `GO_ARGS` が削除されています。これは、関数名が `runtime·asmcgocall` から `·asmcgocall` に変更されたことで、リンカが自動的にGoプロトタイプ情報を付与するようになったため、`GO_ARGS` が不要になったことを示しています。

### `test/nosplit.go` の変更

このテストファイルは、Goのアセンブリコードのコンパイルとリンクに関するテストを行っています。変更は、テスト対象のアセンブリコードの生成方法を調整し、新しいリンカの挙動（`·` プレフィックスによる自動的な `GO_ARGS` 相当の処理）を反映させるものです。具体的には、テスト用のGoファイルとアセンブリファイルを生成する際に、関数名に `·` を付与し、`GO_ARGS` を削除するような変更が加えられています。

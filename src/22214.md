このコミットは、Go言語のツールチェインにおけるリンカ（`5l`, `6l`, `8l`, `9l` および `ld`）のC言語で書かれた実装をGo言語による実装に置き換えるという、大規模なリファクタリングを伴う変更です。具体的には、既存のC言語ソースファイルを削除し、`new5l` のようなGo言語で書かれた新しいリンカの実装を、対応するアーキテクチャのリンカ名（例: `5l`）にリネームしています。これにより、Goツールチェインの自己ホスト化（self-hosting）をさらに推進し、Go言語エコシステムの一貫性と開発効率の向上を目指しています。

## 元コミット内容

`cmd/5l` などのコマンドにおいて、C言語で書かれたコードをGo言語で書かれたコードに置き換える。
具体的には、`cmd/new5l` を `cmd/5l` にリネームするなどの作業を行う。
ビルドを維持するための `cmd/dist` および `cmd/go` への最小限の変更が含まれる。
さらなる削除は、後続の変更リスト（CLs）で行われる予定。

## 変更の背景

Go言語は、その開発当初から自己ホスト型コンパイラとツールチェインを目指してきました。これは、コンパイラやリンカといったGo言語の基盤ツール自体をGo言語で記述することで、開発の効率性、保守性、そしてGo言語エコシステム全体の一貫性を高めるという目標です。

このコミット以前、Go言語のリンカはC言語で実装されていました。C言語での実装は、初期のGo言語開発において既存の知識やツールを活用する上で有利でしたが、Go言語が成熟するにつれて、C言語とGo言語の混在は以下のような課題をもたらしていました。

1.  **開発の複雑性**: C言語とGo言語のコードベースが混在することで、ビルドシステム、デバッグ、テスト、そして新しい機能の追加が複雑になります。異なる言語のイディオムやツールセットを扱う必要がありました。
2.  **保守性の課題**: C言語のコードは、Go言語のガベージコレクションや並行処理モデルといった現代的な機能の恩恵を受けられず、メモリ管理やエラーハンドリングにおいて手動での対応が必要でした。これはバグの温床となりやすく、保守コストを増大させます。
3.  **自己ホスト化の推進**: Go言語のツールチェイン全体がGo言語で書かれることは、Go言語の設計思想を体現し、Go言語そのものの信頼性と安定性を示す上で重要です。また、Go言語の新しい機能や最適化をツールチェイン自体に適用できるようになります。

このコミットは、これらの課題を解決し、Goツールチェインの完全なGo言語化に向けた重要な一歩として、リンカのC言語実装をGo言語実装に置き換えることを目的としています。これにより、Go言語のリンカはGo言語のランタイムとより密接に統合され、将来的な最適化や機能拡張が容易になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識があると役立ちます。

1.  **Go言語ツールチェイン**: Go言語のプログラムをビルド、テスト、実行するために使用される一連のツール群です。主要なツールには、コンパイラ (`go tool compile`)、アセンブラ (`go tool asm`)、リンカ (`go tool link`)、そしてそれらを統合する `go` コマンドなどがあります。
2.  **リンカ (Linker)**: コンパイラやアセンブラによって生成されたオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するプログラムです。リンカは、シンボル解決（異なるオブジェクトファイル間で参照される関数や変数のアドレスを決定する）や、ライブラリのリンク（静的リンクまたは動的リンク）といった重要な役割を担います。
    *   **`5l`, `6l`, `8l`, `9l`**: これらはGo言語の初期のリンカの名称で、それぞれ異なるCPUアーキテクチャ（`5l` はARM、`6l` はx86-64、`8l` はx86-32、`9l` はPPC64）に対応していました。これらの名称は、Plan 9オペレーティングシステムに由来しています。
    *   **`ld`**: Go言語のリンカの汎用的な名称です。実際には、各アーキテクチャ固有のリンカ（例: `5l`）が `ld` の実体として機能します。
3.  **自己ホスト化 (Self-hosting)**: プログラミング言語のコンパイラやツールチェインが、その言語自身で記述されている状態を指します。例えば、Go言語のコンパイラがGo言語で書かれている場合、Go言語は自己ホスト型であると言えます。自己ホスト化は、言語の成熟度を示す指標の一つであり、言語の進化とともにツールチェインも進化できるという利点があります。
4.  **Cgo**: Go言語の機能の一つで、C言語のコードをGo言語のプログラムから呼び出す（またはその逆）ことを可能にします。Go言語とC言語のコードベースが混在している場合、Cgoがその橋渡し役となります。このコミットは、リンカにおけるCgoの依存関係を減らす、あるいはなくす方向への一歩と見なせます。
5.  **リファクタリング**: ソフトウェアの外部的な振る舞いを変更せずに、内部構造を改善するプロセスです。このコミットは、リンカの機能を維持しつつ、その実装言語をC言語からGo言語へ変更するという、大規模なリファクタリングに該当します。
6.  **Change-Id**: Goプロジェクトで採用されているGerritコードレビューシステムで使用される識別子です。コミットメッセージに含まれる `Change-Id` は、特定の変更リスト（CL）を一意に識別します。

## 技術的詳細

このコミットの技術的な核心は、Go言語のリンカがC言語からGo言語へと完全に書き換えられた点にあります。これは単なる言語の置き換え以上の意味を持ちます。

Go言語のリンカは、Goプログラムのビルドプロセスにおいて非常に重要な役割を担っています。コンパイラが生成したオブジェクトファイル（`.o` ファイル）には、Goの関数、変数、型情報、そしてGoランタイムに関するメタデータが含まれています。リンカはこれらのオブジェクトファイルを結合し、最終的な実行可能バイナリを生成します。このプロセスには、以下のような複雑な処理が含まれます。

*   **シンボル解決**: 異なるオブジェクトファイル間で参照される関数やグローバル変数のアドレスを解決します。
*   **リロケーション (Relocation)**: コード内のアドレス参照を、最終的なメモリレイアウトに合わせて調整します。これは、プログラムがロードされるベースアドレスや、共有ライブラリ内の関数のアドレスが実行時まで確定しない場合に特に重要です。
*   **セクションの結合**: コードセクション（`.text`）、データセクション（`.data`）、読み取り専用データセクション（`.rodata`）、BSSセクション（`.bss`）などを結合し、最終的なバイナリのメモリレイアウトを決定します。
*   **デバッグ情報の生成**: DWARFなどのデバッグ情報を生成し、デバッガが実行中のプログラムの内部状態を理解できるようにします。
*   **プラットフォーム固有の処理**: ELF（Linux）、Mach-O（macOS）、PE（Windows）など、ターゲットOSの実行可能ファイル形式に合わせた処理を行います。これには、ヘッダの生成、セクションの配置、動的リンク情報の埋め込みなどが含まれます。

C言語で書かれたリンカは、ポインタ演算や低レベルのメモリ操作を多用していました。これをGo言語に移植する際には、Goの型安全性、ガベージコレクション、そしてより抽象化されたI/O操作を活用するように設計が変更されたと考えられます。

具体的には、コミットメッセージと差分から、以下の点が推測されます。

*   **ファイルのリネーム**: `src/cmd/new5l/asm.go` が `src/cmd/5l/asm.go` にリネームされているように、`new` プレフィックスを持つGo言語のリンカ実装が、正式なリンカのパスに移動されています。これは、Go言語実装がC言語実装の機能を完全に置き換える準備ができたことを示します。
*   **C言語ファイルの削除**: `src/cmd/5l/asm.c` や `src/cmd/ld/data.c` など、大量のC言語ソースファイルが削除されています。これは、C言語実装が完全にGo言語実装に置き換えられたことを明確に示しています。
*   **ビルドシステムの変更**: `src/cmd/dist/build.go` や `src/cmd/go/build.go` など、ビルド関連のGoファイルに最小限の変更が加えられています。これは、リンカのビルド方法がC言語からGo言語に変わったことに対応するためです。例えば、CコンパイラやCgoの呼び出しが不要になり、GoコンパイラとGoリンカ自身を使ってリンカをビルドするようになった可能性があります。
*   **Go言語の標準ライブラリの活用**: C言語で手動で実装されていたファイルI/O、データ構造、アルゴリズムなどが、Go言語の標準ライブラリの機能に置き換えられたと考えられます。これにより、コードの可読性、保守性、そして堅牢性が向上します。
*   **クロスコンパイルの容易化**: Go言語で書かれたリンカは、Go言語のクロスコンパイル機能の恩恵を直接受けられます。これにより、異なるアーキテクチャやOS向けのリンカを、単一のGo言語ソースコードベースから容易にビルドできるようになります。

この変更は、Go言語のツールチェインがGo言語自身で完全に構築されるという、Go言語の設計哲学における重要なマイルストーンの一つです。

## コアとなるコードの解説

このコミット自体は、具体的なGo言語のコード実装の詳細を示すものではなく、C言語からGo言語への移行という「行為」と、それに伴うファイルシステムの変更が中心です。したがって、「コアとなるコードの解説」は、削除されたC言語の機能がGo言語でどのように再実装されたかという一般的な概念に焦点を当てます。

Go言語で再実装されたリンカは、C言語版が持っていた以下の主要な機能をGoのイディオムとライブラリを用いて実現しています。

1.  **オブジェクトファイルの解析と読み込み**:
    *   C言語版では、おそらく手動でファイルI/Oを行い、バイナリデータを構造体にマッピングしていました。
    *   Go言語版では、`encoding/binary` パッケージや `bufio` パッケージなどを活用し、より安全かつ効率的にオブジェクトファイル（Goの`.a`アーカイブや`.o`オブジェクト）を解析し、メモリ上のデータ構造に読み込むようになっています。
2.  **シンボルテーブルの管理**:
    *   C言語版では、ハッシュテーブルやリンクリストといったデータ構造をC言語で直接実装していました。
    *   Go言語版では、組み込みの `map` や `slice` を利用してシンボルテーブルを管理します。これにより、メモリ管理の複雑さが軽減され、コードの可読性が向上します。
3.  **リロケーション処理**:
    *   C言語版では、ポインタ演算を駆使して、バイナリ内のアドレス参照を修正していました。
    *   Go言語版では、Goのポインタ型や構造体、そしてバイトスライス操作を組み合わせて、リロケーションエントリを処理し、最終的なバイナリイメージを構築します。Goの型システムは、誤ったポインタ操作によるバグを防ぐのに役立ちます。
4.  **実行可能ファイル形式の生成**:
    *   ELF、Mach-O、PEといった各OSの実行可能ファイル形式の構造を、Go言語の構造体として定義し、それらをバイナリとして書き出すロジックがGoで実装されています。
    *   C言語版では、`write` システムコールなどを直接使用していたかもしれませんが、Go言語版では `io` パッケージのインターフェースや `bytes.Buffer` などを活用し、より抽象化された方法でバイナリデータを構築・書き出します。
5.  **デバッグ情報の処理**:
    *   DWARFなどのデバッグ情報の生成・埋め込みもGo言語で再実装されています。これは、Goのコンパイラが生成するGo固有のデバッグ情報と、標準的なDWARF形式の間の変換ロジックを含みます。

全体として、Go言語での再実装は、C言語での低レベルな手動管理から、Go言語の提供する高レベルな抽象化と安全性への移行を意味します。これにより、リンカのコードベースはよりGoらしい（idiomatic Go）ものとなり、将来的なメンテナンスや機能追加が容易になります。

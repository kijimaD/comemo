# [インデックス 24779] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおいて、TLS (Transport Layer Security) の ServerHello メッセージが空の ALPN (Application-Layer Protocol Negotiation) プロトコルを提示した場合に、それを拒否する変更を導入します。これは、RFC 7301 で規定されている ALPN プロトコル名の要件（空であってはならない）に準拠するためのセキュリティ強化です。

## 変更の背景

この変更の背景には、TLSプロトコル拡張であるALPN (Application-Layer Protocol Negotiation) の仕様遵守があります。ALPNは、TLSハンドシェイク中にクライアントとサーバーがどのアプリケーションプロトコル（例: HTTP/1.1, HTTP/2）を使用するかをネゴシエートするための仕組みです。

RFC 7301のセクション3.1では、ALPNの `ProtocolName` フィールドは空であってはならないと明確に規定されています。しかし、Goの `crypto/tls` パッケージでは、これまで ClientHello メッセージに対してはこの制約を適用していましたが、ServerHello メッセージに対しては適用していませんでした。

この不整合は、悪意のあるサーバーが不正なALPNプロトコル名（空のプロトコル名）を提示した場合に、クライアントが予期しない動作をする可能性や、プロトコルスタックの脆弱性を引き起こす可能性を秘めていました。このコミットは、この仕様不遵守を修正し、セキュリティと堅牢性を向上させることを目的としています。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を提供するための暗号化プロトコルです。ウェブブラウザとサーバー間のHTTPS通信などで広く利用されています。TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために必要なパラメータ（暗号スイート、鍵、プロトコルバージョンなど）をネゴシエートするプロセスです。

### ALPN (Application-Layer Protocol Negotiation)

ALPNは、TLSハンドシェイクの一部として、クライアントとサーバーがどのアプリケーションプロトコルを使用するかをネゴシエートするためのTLS拡張です。例えば、HTTP/1.1とHTTP/2の両方をサポートするサーバーに対して、クライアントがHTTP/2を優先したい場合にALPNを使用します。

*   **ClientHello**: クライアントがTLSハンドシェイクを開始する際にサーバーに送信する最初のメッセージです。クライアントがサポートするTLSバージョン、暗号スイート、拡張機能（ALPNを含む）などを通知します。ALPN拡張が含まれる場合、クライアントはサポートするアプリケーションプロトコル名のリストを優先順位付きで提示します。
*   **ServerHello**: サーバーがClientHelloに応答して送信するメッセージです。サーバーが選択したTLSバージョン、暗号スイート、およびClientHelloで提示された拡張機能に対するサーバーの応答（ALPNを含む）などを通知します。ALPN拡張が含まれる場合、サーバーはクライアントが提示したリストの中から選択した単一のアプリケーションプロトコル名を提示します。

### RFC 7301

RFC 7301は、ALPNプロトコル拡張の仕様を定義するIETF (Internet Engineering Task Force) の文書です。このRFCのセクション3.1「Application-Layer Protocol Negotiation Extension」には、`ProtocolName` の形式に関する重要な制約が記述されています。具体的には、「`ProtocolName` は1バイト以上255バイト以下の長さでなければならない」とされており、これは空のプロトコル名が許可されないことを意味します。

## 技術的詳細

ALPNプロトコルは、TLSハンドシェイクの `ClientHello` および `ServerHello` メッセージ内で `Extension` としてやり取りされます。この拡張には、クライアントがサポートするプロトコル名のリスト（ClientHelloの場合）またはサーバーが選択した単一のプロトコル名（ServerHelloの場合）が含まれます。

RFC 7301の規定は、プロトコル名が意味のある文字列であることを保証し、プロトコルスタックが不正な入力によって混乱したり、予期しない動作をしたりするのを防ぐためのものです。空のプロトコル名は、プロトコルスタックがどのアプリケーションプロトコルを選択すべきか判断できない状況を引き起こす可能性があります。

このコミット以前は、Goの `crypto/tls` パッケージは `ClientHello` メッセージで受信したALPNプロトコル名が空でないことを検証していましたが、`ServerHello` メッセージで受信したALPNプロトコル名に対しては同様の検証を行っていませんでした。この非対称性は、悪意のあるサーバーが空のALPNプロトコル名を送信した場合に、Goクライアントがその不正なメッセージを受け入れてしまう可能性がありました。

この変更により、`ServerHello` メッセージのALPNプロトコル名も厳密に検証されるようになります。具体的には、ALPNプロトコル名の長さが0である場合、ハンドシェイクは失敗し、不正な `ServerHello` メッセージは拒否されます。これにより、GoのTLS実装はRFC 7301の仕様に完全に準拠し、プロトコルスタックの堅牢性とセキュリティが向上します。

## コアとなるコードの変更箇所

変更は `src/crypto/tls/handshake_messages.go` ファイルの `serverHelloMsg` 構造体の `unmarshal` メソッドにあります。

```diff
--- a/src/crypto/tls/handshake_messages.go
+++ b/src/crypto/tls/handshake_messages.go
@@ -763,6 +763,10 @@ func (m *serverHelloMsg) unmarshal(data []byte) bool {
 				return false
 			}
 			d = d[1:]
+			if len(d) == 0 {
+				// ALPN protocols must not be empty.
+				return false
+			}
 			m.alpnProtocol = string(d)
 		case extensionSCT:
 			d := data[:length]
```

## コアとなるコードの解説

`serverHelloMsg` の `unmarshal` メソッドは、受信した `ServerHello` メッセージのバイト列を解析し、`serverHelloMsg` 構造体にマッピングする役割を担っています。このメソッド内で、TLS拡張が処理されます。

変更が加えられた箇所は、`extensionALPN` (ALPN拡張) を処理する `case` ブロック内です。

元のコードでは、ALPNプロトコル名の長さ (`length`) を読み取った後、その長さ分のバイト列 (`d`) を抽出し、それを `m.alpnProtocol` に文字列として格納していました。しかし、この抽出されたバイト列 `d` が実際に空でないかどうかのチェックは行われていませんでした。

追加されたコードは以下の通りです。

```go
			if len(d) == 0 {
				// ALPN protocols must not be empty.
				return false
			}
```

この `if` 文は、ALPNプロトコル名を表すバイト列 `d` の長さが0であるかどうかをチェックします。もし `len(d)` が0であれば、それは空のプロトコル名が提示されたことを意味します。RFC 7301の規定に反するため、この場合は `return false` を実行し、`unmarshal` メソッドは失敗を返します。これにより、不正な `ServerHello` メッセージは処理されずに拒否され、TLSハンドシェイクは中断されます。

この変更により、Goの `crypto/tls` クライアントは、RFC 7301に準拠しない `ServerHello` メッセージを適切に拒否するようになり、プロトコルスタックの堅牢性が向上しました。

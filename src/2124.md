## 変更の背景

Go言語は2009年に初めて公開された比較的新しい言語であり、その仕様は初期段階で継続的に洗練されていました。このコミットが行われた時期は、Go言語の初期の設計段階にあたります。プログラミング言語の仕様において、式の評価順序は非常に重要な要素であり、その曖昧さはプログラマの混乱を招き、予期せぬバグの原因となる可能性があります。

Go言語の設計思想の一つに「シンプルさ」と「明確さ」があります。しかし、初期の仕様書には、特定の複雑な式における評価順序について、読者によっては解釈の余地がある記述が含まれていました。特に、複数の関数呼び出し、チャネルからの受信、配列のインデックス参照などが混在するような式では、どの部分がどの順序で評価されるのかが不明確な場合がありました。

このコミットは、このような曖昧さを解消し、Go言語の評価順序に関するルールをより厳密かつ明確に定義することを目的としています。これにより、Go言語のユーザーがコードの挙動をより正確に予測できるようになり、コンパイラの実装者も一貫した挙動を保証しやすくなります。また、コンパイラ最適化の余地を残しつつも、開発者が混乱しないように、意図的に評価順序が未指定とされるケースについても明確に記述することが求められました。

## 前提知識の解説

このコミットを理解するためには、Go言語における以下の基本的な概念と、一般的なプログラミング言語における評価順序の概念を理解しておく必要があります。

### 1. Go言語の評価順序の基本原則

Go言語では、多くのプログラミング言語と同様に、式の評価順序に関する明確なルールが定められています。基本的な原則として、Goでは「左から右への評価」が適用されることが多いですが、特定の操作（例：関数呼び出しの引数、複合リテラル、代入文の右辺）においては、その評価順序が部分的に未指定となる場合があります。これは、コンパイラが最適化を行うための自由度を確保するためです。

*   **オペランドの評価**: 演算子のオペランドは、通常、左から右に評価されます。
*   **関数呼び出しの引数**: 関数呼び出しの引数は、関数本体が実行される前に評価されます。引数の評価順序は、一般的には左から右ですが、並行処理が絡む場合や、特定の最適化のために未指定となる場合があります。
*   **チャネル操作**: チャネルからの受信（`<-ch`）や送信（`ch <- val`）は、その操作自体が評価されるタイミングで発生します。
*   **副作用**: 式の評価が、プログラムの状態を変更する「副作用」を持つ場合（例：関数呼び出し、代入、チャネル操作）、評価順序の明確さは特に重要になります。

### 2. 未指定の評価順序 (Unspecified Evaluation Order)

プログラミング言語の仕様において「未指定の評価順序」とは、特定の式の部分がどのような順序で評価されるかについて、言語仕様が保証しないことを意味します。これは、コンパイラの実装者が、パフォーマンス最適化のために評価順序を自由に選択できる余地を与えるために意図的に行われることがあります。

しかし、未指定の評価順序は、プログラマがその挙動に依存するコードを書くと、異なるコンパイラや異なるコンパイルオプションでビルドされた場合に、プログラムの挙動が変わってしまうという問題を引き起こす可能性があります。そのため、言語仕様では、未指定の評価順序が存在する箇所を明確に記述し、プログラマがその挙動に依存しないように注意を促すことが重要です。

### 3. Go言語仕様書 (Go Spec)

Go言語の公式な挙動は、Go言語仕様書（The Go Programming Language Specification）によって定義されています。この仕様書は、Go言語の構文、セマンティクス、組み込み型、演算子、ステートメント、パッケージなど、言語のあらゆる側面を網羅しています。開発者は、Go言語の正確な挙動を理解するために、この仕様書を参照します。このコミットが修正しているのは、まさにこの仕様書の一部です。

## 技術的詳細

このコミットは、Go言語仕様書内の「Order of evaluation」セクション、特に式の評価順序に関する例を修正しています。変更の核心は、評価順序が「指定されている部分」と「未指定の部分」をより明確に区別することにあります。

元の記述では、関数呼び出しの引数の評価順序について、`f(g(), h() + x[i()], <-c)` のような例を用いて、`g()`、`h()`、`i()`、`<-c` の順で評価されると説明していました。しかし、`f`、`x`、`i()` の戻り値による `x` のインデックス参照の評価順序については未指定であるとされていました。

このコミットでは、例を `y[f()], ok = g(h(), i() + x[j()], <-c), k()` というより複雑な代入文に変更しています。この新しい例では、以下の評価順序が明確に指定されています。

*   `f()`
*   `h()`
*   `i()`
*   `j()`
*   `<-c`
*   `g()`
*   `k()`

これらの関数呼び出しやチャネル操作は、特定の順序で発生することが保証されます。しかし、`x` の評価とインデックス参照、および `y` の評価については、依然として順序が未指定であると明記されています。

この変更のポイントは、単に例を更新するだけでなく、Go言語の評価順序に関するより一般的な原則を反映している点です。Goでは、関数呼び出しやチャネル操作といった「副作用を伴う操作」は、通常、左から右への順序で評価される傾向があります。しかし、配列やマップのインデックス参照、構造体のフィールドアクセスなど、値の取得のみを行う操作については、コンパイラが最適化のために評価順序を自由に選択できる余地を残しています。

また、別の変更として、`switch` 文の `case` 式の評価順序に関する記述も修正されています。元の記述では「top-to-bottom」（上から下へ）とされていましたが、これを「left-to-right and top-to-bottom」（左から右へ、そして上から下へ）と修正しています。これは、`case` 式が複数の部分から構成される場合に、その内部での評価順序も明確にするための変更です。例えば、`case x + y:` のような式では、`x` と `y` の評価が左から右に行われることを示唆しています。

これらの変更は、Go言語の初期段階において、言語の挙動をより厳密に定義し、開発者がGoコードのセ実行をより正確に理解できるようにするための重要なステップでした。

## コアとなるコードの解説

このコミットの主要な変更点は、Go言語仕様書内の2つの箇所です。

1.  **式の評価順序の例の変更**:
    *   変更前は、関数呼び出しの引数評価の例として `f(g(), h() + x[i()], <-c)` が挙げられていました。この例では、`g()`、`h()`、`i()`、`<-c` の順序が指定されているものの、`f`、`x`、`i()` の戻り値による `x` のインデックス参照の評価順序は未指定であると説明されていました。
    *   変更後は、より複雑な代入文の例 `y[f()], ok = g(h(), i() + x[j()], <-c), k()` に置き換えられました。この新しい例では、`f()`、`h()`、`i()`、`j()`、`<-c`、`g()`、`k()` の順序で関数呼び出しとチャネル通信が発生することが明確に指定されています。しかし、`x` の評価とインデックス参照、および `y` の評価については、依然として順序が未指定であると明記されています。
    *   この変更は、Go言語の評価順序に関するルールをより一般化し、特に副作用を伴う操作（関数呼び出し、チャネル操作）の順序を明確にしつつ、コンパイラ最適化の余地を残す部分（値の参照など）を区別するためのものです。

2.  **`switch` 文の `case` 式の評価順序の明確化**:
    *   変更前は、`switch` 文の `case` 式が「top-to-bottom」（上から下へ）評価されると記述されていました。
    *   変更後は、「left-to-right and top-to-bottom」（左から右へ、そして上から下へ）と修正されました。
    *   この修正は、`case` 式自体が複数の部分から構成される場合（例: `case x + y:`）に、その内部での評価順序（この場合は `x` の評価が `y` の評価より前に行われる）も明確にするためのものです。これにより、`switch` 文の挙動に関する曖昧さがさらに解消されます。

これらの変更は、Go言語の仕様をより厳密かつ正確にし、開発者がGoコードの挙動をより深く理解し、予測できるようにするための重要なドキュメントの改善です。

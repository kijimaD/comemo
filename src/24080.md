## 変更の背景

このコミットは、Go 1.5 リリースノートのドキュメント `doc/go1.5.html` を更新するものです。コミットメッセージによると、以前の変更がGitによって失われたため、再提出されたものです。このドキュメントの目的は、Go 1.5で導入された主要な変更点と新機能をユーザーに伝えることです。

Go 1.5は、Go言語の歴史において非常に重要なリリースであり、いくつかの根本的な変更が含まれていました。これには、C言語で書かれていたGoツールチェーン（コンパイラ、アセンブラ、リンカ）のGo言語への移植、新しい並行ガベージコレクタの導入、実験的なベンダーサポート、新しい`go tool trace`コマンドや`go doc`コマンドの追加などが含まれます。これらの大規模な変更は、Goのパフォーマンス、開発体験、および将来の拡張性に大きな影響を与えるものであり、その詳細を正確かつ包括的にドキュメント化する必要がありました。

コミットメッセージでは、`trace`コマンドとベンダーセクションがまだ不完全であること、そしてTODOが残っていることが言及されており、ドキュメント作成が進行中であったことを示唆しています。

## 前提知識の解説

このコミット内容を理解するためには、以下のGo言語およびコンピュータサイエンスの概念に関する知識が役立ちます。

1.  **Go言語のツールチェーン**: Go言語のプログラムをビルド、テスト、実行するために使用される一連のツール（`go build`, `go run`, `go test`など）と、それらを構成するコンパイラ（`gc`）、アセンブラ（`asm`）、リンカ（`ld`）などのバックエンドツール群を指します。Go 1.4までは、これらのバックエンドツールの一部はC言語で書かれていました。
2.  **ガベージコレクション (GC)**: プログラムが動的に確保したメモリのうち、もはや使用されなくなったものを自動的に解放する仕組みです。Goのガベージコレクタは、プログラムの実行中に一時停止（Stop-The-World: STW）を発生させ、その間に不要なメモリを回収します。STW時間が長いと、アプリケーションの応答性が低下する原因となります。
3.  **並行ガベージコレクタ (Concurrent GC)**: STW時間を最小限に抑えるために、アプリケーションの実行と並行してガベージコレクションの一部を実行するGCアルゴリズムです。Go 1.5で導入されたGCは、この並行性を大幅に強化しました。
4.  **ベンダー (Vendoring)**: プロジェクトが依存する外部ライブラリのソースコードを、プロジェクト自身のレポジトリ内にコピーして管理する手法です。これにより、外部依存のバージョン管理をより厳密に行い、ビルドの再現性を高めることができます。Go 1.5で実験的に導入されました。
5.  **`internal` パッケージ**: Go 1.4で導入され、Go 1.5で一般化された、特定のディレクトリ構造を持つパッケージのインポート制限ルールです。`internal`という名前のディレクトリ内にあるパッケージは、その`internal`ディレクトリを含むサブツリー内のパッケージからのみインポートできます。これにより、ライブラリの内部実装を外部から隠蔽し、APIの安定性を保つことができます。
6.  **`go tool trace`**: Go 1.5で導入された、Goプログラムの実行を詳細にトレースし、視覚化するためのツールです。スケジューラ、GC、システムコールなどのイベントを記録し、パフォーマンス分析に役立ちます。
7.  **`go doc`**: コマンドラインからGoパッケージやシンボルのドキュメントを表示するためのツールです。`godoc`とは異なり、コマンドラインでの利用に特化しており、より簡潔な表示を提供します。
8.  **`math/big` パッケージ**: 任意精度の整数および有理数演算を提供するGoの標準ライブラリパッケージです。コンパイラが定数式を評価する際に、より正確な計算を行うために利用されます。
9.  **`cgo`**: GoプログラムからC言語のコードを呼び出すためのGoの機能です。

## 技術的詳細

このドキュメント更新は、Go 1.5の以下の主要な技術的変更点を網羅しています。

1.  **GoツールチェーンのGo言語への移植 (Self-hosting)**:
    *   Go 1.5の最も画期的な変更点の一つは、コンパイラ、アセンブラ、リンカといったGoツールチェーンの主要部分が、C言語からGo言語に書き換えられたことです。これにより、Goのビルドプロセス全体がGo言語で完結するようになり、Go開発者はGo言語の知識だけでツールチェーンを理解・改善できるようになりました。
    *   コンパイラとリンカは、C言語のコードを機械的にGo言語に翻訳したものであり、機能的には以前のバージョンと同等です。この翻訳プロセスは、既存のバグを修正する効果もありました。
    *   アセンブラは、完全に新しいGo言語のプログラムとして実装されました。
    *   この変更により、GoのビルドにはGo 1.4以降のGoディストリビューションが必要となりました（ブートストラッププロセス）。
    *   ツール名も変更され、`6g`, `8g`などのアーキテクチャ固有のツールは廃止され、`go tool compile`, `go tool asm`, `go tool link`のように、`go tool`コマンドを介してアクセスする単一のツールに統合されました。中間オブジェクトファイルも`.6`, `.8`から`.o`に統一されました。
    *   コンパイラの定数評価には、より高精度な`math/big`パッケージが使用されるようになりました。
    *   `amd64`アーキテクチャ向けに、動的リンクを支援する`-dynlink`オプションがコンパイラに追加されました。
    *   リンカには、共有ライブラリのビルドやGoライブラリを他の言語から呼び出すことを可能にする`-buildmode`オプションが追加されました。

2.  **新しい並行ガベージコレクタ (Concurrent GC)**:
    *   Go 1.5では、ガベージコレクタが大幅に再設計され、並行性が強化されました。これにより、STW（Stop-The-World）ポーズ時間が劇的に短縮され、ほとんどの場合10ミリ秒未満、多くの場合それよりもはるかに短くなりました。
    *   これは、高度なアルゴリズム、コレクタのより良いスケジューリング、およびユーザープログラムと並行してより多くのコレクションを実行することの組み合わせによって実現されました。
    *   特に、ユーザー応答性が重要なウェブサイトなどの低レイテンシが求められるシステムにとって、この変更は非常に重要です。

3.  **ベンダーサポート (Vendoring Support)**:
    *   外部依存関係をプロジェクトのレポジトリ内に含める「ベンダー」の実験的なサポートが`go`コマンドに追加されました。これにより、依存関係の管理とビルドの再現性が向上します。

4.  **新しいツールと`go`コマンドの改善**:
    *   **`go tool trace`**: プログラム実行のきめ細かいトレースをサポートする新しいコマンドが追加されました。これにより、Goプログラムのパフォーマンス特性を詳細に分析できるようになります。
    *   **`go doc`**: `godoc`とは異なる、コマンドラインでの使用に特化した新しい`go doc`コマンドが導入されました。より簡潔で焦点を絞ったドキュメント表示を提供し、大文字小文字を区別しないマッチングや、エクスポートされていないシンボルのドキュメント表示もサポートします。
    *   **`internal` パッケージの一般化**: Go 1.4で導入された`internal`ディレクトリのインポート制限ルールが、すべてのレポジトリで利用可能になりました。これにより、ライブラリの内部実装を保護し、APIの安定性を向上させることができます。
    *   **`go generate` の機能強化**: `-run`オプションが追加され、実行するディレクティブを正規表現で選択できるようになりました。また、`$GOLINE`と`$DOLLAR`という新しい環境変数が利用可能になりました。
    *   **`go test -count`**: `go test`コマンドに`-count`フラグが追加され、テストを複数回実行できるようになりました。
    *   **`go tool vet` の改善**: 構造体タグの検証がより厳密になりました。
    *   **`cgo` の改善**: `#cgo`行で`${SRCDIR}`変数が展開されるようになり、ソースディレクトリからの相対パスをCコンパイラやリンカに渡すことが可能になりました。Windowsでは、`cgo`がデフォルトで外部リンキングを使用するようになりました。

5.  **パフォーマンスへの影響**:
    *   Go 1.5のベンチマークスイートでは、Go 1.4と比較して平均で数パーセント高速化されました。特にGCの一時停止時間は劇的に短縮されました。
    *   しかし、C言語からGo言語へのツールチェーンの翻訳により、ビルド時間は約2倍遅くなりました。これは、機械翻訳されたGoコードが、手書きのGoコードに比べて最適化されていないためです。今後のリリースで改善される予定です。

## コアとなるコードの解説

このコミット自体はドキュメントの変更であるため、直接的な「コアとなるコードの解説」は適用されません。しかし、このドキュメントが解説しているGo 1.5の主要な変更点について、その技術的な意味合いを深く掘り下げて解説します。

1.  **GoツールチェーンのGo言語への移植 (Self-hosting)**:
    *   **意味合い**: GoコンパイラがGo自身で書かれるようになったことは、Go言語の成熟度を示す大きなマイルストーンです。これにより、Go開発者はGo言語の知識だけでコンパイラの内部を理解し、改善できるようになります。C言語の知識が不要になるため、Go言語コミュニティ全体がツールチェーン開発に参加しやすくなります。
    *   **技術的詳細**: 以前のC言語で書かれたコンパイラは、Goのランタイムが持つ独自のスタック管理（goroutineのスタック切り替えなど）と連携するために、カスタムのCコンパイラが必要でした。Go言語で再実装されたことで、この複雑さが解消され、Goランタイムとツールチェーンの統合がよりスムーズになりました。機械翻訳されたコードは、当初は最適化が不十分でビルド時間が長くなるという副作用がありましたが、これは将来的な最適化の余地があることを意味します。`math/big`の利用は、コンパイラがより正確な定数計算を行えるようにするための改善です。

2.  **新しい並行ガベージコレクタ (Concurrent GC)**:
    *   **意味合い**: STWポーズ時間の劇的な短縮は、Goアプリケーションのレイテンシ特性を根本的に改善しました。特に、リアルタイム性の高いサービスやユーザーインタラクションが重要なアプリケーションにおいて、GCによる一時的なフリーズが大幅に減少します。
    *   **技術的詳細**: Go 1.5のGCは、トリコロールマーク＆スイープアルゴリズムをベースに、ライトバリア（write barrier）を導入しています。これにより、GCのマークフェーズの大部分をアプリケーションの実行と並行して行うことが可能になりました。STWフェーズは、マークの開始時と終了時に非常に短時間だけ発生し、主にスタックのスキャンとマークビットのフリップを行います。この並行処理と最適化されたスケジューリングにより、GCのオーバーヘッドが大幅に削減されました。

3.  **ベンダーサポート (Vendoring Support)**:
    *   **意味合い**: 依存関係のベンダーは、Goモジュールが導入される前のGoプロジェクトにおける依存関係管理の一般的な課題に対する重要な解決策でした。これにより、ビルドの再現性が向上し、外部依存の変更が予期せずプロジェクトに影響を与えるリスクが軽減されます。
    *   **技術的詳細**: `go`コマンドが`vendor`ディレクトリを認識し、その中のパッケージを優先的に解決するようになりました。これにより、`GOPATH`に依存する従来の依存解決メカニズムに加えて、プロジェクトローカルな依存関係管理が可能になりました。

4.  **`internal` パッケージの一般化**:
    *   **意味合い**: ライブラリ開発者が、外部に公開したくない内部実装を明確に区別できるようになりました。これにより、ライブラリのAPI設計がよりクリーンになり、後方互換性を維持しやすくなります。
    *   **技術的詳細**: `go`コマンドが`internal`という名前のディレクトリを特別扱いし、その中のパッケージへのインポートを制限します。このルールはコンパイル時に強制され、意図しない内部パッケージへの依存を防ぎます。

これらの変更は、Go言語がより成熟し、大規模なシステム開発や高性能なアプリケーション開発に適応するための基盤を強化したことを示しています。

## 元コミット内容

このコミットは、元々別のチェンジリスト（CL 135490044）に含まれる予定だった修正が、ファイル転送の過程で失われたため、改めて適用されたものです。Goのリンカーである`liblink`がARMアーキテクチャ向けにコードをビルドする際に発生していたエラーを解消することを目的としています。

## 変更の背景

Go言語のコンパイラとリンカーは、様々なアーキテクチャ（x86, ARM, ARM64など）に対応しています。それぞれのアーキテクチャには固有のアセンブリ命令セットと、それらを処理するためのバックエンドコードが必要です。このコミットが発生した2014年当時、GoのARMサポートはまだ進化の途上にあり、特定の命令の扱い方やコード生成ロジックに不整合が生じることがありました。

このコミットの背景には、以下の2つの主要な問題があったと考えられます。

1.  **`ANOP`命令の不適切な扱い**: ARMアーキテクチャにおける`ANOP`（No Operation）命令は、文字通り何もしない命令であり、通常はコードサイズに影響を与えません。しかし、リンカーがこの命令を「ゼロ幅の命令」として誤って診断し、エラーを発生させていた可能性があります。これは、リンカーが命令のサイズを計算するロジックに`ANOP`が考慮されていなかったためと考えられます。
2.  **スタック分割コード生成の不正確さ**: Goランタイムは、ゴルーチンのスタックを効率的に管理するために「スタック分割（stack splitting）」というメカニズムを使用します。これは、関数呼び出しの際にスタックの残量をチェックし、必要に応じてより大きなスタックを動的に割り当てる仕組みです。ARMアーキテクチャ向けのスタックチェックコードを生成する際に、比較命令（`CMP`）や条件分岐命令（`BEQ`, `BNE`）の表現方法に問題があり、正確なアセンブリコードが生成されていなかった可能性があります。

これらの問題は、GoプログラムをARMアーキテクチャ向けにコンパイル・リンクする際にビルドエラーを引き起こし、開発の妨げとなっていました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **Go言語のツールチェイン**: Go言語は、ソースコードをコンパイルして実行可能ファイルを生成するための一連のツール（コンパイラ、アセンブラ、リンカーなど）を提供します。
    *   **コンパイラ**: Goのソースコード（`.go`ファイル）をアセンブリコードに変換します。
    *   **アセンブラ**: アセンブリコードをオブジェクトファイル（`.o`ファイル）に変換します。
    *   **リンカー（`liblink`）**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。この過程で、シンボル解決、アドレスの再配置、スタックフレームの構築などが行われます。
*   **ARMアーキテクチャ**: スマートフォンや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのCPUアーキテクチャです。GoはARMプロセッサをサポートしており、ARMv5、ARMv6、ARMv7などのバージョンに対応しています。
*   **アセンブリ命令**: CPUが直接実行できる低レベルの命令です。各アーキテクチャには固有の命令セットがあります。
    *   **`ANOP` (ARM No Operation)**: 何もしない命令。プログラムの実行フローには影響を与えず、主にコードのアライメント調整やデバッグ時のブレークポイント設定などに使用されます。
    *   **`ACMP` (ARM Compare)**: 2つのオペランドを比較し、その結果をCPUのステータスレジスタ（CPSR）に設定する命令です。このレジスタの値に基づいて、後続の条件分岐命令が実行されます。
    *   **`AB` (ARM Branch)**: 無条件分岐命令。指定されたアドレスにプログラムの実行フローをジャンプさせます。
    *   **`ABEQ` (ARM Branch if Equal)**: 条件分岐命令。直前の比較結果が等しい（Equal）場合にのみ、指定されたアドレスにジャンプします。
    *   **`ABNE` (ARM Branch if Not Equal)**: 条件分岐命令。直前の比較結果が等しくない（Not Equal）場合にのみ、指定されたアドレスにジャンプします。
*   **スタック分割 (Stack Splitting)**: Goランタイムの重要な機能の一つで、ゴルーチンのスタックサイズを動的に調整するメカニズムです。Goのゴルーチンは非常に軽量であり、最初は小さなスタックで開始されます。関数呼び出しの際にスタックが不足しそうになると、ランタイムが自動的に新しい、より大きなスタックを割り当て、古いスタックの内容をコピーして切り替えます。これにより、スタックオーバーフローを防ぎつつ、メモリ使用量を最適化します。スタック分割は、関数のプロローグ（関数の冒頭部分）に挿入されるスタックチェックコードによって実現されます。
*   **`AFUNCDATA`, `APCDATA`, `ADATABUNDLEEND`**: これらはGoのアセンブラやリンカーが内部的に使用する擬似命令（pseudo-instructions）またはディレクティブです。これら自体は実行可能な機械語を生成しませんが、リンカーに対して関数に関するメタデータ（`AFUNCDATA`）、PC（プログラムカウンタ）に関するデータ（`APCDATA`、スタックトレースやプロファイリングに使用）、データバンドルの終了（`ADATABUNDLEEND`）などの情報を提供します。

## コアとなるコードの解説

### `src/liblink/asm5.c`における`ANOP`の追加と修正

`asm5.c`の変更は、GoのリンカーがARMの`ANOP`命令を正しく認識し、処理できるようにするためのものです。
*   `optab`は、リンカーが各命令の特性（オペランドの型、命令のカテゴリなど）をルックアップするために使用するテーブルです。ここに`ANOP`を追加することで、リンカーは`ANOP`を有効な命令として扱えるようになります。
*   `span5`関数は、命令のサイズを計算し、コード生成の際に命令が正しい幅を持っているか検証する役割を担っています。`ANOP`は本来サイズがゼロであるため、この関数が`ANOP`を「ゼロ幅の命令」として誤ってエラー報告しないように、例外リストに追加されました。これにより、リンカーは`ANOP`を正しくスキップし、ビルドエラーを防ぎます。
*   `buildop`関数は、アセンブリ命令を内部的なデータ構造に変換するプロセスの一部です。ここに`ANOP`のケースを追加することで、`ANOP`命令がリンカーのパイプラインで適切に処理されることが保証されます。

これらの変更により、ARMアセンブリコードに`ANOP`命令が含まれていても、Goのリンカーがそれを正しく解釈し、ビルドプロセスが中断されなくなります。

### `src/liblink/obj5.c`におけるスタック分割コードの改善

`obj5.c`の変更は、Goのスタック分割メカニズムがARMアーキテクチャ上でより正確かつ効率的に機能するようにするためのものです。
*   **`ACMP`命令のレジスタ指定**: `p->to.type = D_REG; p->to.reg = X;` から `p->reg = X;` への変更は、Goのリンカーが命令のオペランドを表現する方法の内部的な改善を示しています。これは、特定の命令タイプ（この場合は`ACMP`）において、宛先レジスタをより直接的に指定できるようになったことを意味し、コードの簡潔性や正確性に寄与します。
*   **条件分岐命令の明確化**: `AB`（無条件分岐）と条件コード（`C_SCOND_EQ`, `C_SCOND_NE`）の組み合わせを、直接的な条件分岐命令である`ABEQ`（Branch if Equal）や`ABNE`（Branch if Not Equal）に置き換えることは、非常に重要な改善です。
    *   以前の方式では、リンカーはまず汎用的な分岐命令を生成し、その後に条件を適用していました。これは機能的には正しいかもしれませんが、アセンブリコードの生成ロジックが複雑になる可能性があります。
    *   新しい方式では、リンカーは最初から特定の条件分岐命令を生成します。これにより、生成されるアセンブリコードがより意図に忠実になり、デバッグが容易になり、潜在的なバグのリスクが低減されます。また、コンパイラやリンカーの最適化パスが、よりセマンティックな命令表現に基づいて、より効果的なコードを生成できるようになる可能性もあります。

これらの変更は、Goのスタック分割がARM上で正確に機能するために不可欠であり、Goプログラムの安定性とパフォーマンスに直接影響を与えます。

## 変更の背景

Go言語のコンパイラとリンカーは、様々なアーキテクチャ（x86, ARM, ARM64など）に対応しています。それぞれのアーキテクチャには固有のアセンブリ命令セットと、それらを処理するためのバックエンドコードが必要です。このコミットが発生した2014年当時、GoのARMサポートはまだ進化の途上にあり、特定の命令の扱い方やコード生成ロジックに不整合が生じることがありました。

このコミットの背景には、以下の2つの主要な問題があったと考えられます。

1.  **`ANOP`命令の不適切な扱い**: ARMアーキテクチャにおける`ANOP`（No Operation）命令は、文字通り何もしない命令であり、通常はコードサイズに影響を与えません。しかし、リンカーがこの命令を「ゼロ幅の命令」として誤って診断し、エラーを発生させていた可能性があります。これは、リンカーが命令のサイズを計算するロジックに`ANOP`が考慮されていなかったためと考えられます。
2.  **スタック分割コード生成の不正確さ**: Goランタイムは、ゴルーチンのスタックを効率的に管理するために「スタック分割（stack splitting）」というメカニズムを使用します。これは、関数呼び出しの際にスタックの残量をチェックし、必要に応じてより大きなスタックを動的に割り当てる仕組みです。ARMアーキテクチャ向けのスタックチェックコードを生成する際に、比較命令（`CMP`）や条件分岐命令（`BEQ`, `BNE`）の表現方法に問題があり、正確なアセンブリコードが生成されていなかった可能性があります。

これらの問題は、GoプログラムをARMアーキテクチャ向けにコンパイル・リンクする際にビルドエラーを引き起こし、開発の妨げとなっていました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **Go言語のツールチェイン**: Go言語は、ソースコードをコンパイルして実行可能ファイルを生成するための一連のツール（コンパイラ、アセンブラ、リンカーなど）を提供します。
    *   **コンパイラ**: Goのソースコード（`.go`ファイル）をアセンブリコードに変換します。
    *   **アセンブラ**: アセンブリコードをオブジェクトファイル（`.o`ファイル）に変換します。
    *   **リンカー（`liblink`）**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。この過程で、シンボル解決、アドレスの再配置、スタックフレームの構築などが行われます。
*   **ARMアーキテクチャ**: スマートフォンや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのCPUアーキテクチャです。GoはARMプロセッサをサポートしており、ARMv5、ARMv6、ARMv7などのバージョンに対応しています。
*   **アセンブリ命令**: CPUが直接実行できる低レベルの命令です。各アーキテクチャには固有の命令セットがあります。
    *   **`ANOP` (ARM No Operation)**: 何もしない命令。プログラムの実行フローには影響を与えず、主にコードのアライメント調整やデバッグ時のブレークポイント設定などに使用されます。
    *   **`ACMP` (ARM Compare)**: 2つのオペランドを比較し、その結果をCPUのステータスレジスタ（CPSR）に設定する命令です。このレジスタの値に基づいて、後続の条件分岐命令が実行されます。
    *   **`AB` (ARM Branch)**: 無条件分岐命令。指定されたアドレスにプログラムの実行フローをジャンプさせます。
    *   **`ABEQ` (ARM Branch if Equal)**: 条件分岐命令。直前の比較結果が等しい（Equal）場合にのみ、指定されたアドレスにジャンプします。
    *   **`ABNE` (ARM Branch if Not Equal)**: 条件分岐命令。直前の比較結果が等しくない（Not Equal）場合にのみ、指定されたアドレスにジャンプします。
*   **スタック分割 (Stack Splitting)**: Goランタイムの重要な機能の一つで、ゴルーチンのスタックサイズを動的に調整するメカニズムです。Goのゴルーチンは非常に軽量であり、最初は小さなスタックで開始されます。関数呼び出しの際にスタックが不足しそうになると、ランタイムが自動的に新しい、より大きなスタックを割り当て、古いスタックの内容をコピーして切り替えます。これにより、スタックオーバーフローを防ぎつつ、メモリ使用量を最適化します。スタック分割は、関数のプロローグ（関数の冒頭部分）に挿入されるスタックチェックコードによって実現されます。
*   **`AFUNCDATA`, `APCDATA`, `ADATABUNDLEEND`**: これらはGoのアセンブラやリンカーが内部的に使用する擬似命令（pseudo-instructions）またはディレクティブです。これら自体は実行可能な機械語を生成しませんが、リンカーに対して関数に関するメタデータ（`AFUNCDATA`）、PC（プログラムカウンタ）に関するデータ（`APCDATA`、スタックトレースやプロファイリングに使用）、データバンドルの終了（`ADATABUNDLEEND`）などの情報を提供します。

## コアとなるコードの解説

### `src/liblink/asm5.c`における`ANOP`の追加と修正

`asm5.c`の変更は、GoのリンカーがARMの`ANOP`命令を正しく認識し、処理できるようにするためのものです。
*   `optab`は、リンカーが各命令の特性（オペランドの型、命令のカテゴリなど）をルックアップするために使用するテーブルです。ここに`ANOP`を追加することで、リンカーは`ANOP`を有効な命令として扱えるようになります。
*   `span5`関数は、命令のサイズを計算し、コード生成の際に命令が正しい幅を持っているか検証する役割を担っています。`ANOP`は本来サイズがゼロであるため、この関数が`ANOP`を「ゼロ幅の命令」として誤ってエラー報告しないように、例外リストに追加されました。これにより、リンカーは`ANOP`を正しくスキップし、ビルドエラーを防ぎます。
*   `buildop`関数は、アセンブリ命令を内部的なデータ構造に変換するプロセスの一部です。ここに`ANOP`のケースを追加することで、`ANOP`命令がリンカーのパイプラインで適切に処理されることが保証されます。

これらの変更により、ARMアセンブリコードに`ANOP`命令が含まれていても、Goのリンカーがそれを正しく解釈し、ビルドプロセスが中断されなくなります。

### `src/liblink/obj5.c`におけるスタック分割コードの改善

`obj5.c`の変更は、Goのスタック分割メカニズムがARMアーキテクチャ上でより正確かつ効率的に機能するようにするためのものです。
*   **`ACMP`命令のレジスタ指定**: `p->to.type = D_REG; p->to.reg = X;` から `p->reg = X;` への変更は、Goのリンカーが命令のオペランドを表現する方法の内部的な改善を示しています。これは、特定の命令タイプ（この場合は`ACMP`）において、宛先レジスタをより直接的に指定できるようになったことを意味し、コードの簡潔性や正確性に寄与します。
*   **条件分岐命令の明確化**: `AB`（無条件分岐）と条件コード（`C_SCOND_EQ`, `C_SCOND_NE`）の組み合わせを、直接的な条件分岐命令である`ABEQ`（Branch if Equal）や`ABNE`（Branch if Not Equal）に置き換えることは、非常に重要な改善です。
    *   以前の方式では、リンカーはまず汎用的な分岐命令を生成し、その後に条件を適用していました。これは機能的には正しいかもしれませんが、アセンブリコードの生成ロジックが複雑になる可能性があります。
    *   新しい方式では、リンカーは最初から特定の条件分岐命令を生成します。これにより、生成されるアセンブリコードがより意図に忠実になり、デバッグが容易になり、潜在的なバグのリスクが低減されます。また、コンパイラやリンカーの最適化パスが、よりセマンティックな命令表現に基づいて、より効果的なコードを生成できるようになる可能性もあります。

これらの変更は、Goのスタック分割がARM上で正確に機能するために不可欠であり、Goプログラムの安定性とパフォーマンスに直接影響を与えます。

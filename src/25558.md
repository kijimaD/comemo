## 元コミット内容

`cmd/internal/obj/arm: access global data via GOT on arm when -dynlink`

このコミットは、GoコンパイラのARMアーキテクチャ向けバックエンドにおいて、`-dynlink`オプションが指定された場合に、グローバルデータへのアクセスをGlobal Offset Table (GOT) を介して行うように変更するものです。

## 変更の背景

この変更の背景には、ダイナミックリンクされた実行ファイル（共有ライブラリを使用する実行ファイル）が、メモリ上のどこにロードされても正しく動作するための要件があります。これを「位置独立コード (Position-Independent Code, PIC)」と呼びます。

静的リンクされたプログラムでは、グローバル変数や関数への参照はコンパイル時に固定のアドレスに解決されます。しかし、ダイナミックリンクされたプログラムや共有ライブラリは、実行時に異なるメモリ位置にロードされる可能性があります。このため、コード内の絶対アドレス参照は問題を引き起こします。

ARMアーキテクチャのような一部のCPUアーキテクチャでは、PC（プログラムカウンタ）相対アドレッシングを使用してコード内のデータにアクセスすることが一般的です。しかし、グローバルデータへのアクセスは、通常、絶対アドレスまたはベースレジスタからのオフセットで行われます。PICを生成するためには、これらのグローバルデータへの参照も位置独立である必要があります。

ここでGOT（Global Offset Table）が登場します。GOTは、グローバルデータや外部関数への絶対アドレスを格納するテーブルです。プログラムは、直接グローバルデータのアドレスを参照する代わりに、GOT内のエントリをPC相対で参照し、そのエントリに格納されている絶対アドレスを使って実際のデータにアクセスします。これにより、コード自体はメモリ上のどこにロードされても変更する必要がなくなり、GOTの内容だけがローダーによって修正されることで、位置独立性が保たれます。

Goコンパイラが`-dynlink`フラグをサポートするようになったことで、ARMアーキテクチャにおいてもこのGOTメカニズムを適切に利用する必要が生じました。このコミットは、そのための具体的な実装変更です。

## 前提知識の解説

### ARMアーキテクチャ

ARM（Advanced RISC Machine）は、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのCPUアーキテクチャです。命令セットがシンプルで電力効率が高いため、スマートフォン、タブレット、IoTデバイスなどで主流となっています。ARMプロセッサは、レジスタベースの操作とロード/ストアアーキテクチャを特徴とし、PC（プログラムカウンタ）相対アドレッシングを多用します。

### ダイナミックリンク (Dynamic Linking)

ダイナミックリンクは、プログラムが実行時に共有ライブラリ（WindowsのDLL、Linuxの.soファイルなど）をロードして使用するメカニズムです。

*   **利点**:
    *   **メモリ効率**: 複数のプログラムが同じ共有ライブラリを使用する場合、ライブラリのコードはメモリに一度だけロードされ、各プログラムがそれを共有できます。
    *   **ディスク容量の節約**: ライブラリのコードが各実行ファイルにコピーされないため、実行ファイルのサイズが小さくなります。
    *   **保守性**: ライブラリのバグ修正や機能追加があった場合、ライブラリファイルを更新するだけで、それを使用するすべてのプログラムが恩恵を受けられます。プログラム自体を再コンパイルする必要がありません。
*   **静的リンクとの違い**: 静的リンクでは、必要なライブラリコードがコンパイル時に実行ファイルに直接組み込まれます。これにより、実行ファイルは自己完結型になりますが、サイズが大きくなり、ライブラリの更新にはプログラムの再コンパイルが必要です。

### GOT (Global Offset Table)

GOT（Global Offset Table）は、ダイナミックリンクされたプログラムがグローバル変数や外部関数にアクセスするために使用するデータ構造です。

*   **目的**: 位置独立コード (PIC) を実現するために、グローバルデータや外部関数への参照を間接化します。
*   **仕組み**:
    1.  コンパイル時、リンカはグローバルデータや外部関数への参照を、直接そのアドレスではなく、GOT内のエントリへの参照に変換します。
    2.  GOT自体は、プログラムのデータセクション内に配置され、そのアドレスはプログラムのロードアドレスからのオフセットで表現できます（つまり、GOTへの参照はPC相対で可能です）。
    3.  プログラムがGOT内のエントリを読み込むと、そのエントリには目的のグローバルデータや外部関数の実際のメモリ上のアドレスが格納されています。
    4.  プログラムローダーは、プログラムがメモリにロードされた後、GOT内のエントリを適切な絶対アドレスで埋め直します。
*   **GOTREF**: Goコンパイラの内部では、`obj.NAME_GOTREF`というシンボル名がGOT経由の参照を示すために使用されます。

### PIC (Position-Independent Code)

PIC（Position-Independent Code）は、メモリ上の任意のアドレスにロードされても正しく実行できる機械語コードです。

*   **必要性**: 共有ライブラリやダイナミックリンクされた実行ファイルは、実行時にロードされるメモリ位置が予測できないため、PICである必要があります。
*   **実現方法**:
    *   **PC相対アドレッシング**: コード内のジャンプやブランチ命令は、ターゲットの絶対アドレスではなく、現在のプログラムカウンタからの相対オフセットを使用します。
    *   **GOT/PLT (Procedure Linkage Table)**: グローバルデータや外部関数へのアクセスは、GOTを介して間接的に行われます。外部関数呼び出しにはPLTも使用されます。

### Goコンパイラ/リンカの内部構造に関連する概念

*   `obj.Link`: リンカのコンテキストを表す構造体。コンパイル/リンク処理全体の状態を管理します。`Flag_dynlink`はダイナミックリンクが有効かどうかを示すフラグです。
*   `obj.Prog`: アセンブリ命令（プログラム）を表す構造体。命令の種類（`As`）、オペランド（`From`, `To`, `From3`）、オフセットなどの情報を含みます。
*   `obj.Addr`: オペランドのアドレスを表す構造体。タイプ（`Type`）、名前（`Name`）、シンボル（`Sym`）、オフセット（`Offset`）、レジスタ（`Reg`）などの情報を含みます。
*   `obj.LSym`: リンカシンボルを表す構造体。シンボルの名前、タイプ、アドレスなどの情報を含みます。
*   `obj.TYPE_MEM`: オペランドがメモリ参照であることを示します。
*   `obj.NAME_EXTERN`: 外部シンボル（グローバルデータや関数）への参照を示します。
*   `obj.NAME_GOTREF`: GOT経由で参照されるシンボルを示します。このコミットで導入または利用が強化されています。
*   `obj.R_PCREL`: PC相対リロケーションタイプ。命令のアドレスからの相対オフセットで解決されます。
*   `obj.R_GOTPCREL`: GOTエントリへのPC相対リロケーションタイプ。GOTエントリのアドレスがPC相対で解決されます。
*   `ADUFFCOPY`, `ADUFFZERO`: Goランタイムが使用する特殊な命令で、メモリのコピーやゼロクリアを高速に行うためのものです。これらは通常、アセンブリ言語で実装されたルーチンへの呼び出しに変換されます。

## 技術的詳細

このコミットの主要な目的は、GoコンパイラがARMアーキテクチャ向けにダイナミックリンクされたバイナリを生成する際に、グローバルデータへのアクセスをGOT経由で行うようにすることです。これは、主に`src/cmd/internal/obj/arm/obj5.go`内の`rewriteToUseGot`関数によって実現されます。

`rewriteToUseGot`関数は、`progedit`関数（プログラムの編集、つまりアセンブリ命令の変換を行う関数）から呼び出され、`ctxt.Flag_dynlink`が設定されている場合に実行されます。この関数は、特定のアセンブリ命令パターンを検出し、それらをGOT経由のアクセスに変換する一連のルールを適用します。

### `ADUFFCOPY` / `ADUFFZERO` 命令の変換

`ADUFFCOPY`や`ADUFFZERO`といった特殊な命令は、Goランタイムの内部でメモリ操作のために使用されます。これらの命令は、通常、`runtime.duffcopy`や`runtime.duffzero`といったランタイム関数への呼び出しに変換されます。ダイナミックリンク環境では、これらのランタイム関数もGOT経由でアクセスされる必要があります。

`rewriteToUseGot`関数は、これらの命令を以下のように変換します。

1.  `MOVW runtime.duffxxx@GOT, R9`: `runtime.duffxxx`シンボルのGOTエントリのアドレスをレジスタ`R9`にロードします。`obj.NAME_GOTREF`がここで使用されます。
2.  `ADD $offset, R9`: 元の`ADUFFxxx`命令にオフセットが指定されていた場合、そのオフセットを`R9`に加算します。
3.  `CALL (R9)`: `R9`に格納されたアドレス（GOTエントリから取得した`runtime.duffxxx`関数のアドレス）を介して関数を呼び出します。

### グローバルデータアドレスのロード (`MOVW $sym, Rx` の変換)

グローバルシンボル`sym`のアドレスをレジスタ`Rx`にロードする命令（例: `MOVW $sym, Rx`）は、以下のように変換されます。

1.  `MOVW sym@GOT, Rx`: `sym`のGOTエントリのアドレスを`Rx`にロードします。
2.  `ADD <off>, Rx` (オプション): もし元の命令にオフセット（例: `MOVW $sym+<off>, Rx`）が含まれていた場合、そのオフセットを`Rx`に加算します。

これにより、`Rx`にはグローバルデータ`sym`の実際のメモリ上のアドレスが格納されます。

### グローバルデータへのロード/ストア (`MOVx sym, Ry` / `MOVx Ry, sym` の変換)

グローバルデータ`sym`からレジスタ`Ry`へのロード（例: `MOVx sym, Ry`）や、`Ry`から`sym`へのストア（例: `MOVx Ry, sym`）は、以下のように変換されます。

1.  `MOVW sym@GOT, R9`: `sym`のGOTエントリのアドレスを一時レジスタ`R9`にロードします。
2.  `MOVx (R9), Ry` または `MOVx Ry, (R9)`: `R9`をベースレジスタとして、間接的にグローバルデータにアクセスします。

この変換は、元の命令を`Nopout`（無効化）し、その後に新しい2つの命令（GOTアドレスロードと実際のデータアクセス）を挿入することで実現されます。

### `src/cmd/internal/obj/arm/asm5.go` の変更点

*   `aclass`関数: オペランドのクラスを分類する関数で、`obj.NAME_GOTREF`が`obj.TYPE_MEM`および`obj.TYPE_ADDR`のケースに追加されました。これにより、GOT参照が正しく認識され、処理されるようになります。
*   `asmout`関数: アセンブリ命令を機械語に変換し、リロケーション情報を生成する関数です。
    *   `ctxt.Flag_shared != 0` (ダイナミックリンクが有効) の場合、リロケーションタイプが`obj.R_PCREL`または`obj.R_GOTPCREL`に設定されるようになりました。
    *   特に、`p.To.Name == obj.NAME_GOTREF`の場合に`obj.R_GOTPCREL`が使用されるようになり、GOTエントリへのPC相対リロケーションが正しく生成されます。

これらの変更により、GoコンパイラはARMアーキテクチャ上で、ダイナミックリンクされた実行ファイルがグローバルデータに位置独立な方法でアクセスできるようになります。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm/asm5.go` の変更点

1.  **`aclass` 関数への `obj.NAME_GOTREF` の追加**:
    *   `obj.TYPE_MEM` および `obj.TYPE_ADDR` の `switch a.Name` ステートメントに `obj.NAME_GOTREF` が追加されました。これは、オペランドがGOT経由で参照されるシンボルである場合に、アセンブラがそれを正しく分類できるようにするためです。これにより、リンカが生成するGOT参照がアセンブラによって適切に処理される基盤が作られます。
    *   `ctxt.Instoffset = 0` の追加は、`TYPE_REG` のケースで `Instoffset` をリセットし、誤ったオフセットが後の処理に影響を与えないようにするためのものです。

2.  **`asmout` 関数でのリロケーションタイプ決定ロジックの変更**:
    *   `ctxt.Flag_shared != 0` (ダイナミックリンクが有効) のブロック内で、リロケーションタイプを決定するロジックが追加されました。
    *   `p.To.Name == obj.NAME_GOTREF` の場合、リロケーションタイプは `obj.R_GOTPCREL` に設定されます。これは、GOTエントリ自体がPC相対で参照される必要があることを示します。
    *   それ以外の場合（`obj.NAME_EXTERN`など）、リロケーションタイプは `obj.R_PCREL` に設定されます。これは、通常のPC相対参照を示します。
    *   この変更により、ダイナミックリンクされたバイナリにおいて、GOTエントリへの参照が正しく解決されるようになります。

### `src/cmd/internal/obj/arm/obj5.go` の変更点

1.  **`progedit` 関数からの `rewriteToUseGot` の呼び出し**:
    *   `progedit` 関数は、アセンブリ命令のリストを走査し、必要に応じて命令を変換するGoリンカの重要なフェーズです。
    *   `if ctxt.Flag_dynlink { rewriteToUseGot(ctxt, p) }` という行が追加され、ダイナミックリンクが有効な場合に、各プログラム（命令）`p`に対して`rewriteToUseGot`関数が呼び出されるようになりました。

2.  **`rewriteToUseGot` 関数の実装**:
    *   この関数は、グローバルデータへのアクセスをGOT経由に書き換える主要なロジックを含んでいます。
    *   **`ADUFFCOPY` / `ADUFFZERO` の変換**:
        *   `p.As == obj.ADUFFCOPY || p.As == obj.ADUFFZERO` の条件で、これらの特殊命令を検出します。
        *   `obj.Linklookup` を使用して `runtime.duffzero` または `runtime.duffcopy` のシンボルを取得します。
        *   元の命令を `AMOVW` (GOTアドレスロード)、`AADD` (オフセット加算)、`obj.ACALL` (間接呼び出し) の3つの命令シーケンスに変換します。
        *   `p.From.Name = obj.NAME_GOTREF` を設定することで、このロードがGOT経由であることをアセンブラに伝えます。
    *   **`MOVW $sym, Rx` (アドレスロード) の変換**:
        *   `p.From.Type == obj.TYPE_ADDR && p.From.Name == obj.NAME_EXTERN && !p.From.Sym.Local` の条件で、外部グローバルシンボルのアドレスをロードする命令を検出します。
        *   元の `MOVW` 命令の `From` オペランドのタイプを `obj.TYPE_MEM` に、名前を `obj.NAME_GOTREF` に変更します。これにより、`sym` のアドレスがGOT経由でロードされるようになります。
        *   もしオフセットがある場合 (`p.From.Offset != 0`)、元の命令の後に `AADD` 命令を追加してオフセットを加算します。
    *   **`MOVx sym, Ry` / `MOVx Ry, sym` (データロード/ストア) の変換**:
        *   `p.From.Name == obj.NAME_EXTERN` または `p.To.Name == obj.NAME_EXTERN` の条件で、外部グローバルデータへのロード/ストア命令を検出します。
        *   `obj.ATEXT`, `obj.AFUNCDATA`, `obj.ACALL`, `obj.ARET`, `obj.AJMP` などの命令は変換対象外とします。
        *   `obj.Appendp` を使用して、元の命令の前に2つの新しい命令を挿入します。
            1.  `AMOVW sym@GOT, R9`: グローバルシンボル `sym` のGOTエントリのアドレスを一時レジスタ `R9` にロードします。
            2.  元の `MOVx` 命令を複製し、そのオペランドを `R9` をベースレジスタとする間接参照に書き換えます。
        *   元の命令は `obj.Nopout(p)` によって無効化されます。

これらの変更により、GoコンパイラはARMアーキテクチャにおいて、ダイナミックリンクされたバイナリがグローバルデータにアクセスする際に、GOTを介した位置独立な方法を自動的に適用するようになります。これは、共有ライブラリの利用や、より柔軟なデプロイメントシナリオを可能にする上で不可欠な機能です。

# [インデックス 24136] ファイルの概要

このコミットは、`cmd/go` ツールにおける `go get -u` コマンドが内部パッケージ（internal packages）を含む依存関係を更新する際に発生していた問題を修正します。具体的には、`go get -u` がチェックアウトディレクトリ以外で実行された場合に、内部パッケージのインポートが許可されないというエラー（"use of internal package not allowed"）で失敗する問題を解決します。

## 変更の背景

このコミットは、主にGoのパッケージ管理ツール `go get` の `-u` (update) オプションが、内部パッケージ（`internal` ディレクトリ配下のパッケージ）を含む依存関係を更新する際に発生していたバグを修正するために導入されました。

具体的には、Issue #11307 で報告された問題は、`go get -u` を実行した際に、更新対象のパッケージが `internal` パッケージをインポートしていると、「use of internal package not allowed」というエラーが発生し、更新が失敗するというものでした。この問題は、特に `go get -u` がパッケージのチェックアウトディレクトリ（`GOPATH` 内のソースコードがある場所）以外で実行された場合に顕著でした。

`internal` パッケージは、その親ディレクトリとその兄弟ディレクトリ内のパッケージからのみインポートが許可されるという特殊なアクセス制限を持っています。`go get` がパッケージの依存関係を解決し、ダウンロードする過程で、この `internal` パッケージのアクセスルールが正しく評価されないケースがあったため、上記のエラーが発生していました。このコミットは、パッケージのロードロジックを調整し、`internal` パッケージのインポートが適切なコンテキストで行われるようにすることで、この問題を解決しています。

Issue #11055 については、具体的な情報が見つかりませんでしたが、コミットメッセージに記載されていることから、同様に `go get -u` の動作に関連する問題であったと推測されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念について知っておく必要があります。

1.  **`go get` コマンド**:
    `go get` は、Goのパッケージや依存関係をダウンロードし、インストールするためのコマンドです。指定されたパッケージのソースコードを `GOPATH` (Go 1.11以降はGo Modules) にダウンロードし、必要に応じてビルド・インストールします。
    *   **`go get -u`**: このフラグは、指定されたパッケージとその依存関係を最新バージョンに更新することを指示します。既存のパッケージがある場合、それを最新のコミットやタグに更新しようとします。

2.  **`GOPATH`**:
    Go 1.10以前のGoのワークスペースの概念です。Goのソースコード、コンパイル済みパッケージ、実行可能ファイルが配置されるディレクトリ構造を定義していました。`src`、`pkg`、`bin` の3つのサブディレクトリを持ちます。`go get` はここにパッケージをダウンロードしていました。Go Modulesの導入により、`GOPATH` は必須ではなくなりましたが、一部のレガシーなビルドシステムやツールでは依然として使用されることがあります。

3.  **Go Modules**:
    Go 1.11で導入され、Go 1.13でデフォルトとなった公式の依存関係管理システムです。プロジェクトのルートディレクトリに `go.mod` ファイルを配置することで、プロジェクトの依存関係をバージョン管理し、`GOPATH` の外でもプロジェクトをビルドできるようになります。`go get` コマンドもGo Modulesのコンテキストで動作します。

4.  **パッケージのインポートパス**:
    Goのパッケージは、ファイルシステム上のパスやリポジトリのURLに対応するインポートパスによって識別されます（例: `github.com/user/repo/package`）。

5.  **`internal` パッケージ**:
    Go 1.4で導入された機能で、パッケージの可視性を制限するために使用されます。`internal` という名前のディレクトリに配置されたパッケージは、その `internal` ディレクトリの親ディレクトリにあるパッケージからのみインポートが許可されます。例えば、`example.com/myproject/internal/foo` というパッケージは、`example.com/myproject` 配下のパッケージからはインポートできますが、`example.com/anotherproject` からはインポートできません。これは、ライブラリの内部実装を外部に公開しないための強力なメカニズムです。

6.  **`importStack`**:
    Goのパッケージローダーが依存関係を解決する際に使用する、インポートパスのスタックです。循環参照の検出や、エラーメッセージのコンテキスト提供に役立ちます。

7.  **`loadPackage` と `loadImport`**:
    Goの `cmd/go` 内部で使用されるパッケージロード関数です。
    *   `loadPackage(path string, stk *importStack)`: 通常、ルートレベルのパッケージをロードするために使用されます。
    *   `loadImport(path string, parentDir string, parentSrcDir string, stk *importStack, p *Package)`: 既存のパッケージ（`parent`）のコンテキスト内で、その依存関係として別のパッケージをロードするために使用されます。`internal` パッケージの可視性チェックは、この `parentDir` や `parentSrcDir` の情報に基づいて行われます。

## 技術的詳細

このコミットの核心は、`cmd/go` の `get.go` ファイル内の `download` 関数におけるパッケージのロード方法の変更にあります。

以前の `download` 関数は、常に `loadPackage(arg, stk)` を呼び出してパッケージをロードしていました。しかし、`internal` パッケージの可視性ルールは、インポート元のパッケージ（`parent`）のパスに基づいて評価されます。`loadPackage` は、インポート元のコンテキストを考慮せずにパッケージをロードするため、`go get -u` が依存関係として `internal` パッケージを更新しようとした際に、その `internal` パッケージがインポート元のパッケージと同じ親ディレクトリにない場合、「use of internal package not allowed」というエラーが発生していました。これは、`go get -u` が既にダウンロード済みのパッケージの依存関係を再帰的に更新する際に、`internal` パッケージのインポートが外部からのインポートと誤認されるためです。

この修正では、`download` 関数に `parent *Package` という新しい引数を追加し、インポート元のパッケージのコンテキストを明示的に渡すようにしました。そして、パッケージをロードする際に、この `parent` 引数の有無によって `loadPackage` と `loadImport` を使い分ける `load` クロージャを導入しました。

*   `parent == nil` の場合（つまり、ルートレベルのパッケージをダウンロードする場合）は、これまで通り `loadPackage(arg, stk)` を使用します。
*   `parent != nil` の場合（つまり、既存のパッケージの依存関係をダウンロードする場合）は、`loadImport(arg, parent.Dir, nil, stk, nil)` を使用します。`loadImport` は `parent.Dir` を参照することで、`internal` パッケージの可視性チェックを正しく行えるようになります。

また、`importStack` の操作も変更されています。以前は `download` 関数内で `stk.push(p.ImportPath)` と `stk.pop()` が `downloadPackage` の呼び出しを挟む形で存在していましたが、新しいコードでは `download` 関数の冒頭で `stk.push(arg)` を行い、`defer stk.pop()` を使って関数終了時に必ずスタックから取り除くように変更されています。これにより、スタックの管理がより堅牢になり、エラー発生時にもスタックが正しくクリーンアップされるようになります。

`go_test.go` に追加された `TestIssue11307` は、この修正が正しく機能することを確認するためのテストケースです。`github.com/rsc/go-get-issue-11307` というテスト用のリポジトリを使用して、`go get` と `go get -u` が `internal` パッケージを含む依存関係を正しく処理できることを検証しています。

## コアとなるコードの解説

### `src/cmd/go/get.go` の変更点

1.  **`download` 関数のシグネチャ変更**:
    `func download(arg string, stk *importStack, getTestDeps bool)`
    から
    `func download(arg string, parent *Package, stk *importStack, getTestDeps bool)`
    に変更されました。
    これにより、`download` 関数が呼び出される際に、現在処理しているパッケージの親パッケージ（`parent`）の情報を渡せるようになりました。この `parent` 情報が、`internal` パッケージの可視性チェックにおいて重要になります。

2.  **`runGet` 関数からの `download` 呼び出し**:
    `runGet` 関数内で最初に `download` を呼び出す箇所が、`download(arg, &stk, *getT)` から `download(arg, nil, &stk, *getT)` に変更されました。
    これは、`runGet` が直接 `go get` の引数として与えられたパッケージをダウンロードする最初の呼び出しであるため、親パッケージは存在しない（`nil`）ということを示しています。

3.  **`load` クロージャの導入**:
    `download` 関数内に `load` という匿名関数（クロージャ）が定義されました。
    ```go
    load := func(path string) *Package {
        if parent == nil {
            return loadPackage(arg, stk)
        }
        return loadImport(arg, parent.Dir, nil, stk, nil)
    }
    ```
    このクロージャは、`parent` 引数の値に基づいて、パッケージのロード方法を動的に切り替えます。
    *   `parent == nil` の場合: `loadPackage` を使用します。これは、トップレベルのパッケージをロードする際に適しています。
    *   `parent != nil` の場合: `loadImport` を使用し、`parent.Dir` を渡します。`loadImport` は、指定されたディレクトリ（`parent.Dir`）を基準としてインポートパスを解決するため、`internal` パッケージの可視性ルールを正しく適用できます。これにより、`internal` パッケージが親パッケージのコンテキスト内でインポートされていると正しく認識され、「use of internal package not allowed」エラーが回避されます。

4.  **パッケージロードの統一**:
    `download` 関数内のパッケージロード処理が、すべてこの `load` クロージャを介して行われるようになりました。
    *   `p := loadPackage(arg, stk)` が `p := load(arg)` に変更。
    *   `p := loadPackage(arg, stk)` が `p := load(arg)` に変更（`pkgs` ループ内）。

5.  **`importStack` 操作の変更**:
    以前は `downloadPackage` の前後で `stk.push` と `stk.pop` が行われていましたが、新しいコードでは `download` 関数の冒頭で `stk.push(arg)` を行い、`defer stk.pop()` を使用して関数が終了する際に必ずスタックから要素が取り除かれるように変更されました。
    ```diff
    -	stk.push(p.ImportPath)
     	err := downloadPackage(p)
     	if err != nil {
     		errorf("%s", &PackageError{ImportStack: stk.copy(), Err: err.Error()})
    -		stk.pop()
     		return
     	}
    ```
    ```go
    	stk.push(arg)
    	defer stk.pop()
    ```
    この変更により、エラーが発生した場合でも `importStack` が正しく管理され、スタックの不整合を防ぐことができます。

6.  **依存関係の再帰的なダウンロード呼び出し**:
    パッケージの依存関係（`p.deps`, `p.TestImports`, `p.XTestImports`）を再帰的にダウンロードする際に、`download(dep.ImportPath, stk, false)` のように呼び出されていた箇所が、`download(dep.ImportPath, p, stk, false)` のように、現在のパッケージ `p` を `parent` 引数として渡すように変更されました。
    これにより、依存関係のダウンロード時にも、その依存関係がどのパッケージからインポートされているかというコンテキストが正しく伝達され、`internal` パッケージの可視性チェックが適切に行われるようになります。

### `src/cmd/go/go_test.go` の変更点

1.  **`TestIssue11307` の追加**:
    `go get -u` が `internal` パッケージを含むリポジトリを正しく更新できることを検証するための新しいテストケースが追加されました。
    このテストは、`github.com/rsc/go-get-issue-11307` という特定のテスト用リポジトリを使用しています。このリポジトリは、`internal` パッケージを含む構造になっており、`go get -u` が以前失敗していたシナリオを再現します。テストは、まず `go get` でパッケージをダウンロードし、次に `go get -u` で更新を試みることで、修正が正しく機能することを確認します。

これらの変更により、`go get -u` コマンドは、`internal` パッケージの可視性ルールを正しく尊重しながら、依存関係を更新できるようになりました。

# [インデックス 24173] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）において、関数値シンボルの定義タイミングを「使用時」から「宣言時」に変更するものです。これにより、共有ライブラリを使用する際に発生していた問題を解決します。

## 変更の背景

このコミットの背景には、Goコンパイラが関数値（function value）に関連するシンボルを処理する方法に起因する問題がありました。以前のGoコンパイラでは、関数値のシンボルは「使用時（at use）」に定義されていました。これは、コンパイラが特定の関数値がコード内で実際に参照されるまで、その関数値に対応するシンボルを生成しなかったことを意味します。

しかし、このアプローチは共有ライブラリ（shared libraries）を使用する際に問題を引き起こしました。共有ライブラリは、複数のプログラムで共有されるコードやデータを含むファイルであり、プログラムの実行時に動的にリンクされます。共有ライブラリの文脈では、シンボルが「使用時」に定義されると、リンカがシンボルを解決する際に必要な情報が不足したり、シンボルの重複定義や未定義エラーが発生したりする可能性がありました。特に、異なるコンパイル単位（例えば、メインプログラムと共有ライブラリ）が同じ関数値を異なるタイミングで参照しようとすると、シンボル解決の不整合が生じやすくなります。

この問題は、GoのIssue #11480で報告されたものとされています。共有ライブラリのサポートはGoの進化において重要な側面であり、シンボル解決の正確性は、異なるコンパイルモデルやデプロイメントシナリオに対応するために不可欠です。このコミットは、この根本的なシンボル定義のタイミングの問題を解決し、共有ライブラリとの互換性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールです。コンパイルプロセスは、字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成などの複数のフェーズに分かれています。
2.  **シンボル (Symbol)**: プログラム内の変数、関数、型などの名前を表す識別子です。コンパイラやリンカは、これらのシンボルを使ってコード内の参照を解決し、メモリ上の正しいアドレスにマッピングします。
3.  **関数値 (Function Value)**: Goでは関数は第一級オブジェクトであり、変数に代入したり、引数として渡したり、戻り値として返したりすることができます。このような関数を「関数値」と呼びます。関数値は、実行時に特定のコードブロックへの参照として扱われます。
4.  **クロージャ (Closure)**: 周囲の環境（スコープ）にある変数を捕捉（キャプチャ）する関数値です。クロージャは、その定義された環境の変数を参照し続けることができます。
5.  **共有ライブラリ (Shared Libraries)**: 複数の実行可能ファイルや他のライブラリによって共有されるコードの集合です。プログラムの実行時にメモリにロードされ、シンボル解決によってプログラムとリンクされます。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が促進されます。
6.  **シンボル解決 (Symbol Resolution)**: リンカの主要なタスクの一つで、プログラム内の未解決のシンボル参照（例えば、関数呼び出しや変数アクセス）を、対応する定義（例えば、関数の実装や変数のメモリ位置）に結びつけるプロセスです。
7.  **宣言時 (at declaration) と 使用時 (at use)**:
    *   **宣言時**: 変数や関数がコード内で初めて宣言される時点。
    *   **使用時**: 変数や関数がコード内で実際に参照または呼び出される時点。
    コンパイラがシンボルをいつ定義するかは、これらのタイミングのいずれかになります。

## 技術的詳細

このコミットの核心は、Goコンパイラが関数値のシンボルを生成するタイミングを、これまでの「使用時」から「宣言時」へと変更した点にあります。

以前のコンパイラでは、関数値がコード内で実際に使用されるまで、その関数値に対応するシンボルは生成されませんでした。これは、不要なシンボルを生成しないという点で効率的であるように見えますが、共有ライブラリのコンテキストでは問題を引き起こしました。共有ライブラリは、プログラムのロード時にシンボル解決を行う必要がありますが、もし必要な関数値シンボルがまだ定義されていない場合、リンカはそれらを解決できず、実行時エラーやリンクエラーが発生する可能性がありました。

この変更により、関数値が宣言された時点で、対応するシンボルがコンパイラによって確実に生成されるようになります。これにより、共有ライブラリがリンクされる際に、必要なすべての関数値シンボルが利用可能となり、シンボル解決の失敗を防ぐことができます。

具体的には、`makefuncsym`という新しいヘルパー関数が導入され、既存の`makeclosure`関数と`funchdr`関数から呼び出されるようになりました。

*   `makeclosure`はクロージャ（匿名関数）を生成する際に呼び出されます。クロージャも一種の関数値であるため、そのシンボルも宣言時に定義される必要があります。
*   `funchdr`は通常の関数のヘッダを処理する際に呼び出されます。トップレベルの関数やメソッドも関数値として扱われる可能性があるため、そのシンボルも宣言時に定義されるように変更されました。

`makefuncsym`関数は、与えられたシンボル`s`に対して、対応する関数シンボル`s1`を生成し、その`Def`フィールド（シンボルの定義を表すノード）を設定します。これにより、シンボルテーブルにその関数値の定義が登録され、リンカが参照できるようになります。

この変更は、Goのコンパイルモデル、特に共有ライブラリのサポートにおいて、より堅牢なシンボル管理を実現するための重要なステップです。

## コアとなるコードの変更箇所

変更は主に`src/cmd/compile/internal/gc/closure.go`と`src/cmd/compile/internal/gc/dcl.go`の2つのファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/closure.go`**:
    *   `makeclosure`関数内に`makefuncsym(xfunc.Func.Nname.Sym)`の呼び出しが追加されました。これは、クロージャが作成される際に、その関数値シンボルを宣言時に定義することを保証します。

2.  **`src/cmd/compile/internal/gc/dcl.go`**:
    *   `funchdr`関数内に、`importpkg == nil && n.Func.Nname != nil`という条件付きで`makefuncsym(n.Func.Nname.Sym)`の呼び出しが追加されました。これは、パッケージのインポート時ではなく、現在のパッケージ内で関数が宣言される際に、その関数値シンボルを定義することを意味します。
    *   既存の`funcsym`関数から、`s1.Def == nil`のチェックとそれに続く`s1.Def`、`s1.Def.Func.Shortname`、`funcsyms`への設定ロジックが削除されました。
    *   `makefuncsym`という新しい関数が追加されました。この関数は、与えられたシンボル`s`に対して、`funcsym`を呼び出して関数シンボル`s1`を取得し、`s1.Def`、`s1.Def.Func.Shortname`、`funcsyms`を設定する役割を担います。`isblanksym(s)`のチェックにより、ブランク識別子（`_`）のシンボルは処理されません。

## コアとなるコードの解説

このコミットの核となる変更は、`makefuncsym`関数の導入と、その関数が`makeclosure`および`funchdr`から呼び出されるようになった点です。

### `makefuncsym`関数の役割

```go
func makefuncsym(s *Sym) {
	if isblanksym(s) {
		return
	}
	s1 := funcsym(s)
	s1.Def = newfuncname(s1)
	s1.Def.Func.Shortname = newname(s)
	funcsyms = list(funcsyms, s1.Def)
}
```

*   `isblanksym(s)`: シンボル`s`がブランク識別子（`_`）であるかどうかをチェックします。ブランク識別子は特別な意味を持つため、通常のシンボル定義の対象外とされます。
*   `s1 := funcsym(s)`: 与えられたシンボル`s`に対応する関数シンボル`s1`を取得します。`funcsym`は、`s.Name + "·f"`という形式で関数値の内部シンボル名を生成し、それを`s.Pkg`（パッケージ）内で検索または作成します。
*   `s1.Def = newfuncname(s1)`: `s1`の`Def`フィールドに新しい関数名ノードを設定します。`Def`フィールドは、シンボルの定義を表す抽象構文木（AST）ノードへのポインタであり、これによりコンパイラはシンボルがどこで定義されているかを追跡できます。
*   `s1.Def.Func.Shortname = newname(s)`: 関数値の「短い名前」を設定します。これはデバッグ情報やエラーメッセージなどで使用される可能性があります。
*   `funcsyms = list(funcsyms, s1.Def)`: `funcsyms`というグローバルリストに、新しく定義された関数値の定義ノードを追加します。このリストは、コンパイラの後のフェーズで、すべての関数値シンボルを処理するために使用されます。

### `makeclosure`での呼び出し

```go
// src/cmd/compile/internal/gc/closure.go
func makeclosure(func_ *Node) *Node {
    // ... 既存のコード ...
    makefuncsym(xfunc.Func.Nname.Sym) // ここが追加された
    // ... 既存のコード ...
}
```

`makeclosure`は、Goのクロージャ（匿名関数）がコンパイルされる際に呼び出されます。クロージャは、その場で定義され、変数に代入されたり、直接呼び出されたりする関数値です。この変更により、クロージャが宣言された直後に、そのクロージャに対応する関数値シンボルが`makefuncsym`によって定義されるようになります。これにより、クロージャが共有ライブラリの境界を越えて使用される場合でも、シンボル解決の問題が発生しなくなります。

### `funchdr`での呼び出し

```go
// src/cmd/compile/internal/gc/dcl.go
func funchdr(n *Node) {
    // ... 既存のコード ...
    if importpkg == nil && n.Func.Nname != nil {
        makefuncsym(n.Func.Nname.Sym) // ここが追加された
    }
    // ... 既存のコード ...
}
```

`funchdr`は、通常の（名前付き）関数のヘッダが処理される際に呼び出されます。`importpkg == nil`という条件は、現在のパッケージ内で定義されている関数のみを対象とすることを示します。`n.Func.Nname != nil`は、関数が名前を持っていることを確認します。この変更により、トップレベルの関数やメソッドも、その宣言時に`makefuncsym`を通じて関数値シンボルが定義されるようになります。これにより、これらの関数が共有ライブラリの一部としてエクスポートされたり、他のモジュールから参照されたりする場合でも、シンボル解決が正しく行われることが保証されます。

### `funcsym`からのロジック削除

`funcsym`関数からシンボル定義のロジックが削除されたのは、その役割が`makefuncsym`に分離されたためです。`funcsym`は純粋にシンボルを検索または作成する役割に特化し、シンボルの定義（`Def`フィールドの設定など）は`makefuncsym`が担当するようになりました。これにより、コードの関心事が分離され、より明確な構造になっています。

この一連の変更により、Goコンパイラは関数値シンボルをより早期かつ一貫した方法で定義するようになり、特に共有ライブラリを使用する際のシンボル解決の堅牢性が大幅に向上しました。

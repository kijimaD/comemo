## 元コミット内容

このコミットは、Goランタイムと`reflect`パッケージにおいて、複数の`moduledata`オブジェクトをサポートするように変更します。具体的には、これまで単一のグローバル変数`themoduledata`を参照していた箇所を、`moduledata`オブジェクトのリンクリストを参照するように変更します。これは、将来的に`-linkshared`オプションが正しく機能するために必要となる基盤的な変更です。現時点では、このリストに`moduledata`オブジェクトを追加するメカニズムはまだ存在しないため、この変更は一時的にわずかな命令のオーバーヘッドを発生させるだけであると述べられています。

## 変更の背景

この変更の主な背景は、Go言語における共有ライブラリのサポート、特に`-linkshared`ビルドオプションの実現に向けた準備です。

Go言語は伝統的に、すべての依存関係を単一のバイナリに静的にリンクする「静的リンク」をデフォルトとしています。これにより、デプロイが容易になり、依存関係の問題が少なくなります。しかし、大規模なアプリケーションや、複数のGoプログラムが共通のライブラリを共有するようなシナリオでは、静的リンクされたバイナリのサイズが大きくなるという問題がありました。

`-linkshared`オプションは、この問題を解決するために導入が検討された機能です。これにより、GoプログラムはGoの標準ライブラリなどの共通ライブラリを共有ライブラリ（例: `libstd.so`）としてリンクできるようになります。これにより、個々の実行ファイルのサイズを削減し、メモリ使用量を最適化できる可能性があります。

共有ライブラリをサポートするためには、Goランタイムが複数の「モジュール」の情報を管理できる必要があります。各モジュール（メインの実行ファイルや、動的にロードされる共有ライブラリ）は、それぞれ独自のコード、データ、型情報などを持っています。これらの情報は`moduledata`というランタイム内部の構造体に格納されます。

これまでのGoランタイムは、単一の`themoduledata`グローバル変数にすべてのモジュール情報を集約していました。しかし、`-linkshared`が導入されると、複数の独立したGoモジュールが同時にメモリにロードされることになります。それぞれのモジュールが独自の`moduledata`を持つため、ランタイムはこれらの複数の`moduledata`オブジェクトを効率的に検索し、利用できるメカニズムを必要とします。

このコミットは、そのメカニズムの第一歩として、`themoduledata`をリンクリストの先頭として扱い、ランタイムの様々な箇所でこのリンクリストを走査するように変更することで、将来的な複数モジュールサポートの基盤を構築しています。

## 前提知識の解説

### Goランタイムと`moduledata`

Goランタイムは、Goプログラムの実行を管理する非常に重要な部分です。ガベージコレクション（GC）、スケジューラ、メモリ管理、型情報、スタック管理など、Goプログラムが動作するために必要な低レベルの機能を提供します。

`runtime.moduledata`は、GoランタイムがGoモジュールに関するメタデータを格納するために使用する内部構造体です。この構造体には、以下のような情報が含まれています。

*   **PC (Program Counter) Ranges**: コードセグメントのアドレス範囲。どのPC値がどの関数に属するかを特定するために使用されます。
*   **Function Tables (`ftab`)**: 関数エントリポイントと関連するメタデータ（関数名、ファイル/行情報など）のテーブル。
*   **Type Information (`typelinks`)**: プログラム内で定義されているすべての型に関する情報へのポインタのリスト。リフレクションやGCが型情報を参照するために使用します。
*   **Data/BSS Segments**: 初期化されたデータ（`.data`）と初期化されていないデータ（`.bss`）セグメントのアドレス範囲。これらはグローバル変数や静的変数が格納される領域です。
*   **GC Masks (`gcdatamask`, `gcbssmask`)**: ガベージコレクタがデータセグメントやBSSセグメント内のポインタを識別するために使用するビットマスク。これにより、GCはヒープ上のオブジェクトだけでなく、グローバル変数からも到達可能なオブジェクトを正確に追跡できます。
*   **ABI Compatibility Hashes**: `-linkshared`を使用する際に、異なるモジュール間のABI互換性を検証するために使用されるハッシュ。

これまでのGoランタイムでは、これらの情報が単一のグローバル変数`themoduledata`に集約されていました。これは、Goプログラムが単一の実行ファイルとしてビルドされ、すべてのコードとデータがその単一のモジュール内に含まれるという前提に基づいています。

### ガベージコレクション (GC) とデータ/BSSセグメント

Goのガベージコレクタは、到達可能なオブジェクトを特定し、到達不能なオブジェクトが占めるメモリを解放することで、メモリリークを防ぎます。GCはヒープ上のオブジェクトだけでなく、スタック上の変数やグローバル変数（データ/BSSセグメントに格納される）からも到達可能なオブジェクトを追跡する必要があります。

`moduledata`内の`gcdatamask`と`gcbssmask`は、この追跡において重要な役割を果たします。これらのマスクは、データセグメントやBSSセグメント内のどのオフセットにポインタが含まれているかを示すビットマップです。GCはこれらのマスクを利用して、グローバル変数の中からヒープ上のオブジェクトへの参照を効率的に見つけ出し、それらのオブジェクトを「到達可能」としてマークします。

### 共有ライブラリと動的リンク

共有ライブラリ（例: Linuxの`.so`ファイル、Windowsの`.dll`ファイル）は、複数のプログラムで共有されるコードとデータを含むファイルです。動的リンクは、プログラムの実行時にこれらの共有ライブラリをロードし、リンクするプロセスです。これにより、以下のような利点があります。

*   **ディスク容量の節約**: 共通のライブラリがディスク上で一度だけ存在すればよいため、個々の実行ファイルのサイズが小さくなります。
*   **メモリ使用量の削減**: 複数のプロセスが同じ共有ライブラリを使用する場合、そのライブラリのコードはメモリ上で一度だけロードされ、共有されます。
*   **更新の容易さ**: ライブラリを更新しても、それに依存するすべてのプログラムを再コンパイルする必要がありません。

Go言語は歴史的に静的リンクを好んできましたが、特定のユースケース（特にプラグインシステムや、非常に大きなGoアプリケーションのデプロイ）では、動的リンクの利点が求められることがあります。`-linkshared`オプションは、GoプログラムがGoの共有ライブラリに動的にリンクするための実験的な機能として導入されました。

## 技術的詳細

このコミットの核心は、Goランタイムがモジュール情報を管理する方法を、単一のグローバル変数`themoduledata`から、`moduledata`構造体のリンクリストへと移行することです。

具体的には、`runtime/symtab.go`で定義されている`moduledata`構造体に、`next *moduledata`という新しいフィールドが追加されました。これにより、各`moduledata`オブジェクトが次の`moduledata`オブジェクトへのポインタを持つことができ、複数のモジュールがメモリ上に存在する場合でも、ランタイムがそれらすべてを走査できるようになります。

変更された主な箇所と、その技術的な意味合いは以下の通りです。

1.  **`moduledata`構造体の変更 (`src/runtime/symtab.go`)**:
    *   `next *moduledata`フィールドが追加され、`moduledata`オブジェクトがリンクリストを形成できるようになりました。
    *   `gcdatamask`, `gcbssmask`, `shadow_data`, `data_start`, `data_end`といったGCやライトバリアに関連するフィールドが、グローバル変数から`moduledata`構造体内部に移動されました。これは、各モジュールが独自のデータセグメントとBSSセグメントを持ち、それらに対するGCマスクやライトバリアのシャドウ領域もモジュールごとに管理される必要があるためです。

2.  **リンクリストの走査への移行**:
    *   これまで`themoduledata`を直接参照していた多くのランタイム関数が、`for datap := &themoduledata; datap != nil; datap = datap.next`のようなループ構造を使用して、`moduledata`のリンクリストを走査するように変更されました。
    *   **`src/reflect/type.go`**: `typelinks()`関数が、単一の`moduledata`から型情報を取得するのではなく、すべての`moduledata`オブジェクトから型情報を集約して返すように変更されました。`typesByString`関数も、この新しい`typelinks()`の戻り値の型に合わせて変更されています。
    *   **GC関連のファイル (`src/runtime/heapdump.go`, `src/runtime/mbarrier.go`, `src/runtime/mbitmap.go`, `src/runtime/mfinal.go`, `src/runtime/mgc.go`, `src/runtime/mgcmark.go`)**:
        *   GCルートのスキャン（`markroot`）や、ライトバリアのシャドウメモリの初期化（`wbshadowinit`）、ポインタのシャドウ領域の検索（`shadowptr`）、GCマスクの取得（`getgcmask`）、ファイナライザの登録（`SetFinalizer`）など、メモリ管理やGCに関連する多くの関数が、`moduledata`のリンクリストを走査して、適切なモジュールのデータやBSSセグメント、GCマスクを参照するように変更されました。これにより、GCは複数のモジュールにまたがるグローバル変数やデータ構造を正しく処理できるようになります。
        *   特に`src/runtime/mgc.go`では、`gcdatamask`と`gcbssmask`がグローバル変数から削除され、各`moduledata`のフィールドとして初期化されるようになりました。
    *   **シンボルテーブル関連のファイル (`src/runtime/symtab.go`)**:
        *   `findmoduledatap(pc uintptr)`という新しいヘルパー関数が追加されました。この関数は、与えられたプログラムカウンタ（PC）値がどの`moduledata`オブジェクトのコード範囲に属するかをリンクリストを走査して特定します。
        *   `findfunc`, `pcvalue`, `cfuncname`, `funcline1`など、PC値から関数情報やファイル/行情報を取得する関数が、この`findmoduledatap`を使用して適切な`moduledata`を参照するように変更されました。これにより、複数のモジュールにまたがる関数呼び出しやデバッグ情報の解決が可能になります。
    *   **`src/runtime/signal_windows.go`**: Windows環境でのシグナルハンドリングにおいて、Goバイナリ内の命令実行をチェックする箇所が、将来的に共有ライブラリをサポートするためにループが必要であるというコメントが追加されました。

この変更は、Goランタイムが単一の静的バイナリという前提から、複数の動的にロードされるモジュールを扱うことができる、より柔軟なアーキテクチャへと進化するための重要な一歩です。現時点では`moduledata`をリンクリストに追加するメカニズムはまだ実装されていませんが、このコミットは将来の`-linkshared`機能の基盤を固めるものです。

    ```go
    }
    ```
    これは最も重要な変更です。`moduledata`構造体に`next`というポインタが追加されたことで、複数の`moduledata`オブジェクトをリンクリストとして連結できるようになりました。これにより、Goランタイムは単一の`themoduledata`だけでなく、ロードされているすべてのモジュールのメタデータにアクセスできるようになります。

2.  **`findmoduledatap`関数の追加**:
    ```go
    func findmoduledatap(pc uintptr) *moduledata {
        for datap := &themoduledata; datap != nil; datap = datap.next {
            if datap.minpc <= pc && pc <= datap.maxpc {
                return datap
            }
        }
        return nil
    }
    ```
    この新しいヘルパー関数は、与えられたプログラムカウンタ（`pc`）がどの`moduledata`オブジェクトのコード範囲（`minpc`から`maxpc`まで）に属するかを効率的に検索します。`themoduledata`から始まり、リンクリストを`next`ポインタをたどって走査します。これにより、`findfunc`などの関数が、どのモジュールに属する関数であるかを特定できるようになります。

3.  **`moduledata`内のGCマスクとライトバリア関連フィールドの移動**:
    ```go
    type moduledata struct {
        // ...
        gcdatamask, gcbssmask bitvector
        shadow_data uintptr
        data_start  uintptr
        data_end    uintptr
        // ...
    }
    ```
    以前はグローバル変数として存在していた`gcdatamask`、`gcbssmask`、`shadow_data`、`data_start`、`data_end`といったフィールドが、`moduledata`構造体内部に移動されました。これは、各モジュールが独自のデータセグメントとBSSセグメントを持ち、それらに対するGCマスクやライトバリアのシャドウ領域もモジュールごとに管理される必要があるためです。これにより、GCやライトバリアの処理がモジュールごとに独立して行えるようになります。

4.  **`findfunc`などの関数における`moduledata`リンクリストの利用**:
    `findfunc`、`pcvalue`、`cfuncname`、`funcline1`といった、PC値から関数情報やファイル/行情報を取得するランタイム関数が、直接`themoduledata`を参照する代わりに、新しく追加された`findmoduledatap(pc)`関数を呼び出して、適切な`moduledata`オブジェクトを取得するように変更されました。これにより、複数のモジュールにまたがる関数呼び出しやデバッグ情報の解決が可能になります。

### `src/runtime/mbarrier.go` の変更点

1.  **`wbshadowinit`関数におけるリンクリストの走査**:
    ```diff
    -	start := ^uintptr(0)
    -	end := uintptr(0)
    -	// ... themoduledata を直接参照していた箇所 ...
    -	mheap_.data_start = start
    -	mheap_.data_end = end
    -	// ...
    +	for datap := &themoduledata; datap != nil; datap = datap.next {
    +		start := ^uintptr(0)
    +		end := uintptr(0)
    +		// ... datap を参照するように変更 ...
    +		datap.data_start = start
    +		datap.data_end = end
    +		datap.shadow_data = uintptr(p1) - start
    +		// ...
    +	}
    ```
    `wbshadowinit`関数は、ライトバリアのシャドウメモリを初期化する役割を担っています。この変更により、単一の`themoduledata`のデータセグメントに対してシャドウメモリを確保するのではなく、`moduledata`リンクリスト内の**すべての**`moduledata`オブジェクトに対して、それぞれのデータセグメントに対応するシャドウメモリを確保するように変更されました。これにより、複数のモジュールが存在する場合でも、それぞれのモジュールのデータ領域に対するライトバリアが正しく機能するようになります。

2.  **`shadowptr`関数におけるリンクリストの走査**:
    ```diff
    -	var shadow *uintptr
    -	if mheap_.data_start <= addr && addr < mheap_.data_end {
    -		shadow = (*uintptr)(unsafe.Pointer(addr + mheap_.shadow_data))
    -	} else if inheap(addr) {
    -		shadow = (*uintptr)(unsafe.Pointer(addr + mheap_.shadow_heap))
    -	}
    -	return shadow
    +	for datap := &themoduledata; datap != nil; datap = datap.next {
    +		if datap.data_start <= addr && addr < datap.data_end {
    +			return (*uintptr)(unsafe.Pointer(addr + datap.shadow_data))
    +		}
    +	}
    +	if inheap(addr) {
    +		return (*uintptr)(unsafe.Pointer(addr + mheap_.shadow_heap))
    +	}
    +	return nil
    ```
    `shadowptr`関数は、与えられたアドレスに対応するライトバリアのシャドウポインタを返します。この変更により、単一の`mheap_.data_start`と`mheap_.data_end`の範囲をチェックするのではなく、`moduledata`リンクリストを走査し、アドレスがどの`moduledata`のデータセグメントに属するかを判断するように変更されました。これにより、複数のモジュールにまたがるデータ領域に対するライトバリアの参照が正しく解決されるようになります。

これらの変更は、Goランタイムが単一のモジュールだけでなく、複数のモジュール（特に`-linkshared`によってロードされる共有ライブラリ）の存在を認識し、それらのメモリレイアウト、型情報、GC関連のメタデータを適切に管理するための基盤を構築しています。

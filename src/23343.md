## 変更の背景

このコミットは、Goの`fmt`パッケージが特定の書式設定、特に大きな精度（precision）指定を伴う整数値のフォーマット処理においてパニック（panic）を引き起こす問題を修正するために行われました。具体的には、Issue #10745で報告された問題に対応しています。

以前のコードでは、出力の幅（width）が大きい場合には適切に処理できていましたが、精度（precision）が大きい場合には考慮されていませんでした。これにより、フォーマット処理中に内部バッファのサイズが不足し、結果としてパニックが発生していました。また、`%U`（Unicodeフォーマット）のより複雑なケースも適切に処理されていなかったため、このコミットで同時に修正されています。

## 前提知識の解説

### Goの`fmt`パッケージ

`fmt`パッケージは、Go言語におけるフォーマット済みI/Oを実装するための標準ライブラリです。C言語の`printf`や`scanf`に似た機能を提供し、様々なデータ型を文字列として整形したり、文字列からデータを読み取ったりすることができます。

### 書式指定子（Verb）

`fmt`パッケージでは、値をどのようにフォーマットするかを制御するために書式指定子（verb）を使用します。
- **`%x`**: 整数値を16進数（小文字）でフォーマットします。`%X`は16進数（大文字）です。
- **`%U`**: Unicodeコードポイントを`U+XXXX`形式でフォーマットします。`XXXX`はコードポイントの16進数表現です。

### 幅（Width）と精度（Precision）

書式指定子には、幅と精度を指定することができます。
- **幅（Width）**: 出力される文字列の最小の文字数を指定します。指定された幅よりも短い場合、通常はスペースでパディングされます。
- **精度（Precision）**: フォーマットされる値の種類によって意味が異なります。
    - 浮動小数点数: 小数点以下の桁数。
    - 文字列: 出力される最大文字数。
    - 整数（`%x`など）: 出力される最小桁数。指定された桁数よりも短い場合、通常はゼロでパディングされます。

### `fmt`パッケージの内部構造

`fmt`パッケージの内部では、`fmt`構造体がフォーマットの状態を管理しています。この構造体には、以下のようなフィールドが含まれます。
- `f.widPresent`: 幅が指定されたかどうかを示すブール値。
- `f.wid`: 指定された幅の値。
- `f.precPresent`: 精度が指定されたかどうかを示すブール値。
- `f.prec`: 指定された精度の値。
- `f.unicode`: `%U`書式指定子が使用されているかどうかを示すブール値。
- `f.sharp`: `#`フラグが指定されたかどうかを示すブール値（例: `%#x`は`0x`プレフィックスを追加）。
- `f.uniQuote`: `%U`書式指定子で引用符付き文字（例: `'日'`）を追加するかどうかを示すブール値。

これらのフラグや値に基づいて、`fmt`パッケージは出力に必要なバッファサイズを計算し、値をフォーマットします。

## 技術的詳細

このコミットの核心は、`src/fmt/format.go`内の`(*fmt).integer`メソッドにおけるバッファサイズの計算ロジックの改善です。`integer`メソッドは、整数値を様々な基数（10進数、16進数など）でフォーマットする役割を担っています。

以前の実装では、出力の幅（`f.wid`）はバッファサイズの見積もりに考慮されていましたが、精度（`f.prec`）は適切に考慮されていませんでした。特に、`%x`や`%U`のような書式指定子で非常に大きな精度が指定された場合、必要な出力文字列長が内部的に確保されたバッファサイズを超過し、結果としてランタイムパニック（`index out of range`など）を引き起こす可能性がありました。

この修正では、`f.widPresent`（幅が指定されているか）だけでなく、`f.precPresent`（精度が指定されているか）も考慮して、必要なバッファサイズを計算するように変更されました。

具体的には、`width`変数の計算において、`f.wid`と`f.prec`の両方を加算することで、より大きなバッファサイズを確保するようにしています。コメントにある「Only one will be set, both are positive; this provides the maximum.」という記述は、`wid`と`prec`のどちらか一方が有効な場合に、その最大値を`width`として利用するという意図を示しています。これにより、幅と精度の両方に対応できる十分なバッファが確保されます。

さらに、`%U`書式指定子の場合には、`U+`プレフィックス（2文字）や、`f.uniQuote`が設定されている場合の引用符付き文字（例: `'日'`）の追加スペースもバッファサイズに加算されるようになりました。これにより、`%U`の複雑なケースでもバッファオーバーフローを防ぎます。

`fmt_test.go`に追加されたテストケースは、このパニックが発生していた具体的なシナリオを再現しています。
- `{"%#.80x", 42, ...}`: 非常に大きな精度（80）を指定した16進数フォーマット。
- `{"%.80U", 42, ...}`: 非常に大きな精度（80）を指定したUnicodeフォーマット。
- `{"%#.80U", '日', ...}`: 非常に大きな精度（80）と`#`フラグを指定したUnicodeフォーマット（引用符付き文字を含む）。

これらのテストケースは、修正後のコードがこれらのエッジケースを正しく処理し、パニックを起こさないことを保証します。

## コアとなるコードの解説

`src/fmt/format.go`の`(*fmt).integer`メソッド内の変更がこのコミットの主要な修正点です。

1.  **条件式の変更**:
    ```go
    -	if f.widPresent {
    +	if f.widPresent || f.precPresent {
    ```
    以前は`f.widPresent`（幅が指定されているか）のみをチェックしていましたが、この変更により`f.precPresent`（精度が指定されているか）もチェックするようになりました。これにより、精度が指定されている場合でも、出力に必要なバッファサイズの見積もりロジックが実行されるようになります。

2.  **`width`の計算ロジックの変更**:
    ```go
    -		width := f.wid
    +		width := f.wid + f.prec // Only one will be set, both are positive; this provides the maximum.
    ```
    `width`変数の初期値が`f.wid`から`f.wid + f.prec`に変更されました。コメントにあるように、`f.wid`と`f.prec`のどちらか一方が設定されている場合でも、両方を加算することで、必要な最大バッファサイズを確保しようとしています。これにより、幅または精度のいずれか、あるいは両方が大きい場合に、より大きなバッファが確保されるようになります。

3.  **`%U`書式指定子に対する追加のバッファ計算**:
    ```go
    +		if f.unicode {
    +			// Also adds "U+".
    +			width += 2
    +			if f.uniQuote {
    +				// Also adds " 'x'".
    +				width += 1 + 1 + utf8.UTFMax + 1
    +			}
    +		}
    ```
    `f.unicode`が`true`（つまり`%U`書式指定子が使用されている）の場合、出力文字列には`U+`というプレフィックスが追加されるため、`width`に2が加算されます。
    さらに、`f.uniQuote`が`true`の場合（例: `%#U`で文字自体も表示される場合）、` 'x'`のような形式で文字が追加されるため、その分のスペース（スペース1文字、シングルクォート2文字、UTF-8文字の最大バイト数`utf8.UTFMax`）も`width`に加算されます。これにより、`%U`書式指定子の全てのバリエーションにおいて、正確なバッファサイズが計算されるようになりました。

これらの変更により、`fmt`パッケージは、大きな幅や精度、そして`%U`書式指定子の複雑なケースにおいても、パニックを起こすことなく正しく整数値をフォーマットできるようになりました。

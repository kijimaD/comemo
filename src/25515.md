# [インデックス 25515] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における、`mallocgc`関数内の特定のワークアラウンドコードを削除するものです。このワークアラウンドは、GCコーディネーターのスケジューリングに関連する問題を緩和するために導入されましたが、GCの設計変更により不要となりました。具体的には、Go 1.5のGCコーディネーターが廃止され、`mallocgc`が常にGCの遷移を支援できるようになったため、GCの起動・シャットダウン時の特別な処理が不要になったことを反映しています。

## 変更の背景

このコミットの背景には、Go 1.5で導入された新しいガベージコレクター（GC）の設計と、その後の改善があります。Go 1.5のGCは、従来のストップ・ザ・ワールド（STW）方式から、並行（concurrent）かつ低遅延（low-latency）なGCへと大きく進化しました。しかし、初期のGo 1.5のGCには「GCコーディネーター」と呼ばれる単一のゴルーチンがGCのフェーズ遷移を管理する設計上の課題がありました。

GCコーディネーターは、GCの各フェーズ（マーク、スイープなど）の開始と終了を調整する役割を担っていました。しかし、この集中型のコーディネーターはGoスケジューラーに依存しており、スケジューリングの遅延によってGCのフェーズ遷移が遅れる可能性がありました。これにより、GCサイクルが長引いたり、メモリ割り当てがブロックされたり、一時的に長いポーズが発生したりする問題が報告されていました（例: issue #11677, #11911）。

特に問題だったのは、GCコーディネーターがアクティブになるのを待っている間に、ミューテーター（アプリケーションコード）がメモリを無制限に割り当ててしまう期間や、GCが停止してしまう期間が生じることでした。この問題を緩和するため、`mallocgc`関数内には、GCが支援できない状態でありながらも無制限にメモリを割り当てられない状況で、GCコーディネーターのスケジューリングを助けるために現在のゴルーチンを一時停止（yield）させるワークアラウンドが導入されていました。

このコミットは、issue #11970で議論され、Go 1.6の開発サイクルで実装された「分散型GC調整（Decentralized GC coordination）」の成果を反映したものです。分散型GC調整では、GCコーディネーターという単一のゴルーチンを廃止し、GCの各状態遷移を任意のゴルーチンが実行できるように変更されました。これにより、GCのフェーズ遷移がより迅速かつ予測可能になり、GCコーディネーターのスケジューリングを助けるためのワークアラウンドが不要になったため、このコミットで削除されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する知識が必要です。

1.  **ガベージコレクション (GC)**:
    GoのGCは、プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったものを自動的に解放する仕組みです。Go 1.5以降は、並行マーク＆スイープGCを採用しており、アプリケーションの実行と並行してGC処理を進めることで、STW（Stop The World）ポーズを最小限に抑えています。

2.  **`mallocgc`**:
    Goプログラムがメモリを割り当てる際に呼び出されるランタイム関数です。例えば、`make`や`new`キーワード、スライスやマップの拡張などでメモリが必要になったときに内部的に使用されます。`mallocgc`は単にメモリを割り当てるだけでなく、GCの進行状況を監視し、必要に応じてGCを支援する役割も持っています。

3.  **GCのフェーズと状態**:
    GoのGCは複数のフェーズに分かれています。
    *   **マークフェーズ**: ライブオブジェクト（到達可能なオブジェクト）を識別します。
    *   **スイープフェーズ**: マークされなかった（デッドな）オブジェクトが占めていたメモリを解放します。
    *   **ブラックニング (Blacken)**: マークフェーズ中に、新しいオブジェクトが割り当てられたり、既存のオブジェクトの参照が変更されたりした場合に、GCの正確性を保つために行われる処理です。オブジェクトは「白」（未訪問）、「灰」（訪問済みだが子を未訪問）、「黒」（訪問済みで子も訪問済み）のいずれかの色で表現されます。`gcBlackenEnabled`は、ブラックニングが有効な状態かどうかを示すフラグです。

4.  **GCコーディネーター (Go 1.5以前の概念)**:
    Go 1.5の初期のGC実装では、GCの各フェーズの開始と終了を調整する「GCコーディネーター」と呼ばれる特別なゴルーチンが存在しました。このコーディネーターがGCの状態遷移を管理していましたが、そのスケジューリングが遅れるとGC全体のパフォーマンスに影響を与える可能性がありました。

5.  **`Gosched()`**:
    Goランタイム関数の一つで、現在のゴルーチンを一時停止し、他の実行可能なゴルーチンにCPUを譲渡します。これにより、スケジューラーが別のゴルーチンを実行できるようになります。GCのワークアラウンドでは、GCコーディネーターが実行される機会を増やすために使用されていました。

6.  **`getg()`**:
    現在のゴルーチン（`g`構造体）へのポインタを返します。Goランタイム内部で、現在の実行コンテキストに関する情報を取得するために使用されます。

7.  **`gp.m.g0`**:
    `g0`は、システムコールやGCなどのランタイム処理を実行するための特別なゴルーチンです。通常のアプリケーションゴルーチンとは異なり、スタックサイズが固定されており、プリエンプション（横取り）されにくい特性を持ちます。

8.  **`gp.m.locks`**:
    現在のM（マシン、OSスレッド）が保持しているロックの数を表します。ロックを保持している間は、ゴルーチンはプリエンプションされにくい、あるいはプリエンプションされてはならない場合があります。

9.  **`gp.m.preemptoff`**:
    プリエンプションを無効にする理由を示す文字列です。このフィールドが空文字列（`""`）の場合、プリエンプションは許可されています。ランタイムのクリティカルセクションでは、プリエンプションを一時的に無効にすることがあります。

## 技術的詳細

削除されたコードブロックは、`src/runtime/malloc.go`内の`mallocgc`関数に存在していました。このコードは、GCが特定の状態にあるときに、メモリ割り当てを行うゴルーチンがGCを支援できないが、無制限にメモリを割り当てることもできない場合に、GCコーディネーターのスケジューリングを助けるために自身を一時停止させるロジックでした。

具体的には、以下の条件が満たされた場合に`Gosched()`を呼び出してゴルーチンを一時停止していました。

```go
else if shouldhelpgc && bggc.working != 0 && gcBlackenEnabled == 0 {
    // The GC shutting down, so we can't
    // assist, but we also can't allocate unabated. Slow
    // down this G's allocation and help the GC stay
    // scheduled by yielding.
    //
    // TODO: This is unused. Remove.
    gp := getg()
    if gp != gp.m.g0 && gp.m.locks == 0 && gp.m.preemptoff == "" {
        Gosched()
    }
}
```

各条件の意味は以下の通りです。

*   **`shouldhelpgc`**: 現在のゴルーチンがGCを支援すべきかどうかを示すフラグです。これが`true`の場合、GCが進行中であり、現在のゴルーチンがGC作業に貢献できる可能性があります。
*   **`bggc.working != 0`**: バックグラウンドGCがアクティブに動作していることを示します。
*   **`gcBlackenEnabled == 0`**: ブラックニングフェーズが有効でないことを示します。これは、GCがシャットダウン中であるか、またはブラックニングが完了している状態を示唆します。
*   **`gp := getg()`**: 現在のゴルーチン（`g`）を取得します。
*   **`gp != gp.m.g0`**: 現在のゴルーチンが特別なランタイムゴルーチン（`g0`）ではないことを確認します。`g0`はランタイムの内部処理に専念するため、通常は`Gosched()`で一時停止させるべきではありません。
*   **`gp.m.locks == 0`**: 現在のOSスレッド（`m`）がロックを保持していないことを確認します。ロックを保持しているゴルーチンを一時停止させると、デッドロックや他の問題を引き起こす可能性があります。
*   **`gp.m.preemptoff == ""`**: 現在のゴルーチンがプリエンプションを無効にしていないことを確認します。プリエンプションが無効な状態で`Gosched()`を呼び出すのは不適切です。

これらの条件がすべて満たされた場合、つまり「GCがシャットダウン中で、現在のゴルーチンはGCを支援できないが、無制限にメモリを割り当てることも許されない状況であり、かつ現在のゴルーチンが安全に一時停止できる状態である」場合に、`Gosched()`を呼び出してCPUを他のゴルーチンに譲渡していました。これは、GCコーディネーターが実行される機会を増やし、GCのシャットダウンプロセスを円滑に進めるためのヒューリスティックな試みでした。

しかし、Go 1.6でGCコーディネーターが廃止され、GCのフェーズ遷移が分散型で管理されるようになったため、このワークアラウンドは不要になりました。`mallocgc`は常にGCの遷移を適切に支援できるようになり、GCコーディネーターのスケジューリングを気にする必要がなくなったため、この複雑な条件分岐と`Gosched()`の呼び出しは削除されました。コミットメッセージにある`TODO: This is unused. Remove.`というコメントも、このコードがすでに不要であることを示唆していました。

## コアとなるコードの解説

削除されたコードブロックは、`mallocgc`関数内の条件分岐の一部でした。

元のコードは以下の構造を持っていました。

```go
if shouldhelpgc && gcShouldStart(false) {
    gcStart(gcBackgroundMode, false)
} else if shouldhelpgc && bggc.working != 0 && gcBlackenEnabled == 0 {
    // GCシャットダウン中のワークアラウンド
    // ...
    gp := getg()
    if gp != gp.m.g0 && gp.m.locks == 0 && gp.m.preemptoff == "" {
        Gosched()
    }
}
```

最初の`if`ブロックは、GCを支援すべきであり、かつGCを開始すべき状況であれば、バックグラウンドGCを開始するというロジックです。これはGCの通常の動作の一部であり、このコミットでは変更されていません。

削除された`else if`ブロックが、GCコーディネーターに関連するワークアラウンドでした。
このブロックは、以下の3つの主要な条件がすべて真である場合に実行されました。

1.  `shouldhelpgc`: 現在のゴルーチンがGCを支援するべき状態である。
2.  `bggc.working != 0`: バックグラウンドGCが動作中である。
3.  `gcBlackenEnabled == 0`: ブラックニングフェーズが有効でない。これはGCがシャットダウン中であるか、ブラックニングが完了している状態を示唆します。

これらの条件が満たされると、コメントにあるように「GCがシャットダウン中であり、現在のゴルーチンはGCを支援できないが、無制限にメモリを割り当てることもできない」という状況と判断されました。この状況下で、現在のゴルーチンはGCコーディネーターが実行される機会を増やすために、`Gosched()`を呼び出してCPUを譲渡していました。

さらに、`Gosched()`を呼び出す前に、現在のゴルーチンが安全に一時停止できるかどうかのチェックが行われていました。

*   `gp != gp.m.g0`: 現在のゴルーチンがランタイムの内部ゴルーチン`g0`ではないことを確認。`g0`はプリエンプションされるべきではないため。
*   `gp.m.locks == 0`: 現在のOSスレッドがロックを保持していないことを確認。ロックを保持しているゴルーチンを一時停止するとデッドロックのリスクがあるため。
*   `gp.m.preemptoff == ""`: 現在のゴルーチンがプリエンプションを無効にしていないことを確認。

これらのチェックを通過した場合にのみ`Gosched()`が呼び出され、現在のゴルーチンは一時停止し、他のゴルーチン（特にGCコーディネーター）に実行機会を与えていました。

このコードは、Go 1.5のGCコーディネーターの設計上の制約を回避するための暫定的な措置であり、Go 1.6でGCの調整メカニズムが分散型に変更されたことで、その存在意義を失いました。そのため、このコミットで完全に削除されました。これにより、`mallocgc`のコードは簡素化され、GCの内部動作がより効率的かつ予測可能になりました。

# [インデックス 25354] ファイルの概要

このコミットは、Goランタイムの `m` (Machine) 構造体のメモリフットプリントを削減することを目的としています。具体的には、Plan 9やSolarisといった特定のOSにのみ必要なフィールドを、`mOS`という新しい埋め込み構造体に分離することで、`m`構造体のサイズを最適化しています。これにより、Linux/amd64環境では`m`構造体のサイズが約8%削減（1040バイトから960バイトへ）されました。

## 変更の背景

Goランタイムの `m` 構造体は、OSスレッド（Machine）を表す重要なデータ構造であり、Goプログラムの実行において多数のインスタンスが生成される可能性があります。以前の`m`構造体には、Plan 9やSolarisといった特定のOSにのみ必要なフィールドが直接含まれていました。この設計は、それらのOSを使用しない環境（例えば、広く利用されているLinux/amd64など）においても、不要なフィールドが`m`構造体のメモリフットプリントを不必要に増加させているという問題がありました。

メモリ使用量の最適化は、特に大規模な並行処理を行うGoアプリケーションや、リソースが限られた環境での実行において非常に重要です。`m`構造体のサイズを削減することで、Goプログラム全体のメモリ効率が向上し、パフォーマンスの改善にも寄与します。このコミットは、`m`構造体からOS固有のフィールドを分離し、必要なOSでのみそれらのフィールドがメモリを占有するようにすることで、この問題を解決しようとしています。コミットメッセージにあるように、Linux/amd64環境で`m`構造体のサイズが約8%削減されたことは、この最適化の具体的な成果を示しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念とGo言語の機能に関する知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステムです。これには、Goroutineスケジューラ、メモリ管理（ガベージコレクションを含む）、OSとのインターフェースなどが含まれます。Goプログラムは、OSによって直接実行されるのではなく、Goランタイム上で動作します。
*   **Goroutine (G)**: Go言語における軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万のGoroutineを同時に実行することも可能です。GoroutineはGoランタイムのスケジューラによって管理されます。
*   **Logical Processor (P)**: Goroutineを実行するためのコンテキストを提供します。Pは、実行可能なGoroutineのキューを保持し、M（OSスレッド）にGoroutineを割り当てます。
*   **Machine (M)**: OSスレッドに相当します。Goランタイムは、OSスレッドを抽象化したMを管理し、PとGをM上で実行します。MはOSスレッドと1対1で対応し、OSスレッドのスタック、レジスタ情報、現在のGoroutineへのポインタ、そしてOS固有のデータなどを保持します。`m`構造体は、このMの情報を格納するGoランタイム内の重要なデータ構造です。
*   **構造体のサイズとメモリフットプリント**: プログラム内で定義される構造体は、そのフィールドの型と数に応じてメモリを占有します。構造体のインスタンスが多数作成される場合、個々の構造体のサイズが小さいほど、プログラム全体のメモリ使用量を削減できます。Goランタイムの`m`構造体は、Goプログラムの実行中に多数生成される可能性があるため、そのサイズはメモリ効率に直接影響します。
*   **埋め込み構造体 (Embedded Structs)**: Go言語の機能の一つで、ある構造体の中に別の構造体をフィールド名なしで宣言することです。これにより、埋め込まれた構造体のフィールドやメソッドが、外側の構造体のフィールドやメソッドであるかのように直接アクセスできるようになります。このコミットでは、`m`構造体に`mOS`構造体を埋め込むことで、OS固有のフィールドへのアクセス方法を維持しつつ、`m`構造体の定義を簡潔に保っています。
*   **条件付きコンパイル (Build Tags)**: Goでは、ソースファイルの先頭に `// +build <tag>` のようなコメントを記述することで、特定のビルド環境（OS、アーキテクチャなど）でのみそのファイルをコンパイルするように指定できます。これにより、OSやアーキテクチャに依存するコードを分離し、クロスプラットフォーム対応を容易にします。このコミットでは、各OS固有のファイル（`os_darwin.go`, `os_plan9.go` など）で`mOS`構造体を定義することで、このメカニズムを活用しています。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイムの `m` 構造体からOS固有のフィールドを抽出し、`mOS`という新しい埋め込み構造体にカプセル化することです。

1.  **`m` 構造体の再定義**:
    `src/runtime/runtime2.go` に定義されている `m` 構造体から、Plan 9およびSolarisに特有のフィールド（`notesig`, `errstr`, `perrno`, `ts`, `scratch` など）が削除されました。代わりに、`mOS`という新しい型が埋め込みフィールドとして追加されました。
    ```go
    type m struct {
        // ... 既存の共通フィールド ...
        mOS // OS固有のフィールドをカプセル化する埋め込み構造体
    }
    ```
    この変更により、`m`構造体自体の定義はOSに依存しない共通部分のみとなり、コードの可読性と保守性が向上します。

2.  **OSごとの `mOS` 構造体の定義**:
    各OSに対応する `src/runtime/os_<osname>.go` ファイルで、`mOS`構造体が定義されます。
    *   **汎用OS (Darwin, Dragonfly, FreeBSD, Linux, NaCl, NetBSD, OpenBSD, Windows)**: これらのOSでは、`m`構造体にOS固有の追加フィールドが不要であるため、`mOS`は空の構造体として定義されます。
        ```go
        type mOS struct{}
        ```
        これにより、これらのOSでコンパイルされる際には、`mOS`はメモリをほとんど消費せず、`m`構造体のサイズは最小限に保たれます。
    *   **Plan 9**: `src/runtime/os_plan9.go` では、Plan 9固有のフィールドを持つ`mOS`が定義されます。
        ```go
        type mOS struct {
            notesig *int8
            errstr  *byte
        }
        ```
    *   **Solaris**: `src/runtime/os_solaris.go` では、Solaris固有のフィールドを持つ`mOS`が定義されます。また、`mts`と`mscratch`というSolaris固有の補助構造体もこのファイルに移動されました。
        ```go
        type mts struct {
            tv_sec  int64
            tv_nsec int64
        }

        type mscratch struct {
            v [6]uintptr
        }

        type mOS struct {
            perrno *int32 // pointer to tls errno
            // these are here because they are too large to be on the stack
            // of low-level NOSPLIT functions.
            //LibCall       libcall;
            ts      mts
            scratch mscratch
        }
        ```
    このように、ビルドタグによって各OSに適切な`mOS`の定義が選択されるため、`m`構造体は実行環境に応じて最適なサイズになります。

3.  **アセンブリコードの変更**:
    `m`構造体のレイアウトが変更されたため、Plan 9およびSolarisのアセンブリコード（`src/runtime/sys_plan9_386.s`, `src/runtime/sys_plan9_amd64.s`, `src/runtime/sys_solaris_amd64.s`）も更新されました。これらのファイルでは、`m`構造体内のOS固有のフィールドに直接アクセスしていた箇所が、`mOS`構造体を介してアクセスするように修正されています。
    例えば、Plan 9のアセンブリコードでは `m_errstr(BX)` のような直接アクセスが `(m_mOS+mOS_errstr)(BX)` のように変更され、`mOS`フィールド内の`errstr`へのオフセットが計算されるようになりました。これは、埋め込み構造体のフィールドへのアクセス方法をアセンブリレベルで反映したものです。

この変更により、Goランタイムはよりモジュール化され、OS固有のコードが適切に分離されることで、異なるプラットフォーム間でのコードの再利用性が向上し、また不要なメモリ消費が抑制されます。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/runtime/runtime2.go`**:
    *   `m` 構造体から、Plan 9およびSolaris固有のフィールド（`notesig`, `errstr`, `perrno`, `ts`, `scratch`）が削除されました。
    *   代わりに、`mOS` という型が `m` 構造体内に埋め込みフィールドとして追加されました。
    *   `mts` および `mscratch` 構造体の定義がこのファイルから削除されました。

*   **`src/runtime/os_plan9.go`**:
    *   Plan 9固有のフィールド (`notesig`, `errstr`) を持つ `mOS` 構造体が定義されました。

*   **`src/runtime/os_solaris.go`**:
    *   Solaris固有のフィールド (`perrno`, `ts`, `scratch`) を持つ `mOS` 構造体が定義されました。
    *   `mts` および `mscratch` 構造体がこのファイルに移動され、定義されました。

*   **`src/runtime/os_darwin.go`, `src/runtime/os_dragonfly.go`, `src/runtime/os_freebsd.go`, `src/runtime/os_linux.go`, `src/runtime/os_nacl.go`, `src/runtime/os_netbsd.go`, `src/runtime/os_openbsd.go`, `src/runtime/os_windows.go`**:
    *   これらの各OS固有のファイルに、空の `mOS` 構造体 (`type mOS struct{}`) が追加されました。

*   **`src/runtime/sys_plan9_386.s`, `src/runtime/sys_plan9_amd64.s`**:
    *   Plan 9のアセンブリコードにおいて、`m` 構造体の `errstr` フィールドへのアクセスが、`m_errstr(BX)` から `(m_mOS+mOS_errstr)(BX)` へと変更されました。これは、`mOS` 埋め込み構造体を介したアクセスパスを反映しています。

*   **`src/runtime/sys_solaris_amd64.s`**:
    *   Solarisのアセンブリコードにおいて、`m` 構造体の `perrno` および `scratch` フィールドへのアクセスが、それぞれ `m_perrno(BX)` から `(m_mOS+mOS_perrno)(BX)` へ、`m_scratch(BP)` から `(m_mOS+mOS_scratch)(BP)` へと変更されました。これも同様に、`mOS` 埋め込み構造体を介したアクセスパスを反映しています。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/runtime2.go` における `m` 構造体の定義変更と、各OS固有のファイルにおける `mOS` 構造体の定義です。

`src/runtime/runtime2.go` の `m` 構造体は、以下のように変更されました。

```go
// 変更前 (簡略化)
type m struct {
    g0      *g
    // ... 共通フィールド ...
    // #ifdef GOOS_solaris
    perrno *int32
    ts      mts
    scratch mscratch
    // #endif
    // #ifdef GOOS_plan9
    notesig *int8
    errstr  *byte
    // #endif
    // ... その他のフィールド ...
}

// 変更後 (簡略化)
type m struct {
    g0      *g
    // ... 共通フィールド ...
    mOS // OS固有のフィールドをカプセル化する埋め込み構造体
    // ... その他のフィールド ...
}
```

この変更により、`m` 構造体自体はOSに依存しない共通のフィールドのみを保持し、OS固有のデータは `mOS` という埋め込み構造体を通じてアクセスされるようになります。

各OSの `os_<osname>.go` ファイルでは、ビルドタグ（例: `// +build plan9`）によって、そのOSに特化した `mOS` の定義がコンパイル時に選択されます。

*   **LinuxなどのOSの場合 (`src/runtime/os_linux.go` など)**:
    ```go
    type mOS struct{}
    ```
    `mOS` が空の構造体であるため、`m` 構造体はOS固有のフィールドによるメモリオーバーヘッドを持ちません。

*   **Plan 9の場合 (`src/runtime/os_plan9.go`)**:
    ```go
    type mOS struct {
        notesig *int8
        errstr  *byte
    }
    ```
    `mOS` はPlan 9に必要な `notesig` と `errstr` フィールドを持ちます。

*   **Solarisの場合 (`src/runtime/os_solaris.go`)**:
    ```go
    type mOS struct {
        perrno *int32
        ts      mts
        scratch mscratch
    }
    ```
    `mOS` はSolarisに必要な `perrno`, `ts`, `scratch` フィールドを持ちます。

この設計パターンにより、Goコンパイラは各ターゲットOS向けに `m` 構造体をコンパイルする際に、そのOSで実際に必要な `mOS` の定義を組み込みます。結果として、例えばLinux環境ではPlan 9やSolarisのフィールドが `m` 構造体に含まれなくなり、メモリ使用量が削減されます。

アセンブリコードの変更は、この構造体レイアウトの変更に追従するものです。`m` 構造体内のフィールドへのオフセットが変更されたため、アセンブリコードも新しいオフセットを反映するように修正されました。例えば、`m` のベースアドレスから `errstr` へのオフセットを直接計算する代わりに、`m` のベースアドレスから `mOS` へのオフセットを計算し、さらに `mOS` のベースアドレスから `errstr` へのオフセットを計算する形になります。これは、`m_mOS+mOS_errstr` という表記で示されています。

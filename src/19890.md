## 元コミット内容

このコミットは、Go言語の`net`パッケージにおいて、DNSトランスポート層（UDP/TCPによるデータの送受信）とDNSメッセージのクエリ・レスポンス処理を分離することを目的としています。これは、特定の課題（issue 6579）を修正する前段階として行われ、Goの組み込みDNSリゾルバに、より高度な制御ロジックを追加しやすくするための変更です。

## 変更の背景

Go言語の`net`パッケージは、ネットワーク通信の基本的な機能を提供しており、その中にはDNS（Domain Name System）の名前解決機能も含まれています。DNSの名前解決は、ドメイン名をIPアドレスに変換するために不可欠なプロセスです。

このコミットが行われた背景には、GoのDNSリゾルバの柔軟性と拡張性を向上させる必要がありました。従来の`exchange`関数は、DNSメッセージの構築、ネットワーク接続の確立、データの送受信、レスポンスの解析といった複数の役割を担っていました。この密結合な設計は、例えば、DNSリゾルバの動作を細かく制御する（例: 特定のDNSサーバーへのフォールバックロジック、キャッシュの導入、DNSSEC検証など）ような、より複雑な機能を追加する際に障壁となっていました。

コミットメッセージに記載されている「issue 6579」は、具体的な内容が不明ですが、おそらくDNSリゾルバの挙動に関する問題や機能改善要求であったと推測されます。このコミットは、その問題解決のための前提条件として、コードのモジュール化と責務の分離を進めることを目的としています。これにより、将来的に「組み込みのDNSリゾルバ制御ロジック」を容易に追加できるよう、基盤を整備しています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

*   **DNS (Domain Name System)**: インターネット上のドメイン名とIPアドレスを対応させる分散型データベースシステム。クライアントはDNSサーバーにクエリを送信し、ドメイン名に対応するIPアドレスなどの情報を取得します。
*   **DNSメッセージ構造**: DNSのクエリとレスポンスは、特定のフォーマットに従ったメッセージとして送受信されます。これには、ヘッダー、質問セクション、回答セクション、権威セクション、追加情報セクションなどが含まれます。
*   **UDPとTCPによるDNS通信**:
    *   **UDP (User Datagram Protocol)**: 通常のDNSクエリにはUDPが使用されます。これはコネクションレスで高速ですが、メッセージサイズに制限（通常512バイト）があり、信頼性が保証されません。
    *   **TCP (Transmission Control Protocol)**: ゾーン転送や、UDPで応答しきれない大きなDNSレスポンス（例: DNSSEC署名付きの応答や、多数のレコードを含む応答）の場合にTCPが使用されます。TCPはコネクション指向で信頼性がありますが、UDPよりもオーバーヘッドが大きいです。
*   **Go言語の`net`パッケージ**: ネットワークI/O機能を提供するGoの標準ライブラリ。`Conn`インターフェースは、ネットワーク接続の一般的な振る舞いを定義します。`UDPConn`や`TCPConn`は、それぞれUDPおよびTCP接続を表す具体的な型です。
*   **`dnsMsg`構造体**: Goの`net`パッケージ内部でDNSメッセージを表現するために使用される構造体。DNSメッセージのパース（Unpack）とシリアライズ（Pack）の機能を提供します。
*   **`dnsConfig`構造体**: DNSリゾルバの設定（例: DNSサーバーのアドレス、タイムアウト、リトライ回数など）を保持する構造体。
*   **`Dialer`構造体**: ネットワーク接続を確立するための設定（例: タイムアウト）を持つ構造体。
*   **`exchange`関数 (変更前)**: 従来の`net`パッケージにおける、DNSクエリを送信し、レスポンスを受信する主要な関数。この関数が、トランスポートとメッセージ処理の両方を担当していました。
*   **`tryOneName`関数**: 複数のDNSサーバーに対して名前解決を試みる関数。内部で`exchange`関数を呼び出していました。
*   **RFC 1035**: DNSの基本的な仕様を定義するRFC。UDPのDNSメッセージサイズ制限（512バイト）などが規定されています。
*   **RFC 5966**: DNSのTCPフォールバックに関するRFC。UDPで応答が切り詰められた（truncated）場合にTCPに切り替えるべきであることを示唆しています。
*   **RFC 4035**: DNSSECに関するRFC。DNSSECでは大きなDNSメッセージが生成されるため、TCPの使用やEDNS0によるUDPメッセージサイズの拡張が考慮されます。

## 技術的詳細

このコミットの核心は、DNS通信における「トランスポート層」と「クエリ・レスポンスの相互作用」の分離です。

変更前は、`exchange`関数が以下の役割をすべて担っていました。
1.  DNSメッセージの構築 (`dnsMsg.Pack()`)
2.  ネットワーク接続 (`Conn`) を介したメッセージの送信 (`c.Write()`)
3.  ネットワーク接続からのレスポンスの受信 (`c.Read()` または `io.ReadFull()`)
4.  受信したデータのDNSメッセージへの解析 (`dnsMsg.Unpack()`)
5.  TCP/UDPのプロトコルに応じたメッセージの長さの処理（TCPの場合は先頭に2バイトの長さフィールドを追加）
6.  タイムアウト処理とリトライロジック

このコミットでは、これらの役割を以下のように再編成しています。

1.  **`dnsConn`インターフェースの導入**:
    *   `Conn`インターフェースを埋め込み、さらに`readDNSResponse()`と`writeDNSQuery(*dnsMsg)`という2つのメソッドを追加しています。
    *   これにより、DNSメッセージの読み書きという、より高レベルな操作を抽象化します。
2.  **`UDPConn`と`TCPConn`への`dnsConn`メソッドの実装**:
    *   `UDPConn`と`TCPConn`のそれぞれに、`readDNSResponse()`と`writeDNSQuery()`の具体的な実装が追加されました。
    *   `UDPConn`の実装では、UDPの特性（最大512バイトのメッセージサイズ）を考慮し、`c.Read(b)`でデータを読み込み、`msg.Unpack()`で解析します。
    *   `TCPConn`の実装では、TCPの特性（先頭2バイトの長さフィールド）を考慮し、`io.ReadFull(c, b[:2])`で長さを読み込み、その長さに基づいて残りのメッセージを読み込みます。
3.  **`Dialer.dialDNS()`関数の導入**:
    *   `net.Dialer`を使用して、指定されたネットワーク（"udp", "tcp"など）とサーバーアドレスに対して接続を確立し、その結果を`dnsConn`インターフェースとして返します。
    *   この関数は、DNSルックアップを必要としないIPアドレスへの接続のみを行うように設計されており、無限ループ（DNSルックアップのためにDNSルックアップを呼び出す）を防いでいます。
4.  **`exchange`関数の再設計**:
    *   新しい`exchange`関数は、DNSサーバーのアドレス、クエリ名、クエリタイプ、タイムアウトを受け取るようになりました。
    *   内部で`Dialer.dialDNS()`を呼び出して`dnsConn`を取得し、その`dnsConn`の`writeDNSQuery()`と`readDNSResponse()`メソッドを使用してDNSメッセージの送受信を行います。
    *   UDPとTCPの両方を試行するロジック（UDPで切り詰められた場合にTCPにフォールバックする）が、この新しい`exchange`関数内でより明確に管理されるようになりました。
    *   タイムアウト処理も`dnsConn.SetDeadline()`を通じて一元的に設定されます。
5.  **`tryOneName`関数の簡素化**:
    *   `tryOneName`関数は、個々のDNSサーバーへの接続とメッセージ交換のロジックを、新しい`exchange`関数に委譲するようになりました。これにより、`tryOneName`の責務が、複数のDNSサーバーを順に試行し、適切なエラーハンドリングを行うことに限定されます。

この変更により、DNSメッセージのパース/シリアライズと、ネットワークI/Oの具体的な実装が分離され、`exchange`関数はより高レベルなDNSクエリ・レスポンスのオーケストレーションに集中できるようになりました。これは、将来的な機能追加や改善において、コードの変更範囲を限定し、保守性を高める上で非常に重要なリファクタリングです。

## コアとなるコードの解説

### `dnsConn`インターフェースと実装

```go
// A dnsConn represents a DNS transport endpoint.
type dnsConn interface {
	Conn

	// readDNSResponse reads a DNS response message from the DNS
	// transport endpoint and returns the received DNS response
	// message.
	readDNSResponse() (*dnsMsg, error)

	// writeDNSQuery writes a DNS query message to the DNS
	// connection endpoint.
	writeDNSQuery(*dnsMsg) error
}

func (c *UDPConn) readDNSResponse() (*dnsMsg, error) {
	b := make([]byte, 512) // see RFC 1035
	n, err := c.Read(b)
	if err != nil {
		return nil, err
	}
	msg := &dnsMsg{}
	if !msg.Unpack(b[:n]) {
		return nil, errors.New("cannot unmarshal DNS message")
	}
	return msg, nil
}

func (c *UDPConn) writeDNSQuery(msg *dnsMsg) error {
	b, ok := msg.Pack()
	if !ok {
		return errors.New("cannot marshal DNS message")
	}
	if _, err := c.Write(b); err != nil {
		return err
	}
	return nil
}

func (c *TCPConn) readDNSResponse() (*dnsMsg, error) {
	b := make([]byte, 1280) // 1280 is a reasonable initial size for IP over Ethernet, see RFC 4035
	if _, err := io.ReadFull(c, b[:2]); err != nil {
		return nil, err
	}
	l := int(b[0])<<8 | int(b[1])
	if l > len(b) {
		b = make([]byte, l)
	}
	n, err := io.ReadFull(c, b[:l])
	if err != nil {
		return nil, err
	}
	msg := &dnsMsg{}
	if !msg.Unpack(b[:n]) {
		return nil, errors.New("cannot unmarshal DNS message")
	}
	return msg, nil
}

func (c *TCPConn) writeDNSQuery(msg *dnsMsg) error {
	b, ok := msg.Pack()
	if !ok {
		return errors.New("cannot marshal DNS message")
	}
	l := uint16(len(b))
	b = append([]byte{byte(l >> 8), byte(l)}, b...)
	if _, err := c.Write(b); err != nil {
		return err
	}
	return nil
}
```
`dnsConn`インターフェースは、DNSメッセージの読み書きという、より高レベルな操作を定義します。`UDPConn`と`TCPConn`はそれぞれ、UDPとTCPのプロトコルに応じたメッセージのパッキング/アンパッキング、およびネットワークからの読み書きを実装しています。特にTCPの場合、DNSメッセージの前に2バイトの長さフィールドが付加されるため、その処理が`readDNSResponse`と`writeDNSQuery`にカプセル化されています。

### `Dialer.dialDNS()`関数

```go
func (d *Dialer) dialDNS(network, server string) (dnsConn, error) {
	switch network {
	case "tcp", "tcp4", "tcp6", "udp", "udp4", "udp6":
	default:
		return nil, UnknownNetworkError(network)
	}
	// Calling Dial here is scary -- we have to be sure not to
	// dial a name that will require a DNS lookup, or Dial will
	// call back here to translate it. The DNS config parser has
	// already checked that all the cfg.servers[i] are IP
	// addresses, which Dial will use without a DNS lookup.
	c, err := d.Dial(network, server)
	if err != nil {
		return nil, err
	}
	switch network {
	case "tcp", "tcp4", "tcp6":
		return c.(*TCPConn), nil
	case "udp", "udp4", "udp6":
		return c.(*UDPConn), nil
	}
	panic("unreachable")
}
```
この関数は、指定されたネットワークとサーバーアドレス（IPアドレスであると仮定）に対してネットワーク接続を確立し、その接続を適切な`dnsConn`インターフェース型（`*TCPConn`または`*UDPConn`）に型アサートして返します。これにより、`exchange`関数は具体的な接続タイプを意識することなく、`dnsConn`インターフェースを通じてDNSメッセージの送受信を行えるようになります。

### `exchange`関数の再設計

```go
// exchange sends a query on the connection and hopes for a response.
func exchange(server, name string, qtype uint16, timeout time.Duration) (*dnsMsg, error) {
	d := Dialer{Timeout: timeout}
	out := dnsMsg{
		dnsMsgHdr: dnsMsgHdr{
			recursion_desired: true,
		},
		question: []dnsQuestion{
			{name, qtype, dnsClassINET},
		},
	}
	for _, network := range []string{"udp", "tcp"} {
		c, err := d.dialDNS(network, server)
		if err != nil {
			return nil, err
		}
		defer c.Close()
		if timeout > 0 {
			c.SetDeadline(time.Now().Add(timeout))
		}
		out.id = uint16(rand.Int()) ^ uint16(time.Now().UnixNano())
		if err := c.writeDNSQuery(&out); err != nil {
			return nil, err
		}
		in, err := c.readDNSResponse()
		if err != nil {
			return nil, err
		}
		if in.id != out.id {
			return nil, errors.New("DNS message ID mismatch")
		}
		if in.truncated { // see RFC 5966
			continue
		}
		return in, nil
	}
	return nil, errors.New("no answer from DNS server")
}
```
新しい`exchange`関数は、DNSサーバー、クエリ名、クエリタイプ、タイムアウトを引数として受け取ります。内部では、まずUDPを試行し、もしレスポンスが切り詰められていた場合（`in.truncated`がtrueの場合）はTCPにフォールバックして再試行します。このロジックは、`dnsConn`インターフェースの`writeDNSQuery`と`readDNSResponse`メソッドを呼び出すことで実現されており、トランスポートの詳細から解放されています。

### `tryOneName`関数の変更

```go
func tryOneName(cfg *dnsConfig, name string, qtype uint16) (string, []dnsRR, error) {
	if len(cfg.servers) == 0 {
		return "", nil, &DNSError{Err: "no DNS servers", Name: name}
	}
	if len(name) >= 256 {
		return "", nil, &DNSError{Err: "DNS name too long", Name: name}
	}
	timeout := time.Duration(cfg.timeout) * time.Second
	var lastErr error
	for _, server := range cfg.servers {
		server += ":53"
		lastErr = &DNSError{
			Err:       "no answer from DNS server",
			Name:      name,
			Server:    server,
			IsTimeout: true,
		}
		for i := 0; i < cfg.attempts; i++ {
			msg, err := exchange(server, name, qtype, timeout)
			if err != nil {
				if nerr, ok := err.(Error); ok && nerr.Timeout() {
					lastErr = &DNSError{
						Err:       nerr.Error(),
						Name:      name,
						Server:    server,
						IsTimeout: true,
					}
					continue

				}
				lastErr = &DNSError{
					Err:    err.Error(),
					Name:   name,
					Server: server,
				}
				break
			}
			cname, addrs, err := answer(name, server, msg, qtype)
			if err == nil || err.(*DNSError).Err == noSuchHost {
				return cname, addrs, err
			}
			lastErr = err
		}
	}
	return "", nil, lastErr
}
```
`tryOneName`関数は、設定されたDNSサーバーリストをループし、各サーバーに対して新しい`exchange`関数を呼び出すようになりました。これにより、`tryOneName`はDNSサーバーの選択とリトライロジックに専念し、個々のDNSクエリの実行は`exchange`関数に任せる形になりました。エラーハンドリングも改善され、タイムアウトやその他のエラーがより適切に処理されるようになっています。

このコミットは、Go言語の`net`パッケージにおいて、DNSトランスポート層（UDP/TCPによるデータの送受信）とDNSメッセージのクエリ・レスポンス処理を分離することを目的としています。これは、特定の課題（issue 6579）を修正する前段階として行われ、Goの組み込みDNSリゾルバに、より高度な制御ロジックを追加しやすくするための変更です。

## 変更の背景

Go言語の`net`パッケージは、ネットワーク通信の基本的な機能を提供しており、その中にはDNS（Domain Name System）の名前解決機能も含まれています。DNSの名前解決は、ドメイン名をIPアドレスに変換するために不可欠なプロセスです。

このコミットが行われた背景には、GoのDNSリゾルバの柔軟性と拡張性を向上させる必要がありました。従来の`exchange`関数は、DNSメッセージの構築、ネットワーク接続の確立、データの送受信、レスポンスの解析といった複数の役割を担っていました。この密結合な設計は、例えば、DNSリゾルバの動作を細かく制御する（例: 特定のDNSサーバーへのフォールバックロジック、キャッシュの導入、DNSSEC検証など）ような、より複雑な機能を追加する際に障壁となっていました。

コミットメッセージに記載されている「issue 6579」は、具体的な内容が不明ですが、おそらくDNSリゾルバの挙動に関する問題や機能改善要求であったと推測されます。このコミットは、その問題解決のための前提条件として、コードのモジュール化と責務の分離を進めることを目的としています。これにより、将来的に「組み込みのDNSリゾルバ制御ロジック」を容易に追加できるよう、基盤を整備しています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

*   **DNS (Domain Name System)**: インターネット上のドメイン名とIPアドレスを対応させる分散型データベースシステム。クライアントはDNSサーバーにクエリを送信し、ドメイン名に対応するIPアドレスなどの情報を取得します。
*   **DNSメッセージ構造**: DNSのクエリとレスポンスは、特定のフォーマットに従ったメッセージとして送受信されます。これには、ヘッダー、質問セクション、回答セクション、権威セクション、追加情報セクションなどが含まれます。
*   **UDPとTCPによるDNS通信**:
    *   **UDP (User Datagram Protocol)**: 通常のDNSクエリにはUDPが使用されます。これはコネクションレスで高速ですが、メッセージサイズに制限（通常512バイト）があり、信頼性が保証されません。
    *   **TCP (Transmission Control Protocol)**: ゾーン転送や、UDPで応答しきれない大きなDNSレスポンス（例: DNSSEC署名付きの応答や、多数のレコードを含む応答）の場合にTCPが使用されます。TCPはコネクション指向で信頼性がありますが、UDPよりもオーバーヘッドが大きいです。
*   **Go言語の`net`パッケージ**: ネットワークI/O機能を提供するGoの標準ライブラリ。`Conn`インターフェースは、ネットワーク接続の一般的な振る舞いを定義します。`UDPConn`や`TCPConn`は、それぞれUDPおよびTCP接続を表す具体的な型です。
*   **`dnsMsg`構造体**: Goの`net`パッケージ内部でDNSメッセージを表現するために使用される構造体。DNSメッセージのパース（Unpack）とシリアライズ（Pack）の機能を提供します。
*   **`dnsConfig`構造体**: DNSリゾルバの設定（例: DNSサーバーのアドレス、タイムアウト、リトライ回数など）を保持する構造体。
*   **`Dialer`構造体**: ネットワーク接続を確立するための設定（例: タイムアウト）を持つ構造体。
*   **`exchange`関数 (変更前)**: 従来の`net`パッケージにおける、DNSクエリを送信し、レスポンスを受信する主要な関数。この関数が、トランスポートとメッセージ処理の両方を担当していました。
*   **`tryOneName`関数**: 複数のDNSサーバーに対して名前解決を試みる関数。内部で`exchange`関数を呼び出していました。
*   **RFC 1035**: DNSの基本的な仕様を定義するRFC。UDPのDNSメッセージサイズ制限（512バイト）などが規定されています。
*   **RFC 5966**: DNSのTCPフォールバックに関するRFC。UDPで応答が切り詰められた（truncated）場合にTCPに切り替えるべきであることを示唆しています。
*   **RFC 4035**: DNSSECに関するRFC。DNSSECでは大きなDNSメッセージが生成されるため、TCPの使用やEDNS0によるUDPメッセージサイズの拡張が考慮されます。

## 技術的詳細

このコミットの核心は、DNS通信における「トランスポート層」と「クエリ・レスポンスの相互作用」の分離です。

変更前は、`exchange`関数が以下の役割をすべて担っていました。
1.  DNSメッセージの構築 (`dnsMsg.Pack()`)
2.  ネットワーク接続 (`Conn`) を介したメッセージの送信 (`c.Write()`)
3.  ネットワーク接続からのレスポンスの受信 (`c.Read()` または `io.ReadFull()`)
4.  受信したデータのDNSメッセージへの解析 (`dnsMsg.Unpack()`)
5.  TCP/UDPのプロトコルに応じたメッセージの長さの処理（TCPの場合は先頭に2バイトの長さフィールドを追加）
6.  タイムアウト処理とリトライロジック

このコミットでは、これらの役割を以下のように再編成しています。

1.  **`dnsConn`インターフェースの導入**:
    *   `Conn`インターフェースを埋め込み、さらに`readDNSResponse()`と`writeDNSQuery(*dnsMsg)`という2つのメソッドを追加しています。
    *   これにより、DNSメッセージの読み書きという、より高レベルな操作を抽象化します。
2.  **`UDPConn`と`TCPConn`への`dnsConn`メソッドの実装**:
    *   `UDPConn`と`TCPConn`のそれぞれに、`readDNSResponse()`と`writeDNSQuery()`の具体的な実装が追加されました。
    *   `UDPConn`の実装では、UDPの特性（最大512バイトのメッセージサイズ）を考慮し、`c.Read(b)`でデータを読み込み、`msg.Unpack()`で解析します。
    *   `TCPConn`の実装では、TCPの特性（先頭2バイトの長さフィールド）を考慮し、`io.ReadFull(c, b[:2])`で長さを読み込み、その長さに基づいて残りのメッセージを読み込みます。
3.  **`Dialer.dialDNS()`関数の導入**:
    *   `net.Dialer`を使用して、指定されたネットワーク（"udp", "tcp"など）とサーバーアドレスに対して接続を確立し、その結果を`dnsConn`インターフェースとして返します。
    *   この関数は、DNSルックアップを必要としないIPアドレスへの接続のみを行うように設計されており、無限ループ（DNSルックアップのためにDNSルックアップを呼び出す）を防いでいます。
4.  **`exchange`関数の再設計**:
    *   新しい`exchange`関数は、DNSサーバーのアドレス、クエリ名、クエリタイプ、タイムアウトを受け取るようになりました。
    *   内部で`Dialer.dialDNS()`を呼び出して`dnsConn`を取得し、その`dnsConn`の`writeDNSQuery()`と`readDNSResponse()`メソッドを使用してDNSメッセージの送受信を行います。
    *   UDPとTCPの両方を試行するロジック（UDPで切り詰められた場合にTCPにフォールバックする）が、この新しい`exchange`関数内でより明確に管理されるようになりました。
    *   タイムアウト処理も`dnsConn.SetDeadline()`を通じて一元的に設定されます。
5.  **`tryOneName`関数の簡素化**:
    *   `tryOneName`関数は、個々のDNSサーバーへの接続とメッセージ交換のロジックを、新しい`exchange`関数に委譲するようになりました。これにより、`tryOneName`の責務が、複数のDNSサーバーを順に試行し、適切なエラーハンドリングを行うことに限定されます。

この変更により、DNSメッセージのパース/シリアライズと、ネットワークI/Oの具体的な実装が分離され、`exchange`関数はより高レベルなDNSクエリ・レスポンスのオーケストレーションに集中できるようになりました。これは、将来的な機能追加や改善において、コードの変更範囲を限定し、保守性を高める上で非常に重要なリファクタリングです。

## コアとなるコードの解説

### `dnsConn`インターフェースと実装

```go
// A dnsConn represents a DNS transport endpoint.
type dnsConn interface {
	Conn

	// readDNSResponse reads a DNS response message from the DNS
	// transport endpoint and returns the received DNS response
	// message.
	readDNSResponse() (*dnsMsg, error)

	// writeDNSQuery writes a DNS query message to the DNS
	// connection endpoint.
	writeDNSQuery(*dnsMsg) error
}

func (c *UDPConn) readDNSResponse() (*dnsMsg, error) {
	b := make([]byte, 512) // see RFC 1035
	n, err := c.Read(b)
	if err != nil {
		return nil, err
	}
	msg := &dnsMsg{}
	if !msg.Unpack(b[:n]) {
		return nil, errors.New("cannot unmarshal DNS message")
	}
	return msg, nil
}

func (c *UDPConn) writeDNSQuery(msg *dnsMsg) error {
	b, ok := msg.Pack()
	if !ok {
		return errors.New("cannot marshal DNS message")
	}
	if _, err := c.Write(b); err != nil {
		return err
	}
	return nil
}

func (c *TCPConn) readDNSResponse() (*dnsMsg, error) {
	b := make([]byte, 1280) // 1280 is a reasonable initial size for IP over Ethernet, see RFC 4035
	if _, err := io.ReadFull(c, b[:2]); err != nil {
		return nil, err
	}
	l := int(b[0])<<8 | int(b[1])
	if l > len(b) {
		b = make([]byte, l)
	}
	n, err := io.ReadFull(c, b[:l])
	if err != nil {
		return nil, err
	}
	msg := &dnsMsg{}
	if !msg.Unpack(b[:n]) {
		return nil, errors.New("cannot unmarshal DNS message")
	}
	return msg, nil
}

func (c *TCPConn) writeDNSQuery(msg *dnsMsg) error {
	b, ok := msg.Pack()
	if !ok {
		return errors.New("cannot marshal DNS message")
	}
	l := uint16(len(b))
	b = append([]byte{byte(l >> 8), byte(l)}, b...)
	if _, err := c.Write(b); err != nil {
		return err
	}
	return nil
}
```
`dnsConn`インターフェースは、DNSメッセージの読み書きという、より高レベルな操作を定義します。`UDPConn`と`TCPConn`はそれぞれ、UDPとTCPのプロトコルに応じたメッセージのパッキング/アンパッキング、およびネットワークからの読み書きを実装しています。特にTCPの場合、DNSメッセージの前に2バイトの長さフィールドが付加されるため、その処理が`readDNSResponse`と`writeDNSQuery`にカプセル化されています。

### `Dialer.dialDNS()`関数

```go
func (d *Dialer) dialDNS(network, server string) (dnsConn, error) {
	switch network {
	case "tcp", "tcp4", "tcp6", "udp", "udp4", "udp6":
	default:
		return nil, UnknownNetworkError(network)
	}
	// Calling Dial here is scary -- we have to be sure not to
	// dial a name that will require a DNS lookup, or Dial will
	// call back here to translate it. The DNS config parser has
	// already checked that all the cfg.servers[i] are IP
	// addresses, which Dial will use without a DNS lookup.
	c, err := d.Dial(network, server)
	if err != nil {
		return nil, err
	}
	switch network {
	case "tcp", "tcp4", "tcp6":
		return c.(*TCPConn), nil
	case "udp", "udp4", "udp6":
		return c.(*UDPConn), nil
	}
	panic("unreachable")
}
```
この関数は、指定されたネットワークとサーバーアドレス（IPアドレスであると仮定）に対してネットワーク接続を確立し、その接続を適切な`dnsConn`インターフェース型（`*TCPConn`または`*UDPConn`）に型アサートして返します。これにより、`exchange`関数は具体的な接続タイプを意識することなく、`dnsConn`インターフェースを通じてDNSメッセージの送受信を行えるようになります。

### `exchange`関数の再設計

```go
// exchange sends a query on the connection and hopes for a response.
func exchange(server, name string, qtype uint16, timeout time.Duration) (*dnsMsg, error) {
	d := Dialer{Timeout: timeout}
	out := dnsMsg{
		dnsMsgHdr: dnsMsgHdr{
			recursion_desired: true,
		},
		question: []dnsQuestion{
			{name, qtype, dnsClassINET},
		},
	}
	for _, network := range []string{"udp", "tcp"} {
		c, err := d.dialDNS(network, server)
		if err != nil {
			return nil, err
		}
		defer c.Close()
		if timeout > 0 {
			c.SetDeadline(time.Now().Add(timeout))
		}
		out.id = uint16(rand.Int()) ^ uint16(time.Now().UnixNano())
		if err := c.writeDNSQuery(&out); err != nil {
			return nil, err
		}
		in, err := c.readDNSResponse()
		if err != nil {
			return nil, err
		}
		if in.id != out.id {
			return nil, errors.New("DNS message ID mismatch")
		}
		if in.truncated { // see RFC 5966
			continue
		}
		return in, nil
	}
	return nil, errors.New("no answer from DNS server")
}
```
新しい`exchange`関数は、DNSサーバー、クエリ名、クエリタイプ、タイムアウトを引数として受け取ります。内部では、まずUDPを試行し、もしレスポンスが切り詰められていた場合（`in.truncated`がtrueの場合）はTCPにフォールバックして再試行します。このロジックは、`dnsConn`インターフェースの`writeDNSQuery`と`readDNSResponse`メソッドを呼び出すことで実現されており、トランスポートの詳細から解放されています。

### `tryOneName`関数の変更

```go
func tryOneName(cfg *dnsConfig, name string, qtype uint16) (string, []dnsRR, error) {
	if len(cfg.servers) == 0 {
		return "", nil, &DNSError{Err: "no DNS servers", Name: name}
	}
	if len(name) >= 256 {
		return "", nil, &DNSError{Err: "DNS name too long", Name: name}
	}
	timeout := time.Duration(cfg.timeout) * time.Second
	var lastErr error
	for _, server := range cfg.servers {
		server += ":53"
		lastErr = &DNSError{
			Err:       "no answer from DNS server",
			Name:      name,
			Server:    server,
			IsTimeout: true,
		}
		for i := 0; i < cfg.attempts; i++ {
			msg, err := exchange(server, name, qtype, timeout)
			if err != nil {
				if nerr, ok := err.(Error); ok && nerr.Timeout() {
					lastErr = &DNSError{
						Err:       nerr.Error(),
						Name:      name,
						Server:    server,
						IsTimeout: true,
					}
					continue

				}
				lastErr = &DNSError{
					Err:    err.Error(),
					Name:   name,
					Server: server,
				}
				break
			}
			cname, addrs, err := answer(name, server, msg, qtype)
			if err == nil || err.(*DNSError).Err == noSuchHost {
				return cname, addrs, err
			}
			lastErr = err
		}
	}
	return "", nil, lastErr
}
```
`tryOneName`関数は、設定されたDNSサーバーリストをループし、各サーバーに対して新しい`exchange`関数を呼び出すようになりました。これにより、`tryOneName`はDNSサーバーの選択とリトライロジックに専念し、個々のDNSクエリの実行は`exchange`関数に任せる形になりました。エラーハンドリングも改善され、タイムアウトやその他のエラーがより適切に処理されるようになっています。

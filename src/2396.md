## 変更の背景

このコミットは、Goランタイムの386アーキテクチャ（32ビットシステム）におけるログテストの失敗を修正するために行われました。`runtime.Caller`関数は、呼び出し元の情報を取得するために使用されますが、32ビットシステムで64ビット整数型（`uint64`）をプログラムカウンタ（PC）やスタックポインタ（SP）の格納に使用すると、アライメントやサイズの不一致により問題が発生する可能性があります。特に、ポインタ演算において固定値（例: `8`や`16`バイト）を使用している箇所が、実際のアドレスサイズと異なる場合に、不正なメモリアクセスや誤ったスタックフレームの巻き戻しを引き起こす可能性があります。

この修正は、32ビット環境でのポインタのサイズに合わせた`uintptr`型への変更と、ポインタ演算をより汎用的な`sizeof(uintptr)`を使用するようにすることで、この問題を解決し、テストの安定性を確保することを目的としています。

## 前提知識の解説

### 1. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、スタック管理、プリミティブな同期メカニズムなど、Go言語の多くの低レベルな側面を処理します。`runtime`パッケージは、これらのランタイム機能へのインターフェースを提供します。

### 2. `runtime.Caller`関数

`runtime.Caller`関数は、現在のゴルーチンのコールスタックを遡り、指定された深さの呼び出し元のプログラムカウンタ、ファイル名、行番号、および情報が取得できたかどうかを示すブール値を返します。デバッグ、ロギング、またはリフレクションのような目的で、呼び出し元の情報を動的に取得する際に利用されます。

### 3. `uintptr`型と`uint64`型

*   **`uintptr`**: Go言語における`uintptr`型は、ポインタを保持するのに十分な大きさの符号なし整数型です。そのサイズは、実行されているシステムのアーキテクチャ（32ビットまたは64ビット）に依存します。32ビットシステムでは32ビット（4バイト）、64ビットシステムでは64ビット（8バイト）になります。これは、ポインタと整数間の変換を安全に行うために設計されており、特に低レベルのシステムプログラミングやFFI（Foreign Function Interface）で重要です。
*   **`uint64`**: `uint64`型は、常に64ビット（8バイト）の符号なし整数です。これは、特定のビット幅を持つ数値を格納するために使用され、アーキテクチャに依存しません。

このコミットの文脈では、386アーキテクチャ（32ビット）で実行されるGoプログラムにおいて、プログラムカウンタやスタックポインタは32ビットのアドレスを指します。`uint64`を使用すると、必要以上に大きな型を使い、ポインタ演算で固定値（8バイトなど）を直接使用すると、32ビット環境でのポインタの実際のサイズ（4バイト）と不一致が生じ、誤ったメモリアドレスを計算してしまう可能性があります。`uintptr`を使用することで、ポインタのサイズがアーキテクチャに合わせて自動的に調整されるため、このような問題を回避できます。

### 4. スタックトレースとスタックアンワインド

*   **スタックトレース**: プログラムの実行中に、現在実行中の関数から始まり、その関数を呼び出した関数、さらにその関数を呼び出した関数へと遡って、一連の関数呼び出しの履歴をリストアップしたものです。デバッグ時にエラーの発生源を特定するのに非常に役立ちます。
*   **スタックアンワインド**: スタックトレースを生成するプロセスで、コールスタックを逆方向に辿り、各関数のスタックフレーム情報を解析していくことです。これには、プログラムカウンタ（PC）やスタックポインタ（SP）の値を正確に計算し、スタックフレームのサイズを把握する必要があります。

### 5. 386アーキテクチャ

Intel 80386プロセッサに由来する32ビット命令セットアーキテクチャです。Go言語の初期には、このアーキテクチャ向けのランタイムコードが多数存在しました。32ビットシステムでは、メモリアドレスは32ビット幅で表現されます。

## 技術的詳細

このコミットの核心は、32ビットシステム（386アーキテクチャ）におけるポインタの取り扱いを正確にすることです。

1.  **`runtime.Caller`のシグネチャ変更**:
    `src/lib/runtime/runtime.go`において、`runtime.Caller`関数の戻り値であるプログラムカウンタ`pc`の型が`uint64`から`uintptr`に変更されました。
    ```go
    // 変更前
    func	Caller(n int) (pc uint64, file string, line int, ok bool)
    // 変更後
    func	Caller(n int) (pc uintptr, file string, line int, ok bool)
    ```
    これは、386のような32ビットアーキテクチャでは、プログラムカウンタが32ビット幅であるため、`uintptr`が適切な型であるという認識に基づいています。`uint64`は64ビット幅であり、32ビット環境では過剰なだけでなく、ポインタ演算の際に誤解を招く可能性があります。

2.  **C言語実装における型変更**:
    `src/runtime/386/traceback.c`は、386アーキテクチャにおけるスタックトレースのC言語実装です。ここでも、`runtime·Caller`関数の引数`retpc`およびローカル変数`pc`の型が`uint64`から`uintptr`に変更されています。
    ```c
    // 変更前
    void runtime·Caller(int32 n, uint64 retpc, String retfile, int32 retline, bool retbool)
    {
        uint64 pc;
    // 変更後
    void runtime·Caller(int32 n, uintptr retpc, String retfile, int32 retline, bool retbool)
    {
        uintptr pc;
    ```
    この変更は、Go側のシグネチャ変更と整合性を保つためのものです。

3.  **ポインタ演算の修正**:
    最も重要な変更点は、スタックアンワインド中のポインタ演算です。以前は、スタックポインタ`sp`からのオフセットを計算する際に、固定値`8`や`16`が使用されていました。これは、64ビットシステムではポインタが8バイトであるため、`uint64`のサイズと一致しますが、32ビットシステムではポインタが4バイトであるため、不正確になります。
    このコミットでは、これらの固定値を`sizeof(uintptr)`に置き換えることで、アーキテクチャに依存しない正しいポインタ演算を実現しています。
    *   `pc = *(uint64*)(sp-8);` が `pc = *((uintptr*)sp - 1);` に変更。
        *   `sp-8`は`sp`から8バイト前のメモリを指しますが、32ビット環境ではポインタは4バイトなので、これは2つのポインタ分前の位置を指すことになります。`*((uintptr*)sp - 1)`は、`sp`が指す位置から`uintptr`のサイズ分（32ビット環境では4バイト）前の位置にある`uintptr`型の値を読み取ることを意味します。
    *   `sp += 16;` が `sp += 2*sizeof(uintptr);` に変更。
        *   `16`バイトの加算は、64ビット環境では2つのポインタ分ですが、32ビット環境では4つのポインタ分になります。`2*sizeof(uintptr)`は、常に2つのポインタ分だけスタックポインタを進めることを保証します。
    *   `if(f->frame < 8) sp += 8;` が `if(f->frame < sizeof(uintptr)) sp += sizeof(uintptr);` に変更。
        *   アセンブリ関数がスタックフレームサイズを偽ることがあるため、調整が必要な場合があります。ここでも固定値`8`を`sizeof(uintptr)`に置き換えることで、32ビット環境での正しい調整を保証します。
    *   `sp += *(uint32*)(p+2) + 8;` が `sp += *(uint32*)(p+2) + sizeof(uintptr);` に変更。
        *   クロージャのスタックフレーム調整に関する部分でも、同様に固定値`8`を`sizeof(uintptr)`に置き換えています。

これらの変更により、386アーキテクチャにおいて`runtime.Caller`がスタックを正しくアンワインドし、正確なプログラムカウンタの値を返すことが保証され、結果としてログテストの失敗が修正されました。

## コアとなるコードの解説

このコミットの主要な変更は、`runtime.Caller`関数が返すプログラムカウンタの型を`uint64`から`uintptr`に変更し、それに伴いC言語で実装されているスタックトレース処理内のポインタ演算を修正した点です。

1.  **`runtime.go`における`Caller`関数のシグネチャ変更**:
    Go言語側の`runtime.Caller`関数の定義で、`pc`の型が`uint64`から`uintptr`に変更されました。これは、Goのポインタが実行環境のアーキテクチャのビット幅に依存するため、`uintptr`がポインタ値を表現するのに最も適切であるという原則に基づいています。特に32ビットシステムでは、`uint64`は過剰なサイズであり、ポインタ演算の際に混乱を招く可能性がありました。

2.  **`traceback.c`における型とポインタ演算の修正**:
    `traceback.c`は、GoランタイムがC言語で実装されている部分であり、特にスタックトレースの生成のような低レベルな処理を担当します。
    *   `runtime·Caller`関数の引数`retpc`とローカル変数`pc`の型が`uint64`から`uintptr`に変更されました。これにより、C言語側でもGo言語側の型定義と一致し、32ビット環境でのポインタのサイズに合わせた処理が可能になります。
    *   スタックアンワインドのロジックにおいて、スタックポインタ`sp`からのオフセット計算で、以前は固定値`8`や`16`が使われていました。これらの値は64ビットシステムでのポインタサイズ（8バイト）を前提としていましたが、32ビットシステムではポインタサイズが4バイトであるため、誤ったアドレス計算を引き起こしていました。
    *   この修正では、これらの固定値を`sizeof(uintptr)`に置き換えることで、コードが実行されるアーキテクチャ（32ビットまたは64ビット）に応じて、ポインタの実際のサイズに基づいた正しいオフセット計算が行われるようにしました。例えば、`*(uint64*)(sp-8)`は`*((uintptr*)sp - 1)`に、`sp += 16`は`sp += 2*sizeof(uintptr)`に変更されています。これにより、スタックフレームの境界を正確に特定し、プログラムカウンタを正しく取得できるようになります。
    *   `f->frame < 8`のようなアセンブリ関数のスタックフレームサイズを調整する箇所も、`f->frame < sizeof(uintptr)`に変更され、アーキテクチャに依存しない正しい調整が行われるようになりました。

これらの変更により、386アーキテクチャのような32ビットシステムで`runtime.Caller`がスタックトレースを正確に生成できるようになり、関連するログテストの失敗が解消されました。これは、Goランタイムが異なるアーキテクチャ間で移植性と正確性を保つ上で重要な修正です。

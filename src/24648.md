このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおいて、非定数に対する整数除算の実装を追加するものです。具体的には、AMD64アーキテクチャ向けに、符号付きおよび符号なしの8ビット、16ビット、32ビット、64ビット整数に対する除算操作をサポートします。これにより、Goプログラム内で非定数による整数除算が行われる際に、SSA形式から効率的なAMD64アセンブリコードへの変換が可能になります。

## 変更の背景

Goコンパイラは、プログラムの最適化とコード生成のためにSSA（Static Single Assignment）形式の中間表現を使用します。このコミットが作成された時点では、GoのSSAバックエンドは非定数による整数除算を完全にサポートしていませんでした。これは、コンパイラが非定数オペランドを持つ除算演算に遭遇した際に、効率的なマシンコードを生成できないことを意味します。

整数除算は、特に境界条件（例：最小負数を-1で除算する際のオーバーフロー）において、CPUレベルで特別な注意が必要な複雑な操作です。AMD64アーキテクチャの`DIV`および`IDIV`命令は、特定のレジスタ（`AX`/`DX:AX`など）を使用し、結果を特定のレジスタに格納するという独特の動作をします。また、符号付き除算ではオーバーフローが発生するとCPU例外（`#DE`）を引き起こす可能性があります。

このコミットの目的は、Goコンパイラが非定数整数除算をSSA形式で適切に表現し、AMD64アーキテクチャの特性を考慮した上で、正確かつ効率的なアセンブリコードを生成できるようにすることです。これにより、Goプログラムのパフォーマンス向上と、コンパイラの機能網羅性の向上が図られます。

## 前提知識の解説

### Goコンパイラの構造とSSA

Goコンパイラは、主に以下のステージで構成されます。

1.  **フロントエンド (`cmd/compile/internal/gc`)**: ソースコードのパース、抽象構文木（AST）の構築、型チェック、定数畳み込みなどを行います。このステージで、Goの演算子（`ODIV`など）が識別されます。
2.  **中間表現（IR）生成**: ASTからSSA形式の中間表現を生成します。SSA形式では、各変数が一度だけ代入されるため、データフロー解析や最適化が容易になります。
3.  **SSA最適化**: SSAグラフ上で様々な最適化（デッドコード削除、共通部分式除去、レジスタ割り当てなど）が行われます。
4.  **バックエンド (`cmd/compile/internal/ssa` および `cmd/compile/internal/gc` の一部)**: 最適化されたSSAグラフをターゲットアーキテクチャ（この場合はAMD64）の機械語に変換します。この変換プロセスには、ジェネリックなSSA操作を特定のアーキテクチャの命令にマッピングする「リライトルール」が含まれます。

### AMD64の整数除算命令

AMD64アーキテクチャには、整数除算のための`DIV`（符号なし除算）と`IDIV`（符号付き除算）命令があります。これらの命令は、以下のような特徴を持ちます。

*   **オペランド**:
    *   **被除数**: 常に`AX`（16ビット）、`EAX`（32ビット）、または`RAX`（64ビット）レジスタに格納されます。より大きな被除数（例：32ビット除算で64ビットの被除数）の場合、`DX:AX`、`EDX:EAX`、`RDX:RAX`のペアが使用されます。`DX`レジスタは被除数の上位ビットを保持します。
    *   **除数**: 汎用レジスタまたはメモリ位置に格納されます。
*   **結果**:
    *   **商**: `AX`、`EAX`、または`RAX`レジスタに格納されます。
    *   **剰余**: `DX`、`EDX`、または`RDX`レジスタに格納されます。
*   **符号拡張/ゼロ拡張**:
    *   `IDIV`命令を使用する際、被除数が除数よりも小さいビット幅の場合（例：8ビット整数を16ビット`IDIVW`で除算）、被除数を`AX`レジスタにロードする前に、その符号を`DX:AX`ペア全体に拡張する必要があります。これは`CBW`（バイトからワードへ符号拡張）、`CWD`（ワードからダブルワードへ符号拡張）、`CDQ`（ダブルワードからクワッドワードへ符号拡張）、`CQO`（クワッドワードからオクトワードへ符号拡張）などの命令で行われます。
    *   `DIV`命令（符号なし）の場合、被除数の上位ビットはゼロで埋められる（ゼロ拡張）必要があります。
*   **オーバーフロー**:
    *   符号付き除算（`IDIV`）において、最小負数（例：-2^63 for int64）を-1で除算すると、結果が表現可能な最大正数（2^63 - 1）を超えてしまい、CPU例外（`#DE` - Divide Error）が発生します。これは、2の補数表現の非対称性によるものです。このケースは、コンパイラまたはランタイムで特別に処理する必要があります。

### SSAオペレーションの種類

GoのSSAには、ジェネリックなオペレーションとアーキテクチャ固有のオペレーションがあります。

*   **ジェネリックオペレーション**: `ssa.OpDiv64` のように、特定のアーキテクチャに依存しない抽象的な操作を表します。
*   **アーキテクチャ固有オペレーション**: `ssa.OpAMD64DIVQ` のように、特定のCPU命令に直接対応する操作を表します。

コンパイラのバックエンドは、ジェネリックオペレーションをアーキテクチャ固有オペレーションに変換する役割を担います。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける整数除算のサポートを、以下の主要なコンポーネントにわたって拡張しています。

1.  **SSAオペレーションの定義**:
    *   `src/cmd/compile/internal/ssa/gen/genericOps.go` に、`Div8`, `Div8u`, `Div16`, `Div16u`, `Div32`, `Div32u`, `Div64`, `Div64u` といったジェネリックな除算オペレーションが追加されました。これらは、Goの各整数型（`int8`, `uint8`, `int16`, `uint16`, `int32`, `uint32`, `int64`, `uint64`）に対応する除算を表します。
    *   `src/cmd/compile/internal/ssa/opGen.go` に、AMD64アーキテクチャ固有の除算オペレーション (`OpAMD64DIVQ`, `OpAMD64DIVL`, `OpAMD64DIVW`, `OpAMD64DIVQU`, `OpAMD64DIVLU`, `OpAMD64DIVWU`) が追加されました。これらは、それぞれAMD64の`IDIVQ`, `IDIVL`, `IDIVW`, `DIVQ`, `DIVL`, `DIVW`命令に対応します。
    *   `opGen.go` では、これらのAMD64固有オペレーションのレジスタ使用規則 (`regInfo`) も定義されています。特に、除算命令が`AX`レジスタを被除数として使用し、`DX`レジスタをクリーンアップ（または符号拡張）し、結果を`AX`に格納するというAMD64の慣習が反映されています。`DX`レジスタは`clobbers`（破壊されるレジスタ）としてマークされています。

2.  **SSAからAMD64命令へのリライトルール**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64.rules` に、ジェネリックな`DivX`および`DivXu`オペレーションをAMD64固有の`DIV`または`IDIV`命令に変換するためのリライトルールが追加されました。
    *   特筆すべきは、8ビット整数除算 (`Div8`, `Div8u`) の扱いです。AMD64には8ビット除算命令がないため、これらのルールは8ビットオペランドを16ビットに符号拡張 (`SignExt8to16`) またはゼロ拡張 (`ZeroExt8to16`) してから、16ビット除算命令 (`DIVW`, `DIVWU`) を使用するように変換します。これは、ハードウェアの制約を考慮した適切なコード生成です。
    *   `src/cmd/compile/internal/ssa/rewriteAMD64.go` には、これらのリライトルールを実際に適用するコードが追加されています。`OpDiv16`, `OpDiv16u`, `OpDiv32`, `OpDiv32u`, `OpDiv64`, `OpDiv64u`, `OpDiv8`, `OpDiv8u` の各ケースで、対応するAMD64固有の除算オペレーションに変換し、必要に応じて符号拡張/ゼロ拡張オペレーションを挿入します。

3.  **`gc`パッケージでのSSAマッピングとコード生成**:
    *   `src/cmd/compile/internal/gc/ssa.go` の `opToSSA` マップに、Goの`ODIV`操作と型 (`TINT8`, `TUINT8`など) の組み合わせを、対応するSSAジェネリック除算オペレーション (`ssa.OpDiv8`, `ssa.OpDiv8u`など) にマッピングするエントリが追加されました。これにより、フロントエンドが`ODIV`を検出した際に、正しいSSAオペレーションが生成されるようになります。
    *   `gc/ssa.go` の `genValue` 関数には、AMD64固有の除算オペレーション (`ssa.OpAMD64DIVQ`など) のためのコード生成ロジックが追加されました。
        *   **レジスタの準備**: AMD64の除算命令は被除数を`AX`レジスタに期待するため、`v.Args[0]`（被除数）が既に`AX`にあることを前提としています。
        *   **符号拡張/ゼロ拡張**: 符号付き除算の場合、`CQO`（64ビット）、`CDQ`（32ビット）、`CWD`（16ビット）命令を使用して、`AX`レジスタの値を`DX:AX`ペアに符号拡張します。符号なし除算の場合、`DX`レジスタを`XORQ DX, DX`などでゼロクリアします。これにより、被除数が正しく`DX:AX`に設定されます。
        *   **オーバーフローのハンドリング**: 符号付き除算 (`IDIV`) において、最小負数（例：`int64`の`-9223372036854775808`）を`-1`で除算するとCPU例外が発生します。このコミットでは、除数が`-1`であるかどうかを`CMP`命令でチェックし、もし`-1`であれば、`JEQ`（等しい場合にジャンプ）命令を使って特別な処理に分岐します。この特別な処理では、`NEGQ AX`（`AX`の値を反転）を実行することで、オーバーフローを回避し、正しい結果（最小負数）を生成します。これは、Goの仕様でこのケースがオーバーフローではなく、最小負数自身を返すことになっているためです。

4.  **テストケースの追加**:
    *   `src/cmd/compile/internal/gc/ssa_test.go` に `TestArithmeticBoundary` が追加され、新しいテストデータファイル `arithBoundary_ssa.go` を実行するように設定されました。
    *   `src/cmd/compile/internal/gc/testdata/arithBoundary_ssa.go` は、様々な整数型（`int8`から`uint64`まで）の加算、減算、乗算、除算について、境界値を含む多数のテストケースを定義しています。これにより、新しい除算実装が正確に機能し、特にオーバーフローやアンダーフローなどのエッジケースで正しい結果を生成することが検証されます。

これらの変更により、Goコンパイラは非定数整数除算をSSA形式で処理し、AMD64アーキテクチャ上で効率的かつ正確な機械語を生成できるようになりました。

// genValue 関数内のAMD64除算命令のコード生成ロジック
func genValue(v *ssa.Value) {
	// ... 既存のケース
	case ssa.OpAMD64DIVQ, ssa.OpAMD64DIVL, ssa.OpAMD64DIVW,
		ssa.OpAMD64DIVQU, ssa.OpAMD64DIVLU, ssa.OpAMD64DIVWU:

		// Arg[0] (被除数) は既にAXレジスタにあることを前提とする
		x := regnum(v.Args[1]) // 除数

		// 符号付き除算の場合、-1による除算オーバーフローをチェック
		var j *obj.Prog
		if v.Op == ssa.OpAMD64DIVQ || v.Op == ssa.OpAMD64DIVL ||
			v.Op == ssa.OpAMD64DIVW {

			var c *obj.Prog
			switch v.Op {
			case ssa.OpAMD64DIVQ:
				c = Prog(x86.ACMPQ) // 64ビット比較
			case ssa.OpAMD64DIVL:
				c = Prog(x86.ACMPL) // 32ビット比較
			case ssa.OpAMD64DIVW:
				c = Prog(x86.ACMPW) // 16ビット比較
			}
			c.From.Type = obj.TYPE_REG
			c.From.Reg = x // 除数レジスタ
			c.To.Type = obj.TYPE_CONST
			c.To.Offset = -1 // -1 と比較

			j = Prog(x86.AJEQ) // 等しければジャンプ
			j.To.Type = obj.TYPE_BRANCH
		}

		// 被除数 (AX) をDX:AXペアに符号拡張またはゼロクリア
		switch v.Op {
		case ssa.OpAMD64DIVQU: // 符号なし64ビット除算
			fallthrough
		case ssa.OpAMD64DIVLU: // 符号なし32ビット除算
			fallthrough
		case ssa.OpAMD64DIVWU: // 符号なし16ビット除算
			// DXレジスタをゼロクリア (ゼロ拡張)
			c := Prog(x86.AXORQ)
			c.From.Type = obj.TYPE_REG
			c.From.Reg = x86.REG_DX
			c.To.Type = obj.TYPE_REG
			c.To.Reg = x86.REG_DX
		case ssa.OpAMD64DIVQ: // 符号付き64ビット除算
			Prog(x86.ACQO) // RAXをRDX:RAXに符号拡張
		case ssa.OpAMD64DIVL: // 符号付き32ビット除算
			Prog(x86.ACDQ) // EAXをEDX:EAXに符号拡張
		case ssa.OpAMD64DIVW: // 符号付き16ビット除算
			Prog(x86.ACWD) // AXをDX:AXに符号拡張
		}

		// 除算命令の生成
		p := Prog(v.Op.Asm()) // DIVQ, IDIVQ など
		p.From.Type = obj.TYPE_REG
		p.From.Reg = x // 除数レジスタ

		// 符号付き除算の-1チェック後の処理
		if j != nil {
			j2 := Prog(obj.AJMP) // 無条件ジャンプ
			j2.To.Type = obj.TYPE_BRANCH

			n := Prog(x86.ANEGQ) // AXの値を反転 (結果が最小負数になるように)
			n.To.Type = obj.TYPE_REG
			n.To.Reg = x86.REG_AX

			j.To.Val = n  // -1除算の場合、ANEGQにジャンプ
			j2.To.Val = Pc // それ以外の場合、通常のコードパスにジャンプ
		}
	// ... 既存のケース
}

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

このファイルでは、Goの抽象的な操作（`ODIV`）をSSAの中間表現にマッピングし、さらにそのSSA表現から最終的な機械語を生成する部分が変更されています。

1.  **`opToSSA` マップへの追加**:
    *   `opToSSA` マップは、Goのコンパイラフロントエンドが認識する操作コード（`ODIV`）と型（`TINT8`など）の組み合わせを、SSAバックエンドが使用するジェネリックなオペレーション（`ssa.OpDiv8`など）に変換するためのルックアップテーブルです。
    *   このコミットでは、`ODIV`操作が様々な整数型（`int8`, `uint8`, `int16`, `uint16`, `int32`, `uint32`, `int64`, `uint64`）に対して行われる場合に、それぞれ対応する符号付き/符号なしのジェネリック除算オペレーションにマッピングされるようにエントリが追加されました。これにより、Goのソースコード中の整数除算がSSA形式で正しく表現されるようになります。

2.  **`genValue` 関数内のAMD64除算コード生成**:
    *   `genValue` 関数は、SSAの`Value`（中間表現のノード）を受け取り、それに対応するAMD64アセンブリ命令を生成します。
    *   `case ssa.OpAMD64DIVQ, ...` のブロックは、AMD64固有の除算オペレーションを処理します。
    *   **除数`-1`のチェック**: 符号付き除算 (`IDIV`) の場合、被除数が最小負数で除数が`-1`のときにCPU例外が発生するのを防ぐため、除数が`-1`であるかを`CMP`命令でチェックします。もし`-1`であれば、`AJEQ`命令で分岐し、`ANEGQ AX`（`AX`レジスタの値を反転）を実行して結果を調整します。これにより、Goの仕様に沿った正しい結果（最小負数）が得られます。
    *   **被除数の準備**: AMD64の除算命令は、被除数を`AX`（または`DX:AX`）レジスタに期待します。
        *   符号なし除算 (`DIVQU`, `DIVLU`, `DIVWU`) の場合、`DX`レジスタを`XORQ DX, DX`でゼロクリアし、被除数をゼロ拡張します。
        *   符号付き除算 (`DIVQ`, `DIVL`, `DIVW`) の場合、`CQO`, `CDQ`, `CWD`命令を使用して、`AX`レジスタの値を`DX:AX`ペアに符号拡張します。これにより、被除数が正しく設定されます。
    *   **除算命令の生成**: 準備が整った後、`Prog(v.Op.Asm())` を呼び出して、実際のAMD64除算命令（`IDIVQ`, `DIVQ`など）を生成します。除数は`x`レジスタから取得されます。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更点

このファイルは、ジェネリックなSSAオペレーションをAMD64アーキテクチャに特化したオペレーションに変換する「リライトルール」を定義しています。

*   **`OpDiv16`, `OpDiv16u`, `OpDiv32`, `OpDiv32u`, `OpDiv64`, `OpDiv64u` の変換**:
    *   これらのケースでは、対応するジェネリック除算オペレーションを、直接AMD64固有の除算オペレーション（例：`OpDiv16`を`OpAMD64DIVW`）に変換します。これは、これらのビット幅の除算がAMD64で直接サポートされているためです。

*   **`OpDiv8`, `OpDiv8u` の変換**:
    *   AMD64には8ビット整数を直接除算する命令がないため、このケースはより複雑です。
    *   `OpDiv8`（符号付き8ビット除算）は、まず被除数と除数の両方を`OpSignExt8to16`（8ビットから16ビットへの符号拡張）オペレーションを使って16ビットに拡張します。その後、`OpAMD64DIVW`（16ビット符号付き除算）に変換します。
    *   `OpDiv8u`（符号なし8ビット除算）は、同様に`OpZeroExt8to16`（8ビットから16ビットへのゼロ拡張）オペレーションを使って16ビットに拡張し、`OpAMD64DIVWU`（16ビット符号なし除算）に変換します。
    *   この処理は、ハードウェアの制約を考慮しつつ、正確な結果を得るために不可欠です。

これらの変更は、GoコンパイラがGo言語の整数除算セマンティクスを、AMD64プロセッサの低レベルな命令セットとレジスタの制約に適合させながら、効率的かつ正確に実装するための重要なステップです。

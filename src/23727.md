## 元コミット内容

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal/ssa` において、「単一のライブなメモリ値（single live mem）」の制約を強制する変更を導入します。これは、SSA形式のコードにおいて、ある時点で使用可能なメモリの状態を表す値が常に一つだけであることを保証するためのものです。この制約は、メモリのロード（読み込み）操作が、そのロード元となるメモリ値の次のストア（書き込み）操作よりも前に出現するように強制することで実現されます。このような「アンチ依存性（anti-dependence）」は、SSA形式では明示的に記録されないため、スケジューラがこれを考慮するように修正されています。

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムをSSA形式に変換し、様々な最適化を適用した後に、最終的な機械語コードを生成します。SSA形式では、各変数が一度だけ代入されるため、データフロー解析が容易になります。しかし、メモリ操作（ロードとストア）は特殊な扱いです。メモリ全体は一つの大きな「変数」と見なすことができ、その状態はメモリ操作によって変化します。

従来のSSA形式では、メモリ操作間の順序依存性（例えば、ストアの後にロードが来るべき、など）は明示的に表現されますが、アンチ依存性（例えば、ロードがそのロード元となるメモリの次のストアより前に来るべき）は直接表現されません。これは、SSAが値の定義と使用に焦点を当てているためです。

「単一のライブなメモリ値」という制約は、コンパイラがメモリ操作の順序を正しく決定し、不正確な最適化を防ぐために非常に重要です。もし複数の「ライブな」メモリ値が存在すると、コンパイラはどのメモリ状態が最新であるかを判断できなくなり、誤ったロードやストアの順序付けを行ってしまう可能性があります。特に、ロード操作が、そのロード元となるメモリの次のストア操作の後にスケジュールされてしまうと、古いメモリ値が読み込まれるか、あるいはまだ書き込まれていない値が読み込まれるといった、不正な動作を引き起こす可能性があります。

このコミットの目的は、SSAスケジューラがこの「単一のライブなメモリ値」の制約を強制するように修正することで、メモリ操作の正確な順序付けを保証し、コンパイラの堅牢性を高めることにあります。これにより、よりアグレッシブな最適化が可能になり、生成されるコードの品質が向上することが期待されます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化フェーズで広く用いられる中間表現（IR）の一種です。その主要な特性は以下の通りです。

*   **単一代入**: 各変数はプログラム中で一度だけ代入されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が大幅に簡素化されます。
*   **Φ関数 (Phi function)**: 制御フローグラフ（CFG）の複数のパスが合流する点（支配フロンティア）で、異なるパスから来る同じ論理変数に対応する複数のSSA変数を結合するために使用されます。例えば、`x = Φ(x1, x2)` は、`x1` と `x2` のどちらかの値が `x` に代入されることを意味します。
*   **メモリの表現**: メモリ全体は、SSA形式では特殊な「メモリ値」として扱われることがあります。メモリへの書き込み（ストア）は新しいメモリ値を生成し、メモリからの読み込み（ロード）はそのメモリ値を使用します。これにより、メモリ操作もデータフローの一部として扱えるようになります。

### 2. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現に変換します。Go 1.7以降、コンパイラのバックエンドはSSA形式を使用しており、これにより多くの最適化が可能になりました。SSAバックエンドは、以下の主要なフェーズで構成されます。

*   **SSA生成**: ASTからSSA形式のIRを生成します。
*   **最適化**: 共通部分式の削除、定数畳み込み、デッドコード削除など、様々なSSAベースの最適化を適用します。
*   **スケジューリング**: 最適化されたSSA形式の命令を、ターゲットアーキテクチャの制約（レジスタの利用可能性、命令のレイテンシなど）を考慮して、実行順序を決定します。
*   **機械語コード生成**: スケジュールされた命令から最終的な機械語コードを生成します。

このコミットは、特に「スケジューリング」フェーズに影響を与えます。

### 3. メモリ操作のスケジューリングと「単一のライブなメモリ値」

コンパイラにおける命令スケジューリングは、プログラムのセマンティクス（意味）を維持しつつ、実行性能を最大化するために命令の実行順序を並べ替えるプロセスです。メモリ操作（ロードとストア）のスケジューリングは特に複雑です。

*   **データ依存性**: ある命令の結果が別の命令の入力として使われる場合、それらの間にはデータ依存性があります。例えば、`x = a + b` の後に `y = x * c` が続く場合、`y` は `x` にデータ依存します。
*   **メモリ依存性**: メモリ操作間にも依存性があります。
    *   **Read-After-Write (RAW)**: ストアの後にロードが来る場合。ストアされた値がロードされるべきです。
    *   **Write-After-Read (WAR)**: ロードの後にストアが来る場合。ロードはストアされる前の値を読むべきです。
    *   **Write-After-Write (WAW)**: ストアの後に別のストアが来る場合。後のストアが最終的な値を決定すべきです。
*   **アンチ依存性 (Anti-dependence)**: WAR依存性の一種で、ある命令が読み込む値が、その後に別の命令によって書き換えられる場合を指します。SSA形式では、変数の単一代入特性により、通常の変数に対するWAR依存性は解消されますが、メモリ全体を一つのSSA値として扱う場合、メモリのロードとストアの間には依然としてアンチ依存性が存在し得ます。具体的には、あるロード操作が、そのロード元となるメモリ値の次のストア操作よりも前に実行されなければならない、という制約です。

「単一のライブなメモリ値」とは、あるプログラムポイントにおいて、有効なメモリの状態を表すSSA値がただ一つだけ存在するという概念です。これにより、コンパイラは常に最新のメモリ状態を追跡でき、メモリ操作の順序付けを正確に行うことができます。この制約が破られると、コンパイラはどのメモリ値が「最新」であるかを判断できなくなり、誤ったコードを生成する可能性があります。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/schedule.go` 内の `schedule` 関数に修正を加えています。`schedule` 関数は、各基本ブロック内のSSA値をトポロジカルソートして実行順序を決定する役割を担っています。

変更の核心は、メモリのロード操作とストア操作の間に「アンチ依存性」を明示的に導入し、スケジューラがこれを考慮するようにすることです。

1.  **`nextMem` 配列の導入**:
    *   `nextMem := make([]*Value, f.NumValues())` という新しい配列が導入されます。
    *   この配列は、各メモリSSA値 `w` に対して、そのメモリ値 `w` の「次」にライブになるメモリSSA値 `v` をマッピングします。つまり、`nextMem[w.ID]` は、`w` の後に発生するメモリ操作によって生成される新しいメモリ値を示します。
    *   各ブロックの処理の最初に、この `nextMem` 配列が更新されます。ブロック内の各値 `v` がメモリ型である場合、その引数 `w`（これもメモリ型）に対して `nextMem[w.ID] = v` が設定されます。これにより、ブロック内でのメモリ値の連鎖が確立されます。

2.  **`additionalEdges` 配列の導入**:
    *   `additionalEdges := make([][]*Value, f.NumValues())` という別の配列が導入されます。
    *   これは、通常のデータフロー依存性グラフには存在しない、追加の依存性（アンチ依存性）を表現するために使用されます。
    *   各ブロック内で、メモリ型ではない値 `v`（例えば、ロード操作の結果を使用する演算）が、メモリ型引数 `w` を持つ場合を考えます。もし `nextMem[w.ID]` が存在し、それが現在のブロック `b` 内のメモリ値 `n` であるならば、`additionalEdges[n.ID]` に `v` が追加されます。
    *   これは、「ロード操作 `v` が使用するメモリ値 `w` の次に発生するメモリ値 `n` が、現在のブロック内にある場合、`v` は `n` よりも前にスケジュールされなければならない」というアンチ依存性を表現しています。つまり、`n` が生成される前に `v` が完了している必要があります。

3.  **トポロジカルソートへの組み込み**:
    *   `schedule` 関数は、深さ優先探索（DFS）ベースのトポロジカルソートアルゴリズムを使用して、ブロック内の値を順序付けます。
    *   DFSの `queue` に値を追加する際に、通常の引数依存性に加えて、`additionalEdges` に記録された依存性も考慮されるようになります。具体的には、`v` が `expanded` 状態になった後（つまり、`v` のすべての引数が処理された後）、`additionalEdges[v.ID]` に含まれるすべての値 `w` も `queue` に追加され、処理されるようになります。これにより、`v` が `w` の前にスケジュールされることが保証されます。

### `schedule_test.go` の変更

新しいテストファイル `schedule_test.go` が追加され、`TestSchedule` 関数とヘルパー関数 `isSingleLiveMem` が導入されています。

*   **`TestSchedule`**:
    *   特定のSSAグラフ構造を持つテストケースを定義しています。このテストケースは、複数のストア操作とロード操作が混在するシナリオをシミュレートしています。
    *   `schedule(c.f)` を呼び出して、新しいスケジューラロジックを適用します。
    *   `isSingleLiveMem(c.f)` を呼び出して、スケジューリング後に「単一のライブなメモリ値」の制約が実際に強制されているかを確認します。もし制約が破られていれば、テストは失敗します。

*   **`isSingleLiveMem`**:
    *   このヘルパー関数は、与えられたSSA関数 `f` の各ブロックをイテレートし、各プログラムポイントで「ライブなメモリ値」が一つだけであることを検証します。
    *   `liveMem` という変数を追跡し、メモリ型の引数 `w` が現れたときに、それが現在の `liveMem` と同じであるかを確認します。もし異なる `liveMem` が現れた場合、制約が破られていると判断し `false` を返します。
    *   メモリ型の値 `v` が現れた場合、`liveMem` をその `v` に更新します。

これらの変更により、GoコンパイラのSSAバックエンドは、メモリ操作の順序付けに関してより正確で堅牢な動作をするようになります。

## コアとなるコードの変更箇所

`src/cmd/compile/internal/ssa/schedule.go` ファイルにおいて、以下の主要な変更が行われています。

1.  **新しい変数の宣言**:
    ```go
    	nextMem := make([]*Value, f.NumValues()) // maps mem values to the next live value
    	additionalEdges := make([][]*Value, f.NumValues())
    ```
2.  **`nextMem` の設定ロジック**: 各ブロックのループ内で、メモリ値の連鎖を確立します。
    ```go
    	// Set the nextMem values for this block.  If the previous
    	// write is from a different block, then its nextMem entry
    	// might have already been set during processing of an earlier
    	// block.  This loop resets the nextMem entries to be correct
    	// for this block.
    	for _, v := range b.Values {
    		if v.Type.IsMemory() {
    			for _, w := range v.Args {
    				if w.Type.IsMemory() {
    					nextMem[w.ID] = v
    				}
    			}
    		}
    	}
    ```
3.  **`additionalEdges` の設定ロジック**: ロード操作と次のストア操作の間のアンチ依存性を追加します。
    ```go
    	// Add a anti-dependency between each load v and the memory value n
    	// following the memory value that v loads from.
    	// This will enforce the single-live-mem restriction.
    	for _, v := range b.Values {
    		if v.Type.IsMemory() {
    			continue
    		}
    		for _, w := range v.Args {
    			if w.Type.IsMemory() && nextMem[w.ID] != nil {
    				// Filter for intra-block edges.
    				if n := nextMem[w.ID]; n.Block == b {
    					additionalEdges[n.ID] = append(additionalEdges[n.ID], v)
    				}
    			}
    		}
    	}
    ```
4.  **トポロジカルソートにおける `additionalEdges` の利用**: DFSの `expanded` ステートで追加の依存性を処理します。
    ```go
    					for _, w := range additionalEdges[v.ID] {
    						if w.Block == b && w.Op != OpPhi && state[w.ID] == unmarked {
    							state[w.ID] = found
    							queue = append(queue, w)
    						}
    					}
    ```
5.  **コメントの更新**: `TODO` コメントが更新され、メモリに関する制約が解決されたことが示されています。

`src/cmd/compile/internal/ssa/schedule_test.go` ファイルは新規追加されており、`TestSchedule` と `isSingleLiveMem` 関数が含まれています。

## コアとなるコードの解説

### `schedule.go` の変更点

1.  **`nextMem` と `additionalEdges` の初期化**:
    *   `nextMem` は、メモリSSA値のIDをインデックスとして、そのメモリ値の「次」に生成されるメモリSSA値を格納します。これにより、メモリ操作の連鎖を追跡できます。
    *   `additionalEdges` は、メモリSSA値のIDをインデックスとして、そのメモリSSA値にアンチ依存する（つまり、そのメモリSSA値が生成される前に完了しなければならない）非メモリSSA値のリストを格納します。

2.  **ブロックごとの `nextMem` の構築**:
    *   各基本ブロック `b` の処理の開始時に、`b.Values` を走査します。
    *   もし値 `v` がメモリ型 (`v.Type.IsMemory()`) であれば、その引数 `w` の中にメモリ型があれば、`nextMem[w.ID] = v` と設定します。これは、`w` のメモリ状態が `v` によって更新されることを意味します。このループは、ブロック内のメモリ操作の順序を反映して `nextMem` を構築します。

3.  **ブロックごとの `additionalEdges` の構築**:
    *   次に、再度 `b.Values` を走査します。
    *   もし値 `v` がメモリ型でなければ（例えば、`OpLoad` や他の演算）、その引数 `w` を調べます。
    *   もし `w` がメモリ型であり、かつ `nextMem[w.ID]` が存在する場合、これは `w` のメモリ状態が `nextMem[w.ID]` によって更新されることを意味します。
    *   さらに、`nextMem[w.ID]` が現在のブロック `b` 内の値 `n` である場合、`additionalEdges[n.ID]` に `v` を追加します。
    *   この `additionalEdges` は、`v`（ロード操作など）が `w` のメモリ状態を使用し、その `w` のメモリ状態が `n` によって更新されるという状況を表します。したがって、`v` は `n` が発生する前にスケジュールされる必要があります。これが「アンチ依存性」です。

4.  **トポロジカルソートの修正**:
    *   `schedule` 関数内のトポロジカルソートは、DFSを使用して `queue` に値を積み、`order` に結果を格納します。
    *   値 `v` が `expanded` 状態（つまり、`v` のすべての通常の引数が処理され、`v` 自体が `order` に追加される準備ができた状態）になったとき、`additionalEdges[v.ID]` に含まれるすべての値 `w` も `queue` に追加されます。
    *   これにより、`v` が `additionalEdges` を介して依存するすべての値 `w` が、`v` よりも前に処理されることが保証されます。これは、`v` が `n` にアンチ依存する場合、`v` が `n` の前にスケジュールされることを意味します。

### `schedule_test.go` の新規追加

*   `TestSchedule` は、`OpStore` と `OpLoad` が混在する具体的なSSAグラフを構築します。このグラフは、メモリ操作の順序が重要となる典型的なシナリオを表現しています。
*   `isSingleLiveMem` は、スケジューリング後のSSAグラフを検証するための重要な関数です。この関数は、各ブロックを順に処理し、`liveMem` という変数を更新しながら、常に「単一のライブなメモリ値」が存在するかどうかをチェックします。もし、ある時点で複数の異なるメモリ値が同時に「ライブ」であると判断された場合、この関数は `false` を返し、テストを失敗させます。これにより、スケジューラが正しくアンチ依存性を処理し、メモリの一貫性を維持していることが検証されます。

これらの変更は、GoコンパイラのSSAバックエンドがメモリ操作をより正確に扱い、結果としてより信頼性の高い最適化されたコードを生成するための基盤を強化します。

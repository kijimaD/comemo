# [インデックス 25073] ファイルの概要

このコミットは、Go言語のアセンブラツール `cmd/asm` における、ネストされた `#define` マクロ定義が引き起こすパニック（クラッシュ）を修正するものです。特に、`go-fuzz` ツールによって発見された、以前は「不可能」とされていた条件が実際には発生しうるという問題に対処しています。

## コミット

cmd/asm: fix crash triggered by nested #define

A panic was in place for an impossible condition that turned
out to be possible if one used a macro to define a macro.

Another go-fuzz "win".

## 変更の背景

この変更は、Go言語のアセンブラ `cmd/asm` が、ネストされた `#define` ディレクティブを処理する際に発生するパニックを修正するために行われました。具体的には、マクロ定義の内部でさらに別のマクロを定義するようなケース（例: `#define A #define B ...`）が問題を引き起こしていました。

`cmd/asm` の字句解析器 (`lex` パッケージ) 内の `Slice.Col()` メソッドは、以前は「到達不可能」と見なされるべき状況でのみ呼び出されると想定されており、その場合に `panic("cannot happen: slice col")` を発生させるようになっていました。しかし、`go-fuzz` というファジングツールが、この「不可能」な条件がネストされたマクロ定義によって実際に発生しうることを発見しました。

このパニックは、アセンブラが予期せぬ入力（この場合は特定の形式のネストされたマクロ）に遭遇した際にクラッシュすることを意味し、堅牢性の欠如を示していました。そのため、このパニックを回避し、より適切に処理するための修正が必要となりました。

## 前提知識の解説

### Go言語のアセンブラ (`cmd/asm`)

`cmd/asm` は、Go言語のツールチェーンの一部であり、Goプログラムが利用するアセンブリコードを処理するためのアセンブラです。Go言語自体は高水準言語ですが、パフォーマンスが重要な部分や特定のハードウェア機能を利用する際には、アセンブリコードが使用されることがあります。`cmd/asm` は、これらのアセンブリソースファイルを機械語に変換する役割を担います。

### プリプロセッサディレクティブ (`#define`)

`#define` は、C言語などのプリプロセッサで広く使われるディレクティブで、マクロを定義するために使用されます。マクロは、コード内の特定の文字列を別の文字列に置き換える機能を提供し、定数の定義や簡単な関数のような振る舞いを実現するのに役立ちます。`cmd/asm` も、アセンブリコード内で同様の目的で `#define` をサポートしています。

*   **オブジェクト形式マクロ**: `#define NAME value` のように、名前を値に置き換える。
*   **関数形式マクロ**: `#define NAME(arg1, arg2) replacement_text` のように、引数を受け取り、それらを展開して置き換える。

### ネストされたマクロ定義

ネストされたマクロ定義とは、あるマクロの定義内容の中に、さらに別のマクロ定義（`#define` ディレクティブ）が含まれる形式を指します。例えば、`#define A #define B THIS` のようなケースです。これは一般的なプログラミングではあまり推奨されませんが、特定の複雑なプリプロセッサ処理で発生する可能性があります。`cmd/asm` の字句解析器は、このようなネストされた構造を適切に処理する必要がありました。

### `go-fuzz`

`go-fuzz` は、Go言語で書かれたプログラムのバグを発見するために設計されたファジングツールです。ファジングとは、プログラムに大量のランダムまたは半ランダムな入力を与え、クラッシュ、アサーション失敗、メモリリークなどの異常な動作を検出するテスト手法です。`go-fuzz` は、特にセキュリティ脆弱性や予期せぬエッジケースの発見に非常に効果的であり、Go言語の標準ライブラリやツールチェーンの堅牢性向上に大きく貢献しています。このコミットのケースも、`go-fuzz` が発見したバグの一例です。

### `panic`

Go言語における `panic` は、プログラムの実行を停止させる回復不能なエラーを示します。通常、プログラムが続行できないような深刻な問題（例: nilポインタのデリファレンス、配列の範囲外アクセス）が発生した場合に発生します。開発者は、`panic` が発生しないようにコードを設計するか、`recover` を使用して `panic` から回復することを検討します。このコミットでは、`panic` が発生するべきではないとされていた状況で発生したため、その原因を取り除くことが目的でした。

### `text/scanner`

`text/scanner` はGo言語の標準ライブラリ `text` パッケージの一部で、テキストの字句解析（トークン化）を行うための汎用的なスキャナーを提供します。これは、コンパイラやインタプリタ、その他のテキスト処理ツールで、入力文字列を意味のある単位（トークン）に分割するために使用されます。`cmd/asm` の字句解析器も、この `text/scanner` を利用して入力アセンブリコードを解析しています。

## 技術的詳細

この問題の核心は、`cmd/asm` の字句解析器がマクロ定義を処理する際の `Slice.Col()` メソッドの挙動にありました。

1.  **`Slice.Col()` の役割と以前の挙動**:
    `Slice` 構造体は、字句解析中の現在の位置（行番号、列番号）を管理しています。`Col()` メソッドは現在の列番号を返します。以前の実装では、`Slice.Col()` はマクロ定義時のみに呼び出されると想定されており、その際に「括弧の前に空白があるかどうか」を検出するために位置を増やすことだけを気にしている、とコメントされていました。しかし、コードは `panic("cannot happen: slice col")` となっており、このメソッドが呼び出されること自体が「ありえない」と見なされていました。

2.  **ネストされた `#define` による「不可能」の打破**:
    `go-fuzz` が発見したのは、`#define A #define B THIS` のように、マクロ定義の内部に別の `#define` が含まれる場合、`Slice.Col()` が呼び出される状況が発生しうるということでした。これは、字句解析器がマクロ展開中に再帰的にマクロ定義を処理しようとした際に、予期せぬパスで `Slice.Col()` が呼び出されたためと考えられます。この「ありえない」はずの呼び出しによって、プログラムはパニックを起こしクラッシュしていました。

3.  **修正の内容**:
    修正は非常にシンプルで、`Slice.Col()` メソッド内の `panic` ステートメントを `return s.pos` に置き換えるというものです。`s.pos` は `Slice` 構造体内の現在の位置（オフセット）を表します。これにより、`Slice.Col()` が呼び出されてもパニックすることなく、現在の位置を返すようになります。

4.  **「完璧ではない実装」のトレードオフ**:
    新しい `Slice.Col()` の実装には、コメントで「完璧ではない」という注意書きが追加されています。
    ```go
    // This imperfect implementation means we cannot tell the difference between
    //  #define A #define B(x) x
    // and
    //  #define A #define B (x) x
    // The first has definition of B has an argument, the second doesn't. Because we let
    // text/scanner strip the blanks for us, this is extremely rare, hard to fix, and not worth it.
    ```
    これは、`text/scanner` が空白文字を剥ぎ取ってしまうため、`#define B(x) x`（引数を持つマクロB）と `#define B (x) x`（引数を持たないマクロBで、`(x)` が定義の一部と見なされる）という2つの異なるマクロ定義を区別できない可能性があることを示しています。
    この区別は、マクロが引数を持つかどうかを判断する上で重要ですが、ネストされたマクロ定義のコンテキストでは、この問題は「極めて稀で、修正が困難であり、それだけの価値がない」と判断されました。つまり、クラッシュを回避することを優先し、この稀なケースでの字句解析のわずかな不正確さは許容するというトレードオフがなされています。

5.  **テストケースの追加**:
    この修正を検証するために、`lex_test.go` にネストされた `#define` を含む新しいテストケースが追加されました。これにより、将来的に同様の問題が再発しないように、回帰テストが強化されました。

## コアとなるコードの解説

### `lex_test.go` の変更

追加されたテストケースは、ネストされた `#define` のシナリオを具体的に示しています。

*   **`"nested #define"`**:
    ```
    #define A #define B THIS
    A
    B
    ```
    このテストは、マクロ `A` が展開されると `#define B THIS` となり、その後に `B` が展開されて最終的に `THIS` が出力されることを期待しています。これは、マクロ定義の内部で別のマクロ定義が行われるという、まさにこのコミットが修正しようとしている問題の核心を突くケースです。

*   **`"nested #define with args"`**:
    ```
    #define A #define B(x) x
    A
    B(THIS)
    ```
    このテストは、ネストされたマクロが引数を持つ場合を扱っています。`A` が展開されて `#define B(x) x` となり、その後に `B(THIS)` が展開されて `THIS` が出力されることを期待します。

*   **コメントアウトされたテストケース**:
    ```
    /* This one fails. See comment in Slice.Col.
    {
        "nested #define with args",
        lines(
            "#define A #define B (x) x",
            "A",
            "B(THIS)",
        ),
        "x.\n",
    },
    */
    ```
    このコメントアウトされたテストケースは、`Slice.Col()` の新しいコメントで説明されている「完璧ではない実装」の限界を示しています。`#define B (x) x` のように、マクロ名と括弧の間に空白がある場合、`text/scanner` が空白を剥ぎ取ってしまうため、`B` が引数を持つマクロとして正しく認識されない可能性があります。このテストは、その挙動が期待通りにならないことを示唆しており、現在の実装ではこのエッジケースは許容されていることを明確にしています。

これらのテストケースは、`cmd/asm` の字句解析器がネストされたマクロ定義を正しく処理できるようになったことを検証し、将来的な回帰を防ぐための重要な役割を果たします。

### `slice.go` の `Slice.Col()` の変更

`Slice.Col()` メソッドの変更は、このコミットの機能的な修正の核心です。

以前のコード:
```go
func (s *Slice) Col() int {
	// Col is only called when defining a macro, which can't reach here.
	panic("cannot happen: slice col")
}
```
このコードは、`Slice.Col()` が呼び出されることは「ありえない」という前提に基づいていました。しかし、`go-fuzz` がネストされたマクロ定義のシナリオでこの前提が崩れることを発見しました。

新しいコード:
```go
func (s *Slice) Col() int {
	// TODO: Col is only called when defining a macro and all it cares about is increasing
	// position to discover whether there is a blank before the parenthesis.
	// We only get here if defining a macro inside a macro.
	// This imperfect implementation means we cannot tell the difference between
	//	#define A #define B(x) x
	// and
	//	#define A #define B (x) x
	// The first has definition of B has an argument, the second doesn't. Because we let
	// text/scanner strip the blanks for us, this is extremely rare, hard to fix, and not worth it.
	return s.pos
}
```
`panic` を `return s.pos` に置き換えることで、`Slice.Col()` が呼び出されてもプログラムがクラッシュしなくなりました。代わりに、現在の字句解析位置（オフセット）を返します。これは、マクロ定義のコンテキストで列情報が必要とされる場合に、少なくとも有効な（ただし必ずしも意味的に正確ではない）値を返すことで、プログラムの実行を継続させます。

`TODO` コメントは、この修正が完全な解決策ではないことを認めています。特に、`#define B(x) x` と `#define B (x) x` のような、マクロ名と括弧の間の空白の有無によって引数の有無を区別するような微妙なケースを `text/scanner` が処理できないため、この区別が失われる可能性があることを指摘しています。しかし、この問題は非常に稀であり、修正の複雑さと比較してその価値が低いと判断され、クラッシュ回避を優先した実用的な解決策が採用されました。

この変更により、`cmd/asm` はネストされたマクロ定義を含むアセンブリコードに対しても、より堅牢に動作するようになりました。

# [インデックス 27064] ファイルの概要

このコミットは、Goリンカにおけるデッドコードエリミネーション（DCE）戦略を改善し、特に未使用のメソッドを削除することで生成されるバイナリのサイズを大幅に削減することを目的としています。Goプログラムでリフレクション（`reflect.Value.Call`）が使用されていない場合、リンカは到達可能な型のすべてのメソッドを保持する必要がなくなります。この変更により、リンカはより積極的なメソッドプルーニング（枝刈り）を実行できるようになり、結果としてバイナリサイズが最大20%削減される可能性があります。

## コミット

```
cmd/link: prune unused methods

Today the linker keeps all methods of reachable types. This is
necessary if a program uses reflect.Value.Call. But while use of
reflection is widespread in Go for encoders and decoders, using
it to call a method is rare.

This CL looks for the use of reflect.Value.Call in a program, and
if it is absent, adopts a (reasonably conservative) method pruning
strategy as part of dead code elimination. Any method that is
directly called is kept, and any method that matches a used
interface's method signature is kept.

Whether or not a method body is kept is determined by the relocation
from its receiver's *rtype to its *rtype. A small change in the
compiler marks these relocations as R_METHOD so they can be easily
collected and manipulated by the linker.

As a bonus, this technique removes the text segment of methods that
have been inlined. Looking at the output of building cmd/objdump with
-ldflags=-v=2 shows that inlined methods like
runtime.(*traceAllocBlockPtr).ptr are removed from the program.

Relatively little work is necessary to do this. Linking two
examples, jujud and cmd/objdump show no more than +2% link time.

Binaries that do not use reflect.Call.Value drop 4 - 20% in size:

        addr2line: -793KB (18%)
        asm:       -346KB (8%)
        cgo:       -490KB (10%)
        compile:   -564KB (4%)
        dist:      -736KB (17%)
        fix:       -404KB (12%)
        link:      -328KB (7%)
        nm:        -827KB (19%)
        objdump:   -712KB (16%)
        pack:      -327KB (14%)
        yacc:      -350KB (10%)

Binaries that do use reflect.Call.Value see a modest size decrease
of 2 - 6% thanks to pruning of unexported methods:

        api:    -151KB (3%)
        cover:  -222KB (4%)
        doc:    -106KB (2.5%)
        pprof:  -314KB (3%)
        trace:  -357KB (4%)
        vet:    -187KB (2.7%)
        jujud:  -4.4MB (5.8%)
        cmd/go: -384KB (3.4%)

The trivial Hello example program goes from 2MB to 1.68MB:

        package main

        import "fmt"

        func main() {
                fmt.Println("Hello, 世界")
        }

Method pruning also helps when building small binaries with
"-ldflags=-s -w". The above program goes from 1.43MB to 1.2MB.

Unfortunately the linker can only tell if reflect.Value.Call has been
statically linked, not if it is dynamically used. And while use is
rare, it is linked into a very common standard library package,
text/template. The result is programs like cmd/go, which don't use
reflect.Value.Call, see limited benefit from this CL. If binary size
is important enough it may be possible to address this in future work.

For #6853.
```

## 変更の背景

Goのリンカはこれまで、到達可能な型に属するすべてのメソッドを、たとえ直接呼び出されていなくても最終的なバイナリに含めていました。これは、`reflect.Value.Call` のようなリフレクション機能が実行時に任意のメソッドを呼び出す可能性があるため、安全策として必要とされていました。しかし、Goではエンコーダやデコーダでリフレクションが広く使われている一方で、`reflect.Value.Call` を使ってメソッドを呼び出すケースは比較的稀です。

この「過剰なメソッドの保持」は、特に`reflect.Value.Call`を使用しないプログラムにおいて、バイナリサイズを不必要に増大させる原因となっていました。開発者は、より小さなバイナリを生成したいというニーズを持っており、デッドコードエリミネーションの改善が求められていました。このコミットは、この問題に対処し、`reflect.Value.Call`が使用されていない場合に、より積極的なメソッドプルーニング戦略を導入することで、バイナリサイズを削減することを目的としています。

## 前提知識の解説

### Goのリンカ (Go linker)
Goのリンカ（`cmd/link`）は、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、実行可能なバイナリを生成するツールです。リンカの主要な役割の一つに、デッドコードエリミネーション（DCE）があります。

### デッドコードエリミネーション (Dead Code Elimination - DCE)
デッドコードエリミネーションとは、プログラムの実行に影響を与えない、つまり決して実行されないコード（デッドコード）を最終的なバイナリから削除する最適化手法です。これにより、バイナリサイズが削減され、ロード時間やメモリ使用量が改善されます。Goのリンカは、プログラムのエントリポイント（`main.main`など）から到達可能なシンボル（関数、変数など）を追跡し、到達不可能なシンボルをデッドコードとして削除します。

### Goにおけるリフレクション (`reflect.Value.Call`)
Goのリフレクション機能は、プログラムの実行中に型情報を検査したり、値の操作を行ったりする機能です。`reflect.Value.Call`メソッドは、`reflect.Value`型の値が表す関数やメソッドを動的に呼び出すために使用されます。この機能は非常に強力ですが、リンカにとっては課題となります。なぜなら、`reflect.Value.Call`がプログラム内で使用されている場合、リンカはどのメソッドが実行時に呼び出されるかを静的に判断できないため、安全のためにすべてのメソッドを保持する必要があるからです。

### `*rtype` とメソッドの関連性
Goのランタイムは、プログラム内のすべての型に関する情報を `_type` 構造体（Goのソースコードでは `rtype` と呼ばれることが多い）として保持しています。この `rtype` には、その型が持つメソッドに関する情報も含まれています。リンカは、これらの `rtype` シンボルとメソッドの間のリロケーション（再配置情報）を利用して、どのメソッドがどの型に属するかを把握します。

### `R_METHOD` リロケーション
リロケーションとは、リンカが最終的なアドレスを決定するために必要な情報です。例えば、ある関数が別の関数を呼び出す場合、呼び出し元のコードには呼び出し先の関数のアドレスへのリロケーション情報が含まれます。
このコミットでは、コンパイラが特定のメソッド関連のリロケーションを `R_METHOD` という新しいタイプでマークするように変更されています。これにより、リンカは通常のコード参照とは異なる方法でメソッドのリロケーションを識別し、操作できるようになります。

### インターフェースとメソッドのディスパッチ
Goのインターフェースは、型が特定のメソッドセットを実装していることを保証する抽象的な型です。インターフェースを介してメソッドが呼び出される場合、実行時に適切な具象型のメソッドがディスパッチされます。リンカは、到達可能なインターフェース型が要求するメソッドシグネチャを把握し、それらのシグネチャに一致するすべてのメソッドを保持する必要があります。これは、どの具象型がインターフェースを満たすか、そしてそのメソッドが実際に呼び出されるかを静的に完全に特定することが困難なため、保守的なアプローチが取られます。

## 技術的詳細

このコミットは、Goリンカのデッドコードエリミネーションプロセスに、メソッドプルーニングの新しい戦略を導入します。

1.  **`reflect.Value.Call` の検出**: リンカはまず、プログラム内で `reflect.Value.Call` シンボルが到達可能かどうかをチェックします。
    *   もし `reflect.Value.Call` が到達可能であれば、リンカは保守的なアプローチに戻り、到達可能な型のすべてのエクスポートされたメソッドを到達可能とマークします。これは、リフレクションによって任意のメソッドが呼び出される可能性があるためです。
    *   もし `reflect.Value.Call` が到達可能でなければ、リンカはより積極的なメソッドプルーニング戦略を採用します。

2.  **メソッドの到達可能性の判断**: メソッドの到達可能性は、以下の3つのケースに基づいて判断されます。
    *   **直接呼び出し**: プログラムコードから直接呼び出されるメソッドは、通常のデッドコードエリミネーションのフロー（シンボルの到達可能性の洪水充填アルゴリズム）によって到達可能とマークされます。
    *   **インターフェースを介した呼び出し**: 到達可能なインターフェース型が持つメソッドシグネチャに一致するすべてのメソッドは、到達可能とマークされます。これは、インターフェースを介してどの具象メソッドが呼び出されるかを静的に正確に判断することが難しいため、比較的保守的なアプローチです。
    *   **`reflect.Value.Call` を介した呼び出し**: 前述の通り、このシンボルが到達可能であれば、すべてのエクスポートされたメソッドが保持されます。

3.  **`R_METHOD` リロケーションの導入**:
    *   コンパイラは、レシーバの `*rtype` からそのメソッドへのリロケーションを `R_METHOD` という新しいタイプでマークするように変更されます。
    *   リンカは、この `R_METHOD` リロケーションを特別に扱い、メソッドのテキストセグメントを保持するかどうかを決定します。メソッドが到達可能と判断された場合、`R_METHOD` リロケーションは通常の `R_ADDR` リロケーションに変換され、メソッドのアドレスが埋め込まれます。
    *   メソッドが到達不可能と判断された場合、`R_METHOD` リロケーションは削除され、メソッドのテキストセグメントは最終的なバイナリから除外されます。

4.  **デッドコードエリミネーションのフロー**:
    *   まず、`main.main` などのエントリポイントから始まる通常の洪水充填アルゴリズムで、直接到達可能なシンボルがマークされます。この段階では、メソッドは直接呼び出されない限り無視されます。
    *   次に、`reflect.Value.Call` の到達可能性がチェックされます。
    *   その後、到達可能なインターフェース型から抽出されたメソッドシグネチャに一致するメソッドがマークされます。このプロセスは、新しい型やインターフェースが発見されるたびに繰り返されます。
    *   最終的に、到達可能とマークされなかったすべてのテキストシンボル（メソッドの本体を含む）は、最終的なバイナリから削除されます。

5.  **インライン化されたメソッドへの影響**: この技術は、インライン化されたメソッドのテキストセグメントも削除できるという副次的な効果をもたらします。インライン化されたメソッドは、呼び出し元に展開されるため、元のメソッド本体は不要になりますが、これまではリンカによって保持される可能性がありました。この変更により、不要なインライン化されたメソッドの本体も削除され、さらなるバイナリサイズの削減に貢献します。

6.  **バイナリサイズ削減効果**:
    *   `reflect.Value.Call` を使用しないバイナリでは、4%から20%のサイズ削減が報告されています。例えば、`addr2line` は18%、`nm` は19%削減されています。
    *   `reflect.Value.Call` を使用するバイナリでも、エクスポートされていないメソッドのプルーニングにより、2%から6%の控えめなサイズ削減が見られます。
    *   「Hello, 世界」のような単純なプログラムでも、2MBから1.68MBに削減され、`-ldflags=-s -w` オプションと組み合わせると1.43MBから1.2MBに削減されます。

7.  **制限事項**: リンカは `reflect.Value.Call` が静的にリンクされているかどうかしか判断できず、実行時に実際に使用されるかどうかは判断できません。`text/template` のような一般的な標準ライブラリパッケージが `reflect.Value.Call` をリンクしているため、`cmd/go` のように実際にはリフレクションによるメソッド呼び出しを使用しないプログラムでも、この変更による恩恵が限定的になる場合があります。

```diff
+// deadcode marks all reachable symbols.
+//
+// The basis of the dead code elimination is a flood fill of symbols,
+// following their relocations, begining at INITENTRY.
+//
+// This flood fill is wrapped in logic for pruning unused methods.
+// All methods are mentioned by relocations on their receiver's *rtype.
+// These relocations are specially defined as R_METHOD by the compiler
+// so we can detect and manipulated them here.
+//
+// There are three ways a method of a reachable type can be invoked:
+//
+//	1. direct call
+//	2. through a reachable interface type
+//	3. reflect.Value.Call
+//
+// The first case is handled by the flood fill, a directly called method
+// is marked as reachable.
+//
+// The second case is handled by decomposing all reachable interface
+// types into method signatures. Each encountered method is compared
+// against the interface method signatures, if it matches it is marked
+// as reachable. This is extremely conservative, but easy and correct.
+//
+// The third case is handled by looking to see if reflect.Value.Call is
+// ever marked reachable. If it is, all bets are off and all exported
+// methods of reachable types are marked reachable.
+//
+// Any unreached text symbols are removed from ctxt.Textp.
+func deadcode(ctxt *Link) {
+	if Debug['v'] != 0 {
+		fmt.Fprintf(ctxt.Bso, "%5.2f deadcode\n", obj.Cputime())
+	}
+
+	d := &deadcodepass{
+		ctxt:        ctxt,
+		ifaceMethod: make(map[methodsig]bool),
+	}
+
+	// First, flood fill any symbols directly reachable in the call
+	// graph from INITENTRY. Ignore all methods not directly called.
+	d.init()
+	d.flood()
+
+	callSym := Linkrlookup(ctxt, "reflect.Value.Call", 0)
+	callSymSeen := false
+
+	for {
+		if callSym != nil && callSym.Attr.Reachable() {
+			// Methods are called via reflection. Give up on
+			// static analysis, mark all exported methods of
+			// all reachable types as reachable.
+			callSymSeen = true
+		}
+
+		// Mark all methods that could satisfy a discovered
+		// interface as reachable. We recheck old marked interfaces
+		// as new types (with new methods) may have been discovered
+		// in the last pass.
+		var rem []methodref
+		for _, m := range d.markableMethods {
+			if (callSymSeen && m.isExported()) || d.ifaceMethod[m.m] {
+				d.markMethod(m)
+			} else {
+				rem = append(rem, m)
+			}
+		}
+		d.markableMethods = rem
+
+		if len(d.markQueue) == 0 {
+			// No new work was discovered. Done.
+			break
+		}
+		d.flood()
+	}
+
+	// Remove all remaining unreached R_METHOD relocations.
+	for _, m := range d.markableMethods {
+		d.cleanupReloc(m.r0)
+		d.cleanupReloc(m.r1)
+	}
+
+	if Buildmode != BuildmodeShared {
+		// Keep a typelink if the symbol it points at is being kept.
+		// (When BuildmodeShared, always keep typelinks.)
+		for _, s := range ctxt.Allsym {
+			if strings.HasPrefix(s.Name, "go.typelink.") {
+				s.Attr.Set(AttrReachable, len(s.R) == 1 && s.R[0].Sym.Attr.Reachable())
+			}
+		}
+	}

+		}

+		} else {

+		}
+		last = s
+	}

+		ctxt.Etextp = nil
+	} else {
+		last.Next = nil
+		ctxt.Etextp = last
+	}
+}

+// As it goes, it collects methodref and interface method declarations.
+func (d *deadcodepass) flood() {
+	for len(d.markQueue) > 0 {
+		s := d.markQueue[0]
+		d.markQueue = d.markQueue[1:]
+		if s.Type == obj.STEXT {
+			if Debug['v'] > 1 {
+				fmt.Fprintf(d.ctxt.Bso, "marktext %s\n", s.Name)
+			}
+			for _, a := range s.Autom {
+				d.mark(a.Gotype, s)
+			}
+		}
+
+		if strings.HasPrefix(s.Name, "type.") && s.Name[5] != '.' {
+			if decodetype_kind(s)&kindMask == kindInterface {
+				for _, sig := range decodetype_ifacemethods(s) {
+					if Debug['v'] > 1 {
+						fmt.Fprintf(d.ctxt.Bso, "reached iface method: %s\n", sig)
+					}
+					d.ifaceMethod[sig] = true
+				}
+			}
+		}
+
+		var methods []methodref
+		for i := 0; i < len(s.R); i++ {
+			r := &s.R[i]
+			if r.Sym == nil {
+				continue
+			}
+			if r.Type != obj.R_METHOD {
+				d.mark(r.Sym, s)
+				continue
+			}
+			// Collect rtype pointers to methods for
+			// later processing in deadcode.
+			if len(methods) > 0 {
+				mref := &methods[len(methods)-1]
+				if mref.r1 == nil {
+					mref.r1 = r
+					continue
+				}
+			}
+			methods = append(methods, methodref{src: s, r0: r})
+		}
+		if len(methods) > 0 {
+			// Decode runtime type information for type methods
+			// to help work out which methods can be called
+			// dynamically via interfaces.
+			methodsigs := decodetype_methods(s)
+			if len(methods) != len(methodsigs) {
+				panic(fmt.Sprintf("%q has %d method relocations for %d methods", s.Name, len(methods), len(methodsigs)))
+			}
+			for i, m := range methodsigs {
+				name := string(m)
+				name = name[:strings.Index(name, "(")]
+				if !strings.HasSuffix(methods[i].r0.Sym.Name, name) {
+					panic(fmt.Sprintf("%q relocation for %q does not match method %q", s.Name, methods[i].r0.Sym.Name, name))
+				}
+				methods[i].m = m
+			}
+			d.markableMethods = append(d.markableMethods, methods...)
+		}
+
+		if s.Pcln != nil {
+			for i := 0; i < s.Pcln.Nfuncdata; i++ {
+				d.mark(s.Pcln.Funcdata[i], s)
+			}
+		}
+		d.mark(s.Gotype, s)
+		d.mark(s.Sub, s)
+		d.mark(s.Outer, s)
+	}
+}
```

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/reflect.go` の変更
*   **`dmethodptr` 関数の追加**: この新しい関数は、コンパイラがメソッドのリロケーションを生成する際に使用されます。`obj.R_METHOD` という新しいリロケーションタイプを設定することで、リンカがこのリロケーションを特別に処理できるようにします。
*   **`dextratypeData` での `dmethodptr` の使用**: `dextratypeData` 関数内で、`a.isym` と `a.tsym`（それぞれインターフェースメソッドと型メソッドのシンボル）に対するリロケーション生成が、従来の `dsymptr` から `dmethodptr` に変更されています。これにより、これらのメソッドへのポインタが `R_METHOD` タイプでマークされるようになります。

### `src/cmd/internal/obj/link.go` の変更
*   **`R_METHOD` リロケーションタイプの定義**: `obj` パッケージに `R_METHOD` という新しいリロケーションタイプが追加されています。このコメントには、`R_METHOD` が `*rtype` の `uncommonType` からメソッドへのリンクに使用され、リンカがメソッドのテキストが到達不可能と判断した場合にゼロに設定される可能性があることが明記されています。これは、メソッドプルーニングの核心となる部分です。

### `src/cmd/link/internal/ld/deadcode.go` (新規ファイル)
このファイルは、新しいデッドコードエリミネーションロジック、特にメソッドプルーニング戦略を実装しています。
*   **`deadcode(ctxt *Link)` 関数**: 新しいデッドコードエリミネーションのメインエントリポイントです。
    *   `deadcodepass` 構造体を初期化し、`ifaceMethod` (到達可能なインターフェースメソッドのシグネチャを保持) と `markableMethods` (到達可能な型のメソッド参照を保持) を設定します。
    *   `d.init()` と `d.flood()` を呼び出し、まず直接到達可能なシンボルをマークします。この初期フェーズでは、メソッドは直接呼び出されない限り無視されます。
    *   `reflect.Value.Call` シンボルが到達可能かどうかをチェックします。もし到達可能であれば、`callSymSeen` フラグを立て、すべてのエクスポートされたメソッドを保持する保守的なモードに切り替えます。
    *   ループ内で、`d.markableMethods` に格納されているメソッド参照を反復処理します。
        *   もし `reflect.Value.Call` が使用されている場合、またはメソッドが到達可能なインターフェースのシグネチャに一致する場合、`d.markMethod(m)` を呼び出してメソッドを到達可能とマークし、その `R_METHOD` リロケーションを `R_ADDR` に変換します。
        *   それ以外の場合、メソッドは `rem` スライスに移動され、次のパスで再評価されるか、最終的に削除されます。
    *   `d.flood()` を再度呼び出し、新しくマークされたシンボルから到達可能なものをさらに探索します。
    *   `d.markQueue` が空になり、新しい作業が発見されなくなったらループを終了します。
    *   残りの到達不可能な `R_METHOD` リロケーションを `d.cleanupReloc` で削除します。
    *   最後に、到達不可能なテキストシンボルを `ctxt.Textp` から削除し、バイナリサイズを削減します。
*   **`methodref` 構造体**: レシーバ型シンボルからそのメソッドへのリロケーション（`r0` と `r1` の2つのリロケーション）を保持します。`m` フィールドにはメソッドシグネチャが格納されます。
*   **`deadcodepass` 構造体**: デッドコードエリミネーションの洪水充填プロセス中の状態を保持します。
    *   `markQueue`: 次のパスで洪水充填するシンボルのキュー。
    *   `ifaceMethod`: 到達可能なインターフェースで宣言されたメソッドのシグネチャのマップ。
    *   `markableMethods`: 到達可能な型のメソッド参照のリスト。
*   **`cleanupReloc(r *Reloc)`**: リロケーションをクリーンアップするヘルパー関数。メソッドが到達可能であれば `R_METHOD` を `R_ADDR` に変更し、到達不可能であればリロケーションを削除します。
*   **`mark(s, parent *LSym)`**: シンボルを到達可能とマークし、`markQueue` に追加します。
*   **`markMethod(m methodref)`**: `methodref` で指定されたメソッドを到達可能とマークし、関連する `R_METHOD` リロケーションを `R_ADDR` に変換します。
*   **`init()`**: `INITENTRY` や `main.main` などの初期エントリポイントシンボルを到達可能とマークします。
*   **`flood()`**: `markQueue` からシンボルを取り出し、そのリロケーションをたどって到達可能なシンボルをマークする洪水充填アルゴリズムを実行します。この関数は、インターフェース型からメソッドシグネチャを抽出し、`R_METHOD` タイプのリロケーションを `markableMethods` に収集する役割も担います。

### `src/cmd/link/internal/ld/decodesym.go` の変更
*   **`methodsig` 型の追加**: メソッドシグネチャを表す `string` エイリアス `methodsig` が追加されました。
*   **`kindArray` から `kindMask` までの定数**: `runtime/typekind.go` と `reflect.Kind` に対応する型定数が追加され、型情報のデコードに使用されます。
*   **`decode_methodsig` 関数の追加**: `runtime.method` および `runtime.imethod` のレイアウトに基づいて、メソッドシグネチャ情報をデコードする汎用関数です。シンボルからメソッド名、引数型、戻り値型を抽出し、`methodsig` 形式の文字列を生成します。
*   **`decodetype_ifacemethods(s *LSym)` 関数の追加**: インターフェース型シンボルから、そのインターフェースが持つメソッドのシグネチャのリストをデコードします。
*   **`decodetype_methods(s *LSym)` 関数の追加**: 具象型シンボルから、その型が持つメソッドのシグネチャのリストをデコードします。
*   **`decodetype_stringptr` の追加と `decodetype_structfieldname` の変更**: シンボルから文字列ポインタをデコードするヘルパー関数が追加され、`decodetype_structfieldname` がこれを利用するように変更されました。これは、メソッドシグネチャのデコードに必要な基盤となります。

### `src/cmd/link/internal/ld/go.go` の変更
*   **古いデッドコードエリミネーションロジックの削除**: `markQueue`, `mark1`, `mark`, `markflood`, `deadcode` といった古いデッドコードエリミネーション関連の関数が削除されました。これらの機能は、新しい `src/cmd/link/internal/ld/deadcode.go` に移動・再実装されました。
*   **`deadcode()` の呼び出しの変更**: `Ldmain` 関数内で、`deadcode()` の呼び出しが `deadcode(Ctxt)` に変更され、新しい `deadcode` 関数がリンカコンテキスト `Ctxt` を引数として受け取るようになりました。

### `src/cmd/link/internal/ld/pobj.go` の変更
*   **`Ldmain` からの古い `mark` 呼び出しの削除**: `Ldmain` 関数から、ARMアーキテクチャ固有の `_sfloat` や `runtime.read_tls_fallback` をマークする古いロジックが削除されました。これらの初期マークは、新しい `deadcode.go` の `init()` 関数に統合されています。
*   **`deadcode(Ctxt)` の呼び出し**: `deadcode()` の呼び出しが `deadcode(Ctxt)` に変更され、新しいデッドコードエリミネーションが使用されるようになりました。

これらの変更により、Goリンカはより洗練されたデッドコードエリミネーション、特にメソッドプルーニングを実行できるようになり、Goバイナリのサイズ削減に大きく貢献します。

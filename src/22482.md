# [インデックス 22482] ファイルの概要

このコミットは、Goランタイムが起動時に環境変数を処理する方法に関するバグを修正します。特に、AndroidのBionic libc環境において、GoランタイムとCライブラリ間で環境変数文字列のメモリが共有されることによって発生する競合状態を解消することを目的としています。この修正により、`syscall.Setenv`が呼び出された際に環境変数データが破損する問題が解決されます。

Some versions of libc, in this case Android's bionic, point environ

Covered by runtime.TestFixedGOROOT on android/arm.

## 変更の背景

この変更は、Goランタイムが起動時に環境変数を初期化する際の問題に対処するために行われました。特に、AndroidのBionic libcを使用するシステムで顕著でした。問題の根源は、GoランタイムとBionic libcが環境変数文字列のメモリを共有していたことにあります。

具体的には、Bionic libcの一部のバージョン（例：`libc_init_common.cpp`の該当箇所）では、`environ`ポインタが直接`envp`メモリ（プログラム起動時にカーネルから渡される環境変数配列）を指していました。一方、Goランタイムも同様に、内部の環境変数スライス`envs []string`を構築する際に、効率化のために`gostringnocopy`関数を使用して、CのメモリをコピーせずにGoの文字列として扱っていました。

この二重のメモリ再利用が問題を引き起こしました。Goプログラム内で`syscall.Setenv`が呼び出され、Cgoを介して`setenv(3)`システムコールが実行されると、Cライブラリは共有されている基盤のメモリを直接変更します。これにより、Goランタイムが保持している環境変数文字列のデータが意図せず変更され、破損するという結果になりました。

コミットメッセージの例では、`GOROOT=/data/local/tmp`が設定された環境で`syscall.Setenv("/os")`を呼び出すと、`runtime.GOROOT()`が誤って`"/os\x00a/local/tmp/goroot"`のような不正な値になることが示されています。これは、`"/os"`が元の`GOROOT`文字列の一部を上書きし、ヌル文字（`\x00`）が途中に挿入されたためです。

この問題を解決するため、Goランタイムが起動時に環境変数文字列をGoのメモリ空間にコピーするよう変更されました。これにより、Cライブラリによるメモリ変更がGoの環境変数表現に影響を与えることがなくなります。

## 前提知識の解説

### Goにおける環境変数管理

Go言語では、`os`パッケージを通じて環境変数にアクセス・操作します。`os.Getenv`で環境変数の値を取得し、`os.Setenv`で設定、`os.Unsetenv`で削除します。内部的には、Goランタイムは起動時にOSから渡される環境変数（通常はCの`environ`グローバル変数を通じてアクセスされる）を読み込み、Goの文字列スライスとして保持します。

### `gostringnocopy`関数

`gostringnocopy`はGoランタイム内部で使用される関数で、`*byte`ポインタからGoの`string`型を生成しますが、その際に基盤となるバイトデータを**コピーしません**。これは、Cのメモリ領域をGoの文字列として効率的に扱うための最適化であり、特にランタイムの初期化フェーズや、Cgoを介してCのデータを受け取る際に利用されます。コピーが発生しないため、パフォーマンス上の利点がありますが、元のCのメモリが変更されると、対応するGoの文字列も変更されてしまうというリスクを伴います。

### Android Bionic libc

Bionicは、GoogleがAndroidオペレーティングシステム向けに開発したC標準ライブラリの実装です。一般的なLinuxシステムで使われるGNU C Library (glibc) と比較して、軽量でリソースに制約のあるモバイルデバイス向けに最適化されています。Bionicも標準的なCライブラリと同様に、`environ`というグローバル変数を通じて環境変数へのアクセスを提供します。この`environ`が、プログラム起動時にカーネルから渡される`envp`メモリを直接指す実装になっていることが、今回の問題の引き金となりました。

### `syscall.Setenv`とCgo

Goの`syscall`パッケージは、OSのシステムコールへの低レベルなインターフェースを提供します。`syscall.Setenv`は、環境変数を設定するために使用されます。内部的には、この関数はCgo（GoとCのコードを相互運用するためのメカニズム）を介して、Cライブラリの`setenv(3)`関数を呼び出すことがあります。`setenv(3)`は、環境変数を変更する標準的なCライブラリ関数であり、その実装によっては`environ`が指すメモリ領域を直接操作します。

## 技術的詳細

この問題の核心は、GoランタイムとBionic libcが、環境変数文字列の基盤となるメモリを共有していた点にあります。

1.  **起動時の環境変数初期化**: Goランタイムは起動時、OSから渡される環境変数（`envp`）を読み込み、内部の`envs []string`スライスに格納します。この際、`src/runtime/runtime1.go`内の`goenvs_unix`関数で、各環境変数文字列を`gostringnocopy`を使ってGoの文字列に変換していました。`gostringnocopy`はメモリコピーを行わないため、Goの文字列は`envp`が指すCのメモリ領域を直接参照していました。
2.  **Bionic libcの`environ`**: AndroidのBionic libcでは、グローバル変数`environ`が、やはり`envp`メモリを直接指すように実装されていました。
3.  **メモリの競合**: この状況下で、Goプログラムが`syscall.Setenv`を呼び出すと、Cgoを介してBionic libcの`setenv(3)`が実行されます。`setenv(3)`は、新しい環境変数を設定したり、既存の環境変数を変更したりする際に、`environ`が指すメモリ領域を操作します。
4.  **データ破損**: `setenv(3)`が`environ`が指すメモリ（つまり、Goの環境変数文字列が参照しているのと同じメモリ）を変更すると、Goの文字列の内容も意図せず変更されてしまいます。特に、新しい環境変数が元の環境変数よりも短い場合、ヌル文字（`\x00`）が途中に挿入され、Goの文字列が途中で切れてしまうなどの破損が発生しました。コミットメッセージの例では、`GOROOT`が`"/os\x00a/local/tmp/goroot"`となる現象がこれに該当します。

この問題を解決するために、`gostringnocopy`の使用を`gostring`に変更しました。`gostring`関数は、Cのバイト配列からGoの文字列を生成する際に、必ずメモリをコピーします。これにより、Goの環境変数文字列は独自のメモリ空間を持つようになり、Bionic libcが`environ`メモリを操作しても、Goの環境変数データが影響を受けることがなくなりました。

## コアとなるコードの変更箇所

変更は`src/runtime/runtime1.go`ファイル内の`goenvs_unix`関数にあります。

```diff
--- a/src/runtime/runtime1.go
+++ b/src/runtime/runtime1.go
@@ -80,7 +80,7 @@ func goenvs_unix() {
 
 	envs = make([]string, n)
 	for i := int32(0); i < n; i++ {
-		envs[i] = gostringnocopy(argv_index(argv, argc+1+i))
+		envs[i] = gostring(argv_index(argv, argc+1+i))
 	}
 }
 
```

## コアとなるコードの解説

`goenvs_unix`関数は、Unix系システムでGoランタイムが環境変数を初期化する際に呼び出されます。この関数は、OSから渡された環境変数（`argv`配列の`argc+1`以降に格納されている）を読み取り、Goの`[]string`スライスである`envs`に格納します。

変更前は、ループ内で各環境変数文字列をGoの文字列に変換する際に`gostringnocopy`が使用されていました。

```go
envs[i] = gostringnocopy(argv_index(argv, argc+1+i))
```

`gostringnocopy`は、前述の通り、CのメモリをコピーせずにGoの文字列として扱います。これがBionic libcとのメモリ共有問題を引き起こしていました。

このコミットでは、`gostringnocopy`を`gostring`に置き換えています。

```go
envs[i] = gostring(argv_index(argv, argc+1+i))
```

`gostring`関数は、`argv_index`が返すCのバイトポインタが指す内容を、Goのヒープ上に新しく割り当てられたメモリ領域に**コピー**してGoの文字列を生成します。これにより、Goの環境変数スライス`envs`内の各文字列は、Cの`envp`メモリとは独立した独自のメモリを持つことになります。結果として、`syscall.Setenv`がCライブラリを介して`envp`メモリを変更しても、Goランタイムが保持する環境変数データが破損する問題が解消されます。

この変更は、特にAndroid/ARM環境での`runtime.TestFixedGOROOT`テストによってカバーされており、修正が正しく機能することを確認しています。

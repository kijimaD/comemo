# [インデックス 25702] ファイルの概要

このコミットは、Go言語の標準ライブラリである`crypto/tls`パッケージ内の`conn.go`ファイルに対する変更です。`conn.go`は、TLS (Transport Layer Security) プロトコルの接続処理、特にレコード層の読み書きに関するロジックを実装しています。具体的には、TLSレコードヘッダーの解析と、それに関連するエラーハンドリングを扱っています。

## コミット

このコミットは、無効なTLSレコードヘッダーが検出された際に、より詳細な情報を含む型付きエラーを返すように`crypto/tls`パッケージを改善します。これにより、呼び出し元はエラーの種類を特定しやすくなり、特に`net/http`クライアントがHTTPS接続を試みた際に、誤ってHTTPサーバーに接続してしまった場合などを検出できるようになります。

## 変更の背景

これまでの`crypto/tls`パッケージでは、無効なTLSレコードヘッダーが検出された際に、一般的な`error`インターフェースを介してエラーを返していました。この一般的なエラーでは、エラーが発生した具体的な原因や、エラーを引き起こした生のリコードヘッダーデータに関する詳細な情報をプログラム的に取得することが困難でした。

このコミットの主な動機は、`net/http`クライアントがHTTPS接続を確立しようとした際に、実際にはHTTPサーバーに接続してしまった状況をより正確に検出できるようにすることです。例えば、ユーザーが`https://example.com`にアクセスしようとしたが、DNS設定ミスやプロキシの問題により、実際には`http://example.com`のサーバーに接続してしまった場合、TLSハンドシェイクは失敗します。このとき、サーバーから返されるデータはTLSレコードヘッダーの形式を満たさないため、`crypto/tls`はエラーを発生させます。

型付きエラーを導入することで、`net/http`クライアントは返されたエラーが`RecordHeaderError`型であるかをチェックし、その内部に含まれる`RecordHeader`フィールドを検査することで、相手側がTLSプロトコルを使用していないことをプログラム的に判断できるようになります。これにより、より適切なエラーメッセージをユーザーに提示したり、フォールバック処理を行ったりすることが可能になります。

関連するIssueは[#11111](https://github.com/golang/go/issues/11111)で、これは「net/http: HTTPSクライアントがHTTPサーバーに接続したときに、より良いエラーを報告する」という内容です。

## 前提知識の解説

### TLS (Transport Layer Security) プロトコル
TLSは、インターネット上でデータを安全にやり取りするための暗号化プロトコルです。HTTP通信を暗号化するHTTPSで広く利用されています。TLS通信は、ハンドシェイクプロトコル、レコードプロトコルなど複数のサブプロトコルで構成されます。

### TLSレコードプロトコルとレコードヘッダー
TLSレコードプロトコルは、上位層のデータをフラグメント化し、圧縮、MAC（メッセージ認証コード）の付加、暗号化を行い、信頼性の高いデータ転送を提供します。各TLSレコードは、以下の構造を持つ5バイトのヘッダーから始まります。
- **Content Type (1バイト)**: レコードに含まれるデータの種類（例: ハンドシェイク、アラート、アプリケーションデータなど）を示します。
- **Protocol Version (2バイト)**: TLSのバージョン（例: TLS 1.2は0x0303）を示します。
- **Length (2バイト)**: レコードのデータ部分の長さを示します。

### Go言語のエラーハンドリングと型付きエラー
Go言語では、エラーは組み込みの`error`インターフェースによって表現されます。
```go
type error interface {
    Error() string
}
```
通常、エラーは`errors.New`で文字列から生成されるか、`fmt.Errorf`でフォーマットされた文字列から生成されます。これらは一般的なエラーであり、エラーメッセージの内容を解析しない限り、プログラム的にエラーの種類を特定することは困難です。

「型付きエラー」とは、特定のエラー情報を保持するためのカスタム構造体を定義し、その構造体が`error`インターフェースを実装するようにしたものです。これにより、呼び出し元は型アサーション（例: `if err, ok := err.(MyCustomError); ok { ... }`）を使用してエラーの具体的な型をチェックし、その構造体に含まれる追加情報（このコミットの`RecordHeaderError`の場合は`RecordHeader`フィールド）にアクセスできるようになります。

### SSLv2
SSLv2は、TLSの前身であるSSL (Secure Sockets Layer) プロトコルの古いバージョンです。セキュリティ上の脆弱性があるため、現代のシステムでは使用が推奨されていません。TLS実装は、SSLv2のハンドシェイクメッセージを検出した場合、通常はエラーとして処理します。

## 技術的詳細

このコミットの核となる変更は、`RecordHeaderError`という新しい型付きエラーの導入です。

### `RecordHeaderError`構造体
```go
type RecordHeaderError struct {
	// Msg contains a human readable string that describes the error.
	Msg string
	// RecordHeader contains the five bytes of TLS record header that
	// triggered the error.
	RecordHeader [5]byte
}
```
この構造体は、以下の2つのフィールドを持ちます。
- `Msg` (string): エラーの人間が読める説明文を格納します。これは、従来のエラーメッセージに相当します。
- `RecordHeader` ([5]byte): エラーを引き起こした実際の5バイトのTLSレコードヘッダーデータを格納します。このフィールドが、型付きエラーの最大の利点であり、呼び出し元が不正なデータを直接検査することを可能にします。

### `Error()`メソッド
`RecordHeaderError`は`error`インターフェースを実装するために`Error()`メソッドを持ちます。
```go
func (e RecordHeaderError) Error() string { return "tls: " + e.Msg }
```
このメソッドは、エラーメッセージの前に`"tls: "`というプレフィックスを付加して返します。これにより、エラーが`crypto/tls`パッケージから発生したものであることが明確になります。

### `newRecordHeaderError`ヘルパー関数
`Conn`構造体には、`RecordHeaderError`の新しいインスタンスを生成するためのヘルパーメソッド`newRecordHeaderError`が追加されました。
```go
func (c *Conn) newRecordHeaderError(msg string) (err RecordHeaderError) {
	err.Msg = msg
	copy(err.RecordHeader[:], c.rawInput.data)
	return err
}
```
この関数は、エラーメッセージ`msg`を受け取り、`RecordHeaderError`構造体の`Msg`フィールドに設定します。さらに、`c.rawInput.data`（現在の入力バッファの先頭）から5バイトを`RecordHeader`フィールドにコピーします。これにより、エラー発生時の実際のレコードヘッダーデータがエラーオブジェクトに埋め込まれます。

### エラー発生箇所の変更
`readRecord`関数内で、TLSレコードヘッダーの検証に失敗する複数の箇所で、従来の`errors.New`や`fmt.Errorf`による一般的なエラー生成が、`c.newRecordHeaderError`を呼び出す形に変更されました。
具体的には、以下のシナリオで`RecordHeaderError`が返されるようになります。
1.  **SSLv2ハンドシェイクの受信**: 古いSSLv2プロトコルによるハンドシェイクが検出された場合。
2.  **プロトコルバージョンの不一致**: 期待されるTLSバージョンと異なるバージョンがレコードヘッダーで示された場合。
3.  **オーバーサイズレコード**: レコードの長さが`maxCiphertext`（最大暗号文長）を超えている場合。
4.  **最初のレコードがTLSハンドシェイクに見えない**: 接続の最初のレコードがTLSハンドシェイクの形式を満たさない場合。

これらの変更により、`readRecord`関数は、TLSレコードヘッダーの解析中に発生した特定のエラーについて、そのエラーメッセージだけでなく、エラーを引き起こした生のリコードヘッダーデータも含む、よりリッチな情報を提供するようになります。

## コアとなるコードの変更箇所

`src/crypto/tls/conn.go`ファイルにおいて、以下の変更が行われました。

1.  **`RecordHeaderError`構造体の追加**:
    ```go
    // RecordHeaderError results when a TLS record header is invalid.
    type RecordHeaderError struct {
    	// Msg contains a human readable string that describes the error.
    	Msg string
    	// RecordHeader contains the five bytes of TLS record header that
    	// triggered the error.
    	RecordHeader [5]byte
    }

    func (e RecordHeaderError) Error() string { return "tls: " + e.Msg }
    ```

2.  **`newRecordHeaderError`メソッドの追加**:
    ```go
    func (c *Conn) newRecordHeaderError(msg string) (err RecordHeaderError) {
    	err.Msg = msg
    	copy(err.RecordHeader[:], c.rawInput.data)
    	return err
    }
    ```

3.  **`readRecord`関数内のエラー生成箇所の変更**:
    -   SSLv2ハンドシェイク検出時のエラー:
        ```diff
        -		return c.in.setErrorLocked(errors.New("tls: unsupported SSLv2 handshake received"))
        +		return c.in.setErrorLocked(c.newRecordHeaderError("unsupported SSLv2 handshake received"))
        ```
    -   プロトコルバージョン不一致時のエラー:
        ```diff
        -		return c.in.setErrorLocked(fmt.Errorf("tls: received record with version %x when expecting version %x", vers, c.vers))
        +		msg := fmt.Sprintf("received record with version %x when expecting version %x", vers, c.vers)
        +		return c.in.setErrorLocked(c.newRecordHeaderError(msg))
        ```
    -   オーバーサイズレコード検出時のエラー:
        ```diff
        -		return c.in.setErrorLocked(fmt.Errorf("tls: oversized record received with length %d", n))
        +		msg := fmt.Sprintf("oversized record received with length %d", n)
        +		return c.in.setErrorLocked(c.newRecordHeaderError(msg))
        ```
    -   最初のレコードがTLSハンドシェイクに見えない場合のエラー:
        ```diff
        -		return c.in.setErrorLocked(fmt.Errorf("tls: first record does not look like a TLS handshake"))
        +		return c.in.setErrorLocked(c.newRecordHeaderError("first record does not look like a TLS handshake"))
        ```

## コアとなるコードの解説

この変更の核心は、Goのエラーハンドリングの柔軟性を活用し、よりセマンティックなエラー情報を提供することにあります。

以前は、`readRecord`関数が不正なTLSレコードヘッダーを検出した場合、`errors.New`や`fmt.Errorf`を使って一般的な`error`インターフェースを返すだけでした。これにより、エラーを処理する側は、エラーメッセージの文字列を解析する以外に、エラーの具体的な原因や、エラーを引き起こした元のデータを知る術がありませんでした。これは、特にデバッグや、特定のタイプのエラーに基づいて異なる回復戦略を実装する際に不便でした。

新しい`RecordHeaderError`型を導入し、それを返すようにすることで、以下の利点が得られます。

1.  **プログラムによるエラーの識別**: 呼び出し元は、返されたエラーが`RecordHeaderError`型であるかを`switch err := err.(type)`や型アサーションで簡単にチェックできます。これにより、エラーメッセージの文字列解析という脆弱な方法に頼ることなく、エラーの種類を確実に識別できます。
2.  **詳細なコンテキストの提供**: `RecordHeaderError`構造体には、エラーメッセージ（`Msg`）だけでなく、エラーを引き起こした実際の5バイトのレコードヘッダーデータ（`RecordHeader`）が含まれています。これにより、`net/http`クライアントのような上位層のコンポーネントは、この`RecordHeader`を検査して、接続相手がTLSプロトコルを話していないことをプログラム的に確認できます。例えば、HTTP/1.1のGETリクエストの最初の数バイトは`GET /`のようなASCII文字列であり、TLSレコードヘッダーの形式とは全く異なります。この違いを`RecordHeader`フィールドで確認することで、HTTPサーバーへの誤接続を確実に検出できます。
3.  **堅牢なエラーハンドリング**: 型付きエラーは、エラー処理コードをより堅牢で保守しやすいものにします。エラーメッセージの変更が、エラー識別ロジックを壊す心配がなくなります。

この変更は、Goの`crypto/tls`パッケージが提供するエラー情報の質を向上させ、そのクライアントがよりインテリジェントなエラー処理を行えるようにするための重要なステップです。特に、HTTPSクライアントがHTTPサーバーに誤って接続するような一般的な問題シナリオにおいて、ユーザーエクスペリエンスを向上させるための基盤となります。

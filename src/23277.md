# [インデックス 23277] ファイルの概要

このコミットは、Go言語の標準ライブラリである `text/template` パッケージにおける、レキシング（字句解析）ゴルーチンのエラー処理に関する改善です。具体的には、テンプレートのパースエラー発生時に、レキシングを担当するゴルーチンがアイドル状態のまま残ってしまう問題を解決し、リソースの無駄遣いを防ぐことを目的としています。

## コミット

```
commit 64c39a3093db3976201697bb817d5705afc66bed
Author: Rob Pike <r@golang.org>
Date:   Mon May 4 13:09:31 2015 -0700

    text/template: shut down lexing goroutine on error
    
    When a parse error occurred, the lexing goroutine would lay idle.
    It's not likely a problem but if the program is for some reason
    accepting badly formed data repeatedly, it's wasteful.
    
    The solution is easy: Just drain the input on error. We know this
    will succeed because the input is always a string and is therefore
    guaranteed finite.
    
    With debugging prints in the package tests I've shown this is effective,
    shutting down 79 goroutines that would otherwise linger, out of 123 total.
    
    Fixes #10574.
```

## 元コミット内容

`text/template: shut down lexing goroutine on error`

このコミットは、`text/template` パッケージにおいて、パースエラーが発生した際にレキシングを行うゴルーチンがアイドル状態のまま残ってしまう問題を修正します。この問題は、不正なデータが繰り返し入力される場合にリソースの無駄遣いにつながる可能性があります。解決策として、エラー発生時にレキシングゴルーチンの入力チャネルをドレイン（読み尽くす）することで、ゴルーチンが正常に終了するようにします。これにより、テスト環境で確認されたように、残存するゴルーチンの数を大幅に削減できることが示されています。この変更は、Issue #10574 を修正します。

## 変更の背景

Go言語の `text/template` パッケージは、テキストベースのテンプレートを解析し、実行するための機能を提供します。このパッケージの内部では、テンプレート文字列を字句解析（レキシング）する部分と、その字句（トークン）を構文解析（パース）する部分が分かれています。初期のGoの設計思想では、並行処理を積極的に活用することが推奨されており、`text/template` のレキサーも、独立したゴルーチンとして動作し、トークンをチャネルを通じてパーサーに送信する設計が採用されていました。

しかし、この並行処理の設計には潜在的な問題がありました。パーサーがテンプレートの構文エラーを検出した場合、それ以上トークンを必要としなくなるにもかかわらず、レキシングゴルーチンはチャネルへの書き込みを試み続けるか、あるいはチャネルが閉じられるまで待機し続ける状態になる可能性がありました。特に、パーサーがエラーを検出して処理を中断した場合、レキシングゴルーチンはチャネルにデータを送り続けることができなくなり、結果としてチャネルが満杯になり、レキシングゴルーチンがブロックされたまま、あるいはアイドル状態のまま残存してしまうという問題が発生していました。

このような残存するゴルーチンは、プログラムが繰り返し不正なテンプレートデータを処理する場合に、メモリやCPUリソースを無駄に消費する原因となります。特に、サーバーアプリケーションなどでユーザーからの入力に基づいてテンプレートを動的に生成・パースするようなシナリオでは、悪意のある、あるいは単に不正な形式の入力によって、多数のアイドル状態のゴルーチンが蓄積され、システム全体のパフォーマンスや安定性に悪影響を及ぼす可能性がありました。

このコミットは、このようなリソースリークを防ぎ、`text/template` パッケージの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および関連する概念の知識が必要です。

1.  **ゴルーチン (Goroutine)**:
    Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千から数百万のゴルーチンを同時に実行できます。Goランタイムがゴルーチンのスケジューリングを管理します。

2.  **チャネル (Channel)**:
    ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、ゴルーチン間の同期と通信を安全に行うための主要な手段です。バッファなしチャネルとバッファ付きチャネルがあります。バッファなしチャネルは、送信側と受信側が同時に準備ができていないとブロックされます。

3.  **字句解析 (Lexical Analysis / Lexing)**:
    コンパイラやインタプリタの最初の段階で、入力文字列（この場合はテンプレート文字列）を意味のある最小単位（トークン）のシーケンスに分解するプロセスです。例えば、`{{ .Name }}` というテンプレート文字列は、`{{` (アクション開始)、`.` (ドット)、`Name` (識別子)、`}}` (アクション終了) といったトークンに分解されます。

4.  **構文解析 (Parsing)**:
    字句解析によって生成されたトークンのシーケンスを、文法規則に従って解析し、抽象構文木 (AST: Abstract Syntax Tree) などの構造を構築するプロセスです。このASTに基づいて、テンプレートの実行が行われます。

5.  **`text/template` パッケージ**:
    Go言語の標準ライブラリの一つで、テキストベースのテンプレートを処理するための機能を提供します。HTMLやXMLなどの構造化されたテキストを動的に生成する際によく使用されます。内部的には、レキサーとパーサーが協調して動作します。

6.  **Goの `defer` ステートメントと `panic`/`recover`**:
    `defer` は、関数がリターンする直前に実行される関数呼び出しをスケジュールします。エラーハンドリングでは、`panic` が発生した際にリソースをクリーンアップしたり、`recover` を使ってパニックを捕捉し、エラーとして処理するために利用されます。このコミットでは、パーサーのエラーリカバリメカニズムの一部として `defer` と `recover` が使われており、その中でレキシングゴルーチンのドレイン処理が呼び出されています。

## 技術的詳細

このコミットの核心は、`text/template` パッケージのレキシングゴルーチンが、パーサーがエラーを検出して処理を中断した際に、適切に終了するようにすることです。

従来の `text/template` のレキサーは、`lex` 関数によって起動されるゴルーチン (`l.run()`) が、テンプレート文字列を字句解析し、生成されたトークンを `l.items` というチャネルに送信していました。パーサーは `l.nextItem()` メソッドを通じてこのチャネルからトークンを受信していました。

問題は、パーサーが `New("root").parseLexer(lexer, text)` のような処理中にエラー（例えば、不正なテンプレート構文）を検出した場合に発生しました。パーサーはエラーを `panic` として発生させ、`defer` を使って設定された `recover` 関数によってその `panic` を捕捉し、エラーとして返します。この時点で、パーサーはそれ以上トークンを必要としなくなります。しかし、レキシングゴルーチンはまだ実行中で、`l.items` チャネルにトークンを送り続けようとする可能性があります。もし `l.items` チャネルがバッファなし、またはバッファが満杯であれば、レキシングゴルーチンはブロックされ、終了できなくなります。

このコミットの解決策は、パーサーがエラーから回復する (`recover`) 際に、レキシングゴルーチンが使用しているチャネル `l.items` を「ドレイン」することです。ドレインとは、チャネルから残っているすべての値を読み出し、チャネルが閉じられるまで待機することを意味します。

具体的には、以下の変更が行われました。

1.  **`lexer` 構造体に `drain()` メソッドを追加**:
    この新しいメソッド `drain()` は、`l.items` チャネルからすべての値をループで読み出します。チャネルが閉じられるとループは終了します。これにより、レキシングゴルーチンがチャネルへの書き込みでブロックされることなく、自身の処理を完了し、最終的に `close(l.items)` を実行して終了できるようになります。

    ```go
    // drain drains the output so the lexing goroutine will exit.
    // Called by the parser, not in the lexing goroutine.
    func (l *lexer) drain() {
        if l == nil {
            return
        }
        for range l.items {
        }
    }
    ```

2.  **`parse.go` のエラーリカバリ箇所で `drain()` を呼び出し**:
    `Tree.recover` メソッドは、パース中に発生した `panic` を捕捉し、エラーとして処理する役割を担っています。この `recover` 処理の中で、`t.lex.drain()` が呼び出されるようになりました。これにより、パースエラーが発生し、パーサーが処理を中断する際に、レキシングゴルーチンが確実にクリーンアップされるようになります。

    ```go
    // src/text/template/parse/parse.go
    func (t *Tree) recover(errp *error) {
        // ...
        if t != nil {
            t.lex.drain() // <-- ここで drain() が呼び出される
            t.stopParse()
        }
        // ...
    }
    ```

3.  **`lex.go` の `run()` メソッドでチャネルを閉じる**:
    レキシングゴルーチン (`l.run()`) の処理が完了した際に、`close(l.items)` が確実に実行されるようにします。これにより、`drain()` メソッドがチャネルの終了を検出し、ループを終了できるようになります。

    ```go
    // src/text/template/parse/lex.go
    func (l *lexer) run() {
        for l.state = lexText; l.state != nil; {
            l.state = l.state(l)
        }
        close(l.items) // <-- ここでチャネルが閉じられる
    }
    ```

4.  **テストケースの追加 (`lex_test.go`)**:
    `TestShutdown` という新しいテストケースが追加され、パースエラーが発生した際にレキシングゴルーチンが適切にシャットダウンされることを検証します。このテストは、意図的に不正なテンプレート文字列をパースさせ、エラー発生後に `lexer.items` チャネルがドレインされている（つまり、それ以上トークンが送られてこない）ことを確認します。

この変更により、パースエラーが発生してもレキシングゴルーチンが適切に終了し、リソースの無駄遣いが防止されます。コミットメッセージにあるように、デバッグプリントを用いたテストでは、この変更によって多数の残存ゴルーチンがシャットダウンされることが確認されています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の3つのファイルに集中しています。

1.  **`src/text/template/parse/lex.go`**:
    -   `lexer` 構造体に `drain()` メソッドが追加されました。このメソッドは、レキシングゴルーチンがトークンを送信するチャネル `l.items` から、残っているすべてのトークンを読み出すことで、チャネルを空にし、レキシングゴルーチンがブロックされずに終了できるようにします。
    -   `run()` メソッドの最後に `close(l.items)` が追加されました。これにより、レキシングゴルーチンが自身の処理を終えた際に、トークンチャネルが確実に閉じられるようになります。これは `drain()` メソッドがチャネルの終了を検知するために重要です。

2.  **`src/text/template/parse/lex_test.go`**:
    -   `TestShutdown` という新しいテスト関数が追加されました。このテストは、意図的にパースエラーを引き起こすテンプレート文字列を使用し、エラー発生後にレキシングゴルーチンが適切にシャットダウンされ、`l.items` チャネルが空になっていることを検証します。
    -   テストヘルパーとして `parseLexer` メソッドが追加されました。これは `template.Parse` のローカルバージョンで、テストのためにレキサーを直接渡せるようにしたものです。

3.  **`src/text/template/parse/parse.go`**:
    -   `Tree.recover` メソッド内で、パースエラーから回復する際に `t.lex.drain()` が呼び出されるようになりました。これにより、パーサーがエラーを検出して処理を中断する際に、レキシングゴルーチンが確実にクリーンアップされるようになります。

## コアとなるコードの解説

### `src/text/template/parse/lex.go` の変更

```go
// nextItem returns the next item from the input.
// Called by the parser, not in the lexing goroutine.
func (l *lexer) nextItem() item {
	item := <-l.items
	l.lastPos = item.pos
	return item
}

// drain drains the output so the lexing goroutine will exit.
// Called by the parser, not in the lexing goroutine.
func (l *lexer) drain() {
	if l == nil {
		return
	}
	for range l.items { // l.items チャネルから全ての値を読み出す
	}
}

// lex creates a new scanner for the input string.
func lex(name, input, left, right string) *lexer {
	// ... (既存のコード) ...
}

func (l *lexer) run() {
	for l.state = lexText; l.state != nil; {
		l.state = l.state(l)
	}
	close(l.items) // レキシングゴルーチン終了時にチャネルを閉じる
}
```

-   `drain()` メソッドは、`l.items` チャネルから値が送られてこなくなるまで（つまり、チャネルが閉じられるか、レキシングゴルーチンが終了するまで）ループし、チャネルを空にします。これにより、レキシングゴルーチンがチャネルへの書き込みでブロックされる可能性がなくなります。
-   `run()` メソッドの `close(l.items)` は、レキシングゴルーチンが自身の字句解析処理をすべて終えた後に、トークンチャネルを閉じます。これは `drain()` がチャネルの終了を検知し、ループを抜けるために不可欠です。

### `src/text/template/parse/parse.go` の変更

```go
func (t *Tree) recover(errp *error) {
	e := recover()
	if e != nil {
		if _, ok := e.(runtime.Error); ok {
			panic(e)
		}
		if t != nil {
			t.lex.drain() // パースエラー発生時にレキシングゴルーチンをドレイン
			t.stopParse()
		}
		*errp = e.(error)
	}
}
```

-   `Tree.recover` は、パース中に発生した `panic` を捕捉するGoの慣用的なエラーハンドリングパターンです。
-   `t.lex.drain()` の呼び出しが追加されたことで、パースエラーが発生し、パーサーが `panic` から回復する際に、レキシングゴルーチンが使用しているチャネルが確実にドレインされ、ゴルーチンが正常に終了するようになります。

### `src/text/template/parse/lex_test.go` の変更

```go
// Test that an error shuts down the lexing goroutine.
func TestShutdown(t *testing.T) {
	// We need to duplicate template.Parse here to hold on to the lexer.
	const text = "erroneous{{define}}{{else}}1234" // 意図的に不正なテンプレート
	lexer := lex("foo", text, "{{", "}}")
	_, err := New("root").parseLexer(lexer, text) // エラーを期待
	if err == nil {
		t.Fatalf("expected error")
	}
	// The error should have drained the input. Therefore, the lexer should be shut down.
	token, ok := <-lexer.items // チャネルが閉じられているか確認
	if ok {
		t.Fatalf("input was not drained; got %v", token)
	}
}

// parseLexer is a local version of parse that lets us pass in the lexer instead of building it.
// We expect an error, so the tree set and funcs list are explicitly nil.
func (t *Tree) parseLexer(lex *lexer, text string) (tree *Tree, err error) {
	defer t.recover(&err)
	t.ParseName = t.Name
	t.startParse(nil, lex)
	t.parse(nil)
	t.add(nil)
	t.stopParse()
	return t, nil
}
```

-   `TestShutdown` は、このコミットの修正が正しく機能することを確認するための重要なテストです。不正なテンプレート文字列 `erroneous{{define}}{{else}}1234` を使用してパースエラーを誘発します。
-   エラー発生後、`<-lexer.items` を試みることで、チャネルが閉じられている（`ok` が `false` になる）ことを確認します。もしチャネルが閉じられていなければ、レキシングゴルーチンが残存していることになり、テストは失敗します。
-   `parseLexer` は、テストのためにレキサーを直接注入できるようにしたヘルパー関数です。

これらの変更により、`text/template` パッケージは、パースエラー発生時により堅牢に動作し、リソースリークを防ぐことができるようになりました。

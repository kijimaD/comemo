# [インデックス 26485] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `ServeFile` 関数のセキュリティ強化に関するものです。具体的には、ユーザーからの入力（`r.URL.Path`）を直接 `ServeFile` に渡すことによって発生しうるディレクトリトラバーサル攻撃のリスクを軽減するための保護機能が追加されました。これにより、開発者が意図せず脆弱なコードを記述してしまうことを防ぎ、より安全なファイル提供メカニズムを提供します。

## 元コミット内容

このコミットは、`net/http` パッケージの `ServeFile` 関数に、その誤用に対する保護を追加するものです。Martin Lenord氏が指摘したように、オンラインの例で `r.URL.Path[1:]` を `ServeFile` に渡すという不適切なパターンが広まっていました。これは安全ではないため、その危険性を文書化し、いくつかの保護機能を追加しました。

この変更は、Issue #14110 を修正します。

## 変更の背景

`net/http.ServeFile` 関数は、HTTPリクエストに対して指定されたファイルまたはディレクトリの内容を応答するために使用されます。しかし、この関数を誤って使用すると、深刻なセキュリティ脆弱性につながる可能性があります。特に、HTTPリクエストのURLパス（`r.URL.Path`）から直接ファイルパスを構築し、それを `ServeFile` に渡すパターンがオンラインの例で散見されていました。

このパターンは、攻撃者が `..` (親ディレクトリ) を含むパスをURLに含めることで、ウェブサーバーが公開すべきではないファイル（例: `/etc/passwd` や設定ファイルなど）にアクセスできてしまう「ディレクトリトラバーサル」攻撃を許してしまう危険性があります。

コミットメッセージにある「Martin Lenord pointed out that bad patterns have emerged in online examples of how to use ServeFile, where people pass r.URL.Path[1:] to ServeFile. This is unsafe.」という記述が、この変更の直接的な動機です。開発者が意図せず脆弱なコードを書いてしまうことを防ぐため、ライブラリ側で防御的なメカニズムを導入する必要性が認識されました。

## 前提知識の解説

### 1. HTTP `net/http` パッケージ

Go言語の `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。ウェブアプリケーションを構築する上で中心的な役割を果たすパッケージであり、リクエストのルーティング、レスポンスの生成、ファイルの提供など、多岐にわたる機能を提供します。

*   **`http.Request`**: クライアントからのHTTPリクエストを表す構造体です。`URL` フィールドにはリクエストされたURLの情報が含まれます。
*   **`r.URL.Path`**: `http.Request` の `URL` フィールドに含まれるパス部分です。例えば、`http://example.com/static/image.png` というURLの場合、`r.URL.Path` は `/static/image.png` となります。
*   **`http.ResponseWriter`**: HTTPレスポンスを構築するために使用されるインターフェースです。
*   **`http.ServeFile(w http.ResponseWriter, r *http.Request, name string)`**: 指定された `name` のファイルの内容をHTTPレスポンスとしてクライアントに送信する関数です。

### 2. ディレクトリトラバーサル (Path Traversal) 攻撃

ディレクトリトラバーサル（またはパスインジェクション）は、ウェブアプリケーションの脆弱性の一種で、攻撃者がファイルシステム上の制限されたディレクトリ外のファイルにアクセスすることを可能にします。これは通常、ユーザーが提供した入力（例: URLパス、フォームデータ）が、ファイルパスを構築するために適切にサニタイズ（無害化）されずに使用される場合に発生します。

攻撃者は、`../` (ドットスラッシュ) シーケンスを使用して、現在のディレクトリから親ディレクトリに移動し、最終的に任意のファイルにアクセスしようとします。

**例:**
もしウェブサーバーが `/var/www/html/` ディレクトリ以下のファイルのみを公開しているとします。
開発者が `http.example.com/files?name=image.png` のようなリクエストに対して、`ServeFile` を `name` パラメータの値で呼び出すとします。
攻撃者が `http://example.com/files?name=../../../../etc/passwd` のようなリクエストを送信すると、サーバーは `/etc/passwd` ファイルを読み取って応答してしまう可能性があります。

### 3. `filepath.Split` と `filepath.Join`

Go言語の `path/filepath` パッケージは、ファイルパスを操作するためのユーティリティを提供します。

*   **`filepath.Split(path string) (dir, file string)`**: パスをディレクトリ部分とファイル部分に分割します。
*   **`filepath.Join(elem ...string) string`**: 複数のパス要素を結合して、クリーンなパスを生成します。この関数は、結合時に `..` や `.` などの要素を正規化する機能も持っていますが、ユーザー入力のサニタイズには注意が必要です。特に、`filepath.Join` はパスの先頭に `..` がある場合、それを解決して親ディレクトリに移動する挙動を示すため、ユーザー入力と組み合わせて使う際には依然として注意が必要です。

## 技術的詳細

このコミットの主要な変更点は、`http.ServeFile` 関数にディレクトリトラバーサル攻撃に対する防御メカニズムを追加したことです。

1.  **`ServeFile` 関数のドキュメント更新**:
    `ServeFile` のGodocコメントが更新され、以下の重要な警告が追加されました。
    > If the provided file or direcory name is a relative path, it is interpreted relative to the current directory and may ascend to parent directories. If the provided name is constructed from user input, it should be sanitized before calling ServeFile. As a precaution, ServeFile will reject requests where r.URL.Path contains a ".." path element.
    >
    > (提供されたファイルまたはディレクトリ名が相対パスである場合、それは現在のディレクトリからの相対パスとして解釈され、親ディレクトリに遡る可能性があります。提供された名前がユーザー入力から構築される場合、ServeFileを呼び出す前にサニタイズする必要があります。予防策として、ServeFileは `r.URL.Path` に `..` パス要素が含まれるリクエストを拒否します。)

    これにより、開発者に対して `ServeFile` の安全な使用方法と、ユーザー入力のサニタイズの重要性が明確に伝えられます。

2.  **`r.URL.Path` の `..` チェック**:
    `ServeFile` 関数の冒頭で、`r.URL.Path` に `..` (親ディレクトリへの移動を示すパス要素) が含まれているかどうかをチェックするロジックが追加されました。
    ```go
    if containsDotDot(r.URL.Path) {
        // Too many programs use r.URL.Path to construct the argument to
        // serveFile. Reject the request under the assumption that happened
        // here and ".." may not be wanted.
        // Note that name might not contain "..", for example if code (still
        // incorrectly) used filepath.Join(myDir, r.URL.Path).
        Error(w, "invalid URL path", StatusBadRequest)
        return
    }
    ```
    もし `r.URL.Path` に `..` が含まれている場合、`ServeFile` は `http.StatusBadRequest` (400 Bad Request) エラーを返してリクエストを拒否します。これは、多くのプログラムが `r.URL.Path` を `ServeFile` の引数として使用しているという現状を考慮した防御的な措置です。たとえ `name` 引数自体に `..` が含まれていなくても、`filepath.Join(myDir, r.URL.Path)` のように誤って使用されているケースを想定し、`r.URL.Path` 自体をチェックすることで、より広範な誤用を防ぎます。

3.  **`containsDotDot` ヘルパー関数の追加**:
    `..` のチェックを行うために、新しい内部ヘルパー関数 `containsDotDot(v string) bool` が追加されました。
    この関数は、与えられた文字列 `v` が `..` を含むかどうかを効率的に判定します。
    *   まず、`strings.Contains(v, "..")` で高速な事前チェックを行います。`..` が含まれていなければ、それ以上解析する必要はありません。
    *   次に、`strings.FieldsFunc(v, isSlashRune)` を使用して、パスをスラッシュ (`/` または `\`) で区切られた要素に分割します。
    *   分割された各要素が `..` と完全に一致するかどうかをループで確認します。これにより、例えば `foo..bar` のような文字列は `..` を含むと判定されず、`../` や `..` のみが問題となるパス要素として認識されます。

4.  **`isSlashRune` ヘルパー関数の追加**:
    `containsDotDot` 関数内で使用される、スラッシュ文字 (`/` または `\`) を判定するシンプルなヘルパー関数 `isSlashRune(r rune) bool` が追加されました。

5.  **テストケースの追加**:
    `src/net/http/fs_test.go` に `TestServeFile_DotDot` という新しいテスト関数が追加されました。このテストは、様々な `r.URL.Path` のパターン（`..` を含むものと含まないもの）に対して `ServeFile` が期待通りのHTTPステータスコード（200 OK または 400 Bad Request）を返すことを検証します。これにより、追加された防御メカニズムが正しく機能することが保証されます。

これらの変更により、`net/http.ServeFile` はより堅牢になり、開発者が誤ってディレクトリトラバーサル脆弱性を導入するリスクが大幅に低減されました。

## コアとなるコードの解説

### `src/net/http/fs.go` の変更

1.  **`ServeFile` 関数内の `..` チェック**:
    `ServeFile` 関数の冒頭に、`r.URL.Path` に `..` が含まれているかをチェックする `if` 文が追加されました。
    `containsDotDot(r.URL.Path)` が `true` を返した場合、つまり `r.URL.Path` に `..` が含まれている場合、`http.Error` 関数を使って `400 Bad Request` ステータスコードと「invalid URL path」というメッセージをクライアントに返し、処理を中断します。
    このチェックは、`ServeFile` に渡される `name` 引数自体が `filepath.Join` などで既に正規化されている場合でも、元の `r.URL.Path` に `..` が含まれていれば拒否するという、より安全なアプローチを取っています。これは、開発者が `r.URL.Path` を直接 `ServeFile` に渡すという誤用パターンが多いため、その誤用から保護することを目的としています。

2.  **`containsDotDot` 関数の追加**:
    この関数は、文字列 `v` (ここでは `r.URL.Path`) に `..` パス要素が含まれているかを判定します。
    *   `strings.Contains(v, "..")` で、まず文字列全体に `..` が含まれているかを高速にチェックします。含まれていなければ、それ以上詳細な解析は不要なので `false` を返します。
    *   `strings.FieldsFunc(v, isSlashRune)` は、`v` をスラッシュ (`/` または `\`) で区切って個々のパス要素の文字列スライスを生成します。例えば、`/foo/../bar` は `["foo", "..", "bar"]` となります。
    *   そのスライスをループし、各要素が文字列 `".."` と完全に一致するかを確認します。一致する要素があれば、`true` を返します。これにより、`foo..bar` のようなファイル名自体に `..` が含まれるケースと、ディレクトリトラバーサルを意図した `..` パス要素を区別できます。

3.  **`isSlashRune` 関数の追加**:
    `containsDotDot` 関数内で `strings.FieldsFunc` の区切り文字として使用されるシンプルな関数です。`rune` が `/` または `\` のいずれかである場合に `true` を返します。これにより、WindowsとUnixライクなシステムの両方でパス区切り文字を正しく扱えます。

### `src/net/http/fs_test.go` の変更

1.  **`TestServeFile_DotDot` テスト関数の追加**:
    このテストは、`ServeFile` の新しい `..` チェック機能が正しく動作することを検証します。
    *   `tests` スライスには、様々なリクエストパス (`req`) と、それに対応する期待されるHTTPステータスコード (`wantStatus`) のペアが定義されています。
    *   `"/testdata/file"` や `"/file/a"` のように `..` を含まない有効なパスは `200 OK` を期待します。
    *   `"/../file"`, `"/.."`, `"/../foo"`, `"/file/a/.."` のように `..` を含むパスは `400 Bad Request` を期待します。Windows形式のパス区切り文字 `\` を含む `"/..\\foo"` や `"/file/a\\\\.."` もテストされています。
    *   各テストケースでは、`ReadRequest` を使ってダミーのHTTPリクエストを構築し、`httptest.NewRecorder` を使ってレスポンスを記録します。
    *   `ServeFile` を呼び出した後、記録されたステータスコードが期待される `wantStatus` と一致するかを確認します。これにより、新しいセキュリティ保護が意図通りに機能していることが保証されます。

これらの変更は、Goの `net/http` パッケージが提供するファイル提供機能の堅牢性を高め、一般的なセキュリティ脆弱性からアプリケーションを保護するための重要なステップです。

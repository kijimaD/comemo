# [インデックス 22643] ファイルの概要

このコミットは、Goランタイムにおけるシンボル名の重複問題を解決するためのものです。具体的には、`runtime·main·f`というアセンブリシンボルがリンカによって正規化される際に、コンパイラが生成する`runtime.main.f`というシンボルと衝突することを避けるため、`runtime·main·f`を`runtime·mainPC`にリネームしています。これにより、異なるソースから生成される同じ名前のシンボルによるリンカエラーや予期せぬ動作を防ぎます。

## 変更の背景

この変更の背景には、Goのリンカにおけるシンボル名の正規化処理が深く関わっています。Goのランタイムコードには、アセンブリ言語で書かれた部分が多く存在し、これらのアセンブリコード内で定義されるシンボルは、Goのソースコードから生成されるシンボルとは異なる命名規則を持つことがあります。

具体的には、このコミットで問題となっているのは`runtime·main·f`というシンボルです。Goのアセンブリでは、パッケージ名とシンボル名を区切るために中点（`·`、U+00B7）が使用されることがあります。しかし、リンカがこれらのシンボルを処理する際、この中点（`·`）をピリオド（`.`）に正規化する挙動がありました。

一方で、Goコンパイラが生成するシンボルの中には、`runtime.main.f`のように最初からピリオドを含むものも存在します。このため、アセンブリで定義された`runtime·main·f`がリンカによって`runtime.main.f`に正規化されると、コンパイラが生成した既存の`runtime.main.f`シンボルと名前が完全に一致してしまい、シンボル名の重複が発生していました。

シンボル名の重複は、リンカがどのシンボル定義を使用すべきか判断できなくなるため、ビルドエラーを引き起こしたり、最悪の場合、実行時に予期せぬ動作やクラッシュにつながる可能性があります。このコミットは、この特定のシンボル衝突を回避するために、アセンブリ側のシンボル名を`runtime·mainPC`に変更することで、リンカによる正規化後も一意性を保つように修正したものです。コミットメッセージにある`Fixes issue #9934`は、この問題がGoのイシュートラッカーで報告されていたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **Goのアセンブリ言語とシンボル:**
    Goのランタイムや一部の低レベルな処理は、Go言語ではなくアセンブリ言語で記述されています。これは、パフォーマンスの最適化や、OSとの直接的なインタラクション（システムコールなど）を行うために必要です。Goのアセンブリ言語は、一般的なアセンブリ言語とは異なる独自の構文（Plan 9アセンブラの派生）を持っています。
    アセンブリコード内で定義される関数やデータは「シンボル」として扱われます。これらのシンボルは、Goのリンカによって最終的な実行可能ファイル内で解決されます。

2.  **Goのシンボル命名規則と中点（`·`）:**
    Goの内部では、パッケージ名とシンボル名を区切るために中点（`·`）が使われることがあります。例えば、`runtime`パッケージ内の`main`関数に関連するシンボルは`runtime·main`のように表記されます。これは、Goのツールチェーン（特にアセンブラやリンカ）が内部的に使用する慣習です。

3.  **リンカの役割とシンボル正規化:**
    リンカは、コンパイラやアセンブラによって生成された複数のオブジェクトファイル（`.o`ファイルなど）を結合し、最終的な実行可能ファイルを生成するツールです。この過程で、リンカは異なるオブジェクトファイル間で参照されているシンボルを解決し、それぞれのシンボルがメモリ上のどこに配置されるかを決定します。
    「シンボル正規化」とは、リンカがシンボル名を処理する際に、特定のルールに基づいて名前を変換するプロセスを指します。例えば、異なる入力形式（アセンブリとGoソース）から来るシンボル名が、最終的に同じ形式に統一されることがあります。今回のケースでは、アセンブリで使用される中点（`·`）が、リンカによってピリオド（`.`）に変換されるという正規化が行われていました。

4.  **`runtime.main`と`runtime.main.f`:**
    Goプログラムのエントリポイントは`main`パッケージの`main`関数ですが、Goランタイム内部には、このユーザー定義の`main`関数を呼び出すための`runtime.main`という内部関数が存在します。
    `runtime.main.f`のようなシンボルは、`runtime.main`関数の開始アドレスや関連するメタデータを示すために使用されることがあります。`f`は"function"の略である可能性があり、特定の関数のエントリポイントや関連するデータを示す慣例的なサフィックスとして使われることがあります。

5.  **`DATA`と`GLOBL`ディレクティブ:**
    Goのアセンブリファイル（`.s`拡張子）では、`DATA`ディレクティブは初期化されたデータセクションを定義するために使用されます。`GLOBL`ディレクティブは、シンボルをグローバルに公開し、他のファイルから参照できるようにするために使用されます。
    例: `DATA runtime·main·f+0(SB)/4,$runtime·main(SB)` は、`runtime·main·f`というシンボルに`runtime·main`のアドレスをデータとして格納し、そのサイズが4バイトであることを示しています。`GLOBL runtime·main·f(SB),RODATA,$4` は、`runtime·main·f`を読み取り専用データ（RODATA）としてグローバルに公開し、サイズが4バイトであることを宣言しています。

## 技術的詳細

このコミットの技術的な核心は、Goのリンカがシンボル名を正規化する際の挙動と、それによって引き起こされるシンボル衝突の回避策にあります。

Goのアセンブリコードでは、`runtime·main·f`というシンボルが定義されていました。このシンボルは、`runtime.main`関数のエントリポイントのアドレスを保持するためのデータシンボルとして機能していました。Goのリンカは、アセンブリコードで使われる中点（`·`）を、最終的なバイナリのシンボルテーブルではピリオド（`.`）に変換する正規化ルールを持っています。したがって、`runtime·main·f`はリンカによって`runtime.main.f`として扱われます。

問題は、Goコンパイラが生成するコードの中にも、`runtime.main.f`という名前のシンボルが存在していたことです。これは、Go言語で書かれたコードから生成されるシンボルであり、アセンブリで定義されたシンボルとは異なる起源を持ちます。

このように、アセンブリコードとGoコンパイラという異なるソースから、リンカによる正規化後に全く同じ名前（`runtime.main.f`）を持つシンボルが生成される状況が発生していました。リンカは、同じ名前のシンボルが複数定義されている場合、どちらを使用すべきか判断できず、重複シンボルエラー（"duplicate symbol" error）を報告します。これは、プログラムのビルドを妨げ、開発プロセスを停止させる重大な問題です。

このコミットでは、この衝突を解決するために、アセンブリ側のシンボル名を`runtime·main·f`から`runtime·mainPC`へと変更しました。`PC`は"Program Counter"（プログラムカウンタ）の略であり、通常、命令ポインタや関数のエントリポイントを指す際に使われる用語です。この変更により、アセンブリ側のシンボルはリンカによって`runtime.mainPC`と正規化され、既存の`runtime.main.f`シンボルとの衝突がなくなります。

この修正は、`src/runtime/asm_*.s`という複数のアセンブリファイルにわたって行われています。これは、Goがサポートする様々なアーキテクチャ（386, amd64, amd64p32, arm, arm64, ppc64xなど）それぞれに対応するランタイムアセンブリファイルが存在するためです。各アーキテクチャのアセンブリコード内で`runtime·main·f`が参照されている箇所と、そのシンボルが定義されている箇所が、一貫して`runtime·mainPC`に更新されています。これにより、Goランタイムのビルドプロセス全体でシンボルの一意性が保証され、リンカエラーが解消されます。

## コアとなるコードの変更箇所

このコミットでは、Goランタイムのアセンブリファイルにおいて、`runtime·main·f`というシンボルが`runtime·mainPC`にリネームされています。変更は以下の6つのファイルにわたって行われています。

*   `src/runtime/asm_386.s`
*   `src/runtime/asm_amd64.s`
*   `src/runtime/asm_amd64p32.s`
*   `src/runtime/asm_arm.s`
*   `src/runtime/asm_arm64.s`
*   `src/runtime/asm_ppc64x.s`

以下に、`src/runtime/asm_386.s`の変更点を例として示します。他のファイルも同様のパターンで変更されています。

## コアとなるコードの解説

上記のdiffは、`runtime·main·f`シンボルがどのように`runtime·mainPC`に置き換えられたかを示しています。

1.  **シンボル参照の変更:**
    ```diff
    -	PUSHL	$runtime·main·f(SB)	// entry
    +	PUSHL	$runtime·mainPC(SB)	// entry
    ```
    この行は、新しいゴルーチンを起動する際に、プログラムのエントリポイントとして`runtime·main·f`のアドレスをスタックにプッシュしていた箇所です。`PUSHL`命令は32ビットアーキテクチャ（386）で値をスタックにプッシュするために使われます。`$runtime·main·f(SB)`は、`runtime·main·f`シンボルのアドレスを指します。この変更により、参照先が`runtime·mainPC`に切り替わっています。他のアーキテクチャ（amd64, armなど）では、`MOVQ`や`MOVD`、`MOVW`といった命令が使われますが、基本的な意味は同じで、`runtime·main·f`のアドレスをレジスタにロードしたり、スタックにプッシュしたりする操作が`runtime·mainPC`のアドレスに置き換えられています。

2.  **シンボル定義の変更:**
    ```diff
    -DATA	runtime·main·f+0(SB)/4,$runtime·main(SB)
    -GLOBL	runtime·main·f(SB),RODATA,$4
    +DATA	runtime·mainPC+0(SB)/4,$runtime·main(SB)
    +GLOBL	runtime·mainPC(SB),RODATA,$4
    ```
    これらの行は、`runtime·main·f`シンボル自体の定義箇所です。
    *   `DATA runtime·main·f+0(SB)/4,$runtime·main(SB)`: これは、`runtime·main·f`という名前のデータセクションを定義し、その内容として`runtime·main`関数のアドレスを格納しています。`/4`はデータサイズが4バイト（32ビットアドレス）であることを示します。
    *   `GLOBL runtime·main·f(SB),RODATA,$4`: これは、`runtime·main·f`シンボルをグローバルに公開し、読み取り専用データ（RODATA）としてマークし、サイズが4バイトであることを宣言しています。
    これらの行が`runtime·mainPC`に置き換えられることで、`runtime·main·f`という古いシンボルは定義されなくなり、代わりに`runtime·mainPC`という新しいシンボルが同じ目的で定義されるようになります。

この変更は、Goランタイムの初期化フェーズにおいて、ユーザープログラムの`main`関数を実行するゴルーチンを起動する際に参照されるエントリポイントのシンボル名を修正するものです。これにより、リンカによるシンボル名の正規化によって発生していた重複シンボル問題を根本的に解決し、Goプログラムの安定したビルドと実行を保証します。

## 変更の背景

Go 1.4では、Goランタイムの基盤となる部分に大きな変更が加えられました。これには、ガベージコレクタの精度向上、スタック管理の効率化、そしてGo 1.5で導入される予定の並行ガベージコレクタへの準備が含まれます。これらの変更は、Goプログラムのメモリ使用量とパフォーマンスに影響を与えるため、ユーザーに対してその詳細と影響を明確に伝える必要がありました。このコミットは、これらの重要な技術的変更を公式のリリースノートに記述し、開発者がGo 1.4の動作を理解し、必要に応じてアプリケーションを調整できるようにするために行われました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、ゴルーチン（goroutine）スケジューラ、メモリ管理、チャネル、インターフェースなどが含まれます。Goランタイムは、Goプログラムが効率的かつ安全に動作するための基盤を提供します。
*   **ガベージコレクション (Garbage Collection, GC)**: プログラムが動的に確保したメモリ領域のうち、もはや使用されなくなった（参照されなくなった）ものを自動的に解放するプロセスです。GoのGCは、開発者が手動でメモリを管理する手間を省き、メモリリークのリスクを低減します。
*   **正確なGC (Precise GC)**: GCがメモリ上のポインタと非ポインタを正確に区別できるGCのことです。これにより、GCは実際に到達可能なオブジェクトのみを保持し、誤って非ポインタをポインタと解釈して不要なメモリを保持してしまう「偽陽性（false positive）」を防ぐことができます。正確なGCは、メモリ使用量を削減し、GCの効率を向上させます。
*   **スタック (Stack)**: 関数呼び出しやローカル変数などの情報を格納するために使用されるメモリ領域です。Goでは、各ゴルーチンが独自のスタックを持っています。
*   **セグメント化スタック (Segmented Stacks)**: 以前のGoバージョンで採用されていたスタック管理方式です。ゴルーチンのスタックが必要に応じて小さなセグメントとして割り当てられ、スタックが不足すると新しいセグメントが追加されます。この方式は、スタックの拡張時に「ホットスプリット（hot split）」と呼ばれるパフォーマンス上の問題を引き起こす可能性がありました。これは、スタックが拡張される際に、既存のスタックフレームを新しいセグメントにコピーし、スタック内のポインタを更新する必要があるため、一時的な停止やパフォーマンスの低下を招くことがありました。
*   **連続スタック (Contiguous Stacks)**: Go 1.4で導入された新しいスタック管理方式です。ゴルーチンのスタックは連続したメモリ領域として割り当てられ、スタックが不足した場合は、より大きな連続した領域にスタック全体がコピーされます。これにより、セグメント化スタックのホットスプリット問題が解消され、スタックの拡張がより予測可能で効率的になります。
*   **ライトバリア (Write Barrier)**: ガベージコレクタが動作中に、プログラムがヒープ上のポインタ値を変更する際に実行される特別なコードです。これは、GCがオブジェクトグラフを走査している最中に、プログラムがポインタを変更することでGCの認識と実際のメモリ状態との間に不整合が生じるのを防ぐために使用されます。ライトバリアは、並行GCの実装において不可欠な要素です。Go 1.4では、Go 1.5で導入される並行GCの準備として導入されました。
*   **インターフェース値 (Interface Values)**: Goのインターフェースは、型と値のペアとして内部的に表現されます。以前のバージョンでは、格納される具体的な型に応じて、インターフェース値がポインタまたは1ワードのスカラー値を直接保持することがありました。

## 技術的詳細

このコミットが記述しているGo 1.4のランタイム変更は、主に以下の3つの柱に基づいています。

1.  **ランタイムのGo言語への移行と正確なGCの実現**:
    *   Go 1.4以前のGoランタイム（ガベージコレクタ、並行処理サポート、インターフェース管理、マップ、スライス、文字列など）の大部分はC言語で書かれており、一部アセンブラが使用されていました。
    *   Go 1.4では、このコードの大部分がGo言語に翻訳されました。
    *   **目的**: ランタイム内のGoプログラムのスタックをGCがスキャンできるようになり、アクティブな変数に関する正確な情報を取得できるようになりました。
    *   **結果**: Go 1.4のガベージコレクタは完全に正確なGC（fully precise GC）となりました。これは、プログラム内のすべてのアクティブなポインタの位置をGCが認識できることを意味します。これにより、ヒープ上に不要なオブジェクトが保持される「偽陽性」が排除され、ヒープサイズが全体的に10%〜30%削減されました。

2.  **連続スタックの導入**:
    *   Go 1.4以前のセグメント化スタックは、スタックが拡張される際に「ホットスプリット」問題を引き起こす可能性がありました。これは、スタックの拡張時に既存のスタックフレームを新しいセグメントにコピーし、スタック内のポインタを更新する必要があるため、一時的な停止やパフォーマンスの低下を招くことがありました。
    *   Go 1.4では、スタックがセグメント化されなくなり、連続スタックが採用されました。
    *   **メカニズム**: スタックの限界に達すると、より大きな新しいスタックが割り当てられ、ゴルーチンのすべてのアクティブなフレームがそこにコピーされ、スタック内のポインタが更新されます。
    *   **結果**: ホットスプリット問題が解消され、パフォーマンスが一部のケースで顕著に向上し、常に予測可能になりました。
    *   **スタックサイズの最適化**: 連続スタックの採用により、パフォーマンスの問題を引き起こすことなくスタックをより小さく開始できるようになりました。そのため、ゴルーチンのデフォルトの初期スタックサイズは、8192バイトから2048バイトに削減されました（リリース時には4096バイトに引き上げられる可能性も示唆されています）。

3.  **ライトバリアの導入（Go 1.5並行GCの準備）**:
    *   Go 1.5で予定されている並行ガベージコレクタの準備として、ヒープ上のポインタ値への書き込みが関数呼び出し（ライトバリア）を介して行われるようになりました。
    *   **目的**: これにより、GCが実行中にヒープへの書き込みを仲介できるようになります。GCがオブジェクトグラフを走査している最中に、プログラムがポインタを変更しても、GCがその変更を認識し、整合性を保つことができます。
    *   **Go 1.4での影響**: Go 1.4では、この変更自体はプログラムにセマンティックな影響を与えません。しかし、コンパイラと結果的なパフォーマンスをテストするためにこのリリースに含まれました。
    *   **パフォーマンスへの影響**: 新しいライトバリアは、GCの高速化によって得られたパフォーマンス向上を相殺する形で、プログラムの実行速度をわずかに低下させる可能性があります。

4.  **インターフェース値の実装変更**:
    *   以前のリリースでは、インターフェースは格納される具体的なオブジェクトの型に応じて、ポインタまたは1ワードのスカラー値を直接含むことがありました。
    *   この実装はガベージコレクタにとって問題がありました。
    *   Go 1.4からは、インターフェース値は常にポインタを保持するようになりました。
    *   **影響**: 実行中のプログラムのほとんどのインターフェース値は元々ポインタであったため、影響は最小限です。しかし、整数などのスカラー値をインターフェースに格納するプログラムでは、より多くのメモリ割り当てが発生する可能性があります。

これらの変更は、Goランタイムの堅牢性、効率性、および将来の拡張性（特に並行GC）を大幅に向上させることを目的としていました。

## コアとなるコードの解説

このコミットはドキュメントの変更であるため、直接的な「コアとなるコード」の動作変更はありません。しかし、このドキュメントが解説している「コアとなるコード」の変更は、Goランタイムの以下の部分に及びます。

*   **ガベージコレクタ (GC)**:
    *   GCがスタックをスキャンする際の精度が向上し、完全に正確なGCが実現されました。これにより、ヒープのメモリ使用量が削減されます。
    *   GC自体の処理速度も向上しました。
*   **スタック管理**:
    *   セグメント化スタックから連続スタックへの移行により、スタックの拡張メカニズムが根本的に変更されました。これにより、スタックのホットスプリット問題が解消され、スタックの成長がより効率的かつ予測可能になります。
    *   ゴルーチンの初期スタックサイズが削減され、メモリ効率が向上しました。
*   **ライトバリア**:
    *   コンパイラによって生成されるコードに、ヒープへのポインタ書き込み時にライトバリア関数を呼び出すロジックが追加されました。これは、Go 1.5で導入される並行GCが、GC実行中にヒープの変更を追跡できるようにするための基盤となります。
*   **インターフェースの実装**:
    *   インターフェース値の内部表現が変更され、常にポインタを保持するようになりました。これにより、GCがインターフェース値をより簡単に処理できるようになりますが、スカラー値をインターフェースに格納する場合には追加のメモリ割り当てが発生する可能性があります。

これらの変更は、GoランタイムのC言語部分をGo言語に書き換えるという大規模な作業の一環として行われました。Go言語で書かれたランタイムは、Goコンパイラの最適化（インライン化など）の恩恵を受けることができ、全体的なパフォーマンス向上にも寄与しています。

    *   Go 1.4では、このコードの大部分がGo言語に翻訳されました。
    *   **目的**: ランタイム内のGoプログラムのスタックをGCがスキャンできるようになり、アクティブな変数に関する正確な情報を取得できるようになりました。これにより、GCはスタック上のポインタを正確に識別し、不要なオブジェクトが誤って保持されることを防ぎます。
    *   **結果**: Go 1.4のガベージコレクタは完全に正確なGC（fully precise GC）となりました。これは、プログラム内のすべてのアクティブなポインタの位置をGCが認識できることを意味します。これにより、ヒープ上に不要なオブジェクトが保持される「偽陽性」が排除され、ヒープサイズが全体的に10%〜30%削減されました。GoコンパイラはCコンパイラよりも最適化（インライン化など）に優れているため、ランタイムのGo言語化はパフォーマンスのわずかな向上にもつながりました。

2.  **連続スタックの導入**:
    *   Go 1.4以前のセグメント化スタックは、スタックが拡張される際に「ホットスプリット」問題を引き起こす可能性がありました。これは、スタックの拡張時に既存のスタックフレームを新しいセグメントにコピーし、スタック内のポインタを更新する必要があるため、一時的な停止やパフォーマンスの低下を招くことがありました。
    *   Go 1.4では、スタックがセグメント化されなくなり、連続スタックが採用されました。これはGo 1.3で導入された変更ですが、Go 1.4のドキュメントでその影響が強調されています。
    *   **メカニズム**: スタックの限界に達すると、より大きな新しいスタックが割り当てられ、ゴルーチンのすべてのアクティブなフレームがそこにコピーされ、スタック内のポインタが更新されます。
    *   **結果**: ホットスプリット問題が解消され、パフォーマンスが一部のケースで顕著に向上し、常に予測可能になりました。
    *   **スタックサイズの最適化**: 連続スタックの採用により、パフォーマンスの問題を引き起こすことなくスタックをより小さく開始できるようになりました。そのため、ゴルーチンのデフォルトの初期スタックサイズは、8192バイトから2048バイトに削減されました（リリース時には4096バイトに引き上げられる可能性も示唆されています）。

3.  **ライトバリアの導入（Go 1.5並行GCの準備）**:
    *   Go 1.5で予定されている並行ガベージコレクタの準備として、ヒープ上のポインタ値への書き込みが関数呼び出し（ライトバリア）を介して行われるようになりました。
    *   **目的**: これにより、GCが実行中にヒープへの書き込みを仲介できるようになります。GCがオブジェクトグラフを走査している最中に、プログラムがポインタを変更しても、GCがその変更を認識し、整合性を保つことができます。
    *   **Go 1.4での影響**: Go 1.4では、この変更自体はプログラムにセマンティックな影響を与えません。しかし、コンパイラと結果的なパフォーマンスをテストするためにこのリリースに含まれました。
    *   **パフォーマンスへの影響**: 新しいライトバリアは、GCの高速化によって得られたパフォーマンス向上を相殺する形で、プログラムの実行速度をわずかに低下させる可能性があります。これは、ライトバリアの実行オーバーヘッドによるものです。

4.  **インターフェース値の実装変更**:
    *   以前のリリースでは、インターフェースは格納される具体的なオブジェクトの型に応じて、ポインタまたは1ワードのスカラー値を直接含むことがありました。
    *   この実装はガベージコレクタにとって問題がありました。GCがポインタと非ポインタを区別する際に複雑さが増すためです。
    *   Go 1.4からは、インターフェース値は常にポインタを保持するようになりました。
    *   **影響**: 実行中のプログラムのほとんどのインターフェース値は元々ポインタであったため、影響は最小限です。しかし、整数などのスカラー値をインターフェースに格納するプログラムでは、スカラー値がヒープに割り当てられ、そのポインタがインターフェース値に格納されるため、より多くのメモリ割り当てが発生する可能性があります。

これらの変更は、Goランタイムの堅牢性、効率性、および将来の拡張性（特に並行GC）を大幅に向上させることを目的としていました。

## コアとなるコードの変更箇所

このコミット自体は、Goランタイムの実際のコードを変更するものではなく、Go 1.4のリリースノートである `doc/go1.4.html` ファイルに、上記のランタイムとパフォーマンスに関する変更点を記述するものです。

具体的には、`doc/go1.4.html` ファイルの以下のセクションに大幅な追記が行われました。

*   `<h2 id="runtime">Changes to the runtime</h2>` の下
*   `<h2 id="performance">Performance</h2>` の下

変更の差分を見ると、主にHTMLの `<p>` タグ内に、Go 1.4のランタイム変更（Go言語への移行、正確なGC、連続スタック、ライトバリア、インターフェース値の変更）とそれらのパフォーマンスへの影響に関する説明が追加されています。

## コアとなるコードの解説

このコミットはドキュメントの変更であるため、直接的な「コアとなるコード」の動作変更はありません。しかし、このドキュメントが解説している「コアとなるコード」の変更は、Goランタイムの以下の部分に及びます。

*   **ガベージコレクタ (GC)**:
    *   GCがスタックをスキャンする際の精度が向上し、完全に正確なGCが実現されました。これにより、ヒープのメモリ使用量が削減されます。
    *   GC自体の処理速度も向上しました。
*   **スタック管理**:
    *   セグメント化スタックから連続スタックへの移行により、スタックの拡張メカニズムが根本的に変更されました。これにより、スタックのホットスプリット問題が解消され、スタックの成長がより効率的かつ予測可能になります。
    *   ゴルーチンの初期スタックサイズが削減され、メモリ効率が向上しました。
*   **ライトバリア**:
    *   コンパイラによって生成されるコードに、ヒープへのポインタ書き込み時にライトバリア関数を呼び出すロジックが追加されました。これは、Go 1.5で導入される並行GCが、GC実行中にヒープの変更を追跡できるようにするための基盤となります。
*   **インターフェースの実装**:
    *   インターフェース値の内部表現が変更され、常にポインタを保持するようになりました。これにより、GCがインターフェース値をより簡単に処理できるようになりますが、スカラー値をインターフェースに格納する場合には追加のメモリ割り当てが発生する可能性があります。

これらの変更は、GoランタイムのC言語部分をGo言語に書き換えるという大規模な作業の一環として行われました。Go言語で書かれたランタイムは、Goコンパイラの最適化（インライン化など）の恩恵を受けることができ、全体的なパフォーマンス向上にも寄与しています。

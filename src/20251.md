# [インデックス 20251] ファイルの概要

このコミットは、GoランタイムにおけるARMv5アーキテクチャのソフトフロートビルドに関するバグ修正です。具体的には、`runtime._sfloat2`関数が、本来レジスタ`R0`で返すべき値を、誤ってスタック上の`LR`（リンクレジスタ）の保存領域に書き込んでいた問題を修正しています。これにより、ARMv5環境での浮動小数点演算の正確な動作が保証されます。

## 変更の背景

この変更は、Go言語のランタイムがARMv5アーキテクチャ上でソフトフロート（ソフトウェア浮動小数点）モードでビルドされる際に発生していた問題を解決するために行われました。

ARMv5プロセッサの多くは、ハードウェア浮動小数点ユニット（FPU）を搭載していません。そのため、浮動小数点演算を行う際には、ソフトウェアによるエミュレーション（ソフトフロート）が必要となります。Goコンパイラは、`GOARM=5`などの環境変数が設定されている場合、このソフトフロートモードをサポートし、浮動小数点演算を処理するために`_sfloat`のようなソフトウェアエミュレータへの呼び出しを挿入します。

問題は、このソフトフロートエミュレーションの一部である`runtime._sfloat2`関数が、その結果を返す際に、ARMの標準的な呼び出し規約に従っていなかったことにありました。ARMの呼び出し規約では、関数の戻り値は通常`R0`レジスタに格納されます。しかし、`runtime._sfloat2`は、誤って戻り値をスタック上の`LR`（リンクレジスタ）の保存領域に書き込んでいました。これにより、`_sfloat2`の呼び出し元が正しい戻り値を取得できず、浮動小数点演算の結果が不正になる、あるいはプログラムがクラッシュするなどの問題が発生していました。

このコミットは、この誤った戻り値の処理を修正し、`runtime._sfloat2`が`R0`レジスタに正しく戻り値を格納するようにすることで、ARMv5ソフトフロートビルドの安定性と正確性を確保することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

*   **ARMアーキテクチャ (特にARMv5)**:
    ARM（Advanced RISC Machine）は、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）プロセクタアーキテクチャです。ARMv5は、古い世代のARMアーキテクチャであり、多くのデバイスでハードウェアFPUを搭載していません。
*   **ソフトフロート (Softfloat) とハードフロート (Hardfloat)**:
    *   **ハードフロート**: プロセッサに専用のFPUが搭載されており、浮動小数点演算をハードウェアで高速に実行する方式です。
    *   **ソフトフロート**: プロセッサにFPUがない、またはFPUを使用しない場合に、浮動小数点演算をソフトウェア（CPUの整数演算命令とロジック）でエミュレートする方式です。ハードフロートに比べて性能は劣りますが、FPU非搭載の環境でも浮動小数点演算を可能にします。
*   **Goランタイム**:
    Go言語のプログラムは、Goランタイム上で動作します。ランタイムは、ガベージコレクション、スケジューリング、メモリ管理、システムコールなど、プログラムの実行に必要な低レベルの機能を提供します。一部のランタイムコードは、パフォーマンスやハードウェアとの直接的なインタラクションのためにアセンブリ言語で記述されています。
*   **アセンブリ言語 (ARMアセンブリ)**:
    アセンブリ言語は、プロセッサが直接実行できる機械語に1対1で対応する低レベルのプログラミング言語です。ARMアセンブリは、ARMプロセッサの命令セットに対応したアセンブリ言語です。
*   **ARMの呼び出し規約 (Calling Convention)**:
    関数（サブルーチン）が呼び出される際に、引数の渡し方、戻り値の受け取り方、レジスタの保存・復元など、関数間のインタフェースを定義するルールです。ARMの標準的な呼び出し規約（AAPCS: ARM Architecture Procedure Call Standard）では、以下のレジスタが重要な役割を果たします。
    *   **R0**: 通常、関数の最初の引数を渡し、関数の戻り値（整数またはポインタ）を格納するために使用されます。
    *   **LR (Link Register, R14)**: `BL` (Branch with Link) 命令によって関数が呼び出された際に、呼び出し元に戻るためのアドレス（リターンアドレス）が自動的に格納されます。関数がさらに別の関数を呼び出す（ネストされた呼び出し）場合、`LR`の値はスタックに保存される必要があります。
    *   **SP (Stack Pointer, R13)**: スタックの現在のトップを指すレジスタです。
*   **スタック**:
    プログラムの実行中に一時的なデータを格納するために使用されるメモリ領域です。関数呼び出しの際には、ローカル変数、レジスタの保存値、リターンアドレスなどがスタックに積まれます（プッシュ）。関数から戻る際には、これらのデータがスタックから取り除かれます（ポップ）。
*   **Goアセンブリのディレクティブ**:
    Go言語のランタイムや標準ライブラリの一部は、Goのアセンブリ言語で記述されています。これらは、Goのツールチェーンによってコンパイルされます。
    *   `TEXT symbol(SB), flags, frame_size-arg_size`: 関数の定義を開始するディレクティブです。
        *   `symbol(SB)`: 関数のシンボル名です。`SB`は「Static Base」を意味し、グローバルなシンボルであることを示します。
        *   `flags`: 関数の特性を示すフラグです。`NOSPLIT`は、スタックの拡張チェックを行わないことを示します（通常、非常に短い関数や、スタックの拡張が不要な低レベル関数で使用されます）。
        *   `frame_size`: 関数のスタックフレームサイズです。関数が使用するスタック領域の合計サイズを示します。
        *   `arg_size`: 関数が引数として受け取るバイト数です。
    *   `MOVW`: 32ビットワード（4バイト）を移動する命令です。
    *   `MOVM.IA.W`: 複数のレジスタをメモリに一括で保存する命令です。`IA`は「Increment After」を意味し、アドレスを書き込み後にインクリメントします。
    *   `MRS`: CPSR（Current Program Status Register）などの特殊レジスタの値を汎用レジスタに移動する命令です。
    *   `BL`: Branch with Link命令。指定されたアドレスにジャンプし、現在のPC（プログラムカウンタ）の次の命令のアドレスを`LR`レジスタに保存します。これにより、呼び出し元に戻ることができます。

## 技術的詳細

このバグは、GoランタイムのARMアセンブリコード、具体的には`src/pkg/runtime/vlop_arm.s`ファイル内の`_sfloat`関数（`runtime._sfloat2`へのトランポリン関数）の実装に起因していました。

`_sfloat`関数は、`runtime._sfloat2`を呼び出す前に、`LR`を含む複数のレジスタと`CPSR`（Current Program Status Register）をスタックに保存します。これは、`_sfloat2`がこれらのレジスタを変更する可能性があるため、呼び出し元のコンテキストを保護するためです。

問題は、`runtime._sfloat2`がその計算結果を返す際に、ARMの標準的な戻り値レジスタである`R0`ではなく、スタック上の`LR`の保存領域に値を書き込んでしまっていたことです。

元のコードでは、`_sfloat`関数はスタックフレームサイズを`$64-0`と定義しており、これは4つの引数、14個の保存されたレジスタ（R0-R13）、およびCPSRの合計サイズに対応していました。`LR`は`R14`として扱われ、スタックに保存されていました。

`_sfloat2`が`LR`の保存領域に結果を書き込むと、`_sfloat`が`_sfloat2`から戻った後、`LR`の保存領域から`LR`を復元しようとした際に、誤って`_sfloat2`の計算結果を`LR`としてロードしてしまい、プログラムの実行フローが破壊される可能性がありました。

この修正は、以下の2つの主要な変更によってこの問題を解決しています。

1.  **スタックフレームサイズの調整**: `_sfloat`関数のスタックフレームサイズを`$64-0`から`$68-0`に増やしました。これは、`_sfloat2`の戻り値を格納するための追加の4バイト（1ワード）の領域をスタックに確保するためです。コメントには「+ return value」と追記されています。
2.  **戻り値の`R0`への移動**: `BL runtime·_sfloat2(SB)`の呼び出し後、スタック上の新しい領域（`68(R13)`）から`_sfloat2`の戻り値を読み込み、それを`R0`レジスタに移動する`MOVW 68(R13), R0`命令を追加しました。これにより、`_sfloat2`の実際の戻り値が、ARMの呼び出し規約に従って`R0`に格納されるようになります。

この修正により、`_sfloat2`がスタック上の`LR`保存領域に誤って書き込む問題が解消され、`_sfloat`が`_sfloat2`から戻った後も、`LR`が正しく復元され、`R0`に`_sfloat2`の計算結果が格納されるようになります。

## コアとなるコードの解説

変更は`src/pkg/runtime/vlop_arm.s`ファイル内の`_sfloat`関数に集中しています。

1.  **`TEXT _sfloat(SB), NOSPLIT, $64-0` から `TEXT _sfloat(SB), NOSPLIT, $68-0` への変更**:
    *   これは`_sfloat`関数のスタックフレームサイズを定義している部分です。
    *   元の`$64-0`は、4つの引数、14個の保存されたレジスタ（R0-R13）、およびCPSR（Current Program Status Register）の合計サイズ（4 + 14*4 + 4 = 64バイト）を意味していました。
    *   新しい`$68-0`は、この64バイトに加えて、`runtime._sfloat2`の戻り値を格納するための追加の4バイト（1ワード）の領域をスタックに確保することを示しています。コメント「+ return value」が追加され、この目的が明確化されています。

2.  **`MOVW $68(R13), R1` から `MOVW $72(R13), R1` への変更**:
    *   この行は、スタックフレームのサイズを調整するために使用されるオフセットを計算しています。
    *   スタックフレームサイズが64バイトから68バイトに増えたため、関連するオフセットも4バイト分ずらす必要があります。`$68(R13)`はスタックポインタ`R13`からのオフセット68バイトを意味していましたが、新しいフレームサイズに合わせて`$72(R13)`に調整されました。これは、スタック上の特定の場所を指すためのオフセット計算の一部です。

3.  **`BL runtime·_sfloat2(SB)` の直後に `MOVW 68(R13), R0` を追加**:
    *   これがこのコミットの最も重要な変更点です。
    *   `BL runtime·_sfloat2(SB)`命令は、`runtime._sfloat2`関数を呼び出します。
    *   追加された`MOVW 68(R13), R0`命令は、`runtime._sfloat2`がスタック上のオフセット`68(R13)`に書き込んだ戻り値を、ARMの呼び出し規約で戻り値が格納されるべき`R0`レジスタに移動します。
    *   これにより、`_sfloat`の呼び出し元は、`R0`レジスタから`runtime._sfloat2`の正しい計算結果を取得できるようになります。

これらの変更により、`_sfloat`関数は`runtime._sfloat2`の戻り値を正しく処理し、ARMv5ソフトフロート環境での浮動小数点演算の信頼性が向上します。

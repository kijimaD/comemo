# [インデックス 22061] ファイルの概要

このコミットは、Go言語の`crypto/md5`および`crypto/sha1`パッケージのARMアセンブリコードにおけるスタックポインタ（SP）の参照に関する修正です。具体的には、以前の変更によってスタックフレーム外にデータが書き込まれる問題が発生していたため、SP参照を正しい形式に「復元」することで、データの配置を修正しています。

## 変更の背景

このコミットの背景には、以前の変更セット（Change-Id: `CL 5120`）があります。`CL 5120`は「crypto/md5, crypto/sha1: use assembly on arm64」というタイトルで、`crypto/md5`および`crypto/sha1`パッケージのパフォーマンスを向上させるために、ARM64アーキテクチャ向けのアセンブリコードを導入しました。

しかし、このアセンブリコードの導入において、スタックポインタ（SP）の参照方法に問題が生じました。具体的には、データが「スタックフレーム内」に書き込まれるべきところが、「スタックフレームの下（below the stack frame）」に書き込まれるように変更されてしまったとのことです。これは、Goランタイムがスタックフレームを管理する方法や、ガベージコレクションがスタック上のオブジェクトを追跡する方法と矛盾する可能性があり、潜在的なバグやクラッシュの原因となり得ます。

本コミット（22061）は、`CL 5120`の作者であるRuss Cox自身が、その変更後に発見した問題に対する修正として行われました。目的は、SP参照を正しく「復元」し、データが再びスタックフレーム内に適切に配置されるようにすることです。

## 前提知識の解説

### GoアセンブリとARMアーキテクチャにおけるスタックポインタ (SP)

Go言語は、特定のパフォーマンスが要求される箇所でアセンブリ言語を使用します。ARMアーキテクチャにおけるGoのアセンブリでは、スタックポインタ（SP）の扱いが重要です。

1.  **仮想SPとハードウェアSP (R13):**
    *   Goのアセンブラでは、`SP`は「仮想スタックポインタ」を指す擬似レジスタとして扱われます。これは、ローカル変数や関数呼び出しのために準備された引数にアクセスするために使用されます。この仮想SPは、現在のローカルスタックフレームの最も高いアドレスを指し、ローカル変数への参照は通常、この仮想SPからの負のオフセット（例: `x-8(SP)`）を使用します。
    *   一方、ARMアーキテクチャには実際のハードウェアスタックポインタレジスタが存在し、これは通常`R13`としてアクセスされます。
    *   Goアセンブリでは、`SYMBOLNAME+offset(SP)` の形式はGoの仮想SPレジスタを参照し、ローカル変数に使用されます。
    *   単に `offset(SP)` の形式は、ネイティブのARM64のハードウェアSPレジスタを参照します。
    *   この違いは非常に重要で、`x-8(SP)` と `-8(SP)` は異なるメモリ位置を参照します。前者は仮想SP擬似レジスタを参照し、後者はハードウェアのSPレジスタを参照します。

2.  **スタックフレーム:**
    *   スタックは、関数呼び出しに関する情報を格納するためのLIFO（後入れ先出し）データ構造です。
    *   関数が呼び出されると、新しいスタックフレームがスタックに追加され、関数が戻るとそのフレームは破棄されます。
    *   スタックフレームには、関数のローカル変数、引数、戻りアドレスなどが格納されます。
    *   SPは、常にスタックの現在のトップを指します。ローカル変数は関数エントリ時に作成され、関数が戻るときに破棄され、SPはそれに応じて移動します。
    *   Goランタイムはスタックのリサイズを実装しており、任意の関数呼び出し中にスタックポインタが変更される可能性があります。そのため、スタックデータへのポインタをローカル変数に保持すべきではありません。

### `R13`と`SP`の使い分け

Goのアセンブリでは、`R13`はARMのハードウェアSPレジスタを直接指しますが、`SP`はGoランタイムが管理する抽象化されたスタックポインタを指します。通常、Goのアセンブリコードでは、Goランタイムのスタック管理と整合性を保つために、ローカル変数やスタックフレーム内のデータへのアクセスには`SP`擬似レジスタを使用することが推奨されます。`R13`を直接使用すると、Goランタイムのスタックフレームの構造やガベージコレクションのメカニズムと衝突する可能性があります。

## 技術的詳細

このコミットの技術的な核心は、`CL 5120`で導入されたARMアセンブリコードが、スタック上のデータ配置に関してGoランタイムの期待する規約から逸脱してしまった点を修正することにあります。

`CL 5120`では、`crypto/md5`と`crypto/sha1`のARMアセンブリ実装において、スタックフレーム内のローカル変数や一時バッファへの参照方法が変更されました。元のコミットメッセージにある「The rewrite there changed the code from writing to the stack frame to writing below the stack frame」という記述は、この変更が、本来スタックフレーム内に確保されるべき領域にデータを書き込む代わりに、スタックフレームの境界外（より低いアドレス、つまりスタックの成長方向とは逆の方向）にデータを書き込むようになってしまったことを示唆しています。

このような問題が発生すると、以下のような影響が考えられます。

1.  **ガベージコレクションの誤動作:** Goのガベージコレクタは、スタックフレームの境界を認識し、その内部にあるポインタをスキャンして到達可能なオブジェクトを特定します。スタックフレーム外にデータが書き込まれると、ガベージコレクタがそのデータを正しく認識できず、誤って解放してしまったり、逆に解放すべきでないメモリを保持し続けたりする可能性があります。
2.  **スタックオーバーフロー/アンダーフロー:** スタックフレームの規約を破ることで、スタックの境界チェックが正しく機能しなくなり、スタックオーバーフローやアンダーフローといったメモリ破壊を引き起こす可能性があります。
3.  **未定義の動作:** 予期せぬメモリ領域への書き込みは、プログラムのクラッシュや予測不能な動作につながります。

このコミットは、これらの問題を解決するために、アセンブリコード内のSP参照を「復元」しています。具体的には、`#define`ディレクティブで定義されていたスタック上のオフセット計算を修正し、さらにコード内で`R13`レジスタを直接使用してスタック上の位置を計算していた箇所を、Goアセンブラの`SP`擬似レジスタを使った相対参照に戻しています。これにより、データがGoランタイムが管理するスタックフレームの範囲内に正しく配置されるようになります。

例えば、`p_end(R13)`のような記述は、ハードウェアSP (`R13`) からのオフセットでメモリを参照していましたが、これを`p_end`というシンボル名（Goアセンブラが仮想SPからのオフセットとして解決する）に置き換えることで、Goランタイムのスタック管理規約に準拠させています。

## コアとなるコードの解説

上記の変更は、主に以下の2つの側面でスタックポインタの参照を修正しています。

1.  **`#define` ディレクティブの修正:**
    *   以前は、`p_end`, `p_data`, `buf`, `w_buf`, `saved` といったスタック上のオフセットを定義する際に、`-4`, `-8` のような直接的な負のオフセット値を使用していました。これは、ハードウェアSP (`R13`) からの相対オフセットとして解釈される可能性がありました。
    *   修正後は、`end-4(SP)`, `data-8(SP)`, `buffer-(8+4*16)(SP)` のように、シンボル名（`end`, `data`, `buffer`, `abcde`）と`SP`擬似レジスタを組み合わせた形式に変更されています。この形式は、GoアセンブラがGoランタイムのスタックフレーム規約に従って、仮想SPからの正しいオフセットを計算するように指示します。これにより、これらの変数がGoのスタックフレーム内に正しく配置されることが保証されます。

2.  **`R13` を使用した直接参照の削除と `SP` 参照への置き換え:**
    *   変更前は、`MOVW Rt0, p_end(R13)` や `MOVW $buf(R13), Rtable` のように、`R13`（ハードウェアSP）を明示的に使用してスタック上のメモリ位置にアクセスしていました。
    *   修正後は、`MOVW Rt0, p_end` や `MOVW $buf, Rtable` のように、`R13`の記述が削除され、`#define`で定義されたシンボル名が直接使用されています。これにより、Goアセンブラがこれらのシンボルを仮想SPからのオフセットとして解決し、Goランタイムのスタック管理と整合性の取れたアクセスが行われるようになります。

これらの変更により、`crypto/md5`と`crypto/sha1`のARMアセンブリコードは、Goランタイムのスタックフレーム規約に完全に準拠するようになり、以前の変更で発生していた「スタックフレームの下への書き込み」という問題が解消されました。これにより、ガベージコレクションの正確性が保たれ、プログラムの安定性が向上します。
